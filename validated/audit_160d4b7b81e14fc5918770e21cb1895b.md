## Analysis

The H-6 report's root cause is a **value-tracking assumption tied to call context/position that breaks under a non-standard code path** (ETH as secondary token instead of primary), causing funds to be silently dropped instead of forwarded. The reachable Cosmos EVM analog is in the shared `BalanceHandler` mechanism used by every stateful precompile (`x/erc20`, `ics20`, `werc20`, `staking`, `distribution`, `gov`, `slashing`, `bank`), which makes the same category of assumption: that the slice of Cosmos SDK events recorded between "before" and "after" a precompile call belongs exclusively to that single call.

### Title
Balance-changing bank events are double-applied to the EVM StateDB during nested/recursive precompile calls, causing EVM-balance duplication relative to bank-keeper balances - (File: precompiles/common/precompile.go, precompiles/common/balance_handler.go)

### Summary
`Precompile.runNativeAction` snapshots `len(ctx.EventManager().Events())` as `prevEventsLen` before executing a precompile's native action, and afterwards replays only `events[prevEventsLen:]` into the EVM `StateDB` via `BalanceHandler.AfterBalanceChange`. [1](#0-0)  This design assumes the recorded event window is exclusively produced by the current precompile invocation. When a precompile's native action itself triggers another EVM call that lands on a (possibly the same) stateful precompile — a nested/recursive precompile call sharing the same `sdk.Context`/`EventManager` — the inner call's own `BeforeBalanceChange`/`AfterBalanceChange` cycle already consumes and applies a sub-range of those events to the StateDB. When control returns to the outer call, the outer's `AfterBalanceChange` re-processes the full range starting from its own (earlier) `prevEventsLen`, which still includes the events the inner call already applied, applying the same `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` deltas to `StateDB.AddBalance`/`SubBalance` a second time. [2](#0-1) 

### Finding Description
`BalanceHandler.BeforeBalanceChange` simply records the current event count; `AfterBalanceChange` iterates `events[bh.prevEventsLen:]` and, for `EventTypeCoinSpent`/`EventTypeCoinReceived`/`EventTypeFractionalBalanceChange`, mutates `stateDB.SubBalance`/`AddBalance` directly. [3](#0-2)  This is invoked around every native action:
```
balanceHandler.BeforeBalanceChange(ctx)
bz, err = action(ctx)
...
balanceHandler.AfterBalanceChange(ctx, stateDB)
``` [1](#0-0) 

Several precompile `action` implementations call back into the EVM (e.g. `evmKeeper.CallEVMWithData`) from within their own native-action execution, which can re-enter the precompile dispatch path and trigger another `runNativeAction`/`BalanceHandler` cycle using the *same* `ctx.EventManager()`. The project's own integration tests document and reproduce exactly this scenario:

> "BalanceHandlerTestSuite tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB." [4](#0-3) 

The accompanying `debug` precompile explicitly demonstrates a self-recursive precompile call via `p.evmKeeper.CallEVMWithData(ctx, p.Address(), &caller, data, true, nil)` invoked from inside `Call0`, i.e. from inside the outer `action` closure that the outer `BalanceHandler` is wrapping. [5](#0-4)  Any precompile that performs a bank-affecting operation (`SendCoins`, `MintCoins`, etc., which emit `CoinSpent`/`CoinReceived` events) and, within the same call, performs another EVM call that reaches a stateful precompile doing its own bank operation, will have the inner precompile's bank events double-counted by the outer `AfterBalanceChange`.

Because the exact same class of "index/position/window assumption breaks in a non-primary code path" defect as H-6 (there: primary-token-only `msgValue` assumption; here: single-call-exclusive event-window assumption) leads to a **StateDB balance value that no longer matches the true bank-keeper-backed value**, this is a genuine analog: instead of losing value (as in H-6), the EVM-visible balance can be duplicated relative to the actual spendable bank balance.

### Impact Explanation
If StateDB balances (which back `eth_getBalance`, EVM `CALL`/`transfer` semantics, and any DeFi contract logic built on top of precompile-mediated token balances such as `werc20`/`erc20`/`ics20`) get incremented twice for a single real bank-side credit, an attacker who can trigger nested precompile calls (e.g., a contract wrapping/depositing native tokens that also triggers a secondary precompile action, or IBC/ERC20 conversion flows that internally invoke `CallEVMWithData`) can create EVM-balance values that exceed what is actually escrowed/held in the bank module. This is unauthorized duplication of spendable value across EVM balances vs. native/bank balances — an irreversible accounting-invariant break matching the Critical impact gate (duplication/inflation of spendable user value between native and EVM-visible balances).

### Likelihood Explanation
Likelihood depends on finding/crafting a real production call chain (not just the debug precompile) where a precompile's bank-affecting action also triggers, within the same native-action execution, another EVM call that reaches a stateful precompile with its own `BalanceHandler`-wrapped bank operation. The repository's own test explicitly recreates this via nested `CallEVMWithData` calls and confirms desync behavior, showing the mechanism is real and reachable through ordinary contract-call composition, not a privileged path. However, I was not able to fully confirm within the available tool budget whether any of the *production* precompiles (as opposed to the test-only `debug` precompile) currently have a call chain that actually re-enters another `BalanceHandler`-guarded precompile mid-action, or whether the test in question is asserting that the current code is already fixed/protected (the assertions on `res.Events` count/`debug_count` could represent either a demonstration of the bug or a regression guard confirming it no longer occurs). This should be verified with a live/dynamic trace in a full Devin session before treating it as confirmed-exploitable in production precompiles.

### Recommendation
- Make `BalanceHandler` reentrancy-safe: instead of only recording `len(events)` before/after, track and mark specific events as "consumed" (e.g., by index or a processed-set) so that a nested call's already-applied events cannot be reprocessed by an outer call's `AfterBalanceChange`.
- Alternatively, maintain a single, call-stack-aware `BalanceHandler` per top-level EVM transaction/precompile-call-tree (e.g., passed down through nested `CallEVMWithData` invocations) rather than instantiating window-based tracking independently at every nesting depth.
- Add an explicit reentrancy guard/depth counter in `runNativeAction` so nested precompile calls either skip `BalanceHandler` processing (deferring to the outermost handler) or assert on and reject unexpected overlaps.
- Extend `evmd/tests/integration/balance_handler/balance_handler_test.go` coverage to production precompiles (`ics20`, `erc20`, `werc20`, `staking`, `distribution`) with genuine nested call chains, and add an invariant check comparing `bankKeeper` balances against `StateDB` balances after any nested-precompile transaction.

### Proof of Concept
Conceptual PoC (mirrors the existing `BalanceHandlerTestSuite.TestRecursivePrecompileCallsWithDebugPrecompile`):
1. Deploy a caller contract that invokes a stateful precompile method performing a bank transfer (emits `CoinSpent`/`CoinReceived`).
2. From within that precompile's native action, trigger `evmKeeper.CallEVMWithData` back into another (or the same) stateful precompile that performs its own bank transfer emitting further `CoinSpent`/`CoinReceived` events, as done in `debug.Call0` → `debug.Call1`. [6](#0-5) 
3. After the outer call finishes, compare the resulting `StateDB.GetBalance` for the involved addresses against the true `BankKeeper.GetBalance`; the existing test infrastructure in `evmd/tests/integration/balance_handler/balance_handler_test.go` is set up specifically to detect and measure this desync. [7](#0-6) 

I was not able to fully validate an end-to-end exploit using only production (non-debug) precompiles within the available investigation; this would need to be confirmed with a live Devin session tracing actual nested-call paths (e.g., `x/erc20` keeper calls into EVM from within an `ics20`/`werc20` precompile action) before treating this as a fully proven, in-scope Critical finding rather than a strongly-suggested one based on the repository's own acknowledged test.

// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

// AfterBalanceChange processes the recorded events and updates the stateDB accordingly.
// It handles the bank events for coin spent and coin received, updating the balances
// of the spender and receiver addresses respectively.
//
// NOTES: Balance change events involving BlockedAddresses are bypassed.
// Native balances are handled separately to prevent cases where a bank coin transfer
// initiated by a precompile is unintentionally overwritten by balance changes from within a contract.

// Typically, accounts registered as BlockedAddresses in app.go—such as module accounts—are not expected to receive coins.
// However, in modules like precisebank, it is common to borrow and repay integer balances
// from the module account to support fractional balance handling.
//
// As a result, even if a module account is marked as a BlockedAddress, a keeper-level SendCoins operation
// can emit an x/bank event in which the module account appears as a spender or receiver.
// If such events are parsed and used to invoke StateDB.AddBalance or StateDB.SubBalance, authorization errors can occur.
//
// To prevent this, balance changes from events involving blocked addresses are not applied to the StateDB.
// Instead, the state changes resulting from the precompile call are applied directly via the MultiStore.
func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case precisebanktypes.EventTypeFractionalBalanceChange:
			addr, err := ParseAddress(event, precisebanktypes.AttributeKeyAddress)
			if err != nil {
				return fmt.Errorf("failed to parse address from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}
			if bh.bankKeeper.BlockedAddr(addr) {
				// Bypass blocked addresses
				continue
			}

			delta, err := ParseFractionalAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}

			deltaAbs, err := utils.Uint256FromBigInt(new(big.Int).Abs(delta))
			if err != nil {
				return fmt.Errorf("failed to convert delta to Uint256: %w", err)
			}

			if delta.Sign() == 1 {
				stateDB.AddBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			} else if delta.Sign() == -1 {
				stateDB.SubBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			}

		default:
			continue
		}
	}

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug

func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)

	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))

		input,         // data

	)

		}

	s.chain.NextBlock()
}
