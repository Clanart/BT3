## Title
Unauthenticated `signer` field in ISMP `RequestMessage`/`ResponseMessage` lets any deliverer self-attest relayer identity that later authorizes fee/reward payouts - (File: `modules/ismp/core/src/handlers/request.rs`, `modules/pallets/ismp/src/host.rs`, `modules/pallets/relayer/src/accumulate.rs`)

### Summary
The external report's core defect is that a backend accepts caller-supplied identity/role parameters (`userId`, `levelName`) at face value, with no proof that the caller is entitled to that identity, and then issues a credential based on those unverified parameters. The Hyperbridge analog is the `signer: Vec<u8>` field on `RequestMessage`/`ResponseMessage`: it is documented as advisory ("Ideally should be their account identifier"), passed straight from the message to `IsmpHost::store_request_receipt`/`store_response_receipt`, and persisted verbatim into `RequestReceipts[commitment]` / `ResponseReceipts[commitment]` — the exact record that downstream fee-accumulation and reward-claim logic later trusts as "who delivered this."

### Finding Description
On the EVM side, relayer attribution is cryptographically bound: `HandlerV2.handlePostRequests` calls `host.dispatchIncoming(leaf.request, _msgSender())`, so `_requestReceipts[commitment] = relayer` can only ever be the transaction's real sender [1](#0-0) [2](#0-1) .

On the Substrate side, the equivalent identity is not derived from the transaction origin at all — it is an arbitrary caller-supplied `Vec<u8>` field on the message itself: [3](#0-2) 

`request::handle` forwards this untrusted field straight into the receipt store with no signature or ownership check performed by the ISMP core handler: [4](#0-3) 

The pallet-level host implementation persists it into the child trie as the permanent "who delivered this" record (`extract_signer` reformats the bytes but the value still originates entirely from the attacker-controlled `msg.signer` parameter, not from any authenticated origin): [5](#0-4) [6](#0-5) 

This `RequestReceipts[commitment]` value is exactly what later gates money movement in two places:
1. `pallet-relayer::accumulate` reads it (via a state proof of the destination chain) as `delivery_address`, the account credited with the source-chain relayer fee [7](#0-6) .
2. `outbound_request_delivery_claim` reads it via `decode_receipt_relayer` as `delivered_by`, and pays the `OutboundRequestDeliveryReward` to whoever's claim signature recovers to that value [8](#0-7) [9](#0-8) .

Because `msg.signer` is never checked by the core `RequestMessage`/`ResponseMessage` handler against any cryptographic proof of who actually delivered the message (unlike the EVM path's hard-bound `_msgSender()`), the identity written into the receipt trie is a purely self-declared value at message-submission time — structurally the same class of bug as the SumSub endpoint trusting a client-supplied `userId`/`levelName` with no authorization check binding it to the caller.

### Impact Explanation
`RequestReceipts`/`ResponseReceipts` are the canonical, state-proven record consumed by relayer-fee accumulation (`accumulate_fees`) and the hyperbridge-originated-request reward claim (`claim_outbound_request_delivery_reward`). Since the identity stored there is not bound to the actual message deliverer by any signature check at the ISMP handler layer, whoever calls the unsigned `handle_unsigned`/request-delivery extrinsic on the substrate side controls which bytes end up as the "delivering relayer" for that commitment, independent of whether those bytes correspond to a keypair they hold. This weakens the chain of custody that `accumulate_fees`/`outbound_request_delivery_claim` rely on to decide "wrong beneficiary or amount" and "one-time receipt handling," directly touching the Impact Gate's relayer-reward and bandwidth-accounting money-movement paths.

### Likelihood Explanation
Delivering a `RequestMessage`/`ResponseMessage` (submitting a valid membership/state proof for an already-finalized commitment) is a public, unprivileged action available to anyone with the state proof — it is not a "malicious relayer/prover" precondition, it is the ordinary permissionless self-relay flow the docs describe. The `signer` field itself carries no independent verification requirement in `request::handle`/`response::handle`, so the gap is reachable by any unprivileged caller who can construct the proof, which is the normal relayer/self-relay use case.

### Recommendation
Bind the `signer` field cryptographically to the caller before it is persisted as a `RequestReceipts`/`ResponseReceipts` value: either require `signer` to be a `Signature` over the request/response batch (as `messaging-incentives::relayer_for` already does for its own separate reputation-mint path) and verify it inside `request::handle`/`response::handle` before calling `store_request_receipt`, or derive the credited identity from the actual extrinsic's signed origin the same way the EVM host derives it from `_msgSender()`. Confirm and, if necessary, harden `extract_signer` in `modules/pallets/ismp/src/host.rs` so it cannot pass through an unverified value into `RequestReceipts`.

### Proof of Concept
1. Attacker observes a hyperbridge-originated `PostRequest` with a state/membership proof available (any post-finality window).
2. Attacker submits the unsigned `RequestMessage` extrinsic (`ensure_none` origin) with `signer` set to an arbitrary 32/20-byte value of their choosing (self-generated keypair, requiring no ownership proof at delivery time).
3. `request::handle` stores that value into `RequestReceipts[commitment]` via `store_request_receipt` with no signature check [10](#0-9) .
4. Attacker later submits `OutboundRequestDeliveryClaim`/`WithdrawalProof` with a signature matching the self-chosen `signer` value, which `decode_receipt_relayer`/`accumulate` accept as proof of delivery, releasing the treasury reward/accumulated fee to the attacker's chosen payee — without the message ever having been verifiably delivered by a signed, identity-bound relayer transaction the way the EVM path enforces via `_msgSender()`.

**Note:** the exact byte-level behavior of `extract_signer` (whether it performs any additional format validation) could not be fully confirmed from the indexed code; a Devin session with full repository access should verify `extract_signer`'s implementation in `modules/pallets/ismp/src/host.rs` before treating this as final.

	fn store_request_receipt(&self, req: &Request, signer: &Vec<u8>) -> Result<Vec<u8>, Error> {
		let signer = extract_signer(signer)?;

		let hash = hash_request::<Self>(req);
		child_trie::RequestReceipts::<T>::insert(hash, &signer);
		Ok(signer)
	}

	fn store_response_receipt(
		&self,
		res: &GetResponse,
		signer: &Vec<u8>,
	) -> Result<Vec<u8>, Error> {
		let signer = extract_signer(signer)?;

		let hash = hash_request::<Self>(&res.request());
		let response = hash_response::<Self>(&res);
		child_trie::ResponseReceipts::<T>::insert(
			hash,
			ResponseReceipt { response, relayer: signer.clone() },
		);
		Ok(signer)
	}

impl<T: Config> Pallet<T> {
	/// Decode a proven `RequestReceipts[commitment]` value into the delivering
	/// relayer's bytes. EVM stores the address RLP encoded, substrate stores the
	/// signer bytes or a signature to recover the signer from. Used by both fee
	/// accumulation and the outbound request delivery claim.
	pub fn decode_receipt_relayer(state_id: StateMachine, raw: &[u8]) -> Result<Vec<u8>, Error<T>> {
		match state_id {
			s if crate::is_pharos(&s) =>
				if raw.len() == 32 {
					Ok(Address::from_slice(&raw[12..]).0.to_vec())
				} else {
					Err(Error::<T>::ProofValidationError)
				},
			s if s.is_evm() => {
				use alloy_rlp::Decodable;
				Ok(Address::decode(&mut &*raw)
					.map_err(|_| Error::<T>::ProofValidationError)?
					.0
					.to_vec())
			},
			s if s.is_substrate() => {
				use codec::Decode;
				let bytes =
					<Vec<u8>>::decode(&mut &*raw).map_err(|_| Error::<T>::ProofValidationError)?;
				Ok(if bytes.len() > 32 {
					Signature::decode(&mut &*bytes)
						.map_err(|_| Error::<T>::SignatureDecodingError)?
						.signer()
				} else {
					bytes
				})
			},
			_ => Err(Error::<T>::MismatchedStateMachine),
		}
	}
