### Title
Keyring status debug log bypasses `redact_sensitive_data()` and can leak the user's passphrase hint to the daemon log - (File: `chia/daemon/server.py`)

### Summary
The Chia daemon defines a redaction helper, `redact_sensitive_data()`, specifically to strip credential-like fields (`pass`, `key`, `secret`, `mnemonic`) before any daemon message content is written to the debug log [1](#0-0) . This redaction is applied to inbound/outbound WebSocket message logging [2](#0-1) , but `WebSocketServer.keyring_status()` constructs its own response dict and logs it directly with `self.log.debug(f"Keyring status: {response}")`, never routing it through `redact_sensitive_data()` [3](#0-2) . This is the same bug class as CVE-2025-30205: a helper meant to scrub sensitive fields from logs exists, but one specific instrumentation call site was never wired to it, so debug-level logging leaks credential-adjacent data.

### Finding Description
`keyring_status()` builds a response dict that includes `passphrase_hint`, which comes directly from `Keychain.get_master_passphrase_hint()` (a user-supplied string that often contains fragments of, or clues strongly correlated with, the keyring master passphrase) [4](#0-3) . Right after building the response it logs the raw dict with `self.log.debug(f"Keyring status: {response}")`, with an explicit comment "Help diagnose GUI launch issues" showing this was intentional but unreviewed instrumentation [5](#0-4) .

Every other debug-log call path that handles daemon message payloads is required to pass through `redact_sensitive_data()` per the project's own documentation of this exact security control [6](#0-5) , and the dedicated regression test `test_message_logging_redaction` proves the intended behavior for the generic message path (`password`, `private_key`, `mnemonic`, `passphrase`, etc. all become `***<redacted>***`) [7](#0-6) . `keyring_status()`'s direct `self.log.debug(f"Keyring status: {response}")` call is outside that protected path, so `passphrase_hint` is written to the log verbatim at DEBUG level whenever any RPC/GUI client queries keyring status — this mirrors kanidm-provision's flaw where a specific instrumented function bypassed the intended credential-scrubbing logic.

### Impact Explanation
Any local process able to reach the daemon's `keyring_status` command (used routinely by the GUI and CLI at startup and on passphrase-related flows) will trigger a DEBUG-level log line containing the plaintext passphrase hint. Passphrase hints are commonly close approximations of, or strong clues to, the actual master passphrase (that's their purpose), so this materially weakens the confidentiality of the keyring passphrase and can be combined with other information to defeat the keyring's protection. The CHANGELOG entry for a related earlier incident already acknowledges that DEBUG logging is a known risk area for passphrase exposure in this codebase [8](#0-7) , confirming this class of leak has occurred here before and is inadequately covered by the existing redaction test suite, which only exercises the generic message-received path.

### Likelihood Explanation
Exploitation requires no special privilege beyond the ability to issue an authorized daemon/RPC request (e.g., a local GUI, wallet UI, or any authenticated local RPC caller) and DEBUG logging enabled — a normal, supported configuration, not an artificially contrived one. `keyring_status` is called routinely (e.g., after `unlock_keyring()` to notify `wallet_ui`) [9](#0-8) , making the leak trigger under everyday operation, not merely on rare/error code paths.

### Recommendation
Route the `keyring_status()` debug log through `redact_sensitive_data()` (or otherwise omit `passphrase_hint` from the logged representation) so it receives the same protection as every other debug-logged daemon payload, e.g.:
```python
self.log.debug(f"Keyring status: {redact_sensitive_data(response)}")
```
Add a regression test analogous to `test_message_logging_redaction` that specifically exercises `keyring_status()` logging to prevent recurrence.

### Proof of Concept
1. Start the daemon with `KANIDM`-style debug logging enabled (`log_level: DEBUG`, analogous to Chia's `chia_logging` debug level).
2. Set a master passphrase with a hint via `set_keyring_passphrase` (`passphrase_hint` field) [10](#0-9) .
3. From any authorized local RPC/GUI client, call the `keyring_status` daemon command [11](#0-10) .
4. Inspect the daemon log file: the line `Keyring status: {...'passphrase_hint': '<hint value>'...}` appears in cleartext, unlike inbound WebSocket message logs which are redacted per `test_message_logging_redaction` [2](#0-1) .

```python
def redact_sensitive_data(obj: Any, redaction_triggers: Collection[str] = ("pass", "key", "secret", "mnemonic")) -> Any:
    """Recursively redact sensitive data from nested dictionaries."""
    if isinstance(obj, dict):
        return {
            key: "***<redacted>***"
            if any(trigger.casefold() in key.casefold() for trigger in redaction_triggers)
            else redact_sensitive_data(value, redaction_triggers)
            for key, value in obj.items()
        }
    else:
        return obj
```

```python
    async def set_keyring_passphrase(self, websocket: WebSocketResponse, request: dict[str, Any]) -> dict[str, Any]:
        success: bool = False
        error: str | None = None
        current_passphrase: str | None = None
        new_passphrase: str | None = None
        passphrase_hint: str | None = request.get("passphrase_hint", None)
        save_passphrase: bool = request.get("save_passphrase", False)

        if using_default_passphrase():
            current_passphrase = default_passphrase()

        if Keychain.has_master_passphrase() and not current_passphrase:
            current_passphrase = request.get("current_passphrase", None)
            if type(current_passphrase) is not str:
                return {"success": False, "error": "missing current_passphrase"}

        new_passphrase = request.get("new_passphrase", None)
        if type(new_passphrase) is not str:
            return {"success": False, "error": "missing new_passphrase"}

        if not Keychain.passphrase_meets_requirements(new_passphrase):
            return {"success": False, "error": "passphrase doesn't satisfy requirements"}

        try:
            assert new_passphrase is not None  # mypy, I love you
            Keychain.set_master_passphrase(
                current_passphrase,
                new_passphrase,
                passphrase_hint=passphrase_hint,
                save_passphrase=save_passphrase,
            )
```
