### Title
Daemon RPC `unlock_keyring`/`validate_keyring_passphrase` allow unbounded remote brute-force of the keyring master passphrase - (File: chia/daemon/server.py)

### Summary
`chia/daemon/server.py`'s `WebSocketServer` exposes `unlock_keyring()` and `validate_keyring_passphrase()` as daemon websocket RPC commands that any connected daemon RPC client can invoke repeatedly with no attempt-count throttling, lockout, or delay enforced server-side.

### Finding Description
`unlock_keyring()` [1](#0-0)  and `validate_keyring_passphrase()` [2](#0-1)  each call `Keychain.master_passphrase_is_valid(key, force_reload=True)` directly on every invocation and return a simple success/failure boolean, with no per-connection or global counter, delay, or lockout applied inside `WebSocketServer`.

The only place `MAX_RETRIES`/lockout logic (`FAILED_ATTEMPT_DELAY`, `KeychainMaxUnlockAttempts`) exists is in the interactive CLI helper `obtain_current_passphrase()` in `chia/util/keyring_wrapper.py` [3](#0-2) , which is invoked only by local CLI flows such as `chia/cmds/start_funcs.py`'s `create_start_daemon_connection()` [4](#0-3) . `KeychainMaxUnlockAttempts` is never referenced inside `chia/daemon/server.py`, confirming the daemon RPC command handlers themselves enforce no attempt limit at all — a caller that reaches the daemon websocket can call `unlock_keyring`/`validate_keyring_passphrase` as many times per second as the transport allows.

`chia/daemon/server.py`'s message dispatcher (`handle_message`) routes these commands straight to their handlers with no rate-limiting middleware in the path, unlike the peer-protocol layer (`chia/server/rate_limits.py`, `chia/server/rate_limits_v3.py`), which has dedicated per-message throttling for P2P traffic but has no analogous protection wired into the daemon websocket command dispatch [5](#0-4) . This mirrors the reported bug class precisely: an auth-checkable endpoint (`unlock_keyring`/`validate_keyring_passphrase` gate access to the master-passphrase-encrypted keyring) is reachable with no throttling despite functionally equivalent protections existing elsewhere in the codebase.

### Impact Explanation
If a user sets a custom, human-guessable master passphrase to protect their keyring at rest (rather than relying on the default constant passphrase), the daemon RPC surface allows unlimited automated guesses of that passphrase from any client capable of establishing a daemon websocket connection. A successful guess unlocks the keyring and grants access to private keys via subsequent keychain RPC commands (`get_key`, `get_all_private_keys`, etc., in `chia/daemon/keychain_server.py`), enabling unauthorized signing and coin movement. This is a defense-in-depth/CWE-290/CWE-770 style weakness consistent with the reported analog, not a bypass of TLS itself.

### Likelihood Explanation
Exploitation requires the ability to open a daemon websocket connection, which in normal Chia deployments requires possession of the daemon's private TLS client certificate under `CHIA_ROOT`. That certificate is a strong local-admin credential, and any holder of it already has substantial daemon RPC capability. This significantly limits practical exploitability to callers who already have meaningful local access (analogous to the "operator lowers practical risk" caveat noted in the original report for local-first deployments), but does not eliminate the class of risk for setups sharing that certificate more broadly (e.g., multi-user hosts, remote daemon exposure, or leaked/broadly-distributed daemon certs) where the master passphrase is the last line of defense for the keyring.

### Recommendation
Add server-side attempt throttling/lockout to `unlock_keyring()` and `validate_keyring_passphrase()` in `chia/daemon/server.py` (e.g., an increasing delay or hard lockout after N consecutive failed attempts per connection or globally, mirroring `MAX_RETRIES`/`FAILED_ATTEMPT_DELAY`/`KeychainMaxUnlockAttempts` already used in the CLI path), so that the RPC surface is protected independent of the interactive CLI helper.

### Proof of Concept
A daemon RPC client that can open the daemon websocket (as exercised by `chia/_tests/core/daemon/test_daemon.py::test_validate_keyring_passphrase_rpc`) can send an unbounded sequence of `validate_keyring_passphrase` (or `unlock_keyring`) commands with different `key` guesses back-to-back over the same or new connections; each is processed immediately with no increasing delay or lockout, differing only in `{"success": false, "error": ...}` vs `{"success": true, ...}`, demonstrating that online guessing of the master passphrase is unthrottled server-side [6](#0-5) .

    async def unlock_keyring(self, websocket: WebSocketResponse, request: dict[str, Any]) -> dict[str, Any]:
        success: bool = False
        error: str | None = None
        key: str | None = request.get("key", None)
        if type(key) is not str:
            return {"success": False, "error": "missing key"}

        try:
            if Keychain.master_passphrase_is_valid(key, force_reload=True):
                Keychain.set_cached_master_passphrase(key)
                success = True
                # Inform the GUI of keyring status changes
                self.keyring_status_changed(await self.keyring_status(), "wallet_ui")
            else:
                error = "bad passphrase"
        except Exception as e:
            tb = traceback.format_exc()
            self.log.error(f"Keyring passphrase validation failed: {e} {tb}")
            error = "validation exception"

def obtain_current_passphrase(prompt: str = DEFAULT_PASSPHRASE_PROMPT, use_passphrase_cache: bool = False) -> str:
    from chia.util.keyring_wrapper import KeyringWrapper

    """
    Obtains the master passphrase for the keyring, optionally using the cached
    value (if previously set). If the passphrase isn't already cached, the user is
    prompted interactively to enter their passphrase a max of MAX_RETRIES times
    before failing.
    """

    if use_passphrase_cache:
        passphrase, validated = KeyringWrapper.get_shared_instance().get_cached_master_passphrase()
        if passphrase:
            # If the cached passphrase was previously validated, we assume it's... valid
            if validated:
                return passphrase

            # Cached passphrase needs to be validated
            if KeyringWrapper.get_shared_instance().master_passphrase_is_valid(passphrase):
                KeyringWrapper.get_shared_instance().set_cached_master_passphrase(passphrase, validated=True)
                return passphrase
            else:
                # Cached passphrase is bad, clear the cache
                KeyringWrapper.get_shared_instance().set_cached_master_passphrase(None)

    # Prompt interactively with up to MAX_RETRIES attempts
    for i in range(MAX_RETRIES):
        colorama.init()

        passphrase = prompt_for_passphrase(prompt)

        if KeyringWrapper.get_shared_instance().master_passphrase_is_valid(passphrase):
            # If using the passphrase cache, and the user inputted a passphrase, update the cache
            if use_passphrase_cache:
                KeyringWrapper.get_shared_instance().set_cached_master_passphrase(passphrase, validated=True)
            return passphrase

        time.sleep(FAILED_ATTEMPT_DELAY)
        print("Incorrect passphrase\n")
    raise KeychainMaxUnlockAttempts

async def create_start_daemon_connection(
    root_path: Path, config: dict[str, Any], *, skip_keyring: bool
) -> DaemonProxy | None:
    connection = await connect_to_daemon_and_validate(root_path, config)
    if connection is None:
        print("Starting daemon", flush=True)
        # launch a daemon
        launch_start_daemon(root_path)
        connection = await connect_to_daemon_and_validate(root_path, config, wait_for_start=True)
    if connection:
        if skip_keyring:
            print("Skipping to unlock keyring")
        else:
            passphrase = None
            if await connection.is_keyring_locked():
                passphrase = Keychain.get_cached_master_passphrase()
                if passphrase is None or not Keychain.master_passphrase_is_valid(passphrase):
                    with ThreadPoolExecutor(max_workers=1, thread_name_prefix="get_current_passphrase") as executor:
                        passphrase = await asyncio.get_running_loop().run_in_executor(executor, get_current_passphrase)

            if passphrase:
                print("Unlocking daemon keyring")
                await connection.unlock_keyring(passphrase)

        return connection
    return None

async def test_validate_keyring_passphrase_rpc(daemon_connection_and_temp_keychain):
    ws, keychain = daemon_connection_and_temp_keychain

    # When: the keychain has a master passphrase set
    keychain.set_master_passphrase(
        current_passphrase=DEFAULT_PASSPHRASE_IF_NO_MASTER_PASSPHRASE, new_passphrase="the correct passphrase"
    )

    bad_passphrase_case_response_data = {
        "success": False,
        "error": None,
    }

    missing_passphrase_response_data = {
        "success": False,
        "error": "missing key",
    }

    empty_passphrase_response_data = {
        "success": False,
        "error": None,
    }

    # When: using the correct passphrase
    await ws.send_str(
        create_payload("validate_keyring_passphrase", {"key": "the correct passphrase"}, "test", "daemon")
    )
    # Expect: validation succeeds
    # TODO: unify error responses in the server, sometimes we add `error: None` sometimes not.
    assert_response(await ws.receive(), {**success_response_data, "error": None})

    await ws.send_str(create_payload("validate_keyring_passphrase", {"key": "the wrong passphrase"}, "test", "daemon"))

    assert_response(await ws.receive(), bad_passphrase_case_response_data)
