## Valid Analog Found

### Title
Tokenfactory denom admin can permanently freeze user funds via unrestricted post-hoc `AllowList` updates - (File: `x/tokenfactory/keeper/msg_server.go`)

### Summary
The tokenfactory module lets any account permissionlessly create a denom (`factory/{creator}/{subdenom}`) and become its "admin," analogous to the `uriSetter` role in the reported bug. That admin can call `MsgUpdateDenom` at any time — even after tokens have already been distributed to third-party holders — to install an arbitrary `AllowList` on the denom, with no restriction that it only applies going forward or that existing holders be grandfathered in.

### Finding Description
`CreateDenom` is permissionless: any unprivileged sender can create `factory/{creator}/{subdenom}` and is automatically set as its admin. [1](#0-0) 
The admin can subsequently mint/transfer tokens to third parties, and later call `MsgUpdateDenom` to set/replace the denom's `AllowList` without any check on current holders or existing distribution: [2](#0-1) 
Just like `setBaseURI` in the reported bug — a single-role setter with no time-lock, no two-step confirmation, and no protection for state that other parties already depend on — `UpdateDenom` lets the admin unilaterally rewrite the `AllowList` field used to gate every future transfer of that denom.

The bank keeper enforces this allow list on both the sender and the recipient side of every `Send`/`MultiSend` for any denom with the `factory/` prefix: [3](#0-2) [4](#0-3) 
If the admin sets an allow list that excludes an existing holder, that holder's already-received balance becomes permanently untransferable: `IsInDenomAllowList` returns `false` for both send and receive since there is no grandfathering of holders who are not listed: [5](#0-4) 

### Impact Explanation
This results in permanent freezing of user funds for any tokenfactory denom whose admin decides (or is compromised) to restrict the allow list after distribution — no interaction from the victim is required, and there is no way for the frozen holder to recover the ability to move that balance short of the admin reversing the allow list. This directly matches the accepted "permanent freezing" impact criterion.

### Likelihood Explanation
Likelihood is high: creating a tokenfactory denom, minting/distributing to others, then calling `MsgUpdateDenom` with a restrictive allow list is a single unprivileged transaction sequence requiring no special access, consistent with the "tokenfactory denom creator" persona explicitly in scope. The tokenfactory README documents that denom admins are expected to remain "trusted" for their own denom, but nothing in code prevents a denom that has already achieved broad distribution/liquidity from having its holders retroactively locked out. [6](#0-5) 

### Recommendation
Mirror the report's suggested mitigation pattern (staged/confirmed privileged changes) for `MsgUpdateDenom`: either (a) disallow narrowing an existing `AllowList` to exclude addresses that already hold a nonzero balance of the denom, (b) require a timelock/two-step confirmation before an `AllowList` update takes effect, or (c) grandfather existing holders' ability to at least transfer out their pre-existing balance even if newly excluded from the allow list.

### Proof of Concept
1. Attacker calls `MsgCreateDenom` to create `factory/{attacker}/evil`, becoming its admin.
2. Attacker mints and distributes the denom to victims (e.g., via a DEX/airdrop) with no `AllowList` set, so anyone can hold/transfer it freely.
3. Once victims hold meaningful balances, attacker calls `MsgUpdateDenom` with an `AllowList` containing only the attacker's own address (`x/tokenfactory/keeper/msg_server.go:57-92`).
4. Any subsequent `MsgSend`/`MsgMultiSend` involving a victim's balance of that denom fails with "not allowed to send/receive funds" (`sei-cosmos/x/bank/keeper/msg_server.go:26-49`, `sei-cosmos/x/bank/keeper/send.go:501-524`), permanently freezing the victims' already-held tokens.

func (server msgServer) UpdateDenom(goCtx context.Context, msg *types.MsgUpdateDenom) (*types.MsgUpdateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.validateUpdateDenom(ctx, msg)
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	updateDenomEvent := sdk.NewEvent(
		types.TypeMsgUpdateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeUpdatedTokenDenom, denom),
	)

	if msg.AllowList != nil {
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		updateDenomEvent = updateDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		updateDenomEvent,
	})

	return &types.MsgUpdateDenomResponse{}, nil
}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}
