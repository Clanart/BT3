### Title
DataLayer Mirror URLs Allow Server-Side Request Forgery via Attacker-Controlled On-Chain URL Publication - (File: chia/data_layer/data_layer_wallet.py)

### Summary
`DataLayerWallet.create_new_mirror()` lets any wallet holding XCH publish a "mirror" coin with an arbitrary `launcher_id` (DataLayer store id) and arbitrary URL list, with no check that the caller owns or controls that store. [1](#0-0)  Any DataLayer node that subscribes to / owns that store will later fetch those attacker-chosen URLs directly via `http_download()`/`download_file()` with no restriction against private, loopback, or link-local (cloud metadata) targets, similar to the Vault ACME SSRF pattern where attacker-controlled targets caused unauthenticated outbound requests.

### Finding Description
The DataLayer mirror mechanism records URLs on-chain as coin memos: `create_new_mirror(launcher_id, amount, urls, ...)` builds a standard coin with `memos=[[launcher_id, *urls]]` and no validation that `launcher_id` corresponds to a store owned or controlled by the sender. [1](#0-0)  The RPC path `dl_new_mirror` simply forwards the caller-supplied `launcher_id`/`urls` to this method without any ownership or URL sanity check. [2](#0-1) 

Later, DataLayer service code pulls these mirror URLs for a store via `dl_get_mirrors` and feeds them straight into the subscription list used for downloading delta/full files: `update_subscriptions_from_wallet()` collects `mirror.urls` for the store id and hands them to `data_store.update_subscriptions_from_wallet()`. [3](#0-2)  During the periodic sync loop, `fetch_and_validate()` shuffles available server URLs and calls `insert_from_delta_file()` → `download_file()` → `http_download()`, which performs a plain `aiohttp` GET against `server_info.url + "/" + filename` with no host/IP allow-list, no rejection of loopback/private/link-local addresses, and no DNS-rebinding protection. [4](#0-3)  The same untrusted URL is also passed to `get_downloader()`, which POSTs JSON (`{"store_id":..., "url":...}`) to configured plugin services, and if a plugin is configured it will act on the attacker-supplied `url` as well. [5](#0-4)  Existing tests explicitly demonstrate the request going straight to arbitrary URLs including loopback addresses like `http://127.0.0.1/8000` with no filtering. [6](#0-5) 

The module-context documentation itself flags this as an explicit trust boundary that must be guarded (though it focuses on data-integrity, not SSRF): "Do not treat mirror URLs, plugins, or static file names as trusted data sources." 

This mirrors CVE-2026-5052's root cause: a validation service (Vault's ACME challenge validator / here, Chia's DataLayer sync) accepts an externally/attacker-supplied network target (DNS-resolved challenge host / here, an on-chain mirror URL) and issues outbound HTTP requests without restricting resolution to public, non-local addresses, enabling SSRF against internal network services (e.g., cloud metadata endpoints, internal admin panels, or other local services reachable by the DataLayer host).

### Impact Explanation
Any user who can create a DataLayer mirror coin — a normal, unprivileged, permissionless spend (only requires paying `fee` + `amount` for their own coin) — can point arbitrary victim DataLayer nodes at attacker-chosen internal or local URLs. Because the `launcher_id` is not required to be owned by the mirror creator, an attacker can target any publicly known/tracked DataLayer store id. Once any node subscribes to or owns that store, its periodic `periodically_manage_data()` → `fetch_and_validate()` loop will issue outbound HTTP requests to those attacker-chosen destinations (e.g., `http://169.254.169.254/...`, `http://127.0.0.1:<internal-port>/...`, or internal LAN hosts), potentially leaking cloud instance credentials/metadata, probing internal services, or triggering unintended side effects on internal HTTP endpoints reachable from the DataLayer host. This is classified Medium severity, matching the referenced advisory's CVSS (network-reachable, low complexity, no privileges, confidentiality impact only, no direct integrity/availability compromise of the DataLayer store itself since inserted data is still validated against the wallet-advertised Merkle root).

### Likelihood Explanation
High likelihood of triggerability: creating a mirror coin is a standard, unauthenticated (from the network's perspective) wallet operation available to any spend-bundle submitter with dust-level XCH, requiring no coordination with the store owner. The DataLayer background sync loop (`periodically_manage_data()`) runs automatically and will pick up subscription/mirror URLs without user interaction, meaning the SSRF fires passively as soon as a victim node subscribes to (or already owns/tracks) the targeted store.

### Recommendation
Add outbound-request target validation before any DataLayer HTTP fetch (`http_download()` in `chia/data_layer/download_data.py`, and the plugin POST in `get_downloader()`/`download_file()`): resolve the URL's hostname and reject requests whose resolved IP is loopback, link-local (including `169.254.169.254`), private/RFC1918, or otherwise non-public, unless explicitly allow-listed by local configuration (mirroring Vault's fix of preventing local-network HTTP validation targets). Additionally, consider requiring the DataLayer node operator to explicitly opt in per-mirror-URL (trust-on-first-use / allow-list) rather than automatically consuming any on-chain-published mirror URL for stores that aren't locally owned.

### Proof of Concept
1. Attacker (any wallet holding minimal XCH) calls `dl_new_mirror` RPC targeting a `launcher_id` of a DataLayer store that other network participants track/subscribe to, with `urls=["http://169.254.169.254/latest/meta-data/iam/security-credentials/"]` — as shown reachable via `chia/wallet/wallet_rpc_api.py:dl_new_mirror` with no ownership check. [2](#0-1) 
2. Transaction confirms; the mirror coin's memo is now on-chain, associated with the targeted `launcher_id`.
3. Any victim node that has this store's `DataLayerWallet` tracking the launcher id and runs `update_subscriptions_from_wallet()` will ingest the attacker's URL into its subscription list. [3](#0-2) 
4. On the next periodic sync cycle, `fetch_and_validate()` selects the attacker's URL and calls `http_download()`, causing the victim's DataLayer server process to issue an outbound HTTP GET to the attacker-chosen internal/local target. [4](#0-3) 

Note: I was unable to fully verify from the indexed code whether `launcher_id` ownership is checked anywhere further upstream (e.g., at coin-state processing when a mirror coin is first parsed) since `chia/data_layer/data_layer_wallet.py`'s mirror-coin-parsing logic (`get_mirrors_for_launcher` / coin-state handling) was only partially retrieved. If such a check exists elsewhere in that file, it would need to be confirmed to fully validate the "arbitrary launcher_id" claim; a Devin session with full file access would be needed to confirm this definitively.

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```
