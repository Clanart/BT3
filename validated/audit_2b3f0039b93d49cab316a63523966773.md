Confirmed analog found. The invariant here is the same broken pattern as the Olympus TRSRY bug: **the code separates "what was measured/shown" from "what is measured/applied at execution time," and treats the second measurement as if it were still bound to the first.**

### Title
Stale line-selection applied against a freshly re-fetched working directory diff enables silent corruption of partial commits - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user partially stages a file (selecting individual lines/hunks in the Changes diff view), GitHub Desktop records the selection as **absolute line indices** into the diff that was rendered in the UI [1](#0-0) . At commit time, instead of reusing that same diff object, `applyPatchToIndex` re-runs `git diff` against the working directory a second time via `getWorkingDirectoryDiff` and builds the patch from hunks of this *new* diff, using the *old* selection's line indices [2](#0-1) .

### Finding Description
`stageFiles` is invoked from `createCommit` right before running `git commit` [3](#0-2) . For files with a partial selection it calls `applyPatchToIndex`, which:
1. Re-fetches the diff from disk: `const diff = await getWorkingDirectoryDiff(repository, file)` [4](#0-3) .
2. Builds the patch using `formatPatch(file, diff)`, which walks `diff.hunks` and decides inclusion per line via `file.selection.isSelected(absoluteIndex)` [5](#0-4) , where `absoluteIndex` is computed purely from the *new* diff's hunk offsets (`hunk.unifiedDiffStart + lineIndex`).

The `file.selection` bitset, however, was populated earlier by the UI against the diff that was displayed when the user clicked checkboxes (`onLineNumberCheckedChanged` / `_changeFileLineSelection`) [1](#0-0) [6](#0-5) . There is no check that the diff used to build the selection and the diff used to build the patch are the same content/hash — the code simply assumes the working directory hasn't changed between "diff shown" and "diff applied," exactly analogous to the treasury module assuming the balance delta between two measurements is attributable to the original actor.

If the file's contents on disk change between the moment the user reviews/selects lines and the moment `_commitIncludedChanges` runs `createCommit` → `stageFiles` → `applyPatchToIndex` (e.g., a build tool, editor auto-format-on-save, a file watcher, or content written by a `smudge`/`clean` filter defined in `.gitattributes` — which is part of the cloned repository and therefore attacker-controlled), the hunk boundaries and `unifiedDiffStart` offsets shift. The stale bitmask of "selected" absolute indices then no longer corresponds to the same logical lines, so `formatPatch` can silently include unreviewed/attacker-modified content in the patch, or exclude content the user intended to commit, or in degenerate cases the `git apply --cached` may even fail/apply against unexpected context.

This satisfies the "silent corruption of what the user commits" impact category: nothing prevents an unprivileged, repository-controlled mechanism (a `.gitattributes` filter, or any process spawned by opening/building the checked-out repo) from mutating tracked file content in the small window between diff-render and commit-time re-diff, causing Desktop to stage/commit content the user never reviewed or explicitly selected.

### Impact Explanation
Impact is scoped to the currently open, partially-selected file(s) at commit time: the committed diff can diverge from what the user visually approved via line/hunk checkboxes, without any error or warning being surfaced. This is a data-integrity issue (silent corruption of commit contents) rather than a sandbox escape or credential leak, but it is squarely in the report's "silent corruption of what the user commits or pushes" category.

### Likelihood Explanation
Likelihood is limited by timing: an attacker (via a malicious `.gitattributes` clean/smudge filter or any repo-triggered tooling) needs the working tree to change between when the diff was rendered for line-selection and when `createCommit` executes `stageFiles`. This is not guaranteed but is plausible for repos with build-on-save tooling, format-on-commit filters, or slow user interaction between selecting lines and clicking Commit. No local/physical access or elevated privileges are required — only that the user opens/works in an attacker-supplied repository.

### Recommendation
Bind the selection to the exact diff it was computed from (e.g., store a hash/version of the diff alongside the `DiffSelection`, or pass the already-loaded `ITextDiff` object itself through to `applyPatchToIndex`/`stageFiles` instead of re-fetching a new diff). If the working directory content or diff hash has changed since the selection was made, refuse to stage/commit and force the user to re-review, mirroring the `min(received, amount_)`-style fix used in the original report: never trust a second measurement to validate an action authorized against a first, different measurement.

### Proof of Concept
1. Modify a tracked file so it has multiple hunks; open GitHub Desktop's Changes view and partially select individual lines within one hunk (this records `DiffSelection` line indices tied to the currently rendered diff's `hunk.unifiedDiffStart`/`unifiedDiffEnd`, per `formatPatch`'s use of `absoluteIndex`).
2. Before clicking "Commit", have an external process (e.g. simulate a `.gitattributes` `clean`/`smudge` filter or an editor auto-save) insert/remove lines above the selected hunk in the same file, shifting subsequent line numbers.
3. Click "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-runs `getWorkingDirectoryDiff` [4](#0-3)  and reuses the stale `file.selection` bitset against the new hunk layout in `formatPatch` [5](#0-4) .
4. Inspect the resulting commit (`getChangedFiles`) and observe it differs from what was highlighted/checked in the UI at selection time — content the user never explicitly approved is committed (or approved content is dropped).
