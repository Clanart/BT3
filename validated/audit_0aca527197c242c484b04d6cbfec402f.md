### Title
Debt held in a DAO-disabled asset id is silently excluded from `debt-total` in `get-notional-evaluation`, permanently understating a borrower's debt and letting them drain collateral - ([File: local-testing/contracts/market/market.clar])

### Summary
`get-notional-evaluation` computes `debt-total` by folding over the `assets` list, which is built by `get-assets` and is filtered to only the currently DAO-enabled asset bitmap. Meanwhile, `market-vault.clar`'s `get-position` fetches the user's full debt list using `MAX-U128` (i.e., ignoring the enabled mask), so a user's real debt in a disabled asset id still exists in `position.debt` but is never visited during the notional fold, permanently pricing that debt as `u0` for as long as the asset stays disabled.

### Finding Description
Tracing the debt value end to end:

1. `get-position` in `local-testing/contracts/market/market-vault.clar:325-333` builds the position for health/borrow/withdraw checks:
```
(is-collateral (lookup-collateral user-id mask enabled-mask))
(is-debt (lookup-debt user-id mask MAX-U128))
```
Collateral is filtered by `enabled-mask` (the DAO-current enabled bitmap), but debt is looked up with `MAX-U128` - i.e., **all** debt regardless of whether the asset is currently enabled. So a borrower's debt entry `{ aid: excluded-id, scaled: X }` for a disabled asset id is present in `position.debt`. [1](#0-0) 

2. `get-assets` (`local-testing/contracts/market/market.clar:504-514`) builds the `assets` list used for pricing:
```
(mask-enabled (get-enabled-bitmap))
(safe-mask (user-safe-mask mask-user mask-enabled))
(iter (mask-to-list-collateral safe-mask))
```
This intersects with `mask-enabled` (the current DAO enabled bitmap) before turning into the asset-id iteration list, so a disabled asset id is guaranteed to be absent from `assets`. [2](#0-1) 

3. `get-notional-evaluation` (`local-testing/contracts/market/market.clar:536-564`) folds `calculate-asset-notional-value` **over `assets`, not over `debt-list`**:
```
(result (fold calculate-asset-notional-value assets
              { clist: collateral-list, dlist: debt-list, coll-total: u0, debt-total: u0 }))
```
Since the excluded asset id never appears as an element of `assets`, `calculate-asset-notional-value` is never invoked for that id, so the `find-debt-scaled` lookup for that id (which would otherwise price the $50000 debt) never happens. The accumulator's initial `debt-total: u0` is never incremented for that asset. [3](#0-2) [4](#0-3) 

4. The resulting `{ collateral: coll-total, debt: u0 }` is the value fed into every downstream health/LTV computation (e.g., `current-ltv` in `liquidate`, and analogous logic reused for `borrow`/`withdraw`), such as:
```
(current-ltv (if (is-eq total-collateral-usd u0) ... (mul-div-down total-debt-usd BPS total-collateral-usd)))
```
With `total-debt-usd = u0`, `current-ltv = u0`, which always passes any withdraw/borrow health gate regardless of how much real, accruing debt the borrower carries. [5](#0-4) 

No later gate recovers this: there is no cross-check that debt-list ids are a subset of the priced `assets` ids, and no separate accounting step re-adds omitted debt. The condition persists across every subsequent `borrow`/`withdraw` call as long as the asset id stays disabled, i.e., it is not momentary - it is permanent until (and unless) the DAO re-enables the id.

### Impact Explanation
The error is a **debt-undervaluation** (understated to exactly zero) for any debt held in a currently-disabled asset id, while collateral valuation is unaffected. This benefits the borrower: they can pass health checks that should fail and withdraw all collateral while the vault-level scaled debt (tracked correctly in `market-vault`'s `debt` map) remains outstanding and continues to accrue interest that can never be repaid from seized collateral. This is direct protocol insolvency / theft of protocol/lender funds, matching the **Critical** severity category (protocol insolvency, permanent freezing/loss of funds backing the debt).

### Likelihood Explanation
The attacker needs only: (1) borrow (or already hold debt) in an asset id that later becomes DAO-disabled (a normal, expected DAO action such as deprecating an asset, not a misconfiguration), and (2) call ordinary public `withdraw`/`borrow` functions. No special privilege, oracle manipulation, or DAO compromise is required - the exclusion is a natural consequence of the disable action interacting with this fold logic. Any account with existing debt in an asset id that is later disabled can exploit this immediately and repeatedly (every subsequent transaction) until the id is re-enabled.

### Recommendation
Compute `debt-total` (and any similar aggregate) by folding over the union of asset ids present in `position.debt`, not just the DAO-enabled `assets` list - or explicitly require/resolve pricing for every id present in `debt-list` regardless of its enabled status, since debt obligations must always be counted even for assets removed from new borrowing/collateral eligibility. Alternatively, disallow disabling an asset id while any account still carries outstanding debt in it, or force full price resolution for disabled ids that still have live debt/collateral until debt is fully repaid.

### Proof of Concept
Clarinet/vitest simnet outline:
1. Configure `v0-assets`/`v0-egroup` (or `assets`/`egroup` in local-testing) with an asset `stSTXbtc` enabled, borrow `$50000` notional worth of it against sufficient collateral, confirming `debt-add-scaled` records the debt (`market-vault` `debt` map, `position.mask` debt bit set).
2. Have the DAO executor call the asset registry's disable function to remove `stSTXbtc`'s bit from `get-bitmap` (simulating a normal deprecation, no misconfiguration).
3. Call `get-position`/`get-full-position` for the borrower and confirm `debt-list` still contains `{ aid: stSTXbtc-id, scaled: <nonzero> }` (via `MAX-U128` lookup).
4. Call the public `withdraw` (or a read-only wrapper exposing `get-notional-evaluation`) for the borrower's remaining collateral and assert `debt-total` returned is `u0` despite the outstanding `$50000` scaled debt.
5. Call `withdraw` twice in sequence (same or later blocks) and assert both succeed, driving the account's collateral balance to zero, while `market-vault`'s `debt` map for that account/asset still shows the full `$50000` scaled debt outstanding - demonstrating permanent insolvency.

(define-private (calculate-asset-notional-value
          (asset-entry {
              id: uint, addr: principal, decimals: uint,
              oracle: { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint },
              collateral: bool, debt: bool, price: uint })
          (acc { clist: (list 64 { aid: uint, amount: uint }),
                  dlist: (list 64 { aid: uint, scaled: uint }),
                  coll-total: uint,
                  debt-total: uint }))
  (let ((asset-id (get id asset-entry))
        (price (get price asset-entry))
        (decimals (get decimals asset-entry))
        (collateral-list (get clist acc))
        (debt-list (get dlist acc))
        (coll-amount (find-collateral-amount collateral-list asset-id))
        (coll-notional (if (> coll-amount u0)
                           (normalize (* coll-amount price) decimals false)
                           u0))

        (debt-scaled   (find-debt-scaled debt-list asset-id))
        (debt-notional (if (> debt-scaled u0) ;; use cache instead here
                           (let ((cached (unwrap-panic (accrue-and-cache asset-id)))
                                 (ib (get index cached))
                                 (actual (mul-div-up debt-scaled ib INDEX-PRECISION)))
                             (normalize (* actual price) decimals true))
                           u0)))

    { clist: collateral-list,
      dlist: debt-list,
      coll-total: (+ (get coll-total acc) coll-notional),
      debt-total: (+ (get debt-total acc) debt-notional) }))
