### Title
Unbounded, never-evicted `commitLookup` cache lets a malicious remote force unbounded in-memory commit accumulation - (File: `app/src/lib/stores/git-store.ts`)

### Summary
`GitStore` (one instance is cached per repository for the lifetime of the app via `gitStoreCache`) keeps every `Commit` object it has ever parsed in a plain `Map<string, Commit>` called `commitLookup`, with no size cap, TTL, or eviction policy. [1](#0-0) 
Every code path that resolves a commit - loading history batches, local-commit pagination, comparing branches, and resolving tags after a fetch - permanently inserts into this map: [2](#0-1) [3](#0-2) 

This mirrors the structure of the libp2p bug: a remote-controlled data source (there, identify-delta protocol strings; here, git commit objects reachable from an attacker-controlled remote) is fed continuously into an in-memory structure that has no bound, no expiration, and no sanity checking on total size, growing until memory pressure becomes a problem.

### Finding Description
`GitStore.storeCommits()` is the sole insertion point for `commitLookup` and simply does `this.commitLookup.set(commit.sha, commit)` for every commit it is given, with nothing removing entries afterwards. [2](#0-1) 

The most attacker-reachable feeder of this map is `refreshTags()` / `emitUpdatesForChangedTags()`, which runs automatically after every fetch (a routine, unprompted background operation, not something the user has to manually trigger). It diffs the locally-known tags (`_localTags`) against the freshly fetched tags and, for every tag that is new or has moved, calls `getCommit()` and stores the result: [4](#0-3) 

Because a remote/attacker fully controls how many tags exist in the repository and how often they change between fetches, they can force this loop to resolve and permanently cache an attacker-chosen number of distinct commit objects (each carrying up to 100 KB of summary/body text, per the truncation logic in `getCommits`) on every background fetch cycle, without the user ever visiting the history view. [5](#0-4) 

History pagination adds a second amplification path: `_loadNextCommitBatch` / `loadCommitBatch` keep concatenating SHAs and calling `storeCommits`, and the SHA list itself (`compareState.commitSHAs`) is also concatenated without any cap: [6](#0-5) [7](#0-6) 

Existing guards elsewhere in the codebase show the project is aware of this class of problem and normally mitigates it - e.g. `CommitStatusStore` explicitly caps its cache with a `QuickLRU` bounded to 250 entries specifically "to ensure the cache won't grow unbounded": [8](#0-7) 
No equivalent bound exists for `GitStore.commitLookup`, which is the exact "no expiration, no pruning, no sanity checks" pattern called out in the libp2p report.

### Impact Explanation
A crafted/attacker-controlled remote repository can cause the Desktop process to accumulate an unbounded, ever-growing set of `Commit` objects in memory across the normal lifetime of the app (repeated background fetches, periodic tag refresh, and routine history scrolling), eventually degrading performance or crashing the renderer/main process (OOM) - the same broken invariant as the disclosed libp2p bug (no cap on attacker-fed, in-memory records). This is a memory-exhaustion/DoS class issue triggered purely by adding a cloned/fetched repository and letting Desktop's normal background fetch/tag-refresh operate; no unusual user action is required.

### Likelihood Explanation
Moderate. It requires the victim to add/clone a malicious repository (satisfies the "attacker controls a cloned/fetched repository" criterion) and leave Desktop running so that background fetch/tag refresh executes repeatedly, or to scroll a large amount of history. The growth rate depends on how aggressively the attacker manipulates tags/commit counts between fetches; it is a leak/DoS rather than an instant one-minute crash, so exploitation speed is lower than the original libp2p report, but the underlying missing-bound condition is directly analogous.

### Recommendation
Bound `GitStore.commitLookup` the same way `CommitStatusStore` bounds its cache (e.g., wrap it in a size-limited LRU, or cap it to the commits currently visible/relevant to the UI and evict entries once they fall out of the visible history window or are older than N accesses). Additionally, cap the number of tags processed per `refreshTags()` cycle (or rate-limit how many new/moved tags trigger a `getCommit` call per refresh) to prevent a single malicious fetch from injecting unbounded commit objects into memory.

### Proof of Concept
1. Create a git repository and push a very large number of lightweight tags (e.g., hundreds of thousands), each pointing at a distinct commit with a large (~100 KB) commit body/summary.
2. Have the victim clone/add this repository in GitHub Desktop.
3. On the first background fetch after the initial state is established, force the tag set to change (e.g., move or recreate a large batch of tags) so `refreshTags()`'s diff in `emitUpdatesForChangedTags` treats them as newly created/moved.
4. Each subsequent scheduled fetch cycle causes `getCommit()` to be called and cached for every changed tag via `storeCommits`, permanently growing `commitLookup` with no eviction.
5. Repeat step 3 across successive fetches (or combine with continuous `loadCommitBatch` pagination while the user browses history) to observe unbounded, monotonically increasing memory usage in the Desktop process over time, with no corresponding decrease.

  public async loadCommitBatch(commitish: string, skip: number) {
    if (this.requestsInFight.has(LoadingHistoryRequestKey)) {
      return null
    }

    const requestKey = `history/compare/${commitish}/skip/${skip}`
    if (this.requestsInFight.has(requestKey)) {
      return null
    }

    this.requestsInFight.add(requestKey)

    const commits = await this.performFailableOperation(() =>
      getCommits(this.repository, commitish, CommitBatchSize, skip)
    )

    this.requestsInFight.delete(requestKey)
    if (!commits) {
      return null
    }

    this.storeCommits(commits)
    return commits.map(c => c.sha)
  }

  /**
   * Calculates the commits that have changed based on the changes in existing tags
   * to emit the correct updates.
   *
   * This is specially important when tags are created/modified/deleted from outside of Desktop.
   */
  private async emitUpdatesForChangedTags(
    previousTags: Map<string, string>,
    newTags: Map<string, string>
  ) {
    const commitsToUpdate = new Set<string>()
    let numCreatedTags = 0

    for (const [tagName, previousCommitSha] of previousTags) {
      const newCommitSha = newTags.get(tagName)

      if (!newCommitSha) {
        // the tag has been deleted.
        commitsToUpdate.add(previousCommitSha)
      } else if (newCommitSha !== previousCommitSha) {
        // the tag has been moved to a different commit.
        commitsToUpdate.add(previousCommitSha)
        commitsToUpdate.add(newCommitSha)
      }
    }

    for (const [tagName, newCommitSha] of newTags) {
      if (!previousTags.has(tagName)) {
        // the tag has just been created.
        commitsToUpdate.add(newCommitSha)
        numCreatedTags++
      }
    }

    if (numCreatedTags > 0) {
      this.statsStore.increment('tagsCreated', numCreatedTags)
    }

    const commitsToStore = []
    for (const commitSha of commitsToUpdate) {
      const commit = await getCommit(this.repository, commitSha)

      if (commit !== null) {
        commitsToStore.push(commit)
      }
    }

    this.storeCommits(commitsToStore)
  }

  private async lookupCommit(sha: string): Promise<Commit> {
    const cachedCommit = this.commitLookup.get(sha)
    if (cachedCommit != null) {
      return Promise.resolve(cachedCommit)
    }

    const foundCommit = await this.performFailableOperation(() =>
      getCommit(this.repository, sha)
    )

    if (foundCommit != null) {
      this.commitLookup.set(sha, foundCommit)
      return foundCommit
    }

    throw new Error(`Could not load commit: '${sha}'`)
  }
