### Title
Path-containment bypass in `resolveWithin` via sibling-directory name prefix, reachable from `x-github-client://openrepo` deep link `filepath` parameter - (File: `app/src/lib/path.ts`)

### Summary
The Curve `safetyCheck` bug is a class of "incomplete boundary/invariant check" flaw: it validates related quantities pairwise but the check is not precise enough to guarantee the real invariant (containment/ratio) it claims to enforce. The same flaw class exists in Desktop's `_resolveWithin` helper in `app/src/lib/path.ts`, which is supposed to guarantee that a resolved path stays "underneath the root path" but actually only checks a raw string prefix (`realResolved.startsWith(realRoot)`) without verifying a path-separator boundary. This lets an attacker-controlled relative path escape the intended root into a sibling directory whose name happens to share the root directory's name as a prefix, while still passing the "containment" check — analogous to how checking `a/b` and `a/c` ratios doesn't guarantee the real `b/c` relationship.

### Finding Description
`_resolveWithin` in `app/src/lib/path.ts` is documented as guaranteeing "the resolved path is guaranteed to reside at, or underneath this [root] path" [1](#0-0) . Its actual containment check is:

```
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
``` [2](#0-1) 

`String.prototype.startsWith` has no notion of path-segment boundaries: if `realRoot` is `/Users/victim/Documents/GitHub/repo`, then `/Users/victim/Documents/GitHub/repo-secrets/config.json` also satisfies `startsWith(realRoot)`, even though `repo-secrets` is a completely different, sibling directory. This is the exact same class of imprecision the Curve report describes — the check verifies an adjacent, weaker relationship (string prefix) instead of the actual invariant it's supposed to enforce (directory containment), and the assumption that "prefix ⇒ containment" silently fails, just like "a/b in range ⇒ b/a in range" silently fails.

This function is reachable with fully attacker-controlled input via the `x-github-client://openrepo` deep-link handler. `parseAppURL` extracts an unsanitized `filepath` query-string value from the URL [3](#0-2) , and `Dispatcher.openRepositoryFromUrl` passes it straight to `resolveWithin`, only rejecting absolute paths:

```
if (filepath !== null) {
  if (isAbsolute(filepath)) {
    log.error(`Refusing to open absolute path: ${filepath}`)
    return
  }
  const resolved = await resolveWithin(repository.path, filepath)
  if (resolved !== null) {
    shell.showItemInFolder(resolved)
  } else {
    log.error(...)
  }
}
``` [4](#0-3) 

Because `isAbsolute` only blocks absolute paths, a relative traversal such as `../repo-secrets/config.json` is allowed through to `resolveWithin`. If the victim's already-cloned repository directory name (e.g. `repo`) is a prefix of a sibling directory name (e.g. `repo-secrets`, `repo2`, `repository-backup`, `repo.bak`) — a very common pattern for related/backup/staging checkouts under a shared parent folder like `~/Documents/GitHub/` — the traversal resolves outside the repo but still passes the flawed `startsWith` check.

### Impact Explanation
An attacker who gets a victim to click a crafted `x-github-client://openrepo/<owner>/<repo>?filepath=..%2F<sibling-dir>%2F<sensitive-file>` link (e.g. embedded in a webpage, README, or issue comment) can cause Desktop to call `shell.showItemInFolder` on a file outside the intended repository boundary — exactly the "file read outside the repo" class of impact the task requires. `shell.showItemInFolder` reveals the existence, name, and location of the targeted file in the OS file manager, and on some platforms/configurations selecting/revealing a file can be a stepping stone to opening it, disclosing information the user did not intend to expose via a git-cloned-repo-driven action. The check exists specifically to prevent exactly this (`log.error('Prevented attempt to open path outside of the repository root...')`) but the underlying primitive it relies on is broken.

### Likelihood Explanation
This requires: (1) the victim to have GitHub Desktop installed and already have a matching repository cloned locally (the `url` in the deep link must resolve to an existing/clonable repo), and (2) a sibling directory existing with a name that shares a prefix with the target repo's directory name. Developers very commonly clone multiple related repos under one parent folder (`GitHub/`, `src/`, `Projects/`) using predictable naming conventions (`repo`, `repo-old`, `repo2`, `repo.bak`, `repo-secrets`), so this is a realistic, non-contrived layout, but it is not guaranteed for every victim — it depends on their folder naming. This is comparable to the Curve finding's own likelihood characterization ("small differences ... sufficiently small error margin" vs. the judge's view that the missing check still "deserves high risk") — here the flaw is deterministic once the naming precondition holds, and requires only a single click on a link, with no local access, malware, or credentials needed.

### Recommendation
Fix `_resolveWithin` in `app/src/lib/path.ts` to check for a real directory-boundary, not a bare string prefix, e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(with platform-appropriate separator handling for the `Path.win32`/`Path.posix` variants). Add a regression test alongside the existing `path-test.ts` cases covering the sibling-directory-prefix scenario (e.g. root `/tmp/repo` vs. resolved `/tmp/repo-evil/file`) to lock in the fix, mirroring how the Curve fix added the missing `b/c` ratio check.

### Proof of Concept
1. Victim has GitHub Desktop with two repos cloned side by side:
   - `~/Documents/GitHub/repo` (the target, tracked by Desktop)
   - `~/Documents/GitHub/repo-secrets` (an unrelated sibling directory containing sensitive files)
2. Attacker sends the victim a link:
   `x-github-client://openrepo/owner/repo?filepath=..%2Frepo-secrets%2Fconfig.json`
3. Victim clicks the link. Desktop's URL handler parses it via `parseAppURL`, producing `filepath = "../repo-secrets/config.json"` [3](#0-2) .
4. `Dispatcher.openRepositoryFromUrl` opens/selects the local `repo` repository, then calls `isAbsolute(filepath)` — false, so it proceeds — and calls `resolveWithin(repository.path, filepath)` [5](#0-4) .
5. Inside `_resolveWithin`, `resolved = Path.resolve(".../GitHub/repo", "../repo-secrets/config.json")` = `.../GitHub/repo-secrets/config.json"`. `realRoot = ".../GitHub/repo"`. The check `realResolved.startsWith(realRoot)` evaluates to `true` because `"...repo-secrets/config.json".startsWith("...repo")` is true as a string comparison [6](#0-5) .
6. `resolveWithin` returns the out-of-repo path instead of `null`, and `shell.showItemInFolder(resolved)` opens the OS file explorer directly at the sensitive sibling file, disclosing its existence/location outside the repository the link claimed to operate on.
