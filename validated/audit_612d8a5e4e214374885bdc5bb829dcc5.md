### Title
Scanner reports uneconomical/dust outputs as received funds that can never be profitably spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the reference bug (bribe tokens pushed into the returned `TokenAmount` accounting array without ever being transferred to the staking contract), `Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs` reports any transaction output whose `script_pubkey` matches a registered offset as a `ReceivedOutput`, with no minimum-value check. Outputs carrying less than the network's `DUST` threshold — and even 0-value outputs — are therefore credited to the key's received set even though they can never be spent profitably (and may be non-standard/unbroadcastable when spent). They are "received" in accounting but are not usable funds, mirroring tokens recorded as distributed yet never delivered.

### Finding Description
`Scanner::scan_transaction` iterates `tx.output` and pushes a `ReceivedOutput` for every output matching `self.scripts`:

```rust
// networks/bitcoin/src/wallet/mod.rs:199-213
pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for (vout, output) in tx.output.iter().enumerate() {
    let Ok(vout) = u32::try_from(vout) else { break };
    if let Some(offset) = self.scripts.get(&output.script_pubkey) {
      res.push(ReceivedOutput {
        offset: *offset,
        output: output.clone(),
        outpoint: OutPoint::new(tx.compute_txid(), vout),
      });
    }
  }
  res
}
```

There is no check on `output.value`. By contrast, the consuming code acknowledges that such outputs are not real funds: `processor` filters with `output.balance().amount.0 >= N::DUST` (processor/src/multisigs/scanner.rs:564), and `SignableTransaction::new` rejects dust *payments* (`Err(TransactionError::DustPayment)`, networks/bitcoin/src/wallet/send.rs:165-169) — yet it performs no equivalent check on dust *inputs*. `N::DUST` is explicitly defined as a value that "MUST exceed the cost to spend said output, and should by a notable margin" (processor/src/networks/mod.rs:295-301).

So an unprivileged party can send a transaction to the multisig's external address (offset `Scalar::ZERO`, always registered) or any registered offset with a value below `DUST` — including a 1-satoshi or 0-satoshi output. `scan_transaction`/`scan_block` will report it as a `ReceivedOutput`. The wallet library itself then treats this output as a spendable input: `SignableTransaction::new` will include it in `tx_ins` and add its value to `input_sat`, even though the marginal signature/witness weight of the input costs more in fees than the output contributes (the `calculate_weight_vbytes` witness model at send.rs:71-84 charges one 64-byte-signature input each). The reported funds are consequently not spendable at a profit — they exist only in the "received" accounting, exactly as bribe amounts existed only in the returned `TokenAmount` array while the assets sat stuck in `SdtBuffer`.

### Impact Explanation
- Received-balance accounting is inflated by outputs that cannot be economically redeemed: each such output contributes less than its marginal spend cost, so including it strictly *destroys* value (the fee for the extra input exceeds its sat value).
- An attacker can cheaply fabricate "received" outputs (a single transaction can carry many sub-dust outputs to the same script_pubkey at minimal cost), forcing the wallet/processor to either track permanently-unspendable UTXOs or burn fees spending them.
- In aggregate this is a griefing/dilution vector on the treasury's reported and spendable balance — funds reported received that are not spendable, the accepted analog consequence class.

### Likelihood Explanation
Fully reachable by an unprivileged party: sending a Bitcoin transaction paying to the multisig's known P2TR script is public. No key material, validator status, or collusion is required. The only mitigating factor is that the downstream processor applies its own `N::DUST` filter, but the in-scope wallet library itself (`Scanner`, `SignableTransaction::new`) contains no such guard, and other consumers of `scan_transaction`/`scan_block` would inherit the flaw.

### Recommendation
Enforce a minimum-value bound in the wallet layer, consistent with the network's `DUST` contract:

- Add a `dust_threshold: u64` (or equivalent) to `Scanner`/`ReceivedOutput` handling, and skip outputs where `output.value.to_sat() < dust_threshold` inside `scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214).
- Independently, validate inputs in `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs): reject or warn on any `ReceivedOutput` whose value is below the dust threshold, so a sub-dust input can never silently degrade the transaction's net value — mirroring the reference fix where the missing `token.transfer(...)` was added so accounted assets were actually delivered.

### Proof of Concept
```rust
// Conceptual, against networks/bitcoin/src/wallet/mod.rs
let key = /* even-Y multisig key */;
let scanner = Scanner::new(key).unwrap();

// Attacker crafts a TX paying 1 sat to the multisig's P2TR script
let dust_tx = Transaction {
  // ...
  output: vec![TxOut {
    value: Amount::from_sat(1),               // far below DUST
    script_pubkey: p2tr_script_buf(key).unwrap(),
  }],
  ..
};

let received = scanner.scan_transaction(&dust_tx);
assert_eq!(received.len(), 1);                // reported as received
assert_eq!(received[0].value(), 1);           // credited

// The wallet then accepts it as an input
let stx = SignableTransaction::new(
  vec![received[0].clone()],
  &[(p2tr_script_buf(key).unwrap(), DUST)],
  None, None, FEE_PER_VBYTE,
);
// Succeeds or fails only due to insufficient total funds — never because the
// input is unspendable-at-a-profit. The 1-sat input's marginal fee cost
// (~68 vbytes * fee_per_vbyte for a Taproot input) vastly exceeds 1 sat.
```

Every input added costs roughly 57.5–68+ vbytes of weight (fixed `TxIn` fields plus a 64-byte witness, per `calculate_weight_vbytes` at send.rs:71-99), so any output worth less than `input_vbytes * fee_per_vbyte` is a net loss — yet it is reported as received funds and accepted as a spendable input without complaint.
