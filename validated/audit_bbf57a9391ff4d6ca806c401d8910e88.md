Confirmed: `create_reimburse_txhandler` spends `move_txhandler.get_spendable_output(UtxoVout::DepositInMove)` — the actual deposited BTC — to pay `operator_reimbursement_address`, with the reimbursement amount equal to the full deposit value.### Title
Payout tx OP_RETURN operator attribution is unauthenticated, letting anyone force an operator's automated reimbursement for a payout it never funded - ([File: core/src/verifier.rs])

### Summary
`update_finalized_payouts` derives `payout_payer_operator_xonly_pk` solely from the OP_RETURN push-data of an on-chain Payout transaction, with no signature check binding that pubkey to whoever supplied the transaction's input funds. Any unprivileged party can spend the registered withdrawal UTXO to the registered output, append operator O's x-only pubkey in the OP_RETURN, and the verifier database will record O as the payer even though O never called `Operator::withdraw`/`handle_finalized_payout` for that index.

### Finding Description
The broken binding is: `payout_payer_operator_xonly_pk` (DB column, read back by `get_first_unhandled_payout_by_operator_xonly_pk` and `get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id`) should equal "the xonly_pk of the party whose own funds paid for the withdrawal `i`". Instead it equals whatever bytes are pushed after `OP_RETURN` in the Payout transaction's OP_RETURN output, with no cryptographic tie to the input signer.

Code path:
- `verifier.rs::update_finalized_payouts` (core/src/verifier.rs:2283-2353) scans a finalized block for the payout tx tied to withdrawal `idx` (matched purely by which tx spends the registered `withdrawal_utxo`, via `get_payout_txs_for_withdrawal_utxos`), then does: [1](#0-0) 
This extracts the operator pubkey exclusively from `op_return_output` via `parse_op_return_data`, which merely returns the raw pushed bytes of the OP_RETURN script with no signature verification over that byte range: [2](#0-1) 
- The result is persisted unconditionally by `update_payout_txs_and_payer_operator_xonly_pk` (core/src/database/verifier.rs:198-251).
- `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) shows the legitimate payout tx has a **KeySpend** input using only the withdrawal UTXO's presigned user signature (`NormalSignatureKind::NotStored`, `SpendPath::KeySpend`) - the operator's own key never signs or otherwise appears in the payout transaction. Nothing about the transaction's witness commits the operator's identity to the input; only the OP_RETURN push-data (an unauthenticated, freely-choosable field) does.
- Consequently, an attacker who (a) knows the registered withdrawal UTXO/output (public, from Citrea withdraw event) and (b) has the presigned user signature (also observable/obtainable off-chain by anyone able to fund the payout, per the described attacker capability) can broadcast a valid Payout transaction that satisfies `input_outpoint`/`output[0]` exactly, but stamps operator O's pubkey in `output[2]`'s OP_RETURN while funding fees from attacker-controlled UTXOs.
- Downstream, `PayoutCheckerTask::run_once` (core/src/task/payout_checker.rs:39-47) polls `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` - i.e., each operator node automatically picks up any withdrawal whose recorded `payout_payer_operator_xonly_pk` matches its own key, with no additional proof that it actually performed the payout. This calls `Operator::handle_finalized_payout` (core/src/operator.rs:839-960), which allocates a kickoff connector and signs/broadcasts the full Kickoff → Reimburse transaction chain for O.
- `create_reimburse_txhandler` (core/src/builder/transaction/operator_reimburse.rs:341-385) spends `MoveToVaultTx`'s `DepositInMove` output (the full deposited BTC) to `operator_reimbursement_address` - i.e., real bridge value leaves the deposit UTXO to reimburse O.
- `Verifier::is_kickoff_malicious` (core/src/verifier.rs:1859-1915) only re-checks that `operator_xonly_pk` read from the DB equals `kickoff_data.operator_xonly_pk` and that the committed payout blockhash matches - both values it re-derives from the same unauthenticated OP_RETURN/DB row, so it cannot detect the forgery; it never checks who funded the payout's input.

Why existing guards fail: `Verifier::is_deposit_valid`, `SPV::verify`, `verify_storage_proofs`, and `is_kickoff_malicious` all validate that the payout transaction correctly spends the registered withdrawal UTXO to the registered output and that the blockhash/operator consistency between kickoff and OP_RETURN holds - but none of them verify that the OP_RETURN pubkey corresponds to the actual signer/funder of the transaction's inputs. There is no such signature check anywhere in the flow.

### Impact Explanation
BTC leaves the specific deposit's `MoveToVaultTx` `DepositInMove` output and is paid to operator O's reimbursement address via the `Reimburse` transaction, even though O never funded/broadcast the underlying payout for that withdrawal index - this squarely matches the listed Critical category "an operator reimbursed for a payout it never funded." The attacker forces O's automation (`PayoutCheckerTask`) to consume one of O's presigned kickoff connectors and complete an entire kickoff→reimburse cycle for a payout O did not choose to make, diverting the deposit's BTC to O instead of, e.g., remaining available for the honest operator who should have fronted it, or for an optimistic-payout/no-operator outcome. This is repeatable per withdrawal index and per operator, since the same forging technique applies to any pending withdrawal and any target operator xonly_pk.

### Likelihood Explanation
Preconditions: the attacker needs the exact registered `withdrawal_utxo` (public knowledge from Citrea's withdraw event) and the presigned user Schnorr signature for that UTXO's key-spend (needed to satisfy the KeySpend witness) - the prompt's threat model explicitly grants the attacker the ability to "choose the bytes of a withdrawal UTXO" and "a Schnorr signature and its sighash flag," implying this signature is obtainable/forgeable within scope. Given that, the attacker only pays normal Bitcoin transaction fees to broadcast the forged Payout tx; no verifier/operator/aggregator privilege, key share, or collateral is required. This is feasible and repeatable for every pending withdrawal.

### Recommendation
Bind the OP_RETURN operator attribution cryptographically to whoever actually authorizes the payout - e.g., require the operator to co-sign the payout transaction (or a separate commitment covering the exact `(withdrawal_utxo, output_script_pubkey, output_amount, operator_xonly_pk)` tuple) so that `update_finalized_payouts` can verify a signature from the claimed operator over that OP_RETURN payload before writing `payout_payer_operator_xonly_pk`, rather than trusting unauthenticated push-data.

/// Parses the OP_RETURN data from a Bitcoin script. It retrieves the first data push after an OP_RETURN.
pub fn parse_op_return_data(script: &Script) -> Option<&[u8]> {
    let mut instructions = script.instructions();
    if let Some(Ok(Instruction::Op(opcodes::all::OP_RETURN))) = instructions.next() {
        if let Some(Ok(Instruction::PushBytes(data))) = instructions.next() {
            return Some(data.as_bytes());
        }
    }
    None
}
