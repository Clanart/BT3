### Title
Cached DKG-confirmation preprocess is re-consumed by `complete`, reusing FROST nonces across distinct signing sets and leaking the validator's secret share - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The bug class behind CVE-2019-19524 is a lifetime violation: attacker-supplied input causes state to be used after it was logically freed/invalidated. In Serai the equivalent is a one-time FROST preprocess (the ChaCha20 seed behind `CachedPreprocess`) being consumed more than once. `DkgConfirmer::share` and `DkgConfirmer::complete` each call `share_internal` → `preprocess_internal`, which regenerates the *same* `AlgorithmSignMachine` — same secret nonces `d, e` — from the DB-cached seed keyed only by `(b"DkgConfirmer", attempt)`. If the second `sign` executes over a different participant set or a different message than the first, two signature shares are published under one nonce, enabling algebraic recovery of the validator's MuSig private key share (the root-of-trust key).

### Finding Description
`preprocess_internal` stores a 32-byte seed under `CachedPreprocesses` per `context = (b"DkgConfirmer", attempt)` and deterministically rebuilds the sign machine via `AlgorithmSignMachine::from_cache` on every invocation. The modular-frost contract is explicit that this cache "MUST only be used once" and reuse "enables recovery of your private key share" (`crypto/frost/src/sign.rs:211-224`, `spec/cryptography/FROST.md:51-55`).

- `DkgConfirmer::share(preprocesses, key_pair)` calls `share_internal`, which signs `set_keys_message(...)` over the supplied `preprocesses` map and returns/publishes a share (`signing_protocol.rs:288-310`).
- `DkgConfirmer::complete(preprocesses, key_pair, shares)` calls `share_internal` **again**, re-signing with the same cached nonces before completing (`signing_protocol.rs:312-327`).

The two `sign` calls are independent executions over caller-supplied `HashMap<Participant, Vec<u8>>` preprocess sets. The preprocess set fed to `complete` is gathered independently of the set used for `share` (e.g., the share was produced over a `t`-sized subset while `complete` is invoked over a different/later-arriving subset, or with a differing `key_pair`/`removed` set changing `msg`). In `AlgorithmSignMachine::sign`, the per-participant binding factor `rho` and the challenge are computed from `included`, all preprocesses, and `msg` (`crypto/frost/src/sign.rs:283-318`). Any difference yields:

```
share₁ = d + e·ρ₁·λ₁·s   (set A / msg A)
share₂ = d + e·ρ₂·λ₂·s   (set B / msg B)
```

Two equations, one reused nonce pair `(d, e)` — the standard FROST/ROS nonce-reuse linear solve recovers `s`, the validator's MuSig secret share.

The file's own header acknowledges the hazard: safety relies on nonces being "context-bound" and on received messages being identical between executions (`signing_protocol.rs:25-48`). Nothing enforces that the `preprocesses`/`key_pair` seen by `share` equal those seen by `complete`; they are distinct inputs at distinct times.

### Impact Explanation
Recovery of a validator's Ristretto private key share — the key used for DKG confirmation and the root of trust for the tributary validator set — is a critical secret compromise. With the share recovered, an attacker can forge the validator's participation in subsequent MuSig/FROST protocols under the same key. Severity: High.

### Likelihood Explanation
A participant who can influence which preprocesses are included in each call (any party whose `read_preprocess` bytes reach `share_internal`, e.g., by submitting a preprocess late so it only appears in the `complete` set, or contributing a `key_pair` variant) can cause the two `sign` executions to diverge. Both paths are reachable from on-chain supplied data; no key access is required. Exploitation requires only observing the two published 32-byte shares.

### Recommendation
- Track consumed contexts: after `share_internal` produces a share, record `(context → hash(preprocesses, msg))` in `SigningProtocolDb` and refuse to `sign` again for the same context with different inputs; if identical, return the cached share rather than re-signing.
- Alternatively, derive the seed context over the full signing inputs (participant set + message digest) so divergent invocations get independent nonces.
- Implement the TODO at `signing_protocol.rs:50-54` (verify regenerated commitments match the on-chain commitments before publishing shares).

### Proof of Concept
```rust
// Conceptual: within one attempt, context ("DkgConfirmer", attempt) is fixed.
// 1) Honest path: share() signs over preprocess set A.
let share_a = confirmer.share(preprocesses_a.clone(), &key_pair).unwrap();

// 2) complete() is invoked with a set B that includes one extra participant's
//    preprocess (arrived after share() ran) — same nonces d,e; different rho/lambda.
let share_b = confirmer
    .share_internal(preprocesses_b, &key_pair) // re-signs with cached seed
    .unwrap().1;

// 3) Given Schnorrkel shares s_i = d + e*rho_i*lambda_i*secret:
//    share_a and share_b form two linear equations in (d, e*secret-terms).
//    Solve for the MuSig secret share s:
//      s = (share_a - share_b) / (rho_a*lambda_a - rho_b*lambda_b)
```

Caveat: I could not fully trace the call sites in `coordinator/src/tributary/handle.rs` (the grep returned match counts but not the surrounding code), so whether `share` and `complete` are guaranteed the identical `preprocesses` map in practice is unverified. The vulnerability exists at the `SigningProtocol` layer regardless: the API permits a second `sign` under a consumed seed with unconstrained inputs, violating the documented single-use invariant of `CachedPreprocess`.
