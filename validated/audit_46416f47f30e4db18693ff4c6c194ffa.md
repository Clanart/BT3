## Title
Version-5 metadata attributes are cleared during publish validation but not during runtime resource-group resolution, allowing unvalidated `resource_group`/`resource_group_member` attributes to reach storage-layout logic - (File: `types/src/vm/module_metadata.rs`)

### Summary
`get_metadata_from_compiled_code` special-cases `file_format` version `5` and clears `struct_attributes`/`fun_attributes` from the deserialized `RuntimeModuleMetadataV1` before returning it, because V1 metadata is only supposed to exist from `METADATA_V1_MIN_FILE_FORMAT_VERSION = 6` onward [1](#0-0) . This clearing happens in-memory only; the raw `aptos::metadata_v1` bytes stored inside the module remain untouched on chain [2](#0-1) .

`verify_module_metadata_for_module_publishing`, which enforces `is_valid_resource_group`, `is_valid_resource_group_member`, `is_valid_view_function`, etc., calls `get_metadata_from_compiled_code` and therefore iterates over an *empty* `struct_attributes`/`fun_attributes` map for any V5 module — so no per-attribute validation is ever performed for such a module, regardless of what is actually BCS-encoded in the metadata section [3](#0-2) .

`resource_groups.rs` (`validate_module_and_extract_new_entries`, `extract_resource_group_metadata_from_module`) also uses `get_metadata_from_compiled_code`, so it consistently treats the V5 module's attributes as empty both at publish time and later when another module references it as a group [4](#0-3) [5](#0-4) .

However, `data_cache.rs::get_resource_group_member_from_metadata`, which is used at execution time to resolve whether a struct is a resource-group member (affecting the storage key/layout used to read and write the resource), calls the *plain* `get_metadata` function instead [6](#0-5) . That function has no version awareness at all — it just deserializes whatever bytes are stored under `aptos::metadata_v1` [7](#0-6) .

### Finding Description
Because the two extraction functions diverge (`get_metadata_from_compiled_code` clears V5 attributes; `get_metadata` does not), a module compiled/crafted with `file_format` version exactly `5` that BCS-encodes a populated `struct_attributes` map (e.g., a `resource_group_member` attribute pointing at an arbitrary group `StructTag`) will:

1. Pass `verify_module_metadata_for_module_publishing` and `validate_module_and_extract_new_entries` trivially — because both use the version-gated function, the attribute loops never execute, so `is_valid_resource_group_member` (which requires the struct to have the `key` ability) and the upgrade-compatibility/no-new-attribute checks in `resource_groups.rs` are never invoked for this module.
2. Retain the original, unvalidated `resource_group_member`/`resource_group` bytes in on-chain storage, since clearing only mutates the temporary in-memory struct, not the stored module bytecode.
3. Be interpreted at runtime by `get_resource_group_member_from_metadata` (via the version-unaware `get_metadata`), which will honor the attacker-supplied group attribute when resolving the resource's storage state key/group membership.

This is exactly the "publish-time validated view vs. runtime-enforced view" mismatch called out in the question: `RuntimeModuleMetadataV1` is effectively different depending on which extraction path (`get_metadata_from_compiled_code` vs. `get_metadata`) is used, and only one of those paths is reachable from validation.

### Impact Explanation
Resource-group membership/scope controls how a resource is grouped for on-chain storage (which container blob it lives in). An unprivileged publisher could smuggle a `resource_group_member` attribute that was never checked for the `key`-ability requirement or for the resource-group compatibility invariants (`is_less_strict`, no removal/no-arbitrary-addition rules), by hiding it behind file_format version 5 metadata. Because `get_resource_group_member_from_metadata` honors this unvalidated attribute at execution time, the actually-enforced storage/group semantics for this module diverge from what publish-time verification certified as valid — a mismatch between verified bytes and executed behavior, which is the class of bug this review scope targets (compatibility/attribute enforcement bypass reaching protected state mutation via resource-group storage resolution).

### Likelihood Explanation
Exploitation requires the attacker to produce a `CompiledModule` whose `file_format` version field is `5` while still emitting a populated `aptos::metadata_v1` metadata entry — outside what the standard Move compiler emits (the compiler ties metadata format version to `METADATA_V1_MIN_FILE_FORMAT_VERSION = 6`), so it requires either a custom/patched compiler or direct raw-bytecode construction. There is no bytecode-verifier or module-loading rule in the code I reviewed that rejects a self-consistent V5 module carrying a V1 metadata section outright before `verify_module_metadata_for_module_publishing` is invoked; the comment at [8](#0-7)  ("Note, this should have been gated in the verify module metadata") confirms this is a known, unresolved gap rather than a hardened boundary. This is fully reachable through the ordinary unprivileged publish path (raw module bytes/write-set for a package publish transaction), so likelihood is non-trivial but requires deliberate hand-crafted bytecode.

### Recommendation
- Reject modules with `file_format` version `< METADATA_V1_MIN_FILE_FORMAT_VERSION` that also carry a non-empty `aptos::metadata_v1` section at publish time (fail closed instead of silently clearing), inside `check_metadata_format`/`verify_module_metadata_for_module_publishing`.
- Make `get_metadata` (the version-unaware, cached function used by `data_cache.rs`, `aptos_vm.rs`, etc.) apply the same version-based clearing as `get_metadata_from_compiled_code`, or refactor all runtime call sites (especially `get_resource_group_member_from_metadata`) to use the version-gated extraction consistently so publish-time and runtime enforcement can never diverge.

### Proof of Concept
1. Hand-construct (or patch the compiler output for) a `CompiledModule` with `version = 5` in its `file_format` header.
2. Attach an `aptos::metadata_v1` metadata entry whose BCS-encoded `RuntimeModuleMetadataV1.struct_attributes` maps some struct name to a `KnownAttribute::resource_group_member(<arbitrary_group_struct_tag>)`, where the struct does **not** have the `key` ability (which would fail `is_valid_resource_group_member` if checked).
3. Publish the module. `verify_module_metadata_for_module_publishing` calls `get_metadata_from_compiled_code`, sees `code.version() == 5`, clears `struct_attributes`, and the attribute loop at [9](#0-8)  never executes — publish succeeds despite the invalid attribute.
4. At runtime, trigger a resource read/write on the struct so `get_resource_group_member_from_metadata` (data_cache.rs) is invoked; it calls the plain `get_metadata`, which deserializes the *original* (uncleared) bytes and returns the crafted `resource_group_member` attribute, honoring group membership that was never validated.
5. Compare against `validate_module_and_extract_new_entries`/`extract_resource_group_metadata_from_module` (resource_groups.rs), which — using the version-gated function on the same stored module — report the struct has *no* resource-group attributes at all, demonstrating the inconsistency described in the question.

pub fn get_metadata_from_compiled_code(
    code: &impl CompiledCodeMetadata,
) -> Option<RuntimeModuleMetadataV1> {
    if let Some(data) = find_metadata(code.metadata(), APTOS_METADATA_KEY_V1) {
        let mut metadata = bcs::from_bytes::<RuntimeModuleMetadataV1>(&data.value).ok();
        // Clear out metadata for v5, since it shouldn't have existed in the first place and isn't
        // being used. Note, this should have been gated in the verify module metadata.
        if code.version() == 5 {
            if let Some(metadata) = metadata.as_mut() {
                metadata.struct_attributes.clear();
                metadata.fun_attributes.clear();
            }
        }
        metadata
    } else if let Some(data) = find_metadata(code.metadata(), APTOS_METADATA_KEY) {
        // Old format available, upgrade to new one on the fly
        let data_v0 = bcs::from_bytes::<RuntimeModuleMetadata>(&data.value).ok()?;
        Some(data_v0.upgrade())
    } else {
        None
    }
}
