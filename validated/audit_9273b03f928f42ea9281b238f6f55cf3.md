I found a promising area — the fee/weight calculation in the Bitcoin wallet. Let me verify the details.### Title
OP_RETURN data output omitted from weight/vbyte calculation causes systematically under-priced fees and bypass of the standard-weight check - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report's bug class is a safety check evaluated against an operand that omits a required component: the liquidation check used `assetAmount` (principal) instead of `repaymentAmount` (principal + interest), so the trigger fired only after the deficit was already guaranteed. The same shape exists in `SignableTransaction::new`: the transaction's weight and vsize — which drive `needed_fee`, the `NotEnoughFunds` bound, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` bound — are computed by `calculate_weight_vbytes`, which builds its template transaction exclusively from `payments` and `change`, never including the OP_RETURN `data` output that is unconditionally appended to `tx_outs` when `data` is `Some`. The signed transaction is therefore larger than every bound checked against, by up to ~92 vbytes (80-byte data cap + script overhead).

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` pushes the OP_RETURN output into `tx_outs` at lines 194–202, but both calls to `calculate_weight_vbytes` (lines 204 and 226) pass only `payments` (and optionally `change`). `calculate_weight_vbytes` (lines 62–99) constructs the template `Transaction` solely from those arguments, so:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) undercounts the real virtual size. The actual transaction broadcast by `TransactionSignatureMachine::complete` includes the OP_RETURN output, so the realized fee rate is `needed_fee / actual_vsize < fee_per_vbyte`. With an 80-byte payload the shortfall is ~90+ vbytes worth of fee.
- The `weight > MAX_STANDARD_TX_WEIGHT` check at line 241 uses the understated `weight`, so a transaction that is actually non-standard (> 400,000 WU) passes construction and can never be relayed — the inputs backing it are effectively locked/unspendable in the intended plan.
- The `NotEnoughFunds` check at line 215 and the change-amount computation at lines 224–235 are likewise evaluated against the understated fee, so change is slightly over-credited relative to the real required fee (the difference is burned as extra fee, but the bounds are wrong).

The bug is reachable through the public API `SignableTransaction::new(inputs, payments, change, data, fee_per_vbyte)` where `data` is attacker-influenced transaction data committed into the signed transaction (the codebase's test at `networks/bitcoin/tests/wallet.rs` lines 185–191 exercises `Some(vec![0; 80])` as a valid input). The signed bytes (the Bitcoin transaction the threshold key signs via `taproot_key_spend_signature_hash`, lines 373–390) include an output the fee/size logic pretended did not exist — directly analogous to the report's liquidation check ignoring the interest component of `repaymentAmount`.

### Impact Explanation
Any transaction carrying an OP_RETURN payload pays a strictly lower effective fee rate than the caller specified. At fee rates near the relay minimum, the produced transaction is below `DEFAULT_MIN_RELAY_TX_FEE` on its true vsize and will be rejected or sit unconfirmed, stalling the spend of the multisig inputs. At the size boundary, a transaction exceeding `MAX_STANDARD_TX_WEIGHT` slips past the check and is non-relayable, rendering the consumed inputs' value unspendable through the intended path (DoS / freezing of funds). This is deterministic for every caller that supplies `data`; no malicious peer or special timing is required. Severity: Medium — it is a systematic mis-computation degrading/breaking liveness of spends rather than direct theft.

### Likelihood Explanation
The flaw triggers whenever `data.is_some()` at construction. The omission is unconditional — `calculate_weight_vbytes` has no parameter that could account for the OP_RETURN output — so the under-estimate occurs on every such call. One caveat: in the current processor wiring (`processor/src/networks/bitcoin.rs` `make_signable_transaction`), `None` is passed for `data`, so the vulnerability is latent in the in-scope wallet library rather than exercised by the deployed Bitcoin processor today; it is reachable by any integrator/caller (or future wiring of `Payment.data`, which exists at `processor/src/plan.rs:19`) passing OP_RETURN data to be signed.

### Recommendation
Include the OP_RETURN output in the template transaction used for weight/vbyte calculation. The cleanest fix is to compute the template from `tx_outs` after all outputs (payments, OP_RETURN, change) are determined, or to add a `data: Option<&[u8]>` parameter to `calculate_weight_vbytes` that pushes the same `ScriptBuf::new_op_return` output before calling `tx.weight()`, mirroring the existing `change` handling. Both `calculate_weight_vbytes` call sites (lines 204 and 226) must account for the data output so `needed_fee`, `NotEnoughFunds`, `TooLowFee`, and `TooLargeTransaction` are evaluated against the transaction that will actually be signed.

### Proof of Concept

```rust
// networks/bitcoin/tests/wallet.rs-style PoC
let inputs = vec![funded_output];               // ReceivedOutput worth >> payments
let payments = vec![(p2tr_script_buf(key).unwrap(), 1000)];
let data = vec![0u8; 80];                       // max allowed OP_RETURN payload
let fee_per_vbyte = FEE;

let st = SignableTransaction::new(
    inputs, &payments, None, Some(data), fee_per_vbyte
).unwrap();

// The vsize the fee was computed on:
let assumed_vbytes = st.needed_fee() / fee_per_vbyte;
// The real signed transaction's vsize:
let actual_vbytes = st.transaction().vsize() as u64; // includes the OP_RETURN output

assert!(actual_vbytes > assumed_vbytes);        // OP_RETURN output was never counted
// Effective fee rate is strictly below the requested rate:
assert!(st.needed_fee() < fee_per_vbyte * actual_vbytes);
```

With `fee_per_vbyte` set so that `needed_fee` just clears `DEFAULT_MIN_RELAY_TX_FEE * assumed_vbytes / 1000`, the check at line 211 passes, yet the broadcast transaction pays under the minimum relay fee on its true vsize and is rejected — demonstrating a transaction the library "validated" that cannot actually confirm, the analog of a loan whose liquidation check validated a collateral level that already guaranteed lender loss.
