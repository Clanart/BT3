### Title
Auction module bid pool defaults to an effectively unbounded size (`math.MaxInt64`), allowing unauthenticated bidders to exhaust node memory via unbounded bid accumulation - ([File: kaiax/auction/config.go])

### Summary
The `kaiax/auction` module's `BidPool` accepts bids from any external caller (via RPC or p2p bid propagation) and only rejects a bid once `len(bidMap) >= maxBidPoolSize`. The default value of `maxBidPoolSize` is `math.MaxInt64`, i.e., effectively unlimited, so the "guardrail" never triggers in default node configurations. This mirrors the Spring Cloud Function Registry bug class (CWE-770, uncontrolled resource consumption): an actor can keep adding entries to an in-memory registry/pool with no meaningful upper bound, driving the process toward OOM.

### Finding Description
`DefaultMaxBidPoolSize` is defined as `math.MaxInt64` [1](#0-0) , and this value is used unless an operator explicitly overrides it via the `--auction.max-bid-pool-size` CLI flag [2](#0-1) [3](#0-2) .

The `BidPool.insertBid` function is the only size gate: it only refuses a new bid when there's no existing higher bid for the same `(blockNumber, targetTxHash)` key, and even then only checks `len(bp.bidMap) >= bp.maxBidPoolSize` [4](#0-3) . With the default `math.MaxInt64` cap, this check is a no-op in practice.

Critically, the only per-sender constraint is `senderHasDifferentWinner`, which only prevents a sender from holding two *winning* bids across different targets simultaneously — it does not cap the number of distinct bids (for distinct `targetTxHash` values, or distinct future block numbers up to `allowFutureBlock`) a single sender can insert into `bidMap`/`bidTargetMap`/`bidWinnerMap` before eviction occurs. Each accepted bid is stored in three separate maps (`bidMap`, `bidTargetMap`, `bidWinnerMap`) [5](#0-4) , multiplying the per-bid memory footprint.

Bids reach this insertion path from a `BidPool.AddBid` call gated only by `validateBid` and a peer-level rate limiter (`bidsPerSecondPerPeer = 300`) [6](#0-5) ; the rate limiter throttles *messages per second per peer identity* but does not bound the total pool size or total number of distinct targets/blocks a bidder can occupy over time. Cleanup only occurs via `removeOldBids`, which is driven by block progression (`num`, `allowFutureBlock = 2`) [7](#0-6)  — so an attacker who can sustain bid submission faster than blocks are produced, or who spreads bids across many distinct `targetTxHash` values within the small future-block window, can grow the three maps without the `maxBidPoolSize` cap ever being reached.

### Impact Explanation
Because `maxBidPoolSize` defaults to `math.MaxInt64`, a consensus node running the auction module with default configuration has no effective memory bound on the bid pool. A remote bidder (an "unprivileged... auction bidder" per the allowed threat model) can submit a high volume of syntactically valid bids targeting many distinct pending transaction hashes and near-future block numbers, causing `bidMap`, `bidTargetMap`, and `bidWinnerMap` to grow without bound between block insertions. This is a memory-exhaustion (OOM) condition on validator/proposer nodes running the auction module, directly analogous to CVE-2026-40990's "OOM error... while attempting to add infinite amount of functions to Function Registry."

### Likelihood Explanation
The auction module is only active on consensus nodes (`SetAuctionConfig` disables it for non-consensus node types) [8](#0-7) , which somewhat limits which nodes are exposed, but consensus/validator nodes are exactly the nodes whose availability is most critical to protect. The bid submission path is reachable by any external bidder without special privileges, gated only by a per-peer rate limiter of 300 bids/sec — which still allows very high absolute throughput over time — and by the (default: unbounded) `maxBidPoolSize` check. No additional value-locking, staking, or KYC gate is required to submit a bid. This makes the likelihood of exploitation moderate-to-high on any node that has not explicitly overridden the default via `--auction.max-bid-pool-size`.

### Recommendation
- Change `DefaultMaxBidPoolSize` to a sane, finite bound (e.g., low thousands) rather than `math.MaxInt64`, so the size check in `insertBid` is a meaningful guardrail out-of-the-box.
- Add an explicit per-sender cap on the number of concurrent bids (across `bidTargetMap`/`bidWinnerMap` entries and future block numbers within `allowFutureBlock`), not just a "different winner" check, to prevent a single sender from occupying a disproportionate share of pool capacity.
- Consider bounding memory more directly (e.g., a size-based `SizeConstrainedCache`-style bound, similar to the existing pattern in `common/lru/blob_lru.go` [9](#0-8) ) instead of relying solely on entry count with an unbounded default.

### Proof of Concept
Not executed against a live node; based on static analysis of the default configuration and insertion logic:
1. Start a Kaia consensus node with default `auction.max-bid-pool-size` (`math.MaxInt64`) [1](#0-0) .
2. As an external bidder, repeatedly submit `AddBid` requests (via RPC or p2p) with distinct `TargetTxHash` values and block numbers within `allowFutureBlock` of the current head, at up to the per-peer rate limit (300/sec) using multiple peer identities to multiply throughput.
3. Because `insertBid`'s only capacity check (`len(bp.bidMap) >= bp.maxBidPoolSize`) never trips with the default value, and `senderHasDifferentWinner` doesn't limit the number of distinct targets a sender can occupy, `bidMap`, `bidTargetMap`, and `bidWinnerMap` grow unbounded between block-driven `removeOldBids` cleanups [10](#0-9) .
4. Sustained submission drives node memory usage upward until the process is OOM-killed or becomes unresponsive.

Note: I was not able to fully verify the exact behavior of `senderHasDifferentWinner` and `validateBid` (their full bodies were not returned in my searches), so the precise per-sender bid multiplicity bound is inferred from the visible `insertBid` logic and should be confirmed by a full code review before remediation.

// removeOldBids removes the old bids for the given block number.
func (bp *BidPool) removeOldBids(num uint64, txHashMap map[common.Hash]struct{}) {
	bp.bidMu.Lock()
	defer bp.bidMu.Unlock()

	// Remove the old bids.
	for bn := range bp.bidWinnerMap {
		if bn > num {
			continue
		}

		for _, bh := range bp.bidWinnerMap[bn] {
			delete(bp.bidMap, bh)
		}
		delete(bp.bidTargetMap, bn)
		delete(bp.bidWinnerMap, bn)
	}

	// Remove the bid which target tx is in the txHashMap.
	toBlock := num + allowFutureBlock
	for blockNum := num + 1; blockNum <= toBlock; blockNum++ {
		targetMap := bp.bidTargetMap[blockNum]
		if targetMap == nil {
			continue
		}

		// Collect bids to remove first to avoid modifying map during iteration
		var bidsToRemove []*auction.Bid
		for _, bid := range targetMap {
			if _, ok := txHashMap[bid.TargetTxHash]; ok {
				bidsToRemove = append(bidsToRemove, bid)
			}
		}

		// Remove collected bids
		for _, bid := range bidsToRemove {
			delete(targetMap, bid.TargetTxHash)
			delete(bp.bidWinnerMap[blockNum], bid.Sender)
			delete(bp.bidMap, bid.Hash())
		}
	}

	numBidsGauge.Update(int64(len(bp.bidMap)))
}

func (bp *BidPool) insertBid(bid *auction.Bid) error {
	bp.bidMu.Lock()
	defer bp.bidMu.Unlock()

	var (
		blockNumber  = bid.BlockNumber
		targetTxHash = bid.TargetTxHash
		sender       = bid.Sender
	)

	// Re-check bidWinnerMap here — two concurrent bids can pass validateBid together.
	if _, ok := bp.bidMap[bid.Hash()]; ok {
		return auction.ErrBidAlreadyExists
	}
	if bp.senderHasDifferentWinner(bid) {
		return auction.ErrBidSenderExists
	}

	// If same block number, same target tx hash exists, replace it if it's better
	if existingBid, ok := bp.bidTargetMap[blockNumber][targetTxHash]; ok {
		// FCFS if the bid is the same.
		if existingBid.Bid.Cmp(bid.Bid) >= 0 {
			return auction.ErrLowBid
		}

		logger.Trace("Replace bid", "old", existingBid.Hash(), "new", bid.Hash())
		delete(bp.bidMap, existingBid.Hash())
		delete(bp.bidWinnerMap[blockNumber], existingBid.Sender)
	} else {
		if int64(len(bp.bidMap)) >= bp.maxBidPoolSize {
			logger.Info("Bid pool is full", "maxBidPoolSize", bp.maxBidPoolSize, "bid", bid.Hash())
			return auction.ErrBidPoolFull
		}
	}

	hash := bid.Hash()

	bp.initializeBidMap(blockNumber)

	bp.bidMap[hash] = bid
	bp.bidTargetMap[blockNumber][targetTxHash] = bid
	bp.bidWinnerMap[blockNumber][sender] = hash

	numBidsGauge.Update(int64(len(bp.bidMap)))

	logger.Trace("Add bid", "bid", hash)

	return nil
}

// SizeConstrainedCache is a cache where capacity is in bytes (instead of item count). When the cache
// is at capacity, and a new item is added, older items are evicted until the size
// constraint is met.
//
// OBS: This cache assumes that items are content-addressed: keys are unique per content.
// In other words: two Add(..) with the same key K, will always have the same value V.
type SizeConstrainedCache[K comparable, V blobType] struct {
	size    uint64
	maxSize uint64
	lru     BasicLRU[K, V]
	lock    sync.Mutex
}

// NewSizeConstrainedCache creates a new size-constrained LRU cache.
func NewSizeConstrainedCache[K comparable, V blobType](maxSize uint64) *SizeConstrainedCache[K, V] {
	return &SizeConstrainedCache[K, V]{
		size:    0,
		maxSize: maxSize,
		lru:     NewBasicLRU[K, V](math.MaxInt),
	}
}
