### Title
First-depositor capture of pre-accumulated `queuedRewards` backlog in `donateRewards` - (File: rewards/BaseRewardPool.sol)

### Summary
`_provisionReward`, invoked by the permissionless `donateRewards(uint256 _amountReward, address _rewardToken)`, routes any provisioned reward into `rewards[token].queuedRewards` whenever `totalStaked() == 0`, and only converts the accumulated backlog into `rewardPerTokenStored` on the next provisioning call that finds `totalStaked() > 0`. Whoever holds the pool's entire stake at that single triggering block captures the full backlog in one `rewardPerTokenStored` jump, regardless of how long they have actually been staked.

### Finding Description
In `_provisionReward` [1](#0-0) , the branch is:
- If `this.totalStaked() == 0`, the incoming `_amountReward` is only added to `rewardInfo.queuedRewards` (no distribution happens).
- Otherwise, any accumulated `queuedRewards` is merged into `_amountReward` and converted into a `rewardPerTokenStored` increment scaled by `10**stakingDecimals() / totalStaked()`.

`totalStaked()` reads `IERC20(stakingToken).balanceOf(operator)` [2](#0-1) , i.e., the entire pool-wide stake held by MasterMagpie for that staking token, not a per-user snapshot at accrual time.

Exploit flow:
1. Pool has `rewards[token].queuedRewards` already large (accumulated through prior `donateRewards` or manager `queueNewRewards` calls while `totalStaked() == 0`).
2. Attacker deposits any (even minimal) amount of `stakingToken` through MasterMagpie so `totalStaked() > 0`.
3. Attacker (or anyone) calls `donateRewards(1, _rewardToken)` with `_amountReward = 1` wei — no role check beyond `isRewardToken[_rewardToken]` [3](#0-2) .
4. `_provisionReward` now sees `totalStaked() > 0`, folds the entire pre-existing `queuedRewards` backlog plus the 1 wei into `rewardPerTokenStored`, dividing by the current (attacker-dominated, possibly minimal) `totalStaked()`.
5. Attacker's `earned()` reflects (balanceOf(attacker) * rewardPerTokenStored delta) / 10**stakingDecimals — capturing the whole backlog since they are the sole/majority staker at that instant.
6. Attacker calls `getReward` through MasterMagpie and withdraws, realizing reward funds that were accrued over time and intended to be shared with future stakers proportionally.

Existing checks that fail to prevent this: there is no time-weighting, vesting, or minimum staking-duration requirement tying `queuedRewards` release to the stakers who were present while it accrued; `donateRewards` has no size floor or cooldown, and `_provisionReward` treats any nonzero `totalStaked()` at the moment of the call as fully entitled to the backlog.

### Impact Explanation
The queued backlog represents already-transferred reward tokens sitting in the contract, previously provisioned by the reward manager (`queueNewRewards`) or other donors while the pool had no stakers. A single opportunistic staker who arrives immediately before the next provisioning call can redirect the entire backlog to themselves instead of it being distributed proportionally among the accounts that actually earn it over time. This matches "theft or permanent freezing of unclaimed yield" — value that should have accrued broadly is diverted to one address.

### Likelihood Explanation
This requires: (a) a non-trivial `queuedRewards` backlog to exist (achievable any time a pool starts with rewards flowing in before the first staker, or after all stakers withdraw and rewards keep being donated), and (b) the attacker being the one who is staked when the flush-triggering provisioning call happens (which the attacker can force themselves via a 1-wei `donateRewards`). Capital cost is minimal — a trivial stake amount plus 1 wei of the reward token — and the action is fully repeatable each time the pool's `totalStaked()` returns to zero and then rewards get queued again before a new depositor arrives.

### Recommendation
Do not allow an instantaneous stake to claim a backlog accrued while `totalStaked()` was zero in a single step. Options: (1) stream/vest the flushed backlog over time rather than crediting it entirely at the next non-zero `totalStaked()` snapshot; (2) require a minimum bonding/staking duration before `rewardPerTokenStored` deltas apply to newly-staked balances; (3) refuse to flush `queuedRewards` in the very same block/transaction that a user's stake changes `totalStaked()` from zero to non-zero, instead deferring the flush to a subsequent block where the staked set is stable.

### Proof of Concept
Hardhat test plan:
1. Deploy `BaseRewardPool` with a mock `stakingToken` and `rewardToken`, and a mock `MasterMagpie` (`operator`) exposing `stakingInfo` and controllable `balanceOf(stakingToken)`.
2. With `totalStaked() == 0`, call `donateRewards(largeAmount, rewardToken)` from an arbitrary donor — assert `rewards[rewardToken].queuedRewards == largeAmount` and `rewardPerTokenStored == 0`.
3. Simulate attacker depositing a minimal stake through mocked MasterMagpie so `totalStaked() > 0` and `balanceOf(attacker) == totalStaked()`.
4. Attacker calls `donateRewards(1, rewardToken)`.
5. Assert `rewardPerTokenStored` jumped by `(largeAmount+1) * 10**stakingDecimals() / totalStaked()`, and `earned(attacker, rewardToken) ≈ largeAmount`.
6. Compare against a scenario where multiple long-term stakers were present continuously — assert the split-call/differential run yields a different (fairer) distribution than the single-flush run, demonstrating the reconciliation break between `totalStaked()` and the backlog's intended distribution.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
```
