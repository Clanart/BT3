## Analysis

The External Report's core broken invariant: a shared **spender-approval-granting mechanism** on a custody contract can leave dangling ERC-20 allowances that persist beyond the intended single-use context, because the approval-setting logic is not properly gated to the trade's success/failure path — letting an attacker exploit the standing allowance later.

The Hyperbridge analog is not "allowance not reset on failure" but a strictly stronger version of the same primitive: `CallDispatcher.dispatch()` — the shared execution vault used by `IntentGatewayV2`'s predispatch/postdispatch calldata flows — has **no caller restriction at all**. [1](#0-0) 

```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
```

There is no `onlyGateway`, `msg.sender` check, or `Ownable` guard — `dispatch()` is a bare `external` function that executes **arbitrary attacker-supplied `Call[]`** from the `CallDispatcher`'s own address/context. `CallDispatcher` also accepts raw ETH via a permissionless `receive()`. [2](#0-1) 

`CallDispatcher` is not an ephemeral, per-order contract — it is the single shared `_params.dispatcher` instance used by every order in the gateway, for both predispatch (pre-escrow swaps) and postdispatch (post-fill calldata) flows: [3](#0-2) 

Per the documented flow, predispatch assets are transferred to the `CallDispatcher`, arbitrary calls execute, and only the tokens named in `order.output.assets` / the predispatch input token are swept back to the gateway: [4](#0-3) 

Because the sweep in `_execute()` only iterates over `order.output.assets[i]` (the tokens the *order's own* calldata is expected to touch), any intermediate/residual token or ETH balance left on `CallDispatcher` by a swap route not enumerated in that specific order's outputs is **not swept** and remains sitting on the contract. Since `dispatch()` is callable by anyone, that balance — or a standing approval the attacker forces `CallDispatcher` to grant to itself — is directly stealable at will, with no dependency on a malicious relayer, prover, admin, or front-running: any EOA can call `CallDispatcher.dispatch()` directly at any block.

### Title
Permissionless `CallDispatcher.dispatch()` Allows Theft of Funds and Self-Granted Token Allowances - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.sol`, the shared execution vault used by `IntentGatewayV2` for predispatch/postdispatch order calldata, exposes `dispatch(bytes)` as an unrestricted `external` function with no caller authentication. Any address can invoke it directly to execute arbitrary `Call[]` from the dispatcher's own context — including `IERC20.approve(attacker, type(uint256).max)` on any token, or direct `transfer`/ETH-drain calls against whatever balance the dispatcher currently holds.

### Finding Description
`IntentGatewayV2` (via `IntentsBase._execute`) routes predispatch swaps (pre-escrow) and postdispatch calldata (post-fill DeFi routing) through one shared `CallDispatcher` instance referenced by `_params.dispatcher`. Assets are transferred into `CallDispatcher`, `dispatch()` runs the order's calldata, and the code then sweeps back only the tokens enumerated in that order's `output.assets` (or predispatch input token). Because `dispatch()` has no access control, this analog of the report's "approval not reset" bug is worse: the approval-granting/fund-moving capability was never gated to the gateway at all.

Any unprivileged attacker can call `CallDispatcher.dispatch()` directly (it is deployed as its own, publicly-addressable contract, referenced by address in `_params.dispatcher`) with a `Call[]` that:
1. Grants an unlimited allowance from `CallDispatcher` to an attacker-controlled address for any ERC-20 (`approve(attacker, type(uint256).max)`), exactly mirroring the report's "inflation of approvals" primitive — except here the approval is entirely attacker-initiated, not merely left over from a failed trade.
2. Directly transfers out any residual ERC-20/ETH balance sitting on `CallDispatcher` — e.g., intermediate-hop tokens from a multi-hop predispatch/postdispatch swap that are not part of `order.output.assets` and therefore never get swept back by `_execute()`.

### Impact Explanation
This is a direct "stealing or loss of funds" / "unauthorized transaction or execution" path per the bounty scope. An attacker-controlled standing allowance on the shared `CallDispatcher` lets them drain any token balance the dispatcher legitimately handles in a *future*, unrelated order's predispatch/postdispatch flow (e.g., an intermediate swap hop token), and unswept residuals from multi-hop routes can be siphoned immediately and repeatedly by anyone monitoring the dispatcher's balance — with zero reliance on a malicious relayer, governance actor, or front-running.

### Likelihood Explanation
High. `dispatch()` requires no privilege, no proof, and no special conditions — it is a plain external call. The only prerequisite is that `CallDispatcher` at some point holds a non-trivial token/ETH balance, which is a routine byproduct of the documented predispatch/postdispatch swap-then-escrow and fill-then-act patterns (Uniswap V2/V3 multi-hop calldata is explicitly supported and tested in the repo's own test suite).

### Recommendation
Restrict `CallDispatcher.dispatch()` to the authorized `IntentGatewayV2` instance(s) (e.g., an `onlyGateway`/allowlisted-caller modifier set at deployment), and additionally have `_execute()`/predispatch sweep *all* token balances the calldata could plausibly have touched (or make `CallDispatcher` a single-use, ephemeral (CREATE2/clone) contract per order rather than a long-lived shared singleton) so no allowance or balance can outlive a single order's atomic execution.

```text
### Predispatch

The `predispatch` field in `Order` contains calldata to execute *before* escrowing inputs. The predispatch assets specified in `DispatchInfo.assets` are transferred to the `CallDispatcher`, the encoded calls are executed, and the resulting tokens are transferred back to the gateway for escrow. This enables swap-then-escrow patterns — for example, a user sends ETH which the `CallDispatcher` swaps to DAI on Uniswap, and the resulting DAI is escrowed as the order input.

### Postdispatch

The `call` field in `PaymentInfo` contains calldata to execute *after* the order is filled. This enables fill-then-act patterns — for example, output tokens received from the solver are routed through a DeFi protocol before reaching the beneficiary.

Execution timing differs by mode:

- **Same-chain**: Calldata executes only after the order is **fully filled**. Partial fills do not trigger calldata — only the final fill that completes the order executes it. This ensures all output tokens are available when the calls run.
- **Cross-chain**: Calldata executes **immediately** after the solver delivers output tokens to the beneficiary, before the settlement message is dispatched back to the source chain.

After execution, any tokens remaining in the `CallDispatcher` are swept back to the gateway and collected as dust (emitting `DustCollected` for each token). When postdispatch calldata is present, 100% of any surplus (solver overpayment) goes to the protocol rather than being split with the beneficiary — this prevents manipulation of surplus distribution through calldata side effects.
```
