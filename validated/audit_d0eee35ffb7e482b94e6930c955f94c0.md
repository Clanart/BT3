### Title
Identity-encoding alias accepted by `read_G`/`EdwardsPoint::from_bytes` yields degenerate identity group keys with forgeable signatures - (crypto/dalek-ff-group/src/lib.rs)

### Summary
The external report concerns a validation boundary that passes an aliased value which resolves outside the intended domain. In Serai, `GroupEncoding::from_bytes` for `EdwardsPoint` (Ed25519) validates only that a decompressed point is torsion-free; it does not reject the identity. `C::read_G` in `crypto/ciphersuite` then enforces only canonicality of the byte encoding (`to_bytes() == encoding`), not membership in the "valid key" domain. The identity encoding is a canonical alias for a degenerate point, exactly as the symlink alias was a canonical path that escaped `sandboxRoot`. Untrusted bytes fed to `Commitments::read`, `ThresholdKeys::read`, `SchnorrSignature::read`, etc., can therefore carry identity points that downstream code treats as keys/nonces.

### Finding Description
`dalek_group!` implements `from_bytes` as:

```rust
// crypto/dalek-ff-group/src/lib.rs:429-437
fn from_bytes(bytes: &Self::Repr) -> CtOption<Self> {
  let decompressed = $DCompressed(*bytes).decompress();
  let point = decompressed.unwrap_or($DPoint::identity());
  CtOption::new(
    $Point(point),
    choice(black_box(decompressed).is_some()) & choice($torsion_free(point)),
  )
}
```

For `EdwardsPoint`, `$torsion_free` is `point.is_torsion_free()` (line 473), which is `true` for the identity. The `Group` spec's identity ban is applied only in `random()` (lines 400-410), not in `from_bytes`. `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) adds only a canonical-encoding check, which the identity encoding satisfies.

Downstream, `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:618-631`) reads `secret_share` and `n` verification shares via `read_G`/`read_F` and passes them to `ThresholdKeys::new`, which derives `group_key` by Lagrange/Constant interpolation over the shares. Bytes encoding `secret_share = 0` and all verification shares = identity deserialize successfully (identity = `0·G` is self-consistent with a zero secret share), producing `ThresholdKeys` whose `group_key` is the identity — an encoding-level alias that escaped the prime-group-minus-identity domain the `Group` contract intends.

Verification then accepts forgeries against that key: `SchnorrSignature::verify` (`crypto/schnorr/src/lib.rs:108-110`) checks `R + cA - sG == identity` via `batch_statements` (lines 88-100). With `A = identity`, the signature `(R = identity, s = 0)` satisfies `id + c·id − 0·G = identity` for every challenge `c`, i.e., for every message.

### Impact Explanation
Anyone who can feed attacker-chosen bytes to `ThresholdKeys::read` (listed as a permitted untrusted input surface) can instantiate a threshold key whose group public key is the identity, then produce valid Schnorr signatures `(identity, 0)` over arbitrary messages/challenges — a universal signature forgery against that deserialized key, with no knowledge of any private key. The same identity-acceptance applies to `Commitments::read` nonces and `DLEqProof`/`SchnorrPoK` points, where an identity nonce or public key similarly collapses the verification equation.

### Likelihood Explanation
The path is deterministic: `read_G` provably accepts the canonical identity encoding (no identity check exists in `from_bytes` or `read_G`), and the forgery equation is unconditional once `A` is identity. Reachability depends on an integrator deserializing attacker-controlled `ThresholdKeys`/signature bytes, which is the stated scope of this review. No collusion or privileged access is required — only untrusted bytes.

### Recommendation
Reject the identity in `GroupEncoding::from_bytes` for both `EdwardsPoint` and `RistrettoPoint` (add `& !point.is_identity()` to the `CtOption` choice, mirroring the `random()` ban), and/or have `Ciphersuite::read_G` reject identity points globally. Additionally, `ThresholdKeys::new` should reject identity verification shares and an identity resulting `group_key`, providing defense in depth at the domain boundary — the equivalent of requiring the fallback root to be a real, non-alias directory.

### Proof of Concept
```rust
// Attacker-controlled bytes -> ThresholdKeys::read
let mut buf = vec![];
buf.extend((Ed25519::ID.len() as u32).to_le_bytes());
buf.extend(Ed25519::ID);
buf.extend(1u16.to_le_bytes());      // t = 1
buf.extend(1u16.to_le_bytes());      // n = 1
buf.extend(1u16.to_le_bytes());      // i = 1
buf.push(1);                         // Interpolation::Lagrange
buf.extend([0u8; 32]);               // secret_share = 0
buf.extend(EdwardsPoint::identity().to_bytes()); // verification share = identity
let keys = ThresholdKeys::<Ed25519>::read(&mut buf.as_slice()).unwrap();
assert!(bool::from(keys.group_key().is_identity()));

// Forgery for any message/challenge
let sig = SchnorrSignature::<Ed25519> {
  R: EdwardsPoint::identity(),
  s: Scalar::ZERO,
};
assert!(sig.verify(keys.group_key(), any_challenge));
```
`R + cA − sG = id + c·id − 0·G = id` holds for every `c`, so verification succeeds for arbitrary messages.
