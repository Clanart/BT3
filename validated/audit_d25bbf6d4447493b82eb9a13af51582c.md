## Title
Unhandled CLVM execution exception in `TradeManager.calculate_tx_records_for_offer` can halt offer processing for a malicious offer file - (File: chia/wallet/trade_manager.py)

### Summary
The wire-webapp CVE describes an unhandled exception thrown while converting attacker-controlled message content (Markdown) to a rendered form, which permanently blocks further processing of that data. An analogous pattern exists in the Chia wallet's offer-handling code: `calculate_tx_records_for_offer` runs the puzzle/solution of every coin spend in an externally supplied `Offer` through `run()` with no exception handling, unlike the sibling `Offer.conditions()` method which wraps the same kind of CLVM execution in `try/except Exception: continue`.

### Finding Description
`TradeManager.calculate_tx_records_for_offer` (chia/wallet/trade_manager.py, in the `valid_times` computation) executes:
```python
valid_times: ConditionValidTimes = parse_timelock_info(
    parse_conditions_non_consensus(
        condition
        for spend in final_spend_bundle.coin_spends
        for condition in run(spend.puzzle_reveal, Program.from_serialized(spend.solution)).as_iter()
    )
)
``` [1](#0-0) 
This iterates over every `coin_spend` in a possibly-untrusted `Offer` (i.e., an offer file sent to the wallet by a counterparty) and calls `run()` (CLVM execution) directly with no `try/except`.

Contrast this with `Offer.conditions()` in the same subsystem, which performs the identical operation (`run_with_cost(cs.puzzle_reveal, max_cost, cs.solution)`) but explicitly wraps it:
```python
try:
    cost, conds = run_with_cost(cs.puzzle_reveal, max_cost, cs.solution)
    ...
except Exception:  # pragma: no cover
    continue
``` [2](#0-1) 

This shows the codebase is aware that CLVM execution over attacker-supplied puzzle/solution pairs can raise unexpected exceptions and must be defensively caught — but `calculate_tx_records_for_offer` does not apply the same defensive pattern.

`calculate_tx_records_for_offer` is called from `_create_offer_for_ids`/offer acceptance and preview flows in `TradeManager`, which are reached when a wallet user previews, validates, or takes an `Offer` supplied by a counterparty (an untrusted party by design in the offers protocol). If a crafted puzzle reveal/solution pair causes `run()` to raise an exception other than the ones normally expected from a bad CLVM program (e.g., a Python-level exception from a pathological/oversized program, deep recursion, or other runtime failure that CLVM execution can surface), the exception propagates unhandled out of `calculate_tx_records_for_offer`.

### Impact Explanation
Because the offending code path is only reachable when a wallet evaluates a specific, attacker-crafted offer, the practical effect is a denial of service against the wallet's ability to process that offer (and any RPC/CLI call chain built on top of `calculate_tx_records_for_offer`, e.g. offer preview / take-offer flows) — mirroring the wire-webapp bug where a single malformed message blocks rendering of the conversation until manually worked around. This does not directly cause fund loss, forged asset identity, or invalid chain state, so per the CVSS analogy this is a bounded, spend-triggered processing halt rather than a critical coin-safety bug.

### Likelihood Explanation
Likelihood is moderate: an attacker only needs to construct an `Offer` (a bytes-encoded `SpendBundle` plus notarized payments) with a puzzle reveal/solution that triggers an unexpected runtime exception during `run()` and get a victim wallet to attempt to preview/validate/take it — a normal, unprivileged interaction in the offers flow. It requires finding a CLVM input that raises something other than the "well-formed CLVM error" class already tolerated elsewhere in the codebase (as evidenced by `Offer.conditions()`'s deliberate broad catch), so exploitability depends on the existence of such an input, which was not verified with a concrete PoC failing program (see Proof of Concept caveat below).

### Recommendation
Wrap the `run()` call inside `calculate_tx_records_for_offer`'s valid-times computation in the same defensive pattern used by `Offer.conditions()` — i.e., catch `Exception` per-spend (or overall) and either skip/report the spend as having no discoverable timelock conditions rather than letting the exception propagate and abort the whole offer evaluation. Additionally, audit other CLVM `run()`/`run_with_cost()` call sites operating on offer-supplied or otherwise externally-supplied puzzle/solution pairs outside of consensus-validated code (mempool/full-node paths already defensively catch `BaseException` in `get_name_puzzle_conditions`, per [3](#0-2) ) to ensure consistent exception handling.

### Proof of Concept
A concrete failing CLVM program that causes `run()` to raise an exception distinct from ordinary CLVM evaluation errors was not identified or verified in this analysis — this is a code-inspection-based finding (asymmetry between `Offer.conditions()`'s defensive `try/except` and `calculate_tx_records_for_offer`'s unguarded `run()` over the same offer-supplied data), not a confirmed exploit. A background engineer should construct/fuzz an `Offer` with a puzzle_reveal/solution pair designed to trigger a non-standard exception (e.g., recursion limit, resource exhaustion, or a Python-level error surfaced by the CLVM interpreter bindings) and confirm it propagates out of `calculate_tx_records_for_offer` uncaught, to fully validate exploitability before treating this as a confirmed vulnerability.
