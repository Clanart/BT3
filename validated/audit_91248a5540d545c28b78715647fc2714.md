## Finding: CEI Violation in Tron IntentGatewayV2 `withdraw()` — External Transfer Before Escrow-Accounting Update

### Title
Order escrow accounting mutated after external token/ETH transfer in Tron `IntentGatewayV2.withdraw()` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron fork of `IntentGatewayV2` re-implements the intent-settlement escrow-release logic (`withdraw()`) but does **not** carry over the checks-effects-interactions (CEI) fix that the canonical EVM implementation applies. In the canonical contract, `_orders[commitment][token]` is decremented *before* the external transfer [1](#0-0) . In the Tron contract, the external transfer happens first and the escrow ledger is only updated afterward, for both per-token escrow and accumulated transaction fees [2](#0-1) . This is precisely the bug class described in the seed report: state (the balance/escrow record) is updated in a callback/after-effect step instead of before the value transfer.

### Finding Description
`withdraw()` in the Tron contract:
1. Sets `_filled[body.commitment] = beneficiary` (correctly, before any external call) [3](#0-2) .
2. For each escrowed token, only checks `_orders[body.commitment][token] == 0` (a non-zero check, not an amount-bound check), performs the external `.call` transfer, and **only then** subtracts `amount` from `_orders[body.commitment][token]` [4](#0-3) .
3. For the accumulated transaction fees, it reads `fees`, transfers it out, and only afterwards deletes the entry [5](#0-4) .

By contrast, the canonical EVM `IntentGatewayV2`/`IntentsBase._withdraw` decrements the escrow ledger entry *before* issuing the transfer [6](#0-5) , exactly the CEI pattern the seed report recommends. The repository's own reentrancy regression tests document that this ordering was a **known, previously-exploited bug class** in `_fillSameChain`/`_withdraw` that was deliberately fixed by moving the state-write (`_filled[...] = msg.sender`) ahead of external calls [7](#0-6) .

Additionally, the Tron contract's `cancelOrder()` — the public, unprivileged entrypoint that invokes `withdraw()` for same-chain orders — has **no `nonReentrant` modifier**, whereas the canonical EVM `cancelOrder()` explicitly declares `public payable nonReentrant` [8](#0-7) . The Tron version is declared merely `public payable` [9](#0-8) , and a repo-wide check confirms no `nonReentrant` guard exists anywhere in this file.

### Impact Explanation
For a same-chain order whose input includes native TRX/ETH, `cancelOrder()` (unprivileged, callable by `order.user`) drives `withdraw(body, true)`, which sends value to `beneficiary` via a low-level `.call` before decrementing that token's escrow entry and before clearing the fee-escrow entry. Because the surrounding call stack lacks a reentrancy guard, the transferred value's `receive()`/fallback executes while the ledger for that commitment is still in its pre-transfer state. This directly matches the "fund loss / duplicate settlement" impact class covered by the bounty — order escrow, refunds, and relayer/solver-bound funds must move exactly once. Even though `_filled[commitment]` is set before the loop (blocking a trivial reentrant re-cancel of the *same* order), the ledger-then-transfer ordering for multi-token orders and for the fee sub-ledger is a structural CEI violation that removes the safety margin the canonical contract explicitly hardened against, and is inconsistent with the documented, tested security invariant elsewhere in the same protocol.

### Likelihood Explanation
High confidence that the code pattern itself is a regression relative to the hardened reference implementation (directly diffable, same protocol, same function name/purpose). What I could **not** conclusively verify within the available tool budget is a second, `_filled`-unguarded external entrypoint that reads/mutates `_orders[commitment][token]` for the *same* commitment during the reentrant window, which would be needed for an end-to-end double-spend PoC purely through Tron's `IntentGatewayV2`. This should be verified with a live reentrancy test (as already exists for the EVM side) against the Tron contract specifically.

### Recommendation
1. In `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw()`, decrement `_orders[body.commitment][token]` (and delete the `TRANSACTION_FEES` entry) **before** performing the external transfer, mirroring `IntentsBase._withdraw` in the canonical EVM contract.
2. Add a `nonReentrant` modifier (or the underlying `ReentrancyGuard`) to `cancelOrder()` in the Tron contract, matching the canonical EVM implementation.
3. Add a Tron-specific counterpart to `IntrinsicIntentsReentrancyTest.sol` to lock in the fix and catch future regressions.

### Proof of Concept
Not independently reproduced end-to-end (blocked by the `_filled[commitment]` guard for same-commitment re-entry within the scope I could verify); the finding is a confirmed code-level CEI/guard regression versus the hardened, tested reference implementation:
- Canonical (safe): decrement-then-transfer [1](#0-0) 
- Tron (unsafe): transfer-then-decrement, transfer-then-delete [10](#0-9) 
- Missing reentrancy guard on the public entrypoint: [9](#0-8)  vs. [8](#0-7)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }
