### Title
Quadratic Lagrange interpolation DoS via attacker-controlled `n`/`t` in `ThresholdKeys::read` - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to the ReDoS class (superlinear work triggered by parsing attacker-controlled input), `ThresholdKeys::read` accepts an attacker-chosen participant count `n` and threshold `t` (both `u16`, up to 65535) and then runs `ThresholdKeys::new`, which derives the group key by interpolating the verification shares over participants `1..=t`. Under `Interpolation::Lagrange`, evaluating the polynomial at zero requires computing a Lagrange coefficient per share, each coefficient being a product over all `t` indexes — O(t²) scalar operations. An unprivileged party that can feed bytes to `ThresholdKeys::read` (a listed reachable read API) obtains ~4×10⁹ field multiplications of CPU work for a ~2 MB input, an amplification far beyond linear parsing.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i` directly from the input stream at crypto/dkg/src/lib.rs:591-602, then reads `n` verification-share points at lines 620-623, and finally calls `ThresholdKeys::new(ThresholdParams::new(t, n, i)?, interpolation, ...)` at lines 625-631. `ThresholdParams::new` only validates consistency (`t <= n`, nonzero, `i <= n`); it does not bound `n` to a small constant, so `n` may be up to `u16::MAX`. With `interpolation` byte `1` (Lagrange, line 614), `ThresholdKeys::new` computes `group_key` by interpolating shares for participants `1..=t`, which performs an O(t) inner product per share — O(t²) field multiplications total.

### Impact Explanation
A ~2 MB serialized `ThresholdKeys` blob (`n = t = 65535`, Lagrange) forces billions of scalar multiplications inside key deserialization — a CPU-exhaustion DoS on any service that accepts serialized `ThresholdKeys` from untrusted input before any signature/proof check, mirroring the ReDoS advisory's "small crafted input → disproportionate compute" shape.

### Likelihood Explanation
Requires a deployment path where untrusted bytes reach `ThresholdKeys::read`. In-tree usage loads keys from the node's own database (`processor/src/key_gen.rs:57`), which is not attacker-controlled, so practical reachability depends on integrator/network exposure — hence Medium rather than High. Note this assessment is partially unverified: the exact loop structure inside `ThresholdKeys::new`'s Lagrange evaluation was not fully read, though the documented `1..=t` interpolation pattern is standard O(t²).

### Recommendation
Cap `n`/`t` at deserialization to the protocol's actual maximum set size (e.g., `MAX_KEY_SHARES_PER_SET`), or precompute Lagrange coefficients with an O(t) prefix/suffix-product formulation.

### Proof of Concept
Serialize a `ThresholdKeys` blob with `t = n = 0xffff`, interpolation byte `1`, one valid scalar, and `n` valid non-identity point encodings; feed to `ThresholdKeys::read::<&[u8]>` — the group-key derivation interpolates over all 65535 indexes, performing ~65535² coefficient multiplications before returning.
