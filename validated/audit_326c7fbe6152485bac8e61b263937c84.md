### Title
Precompile pointer registration can leave a stale pointer mapping pointing to a reverted/nonexistent contract - ([File: x/evm/keeper/pointer_upgrade.go])

### Summary
`Keeper.UpsertERCPointer` deploys pointer bytecode via `evm.Create`/`evm.GetDeploymentCode` (which run inside the EVM's snapshot/`Freeze()`-based Multistore layering) and then immediately records the pointer address via `setter(liveCtx(), pointee, contractAddr)`, where `liveCtx()` deliberately bypasses the frozen EVM snapshot layer and writes straight to the live unfrozen top of the store. [1](#0-0) 

### Finding Description
`UpsertERCPointer` explicitly documents that `evm.Create`/`evm.GetDeploymentCode` take EVM snapshots that `Freeze()` the Multistore layer, and that pointer existence checks and the final pointer-address write must instead go through `liveCtx()` — the *live, unfrozen* top of the store — because `cachekv` forbids writing to a frozen layer. [2](#0-1) 

This is structurally the same bug class as the Linux CVE: a lower-level resource (here, deployed EVM bytecode created inside an `evm.Create` call, which is itself wrapped in the caller's own outer EVM snapshot from `Prepare`/`Snapshot()`) is created, and a higher-level "mapping" (the pointer registry entry `pointee -> contractAddr`) is committed via a path (`liveCtx()`) that is deliberately outside the normal snapshot/rollback machinery that would otherwise unwind both together on error. `DBImpl.Snapshot()`/`RevertToSnapshot()` shows that reverting an outer snapshot restores `s.ctx` to a prior (unfrozen) layer and discards journal entries recorded after that watermark — but a write issued through `liveCtx()` targets the actual current top-of-stack context object captured at call time, not necessarily the frame that gets discarded by an outer-caller's `RevertToSnapshot`. [3](#0-2) 

Concretely: `UpsertERCPointer` calls `evm.Create` (line 133) which allocates and initializes the pointer contract's code inside the EVM's own snapshot layer. If that succeeds, `setter(liveCtx(), pointee, contractAddr)` (line 139) commits the pointee→contractAddr mapping outside that frame. Any precompile executor invoking `UpsertERCPointer` from inside its own EVM call frame (e.g. an `AddCW20`/`AddCW721` style precompile method executing as part of a larger outer EVM transaction) can subsequently fail for unrelated reasons after this point (e.g. running out of gas on the outer call, a revert triggered by the caller contract, or any error surfacing from code executed after the precompile call returns within the same EVM message). Because the outer EVM call's `RevertToSnapshot` unwinds the EVM-level `Create` state (the deployed contract's code, storage, and account existence) but the mapping write done through `liveCtx()` was made to the live top-level store rather than to the snapshot that gets discarded, the registry can end up recording a pointer address for a contract whose code/deployment was actually rolled back — i.e., a dangling/stale mapping analogous to a stale PTE pointing at freed memory. [4](#0-3) 

### Impact Explanation
If the pointer registry (`GetERC20CW20Pointer`/`GetERC721CW721Pointer`/etc.) records an address for which the actual contract bytecode/deployment was reverted, downstream consumers (CW<->EVM pointer bridge callers, ERC20/ERC721/ERC1155/native token pointer lookups used by both the EVM JSON-RPC and CosmWasm bridge) would resolve to a contract address with missing or inconsistent code/state. Depending on how that address is subsequently reused (e.g. a future `evm.Create` at the same address, or funds/approvals routed through the stale pointer), this can manifest as broken CW<->EVM bridging, unexpected reverts, or a state where token transfers routed through the pointer never reach a real contract — a fund-freezing/bridge-integrity issue reachable by any account able to trigger pointer registration (tokenfactory/pointer users, contract deployers) through the EVM/CW pointer bridge.

### Likelihood Explanation
This requires the pointer upsert to run inside a nested/outer EVM call context that can fail *after* `UpsertERCPointer` returns success but *before* the whole transaction commits, and for that outer failure's revert path to specifically discard the `evm.Create` frame while not discarding the `liveCtx()` write. The code comments show the authors are aware of and have carefully engineered around the frozen-layer/live-layer split, suggesting mitigations are already partially in place; however, the split write path (EVM snapshot frame vs. live unfrozen top) is exactly the kind of "two related mutations committed through different lifetime domains" pattern that historically causes these partial-state bugs, and it is unclear from the available code whether all outer call sites guarantee the `liveCtx()` write and the `evm.Create` are always unwound together in every failure path (e.g. legacy precompile versions in `precompiles/pointer/legacy/*` call analogous `AddCW20`/`AddCW721` methods with slightly different sequencing of `evm.Create` + `Set*Pointer`).

### Recommendation
Ensure the pointer-address registration write and the EVM contract deployment are unwound atomically: either journal the `setter()` write so that it participates in the same `RevertToSnapshot` unwind as the `evm.Create`/`GetDeploymentCode` call, or defer the `setter()` write until after the outer-most EVM call frame that could still revert has fully committed (e.g. record the pending pointer registration and only persist it in a post-`Finalize()` step, similar to how `RunWithOneOffEVMInstance` finalizes state after successful execution). At minimum, add an invariant check that verifies, before or after commit, that every registered pointer address in the store actually has corresponding contract code in the same committed store layer.

### Proof of Concept
Not able to construct a concrete reproducing transaction from static analysis alone — this requires confirming, via a live/instrumented node, a specific caller path where `UpsertERCPointer` is invoked from within a nested EVM call frame that subsequently fails and reverts the outer snapshot while leaving `liveCtx()`'s pointer-registry write intact. This determination requires runtime tracing of the Multistore `Freeze`/`Unfreeze`/`RevertToSnapshot` sequence across nested precompile calls, which is beyond what static code reading can conclusively prove.

func (k *Keeper) UpsertERCPointer(
	ctx sdk.Context, evm *vm.EVM, typ string, args []interface{}, getter PointerGetter, setter PointerSetter,
) (contractAddr common.Address, err error) {
	pointee := args[0].(string)
	evmModuleAddress := k.GetEVMAddressOrDefault(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName))

	var bin []byte
	bin, err = artifacts.GetParsedABI(typ).Pack("", args...)
	if err != nil {
		panic(err)
	}
	bin = append(artifacts.GetBin(typ), bin...)
	// GetDeploymentCode / Create take EVM snapshots that Freeze() Multistore layers.
	// Exists-lookup and commits must use the live unfrozen top (sdb.Ctx): cachekv
	// forbids writing a frozen layer, and same-tx readers that skip frozen-empty
	// parents would miss those writes. The precompile Prepare `ctx` is that top at
	// Prepare time, but is frozen once this Upsert snapshots. Always attach the
	// caller's gas meter (finite precompile meter in deliver) — sdb.Ctx() alone
	// carries the infinite EVM meter.
	sdb := state.GetDBImpl(evm.StateDB)
	liveCtx := func() sdk.Context {
		if sdb == nil {
			return ctx
		}
		return sdb.Ctx().WithGasMeter(ctx.GasMeter())
	}
	existingAddr, _, exists := getter(liveCtx(), pointee)
	suppliedGas := k.getEvmGasLimitFromCtx(ctx)
	var remainingGas uint64
	if exists {
		var ret []byte
		contractAddr = existingAddr
		ret, remainingGas, err = evm.GetDeploymentCode(evmModuleAddress, bin, suppliedGas, utils.Big0, existingAddr)
		if err != nil {
			return
		}
		// Only write on success: a failed GetDeploymentCode can leave ret as nil or
		// revert data, which must not clobber live pointer bytecode (even transiently).
		writeCtx := liveCtx()
		k.SetCode(writeCtx, contractAddr, ret)
		if sdb != nil {
			sdb.RefreshCodeCache(contractAddr, ret)
		}
	} else {
		_, contractAddr, remainingGas, err = evm.Create(evmModuleAddress, bin, suppliedGas, uint256.NewInt(0))
	}
	if err != nil {
		return
	}
	ctx.GasMeter().ConsumeGas(k.GetCosmosGasLimitFromEVMGas(ctx, suppliedGas-remainingGas), "ERC pointer deployment")
	if err = setter(liveCtx(), pointee, contractAddr); err != nil {
		return
	}
	ctx.EventManager().EmitEvent(sdk.NewEvent(
		types.EventTypePointerRegistered, sdk.NewAttribute(types.AttributeKeyPointerType, typ),
		sdk.NewAttribute(types.AttributeKeyPointerAddress, contractAddr.Hex()), sdk.NewAttribute(types.AttributeKeyPointee, pointee)))
	return
}

func (s *DBImpl) Snapshot() int {
	oldMS := s.ctx.MultiStore()
	newCtx := s.ctx.WithMultiStore(oldMS.CacheMultiStore()).WithEventManager(sdk.NewEventManager())
	// The layer we just branched from is now superseded: all subsequent writes go
	// to newCtx, so this layer will not change again until it is flushed (after
	// execution) or discarded by a revert. Freeze it so that deeper layers can skip
	// it for reads while it stays empty — without this, a Cosmos read at call depth
	// N (e.g. delegation-reward queries via precompiles) walks all N nested cache
	// layers, making a linear number of reads quadratic. We never freeze the base
	// layer (snapshottedCtxs[0]): it is the flush target and is read directly by
	// GetCommittedState, and it is not an EVM-created frame.
	if len(s.snapshottedCtxs) > 0 {
		if f, ok := oldMS.(interface{ Freeze() }); ok {
			f.Freeze()
		}
	}
	s.snapshottedCtxs = append(s.snapshottedCtxs, s.ctx)
	s.ctx = newCtx
	version := len(s.snapshottedCtxs) - 1
	s.journal = append(s.journal, &watermark{version: version})
	return len(s.snapshottedCtxs) - 1
}

func (s *DBImpl) RevertToSnapshot(rev int) {
	// Add bounds checking
	if rev < 0 || rev >= len(s.snapshottedCtxs) {
		panic("invalid revision number")
	}

	s.ctx = s.snapshottedCtxs[rev]
	s.snapshottedCtxs = s.snapshottedCtxs[:rev]

	// The layer we just re-exposed becomes the writable top again, so it must no
	// longer be treated as a frozen (skippable) layer: writes may now land here,
	// and Snapshot() froze it when it was superseded. Unfreezing also drops the
	// skip on any store whose parent is this layer, so reads see the new writes.
	if f, ok := s.ctx.MultiStore().(interface{ Unfreeze() }); ok {
		f.Unfreeze()
	}

	// Find the watermark index to truncate the journal
	watermarkIndex := -1
	for i := len(s.journal) - 1; i >= 0; i-- {
		entry := s.journal[i]
		entry.revert(s)
		if wm, ok := entry.(*watermark); ok && wm.version == rev {
			watermarkIndex = i
			break
		}
	}

	// Truncate the journal to remove reverted entries. codeCache mutations are
	// journaled per address (codeCacheChange), so unrelated warmed entries survive.
	if watermarkIndex >= 0 {
		s.journal = s.journal[:watermarkIndex]
	}
}
