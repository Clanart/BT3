This is a strong analog: `updateRemoteUrl` silently rewrites the local git remote based on an untrusted GitHub API field (`clone_url`), while any git operation already in flight (or started immediately after, keyed by a now-stale `gitStore.defaultRemote`/`repository.gitHubRepository`) continues to assume the old identity, mirroring the `OffRamp` bug where `usc` is swapped out from under pending operations.

### Title
Silent remote-URL rewrite from untrusted GitHub API `clone_url` redirects future pushes/fetches to attacker-controlled repository - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
Whenever Desktop refreshes a repository's GitHub metadata, `repositoryWithRefreshedGitHubRepository` fetches the repo object from the API and passes it to `updateRemoteUrl`, which will call `gitStore.setRemoteURL(...)` and rewrite the local `origin` remote to whatever `clone_url` the API returned, with no user confirmation. [1](#0-0) [2](#0-1)  This is functionally the same broken invariant as the `OffRamp` bug: a background "refresh" silently swaps out the reference (`usc`/remote URL) that all subsequent operations (`completeRequest`/`git push`) implicitly trust to still identify the same resource.

### Finding Description
`repositoryWithRefreshedGitHubRepository` is invoked frequently and automatically — on repository selection, account changes, background fetch, etc. [3](#0-2) [4](#0-3)  It calls the GitHub API for the repo's current metadata and feeds the response's `clone_url` straight into `updateRemoteUrl`, which rewrites the remote if the protocol matches and the remote hadn't been "manually changed" (i.e., it still matches the previously cached `gitHubRepository.cloneURL`) [5](#0-4) .

The guard only compares against Desktop's own previously cached `cloneURL`, not against any user intent or cryptographic binding to the repo ID. If the API response for a repository the user has open changes its `clone_url` — e.g. because the repo was renamed/transferred, a fork relationship changed, or (for GHES) a compromised/malicious server instance returns a different `clone_url` for the same `owner/name` — Desktop will accept the new value as authoritative and silently repoint `origin` at it via `git remote set-url`. [6](#0-5) 

Once the remote is repointed, `envForRemoteOperation(remote.url)` is used for the *next* push/fetch based on the *new* URL [7](#0-6) , and `getFallbackUrlForProxyResolve`/`getAccountForRepository` route credentials by endpoint/host — so if the attacker's `clone_url` still resolves to the same GitHub host, the trampoline credential helper will happily authenticate to it with the user's existing token via `findGitHubTrampolineAccount`'s origin match [8](#0-7) . The commit history and working tree are unaffected, but every `git push`/`git fetch` the user believes is talking to their known repository silently starts talking to a different repository — corrupting what the user pushes to (their commits land in the wrong/attacker repo) and what they believe they've fetched.

Existing guards do not stop this path:
- The "remote unchanged" check in `updateRemoteUrl` compares to Desktop's own cache, which was populated by the same trust chain — so a persistently malicious/compromised API response poisons the cache and then "confirms" itself on every subsequent refresh.
- There is no user prompt before `setRemoteURL` runs, unlike the explicit, user-initiated `_setRemoteURL` dispatcher action [9](#0-8) .
- There is no re-verification that the returned repository is actually the *same* repository (e.g., by GitHub numeric ID) rather than merely the same owner/name path at the time of the request.

### Impact Explanation
This allows silent corruption of what the user pushes: local commits can be pushed to a different remote URL than the one the user configured/expects, without any dialog or confirmation, matching the "silent corruption of what the user commits or pushes" impact class. Because the credential lookup only checks the URL's *origin*, and the attacker-controlled `clone_url` need not have a different origin, existing account credentials will be reused against the substituted repository.

### Likelihood Explanation
The refresh path is triggered automatically and routinely (repository selection, background fetch cycles, account changes), not only on explicit user action [4](#0-3) . The precondition is that the attacker can influence the `clone_url` field returned by the GitHub/GHES API for a given `owner/name` — this is plausible for a GitHub Enterprise Server the attacker administers/compromises, or via any scenario where the API-object trust boundary is violated (matching the "attacker controls a GitHub API object" impact category in scope). It does not require local/physical access, admin rights on the victim's machine, or pre-existing malware.

### Recommendation
- Never silently rewrite an existing remote based on API data; require explicit user confirmation before altering `git remote set-url`, similar to how forking/upstream conversion is presented to the user.
- Bind the "remote unchanged" comparison and any future rewrite to the immutable GitHub repository ID (already tracked in `GitHubRepository`) rather than only to the previously cached `clone_url`, so a same-origin but different-repository response cannot be silently accepted.
- Treat any in-flight push/fetch/credential resolution as bound to the remote URL captured at the start of the operation; do not let a concurrent metadata refresh alter the URL underneath an operation already using it.

### Proof of Concept
1. Add a GitHub Enterprise Server (or compromised/MITM'd API endpoint) account in Desktop and open a repository whose `origin` remote matches the account's `cloneURL` exactly (satisfying `remoteUrlUnchanged`).
2. Have the server return, for a subsequent `GET /repos/{owner}/{name}` call reached via Desktop's periodic/foreground refresh (`repositoryWithRefreshedGitHubRepository`), a JSON payload identical except for `clone_url` pointing to a different repository path on the same host (protocol unchanged, so `protocolsMatch` is true, and `urlsMatch` is false).
3. Observe that `updateRemoteUrl` executes `gitStore.setRemoteURL('origin', <new_clone_url>)` with no prompt to the user [10](#0-9) , confirmed by the existing unit test that demonstrates the rewrite happens automatically when `clone_url` changes [11](#0-10) .
4. Any subsequent `git push`/`git fetch` initiated by the user now targets the substituted repository using the user's existing stored credentials for that host.

```typescript
import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
```
