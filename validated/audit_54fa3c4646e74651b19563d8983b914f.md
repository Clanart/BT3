### Title
Webhook `shop_domain` used for job dispatch is not covered by HMAC verification, enabling cross-shop misattribution - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification` validates a webhook's authenticity using only the raw request body, while the shop identity it exposes for use by application code (`shop_domain`) is read from an unauthenticated HTTP header that is never included in that signature check. Any code that uses `shop_domain` to select which shop record a webhook job acts on — the exact pattern the gem documents and generates — trusts a value that is decoupled from what was actually cryptographically verified, mirroring the `2022-02-concur` bug class where an action is credited to the wrong identity because the accounting key was taken from an unverified/incorrect source.

### Finding Description
`PayloadVerification#hmac_valid?` computes and compares the HMAC exclusively over `request.raw_post`: [1](#0-0) 

`WebhookVerification#verify_request` only checks that HMAC, and separately exposes `shop_domain`, which is read straight from the `HTTP_X_SHOPIFY_SHOP_DOMAIN` header — a value that is never part of the data passed to `hmac_valid?`: [2](#0-1) 

The gem's own documentation instructs developers building custom webhook controllers to key their job dispatch off this unauthenticated `shop_domain` value: [3](#0-2) 

and the bundled generator templates for the mandatory privacy jobs and custom webhooks follow the same pattern, looking up the acted-upon `Shop` record purely by the `shop_domain` parameter that ultimately traces back to this unverified header: [4](#0-3) [5](#0-4) 

Because the HMAC only binds the request body, an actor who can obtain (or generate, for their own installed shop) one validly-signed webhook body can replay that same body to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` header. `verify_request` will still pass (body signature unchanged), but the dispatched job will act on the shop named in the attacker-controlled header rather than the shop that actually produced the signed body — an accounting/identity mismatch structurally analogous to the report's `masterChef.deposit()`/`withdraw()` crediting the wrong address because the identity used for bookkeeping (`_msgSender()`) didn't match the intended beneficiary.

### Impact Explanation
A malicious merchant (an "unrelated" but legitimately onboarded actor, not a privileged operator) who owns one genuinely signed webhook payload for their own shop can direct app-side, shop-scoped side effects (e.g., a `shop/redact` privacy action or any custom webhook-triggered mutation implemented per the documented pattern) at a different shop's record by only forging the header, without ever knowing the app's shared secret. This is a cross-shop data-integrity/action-misattribution issue.

### Likelihood Explanation
Exploitability requires the attacker to possess at least one validly-HMAC-signed webhook body (trivially obtainable for events on their own installed shop) and the ability to send an HTTP request with a modified `X-Shopify-Shop-Domain` header to the app's public webhook endpoint — no secret knowledge or elevated privilege is required, making this reachable from an unrelated-merchant HTTP request as required by scope.

### Recommendation
Do not use the `X-Shopify-Shop-Domain` header (or any other header/param not covered by the HMAC) as the authoritative shop identity for job dispatch or data mutation. Instead, derive the acting shop strictly from data that is part of the HMAC-signed payload (e.g., shop id embedded in the verified body, or the identity bound during webhook registration/session), and update `WebhookVerification`, the documentation, and all generator templates (`shop_redact_job.rb.tt`, `add_webhook/templates/webhook_job.rb.tt`, `add_declarative_webhook/templates/webhook_job.rb.tt`, `customers_redact_job.rb.tt`, `customers_data_request_job.rb.tt`) to stop keying shop lookup solely off the unauthenticated header value.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `shop/redact` via uninstall, or any subscribed topic) for their own shop, capturing the exact raw request body Shopify sends (and its valid `X-Shopify-Hmac-Sha256` value) via a proxy/log they control.
2. Attacker replays that exact captured request to the app's webhook endpoint, keeping the body and HMAC header identical (so `hmac_valid?` in `PayloadVerification#hmac_valid?` still succeeds), but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `WebhookVerification#verify_request` accepts the request; the custom controller/job pattern shown in `docs/shopify_app/webhooks.md` and the generator templates (e.g., `shop_redact_job.rb.tt`) looks up `Shop.find_by(shopify_domain: shop_domain)` using the forged header value and performs the shop-redaction/mutation logic against `victim-shop`, even though the cryptographically verified body was never produced by or for that shop.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
