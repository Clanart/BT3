### Title
Unbounded u32 length prefix in `SchnorrAggregate::read` allows up to ~4.3 billion point decodes per message (CPU/memory DoS) - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::<C>::read` trusts a little-endian `u32` count read from the input stream and then calls `C::read_G(reader)` once per declared element, with no upper bound. This is the same bug class as CVE-2017-15119: a remote party declares a large count/length in a message, and the deserializer burns work proportional to the declared value rather than any protocol-level limit. [1](#0-0) 

### Finding Description
`SchnorrAggregate::read` performs:

```rust
let mut len = [0; 4];
reader.read_exact(&mut len)?;
let mut Rs = vec![];
for _ in 0 .. u32::from_le_bytes(len) {
  Rs.push(C::read_G(reader)?);
}
``` [1](#0-0) 

The `u32` count can be as high as 4,294,967,295. There is no `MAX_SIGNATURES`/size cap anywhere in the loop. Every other untrusted-input deserializer in the in-scope crates is bounded by trusted parameters: `Commitments::read` in PedPoP reads exactly `params.t()` points [2](#0-1) , FROST `Commitments::read` reads exactly `generators.len()` entries from locally configured algorithm parameters [3](#0-2) , `ThresholdKeys::read` is bounded by a `u16` `n` (max 65535) [4](#0-3) , and `SecretShare`/`EncryptedMessage`/`EncryptionKeyProof` read fixed-size encodings only [5](#0-4) [6](#0-5) . `SchnorrAggregate::read` is the outlier: the only bound is the full 32-bit attacker-supplied field.

Each loop iteration performs a full point decode (`C::read_G` → `GroupEncoding::from_bytes` plus canonicity/identity validation), which is a non-trivial CPU operation, and pushes into a growable `Vec<C::G>`. With a declared count of `0xFFFFFFFF`, a peer supplying a stream of repeated valid point encodings (e.g., the same 32-byte generator encoding replayed — the loop does not check uniqueness) forces up to ~4.3 billion decompression operations and a `Vec` growing toward ~100+ GiB of `C::G` elements. Because reads happen lazily from the reader, the bytes can be trickled, keeping the victim in the decode loop for as long as the attacker keeps the stream alive — directly analogous to the QEMU NBD server reading up to 4 GB per request.

### Impact Explanation
An unprivileged party who can feed bytes into `SchnorrAggregate::read` (aggregate Schnorr signatures exchanged during signing/verification protocols built on `crypto/schnorr`) can cause unbounded CPU consumption and memory growth on the verifier/host. Since the aggregate signature is the signature output of FROST/PedPoP signing sessions and may be relayed between validators or submitted by external parties, any node deserializing an attacker-supplied aggregate signature without an outer size cap is exposed. Severity: Medium — resource exhaustion of a participating node, no secret leakage or forgery required.

### Likelihood Explanation
Reaching the bug only requires control of a serialized `SchnorrAggregate` byte stream and a reader that will supply bytes (or a large in-memory buffer). The attacker does not need a valid signature — `read` succeeds on any stream of valid point encodings regardless of whether `verify` would later pass; the damage is done during deserialization. The attacker's own bandwidth cost is the limiting factor for the memory-growth variant, but even a modest stream (e.g., 320 MB of repeated generator encodings) yields 10 million decompressions and ~300+ MB of `C::G` allocations — substantial per-request amplification of parsing CPU over typical messages. The trickle variant (slow reader) pins the deserializing thread indefinitely against a `0xFFFFFFFF` declared count.

### Recommendation
Cap the declared `Rs` count before looping. Options:
- Read the length, compare against a sane maximum (e.g., the protocol's max participant count, or a `MAX_AGGREGATE_SIGNATURES` constant), and error out early — mirroring how `RrCodec::read_request` in `coordinator/src/p2p.rs` checks `len > MAX_LIBP2P_REQRES_MESSAGE_SIZE` before allocating.
- Alternatively, verify `Rs.len() == keys_and_challenges.len()` semantics can't be enforced at read time, so a hard constant bound plus failing the read on trailing garbage (`reader` must be empty after `s`) is sufficient.

### Proof of Concept
```rust
use std::io::Cursor;
use ciphersuite::Ciphersuite;
use schnorr::SchnorrAggregate;

// C = any in-scope ciphersuite, e.g. dalek_ff_group::Ed25519
fn dos<C: Ciphersuite>() {
    // Declare u32::MAX signatures
    let mut buf = u32::MAX.to_le_bytes().to_vec();
    // Append many copies of a valid point encoding (generator is always valid).
    // Each copy costs the victim one full C::read_G decode.
    for _ in 0 .. 10_000_000 {
        buf.extend(C::generator().to_bytes().as_ref());
    }
    // The reader happily decodes all supplied points, then keeps trying to read
    // up to the declared 4.29 billion, growing Rs without bound.
    let _ = SchnorrAggregate::<C>::read(&mut Cursor::new(&buf)); // ~10M decompressions, huge Vec
}

// Trickle variant: a reader that yields valid encodings indefinitely
// (e.g., a network stream) keeps the loop alive for the full u32::MAX range.
```
