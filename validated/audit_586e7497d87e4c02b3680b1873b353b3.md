### Title
Hookify `PreToolUse`/`Stop` block rules silently no-op on unmatched field or unknown operator, giving users false confidence of protection - (File: plugins/hookify/core/rule_engine.py)

### Summary
The `hookify` plugin lets users write declarative security rules (in `.claude/hookify.*.local.md`) that are evaluated by `RuleEngine._check_condition` in `plugins/hookify/core/rule_engine.py` to decide whether a `PreToolUse`/`Stop` hook should `block` a dangerous tool call (e.g. a `rm -rf`, a write to `.env`, etc.). Just like the `payUser` bug — where an `if (amount > 0)` guard silently skipped the payout with no notice to the caller when the condition failed — `_check_condition` has two `if` branches that silently return `False` (rule does not match → operation is allowed) instead of surfacing that the rule itself is broken or malformed.

### Finding Description
`_check_condition` extracts a field value and applies a configured operator: [1](#0-0) 

Two conditions fail closed on the *evaluator*, but fail *open* on the *security decision*, with zero feedback to the user:

1. If `_extract_field` returns `None` (e.g. the rule author specifies a `field` name that isn't recognized for the given tool — there's no fallback/error path, `_extract_field` just falls through to `return None` at line 254), `_check_condition` returns `False` immediately, meaning the condition — and therefore the entire rule, since `_rule_matches` requires **all** conditions to match — never fires. There is no warning printed to stderr and no `systemMessage` describing that the rule was misconfigured. This mirrors `_extract_field`'s own `return None` fallback: [2](#0-1) 

2. If `condition.operator` doesn't match any of the six known operators (`regex_match`, `contains`, `equals`, `not_contains`, `starts_with`, `ends_with`), the `else` branch silently returns `False` with only a code comment `# Unknown operator` — no `print(..., file=sys.stderr)`, no message injected into `evaluate_rules`'s output.

Because `evaluate_rules` returns `{}` (i.e., "allow, no message") whenever no rule matches, a rule with a typo'd operator (e.g. `"regexmatch"` instead of `"regex_match"`, a docs/example mismatch, or a future operator name added to `writing-rules` docs but not yet implemented in the engine) behaves exactly like a rule that legitimately didn't match — the tool call is allowed, and the user sees no indication their intended `block` rule for that command ever existed or was evaluated: [3](#0-2) 

Compare this to `config_loader.py`'s `load_rule_file`/`load_rules`, which *do* print `Warning:`/`Error:` messages to stderr on malformed frontmatter or parse failures — showing the project's own established pattern of surfacing configuration problems, which `_check_condition` does not follow for its two silent-`False` paths.

### Impact Explanation
`hookify` is explicitly a user-authored guardrail mechanism for blocking dangerous `Bash`/`Write`/`Edit` operations before they execute (the PR-review analog documentation in this same repo, `plugins/pr-review-toolkit/agents/silent-failure-hunter.md`, explicitly calls silent failures a "critical defect" for exactly this reason: [4](#0-3) ). If a user configures a `block` rule intending to stop a dangerous command and makes a small, easy-to-make mistake (wrong `field` name, or an operator typo/mismatch with documentation), the rule is silently treated as non-matching. The tool call proceeds unblocked with no `systemMessage`, no stderr warning, and no telemetry — the user has no way to know their protection never engaged. This is a direct "hook bypass" / "tool authorization" trust-boundary failure: a locally-configured safety control that appears to exist but silently does nothing, exactly analogous to `payUser`'s `if (amount > 0)` swallowing a failed payout without notice.

### Likelihood Explanation
This requires no attacker — it's triggered purely by ordinary/likely user error when authoring hookify rules (a wrong `field` name for a given tool, or a misspelled/legacy operator string), which is a common occurrence given the freeform YAML-like frontmatter format that `config_loader.py` parses with a hand-rolled parser (no schema validation of `field`/`operator` values against the tool type). Given hookify rules are the primary customization surface for this plugin's safety enforcement, the likelihood of a rule being misconfigured (and never producing any feedback about it) is moderate-to-high.

### Recommendation
Mirror the payUser fix pattern: complement each silent `return False` with an explicit warning/notice.
- In the "unknown operator" branch (`plugins/hookify/core/rule_engine.py` line ~178-180), emit `print(f"Warning: Unknown operator '{operator}' in rule", file=sys.stderr)` before returning `False`, and consider propagating this into `evaluate_rules`'s output (e.g. a `systemMessage`) so the user is told at rule-evaluation time (not just in a debug log) that a `block`/`warn` rule is non-functional.
- In `_extract_field`'s terminal `return None` (line 254) and the corresponding `field_value is None` branch in `_check_condition` (lines 159-160), similarly warn when a configured `field` isn't recognized for the given `tool_name`, so users can tell "rule didn't match this input" apart from "rule is broken and can never match."
- Consider validating `Rule`/`Condition` objects against a known operator/field allowlist at load time (in `config_loader.py`, alongside its existing `Warning:`/`Error:` stderr messages for other malformed-file cases), fail-loud rather than fail-silent for security-relevant rules with `action: block`.

### Proof of Concept
1. Create `.claude/hookify.block-rm.local.md`:
```markdown
---
name: block-dangerous-rm
enabled: true
event: bash
action: block
conditions:
  - field: comand
    operator: regex_match
    pattern: "rm\\s+-rf"
---
Blocked: dangerous rm -rf detected!
```
(Note the typo `comand` instead of `command`.)

2. Claude Code fires the `PreToolUse` hook on a `Bash` tool call with `command: "rm -rf /important-data"`.
3. `RuleEngine._rule_matches` → `_check_condition` → `_extract_field(field="comand", tool_name="Bash", ...)` returns `None` (no matching branch for `"comand"`), so `_check_condition` returns `False` at line 160.
4. `_rule_matches` returns `False`, `evaluate_rules` finds no blocking/warning rules matched, and returns `{}` — i.e., allow, no message.
5. The `rm -rf` command executes with **zero indication** to the user that their `block` rule never evaluated as intended — identical in effect to `payUser`'s `if (amount > 0)` silently skipping the payout.

Note: I was unable to execute the plugin directly (no filesystem/terminal access in this mode) to confirm the exact runtime hook wiring end-to-end (e.g. `commands/hookify.md`/`hooks.json` invocation path); this PoC is based on static reading of `rule_engine.py` and `config_loader.py`.     def evaluate_rules(self, rules: List[Rule], input_data: Dict[str, Any]) -> Dict[str, Any]:
        """Evaluate all rules and return combined results.

        Checks all rules and accumulates matches. Blocking rules take priority
        over warning rules. All matching rule messages are combined.

        Args:
            rules: List of Rule objects to evaluate
            input_data: Hook input JSON (tool_name, tool_input, etc.)

        Returns:
            Response dict with systemMessage, hookSpecificOutput, etc.
            Empty dict {} if no rules match.
        """
        hook_event = input_data.get('hook_event_name', '')
        blocking_rules = []
        warning_rules = []

        for rule in rules:
            if self._rule_matches(rule, input_data):
                if rule.action == 'block':
                    blocking_rules.append(rule)
                else:
                    warning_rules.append(rule)

        # If any blocking rules matched, block the operation
        if blocking_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in blocking_rules]
            combined_message = "\n\n".join(messages)

            # Use appropriate blocking format based on event type
            if hook_event == 'Stop':
                return {
                    "decision": "block",
                    "reason": combined_message,
                    "systemMessage": combined_message
                }
            elif hook_event in ['PreToolUse', 'PostToolUse']:
                return {
                    "hookSpecificOutput": {
                        "hookEventName": hook_event,
                        "permissionDecision": "deny"
                    },
                    "systemMessage": combined_message
                }
            else:
                # For other events, just show message
                return {
                    "systemMessage": combined_message
                }

        # If only warnings, show them but allow operation
        if warning_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in warning_rules]
            return {
                "systemMessage": "\n\n".join(messages)
            }

        # No matches - allow operation
        return {}

        # Apply operator
        operator = condition.operator

        if operator == 'regex_match':
            return self._regex_match(pattern, field_value)
        elif operator == 'contains':
            return pattern in field_value
        elif operator == 'equals':
            return pattern == field_value
        elif operator == 'not_contains':
            return pattern not in field_value
        elif operator == 'starts_with':
            return field_value.startswith(pattern)
        elif operator == 'ends_with':
            return field_value.endswith(pattern)
        else:
            # Unknown operator
            return False
