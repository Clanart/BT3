## Finding: GitHub Desktop's clone routine explicitly disables Git's built-in protection against malicious repository clones

### Title
Disabled `GIT_CLONE_PROTECTION_ACTIVE` check re-enables case-confusion/symlink submodule RCE on `git clone --recursive` (CVE-2024-32002 class) - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` in `app/src/lib/git/clone.ts` builds the environment for every `git clone` invocation and explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` while always passing `--recursive`. [1](#0-0)  This directly disables the safety check that upstream Git introduced specifically to block malicious repositories from exploiting `clone --recursive` to write files outside the intended worktree or execute arbitrary code via crafted submodules (the class of vulnerability fixed as CVE-2024-32002/32004/32465, where a case-insensitive or symlink-confusable submodule path collides with `.git` and allows hook execution during clone). By turning this protection off unconditionally, GitHub Desktop reintroduces exactly the "attacker controls a cloned/fetched repository → code execution" scenario the external report's bug class is warning about (performing a state-changing/dangerous operation on unvalidated attacker-controlled input without the safety checks that would normally reject it).

### Finding Description
Git's own hardening flag `GIT_CLONE_PROTECTION_ACTIVE` (and the related `protected.clone` mechanism it enables) was added upstream to detect and refuse clones of repositories containing submodules whose paths are crafted to collide with the repository's own `.git` directory on case-insensitive or otherwise permissive filesystems. Without this protection, a malicious repository can be crafted so that `git clone --recursive` writes hook scripts or other files into the parent repository's `.git` directory, which are subsequently executed by Git itself (e.g., during checkout or later Git operations), yielding remote/arbitrary code execution purely by cloning an attacker-supplied repository.

In this codebase, `clone()` builds:
```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = ['-c', `init.defaultBranch=${defaultBranch}`, 'clone', '--recursive']
``` [1](#0-0) 

`--recursive` is unconditional (every clone recurses into submodules) and `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` for every clone regardless of the source (any remote URL, including one supplied via the `x-github-client://openRepo/<url>` deep link or `github://` "Open in Desktop" flow, or a CLI `--cli-clone` argument). [2](#0-1) [3](#0-2)  The `clone()` function itself contains other hardening (a `--` separator before `url`/`path` to stop CLI flag injection, and `isClonePathSensitive` to stop the destination path from targeting `~/.ssh` etc.) [4](#0-3) [5](#0-4)  — but none of those guards address the submodule-collision class of attack that `GIT_CLONE_PROTECTION_ACTIVE` was designed to stop, and this specific guard is turned off.

This mirrors the report's broken invariant precisely: the code performs a state-changing, potentially dangerous operation (`git clone --recursive`) on fully attacker-controlled input (a remote repository crafted by anyone) while deliberately bypassing the validation that upstream Git would otherwise perform, on the theory that it is "not needed."

### Impact Explanation
If Git's protection would have blocked a clone of a repository whose submodules were crafted to collide with `.git` (case-insensitive filesystem or symlink tricks), disabling `GIT_CLONE_PROTECTION_ACTIVE` removes that backstop entirely for GitHub Desktop users. Any user who clones or opens (via "Open in Desktop"/deep link) a malicious repository can have arbitrary files written into their `.git` directory and subsequently have code executed by Git — a full local code-execution primitive triggered merely by cloning a repository the attacker controls, which matches the "attacker controls a cloned/fetched repository ... result is code execution" impact category exactly.

### Likelihood Explanation
The path to trigger this is low-effort for an attacker and requires no unusual user action: publish a repository with the crafted submodule layout and get the victim to clone it through Desktop's normal "Clone repository" flow, the CLI (`github clone <url>`), or the `x-github-client://openRepo/<url>` deep link/"Open in Desktop" button, all of which funnel into the same `clone()` implementation with `GIT_CLONE_PROTECTION_ACTIVE` forced off. Because the flag is hardcoded (not conditional on any validation of the remote or its filesystem), every clone path is affected uniformly, making exploitation as reliable as the underlying Git filesystem-collision bug is on the victim's OS/filesystem.

### Recommendation
- Remove the hardcoded `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` (and any other call site importing this env override) so that Git's native submodule-collision protection remains active during clone.
- If some legitimate case requires bypassing the check, gate it behind an explicit, narrowly-scoped opt-in (not a blanket default) and document the exact trusted scenario that requires it.
- Add regression tests asserting that clones of repositories with colliding/symlinked submodule paths are rejected, mirroring the upstream Git test suite for CVE-2024-32002-class fixes.
- Audit `envForRemoteOperation` and other `git`-invocation call sites for similarly disabled safety-related environment variables.

### Proof of Concept
1. On a case-insensitive filesystem (default macOS/Windows), create a malicious repository containing a submodule whose path/name is crafted to case-collide with the top-level `.git` directory (or otherwise satisfies the layout that upstream Git's `protected.clone`/`GIT_CLONE_PROTECTION_ACTIVE` check is designed to reject), embedding a malicious hook (e.g., `post-checkout`) inside the submodule's `.git` contents.
2. Publish this repository and get a victim to open it in GitHub Desktop via any of: the Clone dialog, `github clone <url>` CLI, or an `x-github-client://openRepo/<attacker-url>` deep link.
3. Desktop calls `clone(url, path, options)`, which runs `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false` set in the environment. [1](#0-0)  Because the protection is disabled, Git proceeds with the recursive clone instead of aborting, allowing the crafted submodule content to land in/overwrite files under the victim's real `.git` directory.
4. Subsequent Git operations (or the clone itself, depending on the exact hook leveraged) execute the attacker's hook script, achieving code execution on the victim's machine.

Note: I was not able to execute this PoC in a live environment (no filesystem/terminal access here); the finding is based on static code evidence that the protective flag is unconditionally disabled for all clone operations in this codebase, which is the documented purpose-built mitigation for this exact repository-triggered RCE class in upstream Git.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
