## Finding

GitHub Desktop's `clone()` function explicitly disables Git's own built-in clone-time safety guard by setting `GIT_CLONE_PROTECTION_ACTIVE: 'false'` while performing a `--recursive` clone of an attacker-controlled remote URL. [1](#0-0) 

### Title
Recursive clone runs with Git's clone-time protection explicitly disabled (`GIT_CLONE_PROTECTION_ACTIVE=false`) - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` builds the environment for `git clone --recursive` and unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. [2](#0-1) 
`GIT_CLONE_PROTECTION_ACTIVE` is Git's own internal safety switch (added upstream to mitigate symlink/hardlink-based submodule and hooks-path attacks, e.g. the class of issues fixed by CVE-2024-32004/32020/32021/32022/32023) that is meant to detect when a nested/recursive clone operation could be tricked into writing into or executing from an unsafe location (such as a submodule path aliasing `.git/hooks` via symlinks). By force-disabling it for every clone Desktop performs, the app removes Git's own last line of defense right at the exact moment (`--recursive` clone of a fully attacker-controlled repository) that this protection is designed to catch.

### Finding Description
The report's broken invariant is: "a safety check that exists to prevent a dangerous action during a sensitive operation is not applied where it matters, and the sensitive operation is attacker-influenced." Here the analogous broken invariant is: Git ships a protection specifically to guard `clone --recursive` against malicious submodules/hooks, and Desktop actively turns that protection off rather than merely omitting to add it. The attacker fully controls the value that matters — the contents of the repository being cloned (submodule definitions, `.gitmodules`, nested paths) — via `IOpenRepositoryFromURLAction`/deep-link driven clones (`app/src/main-process/main.ts` `handleAppURL` → `parseAppURL` → `dispatcher.openRepositoryFromUrl` → `clone()`), or via a normal "Clone repository" action against any public/malicious remote. [3](#0-2) [4](#0-3) 

Existing guards in the same file do not stop this path: `isClonePathSensitive()` only checks the destination directory the user chose against a short list of sensitive home-directory locations (`.ssh`, `.gnupg`, `.config`, `.gitconfig`) — it says nothing about what happens to nested submodule checkouts once inside that directory, which is exactly the class of attack `GIT_CLONE_PROTECTION_ACTIVE` exists to stop. [5](#0-4) 
Additionally, `updateSubmodulesAfterOperation()` elsewhere in the codebase conditionally re-enables `protocol.file.allow=always` for submodule updates, showing the team is aware submodule handling requires special protocol/permission gating — yet the top-level clone path bypasses Git's dedicated clone protection entirely and unconditionally. [6](#0-5) 

### Impact Explanation
If the disabled protection is what stands between a crafted recursive-submodule repository and unsafe filesystem writes/execution (its designed purpose upstream), a malicious repository cloned through Desktop — including via the `x-github-client://openRepo/...` deep link that a user can be lured into clicking — could write into or run from a location Git's own guard would otherwise have refused, silently corrupting the resulting checkout or worse. This satisfies the "attacker controls a cloned/fetched repository...or a deep link" criterion and the "code execution / file write outside the repo" impact bar in the task's Valid Impact section.

### Likelihood Explanation
Likelihood is moderate-to-high for triggering the code path (every single clone, including one launched from a URL/deep link, goes through this exact function with the protection off, and `--recursive` means submodules are always processed), but the report does not have access to the specific Git version bundled with Desktop or a proof that a still-exploitable payload exists against that version — confirming actual exploitability requires testing against Desktop's bundled Git binary and Git's real behavior when `GIT_CLONE_PROTECTION_ACTIVE=false` is combined with a crafted `.gitmodules`.

### Recommendation
Do not unconditionally disable `GIT_CLONE_PROTECTION_ACTIVE`. If it is being turned off to work around Desktop's own progress-parsing or destination pre-creation, scope the disablement narrowly (e.g., only after confirming the destination and submodule targets resolve inside the intended directory tree via `resolveWithin`-style checks, similar to `app/src/ui/dispatcher/dispatcher.ts` lines 1957-1972), or drop `--recursive` from the initial clone and perform submodule initialization through the already-hardened `updateSubmodulesAfterOperation` path, which at least conditionally gates `protocol.file.allow`. [7](#0-6) 

### Proof of Concept
1. Attacker publishes a public repository containing a submodule definition (`.gitmodules`) crafted to alias a sensitive path (e.g., pointing a nested submodule's git-dir/hooks location at a symlink or relative path designed to escape the intended clone directory) — the classic vector `GIT_CLONE_PROTECTION_ACTIVE` was introduced to catch upstream.
2. Victim clicks a link such as `x-github-client://openRepo/<attacker-repo-url>` or uses Desktop's normal "Clone a repository" with that URL.
3. `handleAppURL` → `parseAppURL` → `dispatcher.openRepositoryFromUrl` → `openOrCloneRepository` eventually calls `clone(url, path, options)`. [3](#0-2) 
4. `clone()` runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` explicitly set, removing Git's own defense against the crafted submodule layout, while `isClonePathSensitive` only screens the top-level destination, not nested submodule targets. [2](#0-1) 

Note: I was not able to verify from this index alone the exact Git version bundled with Desktop or run an end-to-end exploit against `GIT_CLONE_PROTECTION_ACTIVE=false`; that verification would require a live Devin session with filesystem/terminal access to test against the actual bundled `dugite`/Git binary.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
