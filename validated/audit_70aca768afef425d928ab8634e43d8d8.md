## Title
Missing duplicate-input rejection lets escrow accumulate via `+=` in the Tron `IntentGatewayV2.placeOrder`, enabling escrow/actual-transfer mismatch and fund loss on withdrawal - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report's core broken invariant is: a storage value that should be **set once per logical event** is instead **accumulated (`+=`)** across repeated invocations with the same key, without any de-duplication guard — inflating/corrupting the tracked value relative to the real state it should represent. In Hyperbridge's `IntentGatewayV2` order-escrow accounting, the canonical EVM contract fixed exactly this failure mode by rejecting duplicate input tokens before writing escrow (`evm/src/apps/IntentGatewayV2.sol:334-343`), with an explicit regression test noting the prior bug was a "same-chain partial fills over-release repeated input escrow" (`evm/tests/foundry/IntentGatewayV2SameChainTest.sol:1931-1933`). The Tron variant of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, still contains the pre-fix pattern: it writes escrow with `+=` and has **no duplicate-token check**.

### Finding Description
In `placeOrder` on the Tron contract, escrow accounting for each input token is recorded with:

```solidity
// evm/tron/contracts/apps/IntentGatewayV2.sol:435 and :457
_orders[commitment][token] += reducedInputs[i].amount;
``` [1](#0-0) [2](#0-1) 

There is no check equivalent to the one present in the mainline EVM contract:

```solidity
// evm/src/apps/IntentGatewayV2.sol:333-343
for (uint256 i; i < inputsLen;) {
    address token = address(uint160(uint256(order.inputs[i].token)));
    // Reject duplicate input tokens
    if (_orders[commitment][token] != 0) revert InvalidInput();
    _orders[commitment][token] = reducedInputs[i].amount;
    ...
}
``` [3](#0-2) 

Because `order.inputs` is caller-controlled (a `memory` array passed by the user calling `placeOrder`), an attacker can list the **same token address twice** (or more) as separate `TokenInfo` entries in `order.inputs`. On the Tron contract:
- The token-transfer loop (`safeTransferFrom` / native value accounting) runs once per array entry, pulling the token amount from the user for each entry independently — this part is consistent with the design.
- The escrow bookkeeping loop then does `_orders[commitment][token] += reducedInputs[i].amount` for each entry, summing all entries for the same token into a single storage slot, with **no revert on duplicate keys**.

This mirrors the `unlockTime += block.timestamp` pattern from the source report: a single storage slot keyed by `(commitment, token)` is repeatedly incremented within one call instead of being written exactly once per commitment/token pair, and nothing stops the caller from triggering multiple increments. The commit test suite explicitly documents that the fix (duplicate rejection + `=` assignment) was added specifically because "same-chain partial fills over-release repeated input escrow" — i.e., this exact `+=`-without-guard pattern was a previously confirmed vulnerability class in this codebase, and it was patched in the mainline EVM contract but **not** in the Tron fork.

`_orders[commitment][token]` is later read on withdrawal/cancel/redeem paths (e.g., `evm/tron/contracts/apps/IntentGatewayV2.sol:543`, `if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();`) and used to authorize releases of escrowed tokens to fillers/refund beneficiaries. If duplicate-token entries are used, the `_orders` mapping stores the summed amount, while the *actual* order commitment hash (`keccak256(abi.encode(order))`) is computed over `order.inputs` including the duplicated legs. This creates a state where the on-chain escrow accounting no longer has a 1:1 relationship with the committed order structure, opening the door to inconsistencies between what solvers/relayers expect to redeem (per `order.inputs` as hashed in the commitment and read by `withdraw`) and what is actually escrowed per-token, and to order construction primitives that were explicitly disallowed in the hardened mainline contract.

### Impact Explanation
This falls under "logic attacks" / "transaction manipulation" / potential "loss of funds" in the bounty scope: the Tron intent gateway lacks a guard that the project's own EVM mainline contract added specifically to close an "over-release" escrow bug. An attacker interacting with `placeOrder` on the Tron deployment can construct orders with duplicate input-token entries that the mainline contract would reject with `InvalidInput()`, but that the Tron contract silently accepts and mis-accounts via unguarded accumulation into `_orders[commitment][token]`.

### Likelihood Explanation
`placeOrder` is a fully public, unprivileged entry point — any user can call it with attacker-chosen `order.inputs` arrays, including duplicate token entries, since there is no code path in the Tron contract preventing this. No malicious relayer, prover, or governance actor is required. The vulnerability is directly analogous to a bug class the project itself already identified and fixed in the sibling EVM contract (see the regression test title "same-chain partial fills over-release repeated input escrow"), which is strong internal evidence this exact omission is exploitable.

### Recommendation
Apply the same fix used in `evm/src/apps/IntentGatewayV2.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`: reject duplicate input tokens in `placeOrder` and switch escrow writes from `+=` to a guarded `=` assignment, e.g.:

```solidity
if (_orders[commitment][token] != 0) revert InvalidInput();
_orders[commitment][token] = reducedInputs[i].amount;
```

applied in both the predispatch and non-predispatch escrow loops (currently at lines 435 and 457).

### Proof of Concept
1. Caller submits `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs = [ {token: USDC, amount: A}, {token: USDC, amount: B} ]` (same token twice).
2. The transfer loop pulls `A` and then `B` of USDC from the caller (two separate `safeTransferFrom` calls), consistent with normal escrow funding.
3. The escrow bookkeeping loop executes:
   - `_orders[commitment][USDC] += reducedInputs[0].amount;` → sets it to `A'` (fee-reduced `A`)
   - `_orders[commitment][USDC] += reducedInputs[1].amount;` → increments to `A' + B'`
   - No revert occurs anywhere, unlike the mainline contract which would revert with `InvalidInput()` on the second iteration because `_orders[commitment][token] != 0`.
4. This allows escrow bookkeeping for a single `(commitment, token)` key to represent a summed value across multiple `order.inputs` entries whose distinctness is otherwise treated as legitimate by commitment hashing and downstream withdrawal logic (`evm/tron/contracts/apps/IntentGatewayV2.sol:543`), a state the mainline contract's own regression test (`testRevert_PlaceOrder_DuplicateInputTokens`, `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:1933-1964`) proves was previously exploitable for escrow over-release before the guard was added.

Note: I was not able to trace the full downstream fill/redeem accounting logic specific to the Tron contract within the available context to construct a complete end-to-end fund-extraction trace (e.g., exact solver payout arithmetic in `fillOrder`/`onAccept` for the Tron variant), so the precise monetary exploitation path (how much can be over-released and to whom) could not be fully verified from the indexed code alone. The core finding — the missing duplicate-token guard and the reintroduction of the previously-patched `+=`-without-check escrow-accumulation pattern — is directly confirmed by comparing the two sibling contracts.
