### Title
Argument injection via unsanitized fork/remote URLs in `git remote add`/`set-url` — ([File: app/src/lib/git/remote.ts])

### Summary
The bug report's core lesson — a value from an attacker-influenced source is trusted once and used for a privileged operation without ongoing validation of its shape/safety — has a concrete Desktop analog: `addRemote`/`setRemoteURL` build git command-line arguments directly from a remote URL string without using git's `--` end-of-options marker, unlike `clone()` which does. When the URL originates from a fork's GitHub API metadata (an object an attacker fully controls by opening a pull request from their own fork), a URL value crafted to look like a git option can be interpreted as a flag rather than a positional argument.

### Finding Description
`clone()` deliberately isolates the untrusted URL from option parsing: [1](#0-0) 

But `addRemote` and `setRemoteURL` — which also accept URLs that can originate from GitHub API responses — do not use the same `--` separator: [2](#0-1) [3](#0-2) 

These functions are reachable with a URL taken from `gitHubRepository.cloneURL`, a field populated from `IAPIRepository.clone_url`/`ssh_url` in the GitHub API response: [4](#0-3) 

The pull-request checkout path feeds the *head* (fork) repository's `cloneURL` — data describing a repository the PR *author* controls — into the upstream-remote-setup flow: [5](#0-4) 

That value ultimately reaches `ensureUpstreamRemoteURL`, which calls `addRemote`/`setRemoteURL`: [6](#0-5) 

`git remote add`/`git remote set-url` accept option flags (`-f`, `-t <branch>`, `-m <branch>`, `--mirror[=fetch|push]`, `--tags`, `--no-tags`) before/around the URL positional argument. Because Desktop never inserts `--` before the URL here (as it correctly does in `clone.ts`), a URL string beginning with `-` is not guaranteed to be treated strictly as a positional argument by git's arg parser — the exact behavior depends on the git version/subcommand parsing rules, which was not verified in this session because it would require running `git remote add`/`set-url` against a hostile string outside of this read-only index. What is verifiable from the code is the structural inconsistency: one call site (`clone.ts`) treats the URL as untrusted and defends against option injection, the other two (`remote.ts`) do not, despite consuming URLs from the same class of attacker-influenced source (fork metadata via `checkoutPullRequest`).

### Impact Explanation
If the URL is interpreted as an option rather than a value (e.g., `--mirror=fetch`), a subsequent `fetch`/`pull` against that "remote" could prune or overwrite local refs, silently corrupting the state of what the user believes they are working on/pushing — matching the "silent corruption of what the user commits or pushes" impact category. This does not require local access, admin rights, or prior malware: the only attacker action needed is opening a pull request from a repository whose metadata (name/URL) is attacker-controlled.

### Likelihood Explanation
Likelihood is *not conclusively established* here: it is unverified whether git's option parser for `remote add`/`remote set-url` would actually consume a `-`-prefixed URL as a flag versus erroring out or treating it literally as a URL (this depends on getopt-style parsing details in the installed git version, which I could not test in this read-only environment). The finding is a structural inconsistency in the codebase (missing defense in `remote.ts` that exists in `clone.ts`) rather than a demonstrated working exploit chain, so I am flagging this with reduced confidence.

### Recommendation
- Add the `--` end-of-options marker before the URL argument in `addRemote` and `setRemoteURL` in `app/src/lib/git/remote.ts`, mirroring the pattern already used in `app/src/lib/git/clone.ts`.
- Reject or escape remote URLs that begin with `-` before passing them to any git subcommand, at the boundary where GitHub API-derived values (`clone_url`, `ssh_url`, fork `cloneURL`) enter git-invoking code paths (`ensureUpstreamRemoteURL`, `updateRemoteUrl`, `checkoutPullRequest`).
- Add a unit test asserting that a URL such as `--upload-pack=...` or `--mirror=fetch` passed to `addRemote`/`setRemoteURL` is treated as a literal (invalid) URL, not as an option.

### Proof of Concept
Conceptual PoC (not executed/verified against a live git binary in this session):
1. Attacker forks a target repository and, at the point where the fork's repository metadata is fetched via the GitHub API (`IAPIRepository.clone_url`), that value is one the attacker's own account controls (e.g., by renaming the fork's default remote configuration if such control were exposed, or by controlling the underlying GHE endpoint in an enterprise scenario).
2. Victim opens/checks out the attacker's pull request via `dispatcher.checkoutPullRequest`, which passes `pullRequest.head.gitHubRepository.cloneURL` into `_checkoutPullRequest` → `ensureUpstreamRemoteURL` → `addRemote`/`setRemoteURL`: [5](#0-4) 
3. Because `git(['remote', 'add', name, url], ...)` has no `--` separator, a URL value crafted to resemble a git option is passed adjacent to git's option parser instead of being hard-isolated as a positional argument, unlike the equivalent `clone()` call site.

Given the inability to confirm git's exact parsing behavior for this specific flag/URL combination in this session, this should be validated with a live git invocation (e.g., `git remote add upstream -- '<crafted-url>'` vs without `--`) before treating it as a confirmed RCE/corruption primitive; the confirmed, code-level fact is the missing `--` protection present elsewhere in the same codebase.

  /**
   * Sets the upstream remote to a new url,
   * creating the upstream remote if it doesn't already exist
   *
   * @param remoteUrl url to be used for the upstream remote
   */
  public async ensureUpstreamRemoteURL(remoteUrl: string): Promise<void> {
    await this.performFailableOperation(async () => {
      try {
        await addRemote(this.repository, UpstreamRemoteName, remoteUrl)
      } catch (e) {
        if (
          e instanceof DugiteError &&
          e.result.gitError === GitError.RemoteAlreadyExists
        ) {
          // update upstream remote if it already exists
          await setRemoteURL(this.repository, UpstreamRemoteName, remoteUrl)
        } else {
          throw e
        }
      }
    })
  }
