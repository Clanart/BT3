### Title
Unvalidated `Participant` indexes in PedPoP blame adjudication cause a reachable panic (DoS) - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to CVE-2018-14045 (assertion failure → application exit via untrusted input), `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` with a `Participant` value taken verbatim from an attacker-supplied blame accusation. `Participant` only guarantees non-zero `u16` — there is no check that the index is ≤ `n` or was ever registered — so any value in `(n, u16::MAX]` triggers a `HashMap` index panic, aborting the blame-handling process.

### Finding Description
`BlameMachine::blame` and `AdditionalBlameMachine::blame` accept `sender` and `recipient` as raw `Participant` values and pass them unchecked into `blame_internal` → `Decryption::decrypt_with_proof` (crypto/dkg/pedpop/src/lib.rs:575-632, 674-682). Inside `decrypt_with_proof`, the DLEq statement is built by evaluating `self.enc_keys[&decryptor]` (crypto/dkg/pedpop/src/encryption.rs:388). `enc_keys` is only populated for legitimate registered participants (1..=n) via `Decryption::register`, so any other index panics. A second panic site exists in `blame_internal` at `self.commitments[&sender]` (crypto/dkg/pedpop/src/lib.rs:599) for a bogus `sender` index, reached after a successful decryption.

The attacker-controlled inputs are exactly the in-scope surface: an accusation carrying `sender`, `recipient`, an `EncryptedMessage` (readable via `EncryptedMessage::read`, crypto/dkg/pedpop/src/encryption.rs:171) and an optional `EncryptionKeyProof` (`EncryptionKeyProof::read`, line 267). To reach the panic, the message's PoP must verify for the claimed `from`, which a real participant satisfies trivially by reusing the authentic share message sent to them (the PoP binds `from` and the ciphertext, encryption.rs:302-324), or by encrypting a share to themselves.

### Impact Explanation
A single malicious participant (or, via `AdditionalBlameMachine`, any party adjudicating blame from public commitment messages) can deterministically crash the blame-evaluation path with a panic, rather than receiving a `PedPoPError`. Since DKG blame resolution typically runs inside the validator/coordinator process that must also handle signing, a panic aborts the protocol (and, if uncaught, the process), producing remote denial of service from a single unauthenticated-in-index message — the same availability-only impact class as the FIRFilter assertion failure.

### Likelihood Explanation
Trivially triggerable: no grinding, collusion, or cryptographic break is required. The accusing party simply supplies `recipient = Participant(n+1)` (or any unregistered index ≤ u16::MAX) together with a message carrying a valid PoP — which any participant possesses for messages legitimately addressed to them. `AdditionalBlameMachine::new` explicitly invites non-members to evaluate blame from commitment messages (lib.rs:649-661), widening reachability. The only mitigation is that a panic handler catching `panic::catch_unwind` would contain it, which is not guaranteed for callers of this library.

### Recommendation
Validate `sender`/`recipient` in `blame_internal` (or in `blame`/`AdditionalBlameMachine::blame`) against the registered participant set before indexing: return the accuser (`recipient`/`sender` as appropriate) or a new `PedPoPError`/`Participant` error variant when either index is not in `enc_keys`/`commitments`. Replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `.get(&k)` lookups mapped to a blame decision instead of panicking.

### Proof of Concept
```rust
// Assume a completed/ongoing PedPoP session with n participants and a
// BlameMachine (or AdditionalBlameMachine built via ::new(context, n, msgs)).
// `msg` is any EncryptedMessage<C, SecretShare<C::F>> whose PoP verifies for
// `from == honest_sender` — e.g. the real share message sent to the attacker,
// or one the attacker encrypted to themselves.
let bogus_recipient = Participant::new(u16::from(params.n()) + 1).unwrap();
// proof only needs to be Some(_); it is read via EncryptionKeyProof::read and
// the panic fires while evaluating `self.enc_keys[&decryptor]` before the
// DLEq proof is even checked.
let (_, faulty) = blame_machine.blame(honest_sender, bogus_recipient, msg, Some(proof));
// ^ panics: HashMap index `self.enc_keys[&bogus_recipient]` (encryption.rs:388)
```
Equivalently, after `decrypt_with_proof` succeeds, a `sender` index outside 1..=n panics at `self.commitments[&sender]` (crypto/dkg/pedpop/src/lib.rs:599).
