## Analog Found

### Title
Unverified callback-target address grants execution control mid-transfer in `CW1155ERC1155Pointer`, enabling reentrancy against pointer contract state - (File: `contracts/src/CW1155ERC1155Pointer.sol`)

### Summary
The Wido `performCollateralSwap` report describes handing execution control to an unverified, attacker-suppliable address at a critical point in a transaction. The same bug class is reachable in sei-chain's CW1155-to-ERC1155 pointer contract: `safeTransferFrom`/`safeBatchTransferFrom` accept an arbitrary `to` address, execute the underlying CosmWasm state transition first, and only then hand execution control to that unverified address via `onERC1155Received`/`onERC1155BatchReceived`, with no reentrancy protection anywhere in the pointer contract.

### Finding Description
`safeTransferFrom` performs the CW1155 `send` state mutation via `_execute` and only afterwards calls back into the caller-supplied `to` address if it has code, without any allowlist/verification of that address: [1](#0-0) 

The same unverified-callback-target pattern exists in `safeBatchTransferFrom`: [2](#0-1) 

The only gate on `to` is `to.code.length > 0` — there is no check that the target is a legitimate/expected receiver contract, mirroring the report's core issue that a critical-path address is not confirmed to be the intended trusted party. Unlike the Wido case (custom Comet market address), here the untrusted address is fully attacker-controlled input to a public function reachable by any EVM transaction sender. The contract has no reentrancy guard: a repository-wide search for `Reentran`/`nonReentrant` under `contracts/src/` returns no matches for the pointer contracts, confirming `CW1155ERC1155Pointer` has no protection against reentrant calls made from within `onERC1155Received`.

Because the CosmWasm-side balance mutation (`_execute`) happens strictly before the callback, an attacker can deploy a malicious `to` contract implementing `onERC1155Received` that reenters the pointer contract (e.g., calling `safeTransferFrom`/`safeBatchTransferFrom`/`balanceOf` again, or interacting with other integrations relying on this pointer) while the top-level transfer has not yet returned, observing/exploiting the already-mutated CW1155 state before external invariants (e.g., in calling DeFi contracts) are finalized.

### Impact Explanation
This falls under "unauthorized transfer via precompile or pointer" — the CW<->EVM pointer bridge is explicitly an in-scope reachable surface. A malicious, unverified `to` contract gains execution control at a point where the underlying CW1155 token balances have already moved, enabling classic cross-function/cross-contract reentrancy that can be leveraged to drain funds from any protocol or user that composes with this pointer (e.g., marketplaces, wrappers, or other contracts that trust pointer balances/transfer semantics mid-call).

### Likelihood Explanation
`safeTransferFrom`/`safeBatchTransferFrom` are public, unprivileged entry points on a pointer contract that any EVM user can call, and the `to` parameter is entirely attacker-chosen with only a bytecode-length check — no allowlisting, no `ReentrancyGuard`, and no check-effects-interactions ordering protects against reentrant callback abuse.

### Recommendation
Add a reentrancy guard (e.g., OpenZeppelin `ReentrancyGuard`/`nonReentrant`) to `safeTransferFrom` and `safeBatchTransferFrom` in `contracts/src/CW1155ERC1155Pointer.sol`, and/or reorder logic to perform the receiver-hook check before any further contract state is treated as finalized, following checks-effects-interactions. Consider also validating that `to` correctly implements `IERC165`/`IERC1155Receiver` beyond the bare `onERC1155Received` return-value check.

### Proof of Concept
1. Attacker deploys `MaliciousReceiver` implementing `onERC1155Received` that, upon being called, re-enters `CW1155ERC1155Pointer.safeTransferFrom` (or a downstream protocol relying on the pointer) using stale/mutated balance state exposed after the CW-side `_execute` has already run but before the initial call unwinds.
2. Attacker calls `safeTransferFrom(victim, address(MaliciousReceiver), tokenId, amount, data)` (assuming approval or being `from`) triggering `_execute` (CW1155 `send`) first at [3](#0-2) .
3. `MaliciousReceiver.onERC1155Received` is invoked with full execution control per [4](#0-3) , before the outer call context completes, allowing reentrant calls that exploit the already-applied state change.
