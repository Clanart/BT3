### Title
Cross-transaction contamination of `presumed_origin` and `data` in `Bitcoin::get_outputs` lets an attacker hijack other deposits' instructions and refund addresses - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::get_outputs` accumulates scanned outputs into a single `outputs` vector across all transactions in a block, but then applies the *current* transaction's `presumed_origin` (derived from `tx.input[0]`'s spent output) and embedded Serai `data` to **every** accumulated output — including outputs belonging to earlier, unrelated transactions. An unprivileged attacker who sends a dust-sized transaction to the multisig address later in the same block can overwrite a victim deposit's `presumed_origin` and `data`, causing the victim's funds to be credited to the attacker's Serai instruction or refunded to an attacker-controlled Bitcoin address.

### Finding Description
In `get_outputs`, the accumulation buffer is declared once outside the per-transaction loop:

```rust
let mut outputs = vec![];
// Skip the coinbase transaction which is burdened by maturity
for tx in &block.txdata[1 ..] {
  for output in scanner.scan_transaction(tx) { ... outputs.push(output); }
  if outputs.is_empty() { continue; }
  // populate the outputs with the origin and data
  let presumed_origin = { ... &tx.input[0] ... };
  let data = Self::extract_serai_data(tx);
  for output in &mut outputs {
    if output.kind == OutputType::External {
      output.data.clone_from(&data);
    }
    output.presumed_origin.clone_from(&presumed_origin);
  }
}
``` [1](#0-0) 

Because `outputs` is never drained per-transaction, the `&mut outputs` loop at lines 731-736 rewrites the `data` and `presumed_origin` of outputs scanned from *previous* transactions each time a later transaction also pays the scanned key. The `if outputs.is_empty() { continue }` guard is also wrong: it checks the accumulated vector, not the current transaction's contribution, so a transaction with no matching outputs still triggers recomputation as long as an earlier tx contributed — and even an attacker tx with no matching output would not trigger it, but one that does (a dust payment to the victim's multisig address) contaminates all prior entries.

Downstream, `instruction_from_output` decodes `output.data()` as a `Shorthand`/`RefundableInInstruction` and uses `instruction.origin.or(presumed_origin)` as the refund origin, deducting `2 * N::COST_TO_AGGREGATE` from the balance. [2](#0-1) 

### Impact Explanation
The attacker controls both fields injected into the victim's output:

- **`data`**: By embedding a valid `Shorthand::transfer` instruction to the attacker's own Serai address inside their own transaction (via OP_RETURN or the `OP_SHA256 PUSH MSG_HASH OP_EQUALVERIFY` witness pattern parsed by `extract_serai_data`), the attacker causes the victim's `External` output to be decoded with the *attacker's* instruction. The victim's deposit balance (minus `2 * COST_TO_AGGREGATE`) is credited to the attacker's instruction — outright theft of the deposit.
- **`presumed_origin`**: Even if the attacker's `data` is garbage, the overwritten `presumed_origin` becomes the refund destination (`instruction.origin.or(presumed_origin)`), so a failed decode refunds the victim's funds to the attacker's input address rather than the victim's.

This is a direct monetary impact reachable by any unprivileged party able to broadcast a Bitcoin transaction paying ≥ `DUST` to the multisig's P2TR script in the same block as a victim deposit.

### Likelihood Explanation
Exploitation requires the attacker's transaction to (a) appear in the same block as the victim's deposit, (b) be ordered *after* it, and (c) contain at least one output matching a registered scanner script (`scanner.scan_transaction` must return non-empty for that tx). All three are trivially satisfiable: the attacker observes the victim's deposit in mempool, crafts a dust payment to the same published multisig address with malicious `data`, and fee-bumps to land in the same block. Block ordering is minable/non-deterministic but achievable with modest probability; the attack can be retried on every deposit at near-zero cost (dust + fees only, and the attacker's own output is itself credited/refunded).

### Recommendation
Scope the origin/data assignment to only the outputs scanned from the *current* transaction: collect `scanner.scan_transaction(tx)` results into a per-transaction temporary vector, populate that vector, then `extend` the outer `outputs` — or slice `outputs[start..]` where `start` was captured before pushing the current tx's outputs. Also fix the `is_empty` guard to test the current transaction's outputs, not the accumulated buffer.

### Proof of Concept
Within a single Bitcoin block:

1. Victim broadcasts `tx_v` paying 1 BTC to the Serai multisig's external P2TR address, with a valid `Shorthand` transfer to the victim's Serai account embedded as OP_RETURN. `get_outputs` pushes `output_v` into `outputs` and correctly assigns `data_v`/`origin_v`.
2. Attacker broadcasts `tx_a` (ordered after `tx_v`) paying `DUST` to the same multisig address, embedding `Shorthand::transfer` to the **attacker's** Serai address, spending from an attacker-controlled input `in_a`.
3. `get_outputs` pushes `output_a`, then the loop at lines 731-736 iterates over `outputs = [output_v, output_a]` and writes `data_a` and `origin(in_a)` into **both**.
4. `scanner_event_to_multisig_event` → `instruction_from_output` decodes `output_v.data()` as the attacker's instruction; the victim's ~1 BTC balance is credited to the attacker's Serai address (or, if `data_a` is made undecodable, the victim's funds are refunded to `in_a`'s origin — the attacker).

The bug class mirrors CVE-2017-6590: an interface fed attacker-controlled external input (here, on-chain transaction ordering and content) performs actions on behalf of unintended data (the victim's output) because per-input scoping is violated.
