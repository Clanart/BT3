### Title
PedPoP releases the ECDH decryption key (`EncryptionKeyProof`) before the message proof-of-possession is verified, enabling an unauthenticated party to decrypt any observed encrypted share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`Encryption::decrypt` computes `key = ecdh(enc_key, msg.key)` and returns a valid `EncryptionKeyProof { key, dleq }` unconditionally; the sender's proof-of-possession (`msg.pop`) over `msg.key` is only *queued* into a `BatchVerifier`, not verified inline. In `KeyMachine::calculate_share`, a non-canonical share encoding causes an early return with `PedPoPError::InvalidShare { blame: Some(blame) }` — releasing the ECDH result — *before* `batch.verify_with_vartime_blame()` ever runs. This re-opens the exact attack the PoP was added to prevent: a malicious DKG participant reuses the per-message key `X` of another participant's ciphertext to the victim, forces a blame release, obtains `b·X`, and decrypts that victim's real message.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `Encryption::decrypt` queues `msg.pop` for batch verification under a caller-chosen `batch_id`, then immediately performs `ecdh(&self.enc_key, msg.key)` where `msg.key` is attacker-controlled, and returns `EncryptionKeyProof { key, dleq }` proving the result is correct (lines 478–500). The `EncryptedMessage` struct's own comment documents that without the PoP, "Eve could observe Alice encrypt to Bob with key X, then send Bob a message also claiming to use X … Bob would then use this to create a blame argument against Eve. When they do, they'd reveal bX, revealing Alice's message to Bob" (lines 84–90).

The protection fails in `KeyMachine::calculate_share` (`crypto/dkg/pedpop/src/lib.rs:476-499`): after `decrypt` returns `(share_bytes, blame)`, the code checks `C::F::from_repr(share_bytes.0)` and, on failure, immediately returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }` — the `BatchVerifier` containing the never-verified PoP is dropped. The share-verification statements are queued under a *distinct* `BatchId::Share(l)` and `BatchId::Decryption(l)` is only consulted if `batch.verify_with_vartime_blame()` executes, which it does not on this path. In `processor/src/key_gen.rs:416-425`, this blame is serialized and broadcast as `ProcessorMessage::InvalidShare { blame: Some(...) }`, publishing `b·X` plus a valid `DLEqProof` to everyone (verifiable via `AdditionalBlameMachine::blame` → `decrypt_with_proof`).

### Impact Explanation
Any DKG participant can send the victim an `EncryptedMessage` whose `key` field equals the per-message public key `X` of *any other participant's* ciphertext addressed to that victim, with a garbage PoP and a non-scalar-encrypted payload. The victim's published blame proof leaks `b·X` (b = victim's static encryption key). Since the ChaCha20 cipher uses a static IV (`b"DKG IV v0.2\0"`, encryption.rs:124-126) keyed solely by `hash(context, b·X)`, the attacker derives the exact keystream and decrypts the observed original ciphertext — recovering another participant's Pedersen secret share `f_alice(victim)` in plaintext. Leaked shares reduce the effective security of the DKG and, combined with other leaked/compromised shares up to `t`, enable full group private key recovery. This is unauthenticated disclosure of secret key material reachable purely through `EncryptedMessage::read` + `calculate_share` inputs.

### Likelihood Explanation
High: triggering requires only participating in a DKG session and submitting a crafted encrypted share with a non-canonical scalar payload (e.g., all-`0xFF` bytes for Ristretto/Secp256k1 field encodings) — trivially constructible. No race, no collusion, no special timing is needed; the blame release is automatic on the honest victim's code path and is even propagated by the in-tree processor (`ProcessorMessage::InvalidShare`).

### Recommendation
Verify `msg.pop` synchronously inside `Encryption::decrypt` (or before producing the `EncryptionKeyProof`) so the ECDH result is never returned for a message whose PoP is invalid — e.g., call `msg.pop.verify(msg.key, pop_challenge(...))` directly and return `None`/an error instead of queuing it. Alternatively, in `calculate_share`, defer attaching `blame` until the batch (including all `BatchId::Decryption` PoP statements) has been verified, and only release `EncryptionKeyProof` for senders whose PoP passed.

### Proof of Concept
Setup: PedPoP with `n = 3`, `t = 2` over `Ristretto`; participants Bob(1), Eve(2), Alice(3).

1. Round 2: Alice sends Bob `EncryptedMessage { key: X, pop, msg: enc_a }` where `enc_a = cipher(context, b·X) XOR repr(f_alice(1))`. Eve observes it (shares are relayed/broadcast).
2. Eve crafts `evil = EncryptedMessage { key: X, pop: <any invalid SchnorrSignature>, msg: SecretShare([0xFF; 32]) }` — the all-`0xFF` repr fails `F::from_repr` for both Ristretto and Secp256k1 scalars.
3. Bob calls `calculate_share(rng, {2: evil, 3: alice_msg})`. In `decrypt`, `evil.pop` is *queued* under `BatchId::Decryption(2)`, `key = b·X` computed, `proof = EncryptionKeyProof { key: b·X, dleq }` returned. `from_repr([0xFF;32])` returns `None` → `Err(PedPoPError::InvalidShare { participant: 2, blame: Some(proof) })`; the batch — and Eve's invalid PoP — is never verified.
4. Bob publishes `blame.serialize()` (as `processor/src/key_gen.rs` does). Eve reads `EncryptionKeyProof::read` → `proof.key = b·X`, verified by the included DLEq.
5. Eve computes `ChaCha20` via `cipher(context, proof.key)` (transcript `"DKG Encryption v0.2"`, domain `"encryption_key"`, IV `"DKG IV v0.2\0"`) and XORs the keystream against Alice's `enc_a` bytes → recovers Alice's secret share for Bob's index in clear, despite Eve never knowing `x = dlog(X)`.
