### Title
Line-count arithmetic in diff-hunk expansion can splice mismatched file content into a hunk without validating it against the actual working-file line count - (File: app/src/ui/diff/text-diff-expansion.ts)

### Summary
The external report's broken invariant is: an unchecked subtraction between a trusted assumption (`decimals <= 18`) and an externally-controlled value (a token's `decimals()`), producing a wrapped/garbage number that is used downstream without validation. The closest analog I could substantiate in this codebase is the arithmetic in the diff-hunk-expansion code path (`app/src/ui/diff/text-diff-expansion.ts`), which computes hunk line ranges by subtracting/adding hunk-header line counts (parsed from `git diff` output) against the actual number of lines in the file read from disk, and uses the result to slice lines that get inserted into the hunk as trusted "context" — with no check that the header-derived numbers actually agree with the real file content. [1](#0-0) 

### Finding Description
`getTextDiffWithBottomDummyHunk` builds a synthetic trailing hunk header directly from a subtraction of the real file line counts (`numberOfOldLines`, `numberOfNewLines`, computed from the file actually read from disk) and the *hunk-header-derived* start lines (`dummyOldStartLine`, `dummyNewStartLine`, which come from `oldStartLine + oldLineCount` / `newStartLine + newLineCount` as reported by `git diff`'s hunk header): [2](#0-1) 

Only the "new" side is guarded (`if (lastHunkNewLine >= numberOfNewLines) return null`); there is no equivalent guard for the "old" side, so `numberOfOldLines - dummyOldStartLine + 1` can go negative if the hunk header's old-side line accounting and the actual file's old-side line count ever diverge (for example, when the diff line counter used by `DiffParser`/`git diff` disagrees with the plain `\n`-based line count used elsewhere in the app, or when whitespace/line-ending settings, CRLF normalization, or a `.gitattributes` filter cause the number of lines git reports for a hunk to differ from the number of lines the renderer counts when reading the file directly). The same class of unguarded subtraction recurs in `expandTextDiffHunk`, where `from`/`to` (used to slice `newContentLines`) are derived by adding/subtracting `hunk.header.newLineCount`/`oldStartLine`/`newStartLine` without validating that these header-reported counts still correspond to the file actually on disk: [3](#0-2) 

The resulting hunk (including any newly-sliced "context" lines) is stored back into diff/UI state and is exactly the object consumed later by the partial-staging code path, where context lines are unconditionally trusted and copied verbatim into the patch that is fed to `git apply --cached`: [4](#0-3) [5](#0-4) 

### Impact Explanation
If the header-derived counts and the actual on-disk line count diverge, the "underflowed"/mismatched range can cause the expansion logic to slice the wrong lines from `newContentLines` (or produce a header with an invalid/negative line count) while still labeling the result as safe, unmodified "context." Because `formatPatch` always includes `DiffLineType.Context` lines verbatim into the outgoing patch regardless of user selection, a user who expands a hunk and stages/commits believing they are only including reviewed, unchanged context could have unintended/incorrect file content silently included in what they commit — this matches the "silent corruption of what the user commits" impact category. However, unlike the Solidity finding (a hard on-chain revert or price corruption from `decimals()` returning >18), I could not fully trace a concrete, reliable way for a hostile repository/blob to force the specific line-count divergence needed to trigger this (e.g., proving `git diff`'s line accounting and the renderer's plain-text line splitting disagree for some crafted file) within the scope of this investigation.

### Likelihood Explanation
Low-to-moderate confidence, not fully proven. The guard in `getTextDiffWithBottomDummyHunk` only checks the new-file side, which is a real asymmetry/bug, but I was not able to confirm from the indexed code exactly how `numberOfOldLines`/`numberOfNewLines` are computed at the call site relative to how `DiffParser` counts old/new lines from a possibly crafted diff (e.g., mixed line endings, no-trailing-newline markers, or binary-ish content), so I cannot assert this is reliably triggerable by a malicious repository alone.

### Recommendation
Add symmetric bounds validation for both the old and new line counts in `getTextDiffWithBottomDummyHunk` and `expandTextDiffHunk` (reject/no-op when a computed line count would be negative or otherwise inconsistent with the actual file length), and treat any header-vs-actual-file-length mismatch as a hard failure of the expansion feature rather than silently emitting a hunk with unchecked arithmetic. Given that expanded "context" lines flow directly into `formatPatch`/`git apply --cached`, consider additionally re-validating that lines marked as `Context` during expansion are byte-identical to what git itself would report for that range before allowing them into a staged patch.

### Proof of Concept
Not reproduced end-to-end; I was unable to construct a concrete crafted repository/file within this investigation that forces `numberOfOldLines < dummyOldStartLine` in `getTextDiffWithBottomDummyHunk` (app/src/ui/diff/text-diff-expansion.ts:432-441), which is the specific condition needed to trigger the missing-guard underflow. This should be treated as a leads-only finding requiring further local reproduction (e.g., via a Devin session with terminal/repo access) rather than a confirmed exploit.

export function getTextDiffWithBottomDummyHunk(
  diff: ITextDiff,
  hunks: ReadonlyArray<DiffHunk>,
  numberOfOldLines: number,
  numberOfNewLines: number
): ITextDiff | null {
  const lastHunk = hunks.at(-1)

  if (lastHunk === undefined) {
    return null
  }

  // If the last hunk doesn't reach the end of the file, create a dummy hunk
  // at the end to allow expanding the diff down.
  const lastHunkNewLine =
    lastHunk.header.newStartLine + lastHunk.header.newLineCount

  if (lastHunkNewLine >= numberOfNewLines) {
    return null
  }
  const dummyOldStartLine =
    lastHunk.header.oldStartLine + lastHunk.header.oldLineCount

    lastHunk.header.newStartLine + lastHunk.header.newLineCount

    numberOfOldLines - dummyOldStartLine + 1,
    dummyNewStartLine,
