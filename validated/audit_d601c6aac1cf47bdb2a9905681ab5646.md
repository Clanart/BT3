### Title
Missing HTML/XSS-safety escaping (`<`, `>`) in upb-based ProtoJSON string encoder — (`upb/json/encode.c`, also `php/ext/google/protobuf/php-upb.c`, `ruby/ext/google/protobuf_c/ruby-upb.c`)

### Summary
The Kirby CMS advisory (GHSA-qgp4-5qx6-548g) is a stored-XSS bug where attacker-controlled content (an uploaded SVG containing `<script>`) is served back to other users' browsers because the application failed to sanitize/escape HTML-significant characters in content it later serves as part of a page. The reusable invariant is: *any attacker-controlled string that a library serializes for eventual embedding into a browser-consumed document must escape HTML-breaking characters (`<`, `>`), because downstream consumers commonly cannot re-sanitize before rendering.*

Protobuf's own JSON printers already encode this invariant as a deliberate, cross-language defense-in-depth rule: the C++ `google::protobuf::json` writer and the Java and C# `JsonFormat`/`JsonFormatter` printers explicitly escape `<`, `>` (and in Java's case also `&`, `=`, `'`) with the comment "not required by the JSON spec, but... to prevent security bugs in javascript" / "to prevent XSS risks." The upb-based JSON encoder — shared by the C++ `upb` core, and vendored into the PHP and Ruby native extensions (`php-upb.c`, `ruby-upb.c`) — implements `jsonenc_put_escaped_char()` without that protection: only `\n \r \t \" \f \b \\` and raw control bytes `< 0x20` are escaped; `<` and `>` fall through to the `default` branch and are written verbatim.

### Finding Description
`jsonenc_put_escaped_char` in `upb/json/encode.c` (identical code duplicated in `php/ext/google/protobuf/php-upb.c` and `ruby/ext/google/protobuf_c/ruby-upb.c`): [1](#0-0) 

only escapes JSON-mandated control characters and quote/backslash; `'<'` (0x3C) and `'>'` (0x3E) are not special-cased and are copied byte-for-byte via `jsonenc_putbytes`.

Compare this with the C++ core JSON writer, which explicitly whitelists `<`/`>` as dangerous for JavaScript embedding contexts: [2](#0-1) [3](#0-2) 

and the Java `JsonFormat` printer, which escapes `<`, `>`, `&`, `=`, `'` with an explicit comment that this is "to prevent XSS risks": [4](#0-3) 

and the C# `JsonFormatter`, which does the same with a comment "Escaping of < and > are required for HTML security": [5](#0-4) 

A regression test in the Java codebase (referencing an internal bug `b/73832901`) shows this protection was added specifically to fix an HTML/script-tag injection concern: [6](#0-5) 

The pure-PHP fallback encoder (`GPBJsonWire::escapedJson`, used when the native `php-upb.c` extension is not loaded) has the same gap — it only escapes control characters below `0x20` plus `"` and `\`: [7](#0-6) 

The failed invariant that transfers from the Kirby report: a value that is (a) fully attacker-controlled (an arbitrary protobuf `string` field), (b) passed through a "safe" library transformation (ProtoJSON serialization) that other sibling implementations already treat as a security boundary, and (c) commonly re-embedded by consuming applications directly into HTML/`<script>` contexts (a documented, common pattern for hydrating client-side state from server-rendered JSON) is not defended against consistently across Protobuf's own official language implementations.

### Impact Explanation
If a consuming application (a) accepts protobuf messages/binary from a client, (b) stores or forwards attacker-controlled string fields, and (c) serializes them to JSON using PHP's or Ruby's protobuf bindings (which use the upb native extension by default) for direct inclusion inside an inline `<script>` block or HTML attribute — a pattern explicitly anticipated and defended against by Java/C#/C++ protobuf — an attacker can inject a string value such as `</script><script>alert(document.cookie)</script>` that breaks out of the script context and executes arbitrary JavaScript in the victim's browser. This is a stored/reflected XSS in the consuming application whose root cause is an inconsistency in Protobuf's own hardening across official bindings — precisely the class of "content served without expected sanitization" the Kirby advisory describes, except the "unsanitized content" here is a Protobuf library's JSON emitter, and the "editor upload" is any attacker-controlled string field a client can set.

### Likelihood Explanation
Medium-to-High for applications that (1) use the PHP or Ruby protobuf runtime (default is the native upb extension, not pure-PHP), (2) use `serializeToJsonString`/ProtoJSON on messages containing attacker-controlled strings, and (3) embed that JSON textually into HTML/JS (a common SSR/hydration pattern) rather than via the DOM API or a proper JSON-in-`<script type="application/json">` parse. No special privileges, memory corruption, or huge input is required — this is a pure logic/consistency gap reachable via the public, documented ProtoJSON API with a small, valid, bounded string payload.

### Recommendation
Align `jsonenc_put_escaped_char()` in `upb/json/encode.c` (and the vendored copies in `php-upb.c` / `ruby-upb.c`) with the C++ core (`src/google/protobuf/json/internal/writer.cc`), Java, and C# printers by escaping `<` and `>` (ideally also mirroring the additional Unicode line/paragraph-separator and bidi-control escapes already applied elsewhere) as `\u003c` / `\u003e`. Apply the same fix to the pure-PHP `GPBJsonWire::escapedJson` fallback. Add a cross-implementation regression test (mirroring `JsonFormatTest.testHtmlEscape`) to PHP/Ruby/upb JSON test suites asserting that `</script>` is emitted as `\u003c/script\u003e`.

### Proof of Concept
1. Define any proto message with a `string` field, e.g. `message M { string s = 1; }`.
2. In PHP (using the default native upb extension) or Ruby:
   - Set `s = "</script><script>alert(1)</script>"`.
   - Call the message's JSON serialization (`serializeToJsonString()` in PHP, or the Ruby equivalent).
3. Observed output (from tracing `jsonenc_put_escaped_char` in `upb/json/encode.c`, lines 268–301) contains the literal substring `</script><script>alert(1)</script>` unescaped inside the JSON string value, because `<` and `>` are not in the escape switch and fall through to the byte-copy `default` branch.
4. Contrast with the equivalent Java call `JsonFormat.printer().print(message)` on the same field value, which — per the test at `java/util/src/test/java/com/google/protobuf/util/JsonFormatTest.java:2016-2035` — produces `\u003c/script\u003e` instead, confirming the discrepancy is a genuine, currently-unpatched gap in the upb/PHP/Ruby JSON encoders rather than an intentional design difference.

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}

    private static function isJsonEscaped($c)
    {
        // See RFC 4627.
        return $c < chr($k_control_char_limit) || $c === "\"" || $c === "\\";
    }

    public static function escapedJson($value)
    {
        $escaped_value = "";
        $unescaped_run = "";
        for ($i = 0; $i < strlen($value); $i++) {
            $c = $value[$i];
            // Handle escaping.
            if (static::isJsonEscaped($c)) {
                // Use a "nice" escape, like \n, if one exists for this
                // character.
                $escape = static::jsonNiceEscape($c);
                if (is_null($escape)) {
                    $escape = "\\u00" . bin2hex($c);
                }
                if ($unescaped_run !== "") {
                    $escaped_value .= $unescaped_run;
                    $unescaped_run = "";
                }
                $escaped_value .= $escape;
            } else {
              if ($unescaped_run === "") {
                $unescaped_run .= $c;
              }
            }
        }
        $escaped_value .= $unescaped_run;
        return $escaped_value;
    }
