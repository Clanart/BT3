## Unprotected Recursive Clone Disables Git's Anti-RCE Config Protection — `GIT_CLONE_PROTECTION_ACTIVE=false` (File: `app/src/lib/git/clone.ts`)

### Summary
The external report's broken invariant is: a critical safety check that is supposed to gate untrusted, attacker-supplied data is disabled/bypassed, and the caller does not restore the missing protection, so attacker-controlled input reaches a sensitive operation unguarded. In `LendingMarket.cleanUpOrders()` the missing guard was access control; in GitHub Desktop's `clone()` function the missing guard is Git's own built-in protection against malicious repository content during `--recursive` clones.

### Finding Description
Desktop's `clone()` helper builds the environment for `git clone` and explicitly sets: [1](#0-0) 

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
  '-c',
  `init.defaultBranch=${defaultBranch}`,
  'clone',
  '--recursive',
]
```

`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git uses to control its "protected configuration" defense that was added to prevent attacker-supplied repository content (in particular malicious `.gitmodules`/submodule config combined with `--recursive`) from injecting `core.hooksPath`, `core.fsmonitor`, or other config that leads to command execution or config exfiltration on the machine performing the clone. By hard-coding this to `'false'`, Desktop unconditionally disables that check for every clone it performs, regardless of whether the URL/remote is attacker-controlled (e.g., "Open in Desktop" deep links, cloning a URL pasted by another user, or cloning a fork/PR remote added by `_findPullRequestBranch`) [2](#0-1) .

This mirrors the report's pattern exactly: the function that ingests untrusted external data (a repository's own config/submodule tree, analogous to the order book's active-order arrays) explicitly turns off the mechanism meant to reconcile/validate that data, and nothing downstream in the clone flow re-applies the missing protection. `clone()` is invoked directly from user-facing/CLI/protocol-triggered flows without any additional sanitization of submodule URLs or hook paths.

### Impact Explanation
If Git's clone protection would otherwise reject or neutralize a maliciously crafted `.gitmodules`/submodule structure (e.g., one that would set `core.hooksPath` to point at attacker-controlled executable content inside the cloned tree, or embeds symlink tricks in nested `.git` directories), forcing `GIT_CLONE_PROTECTION_ACTIVE=false` re-opens that path for any repository Desktop clones with `--recursive`. Since Desktop always uses `--recursive` [3](#0-2) , this is not an opt-in feature — it is unconditionally applied to every clone, including clones of untrusted third-party/fork URLs reached via the "Open in Desktop" URL handler (`parseAppURL`/`open-repository-from-url`) [4](#0-3)  or via `_findPullRequestBranch`'s fork-remote handling. This matches the impact classes: code execution / silent corruption of local repository state driven purely by attacker-controlled repository content, with no local/physical access or prior compromise required.

### Likelihood Explanation
Likelihood is high for exposure but requires the environment (embedded Git version and the specific submodule/hooks-path exploitation technique the protection is meant to stop) to actually be vulnerable when the safeguard is off — this is a defense-in-depth control, not the only layer (Desktop separately blocks untrusted-owner repositories via the "unsafe repository" warning shown in `add-existing-repository.tsx`/`missing-repository.tsx`, and hook execution goes through `getRepoHooks`/`withHooksEnv`) [5](#0-4) [6](#0-5) . However, those checks apply to *opening* an existing on-disk repository based on file ownership, not to the *clone* operation itself, so they do not cover the window during which `git clone --recursive` with disabled protection processes the attacker's submodule/config data.

### Recommendation
1. Do not disable `GIT_CLONE_PROTECTION_ACTIVE` globally. Determine why it was set to `'false'` (likely to work around a compatibility issue with `init.defaultBranch` or an older embedded Git behavior) and scope any workaround narrowly, or remove it entirely if the embedded Git version already handles the safe defaults correctly.
2. If disabling is required for a specific compatibility reason, apply additional mitigations: validate/sanitize `.gitmodules` entries before allowing `--recursive` to run, or perform a two-step clone (non-recursive clone + explicit `submodule update` after inspecting `.gitmodules`).
3. Add regression tests asserting that cloning a repository with a malicious `.gitmodules` (pointing to `ext::` transports or overriding `core.hooksPath`) is rejected or neutralized, matching the upstream Git protection's intended behavior.

### Proof of Concept
Conceptual PoC (requires validation on the embedded Git version bundled with this build to confirm exploitability of the specific class of protection that `GIT_CLONE_PROTECTION_ACTIVE` guards):
1. Attacker publishes a public repository containing a `.gitmodules` file crafted to abuse submodule handling during recursive clone (e.g., pointing a submodule at a path/config designed to set `core.hooksPath` or leverage a symlinked `.git` directory).
2. Attacker shares the repo URL, or a "x-github-client://openRepo/<url>" deep link, or opens a PR from a fork so Desktop calls `_findPullRequestBranch`, which adds the fork as a remote and fetches/clones it.
3. Victim clicks the link or checks out the PR in GitHub Desktop; Desktop invokes `clone()`/`git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false` [7](#0-6) .
4. With Git's built-in protection disabled, the malicious config/submodule content that the protection exists to block is processed, potentially leading to hook execution or configuration injection on the victim's machine.

Note: I was not able to execute an end-to-end exploit against the specific embedded Git binary version in this repository to confirm whether the disabled protection is currently exploitable in practice (that depends on the exact Git version and known CVE fixed by `GIT_CLONE_PROTECTION_ACTIVE`); this should be verified in a live Devin session with access to the bundled Git binary and a real clone test.
