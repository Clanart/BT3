### Title
`ThresholdKeys::read` accepts semantically inconsistent key shares, producing an unspendable group key and stuck funds - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::new` validates the *shape* of its parameters (`t <= n`, `i <= n`, share count, interpolation applicability) but never validates the *consistency* of the cryptographic material: the `secret_share` is never checked against `verification_shares[params.i()]`, and the `verification_shares` map is never checked to encode a valid threshold sharing. `ThresholdKeys::read` reconstructs `ThresholdKeys` entirely from untrusted bytes and forwards them to `ThresholdKeys::new` [1](#0-0) , so a corrupted or adversarially crafted serialization is accepted, produces a `group_key` that funds can be sent to, yet can never yield a valid signature — permanently stuck funds.

### Finding Description
`ThresholdKeys::new` checks `verification_shares.len() == n` and that each participant index is `<= n` [2](#0-1) , then computes `group_key` as the interpolation of `verification_shares` over participants `1..=t` [3](#0-2) . It never computes `C::generator() * secret_share` or compares it to `verification_shares[&params.i()]`.

Consequences, all reachable via `ThresholdKeys::read` (explicitly an untrusted-bytes entry point):

1. **Mismatched secret share.** A crafted blob with a `secret_share` unrelated to `verification_shares[i]` is accepted. At signing time, `view()` interpolates the bogus secret share [4](#0-3) , producing an invalid signature share. `complete()` fails share verification and returns `FrostError::InvalidShare` [5](#0-4)  — or worse, hits the `InternalError` path, which the code comments admit is only reachable "to deserialize a semantically invalid FrostKeys" [6](#0-5) .

2. **Garbage verification shares / wrong group key.** Nothing verifies that the `verification_shares` map corresponds to any honest sharing. An arbitrary map yields an arbitrary `group_key`; the Bitcoin `Scanner`/`tweak_keys` stack will happily register and scan for that key [7](#0-6) . Funds received at that address can never be signed for, since no `view()` of the deserialized keys can produce a quorum of consistent shares.

3. **`Interpolation::Constant` length.** `interpolation_factor` indexes `c[i - 1]` unchecked [8](#0-7) ; `ThresholdKeys::new` only checks `t == n`, not `c.len() == n` — though `read` happens to read exactly `n` coefficients, direct construction (as `GeneratorPromotion::complete` does via `.unwrap()` [9](#0-8) ) can panic or misbehave.

This is the direct analog of the Zerem report: configuration accepted without consistency validation leaves the system in a state where funds locked under the derived key are unrecoverable — there is no equivalent of `liquidateFunds`; an invalid `ThresholdKeys` can never sign.

### Impact Explanation
Funds sent to the `group_key` derived from an inconsistent `ThresholdKeys` are permanently unspendable: every signing attempt either errors or panics. If the corrupted keys back a Bitcoin multisig, scanned outputs (`ReceivedOutput`s) are registered against an offset key whose spend path requires a FROST signature that can never complete.

### Likelihood Explanation
Requires loading corrupted or adversarially supplied serialized keys via `ThresholdKeys::read` — plausible in recovery/backup-restore paths where key material is imported. It is not reachable from a pure network peer unless the application deserializes untrusted key blobs. Analogous to the external report: misconfiguration, not active exploitation, so Medium.

### Recommendation
In `ThresholdKeys::new`, verify `C::generator() * secret_share == verification_shares[&params.i()]` and, for `Interpolation::Constant(c)`, assert `c.len() == usize::from(params.n())`. Optionally verify the interpolation of `verification_shares` over `1..=t` is self-consistent with each share. This makes `read` reject semantically invalid keys at parse time rather than at signing time.

### Proof of Concept
```rust
// Serai dkg, any Ciphersuite C
let mut rng = OsRng;
let (t, n) = (2u16, 3u16);
// Honest-looking verification shares
let vshares: HashMap<_, _> = (1..=n).map(|i| (
    Participant::new(i).unwrap(),
    C::generator() * C::F::random(&mut rng),
)).collect();
// secret_share unrelated to vshares[i]
let keys = ThresholdKeys::<C>::new(
    ThresholdParams::new(t, n, Participant::new(1).unwrap()).unwrap(),
    Interpolation::Lagrange,
    Zeroizing::new(C::F::random(&mut rng)),
    vshares,
).unwrap(); // accepted — no consistency check
// keys.group_key() is a valid-looking point; any attempt to sign yields
// FrostError::InvalidShare or InternalError — funds sent to group_key() are stuck.
```
The same result is reachable byte-level via `ThresholdKeys::read` by flipping bytes within the `secret_share` field of an otherwise valid serialization [10](#0-9) .

    {
      let different = || io::Error::other("deserializing ThresholdKeys for another curve");

      let mut id_len = [0; 4];
      reader.read_exact(&mut id_len)?;
      if u32::try_from(C::ID.len()).unwrap().to_le_bytes() != id_len {
        Err(different())?;
      }

      let mut id = vec![0; C::ID.len()];
      reader.read_exact(&mut id)?;
      if id != C::ID {
        Err(different())?;
      }
    }

    let (t, n, i) = {
      let mut read_u16 = || -> io::Result<u16> {
        let mut value = [0; 2];
        reader.read_exact(&mut value)?;
        Ok(u16::from_le_bytes(value))
      };
      (
        read_u16()?,
        read_u16()?,
        Participant::new(read_u16()?).ok_or(io::Error::other("invalid participant index"))?,
      )
    };

    let mut interpolation = [0];
    reader.read_exact(&mut interpolation)?;
    let interpolation = match interpolation[0] {
      0 => Interpolation::Constant({
        let mut res = Vec::with_capacity(usize::from(n));
        for _ in 0 .. n {
          res.push(C::read_F(reader)?);
        }
        res
      }),
      1 => Interpolation::Lagrange,
      _ => Err(io::Error::other("invalid interpolation method"))?,
    };

    let secret_share = Zeroizing::new(C::read_F(reader)?);

    let mut verification_shares = HashMap::new();
    for l in (1 ..= n).map(Participant) {
      verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
    }

    ThresholdKeys::new(
      ThresholdParams::new(t, n, i).map_err(io::Error::other)?,
      interpolation,
      secret_share,
      verification_shares,
    )
    .map_err(io::Error::other)
  }

  // Adds the unspendable script path per
  // https://github.com/bitcoin/bips/blob/master/bip-0341.mediawiki#cite_note-23
  let keys = {
    use k256::elliptic_curve::{
      bigint::{Encoding, U256},
      ops::Reduce,
      group::GroupEncoding,
    };
    let tweak_hash = TapTweakHash::hash(&keys.group_key().to_bytes().as_slice()[1 ..]);
    /*
      https://github.com/bitcoin/bips/blob/master/bip-0340.mediawiki#cite_ref-13-0 states how the
      bias is negligible. This reduction shouldn't ever occur, yet if it did, the script path
      would be unusable due to a check the script path hash is less than the order. That doesn't
      impact us as we don't want the script path to be usable.
    */
    keys.offset(<Secp256k1 as Ciphersuite>::F::reduce(U256::from_be_bytes(
      *tweak_hash.to_raw_hash().as_ref(),
    )))
  };

  let needs_negation = needs_negation(&keys.group_key());
  keys
    .scale(<_ as subtle::ConditionallySelectable>::conditional_select(
      &Scalar::ONE,
      &-Scalar::ONE,
      needs_negation,
    ))
    .expect("scaling keys by 1 or -1 yet interpreted as 0?")
}
