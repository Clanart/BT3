### Title
Excess ETH Sent to `MultiSender.batchTransferEqualAmount`/`batchTransfer` Is Permanently Locked (No Refund, No Withdrawal) - (File: contracts/src/MultiSender.sol)

### Summary
`MultiSender.sol`, deployed as an in-repo EVM contract used for batching Sei EVM native-coin transfers, exposes two `payable` functions that only check `msg.value >= totalAmount` rather than requiring exact payment, and never refund or otherwise route back any excess `msg.value`. Because the contract has no `withdraw`, `receive`/`fallback` sweep, or refund logic, any overpaid usei/wei sent by a caller is captured by the contract and can never be recovered, which is a stronger variant of the reported "Excess Ethereum Payment" bug class (permanent freezing vs. just discretionary retention by an admin-controlled treasury).

### Finding Description
Both public entry points compute the required payment and only enforce a lower bound: [1](#0-0) [2](#0-1) 

`batchTransferEqualAmount` computes `totalAmount = amount * recipients.length` and asserts `msg.value >= totalAmount` [3](#0-2) , then only forwards `amount` to each recipient via `send`, never touching any surplus. `batchTransfer` does the identical check with a summed `totalAmount` from the `amounts` array [4](#0-3) . In both functions, if `msg.value > totalAmount`, the difference remains in the contract's balance. Unlike the FootiumAcademy analog — where the excess is merely retained by the protocol (and could in principle be swept by an admin function elsewhere) — `MultiSender.sol` defines no `withdraw`, `owner`, `receive`, or any other function capable of moving ether out of the contract balance except the two batch-transfer functions, which only ever pay out the exact `amount`/`amounts` values specified by the caller, not the contract's full balance. Consequently, once ether is stuck as "excess" in the contract, it is permanently unreachable by any account — not the original sender, not any operator, not even via a subsequent call to the same functions (since those only transfer the fixed `amount` per recipient, not the contract's spare balance).

### Impact Explanation
Any unprivileged EVM transaction sender interacting with the deployed `MultiSender` contract who miscalculates `msg.value` (e.g., off-by-one in `amount * recipients.length`, sending a round number instead of the exact sum, or a wallet UI/estimate rounding error) permanently loses the excess native coin — this is not merely a UX inconvenience but concrete, un-recoverable fund loss/freezing, since sei-chain wei/usei sent to this contract has no exit path. This satisfies the "permanent freezing" bar in the validation criteria, and is more severe than the original report because the reported contract at least allowed a hypothetical admin refund fix at the protocol layer, whereas here there is no privileged function at all to reach the trapped balance.

### Likelihood Explanation
Likelihood is moderate-to-high: any user of the `MultiSender` batch-transfer utility can trigger this simply by sending `msg.value` greater than the computed total (a very plausible operational mistake, especially for `batchTransfer` where the caller must independently sum an arbitrary `amounts` array off-chain before submitting the transaction). No malicious actor, special privileges, or preconditions are needed — a normal, well-intentioned transaction sender can hit this every time they overestimate the required native-coin payment.

### Recommendation
Either enforce exact payment (`require(msg.value == totalAmount, ...)`) so failed pre-conditions revert instead of silently trapping funds, or, if overpayment should be tolerated, explicitly refund the excess to `msg.sender` at the end of each function (e.g., `if (msg.value > totalAmount) payable(msg.sender).transfer(msg.value - totalAmount);`) before completing execution.

### Proof of Concept
1. Deploy `MultiSender` on Sei EVM.
2. Call `batchTransferEqualAmount(recipients, amount)` with `recipients.length == 2`, `amount = 1 ether`, but send `msg.value = 3 ether` (1 ether excess).
3. The function requires `msg.value >= totalAmount` (`2 ether`), passes, and pays exactly `1 ether` to each of the 2 recipients (`2 ether` total) via `send` [5](#0-4) .
4. The remaining `1 ether` stays in the `MultiSender` contract's balance.
5. Inspect the contract: there is no `withdraw`, `receive`, `fallback`, or owner-only sweep function anywhere in `contracts/src/MultiSender.sol` — the `1 ether` surplus is permanently locked and unrecoverable by any account.

  function batchTransferEqualAmount(
    address[] calldata recipients,
    uint256 amount
  ) external payable {
    uint256 totalAmount = amount * recipients.length;
    require(msg.value >= totalAmount, "Insufficient amount sent");

    for (uint256 i = 0; i < recipients.length; i++) {
      bool success = payable(recipients[i]).send(amount);
      require(success, "Failed to send Ether");
      emit SendSuccessful(msg.sender, recipients[i], amount);
    }
  }

  function batchTransfer(
    address[] calldata recipients,
    uint256[] calldata amounts
  ) external payable {
    require(
      recipients.length == amounts.length,
      "Recipients and amounts do not match"
    );
    uint256 totalAmount = 0;
    for (uint256 i = 0; i < amounts.length; i++) {
      totalAmount += amounts[i];
    }

    require(msg.value >= totalAmount, "Insufficient amount sent");

    for (uint256 i = 0; i < recipients.length; i++) {
      bool success = payable(recipients[i]).send(amounts[i]);
      require(success, "Failed to send Ether");
      emit SendSuccessful(msg.sender, recipients[i], amounts[i]);
    }
  }
}
