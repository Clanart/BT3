## Finding

The strongest analog to the Jet v2 "trusted-but-unvalidated CPI target" bug (where a signed authority is handed to a program identity taken from attacker-influenced input without confirming it's on an allow-list) is in how GitHub Desktop derives the *destination path for launching an external editor / opening a file* from repository-relative file paths reported for a `CommittedFileChange` / `WorkingDirectoryFileChange`, using plain `Path.join(repository.path, file.path)` instead of the hardened `resolveWithin()` containment helper that the codebase already uses elsewhere for the exact same kind of untrusted-relative-path problem.

### Title
Unvalidated repo-relative file path passed to `Path.join` before launching the external editor/opening a file (missing containment check) - (File: `app/src/ui/history/selected-commits.tsx`, `app/src/ui/open-pull-request/pull-request-files-changed.tsx`, `app/src/ui/app.tsx`, `app/src/ui/changes/filter-changes-list.tsx`)

### Summary
Several UI code paths build the full filesystem path to open in the external editor, "Reveal in File Manager", or "Open with default program" by concatenating `repository.path` with a path string that ultimately originates from Git-reported paths for committed/working-directory files, using `Path.join(repository.path, file.path)`. [1](#0-0) [2](#0-1) [3](#0-2) 

This is architecturally identical to the pattern the same codebase already recognizes as dangerous and has hardened elsewhere: `dispatcher.ts`'s handling of the `filepath` query parameter from the `x-github-client://openRepo/...` deep link explicitly rejects absolute paths and calls `resolveWithin(repository.path, filepath)`, refusing to proceed if the resolved path escapes the repository root. [4](#0-3) [5](#0-4) 

### Finding Description
`resolveWithin` was specifically built to defend against "a crafted URL/path that tricks the UI into deriving a path outside the intended base directory" (per its own docstring and the `clone.ts`/`remote-parsing.ts` hardening comments), and is used for the deep-link `filepath` action. [6](#0-5) [7](#0-6) 

However, `file.path` values flowing into `Path.join(repository.path, file.path)` in `selected-commits.tsx`, `pull-request-files-changed.tsx`, and the `onOpenInExternalEditor`/`onOpenItem`/`revealInFileManager`/`getCopySelectedPathsMenuItem` handlers in `app.tsx` and `filter-changes-list.tsx` are not passed through the same containment check. [8](#0-7) [9](#0-8) 

`file.path` for a `CommittedFileChange`/`WorkingDirectoryFileChange` is populated from Git's own status/diff output for the currently checked-out commit/tree — data that originates from a cloned/fetched, attacker-authored repository (e.g. a malicious pull request the user opens with "Open Pull Request" or a malicious commit history the user browses in History). Normal Git tree entries cannot literally contain `../` path segments (Git's own fsck path checks reject this on checkout), so today this specific path likely can't be forced outside the repository by ordinary tree-entry crafting — this is the part I could not fully verify malicious feasibility for, since it depends on Git's own path-safety guarantees for tree/index entries and rename/copy detection edge cases, which I did not have tooling to test directly.

### Impact Explanation
If any code path can produce a `CommittedFileChange`/`WorkingDirectoryFileChange.path` value that resolves outside the repository root (e.g., via rename/copy metadata, case-folding tricks on case-insensitive filesystems, or another Git edge case not covered by Git's own tree-entry validation), the missing containment check means Desktop would happily launch the user's configured external editor, "reveal in file manager", or "open with default program" against a path outside the repository — potentially disclosing or letting a crafted diff view execution proceed against files like SSH keys or config outside the repo, mirroring the "arbitrary CPI target" impact class (untrusted input decides what gets acted on with the user's/host's authority).

### Likelihood Explanation
Low-to-Medium. Git's built-in path validation on checkout is a real, effective barrier for the common case, and the codebase's existing `resolveWithin` guard for the deep-link `filepath` shows the authors are aware of and defending this exact class of bug in one place but not consistently everywhere paths are derived from repository content. I was not able to confirm a concrete Git-level bypass (e.g., via renames, submodule gitlinks, or case-insensitive filesystem tricks) using the tools available, so this should be treated as an inconsistently-applied defense rather than a confirmed exploitable primitive.

### Recommendation
Route all `file.path` → filesystem-path conversions used for "open in external editor", "reveal in file manager", "open with default program", and clipboard "copy path" actions (`selected-commits.tsx`, `pull-request-files-changed.tsx`, `app.tsx#onOpenInExternalEditor`, `filter-changes-list.tsx`, `unmerged-file.tsx`) through `resolveWithin(repository.path, file.path)` (as already done for the deep-link `filepath` action in `dispatcher.ts`), refusing the action and logging an error if the resolved path escapes the repository root, for defense-in-depth against any Git edge case that could yield an escaping relative path.

### Proof of Concept
Not independently confirmed against live Git checkout behavior; the report is based on code-pattern comparison (inconsistent application of the existing `resolveWithin` containment guard) rather than a demonstrated Git tree-entry bypass. A concrete PoC would require constructing a repository/commit (via renames, gitlinks, or filesystem case tricks) whose reported `file.path` resolves outside `repository.path` when joined with `Path.join`, then exercising "Open in External Editor" from the Changes/History/PR-files-changed context menu — this step could not be completed with the tools available in this session.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```

```typescript
/**
 * Resolve one or more path sequences into an absolute path underneath
 * or at the given root path.
 *
 * The path segments are expected to be relative paths although
 * providing an absolute path is also supported. In the case of an
 * absolute path segment this method will essentially only verify
 * that the absolute path is equal to or deeper in the directory
 * tree than the root path.
 *
 * If the fully resolved path does not reside underneath the root path
 * this method will return null.
 *
 * This method will resolve paths using the current platform path
 * structure.
 *
 * @param rootPath     The path to the root path. The resolved path
 *                     is guaranteed to reside at, or underneath this
 *                     path.
 * @param pathSegments One or more paths to join with the root path
 */
export function resolveWithin(
  rootPath: string,
  ...pathSegments: string[]
): Promise<string | null> {
  return _resolveWithin(rootPath, pathSegments)
}
```
