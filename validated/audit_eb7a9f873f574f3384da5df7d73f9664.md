### Title
Gasless swap admission check performs a stale, zero-slippage `minAmountOut` validation, causing valid gasless bundles to revert on execution - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The `kaiax/gasless` module lets a proposer front gas for a user's swap-and-repay transaction (`GaslessSwapTx`), executed on-chain via `GaslessSwapRouter.swapForGas(token, amountIn, minAmountOut, amountRepay, deadline)`. Before a `GaslessSwapTx` is admitted into the pool, `checkBalanceForSwap` validates that the user-supplied `amountIn` is sufficient for the user-supplied `minAmountOut`, using a single point-in-time snapshot of the router's exchange rate (`GetAmountIn`). This is directly analogous to the reported Tokemak `LiquidationRow` issue: an automated on-chain component enforces a strict "received ≥ expected" check with no slippage tolerance, and the value used to satisfy that check is computed once and never revalidated as market/reserve conditions change before actual execution.

### Finding Description
`checkBalanceForSwap` in `kaiax/gasless/impl/tx_pool.go` performs: [1](#0-0) 

This check runs only once, at the moment the tx is admitted/promoted in the pool (`GetCheckBalance`), and is gated by `BalanceCheckLevel >= BalanceCheckLevelSwapAmount`: [2](#0-1) 

The `minAmountOut` and `amountIn` values are fixed at the time the user signs the `GaslessSwapTx` (`decodeSwapTx`), and are never updated: [3](#0-2) 

A `GaslessSwapTx` does not execute immediately upon being validated — it must first become "ready" (e.g. requires a paired `ApproveTx` at the correct nonce, `IsExecutable`) and is only bundled and executed at block-building time via `ExtractTxBundles`/`GetLendTxGenerator`: [4](#0-3) [5](#0-4) 

Because the tx can sit in the pending pool across one or more blocks (waiting for the paired approve tx, block space, or proposer inclusion), the AMM reserves backing `GaslessSwapRouter.swapForGas`'s exchange rate can move due to unrelated trades in the interim. When the bundle finally executes, `swapForGas` on-chain enforces the user's fixed `minAmountOut` with (per the audit-analog pattern) no slippage buffer; if actual output is even slightly below `minAmountOut`, the swap reverts.

Critically, the block-building path treats any non-success receipt for a bundled tx as fatal to the *entire* bundle: `commitBundleTransaction` reverts state and marks the offending transaction (and by extension the associated approve/swap pair) unexecutable, discarding the whole `[LendTxGenerator, ApproveTx, SwapTx]` bundle: [6](#0-5) 

This mirrors the audit finding precisely: an automated pipeline (proposer-driven gasless settlement, analogous to Tokemak's automated liquidation) enforces a strict slippage-free output check that was validated against a stale price snapshot, so ordinary short-term price movement between admission-time validation and execution-time settlement can make an otherwise legitimate, previously-"ready" transaction permanently fail to execute.

### Impact Explanation
Under even modest AMM volatility between admission and execution, gasless swap bundles that passed pool admission checks will revert at execution. Because the entire bundle (lend + approve + swap) is atomically discarded on any failure, users relying on the gasless mechanism to pay gas fees in ERC-20 tokens can have their transactions repeatedly fail to be included, degrading availability of the KIP-247 gasless feature and reducing throughput of the automated settlement pipeline that proposers run. This is analogous to the original report's impact ("prevent the automated liquidation from working in some cases") but here applies to the automated gasless-swap settlement path reachable by any ordinary transaction sender.

### Likelihood Explanation
The `checkBalanceForSwap` amount check is optional and controlled by `BalanceCheckLevel` (must be `>= BalanceCheckLevelSwapAmount`, which is the default level `BalanceCheckLevelAll`), so by default this check is active but stale by design — it is a single evaluation using `GetAmountIn` at admission time, not re-verified before inclusion. Any AMM reserve movement (from unrelated swaps in the same pool) between the time a `GaslessSwapTx` becomes pending/ready and the time it is actually picked up in `ExtractTxBundles`/`commitBundleTransaction` is sufficient to trigger the failure. Given normal per-block reordering, pending-queue depth (`MaxBundleTxsInPending`), and the requirement to wait for a paired `ApproveTx` at the correct nonce, this window is non-trivial and reachable from a single unprivileged gasless tx submission — no privileged actor is required.

### Recommendation
- Re-validate `checkBalanceForSwap` (or at minimum the `GetAmountIn`/exchange-rate portion) immediately before bundle commitment in `commitBundleTransaction`/`ExtractTxBundles`, using the state at the point of actual execution rather than only at pool admission.
- Alternatively, treat a swap-amount revert distinctly from other bundle failures: rather than discarding/marking the whole gasless bundle unexecutable on a single stale-price failure, allow the module to re-derive/re-check freshness and re-queue the tx instead of permanently failing it, or surface the failure back to the pool so the tx can be retried at a later block once conditions normalize, instead of `markAllTxUnexecutable`.
- Consider recommending that `GaslessSwapRouter.swapForGas`'s on-chain slippage enforcement allow the router/proposer role to recompute a fair `minAmountOut` bound (rather than relying purely on a client-signed static value that can go stale), or shorten the maximum allowed pending time for gasless swap txs to reduce the staleness window.

### Proof of Concept
1. User submits `GaslessApproveTx` (nonce N) and `GaslessSwapTx` (nonce N+1) with `minAmountOut` computed from the router's exchange rate at submission time; `checkBalanceForSwap` passes because `amountIn >= GetAmountIn(token, minAmountOut)` holds against the current reserves at admission: [1](#0-0) 
2. The pair becomes "ready" only once both are present and validated by `isApproveTxReady`/`isSwapTxReady`/`IsExecutable`: [7](#0-6) 
3. Before the pair is selected into a bundle and executed on-chain (`ExtractTxBundles` → `commitBundleTransaction`), other unrelated transactions execute against the same swap pool, shifting reserves such that the real output for `amountIn` would now be less than `minAmountOut`.
4. `swapForGas` executes on-chain with the stale `minAmountOut` and reverts (analogous to `InsufficientBuyAmountReceived` in the original report).
5. `commitBundleTransaction` observes `receipt.Status != types.ReceiptStatusSuccessful`, calls `markAllTxUnexecutable()` and `restoreEnv()`, discarding the entire `[LendTxGenerator, ApproveTx, SwapTx]` bundle: [6](#0-5) 
6. The user's previously admission-valid gasless transaction never gets included, despite having passed all pool-level checks, purely due to ordinary price movement — the automated gasless settlement fails exactly as described in the original report's "expects zero slippage" bug class.

I was unable to directly inspect the Solidity source of `GaslessSwapRouter.swapForGas` (only the compiled ABI/bytecode bindings were indexed), so the exact on-chain slippage-check implementation is inferred from the function signature (`minAmountOut` parameter) and the `tests/gasless_test.go` behavior showing swap reverts are expected when output conditions aren't met. A Devin session with full repository access could confirm the exact Solidity revert condition in the router contract if further precision is needed.

func (g *GaslessModule) isApproveTxReady(approveTx, nextTx *types.Transaction) bool {
	addr, err := types.Sender(g.signer, approveTx)
	if err != nil {
		return false
	}
	nonce := g.getCurrentStateNonce(addr)

	if approveTx.Nonce() != nonce {
		return false
	}
	if nextTx == nil || !g.IsSwapTx(nextTx) {
		return false
	}

	return g.IsExecutable(approveTx, nextTx)

func (g *GaslessModule) ExtractTxBundles(txs []*types.Transaction, prevBundles []*builder.Bundle) []*builder.Bundle {
	// there are only at most two gasless transactions in pending for a sender
	bundles := []*builder.Bundle{}
	approveTxs := map[common.Address]*types.Transaction{}
	targetTxHash := common.Hash{}
	for _, tx := range txs {
		addr, err := types.Sender(g.signer, tx)
		if err != nil {
			continue
		}
		if g.IsApproveTx(tx) {
			approveTxs[addr] = tx
		} else if g.IsSwapTx(tx) && g.IsExecutable(approveTxs[addr], tx) {
			bundleTxs := builder.NewTxOrGenList(g.GetLendTxGenerator(approveTxs[addr], tx))
			if approveTxs[addr] != nil {
				bundleTxs = append(bundleTxs, builder.NewTxOrGenFromTx(approveTxs[addr]))
			}
			bundleTxs = append(bundleTxs, builder.NewTxOrGenFromTx(tx))

			b := builder.NewBundle(
				bundleTxs,
				targetTxHash,
				false,
			)

			targetTxHash = tx.Hash()

			isConflict := false
			for _, prev := range append(prevBundles, bundles...) {
				if prev.IsConflict(b) {
					isConflict = true
					break
				}
			}
			if isConflict {
				// Gasless transactions will just fail even if they aren't bundled.
				continue
			}
			bundles = append(bundles, b)
		} else {
			targetTxHash = tx.Hash()
		}
	}
	return bundles
}
