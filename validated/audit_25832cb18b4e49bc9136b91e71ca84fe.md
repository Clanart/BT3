### Title
Unhandled exception / assertion failure while parsing an untrusted offer's settlement conditions causes wallet transaction-processing halt - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer._get_offered_coins()` parses CLVM conditions produced by running the inner puzzle/solution of *each coin spend in an untrusted offer file* supplied by an offer counterparty, without validating the shape of the `CREATE_COIN` condition before indexing into it. This mirrors the CVE-2025-63647 bug class: a crafted/malformed message field is dereferenced by a parser without a presence/shape check, causing an unhandled crash when the server processes attacker-supplied input.

### Finding Description
In `Offer._get_offered_coins()`: [1](#0-0) 

```python
puzzle_cost, conditions = inner_puzzle.run_with_cost(cost_left, inner_solution)
...
for condition in conditions.as_iter():
    if condition.first() == 51 and condition.rest().first() == OFFER_MOD_HASH:
```

The code assumes that any `CREATE_COIN` (opcode `51`) condition whose puzzle-hash argument equals `OFFER_MOD_HASH` always has a third argument (the amount). `inner_puzzle`/`inner_solution` come directly from an attacker-controlled `CoinSpend` (puzzle_reveal + solution) embedded in the offer bytes that a wallet loads via `Offer.from_bytes`/`Offer.from_bech32` (i.e., an offer file received from a trade counterparty). A malicious offer can craft an inner puzzle whose CLVM program returns a truncated `(51 OFFER_MOD_HASH)` condition (missing amount), or non-canonical structures reachable through the attacker-supplied puzzle code, causing `condition.rest().rest().first()` to raise (`EvalError`/`ValueError` in the `Program`/CLVM layer) when it hits the terminating nil where an atom is expected.

Just above, at line 260, a similar unguarded-null pattern exists: [2](#0-1) 

```python
puzzle_driver = match_puzzle(parent_puzzle)
if puzzle_driver is not None:
    asset_id = create_asset_id(puzzle_driver)
```

`get_inner_puzzle`/`get_inner_solution` are driver-dispatch functions (`chia/wallet/outer_puzzles.py`) whose concrete implementations (e.g. `MetadataOuterPuzzle.get_inner_puzzle` at [3](#0-2)  ) can legitimately return `None` for puzzle/driver combinations that don't match perfectly, or raise `ValueError`. A crafted offer combining a matched outer puzzle (so `match_puzzle` succeeds) with an inconsistent/malformed inner structure can force these helpers to return `None`, tripping the `assert`, or to throw uncaught `ValueError`s that propagate out of `_get_offered_coins`.

Neither `Offer.__post_init__` (which only wraps the unrelated `compute_spend_hints_and_additions` call in broad `try/except`, see [4](#0-3) ) nor `get_offered_coins()`/`_get_offered_coins()` themselves wrap this specific condition-parsing/`assert` logic in any exception handling: [5](#0-4) 

```python
def get_offered_coins(self) -> dict[bytes32 | None, list[Coin]]:
    try:
        if self._offered_coins is not None:
            return self._offered_coins
    except AttributeError:
        object.__setattr__(self, "_offered_coins", self._get_offered_coins())
    return self._offered_coins
```

`get_offered_coins()`/`_get_offered_coins()` are invoked from many code paths that a wallet exercises as soon as it examines an incoming offer — `summary()`, `arbitrage()`, `is_valid()`, `get_pending_amounts()`, `get_primary_coins()`, `to_valid_spend()` — all of which are reached by the wallet RPC/trade flow that processes any offer string handed to the daemon by a peer (e.g. via `TradeManager` when a user pastes/loads an offer, or via `get_offer_summary`-style RPCs). Because construction of `Offer` from raw bytes performs relatively little validation before these accessor methods are exercised, an attacker who hands a wallet user a crafted offer string can trigger an uncaught exception/`AssertionError` deep in trade-processing code the moment the wallet inspects it (to show a summary, validate it, or attempt to take it).

### Impact Explanation
This is a spend-triggered/offer-triggered transaction-processing halt: a malicious offer counterparty can craft an offer bech32 string that, once loaded by any recipient wallet, throws an unhandled exception in `Offer._get_offered_coins()` instead of failing gracefully. Depending on how the caller in `TradeManager`/RPC layer handles this, it can manifest as a denial of service against the wallet's trade-processing logic — the wallet is unable to safely evaluate/summarize/take the offer, and repeated malicious offers can be used to disrupt normal offer handling for a victim wallet. This matches the `AV:N/AC:L/PR:N/UI:N/A:H` DoS profile of the source CVE, adapted to the "unprivileged wallet user / offer counterparty" reachable surface allowed by scope.

### Likelihood Explanation
Likelihood is high for any wallet user who evaluates offers: creating a malformed `CREATE_COIN` condition with `OFFER_MOD_HASH` and no amount argument, or crafting mismatched outer/inner puzzle combinations, is a straightforward CLVM authoring task that does not require any privileged access — only the ability to produce an offer file/bech32 string and have a victim load it (a completely standard trading interaction). No cryptographic material or block acceptance is needed to trigger the crash.

### Recommendation
- In `_get_offered_coins()`, validate the length/shape of each condition before indexing (e.g., check `condition.rest().rest()` is not nil before calling `.first()`), and wrap the CLVM parsing loop in a narrow `try/except` that treats malformed conditions as "no match" rather than propagating an exception.
- Replace the bare `assert inner_puzzle is not None and inner_solution is not None` with an explicit check that raises a caught/expected `ValueError`, and ensure all callers of `get_offered_coins()`/`summary()`/`is_valid()` in the trade-manager/RPC layer wrap offer parsing in exception handling that returns a clean "invalid offer" error to the caller instead of letting the exception surface as an unhandled fault.
- Add fuzz/unit tests that feed truncated/malformed `CREATE_COIN` conditions and mismatched driver/puzzle offer bundles through `Offer.from_bytes`/`Offer.from_bech32` followed by `summary()`/`is_valid()` to confirm graceful rejection.

### Proof of Concept
1. Construct a `CoinSpend` whose puzzle reveal, when run with its solution, is matched by an outer puzzle driver (e.g. `match_cat_puzzle`) but whose CLVM program emits a `CREATE_COIN` condition of the form `(51 <OFFER_MOD_HASH>)` (missing the amount arg) rather than `(51 <OFFER_MOD_HASH> <amount>)`.
2. Embed this coin spend into an `Offer`/`WalletSpendBundle`, serialize it via `Offer.to_bech32()`/manually crafted bytes, and deliver the resulting offer string to a victim wallet as if it were a legitimate trade offer.
3. When the victim wallet loads the offer (`Offer.from_bech32`) and calls any of `summary()`, `is_valid()`, `get_pending_amounts()`, or `to_valid_spend()` (paths exercised automatically by normal "view/accept offer" wallet flows), `_get_offered_coins()` executes `condition.rest().rest().first().as_int()` on the malformed condition, raising an uncaught CLVM evaluation error that propagates out of offer processing, halting that operation for the victim.

*(Note: full exercise of this PoC against the running RPC layer/`TradeManager` call sites could not be completed within the available exploration — the exact exception-handling wrapper, if any, around `TradeManager`'s calls into `Offer.summary()`/`is_valid()` was not fully confirmed due to tool/iteration limits, but no exception handling was found within `offer.py` itself around this code path.)*
