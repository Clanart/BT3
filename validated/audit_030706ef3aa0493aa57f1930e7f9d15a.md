### Title
Floating-point stake-ratio threshold checks in Tower consensus lose precision, allowing threshold decisions (duplicate-confirmation, switch-proof, lockout, root) to be computed incorrectly - (File: `core/src/consensus.rs`)

### Summary
The Backed Protocol finding is a class of bug where a percentage/ratio comparison against an improvement threshold loses precision due to the arithmetic representation used, silently weakening or bypassing an intended guard. In Agave's legacy Tower-BFT consensus code, the analogous pattern is that stake-percentage threshold checks (vote lockout thresholds, duplicate-confirmation thresholds, switch-fork thresholds, and root/commitment thresholds) are computed by casting `u64` stake amounts to `f64` and dividing, e.g. `(*stake as f64 / total_stake as f64) > threshold`. `f64` has only a 52-bit mantissa, so any `u64` stake value above `2^53` (~9.007 * 10^15) cannot be represented exactly, and division introduces rounding. This is the exact same "precision loss at a comparison boundary" class as the Solidity finding, just manifesting through float rounding rather than integer truncation.

### Finding Description
Several consensus-critical stake-ratio comparisons in the codebase are implemented with `u64 as f64` division instead of exact integer/fraction arithmetic:

- `Tower::is_slot_duplicate_confirmed` and `Tower::is_slot_confirmed` in [1](#0-0) 
- `Tower::check_vote_stake_threshold` in [2](#0-1) 
- `Tower::make_check_switch_threshold_decision` (`SWITCH_FORK_THRESHOLD` comparisons) in [3](#0-2) 
- `get_highest_super_majority_root` in [4](#0-3) 
- `BlockCommitmentCache::get_lockout_count` (`VOTE_THRESHOLD_SIZE`) in [5](#0-4) 

All of these compute `stake as f64 / total_stake as f64` and compare the result with `>` against a fixed threshold constant (`VOTE_THRESHOLD_SIZE`, `DUPLICATE_THRESHOLD`, `SWITCH_FORK_THRESHOLD`). The codebase itself demonstrates, in a newer sibling module written for the Alpenglow/votor consensus pool, that this exact operation is unsound: a dedicated `Fraction` type was introduced "for precise stake threshold comparisons" specifically to avoid this bug, with an explicit regression test proving the float computation gives the wrong answer at a percentage boundary: [6](#0-5) 

That test shows `stake = 60% of total_stake + 1 lamport`, yet `stake as f64 / total_stake as f64 <= 0.6` evaluates to `true` — i.e., the floating-point ratio is computed as *not exceeding* 60% even though the true integer ratio strictly exceeds 60%. This directly corrupts any `> threshold` boolean decision built on that ratio, in the same way the Solidity bug corrupted the "at least 10% better" boolean decision: the guard silently passes (or fails) at exactly the boundary case it was designed to gate.

The votor/Alpenglow code (`votor/src/consensus_pool/slot_stake_counters.rs`, using `Fraction`) was fixed, but the currently-active Tower-BFT legacy consensus path in `core/src/consensus.rs`, `core/src/commitment_service.rs`, and `runtime/src/commitment.rs` was not migrated and still relies on the vulnerable `f64` division.

### Impact Explanation
`check_vote_stake_threshold`, `is_slot_duplicate_confirmed`, and `make_check_switch_threshold_decision` gate whether a validator is allowed to vote, whether a slot is treated as duplicate-confirmed, and whether a fork switch is permitted. `get_highest_super_majority_root` / `get_lockout_count` gate root advancement and confirmation-count reporting. A boundary miscomputation in any of these can cause:
- A slot being treated as duplicate-confirmed (or not) incorrectly — false acceptance of a fork.
- A switch-threshold decision passing when the true integer stake proof did not actually clear `SWITCH_FORK_THRESHOLD`, or vice versa — enabling switching votes on insufficient stake evidence.
- A root/commitment level being reported/advanced at the wrong slot.

These map to the "false execution/rooting/acceptance" and potentially "consensus halt" categories listed as valid impact for this scan.

### Likelihood Explanation
Total staked lamports on Solana mainnet are already several orders of magnitude above `2^53` (≈9.007 * 10^15 lamports ≈ 9 million SOL), since staked SOL supply is in the hundreds of millions of SOL (i.e., 10^17+ lamports). Individual large-stake validators or aggregated `fork_stake`/`locked_out_stake`/`total_stake` sums used in these comparisons routinely exceed `2^53`, so the precision-loss condition is not a contrived edge case — it is a normal operating condition for the network today. The precise boundary flip requires the ratio to land extremely close to the threshold constant, which is a narrower condition, but with continuously varying stake distributions and votes, boundary crossings will occur over time. This is an "unprivileged" issue in the sense that no attacker action is required — it is triggered purely by ambient stake magnitudes and normal voting/threshold arithmetic in the consensus path, not by a malicious peer assumption.

### Recommendation
Replace `u64 as f64` division-based threshold comparisons in `core/src/consensus.rs`, `core/src/commitment_service.rs`, and `runtime/src/commitment.rs` with exact/precise arithmetic, mirroring the fix already applied for votor: use the existing `agave_votor_messages::fraction::Fraction` type (cross-multiplication in `u128`, as in [7](#0-6) ) or equivalent integer-only comparisons (`stake * denom > threshold_num * total_stake` using `u128`) instead of casting to `f64`.

### Proof of Concept
Using the codebase's own demonstration test as the PoC for the underlying arithmetic flaw:
```rust
// from votor-messages/src/fraction.rs (test_f64_precision_loss)
let total_stake = 100_000_000_000_000_000u64; // 10^17 lamports, realistic total stake
let stake = 60_000_000_000_000_001u64;        // 60% of total_stake + 1 lamport

let f64_ratio = stake as f64 / total_stake as f64;
assert!(f64_ratio <= 0.6); // WRONG: true integer ratio is > 60%
```
The identical `stake as f64 / total_stake as f64` pattern is used verbatim in `Tower::is_slot_duplicate_confirmed` [8](#0-7) , `Tower::check_vote_stake_threshold` [9](#0-8) , and the switch-threshold check [10](#0-9) , so any stake/total_stake pair sitting at an analogous boundary above `2^53` will cause these production threshold gates to return the wrong `PassedThreshold`/duplicate-confirmed/switch-proof decision.
