### Title
Secret-indexed table/bucket lookups in `straus`/`pippenger` leak DKG key shares via cache timing - (File: crypto/multiexp/src/straus.rs)

### Summary
The "constant-time" `multiexp` implementation indexes precomputed point tables (`straus`) and buckets (`pippenger`) with window-sized bit-groups taken directly from the scalar. When `BatchVerifier::verify()` runs `multiexp` over statements that contain a secret scalar — concretely, the received secret share queued in PedPoP's `calculate_share` — the array index is a function of secret key material, exactly the CacheD bug class from CVE-2017-14737.

### Finding Description
`multiexp` is documented as the constant-time path (`crypto/multiexp/src/lib.rs:180-190`), but:

- `straus` (line 43): `res += tables[s][usize::from(groupings[s][b])];` — `groupings[s][b]` is a window-bit group of the scalar produced by `prep_bits` (`src/lib.rs:54-74`).
- `pippenger` (line 26): `buckets[usize::from(bits[p][n])] += pairs[p].1;` — same secret-derived index, plus the accumulation loop `intermediate_sum += buckets[b]` touches buckets in index order correlated with which were populated.

Both index memory with bits of the scalar. This is constant-*operations* but not constant-*access-pattern*: each access leaks the index through the cache, identical to Botan's secret-key-indexed array.

The reachable secret-carrying path is in PedPoP: `KeyMachine::calculate_share` queues each decrypted participant share — a secret `C::F` — as a scalar in a statement:

- `crypto/dkg/pedpop/src/lib.rs:487-491`: `batch.queue(rng, BatchId::Share(l), share_verification_statements::<C>(self.params.i(), &self.commitments[&l], share))`
- `crypto/dkg/pedpop/src/lib.rs:493`: `batch.verify_with_vartime_blame()` → `BatchVerifier::verify()` (`crypto/multiexp/src/batch.rs:93-95`) → `multiexp(&flat(&self.0))` → `straus`/`pippenger`.

`flat` even acknowledges this: "Wrapped in Zeroizing in case any of the included statements contain private values" (`src/batch.rs:13`). For typical DKG sizes `share_verification_statements` yields few pairs, so `algorithm()` selects `Straus(3)`/`Straus(4)`, hitting the indexed-table line on every window of the share.

### Impact Explanation
A local attacker sharing a core/cache with a PedPoP participant (co-located VM, SGX-style adversary, or unprivileged process, as in CacheD) can observe which of the 8/16 table entries per window is touched, recovering the scalar bits of the received secret share. The accumulated `self.secret` is the participant's threshold key share; recovering it yields the FROST secret share, enabling signature forgery in combination with threshold-1 other shares — i.e., key share recovery, not mere timing noise. This matches the accepted impact class (secret leakage via cache side channel), not a timing-only analog.

### Likelihood Explanation
Requires a local attacker with cache-observation capability on the DKG host during `calculate_share`. Each share is used only once per index window, so leakage per observation is the full window pattern of that share — a single run of the loop covers all ~85 windows of a 256-bit scalar, and the attacker can influence which points are added per bucket via the commitments they control as a DKG participant. No privileged access, no malicious-validator assumption beyond co-location, and no misuse of a documented-MUST-vartime API is required: the bug is that the *constant-time* entry point is itself not cache-safe. Medium severity, consistent with the source CVE (CVSS 5.5).

### Recommendation
In `straus`, replace the direct index with a constant-time selection over the table (e.g., `conditional_select`/`ct_eq` over all `2^window` entries, as `EdwardsPoint::mul`/`Scalar::pow` already do in `crypto/ed448/src/point.rs:258-265` and `crypto/dalek-ff-group/src/lib.rs:223-230`). In `pippenger`, accumulate into buckets via constant-time conditional adds rather than index-based placement, or document `multiexp` as not cache-safe for secret scalars and route the PedPoP share statement through a scalar-mul that is. Alternatively, avoid placing the secret share scalar in the batched statement (e.g., verify `share * G == expected` via the constant-time `Mul<Scalar>` impl instead of through `BatchVerifier`).

### Proof of Concept
Conceptual, mirroring CacheD: run PedPoP `KeyMachine::calculate_share` on a machine while a co-located spy primes/evicts the cache lines covering `tables[s]` (Straus, window 3 → 8 point entries) or `buckets` (Pippenger). Each iteration `res += tables[s][groupings[s][b]]` at `straus.rs:43` touches exactly the line for the 3-bit group of the secret share at window `b`; a Prime+Probe trace of 8 lines × ~85 windows recovers all bits of `share`, which is added into `self.secret` (`pedpop/src/lib.rs:484`) — the participant's threshold signing key. pub fn multiexp<G: Zeroize + Group<Scalar: Zeroize + PrimeFieldBits>>(
  pairs: &[(G::Scalar, G)],
) -> G {
  match algorithm(pairs.len()) {
    Algorithm::Null => Group::identity(),
    Algorithm::Single => pairs[0].1 * pairs[0].0,
    // These functions panic if called without any pairs
    Algorithm::Straus(window) => straus(pairs, window),
    Algorithm::Pippenger(window) => pippenger(pairs, window),
  }
}
