### Title
Unbounded recursive decoding of nested `AccountKeyRoleBased` via public `kaia_decodeAccountKey` RPC causes stack-overflow DoS - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
The public RPC method `KaiaAPI.DecodeAccountKey` accepts arbitrary attacker-supplied RLP bytes and calls `rlp.DecodeBytes` into an `AccountKeySerializer` with no depth limit. `AccountKeyRoleBased.DecodeRLP` recursively invokes `rlp.DecodeBytes` on each sub-key, and that recursion can itself decode another `AccountKeyRoleBased`, with no check preventing nested `RoleBased` keys at decode time. Because the type-level "nested composite" rejection (`ErrNestedCompositeType`) is only enforced later, during account-key *installation/update* (`CheckInstallable`/`CheckUpdatable`), not during RLP decoding, an attacker can submit a deeply self-nested RoleBased key blob that recurses through Go call stacks until the process hits a fatal, unrecoverable stack overflow.

### Finding Description
`KaiaAPI.DecodeAccountKey` is a public JSON-RPC endpoint reachable by any unauthenticated/unprivileged RPC caller: [1](#0-0) 

It decodes caller-controlled bytes directly:
```go
dec := accountkey.NewAccountKeySerializer()
if err := rlp.DecodeBytes(encodedAccKey, &dec); err != nil { ... }
```

`AccountKeySerializer.DecodeRLP` reads a key type, then dispatches to the concrete `AccountKey` implementation's `DecodeRLP`: [2](#0-1) 

When the type is `AccountKeyTypeRoleBased`, `AccountKeyRoleBased.DecodeRLP` decodes a list of byte-slices and, for **each element**, calls `rlp.DecodeBytes(b, &serializer)` — i.e., it recursively re-enters `AccountKeySerializer.DecodeRLP`, which can again resolve to `AccountKeyRoleBased`: [3](#0-2) 

Nowhere in this decode path is `IsCompositeType()`/nested-RoleBased rejection checked. That check only exists in `CheckInstallable` and `CheckUpdatable`, which are invoked later when an `AccountUpdate` transaction is actually applied to state — not when the RPC merely decodes bytes for display: [4](#0-3) 

Each recursion level requires only a small, fixed number of encoded bytes (an outer list wrapping one inner serialized RoleBased key), so an attacker can encode thousands of nesting levels within a modest, RLP-size-limit-compliant payload, driving Go's call stack to its limit. Go's runtime stack-overflow ("goroutine stack exceeds ... fatal error: stack overflow") is a fatal, unrecoverable error — it cannot be caught by `recover()` in the RPC handler, so it terminates the entire node process, unlike a normal panic.

### Impact Explanation
This is a Denial-of-Service impacting node/RPC availability: a single RPC call from any public, unprivileged caller can crash the node process (fatal runtime error is not recoverable), taking down the RPC server and requiring a restart. This maps to the same bug class as the reported `langchain-community` `SitemapLoader` issue (CWE-400/674, uncontrolled recursion leading to resource exhaustion/crash), but here the reachable analog is a public Kaia RPC method rather than a document loader.

### Likelihood Explanation
High likelihood of reachability: `DecodeAccountKey` is a standard public RPC method with no special privileges required, and constructing a deeply nested RLP-encoded RoleBased key is straightforward and requires no valid signatures, no funds, and no prior chain state.

### Recommendation
Enforce the existing "no nested composite key" invariant during RLP/JSON decoding itself (not only at installation time), e.g. reject `AccountKeyTypeRoleBased` sub-keys inside `AccountKeyRoleBased.DecodeRLP`, and/or add an explicit recursion-depth counter threaded through `AccountKeySerializer.DecodeRLP`/`AccountKeyRoleBased.DecodeRLP` that aborts decoding once a small maximum nesting depth (e.g., 1, since RoleBased must only contain non-composite keys) is exceeded.

### Proof of Concept
Conceptually:
1. Build a base non-RoleBased key (e.g., `AccountKeyNil`/`AccountKeyLegacy`), RLP-encode it as an `AccountKeySerializer`.
2. Wrap it in an `AccountKeyRoleBased` list-of-one, RLP-encode that as a new `AccountKeySerializer` (`enc := [][]byte{ inner }`, per `EncodeRLP`).
3. Repeat step 2 thousands of times, each time wrapping the previous encoded blob as the sole element of a new `AccountKeyRoleBased`.
4. Call the public RPC `kaia_decodeAccountKey` (or `klay_decodeAccountKey`) with the final deeply-nested hex-encoded blob.
5. `DecodeRLP` recurses once per nesting level via `rlp.DecodeBytes` inside `AccountKeyRoleBased.DecodeRLP`, exhausting the goroutine stack and crashing the node process with a fatal, unrecoverable runtime error.

Note: I was unable to execute this against a live node to confirm the exact required nesting depth or verify whether an overarching RLP size/list-depth limit in `rlp.Stream` (not found in the indexed `rlp` package files) might curb this before reaching the Go runtime's stack limit; this should be validated with an actual Devin session/test run against the target binary.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
