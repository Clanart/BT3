### Title
Outputs scanned from earlier transactions in a block have their `data`/`presumed_origin` overwritten by a later transaction, so deposits are credited to (or refunded to) an attacker - (File: processor/src/networks/bitcoin.rs)

### Summary
`get_outputs` accumulates `outputs` across all transactions in a block, but applies the per-transaction metadata (`presumed_origin` and `data`, the `InInstruction`/`Shorthand` payload that decides who is minted or refunded) to the entire accumulated vector on every iteration. A later transaction's origin and data overwrite the metadata of outputs from earlier transactions. An unprivileged party can include a transaction paying a Serai key in the same block as a victim's deposit, causing the victim's `data` (destination `SeraiAddress`) to be replaced by the attacker's, and/or the victim's refund `presumed_origin` to be replaced by an attacker-controlled address.

### Finding Description
In `Bitcoin::get_outputs`, the `outputs` vector is declared outside the `for tx in &block.txdata[1 ..]` loop and is never cleared between transactions:

```rust
// processor/src/networks/bitcoin.rs:686-737
let mut outputs = vec![];
// Skip the coinbase transaction which is burdened by maturity
for tx in &block.txdata[1 ..] {
  for output in scanner.scan_transaction(tx) {
    ...
    outputs.push(output);
  }

  if outputs.is_empty() {
    continue;
  }

  // populate the outputs with the origin and data
  let presumed_origin = { ... tx.input[0] ... };
  let data = Self::extract_serai_data(tx);
  for output in &mut outputs {           // iterates ALL accumulated outputs
    if output.kind == OutputType::External {
      output.data.clone_from(&data);     // overwrites earlier txs' data
    }
    output.presumed_origin.clone_from(&presumed_origin); // overwrites earlier origin
  }
}
```

Because the `if outputs.is_empty() { continue; }` guard only skips transactions that produced no new output *and* no prior output exists, the inner `for output in &mut outputs` loop runs over outputs pushed by earlier transactions too, and `clone_from` unconditionally overwrites their fields with the *current* transaction's `data` and `presumed_origin`.

This is the same bug class as the reference issue: a handler written as if it covers a single item (`tx`), applied to a superset (all outputs collected so far), so per-asset-type/per-item handling (the NFT `data`/origin) for earlier items is silently dropped and replaced.

The `data` field of an `External` output is the `Shorthand`-encoded `InInstruction` that determines the destination `SeraiAddress` for the mint (see `extract_serai_data` and the test at `processor/src/tests/literal/mod.rs` asserting `outputs[0].data() == message`). The `presumed_origin` is used downstream by the refund path (`PlanFromScanning::Refund(output, refund_to)` in `processor/src/multisigs/mod.rs`).

### Impact Explanation
High. If a block contains (a) a victim transaction paying a Serai `External` key carrying `data` = the victim's `SeraiAddress`, and (b) a subsequent attacker transaction also paying any scanned Serai key with `data` = an attacker `SeraiAddress`, then the victim's output metadata is overwritten with the attacker's `data`. The batch minted on Serai credits the attacker's Serai account with sriBTC funded by the victim's Bitcoin. Equivalently, an attacker can overwrite `presumed_origin` with their own Bitcoin address, so any later refund of the victim's output is paid to the attacker. This is theft of deposits, reachable purely by sending ordinary Bitcoin transactions — no validator, key, or RPC compromise needed.

### Likelihood Explanation
Medium. The attacker must land their transaction in the same block as the victim's deposit, after it in ordering, and have it scanned (pay a registered Serai script: external, branch, change, or forward address — all derivable from the public group key). Watching the mempool and submitting a second transaction with a fee sufficient for same-block inclusion is realistic; miners/block templates make exact ordering partially attackable but not guaranteed. Once the condition holds, theft is deterministic.

### Recommendation
Scope the metadata population to only the outputs produced by the current transaction:

```rust
for tx in &block.txdata[1 ..] {
  let start = outputs.len();
  for output in scanner.scan_transaction(tx) { ... outputs.push(output); }
  if outputs.len() == start { continue; }

  let presumed_origin = ...;
  let data = Self::extract_serai_data(tx);
  for output in &mut outputs[start ..] {   // only this tx's outputs
    ...
  }
}
```

Alternatively collect per-transaction outputs in a temporary vector, populate them, then extend `outputs`. Additionally, consider only treating the *first* input's prevout as origin when the transaction actually paid a Serai output, and asserting that `data` is only attached to transactions whose `OP_RETURN`/`Shorthand` decodes for the intended instruction.

### Proof of Concept
1. Attacker observes a victim broadcast transaction T_v paying `external_address(group_key)` with an `OP_RETURN` `Shorthand::transfer(None, victim_serai_addr)`.
2. Attacker broadcasts T_a paying any small amount (≥ `DUST = 10_000` sats) to the same external address (or a registered offset script), with `OP_RETURN` `Shorthand::transfer(None, attacker_serai_addr)`, paying a fee that gets T_a mined in the same block after T_v.
3. `get_outputs` scans T_v first, pushes the victim `Output` with `kind = External`; it then runs the population loop for T_v, setting `data = victim_serai_addr`. It then scans T_a, pushes the attacker's output, and runs the population loop for T_a over *both* outputs — `clone_from` sets the victim output's `data` to `attacker_serai_addr`.
4. The processor emits `ScannerEvent::Block` with the corrupted output; the batch mints sriBTC to `attacker_serai_addr` funded by the victim's UTXO. The same overwrite applies to `presumed_origin`, redirecting any refund of the victim's output to the address derived from T_a's `input[0]` prevout.

Note: I could not read the downstream `extract_serai_data`/refund-consumer code in full due to limited iterations, so the exact gating of when `data` is honored (e.g., whether a `Branch`-kind attacker output suffices as the carrier) is inferred from `processor/src/tests/literal/mod.rs:175-190` and the `Refund`/`Forward` plan construction in `processor/src/multisigs/mod.rs:584-601`; the overwrite itself is directly visible in `processor/src/networks/bitcoin.rs:686-737`.
