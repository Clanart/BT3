### Title
Wrong Variable Passed to `deposit_constant` in Host-Side Journal Hash Computation Permanently Blocks Operator Proof Generation — (`File: bridge-circuit-host/src/structs.rs`)

---

### Summary

The host-side helper `host_deposit_constant` passes `deposit_value_bytes` (the deposit amount in wei from the EIP-1186 storage proof) as the `move_txid` argument to `deposit_constant()`. The ZK circuit (guest) correctly passes `*move_txid` (the Bitcoin move-to-vault transaction ID recovered from `verify_storage_proofs`). Because the two callers feed different 32-byte values into the same hash, the host-computed `deposit_constant` is always wrong, the host-computed `journal_hash` never matches the circuit's committed journal, and `prove_bridge_circuit` always returns `Err("Journal hash mismatch")`. An operator can never produce a valid bridge-circuit proof, making them unable to respond to any challenge and exposing their entire collateral to slashing.

---

### Finding Description

`deposit_constant()` is defined in `circuits-lib/src/bridge_circuit/mod.rs` with the following signature:

```rust
pub fn deposit_constant(
    operator_xonlypk: [u8; 32],
    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],          // ← 4th parameter: Bitcoin move-to-vault txid
    round_txid: [u8; 32],
    kickoff_round_vout: u32,
    genesis_state_hash: [u8; 32],
) -> DepositConstant
```

**Inside the ZK circuit (guest)** — `circuits-lib/src/bridge_circuit/mod.rs` lines 221-229 — the call is correct:

```rust
let deposit_constant = deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    *move_txid,          // ← correct: Bitcoin txid from verify_storage_proofs
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
);
```

**Inside the host helper** — `bridge-circuit-host/src/structs.rs` lines 505-515 — the wrong variable is passed:

```rust
let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();

Ok(deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    deposit_value_bytes,  // ← BUG: deposit amount in wei, not move_txid
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
))
```

`deposit_value_bytes` is the big-endian encoding of the EIP-1186 storage proof's `value` field (the deposit amount in wei). It is semantically and numerically unrelated to `move_txid`.

`host_deposit_constant` is called from `SuccinctBridgeCircuitPublicInputs::new()` (`structs.rs` line 436), which is called from `prove_bridge_circuit()` (`bridge_circuit_host.rs` line 205-206). The resulting wrong `deposit_constant` propagates into `host_journal_hash()` (line 208). After the STARK proof is generated, the host checks:

```rust
if *journal_hash.as_bytes() != succinct_receipt_journal {
    return Err(eyre!("Journal hash mismatch"));
}
```

Because the circuit committed a journal hash built from the correct `move_txid` and the host computed a journal hash built from `deposit_value_bytes`, these 32-byte values are virtually never equal. `prove_bridge_circuit` always returns an error.

---

### Impact Explanation

The operator calls `prove_bridge_circuit` (via `send_asserts` in `core/src/operator.rs`) to generate the Groth16 proof needed to respond to a BitVM2 challenge. Because `prove_bridge_circuit` always fails with "Journal hash mismatch", the operator can never produce a valid proof. In the BitVM2 challenge game, an operator who cannot post valid Assert transactions within the protocol timeout loses their collateral. Every operator collateral deposit is therefore at risk of being slashed by any challenger who initiates a challenge, with no possibility of a legitimate defense.

Additionally, the `BridgeCircuitBitvmInputs.deposit_constant` field returned from `prove_bridge_circuit` (line 293) would carry the wrong value, so even if the journal-hash guard were bypassed, the downstream Groth16 public-input verification (`verify_bridge_circuit`, `structs.rs` line 609) would also fail.

---

### Likelihood Explanation

The bug is triggered on every single call to `prove_bridge_circuit` with real data. `deposit_value_bytes` (a wei amount such as `0x0000…05F5E100` for 1 BTC) and `move_txid` (a random-looking 32-byte Bitcoin txid) are always different. No special input is required; the normal withdrawal/challenge flow is sufficient to trigger it.

---

### Recommendation

**Short term:** In `host_deposit_constant` (`bridge-circuit-host/src/structs.rs`), replace `deposit_value_bytes` with the actual `move_txid` recovered from the storage proof, mirroring the circuit logic:

```rust
// Deserialize move_txid from storage_proof_utxo (same source as verify_storage_proofs uses)
let storage_proof_utxo: EIP1186StorageProof =
    serde_json::from_str(&input.sp.storage_proof_utxo)...;
let move_txid_bytes: [u8; 32] = storage_proof_utxo.value.to_be_bytes::<32>();

Ok(deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    move_txid_bytes,   // ← correct field
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
))
```

**Long term:** Add a unit test that runs both the circuit and `host_deposit_constant` on the same input and asserts the resulting `deposit_constant` values are equal, preventing future host/guest divergence.

---

### Proof of Concept

1. Operator initiates a withdrawal and calls `prove_bridge_circuit` with valid `BridgeCircuitHostParams`.
2. `SuccinctBridgeCircuitPublicInputs::new()` calls `host_deposit_constant`, which computes `deposit_constant` using `deposit_value_bytes` (e.g., `[0,0,…,0,5,245,225,0]` for a 1 BTC deposit).
3. The ZK circuit runs and commits a `journal_hash` built from `move_txid` (e.g., `[ab,cd,…,12,34]`).
4. The host computes its own `journal_hash` using the wrong `deposit_constant`.
5. Line 239 of `bridge_circuit_host.rs` fires: `*journal_hash.as_bytes() != succinct_receipt_journal` → `Err("Journal hash mismatch")`.
6. The operator's `send_asserts` call fails; no Assert transactions are posted.
7. A challenger times out the operator and executes the pre-signed slash transaction, burning the operator's collateral.
