### Title
Liquidity index used as a zToken price multiplier is a lazy-updated, utilization-manipulable snapshot - (File: `mainnet/contracts/market/v0-4-market.clar`, `mainnet/contracts/vault/v0-vault-*.clar`)

### Summary
Zest prices zTokens (`zSTX`, `zsBTC`, `zstSTX`, `zUSDC`, `zUSDH`, `zstSTXbtc`) as collateral by multiplying the underlying oracle price by each vault's **liquidity index** (`lindex`), fetched through a per-block cache and applied via the `resolve-ztoken` callcode transform in the market contract. That liquidity index is advanced lazily: whenever it is finally refreshed (`accrue`/`next-liquidity-index`), the *entire* elapsed time since the last update is compounded using the **instantaneous** interest rate computed from the vault's utilization at the moment of the call. Because utilization is derived from live, atomically-manipulable state (`available-assets`, `total-debt`), an attacker can spike utilization immediately before triggering an update, causing the whole unsynced period to compound at an inflated rate, permanently ratcheting `lindex` upward, then reverse the utilization spike. This is the same "lazy-updated snapshot rate" root cause as the Morpho/Aave finding, just relocated from Morpho's P2P mid-rate to Zest's vault liquidity index that feeds zToken collateral pricing.

### Finding Description
`resolve-ztoken` multiplies the raw oracle price by the cached liquidity index for the corresponding vault: [1](#0-0) [2](#0-1) 

The cache is populated per block timestamp by `accrue-and-cache`, which calls the vault's `accrue()` (returning `{index, lindex}`) only on cache miss: [3](#0-2) [4](#0-3) 

Inside the vault, `next-liquidity-index` computes the new index by applying a multiplier derived from `interest-rate()` (an instantaneous function of current `utilization()`) over the elapsed `time-delta` since `last-update`: [5](#0-4) 

`interest-rate` and `utilization` are computed live from current vault state at call time: [6](#0-5) 

`accrue()` then permanently commits the resulting `lindex` to storage and mints treasury shares, only advancing `last-update` when the index actually changed: [7](#0-6) 

Because the multiplier defaults to the identity only when `time-delta == 0` (i.e., the vault was already accrued in the current block), any vault that has gone one or more blocks without activity is exposed: the *whole* elapsed period is compounded using whatever utilization exists at the exact instant `accrue()` finally runs. An attacker can:
1. Push utilization to its ceiling (e.g., borrow heavily from the vault, using flashloaned collateral purely as capital — not exploiting flashloan permission logic itself).
2. In the same transaction, perform any market operation that touches that vault's zToken as collateral (e.g. `collateral-add`), triggering `accrue-and-cache` → `accrue` → `next-liquidity-index`, which compounds the entire stale period at the manipulated peak rate and writes the inflated `lindex` to the vault's storage.
3. The market's health check for that same transaction calls `price-resolve`/`resolve-ztoken`, which reads the now-inflated cached `lindex` and overstates the zToken collateral's dollar value.
4. Attacker borrows against the inflated collateral value, then repays/undoes the utilization spike in the same transaction. The inflated `lindex` remains permanently in vault storage (it is monotonic and never rolled back), and the attacker walks away with debt in excess of what their real collateral backs.

### Impact Explanation
This lands in the in-scope **Critical** bucket: undercollateralized debt extracted against an artificially inflated zToken collateral price is direct theft of user funds at rest (the vault's real assets back less debt than recorded, socializing the shortfall onto suppliers) and can also cause protocol insolvency in that vault. It can also let an otherwise-unhealthy position avoid liquidation for the duration of the manipulated block, which is at minimum a temporary freezing/misallocation of funds.

### Likelihood Explanation
Likelihood is highest for vaults with low interaction frequency, where multiple blocks elapse between accruals — the exact caveat the original report flags ("ensure the rate is updated often... this can be detrimental in low-activity markets"). The attack only costs gas plus the temporary capital used to spike utilization (which can be obtained via a flashloan used purely as capital, out-of-scope-exempt per the rules), making it economically attractive whenever the attacker holds — or opens within the same transaction — a zToken collateral position on the targeted vault. Note: the exact rate curve (`interpolate-rate`) and multiplier math (`calc-multiplier-delta`, `calc-index-next`) live in helper functions I could not open the source of within this session (not returned by search/grep, likely due to index truncation); the monotonic-increasing/compounding relationship is confirmed structurally from `next-liquidity-index`/`accrue` above and from the docs' explicit AAVE-model reference, but the precise sensitivity of `liquidity-rate` to `utilization` should be re-verified against `calc-liquidity-rate`/`interpolate-rate` source before remediation.

### Recommendation
- Do not compound an entire stale multi-block interval using the interest rate observed only at the instant of the final `accrue()` call. Either accrue at fixed intervals using a time-weighted/averaged utilization, or cap the utilization/rate used in a single `accrue()` step to avoid using a single-block spike to inflate the multi-block interval.
- Consider snapshotting utilization/rate at the start of the transaction (before any borrow/repay within the same call) so that in-transaction utilization manipulation cannot influence the index update applied for the elapsed historical period.
- Alternatively, force `accrue()` (and therefore `lindex` refresh) to run automatically/frequently (e.g., keeper-triggered every block) so the staleness window that can be exploited is minimized, mirroring Morpho's own mitigation guidance.

### Proof of Concept
1. Wait for (or pick) a vault, e.g. `v0-vault-usdc`, where several blocks have passed since `last-update` (low activity).
2. Attacker uses flashloaned capital (not flashloan-fee/whitelist exploitation, purely as capital) to `system-borrow` up to `available-assets`, driving `utilization()` to its ceiling.
3. In the same transaction, attacker calls a market operation (e.g. `collateral-add` with `zUSDC`) that triggers `accrue-and-cache` → vault `accrue()`; this computes `next-liquidity-index` compounding the full stale `time-delta` at the manipulated peak `interest-rate()`, and commits the inflated `lindex` to storage. [7](#0-6) 
4. Market health check resolves the attacker's `zUSDC` collateral price via `resolve-ztoken`, using the freshly inflated cached `lindex`, overstating collateral value. [2](#0-1) 
5. Attacker borrows against the inflated collateral valuation, then repays the step-2 loan, restoring utilization — but the inflated `lindex` (and the excess debt drawn against it) persists.
