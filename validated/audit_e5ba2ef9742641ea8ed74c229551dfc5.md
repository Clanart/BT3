### Title
Unauthenticated decryption-oracle leak: early `from_repr` abort in `calculate_share` publishes a blame proof (revealing the ECDH shared key) before the sender's proof-of-possession is verified, exposing an honest victim's encrypted secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` decrypts each incoming `EncryptedMessage` and immediately produces an `EncryptionKeyProof` (which publicly reveals the ECDH shared key plus a DLEq proving its correctness) before the message's proof-of-possession Schnorr signature is actually checked — the PoP is only queued into a `BatchVerifier` and verified at the end of the loop. If the decrypted bytes fail scalar deserialization (`C::F::from_repr`), the function early-returns `PedPoPError::InvalidShare { blame: Some(blame) }` containing that key-revealing proof, without ever verifying the attacker's PoP.

This is exactly the side-channel the code comments warn about: Eve copying Alice's per-message encryption key `X` causes Bob to publish `b·X`, which decrypts Alice's genuine message to Bob. The PoP in `encrypt` was added specifically to stop this — but the ordering bug reintroduces it.

### Finding Description
In `Encryption::decrypt` (crypto/dkg/pedpop/src/encryption.rs:469-501), the PoP signature is deferred via `msg.pop.batch_verify(...)`, while `ecdh(...)` is computed and the keystream applied immediately, returning the plaintext and an `EncryptionKeyProof { key, dleq }` that reveals the ECDH shared key `recipient_enc_key · msg.key`.

In `KeyMachine::calculate_share` (crypto/dkg/pedpop/src/lib.rs:476-499):
- line 478: `self.encryption.decrypt(...)` produces `(share_bytes, blame)` where `blame` is the `EncryptionKeyProof`
- lines 479-482: `C::F::from_repr(share_bytes.0)` failure → `Err(InvalidShare { blame: Some(blame) })` — returned via `?` **inside** the loop
- line 493: `batch.verify_with_vartime_blame()` — the only place the PoP is actually verified — is never reached on that early return

The comments in encryption.rs:84-90 explicitly document the attack: "Eve could observe Alice encrypt to Bob with key X, then send Bob a message also claiming to use X... Bob would then use this to create a blame argument against Eve. When they do, they'd reveal bX, revealing Alice's message to Bob. This is a massive side effect." The fix relies on `pop.verify` rejecting Eve's forged message — but because the blame proof is emitted on the deserialization path *before* the batched PoP check, Eve needs no valid PoP.

### Impact Explanation
An unprivileged DKG participant Eve sends Bob an `EncryptedMessage` whose `key` field equals victim Alice's per-message ephemeral public key `X` (observed on the authenticated channel), a ciphertext chosen so decryption is a non-canonical scalar (any random bytes fail `from_repr` with overwhelming probability), and a garbage PoP. Bob's `calculate_share` errors early and returns a blame object revealing `Bob_enc_key · X` with a valid DLEq attestation. Anyone (including Eve) can then apply `cipher(context, proof.key)` to Alice's real ciphertext for key `X` and recover Alice's secret share — unauthorized read access to a subset of protocol data, mirroring the CVE's confidentiality-only impact (CVSS C:L, no integrity/availability impact). Recovery of a share weakens/leaks a FROST participant's key share.

### Likelihood Explanation
Requires only a participant (or anyone who can deliver a message attributed to a participant) to submit a crafted `EncryptedMessage` during `calculate_share`; no valid signatures, no collusion, no key knowledge. The failure path is deterministic: decryption with the real ECDH key always succeeds as an XOR, and random bytes are non-canonical scalars with probability ≈ 1.

### Recommendation
In `KeyMachine::calculate_share`, do not attach the `EncryptionKeyProof` to errors that occur before the batched PoP verification completes. Either:
- Buffer decryption results and only map errors to `blame: Some(proof)` after `batch.verify_with_vartime_blame()` confirms every PoP, returning `blame: None` for the deserialization failure path; or
- Verify each `msg.pop` synchronously inside `decrypt` before producing/using the plaintext, removing the deferred-verification gap for the blame-relevant case.

### Proof of Concept
```rust
// Eve observes Alice's EncryptedMessage to Bob with key X (a C::G point).
// Eve crafts her own message to Bob:
let mut evil = EncryptedMessage::<C, SecretShare<C::F>> {
  key: alice_msg.key,                    // reuse victim's per-message key X
  pop: <garbage SchnorrSignature>,       // will never be checked on this path
  msg: SecretShare([0xff; 32]),          // after XOR -> non-canonical scalar w.h.p.
};

// Bob calls KeyMachine::calculate_share(shares incl. evil as from = Eve).
// decrypt() computes ecdh(Bob_enc_key, X), applies keystream, and queues the PoP.
// share_bytes are garbage -> C::F::from_repr fails at lib.rs:480 ->
//   returns InvalidShare { participant: Eve, blame: Some(EncryptionKeyProof{ key: Bob·X, dleq }) }
// batch.verify_with_vartime_blame() at lib.rs:493 is never reached; Eve's fake PoP is irrelevant.

// Anyone holding the published EncryptionKeyProof decrypts Alice's real ciphertext:
//   cipher::<C>(context, &proof.key).apply_keystream(alice_msg.msg.as_mut());
// => Alice's secret share to Bob is recovered.
```
