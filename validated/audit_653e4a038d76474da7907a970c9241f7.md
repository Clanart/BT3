### Title
Wallet-side VC auto-authorization in offers redirects a user's CR-CAT into an attacker-chosen "pending approval" recipient without informed consent - (File: chia/wallet/vc_wallet/vc_wallet.py)

### Summary
When a wallet takes or completes an offer that involves credential-restricted CATs (CR-CATs), `TradeManager.check_for_final_modifications` automatically delegates to `VCWallet.add_vc_authorization` to sign off on any CR-CAT movement in the offer using whatever VC the local wallet happens to hold for that provider. [1](#0-0)  `add_vc_authorization` accepts a CR-CAT output as "OK to approve" if it is (a) coming back to a wallet-known puzzle hash, (b) returning to its own origin (change), (c) going to the `OFFER_MOD`, or (d) wrapped in a "pending approval" construction - and that last check is self-referential rather than tied to any offer term the user actually agreed to. [2](#0-1) 

### Finding Description
`construct_pending_approval_state(puzzle_hash, amount)` just curries an arbitrary `puzzle_hash`/`amount` pair into a fixed announcement puzzle: `PENDING_VC_ANNOUNCEMENT.curry(...)`. [3](#0-2) 

Inside `add_vc_authorization`, the "pending state" branch of the `outputs_ok` check does not validate that the destination puzzle hash corresponds to an intended, previously-agreed recipient of the trade. It only checks that the output's puzzle hash is *internally consistent* with a `construct_pending_approval_state(target, amount)` hash, where `target` is read straight out of the same coin-spend's own memo field (`cc.at("rrrff")`):

```
or (  # it's going to the pending state
    cc.at("rrr") != Program.NIL
    and cc.at("rrrf").atom is None
    and bytes32(cc.at("rf").as_atom())
    == construct_pending_approval_state(
        bytes32(cc.at("rrrff").as_atom()), uint64(cc.at("rrf").as_int())
    ).get_tree_hash()
)
``` [4](#0-3) 

Because `target` is taken from data supplied inside the very same untrusted offer/spend-bundle being evaluated, an offer maker can trivially satisfy this check for *any* arbitrary `target` puzzle hash they choose (their own address) by constructing the output puzzle hash to already equal `construct_pending_approval_state(target, amount).get_tree_hash()` and setting the memo consistently. The wallet never cross-checks `target` against the wallet's own puzzle-hash records, against the offer's `requested_payments`, or against any user-visible summary of the trade. If `outputs_ok` (or `our_crcat`) passes, `VCWallet.add_vc_authorization` automatically generates a signed VC transaction that produces the announcements needed to authorize spending the CR-CAT into that state:

```
async with self.wallet_state_manager.new_action_scope(...) as inner_action_scope:
    for launcher_id, vc in vcs.items():
        await self.generate_signed_transaction(
            [uint64(1)], [...], inner_action_scope, vc_id=launcher_id,
            extra_conditions=(*announcements_to_assert[launcher_id], *announcements_to_make[launcher_id]),
        )
``` [5](#0-4) 

This mirrors the Nextcloud Approval-app bug class: a party who should not have authority to force a "share"/approval action (here, VC-authorized transfer) can still cause the system to auto-perform that authorization on their behalf, because the acceptance path checks only the *shape* of the destination construct rather than whether it was actually one of the negotiated terms of the trade the local wallet's user agreed to.

### Impact Explanation
A user completing (taking or finalizing) an offer that includes any CR-CAT asset type can have their own VC used to sign an authorization that lets a CR-CAT (that they thought they were only trading according to the negotiated `requested_payments`) get redirected into a "pending approval" state addressed to an attacker-chosen recipient, since the sanity check that gates automatic authorization is satisfiable by data controlled entirely by the counterparty crafting the offer. This can result in unauthorized/unexpected movement of CR-CAT balances outside the terms the user believes they are accepting - a coin-movement/authorization-bypass issue analogous to forced, unauthorized sharing.

### Likelihood Explanation
Exploitation requires only that the victim be running the CR-CAT/VC workflow (an optional feature) and take/complete an offer crafted by an adversarial counterparty containing a CR-CAT asset; no special network position or elevated privilege is required beyond normal offer creation, matching the CVSS profile of the analog (network, low complexity, low privilege, no user interaction beyond normal trade acceptance).

### Recommendation
`add_vc_authorization`'s "pending state" branch should validate the destination `target` puzzle hash against the actual `requested_payments`/offer summary that the user reviewed and approved (or otherwise require it to match a value the wallet independently derived), rather than trusting a `target` value extracted from the same untrusted coin-spend memo being validated. Cross-check the pending-approval target against the offer's driver dict / notarized payments before authorizing with the VC.

### Proof of Concept
Not independently executable from static analysis alone; a concrete PoC would require constructing a CR-CAT offer whose settlement coin spend places the CR-CAT output puzzle hash as `construct_pending_approval_state(attacker_ph, amount).get_tree_hash()` with a matching memo, then having a victim wallet with a compatible VC take/complete that offer via `TradeManager.respond_to_offer` → `check_for_final_modifications` → `VCWallet.add_vc_authorization`, and observing that the wallet signs the authorization for the attacker-chosen `attacker_ph` without further prompt. [6](#0-5)  This exact call path is exercised (without malicious payloads) in existing tests such as `test_cat_trades`'s CR-CAT scenarios. [7](#0-6)

    async def respond_to_offer(
        self,
        offer: Offer,
        peer: WSChiaConnection,
        action_scope: WalletActionScope,
        solver: Solver | None = None,
        fee: uint64 = uint64(0),
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> TradeRecord:
        if solver is None:
            solver = Solver({})
        take_offer_dict: dict[bytes32 | int, int] = {}
        arbitrage: dict[bytes32 | None, int] = offer.arbitrage()

        for asset_id, amount in arbitrage.items():
            if asset_id is None:
                wallet: WalletProtocol | None = self.wallet_state_manager.main_wallet
                assert wallet is not None
                key: bytes32 | int = int(wallet.id())
            else:
                # ATTENTION: new wallets
                wallet = await self.wallet_state_manager.get_wallet_for_asset_id(asset_id)
                if wallet is None and amount < 0:
                    raise ValueError(f"Do not have a wallet for asset ID: {asset_id} to fulfill offer")
                elif wallet is None or wallet.type() in {WalletType.NFT, WalletType.DATA_LAYER}:
                    key = asset_id
                else:
                    key = int(wallet.id())
            take_offer_dict[key] = amount

        # First we validate that all of the coins in this offer exist
        valid: bool = await self.check_offer_validity(offer, peer)
        if not valid:
            raise ValueError("This offer is no longer valid")
        # We need to sandbox the transactions here because we're going to make our own
        async with self.wallet_state_manager.new_action_scope(
            action_scope.config.tx_config, push=False
        ) as inner_action_scope:
            result = await self._create_offer_for_ids(
                take_offer_dict,
                inner_action_scope,
                offer.driver_dict,
                solver,
                fee=fee,
                extra_conditions=extra_conditions,
                taking=True,
            )
            if not result[0] or result[1] is None:
                raise ValueError(result[2])

            _success, take_offer, _error = result

            complete_offer, valid_spend_solver = await self.check_for_final_modifications(
                Offer.aggregate([offer, take_offer]), solver, inner_action_scope
            )

def construct_pending_approval_state(puzzle_hash: bytes32, amount: uint64) -> Program:
    return PENDING_VC_ANNOUNCEMENT.curry(Program.to([[51, puzzle_hash, amount, [puzzle_hash]]]))
