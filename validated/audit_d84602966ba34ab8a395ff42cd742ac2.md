## Analysis

The external bug (Bitcoin.js `waitForPayment` callback executed multiple times due to a missing reentrancy/replay guard) maps to a native analog in the **Balance-Handler / precompile execution accounting path** of this Cosmos EVM codebase: `x/vm` precompile dispatch reuses a **cumulative, non-isolated Cosmos SDK event index** (`prevEventsLen`) to translate bank events into `StateDB` balance deltas, and this window is not properly isolated across **nested/recursive precompile calls** within a single EVM transaction — allowing the same underlying bank transfer event(s) to be translated into `StateDB.AddBalance`/`SubBalance` more than once.

### Title
Recursive precompile calls cause duplicate application of bank balance-change events to the EVM StateDB - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
`BalanceHandler.BeforeBalanceChange`/`AfterBalanceChange` translate Cosmos SDK bank events (`coin_spent`/`coin_received`) emitted during a precompile call into `StateDB.AddBalance`/`SubBalance` calls, using a simple slice-offset (`prevEventsLen`) into the shared, monotonically-growing `ctx.EventManager().Events()` list [1](#0-0) . Each precompile invocation via `RunNativeAction`/`runNativeAction` creates its own `BalanceHandler` and records the event count at the start, then re-applies all events since that offset at the end [2](#0-1) . When a precompile call (e.g. distribution `ClaimRewards`, staking `Delegate`) recursively/re-entrantly triggers another precompile call within the same EVM transaction — e.g. via an ERC20 `_beforeTokenTransfer`/`_afterTokenTransfer` hook or a contract that calls back into the precompile before returning (as exercised by `ERC20RecursiveNonRevertingPrecompileCall.sol`, `StakingReverter.sol`, and `DebugPrecompileCaller.sol`) — the *outer* call's `prevEventsLen` was captured before the *inner* call executed. Since events accumulate globally on the shared event manager, the outer call's `AfterBalanceChange` re-scans and re-applies balance deltas for events that were already consumed and applied to `StateDB` by the inner call's own `AfterBalanceChange`.

### Finding Description
`BeforeBalanceChange` stores `len(ctx.EventManager().Events())` as an offset [3](#0-2) . `AfterBalanceChange` slices `events[bh.prevEventsLen:]` and, for every `coin_spent`/`coin_received`/precisebank fractional event in that slice, calls `stateDB.SubBalance`/`AddBalance` [4](#0-3) . This offset-based windowing assumes call frames are non-overlapping (LIFO, no re-entrancy across the *same* event stream), but recursive precompile-to-precompile or precompile-to-EVM-to-precompile calls violate that assumption: the inner frame's events lie inside `[outerPrevEventsLen, finalLen)` and are processed twice — once by the inner handler at inner-return time, and again by the outer handler at outer-return time, because the outer's start offset predates the inner call entirely.

The regression test `TestRecursivePrecompileCallsWithDebugPrecompile` explicitly documents this class of bug ("recursive precompile calls share ... causing prevEventsLen to be overwritten ... leads to balance desync between native bank keeper and EVM stateDB") [5](#0-4) , and dedicated exploit-style contracts exist to trigger nested/recursive precompile calls from a user-controlled ERC20 hook (`_beforeTokenTransfer` invoking `claimRewards()`/`delegate()` against the distribution/staking precompiles) [6](#0-5) , as well as an IBC/ICS20 test suite explicitly built around this ("Tests the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated") [7](#0-6) .

### Impact Explanation
Because `StateDB.AddBalance`/`SubBalance` directly determine an account's EVM-visible native balance, duplicate application of a single bank-transfer event to the outer handler's window causes the EVM balance to diverge from the actual bank-keeper-backed balance. An attacker who controls a contract that recursively re-enters a balance-mutating precompile (distribution, staking, bank, ics20, erc20 wrapper precompiles, all of which set `BalanceHandlerFactory`) can cause the EVM `StateDB` to double-credit (or double-debit) a balance relative to the real underlying Cosmos bank ledger, producing unauthorized duplication/desync of spendable value between native balances and EVM balances — this is a Critical accounting-corruption impact per the specified impact gate (unauthorized duplication or irreversible accounting corruption of spendable value across native/EVM balances).

### Likelihood Explanation
The trigger requires only an unprivileged user to deploy an ordinary ERC20-like contract with a transfer hook (or any contract) that calls back into a balance-affecting precompile during its own precompile-triggered execution — a pattern already demonstrated working end-to-end in this repo's own test contracts (`ERC20RecursiveNonRevertingPrecompileCall.sol`, `StakingReverter.sol`, `DebugPrecompileCaller.sol`) and exercised by first-party regression/integration tests, indicating the recursive-call path is reachable via normal transaction/contract execution with no privileged access needed.

### Recommendation
Make the balance-handler event window re-entrancy-safe: either (1) track a per-call-frame event range as a stack (push/pop around each `runNativeAction` invocation) so an outer frame never reprocesses events already consumed by an inner frame, or (2) mark/consume events as "applied" (e.g., tag them or remove/replace them from the manager once translated) so no event is ever translated into a `StateDB` balance change more than once, mirroring a reentrancy guard around the event-consumption region analogous to guarding the vulnerable `waitForPayment` callback.

### Proof of Concept
The existing `TestRecursivePrecompileCallsWithDebugPrecompile` test [8](#0-7)  already provides a working PoC: it deploys `DebugPrecompileCaller.sol`, which recursively calls a debug precompile that itself recursively re-enters (`callback(counter)` at contract lines 7–29 [9](#0-8) ), and the ICS20/distribution recursive-precompile-call integration test suite documents the resulting balance desync between the bank keeper and EVM StateDB in the presence of nested precompile calls triggered from an ERC20 `_beforeTokenTransfer` hook [10](#0-9) .

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)

				// Bypass blocked addresses

			}

				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

    function callback(uint256 counter) public {
        bool result;
        bytes memory data;

        // emit events
        for (uint i = 0; i < counter; i++) {
            (result, data) = debugPrecompile.call(abi.encodePacked(uint8(1)));
            if (!result) {
                revert CallFailed(data);
            }

        if (counter > 3) {
            // stop the recursion
            return;
        }

        // recursive call
        (result, data) = debugPrecompile.call(abi.encodePacked(uint8(0), counter));

            revert CallFailed(data);
        }
