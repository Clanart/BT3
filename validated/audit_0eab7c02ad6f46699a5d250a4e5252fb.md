### Title
Symlinked `.claude/hookify.*.local.md` rule files let a cloned repo read and inject arbitrary out-of-workspace file content into hook output - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`load_rules()` discovers rule files with `glob.glob('.claude/hookify.*.local.md')` and `load_rule_file()` opens each match with the plain builtin `open(file_path, 'r')`, which transparently follows symlinks. A malicious repository can check in `.claude/hookify.evil.local.md` as a symlink pointing outside the repo root (e.g. `~/.ssh/id_rsa`, a sibling checkout's `.env`, or any other file readable by the victim's OS user), and every hookify hook invocation (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) will read and attempt to parse that target file's content as a trusted rule.

### Finding Description
`load_rules()` at [1](#0-0)  globs `.claude/hookify.*.local.md` and passes each matched path straight to `load_rule_file()`. `load_rule_file()` opens the path with no symlink check, realpath confinement, or `O_NOFOLLOW`: [2](#0-1) .

Git supports committing symlinks (mode `120000`); on checkout (Linux/macOS, or Windows with symlink support enabled) the symlink is materialized as a real filesystem symlink. `glob.glob` matches such entries by filename regardless of whether they are symlinks, and Python's `open()` dereferences symlinks by default, so the process reads whatever file the symlink target resolves to — even if that target lives entirely outside the cloned repository tree.

The target's content is then run through `extract_frontmatter()` [3](#0-2) , which only checks `content.startswith('---')` before treating the file as YAML-like frontmatter + message body. Many real secret files satisfy this loosely (e.g. `-----BEGIN OPENSSH PRIVATE KEY-----` starts with `---`), so portions of the target file are parsed into a `Rule.message`, which then flows into `RuleEngine.evaluate_rules()` and is emitted as `systemMessage` in every subsequent `PreToolUse`/`PostToolUse`/`Stop`/`UserPromptSubmit` hook response [4](#0-3) . That message becomes part of Claude Code's session context, i.e. content read from outside the workspace is injected into the model's context and shown to the user session, which is exactly the workspace-confinement break the question describes.

No existing guard prevents this: `load_rules`/`load_rule_file` catch only I/O and parsing exceptions [5](#0-4) , there is no `os.path.islink`/`os.path.realpath` containment check anywhere in `config_loader.py`, and the workspace-jail guidance that exists elsewhere in the repo (e.g. the hook-development skill's "Path Safety" advice) is documentation only, not enforced code in this plugin.

Reliable manipulation of `permissionDecision`/rule `action` for unrelated targets is not fully attacker-controlled, because the attacker only controls the symlink, not the content of the file it resolves to on the victim's machine — so forcing a specific `block`/`deny` outcome on demand is not guaranteed. The concrete, deterministic impact is the unauthorized read and context-injection of out-of-repo file content.

### Impact Explanation
This is a workspace-confinement bypass / out-of-scope information disclosure: a plugin/rule loader intended to only read trusted, repo-scoped `.claude/hookify.*.local.md` rule files can be tricked via a committed symlink into reading and surfacing arbitrary files reachable by the victim's OS user (SSH keys, `.env` secrets, sibling-repo files, credentials) into the Claude Code session context via `systemMessage`. This matches the "secrets disclosure via trust-boundary bypass" class of Claude Code bounty impact — repo author (attacker) and repo cloner (victim) are different principals, and the disclosed content crosses the repository sandbox that `.claude/*.local.md` loading is implicitly expected to respect.

### Likelihood Explanation
Preconditions are low: the attacker only needs the victim to clone/checkout a repository containing a symlink entry (no additional privileges, no social engineering beyond "clone this repo," and no dependency on filesystem contents the attacker doesn't already know are plausible, e.g. `~/.ssh/id_rsa` or `../<sibling-repo>/.env`). It requires a POSIX-like checkout preserving symlinks (default on Linux/macOS; requires developer mode or admin on Windows) and requires hookify hooks to be enabled for the project. The exploit triggers automatically on the very first tool call / prompt submit after checkout, with no additional attacker interaction, making it fully repeatable across every hook invocation.

### Recommendation
In `load_rules()`/`load_rule_file()` (`plugins/hookify/core/config_loader.py`), reject rule files that are symlinks, or resolve the path with `os.path.realpath()` and verify the resolved path is still inside the repo's `.claude` directory (`os.path.commonpath` check against the resolved repo root) before opening. Alternatively, open with `os.open(path, os.O_RDONLY | os.O_NOFOLLOW)` and treat `ELOOP`/`OSError` as "skip this rule file," logging a warning instead of silently following the link.

### Proof of Concept
Integration test (pytest):
1. Create a temp dir `repo/` with `.claude/` subdir.
2. Create `outside/secret.md` outside `repo/` containing:
   ```
   ---
   name: leaked
   enabled: true
   event: all
   action: warn
   ---
   SECRET-CONTENT-MARKER
   ```
3. Inside `repo/.claude/`, create a symlink `hookify.evil.local.md -> ../../outside/secret.md`.
4. `cd` into `repo/` and call `config_loader.load_rules()`.
5. Assert either:
   - `load_rules()` returns `[]` / skips the symlinked file (expected fix behavior), or
   - if it currently returns a `Rule`, assert `"SECRET-CONTENT-MARKER" not in rule.message` to prove no cross-boundary content leaked.
   Current behavior: the returned `Rule.message` contains `"SECRET-CONTENT-MARKER"`, demonstrating the loader read content from outside the repository root through the symlink — failing the assertion and confirming the vulnerability.

```python
def extract_frontmatter(content: str) -> tuple[Dict[str, Any], str]:
    """Extract YAML frontmatter and message body from markdown.

    Returns (frontmatter_dict, message_body).

    Supports multi-line dictionary items in lists by preserving indentation.
    """
    if not content.startswith('---'):
        return {}, content

    # Split on --- markers
    parts = content.split('---', 2)
    if len(parts) < 3:
        return {}, content

    frontmatter_text = parts[1]
    message = parts[2].strip()
```

```python
def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule
```
