### Title
Path-containment bypass in `resolveWithin()` via unbounded prefix match lets a malicious "Open in Desktop" deep link escape the cloned repository directory - ([File: app/src/lib/path.ts])

### Summary
`resolveWithin()` is GitHub Desktop's central guard against path traversal/symlink escape when resolving a repository-relative path supplied from untrusted input (deep links, conflict file paths). It validates containment by doing a raw string `startsWith()` comparison between the resolved real path and the repository's real root path, with no check for a path-separator boundary. This is structurally the same class of bug as the reported Perpetual issue: a security check compares the wrong unit/granularity (raw string prefix instead of a path-segment-bounded comparison), so a value that should fail the check (a sibling directory whose name merely *starts with* the root directory's name) passes it, allowing access outside the intended boundary.

### Finding Description
`_resolveWithin()` computes the final containment check as: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` performs a raw character-prefix comparison, not a path-segment comparison. If `realRoot` is e.g. `/Users/victim/Documents/GitHub/myrepo` and the traversal segments resolve to `/Users/victim/Documents/GitHub/myrepo-secrets/notes.txt`, then `realResolved.startsWith(realRoot)` evaluates to `true` (because `"myrepo-secrets"` textually starts with `"myrepo"`), even though `myrepo-secrets` is a completely different, sibling directory outside the intended repository tree. The function returns the escaped path as "safely resolved" instead of `null`.

This is analogous to the Perpetual bug: the check `rawAmount <= insuranceFundBalance` compared values in mismatched units and thus didn't enforce the real invariant ("do not withdraw more than the WAD-denominated balance"). Here, `startsWith(realRoot)` compares byte/character prefixes and thus doesn't enforce the real invariant ("resolved path must be `root` or `root + path.sep + ...`"). The existing unit tests only cover `..`-traversal and symlink-based escapes (`app/test/unit/path-test.ts:44-102`), never a same-prefix sibling directory, so this gap has gone unnoticed and unguarded.

`resolveWithin` is used in two places that consume attacker/repository-controlled input:
1. `app/src/ui/dispatcher/dispatcher.ts` `openRepositoryFromUrl()` resolves the `filepath` query parameter from an `x-github-client://openRepo` deep link against `repository.path`, then calls `shell.showItemInFolder(resolved)`: [2](#0-1) 
The `filepath` value originates directly from `parseAppURL()`/`parse-app-url.ts`, which only rejects absolute paths and otherwise passes the raw query-string value through unchanged. [3](#0-2) 
2. `app/src/lib/copilot-conflict-context.ts` resolves `file.path` (from merge-conflict file listings, i.e., attacker-influenced repository content) against the working directory before reading file contents into an AI conflict-resolution context: [4](#0-3) 

Because containment is the only thing standing between "stay inside repo" and "read/reveal arbitrary sibling paths," the `startsWith` bug directly undermines the security guarantee these call sites depend on.

### Impact Explanation
A user who opens Documents/GitHub or a similar folder with multiple repositories cloned side-by-side (the default and extremely common GitHub Desktop clone layout) is exposed to a deep link/PR-URL that supplies `filepath=../<reponame>-something/...`, resolving to a sibling folder that merely shares a name prefix with the legitimate repository. This can be used to reveal (via `shell.showItemInFolder`) files residing in a different repository or directory than the one the user intended to open — an unintended disclosure of file locations/paths outside the target repository, driven entirely by content the attacker controls (the deep link URL). The `copilot-conflict-context.ts` path is a secondary vector: if repository layout/tooling ever creates same-prefix sibling directories, conflict-resolution file reads could similarly escape the intended working directory boundary and leak file contents from outside the repo into the AI request context.

### Likelihood Explanation
Exploitation requires: (1) the victim clicking an attacker-crafted `x-github-client://openRepo?...&filepath=...` link, and (2) a sibling directory existing whose name is a superset-prefix of the target repository's directory name (e.g., cloning `myrepo` next to a pre-existing `myrepo-old`, `myrepo2`, `myrepo-secrets`, etc., which is a realistic naming pattern in a shared clone root like `~/Documents/GitHub/`). No admin rights, local access, or leaked credentials are needed — only a link click, matching the "unprivileged... link or deep link the user clicks" impact criteria. Likelihood is moderate: it depends on the presence of a favorably-named sibling directory, but such naming collisions are common in practice (fork clones, renamed/duplicated projects, `-old`/`-backup`/`-v2` suffixes).

### Recommendation
Fix the containment check in `_resolveWithin()` (`app/src/lib/path.ts`) to require a path-segment boundary, not just a string prefix, e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add regression tests in `app/test/unit/path-test.ts` covering the sibling-directory-with-shared-prefix case (both POSIX and Windows separators), mirroring how the original report recommended adding tests for the previously-untested precision/unit mismatch.

### Proof of Concept
```ts
import { resolveWithin } from '../../src/lib/path'
import { mkdtemp, mkdir } from 'fs/promises'
import { join } from 'path'
import { tmpdir } from 'os'

const parent = await mkdtemp(join(tmpdir(), 'gh-desktop-'))
const repoRoot = join(parent, 'myrepo')
const siblingSecret = join(parent, 'myrepo-secrets')
await mkdir(repoRoot)
await mkdir(siblingSecret)
await writeFile(join(siblingSecret, 'notes.txt'), 'private data')

// Attacker-supplied deep link filepath: "../myrepo-secrets/notes.txt"
const result = await resolveWithin(repoRoot, '..', 'myrepo-secrets', 'notes.txt')

// BUG: result is NOT null even though it resolves outside repoRoot,
// because "myrepo-secrets" textually starts with "myrepo".
console.log(result) // -> "<parent>/myrepo-secrets/notes.txt" (should be null)
```
This mirrors the `openRepositoryFromUrl` flow in `dispatcher.ts`, where such a `filepath` reaching `resolveWithin` unexpectedly returns a non-null, out-of-repo path that is then passed to `shell.showItemInFolder`.
