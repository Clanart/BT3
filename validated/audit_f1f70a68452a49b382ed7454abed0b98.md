### Title
Symlink-Following Arbitrary File Overwrite in DataLayer File Writer - (File: chia/data_layer/download_data.py)

### Summary
`write_files_for_root()` in `chia/data_layer/download_data.py` writes DataLayer full-tree/delta `.dat` files to fully predictable, deterministically-named paths derived only from public values (`store_id`, `root_hash`, `generation`). When called with `overwrite=True` it opens the target path in plain `"wb"` mode instead of an exclusive/no-follow mode, so if a symlink already exists at that predictable path, the write follows the symlink and overwrites whatever file it points to — the same bug class as CVE-2026-53803 (rsync following symlinks at predictable ancillary output paths).

### Finding Description
`get_full_tree_filename_path()` / `get_delta_filename_path()` compute file names purely from `store_id.hex()`, `root_hash.hex()`, and `generation` [1](#0-0) , values that are all publicly known (store ids and roots are published on-chain / via wallet singleton history per the DataLayer module doc  and referenced at `.cursor/context/data-layer.md` lines 33-37). Because these names are fully predictable ahead of time, a local attacker with write access to the target directory can pre-place a symlink at the exact future filename.

`write_files_for_root()` chooses the open mode based on `overwrite`:
```
mode: Literal["wb", "xb"] = "wb" if overwrite else "xb"
``` [2](#0-1) 

When `overwrite=True`, the file is opened with `"wb"`, which follows an existing symlink and truncates/writes through it instead of failing like the default `"xb"` (exclusive-create) mode would. The same unguarded `"wb"` pattern is also used unconditionally in `http_download()` [3](#0-2)  and in the full-tree write inside `insert_from_delta_file()` [4](#0-3) .

The `overwrite` flag and destination `foldername` are ultimately controllable through `DataLayer.add_missing_files()` [5](#0-4) , which is exposed as a DataLayer RPC endpoint (`add_missing_files` appears in `chia/data_layer/data_layer_rpc_api.py`, `data_layer_rpc_client.py`, and the `chia data` CLI in `chia/cmds/data.py`/`data_funcs.py`). A local RPC caller invoking this endpoint with `overwrite=True` (and optionally a custom `foldername`) drives the vulnerable write-through-symlink code path.

### Impact Explanation
If an unprivileged local user can predict/pre-create a symlink at the deterministic `.dat` filename inside a directory the DataLayer service writes into (e.g. `server_files_location`, or a caller-supplied `foldername` for `add_missing_files`), the DataLayer process — potentially running as a different, more privileged local user/service account — will write attacker-influenced or attacker-redirected content through that symlink to an arbitrary filesystem location, since the data written comes from the local Merkle tree content the DataLayer already knows about the store. This can overwrite arbitrary files reachable by the DataLayer process's permissions (e.g. config files, keys, other services' files), a local file-overwrite/integrity impact analogous to the rsync CVE.

### Likelihood Explanation
Exploitation requires: (1) local access to write into a directory the DataLayer process will write `.dat` files into, and (2) knowledge of the target `store_id`/`root_hash`/`generation` triple, which is derivable from public on-chain/wallet singleton state, and (3) triggering the `overwrite=True` write path (via the `add_missing_files` RPC/CLI command, which is reachable by any local Data Layer client with RPC access) or the periodic `http_download`/`insert_from_delta_file` writes. Because filenames are fully deterministic and the write path is reachable through a documented RPC endpoint, likelihood is moderate — it depends on local co-tenancy or a compromised/malicious downloader plugin having filesystem write access ahead of the legitimate write.

### Recommendation
- Never open ancillary/output files in `"wb"` mode when the destination path is externally predictable; use `os.open(path, os.O_WRONLY | os.O_CREAT | os.O_TRUNC | os.O_NOFOLLOW, ...)` or equivalent to reject symlinks, for both the `overwrite=True` branch of `write_files_for_root()` and the `http_download()`/`insert_from_delta_file()` full-tree writes.
- Before writing, `os.lstat()` the target path and refuse to proceed if it is a symlink.
- For the `add_missing_files` RPC, validate/restrict caller-supplied `foldername` and require the DataLayer service directories to be privately owned (mode 0700) so other local users cannot pre-plant symlinks.

### Proof of Concept
1. As a local unprivileged user co-located with the DataLayer service, determine a store's `store_id` (public) and predict a future `root_hash`/`generation` (or wait for a known committed root).
2. Compute the exact target filename via `get_full_tree_filename_path`/`get_delta_filename_path` logic (deterministic, reproducible from public inputs) [1](#0-0) .
3. Create a symlink at that path inside the DataLayer's writable directory (`server_files_location` or an attacker-influenced `foldername`) pointing at a sensitive target file.
4. Trigger `add_missing_files` with `overwrite=True` via RPC/CLI, or wait for the service's normal `write_files_for_root`/`http_download` cycle to run [2](#0-1) .
5. Observe that the DataLayer process writes through the symlink, overwriting the sensitive target file instead of creating a new file at the intended path.

Note: I could not fully trace the exact RPC parameter validation for `add_missing_files` in `chia/data_layer/data_layer_rpc_api.py` (its handler body was not retrievable within the available context), so the precise authorization/parameter-passing details for that specific RPC call are unverified — only its existence and the vulnerable file-writing primitives in `download_data.py` are confirmed from source.
