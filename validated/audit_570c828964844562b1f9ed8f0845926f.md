### Title
Consumed forwarded-output instruction is restored to the database and executed a second time — ([File: processor/src/multisigs/db.rs](processor/src/multisigs/db.rs))

### Summary
`ForwardedOutputDb::take_forwarded_output` decodes one `InInstructionWithBalance` out of a stored byte buffer, but when additional bytes remain it writes back the **entire original buffer** (`&outputs`) instead of the unconsumed remainder (`outputs_ref`). The consumed instruction is therefore resurrected in the database and will be returned again by the next `take_forwarded_output` call for the same `ExternalBalance` key. This is the same bug class as CVE-2024-26739: state is mutated as though an object were still owned after it has already been consumed/handled, so a single logical event is processed twice.

### Finding Description
In `processor/src/multisigs/db.rs`, `take_forwarded_output` reads the stored buffer, advances `outputs_ref` past one decoded instruction, then:

```rust
if outputs_ref.is_empty() {
  txn.del(Self::key(balance));
} else {
  Self::set(txn, balance, &outputs);   // should be outputs_ref
}
``` [1](#0-0) 

When the queue holds ≥2 encoded instructions, `set` stores `outputs` — the full pre-decode buffer including the instruction just returned — so the first instruction remains at the head of the queue.

This queue is populated in `scanner_event_to_multisig_event` when the old multisig is in `RotationStep::ForwardFromExisting`: each forwarded external output causes `ForwardedOutputDb::save_forwarded_output` to append its `InInstructionWithBalance`, keyed by the (coin, amount) `ExternalBalance`. The queue is drained in the same function when scanned `OutputType::Forwarded` outputs arrive at the new multisig:

```rust
if let Some(instruction) = ForwardedOutputDb::take_forwarded_output(txn, output.balance()) {
  instructions.push(instruction);
}
``` [2](#0-1) 

The second forwarded output with the same balance therefore yields the *same* `InInstructionWithBalance` again, and the instruction is appended to the batch twice (`batch.instructions.push(instruction)` at `mod.rs:987-989`).

### Impact Explanation
An `InInstructionWithBalance` returned twice is emitted into the Substrate batch twice. For a deposit-style instruction this credits the originator's balance twice while only one real payment ever arrived — funds are reported as received that are not actually backed by forwarded coins. The threshold multisig's backing is diluted: a depositor who makes two distinct forwarded deposits sharing the same `ExternalBalance` (same coin, same post-fee amount) is credited for the first deposit twice, or depending on ordering, a stale instruction is replayed. This is a High-severity accounting/double-credit flaw reachable purely from on-chain transaction data an unprivileged depositor controls (they choose deposit amounts, hence the `balance` key collisions).

### Likelihood Explanation
The trigger requires (a) a multisig rotation in the `ForwardFromExisting` step, (b) two or more external deposits to the old multisig that produce `InInstructionWithBalance` entries whose *post-fee* `ExternalBalance` collides (the DB key is `instruction.balance` after `instruction.balance.amount.0 -= tx.0.fee()` at `mod.rs:884`), and (c) the corresponding `Forwarded` outputs being detected at the new multisig. A user can deliberately create two deposits of identical amount in the same or adjacent blocks to force the collision — no validator compromise, malformed encoding, or race is needed. The bug is deterministic once two entries share a key.

### Recommendation
In `take_forwarded_output`, persist the remainder rather than the original buffer:

```rust
if outputs_ref.is_empty() {
  txn.del(Self::key(balance));
} else {
  Self::set(txn, balance, &outputs_ref.to_vec());
}
```

Alternatively (more robust), store the queue as `Vec<InInstructionWithBalance>`-of-records and remove by index, so consumption cannot accidentally duplicate the head element. A regression test should save two distinct instructions under one `ExternalBalance`, call `take_forwarded_output` twice, and assert the two returned instructions differ and a third call returns `None`.

### Proof of Concept
1. Put the processor in `RotationStep::ForwardFromExisting` (multisig rotation in progress).
2. An attacker sends two external deposits `D1`, `D2` to the old multisig address with identical amounts, each carrying a valid `InInstruction` (e.g., deposits to distinct Serai addresses `A` and `B`).
3. `scanner_event_to_multisig_event` runs `instruction_from_output` for each, calls `prepare_send`, subtracts the same fee from each balance, and calls `save_forwarded_output` twice — producing one DB entry `[enc(I_A) || enc(I_B)]` under key `balance` (assuming equal post-fee amounts; with different amounts, two keys each holding one instruction, and a *third* colliding deposit still triggers the bug).
4. When the forwarded outputs land at the new multisig, the first `Forwarded` output calls `take_forwarded_output`, returns `I_A`, and stores back `[enc(I_A) || enc(I_B)]` instead of `[enc(I_B)]`.
5. The second `Forwarded` output calls `take_forwarded_output` again and returns `I_A` a second time.
6. The batch emitted contains `I_A` twice: address `A` is credited twice, `I_B` is never emitted, and the DB entry is only deleted once the queue drains — or `I_A` replays indefinitely across subsequent same-balance forwards.

    txn: &mut impl DbTxn,

    }
