### Title
`placeOrder` in IntentGatewayV2 escrows arbitrary, unwhitelisted ERC-20 tokens as order inputs - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
The external report's core defect is a public deposit entrypoint that accepts any `address token` parameter without validating it against a protocol-managed whitelist, causing user funds to become effectively unrecoverable except via manual/privileged intervention. `IntentGatewayV2.placeOrder` exhibits the same broken invariant: `order.inputs[i].token` is an arbitrary `bytes32`-encoded address supplied by the caller, and the function transfers it into escrow with no check that the token is registered, supported, or has any liquidity/solver market on the destination side.

### Finding Description
`placeOrder` iterates `order.inputs` and, for each entry, either sends it to the `CallDispatcher` (predispatch path) or does `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` directly into the gateway's own escrow, recording the amount in `_orders[commitment][token]`. [1](#0-0) 

There is no whitelist, registry, or `isSupported`/`allowedToken` check anywhere in this contract for input tokens — a `grep` for such patterns in `IntentGatewayV2.sol` returns no matches. Any `address` can be encoded into `order.inputs[i].token` and escrowed, exactly like the `MultipliBridger.deposit(address token, uint256 amount)` pattern in the referenced report, which accepted unrestricted tokens.

The consequence mirrors the report's stuck-funds scenario: escrowed input tokens are only released in two ways — (1) a solver fills the order and the input is transferred to the solver via `withdraw()` after a `RedeemEscrow`/cross-chain settlement message, as seen in the test flow that calls `intentGateway.onAccept()` with a `WithdrawalRequest` to release `_orders[commitment][token]` to a beneficiary, [2](#0-1)  or (2) cancellation/refund back to the user. If a user places an order whose input token is not one any solver is willing/able to acquire the corresponding output for (e.g., an obscure, illiquid, or protocol-unsupported ERC-20), no solver will ever call `fillOrder`, and the tokens remain locked in the gateway's escrow (`_orders[commitment][token]`) until the deadline passes and the user manually cancels. Unlike a simple UX inconvenience, this is structurally identical to the seed bug: the contract's deposit-style entrypoint (`placeOrder`) has no gating on the asset type, so a naive/malicious front-end integration or a mis-specified NFT/exotic-token order can silently strand user funds in a specialized cross-chain settlement contract that assumes deep counterpart liquidity and solver willingness — with no owner/whitelist-based recovery mechanism at all in this contract (there's no `removeFunds`-style escape hatch; recovery depends entirely on `cancelOrder` succeeding, which itself depends on the order not being "filled").

### Impact Explanation
Users can have their escrowed input tokens made effectively inaccessible for extended periods (until deadline + cancellation) because the contract offers no validation that a token is tradable/supported by the solver network before accepting it into escrow. This is a fund-lock class impact directly analogous to the accepted Medium-severity finding in the seed report, reachable by any unprivileged user through the normal `placeOrder` public entrypoint.

### Likelihood Explanation
High likelihood of accidental triggering: any front-end bug, user error, or unsupported/newly-listed token passed into `order.inputs` will escrow funds with no on-chain safeguard. No privileged actor, relayer, or malicious peer is required — this is purely a self-inflicted but system-permitted state reachable via the public `placeOrder` function.

### Recommendation
Introduce an owner/governance-managed token whitelist (or a minimum-liquidity/registered-asset check tied to the price oracle or a solver-support registry) that `placeOrder` validates each `order.inputs[i].token` against before transferring funds into escrow, rejecting orders that reference unsupported tokens. Optionally, since orders already have a `deadline` and `cancelOrder`, ensure the whitelist check happens before any transfer to avoid any custody of unsupported assets in the first place.

### Proof of Concept
1. A user calls `placeOrder` with `order.inputs[0].token` set to an arbitrary ERC-20 that no solver will accept as an input asset (e.g., a low-liquidity or unlisted token) and reasonable `output.assets`.
2. `placeOrder` executes `IERC20(token).safeTransferFrom(msg.sender, address(this), amount)` and records `_orders[commitment][token] = reducedInputs[i].amount` with no validation of `token`. [1](#0-0) 
3. Because no solver profitably or practically fills orders with this input token, `fillOrder` is never called before `order.deadline`.
4. The user's only recovery path is `cancelOrder`, and until then (or if cancellation is also neglected/misused) the tokens sit locked in the contract's escrow with no owner-level whitelist ever having prevented the initial deposit — reproducing the "stuck funds due to lack of whitelisting" pattern from the seed report inside Hyperbridge's intent-settlement contract.
