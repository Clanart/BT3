### Title
Permissionless `donateRewards` reward-per-share update rounds down to zero, permanently freezing/losing staker rewards - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool.donateRewards` (and its equivalent in `BaseRewardPoolV2.sol`, `rewards/mWOMSVBaseRewarder.sol`, and `rewards/vlMGPBaseRewarder.sol`) is callable by any unprivileged wallet and feeds directly into `_provisionReward`, which updates `rewardInfo.rewardPerTokenStored` using integer (floor) division against `totalStaked()`. When the deposited amount is small relative to `totalStaked()`, the division rounds to zero and the newly transferred reward tokens are permanently lost from the per-share accounting, even though the tokens are pulled into the contract and `historicalRewards` is incremented.

### Finding Description
`donateRewards` has no access control beyond requiring the token be already registered as a reward token: [1](#0-0) 

It calls `_provisionReward`, which computes the per-share delta with floor division: [2](#0-1) 

Note the `queuedRewards` "carry-over" mechanism only fires when `totalStaked() == 0` — it does **not** protect against the case where `totalStaked() > 0` but `(_amountReward * 10**stakingDecimals()) / totalStaked()` rounds to zero. In that case the reward amount is silently dropped from `rewardPerTokenStored` forever; it is not queued, not refunded, and not distributable to any staker. The same pattern recurs in `BaseRewardPoolV2._provisionReward` [3](#0-2) , `mWOMSVBaseRewarder._provisionReward` [4](#0-3) , and `vlMGPBaseRewarder.queueNewRewards` [5](#0-4) .

Because `queueNewRewards` (the legitimate path used by `WombatStaking.vote` to distribute harvested bribe rewards [6](#0-5) ) shares this exact same `_provisionReward` rounding logic, an attacker can also grief the "carry-over" `queuedRewards` bucket: whenever `queuedRewards > 0` and a subsequent `donateRewards`/`queueNewRewards` call combines a small amount with the queued balance, the combined total can still round to zero relative to a large `totalStaked()`, silently zeroing out the previously queued (and legitimately due) reward balance as well — since `rewardInfo.queuedRewards` is unconditionally reset to `0` before the division occurs.

This matches the root cause described in the referenced report: a floor-division update to a global reward-per-share accumulator that any unprivileged caller can trigger with small amounts, causing rewards to round down to zero and become permanently unrecoverable by stakers.

### Impact Explanation
Every time this rounds to zero, the corresponding reward tokens are transferred into the pool contract but become permanently untracked in `rewardPerTokenStored` — no staker can ever claim them (the tokens sit in the contract as unaccounted balance). This is a permanent freezing/loss of unclaimed yield belonging to all current stakers in the pool. As `totalStaked()` grows (i.e., the more successful/larger the vault), the attack becomes trivially easy since even legitimate small `donateRewards`/`queueNewRewards` calls will round to zero. Because `donateRewards` is fully unprivileged, any wallet can repeatedly call it with dust reward-token amounts (once they hold the registered reward token) to force this condition and wipe out any `queuedRewards` carry-over balance intended for stakers, weaponizing what is otherwise an innocuous "top-up" function into a griefing vector against reward distribution.

### Likelihood Explanation
Likelihood is elevated on low-fee networks: an attacker only needs to acquire a small amount of the already-registered reward token and repeatedly call the unauthenticated `donateRewards` function. No special role or governance access is required — this is directly reachable by an ordinary wallet. The larger a pool's TVL grows, the smaller the amount needed to trigger the zero-rounding, and the more often it can be triggered incidentally (e.g., during normal `queueNewRewards` calls from `WombatStaking.vote`) as well as maliciously.

### Recommendation
Track and carry over any residual/undistributed reward remainder (the "dust" lost to floor division) instead of discarding it, e.g., accumulate `(_amountReward * 10**decimals) % totalStaked()` into `rewardInfo.queuedRewards` so it is included in the next distribution rather than being silently zeroed. Additionally, consider requiring `donateRewards` (and any code path resetting `queuedRewards`) to only reduce `queuedRewards` by the amount actually consumed by the division, not the whole balance.

### Proof of Concept
1. Assume a `BaseRewardPool` for a staking token with `stakingDecimals() == 18`, and `totalStaked()` (i.e., the operator's total staked balance) is large, e.g. `1_000_000e18`.
2. A previous legitimate `queueNewRewards` call left `rewardInfo.queuedRewards = 500e6` (a reward token with 6 decimals) because stakers hadn't been fully paid.
3. Attacker calls `donateRewards(1, rewardToken)` (owning at least 1 wei of the registered reward token).
4. In `_provisionReward`: `totalStaked() != 0`, `queuedRewards > 0` so `_amountReward = 1 + 500e6 = 500000001`; then `rewardInfo.queuedRewards` is reset to `0`.
5. `rewardInfo.rewardPerTokenStored += (500000001 * 1e18) / 1_000_000e18 = 500000001 * 1e18 / 1e24 ≈ 0` (rounds to zero given the magnitude mismatch, e.g., for the report's own example `10000000 > tokensClaimed` threshold analogously applies here with `stakingDecimals` and `totalStaked` in the denominator).
6. Result: the entire `500e6` previously-queued reward balance plus the attacker's donated dust is now unaccounted for in `rewardPerTokenStored`; no staker can ever claim it via `earned()`/`getReward()`, even though the tokens remain locked in the contract. This directly demonstrates a repeatable, permissionless mechanism to permanently freeze staker rewards.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
