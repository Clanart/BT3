### Title
Unchecked `fee_per_vbyte * vbytes` / `payment_sat + needed_fee` arithmetic lets the fee bound checks pass while the computed values violate their bounds — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The nouns-builder report describes a guard that bounds an intermediate (`totalBPS < BPS_PER_100_PERCENT`) but not the derived product (`_finalBidAmount * totalBPS`), so the check passes while the value it was meant to constrain overflows/underflows downstream. `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` exhibits the same shape: it bounds-checks the *rate* (`needed_fee < min_relay`) and the *inputs vs a sum* (`input_sat < payment_sat + needed_fee`), yet every product and sum feeding those checks is computed with unchecked `u64` arithmetic. A wrapped `fee_per_vbyte * vbytes` or `payment_sat + needed_fee` makes the guards pass while the actual transaction economics violate them, producing a transaction that is signed yet unconfirmable, or a panic that aborts the caller.

### Finding Description
In `SignableTransaction::new`, the fee/solvency logic is:

- `let mut needed_fee = fee_per_vbyte * vbytes;` (send.rs:206) — unchecked multiplication.
- `if needed_fee < ((DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000) { Err(TooLowFee) }` (send.rs:211) — checks `needed_fee`, but if `fee_per_vbyte * vbytes` wrapped to a small value, the check compares the wrapped result, not the true product — the exact "check the intermediate, not the derived value" flaw from the report.
- `if input_sat < (payment_sat + needed_fee) { Err(NotEnoughFunds) }` (send.rs:215) — `payment_sat + needed_fee` is an unchecked addition; if it overflows, the solvency check passes while outputs+fee exceed inputs.
- `input_sat.checked_sub(payment_sat + fee_with_change)` (send.rs:228) — `payment_sat + fee_with_change` itself overflows *before* `checked_sub` runs, and `fee_with_change = fee_per_vbyte * vbytes_with_change` (send.rs:227) is another unchecked product. A wrapped `fee_with_change` also makes the change output absorb nearly all leftover funds, so `fee()` (send.rs:138–141) returns a far smaller value than `needed_fee()`, and the signed transaction pays a sub-relay fee.

`fee_per_vbyte` is supplied by the caller; in production the processor feeds it `self.median_fee(&block_for_fee)` (processor/src/networks/bitcoin.rs:430–451), a value derived from fee rates of transactions in a recent block — i.e., influenced by transactions any unprivileged party broadcasts to the Bitcoin network. There is no bound on `fee_per_vbyte` anywhere in `SignableTransaction::new`, mirroring how `_computeTotalRewards` never bounds `_finalBidAmount`.

### Impact Explanation
- With overflow-checks enabled (debug builds), `fee_per_vbyte * vbytes` or `payment_sat + fee_with_change` panics, crashing the caller — a DoS of transaction construction triggered by attacker-influenced fee data.
- With wrapping arithmetic (release), a wrapped-small `needed_fee` passes `TooLowFee`, and a wrapped `fee_with_change` inflates the change output so the signed transaction pays a near-zero actual fee: it signs successfully but will not be relayed/confirmed, causing a liveness failure of the payout and repeated signing attempts. A wrapped `payment_sat + needed_fee` defeats `NotEnoughFunds`, producing a transaction whose outputs+intended fee exceed the inputs — downstream `fee()` then underflows/panics (send.rs:139–140).

### Likelihood Explanation
Medium. `fee_per_vbyte` is attacker-influenced through publicly sent Bitcoin transactions (block fee median) and is unbounded by the API; `payments` amounts are also externally-derived (`(ScriptBuf, u64)` tuples with only a per-payment dust check, send.rs:165–169 — no bound on the aggregate). The wrap requires very large inputs, so exploitation is expensive but requires no privilege, no collusion, and no leaked keys — matching the report's Medium severity.

### Recommendation
Use checked/saturating arithmetic and bound the inputs, not just the intermediate:

```rust
let needed_fee = fee_per_vbyte
    .checked_mul(vbytes)
    .ok_or(TransactionError::TooLowFee)?; // or a dedicated FeeOverflow error

let total_out = payment_sat
    .checked_add(needed_fee)
    .ok_or(TransactionError::NotEnoughFunds { inputs: input_sat, payments: payment_sat, fee: needed_fee })?;
if input_sat < total_out { /* ... */ }

// likewise:
let fee_with_change = fee_per_vbyte.checked_mul(vbytes_with_change).ok_or(...)?;
if let Some(value) = input_sat
    .checked_sub(payment_sat)
    .and_then(|v| v.checked_sub(fee_with_change))
{ /* ... */ }
```
