### Title
Unauthenticated / unbound `SendMoveToVaultTx` broadcasts a move-tx tagged with an attacker-chosen `deposit_outpoint` - (File: core/src/rpc/aggregator.rs)

### Summary
`ClementineAggregator::send_move_to_vault_tx` accepts a raw `movetx` and a caller-supplied `deposit_outpoint`, validates only the *shape* of the transaction (input/output counts, output amounts, output script pubkeys), and never checks that `movetx.input[0].previous_output` actually equals the supplied `deposit_outpoint`. It then stores the mismatched pair in `TxMetadata` used by the tx-sender queue.

### Finding Description
In `send_move_to_vault_tx` [1](#0-0) , the code:
1. Deserializes the caller-provided `movetx`.
2. Checks `movetx.input.len() == 1 && movetx.output.len() == 2`.
3. Checks `movetx.output[0].value == bridge_amount` and `movetx.output[1].value == 0`.
4. Checks the two output script pubkeys equal the derived N-of-N + security-council vault address and the anchor script.
5. Never reads or verifies `movetx.input[0].previous_output` against the `deposit_outpoint` taken from the request [2](#0-1) .
6. Persists `TxMetadata { deposit_outpoint: Some(deposit_outpoint), ... tx_type: TransactionType::MoveToVault }` together with the raw `movetx` into the tx-sender queue via `insert_try_to_send` [3](#0-2) .

Because the only cryptographic binding checked is on the *outputs* (which are attacker-controlled fields of a legitimately-signed move-tx), an attacker can:
- Obtain a valid move-tx signed by verifiers for deposit A (with `input[0].previous_output = A`).
- Call `send_move_to_vault_tx` with the same `movetx` but claim `deposit_outpoint = B` (where B is a different UTXO).
- The method will accept it and queue the move-tx with metadata claiming it belongs to deposit B.

### Impact Explanation
The move-to-vault transaction is the critical bridge-custody transaction that transfers a user's deposit from the user-controlled address to the N-of-N vault. The `TxMetadata.deposit_outpoint` is used by downstream systems (e.g., state machines, database queries) to track which deposit a move-tx belongs to.

By misattributing a move-tx to a different deposit:
- **Custody attribution breaks**: The system records that deposit B's move-tx was broadcast, when in fact deposit A's move-tx was broadcast. Deposit B's actual move-tx may never be sent.
- **Operator reimbursement misattribution**: If the operator is reimbursed based on which deposits have confirmed move-txs, the operator can be credited for a move-tx it never funded or fronted.
- **Deposit state corruption**: The verifier/operator state machines may mark deposit B as "moved to vault" when it is not, preventing legitimate withdrawal or recovery flows for deposit B.

This breaks the custody binding: `move_tx_broadcast_for_deposit_X == move_tx_actually_spends_deposit_X`.

### Likelihood Explanation
The vulnerability is reachable by any unauthenticated caller (the `send_move_to_vault_tx` RPC is public, not guarded by the `OnlyAggregatorAndSelf` interceptor [4](#0-3) ). The attack requires only:
1. A valid move-tx (obtained from a prior legitimate `new_deposit` call or from observing the network).
2. A different deposit outpoint (trivial to construct).
3. A single RPC call.

No key compromise, majority hashrate, or malicious peer is required.

### Recommendation
Before persisting `TxMetadata`, verify that `movetx.input[0].previous_output == deposit_outpoint`. This ensures the move-tx actually spends the claimed deposit UTXO.

### Proof of Concept
1. Call `new_deposit(deposit_A)` → receive `movetx_A` (signed by verifiers, spends deposit A).
2. Call `send_move_to_vault_tx(movetx_A, deposit_outpoint=B)` where B ≠ A.
3. The RPC succeeds and queues `TxMetadata { deposit_outpoint: B, tx_type: MoveToVault }` with `movetx_A`.
4. Downstream systems believe deposit B's move-tx was broadcast, but the actual transaction spends deposit A.
5. Deposit B remains unspent; operator is credited for a move-tx it did not fund. [5](#0-4)
