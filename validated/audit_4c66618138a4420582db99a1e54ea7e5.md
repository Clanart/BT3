### Title
Non-global `startRe` match anchors on attacker-echoed fake `--printenvz--begin` marker, corrupting parsed hook environment - (File: app/src/lib/hooks/get-shell-env.ts)

### Summary
`getShellEnv` spawns the user's shell in interactive-login mode (`-ilc` for bash/zsh) with `cwd` set to the repository directory, then greps its combined stdout for a `--printenvz--begin` / `--printenvz--end` marker pair emitted by the trusted `printenvz` helper to isolate the real environment dump from any noise the shell's startup files might print. The start marker is found with a **non-global** regex (`stdout.match(startRe)`), which always returns the *first* match in the buffer. If repository-controlled shell configuration (e.g. a project `.envrc` sourced via direnv's shell hook, or any rc script) prints the literal string `--printenvz--begin` to stdout before the real `printenvz` binary executes, that fake occurrence becomes `startMatch`, and everything between it and the genuine `--printenvz--end` (found via `matchAll` + `.at(-1)`, which correctly takes the *last* end marker) is parsed as trusted `KEY=VALUE\0` environment data.

### Finding Description
The comment at [3](#0-2)  explains the marker's purpose is precisely to defend against a hostile/noisy shell init script, but the implementation only defends the *end* side (via `matchAll` + `.at(-1)` picking the last end marker) and not the *start* side (`stdout.match(startRe)` picks the first begin marker unconditionally, since `startRe` has no `g` flag).

Attack flow:
1. Desktop clones/opens a repository whose checkout causes an interactive-login shell (bash/zsh `-ilc`) to source rc files that, in turn, load a repo-scoped mechanism (direnv `.envrc`, asdf `.tool-versions` hook, custom `.bashrc` sourcing a repo file, etc.) because `cwd` is the repository path. [4](#0-3) 
2. That mechanism prints attacker-controlled text to stdout that includes the literal marker `--printenvz--begin\n` followed by attacker-chosen `KEY=VALUE\0`-formatted data (mimicking the null-byte-delimited format the real parser expects, see `printenvz.c`) before the real `printenvz` binary is invoked and emits the genuine markers.
3. `stdout.match(startRe)` matches the attacker's fake begin marker (the first one in the buffer), not the real one from `printenvz`. [5](#0-4) 
4. The substring parsed as environment (`stdout.substring(startMatch.index + startMatch[0].length, lastEndMatch.index)`) now spans from the attacker's fake begin through the real `printenvz--end`, i.e. it includes the attacker's injected fake-begin payload *and* the genuine env dump, both matched by `/([^=]+)=([^\0]*)\0/g`. [6](#0-5) 
5. Because `Object.fromEntries` is used, later duplicate keys overwrite earlier ones, but the attacker's injected key/value pairs are processed in the same trusted stream — the attacker can inject *new* keys not present in the real env, or (depending on ordering) override real values that appear after their injected block but before the real dump, since attacker content is prepended into the parsed range.

### Impact Explanation
The resulting `env` object from `getShellEnv` is merged (with `GIT_` /`GITHEAD_`-prefixed proxy env and `GITHUB_DESKTOP=1`) into the actual environment used to execute the real Git hook via `git hook run` in `hooks-proxy.ts`: `env: { ...shellEnv.env, ...safeEnv, GITHUB_DESKTOP: '1' }`. [7](#0-6)  It is also used to resolve `GIT_EXEC_PATH`/system `git` location by looking up `PATH` from this same env object. [8](#0-7)  An attacker who can inject arbitrary key/value pairs into this "trusted" shell env (via a repo-scoped rc/`.envrc` hook that fires before `printenvz` prints its real begin marker) can smuggle in extra environment variables such as an attacker-controlled `PATH` prefix, which `which('git', { path: pathEnv })` will consult to locate "system git" and thus influence which `git` binary Desktop resolves `GIT_EXEC_PATH` from — a path that then feeds into the hook execution environment for hooks run against the user's real repository. This is a supply-chain-style environment poisoning primitive reachable purely from repository content (shell rc/`.envrc` files that ship with, or are triggered by opening, a cloned repo), landing on the exact hook-execution environment Desktop uses for pre-commit/post-checkout/etc. hooks.

### Likelihood Explanation
Exploitability depends on the user's shell configuration honoring a repository-scoped hook (direnv, asdf, custom dotfiles that `source` files relative to `$PWD`) on interactive-login shell startup, which is common in developer environments (direnv is popular specifically for this purpose) and is exactly the class of "cwd-triggered shell startup" this code's own comment already anticipates as a risk (hence the marker mechanism existing at all) — it's a real gap in that intended mitigation rather than a purely theoretical one, though it requires the victim to already have such a shell hook mechanism installed and enabled, which is a plausible but not universal environment/local-config precondition.

### Recommendation
Anchor on the *last* begin marker rather than the first, mirroring the existing handling of the end marker: use `matchAll` on `startRe` (with the `g` flag) and take `.at(-1)`, so that any earlier attacker-echoed fake `--printenvz--begin` text is ignored and only the last (i.e., the real, since `printenvz` runs last in the command list) begin/end marker pair delimits the parsed range. Additionally, consider having `printenvz` print a random per-invocation nonce (passed via argv) into the markers so a static string can't be pre-echoed at all.

```ts
// Simulated repro against the parsing logic in get-shell-env.ts
const fakeShellStdout =
  '--printenvz--begin\n' +          // attacker-echoed fake begin (from .envrc/rc script)
  'PATH=/tmp/evil:/usr/bin\0' +      // attacker-injected fake env entries
  'GIT_EXEC_PATH=/tmp/evil\0' +
  '--printenvz--begin\n' +          // real begin, printed by printenvz
  'PATH=/usr/bin:/bin\0HOME=/home/user\0' +
  '\n--printenvz--end\n'

const startRe = /--printenvz--begin\r?\n/
const endRe = /\r?\n--printenvz--end\r?\n/g
const startMatch = fakeShellStdout.match(startRe)          // matches the FIRST (fake) marker
const lastEndMatch = [...fakeShellStdout.matchAll(endRe)].at(-1)

const parsed = Object.fromEntries(
  fakeShellStdout
    .substring(startMatch.index + startMatch[0].length, lastEndMatch.index)
    .matchAll(/([^=]+)=([^\0]*)\0/g)
)
console.log(parsed)
// => { PATH: '/tmp/evil:/usr/bin', GIT_EXEC_PATH: '/tmp/evil' }  <-- attacker-controlled PATH wins
// The real printenvz PATH/HOME entries after the second fake begin marker are still parsed too,
// but the injected GIT_EXEC_PATH / earlier PATH entry is present in the final env, and depending
// on key ordering an attacker can force their own values to be the ones that persist.
```
