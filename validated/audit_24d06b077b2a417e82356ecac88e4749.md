### Title
IBC-Callbacks destination path permanently traps unescrowed/minted funds in an unreachable isolated address instead of atomically reverting on callback failure - ([File: x/ibc/callbacks/keeper/keeper.go])

### Summary
This is the closest reachable analog to the Peapods `_swapV2()` bug: a multi-step value-transfer pipeline (unescrow/mint → convert to ERC20 → invoke external contract) where a failure partway through the pipeline leaves value stranded at an intermediate address instead of being fully rolled back or fully delivered, exactly like the intermediate `tokenB` stuck by the `maxSwap` cap in the original report.

### Finding Description
The EVM IBC-callbacks flow (`x/ibc/callbacks/keeper/keeper.go`, `IBCReceivePacketCallback`) is invoked by ibc-go's callbacks middleware *after* the base ICS20 transfer application has already run `OnRecvPacket`, which unescrows/mints the transferred coin directly to the "isolated address" (`data.Receiver`) [1](#0-0) . Only the subsequent steps — `approve` and the arbitrary EVM contract call — run inside a `CacheContext` (`cachedCtx`/`writeFn`) [2](#0-1) . If those steps fail (e.g. the target contract call reverts, or a downstream restriction such as `SendEnabled=false` blocks conversion), `IBCReceivePacketCallback` returns an error and the overall packet acknowledgement becomes an `ErrorAcknowledgement` [3](#0-2) .

Crucially, the base transfer module's unescrow/mint into the isolated address (performed by `im.Module.OnRecvPacket` before the callback keeper even runs) is **not** wrapped in the same `CacheContext` and is therefore **not reverted** when the callback later fails. This exact behavior is demonstrated in the test suite: after a failed callback attempt, the value is confirmed to sit permanently in the isolated address's bank balance rather than being reverted: [4](#0-3) 

The isolated address has no private key and, per the module's own documentation, any funds deposited there directly (rather than forwarded by the callback contract) are explicitly acknowledged as unreachable: [5](#0-4) 

Meanwhile, because the destination chain returns an `ErrorAcknowledgement` for this packet, the standard ICS20 semantics on the **source** chain will refund/re-mint the sender's tokens there (standard ack-error refund path), while the **destination** chain has already, irreversibly, credited the same value to the unreachable isolated address. This produces two live claims on what should be a single unit of value — a duplication of spendable value across the two chains' IBC escrow/voucher accounting, rather than a strict "leftover stuck token" as in the Peapods analog.

### Impact Explanation
This maps to the Critical impact category "unauthorized minting, burning, duplication, resurrection, or irreversible accounting corruption of spendable user value across native balances ... IBC escrows." The unescrowed/minted amount becomes permanently locked/unreachable at the isolated address (Critical permanent freezing of user funds) while, per standard ICS20 ack-failure semantics, the sender is separately made whole on the source chain — resulting in double-counted value across chains and an irreversible loss for the destination chain's asset backing.

### Likelihood Explanation
This is triggered by any unprivileged user who initiates an ICS20 transfer with an EVM dest-callback memo where the destination contract (or any downstream restriction affecting the approve/call path) fails after the transfer has been received. No privileged actor or malicious relayer is required — a legitimate transfer that merely encounters a reverting/misbehaving destination contract, or hits `SendEnabled=false`/minting restrictions, is sufficient, and the test suite already demonstrates this exact scenario occurring in normal operation.

### Recommendation
Wrap the entire destination-side pipeline — the base transfer unescrow/mint to the isolated address, the ERC20 conversion, `approve`, and the target contract call — in a single `CacheContext` that is only committed if every step (including the final "sender has zero remaining balance" check) succeeds. If any step fails, the whole receive should be rolled back so no coin is materialized on the destination chain, ensuring the resulting `ErrorAcknowledgement` truthfully reflects that no value was transferred, consistent with what the source chain's refund logic assumes.

### Proof of Concept
The existing test `TestOnRecvPacketNativeErc20` (case `withCallback: true`) in `evmd/tests/ibc/ibc_middleware_test.go` already reproduces the state: with `SendEnabled=false`, `OnRecvPacket` returns an error acknowledgement (`errAck.Success()` is `false`), yet the balance check afterward confirms `recvAmt` sits permanently in the isolated address's bank balance [6](#0-5) . Full end-to-end confirmation that the source chain simultaneously refunds the sender (rather than leaving the packet failed with no state change on either side) was not directly located in the indexed code and would require validating the source-chain `OnAcknowledgementPacket`/ack-error refund path together with this destination-side test in a live two-chain relay — this final cross-chain double-accounting linkage is asserted based on standard ICS20 ack-error semantics but was not independently traced end-to-end within the available search results, so it should be verified with a running Devin session using the full IBC relay test harness (`evmibctesting`) before treating this as fully confirmed.

		return err
	}
	if !isCbPacket {
		return nil

```markdown
## Limitations

The receiver side callback **must** receive funds to an ephemeral address generated from the channelId and packet
sender address. Note that since this is a generated address, no user has the ability to sign messages on behalf of
this account even though it is a cross-chain representation of the packet sender.

Thus, a contract that receives the funds and calldata from the isolated receiver address **must** send the tokens
onwards to a desired address that is specified in the calldata. If tokens are deposited back into the isolated address,
they are unreachabe. If you wish to interact with a contract that does not implement functionality for sending the
tokens to a different address then you must interact with that contract through some wrapper contract interface that
can receive the funds, call the contract which deposits funds back to `msg.sender` and then the wrapper contract
can move the funds to a final desired address.
```
