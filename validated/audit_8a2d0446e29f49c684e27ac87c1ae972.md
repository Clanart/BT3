### Title
OAuth CSRF `state` (the "escrow" for a sign-in attempt) is checked-but-not-consumed, allowing a single browser sign-in callback to be replayed for repeated token exchanges - ([File: app/src/lib/stores/sign-in-store.ts])

### Summary
`SignInStore.resolveOAuthRequest` validates an incoming `x-github-client://oauth?code=...&state=...` deep link by comparing `action.state` to the `oauthState.state` value that was generated in `authenticateWithBrowser`. This comparison is the only guard against re-processing a callback, but the guard is never invalidated: the `state` value stays valid for the entire duration of the async `requestOAuthToken`/`fetchUser` call chain and is only ever superseded when the sign-in eventually transitions to `SignInStep.Success`. Any deep-link invocation delivered before that transition completes will pass the equality check again, exactly the "condition cannot guarantee correctness for two consecutive executions" pattern described in the report.

### Finding Description
`authenticateWithBrowser` creates a per-attempt token and stores it as `oauthState.state`: [1](#0-0) 

`resolveOAuthRequest`, invoked from the OS protocol handler via `dispatchURLAction` for every `x-github-client://oauth` URL the app receives, only checks that `state` matches; it does not delete, rotate, or otherwise consume `oauthState` before making the network calls that actually exchange the authorization `code` for a token and fetch the account: [2](#0-1) 

Because the state comparison and the state-clearing/`Success` transition are separated by two `await`s (`requestOAuthToken`, `fetchUser`), the store remains in `SignInStep.Authentication` with the identical `oauthState.state` for the entire round trip. Any second `x-github-client://oauth` URL carrying the same `state` (and the same or a different `code`) delivered to `dispatchURLAction` during that window will pass the check again: [3](#0-2) [4](#0-3) 

The `state` value here plays the role of the "escrow" in the report: a value meant to authorize exactly one continuation of a flow, but whose validity is never revoked after a use, so the same authorization can be exercised more than once.

### Impact Explanation
A replayed/duplicate deep-link invocation with the same `state` causes `resolveOAuthRequest` to execute `requestOAuthToken` and `fetchUser` a second time concurrently with the first, using whatever `code` is present in the second URL. Custom URL-scheme invocations on Windows/macOS can be delivered more than once for a single click (e.g. via `second-instance` activation, OS URL-scheme dispatch quirks, or a malicious page that fires the callback URL to the app twice), and an attacker who can get a victim to open a second copy of a previously observed OAuth callback link (or race the handler) can force a second in-flight token exchange for the same sign-in attempt. This does not directly forge a new account, but it demonstrates the underlying invariant break: a value the code treats as single-use is not enforced as such, so any code exchange delivered with a still-valid `state` is accepted and processed regardless of how many times it has already been consumed.

### Likelihood Explanation
This requires an active social-engineering step (getting the user to click a captured/duplicated OAuth callback link) and a timing window during the async request/response of the OAuth token exchange; it is not a "click one link" one-shot server-side vulnerability. It's a moderate-likelihood logic gap rather than a straightforward remote-code path, and depends on race conditions in the OS protocol dispatch mechanism, which is why it maps closely, but only closely, to the reported "escrow reused" pattern.

### Recommendation
Consume (delete/replace) `oauthState` synchronously as soon as the `state` comparison succeeds in `resolveOAuthRequest`, before awaiting `requestOAuthToken`/`fetchUser`, so that any subsequent callback with the same `state` is rejected. Equivalently, transition the store out of `SignInStep.Authentication` (or clear `oauthState.state`) immediately upon a successful match rather than only after the network round trip completes.

### Proof of Concept
1. Start a browser sign-in (`authenticateWithBrowser`); the store enters `SignInStep.Authentication` with `oauthState.state = csrfToken` [1](#0-0) .
2. The OS delivers `x-github-client://oauth?code=CODE&state=csrfToken` to `dispatchURLAction` → `_resolveOAuthRequest` → `resolveOAuthRequest`.
3. Before the first call's `await requestOAuthToken(...)` resolves, deliver the identical URL a second time (e.g., duplicate protocol-handler invocation or a webpage that fires the callback link twice).
4. Because `this.state.oauthState.state !== action.state` is still `false` (unchanged), the check at [5](#0-4)  passes a second time, and `requestOAuthToken`/`fetchUser` execute again concurrently for the same sign-in attempt.

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }
