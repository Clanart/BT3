### Title
OP_RETURN data bypasses transaction fee accounting - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends a caller-controlled `OP_RETURN` output to the signed transaction, but calculates transaction weight and required fees without including that output. Transactions carrying up to 80 bytes of data therefore pay the fee rate calculated for a materially smaller transaction.

### Finding Description
`SignableTransaction::new` accepts up to 80 bytes of `data` and pushes an `OP_RETURN` output into `tx_outs`. [1](#0-0) 

The subsequent weight calculation is invoked with only `tx_ins.len()` and `payments`; `tx_outs`, including the newly added `OP_RETURN`, is not passed to `calculate_weight_vbytes`. [2](#0-1) 

`calculate_weight_vbytes` reconstructs a transaction containing inputs, payment outputs, and optional change, but has no parameter or logic for data outputs. [3](#0-2) 

When change is supplied, the change amount is calculated using the incorrectly low `fee_with_change`, locking the underpayment into the final output amounts. [4](#0-3) 

The transaction retained for signing still contains the omitted `OP_RETURN` output. [5](#0-4) 

### Impact Explanation
With a change output, the actual fee is exactly the underestimated `needed_fee` because all remaining value after payments and `needed_fee` is assigned to change. A maximum-size `OP_RETURN` adds approximately 91 serialized bytes and therefore approximately 91 additional vbytes, none of which are included in the requested-fee calculation. At a requested rate near Bitcoin's minimum relay rate, the completed transaction can fall below the minimum relay rate and be rejected or remain unconfirmed. If a caller relies on `needed_fee()` to charge users or report the transaction's required fee, the reported fee is incorrect by `fee_per_vbyte * op_return_vbytes`.

### Likelihood Explanation
The issue is deterministic whenever `data` is `Some` and sufficient residual value creates a change output. The API publicly accepts the data as part of transaction construction, and no malformed signatures, invalid encodings, or privileged state are required. Its impact is bounded by the 80-byte data limit, but the missing output can represent a substantial fraction of the virtual size of a typical Taproot transaction.

### Recommendation
Include the `OP_RETURN` output in both fee-estimation calls. Pass the optional serialized data into `calculate_weight_vbytes` or calculate the weight after constructing the complete `tx_outs` vector. The change-capable calculation must model the payment outputs, `OP_RETURN` output, and change output together before deriving `fee_with_change` and the change amount.

### Proof of Concept
For one Taproot input, one change output, no payments, an 80-byte `OP_RETURN`, and `fee_per_vbyte = 1`, `needed_fee` is calculated without the data output even though the final transaction includes it. The constructed transaction's actual virtual size is approximately 91 vbytes larger than estimated, so `tx.fee()` equals the original underestimated `needed_fee` while `tx.fee() / tx.vsize()` is materially below the requested 1 sat/vbyte rate.

```rust
let tx = SignableTransaction::new(
  vec![input],
  &[],
  Some(change_script),
  Some(vec![0u8; 80]),
  1,
).unwrap();

assert_eq!(tx.fee(), tx.needed_fee());
assert!(
  tx.fee() < u64::try_from(tx.transaction().vsize()).unwrap()
);
```

The failed inequality follows because `needed_fee` was derived from a transaction that did not contain the `OP_RETURN` output.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
