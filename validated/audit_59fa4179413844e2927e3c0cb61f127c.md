### Title
Timed-out CosmWasm `Create` (contract upload) leaves engine call running unsynchronized, allowing racing calls into the non-reentrant WasmVM engine - ([File: sei-wasmd/x/wasm/keeper/vm_wrapper.go])

### Summary
`VMWrapper` serializes every call into the underlying `WasmerEngine` (the Rust `wasmvm` FFI) behind a single `*sync.Mutex`, which strongly implies the underlying engine is not safe for concurrent invocation. `VMWrapper.Create` bounds contract-code compilation with a 15-second timeout using a background goroutine, but on timeout it returns while that goroutine keeps running against the shared engine, and `defer w.mu.Unlock()` releases the lock immediately — allowing a subsequent `Instantiate`/`Execute`/`Migrate`/`Pin` call to enter the engine concurrently with the still-running, abandoned `Create` call. [1](#0-0) 

### Finding Description
Every method on `VMWrapper` (`Create`, `Instantiate`, `Execute`, `Migrate`, `Sudo`, `Reply`, `Pin`, `Unpin`) takes the same `w.mu` mutex before delegating to `w.WasmerEngine`, which is the strongest evidence in the codebase that concurrent calls into the underlying wasmvm engine are unsafe and must be fully serialized: [2](#0-1) [3](#0-2) 

`Create` breaks this invariant. It locks `w.mu`, spawns a goroutine that calls `w.WasmerEngine.Create(code)` (compiling/validating the uploaded Wasm bytecode), and races that goroutine against a 15-second timer:
```go
func (w *VMWrapper) Create(code wasmvm.WasmCode) (checksum wasmvm.Checksum, err error) {
	w.mu.Lock()
	defer w.mu.Unlock()
	timer := time.NewTimer(CreateTimeout)
	done := make(chan struct{}, 1)
	go func() {
		checksum, err = w.WasmerEngine.Create(code)
		done <- struct{}{}
	}()
	select {
	case <-done:
		timer.Stop()
		return
	case <-timer.C:
		err = errors.New("create wasm code timed out")
		return
	}
}
``` [1](#0-0) 

If compilation exceeds `CreateTimeout` (15s), the `select` takes the timeout branch, `Create` returns an error, and the `defer` unlocks `w.mu` — but the background goroutine is never cancelled and continues executing `w.WasmerEngine.Create(code)` inside the shared, non-thread-safe Rust engine. Because the mutex is already released, any following contract call (another `MsgStoreCode`, `MsgInstantiateContract`, `MsgExecuteContract`, etc., from any sender in the same or a subsequent block) can immediately acquire `w.mu` and invoke `Instantiate`/`Execute`/`Migrate`/`Pin` on the very same `WasmerEngine` instance while the abandoned `Create` call is still running underneath — i.e., two engine calls execute concurrently against internal, non-reentrant Rust/FFI state, in direct violation of the invariant the mutex is meant to enforce.

This is structurally analogous to the referenced Linux CVE-2022-49316 bug class: a lock meant to protect a critical resource across a bounded operation is dropped (or never truly enforced) around a call that can outlive the lock's scope, letting a second caller reach the same protected resource concurrently with the first, unsynchronized in-flight operation.

### Impact Explanation
Concurrent, unsynchronized access to a native (cgo/FFI) engine that was deliberately wrapped in a mutex because it is not designed for concurrent invocation can corrupt internal engine state (e.g., its module/instance cache, compiled-module registries, or memory arenas) or trigger undefined behavior/crashes in the underlying Rust library. In the worst case this crashes the node process handling the transaction — a validator node executing the block, or an RPC node evaluating the same tx via `CheckTx`/simulation — producing a chain halt or block-processing delay while the timing race is hit repeatedly, and at minimum a crash of default-configuration nodes. Any unprivileged CosmWasm user who can submit `MsgStoreCode` with bytecode engineered to make compilation take longer than 15 seconds (e.g., a large/complex, pathologically structured but otherwise valid Wasm module) can trigger the timeout branch and open this race window.

### Likelihood Explanation
Reaching the timeout branch requires crafting Wasm bytecode whose validation/compilation in the wasmvm engine consistently exceeds 15 seconds — plausible for a large or adversarially structured contract, though it requires some engineering effort and is timing-dependent (the race window depends on how long the abandoned `Create` goroutine keeps running after timeout, and whether another wasm-engine call is submitted during that window). This is a contract-deployer-triggerable path with no special privileges, but the need to line up a slow-compiling upload with a concurrently arriving second wasm call makes exploitation non-trivial and probabilistic rather than deterministic.

### Recommendation
Do not unlock `w.mu` while the spawned `Create` goroutine is still running. Either:
- keep the mutex held until the background goroutine actually completes (wait on `done` even after the timeout fires, before releasing the lock and returning the timeout error), or
- pass a cancellable context/mechanism into the underlying engine call so it can actually be aborted before the lock is released, or
- avoid the goroutine/timeout pattern entirely and instead bound compilation cost deterministically (e.g., a gas/size-based static analysis limit) so `Create` cannot run unbounded in the first place.
The key invariant to preserve is that no other `VMWrapper` method may enter `w.WasmerEngine` while a prior call (including a timed-out one) is still executing inside it.

### Proof of Concept
1. Submit `MsgStoreCode` with a Wasm binary crafted so that `w.WasmerEngine.Create(code)` (compilation/validation in the underlying wasmvm engine) takes longer than `CreateTimeout` (15s) — e.g., a large module with many functions/tables designed to stress the compiler.
2. `VMWrapper.Create`'s `select` hits the `case <-timer.C` branch, returns `"create wasm code timed out"`, and its `defer w.mu.Unlock()` fires, releasing the lock while the spawned goroutine's `w.WasmerEngine.Create(code)` call is still executing.
3. Immediately submit a second CosmWasm message that reaches `VMWrapper.Instantiate` or `VMWrapper.Execute` (e.g., instantiate/execute an already-deployed contract). This acquires the now-free `w.mu` and invokes `w.WasmerEngine.Instantiate`/`Execute` concurrently with the still-running abandoned `Create` call from step 1.
4. Because the underlying engine was wrapped in a mutex specifically to prevent concurrent invocation, this concurrent access can corrupt engine internals or crash the process, deterministically reproducible by controlling the size/complexity of the uploaded bytecode to consistently exceed the 15-second timeout.

Note: I was unable to directly inspect the Rust/FFI internals of `sei-wasmvm/libwasmvm` in this environment to conclusively confirm the exact failure mode (crash vs. silent corruption) of concurrent engine invocation; the wrapping of every single engine method in the same mutex is the strongest available evidence that concurrent access is unsafe. A full validation of the crash/corruption mechanism would require running this race under the actual compiled `libwasmvm` binary.
