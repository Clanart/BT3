### Title
Missing Cross-Validation Between `time_to_send_watchtower_challenge` and `watchtower_challenge_timeout_timelock` Allows Operator to Bypass Watchtower Challenge Mechanism — (File: `core/src/config/mod.rs`)

---

### Summary

`BridgeConfig::time_to_send_watchtower_challenge` and `ProtocolParamset::watchtower_challenge_timeout_timelock` are configured independently with no cross-validation in production code. When `time_to_send_watchtower_challenge >= watchtower_challenge_timeout_timelock`, the operator can claim the on-chain `WatchtowerChallengeTimeout` before any verifier sends its watchtower challenge, silently bypassing the entire watchtower challenge mechanism and allowing a fraudulent BitVM proof to go unchallenged.

---

### Finding Description

The Clementine bridge protocol uses a watchtower challenge mechanism to force operators to include valid work proofs in their BitVM proofs. When a kickoff is challenged, the `KickoffStateMachine` in `on_challenged_entry` inserts a `Matcher::BlockHeight` event that fires at `kickoff_height + config.time_to_send_watchtower_challenge`, triggering `TimeToSendWatchtowerChallenge` and causing the verifier to send its watchtower challenge transaction. [1](#0-0) 

Separately, the on-chain `WatchtowerChallengeTimeout` transaction is pre-signed with a relative timelock of `paramset.watchtower_challenge_timeout_timelock` blocks from the kickoff: [2](#0-1) 

The required invariant is:

```
time_to_send_watchtower_challenge  <  watchtower_challenge_timeout_timelock
```

These two values live in **separate configuration structures** that are loaded and validated independently:

- `time_to_send_watchtower_challenge: u16` is in `BridgeConfig` (per-node, operator-controlled config): [3](#0-2) 

- `watchtower_challenge_timeout_timelock: u16` is in `ProtocolParamset` (protocol-level config): [4](#0-3) 

The `check_general_requirements()` function — the only production startup validation — checks genesis hash, start height, and finality depth, but **never validates the relationship between these two timing parameters**: [5](#0-4) 

Default values happen to satisfy the invariant (216 < 288), but there is no code-level enforcement. Because `time_to_send_watchtower_challenge` is a `BridgeConfig` field (not part of `ProtocolParamset`), it can be set to any value without triggering a compatibility error between actors.

---

### Impact Explanation

If `time_to_send_watchtower_challenge >= watchtower_challenge_timeout_timelock`:

1. A kickoff is sent on-chain and challenged.
2. The verifier's state machine schedules the watchtower challenge at `kickoff_height + time_to_send_watchtower_challenge` — a block height that is **at or after** the block at which the operator's `WatchtowerChallengeTimeout` becomes valid.
3. The operator broadcasts `WatchtowerChallengeTimeout` (spending both the `WatchtowerChallenge` UTXO and the `WatchtowerChallengeAck` UTXO) before the verifier's scheduled send time.
4. When the verifier's timer fires, the `WatchtowerChallenge` UTXO is already spent; the verifier's challenge transaction is invalid and will never confirm.
5. The operator proceeds to the assert phase without any watchtower work proof being committed on-chain.
6. The operator submits a BitVM proof that does not include the watchtower's Groth16 work proof. Because no valid watchtower challenge was ever included, the verifier has no on-chain data with which to construct a disprove transaction.
7. The `DisproveTimeout` fires, the operator claims reimbursement, and the bridged BTC (up to `bridge_amount`, default 1 BTC = 1,000,000,000 sat) is stolen. [6](#0-5) 

---

### Likelihood Explanation

**Low-to-Medium.** The default values are correctly ordered (216 < 288 in all shipped configs). However:

- `time_to_send_watchtower_challenge` is a `BridgeConfig` field, not a `ProtocolParamset` field, so it is not subject to the inter-actor compatibility check. Any verifier operator can set it independently.
- There is no startup assertion, no runtime warning, and no documentation warning about the required ordering.
- A misconfiguration (e.g., setting `TIME_TO_SEND_WATCHTOWER_CHALLENGE=300` while `WATCHTOWER_CHALLENGE_TIMEOUT_TIMELOCK=288`) silently breaks the watchtower challenge for every challenged kickoff handled by that verifier, with no error logged until the UTXO is already spent.

---

### Recommendation

Add a cross-validation check in `check_general_requirements()` (or at config parse time):

```rust
if self.time_to_send_watchtower_challenge
    >= self.protocol_paramset().watchtower_challenge_timeout_timelock
{
    reasons.push(format!(
        "time_to_send_watchtower_challenge ({}) must be strictly less than \
         watchtower_challenge_timeout_timelock ({})",
        self.time_to_send_watchtower_challenge,
        self.protocol_paramset().watchtower_challenge_timeout_timelock,
    ));
}
``` [7](#0-6) 

Alternatively, move `time_to_send_watchtower_challenge` into `ProtocolParamset` so that it is subject to the same inter-actor compatibility enforcement as all other timing parameters.

---

### Proof of Concept

1. Deploy a verifier with `TIME_TO_SEND_WATCHTOWER_CHALLENGE=300` and `WATCHTOWER_CHALLENGE_TIMEOUT_TIMELOCK=288` (or any pair where the former ≥ the latter). No startup error is produced.
2. A user deposits BTC; the operator sends a kickoff for a fraudulent payout.
3. A challenger sends the `Challenge` transaction, spending `UtxoVout::Challenge`.
4. The verifier's `on_challenged_entry` inserts `Matcher::BlockHeight(kickoff_height + 300)`.
5. At `kickoff_height + 288`, the operator broadcasts `WatchtowerChallengeTimeout` (valid because `Sequence::from_height(288)` is satisfied). Both `WatchtowerChallenge` and `WatchtowerChallengeAck` UTXOs are spent.
6. At `kickoff_height + 300`, the verifier fires `TimeToSendWatchtowerChallenge` and attempts to broadcast the watchtower challenge transaction — which is rejected by the mempool because its input UTXO is already spent.
7. The operator proceeds through the assert phase with no watchtower work proof on-chain, submits a fraudulent BitVM proof, and after `disprove_timeout_timelock` blocks claims the full `bridge_amount` reimbursement. [8](#0-7) [9](#0-8)

    pub(crate) async fn on_challenged_entry(&mut self, context: &mut StateContext<T>) {
        self.challenged = true;
        context
            .capture_error(async |context| {
                {
                    // create times to send necessary challenge asserts
                    self.matchers.insert(
                        Matcher::BlockHeight(
                            self.kickoff_height
                                + context.config.time_to_send_watchtower_challenge as u32,
                        ),
                        KickoffEvent::TimeToSendWatchtowerChallenge,
                    );
                    // Add relevant txs to tx sender if the kickoff is challenged
                    context
                        .dispatch_duty(Duty::AddRelevantTxsToTxSenderIfChallenged {
                            kickoff_data: self.kickoff_data,
                            deposit_data: self.deposit_data.clone(),
                        })
                        .await?;
                    Ok::<(), BridgeError>(())
                }
                .wrap_err(self.kickoff_meta("on_challenged_entry"))
            })
            .await;
        // check if any action is ready to be started as it could already be ready before a challenge arrives
        // but we want to make sure kickoff is actually challenged before we start sending actions
        self.create_matcher_for_latest_blockhash_if_ready(context)
            .await;
        self.send_operator_asserts_if_ready(context).await;
        self.disprove_if_ready(context).await;
    }

pub fn create_watchtower_challenge_timeout_txhandler(
    kickoff_txhandler: &TxHandler,
    watchtower_idx: usize,
    paramset: &'static ProtocolParamset,
) -> Result<TxHandler, BridgeError> {
    let watchtower_challenge_vout = UtxoVout::WatchtowerChallenge(watchtower_idx);
    let challenge_ack_vout = UtxoVout::WatchtowerChallengeAck(watchtower_idx);
    Ok(
        TxHandlerBuilder::new(TransactionType::WatchtowerChallengeTimeout(watchtower_idx))
            .with_version(NON_STANDARD_V3)
            .add_input(
                (
                    NumberedSignatureKind::WatchtowerChallengeTimeout1,
                    watchtower_idx as i32,
                ),
                kickoff_txhandler.get_spendable_output(watchtower_challenge_vout)?,
                SpendPath::ScriptSpend(0),
                Sequence::from_height(paramset.watchtower_challenge_timeout_timelock),
            )
            .add_input(
                (
                    NumberedSignatureKind::WatchtowerChallengeTimeout2,
                    watchtower_idx as i32,
                ),
                kickoff_txhandler.get_spendable_output(challenge_ack_vout)?,
                SpendPath::ScriptSpend(1),
                Sequence::from_height(paramset.watchtower_challenge_timeout_timelock),
            )
            .add_output(UnspentTxOut::from_partial(
                builder::transaction::anchor_output(paramset.anchor_amount()),
            ))
            .finalize(),
    )
}

    pub async fn check_general_requirements(&self) -> Result<(), BridgeError> {
        // check genesis state hash
        let rpc = ExtendedBitcoinRpc::connect(
            self.bitcoin_rpc_url.clone(),
            self.bitcoin_rpc_user.clone(),
            self.bitcoin_rpc_password.clone(),
            None,
        )
        .await
        .wrap_err("Failed to connect to Bitcoin RPC while checking general requirements")?;

        let genesis_chain_state = HeaderChainProver::get_chain_state_from_height(
            &rpc,
            self.protocol_paramset().genesis_height.into(),
            self.protocol_paramset().network,
        )
        .await
        .wrap_err("Failed to get genesis chain state while checking general requirements")?;

        let mut reasons = Vec::new();

        if genesis_chain_state.to_hash() != self.protocol_paramset().genesis_chain_state_hash {
            reasons.push(format!(
                "Genesis chain state hash mismatch, state hash generated from Bitcoin RPC ({}) does not match value in config ({})",
                hex::encode(genesis_chain_state.to_hash()),
                hex::encode(self.protocol_paramset().genesis_chain_state_hash)
            ));
        }

        if self.protocol_paramset().start_height < self.protocol_paramset().genesis_height {
            reasons.push(format!(
                "Start height is less than genesis height: {} < {}",
                self.protocol_paramset().start_height,
                self.protocol_paramset().genesis_height
            ));
        }

        if self.protocol_paramset().finality_depth < 1 {
            reasons.push(format!(
                "Finality depth ({}) cannot be less than 1",
                self.protocol_paramset().finality_depth
            ));
        }

        if !reasons.is_empty() {
            return Err(BridgeError::ConfigError(format!(
                "Invalid configuration due to: {}",
                reasons.join(" - ")
            )));
        }

        Ok(())
    }
