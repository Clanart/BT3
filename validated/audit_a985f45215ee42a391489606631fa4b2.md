### Title
`mWOMSVBaseRewarder._calExpireForfeit` never forfeits rewards for unlocking mWomSV holders, letting cooling-down/early-exiting stakers keep 100% of boosted rewards meant to be redistributed to loyal lockers - (File: `rewards/mWOMSVBaseRewarder.sol`)

### Summary
`mWOMSVBaseRewarder` is the reward pool paired with `mWomSV` (mWOM Stability Vault), and it mirrors `vlMGPBaseRewarder`'s "expire forfeit" mechanism, which is meant to claw back a portion of rewards from users who have entered/finished their cool-down (i.e., are exiting their lock) so that the forfeited amount is redistributed to users who remain fully locked. In `vlMGPBaseRewarder`, this is computed from `vlMGP.getRewardablePercentWAD(_account)` [1](#0-0) . `mWomSV` itself implements the exact same `getRewardablePercentWAD` function used for this purpose [2](#0-1) , but `mWOMSVBaseRewarder._calExpireForfeit` never calls it - it hardcodes `rewardableAmount = _amount`, so `forfeitAmount` is always `0` regardless of the account's lock/cool-down state [3](#0-2) .

### Finding Description
This bug class is analogous to the report's core theme: a threshold/rounding value that is supposed to gate an economic penalty is effectively fixed at (or collapses to) zero, letting ordinary users bypass the penalty and extract value that should be shared with other participants. In the original report, `minDebt`/`minBorrow` being low lets a borrower avoid providing meaningful collateral because the computed collateral requirement rounds to zero. Here, the "rewardable percent" computation - the analog of the collateral/penalty computation - is dead code, so it always evaluates as if the account is 100% "rewardable" (i.e., 0% forfeited), even when the account has actually started or completed unlocking (`getUserAmountInCoolDown` > 0): [3](#0-2) 

Compare to the correctly implemented sibling in `vlMGPBaseRewarder`, which uses the locker's live percentage: [1](#0-0) 

Any unprivileged holder of `mWomSV` can call `startUnlock` to move part of their balance into cool-down (this still counts in `balanceOf`/reward accrual per `wombat/mWomSV.sol` lines 101-132) [4](#0-3) , then claim/harvest their accrued `mWOMSVBaseRewarder` rewards via `MasterMagpie`. Because `_calExpireForfeit` never reduces the payable amount, `_sendReward` always pays out `userRewards[_rewardToken][_account]` in full, and the "forfeit re-queue" path (`_queueNewRewardsWithoutTransfer`) is unreachable dead code for this pool: [5](#0-4) 

### Impact Explanation
The forfeit mechanism exists to align incentives: users who are exiting their `mWomSV` lock (and thus withdrawing governance/voting power backing the protocol's Wombat yield) are supposed to give up part of their reward share back to users who remain committed. Because the forfeit calculation is broken (always zero), every mWomSV holder can unlock/cool-down and still harvest full, undiminished rewards from `mWOMSVBaseRewarder`, permanently diverting yield that should accrue to long-term lockers. This is a direct theft/misallocation of unclaimed yield away from loyal stakers to any account that starts unlocking, since the code path that would return that yield to the shared pool (`_queueNewRewardsWithoutTransfer`) is never executed.

### Likelihood Explanation
High likelihood: this requires no special conditions - any `mWomSV` holder can trigger it via the normal `startUnlock` → harvest/claim flow, which are unprivileged, permissionless actions available to every user of the protocol.

### Proof of Concept
1. User locks `mWOM` via `mWomSV.lock()`, accrues `mWOMSVBaseRewarder` rewards over time while `getRewardablePercentWAD` would normally be 100% (fully locked).
2. User calls `mWomSV.startUnlock(amount)` to move part/all of their stake into cool-down; per `getRewardablePercentWAD`, their rewardable percent should now be reduced proportionally to the time remaining in cool-down [2](#0-1) .
3. User calls the standard harvest/claim path leading into `mWOMSVBaseRewarder._sendReward` → `_calExpireForfeit`. Because `_calExpireForfeit` ignores the account's actual cool-down state and simply sets `rewardableAmount = _amount`, `forfeitAmount` is always `0` [3](#0-2) .
4. User receives 100% of `userRewards[_rewardToken][_account]` despite being in (or having exited) cool-down, and no amount is ever re-queued to `rewardInfo.rewardPerTokenStored` for the benefit of still-locked holders.

Note: I could not find/verify a corresponding unit test or deployment config confirming this was intentionally left unimplemented versus a copy-paste omission from `vlMGPBaseRewarder`; the side-by-side comparison of both `_calExpireForfeit` implementations and the fact that `mWomSV` already exposes the needed `getRewardablePercentWAD` function are the direct evidence for the root cause.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
