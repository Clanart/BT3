### Title
`SignableTransaction::new` computes weight/fee on a transaction missing the OP_RETURN data output, understating the real fee rate and bypassing the standardness weight check - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the external report — where a value is recomputed from a source that does not reflect a mutation, so the derived state no longer matches reality — `SignableTransaction::new` derives `weight`, `vbytes`, and hence `needed_fee` from a synthetic transaction built **only from `payments`**, even though the final transaction additionally carries an `OP_RETURN` data output that was never included in the weight calculation. The committed transaction is therefore heavier and more expensive (in vbytes) than the values `needed_fee`, `fee()`, and the `MAX_STANDARD_TX_WEIGHT` gate were computed against, so the "settled" fee/standardness verdict silently reverts to a stale, incorrect one once the data output is appended.

### Finding Description
In `SignableTransaction::new`, the data output is pushed to `tx_outs` first:

```rust
// networks/bitcoin/src/wallet/send.rs:194-202
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data)
        .expect("data didn't fit into PushBytes depsite being checked"),
    ),
  })
}
```

but the weight/vbytes used for the fee and for the standardness check are computed from a transaction whose outputs are only `payments` (and optionally `change`):

```rust
// networks/bitcoin/src/wallet/send.rs:204
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` builds its scratch `Transaction` exclusively from `payments` (lines 85–98). The same omission occurs in the change path (line 226), where `payments` — not `tx_outs` — is passed again. The final `MAX_STANDARD_TX_WEIGHT` check (line 241) uses this `weight`, which excludes the OP_RETURN output (up to 80 bytes of data plus ~3 bytes of script/value overhead, i.e. up to ~90+ vbytes) even though the real `self.tx` contains it.

Consequences, both driven by the same stale-derivation flaw:

1. `needed_fee = fee_per_vbyte * vbytes` is computed on a smaller `vbytes` than the actual transaction, so `fee()` (which returns the true `sum(inputs) - sum(outputs)`) corresponds to a real fee rate strictly below the `fee_per_vbyte` the caller specified, whenever `data` is present.
2. A transaction whose true weight exceeds `MAX_STANDARD_TX_WEIGHT` but whose payments-only weight does not will pass the `TooLargeTransaction` check, be signed by `TransactionMachine`, and then fail mempool relay — a non-standard, unbroadcastable transaction whose input outpoints have been consumed by the signing flow.

### Impact Explanation
The processor produces a signed Bitcoin transaction that either pays materially less than the requested fee rate (transaction may stall indefinitely in the mempool or never confirm, locking the spent UTXOs in limbo) or is outright unbroadcastable for exceeding the standard weight limit (funds committed to inputs that must be re-assembled in a new transaction). An unprivileged depositor/user whose withdrawal request carries a `data` payload — or who induces a send near the weight boundary — reaches this purely through the public `data`/`payments` inputs to `SignableTransaction::new`. No malicious validator, leaked key, or integrator misuse of documented requirements is involved; the defect is internal to the fee/weight derivation.

### Likelihood Explanation
Any call to `SignableTransaction::new` with `Some(data)` triggers the miscalculation; the data path is explicitly supported (with an 80-byte bound), not an edge input. The fee understatement is deterministic whenever data is present. The standardness bypass requires the payments-only weight to sit within ~90 vbytes of `MAX_STANDARD_TX_WEIGHT`, which is less common but not attacker-improbable since input/output counts are user-influenced.

### Recommendation
Compute the scratch transaction for `calculate_weight_vbytes` from the actual output list (`tx_outs`, including the OP_RETURN output) rather than `payments`. Concretely, either build the weight-estimation transaction by cloning `tx_outs` (with a zero-value placeholder for change before its amount is known) or add an explicit `data_output_len`/`op_return` parameter so the serialized OP_RETURN output contributes to `weight`. Re-derive `weight`, `vbytes`, `needed_fee`, and the `MAX_STANDARD_TX_WEIGHT` check from the true output set in both the change and non-change paths.

### Proof of Concept
1. Construct `SignableTransaction::new(inputs, payments, None, Some(vec![0u8; 80]), fee_per_vbyte)` where `inputs` covers `payment_sat + fee_per_vbyte * vbytes_payments_only`.
2. The function returns `Ok(stx)` with `needed_fee = fee_per_vbyte * vbytes(payments_only)`, but `stx.transaction().output` contains an additional ~90-byte OP_RETURN output, so `stx.fee() / actual_vbytes < fee_per_vbyte`.
3. Alternatively, choose inputs/payments so `weight(payments) <= MAX_STANDARD_TX_WEIGHT < weight(payments + op_return)`: `new` returns `Ok`, `multisig`/`preprocess`/`sign`/`complete` produce a fully signed `Transaction` that every Bitcoin node rejects as non-standard, leaving the consumed outpoints unspendable via this transaction.
