## Title
Missing scheme validation in `open-external` IPC handler allows arbitrary local file / custom protocol handler launch via `shell.openExternal` — (File: `app/src/main-process/main.ts`)

### Summary
The main-process IPC handler for `open-external` performs a URL-scheme check only to decide whether to write a log line, but it unconditionally forwards the caller-supplied `path` string to `shell.openExternal()` regardless of the result of that check.

### Finding Description
The handler is: [1](#0-0) 

```
ipcMain.handle('open-external', async (_, path: string) => {
  const pathLowerCase = path.toLowerCase()
  if (
    pathLowerCase.startsWith('http://') ||
    pathLowerCase.startsWith('https://')
  ) {
    log.info(`opening in browser: ${path}`)
  }

  try {
    await shell.openExternal(path)
    return true
  } catch (e) {
    log.error(`Call to openExternal failed: '${e}'`)
    return false
  }
})
```

The `if` block only gates the `log.info` call — there is no `return`/`reject` for non-`http(s)` values, so `shell.openExternal(path)` executes for **any** string the renderer sends, including `file://…`, `\\server\share\payload.exe` (Windows UNC), or arbitrary custom protocol URIs (e.g. `steam://`, `ms-word://`, etc.). Electron's `shell.openExternal` will happily hand such values off to the OS shell, which can launch local executables, mounted network shares, or any registered protocol handler.

On the renderer side, this IPC call is exposed generically as `openExternal` and is invoked from many UI code paths whenever a user clicks a link rendered from remote/repository content, for example: [2](#0-1) 

```
private onClick = (event: React.MouseEvent<HTMLAnchorElement>) => {
  event.preventDefault()
  ...
  const uri = this.props.uri
  if (uri) {
    shell.openExternal(uri)
  }
  ...
}
```

`shell` here is the app-shell wrapper that proxies straight to the main-process handler: [3](#0-2) 

Neither `LinkButton` nor `app-shell.ts`'s `openExternal` perform any scheme allow-listing before invoking the IPC call, so protection (if any) is expected to live in the main-process handler — but that handler, as shown above, does not actually reject anything.

Regarding the specific proof-idea mentioned in the question (`IssueLinkFilter`): I confirmed that `IssueLinkFilter` (`app/src/lib/markdown-filters/issue-link-filter.ts`) only rewrites the *text content* of an anchor to a normalized `#123` reference — it never touches `href`, and it only matches links whose `href` already resolves to the configured GitHub endpoint's issue/pull/discussion URL pattern [4](#0-3) . So this particular filter is not itself the source of a malicious non-http `href`. However, it does not sanitize or constrain `href` values produced by the broader markdown pipeline for other kinds of links (plain markdown links, autolinks, etc.), and I was not able to fully trace, within the tool budget available, whether a separate sanitizer elsewhere strips `file://`/custom-scheme `href`s before they reach a clickable `<a>`/`LinkButton` element. What is verifiable from the code inspected is that **the last line of defense — the main-process `open-external` handler — does not enforce any scheme restriction**, so if any upstream rendering path (markdown link rendering, PR/issue descriptions, commit messages, etc.) allows a non-`http(s)` `href` through to a clickable element wired to `shell.openExternal`, the request will not be blocked before reaching `shell.openExternal`.

### Impact Explanation
If a non-http(s) URI reaches this call path (e.g., from a link in an issue body, PR description, or commit message authored by an attacker-controlled repository/API object), `shell.openExternal` can be used to open local files (`file://` — potentially triggering OS-level auto-execution of certain file types), UNC paths on Windows (`\\attacker-server\share\evil.exe`, which can also leak NTLM credentials via SMB), or arbitrary custom URI-scheme handlers registered on the victim's machine — some of which are known to lead to remote code execution (a well-documented class of Electron `shell.openExternal` vulnerabilities).

### Likelihood Explanation
The likelihood depends entirely on whether any UI/markdown-rendering path in Desktop allows a non-`http(s)` `href` from untrusted repository/API content to reach a clickable element wired to `openExternal`. The `IssueLinkFilter` itself does not introduce this because it constrains matches to the repository's known GitHub host and only alters anchor text, not `href`. I could not conclusively verify, within the available search budget, that some *other* rendering path (e.g., generic markdown link rendering for arbitrary hrefs in issue/PR bodies) fails to sanitize schemes before producing a clickable link element — this is the key unresolved uncertainty.

### Recommendation
Regardless of the upstream reachability question, the `open-external` handler in `app/src/main-process/main.ts` should be hardened to defense-in-depth: explicitly reject (return `false`, or throw) for any `path` that does not start with `http://` or `https://` (or an explicit allow-list of additional safe schemes such as `mailto:`), instead of only gating a log statement on that check.

### Proof of Concept
Not fully constructible with certainty from static review alone: while it's trivial to show that `ipcMain.handle('open-external', ...)` does not reject a `file://` or UNC string (the `if` block only controls logging, and `shell.openExternal(path)` executes unconditionally per lines 581–597 of `main.ts`), I was unable to fully confirm within this investigation which specific renderer-side markdown/link-rendering code path would let an attacker-controlled repository issue/PR body produce a clickable `<a href="file://...">` (as opposed to plain text) that a user could click to trigger this call chain — `IssueLinkFilter` itself does not create such hrefs. This should be confirmed with a live reproduction: render an issue/PR/commit description containing a raw `file://…` or `\\host\share\payload` markdown link, inspect whether it becomes a clickable `LinkButton`/anchor element in the UI, click it, and observe whether `shell.openExternal` is invoked with the unsanitized value.
