### Title
Agent-controlled hookify safety rules can be self-disabled via Edit/Write before the guarded action runs, letting the restricted actor bypass its own block/warn checks - ([File: plugins/hookify/core/config_loader.py])

### Summary
The reported AbranaFT bug lets the *lender* — the same party whose loan terms are meant to be enforced against — call `updateLoanParams()` to zero out `ltvBPS` and then immediately call `removeCollateral()`, defeating the collateral-seizure guard because the guard trusts a parameter the lender itself controls at will. The `hookify` plugin in this repo has the same trust-boundary flaw: the entity that a `PreToolUse` safety rule is meant to restrict (the model/agent operating the `Edit`/`Write` tools) is also the entity that can rewrite the rule's `enabled`/`action` frontmatter, and the rule engine re-reads that file fresh on every tool call with no restart and no integrity check.

### Finding Description
Hookify rules live in `.claude/hookify.*.local.md` files and are loaded fresh on every tool invocation by `load_rules()`, which only includes a rule if `rule.enabled` is `True` at read time: [1](#0-0) . There is no distinction between a "protected"/immutable rule store and the workspace files the agent is normally allowed to edit — `.claude/hookify.*.local.md` are ordinary project files.

Documentation for the plugin explicitly describes this self-service, immediate-effect toggle mechanism: `enabled: true` → `enabled: false` disables a rule "immediately... no restart needed", and the plugin's own `configure` command performs this Edit for the user: [2](#0-1)  and [3](#0-2) . The `hookify.md` skill likewise tells the agent that "Rules take effect immediately on the next tool use" and that changing `action: block` to `action: warn` is an accepted way to relax an over-strict rule "on next tool use": [4](#0-3) .

Because the model (Claude) itself decides when and how to invoke `Edit`/`Write`, and hookify rules are just markdown files with no separate ACL, the same agent whose dangerous action (`rm -rf`, editing `.env`, etc.) a rule is meant to block can:
1. Use `Edit` to flip the guarding rule's frontmatter from `enabled: true`/`action: block` to `enabled: false` or `action: warn`.
2. Immediately issue the previously-blocked `Bash`/`Edit`/`Write` call.
3. Because `load_rules()` re-reads the directory on every `PreToolUse` invocation (no caching across calls, no re-validation against a trusted baseline), the now-disabled/weakened rule no longer matches, and `RuleEngine.evaluate_rules()` returns `{}` (allow) or only a warning instead of `permissionDecision: "deny"`: [5](#0-4) .

This mirrors the loan-parameter bug precisely: a single-party-controlled configuration value (`ltvBPS` / `enabled`+`action`) that a security check relies on can be updated by the very party the check is supposed to constrain, with no cooldown, second signer, or immutability window between the parameter change and the exploitation of the resulting gap.

Additionally, the hook's own failure handling defaults to permissive: any exception in `pretooluse.py` (e.g., a parse error induced by malformed frontmatter) results in `sys.exit(0)` and an "allow" response, reinforcing that this control is fail-open by design: [6](#0-5) .

### Impact Explanation
Hookify is explicitly marketed and used as a lightweight safety-rail plugin — e.g., blocking `rm -rf`, blocking edits to `.env`/`.git`, or requiring tests before stop — and its own documentation frames these as protections against "unwanted behaviors" from the agent. If the guarded party (the agent, potentially acting on attacker-influenced instructions such as prompt injection from fetched content) can silently edit the rule file to disable or downgrade the very rule about to be triggered, and that change takes effect on the next tool call with no re-approval or notification distinct from a normal file edit, the safety control provides no real assurance once an adversarial instruction reaches the model. This is a local, project-scoped bypass of a supplementary safety layer — not a bypass of Claude Code's core, non-plugin permission system (`permissions.deny`, sandbox, etc.), but it does allow unauthorized destructive/exfiltration actions that the user configured hookify specifically to prevent.

### Likelihood Explanation
Likelihood is moderate-to-high in any project that relies on hookify for guardrails against agent misbehavior: it requires no special privilege beyond the `Edit`/`Write` tool access the agent already has, no additional user approval step is described for editing `.local.md` files versus any other file, and the plugin's own docs actively teach the agent this exact workflow (edit frontmatter → verify no restart needed → trigger the rule). An attacker who can influence the agent's instructions (e.g., via a malicious file/webpage the agent reads) could direct it to disable a rule immediately before performing the disallowed action.

### Recommendation
- Do not let `PreToolUse`/`Stop` rule enforcement trust the same on-disk rule state that the guarded tool call (`Edit`/`Write`) can modify in the same turn; snapshot/cache the active rule set at session start (or require an explicit re-approval step) rather than re-reading `.claude/hookify.*.local.md` fresh on every tool invocation.
- Treat edits to `hookify.*.local.md` (and any other file that defines active safety/permission rules) as security-sensitive: require the same or a stronger confirmation path used for changes to `settings.json`/`permissions.deny`, and consider blocking the agent from silently disabling a rule immediately before it would be triggered (e.g., detect "disable rule for pattern X" followed within the same turn or few tool calls by an action matching pattern X, and treat this as a stop/ask event).
- Make failure handling in `pretooluse.py` configurable to fail-closed for `block`-type rules rather than always exiting 0/allow on any parsing exception.

### Proof of Concept
1. Create `.claude/hookify.dangerous-rm.local.md` with `enabled: true`, `event: bash`, `action: block`, `pattern: rm\s+-rf` (as shown in the plugin's own examples): [7](#0-6) .
2. Ask/instruct the agent (directly or via injected content) to run `rm -rf /important/dir` — the `PreToolUse` hook blocks it via `permissionDecision: "deny"` per `RuleEngine.evaluate_rules()`: [8](#0-7) .
3. Instruct the agent to use `Edit` on `.claude/hookify.dangerous-rm.local.md` to change `enabled: true` to `enabled: false` (a documented, expected operation): [9](#0-8) .
4. Immediately re-issue `rm -rf /important/dir`. Because `load_rules()` re-globs and re-parses the directory on this new invocation and the rule is now `enabled: False`, it is excluded from `rules` and `RuleEngine.evaluate_rules()` returns `{}`, allowing the previously blocked destructive command to execute: [10](#0-9) .

Note: I was unable to find any Claude-Code-core (non-plugin) permission-engine code that has this exact same self-modifiable-check pattern in the indexed portion of the codebase; the strongest concrete analog found is in the bundled `hookify` plugin. If a more central, non-plugin instance of this pattern exists elsewhere in the codebase, it was not surfaced by the available search index.

```python
def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)
```

```python
    def evaluate_rules(self, rules: List[Rule], input_data: Dict[str, Any]) -> Dict[str, Any]:
        """Evaluate all rules and return combined results.

        Checks all rules and accumulates matches. Blocking rules take priority
        over warning rules. All matching rule messages are combined.

        Args:
            rules: List of Rule objects to evaluate
            input_data: Hook input JSON (tool_name, tool_input, etc.)

        Returns:
            Response dict with systemMessage, hookSpecificOutput, etc.
            Empty dict {} if no rules match.
        """
        hook_event = input_data.get('hook_event_name', '')
        blocking_rules = []
        warning_rules = []

        for rule in rules:
            if self._rule_matches(rule, input_data):
                if rule.action == 'block':
                    blocking_rules.append(rule)
                else:
                    warning_rules.append(rule)

        # If any blocking rules matched, block the operation
        if blocking_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in blocking_rules]
            combined_message = "\n\n".join(messages)

            # Use appropriate blocking format based on event type
            if hook_event == 'Stop':
                return {
                    "decision": "block",
                    "reason": combined_message,
                    "systemMessage": combined_message
                }
            elif hook_event in ['PreToolUse', 'PostToolUse']:
                return {
                    "hookSpecificOutput": {
                        "hookEventName": hook_event,
                        "permissionDecision": "deny"
                    },
                    "systemMessage": combined_message
                }
            else:
                # For other events, just show message
                return {
                    "systemMessage": combined_message
                }

        # If only warnings, show them but allow operation
        if warning_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in warning_rules]
            return {
                "systemMessage": "\n\n".join(messages)
            }

        # No matches - allow operation
        return {}
```
