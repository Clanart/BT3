### Title
Unprivileged callers can force-lock any WOM sitting in `WombatStaking` into veWOM via `convertWOM`, permanently freezing protocol WOM with no mWOM issued - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking.convertWOM(uint256 _amount)` is `external` and gated only by `whenNotPaused`, with no `onlyMWom`, `onlyPoolHelper`, or `onlyOwner` restriction. Any unprivileged EOA can call it directly with any amount up to the contract's current WOM balance, forcing WOM held by the contract (including protocol-owned dust/fee remnants) into a 1461-day veWOM lock without any corresponding mWOM being minted to a receipt holder.

### Finding Description
`convertWOM` is defined as: [1](#0-0) 
It takes `_amount` from the caller's input, approves and calls `IVeWom(veWom).mint(_amount, lockDays)` directly against the contract's own WOM balance, with `lockDays = 1461` set in the initializer: [2](#0-1) 

The only modifier present is `whenNotPaused`; there is no caller-restriction such as `_onlyPoolHelper` or a dedicated mWOM-only modifier, unlike `deposit`, `withdraw`, and `burnReceiptToken` which use `_onlyPoolHelper`/`_onlyActivePoolHelper`: [3](#0-2) [4](#0-3) 

Minting of mWOM as a receipt only happens in `mWOM._convert`/`_lockWom`, which is the intended, privileged/expected caller path into `convertWOM`: [5](#0-4) 
Because `convertWOM` itself has no caller restriction, an attacker can bypass `mWOM` entirely and call `WombatStaking.convertWOM(_amount)` directly for any WOM balance already resident in the `WombatStaking` contract (e.g., transient/dust WOM from reward or fee routing during `_toMasterWomAndSendReward`/harvest flows), locking it into veWOM for 1461 days with `lockDays` non-configurable per call. No mWOM is minted in this path since `convertWOM` does not call `_mint`; only `mWOM._convert` does that, and the attacker's direct call skips it.

### Impact Explanation
This causes real, permanent freezing of protocol-owned WOM for far more than 24 hours (1461 days lock), with no receipt token (mWOM) issued to anyone to represent a claim on the resulting veWOM. This matches the "permanent freezing of funds" / "protocol insolvency" Immunefi impact class, since the WOM becomes economically inaccessible (locked as veWOM under `WombatStaking`) while backing accounting (`totalConverted`/`totalAccumulated` tracked only in `mWOM`) is never updated, desynchronizing mWOM's asset backing from actual locked veWOM.

### Likelihood Explanation
Feasibility depends entirely on whether exploitable WOM balances (dust) can accumulate in `WombatStaking` outside of an active `mWOM._convert`/`lockAllWom` call — this requires confirming that `_toMasterWomAndSendReward`/harvest fee routing paths for pool operations leave residual WOM balance in the contract between transactions. I was not able to fully verify, within the available tool budget, the exact mechanics of `_toMasterWomAndSendReward` and whether it can leave non-zero WOM dust standing in `WombatStaking` at rest (this function's body was not retrieved). If such dust reliably exists (even small amounts from reward-fee routing), the attack is trivially and repeatably callable by anyone with zero capital cost beyond gas, since `convertWOM` requires no token transfer from the caller — it only consumes the contract's own balance.

### Recommendation
Restrict `convertWOM` (and `convertAllWom`) to only be callable by `mWOM` (or another explicitly authorized contract), e.g. add a modifier such as `onlyMWom` checking `msg.sender == mWom`, consistent with the access-control pattern already used for `deposit`/`withdraw`/`burnReceiptToken` via `_onlyPoolHelper`.

### Proof of Concept
Hardhat test plan:
1. Deploy `WombatStaking`, mock `veWom` (implementing `mint(amount, lockDays)` returning veWom amount and crediting `WombatStaking`), and WOM ERC20 mock.
2. Seed `WombatStaking` with a small WOM balance (simulate dust, e.g. via direct `wom.transfer(wombatStaking.address, dustAmount)`).
3. From an unprivileged EOA (not `mWOM`, not owner, not pool helper), call `wombatStaking.convertWOM(dustAmount)`.
4. Assert: (a) call succeeds without revert; (b) `veWom.balanceOf(wombatStaking.address)` increased by the expected minted veWom amount; (c) `mWOM.balanceOf(attacker)` and `mWOM.totalSupply()` remain unchanged (no receipt minted); (d) `wombatStaking`'s WOM balance decreased by `dustAmount` with no corresponding accounting update in `mWOM.totalConverted`/`totalAccumulated`.

    function convertWOM(uint256 _amount) whenNotPaused external returns(uint256) {
        uint256 veWomMintedAmount = 0;
        if (_amount > 0) {
            IERC20(wom).safeApprove(veWom, _amount);
            veWomMintedAmount = IVeWom(veWom).mint(_amount, lockDays);
        }

        emit WomLocked(_amount, lockDays, veWomMintedAmount);

        return veWomMintedAmount;
    }
