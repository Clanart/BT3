### Title
Stale/incorrect SSH credential persists silently because `mostRecentSSHCredentials` only tracks the last of multiple prompts within a single git operation - ([File: app/src/lib/ssh/ssh-credential-storage.ts])

### Summary
The reported Solidity bug is that `commitToMint` consumes `msg.value` on every call, but `batchCommitToMint` reuses the *same* value across loop iterations, so only the first iteration's use of the shared, single-use resource is valid — subsequent iterations silently misuse stale/incorrect state. The same broken invariant — "a value meant to track exactly one in-flight authentication attempt is instead shared/overwritten across multiple attempts that occur within the same logical operation" — exists in Desktop's SSH askpass credential bookkeeping.

### Finding Description
`withTrampolineEnv` allocates exactly one `trampolineToken` (`operationGUID`) for an entire git invocation, no matter how many separate authentication prompts occur during that single git process: [1](#0-0) 

A single git command such as `fetch --recurse-submodules` (used by Desktop when fetching a repository that references submodules) can, in one process, need to authenticate against multiple distinct remotes/hosts, each potentially prompting for a different SSH key passphrase via `GIT_ASKPASS`: [2](#0-1) 

Every time `handleSSHKeyPassphrase` (or the analogous password handler) is invoked — once per key/host the attacker-controlled repository's `.gitmodules` references — it calls `setSSHKeyPassphrase`/`setMostRecentSSHKeyPassphrase` keyed only by the shared `operationGUID`: [3](#0-2) 

That in turn calls `setMostRecentSSHCredential`, which stores the tracking entry in a `Map<string, SSHCredentialEntry>` keyed by `operationGUID` — i.e. **one slot per whole git operation, not one slot per credential prompt**: [4](#0-3) 

Each subsequent prompt (for a second/third submodule remote) calls `.set(operationGUID, {store, key})` again, silently overwriting the entry for the first credential — exactly like reusing `msg.value` on each loop iteration instead of tracking it per-iteration. When the overall git operation ultimately fails with an SSH authentication error, `withTrampolineEnv`'s cleanup path calls `deleteMostRecentSSHCredential(token)` exactly once: [5](#0-4) 

Because the map holds only the *last* `{store, key}` pair for that `operationGUID`, only the last-entered credential is ever rolled back from the OS keychain (`TokenStore`). Any credential(s) stored for earlier submodules/hosts processed earlier in the same operation are never deleted, even though the git operation as a whole failed and even if the earlier credential was entered incorrectly or was intended to be rejected. The docstring in `handleSSHKeyPassphrase` explicitly acknowledges the retry scenario ("it's possible that the user will need to enter the passphrase multiple times") but the fix implemented only guards the "user declines to remember" case, not the "multiple different keys prompted within the same operation" case, because the underlying data structure has no way to represent more than one pending credential per operation.

### Impact Explanation
An attacker who controls a cloned/fetched repository's `.gitmodules` (a fully attacker-controlled artifact fetched over the network) can define several submodules pointing at different SSH hosts/keys. During a single `fetch --recurse-submodules`, the user may be prompted multiple times for different SSH key passphrases within the *same* trampoline token/operation. If the operation ultimately fails, Desktop's cleanup path silently forgets to purge earlier stored credentials, leaving stale or user-mistyped SSH key passphrases persisted in the OS credential store (keychain/Credential Manager/libsecret) indefinitely. This is a silent corruption of the credential store driven entirely by an untrusted repository's submodule configuration, without any social engineering or local access — it only requires the victim to fetch/clone a hostile repo with submodules and interact with the normal (legitimate-looking) SSH passphrase prompts.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an attacker-controlled repo with multiple submodules referencing distinct SSH-authenticated remotes, (b) the user having SSH keys configured for more than one of those hosts so multiple distinct askpass prompts fire within one `fetch --recurse-submodules` invocation, and (c) the overall operation subsequently failing (e.g., one of the submodule fetches fails). These conditions are all reachable purely through normal Desktop usage (clone/fetch a repo with submodules) — no privileged access or pre-existing compromise is required — but they do depend on specific SSH key configuration on the victim's machine, reducing but not eliminating exploitability.

### Recommendation
Track pending SSH credentials per prompt (e.g., keyed by `(operationGUID, store, key)` in a `Set`/array) rather than overwriting a single `Map<operationGUID, entry>` slot. On operation failure, iterate and delete **all** pending entries associated with that `operationGUID`, not just the most recently set one — mirroring the fix needed for `batchCommitToMint`, where the resource-consuming call must be adjusted to account for each iteration individually rather than assuming a single shared value suffices for the whole batch.

### Proof of Concept
1. Attacker publishes a repository with a `.gitmodules` file containing two submodules, each with an `ssh://` URL pointing to a different host, each requiring a different local SSH key (`keyA`, `keyB`) that has never been used with Desktop before.
2. Victim (who has both `keyA` and `keyB` configured with passphrases) clones the attacker's repo in Desktop, which runs `git fetch --recurse-submodules` under one `withTrampolineEnv`/`trampolineToken` call: [2](#0-1) 
3. Desktop prompts for `keyA`'s passphrase; victim enters it and checks "Remember passphrase" → `setSSHKeyPassphrase(token, keyA, passphrase)` stores it in `TokenStore` and sets `mostRecentSSHCredentials.set(token, {store, keyA})`.
4. Desktop then prompts for `keyB`'s passphrase (second submodule); victim enters an incorrect passphrase but still checks "Remember" → `mostRecentSSHCredentials.set(token, {store, keyB})` overwrites the previous entry, and the (wrong) `keyB` passphrase is written to `TokenStore`.
5. The submodule fetch for `keyB`'s host fails SSH authentication, causing the whole `fetch` to throw an `SSHAuthenticationFailed`-classified error, triggering `deleteMostRecentSSHCredential(token)` in `withTrampolineEnv`'s catch block: [5](#0-4) 
6. Only `keyB`'s bad passphrase entry is deleted from `TokenStore`; the entry for `keyA` (set earlier in the same operation) is never revisited or validated, and remains persisted regardless of whether the operation ultimately succeeded — illustrating that only the "most recent" of several credentials handled within one operation is ever tracked/cleaned up, an exact structural analog of using a single `msg.value` across multiple loop iterations.

/**
 * Stores an SSH credential and also keeps it in memory to be deleted later if
 * the ongoing git operation fails to authenticate.
 *
 * @param operationGUID A unique identifier for the ongoing git operation. In
 *                      practice, it will always be the trampoline token for the
 *                      ongoing git operation.
 * @param store         Store where the SSH credential is stored.
 * @param key           Key that identifies the SSH credential (e.g. username or
 *                      key hash).
 * @param password      Password for the SSH key / user.
 */
export async function setSSHCredential(
  operationGUID: string,
  store: string,
  key: string,
  password: string
) {
  setMostRecentSSHCredential(operationGUID, store, key)
  await TokenStore.setItem(store, key, password)
}

/**
 * Keeps the SSH credential details in memory to be deleted later if the ongoing
 * git operation fails to authenticate.
 *
 * @param operationGUID A unique identifier for the ongoing git operation. In
 *                      practice, it will always be the trampoline token for the
 *                      ongoing git operation.
 * @param store         Store where the SSH credential is stored.
 * @param key           Key that identifies the SSH credential (e.g. username or
 *                      key hash).
 */
export function setMostRecentSSHCredential(
  operationGUID: string,
  store: string,
  key: string
) {
  mostRecentSSHCredentials.set(operationGUID, { store, key })
}
