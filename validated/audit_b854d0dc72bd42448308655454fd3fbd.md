### Title
Missing zero-check on governance-settable `Kip71GasTarget` causes division-by-zero panic in `NextMagmaBlockBaseFee` - (File: params/kip71_config.go)

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by `gasTarget` when the parent block's gas usage differs from the gas target, but the `GasTarget` governance parameter has no non-zero format check (unlike the sibling `BaseFeeDenominator` parameter, which is explicitly checked). If `GasTarget` is ever set/interpreted as `0`, every subsequent block header validation and base-fee computation will divide by zero and panic, mirroring the Blend "division before checking a governance/oracle-controlled denominator" bug class.

### Finding Description
`params/kip71_config.go` computes the next block's base fee: [1](#0-0) 
and, symmetrically, in the decreasing-gas branch: [2](#0-1) 
Both branches call `new(big.Int).SetUint64(gasTarget)` as a divisor with no guard. Compare this to `BaseFeeDenominator`, which explicitly falls back to `64` when zero to avoid a panic: [3](#0-2) 
No equivalent fallback exists for `gasTarget := kc.GasTarget`.

Critically, the governance parameter registry validates `Kip71BaseFeeDenominator` with a non-zero `FormatChecker`: [4](#0-3) 
but `Kip71GasTarget` uses `noopFormatChecker`, performing no validation at all: [5](#0-4) 
This is the exact analog of the Blend finding: an important divisor-controlling configuration value (`oracle_scalar`/`oracle.decimals()` in Blend vs. `GasTarget` in Kaia) is accepted without a minimum-value check, while a related value in the same code path (`BaseFeeDenominator`) *is* checked, showing the omission is inconsistent and overlooked rather than intentional.

`NextMagmaBlockBaseFee` is invoked on every block during header validation/verification (`VerifyMagmaHeader`) and block assembly, so a zero `GasTarget` is not an edge-case auction/interest-auction failure (as in Blend) — it is a chain-halting panic reachable on the very next block after the parameter takes effect.

### Impact Explanation
If `GasTarget` is set to `0` via governance (single-governing-node vote or DAO-mode governance contract vote, per `kaiax/gov`), every node computing the next base fee — during block proposal, and during `ValidateHeader`/`VerifyMagmaHeader` for every full node syncing or validating — will panic with a division by zero. This is a chain-wide denial of service / consensus halt, categorically worse than the Blend low-severity/medium DoS on auctions, since it stops block production entirely rather than temporarily blocking a fallback auction path. It maps to the "acceptance of an invalid transaction or block" / "state divergence between honest nodes" impact categories, since a crashing node cannot validate or produce blocks, and any node that doesn't crash first could diverge in behavior depending on how the panic is recovered (if at all) at the call site.

### Likelihood Explanation
Likelihood depends entirely on whether the governance layer or genesis/chain-config loading permits `GasTarget = 0` to be persisted and later read by `NextMagmaBlockBaseFee`. The registry-level format check is confirmed absent (`noopFormatChecker`), which is a real gap compared to `BaseFeeDenominator`. However:
- I was not able to fully trace every layer (e.g., possible additional validation in genesis-loading code, `ChainConfig.SetDefaults()`, or vote-application code in `kaiax/gov/headergov` beyond the `FormatChecker`) within the tool budget, so I cannot rule out a secondary guard elsewhere that would prevent `0` from ever reaching `NextMagmaBlockBaseFee`.
- Setting `GasTarget` still requires governance-vote privileges (the governing node in single mode, or DAO voters in contract mode) rather than being reachable from a fully permissionless, single unprivileged transaction — this is a materially weaker likelihood than the Blend bug, where *any* address could permissionlessly deploy a malicious pool.

Given the explicit exclusion of "governance parameters" is not disqualified per the allowed-domain list, but the actor is privileged (governance voter, not an arbitrary sender), likelihood should be considered low-to-uncertain, though impact if triggered is severe.

### Recommendation
Add a non-zero `FormatChecker` for `Kip71GasTarget` (and ideally `MaxBlockGasUsedForBaseFee`) in `kaiax/gov/param.go`, mirroring the check already present for `Kip71BaseFeeDenominator`. Additionally, add a defensive fallback in `KIP71Config.NextMagmaBlockBaseFee` (similar to the `baseFeeDenominator` zero-fallback) so that a zero or otherwise degenerate `GasTarget` cannot cause a division-by-zero panic during block validation or assembly.

### Proof of Concept
1. Via governance (single mode governing node, or DAO-mode vote passing through `kaiax/gov/headergov`), submit a parameter update setting `governance.kip71.gastarget` (`Kip71GasTarget`) to `0`. Because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, this value passes validation and is written into the governance history / `ChainConfig.Governance.KIP71.GasTarget`. [5](#0-4) 
2. On the next block after the parameter activates, any block gas usage other than exactly `0` will not equal `gasTarget` (`0`), so execution enters either the "used more gas than target" or "used less gas than target" branch of `NextMagmaBlockBaseFee`. [6](#0-5) 
3. Both branches execute `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0`, which panics with a division-by-zero runtime error in Go's `big.Int.Div`.
4. Because this function is invoked both by block proposers computing the next base fee and by validators verifying `header.BaseFee` via `VerifyMagmaHeader`, all nodes on the network panic/crash when processing the first block after the bad parameter is active, halting the chain.
