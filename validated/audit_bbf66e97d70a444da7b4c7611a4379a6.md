### Title
Incomplete blacklist in `AGG_SIG_UNSAFE` domain-separation check allows signature replay across AGG_SIG opcodes - ([File: chia/consensus/condition_tools.py])

### Summary
`pkm_pairs_for_conditions_dict()` and the equivalent Rust-backed `pkm_pairs()` in `chia/consensus/condition_tools.py` guard `AGG_SIG_UNSAFE` messages by checking only that the message does not *end with* one of a small set of precomputed domain-separator suffixes (`agg_sig_additional_data()`), then unconditionally accepting the message and pairing it with the public key for BLS verification. [1](#0-0)  This mirrors the WildFly CVE-2016-0793 bug class: a security-relevant filter implemented as an incomplete blacklist of "known-bad" values rather than a complete/structural check, which is trivially bypassable by crafting an input that is functionally equivalent to a blocked value but does not match the blacklist's exact byte pattern.

### Finding Description
`AGG_SIG_UNSAFE` is intentionally not bound to a specific coin (unlike `AGG_SIG_ME`/`AGG_SIG_PARENT`/etc., whose final signed message is built via `make_aggsig_final_message()` by appending coin-derived addenda plus a domain separator, see lines 73-96). [2](#0-1)  Because `AGG_SIG_UNSAFE` messages are signed and verified as-is, a message crafted to *look like* the final message of some other AGG_SIG_* condition for a target coin could be replayed to authorize spends that were never intended, which is the classic BLS message-domain-separation attack this Chia mechanism exists to stop.

The mitigation in `pkm_pairs_for_conditions_dict()` is a denylist: it computes `agg_sig_additional_data(additional_data)` — a fixed dict of six `std_hash(agg_sig_data + opcode)` suffixes plus the raw `AGG_SIG_ME` additional data — and rejects an `AGG_SIG_UNSAFE` message only if it exactly `.endswith()` one of these six specific suffix values. [3](#0-2) [4](#0-3) 

This is an incomplete blacklist because:
- It only covers the network's *current* `AGG_SIG_ME_ADDITIONAL_DATA`-derived values on the *current* chain. Any message whose meaningful "coin-binding" bytes take a different but still coin-derivable form (e.g. combined with future opcodes, a different additional-data constant such as another fork/testnet's `AGG_SIG_ME_ADDITIONAL_DATA`, or values from a different genesis challenge) does not match any of the six precomputed suffixes and is not rejected, even though it may still be usable to construct/replay a colliding signed message on another context that shares the signing key.
- The check is a suffix string match (`.endswith()`), not a semantic/structural rejection of "any AGG_SIG_UNSAFE message that could double as a coin-bound signature." A byte-for-byte identical suffix crafted by an attacker off-chain (e.g., precomputed for a different `additional_data` value, a different height's soft-fork variant, or simply a message that legitimately needs to end in those exact bytes for an unrelated protocol reason) is blocked, but any semantically equivalent message that isn't a literal suffix match of one of exactly six fixed byte strings sails through the "safe" path and gets signed/verified without further restriction.

### Impact Explanation
If a wallet signs an `AGG_SIG_UNSAFE` message under attacker influence (e.g., an offer, DID recovery message, or third-party delegated puzzle that requests an `AGG_SIG_UNSAFE` signature over attacker-chosen bytes), and the blacklist fails to reject a value that is semantically equivalent to a coin-bound AGG_SIG message outside the six hardcoded suffixes, the resulting BLS signature over that message could be reused/replayed to authorize a different, unintended spend condition for a coin controlled by the same key — i.e., unsigned/unauthorized coin movement. This satisfies the "concrete unsigned or unauthorized coin movement" bar from the validation rules, since the entire security purpose of this check is to prevent exactly that class of signature reuse.

### Likelihood Explanation
Reachable purely from a single submitted spend bundle / offer / wallet-signing request: any counterparty who can get a victim's wallet to countersign an `AGG_SIG_UNSAFE` condition (a normal, permitted condition type used throughout offers, DID recovery, and custom puzzles) controls the message bytes subject only to this denylist. No malicious peer, node, or privileged access is required — this is exactly the spend-bundle-submitter / offer-counterparty attack surface the scope allows. However, actually engineering a colliding/collision-equivalent message that both (a) evades the six-suffix denylist and (b) is accepted as a valid message by some other AGG_SIG_* verification path requires the attacker to find or construct such a semantic collision, which is non-trivial but not proven infeasible from the source alone.

### Recommendation
Replace the incomplete `.endswith()` denylist against a fixed six-value set with a structural/allowlist-based validation: require `AGG_SIG_UNSAFE` messages to be provably independent of any coin-binding format for the target signing context (e.g., rejecting any message that could be reinterpreted as `msg' + coin_addendum + domain_separator` for any current, historical, or cross-network domain separator/opcode combination), or bind `AGG_SIG_UNSAFE` verification to a length/prefix scheme that cannot alias with `make_aggsig_final_message()` outputs regardless of which `additional_data` constant is in effect. At minimum, broaden `agg_sig_additional_data()`'s "disallowed" set to include all networks' additional-data constants, not just the currently active one, and add fuzz/property testing that generates arbitrary coin/opcode/additional-data combinations to confirm none of the six checked suffixes can be circumvented by construction.

### Proof of Concept
Not independently reproducible from static analysis alone. The code path is confirmed at [3](#0-2)  and [1](#0-0) , but demonstrating an actual bypass requires constructing a concrete colliding message under a specific `additional_data`/opcode combination and showing it validates as both an accepted `AGG_SIG_UNSAFE` message and a semantically valid coin-bound signature elsewhere — this would require running the mempool/consensus validation code against a crafted spend bundle, which is outside what can be confirmed via code reading alone. This should be treated as a design-level "incomplete blacklist" concern flagged for a dynamic/fuzzing follow-up rather than a proven exploit at this time.

```python
@lru_cache
def agg_sig_additional_data(agg_sig_data: bytes) -> dict[ConditionOpcode, bytes]:
    ret: dict[ConditionOpcode, bytes] = {}
    for code in [
        ConditionOpcode.AGG_SIG_PARENT,
        ConditionOpcode.AGG_SIG_PUZZLE,
        ConditionOpcode.AGG_SIG_AMOUNT,
        ConditionOpcode.AGG_SIG_PUZZLE_AMOUNT,
        ConditionOpcode.AGG_SIG_PARENT_AMOUNT,
        ConditionOpcode.AGG_SIG_PARENT_PUZZLE,
    ]:
        ret[code] = std_hash(agg_sig_data + code)

    ret[ConditionOpcode.AGG_SIG_ME] = agg_sig_data
    return ret
```

```python
def make_aggsig_final_message(
    opcode: ConditionOpcode,
    msg: bytes,
    spend_conditions: Coin | SpendConditions,
    agg_sig_additional_data: dict[ConditionOpcode, bytes],
) -> bytes:
    if isinstance(spend_conditions, Coin):
        coin = spend_conditions
    elif isinstance(spend_conditions, SpendConditions):
        coin = Coin(spend_conditions.parent_id, spend_conditions.puzzle_hash, uint64(spend_conditions.coin_amount))
    else:
        raise ValueError(f"Expected Coin or Spend, got {type(spend_conditions)}")  # pragma: no cover

    COIN_TO_ADDENDUM_F_LOOKUP: dict[ConditionOpcode, Callable[[Coin], bytes]] = {
        ConditionOpcode.AGG_SIG_PARENT: lambda coin: coin.parent_coin_info,
        ConditionOpcode.AGG_SIG_PUZZLE: lambda coin: coin.puzzle_hash,
        ConditionOpcode.AGG_SIG_AMOUNT: lambda coin: int_to_bytes(coin.amount),
        ConditionOpcode.AGG_SIG_PUZZLE_AMOUNT: lambda coin: coin.puzzle_hash + int_to_bytes(coin.amount),
        ConditionOpcode.AGG_SIG_PARENT_AMOUNT: lambda coin: coin.parent_coin_info + int_to_bytes(coin.amount),
        ConditionOpcode.AGG_SIG_PARENT_PUZZLE: lambda coin: coin.parent_coin_info + coin.puzzle_hash,
        ConditionOpcode.AGG_SIG_ME: lambda coin: coin.name(),
    }
    addendum = COIN_TO_ADDENDUM_F_LOOKUP[opcode](coin)
    return msg + addendum + agg_sig_additional_data[opcode]
```

```python
def pkm_pairs_for_conditions_dict(
    conditions_dict: dict[ConditionOpcode, list[ConditionWithArgs]],
    coin: Coin,
    additional_data: bytes,
) -> list[tuple[G1Element, bytes]]:
    ret: list[tuple[G1Element, bytes]] = []

    data = agg_sig_additional_data(additional_data)

    for cwa in conditions_dict.get(ConditionOpcode.AGG_SIG_UNSAFE, []):
        validate_cwa(cwa)
        for disallowed in data.values():
            if cwa.vars[1].endswith(disallowed):
                raise ConsensusError(Err.INVALID_CONDITION)
        ret.append((G1Element.from_bytes(cwa.vars[0]), cwa.vars[1]))
```
