## Title
CW721-to-ERC721 pointer's `transfer_nft`/`send_nft`/`burn` handler queries the current NFT owner instead of validating the caller, allowing any address to move an ERC721-backed token it does not own - (File: example/cosmwasm/cw721/src/contract.rs)

### Summary
The `example/cosmwasm/cw721/src/contract.rs` CW721 pointer contract (the wasm side of the ERC721↔CW721 pointer bridge) implements `transfer_nft` by looking up the *actual on-chain owner* of the token via `querier.erc721_owner(...)` and then building an ERC721 `transferFrom(owner, recipient, tokenId)` payload using that queried owner as the `from` address — instead of using/validating `info.sender` (the CosmWasm caller) as the required owner/approved party.

### Finding Description
`transfer_nft` (and, by extension, `send_nft`/`burn`, which reuse the same helper) is implemented as: [1](#0-0) 

```rust
fn transfer_nft(
    deps: DepsMut<EvmQueryWrapper>,
    info: &MessageInfo,
    recipient: &str,
    token_id: &str,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(recipient)?;
    let erc_addr = ERC721_ADDRESS.load(deps.storage)?;
    let querier = EvmQuerier::new(&deps.querier);
    let owner = querier.erc721_owner(info.sender.to_string(), erc_addr.to_string(), token_id.to_string())?.owner;
    let payload = querier.erc721_transfer_payload(owner, recipient.to_string(), token_id.to_string())?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new().add_message(msg);
    Ok(res)
}
```

This function never checks that `info.sender` equals the queried `owner`, nor that `info.sender` is approved to move the token. It simply queries whoever currently owns `token_id` on the underlying ERC721 pointer contract, and then packs a `transferFrom(owner, recipient, tokenId)` call that is executed via `EvmMsg::DelegateCallEvm` against the ERC721 pointer. This mirrors the ThunderNFT bug class ("insufficient validation ... due to insufficient validation of NFT ownership" / "no validation to ensure that the attacker actually owns the NFT") — here the wasm-side entrypoint fails to bind the caller identity to the ownership check before initiating the transfer, delegating authorization implicitly to whatever `msg.sender` context the delegatecall ends up executing with on the EVM side.

Because the call is issued as `DelegateCallEvm` rather than a normal `Call`, the security of this design hinges entirely on what `msg.sender` is preserved as when the EVM interpreter executes the delegated `transferFrom` inside the underlying `ERC721CW721Pointer`/native ERC721 pointer contract logic. The underlying pointer's `transferFrom` enforces `require(_isApprovedOrOwner(from, msg.sender, id), "not authorized")` (see `contracts/src/ERC721.sol:121-134`), so the exploitability specifically depends on whether `msg.sender` in that delegatecall context resolves to the CW721 message's `info.sender` (the actual transaction sender) or to some other value (e.g., the CW721 contract's own address, in which case the check could pass unexpectedly if the contract itself was ever authorized, or could resolve to an unrelated address entirely bypassing intent). I was not able to fully trace the `DelegateCallEvm` handler implementation in the `x/evm` message-server/precompile dispatch path within the indexed context to conclusively confirm which address is substituted as `msg.sender` for the delegated call — this is a gap in my verification and would need to be confirmed by reading the `EvmMsg::DelegateCallEvm` execution path in `x/evm/keeper` (handler for wasm bindings) directly.

### Impact Explanation
If the `DelegateCallEvm` execution preserves the origin CosmWasm contract's own address as `msg.sender` for the underlying ERC721 `transferFrom` (a common delegatecall semantic — the delegatecall keeps the original caller context of the calling contract) rather than requiring the original `info.sender` who invoked `transfer_nft` to be checked against ownership at the wasm layer, then any account could invoke `transfer_nft`/`send_nft`/`burn` on the CW721 pointer specifying an arbitrary `token_id` it does not own and an arbitrary `recipient`, resulting in unauthorized transfer of NFTs it does not control — a direct fund/asset theft matching the "Unauthorized transfer via precompile or pointer" impact category.

### Likelihood Explanation
Reaching this code path only requires submitting a standard `MsgExecuteContract` against a CW721 pointer contract with a `transfer_nft`/`send_nft`/`burn` payload specifying any token ID and any recipient — no privileged access, precompile‑level trust, or validator cooperation is required, making this trivially reachable by any unprivileged transaction sender if the underlying authorization gap is confirmed.

### Recommendation
In `transfer_nft` (`example/cosmwasm/cw721/src/contract.rs`), explicitly validate that `info.sender` is the owner of `token_id` (or is approved/operator for it) via the same `erc721_owner`/approval queries *before* constructing and dispatching the `transferFrom` payload, rather than trusting the delegatecall's implicit `msg.sender` resolution to gate authorization. Reject the request with `ContractError::Unauthorized` if `info.sender != owner` and the sender is not an approved operator, mirroring the ownership check already present in `contracts/src/CW721ERC721Pointer.sol` (`require(from == ownerOf(tokenId), ...)`) and `contracts/src/ERC721.sol`'s `_isApprovedOrOwner` check, so authorization is enforced at the wasm entrypoint itself rather than depending on EVM delegatecall semantics.

### Proof of Concept
1. Alice mints/owns CW721-pointer-backed ERC721 token `tokenId=5` (owner via `erc721_owner` resolves to Alice's EVM address).
2. Mallory, an unrelated account, submits `MsgExecuteContract` to the CW721 pointer contract: `{"transfer_nft": {"recipient": "<Mallory's sei address>", "token_id": "5"}}`.
3. `transfer_nft` executes `querier.erc721_owner(Mallory, erc_addr, "5")` — this returns Alice's address as the owner regardless of who is asking, since the query does not gate on caller.
4. The contract builds `erc721_transfer_payload(Alice, Mallory, "5")` and dispatches it via `EvmMsg::DelegateCallEvm` to the ERC721 pointer, without ever confirming Mallory has any right to move Alice's token.
5. If the delegatecall's `msg.sender` on the EVM side does not correctly resolve to Mallory as an unauthorized caller (e.g., resolves to the CW721 contract's own associated address, or any value that satisfies `_isApprovedOrOwner`), the `transferFrom(Alice, Mallory, 5)` call succeeds, and Mallory now owns Alice's NFT without consent.

*Note: Step 5's exploitability is contingent on the exact `msg.sender` semantics of `EvmMsg::DelegateCallEvm` in the `x/evm` keeper's wasm-binding executor, which I could not fully confirm within the available indexed context — a background engineer should trace this dispatch path in `x/evm/keeper` to confirm whether the check in the underlying ERC721's `transferFrom` is actually bypassed in practice, or whether it happens to be safe due to `msg.sender` correctly reflecting the true CW721 message sender.*
