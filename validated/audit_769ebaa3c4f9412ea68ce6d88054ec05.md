### Title
`cancelUnlock` skips `MasterMagpie.multiclaimFor`, letting rewards accrued during cooldown be checkpointed and paid out later at the post-cancel 100%-locked forfeit rate - ([File: VLMGP.sol])

### Summary
`VLMGP.cancelUnlock` mutates `slot.amountInCoolDown` and `totalAmountInCoolDown` directly without first calling `IMasterMagpie(masterMagpie).multiclaimFor`, unlike `startUnlock` and `unlock` which call it before mutating cooldown state. Because reward forfeiture in `vlMGPBaseRewarder`/`mWOMSVBaseRewarder` is computed lazily at claim time using the *current* `getRewardablePercentWAD(_account)` applied to the whole unclaimed reward bucket, skipping the pre-mutation claim lets rewards that accrued while the user was in cooldown (and should be partially forfeited) later be settled at the more favorable fully-locked rate.

### Finding Description
`startUnlock` and `unlock` both call `IMasterMagpie(masterMagpie).multiclaimFor(...)` before changing `slot.amountInCoolDown`/`totalAmountInCoolDown` [1](#0-0) , [2](#0-1) . This forces a reward checkpoint (`_updateFor`) and settlement (`_sendReward`/`_calExpireForfeit`) using the *pre-mutation* `getRewardablePercentWAD` state, so forfeiture correctly reflects the cooldown state that was actually in effect while rewards accrued.

`cancelUnlock`, in contrast, directly zeroes `slot.amountInCoolDown` and decrements `totalAmountInCoolDown` with **no** call to `multiclaimFor` beforehand [3](#0-2) .

The forfeit rewarders compute forfeiture lazily: `_updateFor` snapshots `userRewards[token][account] = _earned(...)` using the reward-per-token delta since the last checkpoint [4](#0-3) , and the actual forfeiture percentage is only computed later in `_sendReward` via `_calExpireForfeit`, which reads `vlMGP.getRewardablePercentWAD(_account)` **at the time of the call**, not at the time the reward accrued [5](#0-4) . `getRewardablePercentWAD` itself is a live view over the user's current `userUnlockings` array and total locked amount [6](#0-5) .

Exploit flow:
1. User is fully locked, then calls `startUnlock` (checkpoints past rewards at 100% rate, fine).
2. Time passes while the user is in cooldown; rewards accrue under a partially-forfeitable state (`getRewardablePercentWAD` < 100%), but the user does not claim, so no `_updateFor`/`_sendReward` fires yet — the reward is only implicitly "owed" via the growing `rewardPerToken` delta.
3. User calls `cancelUnlock`, which resets `amountInCoolDown` to 0 without ever calling `multiclaimFor`/triggering `_updateFor`. No checkpoint of the cooldown-period rewards occurs.
4. More time passes while now fully locked (100% rewardable).
5. User calls `claim` → `MasterMagpie.multiclaimFor` → rewarder `getReward` → `updateReward` modifier → `_updateFor`, which lumps together the entire delta since the last real checkpoint (steps 2–4) into one `userRewards` value, then `_sendReward` applies `_calExpireForfeit` using the **current** (100%, fully-locked, no-cooldown) `getRewardablePercentWAD`.

The forfeiture that should have applied proportionally to the cooldown-period rewards is never applied because no checkpoint ever occurred while the user was actually in cooldown; the entire batch is settled at the post-cancel, fully-locked rate.

### Impact Explanation
This is theft of unclaimed yield: reward tokens that should have been partially routed to the forfeiture pool (`_queueNewRewardsWithoutTransfer`, redistributed to other/remaining lockers) via `_calExpireForfeit` instead flow entirely to the attacker. Any user can start a cooldown, let reward-bearing time pass, then costlessly cancel (no penalty is charged in `cancelUnlock`, unlike `forceUnLock`) and claim later, laundering what should have been a forfeited share of yield. This matches the "theft of unclaimed yield that should have been partially forfeited" scoped impact class.

### Likelihood Explanation
No special privileges or capital are required beyond normal locking behavior: any vlMGP/mWomSV holder can call `startUnlock`, wait, `cancelUnlock`, wait, then claim. The only precondition is holding a lock position and having reward accrual occur during the cooldown window before cancellation, and no reward-triggering call (which would call `multiclaimFor` first) occurs during the cooldown other than the attacker's own `cancelUnlock`. This is repeatable indefinitely by any user and scales with reward flow and cooldown duration.

### Recommendation
Make `cancelUnlock` call `IMasterMagpie(masterMagpie).multiclaimFor(lps, rewards, msg.sender)` (mirroring `startUnlock`/`unlock`) **before** zeroing `slot.amountInCoolDown` and decrementing `totalAmountInCoolDown`, so any pending reward accrual is checkpointed and correctly forfeited against the pre-cancel (cooldown) state before the balance representation changes. Apply the same fix in `mWomSV.cancelUnlock`, which has the identical pattern [7](#0-6) .

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, `vlMGPBaseRewarder`, and a reward token; fund the rewarder pool.
2. Lock MGP for two users, A (attacker) and B (control), with equal amounts.
3. Both call `startUnlock` for the same amount at the same time (checkpoints their prior rewards).
4. Advance time by `T1` while both are in cooldown; queue/distribute reward tokens to the rewarder so `rewardPerTokenStored` increases.
5. For B (baseline), call `vlMGPBaseRewarder.updateFor(B)` (or trigger `multiclaimFor`) at this point, checkpointing B's cooldown-period rewards against the in-cooldown `getRewardablePercentWAD`.
6. For A (attacker), call `VLMGP.cancelUnlock(slotIndex)` instead (no checkpoint).
7. Advance time by `T2` while both are fully locked (B re-locked via a normal `unlock`/re-lock path with equivalent economics, A via cancel).
8. Both call `MasterMagpie.multiclaimFor` to claim rewards.
9. Assert: A's `RewardPaid` amount is strictly greater than B's `RewardPaid` amount despite identical starting positions and identical total reward accrual, and that A's `ForfeitRewardAdded` amount (or lack thereof) is smaller than B's proportional forfeiture recorded in `_calExpireForfeit`/`_queueNewRewardsWithoutTransfer`, demonstrating the attacker evaded forfeiture that should have applied to rewards accrued during cooldown.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }

    function _updateFor(address _account) internal {
        uint256 length = rewardTokens.length;
        uint256 userVlMGPAmount = balanceOf(_account);

        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = rewardTokens[index];
            if (userRewardPerTokenPaid[rewardToken][_account] == rewardPerToken(rewardToken))
                continue;

            userRewards[rewardToken][_account] = _earned(_account, rewardToken, userVlMGPAmount);
            userRewardPerTokenPaid[rewardToken][_account] = rewardPerToken(rewardToken);
        }
    }

    function _sendReward(address _rewardToken, address _account, address _receiver) internal {
        uint256 forfeitAmount = _calExpireForfeit(_account, userRewards[_rewardToken][_account]);
        uint256 toSend = userRewards[_rewardToken][_account] - forfeitAmount;


        userRewards[_rewardToken][_account] = 0;
            
        if (toSend > 0) {
            IERC20(_rewardToken).safeTransfer(_receiver, toSend);
            emit RewardPaid(_account, _receiver, toSend, _rewardToken);
        }

        if(forfeitAmount > 0)
            _queueNewRewardsWithoutTransfer(forfeitAmount, _rewardToken);
    }

    function _earned(address _account, address _rewardToken, uint256 _userVlmgpShare) internal view returns (uint256) {
        return ((_userVlmgpShare *
                (rewardPerToken(_rewardToken) -
                    userRewardPerTokenPaid[_rewardToken][_account])) /
                10**vlMGPDecimal) + userRewards[_rewardToken][_account];
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
