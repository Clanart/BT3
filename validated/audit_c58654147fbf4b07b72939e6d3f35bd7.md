### Title
Concurrent transactions can reserve and sign the same Bitcoin UTXO - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` computes available funds by summing every supplied `ReceivedOutput`, but it neither rejects duplicate outpoints nor records that an input has already been reserved by another pending transaction. Consequently, the same confirmed output can be counted multiple times in one transaction or reused across concurrent `SignableTransaction` instances. The resulting transactions can reach threshold signing despite being mutually exclusive or consensus-invalid.

### Finding Description
`SignableTransaction::new` derives `input_sat` directly from all supplied `ReceivedOutput` values and independently converts every item into a `TxIn`, without checking whether two items contain the same `OutPoint` [1](#0-0) . It then accepts the transaction when that summed value covers the requested payments and fee [2](#0-1) .

The only later input-specific check in `multisig` verifies that each stored prevout's `script_pubkey` corresponds to the threshold key plus the supplied offset; it does not verify uniqueness of `previous_output` or global pending-use state [3](#0-2) . `TransactionSignMachine::sign` subsequently produces a distinct BIP-341 signature share for every supplied input index [4](#0-3) , and `complete` inserts each completed witness [5](#0-4) .

Because `ReceivedOutput` is a serialized attacker-influenceable structure containing the outpoint, claimed `TxOut`, and scalar offset [6](#0-5) , untrusted bytes passed through `ReceivedOutput::read` can supply the same outpoint more than once [7](#0-6) .

### Impact Explanation
Two payment transactions can be created and signed while relying on the same liquid UTXO. At most one can be confirmed; the other becomes permanently unbroadcastable once the shared output is spent. A single transaction can also include the same outpoint twice, making it consensus-invalid even though its nominal input sum makes the payment appear funded.

This can leave requested withdrawals or payment plans signed but unsettleable and can waste threshold-signing work. Under repeated submissions, an attacker can repeatedly cause the same reserve to be earmarked for conflicting transactions without any pending-reservation check rejecting the later request.

### Likelihood Explanation
The issue is reachable whenever untrusted `ReceivedOutput` encodings or caller-selected outputs can be supplied to transaction construction. Triggering it only requires duplicating a valid received outpoint or submitting the same output to two concurrent transaction requests. No validator key access, malformed curve point, malformed transaction encoding, or compromised Bitcoin peer is required.

The threshold key must correspond to the claimed output script for `multisig` to proceed, so the attacker cannot merely invent an arbitrary script. The practical target is therefore a genuine output controlled by the multisig and reused concurrently, rather than fabrication of unrelated ownership.

### Recommendation
Maintain a set of `OutPoint`s while constructing `SignableTransaction` and reject duplicates before summing values or creating `TxIn`s. At the caller/scheduler layer, atomically mark an outpoint as pending when a plan or signing session is created, and reject any concurrent transaction that attempts to reserve the same outpoint until the first spend is confirmed or explicitly abandoned.

For defense in depth, validate within `SignableTransaction::new` that:

- all `previous_output` values are unique;
- supplied prevouts are authenticated trusted outputs rather than arbitrary attacker claims;
- input reservation occurs before signing;
- a restart/retry path cannot construct a second conflicting spend for the same logical reservation.

### Proof of Concept
The following demonstrates the root cause using a real scanned output. `bad` double-counts one UTXO inside a single consensus-invalid transaction, while `first` and `second` demonstrate two separately signable transactions competing for it.

```rust
// From networks/bitcoin/src/wallet/send.rs and wallet/mod.rs APIs.
let mut scanner = Scanner::new(group_key).unwrap();
let output = scanner.scan_transaction(&funding_tx).remove(0);

let payment = vec![(recipient_script.clone(), output.value())];
let change = Some(change_script.clone());

// Same confirmed outpoint is included twice. Its value is counted twice,
// even though it can be spent only once.
let bad = SignableTransaction::new(
  vec![output.clone(), output.clone()],
  &payment,
  change.clone(),
  None,
  fee_per_vbyte,
)
.unwrap();

// Separately constructed requests also have no shared pending reservation.
let first = SignableTransaction::new(
  vec![output.clone()],
  &payment,
  change.clone(),
  None,
  fee_per_vbyte,
)
.unwrap();

let second = SignableTransaction::new(
  vec![output],
  &payment,
  change,
  None,
  fee_per_vbyte,
)
.unwrap();
```

`bad` contains two identical `previous_output` entries and will be rejected by Bitcoin consensus. `first` and `second` are conflicting spends: both pass the available-funds check, both can proceed to threshold signing, and only one can be confirmed.
