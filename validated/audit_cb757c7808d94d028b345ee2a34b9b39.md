Blame proof leaks the ECDH key for a co-opted per-message key, publicly revealing an honest participant's encrypted DKG secret share - (File: crypto/dkg/pedpop/src/encryption.rs, crypto/dkg/pedpop/src/lib.rs)

### Summary

The PedPoP DKG encrypts each secret share with a per-message ephemeral key `msg.key`, deriving the ChaCha20 key from `ecdh = enc_key_recipient * msg.key`. The blame mechanism intentionally lets a recipient publish an `EncryptionKeyProof { key, dleq }` that reveals this ECDH shared point so all participants can decrypt the accused message and assign fault. The code comments claim a Schnorr proof-of-possession on `msg.key` prevents an attacker from copying an honest sender's `msg.key` and tricking the recipient into revealing `bX` (which would also decrypt the honest sender's real message). The PoP does fix the *attribution*, but not the *disclosure*: `Encryption::decrypt` computes and returns the revealing `EncryptionKeyProof` unconditionally, and `KeyMachine::calculate_share` attaches that proof to the `InvalidShare` error on share-deserialization failure *before* the batched PoP verification result is ever consumed. A participant Eve who copies Alice's `msg.key` `X` into a garbage message to Bob causes Bob to emit a blame proof revealing `bX`, which publicly decrypts Alice's legitimate share ciphertext to Bob — exposing secret share material to every observer, the same over-disclosure shape as the DirSync flaw (a legitimately-scoped reveal right exposing secrets beyond its intent).

### Finding Description

- `EncryptedMessage` carries `key` (ephemeral public key), `pop`, and ciphertext; `ecdh(private=enc_key, public=msg.key)` is the shared key and `cipher()` derives the ChaCha20 key from it (`crypto/dkg/pedpop/src/encryption.rs` lines 95-133).
- The safety comment states the threat: if Eve reuses Alice's key `X`, Bob's blame would reveal `bX`, "revealing Alice's message to Bob"; the `pop` field was added to stop this (`encryption.rs` lines 83-91).
- `Encryption::decrypt` queues the PoP into a `BatchVerifier` under `batch_id` but *immediately* computes `key = ecdh(enc_key, msg.key)`, decrypts, and returns `EncryptionKeyProof { key, dleq }` — a full decryption capability for any ciphertext sharing that ECDH — regardless of whether the PoP later verifies (`encryption.rs` lines 469-501).
- In `KeyMachine::calculate_share`, the loop over `shares` calls `decrypt`, then `C::F::from_repr` on the plaintext. On failure it returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }` immediately — the function exits without calling `batch.verify_with_vartime_blame()`, so Eve's invalid PoP never downgrades the blame to `None` (`crypto/dkg/pedpop/src/lib.rs` lines 476-499).
- The processor serializes that blame into `ProcessorMessage::InvalidShare` and the coordinator verifies it via `CoordinatorMessage::VerifyBlame` → `AdditionalBlameMachine::blame` → `decrypt_with_proof` (`processor/src/key_gen.rs` lines 419-425, 504-549). The published `EncryptionKeyProof.key` = `bX` is now public; anyone holding Alice's `EncryptedMessage` to Bob (shares are disseminated set-wide) can run `cipher(context, bX)` over Alice's ciphertext and recover `SecretShare` bytes — Alice's polynomial evaluation for Bob.
- `blame_internal` still correctly blames Eve (`InvalidSignature` → `sender`), so accountability is intact — but the secret material is already revealed, exactly the fail-open/over-exposure pattern.

### Impact Explanation

Confidentiality of the Pedersen/Feldman DKG is broken: an encrypted secret share intended for a single recipient is decrypted publicly. Each revealed value is one participant's share-contribution to a victim's final secret; repeated triggers (per sender, per DKG) disclose multiple secret shares on-chain, degrading the privacy the ECDH layer exists to provide, and any ciphertexts encrypted under a reused `msg.key` to the same recipient are all compromised by one blame. This is secret material exposure to parties holding only the limited "file a blame" capability — analogous to GET_CHANGES holders receiving all DirSync attributes.

### Likelihood Explanation

Exploitation needs a DKG participant (or anyone able to route a share message to a victim under a participant index) to copy the victim-visible `msg.key` of an honest sender's `EncryptedMessage` into their own share message; no secret knowledge is required since the PoP is deliberately left invalid. The malicious sender is blamed and presumably slashed, which raises the cost, but the disclosure itself is unpreventable — nothing in `decrypt`/`calculate_share` withholds the revealing key when the PoP is bad. Medium severity is consistent: secret leakage, gated by a slashable-but-cheap malicious action.

### Recommendation

Do not produce or propagate the `EncryptionKeyProof` until the message's PoP has been verified. In `KeyMachine::calculate_share`, verify the decryption batch (or at least the PoP statements) before attaching `blame` to `InvalidShare` errors, or return `blame: None` for any share whose PoP is invalid rather than leaking the ECDH key. More robustly, restructure `Encryption::decrypt` to only yield `EncryptionKeyProof` after PoP validity is established. Additionally, consider deriving the cipher per unique `msg.key` such that a reveal only ever exposes ciphertexts the accuser legitimately received, and document that a blame proof discloses the shared key for *all* ciphertexts using that ECDH pair.
