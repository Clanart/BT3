### Title
Asymmetric decimal-scaling bug in `pallet-hyper-fungible-token` allows minting/releasing far more tokens on the destination chain than were locked on the source — ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
The external report's core broken invariant is: *a decimals value assumed consistent in one part of the code is actually attacker/configuration-controlled and different in another part, and the scaling math that bridges the two silently produces a wrong amount instead of failing safely.* The Hyperbridge analog is in `pallet-hyper-fungible-token`'s cross-chain amount conversion helpers, where `saturating_sub` is used to compute a decimal-scaling exponent. When the local asset has **more** decimals than the paired EVM contract (`erc_decimals < local_decimals`), the exponent underflows to `0` instead of triggering a division, causing the raw balance to be forwarded to the destination chain completely unscaled.

### Finding Description
`convert_to_erc20` and `convert_to_balance` in [1](#0-0) 
compute scaling as `10u128.pow(erc_decimals.saturating_sub(local_decimals))` (and the mirrored `local_decimals.saturating_sub` direction is missing entirely). This formula is only correct when `erc_decimals >= local_decimals`. When `local_decimals > erc_decimals`, `erc_decimals.saturating_sub(local_decimals)` clamps to `0`, so the code multiplies (or divides) by `10^0 = 1` — i.e. **no scaling is applied at all**, even though one is required.

This function is invoked from the public, unprivileged `send` extrinsic: [2](#0-1) 
where `erc20_amount = convert_to_erc20(amount, erc_decimals, decimals)` becomes the `Message.amount` dispatched to the EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract, which will mint or release custody funds based on that raw value.

Per-asset, per-chain decimal configuration is stored in `Precisions` and set by `register_token`/`update_token` (`CreateOrigin`), independent of the actual local asset's decimals (`T::Decimals` or `Assets::decimals`): [3](#0-2) 
There is no visible invariant anywhere in the pallet enforcing `erc_decimals >= local_decimals`, so any asset registered with a lower EVM-side precision than its local precision (a completely normal, legitimate configuration — e.g., an 18-decimal Substrate asset paired with a 6-decimal representation on an EVM chain) hits the broken branch.

Concretely, with `local_decimals = 18`, `erc_decimals = 6`:
- Correct scaling: `erc20_amount = amount / 10^12`.
- Actual (buggy) scaling: `erc20_amount = amount * 10^0 = amount` (unchanged).

A user calling `send()` with `amount = 1e18` (1 whole token, locking/burning exactly 1 token locally) produces `Message.amount = 1e18`. On the EVM side, the contract treats this as a raw ERC-20 value at 6 decimals, i.e. `1e18 / 1e6 = 1,000,000,000,000` (one trillion) whole tokens minted or released from custody — a 10¹²× amplification of value created out of a single locked/burned token.

### Impact Explanation
This is a direct, unprivileged fund-forging bug: an ordinary signed account can call `send()` and cause the counterpart EVM contract to mint (non-native asset) or unlock from custody (native asset) an amount inflated by `10^(local_decimals - erc_decimals)` relative to what was actually escrowed/burned on the source chain. This can drain the token-gateway's custody pool or mint an unbounded supply of the wrapped asset — squarely "stealing or loss of funds" / "unauthorized... amount" per the impact gate, reachable through a normal message flow (no malicious relayer, prover, or admin required).

### Likelihood Explanation
Any asset registered where the EVM-side decimals (`Precisions`) are lower than the local chain's asset decimals triggers this bug on every `send()` call — this is not an edge case requiring adversarial input, just a common decimal-mismatch configuration (e.g., bridging an 18-decimal Substrate token to a 6-decimal EVM representation). No special privileges are needed to trigger it, only knowledge of the registered asset's decimal configuration, which is public runtime state.

### Recommendation
Fix the scaling helpers to handle both directions explicitly instead of relying on `saturating_sub` to silently no-op:
```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
and symmetrically for `convert_to_balance`. Add explicit tests covering `local_decimals > erc_decimals` for both `send` and `on_accept`/`on_timeout` paths, since the existing test suite only exercises `erc_decimals(18) > local_decimals(10)` [4](#0-3) 
which never exposes the broken branch.

### Proof of Concept
1. Governance/`CreateOrigin` registers a non-native asset with `local_decimals = 18` (via `pallet-assets` or as the chain's native currency with `T::Decimals = 18`) and sets `Precisions::<T>::insert(asset_id, StateMachine::Evm(x), 6)` (EVM contract uses 6 decimals) — a legitimate, unremarkable configuration.
2. Attacker (any signed account) calls `send(SendParams { asset_id, destination: Evm(x), amount: 1_000_000_000_000_000_000 /* 1 token, 18dp */, .. })`.
3. Inside `send`, `erc20_amount = convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)`. Since `erc_decimals.saturating_sub(local_decimals) == 0`, `erc20_amount = 1e18` unchanged [5](#0-4) [6](#0-5) 
4. Only 1 token's worth of local balance was locked/burned, but the dispatched `Message.amount = 1e18` reaches the destination `HyperFungibleToken` contract, which (at 6 decimals) mints/releases `1e18 / 1e6 = 1e12` tokens to the attacker's chosen recipient — a 10¹²× fund amplification from a single legitimately-locked token.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
