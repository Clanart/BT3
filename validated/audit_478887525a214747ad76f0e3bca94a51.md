### Title
Reward forfeiture bypass for locked mWomSV holders in cool-down - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` never calls `mWomSV.getRewardablePercentWAD`, unlike the analogous `vlMGPBaseRewarder._calExpireForfeit` which does. It sets `rewardableAmount = _amount` unconditionally, so `forfeitAmount = _amount - rewardableAmount` is always `0`, meaning users in active cool-down receive 100% of rewards instead of the reduced amount dictated by `mWomSV.getRewardablePercentWAD`.

### Finding Description
`mWomSV.getRewardablePercentWAD` ( [1](#0-0) ) computes a percentage below 100% for any user with tokens `amountInCoolDown > 0` that has not yet fully unlocked, intending that a portion of rewards be forfeited back to the pool (via `_queueNewRewardsWithoutTransfer`) for users mid-cool-down.

`vlMGPBaseRewarder._calExpireForfeit` correctly implements this by calling `vlMGP.getRewardablePercentWAD(_account)` and scaling `_amount` by it ( [2](#0-1) ).

In contrast, `mWOMSVBaseRewarder._calExpireForfeit` sets `rewardableAmount = _amount` directly without ever calling `mWOMSV.getRewardablePercentWAD(_account)`: [3](#0-2) 
Because `rewardableAmount` always equals `_amount`, `forfeitAmount = _amount - rewardableAmount` is always `0`. This is called from `_sendReward` ( [4](#0-3) ), which is invoked from `getReward`/`getRewards`, both gated only by `onlyMasterMagpie` ( [5](#0-4) ) — any unprivileged user reachable through `MasterMagpie.multiclaimFor` can trigger this path for themselves.

Attack flow: an attacker calls `mWomSV.lock(amount)` to lock mWOM, then `mWomSV.startUnlock(partialAmount)` to place a portion into cool-down ( [6](#0-5) ). While in cool-down, `getRewardablePercentWAD` for that user is less than 100% (weighted by locked vs cool-down amounts). The attacker then calls `MasterMagpie.multiclaimFor([mWomSV], accounts, self)`, which routes to `mWOMSVBaseRewarder.getReward`, and because `_calExpireForfeit` never applies the discount, the attacker receives their full `earned()` reward with zero forfeiture — contrary to the intended tokenomics where a fraction should instead be redistributed to other lockers via `_queueNewRewardsWithoutTransfer`.

No existing modifier (`onlyMasterMagpie`, `updateReward`, `nonReentrant`) prevents this since the flaw is a pure logic/calculation bug independent of access control.

### Impact Explanation
This is theft/permanent misallocation of unclaimed yield: locked users who should forfeit a proportional share of rewards for withdrawing early into cool-down instead capture 100% of accrued rewards, permanently depriving remaining/fully-locked stakers of the forfeited yield that `_queueNewRewardsWithoutTransfer` was designed to redistribute to them. This matches the Immunefi "theft of unclaimed yield" impact class. The magnitude scales with reward token amounts and the fraction of the pool's users utilizing cool-down while still farming rewards.

### Likelihood Explanation
Highly likely and trivially repeatable: it requires no special privileges, only holding mWOM, calling `lock`, `startUnlock` for any partial amount, and then harvesting via `MasterMagpie.multiclaimFor`/`getReward`. No capital beyond the ordinary lock amount is needed, and it can be repeated by any/every mWomSV holder indefinitely, whenever they choose to start a cool-down, with no window restriction.

### Recommendation
Fix `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder._calExpireForfeit`: query `mWOMSV.getRewardablePercentWAD(_account)` and scale `_amount` by it to compute `rewardableAmount`, e.g.:
```solidity
uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
```

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `mWOMSVBaseRewarder`, `MasterMagpie`, and a reward token; register `mWomSV` as a pool and set the rewarder.
2. Fund attacker with mWOM, call `mWomSV.lock(1000e18)`.
3. Queue rewards into `mWOMSVBaseRewarder` (e.g. `queueNewRewards`) so `earned()` accrues for the attacker.
4. Call `mWomSV.startUnlock(500e18)` to place half the balance into cool-down; assert `mWomSV.getRewardablePercentWAD(attacker) < 1e18`.
5. Compute expected forfeited amount off-chain as `earned * (1e18 - rewardablePercentWAD) / 1e18`.
6. Call `MasterMagpie.multiclaimFor([address(mWomSV)], [rewardTokens], attacker)` (routes to `mWOMSVBaseRewarder.getReward`).
7. Assert `userRewards paid == earned()` in full (no forfeiture occurred) despite `getRewardablePercentWAD < 100%`, and assert `rewards[token].queuedRewards`/`rewardPerTokenStored` show no forfeited amount was re-queued via `_queueNewRewardsWithoutTransfer`.
8. Repeat the same scenario against `vlMGPBaseRewarder`/`VLMGP` with an equivalent cool-down state to show it correctly applies a nonzero forfeit, contrasting the two implementations.

        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
