## Title
Line-index-based partial-commit selection is applied to a freshly re-fetched diff without content validation, allowing silent inclusion of unintended edits into a commit - (File: `app/src/lib/git/apply.ts`)

### Summary
Github Desktop's partial-commit ("stage selected lines") feature stores the user's line selection purely as a set of integer line indices (`DiffSelection`), with no binding to the actual diff content those indices describe. When the commit is executed, `applyPatchToIndex` re-fetches a brand-new diff from disk and blindly re-applies the old index-based selection to it, optimistically assuming the new diff has the same hunk/line layout as the one the user actually looked at. If the working directory changed between the moment the user selected lines in the UI and the moment the commit runs, the index-to-content mapping can shift, causing Desktop to stage and commit different content than what the user selected — without any error, warning, or diff re-validation.

### Finding Description
`DiffSelection` is explicitly documented as content-agnostic: [1](#0-0) 

It only tracks "diverging" line numbers and has no notion of what text is at those indices. The `isSelected(lineIndex)` method purely does index math.

The write path, `applyPatchToIndex`, fetches a **fresh** diff at commit time and then formats a patch by walking that fresh diff's hunks and asking `file.selection.isSelected(absoluteIndex)` for each line index: [2](#0-1) 

`formatPatch` trusts these indices completely to decide which lines to include, drop, or convert to context: [3](#0-2) 

The UI code that manages the diff shown to the user (`app-store.ts`) is aware that this is unsafe but does not fully address it — it only trims stale line indices from the *selectable* set, it does not detect whether the diff a user selected against still matches the diff being committed against: [4](#0-3) 

Crucially, this comment applies to the *displayed* diff refresh only. There is no equivalent re-validation performed in the actual git write path (`_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex`): [5](#0-4) [6](#0-5) 

At commit time, `applyPatchToIndex` does not compare the newly fetched diff against the diff that was on screen when the user made their selection; it simply re-fetches (`getWorkingDirectoryDiff`) and reuses the stale index set. If a file's content is modified between selection and commit — e.g., by a build tool, linter/formatter, `.gitattributes` clean/smudge filter, a background file watcher, or any tool triggered by opening/fetching an attacker-controlled repository — the hunk boundaries and line ordering can shift. The stale indices in `file.selection` then point at different logical lines in the new diff, so `formatPatch` can silently: include lines the user never selected, drop lines the user did select, or convert an intended deletion/addition into context (i.e., include it unintentionally). This is the same "broken invariant" as the Sherlock finding: a previously-computed, snapshot-based value (`amounts`/selection) is optimistically treated as still accurate against fresh state (`totalSherX`/new diff) at the point of an irreversible action (payout/commit), with no check that the assumption still holds.

### Impact Explanation
The corrupted value is the **content of the git commit the user believes they are creating**. Because the commit is produced silently with no error and no additional confirmation of the final diff, a user could unknowingly commit and push unintended content — including content they explicitly deselected, or omit content they explicitly selected. In a repository with tooling that programmatically alters files shortly after checkout/fetch (formatters, generated files, LFS smudge filters, editor auto-save, CI-adjacent scripts run locally), an attacker who controls repository configuration (e.g. `.gitattributes` filters or build scripts invoked by the repo's own tooling) can increase the odds that files are rewritten between diff display and commit, causing Desktop to commit/push content the user did not intend. This falls in the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
This requires a timing window between the user reviewing/selecting diff lines in the Changes view and clicking Commit, during which the underlying file content changes (hunk/line-count altering edit) without Desktop refreshing the diff shown to the user or invalidating the stale selection. This is plausible in real workflows (auto-formatters on save, file watchers, LFS/clean filters triggered by repository-defined `.gitattributes`), but requires an external actor/process to modify the file in that specific window, so it is not trivially triggerable by a remote attacker alone — it depends on repo-configured tooling being present and running. Likelihood is therefore moderate, not high.

### Recommendation
When performing the partial commit at `applyPatchToIndex`/`formatPatch` time, validate that the freshly-fetched diff structurally matches the diff the current `DiffSelection` was built against (e.g., by storing a content hash or hunk fingerprint alongside the selection) before applying line indices. If a mismatch is detected, refuse to auto-apply the stale selection and instead force a diff refresh and require the user to re-confirm their selection, mirroring (and completing) the intent already partially expressed in the `updateChangesWorkingDirectoryDiff` comment in `app-store.ts`.

### Proof of Concept
1. Modify a tracked file so it has multiple hunks; open it in Desktop's Changes view and diff renders with hunks A and B.
2. Select only specific lines in hunk B for the commit (deselect hunk A).
3. Before clicking "Commit", have an external process (e.g., a formatter/watcher/clean filter tied to the repo) rewrite the file such that the line count/position of hunk B shifts (e.g., inserts blank lines earlier in the file) — Desktop's Changes list may not immediately re-render the diff/selection state.
4. Click Commit. `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) fetches the new diff and `formatPatch` (`app/src/lib/patch-formatter.ts:129`) applies the old line-index selection (still keyed to the pre-edit hunk layout) against the new hunk layout.
5. Inspect the resulting commit: it contains different line content than what was highlighted/selected in the UI just before commit, with no warning shown to the user.

Note: I was not able to execute this end-to-end in a live environment from the index alone (no filesystem/terminal access here), so the timing window and exact reproduction steps should be validated by a Devin session with actual repository access to confirm the race is triggerable in practice.
