Based on my analysis, the strongest local analog to the OUSD bug (a rate computed via division that silently floors to zero and breaks a fundamental protocol invariant) is in Hyperbridge's `SimplexPaymaster`, where the token/gas conversion rate can floor to zero via integer division, causing the paymaster to sponsor gas for free.

### Title
`SimplexPaymaster._tokenPrice` can floor to zero, letting UserOps drain the EntryPoint deposit without paying any ERC‑20 cost - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster._tokenPrice()` computes the ERC‑4337 `tokenPrice` (token-base-units per wei, scaled by 1e18) as an integer division of two Chainlink-derived USD values. Nothing in the contract enforces that this quotient is non-zero before it is used by `PaymasterERC20` to bill the UserOp sender. Just as OUSD's `rebasingCreditsPerToken` could be driven to zero by ordinary parameter values and silently break `balanceOf`, `_tokenPrice` can floor to zero for legitimate, governance-registered tokens whose price ratio relative to the native asset exceeds `10**tokenDecimals`, and every downstream consumer trusts the result unconditionally.

### Finding Description
`_tokenPrice` is:
```solidity
return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
``` [1](#0-0) 

This value feeds `_fetchDetails`, which `PaymasterERC20` uses to compute `erc20Cost = weiCost * tokenPrice / 1e18` (documented directly in the contract's own comment): [2](#0-1) 

If `tokenUsd * 10_000 > nativeUsd * 10**tokenDecimals * (10_000 + markupBps)`, integer division truncates `tokenPrice` to `0`. This is exactly the OUSD pattern: a per-unit rate computed by division, with no `> 0` guard, whose degenerate value (zero) is then propagated into a cost calculation that other code paths implicitly assume is always positive. Unlike OUSD's `balanceOf`, which reverts on the degenerate case, here the degenerate case produces `erc20Cost == 0`, i.e., a false "gas is free" acceptance state — the more dangerous direction because it fails open rather than closed.

`_getOraclePrice` only guards staleness and non-positive answers, never magnitude relative to the paired oracle: [3](#0-2) 

Both `_validatePaymasterUserOp` and `_fetchDetails` check only that the token is registered and active — never that the computed price is non-zero: [4](#0-3) 

No existing guard stops this: `TokenNotRegistered`/`TokenNotActive` checks only gate *which* token is used, not the *magnitude* of the derived price; `StaleOraclePrice`/`InvalidOraclePrice` only gate freshness/sign, not ratio; and `MAX_MARKUP_BPS` bounds markup, not the base ratio. There is no `if (tokenPrice == 0) revert(...)` anywhere in the pricing path, and the OZ `PaymasterERC20` base being wrapped is not visible/patched by this contract to add one.

### Impact Explanation
When `tokenPrice == 0`, `estimateTokenCost` and the actual `_erc20Cost` charged during `postOp` both evaluate to zero. The UserOp sender pays nothing in the ERC‑20 token while the paymaster still fronts the real gas cost from its EntryPoint deposit (the paymaster's pooled native-asset balance funding all sponsored UserOps, described in the contract's own security model as bounded by client-side allowance limits, not by this invariant). Any account can then repeatedly submit UserOps using the affected token in `paymasterData`, draining the shared EntryPoint deposit — a direct, unauthorized loss of protocol/treasury funds with no privileged actor, malicious oracle operator, or governance compromise required; only an oracle-price ratio condition need be reached (e.g., a low-decimal registered token, or the native asset's USD price collapsing relative to the token's), matching the bounty's "stealing or loss of funds" / "unauthorized transaction execution" categories.

### Likelihood Explanation
Reachability depends on the token/native price ratio and `tokenDecimals` at registration. Governance can register "any token with a Chainlink feed," not only $1‑pegged stablecoins, per the contract's own header comment. For tokens with few decimals (e.g., 0–2 decimals) or during periods where the native asset's USD price is materially lower than the registered token's, the threshold `tokenUsd/nativeUsd > 10**tokenDecimals` is realistically reachable purely from normal price data — no oracle manipulation needed, since the check is a plain unguarded integer division. This is a medium-likelihood, high-impact configuration/market-condition-triggered path rather than a pure design flaw exploitable instantly, but it requires zero attacker privilege to trigger once the condition holds.

### Recommendation
- **Short term:** In `_tokenPrice` (and its callers `getTokenPrice`/`estimateTokenCost`/`_fetchDetails`), revert if the computed `tokenPrice == 0` (mirroring the OUSD fix's "require rate non-zero" pattern). Additionally, enforce a sane minimum price floor at `RegisterToken` time as a defense-in-depth check on decimals/ratio plausibility.
- **Long term:** Add an invariant/fuzz test (Echidna/Foundry invariant) asserting `_tokenPrice(cfg) > 0` for all registered active tokens across the oracle price ranges the contract is expected to tolerate, and assert `erc20Cost > 0` whenever `weiCost > 0`.

### Proof of Concept
1. Governance registers a token `T` with `tokenDecimals = 0` (or very low decimals) and a valid Chainlink `T/USD` feed via `RequestKind.RegisterToken`.
2. Market conditions (or a temporary native-asset price dip) cause `tokenUsd(T) > nativeUsd` at 8-decimal normalization — plausible for any token priced above the native asset's USD value.
3. Any account builds a `PackedUserOperation` with `paymasterData` mode `0x01` (APPROVE) referencing token `T`.
4. `_fetchDetails` computes `tokenPrice = (nativeUsd * 10**0 * 10_000) / (tokenUsd * 10_000)`, which truncates to `0` once `tokenUsd > nativeUsd`.
5. `PaymasterERC20`'s `_erc20Cost = weiCost * 0 / 1e18 = 0` — the UserOp executes, EntryPoint gas is drawn from the paymaster's deposit, and `transferFrom` for 0 tokens costs the sender nothing.
6. Repeat across many UserOps to drain the paymaster's EntryPoint deposit at zero cost.

    ///
    ///      PaymasterERC20 computes `erc20Cost = weiCost * tokenPrice / 1e18`,
    ///      so tokenPrice must be token base units per wei, scaled by 1e18:
    ///        tokenPrice = (nativeUsd * 10^tokenDecimals) / tokenUsd
    ///      e.g. BNB at $600, USDC at $1 with 6 decimals: 0.001 BNB (1e15 wei)
    ///      should cost 0.60 USDC (600000 units), giving tokenPrice = 6e8, which
    ///      is exactly (600e8 * 1e6) / 1e8. Markup is applied on top.
    function _fetchDetails(
        PackedUserOperation calldata userOp,
        bytes32 /* userOpHash */
    ) internal view override returns (uint256 validationData, IERC20 token, uint256 tokenPrice) {
        bytes calldata data = userOp.paymasterData();
        if (data.length < 21) revert InvalidPaymasterData(data.length);

        uint8 mode = uint8(data[0]);
        if (mode > 0x01) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction
    }

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
