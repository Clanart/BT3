### Title
`_getClaimable` in ArbitrumMWomAirdrop always returns full `totalAmount`, completely bypassing the linear vesting schedule - (File: rewards/ArbitrumMWomAirdrop.sol)

### Summary
`ArbitrumMWomAirdrop._getClaimable` sets `uint256 vested = totalAmount;` instead of computing a time-based linear vesting amount, so the subsequent `if (vested > totalAmount)` check can never be true and the function always returns `totalAmount - claimed`. Any eligible claimant can call `claim()` the instant `block.timestamp >= startVestingTime` and withdraw their entire allocation in one transaction, defeating the vesting mechanism entirely.

### Finding Description
The public `claim()` function only requires `block.timestamp >= startVestingTime` and a valid merkle proof before computing `claimable` via `_getClaimable`: [1](#0-0) 

`_getClaimable` is supposed to gate the claimable amount by a linear vesting curve based on `startVestingTime`, `vestingPeriodCount`, and `intervals` (as correctly implemented in the sibling contract `Airdrop2.sol`, which computes `vested = (totalAmount * 5 / 100) + (totalAmount * 95 / 100) * ((block.timestamp - startVestingTime) / intervals) / vestingPeriodCount`): [2](#0-1) 

However, in `ArbitrumMWomAirdrop`, the vesting computation is replaced with a hardcoded assignment `vested = totalAmount`, making the `vestingPeriodCount` and `intervals` state variables completely unused in the calculation: [3](#0-2) 

Because `vested` is always equal to `totalAmount`, the guard `if (vested > totalAmount)` is dead code (never true), and the function always falls through to `return vested - claimed`, i.e. `totalAmount - claimed`. This means one second after `startVestingTime`, any claimant with a valid merkle proof can withdraw 100% of their allocated `totalAmount` in a single `claim()` call, regardless of `vestingPeriodCount` or `intervals`. No modifier, receipt-token accounting, or reward-index update in the contract prevents this, since `whenNotPaused` and `nonReentrant` do not constrain the claimable amount logic.

### Impact Explanation
This breaks the intended linear vesting/lock schedule that is meant to gradually release reward tokens (backing protocol emissions) over `vestingPeriodCount` intervals. Every eligible claimant can immediately drain their full entitlement instead of receiving it in tranches, which for the protocol constitutes theft/premature release of tokens meant to be locked as unclaimed yield/emissions backing over time — matching the "theft or permanent freezing of unclaimed yield" impact class, since the vesting design is fully circumvented for all users simultaneously.

### Likelihood Explanation
This requires no privileged access — only a valid merkle proof entry (i.e., being a legitimate airdrop recipient) and waiting until `startVestingTime` passes, which is a normal, expected, and repeatable interaction path (`claim()` is a public/external function). The bug is deterministic and triggers on the very first claim by any user, with 100% reliability.

### Recommendation
Restore the correct linear vesting formula in `_getClaimable`, matching the logic in `Airdrop2.sol`:
```solidity
uint256 vested = initialUnlockAmount + (totalAmount - initialUnlockAmount) * ((block.timestamp - startVestingTime) / intervals) / vestingPeriodCount;
if (vested > totalAmount) {
    return totalAmount - claimed;
}
return vested - claimed;
```
ensuring `vestingPeriodCount` and `intervals` actually gate the claimable amount over time.

### Proof of Concept
Foundry test plan:
1. Deploy `ArbitrumMWomAirdrop` with `vestingPeriodCount = 12`, `intervals = 30 days`, `startVestingTime = block.timestamp + 1 days`, and a merkle root covering a test account with `totalAmount = 1200e18`.
2. Fund the contract with `reward` tokens equal to `totalAmount`.
3. Warp to `startVestingTime + 1`.
4. Call `claim(1200e18, proof, false, false)` from the test account.
5. Assert `reward.balanceOf(account) == 1200e18` (full amount) immediately, instead of the expected ~`100e18` (1/12th tranche) that a correct linear vesting schedule would allow at that timestamp — confirming the vesting cap is broken.
