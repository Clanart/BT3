### Title
Webhook HMAC verification does not bind the trusted `X-Shopify-Shop-Domain` header, allowing shop-attribution forgery in `ShopifyApp::WebhookVerification` - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` validates the HMAC of the raw request body only, while `#shop_domain` reads the shop identifier from an unauthenticated request header that is never included in that HMAC computation. Just as the reported Tigris bug computed `_feePaid`/`_positionSize` from an incomplete input (omitting referral fees) and then used that incomplete result to drive a security-relevant downstream calculation, this concern computes "is this request authentic" from an incomplete input (body only) and then lets a completely separate, unverified value (`shop_domain` header) drive the downstream security-relevant action (which shop's job/data the webhook is attributed to).

### Finding Description
`ShopifyApp::PayloadVerification#hmac_valid?` computes/validates the HMAC strictly over `request.raw_post`: [1](#0-0) 

`ShopifyApp::WebhookVerification#verify_request` uses only that body-based check to decide whether to accept the request, and separately exposes `shop_domain` sourced from the `HTTP_X_SHOPIFY_SHOP_DOMAIN` header, which is not part of the signed data at all: [2](#0-1) 

The gem's own documentation instructs developers to build custom webhook controllers that trust this same unauthenticated `shop_domain` value for dispatching shop-scoped background jobs: [3](#0-2) 

Because the header is excluded from the HMAC input, a request whose body+signature pair is valid (i.e., a genuine webhook body that was legitimately signed using the app's shared secret) can be replayed with an arbitrary/forged `X-Shopify-Shop-Domain` header value. `hmac_valid?` still returns `true` (it only checks the body), and `verify_request` lets the request through; the shop attribution used by the rest of the pipeline (`shop_domain`) is fully attacker-controlled.

### Impact Explanation
Any custom webhook controller built per the documented pattern — and any code relying on `WebhookVerification#shop_domain` for authorization/scoping decisions — can be tricked into associating a validly-signed webhook payload with a different (attacker-chosen) shop domain. This is a cross-shop data/action confusion: a party capable of triggering or capturing one genuinely signed webhook (e.g., from their own installed shop) can cause the app to process that payload as if it belongs to another shop, potentially triggering shop-scoped jobs (including sensitive ones like `customers/redact`, `shop/redact`) attributed to a victim shop.

### Likelihood Explanation
Exploitability requires possession of at least one validly HMAC-signed webhook body (trivially obtainable by any merchant who has installed the app, since Shopify sends them real, signed webhooks for their own shop), plus the ability to POST an HTTP request with a modified header to the app's webhook endpoint — both are reachable from an unprivileged, unrelated-merchant vantage point, with no secret-key knowledge required.

### Recommendation
Include the shop-identifying value in the data that is HMAC-verified (Shopify's genuine webhook HMAC already is computed only over the body, so instead the app should not trust the `X-Shopify-Shop-Domain` header for security decisions on its own). Concretely:
- Derive the trusted shop identity from the verified webhook body/topic mapping (e.g. via `ShopifyAPI::Webhooks::Request#shop`, which Shopify's library derives from validated webhook context) rather than from the raw header.
- If the header must be used, cross-check it against the shop encoded/derivable from the verified payload and reject mismatches before dispatching any job.

### Proof of Concept
1. Install the app on Shop A; capture a legitimate webhook request Shopify sends to the app's custom webhook endpoint (valid `X-Shopify-Hmac-Sha256` computed over the raw body using the app's shared secret, and header `X-Shopify-Shop-Domain: shop-a.myshopify.com`).
2. Resend the identical body and `X-Shopify-Hmac-Sha256` header to the same endpoint, but replace `X-Shopify-Shop-Domain` with `shop-b.myshopify.com`.
3. `ShopifyApp::WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which only checks the body — it returns `true` because the body/signature pair is unchanged.
4. `shop_domain` returns the forged `shop-b.myshopify.com`. The controller (built per the documented pattern) executes `SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)`, running shop-scoped logic against Shop B using data intended for Shop A.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
