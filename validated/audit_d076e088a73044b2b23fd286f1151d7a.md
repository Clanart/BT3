## Title
Malicious tokenfactory denom allow-list can cause `gov` `RefundDeposits` to panic, halting the chain at `EndBlock` - (File: `sei-cosmos/x/gov/keeper/deposit.go`)

## Summary
Any unprivileged account can create a tokenfactory denom, deposit it on a governance proposal via `MsgDeposit`, and later attach a `DenomAllowList` to that denom that excludes the `gov` module account. When the proposal is finalized, `RefundDeposits` iterates all deposits and calls `SendCoinsFromModuleToAccount` for each one; if that call errors for any reason other than the two conditions the function explicitly pre-checks (`BlockedAddr` / `CanSendTo`), the function `panic(err)`s. A tokenfactory allow-list restriction is not covered by those pre-checks, so this is a reachable, attacker-controlled panic path inside `EndBlock`.

## Finding Description
`MsgDeposit.ValidateBasic()` only validates that the coins are well-formed and non-negative — it does not restrict which denom can be deposited: [1](#0-0) 

`AddDeposit` moves the deposited coins from the depositor to the governance module account via a generic `SendCoinsFromAccountToModule` call, with no denom allowlisting/blocklisting at deposit time: [2](#0-1) 

Anyone can permissionlessly create a tokenfactory denom (`factory/{creator}/{subdenom}`), and the creator is automatically granted "admin" privileges over that denom, including the ability to attach or change a `DenomAllowList` at any later time: [3](#0-2) [4](#0-3) 

When a proposal concludes, `RefundDeposits` iterates each depositor's record and only pre-checks `BlockedAddr` / `CanSendTo` before calling `SendCoinsFromModuleToAccount`. Any other error returned by the send call — including a tokenfactory `DenomAllowList` rejection — is not tolerated: it is treated as fatal and the function panics: [5](#0-4) 

The `IsInDenomAllowList` check (a distinct mechanism from `BlockedAddr`/`CanSendTo`) is enforced deeper in the bank send path for any coin whose denom carries the tokenfactory prefix, and it can reject sends to arbitrary addresses (including module accounts) that are not on the allow list: [6](#0-5) 

Because `RefundDeposits` only special-cases `BlockedAddr`/`CanSendTo` and not `IsInDenomAllowList` failures, a depositor can:
1. Create a tokenfactory denom (`factory/attacker/evil`) — permissionless.
2. Deposit some of that denom on any governance proposal via `MsgDeposit` — permissionless, no denom restriction.
3. Before the proposal concludes, call `MsgCreateDenom`'s companion admin action (`MsgUpdateDenom`/allow-list update path) to set a `DenomAllowList` for `factory/attacker/evil` that does not include the `gov` module account address.
4. When the proposal's deposit/voting period ends, `gov`'s `EndBlocker` calls `RefundDeposits` (on rejection) or the deposit-refund path (on pass), which iterates over ALL deposits for that proposal, including the attacker's evil-denom deposit. The `SendCoinsFromModuleToAccount` call for that denom fails with the allow-list error, and `RefundDeposits` panics.

This is analogous to the reported Teller `CollateralManager.commitCollateral` bug class: an unprivileged party injects a malicious/`revert`-able asset into a shared, loop-processed collection (here, the proposal's deposit set) that a privileged/automatic process (here, `EndBlock`'s deposit refund) must fully drain, and the malicious entry causes the whole operation to fail catastrophically rather than being isolated.

## Impact Explanation
`RefundDeposits` runs inside `gov.EndBlocker`, which is invoked unconditionally during `EndBlock` for every block in which a proposal's voting/deposit period ends. A `panic` there is not contained to a single transaction — it propagates through `EndBlock` execution. Depending on recovery handling at the app layer, this either halts block production for all validators processing that block (since `EndBlock` state transitions must be deterministic and identical across the validator set) or, if a generic recover/re-panic exists upstream, still forces a chain-wide error state for that height, since every honest validator executing the same deterministic state transition hits the same panic. This satisfies the "validator halt" / "block delay beyond 2.5 seconds" criteria: an attacker can force this at a time of their choosing by controlling when they update the allow list relative to the proposal's known voting-end time, and can also lock up legitimate co-depositors' funds in the same proposal (since `RefundDeposits` may never reach/complete for the remaining depositors if the panic halts processing entirely, or leaves proposal deposit state inconsistent).

## Likelihood Explanation
Every step is reachable by a single unprivileged account issuing normal, permitted transactions: `MsgCreateDenom` (tokenfactory), `MsgDeposit` (gov), and a denom admin allow-list update — all are standard, unprivileged message types with no special permission required beyond being the tokenfactory denom's own creator/admin. The attacker fully controls the timing of the allow-list change and the proposal's known end time (visible on-chain), making this reliably triggerable rather than probabilistic.

## Recommendation
- In `RefundDeposits` (and the analogous `DeleteAndBurnDeposits`/reject path, if similarly structured), treat *any* error from `SendCoinsFromModuleToAccount` the same way as the already-handled `BlockedAddr`/`CanSendTo` cases: skip and retain the deposit record rather than panicking, emitting an error event/log instead.
- Alternatively, validate at deposit time (`AddDeposit`) that the module account is guaranteed to remain able to receive the deposited denom for the life of the proposal — e.g., reject deposits in tokenfactory denoms that currently have (or could later gain) an allow list excluding the gov module account, or snapshot allow-list-exempt status.
- More generally, audit other `EndBlock`/`BeginBlock` code paths that iterate over user-supplied, denom-driven collections and call bank-send primitives with a bare `panic(err)`, since the tokenfactory allow-list feature introduces a new user-controlled failure mode for `SendCoins` calls that many older code paths were not written to expect.

## Proof of Concept
1. Attacker account `A` submits `MsgCreateDenom{sender: A, subdenom: "evil"}` → creates `factory/A/evil`, with `A` as admin. [4](#0-3) 
2. `A` mints some `factory/A/evil` to itself via `MsgMint`.
3. `A` submits `MsgDeposit{depositor: A, proposal_id: P, amount: [1 factory/A/evil]}` on any open governance proposal `P` (deposit or voting period). This succeeds because `AddDeposit`/`ValidateBasic` impose no denom restriction. [2](#0-1) 
4. Before proposal `P`'s voting period ends, `A` (as denom admin) sets a `DenomAllowList` for `factory/A/evil` that does not include the `gov` module account's bech32 address (an address `A` can compute deterministically since module account addresses are derived from the module name).
5. When `P`'s voting period ends, `gov.EndBlocker` calls `RefundDeposits(ctx, P)` (on pass or non-vetoed reject). Iterating deposits, when it reaches `A`'s deposit of `factory/A/evil`, `BlockedAddr`/`CanSendTo` pass (these don't check tokenfactory allow lists), but the underlying `SendCoins` call fails via `IsInDenomAllowList` because the gov module account isn't on the allow list. [6](#0-5) 
6. `RefundDeposits` panics on this non-nil error: [7](#0-6) 
7. This panic occurs deterministically for every validator processing this block's `EndBlock`, producing a chain-wide halt/crash condition at that height.

**Uncertainty:** I could not fully trace whether an upstream `recover()` in `app.go`'s block-processing (similar to the one seen in `ProcessBlock`) converts this specific `EndBlock` panic into a graceful error versus an actual consensus-halting panic, since `gov.EndBlocker` is invoked via the module manager's standard `EndBlock` rather than the custom `ProcessBlock`/`ProcessTXsWithOCCGiga` paths I was able to inspect directly. I also did not directly confirm the CLI/message path for updating an existing tokenfactory denom's allow list post-creation (only creation-time `AllowList` was directly observed in `MsgCreateDenom`); a background Devin session with full repo access should verify whether `MsgUpdateDenom` (referenced in `x/tokenfactory/client/cli/tx.go`'s command list) supports changing the allow list after creation, since that is required for the exact PoC sequence (deposit first, restrict allow-list later) though even restricting the allow-list before depositing already achieves the same panic.

func (msg MsgDeposit) ValidateBasic() error {
	if msg.Depositor == "" {
		return sdkerrors.Wrap(sdkerrors.ErrInvalidAddress, msg.Depositor)
	}
	if !msg.Amount.IsValid() {
		return sdkerrors.Wrap(sdkerrors.ErrInvalidCoins, msg.Amount.String())
	}
	if msg.Amount.IsAnyNegative() {
		return sdkerrors.Wrap(sdkerrors.ErrInvalidCoins, msg.Amount.String())
	}

	return nil
}

func (keeper Keeper) AddDeposit(ctx sdk.Context, proposalID uint64, depositorAddr sdk.AccAddress, depositAmount sdk.Coins) (bool, error) {
	// Checks to see if proposal exists
	proposal, ok := keeper.GetProposal(ctx, proposalID)
	if !ok {
		return false, sdkerrors.Wrapf(types.ErrUnknownProposal, "%d", proposalID)
	}

	// Check if proposal is still depositable
	if (proposal.Status != types.StatusDepositPeriod) && (proposal.Status != types.StatusVotingPeriod) {
		return false, sdkerrors.Wrapf(types.ErrInactiveProposal, "%d", proposalID)
	}
	if keeper.IncrementalTallyEnabled(ctx) && proposal.Status == types.StatusVotingPeriod {
		if proposal.VotingEndTime.Before(ctx.BlockTime()) || keeper.voteDelegationSnapshotFrozen(ctx, proposal) {
			return false, sdkerrors.Wrapf(types.ErrInactiveProposal, "%d", proposalID)
		}
	}

	// update the governance module's account coins pool
	err := keeper.bankKeeper.SendCoinsFromAccountToModule(ctx, depositorAddr, types.ModuleName, depositAmount)
	if err != nil {
		return false, err
	}

// RefundDeposits refunds deposits whose recipients can receive funds and deletes
// their records. Deposits for unpayable recipients remain recorded and backed by
// the governance module balance.
func (keeper Keeper) RefundDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		depositor := sdk.MustAccAddressFromBech32(deposit.Depositor)
		if keeper.bankKeeper.BlockedAddr(depositor) || !keeper.bankKeeper.CanSendTo(ctx, depositor) {
			// Retain the deposit so its record continues to account for the backing
			// module balance. Recovering a permanently unreceivable deposit requires
			// a migration.
			return false
		}

		err := keeper.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, depositor, deposit.Amount)
		if err != nil {
			panic(err)
		}

		store.Delete(types.DepositKey(proposalID, depositor))
		return false
	})
}

# Token Factory

The tokenfactory module allows any account to create a new token with
the name `factory/{creator address}/{subdenom}`. Because tokens are
namespaced by creator address, this allows token minting to be
permissionless, due to not needing to resolve name collisions. A single
account can create multiple denoms, by providing a unique subdenom for each
created denom. Once a denom is created, the original creator is given
"admin" privileges over the asset. This allows them to:

- Mint their denom to any account
- Burn their denom from any account
- Create a transfer of their denom between any two accounts
- Change the admin. In the future, more admin capabilities may be added. Admins
  can choose to share admin privileges with other accounts using the authz
  module. The `ChangeAdmin` functionality, allows changing the master admin
  account, or even setting it to `""`, meaning no account has admin privileges
  of the asset.

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}
