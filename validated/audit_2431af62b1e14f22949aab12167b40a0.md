## Analysis

The external report's core broken invariant: **a price-oracle read path that can silently return outdated/incomplete round data because the code doesn't verify round completeness, only checking the raw price value.** The Chainlink-recommended fix requires checking `answeredInRound >= roundId` (round completeness) in addition to freshness (`updatedAt`).

Hyperbridge's on-chain analog is `evm/src/utils/SimplexPaymaster.sol`, a production ERC-4337 paymaster that charges users ERC-20 tokens for gas by converting price via two Chainlink `AggregatorV3Interface.latestRoundData()` feeds. [1](#0-0) 

### Title
Missing Chainlink round-completeness check in `SimplexPaymaster._getOraclePrice` allows stale/carried-over price acceptance - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster._getOraclePrice` already migrated away from the deprecated `latestAnswer()` API to `latestRoundData()`, and it does check `answer > 0` and `block.timestamp - updatedAt <= maxOracleAge`. However, it discards the `roundId` and `answeredInRound` return values entirely, so it never verifies that the returned round is complete/current. This is exactly the residual risk Chainlink's own integration guidance calls out beyond the deprecated-function fix: a phase-changed or stalled aggregator can keep reporting an old round's price while `updatedAt` still looks "fresh enough" relative to `maxOracleAge`, silently passing both of the existing guards.

### Finding Description
`_getOraclePrice` is the single price-fetching primitive used both to price gas for every UserOperation (`_tokenPrice` → `_fetchDetails`) and to compute the swap minimum-output guard in `swapAndDeposit`: [2](#0-1) [3](#0-2) 

The check only validates:
1. `answer > 0`
2. `block.timestamp - updatedAt <= maxOracleAge`

It never checks `answeredInRound >= roundId`. Chainlink explicitly documents that during aggregator congestion, migrations, or feed pauses, `latestRoundData()` can return the *last completed* round's data (with a plausible-looking `updatedAt`) even though the *current* round has not yet answered — i.e. `answeredInRound < roundId`. Because `maxOracleAge` is a governance-set duration (up to `MAX_ORACLE_AGE = 7 days` per the code comments, since "Base/Ethereum stablecoins" heartbeats can be up to 24h), a carried-over/incomplete round can still fall inside the staleness window and be silently accepted as legitimate. [4](#0-3) 

### Impact Explanation
Both fund-moving paths in the contract depend on this single unguarded price source:
- `_fetchDetails`/`_tokenPrice` sets the ERC-20 amount charged to every UserOperation sender for gas — an incorrect/stale price directly over- or under-charges users of real ERC-20 tokens.
- `swapAndDeposit` derives `amountOutMin` for a live Uniswap V2 swap of the accrued token surplus from the same unguarded price, so a stale price weakens the on-chain slippage protection guarding treasury funds during the swap.

This falls within the bounty's "stealing or loss of funds" / "logic attacks" impact category because it is a public/permissionless (paymaster charging) and treasury-relevant (swap) code path that trusts oracle data without the completeness check that the existing `maxOracleAge`/`answer>0` guards do not substitute for.

### Likelihood Explanation
Likelihood is bounded by the fact that this requires an actual Chainlink feed staleness/round-carryover event (not attacker-controlled), and the contract's own doc comments show the developers deliberately keep "allowances and permit amounts small... bounding exposure... even against a malicious oracle," indicating partial risk acceptance already baked into the design. It is a real gap relative to Chainlink's documented integration guidance, but it is not independently attacker-triggerable without an oracle-side anomaly.

### Recommendation
In `_getOraclePrice`, decode and check `roundId`/`answeredInRound` in addition to the existing `answer > 0` and staleness checks:
```solidity
(uint80 roundId, int256 answer, , uint256 updatedAt, uint80 answeredInRound) = oracle.latestRoundData();
if (answeredInRound < roundId) revert IncompleteRound(address(oracle), roundId, answeredInRound);
```
Apply consistently to both the `nativeOracle` and each `TokenConfig.tokenOracle` reads used in `_tokenPrice` and `swapAndDeposit`.

### Proof of Concept
1. Chainlink aggregator for a registered token feed enters a stalled/phase-changed state so `latestRoundData()` returns `roundId=N`, `answeredInRound=N-1` (or similar carried-over combination), with `updatedAt` still within `maxOracleAge`.
2. `_getOraclePrice` passes both of its checks (`answer > 0`, `updatedAt` fresh enough) and returns the stale price as authoritative.
3. `_tokenPrice` computes `tokenPrice` from this stale value; every subsequent UserOperation is charged based on it via `_fetchDetails`, and `swapAndDeposit`'s `amountOutMin` is derived from the same stale value, weakening slippage protection on the treasury's swap. [5](#0-4)

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
