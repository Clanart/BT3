### Title
Index-out-of-bounds panic (crash / DoS) in Straus multiexponentiation on an empty pair list — (File: crypto/multiexp/src/straus.rs)

### Summary
Analogous to CVE-2022-0562 (a crafted input driving the parser into a null-pointer dereference inside `memcpy` → process crash), Serai's Straus multiexponentiation unconditionally indexes `groupings[0]` on the first iteration. `prep_bits` builds `groupings` with one entry per input pair, so when `pairs` is empty `groupings` is an empty `Vec`, and `groupings[0]` panics. The same `groupings[0]` dereference exists in both the constant-time `straus` and `straus_vartime`. Any `verify`/`complete`/batch path that forwards an attacker-influenced, potentially-empty pair list into `multiexp`/`multiexp_vartime`/`straus_vartime` crashes the host process — an unprivileged remote party can deny service by supplying inputs that reduce the verification statement count to zero rather than producing a handled `Err`.

### Finding Description
In `crypto/multiexp/src/straus.rs`:

- `straus` (lines 27–50): `let mut groupings = prep_bits(pairs, window);` then `for b in (0 .. groupings[0].len()).rev()` at line 35. No check that `pairs` (and hence `groupings`) is non-empty.
- `straus_vartime` (lines 52–78): identical unguarded `groupings[0]` access at line 60.

`prep_bits` (in `crypto/multiexp/src/lib.rs`, used at lines 31 and 56) maps each `(scalar, point)` pair to a bit-grouping vector; with `pairs.is_empty()` it returns `vec![]`, so `groupings[0]` is an unconditional `index out of bounds` panic. Both functions also feed `prep_tables`, which is harmless on empty input — the crash is purely the `groupings[0]` index.

This is the Rust analog of the libtiff bug: an unchecked assumption that at least one element exists before dereferencing, reachable purely through the count/shape of attacker-supplied verification inputs, not their cryptographic validity.

### Impact Explanation
A panic inside `straus`/`straus_vartime` unwinds through the calling `verify`/`complete`/`batch` API instead of returning `Err(InvalidProof)`/`false`. In a signer/validator/coordinator context (e.g., batch verification of Schnorr statements, DLEq verification aggregating attacker-controlled statement counts, or a blame/`BatchVerifier` path that ends up with an empty queue), a single crafted message — one that legitimately parses but corresponds to zero statements/pairs — crashes the signing node. Because panic occurs before any group arithmetic, it is a guaranteed crash primitive, mirroring the CVE's `S:U/.../A:H` availability-only impact (Medium severity).

### Likelihood Explanation
The bug requires a code path where a caller forwards an empty (or attacker-emptied) pair list. `prep_tables` is safe on empty input, and many callers (e.g., `SchnorrAggregate::verify`, which always appends `(-s, generator)` at `crypto/schnorr/src/aggregate.rs:144`) guarantee at least one pair. Likelihood therefore depends on whether a reachable public `verify`/batch API can produce `pairs.is_empty()` — e.g., a `BatchVerifier`/`verify_vartime` invoked over zero queued statements, or a per-input commitment loop that ends up empty when the attacker supplies zero items where the protocol allowed a variable count. Wherever that occurs, exploitation is deterministic: no race, no privileged position, just message shape control. I could not exhaustively enumerate every internal caller of `straus_vartime`/`multiexp_vartime` within the iteration budget, so the exact triggering call chain should be confirmed at the `BatchVerifier` and batch-`verify` entry points in `crypto/multiexp/src/batch.rs`, `crypto/schnorr`, and `crypto/dleq`.

### Recommendation
Return the identity element immediately when `pairs.is_empty()` at the top of `straus` and `straus_vartime` (the empty multiexponentiation is defined as identity, which is also the correct mathematical result), and/or add a debug-level `assert!(!pairs.is_empty())` at public callers so empty input is a defined result rather than a panic. More broadly, audit all `verify`/`batch` entry points that translate attacker-controlled message counts into multiexp pair lists so that `Err`/`false`, not a panic, is returned for degenerate inputs.

Concrete demonstration: `prep_bits` returns one inner `Vec<u8>` per pair (`crypto/multiexp/src/lib.rs`, invoked at `straus.rs:56`); with zero pairs the subsequent `for b in (0 .. groupings[0].len()).rev()` (`crypto/multiexp/src/straus.rs:60`) indexes element 0 of an empty vector, producing `index out of bounds: the len is 0 but the index is 0` and aborting/unwinding the thread performing verification.
