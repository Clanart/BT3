### Title
Payout OP_RETURN operator identity is self-declared and unauthenticated, letting anyone attribute a confirmed payout to an operator that never funded it - (File: circuits-lib/src/bridge_circuit/mod.rs / bridge-circuit-host/src/structs.rs / core/src/task/payout_checker.rs)

### Summary
`deposit_constant.operator_xonlypk` is derived purely from the first OP_RETURN output of the confirmed payout transaction, with no signature or other cryptographic proof that the named operator actually funded/broadcast that transaction. [1](#0-0) [2](#0-1)  Because the user's withdrawal authorization is a `SinglePlusAnyoneCanPay` Schnorr signature that only commits to the input and output-0 (the user's payout), and additional outputs like the OP_RETURN and any funding inputs are unconstrained, an unprivileged withdrawer can construct and confirm an alternate payout transaction naming an arbitrary operator's x-only pubkey while funding output 0 entirely from their own money. Any operator's own unattended automation (`PayoutCheckerTask`) then blindly trusts this chain-derived OP_RETURN attribution and issues a kickoff to claim bridge-funded reimbursement for a payout it never made.

### Finding Description
The binding that should hold is: `deposit_constant.operator_xonlypk == the operator that actually funded output 0 of the payout transaction`. In reality the code enforces only: `deposit_constant.operator_xonlypk == whatever x-only pubkey bytes appear in the first OP_RETURN output of the confirmed payout transaction`, with no check that this pubkey's owner supplied the funds.

- The user authorizes withdrawal by signing with `TapSighashType::SinglePlusAnyoneCanPay`, enforced in `parse_withdrawal_sig_params`. [3](#0-2)  This sighash type commits only to the specific input being spent and the output at the same index (output 0, the user's payout). It places no constraint on any other output, including the OP_RETURN output that names the operator, or on which entity funds and broadcasts the final transaction (`create_payout_txhandler` builds output 0, an anchor, and an OP_RETURN naming `operator_xonly_pk`, but only output 0's script/amount is signature-protected). [4](#0-3) 
- Consequently, any party in possession of the user's signature - including the withdrawer themselves - can build their own transaction spending the same withdrawal UTXO and output-0, fund it entirely with their own additional inputs (there is no requirement that a specific operator's wallet fund it), and put any x-only pubkey (an honest, uninvolved operator's key) into the OP_RETURN, then broadcast/confirm it. Because Bitcoin's UTXO model rejects a double-spend of the underlying withdrawal outpoint, this transaction can preempt the "real" operator's payout.
- Once confirmed, `Verifier::update_finalized_payouts` scans the block and records the OP_RETURN pubkey verbatim as `payout_payer_operator_xonly_pk` in the `withdrawals` table, without any cross-check against who broadcast/funded the tx. [5](#0-4) 
- The named operator's own background automation, `PayoutCheckerTask::run_once`, polls `get_first_unhandled_payout_by_operator_xonly_pk` using its own pubkey and, purely because a row exists naming it, calls `handle_finalized_payout` to build and submit a kickoff to claim reimbursement - with no verification that the operator itself created or funded that specific payout tx. [6](#0-5) [7](#0-6) 
- `deposit_constant` in the bridge circuit (both in-circuit and host-side) then commits `operator_xonlypk` taken from the same unauthenticated OP_RETURN, with no re-derivation from a signed field. [8](#0-7) [9](#0-8) 
- `Verifier::is_kickoff_malicious`, the only guard that inspects operator attribution, merely compares the kickoff's `operator_xonly_pk` to the db's `payout_payer_operator_xonly_pk` (which the attacker fully controls via the forged OP_RETURN) - by construction they match, so this check does not catch the discrepancy. [10](#0-9) 

### Impact Explanation
An operator can be automatically credited (via its own automation, or by a colluding/complicit operator) with a full reimbursement (bridge_amount from the move-to-vault UTXO/kickoff-assert-reimburse chain) for a payout it never funded, while the actual output-0 payment was funded entirely by the withdrawer's own money. This matches the Critical category "an operator reimbursed for a payout it never funded." It is repeatable per deposit/withdrawal and can target any operator whose x-only pubkey is public (all registered operators' pubkeys are public protocol data), so the blast radius spans every future withdrawal cycle.

### Likelihood Explanation
The attacker only needs: (1) their own valid `SinglePlusAnyoneCanPay` withdrawal signature (which they already control, since they are the withdrawer), (2) enough of their own BTC to fund output 0 themselves (the same amount they would have received anyway - no net cost to the attacker beyond fees), and (3) the ability to broadcast a Bitcoin transaction before the intended operator's payout confirms. No verifier/operator/aggregator credential, TLS cert, or key compromise is required. The only external dependency for the *reimbursement to be claimed* is that the named operator's automation runs unattended and doesn't cross-check its own broadcast history against on-chain OP_RETURN attribution - based on the code reviewed, `PayoutCheckerTask` performs no such cross-check, making this fully automatic and not requiring operator collusion.

### Recommendation
Bind the OP_RETURN operator identity to a value that only the actual funding operator can produce, e.g., require the operator to co-sign the payout transaction (covering the OP_RETURN output) with `SIGHASH_ALL`/`SIGHASH_SINGLE` over their own added inputs, or have the operator's kickoff/reimbursement flow independently verify (from its own wallet/broadcast records) that it actually created and funded the specific payout transaction referenced by `deposit_constant`, before automation submits a kickoff for it. In circuits-lib and bridge-circuit-host, avoid trusting an unauthenticated OP_RETURN as sole source of `operator_xonlypk`; require it to be corroborated by data that is cryptographically tied to the funder (e.g., a signed commitment or an input which the operator controls).

fn host_deposit_constant(
    input: &BridgeCircuitInput,
) -> Result<DepositConstant, BridgeCircuitHostParamsError> {
    let first_op_return_output = get_first_op_return_output(&input.payout_spv.transaction)
        .ok_or(BridgeCircuitHostParamsError::InvalidOperatorPubkey)?;

    let deposit_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&input.sp.storage_proof_deposit_txid).map_err(|e| {
            BridgeCircuitHostParamsError::StorageProofDeserializationError(e.to_string())
        })?;

    let round_txid = input.kickoff_tx.input[0]
        .previous_output
        .txid
        .to_byte_array();

    let kickoff_round_vout = input.kickoff_tx.input[0].previous_output.vout;

    let operator_xonlypk: [u8; 32] = parse_op_return_data(&first_op_return_output.script_pubkey)
        .ok_or(BridgeCircuitHostParamsError::InvalidOperatorPubkey)?
        .try_into()
        .map_err(|_| BridgeCircuitHostParamsError::InvalidOperatorPubkey)?;

    let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();

    Ok(deposit_constant(
        operator_xonlypk,
        input.watchtower_challenge_connector_start_idx,
        &input.all_tweaked_watchtower_pubkeys,
        deposit_value_bytes,
        round_txid,
        kickoff_round_vout,
        input.hcp.genesis_state_hash,
    ))
}

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
