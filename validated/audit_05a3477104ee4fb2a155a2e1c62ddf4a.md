Delegating a wallet to `SolverAccount` via EIP-7702 is permissionless — anyone can sign an EIP-7702 authorization pointing their own EOA at the canonical `SolverAccount` bytecode and start bidding as a "solver" [1](#0-0) [2](#0-1) . There is no admin allowlist gating who can become a weighted price contributor, so this is an unprivileged-attacker-reachable path, not a "malicious relayer/operator" exclusion.

### Title
Liquidity-weighted Phantom price snapshot can be skewed by a solver temporarily inflating its spot balance - (File: `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`)

### Summary
`aggregatePhantomBids` weights each solver's quoted output price by a **spot** balance read (`balanceOf` + ERC-4626 `maxWithdraw`) taken via a single `eth_call` at aggregation time [3](#0-2) . `weightedMedian` gives a bidder whose weight reaches half the total weight full control of the reported price, regardless of what other, legitimately-liquid solvers quoted [4](#0-3) . This snapshot's `medianPrice` is then consumed directly to price real `IntentGateway` orders that move real user funds [5](#0-4) . This is the same broken invariant as the C4 report: a value that determines a counterparty's economic outcome is read from mutable, attacker-controlled spot state instead of a value that is expensive/impossible for the beneficiary to manipulate at will.

### Finding Description
`getTotalSolverBalance` sums a solver's raw ERC-20 balance and its ERC-4626 `maxWithdraw` across configured vaults for the output token, read once via `eth_call` at "latest" when the indexer processes the `PhantomBidWindowExhausted` event [3](#0-2) . This spot balance becomes the `weight` fed into `weightedMedian`, and the weighted-median algorithm returns the price of whichever bidder's cumulative weight first reaches half the total — i.e. a single dominant-weight bidder fully determines the output price [6](#0-5) , confirmed by the test showing a 100-weight bid overriding two 1-weight bids [7](#0-6) .

Because any EOA can permissionlessly EIP-7702-delegate to `SolverAccount` and submit a bid [1](#0-0) , an attacker only needs to: (1) delegate an EOA, (2) submit a lowball bid for the phantom order (quoting less `tokenB` output than a fair price), and (3) transiently hold/borrow a large balance of `tokenB` (or an ERC-4626 position redeemable for it) on the destination chain at the moment the indexer's `eth_call` fires, so their `weight` dominates. The resulting `PhantomOrderPriceSnapshot.medianPrice` is written on-chain-derived state used verbatim by `PhantomSnapshotIntentQuoteStrategy.quoteSnapshot`, which computes real users' `amountOut`/`amountIn` for actual `IntentGateway` orders with no sanity bound against the raw `lowestPrice`/`highestPrice` spread or a minimum distinct-weight threshold [8](#0-7) . `validateSnapshot` only checks that fields are non-zero/well-formed — it never checks weight concentration, staleness beyond `snapshotTime` well-formedness, or requires more than one contributing solver's weight to be meaningfully represented [8](#0-7) .

This mirrors the C4 Particle finding precisely: the "fee" there was the Uniswap `feeGrowthInside` snapshot, manipulable by the party (lender) who could unilaterally add liquidity to dominate its share; here the "price" is a liquidity-weighted median, manipulable by the party (solver) who can unilaterally inflate its measured balance to dominate its weight — in both cases the counterparty (borrower / real swap user) is forced into an economically worse outcome determined by a spot value the beneficiary controls.

### Impact Explanation
Real users quoting via `phantom_snapshot` strategy receive `amountOut`/`amountIn` computed directly from the manipulated `medianPrice` [9](#0-8) , and are expected to use these values "directly as the order's `inputs` and `output.assets` — no further fee or slippage adjustment is required" per SDK docs. A skewed low price causes real cross-chain intent orders to be placed with less output than a fair market rate would provide, i.e. **loss of funds for the ordering user, captured by the manipulating solver** on subsequent unrelated fills priced off the stale, skewed snapshot. This satisfies the bounty's "logic attacks" / "wrong beneficiary or amount" impact category.

### Likelihood Explanation
Comparable to the source report: judged Medium because the attack is possible but requires real capital to hold the inflated balance for an indeterminate window (the indexer processes the event asynchronously, not necessarily same-block, so a single-block flash loan is unlikely to suffice — the attacker likely needs actual borrowed/owned capital for some duration). It requires no privileged role, no relayer/prover/admin collusion, and no consensus assumptions — only permissionless solver delegation and a bid, making it a legitimate unprivileged-attacker path, but the capital-cost-vs-profit economics bound its practicality the same way the original C4 discussion concluded.

### Recommendation
Do not let a single bidder's spot balance dominate the weighted median unconditionally. Options: cap any single solver's weight contribution (e.g., at some fraction of total weight), require a minimum number of distinct solvers before writing/consuming a snapshot, average balance over multiple blocks/time rather than one spot read, or require solvers to post a bond/skin-in-the-game proportional to claimed weight (e.g., an actual filled amount) rather than a redeemable-on-demand balance snapshot.

### Proof of Concept
1. Attacker generates a fresh EOA and EIP-7702-delegates it to the canonical `SolverAccount` address (permissionless, `DelegationService.setupDelegation`) [1](#0-0) .
2. Attacker observes an active `PhantomOrder` and submits a signed bid quoting a lowball `tokenB` output amount, satisfying `isVerifiedSolverBid`'s signature/session checks [10](#0-9) .
3. Before/around the time the `PhantomBidWindowExhausted` handler fires its RPC sweep, attacker acquires a large `tokenB` balance (borrow, temporary loan, or wraps existing capital into a configured ERC-4626 vault so `maxWithdraw` reflects it) on the destination chain.
4. `getTotalSolverBalance` reads this inflated balance via `eth_call`, giving the attacker's quote a dominant `weight` in `aggregatePhantomBids` [3](#0-2) ; `weightedMedian` returns the attacker's lowball price [4](#0-3) .
5. The skewed `PhantomOrderPriceSnapshot.medianPrice` is persisted and served by `_queryLatestPhantomOrderPriceSnapshot`; every subsequent `quoteIntent()` call on the `USDC↔cNGN` pair via `phantom_snapshot` strategy computes `amountOut = netAmountIn * medianPrice / standardAmount` off this skewed value [11](#0-10)  until the next snapshot is written, causing real users placing orders on that quote to receive less output than fair value.

// Liquidity-weighted median of solver quotes. Each quote's influence is proportional to `weight` —
// the solver's total balance for the output token across native + vault venues — so a solver that
// can actually deliver size moves the price more than one quoting on thin liquidity. Returns the
// lower weighted median: the smallest price whose cumulative weight reaches half of the total.
// Zero-weight quotes contribute nothing; if every weight is zero it falls back to the unweighted
// median so a price is still reported.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

// Sums the solver's redeemable balance of a single token on its destination chain: the raw ERC-20
// balance plus any ERC-4626 vault positions wrapping it.
async function getTotalSolverBalance(
	evmRpcUrl: string,
	chain: string,
	token: string,
	solver: string,
	yieldVaults: YieldVaultMap,
): Promise<bigint> {
	const padded = solver.replace("0x", "").padStart(64, "0")
	const raw = await ethCallUint(evmRpcUrl, token, `0x70a08231${padded}`) // balanceOf(address)
	const vaults = yieldVaults[chain]?.[token.toLowerCase()] ?? []
	const vaultBalances = await Promise.all(
		vaults.map((v) => ethCallUint(evmRpcUrl, v, `0xce96cb77${padded}`)), // maxWithdraw(address)
	)
	return vaultBalances.reduce((acc, b) => acc + b, raw)
}
