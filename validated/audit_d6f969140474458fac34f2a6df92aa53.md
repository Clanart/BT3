### Title
Operator attribution for a payout is based solely on an unauthenticated OP_RETURN pubkey, letting anyone credit an arbitrary operator for a payout it never funded - (File: core/src/verifier.rs)

### Summary
`Verifier::update_finalized_payouts` attributes a payout to whichever operator's x-only pubkey appears in the payout transaction's OP_RETURN output, with no check that this operator actually supplied any funds to the transaction. Because the mandatory user withdrawal signature uses `SinglePlusAnyoneCanPay` (which commits only to input 0 and output 0), the OP_RETURN output (output index 2) is completely unconstrained, so anyone who constructs the final payout transaction — including the withdrawer/attacker themselves — can name any operator's pubkey there.

### Finding Description
The claimed binding is: `payout_payer_operator_xonly_pk` (stored for a `citrea_idx`/withdrawal) should equal the xonly pubkey of the operator whose own BTC actually funded that withdrawal's payout.

In `update_finalized_payouts` (`core/src/verifier.rs:2283-2354`), for every payout tx matched to a withdrawal UTXO the verifier does:
```
let operator_xonly_pk = op_return_output
    .and_then(|output| parse_op_return_data(&output.script_pubkey))
    .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());
``` [1](#0-0) 
and persists it via `update_payout_txs_and_payer_operator_xonly_pk` with no further validation that the named operator contributed any input to the transaction.

`Verifier::is_kickoff_malicious` later trusts this value directly:
```
if operator_xonly_pk != kickoff_data.operator_xonly_pk {
    ... return Ok(true);
}
``` [2](#0-1) 

The root cause is that the OP_RETURN carrying the operator pubkey is never cryptographically bound to the withdrawer's authorization. The withdrawer's signature is required to use `TapSighashType::SinglePlusAnyoneCanPay`, enforced in `parse_withdrawal_sig_params`:
```
if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
    return Err(...)
}
``` [3](#0-2) 
`SIGHASH_SINGLE | ANYONECANPAY` commits only to the signed input and the output at the *same index* (index 0, the user payout output). It does **not** cover the anchor output or the OP_RETURN output (`create_payout_txhandler` places the operator pubkey OP_RETURN at output index 2):
```
.add_output(output_txout)                    // index 0 - covered by SINGLE
.add_output(anchor_output(...))              // index 1 - NOT covered
.add_output(op_return_txout)                 // index 2 - NOT covered
``` [4](#0-3) 

Consequently, the attacker (an unprivileged user who called Citrea's `withdraw`, chose the withdrawal UTXO bytes, and produced the required `SinglePlusAnyoneCanPay` signature per the threat-model rules) can construct and broadcast the completing payout transaction *before any operator does*, funding the payout output entirely from their own UTXO and appending an OP_RETURN naming an arbitrary honest operator's xonly pubkey. No signature check, storage-proof check, or database uniqueness constraint ties the OP_RETURN pubkey to whoever actually funded the transaction — `Verifier::is_deposit_valid`, `SECP.verify_schnorr` (only checks the input-0 signature, unrelated to OP_RETURN), and `is_kickoff_malicious` all operate purely on the attacker-controlled OP_RETURN field.

Exploit flow:
1. Attacker calls Citrea `withdraw()` for a withdrawal UTXO they fully fund and control, producing a valid `SinglePlusAnyoneCanPay` signature over input 0 / output 0.
2. Attacker (not any operator) constructs the payout transaction themselves, adding whatever inputs/outputs they like beyond index 0/1, including an OP_RETURN naming operator A's xonly pubkey, and broadcasts/confirms it.
3. `update_finalized_payouts` parses this OP_RETURN and records `payout_payer_operator_xonly_pk = A` for that withdrawal.
4. `PayoutCheckerTask::run_once` for operator A (`core/src/task/payout_checker.rs:41-79`) picks up the "unhandled payout" attributed to A via `get_first_unhandled_payout_by_operator_xonly_pk`, and calls `Operator::handle_finalized_payout`, which allocates a kickoff connector and starts the reimbursement flow (`core/src/operator.rs:839-885`) for a payout A never funded.
5. `is_kickoff_malicious` will find `operator_xonly_pk == kickoff_data.operator_xonly_pk` (both equal A), so the kickoff is deemed non-malicious and verifiers will not challenge it, letting A eventually claim `Reimburse` funds (`create_reimburse_txhandler`, `core/src/builder/transaction/operator_reimburse.rs:341-385`) from the bridge's collateral.

### Impact Explanation
Operator A is credited/started on a reimbursement path (kickoff → challenge-timeout → reimburse) for a withdrawal it never funded, effectively an unauthorized claim on bridge/collateral funds. This matches the Critical category "an operator reimbursed for a payout it never funded." The attack is repeatable per withdrawal and can be aimed at any operator by simply changing the OP_RETURN bytes; it costs the attacker only their own withdrawal amount (which they get back to themselves) plus Bitcoin fees, and requires no operator private keys, verifier collusion, or majority hashrate.

### Likelihood Explanation
Preconditions are all within the declared unprivileged attacker capability set: choosing withdrawal UTXO bytes, choosing a Schnorr signature and its sighash flag, calling Citrea `withdraw`, and broadcasting arbitrary Bitcoin transactions/OP_RETURNs. No verifier, operator, security-council or aggregator privilege is required. The `SinglePlusAnyoneCanPay` requirement is a hard, standard requirement of the protocol (enforced in `parse_withdrawal_sig_params`), so this is not a misconfiguration — it's an intrinsic property of the currently mandated sighash type combined with unchecked OP_RETURN trust in `update_finalized_payouts`. Feasibility is high and fully reproducible on regtest with no mainnet or live Citrea dependency (the `MockCitreaClient`/`internal_finalized_payout` test RPC path in `core/src/rpc/operator.rs:373-421` shows the full flow is already exercised in existing tests).

### Recommendation
Bind the operator attribution cryptographically to the actual funding operator instead of trusting a free-form OP_RETURN field:
- Require the OP_RETURN output (or an equivalent commitment) to be covered by the withdrawer's signature (e.g., require `SIGHASH_ALL` or a sighash type that commits to all outputs, or have the withdrawer pre-commit to the intended operator's pubkey off-chain as part of the message that's signed and forwarded).
- Alternatively/additionally, in `update_finalized_payouts`, verify that the operator named in the OP_RETURN actually contributed one of the additional (non-index-0) transaction inputs, e.g., by checking that at least one input's previous output belongs to a known operator-controlled UTXO/wallet, before recording `payout_payer_operator_xonly_pk`.
- Reject payout txs where the OP_RETURN pubkey cannot be tied to a signature/commitment made by that specific operator.
