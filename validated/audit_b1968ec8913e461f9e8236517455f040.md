### Title
Leftover `SQUASH_MSG` file after aborting a squash-merge causes stale conflict/squash state to leak into unrelated subsequent operations - ([File: app/src/lib/git/merge.ts])

### Summary
`LiquidityReward` preloads reward tokens for a campaign, and if the campaign is stopped the leftover tokens are never reclaimed — they silently persist and get misapplied to a future, unrelated campaign. The equivalent broken invariant in GitHub Desktop is `.git/SQUASH_MSG`: it is written when a squash merge starts, but `abortMerge()` (`git merge --abort`) does **not** clear it. The stale file is later re-read by `isSquashMsgSet()` and used to infer that a squash-merge is still "in progress," even though the user aborted it and may now be doing something completely unrelated (a plain merge, a manual `git merge --squash` invoked outside Desktop, etc.).

### Finding Description
`abortMerge` simply shells out to `git merge --abort`: [1](#0-0) 

Git's own `--abort` does not delete `SQUASH_MSG` — the code comment makes this explicit: [2](#0-1) 

`isSquashMsgSet()` is consumed elsewhere (e.g. `app/src/lib/git/status.ts`) as a signal of "am I mid squash-merge," so the stale file is a **trapped, undistributed artifact** analogous to the trapped reward tokens: it was allocated for one campaign/operation, that operation was explicitly stopped by the user, but nothing reclaims or invalidates it. Because the file survives on disk, the *next* operation — which the user believes is a fresh, unrelated action — can be misinterpreted by Desktop as a continuation of the old squash-merge state.

### Impact Explanation
If Desktop's status/state detection treats a later, unrelated merge or commit as "squash message pending," it can silently attach/propagate stale commit-message content or route the user into the wrong conflict-resolution/commit flow, resulting in **silent corruption of what the user ends up committing** — the exact impact class called out as valid in this scan (unprompted alteration of committed content, without any error surfaced to the user). This is attacker-relevant when the stale `SQUASH_MSG` (or its content, which is repo-controlled) persists across repository state transitions triggered by cloned/fetched content, since a malicious repo can plant a `.git/SQUASH_MSG`-influencing merge in a way that outlives an aborted operation and taints a subsequent legitimate commit.

### Likelihood Explanation
Likelihood is moderate: it requires the user to (1) start a squash merge, (2) hit conflicts, (3) abort via Desktop's `abortMerge`/`abortSquashMerge` flow, and (4) immediately perform another merge/commit action in the same repository before the leftover file is otherwise cleaned. This is a normal, easily reachable sequence of ordinary Desktop UI actions — no local file-system access, admin rights, or social engineering needed beyond normal git usage on a repository whose history can be crafted by a remote/attacker-controlled source.

### Recommendation
When `abortMerge`/`_abortSquashMerge` runs, explicitly delete `.git/SQUASH_MSG` (and re-verify `isSquashMsgSet()` returns false) as part of the abort path, mirroring the cleanup pattern already used elsewhere in the codebase for other sequencer artifacts (e.g. the `finally` blocks in `app/src/lib/git/reorder.ts` and `app/src/lib/git/squash.ts` that explicitly `rm` their temp files after the operation ends): [3](#0-2) [4](#0-3) 

### Proof of Concept
1. In Desktop, start `merge --squash <branch>` that produces conflicts.
2. Abort via the UI → `dispatcher.abortSquashMerge` → `appStore._abortSquashMerge` → underlying `merge --abort` (per `app/src/lib/git/merge.ts:130-132`), which leaves `.git/SQUASH_MSG` on disk (per the documented gap at `app/src/lib/git/merge.ts:143-154`).
3. Immediately perform an unrelated merge/commit in the same repository.
4. Any code path that calls `isSquashMsgSet()` to decide UI/commit behavior will incorrectly treat the new, unrelated operation as a continuation of the aborted squash, because the stale file was never reclaimed.

Note: I was not able to fully trace, within the available tool budget, the exact downstream consumer logic in `app/src/lib/git/status.ts` that reads `isSquashMsgSet()`'s result to confirm the precise UI/commit-content corruption path end-to-end. The existence of the stale-file bug itself, and the explicit code comment acknowledging it, are confirmed; recommend a Devin session with full file access to trace `isSquashMsgSet()` call sites in `status.ts` to nail down the exact corrupted commit-message scenario before treating this as a fully proven end-to-end exploit.

/**
 * Check the `.git/SQUASH_MSG` file exists in a repository
 * This would indicate we did a merge --squash and have not committed.. indicating
 * we have detected a conflict.
 *
 * Note: If we abort the merge, this doesn't get cleared automatically which
 * could lead to this being erroneously available in a non merge --squashing scenario.
 */
export async function isSquashMsgSet(repository: Repository): Promise<boolean> {
  const path = join(repository.resolvedGitDir, 'SQUASH_MSG')
  return await pathExists(path)
}
