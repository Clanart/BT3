Based on my investigation, I found a genuine local analog to the Malt bug-class (a Solidity-0.8 checked-arithmetic guard placed in a position where it no longer protects the invariant it appears to protect) in the Tron variant of the IntentGateway's escrow-withdrawal path.

### Title
Escrow debit performed after external transfer in `withdraw()` allows a stale-ledger read during reentrancy - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Malt report's core lesson is that a Solidity-0.8 checked arithmetic operation, when relied upon as the *only* correctness guard for a value that has already been externally observed/spent, does not protect against the underlying invariant violation — it only reverts *after* the damage-causing side effect. The same anti-pattern exists in the Tron fork of `IntentGatewayV2`.

### Finding Description
In `withdraw()`, the escrowed-token/native transfer is executed **before** the escrow ledger (`_orders[commitment][token]`) is decremented, and the pre-check only verifies the ledger entry is non-zero — not that it covers the requested `amount`: [1](#0-0) 

Compare this to the hardened mainline EVM implementation, `_withdraw()` in `IntentsBase.sol`, which computes and writes the reduced escrow value **before** performing the external transfer (classic checks-effects-interactions ordering): [2](#0-1) 

In the Tron version, `_orders[body.commitment][token] -= amount` is a checked (Solidity ^0.8.24) subtraction that will only revert if `amount` exceeds the recorded escrow — but that revert happens **after** `beneficiary.call{value: amount}("")` or `token.call(...transfer...)` has already executed. This function is reached only via `onAccept` (for `RedeemEscrow`/`RefundEscrow` requests, gated by `onlyHost` + `authenticate`) and `onGetResponse` (gated by `onlyHost`), i.e. it is driven by verified cross-chain ISMP request/response delivery: [3](#0-2) [4](#0-3) 

Because the native-token branch uses a raw `.call{value: amount}("")` to an attacker-controlled `beneficiary` address *before* the ledger is updated, a malicious beneficiary contract can re-enter the gateway during that callback while `_orders[commitment][token]` still holds its pre-debit (stale) value. Any other externally reachable function that reads or mutates `_orders[commitment][token]` for that same commitment (e.g. escrow amount checks in `cancelSameChain`/`fillOrder` style paths that key off the same mapping) would observe the un-decremented balance during the reentrant window.

### Impact Explanation
This corrupts the exact value `_orders[commitment][token]`, which is the single source of truth for how much of a given token is still escrowed and payable for an order. Since the contract's token balance is pooled across all commitments (it is not a segregated-vault design), a stale read during reentrancy can be leveraged to authorize a second payout against the same escrow entry before it is finally zeroed/decremented, i.e., unauthorized double-settlement of the same escrow. This falls squarely under the bounty's "double-claim/double-settlement" and "loss of funds" categories, since it is reachable through a fully-verified, unprivileged cross-chain message flow — the attacker only needs to be the legitimate `beneficiary` (solver or refund recipient) of one order and does not need a malicious relayer, prover, or admin.

### Likelihood Explanation
Likelihood is moderate rather than high: the transfer-then-debit ordering is confirmed by direct code reading, and the entrypoints (`onGetResponse`, `onAccept`) are reachable by any relayer delivering a normal, correctly-proven ISMP message — no privileged actor is required. However, I was not able to fully trace, within the remaining investigation budget, the exact secondary function on this contract that reads/writes `_orders[commitment][token]` and is reachable synchronously from within the native-token reentrant callback (the natural candidates are gated `onlyHost` and thus not directly reenterable by the attacker's own call). This is the one piece of uncertainty I could not close out: confirming a concrete, currently-callable secondary entrypoint that consumes the stale escrow value during the reentrant window is necessary to fully prove exploitability end-to-end, and should be the first thing a follow-up review resolves.

### Recommendation
Rewrite `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to follow strict checks-effects-interactions, matching `IntentsBase._withdraw()`:
1. Validate `amount <= _orders[commitment][token]` explicitly (don't rely solely on the post-transfer checked subtraction to catch over-withdrawal).
2. Compute and write the decremented escrow value to storage *before* performing the native/ERC-20 transfer.
3. Add a reentrancy guard on `withdraw`/`onAccept`/`onGetResponse` as defense in depth, since native-token transfers to arbitrary beneficiaries are unavoidable in this design.

### Proof of Concept
1. Attacker places (or is designated beneficiary/solver of) an order with a native-token (`address(0)`) escrow leg, and is a contract with a `receive()`/fallback that re-enters the gateway.
2. Hyperbridge relays a legitimately-proven `RedeemEscrow`/`RefundEscrow` request (or the corresponding GET response) for this commitment, invoking `onAccept`/`onGetResponse` → `withdraw(body, ...)`.
3. Inside the loop, `_orders[commitment][token]` is checked only for non-zero, then `beneficiary.call{value: amount}("")` sends the escrowed ETH to the attacker's contract — *before* `_orders[commitment][token] -= amount` runs.
4. During the callback triggered by that ETH transfer, the attacker's contract attempts to trigger any other externally-reachable path in the gateway that consumes `_orders[commitment][token]` while it still reflects the pre-debit value, aiming to extract value twice against the same escrow entry before the first call's decrement finalizes.
5. Confirming step 4 requires identifying a concrete non-`onlyHost` function that reads/mutates the same mapping entry and is reachable from the reentrant context — this is the remaining verification gap noted above.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
