### Title
Future-dated oracle timestamp bypasses staleness gating in `oracle-timestamp-fresh` - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`oracle-timestamp-fresh` is the staleness-gating check used by `price-resolve` (the function `liquidate` and `borrow` depend on for every collateral/debt USD valuation). When a price feed's reported timestamp is greater than `stacks-block-time` (i.e., a future timestamp), the function sets `delta` to `u0` instead of computing an actual staleness value, which unconditionally satisfies `(<= delta max-staleness)`. This means a feed with a timestamp ahead of the chain's current time is always treated as maximally fresh, regardless of how old (or manipulated) the underlying price actually is.

### Finding Description
`price-resolve` gates every price used for collateral/debt valuation with:
```clarity
(asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
          ERR-ORACLE-INVARIANT)
``` [1](#0-0) 

`oracle-timestamp-fresh` is defined as:
```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
``` [2](#0-1) 

This is the analogous safety gate to the Chainlink-freshness check in the referenced report, but it has an inverted-condition flaw: instead of treating `ts > stacks-block-time` (a future timestamp, which should never legitimately occur and is itself a red flag) as suspicious/stale, the code forces `delta = u0`, the value that represents "perfectly fresh." Since `ts` is attacker- or feed-supplied (Pyth `publish-time` written into the storage contract by whoever calls `verify-and-update-price-feeds`/`write-feeds`, or DIA's timestamp converted from milliseconds), any published price whose timestamp is even slightly ahead of the market contract's view of `stacks-block-time` (which can legitimately drift due to block-processing timing) automatically defeats the staleness check that is supposed to protect `liquidate`/`borrow` from using outdated valuations.

The monotonic check `(>= ts prev)` is still enforced, so this doesn't allow arbitrarily old timestamps to be replayed, but it does allow a timestamp that is only nominally "newer" (e.g., off-by-a-few-seconds due to clock skew or a lagging feed publisher) to bypass the intended staleness bound entirely, since `delta` is forced to `0` rather than reflecting the real (potentially large, if `stacks-block-time` is behind for any reason, or if a stale feed publishes a timestamp that races ahead of the market's cached clock) discrepancy.

### Impact Explanation
Because `price-resolve` feeds directly into `get-notional-evaluation`, `total-collateral-usd`/`total-debt-usd`, and ultimately `current-ltv` in `liquidate` [3](#0-2) , a defeated staleness gate can let the protocol accept a price that should have been rejected as stale, producing an incorrect health-factor/LTV verdict. Depending on price direction, this can either (a) block a legitimately liquidatable position from being liquidated (temporary freezing of funds/insolvency risk, mirroring the original report's impact), or (b) allow a borrower to be liquidated or to over-borrow against a stale valuation. This lands on **High/Critical — temporary freezing of funds or protocol insolvency risk**, consistent with the scope's definition.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires a price feed whose `publish-time` timestamp is ahead of the market contract's `stacks-block-time` reference, which can occur due to routine clock/block-processing skew between Pyth/DIA publishers and the Stacks chain, not just adversarial action. This does not require any third-party oracle to report a materially wrong *value* — only a timestamp slightly ahead of the chain's clock — so it is a logic bug in this code's gating condition rather than bad third-party data.

### Recommendation
When `ts > stacks-block-time`, treat the feed as invalid/not-fresh (or clamp using an appropriate future-timestamp guard with its own explicit check) instead of forcing `delta = u0`. For example:
```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (and
    (<= ts stacks-block-time)
    (<= (- stacks-block-time ts) max-staleness)
    (>= ts prev)))
```
This ensures a future-dated timestamp is rejected rather than treated as maximally fresh.

### Proof of Concept
1. A price feed (Pyth or DIA) is written via `write-feeds`/`call-pyth`/`call-dia` with a `publish-time`/timestamp value `ts` that is 1 second ahead of the market contract's `stacks-block-time` (plausible due to normal clock drift between the oracle publisher and the Stacks chain, or a slightly fast-forward feed).
2. `oracle-timestamp-fresh` computes `delta = u0` because `ts > stacks-block-time`, so `(<= delta max-staleness)` is trivially true regardless of the real staleness of the underlying price.
3. `price-resolve` accepts the price and updates `last-update` to this future `ts`.
4. `liquidate` or `borrow` proceeds using this price for `total-collateral-usd`/`total-debt-usd`, even though the staleness gate that should have bounded acceptable price age was bypassed, potentially leading to an incorrect health-factor verdict at the exact moment a real check should have failed.
