### Title
Blame proof generated before PoP verification leaks ECDH shared key, enabling decryption of a victim's secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The sopel-weather advisory is a secret-leakage bug: an API key is exposed to a public channel when a downstream dependency misbehaves. The Serai analog lives in PedPoP's blame mechanism. `KeyMachine::calculate_share` returns an `EncryptionKeyProof` (which contains the raw ECDH shared key for a message) before the message's proof-of-possession is ever verified. A malicious sender can copy a victim's per-message encryption key, attach a garbage ciphertext and an invalid PoP, and cause an honest recipient to publish a blame proof that decrypts the victim's secret-share message to everyone.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs:476-499`, `calculate_share` iterates over shares, calling `self.encryption.decrypt(...)` which both decrypts the message *and* unconditionally constructs an `EncryptionKeyProof` revealing `key = ecdh(enc_key, msg.key)` (`crypto/dkg/pedpop/src/encryption.rs:487-499`). The PoP (`msg.pop`) is only queued into the `BatchVerifier` (encryption.rs:479-485) and checked at `batch.verify_with_vartime_blame()` (lib.rs:493).

However, if the decrypted bytes fail `C::F::from_repr` at lib.rs:480-482, the function returns immediately via `ok_or_else`/`?` with `PedPoPError::InvalidShare { blame: Some(blame) }` — the batch verification, including the PoP check, never runs. The caller in `processor/src/key_gen.rs:419-425` then serializes this blame into `ProcessorMessage::InvalidShare`, publishing the ECDH shared key.

`msg.key` is a fully attacker-controlled group element read via `EncryptedMessage::read`. The comment at encryption.rs:84-90 describes exactly this attack (Eve copying Alice's key `X` so Bob's blame reveals `bX`, decrypting Alice's message) and states the PoP exists to prevent it. But because the `from_repr` error path emits the proof before the PoP is verified, the mitigation is bypassed. Eve copies the `key` field `X` from Alice's `EncryptedMessage` to Bob (shares are broadcast via the coordinator/tributary), submits `{key: X, pop: <invalid>, msg: <garbage>}`. With probability ~1/2 the ChaCha-decrypted garbage fails `from_repr`, triggering the early return with a published `EncryptionKeyProof` containing `b·X` — the exact key needed to decrypt Alice's secret share to Bob.

### Impact Explanation
The published `EncryptionKeyProof.key` is the plaintext ECDH shared point. Combined with Alice's publicly-broadcast `EncryptedMessage`, any observer can run `cipher(context, b·X)` (encryption.rs:101-133) and recover Alice's secret share contribution to Bob. This leaks secret-share material that the protocol explicitly designs blame to never expose (spec "Distributed Key Generation.md" §Blame). Repeated across senders/attempts, leaked shares reduce the threshold security of the resulting `ThresholdKeys`.

### Likelihood Explanation
Requires only a DKG participant sending one malformed message — fully within the unprivileged-input model (untrusted bytes into `EncryptedMessage::read`/`calculate_share`). Success is probabilistic per attempt (~50% that decrypted garbage is non-canonical), and each DKG session offers many sender/recipient pairs to target.

### Recommendation
Verify `msg.pop` synchronously inside `Encryption::decrypt` (or before emitting the `EncryptionKeyProof` on any error path), and return `blame: None` when the PoP is invalid — matching the `BatchId::Decryption` → `None` mapping already used at lib.rs:495. Alternatively, delay constructing the `EncryptionKeyProof` until the PoP has been batch-verified.

### Proof of Concept
1. Honest Alice runs `generate_secret_shares`, broadcasting `EncryptedMessage { key: X, pop, msg }` to Bob.
2. Malicious Eve (a DKG participant) reads Alice's message, extracts `X`, and sends Bob `EncryptedMessage { key: X, pop: random_invalid_sig, msg: random_bytes }`.
3. Bob's `calculate_share` calls `decrypt`, producing `(garbage_bytes, EncryptionKeyProof { key: b·X, dleq })`; `from_repr` fails → returns `InvalidShare { blame: Some(proof) }` before the PoP batch check runs.
4. Bob's processor emits `ProcessorMessage::InvalidShare` with the serialized proof. Any observer computes `cipher(context, proof.key)` and XORs it against Alice's `msg` ciphertext, recovering Alice's secret share for Bob — material blame was designed never to reveal.
