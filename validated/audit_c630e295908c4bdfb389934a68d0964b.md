### Title
Fee-on-transfer/deflationary reward tokens allow reward accounting inflation via `donateRewards` - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool._provisionReward` credits `historicalRewards` and `rewardPerTokenStored` using the caller-supplied `_amountReward` parameter instead of the actual tokens received by the contract. Any unprivileged account can call the permissionless `donateRewards` function with a fee-on-transfer/deflationary token that is already registered as a reward token, causing the pool's internal reward accounting to exceed its real token balance.

### Finding Description
`donateRewards` has no access control (unlike `queueNewRewards`, which is `onlyManager`): [1](#0-0) 

It calls `_provisionReward`, which performs `safeTransferFrom(msg.sender, address(this), _amountReward)` and then unconditionally adds the full `_amountReward` to `historicalRewards` and factors it into `rewardPerTokenStored`, without checking the pool's actual balance delta: [2](#0-1) 

`SafeERC20.safeTransferFrom` only verifies that the call succeeded (and optionally that the return value is true/absent); it does not verify that the recipient's balance increased by the requested amount. For a deflationary/fee-on-transfer ERC20 registered as `_rewardToken`, an attacker can call `donateRewards(largeAmount, feeToken)` while only holding/approving `largeAmount` nominal tokens; the pool actually receives `largeAmount - fee`, but `rewardPerTokenStored` (and thus every user's `earned()`) is computed as if the pool received the full `largeAmount`. As the majority (or sole) staker, the attacker can then call `getReward` and drain more of the token than the pool actually holds, leaving other stakers unable to claim their true `earned()` balance — `IERC20(rewardToken).safeTransfer` will eventually revert or leave dust once the real balance is exhausted, but the attacker who claims first gets an outsized share, socializing the shortfall onto remaining stakers.

No existing modifier (`onlyManager`, `updateReward`, `onlyMasterMagpie`) prevents this because `donateRewards` deliberately allows any caller for legitimate donation purposes, and there is no balance-based accounting check anywhere in the reward provisioning path.

### Impact Explanation
This corresponds to the Backing invariant violation described: `rewardPerTokenStored`/`historicalRewards` no longer reflect the pool's real token holdings, enabling the attacker to over-claim relative to actual deposits and causing insolvency/fund loss for the remaining stakers of that reward token pool. This matches the Immunefi "theft of user funds" / "protocol insolvency" impact class, scoped to the affected reward token.

### Likelihood Explanation
Requires only that a fee-on-transfer/deflationary token be registered as a reward token for the pool (a common occurrence in DeFi reward ecosystems, and explicitly listed as a precondition here) and that the attacker holds a staking position (ideally a majority share) to capture the inflated accounting via `getReward`. No privileged role is needed — `donateRewards` is intentionally open to any caller. The attack is repeatable each time new reward is donated with the deflationary token.

### Recommendation
In `_provisionReward`, measure the actual amount received by comparing the reward token balance of the pool before and after the `safeTransferFrom` call, and use that measured delta (not the caller-supplied `_amountReward`) for updating `historicalRewards`, `queuedRewards`, and `rewardPerTokenStored`.

### Proof of Concept
Foundry test plan:
1. Deploy a mock `FeeOnTransferToken` whose `transferFrom` deducts e.g. 10% fee and transfers only 90% to the recipient, while still returning `true`.
2. Deploy `BaseRewardPool` with this token registered as `rewardToken` (via constructor or `queueNewRewards` from an authorized manager once), and a mock `MasterMagpie`/staking token setup with at least two stakers (attacker with majority stake, victim with minority stake).
3. Attacker mints/approves `largeAmount` of the fee token and calls `donateRewards(largeAmount, feeToken)`.
4. Assert: pool's actual `feeToken.balanceOf(pool)` increased by only `largeAmount * 0.9`, but `rewards[feeToken].historicalRewards` and the computed `rewardPerTokenStored` reflect the full `largeAmount`.
5. Attacker calls `getReward` and receives `earned(attacker, feeToken)`; assert `sum(earned(attacker) + earned(victim)) > feeToken.balanceOf(pool)` before attacker's claim, and that after attacker's claim the pool balance is insufficient to pay the victim's full `earned()`, demonstrating insolvency.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
```
