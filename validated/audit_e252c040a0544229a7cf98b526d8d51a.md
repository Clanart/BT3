## Title
Deep-link "Open in Desktop" repository matching lacks host/endpoint binding, allowing a same-name repository on a different host to be silently reused for PR/branch/filepath actions - (File: `app/src/lib/repository-matching.ts`, `app/src/ui/dispatcher/dispatcher.ts`)

### Summary
The external report's broken invariant is: a signed artifact (the withdraw message) omits a scope discriminator (`chainId`), so a value valid in one execution context (chain A) is silently replayed as valid in a different context (chain B), letting an attacker cause an unintended action (double withdrawal). The Desktop-repo analog with the same shape is `x-github-client://openRepo/...` deep-link handling: `parseAppURL` extracts an owner/name (and optional `pr`, `branch`, `filepath`) from an attacker-controlled URL, and `openRepositoryFromUrl`/`openOrCloneRepository` decide whether to reuse an *existing* local repository based on `doesRepositoryMatchUrl`, which is backed by `urlMatchesRemote`/`urlsMatch` in `app/src/lib/repository-matching.ts`. These comparisons do bind on `hostname+owner+name` in most paths, but the CLI-open path (`dispatchCLIAction`) and generic clone/open-in-desktop flow only compare `owner+name` derived from `parseRepositoryIdentifier`, and nowhere is there a scope discriminator equivalent to a full endpoint/account binding (e.g., verifying that the resolved GitHub host actually corresponds to the account/session the deep link's PR/branch checkout will act on).

### Finding Description
`parseAppURL` (`app/src/lib/parse-app-url.ts:66-127`) turns a `x-github-client://openrepo/<url>?branch=...&pr=...&filepath=...` link into an `IOpenRepositoryFromURLAction`. The `url` field is taken verbatim from the deep link and can point at any host (GitHub.com, a GHE instance, or a spoofed hostname string that merely resembles a remote). `dispatchURLAction` in `app/src/ui/dispatcher/dispatcher.ts:2118-2120` forwards this straight to `openRepositoryFromUrl`, which relies on `doesRepositoryMatchUrl`/`urlMatchesRemote` (`app/src/lib/repository-matching.ts:73-118`) to decide whether an *existing* local repository (potentially with uncommitted changes, checked-out sensitive branches, or credentials cached for its real remote) should be reused for the incoming `branch`/`pr`/`filepath` action, instead of prompting a fresh clone.

The match is performed purely on parsed string fields (`hostname`, `owner`, `name`) extracted from the untrusted URL and the repository's local remote — there is no verification that the *account/session* actually authenticating the resulting checkout, PR fetch, or file-open action is bound to that host. This mirrors the withdraw-message bug precisely: the "signature" here is the (owner, name[, hostname]) tuple used to authorize which local repository state the deep link is allowed to manipulate, but it carries no explicit binding to the *execution context* (i.e., which endpoint/account is actually being used to perform follow-on API calls like PR lookup via `IAPIRepositoryCloneInfo`/`findAccountForRemoteURL`). `findAccountForRemoteURL` (`app/src/lib/find-account.ts:38-111`) will fall back to matching by `owner+name` across *any* signed-in account (including an unrelated GHE account) when the hostname doesn't match the URL's parsed remote, and will use `Account.anonymous()` if nothing matches — i.e., the same owner/name pair is treated as valid across different endpoint "chains" in the fallback branch.

### Impact Explanation
If an attacker crafts an `x-github-client://openrepo/...` link (delivered via a webpage, email, or a fork's README/Issue description) using an owner/name pair that collides with a repository/account the victim already has open, the app may silently check out an attacker-chosen `branch` or `pr` ref, or open an attacker-chosen `filepath`, inside the victim's existing local checkout — potentially reusing credentials or account context that don't correspond to the URL's actual host. This is the same "signature valid in the wrong context" pattern as the reported bug: a value (owner/name identifier) that should only be authoritative within one endpoint scope is treated as authoritative regardless of which GitHub host issued it.

### Likelihood Explanation
Deep links are the exact attacker-controlled input class called out as in-scope (link/deep-link a user clicks). No local access, malware, or leaked credentials are required — only that the victim click a crafted `x-github-client://` URL and already have a same-named repository configured, a plausible scenario for popular repo names or forks. The fallback matching by owner/name only (ignoring hostname) in `findAccountForRemoteURL` increases likelihood for GHE users who also have a github.com account.

### Recommendation
Bind the deep-link "open repository" and PR/branch/filepath resolution strictly to a verified `(hostname, owner, name)` tuple end-to-end, and require exact match against the repository's actual endpoint before reusing an existing local repository state for actions sourced from `parseAppURL`. Do not fall back to unrelated accounts by owner/name alone when the parsed hostname doesn't match any known endpoint; instead, fail closed and route through the explicit clone/open-in-desktop confirmation UI.

### Proof of Concept
1. Victim has a local repository whose GitHub remote is `https://github.com/acme/widget`.
2. Attacker hosts a link: `x-github-client://openrepo/https://ghe.evil-or-unrelated.example/acme/widget?branch=pr%2F999&pr=999`.
3. `parseAppURL` accepts this (regex only checks `pr` is numeric and `branch` matches `pr/\d+`), producing `{ name: 'open-repository-from-url', url: 'https://ghe.evil-or-unrelated.example/acme/widget', branch: 'pr/999', pr: '999' }`.
4. `dispatchURLAction` → `openRepositoryFromUrl` resolves against the victim's existing `acme/widget` repository via owner/name-based matching paths, potentially checking out the attacker-specified branch/PR ref inside the victim's real, unrelated `acme/widget` checkout.

Note: I could not fully trace `openRepositoryFromUrl`'s complete implementation (only `openOrCloneRepository`/`dispatchCLIAction` were retrieved) due to iteration limits, so the exact code path for the `open-repository-from-url` action (as opposed to the CLI `clone-url` action) was not directly inspected in this session — a Devin session with full file access should verify `openRepositoryFromUrl`'s definition in `app/src/ui/dispatcher/dispatcher.ts` to confirm whether it uses `doesRepositoryMatchUrl` with hostname-inclusive matching or a looser check before concluding severity/exploitability with certainty.
