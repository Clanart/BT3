## Analysis

The Morpho report's core broken invariant: an admin-controlled "block new activity" flag (deprecation) is allowed to be set without checking that a dependent "recovery/exit" flag (liquidation pause) is disabled, permanently locking bad debt because the recovery path stays blocked.

The Hyperbridge analog lives in `EvmHost`'s `FrozenStatus` design. `FrozenStatus` has four states (`None`, `Incoming`, `Outgoing`, `All`), and the `HandlerV2` contract enforces `notFrozen(host)` — which reverts on `Incoming` or `All` — uniformly across **every** relayer entrypoint: `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts`. ### Title
Freezing incoming messages (`FrozenStatus.Incoming`/`All`) blocks timeout-refund processing and permanently locks payer relayer-fee escrow - (File: `evm/src/core/HandlerV2.sol`, `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost` collects and escrows a `payer`'s relayer fee at dispatch time in `_requestCommitments[commitment]` [4](#0-3) . The only way to release that escrow — either to a relayer on successful delivery or back to the payer on timeout — is through `HandlerV2.handlePostRequestTimeouts` / `handleGetRequestTimeouts`, both of which are gated by the exact same `notFrozen(host)` modifier used for incoming message delivery [5](#0-4) . This modifier reverts whenever `host.frozen()` returns `Incoming` or `All` [6](#0-5) . There is no separate, weaker guard that still permits refund/timeout processing while blocking new incoming deliveries — the same flag that is meant to stop malicious/faulty incoming request execution also blocks the legitimate exit path for funds already escrowed by outgoing dispatches, exactly mirroring the Morpho pattern where one pause flag (borrow pause / deprecation) is not decoupled from the flag governing the recovery action (liquidation pause).

### Finding Description
- `dispatch()` escrows `post.fee` under `_requestCommitments[commitment]` when a POST/GET is sent outward, and is itself only blocked by `Outgoing`/`All` freeze states via its own `notFrozen` modifier [7](#0-6) .
- The refund of that same escrow can only happen through `dispatchTimeOut(...)`, invoked exclusively from `HandlerV2.handlePostRequestTimeouts`/`handleGetRequestTimeouts` [8](#0-7) .
- Both timeout handlers share the identical `notFrozen(host)` modifier as the incoming-delivery handlers, checking `Incoming || All` [3](#0-2) , [9](#0-8) .
- There is no independent state (e.g. an `Outgoing`-only freeze, or a bypass for timeout/refund processing) that keeps the exit/refund path open once `Incoming` or `All` is set. Whoever can set `FrozenStatus.Incoming` (per the host's freezing mechanism) simultaneously — and likely unintentionally — halts all refund settlement for requests that already timed out or will time out during the freeze window.

### Impact Explanation
Any relayer fee escrowed via `dispatch()` for a request whose destination processing coincides with an `Incoming`/`All` freeze cannot be refunded to its rightful `payer` until the freeze is lifted. If the freeze condition is long-lived (e.g. tied to an unresolved dispute/fork event on the source consensus client), payer funds are effectively locked in the `EvmHost` contract with no way to reclaim them via the documented recovery flow (`onPostRequestTimeout` → refund), directly violating the pivot that "refunds ... must move exactly once and only to the rightful beneficiary." This matches the Medium-severity classification of the seed report: it is not an outright fund-theft, but a fund-lock caused by unification of two flags (block incoming vs. block recovery) that should be independent.

### Likelihood Explanation
This occurs any time the host is put into `FrozenStatus.Incoming` or `FrozenStatus.All` while there exist outstanding, fee-bearing dispatches nearing or past their timeout — a realistic and expected operational scenario (freezing is the documented emergency response to a compromised/forked consensus client, and outstanding requests with fees are the normal steady state of the bridge). No malicious relayer, prover, or attacker action is required; the flaw is purely in the coupling of the two checks, identical in structure to the original report where the acknowledged flaw stems from insufficient separation between a "stop new activity" flag and a "allow settlement/exit" flag.

### Recommendation
Decouple timeout/refund processing from the `Incoming`/`All` freeze check. Introduce a distinct guard for `handlePostRequestTimeouts` and `handleGetRequestTimeouts` that only blocks when freezing is meant to halt *new* execution of incoming application callbacks, while still allowing verified timeout proofs to release escrowed relayer fees back to the `payer`. Alternatively, split `dispatchTimeOut`'s refund step from the `IApp` callback so that even if the destination callback needs to be gated by freeze status, the underlying escrow refund logic (or at minimum a payer-triggered emergency withdrawal after a freeze-plus-timeout condition) is never blocked indefinitely by the same flag used to stop malicious incoming delivery.

### Proof of Concept
1. User dispatches a `PostRequest` via `EvmHost.dispatch()` with `fee = X`, `payer = alice`, `timeout = 1 hour`. `_requestCommitments[commitment] = {sender: alice, fee: X}` is stored [4](#0-3) .
2. Before the request is delivered, the host is frozen with `FrozenStatus.Incoming` (or `All`) in response to a detected fork/consensus issue.
3. The request times out on the destination side; a relayer submits the timeout proof to `HandlerV2.handlePostRequestTimeouts`.
4. The call reverts with `HostFrozen()` because `notFrozen(host)` checks `state == Incoming || state == All` [5](#0-4) , [3](#0-2) .
5. `alice`'s escrowed fee `X` remains locked in `_requestCommitments[commitment]` with no available function to reclaim it until an admin manually restores `FrozenStatus.None` — which may not happen promptly, or at all, if the freeze condition (e.g. unresolved consensus dispute) persists.

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }

    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }

        // adjust the timeout
        uint64 timeoutTimestamp = post.timeout == 0 ? 0 : uint64(block.timestamp) + uint64(post.timeout);
        PostRequest memory request = PostRequest({
            source: host(),
            dest: post.dest,
            nonce: uint64(_nextNonce()),
            from: abi.encodePacked(_msgSender()),
            to: post.to,
            timeoutTimestamp: timeoutTimestamp,
            body: post.body
        });

        // make the commitment
        commitment = request.hash();
        _requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee});
