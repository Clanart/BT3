### Title
`SignableTransaction` weight/fee calculation omits the OP_RETURN data output, producing under-estimated `needed_fee` and a bypassable max-weight check - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an OP_RETURN output carrying up to 80 bytes of caller-supplied data to `tx_outs`, but computes transaction weight/vbytes via `calculate_weight_vbytes(tx_ins.len(), payments, ...)` which is passed only the *payments* — never the data output. Both the `needed_fee` calculation and the `MAX_STANDARD_TX_WEIGHT` standardness check therefore omit the data output's contribution.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` when `data` is specified (send.rs:194-202). Weight is then computed at line 204:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` (send.rs:62-127) builds a template `Transaction` whose `output` list is constructed from `payments` plus an optional `change` — it never receives `tx_outs`, so the data output (≈90 bytes: 8-byte value + varint + OP_RETURN script with up to 80 bytes) is absent from the template. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) undercharges by roughly `fee_per_vbyte * ~90` vbytes.
- The `TooLowFee` check at line 211 compares `needed_fee` against the under-estimated `vbytes`, so the *actual* fee rate of the produced transaction is lower than `fee_per_vbyte` and can fall below `DEFAULT_MIN_RELAY_TX_FEE` even when the check passes.
- The change branch (lines 224-235) recomputes weight via `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` — still omitting the data output.
- The `weight > MAX_STANDARD_TX_WEIGHT` check at line 241 can pass while the real transaction exceeds the standard weight limit by up to ~360 WU per omitted data output.

### Impact Explanation
An unprivileged caller controlling the `data` argument (and inputs/payments) can obtain a `SignableTransaction` whose serialized form either pays a fee rate below the minimum relay fee (transaction rejected by mempool, funds unmovable until reconstructed) or exceeds `MAX_STANDARD_TX_WEIGHT` (non-standard, unrelayable). The transaction's `needed_fee()`/`fee()` values are also inconsistent with the real vsize, breaking downstream fee amortization logic that assumes `needed_fee = vsize * fee_per_vbyte`.

### Likelihood Explanation
Reachable whenever `data.is_some()`. The missing ~90 vbytes matter whenever the configured `fee_per_vbyte` is near the minimum relay fee (so the effective rate drops below 1 sat/vb) or when the transaction is already near the 400,000 WU standardness cap. Severity is bounded to a single transaction's relayability, hence Medium.

### Recommendation
Pass the fully-built `tx_outs` (or `payments` plus the serialized data output) into `calculate_weight_vbytes`, so the weight estimate covers every output actually included in the final transaction — e.g., push the OP_RETURN `TxOut` before the weight calculation and iterate `tx_outs` when building the template, adding the change `TxOut` on top when applicable.

### Proof of Concept
```rust
// 1 input covering payments, no change, maximum data
let inputs = vec![received_output_with_value(100_000)];
let payments = vec![(payment_scriptbuf(), 10_000u64)];
let data = Some(vec![0u8; 80]);
let fee_per_vbyte = 1; // minimum-relay-adjacent rate

let tx = SignableTransaction::new(inputs, &payments, None, data, fee_per_vbyte).unwrap();

// The real serialized transaction includes the ~90-byte OP_RETURN output,
// so its actual vsize is larger than needed_fee / fee_per_vbyte implies.
// needed_fee == 1 * vbytes_without_data, but tx.vsize() = vbytes_without_data + ~90,
// giving an effective fee rate < 1 sat/vb and a mempool rejection under
// DEFAULT_MIN_RELAY_TX_FEE policy, despite the TooLowFee check passing.
```
