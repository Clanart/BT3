### Title
Anyone can send Bitcoin to Serai's deterministic internal (Change/Branch/Forwarded) offset addresses, causing outputs to be misclassified and silently dropped from external-deposit handling - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner` classifies received outputs purely by `script_pubkey`, and the "internal" output kinds (`Branch`, `Change`, `Forwarded`) use deterministic, publicly computable scalar offsets (`hash_to_F(KEY_DST, "branch" | "change" | "forward")`) added to the public group key. Any external party can therefore craft a payment whose output the processor treats as an internal output rather than an `External` deposit. Analogous to ETHAdapter sweeping its full balance, the scanner indiscriminately attributes every output paying to a registered script to a fixed internal role, letting unsolicited attacker funds be absorbed into internal flows (or silently dropped) instead of being handled as deposits.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs`, `Scanner::scan_transaction` matches `output.script_pubkey` against `self.scripts` and returns a `ReceivedOutput` carrying whatever offset was registered for that script — with no further distinction between an output the protocol itself created and one an arbitrary third party sent [1](#0-0) .

In `processor/src/networks/bitcoin.rs`, `scanner()` registers the internal offsets deterministically: `BRANCH_OFFSET`/`CHANGE_OFFSET`/`FORWARD_OFFSET` are `Secp256k1::hash_to_F(KEY_DST, b"branch"|b"change"|b"forward")`, and `register_offset` only increments until an even point is found [2](#0-1) . The group key is public, so every internal address (`key + G*offset`) is computable by anyone.

`Bitcoin::get_outputs` then labels every scanned output with `kind = kinds[offset_repr]` — so an attacker-sent payment to the change address is tagged `OutputType::Change`, not `External` [3](#0-2) . Downstream, `scanner_event_to_multisig_event` retains only `OutputType::External` outputs for instruction processing [4](#0-3) , while `Forwarded`-kind outputs trigger `ForwardedOutputDb::take_forwarded_output` and forwarding plans [5](#0-4) .

### Impact Explanation
- Outputs sent by third parties to internal offset addresses are misclassified as `Change`/`Branch`/`Forwarded`. Misclassified-as-internal outputs are dropped from the external-deposit path (`retain(kind == External)`), so no `InInstruction`/refund flow is created — funds land on the multisig but are never credited through normal deposit handling.
- Outputs sent to the `Forwarded` address can inject `PlanFromScanning::Forward` entries and interact with `ForwardedOutputDb`, polluting the forwarding/rotation logic with attacker-chosen amounts and outpoints.
- An attacker can also send dust/many outputs to internal addresses, bloating the output set the multisig must eventually spend or track, and `assert_eq!(output.key(), key)` / `kinds[offset]` indexing assumes only registered offsets appear — a reachable panic if offset handling diverges.

### Likelihood Explanation
Only requires sending a standard Bitcoin transaction to a publicly derivable P2TR address; no validator status, key material, or timing is needed. The offsets are constants derivable from the public group key and fixed DST strings.

### Recommendation
Distinguish protocol-created outputs from externally-received ones: e.g., record expected change/branch/forward outpoints when constructing transactions and only classify those specific outpoints as internal, or treat any output at an internal offset whose outpoint was not self-created as `External` (or reject it). Avoid `register_offset`-style script-only attribution for privileged output kinds.

### Proof of Concept
1. Obtain the multisig group key `K` (public).
2. Compute `off = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"change")`, incrementing until `K + off*G` is even — exactly what `scanner()`/`register_offset` does.
3. Send any amount to `p2tr_script_buf(K + off*G)`.
4. `get_outputs` returns this output with `kind == OutputType::Change`; `scanner_event_to_multisig_event` filters it out of `External` handling, so the deposit is never credited — the funds sit on an internal address indistinguishable from the protocol's own change.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }

    kinds.insert(offset_ref.to_vec(), kind);
