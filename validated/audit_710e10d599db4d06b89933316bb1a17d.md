### Title
Anonymous P2A anchor-spend pinning can delay confirmation of `create_package`'s CPFP child transaction past a bridge deadline - (File: crates/clementine-tx-sender/src/cpfp.rs)

### Summary
`create_package` builds a CPFP child that spends the parent's P2A anchor output using an "anyone-can-spend" script (`51024e73`). Because the anchor requires no signature, any unprivileged party watching the mempool can spend it first with their own low-fee, non-signaling transaction, occupying the single descendant slot that TRUC/v3 mempool policy allows for the parent, and blocking the honest CPFP child from being accepted as a package until the pinning transaction is replaced or evicted.

### Finding Description
The binding this module relies on is: `parent_tx.p2a_anchor_output` can only be spent by `TxSender`'s CPFP child == the fee-bumping path can always attach a higher-fee child to the deadline-bound parent before its timeout.

`create_package` (`crates/clementine-tx-sender/src/cpfp.rs:338-364`) locates the P2A anchor via `find_p2a_vout`/`is_p2a_anchor` [1](#0-0) , and the anchor script itself is defined as `OP_1 <0x4e73>` — a script with no key or signature requirement [2](#0-1) [3](#0-2) . Any party who can construct and broadcast a Bitcoin transaction (an explicitly listed capability of the unprivileged attacker) can spend this exact anchor output the moment the deadline-bound parent transaction appears in the mempool, without needing any key share, TLS cert, or bridge role.

Under TRUC/v3 relay policy (referenced in the module docstring, `bip-0431`), a v3 parent transaction may have at most one in-mempool descendant. If the attacker's spend of the anchor lands first, it occupies that single-descendant slot, so `submit_package`'s subsequent parent+child submission in `send_cpfp_tx` (`crates/clementine-tx-sender/src/cpfp.rs:615-679`) is rejected because the honest child transaction would create a second, disallowed descendant of the parent. The tx-sender's automatic retry loop (`try_to_send_unconfirmed_txs` in `crates/clementine-tx-sender/src/lib.rs:318-457`) re-attempts `send_cpfp_tx` repeatedly, but each attempt fails the same way as long as the attacker's low-fee spend remains in the mempool.

For the honest side to recover, it would need to either (a) directly RBF-replace the attacker's transaction — which only works if that transaction opts into replacement (BIP125 `nSequence < 0xFFFFFFFE`) or if the network runs full-RBF, neither of which is guaranteed or enforced by this code — or (b) wait for the attacker's transaction to be mined or evicted. `create_child_tx`/`build_and_sign_child_tx` (lines 47-127, 288-327) contain no logic that detects or reacts to an existing spend of the anchor output; they unconditionally attempt to build a transaction spending `p2a_anchor`, and `create_package` will keep producing packages that get rejected as long as the anchor is already spent in mempool by someone else. There is no check anywhere in this file (or in `send_cpfp_tx`) for "is the anchor output already spent in mempool" with a corresponding accelerated-replacement strategy.

This directly matches the question's premise: an unprivileged party who can broadcast a transaction and pay fees can attach/occupy the P2A anchor descendant slot of a bridge transaction handled by `create_package`, preventing the fee-bumping path from raising the package's effective fee before a protocol deadline.

### Impact Explanation
If the parent transaction pinned this way is a deadline-bound transaction (e.g., a challenge, disprove, or timeout transaction in the presigned graph, or an operator payout/kickoff-adjacent transaction that races a timelocked alternative), being unable to confirm before the deadline lets the competing timeout path win instead. This can result in bridged BTC being claimed by the wrong side, an honest operator failing to be reimbursed, or a legitimate claim/disprove failing to land in time — matching the "High: a deadline-bound challenge/disprove/timeout transaction made unconfirmable by attacker-shaped chain data" impact category. The attack is repeatable per bridge transaction that exposes a P2A anchor and costs the attacker only the fee of a single small mempool transaction (potentially at the mempool minimum relay fee), which is cheap relative to the value it can put at risk.

### Likelihood Explanation
Preconditions: the attacker must observe the deadline-bound parent transaction in the mempool (public information) and race a transaction spending its known anchor outpoint before the operator's tx-sender does — a purely observational and cheap action requiring only mempool monitoring and minimal fees. No special privileges, keys, or bridge participation are needed. Success depends on network-specific relay/mempool policy details (whether the attacker's spend signals RBF, whether the node runs full-RBF, and how TRUC package-relay pinning defenses in the deployed Bitcoin Core version behave), which affects but does not eliminate the pinning window; even with eventual RBF-based recovery, each pinning attempt can consume mempool time that is scarce near a hard deadline, and the attacker can repeat the race on every rebroadcast/bump attempt.

### Recommendation
Do not rely on an anyone-can-spend, unauthenticated anchor as the sole always-available CPFP attachment point for deadline-critical transactions. Mitigations to evaluate: pre-broadcast a signed, RBF-signaling reservation transaction for the anchor as soon as the parent is created; monitor the mempool for third-party spends of the anchor outpoint and immediately attempt a higher-feerate RBF replacement using the appropriate signaling; fall back to an alternative CPFP anchor path or additional own-controlled input that isn't anyone-can-spend for time-critical transactions; and/or track anchor-spend detection in `create_package`/`send_cpfp_tx` so `TxSender` reacts within the same tip-height cycle rather than only via the periodic bump loop.

```
cargo test -p clementine-tx-sender --features testing -- cpfp_anchor_pinning
```
Test plan (regtest):
1. Have `TxSender` broadcast a deadline-bound transaction `tx` containing a P2A anchor output, unconfirmed in the mempool.
2. Before `send_cpfp_tx` is invoked/succeeds, from a wallet with no relationship to the bridge (simulating the unprivileged attacker), craft and broadcast `attacker_tx` spending `OutPoint{txid: tx.compute_txid(), vout: p2a_vout}` with a minimal fee and `nSequence = 0xFFFFFFFF` (no RBF signaling).
3. Call `TxSender::send_cpfp_tx` for `tx` and assert `create_package`'s resulting `submit_package` call fails/rejects because the anchor UTXO is already spent (assert on `PackageTransactionResult::Failure` referencing the anchor outpoint), demonstrating package submission is blocked.
4. Advance blocks/time to just before the protocol deadline (e.g., `current_tip_height` reaching the relevant timelock height) and assert `tx` remains unconfirmed, i.e. `get_tx_out(tx.compute_txid(), main_vout)` returns `None`/unconfirmed while the deadline height is reached — violating "every deadline-bound bridge transaction remains fee-bumpable to confirmation before its timeout matures."
