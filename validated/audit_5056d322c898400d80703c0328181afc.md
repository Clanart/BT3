### Title
Approve front-run in `CW20ERC20Pointer.approve()` allows a spender to obtain old + new allowance - (contracts/src/CW20ERC20Pointer.sol)

### Summary
`CW20ERC20Pointer.approve()` implements the standard OpenZeppelin `ERC20.approve` interface but internally reimplements it as an owner-driven delta between the currently-queried allowance and the requested amount, dispatching either `increase_allowance` or `decrease_allowance` to the underlying CW20 contract. This retains the classic ERC20 approve front-running problem: a spender who observes a pending "lower my allowance" transaction can front-run it with `transferFrom`, spend the old allowance, and still receive the newly-approved amount on top.

### Finding Description
`approve()` reads the current on-chain allowance via a synchronous CosmWasm query and then computes and dispatches a delta message (`increase_allowance`/`decrease_allowance`) to reach the caller-specified target amount: [1](#0-0) 

Because the actual on-chain allowance amount is not atomically tied to the value observed when the owner submitted the transaction, a malicious spender can:
1. Observe the owner's pending `approve(spender, M)` transaction in the mempool while their existing allowance is `N` (`N > M`, or any nonzero `N`).
2. Front-run it with `transferFrom(owner, spender_controlled, N)`, spending the full existing allowance before the owner's transaction lands.
3. Let the owner's `approve` transaction execute; it queries the (now-zero) allowance and dispatches `increase_allowance` for `M`, since `currentAllowance (0) < amount (M)`: [2](#0-1) 
4. The spender ends up having transferred `N` and now holds an additional allowance of `M`, i.e. `N + M` total value extracted versus the owner's intended maximum of `max(N, M)`.

This is functionally identical to the classic ERC20 `approve` race condition described in the reference report, and this pointer contract does not mitigate it — the internal increase/decrease-based dispatch does not make the read-then-act sequence atomic with the owner's original approval decision.

### Impact Explanation
`CW20ERC20Pointer` is a bridge contract that lets EVM callers interact with CW20 tokens through an ERC20 interface; it is deployed/associated for CW20 denoms and reachable by any EVM transaction sender through standard `approve`/`transferFrom` calls. A spender that races an owner's allowance-reduction transaction can extract more CW20 token value than the owner intended, resulting in unauthorized transfer of funds through the pointer beyond the owner's authorized amount — a concrete fund-loss scenario reachable by an unprivileged transaction sender/spender via public mempool front-running.

### Likelihood Explanation
Exploitation requires only: (a) an owner holding a nonzero allowance for a spender who calls `approve` again to change (typically lower) that allowance, and (b) the spender being adversarial or compromised and capable of submitting a `transferFrom` transaction with higher priority/gas before the owner's `approve` is included. This is a standard, low-cost MEV/front-running pattern requiring no special privileges — any transaction sender on the public network can perform it against any counterparty that grants and later re-approves allowances to them.

### Recommendation
Add an atomic "compare-and-set" style approve, e.g. an `approve(spender, expectedCurrentAllowance, newAmount)` or rely exclusively on `increaseAllowance`/`decreaseAllowance` semantics enforced against an expected prior value, so that the state-changing effect fails (reverts) if the on-chain allowance has changed since the caller last observed it. Alternatively, document and encourage callers to always set allowance to zero and confirm before setting a new nonzero value, and/or expose the same guard in `CW20ERC20Pointer.approve()` (revert if `allowance(msg.sender, spender)` unexpectedly changed between call time expectations, requiring the caller to pass the expected current allowance).

### Proof of Concept
1. Owner calls `pointer.approve(spender, 1000)`; CW20 allowance for (owner, spender) becomes `1000`.
2. Spender (aware they will soon be de-authorized) submits `pointer.transferFrom(owner, spenderAddr, 1000)` with high gas price when they detect owner's follow-up `approve(spender, 500)` transaction (attempting to lower allowance) in the mempool.
3. Spender's `transferFrom` mines first: allowance becomes `0`, spender receives `1000` tokens.
4. Owner's `approve(spender, 500)` then executes: `currentAllowance` is queried as `0` (< 500), so `increase_allowance` for `500` is dispatched, setting allowance to `500`.
5. Spender now calls `transferFrom(owner, spenderAddr, 500)`, extracting another `500` tokens.
6. Total extracted by spender: `1500`, versus the owner's intended maximum exposure of `500` (or `1000` before reduction) — demonstrating the front-run yields `N + M` instead of `max(N, M)`. [1](#0-0)

    function approve(address spender, uint256 amount) public override returns (bool) {
        // if amount is larger uint128 then set amount to uint128 max
        if (amount > type(uint128).max) {
            amount = type(uint128).max;
        }
        uint256 currentAllowance = allowance(msg.sender, spender);
        if (currentAllowance > amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(currentAllowance - amount)));
            string memory req = _curlyBrace(_formatPayload("decrease_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        } else if (currentAllowance < amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount - currentAllowance)));
            string memory req = _curlyBrace(_formatPayload("increase_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        }
        return true;
    }
