### Title
`ThresholdKeys::new` never checks the secret share nor the verification shares outside the first-`t` interpolation subset, so `ThresholdKeys::read` accepts inconsistent keys that later mis-attribute blame to honest signers - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to CVE-2019-19646 — where `integrity_check` skipped the `NOT NULL` constraint on generated columns — `ThresholdKeys::new` acts as the integrity check for a deserialized key set, yet it only validates the *count* and *index range* of `verification_shares` and derives `group_key` solely from the shares of participants `1..=t`. It never verifies that the holder's own `secret_share` matches `verification_shares[params.i()]` (`G * secret_share == verification_share`), and it never checks the consistency of verification shares for participants `t+1..=n` (the "generated columns" of the polynomial, which are fully determined once any `t` shares fix the polynomial). These unchecked fields are attacker-controlled bytes when reached via `ThresholdKeys::read`.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::new` (lines 349-391) performs only two validations: `verification_shares.len() == n` (line 355) and every key `<= n` (lines 361-365). It then computes `group_key` by interpolating *only* the shares of participants `1..=t`:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

There is no check that `C::generator() * secret_share == verification_shares[&params.i()]`, and no check that shares `t+1..=n` lie on the polynomial implied by the first `t` shares. `ThresholdKeys::read` (lines 573-632) reconstructs these fields from untrusted bytes and funnels directly into `ThresholdKeys::new` (lines 625-631), so the missing constraints are reachable from deserialized input.

The corrupted fields are later consumed as ground truth in the FROST blame path. In `crypto/frost/src/sign.rs` `AlgorithmSignatureMachine::complete` (lines 447-495), when the aggregate signature check fails (line 465), each participant's share is verified against `self.view.verification_share(*l)` (lines 475-481), which is derived in `ThresholdKeys::view` from the unchecked `core.verification_shares` map (crypto/dkg/src/lib.rs lines 500-507). A crafted `verification_shares[victim]` therefore makes an honest participant's *valid* share fail `verify_share`, and `batch.verify_vartime_with_vartime_blame()` returns the honest participant's index, producing `FrostError::InvalidShare(victim)`.

### Impact Explanation
An attacker who can supply bytes to `ThresholdKeys::read` (e.g., a corrupted or maliciously written key-share blob consumed by a processor/validator) can craft a `ThresholdKeys` where an honest participant's verification share is wrong. During a signing session, any trigger of the blame path — including the attacker simply submitting a bad signature share of their own — causes the batch verifier to attribute fault to the honest victim. Downstream (`processor/src/batch_signer.rs` ~line 282, `processor/src/key_gen.rs` `VerifyBlame` ~line 504), `InvalidShare(l)` / blame results are translated into `ProcessorMessage::InvalidParticipant` / `Blame` messages, which carry slashing consequences on-chain. An honest validator can thus be fatally blamed for a fault they did not commit — incorrect blame attribution / fabricated proof of misbehavior. Severity: Medium.

### Likelihood Explanation
Exploitation requires the attacker to influence the bytes passed to `ThresholdKeys::read` *and* a signing session to subsequently fail the aggregate check (which the same attacker can guarantee by submitting an invalid share). The DKG-produced `ThresholdKeys` are internally consistent, so this cannot corrupt an honestly generated key in place; it applies where serialized keys are stored/reloaded (e.g., processor DB restore after restart) and an attacker can tamper with or supply the blob. The missing-check window is narrow but concrete, which is why Medium rather than High.

### Recommendation
In `ThresholdKeys::new`, add two integrity checks over the fields it currently trusts:

1. Verify the holder's secret share matches its verification share: `if (C::generator() * secret_share.deref()) != verification_shares[&params.i()] { Err(...) }`.
2. Optionally, verify consistency of shares `t+1..=n` against the polynomial defined by any `t` shares (or document that only `1..=t` are normative and that all other shares are advisory). At minimum, check the local secret share so a mismatched (corrupted or crafted) serialization is rejected at construction instead of surfacing as fabricated blame during signing.
