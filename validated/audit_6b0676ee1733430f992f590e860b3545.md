### Title
Malicious offer with a cyclic ephemeral coin chain causes an infinite loop in `Offer.get_root_removal` / `get_pending_amounts` - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer.get_root_removal()` walks a chain of ephemeral (spent-within-the-bundle) removal coins by following `coin.parent_coin_info` until it finds a coin classified as "non-ephemeral" [1](#0-0) . The set of removal coins in an `Offer`/`WalletSpendBundle` is fully attacker-controlled by whoever constructs the offer (a wallet counterparty), and nothing prevents a counterparty from crafting two or more coin spends whose `parent_coin_info` values point at each other, forming a cycle. Because every coin in the cycle has a `parent_coin_info` that is present in `all_removal_ids`, none of them qualify as `non_ephemeral_removals`, so the `while coin not in non_ephemeral_removals` loop never terminates — it bounces between the cyclic coins forever. This is a direct analog to the Routinator issue: an untrusted, attacker-supplied chain (RRDP repository chain / here, a coin-parentage chain inside an offer) is walked without a bound or cycle check, hanging the walker (Routinator's validation run / here, the wallet's offer-processing call) indefinitely.

### Finding Description
`get_root_removal()` is invoked by `get_pending_amounts()` for every offered coin returned from `get_offered_coins()` [2](#0-1) . `get_pending_amounts()` in turn is called from `TradeRecordOld.to_json_dict_convenience()` [3](#0-2) , which is used to serialize trade records — including a counterparty-supplied `taken_offer` — for consumption over the wallet RPC (e.g. listing/retrieving trades). Because `offer_to_summarize` is built directly from `self.taken_offer`, an offer bytes blob received from a counterparty, a malicious offer file can be crafted so that:

- Two (or more) removal coins reference each other as parents (`A.parent_coin_info == B.name()` and `B.parent_coin_info == A.name()`), both present in the bundle's `removals()`.
- Both coins therefore fail the `non_ephemeral_removals` predicate (`c.parent_coin_info not in {r.name() for r in all_removals}`) [4](#0-3) .
- The `while` loop in `get_root_removal` keeps calling `next(c for c in all_removals if c.name() == coin.parent_coin_info)`, oscillating between `A` and `B` (or around a longer cycle) with no termination condition and no cycle detection, hanging forever.

This mirrors the Routinator bug class (CWE-674/CWE-835): an externally supplied chain structure is walked with an assumption of eventual termination (reaching a well-formed root/non-ephemeral coin), but a malicious party can build a structure with no terminus (a cycle), causing unbounded, non-terminating processing.

### Impact Explanation
Any code path that calls `Offer.summary()`/`get_pending_amounts()`/`get_primary_coins()` on an untrusted offer (accepting an incoming offer, listing trade history that includes a taken offer from a counterparty, or examining an offer before deciding to accept it) will hang the calling coroutine indefinitely. Since wallet RPC handling in Chia typically processes requests on the main event loop, a single malicious offer can stall the wallet's RPC service, preventing legitimate wallet operations (balance checks, spend submission, other trade processing) from completing — a spend/offer-triggered processing halt, which the validation rules explicitly recognize as in-scope impact.

### Likelihood Explanation
High: constructing an `Offer`/`WalletSpendBundle` with cyclic ephemeral coin parentage requires no privileged access — it only requires crafting a spend bundle with self-referential `parent_coin_info` fields, something any offer-issuing counterparty fully controls. No signature validity, on-chain confirmation, or special network position is needed; the loop is hit purely from local computation on attacker-supplied offer bytes.

### Recommendation
Add a visited-set / iteration bound in `get_root_removal()` (and any similar ancestor-walk in `offer.py`) so that once a coin is revisited (cycle detected) or the number of hops exceeds the size of `all_removals`, the function raises a `ValueError` instead of looping forever. Additionally, validate that the removal graph implied by an incoming offer's coin spends is acyclic before running any pending/summary computations on it.

### Proof of Concept
Conceptually (pseudo-code, mirroring the existing code path):
```python
# Two coins forming a 2-cycle via parent_coin_info, both included as removals
# in a crafted WalletSpendBundle used to build a malicious Offer/taken_offer.
coin_a = Coin(parent_coin_info=coin_b.name(), puzzle_hash=..., amount=...)
coin_b = Coin(parent_coin_info=coin_a.name(), puzzle_hash=..., amount=...)
# Both coin_a and coin_b are added as CoinSpends in the bundle's removals,
# and one of them is referenced from get_offered_coins() (e.g. as a primary/offered coin).

offer = Offer(requested_payments, WalletSpendBundle([spend_a, spend_b, ...], G2Element()), driver_dict)
offer.get_pending_amounts()  # hangs forever inside Offer.get_root_removal()
```
Reaching this from the wallet requires only that a counterparty send this crafted offer, which the victim wallet processes via `TradeRecordOld.to_json_dict_convenience()` [3](#0-2)  when listing or inspecting trades through the wallet RPC.

```python
    # This returns the non-ephemeral removal that is an ancestor of the specified coin
    # This should maybe move to the SpendBundle object at some point
    def get_root_removal(self, coin: Coin) -> Coin:
        all_removals: set[Coin] = set(self.removals())
        all_removal_ids: set[bytes32] = {c.name() for c in all_removals}
        non_ephemeral_removals: set[Coin] = {
            c for c in all_removals if c.parent_coin_info not in {r.name() for r in all_removals}
        }
        if coin.name() not in all_removal_ids and coin.parent_coin_info not in all_removal_ids:
            raise ValueError("The specified coin is not a coin in this bundle")

        while coin not in non_ephemeral_removals:
            coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)

        return coin
```
