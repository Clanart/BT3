### Title
Precompile signature-verification loops (`ed25519`/`secp256k1`/`secp256r1`) execute unmetered by the SBF compute meter, allowing materially underpriced compute via `InvokeContext::process_precompile` - (File: `program-runtime/src/invoke_context.rs`)

### Summary
The C4 finding describes an unbounded/underpriced loop (`SurplusGuildMinter.getReward()` → `ProfitManager.claimRewards()`) whose per-iteration cryptographic/state work is not gated by a cost proportional to the loop length. The closest reachable analog in this codebase is the precompile-verification path: `ed25519::verify`, `secp256k1::verify`, and `secp256r1::verify` each loop over `num_signatures` (attacker-controlled, up to 255 for ed25519/secp256k1 and up to 8 for secp256r1) performing real signature-verification cryptography, but this loop executes entirely **outside** the SBF VM's per-instruction compute meter.

### Finding Description
`InvokeContext::process_message` special-cases precompile program IDs and calls `process_precompile` instead of `process_instruction`: [1](#0-0) 

`process_precompile` never touches `self.compute_meter`; it simply pushes/pops the instruction context and calls the verification callback directly: [2](#0-1) 

The verification callback in turn runs the loop that performs the actual expensive cryptography per signature, e.g. `ed25519::verify`: [3](#0-2) 
and `secp256r1::verify` (up to 8 OpenSSL EC verifications, each involving `BigNum`/`EcPoint` construction and ECDSA verification): [4](#0-3) 

Unlike every other CPU-bound operation reachable from an instruction (CPI translation, `create_program_address`, memory-mapping translations), which explicitly call `invoke_context.compute_meter.consume_checked(...)` per unit of work (see `cpi.rs` and `syscalls/src/lib.rs`), the precompile verify loop has **no such call**. The only "cost" charged for a precompile instruction is the fixed default builtin cost used by the cost model/compute-budget estimator: [5](#0-4) 

and the test explicitly documents that VM execution "consume[s] 0 from CU-meter" for a precompile instruction, with the entire allocated builtin CU budget (3,000 CU) simply refunded: [6](#0-5) 

Separately, `num_secp256k1/ed25519/secp256r1_instruction_signatures` are used only to compute the **signature fee** (extra lamports charged to the fee payer) and an **estimated execution cost heuristic** used by the cost model for block-packing: [7](#0-6) [8](#0-7) 

Neither of these consumes the transaction's actual `compute_unit_limit`/compute meter during execution — they only affect fee lamports and the cost-tracker's block-packing estimate, which is a static per-signature constant, not an enforced runtime budget checked against `compute_meter`. This is structurally identical to the C4 bug class: a per-item loop (`num_signatures`, analogous to "all gauges/terms") whose real per-iteration cost (cryptographic verification, analogous to `claimGaugeRewards`) is not checked against/consumed from the resource budget that is supposed to bound work done inside instruction/message processing.

### Impact Explanation
A transaction can include multiple precompile instructions (e.g., several `ed25519_program` or `secp256r1_program` instructions), each specifying the maximum `num_signatures` its format allows (255 for ed25519/secp256k1, 8 for secp256r1), with signature/pubkey/message offsets pointing at small, reused byte ranges within the transaction's own instruction data (transaction size is capped at ~1232 bytes, but offsets can overlap/reuse the same bytes many times). Each such instruction forces the validator to perform tens to hundreds of full cryptographic signature verifications (ed25519 strict verification, secp256k1 ECDSA recovery, or secp256r1 OpenSSL ECDSA verification with `EcPoint`/`BigNum` construction) during `process_precompile`, which is not gated by the transaction's declared compute-unit limit and does not consume from `invoke_context.compute_meter`. Because the cost model / cost tracker only charges a fixed per-instruction constant (and a linear-but-modest per-signature fee/estimate) rather than enforcing the real CPU work against the compute budget, an attacker can submit many such transactions (each cheap in declared CUs and lamports) that impose disproportionate CPU cost on the leader/validators processing them, degrading transaction processing throughput — a compute-underpricing DoS vector, mirroring the "unbounded work not billed against the intended limiter" root cause of the C4 issue.

### Likelihood Explanation
This requires no special privilege — any user can craft and submit a transaction containing precompile instructions with attacker-chosen `num_signatures` and offsets; there is no admin/authority gate on precompile instruction content. The precompile programs (`secp256k1_program`, `ed25519_program`, `secp256r1_program`) are always enabled (`None` feature gate) as shown in the precompile registry: [9](#0-8) 
The per-field maxima (255 sigs for ed25519/secp256k1, 8 for secp256r1) and per-transaction size limits bound the worst case per single transaction, but the underlying design gap (no compute-meter consumption during verification) applies unconditionally to every precompile instruction processed, making the underpricing systemic rather than a rare edge case — similar to the judges' conclusion in the referenced report that likelihood of exploitation is uncertain but the impact/lack of mitigation makes it worth flagging.

### Recommendation
Charge `invoke_context.compute_meter` inside `process_precompile` (or before invoking the verification callback) proportionally to the actual work to be performed — i.e., derived from `num_signatures` for each precompile instruction — before or during verification, and fail with `ComputationalBudgetExceeded` if the transaction's remaining compute budget cannot cover it. This mirrors how CPI translation costs (`cpi_bytes_per_unit`) and `create_program_address_units` are already metered elsewhere in `program-runtime/src/cpi.rs` and `syscalls/src/lib.rs`, and would close the gap where the cost model's static per-signature "estimate" is not actually enforced as a resource limit during execution.

### Proof of Concept
Not independently executed (no runtime access), but derivable from the cited code paths and the existing test `test_builtin_ix_precompiled` which explicitly asserts "VM Execution: consume 0 from CU-meter" for a precompile instruction: [6](#0-5) 
A PoC transaction would construct a single `ed25519_program` (or `secp256r1_program`) instruction with `num_signatures` set to its maximum (255 / 8 respectively), with all `signature_instruction_index`/`public_key_instruction_index`/`message_instruction_index` offsets pointing at the same small in-instruction byte range (reusing bytes), repeated across several instructions in one transaction (bounded by the ~1232-byte packet limit), and measure wall-clock CPU time spent in `process_precompile`/`verify` versus the compute units actually deducted from `invoke_context.compute_meter` (expected: zero CU deducted for the verification loop itself, confirming the underpricing).

    #[cfg_attr(feature = "dev-context-only-utils", qualifiers(pub))]
    fn process_precompile(
        &mut self,
        program_id: &Pubkey,
        instruction_data: &[u8],
        message_instruction_datas_iter: impl Iterator<Item = &'ix_data [u8]>,
    ) -> Result<(), InstructionError> {

        let instruction_datas: Vec<_> = message_instruction_datas_iter.collect();

            .map_err(InstructionError::from)
            .and(self.pop())
    }

        .saturating_add(SIGNATURE_OFFSETS_START);

        BigNum::from_slice(&SECP256R1_HALF_ORDER).map_err(|_| PrecompileError::InvalidSignature)?;

    let order_minus_one: BigNum = BigNum::from_slice(&SECP256R1_ORDER_MINUS_ONE)
        .map_err(|_| PrecompileError::InvalidSignature)?;

        let start = i
            .saturating_mul(SIGNATURE_OFFSETS_SERIALIZED_SIZE)
            .saturating_add(SIGNATURE_OFFSETS_START);

        // SAFETY:
        // - data[start..] is guaranteed to be >= size of Secp256r1SignatureOffsets
        // - Secp256r1SignatureOffsets is a POD type, so we can safely read it as an unaligned struct
        let offsets = unsafe {
            core::ptr::read_unaligned(data.as_ptr().add(start) as *const Secp256r1SignatureOffsets)
        };

        // Parse out signature
        let signature = get_data_slice(
            data,
            instruction_datas,
            offsets.signature_instruction_index,
            offsets.signature_offset,
            SIGNATURE_SERIALIZED_SIZE,
        )?;

        // Parse out pubkey
        let pubkey = get_data_slice(
            data,
            instruction_datas,
            offsets.public_key_instruction_index,
            offsets.public_key_offset,
            COMPRESSED_PUBKEY_SERIALIZED_SIZE,
        )?;

        // Parse out message
        let message = get_data_slice(
            data,
            instruction_datas,
            offsets.message_instruction_index,
            offsets.message_data_offset,
            offsets.message_data_size as usize,
        )?;

        let r_bignum = BigNum::from_slice(&signature[..FIELD_SIZE])
            .map_err(|_| PrecompileError::InvalidSignature)?;
        let s_bignum = BigNum::from_slice(&signature[FIELD_SIZE..])
            .map_err(|_| PrecompileError::InvalidSignature)?;

        // Check that the signature is generally in range
        let within_range = r_bignum >= one
            && r_bignum <= order_minus_one
            && s_bignum >= one
            && s_bignum <= half_order;

        if !within_range {
            return Err(PrecompileError::InvalidSignature);
        }

        // Create an ECDSA signature object from the ASN.1 integers
        let ecdsa_sig = openssl::ecdsa::EcdsaSig::from_private_components(r_bignum, s_bignum)
            .and_then(|sig| sig.to_der())
            .map_err(|_| PrecompileError::InvalidSignature)?;

        let public_key_point = EcPoint::from_bytes(&group, pubkey, &mut ctx)
            .map_err(|_| PrecompileError::InvalidPublicKey)?;
        let public_key = EcKey::from_public_key(&group, &public_key_point)
            .map_err(|_| PrecompileError::InvalidPublicKey)?;
        let public_key_as_pkey =
            PKey::from_ec_key(public_key).map_err(|_| PrecompileError::InvalidPublicKey)?;

        let mut verifier =
            Verifier::new(openssl::hash::MessageDigest::sha256(), &public_key_as_pkey)
                .map_err(|_| PrecompileError::InvalidSignature)?;
        verifier
            .update(message)
            .map_err(|_| PrecompileError::InvalidSignature)?;

        if !verifier
            .verify(&ecdsa_sig)
            .map_err(|_| PrecompileError::InvalidSignature)?
        {
            return Err(PrecompileError::InvalidSignature);
        }
    }
    Ok(())

/// Calculate fees from signatures.
pub fn calculate_signature_fee(
    SignatureCounts {
        num_transaction_signatures,
        num_ed25519_signatures,
        num_secp256k1_signatures,
        num_secp256r1_signatures,
    }: SignatureCounts,
    lamports_per_signature: u64,
) -> u64 {
    let signature_count = num_transaction_signatures
        .saturating_add(num_ed25519_signatures)
        .saturating_add(num_secp256k1_signatures)
        .saturating_add(num_secp256r1_signatures);
    signature_count.saturating_mul(lamports_per_signature)
}
