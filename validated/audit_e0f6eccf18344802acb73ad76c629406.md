### Title
Division-by-zero panic in KIP-71 base fee calculation via ungated `kip71.gastarget` governance parameter - (File: `params/kip71_config.go`)

### Summary
`KIP71Config.NextMagmaBlockBaseFee` performs `x.Div(x, new(big.Int).SetUint64(gasTarget))` using the governance-controlled `GasTarget` value without checking it is non-zero, while the sibling parameter `BaseFeeDenominator` is explicitly guarded against zero. The `kip71.gastarget` parameter is registered with a `noopFormatChecker`, allowing it to be set to `0` through the governance parameter pipeline, which will cause every node to panic on `big.Int` division by zero when computing/verifying the next block's base fee.

### Finding Description
`NextMagmaBlockBaseFee` computes the next base fee using the governance parameter `GasTarget`: [1](#0-0) 

Note the defensive fallback for `BaseFeeDenominator == 0` ("To avoid panic, set the fluctuation range small"), which shows the maintainers are aware this class of bug exists and previously fixed one occurrence of it.

However, `GasTarget` has no equivalent guard. When `parentGasUsed != GasTarget`, both branches divide by `gasTarget` directly: [2](#0-1) [3](#0-2) 

If `GasTarget == 0`, then unless `parentGasUsed` is also exactly `0` (which returns early at line 90), the code enters either the `parentGasUsed > gasTarget` branch or the `else` branch and executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with a zero divisor. Go's `math/big.Int.Div` panics on division by zero (unlike Solidity/EVM opcodes, which return 0).

Critically, the parameter registration for `Kip71GasTarget` uses `noopFormatChecker` (always returns `true`), whereas the analogous `Kip71BaseFeeDenominator` parameter explicitly rejects zero: [4](#0-3) 

The governance vote-consistency check (`checkConsistency`) in header-based governance also does not add any extra validation for `Kip71GasTarget` beyond the format checker — it is in the pass-through list that returns `nil`: [5](#0-4) 

`NextMagmaBlockBaseFee` is called from core block-processing paths reachable by every node processing a block header or building a block, including:
- Block header verification: [6](#0-5) 
- Chain/header construction: [7](#0-6) 
- Tx pool gas price update after every new head: [8](#0-7) 
- Block assembly in the miner/worker: [9](#0-8) 
- Public RPC gas price / fee history estimation: [10](#0-9) , [11](#0-10) 

Once `GasTarget` is set to `0` via a successful governance vote (or via the GovParam contract path, which uses the same `Params` map and `FormatChecker` in `contractgov`), every node in the network will panic the first time it evaluates `NextMagmaBlockBaseFee` for the following block — in block validation, block building, the tx pool reset routine, and RPC gas price/fee-history calls. This is not a localized error return; it is an uncaught panic that crashes the process, unless recovered by an external supervisor, effectively halting the chain network-wide (all honest nodes, not just one).

### Impact Explanation
This is a chain-halting, node-crashing denial of service reachable through the in-scope "governance parameters" pathway. Every node (validators, RPC nodes) that evaluates the next Magma base fee — which happens on every new block (`tx_pool.go` reset, block validation, block assembly) — will panic identically, producing a synchronized network-wide crash rather than a localized failure. This matches the CVE's bug class (uncontrolled division/modulo by zero causing DoS) and is more severe than the original CVE because it can crash all nodes on the network in lockstep from a single malicious/misconfigured governance parameter change, rather than an isolated single-process crash from a malformed file.

### Likelihood Explanation
The likelihood depends on how privileged the actor setting `kip71.gastarget` needs to be. In the current governance implementation (header-vote based, single-governing-node mode, or via `GovParamContract`), setting a governance parameter to an invalid value is not restricted by any format check for `GasTarget` (`noopFormatChecker`), unlike the equivalent `BaseFeeDenominator` parameter, which does check `v != 0`. This inconsistency strongly suggests the zero-check for `GasTarget` was simply forgotten, since the underlying code (`params/kip71_config.go`) was already patched defensively for `BaseFeeDenominator == 0` but not for `GasTarget == 0`. Any governance actor able to push a `kip71.gastarget` vote/value of `0` (whether via the governing node header vote path or via the `GovParam` contract path, depending on deployment's governance mode) can trigger the crash on the very next block.

### Recommendation
Add a zero-check for `GasTarget` in `NextMagmaBlockBaseFee`, mirroring the existing `BaseFeeDenominator` guard (e.g., fall back to a safe default value when `kc.GasTarget == 0`), and additionally fix the `Kip71GasTarget` parameter's `FormatChecker` in `kaiax/gov/param.go` to reject `0` (as is already done for `Kip71BaseFeeDenominator`), preventing the invalid value from ever being accepted into the governance parameter set in the first place.

### Proof of Concept
1. Submit/pass a governance vote (or GovParam contract update, depending on governance mode) setting `kip71.gastarget = 0`. This passes validation because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker` (`kaiax/gov/param.go:324-334`) and `checkConsistency` performs no additional validation for this parameter (`kaiax/gov/headergov/impl/header.go:214-220`).
2. Once the parameter takes effect at the next epoch/block, any block with `parentGasUsed != 0` triggers `NextMagmaBlockBaseFee` to compute `x.Div(x, new(big.Int).SetUint64(0))` (`params/kip71_config.go:102` or `:120`).
3. `big.Int.Div` with a zero divisor panics, crashing every node that evaluates this function — during block validation, block building (`work/worker.go:382`), tx pool reset (`blockchain/tx_pool.go:576`), and gas price RPC calls (`node/cn/gasprice/gasprice.go:334`) — resulting in a network-wide denial of service.
