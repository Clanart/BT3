### Title
Keychain user/service cache-key concatenation collision causes cross-identity keychain confusion in daemon `KeychainServer` - ([File: chia/daemon/keychain_server.py])

### Summary
`KeychainServer.get_keychain_for_request()` builds a cache key for non-default keychains by naively concatenating the caller-supplied `kc_user` and `kc_service` strings with no separator or length-prefixing. This is the same bug class as the Istio fragment issue: two different logical identities can be resolved to the same internal object because the code conflates distinct inputs into one ambiguous string before using it as an identity/authorization key (CWE-706 "Use of Incorrectly-Resolved Name or Reference" combined with CWE-863 "Incorrect Authorization").

### Finding Description
`get_keychain_for_request()` is: [1](#0-0) 

```python
user = request.get("kc_user", self._default_keychain.user)
service = request.get("kc_service", self._default_keychain.service)
if user == self._default_keychain.user and service == self._default_keychain.service:
    keychain = self._default_keychain
else:
    key = (user or "unnamed") + (service or "")
    if key in self._alt_keychains:
        keychain = self._alt_keychains[key]
    else:
        keychain = Keychain(user=user, service=service)
        self._alt_keychains[key] = keychain
return keychain
```

`kc_user` and `kc_service` are attacker/caller-controlled fields taken directly from the request dict sent over the daemon websocket, and `KeychainProxy.format_request()` sets them from its own `keychain_user`/`keychain_service` attributes when composing any keychain command: [2](#0-1) 

Because `key = user + service` (string concatenation with no delimiter), two different `(user, service)` pairs can produce an identical cache key — e.g. `user="ab", service="c"` and `user="a", service="bc"` both yield `"abc"`. Whichever pair is first seen creates and caches the real `Keychain(user=..., service=...)` instance under that ambiguous key; every subsequent request bearing the *other* pair silently receives the already-cached `Keychain` object instead of the one that actually corresponds to its own `(user, service)` identity, per `keychain_commands` dispatch in `handle_command()`: [3](#0-2) 

This is directly analogous to the Istio bug: one code path (the string that is used to key/authorize/route the request) is parsed/composed in a way that is inconsistent with the caller's actual intended identity, so the *effective* target the request operates on diverges from what the caller (or a security boundary) believes it is operating on.

### Impact Explanation
`Keychain(user=user, service=service)` partitions the keyring backend by user/service, which is the security boundary between different local logged-in identities using the same daemon (e.g. multiple wallet fingerprints/services sharing one keychain-server instance, as documented and tested via `_alt_keychains`). If a request for `(user_A, service_A)` collides with a previously-cached `(user_B, service_B)` due to the concatenation ambiguity, subsequent `get_key`, `get_keys`, `add_key`, `delete_key_by_fingerprint`, `delete_all_keys`, `get_public_key(s)`, `set_label`, `delete_label`, and other keychain RPCs routed through `run_request()` silently operate on the wrong identity's key material: [4](#0-3) 

This can expose fingerprints/public keys (and with `include_secrets=True`, private key material) belonging to a different logical user/service to a caller who only supplied a colliding `kc_user`/`kc_service` pair, or cause one identity's `delete_all_keys`/`delete_key_by_fingerprint` operation to silently mutate another identity's keychain — a concrete confidentiality/integrity break across what is supposed to be an isolated keychain namespace, without any exploit against TLS or the socket itself.

### Likelihood Explanation
Exploitation requires only knowledge of, or the ability to choose, the `kc_user`/`kc_service` strings sent in a keychain command over the local daemon websocket — no cryptographic material or malicious peer/node access is needed. Any local process capable of establishing an authorized daemon connection (a "local RPC caller" per the defined threat model) can pick a `kc_user`/`kc_service` pair to intentionally collide with another known/anticipated pairing and read or corrupt that identity's keychain. The collision is deterministic and trivial to construct (simple string concatenation with no delimiter), so likelihood is high once daemon access is available, though it is capped by the daemon being a locally-authenticated (mTLS) admin surface rather than an anonymous network endpoint.

### Recommendation
Use an unambiguous, delimiter-safe cache key, e.g. a tuple `(user, service)` as the dict key instead of string concatenation, or encode lengths/escape the delimiter (`f"{len(user)}:{user}:{service}"`). Never combine two independently-controlled strings into one identity/lookup key via naive concatenation, mirroring the general fix pattern for the Istio path/fragment class of bugs: normalize/structure the identity before it is used for routing or authorization decisions rather than composing free-form strings.

### Proof of Concept
1. Local caller A connects to the daemon and sends `add_private_key` (or any keychain command) with `kc_user="ab"`, `kc_service="c"`. `get_keychain_for_request()` computes `key = "ab" + "c" = "abc"`, creates `Keychain(user="ab", service="c")`, and caches it under `"abc"`.
2. Local caller B connects and sends `get_key` (with `include_secrets=True`) using `kc_user="a"`, `kc_service="bc"`. `get_keychain_for_request()` computes `key = "a" + "bc" = "abc"`, finds it in `_alt_keychains`, and returns caller A's `Keychain(user="ab", service="c")` instance instead of creating/using a keychain scoped to `("a", "bc")`.
3. Caller B's `get_key`/`get_keys`/`delete_all_keys` request is now served against caller A's key material, disclosing or mutating keys that belong to a different logical user/service, even though B never had `kc_user="ab"`/`kc_service="c"`.

    def get_keychain_for_request(self, request: dict[str, Any]) -> Keychain:
        """
        Keychain instances can have user and service strings associated with them.
        The keychain backends ultimately point to the same data stores, but the user
        and service strings are used to partition those data stores. We attempt to
        maintain a mapping of user/service pairs to their corresponding Keychain.
        """
        user = request.get("kc_user", self._default_keychain.user)
        service = request.get("kc_service", self._default_keychain.service)
        if user == self._default_keychain.user and service == self._default_keychain.service:
            keychain = self._default_keychain
        else:
            key = (user or "unnamed") + (service or "")
            if key in self._alt_keychains:
                keychain = self._alt_keychains[key]
            else:
                keychain = Keychain(user=user, service=service)
                self._alt_keychains[key] = keychain
        return keychain

    async def run_request(self, request_dict: dict[str, Any], request_type: type[Any]) -> dict[str, Any]:
        keychain = self.get_keychain_for_request(request_dict)
        if keychain.is_keyring_locked():
            return {"success": False, "error": KEYCHAIN_ERR_LOCKED}

        try:
            request = request_type.from_json_dict(request_dict)
        except Exception as e:
            return {
                "success": False,
                "error": KEYCHAIN_ERR_MALFORMED_REQUEST,
                "error_details": {"message": str(e)},
            }

        try:
            return {"success": True, **request.run(keychain).to_json_dict()}
        except KeychainFingerprintNotFound as e:
            return {
                "success": False,
                "error": KEYCHAIN_ERR_KEY_NOT_FOUND,
                "error_details": {"fingerprint": e.fingerprint},
            }
        except KeychainException as e:
            return {
                "success": False,
                "error": KEYCHAIN_ERR_MALFORMED_REQUEST,
                "error_details": {"message": str(e)},
            }

        """
        Overrides DaemonProxy.format_request() to add keychain-specific RPC params
        """
        if data is None:
            data = {}

        if self.keychain_user or self.keychain_service:
            data["kc_user"] = self.keychain_user
            data["kc_service"] = self.keychain_service
