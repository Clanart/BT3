### Title
GaslessSwapRouter owner can register an arbitrary/unvalidated token-factory-router triple, enabling theft of gasless-swap users' tokens - ([File: kaiax/gasless/impl/getter.go], [File: contracts/bindings/kip247/GaslessSwapRouter.go])

### Summary
The KIP-247 gasless module trusts the on-chain `GaslessSwapRouter` (GSR) contract as the sole source of truth for which tokens are "allowed" for gasless swaps and which DEX (`factory`/`router`) is used to execute the swap for a given token. The GSR owner registers this token/factory/router mapping via `addToken(token, factory, router)`, and the Kaia node's `GaslessModule.updateAddresses` blindly ingests whatever the GSR contract reports, exactly mirroring the Y2K pattern where an admin-supplied token/oracle pair is trusted without validation.

### Finding Description
`GaslessModule.updateAddresses` reads `swapRouter` and the list of allowed tokens directly from the GSR contract every block and populates `g.allowedTokens` with no independent verification of the token's legitimacy, nor of the `factory`/`router` DEX pair backing it: [1](#0-0) 

The GSR contract exposes an owner-gated `addToken(address token, address factory, address router)` function that binds an arbitrary ERC-20 token address to an arbitrary DEX `factory`/`router` pair with no on-chain validation that the router is a legitimate, correctly priced DEX, or that the factory actually produced that router: [2](#0-1) 

`IsApproveTx`/`IsSwapTx` in the Kaia client only check that `token` is in `g.allowedTokens` and that the router matches `g.swapRouter` (the GSR itself) — they never check the underlying DEX `factory`/`router` used inside `swapForGas`: [3](#0-2) 

Pricing validation performed by the node (`checkBalanceForSwap`) calls `GetAmountIn` on the GSR contract itself, which internally derives price from whatever `factory`/`router` was registered by the owner for that token via `addToken`: [4](#0-3) 

Because gasless swap flow works as: (1) proposer fronts KAIA via `LendTxGenerator`, (2) user's token is pulled by GSR via the approved allowance, (3) GSR swaps the token through the registered `factory`/`router` to recover KAIA, repay the proposer, and return the remainder to the user — an owner who registers a token with a malicious/misconfigured `factory`/`router` pair (e.g., a "router" contract that reports inflated `getAmountsOut`/`getAmountIn` results, or that routes swap proceeds to a third party instead of the GSR) can cause the swap step to under-deliver KAIA back to the contract while still debiting the user's full token amount, or cause the client-side balance/price pre-check to pass with a manipulated `GetAmountIn` while the real swap yields far less. This lets the owner siphon value between the token the user thought they were swapping and the actual DEX liquidity that executes the trade, precisely analogous to the reported Y2K bug where an admin supplies an unvalidated insured token/oracle pair to trick users and later exploit the mismatch. The `TokenAdded` event/binding confirms the token/factory/router relationship is set as raw, unchecked data: [5](#0-4) 

### Impact Explanation
This directly matches an "acceptance of an invalid transaction" / "gasless settlement theft" pattern: gasless swap users, who never chose or validated the DEX pair being used to liquidate their token for gas, can have their approved token balances drained through a malicious router the GSR owner privately controls, while proposers and users receive less KAIA than expected from the on-chain accounting the Kaia node trusts. This is a High-severity value-extraction path because it is fund-affecting and requires no cooperation from the victim beyond having previously approved/held a token registered by the (compromised or malicious) GSR owner.

### Likelihood Explanation
Likelihood is Medium: it requires the GSR contract owner (a governance/ops-level privileged role, analogous to the Y2K admin) to act maliciously or be compromised, which is the exact threat model described in the reference report ("Admin should not be able to steal user funds"). Since `addToken` performs zero validation of the factory/router relationship or price sanity, exploitation requires only a single `addToken` transaction plus normal user gasless-swap activity that the Kaia client automatically bundles.

### Recommendation
- Validate on-chain in `GaslessSwapRouter.addToken` that `router` is the canonical router deployed by `factory` for the `token`/base-asset pair (e.g., verify `factory.getPair(token, WKAIA)` and known router bytecode hash) before registering.
- Add a timelock/whitelist governance process for `addToken`/`removeToken` calls rather than a single-owner `onlyOwner` function.
- Have the Kaia `GaslessModule` cross-check the registered `factory`/`router` bytecode or a canonical registry rather than trusting the GSR's self-reported DEX info unconditionally.

### Proof of Concept
1. GSR owner calls `addToken(maliciousToken, maliciousFactory, maliciousRouter)` — accepted with no validation, as shown by the transactor binding with only an `onlyOwner`-style guard and no relationship check: [2](#0-1) 
2. Kaia node's `updateAddresses` (run every block) picks up `maliciousToken` as allowed and `swapRouter` unchanged, with no additional verification: [1](#0-0) 
3. A gasless user submits `GaslessApproveTx`/`GaslessSwapTx` for `maliciousToken`; `IsApproveTx`/`IsSwapTx` pass because they only check membership in `g.allowedTokens` and router identity, not the DEX pair correctness: [3](#0-2) 
4. During `swapForGas` execution, the malicious `factory`/`router` returns manipulated output/pricing, causing token value pulled from the user to not be fully returned as KAIA to repay the proposer/user, resulting in fund loss for the gasless user and/or proposer — the same "supply arbitrary, unvalidated asset metadata to trick users into a bad exchange" root cause as the referenced Y2K report.

Note: The actual Solidity source for `GaslessSwapRouter.sol` (its `swapForGas`/`addToken` implementation body) was not present in the indexed codebase — only the Go ABI bindings (`contracts/bindings/kip247/GaslessSwapRouter.go`) and tests (`tests/gasless_test.go`) were available. Full confirmation of the exact internal swap/commission logic would require inspecting that Solidity source directly; if you need the precise line-level guarantees of `swapForGas`'s repay/commission calculation, start a Devin session to pull and inspect the full `GaslessSwapRouter.sol` contract.

func (g *GaslessModule) updateAddresses(header *types.Header) error {
	g.gaslessInfoMu.Lock()
	defer g.gaslessInfoMu.Unlock()

	swapRouter, tokens, err := getGaslessInfo(g.Chain, header)
	// proceed even if there is something wrong with multicall contract
	if err != nil {
		g.swapRouter = common.Address{}
		g.allowedTokens = map[common.Address]bool{}
		logger.Warn("there is something wrong with multicall contract", "err", err.Error())
		return nil
	}

	g.swapRouter = swapRouter

	g.allowedTokens = map[common.Address]bool{}
	for _, addr := range tokens {
		// all tokens are allowed if nil
		if g.GaslessConfig.AllowedTokens == nil {
			g.allowedTokens[addr] = true
		}
		for _, allowed := range g.GaslessConfig.AllowedTokens {
			if addr == allowed {
				g.allowedTokens[addr] = true
			}
		}
	}
