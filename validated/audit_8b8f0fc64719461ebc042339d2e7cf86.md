### Title
Single Failing `KickoffStateMachine` Duty Halts All State Machine Block Processing — (`core/src/states/mod.rs`)

### Summary

In `process_block_parallel`, any error captured by **any** kickoff or round state machine during a block causes the entire function to return `Err`, halting processing for **all** state machines. This is a direct structural analog to the `KeeperOracle.commit` bug: a shared processing loop where one participant's failure bricks all others.

### Finding Description

`process_block_parallel` drives all `KickoffStateMachine` and `RoundStateMachine` instances forward on each finalized Bitcoin block. Individual state machine actions use `capture_error` to store errors softly into `context.errors` without stopping their own machine. However, after all machines run, the function aggregates every error from every context and returns a hard error if the combined list is non-empty: [1](#0-0) 

The errors that feed into this list come from kickoff duties dispatched via `capture_error`:

- `send_watchtower_challenge` — calls `get_tip_header_chain_proof()` + `prove_work_only()`, both of which can fail
- `send_operator_asserts_if_ready` — dispatches `Duty::SendOperatorAsserts`
- `send_disprove` — dispatches `Duty::VerifierDisprove`, which runs the full BitVM disprove computation [2](#0-1) 

The verifier's `send_watchtower_challenge` implementation calls `get_tip_header_chain_proof()` and `prove_work_only()`: [3](#0-2) 

If either call fails (e.g., "No finalized blocks in header chain proofs table" from `get_tip_header_chain_proof`, or a prover resource failure from `prove_work_only`), the error is captured into `context.errors`. When `process_block_parallel` collects it, the entire block processing returns `Err`, and `next_height_to_process` is **not** advanced: [4](#0-3) 

The `handle_event` caller propagates this error with `?`: [5](#0-4) 

### Impact Explanation

When one kickoff's duty fails persistently, the state manager cannot advance any kickoff or round state machine. Concretely:

1. **Kickoff A** (legitimate operator) reaches `TimeToSendWatchtowerChallenge`. The header chain prover is not yet ready — `get_tip_header_chain_proof` returns `Err("No finalized blocks")`. This error is captured.
2. `process_block_parallel` sees the non-empty error list and returns `Err`. `next_height_to_process` stays at the same height.
3. **Kickoff B** (malicious operator) has all asserts and acks present; `disprove_if_ready` would fire and slash the operator — but it never runs because the block processing failed before reaching kickoff B's machine.
4. The operator's `AssertTimeout` or `ChallengeTimeout` window expires. The operator is reimbursed for a fraudulent withdrawal, and bridged BTC is lost.

The `Duty::VerifierDisprove` path has the same structure: if the disprove computation fails for one kickoff (e.g., a bug in `verify_disprove_conditions` for a specific operator-crafted assert), it permanently blocks all other kickoffs from being disproved. [6](#0-5) 

### Likelihood Explanation

- **Transient trigger (medium likelihood)**: The header chain prover being behind the finalized block tip is a normal operational condition during startup or after a restart. Any kickoff that fires `TimeToSendWatchtowerChallenge` during this window will fail and block all other machines until the prover catches up.
- **Persistent trigger (lower likelihood but higher impact)**: A malicious operator who can craft assert transactions that cause `verify_disprove_conditions` to error (rather than return `None` or `Some`) would permanently block all other kickoffs from being disproved, allowing their own fraudulent withdrawal to succeed.

### Recommendation

Replace the all-or-nothing error aggregation with per-machine isolation. Errors from one state machine should be logged and skipped, not propagated to block all others:

```rust
// Instead of:
if !all_errors.is_empty() {
    return Err(eyre::eyre!("Multiple errors occurred: {:?}", all_errors));
}

// Use:
for e in &all_errors {
    tracing::error!("State machine error (non-fatal, continuing): {:?}", e);
}
// Do NOT return Err — continue processing other machines
```

This mirrors the recommended fix in the external report: wrap individual callbacks in `try...catch` so one failure does not abort the entire batch.

### Proof of Concept

1. Deploy two deposits, each with a challenged kickoff (kickoff A and kickoff B).
2. Advance to the block height where `TimeToSendWatchtowerChallenge` fires for kickoff A.
3. Ensure the header chain prover has no finalized blocks proven yet (e.g., restart the verifier before the prover task runs).
4. Observe: `send_watchtower_challenge` for kickoff A calls `get_tip_header_chain_proof()`, which returns `Err("No finalized blocks in header chain proofs table")`.
5. `capture_error` stores this in `context.errors`.
6. `process_block_parallel` returns `Err`; `next_height_to_process` is not advanced.
7. Kickoff B, which has all asserts and acks present and is ready for `disprove_if_ready`, is never processed.
8. The malicious operator for kickoff B waits for `AssertTimeout` to expire and claims reimbursement, extracting bridged BTC without being slashed.

    async fn send_watchtower_challenge(
        &self,
        kickoff_data: KickoffData,
        deposit_data: DepositData,
        dbtx: DatabaseTransaction<'_>,
    ) -> Result<(), BridgeError> {
        let current_tip_hcp = self
            .header_chain_prover
            .get_tip_header_chain_proof()
            .await?;

        let (work_only_proof, work_output) = self
            .header_chain_prover
            .prove_work_only(current_tip_hcp.0)
            .await?;

        let g16: [u8; 256] = work_only_proof
            .inner
            .groth16()
            .wrap_err("Work only receipt is not groth16")?
            .seal
            .to_owned()
            .try_into()
            .map_err(|e: Vec<u8>| {
                eyre::eyre!(
                    "Invalid g16 proof length, expected 256 bytes, got {}",
                    e.len()
                )
            })?;

        let g16_proof = CircuitGroth16Proof::from_seal(&g16);
        let mut commit_data: Vec<u8> = g16_proof
            .to_compressed()
            .wrap_err("Couldn't compress g16 proof")?
            .to_vec();

        let total_work =
            borsh::to_vec(&work_output.work_u128).wrap_err("Couldn't serialize total work")?;

        #[cfg(test)]
        {
            let wt_ind = self
                .config
                .test_params
                .all_verifiers_secret_keys
                .iter()
                .position(|x| x == &self.config.secret_key)
                .ok_or_else(|| eyre::eyre!("Verifier secret key not found in test params"))?;

            self.config
                .test_params
                .maybe_disrupt_commit_data_for_total_work(&mut commit_data, wt_ind);
        }

        commit_data.extend_from_slice(&total_work);

        tracing::info!("Watchtower prepared commit data, trying to send watchtower challenge");

        self.queue_watchtower_challenge(kickoff_data, deposit_data, commit_data, dbtx)
            .await
    }
