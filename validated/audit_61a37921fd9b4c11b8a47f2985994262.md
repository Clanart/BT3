This confirms the mechanism: `rejectable()` returns `false` for `VmExecutionError::Runtime(..)` and `VmExecutionError::EarlyReturn(_)`, meaning arithmetic errors, `NoSuchToken`, `UnwrapFailure`-type errors, `asserts!` failures, etc. thrown from within a `restrict-assets?`/`as-contract?` body are treated as non-rejectable and fall through to the commit path in `evaluate_body_with_allowance_check`.

### Title
`evaluate_body_with_allowance_check` Commits Partial State on Non-Rejectable Body Errors, Bypassing Allowance/Post-Condition Enforcement - (File: clarity/src/vm/functions/post_conditions.rs)

### Summary
`evaluate_body_with_allowance_check` (used by `restrict-assets?` and `as-contract?`) evaluates the protected body inside a closure and inspects the resulting `Result` only to decide whether to abort immediately (`err.rejectable()`). For non-rejectable errors — `VmExecutionError::Runtime(..)` (e.g. `ArithmeticOverflow`, `NoSuchToken`, `UnwrapFailure`, `DivisionByZero`) and `VmExecutionError::EarlyReturn(_)` (`asserts!`/`unwrap!` failures) — execution does not return early. Instead the code proceeds to compute `asset_maps`, runs `check_allowances`, and — if no allowance violation is detected — **commits** the sub-context, even though the body itself errored out partway through and the transaction ultimately still returns `Err(e)` to the caller.

### Finding Description [1](#0-0) 

The control flow is:
1. Body expressions are evaluated in a loop inside a closure; if expression `k` errors with a non-rejectable error, evaluation stops there, but everything before expression `k` (including any asset transfers already executed, e.g. `stx-transfer?`, `ft-transfer?`, `nft-transfer?`) has already mutated `exec_state.global_context`.
2. Because `err.rejectable()` is `false` for `Runtime`/`EarlyReturn` errors, the "abort early" branch is skipped.
3. `check_allowances` is run against whatever partial asset movement occurred before the error, using the allowances declared by the caller.
4. If those partial movements happen to satisfy the allowances (which is a much smaller, partial set of movements than the caller intended to protect against), `exec_state.global_context.commit()` is called — the partial state mutation becomes permanent.
5. Only after commit does the function return `Err(e)` for the original body error, terminating the *rest* of the contract call, but the already-committed partial writes are now durable (assuming a higher call frame doesn't itself roll back — which is not guaranteed for `Runtime`/`EarlyReturn` errors specifically, since those are exactly the class of errors Clarity is designed to let a contract catch/recover from via `try!`/`match`/`unwrap!` at a higher scope, i.e. the transaction is *not* necessarily aborted).

This is a direct structural analog of the report's core defect: an error thrown from an *internal* (non-external) code path is not actually treated as a full-stop condition by the surrounding guard logic (the `try`/`catch`-style dispatch in `err.rejectable()`), so the "protective" wrapper (`restrict-assets?`/`as-contract?`, whose entire purpose is analogous to the escrow/asset-protection logic in the report) ends up committing asset movements that were never fully vetted against the complete, intended set of allowances, because the body never finished running and the allowance list itself may not even have been fully evaluated for later assets in a multi-expression body.

### Impact Explanation
This breaks the core equality that `restrict-assets?`/`as-contract?` is meant to guarantee: *"every asset movement performed inside the protected body must be covered by a declared allowance, or the whole scope is rolled back."* Instead, a contract can:
- Perform an authorized transfer that satisfies a narrow allowance,
- Then trigger a `Runtime`/`EarlyReturn` error (trivially, e.g. `(unwrap! none u0)` or `(/ x 0)`),
- And still have the initial transfer permanently committed, while the caller only sees an error return and may believe (based on normal try!/match semantics) that nothing happened.

This matches the High/Critical bar: "an asset moving past its post-conditions" for the calling contract logic that relies on `restrict-assets?`/`as-contract?` as an atomic guard — the asset move is not actually undone by an apparent failure, and a caller contract that wraps this in `(match (as-contract? ...) ok-val ... err-val ...)` and treats the `err` branch as "nothing happened, safe to retry/ignore" will be wrong, since state was already mutated.

### Likelihood Explanation
Reachable by any unprivileged Clarity contract author: they only need a contract that calls `restrict-assets?`/`as-contract?` with a multi-statement body where an early statement performs an allowed asset transfer and a later statement deterministically triggers a `Runtime`/`EarlyReturn` error (division by zero, unwrap failure, etc.) — both trivial and fully within an ordinary user's control, no privileged role or off-chain assumption needed.

### Recommendation
In `evaluate_body_with_allowance_check`, any error from body evaluation — rejectable or not — should cause `exec_state.global_context.roll_back()` before returning, unless the intent is genuinely to allow partial commits gated purely by `check_allowances`. If partial commits are intended by design (i.e., "the allowances are the only enforcement point, regardless of whether the body fully completed"), that behavior should be explicitly documented and covered by tests demonstrating that a caller cannot be misled by receiving `Err` while state was mutated; otherwise, gate the commit strictly on `eval_result.is_ok()` in addition to the allowance check.

### Proof of Concept
Conceptually:
```clarity
(as-contract?
  ((with-ft .token "asset" u10))
  (contract-call? .token transfer u10 tx-sender 'SPOWNER) ;; allowed transfer, satisfies allowance
  (unwrap! none u0)) ;; triggers EarlyReturn error, non-rejectable
```
Tracing `evaluate_body_with_allowance_check`:
- `eval_result` = `Err(VmExecutionError::EarlyReturn(...))`, `rejectable()` = `false` → no early abort. [2](#0-1) 
- `check_allowances` sees only the FT transfer of `u10`, which satisfies the `with-ft` allowance of `u10` → `Ok(None)`.
- `exec_state.global_context.commit()` is called, making the FT transfer permanent.
- Function returns `Err(EarlyReturn(...))` to the caller, even though the transfer already happened.

    let eval_result: Result<Option<Value>, VmExecutionError> =
        (|| -> Result<Option<Value>, VmExecutionError> {
            let mut last_result = None;
            for expr in body_exprs {
                let result =
                    eval(expr, exec_state, invoke_ctx, context)?.clone_with_cost(exec_state)?;
                last_result.replace(result);
            }
            Ok(last_result)
        })();

    // A block-rejecting error raised inside the body must abort the transaction.
    if matches!(&eval_result, Err(err) if err.rejectable()) {
        exec_state.global_context.roll_back()?;
        return Err(eval_result.unwrap_err());
    }

    let asset_maps = exec_state.global_context.get_readonly_asset_map()?;

    // If the allowances are violated:
    // - Rollback the context
    // - Return an error with the index of the violated allowance
    match check_allowances(asset_owner, allowances, asset_maps, epoch) {
        Ok(None) => {}
        Ok(Some(violation_index)) => {
            exec_state.global_context.roll_back()?;
            return Ok(Value::error(Value::UInt(violation_index))?);
        }
        Err(e) => {
            exec_state.global_context.roll_back()?;
            return Err(e);
        }
    }

    exec_state.global_context.commit()?;
