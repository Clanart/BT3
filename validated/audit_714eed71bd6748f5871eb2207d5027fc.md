But the payout paths — `withdraw()` and the `SweepDust` branch of `onAccept()` — bypass `SafeERC20` entirely and use a raw low-level `.call` with the `IERC20.transfer.selector`, checking only the call's `success` boolean and ignoring the ABI-encoded return value [2](#0-1) [3](#0-2) .

### Title
Unchecked ERC20 return value in escrow withdraw/sweep allows silent fund loss on false success - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`withdraw()` and the `SweepDust` handler in `onAccept()` release escrowed intent funds using a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the low-level `call` succeeded, not that the token's returned boolean was `true`. This is the direct analog of the ERC721 `transferFrom` bug: instead of using the "safe" wrapper (`SafeERC20`, or `safeTransferFrom`/`safeTransfer`) that validates the operation actually succeeded, the code accepts a call as successful even when the underlying asset movement silently failed.

### Finding Description
In `withdraw()`, escrow accounting (`_orders[body.commitment][token] -= amount`) and order finalization (`_filled[body.commitment] = beneficiary`) happen unconditionally, gated only on `success` from the raw call [4](#0-3) . Any ERC20/TRC20 token that returns `false` on failure instead of reverting (a well-known non-standard-but-common pattern, especially prevalent on Tron/TRC20 tokens which this file specifically targets) will make the `call` succeed while the beneficiary receives nothing. The `success` flag from `.call` reflects only that the callee didn't revert — it says nothing about the ABI-encoded `bool` return value that `IERC20.transfer` is supposed to return. The same pattern repeats in the `SweepDust` branch of `onAccept()` [5](#0-4) , and again for transaction fee payout [6](#0-5) .

This directly contrasts with the deposit-side code in the same contract, which correctly uses `SafeERC20.safeTransferFrom` (imported and aliased via `using SafeERC20 for IERC20;`) [7](#0-6) , confirming the safe pattern is available and used elsewhere but was omitted specifically on the payout path — the same asymmetry as the `transferFrom`/`safeTransferFrom` bug in the original report (safety wrapper present but not used where asset custody actually changes hands).

### Impact Explanation
Because `_orders[...]` is decremented and `_filled[...]` is set to mark the order as settled regardless of whether tokens were actually delivered, a false-returning token transfer causes the escrow to be permanently marked "released"/"refunded" while the beneficiary's balance never changes. This is unrecoverable loss of bridged/escrowed funds — the beneficiary cannot re-claim, and the recorded escrow balance is destroyed. This satisfies the bounty's fund-loss and false-state-acceptance impact categories: value is destroyed/locked in the intent gateway's internal accounting with no path for the rightful beneficiary to recover it.

### Likelihood Explanation
Reaching this path requires no privileged actor — any solver/user can place an order denominated in a token whose `transfer` returns `false` on failure (or that has non-standard behavior) rather than reverting, or the condition can be triggered by ordinary transient failure conditions of such tokens (e.g., paused/blacklist states returning `false`). The `onAccept`/`withdraw` flow is invoked automatically by the host on `RedeemEscrow`/`RefundEscrow`/`SweepDust` message delivery, so no relayer or admin collusion is needed — only a token that doesn't strictly follow the revert-on-failure convention needs to be in the input/output set of an order.

### Recommendation
Replace all `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout patterns in `withdraw()` and the `SweepDust` handling of `onAccept()` with `SafeERC20.safeTransfer`, mirroring the deposit path's use of `safeTransferFrom`. This ensures both call-level revert and return-value semantics are validated before escrow state is finalized.

### Proof of Concept
1. An order is placed with an input/output token that implements ERC20 but returns `false` (rather than reverting) on a failed `transfer` (e.g., a token that is paused, or the beneficiary is blacklisted).
2. The order proceeds to settlement; the host delivers a `RedeemEscrow` message, invoking `onAccept` → `withdraw()` [8](#0-7) .
3. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes; the token contract returns `false` without reverting, so `success` is `true` [9](#0-8) .
4. `_orders[body.commitment][token] -= amount` executes, and `_filled[body.commitment] = beneficiary` is set, permanently marking the order filled [10](#0-9) .
5. The beneficiary's token balance is unchanged, but the escrowed funds are gone from contract accounting with no remaining code path to reclaim them — funds are lost.
