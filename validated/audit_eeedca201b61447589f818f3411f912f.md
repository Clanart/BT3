### Title
`Scanner::scan_transaction` reports sub-dust outputs as spendable `ReceivedOutput`s, letting an attacker burn vault funds as fees - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The external report describes a "sweep" function that transfers the contract's entire balance to a caller-chosen recipient — an unprotected path by which value held in an intermediate location is extracted by an unprivileged party. The analogous shape in Serai is the Bitcoin wallet's reception/spend path: `Scanner::scan_transaction` accepts *any* on-chain output paying to a registered `script_pubkey` as a spendable `ReceivedOutput`, with no minimum-value check, and `SignableTransaction::new` will happily consume such outputs as inputs even when each input costs more in fees than it is worth. An attacker sends dust transactions to the multisig's public deposit address; each dust output is treated as real funds, and when it is later used as an input the network's fee cost to spend it is burned to miners — draining the honest inputs co-spent in the same transaction.

### Finding Description
`Scanner::scan_transaction` iterates all outputs and pushes a `ReceivedOutput` whenever `self.scripts.get(&output.script_pubkey)` matches, unconditionally on `output.value`. `scan_block` has the same property for every non-filtered transaction (and additionally includes immature coinbase outputs, though `processor` currently skips `txdata[0]`).

`SignableTransaction::new` then treats every supplied `ReceivedOutput` as worth its full face value: `input_sat` is the sum of all input values, and each input adds ~57 vbytes (~230 WU) to the transaction per `calculate_weight_vbytes`. There is no check that an input's value exceeds the marginal fee it adds. So a 1-satoshi attacker-sent input contributes 1 sat to `input_sat` while adding `fee_per_vbyte * 57` sats of cost; the deficit is silently paid out of the honest inputs' change (or as extra fee if `change` is `None`, since all leftover becomes fee). This is exactly the reported class: value pooled in an intermediate place (the scanner's output set / the transaction's input set) that an unprivileged party causes to be transferred out (to miners) without any authorization check on their contribution.

The `ReceivedOutput` is also fully attacker-serializable via `ReceivedOutput::read`, which decodes `offset`, `TxOut`, and `OutPoint` from untrusted bytes without binding the `outpoint`/`TxOut` to the registered key's `script_pubkey` — a crafted `ReceivedOutput` claims an arbitrary `offset`, and `SignableTransaction::new` trusts it (`offsets` are taken verbatim, `prevouts` from the embedded `TxOut`).

### Impact Explanation
Each injected dust input destroys `fee_per_vbyte * ~57 − value` satoshis of multisig funds, paid to miners as fee. Repeated injections scale linearly with attacker spend (sub-dust outputs cost the attacker only the relay fee of their own transaction). Additionally, outputs below Bitcoin's dust relay rules or immature coinbase outputs reported as `ReceivedOutput`s are "funds reported received that are not spendable": a `SignableTransaction` built over them either burns their deficit or produces a transaction the network rejects, stalling the signing plan.

### Likelihood Explanation
The attacker's only requirement is knowledge of a registered `script_pubkey`, which is public on-chain after any deposit, plus the ability to send ordinary Bitcoin transactions — a fully unprivileged path. The vulnerable acceptance is unconditional in `scan_transaction` (lines 205–211 of `mod.rs`) and unconditional consumption in `SignableTransaction::new`. (Note: `processor`'s outer scan loop filters `output.balance().amount.0 >= N::DUST`, which mitigates the deployed path; the bug lives in `bitcoin-serai` itself, where neither the scanner nor the transaction builder enforces a spendability threshold, and the `ReceivedOutput::read` trust gap is unconditional.)

### Recommendation
Apply a minimum-value floor inside `Scanner::scan_transaction`/`ReceivedOutput::read` (e.g., reject outputs below the network `DUST` constant defined in `send.rs`, or a documented spend-cost multiple) rather than relying on downstream callers. In `SignableTransaction::new`, drop inputs whose value is less than their marginal fee contribution, and verify each `prevout.script_pubkey` corresponds to `group_key + offset·G` at construction time (the check currently exists only in `multisig()`, after the fee/change math has already committed to the input set).

### Proof of Concept
```rust
// Attacker sends N dust outputs (e.g., 1 sat each) to the known deposit
// script_pubkey in a single transaction. Wallet side:
let outputs = scanner.scan_transaction(&attacker_tx); // all N returned as ReceivedOutput
// Later, honest inputs are combined with the dust:
let signable = SignableTransaction::new(
    [honest_inputs, dust_outputs].concat(), // dust accepted unconditionally
    &payments, Some(change), None, fee_per_vbyte,
).unwrap();
// Each dust input adds ~57 vbytes of fee while contributing 1 sat;
// honest change is reduced by ~(fee_per_vbyte*57 - 1) * N sats,
// paid to miners — value extracted from pooled funds by an unprivileged party.
```
