### Title
Missing MMR-leaf freshness check in the native ECDSA BEEFY verifier allows authority-set rotation to be silently suppressed while `latest_beefy_height` still advances - (File: modules/consensus/beefy/verifier/src/lib.rs, evm/src/consensus/EcdsaBeefy.sol)

### Summary
The literal claim in the question ("`beefy_next_authority_set.id < trusted_state.next_authorities.id` is silently accepted") is not itself a bug — the rotation-guard `if mmr.latest_mmr_leaf.beefy_next_authority_set.id > trusted_state.next_authorities.id` is a monotonicity check that is correct *as long as the submitted MMR leaf is the leaf actually appended at the commitment's `block_number`*. However, tracing the code shows that this precondition is **not enforced** on the native (ECDSA) verification path, even though the codebase explicitly recognizes and has already fixed the exact same class of bug on the parallel SP1 (ZK) path.

### Finding Description
`verify_mmr_update_proof` accepts an arbitrary, relayer-chosen `mmr.mmr_proof.leaf_indices[0]` and only checks that this leaf is included under the signed `mmr_root`: [1](#0-0) 

Since an MMR is append-only, *any* historical leaf (including ones committing to a `beefy_next_authority_set` that is now stale/retired) verifies correctly against a *newer* `mmr_root` produced by a legitimately-signed, high-`block_number` commitment. The function then does: [2](#0-1) 

Because the leaf is not pinned to `block_number - 1`, an unprivileged submitter can pair a real, validly-signed, high-height commitment (obtained from public relay-chain data — no malicious validator/relayer collusion required) with an **old** MMR leaf from before a real rotation occurred. The result:
- `trusted_state.latest_beefy_height` advances to the new height (satisfying the `StaleHeight` freshness check at the top of the function).
- The rotation guard (`> trusted_state.next_authorities.id`) never fires because the replayed leaf's `beefy_next_authority_set.id` is not newer than what the client already knows.
- The client's `current_authorities`/`next_authorities` become permanently desynchronized from the real relay chain's authority sets while `latest_beefy_height` has already moved past the point where the real rotation occurred.

The exact same attack is already documented and fixed for the SP1 path: [3](#0-2) 
with a dedicated `Error::StaleMmrLeaf` variant and unit test: [4](#0-3) 

No equivalent `parent_number + 1 == block_number` check exists in the native `verify_mmr_update_proof`, nor in its Solidity mirror, `EcdsaBeefy.verifyMmrUpdateProof`, which has the identical unguarded pattern: [5](#0-4) 
(compare to `SP1Beefy.sol`, which does enforce it: `if (uint256(proof.mmrLeaf.parentNumber) + 1 != commitment.blockNumber) revert StaleMmrLeaf();`)

### Impact Explanation
This lets an unprivileged proof submitter cause the consensus client (Substrate `verify_mmr_update_proof` / EVM `EcdsaBeefy`) to accept false/incomplete state about relay-chain authority-set rotation while advancing its trusted height — a false-state-acceptance condition. Once desynchronized, the client continues trusting an authority set the real chain has already retired for future height comparisons, and legitimate commitments from the chain's actual current epoch may later be rejected as `UnknownAuthoritySet`, or (in the worst case, if a retired key set is later compromised) create a long-range-attack surface the rotation mechanism was designed to prevent. This directly falls under the "consensus proofs ... must never let false remote state become trusted" pivot.

### Likelihood Explanation
Medium-high: the only requirements are (1) a genuinely, currently-valid signed BEEFY commitment at a height beyond the last verified height (public relay-chain data, no validator collusion needed), and (2) freedom to choose which historical MMR leaf/leaf-index to pair with it in the proof — both of which are fields the caller controls when submitting a consensus proof/extrinsic.

### Recommendation
Add the same freshness constraint used in `sp1.rs` to the native path: require `mmr.latest_mmr_leaf.parent_number + 1 == mmr.signed_commitment.commitment.block_number` (or otherwise force `leaf_index` to correspond to the leaf appended at `block_number`) in `verify_mmr_leaf`/`verify_mmr_update_proof`, and apply the equivalent fix to `EcdsaBeefy.verifyMmrUpdateProof` in Solidity.

### Proof of Concept
1. Let the light client trust `current_authorities.id = N`, `next_authorities.id = N+1`, `latest_beefy_height = H0`.
2. On the real relay chain, authorities rotate at height `H1 > H0` (next set becomes `N+2`), then further blocks are produced and signed under `N+1`/`N+2`.
3. An unprivileged submitter fetches a legitimately signed commitment at `block_number = H2 >> H1`, still validly signed by supermajority of `current_authorities`/`next_authorities` known to the client (`N` or `N+1`), and pairs it with an MMR leaf/leaf-index from *before* `H1` (valid under append-only MMR against the `H2` root).
4. Submit via the public consensus-proof extrinsic/contract call; `verify_mmr_update_proof`/`EcdsaBeefy.verifyMmrUpdateProof` accepts it, setting `latest_beefy_height = H2` without updating `next_authorities` to `N+2`.
5. Assert the client's tracked authority-set state no longer matches the real relay chain's rotation history at height `H2`, despite `latest_beefy_height` having advanced past `H1`.

fn verify_mmr_leaf<H: Keccak256 + Send + Sync>(
	mmr: &MmrProof,
	mmr_root: H256,
) -> Result<(), Error> {
	// `leaf_indices` is supplied by the relayer in the unsigned consensus message;
	// an empty vector previously panicked the runtime via the unchecked `[0]` index
	// after the BEEFY signature and authority membership checks had already succeeded.
	// This verifier checks a single MMR leaf, so reject any proof that does not carry
	// exactly one leaf index.
	if mmr.mmr_proof.leaf_indices.len() != 1 {
		Err(Error::InvalidMmrProof)?
	}
	let leaf_index = mmr.mmr_proof.leaf_indices[0];
	let leaf_hash = H::keccak256(&mmr.latest_mmr_leaf.encode());
	let mmr_size = leaf_index_to_mmr_size(leaf_index);

	let mmr_proof = MmrMerkleProof::<[u8; 32], KeccakMerge<H>>::new(
		mmr_size,
		mmr.mmr_proof.items.iter().map(|h| (*h).into()).collect(),
	);
	let leaf_pos = leaf_index_to_pos(leaf_index);
	let leaf = (leaf_pos, leaf_hash.into());
	let valid = mmr_proof
		.verify(mmr_root.into(), vec![leaf])
		.map_err(|e| Error::MmrVerificationFailed(e.to_string()))?;

	if !valid {
		Err(Error::InvalidMmrProof)?
	}

	Ok(())
}
