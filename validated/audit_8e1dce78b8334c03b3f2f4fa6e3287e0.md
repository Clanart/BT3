### Title
`SchnorrAggregate::verify` derives aggregation weights only from the challenges, never binding the nonces/public keys, allowing trivial forgery of the aggregate equation - (File: crypto/schnorr/src/aggregate.rs)

### Summary
Like the CVE (a security check that only binds part of the input, letting attacker-controlled fields bypass it), `SchnorrAggregate::verify` authenticates the aggregate Schnorr equation `Σ z_i·R_i + z_i·c_i·P_i − s·G = 0` with weights `z_i` that bind only the challenges, not the nonces `R_i`. An attacker who can choose `R_i` (all inputs are fully public/attacker-controlled) can solve for one `R` to cancel the equation and forge an aggregate signature for arbitrary keys and challenges without knowing any discrete logarithm.

### Finding Description
In `crypto/schnorr/src/aggregate.rs:127-146`, `verify` builds a `DigestTranscript` over `dst` and appends only each challenge scalar (`append_message(b"challenge", challenge.to_repr())`), then draws each weight via `weight(&mut digest)` (lines 132-143). The `Rs` and `keys` are never appended to the digest. The final check is `multiexp_vartime(&pairs).is_identity()` over `z_i·R_i`, `z_i·c_i·P_i`, and `-s·G` (lines 138-145).

Because the weights are deterministic functions of only `dst` and the challenges, the attacker can compute every `z_i` before choosing any `R_i`. They pick arbitrary `s` and arbitrary `R_1..R_n`, then set

```
R_0 = z_0^{-1} · ( s·G − Σ_{i≥1} z_i·R_i − Σ_i z_i·c_i·P_i )
```

which makes the batched equation identically zero. No discrete log knowledge is required anywhere — `R_0` is just a curve point, and `read_G` happily accepts it since it is canonical (crypto/ciphersuite/src/lib.rs:91-101). This is exactly the failure mode the cited paper (eprint 2021/350) prevents by making each coefficient bind `(key, nonce, message)` — here only the challenge is bound.

Notably, `BatchVerifier::queue` in crypto/multiexp/src/batch.rs:46-48 pins the first statement's weight to `ONE` precisely so an attacker cannot scale/cancel statements; `SchnorrAggregate::verify` performs the same style of randomized linear-combination check but leaves every weight a predictable, attacker-computable scalar, which is strictly weaker than pinning plus binding to the full statement.

### Impact Explanation
Any caller that verifies an aggregate Schnorr signature via `SchnorrAggregate::read`/`verify` accepts a forgery. The attacker needs only public data (the set of `(P_i, c_i)` pairs and the DST) — an unprivileged party reachable input, satisfying the reachable-path requirement. Result: a forged aggregate signature accepted as valid, i.e., signature forgery against an in-scope verification API.

### Likelihood Explanation
The exploit is deterministic and requires zero secret knowledge; any untrusted `Rs`/`s` bytes deserialized via `SchnorrAggregate::read` (lines 77-88) can be crafted to pass `verify`. Cost is one multiexp's worth of scalar arithmetic performed offline by the attacker.

### Recommendation
Bind the full statement into the weight transcript: `append_message` each `R_i` and each public key `P_i` (and any message binding) into `digest` before drawing `weight()`, and/or pin `z_0 = 1` as `BatchVerifier::queue` does. Without both, the linear combination is underdetermined and forgeable.

The root cause is at crypto/schnorr/src/aggregate.rs:132-145 — the digest binds `challenge` fields only, so `Rs` are unconstrained unknowns in an equation the attacker fully controls.
