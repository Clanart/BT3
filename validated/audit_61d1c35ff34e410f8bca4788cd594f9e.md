### Title
Modified-row line-selection checkbox always reads the same column's line number, silently dropping the paired line from partial-commit selection - (File: app/src/ui/diff/side-by-side-diff.tsx)

### Summary
`onLineNumberCheckedChanged` in `side-by-side-diff.tsx` is supposed to update the selection state for both the "before" (deleted) and "after" (added) line numbers of a diff row when the user toggles a line-selection checkbox. Instead, both lookups use the exact same `column` argument, so for `Modified` rows only one side's line number is ever computed and applied to the selection — twice, redundantly — while the other side is never touched.

### Finding Description
`getDiffLineNumber`/`getDiffRowLineNumber` return different line numbers depending on which `DiffColumn` (`Before` or `After`) is passed in for a `Modified` row: [1](#0-0) 

`onLineNumberCheckedChanged` is the handler wired to the checkbox `onChange` in `side-by-side-diff-row.tsx` (via `onLineNumberCheckedChanged`), and is meant to translate a single checkbox click into selection updates for the underlying unified-diff line index(es): [2](#0-1) 

The bug: both `lineBefore` and `lineAfter` are computed by calling `this.getDiffLineNumber(row, column)` with the *same* `column` parameter that was passed into the handler, rather than explicitly querying `DiffColumn.Before` and `DiffColumn.After` respectively. This is structurally identical to the Weiroll flaw — a routine that is supposed to resolve two distinct indices/values ends up always resolving the same one because a shared/generic parameter is reused instead of the value-specific one.

For `Added`/`Deleted` rows this has no visible effect (both branches return the same `row.data.diffLineNumber`), which is why normal add/delete checkbox tests pass. But for `Modified` rows (a line that is simultaneously a deletion in the old file and an addition in the new file, rendered as one row with two checkboxes/columns in side-by-side view), clicking either checkbox will only ever update the diff-line-number belonging to whichever `column` was clicked — applied twice — and never touches the line number of the *other* column.

### Impact Explanation
This directly falls under "silent corruption of what the user commits or pushes." A user reviewing a side-by-side diff of a repository (potentially attacker-influenced content, e.g. a maliciously crafted file whose diff produces many `Modified` rows) who intends to stage/commit only a specific paired before/after line via the checkbox UI may end up committing a patch that does not match what was visually selected: the counterpart line (deletion or addition) silently remains at its default selection state rather than the state the user just set. Because `formatPatch`/`formatPatchToDiscardChanges` build the actual git patch purely from `DiffSelection.isSelected(absoluteIndex)`, the resulting staged/committed diff can differ from user intent without any error or warning, which is exactly the kind of silent commit corruption this bug class targets.

### Likelihood Explanation
This triggers through completely ordinary UI interaction — no crafted repo required beyond a file producing `Modified` rows in the side-by-side diff view (any file with adjacent removed+added lines that get paired) — and no confirmation step catches the discrepancy, so it is easily reachable in normal usage whenever a user partially selects lines in the side-by-side diff.

### Recommendation
Fix `onLineNumberCheckedChanged` to query both columns explicitly instead of reusing the shared `column` argument for both lookups, e.g. compute `lineBefore = this.getDiffLineNumber(row, DiffColumn.Before)` and `lineAfter = this.getDiffLineNumber(row, DiffColumn.After)`.

### Proof of Concept
1. Modify a file such that a line changes content (e.g. `line1` → `line1-updated`), producing a `Modified` row in side-by-side diff view.
2. In the Changes view, uncheck the "before" (deleted) checkbox for that row while leaving the "after" (added) checkbox checked, or vice versa.
3. Observe (via `onLineNumberCheckedChanged` at [3](#0-2) ) that both internal calls resolve to the line number of the clicked column only — the intended selection change never propagates to the paired column's diff line index.
4. Commit the partial selection; inspect the generated patch (via `formatPatch`) and confirm it does not match the visual selection shown in the UI (the counterpart line's inclusion/exclusion silently reflects its previous/default state, not what was displayed as toggled).

Note: I could not verify via `git blame`/commit history when this discrepancy was introduced (blame tool call failed due to missing `ref` parameter), so I cannot confirm whether this is a recent regression or a long-standing latent bug; this should be verified with a full git history check in a Devin session.

  private onLineNumberCheckedChanged = (
    row: number,
    column: DiffColumn,
    isSelected: boolean
  ) => {
    if (this.props.onIncludeChanged === undefined) {
      return
    }

    let selection = this.getSelection()
    if (selection === undefined) {
      return
    }

    const lineBefore = this.getDiffLineNumber(row, column)
    const lineAfter = this.getDiffLineNumber(row, column)

    if (lineBefore !== null) {
      selection = selection.withLineSelection(lineBefore, isSelected)
    }

    if (lineAfter !== null) {
      selection = selection.withLineSelection(lineAfter, isSelected)
    }

    this.props.onIncludeChanged(selection)
  }

  private getDiffRowLineNumber(row: SimplifiedDiffRow, column: DiffColumn) {
    if (row.type === DiffRowType.Added || row.type === DiffRowType.Deleted) {
      return row.data.diffLineNumber
    }

    if (row.type === DiffRowType.Modified) {
      return column === DiffColumn.After
        ? row.afterData.diffLineNumber
        : row.beforeData.diffLineNumber
    }

    return null
  }
