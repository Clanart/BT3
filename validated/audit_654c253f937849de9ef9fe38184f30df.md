### Title
Payout transaction's operator-identifying OP_RETURN is not committed by the withdrawal signature, allowing an unprivileged party to frame an honest operator as malicious - (`core/src/verifier.rs`)

### Summary
The user's payout-authorizing signature for the withdrawal input uses `TapSighashType::SinglePlusAnyoneCanPay`, which under BIP-341 only commits to input 0 and output 0. The OP_RETURN output (holding the paying operator's x-only pubkey) at output index 2 is completely uncommitted, so anyone who observes the unconfirmed payout transaction can rebroadcast a variant with an unrelated/random x-only key in the OP_RETURN and get it mined instead. `Verifier::is_kickoff_malicious` trusts this on-chain OP_RETURN value as ground truth for "who funded the payout," so the honest operator that actually paid the user gets flagged malicious and challenged/disproved.

### Finding Description
The claimed binding is: `payout_payer_operator_xonly_pk` (as recorded in the `withdrawals` table for `move_to_vault_txid`) `== kickoff_data.operator_xonly_pk` of the operator that genuinely fronted the payout for that withdrawal.

This binding is derived purely from parsing the OP_RETURN of whichever transaction happens to be mined spending the withdrawal UTXO: [1](#0-0) 

`create_payout_txhandler` builds the payout tx with output[0] = user payout (sighash-committed), output[1] = anchor, output[2] = OP_RETURN(move_txid || operator_xonly_pk), and the only witness is the user's `SinglePlusAnyoneCanPay` taproot key-spend signature over input 0: [2](#0-1) 

The signature verification in `Operator::withdraw` explicitly documents and enforces this sighash type: [3](#0-2) 

Per BIP-341, `SIGHASH_SINGLE` only commits to the output whose index equals the signed input's index (index 0 here); `ANYONECANPAY` only relaxes input commitment. Output 1 (anchor) and output 2 (OP_RETURN operator pubkey) are **not covered** by the signature at all. Consequently, once operator A broadcasts the payout tx (visible in mempool/relay before confirmation), any unprivileged party can construct a different, still-validly-signed transaction that: reuses input 0 and its witness unchanged, reuses output 0 unchanged (user is still paid, so nothing looks wrong to the user), but replaces output 2's OP_RETURN with a syntactically valid but unregistered random x-only public key. This is a different txid competing for the same UTXO; if it gets mined instead of A's original (feasible via a simple fee-bump/relay-race — no hashpower majority, no key compromise, no privileged access required, only broadcasting fee-paying Bitcoin transactions, which is explicitly within the modeled attacker's capability), then:

- `update_finalized_payouts` parses the malicious OP_RETURN and stores the random key as `payout_payer_operator_xonly_pk` for that withdrawal: [4](#0-3) 
- When A subsequently sends its real Kickoff (`kickoff_data.operator_xonly_pk = A`), `is_kickoff_malicious` fetches the stored (random) key and compares it against `kickoff_data.operator_xonly_pk`: [5](#0-4) 
- Since `random_key != A`, the function returns `Ok(true)`, and `handle_kickoff` queues a Challenge transaction against A's kickoff: [6](#0-5) 

No existing guard prevents this: `is_deposit_valid`, `SECP.verify_schnorr` (verifies only the signed, unaffected part of the tx), `only_aggregator_and_self`, and the presigned tx graph all operate correctly but none of them protect the OP_RETURN's integrity, because it was never meant to be signed by the withdrawal signature — it is populated by whichever party's transaction wins the race to be mined.

### Impact Explanation
This directly matches the Critical category "an honest operator's collateral burned": operator A genuinely fronted the peg-out (paid the user out of pocket) yet is flagged malicious, a Challenge is queued and confirmed against A's kickoff/round, and — since the bridge circuit used for Disprove derives `deposit_constant` from the same corrupted on-chain OP_RETURN pubkey rather than A's real committed kickoff data — A cannot construct a valid disprove-resistant path, resulting in A's collateral being burned despite correct behavior. This is repeatable against any operator, for any withdrawal, and requires no compromise of keys, verifiers, or majority hashrate — only observing a public mempool transaction and winning a fee/relay race for its confirmation.

### Likelihood Explanation
Preconditions are simply: a normal deposit/withdrawal exists and an operator broadcasts a normal payout tx (mandatory step of the protocol). The attacker's only capability needed is broadcasting a fee-paying Bitcoin transaction that conflicts with the honest payout tx before it confirms — well within the standard attacker model (no privileged access, no compromised keys). The cost is one witness reuse plus a marginally higher fee to win the mempool/mining race, i.e., typically a few hundred to a few thousand sats, making this cheap and repeatable across every payout the bridge processes.

### Recommendation
Bind the OP_RETURN (operator identity) to the same signature that authorizes the withdrawal spend, e.g., require the user to sign with `SIGHASH_ALL` (or otherwise commit to all outputs, including the OP_RETURN), or have the aggregator/verifiers co-sign the payout transaction (via MuSig2) so the OP_RETURN content cannot be altered post-broadcast without invalidating the signature.

### Proof of Concept
`cargo test` plan (regtest, no mainnet/live Citrea):
1. Reuse `deposit_and_withdraw_e2e.rs` harness: perform a real deposit and register a withdrawal via `run_single_deposit`.
2. Have honest operator A call `withdraw`/`payout_and_start_kickoff` to build and broadcast its real payout tx (input0 signed `SinglePlusAnyoneCanPay`, output0=user payout, output2=OP_RETURN(move_txid||A_pk)); capture it before it's mined.
3. Construct the attacker's variant transaction: copy input0 (witness untouched), copy output0 untouched, replace output2's OP_RETURN with `move_txid || random_xonly_pk` (`generate_random_xonly_pk()` helper already exists in `core/src/test/common/*`), and rebroadcast/mine this variant first.
4. Assert on-chain: the confirmed payout tx spending the withdrawal UTXO is the attacker's variant (`get_txid_where_utxo_is_spent`).
5. Let bitcoin_syncer index the block; assert via `db.get_payout_info_from_move_txid` that `payout_payer_operator_xonly_pk == random_xonly_pk`, i.e. `random_xonly_pk != A_pk` (the broken binding, both sides captured explicitly).
6. Run A's normal kickoff flow (`internal_finalized_payout`) with `kickoff_data.operator_xonly_pk = A_pk`.
7. Assert `Verifier::handle_kickoff` / `is_kickoff_malicious` returns `true`, and that a `Challenge` transaction is queued/confirmed against A's kickoff (mirroring the assertion style already used in `mock_citrea_run_malicious_after_exit`/`malicious_operator*` tests in `core/src/test/deposit_and_withdraw_e2e.rs`), despite A having genuinely funded and correctly kicked off.

```rust
pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
```
