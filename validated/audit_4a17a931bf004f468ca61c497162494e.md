### Title
Fixed-window scalar multiplication drops the low bits when the bit length isn't a multiple of 4 - (File: crypto/ed448/src/point.rs)

### Summary
The external report describes a loop that applies a multiplicative step the wrong number of times because termination handling is off. The analog in Serai is the 4-bit fixed-window scalar multiplication in `Mul<Scalar> for Point` (`crypto/ed448/src/point.rs:233-272`) and the identical windowed `pow` in `crypto/ed448/src/backend.rs:151-186` / `crypto/dalek-ff-group/src/lib.rs:200-236`. The loop accumulates bits into a nibble and only processes the nibble when `(i + 1) % 4 == 0`:

```rust
if ((i + 1) % 4) == 0 {
  if i != 3 { for _ in 0 .. 4 { res = res.double(); } }
  ... res += add_by; // or res *= scale_by
}
```

Any trailing bits whose index does not complete a full 4-bit window are silently discarded — the loop "ends" without ever folding the final partial window into `res`. For Ed448, the scalar field order is ~2^446, so `PrimeFieldBits::to_le_bits()` returns `NUM_BITS + 1 = 447` bits; `447 % 4 = 3`, leaving bits at `i = 444, 445, 446` (the scalar's three least-significant bits, since iteration is `.rev()` from the MSB) never added. The computed result is `P * (s - (s mod 8))` instead of `P * s`. The same applies to `FieldName::pow` and `Scalar::pow` in `backend.rs:151-186`, which square/multiply on the same `(i+1) % 4` schedule.

### Impact Explanation
`Point::mul` is the scalar multiplication used by Ed448 point operations and, through the `Ciphersuite` impl, by `C::generator() * s` style operations across FROST/DLEq/Schnorr paths on that curve. Every scalar multiplication is wrong whenever `s mod 8 != 0` (7/8 of scalars): produced signatures won't verify under the correct relation, verification shares/commitments computed as `G * share` won't match the shares' polynomial evaluation, and any Ed448 key recovery / proof verification that relies on scalar multiplication computes an incorrect value. An unprivileged party feeding attacker-controlled scalars via `read_F`/`read_G` into `verify`/`multiexp` paths reaches this code. This is reachable purely from public inputs (a proof or signature with a scalar whose low 3 bits are nonzero).

### Likelihood Explanation
Deterministic: it triggers on every `Point * Scalar` / `pow` call on Ed448 whose operand has any of the low 3 bits set — i.e., ~87.5% of random inputs. For `dalek-ff-group` (Ristretto/ed25519 scalars, `NUM_BITS = 253`, bits length 254, `254 % 4 = 2`) and `k256` (256 bits), whether trailing bits are dropped depends on the actual `to_le_bits` length per curve: any curve whose bit-representation length is not a multiple of 4 is affected. I was unable to fully confirm the exact `to_le_bits` length returned for each scalar type in this snapshot (e.g., whether `dalek_ff_group::Scalar` reports 254 or 256 bits); if the length is a multiple of 4, the loop is correct for that curve. For Ed448 the 447-bit length makes the bug certain if `NUM_BITS` is 446 as standard.

### Recommendation
Process the final partial window after the loop: after iterating all bits, if `bits != 0` (or if the last nibble wasn't flushed), perform the table lookup/addition for the remaining `bits` value — i.e., treat the loop as `ceil(len/4)` windows rather than `floor(len/4)`. Equivalently, iterate `i` over `0 .. bits.len().div_ceil(4)` windows explicitly. Add a cross-check test comparing `Point::mul` against naive double-and-add for scalars with set bits in every position (the existing test scaffolding in `crypto/ff-group-tests/src/prime_field.rs:215-285` for `pow` is the right model).

### Proof of Concept
```rust
// crypto/ed448 — conceptual PoC
// Let s = Scalar::ONE (bits: only bit 0 set, which sits in the dropped tail window).
let s = Scalar::ONE;
let p = Point::generator();
// With 447 bits enumerated MSB-first, bit 0 of s is processed at i = 446,
// which never satisfies (i + 1) % 4 == 0, so it is never added.
// Result: identity (or p * 0-ish nibble accumulation) instead of p.
assert_eq!(p * s, p); // FAILS: returns identity / wrong point
```
Concretely: for any scalar `s` with `s mod 8 != 0`, `Point::mul(p, s)` returns `p * (s & !7)`, so e.g. a Schnorr-style verification `sG == R + cA` fails for honestly-generated signatures, and a `G * share` verification share will mismatch the polynomial evaluation — mirroring the report's "value computed with the multiplicative step applied the wrong number of times across phases."

Key caveat: I could not run the code or fully confirm each scalar type's `to_le_bits` bit-length from the index, so the affected-curve set beyond Ed448 (446-bit NUM_BITS → 447-bit encoding) should be verified by running the point-mul test with a low-bit-only scalar.
