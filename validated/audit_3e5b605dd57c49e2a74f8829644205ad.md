Based on the code I traced, `Verifier::is_deposit_valid` for a `ReplacementDeposit` only validates that:

1. The deposit outpoint's on-chain `script_pubkey` matches the taproot address built from `[ReplacementDepositScript::new(nofn_xonly_pk, old_move_txid), Multisig::from_security_council(...)]` [1](#0-0) .
2. The output value equals `bridge_amount` and the tx is confirmed above `start_height` [2](#0-1) .

`get_deposit_scripts` simply embeds `replacement_deposit_data.old_move_txid` (attacker-supplied bytes from the gRPC `ReplacementDeposit.old_move_txid` field) into the script commitment, with no lookup against the verifier's DB or chain history to confirm that txid is a real `TransactionType::MoveToVault` transaction previously signed by this deployment's N-of-N, nor that it was ever spent by a genuine `Multisig::from_security_council` transaction [3](#0-2) . Since `nofn_xonly_pk` and the security council's public keys/threshold are public protocol parameters, and the script construction (`ReplacementDepositScript::to_script_buf`, `Multisig::from_security_council`) is fully deterministic and computable off-chain, any unprivileged party can compute the exact taproot address for an arbitrary `old_move_txid` and fund it themselves [4](#0-3) . The parser for gRPC requests performs no additional binding check either — it only converts bytes into a `Txid` type [5](#0-4) . I found no code in `verifier.rs`, `deposit.rs`, or `aggregator.rs` (searched for `MoveToVault`, `move_to_vault`, `old_move_txid` outside `deposit.rs`/script builders) that cross-references `old_move_txid` against a real prior move-to-vault transaction or its security-council spend. The CLI/test helpers (`run_single_replacement_deposit`, `send_replacement_deposit_tx`, `scripts/replacement_test.py`) all assume `old_move_txid` legitimately came from a prior genuine deposit, but nothing in the verifier enforces this at protocol level [6](#0-5) .

This matches the described binding violation: `is_deposit_valid` checks `expected_scriptpubkey == deposit_txout_in_chain.script_pubkey`, but never checks `old_move_txid == txid of a genuine prior MoveToVault tx of this deployment spent by security council`. ### Title
Replacement-deposit script binding does not verify `old_move_txid` was ever a genuine move-to-vault UTXO of this bridge - (File: core/src/deposit.rs)

### Summary
`get_deposit_scripts` for `DepositType::ReplacementDeposit` embeds an attacker-supplied `old_move_txid` into `ReplacementDepositScript` without any check that this txid corresponds to a real, prior `MoveToVault` transaction of this bridge deployment that was spent by the security council. `Verifier::is_deposit_valid` only checks that the on-chain output's script/amount match the script derived from this unverified `old_move_txid`, allowing a self-funded taproot UTXO with an arbitrary chosen `old_move_txid` to pass validation.

### Finding Description
The claimed binding, `old_move_txid == txid of a genuine MoveToVault tx previously signed by this deployment's N-of-N and spent by Multisig::from_security_council`, is never checked anywhere I could find in `deposit.rs`, `verifier.rs`, or the gRPC parser. `get_deposit_scripts` (core/src/deposit.rs:206-217) constructs `ReplacementDepositScript::new(nofn_xonly_pk, replacement_deposit_data.old_move_txid)` directly from client-supplied data, and `is_deposit_valid` (core/src/verifier.rs:659-705) only verifies the derived taproot `script_pubkey` and `bridge_amount` match the on-chain outpoint the attacker names via `deposit_outpoint`. Because `nofn_xonly_pk` and the security council configuration are public, any unprivileged actor can compute this exact script/address for any `old_move_txid` value of their choosing and fund it with their own BTC, then submit it via the aggregator's `new_deposit` gRPC call as a `ReplacementDeposit`.

### Impact Explanation
If verifiers accept and N-of-N sign the resulting move-to-vault transaction, BTC would leave (or rather, be created in) a move-to-vault UTXO with no genuine prior deposit backing it, matching the Critical impact category ("BTC leaving a move-to-vault UTXO without a matching fronted withdrawal"). This would be repeatable per attacker-funded UTXO and would apply to any deposit under this deployment.
