## Title
Unchecked ERC20 boolean return value on Tron `IntentGatewayV2.withdraw()` and dust-sweep lets non-standard tokens silently fail while escrow state is finalized — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` imports `SafeERC20` and declares `using SafeERC20 for IERC20`, and correctly uses `safeTransferFrom` for inbound deposits. However, all three outbound token-payout sites — the escrow `withdraw()` function, the fee payout inside it, and the `SweepDust` branch of `onAccept` — bypass `SafeERC20` and instead perform a raw low-level `.call()` with `IERC20.transfer.selector`, checking only that the call did not revert (`success`) and never decoding/validating the ERC20's own returned boolean. This is exactly the bug class from the referenced report: a non-ERC20-compliant token that returns `false` instead of reverting on a failed transfer will pass the `success` check while the tokens never move, yet the contract still finalizes escrow state as if the payout succeeded.

### Finding Description
In `withdraw()`: [1](#0-0) 

and in the `SweepDust` handler inside `onAccept`: [2](#0-1) 

Both use the pattern:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
`success` here only reflects whether the external call reverted — it does not decode the ABI-encoded `bool` that `IERC20.transfer` returns. For a non-compliant ERC20 (the report's cited example is `BADGER`, which returns `false` rather than reverting on a failed transfer), the call returns cleanly with `success = true` and an encoded `false` payload that is discarded. The contract has `SafeERC20` fully imported and in scope (`using SafeERC20 for IERC20;`) and uses it correctly for `safeTransferFrom` on deposits, but the three payout call sites (escrow release/refund, transaction-fee release, and dust sweep) were written with the raw `.call()` pattern instead of `safeTransfer`. [3](#0-2) 

Immediately after the unguarded transfer, `withdraw()` unconditionally decrements the escrow accounting and marks the order filled: [4](#0-3) 

So if the ERC20 transfer silently fails, `_orders[commitment][token]` is decremented, `_filled[commitment] = beneficiary` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — all as if the beneficiary was paid — while the tokens remain stuck in the gateway contract. This contradicts the pattern already fixed correctly in the mainline EVM contract (`evm/src/apps/intentsv2/IntentsBase.sol`), which uses `safeTransfer` for the equivalent payout path: [5](#0-4) 

showing the Tron variant is a regression of the exact bug class described in the external report.

### Impact Explanation
This directly matches "stealing or loss of funds" and "transaction manipulation" under the impact gate: escrowed input tokens (deposited by the order creator, intended for the solver/beneficiary) and accumulated transaction fees can become permanently locked in the gateway while the on-chain bookkeeping (`_orders`, `_filled`) and events report a completed, successful settlement. Any downstream consumer (solver accounting, off-chain indexers, or a subsequent GET-response cancellation check via `onGetResponse`, which also calls `withdraw`) will treat the order as finalized even though the beneficiary received nothing, causing fund loss/lock without any privileged, relayer, or malicious-peer assumption — the vulnerable code path is triggered by ordinary `onAccept`/`onGetResponse` execution against whatever token address the order specifies.

### Likelihood Explanation
The trigger only requires that one of the assets in an order (input token, fee token, or a token swept via `SweepDust`) be a non-standard ERC20 that returns `false` on failure instead of reverting — a real, deployed token behavior (e.g., legacy `BADGER`), not a hypothetical. Since `IntentGatewayV2` orders allow arbitrary ERC20 token addresses to be specified as inputs/outputs, an order creator (unprivileged) can pick such a token, and the failure condition (e.g., transient balance mismatch from fee-on-transfer/rounding, or the token's own non-standard failure semantics) can occur without any attacker collusion with relayers or provers.

### Recommendation
Replace all three raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout sites in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()`'s escrow loop, `withdraw()`'s fee transfer, and the `SweepDust` branch in `onAccept`) with `IERC20(token).safeTransfer(beneficiary, amount)`, consistent with the already-imported `SafeERC20` library and with the pattern used in `evm/src/apps/intentsv2/IntentsBase.sol`.

### Proof of Concept
1. Deploy or use a non-compliant ERC20 token `T` that returns `false` (without reverting) on a failed `transfer` call (mirroring `BADGER`'s pre-fix behavior).
2. Create an intent order with input token `T`, deposited into escrow via the (correctly `safeTransferFrom`-guarded) deposit path.
3. Trigger fulfillment such that `onAccept` invokes `withdraw(body, false)` for token `T`, under conditions where `T.transfer(beneficiary, amount)` returns `false` (e.g., due to `T`'s internal invariant, insufficient real balance from prior dust/fee accounting drift, or any non-standard failure condition specific to `T`).
4. Observe: `success == true` (low-level call didn't revert) so `TransferFailed` is not raised; `_orders[commitment][token] -= amount` executes; `_filled[commitment] = beneficiary` is set; `EscrowReleased` is emitted — yet `T.balanceOf(beneficiary)` is unchanged and the tokens remain in the `IntentGatewayV2` contract, unrecoverable through the normal withdrawal path since the order is now marked filled.
