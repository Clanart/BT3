### Title
Unchecked arithmetic overflow in fee/funds-sufficiency computation allows signing a transaction that does not cover its payments — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` multiplies `fee_per_vbyte * vbytes` and adds `payment_sat + needed_fee` with plain `u64` operators whose results are trusted for the `NotEnoughFunds` sufficiency check. Like the lcms2 `CubeSize` overflow, the arithmetic result is used (and only "checked" implicitly by comparison) after the overflow has already occurred. In release builds the operations wrap silently, so an attacker who can influence payment amounts or the fee rate can make the sufficiency check pass when it should fail.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs` the constructor computes:

- `let mut needed_fee = fee_per_vbyte * vbytes;` (line 206) — unchecked multiplication.
- `if needed_fee < ((DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000)` (line 211) — the minimum-fee bound is itself a wrapped product of the wrapped `needed_fee`, so a wrapped `needed_fee` can satisfy it.
- `if input_sat < (payment_sat + needed_fee)` (line 215) — the addition can wrap; a wrapped small sum compares `<= input_sat` and the `NotEnoughFunds` rejection is skipped.
- `input_sat.checked_sub(payment_sat + fee_with_change)` (line 228) — `checked_sub` is applied, but the inner `payment_sat + fee_with_change` is again unchecked and may already have wrapped, so `checked_sub` operates on a corrupted operand.

The payment amounts (`payments: &[(ScriptBuf, u64)]`) are only checked against `DUST` (lines 165–169); there is no upper bound on a payment amount or on the number of payments. `fee_per_vbyte` and the resulting `vbytes` product are likewise unbounded. The resulting `SignableTransaction` is fed into `TransactionSignMachine::sign`, which produces FROST signature shares over the Taproot sighashes of this malformed transaction (lines 373–397).

### Impact Explanation
Two concrete failure modes follow, both reachable from public withdrawal/payment inputs that flow into `SignableTransaction::new`:

1. **Fee collapse**: choose `fee_per_vbyte` such that `fee_per_vbyte * vbytes` wraps to a small value still ≥ the (also wrapped) minimum-fee bound. The constructed transaction then pays a drastically lower fee than intended while `needed_fee()` reports the wrapped value. The multisig signs a transaction whose real fee is not what was requested — the signed message is not the intended transaction economics, and the broadcast transaction can be non-relayable/stranded, burning the FROST signing session and the associated UTXO scheduling.

2. **Sufficiency bypass**: with a large `needed_fee` (or large attacker-controlled `payment_sat`), `payment_sat + needed_fee` wraps below `input_sat`, so `NotEnoughFunds` is not raised even though `sum(outputs) + fee > sum(inputs)`. The change calculation at line 228 then computes `change` from a wrapped operand, producing outputs whose arithmetic does not match the intended split — the network signs and the resulting transaction is either invalid (inputs < outputs) or sends the wrong change amount. In both cases funds accounting diverges from what the signers authorized.

### Likelihood Explanation
`payments` and `fee_per_vbyte` are caller-supplied parameters to `SignableTransaction::new` with no bound checks beyond `DUST` and a lower-bound fee check that is itself computed with the same unchecked multiplication. Any upstream path that forwards user-requested withdrawal amounts (script_pubkey + satoshi amount) reaches this code directly. The wrap is silent in release builds (`overflow-checks` off), so the corrupted values propagate into sighash signing without panic. Exploitation requires the product or sum to cross `u64::MAX`, i.e. adversarially large payment amounts or fee rates that downstream validation must rely on `NotEnoughFunds`/`TooLowFee` to reject — precisely the checks the overflow defeats.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new`:

- `let needed_fee = fee_per_vbyte.checked_mul(vbytes).ok_or(TransactionError::Overflow)?;`
- `let min_fee = u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE).checked_mul(vbytes).ok_or(...) ? / 1000;`
- `let total_out = payment_sat.checked_add(needed_fee).ok_or(TransactionError::Overflow)?;` before the `input_sat < total_out` check.
- `let out_with_change = payment_sat.checked_add(fee_with_change).ok_or(...)?;` feeding `checked_sub` at line 228.
- Accumulate `input_sat`/`payment_sat` with `checked_add`/`try_fold` instead of `sum::<u64>()`, and bound each payment amount to `Amount::MAX_MONEY` (21M BTC).

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs analog of CVE-2026-41254:
// the "check" is a comparison against a value that already overflowed.

// vbytes for a realistic 1-in/2-out P2TR tx is ~150.
let vbytes: u64 = 150;
// Attacker-influenced fee rate chosen so the product wraps to a small
// value that still exceeds the wrapped minimum-fee bound.
let fee_per_vbyte: u64 = (u64::MAX / vbytes) + 1; // wraps on multiply

// Release-mode semantics (wrapping):
let needed_fee = fee_per_vbyte.wrapping_mul(vbytes); // == fee_per_vbyte*vbytes - 2^64, small

let input_sat: u64 = 100_000;
let payment_sat: u64 = 90_000; // attacker payment above DUST, unbounded by ::new

// The sufficiency check sees the wrapped sum:
let wrapped_sum = payment_sat.wrapping_add(u64::MAX - 50_000); // wraps below input_sat
assert!(input_sat >= wrapped_sum); // NotEnoughFunds skipped in release mode
// With real arithmetic input_sat < payment_sat + needed_fee must have fired.
// The resulting tx signs outputs/fee not backed by inputs, or pays a ~0 fee.
```

The root cause is identical in shape to the lcms2 `CubeSize` bug: the multiplicative/additive result is consumed by the guard check only *after* the overflow has already corrupted it — the check sees the wrapped value, not the true one.
