### Title
JIT (just-in-time) vote-stake/unvote allows attackers to siphon bribe rewards without time-weighted stake - (File: rewards/BribeRewardPool.sol / wombat/WombatBribeManager.sol)

### Summary
`WombatBribeManager.vote()`/`unvote()` call `IBribeRewardPool(pool.rewarder).stakeFor()` / `withdrawFor()` with no cooldown or minimum holding period, and `BribeRewardPool` (extends `BaseRewardPoolV2`) computes rewards purely via a cumulative `rewardPerTokenStored` checkpoint model with no time-weighting. An attacker holding locked vlMGP can `vote()` into a pool immediately before another user's `castVotes()` triggers `queueNewRewards()`, then `unvote()` in the same or next block, capturing a full proportional share of the freshly queued bribe reward while diluting the entitlement of genuine long-term voters.

### Finding Description
`WombatBribeManager.vote()` calls `IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, uint256(delta))` [1](#0-0)  with no cooldown, gated only by `getUserVotable`, which simply checks the caller's currently locked vlMGP balance (`IVLMGP(vlMGP).getUserTotalLocked`), not a time-weighted contribution [2](#0-1) [3](#0-2) .

`stakeFor`/`withdrawFor` in `BribeRewardPool.sol` are wrapped in the `updateRewards` modifier, which snapshots `balanceOf(_account)` *before* the state-changing body runs and computes `_earned()` using that snapshot against the current `rewardPerToken(_rewardToken)`: [4](#0-3)  and [5](#0-4) . `_earned` is a pure cumulative-index formula with no time dimension: [6](#0-5) .

Rewards are queued into `rewardPerTokenStored` by `_provisionReward`, which distributes `_amountReward` across `totalStaked()` at the moment of the call: [7](#0-6) . This is invoked from `castVotes()` -> `wombatStaking.vote()` -> `IBaseRewardPool(_rewarders[i]).queueNewRewards(...)`: [8](#0-7) , itself triggered by any external caller of `castVotes()` on the bribe manager [9](#0-8) .

Exploit flow:
1. Attacker already holds locked vlMGP (any amount, reusable across attacks since locking is not consumed by voting).
2. Attacker observes (or front-runs) a pending `castVotes()`/`voteAndCast()`/`castVotesAndClaimBribes()` transaction that will trigger `queueNewRewards()` on a target pool's rewarder.
3. Attacker calls `vote(lps, deltas)` with a large positive delta for that pool just before the reward-queuing transaction, calling `stakeFor(attacker, X)` — this only checkpoints `userRewardPerTokenPaid` at the pre-reward value (no free reward yet since `rewardPerToken` hasn't changed).
4. The target's `castVotes()` executes, incrementing `rewardPerTokenStored` for that pool's rewarder based on `totalStaked()` which now includes the attacker's inflated balance `X`, diluting the per-token rate that will accrue to real long-term stakers while granting a large numerator for the attacker's own share.
5. Attacker immediately calls `unvote(lp)` -> `withdrawFor(attacker, X, true)`, which through `updateRewards` computes `_earned` using the just-staked balance `X` against the now-incremented `rewardPerToken`, crediting/paying out a full share of the just-queued reward, then removes `X` from `totalSupply` again.

No cooldown, vesting period, or minimum stake-duration check exists in `vote`/`unvote`/`stakeFor`/`withdrawFor` to prevent this. `nonReentrant` is irrelevant here since this is not a reentrancy attack — it is a legitimate sequential call pattern (JIT staking).

### Impact Explanation
This constitutes theft of unclaimed bribe yield from long-term voters: the attacker extracts reward tokens proportional to a stake held for a single block/transaction, funded by diluting `rewardPerTokenStored` accrual that would otherwise go entirely to voters who maintained their position for the full epoch between `castVotes()` calls. This matches the "theft of unclaimed yield" impact class named in the prompt's scoped impact.

### Likelihood Explanation
Preconditions are minimal for an unprivileged attacker: only requires holding some locked vlMGP (capital is not consumed — it can be reused indefinitely for repeated attacks) and the ability to time a transaction immediately before a known/mempool-visible `castVotes()` call (which is a public, permissionless, incentivized function anyone can call, making its execution highly observable and front-runnable). The attack is fully repeatable every time a bribe/reward distribution event occurs, and does not require flash loans, special permissions, or protocol misconfiguration — it exploits the fundamental lack of time-weighting in the reward accounting design.

### Recommendation
Introduce a minimum stake-duration or checkpoint-based cooldown for vote/unvote reward eligibility (e.g., only allow reward accrual for votes held before the last `castVotes()` checkpoint), or switch the bribe rewarder to a time-weighted / streaming distribution model instead of instantaneous `rewardPerTokenStored` increments, so a single-block stake cannot claim a full period's proportional share of freshly queued rewards.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `WombatBribeManager`, `WombatStaking`, and a `BribeRewardPool` for a test LP pool; register the pool and activate it.
2. User A locks MGP into vlMGP and calls `vote()` to allocate a large vote to pool P well before any reward distribution (long-term voter, held for N blocks).
3. Attacker locks a smaller amount of MGP into vlMGP.
4. Simulate a pending `castVotes()` transaction that will call `queueNewRewards(rewardAmount, token)` on pool P's rewarder (e.g., mock `voter.vote` and `IWombatBribe` to return a fixed reward amount).
5. In the block immediately preceding the `castVotes()` call, attacker calls `vote([P], [+X])` (large delta) — asserts `BribeRewardPool.balanceOf(attacker) == X` and `userRewardPerTokenPaid[token][attacker] == rewardPerToken(token)` (no premature earning).
6. Execute `castVotes()` triggering `queueNewRewards` — assert `rewardPerTokenStored` increased.
7. Immediately (same or next block) attacker calls `unvote(P)` -> `withdrawFor(attacker, X, true)`.
8. Assert `earned(attacker, token)` (paid out) > 0 and specifically that `attacker_reward / X` (per-unit reward for one-block stake) ≈ equal to `userA_reward_share / userA_stake` despite User A having staked for many more blocks — i.e., `_earned()` gives the attacker the same per-token rate as User A despite zero time-weighted contribution, proving `attacker's realized APR >> User A's realized APR` for that single distribution event, confirming dilution/theft of long-term voter yield.

    modifier updateRewards(address _account, address[] memory _rewards) {
        uint256 length = _rewards.length;
        uint256 userShare = balanceOf(_account);
        
        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = _rewards[index];
            // if a reward stopped queuing, no need to recalculate to save gas fee
            if (userRewardPerTokenPaid[rewardToken][_account] == rewardPerToken(rewardToken))
                continue;
            userRewards[rewardToken][_account] = _earned(_account, rewardToken, userShare);
            userRewardPerTokenPaid[rewardToken][_account] = rewardPerToken(rewardToken);
        }
        _;
    }
