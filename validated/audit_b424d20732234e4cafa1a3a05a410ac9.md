## Title
Shared `CallDispatcher` balance is read as an absolute value (not a pre-call delta), letting an attacker sweep residual/foreign token balance into their own escrowed order — `evm/src/apps/IntentGatewayV2.sol` (`placeOrder`)

### Summary
The external report's core defect is: a price/value used for accounting is derived from a contract's *raw* `balanceOf`, which can be inflated by anyone simply transferring tokens directly to that contract, instead of from a value isolated to the specific operation being priced. `IntentGatewayV2.placeOrder` reproduces the identical pattern: when an order has a `predispatch` step, the amount credited to the user's escrow (`order.inputs[i].amount`, which becomes `_orders[commitment][token]`) is computed from the *absolute* `IERC20(token).balanceOf(dispatcher)` at the shared, permissionless `_params.dispatcher` address, with no snapshot of the dispatcher's balance taken *before* `predispatch.call` executes.

### Finding Description
In `placeOrder` (`evm/src/apps/IntentGatewayV2.sol:203-298`), when `order.predispatch` is used:

1. The caller's `predispatch.assets` are transferred to the shared `dispatcher` [1](#0-0) .
2. `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` executes arbitrary, caller-supplied calldata [2](#0-1) .
3. For each `order.inputs[i]`, the code reads `balance = IERC20(token).balanceOf(dispatcher)` — the dispatcher's *total current* balance, not a delta produced by step 2 — checks only `balance >= requiredAmount`, and builds a sweep call that transfers the **entire** `balance` (not `requiredAmount`) to the gateway [3](#0-2) .
4. The measured `received` (gateway's own balance delta) becomes `order.inputs[i].amount` [4](#0-3) .
5. That amount is stored as the order's escrow credit in `_orders[commitment][token]`, which backs the commitment a solver later fills against [5](#0-4) .

There is no snapshot of `dispatcher`'s per-token balance taken immediately *before* `dispatch(order.predispatch.call)` is invoked, so nothing distinguishes tokens produced by *this* order's predispatch call from tokens that were already sitting in `dispatcher` for any other reason (dust left by another order's unwind/swap that produced excess, an interrupted/partial predispatch from a different transaction, or a plain ERC-20 `transfer` sent straight to the dispatcher address, since `dispatcher` has no access control on inbound transfers). Because the sweep call moves the dispatcher's *full* balance, whoever calls `placeOrder` next with that token as an input silently absorbs that pre-existing balance into their own escrow credit — exactly the "influence the accounted value via a direct transfer to the contract" primitive from the report, just applied to escrow crediting instead of to an oracle price.

### Impact Explanation
`_orders[commitment][token]` is the authoritative escrow record consumed by the fill/settlement path; inflating it beyond what the caller actually contributed lets an attacker obtain a larger, fully-backed order commitment for a solver to fill (and be paid out for on the destination chain) than the value they deposited, at the expense of whichever legitimate flow the swept balance belonged to. This is unauthorized/incorrect fund crediting in the intent-settlement custody path, reachable by any unprivileged caller through the public `placeOrder` entrypoint — matching the bounty's "stealing or loss of funds" / "transaction manipulation" categories.

### Likelihood Explanation
No relayer, prover, admin, or governance action is required. The shared `dispatcher` address is a plain contract with no restriction on who can transfer tokens to it, and `placeOrder` is fully public. Any residual balance — organically created by another order's predispatch (e.g., an LP-unwrap producing rounding excess handled as "dust" within its own order, but only if swept in the *same* call; anything left behind persists in `dispatcher` for the next caller) or deliberately primed by an attacker's own prior direct transfer — is swept wholesale on the next `placeOrder` call that references that token as an input. The precondition (some balance resident in `dispatcher` for the target token) is easy for an attacker to create or wait for, requiring no compromised infrastructure.

### Recommendation
Snapshot `IERC20(token).balanceOf(dispatcher)` immediately before invoking `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`, and only sweep/credit the *delta* produced by that specific call (`balanceAfterPredispatch - balanceBeforePredispatch`), capped at `requiredAmount` plus any legitimately-attributed excess, rather than the dispatcher's absolute balance. Alternatively, make the dispatcher's sweep transfer only `requiredAmount` (not the observed `balance`), and separately reconcile/sweep any leftover dust to a protocol-controlled account rather than to whichever order happens to run next.

### Proof of Concept
1. Attacker (or any user) sends `X` tokens directly to `_params.dispatcher` via a plain `IERC20.transfer`, or such a balance exists because a prior order's predispatch call produced excess that wasn't fully swept in its own call.
2. Attacker calls `placeOrder` with `predispatch.assets` containing a cheap/unrelated token (satisfying the non-zero-amount check) and `order.predispatch.call` set to a no-op or trivial call, while `order.inputs[i].token == X` and `order.inputs[i].amount <= dispatcher's current balance of X`.
3. In the sweep loop, `balance = IERC20(X).balanceOf(dispatcher)` includes the pre-existing `X` tokens; the check `balance >= requiredAmount` passes, and the full `balance` (including tokens the attacker never contributed for this order) is transferred to the gateway.
4. `received` is computed as the gateway's balance delta, set as `order.inputs[i].amount`, and credited into `_orders[commitment][X]`, giving the attacker a solver-fillable commitment backed by tokens they did not deposit for this order.
