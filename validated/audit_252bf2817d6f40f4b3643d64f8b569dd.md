### Title
Reentrancy in `withdraw()` releases escrowed order funds before state update, enabling double redemption - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The external bug report is fundamentally about violating check-then-effect ordering when releasing custodied funds: a balance/state check is performed against the wrong or stale value, and the actual state cleanup happens (or is checked) in the wrong place relative to the transfer. The local Hyperbridge analog is in the Tron variant of the intent-settlement contract's escrow-release routine, `withdraw()`, which sends the escrowed tokens to the beneficiary via an external call **before** decrementing the `_orders` escrow accounting, unlike the canonical EVM implementation which updates state first.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is the function that releases escrowed order funds to a beneficiary for both `RedeemEscrow` (fill payout) and `RefundEscrow` (cancellation) flows, invoked from `onAccept` and `onGetResponse`: [1](#0-0) 

The relevant sequence for each token in the withdrawal is:
1. `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` — checks only that *some* escrow exists, not that it covers `amount`.
2. Sends `amount` to `beneficiary` via `beneficiary.call{value: amount}("")` for native assets, or an ERC20 `transfer` call for tokens.
3. Only afterward does it run `_orders[body.commitment][token] -= amount;`.

This is a Checks-Effects-Interactions violation: the escrow ledger (`_orders[commitment][token]`) is decremented *after* the external call that hands control to `beneficiary`. Compare this with the canonical EVM implementation of the same logic in `IntentsBase.sol`, which decrements the escrow mapping first and only then performs the transfer: [2](#0-1) 

Because `beneficiary` in the `WithdrawalRequest` is attacker-influenced (it is the `msg.sender`/filler who filled the order on the destination chain, propagated verbatim into the cross-chain `RedeemEscrow` message body), an attacker can set `beneficiary` to a malicious contract: [3](#0-2) 

When the resulting message is delivered on the source chain and `withdraw()` executes the native-asset branch, the malicious `beneficiary` contract's fallback runs *while `_orders[body.commitment][token]` still reflects the pre-withdrawal (undecremented) escrow balance*. From that fallback, the attacker can re-enter any other public entry point that reads `_orders[commitment][token]` (e.g. the cancellation path, which independently computes `escrowed = _orders[commitment][token]` and dispatches its own withdrawal/refund) before the original call finishes zeroing/reducing the balance, causing the same escrow to be paid out twice.

### Impact Explanation
This directly matches the bounty's core categories: stealing/loss of funds and replay/double-claim/double-settlement of escrowed order funds. An attacker who is nothing more than an ordinary solver/filler (no relayer, prover, or admin privileges needed) can drain more than the legitimately escrowed amount for an order by re-entering the contract mid-transfer, since the accounting update that is supposed to prevent double-spending of the same commitment/token pair has not yet been committed when external control is handed to the attacker.

### Likelihood Explanation
Likelihood is high for this specific contract variant: the reentrant call is only one hop away (native-asset withdrawal directly `.call`s an attacker-controlled beneficiary address, and `beneficiary` is fully attacker-chosen since it originates from the filler's own address). No relayer or prover misbehavior is required — the message being delivered is a legitimate, correctly-authenticated cross-chain message; the vulnerability is purely in the local ordering of state update vs. external call.

### Recommendation
Apply the checks-effects-interactions pattern consistently: decrement `_orders[body.commitment][token]` (and validate `amount <= escrowed`, not just `escrowed != 0`) **before** performing the native-asset `.call` or ERC20 transfer, matching the pattern already used in `IntentsBase.sol::_withdraw`. Additionally, add a reentrancy guard around functions that read/write `_orders[commitment][...]` (`withdraw`, cancel/refund paths) to eliminate any read-during-external-call window.

### Proof of Concept
1. Attacker deploys a malicious contract `Evil` with a `receive()`/fallback that re-enters `IntentGatewayV2` (e.g., calls the order-cancellation function) for the same `commitment`.
2. Attacker uses `Evil` as `msg.sender` to fill a cross-chain order via `_fillCrossChain` on the destination chain, which sets `beneficiary = Evil` in the dispatched `RedeemEscrow` `WithdrawalRequest`: [4](#0-3) 
3. The message is relayed (normal, honest relaying) and delivered to the source-chain `IntentGatewayV2` (Tron) via `onAccept` → `withdraw()`.
4. Inside `withdraw()`, the native-asset branch executes `beneficiary.call{value: amount}("")` while `_orders[commitment][token]` is still non-zero/undecremented: [5](#0-4) 
5. `Evil.receive()` re-enters and triggers a second release/refund path that reads the still-stale `_orders[commitment][token]`, resulting in the same escrow being paid out more than once.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
