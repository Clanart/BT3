### Title
Unchecked `u64` arithmetic overflow in `SignableTransaction::new` produces a signed transaction whose outputs exceed its inputs — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report's bug class — missing checked math (SafeMath) on value computations — maps directly onto `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`. The sums `input_sat`, `payment_sat`, the product `fee_per_vbyte * vbytes`, and the addition `payment_sat + needed_fee` are all performed with plain `u64` operators. An overflowing payment sum wraps the `NotEnoughFunds` check, and the resulting transaction carries output values that exceed the input value — an invalid transaction that the FROST multisig machines in the same file will still sign.

### Finding Description
`SignableTransaction::new` computes:

- `input_sat` via `sum::<u64>()` over prevout values (line 175).
- `payment_sat` via `sum::<u64>()` over the caller-supplied `(ScriptBuf, u64)` payment amounts (line 187).
- `needed_fee = fee_per_vbyte * vbytes` and `fee_with_change = fee_per_vbyte * vbytes_with_change` (lines 206, 227) — unchecked multiplication.
- The solvency check `if input_sat < (payment_sat + needed_fee)` (line 215) — unchecked addition.
- The change computation `input_sat.checked_sub(payment_sat + fee_with_change)` (line 228), where the inner `payment_sat + fee_with_change` is itself unchecked and can wrap *before* `checked_sub` runs.

Only the outer subtraction is checked; the additions and multiplication that feed it are not. In release builds (`overflow-checks` off, as is standard) these wrap silently.

Two concrete wrap paths:

1. `payment_sat` overflows. Each payment amount is only constrained by `*amount >= DUST` (line 166); there is no per-payment or aggregate upper bound. Two or more payments whose amounts sum past `u64::MAX` wrap `payment_sat` to a small value. Then `payment_sat + needed_fee` is small, so `input_sat < (payment_sat + needed_fee)` is false and `NotEnoughFunds` is bypassed. The transaction is built with `TxOut`s carrying the raw huge `Amount::from_sat(payment.1)` values (lines 188–191), plus potentially a change output computed as `input_sat - wrapped_sum` (line 230), which is nearly the entire input. Total outputs now exceed `input_sat` — consensus-invalid — yet the function returns `Ok(SignableTransaction)`.

2. `fee_per_vbyte * vbytes` overflows. `vbytes` grows with attacker-influenced payment count (`calculate_weight_vbytes`, lines 62–127); a large `fee_per_vbyte` wraps the product to a small value, defeating the fee logic and the `TooLowFee` guard (line 211).

The downstream `multisig()` / `TransactionMachine` / `AlgorithmMachine` path (lines 273–318) signs every input of this malformed transaction via BIP-340 Schnorr without ever re-validating that `sum(outputs) <= sum(inputs)`. `fee()` (lines 138–141) also performs an unchecked `sum(inputs) - sum(outputs)` subtraction which underflows on the overflowed transaction.

### Impact Explanation
The threshold wallet signs a transaction that is consensus-invalid (outputs > inputs) or that pays a wrapped, unintended fee. Every signer in the quorum produces a valid signature share for a transaction that cannot be included in a block, burning the input selection and stalling the payment plan — signatures are produced for an unintended message (the malformed sighash), and the funds in the selected `prevouts` cannot be recovered through that transaction. Where the multiplication wraps instead, a transaction paying far more or far less fee than intended is signed and broadcast, with excess input value lost to miners if outputs still balance.

### Likelihood Explanation
`SignableTransaction::new` is the library entry point used by `processor/src/networks/bitcoin.rs::make_signable_transaction` with payment amounts that ultimately originate from withdrawal requests — untrusted, attacker-influenced `u64` amounts. While individually huge balances are economically unlikely, the code places no bound on payment count or aggregate sum, and the wrapped-addition bypass at line 215 requires only that `payment_sat + needed_fee` wrap below `input_sat`. The bug is deterministic once triggered and requires no cryptographic break — it is purely the missing checked arithmetic the source report describes. Rated Medium: it yields signing of an unintended/invalid transaction and potential fee loss, but does not directly hand funds to the attacker.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new` (the Rust analog of SafeMath):

```rust
let payment_sat = payments.iter().try_fold(0u64, |acc, p| acc.checked_add(p.1))
  .ok_or(TransactionError::NotEnoughFunds { inputs: input_sat, payments: u64::MAX, fee: 0 })?;
let needed_fee = fee_per_vbyte.checked_mul(vbytes).ok_or(TransactionError::TooLowFee)?;
let required = payment_sat.checked_add(needed_fee).ok_or(TransactionError::NotEnoughFunds {
  inputs: input_sat, payments: payment_sat, fee: needed_fee })?;
if input_sat < required { Err(TransactionError::NotEnoughFunds { .. })? }
```

Apply the same to `fee_with_change` (line 227), the inner sum at line 228, `input_sat` (line 175), and `fee()` (lines 138–141, use `checked_sub` or `i128`). Additionally bound `payments.len()` before `calculate_weight_vbytes` so `vbytes` cannot grow unboundedly.

### Proof of Concept
Reachable with public inputs to `SignableTransaction::new` — the payment list and its `u64` amounts:

```rust
// networks/bitcoin/src/wallet/send.rs semantics
// inputs: a single ReceivedOutput worth, say, 1_000_000 sats (attacker-deposited
//         or protocol-held; only needs to pass the wrapped solvency check)
// payments: two attacker-influenced payments, each amount = u64::MAX - 1000,
//           each individually >= DUST (line 166 passes)
// change: Some(script), data: None, fee_per_vbyte: small e.g. 10

let payment_sat = (u64::MAX - 1000u64).wrapping_add(u64::MAX - 1000u64); // wraps to small value
// line 215: input_sat (1_000_000) < payment_sat + needed_fee  -> false, NotEnoughFunds bypassed
// line 228: input_sat.checked_sub(payment_sat + fee_with_change) -> Some(~1_000_000 - small)
//           -> change output worth ~all inputs is appended (line 230)
// tx_outs now contain two TxOuts of ~u64::MAX each + change: outputs >> inputs
// -> Ok(SignableTransaction) returned; TransactionMachine signs every input's
//    BIP-340 sighash (lines 302-318), producing a fully signed transaction that
//    is consensus-invalid and can never be broadcast.
```

The overflow is in the caller-facing arithmetic of `send.rs` itself; no SafeMath-style guard exists anywhere in the function.
