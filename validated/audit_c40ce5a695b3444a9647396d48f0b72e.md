### Title
Unauthenticated participant can panic the DKG via duplicate encryption-key registration - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
The CVE class is a denial of service triggered by crafted/untrusted input (a memory leak in an XPM parser). The closest reachable analog in Serai's in-scope code is a hard panic in PedPoP's encryption-key bookkeeping: `Decryption::register` uses `assert!` to reject a second `EncryptionKeyMessage` for the same participant index, so an unprivileged DKG participant who submits a duplicate registration message crashes the recipient's process instead of receiving a recoverable error.

### Finding Description
`Decryption::register` stores each participant's encryption public key in `self.enc_keys` and guards re-registration with an assertion:

```rust
// crypto/dkg/pedpop/src/encryption.rs
assert!(
  !self.enc_keys.contains_key(&participant),
  "Re-registering encryption key for a participant"
);
self.enc_keys.insert(participant, msg.enc_key);
``` [1](#0-0) 

The `participant` argument and the `EncryptionKeyMessage` are entirely attacker-controlled bytes: `EncryptionKeyMessage::read` accepts arbitrary serialized input (a message `M` plus an arbitrary `C::G` point) with no uniqueness checks. [2](#0-1)  `Encryption::register` forwards directly to this asserting call. [3](#0-2)  There is no error type for this failure mode — the API returns `M`, not `Result<M, _>` — so the only outcome of a duplicate is a panic that unwinds (or aborts, in `panic = "abort"` builds) the executing party.

By comparison, other `read`/`write` paths in the same crate family return `io::Result` and gracefully reject malformed input (`ThresholdKeys::read`, `EncryptedMessage::read`), which shows this panic is an anomaly rather than an accepted design pattern. [4](#0-3) 

### Impact Explanation
A participant in a PedPoP DKG round can broadcast (or send) a second `EncryptionKeyMessage` under their own index — or under an index they can cause to be registered twice — forcing `Decryption::register` to panic on every honest party that processes it. In a validator/node context this kills the DKG round at minimum and, depending on the caller's panic handling, aborts the whole process. This is a remotely triggerable availability failure, matching the CVE's denial-of-service impact class.

### Likelihood Explanation
The trigger requires only that an unprivileged DKG participant emit a second registration message — a few dozen bytes of well-formed input — which is within the allowed threat model (public inputs fed to `read`/`register` APIs). No collusion, threshold compromise, or leaked keys are needed. One caveat I could not fully verify within the indexed code: whether upstream PedPoP orchestration code already deduplicates registration messages before reaching `register`; if it does not, the panic is directly reachable, and even if it does, the library itself provides no defense, making misuse fragile.

### Recommendation
Replace the `assert!` with a checked error. Change `Decryption::register` to return `Result<M, DkgError>` (e.g., reuse `DkgError::DuplicatedParticipant`), and propagate the `Result` through `Encryption::register`. If deduplication is the caller's responsibility, at minimum use `.insert()`'s return value or an explicit `contains_key` check returning an error, and document the requirement — a panic on attacker-controlled input is never appropriate in protocol code.

### Proof of Concept
```rust
// Conceptual reproduction for a PedPoP participant processing registrations:
let mut decryption = Decryption::<Ed25519>::new(context);
let msg1 = EncryptionKeyMessage::<Ed25519, M>::read(&mut bytes1, params)?;
decryption.register(Participant::new(1).unwrap(), msg1);
// Attacker re-sends under the same index:
let msg2 = EncryptionKeyMessage::<Ed25519, M>::read(&mut bytes2, params)?;
decryption.register(Participant::new(1).unwrap(), msg2); // panic: "Re-registering encryption key"
```
The second `register` call hits the `assert!` at `crypto/dkg/pedpop/src/encryption.rs` and panics, with no way for the caller to catch the condition as an `Err`.
