### Title
Nested/recursive precompile calls cause the shared, monotonically-growing event log to be double-consumed by `BalanceHandler`, duplicating bank-triggered EVM balance updates - (File: `precompiles/common/balance_handler.go`)

### Summary
This is the same bug-class as the referral bonus report: a single accumulator that is meant to track a *bounded, exclusive* window of state is instead shared across overlapping accounting scopes, so one scope's data bleeds into another's and gets counted twice (or capped incorrectly). Here the accumulator is `sdk.Context.EventManager()`'s event slice, and the "window" is `BalanceHandler.prevEventsLen`, recorded per precompile invocation via `BeforeBalanceChange`/`AfterBalanceChange` in `precompiles/common/balance_handler.go`.

### Finding Description
Every stateful precompile call goes through `Precompile.runNativeAction` [1](#0-0) , which:
1. Creates a `BalanceHandler`, calls `BeforeBalanceChange(ctx)` which records `prevEventsLen = len(ctx.EventManager().Events())`.
2. Runs the native `action(ctx)`.
3. Calls `AfterBalanceChange(ctx, stateDB)`, which iterates `events[bh.prevEventsLen:]` and applies every `CoinSpent`/`CoinReceived`/fractional-balance event in that suffix to the EVM `stateDB` via `AddBalance`/`SubBalance` [2](#0-1) .

The `sdk.Context` (and its `*EventManager`) is shared/threaded through the whole call stack, so if the native `action` of an *outer* precompile call synchronously triggers an *inner* precompile call (reentrancy), the inner call's own `BeforeBalanceChange`/`AfterBalanceChange` pair consumes and applies a sub-range of events to the stateDB, and then returns control to the outer action. When the outer action finishes and its own `AfterBalanceChange` runs, it re-scans `events[outerPrevLen:]`, which still contains the inner call's already-applied events (the event log only grows, it is never truncated or marked "consumed"). This causes the inner precompile's `CoinSpent`/`CoinReceived` deltas to be re-applied to the stateDB a second time.

This exact nested-call scenario is reachable by an unprivileged user: an ERC20 token that overrides `_beforeTokenTransfer` to call another native precompile (e.g., `distribution.claimRewards`) mid-transfer is a normal, permissionless contract pattern, demonstrated in-repo by `contracts/solidity/ERC20RecursiveNonRevertingPrecompileCall.sol` [3](#0-2) . Triggering an ICS20 transfer of such a token (which internally invokes the ERC20 hook, which invokes the distribution precompile) exercises the double-processing path; the repository's own test suite documents this as a known bug: "Tests the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated" [4](#0-3) , and a dedicated regression test states outright that "recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB" [5](#0-4) .

### Impact Explanation
When the duplicated events are `CoinReceived` events for an address, that address's EVM-visible `stateDB` balance is credited twice for a single real bank-module credit, i.e. unauthorized duplication of spendable value that is not backed by an equivalent native/bank balance — this desyncs EVM balances from the native ledger and can be leveraged to spend/withdraw more than was actually received. Conversely, duplicate `CoinSpent` application can incorrectly double-debit a victim's stateDB balance. Either direction is an accounting-invariant break between native bank balances and EVM `stateDB` balances mediated entirely through precompiles, matching the "unauthorized duplication ... of spendable user value across native balances, EVM balances ... or precompile-mediated assets" critical impact class.

### Likelihood Explanation
Likelihood is high: no privileged role is required. Any user can deploy (or already-deployed contracts can already implement) an ERC20/ERC677-style token with transfer hooks that call another precompile, and then route a transfer of that token through any precompile flow that wraps native actions with `BalanceHandler` (e.g., ICS20 transfer of an ERC20-backed voucher, or a contract that calls two precompiles within one call frame). This is a generic reentrancy-across-precompiles condition, not tied to one specific token or contract.

### Recommendation
Do not rely on a single mutable `prevEventsLen` cursor read from a shared, ever-growing event log across nested precompile invocations. Options:
- Track a monotonically increasing "consumed" watermark on the shared `ctx` (not per-`BalanceHandler` instance) so that once an inner call has applied events `[a:b]`, an outer call's later `AfterBalanceChange` only scans events `[max(outerPrevLen, lastConsumed):end]`.
- Alternatively, tag/mark each event as "consumed" once applied to `stateDB`, and have `AfterBalanceChange` skip already-consumed events regardless of index range.
- Add reentrancy protection so a precompile's native action cannot call back into another precompile's balance-handled path within the same EVM call frame without properly nesting/restoring the outer handler's bookkeeping.

### Proof of Concept
1. Deploy an ERC20 token contract identical in behavior to `contracts/solidity/ERC20RecursiveNonRevertingPrecompileCall.sol`, whose `_beforeTokenTransfer` hook calls the distribution precompile's `claimRewards` (or any other precompile) synchronously during transfer.
2. Register this token via the ERC20/token-pair path and delegate/accrue distribution rewards to the contract address as done in `setupContractForTesting` [6](#0-5) .
3. Trigger an ICS20 `transfer` of the ERC20-backed denom through the `ics20.Precompile`, as in `TestHandleMsgTransfer`'s "test recursive precompile call without reverts" case [7](#0-6) .
4. Compare the EVM `stateDB`/native bank balance of the contract address before and after: the existing test asserts a specific non-zero leftover native balance (`sdkmath.NewInt(50)`) and a specific inflated event count, which is direct evidence that reward-claim events are being counted/applied outside of the expected single-application semantics, confirming the duplication path is live and observable without any privileged setup.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

func (suite *ICS20RecursivePrecompileCallsTestSuite) setupContractForTesting(
	contractAddr common.Address,
	contractData evmtypes.CompiledContract,
	senderAcc evmibctesting.SenderAccount,
) {
	evmAppA := suite.chainA.App.(*evmd.EVMD)
	ctxA := suite.chainA.GetContext()
	senderAddr := senderAcc.SenderAccount.GetAddress()
	senderEVMAddr := common.BytesToAddress(senderAddr.Bytes())
	deployerAddr := common.BytesToAddress(suite.chainA.SenderPrivKey.PubKey().Address().Bytes())

	// Register ERC20 contract
	_, err := evmAppA.Erc20Keeper.RegisterERC20(ctxA, &erc20types.MsgRegisterERC20{
		Signer:         evmAppA.AccountKeeper.GetModuleAddress("gov").String(),
		Erc20Addresses: []string{contractAddr.Hex()},
	})
	suite.Require().NoError(err, "registering ERC20 token should succeed")
	suite.chainA.NextBlock()

	// Send native tokens to contract for delegation
	bondDenom, err := evmAppA.StakingKeeper.BondDenom(ctxA)
	suite.Require().NoError(err)

	contractAddrBech32, err := sdk.AccAddressFromHexUnsafe(contractAddr.Hex()[2:])
	suite.Require().NoError(err)

	deployerAddrBech32 := sdk.AccAddress(deployerAddr.Bytes())
	deployerBalance := evmAppA.BankKeeper.GetBalance(ctxA, deployerAddrBech32, bondDenom)

	// Send delegation amount to contract
	sendAmount := sdkmath.NewInt(DelegationAmount)
	if deployerBalance.Amount.LT(sendAmount) {
		sendAmount = deployerBalance.Amount.Quo(sdkmath.NewInt(2))
	}

	err = evmAppA.BankKeeper.SendCoins(
		ctxA,
		deployerAddrBech32,
		contractAddrBech32,
		sdk.NewCoins(sdk.NewCoin(bondDenom, sendAmount)),
	)
	suite.Require().NoError(err, "sending native tokens to contract should succeed")

	// Mint ERC20 tokens
	_, err = evmAppA.GetEVMKeeper().CallEVM(
		suite.chainA.GetContext(),
		contractData.ABI,
		deployerAddr,
		contractAddr,
		true,
		nil,
		"mint",
		senderEVMAddr,
		big.NewInt(InitialTokenAmount),
	)
	suite.Require().NoError(err, "mint call failed")
	suite.chainA.NextBlock()

	// Delegate tokens
	vals, err := evmAppA.StakingKeeper.GetAllValidators(suite.chainA.GetContext())
	suite.Require().NoError(err)

	_, err = evmAppA.GetEVMKeeper().CallEVM(
		ctxA,
		contractData.ABI,
		deployerAddr,
		contractAddr,
		true,
		nil,
		"delegate",
		vals[0].OperatorAddress,
		big.NewInt(DelegationAmount),
	)
	suite.Require().NoError(err)

	suite.Require().NoError(err)

	amt, err := evmAppA.StakingKeeper.GetDelegation(suite.chainA.GetContext(), contractAddrBech32, valAddr)
	suite.Require().NoError(err)
	suite.Require().Equal(sendAmount.BigInt(), amt.Shares.BigInt())

	// Setup rewards for testing

	suite.chainA.NextBlock()

	suite.Require().Equal(big.NewInt(InitialTokenAmount), bal, "unexpected ERC20 balance")
