### Title
Cached FROST nonce seed is never deleted after signing, enabling nonce reuse and secret share recovery on re-execution — ([File: coordinator/src/tributary/signing_protocol.rs])

### Summary
The coordinator persists the FROST preprocess nonce seed (`CachedPreprocesses`) in the database keyed only by a static context, reads it back on every signing invocation, and never deletes it. Every subsequent `preprocess`/`share`/`complete` call for the same context deterministically regenerates the identical FROST nonces `(d, e)`. modular-frost explicitly documents that a cached preprocess "MUST only be used once" and "must be deleted so it's never reused" — a contract this code violates, directly analogous to the IndexedDB-file-not-deleted bug class of CVE-2024-4767.

### Finding Description
`SigningProtocol::preprocess_internal` stores a freshly generated nonce seed on first use and otherwise reuses the entry already in the DB: [1](#0-0) 

There is no `CachedPreprocesses::del` anywhere in the codebase — the table is only ever `get`/`set` (`create_db!` at `coordinator/src/tributary/signing_protocol.rs:86-90`). The DB row therefore survives indefinitely after the signature share has been produced and published.

The seed is fed into `ChaCha20Rng::from_seed` and expanded into the FROST nonces inside `seeded_preprocess`: [2](#0-1) 

FROST requires the machine to consume the preprocess exactly once; `SignMachine::from_cache` states "the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share": [3](#0-2) 

Here, from_cache is invoked on *every* call to `preprocess_internal` — including `DkgConfirmer::share` and `DkgConfirmer::complete`, the latter of which calls `share_internal` (and hence `preprocess_internal` + `sign`) a second time within the same attempt/context: [4](#0-3) 

The safety comment at the top of the file justifies fixed nonces by claiming "Upon any complete rebuild, we'd re-decide nonces, achieving safety" — but this is false: the seed is cached in the DB, so a rebuilt process regenerates the *same* nonces rather than re-deciding them. Any re-execution path (restart mid-attempt, `share` followed by `complete`, or re-processing finalized data under the same `(b"DkgConfirmer", attempt)` context with a different accumulated preprocess set or different `key_pair`) produces a second signature share under identical `(d, e)`.

### Impact Explanation
With FROST/MuSig, reusing a nonce pair across two signing sessions with different participant sets (different binding factors `rho`) or different messages yields linearly independent equations in `d`, `e`, and the secret share. Anyone observing the two published shares recovers the validator's MuSig private key, after which they can forge DKG-confirmation signatures and arbitrarily set validator key pairs on Substrate — full compromise of the validator's root-of-trust key. This is exactly the "secret material persisted past its session of use" class: the nonce seed, which is secret equivalent to the key share itself, is written to a non-secret-store DB and left there permanently.

### Likelihood Explanation
Triggering requires a second `sign` under the same context. `complete` demonstrably performs a second `share_internal`/`sign` invocation for the same attempt (the second share is computed and discarded, so it is not broadcast — limiting immediate exposure), and a crash/restart between the preprocess phase and share publication within an attempt reuses the same seed if the accumulated preprocess set differs post-restart. The code's own threat analysis acknowledges the residual risk ("a bound preventing partial rebuilds which is accepted") but the foundational claim that rebuilds re-decide nonces is incorrect given DB persistence. Reachability for an unprivileged party is indirect (they cannot invoke these functions), so this is rated Medium rather than High.

### Recommendation
- Delete the `CachedPreprocesses` entry (`CachedPreprocesses::del`) in the same DB transaction that produces the signature share, or consume-and-delete on read.
- Track and gate on share-publication state so a given context can never produce a second share, and fix the safety comment's incorrect claim that rebuilds re-decide nonces — they reuse the persisted seed.
- Implement the already-noted TODO to verify cached commitments match on-chain published commitments before signing.

### Proof of Concept
1. `DkgConfirmer::preprocess`/`share` for `(b"DkgConfirmer", attempt = k)` writes and reads `CachedPreprocesses[context]`; `machine.sign` emits share `s1` under nonces `(d, e)` expanded from `ChaCha20Rng::from_seed(seed)`.
2. `DkgConfirmer::complete` for the same attempt calls `share_internal` again; `preprocess_internal` finds the same DB entry (never deleted), `from_cache` re-derives identical `(d, e)`, and `sign` emits share `s2`.
3. If the preprocess set or `key_pair` (message) differs between the two calls — e.g., after a mid-attempt restart where `DataDb` accumulated additional preprocesses — `s1` and `s2` satisfy `s_i = λ_i·share + d + ρ_i·e` with known `λ_i`, `ρ_i`, challenges; solving the 2-equation system recovers `d`, `e`, and the validator's secret key share.
