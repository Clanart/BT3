## Analysis

The Tron variant of `IntentGatewayV2` mixes two ERC-20 transfer patterns inconsistently: inbound escrow deposits use the safe pattern (`IERC20(token).safeTransferFrom(...)`) [1](#0-0) , but outbound escrow release in `withdraw()` and dust sweeping in `onAccept`'s `SweepDust` branch use raw low-level `.call()` and only check that the call didn't revert — never decoding the actual boolean return value.

### Title
Unchecked boolean return value on ERC-20 payout in `withdraw()` permanently finalizes and burns escrowed funds for non-reverting tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()`, the internal function that releases or refunds escrowed order funds on `RedeemEscrow`/`RefundEscrow`/GET-response paths, pays out ERC-20 tokens via `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` and only checks the outer `success` boolean of the low-level call, not the ABI-decoded return value [2](#0-1) . The same pattern appears in the `SweepDust` handler [3](#0-2)  and in the transaction-fee payout at the end of `withdraw()` [4](#0-3) .

### Finding Description
For a standard-compliant token that reverts on failure, `success` correctly reflects transfer success. But for tokens that return `false` instead of reverting on failure (the exact class cited in the seed report, e.g. `ZRX`-style tokens, and common among arbitrary TRC-20 tokens on Tron, which is what this file specifically targets per its header comment "Implements the IntentGatewayV2 contract for Tron" [5](#0-4) ), the low-level `.call` itself succeeds (`success == true`) even though the encoded `bool` return data is `false` and no tokens moved.

Because `withdraw()` never decodes and checks that return value, execution proceeds past the `if (!success) revert TransferFailed();` guard as if the transfer succeeded. It then unconditionally decrements the escrow accounting (`_orders[body.commitment][token] -= amount;`) and sets `_filled[body.commitment] = beneficiary;` at the top of the function, marking the order permanently settled [2](#0-1) . The contract still holds the tokens, but:
- The beneficiary never receives them.
- `_orders[commitment][token]` is now zero, so no other code path can redeem them.
- `_filled[commitment]` is already set, so any retry of `RedeemEscrow`/`RefundEscrow` or GET-response verification for that commitment is blocked (`UnknownOrder`/`Filled` semantics elsewhere in the contract rely on these being mutually exclusive, single-use states).

This is a direct case of "false state acceptance" of a fund-movement outcome that never happened — the contract's internal accounting believes settlement occurred, but the beneficiary's balance never changed, and the tokens become permanently stuck (unauthorized loss/lock of escrowed value), matching the bridge-custody/escrow invariant from the pivots ("Bridged assets, order escrow, refunds... must move exactly once and only to the rightful beneficiary and amount").

Note this is a purely local implementation gap: the sibling contract used for other EVM chains already fixes this correctly via `IntentsBase.sol`'s `IERC20(token).safeTransfer(beneficiary, amount);` [6](#0-5) , and the Tron file itself already imports and uses `SafeERC20`/`safeTransferFrom` for inbound escrow [7](#0-6)  — but the outbound `withdraw()`/`SweepDust` paths were left on the unsafe raw-call pattern.

### Impact Explanation
Escrowed input tokens (and accrued protocol/tx fees) can become permanently locked/lost whenever the escrowed token is a non-reverting, false-returning ERC-20/TRC-20. The order is marked filled/refunded on-chain (`_filled` set, `_orders` zeroed) with no possibility of retry, while the actual token balance remains stuck in the contract with no accounting path pointing to it. This is a direct, unauthorized loss of user/solver funds in the bridge's escrow custody logic, not merely a griefing or DoS issue.

### Likelihood Explanation
Medium: it requires the order's escrowed token to have non-standard transfer semantics (return `false` on failure rather than reverting). Such tokens are common enough (the seed report itself flags `USDT`/`ZRX`/`BNB`/`OMG`), and this contract explicitly targets Tron (TRC-20), an ecosystem with widespread non-standard token implementations, making the "non-reverting return-false" precondition realistic without needing any malicious relayer, prover, or governance actor.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout patterns in `withdraw()` and the `SweepDust` branch of `onAccept` with `SafeERC20.safeTransfer`, consistent with the rest of the contract's inbound transfer handling and with the fixed pattern already used in `IntentsBase.sol`.

### Proof of Concept
1. Deploy (or use) an escrow input token whose `transfer` returns `false` on failure instead of reverting (e.g., insufficient internal balance, paused, or blacklisted recipient — many real TRC-20 tokens exhibit this).
2. Place an order on `IntentGatewayV2` (Tron) escrowing that token as an input, going through the normal `safeTransferFrom`-based deposit path.
3. Trigger settlement so `onAccept` dispatches `withdraw(body, isRefund)` with that token in `body.tokens`, under conditions that make the token's internal `transfer` return `false` (e.g., beneficiary is blacklisted, or the token pauses payouts) — the low-level `.call` still returns `success = true` because the call did not revert.
4. Observe: `_filled[commitment]` is set and `_orders[commitment][token]` is decremented to zero, `EscrowReleased`/`EscrowRefunded` is emitted, yet `token.balanceOf(beneficiary)` is unchanged and the tokens remain stuck in the `IntentGatewayV2` contract with no remaining code path to recover them.
