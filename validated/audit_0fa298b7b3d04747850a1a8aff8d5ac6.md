### Title
Wrapped-SEI (`WSEI`) `withdraw()` uses `.transfer()`, causing failed withdrawals for smart-contract holders - (File: contracts/src/WSEI.sol)

### Summary
`WSEI.sol`'s `withdraw` function sends the underlying native SEI back to `msg.sender` using `payable(msg.sender).transfer(wad)`, which is limited to a 2300-gas stipend [2](#0-1) . This is the same official Sei-provided wrapped-native-asset contract, compiled and embedded as deployable bytecode in `x/evm/artifacts/wsei/artifacts.go`, and exposed through the `seid tx evm deploy-wsei` CLI command [3](#0-2) [4](#0-3) .

### Finding Description
Any smart contract (multisig wallet, DEX router, vault, proxy, etc.) that holds `WSEI` and calls `withdraw()` will have the native SEI sent back via `.transfer()`. If that contract's `receive`/`fallback` function consumes more than 2300 gas (e.g. it does any storage write, emits events, or forwards to another call), the transfer reverts and the entire `withdraw` transaction fails [2](#0-1) . The same pattern also appears in the `evmrpc/solidity/ERC20.sol` and `evmrpc/tests/solidity/ERC20.sol` test/RPC fixtures with identical `WSEI`-named token metadata, and in `WETH9.sol` under the load-generator mocks, all sharing the same `.transfer()`-based withdrawal pattern [5](#0-4) [6](#0-5) .

### Impact Explanation
Because Solidity 0.8's built-in checked arithmetic and `require(success)` semantics mean the state change (`balanceOf[msg.sender] -= wad`) is reverted along with the failed `.transfer()`, this does not cause permanent loss of funds for the caller — the withdrawal simply always fails, permanently locking the wrapped balance for that specific contract account as long as it interacts through a fallback function costing more than 2300 gas. This is a denial-of-service / fund-freezing issue for any smart-contract holder of `WSEI`, not a direct fund-theft vector, since `.transfer()`'s revert-on-failure semantics prevent silent loss.

### Likelihood Explanation
`WSEI` is an optional, explicitly-deployed contract (via `deploy-wsei` CLI command) rather than a chain-critical system contract instantiated at genesis [1](#0-0) ; genesis-time contract creation only sets up the CW20/CW721/CW1155 ERC pointer codes, not `WSEI` itself [7](#0-6) . Likelihood of impact therefore depends on whether/how widely `WSEI` gets adopted and whether contract wallets interact with it directly (rather than via an EOA), which is plausible in a DeFi ecosystem (routers, vaults) that treat wrapped-native tokens like WETH.

### Recommendation
Replace `payable(msg.sender).transfer(wad)` in `contracts/src/WSEI.sol` (and the analogous `evmrpc/solidity/ERC20.sol` fixture) with a low-level `call` pattern following checks-effects-interactions and a reentrancy guard, e.g.:
```solidity
balanceOf[msg.sender] -= wad;
(bool success, ) = msg.sender.call{value: wad}("");
require(success, "WSEI: ETH transfer failed");
emit Withdrawal(msg.sender, wad);
```
Re-generate `x/evm/artifacts/wsei/WSEI.bin`/`WSEI.abi` from the patched source so any future `deploy-wsei` deployments use the fixed bytecode.

### Proof of Concept
1. Deploy `WSEI` via `seid tx evm deploy-wsei` (or via the embedded bytecode in `x/evm/artifacts/wsei`).
2. Deploy a minimal smart contract wallet whose `receive()` function performs a storage write (e.g., increments a counter) costing more than 2300 gas.
3. Have the smart contract call `WSEI.deposit{value: X}()` then `WSEI.withdraw(X)`.
4. Observe the `withdraw` call reverts because the internal `.transfer()` runs out of gas in the recipient's `receive()`, permanently preventing that contract from redeeming its wrapped SEI through this path.
