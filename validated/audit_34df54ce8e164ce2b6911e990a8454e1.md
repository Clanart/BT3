### Title
Order settlement is authenticated against a live, mutable `_instances` mapping instead of the gateway instance active at order-placement time, enabling refund+fill double-settlement across a `NewDeployment` migration - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
IntentGatewayV2 keeps a single mutable mapping, `_instances[keccak256(chain)]`, that records the *currently registered* gateway contract address for each remote chain. This mapping is used both to authenticate inbound settlement messages (`_authenticate`) and to compute the destination-chain storage key used for cross-chain cancellation proofs (`_cancelFromSource`). No order stores which gateway instance was live when it was placed or filled. When Hyperbridge governance migrates a chain's gateway (`NewDeployment` → `_addDeployment`) — an ordinary, expected maintenance operation, not an attack — orders that are in-flight across the migration boundary become vulnerable to double-settlement: the source-chain cancellation path silently checks the *new* (empty) contract's storage instead of the *old* contract that actually processed the fill, allowing a user to collect both the solver's fill and their own refund.

### Finding Description
`_instances` is a chain-keyed mapping updated unconditionally by governance: [1](#0-0) 

It is read live, with no order-scoped snapshot, by:
- `_instance()`, used to authenticate incoming `RedeemEscrow`/`RefundEscrow` messages: [2](#0-1) 
- `_cancelFromSource()`, which builds the destination storage-proof key from *whatever address is currently registered* for `order.destination`: [3](#0-2) 
- `onGetResponse()`, which trusts an empty proof unconditionally and refunds escrow: [4](#0-3) 

Attack sequence:
1. User places a cross-chain order on chain A, escrowing input tokens under `_orders[commitment]`, targeting chain B where the currently registered instance is gateway `X` (`_instances[hash(B)] = X`).
2. A solver fills the order on `X` on chain B: `X` sets `_filled[commitment] = solver`, pays the beneficiary, and dispatches `RedeemEscrow` back toward chain A.
3. Before that `RedeemEscrow` message is relayed/processed (normal ISMP latency window), governance performs a routine gateway migration on chain A's records, calling `NewDeployment` for chain B, which overwrites `_instances[hash(B)] = Y` (a freshly deployed, empty-storage gateway).
4. The user calls `cancelOrder` → `_cancelFromSource`. The GET request key is now built against `_instance(order.destination)` == `Y`, not `X`. Because `Y` never processed this order, the `_filled` slot at that key is empty.
5. `onGetResponse` sees an empty value and calls `_withdraw(..., isRefund=true, finalize=true)`, refunding the escrowed input tokens to the user on chain A — even though the order was already filled and paid out by `X` on chain B.
6. Whichever of the legitimate `RedeemEscrow` (crediting the solver) or the illegitimate refund (crediting the user) reaches `_withdraw` first drains `_orders[commitment][token]`; the loser reverts with `UnknownOrder`. By timing the cancel call to land before the solver's `RedeemEscrow`, the user can guarantee they receive the refund while the solver — having already paid out real output tokens on chain B — never recovers the escrowed input tokens.

No malicious relayer, prover, or governance actor is required: governance performs a normal, documented migration (analogous to `updateFantiumNFTAddress`), and an ordinary unprivileged user/solver pair is left exposed purely because settlement state is checked against the *current* registered address rather than the address that was authoritative when the order was filled.

### Impact Explanation
This is a fund-loss / double-settlement bug matching the bounty's "stealing or loss of funds" and "replay/double-claim/double-settlement" categories. A user can obtain a refund of escrowed input tokens on the source chain while a solver has already unconditionally delivered the equivalent output tokens on the destination chain — the solver's payment is unrecoverable, and the protocol's escrow accounting reflects a duplicate release of the same commitment's value to two different parties.

### Likelihood Explanation
Triggering requires only a gateway/instance migration (`NewDeployment`) — a normal operational event that the docs explicitly support for redeployments — coinciding with in-flight orders, plus an unprivileged user racing a `cancelOrder` call against a delayed `RedeemEscrow` relay. Cross-chain relaying inherently introduces delay windows, and migrations are advertised as supported operations, so the race window is realistically reachable without any privileged or malicious actor.

### Recommendation
Bind settlement authentication and cancellation proof lookups to the gateway instance address that was registered for the destination chain **at order-placement time** (snapshot it into the order/commitment record), rather than resolving `_instance()` live at fill/cancel time. Additionally, `_cancelFromSource`/`onGetResponse` should require that the queried instance address matches the instance recorded for that specific order, and migrations should not silently invalidate proofs for orders still pending settlement — e.g., retain the old instance mapping until all orders opened against it have settled, or require an explicit drain/quiesce period during `NewDeployment` migrations before old addresses become unqueryable.

### Proof of Concept
1. Deploy IntentGatewayV2 on chain A and gateway `X` on chain B; register `_instances[hash(B)] = X` via `NewDeployment`.
2. User places order O on chain A (destination B), escrowing input tokens.
3. Solver calls `fillOrder` on `X`; `X` sets `_filled[commitment(O)] = solver` and dispatches `RedeemEscrow` toward A (do not yet deliver this message in the PoC harness).
4. Governance calls `NewDeployment` on chain A's gateway to migrate chain B's registration to a freshly deployed `Y` (empty storage), setting `_instances[hash(B)] = Y`.
5. User calls `cancelOrder`/`_cancelFromSource` for O; the dispatched GET request's key is built from `_instance(B)` == `Y`.
6. Simulate the GET response with an empty value (since `Y` has no `_filled[commitment(O)]` entry) — `onGetResponse` refunds O's escrow to the user.
7. Now deliver the originally-dispatched `RedeemEscrow` from step 3 — observe it reverts with `UnknownOrder` (escrow already zeroed), proving the solver cannot recover funds after having already paid the beneficiary in step 3, while the user received both the destination-chain output tokens and the source-chain refund.
