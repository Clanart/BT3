### Title
Permissionless `harvest()` allows attackers to siphon accrued WOM rewards from long-term stakers via flash deposit/withdraw - (File: `wombat/WombatStaking.sol`, `rewards/BaseRewardPoolV2.sol`, `wombat/WombatPoolHelper.sol`)

### Summary
`WombatPoolHelper.harvest()` / `WombatPoolHelperV2.harvest()` call `WombatStaking.harvest(_lpToken)` with no access control beyond `whenNotPaused` and `_onlyActivePool`, meaning any unprivileged wallet can trigger realization of pending WOM rewards from the underlying Wombat exchange at will. [1](#0-0) [2](#0-1)  Because reward distribution in `BaseRewardPool`/`BaseRewardPoolV2` uses a `rewardPerTokenStored` accumulator that is updated proportionally to `totalStaked()` **at the moment `queueNewRewards` is called**, an attacker can deposit LP tokens, immediately call the permissionless `harvest()` to pull in WOM rewards that had accrued to long-standing depositors while the attacker had zero exposure, then withdraw right away since there is no deposit cooldown, vesting, or withdrawal fee anywhere in the staking/pool-helper/rewarder contracts. [3](#0-2) 

### Finding Description
Reward accrual in the underlying Wombat protocol happens continuously (time-weighted), but the Magpie wrapper contracts only "realize" those rewards into `BaseRewardPool`/`BaseRewardPoolV2` at discrete, permissionlessly-triggerable points: when a user deposits, withdraws, or calls `harvest()` directly. [4](#0-3) [5](#0-4) [2](#0-1) 

Reward distribution is done via the standard `rewardPerTokenStored` accumulator pattern: `_provisionReward` increments `rewardPerTokenStored` by `(_amountReward * 10**decimals) / totalStaked()`, i.e., proportional to whoever is staked **at the instant the reward is queued**, with no consideration of how long each staker has held their position. [6](#0-5) 

`MasterMagpie._deposit` does correctly harvest pending rewards for the depositor's account and set `user.rewardDebt` to the current `accMGPPerShare` before adding the new stake, which prevents a depositor from stealing rewards realized within the *same* deposit transaction (the deposit call inside `WombatStaking.deposit` triggers `_toMasterWomAndSendReward` before the receipt token is minted and staked into `MasterMagpie`). [7](#0-6) [8](#0-7) 

However, this ordering protection only covers the single harvest call embedded in the deposit itself. Nothing prevents an attacker from:
1. Depositing LP tokens (staking into `MasterMagpie`/`BaseRewardPool` with rewardDebt set at current `accRewardPerShare`).
2. Immediately calling the fully permissionless `WombatPoolHelper.harvest()` in a subsequent call (even the very next block, or possibly the same transaction via a custom contract), which invokes `WombatStaking.harvest(_lpToken)` → `_toMasterWomAndSendReward` → `IBaseRewardPool.queueNewRewards`, realizing WOM rewards that had been accruing to existing long-term stakers. [2](#0-1) 
3. Because `totalStaked()` at the time of `queueNewRewards` now includes the attacker's freshly-added stake, the attacker receives a proportional share of that reward drop despite having contributed zero time/risk. [9](#0-8) 
4. Withdraw immediately afterward — there is no cooldown, timelock, or exit fee anywhere in `WombatStaking.withdraw`/`WombatPoolHelper.withdraw`. [10](#0-9) [5](#0-4) 

This is the same bug class as the reported issue in `Delegation.sol`: reward distribution is based on stake at the moment of distribution rather than time-weighted contribution, allowing opportunistic depositors to front-run/trigger reward realization events and siphon rewards away from long-term backers.

### Impact Explanation
Long-term LPs who have been staked for extended periods and accumulated exposure to WOM emissions have their expected yield diluted every time an attacker deposits and force-harvests, then exits. Since `harvest()` is unrestricted and callable by anyone at any time and there's no minimum holding period, this can be repeated systematically, resulting in an ongoing, permanent siphoning of unclaimed yield that rightfully belongs to long-standing depositors. This qualifies as theft of unclaimed yield.

### Likelihood Explanation
The likelihood is high: the `harvest()` entrypoint is deliberately permissionless (documented as the only function anyone can call), deposits and withdrawals carry no cooldown, fee, or vesting mechanism, and the exploit requires only ordinary wallet transactions (deposit → harvest → withdraw) — no privileged role, oracle manipulation, or governance is needed. [11](#0-10) 

### Recommendation
Short term: introduce a minimum staking duration or a deposit-to-reward-eligibility delay so that newly deposited stake does not participate in reward distributions realized within the same epoch/block, or apply a withdrawal fee/cooldown to remove the profitability of flash-deposit reward sniping. Long term: consider time-weighted reward accounting (e.g., vesting rewards over the accrual period rather than snapshotting at harvest time) so that reward share reflects actual time-weighted exposure rather than instantaneous balance at harvest time.

### Proof of Concept
1. Attacker observes (or simply waits for) a period where the underlying Wombat pool has significant unharvested WOM rewards.
2. Attacker calls `WombatPoolHelper.deposit(_amount, _minimumLiquidity)` which stakes receipt tokens into `MasterMagpie`/`BaseRewardPoolV2` at the current `rewardPerTokenStored`, with `user.rewardDebt` set to the pre-deposit accumulator value. [12](#0-11) [8](#0-7) 
3. Attacker (or anyone) calls `WombatPoolHelper.harvest()`, which force-realizes the pending WOM rewards into `BaseRewardPoolV2.queueNewRewards`, incrementing `rewardPerTokenStored` based on `totalStaked()` that now includes the attacker's stake. [1](#0-0) [6](#0-5) 
4. Attacker calls `WombatPoolHelper.withdraw(_liquidity, _minAmount)`, which internally harvests the attacker's now-earned share of the just-realized reward before returning the principal — with no fee or delay. [10](#0-9) 
5. The attacker walks away with a share of rewards that had accrued while they had no stake, at the expense of genuine long-term depositors' proportional share.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
