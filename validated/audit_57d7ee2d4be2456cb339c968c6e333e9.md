### Title
Unauthenticated OP_RETURN attribution lets an attacker redirect `get_first_unhandled_payout_by_operator_xonly_pk` to assign operator O an unfunded withdrawal while starving O's real one - ([File: core/src/database/verifier.rs])

### Summary
`get_first_unhandled_payout_by_operator_xonly_pk` (and the `payout_payer_operator_xonly_pk` column it reads) trusts an unauthenticated value parsed straight out of a payout transaction's `OP_RETURN` output, with no check that the named operator actually funded that payout. Because a payout transaction's `OP_RETURN` output is not covered by the user's `SinglePlusAnyoneCanPay` signature, any unprivileged party can construct a valid payout for withdrawal `j`, fund output0 with their own money, and stamp any operator O's real x-only pubkey into the `OP_RETURN`, causing `PayoutCheckerTask` to process `j` under O's identity instead of O's genuinely funded withdrawal `i`.

### Finding Description
Binding claimed: `payout_payer_operator_xonly_pk(idx) == O` ⟺ `O`'s own funds paid `idx`'s output0.

Trace:
- A payout tx's only user-signed material is input0 (the withdrawal claim UTXO) and output0 (payout amount/address), signed with `TapSighashType::SinglePlusAnyoneCanPay`, enforced in `core/src/rpc/parser/operator.rs::parse_withdrawal_sig_params` (lines 161-203) and verified in `core/src/operator.rs::withdraw` (lines 620-637) via `SECP.verify_schnorr` over `calculate_sighash_txin(0, ...)`.
- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) appends an `OP_RETURN` output containing `operator_xonly_pk` as plain `PushBytesBuf` data — this output is *not* covered by the ANYONECANPAY|SINGLE signature, so it can be swapped freely by whoever finalizes/broadcasts the transaction, as can any additional funding inputs (added via `fund_raw_transaction`, e.g., `core/src/operator.rs:652-674`).
- The verifier's block scanner blindly parses this `OP_RETURN` as the payer's identity with zero authentication: `core/src/verifier.rs::update_finalized_payouts` (lines 2312-2342) does `parse_op_return_data` → `XOnlyPublicKey::from_slice` and stores it via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`) into `withdrawals.payout_payer_operator_xonly_pk`.
- `get_first_unhandled_payout_by_operator_xonly_pk` (`core/src/database/verifier.rs:282-313`) simply selects `MIN(idx)` where this unauthenticated column equals O's pubkey and `is_payout_handled = FALSE`.
- `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) takes whatever idx this query returns and calls `Operator::handle_finalized_payout` (`core/src/operator.rs:839-916`), which only validates that a deposit exists and that O has an unused/signed kickoff connector for it (`get_unused_and_signed_kickoff_connector`) — it never checks that O's wallet actually supplied the payout tx's additional funding inputs.

Because nothing ties the `OP_RETURN` pubkey to the real source of funds, an attacker who observes/possesses ANY user's handed-over `SinglePlusAnyoneCanPay` signature for withdrawal `j` (a withdrawal O never touched) can build and broadcast a payout tx for `j` funded from the attacker's own coins, embedding O's real (public) x-only pubkey in the `OP_RETURN`. Once confirmed, `payout_payer_operator_xonly_pk = O` for idx `j`. If `j < i` (O's genuinely-funded withdrawal), `get_first_unhandled_payout_by_operator_xonly_pk(O)` returns `j` instead of `i`, and `PayoutCheckerTask` drives O through `handle_finalized_payout`/`mark_payout_handled` for a deposit O never funded, consuming one of O's limited per-round kickoff connectors. Combined with a separate `OP_RETURN`-stripping/overwrite on `i` (a distinct, previously identified issue), O's real payout `i` is left permanently unattributed and unhandled while O's finite round/kickoff capacity is wasted on `j`.

No existing guard closes this gap: `Verifier::is_deposit_valid`, `is_profitable`, and `SECP.verify_schnorr` only validate the withdrawal claim UTXO/output0 signature and deposit legitimacy — none of them, nor the bridge circuit's `deposit_constant` computation (`circuits-lib/src/bridge_circuit/mod.rs`), verify that the operator whose pubkey appears in `OP_RETURN` actually supplied the payout funding inputs.

### Impact Explanation
This breaks the "operator reimbursed for a payout it never funded" Critical category directly: `handle_finalized_payout`/`mark_payout_handled` proceeds for O using an attacker-forged attribution, consuming O's scarce kickoff-connector/round capacity. When paired with the referenced OP_RETURN-stripping attack on the genuinely-funded idx, this can make an honest operator permanently unable to be reimbursed for money it actually fronted — also Critical. The attack is repeatable across any withdrawal/operator pair as long as the attacker can front the payout output amount (which they recoup no protection against, but can target repeatedly against any operator whose pubkey is public).

### Likelihood Explanation
Preconditions are modest for an unprivileged attacker: obtain a legitimate user's ANYONECANPAY|SINGLE signature for some unrelated withdrawal `j` (these are exchanged off-chain to operators/aggregator but are not bound to any specific operator and are not secret in a cryptographic sense — anyone who receives them, e.g., via the aggregator's `withdraw` broadcast to multiple operators, can reuse them), fund `j`'s output amount from their own BTC, and know any operator's public x-only key (published via `GetParams`). No verifier/operator/aggregator compromise is required. The main cost is the attacker fronting `j`'s payout amount in BTC plus fees, which is bounded but real; the payoff is targeted disruption of a specific operator's reimbursement pipeline.

### Recommendation
Do not trust `OP_RETURN` payer attribution as an unauthenticated fact. Require that the operator claiming credit for a payout produce/co-sign proof that they supplied the payout tx's funding (e.g., require an additional operator-specific signature over the full payout tx, or bind the `OP_RETURN` operator claim into the ANYONECANPAY sighash so it cannot be swapped by a third party), and have `handle_finalized_payout`/`PayoutCheckerTask` verify this binding before consuming kickoff/round resources.

### Proof of Concept
```rust
// core/src/database/verifier.rs (extend existing test module)
#[tokio::test]
async fn forged_op_return_redirects_payout_checker_to_wrong_idx() {
    let config = create_test_config_with_thread_name().await;
    let db = Database::new(&config).await.unwrap();
    let mut dbtx = db.begin_transaction().await.unwrap();

    let operator_pk = generate_random_xonly_pk();

    // idx_i: genuinely funded by operator O
    let idx_i = 10u32;
    let txid_i = Txid::from_byte_array([0x11; 32]);
    // ... insert block/spent-utxo/move-to-vault/withdrawal-utxo rows for idx_i as in existing test ...
    db.update_payout_txs_and_payer_operator_xonly_pk(
        Some(&mut dbtx), vec![(idx_i, txid_i, Some(operator_pk), BlockHash::all_zeros())],
    ).await.unwrap();

    // idx_j: attacker-forged attribution to the SAME operator_pk, O never funded it
    let idx_j = 3u32; // lower idx than idx_i
    let txid_j = Txid::from_byte_array([0x22; 32]);
    // ... insert block/spent-utxo/move-to-vault/withdrawal-utxo rows for idx_j (attacker-funded output0) ...
    db.update_payout_txs_and_payer_operator_xonly_pk(
        Some(&mut dbtx), vec![(idx_j, txid_j, Some(operator_pk), BlockHash::all_zeros())],
    ).await.unwrap();

    // Binding under test: get_first_unhandled_payout_by_operator_xonly_pk(O) should
    // only ever return an idx that O truly funded (idx_i), never idx_j.
    let (returned_idx, _, _) = db
        .get_first_unhandled_payout_by_operator_xonly_pk(Some(&mut dbtx), operator_pk)
        .await
        .unwrap()
        .expect("must be Some");

    // FAILS today: returns idx_j (attacker-forged, lower idx), not idx_i (O's real payout)
    assert_eq!(returned_idx, idx_i, "PayoutCheckerTask would process an unfunded withdrawal for O");
}
```
Run with `cargo test -p clementine-core forged_op_return_redirects_payout_checker_to_wrong_idx -- --nocapture` against a local Postgres test DB (no mainnet/live Citrea needed, matching the existing `update_get_payout_txs_from_citrea_withdrawal` test pattern in `core/src/database/verifier.rs`). The assertion fails because the query has no way to distinguish a forged `OP_RETURN` attribution from a genuine one.
