### Title
Aggregator gRPC server accepts state-changing/broadcasting calls without client authentication - (File: core/src/servers.rs, core/src/rpc/aggregator.rs)

### Summary
Clementine's Operator and Verifier gRPC servers enforce mTLS-based client authentication via an `Interceptors::OnlyAggregatorAndSelf` layer that restricts callers to the Aggregator or the entity itself [1](#0-0) . The Aggregator server, however, is documented and implemented to skip this restriction entirely: *"The aggregator does not enforce client certificates but does use TLS for encryption"* [2](#0-1) . This mirrors the reported bug class — a missing access-control check that lets an unintended caller reach a privileged, state-changing entry point (the `DepositLog`/`TBTCSystem` analog here being the Aggregator's coordination and broadcast RPCs, which are documented as intended only for the "clementine-backend service").

### Finding Description
The gRPC server bootstrap function `create_grpc_server` builds an `InterceptedService` wrapping either `OnlyAggregatorAndSelf` (when `client_verification` is enabled) or `Noop`, and this same generic function is reused for Verifier and Operator servers, which are started with `client_verification` enforced and their interceptor validates the TLS leaf certificate against the configured `aggregator_cert_path`/`client_cert_path` [3](#0-2) . For the Verifier/Operator, calling an "Internal*" method requires the caller's own certificate, and calling any other method requires either the entity's own cert or the Aggregator's cert [4](#0-3) .

The Aggregator's own gRPC endpoint is not gated by this mechanism — per the documentation it only uses TLS for transport encryption, not for authenticating who is allowed to call it. Yet the Aggregator's proto/service comments repeatedly state these RPCs are "Used by the clementine-backend service" only, e.g. `NewDeposit`, `Withdraw`, `SendMoveToVaultTx`, `InternalSendTx`, `OptimisticPayout` [5](#0-4) . These are state-changing/broadcasting operations:
- `internal_send_tx` inserts an arbitrary caller-supplied raw signed transaction directly into the `TxSender` queue for broadcast to the Bitcoin network [6](#0-5) .
- `send_move_to_vault_tx` validates output shape/amounts and then broadcasts the move-to-vault transaction, driving BTC out of a deposit UTXO on-chain [7](#0-6) .
- `new_deposit` triggers key collection/distribution and a full N-of-N nonce/signature ceremony across all verifiers and operators [8](#0-7) .

None of these Aggregator RPC handlers perform any caller-identity check of their own (no signature-based caller authentication comparable to the operator's `verification_signature` check inside `withdraw`) [9](#0-8) ; the only boundary that exists for these calls is transport-level TLS, and that boundary is explicitly not used to authenticate the caller for the Aggregator.

### Impact Explanation
This falls under the report's "High" bucket: *"an unauthenticated state-changing or broadcasting call."* Any network party that can reach the Aggregator's gRPC port can directly invoke privileged coordination and broadcast entry points that the documentation says are reserved for the trusted backend service, without presenting any credential the Aggregator actually checks. Concretely:
- `InternalSendTx` lets an unauthenticated caller force broadcast of a signed transaction of their choosing directly through the bridge's own fee-bumping `TxSender` infrastructure, bypassing whatever timing/ordering logic the backend service would otherwise enforce.
- `SendMoveToVaultTx` and `NewDeposit` let any unauthenticated caller drive the Aggregator through its verifier/operator coordination and Bitcoin-broadcast pipeline for deposits, at will, without going through the intended `clementine-backend` gatekeeper.

While value-forging is still blocked by cryptographic signature checks further down the pipeline (verifiers/operators still enforce their own mTLS via `OnlyAggregatorAndSelf`, and Bitcoin consensus rejects invalid witnesses), the access-control gap itself is a real, exploitable boundary violation matching the reported bug class: the caller reaching a state-changing/broadcasting method is not the party ("clementine-backend service") the method is meant for.

### Likelihood Explanation
High. The Aggregator's gRPC listener is a normal TCP/TLS endpoint reachable by any network client that can connect to its configured `host:port`; no additional secret, certificate pinning, or signature is required to invoke these RPCs, and this behavior is by explicit design/documentation ("aggregator does not enforce client certificates"), not an edge-case misconfiguration.

### Recommendation
Apply the same certificate-based authentication used for the Operator/Verifier servers to the Aggregator's incoming connections (or an equivalent explicit caller-authentication mechanism), restricting Aggregator RPCs — especially state-changing/broadcasting ones such as `NewDeposit`, `Withdraw`, `SendMoveToVaultTx`, `InternalSendTx`, and `OptimisticPayout` — to the intended `clementine-backend` service identity, consistent with the documented trust model.

### Proof of Concept
1. Start an Aggregator server per the standard configuration (`client_verification` has no effect on the Aggregator per `docs/usage.md`) [2](#0-1) .
2. From any machine with network access to the Aggregator's TLS endpoint (no special client certificate required beyond generic TLS), open a gRPC channel and call `ClementineAggregator/InternalSendTx` with an arbitrary previously-observed signed raw transaction, or call `ClementineAggregator/SendMoveToVaultTx` / `ClementineAggregator/NewDeposit` directly [6](#0-5) .
3. Observe the Aggregator processes the request and performs the associated state-changing action (queuing/broadcasting a transaction, or driving the multi-party deposit signing ceremony) with no caller-authentication check having been performed — unlike the analogous calls into Operator/Verifier, which would reject an unrecognized client certificate per `only_aggregator_and_self` [10](#0-9) .

use tonic::{service::Interceptor, transport::CertificateDer, Request, Status};

#[derive(Debug, Clone)]
pub enum Interceptors {
    OnlyAggregatorAndSelf {
        aggregator_cert: CertificateDer<'static>,
        our_cert: CertificateDer<'static>,
    },
    Noop,
}

fn is_internal(req: &Request<()>) -> bool {
    // This normally doesn't exist but we add it in the AddMethodMiddleware
    let Some(path) = req.metadata().get("grpc-method") else {
        // No grpc method? this should not happen
        tracing::error!("Missing grpc-method header in request");
        return false;
    };
    path.as_bytes().starts_with(b"Internal")
}

impl Interceptor for Interceptors {
    #[allow(clippy::result_large_err)]
    fn call(&mut self, req: Request<()>) -> Result<Request<()>, Status> {
        match self {
            Interceptors::OnlyAggregatorAndSelf {
                our_cert,
                aggregator_cert,
            } => only_aggregator_and_self(req, our_cert, aggregator_cert),
            Interceptors::Noop => Ok(req),
        }
    }
}

fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
}

## RPC Authentication

Clementine uses mutual TLS (mTLS) to secure gRPC communications between entities
