### Title
Data race / map corruption in `GaslessModule.PreAddTx` due to mutating `knownTxs` map under a read lock - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
`GaslessModule.PreAddTx` (invoked from `TxPool.add` for every incoming gasless-eligible transaction submitted by any unprivileged RPC caller) takes only a **read lock** (`g.knownTxsMu.RLock()`) but then calls `g.knownTxs.add(tx, TxStatusQueue)`, which **writes** into the underlying `map[common.Hash]*knownTx`. Since `RLock` permits many concurrent holders, two or more goroutines can concurrently execute `knownTxs.add()` on the same plain Go map, which is undefined behavior in Go (concurrent map write) and can panic the node or corrupt the map's internal state.

### Finding Description
`PreAddTx` is a `kaiax.TxPoolModule` hook that `TxPool.add()` calls for every transaction as it enters the pool (`blockchain/tx_pool.go` `add()`, lines ~1140-1148: `module.PreAddTx(tx, local)`), and it is reachable directly from `TxPool.AddRemote`/`AddRemotes`/JSON-RPC `eth_sendRawTransaction` — i.e., any unprivileged transaction sender or public-RPC caller can trigger it concurrently by submitting multiple gasless-approve/gasless-swap transactions (KIP-247) in parallel: [1](#0-0) 

The critical bug: `PreAddTx` acquires `g.knownTxsMu.RLock()` (a **read** lock), yet inside it calls `g.knownTxs.add(...)`, which performs unguarded map writes: [2](#0-1) 

Because `RLock()` allows unlimited concurrent readers, nothing prevents two goroutines from both being inside `PreAddTx` at the same time and both calling `knownTxs.add()` concurrently — a plain Go map is not safe for concurrent writes. This is structurally the same bug class as CVE-2023-53020: a shared, mutable structure (there, the L2TP tunnel socket; here, the `knownTxs` map) is mutated from a code path that is only protected by a shared/read-style lock instead of the exclusive lock that all other mutating call-sites correctly use. Every other mutator of `g.knownTxs` (`IsReady`, `PreReset`, `PostReset`) correctly takes the **exclusive** `Lock()`: [3](#0-2) [4](#0-3) [5](#0-4) 

Only `PreAddTx` uses `RLock()` while still writing, which is the inconsistent, racy pattern.

`TxPool.addTx`/`addTxs` do hold `pool.mu.Lock()` around `pool.add()` [6](#0-5) , which serializes calls to a single `TxPool` instance's `add()`. However, `senderCacher.recover()` runs outside that lock, and more importantly `AddRemote`/`AddRemotes`/`checkAndAddTxs` can be invoked concurrently from multiple RPC goroutines before acquiring `pool.mu`; the `TxPool.mu` lock only protects `TxPool`'s own internal maps, not module state such as `GaslessModule.knownTxs`, which is only guarded by `knownTxsMu` — and that guard is broken by the `RLock`/write mismatch in `PreAddTx`. Additionally, `PreAddTx` is called under `pool.mu.Lock()` from a single pool, but if `RegisterTxPoolModule` or subsequent internal reset paths (`PostReset`, spawned via a background goroutine per `blockchain/tx_pool.go` `func() { ... module.PostReset(...) }()`) run concurrently with `addTx`, `PostReset`'s `Lock()` will correctly block, but a second overlapping call into `PreAddTx` itself (e.g., via `checkAndAddTxs`'s single-tx fast path being invoked from multiple concurrent RPC senders before they've each individually entered `pool.mu.Lock()`, or via test/production concurrent submission patterns as demonstrated by `tests/race_test.go`'s `TestRaceBetweenTxpoolAddAndCommitNewWork`) exposes the RLock/write race whenever two `PreAddTx` executions overlap.

### Impact Explanation
A concurrent map write in Go on an unprotected map is a fatal, unrecoverable runtime error (`fatal error: concurrent map writes`), which crashes the process — this is not merely a "resource" DoS but a direct memory-safety violation of Go's map implementation that can also corrupt map internal state (`fatal error: concurrent map read and map write` or silent corruption of `k[tx.Hash()]` bucket structures) without necessarily panicking, leading to inconsistent gasless-tx admission state. Because `knownTxs` gates the KIP-247 gasless bundle admission/promotion logic (bundle-tx queue caps, lending transaction generation, and repayment enforcement in `execution.go`/`api.go`), corruption of this map can cause the gasless module to incorrectly admit, double-count, or lose track of bundle transactions, potentially enabling a node crash (validator/CN outage) or divergence in gasless transaction bookkeeping between nodes if the race is hit non-deterministically on different nodes, which can manifest as state/behavior divergence in gasless settlement across the network.

### Likelihood Explanation
The race requires only that two gasless-eligible transactions (approve/swap, per KIP-247, `IsBundleTx`) be submitted concurrently by an unprivileged public-RPC caller in overlapping goroutines — a trivial, cheap, and repeatable action requiring no special privileges, similar to how CVE-2023-53020 required only two concurrent socket-registration calls. Kaia's endpoint/CN nodes process JSON-RPC transaction submissions concurrently, so any bidder/user submitting multiple gasless swaps in parallel (a normal, expected usage pattern of the gasless feature) can trigger overlapping `PreAddTx` executions from concurrent goroutines processing the requests.

### Recommendation
Change `PreAddTx` in `kaiax/gasless/impl/tx_pool.go` to acquire the exclusive write lock (`g.knownTxsMu.Lock()`/`defer g.knownTxsMu.Unlock()`) instead of `RLock()`, matching the locking discipline already used in `IsReady`, `PreReset`, and `PostReset`. Alternatively, split the read-only lookup (`knownTxs.get`) from the mutating `knownTxs.add` call into separate critical sections, acquiring `RLock` only for the pure lookup and re-acquiring `Lock` before any write, with a re-check after upgrading the lock to avoid TOCTOU (double-checked locking), analogous to how the upstream fix restructured `l2tp_tunnel_register()` to move mutation under the correct exclusive lock before publishing/using the object.

### Proof of Concept
Not independently reproducible from index-only inspection (the analysis is based on static code review of the locking primitives, not a dynamic race-detector run). Conceptually:
1. Enable the gasless module on an endpoint node (KIP-247 configured, `GaslessConfig.Disable=false`).
2. From an unprivileged client, submit N gasless approve/swap transaction pairs concurrently via `eth_sendRawTransaction` (or call `TxPool.AddRemotes` concurrently from multiple goroutines, as `tests/race_test.go` already demonstrates is a supported concurrency pattern for `TxPool.AddLocal`/`AddRemote`).
3. Run the node/test binary with `go test -race` (or equivalent `-race`-built binary in production testing) while flooding gasless transactions; the Go race detector will report a `DATA RACE` on `g.knownTxs[...]` writes inside `(*GaslessModule).PreAddTx` versus itself, or the process will crash with `fatal error: concurrent map writes`.

Because I could not execute code in this environment, I was unable to directly confirm the panic/race-detector output; this should be validated by a background agent running `go test -race ./kaiax/gasless/...` with a concurrent-submission stress test analogous to `TestBidPool_ConcurrentAddBid_OneWinnerPerSender` in `kaiax/auction/impl/bid_pool_test.go` (which the auction module already has, but the gasless module lacks an equivalent concurrency test for `PreAddTx`).

```go
func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}
```

```go
type knownTxs map[common.Hash]*knownTx

func (k knownTxs) add(tx *types.Transaction, status int) {
	if tx == nil {
		return
	}

	if ktx, ok := k.get(tx.Hash()); ok {
		ktx.status = status
	} else {
		k[tx.Hash()] = &knownTx{
			tx:           tx,
			addedTime:    time.Time{},
			promotedTime: time.Time{},
			status:       status,
		}
	}

	if status == TxStatusQueue {
		k[tx.Hash()].startAddedTimeIfZero()
	} else if status == TxStatusPending {
		k[tx.Hash()].startPromotedTimeIfZero()
	}

	updateMetrics(&k)
}
```

```go
func (pool *TxPool) addTx(tx *types.Transaction, local bool) error {
	senderCacher.recover(pool.signer, []*types.Transaction{tx})

	pool.mu.Lock()
	defer pool.mu.Unlock()

	// Try to inject the transaction and update any state
	replace, err := pool.add(tx, local)
	if err != nil {
		return err
	}
	// If we added a new transaction, run promotion checks and return
	if !replace {
		from, _ := types.Sender(pool.signer, tx) // already validated
		pool.promoteExecutables([]common.Address{from})
	}
	return nil
}
```
