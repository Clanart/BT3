### Title
`ReceivedOutput::read` accepts an arbitrary `offset` never validated against the output's `script_pubkey`, breaking the spendability invariant established by `Scanner` - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report's bug class is a recorded constraint (`expiration`) that is stored and even mutated (`extendDeposit`) yet never enforced on the action it should gate (`claimBounty`), so the field serves no external purpose. In `bitcoin-serai`, `Scanner` maintains a `script → offset` map keyed by `p2tr_script_buf(key + offset·G)`, which guarantees by construction that every `ReceivedOutput` it emits carries an `offset` consistent with `output.script_pubkey` [1](#0-0) . `ReceivedOutput::read`, however, deserializes `offset`, `output`, and `outpoint` as three independent attacker-controlled fields and performs no consistency check between them [2](#0-1) . Like the unchecked expiration, the `offset` is stored and later consumed as authoritative without ever being validated against the on-chain commitment (`script_pubkey`).

### Finding Description
`Scanner::register_offset` inserts `script_pubkey → offset` pairs where `script_pubkey = p2tr(key + offset·G)`, and `scan_transaction` only emits `ReceivedOutput`s whose `output.script_pubkey` matched a registered script, so scan-derived outputs always satisfy `p2tr_script_buf(key + offset·G) == output.script_pubkey` [3](#0-2) . This is the protocol's implicit "expiration-equivalent" invariant: the offset is the only data tying the received UTXO to a spendable key. `ReceivedOutput::read` on untrusted bytes (an in-scope `read` API) decouples the two: it reads any scalar via `Secp256k1::read_F` and any `TxOut`/`OutPoint` via consensus decoding, with no recomputation of the expected script [2](#0-1) . No caller-visible API re-derives `p2tr_script_buf(key + offset)` to compare against `output.script_pubkey` — the stored field is simply trusted, mirroring `claimBounty` ignoring `expiration` entirely.

### Impact Explanation
An unprivileged party feeding crafted bytes into `ReceivedOutput::read` can produce an output the wallet treats as a received deposit while the associated `offset` does not correspond to the key paying to `output.script_pubkey`. Downstream spend logic signs with `key.offset(offset)`, yielding a signature for a key that does not control the UTXO — funds reported as received are not spendable, and any transaction built on such an input is invalid, burning fee/change assumptions in the coin-join-style spends this wallet constructs. Per `register_offset`'s own documentation, arbitrary offsets "may introduce a script path into the output, allowing the output to be spent by satisfaction of an arbitrary script"; a mismatched offset silently asserts an ownership claim the protocol never verified [4](#0-3) .

### Likelihood Explanation
`ReceivedOutput::read` is explicitly an untrusted-bytes entry point; any input path that round-trips scanner results through serialization (peer relays, processor payloads, coordinator messages) lets a malicious sender substitute `offset`. The scanner path cannot produce such objects — only the `read` path can — which is exactly why a deserialization-side check is needed, just as the report recommends enforcing expiration at claim time rather than only at deposit time.

### Recommendation
Either make `ReceivedOutput` construction impossible outside `Scanner` (remove the public `read` or make it private and validate internally), or add a `ReceivedOutput::verify(key)` / check inside spend-path entry points that recomputes `p2tr_script_buf(key + (GENERATOR * offset))` and compares it to `output.script_pubkey`, rejecting mismatches — the direct analog of adding the missing `require` on expiration before honoring the claim.

### Proof of Concept
```rust
// Given a scanner-registered `key` and a real deposit output paying to
// script_pubkey = p2tr(key + real_offset * G):
let real = scanner.scan_transaction(&tx).pop().unwrap();

// Attacker serializes a forged ReceivedOutput: same TxOut/outpoint,
// but an unrelated offset (e.g. a scalar committing to an attacker script
// path, or simply garbage):
let mut forged_bytes = Vec::new();
forged_bytes.extend(attacker_offset.to_bytes());
forged_bytes.extend(serialize(real.output()));
forged_bytes.extend(serialize(real.outpoint()));

// Accepted without complaint — no consistency check exists:
let forged = ReceivedOutput::read(&mut forged_bytes.as_slice()).unwrap();
assert_eq!(forged.offset(), attacker_offset);            // attacker-chosen
assert_ne!(
  p2tr_script_buf(key + ProjectivePoint::GENERATOR * forged.offset()),
  Some(forged.output().script_pubkey.clone()),
); // invariant violated, yet nothing rejects it
```
Any spend built from `forged` signs under `key.offset(attacker_offset)`, which does not control `output.script_pubkey`, so the input is permanently unspendable despite being reported received — the exact "recorded but never enforced" failure of the source report.

One caveat: I was unable to fully inspect `networks/bitcoin/src/wallet/send.rs` (the spend path consuming `offset`) within available iterations, so the claim that no downstream check re-validates the offset rests on `mod.rs` exposing no such verification API and `read` performing none itself.

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }
