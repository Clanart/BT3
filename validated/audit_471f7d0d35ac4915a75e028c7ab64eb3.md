### Title
Forced reward transfer inside `unlock()` can permanently block MGP unlocking and freeze unclaimed yield for blacklisted-token recipients - (File: `VLMGP.sol`, `rewards/MasterMagpie.sol`, `rewards/vlMGPBaseRewarder.sol`)

### Summary
`VLMGP.unlock()` unconditionally forces a claim-and-transfer of all pending vlMGP rewards to `msg.sender` before releasing the user's own previously-cooled-down MGP. If any reward token queued for that vlMGP pool is a token capable of blacklisting an address (e.g. a USDC-denominated bribe/reward routed through vlMGP's rewarder), and the caller's address is blacklisted on that token, the forced transfer reverts and the entire `unlock()` call reverts, mirroring the Notional `settleVaultAccount` bug class exactly: a permissionless "settle-before-action" step that pushes tokens to the account and blocks the intended action if the transfer fails.

### Finding Description
`VLMGP.unlock()` first calls `IMasterMagpie(masterMagpie).multiclaimFor(lps, vlMGPrewards, msg.sender)` before unlocking and transferring the user's own MGP: [1](#0-0) 

`multiclaimFor` routes into `_claimBaseRewarder`, which calls `rewarder.getReward(_account, _receiver)` when no specific token list is passed (as is the case here, since `vlMGPrewards` is left as an empty inner array): [2](#0-1) 

That `getReward` call reaches `vlMGPBaseRewarder._sendReward`, which does an unconditional `IERC20(_rewardToken).safeTransfer(_receiver, toSend)` for every reward token registered for the pool, in a loop, within the same transaction: [3](#0-2) 

Because `_sendReward` is invoked once per reward token in a loop (via `_updateFor`/`getReward`), if *any single* reward token in the array reverts the transfer (e.g. USDC blacklist), the entire `unlock()` transaction reverts — including the unrelated MGP unlock at the end of the function. This is structurally identical to the Notional issue: an unconditional ERC20 push to the caller, embedded as a "settle first" precondition inside an otherwise permissionless/self-serve action, with no way to skip or bypass the transfer.

### Impact Explanation
A user whose address becomes blacklisted on any ERC20 token that is ever queued as a vlMGP reward (bribe tokens can be arbitrary ERC20s, commonly stablecoins like USDC per `WombatBribeManager`/reward flows in this codebase) can never successfully call `unlock()` again for that pool. This:
- Permanently freezes any yet-unclaimed vlMGP rewards for that account (since `getReward` will always revert before any transfer is recorded/cleared), satisfying "permanent freezing of unclaimed yield."
- Blocks the user from completing their normal unlock flow via `unlock()` (the intended zero-penalty exit path is blocked indefinitely), which is a permanent freeze of the intended withdrawal path.

The user does retain `forceUnLock()` as an alternative path since it does not call `multiclaimFor` and only transfers the underlying MGP token: [4](#0-3) 
but doing so forces the user to accept a penalty (`expectedPenaltyAmount`) purely because of an unrelated reward token's blacklist status, and it still does not resolve the permanently stuck/unclaimed reward tokens tied to that account within the rewarder's accounting.

### Likelihood Explanation
Likelihood depends on a reward/bribe token used by the vlMGP rewarder being a token with blacklist functionality (e.g., USDC) and the specific user's address being blacklisted by that token's issuer — an external precondition outside the protocol's control, same as in the original Notional report. Given bribe/reward tokens in this ecosystem are configurable by governance and commonly include mainstream stablecoins, this is a realistic configuration, not a purely theoretical one.

### Recommendation
Wrap each reward token transfer in `_sendReward` (and equivalently in `mWOMSVBaseRewarder`, `BaseRewardPoolV2`, `BribeRewardPool`) in a try/catch or low-level call, and if the transfer fails, retain the reward as a claimable/queued balance instead of reverting the whole batch. This decouples the unrelated core action (`unlock()`'s MGP release) from the success of reward-token pushes, preventing one non-transferable token from freezing both future reward claims and the core unlock functionality.

### Proof of Concept
1. Governance/whitelisted party adds a blacklist-capable token (e.g., a USDC-based bribe) as a reward token routed through vlMGP's rewarder for the vlMGP pool.
2. Reward accrues to a user's vlMGP position over time (`userRewards[usdc][user] > 0`).
3. USDC issuer blacklists the user's address (external event, as assumed valid per the original report's precedent).
4. User's lock cooldown finishes; user calls `VLMGP.unlock(slotIndex)`.
5. `unlock()` calls `multiclaimFor` → `_claimBaseRewarder` → `getReward` → `_sendReward`, which attempts `IERC20(USDC).safeTransfer(user, toSend)`; this reverts due to blacklist.
6. The entire `unlock()` transaction reverts, so the user cannot retrieve their unlocked MGP through the intended path, and their pending USDC reward remains permanently unclaimable through this function.
