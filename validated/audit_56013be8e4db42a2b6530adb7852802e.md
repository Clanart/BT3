### Title
Unchecked ERC20 `transfer()` return value in `ArbWomUp`/`ArbWomUp2` reward payout permanently forfeits unclaimed yield - (File: `wombat/ArbWomUp.sol`, `wombat/ArbWomUp2.sol`)

### Summary
`ArbWomUp.incentiveDeposit()` and `ArbWomUp2.incentiveDeposit()` are unprivileged, user-callable functions that deposit WOM and pay out a USDT/BUSD reward. Both contracts correctly use `safeTransferFrom` to pull the user's WOM, but the reward payout uses a plain, unchecked `IERC20(...).transfer(...)` call, and the internal `claimedReward` accounting is updated unconditionally *before* the transfer even executes.

### Finding Description
In `ArbWomUp.sol`: [1](#0-0) 
`claimedReward[msg.sender]` is incremented, and then the USDT reward is sent via a raw `IERC20(usdt).transfer(msg.sender, rewardToSend)` call whose boolean return value is never checked.

The same pattern exists in `ArbWomUp2.sol`: [2](#0-1) 
where `claimedReward[msg.sender]` is bumped and `IERC20(busd).transfer(msg.sender, rewardToSend)` is called without checking success, while the WOM inbound leg still correctly uses `safeTransferFrom`: [3](#0-2) 

This is the exact bug class described in the report: for ERC20 tokens that signal failure by returning `false` instead of reverting, a failed transfer is silently ignored. Because `claimedReward` is already incremented and `getRewardAmount()` computes future entitlement as `(tier_reward / DENOMINATOR) - claimedReward[_account]`: [4](#0-3) 
the user's reward is treated as "paid" even though it never left the contract. Any subsequent `incentiveDeposit` call will compute a smaller (or zero) reward, since `claimedReward` already reflects the failed payout — permanently forfeiting that portion of the user's yield with no path to reclaim it.

This can also be triggered without any malicious token behavior: `getRewardAmount()` caps the reward to the contract's live USDT/BUSD balance (`usdtleft`/`busdleft`), but this check and the subsequent transfer are not atomic with respect to concurrent calls in the same block/mempool. If the reward token used is one that returns `false` on insufficient balance rather than reverting (a known category of non-compliant ERC20 tokens), a user whose transfer silently fails still has `claimedReward` permanently incremented as if they were paid.

### Impact Explanation
An ordinary user calling `incentiveDeposit()` can have their WOM correctly pulled (via `safeTransferFrom`) while their promised USDT/BUSD reward silently fails to arrive, yet the contract's internal ledger (`claimedReward`) marks it as claimed. This is a permanent, unrecoverable loss of the user's earned incentive/airdrop-style reward, matching the "theft or permanent freezing of unclaimed yield" impact category.

### Likelihood Explanation
The path is reachable directly from any unprivileged wallet calling `incentiveDeposit()` with no special preconditions beyond the reward token exhibiting return-false-on-failure semantics or balance-race conditions — both realistic behaviors for ERC20 tokens deployed on BSC/Arbitrum, and the affected `usdt`/`busd` addresses can be configured to any token via the owner's `__arbWomUp_init`/`setup` calls, but the trigger itself requires no privileged action by the caller.

### Recommendation
Use `SafeERC20.safeTransfer` (already imported via `using SafeERC20 for IERC20`) instead of the raw `.transfer()` call in `incentiveDeposit()` in both `ArbWomUp.sol` (line 76) and `ArbWomUp2.sol` (line 94), and only update `claimedReward` after a successful transfer, so failed payouts revert the whole deposit rather than being silently recorded as claimed.

### Proof of Concept
1. Owner configures `usdt` (or `busd`) to a non-standard ERC20 that returns `false` instead of reverting when a transfer cannot be completed (e.g., due to insufficient contract balance, which can occur once `usdtleft`/`busdleft` is drawn down by concurrent claims).
2. User A calls `incentiveDeposit(amount)`; `getRewardAmount` returns a `rewardToSend` value based on the currently available balance.
3. Before A's transaction is mined, User B's `incentiveDeposit` call executes first and drains the remaining USDT/BUSD balance.
4. A's transaction executes: `claimedReward[A] += rewardToSend` runs unconditionally, then `IERC20(usdt).transfer(A, rewardToSend)` returns `false` (no tokens sent) but the call does not revert.
5. `claimedReward[A]` now reflects a reward A never received; all future `getRewardAmount` calls for A subtract this phantom claimed amount, permanently reducing/eliminating A's future reward entitlement with no way to recover the lost funds.

```text
    function getRewardAmount(uint256 _amount, address _account) external view returns (uint256) {
        if (_amount == 0 || rewardMultiplier.length == 0) return 0;
        uint256 accumulated = _amount + userWOMDeposited[_account];

        uint256 rewardAmount = 0;
        uint256 i = 1;
        while (i < rewardTier.length && accumulated > rewardTier[i]) {
            rewardAmount +=
                (rewardTier[i] - rewardTier[i - 1]) *
                rewardMultiplier[i - 1];
            i++;
        }
        rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];

        uint256 usdtReward = (rewardAmount / DENOMINATOR) - claimedReward[_account];
        uint256 usdtleft = IERC20(usdt).balanceOf(address(this));

        return usdtReward > usdtleft ? usdtleft : usdtReward;
    }
```
