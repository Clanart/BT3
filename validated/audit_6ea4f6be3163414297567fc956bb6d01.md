### Title
Address association via `AssociateTx`/`associate` precompile lacks chain-ID/purpose domain separation, enabling forced-association signature replay - (File: `x/evm/types/ethtx/associate_tx.go`, `precompiles/addr/addr.go`, `app/ante/evm_checktx.go`)

### Summary
The CVE describes an authentication bypass where a captured OIDC `id_token` can be replayed because the verifier checks signature/`aud`/`iss` but never binds the token to a session-specific nonce. The analogous bug class in sei-chain is present in the Sei↔EVM address-association flow: both the `AssociateTx` type and the `associate` precompile method derive the caller's identity purely from an ECDSA signature over an arbitrary, attacker/user-supplied `customMessage` string, with **no chain-ID, nonce, or purpose binding** in the hashed payload (`crypto.Keccak256Hash([]byte(customMessage))`). This is the exact bug class the codebase itself documents and specifically fixed for EIP-7702 `SetCode` authorities (`AuthorityToPreAssociate` in `utils/helpers/address.go:143-188`), but the fix was not applied to the older `AssociateTx`/`associate()` signature-replay path.

### Finding Description
`HandleAssociateTx` (`app/ante/evm_checktx.go:182-204`) and the `associate` precompile method (`precompiles/addr/addr.go:160-203`, duplicated across `precompiles/addr/legacy/v*/addr.go`) both compute:
```go
customMessageHash := crypto.Keccak256Hash([]byte(atx.CustomMessage))
evmAddr, seiAddr, seiPubkey, err := helpers.GetAddresses(V, R, S, customMessageHash)
``` [1](#0-0) [2](#0-1) 

Unlike a Cosmos/EVM transaction signature (which is bound to a specific chain ID and nonce via `CheckAndDecodeSignature`, `app/ante/evm_checktx.go:206-238`) or a `SetCodeAuthorization` (which the codebase explicitly re-validates for chain ID before pre-association, per `AuthorityToPreAssociate` in `utils/helpers/address.go:143-188`), `CustomMessage` is an arbitrary string with **no domain separation whatsoever** — no chain ID, no nonce, no contract address, no expiry. Anyone who can obtain *any* signature the victim produced over that exact message format (e.g. a signature made for a different chain, a different dApp's "sign-in" flow, or Sei testnet) can submit it as a public EVM transaction (`AssociateTx`) or call the `associate` precompile directly (reachable by any unprivileged EVM caller — the precompile does not check `msg.sender` against the derived address) to force-associate the victim's Sei/EVM addresses on mainnet without their consent.

The codebase's own comment on the (correctly fixed) SetCode path spells out the consequence of exactly this bug class:
> "a publicly-visible authorization a user signed for another chain (e.g. Ethereum mainnet) could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their direct-cast balance and orphaning staking/distribution state ... which can then halt the chain via the distribution validator-removal hook." [3](#0-2) 

Both the `AssociateTx` and precompile `associate()` paths funnel into the same underlying `AssociateAddresses`/`MigrateBalance` machinery used by the SetCode path (`helpers.NewAssociationHelper(...).AssociateAddresses`), so a forced association via signature replay on this path carries the identical documented risk of balance migration and orphaned staking/distribution state, but with **none of the chain-ID/nonce checks** that were added to guard the SetCode path.

### Impact Explanation
A forced, non-consensual address association can:
- Migrate a victim's direct-cast EVM/Sei balance into the newly-associated account state without the victim's initiation (unauthorized state change / fund-location manipulation).
- Orphan staking/distribution positions held under the victim's prior direct-cast identity, which the codebase itself states "can halt the chain via the distribution validator-removal hook" — a validator-halt/chain-availability impact.
- Be executed by any unprivileged EVM caller who possesses a leaked signature+message pair produced by the victim for an unrelated purpose (no domain separation ties the signature to Sei mainnet, to the `associate` action, or to a specific nonce/session), directly paralleling the "nonce-less" OIDC token replay in the reference CVE.

### Likelihood Explanation
Medium-High. Exploitation requires the attacker to obtain a valid `(v, r, s, customMessage)` tuple signed by the victim. Because the message has no chain-ID/nonce binding, such signatures can leak from many unrelated contexts (other chains, dApp "sign-in with wallet" flows using an identical message template, Sei testnet, or an earlier legitimate association attempt) — all of which remain replayable indefinitely since there is no expiry or one-time-use nonce. The precompile is reachable by any transaction sender with no special privilege (`Associate` method, address `0x...1004`), and the `AssociateTx` path is directly reachable via the standard EVM ante pipeline.

### Recommendation
Apply the same protections used in `AuthorityToPreAssociate` to the `AssociateTx`/`associate()` signature-verification path:
- Bind the signed payload to the local chain ID (reject or require the message to encode the actual Sei chain ID).
- Include a per-account, monotonically increasing nonce (or a one-time association nonce stored in state) in the hashed message, invalidated after first use.
- Optionally bind the message to the precompile/action name and an expiry timestamp to prevent cross-purpose replay.

### Proof of Concept
1. Victim signs a personal message with the exact prefixed format used by association (`"\x19Ethereum Signed Message:\n32" + <32 zero bytes>`, as constructed in `x/evm/ante/preprocess_test.go:233-276`'s `TestPreprocessAssociateTx`) for an unrelated purpose (e.g., an off-chain login flow, or the same association flow performed on a different Sei network/testnet), producing `(v, r, s)`.
2. This tuple, together with the fixed `customMessage`, becomes publicly known (e.g. captured from a testnet explorer, a dApp log, or network traffic) since nothing in the signed data ties it to mainnet or a single use.
3. An attacker submits either:
   - An `AssociateTx` (`MsgEVMTransaction` wrapping `ethtx.AssociateTx{V, R, S, CustomMessage}`) via `EvmCheckTxAnte`/`EvmDeliverTxAnte`, or
   - A call to the `associate` precompile at `0x0000000000000000000000000000000000001004` with the same `(v, r, s, customMessage)`.
4. `HandleAssociateTx`/`associate()` recovers the victim's `evmAddr`/`seiAddr` from the replayed signature and, provided the victim's Sei account is not already associated, calls `AssociateAddresses`, force-linking the victim's addresses and triggering balance migration — without the victim ever intending or authorizing this action on Sei mainnet.

Note: I could not directly execute/verify the runtime behavior of `MigrateBalance`/the distribution validator-removal hook in this environment (index limits); the halt-on-orphaned-staking-state claim is taken directly from the codebase's own documented rationale for the analogous SetCode fix (`utils/helpers/address.go:149-155`) rather than independently reproduced here. A Devin session with full repo/test access would be needed to build and run an end-to-end PoC confirming the balance-migration and validator-halt consequences on the `AssociateTx`/precompile path specifically.

func HandleAssociateTx(ctx sdk.Context, ek *evmkeeper.Keeper, atx *ethtx.AssociateTx, readOnly bool) (sdk.Context, error) {
	V, R, S := atx.GetRawSignatureValues()
	V = new(big.Int).Add(V, utils.Big27)
	// Hash custom message passed in
	customMessageHash := crypto.Keccak256Hash([]byte(atx.CustomMessage))
	evmAddr, seiAddr, seiPubkey, err := helpers.GetAddresses(V, R, S, customMessageHash)
	if err != nil {
		return ctx, err
	}
	_, isAssociated := ek.GetEVMAddress(ctx, seiAddr)
	if isAssociated {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrInvalidRequest, "account already has association set")
	}
	if !IsAccountBalancePositive(ctx, ek, seiAddr, evmAddr) {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrInsufficientFunds, "account needs to have at least 1 wei to force association")
	}

func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)
```
