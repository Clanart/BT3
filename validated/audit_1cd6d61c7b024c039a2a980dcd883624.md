### Title
Unhandled exception in `Offer.from_spend_bundle` when parsing a malformed offer causes wallet-side spend-triggered processing failure - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.from_bech32` / `Offer.from_bytes` / `Offer.parse` all funnel untrusted, counterparty-supplied offer data into `Offer.from_spend_bundle()`, which walks the "dummy" CoinSpend solution to reconstruct `NotarizedPayment`s without validating the shape of the attacker-controlled CLVM data before indexing into it. [1](#0-0) 

### Finding Description
`Offer.from_spend_bundle` iterates the solution of each "dummy" coin spend (identified by `parent_coin_info == bytes32.zeros`, i.e. a value fully under the offer author's control) and does:
```python
for payment_group in Program.from_serialized(coin_spend.solution).as_iter():
    nonce = bytes32(payment_group.first().as_atom())
    payment_args_list = payment_group.rest().as_iter()
    notarized_payments.extend(
        [NotarizedPayment.from_condition_and_nonce(condition, nonce) for condition in payment_args_list]
    )
``` [2](#0-1) 

`payment_group.first().as_atom()` can legitimately return `None` (if `first()` resolves to a pair rather than an atom) or a byte string whose length is not 32. `bytes32(...)` requires exactly 32 bytes and raises `ValueError`/`TypeError` on mismatch; passing `None` raises `TypeError`. None of this is wrapped in a `try/except` in `from_spend_bundle`, unlike the sibling `conditions()` method just above it in the same class, which explicitly wraps the analogous parsing step in `try: ... except Exception: continue` because it anticipates malformed/adversarial CLVM content. [3](#0-2) 

This code path is reached purely by parsing an untrusted, attacker-crafted offer string/bytes — via `Offer.from_bech32` (offer files exchanged between trade counterparties, e.g. `.offer` files or bech32-encoded pastes), `Offer.from_bytes`, or `Offer.parse` (Streamable path) — with no need for the CLVM inside the dummy coin spend to be run or validated first. The malformed data only needs to structurally deserialize as a valid CLVM program (trivial to construct: e.g. a payment group whose first element is a pair `(() . ())` instead of an atom, or an atom whose length isn't 32 bytes). [4](#0-3) 

This mirrors the lol-html bug class: a structured-data parser that panics/raises unhandled exceptions on malformed-but-well-formed-enough input from an untrusted third party, rather than gracefully rejecting it.

### Impact Explanation
Any code path that accepts an offer file from an untrusted counterparty and calls `Offer.from_bech32`/`from_bytes` (offer summary display, offer validation before accept, CLI/RPC endpoints that parse offer strings prior to `take_offer`) will raise an unhandled `TypeError`/`ValueError` instead of returning a graceful validation failure. Depending on the calling context (RPC handler, CLI command, trade manager background task) this manifests as an unhandled exception surfacing to the caller — a spend/offer-triggered processing halt for that request, which matches the "spend-triggered transaction-processing halt" impact category. It is a wallet-side/local DoS against whoever attempts to inspect or validate a maliciously crafted offer, not a consensus/full-node crash, and does not enable fund theft or supply inflation by itself.

### Likelihood Explanation
High from the standpoint of ease of construction — no signature, valid puzzle execution, or spend is required; the attacker only needs to hand-craft the "dummy" coin spend's solution bytes (which are entirely attacker-controlled since these coins never actually exist on chain) so that `payment_group.first()` is a pair or a non-32-byte atom. Any user, wallet, or service that parses an incoming offer before deciding whether to accept it is exposed.

### Recommendation
Wrap the parsing loop in `Offer.from_spend_bundle` in the same defensive pattern already used in `Offer.conditions()` — catch parsing exceptions per dummy coin spend / per payment group and turn them into a graceful `ValidationError`/`ValueError` with a clear message (e.g. "Invalid offer: malformed notarized payment"), rather than letting `bytes32()`/`.as_atom()` exceptions propagate uncaught. Additionally validate that `payment_group.first()` is an atom of length 32 before constructing `bytes32(...)`.

### Proof of Concept
1. Construct a `WalletSpendBundle` containing one "dummy" `CoinSpend` with `coin.parent_coin_info == bytes32.zeros` (as produced by `Offer.to_spend_bundle`), and set `coin_spend.solution` to a CLVM program equivalent to:
```
(( (() . ()) . () ))
```
i.e. a list containing one payment group whose first element is a pair, not an atom (bypassing the "first().as_atom()" expectation), or alternatively an atom shorter than 32 bytes, e.g.:
```
((0xdead . ()))
```
2. Serialize this into a full offer using the standard `to_spend_bundle`/`compress`/`to_bech32` wrapping (or simply craft equivalent raw bytes matching the `Offer.__bytes__`/`from_bytes` format).
3. Call `Offer.from_bech32(offer_string)` (or `Offer.from_bytes`) on the resulting data.
4. Observe an unhandled `TypeError` (from `bytes32(None)`) or `ValueError` (from `bytes32()` with wrong length) raised out of `Offer.from_spend_bundle`, rather than a graceful rejection — crashing/erroring the calling code path (e.g., an RPC offer-summary or offer-validation call) that expected `Offer.from_bech32`/`from_bytes` to either succeed or raise a well-defined `ValidationError`.

*Note on confidence*: I was not able to trace every RPC/CLI call site that parses an incoming offer string down to confirm whether all of them wrap `Offer.from_bech32`/`from_bytes` in broad exception handling (some outer layers, e.g. RPC endpoint dispatch, may catch generic `Exception` and convert to an RPC error response, which would reduce this to a benign error rather than a true crash). Given index size limits, I could not fully inspect `chia/wallet/wallet_rpc_api.py`'s offer-related endpoints or CLI offer commands to verify whether they add their own try/except around this call. If a full audit of exception handling at every call site is required, a Devin session with full repository access would be needed to confirm the exact blast radius.
