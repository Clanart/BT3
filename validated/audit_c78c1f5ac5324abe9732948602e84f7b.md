### Title
Stale-state OAuth completion allows a crafted deep link to bind an attacker-influenced account to an unrelated, currently in-progress sign-in - (File: app/src/lib/stores/sign-in-store.ts)

### Summary
`SignInStore.resolveOAuthRequest` validates the OAuth CSRF `state` parameter only against the sign-in session that is live *when the deep link arrives*, then performs two `await`s (`requestOAuthToken`, `fetchUser`) against `this.state.endpoint` before finally invoking `this.state.oauthState.onAuthCompleted(account)` — but it re-reads `this.state` fresh after the awaits instead of using the session object it originally validated. If the store's `state` has been replaced by a *different* sign-in attempt in the meantime, the stale network result is delivered as if it belonged to the new session, without the new session's CSRF token ever being checked against it.

### Finding Description
`resolveOAuthRequest` is the handler invoked from the `x-github-client://oauth?...` deep link (`dispatchURLAction` → `_resolveOAuthRequest`), i.e., it is driven directly by a URL the user clicks, exactly the "link/deep link" attacker-control surface called out in the task. [1](#0-0) 

The relevant code: [2](#0-1) 

Walking through it:
1. It checks `this.state.kind === Authentication` and `this.state.oauthState.state === action.state` — a snapshot check of the *current* state at entry.
2. It captures only `endpoint` locally, not the whole `oauthState`/session object: `const { endpoint } = this.state`.
3. It then performs two asynchronous network round-trips: `requestOAuthToken(endpoint, action.code)` and `fetchUser(endpoint, token)`.
4. Only after both awaits complete does it call `this.state.oauthState.onAuthCompleted(account)` — reading `this.state` again, live, instead of the object validated in step 1.

Between steps 1 and 4 the user (or an attacker inducing user action, e.g. via a second crafted deep link, or the user simply starting a new sign-in while a previous flow is still pending) can start a brand-new sign-in flow. `authenticateWithBrowser` freely overwrites `this.state` with a new `Authentication` step containing a new `oauthState` (new CSRF `state`, new `resolve`/`reject` callbacks, new `endpoint`) without waiting for or cancelling any in-flight `resolveOAuthRequest` call: [3](#0-2) 

When the delayed `resolveOAuthRequest` call finally resolves, it calls `this.state.oauthState.onAuthCompleted(account)` on this *new* state — completing the *new* sign-in attempt with an account object that was actually derived from the *old* endpoint/token exchange, and the new session's CSRF `state` is never checked against the old request. The `.then()` handler inside `authenticateWithBrowser` only checks `this.state.kind === SignInStep.Authentication` (which is true, since that's precisely the new pending state) before calling `emitAuthenticate(account)` and transitioning to `Success` — it performs no additional verification that the resolved account actually corresponds to the session's own OAuth exchange: [4](#0-3) 

The broken invariant is identical in shape to the Basket bug: a permission/identity check ("is this the right session/state=T") is performed once at the top of a function, external calls happen in between, and the function's side effect at the end is applied against live, potentially-mutated state rather than the state that was actually validated.

### Impact Explanation
If exploited, a user's currently-pending sign-in (e.g., to github.com) can be silently completed with an `Account` object populated from data returned by a *different* endpoint — including a GitHub Enterprise host the user previously started (but didn't necessarily finish) authenticating against. Because `fetchUser` populates the `Account`'s `login`, `id`, `avatarURL`, `emails`, etc. straight from that endpoint's response, a malicious or compromised Enterprise endpoint the user once pointed Desktop at could supply attacker-chosen identity data that gets bound into the app as an authenticated account for a session the user believed was talking to a different, trusted host. This is exactly the "unauthorized OAuth or account binding" impact class called out as valid.

### Likelihood Explanation
Exploitation requires: (1) the user has a sign-in attempt in flight (browser opened, deep link not yet returned) and (2) a second, later-arriving OAuth deep link resolves against a *different*, now-current sign-in session before the first browser round-trip returns. This can be triggered by normal but slightly unusual user interaction (starting a second sign-in before finishing/cancelling the first) or by an attacker who can get the user to click/receive an additional `x-github-client://oauth?...` link while a legitimate flow is pending (browser tabs, previously cached callback pages, multiple accounts, GHE self-hosted flows are more plausible targets here). It does not require local/physical access, admin rights, prior malware, or leaked credentials — only a link click, matching the valid-impact bar. Likelihood is moderate: it depends on timing/overlap of two sign-in attempts, which is plausible but not trivially guaranteed on every run.

### Recommendation
Capture the specific `oauthState` object (not just `endpoint`) at the top of `resolveOAuthRequest`, and after the awaits, re-validate that `this.state` is still the *same* session (e.g., compare `this.state.oauthState === capturedOauthState`, or re-check `this.state.oauthState?.state === action.state`) before invoking `onAuthCompleted`/`onAuthError`. If the session has changed, drop the stale result instead of applying it to whatever session happens to be current.

### Proof of Concept
Conceptual sequence (cannot be executed here, described from the code paths cited above):
1. User clicks "Sign in" for a GitHub Enterprise instance controlled by an attacker (or already compromised); Desktop enters `Authentication` step with `oauthState = { state: T1, endpoint: EVIL }`.
2. Attacker's OAuth authorize endpoint redirects to `x-github-client://oauth?state=T1&code=C1` but the desktop app is slow to process it (e.g., artificial delay from the malicious server, or the user simply doesn't finish the flow).
3. Before `resolveOAuthRequest` finishes network exchange for `T1`, the user starts a fresh, legitimate sign-in to `github.com`; `authenticateWithBrowser` overwrites `this.state` with `oauthState = { state: T2, endpoint: github.com }`.
4. The delayed handling of the `T1` deep link resumes: `requestOAuthToken(EVIL, C1)` and `fetchUser(EVIL, token)` succeed (attacker fully controls `EVIL`, so both calls return whatever account data the attacker wants).
5. `resolveOAuthRequest` calls `this.state.oauthState.onAuthCompleted(account)` — but `this.state` is now the `T2` (github.com) session. The github.com sign-in flow completes with the attacker-supplied account object, without `T1` ever being checked against `T2`. [2](#0-1) [5](#0-4)

    const currentState = this.state

    if (
      currentState?.kind !== SignInStep.Authentication &&
      currentState?.kind !== SignInStep.ExistingAccountWarning
    ) {
      const stepText = currentState ? currentState.kind : 'null'
      return fatalError(
        `Sign in step '${stepText}' not compatible with browser authentication`
      )
    }

    this.setState({ ...currentState, loading: true })

    if (currentState.kind === SignInStep.ExistingAccountWarning) {
      const { existingAccount } = currentState
      // Try to avoid emitting an error out of AccountsStore if the account
      // is already gone.
      if (this.accounts.find(x => x.endpoint === existingAccount.endpoint)) {
        await this.accountStore.removeAccount(existingAccount)
      }
    }

    const csrfToken = crypto.randomUUID()

    new Promise<Account>((resolve, reject) => {
      const { endpoint, resultCallback } = currentState
      log.info('[SignInStore] initializing OAuth flow')
      this.setState({
        kind: SignInStep.Authentication,
        endpoint,
        resultCallback,
        error: null,
        loading: true,
        oauthState: {
          state: csrfToken,
          endpoint,
          onAuthCompleted: resolve,
          onAuthError: reject,
        },
      })
      shell.openExternal(getOAuthAuthorizationURL(endpoint, csrfToken))
    })
      .then(account => {
        if (!this.state || this.state.kind !== SignInStep.Authentication) {
          // Looks like the sign in flow has been aborted
          log.warn('[SignInStore] account resolved but session has changed')
          return
        }

        log.info('[SignInStore] account resolved')
        this.emitAuthenticate(account)
        this.setState({
          kind: SignInStep.Success,
          resultCallback: this.state.resultCallback,
        })
      })
      .catch(e => {
        // Make sure we're still in the same sign in session
        if (
          this.state?.kind === SignInStep.Authentication &&
          this.state.oauthState?.state === csrfToken
        ) {
          log.info('[SignInStore] error with OAuth flow', e)
          this.setState({ ...this.state, error: e, loading: false })
        } else {
          log.info(`[SignInStore] OAuth error but session has changed: ${e}`)
        }
      })

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }
