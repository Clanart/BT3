## Title
Unsafe unchecked ERC20 `transfer()` used for user reward payouts causes permanent loss of unclaimed reward accounting - (File: `wombat/ArbWomUp.sol`, `wombat/ArbWomUp2.sol`)

### Summary
`ArbWomUp.sol` and `ArbWomUp2.sol` both import and use OpenZeppelin's `SafeERC20` for token movements from the user into the contract (`safeTransferFrom`, `safeApprove`), but the reward payout leg of `incentiveDeposit()` — the path that sends value back to an ordinary caller — uses a raw, unchecked `IERC20.transfer()` call instead of `safeTransfer`. This is the exact bug class described in the external report (TRST-M-4): using the raw ERC20 interface transfer instead of the safe wrapper, so a token that returns `false` (rather than reverting) on failure will not cause the transaction to revert.

### Finding Description
In `ArbWomUp.sol`: [1](#0-0) 
`incentiveDeposit()` first performs `_deposit()` (which correctly uses `safeTransferFrom` for pulling WOM from the user), then increments `claimedReward[msg.sender]`, and finally attempts to pay the caller with `IERC20(usdt).transfer(msg.sender, rewardToSend)` — the return value of `transfer()` is never checked.

The same pattern exists in `ArbWomUp2.sol`: [2](#0-1) 
where the BUSD reward payout `IERC20(busd).transfer(msg.sender, rewardToSend)` is also unchecked, while `_deposit()` and `_bullMGP()` in the very same contract correctly use `safeTransferFrom`/`safeApprove`.

Both contracts already import `SafeERC20` and apply `using SafeERC20 for IERC20;`, showing the developers were aware of the safe-transfer pattern but did not apply it consistently to the user-facing reward payout call. If the configured reward token (`usdt`/`busd`) is one that returns `false` on failure instead of reverting (e.g. insufficient balance/allowance edge cases, blacklist checks, or any non-fully-compliant ERC20), the `transfer()` call will silently fail while `claimedReward[msg.sender]` has already been permanently incremented in state.

### Impact Explanation
Because `claimedReward[account]` is updated unconditionally before/without confirming that `transfer()` succeeded, a failed-but-silent transfer permanently records the user as having received their reward even though no funds were actually moved. Since `getRewardAmount()` computes the remaining reward as `(rewardAmount / DENOMINATOR) - claimedReward[_account]`, this permanently and irrecoverably reduces (or zeroes) the reward the user can ever claim, resulting in permanent freezing/loss of that unclaimed yield with no on-chain remediation path available to the ordinary user.

### Likelihood Explanation
Likelihood is dependent on the specific token contract configured as `usdt`/`busd` at deployment exhibiting non-reverting-false-return behavior under some condition (e.g., transfer to a blacklisted/paused account, or any implementation that returns `false` instead of reverting). This is a known real-world ERC20 behavior class (the same class flagged in the original report), so it is plausible for any token that isn't a fully OpenZeppelin-standard ERC20 with strict revert semantics.

### Recommendation
Replace the raw `IERC20(usdt).transfer(...)` and `IERC20(busd).transfer(...)` calls in `incentiveDeposit()` with `safeTransfer` from the already-imported `SafeERC20` library, consistent with the rest of the codebase's token-handling calls, so that any failed transfer causes the whole transaction (including the `claimedReward` update) to revert.

### Proof of Concept
1. Deploy `ArbWomUp` with a reward token whose `transfer()` returns `false` on failure instead of reverting (e.g., a token that returns `false` when the contract's balance is momentarily insufficient due to a race, or a non-standard token with silent-failure semantics).
2. A user calls `incentiveDeposit(amount)`; `_deposit()` succeeds (pulls WOM via `safeTransferFrom`), `claimedReward[msg.sender]` is incremented by `rewardToSend`.
3. `IERC20(usdt).transfer(msg.sender, rewardToSend)` returns `false` silently; no revert occurs, `USDTRewarded` event is still emitted.
4. The user's WOM has been deposited and accounted, but no USDT reward was received; because `claimedReward[msg.sender]` already reflects the full reward, subsequent calls to `getRewardAmount()` will not re-issue the missed reward — the yield is permanently lost. [3](#0-2) [4](#0-3)

    function incentiveDeposit(
        uint256 _amount, uint256 _minMGPRec, bool _bullMode
    ) external _checkAmount(_amount) whenNotPaused nonReentrant {
        if (_amount == 0) return;

        uint256 rewardToSend = this.getRewardAmount(_amount, msg.sender);
        _deposit(_amount);
        claimedReward[msg.sender] += rewardToSend;
        
        if (_bullMode) {
            _bullMGP(rewardToSend, _minMGPRec, msg.sender);
        } else {
            IERC20(busd).transfer(msg.sender, rewardToSend);
            emit BUSDRewarded(msg.sender, rewardToSend);
        }
    }
