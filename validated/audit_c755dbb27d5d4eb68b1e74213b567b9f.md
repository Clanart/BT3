### Title
Deserialized `ThresholdKeys` with identity verification shares produce an identity group key and panic during signature completion — ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` in `crypto/dkg` deserializes `verification_shares` via `Ciphersuite::read_G`, which rejects only non-canonical encodings — not the identity point. `Curve::read_G` (the stricter FROST reader) explicitly rejects identity, but it is not used here. A crafted `ThresholdKeys` serialization whose verification shares interpolate to the point at infinity yields `group_key() == identity`. When such keys are used in the Bitcoin `Schnorr` algorithm, `AlgorithmSignatureMachine::complete` calls `algorithm.verify(group_key, ...)`, which is documented to panic when the group key is the point at infinity — a reachable denial-of-service analogous to CVE-2025-53062 (authenticated-crafted input → full crash/hang of the service).

### Finding Description
`ThresholdKeys::read` reads `n` verification shares with `<C as Ciphersuite>::read_G`:

```rust
// crypto/dkg/src/lib.rs:620-623
let mut verification_shares = HashMap::new();
for l in (1 ..= n).map(Participant) {
  verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
}
```

`Ciphersuite::read_G` only enforces canonical encoding (crypto/ciphersuite/src/lib.rs:91-100). By contrast, `Curve::read_G` rejects identity explicitly (crypto/frost/src/curve/mod.rs:125-131), but `ThresholdKeys::read` never calls it, and `ThresholdKeys::new` performs no identity check on `verification_shares` or on the resulting `group_key` (crypto/dkg/src/lib.rs:376-378).

The interpolated group key is:

```rust
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

With `Interpolation::Constant` (deserialization tag `0`), the attacker fully controls both the coefficient vector (`n` scalars) and the `n` verification-share points. Setting every verification share to the canonical encoding of the identity element yields `group_key == identity` regardless of the coefficients. `ThresholdParams::new` is satisfied with any `t <= n`, `1 <= i <= n`.

Downstream, `AlgorithmSignatureMachine::complete` calls `self.params.algorithm.verify(self.view.group_key(), &self.Rs, sum)` (crypto/frost/src/sign.rs:465). The Bitcoin `Schnorr` algorithm wrapper is explicitly documented:

```rust
// networks/bitcoin/src/crypto.rs:76-83
/// This may panic if called with nonces/a group key which are the point at infinity ...
```

`verify` computes `needs_negation(&sig.R)` on the completed signature whose group key/aggregated nonce can be the point at infinity, and for secp256k1 there is no SEC1 x-only encoding for the identity — the parity/x-coordinate access panics. The same panic boundary exists for the nonce sums: although per-commitment points are read through `Curve::read_G` (rejecting identity), a participant's *bound* contribution `D + rho·E` is a sum of two accepted non-identity points and the aggregated `Rs` are never re-checked for identity before `verify` consumes them.

### Impact Explanation
A single crafted `ThresholdKeys` blob (or crafted preprocess set driving an aggregate nonce to infinity) causes a deterministic panic inside `complete()` — aborting the signing process / crashing the node mid-operation. This is an availability-only compromise, matching the CVE bug class: well-formed-but-malicious input reaching a panic path that honest flows never hit, with no key disclosure required.

### Likelihood Explanation
- The `ThresholdKeys::read` path is deterministic: an attacker supplying a serialized key file (restored key material, imported shares, or any deployment feeding `ThresholdKeys::read` untrusted/peer-derived bytes) needs no brute force — all-identity shares are trivially constructible.
- The preprocess path (driving `Rs[n][g]` to identity) is harder: `rho` binds to the attacker's own commitments, so constructing `D + rho·E = identity` requires solving a hash fixpoint and is not practical. The realistic trigger is the serialized-keys path.
- Per the rules this is rated Medium: reachable panic, but it requires the crafted-keys input surface rather than an ordinary network message.

### Recommendation
1. In `ThresholdKeys::read` (and `ThresholdKeys::new`), reject identity verification shares — or at minimum reject an identity `group_key` after interpolation (crypto/dkg/src/lib.rs:376-390).
2. In `networks/bitcoin/src/crypto.rs` `Schnorr::verify`, return `None` when `group_key` or `nonces[0][0]` is identity instead of relying on "may panic" behavior.
3. In `BindingFactor::nonces` / `AlgorithmSignatureMachine::complete`, treat an identity aggregate nonce as an invalid preprocess (blame the participant whose bound contribution is identity, or fail verification cleanly) rather than letting the algorithm hit the panic edge case (crypto/frost/src/nonce.rs:194-212, crypto/frost/src/sign.rs:465).

### Proof of Concept
```rust
use std::io;
use frost::{
  curve::Secp256k1,
  ThresholdKeys,
};
use ciphersuite::{Ciphersuite, group::{Group, GroupEncoding, ff::PrimeField}};

// Craft a ThresholdKeys<Secp256k1> blob with all-identity verification shares.
fn malicious_keys_blob() -> Vec<u8> {
    let mut buf = vec![];
    // C::ID length + ID
    buf.extend(u32::try_from(Secp256k1::ID.len()).unwrap().to_le_bytes());
    buf.extend(Secp256k1::ID);
    // t = 2, n = 2, i = 1
    buf.extend(2u16.to_le_bytes());
    buf.extend(2u16.to_le_bytes());
    buf.extend(1u16.to_le_bytes());
    // Interpolation::Constant with n scalars (any values)
    buf.push(0);
    buf.extend(<Secp256k1 as Ciphersuite>::F::ONE.to_repr().as_ref());
    buf.extend(<Secp256k1 as Ciphersuite>::F::ONE.to_repr().as_ref());
    // secret_share
    buf.extend(<Secp256k1 as Ciphersuite>::F::ONE.to_repr().as_ref());
    // n identity verification shares — canonical encodings, so Ciphersuite::read_G accepts them
    for _ in 0 .. 2 {
        buf.extend(<Secp256k1 as Ciphersuite>::G::identity().to_bytes().as_ref());
    }
    buf
}

// Succeeds — no identity rejection — and yields group_key() == identity.
let keys = ThresholdKeys::<Secp256k1>::read(&mut malicious_keys_blob().as_slice()).unwrap();
assert!(bool::from(keys.group_key().is_identity()));

// Using these keys in a SignableTransaction::multisig -> AlgorithmSignatureMachine::complete
// reaches bitcoin_serai's Schnorr::verify with an identity group key / aggregate nonce,
// hitting the documented panic on the point at infinity.
```
