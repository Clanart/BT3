### Title
Conflict resolution reassembly splices AI-generated hunk content by positional index, not by a stable hunk identity, allowing an attacker-controlled merge conflict to cause silent misplacement of resolved code - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
Desktop's Copilot conflict-resolution feature extracts conflict hunks from a file once (to build the model prompt and to validate the model's response), then independently re-scans the same file a second time to splice the model's per-hunk resolutions back in. Both scans are driven purely by a positional counter (`i` / `hunkIndex`), with no shared, stable identity tying a resolution to the specific marker block it was generated for — exactly the "wrong index" pattern in the source report, where `claimed[_tokenId][claimableIndex]` was updated using `amounts[i]` instead of `amounts[claimableIndex]`.

### Finding Description
`buildConflictContext` reads the conflicted file from disk and calls `extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) to produce the ordered list of hunks that gets sent to the model and used to validate the response (`validateResolutionPaths`, `app/src/lib/copilot-conflict-resolution.ts:473-521`, which just compares `resolution.hunks.length` to `expectedHunkCounts`).

Later, `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) re-parses the *same raw file content* from scratch, using its own, separately defined marker regexes (`reassemblyOursMarker`, `reassemblySeparatorMarker`, `reassemblyTheirsMarker`, lines 524-526) that are distinct objects from the ones used inside `extractConflictHunks`. It walks the file, and for every well-formed `<<<<<<< … ======= … >>>>>>>` block it finds, it splices in `hunkResolutions[hunkIndex]` — purely by incrementing counter, per the function's own doc comment: "matched by order, not by line number" (line 535-536).

This is a correctness invariant that depends on the two independent scans agreeing, block-for-block, on:
- how many conflict blocks exist,
- which blocks are "well-formed" vs. skipped/malformed,
- the order in which they appear.

`extractConflictHunks` silently drops any block whose closing `>>>>>>>` is never found (`app/src/lib/copilot-conflict-context.ts:240-242`, confirmed by the test "skips a malformed hunk with no closing marker" at `app/test/unit/copilot-conflict-context-test.ts:346-357`, which asserts a 0-hunk result for the whole file). `reassembleResolvedFile` has its *own*, separately coded notion of "malformed" (missing separator or closing marker) that copies the offending `<<<<<<<` line through as ordinary content and continues scanning (lines 559-579). Because these are two independently maintained implementations rather than a single source of truth, any file whose marker layout is at the edge of what one parser accepts and the other rejects — nested/duplicated marker lines, marker lines with trailing text, mixed CRLF, or multiple adjacent hunks where only one is malformed — can cause the two functions to disagree on the hunk count or ordering for the *same file*.

When they disagree, `reassembleResolvedFile` will still happily consume `hunkResolutions[hunkIndex]` for whichever conflict block it encounters at that position, splicing content generated for conflict N into the file at the location of conflict M.

### Impact Explanation
The content of a conflicted file is derived directly from a remote branch, PR, or commit that an attacker controls (this feature runs during merge/rebase/cherry-pick against attacker-influenced refs). If the attacker crafts conflict-marker text that trips this extraction/reassembly mismatch, Desktop will silently write AI-resolved content for the wrong conflict block into the file that becomes the final "resolved" version the user reviews and commits. This is a silent-corruption-of-what-the-user-commits scenario: the diff the user sees in the resulting commit does not correspond to the resolution the model actually reasoned about and displayed reasoning for, and could reintroduce vulnerable/malicious code, drop a security-relevant fix, or splice attacker-supplied text into an unrelated code region without any warning, since nothing besides a hunk-count equality check (`validateResolutionPaths`) guards this path, and that check operates on the same (potentially wrong) hunk count from `extractConflictHunks`.

### Likelihood Explanation
The likelihood is moderate: it does not require any local access, admin rights, or user missteps — only that the user resolve a conflict (a common workflow) against a repository/branch that includes attacker-crafted content with edge-case conflict-marker formatting. It requires finding one of the parser divergence cases (unverified whether such a concrete byte-for-byte divergence exists without deeper regex analysis of `oursMarker`/`baseMarker`/`separatorMarker`/`theirsMarker` in `copilot-conflict-context.ts`, which were not fully retrievable from this repository's index), so this is presented as a structural design flaw (duplicated independent parsers correlated by positional index, matching the exact "wrong index" bug class from the report) rather than a proven exploit with a fully reproduced payload.

### Recommendation
Do not use two independently implemented marker scanners correlated by a bare positional counter. Have `extractConflictHunks` return the exact line ranges (`markerStart`, `hunkEnd`) of each accepted hunk, and have `reassembleResolvedFile` consume that same list of ranges (rather than re-scanning and re-deciding well-formedness) to guarantee that resolution `i` is spliced into precisely the block that produced context/hunk `i`. Additionally, `validateResolutionPaths` should be strengthened to fail closed (throw) if the reassembly pass ever finds a different number of well-formed blocks than `extractConflictHunks` did for the same file, rather than trusting a single length check performed before reassembly.

### Proof of Concept
This is a design-level PoC based on local code inspection, since a concrete divergent payload between the two regex sets could not be fully derived from the available index:
1. Attacker pushes/prepares a branch that, when merged, produces a conflicted file containing two conflict blocks, where the first block is malformed in a way `extractConflictHunks` discards (e.g., no closing `>>>>>>>` before EOF-like content, per `app/src/lib/copilot-conflict-context.ts:240-242`) but that `reassembleResolvedFile`'s independent scan (`app/src/lib/copilot-conflict-resolution.ts:559-579`) treats differently (e.g., considers it well-formed due to different regex boundaries, or treats a different block as malformed).
2. `buildConflictContext` reports 1 hunk to the model; the model returns 1 resolution matching `validateResolutionPaths`' count check.
3. `reassembleResolvedFile` walks the file and encounters 2 well-formed-looking blocks in its own logic, consuming the single model resolution (`hunkResolutions[0]`) for whichever block it reaches first — which may not be the block the model actually reasoned about — while leaving the second block's original conflict-marker text in place or replacing the wrong region.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

/**
 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *
 * A `<<<<<<<` line that is not followed by both a `=======` separator and
 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved
 */
export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
