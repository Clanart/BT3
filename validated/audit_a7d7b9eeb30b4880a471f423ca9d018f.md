### Title
Missing `--` end-of-options separator allows argument injection via attacker-controlled fork clone URL in `addRemote`/`setRemoteURL` - (File: `app/src/lib/git/remote.ts`)

### Summary
The reported Comet bug is a missing-authorization-check class of flaw: an attacker-facing entry point performs a privileged/state-mutating operation without validating who/what is allowed to trigger it. The closest reachable analog in this GitHub Desktop codebase is not an auth check but an equivalent "missing guard before passing untrusted data to a privileged sink" pattern: `addRemote()` and `setRemoteURL()` in [1](#0-0)  build `git remote add`/`git remote set-url` argument arrays and pass an externally-derived `url` value as a bare positional argument, with no `--` end-of-options marker separating it from `git`'s option parser and no scheme/character validation.

### Finding Description
Compare this to `clone()` in the same directory, which explicitly guards against unsafe input: it checks `isClonePathSensitive` and terminates the option list with `--` before the URL/path: `args.push('--', url, path)` [2](#0-1) . The `checkout` code path in `app/src/lib/git/checkout.ts` follows the same defensive pattern, always appending `'--'` after the ref argument list [3](#0-2) .

`addRemote` and `setRemoteURL`, however, do not follow this pattern:
```
await git(['remote', 'add', name, url], repository.path, 'addRemote')
...
await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
``` [1](#0-0) 

These functions are invoked with values that ultimately originate from a GitHub API response object (`pull_request.head.repo.clone_url`) when a user views/checks out a pull request from a fork — an object an attacker can influence by opening a PR from a repository they control:
- `openPullRequestFromUrl` passes `pullRequest.head.repo.clone_url` straight through to `_checkoutPullRequest` [4](#0-3) .
- `_findPullRequestBranch` calls `addRemote(repository, forkRemoteName, headCloneUrl)` with that value when no matching remote exists [5](#0-4) .
- `updateRemoteUrl` similarly feeds `apiRepo.clone_url` into `gitStore.setRemoteURL(...)` [6](#0-5) .

None of `urlMatchesRemote` [7](#0-6) , `parseRemote` [8](#0-7) , or the call sites reject a value that fails to parse as a URL and instead pass it through raw to `git remote add`. Because there is no `--` separator, a value beginning with `-` (e.g., `--upload-pack=...`, or other option-like git remote/url flags) would be interpreted by git's argument parser as an option rather than a literal URL string — the classic "leading dash" argument-injection primitive that the `clone()`/`checkout()` code paths were explicitly hardened against (see the `isClonePathSensitive` comment referencing "a crafted URL tricks the UI ... path traversal" as the reason for the equivalent hardening in `clone.ts` [9](#0-8) ). `remote.ts` has no equivalent hardening or test coverage for such values, unlike `clone-path-safety-test.ts`, which specifically exercises traversal/crafted-URL payloads for the clone path [10](#0-9) .

### Impact Explanation
If exploitable, this would let an attacker who controls a forked/cross-origin repository's PR metadata inject git command-line options into `remote add`/`remote set-url` executed against the victim's local repository, potentially altering remote configuration in unexpected ways (e.g., using `--tags`/`--mirror`-style abuses of the `remote add` option surface, or corrupting the remote's on-disk representation) without any explicit user confirmation of the raw string, silently affecting what remote the victim's Desktop client considers "origin" and will later fetch from or push to.

### Likelihood Explanation
This is **not confirmed exploitable** with the evidence available: GitHub's own API server generates `clone_url` for repositories, and repository/owner names are constrained by GitHub's own naming rules (no leading `-`, restricted charset), which likely prevents a value that git's parser would treat as an option flag from ever reaching this code path via github.com. I could not verify whether GitHub Enterprise Server instances enforce the same naming restrictions, and I have no evidence in this codebase of an independent allow-list check on `clone_url`/`headCloneUrl` before it reaches `addRemote`/`setRemoteURL`. Without confirming that GHES (or another attacker-reachable API source) can produce a repo name/clone URL that is or starts with a dash, this remains a defense-in-depth gap rather than a demonstrated end-to-end vulnerability.

### Recommendation
Add the same defensive pattern already used in `clone.ts` and `checkout.ts` to `app/src/lib/git/remote.ts`: terminate `git remote add`/`git remote set-url` invocations with `--` before the URL argument, and/or reject URLs that do not parse as a well-formed remote (via `parseRemote`) or that begin with `-` before ever reaching `git()`.

### Proof of Concept
Not independently reproducible from local code alone — reproducing this would require confirming that a PR's `head.repo.clone_url` (or `IAPIRepository.clone_url` more generally) can be made to start with `-` on a real or Enterprise GitHub instance, which is outside what can be verified from the client codebase in this index. Given this residual uncertainty, treat this as a hardening gap flagged by comparison to the mitigations already present in sibling functions (`clone()`, `checkoutBranch()`) rather than a fully proven exploit chain.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

const remoteRegexes: ReadonlyArray<{ protocol: GitProtocol; regex: RegExp }> = [
  {
    protocol: 'https',
    regex: new RegExp(
      '^https?://(?:.+@)?(.+)/([^/]+)/([^/]+?)(?:/|\\.git/?)?$'
    ),
  },
  {
    protocol: 'ssh',
    regex: new RegExp('^git@(.+):([^/]+)/([^/]+?)(?:/|\\.git)?$'),
  },
  {
    protocol: 'ssh',
    regex: new RegExp(
      '^(?:.+)@(.+\\.ghe\\.com):([^/]+)/([^/]+?)(?:/|\\.git)?$'
    ),
  },
  {
    protocol: 'ssh',
    regex: new RegExp('^git:(.+)/([^/]+)/([^/]+?)(?:/|\\.git)?$'),
  },
  {
    protocol: 'ssh',
    regex: new RegExp('^ssh://git@(.+)/(.+)/(.+?)(?:/|\\.git)?$'),
  },
]

/** Parse the remote information from URL. */
export function parseRemote(url: string): IGitRemoteURL | null {
  for (const { protocol, regex } of remoteRegexes) {
    const match = regex.exec(url)
    if (match !== null && match.length >= 4) {
      return { protocol, hostname: match[1], owner: match[2], name: match[3] }
    }
  }

  return null
}
