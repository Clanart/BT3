Confirmed: `_orders` is `mapping(bytes32 commitment => mapping(address token => uint256 amount))` [1](#0-0) , keyed only by token address, not by the output-leg index. This means if an `Order.inputs` array contains two entries with the same token address (a legal, unvalidated configuration — nothing in `placeOrder`/`_fillSameChain` rejects duplicate input tokens), the per-leg escrow amounts are pooled into a single counter, breaking the pro-rata release invariant that `_fillSameChain` assumes.

### Title
Duplicate-token input legs let a solver drain another leg's escrow via a single-leg full-fill in `IntrinsicIntents._fillSameChain` - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_fillSameChain` releases escrow per output leg by indexing `order.inputs[i]`, but the actual escrow ledger `_orders[commitment][token]` is keyed by token address only, summed across all legs sharing that token. When leg `i` reaches full completion (`amountFilled == totalRequired`), the code releases `_orders[commitment][token]` in its entirety [2](#0-1)  rather than the amount escrowed for that specific leg — silently assuming a 1:1, non-overlapping mapping between input token and output leg that the data structures do not enforce.

### Finding Description
`_orders` is a flat `(commitment, token) -> amount` map [1](#0-0) . Nothing in `placeOrder`, `_fillSameChain`, or `_cancelSameChain` requires `order.inputs[i].token` to be unique across `i`. If a user's order (or a maliciously crafted one on their own behalf, or one crafted by a solver colluding with order construction, e.g. via `predispatch` calldata that produces two separate input legs of the same ERC-20) contains two input legs backed by the same token — for example `inputs[0].token == inputs[1].token == USDC`, each escrowing 100 USDC (200 USDC total in `_orders[commitment][USDC]`) against two different, independent output legs — then a solver who fully fills only `output[0]` (paying the required amount for leg 0) hits the `amountFilled == totalRequired` branch and is paid `escrowedAmount = _orders[commitment][USDC]` (the full 200 USDC pooled balance, i.e. leg 0's *and* leg 1's escrow), not the 100 USDC actually attributable to leg 0 [3](#0-2) .

`_withdraw` then blindly decrements `_orders[commitment][token] -= amount` [4](#0-3)  and transfers the full pooled amount to the solver's beneficiary. `isFullyFilled` remains `false` because leg 1's `totalRequired > amountFilled` still holds [5](#0-4) , so the order stays open as a `PartialFill`, but its backing escrow for the still-open leg (leg 1) has already been drained to zero. When a second solver later attempts to complete leg 1, `_withdraw`'s guard `if (escrowed == 0) revert UnknownOrder()` fires [6](#0-5) , permanently freezing that leg: the user can never be made whole, the order can never fully complete, and the second output cannot be delivered even though its output tokens are transferred by the second solver — a fund-loss and stuck-order primitive directly analogous to the Starknet report's core theme: a completion/zero-balance boundary condition that the code's guard rails do not anticipate, leaving state that cannot progress toward safe termination.

This exactly mirrors the external report's broken invariant — code assumes a coupling between two independently-tracked quantities (there: `TR` and position solvency; here: per-leg output progress and pooled per-token escrow) that does not hold once a boundary/degenerate input is reached (there: `TR == 0` after full liquidation; here: two legs sharing one token address), and the mismatch either wrongly blocks legitimate completion (there) or wrongly over-releases escrow while blocking legitimate completion of the other leg (here).

### Impact Explanation
An unprivileged solver (the ordinary, permissionless entry point to `fillOrder`/`_fillSameChain`) can, on an order with duplicate input token legs, extract escrow belonging to a leg they never paid for, receiving more input tokens than they delivered outputs for. The order's original user loses the difference (their escrow is drained without receiving the corresponding output), and the order becomes permanently stuck in a `PartialFill` state that cannot be completed (`UnknownOrder` revert on the remaining leg) nor cleanly refunded for the drained portion, since `_cancelSameChain` also only sees per-token totals in `_orders` [7](#0-6)  and cannot distinguish which leg the remaining balance belongs to. This is a direct loss/lock of user funds through the gateway's own public fill entrypoint — matching the bounty's "stealing or loss of funds" / "logic attacks" impact categories.

### Likelihood Explanation
Requires only that an `Order` be constructed with two or more `inputs[]` entries sharing the same `token` address, paired with independent output legs — nothing in `placeOrder` or `IntentGatewayV2.fillOrder` validates input-token uniqueness across legs [8](#0-7) . Any user (accidentally, via a naive order-building client, or an attacker targeting their own subsequently-resold order / a griefing solver targeting a victim's multi-leg order) can create this condition; a solver simply calls the standard public `fillOrder` on one leg. No relayer, prover, or governance actor is involved.

### Recommendation
Track escrow per `(commitment, outputIndex)` rather than per `(commitment, token)`, or explicitly reject orders whose `inputs[]` contain duplicate token addresses at `placeOrder` time. Alternatively, change the full-fill release path in `_fillSameChain` to always release the leg-specific pro-rata amount (`order.inputs[i].amount * fillAmount / totalRequired`, capped by remaining escrow) instead of reading `_orders[commitment][token]` in full whenever `amountFilled == totalRequired`.

### Proof of Concept
1. Construct `Order` with `inputs = [{token: USDC, amount: 100e6}, {token: USDC, amount: 100e6}]` and two independent output legs (e.g., two different output tokens or beneficiaries), each requiring the solver to pay the counter-party.
2. `placeOrder` escrows `200e6 USDC` total into `_orders[commitment][USDC]`.
3. Solver A calls `fillOrder` providing only `outputs[0]` at the exact `totalRequired` for leg 0; `amountFilled == totalRequired` triggers, and `escrowedAmount = _orders[commitment][USDC] == 200e6`, all released to Solver A despite leg 0 only being backed by 100e6.
4. `isFullyFilled` is `false` (leg 1 untouched), so the order remains open with `_partialFills` recording leg 1 as unfilled, but `_orders[commitment][USDC]` is now `0`.
5. Solver B attempts to fill leg 1 correctly, providing the required output; `_withdraw` reverts with `UnknownOrder()` since `escrowed == 0` [6](#0-5) , permanently blocking completion of leg 1 and leaving the user's escrow drained without full order settlement.

Note: I could not exhaustively confirm whether any off-chain SDK order-construction path (`placeOrder` helpers in `sdk/packages/sdk`) implicitly deduplicates input tokens before submission — the on-chain contracts themselves impose no such restriction, which is the root of the issue. A Devin session with full repo access could grep the SDK's order-building code to confirm whether this can only be reached via a bespoke/malformed transaction or is also reachable through the standard client SDK flow.
