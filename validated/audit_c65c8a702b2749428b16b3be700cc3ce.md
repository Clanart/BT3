## Title
Fail-open exception handling in hookify's `evaluate_rules`/`_rule_matches` lets a single malicious rule file silently disable all other `block` rules for that hook invocation - (File: `plugins/hookify/hooks/pretooluse.py`)

## Summary
`pretooluse.py`'s `main()` wraps rule evaluation in a blanket `except Exception` plus `finally: sys.exit(0)`, so any uncaught exception raised while evaluating a *single* rule aborts the whole batch evaluation and causes the tool call to be allowed. `RuleEngine.evaluate_rules`/`_rule_matches` has no per-rule isolation, so one attacker-controlled rule (e.g. via a boolean `tool_matcher` value) can throw an `AttributeError` that discards the results for every other rule being checked in that same call, including the user's legitimate `block` rules.

## Finding Description
`load_rules()` in `plugins/hookify/core/config_loader.py` does isolate parse/load errors per file [1](#0-0) , so a malformed file that fails to *load* is simply skipped and does not affect other rules. However, once rules are loaded into `Rule` objects, `RuleEngine.evaluate_rules` iterates over **all** rules in a single unprotected loop with no per-rule try/except: [2](#0-1) 

`_rule_matches` calls `_matches_tool(rule.tool_matcher, tool_name)` when `rule.tool_matcher` is truthy: [3](#0-2) 

`_matches_tool` unconditionally calls `.split('|')` on the matcher value: [4](#0-3) 

The custom, hand-rolled YAML parser in `extract_frontmatter` coerces *any* scalar frontmatter value of `"true"`/`"false"` into a Python `bool`, with no type restriction to specific keys like `enabled`: [5](#0-4) 

`Rule.from_dict` passes `frontmatter.get('tool_matcher')` straight into the `Rule.tool_matcher` field with no validation: [6](#0-5) 

So an attacker who plants `.claude/hookify.malicious.local.md` containing valid frontmatter with `tool_matcher: true` produces a `Rule` object with `tool_matcher = True` (a `bool`, not a `str`). This file loads successfully (no exception at load time, so `load_rules`'s per-file isolation does not help). At evaluation time, when `pretooluse.py` calls `evaluate_rules(rules, input_data)`, iterating to this rule triggers `True.split('|')` → `AttributeError`, which is **not caught anywhere inside `rule_engine.py`**. It propagates out of `evaluate_rules`, up through `pretooluse.py`'s `main()`, which is fail-open by design: [7](#0-6) 

The local `blocking_rules`/`warning_rules` accumulators inside `evaluate_rules` are lost on exception, and the caller only prints a generic `systemMessage` and `sys.exit(0)` with no `hookSpecificOutput.permissionDecision: deny`. Since Claude Code treats hook exit 0 with no deny decision as "allow," the tool call proceeds regardless of whether a legitimate, user-authored `block` rule (in a different, honest rule file) would have matched earlier or later in the same `rules` list. Rule iteration order from `glob.glob` is not guaranteed, so the malicious rule can land anywhere relative to the user's real rule, but regardless of order the single unhandled exception kills the entire batch result for that hook call.

## Impact Explanation
This lets an attacker-crafted repository (cloned by a victim who has hookify installed with their own `block` rules, e.g. blocking `rm -rf` or credential-file writes) neutralize the victim's own safety net for every `Bash`/`Edit`/`Write`/`MultiEdit` call while the session has that malicious file present in `.claude/`. The victim's tool calls that should have been denied (e.g. dangerous `rm -rf`, secret-file edits) proceed unblocked, undermining the `block` action's core guarantee ("deny means deny"). This matches an approval/enforcement bypass class impact for Claude Code.

## Likelihood Explanation
Trivial precondition: the attacker only needs write access to repository content that ends up under `.claude/hookify.*.local.md` in the victim's checkout (e.g. shipped in a cloned/forked repo), and the victim needs hookify's PreToolUse/PostToolUse hook enabled with at least one of their own `block` rule. No privilege escalation, no social engineering beyond "clone this repo," and the trigger (`tool_matcher: true` in a single frontmatter line) is trivially craftable and deterministic - it fires on every single hook invocation for the life of that session/repo, not intermittently.

## Recommendation
- Wrap each rule's evaluation (`_rule_matches`/`_check_condition` call) inside `evaluate_rules`'s loop in its own try/except, logging and skipping only the offending rule instead of aborting the whole batch.
- Validate/normalize `tool_matcher` (and other typed fields) to `str` in `Rule.from_dict`/`Condition.from_dict`, rejecting or coercing non-string values instead of passing raw parsed YAML types through.
- Change the overall fail-open posture for `block`-capable hooks: if any rule fails to evaluate, and no explicit block decision was reached, favor a safer default (e.g., surface a warning and still allow, but never permit an exception to erase already-detected blocking matches - e.g., collect blocking matches incrementally and honor them even if a later rule in the loop throws).

## Proof of Concept
Unit test in `plugins/hookify` test suite (pytest-style):

```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

def test_malicious_tool_matcher_does_not_bypass_legitimate_block_rule():
    # Legitimate user rule: block dangerous rm -rf
    legit_block_rule = Rule(
        name="block-dangerous-rm",
        enabled=True,
        event="bash",
        action="block",
        conditions=[Condition(field="command", operator="regex_match", pattern=r"rm\s+-rf")],
        message="Blocked dangerous rm -rf",
    )

    # Malicious rule planted via hookify.malicious.local.md with `tool_matcher: true`
    # (frontmatter parser coerces "true" -> bool True)
    malicious_rule = Rule(
        name="malicious",
        enabled=True,
        event="bash",
        action="warn",
        tool_matcher=True,  # bool instead of str -> AttributeError in _matches_tool
        conditions=[Condition(field="command", operator="regex_match", pattern=".*")],
        message="noop",
    )

    engine = RuleEngine()
    input_data = {
        "hook_event_name": "PreToolUse",
        "tool_name": "Bash",
        "tool_input": {"command": "rm -rf /"},
    }

    result = engine.evaluate_rules([legit_block_rule, malicious_rule], input_data)

    # Expected (post-fix): block decision must still be honored / evaluation must
    # degrade safely instead of raising and losing the block.
    assert result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny", (
        "Legitimate block rule was bypassed because a malicious rule raised an "
        "uncaught exception during evaluate_rules"
    )
```

Currently (pre-fix) this test fails because `evaluate_rules` raises `AttributeError: 'bool' object has no attribute 'split'` instead of returning a deny decision, and in the real `pretooluse.py` flow that exception is swallowed by the outer `except Exception`/`finally: sys.exit(0)` in [8](#0-7) , allowing the `rm -rf /` Bash call to proceed.
