### Title
Single `_minRec` Slippage Parameter Reused Across All Reward-Token Conversions Makes Slippage Protection Ineffective or Causes Compound DoS - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` accepts a single `_minRec` value and applies it, unchanged, to every registered reward token that has a `convertor` configured, even though each reward token can have a completely different balance, price, and decimals. This mirrors the reported GMX bug class of reusing one `minOut`/slippage bound across multiple independent conversions with different underlying amounts.

### Finding Description
`compound()` iterates over all `rewards[i]` entries and, for every token that has a non-zero `convertor`, calls `IConverter(_convertor).convertFor(receivedBalance, _convertRatio, _minRec, msg.sender, 2)` using the same caller-supplied `_minRec` for each iteration: [1](#0-0) 

The receiving converter (`SmartWomConvert._convertFor`) enforces the bound as an absolute-value check against the combined swap+direct-mint output of that specific call: [2](#0-1) 

Because `receivedBalance` differs per reward token (different accrued amounts, potentially different underlying assets if more converters/reward tokens are added via `addReward`/`setConvertor`), a single absolute `_minRec` cannot correctly bound slippage for more than one token in the same call: [3](#0-2) [4](#0-3) 

- If `_minRec` is sized for the token with the smallest converted amount, slippage protection for larger-balance tokens is effectively void.
- If `_minRec` is sized for the token with the largest converted amount, `convertFor` calls for every other (smaller-balance) reward token will revert with `MinRecNotMatch`, aborting the whole `compound()` transaction (since the reward-loop is not wrapped in try/catch) and blocking legitimate compounding.

`compound()` is an unrestricted external function reachable directly by any ordinary wallet compounding its own claimed rewards; no privileged role is required to trigger the vulnerable path.

### Impact Explanation
When multiple reward tokens are routed through converters, this bug either (a) nullifies slippage protection for some tokens — enabling MEV/sandwich extraction of value during the swap leg inside `_convertFor`, directly reducing the amount of `mWom`/locked value a user receives, or (b) causes `compound()` to revert whenever the configured `_minRec` doesn't fit every converted token's balance in the same call, blocking users from compounding rewards for as long as multiple divergent-value reward tokens with a convertor remain configured.

### Likelihood Explanation
This triggers under normal operation as soon as more than one reward token is configured with a `convertor` (an admin-configurable but not attacker-controlled state, reachable via routine protocol config through `addReward`/`setConvertor`), and any user calling `compound()` with rewards accrued across those tokens — no attacker privilege is needed beyond calling `compound()` and choosing/being forced to reuse one `_minRec`.

### Recommendation
Pass a `_minRec` (or array of `_minRec` values) per reward-token entry in the `compound()` loop, computed relative to each token's own `receivedBalance` and its converter's expected output, rather than a single scalar shared by all iterations.

### Proof of Concept
1. Owner registers two reward tokens with the `SmartWomConvert` convertor: `WOM` (18 decimals, larger accrued balance) and another reward token `X` (different decimals/lower balance) via `addReward`/`setConvertor`. [3](#0-2) 
2. User calls `compound(lps, rewards, convertRatio, minRec, lockMgp)` with `minRec` sized to be a meaningful slippage bound for the large `WOM` balance. [5](#0-4) 
3. For token `X`, `receivedBalance` is much smaller than `minRec`, so `_convertFor`'s check `convertAmount + amountRec < _minRec` reverts with `MinRecNotMatch`, reverting the entire `compound()` call and blocking all reward compounding in that transaction. [6](#0-5) 
4. Conversely, if the user sets `minRec` small enough to pass for token `X`, the check becomes ineffective for `WOM`'s much larger conversion, allowing a sandwiched swap to extract value from the `WOM→mWom` buyback leg with no meaningful protection.
