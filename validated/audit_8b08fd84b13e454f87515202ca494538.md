### Title
Relayer fee withdrawal requires an ECDSA/Sr25519 signature from the delivery address — fees credited to a smart-contract relayer are permanently unclaimable - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`pallet-ismp-relayer` credits fee balances to whichever address is recorded as having delivered a message on the destination chain, and only allows that same address to withdraw the accumulated fees by producing a cryptographic signature (`Signature::Evm`/`Sr25519`/`Ed25519`) proving key ownership. On EVM destinations, the "delivery address" credited is `_msgSender()` of whoever called `HandlerV2.handlePostRequests`/`handleGetResponses`/etc., which can be a smart-contract relayer wrapper (batcher, Safe, automation bot) rather than an EOA. A smart contract has no private key and can never produce a valid `Signature::Evm` over the withdrawal (or beneficiary-redirect) message, so any fees accumulated to that address become permanently stuck — the exact bug-class described in the report (a receiver that is a contract cannot satisfy an authorization check that assumes an EOA/key-holder).

### Finding Description
On the EVM side, `HandlerV2.handlePostRequests` (and the analogous GET-response/timeout handlers) records the caller as the relayer credited for delivery: [1](#0-0) 
That relayer address flows into `EvmHost.dispatchIncoming`, which stores it directly in `_requestReceipts[commitment]`: [2](#0-1) 
Nothing here restricts the caller to an EOA — any contract can call `handlePostRequests` (e.g. a gas-optimizing batching contract, a Gelato/Chainlink Automation relay, or a multisig executor) and become the recorded "relayer."

On the Hyperbridge (Substrate) side, `pallet-ismp-relayer::accumulate` reads this state-proven delivery address and credits fees to it (or to a `beneficiary_address` chosen at accumulation time, but that redirect itself must be authorized by a signature *from the delivery address*): [3](#0-2) 

To later withdraw those accumulated fees, `Pallet::withdraw` requires the caller to supply a signature over a nonce/destination message, and validates it by recovering/verifying against the credited `address`: [4](#0-3) 

If `address` is an EVM smart-contract address (not an EOA), there is no private key to produce a valid ECDSA signature (`Signature::Evm`) that will `ecrecover` back to that address. The same applies to the `beneficiary_details` signature check at accumulation time in `accumulate.rs` — it too must be signed by the delivery address, so a contract-delivery-address cannot even redirect its own fees to an EOA it controls before or after accumulation. This mirrors the reported bug precisely: an on-chain balance is earmarked for an address, but the only path to claim it is a signature/call that only an EOA (or a contract with matching custom logic that was never anticipated) can produce.

### Impact Explanation
Any protocol/user fees legitimately earned by a smart-contract-operated relayer become permanently locked in `pallet-ismp-relayer`'s `Fees` storage with no recovery path — there is no admin/governance override to force-pay or reassign a stuck balance to a different signer. This is a direct loss-of-funds condition matching the bounty's "loss of funds" impact category, triggered purely by legitimate use of smart-contract-based relaying infrastructure (increasingly common for MEV-protected, automated, or multisig-operated relayers), not by any malicious peer/relayer/prover behavior.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: nothing in `HandlerV2`/`EvmHost` prevents or discourages contract-based callers from submitting `handlePostRequests`/`handleGetResponses`, and running relayers behind smart contracts (for batching, access control, or automation frameworks) is a normal operational pattern. Any relayer operator who runs their submission through a contract wallet, proxy, or automation service will unknowingly render their earned fees unclaimable, with no on-chain signal warning them before the funds are credited.

### Recommendation
- Detect at accumulation/withdrawal time whether the credited address is a contract (on EVM, an `extcodesize` check surfaced via the state proof, or requiring an explicit registration step) and provide an alternative authorization path (e.g., an `EIP-1271`-style signature validation, or letting the contract itself submit the withdrawal call under `ensure_signed`/its own transaction rather than requiring an off-chain ECDSA signature).
- Alternatively, require relayers to pre-register a "payout" EOA/beneficiary before earning credit (rather than only being able to set it via a signature from the credited address), so a contract-operated relayer can nominate a claimable beneficiary independently of ECDSA signing.
- At minimum, document/reject contract-address relayers at the `dispatchIncoming` layer so fees are never credited to an address that cannot subsequently authenticate a withdrawal.

### Proof of Concept
1. Deploy a minimal relayer-wrapper contract `RelayerBot` on the EVM destination chain whose sole purpose is to call `HandlerV2.handlePostRequests(host, msg)` (e.g., to batch multiple deliveries atomically or restrict callers via its own access control).
2. Have `RelayerBot` successfully deliver a fee-bearing POST request; `EvmHost.dispatchIncoming` records `_requestReceipts[commitment] = address(RelayerBot)` [5](#0-4) 
3. Submit `pallet_ismp_relayer::accumulate_fees` with a valid state proof of this delivery; `Fees::<T>::get(dest_chain, RelayerBot_address)` is credited with the accrued fee [6](#0-5) 
4. Attempt `pallet_ismp_relayer::withdraw_fees` with `WithdrawalInputData { signature: Signature::Evm { address: RelayerBot_address, signature: <any> }, ... }` — since `RelayerBot` has no private key, no signature can be produced that `ecrecover`s to `RelayerBot_address`; `Pallet::withdraw` always fails at [7](#0-6) 
5. The fee balance under `Fees::<T>::get(dest_chain, RelayerBot_address)` remains permanently non-zero and unclaimable, with no governance function available to reassign or force-pay it.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
