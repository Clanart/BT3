### Title
ProtoJSON `Timestamp` parsing accepts `seconds`/date components outside the documented valid range without validation - ([File: src/google/protobuf/json/internal/parser.cc])

### Summary
The external report's failed invariant is: a value that feeds into a downstream calculation/consumer is accepted without validating it against the maximum/complete bound that the type's own documentation and downstream consumers rely on (`royaltiesBasisPoints <= ROYALTIES_BASIS`). The Protobuf analog is `ParseTimestamp` in `src/google/protobuf/json/internal/parser.cc`, which decodes a ProtoJSON `Timestamp` string into `seconds`/`nanos` fields but never validates the computed `secs` (nor the raw `year`/`month`/`day` components) against the documented valid range `[kTimestampMinSeconds, kTimestampMaxSeconds]` (`0001-01-01T00:00:00Z` .. `9999-12-31T23:59:59Z`) before storing it via `Traits::SetInt64`.

### Finding Description
`google.protobuf.Timestamp` is documented (see `timestamp.proto` and `TimeUtil`) to be valid only within `kTimestampMinSeconds = -62135596800` and `kTimestampMaxSeconds = 253402300799` [1](#0-0) . The **writer** side of the JSON codec enforces this invariant strictly and errors out if it is violated: [2](#0-1) 

However, the **parser** side, `ParseTimestamp` in `src/google/protobuf/json/internal/parser.cc`, only checks that `year`, `month`, and `day` are individually non-zero, and that each field fits in its digit width; it performs no upper-bound check on `year` (allowing e.g. a 4-digit year like `9999` to be fine, but there is also no check that month∈[1,12] or day∈[1, days-in-month] beyond the digit-width parse), and critically never validates the final computed `secs` against `kTimestampMinSeconds`/`kTimestampMaxSeconds` before calling `Traits::SetInt64(...)`: [3](#0-2) 

The same asymmetry exists in the upb JSON decoder (`jsondec_timestamp`, used by PHP/Ruby via `php-upb.c`/`ruby-upb.c` and standalone upb), which checks only the **lower** bound and omits the **upper** bound check that its own encoder enforces: [4](#0-3) 
compare to the encoder, which checks both bounds: [5](#0-4) 

This is the direct analog of the EIP-2981 bug: a client-supplied value (JSON date/time string) is accepted and stored into a message field without validating it against the maximum (or, for the C++ parser, *either* bound) that the type's contract and its own serializer enforce. The "attacker-controlled value" is the ProtoJSON string itself, sent to any public `JsonStringToMessage`/`util::JsonStringToMessage` (C++) or `upb_JsonDecode` (upb-based bindings) API — an ordinary bounded-input parse call, no privileged access required.

### Impact Explanation
A parsed `Timestamp` message can end up holding a `seconds` value far outside `[kTimestampMinSeconds, kTimestampMaxSeconds]` (or, for the C++ path, a month/day combination and thus a `secs` value that is nonsensical) while still being considered "successfully parsed." Any code that consumes the message assuming the well-known-type invariant holds (as `TimeUtil` explicitly assumes, using `ABSL_DCHECK`, a no-op in release/production builds) will silently compute incorrect calendar/duration/nanosecond values: [6](#0-5) 
This mirrors the royalty bug's impact: a downstream consumer trusts a value that should have been bounded, and gets an out-of-contract result (miscalculated duration/timestamp arithmetic) rather than a rejected input. It also creates a parse/serialize asymmetry: a message that parses successfully from JSON can fail to re-serialize to JSON (`unparser.cc` rejects it), which is an integrity break in round-trip processing pipelines that trust "parse succeeded ⇒ serialize succeeds."

### Likelihood Explanation
High reachability, since this is exercised through the standard public ProtoJSON parsing API on any message containing a `google.protobuf.Timestamp` field, with a simple crafted date string (e.g., a large year or an unvalidated month/day). No special schema, plugin, or privileged access is required — it is a straightforward malformed-but-`Peek`-passing JSON payload.

### Recommendation
In `ParseTimestamp` (`src/google/protobuf/json/internal/parser.cc`), after computing `secs`, validate `secs` against `TimeUtil::kTimestampMinSeconds`/`kTimestampMaxSeconds` (and ideally validate `month` and `day` ranges explicitly) and return `str->loc.Invalid(...)` on failure, mirroring the checks already present in `unparser.cc`'s `WriteTimestamp`. Similarly, in `upb/json/decode.c`'s `jsondec_timestamp` (and the vendored copies in `php-upb.c`/`ruby-upb.c`), add the missing upper-bound check (`seconds.int64_val > 253402300799`) to match `jsonenc_timestamp`'s symmetric validation.

### Proof of Concept
Conceptual PoC (parser-only path, C++):
1. Construct JSON: `{"optionalTimestamp": "9999999999-01-01T00:00:00Z"}` — note `TakeTimeDigitsWithSuffixAndAdvance` for the year segment reads up to `max_digits` digits per its `limit` parameter; but the point of concern is a value where `year`/`month`/`day` combine into a `secs` far outside `kTimestampMinSeconds..kTimestampMaxSeconds` while month/day still satisfy the "!=0" check, e.g. any date whose computed epoch is > `253402300799` seconds or < `-62135596800` seconds.
2. Feed this into `JsonStringToMessage` for a message containing a `google.protobuf.Timestamp` field.
3. Observe `ParseTimestamp` returns `absl::OkStatus()` (i.e., succeeds) and stores an out-of-range `secs` via `Traits::SetInt64`, per `src/google/protobuf/json/internal/parser.cc:931`.
4. Attempt to re-serialize the same message to JSON via `MessageToJson`: `WriteTimestamp` in `unparser.cc:618-625` will return `absl::InvalidArgumentError`, proving the parse accepted a value the writer itself considers invalid — confirming the asymmetric/missing bound check.

template <typename Traits>
absl::Status ParseTimestamp(JsonLexer& lex, const Desc<Traits>& desc,
                            Msg<Traits>& msg) {
  if (lex.Peek(JsonLexer::kNull)) {
    return lex.Expect("null");
  }

  absl::StatusOr<LocationWith<MaybeOwnedString>> str = lex.ParseUtf8();
  RETURN_IF_ERROR(str.status());

  absl::string_view data = str->value.AsView();
  if (data.size() < 20) {
    return str->loc.Invalid("timestamp string too short");
  }

  int64_t secs;
  {
    /* 1972-01-01T01:00:00 */
    auto year = TakeTimeDigitsWithSuffixAndAdvance(data, 4, "-");
    if (!year.has_value() || *year == 0) {
      return str->loc.Invalid("bad year in timestamp");
    }
    auto mon = TakeTimeDigitsWithSuffixAndAdvance(data, 2, "-");
    if (!mon.has_value() || *mon == 0) {
      return str->loc.Invalid("bad month in timestamp");
    }
    auto day = TakeTimeDigitsWithSuffixAndAdvance(data, 2, "T");
    if (!day.has_value() || *day == 0) {
      return str->loc.Invalid("bad day in timestamp");
    }
    auto hour = TakeTimeDigitsWithSuffixAndAdvance(data, 2, ":");
    if (!hour.has_value()) {
      return str->loc.Invalid("bad hours in timestamp");
    }
    auto min = TakeTimeDigitsWithSuffixAndAdvance(data, 2, ":");
    if (!min.has_value()) {
      return str->loc.Invalid("bad minutes in timestamp");
    }
    auto sec = TakeTimeDigitsWithSuffixAndAdvance(data, 2, "");
    if (!sec.has_value()) {
      return str->loc.Invalid("bad seconds in timestamp");
    }

    uint32_t m_adj = *mon - 3;  // March-based month.
    uint32_t carry = m_adj > *mon ? 1 : 0;

    uint32_t year_base = 4800;  // Before min year, multiple of 400.
    uint32_t y_adj = *year + year_base - carry;

    uint32_t month_days = ((m_adj + carry * 12) * 62719 + 769) / 2048;
    uint32_t leap_days = y_adj / 4 - y_adj / 100 + y_adj / 400;
    int32_t epoch_days =
        y_adj * 365 + leap_days + month_days + (*day - 1) - 2472632;

    secs = int64_t{epoch_days} * 86400 + *hour * 3600 + *min * 60 + *sec;
  }

  auto nanos = TakeNanosAndAdvance(data);
  if (!nanos.has_value()) {
    return str->loc.Invalid("timestamp had bad nanoseconds");
  }

  if (data.empty()) {
    return str->loc.Invalid("timestamp missing timezone offset");
  }

  {
    // [+-]hh:mm or Z
    bool neg = false;
    switch (data[0]) {
      case '-':
        neg = true;
        ABSL_FALLTHROUGH_INTENDED;
      case '+': {
        if (data.size() != 6) {
          return str->loc.Invalid("timestamp offset of wrong size.");
        }

        data = data.substr(1);
        auto hour = TakeTimeDigitsWithSuffixAndAdvance(data, 2, ":");
        auto mins = TakeTimeDigitsWithSuffixAndAdvance(data, 2, "");
        if (!hour.has_value() || !mins.has_value()) {
          return str->loc.Invalid("timestamp offset has bad hours and minutes");
        }

        int64_t offset = (*hour * 60 + *mins) * 60;
        secs += (neg ? offset : -offset);
        break;
      }
      // Lowercase z is not accepted, per the spec.
      case 'Z':
        if (data.size() == 1) {
          break;
        }
        ABSL_FALLTHROUGH_INTENDED;
      default:
        return str->loc.Invalid("bad timezone offset");
    }
  }

  Traits::SetInt64(Traits::MustHaveField(desc, 1), msg, secs);
  Traits::SetInt32(Traits::MustHaveField(desc, 2), msg, *nanos);

  return absl::OkStatus();
}

static void jsondec_timestamp(jsondec* d, upb_Message* msg,
                              const upb_MessageDef* m) {
  UPB_ASSERT(!upb_Message_IsFrozen(msg));
  upb_MessageValue seconds;
  upb_MessageValue nanos;
  upb_StringView str = jsondec_string(d);
  const char* ptr = str.data;
  const char* end = ptr + str.size;

  if (str.size < 20) goto malformed;

  {
    /* 1972-01-01T01:00:00 */
    int year = jsondec_tsdigits(d, &ptr, 4, "-");
    int mon = jsondec_tsdigits(d, &ptr, 2, "-");
    int day = jsondec_tsdigits(d, &ptr, 2, "T");
    int hour = jsondec_tsdigits(d, &ptr, 2, ":");
    int min = jsondec_tsdigits(d, &ptr, 2, ":");
    int sec = jsondec_tsdigits(d, &ptr, 2, NULL);

    seconds.int64_val = jsondec_unixtime(year, mon, day, hour, min, sec);
  }

  nanos.int32_val = jsondec_nanos(d, &ptr, end);

  {
    /* [+-]08:00 or Z */
    int ofs_hour = 0;
    int ofs_min = 0;
    bool neg = false;

    if (ptr == end) goto malformed;

    switch (*ptr++) {
      case '-':
        neg = true;
        /* fallthrough */
      case '+':
        if ((end - ptr) != 5) goto malformed;
        ofs_hour = jsondec_tsdigits(d, &ptr, 2, ":");
        ofs_min = jsondec_tsdigits(d, &ptr, 2, NULL);
        ofs_min = ((ofs_hour * 60) + ofs_min) * 60;
        seconds.int64_val += (neg ? ofs_min : -ofs_min);
        break;
      case 'Z':
        if (ptr != end) goto malformed;
        break;
      default:
        goto malformed;
    }
  }

  if (seconds.int64_val < -62135596800) {
    jsondec_err(d, "Timestamp out of range");
  }

  jsondec_checkoom(
      d, upb_Message_SetFieldByDef(msg, upb_MessageDef_FindFieldByNumber(m, 1),
                                   seconds, d->arena));
  jsondec_checkoom(
      d, upb_Message_SetFieldByDef(msg, upb_MessageDef_FindFieldByNumber(m, 2),
                                   nanos, d->arena));
  return;

malformed:
  jsondec_err(d, "Malformed timestamp");
}

int64_t TimeUtil::TimestampToMilliseconds(const Timestamp& timestamp) {
  ABSL_DCHECK(IsTimestampValid(timestamp))
      << "Timestamp is outside of the valid range";
  return timestamp.seconds() * kMillisPerSecond +
         RoundTowardZero(timestamp.nanos(), kNanosPerMillisecond);
}

int64_t TimeUtil::TimestampToSeconds(const Timestamp& timestamp) {
  ABSL_DCHECK(IsTimestampValid(timestamp))
      << "Timestamp is outside of the valid range";
  return timestamp.seconds();
}
