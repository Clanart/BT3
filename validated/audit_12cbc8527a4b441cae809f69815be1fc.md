### Title
Webhook shop identity spoofing via unauthenticated `X-Shopify-Shop-Domain` header, bypassing HMAC scope binding - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
The C4 finding describes a class of bug where a privileged operation trusts a **mutable, attacker-influenceable reference** (`ownerOf(id)`) instead of an **immutable, cryptographically-bound value** recorded at creation time, letting an attacker redirect a sensitive state mutation to an unintended target by manipulating that mutable reference before the check runs. The same bug class exists in `ShopifyApp::WebhookVerification`: the HMAC signature only binds the request **body**, while the shop identity used for all downstream authorization/lookups is read from a completely unauthenticated, mutable HTTP **header**.

### Finding Description
`ShopifyApp::WebhookVerification#verify_request` computes `hmac_valid?` over `request.raw_post` only: [1](#0-0) 

The `shop_domain` accessor used by every generated privacy/webhook job (`shop.find_by(shopify_domain: shop_domain)`, `shop.with_shopify_session`) reads directly and unconditionally from the `X-Shopify-Shop-Domain` header, which is **not part of the HMAC-signed material**: [2](#0-1) 

This "shop" value flows unchecked into all generated job templates that resolve tenant/session context by it, e.g.: [3](#0-2) [4](#0-3) [5](#0-4) 

`ShopifyApp::WebhooksController#receive` passes `request.headers.to_h` (including the unauthenticated shop-domain header) straight into `ShopifyAPI::Webhooks::Registry.process`, and the resulting `handle(shop:, ...)` value is what's forwarded to `perform_later(shop_domain: shop, ...)`: [6](#0-5) 

The app's webhook shared secret (`ShopifyApp.configuration.secret`) is **the same for every shop that installs the app** — it is not per-shop — as seen in `PayloadVerification#hmac_valid?`: [7](#0-6) 

Because the secret is shared and the HMAC only covers the body, any party who can obtain one validly-signed `(body, hmac)` pair for the app (e.g. a merchant who has installed the app themselves, or captured a webhook their own shop legitimately received) can replay that exact body+HMAC to the app's public webhook endpoint while swapping only the `X-Shopify-Shop-Domain` header to a victim shop's domain. `verify_request` will still pass (it never inspects the header), and the job will process the payload under the *victim's* identity — exactly the "mutable reference used instead of the immutable/bound one" pattern from the report, here manifesting as shop-identity confusion instead of vault-ownership confusion.

### Impact Explanation
An attacker can cause the app to execute shop-scoped privileged actions (e.g. calling `shop.with_shopify_session` for the mandatory `shop/redact`, `customers/redact`, `customers/data_request` jobs, or any custom `CartsUpdateJob`-style handler) attributed to an arbitrary victim shop domain of the attacker's choosing, without possessing that shop's session or token. Depending on what the app's webhook jobs do with `shop_domain` (data deletion, session-based API calls, business logic keyed by shop), this is a cross-shop trust boundary violation: one tenant's valid signed payload can be "reassigned" to another tenant purely via header manipulation.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one validly HMAC-signed webhook body for the shared app secret — trivially achievable by any merchant who installs the app themselves (their own webhooks are signed with the same app-wide secret) or by intercepting/replaying any webhook delivery. The webhook endpoint is a public, unauthenticated-by-design HTTP endpoint, so no merchant/admin session is needed to send the forged request. This is a realistic, low-effort attack path reachable from an unrelated-merchant HTTP request.

### Recommendation
Do not trust `X-Shopify-Shop-Domain` (or any header) as the authoritative shop identity for a webhook. Bind the shop/tenant identity into the HMAC-verified material, e.g. by requiring `ShopifyAPI::Webhooks::Request`/`Registry.process` to derive shop context strictly from the verified body payload (most Shopify webhook bodies include the shop's `myshopify_domain`/shop id), or explicitly include the header value in the data covered by `hmac_valid?` before trusting it, and reject requests where the header disagrees with the verified shop reference.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (or otherwise obtains one legitimately-signed webhook delivery for the app).
2. Shopify (or the attacker, replaying) sends `POST /webhooks/:type` with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` — valid because the secret is shared across all shops.
3. Attacker resends the same request but changes `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyApp::WebhookVerification#verify_request` still passes because it only checks `hmac_valid?(request.raw_post)`, which is unchanged. `ShopifyApp::WebhooksController#receive` processes the request, and any downstream job (e.g. `ShopRedactJob`, `CustomersRedactJob`, or a custom job) receives `shop_domain: "victim-shop.myshopify.com"` and performs shop-scoped actions (e.g. `Shop.find_by(shopify_domain: shop_domain)` then `shop.with_shopify_session`) against the victim shop, not the attacker's shop.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
