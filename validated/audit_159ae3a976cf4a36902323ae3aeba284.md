## Analysis

The Notional bug's core pattern: a protection mechanism (`minImpliedRate` slippage check) is applied only inside one branch of an amount-based `if` condition, and is silently skipped when the amount crosses into the other branch (`maxFCash < fCashAmount`). No validation exists to prevent reaching that unprotected branch.

The same control-flow shape exists in the Hyperbridge Intent Gateway's same-chain fill path.

### Title
Surplus/dust protocol-fee split is skipped once a leg has any prior partial fill, letting a solver structure fills to avoid ever paying the protocol/beneficiary surplus share - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` computes a `dust`/surplus split (protocol share + beneficiary share) only when `alreadyFilled == 0 && solverAmount > totalRequired`. As soon as any partial fill has happened for that output token (`alreadyFilled != 0`), the code takes the `else` branch which simply clamps `fillAmount = min(solverAmount, remaining)` with `beneficiaryShare = protocolShare = 0` — no matter how large `solverAmount` is. [1](#0-0) 

### Finding Description
The surplus-collection guard (analogous to `minImpliedRate`) is gated purely on the *state variable* `alreadyFilled`, which any unprivileged solver fully controls: a solver can submit a trivial partial fill (even a 1-wei `solverAmount`) as the *first* fill for an output-token leg. Because `remaining == 0` isn't reached, the fill succeeds and sets `_partialFills[commitment][outputToken] = 1`. [2](#0-1) 

On every subsequent fill of that same leg (by the same solver or any other), `alreadyFilled != 0` is now permanently true for the life of the order, so the `if (alreadyFilled == 0 && solverAmount > totalRequired)` branch that computes `protocolShare`/`beneficiaryShare` can never trigger again — the `else` branch just clamps `fillAmount` to `remaining` and transfers only `beneficiaryTotal = fillAmount` (no share is ever pulled via `safeTransferFrom`). [3](#0-2) 

Contrast this with the cross-chain fill path, `_fillCrossChain`, where the dust/surplus split is computed unconditionally on every fill (no partial-fill state to bypass, since cross-chain orders are all-or-nothing) — confirming the same-chain code's dependence on `alreadyFilled` is a real, avoidable branch rather than an inherent design constraint: [4](#0-3) 

This mirrors the wfCash bug precisely: the slippage/economic-safety check (`minImpliedRate` there, `surplusShareBps` split here) is applied only within one branch of an amount comparison, and the *other* branch is reachable at will and silently skips it — except here the attacker doesn't need a second party to front-run; a lone solver drives both calls (the 1-wei seed fill and the real fill), so this does not depend on any malicious peer, relayer, prover, or front-running of another actor, satisfying the impact gate.

### Impact Explanation
This is a protocol-fee/logic-manipulation bug rather than a fund-theft-from-users bug: it lets a solver unilaterally suppress the protocol's `surplusShareBps` fee-collection mechanism (and the beneficiary's surplus cut) on every same-chain order leg it chooses to seed with a dust-sized partial fill first. Protocol dust revenue (`DustCollected`) and beneficiary surplus, both explicit, documented economic guarantees of the intent-fill design, can be permanently zeroed for that leg regardless of how much genuine overpayment/surplus later occurs — a logic attack against the fee model rather than a direct fund-safety break for the escrowed user assets.

### Likelihood Explanation
High: any solver can call `fillOrder` themselves twice — once with a negligible amount, once with the real amount — with no special privileges, no cooperation from any other actor, and no reliance on timing/front-running. The `if (alreadyFilled == 0 ...)` condition is trivially defeated by any solver who wants to avoid contributing surplus.

### Recommendation
Decouple the surplus/dust computation from the `alreadyFilled == 0` state. Compute `dust = solverAmount - fillAmount` (the actual clamped amount charged) on every fill regardless of prior partial-fill history, and always split it via `surplusShareBps`/`protocolShare` the same way `_fillCrossChain` does, e.g.:
```solidity
uint256 fillAmount = solverAmount > remaining ? remaining : solverAmount;
uint256 dust = solverAmount - fillAmount; // charge is fillAmount, but only pull fillAmount from solver if dust==0 is desired
if (dust > 0) { /* split protocolShare/beneficiaryShare as in the fresh-order branch */ }
```
so the fee guard cannot be neutralized purely by manipulating `_partialFills` state via a preceding trivial fill.

### Proof of Concept
1. Solver A calls `fillOrder(order, {outputs: [{token, amount: 1}]})` on a fresh same-chain order → `alreadyFilled == 0`, `solverAmount(1) < totalRequired`, so no surplus branch triggers; `_partialFills[commitment][token]` becomes `1`.
2. Solver A (or B) calls `fillOrder` again with `solverAmount = remaining` (or any amount ≥ `remaining`, clamped) → since `alreadyFilled != 0` now, the `else` branch executes unconditionally: `fillAmount = remaining`, `beneficiaryShare = protocolShare = 0`.
3. No `DustCollected` event fires, and the protocol/beneficiary never receive any surplus share for this leg, even though the solver would have owed a split had step 1 not been performed first. [5](#0-4)
