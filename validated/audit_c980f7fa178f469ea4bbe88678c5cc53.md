Audit Report

## Title
Unauthenticated RPC-pubsub WebSocket connections have no handshake/idle read timeout, enabling remote resource exhaustion - (File: rpc/src/rpc_pubsub_service.rs)

## Summary
`listen()` accepts unlimited unauthenticated TCP connections to the JSON-RPC pubsub port and spawns a task per connection with no cap, and `handle_connection()` awaits the WebSocket handshake and subsequent idle reads with no timeout. An attacker can open many TCP connections that never complete the handshake or go silent after connecting, causing unbounded accumulation of tokio tasks, sockets, and per-connection state (`DashMap`, broadcast receiver) on the validator's pubsub service.

## Finding Description
`listen()` at rpc/src/rpc_pubsub_service.rs:429-474 accepts every incoming TCP connection unconditionally in its `select!`/`listener.accept()` branch and spawns `handle_connection` per connection, using `TokenCounter` only for a metric (`rpc/src/rpc_pubsub_service.rs:448,457`; `metrics/src/lib.rs:30-49`), not for any limit enforcement. Inside `handle_connection` (rpc/src/rpc_pubsub_service.rs:349-427), `server.receive_request().await?` (line 356) awaits the WebSocket handshake with no timeout, and the main loop's inner `select!` (lines 386-411) only races `receive_future`, `broadcast_receiver.recv()`, and `tripwire`—none of which resolve due to client inactivity, so an idle connection blocks forever. `PubSubConfig` (rpc/src/rpc_pubsub_service.rs:40-49) and its corresponding CLI arguments (validator/src/commands/run/args/pub_sub_config.rs) expose no option for maximum concurrent connections or idle/handshake timeout. This contrasts with the QUIC/TPU path (streamer/src/nonblocking/quic.rs:331-379), which enforces connection-attempt timeouts, rate limiting, and connection caps, and with net-utils/src/ip_echo_server.rs:92-102,189-225, which enforces `MAX_CONCURRENT_CONNECTIONS`, per-IP limits, and an I/O deadline.

## Impact Explanation
This is a non-RPC-request remote exhaustion vector against the RPC/pubsub service. Because there is no per-connection or per-IP cap and no timeout, an unprivileged, unauthenticated attacker can open many TCP sockets to the pubsub port and stall the handshake or go silent post-handshake, causing unbounded accumulation of server-side tokio tasks, sockets, and memory (DashMap/broadcast state) until the pubsub service degrades or the process runs out of file descriptors/memory.

## Likelihood Explanation
Likelihood is high for any validator/RPC node exposing the pubsub WebSocket port: the attack requires only opening raw TCP sockets, optionally without completing the handshake, or completing it once and sending nothing further—no valid subscription, authentication, or protocol payload is needed, and it is trivially scriptable at scale from one or a few source IPs.

## Recommendation
Wrap the WebSocket handshake (`server.receive_request()`/`send_response()`) in a bounded `tokio::time::timeout`; add an idle-read timeout branch to the `select!` loop in `handle_connection` that closes connections receiving no client frames within a bounded window; and enforce a maximum number of concurrent pubsub connections globally and per source IP, mirroring the protections in `streamer/src/nonblocking/quic.rs` and `net-utils/src/ip_echo_server.rs`.

## Proof of Concept
1. Start a validator/RPC node with the JSON-RPC pubsub service enabled (`PubSubService::new`, `listen()` in rpc/src/rpc_pubsub_service.rs).
2. From an unprivileged client, open N raw TCP connections to the pubsub port without completing the WebSocket handshake, or complete the handshake once and then send nothing further.
3. Because the handshake await (line 356) and the main-loop `receive_future` await (lines 384-398) have no timeout, and `listen()` (lines 448-467) spawns an unbounded number of tasks, each connection persists indefinitely, consuming a tokio task, socket, and associated buffers.
4. Repeating at scale from one or a few source IPs accumulates unbounded resource usage on the pubsub runtime (`pubsub_config.worker_threads`), eventually degrading or exhausting the validator's RPC pubsub service.
