### Title
Unauthenticated `WWW-Authenticate` header spoofs GitHub identity in credential trust decision - (File: app/src/lib/trampoline/trampoline-credential-helper.ts)

### Summary
`getEndpointKind()` in Desktop's git-credential trampoline classifies a remote endpoint as `'enterprise'` (i.e., "this is a GitHub host") solely because the HTTP response forwarded by git contains a `WWW-Authenticate` header with `realm="GitHub"`. This value comes directly from the remote server's response and is never authenticated or cross-checked before it is trusted, letting any git remote/proxy the user connects to impersonate a GitHub Enterprise endpoint and short-circuit Desktop's real host-verification path (`isGitHubHost()`).

### Finding Description
`getEndpointKind` decides how Desktop's credential helper should treat a git host: [1](#0-0) 

```
  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }
  ...
  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
``` [2](#0-1) 

This is structurally the same broken invariant as the SGX report: a decision that should be bound to a verified/authenticated value (there, the signed `newInstance`; here, "is this host really GitHub") is instead taken from an attacker-controlled input (`newInstance` set arbitrarily by `msg.sender`; here, the `realm=` string in a header the remote server itself chooses to send) that bypasses the actual verification routine (`isGitHubHost(endpoint)`, an authenticated call to the real API) that exists specifically to make that determination safely.

`getEndpointKind`'s result feeds directly into `getCredential`: [3](#0-2) 

If the classification is anything other than `'generic'` and no stored account matches the endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)`, which drives the user into the GitHub Enterprise sign-in flow scoped to that (attacker-controlled) endpoint: [4](#0-3) 

`promptForGitHubSignIn` treats any non-`github.com` hostname as Enterprise and calls `dispatcher.setSignInEndpoint(origin)`/`beginEnterpriseSignIn`, i.e., the app itself now presents the attacker's host as a legitimate GitHub Enterprise instance to authenticate against.

### Impact Explanation
An attacker who controls (or MITM-proxies) a git remote the victim clones/fetches/pushes to can trivially force this misclassification simply by answering the HTTP Basic auth challenge with `WWW-Authenticate: Basic realm="GitHub"`. This turns an ordinary, unprivileged "malicious remote" primitive into:
- Desktop treating a non-GitHub host as GitHub Enterprise and initiating the OAuth/enterprise sign-in flow bound to that attacker-controlled origin — unauthorized/misleading OAuth account binding directed at attacker infrastructure, which the user is primed to trust because Desktop's own UI now vouches for it as "GitHub".
- Silent divergence from the intended `isGitHubHost()` verification path (an authenticated API probe) for `storeCredential`/`eraseCredential`, which also gate on `getEndpointKind`, so credential persistence behavior is altered purely by attacker-supplied header content.

This matches the report's accepted impact classes: unauthorized OAuth/account binding driven by attacker-controlled remote/proxy responses, without any local access, admin rights, or social engineering beyond the user performing an ordinary fetch/clone/push against an attacker-influenced remote.

### Likelihood Explanation
Any git operation against a remote (clone, fetch, push, or pull) that returns a 401/407 response is enough to trigger this path — git forwards `WWW-Authenticate` headers to the credential helper by design, and the header value is entirely controlled by the remote server or an on-path proxy. No cryptographic material, certificates, or GitHub API confirmation is checked before Desktop accepts the `realm="GitHub"` claim. This makes the trigger trivial and reliable for any attacker capable of serving/proxying a git HTTP endpoint the user interacts with.

### Recommendation
Do not treat the `WWW-Authenticate` `realm=` value as authoritative for host classification. Either remove the header-based "happy path" entirely and always fall back to the authenticated `isGitHubHost(endpoint)` check, or require the header hint to be corroborated by an actual authenticated request to the endpoint (mirroring the SGX fix of binding the decision to verified data instead of unauthenticated attacker input) before granting `'enterprise'`/`'github.com'` classification and before invoking `promptForGitHubSignIn`.

### Proof of Concept
1. Attacker serves a git-over-HTTP endpoint (e.g., `https://attacker.example.com/repo.git`), either as the origin of a repo the victim is lured into cloning, or as a MITM/proxy in front of a legitimate-looking remote.
2. When Git in GitHub Desktop performs an authenticated request against this remote, the attacker's server responds `401 Unauthorized` with header `WWW-Authenticate: Basic realm="GitHub"`.
3. Git forwards this header to Desktop's credential helper as a `wwwauth[...]` credential field.
4. `getEndpointKind()` matches `realm="GitHub"` and returns `'enterprise'` for `attacker.example.com`, skipping the real `isGitHubHost()` check.
5. Since no stored account matches `attacker.example.com`, `getCredential()` calls `ui.promptForGitHubSignIn('https://attacker.example.com')`, and Desktop shows a "Sign in" dialog that begins the Enterprise sign-in flow scoped to the attacker's host, presenting it to the user as a trusted GitHub Enterprise instance.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
