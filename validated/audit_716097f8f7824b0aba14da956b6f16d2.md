### Title
Reward theft in `pallet-consensus-incentives::on_executed` — all state-machine advances in a batch are paid to the signer of `messages[0]` only - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-ismp` invokes `FeeHandler::on_executed` with the full `Vec<MessageWithWeight>` submitted in a single extrinsic call and the full `Vec<IsmpEvent>` produced by processing that whole batch. `pallet-consensus-incentives`'s implementation derives the reward payee from **only the first message in the batch** (`messages.get(0)`), then iterates over **every** `StateMachineUpdated` event in the batch (across all state machines / all messages) and pays the resulting reward to that single derived account.

### Finding Description
In `modules/pallets/consensus-incentives/src/impls.rs`: [1](#0-0) 

`on_executed` extracts `relayer_account` exclusively from `messages[0]`, decoding its embedded `signer` and verifying the signature over `keccak_256(consensus_msg.consensus_proof)`. It then builds `highest_per_state_machine` from **all** `StateMachineUpdated` events in the batch — regardless of which message in the batch produced them — and rewards every one of those state-machine advances to the single `relayer_account` recovered from message 0: [2](#0-1) 

Each `ConsensusMessage` carries its own embedded, independently-verifiable `signer` field which is meant to bind a specific proof to a specific relayer for reward-attribution purposes (the same "prover-bound proof" pattern documented for SP1 proofs — see `docs/content/developers/explore/provers.mdx`). However, this binding is only checked/used for message index 0. If a single extrinsic submission (a `Vec<Message>` handled through `pallet-ismp`'s message handler) contains multiple `Message::Consensus` entries signed by *different* relayer accounts — e.g. because a batch aggregates consensus updates for multiple state machines, each originally produced/signed by a different relayer — every state-machine advance in that batch is credited to whoever's message happens to occupy index 0, not to the actual signer of the message that produced each `StateMachineUpdated` event.

Because consensus proofs (BEEFY proofs, signed consensus messages) are broadcast data that must be publicly visible before submission/inclusion, an unprivileged party can observe other relayers' already-signed, valid `ConsensusMessage`s and simply repackage them into their own single extrinsic submission, placing one of their own (or any) validly-signed messages first. The batch executes successfully (each message's own consensus proof is independently verified by the underlying consensus client — this part is unaffected), producing legitimate `StateMachineUpdated` events for every included message, but `on_executed` pays the *entire* combined reward for the batch to the account recovered from `messages[0]` alone.

This is exactly analogous to the tiered-pricing bug's core defect pattern: a computation that should be scoped/attributed per-unit (per-tier / per-message) is instead computed against an aggregate/global view (cumulative cap / batch-wide event set) keyed off the wrong reference point (`_remainingAmount` vs. tier cap ↔ all events vs. `messages[0]`'s signer).

### Impact Explanation
This directly enables stealing of `$BRIDGE` treasury funds intended for other relayers: an unprivileged actor can redirect consensus-incentive rewards for state-machine advances they did not produce to their own account, simply by controlling message ordering/bundling in a single submission. This is a "stealing/loss of funds" and "wrong beneficiary" outcome explicitly in scope of the bounty — funds move to the wrong party with no proof forgery or privileged access required, only reordering of otherwise-legitimate, publicly-broadcast consensus messages.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires the existence of a submission path where multiple independently-signed `Message::Consensus` entries for potentially different state machines can be included and processed together in a single call (batched relaying, which the outbound-delivery documentation confirms is a normal pattern — see `docs/content/developers/explore/relayers.mdx`), and it requires that more than one signer's consensus messages land in the same processed batch. Given Hyperbridge's own documentation states relayers commonly batch multiple things together for efficiency, and that proofs are public before inclusion, an attacker capable of observing pending/broadcast consensus messages and constructing/submitting their own batch has a straightforward path to trigger this misattribution.

### Recommendation
Compute the reward payee per-message rather than once for the whole batch. Iterate over each `Message::Consensus` in `messages`, recover its own `signer`, and only attribute the `StateMachineUpdated` event(s) that resulted from *that specific message* (e.g. by correlating message order/state-machine-id to the events it produced, or by having the consensus-client/message-handling layer emit event data annotated with the originating message's signer) to that signer's reward. Do not use `messages.get(0)` as a stand-in for "the batch's relayer."

### Proof of Concept
Conceptual sequence (cannot be executed without full node/testnet access, but the code path is deterministic):
1. Relayer R1 broadcasts a validly-signed `Message::Consensus(C1)` advancing `StateMachine::Evm(1)`.
2. Relayer R2 broadcasts a validly-signed `Message::Consensus(C2)` advancing `StateMachine::Evm(2)`.
3. Attacker A observes both broadcasts (public mempool/gossip) before either lands on-chain, and submits a single extrinsic with `messages = [C_A, C1, C2]` where `C_A` is any trivially-obtainable valid consensus message signed by A (even for a low-cost/no-op advance, or reusing A's own prior valid proof).
4. `pallet-ismp` processes all three messages, each independently verified as valid, producing `StateMachineUpdated` events for `Evm(1)` and `Evm(2)` (and possibly A's own chain).
5. `on_executed` in `modules/pallets/consensus-incentives/src/impls.rs` derives `relayer_account` from `messages[0]` = A, then loops over `highest_per_state_machine` built from *all* events in the batch and calls `process_message(..., relayer_account = A)` for `Evm(1)` and `Evm(2)` too — transferring R1's and R2's rewards to A instead of them, per `T::Currency::transfer(&Treasury, &relayer_account, reward, ...)`. 	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});
