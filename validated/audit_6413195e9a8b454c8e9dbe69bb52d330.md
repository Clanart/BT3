### Title
Stale manual conflict resolutions silently reapplied to later rebase commits, causing incorrect content to be committed - (File: `app/src/lib/git/rebase.ts`, `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`updateConflictState` carries the `manualResolutions` map forward across every status refresh for as long as the rebase is in the "rebase" conflict kind, and `continueRebase` blindly reapplies whatever resolution exists for a given file `path` when the rebase stops again on a later commit. There is no invalidation of a path's resolution once it has been "spent" on one commit's conflict, so if the same file path conflicts again on a subsequent commit in the same multi-commit rebase, Desktop silently applies the user's earlier choice (ours/theirs) to the new, unrelated conflict content instead of prompting the user again.

### Finding Description
When a rebase stops due to conflicts, `getConflictState` builds a `RebaseConflictState` and `updateConflictState` decides whether to keep the previous `manualResolutions` map: [1](#0-0) 

For rebases specifically, as long as the state stays `RebaseConflictState` (i.e., the multi-commit rebase is still in progress across commits), the map is passed through untouched between refreshes: [2](#0-1) 

When the user resolves a file manually, the resolution is recorded keyed only by file `path`, with no association to which commit/tree-state it was resolved against: [3](#0-2) 

When `continueRebase` is invoked to proceed to the next commit, it iterates the `manualResolutions` map and applies `stageManualConflictResolution` to any file in the working directory that matches the stored `path`, with no check that this is the same conflict occurrence the resolution was originally made for: [4](#0-3) 

Nothing in the codebase removes an entry from `manualResolutions` once it has been consumed for one commit's conflict. If git then advances the rebase and stops again because a *later* commit in the sequence also touches the same path (a very common scenario, e.g. multiple commits editing the same file), `continueRebase` will find the stale entry still in the map and apply the old "ours"/"theirs" decision to the brand-new conflict hunk without ever surfacing it to the user in the conflicts dialog. This is the direct analog of the `forceWithdraw` bug: a piece of "accounted" state (the resolution the user has already spent) is not decremented/cleared after being consumed, so subsequent operations silently trust a stale value instead of re-deriving the truth.

### Impact Explanation
This can cause a user to unknowingly commit and push content they never reviewed or approved for a specific conflict: if the earlier resolution was `theirs`, an attacker who controls the branch being rebased onto (a git remote/fetched ref) could arrange for the same file path to conflict again with different, malicious content on a later commit, which would then be auto-resolved and committed using the stale choice without any prompt. This matches "silent corruption of what the user commits or pushes" from an attacker-controlled remote/fetched repository.

### Likelihood Explanation
Multi-commit rebases where the same file is modified across several commits are common, and Desktop already resolves per-commit rebase conflicts one at a time via `continueRebase`, so the vulnerable code path is exercised on virtually every multi-file, multi-commit conflicted rebase. No unusual user action is required beyond resolving one conflict and continuing the rebase; the second occurrence is auto-resolved without any additional confirmation dialog.

### Recommendation
Clear or invalidate a path's entry from `manualResolutions` as soon as it has been consumed by `continueRebase` (i.e., after `stageManualConflictResolution` succeeds for that step), so that if the same path conflicts again on a subsequent commit the user is required to explicitly resolve it again rather than having the prior decision silently reapplied.

### Proof of Concept
1. Start a multi-commit rebase where commit A and commit B (later in the sequence) both modify the same file `shared.txt` in conflicting ways relative to the target branch.
2. Rebase stops on commit A's conflict for `shared.txt`; user manually resolves via `_updateManualConflictResolution(repository, 'shared.txt', ManualConflictResolution.theirs)`.
3. User continues the rebase (`continueRebase`), which stages `shared.txt` per the `theirs` resolution for commit A and advances.
4. Git rebase stops again on commit B, which also conflicts on `shared.txt` with entirely different content.
5. Because `manualResolutions` still contains `'shared.txt' -> theirs` from step 2 (never cleared per `changes-state.ts:294-305`), the next call to `continueRebase` finds the stale mapping in `rebase.ts:449-458` and silently stages `shared.txt` using `theirs` for commit B's unrelated conflict — without ever showing the conflicts dialog for commit B's `shared.txt` — and the rebase (and eventual commit/push) proceeds with unreviewed content.   public _updateManualConflictResolution(
    repository: Repository,
    path: string,
    manualResolution: ManualConflictResolution | null
  ) {
    this.repositoryStateCache.updateChangesState(repository, state => {
      const { conflictState } = state

      if (conflictState === null) {
        // not currently in a conflict, whatever
        return { conflictState }
      }

      const updatedManualResolutions = new Map(conflictState.manualResolutions)

      if (manualResolution !== null) {
        updatedManualResolutions.set(path, manualResolution)
      } else {
        updatedManualResolutions.delete(path)
      }

      return {
        conflictState: {
          ...conflictState,
          manualResolutions: updatedManualResolutions,
        },
      }
    })

export async function continueRebase(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  manualResolutions: ReadonlyMap<string, ManualConflictResolution> = new Map(),
  opts?: RebaseInteractiveOptions
): Promise<RebaseResult> {
  const trackedFiles = files.filter(f => {
    return f.status.kind !== AppFileStatusKind.Untracked
  })

  // apply conflict resolutions
  for (const [path, resolution] of manualResolutions) {
    const file = files.find(f => f.path === path)
    if (file !== undefined) {
      await stageManualConflictResolution(repository, file, resolution)
    } else {
      log.error(
        `[continueRebase] couldn't find file ${path} even though there's a manual resolution for it`
      )
    }
  }

  const otherFiles = trackedFiles.filter(f => !manualResolutions.has(f.path))

  await stageFiles(repository, otherFiles)
