### Title
Integer-division truncation of `curve-exponent` in `calc-liq-factor-exp` silently collapses graduated liquidation curves to a lower linear tier, over-penalizing borrowers - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`calc-liq-factor-exp` is meant to raise the linear liquidation factor to a configurable power (`curve-exponent`, expressed in BPS, e.g. `15000` = 1.5) so that the liquidation percentage/penalty scales smoothly as LTV worsens. Because the exponent's integer part is extracted with plain integer division (`(/ exp BPS)`), any `curve-exponent` that is not an exact multiple of `BPS` (10000) is silently floored to the next-lower whole exponent, which for the common `>BPS` (aggressive-curve) case collapses back to the purely linear result — exactly the same class of "floor-division skips the intended incremental step" bug described in the NextGen `getPrice` finding.

### Finding Description
`calc-liq-factor-exp` in `v0-4-market.clar`: [1](#0-0) 

```clarity
(define-private (calc-liq-factor-exp (factor uint) (exp uint))
  (if (is-eq exp BPS) 
    factor
    (if (> exp BPS) 
        (/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))
        (sqrti (* factor BPS)))))
```

`egroup.clar`'s docs explicitly state `LIQ-CURVE-EXP` is a BPS value that can be any number `>10000` for an "aggressive curve" (penalty increases faster) [2](#0-1) , not just exact multiples of `10000`.

However, when `exp` is strictly between `k*BPS` and `(k+1)*BPS` (e.g. `exp = 15000`, intending a 1.5× curve), `(/ exp BPS)` truncates to `k = 1`. The formula then evaluates to `(pow factor 1) / (pow BPS 0) = factor`, i.e. exactly the same result as the `is-eq exp BPS` (pure-linear, 1.0×) branch. The fractional part of the configured exponent is completely discarded — any `curve-exponent` in `(10000, 20000)` behaves identically to `10000`, any value in `(20000, 30000)` behaves identically to `20000`, and so on. This is the same root cause pattern as the NextGen finding: a floor-division inside a scaling calculation causes the code to skip the intended intermediate values and jump straight to a "boundary" result.

Since `factor` (the linear liquidation percentage, `0 <= factor <= BPS`) is `<= 1` in real terms, raising it to a higher exponent (as intended by an aggressive curve) should *shrink* `liq-pct-scaled` relative to the linear value. The truncation bug instead keeps returning the *larger* linear value whenever the exponent isn't an exact multiple of BPS.

`liq-pct-scaled` directly drives two USD-denominated, price-derived outputs used inside `liquidate`: [3](#0-2) 

```clarity
(define-private (calc-liquidation-params ...)
  (let ((liq-pct-linear (calc-liq-factor current-ltv ltv-liq-partial ltv-liq-full))
        (liq-pct-scaled (calc-liq-factor-exp liq-pct-linear curve-exponent))
        (liq-penalty (calc-liq-factor-bound liq-pct-scaled liq-penalty-min liq-penalty-max))
        (max-debt-usd (calc-liq-debt-repay total-debt-usd liq-pct-scaled)))
    ...))
```

`liq-penalty` scales the liquidator's bonus multiplied onto oracle-priced collateral (`calc-liq-collateral-repay`), and `max-debt-usd` caps the oracle-priced debt eligible for liquidation — both feed straight into the seized-collateral computation used by `liquidate` [4](#0-3) .

### Impact Explanation
Whenever a DAO-configured `LIQ-CURVE-EXP` for an egroup is a valid, intentionally aggressive value that is not an exact multiple of `10000` (e.g. `12500`, `15000`, `17500`), the protocol silently applies the weaker, purely linear penalty/eligible-debt curve instead of the configured steeper one. This means:
- `liq-penalty` is computed higher than the curve design intends, so the liquidator's bonus (paid out of the borrower's price-denominated collateral) is larger than intended.
- `max-debt-usd` is computed higher than intended, letting liquidators liquidate a larger USD amount of debt (and therefore seize more collateral) than the configured curve should allow at that LTV.

The borrower systematically loses more collateral value than the risk parameters were designed to permit, and the liquidator correspondingly gains more — a direct transfer of value away from the borrower on every liquidation under an affected egroup. This is theft of user funds via a price/valuation-scaling computation error, not a misconfiguration (the configured value is valid input per the documented parameter range; the bug is in how the contract math consumes it).

### Likelihood Explanation
This triggers automatically, with no attacker action required, on every liquidation of any egroup whose DAO-approved `LIQ-CURVE-EXP` is not an exact multiple of `BPS` (10000). Given the docs frame the parameter as a general BPS value (not restricted to multiples of 10000) and show `20000` as one example, it is plausible operators would pick intermediate values (e.g. `15000`) to fine-tune curve aggressiveness, making this a realistic configuration rather than an edge case.

### Recommendation
Avoid truncating integer division on the exponent. Either:
1. Restrict `LIQ-CURVE-EXP` at the registry level to only exact multiples of `BPS` (document/enforce this), or
2. Implement fractional-exponent support properly, e.g. by decomposing `exp` into integer and fractional BPS parts and applying `sqrti`/binary-exponentiation-style interpolation for the fractional remainder instead of discarding it via `(/ exp BPS)`.

### Proof of Concept
Given `factor = 5000` (50% linear liquidation factor) and `curve-exponent = 15000` (intended 1.5× aggressive curve):

- `(is-eq exp BPS)` → false (`15000 != 10000`)
- `(> exp BPS)` → true
- `(/ exp BPS)` → `(/ 15000 10000)` → `1` (floored)
- Result: `(/ (pow 5000 1) (pow 10000 (- 1 1))) = (/ 5000 (pow 10000 0)) = (/ 5000 1) = 5000`

This is identical to the `is-eq exp BPS` branch's output of `factor` (`5000`) unmodified — i.e., the 1.5× curve configured by the DAO is silently ignored and treated as a 1.0× linear curve, inflating `liq-pct-scaled`/`liq-penalty`/`max-debt-usd` beyond what the configured curve intends, in favor of the liquidator and against the borrower.
