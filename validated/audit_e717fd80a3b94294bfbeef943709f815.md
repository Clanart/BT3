### Title
Instant, live-read `challengePeriod` lets governance shorten the dispute window for already in-flight state commitments, letting an attacker slip a malicious/stale commitment past fishermen before they can veto it - ([File: evm/src/core/HandlerV2.sol])

### Summary
The external report's core broken invariant is: a global risk parameter (`CollateralizationRatio`) can be changed instantly with no grace period, and the change is applied retroactively to already-existing positions, so a value someone relied on to stay safe can be yanked out from under them and exploited by a back-runner before they can react. The same structural pattern exists in Hyperbridge's challenge-period mechanism for state commitments.

### Finding Description
`HostParams.challengePeriod` can be updated at any time via `EvmHost.updateHostParams` / `updateHostParamsInternal` (invoked through cross-chain governance via `HostManager.onAccept`, see `evm/src/core/EvmHost.sol:573-645` and `evm/src/core/HostManager.sol:95-108`). The update takes effect immediately and unconditionally for **all already-stored state machine commitments**, not just new ones going forward.

`HandlerV2.sol` enforces the challenge-period gate by comparing the *elapsed time since the commitment was stored* against the *current, live* `challengePeriod()` value read at call time: [1](#0-0) [2](#0-1) 

The same pattern repeats in `handlePostRequestTimeouts` and `handleGetRequestTimeouts`: [3](#0-2) [4](#0-3) 

The commitment-storage timestamp is fixed once (`stateMachineCommitmentUpdateTime`), but the *duration required to pass* (`challengePeriod`) is not pinned to the value in effect when that commitment was stored — it's whatever the live `_hostParams.challengePeriod` is at the moment `handlePostRequests`/`handleGetResponses`/timeout handlers are called: [5](#0-4) 

The purpose of the challenge period is to give fishermen time to detect and veto a fraudulent/malicious state commitment before it can be used to process requests, responses, or timeouts — this is exactly the invariant called out in the Hyperbridge pivots ("Consensus proofs, state proofs, challenge periods... must never let false remote state become trusted"). The Rust ISMP core enforces the analogous check the same live-value way: [6](#0-5) 

Because `updateHostParamsInternal` performs no reconciliation against in-flight/pending commitments (no grandfathering, no minimum-of-old-and-new enforcement, no per-commitment snapshot of the challenge period that applied when it was stored), any reduction of `challengePeriod` instantly shortens (or eliminates, if set near 0) the remaining dispute window for every commitment that is currently mid-challenge — including ones deliberately stored by an attacker/relayer that fishermen have not yet had time to review under the original, longer window they were promised.

### Impact Explanation
If `challengePeriod` is lowered while a state commitment is still within its original challenge window, an attacker (or a relayer racing the parameter update) can immediately call `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, or `handleGetRequestTimeouts` against that commitment the moment the new, shorter delay is satisfied — even though fishermen were never given the originally-configured amount of time to veto it. This can result in false/unverified remote state being trusted and acted upon: requests dispatched to modules, responses delivered, or timeouts triggered based on a state commitment that has not survived its intended full dispute period, i.e., exactly the "false proof/state acceptance" impact category called out in the bounty scope.

### Likelihood Explanation
This requires only a routine, legitimate `updateHostParams` governance action (which is an expected, non-malicious operational event — protocol parameters are meant to be tunable) to occur while any state commitment happens to be inside its old, longer challenge window. Since `updateHostParamsInternal` has no awareness of or interaction with in-flight commitments, this is a structural gap rather than a rare edge case — any downward adjustment of `challengePeriod` (e.g., to reduce latency for a well-behaved consensus client) silently truncates the dispute window for every commitment already in-flight at that moment, and the exploitation step (calling the handler as soon as the shortened delay is met) is a fully permissionless, single-transaction action requiring no privileged role.

### Recommendation
Snapshot the `challengePeriod` value at the time each `StateMachineHeight` commitment is stored (alongside `_stateCommitmentsUpdateTime`) and use that snapshotted value — not the live `_hostParams.challengePeriod` — when validating delay in `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts`. Alternatively, when `updateHostParamsInternal` lowers `challengePeriod`, enforce that the new value only applies to commitments stored after the update (i.e., take `max(old, new)` for any commitment whose original challenge window has not yet elapsed), mirroring the report's recommended two-step/grace-period approach.

### Proof of Concept
1. Governance calls `updateHostParams` with `challengePeriod = 7 days` (a legitimate initial config).
2. A state commitment for `stateMachineId = X` at `height = H` is stored via `storeStateMachineCommitment`, setting `_stateCommitmentsUpdateTime[X][H] = T0`. Fishermen are expected to have 7 days to detect and veto a bad commitment.
3. One day later (`T0 + 1 day`), governance legitimately updates `challengePeriod` to `1 hour` for unrelated operational reasons via `HostManager.onAccept` → `EvmHost.updateHostParams` (`evm/src/core/EvmHost.sol:573-645`).
4. Immediately after, any permissionless caller invokes `HandlerV2.handlePostRequests` (or `handleGetResponses`/timeout variants) referencing `height = H`. The check `challengePeriod > delay` now uses the live `1 hour` value against a `delay` of `1 day`, passing trivially (`evm/src/core/HandlerV2.sol:182-185`), even though fishermen were promised — and had only used 1 of — the original 7 days to veto commitment `H`.
5. Requests/responses/timeouts tied to that commitment are processed before the originally-committed dispute window elapses, with no mechanism having warned or protected against the parameter change, mirroring the original report's back-running-after-instant-parameter-change pattern.

        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
