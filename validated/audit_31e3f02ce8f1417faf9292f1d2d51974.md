### Title
`git clone` explicitly disables Git's built-in clone-time symlink/hook protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) - ([File: app/src/lib/git/clone.ts])

### Summary
GitHub Desktop's clone implementation always runs `git clone --recursive` with the environment variable `GIT_CLONE_PROTECTION_ACTIVE` explicitly set to `'false'`. This variable is the kill-switch for Git's built-in protections against malicious repository layouts (added upstream to defend against symlinked/case-confusable `.git` directories and files placed where submodule hooks or config can be smuggled in during clone/checkout, e.g. GHSA-fixed classes of issues around CVE-2024-32002-style clone/checkout confusion). By forcing this protection off for every clone Desktop performs, an attacker who controls the content of a repository (including nested submodules) that a victim clones through Desktop can potentially reintroduce the exact class of local file write / hook execution the upstream Git protection was designed to prevent. [1](#0-0) 

### Finding Description
`clone()` builds the execution environment for every `git clone --recursive` invocation and unconditionally injects `GIT_CLONE_PROTECTION_ACTIVE: 'false'` into it: [2](#0-1) 

`GIT_CLONE_PROTECTION_ACTIVE` is the internal safety-valve Git itself uses to gate its symlink/hook-smuggling defenses that run during clone and recursive submodule checkout (protections against a `.git`-adjacent path in a submodule being replaced with a symlink or case-variant that lets a malicious repository plant executable hooks/config outside the intended clone directory). By setting this to `'false'` on every clone, Desktop is telling Git to skip that safety check entirely, for every repository the user clones — including third-party or forked repositories reached via "Clone repository", `x-github-client://openRepo/...` deep links, or CLI `github clone` invocations, all of which ultimately funnel into this same `clone()` function.

The corrupted/misconfigured value is the environment variable itself: it is hardcoded to the value that *disables* the mitigation rather than the value that *enables* it, mirroring the report's pattern of a stale/incorrect "system constant" silently defeating a protocol-level safety mechanism.

Existing guards in the file do not cover this gap:
- `isClonePathSensitive()` only checks the top-level destination directory chosen by the user; it does nothing to constrain what a malicious submodule can write to via symlink tricks inside the `.git` metadata of the repository being cloned.
- `envForRemoteOperation(url)` only manages credentials/proxy configuration, not clone safety. [3](#0-2) 

Because the attacker fully controls the content of a repository they publish (an "unprivileged" attacker in the sense of the report's valid-impact definition — the victim only has to clone/open a link to that repository), this fits the "attacker controls a cloned/fetched repository" primitive directly, and the outcome (defeating a filesystem-safety protection that Git added specifically to stop crafted repositories from writing/executing files outside the intended clone tree) matches the "file write outside the repo" / code execution impact class named as valid.

### Impact Explanation
If `GIT_CLONE_PROTECTION_ACTIVE=false` disables checks that would otherwise prevent a submodule's `.git` file/directory from being swapped for a symlink pointing outside the clone destination (the class of bug the Git-side protection exists for), a malicious repository cloned through Desktop could cause files to be written to or hooks to be executed from a location outside the intended clone directory during the automatic `--recursive` submodule checkout that Desktop always performs. This can translate into local file corruption or, in the worst case, arbitrary code execution on the victim's machine merely from cloning or "Open in Desktop"-linking to a malicious repository — no additional local access, malware, or credentials required.

### Likelihood Explanation
Likelihood is Medium-High for exposure but depends on which specific Git-side CVE(s)/mitigations `GIT_CLONE_PROTECTION_ACTIVE` gates in the bundled `dugite`/Git version, which could not be independently confirmed from the indexed code (the flag's exact semantics live in the vendored Git binary, not in this repository). What is certain from the code is that:
1. Every clone path in Desktop (UI clone dialog, CLI `github clone`, and `x-github-client://openRepo/...`/`github-mac://openRepo/...` deep links) funnels through this single `clone()` function, and
2. That function always disables this protection, with no code path that re-enables it or offers the user a choice. [4](#0-3) [5](#0-4) 

An attacker only needs to get a victim to clone or open-in-Desktop a repository they control (public repo, fork, or malicious link), which matches the report's "attacker controls a cloned/fetched repository" trigger exactly.

### Recommendation
- Do not hardcode `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. Determine why this override exists (check git history/commit message for `app/src/lib/git/clone.ts`) — if it was added to work around a compatibility issue with a specific Git version bundled by `dugite`, scope the override narrowly (e.g., only for that version) rather than unconditionally for every clone.
- If the protection must be disabled for compatibility reasons, compensate with equivalent application-level checks (e.g., detect and reject symlinked `.git` entries/submodule paths that escape the clone root) before/after the clone, similar to the existing `isClonePathSensitive()` backstop but scoped to submodule content, not just the top-level destination path.
- Add regression tests that assert clones of repositories containing submodules with symlinked or case-conflicting `.git` paths fail safely rather than writing outside the clone root.

### Proof of Concept
Conceptual PoC (exact reproduction depends on the bundled Git/dugite version's specific check gated by this flag):
1. Attacker publishes a public repository containing a submodule entry whose `.git` file (inside `.git/modules/<name>`) is crafted so that, absent Git's clone-time protection, it would resolve outside the intended submodule checkout directory (e.g., via a symlink or a case-insensitive-filesystem collision with a sensitive path).
2. Victim uses "Clone repository..." in GitHub Desktop, or clicks an `x-github-client://openRepo/https://github.com/attacker/repo` link, which is parsed by `parseAppURL` and dispatched to `openOrCloneRepository` → `dispatcher.clone` → `CloningRepositoriesStore.clone` → `git/clone.ts:clone()`. [6](#0-5) 
3. Because `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` for this invocation, the Git-side defense that would normally reject/neutralize the crafted submodule layout is skipped, and the crafted content is written to/executed from a location the protection was designed to block.

Note: I was not able to inspect the vendored `dugite`/Git source in this index to confirm the precise CVE(s) `GIT_CLONE_PROTECTION_ACTIVE` maps to, or to find the commit/PR that introduced this override in `clone.ts`; a Devin session with full repository/history access (including `git log -- app/src/lib/git/clone.ts` and the bundled Git version) would be needed to pin down the exact upstream advisory this disables and to validate a concrete exploit payload.

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
