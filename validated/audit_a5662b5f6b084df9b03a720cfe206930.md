### Title
ThresholdKeys serializes/persists the FROST secret share in cleartext - (File: crypto/dkg/src/lib.rs)

### Summary
The Jenkins Consul KV advisory (CWE-312) concerns a credential stored unencrypted in a configuration file readable by anyone with filesystem access. The analog in Serai is `ThresholdKeys::write` / `ThresholdKeys::serialize`, which emits the FROST secret share as raw scalar bytes with no encryption or wrapping, and whose output is persisted verbatim into the node's plaintext database.

### Finding Description
`ThresholdKeys::write` writes `self.core.secret_share.to_repr()` directly to the writer in cleartext at `crypto/dkg/src/lib.rs:553-555`, and `serialize()` wraps this into a `Zeroizing<Vec<u8>>` at `crypto/dkg/src/lib.rs:567-571`. The serialized blob is the value stored by the processor's `GeneratedKeysDb::save_keys` via `txn.put(...)` in `processor/src/key_gen.rs:65-84`, so the secret share rests unencrypted in the node's DB. The read side `ThresholdKeys::read` at `crypto/dkg/src/lib.rs:618` reconstitutes the share verbatim, confirming round-trip cleartext. There is no encryption-at-rest layer, masking, or sealed/encrypted envelope anywhere in the `crypto/dkg` serialization path — compare with `SigningProtocol::preprocess_internal` in `coordinator/src/tributary/signing_protocol.rs:104-134`, which explicitly XORs the cached FROST preprocess seed with a key derived from the validator's private key precisely because "the DB isn't expected to be arbitrarily readable... it isn't a proper secret store." That mitigation exists for preprocesses but not for the long-term secret shares themselves.

### Impact Explanation
Any party able to read the node's database (filesystem access, DB snapshot, backup, or a log/replication leak) directly recovers the validator's FROST secret share in usable form — a "key share recovery" impact. Combined with the same disclosure on `t` distinct validators' databases, the full group private key is reconstructed via the documented Lagrange/`dkg-recovery` path, allowing arbitrary signatures (Bitcoin spends, Substrate slash/key confirmations). This mirrors the Jenkins advisory: CWE-312, severity Medium, where the accepted attacker model is read access to stored configuration/state.

### Likelihood Explanation
Exploitation requires read access to a validator's on-disk database — a privileged-local position, not remotely reachable with only public inputs. However, the exact same threat model was already accepted in this codebase for the cached preprocess (which is XOR-encrypted before DB storage on the grounds that the DB is not a secret store). The secret share is strictly more sensitive than a preprocess seed — a leaked seed enables share recovery only if a signature is later produced with it, while a leaked share is directly usable. The inconsistency makes exposure probable wherever DB contents leak (backups, forensic capture, hosting provider access), while honest-protocol usage keeps it non-remote.

### Recommendation
Apply the same protection used for `CachedPreprocesses` to `ThresholdKeys` persistence: encrypt the serialized keys under a key derived from the validator's secret material (or an external secret store) before `txn.put`, or route `ThresholdKeys` storage through a dedicated secret-store abstraction rather than the general-purpose DB. At minimum, document on `ThresholdKeys::write`/`serialize` that the output is raw secret material that must not be persisted to non-secret storage.

### Proof of Concept
1. A validator completes PedPoP; `KeyGen` calls `GeneratedKeysDb::save_keys`, storing `substrate_keys.serialize() || network_keys.serialize()` output under `GeneratedKeysDb::key(session, group_keys)` in the plaintext DB (`processor/src/key_gen.rs:65-84`).
2. An attacker with read access to the DB locates the entry. The blob layout is deterministic: `[u32 curve_id_len][curve_id][u16 t][u16 n][u16 i][interpolation tag][secret_share repr][n × verification_share bytes]` per `crypto/dkg/src/lib.rs:538-562`.
3. The attacker feeds the bytes to `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`), which validates the share against the verification shares and returns working `ThresholdKeys` containing `core.secret_share`.
4. Repeating for `t` validators and combining via `dkg-recovery` reconstructs the group private key, yielding full signing capability.
