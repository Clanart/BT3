### Title
Copilot conflict-resolution splices unbounded, unvalidated model output into working-directory files before staging - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`UnikuraPhygitalCollection.mint()` accepted `msg.value >= required` and silently absorbed the excess with no cap, no refund, and no recovery path. The Desktop analog is in the Copilot merge-conflict resolver: `validateResolutionPaths` only checks that the *number* of hunks returned by the model matches the expected count, and `reassembleResolvedFile` only checks that a returned hunk's `resolvedContent` is non-empty and free of literal conflict markers. Neither function bounds the *size or content* of what the model returns before it is spliced verbatim into the on-disk file and `git add`-ed. The size gate that exists (`MAX_CONFLICT_CONTENT_SIZE`, `MAX_CONFLICT_LINE_LENGTH` in `getHunkSkipReason`, `app/src/lib/copilot-conflict-context.ts:281-315`) only constrains what is *sent* to the model, mirroring the report's "accepts more than required" pattern but on the output side: excess/attacker-influenced content is accepted with no upper bound and no reconciliation.

### Finding Description
The conflict-resolution pipeline is:
1. `copilot-conflict-context.ts` gathers PR titles/descriptions and commit summaries — data pulled from the GitHub API for the branches being merged — and folds them into the prompt (`formatConflictContextForPrompt`), alongside the conflicting hunk text itself.
2. The model returns JSON parsed by `parseCopilotConflictResolution` (`app/src/lib/copilot-conflict-resolution.ts:281-466`). Each hunk's `resolvedContent` is checked only for being a string and for not containing an obvious `<<<<<<<`/`=======` conflict-marker pair [1](#0-0) .
3. `validateResolutionPaths` enforces path membership and *hunk count* equality only [2](#0-1) .
4. `reassembleResolvedFile` splices each hunk's `resolvedContent` into the file in place of the marker block, with the only guard being `resolved.length > 0` [3](#0-2) .
5. `_applyCopilotConflictResolutions` in `app-store.ts` writes this reassembled content straight to disk and stages it with `git add` once the user clicks "Continue Merge" [4](#0-3) .

At no point is `resolvedContent` bounded relative to the original conflicting region (`oursContent`/`theirsContent`/`baseContent` sizes), and at no point is it diffed or highlighted against the original hunk for the user before staging. This is the same class of defect as the reported contract bug: the check that exists (`>=` for payment, `hunks.length === expectedCount` here) validates a coarse invariant while leaving the actual payload magnitude/content unconstrained, so anything the untrusted source (payer / LLM whose prompt is built from attacker-influenced repo/PR data) decides to add above the minimum is accepted and permanently retained (committed into repo history) with no recovery mechanism, exactly like the locked excess ETH.

### Impact Explanation
If a malicious collaborator crafts a PR title/description or commit message that gets pulled into the resolution prompt as trusted context (per `copilot-conflict-context.ts`), and the model can be steered by that injected text, `resolvedContent` for a hunk can carry arbitrary extra code beyond what the actual conflict warranted. Because reassembly performs no size/diff-bound check, this extra content is silently written to disk and `git add`ed as part of the "resolved" file — i.e., silent corruption of what the user ultimately commits/pushes, matching the "Valid Impact" criterion for corruption of committed/pushed content, without requiring local access, admin rights, or leaked credentials.

### Likelihood Explanation
Reaching this path requires: (a) a repository with a merge/rebase/cherry-pick conflict, (b) the user opting into "Resolve with Copilot," and (c) the model actually being influenced to return oversized/off-scope content for a hunk — the last point depends on LLM behavior and is not deterministically triggerable purely from code, which lowers certainty relative to the original strict-equality/`msg.value` bug (which was 100% deterministic). The structural gap (no bound on `resolvedContent` size/content beyond the marker-string check) is verifiable in code, but full end-to-end exploitability depends on model steerability, which I could not verify from static code alone.

### Recommendation
- Bound each hunk's `resolvedContent` length relative to its corresponding `oursContent`/`theirsContent`/`baseContent` (e.g., reject or flag resolutions whose combined length grossly exceeds the original conflicted region) inside `reassembleResolvedFile`/`validateResolutionPaths`.
- Surface a diff/highlight of Copilot's resolution vs. the original hunks in the result dialog so unexpected insertions are visible before "Continue Merge" stages them.
- Treat PR/commit text pulled from the GitHub API as untrusted input to the prompt and consider explicit delimiting/escaping to reduce prompt-injection influence on `resolvedContent`.

### Proof of Concept
Not independently reproducible from static analysis alone — full exploitation requires demonstrating that the model can be steered via PR/commit context to emit oversized `resolvedContent`. What is concretely demonstrable from code:
1. Create a repo with a conflicting hunk of `N` characters.
2. Have `parseCopilotConflictResolution` receive/mocked a resolution whose `resolvedContent` for that hunk is, say, 100x the size of the original hunk, containing unrelated code.
3. Observe that `validateResolutionPaths` and `reassembleResolvedFile` accept it unconditionally (only the hunk-count and non-empty/marker checks apply) [2](#0-1) [3](#0-2) , and it is written and `git add`ed by `_applyCopilotConflictResolutions` [4](#0-3)  without further size/content validation.
