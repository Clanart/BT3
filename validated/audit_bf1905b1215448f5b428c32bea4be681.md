### Title
lpSupply inflation via direct token donation manipulates `accMGPPerShare` and dilutes staker rewards - (File: rewards/MasterMagpie.sol)

### Summary
`_calLpSupply()` computes the reward-share denominator for any non-`vlmgp`/non-`mWomSV` pool as the raw `balanceOf(address(this))` of the staking token rather than the sum of credited `UserInfo.amount`. An unprivileged attacker can transfer staking-token dust directly to `MasterMagpie` (bypassing `_deposit`), inflating this denominator so that every subsequent `updatePool()` call — including the ones triggered inside `multiclaim`/`multiclaimSpec`/`multiclaimFor` — permanently understates `accMGPPerShare` growth for that pool.

### Finding Description
`_calLpSupply()` is defined as: [1](#0-0) 

For any staking token other than `vlmgp` or `mWomSV`, it returns `IERC20(_stakingToken).balanceOf(address(this))` instead of an internally tracked "total credited stake" value. Legitimate deposits go through `_deposit()`, which both increases `user.amount`/`user.available` and pulls tokens in via `safeTransferFrom`: [2](#0-1) 

Because ERC20 tokens can be transferred directly to any address without going through `_deposit`, an attacker can call `IERC20(stakingToken).transfer(masterMagpie, amount)` to raise `balanceOf(this)` without incrementing any `UserInfo.amount`. Any subsequent `updatePool()` call then divides the newly emitted `mgpReward` by this inflated `lpSupply`: [3](#0-2) 

`updatePool()` is invoked unconditionally, for attacker-chosen staking tokens, inside `_multiClaim`, which is reachable via the unprivileged, public `multiclaim(address[])` entrypoint: [4](#0-3) [5](#0-4) 

Since `pool.accMGPPerShare` accumulates monotonically over time (`pool.accMGPPerShare + (mgpReward * 1e12) / lpSupply`) and `pool.lastRewardTimestamp` advances irreversibly after each `updatePool()` call, the reward-rate deficit incurred while `lpSupply` is inflated can never be recovered for the interval that already elapsed — the MGP nominally "due" for that interval (per `mgpPerSec * pool.allocPoint / totalAllocPoint`) is permanently under-credited to legitimate stakers' `accMGPPerShare`-based entitlement. No modifier, `nonReentrant` guard, or accounting check in `deposit`/`withdraw`/`multiclaim` prevents an arbitrary address from inflating `balanceOf(address(this))` via a plain transfer, and `_calLpSupply()` never reconciles against `sum(UserInfo.amount)`.

### Impact Explanation
Legitimate stakers permanently lose part of the MGP yield they would otherwise have accrued for the pool during the period the inflated balance is present, because `accMGPPerShare` growth for that interval is diluted and `pool.lastRewardTimestamp` cannot be rewound. This matches the "Theft or permanent freezing of unclaimed yield" impact class: the difference between the MGP that `mgpPerSec`/`allocPoint` accounting implies should be distributed and what is actually reflected in `accMGPPerShare` becomes permanently unclaimable by any staker.

### Likelihood Explanation
Exploitation requires only an ERC20 `transfer` call to `MasterMagpie` with the pool's staking token (a receipt/LP token), which any holder can do — no roles, deposits, or special conditions besides holding the staking token are required. The effect scales with how "low-decimal"/small `totalStaked()` is relative to the donated amount; pools with small `10**stakingDecimals()` relative to typical staked amounts are more easily diluted with modest capital. The attack is repeatable on every pool that uses the default `balanceOf(this)` branch of `_calLpSupply()`.

### Recommendation
Track a dedicated internal `totalStaked[_stakingToken]` (or `pool.totalStaked`) variable that is incremented/decremented only inside `_deposit`/`_withdraw`/`_harvestAndUnstake`, and use that value in `_calLpSupply()` instead of `IERC20(_stakingToken).balanceOf(address(this))`, mirroring the approach already used for `vlmgp`/`mWomSV` (`totalSupply()` of a controlled locker contract rather than raw balance).

### Proof of Concept
1. Deploy `MasterMagpie` with a mock low-decimal ERC20 receipt token registered as a pool (`addPool`), MGP set, `mgpPerSec` and `allocPoint` configured.
2. Victim deposits `N` tokens via `deposit(stakingToken, N)`, establishing `UserInfo.amount = N` and `balanceOf(this) = N`.
3. Advance time by `t1`, call `updatePool(stakingToken)`, record `accMGPPerShare_1`.
4. Attacker (unprivileged EOA, no prior deposit) calls `stakingToken.transfer(masterMagpie, M)` where `M >> N`, then calls `multiclaim([stakingToken])` (or `updatePool` directly) to trigger `_calLpSupply()` recomputation with `lpSupply = N + M`.
5. Advance time by `t2`, call `updatePool(stakingToken)` again; record `accMGPPerShare_2`.
6. Assert `accMGPPerShare_2 - accMGPPerShare_1` (per-second growth) is materially smaller than in a control run without the attacker's donation, and that `victim`'s pending MGP (`_calMGPReward`) after the donation is permanently reduced compared to the undiluted baseline for the same elapsed time — while `mgp.balanceOf(masterMagpie)` / `mgpPerSec`-implied emission for that interval remains unchanged, showing the MGP intended for stakers is unrecoverable through `accMGPPerShare`.

    function updatePool(address _stakingToken) public whenNotPaused {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        if (block.timestamp <= pool.lastRewardTimestamp || totalAllocPoint == 0) {
            return;
        }
        uint256 lpSupply = _calLpSupply(_stakingToken);
        if (lpSupply == 0) {
            pool.lastRewardTimestamp = block.timestamp;
            return;
        }        
        uint256 multiplier = block.timestamp - pool.lastRewardTimestamp;
        uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) / totalAllocPoint;
        
        pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
        pool.lastRewardTimestamp = block.timestamp;

        emit UpdatePool(
            _stakingToken,
            pool.lastRewardTimestamp,
            lpSupply,
            pool.accMGPPerShare
        );
    }
