### Title
DoS of offer parsing/validation via griefing `Offer._get_offered_coins` heuristic matcher - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer._get_offered_coins` reconstructs which coins are "offered" in a trade by counting how many `CREATE_COIN` outputs of a spend match a set of expected amounts, and raises an unhandled `ValueError` if the count of matching additions doesn't exactly equal the expected number of matches. This is structurally the same bug class as the reported Curve issue: a strict equality/count check (`len(matching_spend_additions) == expected_num_matches`) that assumes no "extra" coins are present, which can be defeated by adding griefing outputs that collide with the expected amounts — causing denial of service to any code path that needs to parse the offer (summary, validity check, or completion).

### Finding Description
`_get_offered_coins` builds the list of coins being offered for each asset in a trade by inspecting the `CREATE_COIN` conditions of the inner puzzle of each spend in the offer's bundle, counting the number of conditions that pay to `OFFER_MOD_HASH` (`expected_num_matches`), and collecting their amounts: [1](#0-0) 

It first tries to match by amount alone, and if that count doesn't line up, falls back to filtering by puzzle hash; if it still doesn't get an exact count match it raises: [2](#0-1) 

This function is memoized via `get_offered_coins()` and is the basis for essentially every downstream computation on an offer: `get_offered_amounts()`, `arbitrage()` (which determines `is_valid()`), and `to_valid_spend()`: [3](#0-2) 

Because the matching logic depends purely on counting amounts/puzzle-hashes among the additions of a coin spend rather than deterministically identifying the exact offer-payment outputs (e.g., by a nonce or a dedicated hint), it can be confused if a spend included in the offer bundle emits an "extra" `CREATE_COIN` to `OFFER_MOD_HASH` whose amount collides with one of the values in `offered_amounts` (or an amount that is already accounted for by another expected payment) — exactly analogous to sending 1 wei of a base_pool token directly to the meta_pool to break the Curve `dx == _dx` accounting.

### Impact Explanation
If this heuristic fails, `_get_offered_coins` raises an uncaught `ValueError`. Any caller that needs to parse or evaluate an untrusted `Offer` object — e.g. a wallet or marketplace computing `Offer.summary()`, checking `is_valid()`, or a taker calling `respond_to_offer` → `calculate_tx_records_for_offer` — will fail with an unhandled exception: [4](#0-3) [5](#0-4) 

This lets an offer creator (or anyone who can shape the offer's underlying spends, e.g. via a crafted CAT/singleton spend included in the offer bundle) publish a superficially valid-looking offer file that reliably crashes any client attempting to inspect, summarize, or take it — a spend-triggered processing halt for the offer-parsing code path used by wallets and offer marketplaces.

### Likelihood Explanation
Medium. Constructing an offer bundle whose additional coin spends include an extra `CREATE_COIN` to `OFFER_MOD_HASH` with a colliding amount requires only that the attacker control the puzzle/solution of one of the coins in their own offer (which they always do as the offer maker), so no special privileges are required. The main uncertainty is how often colliding amounts naturally arise vs. need to be deliberately engineered, but since the maker fully controls conditions produced by their own spends, they can always engineer such a collision deliberately.

### Recommendation
Replace the amount/puzzle-hash heuristic in `_get_offered_coins` with a deterministic mechanism for identifying settlement payments — e.g., match by the exact `NotarizedPayment` nonce/hash used to compute `calculate_announcements`, rather than by counting coincidental amount matches. At minimum, treat a mismatch as marking that specific asset/spend's offered-coins as unresolved and reject the offer as invalid/malformed with a caught, well-defined error rather than letting a raw `ValueError` propagate to callers.

### Proof of Concept
Not independently verified with a live spend bundle (would require exercising the wallet/offer stack), but the logical trigger is: an offer maker crafts an offer whose spent coin's inner puzzle emits `(CREATE_COIN OFFER_MOD_HASH X)` for the legitimate settlement payment of amount `X`, plus a second, unrelated `CREATE_COIN OFFER_MOD_HASH X` (or an amount colliding with another asset's expected offered amount) from the same or another spend in the bundle. When any code calls `offer.get_offered_coins()` / `offer.summary()` / `offer.is_valid()`, `expected_num_matches` will no longer equal the count of `matching_spend_additions`, and `_get_offered_coins` raises `ValueError("Could not properly guess offered coins from parent spend")`, aborting processing for any caller of that offer object.     def get_offered_coins(self) -> dict[bytes32 | None, list[Coin]]:
        try:
            if self._offered_coins is not None:
                return self._offered_coins
        except AttributeError:
            object.__setattr__(self, "_offered_coins", self._get_offered_coins())
        return self._offered_coins

    def get_offered_amounts(self) -> dict[bytes32 | None, int]:
        offered_coins: dict[bytes32 | None, list[Coin]] = self.get_offered_coins()
        offered_amounts: dict[bytes32 | None, int] = {}
        for asset_id, coins in offered_coins.items():
            offered_amounts[asset_id] = uint64(sum(c.amount for c in coins))
        return offered_amounts

    def get_requested_payments(self) -> dict[bytes32 | None, list[NotarizedPayment]]:
        return self.requested_payments

    def get_requested_amounts(self) -> dict[bytes32 | None, int]:
        requested_amounts: dict[bytes32 | None, int] = {}
        for asset_id, coins in self.get_requested_payments().items():
            requested_amounts[asset_id] = uint64(sum(c.amount for c in coins))
        return requested_amounts

    def arbitrage(self) -> dict[bytes32 | None, int]:
        """
        Returns a dictionary of the type of each asset and amount that is involved in the trade
        With the amount being how much their offered amount within the offer
        exceeds/falls short of their requested amount.
        """
        offered_amounts: dict[bytes32 | None, int] = self.get_offered_amounts()
        requested_amounts: dict[bytes32 | None, int] = self.get_requested_amounts()

        arbitrage_dict: dict[bytes32 | None, int] = {}
        for asset_id in [*requested_amounts.keys(), *offered_amounts.keys()]:
            arbitrage_dict[asset_id] = offered_amounts.get(asset_id, 0) - requested_amounts.get(asset_id, 0)

        return arbitrage_dict
