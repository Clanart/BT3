### Title
Unauthenticated operator attribution in payout OP_RETURN allows a withdrawer to self-front their own withdrawal and permanently lock any operator out of reimbursement - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds the OP_RETURN output naming the reimbursing operator using only the caller-supplied `operator_xonly_pk` argument, while the withdrawer's `TapSighashType::SinglePlusAnyoneCanPay` signature (verified in `Operator::withdraw`, `core/src/operator.rs:630-637`) only ever commits to input 0 (`in_outpoint`) and output 0 (the user's own payout output), never to the OP_RETURN or to the total set of inputs/outputs. Because the withdrawer is the one who produces `in_signature` over their own `in_outpoint` in the first place, they can independently build and self-fund (i.e., pay themselves back at output 0) a competing payout transaction with an arbitrary or non-existent operator xonly pubkey in the OP_RETURN, broadcast it before any real operator, and permanently corrupt the on-chain-derived attribution that gates reimbursement.

### Finding Description
The broken binding: for withdrawal `idx`, the party credited in `withdrawals.payout_payer_operator_xonly_pk` (set in `update_finalized_payouts`, `core/src/verifier.rs:2283-2352`, from whatever OP_RETURN happens to be in the confirmed transaction spending `withdrawal_utxo`) should equal the operator that actually fronted the withdrawal amount. This is never actually enforced.

Path:
1. Attacker (the withdrawer) calls the Citrea bridge contract's withdraw with a `withdrawal_utxo` outpoint and destination `output_script_pubkey`/`output_amount` they fully control, and signs a `TapSighashType::SinglePlusAnyoneCanPay` signature over that input — they generate this signature themselves, so no operator secrecy or "capture" is even required.
2. `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) constructs `TransactionType::Payout` with input 0 = `input_utxo`, output 0 = the payout, output 2 = `op_return_txout(operator_xonly_pk.serialize())` — `operator_xonly_pk` is a plain function argument, not something the withdrawer's signature covers.
3. `calculate_pubkey_spend_sighash`/`taproot_key_spend_signature_hash` (`core/src/builder/transaction/txhandler.rs:210-233`) for `SinglePlusAnyoneCanPay` commits only to input 0's outpoint/value/scriptPubKey and to output 0's content (confirmed by the BIP341 encoder at `circuits-lib/src/bridge_circuit/mod.rs:750-810`, which skips `sha_outputs` for `Single` and skips prevouts/sequences hashing for `anyone_can_pay`). Nothing else in the transaction — additional inputs, output count, or the OP_RETURN — is bound by the signature.
4. Since output 0 must exactly match what the withdrawer already agreed to receive, the withdrawer can self-fund the transaction with their own UTXOs (getting that same value back to themselves at output 0) and stamp any OP_RETURN they want (a real but non-participating operator's key, or 32 random bytes that fail `XOnlyPublicKey::from_slice`, yielding `None`), at a cost of only the miner fee.
5. Whichever transaction confirms first wins the double-spend on `withdrawal_utxo`. `update_finalized_payouts` records that transaction's OP_RETURN content verbatim as `payout_payer_operator_xonly_pk`, with no check that a real operator authorized or funded it (`core/src/verifier.rs:2319-2321`).
6. `is_kickoff_malicious` (`core/src/verifier.rs:1887-1890`) and the bridge-circuit's `deposit_constant`/`host_deposit_constant` (`bridge-circuit-host/src/structs.rs:500-503`, `circuits-lib/src/bridge_circuit/mod.rs:216-219`) both hard-bind the reimbursing operator identity to this same OP_RETURN content parsed straight from the confirmed payout transaction. If it names a bogus/non-existent key, no operator's xonly_pk can ever equal it, so no operator can ever pass the disprove-circuit check or the verifiers' malicious-kickoff check for that deposit.

Existing guards checked and why they don't help: `SECP.verify_schnorr` in `Operator::withdraw` (`core/src/operator.rs:632-637`) only checks the user's signature is valid for the constructed sighash — it doesn't stop the withdrawer from constructing a different transaction with the same valid signature and a different OP_RETURN, because the signature never bound the OP_RETURN in the first place. `is_kickoff_malicious` and the bridge circuit's deposit-constant check operate purely on whatever is already on-chain — they cannot detect that the attribution was forged rather than genuine, they only enforce that it be self-consistent.

### Impact Explanation
Once the attacker's self-funded transaction with a bogus/foreign OP_RETURN confirms and is scanned by `update_finalized_payouts`, `withdrawals.payout_payer_operator_xonly_pk` for that withdrawal index is permanently fixed. Every operator's future kickoff for the corresponding deposit will be flagged malicious by verifiers (`is_kickoff_malicious`) and will fail the bridge circuit's `deposit_constant` check, since none of them can ever match the forged/non-existent xonly pubkey. This permanently blocks any operator — honest or otherwise — from ever being reimbursed for that deposit's move-to-vault UTXO, matching the Critical category "an honest operator permanently unable to be reimbursed" / "a move-to-vault UTXO permanently frozen." It is repeatable per withdrawal/deposit and is independent of which operator(s) would have serviced it.

### Likelihood Explanation
The attacker needs no privileged role: they are simply the withdrawer, who by definition already produces and controls `in_signature`/`in_outpoint`/`output_script_pubkey`/`output_amount`. They need enough of their own BTC to temporarily fund the payout output (which comes right back to themselves at output 0), plus a normal miner fee — no capital is actually lost besides fees. This can be executed proactively, before any operator has even reacted to the Citrea withdrawal event, so no race against a specific operator's broadcast is even required. This is straightforward to reproduce on regtest.

### Recommendation
Bind the operator attribution to something the withdrawer's signature (or a separate authenticated channel) actually commits to — e.g., require `SIGHASH_ALL` (or a custom covenant covering all outputs) for the payout input so the OP_RETURN cannot be swapped, or have the aggregator's/verifiers' registered "known txid" for that withdrawal (the one they actually observed being broadcast by a specific operator via `TxSender`) be the source of truth for attribution instead of blindly trusting whatever OP_RETURN is found in the first confirmed transaction spending `withdrawal_utxo`.
