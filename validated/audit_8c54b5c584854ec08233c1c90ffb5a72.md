### Title
PedPoP blame proof leaks a reused message’s ECDH key before PoP verification - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` decrypts each submitted `EncryptedMessage` and immediately returns an `EncryptionKeyProof` if the decrypted share is not a canonical scalar, before the batched Schnorr proof-of-possession for `msg.key` has been verified. [1](#0-0) 

### Finding Description
`EncryptedMessage::read` accepts attacker-controlled `key`, `pop`, and encrypted `msg` fields. [2](#0-1)  `Encryption::decrypt` queues `pop` for later batch verification, computes `ecdh(self.enc_key, msg.key)`, decrypts the message, and returns an `EncryptionKeyProof` containing that ECDH point and a DLEq proof. [3](#0-2)  The caller uses that proof immediately when `SecretShare` bytes do not decode to a canonical scalar, without first executing `batch.verify_with_vartime_blame()` and therefore without first rejecting an invalid or copied `pop`. [4](#0-3) 

The code explicitly identifies this disclosure pattern as dangerous: revealing `bX` for an attacker-reused encryption key can reveal an unrelated message encrypted under that same ECDH key. [5](#0-4)  The PoP is intended to prevent this, but the early canonical-scalar error path bypasses the PoP check and emits the blame proof anyway. [6](#0-5) 

### Impact Explanation
An attacker can copy the public `key`, `pop`, and ciphertext from an honest participant’s encrypted share to the victim, then flip ciphertext bits so the plaintext becomes a noncanonical scalar. [7](#0-6)  The victim returns a publicly serializable `EncryptionKeyProof` for the copied `msg.key`, exposing the ECDH shared point for the original ciphertext. [8](#0-7)  Because the ChaCha20 key is derived only from the protocol context and that shared point, anyone receiving the blame proof can decrypt the original honest share. [9](#0-8)  Disclosure of DKG secret shares can enable key-share/key recovery when combined with enough exposed shares and therefore crosses the secret-disclosure boundary. [10](#0-9) 

### Likelihood Explanation
The attacker only needs to supply a malformed encrypted share through the normal `EncryptedMessage::read` / `calculate_share` path; no filesystem, private-key, or validator-secret access is required. [11](#0-10)  ChaCha20 is malleable, so an attacker who observed a ciphertext can predictably change its plaintext bits while reusing its public ECDH key, making the victim reach the noncanonical-scalar branch before PoP batch verification. [12](#0-11) 

### Recommendation
Do not create or return an `EncryptionKeyProof` until the message’s PoP has been verified. [13](#0-12)  Restructure `calculate_share` so PoP verification completes before scalar decoding, or make `Encryption::decrypt` return a pending proof that is only disclosed after `batch.verify_with_vartime_blame()` confirms `BatchId::Decryption(from)`. [1](#0-0)  Add a regression test that reuses an honest ciphertext’s `key`, mutates `msg` into a noncanonical scalar, and asserts `calculate_share` reports `InvalidShare` with `blame: None` rather than revealing the ECDH key. [14](#0-13) 

### Proof of Concept
Conceptually, let `honest_msg: EncryptedMessage<C, SecretShare<C::F>>` be an honest encrypted share addressed to the victim. Construct:

```rust
let mut forged = honest_msg.clone();

// Keep honest_msg.key and honest_msg.pop.
// Flip ciphertext bits so the plaintext becomes a non-canonical field encoding.
for byte in forged.msg.as_mut().as_mut() {
  *byte = 0xff;
}

let mut shares = normal_shares_for_victim();
shares.insert(attacker_participant, forged);

match victim_machine.calculate_share(&mut rng, shares) {
  Err(PedPoPError::InvalidShare { participant, blame: Some(proof) })
    if participant == attacker_participant =>
  {
    // Vulnerable: `proof` contains the ECDH point for honest_msg.key even though
    // honest_msg.pop is bound to the honest sender, not attacker_participant.
    let key = proof.key; // exposed ECDH result
    // derive cipher(context, key) and decrypt honest_msg.msg
  }
  _ => {}
}
```

The vulnerable ordering is that the proof is produced at `decrypt` and returned on the noncanonical-scalar branch, while the queued PoP is only checked later by `batch.verify_with_vartime_blame()`. [1](#0-0)

  pub fn calculate_share<R: RngCore + CryptoRng>(
    mut self,
    rng: &mut R,
    mut shares: HashMap<Participant, EncryptedMessage<C, SecretShare<C::F>>>,
  ) -> Result<BlameMachine<C>, PedPoPError<C>> {
    validate_map(
      &shares,
      &self.params.all_participant_indexes().collect::<Vec<_>>(),
      self.params.i(),
    )?;

    let mut batch = BatchVerifier::new(shares.len());
    let mut blames = HashMap::new();
    for (l, share_bytes) in shares.drain() {
      let (mut share_bytes, blame) =
        self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
      let share =
        Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
          PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
        })?);
      share_bytes.zeroize();
      *self.secret += share.deref();

      blames.insert(l, blame);
      batch.queue(
        rng,
        BatchId::Share(l),
        share_verification_statements::<C>(self.params.i(), &self.commitments[&l], share),
      );
    }
    batch.verify_with_vartime_blame().map_err(|id| {
      let (l, blame) = match id {
        BatchId::Decryption(l) => (l, None),
        BatchId::Share(l) => (l, Some(blames.remove(&l).unwrap())),
      };
      PedPoPError::InvalidShare { participant: l, blame }
    })?;

/// An encrypted message, with a per-message encryption key enabling revealing specific messages
/// without side effects.
#[derive(Clone, Zeroize)]
pub struct EncryptedMessage<C: Ciphersuite, E: Encryptable> {
  key: C::G,
  // Also include a proof-of-possession for the key.
  // If this proof-of-possession wasn't here, Eve could observe Alice encrypt to Bob with key X,
  // then send Bob a message also claiming to use X.
  // While Eve's message would fail to meaningfully decrypt, Bob would then use this to create a
  // blame argument against Eve. When they do, they'd reveal bX, revealing Alice's message to Bob.
  // This is a massive side effect which could break some protocols, in the worst case.
  // While Eve can still reuse their own keys, causing Bob to leak all messages by revealing for
  // any single one, that's effectively Eve revealing themselves, and not considered relevant.
  pop: SchnorrSignature<C>,
  msg: Zeroizing<E>,

fn ecdh<C: Ciphersuite>(private: &Zeroizing<C::F>, public: C::G) -> Zeroizing<C::G> {
  Zeroizing::new(public * private.deref())
}

// Each ecdh must be distinct. Reuse of an ecdh for multiple ciphers will cause the messages to be
// leaked.
fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res
}
