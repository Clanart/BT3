## Title
Uncontrolled recursion in wallet puzzle-driver matching/merkle-tree code causes a crash when parsing an attacker-crafted offer or custody puzzle - (File: `chia/wallet/outer_puzzles.py`, `chia/wallet/cat_wallet/cat_outer_puzzle.py`, `chia/wallet/nft_wallet/singleton_outer_puzzle.py`, `chia/wallet/nft_wallet/ownership_outer_puzzle.py`, `chia/wallet/nft_wallet/metadata_outer_puzzle.py`, `chia/wallet/vc_wallet/cr_outer_puzzle.py`, `chia/wallet/util/merkle_tree.py`, `chia/wallet/util/curry_and_treehash.py`)

### Summary
CVE-2019-15144 is a DjVuLibre stack-overflow crash caused by an unbounded, attacker-controlled recursive sort routine. The same bug class — Python-level uncontrolled recursion driven by attacker-controlled nesting depth, with no depth cap — exists in several chia wallet code paths that process untrusted puzzle reveals and puzzle-hash inputs supplied by an offer counterparty or via custody puzzle construction.

### Finding Description
The wallet's "outer puzzle driver" framework recursively unwraps nested puzzle layers (CAT, singleton, ownership, metadata, credential-restricted/CR) with no recursion-depth limit. `match_puzzle()` in [1](#0-0)  iterates drivers and each driver's `match()` recursively calls back into `match_puzzle` on its inner puzzle for every additional layer, e.g. in `CATOuterPuzzle.match()` [2](#0-1) , `SingletonOuterPuzzle.match()` [3](#0-2) , `OwnershipOuterPuzzle.match()` [4](#0-3) , `MetadataOuterPuzzle.match()` [5](#0-4) , and `CROuterPuzzle.match()` [6](#0-5) . The same recursive pattern also applies to `get_inner_puzzle()`, `get_inner_solution()`, `construct()`, and `solve()` across these drivers.

This machinery is invoked on attacker-supplied puzzle reveals when a wallet parses an offer received from a counterparty: `Offer._get_offered_coins()` calls `match_puzzle(parent_puzzle)` on every `parent_spend.puzzle_reveal` taken directly from the untrusted `SpendBundle` [7](#0-6) . A counterparty can construct a puzzle reveal with an arbitrarily deep chain of curried CAT/singleton/ownership/metadata/CR layers (each layer is cheap to construct and does not require executing CLVM, only currying), so the depth of Python-level recursion in `match_puzzle`/`get_inner_puzzle`/`get_inner_solution` is entirely attacker-controlled and unbounded, exactly analogous to the unbounded `GArrayTemplate<TYPE>::sort` recursion in the CVE.

A related, independently unbounded recursion exists in `chia/wallet/util/merkle_tree.py`: `MerkleTree._root()` and `MerkleTree._proof()` recurse once per bisection of the node list with no depth cap [8](#0-7) . `MerkleTree` is used to build clawback puzzles and multi-of-n custody puzzles (`MofN._merkle_tree`, `puzzle()`, `solve()`) from lists whose size is derived from user/offer-supplied data [9](#0-8) . Likewise `curried_values_tree_hash()` in `chia/wallet/util/curry_and_treehash.py` recurses once per curried argument with no bound [10](#0-9) , unlike the deliberately-iterative `sha256_treehash()` implementation that the codebase itself documents as existing specifically "so we don't have to worry about blowing out the python stack" [11](#0-10) .

### Impact Explanation
A malicious offer counterparty (or a malicious custody puzzle-reveal) can craft a spend bundle/puzzle whose nesting depth exceeds Python's default recursion limit. When the victim wallet processes the offer (e.g., displaying an offer summary, computing offered coins, or accepting the trade), the recursive `match_puzzle`/`get_inner_puzzle`/`get_inner_solution`/`construct` chain raises `RecursionError`, crashing wallet request handling for that offer and denying service to the local wallet process/RPC caller — a spend/offer-triggered transaction-processing halt, matching the bug class of the reference CVE (uncontrolled recursion → crash on attacker-supplied data).

### Likelihood Explanation
The attack requires only sending a crafted offer file/spend bundle to a wallet user, or otherwise getting a deeply nested puzzle reveal in front of `match_puzzle()` — actions well within reach of an unprivileged offer counterparty with no special privileges, matching the allowed threat model (offer counterparty / wallet user). Constructing such a puzzle requires only repeated `curry()` calls (cheap, no CLVM execution/cost accounting bounds this recursion), making the exploit low-cost and easy to reproduce.

### Recommendation
- Add an explicit maximum unwrap depth to `match_puzzle`, `get_inner_puzzle`, `get_inner_solution`, `construct`, and `solve` in the driver framework (`chia/wallet/outer_puzzles.py` and all `*_outer_puzzle.py` drivers), returning a clean error/`None` instead of recursing unboundedly.
- Convert `MerkleTree._root()`/`_proof()` in `chia/wallet/util/merkle_tree.py` to iterative implementations, mirroring the pattern already used for `sha256_treehash()`.
- Convert `curried_values_tree_hash()` in `chia/wallet/util/curry_and_treehash.py` to an iterative implementation, or cap the number of curried arguments processed.
- Wrap offer-summary/offer-parsing entry points (`Offer._get_offered_coins`, `Offer.__post_init__`) to catch `RecursionError` and convert it into a validation error rather than letting it propagate and crash the RPC/wallet process.

### Proof of Concept
1. Build a puzzle reveal `P` by repeatedly wrapping an inner ACS puzzle with `construct_cat_puzzle`/`CAT_MOD.curry`, `SINGLETON_TOP_LAYER_MOD.curry`, or `puzzle_for_ownership_layer` several thousand times (each wrap is a cheap `curry()` call, no CLVM execution needed).
2. Place `P` as the `puzzle_reveal` of a `CoinSpend` inside a `WalletSpendBundle`, and package it as an `Offer` (`chia/wallet/trading/offer.py`).
3. Send the resulting offer file to a victim wallet and have it call any code path that invokes `match_puzzle()`/`_get_offered_coins()` on the offer (e.g. viewing the offer summary or accepting the trade).
4. Observe the victim wallet raise `RecursionError` inside the recursive `match()`/`get_inner_puzzle()` chain, aborting the offer-processing request.

    def solve(self, spends_to_prove: dict[bytes32, ProvenSpend]) -> Program:
        assert len(spends_to_prove) == self.m, "Must prove as many spends as the M value"
        if self.m == self.n:
