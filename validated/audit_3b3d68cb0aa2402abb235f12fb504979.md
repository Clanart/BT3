### Title
Fee-amortization underflow in `created_output` panics the UTXO scheduler, halting all payments for a multisig - (File: processor/src/multisigs/scheduler/utxo.rs)

### Summary
Analogous to the `KangarooVault` finding (`totalFunds - usedFunds` underflow freezing withdrawals), Serai's UTXO scheduler subtracts the pre-fee expected amount from the post-fee actual amount (`actual - expected`) instead of the reverse. Since branch outputs are always created with `actual <= expected` (the fee is deducted), any fee deduction causes a `u64` underflow panic inside `created_output`, crashing the scheduler path and freezing that multisig's queued payments.

### Finding Description
When a plan contains more payments than fit in a single transaction (`N::MAX_OUTPUTS`), `schedule`/`execute` creates an intermediate "branch" output whose value funds a queue of child payments (`self.plans`/`self.queued_plans`, keyed by amount). When that branch output is later observed on-chain, `created_output` is called with the `expected` (pre-fee) amount and the `actual` (post-fee) amount, as reported via `PostFeeBranch { expected: initial_amount, actual: ... }` in `prepare_send`. The code then computes the fee to amortize as:

```rust
let mut to_amortize = actual - expected;
```

at `processor/src/multisigs/scheduler/utxo.rs:485`. But `actual` is the branch output value *after* fees were deducted in `prepare_send` (`payment.balance.amount.0 -= subtractable`, `processor/src/networks/mod.rs:493`), so `actual < expected` whenever any nonzero fee was amortized — the normal case. The subtraction underflows and panics. The intended value is `expected - actual` (the fee incurred), matching the comment "Amortize the fee amongst all payments underneath this branch" and the following check `payments.sum() < to_amortize`.

### Impact Explanation
`created_output` is invoked while processing scanned outputs for an active multisig. The panic aborts the processor's scheduler handling for that multisig. All queued child payments under that branch — which correspond to user burns/withdrawals — are never scheduled, and on restart the persisted scheduler state (`txn.put(scheduler_key...)`) still triggers the same panic when the branch output is handled, permanently wedging payment execution for that multisig instance, mirroring the vault finding's "cannot close trades / users cannot withdraw" outcome.

### Likelihood Explanation
The trigger is routine protocol operation, not attacker-specific: any unprivileged user issuing burns creates payments; once queued payments exceed `N::MAX_OUTPUTS` per plan, a branch output is created with a fee deducted, making `actual < expected` and guaranteeing the underflow when `created_output` runs. The only escape is `actual == expected` (zero fee), which cannot occur since `needed_fee >= DEFAULT_MIN_RELAY_TX_FEE` is enforced in `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:211`).

### Recommendation
Replace `let mut to_amortize = actual - expected;` with `let mut to_amortize = expected - actual;` (or `expected.checked_sub(actual)` with an explicit error path), so the value amortized is the fee actually charged rather than a negative amount.

### Proof of Concept
1. Users issue more than `N::MAX_OUTPUTS` payments for a multisig, so `schedule` creates a plan paying a branch address (`payments.insert(0, Payment { address: branch_address, ... })`, `utxo.rs:249`).
2. `prepare_send` computes a nonzero `tx_fee`, amortizes it across the branch payment, and records `PostFeeBranch { expected: initial_amount, actual: Some(initial_amount - fee) }` (`processor/src/networks/mod.rs:493`, `508-515`).
3. When the branch output confirms, `created_output` is called with `expected = initial_amount`, `actual = initial_amount - fee`.
4. `actual - expected` = `u64` underflow → panic → scheduler aborts; all payments under that branch (and subsequent scheduling) are stuck.
