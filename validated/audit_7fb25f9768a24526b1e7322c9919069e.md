### Title
Reachable panic on unvalidated `Participant` index in PedPoP blame evaluation causes denial of service - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
Analogous to CVE-2026-63140 (reachable assertion → process termination via a crafted request), Serai's PedPoP DKG contains reachable panics in the blame path. `BlameMachine::blame` / `AdditionalBlameMachine::blame` accept attacker-supplied `sender`/`recipient` `Participant` values and index `HashMap`s with them (`self.commitments[&sender]` in `blame_internal`, `self.enc_keys[&decryptor]` in `Decryption::decrypt_with_proof`) without checking the participant is within `1 ..= n`. A `Participant` value greater than `n` (any nonzero `u16` deserializes successfully) causes a panic, crashing the node evaluating the blame proof.

### Finding Description
`AdditionalBlameMachine::blame` (crypto/dkg/pedpop/src/lib.rs:674) forwards `sender`, `recipient`, an `EncryptedMessage`, and an optional `EncryptionKeyProof` to `blame_internal` (lib.rs:575). `blame_internal` first calls `Decryption::decrypt_with_proof` (crypto/dkg/pedpop/src/encryption.rs:366), which verifies the message's per-message Schnorr PoP and, if a proof is present, evaluates `self.enc_keys[&decryptor]` at encryption.rs:388 — a `HashMap` `Index` access that **panics** if `decryptor` (the `recipient`/`accuser` parameter) was not registered, i.e. any `Participant` outside `1 ..= n` or one whose registration was removed. If the decrypted payload parses as a canonical scalar, `blame_internal` then evaluates `self.commitments[&sender]` at lib.rs:599, which **panics** for any `sender` not among the DKG participants.

No bounds check on `sender` or `recipient` exists anywhere in `blame`, `blame_internal`, or `decrypt_with_proof`. `Participant` is only guaranteed nonzero (`Participant::new` rejects 0); values `> n` are representable and parseable from message bytes. The PoP signature check does not bind to a registered participant either: `pop_challenge` binds `from` into the challenge, but `from` is the same attacker-supplied `sender` passed in by the caller, so an attacker simply crafts the PoP for their chosen out-of-range index.

### Impact Explanation
A single crafted blame/accusation message causes an unconditional panic in the victim's key-management code path. In Rust nodes not catching panics, this aborts the thread/process performing blame evaluation, mirroring the Elasticsearch assertion-failure DoS: one request from a low-privilege participant terminates node availability. Since `AdditionalBlameMachine::new` explicitly supports evaluation by parties who were *not* DKG members (any observer processing `VerifyBlame`-style accusations), the crash can hit third-party evaluators too.

### Likelihood Explanation
Exploitation requires the attacker to produce:
- An `EncryptedMessage` whose Schnorr PoP verifies under `msg.key` — trivial by choosing `k` and setting `key = k*G`, then signing `pop_challenge(context, R, key, sender, ciphertext)` with `sender = Participant::new(n + k)` (deserialization only rejects 0).
- A valid `EncryptionKeyProof` — the attacker, acting as `recipient`, knows their own encryption scalar and computes the ECDH point `enc_key * msg.key` plus a DLEq over `[G, msg.key]`, which `dleq.verify` accepts.
- The decrypted body must be a canonical `C::F` — the attacker knows the shared key and therefore controls the keystream-decrypted plaintext entirely.

At that point `blame_internal` reaches `self.commitments[&sender]` with an out-of-range key and panics (the earlier `enc_keys[&decryptor]` requires `recipient` to be a real participant, which the attacker is). Cost: one message, no race, no collusion.

### Recommendation
Validate `sender` and `recipient` against the registered participant set at the top of `BlameMachine::blame`, `AdditionalBlameMachine::blame`, and `Decryption::decrypt_with_proof`; return a `PedPoPError`/`DecryptionError` instead of indexing. Replace `self.commitments[&sender]` and `self.enc_keys[&decryptor]` with `HashMap::get` and map `None` to a fault verdict (e.g. blame the party referencing a nonexistent participant).

// Build EncryptionKeyProof { key: ecdh_point, dleq } over [G, msg.key] proving
// log_G(enc_pub_key) == log_{msg.key}(ecdh_point) — attacker holds enc_key, proof verifies.

// Victim evaluates:
additional_blame_machine.blame(fake_sender, attacker_i, crafted_msg, Some(crafted_proof));
// decrypt_with_proof: pop verifies; enc_keys[&attacker_i] exists; DLEq verifies;
// ciphertext decrypts to canonical F::ONE.
