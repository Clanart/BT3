Based on my investigation, I found a concrete, provable local analog: **the Tron deployment of `IntentGatewayV2` lacks the reentrancy guard that the mainline EVM `IntentGatewayV2` was specifically hardened with after a documented fee/escrow-theft reentrancy exploit.**

### Title
Missing reentrancy guard in Tron `IntentGatewayV2` allows cross-function re-entry during order fill/withdrawal token transfers - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The canonical EVM `IntentGatewayV2` contract imports `ReentrancyGuardTransient` and applies `nonReentrant` to `placeOrder`, and its fill logic was patched with a Checks-Effects-Interactions (CEI) fix — setting `_filled[commitment] = msg.sender` at the very top of `_fillSameChain`/`_fillCrossChain`, *before* any native ETH transfer to the beneficiary [1](#0-0) [2](#0-1) . Dedicated regression tests in `IntrinsicIntentsReentrancyTest.sol` document that *before* this fix, a malicious beneficiary could re-enter `fillOrder` during the `beneficiary.call{value: ...}("")` ETH transfer to steal escrowed transaction fees or entire input escrows [3](#0-2) [4](#0-3) .

The Tron variant of the identical contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, has **no `ReentrancyGuard`/`nonReentrant` import or usage anywhere in the file or directory** (confirmed via repository-wide search restricted to `evm/tron/**`, which returned zero matches for `nonReentrant|ReentrancyGuard`) [5](#0-4) . Its `withdraw` internal function performs the same untrusted external calls — a raw `beneficiary.call{value: amount}("")` for native tokens and a low-level `token.call(...)` for ERC-20 transfers — while only setting `_filled[body.commitment] = beneficiary` unconditionally at its own top, with no contract-wide reentrancy lock protecting the surrounding `fillOrder`/`placeOrder`/`cancelOrder` entry points [6](#0-5) .

### Finding Description
The per-commitment `_filled[commitment]` check only prevents re-entering the *same* order's fill/withdraw path. It does not stop an attacker-controlled beneficiary (native ETH `receive()`) or malicious ERC-20 token (with hooks/callback semantics) from re-entering **other** state-mutating entry points during the `.call` in `withdraw()` — e.g., `placeOrder` (which increments the global `_nonce` and computes commitments) or `fillOrder` for a *different* commitment that touches shared/global accounting such as protocol dust, treasury sweeps, or fee-token balances. This is exactly the broken invariant in the external report: a state-mutating function reachable via an external call sequence lacks a guard, so it "can change important contract state and interfere with other functions that don't expect this to happen." The mainline EVM contract closed this exact class of bug with `ReentrancyGuardTransient`; the Tron port does not carry that protection, despite reusing the same escrow/withdraw code shape and the same external `.call` interaction points.

### Impact Explanation
Cross-function reentrancy through the unguarded native/ERC-20 transfer callbacks in `withdraw()` can be used to interleave a second `placeOrder`, `fillOrder`, or dust-sweep call mid-transaction, corrupting shared state (nonce sequencing, dust/fee accounting, or escrow bookkeeping) before the outer call completes. Depending on the interleaving, this can lead to double-processing of protocol fee/dust transfers or manipulation of escrow amounts recorded for unrelated orders — i.e., fund loss or wrong-beneficiary/wrong-amount transfers, matching the bounty's "stealing or loss of funds" and "logic attacks" categories.

### Likelihood Explanation
The attack is reachable by any unprivileged solver or beneficiary who controls a contract address as the order beneficiary or supplies a malicious ERC-20 as an input/output token — no relayer, prover, or admin compromise is required, matching the "public entrypoint, unprivileged attacker" requirement. The mainline codebase's own test suite proves this exact call-shape (`beneficiary.call{value:...}("")` during fill) is exploitable without a guard; the Tron contract has that identical unguarded call shape.

### Recommendation
Add a `ReentrancyGuard`/`ReentrancyGuardTransient` (or a contract-wide transient lock) to `evm/tron/contracts/apps/IntentGatewayV2.sol` and apply `nonReentrant` to all public entry points (`placeOrder`, `fillOrder`, `cancelOrder`, and any dust-sweep/admin function that transfers funds), mirroring the fix already applied to `evm/src/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Attacker deploys a malicious beneficiary/token contract analogous to `ReentrantBeneficiary` in `IntrinsicIntentsReentrancyTest.sol` [7](#0-6) .
2. Attacker places/fills an order on the Tron `IntentGatewayV2` such that the beneficiary receives a native-token transfer inside `withdraw()` [8](#0-7) .
3. During the `beneficiary.call{value: amount}("")`, the attacker's `receive()` re-enters `placeOrder` (or a second `fillOrder` for a different commitment) since no `nonReentrant` guard exists anywhere in the contract.
4. The reentrant call mutates shared state (`_nonce`, dust accounting, or another order's escrow) before the outer `withdraw()` call finishes, producing inconsistent bookkeeping that a subsequent legitimate call can exploit for fund loss.

Note: I was not able to fully read the Tron contract's `fillOrder`/`_fillSameChain` equivalent body (ran out of tool iterations before retrieving it), so the exact interleaving details for that specific function are inferred from the structurally identical mainline contract and the confirmed absence of any reentrancy guard in the entire `evm/tron` directory. A background engineer should read the full `evm/tron/contracts/apps/IntentGatewayV2.sol` fill/cancel functions to confirm the precise reentrant call graph before patching.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];

            address feeToken = IDispatcher(host()).feeToken();

            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
