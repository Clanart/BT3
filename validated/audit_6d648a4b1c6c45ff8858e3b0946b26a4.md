### Title
Missing zero-address validation on withdrawal beneficiary permanently burns escrowed native-token funds - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw` and its Tron counterpart `IntentGatewayV2.withdraw` derive the payout `beneficiary` directly from a `bytes32` field (`body.beneficiary`) supplied by order data, with no check that it decodes to a non-zero address, before pushing native-token escrow via a raw `.call{value: amount}("")`.

### Finding Description
`_withdraw` computes the beneficiary purely by truncation and never validates it: [1](#0-0) 

The same unguarded pattern exists in the Tron variant's `withdraw`: [2](#0-1) 

`body.beneficiary` traces back to `order.user` (bytes32), which is supplied by the order-placing account when calling the public `placeOrder` entrypoint, and is later propagated unchanged into refund/cancel paths such as `_cancelFromDest` and `_cancelSameChain`: [3](#0-2) [4](#0-3) 

A raw `CALL` with value to `address(0)` succeeds in the EVM (no code, no revert) — unlike ERC20 `_mint`/`transfer`, which OpenZeppelin explicitly guards against a zero recipient. This is the exact bug class from the external report: a public-facing address-bearing parameter (here, `order.user`, which seeds the refund `beneficiary`) has no zero-address check anywhere in the placement or withdrawal path.

### Impact Explanation
If `order.user` is ever `bytes32(0)` (through a client bug, malformed order construction, or fee-token/native-only order where the "user" field is never meant to be redeemed as an address) and that order is later cancelled/refunded through `_cancelSameChain`, `_cancelFromDest`, or the destination `onGetResponse`/`withdraw` path, the escrowed native ETH is sent to `address(0)` and is permanently and irrecoverably lost — matching the report's "user positions become permanently locked" impact, except here it's an unconditional fund burn rather than a revert-based lock.

### Likelihood Explanation
Likelihood depends entirely on whether `placeOrder` (not fully reviewed within the available context) rejects `bytes32(0)` for `order.user`. I could not verify this constraint from the indexed code, so I cannot assert with certainty that this path is reachable by an ordinary user without any privileged actor. This is the main open question that would need to be resolved by reading `evm/src/apps/IntentGatewayV2.sol`'s `placeOrder` function directly (recommend a Devin session with full file access, since the index may not contain the complete function body).

### Recommendation
Add an explicit zero-address / zero-`bytes32` check on `order.user` at `placeOrder` time, and defensively re-validate `beneficiary != address(0)` inside `_withdraw` / `withdraw` before executing the native-token `.call` or ERC20 `safeTransfer`, reverting instead of silently succeeding.

### Proof of Concept
Not independently reproduced — this requires confirming that `placeOrder` (evm/src/apps/IntentGatewayV2.sol) accepts an order with `user = bytes32(0)`. If confirmed, the PoC would be: place a same-chain order with `order.user = bytes32(0)`, then call `cancelOrder`, which routes to `_cancelSameChain` → `_withdraw`, sending the escrowed native token to `address(0)` and burning it irrecoverably.

        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        if (orderSource != currentChain) revert WrongChain();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
