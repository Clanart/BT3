## Finding [1](#0-0) 

### Title
Unrestricted `CallDispatcher.dispatch()` allows any unprivileged address to drain funds held by the shared bridge call-execution utility - (`evm/src/utils/CallDispatcher.sol`)

### Summary
The external report's core broken invariant is: a shared execution/custody primitive fails to authenticate *who* is allowed to trigger a privileged action on its behalf, allowing an unrelated caller to impersonate the trusted flow. The direct Hyperbridge analog is `CallDispatcher.sol`, the single shared contract used by `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2` to execute calldata against escrowed/bridged assets. Its `dispatch()` entrypoint has no caller restriction whatsoever, and its `receive()` accepts value from anyone, so any balance the contract holds can be moved to an arbitrary address by any unprivileged EOA — not just by the bridge apps that are supposed to be its only legitimate callers.

### Finding Description
`CallDispatcher` is deployed once per chain and shared across multiple bridge/custody apps: [2](#0-1) [3](#0-2) 

Its full implementation is: [4](#0-3) 

`dispatch(bytes memory encoded)` is `external` with **no modifier** — no `onlyHost`, no `restrict`, no owner check, nothing that verifies the caller is `HyperFungibleToken`, `WrappedHyperFungibleToken`, or `IntentGatewayV2`. It decodes an attacker-controlled `Call[]` and, for each entry, performs `to.call{value: call.value}(call.data)` using the *contract's own ETH balance* for `call.value`. The `receive()` function is likewise unguarded, so anyone can push ETH into the contract.

The bridge apps rely on `CallDispatcher` legitimately holding value transiently during multi-step escrow/execute/sweep sequences, e.g. in `IntentGatewayV2`'s predispatch flow: [5](#0-4) 

and in the postdispatch/output execution flow: [6](#0-5) 

Because `dispatch()` performs no origin/caller check, none of these flows can assume that the only party invoking `dispatch()` against the dispatcher's balance is the legitimate app contract acting on a verified cross-chain message or an authenticated order. Anyone can call `CallDispatcher.dispatch()` directly, at any time, with a `Call[]` that transfers out whatever native ETH (or ERC20 balance, via `to: token, data: transfer(attacker, balance)`) the shared contract currently holds — this is exactly the missing-origin-authentication class from the external report, but worse: the report's issue was merely "the recipient can't identify who is calling it"; here, literally *anyone* can call the execution primitive that moves bridge-custodied value, since there is no restriction at all.

### Impact Explanation
This satisfies the bounty's "stealing or loss of funds" and "unauthorized transaction or execution" impact classes: value that legitimately transits the shared `CallDispatcher` (native ETH via the unguarded `receive()`, or ERC20 dust left mid-sequence) can be seized by an unprivileged third party rather than reaching "the rightful beneficiary and amount," violating the bridge-custody invariant. Because the same `CallDispatcher` instance backs `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2` on a given chain simultaneously, the blast radius spans all apps sharing that address.

### Likelihood Explanation
No malicious relayer, prover, admin, or leaked key is required — `dispatch()` is a plain public entrypoint. The only precondition is that the shared `CallDispatcher` momentarily or persistently holds value (native ETH sent via its unrestricted `receive()`, or token/ETH dust from a predispatch/postdispatch step that has not yet been swept back at the moment of the attacker's call). Given the contract's `receive()` accepts unconditional ETH and is a long-lived, address-stable, shared deployment referenced by config across every app on the chain, it is realistic for value to sit in the contract at some observable point, and any observer can then race a `dispatch()` call to claim it.

### Recommendation
Restrict `CallDispatcher.dispatch()` to an explicit allowlist of trusted callers (e.g., the configured `HyperFungibleToken`/`WrappedHyperFungibleToken`/`IntentGatewayV2` instances, or a single `restrict(msg.sender)` check analogous to `EvmHost`'s `restrict` modifier), and/or make the dispatcher non-custodial by design — e.g., require callers to pass exact expected balances/allowances and immediately revert/sweep any leftover value to a safe owner-controlled account rather than leaving it callable by the public `dispatch()` path.

### Proof of Concept
1. Read the shared `CALL_DISPATCHER` address from chain config (e.g. `evm/config.testnet.toml` — `CALL_DISPATCHER = "0x2B33..."`).
2. Send ETH directly to that address (its `receive()` accepts it unconditionally), or wait for a normal `IntentGatewayV2` predispatch/postdispatch call to place value there.
3. As any unprivileged EOA, call:
```solidity
Call[] memory calls = new Call[](1);
calls[0] = Call({to: attacker, value: address(callDispatcher).balance, data: ""});
ICallDispatcher(callDispatcher).dispatch(abi.encode(calls));
```
4. `dispatch()` executes `attacker.call{value: balance}("")` with no check that the caller is `IntentGatewayV2`/`HyperFungibleToken`/`WrappedHyperFungibleToken`, transferring the dispatcher's balance to the attacker.

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
