### Title
Untrusted participant count in `ThresholdKeys::read` drives an up-front heap allocation before validation - ([File: crypto/dkg/src/lib.rs](File: crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` deserializes `n` (a `u16`) directly from the input stream and immediately calls `Vec::with_capacity(usize::from(n))` — and separately loops `1..=n` reading verification shares into a `HashMap` — before `ThresholdParams::new(t, n, i)` has any opportunity to reject the parameters. The same class of bug appears in `SchnorrAggregate::read`, which loops over an attacker-controlled `u32` count.

### Finding Description
The CVE-2019-20013 bug class is "crafted length field → attempted excessive memory allocation". In `crypto/dkg/src/lib.rs:591-616`, `ThresholdKeys::read` reads three `u16`s (`t`, `n`, `i`) from the reader, then for `Interpolation::Constant` performs `Vec::with_capacity(usize::from(n))` and `n` `read_F` calls, and unconditionally inserts `n` entries into `verification_shares` via `read_G` (`crypto/dkg/src/lib.rs:608-623`). Only afterwards does `ThresholdParams::new` validate the parameters (`crypto/dkg/src/lib.rs:625-631`). A blob claiming `n = 65535` triggers allocation and up-to-65k element processing before any sanity check.

Similarly, `SchnorrAggregate::read` in `crypto/schnorr/src/aggregate.rs:77-88` reads an attacker-controlled `u32` element count and iterates `C::read_G` up to ~4.3 billion times (bounded only by input exhaustion rather than by any protocol bound). While this loop does not pre-allocate, a reader backed by a large buffer or stream causes memory growth proportional to the claimed count with no upper bound tied to the protocol's real signer set (bounded by `u16` participants elsewhere).

### Impact Explanation
An unprivileged party that can feed bytes to `ThresholdKeys::read` (listed reachable sink) or `SchnorrAggregate::read` can force the victim to perform allocations/element-reads scaled purely by attacker-chosen header fields, not by data actually present or by protocol limits. Repeated calls exhaust memory/CPU, crashing the process — matching the availability impact (A:H) of the original CVE.

### Likelihood Explanation
Both `read` functions are public deserialization APIs intended for exactly this purpose, and neither validates the count against a bound before acting on it. `ThresholdKeys::read` allocates before `ThresholdParams::new` can reject the claimed `n`, so the cost is paid even when the input is later rejected.

### Recommendation
- In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:608`): replace `Vec::with_capacity(usize::from(n))` with a plain `Vec::new()` (or cap `n` against a sane protocol bound, e.g. `u16::MAX` participants is already the implicit bound — enforce `t <= n` and `n >= 1` via `ThresholdParams::new` *before* allocating).
- In `SchnorrAggregate::read` (`crypto/schnorr/src/aggregate.rs:83`): reject `len` exceeding a documented maximum signature count before looping.
- Prefer chunked reading (as done in `networks/ethereum/src/machine.rs:51-60`) so memory use tracks bytes actually present.

### Proof of Concept
```rust
// crypto/dkg: bytes claiming n = u16::MAX with a truncated body still drive
// with_capacity + per-participant read_G work before params are validated.
let mut bytes = vec![];
bytes.extend(&(C::ID.len() as u32).to_le_bytes());
bytes.extend(C::ID);
bytes.extend(&1u16.to_le_bytes());        // t
bytes.extend(&u16::MAX.to_le_bytes());    // n = 65535
bytes.extend(&1u16.to_le_bytes());        // i
bytes.push(0);                            // Interpolation::Constant
// Appends no further data: with_capacity(65535) already ran; the loop then
// fails on read_F, but the oversized Vec was allocated.
let _ = ThresholdKeys::<C>::read(&mut bytes.as_slice());
```
