### Title
Webhook `shop_domain` derived from unauthenticated `HTTP_X_SHOPIFY_SHOP_DOMAIN` header enables cross-shop record manipulation - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#shop_domain` returns the raw `HTTP_X_SHOPIFY_SHOP_DOMAIN` header value, and `#verify_request` only validates the HMAC over the raw request body, never cross-checking it against the shop identity claimed in the header. Any downstream job/controller (including the templates shipped by this gem) that uses this header to locate a `Shop` record and perform state-changing actions can be tricked into acting on a victim shop using a request whose HMAC was legitimately computed for a different (attacker-controlled) payload/shop.

### Finding Description
`verify_request` only checks `hmac_valid?(request.raw_post)`, comparing the `X-Shopify-Hmac-Sha256` header against `HMAC(app_secret, raw_body)`: [1](#0-0) [2](#0-1) 

The `HTTP_X_SHOPIFY_SHOP_DOMAIN` header is not part of the HMAC-signed bytes at all — it is returned unchecked: [3](#0-2) 

This value is passed straight into `perform_later(shop_domain: ...)` and then used by the generated job templates to look up and mutate a `Shop` record with no corroboration against the actual signed payload: [4](#0-3) [5](#0-4) 

The gem's own documentation explicitly instructs developers to pass this unverified header straight into a job for session/token-adjacent processing: [6](#0-5) 

Because the app's HMAC secret (`ShopifyApp.configuration.secret`) is shared across every shop that has the app installed, an attacker who controls their own shop (an unrelated, unprivileged merchant) can trigger a webhook delivery to the app's public endpoint and observe/capture a genuinely-signed `(body, HMAC)` pair for their own tenant. They can then re-issue an HTTP request to the same public webhook route with the identical body/HMAC pair but with `X-Shopify-Shop-Domain` rewritten to a victim shop's `myshopify.com` domain. `verify_request` still passes because the HMAC only covers `raw_post`, and `shop_domain` blindly returns the attacker-supplied header. Downstream code (e.g., `AppUninstalledJob`) then resolves `Shop.find_by(shopify_domain: shop_domain)` to the **victim** shop and executes `shop.destroy` (or overwrites/queues session-affecting logic) — an action the attacker never had authorization to trigger for that shop.

None of the existing safeguards stop this: `hmac_valid?` validates payload integrity/authenticity but not shop binding; there is no `ShopifyApp::Utils.sanitize_shop_domain` call or comparison against a shop identifier embedded in the verified payload/body in `WebhookVerification`.

### Impact Explanation
An attacker can cause the host app to perform shop-scoped state-changing operations (e.g., deleting/destroying a `Shop` record via `AppUninstalledJob`, or running arbitrary custom webhook-job business logic) against a victim shop they don't control, by supplying a validly-HMAC'd request for their own tenant and spoofing the domain header. This maps to Shopify's "cross-shop data manipulation / unauthorized action on another merchant's data" impact class — a broken tenant-isolation issue stemming from trusting an unauthenticated header for shop binding.

### Likelihood Explanation
Preconditions are attacker-feasible under the stated threat model: the attacker only needs to be a merchant with the app installed on their own shop (unprivileged) to obtain one genuinely HMAC-signed webhook request, and the webhook endpoint is a public, unauthenticated-beyond-HMAC route. The exploit is fully repeatable for any topic/job that keys lookups off `shop_domain` without corroborating it against the signed payload.

### Recommendation
Do not trust `HTTP_X_SHOPIFY_SHOP_DOMAIN` for shop resolution. Derive the shop identity from a verified source — e.g., use `ShopifyAPI::Webhooks::Request#shop` (which Shopify's SDK derives from validated webhook metadata tied to the registration) exclusively, or cross-check the header against a shop identifier embedded in and covered by the signed payload, and reject the request if they don't match. Additionally consider binding webhook processing to the specific `webhook_id`/registration rather than a client-supplied domain string.

### Proof of Concept
```ruby
# test/controllers/concerns/webhook_verification_spoof_test.rb
class WebhookVerificationSpoofTest < ActionController::TestCase
  test "hmac validity does not bind to shop_domain header" do
    body = '{"id":1}'
    secret = ShopifyApp.configuration.secret
    valid_hmac = Base64.strict_encode64(OpenSSL::HMAC.digest("sha256", secret, body))

    # Attacker's own valid signed request, then domain header swapped to victim's shop
    post :receive, body: body, headers: {
      "HTTP_X_SHOPIFY_HMAC_SHA256" => valid_hmac,
      "HTTP_X_SHOPIFY_SHOP_DOMAIN" => "victim-shop.myshopify.com",
    }

    assert_response :no_content # or :ok — request passes verify_request
    # yet AppUninstalledJob/etc. is subsequently invoked with
    # shop_domain: "victim-shop.myshopify.com", acting on a shop
    # the request was never actually signed for.
  end
end
```
Expected: the test demonstrates that `verify_request` succeeds and `shop_domain` returns the attacker-controlled `victim-shop.myshopify.com` value even though the HMAC was computed only over the attacker's own body — confirming no cross-check exists between the signed payload and the shop-binding header consumed by downstream jobs/controllers.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
