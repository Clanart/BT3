### Title
Unauthenticated `send_tx` JSON-RPC Endpoint Allows Permanent Lock of Bridge Transactions via Fake `activate_outpoints` — (`crates/clementine-tx-sender/src/jsonrpc/server.rs`)

---

### Summary

The tx-sender JSON-RPC server exposes a `send_tx` method with no authentication. Any caller who can reach the endpoint can submit a bridge transaction with `activate_outpoints` referencing a nonexistent on-chain UTXO. Because the activation-outpoint tracking loop can never set `seen_at_height` for a txid that does not exist on-chain, the submitted transaction is permanently excluded from `get_sendable_txs` via the `non_active_txs` CTE. If the attacker races to submit a legitimate bridge txid before the bridge component does, the deduplication check causes the bridge to silently reuse the poisoned queue entry, permanently locking the transaction and any BTC or collateral it was meant to release.

---

### Finding Description

**Step 1 — Unauthenticated endpoint**

`start_jsonrpc_server` builds the server with `ServerBuilder::default()` and registers `send_tx` with no authentication middleware or token check. [1](#0-0) 

The bind address is configurable as either `127.0.0.1` or `0.0.0.0`; the latter is explicitly supported for containerized deployments. [2](#0-1) 

**Step 2 — No validation of `activate_outpoints`**

`insert_try_to_send` blindly persists every caller-supplied `ActivatedWithOutpoint` to `tx_sender_activate_try_to_send_outpoints` with `seen_at_height = NULL` (the column default). No existence check against Bitcoin RPC is performed. [3](#0-2) 

**Step 3 — `seen_at_height` can never be set for a nonexistent txid**

The confirmation loop calls `check_spent`, which calls `is_utxo_spent`. `is_utxo_spent` first calls `is_tx_on_chain`; if the txid does not exist on-chain it returns `Err(BitcoinRPCError::TransactionNotConfirmed)`. [4](#0-3) 

`check_spent` maps `TransactionNotConfirmed` to `Ok(None)`. [5](#0-4) 

The `Ok(Some(false)) | Ok(None)` branch only clears `seen_at_height` if it was already set; when it is already `NULL` the row is left untouched. The outpoint therefore stays with `seen_at_height = NULL` indefinitely. [6](#0-5) 

**Step 4 — Permanent exclusion from `get_sendable_txs`**

The `non_active_txs` CTE includes any tx whose activate-outpoint row has `seen_at_height IS NULL`. Such a tx is excluded from the final `SELECT` forever. [7](#0-6) 

**Step 5 — Deduplication race**

`insert_try_to_send` deduplicates by `txid`. If the attacker submits the bridge tx first with a fake `activate_outpoint`, the bridge component's subsequent call returns the existing poisoned `try_to_send_id` without overwriting the activation rows. [8](#0-7) 

---

### Impact Explanation

A bridge transaction permanently stuck in `non_active_txs` is never broadcast. Any BTC, operator collateral, reimbursement output, or bridge-controlled UTXO that the transaction was meant to release remains locked with no recovery path in the current code. The tx-sender has no administrative endpoint to remove or repair a poisoned queue entry.

---

### Likelihood Explanation

**Prerequisite 1 — Network reachability:** The default bind is `127.0.0.1`, limiting the attack to processes on the same host. However, the code explicitly supports `0.0.0.0` for containerized deployments, and in that configuration any network peer can call `send_tx` without credentials.

**Prerequisite 2 — Knowing bridge txids in advance:** Bitcoin transactions are deterministic. Bridge transactions are constructed from public protocol parameters, operator public keys, and on-chain deposit outpoints. An attacker who monitors the Bitcoin chain and knows the Clementine protocol can precompute the txids of pending bridge transactions before the bridge component queues them.

**Prerequisite 3 — Race condition:** The attacker must submit before the bridge component. Given that bridge transactions are queued in response to on-chain events (deposits, kickoffs, etc.), the window is bounded but non-zero, especially under network congestion or bridge restart.

When the server is bound to `0.0.0.0`, all three prerequisites are achievable by an unprivileged network attacker.

---

### Recommendation

1. **Add authentication to the JSON-RPC server.** Implement a shared-secret bearer token or mTLS between bridge components and the tx-sender. Reject unauthenticated `send_tx` calls at the HTTP layer before any DB write.
2. **Validate `activate_outpoints` at insertion time.** Before persisting an `ActivatedWithOutpoint`, verify that the referenced txid exists on-chain (or at minimum that it is syntactically non-zero). Reject submissions referencing obviously nonexistent outpoints.
3. **Provide an administrative repair endpoint** (authenticated) to remove or re-queue a poisoned tx-sender entry.
4. **Restrict the default bind to `127.0.0.1`** and document that `0.0.0.0` requires network-level access control (firewall, VPC, etc.).

```rust
// Rust integration test sketch
#[tokio::test]
async fn test_fake_activate_outpoint_permanent_lock() {
    // 1. Start tx-sender with JSON-RPC on 0.0.0.0 (or 127.0.0.1 for local PoC).
    let (addr, _handle) = spawn_txsender_loop_with_free_localhost_jsonrpc_port(config);
    let client = JsonRpcTxSenderClient::new(&format!("http://{addr}")).unwrap();

    // 2. Build a syntactically valid signed_tx (the "bridge tx").
    let bridge_tx = build_minimal_tx(); // any valid serializable tx

    // 3. Submit it with an activate_outpoint referencing a nonexistent txid.
    let fake_outpoint = ActivatedWithOutpoint {
        outpoint: OutPoint { txid: Txid::all_zeros(), vout: 0 },
        relative_block_height: 0,
    };
    let id = client
        .insert_try_to_send(None, &bridge_tx, FeePayingType::NoFunding,
                            None, &[], &[], &[], &[fake_outpoint])
        .await
        .unwrap();

    // 4. Mine many blocks; the tx-sender loop runs repeatedly.
    rpc.mine_blocks(100).await.unwrap();
    tokio::time::sleep(Duration::from_secs(10)).await;

    // 5. Assert the tx never appears in get_sendable_txs regardless of tip height.
    let db = TxSenderDb::from_pool(pool.clone());
    let sendable = db.get_sendable_txs(None, FeeRateKvb::MAX, 9999).await.unwrap();
    assert!(!sendable.contains(&id),
        "tx with fake activate_outpoint must never become sendable");
}
```

The test will pass (the tx is never sendable), confirming the permanent lock. If the same `bridge_tx` is then submitted by the legitimate bridge component, `insert_try_to_send` returns the existing poisoned `id` without correcting the activation rows, demonstrating the deduplication-race vector.
