### Title
`popStashEntry()` silently drops the stash entry (permanent data loss) when Git reports a non-zero exit code with empty `stderr`, without verifying the stash was actually applied - (File: `app/src/lib/git/stash.ts`)

### Summary
The NFT report's core broken invariant is: *the code treats a two-sided operation as "successful" and finalizes an irreversible side effect (releasing funds / consuming the transfer) without verifying that the other half of the operation (the actual transfer) really happened.* The GitHub Desktop analog is `popStashEntry()`, which treats "exit code 1 with empty `stderr`" from `git stash pop` as proof that the stash was successfully applied, and then irreversibly deletes the stash entry (`dropDesktopStashEntry`) - without ever checking that the working directory actually received the stashed changes.

### Finding Description
`popStashEntry()` runs `git stash pop --quiet <name>` and, on failure, inspects the error: [1](#0-0) 

If the exit code is `1` and `result.stderr.length === 0`, the code assumes "a stash was popped successfully" purely from the *absence* of stderr text, and calls `dropDesktopStashEntry` to permanently delete the stash ref. There is no independent verification (e.g. diffing the working directory before/after, checking `git stash list`, or confirming the stashed files are actually present) that the pop actually materialized the user's changes.

This mirrors the reported flaw closely: the "payment" (irreversible deletion of the only copy of the stashed changes) is executed based solely on a heuristic signal (empty stderr + exit code 1) rather than on verifying the actual deliverable (files restored to the working directory). The code comment itself acknowledges this is fragile: *"Not the greatest approach but stash isn't very communicative."* A related, similarly unverified heuristic exists in `createDesktopStashEntry()`, which assumes a stash was created successfully under analogous conditions (exit code 1, no `error:`-prefixed stderr lines): [2](#0-1) 

Because `git`'s exit codes and stderr content for `stash pop`/`stash push` can be influenced by repository-local configuration and hooks that ship with an attacker-controlled/fetched repository (e.g. custom `merge.conflictStyle`, clean/smudge filters, or `post-checkout`/`pre-command` hooks that intercept and redirect diagnostic output, or environment quirks that cause Git to print errors to stdout instead of stderr in unusual repository states), the "empty stderr" heuristic is not a reliable success signal. In such cases Desktop would erroneously believe the pop succeeded and delete the only record of the stashed changes even though they were never restored, silently corrupting/destroying what the user believed was committed to their working directory.

### Impact Explanation
If the heuristic misfires, the user's uncommitted work captured in the stash is permanently lost with no error shown to the user - Desktop reports/behaves as if the operation completed cleanly. This satisfies the "silent corruption of what the user commits" impact class: the working directory ends up in a state that does not match what the user intended (missing changes), and there's no recovery path because the stash entry backing those changes has already been dropped. Given stashes are often the only copy of unstaged/uncommitted work, this is a data-loss-with-no-warning scenario directly analogous to the NFT report's "seller paid, buyer gets nothing, and everyone believes the trade succeeded."

### Likelihood Explanation
The mechanism is directly reachable through normal Desktop usage (any user popping a stash) and depends only on the exit-code/stderr behavior of `git stash pop` in edge-case repository states - a condition explicitly called out by the developers themselves as under-specified and not well audited (the surrounding comment history in `createDesktopStashEntry` shows the author auditing this exact heuristic and finding it unreliable, e.g. the unborn-repository counterexample). This makes it plausible that other edge cases (conflicting hooks, custom merge tools, unusual locale/config output redirection) can produce the same "exit 1, empty stderr" signature without the stash actually having been applied. However, I was not able to independently reproduce a concrete Git scenario in which `stash pop` exits 1 with truly empty stderr without the changes being applied - this is model uncertainty; the developers' own comments indicate the exact boundary conditions of this heuristic are not fully understood even by the codebase maintainers.

### Recommendation
Do not treat exit code + stderr length as proof of success for `stash pop`. After the `git stash pop` command settles into the "possible success" branch, verify the actual outcome before calling `dropDesktopStashEntry`, for example by re-checking `git stash list` for the specific `stashSha` and/or comparing the working directory status against the stash's tree contents. Only drop the stash entry once its effects have been positively confirmed in the working directory; otherwise, leave the entry intact and surface an error/warning to the user instead of silently discarding data.

### Proof of Concept
Not independently reproducible from static analysis alone (requires crafting a Git repository/hook configuration that causes `git stash pop` to exit with code `1` and empty `stderr` while not actually restoring the stashed content). Conceptual PoC path:
1. Clone/create a repository containing a custom hook or filter configuration engineered so that a stash-pop attempt fails to restore changes but Git's error output goes to stdout (or is suppressed) rather than stderr, yielding exit code 1 with empty stderr.
2. In Desktop, stash changes, then trigger `popStashEntry` on that stash.
3. Observe that `dropDesktopStashEntry` runs (per `app/src/lib/git/stash.ts:257-267`), deleting the stash entry, while the working directory does not actually contain the previously stashed changes - resulting in silent, unrecoverable loss of the user's work. [3](#0-2)

export async function popStashEntry(
  repository: Repository,
  stashSha: string
): Promise<void> {
  // ignoring these git errors for now, this will change when we start
  // implementing the stash conflict flow
  const expectedErrors = new Set<DugiteError>([DugiteError.MergeConflicts])
  const stashToPop = await getStashEntryMatchingSha(repository, stashSha)

  if (stashToPop !== null) {
    const args = ['stash', 'pop', '--quiet', `${stashToPop.name}`]
    await git(args, repository.path, 'popStashEntry', {
      expectedErrors,
    }).catch(e => {
      // popping a stashes that create conflicts in the working directory
      // report an exit code of `1` and are not dropped after being applied.
      // so, we check for this case and drop them manually unless there's
      // anything in stderr as that could have prevented the stash from being
      // popped. Not the greatest approach but stash isn't very communicative
      if (
        e instanceof GitError &&
        e.result.exitCode === 1 &&
        e.result.stderr.length === 0
      ) {
        log.info(
          `[popStashEntry] a stash was popped successfully but exit code ${e.result.exitCode} reported.`
        )
        // bye bye
        return dropDesktopStashEntry(repository, stashSha)
      }
      return Promise.reject(e)
    })
  }
}
