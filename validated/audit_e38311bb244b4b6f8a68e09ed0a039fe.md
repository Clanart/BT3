Confirmed: `create_object_internal` asserts the destination address does not already hold an `ObjectCore`, aborting with `EOBJECT_EXISTS` if it does [1](#0-0) . `create_named_object` derives the address deterministically from `creator_address` and `seed` via `create_object_address` (`sha3_256(creator | seed | 0xFE)`), then calls `create_object_internal`, which aborts if an object already exists there [2](#0-1) . `object_code_deployment::publish` uses this exact deterministic path: the seed is `OBJECT_CODE_DEPLOYMENT_DOMAIN_SEPARATOR || bcs(sequence_number+1)`, entirely public/predictable knowledge before the deployer's transaction lands [3](#0-2) , and this is mirrored in the CLI's own precomputation of `object_address` from `sender_address` + next `sequence_number` [4](#0-3) .

### Title
Front-runnable deterministic object-code deployment address permits permanent DoS of `object_code_deployment::publish` - (File: aptos-move/framework/aptos-framework/sources/object_code_deployment.move)

### Summary
`object_code_deployment::publish` derives the code object's address purely from the publisher's address and their *next* sequence number, both of which are public before the publish transaction executes. Anyone can pre-create a named/derived object (or any resource requiring `ObjectCore`) at that exact address using a cheap, unrelated transaction. Because `create_object_internal` strictly aborts with `EOBJECT_EXISTS` if an `ObjectCore` already exists at the target address, the legitimate publisher's `publish` call will permanently abort for that sequence number.

### Finding Description
The seed used for the deployment object is fully deterministic and computable off-chain by anyone watching the mempool/chain state: `OBJECT_CODE_DEPLOYMENT_DOMAIN_SEPARATOR || bcs(sequence_number + 1)` [5](#0-4) . `create_object_address` is a pure, non-secret hash function of `(creator, seed)` [6](#0-5) , so an attacker who observes a target account's current sequence number can compute the exact object address the deployer will target for their *next* transaction, well before that transaction is mined.

`create_named_object` unconditionally calls `create_object_internal(creator_address, obj_addr, false)`, and that function's documented and formally-verified invariant is "Creating an object twice on the same address must never occur" — it aborts with `EOBJECT_EXISTS` if `ObjectCore` already exists at `obj_addr` [7](#0-6) [8](#0-7) . This is analogous to the reported bug's pattern: a strict "must be empty/zero" precondition, whose target address/state is attacker-influenceable via an unprivileged, cheap transaction, causing a legitimate operation to permanently fail.

Note that the framework's other deterministic-address flow, `account::create_resource_account`, explicitly anticipates and defangs this exact griefing vector: if the target address already has an `Account` resource, it checks `signer_capability_offer.for.is_none()` and `sequence_number == 0` and proceeds by hijacking/claiming the pre-existing account rather than aborting [9](#0-8) . `object_code_deployment::publish`/`create_named_object` has no equivalent recovery path — it just aborts.

### Impact Explanation
An attacker can permanently deny a specific `object_code_deployment::publish` call (and any transaction reusing this call pattern, e.g. via the CLI's `create-object-and-publish-package` flow that also precomputes the address from `sequence_number + 1` [4](#0-3) ) for a targeted account/sequence-number, forcing the victim to bump their sequence number (e.g. via an unrelated no-op transaction) before retrying, and the attacker can repeat this for the next sequence number as well. This is griefing/DoS on a legitimate publish path, not fund loss or code compromise, but it directly targets the "unauthorized... publish" surface named in the Publish Impact Gate ("must not be griefable/blocked by unprivileged front-running of the deterministic target address").

### Likelihood Explanation
Requires only a public sequence-number read (via full node/indexer) and any low-cost transaction (e.g., `object::create_named_object` from an unrelated module, or any other flow that lands an `ObjectCore` at that computed address) submitted before the victim's publish transaction is included. No special privilege or economic cost beyond one transaction fee is required, and it is repeatable per sequence number.

### Recommendation
Mirror the resource-account pattern in `account.move`: when the computed object address already has residual/attacker-planted state but no legitimate ownership/publish history (e.g., `ObjectCore` exists but no `ManagingRefs`/`PackageRegistry` and the object is still owned by the intended creator or otherwise unclaimed), allow `object_code_deployment::publish` to proceed by taking over that address rather than hard-aborting. Alternatively, incorporate a component in the seed that only the publisher's own transaction can supply and that an attacker cannot predict/replicate ahead of time (e.g., a value bound to the transaction's own execution, not merely the pre-transaction sequence number), or document/require sequence-number-skip recovery tooling.

### Proof of Concept
1. Attacker observes victim account `V` currently has sequence number `n` (public on-chain state) and intends to call `object_code_deployment::publish`.
2. Attacker computes `seed = bcs(OBJECT_CODE_DEPLOYMENT_DOMAIN_SEPARATOR) || bcs(n+1)` and `obj_addr = create_object_address(V, seed)` — reproducing the exact logic in `object_seed`/`create_object_address` [5](#0-4) [6](#0-5) .
3. Attacker (any account, no special permission) submits any transaction that creates a named/derived object at `obj_addr` (or otherwise causes `ObjectCore` to exist there) before `V`'s publish transaction for sequence number `n` lands.
4. When `V`'s transaction executes with sequence number `n` (so `n+1` matches the pre-computed seed), `object_code_deployment::publish` calls `object::create_named_object`, which calls `create_object_internal`, which asserts `!exists<ObjectCore>(obj_addr)` and aborts with `EOBJECT_EXISTS` since the attacker already placed an object there [8](#0-7) .
5. `V`'s publish transaction fails; `V` must consume a sequence number (e.g., submit a dummy transaction) and retry, and the attacker can repeat the griefing for the new target sequence number.

**Confidence caveat:** I was unable to inspect the actual Rust implementation body of `create_object_internal` (only its Move spec/summary was retrieved) to fully confirm there is no alternate "reclaim" branch (e.g., for burnt/tombstoned objects) that might mitigate this; if such a branch exists, the practical impact could be lower. I recommend verifying `create_object_internal`'s full Move source directly before treating this as final.

    public fun create_object_address(source: &address, seed: vector<u8>): address {
        let bytes = bcs::to_bytes(source);
        bytes.append(seed);
        bytes.push_back(OBJECT_FROM_SEED_ADDRESS_SCHEME);
        from_bcs::to_address(hash::sha3_256(bytes))
    }
