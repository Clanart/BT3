### Title
`SignableTransaction::new` undercounts the fee when `data` is present, producing transactions that fail relay - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` checks solvency (`input_sat >= payment_sat + needed_fee`) and the minimum-relay-fee bound using a weight/vbyte count computed only from `payments` and `inputs`. The OP_RETURN output carrying `data` is pushed onto `tx_outs` *before* the fee calculation but is never included in the weight estimate, so the extra output makes the finalized transaction "insolvent" against its own declared fee rate — exactly the external report's pattern of a fee added on top of an amount already checked, with the failure only surfacing later when Bitcoin nodes reject the underpriced transaction.

### Finding Description
In `SignableTransaction::new`, the data output is appended to `tx_outs` at lines 194–202: [1](#0-0) 

However, both weight computations — the initial one at line 204 and the change variant at lines 225–226 — pass `payments`, not `tx_outs`, to `calculate_weight_vbytes`: [2](#0-1) [3](#0-2) 

`calculate_weight_vbytes` builds its template transaction's `output` vector solely from `payments` (plus optional change), so the OP_RETURN output's weight (≈ `8 + 1 + data_len` bytes, up to ~90 bytes for the permitted 80 bytes of data) is excluded from `vbytes`. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` is too small.
- The `TooLowFee` check at line 211 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`, also using the undercounted `vbytes`.
- The `NotEnoughFunds` solvency check at line 215 passes even though the real transaction is larger and needs a higher fee to hit the requested rate. [4](#0-3) 

The actual fee paid is `sum(inputs) - sum(outputs)` (line 139–141), which only satisfies the *understated* `needed_fee`. For a transaction carrying 80 bytes of OP_RETURN data, the true vsize is ~90 vbytes higher than estimated; if `fee_per_vbyte` is near the 1 sat/vbyte minimum relay bound, the achieved fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` and the transaction is rejected by the mempool despite `SignableTransaction::new` having validated it.

### Impact Explanation
Any caller (including the coordinator path that can attach data outputs) can construct a `SignableTransaction` that passes all of Serai's checks — `TooLowFee`, `NotEnoughFunds`, `TooLargeTransaction` — yet produces a transaction below the Bitcoin network's minimum relay fee. The threshold signature ceremony (`TransactionSignMachine::sign` → `complete`) then signs and finalizes a transaction that honest nodes will not relay or mine, so the spend is dead on arrival: the funds remain locked in the multisig output and the plan cannot complete until a new transaction is constructed and re-signed. This mirrors the report's "cannot be liquidated until conditions change" outcome — a validation done before an extra cost is attached, with the failure deferred to an external check Serai cannot satisfy.

### Likelihood Explanation
Reachable by any unprivileged party able to supply `data` and a `fee_per_vbyte` to `SignableTransaction::new` (the API accepts arbitrary `data` up to 80 bytes and any fee rate). The trigger requires `fee_per_vbyte` low enough that the missing ~90 vbytes pushes the real rate under min-relay — most easily at the 1 sat/vbyte floor, where the deficit is ~90 sats and the TooLowFee gate was evaluated against ~90 fewer vbytes than reality. The miss scales linearly with `fee_per_vbyte`, so higher fee rates widen the absolute shortfall.

### Recommendation
Include the OP_RETURN output in the weight estimate: either pass the fully built `tx_outs` (or a `data: Option<&[u8]>` parameter) into `calculate_weight_vbytes` so the template transaction contains the data output, or compute `vbytes` after constructing all outputs including `data`. Additionally, compute the `TooLowFee` bound against the final transaction's actual vsize (`tx.weight()`/`get_virtual_tx_size` on `self.tx`) rather than the estimate, so the minimum-fee invariant is verified on the artifact that will actually be broadcast.

### Proof of Concept
```rust
// In networks/bitcoin (test outline):
// One input worth `input_sat`, one payment, no change, 80 bytes of OP_RETURN data.
let data = vec![0u8; 80];
let stx = SignableTransaction::new(
    inputs, &payments, None, Some(data), /* fee_per_vbyte = */ 1,
).unwrap(); // passes TooLowFee + NotEnoughFunds against vbytes computed WITHOUT
            // the OP_RETURN output

let real_vbytes = bitcoin::policy::get_virtual_tx_size(
    i64::try_from(stx.transaction().weight().to_wu()).unwrap(), 0) as u64;
// real_vbytes ≈ counted_vbytes + ~90

let actual_fee = stx.fee();
// actual_fee >= 1 * counted_vbytes, but
assert!(actual_fee < (bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE as u64) * real_vbytes / 1000);
// The finalized transaction is below min relay fee: broadcast fails,
// even though construction succeeded.
```

Root cause lines: `data` pushed to `tx_outs` before fee math at `networks/bitcoin/src/wallet/send.rs:194-202`; both `calculate_weight_vbytes` calls use `payments` only at `send.rs:204` and `send.rs:225-226`; solvency/min-fee gates consume the understated `vbytes`/`needed_fee` at `send.rs:206-221`.
