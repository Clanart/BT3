## Analysis

The FiatDAO bug's core invariant: a **mutable allow/deny-list is checked against a live value with no memory of prior valid values**, so a legitimate config change (blocklist migration) retroactively invalidates state that was created under the old rules, and there is no unblock/rollback path — permanently trapping already-committed funds.

The direct local analog is in the Intent Gateway's cross-chain module binding. `_instances[keccak256(chain)]` is the "trust anchor" that authenticates settlement messages between two gateway deployments, and it is a single mutable slot with no migration grace period or fallback to the previously-trusted address. ### Title
Gateway-instance rotation (`_addDeployment`) permanently strands in-flight escrow settlement — ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`_instances[keccak256(chain)]` is the sole authentication anchor `_authenticate` uses to accept `RedeemEscrow`/`RefundEscrow` settlement messages from a remote `IntentGatewayV2` deployment. `_addDeployment` overwrites this mapping unconditionally and instantly whenever Hyperbridge dispatches a `NewDeployment` message, with no grandfathering of the previous address. Any settlement message already dispatched by the *old* remote gateway (for orders that were already filled or cancelled on the remote chain before the rotation) will be rejected by `_authenticate` on delivery, because `request.from` (the old gateway) no longer equals the now-updated `_instances[...]` entry. Because the remote side has already marked the order `_filled`, the user's only alternative recovery path (`cancelOrder` → GET proof of "not filled") is also blocked (`Filled()` revert in `onGetResponse`). The escrow becomes permanently unredeemable, exactly mirroring the FiatDAO issue: a config value change traps funds that were valid under the old configuration, with no unblock function.

### Finding Description
- `_instances` maps a hashed state-machine id to the trusted counterpart gateway address, and is used both to authenticate inbound settlement (`_authenticate`) and to address outbound dispatches (`_instance(order.source)`). [4](#0-3) 
- `_addDeployment` is invoked from `onAccept` whenever Hyperbridge sends a `NewDeployment` message, and simply replaces the stored address with no validation, versioning, or timelock: [2](#0-1) 
- `_authenticate` strictly compares `request.from` against the *current* `_instances` value: [5](#0-4) 
- `RedeemEscrow`/`RefundEscrow` inbound handling goes through this exact check before releasing escrow: [6](#0-5) 
- The only alternate recovery path a user has — `cancelOrder` → `_cancelFromSource` → GET proof that `_filled` is empty on destination — explicitly reverts once the order is actually filled/cancelled remotely: [7](#0-6) 

Sequence that traps funds:
1. User places a cross-chain order on chain A; tokens are escrowed in `_orders[commitment][token]`.
2. Solver fills (or user cancels) the order on chain B (destination). Chain B marks `_filled[commitment]` and dispatches a `RedeemEscrow`/`RefundEscrow` `PostRequest` back to chain A, addressed via `_instance(order.source)` at that time, with `from` = chain B gateway's own address.
3. Before that message is delivered/relayed to chain A, Hyperbridge governance rotates the registered gateway for chain B (redeploy, upgrade, migration) by dispatching `NewDeployment`, which chain A's `onAccept` applies immediately via `_addDeployment`, overwriting `_instances[keccak256(chainB)]`.
4. The pending settlement message from the *old* chain-B gateway is finally delivered to chain A. `_authenticate` now compares `request.from` (old gateway) against `_instances[chainB]` (new gateway) → mismatch → revert `Unauthorized`.
5. Because ISMP `on_accept` reverting does not delete the request commitment on the source side status for A (it simply fails; per ISMP semantics a relayer can retry, but the check will always fail identically since `_instances` has no memory of the old value), the message can never be authenticated again.
6. `_orders[commitment][token]` on chain A remains escrowed forever. The user cannot cancel because chain B already marked `_filled[commitment]`, so any source-side `cancelOrder` GET-proof route reverts with `Filled()`.

This is unprivileged-attacker-reachable in the sense that no malicious actor is needed at all — it is a straightforward race between a legitimate governance action and normal in-flight settlement traffic, matching the "acknowledged rug/ops vector" class of the original finding (no unblock function once the mismatch state is reached).

### Impact Explanation
User funds (order input tokens) already escrowed and already legitimately settled on the remote chain become permanently irretrievable on the source chain. There is no `_instances` history, no grace window, and no admin/governance path in `IntentsBase`/`ExtrinsicIntents` to re-authenticate a stale-but-valid settlement message or manually release escrow for such a commitment. This is a direct, permanent loss-of-funds condition triggered by ordinary protocol operations (deployment migration), not by a compromised relayer or admin key.

### Likelihood Explanation
Gateway migrations (new deployments, upgrades via `UpgradeContract`, redeployments to fix bugs) are an expected, routine operational event for a live cross-chain protocol — the code base explicitly documents this pattern (`NewDeployment`, `UpgradeContract` message kinds). Any settlement message in flight at the moment of such a migration is affected; the wider Hyperbridge message-delivery pipeline (state proofs, challenge periods, relayer batching) makes multi-block or multi-hour delivery latency routine, giving a realistic window in which an in-flight settlement can race a routine gateway rotation.

### Recommendation
- Retain the previous gateway address for a chain (e.g., a small history/set of valid addresses per chain, or a timestamped deprecation window) so `_authenticate` accepts messages from the prior address until pending settlements are guaranteed to have drained.
- Alternatively, version `_instances` writes and have `_authenticate` accept messages that were dispatched (per an included, provable timestamp/height) before the rotation.
- Add an explicit governance-triggered recovery/sweep path that can release specific `_orders[commitment][token]` balances when authentication permanently fails due to a resolved gateway migration, mirroring the FiatDAO recommendation of adding an "unblock" mechanism.

### Proof of Concept
1. Deploy `IntentGatewayV2`/`ExtrinsicIntents` on chain A and chain B, register B's address in A's `_instances` via `NewDeployment`.
2. User places a cross-chain order on A, escrowing `USDC` in `_orders[commitment][USDC]`.
3. On B, solver calls `fillOrder`, which calls `_fillCrossChain` and dispatches `RedeemEscrow` addressed to `_instance(order.source)` (A) — this `PostRequest` is now "in flight" (simulate by not yet delivering it to A).
4. On A, simulate Hyperbridge dispatching `NewDeployment` for chain B pointing at a new address (`onAccept` → `_addDeployment` overwrites `_instances[keccak256(chainB)]`).
5. Deliver the original `RedeemEscrow` `PostRequest` (still carrying `from` = old B gateway address) to A's `onAccept`.
6. Observe `_authenticate` reverts with `Unauthorized` because `_instance(request.source) != module` (old vs. new address).
7. Attempt `cancelOrder` from A (source route): the corresponding GET proof against B shows `_filled[commitment]` is non-empty (order was filled in step 3) → `onGetResponse` reverts with `Filled()`.
8. Result: `_orders[commitment][USDC]` on A can never be released — no code path authenticates the pending message nor allows a source-side refund once `_filled` is set on the destination.

    /**
     * @dev Authenticates an incoming cross-chain post request by verifying that the
     * sender module matches the registered gateway instance for the source chain.
     * Reverts with InvalidInput if the sender address is malformed, or Unauthorized
     * if the sender is not the expected gateway.
     * @param request The incoming post request to authenticate.
     */
    function _authenticate(PostRequest calldata request) internal view {
        if (request.from.length != 20) revert InvalidInput();
        address module = address(bytes20(request.from));
        if (_instance(request.source) != module) revert Unauthorized();
    }
