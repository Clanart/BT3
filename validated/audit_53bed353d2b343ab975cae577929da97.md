### Title
Silent auto-rewrite of the `origin` remote URL from untrusted GitHub API data can silently redirect future pushes — (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` compares the locally-configured `origin` remote against data returned by the GitHub API and, if a set of heuristic string checks pass, calls `gitStore.setRemoteURL()` which directly runs `git remote set-url` on the user's repository — with no user prompt, diff, or confirmation dialog. The decision to trust and apply this rewrite is based purely on string/hostname matching of the previous vs. new `clone_url`, not on a stable, verified repository identity, which mirrors the reported class of bug: **a state-changing operation is triggered by external/attacker-influenced data without validating that the resulting configuration is consistent/intended, and the change is applied silently.**

### Finding Description
`updateRemoteUrl` is invoked with a `GitHubRepository` (cached local state) and an `IAPIRepository` (`apiRepo`) fetched live from the GitHub API. [1](#0-0) 

The function decides to rewrite the local remote purely from string comparisons — whether the protocol of the old vs. new clone URL matches, and whether the stored `gitHubRepository.cloneURL` still matches the current on-disk remote (`remoteUrlUnchanged`) — and if the new API-reported URL differs, it silently calls `setRemoteURL`: [2](#0-1) 

`setRemoteURL` on the `GitStore` performs the mutation directly against the git config with no confirmation step: [3](#0-2) 

which in turn shells out to `git remote set-url`: [4](#0-3) 

The equality check itself, `urlMatchesRemote`, only compares hostname/owner/name strings parsed out of the URL — it never verifies the underlying repository identity (e.g., a stable database id) is unchanged: [5](#0-4) 

This is analogous to the reported `setPlugin` bug: an externally-influenced object (`apiRepo`, sourced from the GitHub API — akin to the "new plugin" in the report) is swapped into active, persistent configuration (`origin` remote URL — akin to `pluginConfig`) purely on the basis of superficial matching, without any invariant that the new value is safe/expected, and without giving the operator (the pool admin / here, the Desktop user) any chance to review or approve the resulting state before it takes effect.

### Impact Explanation
If the URL reported by the GitHub API for a repository changes (e.g., because the repository was renamed or transferred to a different owner that the original maintainer/attacker also controls, while remaining reachable over the same protocol), Desktop will silently rewrite the victim's `origin` remote to the new location with no user-facing indication. This falls under "silent corruption of what the user commits or pushes": subsequent `git push` operations from the victim's machine will go to a destination the victim never explicitly approved. Because this path requires only that the party who controls the tracked GitHub repository change its identity metadata via the (unprivileged, non-local) GitHub API, and Desktop's own polling/refresh logic applies the change automatically, this qualifies as an attacker-controlled-GitHub-API-object primitive.

### Likelihood Explanation
The trigger conditions (`protocolsMatch && remoteUrlUnchanged && !urlsMatch`) are narrow but easily satisfiable by a repository owner performing an ordinary rename/transfer — no exploit primitive beyond normal GitHub API usage is required, and no user interaction or local access is needed on the victim side, since `updateRemoteUrl` runs as part of Desktop's background repository refresh flow. The only mitigating guard is that the check requires the URL host to still resolve and the protocol to remain unchanged, which does not meaningfully reduce attacker capability since the attacker/owner fully controls both the old and new URL. I was not able to fully trace every call site of `updateRemoteUrl` in `app-store.ts` (only one reference was found and not read in full) to confirm whether any additional confirmation dialog wraps this call in the current app-store flow; this should be verified before treating this as conclusively unmitigated.

### Recommendation
Do not silently rewrite the local `origin` remote based solely on heuristic URL matching. Either (a) prompt the user with a clear notification/dialog showing the old and new URL before applying `setRemoteURL`, giving them the ability to decline, or (b) tie the auto-update decision to a verified, stable repository identifier (e.g., the GitHub repository's database id, already tracked in `GitHubRepository`) rather than string-parsed hostname/owner/name equality, and log/surface the change prominently regardless.

### Proof of Concept
1. Victim clones a public GitHub repository and Desktop associates it with a `GitHubRepository` record whose `cloneURL` matches the on-disk `origin` remote.
2. The repository owner (attacker) renames/transfers the repository so that the GitHub API's `clone_url` for the same tracked GitHub repository object changes (same protocol, different owner/name), pointing to a destination fully controlled by the attacker.
3. On the next background repository refresh, Desktop fetches the updated `IAPIRepository` and calls `updateRemoteUrl(gitStore, gitHubRepository, apiRepo)`. [6](#0-5) 
4. Because `remoteUrlUnchanged` is true (the victim never manually edited the remote) and `protocolsMatch` is true, Desktop calls `gitStore.setRemoteURL(...)`, which runs `git remote set-url origin <attacker-url>` with no prompt. [3](#0-2) 
5. The victim's next `git push` (via Desktop or CLI) sends commits to the attacker-controlled remote without any warning being shown.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
```

```typescript
export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
```
