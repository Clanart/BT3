### Title
Symlink escape in "Reveal in File Manager" / "Open with Default Program" allows a malicious repository to read/open files outside the repo - ([File: app/src/lib/app-shell.ts])

### Summary
`revealInFileManager` and `openFile` build the target path with a plain `Path.join(repository.path, path)` and hand it to Electron's `shell.showItemInFolder` / `shell.openExternal`, both of which dereference symlinks. Elsewhere in the same codebase (`app/src/lib/copilot-conflict-context.ts`, `app/src/ui/dispatcher/dispatcher.ts`) the developers explicitly wrap equivalent repository-relative paths with `resolveWithin`, which does a `realpath`-based check specifically to reject "path traversal and symlink escapes." That guard is missing from the file-open/reveal code paths reachable from the Changes list, Commit/History file list, and conflict-resolution UI, all of which display `path` values that come straight from `git status`/`git diff`/`git log` output for a checked-out working tree — content the author of a malicious, cloned/fetched repository fully controls.

### Finding Description
Git allows a tracked blob with mode `120000` (a symlink) to point anywhere on disk, including outside the repository (e.g. `~/.ssh/id_ed25519`, `~/.aws/credentials`, or a Windows `%APPDATA%\GitHub Desktop\...` file). When a user clones or fetches+checks out a branch containing such an entry, git creates a real filesystem symlink under the repository, and the symlink's repo-relative name (e.g. `notes.txt`) is what shows up as `file.path` in:

- `app/src/ui/changes/filter-changes-list.tsx` context menu items (`getRevealInFileManagerMenuItem`, `OpenWithDefaultProgramLabel`)
- `app/src/ui/history/selected-commits.tsx` (`onContextMenu`, `onOpenItem`)
- `app/src/ui/lib/conflicts/unmerged-file.tsx` and `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx` [1](#0-0) [2](#0-1) 

Each of these calls `revealInFileManager(repository, file.path)` or `openFile(fullPath, dispatcher)` with `fullPath = Path.join(repository.path, path)`: [3](#0-2) [4](#0-3) 

`Path.join` performs purely lexical joining — it does not consult the filesystem, so it cannot detect that `path` resolves, at the OS level, to a symlink whose target lies outside `repository.path`. `shell.showItemInFolder`/`shell.openPath`/`openExternal` all dereference the symlink and act on its target.

The codebase already contains the correct fix pattern, used in the two places where the authors clearly recognized this exact risk: [5](#0-4) [6](#0-5) 

`resolveWithin` performs `realpath()` on both the root and the resolved target and only returns the path if the real, symlink-resolved location is still under the real root: [7](#0-6) 

A dedicated unit test even documents that this exact symlink-escape case is what `resolveWithin` is meant to stop: [8](#0-7) 

None of the "Reveal in File Manager" / "Open with Default Program" / "Open in External Editor" call sites use `resolveWithin`; they use raw `Path.join`, so the guard that exists elsewhere in the app does not cover this reachable sink.

### Impact Explanation
An attacker who controls a repository (or a branch/PR the victim fetches, e.g. via "Open in Desktop" or a normal clone URL) can plant a symlink blob pointing at a sensitive file outside the repository. When the victim performs ordinary Desktop actions — viewing the Changes list or commit history and right-clicking a file to "Reveal in File Manager" or "Open with Default Program" — Desktop will show/open the attacker-chosen target path instead of a file confined to the repo. This is a file-read/disclosure-outside-repo primitive: it can expose SSH keys, cloud credentials, or Desktop's own token/config files depending on what path the attacker targets and what the OS's file manager/"open" action does with it. It also expands attack surface for chained issues (e.g., if the resolved target has an executable/script association, "Open with Default Program" could execute it).

### Likelihood Explanation
High reachability, no special privileges required: cloning/fetching a repository is the core, expected GitHub Desktop workflow, and viewing changes/history + right-click "Reveal"/"Open" is normal user behavior, not an unnatural step. The only unpatched piece is that the sanitization applied to the deep-link `filepath` parameter and to Copilot conflict-resolution file reads (`resolveWithin`) was never extended to these UI-triggered open/reveal actions, even though they operate on the same class of repository-relative, attacker-influenced paths.

### Recommendation
Route `revealInFileManager`, `openFile`'s callers, and `onOpenInExternalEditor`/`openFileInExternalEditor` call sites through `resolveWithin(repository.path, path)` (as already done in `dispatcher.ts`'s `openRepositoryFromUrl` and `copilot-conflict-context.ts`) before calling `shell.showItemInFolder`/`shell.openExternal`, and refuse the action (with a user-facing error, mirroring the `Prevented attempt to open path outside of the repository root` log message) when the resolved real path is not inside the repository.

### Proof of Concept
1. Attacker creates a repository containing a tracked symlink entry, e.g. via `git`:
   ```
   ln -s ~/.ssh/id_ed25519 secret-notes.txt
   git add secret-notes.txt
   git commit -m "notes"
   ```
   (a normal, git-legal `120000` mode blob).
2. Victim clones this repository (or fetches/checks out the branch) in GitHub Desktop — a completely ordinary action.
3. Victim opens the "Changes" tab (or Commit/History view) where `secret-notes.txt` is listed, right-clicks it, and selects "Reveal in File Manager" or "Open with Default Program."
4. `revealInFileManager`/`openFile` compute `Path.join(repository.path, 'secret-notes.txt')`; the OS/Electron shell dereferences the symlink and reveals/opens `~/.ssh/id_ed25519` instead of a file confined to the repository, disclosing its location/content to the user's default viewer — outside the cloned repository, driven entirely by attacker-controlled repo content.
```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
