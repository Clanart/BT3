### Title
`compute_royalty_amount()` divides before multiplying, causing NFT royalty underpayment - ([File: chia/wallet/nft_wallet/nft_wallet.py])

### Summary
`compute_royalty_amount()` in `chia/wallet/nft_wallet/nft_wallet.py` computes the royalty owed to an NFT creator during an offer trade by first floor-dividing the offered amount by `royalty_split`, then multiplying by `percentage`, then floor-dividing by `MAX_ROYALTY_BASIS_POINTS`. This "divide before multiply" ordering discards precision at an intermediate step, systematically under-paying the royalty recipient compared to computing the total royalty first and only dividing by the split at the end.

### Finding Description
`compute_royalty_amount()` is defined as: [1](#0-0) 

```
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
```

The correct mathematically-precise order for this calculation is `(abs(offered_amount) * percentage // MAX_ROYALTY_BASIS_POINTS) // royalty_split`, i.e. multiplication should be applied before either division. Instead, the current code divides by `royalty_split` first (`abs(offered_amount) // royalty_split`), which truncates the value before it is scaled by `percentage`. This is the exact bug class from the external report: dividing before multiplying causes avoidable, compounding precision loss.

This function is called from `NFTWallet.make_nft1_offer()` when constructing the royalty payment for each royalty-enabled NFT in an offer/trade, whenever `request_side_royalty_split > 1` (i.e., more than one royalty-enabled NFT is on the requesting side of an offer): [2](#0-1) 

This is directly reachable by any wallet user or offer counterparty who creates/takes an NFT offer bundling multiple royalty NFTs on one side (e.g. via `chia wallet make_offer` / `take_offer` RPCs), with no special privileges required.

Concrete example showing amplified loss: for `offered_amount = -7`, `royalty_split = 3`, `percentage = 9999` (99.99%):
- Current code: `7 // 3 = 2`; `2 * 9999 = 19998`; `19998 // 10000 = 1` royalty per NFT, times 3 NFTs = **3** total mojos paid to the royalty address.
- Correct order (multiply before divide): `7 * 9999 = 69993`; `69993 // 10000 = 6`; `6 // 3 = 2` per NFT, times 3 = **6** total mojos.

The current implementation pays roughly half of what the correctly-ordered arithmetic would yield in this case — a real, deterministic underpayment of the royalty recipient's entitled funds, baked directly into the spend bundle's `CreateCoin` outputs.

### Impact Explanation
This causes systematic accounting inaccuracy in NFT royalty distribution: royalty-address recipients (NFT creators) are paid less than their entitled percentage of the trade amount whenever an offer bundles multiple royalty-enabled NFTs sharing a `royalty_split`. Because the computed (undervalued) `CreateCoin` amount is embedded directly in the notarized/settlement payments of the offer's spend bundle, the shortfall is a real, unrecoverable value transfer away from the royalty recipient and toward the offer taker/maker — not a display-only rounding artifact. This qualifies as a concrete, unauthorized diversion of value in the offers/trade flow.

### Likelihood Explanation
Any two unprivileged wallet users negotiating an offer that includes multiple royalty NFTs on one side of the trade (a common real-world pattern, e.g., bundling several NFTs from the same creator/collection) will trigger this code path with no special conditions beyond constructing a normal offer. The loss magnitude grows with higher royalty percentages and larger `royalty_split` values, and is present on essentially every affected trade, not just edge cases.

### Recommendation
Reorder the arithmetic in `compute_royalty_amount()` to multiply before dividing, and only divide by `royalty_split` as the final step:
```python
amount = abs(offered_amount) * percentage // MAX_ROYALTY_BASIS_POINTS // royalty_split
```
This mirrors the exact fix pattern from the referenced report—perform division only after all multiplications are complete—to minimize precision loss in royalty accounting.

### Proof of Concept
Using the existing test harness in `chia/_tests/wallet/nft_wallet/test_nft_royalty.py` [3](#0-2) , add a case such as:
```python
def test_split_precision_loss() -> None:
    # current implementation
    current = compute_royalty_amount(offered_amount=-7, royalty_split=3, percentage=9999)
    assert current == uint64(1)  # per-NFT payment using existing divide-before-multiply logic

    # mathematically correct ordering (multiply before dividing)
    correct = (abs(-7) * 9999 // 10000) // 3
    assert correct == 2
    assert current < correct  # demonstrates systematic underpayment
```
This demonstrates that, for realistic percentage/split combinations, the current implementation underpays the royalty recipient relative to the mathematically correct multiply-then-divide ordering, matching the root cause identified in the referenced report.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```

```python
import pytest
```
