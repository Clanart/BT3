### Title
Nested/recursive precompile calls cause `AfterBalanceChange` to double-apply bank events, duplicating spendable balance in the EVM StateDB - ([File: precompiles/common/precompile.go])

### Summary
This is a "stale bookmark gets clobbered by re-entrant state" bug analogous to the Witch.sol `vaultOwners[vaultId]` overwrite. In Witch.sol, a mapping used to remember prior state (`vaultOwners[vaultId]`) is silently overwritten by a second `grab()` before the first operation completes, so later code (`buy`) reads the wrong bookmark and permanently loses/misroutes value. The Cosmos EVM analog is the `BalanceHandler.prevEventsLen` bookmark in `precompiles/common/balance_handler.go` combined with `runNativeAction` in `precompiles/common/precompile.go`, used to track "which bank events have already been converted to StateDB balance deltas."

### Finding Description
Every stateful precompile call goes through `Precompile.runNativeAction` (`precompiles/common/precompile.go:57-126`). Before executing the native action it records a bookmark: [1](#0-0) 
via `BeforeBalanceChange`, which stores `len(ctx.EventManager().Events())` at that instant: [2](#0-1) 

After `action(ctx)` runs, `AfterBalanceChange` replays every event emitted *since that bookmark* (`events[bh.prevEventsLen:]`) and applies `CoinSpent`/`CoinReceived`/fractional-balance deltas directly to the EVM `StateDB` via `AddBalance`/`SubBalance`: [3](#0-2) 

The problem: `ctx.EventManager()` in this call chain is the *same shared* Cosmos SDK event manager for the whole EVM transaction — it is not scoped per precompile invocation. If a precompile's native action itself performs a nested/re-entrant call that invokes another (or the same) stateful precompile — e.g. via `p.evmKeeper.CallEVMWithData(...)` as demonstrated by the test precompile's `Call0` (`evmd/tests/testdata/debug/debug.go:58-75`) which calls back into itself — that nested call runs its own `runNativeAction`, which creates a *new* `BalanceHandler` (`NewBalanceHandler()` at `precompiles/common/balance_handler.go:30-35`) and records **its own** `prevEventsLen` counted from the *current* (already-inflated) length of the shared event manager. The nested call's `AfterBalanceChange` correctly consumes and applies only the events emitted during its own nested execution, advancing state to match those events.

However, when execution returns to the **outer** call and the outer `AfterBalanceChange` runs, it still uses the outer's original `prevEventsLen`, which was captured *before* the nested call. The slice `events[outer.prevEventsLen:]` therefore includes **all events emitted during the nested call as well**, because bank/`CoinSpent`/`CoinReceived`/fractional-balance events are appended to the same shared `ctx.EventManager()` for the whole EVM transaction and are never removed. As a result, the outer `AfterBalanceChange` re-applies `AddBalance`/`SubBalance` for the same underlying bank transfer that the nested call's `AfterBalanceChange` already applied — a duplicate credit or debit to the StateDB balance of the EVM addresses involved. This is structurally identical to Witch.sol: a bookmark meant to represent "processed so far" gets silently invalidated by nested/recursive activity, and code downstream (the outer `AfterBalanceChange`) acts on stale information, corrupting accounting instead of merely losing state.

The repository itself documents recursive-call corruption in this exact code path in its own test suite comment: [4](#0-3) 

### Impact Explanation
If a nested precompile call triggers a bank `CoinSpent`/`CoinReceived` event (e.g. a `transfer`/staking/distribution/ICS20 precompile calling another precompile, or a contract that reenters the same precompile through a callback as in the debug precompile PoC), the outer `AfterBalanceChange` will reprocess and re-apply the same event(s) to the StateDB. Depending on transfer direction and address ordering this desynchronizes the EVM `StateDB` balance from the true bank-keeper-backed balance: the EVM-visible balance of a user/contract can be inflated (duplicated credit) relative to actual escrowed/spendable bank coins, or a spender's StateDB balance can be double-debited relative to actual bank balance. Because `StateDB.Commit()` writes these (now-wrong) balances back to the account keeper (`x/vm/statedb/statedb.go:695-745`), the corruption becomes a permanent, on-chain accounting divergence between native bank balance and EVM balance for unprivileged callers — matching the "unauthorized ... duplication ... irreversible accounting corruption of spendable user value across native balances, EVM balances" allowed-impact category.

### Likelihood Explanation
Triggering this requires only an ordinary unprivileged EVM transaction: any contract that calls a stateful precompile (staking, distribution, ICS20, erc20) in a way that causes that precompile's native logic to itself invoke another (or the same) stateful precompile — i.e., a nested/re-entrant precompile call within the same EVM call frame — is sufficient. No governance, validator, or relayer privilege is needed; only ordinary contract composition is required. The project's own integration test explicitly exercises "recursive precompile calls" through a caller contract and debug precompile, confirming the trigger path is reachable in production code (not a mock-only scenario).

### Recommendation
Do not rely on a single shared, transaction-wide `ctx.EventManager()` event index as a bookmark across nested precompile invocations. Options:
1. Give each nested `runNativeAction` invocation an isolated event manager (e.g., via `ctx.WithEventManager(sdk.NewEventManager())`) scoped strictly to that precompile call, so nested/outer event windows never overlap, and manually re-emit/merge the events into the parent context only after balances have been reconciled.
2. Alternatively, track a call-depth-aware watermark stack (analogous to the report's suggestion of a "stack of previous owners") so that an outer call's `AfterBalanceChange` only processes events not already consumed by any nested call, rather than a flat `events[prevEventsLen:]` slice that a nested call can silently "consume past."
3. Add an invariant check post-call verifying that the sum of StateDB balance deltas applied by `AfterBalanceChange` matches the net bank-keeper balance delta for the same span, failing loudly (reverting the precompile call) on mismatch instead of silently drifting.

```go
func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
```
