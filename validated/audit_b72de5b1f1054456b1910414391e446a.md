## Finding [1](#0-0) 

### Title
Missing zero-value check for `target_puzzle_hash` in `PoolWallet._verify_pool_state` can permanently burn pool/self-pooling rewards - (File: chia/pools/pool_wallet.py)

### Summary
`PoolState.target_puzzle_hash` is the "final payout destination" for pool/self-pooling rewards [2](#0-1) . The only validation performed on it, in `PoolWallet._verify_pool_state`, is an `is None` check [3](#0-2) . Since `target_puzzle_hash` is typed as a non-optional `bytes32`, this check can never actually trigger, and there is no check rejecting an all-zero (`bytes32.zeros`) puzzle hash, which is not spendable by anyone (functionally a burn address, as the codebase's own tests label a zero-filled 32-byte value `BURN_PUZZLE_HASH`).

### Finding Description
`_verify_pool_state` is invoked from `_verify_initial_target_state`, which gates both creation of a new pool wallet and every `join_pool` state transition (via `pw_join_pool` / `PWJoinPool.target_puzzlehash`) [4](#0-3) [5](#0-4) . The RPC entry point `pw_join_pool` passes the caller-supplied `request.target_puzzlehash` straight into `create_pool_state` with no additional zero-address filtering [6](#0-5) .

Once a `PoolState` with `target_puzzle_hash = bytes32.zeros` is committed on-chain (self-pooling final address, or pool-supplied address in `FARMING_TO_POOL`), reward coins farmed to the associated p2-singleton puzzle hash are permissionlessly claimable/absorbable by anyone into the singleton chain, and are ultimately paid out to the singleton's configured `target_puzzle_hash` on escape/self-claim, per the documented lifecycle ("records an outgoing transaction paying the absorbed amount to the current target puzzle hash") [7](#0-6) . If that destination is the zero puzzle hash, the payout is unrecoverable — structurally the same "burn via unauthenticated/permissionless action following an unchecked zero destination" pattern as the reported `PassThroughWalletImpl.passThroughTokens` issue.

This is not merely theoretical: the test suite repeatedly uses `bytes32.zeros` interchangeably as a "pool puzzle hash" target with no rejection anywhere in the codebase [8](#0-7) [9](#0-8) , confirming there is no runtime guard preventing an owner (or a malicious/compromised pool operator supplying the `target_puzzle_hash` during `FARMING_TO_POOL` setup) from configuring a burn destination.

### Impact Explanation
If `target_puzzle_hash` is ever set to the zero puzzle hash (owner mistake, buggy client, or malicious pool operator value accepted during `join_pool`), every future pool/self-pooling reward payout for that plot-NFT/singleton is irrecoverably lost, since permissionless reward-claiming logic will keep sending real XCH to an unspendable puzzle hash. This is a concrete, unauthorized/irrecoverable loss of funds reachable without any privileged access beyond the normal `pw_join_pool`/pool-creation flow.

### Likelihood Explanation
Likelihood is moderate: it requires either a user/client bug supplying an all-zero address, or a malicious/compromised pool server returning a zero `target_puzzle_hash` during the pool protocol handshake that gets incorporated via `join_pool`/`pw_join_pool`. No additional privilege beyond normal use of the plotnft/pooling wallet flow is required, and the actual burning of subsequent reward coins is executed by ordinary, permissionless "absorb"/claim transactions.

### Recommendation
Add an explicit zero-value check for `target_puzzle_hash` (`if state.target_puzzle_hash == bytes32.zeros`) in `PoolWallet._verify_pool_state` (and equivalently on the `PlotNFT2Wallet` / `PoolConfig.pool_puzzle_hash` path), rejecting it the same way `pool_url`/`relative_lock_height` misconfigurations are rejected, rather than relying on the always-false `is None` check.

### Proof of Concept
1. Call `pw_join_pool` (or the plot-NFT create/join flow) with `target_puzzlehash=bytes32.zeros` — `_verify_pool_state`/`_verify_initial_target_state` accepts it because the only guard is `state.target_puzzle_hash is None`, which is never true for a `bytes32` value.
2. The pool singleton transitions to `FARMING_TO_POOL`/`SELF_POOLING` with the zero target puzzle hash committed on-chain.
3. Anyone (any node/wallet) can subsequently submit the permissionless absorb/claim spend that pays farmed rewards to `target_puzzle_hash`.
4. Rewards are sent to `bytes32.zeros`, an address with no known spending puzzle, permanently burning them.

    def _verify_pool_state(cls, state: PoolState) -> str | None:

        elif state.state in {PoolSingletonState.FARMING_TO_POOL.value, PoolSingletonState.LEAVING_POOL.value}:

            return "Internal Error"

        if target_state.state != FARMING_TO_POOL.value:
            raise ValueError(f"join_pool must be called with target_state={FARMING_TO_POOL} (FARMING_TO_POOL)")
        if self.target_state is not None:
            raise ValueError(f"Cannot join a pool while waiting for target state: {self.target_state}")
        if await self.have_unconfirmed_transaction():
            raise ValueError(
                "Cannot join pool due to unconfirmed transaction. If this is stuck, delete the unconfirmed transaction."
            )

        current_state: PoolWalletInfo = await self.get_current_state()

        total_fee = fee
        if current_state.current == target_state:
            self.target_state = None
            msg = f"Asked to change to current state. Target = {target_state}"
            self.log.info(msg)
            raise ValueError(msg)
        elif current_state.current.state in {SELF_POOLING.value, LEAVING_POOL.value}:
            total_fee = fee
        elif current_state.current.state == FARMING_TO_POOL.value:
            total_fee = uint64(fee * 2)

        if self.target_state is not None:
            raise ValueError(
                f"Cannot change to state {target_state} when already having target state: {self.target_state}"
            )

class PoolState(Streamable):
    """
    `PoolState` is a type that is serialized to the blockchain to track the state of the user's pool singleton
    `target_puzzle_hash` is either the pool address, or the self-pooling address that pool rewards will be paid to.
    `target_puzzle_hash` is NOT the p2_singleton puzzle that block rewards are sent to.
    The `p2_singleton` address is the initial address, and the `target_puzzle_hash` is the final destination.
    `relative_lock_height` is zero when in SELF_POOLING state
    """

    version: uint8
    state: uint8  # PoolSingletonState
    # `target_puzzle_hash`: A puzzle_hash we pay to
    # When self-farming, this is a main wallet address
    # When farming-to-pool, the pool sends this to the farmer during pool protocol setup

    # owner_pubkey is set by the wallet, once
    owner_pubkey: G1Element
    pool_url: str | None
    relative_lock_height: uint32

        self,
        request: PWJoinPool,
        action_scope: WalletActionScope,
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> PWJoinPoolResponse:
        wallet = self.service.wallet_state_manager.wallets[request.wallet_id]

        if isinstance(wallet, PoolWallet):
            pool_wallet_info: PoolWalletInfo = await wallet.get_current_state()
            if (
                pool_wallet_info.current.state == FARMING_TO_POOL.value
                and pool_wallet_info.current.pool_url == request.pool_url

                FARMING_TO_POOL,
                request.target_puzzlehash,
                pool_wallet_info.current.owner_pubkey,
                request.pool_url,
                request.relative_lock_height,
            )

            total_fee = await wallet.join_pool(new_target_state, request.fee, action_scope)
