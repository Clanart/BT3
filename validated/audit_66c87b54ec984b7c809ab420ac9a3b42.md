### Title
Unbounded attacker-controlled allocation in `ThresholdKeys::read` enables deserialization memory-DoS - (File: crypto/dkg/src/lib.rs)

### Summary
CVE-2016-6793 is a deserialization bug: `DiskFileItem` processed attacker-supplied serialized data in a way that enabled denial of service. The analog in Serai is `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`), which deserializes `ThresholdKeys` from an untrusted byte stream and performs attacker-controlled heap allocation and parsing *before* validating the threshold parameters.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from the input stream as raw `u16` values, then immediately trusts `n`:

- `Interpolation::Constant` allocates `Vec::with_capacity(usize::from(n))` and then reads `n` scalars via `C::read_F` (`crypto/dkg/src/lib.rs:607-612`).
- It then loops `(1 ..= n)` reading `n` group elements into `verification_shares` (`crypto/dkg/src/lib.rs:620-623`).
- Only after all of this does it call `ThresholdParams::new(t, n, i)` to validate the values (`crypto/dkg/src/lib.rs:625-626`).

Because `n` is a 16-bit attacker-controlled field, a crafted input whose actual length is only ~40 bytes (curve ID + `t`/`n`/`i` + interpolation tag) triggers `Vec::with_capacity(65535)` — an allocation of ~2 MB for `Scalar` elements — plus `HashMap` setup, before the first `read_F` fails on the empty stream. This is the same pattern rust-bitcoin and the Serai Ethereum machine explicitly defend against (`networks/ethereum/src/machine.rs:51-60` reads length-prefixed data in 1 KB chunks, noting "A valid DoS would be to claim a 4 GB data is present for only 4 bytes"); `ThresholdKeys::read` applies no such defense.

Additionally, even when the stream is fully provisioned, `t`, `n`, and `i` are never checked before they drive the allocation and loop bounds, so a serialized `ThresholdKeys` claiming `n = 65535` is fully parsed (65535 scalars + 65535 points ≈ 4 MB of `read_F`/`read_G` work, each point decompressed and canonicality-checked per `Ciphersuite::read_G`, `crypto/ciphersuite/src/lib.rs:91-101`) and only then rejected by `ThresholdParams::new`.

### Impact Explanation
`ThresholdKeys::read` is listed as a reachable entry point for untrusted bytes (it is used, e.g., by `GeneratedKeysDb::read_keys` in `processor/src/key_gen.rs:56-60` and wherever serialized keys are ingested). Each call lets a remote party force ~2-4 MB of allocation and tens of thousands of point-decompression operations with a tiny input. Replayed across many calls, this exhausts memory and CPU on the target processor/coordinator — a denial of service of the same class as CVE-2016-6793 (resource consumption via crafted serialized input), reachable by an unprivileged party supplying bytes.

### Likelihood Explanation
High. The field `n` is a single `u16` at a fixed offset in the wire format; no authentication or validation precedes its use as an allocation/loop bound. Any code path that feeds peer- or disk-supplied bytes to `ThresholdKeys::read` is exploitable. The only mitigating factor is that the allocation is transient (freed on error), so a persistent OOM requires repeated/concurrent invocations — hence Medium rather than High severity.

### Recommendation
Validate `t`, `n`, `i` via `ThresholdParams::new` (or explicit bounds checks, e.g. `n <= MAX_PARTICIPANTS`) immediately after reading them, before any allocation or loop. Replace `Vec::with_capacity(n)` and the `1 ..= n` loops with incremental pushes bounded by validated `n`, consistent with the chunked-read approach already used in `Call::read` (`networks/ethereum/src/machine.rs:54-60`).

### Proof of Concept
```rust
use std::io;
use frost::curve::Secp256k1;
use frost::ThresholdKeys;

fn main() {
    // Construct a ThresholdKeys encoding with n = 0xFFFF but no body.
    let mut buf = vec![];
    // C::ID for Secp256k1 (length-prefixed)
    buf.extend(u32::try_from(Secp256k1::ID_LEN).unwrap().to_le_bytes());
    buf.extend(Secp256k1::ID_BYTES);
    // t = 1, n = 65535, i = 1
    buf.extend(1u16.to_le_bytes());
    buf.extend(u16::MAX.to_le_bytes());
    buf.extend(1u16.to_le_bytes());
    // interpolation = Constant(0)
    buf.push(0);

    // ~50 bytes of input causes Vec::with_capacity(65535) (~2 MB) and
    // attempts to read 65535 scalars before params are validated.
    let _ = ThresholdKeys::<Secp256k1>::read(&mut buf.as_slice());
}
```

A single invocation causes an allocation orders of magnitude larger than the input and O(n) `read_F`/`read_G` work on attacker-controlled `n`; looping it from untrusted input exhausts memory/CPU.
