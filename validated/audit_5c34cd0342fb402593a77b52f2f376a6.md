### Title
Unbounded u32 element count in `SchnorrAggregate::read` enables remote resource exhaustion - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs#L77-L88))

### Summary
`SchnorrAggregate::read` trusts an attacker-supplied 32-bit length field and performs up to 4,294,967,295 point deserialization attempts (`C::read_G`) without any bound, cap, or pre-validation of the remaining input. This mirrors the OpenEXR advisory class — an untrusted length/offset drives a memory operation far beyond the actual buffer — mapped onto Serai's streaming `Read`-based decoding, where the attacker-controlled count controls the amount of work and allocation performed on untrusted bytes. [1](#0-0) 

### Finding Description
`SchnorrAggregate::read` reads a little-endian `u32` and then loops that many times calling `C::read_G(reader)`, pushing each decoded point into `Rs` before reading the trailing scalar `s`. There is no maximum on the declared count, no check that the declared count is consistent with the bytes actually available, and no chunked/bounded read strategy (contrast `Call::read` in `networks/ethereum/src/machine.rs`, which explicitly chunks reads because "a valid DoS would be to claim a 4 GB data is present for only 4 bytes" — the same awareness was not applied here). [1](#0-0) [2](#0-1) 

An unprivileged party controlling bytes fed into this reader (aggregate signatures are, by design, data produced by external signers and transported over the wire) can declare `len = u32::MAX` and then stream valid point encodings, forcing the verifier to decode and retain up to ~137 GB of `C::G` elements in `Rs` — and, for a `Read` backed by a network/socket rather than a fixed slice, the loop never terminates early because `read_G` succeeds as long as bytes keep arriving. Each iteration performs a full point decompression/validation, so even a moderate stream causes disproportionate CPU burn per byte. [3](#0-2) 

### Impact Explanation
Availability loss equivalent to the OpenEXR heap-overflow class: the declared length, not the real data size, dictates work. A single malformed `SchnorrAggregate` can cause unbounded memory growth (vec of up to 4 billion group elements) and/or sustained CPU consumption during deserialization, crashing or stalling the verifying node before any signature verification occurs. `verify` would anyway reject `Rs.len() != keys_and_challenges.len()`, but that check is only reached after the malicious length has already been fully consumed and allocated. [4](#0-3) 

### Likelihood Explanation
Any context where an aggregate signature is deserialized from untrusted input (P2P messages, RPC payloads, resync data) reaches this code with a fully attacker-controlled 4-byte count. The attack requires no privileges, no valid signature, and no cooperation — only the ability to supply bytes to the reader. The cost to the attacker is minimal (4 bytes to trigger the maximal decode attempt against a streaming reader).

### Recommendation
Cap the declared count before the loop: since `verify` requires `Rs.len() == keys_and_challenges.len()`, either (a) have `read` take an expected maximum and reject larger counts up front, or (b) enforce a hard protocol bound (e.g., `MAX_KEY_SHARES_PER_SET` or a small constant) on the `u32` before allocating/reading. Rejecting `len > expected` before touching `reader` eliminates the asymmetry between declared and actual work. [3](#0-2) 

### Proof of Concept
Feed `SchnorrAggregate::<C>::read` a buffer/stream beginning with `ff ff ff ff` (u32::MAX little-endian) followed by a repeating valid compressed-point encoding. Against a `&[u8]` reader the loop errors at EOF only after attempting `u32::MAX` reads; against a streaming `Read` (e.g., a socket wrapper) each 33/32-byte block of attacker data is decoded and retained, letting ~130 bytes/sec of upload translate into gigabytes of resident `Vec<C::G>` and continuous point-decompression CPU until OOM — no valid signature ever required.

Caveat: if all production call sites only ever invoke `SchnorrAggregate::read` on strictly bounded in-memory slices, the practical impact degrades to a bounded-parse error rather than exhaustion; I could not enumerate every caller within the search budget, so the severity rests on the untrusted-stream reachability described above.

    let mut len = [0; 4];
    reader.read_exact(&mut len)?;

    #[allow(non_snake_case)]
    let mut Rs = vec![];
    for _ in 0 .. u32::from_le_bytes(len) {
      Rs.push(C::read_G(reader)?);
    }

    Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
  }
