### Title
`OP_TRUE` Stub Replaces Real Groth16 BitVM Disprove Scripts in Debug Builds, Enabling Unauthorized Operator Collateral Burn - (File: `core/src/bitvm_client.rs`)

---

### Summary

`ClementineBitVMPublicKeys::get_g16_verifier_disprove_scripts` returns a single `OP_TRUE` script (`0x51`) instead of the real Groth16 BitVM disprove scripts whenever `cfg!(debug_assertions)` is true (i.e., all non-`--release` builds). This stub is used in two production-critical paths: (1) computing and storing the disprove Taproot root hash during deposit setup, and (2) constructing the actual Disprove transaction. In any debug build, the Kickoff transaction's disprove output is committed to a Taproot tree containing only `OP_TRUE`, meaning any verifier holding the pre-signed N-of-N disprove transaction can broadcast it and burn an honest operator's collateral without providing a valid Groth16 proof of fraud.

---

### Finding Description

In `core/src/bitvm_client.rs`, the method `get_g16_verifier_disprove_scripts` on `ClementineBitVMPublicKeys` is:

```rust
pub fn get_g16_verifier_disprove_scripts(&self) -> Result<Vec<ScriptBuf>, BridgeError> {
    if cfg!(debug_assertions) {
        Ok(vec![ScriptBuf::from_bytes(vec![0x51])]) // OP_TRUE
    } else {
        Ok(replace_disprove_scripts(self)?)
    }
}
``` [1](#0-0) 

`cfg!(debug_assertions)` evaluates to `true` in every `cargo build` and `cargo test` invocation that does not pass `--release`. This is the default build mode for development and CI test runs.

This function is called in two production-critical locations:

**Location 1 — Deposit setup / `set_operator_keys` in `core/src/verifier.rs`:**

```rust
let scripts: Vec<ScriptBuf> = bitvm_pks.get_g16_verifier_disprove_scripts()?;
let taproot_builder = taproot_builder_with_scripts(scripts);
let root_hash = taproot_builder
    .try_into_taptree()
    .expect("taproot builder always builds a full taptree")
    .root_hash()
    .to_byte_array();
``` [2](#0-1) 

In debug mode, `scripts` is `[OP_TRUE]`. The resulting `root_hash` is `taproot_hash(OP_TRUE)` — not the hash of the real 364 Groth16 disprove scripts. This wrong root hash is then persisted to the database via `insert_bitvm_setup_if_not_exists` and later used to construct the Kickoff transaction's disprove Taproot output as a hidden node. [3](#0-2) 

**Location 2 — Disprove transaction construction in `core/src/builder/transaction/creator.rs`:**

---

### Impact Explanation

The Kickoff transaction's disprove output is a Taproot UTXO whose script tree encodes the BitVM2 fraud-proof game. In debug mode, this output is committed to a tree containing only `OP_TRUE` as the disprove leaf. The pre-signed Disprove transaction (signed by all N-of-N verifiers during deposit setup) spends this output via `SpendPath::Unknown` / `NormalSignatureKind::NoSignature` — meaning the witness for the disprove leaf is provided at broadcast time. [7](#0-6) 

Because the disprove leaf is `OP_TRUE`, any party holding the pre-signed disprove transaction can satisfy it with an empty witness and broadcast the transaction. This burns the operator's collateral (the `BurnConnector` output from the Round transaction) without any valid Groth16 proof of fraud. An honest operator who has posted correct assertions is fully exposed to collateral loss.

The second input of the disprove transaction (the `BurnConnector`) requires the pre-signed N-of-N key-path signature (`NormalSignatureKind::Disprove2`). Since this signature is collected during the deposit setup phase — where the same debug-mode `OP_TRUE` root hash was used to construct the Kickoff tx — the pre-signed transaction is internally consistent and valid on-chain.

**Concrete corrupted value:** The `root_hash` stored in the database and embedded in the Kickoff transaction's disprove output is `taproot_hash(OP_TRUE)` instead of `taproot_hash(real_364_groth16_scripts)`. This single wrong hash makes the entire BitVM2 fraud-proof mechanism unconditionally spendable.

---

### Impact Explanation (Allowed Impact Gate)

- **Slashable exposure of operator collateral:** Any verifier can burn the operator's `BurnConnector` collateral without a valid proof of fraud, by broadcasting the pre-signed disprove transaction against the `OP_TRUE` disprove leaf.
- **Broken challenge safety invariant:** The BitVM2 challenge-response game requires that the disprove transaction can only succeed if the operator's Groth16 proof is demonstrably wrong. In debug builds this invariant is completely eliminated.
- **Tests do not cover production code:** All integration and E2E tests run in debug mode and exercise the `OP_TRUE` path, not the real 364-script Groth16 verification path — a direct analog to the AuctionTimeControl bug.

---

### Likelihood Explanation

`cfg!(debug_assertions)` is `true` by default in all `cargo build` and `cargo test` invocations. Every CI run, every developer test, and any deployment that does not explicitly use `cargo build --release` activates this stub. The E2E disprove tests (`disprove_script_test_healthy`, `disprove_script_test_corrupted_assert`) are marked `#[ignore]` and run separately, but they still run in debug mode and therefore test `OP_TRUE`, not the real scripts. [8](#0-7) 

If a production node is deployed from a debug build (e.g., via `cargo run` without `--release`), the vulnerability is immediately active for every deposit processed by that node.

---

### Recommendation

1. Remove the `cfg!(debug_assertions)` branch entirely from `get_g16_verifier_disprove_scripts`. The real `replace_disprove_scripts` path must be used unconditionally in all builds.
2. If the real script generation is too slow for tests, use a dedicated test feature flag (e.g., `#[cfg(feature = "test-stubs")]`) that is explicitly opt-in and never compiled into production binaries, and document that it must never be used in integration tests that exercise the disprove path.
3. Add a compile-time or runtime assertion that rejects startup if `debug_assertions` is enabled in a context where real disprove scripts are expected.

---

### Proof of Concept

**Setup:** Build and run the Clementine stack without `--release` (the default). Perform a deposit and withdrawal, triggering the full kickoff → challenge → assert flow.

**Observation:** The Kickoff transaction's disprove output (vout `UtxoVout::Disprove`) is committed to a Taproot tree whose only disprove leaf is `OP_TRUE` (script bytes `[0x51]`).

**Exploit:** Any verifier holding the pre-signed disprove transaction can broadcast it immediately after the assert transactions are confirmed, providing an empty witness for input 0 (the `OP_TRUE` leaf). The transaction is valid on-chain because:
- Input 0 (disprove UTXO): satisfied by `OP_TRUE` with empty witness.
- Input 1 (BurnConnector): satisfied by the pre-signed N-of-N key-path signature collected during deposit setup.

**Result:** The operator's collateral is burned. The operator has no recourse because the pre-signed transaction is valid and the disprove output is unconditionally spendable. The honest operator loses their full collateral bond without any proof of fraud.
