### Title
Unvalidated `kip71.gastarget` governance parameter enables division-by-zero panic in KIP-71 base fee calculation - ([File: params/kip71_config.go])

### Summary
`kip71.gastarget` is a mutable governance parameter that controls Kaia's EIP-1559-style (KIP-71/Magma) base fee adjustment formula. Unlike its sibling parameter `kip71.basefeedenominator`, which explicitly rejects zero, `kip71.gastarget` uses `noopFormatChecker` and accepts any `uint64` value, including zero. A zero `GasTarget` causes `KIP71Config.NextMagmaBlockBaseFee` to perform a `big.Int` division by zero, which panics in Go. This function is invoked on every block during header verification and block assembly, so a single governance vote setting `gastarget` to `0` can crash every node that reaches the affected block, blocking chain progress network-wide.

### Finding Description
The governance parameter registry defines format checkers per parameter to reject invalid values before they are accepted into a `ParamSet`: [1](#0-0) 
Note that `Kip71BaseFeeDenominator` explicitly checks `v != 0` to avoid division by zero, but `Kip71GasTarget` uses `noopFormatChecker`, which always returns `true` regardless of value: [2](#0-1) [3](#0-2) 

The consistency check performed on governance votes (`checkConsistency`) also does not add any special-case validation for `Kip71GasTarget` — it is grouped with parameters that are "valid as long as it passes the format checks in `NewVoteData()`. No more checks here": [4](#0-3) 

As a result, `gastarget` can be set to `0` through a normal governance vote and will be accepted into the effective `ParamSet` and subsequently into `KIP71Config.GasTarget` via `ToKip71Config`: [5](#0-4) 

`GasTarget` is then used as a divisor in `NextMagmaBlockBaseFee`: [6](#0-5) [7](#0-6) 

Both branches (`parentGasUsed > gasTarget` and `parentGasUsed < gasTarget`) call `x.Div(x, new(big.Int).SetUint64(gasTarget))`. If `gasTarget == 0`, this is a division by zero in `math/big`, which panics at runtime (Go's `big.Int.Div`/`Quo` explicitly panics on division by zero, it does not return an error). The only case that avoids the divide is `parentGasUsed == gasTarget`, i.e. both being `0`, which requires the block to have exactly zero gas used — not the general case.

This function is the core of the Magma/KIP-71 base fee mechanism and is invoked from block header verification via `VerifyMagmaHeader` (referenced in `blockchain/block_validator.go`) and from block assembly (referenced in `work/worker.go`), meaning it runs on every full node validating a block and on the proposer building the next block, after the parameter takes effect.

This closely parallels the SaiTub `tax` bug: an operationally sensitive numeric governance parameter (`tax` analog: `kip71.gastarget`) lacks a `>= minimum` validation check that its sibling parameters do have, and an out-of-range value causes an arithmetic exception (there: integer underflow triggering a revert in `drip`; here: division by zero triggering a Go panic) in a function that is unconditionally exercised by the most fundamental operations of the system (there: SaiTub CDP interfaces and SaiTop settlement; here: block header verification and block assembly for every block).

### Impact Explanation
If `kip71.gastarget` is voted to `0` (accidentally or maliciously by a governing/council node with voting rights), any block with nonzero gas usage after the effective epoch will cause `NextMagmaBlockBaseFee` to panic when computing/verifying the next base fee. This affects:
- Block proposers building the next block (`work/worker.go`), causing block production to fail/crash.
- All full nodes verifying incoming blocks (`blockchain/block_validator.go` via `VerifyMagmaHeader`), causing them to crash or reject all subsequent blocks.
- RPC gas price estimation code paths (`node/cn/gasprice/gasprice.go`, `node/cn/gasprice/feehistory.go`) that also call this function.

The practical effect is a chain-wide halt (denial of service) once the malformed parameter becomes effective, since every node that processes a block past that point hits the same panic. Because the parameter is also "sticky" (its bad value persists in `ParamSet`/`ChainConfig` state until overridden by a further vote), and because voting/consensus processing itself depends on being able to process blocks, recovery may require operator intervention (similar to how, in the original report, `tax` became effectively unfixable through normal channels).

### Likelihood Explanation
Likelihood is Medium: this requires a governance vote to set `kip71.gastarget` to `0`, which is restricted to authorized governance voters (validators/council in `single` mode, per `GovernanceMode`), not an arbitrary unprivileged sender. However, per the accepted scope for this analysis, governance-parameter mis-validation issues are explicitly in-scope regardless of voter privilege level, and the report itself is explicitly about "accidental" misconfiguration risk (as in the original SaiTub report where `mold` was "accidentally used"). Given there is no format/range check at all preventing `0` for this specific parameter (while an analogous parameter, `BaseFeeDenominator`, does have such protection), an operator/validator misconfiguration is a realistic and easy accidental trigger, and the impact (chain halt) is severe and immediate.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0`, mirroring the protection already applied to `Kip71BaseFeeDenominator`:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
}
```
Additionally, as defense-in-depth, `NextMagmaBlockBaseFee` in `params/kip71_config.go` should guard against `GasTarget == 0` directly (e.g., returning an error or falling back to a safe default) rather than relying solely on upstream governance validation, consistent with the existing defensive fallback already present for `BaseFeeDenominator == 0` at line 71-73 of the same file.

### Proof of Concept
1. A governance vote for `kip71.gastarget` with value `0` is submitted via `headerGovAPI.Vote("kip71.gastarget", uint64(0))`.
2. `NewVoteData`/`Params[Kip71GasTarget].FormatChecker` (i.e., `noopFormatChecker`) accepts the value unconditionally: [8](#0-7) .
3. `checkConsistency` performs no additional validation for `gov.Kip71GasTarget`, so the vote is accepted into the header governance data: [4](#0-3) .
4. Once effective, `GetParamSet(blockNum).GasTarget == 0` propagates into `ToKip71Config().GasTarget`: [5](#0-4) .
5. On the next block with `parentHeaderGasUsed != 0`, `NextMagmaBlockBaseFee` executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0`: [9](#0-8) , causing a runtime panic in every node calling this function during block verification (`VerifyMagmaHeader` in `blockchain/block_validator.go`) or block assembly (`work/worker.go`), halting block production/validation network-wide.
