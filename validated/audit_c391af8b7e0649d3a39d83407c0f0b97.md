### Title
Reward Sniping/Dilution via Instant, Non-Time-Weighted `queueNewRewards` Distribution Triggered by Permissionless `castVotes`/`harvestSinglePool` - ([File: rewards/BaseRewardPool.sol], [File: wombat/WombatStaking.sol], [File: wombat/WombatBribeManager.sol])

### Summary
`BaseRewardPool._provisionReward` distributes newly queued rewards instantly and proportionally to whatever `totalStaked()`/`balanceOf(_account)` values exist at the exact moment `queueNewRewards` is called, with no time-vesting or streaming mechanism. Because `WombatBribeManager.castVotes()` and `harvestSinglePool()` are callable by any unprivileged address and internally trigger `WombatStaking.vote()` → `IBaseRewardPool.queueNewRewards()`, an attacker can deposit LP into `MasterMagpie` immediately before calling these harvest functions in the same transaction, capture a share of the just-harvested bribe reward proportional to their temporary stake, and withdraw right after — diluting the rewards earned by genuine long-term stakers.

### Finding Description
`BaseRewardPool._provisionReward` computes the reward-per-token increment using live state: [1](#0-0) 
`totalStaked()` and `balanceOf(_account)` are both **live reads** from `MasterMagpie`'s current state rather than snapshots: [2](#0-1) 

`earned()` is a pure function of the current `balanceOf(_account)` and the delta between the current `rewardPerToken` and the account's `userRewardPerTokenPaid`, which is only updated when the account's balance changes (via the `updateReward` modifier calling `_updateFor`): [3](#0-2) [4](#0-3) 

`queueNewRewards` is `onlyManager`-gated at the `BaseRewardPool` level, but the *trigger path* that calls it — `WombatStaking.vote()` — is invoked from `WombatBribeManager.castVotes()` and `harvestSinglePool()`, both of which have **no access-control modifier** and can be called by any address: [5](#0-4) [6](#0-5) 
`WombatStaking.vote()` then loops over pools calling `queueNewRewards` for each reward token per pool: [7](#0-6) 

Exploit flow:
1. Attacker deposits LP into `MasterMagpie` for pool `i` (this updates their `userRewardPerTokenPaid` to the pre-harvest `rewardPerTokenStored`, and increases live `totalStaked()`).
2. In the same transaction, attacker calls `harvestSinglePool([lp_i])` (or `castVotes`), which harvests accrued bribes and calls `queueNewRewards`, increasing `rewardPerTokenStored` by `reward / totalStaked()` — where `totalStaked()` now already includes the attacker's just-deposited balance.
3. Attacker's `earned()` immediately reflects `balanceOf(attacker) * (newRewardPerToken - oldPaid)`, giving them a share of the reward despite having staked for zero economically meaningful duration.
4. Attacker withdraws and claims, exiting the position within the same transaction.

Because the reward is not streamed/vested over time (unlike, e.g., Synthetix's `rewardRate` over a fixed `rewardsDuration`), and because the harvest-trigger functions are permissionless, there is no mechanism (nonReentrant, cooldown, or snapshot-at-vote-time) preventing this. The `updateReward`/`_updateFor` logic only protects against double-counting; it does nothing to prevent last-second deposits from capturing a slice of an already-accrued, about-to-be-distributed reward, which simultaneously dilutes the `rewardPerTokenStored` increment that genuine long-term stakers receive.

### Impact Explanation
This results in theft of already-accrued bribe/reward yield from genuine long-term stakers in a `BaseRewardPool`, matching the Immunefi impact class "theft of unclaimed yield" / "direct theft of user funds." The magnitude scales with the size of the attacker's temporary deposit relative to existing `totalStaked()` and the size of the pending harvested reward.

### Likelihood Explanation
Preconditions: attacker needs (a) access to the pool's LP/deposit token (owned or flash-loaned if externally flash-loanable), (b) ability to call `MasterMagpie` deposit/withdraw and `WombatBribeManager.castVotes()`/`harvestSinglePool()` in one transaction (both are public, unprivileged functions). No special role is required. This is repeatable every time meaningful bribe rewards have accrued and are about to be harvested, which is a routine, expected operational event (harvesting happens regularly). The main constraints I could not fully verify from available code are: (1) whether `MasterMagpie.deposit`/`withdraw` enforce any cooldown or same-block restriction, and (2) whether a withdrawal fee exists that could offset the sniped gain — these were not confirmed within the scope of retrieved code for `rewards/MasterMagpie.sol`.

### Recommendation
Replace instant lump-sum reward crediting with a time-weighted/streamed distribution (e.g., Synthetix-style `rewardRate` over a fixed duration), or snapshot `totalStaked()`/eligible balances prior to computing the harvest-triggering transaction and require a minimum staking duration/cooldown before a deposit is eligible to receive freshly queued rewards. Additionally, consider restricting or rate-limiting `castVotes`/`harvestSinglePool` callers, or applying a delay between deposit and reward eligibility to prevent same-block sniping.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `BaseRewardPool`, `WombatStaking`, `WombatBribeManager` with a mock Wombat `voter`/bribe contract that has pending bribe rewards for pool `i`.
2. Simulate an existing "genuine" staker depositing LP into pool `i` and letting bribes accrue (via a prior `castVotes`/time passing) without harvesting yet.
3. In a single test transaction (or via a mock flash-loan contract), have the attacker:
   - Borrow/acquire pool `i` LP tokens.
   - `MasterMagpie.deposit(lp_i, largeAmount)`.
   - Call `WombatBribeManager.harvestSinglePool([lp_i])`, triggering `queueNewRewards`.
   - `MasterMagpie.withdraw(lp_i, largeAmount)` and call `getReward` on the rewarder to claim the sniped share.
   - Repay flash loan.
4. Assert: attacker's net reward-token balance increases (`profit > 0`) while the genuine staker's `earned()` value after the harvest is lower than it would have been had the attacker's deposit not occurred (compute expected `rewardPerTokenStored` with and without attacker's temporary stake and show the genuine staker's post-harvest `earned()` is diluted accordingly).
