### Title
Reward-per-token dilution via same-block stake-then-harvest in `voteAndCast` - ([File: rewards/BribeRewardPool.sol], [wombat/WombatBribeManager.sol])

### Summary
`WombatBribeManager.voteAndCast` calls `vote()` (which credits the caller's stake via `BribeRewardPool.stakeFor`, increasing `totalSupply`/`_balances` immediately) and then `castVotes()` (which harvests bribes and queues them into `rewardPerTokenStored` using the now-inflated `totalSupply`). Because the reward accounting is not time-weighted, the newly-added stake participates fully in the reward index update for a bribe that accrued before the staker contributed any voting weight.

### Finding Description
`stakeFor` uses `updateRewards(_for, rewardTokens)`, which snapshots the caller's `userRewardPerTokenPaid` at the pre-stake `rewardPerTokenStored` value [3](#0-2) , then immediately increases `totalSupply` and `_balances[_for]` [4](#0-3) . Later in the same transaction, `castVotes()` triggers `wombatStaking.vote()`, which harvests the epoch's bribe and calls `queueNewRewards` on the rewarder [1](#0-0) . `_provisionReward` computes `rewardPerTokenStored += amountReward * 10**decimals / totalStaked()` using the **current** `totalStaked()`, which already includes the attacker's freshly added stake [5](#0-4) . Because the attacker's `userRewardPerTokenPaid` was snapshotted *before* this reward-per-token increase, when they later call `getReward`/`claimBribe`, `_earned` credits them `_balances[_for] * (rewardPerTokenStored_after - rewardPerTokenStored_before) / 1e18`, giving them a share of a bribe that accrued entirely before they added their vote in this same transaction [6](#0-5) . No modifier, cooldown, or time-weighting prevents this — `updateRewards`/`updateReward` only guards against double counting, not against timing manipulation.

### Impact Explanation
This dilutes `rewardPerTokenStored` for the bribe being queued (since the denominator `totalStaked()` is artificially inflated by the just-added vote), reducing what long-standing voters would have earned, while allowing the attacker to immediately claim a proportional share of the bribe they didn't help accrue. This is a value transfer from pre-existing voters to the attacker within a single atomic transaction, repeatable every epoch/cast cycle. However, `totalSupply` and the sum of `userVotedForPoolInVlmgp` for the pool remain accounting-consistent (both are updated together via `stakeFor`) — the underlying reconciliation invariant claimed in the prompt is not actually broken; the real issue is reward-timing/dilution, not a supply/vote accounting desync.

### Likelihood Explanation
The attacker must hold sufficient vlMGP voting power (`getUserVotable(msg.sender)`) to move `_deltas` into the target pool, and must be the one calling `voteAndCast` (or sequence `vote()` immediately before `castVotes()`), both of which are permissionless/public functions with no special role required [7](#0-6) [8](#0-7) . The gain scales with the attacker's vlMGP relative to the pool's total staked weight and the bribe size for that epoch, so it requires meaningful capital (locked MGP) to have material impact, and the theft is proportional/diluted rather than a full drain.

### Recommendation
Snapshot/settle the pool's reward index (call `_updateFor`/checkpoint) and require that newly added stake only starts accruing from the moment it's added, i.e., process `queueNewRewards` (via `castVotes`) **before** the new epoch's `stakeFor` calls take effect, or introduce a time-weighted/epoch-boundary mechanism (e.g., only allow votes to count towards the *next* bribe distribution, not the one currently being cast in the same transaction). Alternatively, disallow `vote()` and `castVotes()` from being combined for pools with a pending un-cast bribe, or checkpoint `rewardPerTokenStored` against the pre-transaction `totalSupply` rather than the post-stake value.

### Proof of Concept
1. Deploy `BribeRewardPool` behind a mock `WombatBribeManager` operator; set up two voters, A (pre-existing, balance = 100) and B (attacker, balance = 0).
2. Have the bribe manager mock call `stakeFor(B, 100)` (simulating B's `vote()` call), then immediately call `queueNewRewards(1000, rewardToken)` (simulating `castVotes()` harvesting a bribe accrued while only A had voted).
3. Assert `earned(B, rewardToken) > 0` even though B had zero balance for the entire period the bribe accrued, and compare `earned(A, rewardToken)` against the value A would have received had B not staked before the harvest (run a differential test: same total bribe, but B stakes *after* `queueNewRewards` instead of before) — assert A's reward differs between the two scenarios, demonstrating dilution/timing exploitation.
4. Confirm `totalSupply` and sum of `userVotedForPoolInVlmgp` remain reconciled in both runs (they do — the invariant as stated in the prompt does not actually break), isolating the real bug to reward-timing/dilution rather than supply-vote desync.

    function vote(address[] calldata _lps, int256[] calldata _deltas) override public {
        if (_lps.length != _deltas.length)
            revert LengthMismatch();

        uint256 length = _lps.length;
        int256 totalUserVote;

        for (uint256 i; i < length; i++) {
            Pool storage pool = poolInfos[_lps[i]];
            if (!pool.isActive)
                revert PoolNotActive();
            int256 delta = _deltas[i];
            totalUserVote += delta;
            if (delta != 0) {
                if (delta > 0) {
                    pool.totalVoteInVlmgp += uint256(delta);
                    userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] += uint256(delta);
                    IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, uint256(delta));
                } else {
                    pool.totalVoteInVlmgp -= uint256(-delta);
                    userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] -= uint256(-delta);
                    IBribeRewardPool(pool.rewarder).withdrawFor(msg.sender, uint256(-delta), false);
                }
            }
        }

        if (msg.sender != delegatedPool) {
            if (totalUserVote > 0) {
                userTotalVotedInVlmgp[msg.sender] += uint256(totalUserVote);
                totalVlMgpInVote += uint256(totalUserVote);
            } else {
                userTotalVotedInVlmgp[msg.sender] -= uint256(-totalUserVote);
                totalVlMgpInVote -= uint256(-totalUserVote);
            }
        }

        if (userTotalVotedInVlmgp[msg.sender] > getUserVotable(msg.sender))
            revert NotEnoughVote();
    }
