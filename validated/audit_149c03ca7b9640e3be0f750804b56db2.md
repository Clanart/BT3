### Title
Unbounded recursive memo parsing in `PuzzleWithRestrictions.from_memo()` allows attacker-crafted coin memo to crash wallet/pool clients via Python stack exhaustion - (File: chia/wallet/puzzles/custody/custody_architecture.py)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively parses an attacker-supplied CLVM `Program` memo tree with no depth bound. Each `MofN` branch encountered in the memo causes `PuzzleWithRestrictions.from_memo` to call itself once per member, and members can nest `MofN` branches arbitrarily deep. Unlike the rest of the Chia codebase (which deliberately made `sha256_treehash`/`_tree_hash` non-recursive specifically "so we don't have to worry about blowing out the python stack" [1](#0-0) ), this custody/plotnft memo parser has no such protection.

### Finding Description
`PuzzleWithRestrictions.from_memo()` reads `further_branching_prog` and, if set, treats `puzzle_hint_prog` as a `MofNHint` and recurses into `PuzzleWithRestrictions.from_memo(memo)` for every entry in `member_memos`: [2](#0-1) 

This is a direct structural analog of `libass`'s `parse_tag`, which recursively descended into attacker-controlled override tags without a depth limit (CVE-2020-24994). Here, the attacker-controlled input is the CLVM memo blob attached to any created coin (e.g. a plotnft/singleton `CREATE_COIN` memo), which any spender fully controls in byte content and nesting depth.

The consuming path for plotnft coin tracking is `PlotNFT.get_next_from_coin_spend()`, which calls `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())` directly on the memo of a coin created on-chain, wrapping only `ValueError` (not `RecursionError`): [3](#0-2) 

Because `MofNHint.from_program()` just unpacks the program as an iterable with no bound on `member_memos` length or nesting [4](#0-3) , an attacker can construct a memo containing thousands of nested `MofN` branches. Any wallet/pool client that later parses that memo (e.g. while syncing a PlotNFT or custody-architecture coin) will recurse in Python once per nesting level until it exceeds the interpreter's recursion limit, raising an unhandled `RecursionError` that is not caught by the `except ValueError` in `get_next_from_coin_spend`.

### Impact Explanation
An attacker sends or creates a coin (e.g. a plotnft-style singleton, or any coin adopting the `PuzzleWithRestrictions`/`MofN` memo convention) whose memo contains a deeply nested `MofN` hint structure. Any client that walks the chain and calls `PuzzleWithRestrictions.from_memo()`/`PlotNFT.get_next_from_coin_spend()` on that coin's memo (wallet sync, pool/plotnft tracking) crashes with an unhandled `RecursionError`, halting the coin-tracking/transaction-processing loop for that client — a spend-triggered processing halt (denial of service) reachable from a single crafted coin/spend, consistent with the "Medium/High/Critical" and "spend-triggered transaction-processing halt" criteria in scope.

### Likelihood Explanation
Likelihood is high for any deployed pool/plotnft or custody-architecture wallet feature that walks `from_memo()`/`get_next_from_coin_spend()` on-chain, since the memo is entirely attacker-controlled (arbitrary bytes chosen by whoever creates the coin) and no validation of nesting depth or memo size occurs before recursive descent begins.

### Recommendation
Add an explicit recursion-depth (or iterative worklist) bound in `PuzzleWithRestrictions.from_memo()`/`MofNHint.from_program()` and raise a caught `ValueError` (not letting `RecursionError` escape) when the bound is exceeded, mirroring the iterative approach already used in `chia/types/blockchain_format/tree_hash.py`. Additionally, wrap/catch `RecursionError` explicitly in `PlotNFT.get_next_from_coin_spend()` alongside `ValueError`.

### Proof of Concept
1. Construct a CLVM memo program of the form `(spec_namespace [nonce, [], 1, [m, member_memos]])` where `member_memos` is a single-element list whose element is itself another such nested memo, repeated to a depth of e.g. 5,000–10,000 levels (well within CLVM program size/cost limits, since this is Python-side parsing, not CLVM execution).
2. Create/broadcast a coin (e.g. via the plotnft-style singleton path) whose `CREATE_COIN` memo is this deeply nested structure.
3. Have a victim wallet or pool client sync and process that coin, triggering `PlotNFT.get_next_from_coin_spend()` → `PuzzleWithRestrictions.from_memo()`.
4. Observe an unhandled `RecursionError` propagating out of the `except ValueError` handler, crashing/halting the client's coin-processing loop.

@dataclass(kw_only=True, frozen=True)
class MofNHint:
    m: int
    member_memos: list[Program]

    def to_program(self) -> Program:
        return Program.to([self.m, self.member_memos])

    @classmethod
    def from_program(cls, prog: Program) -> MofNHint:
        m, member_memos = prog.as_iter()
        return MofNHint(
            m=m.as_int(),
            member_memos=list(member_memos.as_iter()),
