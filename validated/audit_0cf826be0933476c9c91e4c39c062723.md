### Title
Hunk-expansion "up" desynchronizes absolute line indices from `DiffSelection`, silently flipping line-selection state before commit - (File: `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
The bug-class in the report is an *order-of-operations arithmetic error*: a base quantity is updated/consumed before a dependent value is recomputed against it, so a downstream ratio silently drifts from the correct value. The closest verified analog in GitHub Desktop is in `expandTextDiffHunk`, where expanding a hunk **upward** inserts new context lines before the hunk's existing lines but does **not** adjust `hunk.unifiedDiffStart` for that hunk to compensate, causing the absolute indices used by `DiffSelection` (the structure that decides which lines actually get staged/committed) to silently desync from the physical position of pre-existing add/delete lines.

### Finding Description
Line selection in Desktop is tracked as an "absolute index" `hunk.unifiedDiffStart + lineIndex` [1](#0-0) , and `DiffSelection.isSelected(absoluteIndex)` is later used by `formatPatch` to decide, line-by-line, whether an added/deleted line is included in the patch that becomes the commit [2](#0-1) .

When a user expands a hunk upward (`kind === 'up'`) in `expandTextDiffHunk`, the new context lines are prepended right after the hunk header: [3](#0-2) 

This shifts the *position* of every pre-existing line in that hunk's `lines` array forward by `numberOfLinesToAdd`. However, the updated hunk keeps the **same** `unifiedDiffStart` as before the expansion: [4](#0-3) 

Since `absoluteIndex = unifiedDiffStart + lineIndex`, and `lineIndex` for every pre-existing add/delete line increased by `numberOfLinesToAdd` while `unifiedDiffStart` did not, every pre-existing line's absolute index silently shifts by `numberOfLinesToAdd` after an "expand up" operation. By contrast, hunks that come *after* the expanded one are correctly re-indexed by `numberOfNewDiffLines`: [5](#0-4) 

but the currently-expanded hunk's own lines are not. The `DiffSelection` object holding the user's per-line selection state (`divergingLines: Set<number>` keyed by absolute index) is immutable and is not told about this renumbering [6](#0-5) [7](#0-6) . Consequently, after an upward hunk expansion:
- A line the user explicitly *deselected* (e.g., to exclude a change from the commit) is looked up at its old absolute index, which after the shift now belongs to one of the new context lines — so the deselection is effectively "lost," and the real line (now at old-index + N) reads as selected under the default `All` state, re-including it in the patch.
- Conversely, a line explicitly *selected* under a `None` default can silently drop out of the commit.

This is exactly the reported bug class transplanted to Desktop: a derived value (`absoluteIndex`/selection state) is computed from a base quantity (`unifiedDiffStart`) that was mutated in one direction (adding lines) without correspondingly updating the dependent index space, producing silent drift between intended and actual state.

### Impact Explanation
The corrupted value is the file's `DiffSelection` mapping of line index → included/excluded from commit. If exploited (e.g., a malicious collaborator crafts a diff/file such that the victim is naturally led to expand a hunk upward — e.g., a large refactor PR where context expansion is a normal workflow step), a user could unknowingly commit and push content they deliberately excluded, or exclude content they meant to include, with no visual indication that the selection changed. This matches the listed valid-impact category "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Expanding a hunk upward is a standard, frequently used UI action in Desktop's diff viewer (used to show surrounding context in large diffs) and requires no unusual steps — it's a normal part of reviewing changes before a partial commit, so the triggering condition (attacker doesn't need special access, just needs the victim to expand a hunk on a multi-hunk diff) is very plausible. However, I was not able to fully verify, within the available tool budget, whether callers such as `side-by-side-diff.tsx` or `app-store.ts` reset/recompute the file's `DiffSelection` (e.g., via `withSelectableLines`) immediately after an expansion in a way that could mask or fully mitigate this desync — those call sites showed matches for `withSelectableLines`/`expandTextDiffHunk` but I ran out of iterations before reading their bodies. This is the main open question that would need to be resolved (e.g., in a Devin session) to confirm real-world exploitability versus a purely internal index bug that happens to be masked by a subsequent full-selection-state rebuild.

### Recommendation
When expanding a hunk upward, recompute `hunk.unifiedDiffStart` for the updated hunk by subtracting `numberOfLinesToAdd` (mirroring how `followingHunks` are shifted by `+numberOfNewDiffLines`), or alternatively, migrate the `DiffSelection`'s `divergingLines` set indices at the same time the hunks are renumbered so the two data structures never drift apart. Add a regression test asserting that a line's selection state (selected/deselected) is preserved for the *same logical line* across an "expand up" operation, not just that hunk boundaries/line counts are correct.

### Proof of Concept
Conceptual reproduction (would need to be exercised against `expandTextDiffHunk` + `DiffSelection` directly, since I could not execute code):
1. Start with a two-hunk diff where hunk 2 contains an added line `L` at absolute index `idx`.
2. Build `DiffSelection.fromInitialSelection(All).withLineSelection(idx, false)` (user deselects `L`).
3. Call `expandTextDiffHunk(diff, hunk2, 'up', ...)`, which prepends `numberOfLinesToAdd` context lines before hunk2's existing lines while keeping `hunk2.unifiedDiffStart` unchanged [8](#0-7) .
4. Recompute the new absolute index of `L`, which is now `idx + numberOfLinesToAdd`.
5. Call `formatPatch` using the *unchanged* `DiffSelection` from step 2, and observe that `selection.isSelected(idx + numberOfLinesToAdd)` returns `true` (since the divergence was only recorded at `idx`), meaning `L` — a line the user deselected — is included in the generated patch/commit.
