### Title
Untrusted `.git` worktree pointer can hijack an already-tracked repository's path/gitDir via `dispatchCLIAction`'s open-repository worktree-matching - (File: `app/src/ui/dispatcher/dispatcher.ts`)

### Summary
The Lien bug's broken invariant is: an operation validates the *record passed in* (`lien`/`lienId`) but not whether the *underlying shared resource* (the NFT) is still exclusively bound to that record, so a stale-but-still-"valid" record can seize a resource that another party has since legitimately claimed. The closest verifiable Desktop analog is in the "open a local folder as a repository" flow, where Desktop resolves worktree identity purely from whatever `git` reports for an attacker-supplied path, and then re-binds an *already-tracked, trusted* repository record to that path without confirming that path is exclusively owned by that record.

### Finding Description
When a repository path is opened via `Dispatcher.dispatchCLIAction` (used for `--cli-open` command-line invocation and other "open repository at path" entry points), Desktop does the following [1](#0-0) :

1. It calls `getRepositoryType(action.path)`, which fully trusts `git rev-parse --is-bare-repository --show-cdup --git-dir` run *inside the attacker-controlled path* to determine `topLevelWorkingDirectory` and `gitDir` [2](#0-1) . Git itself resolves `.git` files that contain a `gitdir:` pointer to an arbitrary location, including one that resolves (via `commondir`) back into a completely different, victim-owned repository's git database.
2. It then calls `listWorktrees(path)` (again run from the attacker path) and uses `matchExistingRepository` to find (a) a worktree entry equal to the given path, and (b) an **already-tracked** `Repository` record (`repositories.find(r => matchExistingRepository(worktrees, r.path) !== undefined)`) whose `path` appears in that worktree listing [3](#0-2) .
3. If both match, Desktop calls `switchWorktree(sharedCommonDirRepository, worktree)` — but `sharedCommonDirRepository` is the **pre-existing, user-trusted repository record**, not the new folder. This flows into `AppStore._switchWorktree`, which again derives `gitDir`/`mainWorktreePath` purely from `getRepositoryType`/`listWorktrees` run against the attacker-controlled path [4](#0-3) , and finally persists the change with `RepositoriesStore.switchWorktree`, which overwrites the existing repository's `path`, `gitDir`, and `mainWorktreePath` fields in the database [5](#0-4) .

The only existing guard is a check for a *literal* duplicate `path` in the repositories table (`db.repositories.get({ path: worktreePath })`) [6](#0-5) ; it does not verify that the worktree/gitDir information being adopted genuinely belongs to (was created by) the record being modified, mirroring the missing `loanStartTime == 0` check in the Lien bug — the code checks "is there a conflicting record at this exact path" but never checks "does this resource actually still belong solely to the record I'm about to mutate."

### Impact Explanation
If successfully triggered, an attacker-supplied directory (delivered as a "repository to open" — e.g. a downloaded/cloned folder the user adds via "Add Local Repository", drag-and-drop, or the CLI `--cli-open`/`x-github-client://` flow) can cause Desktop to silently repoint the `path` and `gitDir` of a repository the user already trusts and has open in Desktop. Since Desktop's identity for a repository is its `path`, subsequent commits, pushes, branch switches and diffs the user performs "on their known project" could now execute against the attacker's directory/gitDir combination instead, leading to silent corruption of what the user commits or pushes, or leaking working-directory contents/credentials associated with the hijacked record — the same class of harm as the Lien bug's "NFT silently taken from the rightful owner."

### Likelihood Explanation
This requires the specific worktree-matching branch in `dispatchCLIAction` to actually fire, which depends on git's worktree-listing semantics (whether a `.git` file redirect can make `git worktree list` report the victim's already-tracked repository path as an entry while also causing `matchExistingRepository` to match the attacker's own path). I was not able to fully verify from the indexed code alone whether both match conditions (`worktree` and `sharedCommonDirRepository`) can be satisfied without write access to the victim repository's own `.git/worktrees` directory — this needs to be validated in a live environment (spawn `git worktree add`/craft a `.git` pointer file and observe `git worktree list --porcelain` output from the crafted directory). Because of this remaining uncertainty, likelihood should be treated as **unconfirmed/requires PoC verification**, not "confirmed."

### Recommendation
- Before calling `switchWorktree` on an existing tracked `Repository`, independently re-verify (e.g., via `git rev-parse --git-common-dir` executed from the *existing* repository's original path) that the resolved `gitDir`/common dir for the candidate worktree genuinely descends from the same git database the tracked repository was added with, rather than trusting a `path` match derived from data produced by running git inside the untrusted candidate folder.
- Treat `.git` pointer files (worktree redirection) discovered while probing a newly-opened, previously-untracked path as requiring the same "unsafe/untrusted" warning path already used for dubious-ownership repositories (`type.kind === 'unsafe'`) [7](#0-6) , since it can redirect Desktop's git operations to a directory that was not the one the user selected.

### Proof of Concept
This is provided as a hypothesis derived from static code reading; it should be verified with a live Devin session, e.g.:
1. Track a legitimate repository `~/victim-repo` in Desktop (`~/victim-repo/.git` is a normal repo).
2. Craft a folder `~/evil-repo` containing a `.git` file: `gitdir: ~/evil-repo/.git-admin/worktrees/fake`, where `~/evil-repo/.git-admin/worktrees/fake/commondir` points at `~/victim-repo/.git`, plus the accompanying `HEAD`/`gitdir` admin files git expects for a linked worktree.
3. In Desktop, invoke "Add Local Repository" (or CLI `--cli-open ~/evil-repo`) pointing at `~/evil-repo`, and observe whether `dispatchCLIAction`'s worktree-matching branch fires and rewrites the tracked `~/victim-repo` repository record's `path`/`gitDir` to reference `~/evil-repo` [8](#0-7) .
4. Confirm via the repositories database (`repositories-store.ts`) whether the victim's original record now has `path = ~/evil-repo`.

export async function getRepositoryType(path: string): Promise<RepositoryType> {
  if (!(await directoryExists(path))) {
    return { kind: 'missing' }
  }

  try {
    const result = await git(
      ['rev-parse', '--is-bare-repository', '--show-cdup', '--git-dir'],
      path,
      'getRepositoryType',
      { successExitCodes: new Set([0, 128]) }
    )

    if (result.exitCode === 0) {
      // Bare repositories will not include gitdir so we handle that separately
      if (result.stdout.startsWith('true\n')) {
        return { kind: 'bare' }
      }

      // --is-bare-repository and --show-cdup each produce a single line but
      // --git-dir could theoretically contain newlines so we parse the known
      // fields first and treat the remainder as the git dir. We use [\s\S]*
      // instead of .* for the git dir capture group because .* doesn't match
      // newlines whereas [\s\S]* matches any character including newlines.
      const match = result.stdout.match(/^(true|false)\n(.*)\n([\s\S]*)\n$/)

      if (match) {
        const [, isBare, cdup, gitDir] = match

        return isBare === 'true'
          ? { kind: 'bare' }
          : {
              kind: 'regular',
              topLevelWorkingDirectory: resolve(path, cdup),
              gitDir: resolve(path, gitDir),
            }
      }
    }

  public async _switchWorktree(
    repository: Repository,
    worktree: WorktreeEntry
  ): Promise<Repository> {
    const type = await getRepositoryType(worktree.path).catch(e => {
      log.error('Could not determine repository type', e)
      return { kind: 'missing' } as RepositoryType
    })

    if (type.kind !== 'regular' && type.kind !== 'unsafe') {
      throw new Error(
        `The worktree path '${worktree.path}' does not appear to be a valid Git repository.`
      )
    }

    // If the repository path isn't trusted we'll mark the repository as
    // missing. The missing repository view knows how to add a path to the
    // allow list.
    const missing = type.kind === 'unsafe'
    const gitDir = type.kind === 'regular' ? type.gitDir : undefined

    // Record the main worktree while the worktree set is still readable.
    // Removing a worktree can take its git metadata with it, leaving nothing to
    // resolve it from afterwards. Only attempted for a regular repository —
    // git won't run at all in one it considers unsafe — and `switchWorktree`
    // keeps the previously recorded path when this is undefined.
    const mainWorktreePath =
      type.kind === 'regular'
        ? await this.findMainWorktreePath(worktree.path)
        : undefined

    const result = await this.repositoriesStore.switchWorktree(
      repository,
      worktree.path,
      missing,
      gitDir,
      mainWorktreePath
    )
