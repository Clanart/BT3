## Finding

CVE-2017-17722 is a reachable-assertion DoS: parsing an untrusted, attacker-crafted TIFF file caused Exiv2 to hit an `assert()` and abort. The Chia codebase has a structurally identical bug class in the wallet's offer-parsing path: an attacker-crafted, syntactically valid `Offer` puzzle reveal deterministically drives a bare Python `assert` to fail with an uncaught `AssertionError`, when a wallet user merely inspects or takes the offer.

### Title
Uncaught `AssertionError` crash when parsing a crafted Offer puzzle reveal matching the royalty-transfer-program driver - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer._get_offered_coins()` matches each coin-spend's puzzle reveal against the registered outer-puzzle driver table and then asserts that the resolved inner puzzle/solution are non-`None`. The `TransferProgramPuzzle` driver (`chia/wallet/nft_wallet/transfer_program_puzzle.py`) unconditionally returns `None` for both `get_inner_puzzle()` and `get_inner_solution()`. An attacker who crafts an offer whose spend bundle contains a coin spend curried against `NFT_TRANSFER_PROGRAM_DEFAULT` will make `match_puzzle()` classify it as `AssetType.ROYALTY_TRANSFER_PROGRAM`, which then trips the assertion in `offer.py`, raising an unhandled `AssertionError`.

### Finding Description
`Offer._get_offered_coins()`: [1](#0-0) 

matches the puzzle reveal with `match_puzzle()` and then calls `get_inner_puzzle`/`get_inner_solution`, asserting neither is `None`. But `TransferProgramPuzzle`, registered under `AssetType.ROYALTY_TRANSFER_PROGRAM`, always returns `None`: [2](#0-1) 

`match_transfer_program_puzzle()` only checks that the puzzle's uncurried mod equals `NFT_TRANSFER_PROGRAM_DEFAULT`: [3](#0-2) 

and it's wired into the driver lookup table used by `match_puzzle()`: [4](#0-3) 

`Offer.__post_init__` builds `_additions`/`_hints` using a broad exception-swallowing loop (so a malformed spend does not prevent `Offer.from_bytes()`/`from_bech32()` from succeeding): [5](#0-4) 

meaning the malicious offer parses successfully and only later, when `get_offered_coins()` is invoked, does the assertion fire. `get_offered_coins()` is reached from many common wallet-user code paths, none of which catch `AssertionError`:
- `offer.summary()` → `get_offered_amounts()` → `get_offered_coins()`, used by the CLI when merely inspecting an offer before deciding whether to accept it (`chia wallet take_offer --examine-only` or normal flow): [6](#0-5) 
- `TradeManager.calculate_tx_records_for_offer()`, called unguarded from `TradeManager.respond_to_offer()` (the RPC `take_offer` implementation), and `save_trade()`: [7](#0-6) [8](#0-7) [9](#0-8) 

None of these call sites wrap the resulting `AssertionError`.

### Impact Explanation
An unprivileged offer counterparty can send/publish a crafted offer file that, when merely examined, summarized, or accepted by a victim wallet user (CLI or RPC `check_offer_validity`/`take_offer`/`respond_to_offer` flow), triggers an unhandled `AssertionError`. This aborts the in-flight wallet RPC/task processing that offer — a spend-triggered transaction-processing halt directly analogous to the reachable-assertion DoS in the CVE. This falls squarely within the allowed "offers and trades" reachable surface for an offer counterparty / wallet user.

### Likelihood Explanation
High likelihood of triggering: the attacker only needs to construct an `Offer` whose spend bundle includes one coin spend whose puzzle reveal is `NFT_TRANSFER_PROGRAM_DEFAULT` curried with arbitrary values — no valid coin ownership, signature, or on-chain state is required, since the crash occurs purely from local puzzle-reveal inspection before any chain validation or signature check takes place.

### Recommendation
In `chia/wallet/trading/offer.py::_get_offered_coins()`, replace the bare `assert inner_puzzle is not None and inner_solution is not None` with an explicit check that raises a caught/handled `ValueError` (consistent with the existing `"Could not properly guess offered coins from parent spend"` pattern), and/or make `TransferProgramPuzzle.get_inner_puzzle`/`get_inner_solution` raise `ValueError` instead of silently returning `None`, so malformed/unexpected offer content produces a clean rejection rather than an uncaught `AssertionError`.

### Proof of Concept
1. Build a `CoinSpend` whose `puzzle_reveal` is `puzzle_for_transfer_program(launcher_id, royalty_puzzle_hash, percentage)` from `chia/wallet/nft_wallet/transfer_program_puzzle.py` (any arbitrary `launcher_id`/`royalty_puzzle_hash`/`percentage`), with any coin/solution.
2. Wrap it in a `WalletSpendBundle` and construct an `Offer` (`Offer(notarized_payments, bundle, driver_dict)`), then serialize with `bytes(offer)`/`to_bech32()`.
3. Have a victim call `Offer.from_bech32(offer_str)` followed by `offer.summary()` (or feed it to `take_offer`/`respond_to_offer`).
4. Observe `_get_offered_coins()` match the puzzle as `AssetType.ROYALTY_TRANSFER_PROGRAM`, call `TransferProgramPuzzle.get_inner_puzzle`/`get_inner_solution` (both return `None`), and hit the `assert inner_puzzle is not None and inner_solution is not None` line, raising an unhandled `AssertionError` that aborts the calling wallet operation.
