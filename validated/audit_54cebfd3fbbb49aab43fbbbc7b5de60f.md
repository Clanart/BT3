### Title
Unverified proof-of-possession allows an attacker to force release of ECDH blame keys, decrypting honest participants' DKG secret shares - (File: crypto/dkg/pedpop/src/lib.rs, crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP DKG encrypts each secret share under a per-message ephemeral key `msg.key`, deriving the ChaCha20 key via ECDH between the recipient's static encryption key and `msg.key`. A Schnorr proof-of-possession (`msg.pop`) on `msg.key` exists specifically to stop an attacker from copying someone else's `key`/`ciphertext` into their own message: if a victim then issued a blame proof, it would publish the ECDH shared key `bX`, revealing the copied message's plaintext (`encryption.rs:84-90`). However, `calculate_share` releases the blame proof (which contains that ECDH key) on the share-deserialization error path **before** the queued PoP batch verification ever runs, re-opening exactly the attack the PoP was added to prevent — an analog of incorrect access control leading to disclosure of sensitive data.

### Finding Description
`Encryption::decrypt` queues `msg.pop` into the `BatchVerifier` but immediately computes `key = ecdh(self.enc_key, msg.key)`, decrypts the ciphertext, and returns `(msg, EncryptionKeyProof { key, dleq })` (`encryption.rs:479-500`). The proof is only *queued*, not verified. In `KeyMachine::calculate_share` the loop calls `decrypt`, then checks `C::F::from_repr(share_bytes.0)`; on a non-canonical scalar it returns `Err(PedPoPError::InvalidShare { participant: l, blame: Some(blame) })` via `?` at `lib.rs:480-482`. This early return means `batch.verify_with_vartime_blame()` at `lib.rs:493` is never reached — the PoP for that message is never checked anywhere before the `EncryptionKeyProof` (containing `key = enc_key_recipient * msg.key_scalar`, i.e. the shared decryption key, plus a DLEq attesting it is correct) is handed to the caller for publication.

Contrast with the code's own intent: when the batch verifier *does* run and fails on `BatchId::Decryption(l)` (the PoP slot), it deliberately returns `blame: None` (`lib.rs:494-498`) so no ECDH key is revealed for a message with a bad PoP. The serialization-error path bypasses that guard. In the processor flow, this blame is submitted for verification via `CoordinatorMessage::VerifyBlame`, where `AdditionalBlameMachine::new(...).blame(...)` re-checks the PoP in `decrypt_with_proof` (`encryption.rs:374-379`) and will correctly blame the malicious sender — but the `EncryptionKeyProof` carrying the ECDH shared key has already been broadcast, which is all the attacker needed.

### Impact Explanation
An attacker Eve, a DKG participant, observes Alice's honest `EncryptedMessage` to victim Bob: `(key = X, pop, ciphertext)`. Eve copies `X` and arbitrary/copied ciphertext into her own share slot to Bob. She cannot forge a PoP for `X` (it binds `from = Eve` and requires the discrete log of `X`), but that no longer matters:

- Bob's `decrypt` computes `key = bX` (Bob's ECDH share with Alice's ephemeral key), decrypts to garbage, and — when the garbage isn't a canonical scalar (≈15/16 probability for Ristretto's ~2²⁵² group order) — returns an `EncryptionKeyProof` revealing `bX` with a DLEq proving correctness.
- Bob's `calculate_share` errors out with `blame: Some(proof)` before the PoP batch check; the proof is published as a blame statement.
- Anyone can now apply `cipher(context, bX)` to Alice's original ciphertext (`encryption.rs:392`) and recover Alice's secret share `f_Alice(Bob)`.

By doing this to every recipient `j` (each has a distinct `enc_key_j` and Alice used distinct per-message keys `X_j`), Eve triggers publication of `b_j X_j` for all `j`, decrypting Alice's shares to *all* participants. That yields `f_Alice(j)` for every `j ≠ Alice` — `n-1 ≥ t` points on Alice's degree `t-1` polynomial — fully recovering Alice's secret polynomial and her DKG secret contribution. This is recovery of key-share material the protocol was explicitly designed to keep confidential; the in-code comment calls this side effect "massive" and states the PoP exists to prevent it.

### Likelihood Explanation
Reachable by any unprivileged DKG participant with public inputs: Eve only needs to send malformed `EncryptedMessage` bytes to a victim's `calculate_share` — no collusion, no malicious node assumptions, no key compromise. The attack aborts that DKG session (blame correctly attributes Eve), but the share material is leaked before the abort, so a single attempt succeeds with high probability (~probability the garbage plaintext is non-canonical, which the attacker can bias by trying multiple times across sessions). Severity: High — confidential DKG share disclosure reachable via unauthenticated-byte parsing.

### Recommendation
Do not release the `EncryptionKeyProof` until the message's PoP has been verified. Concretely: in `calculate_share`, run `batch.verify_with_vartime_blame()` before emitting any blame — or return the blame proof lazily/optionally only after the `BatchId::Decryption(l)` checks pass. A minimal fix is to verify each message's PoP (or at least the PoP of any message whose blame will be emitted) prior to returning `Err` from the `from_repr` path; e.g. partition the batch so PoP verification for share `l` completes before `blame` for `l` is exposed. Alternatively, make `decrypt` take ownership such that the blame proof is only materialized after successful batch verification of `BatchId::Decryption`.

### Proof of Concept
1. Run PedPoP with `t=2, n=3`, participants Alice=1, Bob=2, Eve=3 over `Ristretto`.
2. Alice runs `generate_secret_shares`, producing `EncryptedMessage { key: X, pop, msg }` destined for Bob (ciphertext = share bytes XOR keystream(bX)).
3. Eve constructs her share-to-Bob message as `EncryptedMessage { key: X, pop: <arbitrary/self-signed SchnorrSignature>, msg: <copied or random ciphertext> }` — the PoP cannot be valid since Eve doesn't know `x`.
4. Bob calls `calculate_share` with shares from Alice and Eve. `Encryption::decrypt` queues Eve's PoP into the batch, then computes `key = ecdh(b, X) = bX`, decrypts Eve's ciphertext to garbage, and returns `EncryptionKeyProof { key: bX, dleq }`.
5. `C::F::from_repr(garbage)` fails → `calculate_share` returns `Err(InvalidShare { participant: Eve, blame: Some(proof) })`; `batch.verify_with_vartime_blame()` (which would have caught the forged PoP and suppressed the proof via `blame: None`) is never executed.
6. Bob publishes `proof`. Eve (or anyone) verifies the DLEq against `enc_keys[Bob]` and `X` (`encryption.rs:383-390`), then computes `cipher(context, bX)` and XORs it against Alice's original ciphertext, recovering `f_Alice(2)`.
7. Repeat toward participant 1's machine (and any others) to collect `f_Alice(j)` for all `j`; interpolate to recover Alice's constant coefficient — her DKG secret.
