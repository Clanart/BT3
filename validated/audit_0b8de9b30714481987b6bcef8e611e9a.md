### Title
`SignableTransaction::new` omits the OP_RETURN data output from the fee/weight calculation, undercharging the transaction fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

Analogous to the `Reserve.sol` bug — where a check used a scaled/proxy quantity (`scaledTotalSupply()`) instead of the true quantity (`totalSupply()`) — `SignableTransaction::new` validates the transaction fee against a *partial* transaction size rather than the actual transaction size. The witness/weight and vbyte computation in `calculate_weight_vbytes` is performed over only the inputs, payments, and optional change output; the OP_RETURN output carrying up to 80 bytes of caller-supplied `data` is appended to `tx_outs` *after* the fee and minimum-relay-fee checks are computed, so it is never priced.

### Finding Description

`SignableTransaction::new` accepts an optional `data` payload which is pushed as an additional `TxOut` with an OP_RETURN `script_pubkey` (up to 80 bytes) [1](#0-0) . However, the weight/vbyte calculation used for `needed_fee`, the minimum relay fee check, and the `NotEnoughFunds` check is invoked as `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, which reconstructs a `Transaction` containing only inputs and `payments` — the data output is absent [2](#0-1) .

Concretely:

1. `vbytes` is computed without the OP_RETURN output, so `needed_fee = fee_per_vbyte * vbytes` under-prices the real transaction [3](#0-2) .
2. The change-output value is `input_sat - payment_sat - fee_with_change`, where `fee_with_change` is still computed over a transaction with no data output [4](#0-3) . The change output therefore absorbs sats that should have gone to the fee.
3. The minimum-relay-fee guard compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the understated `vbytes` [5](#0-4) .
4. `needed_fee()` is exposed publicly and `fee()` reveals the actual fee (`inputs - outputs`), which will differ from what the requested `fee_per_vbyte` implies for the *real* transaction size [6](#0-5) .

The check is therefore validating a scaled-down version of the quantity it claims to constrain — exactly the "wrong denominator/total" bug class: the fee check passes against a smaller transaction than the one actually signed and broadcast.

### Impact Explanation

Any caller that supplies `data` produces a transaction whose effective fee rate is lower than the requested `fee_per_vbyte`. With an 80-byte OP_RETURN output (~90+ weight units once output overhead is included, ~23+ vbytes), the effective fee rate is degraded proportionally to the data size relative to the transaction size. For transactions constructed near the minimum relay fee boundary (the code explicitly supports small consolidation/change-only transactions), the real fee rate can fall below `DEFAULT_MIN_RELAY_TX_FEE`, producing a signed transaction that standard Bitcoin nodes will not relay or mine — funds committed to the multisig's outputs become unbroadcastable/unconfirmable despite the code asserting `TooLowFee` protection. In Serai's usage the processor never passes `data`, so this is a latent wallet-library defect reachable by any consumer of `bitcoin-serai` supplying public `data` bytes — the bytes are untrusted caller input to `SignableTransaction::new`.

### Likelihood Explanation

The `data` parameter is a public input; triggering requires only passing a non-empty payload, which is the documented purpose of the argument. The miscalculation is deterministic — the data output is unconditionally excluded from both `calculate_weight_vbytes` call sites [7](#0-6) . Whether the resulting transaction actually fails relay depends on how close `fee_per_vbyte` is to the minimum, but the fee is *always* lower than requested, and `needed_fee` always misreports the true requirement.

### Recommendation

Include the OP_RETURN output in the size estimate: pass the fully-formed output set (payments + data output) into `calculate_weight_vbytes`, or compute the data output's serialized size and add it to `weight`/`vbytes` before deriving `needed_fee`, the minimum-relay check, the `NotEnoughFunds` check, and the change-value subtraction. Optionally assert post-construction that `self.fee() >= fee_per_vbyte * actual_vbytes` and `>= DEFAULT_MIN_RELAY_TX_FEE * actual_vbytes / 1000` over the real transaction.

### Proof of Concept

In `networks/bitcoin/src/wallet/send.rs`, construct:

```rust
let data = vec![0u8; 80];
let tx = SignableTransaction::new(inputs, &payments, Some(change), Some(data), fee_per_vbyte)?;
```

- `tx.tx.output` contains the OP_RETURN output, but `needed_fee` was computed from `calculate_weight_vbytes(inputs, payments, change)` which omits it.
- `tx.fee()` returns `sum(inputs) - sum(outputs)` which equals `needed_fee` — an amount corresponding to `fee_per_vbyte * (vbytes_without_data)`, i.e. strictly less than `fee_per_vbyte * vbytes_of(tx.tx)`.
- With `fee_per_vbyte = 1` and a small transaction (~150 vbytes estimated, ~175 actual), `needed_fee` passes the `TooLowFee` guard (`>= 1000 * 150 / 1000 = 150 sats`) while the real transaction pays ~150 sat for ~175 vbytes — below the 1 sat/vbyte relay floor.
