### Title
Credential helper trusts unauthenticated `WWW-Authenticate` header from a git remote to classify hosts as GitHub, bypassing independent verification - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`getEndpointKind()` in the credential-helper trampoline decides whether a remote host should be treated as `github.com`/`ghe.com`/`enterprise` (first-party) or `generic` (external Git host) before deciding which credential path to use. For hosts it can't classify by URL alone, it inspects the `wwwauth[...]` fields that Git forwards from the server's `WWW-Authenticate` response header and, if the value contains `realm="GitHub"`, unconditionally classifies the host as `'enterprise'` — skipping the only independent verification step (`isGitHubHost(endpoint)`, an actual network probe) that would otherwise be used. [1](#0-0) 

### Finding Description
This mirrors the oracle-price bug class: a value that is attacker-influenced (here, an HTTP response header returned by whatever server Git is talking to — fully controlled by a malicious or compromised remote/proxy) is consumed as ground truth for a security-relevant decision without any staleness/authenticity check, even though a stronger validation primitive (`isGitHubHost`) exists and is normally used as the fallback.

The credential helper's `getCredential()` flow is:
1. Try to match an existing stored GitHub account by origin (`getGitHubCredential`) — bypassed if attacker's host doesn't match any stored account.
2. Call `getEndpointKind(cred, store)` to classify the host.
3. If classification is not `'generic'` and no account exists for the computed API endpoint, prompt `ui.promptForGitHubSignIn(endpoint)`, which drives the user into the GitHub/GitHub-Enterprise sign-in (OAuth) flow, pre-populated with the attacker's endpoint. [2](#0-1) 

Inside `getEndpointKind`, the classification order is:
```
isGist / isDotCom / isGHE  → fast static checks
wwwauth[...] header contains realm="GitHub" → 'enterprise'   (attacker-controlled)
wwwauth[...] header matches other known realms → 'generic'
existing account match by origin → derived from account
protocol !== https → 'generic'
otherwise → isGitHubHost(endpoint) network probe
``` [1](#0-0) 

The `wwwauth[]` value originates from Git's HTTP transport, which simply forwards the server's `WWW-Authenticate` header content into the credential-helper protocol — it is not authenticated or verified in any way before being trusted here. Any HTTP(S) git remote (a public clone URL, an npm-style dependency remote, a corporate proxy, or a compromised/malicious mirror) can return `WWW-Authenticate: Basic realm="GitHub"` for any hostname it likes, forcing Desktop to treat that arbitrary host as GitHub Enterprise and to route the user into the "sign in with GitHub" OAuth flow (`promptForGitHubSignIn` → `beginEnterpriseSignIn` + `setSignInEndpoint(origin)`), all seeded with the attacker's `origin`. [3](#0-2) 

This is exactly the invariant break described in the seed report: a critical trust decision ("is this endpoint really GitHub?") is made from unvalidated, externally supplied data instead of the app's own verification primitive (`isGitHubHost`), and the header-based shortcut is checked *before* the trustworthy network probe, so the stronger check never runs when the header is present.

### Impact Explanation
If the credential helper misclassifies an arbitrary attacker-controlled remote as GitHub Enterprise:
- It routes the user through Desktop's OAuth/Enterprise sign-in UI pre-seeded with the attacker's `origin`, priming the user to authenticate "to GitHub" against a host they did not knowingly choose.
- It suppresses the more accurate, existing `isGitHubHost` network check for that host, which is the intended safety net for exactly this ambiguity.
- More significantly, it changes which credential-handling branch is used at all: hosts that would otherwise fall into the vetted `generic` (external credential manager / stored generic password) path can be pushed into the GitHub-specific branch instead, altering what credentials Desktop is willing to hand back for that endpoint.

Impact is capped at Medium because the resulting sign-in still requires explicit user interaction (clicking through the sign-in dialog/OAuth), and existing accounts already matched by origin take precedence, but the flow silently skips Desktop's own network-based verification, which is the exact "bypass the staleness/validation check" pattern the report warns about.

### Likelihood Explanation
Likelihood is Medium: any attacker who can operate or influence a git remote or MITM an HTTP(S) git transport (a scenario already covered under "the attacker controls ... a git remote/proxy response") can set this header on a normal `git fetch`/`clone`/`push`, triggering the credential helper's `get` command with no additional user action beyond a routine Git operation Desktop already performs. No local access, malware, or leaked credentials are required.

### Recommendation
Do not trust the `wwwauth[]` realm string as authoritative. Either:
- Drop the `wwwauth` heuristic entirely and always fall back to the network-verified `isGitHubHost(endpoint)` check, or
- Use the header only as a hint to *prioritize* the `isGitHubHost` probe, never as a substitute for it, and require the same TLS/hostname validation used elsewhere (e.g., `isDotCom`/`isGHE`) before treating a host as first-party GitHub.

### Proof of Concept
1. Stand up an HTTPS git server (or a MITM proxy in front of any git remote) that, on an unauthenticated request, responds with `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, add/clone/fetch from that remote URL (e.g. `https://evil.example.com/foo/bar.git`).
3. Git forwards the `WWW-Authenticate` header to Desktop's credential helper via the `wwwauth[...]` field on the `get` command's stdin.
4. `getEndpointKind` matches `realm="GitHub"` and returns `'enterprise'` for `evil.example.com` without ever calling `isGitHubHost`. [4](#0-3) 
5. Since no account exists for that endpoint, `getCredential` calls `ui.promptForGitHubSignIn('https://evil.example.com')`, which begins an Enterprise sign-in flow pre-seeded with the attacker's origin. [5](#0-4) 

Note: I was not able to trace this further into `sign-in-store.ts`/`enterprise-validate-url.ts` to confirm whether `setSignInEndpoint` performs additional URL/protocol validation that further limits real-world exploitability (e.g., re-validating the host before completing OAuth); that would need deeper review of `app/src/ui/lib/enterprise-validate-url.ts` and `sign-in-store.ts:setEndpoint` before this can be escalated beyond Medium.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }
