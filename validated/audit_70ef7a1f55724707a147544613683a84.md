### Title
Denial of Service via Underpriced O(n²) Account Lookup in CPI Account Translation - (File: program-runtime/src/cpi.rs)

### Summary
`translate_accounts_common` in [1](#0-0)  performs a linear scan (`account_info_keys.iter().position(...)`) over the full set of caller-supplied `account_infos` for **every** instruction account referenced by a CPI call. This produces O(n²) work in the number of CPI accounts, while the compute-unit charge levied for this step is only proportional to the byte-size of the `account_infos` slice (O(n)), not to the actual quadratic work performed. This mirrors the analog reported for the Move-based order book: cheap, linearly-charged operations that are actually repeated n times, each doing O(n) work, allowing an attacker to force disproportionate CPU consumption relative to the compute units charged.

### Finding Description
`translate_account_infos` charges compute based on the serialized byte size of the account_infos array: [2](#0-1) 

It then invokes a callback (`translate_accounts_common`) that iterates over every instruction account of the *next* CPI instruction and, for every non-executable account, performs a **linear search** through `account_info_keys` to find the matching caller-supplied `AccountInfo`: [3](#0-2) 

Because this `position()` lookup is performed once per instruction account (up to the instruction's account limit) against the full `account_info_keys` slice, the total work scales as O(n²) where n is the number of accounts passed to the CPI. The only compute-unit charge tied to this pass is the flat `account_infos_bytes / cpi_bytes_per_unit` charge computed once in `translate_account_infos`, which is O(n), not O(n²). There is no additional charge that scales with the number of `position()` scans performed inside `translate_accounts_common`.

This is architecturally analogous to the Move `vec_set::remove` bug: a per-item operation that is inherently O(n) is executed n times without being priced for the resulting O(n²) cost, letting a caller pay for O(n) "bytes" while making the validator actually do O(n²) key comparisons.

### Impact Explanation
A malicious BPF program can invoke CPI with the maximum permitted number of duplicated/repeated instruction accounts and a maximally-sized `account_infos` array (bounded by the transaction/instruction account limits enforced via `MAX_ACCOUNTS_PER_TRANSACTION`/`MAX_ACCOUNTS_PER_INSTRUCTION`, referenced in [4](#0-3)  and used throughout `cpi.rs`). Each CPI invocation would then force the validator to perform up to n² pubkey comparisons while being charged compute proportional to n. Repeating such CPIs within a single transaction (bounded by `max_instruction_trace_length`/CU budget) could let an attacker consume disproportionate wall-clock/CPU time relative to the compute units deducted, potentially slowing block processing for other transactions in the same slot — a compute-underpricing/DoS class issue matching the report's core class ("materially underpriced compute").

### Likelihood Explanation
Reachable by any unprivileged program author via a normal CPI (`sol_invoke_signed` syscall path), requiring no special privileges — only a program that issues a CPI instruction referencing many accounts with a correspondingly sized `account_infos` array. The number of accounts is capped by existing instruction/transaction account-count limits, which bounds but does not eliminate the quadratic blow-up (n² comparisons for n up to the per-instruction account cap, on every CPI call, repeatable across many CPIs in one transaction).

### Recommendation
Replace the linear `position()` scan of `account_info_keys` with an O(1) or O(log n) lookup (e.g., build a hash map or sorted index from `account_info_keys` to their position once per `translate_account_infos` call, and reuse it in `translate_accounts_common`), or explicitly price the number of scan operations (e.g., charge compute per comparison rather than only per byte) so the CU cost matches the actual O(n²) work.

### Proof of Concept
Conceptual (not executed, since Ask mode has no code execution): a BPF program that calls `invoke_signed` with an instruction referencing the maximum number of allowed accounts, all distinct pubkeys, and supplies an `account_infos` slice of the same maximal size. Each of the n instruction accounts triggers a full O(n) linear scan of `account_info_keys` inside `translate_accounts_common`, yielding O(n²) key comparisons per CPI call, while the CU cost charged in `translate_account_infos` remains linear in n (bytes of `account_infos`). Issuing several such CPIs in a single transaction (up to the instruction trace / call depth limits) multiplies this effect.

**Note on completeness:** I was unable to confirm within the available iterations the exact numeric values of `MAX_ACCOUNTS_PER_INSTRUCTION`/`MAX_ACCOUNTS_PER_TRANSACTION` and the exact cap enforced by `check_account_infos` in this snapshot of the repo (the index did not surface their definitions before the iteration limit was reached), so the precise magnitude of the achievable n² blow-up (and whether it is large enough to be practically significant versus already bounded to a negligible size by those constants) could not be fully verified. A Devin session with full repository access could confirm these constants and, if needed, produce a runnable benchmark to measure the actual CPU-time-to-CU ratio.
