This is the key finding: `RecoverTxPubkeys` / `TxSignatures.RecoverPubkey` iterates over **all** signatures in the raw RLP-decoded transaction and performs an expensive ECDSA `Ecrecover` for each one, **before** any bound on the number of signatures relative to `MaxNumKeysForMultiSig` (10) is enforced.

The `MaxNumKeysForMultiSig` cap and the `len(recoveredKeys) > len(a.Keys)` check in `AccountKeyWeightedMultiSig.Validate()` [1](#0-0)  only apply *after* `SenderPubkey`/`ValidateSender` has already recovered every public key from every attached signature [2](#0-1) . The recovery step itself, `TxSignatures.RecoverPubkey`, loops over the full, attacker-supplied `TxSignatures` slice with no upper bound check before calling `Ecrecover`: [3](#0-2) .

I looked for a pre-recovery length/size guard (comparable to `NewTxSignaturesWithValues`'s `MaxNumKeysForMultiSig` check, which is only applied on the *signing* path, not the *decoding/validation* path) and found none in `tx_pool.go`'s `validateTx` before `tx.ValidateSender` is invoked [4](#0-3) , nor in RLP decoding of `TxSignatures`. The only pre-signature-recovery gate is `MaxTxDataSize` on overall tx byte size [5](#0-4) , which bounds the count only indirectly (each signature is ~65 bytes RLP-encoded, so `MaxTxDataSize` limits sig count to a large but not small number — I could not find the exact value of `MaxTxDataSize` in the indexed content to compute the precise worst-case count).

### Title
Unbounded ECDSA signature recovery in `TxSignatures.RecoverPubkey` allows CPU-consumption DoS via oversized multi-signature transactions - (File: blockchain/types/tx_signatures.go)

### Summary
A single submitted Kaia transaction using the multi-signature (`TxSignatures`) format can carry an attacker-controlled number of `(V,R,S)` signature tuples. `ValidateSender` calls `SenderPubkey` → `RecoverTxPubkeys` → `TxSignatures.RecoverPubkey`, which performs one `crypto.Ecrecover` (secp256k1 point recovery, a CPU-expensive operation) per signature entry, with no check that the count is bounded by the account's actual key count (`MaxNumKeysForMultiSig` = 10) until *after* all recoveries have already completed. This mirrors CVE-2014-2828 (Keystone V3 "authentication chaining"): the DoS-relevant limit check exists but is applied too late, after the expensive per-item cryptographic work.

### Finding Description
- `NewAccountKeyWeightedMultiSig` accounts are capped at 10 keys via `MaxNumKeysForMultiSig` [6](#0-5) , and this cap is enforced when *creating* signatures via `NewTxSignaturesWithValues` [7](#0-6) .
- However, that helper is only used by the signer's own SDK/test helper path. A transaction received over the wire (RPC `eth_sendRawTransaction` / p2p tx broadcast) is RLP-decoded directly into a `TxSignatures` slice without going through `NewTxSignaturesWithValues`, so an attacker can craft a transaction with an arbitrarily large signature list (bounded only by `MaxTxDataSize`).
- When this transaction reaches `TxPool.validateTx`, the very first cryptographic step is `tx.ValidateSender(...)` [4](#0-3) , which calls `SenderPubkey(signer, tx)` and eventually `TxSignatures.RecoverPubkey`, iterating over every signature and calling `s.RecoverPubkey(...)` (ECDSA recovery) for each one [3](#0-2) .
- Only after all N recoveries complete does `AccountKeyWeightedMultiSig.Validate` check `len(recoveredKeys) > len(a.Keys)` and reject the tx [8](#0-7) .
- Because rejection happens post-hoc, a public RPC caller / unprivileged transaction submitter can force full-cost signature recovery for every entry in the list, with cost scaling linearly (or more, given map operations in `Validate`) with attacker-chosen N, for a single submitted transaction that is ultimately invalid and non-executable.

### Impact Explanation
Each `Ecrecover` call is a nontrivial elliptic-curve computation. An attacker who can reach `TxPool.AddRemote`/`AddLocal` (via public RPC `eth_sendRawTransaction`, `sendTransaction`, or by simply broadcasting a signed raw tx) can submit a transaction with a very large signature array attached to an account, forcing every node's mempool-admission logic to perform O(N) expensive signature recoveries before the transaction is ultimately rejected. Because this happens during `validateTx` in the tx pool (mempool admission, which runs on every full/endpoint node that ingests the transaction), sending a modest number of such crafted transactions can meaningfully raise CPU load network-wide, matching the "CPU consumption" DoS class of CVE-2014-2828 (excess auth-method entries processed before rejection).

### Likelihood Explanation
The prerequisites are minimal: only a validly-formed but adversarial RLP transaction with an inflated `TxSignatures` array is needed; no special privileges, staking, or governance access is required — any transaction sender or public RPC caller can trigger it. The attack is reusable across nodes since the same crafted transaction can be broadcast/gossiped or submitted to multiple public RPC endpoints.

### Recommendation
Add an early, cheap bound check before performing any signature recovery: reject transactions whose `len(tx.RawSignatureValues())` (and fee-payer signature count) exceeds `accountkey.MaxNumKeysForMultiSig` (or another suitable ceiling) in `TxPool.validateTx` / `Transaction.ValidateSender` prior to calling `SenderPubkey`/`RecoverTxPubkeys`. This mirrors the actual Keystone fix pattern: validate/limit the count of "authentication" entries before doing the expensive per-entry cryptographic work, not after.

### Proof of Concept
1. Craft a `TxTypeValueTransfer` (or any Kaia-typed tx) transaction targeting any `from` account.
2. Instead of signing normally via `SignWithKeys`/`NewTxSignaturesWithValues` (which enforces the 10-key cap), directly construct/RLP-encode a `TxSignatures` slice with, e.g., 100,000 arbitrary/garbage `(V,R,S)` triples (they need not be valid signatures for the recovery routine to attempt `Ecrecover` on each — invalid ones will error out only *after* the recovery attempt for that entry).
3. Submit via `eth_sendRawTransaction` / `AddRemote` to a Kaia endpoint node.
4. Observe that `TxPool.validateTx` → `ValidateSender` → `SenderPubkey` → `RecoverTxPubkeys` iterates the full signature list performing `Ecrecover` for each entry [3](#0-2)  before the account-key length check in `AccountKeyWeightedMultiSig.Validate` [8](#0-7)  rejects the transaction — causing disproportionate CPU consumption relative to the (ultimately rejected, fee-less since it never enters a block) transaction.

**Note on confidence**: I was unable to locate the exact numeric value of `MaxTxDataSize` in the indexed portion of the codebase to compute the precise practical maximum signature count achievable within a single RLP-encoded transaction; this bounds the real-world severity of the amplification factor and should be verified directly in a full checkout (`blockchain/tx_pool.go` constants) before finalizing severity.
