## Title
Recursive clone deliberately disables Git's post-clone hook-execution protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), enabling code execution from a malicious repository/submodule during "Clone in Desktop" - (File: `app/src/lib/git/clone.ts`)

## Summary
Modern Git ships a built-in defense-in-depth mechanism (surfaced through the `GIT_CLONE_PROTECTION_ACTIVE` environment variable) that is meant to prevent a repository fetched during a recursive clone (e.g., a submodule) from being able to trigger hook execution or other unsafe local-clone behaviors that were the root cause of CVE-2024-32004-class vulnerabilities. GitHub Desktop's `clone()` function explicitly sets this variable to `'false'` on every `git clone --recursive` invocation it performs, unconditionally overriding Git's own safeguard for every repository a user clones from Desktop's UI. [1](#0-0) 

## Finding Description
`clone()` builds the environment for the `git clone --recursive` subprocess by merging `envForRemoteOperation(url)` with a hard-coded override, `GIT_CLONE_PROTECTION_ACTIVE: 'false'`: [2](#0-1) 

This is invoked for every "Clone in Desktop" / "Clone repository" action, including cloning of URLs typed by the user, URLs resolved from GitHub API responses (`fetchRepositoryCloneInfo`), and URLs delivered via `x-github-desktop` deep links (`openOrCloneRepository`) — all of which are attacker-influenceable inputs (a malicious/compromised repo owner, a crafted GitHub API response, or a crafted deep link pointing at an arbitrary URL). [3](#0-2) [4](#0-3) 

Because Desktop always clones with `--recursive`, this override applies during submodule fetch, which is precisely the scenario Git's protection targets: an attacker-controlled repository can define submodules pointing at other attacker-controlled repositories, and the top-level clone process automatically fetches and checks them out. Git added `GIT_CLONE_PROTECTION_ACTIVE` (and related guards) as the mechanism to stop the class of exploits where cloning with submodules leads to unwanted hook execution or filesystem writes from the nested/submodule clone step. By forcing this flag off, Desktop removes that guard for all clones it performs, regardless of whether the repository is untrusted.

There is no local mitigation in `clone.ts` that substitutes for the disabled protection — `isClonePathSensitive()` only guards against the *destination path* being a sensitive system directory, it does nothing about hook execution or unsafe submodule handling once cloning is underway. [5](#0-4) 

## Impact Explanation
This matches the "attacker controls a cloned/fetched repository ... and the result is code execution" impact category. If Git's own hook/checkout protections for recursive/submodule clones are the thing standing between an attacker-crafted repository and arbitrary hook execution on the user's machine, disabling `GIT_CLONE_PROTECTION_ACTIVE` for every Desktop-initiated clone reintroduces that exposure specifically for GitHub Desktop users, even on a Git version that would otherwise be protected by default. Because the override is unconditional and not scoped to any special trusted case, it also nullifies whatever this variable is meant to protect for GitHub Enterprise/self-hosted remotes and for repositories opened via deep link, not just github.com.

## Likelihood Explanation
Any user who clicks "Clone in Desktop" on a link, opens an `x-github-desktop://openRepo/...` deep link, or clones a repository by URL is unprivileged and requires no special local access — this is exactly the kind of user-initiated-but-attacker-controlled-content flow the bug bounty scope calls out. The likelihood of exploitation depends on the precise Git-side mechanics that `GIT_CLONE_PROTECTION_ACTIVE` guards (which could not be fully confirmed from local repository files alone, since Git's own C source isn't part of this codebase); however, the deliberate, blanket disabling of a security-named environment variable on every clone operation is itself a strong code smell that a Git version bump or configuration change could turn into a directly exploitable path.

## Recommendation
- Determine precisely what `GIT_CLONE_PROTECTION_ACTIVE=false` disables in the bundled Git binary version Desktop ships, and remove the override unless there is a specific, narrowly-scoped, and documented reason for it (e.g., a compatibility workaround for a specific legacy flow).
- If disabling is required for compatibility, restrict it to the minimum necessary condition (e.g., only for local/trusted clones) rather than unconditionally for every remote clone, and add an explicit code comment/test documenting the security trade-off and why it's believed safe.
- Add a regression test that fails if this variable is set to `'false'` without an accompanying justification/allowlist check, so future contributors cannot silently reintroduce or widen this gap.

## Proof of Concept
Local static analysis is sufficient to demonstrate the code path, since the vulnerability is a configuration choice rather than a runtime bug:
1. A user clicks "Clone in Desktop" from a malicious GitHub repo page, or opens a deep link `x-github-desktop://openRepo/<attacker-controlled-url>` handled by `openRepositoryFromUrl`/`openOrCloneRepository`.
2. Desktop calls `dispatcher.clone(url, path)` → `appStore._clone` → `CloningRepositoriesStore.clone` → `cloneRepo` (`app/src/lib/git/clone.ts`).
3. `clone()` spawns `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` set in the environment, unconditionally, for every clone.
4. If the attacker's top-level repository declares a malicious submodule, the recursive clone/checkout of that submodule proceeds without the protection this variable is designed to enforce.

Because the exact downstream Git mechanic could not be verified from this repository's contents alone (it lives in Git's own C implementation, not in this JS/TS codebase), I cannot certify the exact CVE class this reproduces — but the code demonstrably and deliberately disables a security-labeled Git safeguard for all Desktop-initiated clones of attacker-influenceable URLs, which is the core reportable issue.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
