### Title
Webhook Shop Domain Attribution Not Covered by HMAC Signature - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification` validates an incoming webhook's HMAC signature over the raw request body only, but the `shop_domain` value used by apps to attribute the webhook payload to a specific shop is read directly from an unsigned HTTP header. Because the shop attribution is not covered by the signature, any party in possession of one valid `(body, HMAC)` pair signed with the app's shared client secret can replay that pair while forging the `X-Shopify-Shop-Domain` header to any value, and the signature check will still pass.

### Finding Description
`hmac_valid?` computes/validates the HMAC exclusively over `request.raw_post`: [1](#0-0) 

`verify_request` in the `WebhookVerification` concern calls `hmac_valid?(data)` with only the raw body, then separately exposes `shop_domain`, read straight from the `X-Shopify-Shop-Domain` request header, with no cryptographic binding to the signed body: [2](#0-1) 

Apps are explicitly instructed (and the generator scaffolds this pattern) to use this unsigned `shop_domain` value to route/attribute webhook processing to a shop: [3](#0-2) [4](#0-3) 

The webhook signing secret (`ShopifyApp.configuration.secret`) is the app's single shared client secret used for every shop that has installed the app — it is not a per-shop secret: [5](#0-4) 

This mirrors the reported bug class exactly: two logically independent inputs (the signed body vs. the shop-attribution header) are used together, but the signature only covers one of them. A party that legitimately has a valid `(raw_body, HMAC)` pair — e.g., a malicious merchant who installed the app and thus receives real, correctly-signed webhooks for their own shop — can strip/replace the `X-Shopify-Shop-Domain` header with an arbitrary victim shop domain and resend the identical body+signature. `verify_request` will still succeed because the HMAC only checks the untouched body, and the app-level job dispatch will attribute the (attacker-controlled) payload to the forged victim shop.

### Impact Explanation
An attacker who has installed the app on their own shop (an "unrelated merchant" from the perspective of any specific victim shop) can:
1. Trigger a webhook of a chosen topic for their own shop (any legitimate mutation of their own store's data), capturing the genuine `raw_post` body and `HTTP_X_SHOPIFY_HMAC_SHA256`.
2. Replay that exact request to the app's webhook endpoint, substituting `X-Shopify-Shop-Domain` with a victim shop's domain.
3. The signature check passes (it never inspected the header), and the app processes/queues a job (e.g., `CartsUpdateJob`, `CustomersDataRequestJob`, `ShopRedactJob`) attributing attacker-controlled data to the victim shop.

Depending on what the app's webhook job does with `shop_domain` (e.g. looking up the victim's session/access token and performing writes, or fulfilling GDPR data/redact requests against the wrong shop), this enables cross-shop data injection, cross-shop data corruption, or misdirected privacy actions — a genuine cross-shop access violation triggered by a forged (but signature-valid) request.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to be a genuine app installer (any merchant can install most public Shopify apps), after which capturing a valid HMAC for their own webhook traffic is trivial (it's delivered to their own endpoint). No secret leakage or privileged access beyond "being an app user" is required, matching the "unrelated-merchant HTTP request" threat model. The actual impact is entirely dependent on what the app-provided webhook job does with `shop_domain` (the vulnerability is in the framework's building block, not a self-contained exploit).

### Recommendation
Bind the shop attribution to the signed payload rather than trusting the header in isolation:
- Include the shop domain in the HMAC-covered data, or independently verify that the `X-Shopify-Shop-Domain` header corresponds to a shop with a known/expected relationship to the app (e.g., cross-check against an active, previously stored session for that domain) before dispatching shop-scoped work.
- At minimum, document prominently that `shop_domain` in `WebhookVerification` is unauthenticated and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. Malicious merchant `attacker.myshopify.com` installs the app; a real webhook (e.g. `carts/update`) is delivered to `POST /webhooks/carts_update` with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid, since it's signed with the app's shared secret).
2. Attacker resends: `POST /webhooks/carts_update` with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `verify_request` in `lib/shopify_app/controller_concerns/webhook_verification.rb` computes HMAC over `B` only — passes.
4. Controller (per generator template `lib/generators/shopify_app/add_declarative_webhook/templates/webhook_controller.rb.tt`) calls `SomeJob.perform_later(shop_domain: "victim-shop.myshopify.com", webhook: B)`, causing the app to process attacker-controlled webhook data as if it originated from the victim shop.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
