### Title
Empty aggregate signature is accepted as valid - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` accepts an aggregate containing zero `R` values, while `SchnorrAggregate::verify` accepts an empty `keys_and_challenges` slice and verifies the resulting empty multi-scalar multiplication as the identity. An attacker can therefore serialize a zero-length aggregate with `s = 0` and have it verify successfully, even though `SchnorrAggregator::complete` refuses to produce an aggregate when no signatures were supplied.

### Finding Description
`SchnorrAggregate::read` reads a 32-bit count, initializes `Rs` to an empty vector, and performs zero `C::read_G` calls when the count is zero; it then reads `s` without checking that at least one signature was encoded. [1](#0-0) 

During verification, an empty `keys_and_challenges` slice matches an empty `Rs` vector, so execution proceeds without rejecting the empty aggregate. [2](#0-1) 

The verification loop adds no statements when the slice is empty, leaving only `(-s) * G`; with `s = 0`, the result is the identity and `verify` returns `true`. [3](#0-2) 

This state cannot be produced by the legitimate aggregation API because `SchnorrAggregator::complete` explicitly returns `None` when `sigs` is empty. [4](#0-3) 

### Impact Explanation
An attacker-controlled serialized aggregate can satisfy `SchnorrAggregate::verify` without containing any individual Schnorr signature or requiring knowledge of a private key. If a caller treats verification of an empty challenge set as authorization for an aggregate operation, the attacker can forge acceptance of an aggregate signature for no statements.

The concrete public-input path is `SchnorrAggregate::read` on attacker-controlled bytes, followed by `verify` with an empty `keys_and_challenges` slice. The forged encoding is four zero bytes for the count followed by the canonical encoding of scalar zero.

### Likelihood Explanation
The attack requires a caller to invoke verification for an aggregate covering zero signatures. That is a plausible boundary condition when an outer protocol derives its statement list from attacker-supplied or empty data and does not independently reject empty batches. The cryptographic implementation itself provides no defense and accepts the malformed state directly.

### Recommendation
Reject empty aggregates in both `SchnorrAggregate::read` and `SchnorrAggregate::verify`. The verification path should independently return `false` when `Rs` or `keys_and_challenges` is empty, rather than relying on callers or serialization validation.

### Proof of Concept
For any compatible `C: Ciphersuite`, an aggregate encoded as `00 00 00 00 || encode(0)` is parsed successfully and verifies against an empty statement list:

```rust
let mut encoded = Vec::new();
encoded.extend_from_slice(&0u32.to_le_bytes());
encoded.extend_from_slice(C::F::ZERO.to_repr().as_ref());

let aggregate = SchnorrAggregate::<C>::read(&mut encoded.as_slice()).unwrap();
assert!(aggregate.verify(dst, &[]));
```

The result is guaranteed because the statement loop contributes no terms and `(-0) * G` is the identity. [5](#0-4) [3](#0-2)
