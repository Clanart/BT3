### Title
Uncaught UTF-8 decode failure on attacker-controlled DID metadata crashes wallet coin-processing - ([File: chia/wallet/did_wallet/did_wallet_puzzles.py])

### Summary
`did_program_to_metadata()` blindly decodes every key/value atom of a DID's curried metadata program as UTF-8 with no exception handling. DID metadata is fully attacker-controlled (any coin creator can curry arbitrary bytes into the metadata slot of a DID inner puzzle), and this function is invoked automatically during normal wallet sync whenever a wallet observes/tracks a DID coin. A DID minted with a non-UTF-8 byte sequence in any metadata key or value will raise an unhandled `UnicodeDecodeError` in the middle of coin-state processing.

### Finding Description
`did_program_to_metadata()` iterates the metadata program and calls `str(key, "utf-8")` / `str(val, "utf-8")` unconditionally: [1](#0-0) 

This is analogous to CVE-2019-11500's bug class: a parser/decoder that assumes well-formed textual content and mishandles malformed byte sequences supplied by an untrusted remote party, causing abnormal/uncontrolled behavior during protocol/message processing (there, out-of-bounds writes from mishandled quoted-string NULs in Dovecot; here, an unhandled decode exception from mishandled non-UTF-8 bytes in DID metadata).

The function is called from multiple wallet code paths that run automatically as part of coin ingestion, not from any user-initiated, catchable command:

- `DIDWallet.create_new_did_wallet_from_coin_spend()`, invoked when the wallet first discovers/creates a DID wallet for a received DID coin: [2](#0-1) 

- `DIDWallet.coin_added()`, invoked by `WalletStateManager` every time a new DID coin state is added for a wallet the node is tracking: [3](#0-2) 

- `WalletStateManager.determine_coin_type()`, called from the main coin-state ingestion pipeline (`_add_coin_state`) for every newly seen coin, which uncurries the puzzle and, if it matches a DID puzzle, extracts `metadata` and hands it to `DIDWallet.identify()` → eventually `did_program_to_metadata()`: [4](#0-3) [5](#0-4) 

None of these call sites wrap the metadata decoding in a try/except. A DID coin can be created by anyone; nothing in the DID puzzle constrains metadata to valid UTF-8 — `metadata_to_program()` on the construction side simply curries whatever strings the caller supplies, and on-chain metadata is just an arbitrary CLVM atom that any spender can set via a DID metadata-update condition (`opcode -24`) or at DID creation.

### Impact Explanation
When any wallet client (light/full node wallet, RPC-driven wallet service) syncs and encounters a DID coin whose metadata atoms contain a byte sequence that is not valid UTF-8, the coin-state processing coroutine raises an unhandled `UnicodeDecodeError`. Depending on how far up the call stack this propagates, this halts the wallet's coin-state/sync processing loop for that peer/update, which is a spend-triggered transaction-processing halt directly reachable by an unprivileged party who simply creates or updates a DID with malformed metadata — no signature bypass or special privilege needed, only that the victim wallet track (or become subscribed to) the DID coin. This matches the required impact category of a spend-triggered transaction-processing halt.

### Likelihood Explanation
Likelihood is high for any wallet that is watching/receiving DID coins (including via hints, since DID coins are frequently hinted to notify owners, and via `manual_did_search`/`find_lost_did` RPCs which any local RPC caller can trigger against attacker-chosen coin IDs). Constructing a DID with invalid-UTF-8 metadata requires no special privilege — it's just curried CLVM atom data, and CLVM places no charset constraint on it. The main path (`coin_added`/`determine_coin_type`) runs unconditionally during normal sync whenever such a coin is observed by a wallet that has any interest in it (e.g., via hints or DID discovery flows), so a single malicious DID creation/update can degrade or halt processing for wallets that later encounter it.

### Recommendation
Wrap the `str(key, "utf-8")` / `str(val, "utf-8")` conversions in `did_program_to_metadata()` in error handling (e.g., `errors="replace"` or catching `UnicodeDecodeError` per key/value and falling back to a safe representation, similar to how `compute_memos_for_spend`/`run_block.py` already catch `UnicodeError` around comparable memo decoding). Ensure all call sites that invoke this during automatic coin-state ingestion (`coin_added`, `determine_coin_type`, `create_new_did_wallet_from_coin_spend`, `find_lost_did`, `manual_did_search`) continue processing rather than propagate an uncaught exception that halts sync.

### Proof of Concept
1. Craft/curry a DID inner puzzle (`DID_INNERPUZ_MOD`) with a metadata kv_list where a value atom is an invalid UTF-8 byte string, e.g. `[(b"x", b"\xff\xfe")]`, via `metadata_to_program()`-equivalent CLVM currying (no length/charset check exists on this field).
2. Launch this DID on-chain as any unprivileged user (standard DID creation spend), or update an existing DID's metadata via the `-24` update condition to include such bytes.
3. Have a victim wallet (or RPC caller invoking `manual_did_search`/`find_lost_did` on that coin id) observe/sync this coin. `WalletStateManager.determine_coin_type()` → `DIDWallet.identify()`/`coin_added()` → `did_program_to_metadata()` executes `str(val, "utf-8")` on `b"\xff\xfe"`, raising `UnicodeDecodeError`, unhandled at this call site, interrupting the wallet's coin-state processing for that update.

*Note: I was not able to fully trace whether the exception is ultimately caught at a very high level (e.g., a top-level task exception handler) that merely logs it versus truly halting the sync queue permanently, due to tool-call budget exhaustion — this would benefit from a live Devin session tracing `_add_coin_state`'s caller chain and any surrounding try/except in the sync task runner to confirm the exact operational impact (transient vs. persistent halt).*

```python
def did_program_to_metadata(program: Program) -> dict[str, str]:
    """
    Convert a program to a metadata dict
    :param program: Chialisp program contains the metadata
    :return: Metadata dict
    """
    metadata = {}
    for key, val in program.as_python():
        metadata[str(key, "utf-8")] = str(val, "utf-8")
    return metadata
```
