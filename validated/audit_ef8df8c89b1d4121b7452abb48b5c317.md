## Finding [1](#0-0) 

The external report's core broken invariant is: *a precomputed/aggregated value is substituted for the specific value that should have been used, breaking the 1:1 correspondence between what was owed and what was released.* The strongest local analog is in `IntentGatewayV2`'s same-chain partial-fill escrow release, which substitutes the **entire aggregate per-token escrow balance** for the **per-leg proportional amount** when a leg completes.

### Title
Same-chain fill escrow release drains the aggregate per-token balance instead of the per-leg amount, letting a solver steal escrow earmarked for other legs of a multi-input order - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` tracks escrow per `(commitment, token)` in `_orders`, not per input-array index. [2](#0-1)  When a given output leg reaches full completion, the code releases `escrowedAmount = _orders[commitment][inputToken]` - the *entire* remaining escrow balance stored under that token key - rather than the amount proportionally attributable to that specific leg:

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [3](#0-2) 

If an order has two (or more) input entries that use the same token address (nothing in `placeOrder`/`_fillSameChain` forbids this), that shared escrow balance backs multiple, independently-tracked output legs (`_partialFills` is keyed per output token, and completion is evaluated per output index). A solver who completes just one leg gets paid out of the *combined* balance for that token, including the portion the user escrowed to pay for the other, still-unfilled leg.

### Finding Description
- `_orders[commitment][token]` is a single aggregate counter per `(commitment, token)` pair, summing every input entry that uses that token. [2](#0-1) 
- `_fillSameChain` iterates output legs by index and independently tracks each leg's fill progress via `_partialFills[commitment][outputToken]`. [4](#0-3) 
- When a leg's `amountFilled` reaches `totalRequired`, the code releases the *whole current* `_orders[commitment][token]` balance for that leg's input token - not `order.inputs[i].amount` (the amount escrowed specifically for that leg). If a second leg shares the same input token, its share is included in that first release.
- `_withdraw` decrements the aggregate balance by whatever amount it's told and reverts with `UnknownOrder()` only if the balance is already zero; it performs no per-leg reservation check. [5](#0-4) 
- Consequently, a solver filling only the leg with the smaller output requirement first can trigger the "full release" branch and drain the entire shared escrow balance (which also backs the other, larger, unfilled leg). The order is left `isFullyFilled = false` (the other leg is still open), so `_filled[commitment]` is deleted and the order stays open for further fills - but with zero escrow remaining. A second filler who later completes the other leg is skipped in `_withdraw` (amount==0 → `continue`) and receives nothing for the output tokens they supplied to the beneficiary, while the first filler already received tokens meant to compensate that second leg.

### Impact Explanation
This is a direct "wrong amount to the wrong beneficiary" fund-loss bug within the production Intent Gateway escrow/settlement path, not a rounding artifact of a benign dust unit. A single solver can walk away with escrow value that belongs to a different leg of the same order, while a legitimate second solver donates their output tokens for free (or the whole transaction later reverts if both legs are attempted together in one call, since the same aggregate balance gets counted twice into the withdrawal token array). Either way, funds move to the wrong party in the wrong amount without any privileged actor, malicious relayer, or front-running required - this is a plain unprivileged solver action against `fillOrder`.

### Likelihood Explanation
Any user (or attacker acting as their own "user") can place a same-chain order with two input entries denominated in the same token address paired with two independent output legs (e.g., `inputs = [500 USDC, 500 USDC]`, `outputs = [10 DAI, 20 WETH]`). Nothing in `placeOrder` validation rejects duplicate input token addresses. An attacker acting as solver then only needs to call `fillOrder` supplying the smaller-required output first to trigger the drain. No governance, relayer compromise, or proof forgery is needed - this is reachable purely through the public `fillOrder` entrypoint.

### Recommendation
Track escrow per output-leg index (or per `(commitment, inputIndex)`) rather than aggregating by `(commitment, token)` alone, or explicitly cap the "full release" branch's `escrowedAmount` at `order.inputs[i].amount` minus whatever has already been proportionally released for that specific leg, instead of reading the raw aggregate `_orders[commitment][token]` balance. At minimum, disallow duplicate token addresses across `order.inputs` at `placeOrder` time so the aggregate-per-token invariant in `_orders` cannot be shared between independently-tracked legs.

### Proof of Concept
1. User places a same-chain order: `inputs = [{USDC, 500}, {USDC, 500}]`, `outputs = [{DAI, 10}, {WETH, 20}]`. Total escrow recorded is `_orders[commitment][USDC] = 1000`.
2. Solver A calls `fillOrder` supplying `outputs = [{DAI, 10}, {WETH, 0}]` (only fills leg 0).
3. In `_fillSameChain`, leg 0 (`i=0`) hits `amountFilled == totalRequired` → `escrowedAmount = _orders[commitment][USDC] = 1000` (the full balance, not the 500 allocated to leg 0). Leg 1 is skipped (`solverAmount == 0`) → `isFullyFilled = false`.
4. `_withdraw` transfers the full 1000 USDC to Solver A and sets `_orders[commitment][USDC] = 0`. `_filled[commitment]` is deleted (order stays open, `PartialFill` emitted).
5. Solver B later calls `fillOrder` supplying `outputs = [{DAI, 0}, {WETH, 20}]` to complete leg 1. Leg 1 hits `amountFilled == totalRequired` → `escrowedAmount = _orders[commitment][USDC] = 0`. `_withdraw` skips the zero-amount entry (`continue`), so Solver B receives **0 USDC** despite delivering 20 WETH to the user. The order finalizes as fully filled.
6. Net result: Solver A received 1000 USDC for delivering only 10 DAI (should have received 500 USDC); Solver B delivered 20 WETH and received nothing.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
