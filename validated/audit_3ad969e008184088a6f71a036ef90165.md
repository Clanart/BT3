### Title
Auction Bid-Pool TOCTOU Race Causes Send-on-Closed-Channel Panic (Node Crash) via Concurrent `SubmitBid` and Block-Driven Pool Stop - ([File: kaiax/auction/impl/bid_pool.go])

### Summary
`BidPool.AddBid()` and `BidPool.HandleBid()` check the `running` flag and then, after a context switch, unconditionally send to `bp.newBidCh` / `bp.bidMsgCh`. Concurrently, `BidPool.stop()` (invoked from `PostInsertBlock` on every block that disables the auction, e.g. when the auctioneer/entry point becomes unset or during sync) clears `running` and closes those same channels. Because the "check running" and "close channel" operations are not synchronized with the "send to channel" operation, a goroutine that observed `running == 1` can be preempted, have the channel closed by `stop()`, and then resume and send on the now-closed channel, causing a `panic: send on closed channel` that crashes the node process.

### Finding Description
The root cause mirrors the OpenBSD CVE's bug class: a value is validated/checked, a context switch (goroutine scheduling) intervenes, another thread invalidates/frees the resource, and the original thread resumes and uses the stale resource.

- `AddBid()` checks `atomic.LoadUint32(&bp.running) == 0` at the very top, then later unconditionally executes `bp.newBidCh <- bid`: [1](#0-0) 

- `HandleBid()` performs the same pattern with `bp.bidMsgCh`: [2](#0-1) 

- `stop()` clears `running` and closes both channels without any coordination with in-flight `AddBid`/`HandleBid` calls beyond a `sync.WaitGroup` that only tracks the consumer goroutines, not producers (RPC/handler callers): [3](#0-2) 

- `stop()` is driven by `PostInsertBlock`, which is called by the node itself on every inserted block and toggles `running` to 0 whenever the auction is paused, syncing, or the on-chain auctioneer/entry point becomes unset — an event fully outside the RPC caller's control and happening asynchronously with respect to any in-flight bid submission: [4](#0-3) 

- The reachable entry point for an unprivileged actor ("auction bidder") is the `auction_submitBid` RPC method, which calls `bidPool.AddBid(bid)` directly: [5](#0-4) 

Sequence that triggers the panic:
1. Bidder A calls `SubmitBid` → `AddBid()` loads `running == 1`, passes validation, and is about to execute `bp.newBidCh <- bid`.
2. Before that send executes, the node processes a new block whose auction config is unset (or is syncing) → `PostInsertBlock` calls `stop()`, which does `close(bp.bidMsgCh); close(bp.newBidCh)`.
3. Bidder A's goroutine resumes and executes `bp.newBidCh <- bid` on the now-closed channel → Go runtime panics with `send on closed channel`, which is unrecoverable and crashes the entire node process (since there is no recover around the RPC handler goroutine chain leading to a channel send performed outside the RPC dispatcher's panic-recovery boundary, and even if recovered per-request, it still corrupts subsequent behavior of the closed channel state).

The same race applies to `HandleBid()` → `bp.bidMsgCh <- bid` (the `select { case ch <- bid: default: }` still panics if the channel is closed, since a send on a closed channel panics even inside a `select` with a `default` case).

### Impact Explanation
An unprivileged auction bidder (anyone calling the `auction` RPC namespace, or the local node's bid-gossip handler for `HandleBid`) can cause a node to crash with a runtime panic purely by natural, low-probability timing overlap with the node's own per-block `PostInsertBlock` auction-pause path — no malicious peer/consensus behavior required, and it does not require winning the race intentionally on the first attempt: an attacker can simply flood `SubmitBid` calls around blocks where the auction pauses/resumes (e.g., near hard-fork boundaries, auctioneer rotation, or sync toggling) to reliably hit the window. A crashed node is taken out of block production/consensus participation, which can cause state divergence/availability loss for that node and, if this occurs broadly, can affect network liveness — matching the "state divergence between honest nodes" and availability-impact categories in scope.

### Likelihood Explanation
The race window is real but narrow (must overlap the channel send with a `stop()` call), yet exploitability is amplified by attacker control over one side (calls to `SubmitBid`/bid gossip can be sent at arbitrarily high rate) while the other side (`PostInsertBlock`→`stop()`) is deterministic and repeated every block whenever auction parameters are cleared, during initial sync, or if the auctioneer/entry-point registry is unset. This gives an attacker practically unlimited retries against a periodic, predictable trigger, making eventual triggering likely rather than merely theoretical.

### Recommendation
- Guard the channel sends and the channel close/re-create operations with a shared mutex (or use a `sync.RWMutex` held by producers for the duration of the send and by `stop()`/`start()` for the duration of close/recreate), instead of relying solely on the `running` atomic flag as a TOCTOU guard.
- Alternatively, replace `close(ch)` semantics with a non-panicking pattern: never close producer-facing channels; instead have `stop()` set `running=0` and have consumers drain until a separate `done` signal, without ever closing channels that producers write to concurrently.
- Wrap `bp.newBidCh <- bid` and `bp.bidMsgCh <- bid` in a recovered/guarded send helper that checks a coordinated "closed" state under the same lock used by `stop()`.

### Proof of Concept
1. Configure a node with the auction module enabled and a valid on-chain auctioneer/entry point so `bidPool.running == 1`.
2. From a client, repeatedly call the `auction_submitBid` RPC (`AuctionAPI.SubmitBid` in `kaiax/auction/impl/api.go:118`) in a tight loop with valid signed bids.
3. Concurrently, trigger conditions that cause `PostInsertBlock` to toggle `running` off and call `bp.stop()` repeatedly — e.g., toggle the on-chain auctioneer/entry-point registry values across consecutive blocks (or restart sync) so that `updateAuctionInfo` alternates between valid/invalid, causing `atomic.CompareAndSwapUint32(&a.bidPool.running, 1, 0)` and full `stop()`/`start()` cycles (`kaiax/auction/impl/execution.go:29-41`, `kaiax/auction/impl/bid_pool.go:112-138`).
4. Given enough iterations, an `AddBid()` call will pass the `running` check right before `stop()` executes `close(bp.newBidCh)`, and the subsequent `bp.newBidCh <- bid` at `kaiax/auction/impl/bid_pool.go:271` will panic with `send on closed channel`, crashing the node.

```go
func (bp *BidPool) stop() {
	// Stop the bid pool.
	atomic.CompareAndSwapUint32(&bp.running, 1, 0)
	bp.clearBidPool()

	// Only close channels if they haven't been closed before
	if atomic.CompareAndSwapUint32(&bp.stopped, 0, 1) {
		close(bp.bidMsgCh)
		close(bp.newBidCh)
	}
	bp.wg.Wait()
}
```

```go
func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)

	bp.newBidCh <- bid

	return bid.Hash(), nil
```

```go
func (bp *BidPool) HandleBid(peerID string, bid *auction.Bid) {
	if atomic.LoadUint32(&bp.running) == 0 || bid == nil {
		return
	}

	// Check rate limit for this peer
	if !bp.checkRateLimit(peerID) {
		logger.Trace("Rate limit exceeded for peer", "peerID", peerID)
		return
	}

	select {
	case bp.bidMsgCh <- bid:
	default:
		logger.Trace("Bid queue is full, dropping bid", "peerID", peerID)
	}
}
```

```go
func (a *AuctionModule) PostInsertBlock(block *types.Block) error {
	if a.Downloader.Synchronising() || !a.ChainConfig.IsRandaoForkEnabled(block.Number()) {
		atomic.CompareAndSwapUint32(&a.bidPool.running, 1, 0)
		return nil
	}

	if !a.updateAuctionInfo(block.Number()) {
		logger.Debug("stop auction since auctioneer or auction entry point is not set")
		atomic.CompareAndSwapUint32(&a.bidPool.running, 1, 0)
		return nil
	}
```

```go
func (api *AuctionAPI) SubmitBid(ctx context.Context, bidInput BidInput) RPCOutput {
	numBidRequestCounter.Inc(1)
	if api.a.IsDisabled() {
		return makeRPCOutput(EMPTY_HASH, auction.ErrAuctionDisabled)
	}

	//  1. directly send target transaction
	targetTx, errTxDecode := toTx(bidInput.TargetTxRaw)
	if errTxDecode != nil {
		return makeRPCOutput(EMPTY_HASH, errTxDecode)
	}
	if targetTx.Hash() != bidInput.TargetTxHash {
		return makeRPCOutput(EMPTY_HASH, auction.ErrInvalidTargetTxHash)
	}
	errTargetTxSend := api.a.Backend.SendTx(ctx, targetTx)
	// ignore known transaction related errors against target tx validation
	if errTargetTxSend != nil && !(strings.HasPrefix(errTargetTxSend.Error(), "known transaction:") || errors.Is(errTargetTxSend, gasless_impl.ErrUnableToAddKnownBundleTx)) {
		return makeRPCOutput(EMPTY_HASH, errTargetTxSend)
	}

	// 2. add bid
	bid := ToBid(bidInput)
	bidHash, errValidateBid := api.a.bidPool.AddBid(bid)
	return makeRPCOutput(bidHash, errValidateBid)
}
```
