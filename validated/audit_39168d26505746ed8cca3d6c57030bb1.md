### Title
Optional `aggregator_verification_address` Leaves `Withdraw` and `OptimisticPayoutSign` RPCs Unauthenticated When mTLS Enforcement Is Also Disabled — (`core/src/rpc/operator.rs`, `core/src/verifier.rs`, `core/src/servers.rs`)

---

### Summary

Clementine's gRPC authorization for the `Withdraw` (operator) and `OptimisticPayoutSign` (verifier) endpoints relies on two independent, **both-optional** guards: an mTLS certificate interceptor (`client_verification: bool`) and an ECDSA aggregator-identity check (`aggregator_verification_address: Option<Address>`). When both are absent — a reachable production configuration — any network-accessible party can invoke these privileged bridge operations without proving they are the authorized aggregator, constituting a direct authorization bypass in the withdrawal and optimistic-payout flows.

---

### Finding Description

**Guard 1 — mTLS interceptor (`client_verification`).**

`create_grpc_server` in `core/src/servers.rs` wraps every service with either `OnlyAggregatorAndSelf` or `Noop` depending on the boolean flag:

```rust
// core/src/servers.rs lines 114-138
let service = InterceptedService::new(
    service,
    if config.client_verification {
        OnlyAggregatorAndSelf { aggregator_cert, our_cert: client_cert }
    } else {
        Noop          // ← any TLS client passes through
    },
);
```

When `client_verification = false`, the `Noop` interceptor is installed and every gRPC method — including `Withdraw`, `InternalWithdraw`, and `OptimisticPayoutSign` — is reachable by any TLS-capable client.

**Guard 2 — ECDSA aggregator-identity check (`aggregator_verification_address`).**

Both the operator's `withdraw` handler and the verifier's `sign_optimistic_payout` gate their ECDSA check behind an `if let Some(...)`:

```rust
// core/src/rpc/operator.rs lines 209-239
if let Some(address_in_config) = self.operator.config.aggregator_verification_address {
    // verify ECDSA signature …
}
// ← if None, no check; operator.withdraw() is called unconditionally
```

```rust
// core/src/verifier.rs lines 1601-1623
if let Some(address_in_config) = self.config.aggregator_verification_address {
    // verify ECDSA signature …
}
// ← if None, no check; MuSig2 partial-sign proceeds unconditionally
```

`aggregator_verification_address` is typed `Option<alloy::primitives::Address>` in `BridgeConfig`, so it defaults to `None` when omitted from the TOML/env configuration.

**Combined effect.**

When `client_verification = false` **and** `aggregator_verification_address = None`, neither guard fires. Any party that can open a TLS connection to the operator or verifier port can:

1. Call `Withdraw` / `InternalWithdraw` on the operator — the operator will validate the withdrawal against Citrea state, verify profitability, and broadcast a payout transaction, fronting bridge BTC without the aggregator's coordination.
2. Call `OptimisticPayoutSign` on each verifier — the verifier will produce a MuSig2 partial signature over the optimistic-payout transaction without verifying the caller's identity.

Critically, the verifier's `sign_optimistic_payout` does **not** independently verify the user's Schnorr input signature; it trusts the aggregator to have done so. An attacker calling verifiers directly can supply any `input_signature` bytes and any `out_script_pubkey`. The verifier checks only that `input_outpoint` matches the Citrea-recorded withdrawal UTXO and that `output_amount` is within bounds — it does not verify that `out_script_pubkey` matches what the user actually signed.

---

### Impact Explanation

- **Operator liquidity drain / forced payout:** An attacker can replay or race any valid Citrea-registered withdrawal directly to the operator, forcing it to broadcast payout transactions and lock up operator-controlled BTC in the TxSender queue. The operator is eventually reimbursed via kickoff, but the attacker can saturate the operator's liquidity window and disrupt legitimate withdrawal ordering.
- **Unauthorized verifier signing:** An attacker who calls all N verifiers' `OptimisticPayoutSign` endpoints directly (bypassing the aggregator) obtains N partial MuSig2 signatures. Because the verifier does not check the user's Schnorr signature, the attacker can supply a crafted `out_script_pubkey`. However, the resulting optimistic-payout transaction still requires a valid user key-spend witness for input 0 (the withdrawal UTXO), so direct BTC theft is blocked by Bitcoin script validation — but the verifiers' nonce sessions are consumed and the bridge vault UTXO is at risk of being spent with an invalid witness, causing the transaction to be rejected on-chain while the nonce is irrecoverably spent.
- **Authorization invariant broken:** The invariant "only the authorized aggregator may initiate a withdrawal or optimistic payout" is violated without any on-chain or cryptographic evidence of the breach.

---

### Likelihood Explanation

Both flags are independently optional with no code-level enforcement that at least one is active. The `aggregator_verification_address` field is explicitly documented as a temporary launch-phase measure, making `None` a common production value. `client_verification = false` is a valid deployment choice when mTLS termination is handled at the network layer (load balancer, sidecar). Any operator or verifier node reachable from the internet with this configuration is exposed.

---

### Recommendation

1. **Enforce at least one authorization mechanism at startup.** Add a startup assertion that rejects configurations where both `client_verification = false` and `aggregator_verification_address.is_none()` simultaneously, for any service that exposes `Withdraw` or `OptimisticPayoutSign`.

2. **Verify the user's Schnorr signature inside `sign_optimistic_payout`.** The verifier should independently verify `input_signature` against the constructed `opt_payout_txhandler` sighash before producing a partial signature, rather than delegating that check solely to the aggregator.

3. **Promote `aggregator_verification_address` to a required field** (or make `client_verification = true` the enforced default) so that the ECDSA identity check is not silently absent.

---

### Proof of Concept

**Setup:** Deploy operator and verifier with `client_verification = false` and `aggregator_verification_address` omitted from config (both are valid production values).

**Step 1 — Force operator withdrawal without aggregator:**
```
grpcurl -plaintext <operator_host>:<port> \
  clementine.ClementineOperator/Withdraw \
  '{"withdrawal": {"withdrawal_id": 0, "input_signature": "<valid_user_sig>",
     "input_outpoint": {"txid": {"txid": "<hex>"}, "vout": 0},
     "output_script_pubkey": "<hex>", "output_amount": 100000000}}'
```
No `verification_signature` is required. The operator validates against Citrea state and broadcasts the payout transaction, fronting BTC without aggregator approval.

**Step 2 — Collect verifier partial signatures without aggregator:**
```
# First call NonceGen on each verifier to obtain nonce session IDs
# Then call OptimisticPayoutSign on each verifier directly:
grpcurl -plaintext <verifier_host>:<port> \
  clementine.ClementineVerifier/OptimisticPayoutSign \
  '{"opt_withdrawal": {"withdrawal": {...}, "verification_signature": null},
    "nonce_gen": {"id": "<session_id>", "num_nonces": 1},
    "agg_nonce": "<hex>"}'
```
The verifier returns a `partial_sig` without checking the caller's identity or the user's Schnorr signature. Repeating across all N verifiers yields a complete MuSig2 aggregate signature over an attacker-controlled `out_script_pubkey`, consuming the verifiers' nonce sessions irreversibly.
