### Title
Graduated liquidation curve exponent (`LIQ-CURVE-EXP`) is not correctly applied, causing liquidation penalty/amount to diverge from configured risk parameters - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The graduated-liquidation exponent formula implemented in `calc-liq-factor-exp` does not compute `factor^(exp/BPS)` as documented; it truncates the exponent to an integer ratio for `exp > BPS` and hard-codes a square-root (`exp = 0.5`) for any `exp < BPS`, regardless of the actual configured value. This is the same class of bug as Allora's M-4: a normalization/weighting formula in code diverges from the specification that defines it, silently producing wrong outputs that feed directly into fund-moving logic (liquidation penalty and max-debt-to-repay).

### Finding Description
`docs/egroups.md` documents `LIQ-CURVE-EXP` as a general exponent controlling the liquidation curve shape: `>10000` = "aggressive curve", `<10000` = "gentle curve (e.g., square root)" [1](#0-0) .

The implementation, however, is:
```
(define-private (calc-liq-factor-exp (factor uint) (exp uint))
  (if (is-eq exp BPS) 
    factor
    (if (> exp BPS) 
        (/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))
        (sqrti (* factor BPS))))) ;; assume factor^0.5
``` [2](#0-1) 

Two concrete deviations from the documented formula:
1. For `exp > BPS`, Clarity's `(/ exp BPS)` is **integer** division, so any `exp` in `(10000, 19999]` truncates to `1`, making the "aggressive" branch collapse to plain linear (`factor^1`), and any `exp` in `[20000, 29999]` collapses to `factor^2` — the fractional part of the configured exponent is silently discarded, not applied via any fractional-power approximation.
2. For any `exp < BPS` that is not exactly `5000` (0.5), the code still forces `sqrti(factor * BPS)` (i.e., `factor^0.5`) — it never actually reads or uses the configured exponent's value beyond the branch comparison.

This function's output, `liq-pct-scaled`, is not cosmetic — it directly determines the liquidation penalty and the maximum amount of debt that can be liquidated:
```
(liq-pct-scaled (calc-liq-factor-exp liq-pct-linear curve-exponent))
(liq-penalty (calc-liq-factor-bound liq-pct-scaled liq-penalty-min liq-penalty-max))
(max-debt-usd (calc-liq-debt-repay total-debt-usd liq-pct-scaled))
``` [3](#0-2) 

These values are consumed directly inside the `liquidate` public entrypoint to compute how much debt is repaid and how much collateral (with penalty bonus) is seized from the borrower [4](#0-3) .

### Impact Explanation
For any egroup configured with a non-trivial `LIQ-CURVE-EXP` (any value other than exactly `10000` or `5000`), the actual `liq-pct-scaled`/`liq-penalty`/`max-debt-usd` computed on-chain diverge from what the risk parameters were designed to produce:
- When the configured curve is meant to be "aggressive" (`exp` between 10001–19999, intended as e.g. 1.2–1.9), the code truncates it down to linear (`factor^1`), which for `factor < 1` (BPS-scaled fraction) yields a **larger** `liq-pct-scaled`/penalty earlier in the liquidation range than the risk parameters intended — this transfers extra collateral value from borrowers to liquidators beyond what governance configured.
- When the configured curve is meant to be gentle at a value other than 0.5 (e.g. `exp = 3000`), the code forces `factor^0.5` instead of `factor^0.3`, which for `factor < 1` yields a **smaller** `liq-pct-scaled` than intended, under-liquidating the position relative to the configured curve and potentially leaving under-collateralized debt un-liquidated (protocol risk / bad-debt exposure).

Either direction directly changes the amount of collateral seized and debt repaid during liquidation — a wrong "how much to liquidate" verdict, not a display-only discrepancy. Depending on the direction, this results in excess value transfer to liquidators at borrowers' expense, or insufficient liquidation leaving bad debt in the protocol.

### Likelihood Explanation
This triggers deterministically whenever an egroup is configured with `LIQ-CURVE-EXP` outside `{5000, 10000}` and a liquidation occurs in that egroup — no attacker action or oracle manipulation is required, it is a pure logic/formula bug that fires on every graduated liquidation under such egroups. Likelihood depends entirely on whether DAO-configured egroups use non-default curve exponents, which is a normal, expected configuration path (the parameter exists specifically to allow different curve shapes per egroup) rather than a misconfiguration.

### Recommendation
Implement a correct fractional power calculation (e.g., a fixed-point `pow` supporting fractional exponents, or an approximation library) so that `calc-liq-factor-exp` actually computes `factor^(exp/BPS)` for arbitrary configured exponents, matching the documented curve behavior in `docs/egroups.md`. Alternatively, restrict `LIQ-CURVE-EXP` at egroup-registration time to only the values the implementation can correctly handle (e.g., `5000`, `10000`, and integer multiples of `10000`), and update the documentation to reflect this restriction, rather than allowing arbitrary values that silently compute an incorrect curve.

### Proof of Concept
1. Governance registers an egroup with `LIQ-CURVE-EXP = 15000` (documented as "aggressive curve, 1.5x").
2. A borrower's `current-ltv` moves into the partial-liquidation band, producing `liq-pct-linear = factor` (e.g. `6000` bps = 0.6).
3. `calc-liq-factor-exp` computes `(/ exp BPS)` = `(/ 15000 10000)` = `1` (integer truncation), so the "aggressive" branch returns `(pow factor 1) / (pow BPS 0)` = `factor` — i.e., plain linear scaling instead of `factor^1.5`.
4. For `factor = 0.6`, the correct aggressive value `0.6^1.5 ≈ 0.4648` is meaningfully smaller than the actually computed `0.6`; this larger `liq-pct-scaled` flows into `calc-liq-factor-bound` and `calc-liq-debt-repay`, producing a higher `liq-penalty` and larger `max-debt-usd` than the configured curve intended, which is directly consumed by `liquidate` to size the collateral seized from the borrower [4](#0-3) .
