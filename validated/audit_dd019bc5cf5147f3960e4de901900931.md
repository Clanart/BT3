## Title
Stale line-index diff selection can silently commit different lines than the user selected - (File: app/src/lib/stores/app-store.ts, app/src/models/diff/diff-selection.ts)

### Summary
The Sherlock finding is fundamentally about a positional/index invariant (`withdrawSeq` indices into `moneyMarkets`) that is only partially re-validated across mutations, allowing stale indices to silently reference the wrong underlying element. The closest analog I could substantiate in this GitHub Desktop codebase is the working-directory diff partial-selection mechanism in `DiffSelection`, which tracks a user's line-level stage/unstage choices as a `Set<number>` of **unified-diff line indices**, not as content-addressed identifiers. When the diff for the selected file is reloaded (e.g., after a `fetch`/checkout/external change to the working tree), the code only prunes indices that are no longer "selectable" — it does not verify that a surviving index still corresponds to the same line content.

### Finding Description
`DiffSelection` stores partial selections as raw line-index numbers in `divergingLines`/`selectableLines` sets, with no line-content binding: [1](#0-0) [2](#0-1) 

When the diff is reloaded in `updateChangesWorkingDirectoryDiff`, the comment explicitly acknowledges the invariant gap: the diff may have "changed dramatically since last we loaded it," yet the fix applied is only to recompute the *set of selectable indices* and intersect it with the old diverging-lines set — it does not clear or re-derive the selection by content: [3](#0-2) [4](#0-3) 

Concretely: if the working tree file changes shape between two diff loads (lines inserted/removed above a previously-selected hunk), a line index that was previously "line 40, added" can now legitimately be "selectable" as a different, unrelated added line at the same absolute index in the new diff. Because `withSelectableLines` only filters by whether the index is *still selectable* (i.e., still an included-type line at that index), not whether it's the *same* line, the old selection silently carries over onto the new line at that index. This is the same defect class as the Sherlock bug: an index-based array (`withdrawSeq`/`divergingLines`) is preserved across a structural mutation of the thing it indexes (`moneyMarkets`/diff hunks) with only a partial, length/membership-based reconciliation instead of a full content-aware rebuild.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A user who has partially staged a file (some lines checked, some not) and whose working tree diff is reloaded because of an external change to the file — including changes introduced by fetch/checkout of an attacker-controlled remote/branch that the user then merges, rebases onto, or otherwise causes the working copy to be regenerated against — can end up committing lines they never intended to select, or omitting lines they did select, without any warning. The `getSelectionType()`/`isSelected()` computations, and ultimately `formatPatch`, operate purely off these stale indices, so the final patch content sent to `git commit`/`git apply` reflects the corrupted selection rather than the user's actual intent.

### Likelihood Explanation
This requires the file's diff to be reloaded (a normal, frequent event — happens on every status refresh, external edit, or git operation) while the user has an existing partial (line-level) selection on that file, and the diff shape to change in a way that shifts selectable-line indices without invalidating them. This is a fairly common scenario for actively-worked files (e.g., a background `git fetch`+automatic merge, or another process touching the file), and no user action beyond normal partial staging is required. However, I was not able to fully trace every call path that triggers `updateChangesWorkingDirectoryDiff` (e.g., whether `clearPartialState` is always forced to `true` in the specific fetch/merge-triggered refresh paths), so I could not conclusively confirm this reaches production without additional guard rails I didn't have time to locate. The `clearPartialState` flag exists precisely to reset partial state in some flows (see `updateChangedFiles` in `app/src/lib/stores/updates/changes-state.ts`), which may mitigate this in paths I didn't fully audit.

### Recommendation
Rebind partial line selections to diff line *content* (e.g., hash of the line text plus its hunk anchor) rather than raw positional index, or force `clearPartialState = true` (full selection reset) whenever the underlying diff hunks differ from the previously loaded diff for that file, instead of only pruning by selectability.

### Proof of Concept
Not independently executable from static analysis alone — this requires reproducing a live diff-reload sequence:
1. Open a file with multiple hunks, partially select a subset of "added" lines (e.g., select only line at unified-diff index 40).
2. Trigger an external change to the file (e.g., `git fetch && git merge` bringing in unrelated changes above the previously selected hunk) so the diff is reloaded with shifted hunks but the same total selectable-line count/positions overlapping index 40.
3. Observe that `updateChangesWorkingDirectoryDiff` recomputes `selectableLines` and calls `withSelectableLines`, which keeps index 40 as diverging because it is still "selectable," even though it is now a semantically different added line.
4. Commit the file; the produced patch (via `formatPatch`) includes the new, unrelated line at index 40 instead of the originally selected one, with no notification to the user.

**Caveat:** I was unable to fully verify all upstream trigger points and the exact conditions under which `clearPartialState` is or isn't set to `true` for every diff-refresh path in `app-store.ts`, since the file is large and I could not read the complete set of call sites within the available exploration. If a background Devin session traces those call sites and confirms a path where `clearPartialState` is `false` while diff hunks materially change shape (not just line-count), that would fully confirm exploitability; absent that confirmation this should be treated as a **plausible but not fully proven** analog rather than a certainty.

  /**
   * Returns a copy of this selection instance with a specified set of
   * selectable lines. By default a DiffSelection instance allows selecting
   * all lines (in fact, it has no notion of how many lines exists or what
   * it is that is being selected).
   *
   * If the selection instance lacks a set of selectable lines it can not
   * supply an accurate value from getSelectionType when the selection of
   * all lines have diverged from the default state (since it doesn't know
   * what all lines mean).
   */
  public withSelectableLines(selectableLines: Set<number>) {
    const divergingLines = this.divergingLines
      ? new Set([...this.divergingLines].filter(x => selectableLines.has(x)))
      : null

    return new DiffSelection(
      this.defaultSelectionType,
      divergingLines,
      selectableLines
    )
  }
