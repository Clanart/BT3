### Title
PedPoP blame path panics indexing `enc_keys` for the local participant — attacker-triggerable crash during DKG - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP DKG's blame/decryption path in `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` with a HashMap `[]` access. `enc_keys` is only ever populated via `Decryption::register` for *other* participants — the local participant's own index is never inserted, because in `verify_r1` the commitments map is validated to exclude `params.i()` (`validate_map` errors with `DuplicatedParticipant` if our own index is present), so `register` is never called for ourselves. When `KeyMachine::calculate_share` encounters a malformed/invalid encrypted share from any remote participant, the resulting `BlameMachine` needs to produce a decryption/blame proof for *our* ECDH key, i.e. `decryptor == params.i()`. Indexing `enc_keys` with our own index panics (`HashMap` index-out-of-key), crashing the node instead of producing blame.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `Decryption::register` stores per-participant encryption keys:

```rust
assert!(!self.enc_keys.contains_key(&participant), "Re-registering encryption key for a participant");
self.enc_keys.insert(participant, msg.enc_key);
```

`Decryption::new` starts with an empty `enc_keys` map, and `Encryption::new` never inserts the local participant. In `SecretShareMachine::verify_r1` (`crypto/dkg/pedpop/src/lib.rs`), `register` is called only for `l` drawn from `commitment_msgs`, and `validate_map` guarantees that map contains exactly `all_participant_indexes()` *minus* `params.i()`. Therefore `enc_keys` contains every participant except ourselves.

`decrypt_with_proof` then does:

```rust
proof.dleq.verify(
  &mut encryption_key_transcript(self.context),
  &[C::generator(), msg.key],
  &[self.enc_keys[&decryptor], *proof.key],
)
```

The DLEq proves `enc_key_decryptor * msg.key = proof.key`, so `decryptor` must be the local party (`params.i()`), whose encryption public key is held in `Encryption::enc_pub_key` — but `enc_pub_key` is **not** in `decryption.enc_keys`. `self.enc_keys[&params.i()]` is a missing-key `Index` panic on `HashMap`.

A remote DKG participant reaches this path by sending the victim an `EncryptedMessage<C, SecretShare<C::F>>` that fails the PoP batch verification or fails `C::F::from_repr` after decryption (`PedPoPError::InvalidShare` in `calculate_share`). Producing the blame proof then calls `decrypt_with_proof` with `decryptor = params.i()` and panics.

### Impact Explanation
A single malicious DKG participant can crash any honest participant's process during key generation by submitting an invalid share (e.g., an `EncryptedMessage` whose ciphertext doesn't decode to a canonical `C::F`, or with an invalid `pop` Schnorr signature). Instead of returning `PedPoPError::InvalidShare` with a usable blame proof, the node panics on the missing `enc_keys` entry. This is a remotely triggerable, reliably repeatable denial of service during an availability-critical phase (multisig key generation), matching the CVE class (attacker-caused crash/complete DOS, availability impact only).

### Likelihood Explanation
Any untrusted participant in a PedPoP session controls their `EncryptionKeyMessage<Commitments>` and `EncryptedMessage<SecretShare>` bytes end-to-end; triggering `InvalidShare` is trivial (corrupt ciphertext, invalid scalar repr, invalid PoP). The crash then occurs deterministically whenever the blame path is exercised, because `enc_keys` provably never contains the local index — `register` is only invoked for peers in `verify_r1`.

Note: I could not read the `BlameMachine::blame`/`actual_faults` implementation (beyond line 534 of `pedpop/src/lib.rs` was not returned), so the exact call site passing `decryptor = params.i()` is inferred from the DLEq semantics — the proof binds `enc_keys[&decryptor]` to the victim's ECDH key, which can only be the local party's. If the implementation instead passes the accused's index, the panic disappears but the DLEq would verify against the wrong key; either way the blame mechanism is broken. This residual uncertainty should be confirmed against the `BlameMachine` source.

### Recommendation
In `Encryption`, register the local participant's own `enc_pub_key` into `decryption.enc_keys` at construction (e.g., `decryption.enc_keys.insert(i, enc_pub_key)`), or have `decrypt_with_proof` use a stored `enc_pub_key` for `decryptor == i` rather than indexing the peer map. Also replace the `self.enc_keys[&decryptor]` indexing with a checked `get` returning `DecryptionError::InvalidProof` to eliminate the panic entirely.

### Proof of Concept
1. Honest node runs `KeyGenMachine::new(params, context).generate_coefficients(rng)` for `params` with `n >= 2`, obtaining `(SecretShareMachine, EncryptionKeyMessage<Commitments>)`.
2. Attacker `l` submits a valid `EncryptionKeyMessage<Commitments>` (so round 1 passes), then sends the victim an `EncryptedMessage<C, SecretShare<C::F>>` whose ciphertext bytes are non-canonical (e.g., all `0xFF` for the scalar repr, as done by `invalidate_share_serialization` in tests).
3. Victim calls `KeyMachine::calculate_share(rng, shares)` → `C::F::from_repr` fails → `PedPoPError::InvalidShare { participant: l, blame }`; the victim proceeds to the blame flow, calling `Decryption::decrypt_with_proof` with `decryptor = params.i()`.
4. `self.enc_keys[&params.i()]` panics (`HashMap` index on absent key) — process aborts. Deterministic; no race or privileged position required.
