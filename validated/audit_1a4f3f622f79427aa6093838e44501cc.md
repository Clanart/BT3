## #VulnerabilityFound

### Title
Git argv injection via attacker-controlled branch ref name in `rebase()` - (File: `app/src/lib/git/rebase.ts`)

### Summary
`rebase()` builds the `git` argv array as `[...gitRebaseArguments(), 'rebase', baseBranch.name, targetBranch.name]` and passes `baseBranch.name`/`targetBranch.name` directly as positional arguments with no `--` end-of-options separator, unlike `checkoutBranch()` in the same codebase which explicitly guards against this class of bug.

### Finding Description
`Branch.name` is populated straight from `git for-each-ref --format=%(refname:short)` output for both local and remote-tracking refs. [1](#0-0) [2](#0-1) 

Git's low-level ref-name validation (`check-ref-format`) does not forbid a ref component from beginning with `-`; that restriction is only enforced client-side by porcelain commands such as `git branch <name>` / `git checkout -b <name>`. A malicious/compromised git server can advertise (and a client can fetch) a remote ref such as `refs/remotes/origin/--exec=touch$IFS/tmp/pwned`, which is a legal ref name and will be materialized locally as a remote-tracking branch with `Branch.name` beginning with `--`.

`rebase()` then places this attacker-controlled string as a bare positional argument to `git rebase`: [3](#0-2) 

Because there is no `--` separator terminating options before the ref arguments, a name like `--exec=<cmd>` (which implies `-i`/interactive rebase and executes `<cmd>` via the shell after each applied commit) is parsed by git as an *option*, not a ref, corrupting the intended argv and achieving command injection into the git-rebase machinery.

This is a known/previously-mitigated bug class in this codebase: `checkoutBranch()`'s helper `getBranchCheckoutArgs()` explicitly appends `'--'` after the branch ref specifically to stop ref names from being interpreted as git flags: [4](#0-3) 

`rebase()` (and also `pull()`'s `remote.name` positional argument) lacks the equivalent `--` guard. [5](#0-4) 

### Impact Explanation
If exploited, an attacker who controls a git remote (or a maliciously crafted/compromised repo the victim fetches from) can get a locally-fetched remote-tracking branch name interpreted as a `git rebase` flag such as `--exec=<shell command>`, resulting in arbitrary command execution on the victim's machine as soon as they trigger a rebase involving that branch (e.g., "Rebase current branch onto <malicious-branch>"). This meets the "code execution... where the attacker controls a cloned/fetched repository...or a git remote" bar for valid impact.

### Likelihood Explanation
Exploitation requires the victim to actually invoke `rebase()` using the attacker-named branch as `baseBranch` or `targetBranch` (e.g., via the "Rebase current branch onto" dialog), which requires some minimal user interaction, but no unusual/unnatural steps beyond fetching an attacker's remote and choosing to rebase onto/using the malicious branch — a normal desktop-app workflow. The precondition (ref name starting with `-`) is achievable server-side without needing `git branch`'s porcelain restrictions, e.g. via `git update-ref`, a custom smart-HTTP/`git-upload-pack` server, or a hosting provider that permits arbitrary ref names.

### Recommendation
Add an explicit `--` end-of-options terminator before the branch/ref arguments in `rebase()` (and audit `pull()`, `merge.ts`, and other callers that place `Branch.name`/`remote.name` as bare positional args), mirroring the existing mitigation in `checkout.ts`'s `getBranchCheckoutArgs()`. E.g.:
```ts
const result = await git(
  [...gitRebaseArguments(), 'rebase', baseBranch.name, targetBranch.name, '--'],
  repository.path,
  'rebase',
  options
)
```
Note `git rebase` accepts `--` after the branch args to end option parsing; verify the exact syntax/position with `git rebase -h` semantics and add a regression test analogous to the existing `checkout-test.ts` case that verifies rejection/safety of hostile ref names.

### Proof of Concept
1. Set up (or compromise) a git server and create a ref directly (bypassing `git branch`'s naming guard), e.g.:
   ```
   git update-ref refs/heads/--exec=touch$IFS/tmp/pwned value-of-some-commit
   ```
2. Victim adds this remote in GitHub Desktop and fetches — Desktop creates a local remote-tracking `Branch` whose `.name` is `origin/--exec=touch$IFS/tmp/pwned` (or, if used as the local checked-out branch after `checkout -b`, simply `--exec=touch$IFS/tmp/pwned`).
3. Victim opens the "Rebase current branch" flow and selects this branch as the base or target; Desktop calls `rebase(repository, baseBranch, targetBranch)`.
4. The resulting spawned process becomes effectively `git -c rebase.backend=merge rebase --exec=touch$IFS/tmp/pwned <other-branch>`, which git treats as `--exec=...` implying `-i`, executing the injected shell command as part of the rebase, creating `/tmp/pwned` (proof of arbitrary command execution).
