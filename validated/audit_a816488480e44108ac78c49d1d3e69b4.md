### Title
Order-based (not marker-validated) hunk splicing in `reassembleResolvedFile` lets a malformed conflict marker desynchronize resolved content and silently corrupt committed files - (File: app/src/lib/copilot-conflict-resolution.ts)

### Summary
`reassembleResolvedFile` reconstructs a merge-conflicted file by walking the raw on-disk text and splicing each model-provided hunk resolution into the conflict block at the current position, matched **purely by an incrementing index (`hunkIndex`)**, not by any correspondence to the actual marker content. [1](#0-0)  The function explicitly tolerates malformed/stray conflict markers by skipping the `hunkIndex` increment and copying the line through as plain content instead of failing. [2](#0-1)  Meanwhile, the only cross-check performed before reassembly, `validateResolutionPaths`, verifies solely that the **count** of returned hunks matches the **count** of hunks originally extracted for the prompt — it does not verify that the two parses agree on *which* lines constitute a conflict block. [3](#0-2)  This is structurally the same broken invariant as the Vyper report: two derivations of "the same array" (the sequence of conflict hunks) are kept in sync only via a length/count check, while the actual per-element correspondence can silently drift, causing data meant for one slot to be written into another.

### Finding Description
`reassembleResolvedFile` is fed:
1. `rawContent` — the literal file bytes from disk, still containing `<<<<<<<`/`=======`/`>>>>>>>` markers, and
2. `hunkResolutions` — an ordered array of LLM-produced replacement strings, one per conflict hunk, whose ordering and count were determined by a **separate, earlier parse** of the same file (`IFileConflictContext.hunks`, gathered when building the prompt context and validated by `validateResolutionPaths` against `expectedFiles`). [4](#0-3) 

During reassembly, the function re-parses `rawContent` independently, using its own regexes (`reassemblyOursMarker`, `reassemblySeparatorMarker`, `reassemblyTheirsMarker`) and its own well-formedness rule: a `<<<<<<<` line must be followed by a `=======` and then a `>>>>>>>` before EOF to count as a real conflict block; otherwise it is copied through untouched and `hunkIndex` is **not** advanced. [2](#0-1) 

If the earlier extraction stage (which produced the hunk count used by `validateResolutionPaths`) disagrees with this reassembly-time parse about how many/which blocks in the file are "real" conflicts — e.g. because a hunk's `oursContent`/`theirsContent` (attacker-controlled file content merged from a malicious branch/remote) contains a line that superficially matches `^<{7}` inside what is actually code, a string, or a comment, or a genuinely malformed marker sequence that one parser accepts and the other rejects — the two arrays go out of alignment while still satisfying the only guard that exists (`resolution.hunks.length !== expectedCount`). The corrupted invariant is the pairing `(hunkIndex → conflict block)`: it is treated as stable and length-checked, but is only actually valid if both independent parses of `rawContent` agree line-for-line on marker boundaries, which is never verified.

Once desynced, every subsequent real conflict block in the file receives the *wrong* model-produced resolution (off-by-one or worse), and the reassembled content — which the app writes directly to disk as the resolved file and stages/commits — is silently wrong. [5](#0-4)  Because the malformed-marker case is explicitly designed to "avoid data loss" by falling through silently (no error, no warning) [6](#0-5) , there is no signal to the user that hunks were misassigned.

### Impact Explanation
This corrupts what the user commits/pushes without their knowledge — the exact class of impact called out as valid. An attacker who controls a branch, PR, or fetched ref merged/rebased locally can craft a conflicting file containing a spurious `<<<<<<<`/`=======`/`>>>>>>>`-like sequence inside code, comments, or strings that is treated inconsistently by the context-extraction parser (used to determine `expectedHunkCounts` for validation) versus the reassembly parser (used for the actual splice). The victim, trusting the AI conflict-resolution feature to only touch conflicted regions, resolves conflicts via Copilot, and the tool silently swaps in the wrong resolved content for one or more real conflict hunks (potentially reintroducing an attacker's code, dropping the victim's own change, or splicing unrelated hunk text into the wrong location) before the file is written and committed/pushed.

### Likelihood Explanation
Exploitability depends on finding/crafting a real divergence between the (not fully verified here due to iteration limits) hunk-counting/extraction parser in `app/src/lib/copilot-conflict-context.ts` and the marker regexes in `reassembleResolvedFile`. I was able to confirm the reassembly side's exact, permissive well-formedness rule (marker must have both a separator and closing marker before EOF, else it's silently treated as non-conflict content and `hunkIndex` is not advanced), which is a plausible and common source of parser disagreement (e.g. a file that legitimately contains a `<<<<<<<`-looking line as data, or an edge case with nested/adjacent conflicts). I was not able to fully read `copilot-conflict-context.ts` in this session to confirm its exact marker-matching regex is different from the reassembly one, so likelihood should be treated as **plausible but not fully confirmed** — this is the main uncertainty in this analog.

### Recommendation
Do not rely on hunk-count equality alone. `reassembleResolvedFile` should re-derive its markers using the exact same parser/regex used to build `IFileConflictContext.hunks`, or better, carry positional identifiers (e.g., line ranges) alongside each `IHunkResolution` so reassembly can assert `hunk[i]` corresponds to the same marker block that was extracted, and fail loudly (throw `CopilotValidationError`) on any mismatch — including the malformed-marker case — rather than silently falling through.

### Proof of Concept
Conceptual PoC (exact malformed-marker trigger depends on the unverified extraction regex in `copilot-conflict-context.ts`):
1. Attacker's branch/PR introduces a file whose merge produces two real conflicts, but one side's content in the first conflict hunk contains a line beginning with `<<<<<<<` that is not a genuine marker (e.g. it's part of a code string/log format) followed later by a genuine `=======`/`>>>>>>>` pair belonging to the *real* second conflict — i.e., the extraction stage (context builder) either miscounts this as an extra hunk or the reassembly stage's lookahead (`for (let j = i + 1; j < lines.length; j++)`) pairs the fake `<<<<<<<` with the real separator/closer belonging to conflict 2. [2](#0-1) 
2. `validateResolutionPaths` only checks `resolution.hunks.length !== expectedCount`, so if both stages agree on the same *count* (even if not the same *positions*), no error is raised. [7](#0-6) 
3. `reassembleResolvedFile` splices `hunkResolutions[0]` into the (wrong) block boundary its own lookahead found, and increments `hunkIndex`, offsetting every subsequent real hunk's resolution by one position. [8](#0-7) 
4. The resulting `resolvedContent` is written back and can be committed/pushed with silently wrong merged content, with no error surfaced to the user.

**Uncertainty note:** I could not, within the available iterations, fully read `app/src/lib/copilot-conflict-context.ts` to confirm the exact regex/algorithm it uses to enumerate hunks for `expectedHunkCounts` and compare it byte-for-byte against `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker`. The vulnerable *mechanism* (index-only correspondence with no structural re-validation, and silent fallthrough on malformed markers) is confirmed directly in `copilot-conflict-resolution.ts`; whether a concrete two-parser divergence exists in the current code should be verified with a full read of `copilot-conflict-context.ts` and a live repro against a crafted conflicted file.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

/**
 * Combine raw per-hunk model resolutions with original file contexts to
 * produce the final {@link IFileResolution} array that the rest of the app
 * expects (each entry has the complete reassembled file content).
 *
 * This is the bridge between the model's lightweight per-hunk output and
 * the existing UI and write path which need full file content.
 */
export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
