### Title
Panic on unregistered decryptor index in blame-decryption path enables remote DoS - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` directly, so an attacker-controlled `decryptor` participant index for which no encryption key was ever registered causes a panic (HashMap index out-of-bounds) instead of returning an error — a crash/DoS analog of the crafted-input crash in ALPINE-CVE-2017-11552.

### Finding Description
In `decrypt_with_proof`, the accuser supplies an `EncryptionKeyProof` along with a `decryptor` `Participant` index to decrypt an alleged bad share:

```rust
// crypto/dkg/pedpop/src/encryption.rs:381-392
proof
  .dleq
  .verify(
    &mut encryption_key_transcript(self.context),
    &[C::generator(), msg.key],
    &[self.enc_keys[&decryptor], *proof.key],   // panics if decryptor not registered
  )
  .map_err(|_| DecryptionError::InvalidProof)?;
```

`enc_keys` is only populated via `register`, which inserts exactly one entry per participant (`assert!(!self.enc_keys.contains_key(&participant))` at encryption.rs:356-360). Registration happens only for participants that sent a valid `EncryptionKeyMessage`. A `decryptor` index that was never registered — e.g., an index outside the DKG set, or a participant whose registration message was dropped/malformed — hits the `HashMap` `Index` implementation, which panics on a missing key rather than returning the declared `DecryptionError::InvalidProof`.

Because the blame/accusation message is attacker-controlled data (`from`, `decryptor`, the `EncryptedMessage`, and the `EncryptionKeyProof` are all deserialized from peer bytes via `EncryptedMessage::read`/`EncryptionKeyProof::read` at encryption.rs:171-177 and 267-269), an unprivileged DKG participant can craft an accusation naming an arbitrary `decryptor` and reliably panic the honest node processing the blame, matching the "crafted input reaches unchecked memory use → crash" bug class of CVE-2017-11552 in Rust's panic-based form.

### Impact Explanation
A malicious DKG participant aborts the key-generation/blame-handling process on every honest peer that evaluates the accusation, denying service of the PedPoP DKG. Since `decrypt_with_proof` is invoked during fault attribution, a malicious party can also use it to crash peers that attempt to hold them accountable, evading blame while liveliness fails. No memory-unsafe corruption occurs (Rust bounds-checks the map access), but the availability impact — a remotely triggerable, deterministic panic on attacker-supplied public inputs — is the direct analog of the crafted-file crash in the reference advisory. Severity: Medium (availability only, requires participating in/blaming within a DKG session).

### Likelihood Explanation
The trigger is trivial: submit an `EncryptionKeyProof` accusation with any `decryptor` index absent from `enc_keys`. The PoP signature check on `msg` (encryption.rs:374-379) must pass first, but the accuser can satisfy it by encrypting a message under their own PoP key — no collusion, no leaked keys, and no invalid-curve inputs required. Deterministic, single-shot crash.

### Recommendation
Replace the unchecked index `self.enc_keys[&decryptor]` with `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?` so an unknown decryptor index is handled as an invalid proof rather than a panic. Audit `verify_share`/`complete`-adjacent map indexing (e.g., `self.0[&l]` in `BindingFactor::binding_factors`/`bound`, nonce.rs:176-183) for the same pattern.

### Proof of Concept
1. Complete the PedPoP commitment round where honest node H registers encryption keys for a strict subset of `Participant` indexes (or simply omits index `p_x`).
2. Attacker sends H a blame accusation: `EncryptedMessage` with a valid `pop` Schnorr signature (attacker signs it with their own ephemeral key, satisfying `pop.verify` at encryption.rs:374-379) plus an `EncryptionKeyProof` and `decryptor = p_x`.
3. H calls `decrypt_with_proof(from, p_x, msg, Some(proof))`; at encryption.rs:388, `self.enc_keys[&p_x]` panics with "key not found", aborting the process instead of returning `Err(DecryptionError::InvalidProof)`. [1](#0-0) [2](#0-1)

  pub(crate) fn decrypt_with_proof<E: Encryptable>(
    &self,
    from: Participant,
    decryptor: Participant,
    mut msg: EncryptedMessage<C, E>,
    // There's no encryption key proof if the accusation is of an invalid signature
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Result<Zeroizing<E>, DecryptionError> {
    if !msg.pop.verify(
      msg.key,
      pop_challenge::<C>(self.context, msg.pop.R, msg.key, from, msg.msg.deref().as_ref()),
    ) {
      Err(DecryptionError::InvalidSignature)?;
    }

    if let Some(proof) = proof {
      // Verify this is the decryption key for this message
      proof
        .dleq
        .verify(
          &mut encryption_key_transcript(self.context),
          &[C::generator(), msg.key],
          &[self.enc_keys[&decryptor], *proof.key],
        )
        .map_err(|_| DecryptionError::InvalidProof)?;

      cipher::<C>(self.context, &proof.key).apply_keystream(msg.msg.as_mut().as_mut());
      Ok(msg.msg)
    } else {
      Err(DecryptionError::InvalidProof)
    }
  }
