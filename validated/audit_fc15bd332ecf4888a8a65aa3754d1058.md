### Title
`SignableTransaction::new` computes fee and weight without the OP_RETURN data output, underpaying the fee relative to the signed transaction's actual vsize — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The bug class of the reference finding is a *unit/scale mismatch in a composed calculation*: an intermediate quantity is computed in one unit (price decimals) and consumed assuming another. The same shape exists in `SignableTransaction::new`: `tx_outs` includes the OP_RETURN `data` output, but the weight/vbytes used to derive `needed_fee`, the `TooLowFee` check, the `NotEnoughFunds` check, and the change amount are all computed from `payments` alone — i.e., measured in the "vbytes of a transaction without the data output" unit and then applied to a transaction that has one. The signed transaction is up to ~90 vbytes larger than what the fee was priced for.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the `data` output is pushed onto `tx_outs` *before* the weight is measured, but `calculate_weight_vbytes` is only ever called with `payments`, never with `tx_outs`:

- OP_RETURN output is appended to `tx_outs` at `send.rs:193-202` (up to 80 bytes of data, checked at ~`send.rs:178-186`).
- `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` at `send.rs:204` builds a dummy `Transaction` whose `output` list is only the payments (`send.rs:85-93`) — the OP_RETURN output is absent.
- `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) therefore prices a smaller transaction than the one constructed at `send.rs:245-251` (which uses `tx_outs`, including the data output).
- The minimum-relay check `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (`send.rs:211`) and the `MAX_STANDARD_TX_WEIGHT` check (`send.rs:241`) likewise use the data-less `weight`/`vbytes`.
- In the change branch (`send.rs:224-235`), `fee_with_change` and the change `value` are computed from `vbytes_with_change`, again without the data output — so `change = input_sat - payment_sat - fee_with_change` credits the fee shortfall into the change output while the actual transaction still carries the unpriced OP_RETURN.

Net effect: `fee()` (`send.rs:138-141`) equals `needed_fee`, but the real transaction is `data.len() + ~11` bytes (≈ `4*(data+11)` weight units ≈ `data+11` vbytes) larger than the measured one. With the maximum 80-byte payload, the actual fee rate is roughly `fee_per_vbyte * vbytes / (vbytes + ~91)`, and `needed_fee` can be less than `DEFAULT_MIN_RELAY_TX_FEE * actual_vsize / 1000` even though the `TooLowFee` check passed. Conversely `needed_fee()` overstates nothing but understates the true required fee for the requested rate, and `weight` can exceed `MAX_STANDARD_TX_WEIGHT` undetected when the data pushes it over.

This is the same class as `CompositeMultiOracle`: a composed pipeline computes a scaled quantity (vbytes → fee) from inputs measured in the wrong unit (transaction without the data output), and the final consumer (`fee = inputs - outputs`) divides/applies it as if it described the real transaction.

### Impact Explanation
Medium. A `SignableTransaction` built with `data = Some(..)` produces a transaction whose real fee rate is strictly lower than the caller-specified `fee_per_vbyte`, and potentially below the network minimum relay fee despite the explicit `TooLowFee` guard. That yields a signed, intended-message transaction that may not propagate or confirm — funds sit in an unconfirmed/stuck state and change accounting is off by the unpriced output. The `TooLargeTransaction` bound can also be violated on-chain without the constructor catching it. No secret material is exposed, so it does not reach High.

### Likelihood Explanation
Reachability requires a caller to pass `Some(data)` to `SignableTransaction::new`. The in-scope processor call site (`processor/src/networks/bitcoin.rs:446-452`) passes `None`, so within the audited composition this path is only exercised by external integrators embedding OP_RETURN payloads — which is a documented feature of the API (`data` parameter, `TooMuchData` bound at 80 bytes). Any such use deterministically triggers the mispricing; severity of the fee shortfall grows with `data.len()` and with low `fee_per_vbyte`/small payments where ~91 extra vbytes is proportionally large.

### Recommendation
Include the OP_RETURN output in the weight estimation. Either pass the already-built `tx_outs` into `calculate_weight_vbytes` (change appended after), or add an explicit `data: Option<&[u8]>` parameter that pushes the same `ScriptBuf::new_op_return` output into the dummy transaction. Recompute both the `needed_fee`/`TooLowFee`/`NotEnoughFunds` branch and the `fee_with_change`/`weight` branch with the data-bearing layout, and enforce `MAX_STANDARD_TX_WEIGHT` against the weight that includes the data output.

### Proof of Concept
```rust
// networks/bitcoin in-scope API misuse demonstration
let data = vec![0u8; 80]; // maximal permitted OP_RETURN payload (checked <= 80)
let tx = SignableTransaction::new(inputs, &payments, None, Some(data.clone()), fee_per_vbyte)?;

// tx has an extra TxOut { value: 0, script_pubkey: OP_RETURN <80 bytes> }
// actual vsize ≈ measured_vbytes + 80 + ~11 (output base + pushdata overhead)
assert!(tx.tx.output.iter().any(|o| o.script_pubkey.is_op_return()));

// fee actually paid
let paid = tx.fee(); // == needed_fee == fee_per_vbyte * vbytes_without_data
// effective rate = paid / tx.vsize() < fee_per_vbyte
// and possibly paid < DEFAULT_MIN_RELAY_TX_FEE * tx.vsize() / 1000,
// despite SignableTransaction::new not returning TooLowFee.
```
The error is deterministic at `send.rs:204`/`send.rs:225-226`: both `calculate_weight_vbytes` calls receive `payments` while the real outputs (`tx_outs`) contain the additional data output.
