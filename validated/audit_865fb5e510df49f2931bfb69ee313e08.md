Based on my investigation, I found a genuine local analog to the reported reentrancy pattern in the Intent Gateway's same-chain fill logic.

### Title
Reentrancy window in `_fillSameChain` clears the fill lock before an untrusted external call, letting a malicious solver re-enter with an inconsistent `_filled` state - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntrinsicIntents._fillSameChain` sets `_filled[commitment] = msg.sender` at the top of the function (CEI-style, matching the fix documented in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`), which correctly blocks reentrant `fillOrder` calls during the beneficiary token-transfer loop. However, on the **partial-fill path**, the function later does `delete _filled[commitment]` and *then* performs an unguarded external call — `msg.sender.call{value: msgValue}("")` — to refund unspent native tokens to the solver, who is fully attacker-controlled. This restores the exact "transfer in the middle of the code, while the contract is in an inconsistent state" pattern from the external report, except here the "state" that becomes attacker-controllable mid-call is the `_filled` fill-lock itself.

### Finding Description
In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:54-149`): [1](#0-0) 

```solidity
WithdrawalRequest memory body = WithdrawalRequest({
    commitment: commitment, tokens: escrowedInputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
});
_withdraw(body, false, isFullyFilled);

if (isFullyFilled) {
    _execute(order, outputsLen);
    emit OrderFilled(...);
} else {
    delete _filled[commitment];
    emit PartialFill(...);
}

// Refund any unspent native tokens to the solver.
if (msgValue > 0) {
    (bool sent,) = msg.sender.call{value: msgValue}("");
    if (!sent) revert InsufficientNativeToken();
}
```

`_filled[commitment]` is deliberately cleared for the partial-fill branch so the order remains fillable later, but the clearing happens **before** the final native-token refund, which is a raw `.call` to `msg.sender` — the solver, an arbitrary and unprivileged address that calls `fillOrder` directly. A malicious solver contract can:
1. Call `fillOrder` with any nonzero `msg.value` left unconsumed (trivial when outputs are ERC20-denominated, since native value is never touched by the loop) and options producing a partial fill (`isFullyFilled = false`).
2. Receive the native-refund callback in its `receive()` function at a point where `_filled[commitment] == address(0)` again, i.e., the "fill lock" the rest of the contract relies on to gate `fillOrder`/`cancelOrder` re-entry for this commitment has already been reset, even though `_withdraw` and event emission for this call have already executed.
3. From that callback, re-enter `fillOrder` (or other unguarded external functions) against the *same* `commitment` while the outer call's stack frame is still unwound, executing logic (`_execute`, further `_withdraw` calls, `PartialFillNotAllowed` gating, surplus/dust accounting) against state that the outer call's local variables (`isFullyFilled`, `outputFills`, `escrowedInputs`) no longer reflect.
