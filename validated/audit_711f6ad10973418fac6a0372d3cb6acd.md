## Finding

### Title
Insufficient validation in automatic remote-URL rewrite allows silent redirection of `push`/`fetch` traffic to an attacker-controlled host - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
When GitHub Desktop refreshes the metadata for a tracked repository, it compares the locally configured `origin` remote against the `clone_url` returned by the GitHub API and, if it decides the repository was "renamed," silently rewrites the user's git remote to the new URL with `git remote set-url`. The only server-supplied value that is validated before this rewrite is the **URL scheme** (`https:` vs `ssh:`); the **hostname, owner, and repository name of the new URL are never checked against the account's expected endpoint**. Any actor able to influence the API response for a repository the user already has open (a compromised/malicious GitHub Enterprise endpoint, a MITM'd API response, or a takeover of the account's configured endpoint) can therefore point the value at an entirely different host, and Desktop will rewrite the user's remote to it without any prompt.

### Finding Description
The refresh flow is: [1](#0-0) 

`repositoryWithRefreshedGitHubRepository` fetches `apiRepo` from the API (`api.fetchRepository(owner, name)`) for the account associated with the repository, and unconditionally passes it into `updateRemoteUrl`: [2](#0-1) 

The corrupted value is `gitStore.defaultRemote`'s `url` (the `origin` remote configured in `.git/config`). The guard logic is:

1. `protocolsMatch` — only compares `URL.parse(...).protocol` (`https:`/`ssh:`), not hostname.
2. `remoteUrlUnchanged` — checks that the *previously cached* `gitHubRepository.cloneURL` still matches the current remote (via `urlMatchesRemote`), which is normally true for any repository Desktop is already tracking.
3. `urlsMatch` — is deliberately `false` when the API's `clone_url` differs from the current remote (that's the "rename" signal that triggers the rewrite).

None of these three checks constrain `updatedRemoteUrl` to the same hostname/owner as the account's endpoint or as the previously known repository. `urlMatchesRemote` itself only compares `hostname`, `owner`, and `name` — it never validates that the *new* `apiRepo.clone_url` shares a hostname with the *old* remote: [3](#0-2) 

As a result, if the API endpoint associated with the account returns `clone_url: "https://attacker.example.com/foo/bar.git"` (e.g. a compromised GitHub Enterprise Server, a network-level tamperer of the API response, or any other scenario where the "GitHub API object" is attacker-influenced), Desktop treats it exactly like a legitimate GitHub.com rename and silently calls `gitStore.setRemoteURL('origin', updatedRemoteUrl)`, rewriting `.git/config` to point `origin` at the attacker's server — with **no user confirmation dialog**.

The unit tests confirm the guard is protocol-only and never hostname-based: [4](#0-3) 

Note this test only proves the *protocol* mismatch is rejected; there is no test (and no code) rejecting a *hostname* mismatch when protocols agree.

### Impact Explanation
Once `origin` is silently repointed:
- The next `git push` sends the user's code (potentially private/proprietary) to the attacker's server instead of GitHub.
- The next `git fetch`/`pull` merges attacker-controlled commits into the user's working tree under the belief they came from the real repository, enabling supply-chain injection of malicious code that the developer may build/run locally.
- Because Desktop's credential trampoline (`findGitHubTrampolineAccount`) scopes GitHub credentials to matching account origin, this does not directly leak the GitHub token to the attacker host, but the git-history/code exfiltration and injected-commit paths are on their own sufficient to satisfy "silent corruption of what the user commits or pushes" and unauthorized code execution risk once tampered commits are checked out and executed.

This matches the "insufficient validation" bug class from the source report: a value from an external, potentially attacker-influenced source (there, an on-chain price/amount; here, a `clone_url` field from an API response) is trusted and used to mutate critical state without adequate bounds checking.

### Likelihood Explanation
The rewrite path only fires during automatic background repository refresh for any repository Desktop already associates with a `GitHubRepository`, requiring no user interaction beyond having the app open with the repository being periodically refreshed. The precondition is that the API response for `repos/{owner}/{name}` on the account's configured endpoint returns an attacker-chosen `clone_url` — realistic for a malicious/compromised GitHub Enterprise Server the user has added as an account, or any man-in-the-middle position on that endpoint's traffic, without requiring local access, admin rights, or pre-existing malware.

### Recommendation
In `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts`), before rewriting the remote, additionally validate that the new URL's hostname matches either the account's expected endpoint host or the previously known `gitHubRepository` hostname (not just that the protocol matches), and/or surface a confirmation prompt to the user when the hostname of the incoming `clone_url` differs from the currently configured remote's hostname.

### Proof of Concept
1. Add a GitHub Enterprise account in Desktop pointed at a server the attacker controls (or intercept/tamper the API response for that endpoint).
2. Open/track a repository whose `origin` matches that endpoint's `clone_url`.
3. Have the compromised/malicious endpoint respond to `GET repos/{owner}/{name}` with `clone_url: "https://attacker.example.com/foo/bar.git"` (same `https:` scheme as the current remote).
4. Trigger a background repository refresh (`repositoryWithRefreshedGitHubRepository`, invoked periodically by Desktop).
5. Observe that `updateRemoteUrl` calls `gitStore.setRemoteURL('origin', 'https://attacker.example.com/foo/bar.git')` with no prompt, confirmed by the existing unit test file at `app/test/unit/stores/updates/update-remote-url-test.ts:68-81`, which shows a same-protocol, different-URL `clone_url` is silently applied.
6. Subsequent `git push`/`git fetch` in Desktop now targets the attacker's server.

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
