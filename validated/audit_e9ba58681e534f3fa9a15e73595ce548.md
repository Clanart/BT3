### Title
Attacker-controlled `n` in `ThresholdKeys::read` triggers immediate ~2 MB allocation before any input validation — (File: crypto/dkg/src/lib.rs)

### Summary
The deserialization path for `ThresholdKeys` reads the participant count `n` directly from the input stream and immediately calls `Vec::with_capacity(usize::from(n))` when the interpolation tag is `Constant` (tag `0`), before `ThresholdParams::new` validates `t <= n` or confirms that the stream actually contains `n` scalars. An unprivileged party feeding untrusted bytes to `ThresholdKeys::read` can set `n = 65535` and force a ~2 MB heap allocation (65535 × `C::F`) with only a handful of bytes of input — the same CWE-770 "allocation of resources without limits" bug class as CVE-2018-1274.

### Finding Description
In `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632), the header parsing reads `t`, `n`, `i` as raw `u16`s from the reader, then matches on the interpolation tag:

```rust
let interpolation = match interpolation[0] {
  0 => Interpolation::Constant({
    let mut res = Vec::with_capacity(usize::from(n));   // line 608
    for _ in 0 .. n {
      res.push(C::read_F(reader)?);
    }
    res
  }),
  1 => Interpolation::Lagrange,
  ...
};
```

`Vec::with_capacity` commits the full allocation up front. The subsequent `C::read_F` loop fails with EOF after the first missing scalar, but the 65535-element allocation has already been made and only released on drop. Validation via `ThresholdParams::new(t, n, i)` and the `t != n` check for `Constant` interpolation (crypto/dkg/src/lib.rs:367-374) happens only afterward, at `ThresholdKeys::new` (line 625). The advisory's class — trusting a length field to size an allocation before verifying the data exists — maps directly onto this pattern.

The analogous pre-allocation in `Commitments::read` (crypto/dkg/pedpop/src/lib.rs:111) uses `params.t()` from locally configured parameters, not attacker bytes, so it is not attacker-controlled; `ThresholdKeys::read` is the reachable case since `n` comes from the byte stream.

### Impact Explanation
Each call costs the attacker ~11 bytes (4-byte ID len + ID + 6 bytes of `t`,`n`,`i` + 1 tag byte) yet forces the victim to allocate `65535 * size_of::<C::F>()` (~2 MB for 32-byte scalars) and then drop it. Repeated calls create sustained allocation churn and memory pressure proportional to request rate — a classic amplification DoS against any endpoint or component that deserializes `ThresholdKeys` from bytes an unprivileged party can influence. No secret material is exposed; impact is availability only.

### Likelihood Explanation
Exploitation requires only that attacker-influenced bytes reach `ThresholdKeys::read` — an entry point explicitly in scope for untrusted input. Triggering it needs a single valid curve `C::ID` prefix followed by `n = 0xFFFF` and interpolation tag `0`; no valid scalars, proofs, or signatures are needed since the allocation precedes all semantic validation. Likelihood is gated purely by whether the deployment exposes this deserialization to untrusted bytes (e.g., keys/messages relayed or restored from peer-supplied data rather than strictly local storage).

### Recommendation
Cap the pre-allocation: replace `Vec::with_capacity(usize::from(n))` with `Vec::new()` (push as bytes are actually read), or validate `t`/`n` bounds and the `Constant`-requires-`t == n` invariant before allocating. More generally, follow the pattern already used in `Call::read` in `networks/ethereum/src/machine.rs:51-60` — never size an allocation from a declared length until the corresponding bytes have been consumed.
