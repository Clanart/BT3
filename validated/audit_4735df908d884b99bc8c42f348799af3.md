### Title
Unbounded FIFO subscription cap lets any unprivileged purchaser evict another app's already-paid bandwidth allowance - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`pallet-bandwidth` stores each `(app_chain, app)` bandwidth allowance as a FIFO list bounded by a hardcoded cap `MAX_SUBSCRIPTIONS = 1024` [1](#0-0) . When the list is full, `push_subscription` silently **evicts the oldest entry** to make room for the new one [2](#0-1) . Because the `(app_chain, app)` key that receives the credit is attacker-controlled and independent of who pays (documented "Sponsorship" feature), and `purchase()` is a fully public, unauthenticated entrypoint on `BandwidthManager.sol` [3](#0-2) , any unprivileged account can repeatedly buy the cheapest tier against a victim's `(chain, app)` bucket to fill the 1024-slot FIFO and push out the victim's legitimately-purchased, unexpired allowance — destroying bytes the victim already paid for, with `SubscriptionEvicted` firing only after the loss has occurred.

### Finding Description
This is a direct structural analog of the reported bug class: a hardcoded retrieval/storage limit (`1024` in both the Elys delegation case and here) whose overflow behavior causes silent loss of value instead of being handled safely. In Elys, exceeding 1024 delegations meant undercounted rewards; here, exceeding 1024 subscriptions means a real eviction of another party's paid allowance.

Concretely:
- `Allowance<T>` is a `StorageDoubleMap<StateMachine, AppKey, BoundedVec<Subscription, MaxSubscriptions>>` keyed purely by `app_chain` and `app`, both fully attacker-supplied via the purchase message body [4](#0-3) .
- `on_accept` validates only that the `request.from` matches the registered `BandwidthManager` for the *source* chain — it performs no validation tying `msg.chain`/`msg.app` to the actual payer or to any ownership of the target app [5](#0-4) .
- `push_subscription` unconditionally evicts index `0` (the oldest, FIFO-head) subscription once the list length equals `MAX_SUBSCRIPTIONS`, regardless of how much value (unspent bytes, remaining duration) that entry represents [2](#0-1) .
- `BandwidthManager.sol::purchase()` requires no relationship between `msg.sender` and the `app`/`chain` being credited — it is a public function callable by anyone who holds the fee token [3](#0-2) .

An attacker can therefore issue enough minimum-tier, single-month purchases against a target `(app_chain, app)` pair to advance the FIFO head past the victim's subscription, permanently destroying it and emitting `SubscriptionEvicted` only as an after-the-fact record — not a preventive guard.

### Impact Explanation
This falls under "stealing or loss of funds" and "logic attacks" in the bounty scope: a victim who paid for a bandwidth tier (potentially a large multi-month, high-tier purchase bundled into a single FIFO entry) can have that entry destroyed by an unprivileged third party without ever touching the victim's funds directly — the loss is the wasted payment for bandwidth that never gets consumed. This is a genuine value-destruction primitive reachable through a normal, permissionless public entrypoint (`purchase()`), not requiring any relayer, prover, or admin compromise.

### Likelihood Explanation
The attack is economically bounded but real: filling/advancing the FIFO by N slots costs the attacker N minimum-tier purchases (e.g., the $50 plan) [6](#0-5) . Because a single victim purchase — even one buying many months in one call — still occupies exactly **one** FIFO slot [7](#0-6) , an attacker only needs enough purchases to advance the head to the victim's specific slot position, which can be small if the victim's entry is near the front of an already-busy queue, or the attacker pre-fills the queue before the victim buys. The griefing cost scales with the number of slots to evict, not with the value destroyed, so a victim's large, expensive top-up can be destroyed disproportionately cheaply relative to what was paid.

### Recommendation
- Do not evict entries purely by FIFO position; require either (a) per-purchaser scoped allowance buckets so unrelated purchasers cannot affect each other's queue position, or (b) a value/remaining-bytes-aware eviction policy that never destroys a not-yet-consumed subscription without proportional compensation or a governance-controlled path.
- Consider raising or making `MAX_SUBSCRIPTIONS` reflect actual expected churn per app rather than a single global constant, and/or rate-limit or price purchases progressively as the queue for a given `(chain, app)` nears capacity so a low-cost purchase cannot easily reach the head.
- Emit `SubscriptionEvicted` pre-emptively (e.g., reject or require an explicit governance/self-purchaser confirmation) rather than only as a post-hoc audit event.

### Proof of Concept
1. Governance registers a `BandwidthManager` for source chain `EVM-8453` and configures at least one cheap tier (e.g., `TierOne`, `$50`).
2. Victim calls `BandwidthManager.purchase(app=VictimApp, tier=TierFour, months=12, chain="EVM-1")`, crediting a large, single FIFO entry to `(EVM-1, VictimApp)` via `pallet-bandwidth::on_accept` → `push_subscription` [7](#0-6) .
3. Attacker (any address, no relationship to VictimApp) repeatedly calls `purchase(app=VictimApp, tier=TierOne, months=1, chain="EVM-1")` from any source chain with a registered manager, each call appending one cheap entry to the same `(EVM-1, VictimApp)` FIFO list [3](#0-2) .
4. Once the list reaches `MAX_SUBSCRIPTIONS = 1024` entries and the victim's entry becomes the oldest, the next attacker purchase evicts it via `list.remove(0)` in `push_subscription`, deleting the victim's remaining, paid-for byte allowance [2](#0-1) .
5. `Event::SubscriptionEvicted` is emitted with the lost bytes, confirming the destruction occurred with no recourse for the victim.

			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || chain.length == 0 || months == 0) revert InvalidPurchase();
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);
