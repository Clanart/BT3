### Title
Unhandled `KeyError` crash in `Offer.get_cancellation_coins()` from a self-referencing coin announcement dependency - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer.get_cancellation_coins()` and its helper `detect_dependent_coin()` in [1](#0-0)  walk the announcement/assertion graph of the coin spends contained in an (attacker-suppliable) `Offer` object to figure out which coins, if cancelled, would invalidate the whole trade. The propagation loop in [2](#0-1)  pops each identified coin out of the `dependencies`/`announcements` dictionaries exactly once — but it can be made to enqueue the very same coin twice in `remove_these_keys`, leading to a double `dict.pop()` and an unhandled `KeyError`.

### Finding Description
`detect_dependent_coin()` finds a coin `name` whose `ASSERT_COIN_ANNOUNCEMENT` (opcode 61) argument matches an announcement (opcode 60) created by a *different* coin `coin` (`coin != name` is enforced) [3](#0-2) . This returns `(removed_coin, provider)`.

`get_cancellation_coins()` then propagates the removal: it seeds `remove_these_keys = [removed_coin]` and computes `removed_announcements = announcements[removed_coin]` (i.e. the messages `removed_coin` itself announces) [4](#0-3) . It then scans every coin's `dependencies` for anything intersecting `removed_announcements`, excluding only the `provider` coin:

```
for coin, deps in dependencies.items():
    if set(deps) & set(removed_announcements) and coin != provider:
        remove_these_keys.append(coin)
``` [5](#0-4) 

The check only excludes `provider` — it does **not** exclude `removed_coin` itself. If the coin identified as `removed_coin` was crafted so that it both creates an announcement `M` (opcode 60) and also asserts that same announcement `M` on itself (opcode 61 with `asserted_id == removed_coin`'s own coin id), then `dependencies[removed_coin]` intersects `removed_announcements` (which is exactly `announcements[removed_coin]`), and since `removed_coin != provider` is always true (the two are proven distinct by the `coin != name` check in `detect_dependent_coin`), the loop appends `removed_coin` a second time: `remove_these_keys = [removed_coin, removed_coin]`.

The next block then executes:
```
for coin in remove_these_keys:
    dependencies.pop(coin)
    removed_announcements.extend(announcements.pop(coin))
``` [6](#0-5) 

Popping `removed_coin` a second time raises an unhandled `KeyError`, crashing the call to `get_cancellation_coins()`. This is the direct structural analog of CVE-2018-9261: a self-linking node/coin (self-referencing DCH-ID equivalent) that is not excluded from the traversal, causing the loop bookkeeping to corrupt itself instead of a heap overflow, but with the same root cause class — "self-linking" of an identifier that the algorithm assumed could not point back to itself, and only partially guards against (`coin != name` in the detector, but not `coin != removed_coin` in the propagation loop).

### Impact Explanation
`Offer` objects are deserialized from external, untrusted byte streams via `Offer.from_bech32`/`Offer.from_bytes`/`Offer.from_spend_bundle` [7](#0-6) , i.e. an offer file handed to a wallet by an untrusted counterparty. `get_cancellation_coins()` is invoked from `chia/wallet/trade_manager.py` when the wallet examines/manages an offer (e.g. to compute which coins must be spent to cancel a pending trade). A maliciously crafted offer containing a coin spend whose puzzle both creates and asserts the same coin announcement can trigger the double-pop `KeyError`, crashing whatever wallet-side flow calls `get_cancellation_coins()` on that offer — a spend/offer-triggered processing halt in the victim wallet, matching the "spend-triggered transaction-processing halt" acceptance criterion.

### Likelihood Explanation
Crafting a coin spend that both creates a coin announcement and asserts that same announcement on itself is trivial with any custom puzzle (e.g. a `p2_conditions`-style delegated puzzle) and requires no signature validity for the crash to be reached, since the vulnerable code only inspects the CLVM conditions output by running the puzzle/solution (`run_with_cost`) — it does not require the coin to be spendable or the aggregated signature to validate. This makes the trigger reachable purely by handing a crafted offer file to a victim wallet.

### Recommendation
In the propagation loop of `get_cancellation_coins()`, exclude the coin itself in addition to `provider` when scanning for dependents, and/or de-duplicate `remove_these_keys` before iterating to pop from `dependencies`/`announcements`:
```
for coin, deps in dependencies.items():
    if set(deps) & set(removed_announcements) and coin not in (provider, removed_coin):
        remove_these_keys.append(coin)
...
for coin in dict.fromkeys(remove_these_keys):
    dependencies.pop(coin)
    removed_announcements.extend(announcements.pop(coin))
```
This mirrors the upstream Wireshark fix of explicitly prohibiting self-linking.

### Proof of Concept
Construct an `Offer`/`WalletSpendBundle` containing a coin spend `S` whose puzzle, when run with its solution, outputs both:
- `(60 M)` — CREATE_COIN_ANNOUNCEMENT with message `M`
- `(61 M)` — ASSERT_COIN_ANNOUNCEMENT referencing `S.name() + M` (i.e. asserting its own announcement)

and at least one other coin `T` in the same bundle whose conditions cause `detect_dependent_coin` to return `(S, T)` (e.g. `T` creates an announcement that `S` also asserts, or any other pairing that makes `S` the `removed_coin` and `T` the `provider`). Loading this bundle into an `Offer` (`Offer.from_bytes`) and calling `offer.get_cancellation_coins()` (as done inside `chia/wallet/trade_manager.py`) will raise `KeyError` on the second `dependencies.pop(S.name())` call in [6](#0-5) , because `S`'s own self-referencing announcement causes it to be appended twice to `remove_these_keys`.

def detect_dependent_coin(
    names: list[bytes32], deps: dict[bytes32, list[bytes32]], announcement_dict: dict[bytes32, list[bytes32]]
) -> tuple[bytes32, bytes32] | None:
    # First, we check for any dependencies on coins in the same bundle
    for name in names:
        for dependency in deps[name]:
            for coin, announces in announcement_dict.items():
                if dependency in announces and coin != name:
                    # We found one, now remove it and anything that depends on it (except the "provider")
                    return name, coin
    return None
```
