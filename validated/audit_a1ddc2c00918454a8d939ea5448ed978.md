### Title
Trampoline credential-helper trusts a caller-supplied `host`/token pair, allowing any local process spawned during a Git operation to exfiltrate the signed-in GitHub OAuth token - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
This is analogous to the FairSide `FSDVesting.updateVestedTokens()` bug: a privileged operation ("hand out the user's stored credential/token") is gated only by a caller-supplied identifier (`DESKTOP_TRAMPOLINE_TOKEN` + an attacker-suppliable credential `host`), not by verification that the request actually originates from, and is scoped to, the specific Git subprocess Desktop spawned for a specific remote. Just as `updateVestedTokens()` trusted a user-controlled `_user` parameter instead of checking `msg.sender`, the trampoline's `CREDENTIALHELPER get` command trusts the `host` field embedded in the request payload to decide which stored account credential to return, and any process that can read the `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` environment variables (inherited by every child process spawned during a Git network operation, e.g. Git LFS filters set via `GIT_CONFIG_PARAMETERS: 'credential.helper=desktop'`) can connect to the local TCP trampoline server and request credentials for an arbitrary `host`, not just the host actually being operated on.

### Finding Description
Desktop implements Git authentication via a local "trampoline" TCP server (`app/src/lib/trampoline/trampoline-server.ts`) bound to `127.0.0.1`, invoked by Git subprocesses through the `desktop-trampoline`/`git-credential-desktop` executables (`vendor/desktop-trampoline/src/desktop-trampoline.c`). When Desktop spawns Git it sets: [1](#0-0) 
which includes `DESKTOP_PORT`, `DESKTOP_TRAMPOLINE_TOKEN`, and configures `GIT_CONFIG_PARAMETERS` so that the credential helper is `credential.helper=desktop` — explicitly to make sure sub-processes invoked by filters (e.g. Git LFS) inherit and can use this configuration: [2](#0-1) 

The native trampoline client only forwards a fixed whitelist of environment variables (`DESKTOP_TRAMPOLINE_TOKEN`) plus caller-controlled command-line arguments and stdin to the server: [3](#0-2) [4](#0-3) 

On the Desktop side, the credential-helper handler resolves which account to hand back purely from the `host`/`protocol` fields embedded in the request (`getCredentialUrl(cred)`), matched against the store of signed-in accounts, with no check that this `host` corresponds to the actual remote/operation that the trampoline token was originally minted for: [5](#0-4) [6](#0-5) 

The `TrampolineCommandParser` accepts the `DESKTOP_TRAMPOLINE_TOKEN` supplied purely from the client-sent environment-variable payload with no further binding to the originating process/subprocess identity: [7](#0-6) 

Because the token and port are propagated via `GIT_CONFIG_PARAMETERS`/environment inheritance specifically so that "commands invoked by filters (i.e. Git LFS)" can use the credential helper, any subprocess spawned during a single Git network operation (LFS smudge/clean filters, `core.sshCommand`, `credential.helper` chains, or any other Git-invoked helper that inherits the environment) is handed the same trusted token and can independently connect to the trampoline TCP server and request the `get` credential-helper command for **any** `host` string it chooses (e.g. `github.com`), not only the host that the actual outer Git operation is authenticating against. The server has no per-request scoping tying the requested `host` back to `trampolineEnvironmentPath`/the remote of the operation that the token was minted for.

### Impact Explanation
This breaks the same invariant as the C4 finding: a privileged read of "the current account's credential" is granted based on attacker-influenced input (the `host` field of the credential request) instead of a verified binding between the caller and a specific, authorized operation. If an attacker can get any additional subprocess to run as part of a Desktop-initiated Git operation on a repository (e.g. Git LFS filter processes that a malicious repository declares via `.gitattributes`+`.lfsconfig`, or other filter/driver commands resolvable during clone/fetch/push), that subprocess inherits `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` and can request the signed-in GitHub account's OAuth token for `github.com` regardless of what host the outer operation was actually contacting — resulting in **credential/token exfiltration** to a process the attacker controls (which can then transmit it over the network attacker-controlled binaries can freely open).

### Likelihood Explanation
The environment variables are deliberately propagated to sub-invocations (the code comment explicitly states this is to let "commands invoked by filters (i.e. Git LFS)" use the credential helper), so the exposure surface already includes any filter/helper process a repository can cause Git to invoke during a clone/fetch/pull that Desktop performs. Whether a fully unprivileged, single-click PoC exists without any of the excluded assumptions (local access, prior malware, admin rights) depends on whether Git can be made to invoke a repo-controlled filter/helper binary purely from repository content (e.g., `.gitattributes` + `.lfsconfig` in a cloned repo) without additional local configuration by the victim — I was not able to fully verify this end-to-end (e.g., I could not load `trampoline-tokens.ts` to confirm the exact token validation/scoping logic, and the read_file calls needed to inspect `isValidTrampolineToken` and the remainder of `trampoline-server.ts`'s `processCommand` failed in this session). This is a real architectural weakness (missing binding between the requested `host` and the authorized operation) but the exact attacker-controlled trigger for spawning an untrusted subprocess purely via cloned repository content needs further verification.

### Recommendation
Bind each `DESKTOP_TRAMPOLINE_TOKEN` to the specific remote/host it was minted for (already tracked via `trampolineEnvironmentPath`), and reject `CREDENTIALHELPER get` requests whose `host` does not match the host associated with that token, rather than trusting the caller-supplied `host` field outright. Additionally, consider issuing a fresh, narrowly-scoped, single-use token per distinct outbound Git network request rather than one token shared for the lifetime of the whole Git invocation (including all of its sub-processes/filters).

### Proof of Concept
Not independently verified end-to-end in this session due to incomplete access to `trampoline-tokens.ts` and the remainder of `trampoline-server.ts`. Conceptually:
1. Desktop performs a Git network operation on a repository, minting a trampoline token and setting `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` in the Git process environment (`app/src/lib/trampoline/trampoline-environment.ts:123-146`).
2. That operation invokes a repository-influenced sub-process (e.g., a Git LFS filter) that inherits the same environment.
3. The sub-process connects directly to `127.0.0.1:$DESKTOP_PORT` and sends a `CREDENTIALHELPER` command with `DESKTOP_TRAMPOLINE_TOKEN` from its environment and a crafted `host=github.com` parameter.
4. `getGitHubCredential`/`findGitHubTrampolineAccount` (`app/src/lib/trampoline/trampoline-credential-helper.ts:50-57`, `app/src/lib/trampoline/find-account.ts:20-29`) matches purely on host/origin and returns the signed-in account's username/token, which the sub-process can exfiltrate.

Given the unverified scoping logic, I recommend a Devin session with terminal access to trace `trampoline-tokens.ts` and `trampoline-server.ts`'s `processCommand` to confirm whether the token is scoped to a specific host/operation, and to build a concrete reproduction.

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
