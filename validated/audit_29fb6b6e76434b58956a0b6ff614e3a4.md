### Title
Cached FROST preprocess seed is never invalidated, causing deterministic nonce reuse across signing calls - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
In `SigningProtocol::preprocess_internal`, a FROST preprocess is generated deterministically from a seed stored in `CachedPreprocesses`, keyed by `context`. The seed is written once and then reused on every subsequent call for the same context — it is never cleared or rotated after `sign` consumes it. Each call to `share_internal`/`complete` therefore re-derives the identical `AlgorithmSignMachine` (same nonces `d, e`), so a validator that produces signature shares for two different messages under the same context reuses its FROST nonce. Two Schnorr shares under the same nonce over different challenges allow algebraic recovery of the validator's private key share.

This is the same bug class as the reference finding: a mutating operation is applied twice while the second application reads a stale, pre-update value. Here, the "balance" is the consumed nonce seed — `sign` uses the value that was already spent by a prior `sign`, rather than a freshly updated one.

### Finding Description
`preprocess_internal` derives an encryption key from `b"Cached Preprocess Encryption Key" || context || key`, then checks `CachedPreprocesses::get(self.txn, &self.context)`; only if absent does it generate a fresh preprocess and store its seed [1](#0-0) . On every call — including after a signature share was already produced — the stored seed is decrypted and passed to `AlgorithmSignMachine::from_cache`, reconstructing byte-identical nonces [2](#0-1) . There is no `remove`/`take` on `CachedPreprocesses` anywhere; nothing invalidates the consumed seed.

`seeded_preprocess` shows why this is fatal: nonces and commitments are derived purely deterministically via `ChaCha20Rng::from_seed(*seed.0)` [3](#0-2) . The library's own documentation states a cached preprocess "MUST only be used once. Reuse will enable third-party recovery of your private key share" [4](#0-3)  and spec/FROST.md §Caching [5](#0-4) . The coordinator violates this internally rather than by integrator misuse.

Concretely, `share_internal` calls `preprocess_internal` fresh each time [6](#0-5) , and `complete` invokes `share_internal` again to rebuild the machine [7](#0-6) . The `context` for `DkgConfirmer` is `("DkgConfirmer", attempt)` — fixed for the entire attempt — while the signed `msg` varies with the supplied `key_pair` and the binding factor varies with the participant preprocess set [8](#0-7) . Two shares produced under the same `attempt` context with different `key_pair`s (or different preprocess sets changing `rho`) therefore use identical nonces over different challenge values, yielding `s1 - s2 = λ_i · share_i · (c1 - c2)`-style linear recovery of the secret share.

### Impact Explanation
Recovery of a validator's MuSig/FROST secret key share breaks the threshold assumption for the affected tributary set: an attacker collecting the share plus publicly known data can forge the validator's participation in `set_keys` confirmations (and, combined with t-1 cooperating/faulty shares, fully compromise the multisig). Severity: High — key share recovery is the explicit worst case the frost library documents for preprocess reuse.

### Likelihood Explanation
Any peer validator can induce a second `sign` under the same context by gossiping an alternative `key_pair`/preprocess set for the same attempt, since the tributary protocol accepts externally supplied preprocesses and `KeyPair`s. The victim need only call `share()`/`complete()` twice in the same attempt — a routine occurrence across retries or equivocating proposals. No privileged access is required; all inputs are public protocol messages. Likelihood: High-Medium, tempered only by needing the victim to sign twice within one attempt context.

### Recommendation
Consume the cached seed: after `CachedPreprocesses::get` succeeds and the machine is rebuilt, delete the DB entry (e.g., `CachedPreprocesses::remove(self.txn, &self.context)`) or store a monotonically incremented nonce-generation counter within the context so each `sign` uses a fresh seed. Alternatively, tie the context to the exact message/preprocess-set being signed so the same context can never sign twice.

### Proof of Concept
Within one DKG confirmation `attempt`:
1. Honest validator calls `DkgConfirmer::preprocess()` then `share(preprocesses_A, key_pair_A)` — produces share `s1` with nonce seed `X`.
2. Attacker (another validator) circulates `key_pair_B` (e.g., claiming a different DKG result) and the honest node's `share(preprocesses_B, key_pair_B)` is invoked — `preprocess_internal` returns the machine rebuilt from the same seed `X`, identical `d, e` nonces.
3. With `s1`, `s2`, the binding factors, and Lagrange coefficient `λ_i` (all public), solve `share_i = (s1 - s2) / (λ_i·(c1 - c2))` to recover the victim's secret share.

Supporting code: `crypto/frost/src/sign.rs` `AlgorithmSignMachine::sign` produces `share = d + (e·rho) + λ·secret_share·challenge`-style linear shares; identical `d,e` across two challenges is standard Schnorr nonce-reuse key recovery.

```rust
  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))
  }
```

```markdown
# Caching

modular-frost supports caching a preprocess. This is done by having all
preprocesses use a seeded RNG. Accordingly, the entire preprocess can be derived
from the RNG seed, making the cache just the seed.

Reusing preprocesses would enable a third-party to recover your private key
share. Accordingly, you MUST not reuse preprocesses. Third-party knowledge of
your preprocess would also enable their recovery of your private key share.
Accordingly, you MUST treat cached preprocesses with the same security as your
private key share.

Since a reused seed will lead to a reused preprocess, seeded RNGs are generally
frowned upon when doing multisignature operations. This isn't an issue as each
new preprocess obtains a fresh seed from the specified RNG. Assuming the
provided RNG isn't generating the same seed multiple times, the only way for
this seeded RNG to fail is if a preprocess is loaded multiple times, which was
already a failure point.
```
