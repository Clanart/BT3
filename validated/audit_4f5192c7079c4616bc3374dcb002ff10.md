### Title
Blame evaluation swaps accuser and accused, so honest reporters are faulted and malicious share senders are never blamed - (File: processor/src/key_gen.rs)

### Summary
The OpenSSH advisory (JLSEC-2026-65) concerns a helper executed as a different user while retaining the privileges/group memberships of the wrong identity — i.e., an action evaluated under a misattributed identity. Serai's PedPoP blame flow has a direct analog: `BlameMachine::blame`/`AdditionalBlameMachine::blame` takes `(sender, recipient)` where `sender` is the party who sent the disputed secret share and `recipient` is the accusing party, but the call site handling `VerifyBlame` passes `(accuser, accused)`, inverting both roles. The share's proof-of-possession is then verified against the accuser as `sender`, which can never match a message actually created by the accused, so `blame_internal` always returns the accuser as the faulty party.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs`, `BlameMachine::blame` is documented and implemented as `blame(sender, recipient, msg, proof)`, where `msg` is "a copy of the encrypted secret share from the accused sender to the accusing recipient" — i.e., `sender` = accused, `recipient` = accuser. `blame_internal` passes `sender` as `from` to `Decryption::decrypt_with_proof`, which verifies `msg.pop` against `pop_challenge(context, R, key, from, msg)`. The PoP challenge is bound to the sender participant index, so the signature only verifies when `sender` equals the actual author of the encrypted share. [1](#0-0) [2](#0-1) [3](#0-2) 

The in-repo test confirms the intended ordering: a share sent from `ONE` to `TWO` where `ONE` is malicious is checked via `machine.blame(ONE, TWO, msg, ...)` and must return `ONE` (the sender/accused). [4](#0-3) 

In `CoordinatorMessage::VerifyBlame` handling, the machine is invoked as `.blame(accuser, accused, substrate_share, substrate_blame)` (and identically for the network share), placing the accuser in the `sender` position and the accused in the `recipient` position. [5](#0-4) 

Consequences inside `blame_internal` under this ordering:
- `decrypt_with_proof(from = accuser, decryptor = accused, msg, proof)` verifies the PoP with the `sender` field set to `accuser`, but the message was created by `accused` — the Schnorr PoP fails → `DecryptionError::InvalidSignature` → `blame_internal` returns `sender`, which is the *accuser*. [6](#0-5) 
- Even if the PoP had been satisfied (e.g., a message genuinely authored by the accuser is replayed), the DLEq proof is checked against `enc_keys[&decryptor]` = the *accused's* encryption key rather than the accuser's, again inverting the blame outcome. [7](#0-6) 
- The handler then reports `Blame { participant: accuser }` whenever the (correctly swapped) result doesn't equal `accused` — which it essentially never can, since `accused` is evaluated as `recipient` and is only returned when the recipient is at fault for a false accusation, a branch unreachable here because the sender identity itself is wrong. [8](#0-7) 

### Impact Explanation
Every `VerifyBlame` evaluation attributes fault to the wrong party by construction: an honest validator who correctly detects and reports an invalid secret share is marked faulty (the codebase notes this implies being "fatally slashed"), while a participant who actually distributed invalid shares can never be blamed through this path. This is a privilege/identity misattribution: the blame helper is executed under the accuser's identity while the cryptographic evidence binds the accused. Faulty DKG participants escape accountability, and honest participants are penalized for performing the protocol's required reporting duty.

### Likelihood Explanation
Deterministic. Any `VerifyBlame` message reaches this code path with public inputs: the accusing validator supplies `share` (deserialized via `EncryptedMessage::read`) and `blame` (`EncryptionKeyProof::read`), both attacker/peer-controlled byte strings, and `accuser`/`accused` participant indexes. No cryptographic break is needed — the PoP `sender` binding guarantees `InvalidSignature` whenever the accused was the true author, which is precisely the case the mechanism exists for. The only precondition is that a blame event is raised during a key-generation session.

### Recommendation
Swap the arguments at the `VerifyBlame` call site to `.blame(accused, accuser, share, blame)` for both the substrate and network `AdditionalBlameMachine` evaluations. Additionally, harden the in-scope API to make this misordering impossible to express silently: rename the parameters (`accused`/`accuser`), have `blame_internal` verify the PoP `from` field and return `sender` only after confirming the message was authored by `sender` under the correct ordering, and/or validate `sender`/`recipient` against `params.all_participant_indexes()` and the registered `enc_keys` before evaluation. A regression test should exercise `AdditionalBlameMachine::new(...).blame(accused, accuser, ...)` through the coordinator's `VerifyBlame` path rather than only via the pedpop unit tests.

### Proof of Concept
1. Participants `1..=n` run PedPoP. Participant `A` (accused) sends participant `B` (accuser) a ciphertext whose `msg` decrypts to a non-canonical scalar or an invalid share (as `invalidate_share_value` does in tests). `B`'s `calculate_share` fails with `InvalidShare { participant: A, blame: Some(proof) }` and `B` issues `VerifyBlame { accuser: B, accused: A, share, blame }`.
2. The handler calls `AdditionalBlameMachine::new(ctx, n, msgs).blame(B, A, share, proof)` — `sender = B`, `recipient = A`.
3. `decrypt_with_proof(from = B, ...)`: `pop_challenge` is computed with `sender = B`, but the message's PoP was signed by `A` over `sender = A`. `msg.pop.verify(msg.key, challenge)` fails → `InvalidSignature` → `blame_internal` returns `B`.
4. Handler compares `substrate_blame == accused` (`B == A`, false) and `network_blame == accused` (false), then returns `Blame { participant: B }` — the honest accuser is recorded as the faulty party and `A`'s invalid share is never attributed.

By contrast, `blame(A, B, share, proof)` returns `A` correctly, matching `test_blame`'s expectations (`blame(ONE, TWO, msg)` returns `ONE`). [9](#0-8)

  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }

  /// Given an accusation of fault, determine the faulty party (either the sender, who sent an
  /// invalid secret share, or the receiver, who claimed a valid secret share was invalid). No
  /// matter which, prevent completion of the machine, forcing an abort of the protocol.
  ///
  /// The message should be a copy of the encrypted secret share from the accused sender to the
  /// accusing recipient. This message must have been authenticated as actually having come from
  /// the sender in question.
  ///
  /// In order to enable detecting multiple faults, an `AdditionalBlameMachine` is returned, which
  /// can be used to determine further blame. These machines will process the same blame statements
  /// multiple times, always identifying blame. It is the caller's job to ensure they're unique in
  /// order to prevent multiple instances of blame over a single incident.
  pub fn blame(
    self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> (AdditionalBlameMachine<C>, Participant) {
    let faulty = self.blame_internal(sender, recipient, msg, proof);
    (AdditionalBlameMachine(self), faulty)
  }

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}

  pub(crate) fn decrypt_with_proof<E: Encryptable>(
    &self,
    from: Participant,
    decryptor: Participant,
    mut msg: EncryptedMessage<C, E>,
    // There's no encryption key proof if the accusation is of an invalid signature
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Result<Zeroizing<E>, DecryptionError> {
    if !msg.pop.verify(
      msg.key,
      pop_challenge::<C>(self.context, msg.pop.R, msg.key, from, msg.msg.deref().as_ref()),
    ) {
      Err(DecryptionError::InvalidSignature)?;
    }

    if let Some(proof) = proof {
      // Verify this is the decryption key for this message
      proof
        .dleq
        .verify(
          &mut encryption_key_transcript(self.context),
          &[C::generator(), msg.key],
          &[self.enc_keys[&decryptor], *proof.key],
        )
        .map_err(|_| DecryptionError::InvalidProof)?;

      cipher::<C>(self.context, &proof.key).apply_keystream(msg.msg.as_mut().as_mut());
      Ok(msg.msg)
    } else {
      Err(DecryptionError::InvalidProof)
    }
  }
