### Title
ERC20↔CW20 / CW20↔ERC20 pointer contracts assume 1:1 transfer amounts, breaking on fee-on-transfer or otherwise-mutating underlying tokens - ([File: contracts/src/CW20ERC20Pointer.sol])

### Summary
The Sei pointer contracts that bridge an EVM ERC20 token to a CosmWasm CW20 token (and vice versa) assume the amount requested in `transfer`/`transferFrom` is exactly the amount that lands on the recipient's balance. Neither side verifies actual balance deltas before/after the underlying call, so any underlying ERC20 token with non-standard transfer semantics (fee-on-transfer, rebasing, or an upgradable/proxy implementation later modified to deduct a fee) will desynchronize the pointer's accounting from the real token balance.

### Finding Description
`CW20ERC20Pointer.sol` wraps a CW20 token as an ERC20-looking contract for EVM callers. Its `transfer` and `transferFrom` simply forward the requested `amount` to the CW20 `transfer`/`transfer_from` messages via the wasmd precompile and return `true` on success, without ever reading back the recipient's/sender's balance to confirm the delta matches `amount`: [1](#0-0) 

Symmetrically, `ERC20toCW20` pointer path (CW20 wrapping an EVM ERC20, e.g. `example/cosmwasm/cw20/src/contract.rs` `transfer`/`transfer_from`) builds an EVM delegatecall payload for the wrapped ERC20's `transfer`/`transferFrom` and reports success purely based on the EVM call succeeding, using the CW20 message's nominal `amount` for CW20-side attributes/state — again with no check that the actual ERC20 balance change equals `amount`: [2](#0-1) 

The generic native-token pointer, `NativeSeiTokensERC20.sol`, similarly performs `_update` by calling `BankPrecompile.send` and unconditionally emits `Transfer(from, to, value)` using the nominal `value`, regardless of what the bank keeper actually moved: [3](#0-2) 

All three pointer types are the sei-chain analog of the reported "vault lacks mechanism to handle upgradable tokens" bug class: a proxy/wrapper accounting layer that trusts the requested transfer amount rather than measuring the actual balance change. If the wrapped/pointed-to token is upgradable (a CW20 contract can be migrated via `MigrateMsg`, and an EVM ERC20 pointee could itself be a proxy contract upgraded to add a transfer fee, blacklist, or rebase logic), the pointer's ERC20 balance bookkeeping (which is otherwise consistent because `balanceOf`/`totalSupply` on `CW20ERC20Pointer` are computed by *live query* to the CW20, not cached state) would only be exploitable if the *query-based* balance and the *transfer event assumptions* diverge — e.g., a downstream integrator (DEX, lending market, bridge) that listens to the pointer's `Transfer` event or uses `transferFrom`'s boolean return to credit `amount` internally, while the actual on-chain balance moved by less (or more) due to a fee or hook introduced by a CW20 migration.

### Impact Explanation
Because `balanceOf`/`totalSupply` on `CW20ERC20Pointer.sol` are always freshly queried from the underlying CW20 contract rather than cached in local storage, the pointer's own state cannot become permanently inconsistent with the CW20's real balances — it is not a value-holding vault, so it does not directly custody funds subject to draining. The residual risk is limited to third-party integrators that trust the nominal `amount` in `Transfer`/`Approval` events or the boolean return value of `transfer`/`transferFrom`, and could be misled into crediting more value than was actually moved if a CW20 pointee is migrated (via the CW20 contract's own `migrate` capability) to introduce a transfer fee or hook after the pointer already exists. This does not meet the "concrete fund loss" bar directly within pointer-contract code itself, since the pointer never inflates supply or misreports its own `balanceOf`.

### Likelihood Explanation
Low-to-Medium. It requires (a) a CW20 contract whose admin can migrate it to add fee-on-transfer/hook logic after a pointer has been registered, and (b) a downstream consumer that trusts pointer-emitted ERC20 events/return values rather than re-querying balances. Sei's own `CW20ERC20Pointer` design mitigates most of the impact by always live-querying balances rather than tracking internal ledgers, which is different from a typical vault holding a cached balance — this significantly reduces exploitability versus the original Solver Vaults report, where the vault's internal accounting is the source of truth.

### Recommendation
For `CW20ERC20Pointer.sol`'s `transfer`/`transferFrom` (and the ERC20→CW20 pointer's execute handlers), query the counter-party balance before and after the underlying `_execute`/EVM delegatecall and emit the ERC20 `Transfer` event (and pack CW20 response attributes) using the actual observed delta rather than the requested `amount`. Additionally, consider disallowing pointer registration/re-registration for CW20 or ERC20 contracts that are migratable/upgradable by unauthorized parties, or documenting that pointer holders must treat pointee upgrades as a trust assumption.

### Proof of Concept
Not applicable as a standalone exploit against pointer-contract state (queries are live, so no stored balance divergence is created); the demonstrable weakness is confined to `transfer`'s/`transferFrom`'s emitted event and boolean return trusting the caller-supplied `amount`: [1](#0-0)

    function transfer(address to, uint256 amount) public override returns (bool) {
        require(to != address(0), "ERC20: transfer to the zero address");
        string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
        string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount)));
        string memory req = _curlyBrace(_formatPayload("transfer", _curlyBrace(_join(recipient, amt, ","))));
        _execute(bytes(req));
        return true;
    }

    function transferFrom(address from, address to, uint256 amount) public override returns (bool) {
        require(to != address(0), "ERC20: transfer to the zero address");
        string memory sender = _formatPayload("owner", _doubleQuotes(AddrPrecompile.getSeiAddr(from)));
        string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
        string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount)));
        string memory req = _curlyBrace(_formatPayload("transfer_from", _curlyBrace(_join(_join(sender, recipient, ","), amt, ","))));
        _execute(bytes(req));
        return true;
    }

fn transfer(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

pub fn transfer_from(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    owner: String,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&owner)?;
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_from_payload(owner.clone(), recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", owner)
        .add_attribute("to", recipient)
        .add_attribute("by", info.sender)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}
