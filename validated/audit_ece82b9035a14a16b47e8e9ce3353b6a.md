Line 120 of `IntrinsicIntents.sol` computes escrowed release via integer division exactly like the Alchemix `blockSlope` rounding-to-zero pattern, and — unlike the already-fixed "final solver gets remainder" test case for `fillOrder`-batched fills — this per-output-asset proportional release inside a single `_fillSameChain` call has no analogous final-fill top-up, so repeated small partial fills can round the escrow release to zero while consuming real order progress.

### Title
Escrow-release division truncates to zero on small partial fills, permanently locking input escrow - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary

### Finding Description
In `_fillSameChain`, when a fill does not complete the full requested output amount, the escrowed input released to the solver is computed as: [1](#0-0) 

`escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired`. This is structurally identical to the Alchemix `blockSlope = (MULTIPLIER * Δblock) / Δtime` extrapolation: an integer division whose numerator can be smaller than the denominator, producing `0` whenever `order.inputs[i].amount * fillAmount < totalRequired`. This is easy to trigger deliberately — a solver picks a tiny `fillAmount` (e.g. `fillAmount = 1` wei of the output token) against a `totalRequired` that is large relative to `order.inputs[i].amount`.

Crucially, `_partialFills[commitment][outputToken]` is updated unconditionally with `fillAmount` regardless of whether `escrowedAmount` rounded to zero: [2](#0-1) 

So a solver can call `_fillSameChain` (via `fillOrder`) with a sequence of dust-sized `solverAmount`s, each individually causing `escrowedAmount == 0`, advancing `amountFilled` toward `totalRequired` while the corresponding `_orders[commitment][token]` escrow balance is drained by `_withdraw(body, false, isFullyFilled)` for `0` — i.e., nothing is released per call, but progress toward the order being "filled" still accrues. Note the guard against rounding dust that exists for the *multi-solver-to-completion* path (tested in `IntentGatewayV2SameChainTest.sol`, "Finding #4" — final solver gets the full remaining balance) does **not** apply here: that fix only pays out the true remainder on the transaction that reaches `amountFilled == totalRequired`, exactly as coded at line 117-118. But any number of prior zero-escrow-release fills before that final one are never reconciled — each one paid the beneficiary the tiny `fillAmount` of output tokens while the corresponding escrow release rounded to zero, i.e. the user's escrowed input for that increment is never paid to the solver and instead stays trapped until (if ever) a fill happens to divide cleanly or the final full-completion branch executes.

### Impact Explanation
This causes escrowed user input tokens to be permanently under-released relative to the output tokens the solver actually delivered, on every fill where `order.inputs[i].amount * fillAmount < totalRequired`. Concretely: a solver who intentionally fragments a fill into many sub-wei-relative chunks receives no compensation for those increments (a loss to the solver, and a stuck-fund/logic-attack condition on the escrow accounting), while `_partialFills` state has already advanced — an unprivileged party (any solver) can force this mis-accounting purely through the public `fillOrder` entrypoint, with no relayer, prover, or admin involvement, matching the "logic attacks" / fund-loss impact class in the bounty.

### Likelihood Explanation
Likely whenever `order.inputs[i].amount < totalRequired` (a routine cross-token/cross-decimal order, e.g. a large-decimals output token against a small-amount input token) and a solver chooses (or is forced by minimum solver liquidity) to fill in small increments — no special conditions, race, or privileged role are required, only calling `fillOrder` with a small `outputs[i].amount`.

### Recommendation
Mirror the "final release gets the remainder" fix already applied to the full-completion branch to every partial increment: either (a) revert when `escrowedAmount` computed for a partial (non-final) fill would round to zero (`if (escrowedAmount == 0) revert DustFill();`), or (b) track escrow released cumulatively per `(commitment, inputToken)` the same way `_partialFills` tracks output progress, and compute each release as `cumulativeEscrowShouldBeReleased(amountFilled) - alreadyReleased`, so rounding error never compounds and no increment gets zero payout for a non-zero output delivery.

### Proof of Concept
1. Create an order where `order.inputs[0].amount = 100` (e.g., 100 units of a 6-decimal token) and `order.output.assets[0].amount = 1_000_000` (e.g., a large-decimals output requirement), with no output calldata.
2. Solver calls `fillOrder` with `outputs[0].amount = 5000` → `fillAmount = 5000`, `escrowedAmount = (100 * 5000) / 1_000_000 = 0` (rounds down). Beneficiary receives `5000` output tokens; solver receives `0` escrow, yet `_partialFills` advances to `5000/1_000_000`.
3. Repeat several more small fills, each computing `escrowedAmount == 0`, while `_partialFills` keeps advancing and the solver keeps paying real output tokens for zero escrow release.
4. This is directly analogous to the referenced Alchemix `testBlockSlope` PoC, which demonstrates the same numerator-smaller-than-denominator rounding-to-zero failure mode in an extrapolation/proportional-release formula.

Note: I could not find an existing unit test in this repo that specifically exercises this *intra-order small-increment* rounding path (only the "final solver gets full remainder" test for the batched multi-solver-to-completion scenario was found), so this analysis is based on direct reading of `IntrinsicIntents.sol`'s arithmetic rather than an observed failing test.
