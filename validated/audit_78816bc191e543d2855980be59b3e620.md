### Title
Auction bid signature verification crashes the node on malformed (short) signature bytes - ([File: kaiax/auction/bid.go])

### Summary
`getSigner()` in the Kaia auction module slices a caller-supplied signature byte array (`SearcherSig` / `AuctioneerSig`) at fixed offsets (`[0:32]`, `[32:64]`, index `64`) without first checking its length. An auction bidder can submit a `Bid` whose `SearcherSig` (or the relayed `AuctioneerSig`) field is shorter than 65 bytes, causing a Go slice-bounds-out-of-range panic during signature validation. This is the same bug class as the external report (CWE-20, improper input validation of externally supplied data leading to a crash), just manifesting in Kaia's auction/bid verification path instead of an HTTP trace-context header parser.

### Finding Description
`Bid.ValidateSearcherSig` and `Bid.ValidateAuctioneerSig` both call the helper `getSigner(sig, digest)`: [1](#0-0) 

`getSigner` clones the raw signature bytes and immediately indexes/slices them with hard-coded offsets that assume a 65-byte `[R || S || V]` signature, with no length check anywhere in the function: [2](#0-1) 

`BidData.SearcherSig` and `BidData.AuctioneerSig` are plain `[]byte` fields populated directly from external input — either RLP-decoded via `Bid.DecodeRLP` or JSON-unmarshaled (the struct has `json:"searcherSig"` / `json:"auctioneerSig"` tags) — with no length constraint enforced during decoding: [3](#0-2) 

If `sig` (i.e., `SearcherSig` or `AuctioneerSig`) has fewer than 65 bytes (e.g., 0, 1, or 32 bytes), the very first line `copiedSig[crypto.RecoveryIDOffset]` (offset 64) already panics with "index out of range", and even before that, `copiedSig[0:32]` / `copiedSig[32:64]` would panic for inputs under 64 bytes. There is no `len(sig) != 65` guard anywhere in this call chain, unlike other signature-handling code in the same codebase which consistently validates length first (e.g. `crypto.Ecrecover`, `crypto/signature_nocgo.go` `VerifySignature`, `blockchain/types/transaction_signing.go` `decodeSignature`, all of which check `len(sig) != crypto.SignatureLength` before slicing). [4](#0-3) [5](#0-4) 

### Impact Explanation
This is a denial-of-service vulnerability: any unprivileged auction bidder (or an entity relaying an auctioneer signature) who submits a `Bid` with a truncated/malformed `SearcherSig` or `AuctioneerSig` can trigger an unrecovered Go runtime panic during bid signature validation. Because `getSigner` has no `recover()` around it and no upstream length validation, this panic will propagate up through `ValidateSearcherSig`/`ValidateAuctioneerSig` and crash the goroutine (and potentially the node process, depending on whether the calling code path is wrapped in a panic-recovering RPC handler or not). This maps to the "gasless and auction modules" reachable category explicitly listed as in-scope, and represents concrete availability impact (CWE-20 improper input validation → crash), matching the impact class of the reported Swift W3C TraceContext advisory (CVSS AV:N/AC:L/PR:N/UI:N — network-reachable, no privileges, low complexity, availability-only impact).

### Likelihood Explanation
Likelihood is high: constructing a `Bid` with a short `SearcherSig`/`AuctioneerSig` requires no special privileges — it is just a malformed field in an externally-submitted bid (RLP or JSON encoded). There is no gas cost or economic barrier preventing an attacker from repeatedly submitting malformed bids to attempt to crash bid-validation goroutines.

### Recommendation
Add an explicit length check (`len(sig) != crypto.SignatureLength`, i.e. 65 bytes) at the very start of `getSigner()` in `kaiax/auction/bid.go`, returning `ErrInvalidSignature` (or a dedicated error) instead of proceeding to slice the byte array, consistent with the pattern already used in `crypto.Ecrecover`, `crypto/signature_nocgo.go`, and `blockchain/types/transaction_signing.go`.

### Proof of Concept
1. Construct a `Bid` (e.g., via RLP encoding of `BidData`) where `SearcherSig` is set to a byte slice shorter than 65 bytes (e.g., `[]byte{}` or a 10-byte slice).
2. Submit/decode this bid so that `Bid.ValidateSearcherSig(chainId, verifyingContract, version)` is invoked on it.
3. Inside `getSigner`, the line `copiedSig[crypto.RecoveryIDOffset]` (or the subsequent `copiedSig[0:32]`/`copiedSig[32:64]` slices) accesses an index beyond the slice's length, causing a runtime panic: `panic: runtime error: index out of range [64] with length <N>`.
4. Because there is no length validation or panic recovery in this call chain, this crashes the calling goroutine unrecovered.

Note: I was unable to trace the exact upstream RPC/mempool entry point that ingests externally submitted `Bid` objects (e.g., inside `kaiax/auction/impl/bid_pool.go` or `kaiax/auction/impl/api.go`) within the remaining investigation budget, so I could not confirm from source whether that outer layer wraps bid processing in a `recover()`. This should be verified before treating the crash as node-fatal versus goroutine-local; regardless, the missing length check in `getSigner` itself is a concrete, confirmed improper-input-validation defect.

func (b *Bid) ValidateSearcherSig(chainId *big.Int, verifyingContract common.Address, version string) error {
	if chainId == nil {
		return ErrNilChainId
	}

	if common.EmptyAddress(verifyingContract) {
		return ErrNilVerifyingContract
	}

	digest := b.GetHashTypedData(chainId, verifyingContract, version)

	recoveredSender, err := getSigner(b.SearcherSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover searcher sig: %v", err)
	}

	if recoveredSender != b.Sender {
		return fmt.Errorf("invalid searcher sig: expected %v, calculated %v", b.Sender.String(), recoveredSender.String())
	}

	return nil
}

func (b *Bid) ValidateAuctioneerSig(auctioneer common.Address) error {
	digest := b.GetEthSignedMessageHash()

	recoveredAuctioneer, err := getSigner(b.AuctioneerSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover auctioneer sig: %v", err)
	}

	if recoveredAuctioneer != auctioneer {
		return fmt.Errorf("invalid auctioneer sig: expected %v, calculated %v", auctioneer.String(), recoveredAuctioneer.String())
	}

	return nil
}

func getSigner(sig, digest []byte) (common.Address, error) {
	// Manually convert V from 27/28 to 0/1
	copiedSig := slices.Clone(sig)
	if copiedSig[crypto.RecoveryIDOffset] == 27 || copiedSig[crypto.RecoveryIDOffset] == 28 {
		copiedSig[crypto.RecoveryIDOffset] -= 27
	}

	v := copiedSig[crypto.RecoveryIDOffset]
	r := new(big.Int).SetBytes(copiedSig[0:32])
	s := new(big.Int).SetBytes(copiedSig[32:64])
	if !crypto.ValidateSignatureValues(v, r, s, true) {
		return common.Address{}, ErrInvalidSignature
	}

	pub, err := crypto.SigToPub(digest, copiedSig)
	if err != nil {
		return common.Address{}, err
	}
	return crypto.PubkeyToAddress(*pub), nil
}

func Ecrecover(hash, sig []byte) ([]byte, error) {
	pub, err := sigToPub(hash, sig)
	if err != nil {
		return nil, err
	}
	bytes := pub.SerializeUncompressed()
	return bytes, err
}

func decodeSignature(sig []byte) (r, s, v *big.Int) {
	if len(sig) != crypto.SignatureLength {
		panic(fmt.Sprintf("wrong size for signature: got %d, want %d", len(sig), crypto.SignatureLength))
	}
	r = new(big.Int).SetBytes(sig[:32])
	s = new(big.Int).SetBytes(sig[32:64])
	v = new(big.Int).SetBytes([]byte{sig[64] + 27})
	return r, s, v
