### Title
Unbounded recursive memo parsing in `PuzzleWithRestrictions.from_memo()` allows stack-consumption DoS via a crafted custody memo - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively parses a wallet-controlled `Program` (a CLVM memo blob attached to a custody puzzle hint) with no depth bound. Each nested `MofN` "further branching" member triggers another `PuzzleWithRestrictions.from_memo()` call on the corresponding child memo, so a deeply nested member list drives unbounded Python-stack recursion, mirroring the CVE-2018-16369 pattern (`XRef::fetch`/`AcroForm::scanField` unbounded recursive descent parsing of attacker-controlled structured input causing stack consumption).

### Finding Description
`PuzzleWithRestrictions.memo()` encodes an optional `MofN` puzzle hint as a `further_branching` flag plus a list of member memos [1](#0-0) . On the decode side, `from_memo()` reads that same structure and, when `further_branching` is true, calls itself once per member memo to reconstruct the `MofN` members: [2](#0-1) 

There is no recursion-depth limit, cycle check, or member-count/size cap in this path — each `MofNHint.member_memos` entry is itself parsed as another `PuzzleWithRestrictions` memo, and if that nested memo also encodes an `MofN` with `further_branching=True`, the call chain recurses again. `as_iter()` on the `Program` (a thin `SExp` wrapper, see `chia/types/blockchain_format/program.py`) simply walks the CLVM pair structure without protecting the caller from re-entrant recursive use. This is the same bug class as CVE-2018-16369: a recursive-descent parser walking attacker/user-supplied structured data with no depth guard, eventually exhausting the process (or thread) stack.

By contrast, other CLVM tree walkers in this codebase are deliberately iterative specifically to avoid this failure mode — e.g. `sha256_treehash()` in `chia/types/blockchain_format/tree_hash.py` states explicitly: "This implementation goes to great pains to be non-recursive so we don't have to worry about blowing out the python stack" [3](#0-2) . `PuzzleWithRestrictions.from_memo()` has no equivalent protection, and neither does `unknown_puzzles`/`fill_in_unknown_puzzles`, which mirror the same unbounded `MofN` recursion pattern once a `from_memo()`-derived object is in memory [4](#0-3) .

### Impact Explanation
A crafted, deeply nested `MofN` memo processed by `from_memo()` can exhaust the Python call stack, raising an uncaught `RecursionError` (or, in CPython, potentially crashing the interpreter via a native stack overflow depending on nesting depth and platform stack limits) in the process that parses the memo. Because memo parsing happens in wallet-side code handling custody puzzle hints — not inside consensus-critical mempool/CLVM cost accounting — the primary impact is a local/process-level denial of service against whatever component (wallet, tooling, or a service built on `PuzzleWithRestrictions`) decodes an attacker-supplied or counterparty-supplied memo, rather than a chain-wide consensus divergence. This caps the severity below the "unauthorized coin movement / consensus divergence" bar requested, but it is a legitimate spend/data-driven crash primitive against a wallet-side custody-parsing path reachable by any party that can hand a wallet a puzzle hint/memo (e.g., an offer or custody-setup counterparty).

### Likelihood Explanation
The recursion is triggered purely by the shape of a `Program` value supplied to `from_memo()` — no signature, spend acceptance, or special privilege is required. Any code path that calls `PuzzleWithRestrictions.from_memo()` on external data (e.g., reconstructing custody state from a hinted memo, as documented in the CLVM test notes: "`from_memo()` must reconstruct unknown members/restrictions, including recursive `MofN`") is exposed. The only observed non-test caller in-repo besides tests is `chia/pools/plotnft_drivers.py`, so real-world exposure depends on how broadly this custody-architecture memo format is exercised outside tests in the current codebase state.

### Recommendation
- Add an explicit recursion-depth (or total-node-count) limit to `PuzzleWithRestrictions.from_memo()`'s `MofN` branch, and reject memos exceeding it, mirroring the bound already applied to CLVM cost.
- Convert `from_memo()` to an iterative/worklist implementation (as already done for `sha256_treehash()`) so parsing depth cannot exhaust the Python or native stack.
- Add a fuzz/negative test with deeply nested `MofN` memos (analogous to `test_chialisp_deserialization.py`'s serialized-atom-overflow tests) to assert graceful rejection rather than a stack-overflow crash.

### Proof of Concept
1. Build an innermost `MemberHint`-based memo (`further_branching=False`).
2. Wrap it as an `MofNHint(m=1, member_memos=[inner_memo])` and encode via `MofNHint.to_program()`/`PuzzleWithRestrictions.memo()` with `further_branching=True`, producing memo₁.
3. Repeat step 2, feeding memo_{n-1} as the sole member memo of memo_n, for a large N (tens of thousands of nesting levels — trivial to construct as CLVM `Program.to(...)` nested lists).
4. Call `PuzzleWithRestrictions.from_memo(memo_N)`.
5. Observe the call stack depth grow linearly with N until Python raises `RecursionError` (or the process aborts on stack overflow), demonstrating the stack-consumption DoS.

    @classmethod
    def from_memo(cls, memo: Program) -> PuzzleWithRestrictions:
        if memo.atom is not None or memo.first() != Program.to(cls.spec_namespace):
            raise ValueError("Attempting to parse a memo that does not belong to this spec")
        nonce = memo.at("rf")
        restriction_hints_prog = memo.at("rrf")
        further_branching_prog = memo.at("rrrf")
        puzzle_hint_prog = memo.at("rrrrf")
        additional_memos = memo.at("rrrrrf") if memo.at("rrrrr").atom is None else None
        restriction_hints = [RestrictionHint.from_program(hint) for hint in restriction_hints_prog.as_iter()]
        further_branching = further_branching_prog != Program.to(None)
        if further_branching:
            m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
            puzzle: MIPSComponent = MofN(
                m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
            )
        else:
            puzzle_hint = MemberHint.from_program(puzzle_hint_prog)
            puzzle = UnknownMember(puzzle_hint)

        return PuzzleWithRestrictions(
            nonce=nonce.as_int(),
            restrictions=[UnknownRestriction(hint) for hint in restriction_hints],
            puzzle=puzzle,
            additional_memos=additional_memos,
        )
