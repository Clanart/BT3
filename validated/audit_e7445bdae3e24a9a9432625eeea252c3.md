### Title
Copilot conflict-resolution "Continue" flow can silently commit unresolved/malformed conflict markers because the safety check only fires for files git still reports as *fully* conflicted - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
The broken invariant mirrors the Predy bug: a safety check ("don't let the loss/bad state through") is only evaluated when a state variable is in one specific terminal condition (there, `!hasPosition`; here, git status flags the file as still "Conflicted"). Once that terminal condition is no longer true — because the file has been staged/written, not because it was actually verified to be conflict-free — the guard is skipped entirely, even though the underlying content can still be broken.

### Finding Description
`reassembleResolvedFile` explicitly documents and implements a fallback: any `<<<<<<<` block that is not followed by both a `=======` separator and a closing `>>>>>>>` is treated as "regular content" and copied through untouched, "to avoid data loss from malformed or stray markers": [1](#0-0) [2](#0-1) 

That means the "resolved" content written to disk by `_applyCopilotConflictResolutions` can still contain leftover marker-like text whenever the file's conflict layout doesn't match the parser's expectations (e.g. an unusual merge/rebase produced by a crafted/attacker-controlled remote history, nested markers, or a conflict block split by other tooling). `validateResolutionPaths` only checks that hunk **counts** match the app's own hunk-extraction of the file — it never re-parses the *final* reassembled content for leftover marker text: [3](#0-2) 

After Copilot resolutions are written and `git add`'ed, the file is staged and Git no longer reports it as a merge-conflict entry (`Conflicted` status, stage 1/2/3), because `stageFiles`/`git add` clears the unmerged index state: [4](#0-3) 

The "Continue" button in the Copilot conflicts dialog is only disabled by `hasUnresolvedSkippedFiles()`, which iterates the *skipped-by-Copilot* file list — files Copilot explicitly declined to resolve. It never re-checks the set of files Copilot *did* resolve for genuine marker-free content; it trusts that once a file leaves `Conflicted` status (or has zero conflict markers) it is safe: [5](#0-4) [6](#0-5) [7](#0-6) 

Separately, `CommitConflictsWarning` — the dialog meant to stop the user from committing conflicted content — only fires when git status still marks the file `Conflicted` (`isConflictedFile`); once `git add` has staged the (possibly still-broken) reassembled content, that guard cannot trigger either: [8](#0-7) 

So exactly like the Predy bug — where the insolvency check only ran on the fully-closed branch (`!hasPosition`) and could be bypassed by leaving a residual position open — Desktop's marker-integrity check only runs on the "still fully conflicted" branch (raw git conflict status) and is bypassed the moment the file is staged, regardless of whether the actual bytes on disk are truly clean.

### Impact Explanation
This corrupts what the user commits and pushes: leftover `<<<<<<<`/`=======`/`>>>>>>>` text (or genuinely incorrect merged content from a malformed marker block) can be silently baked into a real commit and pushed to a remote, without any warning dialog, because none of the gating logic (`hasUnresolvedSkippedFiles`, `CommitConflictsWarning`, `hasConflictedFiles`) re-inspects post-write content — they all key off git's conflict-state bookkeeping, which is already cleared by the time the write happens. This matches the "Valid Impact" criterion of "silent corruption of what the user commits or pushes," triggered purely by conflicting content coming from a cloned/fetched repository (an attacker-influenced branch/history) that the user is merging/rebasing/cherry-picking.

### Likelihood Explanation
Medium: it requires the repository under merge/rebase/cherry-pick to contain a conflict whose marker layout is atypical enough to defeat the app's hunk parser (unclosed/duplicated marker lines are explicitly anticipated by the code's own comments as a real, non-hypothetical case), and it requires the user to accept Copilot's conflict-resolution flow (a first-class, one-click UI path) rather than manual resolution. No admin rights, local access, or social engineering beyond a normal merge/rebase against attacker-influenced history is needed.

### Recommendation
After `_applyCopilotConflictResolutions` writes and stages files, re-run `getFilesWithConflictMarkers` (already used elsewhere, e.g. `app/src/lib/git/diff-check.ts`) against the *final* staged/working content and treat any file that still reports markers as unresolved — feeding it back into the same gating path used for skipped files (`hasUnresolvedSkippedFiles`) instead of only trusting the pre-write git status snapshot. The "Continue" button and `CommitConflictsWarning` should both key off this fresh, content-based check rather than the git conflict-state flag that gets cleared by the write/stage step itself.

### Proof of Concept
1. Set up a merge/rebase where the incoming (fetched/cloned) branch introduces a conflict block with a stray/duplicated `<<<<<<<` marker not properly closed by a matching `=======`/`>>>>>>>` pair for one hunk (this is directly acknowledged as a supported/expected case by `reassembleResolvedFile`'s "malformed marker" branch).
2. Trigger Copilot conflict resolution; the app's hunk extraction won't recognize the malformed block as a conflict hunk, so no resolution is requested/applied for that block; `reassembleResolvedFile` copies it through verbatim per its documented fallback (`app/src/lib/copilot-conflict-resolution.ts:574-579`).
3. `validateResolutionPaths` passes because hunk counts for the file's *recognized* hunks still match; the malformed block was never counted as a hunk in the first place.
4. `_applyCopilotConflictResolutions` writes the reassembled content (still containing the stray marker) to disk and runs `git add`, clearing the file's conflicted index state (`app/src/lib/stores/app-store.ts:7258-7268`).
5. In `CopilotConflictsDialog`, `hasUnresolvedSkippedFiles()` returns `false` (the file was never in the skipped list), so "Continue" is enabled; `CommitConflictsWarning` never triggers because the file no longer reports as `Conflicted`.
6. The user completes the merge commit; the resulting commit silently contains the stray conflict-marker text/incorrect content, with no warning shown at any point.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

  private isSkippedFileResolved(path: string): boolean {
    if (this.getSkippedFileChoice(path) !== undefined) {
      return true
    }
    const file = this.props.workingDirectory.files.find(f => f.path === path)
    // Gone from the working directory, or no longer reported as conflicted,
    // means the file was resolved/staged externally - there is nothing left to
    // gate Continue on, so treat it as resolved.
    if (file === undefined || !isConflictedFile(file.status)) {
      return true
    }
    // Still conflicted: resolved only once the markers are removed in an editor.
    return this.isFileResolvedExternally(file)
  }
