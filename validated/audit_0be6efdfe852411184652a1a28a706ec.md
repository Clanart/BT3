### Title
Native balance handler double-counts bank events after nested precompile call reverts, inflating EVM-visible balances - (File: `precompiles/common/balance_handler.go`)

### Summary
The `BalanceHandler` used by EVM precompiles to reconcile `x/bank`/`x/precisebank` events into `StateDB` balances relies on a captured event-count index (`prevEventsLen`) into `ctx.EventManager().Events()`. When a nested/recursive precompile call is reverted via `StateDB.RevertToSnapshot`, the event manager on the context is entirely replaced with a fresh one seeded from the snapshot's captured events, invalidating the indices previously captured by outer, still-active `BalanceHandler` instances. This is structurally the same bug class as the Challenger `endBlockHandler` issue: a slice/queue of accumulated items is silently reset/overwritten underneath a consumer that is still relying on a previously computed offset into it, causing state (there: discrepancy events dropped; here: bank events double-counted) to be processed incorrectly.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records the current length of the context's event log before a precompile method executes bank operations, and `AfterBalanceChange` later slices `events[bh.prevEventsLen:]` to apply only the newly-emitted `CoinSpent`/`CoinReceived`/`EventTypeFractionalBalanceChange` events to `StateDB.AddBalance`/`SubBalance`: [1](#0-0) [2](#0-1) 

Separately, `StateDB.Snapshot()` stores the full `sdk.Events` slice present at snapshot time, and `RevertToSnapshot` discards the current context's `EventManager` entirely, replacing it with a brand-new one re-seeded only with the events captured at snapshot time: [3](#0-2) 

This mechanism is also invoked implicitly through `precompileCallChange.Revert`, which rolls back the multistore/events to a snapshot taken before a precompile call: [4](#0-3) [5](#0-4) 

In a recursive precompile call scenario (e.g., an ICS20 transfer that triggers a distribution precompile call, which itself reverts and is retried, matching the scenario explicitly named in the codebase's own regression test), an outer `BalanceHandler.BeforeBalanceChange` captures `prevEventsLen` against the *original* event manager. A nested precompile call emits bank events, then reverts—swapping in a new `EventManager` pre-populated with the *pre-call* snapshot events. Because the event manager object itself is replaced (not just truncated), the outer handler's previously recorded `prevEventsLen` offset no longer corresponds to a consistent, monotonically-growing event log: events that were already accounted for by an inner (successful) `AfterBalanceChange` call can reappear in the new event manager's `Events()` slice at or before the outer's recorded offset, and be re-applied by the outer handler's `AfterBalanceChange` scan. This is confirmed by the project's own test explicitly documenting this exact defect: [6](#0-5) 

### Impact Explanation
Because `BalanceHandler.AfterBalanceChange` directly drives `StateDB.AddBalance`/`SubBalance` for the native EVM denom (and precisebank fractional deltas), double-processing of bank events causes the EVM-visible balance in `StateDB` to be credited/debited more than the underlying `x/bank`/`x/precisebank` ledger actually moved. This breaks the 1:1 accounting invariant between native coin balances and EVM balances that the `x/precisebank`/`x/vm` integration is designed to preserve, allowing an account's EVM balance to be inflated beyond what its bank balance backs — i.e., unauthorized duplication/creation of spendable value, matching the "Critical unauthorized minting/duplication/accounting corruption" impact class.

### Likelihood Explanation
The trigger path is reachable by any unprivileged user constructing a transaction that performs recursive/nested precompile calls where an inner call to a bank-affecting precompile (staking, distribution, ICS20, bank) fails and is reverted while an outer precompile call is still open — a pattern the maintainers themselves built a dedicated regression test for (`ics20_recursive_precompile_calls_test.go`), indicating it is a known, reachable execution path rather than a purely theoretical one.

### Recommendation
Do not rely on a raw event-count offset (`prevEventsLen`) that can be invalidated by an underlying `EventManager` replacement during `RevertToSnapshot`. Instead, tie `BalanceHandler` event tracking to the same snapshot/revision identifiers used by `StateDB` (e.g., record and diff against a stable, monotonically consistent event sequence, or re-derive the outer handler's baseline after any nested `RevertToSnapshot`/`AddPrecompileFn` call completes), ensuring events already applied by a nested `AfterBalanceChange` are never replayed by an enclosing one.

### Proof of Concept
Not independently reproduced beyond the codebase's own test; the existing test `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go` (whose suite comment explicitly states it targets "the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated") should be examined/run to confirm current pass/fail status and whether the duplication is currently mitigated or still exploitable; I was unable to execute the test or read its full body within the available tool budget, so confirmation of current exploitability (vs. an already-fixed regression test) is unverified.

// Snapshot returns an identifier for the current revision of the state.
func (s *StateDB) Snapshot() int {
	id := s.nextRevisionID
	s.nextRevisionID++
	s.validRevisions = append(s.validRevisions, revision{id, s.journal.length(), s.ctx.EventManager().Events()})
	return id
}

// RevertToSnapshot reverts all state changes made since the given revision.
func (s *StateDB) RevertToSnapshot(revid int) {
	// Find the snapshot in the stack of valid snapshots.
	idx := sort.Search(len(s.validRevisions), func(i int) bool {
		return s.validRevisions[i].id >= revid
	})
	if idx == len(s.validRevisions) || s.validRevisions[idx].id != revid {
		panic(fmt.Errorf("revision id %v cannot be reverted", revid))
	}
	snapshot := s.validRevisions[idx].journalIndex

	// revert back to snapshotted events
	eventManager := sdk.NewEventManager()
	eventManager.EmitEvents(s.validRevisions[idx].events)
	s.ctx = s.ctx.WithEventManager(eventManager)

	// Replay the journal to undo changes and remove invalidated snapshots
	s.journal.Revert(s, snapshot)
	s.validRevisions = s.validRevisions[:idx]
}
