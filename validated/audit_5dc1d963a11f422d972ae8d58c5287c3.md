### Title
Hookify PreToolUse/Stop hooks fail open on any internal error, silently disabling all user-configured security rules - (File: plugins/hookify/hooks/pretooluse.py)

### Summary
The Sherlock report describes a fail-open trust-boundary bug: when a market's principal token is uninitialized (`markets[u][m][p] == address(0)`), the `unpaused` gate defaults to permissive rather than denying, letting an attacker mint unlimited tokens through a code path that was supposed to be gated. The structural analog in this repository is the `hookify` plugin's `PreToolUse` (and `Stop`) hook executor: whenever the hook's rule-loading or rule-evaluation logic throws *any* exception — including import failures, malformed `.claude/hookify.*.local.md` config, or unexpected/edge-case `tool_input` shapes reaching `RuleEngine.evaluate_rules` — the script swallows the exception and unconditionally exits `0` with no denial, i.e., the tool call proceeds exactly as if no rule had matched at all.

### Finding Description
`plugins/hookify/hooks/pretooluse.py` is registered as a `PreToolUse` hook that is supposed to approve/deny tool calls (Bash, Edit, Write, MultiEdit) based on user-authored rules loaded from `.claude/hookify.*.local.md`: [1](#0-0) 

The control flow is:
1. Read the tool call JSON from stdin.
2. Call `load_rules(event=...)` (from `hookify/core/config_loader.py`) to parse the user's rule files.
3. Call `RuleEngine().evaluate_rules(rules, input_data)` to decide allow/deny/ask for this specific tool call.
4. Print whatever JSON decision came out.

Critically, both the import step and the `main()` body are wrapped in blanket `try/except Exception` blocks whose `except` and `finally` clauses always print a benign `systemMessage` and call `sys.exit(0)`: [2](#0-1) 

This is the same shape as the Illuminate bug: a security gate (`unpaused`/RuleEngine deny decision) is only enforced when a particular piece of state is *fully and correctly initialized* (`markets[u][m][p]` populated / rule file parses and evaluates without error). When that state is missing, malformed, or triggers an unhandled code path in `config_loader.load_rules` or `RuleEngine.evaluate_rules`, the code does not fail closed — it silently falls back to the default "no decision" (permissive) state, and the operation is allowed to proceed. The companion `Stop` hook (`plugins/hookify/hooks/stop.py`) has the identical pattern: [3](#0-2) 

The `finally: sys.exit(0)` / `# ALWAYS exit 0 - never block operations due to hook errors` comment shows this is a deliberate design choice prioritizing availability over safety, but it means **any input that trips an exception in the user's own rule engine effectively disables that rule for that call**. Since `evaluate_rules` receives attacker/model-influenced `tool_input` fields (e.g., `file_path`, Bash `command` string) directly from the tool call being evaluated, a sufficiently malformed or edge-case `tool_input` (unusual encoding, missing expected keys the rule engine assumes exist, deeply nested/oversized values, etc.) that the `RuleEngine` doesn't defensively handle will raise inside `evaluate_rules`, be caught by the blanket handler, and result in silent allow — with only a cosmetic `systemMessage` and no indication that the security rule was actually skipped.

### Impact Explanation
Users who install `hookify` specifically to enforce deny rules (e.g., "never write to `.env`", "never run `rm -rf`", "deny writes outside `src/`") are relying on this hook as their last line of defense against a misbehaving or prompt-injected Claude session attempting a dangerous tool call. Because the hook fails open rather than closed, an attacker who can influence tool-call arguments (via prompt injection in fetched web content, an untrusted file the agent reads, or a crafted repository) can craft a `tool_input` that crashes rule evaluation and bypasses every configured deny rule for that call, resulting in unauthorized filesystem writes/deletes or unrestricted Bash execution that the user believed was blocked. This is a genuine unprivileged-attacker → privileged-action trust-boundary bypass in the tool-authorization layer, matching the "uninitialized/error state defaults to permissive" bug class from the Illuminate report.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a user to have configured hookify deny rules they trust as a security boundary, and (b) an attacker-controlled or malformed `tool_input`/rule-file condition that trips an exception inside `config_loader.load_rules` or `RuleEngine.evaluate_rules` (neither of which I was able to fully inspect before running out of iterations — I confirmed their existence and call sites at `plugins/hookify/core/rule_engine.py` and `plugins/hookify/core/config_loader.py` via `grep_search`, but did not get to read their internals to enumerate concrete crash-inducing inputs). This is a design-level fail-open pattern rather than a proven single-line exploit; whether a realistic malformed input reliably reaches an unhandled exception in `RuleEngine.evaluate_rules` is unverified.

### Recommendation
Change the fail-safe direction: on any exception during rule loading or evaluation in `pretooluse.py`/`stop.py`, emit an explicit `deny`/`ask` decision (or exit code `2`) rather than silently allowing the operation, and surface the failure prominently to the user (not just a low-visibility `systemMessage`). At minimum, distinguish "no rules configured" (safe to allow) from "rules configured but evaluation errored" (should fail closed).

```python
try:
    from hookify.core.config_loader import load_rules
    from hookify.core.rule_engine import RuleEngine
except ImportError as e:
    # If imports fail, allow operation and log error
    error_msg = {"systemMessage": f"Hookify import error: {e}"}
    print(json.dumps(error_msg), file=sys.stdout)
    sys.exit(0)


def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```
