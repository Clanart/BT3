### Title
Fee-on-transfer reward tokens break reward accounting in `BaseRewardPool`/`BaseRewardPoolV2` via permissionless `donateRewards` - ([File: rewards/BaseRewardPool.sol])

### Summary
`donateRewards` in `BaseRewardPool.sol` and `queueNewRewards`'s shared internal `_provisionReward` credit reward accounting using the caller-supplied `_amountReward` value instead of the actual balance increase received by the contract, exactly mirroring the reported fee-on-transfer accounting bug class.

### Finding Description
`donateRewards` is a permissionless, unprivileged-wallet-reachable function that only requires the token to already be a registered `isRewardToken`: [1](#0-0) 

It forwards directly into `_provisionReward`, which performs `safeTransferFrom(msg.sender, address(this), _amountReward)` and then uses that same `_amountReward` — not the actual balance delta — to update `historicalRewards` and `rewardPerTokenStored`: [2](#0-1) 

The identical pattern exists in `BaseRewardPoolV2.sol`'s `_provisionReward`, called from its `queueNewRewards`: [3](#0-2) 

If a registered `_rewardToken` has any fee-on-transfer/deflationary mechanic, `rewardPerTokenStored` is incremented as though the full `_amountReward` was received, while the contract's actual token balance only increases by `_amountReward` minus the fee. Because `rewardPerTokenStored` directly determines `earned()`/`getReward()` payouts to stakers, the pool's total claimable reward liability now exceeds its real token balance.

### Impact Explanation
Since `getReward()` pays out based on `rewardPerTokenStored` (which is inflated relative to actual holdings), later claimants will be unable to withdraw their full earned rewards once the pool's real balance of that reward token is exhausted — some stakers permanently lose access to their allotted share of rewards. This constitutes protocol insolvency / permanent freezing of unclaimed yield for the affected reward token, consistent with the accepted impact categories.

### Likelihood Explanation
The precondition is that a manager has, at some point through normal protocol operation (`queueNewRewards`), registered a reward token that is fee-on-transfer — this is a routine reward-token-listing action, not a malicious admin action, since the manager's normal intent is simply to add a bonus reward token, not to exploit accounting. Once such a token is registered, ANY unprivileged wallet can call the permissionless `donateRewards` (or the manager can call `queueNewRewards` again) and trigger the miscalculation without any special privileges. The likelihood therefore depends on whether the deployed reward-token set ever includes a fee-on-transfer/rebasing token, which is plausible given the multi-token bonus reward design of `BaseRewardPool`.

### Recommendation
In `_provisionReward` (both `BaseRewardPool.sol` and `BaseRewardPoolV2.sol`), measure the actual amount received by comparing `IERC20(_rewardToken).balanceOf(address(this))` before and after the `safeTransferFrom` call, and use that delta — instead of the caller-supplied `_amountReward` — when updating `historicalRewards` and `rewardPerTokenStored`.

### Proof of Concept
1. Manager calls `queueNewRewards(amount, feeToken)` to register `feeToken` (a fee-on-transfer ERC20) as a reward token for a pool — this is normal reward-listing behavior, not an attack.
2. Any user (or the manager again) calls `donateRewards(1000e18, feeToken)`. [1](#0-0) 
3. `_provisionReward` transfers `feeToken` via `safeTransferFrom`, but the contract only actually receives `1000e18 - fee` due to the token's transfer fee.
4. `rewardPerTokenStored` is nonetheless incremented as if the full `1000e18` were received: [4](#0-3) 
5. As stakers accumulate `earned()` claims based on the inflated `rewardPerTokenStored`, the sum of all claimable `feeToken` rewards exceeds the pool's real `feeToken` balance.
6. Later stakers calling `getReward()` for `feeToken` find the transfer reverts or partially fails once the real balance is depleted, permanently losing access to their earned share. [5](#0-4)

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
