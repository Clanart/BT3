### Title
Shared-token escrow drained by the first completed leg of a multi-leg same-chain order, starving later legs of their promised release - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` computes the escrow amount to release for a completed output leg by reading the **entire** `_orders[commitment][token]` balance rather than a value scoped to that specific leg. Because `_orders` is keyed only by `(commitment, token address)` and aggregates escrow across *all* input legs that use the same token, an order with two or more legs sharing an input token lets whichever leg completes first sweep the combined escrow meant for all legs, leaving nothing for the legs that complete afterward. This is the same broken invariant as the external report: a "full balance instead of the correctly scoped amount" fallback that moves more value than the specific action warrants.

### Finding Description
`_orders` is documented and implemented as a per-token (not per-leg) balance: [1](#0-0) 

In `_fillSameChain`, when a given output leg `i` reaches its full required amount, the escrow released for that leg is read directly from this shared per-token bucket instead of any leg-scoped remainder: [2](#0-1) 

If `order.inputs` contains two (or more) legs that use the *same* input token address (a legitimate configuration — e.g. paying 500 USDC toward an ETH output leg and 500 USDC toward a DAI output leg in the same order), `_orders[commitment][USDC]` holds `1000` — the sum for both legs. When leg 0 (ETH) is completed by a solver, `amountFilled == totalRequired` for leg 0 triggers:
```
escrowedAmount = _orders[commitment][USDC]  // reads 1000, not the 500 owed to leg 0
```
`_withdraw` then decrements the shared bucket to `0` and transfers the full `1000` to the leg-0 filler: [3](#0-2) 

Because leg 1 (DAI) is still unfilled, `isFullyFilled` is `false`, so the order is **not** finalized — `_filled[commitment]` is deleted and a `PartialFill` is emitted, leaving the order open for a subsequent solver to fill leg 1: [4](#0-3) 

When a solver later completes leg 1, the same full-balance branch fires again, but `_orders[commitment][USDC]` is now `0` (already drained by leg 0's filler). The corresponding `escrowedInputs` entry carries `amount = 0`, and `_withdraw` silently `continue`s on zero amounts rather than reverting: [5](#0-4) 

The leg-1 solver delivers real output tokens to the beneficiary but receives zero input-token compensation, while the leg-0 solver walked away with the entire combined escrow instead of only their leg's share.

### Impact Explanation
This is a direct "wrong amount / wrong beneficiary" fund-movement bug in a production, publicly reachable contract path (`fillOrder` → `_fillSameChain`). An attacker can:
- Place a multi-leg order using the same input token across legs, then act as the solver for the cheapest/first leg to capture the entire escrow meant for all legs, permanently shorting whoever fills the remaining leg(s).
- More broadly, any legitimate multi-leg order sharing an input token is at risk of an early filler unintentionally or intentionally draining escrow owed to other legs, causing loss of funds for later fillers and breaking the escrow accounting invariant that the sum of released amounts should equal the sum promised per leg.

This matches the required impact class: stealing/loss of funds and logic attacks causing funds to move to the wrong beneficiary/amount, reachable by an unprivileged solver with no relayer, prover, or governance dependency.

### Likelihood Explanation
Likelihood is moderate: it requires an order with two or more `inputs[]` entries sharing the same token address feeding different `output.assets[]` legs — a configuration the data model explicitly allows (arrays are independently indexed and not required to use distinct tokens). Any user (including the attacker themselves, self-dealing) can construct such an order via `placeOrder`, and any solver — including the attacker — can trigger the drain via a normal `fillOrder` call on the first leg.

### Recommendation
Track escrow per (commitment, input-array-index) or otherwise scope the "full balance on leg completion" branch to the specific leg's remaining balance rather than reading the aggregate `_orders[commitment][token]` bucket. Concretely, compute the leg's owed amount as `min(order.inputs[i].amount - alreadyReleasedForLeg[i], remainingLegBalance)`, and only fall back to sweeping the full per-token bucket when no other pending legs reference that same token.

### Proof of Concept
1. User places a same-chain order with `inputs = [{token: USDC, amount: 500}, {token: USDC, amount: 500}]` and `output.assets = [{token: ETH, amount: 1e18}, {token: DAI, amount: 1000e18}]` (two legs sharing USDC as the input token). `_orders[commitment][USDC] = 1000`.
2. Solver A calls `fillOrder` providing exactly `1e18` ETH for leg 0 only (`solverOutputs[0].amount = 1e18`, and either omits/zeroes leg 1 or the call is structured to fill leg 0 fully in isolation).
3. In the loop, `i = 0`: `amountFilled == totalRequired` (leg 0 done) → `escrowedAmount = _orders[commitment][USDC] = 1000` (the full combined bucket), transferred entirely to Solver A via `_withdraw`; `_orders[commitment][USDC]` becomes `0`.
4. Since leg 1 (DAI) is unfilled, `isFullyFilled = false`; `_filled[commitment]` is deleted, order stays open (`PartialFill` emitted).
5. Solver B later calls `fillOrder` providing `1000e18` DAI to complete leg 1. `escrowedAmount = _orders[commitment][USDC] = 0`. `_withdraw` sees `amount == 0` and skips the transfer — Solver B delivers 1000 DAI to the beneficiary and receives 0 USDC, while Solver A already collected the full 1000 USDC meant to be split 500/500 across both legs.
