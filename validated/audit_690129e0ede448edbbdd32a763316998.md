### Title
Shared `BalanceHandler` instance in nested/recursive precompile calls causes `prevEventsLen` clobbering, leading to balance desync between `x/bank` and EVM `StateDB` — ([File: precompiles/common/balance_handler.go])

### Summary
The reported Perennial bug is a "wrong previous-value tracking in a loop" defect: `MultiInvoker._latest()` reused a stale/incorrectly-scoped `previousMagnitude` across loop iterations, corrupting a derived accounting value (`closableAmount`). The Cosmos EVM analog is structurally identical but in the precompile balance-synchronization path: `BalanceHandler.prevEventsLen` is a single mutable "previous" checkpoint used to slice the event log window that should be re-applied to `StateDB`. When the *same* `BalanceHandler` instance is reused across nested/recursive precompile invocations within one EVM call frame, `BeforeBalanceChange` overwrites `prevEventsLen` for the inner call, and the outer call's `AfterBalanceChange` then processes the wrong (too-short) window of `x/bank` events — exactly mirroring how `previousMagnitude` was clobbered mid-loop in the audited report.

### Finding Description
`BalanceHandler` tracks the length of the event manager's event slice at entry (`BeforeBalanceChange`) and, after the wrapped native action executes, replays exactly the events emitted after that point (`AfterBalanceChange`) into `StateDB.AddBalance`/`SubBalance`, so that native `x/bank`/`x/precisebank` state changes triggered by a precompile call are mirrored into the EVM state: [1](#0-0) [2](#0-1) 

The safe pattern is demonstrated in `precompiles/common/precompile.go`'s `runNativeAction`, which creates a **new** `BalanceHandler` per call via `p.BalanceHandlerFactory.NewBalanceHandler()`: [3](#0-2) 

However, the repository also contains (and the codebase's own integration test documents) a variant where a precompile holds a **single, shared** `BalanceHandler` instance retrieved via `p.GetBalanceHandler()` rather than instantiating a fresh one per invocation, as seen in the debug precompile's `Run`: [4](#0-3) [5](#0-4) 

Several production precompiles (`distribution`, `erc20`, `gov`, `ics20`, `slashing`, `staking`) reference `GetBalanceHandler`/`BalanceHandlerFactory` wiring similarly. When a contract makes a precompile call that, within its execution, re-enters the same precompile (or another call path sharing the handler) before the outer call's `AfterBalanceChange` runs, the inner call's `BeforeBalanceChange` overwrites `bh.prevEventsLen` to a larger index. The outer call's subsequent `AfterBalanceChange` then only replays events emitted *after* the inner call's checkpoint — silently dropping the outer call's own `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` events from being applied to `StateDB`.

This is the same bug class as the Sherlock report: a single mutable "previous marker" variable meant to bound one iteration/step of accounting is instead overwritten by a nested/inner step, corrupting the accounting derived from it (`closableAmount` there; the applied balance delta here).

The repository's own test suite explicitly names and reproduces this defect: [6](#0-5) 

### Impact Explanation
If `StateDB` balances diverge from the underlying `x/bank`/`x/precisebank` balances because some bank-side transfer events are never mirrored into `StateDB`:
- A user's EVM-visible balance can end up higher than their actual backing bank balance (effectively unauthorized balance duplication/inflation visible to subsequent EVM reads/transfers within the same or later transactions), or conversely native balance changes can be lost from the EVM view, corrupting spendable value accounting between the two balance representations that the framework is designed to keep 1:1 (per the `x/precisebank`/bank/StateDB invariant). This matches the "Critical unauthorized minting/duplication/irreversible accounting corruption of spendable user value across native balances, EVM balances ... or precompile-mediated assets" impact category, because `StateDB.Commit()` persists whatever balance state was computed, including any balance drift from a missed or double-applied event window.

### Likelihood Explanation
Triggering this requires a contract-controlled call flow that nests calls to a precompile using a shared/instance-level `BalanceHandler` before the outer call completes (e.g., recursive callback patterns, as demonstrated by the repo's own `DebugPrecompileCaller`/`callback` test flow and the `StakingReverter`-style nested try/catch patterns already present in the test contracts). This is a normal, unprivileged, ordinary-transaction-triggered pattern (arbitrary contract calling a precompile recursively), not a privileged or validator-only scenario. I could not fully confirm from the indexed code whether all shipped/enabled precompiles use the safe per-call `NewBalanceHandler()` factory path (`runNativeAction`) versus the unsafe shared-instance `GetBalanceHandler()` path — the `GetBalanceHandler` accessor's implementation was not found in the indexed content (only usages), so it's uncertain whether this defect is present in currently-enabled production precompiles or only in the `testutil/testdata/debug` test precompile. This uncertainty should be resolved with full repository access.

### Recommendation
Ensure every precompile execution path allocates a **fresh** `BalanceHandler` per top-level `Run`/native-action invocation (as `runNativeAction` already does via `BalanceHandlerFactory.NewBalanceHandler()`), and audit/remove any precompile implementation that stores or reuses a `BalanceHandler` as shared/mutable state across nested or nested-recursive calls. Additionally, consider making `BeforeBalanceChange`/`AfterBalanceChange` reentrancy-safe (e.g., stack-based checkpoints instead of a single scalar `prevEventsLen`) so nested invocations cannot clobber an in-flight outer checkpoint.

### Proof of Concept
The repository's own integration test is effectively the PoC: it deploys a caller contract that recursively invokes a precompile using the shared-`BalanceHandler` pattern and asserts on the resulting event counts, explicitly labeling the scenario "the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB": [7](#0-6) 

A general PoC pattern: deploy a contract that calls a precompile method P1 which, inside its native action, triggers a nested call back into the same precompile (P2) before returning; if the precompile's `Run` uses a shared `BalanceHandler` instance, P2's `BeforeBalanceChange` will move `prevEventsLen` forward past P1's bank events, so P1's own `AfterBalanceChange` (invoked after P2 returns) will skip applying P1's bank-side balance events to `StateDB`, producing a state where `x/bank`/`x/precisebank` balances and `StateDB` balances no longer match.

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())

	callerContract, err := contracts.LoadDebugPrecompileCaller()

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())

	// Pack the input for callback(0)
