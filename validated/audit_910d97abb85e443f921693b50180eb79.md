### Title
Keychain master-passphrase brute-force is unprotected on the daemon WebSocket RPC path - (File: chia/daemon/server.py)

### Summary
Chia's local daemon exposes `validate_keyring_passphrase` and `unlock_keyring` WebSocket RPC commands that check a caller-supplied string against the master keyring passphrase. Unlike the interactive CLI path, which enforces a bounded, delayed retry loop, these RPC handlers perform an unlimited number of passphrase checks with no attempt counting, delay, or lockout — mirroring the Nextcloud Talk bug class where a password-check endpoint bypassed brute-force registration.

### Finding Description
`WebSocketServer.validate_keyring_passphrase()` and `WebSocketServer.unlock_keyring()` both take a `key` from the request and call `Keychain.master_passphrase_is_valid(key, force_reload=True)` directly, returning a boolean success/failure with no side effect that limits repeated guessing: [1](#0-0) [2](#0-1) 

`Keychain.master_passphrase_is_valid()` delegates to `KeyringWrapper.master_passphrase_is_valid()`, which calls `FileKeyring.check_passphrase()` — a stateless decrypt-and-compare operation with no counter or backoff: [3](#0-2) [4](#0-3) 

By contrast, the CLI/interactive path (`obtain_current_passphrase()`) explicitly implements brute-force mitigation: a bounded `MAX_RETRIES = 3`, a `FAILED_ATTEMPT_DELAY = 0.5` second sleep between attempts, and a hard failure via `KeychainMaxUnlockAttempts` once retries are exhausted: [5](#0-4) [6](#0-5) 

This is exactly the CVE-2023-45149 pattern: one code path (interactive/CLI) registers and throttles failed attempts, while a second, functionally equivalent path (the daemon WebSocket RPC used by the GUI and any other daemon client) performs the same secret validation without registering attempts at all, allowing the throttle to be trivially bypassed by calling the RPC command repeatedly instead of the CLI prompt.

The daemon WebSocket is reachable by any client holding a private daemon TLS client certificate (e.g., wallet, farmer, harvester, timelord, or any other locally co-installed service/process using `chia/server/server.py`'s `ssl_context_for_server`), not exclusively by the human operator who set the passphrase — these are separate trust principals that only need daemon connectivity, not knowledge of the keyring passphrase itself.

### Impact Explanation
The master keyring passphrase protects the on-disk encrypted keyring containing all private keys managed by the node (wallet, farmer, pool keys, etc.). Any local principal capable of establishing a daemon WebSocket connection can brute-force this passphrase without rate limiting, and upon success can call `unlock_keyring` to decrypt and expose all private keys, enabling unauthorized transaction signing and coin movement. This matches the report's accepted impact class of unauthorized coin movement / key exposure.

### Likelihood Explanation
Exploitation requires only the ability to open a WebSocket connection to the daemon (something every co-installed Chia service can already do) and does not require any prior knowledge of the passphrase. Weak or moderate-strength passphrases become bruteforceable at network/CPU speed since no delay or attempt cap exists on this path, whereas the CLI path deliberately imposes both.

### Recommendation
Apply the same attempt-limiting/backoff logic used in `obtain_current_passphrase()` (bounded retries, delay, and `KeychainMaxUnlockAttempts`-style lockout) to the `validate_keyring_passphrase` and `unlock_keyring` daemon RPC handlers in `chia/daemon/server.py`, tracked per connection/session, so brute-force protection cannot be bypassed simply by using the RPC surface instead of the interactive prompt.

### Proof of Concept
1. Set a master keyring passphrase via `chia passphrase set`.
2. Connect directly to the daemon WebSocket (using a valid local daemon TLS cert, as any co-installed service would) and repeatedly send `validate_keyring_passphrase` (or `unlock_keyring`) commands with different candidate passphrases, as exercised in the existing test: [7](#0-6) 
3. Observe no delay, counter, or lockout occurs between attempts — unlike `obtain_current_passphrase()`'s `MAX_RETRIES`/`FAILED_ATTEMPT_DELAY` enforcement, an unbounded number of guesses can be submitted until the correct passphrase is found.

def prompt_for_passphrase(prompt: str) -> str:
    if sys.platform == "win32" or sys.platform == "cygwin":
        print(prompt, end="", flush=True)
        prompt = ""
    return getpass(prompt)


def obtain_current_passphrase(prompt: str = DEFAULT_PASSPHRASE_PROMPT, use_passphrase_cache: bool = False) -> str:
    from chia.util.keyring_wrapper import KeyringWrapper

    """
    Obtains the master passphrase for the keyring, optionally using the cached
    value (if previously set). If the passphrase isn't already cached, the user is
    prompted interactively to enter their passphrase a max of MAX_RETRIES times
    before failing.
    """

    if use_passphrase_cache:
        passphrase, validated = KeyringWrapper.get_shared_instance().get_cached_master_passphrase()
        if passphrase:
            # If the cached passphrase was previously validated, we assume it's... valid
            if validated:
                return passphrase

            # Cached passphrase needs to be validated
            if KeyringWrapper.get_shared_instance().master_passphrase_is_valid(passphrase):
                KeyringWrapper.get_shared_instance().set_cached_master_passphrase(passphrase, validated=True)
                return passphrase
            else:
                # Cached passphrase is bad, clear the cache
                KeyringWrapper.get_shared_instance().set_cached_master_passphrase(None)

    # Prompt interactively with up to MAX_RETRIES attempts
    for i in range(MAX_RETRIES):
        colorama.init()

        passphrase = prompt_for_passphrase(prompt)

        if KeyringWrapper.get_shared_instance().master_passphrase_is_valid(passphrase):
            # If using the passphrase cache, and the user inputted a passphrase, update the cache
            if use_passphrase_cache:
                KeyringWrapper.get_shared_instance().set_cached_master_passphrase(passphrase, validated=True)
            return passphrase

        time.sleep(FAILED_ATTEMPT_DELAY)
        print("Incorrect passphrase\n")
    raise KeychainMaxUnlockAttempts
