### Title
mWomSV pool MGP rewards bypass the vlMGP-style forfeiture penalty entirely - ([File: rewards/MasterMagpie.sol])

### Summary
`MasterMagpie._multiClaim` routes MGP rewards earned by the `vlmgp` pool through `_sendMGPForVlMGPPool`, which calls `IvlmgpPBaseRewarder(vlMGPRewarder).queueMGP(...)` and applies a cooldown-based forfeiture via `vlMGPBaseRewarder._calExpireForfeit` / `vlmgp.getRewardablePercentWAD`. MGP rewards earned by the `mWomSV` pool (`MPGRewardPool[_stakingToken] == true`) are instead routed through `_sendMGP`, a plain `safeTransfer` with no forfeiture logic at all, even though `mWomSV.getRewardablePercentWAD` (an identical decay/cooldown percent calculator) exists on the `mWomSV` locker contract.

### Finding Description
In `_multiClaim`, staking-token buckets are classified and dispatched: [1](#0-0) 

- `vlMGPPoolAmount` → `_sendMGPForVlMGPPool(_user, _receiver, vlMGPPoolAmount)`, which forwards to `vlMGPBaseRewarder.queueMGP`: [2](#0-1) 
`queueMGP` computes `forfeitAmount = _calExpireForfeit(_account, _amount)` using `vlMGP.getRewardablePercentWAD(_account)`, sends only the rewardable portion to the receiver, and re-queues the forfeited portion as new rewards for other stakers: [3](#0-2) [4](#0-3) 

- `mWOmPoolAmount` (i.e. the `mWomSV` pool's MGP reward bucket) → `_sendMGP(_user, _receiver, mWOmPoolAmount)`, which is a direct, unconditional transfer with **no** forfeiture calculation whatsoever: [5](#0-4) 

`mWomSV.sol` implements the identical decay/cooldown percent function `getRewardablePercentWAD` used by `vlmgp` (fully-locked vs. cooling-down accounting is structurally identical): [6](#0-5) 

Yet nothing in the MGP-distribution path for the `mWomSV` pool ever calls `mWomSV.getRewardablePercentWAD`. Even `mWOMSVBaseRewarder._calExpireForfeit`, which handles *bonus* reward tokens for that pool (not MGP), is hard-coded to always treat the full amount as rewardable and never forfeit anything: [7](#0-6) 
(`rewardableAmount = _amount;` — the cooldown percent is never consulted at all, unlike `vlMGPBaseRewarder._calExpireForfeit` which reads `vlMGP.getRewardablePercentWAD(_account)`.)

Root cause: the dispatcher in `_multiClaim` (and `MPGRewardPool` mapping design) treats the `mWomSV` staking-token bucket as a plain default-forwarding case (`_sendMGP`) instead of routing it through a forfeiture-aware sender analogous to `_sendMGPForVlMGPPool`/`queueMGP`. No modifier, reentrancy guard, or accounting check in this path enforces forfeiture for `mWomSV` — the check is simply absent by design/omission, not blocked by any existing protection.

### Impact Explanation
Any account holding cooling-down/unlocked `mWomSV` position can claim their full, un-forfeited MGP allocation through `MasterMagpie.claim()`/`multiclaim()` for the `mWomSV` pool, while an economically-identical `vlmgp` position with the same `getRewardablePercentWAD` would have a portion of its MGP forfeited and redistributed to other honest lockers. This is a direct theft of yield that should have been forfeited and redistributed under the intended vlMGP-parity design — it drains value that should accrue to other `mWomSV`/protocol stakers, and is a repeatable systemic leak, not a one-off. This matches "theft of unclaimed yield" impact.

### Likelihood Explanation
Preconditions are trivial and fully unprivileged: stake WOM-derived `mWomSV` normally, initiate an unlock (enter cooldown, decaying `getRewardablePercentWAD`), then call the standard `claim`/`multiclaim` entry point on `MasterMagpie`. No special role, flash loan, or reentrancy needed — this is the intended public reward-claim flow, exploited purely by the routing logic difference. It is repeatable indefinitely for every claim cycle and scales with pool size.

### Recommendation
Route the `mWomSV` MGP bucket through a forfeiture-aware sender mirroring `_sendMGPForVlMGPPool`, e.g. add `_sendMGPForMWomSVPool` that calls `mWOMSVBaseRewarder.queueMGP` (implement `queueMGP` in `mWOMSVBaseRewarder` analogous to `vlMGPBaseRewarder.queueMGP`, forfeiting `1 - mWomSV.getRewardablePercentWAD(_account)` and requeueing the forfeited amount as rewards). Also fix `mWOMSVBaseRewarder._calExpireForfeit` to actually apply `mWOMSV.getRewardablePercentWAD(_account)` instead of hard-coding `rewardableAmount = _amount`.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `vlMGP`, `mWomSV`, `vlMGPBaseRewarder`, `mWOMSVBaseRewarder` per repo setup/mocks.
2. Two users, A and B, each lock equal MGP-equivalent principal: A into `vlmgp`, B into an equivalent `mWomSV` position, both fully vested initially.
3. Both users initiate unlock of the same amount, producing identical `startTime`/`endTime` cooldown windows, so `getRewardablePercentWAD(A)` on `vlmgp` == `getRewardablePercentWAD(B)` on `mWomSV` at every timestamp.
4. Warp to mid-cooldown so `rewardablePercentWAD < 1e18` (e.g. 50%).
5. Accrue identical MGP emission to both pools (equal `allocPoint`, equal `accMGPPerShare` growth).
6. Call `masterMagpie.claim(vlmgp, ...)` for A and `masterMagpie.claim(mWomSV_stakingToken, ...)` for B (or `multiclaim`).
7. Assert: `mgp.balanceOf(A) < expectedFullMGP * 0.5` (approx, forfeited half went to `vlMGPBaseRewarder` as requeued rewards) while `mgp.balanceOf(B) == expectedFullMGP` (full amount, no forfeiture).
8. Assert `B`'s received MGP > `A`'s received MGP despite identical `getRewardablePercentWAD`, proving the parity violation and yield theft.

    function queueMGP(uint256 _amount, address _account, address _receiver) override external onlyManager nonReentrant returns (bool) {
        IERC20(vlMGP.MGP()).safeTransferFrom(msg.sender, address(this), _amount);
        
        uint256 forfeitAmount = _calExpireForfeit(_account, _amount);
        uint256 rewardableAmount = _amount - forfeitAmount;
        
        if (forfeitAmount > 0)
            _queueNewRewardsWithoutTransfer(forfeitAmount, address(vlMGP.MGP()));

        if (rewardableAmount > 0) {
            IERC20(vlMGP.MGP()).safeTransfer(_receiver, rewardableAmount);
            emit MGPHarvested(_account, rewardableAmount, forfeitAmount);
        }

        return true;
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
