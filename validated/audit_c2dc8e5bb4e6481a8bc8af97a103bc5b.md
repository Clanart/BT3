Let me check a couple more candidate paths quickly: the FROST `complete`/BatchVerifier path and bitcoin scanner offset registration.### Title
Missing validation in `ThresholdKeys::read`/`ThresholdKeys::new` accepts identity verification shares, letting a participant occupy a threshold slot with a zero-weight share - (File: crypto/dkg/src/lib.rs)

### Summary
The report's bug class is a *missing initialization/validation step that lets a zero-value default into a security-critical position* (no `GOVERNANCE_ROLE` granted → `payoutAmount` stays 0 → anyone claims for free). The Serai analog lives in `crypto/dkg/src/lib.rs`: `ThresholdKeys::read` deserializes per-participant verification shares with `<C as Ciphersuite>::read_G`, which does **not** reject the identity point — unlike `Curve::read_G` in `crypto/frost/src/curve/mod.rs:125-131`, which explicitly rejects identity for exactly this reason. `ThresholdKeys::new` (lines 355-365) then only checks the count of `verification_shares` and that each index is `<= n`; it never checks that a share is non-identity, nor that `verification_shares[i] == G * secret_share` for the local index.

### Finding Description
- `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:620-623`) fills the verification-share map via `<C as Ciphersuite>::read_G(reader)`, accepting the identity/`0` point. Every other untrusted point input in the signing path (`Commitments::read` via `GeneratorCommitments::read`, `crypto/frost/src/nonce.rs:34-36`) goes through `<C as Curve>::read_G`, which errors on identity (`crypto/frost/src/curve/mod.rs:125-131`). The identity check that the rest of the codebase treats as mandatory is simply absent on this path — the same "missing `_grantRole`" shape.
- `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:376-378`) computes `group_key = Σ_{i=1..=t} verification_shares[i] * λ_i`. An identity share contributes zero, so a claimed `t`-of-`n` group key is actually formed from `t-1` real shares.
- In `ThresholdKeys::view` (`crypto/dkg/src/lib.rs:503-506`), the interpolated verification share for that participant is `identity * scalar * λ` = identity (plus `G*offset` only if it is `included[0]`, line 521).
- In `AlgorithmSignatureMachine::complete` (`crypto/frost/src/sign.rs:475-489`), blame verification calls `verify_share(verification_share, bound_nonces, share)`; for the Schnorr algorithm (`crypto/frost/src/algorithm.rs:219-230`) the batch statement is `s·G = R_bound + c·Y`. With `Y = identity` this degenerates to `s·G = R_bound`, which the malicious participant satisfies with `s = d + ρ·e` — a share containing *zero* secret contribution that still passes per-share verification.

### Impact Explanation
High. An unprivileged party who can feed crafted bytes to `ThresholdKeys::read` (a listed reachable entry point) produces keys where:
1. A participant slot contributes the identity to both `group_key` and share verification — that party can submit valid-looking signature shares knowing no secret, reducing the effective threshold.
2. The attacker fully controls the remaining `verification_shares`, so `group_key` becomes an attacker-influenced linear combination of a victim's real verification share (e.g., `λ_1·Y_victim + attacker-chosen terms`). An honest signer then participates in producing valid aggregate signatures under this unintended, attacker-embedded group key — concrete "signing under an unintended key/message" rather than mere DoS. If `verification_shares[i] ≠ G·s_i` for the honest index, the honest signer is instead reliably blamed (`InvalidShare`), which is only a liveness issue.

### Likelihood Explanation
Medium-High. It requires an attacker to influence the bytes deserialized by `ThresholdKeys::read` (e.g., a participant supplying key material in a flow that reconstructs keys from peer/transit data, or tampered stored keys). No malicious-validator collusion is needed — a single crafted blob suffices — but it does require a consumer that deserializes attacker-controlled `ThresholdKeys` rather than locally generated ones. The code itself acknowledges this gap at `crypto/frost/src/sign.rs:491-494` ("deserialize a semantically invalid FrostKeys") yet never prevents it.

### Recommendation
In `ThresholdKeys::read` and `ThresholdKeys::new`, reject identity verification shares (use the identity-rejecting read or an explicit `is_identity` check), and validate `verification_shares[params.i()] == C::generator() * secret_share` so a deserialized key share is provably consistent with its claimed public share — the analog of adding the missing `_grantRole(GOVERNANCE_ROLE, _admin)`.

### Proof of Concept
1. Victim holds honest keys with `params.i() = 1`, verification share `Y_1 = G·s_1` (known to the attacker from the DKG transcript).
2. Attacker serializes a `ThresholdKeys` blob for curve `C` with `t = 2`, `n = 2`, `i = 1`, `Interpolation::Lagrange`, `secret_share = s_1` (or, where only shares-index consistency matters, any value), `verification_shares = {1: Y_1, 2: identity}`. `ThresholdKeys::read` succeeds; `group_key()` returns `λ_1({1,2})·Y_1 = 2·Y_1` instead of a real 2-of-2 key.
3. In a FROST session with `included = {1, 2}`, the victim signs honestly; the attacker (as participant 2) publishes nonce commitments `(D_2, E_2)` and share `s_2 = d_2 + ρ_2·e_2`.
4. `complete` aggregates `sum = s_1_share + s_2`; `verify` succeeds against `group_key = 2·Y_1`, yielding a valid Schnorr signature under a key whose "second signer" never existed — and if it hadn't, the blame path's statement `s_2·G = R_2 + c·identity` still passes for the attacker's share.

Caveat: I could not fully trace every downstream consumer of `ThresholdKeys::read` (e.g., whether processors reload keys from peer-supplied bytes vs. strictly local storage) within the available iterations; the primitive-level flaw itself is confirmed by the cited code, and `ThresholdKeys::read` is in the listed reachable-API surface.
