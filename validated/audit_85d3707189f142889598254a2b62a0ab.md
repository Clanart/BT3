### Title
Unauthenticated SSRF via DataLayer mirror URLs reaching `http_download` — ([File: chia/data_layer/download_data.py])

### Summary
Any on-chain participant can publish an arbitrary "mirror" URL for any DataLayer store by spending a small/zero-value coin to the mirror puzzle. Every node that tracks that store's singleton (owners, subscribers, or offer counterparties who resolve the store) will ingest that URL as a subscription server and periodically issue outbound HTTP GET requests to it with no validation of scheme, host, or IP range — a classic SSRF primitive reachable purely through normal Data Layer coin-spend/subscription mechanics.

### Finding Description
`DataLayerWallet.create_new_mirror()` creates a coin to `create_mirror_puzzle()` with memos `[launcher_id, *urls]`, requiring only a normal signed spend (fee/amount can be `0` mojos, as used in tests: [1](#0-0) ).

Any node that tracks the target `launcher_id` observes this coin in `coin_added()`, decodes the URLs from the spend, and unconditionally stores them as a `Mirror` record — there is no validation of the URL contents at all: [2](#0-1) .

The DataLayer service periodically pulls these mirror URLs via `update_subscriptions_from_wallet()` and persists them into the local subscriptions table as download servers: [3](#0-2) .

`fetch_and_validate()` (invoked from the periodic `update_subscription()` sync loop) then selects one of these subscribed server URLs and calls `insert_from_delta_file()`/`download_file()` against it: [4](#0-3) .

`download_file()` falls through to `http_download()` when no plugin downloader is configured (the default case for any peer without a custom S3 plugin) [5](#0-4) , and `http_download()` performs an unrestricted `aiohttp` `GET` directly against the attacker-supplied `server_info.url`, concatenated with a filename, with no scheme allowlist, no private/link-local/metadata IP blocking, and default redirect-following: [6](#0-5) .

Unlike the S3 plugin path, which restricts `parse_result.scheme == "s3"` before acting [7](#0-6) , the default HTTP mirror path has no equivalent check. The project's own internal documentation acknowledges "mirror URLs...are external trust inputs" but only calls out data-integrity verification of downloaded content, not SSRF protection for the request itself: [8](#0-7) .

### Impact Explanation
Any node participating in DataLayer for a given store (owners, subscribers, or peers resolving offers/proofs that require tracking a launcher id) can be coerced into making outbound requests to attacker-chosen destinations, including cloud metadata endpoints (`169.254.169.254`) and internal-only services, by any other user who is able to publish a mirror coin for that store — an inexpensive, fully on-chain, unprivileged action. This exposes credential theft, internal network reconnaissance, and firewall bypass risks on any machine running a Data Layer client/service, consistent with the CWE-918 SSRF class in the reference report. It does not directly enable coin theft, but it is a concrete, remotely-triggerable server-side request forgery against Data Layer client infrastructure.

### Likelihood Explanation
Likelihood is high for any store with external subscribers: creating a mirror coin only requires the ability to submit a normal spend bundle with a tiny/zero amount and arbitrary memo strings, no special permissions, and no interaction with the target beyond both parties tracking the same `launcher_id` (which is the normal, intended DataLayer collaboration model — subscribers and offer counterparties routinely track others' launcher IDs).

### Recommendation
Validate mirror/server URLs before use in `http_download()`/`download_file()`: enforce an `http(s)` scheme allowlist, resolve and reject requests to private/loopback/link-local/multicast/metadata IP ranges (with re-validation after DNS resolution to prevent rebinding), and consider disabling automatic redirect following or re-validating the redirect target. Apply the same restriction consistently to `get_downloader()`'s plugin-handshake POST requests, which have the same unrestricted-URL issue.

### Proof of Concept
1. Node A creates DataLayer store `launcher_id`; Node B tracks it (`dl_track_new`) as a normal subscriber.
2. Attacker (any user) spends a `0`-mojo coin to `create_mirror_puzzle()` with memos `[launcher_id, b"http://169.254.169.254/latest/meta-data/"]`, mirroring `create_new_mirror` usage as shown in tests: [9](#0-8) .
3. Once confirmed, Node B's `coin_added()` records this as a `Mirror` for `launcher_id` with no URL validation.
4. Node B's periodic `update_subscription()`/`fetch_and_validate()` cycle picks this URL as a server and calls `http_download()`, issuing `GET http://169.254.169.254/latest/meta-data/<filename>` from Node B's process — confirming outbound SSRF to the attacker-chosen target.

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```
