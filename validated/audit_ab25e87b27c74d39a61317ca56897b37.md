## Title
Stale manual conflict resolutions silently reused across unrelated conflicts on the same file path, causing wrong content to be committed - (File: `app/src/lib/stores/updates/changes-state.ts`)

## Summary
The report describes a state-machine invariant violation: a value ("payoutBalance"/holder status) computed from a stale cache condition is reused when an entity re-enters a state it previously left, causing silent loss/corruption. GitHub Desktop has a structurally identical flaw in its merge/rebase/cherry-pick conflict tracking: `manualResolutions`, a `Map<string, ManualConflictResolution>` keyed only by file **path**, is carried forward from the previous `conflictState` into a new one without verifying that the new conflict on that path is the *same* conflict the user actually resolved. Because `hasUnresolvedConflicts()` trusts the mere *presence* of a path in that map (regardless of which operation/commit produced it), a manual "ours"/"theirs" choice made for one conflict can be silently re-applied to a later, unrelated conflict on the same path, causing Desktop to stage and commit content the user never reviewed.

## Finding Description
In `updateConflictState()`, the `manualResolutions` map is pulled forward unconditionally as long as a previous conflict state existed: [1](#0-0) 

This map is then embedded into whatever new conflict state is computed by `getConflictState()`, even when the new state represents a **different operation** (merge → rebase, or a different commit within the same rebase/cherry-pick sequence) on the **same file path**: [2](#0-1) 

Note that the only checks performed (`branchNameChanged`, tip comparisons) are used solely to increment telemetry counters in `performEffectsForMergeStateChange`/`performEffectsForRebaseStateChange` — they never gate or clear `manualResolutions`. The map survives kind transitions ("Otherwise we transitioned from a merge conflict to a rebase conflict or vice versa, and we should avoid any side effects here" — but the stale map is still returned).

Downstream, `hasUnresolvedConflicts()` treats *any* entry for a path as a full resolution, without validating it against the current conflict's identity: [3](#0-2) 

`getResolvedFiles`/`getConflictedFiles` use this to decide what still needs the user's attention in the conflicts dialog: [4](#0-3) 

When the operation is finished, `_finishConflictedMerge` (and the rebase/cherry-pick equivalents) stage files using that same stale map, choosing "ours" or "theirs" based on the *current* status entry for the path but under the *old* resolution decision: [5](#0-4) [6](#0-5) 

**Why existing guards do not stop this:** the only invalidation of `manualResolutions` happens implicitly when `prevConflictState` becomes `null` (i.e., a status refresh observes no conflict at all in between). There is no invalidation keyed on `currentTip`, `targetBranch`/`currentBranch`, or on the conflict "kind" itself — exactly analogous to the smart-contract bug where `lastPayoutIndexCalculated == currentPayoutIndex` was treated as sufficient proof of "nothing pending" even though the holder had re-entered the state. Here, "path present in `manualResolutions`" is treated as sufficient proof of "this conflict is resolved," even though the underlying conflict identity (commit/operation) has changed.

## Impact Explanation
This falls in the "silent corruption of what the user commits or pushes" category. An attacker who controls a remote/repository the victim merges, rebases, or cherry-picks from can craft history such that:
- The same file path conflicts more than once across a rebase/cherry-pick sequence (very common: rebasing several commits that all touch one file), or
- A merge conflict on a path is manually resolved but the operation continues into another conflict-producing state referencing the same path.

Desktop will silently treat the second, unrelated conflict as already resolved, apply the earlier ours/theirs decision to it, stage it, and let it be committed and pushed without ever showing the user a conflict-resolution prompt for that content. The user believes they resolved every conflict they were shown; in reality the committed/pushed blob contains content they never reviewed, which the attacker can influence by shaping conflicting hunks in the remote branch/commits they control.

## Likelihood Explanation
Multi-file, multi-commit rebases/cherry-picks that repeatedly touch the same path are common, and Desktop explicitly supports resolving conflicts before continuing an operation — the exact usage pattern that triggers this. No special local access, admin rights, or social engineering is required beyond the victim performing an ordinary merge/rebase/cherry-pick against attacker-influenced remote content, which is within the documented valid-impact scope (attacker controls a fetched/cloned repository).

## Recommendation
Do not treat `manualResolutions` entries as valid across a change in conflict identity. Clear (or re-key) the map whenever:
- The conflict `kind` changes (merge ↔ rebase ↔ cherry-pick), or
- The relevant identity fields change (`currentTip` for merge, `originalBranchTip`/`targetBranch` per rebase step, or the specific commit being applied in a rebase/cherry-pick), or
- The underlying conflicted git status entry (`entry.us`/`entry.them`) for that path differs from the one recorded at resolution time.

Concretely, in `updateConflictState`, only pass forward the subset of `prevConflictState.manualResolutions` whose stored resolution still matches the *current* conflict identity for that path, mirroring the mitigation pattern in the original report ("check whether the previously-computed condition still holds before trusting it").

## Proof of Concept
1. Start a rebase of a branch containing two separate commits, C1 and C2, both of which modify the same file `shared.txt` relative to the target branch, each in an independent hunk that both conflict.
2. Desktop shows conflicts for `shared.txt` from C1; the user manually resolves via the "ours"/"theirs" dropdown (`_updateManualConflictResolution` sets `manualResolutions.set('shared.txt', ManualConflictResolution.theirs)`), and clicks Continue.
3. `continueRebase` stages accordingly and re-invokes `git rebase --continue`, which now applies C2 and produces a **new, unrelated** conflict on `shared.txt`.
4. On refresh, `updateConflictState` recomputes conflict state for the rebase; because `prevConflictState` was non-null and still `kind: 'rebase'`, `manualResolutions` (still containing `shared.txt -> theirs` from step 2) is carried forward unchanged.
5. `getConflictedFiles`/`getResolvedFiles` (`app/src/lib/status.ts`) report `shared.txt` as already resolved — the conflicts dialog never prompts the user for the C2 conflict.
6. `continueRebase` stages `shared.txt` again using the stale `theirs` resolution against the *current* (C2) `status.entry`, and the rebase completes; the resulting commit contains content for the C2 conflict that the user never saw or approved, and can be silently pushed.

  state: IChangesState,

  const manualResolutions =
    prevConflictState !== null

      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {

export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}

  public async _finishConflictedMerge(
    repository: Repository,
    workingDirectory: WorkingDirectoryStatus,
    manualResolutions: Map<string, ManualConflictResolution>
  ): Promise<string | undefined> {
    /**
     *  The assumption made here is that all other files that were part of this merge
     *  have already been staged by git automatically (or manually by the user via CLI).
     *  When the user executes a merge and there are conflicts,
     *  git stages all files that are part of the merge that _don't_ have conflicts
     *  This means that we only need to stage the conflicted files
     *  (whether they are manual or markered) to get all changes related to
     *  this merge staged. This also means that any uncommitted changes in the index
     *  that were in place before the merge was started will _not_ be included, unless
     *  the user stages them manually via CLI.
     *
     *  Its also worth noting this method only used in the Merge Conflicts dialog flow, not committing a conflicted merge via the "Changes" pane.
     *
     *  *TLDR we only stage conflicts here because git will have already staged the rest of the changes related to this merge.*
     */
    const conflictedFiles = workingDirectory.files.filter(f => {
      return f.status.kind === AppFileStatusKind.Conflicted
    })
    const gitStore = this.gitStoreCache.get(repository)
    return await gitStore.performFailableOperation(() =>
      createMergeCommit(repository, conflictedFiles, manualResolutions)
    )
  }

export async function stageManualConflictResolution(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  manualResolution: ManualConflictResolution
): Promise<void> {
  const { status } = file
  // if somehow the file isn't in a conflicted state
  if (!isConflictedFileStatus(status)) {
    log.error(`tried to manually resolve unconflicted file (${file.path})`)
    return
  }

  if (isConflictWithMarkers(status) && status.conflictMarkerCount === 0) {
    // If somehow the user used the Desktop UI to solve the conflict via ours/theirs
    // but afterwards resolved manually the conflicts via an editor, used the manually
    // resolved file.
    return
  }

  const chosen =
    manualResolution === ManualConflictResolution.theirs
      ? status.entry.them
      : status.entry.us

  const addedInBoth =
    status.entry.us === GitStatusEntry.Added &&
    status.entry.them === GitStatusEntry.Added

  if (chosen === GitStatusEntry.UpdatedButUnmerged || addedInBoth) {
    await checkoutConflictedFile(repository, file, manualResolution)
  }

  switch (chosen) {
    case GitStatusEntry.Deleted:
      return removeConflictedFile(repository, file)
    case GitStatusEntry.Added:
    case GitStatusEntry.UpdatedButUnmerged:
      return addConflictedFile(repository, file)
    default:
      assertNever(chosen, 'unaccounted for git status entry possibility')
  }
}
