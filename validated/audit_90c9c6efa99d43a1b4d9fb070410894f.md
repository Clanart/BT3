### Title
TextFormat parser logs unredacted snippets of attacker-supplied input to `ABSL_LOG(ERROR)` on parse failure - (File: `src/google/protobuf/text_format.cc`)

### Summary
The SpiceDB advisory (GHSA-jg7w-cxjv-98c2) shows a class of bug where, on a parse failure of attacker-influenced input, the raw offending data (including secret material) is embedded verbatim into an error message that is then written to logs without redaction. Protobuf's `TextFormat::Parser` exhibits the same invariant failure: when a text-format message fails to parse and the caller has not supplied a custom `io::ErrorCollector`, the parser unconditionally writes the error message — which is built from raw tokens/lines of the attacker-controlled input — to the process-wide `ABSL_LOG(ERROR)` sink.

### Finding Description
`TextFormat::Parser::ParserImpl::ReportError` delegates to the free function `ReportErrorImpl`: [1](#0-0) 

When `error_collector_` is `nullptr` (the default for the common `TextFormat::ParseFromString`/`Parser::Parse` call paths that don't set an explicit collector), the error `message` is sent straight to `ABSL_LOG(ERROR)`, tagged only with the message type name and line/column — there is no scrubbing of the message content itself.

The `message` strings that flow into this sink are frequently built directly from the parsed input. The Python tokenizer's `ParseError` helper is the clearest example — it literally splices the raw current source line into the exception text: [2](#0-1) 

So any text being parsed (e.g. `password: "S3cr3t!"` or a config value containing a token/credential) that triggers a tokenizer/parse error on or near that line results in that raw content becoming part of the error string. On the C++ side, many `ReportError` call sites quote back the actual offending field name, enum name, or token text taken from the input (e.g. unknown-field, unknown-enum-value, and multiple-singular-field errors), and all such messages funnel through `ReportErrorImpl`'s unconditional `ABSL_LOG(ERROR)` when no collector is set.

This mirrors SpiceDB's failed invariant exactly: an error path that is supposed to only report *where* parsing failed instead reproduces *what* failed to parse, and that reproduction is written to a shared log sink without any sanitization step, even though the input may contain sensitive values a consuming application embeds in textproto (config files, debug/admin endpoints that accept textproto, RPC reflection debug string round-trips, etc.).

Notably, the JSON side of the codebase is aware of exactly this problem and takes a mitigating step: `JsonLocation::Invalid` explicitly calls `HardenAgainstHyrumsLaw` to obfuscate all but a fixed "invalid JSON" prefix before returning the status: [3](#0-2) 

No equivalent hardening/redaction exists on the `TextFormat` error path before it reaches `ABSL_LOG(ERROR)`.

### Impact Explanation
If a consuming application accepts attacker-supplied text-format protobuf (e.g. a debug/config endpoint, admin tool, or any place a client can submit textproto that is parsed with a default `TextFormat::Parser`/`ParseFromString` without a custom `ErrorCollector`), any secret-bearing field value that happens to be adjacent to or part of a malformed token will be written verbatim into the application's/server's log stream once a parse error is triggered. This matches CWE-532 (information exposure through log files) — the same weakness class as the SpiceDB advisory, C:H/I:N/A:N under a similar CVSS profile (local/log-file disclosure, no confidentiality breach beyond log exposure).

### Likelihood Explanation
Moderate. The behavior requires: (1) an application parsing untrusted text-format protobuf without registering a custom `ErrorCollector` (the default and by far most common usage pattern), and (2) the ability of an attacker to influence which bytes land in the message being parsed and trigger a parse error near sensitive content. This is a realistic pattern for services that expose textproto-based debug/config/import endpoints, but it is less universally reachable than a plain wire-format/binary parse path, since it depends on the TextFormat entry point specifically being exposed to untrusted callers.

### Recommendation
Apply the same hardening already used for JSON errors (`HardenAgainstHyrumsLaw` in `lexer.cc`) to the default `ReportErrorImpl` log path in `text_format.cc`: when no `ErrorCollector` is supplied, log only a fixed, redacted diagnostic (location + generic error class) instead of the raw message text, or require callers that log parse failures to explicitly opt into verbose/raw diagnostics rather than defaulting to it.

### Proof of Concept
Given a service that does:
```cpp
MyConfig cfg;
if (!google::protobuf::TextFormat::ParseFromString(untrusted_textproto, &cfg)) {
  // ReportErrorImpl already fired ABSL_LOG(ERROR) with raw content
}
```
with `untrusted_textproto` containing a line such as:
```
api_key: "sk_live_51H8x...SECRET"
bad_field 123
```
The malformed second line triggers a parser error; per `ReportErrorImpl` (`text_format.cc:342-357`) and the tokenizer's line-embedding error construction (`text_format.py:1814-1823`, mirrored conceptually in the C++ tokenizer's error text), the emitted `ABSL_LOG(ERROR)` entry includes context drawn from the surrounding raw input, exposing the secret line content in the process log — directly analogous to the SpiceDB advisory's leaked-password log line.

```text
void ReportErrorImpl(int line, int col, absl::string_view message,
                     const Descriptor* root_message_type,
                     io::ErrorCollector* error_collector) {
  if (error_collector == nullptr) {
    if (line >= 0) {
      ABSL_LOG(ERROR) << "Error parsing text-format "
                      << root_message_type->full_name() << ": " << (line + 1)
                      << ":" << (col + 1) << ": " << message;
    } else {
      ABSL_LOG(ERROR) << "Error parsing text-format "
                      << root_message_type->full_name() << ": " << message;
    }
  } else {
    error_collector->RecordError(line, col, message);
  }
}
```
