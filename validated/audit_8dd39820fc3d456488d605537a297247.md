### Title
Fee and weight are calculated without the OP_RETURN data output, producing transactions that underpay their true size and can be rejected/stuck - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` builds the final `tx_outs` vector (including the attacker-controlled OP_RETURN `data` output) but computes `weight`, `vbytes`, and therefore `needed_fee` from the `payments` slice alone via `calculate_weight_vbytes`. This mirrors the incident's bug class: a quantity (`needed_fee`/`vbytes`, the analog of `toBurnAmount`) is computed from stale/incomplete state and then consumed after additional balance-affecting data (the data output) has already been committed to the transaction. The resulting signed transaction pays a fee rate far below `fee_per_vbyte` on its real serialized size, and the `TooLowFee` minimum-relay check and `MAX_STANDARD_TX_WEIGHT` check are both evaluated against the underestimated values.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` at lines 194-202 of `networks/bitcoin/src/wallet/send.rs`, before weight/vbytes are computed at line 204: [1](#0-0) 

`calculate_weight_vbytes` only receives `payments` (and optionally `change`), so its constructed sizing transaction never includes the up-to-80-byte data output: [2](#0-1) 

The same underestimation propagates to the change-path recomputation (line 226, which also passes `payments` only), the `TooLowFee` minimum-relay-fee guard at lines 211-213, and the `TooLargeTransaction` check at line 241: [3](#0-2) 

`data` is an untrusted byte vector supplied by external Bitcoin transactions (an InInstruction may carry data; the only bound is `len <= 80` at line 171). Since `TransactionMachine`/`TransactionSignMachine` sign with `TapSighashType::Default` committing to the real `tx.output` vector (lines 373-397), the network can never "fix" the fee — the signed fee is `sum(inputs) - sum(outputs)` and the true vsize is larger than the one used for the fee.

### Impact Explanation
A request that carries `data` produces a signed transaction whose actual fee rate is below the requested `fee_per_vbyte` — potentially below `DEFAULT_MIN_RELAY_TX_FEE` even though the `TooLowFee` check passed, since that check divides by the underestimated `vbytes`. Such a transaction will not relay or confirm; the inputs remain encumbered by a signed-but-unbroadcastable transaction and must be re-signed, i.e., funds are effectively unspendable for that attempt. Additionally, the weight check can pass while the real transaction exceeds `MAX_STANDARD_TX_WEIGHT`, yielding a non-standard transaction that the Bitcoin network rejects outright.

### Likelihood Explanation
Triggerable by any unprivileged party who can cause a withdrawal/transaction to be constructed with non-empty `data` and a low `fee_per_vbyte`, since the discrepancy (up to ~80 bytes + output overhead across a 4-weight-unit-per-byte vbytes conversion) is largest relative to small transactions with a tight fee. This requires no validator collusion, no reorg, and no key material — only public transaction data reaching `SignableTransaction::new`.

### Recommendation
Compute weight/vbytes from the actual `tx_outs` vector (payments + OP_RETURN + change) rather than the `payments` slice — e.g., pass `tx_outs` into `calculate_weight_vbytes` after the data output is appended, and re-derive `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check from the full output set, including when deciding whether the change output can be afforded.

### Proof of Concept
Conceptual: call `SignableTransaction::new` with one input worth `payment + needed_fee + small_margin`, a single payment, `fee_per_vbyte` equal to the minimum relay rate, and `data = vec![0u8; 80]`. `needed_fee()` returns `fee_per_vbyte * vbytes` where `vbytes` excludes the ~91-byte OP_RETURN output; the signed transaction's real size is larger, so its effective feerate falls below `DEFAULT_MIN_RELAY_TX_FEE` and bitcoind rejects it with "min relay fee not met" / non-standard, despite `new` returning `Ok` and `multisig`/`sign` succeeding.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
