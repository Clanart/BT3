## Race Condition Analog Found

### Title
Unsynchronized concurrent access to shared `BLSCache` during unfinished-block signature validation - (File: `chia/full_node/full_node.py`)

### Summary
`FullNode.add_unfinished_block()` explicitly releases `self.blockchain.priority_mutex` before running CLVM/signature validation, and passes the single shared `self._bls_cache` instance into a worker thread via `self.pool.run_in_loop(...)`. Concurrently, `FullNode.add_block()` mutates the very same `self._bls_cache` object (`bls_cache.evict(...)`) while a different unfinished-block validation for another peer's block may be concurrently reading/writing it from a separate OS thread in the `PriorityThreadPoolExecutor`. This mirrors the Algernon CVE-2026-43981 pattern: a lock that is supposed to serialize access to shared, not-safely-reentrant state is released specifically to "allow other blocks and transactions to get validated," but the state it was protecting is still touched concurrently from multiple execution contexts.

### Finding Description
In `add_unfinished_block()`: [1](#0-0) 
the comment states the CLVM generator and signature are deliberately validated **outside** `self.blockchain.priority_mutex` "to allow other blocks and transactions to get validated." The actual validation call is: [2](#0-1) 
which dispatches `run_block_generator`/`run_block_generator2` — passing the node-wide `self._bls_cache` object by reference — onto `PriorityThreadPoolExecutor` real OS worker threads via `run_in_loop()`: [3](#0-2) 
Each worker thread executes `item.fn(*item.args, **item.kwargs)` independently and concurrently with other workers, with no lock guarding `self._bls_cache` across calls.

Meanwhile, `add_block()` — which can run concurrently with pending `add_unfinished_block()` calls for other candidate blocks — mutates the same shared cache object: [4](#0-3) 
`bls_cache.evict(pairs_pks, pairs_msgs)` is called on the asyncio event-loop thread while `blockchain.priority_mutex` is held for that call, but that mutex is never held by the concurrent worker-thread executions of `run_block_generator2(..., self._bls_cache, ...)` from other in-flight `add_unfinished_block()` calls, since those explicitly run outside the mutex by design.

The result is the same shared, mutable cache object (`chia_rs.BLSCache`) being written from the main event-loop thread (`evict`) and read/written concurrently from arbitrary worker threads (`aggregate_verify`/insert during generator execution), with no Python-level lock coordinating the two. Multiple worker threads can also run block/unfinished-block validation concurrently against the same cache instance, since `PriorityThreadPoolExecutor` allows `max_workers` truly parallel OS threads, and Rust extension code invoked through PyO3 commonly releases the GIL during heavy computation, making true concurrent mutation of the underlying Rust map possible.

### Impact Explanation
If the shared BLS pairing cache is mutated concurrently without synchronization, a cache entry keyed by `(pubkey, message)` can be corrupted, evicted mid-read, or hit against stale/wrong pairing data. Because `run_block_generator()`/`run_block_generator2()` rely on this cache to short-circuit `aggregate_verify()` calls ("run_block() also validates the signature" per the code comment at line 2640), a corrupted cache state could cause the validator to treat a spend bundle's aggregate BLS signature as already-verified when it was not, or to skip verifying a subset of `AGG_SIG_*` pairs due to an inconsistent cache read during concurrent eviction. This can lead to a block or unfinished block being accepted with an invalid/unauthorized signature, which is a coin-movement/consensus-integrity issue (invalid spend or block acceptance), not merely a crash.

### Likelihood Explanation
Exploitation requires only ordinary network conditions that already occur on chia full nodes: multiple candidate unfinished blocks (from different farmers/timelords) or concurrent block-add operations racing through `add_unfinished_block()`/`add_block()`, which is routine during normal chain-tip contention and is exactly the scenario the "outside the lock" optimization was added to support. An attacker does not need to be a trusted peer; simply causing multiple unfinished blocks/transactions to be processed concurrently (a normal occurrence, and one an attacker could amplify by broadcasting several competing unfinished blocks) is sufficient to trigger overlapping cache access. Reliably weaponizing the race into a specific forged-signature acceptance is harder to guarantee deterministically, matching the "AC:H" access-complexity characterization in the analogous CVE.

### Recommendation
Guard all mutation and validation-time use of `self._bls_cache` (both the `evict()` call in `add_block()` and the pass-through into `run_block_generator`/`run_block_generator2` in `add_unfinished_block()`) with a dedicated lock (or serialize BLS-cache-touching work onto a single dedicated thread/queue), so the cache is never read or written from more than one thread at a time — independent of `blockchain.priority_mutex`, which was intentionally released around this code for throughput reasons. Alternatively, confirm and enforce (with a test using the race/thread-sanitizer equivalent) that `chia_rs.BLSCache` is fully internally synchronized (e.g., backed by a Rust `Mutex`/`RwLock`) for all its exposed Python operations (`update`, `evict`, and the reads performed inside `run_block_generator*`), and add a regression test that concurrently calls `evict()` from one thread while another thread executes `run_block_generator2()` against the same cache instance.

### Proof of Concept
1. Start a full node and construct two unrelated transaction blocks/unfinished blocks, each with distinct AGG_SIG conditions, such that both can be concurrently validated (e.g., via `full_node.add_unfinished_block()` called concurrently for two different peers/blocks, or interleaved with `full_node.add_block()` for a third block that shares cached pubkey/message pairs, as exercised by the existing test `test_eviction_from_bls_cache`): [5](#0-4) 
2. Modify/extend this test to run `full_node.add_block(block_a, ..., full_node._bls_cache)` on one asyncio task while concurrently invoking `full_node.add_unfinished_block(unfinished_block_b, peer)` (which internally calls `self.pool.run_in_loop(run_block_generator2, ..., self._bls_cache, ...)`) on another task, both racing against the same `self._bls_cache` instance.
3. Run under Python's `-X dev`/`faulthandler` or with a stress multiplier (many concurrent unfinished blocks) to observe inconsistent cache state, a `evict`/insert race, or (if `chia_rs.BLSCache` is not internally synchronized) a crash/incorrect `validated_signature` result — demonstrating that the mutex was released specifically to allow this concurrency while leaving `self._bls_cache` unprotected.

    def _worker(self, q: queue.PriorityQueue[_WorkItem], is_dedicated: bool) -> None:
        while True:
            item = q.get()
            if item.fn is None:
                return
            if not item._claim.acquire(blocking=False):
                continue
            assert item.future is not None
            if not item.future.set_running_or_notify_cancel():
                continue
            if self._instrument:
                with self._stats_lock:
                    if is_dedicated:
                        self._retired_dedicated += 1
                    else:
                        self._retired_general += 1
            try:
                result = item.fn(*item.args, **item.kwargs)
                item.future.set_result(result)
            except BaseException as e:
                item.future.set_exception(e)

@pytest.mark.anyio
@pytest.mark.limit_consensus_modes(allowed=[ConsensusMode.HARD_FORK_2_0], reason="save time")
async def test_eviction_from_bls_cache(one_node_one_block: tuple[FullNodeSimulator, ChiaServer, BlockTools]) -> None:
    """
    This test covers the case where adding a block to the blockchain evicts
    all its pk msg pairs from the BLS cache.
    """
    full_node_1, _, bt = one_node_one_block
    blocks = bt.get_consecutive_blocks(
        3, guarantee_transaction_block=True, farmer_reward_puzzle_hash=bt.pool_ph, pool_reward_puzzle_hash=bt.pool_ph
    )
    await add_blocks_in_batches(blocks, full_node_1.full_node)
    wt = bt.get_pool_wallet_tool()
    reward_coins = blocks[-1].get_included_reward_coins()
    # Setup a test block with two pk msg pairs
    tx1 = wt.generate_signed_transaction(uint64(42), wt.get_new_puzzlehash(), reward_coins[0])
    tx2 = wt.generate_signed_transaction(uint64(1337), wt.get_new_puzzlehash(), reward_coins[1])
    tx = SpendBundle.aggregate([tx1, tx2])
    await full_node_1.full_node.add_transaction(tx, tx.name(), None, test=True)
    assert len(full_node_1.full_node._bls_cache.items()) == 2
    blocks = bt.get_consecutive_blocks(
        1, block_list_input=blocks, guarantee_transaction_block=True, transaction_data=tx
    )
    # Farming a block with this tx evicts those pk msg pairs from the BLS cache
    await full_node_1.full_node.add_block(blocks[-1], None, full_node_1.full_node._bls_cache)
    assert len(full_node_1.full_node._bls_cache.items()) == 0
