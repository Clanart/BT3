### Title
Users cannot retrieve already-unlocked MGP/mWom tokens while the protocol is paused, causing prolonged freezing of funds - ([File: VLMGP.sol, wombat/mWomSV.sol])

### Summary
`VLMGP.unlock()` and `VLMGP.forceUnLock()` (and their identical counterparts in `mWomSV.sol`) are both gated by the `whenNotPaused` modifier. Once a user has already completed the `startUnlock()` cooldown period, the only two paths to actually retrieve their MGP/mWOM tokens out of the contract are these two functions — and both revert while the contract is paused, exactly mirroring the reported bug class where `lockForAnOrder()`'s `whenNotPaused` guard blocks `increasePosition()` and prevents a user from protecting already-committed funds.

### Finding Description
In `VLMGP.sol`, a user locks MGP via `lock()`/`lockFor()`, then calls `startUnlock(_amountToCoolDown)` to begin a cooldown [1](#0-0) . Once the cooldown period (`slot.endTime`) has passed, the tokens are meant to be freely withdrawable via `unlock()`: [2](#0-1) 

Both `unlock()` and the early-exit `forceUnLock()` (which lets a user exit before cooldown ends by accepting a penalty) require `whenNotPaused`: [3](#0-2) 

There is no alternate, pause-independent path (no `whenPaused` emergency withdrawal exists in `VLMGP.sol`, unlike `MasterMagpie.emergencyWithdraw()` which is intentionally `whenPaused`) to retrieve MGP once it is inside the vlMGP contract. If the contract owner pauses `VLMGP` for maintenance or security reasons — a normal, non-malicious administrative action — any user whose cooldown has already completed (or who needs to force-unlock) is unable to withdraw their tokens for the entire duration of the pause.

The exact same pattern exists in `mWomSV.sol`: [4](#0-3) 

This is structurally identical to the reported bug class: a critical, user-funds-recovering function is blocked by `whenNotPaused`, preventing the user from reacting to a state change (in the original report, an unhealthy position; here, tokens sitting unclaimed post-cooldown) while the protocol is paused.

### Impact Explanation
Users' already-cooled-down MGP/mWOM tokens (which represent unclaimed/claimable principal, not merely yield) become frozen inside the `VLMGP`/`mWomSV` contracts for the entire duration of any pause. If a pause persists beyond 24 hours (e.g., extended incident response, prolonged maintenance), this constitutes a freezing-of-funds condition matching the accepted impact bar. Because `forceUnLock()` is also blocked, users cannot even accept a penalty to escape early during the pause window.

### Likelihood Explanation
Pausing is a normal, expected lifecycle action for this protocol (`pause()`/`unpause()` exist on both contracts) and is intended to be used during incidents or maintenance [5](#0-4) . Any user who has locked tokens and is at any stage of the unlock/cooldown lifecycle at the time of a pause is automatically affected — no special conditions or attacker action are required beyond the normal pause being active.

### Recommendation
Allow `unlock()` (and optionally `forceUnLock()`) to remain callable, or provide a `whenPaused`-only emergency withdrawal path for users whose cooldown has already elapsed, analogous to `MasterMagpie.emergencyWithdraw()`, so that pausing the protocol cannot trap already-vested user funds.

### Proof of Concept
1. Alice calls `VLMGP.lock(amount)` then `VLMGP.startUnlock(amount)`.
2. Cooldown period (`coolDownInSecs`) elapses; `slot.endTime <= block.timestamp`, so Alice's tokens are fully eligible for `unlock()`.
3. Protocol owner calls `VLMGP.pause()` for maintenance/security reasons.
4. Alice calls `unlock(slotIndex)` — reverts due to `whenNotPaused` modifier [6](#0-5) .
5. Alice also cannot call `forceUnLock(slotIndex)` for the same reason [7](#0-6) .
6. Alice's MGP remains locked inside the contract for the full duration of the pause, with no alternative withdrawal mechanism available.
