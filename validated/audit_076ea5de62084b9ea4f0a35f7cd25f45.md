Based on my investigation, I found a concrete analog of the reported input-validation issue in the Kaia governance parameter system.

### Title
Missing validation on `reward.mintingamount` governance vote allows negative minting amount to corrupt block reward accounting - (File: kaiax/gov/param.go)

### Summary
The Sherlock report flags UXD's `setRedeemableSoftCap` for accepting unvalidated critical numeric input (allowing zero, which should be rejected). The analogous pattern exists in Kaia's governance parameter system: `RewardMintingAmount` (`reward.mintingamount`) is registered with `FormatChecker: noopFormatChecker`, meaning any canonicalized `*big.Int` value — including negative numbers — is accepted as valid, unlike its sibling parameter `RewardMinimumStake` which explicitly checks `v.Sign() >= 0`.

### Finding Description
In `kaiax/gov/param.go`, the `Params` map defines format checkers per parameter. `RewardMintingAmount` uses `noopFormatChecker` (always returns `true`): [1](#0-0) 

By contrast, `RewardMinimumStake`, right below it, explicitly validates `v.Sign() >= 0`: [2](#0-1) 

The `bigIntCanonicalizer` used for `RewardMintingAmount` only checks that the string/bytes parse into a `*big.Int` — it does not reject negative values: [3](#0-2) 

The value flows through `NewVoteData` (in `kaiax/gov/headergov/vote.go`), which only calls the `Canonicalizer` and `FormatChecker` for the given parameter — since `FormatChecker` is a no-op for `RewardMintingAmount`, a negative vote value passes validation and becomes a valid, canonical vote: [4](#0-3) 

The resulting `ParamSet.MintingAmount` (set via `ParamSet.Set`, which likewise performs no sign check) is later consumed directly in reward computation: [5](#0-4) [6](#0-5) 

In `kaiax/reward/impl/getter.go`, `MintingAmount` is added directly into the proposer's/reward recipients' reward amounts without any additional guard: [7](#0-6) 

Finally, `FinalizeState` in `kaiax/reward/impl/blockstate.go` applies the computed reward map directly via `state.AddBalance(addr, amount)` for every recipient in the spec: [8](#0-7) 

If `MintingAmount` is negative, the derived `spec.Rewards[addr]` values become negative `*big.Int`s that are passed straight into `state.AddBalance`. This either silently decreases account balances (effectively burning KAIA from the proposer/staker/fund addresses under the guise of a "reward" — undetected supply deflation and unauthorized value movement) or, depending on `AddBalance`'s internal handling of negative deltas, could produce inconsistent/invalid state relative to nodes running different (validated) logic, causing state divergence between honest nodes if the check is patched non-uniformly.

### Impact Explanation
`reward.mintingamount` is a chain-wide governance parameter that directly determines the amount of KAIA "minted" and distributed to the proposer, stakers, and community funds every block. Because there is no protocol-level bound (`FormatChecker` is a no-op), a validly-cast governance vote setting a negative minting amount would be accepted by the vote/param pipeline and propagated into `RewardConfig.MintingAmount`, which is then unconditionally summed into recipient balances via `state.AddBalance`. This is a direct path to unauthorized value movement / accounting corruption in the reward distribution system — precisely the "governance parameters" and "state transition / gas accounting" reachable-path categories called out in scope.

### Likelihood Explanation
This requires a governance vote to be cast and approved through the standard `governance.addvalidator`-style vote mechanism used for all `reward.*` parameters, exactly the same mechanism used for legitimate parameter changes today (e.g., via `GovParam` contract `setParamIn`, as exercised in `tests/gov_contract_test.go`). No additional privilege beyond normal governance-vote submission is required, and unlike `RewardMinimumStake`, there is no defense-in-depth check preventing a negative value from being accepted and activated at the specified block, making this a straightforward, directly reachable input-validation gap analogous to the reported `RageDnDepository.setRedeemableSoftCap` issue.

### Recommendation
Add a `FormatChecker` for `RewardMintingAmount` (and any other unconstrained numeric reward/governance parameters relying on `noopFormatChecker`) that enforces `v.Sign() >= 0`, mirroring the existing check already present for `RewardMinimumStake`:
```go
RewardMintingAmount: {
    Canonicalizer: bigIntCanonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(*big.Int)
        if !ok {
            return false
        }
        return v.Sign() >= 0
    },
    ...
}
```

### Proof of Concept
1. A governance-eligible voter submits a vote (via `GovParam.setParamIn` or header vote mechanism) setting `reward.mintingamount` to a negative value string, e.g. `"-1000000000000000000"`. [4](#0-3)  accepts this because `bigIntCanonicalizer` successfully parses the negative string and `noopFormatChecker` returns `true` unconditionally [1](#0-0) .
2. Once activated at the specified block, `NewRewardConfig` copies this negative value into `RewardConfig.MintingAmount` [6](#0-5) .
3. `getDeferredRewardSimple`/full-reward computation in `getter.go` uses `minted := new(big.Int).Set(config.MintingAmount)` and adds it into proposer/staker/fund amounts [7](#0-6) .
4. `FinalizeState` applies these (now negative) reward deltas via `state.AddBalance(addr, amount)` for every recipient [8](#0-7) , producing unauthorized/unintended balance reductions network-wide every block until governance corrects the parameter.

**Note on completeness:** I did not have access to the exact implementation of `state.AddBalance` (whether it panics, wraps, or silently applies negative deltas) to fully confirm the precise on-chain effect of a negative `amount`; this would need to be verified in `blockchain/state` to determine whether the outcome is silent balance corruption, a panic (causing a chain halt / DoS), or safe rejection. This uncertainty should be resolved with a live Devin session that can trace `AddBalance`'s behavior for negative `*big.Int` inputs.

func NewVoteData(voter common.Address, name string, value any) VoteData {
	param, ok := gov.Params[gov.ParamName(name)]
	if !ok {
		param, ok = gov.ValidatorParams[gov.ParamName(name)]
		if !ok {
			logger.Error("Invalid vote name", "name", name)
			return nil
		}
	}

	cv, err := param.Canonicalizer(value)
	if err != nil {
		logger.Error("Canonicalize error", "name", name, "value", value, "err", err)
		return nil
	}

	if !param.FormatChecker(cv) {
		logger.Error("Format check error", "name", name, "value", value)
		return nil
	}

	return &voteData{
		voter: voter,
		name:  gov.ParamName(name),
		value: cv,
	}
}

// getDeferredRewardSimple is for Simple policy.
func getDeferredRewardSimple(config *reward.RewardConfig, execFee, blobFee *big.Int) (*reward.RewardSpec, error) {
	spec := reward.NewRewardSpec()
	minted := new(big.Int).Set(config.MintingAmount)

	// Non-deferred mode
	if !config.DeferredTxFee {
		var proposer *big.Int
		if config.Rules.IsMagma {
			// In non-deferred mode, no fees to distribute here at the end of block processing.
			// Just distribute the minting reward to the proposer and stop.
			proposer = new(big.Int).Set(minted)
			execFee = big.NewInt(0)
		} else {
			// But Simple policy had a bug where transaction fees were distributed to the proposer here at the end of block processing
			// despite configured to non-deferred mode. To keep the backward compatibility, the buggy behavior retains until Magma.
			proposer = new(big.Int).Add(minted, execFee)
		}
		spec.Minted = new(big.Int).Set(minted)
		// Both exec fees and blob fees are burned during state transition in non-deferred mode,
		// not at finalization. TotalFee/BurntFee are completed by specWithNonDeferredFee (GetBlockReward only).
		spec.TotalFee = execFee // Note that we've set it to 0 for non-deferred + Magma (see above).
		spec.BurntFee = big.NewInt(0)
		spec.Proposer = proposer
		spec.IncRecipient(config.Rewardbase, proposer)
		return spec, nil
