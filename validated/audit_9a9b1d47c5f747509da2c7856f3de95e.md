### Title
Local `GitHubRepository` association is re-bound by mutable owner/name instead of the GitHub repository's immutable ID, allowing silent takeover of a repo's cached identity and permissions - (File: app/src/lib/stores/repositories-store.ts)

### Summary
This is analogous to the Canto `Turnstile` finding: a "registration" record (there, an NFT tied to a smart contract; here, a `GitHubRepository` DB row tied to a local `Repository`) is created once and never truly re-validated against an authoritative, immutable identifier. In Turnstile the binding key was the smart-contract address to an NFT `tokenId`, and burns/transfers silently orphaned it. In Desktop, the binding key from a git remote to a `GitHubRepository` record is `[ownerID + name]` — a mutable pair — not GitHub's immutable numeric repo `id`. When the real repository is deleted and the `owner/name` pair is reused (e.g. after a rename, deletion, or org/user handle change), Desktop transparently "re-associates" the local record with whatever repo the API now returns for that name, carrying forward cached local `id`/permissions state without any user-visible re-registration step.

### Finding Description
`_upsertGitHubRepository` looks up the existing DB row purely by `[ownerID+name]`: [3](#0-2) 
and if found, keeps the existing local `id` and merges/overwrites the `cloneURL`, `htmlURL`, and `permissions` fields from whatever `IAPIFullRepository` was just fetched for that owner/name: [4](#0-3) 

The refresh path `repositoryWithRefreshedGitHubRepository`/`matchGitHubRepository` re-derives the "match" purely from the git remote URL's hostname/owner/name, using whichever account has a matching endpoint hostname — again with no check against a previously-known, immutable repo identity: [5](#0-4) [6](#0-5) 

The developers themselves flag the absence of any invalidation/clearing mechanism for this association: [7](#0-6) 

Because the key is `owner.login + repo.name` and not GitHub's stable numeric `id` (which isn't even part of `IDatabaseGitHubRepository`), there is no way for Desktop to detect that "my-user/my-repo" today refers to a completely different underlying repository than it did yesterday. The `permissions` field — used elsewhere to gate whether push/write actions are offered — is refreshed from whatever repo currently occupies that owner/name slot, and any fields the new API response doesn't include (e.g. `permissions` when using the "light" upsert) fall back to the stale, previously cached value: [8](#0-7) 

### Impact Explanation
An attacker who can cause a `owner/name` slot to be reused (classic GitHub repo-name-squatting after the legitimate repo is deleted, or an org member renaming/deleting and an attacker re-creating a repo with the identical owner+name before Desktop's cache is invalidated) can have Desktop silently swap the local `GitHubRepository` record to point at the attacker-controlled repository — same local DB row `id`, same cached permission bits from the old repo, no prompt to the user. Because the git remote URL itself is unchanged (still `owner/name`), the working copy will keep fetching/pushing against whatever now lives at that GitHub location, and Desktop's UI/state (PR lists, checks, branch protection, "you have write access" affordances) will reflect the attacker's repository while presenting it with the trust level of the original. This can lead to silent corruption of what the user pushes (pushing to attacker's repo believing it's their own) or exposure of local commits/PR content to an attacker-controlled endpoint under the account's existing push credentials.

### Likelihood Explanation
Requires the attacker to control a GitHub API object (the repository at a specific owner/name after the original is removed/renamed), which is explicitly in-scope per the task's valid-impact criteria. The likelihood is moderated by the fact that name-reuse race windows on GitHub are narrow and org/user renames typically require some cooperation or timing, but Desktop's own comment (`https://github.com/desktop/desktop/issues/1144`) confirms this exact class of stale-association bug is a known, unaddressed gap rather than a hypothetical.

### Recommendation
Store and validate against the GitHub API's immutable numeric repository `id` (already returned in `IAPIRepository`/`IAPIFullRepository`) as the primary key/consistency check for `GitHubRepository` records, in addition to `[ownerID+name]`. When re-matching or refreshing, if the numeric `id` returned for a given `owner/name` differs from the previously stored `id`, treat this as a new repository: clear cached permissions, branch-protection state, and PR data, and surface a re-registration/confirmation prompt to the user before continuing to fetch/push.

### Proof of Concept
1. Clone `github.com/victim-org/project` in Desktop; Desktop calls `upsertGitHubRepository`, which stores a row keyed by `[ownerID(victim-org), "project"]` with the real repo's `cloneURL`/`permissions` (e.g. `push: true`). [9](#0-8) 
2. `victim-org/project` is deleted (org loses the repo, or it's transferred/renamed away).
3. An attacker creates a new repo at the exact same `victim-org/project` slot (e.g. after the org name becomes available, or a compromised/former member recreates it).
4. Desktop periodically calls `repositoryWithRefreshedGitHubRepository` → `matchGitHubRepository` → `api.fetchRepository(owner, name)`, which now resolves to the attacker's repo, and `upsertGitHubRepository` overwrites the same local DB row's `cloneURL`, `htmlURL`, and `permissions` in place, with no diffing against a previous immutable identity. [10](#0-9) 
5. The user, still trusting their local `victim-org/project` entry, continues committing and pushing; their pushes and any "Open on GitHub"/PR/branch-protection interactions now silently target the attacker's repository, with no re-registration prompt shown.

**Uncertainty/limitations:** I was not able to fully trace every consumer of the `permissions` field (e.g. exact UI push-affordance gating logic in `app.tsx`/`filter-changes-list.tsx`) within the available index to confirm the precise blast radius of stale permission reuse; a background Devin session with full repo access would be needed to enumerate all downstream consumers of `GitHubRepository.permissions` and `cloneURL` to fully bound the impact.

    // if the parent of a repository has a parent (confusing, right?)
    //
    // We do all this to ensure that we only set the parent to null when we know
    // that it needs to be cleared. Otherwise we could have a scenario where
    // we've got a repository network where C is a fork of B and B is a fork of

    //
    // Since going from having a parent to not having a parent is incredibly
    // rare (deleting a forked repository and creating it from scratch again
    // with the same name or the parent getting deleted, etc) we assume that the

    const parentID = ignoreParent

      : parent?.dbID ?? null

    const updatedGitHubRepo: IDatabaseGitHubRepository = {

      htmlURL: gitHubRepository.html_url,
      cloneURL: gitHubRepository.clone_url,

      lastPruneDate: existingRepo?.lastPruneDate ?? null,
      issuesEnabled: gitHubRepository.has_issues,
      isArchived: gitHubRepository.archived,

    if (existingRepo !== undefined) {

      // we can skip writing to the database and (more importantly) avoid
      // telling store consumers that the repo store has changed.
      if (shallowEquals(existingRepo, updatedGitHubRepo)) {
        return this.toGitHubRepository(existingRepo, owner, parent)

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
