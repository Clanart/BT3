`internal_withdraw` is a state-changing/broadcasting RPC that lets any caller who can reach the operator's gRPC endpoint trigger a real BTC payout without any aggregator/verification signature check, unlike `withdraw`, which enforces the EIP-712 verification signature from the configured `aggregator_verification_address` when that address is set.

### Title
Unauthenticated `internal_withdraw` RPC allows anyone to trigger a fronted payout without aggregator authorization - ([File: core/src/rpc/operator.rs])

### Summary
`ClementineOperator::internal_withdraw` [1](#0-0)  parses withdrawal parameters and immediately calls `self.operator.withdraw(...)` to build and return a signed payout transaction, without any verification-signature check. The sibling `withdraw` RPC, by contrast, requires and validates a verification signature recovered against `self.operator.config.aggregator_verification_address` before calling the same `self.operator.withdraw(...)` [2](#0-1) .

### Finding Description
The proto documents `InternalWithdraw` as "intended for operator's own use, so it doesn't include a signature from aggregator" [3](#0-2) . This is a documented design assumption, not an access-control check enforced in code: the gRPC method itself has no caller-identity check, no mTLS/auth guard visible at this layer, and no re-derivation of the "intended caller" (i.e., the operator's own process) at the handler level. Anyone able to reach the operator's `InternalWithdraw` endpoint over the network can invoke `operator.withdraw(...)` directly and obtain (and, if automation is enabled downstream, cause broadcast of) a real payout transaction fronting a withdrawal — the same effect as the authenticated `Withdraw` path, but bypassing the "the party it is meant for" (the aggregator/operator itself) authorization boundary that `Withdraw` explicitly enforces.

The equality this breaks: the party permitted to trigger `operator.withdraw()` (intended: the operator itself, invoking its own internal endpoint locally) should equal the actual caller of `InternalWithdraw` over gRPC. Because the check is absent in `internal_withdraw`, any network caller = the intended caller, which is false in general.

### Impact Explanation
If `InternalWithdraw` is reachable (e.g., exposed on the same network interface as other operator RPCs, or not strictly firewalled to localhost), an unauthorized caller can force the operator to build and (with automation enabled) queue/broadcast a payout transaction for any registered withdrawal, i.e., an unauthenticated state-changing/broadcasting call — one of the listed High-impact categories. This does not itself mint funds or move BTC out of the vault beyond what a legitimate withdrawal would (the same custody checks inside `operator.withdraw` still apply, e.g., withdrawal UTXO/output validation), so it does not rise to a Critical BTC-leaving-vault-without-fronted-withdrawal scenario by itself, but it removes the aggregator-authorization gate that `Withdraw` enforces, letting a third party dictate when/whether the operator fronts a payout — potentially forcing early, unwanted fund commitment by the operator.

### Likelihood Explanation
Depends entirely on network exposure of the operator's gRPC surface. The rules exclude findings that depend on "a deployment ignoring the documented configuration" — and the proto comment explicitly documents that `InternalWithdraw` is meant only for the operator's own (presumably localhost/trusted) use. Since the code has no enforcement of that intent (no auth check at all in the handler, unlike `Withdraw`), this is a code-level absence of access control rather than a deployment misconfiguration, but its exploitability is conditional on the endpoint being network-reachable by an unprivileged party in a given deployment.

### Recommendation
Add the same aggregator-verification-signature check (or equivalent authentication/authorization, e.g., mTLS-bound caller identity) to `internal_withdraw` as is already present in `withdraw`, or otherwise restrict `InternalWithdraw` to a genuinely local/trusted transport so the code itself enforces the "operator's own use" invariant instead of relying on deployment convention.

### Proof of Concept
1. Obtain network access to an operator's gRPC endpoint (`ClementineOperator` service).
2. Call `InternalWithdraw` with a `WithdrawParams` referencing a valid, unspent withdrawal outpoint and signature (as would be produced by the legitimate user flow) — no verification signature is required, per [1](#0-0) .
3. Compare with the `Withdraw` RPC, which requires `verification_signature` matching `aggregator_verification_address` when configured, per [4](#0-3) .
4. The operator returns/broadcasts a signed payout transaction via `internal_withdraw` even though the caller is not the aggregator and provided no proof of authorization.

**Note on scope/confidence**: I could not fully trace whether the gRPC server layer applies any transport-level authentication (e.g., mTLS client-cert restriction) uniformly across all operator RPCs, which would materially affect exploitability; this was not found within `core/src/rpc/operator.rs` or the reachable proto/handler code inspected. If such a transport-level restriction exists and is enforced in code (not just documentation) to bind callers to the aggregator/operator itself, this finding would not hold.

    async fn internal_withdraw(
        &self,
        request: Request<WithdrawParams>,
    ) -> Result<Response<RawSignedTx>, Status> {
        let (withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount) =
            parser::operator::parse_withdrawal_sig_params(request.into_inner())?;

        tracing::warn!("Called internal_withdraw with withdrawal id: {:?}, input signature: {:?}, input outpoint: {:?}, output script pubkey: {:?}, output amount: {:?}", withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount);

        let payout_tx = self
            .operator
            .withdraw(
                withdrawal_id,
                input_signature,
                input_outpoint,
                output_script_pubkey,
                output_amount,
            )
            .await?;

        Ok(Response::new(RawSignedTx::from(&payout_tx)))
    }
