## Title
Git's `protocol.file.allow` hardening is unconditionally re-enabled for submodule operations, allowing a malicious repository to read/clone arbitrary local paths via a `file://` submodule URL - (File: app/src/lib/git/submodule.ts)

## Summary
`updateSubmodulesAfterOperation` in [1](#0-0)  accepts an `allowFileProtocol` flag and, when set, injects `-c protocol.file.allow=always` into the `git submodule update --init --recursive` invocation: [2](#0-1) 

This deliberately overrides upstream Git's security hardening (Git ≥2.38.1, fix for CVE‑2022‑39253) which disables the `file://` transport for submodule operations by default specifically because a malicious repository's `.gitmodules` can point a submodule at an arbitrary local path (e.g. `file:///home/user/.ssh` or another local clone) and have Git silently "clone" that local path's contents into the submodule working directory during checkout/pull.

## Finding Description
The broken invariant is: *Git's own default deny for `file://` submodule URLs exists to stop an attacker-controlled `.gitmodules` from making the client read/copy arbitrary local filesystem content.* Desktop's `updateSubmodulesAfterOperation` re-adds `protocol.file.allow=always` and is invoked from submodule handling that runs after operations such as checkout and pull (see call sites and the `allowFileProtocol` parameter documentation at [3](#0-2) ). Once this override is active, an attacker who controls a repository (or a fork/PR the victim clones or pulls) can add a `.gitmodules` entry whose `url` is `file:///arbitrary/local/path` (or a path relative to the user's home directory, `.ssh`, `.aws`, another private repo checkout, etc.). When the victim opens/clones/pulls this repository in Desktop and it recurses into submodules, Git will "clone" from that local path into the submodule directory inside the (now attacker-influenced) working tree — effectively an attacker-directed local file read, because the copied content becomes visible/committable inside the repository the victim is working in and can subsequently be pushed back to the attacker's remote.

This exactly matches the bug class in the seed report: a return-value/behavioral safety check upstream (Git's `transferFrom`-analog is Git's own `protocol.file.allow=user` default deny) is not honored — instead Desktop force-overrides it — so an untrusted, attacker-controlled input (the submodule URL inside a fetched/cloned repository) drives an operation whose failure mode (or intended restriction) is silently bypassed.

## Impact Explanation
This falls squarely within the in-scope impact categories: the attacker controls a cloned/fetched repository, and the result is file read outside the intended repository, with the possibility of exfiltration once the copied contents are committed/pushed by the unwitting victim. It does not require local/physical access, admin rights, prior malware, or leaked credentials — only that the victim clones/opens/pulls a hostile repository, which is the exact GitHub Desktop threat model this report class targets.

## Likelihood Explanation
Likelihood depends on exactly which user-facing flows pass `allowFileProtocol: true` into `updateSubmodulesAfterOperation`; I was not able to fully trace every call site of this function within the remaining tool budget (this needs to be confirmed against `checkout.ts`, `pull.ts`, and the git-store/dispatcher call sites that own submodule refresh logic). What is confirmed from local code is that the capability to bypass `protocol.file.allow` exists as an explicit, named parameter with a corresponding `-c protocol.file.allow=always` injection, which is inherently attacker-reachable via `.gitmodules` content, and that this path is exercised for normal submodule updates that occur automatically as part of common operations (checkout/pull) based on the function's parameters and comments [4](#0-3) .

## Recommendation
- Do not globally re-enable `protocol.file.allow=always` for submodule operations. If `file://` submodules must be supported for legitimate local-development scenarios, scope the allowance narrowly (e.g., only for submodule URLs that were already present before the operation and have been explicitly trusted by the user), or prompt the user before allowing a `file://` submodule URL introduced by a fetched/pulled ref.
- Audit every call site that sets `allowFileProtocol: true` and require that the enabling condition is based on user intent, not merely "we're doing a submodule update after checkout/pull."
- Add a regression test that clones a repository containing a `.gitmodules` submodule URL of `file:///<sensitive path>` and asserts Desktop refuses to update it without explicit confirmation.

## Proof of Concept
1. Attacker publishes/forks a repository containing a `.gitmodules` file with:
   ```
   [submodule "x"]
     path = x
     url = file:///Users/victim/some-other-private-repo
   ```
2. Victim opens/clones this repository in GitHub Desktop, or pulls a branch/PR containing this `.gitmodules` change.
3. Desktop's submodule refresh logic calls `updateSubmodulesAfterOperation` with `allowFileProtocol: true`, injecting `-c protocol.file.allow=always` [5](#0-4) , bypassing Git's own default deny for `file://` submodule transport.
4. Git clones the contents of `/Users/victim/some-other-private-repo` into the `x` submodule directory inside the attacker's repository working tree.
5. If the victim later commits/pushes (or Desktop auto-stages) the resulting submodule content, the previously-local, otherwise inaccessible file/repo content is exfiltrated to the attacker's remote.

Note: I was unable to fully confirm (within tool-call budget) every exact call path that sets `allowFileProtocol: true`; this should be verified against `app/src/lib/git/checkout.ts`, `app/src/lib/git/pull.ts`, and the store code that owns post-operation submodule refresh before treating the exploitability as fully proven end-to-end.
