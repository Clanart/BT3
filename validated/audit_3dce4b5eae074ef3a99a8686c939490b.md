### Title
Desktop bypasses Git's `protocol.file.allow` submodule protection during submodule initialization, allowing a malicious `.gitmodules` to exfiltrate arbitrary local files into the tracked working tree - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` unconditionally appends `-c protocol.file.allow=always` to `git submodule update --init --recursive` whenever the caller passes `allowFileProtocol=true` [1](#0-0) . This override defeats Git's own hardening (the `protocol.file.allow=user`/deny-by-default behavior introduced after CVE-2022-39253) that normally prevents a repository from silently causing a local `file://` "clone" of an arbitrary path on disk via a submodule URL in `.gitmodules`.

### Finding Description
`checkoutCommit` and (by the same pattern) `checkoutBranch` accept an `allowFileProtocol` boolean that is forwarded straight into `updateSubmodulesAfterOperation` [2](#0-1) . When set, submodule initialization runs with `protocol.file.allow=always`, which tells Git to honor `file://` (and bare local path) submodule URLs without restriction [3](#0-2) .

This is exercised in the "uninitialized submodule" checkout path — confirmed by the test that explicitly checks out a branch containing a previously-uninitialized submodule with `allowFileProtocol=true`, causing Desktop to run `git submodule update --init --recursive` with the file-protocol restriction disabled [4](#0-3) . A `.gitmodules` file is fully attacker-controlled content that arrives via a fetched/cloned remote repository or a branch introduced by a fork/PR. If that file declares a submodule URL of `file:///absolute/path/on/victim/machine` (e.g. a parent directory, `~/.ssh`, or another local repository containing credentials), a normal Git client would refuse this by default; Desktop's override removes that refusal specifically for the "initialize submodule during checkout" workflow.

### Impact Explanation
Because the "clone" happens locally with the protection disabled, Git will copy the contents of the attacker-chosen local path into the submodule directory inside the user's working tree. Those files then appear as ordinary submodule content in Desktop's Changes view. A user who is not scrutinizing an unfamiliar `.gitmodules` entry can stage and commit that submodule reference, and the pointed-to submodule commit (containing copied local file contents) can be pushed to any remote the user has access to — silently exfiltrating local file data (potentially credentials, SSH keys, or other sensitive files) into a commit the user unwittingly pushes. This matches "silent corruption of what the user commits or pushes" and "credential/token exfiltration" in the accepted impact categories, since the trigger is entirely a malicious value inside a fetched/cloned repository's `.gitmodules`.

### Likelihood Explanation
The path requires the victim to check out a branch/commit from a repository they don't control (fork, PR branch, or a repo they cloned) that introduces or contains a not-yet-initialized submodule with a crafted `file://` URL, and for Desktop's submodule-initialization code path to run with `allowFileProtocol=true`. I confirmed this flag is exercised for the "uninitialized submodule" scenario in the test suite [5](#0-4) , which corresponds to an ordinary, non-exotic user action (switching to/checking out a branch containing a submodule that hasn't been cloned locally yet) — not an unusual or contrived user step. I was not able to fully verify every dispatcher/UI call site that sets `allowFileProtocol=true` versus `false` under my remaining search budget, so the exact conditions under which the flag defaults to `true` in the full application flow (versus only in tests) should be independently confirmed.

### Recommendation
Do not blanket-enable `protocol.file.allow=always` for submodule initialization. Instead, only allow `file://` submodule URLs when the target path is verified to resolve within the already-trusted local clone/working directory tree (mirroring `sanitizeCloneName`/`resolveWithin`-style containment checks already used elsewhere in the codebase, e.g. `app/src/lib/remote-parsing.ts` and `app/src/ui/dispatcher/dispatcher.ts`'s `resolveWithin` usage), and warn/prompt the user before initializing a submodule whose URL points outside the repository's own remote host.

### Proof of Concept
1. Attacker creates a repository/branch with a `.gitmodules` file:
```
[submodule "leak"]
    path = leak
    url = file:///Users/victim/.ssh
```
2. Victim clones/fetches this repository or checks out the malicious branch/PR in GitHub Desktop while the submodule is not yet initialized locally.
3. Desktop calls `checkoutBranch`/`checkoutCommit` → `updateSubmodulesAfterOperation(..., allowFileProtocol=true)` → `git -c protocol.file.allow=always submodule update --init --recursive` [6](#0-5) .
4. Git copies the contents of `/Users/victim/.ssh` into the `leak/` submodule directory inside the working tree.
5. Victim stages/commits/pushes, exfiltrating the copied files to any remote they push to.
