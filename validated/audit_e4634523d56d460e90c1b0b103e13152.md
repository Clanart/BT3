### Title
Data Layer mirror coins allow arbitrary-URL SSRF against subscribing peers - (File: `chia/data_layer/data_layer_wallet.py`, `chia/data_layer/data_layer.py`, `chia/data_layer/download_data.py`)

### Summary
Any user can pay a small fee to create a Chia "mirror" coin that advertises an arbitrary URL for *any* DataLayer `launcher_id`, including one they don't own. Any peer that subscribes to/tracks that `launcher_id` will automatically add the attacker's URL to its subscription list and periodically issue outbound HTTP GET requests to it from its own `DataLayer` background sync process, with no validation of scheme, host, or destination. This is the same bug class as the reported `zrok` `ProxyShare` SSRF: an attacker-controlled destination is fed directly into an outbound HTTP client without restricting it to a trusted target.

### Finding Description
`DataLayerWallet.create_new_mirror()` builds a spend that creates a coin with the `create_mirror_puzzle()` puzzle hash and memos `[launcher_id, *urls]`, with no check that `launcher_id` belongs to a store the spender owns: [1](#0-0) 

Anyone can submit such a spend bundle for any `launcher_id` value and any URL string via the `dl_new_mirror` RPC/CLI path: [2](#0-1) 

When any node is tracking that `launcher_id` (i.e. subscribed as a DataLayer client), `DataLayerWallet.coin_added()` picks up the new mirror coin purely because the launcher id is tracked — there is no check that the mirror was created by the store's owner, nor any URL scheme/host allow-listing: [3](#0-2) 

The `DataLayer` service coordinator then blindly pulls every mirror URL for the store and stores it as a subscription source, again with no filtering by trust/ownership: [4](#0-3) 

During the periodic sync loop, `fetch_and_validate()` randomly picks one of these attacker-supplied server URLs and calls `insert_from_delta_file()`/`download_file()`, which ultimately issues a raw `aiohttp` GET to `server_info.url + "/" + filename` with no restriction on the target host (localhost, link-local/cloud-metadata addresses, internal RPC ports, etc.): [5](#0-4) [6](#0-5) 

This mirrors the reported vulnerability class exactly: a value that should be constrained to a trusted target (the report's `path`/`urljoin` target, here the mirror `url`) is instead attacker-controlled and passed straight into an outbound request.

### Impact Explanation
A single low-cost on-chain spend lets any user cause every peer subscribed to (or that later subscribes to) a targeted DataLayer store to make outbound HTTP requests to an attacker-chosen destination — including internal-only services, localhost RPC/admin ports, or cloud metadata endpoints reachable from the DataLayer host. This is a genuine SSRF primitive against any DataLayer client/service operator, reachable purely by submitting a spend bundle (no malicious peer/node/harvester access required), and it also creates a straightforward denial-of-service vector: pointing the mirror at a slow/hanging endpoint stalls `fetch_and_validate()` calls inside the periodic `periodically_manage_data()` sync loop for that DataLayer instance.

### Likelihood Explanation
Likelihood is high: creating a mirror coin requires only a small XCH fee/amount and a normal wallet spend, with the `launcher_id` and `urls` fully attacker-controlled and no ownership check enforced anywhere in the mirror-creation, coin-tracking, or subscription-sync code paths.

### Recommendation
- Restrict mirror URLs to schemes/hosts appropriate for delta-file mirrors (e.g. disallow `localhost`/private/link-local ranges, or require an explicit allow-list/opt-in per store) before they are added to `DataStore` subscriptions.
- Only trust mirror coins whose creator can be verified/authorized for the given `launcher_id`, or clearly mark untrusted mirrors and require explicit user opt-in before the DataLayer service downloads from them.
- Apply SSRF-hardening to `http_download()`/`get_downloader()`/`get_plugin_info()` (resolve and validate destination IPs, block loopback/link-local/multicast ranges, enforce timeouts) similar to the fix pattern used for the reported `zrok` issue.

### Proof of Concept
1. Attacker (any wallet, no special privileges) runs `chia data add_mirror --id <victim_launcher_id> --url http://127.0.0.1:8562/get_root -a 1 -m <fee>` (or the equivalent `dl_new_mirror` RPC call), where `victim_launcher_id` is a DataLayer store id the attacker does not own.
2. Any peer that tracks/subscribes to `victim_launcher_id` (e.g. a wallet/DataLayer client interested in that store) picks up the new mirror via `coin_added()`/`update_subscriptions_from_wallet()`.
3. During its next `periodically_manage_data()` cycle, that peer's `DataLayer.fetch_and_validate()` selects the attacker's URL and issues an `aiohttp` GET request to it via `http_download()`, causing the victim's process to make an outbound HTTP request to whatever host/port the attacker specified (e.g., an internal service, localhost RPC port, or cloud metadata IP).

        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> DLNewMirrorResponse:
        """Add a new on chain message for a specific singleton"""
        if self.service.wallet_state_manager is None:

        dl_wallet = await self.service.wallet_state_manager.get_dl_wallet()
        async with self.service.wallet_state_manager.lock:

                request.launcher_id,
                request.amount,
                Mirror.encode_urls(request.urls),
                action_scope,
                fee=request.fee,
                extra_conditions=extra_conditions,

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
