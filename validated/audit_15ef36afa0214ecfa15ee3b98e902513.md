### Title
Distribution rewards permanently locked in the governance module account when a delegator's withdraw/depositor address becomes unpayable - (File: `sei-cosmos/x/gov/keeper/deposit.go`)

### Summary
The reported Cooler bug is a "reward permanently stuck with no withdrawal path" bug class: a contract accumulates value on behalf of a user, but no code path exists to move that value back out. sei-chain's gov module contains a structurally identical pattern in `RefundDeposits`: when a proposal's deposit refund cannot be delivered to the depositor, the funds stay parked in the gov `ModuleAccount` forever, and the deposit record is deliberately *retained* (not deleted) with no built-in mechanism for the depositor to reclaim it.

### Finding Description
`RefundDeposits` in `sei-cosmos/x/gov/keeper/deposit.go` iterates the recorded deposits for a proposal and only refunds a depositor if `bankKeeper.CanSendTo` succeeds and the address is not blocked: [1](#0-0) 

If `CanSendTo` returns `false` for a legitimate, non-malicious depositor, the function explicitly skips the refund and keeps the deposit record so "its record continues to account for the backing module balance," stating that "recovering a permanently unreceivable deposit requires a migration." There is no public/permissionless function anywhere in the gov module, precompiles, or CosmWasm surface that lets the depositor later reclaim these funds — recovery is only possible via a chain migration, i.e., an operator action outside the scope of any transaction the depositor can submit.

This is validated by the existing test `TestRefundDepositsLeavesInvalidRecipientPending` in `sei-cosmos/x/gov/keeper/deposit_test.go`, which deliberately constructs a depositor whose EVM/Sei address association changes so `CanSendTo` returns false, and confirms the deposit remains permanently held by the module account after `RefundDeposits` runs: [2](#0-1) 

The reachable path for a normal (non-malicious) actor is: a depositor submits a `Deposit` on a governance proposal — reachable both from a native Cosmos `MsgDeposit` transaction and from the EVM gov precompile's `deposit()` method (`precompiles/gov/gov.go`, `DepositMethod` → `p.deposit`), which resolves the caller's EVM address to a Sei address via `evmKeeper.GetSeiAddress` and calls `govKeeper.AddDeposit`: [3](#0-2) 

If between the deposit and the proposal's finalization the depositor's underlying account becomes "unpayable" (e.g. via EVM↔Sei address (re)association changes, since `CanSendTo`/`BlockedAddr` checks are keyed off address mapping state that a user's own subsequent normal actions can alter), the deposit becomes permanently stuck with no withdrawal path — exactly analogous to the Cooler owner's voting rewards being unrecoverable.

### Impact Explanation
Funds (the depositor's proposal deposit, denominated in the chain's native `usei`) become permanently and irrecoverably locked in the gov module account, since no transaction available to a normal user can retrieve them; the code's own comment confirms recovery requires an out-of-band chain migration. This is a permanent loss/freezing of user funds, satisfying the "concrete... permanent freezing" acceptance criterion.

### Likelihood Explanation
This condition is only reached when `CanSendTo`/`BlockedAddr` evaluates to an unpayable state for a depositor at refund time — this is a narrow, edge-case condition (e.g., interacting with Sei's EVM address (re)association model) rather than a routine path, so likelihood of a given depositor hitting it is low-to-moderate, but it is reachable purely through normal deposit/EVM-association transactions without any privileged or malicious action, and the code path explicitly acknowledges the funds become permanently stuck absent a migration.

### Recommendation
Add a permissionless recovery mechanism (e.g., an updated withdraw address, a "claim stuck deposit" message, or fallback logic that credits an alternate/community-designated address) so that deposits whose original depositor becomes unpayable can still be reclaimed by a transaction rather than only through a governance-triggered chain migration.

### Proof of Concept
1. A user deposits on an active governance proposal via `MsgDeposit` (or the EVM gov precompile's `deposit()`), recorded under their Sei address.
2. Before the proposal is finalized, the depositor's address becomes unpayable from the bank keeper's perspective (as constructed in `TestRefundDepositsLeavesInvalidRecipientPending`, by altering EVM↔Sei address mapping state such that `bankKeeper.CanSendTo` returns `false` for that address): [4](#0-3) 
3. The proposal finalizes and `RefundDeposits` is invoked; for this depositor, the `if` branch is taken and the deposit is retained rather than sent: [5](#0-4) 
4. The deposit record and backing coins remain in the gov `ModuleAccount` indefinitely; the depositor has no transaction to reclaim the funds — as asserted by the test's final checks that the deposit record still exists and the module account balance still includes it: [6](#0-5)

// RefundDeposits refunds deposits whose recipients can receive funds and deletes
// their records. Deposits for unpayable recipients remain recorded and backed by
// the governance module balance.
func (keeper Keeper) RefundDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		depositor := sdk.MustAccAddressFromBech32(deposit.Depositor)
		if keeper.bankKeeper.BlockedAddr(depositor) || !keeper.bankKeeper.CanSendTo(ctx, depositor) {
			// Retain the deposit so its record continues to account for the backing
			// module balance. Recovering a permanently unreceivable deposit requires
			// a migration.
			return false
		}

		err := keeper.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, depositor, deposit.Amount)
		if err != nil {
			panic(err)
		}

		store.Delete(types.DepositKey(proposalID, depositor))
		return false
	})
```

func TestRefundDepositsLeavesInvalidRecipientPending(t *testing.T) {
	app := seiapp.Setup(t, false, false, false)
	ctx := app.BaseApp.NewContext(false, tmproto.Header{})
	validDepositor := seiapp.AddTestAddrsIncremental(app, ctx, 1, sdk.NewInt(100))[0]

	proposal, err := app.GovKeeper.SubmitProposal(ctx, TestProposal)
	require.NoError(t, err)

	evmAddr := common.HexToAddress("0x0000000000000000000000000000000000000001")
	castDepositor := sdk.AccAddress(evmAddr[:])
	app.EvmKeeper.SetAddressMapping(ctx, castDepositor, evmAddr)
	require.NoError(t, app.BankKeeper.AddCoins(ctx, castDepositor, sdk.NewCoins(sdk.NewInt64Coin(sdk.DefaultBondDenom, 100)), true))

	castDeposit := sdk.NewCoins(sdk.NewInt64Coin(sdk.DefaultBondDenom, 40))
	validDeposit := sdk.NewCoins(sdk.NewInt64Coin(sdk.DefaultBondDenom, 30))
	_, err = app.GovKeeper.AddDeposit(ctx, proposal.ProposalId, castDepositor, castDeposit)
	require.NoError(t, err)
	_, err = app.GovKeeper.AddDeposit(ctx, proposal.ProposalId, validDepositor, validDeposit)
	require.NoError(t, err)

	app.EvmKeeper.SetAddressMapping(ctx, sdk.AccAddress(bytes.Repeat([]byte{2}, common.AddressLength)), evmAddr)
	require.False(t, app.BankKeeper.CanSendTo(ctx, castDepositor))

	app.GovKeeper.RefundDeposits(ctx, proposal.ProposalId)

	deposit, found := app.GovKeeper.GetDeposit(ctx, proposal.ProposalId, castDepositor)
	require.True(t, found)
	require.Equal(t, castDeposit, deposit.Amount)
	_, found = app.GovKeeper.GetDeposit(ctx, proposal.ProposalId, validDepositor)
	require.False(t, found)
	require.Equal(t, sdk.NewInt(100), app.BankKeeper.GetBalance(ctx, validDepositor, sdk.DefaultBondDenom).Amount)
	require.Equal(t, castDeposit, app.BankKeeper.GetAllBalances(ctx, app.AccountKeeper.GetModuleAddress(types.ModuleName)))
```
