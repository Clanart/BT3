## Title
`_findPullRequestBranch`/`_checkoutPullRequest` checks out a fork's current branch tip without verifying it matches the reviewed `PullRequestRef.sha`, silently checking out attacker-rewritten history - (`app/src/lib/stores/app-store.ts`)

### Summary
The external report's core flaw is: the system caches/reviews a piece of chain state at a point in time, then later acts on "the tip" without re-verifying that tip against the previously observed value, so an attacker who can rewrite history underneath gets its new (unreviewed) state silently accepted. GitHub Desktop has a structurally identical gap in its pull-request checkout flow: it resolves a PR's head to whatever the remote/fork branch currently points to, never comparing it to the `sha` on the `PullRequestRef` object that was fetched and shown to the user earlier.

### Finding Description
`PullRequestRef` stores an explicit `sha` for both `head` and `base` at the time the PR was fetched from the API [1](#0-0) . This `sha` is the value the user actually reviewed (via PR quick view, diff, checks, etc.), but it is never used as an integrity anchor.

When the user checks out a PR, `_checkoutPullRequest` delegates to `_findPullRequestBranch`, which:
1. Finds or creates a remote for the fork (`headCloneUrl`),
2. Looks for a local branch tracking `remote/headRefName`, or a remote-tracking branch with that name,
3. If not found, fetches the remote and re-checks by name only,
4. Creates/uses a branch pointed at whatever `remoteRef` currently resolves to. [2](#0-1) 

At no point is `pullRequest.head.sha` compared against the SHA actually resolved for `remoteRef` before or after the fetch. The lookup is purely by ref name (`headRefName`), and `fetchRefspec`/`fetchRemote` simply pulls whatever the remote currently advertises for that branch [3](#0-2) . If a fork owner (an untrusted, unprivileged actor who owns the PR head repo) force-pushes new commits to that branch between the time the PR was reviewed/opened and the time the Desktop user clicks "checkout this PR," Desktop will silently fetch and check out the new tip with no warning, no diff-based reconciliation, and no detection that "the reviewed head no longer exists."

This is the direct analog of the reported bug: just as `eth-bridge` trusts the current chain tip without checking it against the block hash it expects at that height, Desktop trusts the current branch tip without checking it against the `head.sha` it already has on record for that PR.

### Impact Explanation
A malicious or compromised fork owner can present a PR with benign content, wait for review/approval signals to accumulate (or simply for time to pass), then force-push different code to the same head ref. Since Desktop's checkout path resolves purely by ref name and never pins to `head.sha`, the developer's "checkout PR #N" action (in-app button, or via `x-github-client://openPullRequest` deep link handled in `openPullRequestFromUrl` [4](#0-3) ) silently materializes the attacker's new, unreviewed commits into the user's working directory. Depending on what the developer does next (build, run scripts, commit on top, push), this can lead to local code execution of attacker-controlled code or corruption of the branch the user believes they're working from — matching the "silent corruption of what the user commits/pushes" impact class.

### Likelihood Explanation
This requires only that the attacker control a PR's head branch in their own fork (an ordinary, unprivileged GitHub capability) and that the victim checkout the PR through Desktop after the force-push — no local access, no malware, no leaked credentials. Given PR review workflows commonly have a delay between initial review and checkout/merge action, and Desktop offers one-click "Checkout" and deep-link ("Open in Desktop") flows that always resolve by ref name, the precondition is realistic for any project accepting external contributions.

### Recommendation
- Short term: When checking out a PR, after fetching, compare the resolved branch tip SHA to `pullRequest.head.sha`. If they differ, warn the user ("This pull request's branch has changed since it was last viewed — N new commit(s) found") before checking out, similar to the existing force-push confirmation dialog used elsewhere in the rebase flow [5](#0-4) .
- Long term: Persist the last-seen head SHA per PR and surface a diff/changed-commits view when it changes, so users can explicitly acknowledge history rewrites before code lands in their working directory, mirroring the "reorg-handling strategy" recommended for eth-bridge.

### Proof of Concept
1. Attacker opens PR #1 from fork `attacker/repo:feature` with benign commit `A`.
2. Victim reviews PR #1 in Desktop; `PullRequestRef.sha` for `head` is recorded as `A`.
3. Attacker force-pushes new commit `B` (with malicious build script or destructive changes) to `feature`, replacing `A`.
4. Victim clicks "Checkout this PR" (or opens the `x-github-client://openPullRequest/...` deep link) days later.
5. `_findPullRequestBranch` fetches the fork remote and resolves `origin-fork/feature` to `B`, then checks it out via `_checkoutBranch` — no comparison to the originally recorded `A` ever occurs [6](#0-5) , so the victim silently receives and works on `B` believing it is still the reviewed `A`.

```typescript
  public async _findPullRequestBranch(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {
        log.error(`Failed fetching remote ${remote?.name}`, e)
      }
    }

    if (existingBranch === undefined) {
      this.emitError(
        new Error(
          `Couldn't find branch '${headRefName}' in remote '${remote.name}'. ` +
            `A common reason for this is that the PR author has deleted their ` +
            `branch or their forked repository.`
        )
      )
      return
    }

    // For fork remotes we checkout the ref as pr/[123] instead of using the
    // head ref name since many PRs from forks are created from their default
    // branch so we'll have a very high likelihood of a conflicting local branch
    const isForkRemote =
      remote.name !== gitStore.defaultRemote?.name &&
      remote.name !== gitStore.upstreamRemote?.name

    if (isForkRemote) {
      return await this._createBranch(
        repository,
        `pr/${prNumber}`,
        remoteRef,
        false
      )
    }

    return existingBranch
  }
```

```typescript
  private async openPullRequestFromUrl(
    url: string,
    pr: string
  ): Promise<RepositoryWithGitHubRepository | null> {
    const pullRequest = await this.appStore.fetchPullRequest(url, pr)

    if (pullRequest === null) {
      return null
    }

    // Find the repository where the PR is created in Desktop.
    let repository: Repository | null =
      this.getRepositoryFromPullRequest(pullRequest)

    if (repository !== null) {
      await this.selectRepository(repository)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      log.warn(
        `Open Repository from URL failed, did not find or clone repository: ${url}`
      )
      return null
    }
    if (!isRepositoryWithGitHubRepository(repository)) {
      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`
      )
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    if (pullRequest.head.repo === null) {
      return null
    }

    await this.appStore._checkoutPullRequest(
      repository,
      pullRequest.number,
      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,
      pullRequest.head.ref
    )

    return repository
  }
```

```markdown
## Force Push

When the rebase is completed, the application will update its list of rebased
branches to indicate that the current branch was updated by the user and is
eligible to be "force pushed" to the remote repository.

This has potential downsides, so there are additional checks as part of this
work:

 - only a branch that completed the rebase flow in Desktop will be eligible for
 a "force push" operation - branches rebased outside Desktop will be ignored
 - other branches which are ahead and behind will need to have these commits
 resolved before any commits can be pushed. Depending on your Git configuration,
 this could be a `pull with rebase` or a `pull with merge` commit
 - if the user has enabled "Show Confirmation Dialog before Force Pushing"
 (enabled by default), the user will see a prompt that explains the downstream
 impact of rewriting the branch for other contributors
 - when Desktop invokes `git push` it will also pass the `--force-with-lease`
 flag that guards against the tracking branch being updated without the user
 knowing, to avoid overwriting newer commits since the rebase was completed
```
