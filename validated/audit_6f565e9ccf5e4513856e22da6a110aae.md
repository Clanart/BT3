### Title
Deterministic FROST nonce reuse across multiple signing operations under one context allows secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` caches a 32-byte preprocess seed in the DB keyed only by `context` (`(b"DkgConfirmer", attempt)`), and `share_internal` reconstructs an `AlgorithmSignMachine` from that same seed on every call. Because `crypto/frost`'s `seeded_preprocess` is fully deterministic (ChaCha20Rng seeded from the cached seed feeding `Commitments::new` / `Curve::random_nonce`), every `share_internal` invocation under the same context reuses identical FROST nonces `(d, e)`. If the coordinator signs two distinct messages (or distinct preprocess sets) within one attempt — e.g. multiple `KeyPair` confirmations sharing an attempt, or `share` followed by `complete` on different data — an observer obtains two Schnorr signature shares `s_i = d + e·rho_i + λ_i·share·c_i` under identical nonces but different binding factors/challenges, enabling direct algebraic recovery of the validator's private key share.

### Finding Description
- `coordinator/src/tributary/signing_protocol.rs:123-147`: the seed is generated once per context and *never deleted or rotated*; `from_cache` at line 144-145 deterministically regenerates the same `AlgorithmSignMachine` (same `nonces`, same `Preprocess` commitments) each time.
- `crypto/frost/src/sign.rs:121-144` (`seeded_preprocess`): nonces are derived via `ChaCha20Rng::from_seed(*seed.0)` → `Commitments::new` → `C::random_nonce`, so identical seed ⇒ identical nonces.
- `crypto/frost/src/curve/mod.rs:94-121` (`random_nonce`): `hash_to_F(b"nonce", rng_bytes || secret_share)` — deterministic given the seed.
- `share_internal` (signing_protocol.rs:150-181) calls `machine.sign(preprocesses, msg)` where `msg` is `set_keys_message(...)` bound to a `key_pair`, and the binding factors `rho` mix in `hash_msg(msg)` and all preprocess commitments (`crypto/frost/src/sign.rs:361-371`, `nonce.rs:161-173`). Two distinct `msg`/preprocess inputs therefore produce distinct `rho` and challenge `c` while `d, e` stay fixed.
- `DkgConfirmer::complete` (signing_protocol.rs:312-327) re-invokes `share_internal`, and `share`/`complete` are reachable for every `key_pair` confirmed under the attempt; the header comment (lines 25-54) itself acknowledges nonce reuse occurs if "the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again," and leaves a TODO to verify on-chain preprocesses match presumed ones.

### Impact Explanation
With two shares `(R fixed)`: `s1 − s2 = e·(rho1 − rho2) + λ·share·(c1 − c2)`. When the participant set is identical, `λ` and `share` are constant; `e` is recoverable from `s1 − s2` only if `c1 = c2`, and otherwise the system of two equations in two unknowns `e` and `λ·share` (with `d` eliminated) still yields the secret share `s_share = share·λ`. Since `λ` is public Lagrange data, the validator's FROST private share — effectively the validator's MuSig signing key — is recovered, allowing signature forgery for the validator set key. Signature shares are published on the public tributary chain, so recovery requires only observing the two shares.

### Likelihood Explanation
Triggering requires two `share_internal` executions under the same `(b"DkgConfirmer", attempt)` context with differing `msg` or preprocess sets. `msg` is attacker-influenced through the `key_pair` and `removed` set bound into `set_keys_message`; preprocesses are supplied by other validators. Any code path that signs more than one distinct confirmation message per attempt — or a partial rebuild that re-executes `share` after a different key pair/preprocess set is processed — deterministically reuses nonces. There is no deletion or one-time-use guard on `CachedPreprocesses`, so the hazard is structural, not probabilistic.

### Recommendation
Bind the cached preprocess to the exact `(preprocesses, msg)` tuple it was first used with, or store a monotonically increasing nonce counter; alternatively, record the signed `msg` hash in the DB and refuse to sign a different message under the same context. Rotate (delete) the cached seed after the first `sign` and generate a fresh seed per signing decision, so that determinism is only used for *replay-identical* re-execution, never for distinct inputs.

### Proof of Concept
1. Validator runs `DkgConfirmer::share(preprocesses_A, key_pair_1)` → produces `s1` with nonces `(d, e)` derived from cached seed.
2. Under the same `attempt`, it runs `share(preprocesses_A', key_pair_2)` (distinct `key_pair` → distinct `msg`; or `complete` re-executing on different preprocesses) → produces `s2` with the same `(d, e)` but different `rho`, `c`.
3. Observer collects on-chain `s1`, `s2`, computes `e = (s1 − s2 − λ·share·(c1 − c2)) / (rho1 − rho2)` by solving the 2×2 linear system over `(d, e, λ·share)`-space, then recovers the validator's secret share `share = (s1 − d − e·rho1) / (λ·c1)`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }

  fn random_nonce<R: RngCore + CryptoRng>(
    secret: &Zeroizing<Self::F>,
    rng: &mut R,
  ) -> Zeroizing<Self::F> {
    let mut seed = Zeroizing::new(vec![0; 32]);
    rng.fill_bytes(seed.as_mut());

    let mut repr = secret.to_repr();

    // Perform rejection sampling until we reach a non-zero nonce
    // While the IETF spec doesn't explicitly require this, generating a zero nonce will produce
    // commitments which will be rejected for being zero (and if they were used, leak the secret
    // share)
    // Rejection sampling here will prevent an honest participant from ever generating 'malicious'
    // values and ensure safety
    let mut res;
    while {
      seed.extend(repr.as_ref());
      res = Zeroizing::new(<Self as Curve>::hash_to_F(b"nonce", seed.deref()));
      res.ct_eq(&Self::F::ZERO).into()
    } {
      seed = Zeroizing::new(vec![0; 32]);
      rng.fill_bytes(&mut seed);
    }
    repr.as_mut().zeroize();

    res
  }
