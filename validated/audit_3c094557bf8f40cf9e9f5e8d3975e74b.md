### Title
Unbounded, unmetered iteration over an address's token balances during EVM address association can stall block processing - ([File: x/evm/ante/preprocess.go])

### Summary
The `EVMPreprocessDecorator.AnteHandle` function installs an **infinite gas meter** before performing Sei↔EVM address association, and then calls `AssociationHelper.AssociateAddresses` → `MigrateBalance`, which calls `bankKeeper.SpendableCoins` on the address's "cast" account. `SpendableCoins`/`GetAllBalances` iterates over **every denom balance** held by that account via a KV-store iterator. Because a tokenfactory denom can be created permissionlessly and sent to any address, an attacker can inflate the number of distinct denom balances held by an unassociated EVM address's cast account to an arbitrarily large number, then trigger association from that address. The balance-iteration work happens entirely under the infinite gas meter (i.e., for free), so it is unbounded and unmetered — closely analogous to the reported `Vault.claimTokens()` unbounded loop over `latestID`.

### Finding Description
Every EVM transaction from a not-yet-associated sender goes through `EVMPreprocessDecorator.AnteHandle`: [1](#0-0) 

Key steps:
1. `ctx = ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))` is installed "because EVM handles gas checking from within" — real gas metering for the state-transition happens later, in `NewGasDecorator`, not during this decorator.
2. If the sender is not yet associated, `associateHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)` is invoked directly under this infinite-gas context.

`AssociateAddresses` calls `MigrateBalance`, which does: [2](#0-1) 

`p.bankKeeper.SpendableCoins(ctx, castAddr)` resolves to `BaseViewKeeper.GetAllBalances`, which walks a KV iterator over **every balance entry stored under the account's prefix** (one entry per denom the account holds): [3](#0-2) 

Because tokenfactory denom creation, minting, and bank sends are permissionless and denom balances persist in the KV store indefinitely, any actor can:
1. Create N tokenfactory denoms (`MsgCreateDenom`, admin = attacker) — permissionless creation is documented and supported: [4](#0-3) 
2. Mint 1 unit of each denom and `bank send` it to the cast address (`sdk.AccAddress(evmAddr[:])`) of a target EVM address that has not yet performed on-chain association. This step is ordinary, gas-metered activity paid by the attacker once.
3. Submit (or wait for) any EVM transaction from that EVM address. The very first transaction triggers `EVMPreprocessDecorator.AnteHandle`, which runs the entire `GetAllBalances` iteration over the N stuffed denom balances **under the infinite gas meter**, i.e., with no gas cost or throttling for that specific work.

This mirrors the reported bug class exactly: a per-transaction unbounded loop (`for range latestProtocolId` in the Derby report) whose bound is externally, cheaply, and permanently inflatable by anyone (here, `latestID` analog = number of distinct denoms an address holds), executed without gas metering in this particular code path.

### Impact Explanation
The number of KV-store reads performed is proportional to the number of denoms stuffed into the target cast address, and this work runs with no gas throttling in this specific ante-preprocessing context. A sufficiently large number of stuffed denom balances (achievable with a one-time, attacker-funded setup) can make the association step take substantially longer than normal transaction processing, delaying inclusion of that transaction and consuming validator CPU time disproportionate to the fee paid, since the offending iteration itself is not charged to the gas meter. This can push block processing time beyond the network's target block interval, i.e., a validator-halt/block-delay class impact as called out in the validation criteria.

### Likelihood Explanation
- All required primitives (permissionless tokenfactory denom creation, minting, bank sending, and un-associated EVM addresses) are reachable by any unprivileged account, with no special privileges needed.
- The setup cost (creating/minting/sending N denoms) is paid once by the attacker via ordinary gas-metered transactions; the exploit trigger (submitting a single EVM tx from the stuffed address) is a single, cheap transaction.
- The vulnerable code path (`EVMPreprocessDecorator.AnteHandle` running association under an infinite gas meter) executes unconditionally for every first-time EVM sender, making the trigger condition trivial to hit.

### Recommendation
- Do not run `AssociateAddresses`/`MigrateBalance` (and specifically the `SpendableCoins`/`GetAllBalances` iteration) under an infinite gas meter. Either meter this specific portion of the ante logic with a bounded gas meter (charging KV-read gas as usual), or cap/paginate the number of denom balances migrated in a single association call.
- Consider bounding the number of distinct denom balances a single account may accumulate, or lazily/incrementally migrating balances instead of eagerly enumerating all of them synchronously inside the ante handler.

### Proof of Concept
1. Attacker generates a fresh EVM keypair (`evmAddr`, `seiAddr`) that has never transacted (unassociated).
2. Attacker creates N tokenfactory denoms (e.g., tens of thousands), mints 1 unit of each, and sends each to `castAddr = sdk.AccAddress(evmAddr[:])` — all via ordinary, gas-paid Cosmos transactions from the attacker's own funded account.
3. Attacker signs and submits a single trivial EVM transaction (e.g., a 0-value transfer or `AssociateTx`) from `evmAddr`.
4. During ante processing, `EVMPreprocessDecorator.AnteHandle` sets an infinite gas meter and calls `AssociateAddresses` → `MigrateBalance` → `SpendableCoins(ctx, castAddr)`, which iterates all N balance entries under `types.BalancesPrefix` for `castAddr` without gas metering, consuming wall-clock time proportional to N before the transaction's real gas metering ever begins.

# Token Factory

The tokenfactory module allows any account to create a new token with
the name `factory/{creator address}/{subdenom}`. Because tokens are
namespaced by creator address, this allows token minting to be
permissionless, due to not needing to resolve name collisions. A single
account can create multiple denoms, by providing a unique subdenom for each
created denom. Once a denom is created, the original creator is given
"admin" privileges over the asset. This allows them to:

- Mint their denom to any account
- Burn their denom from any account
- Create a transfer of their denom between any two accounts
- Change the admin. In the future, more admin capabilities may be added. Admins
  can choose to share admin privileges with other accounts using the authz
  module. The `ChangeAdmin` functionality, allows changing the master admin
  account, or even setting it to `""`, meaning no account has admin privileges
  of the asset.
