## Analog Found

### Title
Tokenfactory denom allow-list changes can retroactively freeze existing token holders' ability to transfer their balance via `MsgSend`/`MsgMultiSend` - ([File: sei-cosmos/x/bank/keeper/msg_server.go])

### Summary
This mirrors the Tokemak `perWalletLimit` bug class: a mutable, admin-controlled restriction (`AllowList`) is re-evaluated at transfer time against a holder's *current* balance rather than being scoped to prevent only *new* acquisitions. A tokenfactory denom admin can call `MsgUpdateDenom` at any time to set/shrink a denom's `AllowList`, and any address already holding that denom which is not included is immediately unable to move its balance out via the standard bank message path, even though it legitimately acquired the tokens beforehand.

### Finding Description
The tokenfactory module allows any denom admin to attach or update an `AllowList` for their factory-namespaced denom via `MsgUpdateDenom`, which is written directly into bank module state with no restriction on it excluding existing holders: [1](#0-0) 

The bank module then enforces this allow list in `MsgSend`/`MsgMultiSend` by checking `IsInDenomAllowList` for the sending address, unconditionally, for every coin whose denom has the `factory` prefix: [2](#0-1) [3](#0-2) 

Just like `_setPerWalletLimit` in the Tokemak report is evaluated against the current holder's balance without exempting "return"/burn-style transfers, `IsInDenomAllowList` is evaluated purely against the `from` address's set membership at send time, with no path allowing a currently-non-allow-listed holder to move out funds they legitimately acquired while allow-listed (or before the allow list was ever set). There is no reconciliation logic analogous to "any decrease shouldn't affect what is already held."

### Impact Explanation
If a tokenfactory denom admin (an ordinary, permissionless account — anyone can create a tokenfactory denom and thus become its admin) updates the `AllowList` for a denom to remove or exclude an address that already holds a balance, that holder can no longer transfer, or (via a self-send to the admin) return their tokens using standard `MsgSend`/`MsgMultiSend`. This is a real "permanent freezing" impact for a class of users acting entirely within intended, reachable interaction with a public module (tokenfactory denom admin action + regular bank Send from an unprivileged holder).

### Likelihood Explanation
Reachable purely through two ordinary transactions: (1) the tokenfactory denom admin submits `MsgUpdateDenom` with an `AllowList` excluding an existing holder, and (2) the holder subsequently submits an ordinary `MsgSend`. No governance, validator, or privileged access is required — only the standard denom-admin/holder relationship that tokenfactory already establishes for any permissionless denom.

### Recommendation
Do not apply the current `AllowList` check to the sender's *existing* balance disposal path uniformly; either (a) snapshot/grandfather balances held prior to an allow-list update, or (b) exempt sends whose purpose is to return funds to the denom's admin/module account, analogous to the recommended fix of exempting burn-direction transfers (`to == address(0)`) in the original report. At minimum, document and test that allow-list decreases cannot strand previously-acquired balances.

### Proof of Concept
1. Attacker/normal user `A` creates tokenfactory denom `factory/A/foo` (no `AllowList`), becoming its admin.
2. `A` mints and sends some `factory/A/foo` to user `B` via a normal transfer (allowed since no allow list exists yet).
3. `A` calls `MsgUpdateDenom` setting `AllowList.Addresses = [A]` (excluding `B`). [4](#0-3) 
4. `B` attempts `MsgSend` to move their `factory/A/foo` balance anywhere (including back to `A`): the transaction fails with `"%s is not allowed to send funds"` because `B` is not in the (now-shrunk) allow list. [5](#0-4) 
5. `B`'s balance of `factory/A/foo` is now frozen from the standard bank send path with no way for `B` to unilaterally regain send access.

Note: this analysis is limited to the standard `x/bank` `MsgSend`/`MsgMultiSend` code paths reviewed above; whether other transfer paths (e.g., CosmWasm bank-message sends via `sei-wasmd`) enforce the same allow-list check was not fully confirmed, which could affect the practical severity/permanence of the freeze and would benefit from further verification in a full Devin session.

func (server msgServer) UpdateDenom(goCtx context.Context, msg *types.MsgUpdateDenom) (*types.MsgUpdateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.validateUpdateDenom(ctx, msg)
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	updateDenomEvent := sdk.NewEvent(
		types.TypeMsgUpdateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeUpdatedTokenDenom, denom),
	)

	if msg.AllowList != nil {
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		updateDenomEvent = updateDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		updateDenomEvent,
	})

	return &types.MsgUpdateDenomResponse{}, nil
}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}
