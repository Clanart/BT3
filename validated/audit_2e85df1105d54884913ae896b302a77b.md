### Title
Embedded `---` in a hookify rule's YAML value causes `extract_frontmatter` to silently truncate frontmatter, downgrading `action: block` to the `warn` default - ([File: plugins/hookify/core/config_loader.py])

### Finding Description
`extract_frontmatter` splits the whole file content on the literal delimiter with `content.split('---', 2)` and treats the *second* occurrence of `---` anywhere in the text as the closing frontmatter fence: [1](#0-0) 

This is not a fence-aware YAML/Markdown parser - it has no notion of "the second `---` must be on its own line" or "inside quotes doesn't count." If any frontmatter *value* (e.g. the `pattern` field of a rule, which is user-supplied regex text) contains the three-character substring `---` before the intended closing fence, `split('---', 2)` consumes that embedded occurrence as the second delimiter. Everything after it - including a later `action: block` line and the real closing fence - gets shoved into `parts[2]` (the "message" body) instead of being parsed as frontmatter.

Concretely, a rule file such as:
```
---
name: block-destructive-ops
enabled: true
event: bash
pattern: rm\s+-rf|foo---bar
action: block
---

Blocked!
```
produces `frontmatter_text = "\nname: block-destructive-ops\nenabled: true\nevent: bash\npattern: rm\\s+-rf|foo"`, i.e. the `pattern` value is truncated and the `action: block` line never enters the mini line-by-line parser at all.

`Rule.from_dict` then falls back to the documented default: [2](#0-1) 

producing a `Rule` with `action == "warn"` even though the file's visible text says `action: block`.

This flows through `load_rule_file` -> `load_rules` -> `pretooluse.py` -> `RuleEngine.evaluate_rules`, which only emits `permissionDecision: "deny"` for rules whose `action == 'block'`; anything else (including this silently-downgraded rule) is placed in `warning_rules` and the operation is allowed to proceed with only a `systemMessage`: [3](#0-2) 

No validation, schema check, or fence-matching logic exists anywhere in this path to catch the truncation or to reject a rule whose intended `action: block` failed to parse - `load_rule_file`'s exception handling only guards I/O and type errors, not semantic mis-parses, and a truncated-but-nonempty frontmatter dict is treated as valid.

### Impact Explanation
A rule file that a reviewer/user believes enforces `action: block` for a dangerous pattern (e.g. `rm -rf`, destructive `dd`, secrets exfiltration write) can be authored (accidentally or by a malicious PR/contributor who controls a `.claude/hookify.*.local.md` file checked into the repository, or content that seeds `/hookify`-generated rules) such that the enforced behavior is actually `warn`-only. This breaks the "deny means deny" invariant: `RuleEngine.evaluate_rules` will never return `permissionDecision: "deny"` for the affected rule, so the matching dangerous Bash/Write/Edit operation executes normally despite the human-visible intent to block it.

### Likelihood Explanation
Preconditions are simple and require no special privilege beyond being able to author/merge a `.claude/hookify.*.local.md` file (a routine, git-trackable action in this plugin's normal workflow) or influence its `pattern`/other frontmatter value to contain a literal `---` substring - a not-unusual pattern fragment (e.g. `foo---bar`, a heredoc marker, a YAML-list-looking regex, or three consecutive dashes from an OR-alternation). No exotic crafting is needed and the bug is 100% deterministic given `split(..., 2)` semantics.

### Recommendation
Rewrite `extract_frontmatter` to use a fence-aware split that only recognizes `---` as a delimiter when it appears alone on its own line (e.g. `re.split(r'(?m)^---\s*$', content, maxsplit=2)` after confirming line-anchored matches), rather than a naive substring `split`. Additionally, `Rule.from_dict`/`load_rule_file` should treat an `action` value that fails validation (not in `{"warn","block"}`, or a frontmatter parse that appears truncated/incomplete) as an error to be rejected rather than silently defaulting to `warn`, especially since `warn` is the less-restrictive/less-safe outcome.

### Proof of Concept
Unit test in `plugins/hookify/core/` (pytest-style):
```python
from hookify.core.config_loader import extract_frontmatter, Rule

def test_embedded_dash_dash_dash_downgrades_block_to_warn():
    content = """---
name: block-destructive-ops
enabled: true
event: bash
pattern: rm\\s+-rf|foo---bar
action: block
---

Blocked!
"""
    fm, msg = extract_frontmatter(content)
    rule = Rule.from_dict(fm, msg)
    # Human intent: action should be 'block'
    assert rule.action == "block", (
        f"Expected action='block' but parser silently produced "
        f"action={rule.action!r} due to embedded '---' in pattern value"
    )
```
Running this against the current implementation fails: `rule.action == "warn"` and `fm` lacks the `action` key entirely, confirming the misparse and the resulting silent downgrade from `block` to the `warn` default.
