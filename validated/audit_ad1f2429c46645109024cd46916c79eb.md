### Title
`Scanner::scan_transaction` and `ReceivedOutput::read` accept zero-value / sub-dust outputs, crediting funds that can never be spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Union `redeem()` bug class is "a check meant to ensure at least one non-zero amount (`amountIn != 0 && amountOut != 0`) actually permits both to be zero, letting a zero-value operation flow through to a downstream call." The analog in Serai lives in `bitcoin-serai`'s wallet scanning path: outputs are matched purely on `script_pubkey`, and no minimum-value check exists anywhere on the receive side. `Scanner::scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214) pushes a `ReceivedOutput` for any output paying to a registered script regardless of `output.value`, and `ReceivedOutput::read` (mod.rs:122-134) deserializes the `TxOut` with no value validation. Meanwhile the spend path only enforces `DUST` on *payments* (`send.rs:165-169`), never on *inputs* — an input of value 0 or below the spend cost is happily included, contributing nothing while inflating the fee.

### Finding Description
`Scanner::scan_transaction` iterates `tx.output` and returns a `ReceivedOutput` whenever `self.scripts.get(&output.script_pubkey)` hits (mod.rs:201-211). There is no `output.value != 0` or `>= DUST` check, mirroring the missing both-zero check in `redeem()`. The `DUST` constant and its enforcement exist only on the payment side in `SignableTransaction::new` (send.rs:32, 165-169); inputs are summed blindly (send.rs:175). The result: the scanner reports a `ReceivedOutput` that `SignableTransaction::new` will then treat as spendable input even though its value is zero or less than the ~fee-per-input cost of spending it, and downstream balance accounting (`Output::balance` in processor/src/networks/bitcoin.rs:128-130, which returns `Amount(self.output.value())`) credits it.

### Impact Explanation
An unprivileged party can send a transaction paying a zero-value or sub-dust output to a scanned script (0-value outputs are consensus-valid and any below-dust value can be mined). The Serai processor then records a received output whose value is less than the marginal fee required to spend it — funds "received" that are not economically spendable, matching the "funds reported received that are not spendable" acceptance class. If included as an input in a `SignableTransaction`, it consumes input weight and raises `needed_fee` while contributing nothing, so a batch of dust inputs can turn an otherwise-affordable plan into `NotEnoughFunds` or silently burn additional funds as fee.

### Likelihood Explanation
Any external party can construct a transaction with a dust or zero-valued output to the threshold address or a registered offset script; no privilege, collusion, or validator misbehavior is needed. Exploitation requires such a transaction to be mined (non-standard by default relay policy for 0-value/dust, but valid by consensus), making likelihood moderate rather than certain. The downstream effect (scanner crediting and scheduler attempting to spend the output) is deterministic once confirmed.

### Recommendation
Reject outputs below `DUST` (or at least `value == 0`) in `Scanner::scan_transaction` / `Scanner::scan_block`, and/or validate `output.value >= DUST` inside `ReceivedOutput::read`. Additionally, in `SignableTransaction::new`, account for per-input cost when summing `input_sat`, so inputs whose value is less than the fee they add are dropped rather than treated as covering payments.

// Attacker mines/relays a tx with a 0-value (or 1-sat) P2TR output to the
// threshold key's script_pubkey.
let dust_tx = Transaction {
  output: vec![TxOut {
    value: Amount::from_sat(0), // or any value < DUST
    script_pubkey: p2tr_script_buf(group_key).unwrap(),
  }],
  ../* funding input elsewhere */
};

// Scanner reports it as a received output — no value check exists.
let outputs = scanner.scan_transaction(&dust_tx);
assert_eq!(outputs.len(), 1);            // credited as received
assert_eq!(outputs[0].value(), 0);       // worth nothing

// SignableTransaction::new then accepts it as an input; DUST is only
// enforced on payments (send.rs:165), not on inputs (send.rs:175).
// The input adds weight (raising needed_fee) while contributing 0 sats.
SignableTransaction::new(outputs, &payments, None, None, FEE);
```

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```
