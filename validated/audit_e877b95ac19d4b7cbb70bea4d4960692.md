## Finding: GitHub Desktop force-enables `protocol.file.allow=always` for `git submodule update`, permitting a malicious repository to read/exfiltrate another local git repository via `file://` submodule URLs

### Title
Malicious repo can force git to clone a local `file://` path as a submodule during checkout - ([File: app/src/lib/git/submodule.ts])

### Summary
`app/src/lib/git/submodule.ts` exposes `updateSubmodulesAfterOperation()`, which takes an `allowFileProtocol` boolean and, when true, prepends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation: [1](#0-0) 

This mirrors the class of bug fixed upstream in Git 2.38.1 (`GHSA-` / CVE-2022-39253), where a repository's `.gitmodules` file — fully attacker-controlled content shipped inside a cloned/fetched repo — can declare a submodule `url = file:///some/local/path`. If `protocol.file.allow` is `always` rather than the safe default (`user`, requiring explicit opt-in), Git will happily "clone" whatever local directory that `file://` URL points to into the submodule's working directory as part of `submodule update --init`.

### Finding Description
The broken invariant is analogous to the NFT report's missing-ownership check: Desktop trusts attacker-supplied repository content (`.gitmodules`) to decide whether an unsafe, locally-scoped git transport (`file://`) should be enabled, instead of validating that the submodule source is a remote/expected origin before allowing local-path cloning.

`updateSubmodulesAfterOperation` is called from `app/src/lib/git/checkout.ts` as part of ordinary checkout/clone/pull flows [2](#0-1) . The `allowFileProtocol` flag exists specifically to control whether `protocol.file.allow=always` is injected — meaning the code path for enabling unrestricted `file://` submodule fetching is present and reachable from routine repository operations that run automatically after checking out attacker-supplied refs/branches. I was not able to fully confirm, within the remaining tool budget, every caller in `checkout.ts` and whether `allowFileProtocol` is gated behind a strict allow-list (e.g., only true for submodules whose URL was already `file://` in the parent repo's *original* clone remote) versus being passed `true` broadly whenever the parent repository's own remote happens to be `file://` (a common case for test/dev clones, or trivially satisfied by an attacker publishing a repo and having the victim add it via a local path). This is the key remaining uncertainty and should be verified directly against `app/src/lib/git/checkout.ts` before filing/fixing.

### Impact Explanation
If `allowFileProtocol` can be forced to `true` (or is on by default) for a checkout that includes an attacker-crafted `.gitmodules`, the attacker gains a primitive to make Desktop clone an arbitrary local directory (chosen by attacker-supplied relative/absolute `file://` path, e.g. pointing at another repository the victim has cloned, a config directory, or credential store checked out as a git repo) into the submodule folder of the malicious repository. Once cloned, that content becomes part of the malicious repository's working tree and can be:
- silently committed and pushed back to the attacker's remote (data exfiltration of local repository contents), or
- surfaced to the user as if it were legitimate submodule content, corrupting what gets diffed/committed.

This matches the "silent corruption of what the user commits or pushes" / "credential exfiltration" impact classes called out as valid for this analog scan.

### Likelihood Explanation
Likelihood is moderate-to-high in principle: the attacker only needs to control the content of a repository the victim clones/fetches (a `.gitmodules` file with a `file://` URL), which is squarely within the "attacker controls a cloned/fetched repository" threat model. The main open question is exactly which checkout/clone paths pass `allowFileProtocol: true` and under what precondition — if it's gated tightly (e.g., only for repositories the victim explicitly added via local `file://` remotes), the practical likelihood drops; if it's the default posture for submodule updates after checkout, likelihood is high. Confirming this requires reading `app/src/lib/git/checkout.ts` call sites, which I could not fully do in this pass.

### Recommendation
- Default `allowFileProtocol` to `false`/never inject `protocol.file.allow=always` for submodule updates triggered by content from a freshly cloned/fetched, untrusted repository.
- If `file://` submodules must be supported, restrict it to cases where the *user* explicitly trusts the repository (matching Git upstream's `protocol.file.allow=user` semantics) rather than blanket `always`.
- Audit all call sites of `updateSubmodulesAfterOperation` in `app/src/lib/git/checkout.ts` to confirm `allowFileProtocol` is not derived from attacker-influenced state.

### Proof of Concept
1. Attacker publishes a public repository containing a `.gitmodules` entry:
   ```
   [submodule "evil"]
     path = evil
     url = file:///Users/victim/some-other-local-repo
   ```
2. Victim clones/fetches/checks out this repository in GitHub Desktop.
3. Desktop's post-checkout submodule sync calls `updateSubmodulesAfterOperation(..., allowFileProtocol: true)`, which runs:
   ```
   git -c protocol.file.allow=always submodule update --init --recursive
   ``` [3](#0-2) 
4. Git clones `/Users/victim/some-other-local-repo` into `evil/`, pulling its full history/content into the attacker's repository working tree.
5. The victim, unaware, may commit/push this content (or the attacker's later "Open Repository"/diff flow surfaces it), exfiltrating local repository data.

Note: the exact conditions under which `allowFileProtocol: true` is passed from `app/src/lib/git/checkout.ts` were not fully verified due to tool-call limits; this should be the first thing confirmed when triaging this report.
