### Title
Unchecked `u64` payment total enables signing a malformed Bitcoin transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` validates each requested payment only against the dust limit, then calculates `payment_sat` with an unchecked `u64::sum`. In a build without overflow checks, multiple attacker-supplied payment amounts can wrap the total to a small value while preserving the original oversized `TxOut` values. The insufficient-funds check then operates on the wrapped total and can incorrectly succeed. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Each payment amount is accepted if it is at least `DUST`, with no upper bound or aggregate checked-arithmetic validation. [1](#0-0)  The code copies each unbounded amount into a transaction output before calculating the total. [4](#0-3)  The resulting `payment_sat` is a wrapping `u64` sum in release-style builds, and `payment_sat + needed_fee` is also unchecked. [5](#0-4) [6](#0-5)  The fee calculation and change calculation contain the same unchecked multiplication and addition pattern. [7](#0-6) [8](#0-7) 

For example, payments of `u64::MAX` and `2` both pass the per-payment dust check, but their mathematical total wraps to `1`. A normal 1,000,000-satoshi input therefore passes the balance check even though the encoded transaction contains an output for `u64::MAX` satoshis. The malformed transaction is stored in `SignableTransaction`, and signing commits to it through the Taproot sighash. [9](#0-8) [10](#0-9)  Completion installs the resulting Schnorr signatures as input witnesses and returns the malformed transaction. [11](#0-10) 

### Impact Explanation
An untrusted caller able to specify payment amounts can cause the threshold wallet to produce signatures for a transaction whose outputs exceed its inputs. This satisfies the signing of an unintended transaction and can burn participant signing rounds or cause an invalid withdrawal to be constructed despite the wallet's balance checks. The malformed transaction should be rejected by Bitcoin consensus, so this does not directly create spendable excess Bitcoin, but the threshold signature itself is produced for attacker-shaped transaction data. [12](#0-11) 

### Likelihood Explanation
The issue is reachable wherever `SignableTransaction::new` receives payment values derived from external transaction requests and is built without integer overflow checks. Exploitation requires at least two large amounts whose sum wraps below the available input total, while each individual amount remains above the dust threshold. Debug builds will panic instead of returning the malformed transaction, so practical exploitability depends on the production overflow-check configuration. [13](#0-12) [1](#0-0) 

### Recommendation
Calculate `input_sat`, `payment_sat`, `needed_fee`, `fee_with_change`, and all balance comparisons with `checked_add`, `checked_mul`, and `checked_sub`, returning `TransactionError::NotEnoughFunds` or a new overflow error on failure. Cap each payment and the aggregate payment total at Bitcoin's maximum money supply, and reject `Amount` values that cannot appear in a valid transaction. Apply the same checked arithmetic to `fee()` rather than unchecked subtraction. [14](#0-13) [15](#0-14) [16](#0-15) 

### Proof of Concept
```rust
use bitcoin::{Amount, OutPoint, ScriptBuf, Transaction, TxOut, absolute::LockTime, transaction::Version};
use bitcoin_serai::wallet::{Scanner, SignableTransaction};
use k256::{ProjectivePoint, Scalar};

// Obtain a spendable ReceivedOutput for a 1,000,000-sat funding output.
let key = ProjectivePoint::GENERATOR * Scalar::ONE;
let mut scanner = Scanner::new(key).unwrap();
let offset = scanner.register_offset(Scalar::ONE).unwrap();
let script = bitcoin_serai::wallet::p2tr_script_buf(
    key + (ProjectivePoint::GENERATOR * offset),
).unwrap();

let funding_tx = Transaction {
    version: Version(2),
    lock_time: LockTime::ZERO,
    input: vec![],
    output: vec![TxOut {
        value: Amount::from_sat(1_000_000),
        script_pubkey: script,
    }],
};
let input = scanner.scan_transaction(&funding_tx).remove(0);

// Both amounts pass the dust check, but their u64 sum wraps to 1.
let payments = [
    (ScriptBuf::new(), u64::MAX),
    (ScriptBuf::new(), 2),
];

let tx = SignableTransaction::new(
    vec![input],
    &payments,
    None,
    None,
    10,
).expect("wrapped payment total bypassed balance validation");

assert_eq!(tx.transaction().output[0].value.to_sat(), u64::MAX);
assert_eq!(tx.transaction().output[1].value.to_sat(), 2);

// Passing `tx.multisig(&keys)` into the FROST signing machine causes the
// Taproot sighash over these oversized outputs to be signed.
```

The decisive check is `input_sat < payment_sat + needed_fee`: with `payment_sat == 1` after wrapping, a 1,000,000-satoshi input incorrectly appears sufficient for the oversized outputs. [17](#0-16)
