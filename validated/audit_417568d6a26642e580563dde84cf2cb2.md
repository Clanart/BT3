### Title
Direct token donation to `MasterMagpie` inflates `BaseRewardPool.totalStaked()` and permanently dilutes reward accrual for legitimate stakers - (File: `rewards/BaseRewardPool.sol`, `rewards/BaseRewardPoolV2.sol`)

### Summary
`BaseRewardPool`/`BaseRewardPoolV2` compute `totalStaked()` as the raw `IERC20(stakingToken).balanceOf(operator)` (where `operator` is `MasterMagpie`), rather than from `MasterMagpie`'s own internal per-user accounting. [1](#0-0) [2](#0-1)  This is directly analogous to the GenesisGroup report's root cause: a contract using a raw, externally-manipulable balance (there `address(this).balance`, here `ERC20.balanceOf`) as the denominator for a critical accounting calculation, instead of relying on internally tracked deposit state.

### Finding Description
Any unprivileged wallet holding the pool's `stakingToken` (the mintable/burnable receipt token, e.g. minted by `WombatStaking.deposit`/`depositLP` via `IMintableERC20.mint`) can transfer that token directly to the `MasterMagpie` contract address without ever calling `depositFor`. [3](#0-2)  Because `IERC20.transfer` requires no interaction with `MasterMagpie`'s deposit logic, this raises `IERC20(stakingToken).balanceOf(operator)` without creating any corresponding entry in `MasterMagpie`'s internal `UserInfo`/staking-info accounting. [4](#0-3) 

When a manager subsequently calls `queueNewRewards` (or `donateRewards`) to distribute new rewards, `_provisionReward` divides the incoming reward amount by `totalStaked()` to update `rewardPerTokenStored`: [5](#0-4) 

Since the attacker's donated tokens inflate the denominator (`totalStaked()`) but the attacker has no `balanceOf`/staking-info entry entitling them to any share of rewards, and they cannot withdraw the donated tokens back out (withdrawal in `MasterMagpie` is driven by the internal `UserInfo.amount`, not by `ERC20.balanceOf`), the inflated denominator permanently reduces `rewardPerTokenStored` growth for every future reward distribution. This silently and irreversibly dilutes rewards earned by every legitimate staker in that pool from that point forward.

### Impact Explanation
This causes a permanent reduction (freezing/loss) of unclaimed yield for all stakers of the affected pool, since `rewardPerTokenStored` is a monotonically-accumulating value computed against a permanently and artificially inflated `totalStaked()`. The lost accrual can never be recovered because the denominator error compounds with every future `queueNewRewards` call. This matches the "theft or permanent freezing of unclaimed yield" impact bar.

### Likelihood Explanation
The attack requires only: (1) acquiring the receipt/staking token for a targeted pool (freely obtainable by depositing a small amount or buying/holding it), and (2) a single unprivileged `transfer` call sending it to the `MasterMagpie` address. No special permissions, timing, or governance access are required, making this trivially and repeatedly executable by any wallet at low cost (the cost is only the donated tokens themselves, which are irrecoverable to the attacker but harmful to all other stakers).

### Recommendation
Track `totalStaked` as an internal state variable incremented/decremented exclusively within `MasterMagpie`'s `deposit`/`withdraw` logic (mirroring the `FGEN.totalSupply`-based fix recommended in the GenesisGroup report), rather than deriving it from `IERC20(stakingToken).balanceOf(operator)`. This removes the ability of an external, direct token transfer to affect reward-per-token accounting.

### Proof of Concept
1. Attacker acquires or already holds `stakingToken` (receipt token) for a given `BaseRewardPool`/pool in `MasterMagpie`, e.g. by minting a small amount through `WombatStaking.depositLP`.
2. Attacker calls `stakingToken.transfer(masterMagpieAddress, largeAmount)` directly — bypassing `MasterMagpie.depositFor`/`deposit` entirely. `MasterMagpie`'s internal `UserInfo` accounting for the attacker is unaffected, but `IERC20(stakingToken).balanceOf(operator)` — and thus `BaseRewardPool.totalStaked()` — increases by `largeAmount`. [6](#0-5) 
3. A manager (e.g., `WombatStaking` after harvesting WOM rewards, or `WombatBribeManager`) calls `queueNewRewards(rewardAmount, rewardToken)`. [7](#0-6) 
4. `_provisionReward` computes `rewardPerTokenStored += (rewardAmount * 10**decimals) / totalStaked()`, where `totalStaked()` is now artificially inflated, so the resulting `rewardPerTokenStored` increment is smaller than it should be for legitimate stakers. [8](#0-7) 
5. The attacker's donated tokens remain stuck in `MasterMagpie` (no `UserInfo` entry to withdraw them), permanently deflating future reward accrual for every real staker in the pool.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
