### Title
`operator_xonly_pk` attribution in `Verifier::update_finalized_payouts` trusts an unauthenticated OP_RETURN, letting anyone credit an arbitrary operator for a payout it never funded - (`core/src/verifier.rs`)

### Summary
`Verifier::update_finalized_payouts` derives `operator_xonly_pk` solely from the OP_RETURN output of the confirmed payout transaction, with no verification that the named key belongs to the party who actually supplied the withdrawal-diff funding. Because the payout input is signed by the withdrawer with `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY`, that signature covers only the input and its matching output — it does not cover any additional funding inputs or the OP_RETURN output — so anyone who can broadcast a Bitcoin transaction can spend the registered withdrawal UTXO, add their own fee/funding input, and append an OP_RETURN naming an arbitrary registered operator as the payer.

### Finding Description
The binding this code is supposed to enforce is:
`payout_payer_operator_xonly_pk (recorded in DB) == xonly_pk of the party whose funds actually covered withdrawal_diff (output_amount − input_amount)`.

In `core/src/verifier.rs` `update_finalized_payouts` (lines 2283-2352), for each confirmed payout tx: [1](#0-0) 
the code extracts `operator_xonly_pk` purely via `get_first_op_return_output` + `parse_op_return_data` and stores it via `update_payout_txs_and_payer_operator_xonly_pk`, with zero check against the tx's actual inputs, spender signatures, or any operator-controlled key.

`create_payout_txhandler` (used by `Operator::withdraw`) builds the payout tx with a key-spend input signed by the withdrawer and a separate OP_RETURN output carrying the operator's xonly pubkey: [2](#0-1) 
Critically, `Operator::withdraw` verifies the withdrawer's signature with `sighash_type` taken directly from `in_signature`, which is expected to be `SinglePlusAnyoneCanPay`: [3](#0-2) 
`SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` only commits to input #0 and the correspondingly-indexed output — it places no constraint on any additional inputs (fee/diff funding) or the OP_RETURN output that follows. `Operator::withdraw` funds the transaction via `fund_raw_transaction` (adding extra inputs) after this signature check, exactly the surface an attacker can replicate independently of the `Operator::withdraw` RPC.

Exploit flow: an attacker (any Bitcoin-broadcasting, Citrea-withdraw-capable party) obtains the withdrawer's `SinglePlusAnyoneCanPay` signature and the registered `withdrawal_utxo` (both are public/attacker-controllable per the threat model — the withdrawer chooses the withdrawal UTXO and signature when calling `withdraw` on the Citrea Bridge contract). The attacker constructs their own transaction: input = withdrawal UTXO with the withdrawer's signature, plus their own extra input to cover `withdrawal_diff`/fees, output = the same user-destined output (so the signature check passes), and an OP_RETURN naming a victim operator's real xonly pubkey. They broadcast this directly to bitcoind, bypassing `Operator::withdraw` entirely. Once confirmed, `update_finalized_payouts` records the victim operator as `payout_payer_operator_xonly_pk` for this withdrawal, and the victim's automated `PayoutCheckerTask` picks it up via `get_first_unhandled_payout_by_operator_xonly_pk`: [4](#0-3) 
and proceeds to `handle_finalized_payout` → kickoff → (absent a challenge/disprove) `reimburse_tx`, which pays the full deposit's `bridge_amount` to that operator's reimbursement address: [5](#0-4) 
None of `handle_finalized_payout`, the kickoff flow, or `update_finalized_payouts` cross-checks that the named `operator_xonly_pk` actually supplied the `withdrawal_diff` funding input — attribution is taken at face value from attacker-controlled transaction bytes.

### Impact Explanation
This breaks the Critical invariant "an operator reimbursed for a payout it never funded." The named operator receives the full `bridge_amount` reimbursement from the move-to-vault UTXO while having fronted none of the actual `withdrawal_diff`, and the attacker (who did front `withdrawal_diff`) receives nothing in return for that expenditure — meaning the bridge's fronting/reimbursement accounting is decoupled from real fund flow. This is repeatable across every withdrawal and can target any registered operator arbitrarily, since the only requirement is knowledge of a withdrawer's `SinglePlusAnyoneCanPay` signature and the victim operator's public xonly key (both public/known values).

### Likelihood Explanation
The attacker only needs standard, unprivileged capabilities already granted in this threat model: ability to call `withdraw` on the Citrea Bridge contract (or observe/reuse a signature emitted from a legitimate withdraw call), ability to fund and broadcast a Bitcoin transaction, and knowledge of any registered operator's public xonly pubkey (public information). No verifier, operator, or aggregator privilege is required, and the cost is only the `withdrawal_diff` + fees the attacker chooses to front. This is straightforward to execute with a single crafted transaction.

### Recommendation
Do not derive payer attribution solely from the OP_RETURN. Either (a) require the operator's own signature/commitment over the additional funding input(s) and the OP_RETURN content (e.g., have the operator sign the whole payout tx including OP_RETURN with a key the verifier can check against a known registered operator key, and reject payouts whose funding inputs are not attributable to that operator), or (b) have `update_finalized_payouts`/`handle_finalized_payout` cross-verify that the extra funding input(s) of the payout tx are spendable/controlled by the operator whose xonly_pk appears in the OP_RETURN (e.g., via a musig2/pubkey-tweaked funding address unique per operator) before crediting `payout_payer_operator_xonly_pk`.

### Proof of Concept
`cargo test` plan (new test under a non-excluded location is not permitted per scope rules for demonstration purposes only — describing assertions conceptually):
1. Set up a deposit and a registered withdrawal (`withdrawal_utxo`) as in existing integration harnesses, obtain a valid `SinglePlusAnyoneCanPay` signature for that UTXO as the withdrawer.
2. Instead of calling `Operator::withdraw`, manually build a transaction: input = withdrawal UTXO + attacker's own funding input, output = withdrawer's target output, OP_RETURN = victim operator's xonly pubkey (an operator distinct from the fee/diff-funding attacker). Broadcast directly via the regtest RPC.
3. Mine a block, run the verifier's block-processing path that calls `update_finalized_payouts`.
4. Assert: `db.get_payout_info_from_txid` (or equivalent) returns `payout_payer_operator_xonly_pk == victim_operator_xonly_pk`, i.e. `xonly_pk_recorded_as_payer` equals the victim's key even though `xonly_pk_of_party_whose_funds_paid_the_output` (the attacker's funding key) is different — proving the equality binding is violated.
5. Optionally continue to run the victim operator's `PayoutCheckerTask` and assert it produces a kickoff/reimburse chain for a payout it never funded, confirming downstream Critical impact.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
