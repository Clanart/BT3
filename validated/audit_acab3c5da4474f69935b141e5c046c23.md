## Analysis

I found a direct local analog of the ZRX-style non-reverting ERC20 issue in the Tron variant of the intents gateway contract.

### Title
Non-compliant ERC20 tokens that return `false` instead of reverting cause silent loss of escrowed funds during withdrawal - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()` (and the `SweepDust` handler in `onAccept`) on the Tron deployment release escrowed order funds using a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check the outer call's `success` boolean, never decoding/validating the ERC20 return data. The same contract already imports and uses `SafeERC20`/`safeTransferFrom` for deposit paths [1](#0-0) , but the escrow-release path does not use it.

### Finding Description
`withdraw()` decrements the escrow ledger and marks the order `_filled` based solely on whether the low-level `.call` did not revert: [2](#0-1) 

For a non-standard ERC20 token that returns `false` on failure instead of reverting (the same class described in the external report, e.g. ZRX), `success` is `true` because the outer call did not revert — only the ERC20's internal boolean return value indicates failure, and that value is discarded. The code proceeds to decrement `_orders[body.commitment][token]` and set `_filled[body.commitment] = beneficiary`, permanently finalizing the order even though the beneficiary received nothing.

The identical unchecked-return pattern also exists in the `SweepDust` branch of `onAccept`: [3](#0-2) 

Both `withdraw` and the dust sweep are reached via `onAccept`, which is `onlyHost`-gated for message delivery, but the *token address itself* is attacker-controlled: it originates from `order.inputs[i].token` / `order.output.assets[i].token`, which is chosen by the unprivileged order creator when the order is placed [4](#0-3) . Nothing constrains which ERC20 contract can be used as the input token.

### Impact Explanation
Once `withdraw()` silently "succeeds" without actually moving tokens, `_filled` is set and `_orders[commitment][token]` is decremented — the order can never be retried or refunded. The solver who filled the order (the intended `beneficiary` of the escrow redemption) permanently loses the expected input-token payout while having already delivered the output assets to the user. This is a direct, unrecoverable loss of funds in the bridge's intent-settlement path, matching the bounty's "stealing or loss of funds" and "logic attacks" categories.

### Likelihood Explanation
Any order creator can pick an arbitrary ERC20 token as `order.inputs[i].token` when placing an order — no allowlist is enforced at that layer. Tokens with non-reverting failure semantics exist in production (ZRX and others), so a solver filling an order that happens to use such a token as input is exposed without any special privileges or malicious infrastructure (peer/relayer/prover) being required — only the standard cross-chain settlement flow needs to execute.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer`, consistent with the rest of the contract (which already uses `safeTransferFrom`/imports `SafeERC20`). `SafeERC20` decodes and validates the return data, reverting the whole transaction (and thus the escrow-ledger update) if the underlying token reports failure.

### Proof of Concept
1. Attacker deploys/uses an ERC20 token whose `transfer` returns `false` on failure without reverting (mirroring ZRX's behavior), and places an order with this token as `order.inputs[0].token`, funding escrow normally via `safeTransferFrom` (deposit path works fine).
2. A solver fills the order on the destination chain, delivering the output assets to the user.
3. Hyperbridge delivers the `RedeemEscrow` message; `onAccept` calls `withdraw(body, false)`.
4. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` is executed against the malicious/non-standard token; the token internally fails (e.g., due to a blacklist or paused state) and returns `false`, but the call does not revert, so `success == true`.
5. `_orders[body.commitment][token] -= amount` and `_filled[body.commitment] = beneficiary` proceed; `EscrowReleased` is emitted.
6. The solver's balance of `token` is unchanged — the payout never happened — yet the order is now finalized and cannot be re-withdrawn or refunded, permanently losing the solver's expected proceeds.
