## Title
Re-enabling `protocol.file.allow=always` during submodule updates can allow a malicious repository/branch to exfiltrate arbitrary local files via `file://` submodule URLs (CVE-2022-39253 regression) - (File: `app/src/lib/git/submodule.ts`, `app/src/lib/git/checkout.ts`)

## Summary
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` takes an `allowFileProtocol` flag; when `true` it prepends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation before applying whatever `.gitmodules` content is present in the checked-out tree. [1](#0-0) 
This flag is consumed from `app/src/lib/git/checkout.ts`, which calls `updateSubmodulesAfterOperation` after a branch checkout.

Upstream Git hardened `protocol.file.allow` to default to `user` (i.e. disabled for automatic recursive submodule operations) specifically because of CVE-2022-39253: a repository can define a submodule with a `file://` URL pointing at an arbitrary local path (e.g. another checked-out repo, `~/.ssh`, or any directory readable by the current user), and when Git "clones" that submodule it can hardlink/copy objects out of that local path into the submodule's object store, effectively exfiltrating file contents into tracked, committable data. By explicitly forcing `protocol.file.allow=always` for submodule updates that run automatically after a checkout of a branch (which may originate from an untrusted fetched remote/PR), Desktop can reintroduce exactly the primitive that upstream Git's mitigation was designed to remove.

## Finding Description
The broken invariant is: *submodule URLs from a fetched/cloned repository should not be able to reach local filesystem paths outside the repository without explicit, informed user consent* — this is the invariant Git's `protocol.file.allow=user` default enforces. `updateSubmodulesAfterOperation` bypasses it programmatically: [2](#0-1) 
The `.gitmodules` file (and hence the submodule URLs) is fully attacker-controlled content coming from a cloned/fetched repository or a checked-out remote/PR branch — the same trust boundary called out in the external report ("attacker controls a cloned/fetched repository"). If `checkoutBranch` (in `checkout.ts`) invokes this helper with `allowFileProtocol: true` for a branch checkout that follows a fetch of a remote/PR the user does not control, the resulting `git submodule update --init --recursive -c protocol.file.allow=always` call will honor a malicious `url = file:///path/to/target` entry in `.gitmodules`, allowing Git to read files from that local path into the submodule's `.git/objects`, where they become part of the working tree/history the user may subsequently commit or push.

## Impact Explanation
If reachable from a checkout of an attacker-influenced branch (e.g. a forked PR branch checked out via "Checkout PR" flows) without a corresponding trust prompt, this allows exfiltration of arbitrary local files (SSH keys, credential files, other private repositories on disk) into version-controlled content, which the victim could unknowingly commit and push, disclosing the material to the attacker's remote. This matches the "credential/token exfiltration" and "file read outside the repo" impact classes called out as valid.

## Likelihood Explanation
Likelihood depends entirely on the call sites in `app/src/lib/git/checkout.ts` — specifically whether `allowFileProtocol: true` is passed for checkouts that follow fetching an untrusted remote/PR branch, versus only for locally-created/trusted submodules. I was not able to fully inspect the three call sites in `checkout.ts` before running out of tool iterations, so **I cannot confirm with certainty that the vulnerable path is reachable without additional trust gating** (e.g., it's possible the flag is only set `true` for repositories the user has already explicitly added/cloned, in which case this would not qualify as unprivileged). This needs direct verification of `checkout.ts` before treating this as a confirmed, exploitable issue.

## Recommendation
- Audit every call site of `updateSubmodulesAfterOperation` in `app/src/lib/git/checkout.ts` (and any equivalent in `fetch.ts`/`pull.ts`) to confirm `allowFileProtocol` is never `true` for submodule updates triggered by checking out branches/PRs originating from remotes the user has not explicitly trusted.
- Default to Git's safe `protocol.file.allow=user` (i.e., do not pass `always`) for any submodule update that is not the result of a fully user-initiated, already-trusted local operation.
- If `file://` submodules must be supported for legitimate local-development workflows, surface an explicit warning/confirmation dialog (similar to the existing "Trust Repository" unsafe-directory flow) before allowing `protocol.file.allow=always`.

## Proof of Concept
1. Attacker creates a repository (or PR branch) containing a `.gitmodules` file with:
   ```
   [submodule "leak"]
       path = leak
       url = file:///home/victim/.ssh
   ```
2. Victim fetches/checks out this branch in GitHub Desktop.
3. If the code path in `checkout.ts` that calls `updateSubmodulesAfterOperation` passes `allowFileProtocol: true` for this checkout, `git submodule update --init --recursive -c protocol.file.allow=always` executes and copies objects from `/home/victim/.ssh` into the `leak` submodule's object store, making the victim's private key content part of the checked-out repository, ready to be committed/pushed.

**Caveat:** Step 3's precondition (that `checkout.ts` actually sets `allowFileProtocol: true` for this untrusted flow) is unverified due to tool budget exhaustion; a Devin session with file access should read `app/src/lib/git/checkout.ts` in full to confirm or refute this before treating the finding as exploitable in production.
