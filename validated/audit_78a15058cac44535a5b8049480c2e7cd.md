### Title
Partial-commit patch generation re-fetches the working-directory diff and applies stale line-index selections, letting a repository-controlled file change silently corrupt what gets committed - (File: app/src/lib/git/apply.ts)

### Summary
The Sherlock finding is about a value (`amount`) supplied by the caller not being cross-checked against the value that actually governs execution (`msg.value`), so the two can silently diverge and the wrong quantity is used. The GitHub Desktop analog is `applyPatchToIndex()` in `app/src/lib/git/apply.ts`, which builds a partial-commit patch from a `WorkingDirectoryFileChange`'s line-index `selection` (computed against a diff snapshot the user reviewed in the UI) but re-fetches a *fresh* diff of the working directory right before formatting the patch, without ever verifying that the fresh diff still matches the one the selection was computed against.

### Finding Description
`applyPatchToIndex` does:
```
const diff = await getWorkingDirectoryDiff(repository, file)
...
const patch = await formatPatch(file, diff)
await git(applyArgs, repository.path, 'applyPatchToIndex', { stdin: patch })
``` [1](#0-0) 

`file.selection` is a `DiffSelection` that records selected/deselected line numbers by absolute index into a hunk (`file.selection.isSelected(absoluteIndex)`), and it was originally computed against whatever diff the renderer displayed to the user. [2](#0-1) 

`stageFiles()` in `app/src/lib/git/update-index.ts` calls `applyPatchToIndex` for every file with a `Partial` selection type, right before the commit is created via `createCommit`, without ever re-diffing/re-checking that the selection's indices still line up with the current on-disk content. [3](#0-2) 

Because `getWorkingDirectoryDiff` reads the file from disk *at commit time* rather than reusing the diff object that produced the selection, any change to the file’s line layout between "user reviews/selects lines in the diff view" and "commit is executed" is not detected. `DiffSelection` operates purely on line-index numbers, with no cross-check (e.g. hash of the underlying diff/hunk content) that the diff hasn't shifted: [4](#0-3) 

This means the "declared" quantity (the selected line indices, chosen against diff snapshot A) is trusted and blindly applied to a different "actual" quantity (the freshly fetched diff B) without ever asserting `A == B`, mirroring the `amount` vs. `msg.value` disconnect in the Sherlock report.

### Impact Explanation
If the working tree changes between the moment a diff is rendered/selected and the moment `applyPatchToIndex` regenerates the diff (e.g., a build tool, an editor auto-format/auto-save, a symlinked file whose target is swapped, or content mutated by a background process triggered when the repository is opened), the line indices in the stale `DiffSelection` can map onto different lines/hunks in the freshly fetched diff. `formatPatch` will then unknowingly stage additions/deletions the user never selected (or omit ones they did), and `git apply --cached` will apply that mismatched patch to the index. The net effect is silent corruption of what the user actually commits — additions or deletions can be included or dropped without any visible warning, which is exactly the class of impact called out as valid in the report criteria ("silent corruption of what the user commits or pushes").

### Likelihood Explanation
This requires a realistic window between diff selection and commit combined with an external actor/process altering the file's line structure in that window — e.g., a cloned/fetched repository whose tracked build tooling, format-on-save hook, or a background watcher rewrites the file after the user opens the "Changes" view but before they click "Commit." This does not require local/admin access beyond normal Desktop usage; it only requires an attacker-influenced repository (via its included tooling/hooks/scripts) or a race with another process the user runs against the same working directory — consistent with the "attacker controls a cloned/fetched repository" threat category, but the window is narrow and timing-dependent, so likelihood is moderate rather than high.

### Recommendation
Before applying the patch in `applyPatchToIndex`, re-validate that the diff used to compute `file.selection` still matches the freshly retrieved working-directory diff for that file (e.g., by comparing a checksum/version of the hunks or by re-diffing and rejecting/warning when hunk boundaries have shifted), rather than blindly trusting stale absolute line indices. Alternatively, capture and pass through the exact diff object the selection was made against (instead of re-fetching a new one at staging time), and fail the partial commit with a clear error if it no longer matches disk state.

### Proof of Concept
1. Open a repository in Desktop and modify `file.txt` so the diff view shows a hunk with lines `L1..L10`.
2. Select only line `L5` (an addition) for inclusion via the Changes view; this computes `file.selection` with absolute index for `L5`.
3. Before clicking "Commit," have another process (a file-watcher, a git hook, an npm `postinstall`/format script the repository ships with, or manual edit) insert 2 new lines above `L5`, shifting subsequent content down without changing the total selection state held by the renderer.
4. Click "Commit." `stageFiles` invokes `applyPatchToIndex`, which calls `getWorkingDirectoryDiff` and gets a new diff reflecting the shifted content, then calls `formatPatch(file, diff)` using the *old* absolute index for "L5" [5](#0-4) .
5. The generated patch selects whatever line is now at that absolute index (a different line than the user intended), and `git apply --cached` stages it — the resulting commit contains content the user never reviewed or explicitly selected, with no error or warning surfaced.
