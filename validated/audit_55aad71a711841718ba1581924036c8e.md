### Title
Hardcoded zero-slippage swap in `ArbWomUp3._deposit` enables front-running/sandwich theft of user funds - (File: wombat/ArbWomUp3.sol)

### Summary
The unprivileged, user-facing `incentiveDeposit()` entry point in `ArbWomUp3` allows any wallet to convert WOM into locked mWOM (mode 2). Internally it calls `SmartWomConvert.convert()` with a hardcoded `_minRec = 0`, removing all slippage protection on the underlying Wombat pool swap. This lets an attacker sandwich the victim's transaction in the mempool to extract the swap's value, directly matching the front-running bug class in the external report.

### Finding Description
`incentiveDeposit()` is externally callable by any wallet [1](#0-0) . For `_mode == 2` it calls the internal `_deposit()` function, which splits the user's WOM amount and routes half through `SmartWomConvert.convert()`, explicitly passing `0` as both `_convertRatio`... actually as `_minRec` and mode: [2](#0-1) 

This `convert()` call reaches `SmartWomConvert._convertFor`, which performs a real on-chain swap on the WOM/mWOM Wombat pool via the router and only reverts if the received amount is below `_minRec`: [3](#0-2) 

Because `ArbWomUp3` always supplies `_minRec = 0`, the check `if (convertAmount + amountRec < _minRec) revert MinRecNotMatch();` can never fail — the caller has no way to protect against price movement. An attacker watching the mempool can front-run the victim's `incentiveDeposit()` transaction with a trade that skews the WOM/mWOM pool price, let the victim's swap execute at the worsened price, and back-run to restore/profit from the price difference (a classic sandwich attack). This is architecturally identical to the reported `rolloverAndAddLiquidityForAccount()` front-running issue: an unprivileged multi-step router-like function that performs a DEX swap without allowing the caller to bound acceptable slippage.

### Impact Explanation
The resulting `mWom` from the swap is immediately locked into `mWomSV` on behalf of the victim (`ILocker(mWomSV).lockFor(mWomBal, _account)` at [4](#0-3) ), so the user cannot detect and retroactively cancel a bad execution — the value lost to the sandwich is a direct, irrecoverable theft of user funds transferred to the attacker via the pool trade. Because this concerns WOM being converted/locked into mWOM through `SmartWomConvert` (in-scope: "mWOM/SmartWomConvert minting"), it satisfies the direct-theft-of-user-funds impact bar.

### Likelihood Explanation
Likelihood is high: `incentiveDeposit(_mode=2)` is a normal unprivileged user action, requires no special permissions, and the vulnerable swap size is proportional to the deposit — attractive for MEV bots monitoring the mempool for any sizeable Wombat-pool-moving transaction. The zero-slippage parameter is hardcoded in the contract itself, so no caller-supplied protection is possible.

### Recommendation
Add a caller-supplied (or conservatively pre-computed on-chain via `estimateTotalConversion`) minimum-received parameter to `incentiveDeposit()`/`_deposit()` and forward it as `_minRec` to `SmartWomConvert.convert()` instead of hardcoding `0`. Alternatively, use a private mempool/relay (e.g., Flashbots-style) for this swap, or bound acceptable slippage against `SmartWomConvert.estimateTotalConversion()` computed at call time with a maximum allowed deviation.

### Proof of Concept
1. Attacker monitors mempool for `ArbWomUp3.incentiveDeposit(_amount, _convertRatio, _bullMode, _mode=2)` transactions.
2. Attacker front-runs by swapping WOM→mWOM (or the reverse) on the same Wombat pool (`womMWomPool`) to shift the pool price unfavorably for the pending victim swap.
3. Victim's transaction executes: `_deposit` calls `smartWomConvert.convert(toSwap, _convertRatio, 0, 0)` → `_convertFor` swaps `buybackAmount` WOM for mWOM via `IWombatRouter.swapExactTokensForTokens(..., 0, ...)` at the manipulated price, returning fewer mWOM than a fair-price execution would [5](#0-4) ; the `_minRec` check never blocks this outcome since `_minRec == 0`.
4. Attacker back-runs, reversing their initial swap and pocketing the price-difference profit extracted from the victim's now-locked, under-received mWOM position.
