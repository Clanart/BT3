### Title
Cooldown-pending vlMGP unlocks continue to earn full MGP emissions in `MasterMagpie`, diluting/stealing yield from actually-locked voters - ([File: VLMGP.sol], [File: rewards/MasterMagpie.sol])

### Summary
When a user calls `VLMGP.startUnlock()` to begin unlocking their vote-locked MGP, the amount transitioning into cooldown is **not** removed from the staking balance that `MasterMagpie` uses to calculate MGP emission rewards. The amount keeps its full weight in `MasterMagpie`'s `userInfo[vlmgp][user].amount` and in the pool's `accMGPPerShare` accrual until the user actually finalizes the withdrawal by calling `unlock()`. This is the same root-cause pattern as the external report: tokens that are already economically "leaving" the vault/pool (a pending withdrawal has been committed) are not excluded from the reward-accounting base (`totalSupply`/`user.amount`), so they keep accruing yield that should belong to genuinely-locked participants.

### Finding Description
`VLMGP.startUnlock()` only updates internal bookkeeping — `userUnlockings[msg.sender]` and `totalAmountInCoolDown` — but never calls `IMasterMagpie(masterMagpie).withdrawVlMGPFor(...)`: [1](#0-0) 

The user's staking amount inside `MasterMagpie` is only reduced when `_unlock()` is finally invoked (from `unlock()` or `forceUnLock()`), which calls `withdrawVlMGPFor` → `_withdraw` → `_harvestAndUnstake`, decrementing `user.amount`: [2](#0-1) [3](#0-2) 

Meanwhile, `MasterMagpie.updatePool()` distributes new MGP emissions pro-rata across `lpSupply` (derived from `vlmgp.totalSupply()`, i.e. `totalAmount`) and each user's `accMGPPerShare` accrual is based on `user.amount`: [4](#0-3) [5](#0-4) 

`VLMGP.totalSupply()` itself also stays unchanged when a slot enters cooldown — it only decreases in `_unlock()`: [6](#0-5) 

Because neither `user.amount` nor the pool's `lpSupply` shrink when cooldown starts, a user in cooldown continues to earn the exact same share of newly-minted MGP emissions as a user who is still actively locking/voting — for the entire `coolDownInSecs` period, and indefinitely afterward if they simply delay calling `unlock()`. Contrast this with `vlMGPBaseRewarder`, which uses `getRewardablePercentWAD()` to intentionally decay a cooling-down user's share of secondary reward tokens over time, indicating the protocol is aware such positions should not receive full rewards, yet this decay is never applied to the primary MGP emission accounted for in `MasterMagpie`.

### Impact Explanation
Because cooldown balances are not excluded from `MasterMagpie`'s reward-accounting base, they continue drawing a full share of MGP emissions that should accrue only to genuinely-committed (still locked/voting) vlMGP holders. Since the total emission rate per pool is fixed, this directly dilutes and effectively transfers unclaimed MGP yield away from actively-locked participants to users who have already begun exiting — and who can extend this indefinitely by simply delaying their `unlock()` call after `endTime` passes. This is a theft of unclaimed yield from other, unprivileged, actively-participating users, reachable purely by an ordinary wallet's own transactions (`lock` → `startUnlock` → delay `unlock`).

### Likelihood Explanation
High. Any vlMGP holder can trigger this simply by calling `startUnlock()` and then withholding the final `unlock()` call — no special permissions, no dependency on other actors, and no time-bound cost since MGP emissions keep flowing to `user.amount` regardless of cooldown/completion status.

### Recommendation
When `startUnlock()` moves an amount into cooldown, `MasterMagpie` accounting (`user.amount`, `lpSupply`/`totalSupply` used in `accMGPPerShare`) should be reduced by that amount immediately (e.g., by actually calling `withdrawVlMGPFor` at `startUnlock` time, or by having `MasterMagpie` query `getUserTotalLocked()` instead of raw staked balance when computing rewardable amounts), so that cooling-down/pending-unlock balances stop earning newly emitted MGP rewards, consistent with how `vlMGPBaseRewarder` already decays secondary rewards via `getRewardablePercentWAD()`.

### Proof of Concept
1. User A and User B each lock 1,000 MGP via `VLMGP.lock()`, each acquiring equal weight in the vlMGP pool inside `MasterMagpie`.
2. User A calls `startUnlock(1000)`. Per `VLMGP.sol` lines 275-311, this only updates `userUnlockings`/`totalAmountInCoolDown`; `MasterMagpie.userInfo[vlmgp][A].amount` is untouched.
3. Time passes; `MasterMagpie.updatePool()` accrues MGP rewards proportionally to `user.amount` for both A and B — A still receives the same share as B despite having initiated a full unlock.
4. `coolDownInSecs` elapses, but User A defers calling `unlock()` indefinitely, continuing to farm full MGP rewards on funds it has already economically exited from voting/locking.
5. When A eventually calls `unlock()`, `_unlock()` finally reduces `user.amount`/`totalAmount`, but by then A has captured MGP emissions during the entire cooldown-plus-delay window that should have gone solely to committed lockers like B, permanently diluting B's earned share.

    function updatePool(address _stakingToken) public whenNotPaused {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        if (block.timestamp <= pool.lastRewardTimestamp || totalAllocPoint == 0) {
            return;
        }
        uint256 lpSupply = _calLpSupply(_stakingToken);
        if (lpSupply == 0) {
            pool.lastRewardTimestamp = block.timestamp;
            return;
        }        
        uint256 multiplier = block.timestamp - pool.lastRewardTimestamp;
        uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) / totalAllocPoint;
        
        pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
        pool.lastRewardTimestamp = block.timestamp;

        emit UpdatePool(
            _stakingToken,
            pool.lastRewardTimestamp,
            lpSupply,
            pool.accMGPPerShare
        );
    }

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
