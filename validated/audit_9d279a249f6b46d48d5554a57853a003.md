### Title
Sybil sub-account congestion bypasses spammer-eviction fairness in `TxPool`, allowing a single attacker to monopolize pending slots - ([File: blockchain/tx_pool.go])

### Summary
The SlowMist report describes an EOS "transaction congestion attack" in which an attacker splits activity across many "trumpet" (sock-puppet) accounts to flood the transaction layer and starve legitimate users' transactions from being processed in time, winning a game that depends on transaction ordering/inclusion timing. The same bug class maps directly onto Kaia's `TxPool` fairness/eviction logic: the pool's spammer-equalization mechanism only targets addresses whose pending list exceeds `ExecSlotsAccount`, so an attacker who spreads transactions across many distinct addresses (each individually below the per-account cap) is never selected for eviction, even though in aggregate they can occupy the entire `ExecSlotsAll` global pending budget and shut out single-address honest users.

### Finding Description
`TxPool.promoteExecutables` enforces global pending-slot fairness only by building a priority queue of "spammer" addresses defined as accounts whose pending list length exceeds `pool.config.ExecSlotsAccount`: [1](#0-0) 

Only entries in this `spammers` queue are ever capped/evicted when the aggregate `pendingCount` exceeds `ExecSlotsAll`: [2](#0-1) 

Because eviction eligibility is keyed per-address and gated on exceeding `ExecSlotsAccount`, an attacker who registers many distinct sender addresses and submits at most `ExecSlotsAccount` transactions from each one never appears in `spammers`. There is no cross-address aggregate throttling of a single actor's total footprint (e.g., by IP, funding source, or coordinated submission), and `HandleTxMsg`'s spam throttler only classifies txs based on the `to`-address of previously *failed* transactions, not on sender fan-out: [3](#0-2) 

As a result, an attacker can use N sub-accounts (each funded with minimal balance) to occupy up to `N * ExecSlotsAccount` pending slots, filling `ExecSlotsAll` entirely with the attacker's own transactions before a legitimate single-account user's transaction can be promoted, since promotion/eviction ordering treats each sub-account as an independent low-usage participant that is exempt from the equalization sweep.

### Impact Explanation
This lets a single economic actor (via Sybil sender accounts, each of which any unprivileged party can create for free) monopolize the executable transaction pool's global capacity, denying honest single-account senders inclusion into pending state and therefore into blocks in a timely manner. For any application whose fairness depends on transaction ordering/timely inclusion (auctions, games, time-sensitive settlement, gasless relays), this produces a concrete unfair-advantage/value-diversion outcome analogous to the reported EOS incident, where attackers used multiple accounts to congest transaction processing and extract disproportionate rewards. This is a Medium-severity availability/fairness degradation of the mempool's admission fairness guarantees rather than a direct fund-theft bug, but it can be leveraged to bias outcomes of on-chain games/auctions that rely on FCFS or near-real-time inclusion.

### Likelihood Explanation
Likelihood is Medium-High: the attack requires no special privileges — only the ability to generate multiple EOA private keys and fund each with the minimal balance needed to submit `ExecSlotsAccount` transactions (a cost trivially amortized against game/auction rewards, exactly as in the original incident). No governance, staking, or node-operator access is required; the sender only needs ordinary transaction-submission rights via the public RPC/p2p tx-broadcast paths that feed `AddRemotes`/`addTxsLocked`.

### Recommendation
Add a cross-address fairness dimension to `promoteExecutables`'s equalization logic that also considers correlated submission patterns (e.g., group by originating peer/IP at the p2p ingestion layer, or apply a global per-time-window admission budget independent of address count) rather than relying solely on `ExecSlotsAccount` per unique address. Alternatively, tighten `HandleTxMsg`'s `SpamThrottler` to detect fan-out patterns (many distinct new addresses submitting to the same `to` target within a short window) instead of only reacting to previously failed transactions.

### Proof of Concept
1. Attacker generates `N` fresh keys and funds each with enough balance for `ExecSlotsAccount` transactions and gas.
2. Attacker submits `ExecSlotsAccount` transactions from each of the `N` addresses via `AddRemotes`, driving `pool.pendingCount` up to (or beyond) `ExecSlotsAll`.
3. Because each address's pending list length equals `ExecSlotsAccount` (not greater than it), none qualifies for the `spammers` priority queue built in `promoteExecutables` (`blockchain/tx_pool.go:1786-1792`), so no eviction occurs against the attacker's transactions.
4. A legitimate single-account user (e.g., a game participant) submits a transaction; since `pendingCount` is already at/near `ExecSlotsAll` and the attacker's slots aren't evicted, the honest user's transaction is delayed in the queue/non-executable state, mirroring the reported "transaction congestion" advantage gained by the EOS attacker's multiple "trumpet" accounts.

// HandleTxMsg transfers transactions to a channel where handleTxMsg calls AddRemotes
// to handle them. This is made not to wait from the results from TxPool.AddRemotes.
func (pool *TxPool) HandleTxMsg(txs types.Transactions) {
	if pool.config.DenyRemoteTx {
		return
	}

	// Filter spam txs based on to-address of failed txs
	spamThrottler := GetSpamThrottler()
	if spamThrottler != nil {
		poolSize := uint64(pool.all.Count())

		// Activate spam throttler when pool has enough txs
		if poolSize > uint64(spamThrottler.config.ActivateTxPoolSize) {
			allowTxs, throttleTxs := spamThrottler.classifyTxs(txs)

			for _, tx := range throttleTxs {
				select {
				case spamThrottler.throttleCh <- tx:
				default:
					logger.Trace("drop a tx when throttleTxs channel is full", "txHash", tx.Hash())
					throttlerDropCount.Inc(1)
				}
			}

			txs = allowTxs
		}
	}
