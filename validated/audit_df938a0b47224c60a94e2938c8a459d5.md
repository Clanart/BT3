Audit Report

## Title
`pending_delegator_rewards` on `VoteStateV4` is never decremented after block-reward distribution, causing repeated over-distribution against the same deposited balance and permanent withdrawal lock - (File: `programs/vote/src/vote_state/handler.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

## Summary
`pending_delegator_rewards` is only ever increased via `checked_add` when an unprivileged caller invokes `DepositDelegatorRewards`, and is read every epoch by `calculate_block_reward` as the basis for computing each delegator's share of the "block reward" pool that gets minted onto stake accounts. A repo-wide, exhaustive search for the exact field name `pending_delegator_rewards` across every file that references it turned up no write path that reduces the value after it is used in a distribution, meaning the same nominal deposit is treated as fresh reward budget every subsequent epoch while simultaneously being treated by `withdraw()` as an un-paid, un-closable debt forever.

## Finding Description
`VoteStateHandler::add_pending_delegator_rewards` performs a `checked_add` on `VoteStateV4::pending_delegator_rewards` and is the only mutator of this field found in the codebase [1](#0-0) , invoked from the unprivileged `DepositDelegatorRewards` instruction path in `programs/vote/src/vote_state/mod.rs` after a CPI transfer of lamports into the vote account [2](#0-1) .

Every reward epoch, `calculate_block_reward` reads this same field and computes each stake account's pro-rata share, clamped to the field's current value [3](#0-2) . The computed `block_reward` is then unconditionally credited to the stake account via `checked_add_lamports` in `build_updated_stake_reward`, with no corresponding write anywhere that reduces the *vote account's* `pending_delegator_rewards` [4](#0-3) .

I performed an exhaustive `grep_search` for the literal string `pending_delegator_rewards` across the entire repository. It appears in exactly nine files: `programs/vote/src/vote_state/mod.rs`, `vote_processor.rs`, `vote_state/handler.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`, `vote/src/vote_state_view/frame_v4.rs`, `vote/src/vote_state_view.rs`, `account-decoder/src/parse_vote.rs`, `cli-output/src/cli_output.rs`, `cli/src/vote.rs`. I inspected the relevant matches in each and found only: the getter `pending_delegator_rewards()`, the `checked_add`-only mutator, the `withdraw()` guard read, view/serialization/CLI display code, and test helpers that directly set the field for unit tests. None decrement it.

Meanwhile, `withdraw()` treats `pending_delegator_rewards` as principal still owed to delegators: it forbids closing the account while the value is `> 0`, and forbids withdrawing below `min_rent_exempt_balance + pending_delegator_rewards` [5](#0-4) . Because the field never decreases, once any non-zero deposit is made, the authorized withdrawer can never fully close the vote account, and the reward-calculation logic will compute a nonzero `block_reward` basis of the same magnitude on every subsequent epoch indefinitely, rather than the pool being consumed as it is paid out.

## Impact Explanation
This breaks fund/accounting-correctness invariants in the runtime reward-distribution path in two concrete ways: (1) the vote account's `pending_delegator_rewards` value used as the reward-distribution basis is never reconciled with lamports already paid out, so the *same* deposited amount is repeatedly used to compute delegator payouts epoch after epoch instead of being consumed once; and (2) the withdraw-guard invariant in `withdraw()` permanently and incorrectly treats the vote account as owing `pending_delegator_rewards` lamports even after that amount has already been distributed, blocking the authorized withdrawer from ever fully withdrawing or closing the account. Both are runtime/accounts-level accounting-correctness defects in the exact scoped files.

## Likelihood Explanation
The precondition (an unprivileged call to `DepositDelegatorRewards` with public inputs, followed by normal epoch-boundary reward processing) is trivially reachable and requires no privileged actor, malicious validator, or special timing — it only requires the SIMD-0123 vote-v4 / block-revenue-sharing feature set to be active. My confidence that no decrement exists is high because the search for the field name was exhaustive (9 files, all matches reviewed), but I was not able to fully trace the ultimate source of the lamports backing `block_reward` (i.e., whether the "epoch rewards" sysvar pool that funds `block_reward` payouts, debited in `update_epoch_rewards_sysvar`, is itself replenished from a bounded/finite reserve each epoch or from newly-available inflation). That funding-source detail affects whether the practical consequence is unbounded over-minting (fund theft) versus an eventual `checked_sub_lamports`/`expect` panic in `update_epoch_rewards_sysvar` when the sysvar pool is insufficient to cover a second round of payouts based on stale `pending_delegator_rewards` (a crash/consensus-halt outcome) — I could not conclusively distinguish between these two scenarios within the available tool budget.

## Recommendation
1. Confirm via full trace of `distribute_reward_commissions`, `store_stake_accounts_in_partition`, and the epoch-rewards sysvar funding logic whether `pending_delegator_rewards` is intended to be decremented per-epoch by the amount actually distributed as `block_reward`, and add that decrement in the same partitioned-distribution pass that credits stake accounts.
2. Add an invariant test asserting cumulative `block_reward` paid out for a vote account across N epochs does not exceed the total amount ever deposited via `DepositDelegatorRewards`.
3. Re-verify the `withdraw()` guard correctly reflects `pending_delegator_rewards` post-fix so the withdrawer is not indefinitely blocked once the pending amount has genuinely been paid out.

## Proof of Concept
1. Enable `commission_rate_in_basis_points`, `custom_commission_collector`, and `block_revenue_sharing` features.
2. Create a `VoteStateV4` account with one delegator stake account; call `DepositDelegatorRewards` once with `deposit = D` lamports, setting `pending_delegator_rewards = D`.
3. Advance through multiple reward epochs, using the existing test helper pattern `get_block_reward_for_test` [6](#0-5)  to invoke `calculate_block_reward` each epoch without any intervening write to `pending_delegator_rewards`.
4. Observe that `pending_delegator_rewards` remains `D` across all epochs and that each epoch's computed `block_reward` sum is bounded only by the unchanged `D`, and separately confirm via `withdraw()` that the account can never be closed while `D > 0`, even if `D` has already been paid out in full at least once [7](#0-6) .
