### Title
Panic on mislabeled `GeneratorProof` map in `GeneratorPromotion::complete` causes denial of service - ([File: crypto/dkg/promote/src/lib.rs](File: crypto/dkg/promote/src/lib.rs))

### Summary
`GeneratorPromotion::complete` validates only the *count* and *upper bound* of the participant-keyed proof map it receives, then unconditionally unwraps `proofs.get(&i)` for every expected participant. A proof map that satisfies the length and bounds checks but is missing a required participant (e.g., because it contains the local participant's own index, or any wrong-but-in-range index) causes a synchronous `None.unwrap()` panic, crashing the process. This mirrors the middie advisory class: a malformed/unexpected input passes initial validation and then escapes as a fatal panic in a routine expected to return an error.

### Finding Description
`complete` performs two checks on the caller-supplied `proofs: &HashMap<Participant, GeneratorProof<C1>>`:

1. `proofs.len() == n - 1` [1](#0-0) 
2. every key `i` satisfies `u16::from(i) <= params.n()` [2](#0-1) 

Neither check establishes that the key set equals `{1..=n} \ {params.i()}`. The subsequent loop then does `let proof = proofs.get(&i).unwrap();` for each `i` in `1..=n` other than the local index [3](#0-2) . Because `Participant` is a non-zero index type and the map is keyed by attacker-influenced participant labels (in deployment these keys are populated from coordinator-relayed messages naming which participant each proof came from), a participant can attach a proof under an incorrect index — including the verifier's own index `params.i()`, which is never rejected. The map then has the right size, all keys in range, yet is missing some required `j`, and `proofs.get(&j).unwrap()` panics.

A second `unwrap()` on `ThresholdKeys::new(...)` exists at the end [4](#0-3) , but the `proofs.get` unwrap is the directly attacker-reachable one.

`GeneratorProof::read` itself is safe (it delegates to `C::read_G` and `DLEqProof::read`, both of which return `io::Error` on malformed bytes) [5](#0-4) , so the panic is purely in the set-membership validation, not deserialization.

### Impact Explanation
An unhandled panic in `complete` aborts the calling task/process, exactly the denial-of-service shape of the reference advisory. In a validator/processor context, a single peer supplying a correctly-sized but incorrectly-keyed promotion proof set crashes every participant that runs promotion, halting the generator-promotion ceremony (used to migrate threshold keys between generators, e.g., substrate/Bitcoin) until restart and possibly repeatedly if the poisoned proof set is redelivered.

### Likelihood Explanation
Any peer participating in a promotion ceremony controls the `Participant` index under which their `GeneratorProof` is gossiped/recorded, since the library "does not handle networking" and trusts the caller-populated map. Attaching a valid proof under the wrong index — including the recipient's own index, which passes both guards — requires no valid signature knowledge beyond what an honest participant already produces, making this trivially triggerable by one faulty ceremony participant.

### Recommendation
Replace the count-and-bound checks with exact membership validation: iterate `1..=n` skipping `params.i()` and return `PromotionError::InvalidParticipant` (or a new `MissingParticipant` variant) when `proofs.get(&i)` returns `None`, instead of `unwrap()`. Equivalently, reject up front any `proofs` key equal to `params.i()` and verify `proofs.keys().copied().collect::<HashSet<_>>() == (1..=n).map(Participant).filter(|i| *i != params.i()).collect()`.

### Proof of Concept
```rust
// Assume a base ThresholdKeys<C1> for t-of-n with n = 3, local index i = 1.
let base: ThresholdKeys<C1> = /* our keys */;
let (promotion, our_proof) = GeneratorPromotion::<C1, C2>::promote(&mut rng, base.clone());

// Attacker-controlled map: contains OUR index (1) and participant 2,
// but is missing participant 3. len == n - 1 == 2 passes, all keys <= 3 pass.
let mut proofs: HashMap<Participant, GeneratorProof<C1>> = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), our_proof);   // self-index, not rejected
proofs.insert(Participant::new(2).unwrap(), p2_proof);    // valid in-range key

// Loop: i = 1 skipped (params.i()), i = 2 verified,
// i = 3 -> proofs.get(&Participant(3)) == None -> .unwrap() panics.
let _ = promotion.complete(&proofs); // thread panics instead of returning Err
```

Uncertainty note: reachability through the production `processor` crate is out of scope for this scan, so the concrete deployment path that feeds attacker-labeled `Participant` keys into `complete` was not verified; the vulnerability stands on the library API contract itself, which accepts an externally-populated `HashMap<Participant, _>` and documents no requirement that it contain exactly `{1..=n} \ {i}`.
