### Title
`EvmHost.dispatch()` never refunds leftover ETH from the internal fee-token swap, permanently trapping user funds - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` let a caller pay the protocol's relayer fee in native token by forwarding `msg.value`, which the Host then swaps via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. Unlike every other native-payment code path in this repo (`IntentGatewayV2.placeOrder`, `ExtrinsicIntents._fillOrder`, the `UniV3/UniV4UniswapV2Wrapper` contracts), `dispatch()` never checks the amount actually consumed by the swap and never returns the unspent remainder to the caller. [1](#0-0) 

### Finding Description
`swapETHForExactTokens` is an exact-output swap: it computes `amounts[0]` (the ETH actually required to buy `post.fee` fee-tokens) and, per the standard UniswapV2Router implementation, refunds any `msg.value - amounts[0]` surplus back to **its own caller** — which here is `EvmHost` itself (`address(this)` calls the router), not the end user who funded the transaction. [1](#0-0) [2](#0-1) 

Compare this with the pattern used everywhere else in the codebase that performs the identical swap: `IntentGatewayV2.placeOrder` captures the router's returned `amounts[0]`, decrements the locally tracked `msgValue`, and explicitly forwards the leftover back to `msg.sender`: [3](#0-2) 

and `ExtrinsicIntents._fillOrder` does the same for the solver's overpayment: [4](#0-3) 

`EvmHost.dispatch()` omits this step entirely — it discards the `amounts` return value of the swap (does not even capture it) and has no subsequent refund logic before returning `commitment`. Any ETH sent by the caller in excess of what the swap actually needed is retained inside the router call's `msg.sender`, i.e. the `EvmHost` contract's own balance, with no code path in `EvmHost.sol` that returns it to the original `dispatch()` caller. This is the exact bug class from the external report: exact-output swap leaves unspent input value stranded because the contract fails to forward the refund to the true payer.

### Impact Explanation
Every unprivileged caller of `EvmHost.dispatch(DispatchPost)` / `dispatch(DispatchGet)` who supplies `msg.value` slightly above the exact amount required by the swap (which is the normal case, since callers cannot know the router's precise `getAmountsIn` result at call time, and prices can move favorably between quote and execution) permanently loses that difference — it becomes ETH held by the `EvmHost` contract with no user-facing withdrawal path. This is a direct, unauthorized loss of user funds triggered purely through the intended public dispatch entrypoint, matching the bounty's "stealing or loss of funds" criterion. It requires no malicious relayer, prover, or governance actor — only a normal caller paying in native token.

### Likelihood Explanation
High. Any application built on `HyperApp`/`IDispatcher` that funds requests with native token via `dispatch{value: ...}()` directly (rather than going through `dispatchWithFeeToken` or manually pre-computing the router's exact quote) will trigger this on essentially every call, since matching `msg.value` to the router's exact required input to the wei is impractical for callers who don't simulate the swap beforehand. The sibling contracts in this very repo (`IntentGatewayV2`, `ExtrinsicIntents`) were evidently patched to add this refund, and their explicit foundry tests (`testPlaceOrder_FeeSwap_RefundsExcessNativeToken`, `testFillCrossChain_RefundsSolverExcessNativeToken`) confirm this is a recognized requirement — yet `EvmHost.dispatch()`, the lower-level primitive those contracts wrap, still lacks it. [5](#0-4) 

### Recommendation
In `EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)`, capture the `amounts` array returned by `swapETHForExactTokens` and refund `msg.value - amounts[0]` to `_msgSender()` (or to `post.payer`/`get`'s equivalent field) before returning, mirroring the pattern already implemented in `IntentGatewayV2.sol` and `ExtrinsicIntents.sol`.

### Proof of Concept
1. Deploy `EvmHost` with a configured `uniswapV2Router` and `feeToken`.
2. Caller `Alice` calls `host.dispatch{value: 5 ether}(DispatchPost{..., fee: X, payer: Alice})` where the router's `getAmountsIn(X, [WETH, feeToken])` resolves to, e.g., `0.01 ether`.
3. Internally, `swapETHForExactTokens{value: 5 ether}(X, path, address(this), block.timestamp)` spends `0.01 ether` and refunds `4.99 ether` — but the refund target is `address(this)` (the Host), not Alice.
4. `dispatch()` returns normally with `commitment` computed; Alice's transaction succeeds but she never gets back the `4.99 ether`, which now silently sits in `EvmHost`'s balance with no corresponding accounting or withdrawal function surfaced to her.
5. Repeat this for any caller — funds accumulate in the Host contract, inaccessible to the payers who lost them, confirmed by contrast with `IntentGatewayV2Test.sol`'s `testPlaceOrder_FeeSwap_RefundsExcessNativeToken`, which demonstrates the correct behavior is achievable and expected but is absent from `EvmHost.dispatch()`.

    function testPlaceOrder_FeeSwap_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1000 * 1e6;
        uint256 feeAmount = 1 * 1e18; // 1 DAI worth of fees

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1000 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 1000,
            nonce: 0,
            fees: feeAmount,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userEthBefore = user.balance;

        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        // Send 5 ETH for a fee swap that should cost much less
        intentGateway.placeOrder{value: 5 ether}(order, bytes32(0));
        vm.stopPrank();

        // User should get back most of the 5 ETH — the swap only needed a tiny fraction
        uint256 ethSpent = userEthBefore - user.balance;
        assertTrue(ethSpent < 1 ether, "User should have been refunded most of the 5 ETH");
        assertTrue(ethSpent > 0, "User should have spent some ETH on the fee swap");
    }
