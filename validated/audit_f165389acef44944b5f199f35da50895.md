### Title
OP_RETURN `data` output omitted from weight/vbytes accounting, so `needed_fee`, the min-relay check, and the max-weight check are all computed on a transaction smaller than the one actually signed - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes an attacker-influenced OP_RETURN output into `tx_outs` (lines 194-202) but then calls `calculate_weight_vbytes` with only `payments` (lines 204 and 226). The fee model `needed_fee = fee_per_vbyte * vbytes` is therefore computed over a transaction missing an output of up to ~89 vbytes (script_pubkey length prefix + `OP_RETURN` + push opcode + up to 80 bytes of data). This is the same bug class as the Carapace report: a term (`data` output weight) that should be part of the total is silently dropped, producing a systematically wrong "claimable"/needed amount that downstream logic trusts.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `calculate_weight_vbytes` builds a mock `Transaction` whose `output` list is derived solely from the `payments` slice plus an optional change output (lines 85-99). There is no parameter for the OP_RETURN output. `SignableTransaction::new`:

- pushes the data output onto `tx_outs` (lines 194-202),
- computes `(weight, vbytes)` from `payments` only (line 204),
- sets `needed_fee = fee_per_vbyte * vbytes` (line 206),
- enforces `needed_fee >= DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the same underestimated `vbytes` (line 211),
- enforces `input_sat >= payment_sat + needed_fee` with the underestimated fee (line 215),
- computes the change amount as `input_sat - (payment_sat + fee_with_change)` where `fee_with_change` is again computed without the data output (lines 225-233),
- and enforces `weight <= MAX_STANDARD_TX_WEIGHT` using the underestimated `weight` (line 241).

Every safety/accounting check is evaluated on a lighter transaction than the one serialized into `SignableTransaction.tx` (lines 245-255). The constructed `tx` object — including the OP_RETURN output — is what the threshold signers commit to via `taproot_key_spend_signature_hash` (lines 373-391).

### Impact Explanation
- **Fee rate violation**: the real transaction is up to ~89 vbytes larger than accounted for, so the effective sat/vbyte rate is strictly below `fee_per_vbyte`. Since `needed_fee` is returned and consumed by callers (e.g., `SignableTransaction::needed_fee`, `Network::needed_fee` amortization in `processor/src/networks/mod.rs`), every downstream participant acts on an incorrect fee figure.
- **Min-relay bypass**: a caller selecting `fee_per_vbyte` such that `needed_fee` equals exactly the minimum relay fee passes the check at line 211 but produces a transaction whose actual fee rate is below `DEFAULT_MIN_RELAY_TX_FEE`, so the signed transaction is rejected by the Bitcoin P2P network — a transaction the multisig signed that cannot be relayed, stalling the spend of those inputs.
- **Non-standard weight bypass**: `weight` checked at line 241 excludes the OP_RETURN output, so a transaction up to ~356 WU over `MAX_STANDARD_TX_WEIGHT` can pass the check and be signed, again yielding an unrelayable transaction.

The reachable, concrete consequence is the multisig producing a signed transaction that violates the stated fee/size bounds — funds are locked in a transaction that the network will not accept as constructed, and the "needed fee" value reported to callers is wrong.

### Likelihood Explanation
The trigger is simply `data.is_some()` with non-trivial length. The `data` parameter exists to carry `InInstruction`/arbitrary bytes supplied by external users depositing into the protocol (see `send_and_get_output`-style flows and the OP_RETURN encoding of `RefundableInInstruction` in `tests/processor/src/networks.rs`), so an unprivileged user who attaches up to 80 bytes of instruction data deterministically induces the undercount — no validator misbehavior, collusion, or leaked key is required. The error magnitude scales with data length and is largest exactly when users embed maximal data.

### Recommendation
Pass the constructed `tx_outs` (or equivalently the data output) into `calculate_weight_vbytes` instead of `payments`, i.e., compute weight/vbytes over the actual output set: `payments + OP_RETURN(data) + optional change`. Concretely, change the signature to accept the full `&[TxOut]` list and call it after the OP_RETURN push, both for the no-change fee (line 204) and the with-change recomputation (line 226). Alternatively, add the OP_RETURN output's serialized size (`9 + script_len` bytes ≈ up to ~356 WU) to the computed weight when `data.is_some()`.

### Proof of Concept
In `networks/bitcoin/src/wallet/send.rs`:

1. `tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(data) })` at lines 194-202 adds an output of `8 (value) + 1 (script len) + 1 (OP_RETURN) + 1+ (push) + data.len()` bytes.
2. `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204 and `... (tx_ins.len(), payments, Some(&change))` at line 226 never see that output — `calculate_weight_vbytes` (lines 85-99) only serializes `payments` and `change`.
3. Therefore `vbytes` (line 204) undercounts the final `tx` (lines 245-251) by `(10 + data.len())` bytes ≈ up to 89 vbytes for the 80-byte `TooMuchData` cap (line 171).
4. `needed_fee = fee_per_vbyte * vbytes` (line 206) and `fee_with_change = fee_per_vbyte * vbytes_with_change` (line 227) are both short by `fee_per_vbyte * (10 + data.len())` sats; `tx.fee()` (lines 138-141), computed as `sum(prevouts) - sum(tx.output)`, reveals the discrepancy only after construction.
5. Setting `fee_per_vbyte = 1` sat/vbyte with `data.len() = 80`: the check at line 211 requires `vbytes >= 1000`-scaled minimum; the signed transaction's true vsize is ~89 bytes larger, so its real fee rate is ~`needed_fee / (vbytes + 89)`, below the intended and potentially below the minimum relay rate, while the `TooLowFee` and `NotEnoughFunds` checks at lines 211-221 were evaluated against the smaller, incorrect figure.
