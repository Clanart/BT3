### Title
`ThresholdKeys::new`/`read` never verify the secret share matches its verification share, accepting unusable/inconsistent keys - (File: crypto/dkg/src/lib.rs)

### Summary
The reported bug class is an omitted post-construction step: the factory creates a `StakingRewards` contract but never completes the required handoff (`transferOwnership`/`acceptOwnership`), so the resource exists yet cannot actually be managed by its intended owner. In Serai, `ThresholdKeys::new` performs the analogous omission: it constructs a usable-looking `ThresholdKeys` object while skipping the consistency check that `C::generator() * secret_share == verification_shares[params.i()]`, and `ThresholdKeys::read` — a documented deserializer for untrusted bytes — funnels attacker-controlled data straight into it.

### Finding Description
`ThresholdKeys::new` validates only the *count* of verification shares (`verification_shares.len() == n`), the participant index range, and the interpolation applicability, then derives `group_key` solely from the verification shares of participants `1..=t`:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
``` [1](#0-0) 

It never confirms that the supplied `secret_share` is the discrete logarithm of `verification_shares[params.i()]`: [2](#0-1) 

`ThresholdKeys::read` reads `(t, n, i)`, the interpolation variant, the secret share, and `n` verification shares entirely from the reader, then calls `ThresholdKeys::new`: [3](#0-2) 

So an attacker (or corrupted/mismanaged storage) can hand a node a serialized `ThresholdKeys` whose secret share bears no relation to the claimed verification shares. The object is "created" successfully — every accessor (`group_key()`, `params()`, `view()`) works — but like the `StakingRewards` contract whose managing role was never transferred, it cannot actually perform its function: every signature share the holder produces will fail `verify_share` because `view()` computes the share from the bogus scalar while the rest of the group verifies against the verification-share-derived key: [4](#0-3) 

There is also a second-order integrity issue: `recover_key` (dkg-recovery) checks `G * recovered == group_key` only *after* summing views; an inconsistent member key with `Lagrange` interpolation contributes a garbage share that poisons the reconstructed secret, and the error is only caught at the end rather than at key admission.

### Impact Explanation
- A node fed a malformed `ThresholdKeys` blob accepts it as valid, then participates in FROST signing sessions where its share is guaranteed invalid. `AlgorithmSignMachine::sign` → `verify_share` will attribute blame to this participant (`FrostError::InvalidShare(i)`), ejecting/blaming an honest-in-intent signer and stalling threshold signing — funds controlled by the multisig become unspendable while the corrupted key persists.
- Conversely, an attacker who can write the serialized keys can set `verification_shares`/`group_key` arbitrarily while supplying a *known* secret share that does not match — any downstream code trusting `original_verification_share`/`group_key` derives an address/key the share-holder cannot sign for, or vice versa.
- Because the check is absent in `new`, every constructor path (`read`, `musig`, dealer `key_gen`, PedPoP `calculate_share`) relies on callers to have produced consistent inputs; `read` explicitly exposes this to arbitrary bytes.

### Likelihood Explanation
Exploitation requires an attacker to supply or corrupt the serialized `ThresholdKeys` consumed by `ThresholdKeys::read` (e.g., a restored/migrated key blob, or bytes relayed from an untrusted peer). That is within the stated threat model for `read_*` functions. The result is deterministic share invalidity rather than a probabilistic failure, and mis-blame falls on the victim participant. Severity: Medium — it yields signing DoS/mis-attributed blame and unspendable outputs, not direct key recovery.

### Recommendation
In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`), verify consistency before constructing:

```rust
if (C::generator() * secret_share.deref()) != verification_shares[&params.i()] {
  Err(DkgError::/* new variant: share doesn't match verification share */)?;
}
```

This mirrors PedPoP's `share_verification_statements` check (`crypto/dkg/pedpop/src/lib.rs:430-449`) and the `debug_assert_eq!(our_pub_key, verification_shares[&params.i()])` already present in `musig` (`crypto/dkg/musig/src/lib.rs:152`), closing the gap for the deserialization path where no protocol-level verification ever ran.

### Proof of Concept
```rust
// Serialize a ThresholdKeys whose secret_share does not correspond to
// verification_shares[i]; read() accepts it, signing then always fails.
let params = ThresholdParams::new(2, 3, Participant::new(1).unwrap()).unwrap();
let real_secret = Zeroizing::new(<Secp256k1 as Ciphersuite>::F::random(&mut OsRng));
let mut verification_shares = HashMap::new();
for i in 1 ..= 3u16 {
  let i = Participant::new(i).unwrap();
  // Attacker-chosen verification shares (not derived from our secret)
  verification_shares
    .insert(i, <Secp256k1 as Ciphersuite>::generator() *
      <Secp256k1 as Ciphersuite>::F::random(&mut OsRng));
}
// Currently succeeds despite the inconsistency
let keys = ThresholdKeys::new(params, Interpolation::Lagrange, real_secret, verification_shares)
  .unwrap();
// keys.group_key() is attacker-controlled; keys.view(..).secret_share()
// produces shares that can never pass verify_share against those
// verification shares -> deterministic InvalidShare blame on participant 1.
```
