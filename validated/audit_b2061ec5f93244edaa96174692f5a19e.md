## Analysis

This is a strong local analog to the `old_sum_bias`/`old_bias` mismatch: a helper struct is populated with the **wrong amount variable** — the raw, pre-fee order amount instead of the actually-escrowed (fee-reduced) amount — and that wrong value is later used to decrement an accounting balance, causing an arithmetic underflow that reverts and permanently locks escrowed funds.

### Title
Escrow refund path always underflows/reverts when a protocol fee was charged, permanently locking user funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder` escrows the **fee-reduced** amount per token (`reducedInputs[i].amount`) into `_orders[commitment][token]`, but every cancellation/refund path (`cancelOrder`'s same-chain, source-chain-GET, and destination-chain-RefundEscrow branches) builds the `WithdrawalRequest` using the **original, unreduced** `order.inputs` amounts. `withdraw()` then subtracts that oversized amount from the smaller escrowed balance, which underflows and reverts under Solidity 0.8 checked arithmetic whenever `protocolFeeBps > 0`, making cancellation permanently impossible and locking the user's escrowed tokens forever.

### Finding Description
In `placeOrder`, when `protocolFeeBps > 0`, the escrow bookkeeping stores the reduced amount: [1](#0-0) [2](#0-1) 

`_orders[commitment][token] += reducedInputs[i].amount;` — i.e. `originalAmount - protocolFee`.

Every cancellation branch in `cancelOrder`, however, constructs the `WithdrawalRequest.tokens` from `order.inputs` (the full, pre-fee amount), not `reducedInputs`:
- Same-chain path: `WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user})` [3](#0-2) 
- Source-chain (cross-chain GET) path context: `abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))` [4](#0-3) 
- Destination-chain RefundEscrow dispatch body: `abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))` [5](#0-4) 

`withdraw()` then only guards on the escrow being non-zero (not on it covering `amount`), transfers the oversized `amount`, and finally does an unguarded checked subtraction: [6](#0-5) 

Because `amount` (`order.inputs[i].amount`) is strictly greater than `_orders[body.commitment][token]` (`reducedInputs[i].amount`) whenever a protocol fee was applied, `_orders[body.commitment][token] -= amount` underflows and — since this line is outside any `unchecked` block — reverts the entire transaction under Solidity ≥0.8 checked arithmetic. This is the exact same bug class as the report: a "protective" subtraction (`Math.max(...) - old_bias`) that should use the invariant-consistent operand instead uses a mismatched one, breaking the accounting guard. Here it doesn't cause silent underflow (checked math catches it), but it makes the guard permanently unsatisfiable, which is functionally worse: **the refund path can never succeed**.

### Impact Explanation
Any order placed with a non-zero destination or source `protocolFeeBps` can never be cancelled/refunded through any of the three cancellation paths (same-chain, cross-chain-via-GET, cross-chain-via-RefundEscrow) — the transaction will always revert on the underflow. Since a filled order is claimed via the separate `RedeemEscrow` withdraw path (not analyzed here) and an unfilled order has no other exit route, the user's escrowed input tokens become permanently locked in the contract if no solver fills the order. This is a direct, unauthorized-permanent loss/lock of user bridged assets — squarely within the bounty's "stealing or loss of funds" impact category.

### Likelihood Explanation
This triggers deterministically, with no attacker action required, any time `_params.protocolFeeBps` (or a destination-specific override in `_destinationProtocolFees`) is non-zero and a user calls `cancelOrder` — a normal, expected, unprivileged user flow. It is not a griefing/DoS-only or malicious-actor-dependent bug; it is a straightforward accounting mismatch reachable via public entry points (`placeOrder` + `cancelOrder`).

### Recommendation
Use the same fee-reduced amounts that were actually escrowed when constructing every `WithdrawalRequest` in `cancelOrder` (mirror the `reducedInputs` computed in `placeOrder`, or recompute it identically from `order.inputs` and the applicable `protocolFeeBps`), so that `withdraw()`'s subtraction always matches the true escrowed balance.

### Proof of Concept
1. Admin sets `_params.protocolFeeBps = 100` (1%) via `setParams`/`UpdateParams`.
2. User calls `placeOrder` with `order.inputs[0].amount = 1000e6` USDC. `reducedInputs[0].amount = 990e6` is escrowed: `_orders[commitment][usdc] = 990e6`.
3. User calls `cancelOrder(order, options)` on the same chain (same-chain path).
4. `withdraw` is invoked with `body.tokens[0].amount = order.inputs[0].amount = 1000e6` (from step 1, not the escrowed 990e6).
5. `_orders[commitment][token] == 0` check passes (990e6 ≠ 0); the external transfer of `1000e6` is attempted (may itself fail if contract balance for that specific bookkeeping doesn't cover it, but assuming other orders' funds sit in the same pooled token balance it may succeed), then `_orders[commitment][usdc] -= 1000e6` → `990e6 - 1000e6` underflows → reverts.
6. The entire `cancelOrder` transaction reverts every time, for any caller, permanently — the user's 990e6 USDC stays locked in the contract with no path to recovery.
