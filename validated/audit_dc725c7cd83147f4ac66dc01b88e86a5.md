### Title
Payout OP_RETURN operator attribution is unauthenticated, letting anyone frame an uninvolved operator for reimbursement of a payout they never funded - (File: core/src/verifier.rs)

### Summary
`Verifier::update_finalized_payouts` attributes a confirmed payout transaction to whichever operator's x-only pubkey happens to be syntactically embedded in the payout's OP_RETURN output, without any check that this operator actually supplied the funding inputs of that transaction. Because the withdrawal input signature is `SinglePlusAnyoneCanPay`, anyone can reconstruct the payout transaction, keep the required user-authorized output untouched, and add an arbitrary OP_RETURN naming any real operator, causing that operator's own automation to later claim reimbursement for a payout it never made.

### Finding Description
The claimed binding is: `withdrawals.payout_payer_operator_xonly_pk` (recorded by `update_finalized_payouts`) `== the operator whose funds actually paid the withdrawal output`.

`update_finalized_payouts` extracts this attribution purely from OP_RETURN bytes with no cryptographic link to the transaction's actual funding inputs: [1](#0-0) 

`get_first_op_return_output`/`parse_op_return_data` only check that the bytes form a syntactically valid 32-byte value and, when parsed, a valid `XOnlyPublicKey` — no signature or spend-authority check ties this key to any input of the transaction: [2](#0-1) [3](#0-2) 

The root cause of exploitability is that the withdrawal input signature is `SinglePlusAnyoneCanPay`, enforced in `parse_withdrawal_sig_params`, and it is verified against only the payout output at index 0 in `Operator::withdraw`: [4](#0-3) [5](#0-4) 

`SIGHASH_SINGLE|ANYONECANPAY` binds only input 0 and output 0; it does not constrain any other input or output. `create_payout_txhandler` appends the OP_RETURN (with an arbitrary operator's xonly pubkey) as output index 2, entirely outside the signed commitment: [6](#0-5) 

The withdrawal input (`in_outpoint`), the required output (`out_script_pubkey`/`out_amount`), and the corresponding user signature are all public — they are submitted via the Citrea bridge contract's `withdraw` call. Consequently an unprivileged attacker can:
1. Read a pending withdrawal's `(in_outpoint, input_signature, output_script_pubkey, output_amount)` from Citrea.
2. Build their own transaction spending `in_outpoint` with output 0 exactly matching the signed commitment (adding attacker-funded inputs only if `in_outpoint`'s value is insufficient), output 1 as the anchor, and output 2 as an OP_RETURN containing any real, uninvolved operator's `xonly_pk`.
3. Broadcast and confirm it.

Once finalized, `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) stores `payout_payer_operator_xonly_pk = <victim operator>` for that withdrawal idx, purely because the syntactic parse succeeded, with no check that the victim operator's key ever signed or funded any input.

The impersonated operator's own automation then picks this up as its own unhandled payout: [7](#0-6) 

and calls `Operator::handle_finalized_payout`, which allocates a real, presigned kickoff connector belonging to that operator and proceeds toward reimbursement: [8](#0-7) 

None of the verifier-side guards catch this, because they only check *consistency* of the already-poisoned DB row against the kickoff, not whether the OP_RETURN attribution itself is authentic: [9](#0-8) 

`is_kickoff_malicious` only compares `operator_xonly_pk` (read from the same untrusted DB row) against `kickoff_data.operator_xonly_pk` and checks the committed payout blockhash — both of which trivially match since the impersonated operator's own node issued the kickoff using its own key against the (falsely attributed) DB record. There is no check anywhere in the flow that the inputs of the payout transaction were signed/funded by the credited operator's key.

### Impact Explanation
This breaks the "operator reimbursed for a payout it never funded" invariant explicitly listed as Critical impact: the escrowed `move_to_vault` bridge amount for that deposit is ultimately released via the impersonated operator's kickoff/reimburse transaction graph, crediting an operator that never funded the withdrawal. The attacker needs no operator role, collateral, key share, or aggregator access — only the ability to read public Citrea withdrawal data and broadcast a Bitcoin transaction. The attack is repeatable against any withdrawal and any registered operator whose x-only public key is known (operator pubkeys are public protocol parameters), so the blast radius spans all deposits/withdrawals and all operators.

### Likelihood Explanation
Preconditions are exactly the stated unprivileged-attacker capabilities: ability to observe a pending Citrea withdrawal's public `(input_outpoint, input_signature, output_script_pubkey, output_amount)` and to broadcast a Bitcoin transaction spending that outpoint with a custom OP_RETURN. No majority hashrate, key compromise, or privileged role is required. Cost to the attacker is bounded by any shortfall between the withdrawal input's value and the required output amount (which can be zero if the user-chosen input already covers it) plus a small CPFP fee via the anchor output. This is feasible on regtest/signet for a `cargo test` proof and repeatable across withdrawals/operators.

### Recommendation
Stop trusting the OP_RETURN payload as sole attribution. Options:
- Require the payout transaction's additional funding input(s) (beyond the user's own `in_outpoint`) to be provably controlled by the claimed operator (e.g., require a signature from the claimed operator's key over the payout tx, or require the OP_RETURN commitment to be combined with a signature check that at least one input's scriptPubkey resolves to the operator's known collateral/kickoff key).
- Alternatively, have the aggregator/operator's own `withdraw`/`internal_withdraw` RPC be the only path that produces the OP_RETURN-tagged payout tx, and have verifiers/operators cross-validate against that pre-registered candidate transaction (e.g., matching txid) before trusting the on-chain OP_RETURN attribution, rejecting attribution to any operator that did not pre-register/sign the exact confirmed transaction.

/// Parses the OP_RETURN data from a Bitcoin script. It retrieves the first data push after an OP_RETURN.
pub fn parse_op_return_data(script: &Script) -> Option<&[u8]> {
    let mut instructions = script.instructions();
    if let Some(Ok(Instruction::Op(opcodes::all::OP_RETURN))) = instructions.next() {
        if let Some(Ok(Instruction::PushBytes(data))) = instructions.next() {
            return Some(data.as_bytes());
        }
    }
    None
}

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
