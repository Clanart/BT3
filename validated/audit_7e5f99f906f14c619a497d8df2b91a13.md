## Analysis

The Sentiment report's core broken invariant: a category-wide restriction (delisting) was applied indiscriminately to *all* interactions with an asset, including interactions that must always remain safe/available (repayment/liquidation-style state that shouldn't be gated the same way as new borrowing). The bug is not "delisting exists" — it's that the restriction didn't distinguish "block new use" from "must still allow recovery of already-committed state."

The Hyperbridge analog is in `ProxyModule` in the nexus (Hyperbridge hub) runtime, where a hard-coded deny-list of deprecated `TokenGateway` contract addresses is applied identically to both *new* incoming requests and to *timeouts of already-dispatched requests*.### Title
Deprecated-TokenGateway deny-list on the nexus hub permanently blocks timeout delivery, locking funds in-flight when the ban is enacted - ([File: parachain/runtimes/nexus/src/ismp.rs])

### Summary
The nexus runtime's `ProxyModule` (the ISMP hub callback used for both routing and locally-terminating messages) applies a hard-coded deny-list, `DEPRECATED_TOKEN_GATEWAY_ADDRESSES`, unconditionally to **both** `on_accept` (new incoming Post requests) **and** `on_timeout` (Post-request timeouts). <cite repo="blackvul/hyperbridge--014" path="parachain/runtimes/nexus/src/ismp.rs" start="49="61" /> [1](#0-0) [2](#0-1)  Just as the Sentiment `AccountManager` blocked new deposits of a delisted asset but failed to separate "block new use" from "must still process existing/already-committed state," this code blocks new requests from the deprecated `TokenGateway` (correct) but also blocks the timeout path for the same address (incorrect) — the exact category of interaction that exists specifically to let users recover funds that are already locked.

### Finding Description
`is_deprecated_token_gateway` checks the message's `from`/`post.from` field against a static list of legacy `TokenGateway` contract addresses on Ethereum/Arbitrum/Optimism/Base/BSC/Gnosis/Polygon/Unichain/Soneium. [3](#0-2) 

In `on_accept`, this check runs first and rejects unconditionally, "regardless of destination" (before either the forward-onward path for `dest != HostStateMachine` or the locally-dispatched path) — which is a reasonable way to stop *new* teleports through the deprecated module. [4](#0-3) 

But the identical check is also applied in `on_timeout`:
```
if let Request::Post(post) = &timeout {
    if is_deprecated_token_gateway(&post.from) {
        return Err(anyhow!(
            "rejecting Post-request timeout from deprecated TokenGateway address {:?}",
            post.from,
        ));
    }
}
``` [2](#0-1) 

A Post request's `from` field identifies the *sending* module on the source chain that dispatched the cross-chain transfer (locking/burning the user's tokens), as documented for `pallet-token-gateway`: assets are locked/burned on dispatch and only unlocked/minted on successful delivery, with "funds from undelivered requests" recoverable "by submitting a timeout message." [5](#0-4) 

Because nexus acts as the Hyperbridge routing hub for cross-chain messages (forwarding when `dest != HostStateMachine`, as seen symmetrically in `on_accept`), any in-flight Post request that was dispatched from one of these now-deprecated `TokenGateway` addresses *before* the address was added to the deny-list, and that subsequently times out, has its timeout message rejected by the hub. The timeout can never be delivered to the destination-side callback that would normally free the escrow/refund the user, because the deny-list check fires before any routing or destination-aware logic and returns an `Err`, which — per the ISMP request/response handler pattern seen elsewhere in this codebase — causes the receipt to be deleted for retry, but retries hit the exact same unconditional rejection every time. [6](#0-5) 

This is the direct structural analog to M-11: the guard was designed to stop *new* exposure to a deprecated/risky component, but it was implemented as a blanket address match applied to *all* message kinds from that address, rather than being scoped only to the "new use" entrypoint. The timeout path — which functionally is the escrow-recovery/liquidation-equivalent path that must always remain available — was swept into the same restriction.

### Impact Explanation
Any user (or the `pallet-token-gateway` deployment itself, acting on their behalf) who initiated a cross-chain teleport through one of the listed deprecated `TokenGateway` contracts, whose request has not yet been delivered when the deny-list was enacted, has their tokens permanently locked in the source chain's custody/burn state with no recovery path: the destination never delivers (nothing stops delivery being attempted before deprecation, but any request still pending after deprecation and later timing out cannot be un-stuck), and the timeout that would normally trigger a refund is rejected by the hub every time it is resubmitted. This is an unconditional, permanent loss of user funds caused purely by protocol-level maintenance action (deprecating an old module), not by any external attacker — but it is a genuine "loss of funds" bug in the bridge's fund-custody path, matching the bounty's stated impact category.

### Likelihood Explanation
This is deterministic, not probabilistic: it happens automatically to every pending Post request from a deprecated address the moment its timeout fires after the deny-list is live. Given that TokenGateway timeouts are the sole recovery mechanism (per the docs, "funds from undelivered requests can be recovered by submitting a timeout message"), any transfer in-flight at the exact time the deprecation list was rolled out is guaranteed to hit this path and be permanently stuck. This requires no privileged action, no malicious relayer, and no race condition beyond ordinary bridge latency.

### Recommendation
Do not apply the deprecated-address deny-list to `on_timeout`. Timeouts must always be deliverable regardless of whether the originating module has since been deprecated, since they exist specifically to unwind state that was already committed under the old rules. Scope the deny-list check to `on_accept` only (blocking new requests), and remove it from `on_timeout`, mirroring the recommended fix pattern from the referenced report: split "gate new usage" from "always allow unwind/recovery of already-committed state."

### Proof of Concept
1. A user calls `teleport` on `pallet-token-gateway`, locking/burning tokens and dispatching a Post request whose `from` equals one of the (soon to be) deprecated `TokenGateway` addresses, e.g. `Fd413e3AFe560182C4471F4d143A96d3e259B6dE`.
2. Before the destination chain processes the request, Hyperbridge governance adds this address to `DEPRECATED_TOKEN_GATEWAY_ADDRESSES` in the nexus runtime (a normal, expected maintenance action when migrating to `pallet-hyper-fungible-token`). [7](#0-6) 
3. The request subsequently times out (e.g. destination congestion, relayer downtime, or simply because the request's timeout window elapses).
4. A relayer submits the timeout message through the nexus hub; `ProxyModule::on_timeout` matches `is_deprecated_token_gateway(&post.from)` and returns `Err(...)` unconditionally, before any routing/destination logic runs. [2](#0-1) 
5. The ISMP core handler treats the failed callback as retryable and deletes the receipt, but every subsequent resubmission of the same timeout message hits the identical deny-list check and fails again. [6](#0-5) 
6. The user's locked/burned tokens on the source chain are never refunded — permanently lost with no available recovery mechanism.
