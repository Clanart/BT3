### Title
Governance-only actions in `ExtrinsicIntents.onAccept` are authorized by source-chain identity instead of sender-module identity, allowing any Hyperbridge-chain module to forge privileged calls - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`ExtrinsicIntents::onAccept` (and its Tron twin `IntentGatewayV2.sol::onAccept`) gates privileged actions — `NewDeployment`, `UpdateParams`, `SweepDust`, `UpgradeContract` — with a single check that the incoming request's `source` equals the configured Hyperbridge state-machine id, but never checks `request.from` (the specific module/pallet that dispatched it on that chain). This is the same broken-invariant class as the Jet audit finding: authority is inferred from a coarse identifier (account ownership / chain identity) instead of verifying the precise authorized entity (account type+ownership, or specific module) that is allowed to trigger the privileged path.

### Finding Description
For the two "user" request kinds, the contract calls `_authenticate`, which validates both the source chain **and** the specific sender module address on that chain: [1](#0-0) 

But for the privileged kinds, the only check performed is: [2](#0-1) 

`incoming.request.source` is compared against `IDispatcher(host()).hyperbridge()`, which is documented as "The state machine identifier for hyperbridge" — i.e. the chain-level id of the Hyperbridge parachain, not a specific pallet/module identity: [3](#0-2) 

`request.from` — the field that identifies *which module on that chain* produced the request, and is exactly what `_authenticate` checks for the RedeemEscrow/RefundEscrow path — is never inspected for `NewDeployment`, `UpdateParams`, `SweepDust`, or `UpgradeContract`. On the ISMP dispatch side, `source` is always set to `host_state_machine()` regardless of which pallet or account triggers the dispatch, as seen in the generic ISMP handler and dispatcher code paths (`modules/ismp/core/src/handlers/request.rs`, `modules/pallets/ismp/src/dispatcher.rs`), so `source` alone carries no information about the authorized sender within the chain. Any pallet on the Hyperbridge chain capable of invoking `IsmpDispatcher::dispatch_request` with an attacker-influenced `to`/`body` (a documented, standard integration pattern illustrated for example modules in `docs/content/developers/polkadot/receiving.mdx`) can therefore produce a `PostRequest` whose `source` trivially satisfies this check, while `from` can be set to anything the dispatching pallet uses as its own module id — since the EVM-side check never inspects it.

The exact corrupted value is `incoming.request.from`: it is decoded/available but silently unused in the governance branch of `onAccept`, breaking the invariant that privileged remote calls must be traceable to one specific, pre-registered authorized module — not merely "some module on the correct chain."

### Impact Explanation
If exploited, this allows unauthorized execution of `SweepDust` (drains accumulated protocol dust to an attacker-chosen beneficiary), `UpdateParams` (rewrites protocol fee/config state), `NewDeployment` (poisons the `_instances` mapping used by `_authenticate` to trust a malicious "gateway" on some chain, which then unlocks the RedeemEscrow/RefundEscrow path for arbitrary fund withdrawal), and `UpgradeContract` (a full proxy takeover). This directly matches the bounty's "stealing or loss of funds," "unauthorized transaction or execution," and "false proof/state acceptance via wrong module binding" categories.

### Likelihood Explanation
Exploitability depends on whether any non-privileged/non-governance pallet on the Hyperbridge chain can dispatch a `PostRequest` with an attacker-controlled `to` (targeting the `ExtrinsicIntents`/`IntentGatewayV2` contract address) and body. I was not able to fully trace, within the available context, the specific pallet (likely `host-executive` or `intents-coprocessor`, both of which reference dispatch in `modules/pallets/host-executive/src/lib.rs` and `modules/pallets/intents-coprocessor/src/lib.rs`) that is intended to be the sole authorized sender of these governance messages, nor confirm whether its dispatch extrinsic is restricted to a privileged/root origin. This is the key open question: if that dispatch path is Root/governance-gated on the Substrate side, the missing `from` check is a defense-in-depth gap rather than a directly reachable unprivileged exploit; if any signed-user-triggerable pallet path can set `to`/`body` freely, the vulnerability is directly and trivially exploitable by an unprivileged attacker. Given the index's coverage limits, this should be verified with a full read of the relevant dispatcher pallet before treating likelihood as confirmed-high; regardless, the missing module-identity check is a real, locally-provable code defect independent of that follow-up.

### Recommendation
In `onAccept`, for `NewDeployment`, `UpdateParams`, `SweepDust`, and `UpgradeContract`, additionally verify `incoming.request.from` matches an explicitly configured, single authorized governance module id (analogous to how `_authenticate` checks `_instance(request.source)` for the escrow paths), rather than relying solely on `request.source == hyperbridge()`.

### Proof of Concept
1. Identify or use any pallet on the Hyperbridge parachain capable of calling the generic ISMP dispatcher (`Ismp::dispatch_request` / `IsmpDispatcher`) with a caller-supplied `to` and `body`.
2. Dispatch a `PostRequest` with `dest` = the target EVM chain, `to` = the deployed `ExtrinsicIntents`/`IntentGatewayV2` contract address, and `body` = `bytes1(uint8(RequestKind.SweepDust)) || abi.encode(SweepDust{...})` naming an attacker-controlled beneficiary.
3. Because ISMP always sets `source = host_state_machine()` for any Hyperbridge-originated request (see `evm/src/core/EvmHost.sol:63-66` for the `hyperbridge` chain-id field), the check `keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())` at `evm/src/apps/intentsv2/ExtrinsicIntents.sol:298` passes.
4. `onAccept` executes `_sweepDust(...)` (or `_addDeployment`/`_updateParams`/`ERC1967Utils.upgradeToAndCall`) without ever checking which module dispatched the message, since `evm/src/apps/intentsv2/ExtrinsicIntents.sol:299-308` never reads `incoming.request.from`.
