## Finding

Sei-chain's EVM↔Cosmos address association performs the analogous "switch without full sweep" pattern described in the Sherlock report, but for **vesting/locked balances** rather than yield-strategy funds — and the result is a genuine permanent-freeze, not just a temporary accounting glitch.

### Root cause

When an EVM key is associated with its real, pubkey-derived Sei address, `AssociateAddresses` calls `MigrateBalance` to move funds out of the "direct-cast" address (`sdk.AccAddress(evmAddr[:])`) into the real `seiAddr`: [1](#0-0) 

`MigrateBalance` explicitly sweeps `SpendableCoins` (line 66) and the wei balance (line 73), but never touches `LockedCoins` (vesting balances). The account under the cast address is only removed if `LockedCoins` is zero (line 79) — otherwise the account, and its locked coins, are left behind under the cast address.

This is confirmed by the existing unit test, which sets up a vesting account holding 1 `usei` under the cast address, runs the migration, and asserts the locked coin remains stuck at the cast address while the real `seiAddr` only receives the spendable portion: [2](#0-1) 

### Why this becomes a permanent freeze (not just a temporary imbalance)

Once true association is established, all future EVM transactions from that private key resolve to the real, pubkey-derived `seiAddr` (via `derived.SenderSeiAddr`) rather than the direct-cast identity: [3](#0-2) [4](#0-3) 

The direct-cast address is only usable as a signer identity for *unassociated* EVM accounts (a special-cased bridging mechanism); a native Cosmos-SDK signature check requires the signer address to be the hash of the supplied pubkey, which the EVM cast address is not. So after association, there is no remaining transaction path — EVM or Cosmos-native — that can authorize spending from the cast address. Any coins left locked there (typically vesting grants sent to the EVM address before association) become permanently unreachable, mirroring the "funds get stuck in the old strategy/identity" bug class from the report, except here the loss is not recoverable at all (the Sherlock report's bug could be fixed after-the-fact by re-adding the old strategy; here there is no equivalent recovery path).

The exact same gap exists in the legacy/versioned copies of this helper (`utils/helpers/legacy/v575/associate.go`, `utils/helpers/legacy/v600/asssociate.go`), and in the batch migration used elsewhere (`x/evm/migrations/migrate_cast_address_balances.go`) which only migrates `SpendableCoins`/wei and never locked coins either.

### Reachability

This is triggered by an ordinary, unprivileged flow: any account can receive a vesting grant to an EVM address's cast Sei address (e.g., via a Cosmos-native vesting account creation or `MsgSend` targeting that address before association), and then the owner of that EVM key sends any normal EVM transaction (or calls `addr` precompile's `associate`/`associatePubKey`), which triggers `AssociateAddresses`/`MigrateBalance` and permanently strands the vested balance.

### Recommendation

`MigrateBalance` should also migrate `LockedCoins`/vesting state (e.g., by transferring the underlying vesting account's balance and vesting schedule to `seiAddr`, or by refusing to leave a locked balance behind — e.g., failing the association, or forcing vesting-account migration) instead of silently leaving locked coins stuck at an address that becomes unreachable once real association exists. func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}

	// set a vesting account of 1
