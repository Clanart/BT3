### Title
Unchecked type assertion on attacker-controlled CW20/CW721 query response causes node panic in `pointer` precompile - (File: precompiles/pointer/pointer.go)

### Summary
This is analogous to CVE-2019-6456's root cause class: a parsing routine dereferences/casts a value obtained from external, attacker-influenced input without checking that the value is present and of the expected type before use, causing a crash. In `librec`, `rec_fex_size()` dereferences a NULL pointer from malformed input. In sei-chain, the `AddCW20` (and `AddCW721`) handlers of the `pointer` precompile perform an unchecked Go type assertion `formattedRes["name"].(string)` / `formattedRes["symbol"].(string)` on a JSON map populated from a CosmWasm contract's own query response, which is fully attacker-controlled.

### Finding Description
`AddCW20` in the current `pointer` precompile queries the target CW20 contract for `token_info`, unmarshals the JSON reply into a generic `map[string]interface{}`, and then performs unchecked type assertions: [1](#0-0) 

If the contract-supplied JSON response omits the `name`/`symbol` keys (map lookup returns `nil`) or provides them as a non-string JSON type (e.g. a number, boolean, `null`, object, or array), the single-value type assertion `.(string)` panics with `interface conversion: interface {} is nil/int/... not string`, since it does not use the two-value `v, ok := x.(string)` form. This exact pattern is present unmodified in effectively every historical version of the precompile: [2](#0-1) [3](#0-2) 
and the `AddCW721` variant that queries `contract_info` instead: [4](#0-3) 

The value being cast is not derived from the EVM caller's own ABI-encoded input (which is separately validated), but from `p.wasmdKeeper.QuerySmart`/`QuerySmartSafe` output of the *target CW20/CW721 contract address supplied as the pointer argument* — an address fully controlled by the transaction sender, who can deploy a malicious CosmWasm contract that replies to `token_info`/`contract_info` with a JSON object lacking `name`/`symbol` or containing non-string values for those fields.

### Impact Explanation
The `Precompile.Run` wrapper only recovers from `err` returned by `Prepare`/`Execute`; it has no `recover()` around the executor call itself: [5](#0-4) 
A Go runtime panic from the failed type assertion is therefore not converted into a reverted EVM call — it propagates up through the EVM's call stack during transaction execution. Whether this crashes the node or merely aborts the transaction depends on whether an outer recover exists in the transaction-execution/giga path; the codebase does show block/tx-level panic recovery in some execution paths (e.g. `app.go`'s giga synchronous executor recovers panics and converts them to `ErrPanic` results), so the ultimate blast radius (full node crash vs. tx-level abort with degraded execution) could not be conclusively confirmed from available context. In the worst case (no recover present on the path invoked), this can crash the node executing/validating the block, which would meet the "crash of default-configuration RPC/consensus node" or "validator halt" impact bar. At minimum, it is a reachable unhandled panic triggered entirely by an unprivileged EVM transaction sender registering a pointer for a contract they deploy and control.

### Likelihood Explanation
High: any account can deploy a trivial CosmWasm contract whose `token_info`/`contract_info` query handler returns JSON without `name`/`symbol` fields (or with wrong JSON types), then call `registerPointer`/`AddCW20Pointer` (or the CW721 equivalent) on the `pointer` precompile with that contract's address as `cwAddr`. No special privileges, precompile authority, or governance action is required — this is a single, arbitrary EVM transaction.

### Recommendation
Replace the unchecked single-value type assertions with the two-value comma-ok form (or explicit `map` lookups with default/error handling) in `AddCW20`/`AddCW721` (and their `legacy/v*` counterparts) across `precompiles/pointer/**`, returning a normal precompile error (e.g. "malformed token_info/contract_info response: missing/invalid name or symbol") instead of panicking when the queried CW contract's reply is missing or has invalid types for `name`/`symbol`.

### Proof of Concept
1. Deploy a CosmWasm contract whose `token_info` (for CW20) or `contract_info` (for CW721) query handler returns `{"name": 123, "symbol": null}` (or omits the keys entirely) instead of proper strings.
2. From an EVM account, call the `pointer` precompile's `addCW20Pointer` (or `addCW721Pointer`) method with `cwAddr` set to the malicious contract's bech32 address.
3. Execution reaches `formattedRes["name"].(string)` in `precompiles/pointer/pointer.go`, which panics because the value is not a Go `string`, since the type assertion is unchecked. [6](#0-5)
