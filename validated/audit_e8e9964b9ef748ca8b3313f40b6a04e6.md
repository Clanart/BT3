### Title
`GeneratorPromotion::complete` silently drops the base key's `scalar`/`offset`, producing `ThresholdKeys` for a different secret than the one being promoted - ([File: crypto/dkg/promote/src/lib.rs](crypto/dkg/promote/src/lib.rs))

### Summary
`updateMarket` in the reference report accepts a `marketCapacity_` argument and emits it in an event, yet never stores it, leaving dependent state (`marketCapacity`, `active`) inconsistent. The Serai analog is `GeneratorPromotion::complete`: it promotes a `ThresholdKeys<C1>` to a new generator `C2`, but constructs the result via `ThresholdKeys::new`, which always initializes `scalar = ONE` and `offset = ZERO`. Any scalar/offset previously applied to the base keys (e.g., the Taproot tweak added by `tweak_keys` in `crypto/dkg` consumers like `networks/bitcoin/src/wallet/mod.rs`) is silently discarded, so the "promoted" keys represent a different secret than the base keys.

### Finding Description
`ThresholdKeys` carries two pieces of ephemeral per-key state: `scalar` and `offset`, applied via `scale()` and `offset()` ([crypto/dkg/src/lib.rs:400-417](crypto/dkg/src/lib.rs)). These transform the effective secret share and group key (`scalar * secret_share + offset`), and `ThresholdView` applies them when signing.

`GeneratorPromotion::promote`/`complete` is documented as "an O(n) way to update the generator used with keys" — i.e., to produce the *same* key under a new generator. However:

- `promote` builds the DLEq proof and `share` over `base.original_secret_share()` — the raw share, correctly ignoring scalar/offset since those are ephemeral and not part of the DLEq statement.
- `complete` then calls `ThresholdKeys::new(params, interpolation, original_secret_share, verification_shares)` at [crypto/dkg/promote/src/lib.rs:158-166](crypto/dkg/promote/src/lib.rs). `ThresholdKeys::new` hard-codes `scalar: C::F::ONE, offset: C::F::ZERO` ([crypto/dkg/src/lib.rs:388-389](crypto/dkg/src/lib.rs)).

Just as `updateMarket` never writes `marketCapacity_` into `_range`, `complete` never re-applies `base.scalar`/`base.offset` onto the returned keys. The result is a struct whose group key equals `original_secret * G2` — not `(scalar * original_secret + offset) * G2` — even though the caller supplied keys with a non-trivial scalar/offset. No check rejects promoting keys with non-identity scalar/offset, and nothing in the docs states they are dropped.

Concretely: `tweak_keys` in [networks/bitcoin/src/wallet/mod.rs:46-75](networks/bitcoin/src/wallet/mod.rs) adds the BIP-341 TapTweak as an `offset` and applies a parity `scale`. If such tweaked keys (or any offset/scaled keys) are promoted to a ciphersuite with a different generator, the promoted `ThresholdKeys` control the *untweaked* secret, while the integrator's `Scanner`/address derivation was built on the tweaked group key.

### Impact Explanation
Funds received at addresses derived from the scalar/offset-adjusted group key are not spendable by the promoted key set: the promoted keys produce signatures for the un-tweaked secret under the new generator. This matches the accepted impact class "funds reported received that are not spendable" — the scanner reports outputs to the tweaked/offset address, but the threshold group actually controls a different key. Additionally, the produced signatures verify against a group key no one deposited to, which is an incorrect-key-derivation failure rather than an integrator misuse: the API contract ("update the generator used with keys") implies key preservation, and the field-drop is silent.

### Likelihood Explanation
Medium. It requires an integrator to call `GeneratorPromotion` on keys carrying a non-identity scalar/offset — exactly what happens when Bitcoin Taproot-tweaked keys (which always carry a `tweak_hash` offset and a ±1 scalar) would be promoted to another generator on secp256k1. For bases with identity scalar/offset the bug is inert, which is why the omission is invisible in the crate's own tests.

### Recommendation
In `GeneratorPromotion::complete`, propagate the base's scalar and offset onto the new keys — e.g., apply `ThresholdKeys::new(...).scale(base.current_scalar()).and_then(|k| ... offset ...)`, or equivalently re-derive the effective secret share. Alternatively, explicitly reject promotion when `base.current_scalar() != ONE` or the offset is non-zero, and document that ephemeral scalar/offset state is not carried over.

### Proof of Concept
```rust
// keys: ThresholdKeys<C1> from key_gen
let keys = tweak_keys(keys);              // scalar = ±1, offset = TapTweakHash
let original_group = keys.group_key();    // P = s*sk + o (under G1)

let (promotion, _proof) = GeneratorPromotion::<C1, C2>::promote(&mut rng, keys.clone());
let promoted = promotion.complete(&other_proofs).unwrap();

// promoted.group_key() == original_secret_share * G2
// != expected (s*sk + o) * G2
// Any output scanned under the tweaked address is unspendable by `promoted`.
assert_ne!(promoted.group_key(), expected_tweaked_key_on_C2);
```
The promoted keys are internally consistent (verification shares match `original_secret_share`), so `complete` returns `Ok` and the error is only detectable when a deposit to the expected tweaked address cannot be signed for.
