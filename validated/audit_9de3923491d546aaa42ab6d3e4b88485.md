Based on the investigation, I found a strong structural analog to the reported bug in Agave's SIMD-0123 block-revenue-sharing mechanism, which reuses a persistent "pool" balance (`pending_delegator_rewards`) that is redistributed pro-rata to current stake without any per-stake watermark analogous to `lastVaultDistributedWethRewardPerShareX18`.

### Title
Block-revenue-sharing `pending_delegator_rewards` pool is redistributed in full every epoch with no per-stake watermark, letting newly delegated/undeserving stake claim historically-accumulated rewards - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
The external report's root cause is a reward-per-share accumulator (`CreditDelegation.lastVaultDistributedWethRewardPerShareX18`) that is not properly initialized for newcomers, so the delta `current - last` improperly spans the entire accumulation history instead of only the newcomer's earned period. Agave's SIMD-0123 block revenue sharing feature has the analogous defect: `calculate_block_reward` divides the *entire* current `pending_delegator_rewards` pool stored in the vote account pro-rata by current effective stake, every single epoch, with no tracking of how much of that pool a given stake delegation has already been paid or when it joined.

### Finding Description
`calculate_block_reward` reads the vote account's `pending_delegator_rewards` field and divides it pro-rata among current stake delegations: [1](#0-0) 

The `pending_delegator_rewards` field is only ever incremented, via `add_pending_delegator_rewards`, when a `DepositDelegatorRewards` instruction transfers lamports into the vote account: [2](#0-1) 

Unlike inflation rewards, which use `stake.credits_observed` as a per-delegation watermark to ensure a stake account only earns rewards for credits accrued *after* it joined (see `calculate_stake_points_and_credits` and `calc_earned_credits`): [3](#0-2) [4](#0-3) 

...no equivalent watermark exists for `pending_delegator_rewards`. Extensive searching across `runtime/src/bank/partitioned_epoch_rewards/*.rs`, `programs/vote/src/vote_state/*.rs`, and `programs/vote/src/vote_processor.rs` found no code path that decrements or resets `pending_delegator_rewards` after a portion of it has been paid out to stakers as `block_reward`. The only mutators of the field found are `add_pending_delegator_rewards` (deposit) and the read-only `pending_delegator_rewards()` accessor; `withdraw()` merely treats it as a floor on the withdrawable balance but never reduces it: [5](#0-4) 

Because the pool value used in the division (`pending_delegator_rewards`) never shrinks by the amount already distributed, and because `total_active_stake` is simply "whatever stake is delegated at the end of this rewarded epoch," a stake account that just activated (or a vote account whose delegator base just grew) is treated identically to stake that has been delegated since the deposit was made — exactly the flaw described in the external report where `lastVaultDistributedWethRewardPerShareX18 = 0` at vault creation causes a newcomer to be paid a full share of pre-existing accumulated rewards.

### Impact Explanation
This causes silent minting-adjacent unfairness in the block-revenue-sharing distribution:
- Every epoch, the *same* `pending_delegator_rewards` balance is divided in full among current delegators and paid out as `block_reward` lamports added to stake accounts (`account.checked_add_lamports(partitioned_stake_reward.block_reward)`), inflating total distributed lamports far beyond a single deposit's worth if this repeats across multiple epochs, and diluting/over-paying relative to the vote account's actual remaining lamport balance backing `pending_delegator_rewards`. [6](#0-5) 
- New stake delegators who join a vote account after a `DepositDelegatorRewards` deposit immediately receive a pro-rata share of that deposit despite contributing zero stake-time towards earning it, diluting the fair share owed to long-standing delegators — this is a direct fund-distribution correctness/fairness bug affecting validator commission economics under SIMD-0123 (`block_revenue_sharing` feature).
- Because the vote account's lamport balance backing `pending_delegator_rewards` is finite (enforced by `withdraw`'s floor check), repeated over-distribution against a non-decrementing pool can eventually attempt to pay out more than the vote account actually holds in reserve for delegators, risking `InsufficientFunds`-class failures or accounting drift between the on-chain vote account and the reward math in the bank.

### Likelihood Explanation
This is gated behind the `block_revenue_sharing` feature (SIMD-0123), which is present in the feature set but its activation status could not be confirmed from the index; if/when active, the flaw triggers automatically and deterministically on every reward epoch for every vote account with a nonzero `pending_delegator_rewards`, requiring no attacker action beyond normal delegation/deposit activity. No malicious actor is needed — it is a protocol-correctness defect in reward math, though I could not conclusively confirm the absence of a decrement mechanism beyond the files searched (the vote program and the reward calculation/distribution modules), so there remains some uncertainty whether a compensating decrement exists elsewhere that the index did not surface.

### Recommendation
Introduce a per-stake-delegation watermark for `pending_delegator_rewards` analogous to `credits_observed`, e.g., track the vote account's cumulative "delegator rewards deposited" counter and each stake's last-observed value of that counter, so `calculate_block_reward` only distributes the delta earned since the stake's last redemption/activation, and decrement `pending_delegator_rewards` on the vote account by the total `block_reward` actually distributed in `distribute_epoch_rewards_in_partition`/`store_stake_accounts_in_partition`.

### Proof of Concept
Given the reward math in `calculate_block_reward`: [7](#0-6) 
1. Validator calls `DepositDelegatorRewards` depositing 1,000,000 lamports into vote account V with existing delegated stake S1 = 100 SOL, setting `pending_delegator_rewards = 1,000,000`.
2. At epoch boundary, `calculate_block_reward` distributes the full 1,000,000 pro-rata to S1, but `pending_delegator_rewards` is never decremented back to 0 (no decrement call found in `handler.rs`, `vote_state/mod.rs`, or the distribution path).
3. A new delegator S2 = 100 SOL delegates to V immediately after this deposit (before the next epoch boundary).
4. At the following epoch boundary, `total_active_stake` now includes S2, and `pending_delegator_rewards` is still 1,000,000 (unchanged) — so both S1 and S2 are paid another 500,000 lamports each from the *same* deposit, `total = 2,000,000` distributed from a single 1,000,000-lamport deposit, and S2 collects rewards it never earned.
5. Repeated across epochs, this compounds, eventually exceeding the vote account's actual reserved balance for `pending_delegator_rewards`, contradicted only by the `withdraw()` floor check which does not prevent this internal over-distribution: [8](#0-7)

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}

fn calc_earned_credits(
    stake: &Stake,
    final_epoch_credits: u64,
    initial_epoch_credits: u64,
    new_credits_observed: &mut u64,
) -> u128 {
    let credits_in_stake = stake.credits_observed;

    // figure out how much this stake has seen that
    //   for which the vote account has a record
    let earned_credits = if credits_in_stake < initial_epoch_credits {
        // the staker observed the entire epoch
        final_epoch_credits - initial_epoch_credits
    } else if credits_in_stake < final_epoch_credits {
        // the staker registered sometime during the epoch, partial credit
        final_epoch_credits - *new_credits_observed
    } else {
        // the staker has already observed or been redeemed this epoch
        //  or was activated after this epoch
        0
    };
    *new_credits_observed = (*new_credits_observed).max(final_epoch_credits);
    u128::from(earned_credits)
}
