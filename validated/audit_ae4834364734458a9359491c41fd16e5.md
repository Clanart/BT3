### Title
Aggregate Schnorr signatures accept arbitrary trailing bytes while still verifying - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` parses a length-prefixed list of nonces followed by one scalar, but it never verifies that the supplied signature encoding ends there. An attacker can append arbitrary bytes to an otherwise valid serialized aggregate signature; `SchnorrAggregate::verify` will still accept it. This is the direct Serai analogue of accepting extra elements inside a signature encoding.

### Finding Description
`SchnorrAggregate::read` first reads a `u32` count, then exactly that many group encodings, and finally one scalar. It returns the constructed aggregate without checking whether the input reader contains additional bytes. [1](#0-0) 

`SchnorrAggregate::verify` then authenticates only the parsed `Rs` vector and scalar `s`; no original signature bytes or byte length participate in verification. [2](#0-1) 

Consequently, if a caller treats a byte buffer as a complete signature and calls `SchnorrAggregate::read` followed by `verify`, the following two byte strings both represent the same accepted signature:

```text
canonical_aggregate_encoding
canonical_aggregate_encoding || attacker_controlled_suffix
```

The mathematical signature is unchanged, but the externally submitted signature encoding is attacker-malleable.

### Impact Explanation
An unprivileged party can create a distinct serialized aggregate signature that was never emitted by the aggregation code and have it accepted by verification. Where the signature byte string is hashed, stored, relayed, deduplicated, or embedded in a larger signed/consensus object, this permits invisible attacker-controlled data to accompany a valid signature and can bypass canonical-encoding assumptions.

The resulting primitive is signature-encoding malleability: the attacker does not need to know the private keys or alter the message, nonce, or scalar to produce a new accepted byte-level signature.

### Likelihood Explanation
The flaw is reachable whenever attacker-controlled aggregate signature bytes are supplied to `SchnorrAggregate::read`. Because `read` accepts any `io::Read`, it deliberately supports streaming, but callers that omit an EOF check inherit the vulnerability. The only requirement is possession of a valid aggregate signature, after which appending arbitrary bytes is trivial.

### Recommendation
Require aggregate signature encodings to be consumed completely before verification. For APIs that receive a complete byte slice, parse it as `&[u8]` and reject the signature if any bytes remain. Alternatively, return the parsed aggregate together with explicit consumption status and make callers enforce `reader.is_empty()`. The serialized length can also be checked exactly as `4 + (nonce_count * G::Repr::len()) + F::Repr::len()`.

### Proof of Concept
Starting from any valid `SchnorrAggregate<C>` and its corresponding `keys_and_challenges`, the following demonstrates that an extended encoding remains valid:

```rust
use std::io::Read;
use schnorr::aggregate::SchnorrAggregate;
use ciphersuite::group::GroupEncoding;

// `aggregate` is a valid SchnorrAggregate<C>, and `pairs` are the expected
// (public_key, challenge) pairs.
let mut encoded = aggregate.serialize();
encoded.extend_from_slice(b"attacker-controlled invisible data");

let mut reader = encoded.as_slice();
let decoded = SchnorrAggregate::<C>::read(&mut reader).unwrap();

// The suffix was not consumed or authenticated.
assert_eq!(reader, b"attacker-controlled invisible data");

// The malformed encoding nevertheless verifies.
assert!(decoded.verify(DST, &pairs));
```

The root cause is the unconditional return after reading only the expected prefix fields. [3](#0-2)

  pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
    let mut len = [0; 4];
    reader.read_exact(&mut len)?;
