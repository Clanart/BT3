### Title
Local rebase/history-rewrite after a dangerous commit breaks `head_at_capture` ancestry, causing the review set to go empty and skipping Stop-hook review - ([File: plugins/security-guidance/hooks/diffstate.py])

### Summary
`compute_v2_review_set` only folds in commits made "this turn" when `head_at_capture` (HEAD at `UserPromptSubmit`) is still an ancestor of the current HEAD via `_is_ancestor`. Any git history rewrite performed after the dangerous commit (interactive rebase, `git reset --soft` + re-commit, squash) invalidates that ancestry, so the delta term is silently dropped, the working tree is clean (nothing in `git status --porcelain`), and the review set becomes empty — the dangerous change is never sent to the Stop-hook's LLM review.

### Finding Description
`handle_user_prompt_submit` captures `baseline_sha` (via `capture_git_baseline`, a `git stash create`/HEAD snapshot) and `head_at_capture` (`_git_rev_parse_head`) once per prompt turn [1](#0-0) .

At Stop time, `compute_v2_review_set` builds the review set as:
```
dirty_now = tracked_dirty | new_untracked         # from `git status --porcelain`
if head_at_capture is ancestor of current HEAD:
    dirty_now |= git diff --name-only head_at_capture..HEAD
review_set = dirty_now ∩ changed_since(baseline_sha)   (or dirty_now alone if baseline missing)
``` [2](#0-1) 

The ancestor check uses `git merge-base --is-ancestor head_at_capture HEAD` [3](#0-2) . This is true for a simple `git commit --amend` on the tip commit (parent unchanged), but is **false** for a `git rebase -i` (squash/reorder), `git reset --soft <earlier> && git commit`, or any operation that replaces the commit that introduced the dangerous change with a new SHA whose ancestry no longer contains `head_at_capture` in the expected linear chain, or where the amended commit's parent itself changed.

When that happens:
- The working tree is clean after the rewrite (nothing in `git status --porcelain`), so `dirty_now` is empty.
- The `head_at_capture..HEAD` delta term is skipped because the ancestor check fails.
- `review_set` therefore ends up empty (or intersects to empty), and `handle_stop_hook` exits without emitting any findings via `_skip`, treating the turn as if nothing changed [4](#0-3) .

The other two review surfaces do not close this gap:
- `handle_commit_review_posttooluse` only fires when the Bash command matches `_GIT_COMMIT_RE` (a `git commit` invocation) — a `git rebase`/`git reset` command does not match, so no per-commit review is triggered for the rewritten commit [5](#0-4) .
- `handle_push_sweep_posttooluse` only runs on `git push`, comparing against `.git/sg-reviewed-shas`; if the dangerous commit is never pushed (or the session ends before a push), it's never captured by push-sweep either [6](#0-5) .

So a sequence of ordinary git operations — commit a dangerous change, then rewrite history locally (amend with parent change, squash rebase, or reset+recommit) — shifts the baseline/ancestry state such that the dangerous diff is treated as "already old"/non-existent and is skipped by every review surface in the plugin, while the dangerous code remains on disk and in history ready for the agent to act on it (e.g., run it, commit-and-push it later without further edits triggering review, etc.).

### Impact Explanation
This breaks the stated invariant that "the review set must stay bound to the right repo, baseline, and touched paths." A dangerous local change (e.g., a command-injection payload, altered permission check, or backdoor) introduced during a Claude turn can be made permanently invisible to the plugin's LLM-based security review by an ordinary follow-up git history rewrite, with no attacker privilege beyond normal repository/git operations. Because this security-guidance plugin exists specifically to gate/flag risky code before Claude Code proceeds, silently losing review coverage undermines the approval/deny signal the plugin is meant to provide, matching "Unauthorized local command execution that bypasses Claude Code approval or deny controls" in spirit — the dangerous code is never surfaced for the user/model to reconsider or block.

### Likelihood Explanation
- Precondition: attacker-controlled or prompt-injected content instructs (or Claude autonomously decides, e.g. via commit-hygiene habits) to run a history-rewriting git command (`git commit --amend` when the amend also rebases the parent, `git rebase -i`, or `git reset --soft && git commit`) after introducing a dangerous change, all within the same session/turn boundary tracked by `baseline_sha`/`head_at_capture`.
- These are extremely common, "normal" git workflows (squash-before-push, fixing a commit message together with a parent change, interactive cleanup), making this easy to trigger unintentionally, and trivial to trigger deliberately via prompt injection embedded in repository content (e.g., a CONTRIBUTING.md instructing "always squash your commits before finishing").
- No special privileges are required beyond the ability to run git commands in the working copy, which any user/agent session already has.

### Recommendation
Do not gate the `head_at_capture..HEAD` delta purely on `_is_ancestor`. When `head_at_capture` is no longer an ancestor of `HEAD` (a rewrite occurred), fall back to a diff of `head_at_capture..HEAD` symmetric-difference (`git diff --name-only head_at_capture...HEAD`, triple-dot merge-base diff) or explicitly diff the dangling `head_at_capture` blob tree against current HEAD's tree, rather than dropping the term entirely. Additionally, treat "history rewrite detected" (non-ancestor HEAD change) as its own signal to force a full review rather than silently reducing the review set to whatever `git status` currently shows.

### Proof of Concept
Unit/integration test plan (add to the existing diffstate/security_reminder_hook test suite):
1. Initialize a temp git repo with one commit (`HEAD_0`).
2. Simulate UPS: call `capture_git_baseline`/set `baseline_sha = HEAD_0`, `head_at_capture = HEAD_0`.
3. Simulate a turn: write a dangerous file (e.g., `os.system(user_input)`), `git add` and `git commit` → `HEAD_1` (child of `HEAD_0`).
4. Simulate a local history rewrite: `git rebase -i HEAD_0` non-interactively (e.g., `GIT_SEQUENCE_EDITOR=true git rebase -i HEAD_0~0` or simpler, `git commit --amend --date="..."` combined with `git reset --soft HEAD_0 && git commit -m "combined"`) producing `HEAD_2`, verifying via `git merge-base --is-ancestor HEAD_0 HEAD_2` that it returns non-zero (assert rewrite invalidated ancestry).
5. Call `compute_v2_review_set(cwd, baseline_sha=HEAD_0, head_at_capture=HEAD_0)`.
6. Assert (expected-to-fail on current code): `dangerous_file_path in review_paths`. Current behavior: `review_paths == []` because `dirty_now` is empty and the ancestor check fails, demonstrating the dangerous file is dropped from review.
7. Repeat with a plain `git commit --amend --no-edit` for a "should still work" control assertion, confirming that case correctly still contains the dangerous file (since `_is_ancestor` still holds when only the amend target's parent is unchanged) — highlighting the specific rebase/reset-then-recommit divergence.

def _is_ancestor(cwd, maybe_ancestor, descendant):
    """True if `maybe_ancestor` is reachable from `descendant` (i.e. HEAD
    moved forward via commit/merge, not sideways via checkout)."""
    try:
        result = subprocess.run(
            [*GIT_CMD, "merge-base", "--is-ancestor", maybe_ancestor, descendant],
            cwd=cwd, capture_output=True, text=True, timeout=5,
        )
        return result.returncode == 0
    except (subprocess.TimeoutExpired, FileNotFoundError, OSError):
        return False
