### Title
PedPoP `calculate_share` emits a blame ECDH proof for messages whose proof-of-possession was never verified, letting an unauthenticated sender recover the victim's ECDH shared key — ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
The auth0.js advisory describes a callback handler releasing credentials to a cross-origin caller because it acts on a message before verifying the message's origin. PedPoP has the same shape: `KeyMachine::calculate_share` calls `Encryption::decrypt`, which unconditionally computes the ECDH shared key `enc_key * msg.key` and wraps it in an `EncryptionKeyProof` (with an honest DLEq), **before** the attacker's Schnorr proof-of-possession for `msg.key` is verified — the PoP is merely queued into a `BatchVerifier`. If the decrypted bytes then fail `C::F::from_repr`, `calculate_share` returns `PedPoPError::InvalidShare { blame: Some(proof) }` early, without ever running `batch.verify_with_vartime_blame()`. The returned proof is designed to be published for blame adjudication, so it reaches the attacker.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `Encryption::decrypt` queues `msg.pop` verification into an external `BatchVerifier` (lines 479–485) and then immediately computes `key = ecdh(&self.enc_key, msg.key)` and returns `EncryptionKeyProof { key, dleq }` proving `key = enc_key · msg.key` (lines 487–499). PoP verification is deferred to the batch.

In `crypto/dkg/pedpop/src/lib.rs` `calculate_share` (lines 476–491), the flow per sender `l` is:

1. `decrypt(...)` → returns `(share_bytes, blame)` where `blame.key = b · msg.key` (b = recipient's private encryption key).
2. `C::F::from_repr(share_bytes.0)` fails → `Err(InvalidShare { participant: l, blame: Some(blame.clone()) })` — early return (lines 480–482).
3. Only later is `batch.verify_with_vartime_blame()` called, which is where the invalid PoP would have been caught (line 493).

The code's own comments state the PoP exists precisely to prevent this: "If this proof-of-possession wasn't here, Eve could observe Alice encrypt to Bob with key X, then send Bob a message also claiming to use X… they'd reveal bX, revealing Alice's message to Bob" (`encryption.rs` lines 84–88). The defense exists but is never enforced before the sensitive value is emitted: an invalid-PoP message that also produces a non-canonical scalar short-circuits before the batch verifier runs.

An unprivileged attacker Eve (anyone able to deliver an `EncryptedMessage` to the victim's `calculate_share`, e.g., a DKG participant slot or a relay) sends `EncryptedMessage { key: X }` where `X` is an honest sender Alice's observed per-message key, plus garbage ciphertext and a garbage PoP. The victim returns `blame` containing `bX` with a valid DLEq. Eve uses `cipher(context, bX)` to decrypt Alice's real encrypted secret share to the victim. Repeating per-sender recovers all shares sent to that victim → full victim secret share recovery (`share = Σ shares_l`). The failure probability per attempt is roughly `1 − ℓ/2^256` (≈ ½ for ed25519/Ristretto-class fields), and failed attempts still return blame, so the attack succeeds within a couple of submissions.

### Impact Explanation
Recovery of a participant's threshold secret share from publicly-submitted DKG messages. Combined with the shares routed to other compromised keys (or repeated across DKG sessions reusing the victim's registered `enc_key`), this enables reconstruction of the victim's `ThresholdKeys` secret — key share recovery, the highest-impact class accepted here.

### Likelihood Explanation
Reachable purely with attacker-constructed bytes fed to `calculate_share` / `EncryptedMessage::read` — no malicious validator collusion required beyond the attacker's own DKG participant slot (and `AdditionalBlameMachine`-style flows demonstrate blame proofs are expected to circulate publicly). The triggering condition (non-canonical decrypted scalar) holds with ~50% probability per attempt and is retriable.

### Recommendation
Verify `msg.pop` (or at minimum gate the early `InvalidShare` return) before releasing any `EncryptionKeyProof`. Concretely: in `Encryption::decrypt`, do not build the DLEq/`EncryptionKeyProof` until the caller has confirmed the PoP batch verified; or in `calculate_share`, run a standalone `msg.pop.verify(...)` per message before `decrypt`, and return `InvalidShare { blame: None }` (sender-at-fault, no key disclosure) when it fails — mirroring how `BatchId::Decryption` failures already map to `blame: None`.
