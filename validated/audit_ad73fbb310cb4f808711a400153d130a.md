### Title
Deserialization of attacker-controlled `ReceivedOutput` lets an unprivileged party register fabricated deposits and make the threshold group sign transactions spending nonexistent prevouts - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes a spendable-output record — the scalar `offset`, the full `TxOut` (`value` + `script_pubkey`), and the `OutPoint` — purely from the byte stream, with no authentication of where the output came from or whether it exists on chain. `SignableTransaction::new` then consumes `Vec<ReceivedOutput>` verbatim: it derives the per-input key as `keys.offset(input.offset)`, only checks that `p2tr_script_buf(offset.group_key())` equals the *claimed* `script_pubkey` (a check the attacker can satisfy because the group key is public), and commits `prevouts` into the BIP-341 `Prevouts::All` sighash that every FROST signer signs. An attacker who can feed serialized `ReceivedOutput` bytes into this pipeline can therefore (a) have the system record "received funds" that do not exist and are not spendable, and (b) cause all honest signers to produce signatures over a sighash committing to fabricated input values/scripts, yielding an invalid transaction that wastes a signing round.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs:122-134`, `ReceivedOutput::read` reads:
- `offset` via `Secp256k1::read_F` (any scalar),
- `output` via `TxOut::consensus_decode` (any value and any script_pubkey),
- `outpoint` via `OutPoint::consensus_decode` (any txid/vout),

and returns the triple unconditionally. Unlike the honest path — `Scanner::scan_transaction` (mod.rs:199-214), which only constructs a `ReceivedOutput` for outputs actually present in a confirmed transaction and whose `script_pubkey` is in the scanner's registered `scripts` map — the deserialization path performs no origin validation: the bytes themselves are the sole evidence the output exists and belongs to the group.

`SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-256) trusts the record completely: `input_sat` (claimed total input funds), `offsets`, `tx_ins` (claimed outpoints), and `prevouts` (claimed `TxOut`s) all come straight from the deserialized inputs. `SignableTransaction::multisig` (send.rs:273-285) performs the only validation: `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey`. Because `keys.group_key()` is public, an attacker can pick any scalar `s`, compute `p2tr(group_key + s·G)` themselves, and set `offset = s` and `script_pubkey` to that script, satisfying the check while naming a fictitious `outpoint` and arbitrary `value`. `TransactionSignMachine::sign` (send.rs:373-391) then computes `taproot_key_spend_signature_hash(i, &Prevouts::All(&self.tx.prevouts), ...)`, committing every signer to the fabricated prevout amounts.

This mirrors the reported bug class (CVE-2021-26291): Maven followed repository URLs declared inside an untrusted dependency POM without authenticating the origin; here, Serai follows *prevout declarations* carried inside untrusted `ReceivedOutput` bytes without authenticating that the output exists on chain.

### Impact Explanation
Two concrete impacts, both reachable by an unprivileged party able to supply serialized `ReceivedOutput` bytes (the `read` API is an explicitly in-scope entry point for untrusted bytes):

1. **Funds reported received that are not spendable.** Any downstream consumer that credits a deposit based on a received `ReceivedOutput` will record a balance backed by a nonexistent or unrelated outpoint. The record structurally identical to a scanner-produced one (`offset`, `output`, `outpoint` all attacker-chosen), so it is indistinguishable downstream.
2. **Signing of an unintended message.** All honest FROST participants sign `taproot_key_spend_signature_hash` over `Prevouts::All` containing the fabricated `TxOut`s. Since BIP-341 commits the signature to the claimed prevout amounts and scripts, the produced transaction is consensus-invalid whenever the claimed data does not match the real UTXO — the group signs a message authorizing a spend that can never execute, burning the signing session and requiring detection/re-issuance.

There is no direct theft: a forged prevout whose data matches a real vault-owned UTXO is a legitimate spend, and mismatched data just invalidates the transaction. The impact is false crediting of deposits plus a signer-level invalid-transaction footgun.

### Likelihood Explanation
Exploitation requires the attacker's serialized `ReceivedOutput` to reach `ReceivedOutput::read` and be consumed by `SignableTransaction::new`/`Scanner`-equivalent accounting — i.e., any path where received-output records cross a trust boundary (network messages, shared storage, coordinator instructions) instead of being produced solely by a locally operated `Scanner` over a self-verified chain view. Within the in-scope crate, `read`/`write`/`serialize` exist precisely for transporting these records, so the threat surface is real wherever that transport is not authenticated. No cryptographic break, collusion, or validator misbehavior is required — only public knowledge of the group key.

### Recommendation
Authenticate the origin of `ReceivedOutput` data rather than trusting the serialized record:

- Treat `ReceivedOutput::read` output as untrusted input: before use in `SignableTransaction::new` or balance accounting, re-verify against a trusted chain view that `outpoint` resolves to a real, confirmed UTXO whose `TxOut` (value and script_pubkey) matches the claimed `output` exactly.
- Strengthen `SignableTransaction::multisig`: in addition to the `script_pubkey` check, verify each `prevouts[i]` equals the confirmed UTXO at `tx.input[i].previous_output` (e.g., by re-deriving inputs exclusively via `Scanner` results).
- Consider making the `ReceivedOutput` constructor/`read` crate-private or clearly documented as requiring an authenticated source, since only `Scanner` can produce trustworthy instances.

### Proof of Concept
```rust
use bitcoin::{TxOut, OutPoint, Amount, ScriptBuf};
use bitcoin::hashes::Hash;
use k256::Scalar;
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction, p2tr_script_buf};
use frost::curve::Secp256k1;
use frost::ThresholdKeys;

// group_key: the vault's tweaked ThresholdKeys group key (public knowledge).
// Attacker picks an arbitrary scalar s and computes the matching script:
let s = Scalar::ONE;
let evil_script = p2tr_script_buf(group_key + k256::ProjectivePoint::GENERATOR * s).unwrap();

// Forge a ReceivedOutput claiming a huge deposit at an outpoint the vault
// does not own (e.g., a made-up txid):
let mut forged = Vec::new();
forged.extend_from_slice(&s.to_bytes());                     // offset
forged.extend_from_slice(&bitcoin::consensus::encode::serialize(&TxOut {
    value: Amount::from_sat(21_000_000_0000_0000u64.min(u64::MAX)),
    script_pubkey: evil_script,
}));                                                         // claimed TxOut
forged.extend_from_slice(&bitcoin::consensus::encode::serialize(
    &OutPoint::new(bitcoin::Txid::from_byte_array([0xAA; 32]), 0),
));                                                          // claimed OutPoint

// If these bytes reach the read path (network message / shared record):
let ro: ReceivedOutput = ReceivedOutput::read(&mut forged.as_slice()).unwrap();

// SignableTransaction::new accepts it; input_sat now includes 21M fake BTC,
// so fee/change accounting and the NotEnoughFunds check all pass on fake data.
let stx = SignableTransaction::new(
    vec![ro],
    &[(attacker_payment_script, 546)],
    Some(change_script),
    None,
    10,
).unwrap();

// multisig() passes because offset s was chosen to match evil_script.
// sign() then has every honest signer produce a BIP-340 signature over
// Prevouts::All containing the fabricated TxOut — an unintended message —
// and the resulting transaction is consensus-invalid / the "deposit" is
// unspendable.
let machine = stx.multisig(&vault_keys).unwrap();
```
