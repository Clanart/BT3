### Title
Unvalidated participant indexes in PedPoP blame evaluation cause a panic (node crash) from attacker-supplied blame inputs - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to CVE-2017-11665 (crafted remote input → crash), `BlameMachine::blame` / `AdditionalBlameMachine::blame` in the PedPoP DKG accept attacker-controlled `sender`/`recipient` participant IDs plus an attacker-supplied `EncryptedMessage`/`EncryptionKeyProof`, and then index `HashMap`s with those IDs via `self.enc_keys[&decryptor]` and `self.commitments[&sender]` without validation. A malicious DKG participant can file a blame accusation naming a non-registered `recipient` (or `sender`) and crash every honest party that evaluates the blame proof.

### Finding Description
`Decryption::decrypt_with_proof` indexes the registered-encryption-key map directly: [1](#0-0) 

`self.enc_keys[&decryptor]` panics if `decryptor` was never registered. Registrations only occur for actual DKG participants: `verify_r1` calls `self.encryption.register(l, msg)` per participant [2](#0-1) , and `AdditionalBlameMachine::new` registers `1 ..= n` [3](#0-2) . Neither `BlameMachine::blame` nor `AdditionalBlameMachine::blame` validates that the caller/accuser-supplied `sender` and `recipient` are registered participants [4](#0-3) [5](#0-4) .

A second panic of the same class exists in `blame_internal`, which evaluates the accused share against `self.commitments[&sender]` [6](#0-5) . Since `AdditionalBlameMachine` is explicitly designed to be usable by non-participants evaluating third-party blame statements ("capable of evaluating Blame regardless of if the caller was a member in the DKG protocol"), its inputs are untrusted.

Note: the panic is gated behind a *valid* PoP — `msg.pop.verify(...)` must pass first [7](#0-6)  — but the accuser can trivially construct a valid `EncryptedMessage` since they generate the ephemeral key themselves.

### Impact Explanation
Any honest validator (or third-party auditor via `AdditionalBlameMachine`) that evaluates a crafted accusation hits an unconditional `HashMap` indexing panic, aborting the DKG/blame resolution path. Since blame evaluation is the mechanism by which faulty dealers are identified, crashing it prevents the protocol from completing and lets a faulty participant escape adjudication — a denial of service directly mirroring the crafted-stream → crash class of CVE-2017-11665.

### Likelihood Explanation
Requires only a party able to submit a blame accusation (an unprivileged DKG participant or, for `AdditionalBlameMachine`, anyone relaying accusations). The attacker picks `recipient = Participant(n + 1)` (or any index with no registered encryption key), supplies a self-constructed `EncryptedMessage` with a valid PoP and `Some(proof)`, and triggers the panic deterministically. No key material or collusion is needed.

### Recommendation
In `blame_internal` (or at the top of `blame` / `AdditionalBlameMachine::blame`), validate that `sender` and `recipient` are members of the registered participant set before any map access — e.g., return the accuser/accused as faulty via `enc_keys.get(&decryptor)`/`commitments.get(&sender)` with a graceful `None` path, or an explicit error. Map lookups on attacker-influenced indexes should never use panicking `Index` syntax.

### Proof of Concept
```rust
// Setup: any completed/aborted PedPoP session giving a BlameMachine<C>,
// or independently: AdditionalBlameMachine::new(context, n, commitment_msgs)
// with n registered participants (enc_keys only contains 1..=n).

// Attacker crafts a syntactically valid EncryptedMessage<C, SecretShare<C::F>>
// with a self-generated ephemeral key so `pop.verify` succeeds, plus any
// EncryptionKeyProof, and files a blame accusation where `recipient` is an
// index with no registered encryption key:
let bogus_recipient = Participant::new(n + 1).unwrap(); // never registered
let attacker_sender = Participant::new(2).unwrap();

// Inside decrypt_with_proof, this line executes:
//   &[self.enc_keys[&decryptor], *proof.key]
// `enc_keys` has no entry for `bogus_recipient` -> panic: key not found.
let _faulty = blame_machine.blame(attacker_sender, bogus_recipient, msg, Some(proof));
```

Alternatively, after `decrypt_with_proof` succeeds with a valid registered `recipient`, `blame_internal` reaches `self.commitments[&sender]` with an attacker-chosen unregistered `sender`, panicking at `crypto/dkg/pedpop/src/lib.rs` line ~599.
