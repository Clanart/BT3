### Title
Strict-equality residual-balance check in `IBCReceivePacketCallback` permanently traps tokens in an unrecoverable isolated address - ([File: x/ibc/callbacks/keeper/keeper.go])

### Summary
`MarinateV2.removeApprovedRewardToken` required `balanceOf(this) == 0`, which made the function permanently unusable whenever an unremovable dust residue existed. The Cosmos EVM analog is `ContractKeeper.IBCReceivePacketCallback`, which performs the equivalent strict-equality check `receiverTokenBalance.Cmp(big.NewInt(0)) != 0` on the isolated address's ERC20 balance after invoking a destination callback contract. Unlike the Solidity bug (which only blocks an admin cleanup call), the Cosmos EVM analog is worse: the tokens have *already* been irreversibly moved into a keyless, deterministically-derived "isolated address" before this check runs, and there is no code path to sweep or recover a nonzero residue afterward.

### Finding Description
`IBCReceivePacketCallback` [1](#0-0)  is invoked by the ibc-go callbacks middleware after the ICS20 transfer has already credited tokens to a per-packet `isolatedAddr` derived deterministically from `(destChannel, sender)` [2](#0-1) . This isolated address has no associated private key — it exists purely as a routing construct.

The function then:
1. Approves the destination contract to pull `amountInt` (the *full* transferred amount) from the isolated address [3](#0-2) .
2. Calls the destination contract's calldata, expecting it to `transferFrom(isolatedAddr, contract, amount)` for the *entire* amount [4](#0-3) .
3. Commits the cached context (`writeFn()`) — meaning any partial `transferFrom` pull is already persisted to state [5](#0-4) .
4. Only *after* committing, checks `receiverTokenBalance.Cmp(big.NewInt(0)) != 0` and returns an error if any residue remains [6](#0-5) .

The comment at line 232-233 explicitly acknowledges the risk ("this check is here to prevent funds from getting stuck in the isolated address, since they would become irretrievable") but the check is purely detective, not preventative: by the time it runs, the state mutation (partial pull) is already committed via `writeFn()`. If the destination contract — which is attacker/user-controlled calldata target specified in the IBC transfer memo — does not pull exactly 100% of the approved amount (due to fee-on-transfer semantics, rounding down when computing shares, a deliberate partial-pull bug, or any other reason), the leftover balance remains permanently in `isolatedAddr`, which:
- Has no controlling key, so no `transfer`/`transferFrom` can ever be initiated from it by any user.
- Is per-packet/per-(channel, sender) and not reused with a recoverable owner, so no future callback can sweep it.
- Has no admin/sweep function anywhere in this file or the module to reclaim such dust.

This is functionally identical in structural cause to the audited bug: an exact-equality check on a balance that can legitimately end up nonzero due to normal rounding/partial-consumption behavior of downstream logic, except here the consequence is not "an unrelated cleanup function reverts" but "user funds already moved into an unrecoverable account are permanently lost."

### Impact Explanation
This satisfies the Critical impact criterion of **permanent freezing/locking of user funds**: any nonzero residue left in the isolated address after a destination callback contract's `transferFrom` becomes irrecoverable via any documented or implemented mechanism in this module, because the isolated address is keyless and per-packet. Depending on the destination contract behavior (fee-on-transfer tokens, integer-division rounding in vault/strategy contracts, or a contract that intentionally/unintentionally never pulls the full amount), this can occur on every single IBC-callback transfer routed through such a contract, leading to systematic and repeated fund loss for ordinary users using the IBC-callbacks feature with common DeFi-style contracts (deposit/auto-compound/vault patterns that round down shares).

### Likelihood Explanation
Likelihood is high in practice because:
- The destination contract address and calldata are fully attacker/user-supplied via the IBC transfer's memo/callback data, so any contract with normal rounding behavior (extremely common in vaults, AMMs, and fee-bearing tokens) will trigger this path without any need for malicious intent.
- No unprivileged actor needs special permissions — a standard IBC transfer with callback data pointing to any contract that does not pull 100% of allowance is sufficient.
- The problematic write (`writeFn()`) already happens before the zero-balance check, so the check cannot prevent the loss — it can only detect it after the fact and return an error, which does not undo the already-committed partial pull.

### Recommendation
Do not commit (`writeFn()`) the cached EVM execution results before confirming that the isolated address balance is fully drained. Alternatively, replace the token movement flow so that the module keeper directly transfers the exact amount to the destination contract from the isolated address using a bank-keeper/ERC20 forced transfer (rather than relying on the destination contract's `transferFrom` implementation), removing dependence on third-party contract behavior for correctness. If a nonzero residual balance is detected, provide a recovery/sweep mechanism (e.g., an authorized keeper-level function to return residual isolated-address balances back to the original sender) instead of merely erroring out after the funds are already stuck.

### Proof of Concept
Conceptual PoC (cannot be executed without a running network in this environment):
1. Register an IBC token pair and enable channel callbacks.
2. Deploy a "vault" contract `V` whose callback function computes `sharesToMint = amount * 999 / 1000` and only calls `IERC20(token).transferFrom(isolatedAddr, address(this), sharesToMint)` (a common rounding-down pattern), leaving `amount/1000` un-pulled.
3. Send an ICS20 transfer with a destination callback pointing to `V`, with calldata triggering the deposit function.
4. Observe: `IBCReceivePacketCallback` executes `approve` for the full `amount`, calls `V`'s calldata which pulls only `sharesToMint`, then `writeFn()` commits this partial pull.
5. The subsequent balance check finds `receiverTokenBalance == amount/1000 != 0`, so the function returns `types.ErrEVMCall` — but the partial transfer to `V` has already been committed and the leftover `amount/1000` sits in `isolatedAddr`, which has no private key and is never referenced again by any recovery path in this module, permanently locking those tokens.
