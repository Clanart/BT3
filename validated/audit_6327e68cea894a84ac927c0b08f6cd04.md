### Title
`SignableTransaction` fee calculation omits the OP_RETURN data output, undercharging fees for any spend carrying data - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Andromeda bug class is "accounting that only counts one variant of value-carrying output while ignoring another variant" — `get_tax_amount()` summed `BankMsg::Send` amounts but treated `WasmMsg::Execute` messages as zero. In Serai's Bitcoin wallet, `SignableTransaction::new` builds the real transaction's outputs from `payments` **plus** an `OP_RETURN` data output (`send.rs:194-202`), but computes the required fee and weight via `calculate_weight_vbytes`, which reconstructs a transaction using **only** `payments` and `change` (`send.rs:85-99`). The `OP_RETURN` output — which can carry up to 80 bytes of attacker/user-supplied data — is silently excluded from the weight, vbytes, and therefore the fee, exactly paralleling the ignored `WasmMsg::Execute` taxes.

### Finding Description
In `SignableTransaction::new` (`send.rs:150`), the outputs that will actually appear on-chain are assembled at `send.rs:188-202`:

```rust
// send.rs:194-202
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}
```

However, the fee is computed from a *different* transaction built inside `calculate_weight_vbytes` (`send.rs:62-127`), which is invoked at `send.rs:204` and `send.rs:226` with only `payments` (and optionally `change`) — the `data` output is never passed:

```rust
// send.rs:204
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
// send.rs:226
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
```

`calculate_weight_vbytes` maps `payments` into `tx.output` (`send.rs:85-93`) and pushes `change` (`send.rs:95-99`), but has no parameter for `data`. The resulting `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`, `send.rs:227`) therefore omits the ~11–92+ byte OP_RETURN output (output base + script + pushdata). The actual fee paid is `sum(inputs) - sum(outputs)` (`send.rs:138-141`), so the realized fee rate is strictly lower than `fee_per_vbyte` whenever `data.is_some()`.

This is reachable by an unprivileged party: the `data` field is populated from `Output::data` / `extract_serai_data`, which is arbitrary bytes embedded by the sender of an external Bitcoin deposit (`processor/src/networks/bitcoin.rs:730`, `processor/src/networks/bitcoin.rs:697`), and capped only at 80 bytes (`send.rs:171`).

### Impact Explanation
- The transaction's effective fee rate is below the requested `fee_per_vbyte`, so `needed_fee()` (`send.rs:133`) reports a value that does not achieve the intended rate.
- The minimum-fee check at `send.rs:211` validates the *understated* `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE`; after the OP_RETURN bytes are added, the true rate can fall below the relay minimum, producing a validly-signed transaction that nodes refuse to relay/mine — Serai signs a transaction that cannot confirm, stalling the affected plan/forward/refund until re-signed (the outputs remain locked as inputs).
- Because change inclusion is decided with `fee_with_change` computed the same way (`send.rs:226-234`), the change-versus-dust threshold is also evaluated against an incorrect fee.

### Likelihood Explanation
Any spend path that attaches data — forwarding transactions and refunds that embed `InInstruction` data via OP_RETURN — triggers this whenever `data` is non-empty. The magnitude is bounded (~one small output, ≤80-byte payload), so it degrades the fee rate rather than catastrophically breaking every transaction, consistent with a Medium: either transactions confirm at a lower-than-intended rate or fail relay policy in the edge case near the minimum fee.

### Recommendation
Include the `OP_RETURN` output in `calculate_weight_vbytes` — e.g., pass the already-built `tx_outs` (or `payments` plus the data script) into the weight calculation at `send.rs:204` and `send.rs:226` — so `needed_fee`, `fee_with_change`, and the change/dust decision all account for every output that will exist in the signed transaction.

### Proof of Concept
```rust
// Any call site supplying data, e.g. a forwarded output's instruction data:
let inputs = vec![received_output]; // one P2TR ReceivedOutput
let payments = &[(dest_script, 10_000u64)];
let data = Some(vec![0xAA; 80]);    // max-allowed user-controlled data

let stx = SignableTransaction::new(inputs, payments, None, data.clone(), 10).unwrap();
// stx.tx.output now contains payments + an ~92-byte OP_RETURN output,
// but needed_fee was computed from a transaction WITHOUT that output.

let actual_vbytes = /* vbytes of stx.transaction() */;   // > vbytes used internally
assert!(stx.needed_fee() < 10 * actual_vbytes);          // realized rate < requested
```
With `fee_per_vbyte` chosen so `needed_fee` is just above `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` (`send.rs:211`), the construction succeeds yet the final transaction's true fee rate is below the relay minimum — a signed transaction the network will not propagate.
