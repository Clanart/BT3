## Title
Stale line-selection indices vs. freshly re-fetched working directory diff cause silent corruption of partial commits - (File: `app/src/lib/git/apply.ts`)

### Summary
The C4 report's root cause is that `MoneyMarketHook._handleRepay` computes a value (`repayAmt`) from a **user-supplied quantity** (`shares`) instead of the **actual, current on-chain state** (`positionDebtShares`), and that state can change between when the value is computed and when it is consumed, silently corrupting the outcome. The same broken invariant — "the quantity used to build an operation is taken from a stale snapshot, not the live artifact it's about to be applied to" — exists in GitHub Desktop's partial-commit ("stage part of a diff") pipeline: `DiffSelection` line indices are computed against one diff snapshot (the one rendered in the Changes view), but `applyPatchToIndex` re-fetches a *fresh* diff of the file from disk at commit time and blindly re-applies the old, index-based selection to it.

### Finding Description
When a user stages only some lines/hunks of a modified file, the UI stores a `DiffSelection` keyed by **absolute line indices** (`hunk.unifiedDiffStart + lineIndex`) computed from the diff that was fetched when the file was selected/rendered: [1](#0-0) 

At commit time, `stageFiles` calls `applyPatchToIndex` for every partially-selected file: [2](#0-1) 

Crucially, `applyPatchToIndex` does **not** reuse the diff the selection was computed against — it fetches a brand-new diff straight from the working directory: [3](#0-2) 

That freshly-fetched diff is then handed to `formatPatch`, which re-applies the *old* `file.selection.isSelected(absoluteIndex)` decisions against the *new* hunk/line layout: [4](#0-3) 

If the tracked file's content on disk changes between the moment the user made their line selection (viewing the diff) and the moment `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` executes, the hunk boundaries and `unifiedDiffStart` offsets shift. The stale absolute indices then no longer correspond to the lines the user actually looked at and checked — `isSelected()` will silently select/deselect the wrong lines of the *new* content when building the patch that is `git apply --cached`'d into the index.

The app is aware that selection state can go stale relative to a new diff — `updateChangesWorkingDirectoryDiff` explicitly recomputes `selectableLines` and prunes indices that no longer exist when the diff is refreshed for **display**: [5](#0-4) 

But that reconciliation only happens on the UI-refresh path. `applyPatchToIndex`, which is on the actual commit-construction path, performs no such reconciliation — it fetches a diff and immediately trusts the caller's `file.selection` as still valid for it, with no check that the diff used for the patch matches the diff the selection was made against.

### Impact Explanation
This directly matches the requested "silent corruption of what the user commits or pushes" impact category. A file whose content is mutated by something other than the user's own edit-in-UI action (a background process, an editor's format/lint-on-save, a build step, a git smudge/clean filter triggered by another git operation, or content written by tooling that runs as part of opening/using an attacker-authored repository) between the time a user reviews and checks specific lines and the time they click "Commit" can cause Desktop to build a patch that includes different lines than what the user visually confirmed — without any warning, diff refresh, or confirmation dialog. Because Desktop applies the patch with `--whitespace=nowarn` and no re-validation, the resulting commit can silently contain content the user never selected (or omit content they did select), which is exactly the "corruption of what the user commits" class explicitly called out as valid impact.

### Likelihood Explanation
The window exists on every partial-file commit in Desktop; nothing about the flow re-checks or re-fetches the diff used for selection before it's consumed for the patch. Existing test coverage (`app/test/unit/git/commit-test.ts`) only demonstrates that partial commits work correctly when the file is static and the same diff is used throughout the selection lifecycle — it does not cover the case where the diff used to build the patch differs from the diff used to render the selection UI. This is a genuine, unguarded gap in the architecture rather than a purely theoretical one, since `getWorkingDirectoryDiff` is independently invoked at both the display layer and the commit layer with no cross-check.

### Recommendation
- Have `applyPatchToIndex`/`stageFiles` accept and use the exact diff object the `DiffSelection` was computed against (as already threaded through for `discardChangesFromSelection`, which takes an explicit `diff` parameter) rather than re-fetching a new diff at commit time.
- If a fresh diff must be fetched (e.g., to guard against staleness), validate that the fetched diff's hunk/line structure is unchanged from the one used to build the selection before applying it; if it differs, abort the partial-commit for that file and force the user to re-review the diff, mirroring the reconciliation logic already present in `updateChangesWorkingDirectoryDiff`.
- Surface an explicit error/warning to the user instead of silently applying a patch built from a possibly-mismatched selection/diff pairing.

### Proof of Concept
1. Open a repository in Desktop and modify a tracked file with several distinct hunks.
2. In the Changes view, partially select specific lines within one hunk (e.g., select only line 5 of hunk #2) — this computes `DiffSelection` absolute indices against the diff snapshot fetched by `updateChangesWorkingDirectoryDiff`.
3. Before clicking "Commit", have an external process (editor auto-format/lint-on-save, background build tool, or any file watcher shipped/triggered by the repository's tooling) modify the same file so that hunk boundaries shift (e.g., inserts/removes lines earlier in the file), without Desktop's Changes view refreshing/re-rendering the diff in that instant.
4. Click "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` runs, calling `getWorkingDirectoryDiff` fresh (`app/src/lib/git/apply.ts:60`) and reusing the stale `file.selection` from step 2 in `formatPatch` (`app/src/lib/patch-formatter.ts:157`).
5. Inspect the resulting commit: it contains different line(s) than what was visually checked in the UI in step 2, with no warning shown to the user.
