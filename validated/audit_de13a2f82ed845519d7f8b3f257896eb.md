### Title
Malicious preprocess can force the aggregate nonce `R` to the point at infinity, panicking `x()`/`Hram::hram` and aborting transaction signing - ([File: networks/bitcoin/src/crypto.rs](https://github.com/blackvul/serai--002/blob/main/networks/bitcoin/src/crypto.rs))

### Summary
The MultiInvoker report describes a DoS class: a helper (`_unwrap`) hard-reverts on an insufficient external balance instead of degrading gracefully, blocking `_liquidate`/`_withdraw`. The Serai analog is a hard panic on an attacker-controlled aggregate nonce. `x()` at `networks/bitcoin/src/crypto.rs:13-16` panics when passed the point at infinity, and `Hram::hram` at `crypto.rs:59-73` calls `x(R)` on the aggregate nonce computed from participant-supplied preprocesses. A malicious co-signer who supplies the last preprocess can choose commitments that cancel the running nonce sum, making `R` the identity and deterministically panicking `TransactionSignMachine::sign`.

### Finding Description
- `TransactionSignMachine::sign` (`networks/bitcoin/src/wallet/send.rs:355-398`) calls each per-input `AlgorithmSignMachine::sign` with a map of `Preprocess` values, each parsed from untrusted bytes by `read_preprocess` (`crypto/frost/src/sign.rs:276-281`) via `Commitments::read`, which accepts arbitrary group elements.
- In `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:323-380`), binding factors `rho` are computed over a transcript committing to all preprocesses, and nonce sums `R = D + rho * E` are accumulated per participant. Because rho depends only on the committed transcript, a signer who sends their preprocess last can compute all other participants' bound contributions `sum_i(D_i + rho_i * E_i)` and then choose their own `D, E` (e.g., `D = -sum`, `E = 0` or a point whose bound component cancels the remainder) so the final aggregate `R` is the point at infinity.
- The Schnorr `sign_share` path for Bitcoin then calls `Hram::hram(R, A, m)` (`networks/bitcoin/src/crypto.rs:59`), which calls `x(R)` at line 65. `x()` does `key.to_encoded_point(true).x().expect("point at infinity")` (lines 13-16), so an identity `R` panics rather than returning an error. The doc comment on `Schnorr` (lines 78-80) claims infinity is only "a negligible probability... even with malicious participants present," which is incorrect: it is deterministically reachable by the last preprocessing participant.

### Impact Explanation
Analogous to the `_unwrap` revert: instead of returning `FrostError::InvalidPreprocess`, the code panics inside `sign`. A single malicious or compromised signing participant (or anyone able to feed crafted bytes to `read_preprocess`, e.g., via `CoordinatorMessage::Preprocesses` handled in `processor/src/signer.rs:507-531` / `batch_signer.rs:241-271`) can deterministically crash/abort the signing attempt for every Bitcoin input in the batch. Since each `sign` call recomputes `R` over the same malicious preprocess, retrying the same attempt panics again, halting production of the transaction signature — a persistent disruption of normal operation, not a recoverable error. No secret is leaked; impact is availability of the multisig signing path.

### Likelihood Explanation
Requires a participant slot in the signing set (or the ability to inject preprocess bytes into a `complete`/`sign` path) and ordering to supply the cancellative commitment last — the same "last mover" advantage used in ROS-style attacks. The preprocess channel is exactly the untrusted-input surface listed for `read_preprocess`/`Commitments::read`, so this is reachable with public protocol messages; no validator keys or internal state are needed.

### Recommendation
- In `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs`), reject preprocesses whose bound contribution or the resulting aggregate `R` is the point at infinity, returning `FrostError::InvalidPreprocess(l)` instead of proceeding.
- Alternatively, make `Hram::hram`/`x()` return `Option`/`Result` and propagate an error rather than `expect("point at infinity")` at `crypto.rs:15`, and fix the incorrect "negligible probability" doc comment at `crypto.rs:78-80`.

### Proof of Concept
1. Honest participants broadcast preprocesses `(D_i, E_i)`. Attacker `j` computes each `rho_i` from the `FROST_rho` transcript (group_key, `hash_msg`, `hash_commitments` over the transcript) exactly as `B.calculate_binding_factors` does in `crypto/frost/src/sign.rs:361-371`.
2. Attacker publishes preprocess `(D_j, E_j) = (-(Σ_{i≠j}(D_i + rho_i·E_i))·rho_j^{-1} - 0, 0)` equivalently choosing `D_j`/`E_j` so `D_j + rho_j·E_j` cancels the accumulated sum, yielding `R = identity`.
3. Every signer calls `sign_share` → `Hram::hram(&R, &A, msg)` → `x(&R)` → `to_encoded_point(true).x().expect("point at infinity")` (`crypto.rs:15`) → panic. `TransactionSignMachine::sign` (`send.rs:383-391`) aborts; no shares are produced and reattempts with the same preprocesses panic identically.
