## Analog Found: `placeOrder` in IntentGatewayV2 accepts an unvalidated `order.destination` chain identifier

### Title
Unvalidated destination chain identifier in `placeOrder` can permanently lock escrowed funds - (File: `evm/src/apps/IntentGatewayV2.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report's core defect is that a bridging entry point (`burnAndBridge`) commits user funds to a cross-chain operation without validating that the destination chain identifier is part of a supported/whitelisted set, or that the recipient is valid — creating a path to irrecoverable loss of funds. Hyperbridge's `IntentGatewayV2.placeOrder` has the same missing-invariant shape: it escrows the user's input tokens and computes/emits the order commitment for an arbitrary, caller-supplied `order.destination` value, with no check that this destination corresponds to a chain Hyperbridge/the gateway actually supports.

### Finding Description
`placeOrder` validates only that `order.inputs.length != 0` before escrowing tokens; it never checks `order.destination` against any known/registered state machine: [1](#0-0) 

Compare this to `instance()`, the only place a destination is resolved to a gateway address, which silently falls back to `address(this)` for anything unregistered rather than reverting: [2](#0-1) 

The only place a destination/chain mismatch is actually checked is inside `fillOrder`, and only on the chain where a solver attempts the fill — it compares the *hash* of `order.destination`/`order.source` against the *current* chain's own state-machine id, it does not validate that `order.destination` is a chain that exists/is supported by Hyperbridge at all: [3](#0-2) 

So at `placeOrder` time — the point where the user's tokens are pulled into escrow — there is no whitelist check equivalent to what the external report recommends for `destChainId`. If `order.destination` is garbage, a typo'd state-machine id, or a chain that Hyperbridge has no consensus client for, the order can never be filled (no chain will ever match `orderDest == currentChain` for that value), and per the documented cancellation flow, cross-chain cancellation also depends on dispatching a `DispatchGet` to that same destination and waiting for a Hyperbridge state commitment for it — which never happens for an unsupported/nonexistent state machine, per: [4](#0-3) 

This mirrors the reported bug class exactly: user funds are committed on-chain to a bridging path keyed by an unvalidated destination identifier, with no whitelist gate, and once escrowed there is no address-independent recovery path if that identifier turns out to be unsupported.

### Impact Explanation
Escrowed input tokens for an order with an invalid/unsupported `order.destination` become permanently unfillable and, per the documented cancel flow, also unresolvable via the GET-based cancellation path (which itself routes through Hyperbridge against the same bad destination id) — resulting in a fund lock with no privileged actor, malicious relayer, or governance action required. This satisfies the "stealing or loss of funds" / "logic attacks" bar in the impact gate: an ordinary user (or an integrator's buggy frontend building the `Order` struct, e.g. from `sdk`) can lock their own principal, and there is no on-chain guard preventing it.

### Likelihood Explanation
`placeOrder` is a fully public, unprivileged entry point that any EOA can call directly with an arbitrary `Order` struct, so no relayer/prover/admin/governance compromise is required — the caller alone controls `order.destination` and `order.inputs`. The only friction is that the caller must supply their own bad/unsupported destination id, but nothing in the contract prevents or warns against it, and integrations composing `Order` off-chain (e.g. via the SDK) could pass through a misconfigured or stale state-machine id without any on-chain rejection.

### Recommendation
Validate `order.destination` in `placeOrder` before escrowing any tokens — e.g., require it to equal the current chain (same-chain order) or to be present in `_instances` (a known, registered peer gateway/chain), reverting with a distinct error (e.g. `UnsupportedDestination()`) otherwise. This mirrors the report's recommendation to whitelist `destChainId` before performing the bridging operation, and prevents committing user funds to a destination the protocol cannot actually service.

### Proof of Concept
1. Attacker/user calls `intentGateway.placeOrder(order, graffiti)` with `order.destination = bytes("NOT_A_REAL_CHAIN")` and valid `order.inputs`/approvals.
2. `placeOrder` accepts the call, escrows the input tokens, computes `commitment`, and emits `OrderPlaced` — no revert, since `order.destination` is never checked (`evm/tron/contracts/apps/IntentGatewayV2.sol:332-349`).
3. No solver can ever call `fillOrder` successfully for this order because no real chain's `host().host()` hash will ever equal `keccak256(order.destination)` (`evm/src/apps/IntentGatewayV2.sol:417-424`).
4. `cancelOrder` (source-chain path) attempts to dispatch a `DispatchGet` against `order.destination` to prove non-fill, but Hyperbridge has no consensus client / state commitments for a nonexistent state machine, so the response required to trigger the refund via `withdraw()` never arrives (per `docs/content/developers/evm/intent-gateway/overview.mdx:63`).
5. The escrowed input tokens remain locked in the gateway indefinitely.

Note: I was not able to read the exact `cancelOrder`/`withdraw` implementation source in this session (only its documented behavior), so step 4's exact revert/hang behavior for a truly unregistered/never-verifiable destination should be confirmed against the live `cancelOrder` code before treating this as fully proven.

```text
        if (order.deadline < _blockNumber()) revert Expired();
        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain && orderSource != currentChain) revert WrongChain();
        if (!isSameChain && orderDest != currentChain) revert WrongChain();
```

```text
### Cancellation

There are two modes for cross-chain cancellation:

**Cancel from source chain**: The user calls `cancelOrder()` on the source chain, which dispatches a `DispatchGet` storage read request to query the destination chain's fill status. The `CancelOptions.height` must be greater than `order.deadline` — this ensures the proof is taken from a block after the order has expired. A relayer processes this request on Hyperbridge by providing storage proofs from the destination chain. If the storage slot for `_filled[commitment]` is empty (order unfilled), Hyperbridge dispatches a response back to the source chain. The `onGetResponse` handler verifies the empty proof and calls `withdraw()` to refund the escrowed tokens to the user. If the order was filled, the response contains a non-empty value and the handler reverts with `Filled()`.

![Cancel from Source Chain](/intent-gateway-cancel-source.svg)

**Cancel from destination chain**: Before the deadline, only the order owner can call `cancelOrder()` on the destination chain. After the deadline, anyone can cancel. The function marks the order as cancelled locally (`_filled[commitment] = user`) to prevent future fills, then dispatches a cross-chain `RefundEscrow` message back to the source chain. When the source chain receives this message via `onAccept()`, it calls `withdraw()` to refund the escrowed tokens to the user and emits `EscrowRefunded(commitment)`.
```
