### Title
Unbounded consensus-decoded `TxOut` value accepted into fee/balance arithmetic, enabling wrapped input accounting and signing of transactions over phantom funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

The bug class in CVE-2022-48828 is a 64-bit unsigned wire value being dropped into a domain that cannot represent it (signed `loff_t`), producing a negative/wrapped result caught only downstream. The direct analog exists in `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`), which consensus-decodes an attacker-influenced `TxOut` whose `value` is a full `u64` with no bound check against Bitcoin's `MAX_MONEY` (21e14 sats) or `i64::MAX`, then feeds it into unchecked `u64` sum/subtract arithmetic in `SignableTransaction` (`networks/bitcoin/src/wallet/send.rs:139-140, 175, 187, 215, 228`).

### Finding Description

`ReceivedOutput::read` performs:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
outpoint = OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
Ok(ReceivedOutput { offset, output, outpoint })
```

There is no validation that `output.value` is within the valid satoshi range. The `value` field is then consumed in three unchecked places in `send.rs`:

- `SignableTransaction::new` computes `input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>()` (line 175). A crafted `ReceivedOutput` with `value = u64::MAX` either panics on `sum` overflow (debug/checked builds) or wraps `input_sat` to a small residue (release), corrupting the solvency check `input_sat < payment_sat + needed_fee` (line 215).
- The change computation `input_sat.checked_sub(payment_sat + fee_with_change)` (line 228) relies on `input_sat` being honest; a wrapped or inflated value yields a fabricated change `TxOut`.
- `fee()` (lines 139-140) computes `sum(prevouts) - sum(outputs)` with a plain subtraction; it can underflow-panic if outputs exceed prevouts in any flow where the constructor's invariant was bypassed via wrapped sums.

Because `TransactionSignMachine::sign` hashes `Prevouts::All(&self.tx.prevouts)` into each Taproot sighash (send.rs:375-390), the threshold group ends up signing a transaction committing to a fabricated input value. The resulting signed transaction is consensus-invalid on Bitcoin: the reported/scanned balance is phantom and unspendable.

### Impact Explanation

- A forged `ReceivedOutput` encoding `value = u64::MAX` (or any value above the real UTXO's worth) causes the wallet to treat non-existent satoshis as available balance. Any change output and fee computation derived from it is wrong, and the signed transaction is unbroadcastable — funds are treated as received/available that are not spendable.
- `sum::<u64>()` overflow and the unchecked `fee()` subtraction panic on hostile inputs, denying service to the signing process mid-attempt.
- No `Amount`/range check exists anywhere between the wire bytes and the sighash, mirroring NFSD dumping a raw u64 into `ia_size` and only detecting the problem in the common path.

### Likelihood Explanation

Reachable whenever `ReceivedOutput::read` deserializes bytes not produced by the local `Scanner` (e.g., peer-provided or replayed serialized outputs). Exploitation requires only control of the serialized buffer — no key material, threshold collusion, or validator misbehavior is needed. The arithmetic overflow paths are deterministic once a value exceeding the representable/legitimate range is supplied.

### Recommendation

In `ReceivedOutput::read`, validate `output.value` against `bitcoin::Amount::MAX_MONEY` (or `SignedAmount::MAX_MONEY`) after `consensus_decode`. Additionally, use `checked_add`/`checked_sub` (or `Amount` arithmetic) for `input_sat`, `payment_sat`, `needed_fee`, and `fee()` in `send.rs`, returning `TransactionError` instead of panicking or wrapping.

### Proof of Concept

```rust
use std::io::Cursor;
use bitcoin::{Amount, TxOut, OutPoint, ScriptBuf, consensus::encode::serialize};
use bitcoin_serai::wallet::ReceivedOutput;

// Build a ReceivedOutput claiming u64::MAX satoshis
let mut buf = Secp256k1_scalar_bytes().to_vec();          // any valid scalar offset
buf.extend(serialize(&TxOut {
    value: Amount::from_sat(u64::MAX),                     // > MAX_MONEY, accepted unchecked
    script_pubkey: ScriptBuf::new(),
}));
buf.extend(serialize(&OutPoint::default()));

let output = ReceivedOutput::read(&mut Cursor::new(buf)).unwrap();
assert_eq!(output.value(), u64::MAX); // unbounded value accepted

// Then: SignableTransaction::new(vec![output], &payments, change, None, fee)
// -> input_sat = u64::MAX (+ others) overflows sum::<u64>() / wraps,
// -> NotEnoughFunds check and change math operate on phantom balance,
// -> sighash (Prevouts::All) commits to the fabricated value; the signed tx is
//    consensus-invalid on the Bitcoin network.
```

Uncertainty: I could not fully trace every caller that feeds untrusted bytes into `ReceivedOutput::read` within the indexing limits; per the in-scope rules, `ReceivedOutput::read` is an accepted reachable sink. The panic-vs-wrap behavior on `sum::<u64>()` depends on the build's overflow-checks setting, but the missing range validation is unconditional.
