### Title
Duplicate Bitcoin inputs double-count input value and produce an unspendable transaction - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` does not reject duplicate `ReceivedOutput`s. The same `OutPoint` can therefore be counted once in `input_sat` for every supplied copy, while the transaction also receives a duplicate `TxIn`. The result is a signed transaction whose outputs were funded by non-existent duplicate value and which Bitcoin consensus rejects as invalid.

### Finding Description
`ReceivedOutput::read` accepts an arbitrary offset, `TxOut`, and `OutPoint` without any later uniqueness requirement on the `OutPoint`. [1](#0-0)  `SignableTransaction::new` then sums every supplied input’s `output.value`, creates one `TxIn` for every entry, and preserves every supplied `TxOut` as a sighash prevout. [2](#0-1)  The funding check compares this duplicated `input_sat` against payments and fees. [3](#0-2)  The saved `offsets` and `prevouts` likewise contain one entry per duplicate input. [4](#0-3) 

Each duplicate input is independently key-checked and converted into a signing machine. [5](#0-4)  Signing commits to all duplicated prevouts with `Prevouts::All`, and completion inserts a witness for each duplicate input. [6](#0-5) [7](#0-6) 

### Impact Explanation
This is the same accounting shape as `longToken == shortToken`: one resource occupies two accounting slots without a divisor or equality rejection. A duplicated UTXO with value `v` contributes `2v` to `input_sat`, allowing payments or change that cannot actually be funded. The signed transaction is not spendable because it attempts to consume the same `OutPoint` twice, so downstream accounting may report outputs paid while no valid on-chain transfer exists.

### Likelihood Explanation
Any caller or coordinator able to supply `Vec<ReceivedOutput>` can repeat the same decoded output. `ReceivedOutput::read` makes this reachable from serialized transaction-planning input, and no uniqueness check exists before value aggregation, transaction construction, or signing.

### Recommendation
Reject duplicate `OutPoint`s in `SignableTransaction::new`. Insert each `input.outpoint` into a `HashSet` and return a new `TransactionError::DuplicateInput` when insertion fails. This should occur before `input_sat`, `tx_ins`, `offsets`, or `prevouts` are computed.

### Proof of Concept
```rust
let bytes = received.serialize();
let duplicate = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();

// The same OutPoint is counted twice.
let inputs = vec![received.clone(), duplicate];

// A payment larger than the real UTXO can pass the funding check because
// input_sat = received.value() * 2.
let tx = SignableTransaction::new(
  inputs,
  &[(destination_script, received.value() + spendable_delta)],
  Some(change_script),
  None,
  fee_rate,
).unwrap();

let machine = tx.clone().multisig(&keys).unwrap();
// All signers can sign the generated sighashes, but the resulting transaction
// contains duplicate inputs spending the same OutPoint and is invalid.
```
