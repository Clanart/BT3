## Title
Webhook shop identification header is not covered by HMAC signature, allowing forged/replayed webhook shop-domain claims - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#shop_domain` returns the value of the `X-Shopify-Shop-Domain` request header directly, while `hmac_valid?` only verifies the raw POST body. Because the shop-identifying header is never included in the signed material, an attacker who obtains any single valid `(body, HMAC)` pair — for example by capturing/replaying a webhook delivery from a shop they control — can resend that exact body/signature to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. The request passes `verify_request` unchanged, and code that trusts `shop_domain` (as ShopifyApp's own documentation instructs) will process/attribute the webhook to the wrong shop.

### Finding Description
`before_action :verify_request` in `WebhookVerification` only calls `hmac_valid?(request.raw_post)`: [1](#0-0) 

`hmac_valid?` computes/compares the HMAC solely over `data` (the raw body) against the app's shared secret(s): [2](#0-1) 

`shop_domain` is derived straight from the unauthenticated `X-Shopify-Shop-Domain` header, with no cryptographic binding to the verified body: [3](#0-2) 

ShopifyApp's own documentation instructs developers building custom webhook controllers to use this unvalidated `shop_domain` value directly as the tenant key when enqueuing jobs: [4](#0-3) 

This is analogous to the reported Rolla `Controller._qTokenPermit` bug: the outer envelope (the "interface"/signature) is checked, but the specific identifying field used downstream (`qToken` address / `shop_domain` header) is trusted without being cryptographically tied to, or independently verified against, the thing that was actually authenticated (the permit signature domain / the HMAC-signed body).

### Impact Explanation
Any party capable of obtaining one legitimate `(raw_body, HMAC)` pair from Shopify (trivially available to any merchant who installs the app on their own store, since they can observe/capture their own store's webhook deliveries) can replay that exact pair to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header value. Because the header is outside the signed content, the forged request is accepted as authentic. Any app logic keyed on `shop_domain` (job dispatch, per-shop data writes, cache/queue partitioning, audit logging) can be made to attribute attacker-controlled webhook content to a victim shop, producing cross-shop data confusion/injection.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on any shop to receive at least one real webhook delivery (or otherwise obtaining a valid body/HMAC pair), and (2) sending a crafted HTTP POST to the app's public webhook endpoint with that captured body/HMAC and a spoofed shop-domain header. No secrets need to be extracted; the app secret is never disclosed to the attacker, only its signature output for one known message is reused. This is reachable from an unrelated/anonymous merchant account, matching the "unprivileged" reachability constraints.

### Recommendation
Do not treat `X-Shopify-Shop-Domain` (or any header) as trusted tenant context unless it is cryptographically bound to the verified payload. Either:
- Derive the shop from the signed webhook body/topic metadata parsed by `ShopifyAPI::Webhooks::Request`/`Registry` (as the built-in `WebhooksController` does) rather than exposing/encouraging a raw header-based `shop_domain` helper, or
- Include the shop domain in the HMAC-covered material (e.g., verify header+body together) before trusting it, and update the documented custom-controller pattern in `docs/shopify_app/webhooks.md` accordingly.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; capture one legitimate webhook POST (raw body `B` and its valid `X-Shopify-Hmac-Sha256` value `H`, computed by Shopify using the app's shared secret).
2. Send a new POST to the app's custom webhook endpoint (built with `include ShopifyApp::WebhookVerification` per the documented pattern) with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid), but `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `verify_request` passes because `hmac_valid?(request.raw_post)` only checks `B`/`H`, which are consistent — see `lib/shopify_app/controller_concerns/webhook_verification.rb:15-21` and `lib/shopify_app/controller_concerns/payload_verification.rb:9-23`.
4. The controller action calls `shop_domain`, which returns `"victim.myshopify.com"`, and enqueues/processes the attacker's body `B` as if it belonged to the victim shop, per the pattern shown in `docs/shopify_app/webhooks.md:86-104`.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

```markdown
If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
