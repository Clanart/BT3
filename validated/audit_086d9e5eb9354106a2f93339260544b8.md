## Finding

### Title
Data Layer `add_missing_files` RPC allows arbitrary-path file writes via unvalidated `foldername` - ([File: chia/data_layer/data_layer_rpc_api.py])

### Summary
The DataLayer RPC endpoint `add_missing_files` accepts a client-supplied `foldername` string and converts it directly into a filesystem `Path` with no containment check against the service's configured `server_files_location`, then uses that path as the destination directory for writing `.dat` tree files (creating any missing parent directories along the way).

### Finding Description
`DataLayerRpcApi.add_missing_files()` reads the optional `foldername` field straight from the JSON request body and wraps it in `Path()` without any validation, canonicalization, or restriction to a safe base directory: [1](#0-0) 

That value is passed through to `DataLayer.add_missing_files()`, which uses it verbatim as `server_files_location` for `write_files_for_root()`: [2](#0-1) 

`write_files_for_root()` derives the full/diff filenames under that caller-controlled folder, unconditionally creates the parent directory tree (`mkdir(parents=True, exist_ok=True)`), and opens the file for writing (`"wb"` when `overwrite=True`): [3](#0-2) 

The written content is produced by `DataStore.write_tree_to_file()`, serializing the local Merkle tree for a store the caller already owns/controls (key/value data inserted via prior `batch_update`/`insert` calls), so the caller has meaningful influence over both the destination directory (absolute or relative, anywhere the process has write permission) and, indirectly, part of the written bytes. There is no analog of the filename-shape validation (`is_filename_valid()`) that the static file server or S3 plugin apply to uploaded/served files — that check only guards mirrored uploads, not this local reconstruction path.

The DataLayer service context notes call out this exact gap: "Static file serving validates filenames but uses direct synchronous file reads..." and flags file-system writes for `.dat` files as a fragility hotspot without directory containment. [4](#0-3) 

### Impact Explanation
An authorized DataLayer RPC caller (any client holding the DataLayer service's private RPC client certificate — the "local RPC caller" trust class) can direct the service to create arbitrary directories and write `.dat` files to any path the DataLayer process can access, rather than being confined to the configured `server_files_location`. Because the file content is derived from Merkle-tree data the caller previously inserted into their own store, the caller also has partial control over the written bytes. This is a File System Path/Directory-write vulnerability class consistent with the referenced CVE's "file writing vulnerabilities" bug class, and could be used to plant or overwrite files outside the intended DataLayer server-files sandbox.

### Likelihood Explanation
Reaching this requires only calling the standard `add_missing_files` DataLayer RPC endpoint with a `foldername` value — no chain state, mempool, or consensus interaction is needed, and the endpoint is part of the normal DataLayer client API surface (also exposed via the `chia data add_missing_files -d <dir>` CLI convenience, but independently reachable directly over RPC). The only prerequisite is RPC access to the DataLayer service, which is the explicitly in-scope "local RPC caller" actor.

### Recommendation
Validate and canonicalize `foldername` in `DataLayerRpcApi.add_missing_files()` (and in `DataLayer.add_missing_files()`) to ensure the resolved path stays within an allow-listed base directory (e.g., `server_files_location` or an explicitly configured alternate root), rejecting absolute paths or `..` traversal that escape it. Apply the same filename/path validation used for mirrored/uploaded files (`is_filename_valid()`-style checks) to this local reconstruction path as well.

### Proof of Concept
1. Start a DataLayer node with RPC enabled and create/own a store (`create_data_store`), insert some keys/values, and let it commit at least one generation.
2. Call the RPC endpoint directly:
```
POST /add_missing_files
{
  "ids": ["<store_id_hex>"],
  "overwrite": true,
  "foldername": "/tmp/outside_server_files"
}
```
3. Observe that `data_layer_rpc_api.py`'s `add_missing_files` accepts `foldername` unmodified [5](#0-4)  and that `write_files_for_root()` creates `/tmp/outside_server_files` (via `mkdir(parents=True, exist_ok=True)`) and writes `<store_id>-<node_hash>-full-<gen>-v1.0.dat` / `-delta-` files there — entirely outside the configured `server_files_location` — confirming the unvalidated, caller-controlled write path.

    async def add_missing_files(self, request: dict[str, Any]) -> EndpointResult:
        """
        complete the data server files.
        """
        if "ids" in request:
            store_ids = request["ids"]
            ids_bytes = [bytes32.from_hexstr(id) for id in store_ids]
        else:
            subscriptions: list[Subscription] = await self.service.get_subscriptions()
            ids_bytes = [subscription.store_id for subscription in subscriptions]
        overwrite = request.get("overwrite", False)
        foldername: Path | None = None
        if "foldername" in request:
            foldername = Path(request["foldername"])
        for store_id in ids_bytes:
            await self.service.add_missing_files(store_id, overwrite, foldername)
        return {}

    async def add_missing_files(self, store_id: bytes32, overwrite: bool, foldername: Path | None) -> None:
        root = await self.data_store.get_tree_root(store_id=store_id)
        latest_generation = root.generation
        full_tree_first_publish_generation = max(0, latest_generation - self.maximum_full_file_count + 1)
        singleton_record = (
            await self.wallet_rpc.dl_latest_singleton(DLLatestSingleton(launcher_id=store_id, only_confirmed=True))
        ).singleton
        if singleton_record is None:
            self.log.error(f"No singleton record found for: {store_id}")
            return
        max_generation = min(singleton_record.generation, root.generation)
        server_files_location = foldername if foldername is not None else self.server_files_location
        files = []
        for generation in range(1, max_generation + 1):
            root = await self.data_store.get_tree_root(store_id=store_id, generation=generation)
            res = await write_files_for_root(
                self.data_store,
                store_id,
                root,
                server_files_location,
                full_tree_first_publish_generation,
                overwrite,
                self.group_files_by_store,
            )
            files.append(res.diff_tree.name)
            if res.full_tree is not None:
                files.append(res.full_tree.name)

- Static file serving validates filenames but uses direct synchronous file reads in the request handler. It assumes files are already written under `server_files_location` by the service or plugin.

## Fragility Hotspots

- High-risk edits move work across DB writer transactions, `_update_confirmation_status()`, pending-root status changes, or wallet RPC calls. These boundaries encode publication and rollback assumptions.
- File-system writes for Merkle blobs, key/value blobs, and `.dat` files have TODOs around locking. Concurrent service/plugin/server access should be treated as a real consistency concern.
- Empty-root normalization is subtle and historically uneven. Audit any change touching `bytes32.zeros`, `None`, `Root.node_hash`, or proof roots with both empty and non-empty stores.
- Plugin and mirror URLs are external trust inputs. Downloaded data must continue to be verified against wallet-advertised roots, and file path/name validation must stay strict.
