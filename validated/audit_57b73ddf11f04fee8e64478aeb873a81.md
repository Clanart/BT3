### Title
Stale decimals invariant lets `convert_to_balance` skip scaling and mint an inflated amount - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
This is the same bug class as the `PublicSale._computeTokens` report: an amount-conversion helper that assumes a decimals relationship holds without re-checking it at the point of use. In `hyper-fungible-token`, the `erc_decimals >= local_decimals` invariant is enforced only once, at `register_token`/`update_token` time, and against `local_decimals` captured live from the local asset's mutable metadata. If that metadata's `decimals` value can change after registration, the invariant silently breaks and `convert_to_balance` stops scaling the incoming amount at all, minting/transferring far more than the bridged value warrants.

### Finding Description
`convert_to_balance` divides the incoming ERC20-denominated `U256` by `10^(erc_decimals - local_decimals)`, using `saturating_sub`: [1](#0-0) 

If `local_decimals > erc_decimals`, `erc_decimals.saturating_sub(local_decimals)` clamps to `0`, so the divisor becomes `10^0 = 1` — **no downscaling occurs at all**, and the raw ERC20-precision value is parsed directly as the local balance.

The only place this ordering is checked is at registration/update time, gated by the privileged `CreateOrigin`: [2](#0-1) [3](#0-2) 

But at message-processing time (`on_accept` and `on_timeout`), `local_decimals` is **not** the value that was checked at registration — it is re-fetched live from the asset's own metadata via `fungibles::metadata::Inspect::decimals`, while `erc_decimals` is the value frozen in `Precisions` storage at registration: [4](#0-3) [5](#0-4) 

Because `local_decimals` is sourced from `pallet_assets` metadata rather than from a value frozen inside the HFT pallet, and asset metadata (`decimals`) is normally mutable by the asset's own owner/admin via `set_metadata` — an authority entirely independent of the HFT pallet's `CreateOrigin` — the `erc_decimals >= local_decimals` invariant enforced once at registration is never re-verified before it is relied upon in `on_accept`/`on_timeout`. Bumping the local asset's `decimals` above the registered `erc_decimals` after registration silently defeats the scaling guard.

Once broken, an inbound message carrying `message.amount` denominated at `erc_decimals` gets parsed with **no division**, so the pallet mints/transfers a local balance that is `10^(local_decimals - erc_decimals)` times larger than it should be, and immediately credits it to `beneficiary` via `mint_into`/`transfer`: [6](#0-5) 

### Impact Explanation
This produces unbacked minting or over-transfer of escrowed native currency for a real but comparatively tiny bridged amount — direct fund creation/loss on a live bridge pallet, matching the bounty's "stealing or loss of funds" / "unauthorized transaction execution" categories. The blast radius scales with the decimals gap (e.g., a 12-decimal gap is a 10^12x inflation), so even a dust-sized cross-chain transfer can mint an enormous local balance.

### Likelihood Explanation
Medium: it requires the local asset's decimals metadata to be increased after HFT registration. This does not require compromising the bridge's admin (`CreateOrigin`), a relayer, or a prover — only the ability to alter the registered local asset's own metadata, which in standard `pallet-assets` deployments is controlled by the asset's `Owner`/`Admin` role, a role separate from and typically less privileged than bridge governance. Whether this specific runtime permits post-creation `decimals` mutation on assets registered with HFT could not be fully confirmed from the pallet code alone (that lives in the runtime's `pallet_assets` configuration), so this should be validated against the concrete runtime binding of `Config::Assets`.

### Recommendation
Freeze and store `local_decimals` in the `Precisions` map (or a dedicated storage item) at `register_token`/`update_token` time, exactly as `erc_decimals` already is, instead of re-reading live asset metadata in `send`, `on_accept`, and `on_timeout`. Additionally, re-validate `erc_decimals >= local_decimals` (or explicitly handle both directions safely) at conversion time rather than relying solely on a one-time registration-time check, and reject with `ErcDecimalsBelowLocal` if the relationship no longer holds instead of silently saturating the exponent to zero.

### Proof of Concept
1. Register a local asset `A` with `local_decimals = 6` and `erc_decimals = 18` for chain `C` (passes the `>=` check).
2. Asset `A`'s owner calls `pallet_assets::set_metadata` to raise `A`'s decimals to `24` (no interaction with the HFT pallet needed).
3. A cross-chain `send`/incoming message for `A` from chain `C` carrying `message.amount = 1` (1 wei at 18-decimal ERC precision, effectively dust) arrives at `on_accept`.
4. `local_decimals` is fetched live as `24`; `erc_decimals` from storage is still `18`. `erc_decimals.saturating_sub(local_decimals) = 0`, so `convert_to_balance` returns `1` un-scaled instead of `0` (a dust amount rounds up incorrectly) — for larger crafted amounts this becomes `10^6`x+ inflation of the minted/transferred local balance relative to what the ERC-side escrow/burn actually represents, corrupting `amount` in the `mint_into`/`transfer` call at [7](#0-6) .

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
