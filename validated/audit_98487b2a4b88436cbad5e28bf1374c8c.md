### Title
Missing Ownership Check in `register_remote_coins` Lets a Local RPC Caller Poison the Wallet's Coin/Balance State - ([File: chia/wallet/remote_wallet/remote_wallet.py])

### Summary
`WalletRpcApi.register_remote_coins` and `RemoteWallet.register_remote_coins` accept a caller-supplied list of `coin_ids` and register them for the `RemoteWallet` without ever checking that the coin actually corresponds to a puzzle hash the wallet is entitled to track or that the coin's identity/state is legitimate. This mirrors the act vulnerability's root cause: a control-plane entry point trusts a caller-supplied identifier (there: `workflow_run_backend_id`; here: `coin_id`) without validating it belongs to/should belong to the requester, and the values are inserted directly into persisted state that downstream logic (balance accounting, `coin_added`/`_add_coin_states`) treats as authoritative.

### Finding Description
`register_remote_coins` in `chia/wallet/wallet_rpc_api.py` looks up the target wallet by `wallet_id` and forwards the caller-supplied `coin_ids` straight into `RemoteWallet.register_remote_coins`: [1](#0-0) 

`RemoteWallet.register_remote_coins` performs no validation of the `coin_ids` themselves — it does not verify the coin exists, that it is tied to a puzzle hash controlled by this wallet, or that it is legitimately associated with any actual on-chain activity relevant to the caller. It simply persists the caller-supplied IDs and subscribes to them: [2](#0-1) 

Persistence goes through `RemoteCoinStore.add_coin_ids`, which is a blind `INSERT OR IGNORE` keyed only on the caller-provided `coin_id` and `wallet_id`, with no cross-check against coin ownership or puzzle-hash membership: [3](#0-2) 

Once subscribed, any coin state the full node reports for these IDs is accepted into the wallet's `coin_store` as a `WalletType.REMOTE` record, and — as covered by the module's own tests — this REMOTE record is later promoted to a real wallet record if a puzzle hash becomes recognized, directly feeding wallet balance calculations: [4](#0-3) 

This is directly analogous to the act bug class: a control-plane RPC (`register_remote_coins`) accepts a caller-controlled identifier (`coin_id`) and performs a state-mutating action (subscription + coin-store insertion feeding balance/tx-matching state) without validating that the identifier legitimately belongs to the calling context.

### Impact Explanation
An RPC caller with access to the wallet RPC (any local caller of the wallet daemon RPC, or any code path that can drive `register_remote_coins`) can register arbitrary, attacker-chosen `coin_ids` — including coins that do not belong to the wallet's own puzzle hashes — causing the wallet's coin store and balance tracking to reflect coins/state that were never legitimately validated against the caller's authority over them. Because REMOTE records can transition into real wallet identifiers once a puzzle hash is later recognized (as shown in `test_remote_record_transitions_to_real_wallet_on_reprocess`), this creates a path where unvalidated externally-supplied coin identity can leak into wallet balance/coin-record state that other RPC consumers (send/select-coins flows) rely on, i.e., coin-set/state divergence from what the wallet should actually be authoritative over.

### Likelihood Explanation
Likelihood is Medium: exploitation requires access to the wallet RPC (typically local, or exposed if `--rpc-server-max-request-body-size`/network exposure settings are relaxed), and the `RemoteWallet` mechanism is a relatively new, narrowly-scoped feature (only one `RemoteWallet` instance is supported per wallet, per `create_new_remote_wallet`), which limits blast radius but does not eliminate the missing authorization check at the RPC boundary.

### Recommendation
Before persisting/subscribing to caller-supplied `coin_ids` in `register_remote_coins`, validate the coin's actual on-chain puzzle hash/ownership context (e.g., require the coin to be independently justified, such as via a spend bundle, offer, or other cryptographically-verifiable linkage) rather than accepting bare `bytes32` IDs from the RPC caller at face value. At minimum, rate-limit and audit-log registrations, and ensure REMOTE-to-real-wallet promotion logic re-validates puzzle-hash ownership rather than trusting the prior REMOTE record's provenance.

### Proof of Concept
1. Start a wallet with an RPC client connection (as in `chia/_tests/wallet/remote_wallet/test_remote_wallet.py`).
2. Create a `RemoteWallet` via `create_new_wallet` (`CreateNewWalletType.REMOTE_WALLET`).
3. Call `register_remote_coins` with a `coin_id` chosen arbitrarily by the caller (not derived from any coin the caller has any legitimate claim over) — see `RegisterRemoteCoins(wallet_id=remote_wallet.id(), coin_ids=[coin_id])` in [5](#0-4) .
4. Observe that the coin store persists a `WalletType.REMOTE` record for that ID with no ownership validation, and that subsequent state updates for that coin ID feed directly into wallet-visible balance/coin-record state.

```python
    async def register_remote_coins(self, coin_ids: list[bytes32]) -> None:
        if len(coin_ids) == 0:
            return

        unique_coin_ids = list(dict.fromkeys(coin_ids))
        await self.wallet_state_manager.remote_coin_store.add_coin_ids(unique_coin_ids, self.wallet_info.id)
        await self.wallet_state_manager.add_interested_coin_ids(unique_coin_ids, [self.wallet_info.id])
```

```python
    async def add_coin_ids(self, coin_ids: list[bytes32], wallet_id: uint32) -> int:
        """Insert coin IDs for *wallet_id*, ignoring duplicates. Returns the number of newly inserted rows."""
        if len(coin_ids) == 0:
            return 0

        added = 0
        async with self.db_wrapper.writer_maybe_transaction() as conn:
            for coin_id in coin_ids:
                result = await conn.execute(
                    "INSERT OR IGNORE INTO remote_coins (coin_id, wallet_id) VALUES (?, ?)",
                    (bytes(coin_id), int(wallet_id)),
                )
                added += result.rowcount
        return added
```

```python
async def test_remote_wallet_register_remote_coins_persists_coin_records(
    wallet_environments: WalletTestFramework,
) -> None:
    env = wallet_environments.environments[0]
    wallet: Wallet = env.xch_wallet
    wallet_node: WalletNode = env.node

    # Create multiple coins that no wallet owns by sending to puzzle hashes we don't own.
    target_ph_1 = bytes32(bytes([21] * 32))
    target_ph_2 = bytes32(bytes([22] * 32))
    async with wallet.wallet_state_manager.new_action_scope(wallet_environments.tx_config, push=True) as action_scope:
        await wallet.generate_signed_transaction(
            amounts=[uint64(1), uint64(2)],
            puzzle_hashes=[target_ph_1, target_ph_2],
            action_scope=action_scope,
        )
    [tx] = action_scope.side_effects.transactions

    await wallet_environments.process_pending_states(
        [
            WalletStateTransition(
                pre_block_balance_updates={1: {"set_remainder": True}},
                post_block_balance_updates={1: {"set_remainder": True}},
            )
        ]
    )

    created_coin_1 = next(coin for coin in tx.additions if coin.puzzle_hash == target_ph_1 and coin.amount == uint64(1))
    created_coin_2 = next(coin for coin in tx.additions if coin.puzzle_hash == target_ph_2 and coin.amount == uint64(2))
    coin_id_1 = created_coin_1.name()
    coin_id_2 = created_coin_2.name()

    async with wallet_node.wallet_state_manager.lock:
        remote_wallet = await RemoteWallet.create_new_remote_wallet(
            wallet_node.wallet_state_manager, wallet, name="Remote Wallet #1"
        )

    assert await wallet_node.wallet_state_manager.coin_store.get_coin_record(coin_id_1) is None
    assert await wallet_node.wallet_state_manager.coin_store.get_coin_record(coin_id_2) is None

    await env.rpc_client.register_remote_coins(
        RegisterRemoteCoins(wallet_id=remote_wallet.id(), coin_ids=[coin_id_1, coin_id_2])
    )

    await wallet_environments.process_pending_states(
        [
            WalletStateTransition(
                pre_block_balance_updates={
                    1: {"set_remainder": True},
                    int(remote_wallet.id()): {"init": True, "set_remainder": True},
                },
                post_block_balance_updates={
                    1: {"set_remainder": True},
                    int(remote_wallet.id()): {"set_remainder": True},
                },
            )
        ]
    )

    record_1 = await wallet_node.wallet_state_manager.coin_store.get_coin_record(coin_id_1)
    record_2 = await wallet_node.wallet_state_manager.coin_store.get_coin_record(coin_id_2)
    assert record_1 is not None
    assert record_2 is not None
    assert record_1.wallet_type == WalletType.REMOTE
    assert record_2.wallet_type == WalletType.REMOTE
    assert record_1.wallet_id == int(remote_wallet.id())
    assert record_2.wallet_id == int(remote_wallet.id())
```
