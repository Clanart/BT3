### Title
Unchecked `upb_Arena_Malloc()` return value leads to NULL-pointer write in Lua binding's `lupb_decode()` - (File: lua/msg.c)

### Summary
The kernel CVE-2024-56634 fixes a missing NULL check on `devm_kasprintf()`, whose return value is dereferenced without validation, causing a NULL pointer dereference when the allocation fails. The same invariant — "check the fallible allocator's return value before writing through the pointer" — is violated in the upb Lua binding's public decode entry point, where `upb_Arena_Malloc()`'s result is written into via `memcpy()` without a NULL check.

### Finding Description
`upb_Arena_Malloc()` is explicitly documented as a fallible operation that returns `NULL` on allocation failure: [1](#0-0) 
and its implementation does return `NULL` both when the debug allocation-failure-injection counter trips and when the underlying block allocator fails: [2](#0-1) [3](#0-2) 

The Lua binding's public `upb.decode(MessageClass, bin_string)` entry point, `lupb_decode()`, calls `upb_Arena_Malloc(arena, len)` to copy the attacker-supplied serialized bytes into arena memory, then immediately calls `memcpy()` on the result **without checking for `NULL`**: [4](#0-3) 

This is the same failure pattern as the kernel bug: a fallible allocation/formatting primitive (`devm_kasprintf()` in the kernel, `upb_Arena_Malloc()` here) whose contract explicitly allows a `NULL` return on failure, and a caller in the parsing path that dereferences (writes through, via `memcpy`) that value unconditionally. Other upb bindings and internal callers in this codebase consistently check the return value of `upb_Arena_Malloc()` before use (e.g. `upb/wire/internal/decoder.h:255-256`, `upb/message/message.c:81-92`, `upb/mini_descriptor/decode.c:559-560`), confirming that the missing check in `lupb_decode()` is an omission rather than an intentional invariant.

### Impact Explanation
If the arena allocation fails (e.g., the process is under memory pressure, or the custom/fixed-size arena allocator used by the embedding application cannot satisfy the request), `buf` is `NULL` and `memcpy(buf, pb, len)` performs a write through a NULL pointer. In most environments this is an immediate crash (denial of service) of the embedding Lua/upb process. Because the write is a `memcpy` of attacker/caller-influenced length starting at address 0, the practical impact is a crash rather than exploitable memory corruption (writes near address 0 are non-canonical/unmapped on essentially all supported platforms), matching the Medium severity of the analogous kernel CVE (which is also scored as an availability-only, `C:N/I:N/A:H` NULL-deref crash).

### Likelihood Explanation
The path is reached on every call to the public `upb.decode()` API, which is the standard way a Lua application parses untrusted binary protobuf input — this is a `MergeFrom`/`ParseFrom`-equivalent entry point, not test/benchmark/debug-only code. Reaching the NULL branch does require an arena allocation failure, which in normal (unbounded heap) deployments is a low-probability/OOM-dependent event; but for embedders who configure fixed-size/no-heap arenas via `upb_Arena_Init(mem, n, NULL)` (a documented and supported usage pattern in `docs/upb/design.md`), or under genuine system memory exhaustion, this is a reliably reachable NULL dereference precisely because `upb_Arena_Malloc()` is called directly without a size/capacity check and without verifying the result, exactly mirroring the low-effort, always-possible trigger condition of the kernel `devm_kasprintf()` bug.

### Recommendation
Check the return value of `upb_Arena_Malloc()` in `lupb_decode()` (and any other Lua binding entry points following the same pattern in `lua/msg.c`) before using it, and raise a Lua error (e.g., `luaL_error(L, "out of memory")`, consistent with existing error handling elsewhere in the file such as `lua/msg.c:868-870`) instead of proceeding to `memcpy()`.

Call `upb.decode(MessageClass, bin_string)` where `bin_string` is longer than the remaining arena capacity, so that `upb_Arena_Malloc(arena, len)` inside `lua/msg.c:946` returns `NULL` (per `upb/mem/internal/arena.h:90-116`, allocation past the block/pool capacity returns `NULL` rather than aborting).

UPB_NODISCARD UPB_API_INLINE void* _upb_Arena_Malloc_Unchecked(
    struct upb_Arena* a, size_t size) {
  UPB_PRIVATE(upb_Xsan_AccessReadWrite)(UPB_XSAN(a));

  size_t span = UPB_PRIVATE(_upb_Arena_AllocSpan)(size);

  if (UPB_UNLIKELY(UPB_PRIVATE(_upb_ArenaHas)(a) < span)) {
    void* UPB_PRIVATE(_upb_Arena_SlowMalloc)(struct upb_Arena * a, size_t span);
    return UPB_PRIVATE(_upb_Arena_SlowMalloc)(a, span);
  }

  // We have enough space to do a fast malloc.
  void* ret = a->UPB_ONLYBITS(ptr);
  a->UPB_ONLYBITS(ptr) += span;
  UPB_ASSERT(UPB_PRIVATE(_upb_Arena_IsAligned)(ret));
  UPB_ASSERT(UPB_PRIVATE(_upb_Arena_IsAligned)(a->UPB_ONLYBITS(ptr)));

  return UPB_PRIVATE(upb_Xsan_NewUnpoisonedRegion)(UPB_XSAN(a), ret, size);
}

void* UPB_PRIVATE(_upb_Arena_SlowMalloc)(upb_Arena* a, size_t span) {
  upb_ArenaInternal* ai = upb_Arena_Internal(a);
  if (!_upb_ArenaInternal_BlockAlloc(ai)) return NULL;

  if (!block) return NULL;

static int lupb_decode(lua_State* L) {
  size_t len;
  const upb_MessageDef* m = lupb_MessageDef_check(L, 1);
  const char* pb = lua_tolstring(L, 2, &len);
  const upb_MiniTable* layout = upb_MessageDef_MiniTable(m);
  upb_Message* msg = lupb_msg_pushnew(L, 1);
  upb_Arena* arena = lupb_Arenaget(L, -1);
  char* buf;

  /* Copy input data to arena, message will reference it. */
  buf = upb_Arena_Malloc(arena, len);
  memcpy(buf, pb, len);

  upb_DecodeStatus status = upb_Decode(buf, len, msg, layout, NULL,
                                       kUpb_DecodeOption_AliasString, arena);
