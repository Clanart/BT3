The chia-blockchain codebase has a structurally identical bug in NFT royalty computation, where integer division by a caller-controlled `royalty_split` (the number of royalty-bearing NFTs bundled into one offer) truncates small per-asset royalty shares to zero — letting an offer counterparty dodge paying royalties to NFT creators by bundling enough NFTs into a single trade.

### Title
NFT royalty payment truncates to zero via integer-division precision loss when bundling multiple royalty NFTs in one offer - ([File: chia/wallet/nft_wallet/nft_wallet.py])

### Summary
`compute_royalty_amount` computes each royalty-bearing NFT's share of a fungible payment using integer division: `abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS`. Because `royalty_split` is the count of royalty-enabled NFTs bundled together on one side of an offer (attacker-controlled by choosing how many NFTs to place in a single offer), and both this division and the earlier `//royalty_split` division truncate towards zero, an offer maker/taker can drive the per-NFT royalty amount to exactly zero even when the aggregate traded value is significant — completely bypassing the royalty payment owed to NFT creators, analogous to the reported `mintForToken` decimal-scaling truncation that silently zeroes out small values.

### Finding Description
`compute_royalty_amount` in `chia/wallet/nft_wallet/nft_wallet.py` performs the royalty calculation with plain integer arithmetic: [1](#0-0) 

This is invoked from `make_nft1_offer` while constructing royalty payments for a trade, where `request_side_royalty_split`/`offer_side_royalty_split` are simply the *count* of royalty-enabled NFTs bundled into the offer on each side: [2](#0-1) 

The same truncating pattern (`abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS`) is used in the summary/preview calculation `royalty_calculation`: [3](#0-2) 

Because `royalty_split` grows with the number of NFTs an offer participant chooses to bundle into a single trade, and division truncates toward zero at two points, the per-NFT royalty share can be forced to zero while the underlying fungible amount being exchanged is still non-trivial. The codebase's own test suite confirms this truncation-to-zero behavior is a real, reachable outcome of the arithmetic, not merely a theoretical edge case: [4](#0-3) 

### Impact Explanation
An offer counterparty (maker or taker — both are unprivileged, ordinary wallet users interacting through the standard offer flow) can structure a trade that bundles multiple royalty-enabled NFTs together against a fungible payment, choosing the split/amount combination so `compute_royalty_amount` returns zero for each NFT's royalty. The NFT creator(s) who are supposed to receive a percentage of every sale receive nothing, even though real value changed hands in the trade. This is a direct instance of offer-settlement value being redirected away from the intended royalty recipient — matching the "offer settlement theft" category, since the paid royalty is fully avoidable while the counterparties still receive/settle the full traded value between themselves.

### Likelihood Explanation
Reachable purely through the standard, unprivileged offer-creation path (`make_offer`/`take_offer` via `NFTWallet.make_nft1_offer`), with no special permissions needed — any wallet user constructing an offer bundling several NFTs controls the inputs (`royalty_split`, per-asset amount) that drive the truncation. Because the underlying royalty basis-point percentage set by creators is often small (e.g., 1-10%), and offers can bundle arbitrarily many NFTs, hitting the truncation-to-zero condition is easily achievable by choosing NFT count and payment amount accordingly.

### Recommendation
Track royalty remainder/loss across the batched division (e.g., accumulate the total intended royalty per asset first, then distribute per-NFT shares from that total, ensuring the sum of distributed shares never rounds below the mathematically owed total), or reject/adjust offers where the computed per-NFT royalty would round to zero despite a non-zero percentage and non-zero traded amount.

### Proof of Concept
Using the existing test as the reproduction: `compute_royalty_amount(offered_amount=-50, royalty_split=1, percentage=100)` (1% royalty on 50 mojos) returns `0` instead of a fractional-but-real royalty obligation: [4](#0-3) 
By bundling multiple such NFTs into one `make_nft1_offer` call (increasing `royalty_split`) against a correspondingly scaled fungible amount, an offer participant can reproduce this zero-royalty outcome at arbitrary trade sizes while still exchanging the full underlying asset value with the counterparty, bypassing royalty payments entirely.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
