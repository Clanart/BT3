### Title
Forwarded-output matching keyed only by `ExternalBalance` lets an attacker bind their deposit to someone else's pending `InInstruction` - (File: processor/src/multisigs/db.rs)

### Summary
When the processor forwards outputs during multisig rotation, it stores the associated `InInstructionWithBalance` in `ForwardedOutputDb` keyed solely by `ExternalBalance` (coin + amount), with no binding to the expected outpoint, address, or output identity. Later, **any** scanned output of `OutputType::Forwarded` whose amount matches retrieves and executes the stored instruction. This mirrors CVE-2025-58075's shape: an authorization token (here, the amount) is checked without verifying it belongs to the resource/context it was issued for, letting an attacker "join" an instruction that was created for a different output.

### Finding Description
`ForwardedOutputDb` is defined with key `(balance: ExternalBalance)` (`processor/src/multisigs/db.rs:76`). `save_forwarded_output` appends encoded `InInstructionWithBalance` under that key, and `take_forwarded_output` returns the first stored instruction for any caller presenting a matching balance (`processor/src/multisigs/db.rs:229-243`).

The consumer is `scanner_event_to_multisig_event` (`processor/src/multisigs/mod.rs:824-833`): for each scanned output of kind `Forwarded`, it calls `take_forwarded_output(txn, output.balance())` and, if present, pushes the returned instruction — treating the scanned output as the successful forwarding of a prior deposit and emitting the stored `InInstruction` for execution.

The only check is amount equality. Nothing verifies the scanned output is the forwarding transaction's output for that instruction (no outpoint, txid, or instruction-id binding). An external party who observes (or guesses) a pending forwarded balance can send a transaction paying the forwarded offset address of the retiring multisig (a publicly derivable address via `N::forward_address`) with the exact same amount. Their output is then classified `Forwarded`, pops the victim's stored instruction, and is processed under the attacker's output context — including `presumed_origin` being set from the attacker's own `tx.input[0]` (`processor/src/networks/bitcoin.rs:707-735`).

Note also `save_forwarded_output` uses `extend`, allowing multiple instructions under one balance, and `take_forwarded_output` pops them FIFO — so ordering can additionally be manipulated by an attacker front-running a same-amount forwarded output to reorder which instruction is consumed by which output.

### Impact Explanation
An attacker can cause the processor to attribute a forwarded output they created to a pending `InInstruction` that was intended for a different, legitimate forwarded deposit. Depending on the instruction type, this can attach an instruction (e.g., a refund or swap metadata) to funds the attacker controls or displace the legitimate output's instruction association, producing funds reported/processed under incorrect attribution — effectively letting the attacker's untrusted on-chain input stand in for a different user's authorized flow. Severity: Medium.

### Likelihood Explanation
Requires the attacker to learn or guess a pending forward amount (amounts are on-chain and often distinctive but not secret — mempool observation suffices) and send a matching-amount output to the forward address before the legitimate forward confirms. This is reachable purely with a Bitcoin transaction the attacker broadcasts — no validator status, collusion, or key material needed.

### Recommendation
Key `ForwardedOutputDb` by a value bound to the specific expected output — e.g., the expected outpoint/txid of the forwarding transaction, or the instruction's plan ID — rather than `ExternalBalance`. Alternatively, store the expected forward `OutPoint` inside the record and verify `output.outpoint()` (or the eventuality txid) matches before emitting the instruction. At minimum, match on both balance and the forwarding transaction's ID recorded via the `EventualitiesTracker` path.

### Proof of Concept
1. Processor emits a forwarding TX moving output X (amount A) and calls `save_forwarded_output(txn, instruction)` where `instruction.balance.amount == A`.
2. Attacker observes A in the mempool, derives `forward_address(retiring_key)` via `Secp256k1::hash_to_F(KEY_DST, b"forward")` + `p2tr_script_buf`, and broadcasts a TX paying exactly A to that address, confirmed first.
3. `get_outputs` scans the attacker's TX: `kinds[offset]` → `OutputType::Forwarded` (`processor/src/networks/bitcoin.rs:692-699`).
4. `scanner_event_to_multisig_event` calls `take_forwarded_output(txn, { Bitcoin, A })`, which returns the victim's stored `InInstructionWithBalance` (`processor/src/multisigs/mod.rs:829`).
5. The victim's instruction is emitted bound to the attacker's output; the legitimate forwarded output, when scanned, finds the DB entry consumed.

Caveat: exact downstream effect depends on the `InInstruction` variant processed (not fully traceable within scope here), but the missing binding of stored instruction to expected output is concretely present in `ForwardedOutputDb`'s amount-only keying and its unconditional consumption at `processor/src/multisigs/mod.rs:829`.
