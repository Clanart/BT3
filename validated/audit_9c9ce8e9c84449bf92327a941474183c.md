Audit Report

## Title
Rejected: unpatched claim mischaracterizes the ancestor-hashes repair transport as unauthenticated - (File: `core/src/repair/duplicate_repair_status.rs`)

## Summary
The claim asserts that `AncestorRequestStatus::add_response` de-duplicates and counts agreement purely by an unauthenticated, spoofable `SocketAddr`, allowing an attacker to fabricate `MINIMUM_ANCESTOR_AGREEMENT_SIZE` distinct "votes" via UDP source-address spoofing. Investigation of the surrounding repair transport shows that `sampled_validators` are drawn from cluster contact info by pubkey via `repair_request_ancestor_hashes_sample_peers` and that ancestor-hashes *requests* are signed and bound to a specific responder, and outstanding requests are tracked via a per-request `nonce` registered in `OutstandingAncestorHashesRepairs`, which the claim itself acknowledges it could not fully trace before concluding the vulnerability exists.

## Finding Description
`add_response` in `core/src/repair/duplicate_repair_status.rs` keys responses by `from_addr: &SocketAddr` and checks membership against `self.sampled_validators`, a `HashMap<SocketAddr, bool>` populated from `sampled_validators.into_iter().map(|(_pk, socket_addr)| socket_addr)` in `AncestorHashesService::initiate_ancestor_hashes_requests_for_duplicate_slot`, which itself is derived from `serve_repair.repair_request_ancestor_hashes_sample_peers`, a weighted (stake-based) selection of *actual pubkeys and their registered gossip contact-info repair sockets*. [1](#0-0) [2](#0-1) [3](#0-2) 

The requests themselves are cryptographically signed: `RepairProtocol::AncestorHashes { header, .. }` is signed via `repair_proto_to_bytes`/`ancestor_repair_request_bytes` and the header binds `sender`, `recipient`, `timestamp`, and `nonce`, verified on the receiving (server) side by `verify_signed_packet`, which checks recipient match, time skew, and `header.signature.verify(from_id.as_ref(), &signed_data)`. [4](#0-3) [5](#0-4) 

Critically, the responder is selected from and constrained by the outgoing signed request — each request is addressed to a specific `pubkey`/`socket_addr` pair drawn from `sampled_validators`, and a distinct `nonce` is registered via `outstanding_requests.write().unwrap().add_request(...)` per destination before the packet is sent. [6](#0-5)  On the response side, `verify_and_process_ancestor_response` requires the nonce to match an outstanding, unexpired request via `register_response`, and the claim's author explicitly states they were unable to trace `OutstandingAncestorHashesRepairs::register_response` to confirm whether nonce validation and prior binding closes the gap, flagging this as an open uncertainty rather than a confirmed vulnerability.

This self-acknowledged gap is decisive: the claim depends entirely on demonstrating that (a) an attacker can learn the specific per-destination `nonce` values used for each of the `sampled_validators` entries (which are generated per-request and tracked server-side in `OutstandingAncestorHashesRepairs`, not public), and (b) that spoofing a UDP source address to match one of the sampled validators' registered gossip contact-info address, without also matching the corresponding secret nonce, is sufficient to have `register_response` accept the forged reply. The claim provides no evidence that nonce guessing/leakage is feasible, and does not establish that `from_addr`-based de-duplication in `add_response` is reached at all without first passing nonce validation in the response handler. Without demonstrating that the nonce (effectively an unpredictable per-response authentication token bound to the specific request/destination) can be bypassed or predicted by an unprivileged network attacker, the "spoofable, unauthenticated" characterization is unsupported speculation, not a demonstrated exploit path.

## Impact Explanation
No impact is established. The claim does not demonstrate that the nonce-based binding between `sampled_validators` destination and response acceptance can be defeated by pure UDP source-address spoofing; the nonce itself is the missing authentication piece the report doesn't verify, by its own admission.

## Likelihood Explanation
The report explicitly flags this as unresolved ("I was not able to fully trace the outstanding-request/nonce validation code ... to close out this uncertainty"), which means the claim itself has not established a reachable, unprivileged exploit path — a core requirement. Absent that verification, the described attack (spoof N distinct source addresses matching sampled validators with a valid outstanding nonce for each) requires the attacker to first learn or predict per-destination nonces, which is not shown to be feasible.

## Recommendation
Not applicable — claim rejected for insufficient evidence of exploitability; the nonce-based binding in `OutstandingAncestorHashesRepairs::register_response` needs to be reviewed by the claim's author before resubmission, along with concrete evidence that the nonce can be predicted, leaked, or bypassed by an unprivileged attacker.

## Proof of Concept
None provided that overcomes the nonce requirement; the claim's own PoC section defers verification of the exact mitigating mechanism (nonce/outstanding-request binding) to a follow-up investigation, which is disqualifying for a claim asserting a concrete, reachable vulnerability.

    pub(crate) fn repair_request_ancestor_hashes_sample_peers(
        &self,
        slot: Slot,
        cluster_slots: &ClusterSlots,
        repair_validators: &Option<HashSet<Pubkey>>,
        repair_protocol: Protocol,
        my_pubkey: &Pubkey,
    ) -> Result<Vec<(Pubkey, SocketAddr)>> {
        let repair_peers: Vec<_> = self.repair_peers(repair_validators, slot, my_pubkey);
        if repair_peers.is_empty() {
            return Err(ClusterInfoError::NoPeers.into());
        }
        let (weights, index) = cluster_slots.compute_weights_exclude_nonfrozen(slot, &repair_peers);
        let peers = WeightedShuffle::new("repair_request_ancestor_hashes", weights)
            .shuffle(&mut rand::rng())
            .map(|i| index[i])
            .filter_map(|i| {
                let addr = repair_peers[i].serve_repair(repair_protocol)?;
                Some((*repair_peers[i].pubkey(), addr))
            })
            .take(get_ancestor_hash_repair_sample_size())
            .collect();
        Ok(peers)
    }

    pub fn repair_proto_to_bytes(request: &RepairProtocol, keypair: &Keypair) -> Result<Vec<u8>> {
        debug_assert!(request.supports_signature());
        let mut payload = serialize(&request)?;
        let signable_data = [&payload[..4], &payload[4 + SIGNATURE_BYTES..]].concat();
        let signature = keypair.sign_message(&signable_data[..]);
        payload[4..4 + SIGNATURE_BYTES].copy_from_slice(signature.as_ref());
        Ok(payload)
