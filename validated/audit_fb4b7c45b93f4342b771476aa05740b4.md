### Title
Identical binding factor reused across all nonces instead of a per-nonce factor, enabling nonce-cancellation / rogue attacks in multi-nonce FROST algorithms - (File: crypto/frost/src/nonce.rs)

### Summary
The Plaza bug is a single hardcoded token used where a per-pool (dynamic) value was required, silently breaking accounting for every non-default context. The Serai analog lives in `BindingFactor::calculate_binding_factors` in `crypto/frost/src/nonce.rs`. FROST in Serai supports algorithms requesting multiple nonces (the spec explicitly requires a "per-nonce per-participant binding factor", spec/cryptography/FROST.md L31-33). The code claims to "generate a binding factor per nonce just to ensure it never comes up as a question" (nonce.rs L165-166), but the implementation maps each nonce index to `C::hash_binding_factor(transcript.challenge(b"rho"))` on the *same, un-advanced* cloned transcript. `challenge` is a deterministic read over the cloned transcript state — nothing is appended between iterations — so every entry of `binding.binding_factors` is the identical scalar. Wherever the algorithm needs `k > 1` nonces, the intended per-nonce binding degenerates to a single shared factor, exactly the "one fixed value silently applied to all instances" shape of the Plaza bug.

### Finding Description
In `crypto/frost/src/nonce.rs` L161-173:

```rust
binding.binding_factors = Some(
  (0 .. binding.commitments.nonces.len())
    .map(|_| C::hash_binding_factor(transcript.challenge(b"rho").as_ref()))
    .collect(),
);
```

The closure ignores the nonce index and re-challenges the same `transcript.clone()` state. `MerlinTranscript::challenge` (and equivalent transcript impls) produce output deterministically from the current state without mutating it, so `binding_factors == [rho, rho, ..., rho]` for any number of nonces.

These factors drive the aggregate nonce computation `B.nonces()` (nonce.rs L194-212), where each participant's `E` commitment is multiplied by `binding_factors[n]` and summed via `multiexp_vartime`, and the signer's own nonce combination `*actual *= our_binding_factors[n]; *actual += base` (sign.rs L390-394). With `k` nonces sharing one `rho`, the aggregate `R_n = D_n + rho * E_n` for every `n` uses the same coefficient.

### Impact Explanation
Distinct binding factors per nonce are what prevent an adversarial signer from choosing their `E` commitments to make the aggregate nonces collide across different positions/sessions (the same class of cancellation that MuSig2's per-nonce coefficients `a_j` exist to block, and that FROST's rho exists to block across participants). With `rho_n = rho` for all `n`, a malicious signer can set `E_0 = -E_1` (or arbitrary linear combinations) so that their bound contribution to `R_0` and `R_1` is `rho*(E_0 + E_1) = 0`-controlled across nonces, reducing a `k`-nonce algorithm's effective nonce freedom to `k-1` dimensions. For algorithms using multiple nonces to embed multiple Schnorr statements in one signature (the documented purpose of the multi-nonce extension), this enables ROS-style / Wagner-style grinding: an unprivileged signer who submits untrusted `Preprocess` bytes via `read_preprocess` can bias or unify the effective challenges across the embedded statements, yielding signatures over unintended effective nonce relations — i.e., concrete signing under a malformed verifier formula. For single-nonce algorithms (Schnorrkel, plain Schnorr) the code path is unreachable, which limits but does not eliminate the issue since the framework explicitly advertises multi-nonce support.

### Likelihood Explanation
Any peer signer in a threshold session controls their own preprocess bytes (`read_preprocess` on attacker input is an accepted input surface), so choosing degenerate `E` vectors requires no privileges. Exploitation requires an `Algorithm` implementation that actually requests `nonces().len() >= 2`; I was unable to fully enumerate every algorithm's `nonces()` in the remaining budget — `Schnorr`/`Schnorrkel` use a single nonce (`schnorr.nonces()` delegation in schnorrkel/src/lib.rs L86-88), so the concrete blast radius depends on which multi-nonce algorithms are deployed. The flaw is deterministic in the code (identical factors on every multi-nonce call), so likelihood of the *bug* is certain; likelihood of *exploitability* is conditional on a multi-nonce algorithm being in scope.

### Recommendation
Bind the nonce index into each challenge so the factors are genuinely distinct, e.g.:

```rust
.map(|n| {
  let mut t = transcript.clone();
  t.append_message(b"nonce", C::F::from(n as u64).to_repr());
  C::hash_binding_factor(t.challenge(b"rho").as_ref())
})
```

or append `n` to the cloned transcript before each `challenge(b"rho")` call. This restores the per-nonce per-participant binding required by the spec and prevents cross-nonce cancellation of `E` commitments.

### Proof of Concept
Sketch (library-level, no harness executed):

```rust
// Inside a FROST sign session for an algorithm with nonces().len() == 2.
// After B.calculate_binding_factors(&rho_transcript) in crypto/frost/src/sign.rs:371,
// for every participant l:
let bf = B.binding_factors(l);
assert_eq!(bf[0], bf[1]); // holds unconditionally: same cloned transcript, same challenge
```

Because `transcript.clone()` at nonce.rs L163 is never advanced between map iterations and `challenge` is a pure read, `hash_binding_factor` receives identical input for all `n`, so `binding_factors` is `[rho, rho]`. A malicious participant then submits `Preprocess` commitments with `E_1 = -E_0`; their `bound(l)` contribution `D + rho*E` (nonce.rs L186-188) yields `E`-terms that cancel identically across both nonces, collapsing two independent bound nonces into one — the precondition for ROS/Wagner forgery against multi-nonce signature algorithms.
