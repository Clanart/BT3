### Title
Vault `redeem()` Allows Self-Address as Recipient, Corrupting the `assets` Accounting Used for Interest Rate and zToken Pricing - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
The `redeem` function in the vault contracts (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) accepts an arbitrary `recipient` principal for the withdrawn underlying, with no check preventing `recipient` from being the vault contract itself. Unlike `transfer`, which explicitly guards against sending to `current-contract` [1](#0-0) , `redeem` unconditionally decrements the internal `assets` state variable by `inkind` after sending the underlying to `recipient` [2](#0-1) . If `recipient` equals the vault's own address, the underlying token never actually leaves the vault's real balance, yet `assets` is decremented as though it did — an exact structural analog of the reported `StakingPool` bug where `to == address(this)` breaks the assumption that the tracked liquidity state moves in the direction the code assumes.

### Finding Description
`redeem` computes `inkind` (the underlying amount to pay out), burns the caller's zTokens, calls `(send-underlying inkind recipient)`, and then does `(var-set assets (- current-assets inkind))` unconditionally [3](#0-2) . This logic assumes `inkind` underlying units leave the vault. If `recipient` is the vault's own contract principal, `send-underlying` transfers the tokens to the vault itself — the vault's *actual* underlying token balance is unchanged, but the internal `assets` accounting variable is reduced exactly as if the funds had left.

This corrupts every downstream computation that depends on `assets`:
- `get-available-assets` (`assets - total-borrowed`) becomes artificially low, inflating `utilization` [4](#0-3) .
- `utilization` feeds `interest-rate` and `next-liquidity-index` (`lindex`) via `calc-liquidity-rate` and `calc-index-next` [5](#0-4) .
- `lindex` is the exact value used by `protocol-data.clar`'s `get-asset-price` to price all zTokens (zSTX, zsBTC, zstSTX, zUSDC, zUSDH, zstSTXbtc) that serve as collateral in health/liquidation checks: `(mul-div-down stx-price lindex INDEX-PRECISION)` [6](#0-5) .
- `total-assets-preview`/`convert-to-shares-preview`/`convert-to-assets-preview` (share price) also key off `assets`.

Thus a self-directed `redeem` call desynchronizes the vault's tracked liquidity from its real balance, and that corrupted state directly feeds the liquidity index used to price zTokens for collateral valuation in the market contract's health checks — matching the "value ends up wrong ... via a price attached to the wrong asset / a monotonic index feeding valuation" analog class.

### Impact Explanation
By repeatedly calling `redeem(amount, min-out, recipient=<vault-address>)`, an attacker can artificially depress the vault's tracked `assets` without any real outflow. Because `assets` participates in `utilization`, `interest-rate`, and `lindex` calculation, this can:
- Distort the zToken liquidity index (`lindex`) used to price zSTX/zsBTC/etc. collateral in `get-asset-price`, causing collateral to be over- or under-valued in health checks — a wrong health verdict that can let an under-collateralized position pass as healthy, or let an attacker's zToken collateral be overvalued to borrow more than warranted.
- Corrupt share pricing (`convert-to-shares-preview`/`convert-to-assets-preview`), letting the attacker mint/redeem shares at incorrect ratios relative to real vault reserves.

This lands in the **Critical** impact bucket (protocol insolvency / theft of user funds at rest), since collateral mispricing driven by a corrupted liquidity index can enable extraction of more underlying than backing exists, or block legitimate liquidations of unsafe positions.

### Likelihood Explanation
The `recipient` parameter of `redeem` is fully attacker-controlled and requires no special privilege — any zToken holder can call `redeem` with `recipient` set to the vault's own principal. The only barrier is that this is likely an edge case not exercised in normal operation, and it requires the attacker to hold zToken balance to redeem in the first place (readily obtainable via `deposit`). No DAO/oracle compromise is needed.

### Recommendation
Add an explicit precondition to `redeem` (and any other function that pays out `recipient`-controlled underlying, e.g. `system-borrow`) rejecting `recipient == current-contract`, consistent with the guard already present in `transfer`:
```clarity
(asserts! (not (is-eq current-contract recipient)) ERR-TOKENIZED-VAULT-PRECONDITIONS)
```
Apply this check to `redeem` in all six vault contracts (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`).

### Proof of Concept
1. Attacker deposits `amount` underlying into `v0-vault-stx.clar` via `deposit`, receiving zSTX shares.
2. Attacker calls `redeem(amount, min-out, recipient=<vault-stx-contract-address>)`.
3. `send-underlying` transfers `inkind` underlying to the vault's own address — the vault's real token balance is unchanged.
4. `(var-set assets (- current-assets inkind))` reduces the tracked `assets` variable, understating real reserves [2](#0-1) .
5. Subsequent calls to `accrue`/`get-asset-price` compute `utilization`, `interest-rate`, and `lindex` off the corrupted (understated) `assets`, propagating the wrong liquidity index into zToken collateral pricing used by the market's health checks.

Note: I was unable to fully inspect `send-underlying`'s implementation (its definition body) before the tool budget was exhausted, so the exact low-level transfer mechanics (e.g., whether Clarity's `ft-transfer?`/`stx-transfer?` primitives silently succeed with zero net effect when sender==recipient) are inferred rather than directly confirmed. This should be verified directly in the source before treating this as fully proven.
