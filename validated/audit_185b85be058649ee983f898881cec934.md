### Title
Unauthenticated `setup` call reachable when `client_verification=false` allows any TCP client to force verifier/operator key re-collection mid-round - ([File: core/src/servers.rs])

### Summary
`create_aggregator_grpc_server` reads `config.client_verification` and, when `false`, only logs `tracing::warn!` before proceeding to build the TLS/interceptor stack via `create_grpc_server`, which then configures `ServerTlsConfig` without `client_ca_root` and wraps the service in `InterceptedService::new(service, Noop)` instead of `OnlyAggregatorAndSelf`. Since `Interceptors::Noop::call` unconditionally returns `Ok(req)`, any TCP peer that completes a plain (server-authenticated only) TLS handshake — requiring no client certificate — can call any RPC on `ClementineAggregatorServer`, including `setup`.

### Finding Description
The binding the system is supposed to enforce is: `caller_identity_reaching(ClementineAggregator::setup) == aggregator's own operator client cert` (per docs/usage.md's CALLER_AUTHORITY model, enforced in code by `Interceptors::OnlyAggregatorAndSelf`/`only_aggregator_and_self` matching `leaf_cert == our_cert`). 

The code path: `create_aggregator_grpc_server` (`core/src/servers.rs:293-317`) checks `config.client_verification` only to emit a warning at line 306-308, and unconditionally calls `create_grpc_server` at line 310. Inside `create_grpc_server` (`core/src/servers.rs:106-138`), when `config.client_verification` is `false`:
- `tls_config` is built as `ServerTlsConfig::new().identity(server_identity)` with no `client_ca_root`, so the TLS server does not request/require a client certificate — any TCP client that trusts (or ignores) the server cert can connect via plain TLS.
- The interceptor selection picks `Noop` instead of `OnlyAggregatorAndSelf`.

`Interceptors::Noop::call` (`core/src/rpc/interceptors.rs:30`) returns `Ok(req)` unconditionally, bypassing `only_aggregator_and_self`'s cert-identity check entirely (`core/src/rpc/interceptors.rs:36-77`). Consequently, an attacker with a bare `tonic::transport::Channel` and no client certificate can invoke `ClementineAggregator::setup` (Empty) exposed by `AggregatorServer` on the public gRPC port, since no gRPC-level authorization exists beyond the interceptor. This lets the attacker trigger `AggregatorServer::aggregator.setup()`'s key re-collection/redistribution logic at will, at any time — including mid-round, concurrently with an in-flight `new_deposit`/`DepositFinalize` flow being coordinated for an honest operator — with no authentication barrier at all.

### Impact Explanation
If `setup` mutates in-memory verifier/operator key state (used to construct MuSig2 sessions, sighash streams, nonce/partial-sig aggregation for `new_deposit`) while another deposit round is concurrently negotiating nonces/partial signatures for the presigned move-to-vault or round transactions, the concurrent round can be corrupted (stale/rotated key material), causing the deposit's presigned transaction to never finalize (`DepositFinalize` never reached). This can permanently strand an honest operator's round UTXO chain, matching the Critical category "an honest operator permanently unable to be reimbursed." This is repeatable across any deposit round and any operator, since the trigger requires nothing but network access to the aggregator's TCP port when misconfigured.

### Likelihood Explanation
This vulnerability is entirely gated on the deployment configuration flag `config.client_verification == false`. This is not the code's implicit/default enforced behavior — `create_grpc_server` treats `client_verification` as an operator-controlled TOML/env setting (`core/src/config/mod.rs`, `core/src/config/env.rs`), and the aggregator path explicitly warns (rather than errors or refuses to start) when it is disabled. If an operator deploys the aggregator with `client_verification = false` (e.g., misconfiguration, or for local/dev convenience carried into production), the attack requires no BTC cost, no key material, and no privileged access — only network reachability to the gRPC port — and is trivially repeatable.

### Recommendation
Do not allow `client_verification = false` to silently disable authorization for the aggregator's cross-entity trust model. At minimum: (1) always wrap the aggregator service in `OnlyAggregatorAndSelf`/mTLS enforcement regardless of `client_verification`, since the aggregator process is the most security-critical entry point (per docs/usage.md's CALLER_AUTHORITY), or (2) fail closed — refuse to start the aggregator gRPC server (return an error, not just `tracing::warn!`) when `client_verification` is `false`, rather than silently degrading to `Noop`.

### Proof of Concept
1. In a non-test harness (or `core/src/test`, acknowledging tests are out-of-scope for the audit but useful for local reproduction), start `create_aggregator_grpc_server` with a `BridgeConfig` where `client_verification = false`.
2. Connect using a bare `tonic::transport::Channel::from_shared(...).connect().await` with TLS configured only to trust the server cert (no client identity/cert set).
3. Call `ClementineAggregator::setup(Empty {})` via this unauthenticated channel and confirm it succeeds (`Ok(Response<...>)`), asserting `left = caller had no cert / not `our_cert`` vs `right = docs' CALLER_AUTHORITY requiring caller == our_cert` — showing the binding is broken.
4. Concurrently, drive a `new_deposit` round for an honest operator on a separate task; assert the deposit round's `DepositFinalize` stream/response never completes/returns after step 3's `setup` call runs mid-round, demonstrating the honest operator's round UTXO chain is stranded. pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}
