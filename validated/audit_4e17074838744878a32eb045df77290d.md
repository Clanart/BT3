## Analysis: CPU-exhaustion analog in `Offer._get_offered_coins()`

The GraphQL-java bug class is "no cost/complexity limit enforced during evaluation, causing unbounded CPU use from a single untrusted request." The chia-blockchain codebase generally defends against this class for CLVM execution via strict cost metering (`MAX_BLOCK_COST_CLVM`, `max_tx_clvm_cost`, atom/pair bounds) as documented in `.cursor/context/clvm-execution.md` and enforced everywhere spend bundles/generators are run (mempool admission, block validation, `compute_additions_with_cost`, `compute_spend_hints_and_additions`). However, one offer-processing code path evaluates untrusted CLVM with an effectively unbounded budget.

### Title
CPU-exhaustion Denial of Service via malicious Offer puzzle evaluated with unbounded CLVM cost - (File: chia/wallet/trading/offer.py)

### Summary
`Offer._get_offered_coins()` initializes `cost_left = INFINITE_COST` and runs each coin spend's inner puzzle with `inner_puzzle.run_with_cost(cost_left, inner_solution)` [1](#0-0) , checking `assert cost_left >= puzzle_cost` only *after* execution completes. Because the cost ceiling passed into the CLVM interpreter is effectively infinite, a malicious offer file containing an expensive-but-terminating CLVM program (the same string-doubling/exponential-blowup pattern already used in this repo's own malicious-generator test fixtures, e.g. `SINGLE_ARG_INT_LADDER_COND`/`large_string` doubling via `concat`) will run to completion consuming excessive CPU/memory before any cost accounting kicks in.

### Finding Description
`_get_offered_coins()` is invoked (via `get_offered_coins()`) from multiple offer-inspection code paths that a wallet user or RPC caller triggers on an **untrusted, attacker-supplied offer** before it is ever submitted to the mempool or validated on-chain: `Offer.get_offered_amounts()`, `Offer.arbitrage()`, `Offer.get_pending_amounts()`, and `Offer.summary()` [2](#0-1) . `Offer.summary()` is in turn called directly by the `get_offer_summary` wallet RPC endpoint [3](#0-2)  and is part of the standard offer-viewing/take-offer UX (CLI `get_offer_summary`, `check_offer_validity`, `take_offer`).

Unlike the sibling method `Offer.conditions()`, which correctly bounds cumulative CLVM execution with `max_cost = int(DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM)` and decrements/validates that budget before continuing [4](#0-3) , `_get_offered_coins()` passes `INFINITE_COST` as the `max_cost` argument to `run_with_cost`, meaning the underlying Rust CLVM interpreter (`run_chia_program`) is not given any real ceiling — the `assert cost_left >= puzzle_cost` check only fires *after* the (potentially extremely expensive) execution has already finished, so it provides no protection against an unbounded-cost puzzle.

This mirrors the codebase's own documented "malicious generator" attack class (see `chia/_tests/core/mempool/test_mempool.py:2620-2707`, comments describing puzzles that repeatedly `concat` a string with itself to build exponentially large values while paying deliberately low declared cost) [5](#0-4) . Those tests exist specifically because mempool/block validation enforces `max_cost`; `_get_offered_coins()` is a parallel evaluation path over the exact same untrusted puzzle/solution data (`cs.puzzle_reveal`, `cs.solution`) that omits the cap.

### Impact Explanation
A malicious offer file crafted with one coin spend whose puzzle reveal recognized by `match_puzzle` (e.g. mimicking a CAT/NFT/other outer puzzle so `get_inner_puzzle`/`get_inner_solution` succeed) delegates to an inner puzzle that performs exponential work (e.g., repeated `concat`/`substr` doubling as in the existing test fixtures) will consume large amounts of CPU/memory the moment any user or automated service (wallet, DL wallet's `verify_offer`, GUI, CLI `get_offer_summary`) inspects the offer — well before signature verification, mempool submission, or consensus-level cost checks are ever reached. This can hang or crash the node process (memory exhaustion from unbounded intermediate atoms) handling the offer, denying service to that wallet/RPC client. Any code path that automatically parses/pre-screens incoming offers (e.g. a market/aggregator service, or `DataLayerWallet`/`DataLayer.take_offer`/`verify_offer` flow which also calls into `get_offer_summary`-equivalent logic) is exposed to unauthenticated CPU exhaustion.

### Likelihood Explanation
High reachability: creating and sharing an offer file is a normal, low-privilege user action; no special permissions, signature validity, or on-chain state are required to construct a self-consistent but maliciously expensive puzzle/solution pair, since only `Offer.from_bytes`/`from_bech32` parsing plus `match_puzzle` recognition need to succeed for `_get_offered_coins()` to run the inner puzzle. Any workflow that calls `.summary()`, `.arbitrage()`, `.get_pending_amounts()`, or the `get_offer_summary`/`check_offer_validity`/`take_offer` RPCs on an attacker-supplied offer triggers this path automatically.

### Recommendation
Bound `cost_left` in `_get_offered_coins()` to a finite constant (e.g. `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM`, matching `Offer.conditions()`) and check the remaining budget *before* invoking `run_with_cost` for each subsequent coin spend, raising a `ValidationError`/`Err.BLOCK_COST_EXCEEDS_MAX` immediately once exceeded rather than asserting after the fact. Consider applying the same audit to any other offer/wallet code path that calls `run_with_cost`/`Program.run` with `INFINITE_COST` on data sourced from an untrusted offer or peer-supplied spend bundle.

### Proof of Concept
1. Construct (using the existing test helper patterns in `chia/_tests/core/mempool/test_mempool.py`, e.g. `SINGLE_ARG_INT_LADDER_COND`/`large_string`) a CLVM inner puzzle that repeatedly `concat`s a value with itself N times (e.g. N≈30-40) to blow up execution time/memory, wrapped so `match_puzzle`/`get_inner_puzzle`/`get_inner_solution` treat it as a recognized outer-puzzle's inner puzzle (or fall through to the "bare XCH" branch, which still requires `run_with_cost` on the puzzle for cost accounting only if bare-XCH path is used — recognized outer puzzles exercise the vulnerable branch directly).
2. Package this puzzle reveal/solution as one `CoinSpend` inside an `Offer` object and serialize with `bytes(offer)`/`to_bech32()`.
3. Call `wallet_rpc_client.get_offer_summary(GetOfferSummary(offer=malicious_offer_bech32))` (or simply call `Offer.summary()`/`get_offered_coins()` locally) and observe CPU/memory usage spike disproportionately to the offer's small on-wire size, with no `ValidationError` or cost-limit rejection produced beforehand.     def get_offered_amounts(self) -> dict[bytes32 | None, int]:
        offered_coins: dict[bytes32 | None, list[Coin]] = self.get_offered_coins()
        offered_amounts: dict[bytes32 | None, int] = {}
        for asset_id, coins in offered_coins.items():
            offered_amounts[asset_id] = uint64(sum(c.amount for c in coins))
        return offered_amounts

    def get_requested_payments(self) -> dict[bytes32 | None, list[NotarizedPayment]]:
        return self.requested_payments

    def get_requested_amounts(self) -> dict[bytes32 | None, int]:
        requested_amounts: dict[bytes32 | None, int] = {}
        for asset_id, coins in self.get_requested_payments().items():
            requested_amounts[asset_id] = uint64(sum(c.amount for c in coins))
        return requested_amounts

    def arbitrage(self) -> dict[bytes32 | None, int]:
        """
        Returns a dictionary of the type of each asset and amount that is involved in the trade
        With the amount being how much their offered amount within the offer
        exceeds/falls short of their requested amount.
        """
        offered_amounts: dict[bytes32 | None, int] = self.get_offered_amounts()
        requested_amounts: dict[bytes32 | None, int] = self.get_requested_amounts()

        arbitrage_dict: dict[bytes32 | None, int] = {}
        for asset_id in [*requested_amounts.keys(), *offered_amounts.keys()]:
            arbitrage_dict[asset_id] = offered_amounts.get(asset_id, 0) - requested_amounts.get(asset_id, 0)

        return arbitrage_dict
