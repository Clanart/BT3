### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-shop data/action confusion - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` authenticates only the request body (`request.raw_post`) with an app-wide shared secret. The `shop_domain` it exposes is read straight from the unsigned `X-Shopify-Shop-Domain` header and is not bound into the HMAC computation, so a valid `(body, hmac)` pair from one shop can be replayed with an attacker-chosen shop-domain header and still pass verification. This mirrors the `Project.sol#updateProjectHash` finding: the signed payload doesn't reference the entity ("project"/"shop") it's supposed to be scoped to, so a valid signature can be reused in a different context.

### Finding Description
`PayloadVerification#hmac_valid?` computes/validates the HMAC using only `data` (the raw POST body) and the shared app secret — never the request headers: [1](#0-0) 

`WebhookVerification` reuses this same body-only check for `verify_request`, and separately derives `shop_domain` directly from the `X-Shopify-Shop-Domain` header, which is completely outside the signed data: [2](#0-1) 

Because the secret used is the single app-wide `ShopifyApp.configuration.secret` (not a per-shop secret) and the HMAC only covers the body, any two requests with the same body will have the same valid HMAC value, independent of which shop the header claims to be from. The generated job templates that consume `shop_domain` from this concern's pattern treat it as a trusted shop identifier and perform sensitive, shop-scoped actions keyed on it — e.g. deleting the shop record: [3](#0-2) 

or performing mandatory-privacy redaction/data-request flows: [4](#0-3) [5](#0-4) 

The documented "roll your own webhook controller" pattern explicitly instructs developers to trust this unauthenticated `shop_domain` accessor when enqueuing jobs: [6](#0-5) 

### Impact Explanation
An attacker who can obtain one legitimately-signed `(body, HMAC)` pair (e.g. by installing the app on their own shop and triggering an event that causes a webhook to be delivered, or by any other means of observing a valid body+signature combination) can replay that exact body and signature to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value. Since `hmac_valid?` never inspects the header, the forged request passes verification, and any consumer relying on the `WebhookVerification#shop_domain` convention (as instructed in the gem's own docs, and mirrored by the generator-produced job templates for `shop/redact`, `customers/redact`, and app-uninstall handling) will act on behalf of the spoofed shop. Depending on the app's job implementation, this enables cross-shop data corruption, unauthorized redaction/deletion of another merchant's `Shop` record, or forged uninstall/redact processing for a victim shop — a cross-shop confused-deputy condition analogous to the `updateProjectHash` issue where the signed payload lacked a binding to the entity it targets.

### Likelihood Explanation
Moderate-to-high. The webhook endpoint is a public, unauthenticated-by-design HTTP endpoint (webhooks arrive without prior session), so nothing but the HMAC check stands between an attacker and it. Obtaining one valid signed body is straightforward for anyone who can install the app on a store they control (or any dev/test shop), since Shopify will deliver a genuinely signed webhook to the app for ordinary events. Reusing that exact body+signature against the same endpoint with a different `X-Shopify-Shop-Domain` header requires no cryptographic breakage — only header manipulation, since the secret and HMAC computation are shop-independent by design of `PayloadVerification`.

### Recommendation
- Do not treat `X-Shopify-Shop-Domain` as an authenticated value on its own; instead, prefer deriving the shop identity from data that is actually inside the HMAC-signed body (most Shopify webhook payloads carry `shop_id`/domain-equivalent fields in the JSON body itself), or cross-check the header value against a shop identifier embedded in the signed payload before use.
- Where feasible, verify webhooks using per-shop context (e.g., confirm the resolved shop record's own webhook subscription/state) rather than trusting the header alone for destructive/administrative operations (uninstall, redact).
- Update `docs/shopify_app/webhooks.md`'s custom-controller example and generator templates to avoid conflating the unauthenticated header value with a verified identity, or explicitly document the trust boundary so app authors add their own binding checks.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers (or otherwise legitimately receives) a mandatory `shop/redact` (or any subscribed) webhook, capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify computed for `B` using the app's shared secret.
2. Attacker sends their own POST directly to the app's webhook endpoint:
   ```
   POST /webhooks/shop_redact HTTP/1.1
   X-Shopify-Hmac-Sha256: H
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   X-Shopify-Topic: shop/redact
   Content-Type: application/json

   B
   ```
3. `PayloadVerification#hmac_valid?(request.raw_post)` recomputes HMAC over `B` with the shared secret and finds it matches `H` — verification passes — because the header `X-Shopify-Shop-Domain` was never part of the signed material. [1](#0-0) 
4. The controller/job enqueues processing with `shop_domain: "victim-shop.myshopify.com"` (read via `WebhookVerification#shop_domain`), and generated job logic such as `ShopRedactJob`/`AppUninstalledJob` looks up and acts on the victim's `Shop` record. [7](#0-6) [8](#0-7) 

*Note:* I was unable to fully verify the internal HMAC/header validation logic of the built-in `ShopifyAPI::Webhooks::Registry.process` path used by `app/controllers/shopify_app/webhooks_controller.rb`, since that verification logic lives in the external `shopify_api` gem, not in this repository, and is out of scope per the dependency-only exclusion rule. The finding above is scoped to the `shopify_app`-owned `WebhookVerification`/`PayloadVerification` concerns and the generator-produced job templates that build on the documented `shop_domain` pattern.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

class AppUninstalledJob < ActiveJob::Base
  extend ShopifyAPI::Webhooks::WebhookHandler

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
