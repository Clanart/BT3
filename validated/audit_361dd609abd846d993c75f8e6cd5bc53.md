### Title
Overflow in `payment_sat + needed_fee` check lets outputs exceed inputs, producing an invalid transaction and `fee()` underflow - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The `OndoFees.sol` bug computes `currentVolume - limitVolume` (inverted operands) once the running sum crosses a limit, reverting instead of charging the remainder. The same class exists in `SignableTransaction::new`: the sufficiency check `input_sat < (payment_sat + needed_fee)` at `send.rs:215` sums attacker-influenced `u64` payment amounts before comparing, instead of subtracting under a bound. When `payment_sat + needed_fee` overflows `u64` (release build wraps; debug build panics), the `NotEnoughFunds` guard is bypassed and a `SignableTransaction` is built whose outputs exceed its inputs.

### Finding Description
`SignableTransaction::new` validates funding with an additive comparison:

```rust
// networks/bitcoin/src/wallet/send.rs:215
if input_sat < (payment_sat + needed_fee) {
  Err(TransactionError::NotEnoughFunds { ... })?;
}
```

`payment_sat` is `payments.iter().map(|p| p.1).sum::<u64>()` (`send.rs:187`) over caller-supplied amounts; the only per-payment bound is the lower `DUST` check (`send.rs:165-169`), with no upper bound or overflow-checked accumulation. A payment set whose amounts sum past `u64::MAX` (e.g., a single payment of `u64::MAX - 1000`) makes `payment_sat + needed_fee` wrap to a small value, so the check passes even though `input_sat` is trivially smaller than the true sum. The resulting transaction's outputs exceed its inputs, making it consensus-invalid, and `SignableTransaction::fee()` (`send.rs:138-141`) computes `sum(prevouts) - sum(outputs)` as a raw `u64` subtraction, which underflows/panics when called on this transaction. Unlike the analogous `checked_sub` used for the change calculation at `send.rs:228`, the funding check and `fee()` perform unchecked arithmetic.

### Impact Explanation
The threshold network can be made to produce a `SignableTransaction` that either panics the signing path (`fee()` underflow, or the overflow itself in debug builds) or yields a signed transaction Bitcoin nodes reject as invalid — a DoS on the spend path directly mirroring the subscription/redemption DoS in the report. It also inflates the UTXO set consumed: inputs are drained into `prevouts` (`send.rs:253`) and are only spendable again after the plan is dropped.

### Likelihood Explanation
Payment amounts are `u64` values with no upper bound. Any flow where an unprivileged party can influence a payment amount (e.g., a withdrawal of magnitude `~u64::MAX`, or a batch whose sum overflows) reaches this with public inputs. It requires no malicious validator, key access, or collusion — only a crafted amount in the `payments` slice passed to `SignableTransaction::new`.

### Recommendation
Use checked/saturating arithmetic for the funding check and accumulation:

```rust
let payment_sat = payments.iter().try_fold(0u64, |acc, p| acc.checked_add(p.1))
  .ok_or(TransactionError::NotEnoughFunds { .. })?;
if input_sat.checked_sub(payment_sat).map_or(true, |r| r < needed_fee) {
  Err(TransactionError::NotEnoughFunds { .. })?;
}
```

Also bound individual payment amounts to a sane maximum and make `fee()` use `checked_sub` so a malformed transaction cannot panic.

### Proof of Concept
```rust
// Passes the NotEnoughFunds check in release builds despite outputs >> inputs
let payments = vec![(some_script.clone(), u64::MAX - 1_000)];
let st = SignableTransaction::new(
    vec![received_output], // input_sat e.g. 100_000
    &payments,
    None,
    None,
    10,                  // fee_per_vbyte
).unwrap();              // payment_sat + needed_fee wraps, check bypassed
st.fee();                // u64 underflow: panic in debug, wrap in release
```
