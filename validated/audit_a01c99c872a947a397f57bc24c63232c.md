### Title
Signed-out GitHub account can be silently resurrected in memory via a race between `AccountsStore.refresh()` and `removeAccount()` - (File: app/src/lib/stores/accounts-store.ts)

### Summary
The external report's broken invariant is: an operation meant to *permanently revoke* a privilege (`transferOwnershipToZeroAddress`) doesn't account for a concurrent, already-in-flight async operation (`confirmOwnershipTransfer` via a stale `pendingOwner`) that can complete afterward and silently restore the revoked state. The same invariant is broken in GitHub Desktop's `AccountsStore`: signing out of an account (`removeAccount`) is supposed to permanently drop that account from the trusted, in-memory account list and the keychain, but a concurrently in-flight `refresh()` call can overwrite that removal, silently reinstating the "removed" account (with its token) into `this.accounts`.

### Finding Description
`AccountsStore.refresh()` snapshots the current `this.accounts` array, awaits a per-account async network call (`fetchUser` via `tryUpdateAccount`/`updatedAccount`), and then unconditionally reassigns `this.accounts` to the resolved array: [1](#0-0) 

`removeAccount()` mutates `this.accounts` independently, by deleting the keychain entry and filtering the array by endpoint/id: [2](#0-1) 

Because `refresh()` captures `this.accounts.map(...)` before awaiting, and then does a blind `this.accounts = await Promise.all(...)` after the awaits resolve, any `removeAccount()` call that completes *during* the pending `refresh()` network calls is discarded: the in-memory account list reverts to including the account, with a fresh, valid `Account` object (containing a token, since `tryUpdateAccount`/`fetchUser` returns a new `Account` populated with the token supplied before removal) and `this.save()` persists this reinstated login/endpoint entry back to `localStorage`. This mirrors the LiFi bug precisely: "revoke" (`setContractOwner(0)` / `removeAccount`) does not invalidate or cancel the already-in-flight "pending" completion path (`confirmOwnershipTransfer` / `refresh()`'s deferred assignment), so the revoked state can be silently restored by a delayed async completion that was authorized under the old, still-authenticated context.

Existing guards do not stop this path: `removeAccount()` has no way to signal or cancel an in-flight `refresh()`, and `refresh()` has no re-check of whether an account it fetched is still present in `this.accounts` before overwriting the array.

### Impact Explanation
If successful, a user who signs out of a compromised or expiring GitHub account (e.g., in response to a leaked-token warning, or simply switching accounts) can have that account's session silently and invisibly restored in the app's memory and persisted store, without any user action, re-authentication, or notification. This corrupts the value "the accounts the user is currently authenticated as," which downstream code relies on for git operations (credential helper trampoline, API calls) — effectively continuing to use credentials the user explicitly attempted to revoke.

### Likelihood Explanation
`refresh()` is invoked on accounts periodically/on triggers from `AppStore`, and `removeAccount`/`_removeAccount` is invoked whenever a user signs out or a token is invalidated (`onTokenInvalidated`) — see the sign-out call sites: [3](#0-2) [4](#0-3) 
Both flows write to the same unsynchronized `this.accounts` field with no locking or version-check, so any real-world overlap in timing (e.g., a slow `fetchUser` network round trip during a refresh, coinciding with a user-triggered or automatic sign-out) triggers the race deterministically.

### Recommendation
- In `refresh()`, do not blindly overwrite `this.accounts`; instead, merge the fetched results only for accounts still present in the current `this.accounts` (re-filter by endpoint/id right before assignment), or use a mutation-version/generation counter to detect and discard stale writes.
- Alternatively, make `removeAccount()` and `refresh()` mutually exclusive (e.g., serialize via the same `loadingPromise`-style queue already used for load/add/remove).

### Proof of Concept
1. App has one signed-in GitHub.com account `A` with a valid token.
2. `AccountsStore.refresh()` is triggered (e.g., periodic account refresh) and begins `fetchUser` for account `A` — this call is in flight and awaiting the network response.
3. Before the network response returns, the user signs out (`Dispatcher.removeAccount(A)` → `AppStore._removeAccount(A)` → `AccountsStore.removeAccount(A)`), which deletes `A`'s keychain entry and sets `this.accounts = []`.
4. The in-flight `refresh()` promise resolves with the freshly fetched `Account` object for `A` (including the token that was valid at call time).
5. `refresh()` executes `this.accounts = await Promise.all([...])`, setting `this.accounts = [A]` again, and calls `this.save()`, persisting `A`'s login/endpoint back into `localStorage`'s `users` entry.
6. The app now behaves as if the user never signed out of `A` — in-memory state and persisted store both show `A` as an active account, even though the user explicitly removed it and its keychain secret is gone (a subsequent `fetchUser`/`getItem` call may later fail, but any operation relying on the in-memory `Account.token` in the meantime uses the stale, "revoked" credential).

  public async refresh(): Promise<void> {
    this.accounts = await Promise.all(
      this.accounts.map(acc => this.tryUpdateAccount(acc))
    )

    this.save()
    this.emitUpdate(this.accounts)

  public async removeAccount(account: Account): Promise<void> {
    await this.loadingPromise

    try {
      await this.secureStore.deleteItem(
        getKeyForAccount(account),
        account.login
      )
    } catch (e) {
      log.error(`Error removing account '${account.login}'`, e)
      this.emitError(e)
      return
    }

    this.accounts = this.accounts.filter(
      a => !(a.endpoint === account.endpoint && a.id === account.id)
    )

    this.save()
  }

  private onTokenInvalidated = (endpoint: string, token: string) => {
    const account = getAccountForEndpoint(this.accounts, endpoint)

    if (account === null) {
      return
    }

    // If we have a token for the account but it doesn't match the token that
    // was invalidated that likely means that someone held onto an account for
    // longer than they should have which is bad but what's even worse is if we
    // invalidate an active account.
    if (account.token && account.token !== token) {
      log.error(`Token for ${endpoint} invalidated but token mismatch`)
      return
    }

    // If the token was invalidated for an account, sign out from that account
    this._removeAccount(account)

    this._showPopup({
      type: PopupType.InvalidatedToken,
      account,
    })
  }
