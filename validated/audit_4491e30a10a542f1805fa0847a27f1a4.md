### Title
Boundary-check bypass in `resolveWithin()` allows symlink escape to sibling directories, exfiltrating out-of-repo file contents via Copilot conflict resolution - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` is the shared guard used to keep file reads confined to a repository's working directory. It validates a resolved path by comparing string prefixes: `realResolved.startsWith(realRoot)`. This comparison has no path-separator boundary check, so a symlink that resolves to a *sibling* directory whose name happens to share the root directory's name as a prefix (e.g. root `/Users/victim/app` vs. target `/Users/victim/app-secrets/...` or `/Users/victim/app2/...`) incorrectly passes the "is inside the repo" check. The one caller that reads attacker-influenced, repository-relative paths and then sends file contents off the user's machine over the network is `buildConflictContext()` in `app/src/lib/copilot-conflict-context.ts`, which is used to build the prompt sent to GitHub Copilot for AI-assisted merge-conflict resolution.

### Finding Description
`resolveWithin` (`app/src/lib/path.ts:36-72`) computes: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

The intent (per the doc comment) is to guarantee the resolved path "resides at, or underneath" the root path, and the code even calls `realpath()` on both sides specifically to defeat symlink escapes. However, `String.prototype.startsWith` performs no separator-aware boundary check. If `realRoot` is `/Users/victim/Documents/GitHub/app` and a conflicted file entry is (or contains) a symlink whose target resolves to `/Users/victim/Documents/GitHub/app-secrets/config.json` or `/Users/victim/Documents/GitHub/app2/id_rsa`, then `realResolved.startsWith(realRoot)` evaluates to `true` even though that path is a completely different, sibling directory outside the actual repository. The function then returns `resolved` (the in-repo symlink path), and the caller proceeds to `readFile()` it — the OS follows the symlink and returns the *sibling* directory's content.

This function is called from `buildConflictContext()`: [2](#0-1) 

which is driven by `file.path` values derived from the list of conflicted files during a merge/rebase/cherry-pick — paths that originate from the working tree of a repository the user has cloned or fetched, i.e., attacker-controlled content when the repo is malicious (e.g., a repo staged to produce a merge conflict, with a tracked symlink among the conflicting files). The read file content is fed into `formatConflictContextForPrompt()` and ultimately sent to the Copilot API as part of the AI conflict-resolution prompt (see `app/src/lib/stores/copilot-store.ts`), meaning any successfully "escaped" file content is transmitted off the user's machine to a third-party (Copilot) service.

Existing guards that fail to stop this path:
- The `resolveWithin` realpath+prefix check is specifically the anti-symlink-escape guard, and it is bypassed by the missing separator check.
- The subsequent size guard (`MAX_CONFLICT_FILE_READ_SIZE`) and content-size guard (`MAX_CONFLICT_CONTENT_SIZE`) only bound how much data can be exfiltrated, not whether it can be exfiltrated at all.
- There is no additional check (e.g., `lstat`) elsewhere in `buildConflictContext` to reject symlinks outright before reading.

This is structurally the same bug class as the seed report: a value that should be excluded from a trusted aggregate/boundary (WETH balance not backed by the transmuter; here, a file outside the repo root) is incorrectly included because the inclusion/boundary check has a logic flaw, and downstream consumers (share minting there; the Copilot prompt/network exfiltration here) treat the incorrectly-included value as trustworthy in-scope data.

### Impact Explanation
A malicious or compromised repository that a user clones/fetches and that produces a merge/rebase/cherry-pick conflict can include a tracked symlink as one of the "conflicted" files. If the symlink's target path (after `realpath` resolution) happens to share a string prefix with the repository's root path — an outcome the attacker can influence by choosing where they instruct the victim to place the affected repo relative to other directories, or by exploiting common developer directory layouts (e.g., cloning multiple repos side-by-side into `~/code/<name>`) — GitHub Desktop will read the out-of-repo file and transmit its content to the Copilot API as part of the AI conflict-resolution feature. This can lead to disclosure of files outside the intended repository boundary (e.g., adjacent repositories, credential files, config files) to a third-party network endpoint, matching the "file read outside the repo" / "credential exfiltration" impact class.

### Likelihood Explanation
Exploitation requires: (1) the user to open a malicious/attacker-influenced repo that reaches a merge/rebase/cherry-pick conflict state including a symlink among conflicted files, and (2) the user's directory layout to produce a `realpath` collision under simple string-prefix matching (no separator). Condition (2) is a real-world common pattern (sibling project directories sharing a name prefix, e.g. `app` and `app-old`, or `repo` and `repo2`), making it plausible without requiring exotic host state, though it is not guaranteed for every victim. The feature (`Resolve with Copilot`) must also be enabled/invoked. No local/physical access, admin rights, or pre-existing malware is required — only a crafted repository and normal use of the conflict-resolution feature.

### Recommendation
Fix the boundary check in `_resolveWithin` (`app/src/lib/path.ts:71`) to require an exact match or a match followed by the path separator, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Additionally, consider rejecting symlinked conflict entries outright in `buildConflictContext` (via `lstat` before `readFile`) rather than silently following them, since conflict resolution content should never legitimately need to escape the working directory.

### Proof of Concept
1. Victim has two sibling directories: `/Users/victim/code/app` (a normal repo) and `/Users/victim/code/app-secrets` (another repo/folder containing sensitive files, e.g. `.env`).
2. Attacker crafts a branch in `app` that, when merged, produces a conflict on a file that is a symlink pointing to `../app-secrets/.env` (relative symlink, valid git object).
3. Victim triggers a merge that conflicts, then uses "Resolve with Copilot."
4. `buildConflictContext()` calls `resolveWithin('/Users/victim/code/app', 'symlink-file')`; `resolved` normalizes to a path under `app`, but `realpath(resolved)` resolves through the symlink to `/Users/victim/code/app-secrets/.env`.
5. `realResolved.startsWith(realRoot)` evaluates `'/Users/victim/code/app-secrets/.env'.startsWith('/Users/victim/code/app')` → `true` (bug), so the guard does not reject it.
6. `readFile(absolutePath)` follows the symlink and reads `.env` content, which is then serialized into the Copilot prompt via `formatConflictContextForPrompt()` and sent to the Copilot API, exfiltrating the secret file outside the intended repository boundary. [3](#0-2) [4](#0-3)
