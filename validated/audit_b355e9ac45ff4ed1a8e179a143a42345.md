### Title
Unvalidated `n` field in `ThresholdKeys::read` enables attacker-triggered memory exhaustion (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to the `SystemConfig.initialize()` report — where a user-supplied `ResourceConfig` is consumed without any sanity validation, enabling a resource-exhaustion DoS — `ThresholdKeys::<C>::read` consumes the serialized `t`/`n`/`i` header fields from an untrusted byte stream without bounding them, and immediately sizes heap allocations and deserialization loops from the attacker-controlled `n`. `ThresholdParams::new` only checks `0 < t <= n` and `i <= n`, so `n` may be as large as `u16::MAX` (65535).

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) parses:

1. `t`, `n`, `i` as raw `u16`s from the reader (lines 591-602).
2. If the interpolation tag is `0` (Constant), it executes `Vec::with_capacity(usize::from(n))` and a `0..n` loop of `C::read_F` calls (lines 607-613) — an allocation sized entirely by the untrusted `n`.
3. It then inserts `n` entries into a `HashMap`, each costing a `read_G` (point decompression) (lines 620-623).
4. `ThresholdParams::new` (lines 166-179) validates only `t <= n`, `i <= n`, and non-zero — there is no cap on `n`, and `ThresholdKeys::new` (lines 349-391) computes `group_key` as a sum of `t` interpolated point multiplications, an O(t) multiexp whose cost is also attacker-chosen.

`Participant` is defined as a non-zero `u16` (line 26), so the honest domain is small validator sets, yet nothing in the read path enforces a reasonable bound. An untrusted byte stream reaching `ThresholdKeys::read` (an explicitly in-scope deserialization sink) therefore drives pre-allocation and per-element deserialization work on the order of ~2 MB and 65k field/point reads per call, repeat invocable at near-zero cost to the sender (only ~10 header bytes are needed to trigger the `with_capacity` allocation before the first `read_exact` fails).

The same pattern repeats in the DKG stack: `Commitments::read` in crypto/dkg/pedpop/src/lib.rs:110-128 allocates `Vec::with_capacity(params.t())` and reads `t` group elements, where `t` comes from `ThresholdParams` — validated for internal consistency but not bounded — and every `EncryptedMessage`/share-reader threads the same `params` through.

### Impact Explanation
A remote party able to feed bytes into `ThresholdKeys::read` (or the PedPoP `Commitments`/`EncryptedMessage` readers parameterized by deserialized `ThresholdParams`) can force repeated multi-megabyte allocations and tens of thousands of scalar/point deserialization attempts per message. Issued concurrently or in a loop, this exhausts memory and CPU of the deserializing process — a denial of service against a validator/processor node, directly mirroring the out-of-gas DoS in the reference report.

### Likelihood Explanation
`ThresholdKeys::read` and the PedPoP message readers are public deserialization APIs documented to accept `io::Read` streams, and the audit scope explicitly contemplates untrusted bytes reaching them. Triggering requires only a handful of crafted header bytes; no valid keys, signatures, or protocol state are needed. Likelihood is limited only by whether the deploying layer exposes these readers on untrusted input — which the in-scope threat model assumes.

### Recommendation
- Enforce a protocol-level maximum on `t`/`n` inside `ThresholdParams::new` (or at the top of `ThresholdKeys::read` before any allocation), consistent with the deployed maximum validator set (e.g., the `MAX_KEY_SHARES_PER_SET` style bound already used in the coordinator).
- Avoid `Vec::with_capacity(n)` / `HashMap` pre-sizing on untrusted counts; grow incrementally as bytes are actually read, or check remaining input length before allocating.
- Apply the same bound in `Commitments::read` and all `params`-driven readers in crypto/dkg.

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ristretto;
use dkg::ThresholdKeys;

// Crafted input: valid curve-ID preamble, then n = u16::MAX
let mut buf = vec![];
buf.extend(4u32.to_le_bytes());            // id_len (match C::ID.len())
buf.extend(Ristretto::ID);                 // curve ID
buf.extend(1u16.to_le_bytes());            // t = 1
buf.extend(u16::MAX.to_le_bytes());        // n = 65535
buf.extend(1u16.to_le_bytes());            // i = 1
buf.push(0);                               // Interpolation::Constant
// No further bytes: with_capacity(65535) of 32-byte scalars (~2 MB)
// is still allocated before read_F hits EOF.
let res = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice());
assert!(res.is_err()); // errors only AFTER the oversized allocation
```

Each invocation of `read` on this ~15-byte input performs a ~2 MB allocation plus allocation for 65535 `HashMap` slots; repeated submissions or a fully-populated stream (65535 scalar + point reads) multiply the cost linearly while the attacker pays only per-byte bandwidth. Note: the absolute amplification per call is bounded (~a few MB / 65k deserializations), so this is a Medium-severity resource-exhaustion issue rather than a single-message crash.

Caveat: I was unable to confirm the exact call sites where the coordinator/processor feed network-controlled bytes into `ThresholdKeys::read` within the remaining budget; the finding assumes such exposure per the stated in-scope sinks (`ThresholdKeys::read` on untrusted bytes).
