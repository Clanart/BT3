### Title
Out-of-bounds `Participant` in a blame accusation panics `BlameMachine`/`AdditionalBlameMachine` via unchecked `HashMap` indexing - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP blame-evaluation path (`BlameMachine::blame`, `AdditionalBlameMachine::blame`, and their shared helper `blame_internal`) indexes `self.commitments[&sender]` and `self.enc_keys[&decryptor]` with `Participant` values supplied by the caller as part of an accusation. `Participant::new` only rejects zero; no check ensures the accused `sender`/`recipient` is within the DKG's `1..=n` set that populated those maps. An accusation naming a syntactically-valid-but-unregistered participant index (e.g. `n + 1`) causes a `HashMap` index panic — a remotely triggerable, repeatable crash, the analog of the MariaDB/MySQL "low-privileged network attacker causes hang or repeatable crash (complete DOS)" class.

### Finding Description
`BlameMachine::blame` forwards `sender`, `recipient`, and an attacker-controlled `EncryptedMessage` to `blame_internal` (crypto/dkg/pedpop/src/lib.rs:623-632). `blame_internal` calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)`, which evaluates the message's Schnorr proof of possession and, when a proof is present, verifies a DLEq statement over `self.enc_keys[&decryptor]` (crypto/dkg/pedpop/src/encryption.rs:388) — a direct `HashMap` index that panics if `decryptor` (the `recipient` argument) was never registered. If the signature check fails first, execution still reaches `share_verification_statements::<C>(recipient, &self.commitments[&sender], ...)` at crypto/dkg/pedpop/src/lib.rs:599, which panics identically on an unregistered `sender`.

The maps are only ever populated for participants `1..=n`: `Encryption`/`Decryption::register` is called exactly once per in-range participant in `verify_r1` (crypto/dkg/pedpop/src/lib.rs:313-315) and in `AdditionalBlameMachine::new` (crypto/dkg/pedpop/src/lib.rs:656-660). `Participant::new` accepts any non-zero `u16` up to 65535 (crypto/dkg/src/lib.rs:29-35), and the wire format for accusation messages reads bare `Participant` values with no `<= n` bound (e.g. `InvalidDkgShare` in coordinator/src/tributary/transaction.rs:346-353 reads `accuser`/`faulty` via `Participant::new` only). The doc comments for `blame` promise the function returns one of the two parties as faulty; nothing documents that out-of-range inputs abort via panic, and the function signature returns `Participant`, not `Result`.

### Impact Explanation
A remote party able to submit a blame/accusation message (the very mechanism intended for unauthenticated fault reporting, where `AdditionalBlameMachine::new` explicitly exists so non-participants can evaluate blame) can crash the evaluating process with a single crafted accusation naming `sender` or `recipient` as an unregistered index such as `u16::MAX`. This is a complete, repeatable availability loss of the node processing the blame — the same consequence class as CVE-2017-3308 (PR:L, S:C, A:H). Severity is bounded by whether the panic unwinds into a caught context or aborts the host; as a library panic it propagates to the caller's thread.

### Likelihood Explanation
The panic requires only that `sender` or `recipient` be a `Participant` outside the registered `1..=n` set — trivially constructible, deterministic, and requiring no secret knowledge or race. Reachability depends on integrators routing externally-supplied accuser/faulty fields into `blame`; the `AdditionalBlameMachine` API is designed exactly for third-party evaluation of accusations, so untrusted indexes are the expected input shape.

### Recommendation
In `blame_internal`, validate `sender`/`recipient` membership before indexing: return the accuser (or a defined error/faulty-participant result) when `!self.commitments.contains_key(&sender)` or `!self.encryption`'s `enc_keys` lacks `decryptor`. Replace `self.commitments[&sender]` and `self.enc_keys[&decryptor]` with `.get()` plus explicit error handling, and document the behavior for out-of-range participants.

### Proof of Concept
```rust
// Any ciphersuite C; context arbitrary; n small, e.g. n = 3.
// Build an AdditionalBlameMachine with valid commitment messages for
// participants 1..=n (the constructor validates their structure).
let machine = AdditionalBlameMachine::<C>::new(context, n, commitment_msgs).unwrap();

// Craft an accusation naming a participant index that was never registered.
let bogus_sender = Participant::new(n + 1).unwrap();       // valid Participant, not in maps
let recipient    = Participant::new(1).unwrap();

// msg: any EncryptedMessage whose Schnorr PoP verifies against its embedded
// key (so decrypt_with_proof proceeds), or even an invalid-signature one:
//   - Invalid signature path: blame_internal still reaches
//     self.commitments[&sender] at pedpop/src/lib.rs:599 -> panic.
//   - Valid signature + proof path: enc_keys[&decryptor] at
//     encryption.rs:388 panics if `recipient` is the bogus index instead.
machine.blame(bogus_sender, recipient, msg, None);
// thread panics: "no entry found for key" (HashMap index) — repeatable DoS
```

Caveat: the accept list emphasizes signing/proof/verifier outcomes; a pure panic is the closest faithful analog to this DoS-class advisory, and it is reachable in the blame path which is explicitly designed to consume externally sourced accusations. If the harness requires a signature forgery or verifier-formula bug rather than a crash, this finding should be downgraded.
