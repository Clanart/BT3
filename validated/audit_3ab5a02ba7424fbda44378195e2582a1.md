### Title
Missing `--` end-of-options guard lets an attacker-controlled remote name be interpreted as a `git fetch` option (argument injection) - (File: `app/src/lib/git/fetch.ts`)

### Summary
`fetch()` and `fetchRefspec()` build the `git fetch` argv by appending the remote's short `name` (and, for `fetchRefspec`, an arbitrary `refspec`) as trailing positional tokens, with no `--` end-of-options separator and no validation that the value cannot start with `-`/`--`. Because dugite/git spawns the process via an argv array (no shell), classic shell-metacharacter injection is not reachable here, but git's own option parser still treats any leading-`-` token as a flag regardless of its intended positional role, so this is a genuine argv/flag-injection surface rather than a shell-injection one.

### Finding Description
`getFetchArgs` appends the raw remote name as the last element of the `git fetch` argument vector with no `--` separator: [1](#0-0) 

`fetch()` then executes it directly against the repository path: [2](#0-1) 

`fetchRefspec()` has the same pattern, placing `remote.name` and an attacker-influenceable `refspec` string directly after `'fetch'`, again without a `--` guard: [3](#0-2) 

`remote.name` originates from `getRemotes()`, which parses the *local* `.git/config`/`git remote -v` output verbatim into `IRemote.name` with no format validation: [4](#0-3) [5](#0-4) 

If a remote's name in that config is something like `--upload-pack=<command>`, this string is a *legitimate* git option (`git fetch` accepts `--upload-pack=<cmd>` to select the program invoked on the remote/local side for `ssh://`/`file://` transports), and git's own argument parser recognizes it as an option no matter where it sits positionally, since Desktop never terminates option parsing with `--` before the operand. This is not shell injection (no shell is involved — dugite/git spawn with an argv array), it is argument injection into git itself, which for `--upload-pack`/similar transport-helper options can result in git invoking an attacker-chosen command.

The two realistic ways an attacker gets such a name into `IRemote.name`:
- The user adds/opens an attacker-authored repository whose `.git/config` already contains a `[remote "--upload-pack=..."]` section (an "attacker controls a cloned/fetched repository" scenario per the bounty scope). `getRemotes()` will surface this name unmodified.
- Any code path that derives a remote name from GitHub API data, e.g. `forkPullRequestRemoteName(headRepoOwner)` used when checking out PRs from forks, though this specific path is not exploitable in practice because GitHub enforces a username format that disallows a leading hyphen.

### Impact Explanation
If exploitable, this allows a crafted remote name to be parsed by `git fetch` as `--upload-pack=<command>` (or another sensitive flag), causing git to execute an attacker-chosen executable/command as a side effect of a routine fetch — full local code execution on the user's machine, satisfying the "Critical" impact bar in the target scope (git/child-process invocation executing attacker-chosen options).

### Likelihood Explanation
Exploitation requires the attacker to control the *remote name* stored in the repository's git configuration, not just the URL or ref content that flows through normal clone/fetch/PR metadata. I was not able to verify within this review whether GitHub Desktop's `git remote -v`/config parsing, or dugite's underlying git version, would actually accept and round-trip a remote subsection name beginning with `-`/`--` when the `.git/config` is crafted directly (bypassing `git remote add`'s own validation) rather than created through Desktop's UI. The PR-fork-remote path (`forkPullRequestRemoteName(headRepoOwner)`) is not exploitable because GitHub usernames cannot start with a hyphen. This uncertainty about whether a hand-crafted `.git/config` remote name can actually reach `fetch()`/`fetchRefspec()` unmodified should be validated with a concrete PoC before treating this as confirmed-exploitable; the code pattern itself (no `--` guard, no name validation) is real and matches the described weakness, but the actual reachability of a hostile value is unverified.

### Recommendation
- Insert a `--` end-of-options separator before the remote/refspec operand in `getFetchArgs`, `fetch()`, and `fetchRefspec()` (e.g. `['fetch', ...flags, '--', remote]`), matching the pattern git recommends for exactly this class of bug.
- Validate remote names on ingestion (`getRemotes()`/`addRemote()`) to reject or quarantine names beginning with `-`, and apply the same "operand only, never a flag" invariant consistently across all git wrapper functions that append repository-derived strings (refs, branches, remote names, paths) to argv.

### Proof of Concept
Not verified end-to-end due to the reachability uncertainty noted above. Conceptual PoC: create a repository whose `.git/config` contains a remote section literally named `--upload-pack=touch /tmp/pwned;#` with an arbitrary `url`/`fetch` line; open this repository as a local repository in GitHub Desktop and trigger a fetch on that remote. If `getRemotes()` returns the name unmodified, `getFetchArgs` will produce `['fetch', '--prune', '--recurse-submodules=on-demand', '--upload-pack=touch /tmp/pwned;#']`, causing git to attempt to run the injected command as its upload-pack helper.

```typescript
export async function getRemotes(
  repository: Repository
): Promise<ReadonlyArray<IRemote>> {
  const result = await git(['remote', '-v'], repository.path, 'getRemotes', {
    expectedErrors: new Set([GitError.NotAGitRepository]),
  })

  if (result.gitError === GitError.NotAGitRepository) {
    return []
  }

  return [...result.stdout.matchAll(/^(.+)\t(.+)\s\(fetch\)/gm)].map(
    ([, name, url]) => ({ name, url })
  )
}
```
