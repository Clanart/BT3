## Finding

### Title
Payout attribution keyed by withdrawal UTXO bytes alone (not `(deposit_id, utxo)`) lets one Bitcoin spend cross-attribute or block reimbursement across unrelated deposits - (File: core/src/database/verifier.rs)

### Summary
`get_payout_txs_for_withdrawal_utxos` and `update_payout_txs_and_payer_operator_xonly_pk` match a spent Bitcoin UTXO to a `withdrawals` row purely on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` bytes, and the `withdrawals` table (`core/src/database/schema.sql:269-281`) has no uniqueness constraint preventing two distinct deposit indices from registering the identical outpoint bytes. Since the attacker fully controls the `input_outpoint` bytes passed to `withdraw()` on the Citrea Bridge contract, they can register the same withdrawal UTXO under two different deposit indices `i` and `i'`, causing a single real Bitcoin spend to be joined onto both rows.

### Finding Description
The intended binding is: `payout_payer_operator_xonly_pk[deposit_id]` should equal the operator that actually funded the payout transaction spending `withdrawal_utxo[deposit_id]`, for that specific `deposit_id` only.

The actual code does not enforce this per-deposit:

- `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`) does:
```
SELECT w.idx, bsu.spending_txid
FROM withdrawals w
JOIN bitcoin_syncer_spent_utxos bsu
   ON bsu.txid = w.withdrawal_utxo_txid
  AND bsu.vout = w.withdrawal_utxo_vout
WHERE bsu.block_id = $1
``` [1](#0-0) 

If two `withdrawals` rows (idx = `i` and idx = `i'`) carry identical `withdrawal_utxo_txid`/`withdrawal_utxo_vout` bytes, this join returns **both** `(i, spending_txid)` and `(i', spending_txid)` for the one real bitcoin spend.

- `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:199-251`) then writes the same `payout_txid`/`payout_payer_operator_xonly_pk`/`payout_tx_blockhash` into **both** rows keyed only by `idx`: [2](#0-1) 

- The `withdrawals` table itself has no unique index over `(withdrawal_utxo_txid, withdrawal_utxo_vout)`, only `idx primary key`: [3](#0-2) 

- Registration of the outpoint bytes comes straight from `collect_withdrawal_utxos`/`update_withdrawal_utxo_from_citrea_withdrawal`, driven by attacker-chosen `input_outpoint` in the `withdraw()` call, with no cross-deposit uniqueness check: [4](#0-3) 

An attacker calls `withdraw()` twice with different `withdrawal_id`s but the identical `input_outpoint` bytes (a UTXO they control). An honest operator later fronts the real payout for one of these deposits (say `i'`), spending that UTXO once on Bitcoin. `update_finalized_payouts` → `get_payout_txs_for_withdrawal_utxos` matches that single spend to **both** `i` and `i'`, and `PayoutCheckerTask` (`core/src/task/payout_checker.rs:41-79`) picks up whichever row `get_first_unhandled_payout_by_operator_xonly_pk` returns first via `handle_finalized_payout(deposit_data.get_deposit_outpoint(), payout_tx_blockhash)`: [5](#0-4) 

I could not fully trace `Operator::handle_finalized_payout`'s internal validation (file content for that function body was not retrievable in this session), so I cannot confirm with certainty whether it independently re-derives/checks that the on-chain payout tx structurally matches the specific deposit's presigned payout template before crediting a kickoff. Two outcomes are possible depending on that unverified logic:
1. If `handle_finalized_payout` does not cross-validate the payout tx against the deposit's own committed withdrawal parameters, the operator is credited for a deposit (`i`) it never actually served — "operator reimbursed for a payout it never funded."
2. If it does validate and errors on the mismatched deposit `i`, and `get_first_unhandled_payout_by_operator_xonly_pk` deterministically re-selects the same (lower) index each retry, the task can never advance past `i` to process `i'`, permanently starving the honest operator who funded `i'` — matching the exact scenario in the question.

Either branch is a real divergence caused by the same root cause: **the finalized-payout matching keys on UTXO bytes alone, not on `(deposit_id, utxo)`,** and no DB constraint prevents duplicate UTXO registration across deposits.

### Impact Explanation
This falls under the Critical categories "an operator reimbursed for a payout it never funded" and/or "an honest operator permanently unable to be reimbursed," depending on unverified downstream validation in `handle_finalized_payout`. The blast radius is per attacker-crafted pair of withdrawal registrations sharing an outpoint; it is repeatable across any two deposits the attacker controls the withdrawal ids for.

### Likelihood Explanation
The precondition is cheap and fully within the stated attacker capability: calling `withdraw()` on the Citrea Bridge contract twice with attacker-chosen, identical `input_outpoint` bytes for two different withdrawal/deposit ids — no verifier, operator, or aggregator privilege required, and no on-chain cost beyond ordinary deposit/withdraw fees. The missing DB uniqueness constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` and the UTXO-only join make the duplicate registration silently accepted.

### Recommendation
Add a uniqueness constraint on `withdrawals(withdrawal_utxo_txid, withdrawal_utxo_vout)` (or reject registration of a withdrawal UTXO already used by another deposit id) at `update_withdrawal_utxo_from_citrea_withdrawal`, and change `get_payout_txs_for_withdrawal_utxos`/`update_payout_txs_and_payer_operator_xonly_pk` to fail loudly (rather than silently multi-match) if more than one `withdrawals.idx` maps to the same spent UTXO in a block.

### Proof of Concept
`cargo test` under `core/src/database` (extending the existing `update_get_payout_txs_from_citrea_withdrawal` test at `core/src/database/verifier.rs:390-454`):
1. Insert two `withdrawals` rows via `upsert_move_to_vault_txid_from_citrea_deposit`/`update_withdrawal_utxo_from_citrea_withdrawal` for `idx = i` and `idx = i'` with identical `OutPoint` bytes.
2. Insert a single `bitcoin_syncer_spent_utxos` row for that outpoint (`insert_spent_utxo`).
3. Call `get_payout_txs_for_withdrawal_utxos` and assert the result contains **exactly one** `(idx, txid)` pair (the currently-broken behavior returns two).
4. Call `update_payout_txs_and_payer_operator_xonly_pk` and assert that only the correct `idx` (the one whose UTXO was truly spent by the operator's transaction) has `payout_payer_operator_xonly_pk` set, while the other remains `NULL`/unhandled with an explicit error rather than silent duplication.     async fn update_get_payout_txs_from_citrea_withdrawal() {
        let config = create_test_config_with_thread_name().await;
        let db = Database::new(&config).await.unwrap();

        let txid = Txid::from_byte_array([0x45; 32]);
        let index = 0x1F;
        let operator_xonly_pk = generate_random_xonly_pk();
        let utxo = bitcoin::OutPoint {
            txid: bitcoin::Txid::from_byte_array([0x45; 32]),
            vout: 0,
        };

        let mut dbtx = db.begin_transaction().await.unwrap();

        let block_id = db
            .insert_block_info(
                Some(&mut dbtx),
                &BlockHash::all_zeros(),
                &BlockHash::all_zeros(),
                utxo.vout,
            )
            .await
            .unwrap();
        db.insert_txid_to_block(&mut dbtx, block_id, &txid)
            .await
            .unwrap();
        db.insert_spent_utxo(&mut dbtx, block_id, &txid, &utxo.txid, utxo.vout.into())
            .await
            .unwrap();

        assert!(db
            .get_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), index)
            .await
            .is_err());
        db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), index, &txid)
            .await
            .unwrap();
        db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), index, utxo, block_id)
            .await
            .unwrap();

        let block_hash = BlockHash::all_zeros();

        db.update_payout_txs_and_payer_operator_xonly_pk(
            Some(&mut dbtx),
            vec![(index, txid, Some(operator_xonly_pk), block_hash)],
        )
        .await
        .unwrap();

        let txs = db
            .get_payout_txs_for_withdrawal_utxos(Some(&mut dbtx), block_id)
            .await
            .unwrap();

        assert_eq!(txs.len(), 1);
        assert_eq!(txs[0].0, index);
        assert_eq!(txs[0].1, txid);

        let withdrawal_utxo = db
            .get_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), index)
            .await
            .unwrap();
        assert_eq!(withdrawal_utxo, utxo);
