## Analysis

The external report's core broken invariant: **the same conceptual charge (spread/price-impact fee) is applied inconsistently depending on which code path or historical state a value passes through, and an attacker can sequence operations to land in the path that skips the charge.**

The closest local, self-contained analog in this Hyperbridge repo is in `IntentGatewayV2`'s same-chain intent-filling logic, where surplus-share fee capture (the analog of "spread/price-impact charge") is gated on a state flag (`alreadyFilled == 0`) that a solver fully controls by splitting a single fill into two transactions. [1](#0-0) 

### Title
Surplus-share fee bypass via split partial fills - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` only computes and collects the protocol/beneficiary surplus split (`surplusShareBps`) when `alreadyFilled == 0 && solverAmount > totalRequired` — i.e., only on a fresh, never-before-partially-filled output pair. [2](#0-1)  Once any partial fill has landed on that `(commitment, outputToken)` pair, the `else` branch simply caps `fillAmount` at `remaining` and never computes `beneficiaryShare`/`protocolShare` for any further "overpayment" on that pair. [3](#0-2)  This mirrors the reported bug's structure exactly: the fee/charge computation is state-gated (first fill vs. subsequent fill) rather than being tied to the economic event it is meant to price (solver overpayment), so a solver who is expected to share their overpayment with the beneficiary/protocol can avoid that obligation purely by choosing transaction ordering.

### Finding Description
The documented design intent is: "When a solver provides more tokens than required, the excess is split according to `surplusShareBps`... Surplus only applies on the first fill of each output token pair." [4](#0-3)  This "first fill only" restriction is implemented as a hard state check (`alreadyFilled == 0`) rather than being computed relative to the *order's total remaining requirement across the whole fill lifecycle*. A solver who is obligated (e.g., by a winning bid/auction commitment) to deliver an output amount that includes an intentional overpayment can defeat the surplus-sharing mechanism entirely by:
1. Submitting a first `fillOrder` call for any amount ≤ `remaining` (no excess) — this sets `alreadyFilled != 0` for that output token, with zero surplus computed.
2. Submitting a second `fillOrder` call for exactly the remaining required amount — the `else` branch caps `fillAmount` at `remaining`, so even if the solver intended/was supposed to overpay, no `protocolShare`/`beneficiaryShare` is ever computed or transferred, since the transfer only pulls `beneficiaryTotal = fillAmount + beneficiaryShare` from the solver. [5](#0-4) 

This is confirmed by the existing test `testPartialFill_SurplusOnlyWhenNotPartiallyFilled`, which explicitly asserts "no surplus on partially filled pair" once any prior partial fill exists. [6](#0-5) 

The guard that exists (`if (order.output.call.length > 0 && !isFullyFilled) revert PartialFillNotAllowed();`) only blocks partial fills for calldata-bearing orders; it does nothing to prevent an attacker from using the ordinary partial-fill path purely to launder overpayment out of the surplus-sharing mechanism on plain orders. [7](#0-6) 

### Impact Explanation
The beneficiary and protocol are structurally entitled to a `surplusShareBps` cut of any solver overpayment (this is the on-chain enforcement mechanism for auction/bid-driven price improvement in the Intent Gateway). By sequencing fills, a solver captures 100% of what should have been shared value, corrupting the intended fee/revenue split — the same "logic attack" class as the seed report (fee/charge percentage silently reduced to 0% based on an attacker-controllable state transition rather than the true economic condition the fee is meant to price).

### Likelihood Explanation
High. Any solver filling a same-chain order can trivially split a fill into two `fillOrder` transactions with no special privileges, no relayer/prover/admin cooperation, and no front-running — purely their own transaction ordering. It works for every plain (non-calldata) same-chain order with `surplusShareBps > 0`.

### Recommendation
Compute the surplus split from the aggregate overpayment relative to the order's total required amount for that output token, not from a per-fill `alreadyFilled == 0` gate. E.g., track cumulative solver-provided amount vs. cumulative required amount, and apply `surplusShareBps` to any excess regardless of whether it arrives in the first fill or a later fill that completes the pair.

### Proof of Concept
1. User places a same-chain order requiring 1000 DAI output, `surplusShareBps = 5000` (50/50 split).
2. Solver intends/is contractually expected to deliver 1100 DAI (100 DAI intentional overpayment per their winning bid).
3. Instead of a single `fillOrder` call with `outputs[0].amount = 1100e18` (which would trigger `alreadyFilled == 0 && solverAmount > totalRequired`, splitting the 100 DAI surplus 50/50 as shown in `testPartialFill_SurplusOnFullFill`) [8](#0-7) , the solver calls `fillOrder` twice:
   - Call 1: `outputs[0].amount = 500e18` (no excess, `alreadyFilled` becomes `500e18`).
   - Call 2: `outputs[0].amount = 600e18` — but `remaining = 500e18`, so `fillAmount` is capped to `500e18` in the `else` branch; `beneficiaryShare = protocolShare = 0`, and `IERC20.safeTransferFrom` only pulls `500e18` from the solver, not `600e18`.
4. Result: order fully filled, user receives exactly 1000 DAI, protocol/beneficiary receive 0 DAI of the intended 100 DAI surplus split — verified by the existing `testPartialFill_SurplusOnlyWhenNotPartiallyFilled` test pattern. [6](#0-5)

    function testPartialFill_SurplusOnlyWhenNotPartiallyFilled() public {
        uint256 inputAmount = 1000 * 1e6;
        uint256 outputAmount = 1000 * 1e18;
        Order memory order = _placeStandardOrder(inputAmount, outputAmount);

        // Solver fills 500 DAI (partial)
        vm.startPrank(solver);
        dai.approve(address(intentGateway), 500 * 1e18);
        TokenInfo[] memory outputs1 = new TokenInfo[](1);
        outputs1[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 500 * 1e18});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: outputs1}));
        vm.stopPrank();

        // Solver 2 fills remaining 500 with 600 offered — excess should be capped (no surplus on partially filled pair)
        address solver2 = makeAddr("solver2");
        deal(address(dai), solver2, 100000 * 1e18);
        uint256 solver2DaiBefore = dai.balanceOf(solver2);
        uint256 userDaiBefore = dai.balanceOf(user);

        vm.startPrank(solver2);
        dai.approve(address(intentGateway), 600 * 1e18);
        TokenInfo[] memory outputs2 = new TokenInfo[](1);
        outputs2[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 600 * 1e18});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: outputs2}));
        vm.stopPrank();

        // Solver 2 should only spend 500 DAI (capped)
        assertEq(dai.balanceOf(solver2), solver2DaiBefore - 500 * 1e18, "Solver2 capped to remaining");
        // User should receive exactly 500 more DAI (no surplus)
        assertEq(dai.balanceOf(user), userDaiBefore + 500 * 1e18, "User gets exact remaining, no surplus");
        // No dust in gateway
        assertEq(dai.balanceOf(address(intentGateway)), 0, "No protocol surplus on partially filled pair");
    }

    function testPartialFill_SurplusOnFullFill() public {
        uint256 inputAmount = 1000 * 1e6;
        uint256 outputAmount = 1000 * 1e18;
        uint256 solverAmount = 1100 * 1e18; // 100 DAI surplus
        Order memory order = _placeStandardOrder(inputAmount, outputAmount);

        // Single solver fills the entire order with surplus (pair was never partially filled)
        vm.startPrank(solver);
        uint256 userDaiBefore = dai.balanceOf(user);
        dai.approve(address(intentGateway), solverAmount);

        TokenInfo[] memory outputs = new TokenInfo[](1);
        outputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: solverAmount});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: outputs}));
        vm.stopPrank();

        // surplus = 100 DAI, 50% to beneficiary, 50% to protocol
        uint256 surplus = 100 * 1e18;
        uint256 beneficiaryShare = surplus - (surplus * SURPLUS_SHARE_BPS) / 10_000;
        assertEq(
            dai.balanceOf(user),
            userDaiBefore + outputAmount + beneficiaryShare,
            "User should receive output + beneficiary surplus share"
        );
        uint256 protocolShare = (surplus * SURPLUS_SHARE_BPS) / 10_000;
        assertEq(dai.balanceOf(address(intentGateway)), protocolShare, "Gateway should hold protocol surplus share");
    }
