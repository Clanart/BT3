### Title
Unrecovered `panic()` in `MsgAggregateExchangeRateVote.GetSigners()` on malformed feeder address reachable before `ValidateBasic` - ([File: x/oracle/types/msgs.go])

### Summary
The BIND CVE-2016-8864 bug class is: an attacker-controlled field in a message is dereferenced/asserted before it has been validated, causing an unconditional crash (`assert` failure → daemon exit) instead of a graceful error. The analogous pattern in sei-chain is `GetSigners()` for `MsgAggregateExchangeRateVote` and `MsgDelegateFeedConsent`, which unconditionally calls `panic(err)` if the bech32-encoded feeder/operator address string cannot be parsed, rather than returning an error [1](#0-0) . This method can be invoked on attacker-supplied transaction bytes at points in the transaction lifecycle (e.g. mempool signer/priority extraction, tx decoding) that occur outside of, or ahead of, the `ValidateBasic` checks which normally reject invalid bech32 strings [2](#0-1) .

### Finding Description
`sdk.Msg.GetSigners()` is a standard cosmos-sdk interface method that the framework calls very early when handling an incoming transaction — during transaction decoding/signer extraction and in the mempool's priority/nonce indexing — which can occur before the ante-handler pipeline runs `ValidateBasic`. In `MsgAggregateExchangeRateVote.GetSigners()`, an invalid `msg.Feeder` bech32 string leads directly to `panic(err)` [3](#0-2) , and the equivalent `MsgDelegateFeedConsent.GetSigners()` panics identically on an invalid `msg.Operator` [4](#0-3) .

`ValidateBasic()` — the function that is supposed to catch exactly this malformed input — is a completely separate code path that only runs afterward, inside `sdk.ChainAnteDecorators`/`validateBasicTxMsgs` in `runTx` [5](#0-4) . Any earlier caller of `GetSigners()` (signer extraction for mempool ordering, priority computation, tx pre-processing, etc.) is exposed to the raw panic with no validation gate in front of it, exactly mirroring the BIND flaw where a response field (the DNAME record) reached an `assert()`/processing routine before being sanity-checked, causing the daemon to abort.

The repository's own test suite acknowledges this exact attack shape: `TestProcessProposalHandlerPanicRecovery` constructs "a malicious tx with `MsgAggregateExchangeRateVote` with invalid feeder address" specifically to probe whether `ProcessProposalHandler` panics or is protected by a recovery wrapper [6](#0-5) . Notably, the test does not assert a single expected outcome — it logs either "Precheck caught potential issue" or "Optimistic processing completed normally" / "Backup panic recovery worked correctly" — meaning the test does not conclusively prove the panic is caught in every processing path (e.g., optimistic/asynchronous execution, mempool priority ordering, CheckTx) rather than only being caught by a generic `runTx` recover.

### Impact Explanation
If `GetSigners()` panics in a code path that lacks a `recover()` wrapper (e.g., mempool signer/priority extraction on `CheckTx`, or the asynchronous "optimistic processing" pipeline referenced by the test), a single unprivileged transaction broadcast to the network can crash the node process handling it — a public-RPC-reachable denial of service, analogous to the BIND daemon-exit crash from a single malformed but reachable input. This matches the "crash of default-configuration RPC nodes" / "validator halt" impact bar since `MsgAggregateExchangeRateVote` and `MsgDelegateFeedConsent` are ordinary transaction messages any account can submit via RPC (feeder/validator authorization is enforced later in message handling, not in `GetSigners`).

### Likelihood Explanation
Crafting the malicious transaction is trivial: any string that fails `sdk.AccAddressFromBech32`/`sdk.ValAddressFromBech32` (e.g., truncated or corrupted bech32 checksum) in the `Feeder`/`Operator`/`Delegate` field triggers the panic. The existing dedicated regression test in `app/app_test.go` shows this exact scenario was already identified internally as a plausible attack, and the test's inconclusive assertions (`t.Log` rather than a strict expectation of no-panic) indicate the protection is not verified to be complete across all execution paths — only around `ProcessProposalHandler`/`runTx`.

### Recommendation
Change `GetSigners()` for `MsgAggregateExchangeRateVote` and `MsgDelegateFeedConsent` to avoid panicking on malformed input: either validate/parse defensively and return an empty/zero-value signer list on error (deferring the authoritative error to `ValidateBasic`), or ensure every caller of `GetSigners()` in the transaction lifecycle (mempool indexing, priority computation, tx decoding, `ProcessProposal`, optimistic execution) is wrapped in a `recover()` that converts the panic into a rejected transaction rather than crashing the process. Strengthen `TestProcessProposalHandlerPanicRecovery` to assert a single required outcome (no panic escapes / proposal always safely rejected) rather than logging either branch as acceptable.

### Proof of Concept
1. Construct a `MsgAggregateExchangeRateVote` with `ExchangeRates` set to any valid string, `Validator` set to a valid `sei` operator bech32 address, and `Feeder` set to a corrupted bech32 string (e.g., wrong-length or invalid checksum), matching the malicious tx bytes already embedded in `TestProcessProposalHandlerPanicRecovery` [7](#0-6) .
2. Submit this transaction to a node via the public RPC broadcast endpoint (or during block proposal handling / mempool insertion) so that `GetSigners()` is invoked before `ValidateBasic` runs.
3. Observe that `MsgAggregateExchangeRateVote.GetSigners()` panics on the bad bech32 [3](#0-2) ; if the calling context does not have an enclosing `recover()`, the node process crashes/halts.
