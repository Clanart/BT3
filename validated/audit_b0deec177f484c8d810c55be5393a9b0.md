### Title
`ThresholdKeys::new` binds the group key only to participants `1..=t`, leaving shares `t+1..=n` unchecked — an inconsistent key set can be constructed whose group key receives funds that parts of the declared participant set cannot sign for - (File: crypto/dkg/src/lib.rs)

### Summary
The source finding is an inconsistent-state guard: `setIsDeprecated` requires `isBorrowPaused` but not `isLiquidateBorrowPaused`, so a market can be locked into a state where a required operation (liquidation) is impossible. The Serai analog is in `ThresholdKeys::new`: it validates the *count* and *index range* of `verification_shares`, but derives `group_key` solely from shares `1..=t`, never checking that the shares for participants `t+1..=n` lie on a consistent polynomial — nor that `secret_share` matches `verification_shares[i]`. Untrusted bytes fed to `ThresholdKeys::read` reach this constructor directly.

### Finding Description
`ThresholdKeys::new` performs three validations:

1. `verification_shares.len() == n` [1](#0-0) 
2. every participant index `<= n` [2](#0-1) 
3. `Constant` interpolation only when `t == n` [3](#0-2) 

It then computes the group key exclusively from the first `t` participants:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
``` [4](#0-3) 

The `n - t` remaining verification shares are inserted into `core.verification_shares` without any consistency check against the group key or against each other. `ThresholdKeys::read` feeds attacker-controlled `read_G` output for all `n` shares straight into `ThresholdKeys::new` [5](#0-4) , and `secret_share` is likewise read and stored without ever being verified against `verification_shares[i]` [6](#0-5) . Meanwhile `view()` happily constructs signing views for *any* subset of size `t..=n` drawn from all `n` declared participants [7](#0-6) , so participants `t+1..=n` are treated as fully valid signers even though their shares were never bound to the group key.

This is exactly the Morpho asymmetry: the constructor checks one guard (count/index/`t..=n` bounds — analog of `isBorrowPaused`) while omitting the related guard (consistency of shares `t+1..=n` with the group key — analog of `isLiquidateBorrowPaused`), yielding an object in an internally inconsistent state.

### Impact Explanation
Two distinct verification shares maps `V` and `V'` that differ only at indexes `> t` produce **identical** `group_key` values. An attacker who supplies crafted `ThresholdKeys` bytes (via `ThresholdKeys::read`, e.g., a restored/tampered backup or any integration feeding untrusted serialized keys) can therefore instantiate a key set whose group key is valid and can receive funds, while the shares held by participants `t+1..=n` do not correspond to that key. Any signing quorum that must include such a participant produces interpolation factors against verification shares unrelated to the group key, yielding invalid partial signatures — funds credited to the group key become unspendable by the declared `n`-participant set. Because the group key is unchanged, this inconsistency is invisible to any party that only observes `group_key()`/`original_group_key()`.

### Likelihood Explanation
Reachability requires feeding attacker-influenced bytes to `ThresholdKeys::read`/`new` outside a PedPoP-verified DKG (which does verify shares). Within the scoped API surface (`ThresholdKeys::read` is explicitly listed as an untrusted-bytes sink), the missing consistency check is unconditional: nothing in `new`/`read` ever relates `secret_share` or shares `> t` to the computed `group_key`. The practical severity is Medium: impact is funds-received-but-unspendable / failed signing for affected subsets rather than key recovery or forgery, and honest DKG flows that populate the map correctly are unaffected.

### Recommendation
In `ThresholdKeys::new`, verify internal consistency of all `n` shares: check `secret_share * G == verification_shares[&params.i()]`, and verify the map forms a coherent threshold structure — e.g., confirm that the Lagrange interpolation of the submitted `verification_shares` over *every* size-`t` subset (or the full `n`-share polynomial) yields the same `group_key`, or at minimum interpolate using a subset that includes each participant `> t` once and require equality. This mirrors the recommendation to check `isLiquidateBorrowPaused` before deprecation: bind every declared participant's share to the committed group key before the key set is usable.
