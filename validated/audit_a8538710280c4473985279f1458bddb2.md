### Title
Flash/same-block stake dilution allows front-running `queueNewRewards` to steal a disproportionate share of freshly-queued rewards - ([File: rewards/BaseRewardPoolV2.sol])

### Summary
`BaseRewardPoolV2` distributes new rewards as an instantaneous lump-sum increment to `rewardPerTokenStored`, computed as `_amountReward * SCALE / totalStaked()` at the exact moment `queueNewRewards`/`donateRewards` executes, with no time-based streaming (`rewardRate`/`periodFinish`). Because reward entitlement is purely a function of `balanceOf(_account)` at checkpoint time (via `_updateFor`/`updateReward`), an attacker who inflates their staked balance in `MasterMagpie` immediately before a manager's `queueNewRewards` call, and withdraws immediately after, captures a share of that reward batch proportional to their temporary balance vs. `totalStaked()`, with zero time-weighted contribution.

### Finding Description
`_provisionReward` in `BaseRewardPoolV2.sol` updates the global index using the current `totalStaked()`: [1](#0-0) 

`_earned`/`_updateFor` only compare a user's balance against the delta of `rewardPerTokenStored` since their last checkpoint — there is no mechanism that weights this by how long the balance was actually held between checkpoints: [2](#0-1) 

`getReward` is gated by `onlyMasterMagpie` and the `updateReward(_account)` modifier, which calls `_updateFor` right before reading `userRewards`: [3](#0-2) [4](#0-3) 

`balanceOf` reads the attacker's live staked amount directly from `MasterMagpie.userInfo`: [5](#0-4) 

On the `MasterMagpie` side, `deposit`/`withdraw` have no cooldown, vesting, or minimum holding period — only `whenNotPaused nonReentrant`: [6](#0-5) 

`_deposit` checkpoints the reward pool with the OLD balance (via `_harvestBaseRewarder`) before incrementing `user.amount`, so the attacker's checkpoint (`userRewardPerTokenPaid`) is set to the pre-injection index with zero unclaimed diff: [7](#0-6) 

Exploit flow:
1. Attacker observes/front-runs the manager's pending `queueNewRewards(amount, token)` transaction in the mempool.
2. Attacker calls `MasterMagpie.deposit(stakingToken, D)` with a large `D` (self-funded or flash-borrowed), checkpointing at the pre-injection index (`userRewardPerTokenPaid = current rewardPerToken`, 0 earned so far — correct).
3. Manager's `queueNewRewards(R, token)` executes, bumping `rewardPerTokenStored` by `R*SCALE/(T0+D)` where `T0` is prior total staked.
4. Attacker triggers a claim path that routes through `getReward`/`getRewards` (via MasterMagpie's claim functions, satisfying `onlyMasterMagpie`), earning `D * R / (T0+D)` — which approaches the full reward `R` as `D >> T0`.
5. Attacker calls `MasterMagpie.withdraw(stakingToken, D)` in the same block, exiting with no lockup and no penalty.

Existing guards (`onlyManager`, `onlyMasterMagpie`, `nonReentrant`, `updateReward` checkpointing) do not prevent this because they are designed to protect against reentrancy and access-control bypass, not against time-weighting of reward accrual. The design fundamentally allocates each reward batch by "who holds how much stake at the instant of injection," not by duration held, which is the root cause.

### Impact Explanation
Long-term stakers' share of a specific reward batch is diluted by the attacker's temporary inflated balance, while the attacker extracts a disproportionate (near-100%, if capital is large enough) portion of that batch despite holding stake for effectively zero economic time. This constitutes theft of unclaimed yield from legitimate long-term stakers, matching the Immunefi impact class "theft of unclaimed yield."

### Likelihood Explanation
Feasibility depends on: (1) public mempool visibility of the manager's `queueNewRewards` transaction (reasonable on EVM chains without private relays), (2) attacker having (or flash-borrowing) enough of `stakingToken` to significantly outweigh `totalStaked()` at that block, and (3) no deposit/withdraw cooldown existing in `MasterMagpie` (confirmed absent). This is fully repeatable every time a reward is queued and is executable by any unprivileged EOA/contract with capital or flash-loan access to the specific `stakingToken`.

### Recommendation
Replace the lump-sum reward injection model with a time-streamed accrual (e.g., Synthetix-style `rewardRate`/`periodFinish` that distributes rewards linearly over a duration), or require a minimum stake-duration/cooldown before a deposit counts toward reward-earning balance, or checkpoint/snapshot `balanceOf` at the start of a reward epoch rather than using live balance at claim time.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `BaseRewardPoolV2`, staking token, and reward token; register a manager.
2. Have a "long-term staker" deposit `T0` and hold for many blocks (simulate multiple `queueNewRewards` calls to build up baseline expectations).
3. Before a new `queueNewRewards(R, token)` call, have the attacker:
   - `MasterMagpie.deposit(stakingToken, D)` with `D >> T0` in the same block.
   - Execute (or simulate front-running) the manager's `queueNewRewards(R, token)` in the same block.
   - Trigger the claim path (e.g., `multiclaimSpec`) to call `getReward`/`getRewards`.
   - `MasterMagpie.withdraw(stakingToken, D)` in the same block.
4. Assert: `attackerReward ≈ D * R / (T0 + D)`, which for large `D` approaches `R`.
5. Assert: long-term staker's `earned(token)` for that batch is reduced compared to a control run where the attacker never deposited (i.e., `longTermReward_withAttack < longTermReward_withoutAttack`), proving value transfer despite zero time held by the attacker.
6. Assert attacker's net capital cost (gas + any flash-loan fee) is less than `attackerReward`, proving net profit.
