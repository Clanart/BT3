### Title
Front-running WOM reward harvests to steal disproportionate yield via flash deposit/withdraw around `queueNewRewards()` - (File: `rewards/BaseRewardPool.sol`, `wombat/WombatStaking.sol`, `wombat/WombatPoolHelper.sol`)

### Summary
The Union `exchangeRateStored()` bug class — where a value-injecting event (repayment) instantly inflates a pro-rata accounting variable shared by all current holders, letting an attacker mint right before and redeem right after for riskless profit — has a structural analog in Magpie's `BaseRewardPool` reward-per-token accounting combined with the permissionless `harvest()`/`vote()` flow that calls `queueNewRewards()`.

### Finding Description
`BaseRewardPool._provisionReward()` distributes any newly arriving reward token pro-rata over `totalStaked()` **at the instant the reward is provisioned**: [1](#0-0) 

`rewardPerTokenStored` is bumped for the *entire* current stake, with no vesting or time-weighting — a staker who joined one block earlier gets the exact same `rewardPerToken` increase as a staker who has been in the pool for months.

The reward injection itself is triggered through unprivileged, permissionless paths:
- `WombatPoolHelper.harvest()` is a plain `external` function any wallet can call: [2](#0-1) 
- This calls `WombatStaking.harvest()` → `_toMasterWomAndSendReward()`, which eventually calls `IBaseRewardPool(_rewarders[i]).queueNewRewards(...)` (seen in the `vote()` flow, which is structurally the same reward-injection call used by harvest): [3](#0-2) 

Because deposits/withdrawals into a Magpie pool are also unprivileged (`MasterMagpie.deposit`/`withdraw`, or via `WombatPoolHelper.deposit`/`withdraw`), an attacker can:
1. Deposit a large LP/stable amount into a pool right before triggering (or observing an imminent) `harvest()`, which sets the attacker's `userRewardPerTokenPaid` to the pre-harvest `rewardPerTokenStored`.
2. Call/await `harvest()`, which pumps `rewardPerTokenStored` for the *whole* pool, including the attacker's freshly added (zero-duration) stake: [4](#0-3) 
3. Immediately claim the reward computed by `earned()`, capturing a share of the newly harvested WOM reward proportional to their capital, despite having staked for 0 economically meaningful duration.
4. Withdraw the principal right after, exiting with a risk-free profit extracted from rewards that should have accrued to genuine long-term stakers.

This mirrors the Union root cause precisely: a shared, atomically-updated accounting variable (`totalRedeemable`/`exchangeRateStored()` in Union; `rewardPerTokenStored`/`earned()` here) is inflated by a value-injecting event that any actor can predict or trigger, and the accounting gives newly-added capital the same benefit as pre-existing capital with no time-weighting or entry fee to prevent it.

### Impact Explanation
The attack directly diverts (steals) unclaimed yield that should accrue to genuine long-term LP/reward-pool stakers to a large, momentary depositor who bears essentially no holding-period risk. This is a theft of unclaimed yield from existing users, one of the accepted impact categories.

### Likelihood Explanation
Likelihood is meaningfully high: `harvest()` is callable by anyone with no cooldown or access control [2](#0-1) , deposit/withdraw functions are unprivileged, and the reward math in `_provisionReward`/`earned` has no minimum-duration or exit-fee protection to make single-block deposit/harvest/withdraw sandwiches unprofitable [1](#0-0) . The main constraint is that the attacker's deposit must be large relative to existing pool TVL and the harvested reward size must be economically worth the capital lock (even if only for 1 block), which is a standard MEV/flash-capital consideration, similar to the original Union report's PoC economics.

### Recommendation
Introduce a mechanism to make single/few-block deposit-harvest-withdraw sandwiches unprofitable, consistent with the maintainer-endorsed fix direction discussed in the original report: e.g., an exit fee (redirected to reserves/other stakers) on withdrawals occurring shortly after deposit, and/or a minimum staking duration before a deposit is eligible to receive a `queueNewRewards()` injection (update `userRewardPerTokenPaid` lazily so newly-deposited balances only start accruing from the *next* reward event rather than the currently-in-flight one).

### Proof of Concept
Conceptual sequence (mirrors the Union PoC pattern of mint→value-injection→redeem):
1. Attacker calls `MasterMagpie.deposit(stakingToken, largeAmount)` (or `WombatPoolHelper.deposit`), which stakes into the pool and syncs `userRewardPerTokenPaid[rewardToken][attacker]` to the current `rewardPerTokenStored`.
2. Attacker (or anyone) calls `WombatPoolHelper.harvest()` → `WombatStaking.harvest()` → `queueNewRewards()`, which raises `rewardPerTokenStored` for the whole pool based on `totalStaked()` that now includes the attacker's large deposit: [5](#0-4) .
3. Attacker's `earned()` now reflects a full pro-rata share of the harvested reward despite 0 real staking duration: [6](#0-5) .
4. Attacker claims rewards and calls `MasterMagpie.withdraw(stakingToken, largeAmount)` to exit with the principal intact plus the captured reward share, all within the same or adjacent block.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
```
