### Title
Stale line-index diff selection allows silent corruption of partial commits/discards via race between diff computation and patch application - ([File: app/src/lib/stores/app-store.ts])

### Summary
GitHub Desktop lets users select individual lines/hunks from a previously-rendered diff (`DiffSelection`) to build a partial commit or a partial discard. The line selections are stored as *absolute indices into the diff text that was rendered earlier*, not tied to any content hash or generation of the diff. `createCommit`/`stageFiles`/`applyPatchToIndex` and `discardChangesFromSelection` both regenerate a unified patch from this stale `DiffSelection` object against whatever diff object is handed to them [1](#0-0) [2](#0-1) [3](#0-2) . The code that keeps the selection in sync with a re-loaded diff explicitly acknowledges this is only a partial fix: it only prunes lines that no longer exist, but does not verify that surviving indices still refer to the same underlying content [4](#0-3) .

### Finding Description
`formatPatch` and `formatPatchToDiscardChanges` walk `diff.hunks[*].lines` and decide whether to include each line by calling `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex = hunk.unifiedDiffStart + lineIndex` [5](#0-4) [6](#0-5) . `DiffSelection` is a bare set of numeric line indices with no notion of file content, hash, or diff generation — it only tracks "selectable lines" derived from whichever diff was last supplied to `withSelectableLines` [7](#0-6) .

When the working directory diff is refreshed (e.g. because the underlying file changed on disk), `updateChangesWorkingDirectoryDiff` updates `selectableLines` from the *new* diff but keeps the *same* `divergingLines` (the actual selected line numbers) from the *old* selection. The comment in the code says explicitly:

> "The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines..." [8](#0-7) 

This means: if a line index happens to still be "selectable" in the new diff (i.e., some other addition/deletion line exists at that same absolute offset), the stale index is treated as still selected — even though it now points to a semantically different line (different content) than the one the user actually clicked. The broken invariant is: *the index recorded in `DiffSelection` is assumed to still identify the same line of content the user selected, but nothing enforces that after the diff is reloaded.*

An attacker who controls the content of a cloned/fetched repository (or supplies content that gets written to the working tree via a git filter/hook/merge driver/checkout that Desktop is executing on the user's behalf) can shape a file so that, after a routine file-system change that Desktop reacts to (e.g. a checkout, stash pop, merge, or any operation that mutates tracked files and triggers a status/diff refresh while the Changes view is open with a partial selection), the hunk layout shifts but the total count/position of "includeable" lines at the previously-selected absolute indices happens to line up with different, attacker-planted lines. When the user then commits their previously-checked lines (`_commitIncludedChanges`/`createCommit` → `stageFiles` → `applyPatchToIndex` → `formatPatch`) or discards their selection (`_discardChangesFromSelection` → `discardChangesFromSelection` → `formatPatchToDiscardChanges`), the resulting patch is built against the new diff using the old, now-misaligned indices [9](#0-8) [10](#0-9) . The result silently committed (or discarded) is not the content the user actually reviewed and checked in the UI.

Existing guards do not stop this: `updateChangesWorkingDirectoryDiff` only filters `selectableLines` (drops indices that no longer correspond to *any* includeable line) — it never re-validates that a surviving index still maps to the *same textual content* it did when selected, and no content hash/version tag is attached to `DiffSelection` or checked before `formatPatch`/`formatPatchToDiscardChanges` runs [11](#0-10) [12](#0-11) .

### Impact Explanation
If exploited, this results in silent corruption of what the user commits or discards without any prompt or diff confirmation — the user believes they are staging/discarding the lines they visually reviewed, but git applies a patch computed against different, attacker-influenced content. This can be used to sneak unreviewed/malicious lines into a commit that later gets pushed, or to make a user unknowingly discard changes they intended to keep. Because it corrupts the integrity of what a developer commits and pushes (potentially into a shared/production repository), this matches the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Exploitation requires: (1) the victim to have a partially-selected diff open in the Changes view, and (2) the working tree content for that file to change between the original diff load and the moment the user acts on their earlier selection (e.g., via checkout, merge, stash apply, or a smudge/clean filter triggered by a Desktop-initiated git operation on attacker-supplied repository content), such that the line-count/position alignment coincidentally (or by attacker design) preserves selectability at the old indices while changing content. This is a real but narrow race/timing-and-content-crafting condition — feasible for a determined attacker shaping repository content and hooks, but not trivially reliable, hence Medium likelihood, consistent with the acknowledged-but-unaddressed nature of the code comment.

### Recommendation
Tie `DiffSelection` to the content/version of the diff it was computed against (e.g., a diff hash or generation counter) and invalidate/clear the entire partial selection whenever the underlying diff changes in a way that could shift line semantics, rather than only pruning indices that are no longer selectable. Alternatively, before applying `formatPatch`/`formatPatchToDiscardChanges`, re-diff the file and abort (surfacing an error/refresh prompt) if the diff used to build the patch does not exactly match the diff currently backing the file's on-disk content.

### Proof of Concept
Conceptual sequence (not verified against a live build within this session — see caveat below):
1. Attacker crafts a repository/branch such that checking it out, merging it, or applying a stash leaves a tracked file with a specific number and arrangement of add/delete lines.
2. Victim opens the Changes view for that file, partially selects a subset of lines (e.g., 3 additions across 2 hunks) via `withRangeSelection`/`withLineSelection` [13](#0-12) .
3. Before the victim clicks "Commit"/"Discard", a background git operation Desktop performs on the attacker's behalf (checkout, pull, merge, stash pop) rewrites the file so hunk boundaries shift but the same absolute line indices remain "includeable" per `withSelectableLines` [4](#0-3) .
4. Victim commits/discards using the stale selection; `formatPatch`/`formatPatchToDiscardChanges` build the patch from the *new* diff content at the *old* indices [14](#0-13) [15](#0-14) , silently including/excluding different lines than the ones the user visually checked.

**Caveat:** I was not able to run this end-to-end in a test harness within the available tool budget; the analysis is based on static code review of `patch-formatter.ts`, `diff-selection.ts`, `apply.ts`, `update-index.ts`, and `app-store.ts`, and on the explicit acknowledgment in the code comment that selection validity after a diff reload is not fully checked. A background Devin session with repository access could build a concrete reproduction (e.g., a unit test driving `updateChangedFiles`/`updateChangesWorkingDirectoryDiff` with a crafted before/after diff pair) to confirm the exact conditions under which stale indices remain "selectable" against different content.

  const deletedFiles = []

      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }

export async function applyPatchToIndex(
  repository: Repository,
  file: WorkingDirectoryFileChange
): Promise<void> {
  // If the file was a rename we have to recreate that rename since we've
  // just blown away the index. Think of this block of weird looking commands
  // as running `git mv`.
  if (file.status.kind === AppFileStatusKind.Renamed) {
    // Make sure the index knows of the removed file. We could use
    // update-index --force-remove here but we're not since it's
    // possible that someone staged a rename and then recreated the
    // original file and we don't have any guarantees for in which order
    // partial stages vs full-file stages happen. By using git add the
    // worst that could happen is that we re-stage a file already staged
    // by updateIndex.
    await git(
      ['add', '--update', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    // Figure out the blob oid of the removed file
    // <mode> SP <type> SP <object> TAB <file>
    const oldFile = await git(
      ['ls-tree', 'HEAD', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    const [info] = oldFile.stdout.split('\t', 1)
    const [mode, , oid] = info.split(' ', 3)

    // Add the old file blob to the index under the new name
    await git(
      ['update-index', '--add', '--cacheinfo', mode, oid, file.path],
      repository.path,
      'applyPatchToIndex'
    )
  }

  const applyArgs: string[] = [
    'apply',
    '--cached',
    '--unidiff-zero',
    '--whitespace=nowarn',
    '-',
  ]

  const diff = await getWorkingDirectoryDiff(repository, file)

  if (diff.kind !== DiffType.Text && diff.kind !== DiffType.LargeText) {
    const { kind } = diff
    switch (diff.kind) {
      case DiffType.Binary:
      case DiffType.Submodule:
      case DiffType.Image:
        throw new Error(
          `Can't create partial commit in binary file: ${file.path}`
        )
      case DiffType.Unrenderable:
        throw new Error(
          `File diff is too large to generate a partial commit: ${file.path}`
        )
      default:
        assertNever(diff, `Unknown diff kind: ${kind}`)
    }
  }

  const patch = await formatPatch(file, diff)
  await git(applyArgs, repository.path, 'applyPatchToIndex', { stdin: patch })

  return Promise.resolve()
}

  public withRangeSelection(
    from: number,
    length: number,
    selected: boolean

    const computedSelectionType = this.getSelectionType()
    const to = from + length

    // Nothing for us to do here. This state is when all lines are already
    // selected and we're being asked to select more or when no lines are
    // selected and we're being asked to unselect something.
    if (typeMatchesSelection(computedSelectionType, selected)) {
      return this

export async function createCommit(
  repository: Repository,
  message: string,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  options?: {
    amend?: boolean
    noVerify?: boolean
    signOff?: boolean
    allowEmpty?: boolean
  } & HookCallbackOptions
): Promise<string> {
  // Clear the staging area, our diffs reflect the difference between the
  // working directory and the last commit (if any) so our commits should
  // do the same thing.
  await unstageAll(repository)

  await stageFiles(repository, files)

  const args = ['-F', '-']

  if (options?.amend) {
    args.push('--amend')
  }

  if (options?.noVerify) {
    args.push('--no-verify')
  }

  if (options?.signOff) {
    args.push('--signoff')
  }

  if (options?.allowEmpty) {
    args.push('--allow-empty')
  }

  const result = await git(
    ['commit', ...args],
    repository.path,
    'createCommit',
    {
      stdin: message,
      // https://git-scm.com/docs/githooks/2.46.1
      interceptHooks: [
        'pre-commit',
        'prepare-commit-msg',
        'commit-msg',
        'post-commit',
        ...(options?.amend ? ['post-rewrite'] : []),
        'pre-auto-gc',
      ],
      onHookProgress: options?.onHookProgress,
      onHookFailure: options?.onHookFailure,
      onTerminalOutputAvailable: options?.onTerminalOutputAvailable,
    }
  )
  return parseCommitSHA(result)
}
