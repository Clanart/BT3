### Title
Fee-on-transfer / rebasing LP tokens break accounting in `WombatStaking.depositLP` and reward accounting in `BaseRewardPool._provisionReward` - ([File: wombat/WombatStaking.sol], [File: rewards/BaseRewardPool.sol])

### Summary
`WombatStaking.deposit()` correctly measures the LP tokens actually received by comparing balances before and after the external pool interaction, but the sibling entry point `WombatStaking.depositLP()` and the reward-provisioning helper `BaseRewardPool._provisionReward()` / `BaseRewardPoolV2._provisionReward()` trust the caller-supplied amount parameter instead of the balance actually received via `safeTransferFrom`.

### Finding Description
In `wombat/WombatStaking.sol`, `deposit()` computes the LP actually received: [1](#0-0) 
mints the receipt token based on that measured `lpReceived` value.

By contrast, `depositLP()`, reachable by any ordinary user through a pool helper (`WombatPoolHelper.depositLP`, `WombatPoolHelperV2.depositLP`, `AnkrBNBPoolHelper.depositLP`), transfers the LP token with `safeTransferFrom` but then uses the raw, caller-specified `_lpAmount` both to route funds into MasterWombat (`_toMasterWomAndSendReward`) and to mint the receipt token: [2](#0-1) 

If the underlying `lpAddress` token is deflationary/fee-on-transfer, the amount actually received by `WombatStaking` is smaller than `_lpAmount`, yet the receipt token is minted 1:1 with `_lpAmount`, over-minting receipt tokens not backed by real LP token custody.

Separately, `BaseRewardPool._provisionReward` (and the `V2` equivalent) also pulls `_amountReward` via `safeTransferFrom` but credits the pool's `rewardPerTokenStored`/`historicalRewards` using the full stated `_amountReward`, not the balance delta: [3](#0-2) [4](#0-3) 

If a deflationary/fee-on-transfer token is registered/used as a reward token (via `queueNewRewards` from `WombatStaking` fee routing, or via the permissionless `donateRewards`), the pool promises payouts based on the stated amount while holding fewer actual tokens, meaning some stakers' accrued and claimable rewards for that token cannot be paid out.

### Impact Explanation
For `depositLP`: over-minting receipt tokens beyond actual LP custody creates a shortfall — later withdrawers of that LP token/pool would be unable to fully redeem, resulting in protocol insolvency for that pool's LP holdings.

For `_provisionReward`: any user can call the permissionless `donateRewards(uint256, address)` function on `BaseRewardPool`/`BaseRewardPoolV2` with an already-registered reward token. If that reward token is fee-on-transfer/deflationary, `rewardPerTokenStored` is inflated beyond the reward tokens actually held by the pool, causing the pool to become unable to pay out already-accrued rewards to some stakers — a permanent freeze/loss of unclaimed yield for those users.

### Likelihood Explanation
Likelihood depends on whether an affected LP token or reward token is deflationary/rebasing. Reward tokens are more likely to be a broader, less-curated set (bribe reward tokens flow through `vote()`/`_toMasterWomAndSendReward` into `queueNewRewards`, and `donateRewards` is fully permissionless for anyone holding a registered reward token), so this path is reachable without any privileged action — any ordinary wallet holding a deflationary ERC20 that is already a registered reward token can call `donateRewards` and corrupt the pool's internal accounting for that token.

### Recommendation
In `WombatStaking.depositLP`, measure the LP balance delta before/after `safeTransferFrom` (as already done in `deposit()`) and use that measured amount for minting the receipt token and for `_toMasterWomAndSendReward`. In `BaseRewardPool`/`BaseRewardPoolV2._provisionReward`, compute the actual balance delta received via `safeTransferFrom` and use that value (instead of the caller-supplied `_amountReward`) when updating `historicalRewards` and `rewardPerTokenStored`.

### Proof of Concept
1. A reward token `T` is registered as a reward token on some `BaseRewardPool` (e.g., via a prior `queueNewRewards` call from `WombatStaking`), and `T` charges a transfer fee (deflationary behavior).
2. Any user calls `BaseRewardPool.donateRewards(1000, T)`. `_provisionReward` pulls tokens via `safeTransferFrom(msg.sender, address(this), 1000)`, but the pool only actually receives, say, 950 `T` due to the fee.
3. `rewardInfo.rewardPerTokenStored` is incremented using the full `1000` amount, over-crediting all current stakers' claimable `T` rewards by an amount the contract does not hold.
4. When stakers later call the claim path and `_sendReward` executes `IERC20(T).safeTransfer(_receiver, _amount)` for the inflated `_amount`, the pool will run out of actual `T` balance before all accrued claims can be paid, permanently freezing the unclaimed yield for the remaining stakers.
