### Title
Silent remote-URL rewrite based on unauthenticated GitHub API `clone_url` field, without verifying repository identity - (`app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically rewrites a repository's `origin` remote to whatever `clone_url` the GitHub API currently reports for the associated `GitHubRepository`, as long as the protocol matches and the previously-stored clone URL still matches the remote. The decision to trust and apply this update relies solely on structural comparison of URLs (`urlMatchesRemote`/`parseRemote`, comparing hostname/owner/name case-insensitively) — it never re-validates that the "updated" `clone_url` still refers to the same underlying repository (e.g., by repository ID). This mirrors the oracle bug's core flaw: a value from an external, mutable source is trusted for a security-relevant decision without an invariant check (staleness/identity) that would catch a value that has silently changed to something attacker-influenced.

### Finding Description
`updateRemoteUrl` is invoked with the `apiRepo` object fetched live from the GitHub API for a repository the user already has cloned: [1](#0-0) 

The logic is:
1. Take `gitStore.defaultRemote.url` (the current, on-disk remote).
2. Take `apiRepo.clone_url` (a fresh value from the GitHub API).
3. Confirm protocols match (`URL.parse(...).protocol`).
4. Confirm the *current* remote structurally still matches the *previously cached* `gitHubRepository.cloneURL` (`remoteUrlUnchanged`), via `urlMatchesRemote`.
5. If the current remote no longer structurally matches the fresh `apiRepo.clone_url` (`!urlsMatch`), silently call `gitStore.setRemoteURL(...)` to point `origin` at the new URL.

`urlMatchesRemote` (and the underlying `parseRemote`) only compares `hostname`, `owner`, and `name` as parsed strings — it never checks a persistent identifier such as the GitHub repository's numeric ID: [2](#0-1) 

Because the check is purely structural/string-based and keyed off values returned by the API for a given `GitHubRepository` record (looked up by `endpoint`), there is no cross-check that the "updated" `clone_url` genuinely still identifies the same GitHub repository object the user originally added. If the API ever returns a different `clone_url` string for that stored `GitHubRepository` entity — through repository rename/transfer race conditions, a compromised/malicious GitHub Enterprise Server endpoint, or a man-in-the-middle on that endpoint's API traffic — Desktop will automatically and silently retarget `origin` to the new host/owner/name, with no user confirmation dialog.

This is structurally the same failure mode as the reported Chainlink `verifyPrice` bug: a value pulled from an external, non-atomic source (`latestAnswer()` vs. `apiRepo.clone_url`) is trusted for a trust/security decision using only a coarse comparison (percentage delta vs. structural URL match) instead of validating an authoritative invariant (round freshness vs. repository ID).

### Impact Explanation
Once `origin` is silently repointed, subsequent `git push`/`git fetch`/`git pull` operations use the new URL via `envForRemoteOperation(remote.url)`: [3](#0-2) [4](#0-3) 

This can silently redirect the user's pushes (code, credentials via the credential helper for that host, LFS objects) to an attacker-controlled endpoint, or cause the user to unknowingly fetch/merge content from a different repository the next time they sync — corrupting what the user believes they are pushing/pulling without any visible warning. This satisfies "silent corruption of what the user commits or pushes" / "credential exfiltration" in the valid-impact criteria, driven purely by a GitHub API response Desktop trusts (an in-scope attacker-controlled object per the task's valid-impact list).

### Likelihood Explanation
Exploitability depends on an attacker's ability to control what `clone_url` the GitHub API endpoint returns for the stored `GitHubRepository` record — most plausibly via a malicious/compromised GitHub Enterprise Server the victim is signed into (an explicitly in-scope primitive: "a GitHub API object"), or a repository-transfer/rename race on GitHub.com. This requires no local access, no admin rights, and no unusual user action beyond Desktop's normal background repository refresh. I could not fully trace, within the remaining iterations, the exact call site in `app-store.ts` that triggers `updateRemoteUrl` (e.g., whether it runs on every background API refresh or only after explicit user action), so the precise trigger frequency/timing is unconfirmed and should be verified in a live session.

### Recommendation
Before rewriting the remote URL, verify the fresh `apiRepo` still refers to the same repository identity that `gitHubRepository` represents — e.g., compare `apiRepo.id`/`node_id` (or the persistent repository ID already stored on `GitHubRepository`) rather than relying solely on structural URL matching. If the ID doesn't match, refuse the update and require the user to explicitly confirm changing the remote (similar to how a stale/mismatched oracle round should cause a revert rather than a silent accept).

### Proof of Concept
1. User clones a GitHub-hosted (or GHE-hosted) repository into Desktop; `origin` and the cached `GitHubRepository.cloneURL` both point to `https://host/owner/repo`.
2. The GitHub API endpoint (attacker-controlled GHE, or a race during a legitimate rename) subsequently returns `clone_url: "https://host/attacker/repo"` for the same repository record when Desktop performs its routine background refresh.
3. `updateRemoteUrl` sees: protocol matches, `remoteUrlUnchanged` is true (nothing else changed it), and `urlsMatch` is false → it calls `gitStore.setRemoteURL('origin', 'https://host/attacker/repo')` silently.
4. On the user's next push, `push()` executes against `https://host/attacker/repo` via `envForRemoteOperation(remote.url)`, sending code/credentials to the attacker-controlled destination with no warning shown to the user.

Note: I was not able to fully confirm the exact call sites/frequency of `updateRemoteUrl` invocation from `app-store.ts` due to iteration limits; a full Devin session with repository access would be needed to trace that trigger path precisely.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
