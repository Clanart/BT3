### Title
Missing balance-sufficiency validation for KIP-160 treasury rebalance allows unauthorized supply inflation - (File: blockchain/system/rebalance.go)

### Summary
`RebalanceTreasury` in `blockchain/system/rebalance.go` implements the automatic, hard-fork-triggered treasury reallocation for both KIP-103 (legacy) and KIP-160 (`TreasuryRebalanceV2`) mechanisms. Before executing the reallocation, the code checks that the total balance being removed from "zeroed" addresses is at least as large as the total balance being allocated to "newbie" addresses — but this check is gated behind `isKIP103` only, and is silently skipped for the KIP-160 path.

### Finding Description
`RebalanceTreasury` retrieves the zeroed (to-be-cleared) accounts and their current balances, and the allocated (newbie) accounts with their target balances: [1](#0-0) 

It then performs a sanity check meant to guarantee the reallocation cannot mint tokens beyond what is actually removed from the zeroed accounts: [2](#0-1) 

```go
totalZeroedAmount := result.totalZeroedBalance()
totalAllocatedAmount := result.totalAllocatedBalance()
if isKIP103 && totalZeroedAmount.Cmp(totalAllocatedAmount) < 0 {
    return result, ErrRebalanceNotEnoughBalance
}
```

This condition is `isKIP103 && ...`, meaning when `isKIP160` is true (and `isKIP103` false), the guard is entirely bypassed. Execution then proceeds unconditionally to zero out the zeroed accounts and set the allocated accounts to the amounts defined by the (governance-approved) `TreasuryRebalanceV2` contract: [3](#0-2) 

```go
for addr := range result.Before.Zeroed {
    state.SetBalance(addr, big.NewInt(0))
    ...
}
for addr, balance := range result.After.Allocated {
    currentBalance := state.GetBalance(addr)
    result.Burnt.Add(result.Burnt, currentBalance)
    state.SetBalance(addr, balance)
}
remainder := new(big.Int).Sub(totalZeroedAmount, totalAllocatedAmount)
result.Burnt.Add(result.Burnt, remainder)
```

If, for the KIP-160 path, `totalAllocatedAmount` exceeds `totalZeroedAmount` (e.g., due to a misconfigured or malicious `TreasuryRebalanceV2` contract state, an off-by-one/rounding error in contract-side accounting, or a bug allowing an allocation to be added without a corresponding sufficiently-large zeroed balance), `remainder` becomes negative. The code unconditionally sets every "allocated" account's balance to the (unchecked) target amount via `state.SetBalance`, which directly creates new KAIA balance in state that was never backed by a corresponding removal from the zeroed accounts. This is precisely the same bug class as the reported `resistantBalanceAndFei` issue: a value (the "amount to be created/allocated") is computed and applied without being reconciled against the amount actually removed, so the two quantities — funds removed vs. funds allocated — are not enforced to be consistent at the point of execution, unlike the (correct) KIP-103 path where this consistency is explicitly checked.

### Impact Explanation
`RebalanceTreasury` directly mutates account balances via `state.SetBalance`, which is consensus state — a discrepancy here is not a wallet/estimation bug but an actual unauthorized creation of native KAIA supply for the "newbie" addresses beyond what was removed from "zeroed" addresses. This corresponds exactly to the "supply inflation" impact category explicitly listed as acceptable for this analog: the total native-token supply invariant tracked by `kaiax/supply` (`kaiax/supply/impl/getter.go`, which itself references `Kip160ContractAddress`/`IsKIP160ForkBlock` to compute total supply) would become desynchronized from the actual minted/burnt accounting, and honest nodes computing total supply or verifying the KIP-160 rebalance would derive an incorrect (inflated) figure with no way to detect it from this code path alone.

### Likelihood Explanation
The KIP-160 rebalance is a rare, governance-gated, hard-fork-scheduled event, and in the honest/expected case the `TreasuryRebalanceV2` contract's approval process (`Status == 2`, `CheckZeroedsApproved`) should already guarantee `totalAllocatedAmount <= totalZeroedAmount`. However, this Go-side code is the last line of defense enforced by every node during block processing/state transition, and the report's bug class is specifically about the absence of an *enforced* consistency guarantee between the value removed and value created — here that enforcement exists for KIP-103 but is explicitly missing for KIP-160. Any bug, misconfiguration, or intentional manipulation in the on-chain `TreasuryRebalanceV2` contract's approved allocation set (which this Go code trusts blindly for KIP-160) would translate directly into unchecked, permanent, protocol-level token creation with no independent safety net in the client code.

### Recommendation
Remove the `isKIP103 &&` restriction so the `totalZeroedAmount.Cmp(totalAllocatedAmount) < 0` guard (or an equivalent invariant check) is enforced for both KIP-103 and KIP-160 paths, ensuring the rebalance can never allocate more KAIA than it removes, consistent with how the "consumed" and "created" values are validated elsewhere in the function.

### Proof of Concept
Not independently executable from the index alone (requires deploying/approving a `TreasuryRebalanceV2` contract instance with `Allocateds` summing to more than `Zeroeds`' current balances and advancing to the configured `RebalanceBlockNumber` under a KIP-160-enabled chain config). Conceptually:
1. Deploy `TreasuryRebalanceV2` at `chain.Config().Kip160ContractAddress`, register one or more "zeroed" addresses with small balances and one or more "allocated" addresses with a much larger target balance sum.
2. Complete the contract's approval workflow so `Status(nil) == 2` and `CheckZeroedsApproved` passes.
3. Reach the configured `RebalanceBlockNumber` under `chain.Config().IsKIP160ForkBlock(header.Number) == true`.
4. Observe in `RebalanceTreasury` (`blockchain/system/rebalance.go:300-325`) that the `totalZeroedAmount < totalAllocatedAmount` guard is skipped (since `isKIP103` is false), and the allocated accounts receive balances via `state.SetBalance` exceeding what was removed from zeroed accounts, inflating total native token supply. func (result *rebalanceResult) fillZeroed(contract RebalanceCaller, state *state.StateDB) error {
	numRetiredBigInt, err := contract.GetZeroedCount(nil)
	if err != nil {
		logger.Error("Failed to get ZeroedCount from TreasuryRebalance contract", "err", err)
		return err
	}

	for i := 0; i < int(numRetiredBigInt.Int64()); i++ {
		ret, err := contract.Zeroeds(nil, big.NewInt(int64(i)))
		if err != nil {
			logger.Error("Failed to get Zeroeds from TreasuryRebalance contract", "err", err)
			return err
		}
		result.Before.Zeroed[ret] = state.GetBalance(ret)
		result.After.Zeroed[ret] = state.GetBalance(ret) // will be set as zero if rebalance succeeds
	}
	return nil
}

func (result *rebalanceResult) fillAllocated(contract RebalanceCaller, state *state.StateDB) error {
	numNewbieBigInt, err := contract.GetAllocatedCount(nil)
	if err != nil {
		logger.Error("Failed to get AllocatedCount from TreasuryRebalance contract", "err", err)
		return nil
	}

	for i := 0; i < int(numNewbieBigInt.Int64()); i++ {
		ret, err := contract.Allocateds(nil, big.NewInt(int64(i)))
		if err != nil {
			logger.Error("Failed to get Allocateds from TreasuryRebalance contract", "err", err)
			return err
		}

		result.Before.Allocated[ret.Addr] = state.GetBalance(ret.Addr)
		result.After.Allocated[ret.Addr] = ret.Amount
	}
	return nil
}

// RebalanceTreasury reads data from a contract, validates stored values, and executes treasury rebalancing (KIP-103, KIP-160).
// It can change the global state by removing old treasury balances and allocating new treasury balances.
// The new allocation can be larger than the removed amount, and the difference between two amounts will be burnt.
func RebalanceTreasury(state *state.StateDB, chain backends.BlockChainForCaller, header *types.Header) (*rebalanceResult, error) {
	var (
		err    error
		caller RebalanceCaller

		result   = newRebalanceReceipt()
		isKIP160 = chain.Config().IsKIP160ForkBlock(header.Number)
		isKIP103 = chain.Config().IsKIP103ForkBlock(header.Number)
	)

	if isKIP160 {
		caller, err = rebalance.NewTreasuryRebalanceV2Caller(chain.Config().Kip160ContractAddress, backends.NewBlockchainContractBackend(chain, nil, nil))
	} else if isKIP103 {
		caller, err = NewKip103ContractCaller(state, chain, header)
	} else {
		return nil, errors.New("rebalancing shouldn't be executed unless the block number is kip103 or kip160 hard fork")
	}
	if err != nil {
		return nil, err
	}

	// Retrieve 1) Get Zeroed
	if err = result.fillZeroed(caller, state); err != nil {
		return result, err
	}

	// Retrieve 2) Get Allocated
	if err = result.fillAllocated(caller, state); err != nil {
		return result, err
	}

	// Validation 1) Check the target block number
	if blockNum, err := caller.RebalanceBlockNumber(nil); err != nil || blockNum.Cmp(header.Number) != 0 {
		return result, ErrRebalanceIncorrectBlock
	}

	// Validation 2) Check whether status is approved. It should be 2 meaning approved
	if status, err := caller.Status(nil); err != nil || status != 2 {
		return result, ErrRebalanceBadStatus
	}

	// Validation 3) Check approvals from zeroeds
	if err = caller.CheckZeroedsApproved(nil); err != nil {
		return result, err
	}

	// Validation 4) Check the total balance of zeroeds are bigger than the distributing amount
	totalZeroedAmount := result.totalZeroedBalance()
	totalAllocatedAmount := result.totalAllocatedBalance()
	if isKIP103 && totalZeroedAmount.Cmp(totalAllocatedAmount) < 0 {
		return result, ErrRebalanceNotEnoughBalance
	}

	// Execution 1) Clear all balances of zeroeds
	for addr := range result.Before.Zeroed {
		state.SetBalance(addr, big.NewInt(0))
		result.After.Zeroed[addr] = big.NewInt(0)
	}
	// Execution 2) Distribute KAIA to all allocateds
	for addr, balance := range result.After.Allocated {
		// if an allocated has KAIA before the allocation, it will be burnt
		currentBalance := state.GetBalance(addr)
		result.Burnt.Add(result.Burnt, currentBalance)

		state.SetBalance(addr, balance)
	}

	// Fill the remaining fields of the result
	remainder := new(big.Int).Sub(totalZeroedAmount, totalAllocatedAmount)
	result.Burnt.Add(result.Burnt, remainder)
	result.Success = true
	return result, nil
}
