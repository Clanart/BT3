### Title
ReDoS in hookify `compile_regex`/`_regex_match` lets an attacker-crafted rule + input hang the PreToolUse hook until timeout, causing the block decision to be dropped as a "non-blocking error" - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._regex_match` compiles attacker-supplied regex patterns from `.claude/hookify.*.local.md` rule files with `re.compile`/`re.search`, with no complexity limits or evaluation timeout. A catastrophic-backtracking pattern (e.g. `(a+)+b`) combined with an attacker-influenced long non-matching string (e.g. a long `command`/`file_path`) can make `re.search` hang for far longer than the hook's configured timeout, causing the PreToolUse hook process to be killed by the timeout wrapper and its (never-produced) deny decision to be lost.

### Finding Description
`compile_regex` simply does `re.compile(pattern, re.IGNORECASE)` and is called from `_regex_match`, which then calls `regex.search(text)` with no bound on backtracking or wall-clock time. [1](#0-0) [2](#0-1) 

The pattern comes straight from a rule file's frontmatter `pattern`/`conditions` field with no sanitization or complexity check, and the matched text comes from `tool_input` fields such as `command` or `file_path` for `Bash`/`Edit`/`Write` tools — both attacker-influenceable if the attacker can (a) get a malicious rule file merged into `.claude/hookify.*.local.md`, and (b) control the string an eventual PR/automation feeds into a matching tool call. [3](#0-2) 

The hook is wired with an explicit 10-second timeout in `hooks.json` (not the 60s claimed in the question, but the same class of issue applies): [4](#0-3) 

Per the hook-development documentation shipped in this same repo, hook exit codes are interpreted as: `0` success, `2` blocking error, and any other code (which includes the `124` timeout exit code from the `timeout` wrapper) is treated as a **non-blocking error**: [5](#0-4) 

This means that if `pretooluse.py` hangs inside `compile_regex(...).search(...)` past the timeout, it is killed before it can print its JSON `deny` decision and exit 0/2, and the resulting non-zero/timeout exit is classified as non-blocking — i.e., the tool call proceeds as if no rule matched, even though a `block` rule would otherwise have fired. The script's own `finally: sys.exit(0)` only helps in the non-hang path; a true regex hang bypasses that safety net entirely because the process is killed externally by the timeout wrapper, not exited voluntarily. [6](#0-5) 

### Impact Explanation
This is a fail-open bypass of a user-configured hookify `block` rule (e.g. a rule meant to stop `rm -rf`, credential exfiltration commands, etc.) for `Bash`/`Edit`/`Write`/`MultiEdit` tool calls. An attacker who can get a malicious rule shipped (or a benign-looking rule that happens to contain catastrophic backtracking) merged into the repo's `.claude/hookify.*.local.md`, and who can also control the length/shape of the matched field (command string, file path, edit content) in a later tool invocation, can force the PreToolUse block check to time out and be silently discarded, allowing an otherwise-blocked destructive operation to execute. This matches "deny means deny" bypass impact scoped to hookify's block enforcement.

### Likelihood Explanation
Requires two preconditions that are both plausible via ordinary contribution flow: (1) a hookify rule file with a vulnerable regex is added to the repo (via a merged PR — normal review may miss a subtle ReDoS pattern), and (2) the attacker (or unwitting automation) later supplies a long string into the field the rule inspects. Python's `re` engine has no built-in backtracking limits, so classic patterns like `(a+)+b`, `(a|aa)+b`, `(.*)+` reliably trigger exponential-time behavior on crafted non-matching strings. This is straightforward to reproduce deterministically with a unit/fuzz test.

### Recommendation
- Enforce a hard evaluation timeout per regex match (e.g. run `regex.search` in a subprocess/thread with a strict deadline, or use `regex` module's timeout support, or a linear-time engine such as Google's `re2`).
- Fail closed on internal timeout/exception during rule evaluation for `block`-action rules (i.e., if evaluation cannot complete, treat as a match/deny rather than allow) rather than the current global "any error → allow" behavior in `pretooluse.py`'s `except`/`finally` block.
- Add static ReDoS detection (e.g. via a regex complexity linter) when loading rule files, rejecting or flagging patterns with nested unbounded quantifiers.
- Cap the length of fields fed to `_regex_match` (e.g. truncate extremely long `command`/`content` values) as defense in depth.

### Proof of Concept
Unit/fuzz test for `plugins/hookify/core/rule_engine.py`:
```python
import time
from hookify.core.rule_engine import RuleEngine
from hookify.core.config_loader import Rule, Condition

rule = Rule(
    name="evil-redos",
    enabled=True,
    event="bash",
    action="block",
    conditions=[Condition(field="command", operator="regex_match", pattern=r"(a+)+b")],
    message="blocked"
)
engine = RuleEngine()
payload = "a" * 40 + "!"  # non-matching, triggers catastrophic backtracking
input_data = {"tool_name": "Bash", "tool_input": {"command": payload}}

start = time.time()
result = engine.evaluate_rules([rule], input_data)
elapsed = time.time() - start

# Expected (secure) behavior: evaluation completes within hook timeout budget (<10s)
# and/or fails closed (returns a deny) rather than hanging/being killed externally.
assert elapsed < 10, f"Regex evaluation exceeded hook timeout budget: {elapsed}s"
```
Run this with increasing payload lengths (e.g. 20, 30, 40, 50 'a's) to demonstrate exponential blow-up, and separately simulate the full hook path (`hooks/pretooluse.py` invoked via `timeout 10 python3 pretooluse.py < payload.json`) to confirm exit code `124` and that the JSON deny decision is never emitted, proving the fail-open bypass end-to-end.

```python
    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
```
