### Title
Deterministic cached FROST preprocess is reused across distinct `share`/`complete` calls that may sign different `set_keys_message` payloads, enabling nonce reuse and secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The upstream bug class: a feature path (intra-host migration) accepts a VM variant (SNP) whose security-critical state cannot be transferred, instead of rejecting it. The analog in Serai: `CachedPreprocess`/`from_cache` reconstructs a FROST signing machine purely from a cached RNG seed, so *all* signing state — nonces, commitments, addendum — is deterministically regenerated, but the per-call inputs (`msg`, preprocess map, `key_pair`) are not bound to or burned with the cache. `DkgConfirmer::share` and `DkgConfirmer::complete` each rebuild the machine from the same cached seed under context `(b"DkgConfirmer", attempt)` and sign a message assembled per-call; nothing rejects a second call carrying a different message, so the same nonce can sign two messages and the secret share is recoverable.

### Finding Description
In `SigningProtocol::preprocess_internal` (coordinator/src/tributary/signing_protocol.rs:100-148), a preprocess is generated once, its 32-byte seed is XOR-encrypted and stored under `CachedPreprocesses::set(txn, &self.context, ...)`, and every subsequent call under the same `context` decrypts the same seed and calls `AlgorithmSignMachine::from_cache`, which re-derives identical nonces via `seeded_preprocess` (`ChaCha20Rng::from_seed(*seed.0)`, crypto/frost/src/sign.rs:121-144). The cache is never deleted or marked consumed after `share_internal` runs.

For `DkgConfirmer`, `context = (b"DkgConfirmer", self.attempt)` (signing_protocol.rs:274-277), so all calls within an attempt share one seed. `DkgConfirmer::share` (line 304) and `DkgConfirmer::complete` (line 312) both invoke `share_internal`, which regenerates the same machine/nonces, but the message signed is `set_keys_message(&self.spec.set(), &removed, key_pair)` (lines 296-301) where `key_pair` is a per-call parameter. Likewise, `share` can be invoked multiple times with different `preprocesses` maps (changing the FROST binding factor `rho` and hence the effective challenge/nonce combination) or different `key_pair` values.

The FROST docs explicitly warn this reuse is fatal ("Reusing preprocesses would enable a third-party to recover your private key share", spec/cryptography/FROST.md:51-55), yet the coordinator layer reuses the cached seed unconditionally for every `share`/`complete` in an attempt with no check that the message and signing set are identical to the first use — the missing "state transfer" of binding the consumed cache to its signed message, exactly paralleling the CVE's "reject until proper state transfer is implemented" fix.

### Impact Explanation
If two `share`/`complete` invocations under one attempt sign different messages (different `key_pair`, or a different `preprocesses` set yielding different binding factors), the deterministic nonces `d, e` are identical while the challenge differs. An observer of the two Schnorr signature shares `s1 = k + c1·x`, `s2 = k + c2·x` solves `x = (s1 − s2)/(c1 − c2)`, recovering this validator's interpolated MuSig/FROST secret share. Shares are broadcast over the tributary protocol and are publicly observable, so the recovered share combines with other leaked/compromised material toward threshold key compromise. Critical-to-High severity primitive: key share recovery from observable shares.

### Likelihood Explanation
The deterministic reuse is guaranteed whenever `share` and `complete` run in the same attempt — that is the designed behavior and is safe *only* if `key_pair` and the preprocess set are identical. Divergence occurs if a coordinator retries `share` with a different `key_pair` (e.g., after a slashing/removal changes the confirmed set) or if `share` fails on an invalid preprocess and is retried with a different participant set (different binding factors → different effective nonce under the same `d + b·e`). Whether the surrounding tributary logic ever actually presents differing `key_pair`/`removed` values within one attempt could not be fully confirmed — the call sites in `handle.rs` were not reachable in remaining iterations — so likelihood is conditional on such divergence occurring; the cryptographic consequence is unconditional once it does.

### Recommendation
Bind the cached preprocess to its first use: record (a hash of) the `msg` and the sorted included-participant set alongside `CachedPreprocesses`, and have `share_internal` reject any call whose message/set differs from the recorded one — mirroring the upstream fix of rejecting the variant whose state can't be transferred. Alternatively, key the cache by a digest of `(msg, preprocesses)` so divergent calls derive independent nonces, and delete/mark-consumed the cache entry once a share is emitted.

### Proof of Concept
Within one `attempt`:
1. `DkgConfirmer::share(preprocesses_A, key_pair_1)` → internally `preprocess_internal` loads seed `S`, derives nonces `(d, e)` deterministically, emits share `s_1` over `m_1 = set_keys_message(set, removed, key_pair_1)`.
2. `DkgConfirmer::complete(preprocesses_A, key_pair_2, shares)` (or a second `share` call with a different participant set) rebuilds the same machine from the same `S` — same `(d, e)` — and produces share `s_2` over `m_2 ≠ m_1`.
3. For Schnorr shares `s_i = d + ρ·e + c_i·λ·x` with identical `d, e`, a network observer solves `λ·x = (s_1 − s_2)/(c_1 − c_2)` (or `s_1 − s_2` directly cancels the nonce term when `ρ` is unchanged), recovering the interpolated secret share `λ·x`, and with the known participant set, the underlying share. Both shares are broadcast on the authenticated tributary channel and publicly readable.
