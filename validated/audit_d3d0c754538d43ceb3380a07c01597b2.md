## Analog Found: DID Recovery Attestation Signature Lacks Coin-Binding (AGG_SIG_UNSAFE Replay)

### Title
DID recovery attestation signature is not bound to the recovering coin, enabling attestation replay across DIDs sharing a backup key - (File: `chia/wallet/did_wallet/did_wallet_puzzles.py`)

### Summary
The reported `NodeRegistry.registerNodeFor()` issue is a signed authorization message that omits a domain/identity binding (`registryID`, contract address), letting the same signature be replayed across unrelated registries. The structural analog in this repo is the DID recovery attestation mechanism: a backup/recovery DID signs an `AGG_SIG_UNSAFE` condition over only `(pubkey, newpuz)` — the target puzzle hash and its own key — with **no binding to the specific DID coin being recovered**.

### Finding Description
`create_recovery_message_puzzle()` builds the attestation puzzle: [1](#0-0) 

The puzzle emits two conditions:
- `CREATE_COIN_ANNOUNCEMENT(recovering_coin_id)` — an *unsigned* condition, hard-curried into the message puzzle itself.
- `AGG_SIG_UNSAFE(pubkey, newpuz)` — the only signed data, and it covers **just `newpuz`**, not `recovering_coin_id`, not any registry/singleton/launcher identifier, and not a genesis-challenge/network domain separator (unlike `AGG_SIG_ME`, which the codebase documents as including per-network additional data precisely to prevent replay: [2](#0-1) ).

Because `AGG_SIG_UNSAFE` verification only checks `AugSchemeMPL.verify(pubkey, newpuz, signature)`, the signature is valid for **any** message puzzle that curries in the same `(pubkey, newpuz)` pair, regardless of which `recovering_coin_id` is baked into the accompanying (unsigned) `CREATE_COIN_ANNOUNCEMENT`. An attacker who observes a previously broadcast attestation spend (trivially public, since it is an on-chain coin spend) can:
1. Extract the `(pubkey, signature)` pair for a known `newpuz`.
2. Construct a brand-new, self-funded zero-value message coin using `create_spend_for_message()` with the **victim's** DID coin ID as `recovering_coin_id`, but reusing the same `pubkey`/`newpuz`/`signature`: [3](#0-2) 
3. If the victim DID's `recovery_list` (curried into its inner puzzle, see `uncurry_innerpuz`) happens to include the same backup pubkey — a realistic scenario when a shared custodian/backup service key is reused across multiple DIDs — this forged attestation satisfies the recovery threshold for the victim's coin without the backup ever being asked to authorize *that specific coin's* recovery. [4](#0-3) 

This mirrors the report precisely: the signed payload omits the entity-specific identifier (`recovering_coin_id` ≈ `registryID`), so a signature legitimately produced for one context can be replayed to force an unauthorized state transition (DID ownership handover to `newpuz`) in a different, unrelated context that happens to share the same signer key.

### Impact Explanation
Successful replay redirects ownership of a victim's DID singleton (and any assets/attestations tied to that DID identity, e.g., NFTs, VCs referencing it as `proof_provider`) to the `newpuz` embedded in the reused signature, without the backup key holder's consent for that coin. This is an unauthorized/forged identity transfer via the singleton/DID lineage path, not merely an availability or informational issue.

### Likelihood Explanation
Exploitation requires: (a) a DID's `recovery_list` including a pubkey reused across multiple/unrelated DIDs (a realistic pattern for pooled/backup-service custodians), and (b) an attacker who has observed any prior legitimate attestation signed by that key for some `newpuz`. Both attestation spends and DID puzzle contents are fully public on-chain, so discovery is trivial once the precondition (shared backup key) holds. This is a design gap rather than a rare edge case.

### Recommendation
Include the `recovering_coin_id` (and ideally the DID's `launcher_id`/singleton identity) inside the `AGG_SIG_UNSAFE` signed message itself (or switch to `AGG_SIG_ME`, which is already coin- and network-domain-bound), so a backup signature cannot be replayed across different DID coins that happen to share a recovery key.

### Proof of Concept
Conceptual (chialisp/python) reuse:
1. Backup DID signs attestation for legitimate coin `A` recovering to `newpuz`, producing `sig = AugSchemeMPL.sign(backup_sk, newpuz)`.
2. Attacker observes this on-chain and calls `did_wallet_puzzles.create_spend_for_message(parent_of_message, victim_coin_B_id, newpuz, backup_pk)` — same `pubkey`/`newpuz` inputs used to build the puzzle, but `recovering_coin_id = victim_coin_B_id`.
3. Attacker funds this synthetic message coin and submits a spend bundle aggregating this coin spend with victim coin `B`'s recovery spend (which asserts the coin announcement referencing its own coin id) plus the reused `sig` as the aggregate signature.
4. If `B`'s `recovery_list` includes `backup_pk` and threshold is met, the spend validates and `B`'s ownership is handed to `newpuz` without the backup key holder ever approving `B`'s recovery.

**Caveat on current reachability:** I could not fully confirm, within the available tooling, whether a present-day wallet RPC/CLI path still exposes end-to-end creation and broadcasting of DID attestation + recovery spends in this exact codebase snapshot. `grep` found no `did_create_attest`/`DIDRecoverySpend`-style RPC in `wallet_rpc_api.py` (only historical references in `CHANGELOG.md`), and new DID creation now rejects a non-empty `backup_dids` list [5](#0-4) , meaning this risk is limited to pre-existing DIDs created before that restriction. The underlying puzzle primitives (`create_recovery_message_puzzle`, `create_spend_for_message`) remain in `did_wallet_puzzles.py` and are referenced by `DIDWallet`, but I did not have iterations left to trace the full internal recovery-spend assembly path in `did_wallet.py` to confirm an unmodified, currently-triggerable RPC/CLI entry point. A Devin session with full repo access would be needed to verify live reachability before treating this as confirmed-exploitable in production.

def create_recovery_message_puzzle(recovering_coin_id: bytes32, newpuz: bytes32, pubkey: G1Element) -> Program:
    """
    Create attestment message puzzle
    :param recovering_coin_id: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: Message puzzle
    """
    puzzle = Program.to(
        (
            1,
            [
                [ConditionOpcode.CREATE_COIN_ANNOUNCEMENT, recovering_coin_id],
                [ConditionOpcode.AGG_SIG_UNSAFE, bytes(pubkey), newpuz],
            ],
        )
    )
    return puzzle
```

def create_spend_for_message(
    parent_of_message: bytes32, recovering_coin: bytes32, newpuz: bytes32, pubkey: G1Element
) -> CoinSpend:
    """
    Create a CoinSpend for a atestment
    :param parent_of_message: Parent coin ID
    :param recovering_coin: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: CoinSpend
    """
    puzzle = create_recovery_message_puzzle(recovering_coin, newpuz, pubkey)
    coin = Coin(parent_of_message, puzzle.get_tree_hash(), uint64(0))
    solution = Program.to([])
    return make_spend(coin, puzzle, solution)
```

## AGG_SIG conditions and replay protection

### `AGG_SIG_ME_ADDITIONAL_DATA`

Each network defines its `AGG_SIG_ME_ADDITIONAL_DATA` value (read it from the active constants, not a hard-coded mainnet value). Each AGG_SIG variant appends a different opcode-derived suffix to the additional data before signing, providing per-condition domain separation. Forks MUST change `AGG_SIG_ME_ADDITIONAL_DATA` to prevent cross-chain replay attacks.
