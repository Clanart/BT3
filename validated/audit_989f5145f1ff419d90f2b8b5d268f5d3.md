## Analysis

The Sherlock report's broken invariant is: **an identity check meant to bind a privileged action to exactly one canonical address instead accepts any of several superficially-similar identifiers**, letting an attacker impersonate a trusted entity and divert value (`asset`/`yt`) meant only for that entity.

The closest verifiable analog in this GitHub Desktop codebase is a hostname-identity check that is supposed to recognize *genuine* GitHub hosts but instead accepts any hostname whose first label happens to be `github`, regardless of the actual registrable domain. That misclassification feeds directly into the credential/sign-in trampoline flow, which then presents Desktop's own trusted "sign in" UI for a domain the attacker fully controls.

### Title
GitHub-host detection regex misclassifies attacker-controlled domains as trusted GitHub Enterprise hosts, triggering an in-app phishing sign-in prompt - (File: `app/src/lib/api.ts`)

### Summary
`isGitHubHost()` uses the regex `/(^|\.)(github)\./.test(hostname)` to decide whether an unknown remote host "belongs to GitHub" [1](#0-0) . This pattern only requires the label `github` to appear at the start of the hostname (or after a dot) followed by a dot — it does not anchor to the end of the string or validate the registrable domain/TLD, so `github.attacker.com` satisfies it just as well as a legitimate `github.mycompany.com` GHE instance.

### Finding Description
The credential trampoline calls `getEndpointKind()` to decide how to treat an unknown git host during authentication. It short-circuits on exact matches for `github.com`/`ghe.com` [2](#0-1) , and when neither WWW-Authenticate hints nor an existing stored account resolve the host, it falls back to `isGitHubHost(endpoint)` and labels the result `'enterprise'` if true [3](#0-2) .

`isGitHubHost` first tries a live network probe for the `x-github-request-id` header, which would correctly reject a non-GitHub server [4](#0-3) . However, *before* that network check it applies fast heuristics, one of which is the flawed regex: any hostname containing the label `github` followed immediately by a dot — anywhere, not just as the whole domain or as `github.` at the very start of an enterprise-style FQDN — is unconditionally treated as GitHub, short-circuiting the safer network probe entirely [5](#0-4) .

This is the "multiple address" analog: the check was written to recognize the single canonical family of GitHub-branded hosts (`github.com`, `*.ghe.com`, self-hosted GHE like `github.mycompany.com`), but the pattern is satisfied by attacker-chosen domains that merely *contain* the token `github.` as a leading label of any suffix, e.g. `github.evil-corp.io`, `github.attacker.net`.

Once `getEndpointKind` returns `'enterprise'` for such a host and no matching account exists in the store, `getCredential()` calls `ui.promptForGitHubSignIn(endpoint)` [6](#0-5) . That function inspects the hostname again and, since it isn't literally `github.com`, invokes `beginEnterpriseSignIn` and sets the sign-in endpoint to the attacker's origin, then shows Desktop's built-in `PopupType.SignIn` dialog scoped to that URL [7](#0-6) . The credential-helper trigger path is reached purely by git needing authentication against a remote — i.e., simply adding/fetching a remote or submodule pointing at the attacker's `github.*` domain is enough; no prior trust or user credential entry elsewhere is required.

### Impact Explanation
The victim is shown Desktop's own native "Sign in to GitHub Enterprise" popup, which lends the interaction the credibility of a first-party Desktop feature, for a domain fully controlled by the attacker. A user who completes that enterprise sign-in flow (username/password or PAT) submits credentials directly to the attacker's server via `beginEnterpriseSignIn`/`setSignInEndpoint(origin)`, which is unauthorized credential exfiltration and an unintended "account binding" to an attacker-controlled endpoint — matching the report's class of impact (theft of a protected value — here credentials/tokens — that was supposed to be gated by an exact-identity check).

### Likelihood Explanation
The path is reachable purely by getting the victim's local git/Desktop to attempt a fetch/push/clone against an attacker-chosen remote (e.g., a malicious submodule URL or a repo added via "Clone/Add remote"), which is fully within the "attacker controls a git remote" threat model in scope. Registering a domain like `github.<anything>` is trivial and requires no compromise of GitHub infrastructure. The only mitigating factor is the subsequent network probe (`x-github-request-id` header check) in `isGitHubHost`, but that check only runs if the earlier fast-path heuristics (including the flawed regex) don't already return a verdict — and the regex is checked *before* the network probe and short-circuits it [8](#0-7) .

### Recommendation
Replace the substring/label heuristic with a check against the actual registrable domain (eTLD+1) rather than a leading-label regex, e.g. require `hostname === 'github.<tld-suffix>'` matching a configured allow-list of enterprise domains, or drop the fast heuristic entirely and always rely on the authenticated network probe (`x-github-request-id`) before classifying an unknown host as `'enterprise'`.

### Proof of Concept
1. Attacker hosts a git server (or any HTTP server) at `https://github.attacker.com`.
2. Victim adds this as a remote or submodule URL in a repository opened in GitHub Desktop and triggers a fetch/push (submodule update, clone, etc.), which invokes the git credential trampoline.
3. `getEndpointKind` reaches the fallback branch; `isGitHubHost('https://github.attacker.com/...')` evaluates `/(^|\.)(github)\./.test('github.attacker.com')` → `true`, classifying the host as `'enterprise'` without ever reaching the network probe validation [1](#0-0) .
4. Since no account exists for this endpoint, `getCredential` calls `ui.promptForGitHubSignIn('https://github.attacker.com')`, which shows Desktop's native Enterprise sign-in popup pointed at the attacker's origin [9](#0-8) .
5. If the victim completes sign-in, their enterprise credentials/token are sent to the attacker-controlled server.

**Note on completeness:** I was not able to trace the exact runtime call site(s) that construct/add such a remote URL from repository content (e.g., submodule `.gitmodules` parsing) within the indexed portion of this codebase, so the initial "attacker gets their URL invoked by git" step is inferred from the general trampoline design rather than a directly cited call site. If you need that link fully traced through file contents not covered by this index (e.g., submodule URL validation before invoking git), a full Devin session with repository access would be needed to confirm it exhaustively.

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
