### Title
`ThresholdKeys::read` accepts fully attacker-controlled interpolation coefficients and verification shares, letting untrusted bytes select an arbitrary group key - ([File: crypto/dkg/src/lib.rs])

### Summary
The YARD advisory (CVE-2026-41493, CWE-22) is a path traversal: unsanitized request bytes determine *which resource* the server reads, escaping the intended docroot. The Serai analog is `ThresholdKeys::read`, where untrusted bytes determine *which key material* the signer operates under: `t`, `n`, `i`, the interpolation method and its constant coefficients, the secret share, and all `n` verification shares are read verbatim from the stream with no consistency check tying `secret_share` to `verification_shares[i]` or the shares to any expected group key. The "traversal" is a key-material substitution: the deserializer can be pointed at an attacker-chosen group key the attacker actually controls.

### Finding Description
`ThresholdKeys::read` reconstructs a `ThresholdKeys<C>` purely from attacker-supplied bytes [1](#0-0) :

1. It reads `t`, `n`, `i` and constructs `ThresholdParams` (which only checks `0 < i <= n` and `t <= n`, not consistency with any prior state) [2](#0-1) .
2. For `interpolation[0] == 0` it reads `n` arbitrary scalars as `Interpolation::Constant` coefficients [3](#0-2) .
3. It reads `secret_share` and `n` verification shares (`read_G` rejects non-canonical/identity encodings, but nothing else) [4](#0-3) .
4. `ThresholdKeys::new` computes `group_key` by interpolating verification shares `1..=t` — entirely attacker-chosen — and never verifies `C::generator() * secret_share == verification_shares[i]` [5](#0-4) .

The downstream code acknowledges the consequence: `complete()` notes a signature can fail despite all-valid shares only via "a semantically invalid FrostKeys" — i.e., inconsistent deserialized key material [6](#0-5) .

### Impact Explanation
An unprivileged party whose bytes reach `ThresholdKeys::read` (the listed reachable `read` APIs include it) can cause a signer/verifier to operate under a group key of the attacker's choosing: choose `verification_shares[1..=n] = G * x_j` for known `x_j`, set `secret_share` to a known scalar, and the resulting `ThresholdKeys` produces signatures that verify under an attacker-known discrete log — a forged-signature / key-substitution condition analogous to reading arbitrary files. Even without full control, supplying `Interpolation::Constant` with arbitrary coefficients changes `interpolation_factor` per participant (`c[i-1]`, crypto/dkg/src/lib.rs:228), desynchronizing one node's view of every participant's verification share from its peers and causing it to accept/reject shares inconsistently — a per-node resource-confusion on which key is being signed under.

### Likelihood Explanation
Medium. Exploitation requires the attacker to control the bytes fed to `ThresholdKeys::read`; within the stated threat model (untrusted bytes to the enumerated `read`/`verify`/`sign` APIs), that reachability is assumed. No collusion, no leaked key, and no malformed curve points are needed — all inputs are syntactically valid encodings; the flaw is purely semantic (no binding between share, verification share, and group key), matching the "incorrectly applied sanitization" nature of the original YARD bug.

### Recommendation
After deserialization, verify `C::generator() * secret_share == verification_shares[i]` before constructing `ThresholdKeys`. Where the expected group key or a commitments digest is externally known, compare `ThresholdKeys::new(...).group_key()` against it and reject mismatches. Consider rejecting `Interpolation::Constant` on the deserialize path unless the caller explicitly expects it, since `read` accepts a coefficient vector that `write` can only produce for `t == n`.

### Proof of Concept
Conceptually (Rust):

```rust
// Attacker-chosen scalar
let x = <C as Ciphersuite>::F::random(rng);

// Forge serialized ThresholdKeys bytes:
//   C::ID len + C::ID, t = 1, n = 1, i = 1,
//   interpolation = Lagrange (0x01),
//   secret_share = x.to_repr(),
//   verification_shares = [G * x]
let keys = ThresholdKeys::<C>::read(&mut forged_bytes.as_slice()).unwrap();
// keys.group_key() == G * x; attacker knows x and can sign/verify
// under the substituted group key, or corrupt a node's per-participant
// interpolation factors via Interpolation::Constant coefficients.
```

Uncertain: whether any in-scope production caller actually pipes attacker-controlled bytes into `ThresholdKeys::read` (typical usage loads it from local DB); per the engagement rules, untrusted bytes reaching the enumerated read APIs count as reachable.

        Ok(u16::from_le_bytes(value))
      };

        read_u16()?,
        read_u16()?,
