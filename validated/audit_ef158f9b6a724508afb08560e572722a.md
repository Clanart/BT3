### Title
Webhook HMAC verification does not bind the authenticated body to the shop identity, enabling cross-shop webhook replay - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` authenticates only the raw request body via HMAC, while the shop identity that downstream jobs trust (`X-Shopify-Shop-Domain` header) is read unauthenticated and is never included in the HMAC computation. This mirrors the report's core "leniency" pattern: one piece of data is cryptographically verified (the DKIM header field / here, the raw body) while an adjacent, security-relevant piece of data (the body-hash's tag-boundary / here, the shop-domain header) is trusted without being tied to the verified data, allowing an attacker to splice a validly-signed payload with a different, attacker-chosen identity value.

### Finding Description
`hmac_valid?` computes `OpenSSL::HMAC.digest(digest, secret, data)` where `data = request.raw_post`, and compares it to the `X-Shopify-Hmac-Sha256` header: [1](#0-0) 

`verify_request` only checks this HMAC over the body, and `shop_domain` is derived purely from an unauthenticated header: [2](#0-1) 

Nowhere is the `X-Shopify-Shop-Domain` (or the `X-Shopify-Webhook-Id`/topic) header incorporated into the HMAC digest. The documented, recommended custom-controller pattern explicitly forwards this unauthenticated `shop_domain` value into background jobs that perform destructive/privileged shop-scoped actions: [3](#0-2) 

The generated mandatory-privacy-webhook job templates (`shop_redact_job.rb.tt`, `customers_redact_job.rb.tt`, `customers_data_request_job.rb.tt`, `app_uninstalled_job.rb.tt`) are queued with `shop_domain` sourced the same way, from `ShopifyAPI::Webhooks::Request`'s header-derived `shop` value, not from a value that is cryptographically bound to the signed body.

Because the app's webhook secret (`ShopifyApp.configuration.secret`) is a single, shared per-app secret (not per-shop), any merchant who has installed the app on their own store possesses a store of genuinely-signed `(body, HMAC)` pairs — every real webhook Shopify sends to that merchant is a valid `(body, HMAC)` pair under this same secret. Such a merchant can replay one of their own legitimately-signed webhook bodies (e.g., an `app/uninstalled` or `shop/redact` webhook whose JSON body does not strictly have to be checked for a matching domain by the consuming job) to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with an arbitrary victim shop's domain. `verify_request` will accept it because the HMAC check only covers the untouched body; the header can be freely modified in transit by the attacker since it is not signed.

### Impact Explanation
If a consuming app follows the shopify_app-documented pattern (or uses the generated privacy/uninstall job templates) and trusts the header-derived `shop_domain` to select which shop's session/data to act on (e.g., deleting a shop's session, redacting shop data, disabling billing, or triggering re-authentication for a shop), an attacker can trigger these shop-scoped side effects against an arbitrary victim shop domain, without any knowledge of that victim's actual data — a cross-shop attribution/authorization bypass building on a validly-authenticated (but domain-unbound) signature.

### Likelihood Explanation
Requires the attacker to have (or gain) legitimate installation of the target app on any shop they control — a low bar for any public app — and to intercept/replay one of their own genuine webhooks with a modified header, which is trivial (no cryptography needs to be broken; only the unsigned header is altered). This is a realistic, low-effort attack path when the shared-secret and header-not-signed design is combined with the shopify_app-recommended usage pattern.

### Recommendation
- Do not treat `X-Shopify-Shop-Domain` (or `X-Shopify-Webhook-Id`) as trusted/authenticated on its own. Either:
  - Verify that the shop domain in the header matches a shop-domain value embedded and covered inside the HMAC-signed body (when the topic's payload includes it), and reject the request otherwise; or
  - Look up the installed shop by an identifier that is itself independently verifiable/scoped (e.g., only accept the header value if there is a currently installed, active session for that shop, and additionally cross-check it against body content whenever available).
- Update `docs/shopify_app/webhooks.md` and the generated job templates (`shop_redact_job.rb.tt`, `customers_redact_job.rb.tt`, `customers_data_request_job.rb.tt`, `app_uninstalled_job.rb.tt`) to stop unconditionally trusting the header-derived shop domain for privileged/destructive actions.
- Consider making `hmac_valid?` bind additional signed context (e.g., include topic/shop in the comparison against a body-derived value) rather than relying solely on the raw body digest.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, permitted install).
2. Shopify sends a genuine webhook, e.g. `app/uninstalled`, to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)`.
3. Attacker captures `(B, H)` and replays a POST to the same webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `hmac_valid?(B)` succeeds (HMAC only checked over `B`), `verify_request` passes.
5. `ShopifyAPI::Webhooks::Registry.process` / the generated job (`AppUninstalledJob`, `ShopRedactJob`, etc.) is invoked with `shop_domain: "victim-shop.myshopify.com"`, causing the app to perform the uninstall/redact/data-request handling logic against the victim shop instead of the attacker's own shop.

**Uncertainty note:** Whether this is exploitable in a given deployment depends on (a) whether the specific webhook topic's JSON body itself independently encodes the shop domain and whether the consuming job cross-checks it (this varies by topic and is up to the app developer, outside this repo's control), and (b) the internal validation performed by `ShopifyAPI::Webhooks::Registry.process` in the `shopify_api` gem, which is a dependency not fully indexed here. The vulnerability described is specifically the shopify_app-provided verification/pattern layer (`WebhookVerification`/`PayloadVerification` and the documented/generated consumption pattern), which never binds the shop-domain header to the signed body itself.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
