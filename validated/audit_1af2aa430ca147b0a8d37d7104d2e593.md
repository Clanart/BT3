### Title
Permanently stuck relayer fees in `EvmHost.dispatchTimeOut` when the request-originating module lacks the timeout callback - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchTimeOut` (both the `PostRequestTimeout` and `GetRequestTimeout` overloads) refunds the escrowed relayer fee to the fee payer only *after* successfully invoking `onPostRequestTimeout`/`onGetTimeout` on the request's `from` address. If that low-level `.call` fails, the code deliberately re-persists the `FeeMetadata` "so that it can be retried" instead of refunding the fee. If the `from` address is a smart contract that never implements the callback (and has no compatible fallback), this retry can never succeed, and the escrowed fee is permanently stranded in `EvmHost`. This is the same root cause as the Scroll `L1ScrollMessenger.dropMessage`/`onDropMessage` report: a refund path gated behind a callback that the sender/module is not guaranteed to implement.

### Finding Description
`dispatch(DispatchPost memory post)` sets `request.from = abi.encodePacked(_msgSender())` unconditionally [1](#0-0) , and records the fee payer/fee in `_requestCommitments[commitment]` [2](#0-1) . Thus `from` is whatever contract calls `dispatch()` directly — it does not have to be a `HyperApp`/`IApp`-compliant module; any contract (a custom router, a user's own gateway, a smart-contract wallet, an intermediate proxy) can call `dispatch()`.

When the request times out, `IHandler` calls `EvmHost.dispatchTimeOut`, which does:
```solidity
(bool success,) = _bytesToAddress(timeout.request.from)
    .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

if (!success) {
    // so that it can be retried
    _requestCommitments[commitment] = meta;
    return;
}

if (meta.fee != 0) {
    // refund relayer fee
    IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
}
``` [3](#0-2) 

The identical pattern exists for `GetRequestTimeout` [4](#0-3) .

If `from` is a contract that does not implement `onPostRequestTimeout`/`onGetTimeout` and has no payable fallback that swallows arbitrary calldata, the `.call` reverts (a call to a contract with no matching selector and no fallback reverts), `success` is `false`, and the code path *restores* the fee metadata rather than refunding it. Since the timeout can be resubmitted indefinitely but the destination module's bytecode never changes, this call will fail forever — the `meta.fee` in `feeToken()` remains locked inside `EvmHost` with no other withdrawal path. The documentation itself confirms this is the intended (but unsafe) design: "If this callback reverts, fees are NOT refunded" / "Can be called multiple times until it succeeds" [5](#0-4) .

This is exactly analogous to the reported Scroll issue: a refund is gated behind a callback (`onDropMessage` / `onPostRequestTimeout`) that the sending party is not guaranteed to implement, and there is no fallback path to return the value directly to the fee payer if the callback keeps failing.

### Impact Explanation
Fees are paid up front by the request's `payer` in `feeToken()` and escrowed in `EvmHost`. If the module set as `request.from` never successfully implements the timeout callback, that fee is permanently unrecoverable — a genuine loss of funds inside the bridge's own custody contract, with no admin/rescue function found in `EvmHost` to sweep or manually redirect stuck `_requestCommitments` entries. Any application built directly on `dispatch()` without perfectly matching the `IApp` interface (or one that is later upgraded/removed/self-destructed) permanently loses its escrowed relayer fee on every subsequent timeout of in-flight requests from that address.

### Likelihood Explanation
This does not require a malicious peer, relayer, or governance actor — only a smart-contract caller of `EvmHost.dispatch()` that does not correctly implement `onPostRequestTimeout`/`onGetTimeout` (e.g., a custom integration, an EOA-controlled proxy, or a module that reverts due to a bug in its own timeout handler). Given `dispatch()` is a public entrypoint open to any contract, and integrators are expected to build custom `IApp` modules, this is a realistic and repeatable occurrence, not a contrived edge case.

### Recommendation
Decouple the fee refund from the callback's success. Refund `meta.fee` to `meta.sender` unconditionally (or via a separate, always-successful transfer) before or independent of invoking `onPostRequestTimeout`/`onGetTimeout`, and treat the application callback purely as a best-effort notification (already retryable), not as a gate for fund custody. Alternatively, add an explicit sweep/rescue mechanism so that fees tied to a permanently-failing callback can eventually be released to the fee payer after some governance-controlled process.

### Proof of Concept
1. Deploy a minimal contract `BadModule` with no `onPostRequestTimeout` function and no fallback/receive.
2. From `BadModule`, call `EvmHost.dispatch(DispatchPost{...})` with `post.payer = payerAddress`, `post.fee = X`. `request.from` becomes `address(BadModule)` [6](#0-5) .
3. Let the request time out; a relayer/anyone submits the timeout proof, which reaches `IHandler` → `EvmHost.dispatchTimeOut(PostRequestTimeout, meta, commitment)`.
4. The `.call` to `BadModule.onPostRequestTimeout(...)` reverts (no matching selector, no fallback) → `success == false` → `_requestCommitments[commitment] = meta;` is restored, no fee transfer occurs [7](#0-6) .
5. Resubmitting the timeout message repeatedly always reverts the same way since `BadModule`'s bytecode never changes — the fee `X` in `feeToken()` stays escrowed in `EvmHost` forever, with no recovery path for `payerAddress`.
