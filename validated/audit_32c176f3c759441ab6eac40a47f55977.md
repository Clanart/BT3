### Title
`smartConvert` relies on manipulable spot state (`IAsset.cash()/liability()` and AMM spot price) and executes the buyback swap with zero slippage protection - ([File: wombat/SmartWomConvert.sol])

### Summary
`smartConvert()` decides how much WOM is routed through an AMM buyback (`_convertFor`'s `swapExactTokensForTokens` call) versus minted 1:1 via `IMWom.deposit()`, based on two live, unprotected reads: `maxSwapAmount()` (derived from `IAsset(womAsset).cash()/liability()`) and `currentRatio()` (spot price from `womMWomPool` via `router.getAmountOut`). The actual buyback swap inside `_convertFor` is executed with `amountOutMin = 0`, and the only aggregate protection (`_minRec = _amountIn`, hardcoded by `smartConvert`) is a floor on total mWom received, not a fair-price constraint on the swap leg, so an attacker who manipulates pool state before calling can force the swap to execute against a price they engineered.

### Finding Description
`smartConvert` (wombat/SmartWomConvert.sol:133-147) is a public, unrestricted external function despite the comment that it's "mainly used by wombat staking" - no access control enforces that. It computes: [1](#0-0) 

`maxSwapAmount()` reads `IAsset(womAsset).cash()` and `liability()` directly with no TWAP/oracle protection, and `currentRatio()` reads a live `getAmountOut` quote from `womMWomPool`. Both are attacker-observable/attacker-influenceable within the same transaction via swaps/deposits/withdraws on the underlying Wombat pool and on `womMWomPool`.

Based on these two manipulable reads, `smartConvert` computes `convertRatio`, which determines `buybackAmount` in `_convertFor`: [2](#0-1) 

The buyback swap is called with `amountOutMin = 0` — there is no per-swap slippage bound. The only check afterward is the aggregate floor: [3](#0-2) 

Because `smartConvert` hardcodes `_minRec = _amountIn` (line 146), this floor guarantees the caller never receives *less* than a 1:1 conversion, but it places no cap on how much *more* than fair value the swap can yield. An attacker can, in the same transaction: (1) trade against `womMWomPool` to depress the spot mWom price so `currentRatio()` falls below `buybackThreshold`, forcing buyback mode; (2) optionally trade against the pool underlying `womAsset` to widen `cash()`/`liability()` gap and inflate `maxSwapAmount()`, maximizing how much of `_amountIn` is routed through the now-manipulated `womMWomPool`; then (3) call `smartConvert`, whose zero-slippage internal swap fills at the manipulated price, extracting mWom from `womMWomPool`'s reserves at a rate more favorable than the pool's true price; (4) unwind the manipulating trades to restore price and realize the arbitrage.

### Impact Explanation
This drains value from `womMWomPool` liquidity providers by executing an oversized, unprotected swap at an attacker-manipulated price, which can be repeated. It is a real value-extraction vector rather than a direct mint of uncollateralized mWom (the buyback path moves existing mWom reserves out of `womMWomPool`, it does not mint new mWom), so the "protocol insolvency" framing in the question overstates it — the precise, provable impact is loss of value from the AMM pool's reserves (LP loss) caused by the missing slippage protection on the internal swap, matching an Immunefi "theft of user funds" / LP value-loss class rather than a peg-insolvency class.

### Likelihood Explanation
Feasible for any unprivileged actor: `smartConvert` has no access control, and both `maxSwapAmount()`/`currentRatio()` and the internal swap read live, un-TWAP'd pool state that can be moved within a single atomic transaction using flash loans/flash swaps, requiring only enough capital (which can be largely flash-loaned) to move `womMWomPool`'s and `womAsset`'s spot state and to supply `_amountIn` WOM for the call itself. It is repeatable as long as pool liquidity and available capital permit profitable manipulation net of AMM fees.

### Recommendation
Add real slippage protection to the internal buyback swap in `_convertFor` (do not hardcode `amountOutMin = 0`; derive an acceptable minimum from a time-weighted or externally supplied price), and avoid basing `convertRatio`/`maxSwapAmount` purely on single-block spot reads of `cash()/liability()` and `getAmountOut` — use TWAP-based or bounded-deviation checks, and/or restrict `smartConvert` to a trusted caller (e.g., only `WombatStaking`) as its comment implies.

### Proof of Concept
Foundry fork test plan:
1. Fork BSC at a block where `womMWomPool` and the main Wombat WOM pool exist.
2. Attacker contract flash-loans WOM/mWom, swaps against `womMWomPool` to push `currentRatio()` below `buybackThreshold`, and optionally swaps/withdraws against the WOM `IAsset` pool to widen `cash()` vs `liability()`.
3. Attacker calls `SmartWomConvert.smartConvert(_amountIn, 0)` with real WOM capital.
4. Assert the mWom received by the attacker corresponds to a swap price worse than `womMWomPool`'s pre-manipulation spot price, i.e., diff `womMWomPool` mWom reserve before/after against the WOM actually contributed to the pool side of the swap, and confirm attacker nets positive mWom/WOM profit after unwinding the manipulation trades within the same transaction.
5. Compare against a control run without pre-manipulation to show the manipulated run yields a measurably better rate for the attacker, confirming the missing-slippage-protection root cause.
