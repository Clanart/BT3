### Title
`internal_withdraw` RPC bypasses aggregator verification-signature check that `withdraw` enforces, allowing an unauthenticated broadcast of an operator payout - (File: `core/src/rpc/operator.rs`)

### Summary
The bug pattern in the report is a check performed on the wrong condition (`deposits.length > 0` instead of `debt > 0`), silently breaking the intended authorization/precondition binding for a state-changing action. The equivalent pattern exists in Clementine's operator gRPC service: the `withdraw` handler enforces "caller must be the aggregator" via an ECDSA verification-signature check against `config.aggregator_verification_address`, but the sibling `internal_withdraw` handler calls the exact same state-changing/fund-broadcasting logic (`Operator::withdraw`) while completely omitting that check.

### Finding Description
`ClementineOperator::withdraw` in `core/src/rpc/operator.rs` requires, when `aggregator_verification_address` is configured, that the request carry a `verification_signature` recoverable to that configured address before it calls `self.operator.withdraw(...)`: [1](#0-0) 

`internal_withdraw`, defined immediately above it in the same file, parses the identical `WithdrawParams` and invokes the identical `self.operator.withdraw(...)` state-changing/fund-broadcasting call, but performs **no** verification-signature check at all: [2](#0-1) 

`Operator::withdraw` itself only checks that the Citrea-recorded withdrawal UTXO matches the caller-supplied outpoint and that the payout is "profitable" for the operator; it does not check who invoked it: [3](#0-2) 

The binding that should hold is: *party authorized to trigger an operator payout* (the aggregator, attested by the ECDSA verification signature against `aggregator_verification_address`) **==** *party that actually invoked the payout-broadcasting RPC*. `withdraw` enforces this equality; `internal_withdraw` does not, so any caller able to reach the operator's gRPC surface can drive `Operator::withdraw`, causing the operator to fund and broadcast a real payout transaction from its own on-chain funds and commit to the reimbursement flow (kickoff/reimburse), exactly the "unauthenticated state-changing or broadcasting call" pattern.

### Impact Explanation
`Operator::withdraw` funds a payout transaction from the operator's wallet via `fund_raw_transaction` and broadcasts it via RBF, which starts the operator's reimbursement lifecycle (kickoff → reimburse) for that withdrawal: [4](#0-3) 
If `internal_withdraw` is reachable without the aggregator's authorization, a caller can force the operator to front a withdrawal it was never instructed (by the authorized coordinator) to front, at a caller-chosen time/outpoint, consuming the operator's collateral/round slot and committing it to a payout the operator did not intend to make outside the aggregator-orchestrated flow. This is a state-changing, fund-broadcasting call reachable without the authorization check the codebase itself defines as necessary (see the parallel, correctly-checked `withdraw` handler), matching the High-impact class "an unauthenticated state-changing or broadcasting call."

### Likelihood Explanation
The vulnerability is a straightforward code-path inconsistency (missing an `if let Some(address_in_config) = ... verification_signature` check that exists nearly verbatim one function above it), requiring no privileged role, key compromise, or TLS interception to exploit at the application layer — only network reachability to the operator's gRPC endpoint that exposes `internal_withdraw`. Given both handlers accept the same `WithdrawParams`/`WithdrawParamsWithSig`-derived tuple and route to the identical `Operator::withdraw`, the omission is a clear, reachable authorization gap rather than a deployment-configuration issue.

### Recommendation
Add the same `aggregator_verification_address` / verification-signature check present in `withdraw` to `internal_withdraw` before calling `self.operator.withdraw(...)`, or remove/gate the `internal_withdraw` RPC method entirely behind the same authorization guard, so both entry points into the fund-broadcasting logic enforce that the caller is the authorized aggregator.

### Proof of Concept
1. An operator node exposes its gRPC service with `internal_withdraw` reachable (per `core/src/rpc/clementine.rs` service definition) and has `aggregator_verification_address` configured.
2. A caller crafts a valid `WithdrawParams` (`withdrawal_id`, `input_signature`, `input_outpoint`, `output_script_pubkey`, `output_amount`) referencing a real, Citrea-confirmed withdrawal outpoint (obtainable from public Citrea/Bitcoin state) and calls `internal_withdraw` directly.
3. Unlike `withdraw` (`core/src/rpc/operator.rs:192-239`), `internal_withdraw` (`core/src/rpc/operator.rs:168-190`) performs no ECDSA verification-signature check, so `Operator::withdraw` executes and the operator funds/broadcasts the payout transaction, entering the reimbursement lifecycle without the aggregator ever authorizing the action. [2](#0-1)
