## Analysis

The report's underlying flaw is a **single-step, unconfirmed transfer of a trust-critical value** — the contract overwrites `owner` from unvalidated input with no opportunity to review/revert. The direct Desktop analog is `updateRemoteUrl()` silently rewriting the local git remote (`origin`) based on the GitHub API's `clone_url` field — without any user confirmation — whenever the app auto-refreshes GitHub repository metadata.

### Title
Silent, unconfirmed rewrite of the `origin` remote URL from an untrusted GitHub API field - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` is invoked from `repositoryWithRefreshedGitHubRepository()` in `app-store.ts` during routine background refreshes of a repository's associated GitHub metadata [1](#0-0) . It compares the locally configured remote URL against the `clone_url` returned by the GitHub API and, if a set of heuristics pass, calls `gitStore.setRemoteURL()` to overwrite the remote — with no user prompt, diff view, or ability to reject the change [2](#0-1) .

### Finding Description
The decision to rewrite `origin` is based entirely on the `apiRepo.clone_url` field returned from `api.fetchRepository(owner, name)` [3](#0-2) , which is data sourced from the GitHub REST API (or a GitHub Enterprise Server instance). This is exactly the "GitHub API object" class of attacker-controlled input called out as in-scope. The guard conditions are:

- `protocolsMatch` — only requires that the parsed protocol strings match (`https`/`ssh`), not that the host is legitimate [4](#0-3) .
- `remoteUrlUnchanged` — requires the *current* remote to still match the *previously cached* `gitHubRepository.cloneURL` [5](#0-4) .
- `!urlsMatch` — the new `clone_url` differs from the current remote by owner/name/host per `urlMatchesRemote()` [6](#0-5) .

None of these checks validate that the new hostname is one the user actually trusts — `urlMatchesRemote` only compares owner/name/hostname structurally between two URLs, it does not check the new host against the account's expected endpoint. If satisfied, `gitStore.setRemoteURL(name, updatedRemoteUrl)` is called immediately, which shells out to `git remote set-url` [7](#0-6) [8](#0-7) . This is a direct behavioral analog of `transferOwnership()` overwriting `owner` in one step: a security-relevant pointer (the destination of all future pushes/fetches) is reassigned based on unauthenticated-trust input, with no two-step confirmation, diff display, or rollback path.

### Impact Explanation
If an attacker controls the GitHub API response for a repository the user has already cloned — e.g., a compromised or malicious GitHub Enterprise Server the user is enrolled with, or a MITM/DNS-hijacked GHE endpoint that Desktop is configured to trust — they can return a `clone_url` pointing at an attacker-controlled git host. On the next background metadata refresh, Desktop silently repoints `origin` to that attacker URL. Subsequent `git push` operations by the user (using Desktop's credential helper, which auto-attaches stored tokens for the matched account/endpoint per `findGitHubTrampolineAccount`) would then send the user's commits — and potentially the account's authentication material via the credential helper flow — to the attacker's repository instead of the legitimate one. This is silent corruption of where a user's commits/pushes land, matching the explicitly valid impact class.

### Likelihood Explanation
This path requires the attacker to control (or MITM) the GitHub/GHE API responses for a repository already tracked by the user — a scenario within the defined valid-impact class ("attacker controls...a GitHub API object...or a git remote/proxy response"). It does not require local/physical access, admin rights, or pre-existing malware, and the refresh is triggered automatically in the background rather than by unusual user action, so it does not depend on unnatural user steps.

### Recommendation
Do not silently rewrite `origin` based on API-reported `clone_url`. Require explicit user confirmation (e.g., a dialog showing old vs. new remote URL) before calling `setRemoteURL`, and/or validate that the new host matches the account's known/trusted endpoint (`account.endpoint`) rather than only comparing owner/name structure between two arbitrary URLs.

### Proof of Concept
1. User clones/associates a repository hosted on a GitHub Enterprise Server account added in Desktop.
2. Attacker compromises or MITMs that GHE server's API responses for `GET /repos/{owner}/{name}`, changing `clone_url` to `https://attacker-host/owner/name.git` (same protocol scheme, so `protocolsMatch` holds).
3. Desktop performs its normal periodic `repositoryWithRefreshedGitHubRepository` refresh, calling `updateRemoteUrl()` [9](#0-8) .
4. Since the previously cached `gitHubRepository.cloneURL` still matches the existing remote (`remoteUrlUnchanged`) and the new `clone_url` differs (`!urlsMatch`), `gitStore.setRemoteURL('origin', 'https://attacker-host/owner/name.git')` executes without any prompt [10](#0-9) .
5. The user's next push (and stored credentials via the credential helper) go to the attacker's host.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
