## Analysis

The external report's core broken invariant is: **a ledger/schedule is treated as authoritative and paid out from, while the actual asset movement that should back it is either absent or not yet finalized when the payout logic reads the ledger.** The direct Hyperbridge analog is not in vesting, but in the Intent Gateway's escrow-release function `withdraw()`, where the **Tron fork diverges from the canonical EVM contract by paying out funds before updating the escrow ledger**, breaking the checks-effects-interactions (CEI) pattern that the mainline contract correctly follows.

### Title
Escrow ledger updated after external token transfer in `IntentGatewayV2.withdraw()` (Tron fork) enables reentrant double-redemption of escrowed funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`withdraw()` in the Tron IntentGatewayV2 contract performs the outbound token transfer to the beneficiary **before** decrementing `_orders[commitment][token]`, the escrow accounting map. [1](#0-0)  The canonical (non-Tron) implementation in `IntentsBase.sol` does the opposite — it decrements the escrow ledger first, then performs the transfer — which is the correct CEI ordering. [2](#0-1)  This divergence reintroduces a classic reentrancy window around a fund-custody path that the mainline code has already hardened against.

### Finding Description
`withdraw()` is reached from two `onlyHost`-gated entry points, `onAccept` (for `RedeemEscrow`/`RefundEscrow` cross-chain settlement messages) and `onGetResponse` (for source-chain cancellation after a storage-proof confirms the order was never filled). [3](#0-2) [4](#0-3) 

Inside `withdraw()`, for every token in the withdrawal request the contract:
1. Checks `_orders[commitment][token] == 0` (presence only, not sufficiency).
2. Performs a low-level external call — either a native `.call{value: amount}("")` to an attacker-controlled `beneficiary`, or a raw `token.call(...IERC20.transfer...)` to an attacker-controlled `token` address.
3. Only afterwards decrements `_orders[body.commitment][token] -= amount`. [5](#0-4) 

Both `token` (from `order.inputs[i].token`, set freely by the order creator at `placeOrder` time) and `beneficiary` (the order's `user` for refunds, or the filling `msg.sender` for redemptions) are attacker-controlled values with no allowlist. [6](#0-5)  An attacker can therefore place an order whose input token is a malicious ERC20 contract they fully control (or whose beneficiary is a contract with a reentrant `receive()` for native-token orders). When `withdraw()` executes the low-level call, control transfers to attacker code *while `_orders[commitment][token]` still reflects the pre-payout balance* — the "guard" (`== 0` check) has already passed and the ledger has not yet been debited.

The host's message handler explicitly supports processing multiple ISMP messages in a single external call (`HandlerV2` "Supports batch call execution via `batchCall`"), which is the mechanism by which a second message targeting the same order commitment could be delivered and processed from within the attacker's reentrant callback before the first call's decrement has landed. I was not able to fully trace `HandlerV2`'s per-message reentrancy protections within the available tool budget, so whether a second `onAccept`/`onGetResponse` call for the *same* commitment can be nested inside the first remains unconfirmed — this is the one open question in an otherwise concrete, locally-verifiable divergence from the safe reference implementation.

### Impact Explanation
If the reentrant path into a second settlement/cancellation message for the same commitment is reachable (via the host's batch-call surface or any other re-entry into `onAccept`/`onGetResponse` mid-callback), an attacker can redeem the same escrowed input tokens more than once — a direct double-settlement / fund-loss condition matching the bounty's "stealing or loss of funds" and "replay/double-claim/double-settlement" categories. Even absent a demonstrated second-message reentry, the CEI violation is a real regression relative to the audited mainline contract and is the exact bug class (ledger trusted before the underlying balance movement is finalized) that the external report describes.

### Likelihood Explanation
Both attacker-controlled inputs needed to trigger the external call (a malicious `token` address, or a malicious `beneficiary` contract for native transfers) are freely settable by any unprivileged user at `placeOrder()`/order-fill time — no privileged, relayer, or governance role is required to set up the preconditions. The only uncertainty is whether the host's message-processing surface (`batchCall`, `handlePostRequests`) allows a nested call back into a second pending message for the same commitment while the first is still mid-execution; this determines whether the reentrancy is fully weaponizable end-to-end or "merely" a CEI-hygiene defect.

### Recommendation
Reorder `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to match `IntentsBase.sol`: decrement `_orders[body.commitment][token]` (and the `TRANSACTION_FEES` entry) **before** performing the external native/ERC20 transfer, for every token in the loop and for the fee payout. Additionally, add a `nonReentrant` guard to `onAccept` and `onGetResponse` (mirroring the guard already used on `placeOrder`) as defense-in-depth against any other cross-entry-point reentrancy in the Tron fork.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer(to, amount)` function, when called from `IntentGatewayV2`, re-enters the Hyperbridge host/handler to submit or trigger processing of a second already-relayed settlement message (`RedeemEscrow`/`RefundEscrow`) for the same order `commitment`.
2. Attacker places an order via `placeOrder` on the source chain with `order.inputs[0].token = EvilToken`, escrowing `amount` of `EvilToken`. [6](#0-5) 
3. A legitimate solver fills the order cross-chain, and the resulting `RedeemEscrow` message is delivered to the source chain, invoking `onAccept` → `withdraw()`. [3](#0-2) 
4. Inside `withdraw()`'s loop, `_orders[commitment][EvilToken]` is checked non-zero, then `EvilToken.transfer(beneficiary, amount)` is invoked via low-level call — handing control to attacker code before `_orders[commitment][EvilToken] -= amount` executes. [7](#0-6) 
5. From within `EvilToken.transfer`, the attacker triggers processing of a second pending message for the same commitment (e.g., a queued `RefundEscrow`/duplicate `RedeemEscrow` proof via the handler's batch-processing surface). Because `_orders[commitment][EvilToken]` has not yet been decremented, the second `withdraw()` call's `== 0` check also passes, paying out the same escrowed balance twice.

**Confidence caveat:** step 5's exact reachability depends on `HandlerV2`/`EvmHost` reentrancy behavior across batched or nested message processing, which I could not fully verify within the available investigation budget — a Devin session with full repo access should confirm whether `handlePostRequests`/`batchCall` can be re-entered for a second commitment-bearing message mid-callback to fully validate exploitability, independent of the confirmed CEI-ordering defect itself.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
