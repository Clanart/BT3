### Title
Alpenglow per-epoch delegator reward calculation rounds small stakers' earned credits to zero and then permanently advances `credits_observed`, silently forfeiting their rewards - (File: `runtime/src/inflation_rewards/points.rs`, `runtime/src/inflation_rewards/mod.rs`)

### Summary
The Alpenglow (post-migration) stake reward path computes a delegator's epoch reward as a proportional share of the vote account's total stake using integer division:
`earned_credits * stake_amount / total_stake`. When a staker's `stake_amount` is small relative to the vote account's aggregate delegated stake, this expression truncates to zero even though the staker genuinely earned a nonzero share. Unlike the Tower epoch path — which explicitly refuses to advance `credits_observed` when the reward rounds to zero — the Alpenglow path unconditionally advances `credits_observed` to the current vote credits regardless of whether the computed reward was zero. Because Alpenglow does not accumulate "points" across epochs, this watermark advance permanently forfeits that epoch's real (rounded-away) reward with no path to recover it later. This mirrors the reported `PirexRewards.claim` bug class: a ratio-based reward computation rounds to zero for a "too small" party, and the corresponding accounting/watermark state is cleared/advanced anyway, causing that party's real accrued reward to be lost.

### Finding Description
The Alpenglow points/reward path is: [1](#0-0) 

```
let earned_points = if earned_credits == 0 || stake_amount == 0 {
    0
} else {
    ...
    earned_credits * stake_amount / total_stake as u128
};
```

`earned_credits` and `new_credits_observed` are computed unconditionally by `calc_earned_credits` before this division: [2](#0-1) 

`new_credits_observed` is advanced to `final_epoch_credits` regardless of what the subsequent division yields — it is not gated on `earned_points > 0`.

The resulting `ag_points` is then used *directly* as the lamport reward (Alpenglow does not scale it through `PointValue.rewards/points` like Tower does): [3](#0-2) 

If `ag_points == 0`, `skip_reward(SkippedReason::ZeroPoints)` is invoked. Crucially, whether the skip actually preserves state depends on `is_tower_epoch`: [4](#0-3) 

```
let is_tower_epoch = matches!(ag_epoch_type, AlpenglowEpochType::Tower);
let advance_credits_for_skipped_reward =
    !is_tower_epoch && new_credits_observed != stake.credits_observed;
...
let skip_reward = |reason: SkippedReason| {
    ...
    if advance_credits_for_skipped_reward {
        skipped_reward()   // returns Some(...) with new_credits_observed set — advances the watermark
    } else {
        None                // Tower: leaves credits_observed untouched, preserving the unpaid points
    }
};
```

For `AlpenglowEpochType::Tower`, `is_tower_epoch == true`, so `advance_credits_for_skipped_reward` is `false` and the watermark is *not* advanced when the reward rounds to zero — this is the correct mitigation (matching Recommendation #2 in the referenced report: don't clear accrued state if the payout is zero). But for Alpenglow (`is_tower_epoch == false`), `advance_credits_for_skipped_reward` becomes `true` whenever `new_credits_observed != stake.credits_observed` (which is the normal case whenever the vote account recorded new credits that epoch). The returned `CalculatedStakeRewards { staker_rewards: 0, voter_rewards: 0, new_credits_observed }` is then applied unconditionally in the caller: [5](#0-4) 

```
.map(|calculated_stake_rewards| {
    ...
    stake.credits_observed = calculated_stake_rewards.new_credits_observed;
    (calculated_stake_rewards.staker_rewards, calculated_stake_rewards.voter_rewards)
});
```

Because Alpenglow computes rewards per-epoch directly from `(this_epoch_credits, this_epoch_stake_share)` rather than accumulating cross-epoch "points" (as the code comment notes: "Full AG only considers the latest epoch credit entry"), there is no later epoch in which the truncated fraction can be recovered — moving `credits_observed` forward erases the record that this epoch's credits were ever unredeemed.

### Impact Explanation
Any unprivileged delegator whose stake is small relative to the total stake delegated to their chosen validator's vote account can have their entire epoch reward silently rounded to zero and then permanently lost, because `credits_observed` is advanced past the epoch as if it had been paid. Concretely, for a validator with total effective stake `T` lamports, a delegator earns zero for an epoch whenever `stake_amount < T / earned_credits`; with `earned_credits` bounded by credits-per-epoch and `T` scaling with the validator's total delegated stake, ordinary small-scale delegators to popular/large validators are the ones most likely to repeatedly hit this zero-reward-and-forfeit condition — this is a genuine, non-malicious loss of expected staking yield for regular users, i.e., "fund loss" for an unprivileged party, matching the reported bug class (as opposed to attacker-driven theft).

### Likelihood Explanation
This does not require any malicious actor, privileged role, or crafted transaction — it triggers automatically during ordinary reward calculation (`calculate_stake_rewards` / `calculate_alpenglow_points`) whenever a delegator's proportional stake share is small enough to truncate under integer division, which is common for the long tail of small delegators to large validators once Alpenglow is active. The existing guard (`advance_credits_for_skipped_reward = false` for Tower) shows this exact hazard was already recognized and mitigated in the legacy Tower path but the same protection was not carried over to the Alpenglow branch.

### Recommendation
Apply the same protection used for Tower epochs to the Alpenglow branch: do not advance `stake.credits_observed`/`new_credits_observed` when the computed `ag_points`/reward is zero solely due to rounding (i.e., when `earned_credits > 0 && stake_amount > 0` but the division truncates to zero), or alternatively carry forward the truncated remainder (e.g., accumulate fractional credit debt) so a delegator's real earned share is redeemed in a later epoch instead of being discarded. At minimum, `skip_reward` should distinguish "genuinely zero activity" from "rounded-to-zero nonzero activity" and only advance the watermark in the former case.

### Proof of Concept
1. Delegator A stakes a small amount (e.g., 10 SOL = 1e10 lamports) to validator V, whose total effective Alpenglow-tracked stake (`total_active_stake` / `reward_epoch_delegated_stakes`) is large (e.g., 5,000,000 SOL ≈ 5e15 lamports), as is typical for a heavily-delegated validator.
2. During an epoch, V's vote account records `earned_credits` for the epoch (bounded, e.g., ~200,000 credits, one per slot voted on).
3. At epoch boundary, `calculate_alpenglow_points` (`runtime/src/inflation_rewards/points.rs:280-301`) computes:
   `earned_points = earned_credits * stake_amount / total_stake = 200,000 * 1e10 / 5e15 = 0` (since `200,000 * 1e10 = 2e15 < 5e15`).
4. `calculate_stake_rewards` (`runtime/src/inflation_rewards/mod.rs:278-285`) sees `ag_points == 0` and calls `skip_reward(SkippedReason::ZeroPoints)`.
5. Since `is_tower_epoch == false` (Alpenglow) and `new_credits_observed != stake.credits_observed` (true because the vote account recorded new credits), `advance_credits_for_skipped_reward == true`, so `skip_reward` returns `Some(CalculatedStakeRewards{ staker_rewards: 0, voter_rewards: 0, new_credits_observed })`.
6. `redeem_stake_rewards` (`runtime/src/inflation_rewards/mod.rs:139`) sets `stake.credits_observed = new_credits_observed`, permanently moving the watermark past the epoch whose reward was real but rounded away.
7. Delegator A receives 0 lamports for that epoch and has no way to reclaim the truncated fraction in any later epoch, since Alpenglow computes rewards per-epoch from the latest credit entry only, not from accumulated points — unlike the Tower path, which explicitly avoids this by not advancing `credits_observed` in the analogous situation.

fn calc_earned_credits(
    stake: &Stake,
    final_epoch_credits: u64,
    initial_epoch_credits: u64,
    new_credits_observed: &mut u64,
) -> u128 {
    let credits_in_stake = stake.credits_observed;

    // figure out how much this stake has seen that
    //   for which the vote account has a record
    let earned_credits = if credits_in_stake < initial_epoch_credits {
        // the staker observed the entire epoch
        final_epoch_credits - initial_epoch_credits
    } else if credits_in_stake < final_epoch_credits {
        // the staker registered sometime during the epoch, partial credit
        final_epoch_credits - *new_credits_observed
    } else {
        // the staker has already observed or been redeemed this epoch
        //  or was activated after this epoch
        0
    };
    *new_credits_observed = (*new_credits_observed).max(final_epoch_credits);
    u128::from(earned_credits)
}
