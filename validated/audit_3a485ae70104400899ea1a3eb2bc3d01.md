### Title
Attacker-supplied serialized `ThresholdKeys` is trusted without binding the secret share to the verification shares / group key, allowing a malicious "key secret" to silently replace the signing identity - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) deserializes a `t`, `n`, `i`, an interpolation table, a raw `secret_share`, and `n` arbitrary group elements as `verification_shares`, then calls `ThresholdKeys::new`, which only checks share counts and participant index bounds (crypto/dkg/src/lib.rs:355-365) and derives `group_key` solely from `verification_shares[1..=t]` (crypto/dkg/src/lib.rs:376-378). It never verifies that `secret_share * C::generator() == verification_shares[i]` nor that the resulting group key matches any externally expected key. This mirrors the external report's class: attacker-controlled bytes inside a secret/credential blob are consumed by a privileged component (the threshold signer) and reinterpreted as authoritative identity material, escalating what should be data-plane input into control-plane authority over the signing identity.

### Finding Description
The in-scope reachable entry point is `ThresholdKeys::read`, explicitly listed as an untrusted-bytes sink. A crafted encoding provides:

- `secret_share = s'` chosen by the attacker,
- `verification_shares = { l -> Y'_l }` with `Y'_i = s' * G` and the remaining entries forming any polynomial-consistent set whose interpolation over participants `1..=t` yields an attacker-chosen `Y'`,
- valid `t`, `n`, `i` and `Interpolation::Lagrange`.

`ThresholdKeys::new` accepts this because `group_key` is computed as `Σ_{i=1..=t} Y_i * λ_i` from the supplied points alone (crypto/dkg/src/lib.rs:376-378). The code itself acknowledges the gap: `AlgorithmSignatureMachine::complete` comments that reaching the internal error path is possible "to deserialize a semantically invalid FrostKeys" (crypto/frost/src/sign.rs:492-494). With a *consistent* forgery no error is ever raised: `view()` interpolates `s'` into `ThresholdView::secret_share` (crypto/dkg/src/lib.rs:494-498), `sign_share` produces shares, `verify_share` checks them against the forged `verification_shares`, and `algorithm.verify` accepts the aggregate under the forged `group_key()` (crypto/frost/src/sign.rs:465-489). Every validation layer passes because all checks are self-referential to the attacker-supplied blob.

### Impact Explanation
Any party able to feed serialized key material to `ThresholdKeys::read` (a malicious/corrupted key secret, mirroring the malicious credential-in-DNS-secret of the external report) obtains signatures that verify under a group key fully controlled by the attacker, while the rest of the system believes it is operating the original threshold key. Since `read`/`write` do not serialize the ephemeral scalar/offset (crypto/dkg/src/lib.rs:537-561) and nothing re-derives the expected group key, the forged identity is indistinguishable from the real one to downstream `group_key()` consumers (crypto/dkg/src/lib.rs:445-447). This is a privilege-escalation-style identity substitution: the signer produces valid FROST/Schnorr signatures for an attacker-chosen public key, enabling signatures on unintended keys/messages and, where `group_key` maps to a Bitcoin address, funds routed to / attestations made under attacker control.

### Likelihood Explanation
Exploitation requires the attacker to control the bytes passed to `ThresholdKeys::read` — a credential/config-plane condition rather than a network message, which is exactly the deployment shape of the referenced CVE (malicious values inside an operator-supplied secret). Within that threat model the attack is deterministic: no checks defeat it since consistency can be made perfect. It is not reachable purely from in-band signing-protocol messages (`read_preprocess`, `read_share`, `EncryptedMessage::read`), limiting it to environments where key blobs cross a trust boundary.

### Recommendation
In `ThresholdKeys::new` (and thus `read`), enforce `secret_share * C::generator() == verification_shares[&params.i()]`, rejecting `InvalidSecretShare` otherwise. Additionally, bind the group key externally: have callers compare `group_key()` against the value established by the DKG/protocol context rather than trusting the self-derived interpolation, and consider serializing a hash/commitment of the expected group key inside the blob so `read` can authenticate it.

### Proof of Concept
```rust
// crypto/dkg context; Ristretto shown for concreteness
let n: u16 = 3; let t: u16 = 2; let i = Participant::new(1).unwrap();

// Attacker-chosen secret and fully consistent forged shares
let s_prime = <Ristretto as Ciphersuite>::F::random(&mut OsRng);
let mut verification_shares = HashMap::new();
// degree-(t-1) polynomial p with p(1) = s_prime; p(0) = attacker group secret y
let y = <Ristretto as Ciphersuite>::F::random(&mut OsRng);
let a = s_prime - y; // p(x) = y + a*x
for l in 1..=n {
    let l_f = <Ristretto as Ciphersuite>::F::from(u64::from(l));
    verification_shares.insert(
        Participant::new(l).unwrap(),
        Ristretto::generator() * (y + a * l_f),
    );
}

let keys = ThresholdKeys::<Ristretto>::new(
    ThresholdParams::new(t, n, i).unwrap(),
    Interpolation::Lagrange,
    Zeroizing::new(s_prime),
    verification_shares,
).unwrap();

// group_key is the attacker's key y*G; every subsequent sign()/complete()
// produces signatures valid under it, with no error raised anywhere.
assert_eq!(keys.group_key(), Ristretto::generator() * y);
```
Serializing this via `write` and reloading via `ThresholdKeys::read` preserves the forged identity, demonstrating that deserialization of an attacker-influenced key secret escalates to full control of the signing identity.

Note: this analog depends on serialized key blobs crossing a trust boundary (the credential-in-secret scenario of the report). I verified the parsing/validation path in `crypto/dkg/src/lib.rs` and the consuming path in `crypto/frost/src/sign.rs`; I did not enumerate every upstream caller of `ThresholdKeys::read` in `processor/`/`coordinator/` (out of the stated in-scope set), so the exact injection surface is integrator-dependent.
