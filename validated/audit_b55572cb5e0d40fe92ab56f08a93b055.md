### Title
Non-atomic escrow-then-unescrow in `ConvertCoinNativeERC20` permanently strands refunded IBC coins in the `x/erc20` module account when the native ERC20 transfer reverts - (File: x/erc20/keeper/msg_server.go, x/erc20/keeper/ibc_callbacks.go)

### Summary
The Ajna report describes funds becoming permanently frozen because a withdraw path unconditionally sends value to a fixed address (`msg.sender`) with no fallback if that transfer fails/reverts (e.g., blacklist). The Cosmos EVM analog is in the IBC refund path (`OnTimeoutPacket` / error-ack `OnAcknowledgementPacket`) of `x/erc20`, where `ConvertCoinToERC20FromPacket` calls `ConvertCoinNativeERC20`, which escrows the user's bank `Coin` into the module account **before** attempting to unescrow the backing native ERC20 tokens via an EVM call. If that EVM call reverts (e.g., the underlying "native ERC20" contract implements pausable/blacklist logic — functionally identical to the USDC-blacklist scenario in the original report), the error is caught and swallowed by `ConvertCoinToERC20FromPacket`, which returns `nil` (success), but the escrow step that already ran is never rolled back.

### Finding Description
`ConvertCoinNativeERC20` [1](#0-0)  performs, in sequence, on the live `sdk.Context` (no `ctx.CacheContext()` wrapping to guarantee atomicity across the two operations):

1. `bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins)` — escrows the user's bank `Coin` into the `x/erc20` module account.
2. `evmKeeper.CallEVM(.... "transfer" ....)` — attempts to unescrow the backing native ERC20 tokens from the module's EVM balance to the receiver.
3. Only if step 2 succeeds does it `BurnCoins` the escrowed amount.

If step 2 reverts or returns an unexpected result, the function returns an error, but step 1's state write is already committed to the KVStore (it is not part of a cached/branched context that gets discarded on error).

This function is invoked from the IBC refund path `ConvertCoinToERC20FromPacket` [2](#0-1) , called on `OnTimeoutPacket` and error-ack `OnAcknowledgementPacket` [3](#0-2) . When `ConvertCoinNativeERC20` errors, this handler explicitly swallows the error, emits a `EventTypeFailedConvertERC20` event, and returns `nil` — i.e., treats the entire refund/timeout handling as successful. The code comments explicitly (and incorrectly) assume this is safe: *"...OnTimeoutPacket still succeeds, but the user receives the corresponding bank token from the TokenPair instead."* [4](#0-3)  — but the code does not actually guarantee the user retains the bank coin, because the escrow step already moved it to the module account before the failure was detected.

The same non-atomic sequence exists on the "happy path" `OnRecvPacket` case for native ERC20 (`k.ConvertCoinNativeERC20(...)` call) [5](#0-4) , though there an error at least returns an error acknowledgement (though whether that triggers a proper multistore rollback of the already-executed escrow depends on how the IBC/ICS4 stack branches context for the whole `OnRecvPacket` call — the failure here is deeper in a middleware call inside `OnRecvPacket`, not in the outer transfer-module receive that IBC-go itself branches/rolls back).

The blacklist/pausable failure mode is directly analogous to the Ajna report: any native ERC20 contract registered as a token pair that can revert a `transfer()` call for a given address (blacklist, pause, allowance-based deny-list, or any other legitimate ERC20 behavior) triggers this. This is not a contrived edge case — pausable and blacklistable ERC20 tokens (USDT/USDC-style) are common and would be expected candidates for token-pair registration on any production Cosmos EVM chain bridging real-world assets.

### Impact Explanation
When the unescrow transfer reverts during an IBC timeout/error-ack refund, the user's originally-sent coin is moved into the `x/erc20` module account and burned-coins step never runs, leaving:
- The user's bank balance permanently reduced by the refund amount.
- The `x/erc20` module account permanently holds the escrowed Coin with no code path to return it (the IBC callback reports success/no-op, so no retry is scheduled, and there is no user-facing recovery method for this specific stuck state).
- The backing native ERC20 tokens remain locked in the module's EVM balance as well, since the burn never executes, potentially causing the coin-supply vs. token-escrow invariant to also decouple.

This is a permanent, irreversible loss/freezing of user principal funds triggerable by ordinary IBC transfer usage combined with an unprivileged (or governance-registered, but externally-controlled) ERC20 contract, matching the "Critical permanent freezing/theft of user funds" impact class.

### Likelihood Explanation
Requires (a) a native ERC20 token pair whose contract can revert a `transfer()` for specific addresses/conditions (pausable or blacklistable tokens are common in production), and (b) an IBC transfer of that denom that times out or receives an error acknowledgement. Both are realistic, low-privilege, externally-triggerable conditions — a relayer failing to relay in time, a receiving chain rejecting the packet, or the token issuer pausing/blacklisting the sender's address between send and refund are all ordinary, non-privileged events.

### Recommendation
Wrap the escrow-then-unescrow sequence in `ConvertCoinNativeERC20` in an explicit `ctx.CacheContext()` (or `CacheMultiStore`) and only `Write()` the changes if both the escrow and the EVM unescrow/transfer succeed; otherwise discard all writes so the user's Coin balance is left untouched. In the IBC callback paths (`ConvertCoinToERC20FromPacket`, `OnRecvPacket`), ensure that a failure from `ConvertCoinNativeERC20` truly results in the sender/receiver retaining their original bank Coin (as the code comments claim), rather than assuming this is automatically the case.

### Proof of Concept
1. Register a native ERC20 token pair (`RegisterERC20`) for a token contract implementing pause/blacklist logic that can be toggled to revert `transfer()` calls for a specific address.
2. Convert some ERC20 balance to the mirrored bank Coin via `ConvertERC20`, then perform an IBC transfer of that Coin denom to another chain.
3. Cause the transfer to fail on the receiving chain (reject/timeout) so that `OnTimeoutPacket`/error-ack `OnAcknowledgementPacket` fires, invoking `ConvertCoinToERC20FromPacket` → `ConvertCoinNativeERC20`.
4. Before the refund processes, toggle the ERC20 contract to blacklist/pause the sender's address so the `transfer()` EVM call inside `ConvertCoinNativeERC20` reverts.
5. Observe: `ConvertCoinToERC20FromPacket` returns `nil` (packet lifecycle treated as fully handled), the sender's bank Coin balance is not restored, and the amount is permanently held in the `x/erc20` module account, with the corresponding native ERC20 tokens still locked in the module's own EVM balance and never burned.

Note: I could not fully trace whether IBC-go's outer transfer-module context branching would independently roll back the escrow write in the `OnRecvPacket` case (this depends on ibc-go v10 internals not fully covered by the indexed code), so the strongest, clearly-demonstrated instance of this bug is the `OnTimeoutPacket`/error-ack refund path, where the error is explicitly and intentionally swallowed in `x/erc20` code itself.

```go
func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}
```

```go
func (k Keeper) OnAcknowledgementPacket(
	ctx sdk.Context, _ channeltypes.Packet,
	data transfertypes.FungibleTokenPacketData,
	ack channeltypes.Acknowledgement,
) error {
	switch ack.Response.(type) {
	case *channeltypes.Acknowledgement_Error:
		// convert the token from Cosmos Coin to its ERC20 representation
		return k.ConvertCoinToERC20FromPacket(ctx, data)
	default:
		// the acknowledgement succeeded on the receiving chain so nothing needs to
		// be executed and no error needs to be returned
		return nil
	}
}

// OnTimeoutPacket converts the IBC coin to ERC20 after refunding the sender
// since the original packet sent was never received and has been timed out.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnTimeoutPacket still
// succeeds, but the user receives the corresponding bank token from the TokenPair
// instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnTimeoutPacket(ctx sdk.Context, _ channeltypes.Packet, data transfertypes.FungibleTokenPacketData) error {
	return k.ConvertCoinToERC20FromPacket(ctx, data)
}
```
