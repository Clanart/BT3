### Title
Empty aggregate signature accepted as valid - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` accepts an aggregate containing zero signatures when `s = 0`, even though `SchnorrAggregator::complete` explicitly refuses to produce an empty aggregate. [1](#0-0) 

### Finding Description
`SchnorrAggregate::read` accepts a zero length without treating an empty aggregate as invalid. [2](#0-1) 

During verification, an empty `Rs` matches an empty `keys_and_challenges`, the signature loop adds no weighted statement, and only `(-s)G` remains. [3](#0-2) 

For `s = 0`, that remaining multiexponentiation is the identity, so `verify` returns `true`. [4](#0-3) 

This is inconsistent with the producing API, which returns `None` instead of constructing an aggregate when no signatures were supplied. [1](#0-0) 

### Impact Explanation
An attacker can submit a serialized empty aggregate and have it accepted as a valid aggregate signature for an empty verification batch. [2](#0-1) 

Because the producer explicitly rejects empty aggregation, this is an unauthentic serialized signature rather than an intended representation. [5](#0-4) 

### Likelihood Explanation
The attack is reachable wherever an unauthenticated party controls serialized aggregate bytes and the verifier can process an empty `keys_and_challenges` list. [2](#0-1) 

For ciphersuites with a 32-byte scalar encoding, the complete malicious encoding is 36 zero bytes: four bytes for `Rs.len() == 0` followed by a canonical zero scalar. [2](#0-1) 

### Recommendation
Reject `Rs.is_empty()` in `SchnorrAggregate::read` and defensively reject it in `SchnorrAggregate::verify`. [2](#0-1)
