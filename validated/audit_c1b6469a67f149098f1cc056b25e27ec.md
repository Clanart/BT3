### Title
Checks-Effects-Interactions violation in `IntentGatewayV2.withdraw` allows reentrant double-redemption of escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` performs the external token transfer (`token.call(...transfer...)` / native `.call{value:}`) **before** decrementing the `_orders[commitment][token]` escrow accounting, and only checks that the escrow entry is non-zero rather than that it is sufficient for the requested amount. This is structurally the same defect class as the reported Trie bug: the guard (`_orders[...][token] == 0`) verifies *existence* but not *correctness/sufficiency* before the state that depends on it is mutated — and here the state mutation happens strictly after an untrusted external call, opening a reentrancy window that lets a malicious escrowed token drain the same commitment's escrow multiple times.

### Finding Description
In `withdraw()`, called from `onAccept()` when a `RedeemEscrow`/`RefundEscrow` message settles on the source chain: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();       // (1) existence-only check

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");                // (2) external interaction FIRST
            ...
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            ...
        }

        _orders[body.commitment][token] -= amount;                             // (3) accounting updated AFTER
        ...
    }
```

Compare this to the audited EVM-mainline equivalent, `IntentsBase._withdraw`, which decrements escrow **before** the external transfer: [2](#0-1) 

```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;   // effect BEFORE interaction
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    ...
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
```

The Tron contract inverts this ordering. Because `token` is attacker-controlled at order-placement time (any ERC20-like address can be escrowed as an "input"), a malicious token contract can be crafted so that its `transfer` implementation calls back into the host, which re-dispatches into `onAccept`/`withdraw` for the *same* `body.commitment` before `_orders[body.commitment][token]` has been decremented. Since the guard only checks `!= 0` (not `>= amount`), the reentrant call passes the same check again and triggers a second `transfer` for the same escrowed balance, i.e. a double-redemption of the escrow before the first call's decrement is applied — the exact "found but not validated" flaw described in the seed report, here manifesting as a state-mutation-after-interaction bug rather than a mutation-without-existence-check bug.

The repo already contains a dedicated reentrancy test file (`IntrinsicIntentsReentrancyTest.sol`) confirming this bug class is a recognized concern for the intents contracts, but this test coverage targets `IntrinsicIntents`, not this Tron `IntentGatewayV2.withdraw` path, and this particular function does not follow the checks-effects-interactions pattern that the other confirmed-safe implementation uses.

### Impact Explanation
This falls squarely within the bounty's "stealing or loss of funds" and "double-claim/double-settlement" categories: escrowed bridge funds locked for a cross-chain intent order can be redeemed more than once against the same commitment, draining the contract's actual token balance for other legitimate orders and directly causing bridge custody loss. The entry point (`onAccept`, gated by `onlyHost`) is reached through the normal, permissionless cross-chain settlement flow — no relayer collusion, malicious prover, or governance action is required; the only requirement is that one of the order's escrowed input tokens be a malicious/attacker-deployed token contract, which is attacker-controlled at order-placement time.

### Likelihood Explanation
Likelihood is moderate-to-high in isolation: order inputs are user-specified `TokenInfo.token` addresses at `placeOrder` time, so an attacker can escrow a custom malicious "token" as one of the order's inputs, then trigger settlement (fill on destination, causing a `RedeemEscrow` post request back to source) to land on `onAccept`, invoking `withdraw` and the reentrant callback. The `onlyHost` modifier restricts the caller to the legitimate `EvmHost`, but does not prevent the callback the malicious token issues during its own `transfer()` execution from re-entering the gateway (there is no `nonReentrant` guard on `withdraw`/`onAccept` in this file).

### Recommendation
Reorder `withdraw()` to follow checks-effects-interactions: validate `amount <= _orders[body.commitment][token]` and decrement `_orders[body.commitment][token] -= amount` *before* performing any external call (native send or ERC20 transfer), matching the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`. Additionally add a `nonReentrant` guard around `onAccept`/`withdraw` as defense in depth, and replace the raw `== 0` existence check with a sufficiency check (`amount > _orders[...][token]` should revert) so a corrupted/insufficient escrow can never authorize a transfer.

### Proof of Concept
1. Attacker places an order on the source chain (`placeOrder`) with an input token pointing to a malicious contract `EvilToken` that the attacker controls. `EvilToken.transfer()` is implemented to, on its first invocation for a given `beneficiary`/`amount`, call back into the `EvmHost`'s ISMP inbound path (or directly reconstruct/deliver a duplicate incoming request through the relayer they control acting on the same underlying signed cross-chain message, if replay of the message itself is otherwise blocked, the reentrant path is via calling back into any function that reaches `withdraw` for the same commitment, e.g. re-entering through `onGetResponse`'s cancellation path or a second in-flight `onAccept` dispatch for the same commitment) before returning.
2. The order is filled on the destination chain, causing the destination `IntentGatewayV2` to dispatch a `RedeemEscrow` `PostRequest` back to source.
3. When the host delivers this request to `onAccept` → `withdraw`, execution reaches `token.call(...transfer...)` for `EvilToken` while `_orders[commitment][EvilToken]` is still non-zero (not yet decremented).
4. `EvilToken.transfer()` reenters and, hitting the same `_orders[commitment][EvilToken] == 0` check (still non-zero), forces a second transfer of `amount` for the same commitment before the first call's `_orders[...] -= amount` executes.
5. Both invocations complete, net effect: `amount` is paid out twice against a single escrowed deposit, draining contract balance meant for other users' orders.

**Note on verification**: I was unable to execute this PoC in a live environment — this is a static code-review analog derived from comparing `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw` against the CEI-compliant `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`. Confirming exploitability end-to-end (in particular whether any upstream replay/duplicate-delivery protection in `EvmHost`/`HandlerV2` fully blocks the reentrant second call before it reaches `onAccept`) would require running the existing Foundry test suite (e.g. extending `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`-style tests against this Tron contract) in a Devin session with full repository and toolchain access.
