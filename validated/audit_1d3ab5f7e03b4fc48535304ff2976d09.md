## Analysis

The Mochi bug's core invariant break is: **an externally-influenced ID/pointer gets rolled back, and the write path that keys off that pointer has no "already occupied" check, so a later write silently clobbers a slot that legitimately belonged to prior, unrelated state.**

The direct local analog is in `EvmHost.sol`'s state-machine-commitment bookkeeping, which lacks the duplicate-height guard that the Substrate ISMP core enforces.

### Title
Fisherman veto resets `_latestStateMachineHeight` to a fixed sentinel, re-opening already-committed heights to silent overwrite in `EvmHost`/`HandlerV2` - (File: `evm/src/core/EvmHost.sol`, `evm/src/core/HandlerV2.sol`)

### Summary
`EvmHost.storeStateMachineCommitment` unconditionally overwrites `_stateCommitments[stateMachineId][height]` with no check that a commitment already exists at that height [1](#0-0) . The gating check lives entirely in `HandlerV2.handleConsensus`, which only requires `intermediate.height > latestHeight` [2](#0-1) . When a fisherman vetoes the *current latest* height via `deleteStateMachineCommitment`, `_latestStateMachineHeight` is reset to the hardcoded value `1` rather than the previous valid height [3](#0-2) . This re-opens every height in the range `(1, current tip]` — including heights that already hold a legitimately stored, previously-verified `StateCommitment` — to be re-accepted and silently overwritten by the next consensus proof, because there is no per-height "already stored" check like the one Substrate's core enforces (`if host.state_machine_commitment(state_height).is_ok() { continue; }`) [4](#0-3) .

### Finding Description
`StateMachineHeight` on EVM is keyed only by `(stateMachineId, height)` — a bare `uint256 => uint256 => StateCommitment` mapping [5](#0-4) . The write path (`storeStateMachineCommitment`, called only by the `handler`) never checks whether that slot is already populated before overwriting it:

```solidity
function storeStateMachineCommitment(StateMachineHeight memory height, StateCommitment memory commitment)
    external
    restrict(_hostParams.handler)
{
    _stateCommitments[height.stateMachineId][height.height] = commitment;
    ...
}
``` [1](#0-0) 

The only guard preventing arbitrary overwrite lives one layer up in `HandlerV2.handleConsensus`, and it is purely a monotonicity check against the *latest* pointer, not an existence check against the specific height being written:

```solidity
uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
if (latestHeight != 0 && intermediate.height > latestHeight) {
    host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
}
``` [2](#0-1) 

The `latestHeight` pointer itself is not append-only-safe: when a fisherman vetoes the current latest height (a normal, permissionless-by-design safety mechanism, documented as "called when vetoed by a fisherman"), the pointer is reset to the literal constant `1`, not to the previous known-good height:

```solidity
function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
    StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
    delete _stateCommitments[height.stateMachineId][height.height];
    delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
    if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
        _latestStateMachineHeight[height.stateMachineId] = 1;
``` [6](#0-5) 

Once that reset happens, `intermediate.height > 1` is true for essentially every height that has ever been committed on that chain (except height 1 itself). So the very next consensus proof processed by `handleConsensus` — a fully permissionless entrypoint, callable by anyone — can supply an `IntermediateState` for a height well *below* the pre-veto tip, and `storeStateMachineCommitment` will overwrite whatever `StateCommitment` (overlay root / state root / timestamp) was already legitimately stored there, with zero check that the slot was occupied.

This is precisely the Mochi pattern: a governance/maintenance-adjacent action (vetoing a bad height — a defensive, non-malicious operation) resets an ID/pointer used to key protected state, and the downstream write function that uses that pointer to gate access has no "slot already occupied" check, so subsequent legitimate-looking writes clobber state that other parts of the protocol still depend on.

### Impact Explanation
`stateMachineCommitment(height)` is the trust anchor consumed by every downstream verifier: `handlePostRequests` verifies the MMR multiproof against `stateMachineCommitment(height).overlayRoot` [7](#0-6) , and `handlePostRequestTimeouts`/`handleGetRequestTimeouts` verify non-membership proofs against `.stateRoot` [8](#0-7) . If an already-stored commitment at a given height is silently replaced, any request/response/timeout dispatch that later references that height is verified against a different root than the one relayers and integrators originally observed — enabling false state acceptance for that height, or breaking previously-valid inclusion/non-inclusion assumptions relied on for fund-moving operations (request delivery, timeout refunds). This falls squarely under "false proof/state acceptance" and "transaction manipulation" in the bounty's impact set.

### Likelihood Explanation
Triggering the reset requires only a single fisherman veto of the current latest height — an intended, permissionless protocol mechanism, not a compromised governance/admin action. After that, overwriting a lower, already-committed height requires the consensus client to legitimately (or fraudulently, in a forked/rotated-authority scenario) report an `IntermediateState` for that lower height in a later `verify()` call; nothing in `EvmHost`/`HandlerV2` rejects such a state purely because the height was previously finalized. This is a missing invariant, not a hypothetical: the Substrate side of the same protocol explicitly implements the guard that EVM is missing, showing the intended behavior was to skip duplicate/already-known heights.

### Recommendation
- In `EvmHost.storeStateMachineCommitment`, reject (or no-op) writes where `_stateCommitments[height.stateMachineId][height.height]` is already non-empty, mirroring the Substrate core's `if host.state_machine_commitment(state_height).is_ok() { continue; }` behavior.
- In `deleteStateMachineCommitmentInternal`, reset `_latestStateMachineHeight` to the actual previous valid height (tracked similarly to Substrate's `PreviousStateMachineHeight`) rather than the hardcoded sentinel `1`.

### Proof of Concept
1. Consensus client delivers heights `10` and `11` for `stateMachineId = X` via `handleConsensus`; both get stored, `_latestStateMachineHeight[X] = 11`.
2. A fisherman calls `deleteStateMachineCommitment` on height `11` (it was the latest), which deletes the height-11 commitment and resets `_latestStateMachineHeight[X] = 1` [6](#0-5) .
3. Any relayer submits a subsequent (still-verifiable, e.g. re-derived or forked) consensus proof whose `IntermediateState[]` includes `height = 10` for `X` with a different `StateCommitment`.
4. `HandlerV2.handleConsensus` accepts it because `10 > 1` [9](#0-8) , and `storeStateMachineCommitment` overwrites the previously legitimate height-10 commitment with the new one, with no existence check [1](#0-0) .
5. Any pending/future `handlePostRequests` or `handlePostRequestTimeouts` call referencing `height = 10` is now verified against the replaced root instead of the originally trusted one.
