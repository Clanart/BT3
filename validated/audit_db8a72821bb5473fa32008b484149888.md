### Title
Unbounded recursion in wallet outer-puzzle drivers (`match_puzzle`) via nested curried puzzle layers enables a crafted offer/coin to crash wallet processing (DoS) - (File: `chia/wallet/outer_puzzles.py`)

### Summary
`chia/wallet/outer_puzzles.py:match_puzzle()` and the individual outer-puzzle drivers it dispatches to (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, `CROuterPuzzle`) recursively call back into `match_puzzle` for every recognized "also" (nested inner) layer of a puzzle reveal, with no depth limit. A malicious puzzle reveal containing many nested recognized curried layers (e.g. repeatedly wrapping CAT/singleton/ownership/metadata/CR layers inside each other) drives unbounded Python recursion, which is the same bug class as CVE-2020-36374's stack-overflow in a recursive-descent parser triggered by crafted input.

### Finding Description

It is injected into each driver as the `_match` callback: [2](#0-1) 

Each driver's `match()` method recognizes its own curried layer, then recurses into `self._match(...)` (i.e. `match_puzzle` again) on the inner puzzle whenever another recognized layer is found, e.g.: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

Each such nested layer produces additional stack frames (`match_puzzle` → `driver.match` → `self._match` → `match_puzzle` → ...). Because there is no cap on how many recognized layers a puzzle may contain — an attacker can trivially curry a chain of CAT/singleton/ownership/metadata/CR mods around a puzzle any number of times using only standard `curry()` — the recursion depth is attacker-controlled and unbounded, unlike `sha256_treehash`, which was deliberately rewritten iteratively specifically to avoid this class of Python stack exhaustion: [8](#0-7) 

`match_puzzle` is reachable from offer processing (`chia/wallet/trading/offer.py`), which is the code path an offer counterparty (or any wallet parsing an offer file/coin puzzle reveal from an untrusted party) exercises to identify asset types inside an offer's puzzle reveals. Because `Program.from_bytes()` parses through the fast Rust CLVM path rather than a recursive Python parser, the initial deserialization itself is robust: [9](#0-8) 
but the wallet-side Python `match_puzzle`/`get_inner_puzzle` recursive walk over the *decoded* structure is not similarly hardened, and a sufficiently deep nested-layer puzzle will exceed the Python recursion limit and raise an uncaught `RecursionError`.

### Impact Explanation
An uncaught `RecursionError` inside offer/puzzle-driver processing terminates or corrupts the wallet's processing of that offer or coin, since these driver calls are not wrapped in exception handling that anticipates this failure mode. This is a spend/offer-triggered halt of wallet transaction/offer processing for any user who receives or attempts to inspect a maliciously crafted offer or on-chain coin puzzle reveal — matching the "Rules" requirement of a spend-triggered transaction-processing halt reachable by an offer counterparty. It does not directly cause fund loss but is a genuine, remotely triggerable Denial of Service against wallet software, analogous in class and severity to the referenced Cesanta MJS stack-overflow CVE.

### Likelihood Explanation
Constructing such a puzzle only requires standard `curry()` calls stacking a chain of already-recognized mod layers (CAT/singleton/ownership/metadata/CR) inside one another; no special privileges, cryptographic breaks, or consensus changes are needed. The attacker only needs to get the victim wallet to run `match_puzzle`/`get_inner_puzzle` over the crafted reveal, which naturally happens when parsing an offer file or a received coin's puzzle. This makes the likelihood moderate-to-high for any wallet or trade counterparty that inspects externally supplied offers/puzzle reveals.

### Recommendation
Add an explicit recursion/nesting depth limit (or convert the recursive `match`/`construct`/`get_inner_puzzle`/`get_inner_solution` traversal in `chia/wallet/outer_puzzles.py` and the outer-puzzle driver classes to an iterative work-stack implementation, similar to `sha256_treehash`) so that a puzzle reveal with an attacker-controlled number of nested recognized layers cannot exhaust the Python call stack. Reject or fail gracefully (raising a handled exception) once a sane maximum nesting depth is exceeded, and ensure offer-parsing code paths catch and handle this failure rather than propagating a raw `RecursionError`.

### Proof of Concept
Conceptually: curry a very long chain of recognized outer-puzzle layers around an innermost puzzle, e.g. repeatedly apply `CAT_MOD.curry(...)` around a `SINGLETON_MOD.curry(...)` around another `CAT_MOD.curry(...)`, etc., for several thousand iterations, to produce a single puzzle reveal `P`. Place `P` as the puzzle reveal in an offer (or as a coin puzzle a victim wallet will inspect) and have the victim call `chia.wallet.outer_puzzles.match_puzzle(UnknownPuzzle(known_program=P))` (as done in offer processing, `chia/wallet/trading/offer.py`). Because each recognized layer adds a `match_puzzle → driver.match → self._match → match_puzzle` recursion cycle with no depth cap, once the chain length exceeds the Python interpreter's recursion limit the call raises an uncaught `RecursionError`, halting offer/coin processing for the victim wallet.
