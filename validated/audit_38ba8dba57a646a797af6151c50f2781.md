### Title
Fee accounting computed on a different transaction than the one signed — OP_RETURN output excluded from weight/vbytes, and truncated `/1000` min-relay check — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary

`SignableTransaction::new` computes `vbytes` (and hence `needed_fee` and the minimum-relay-fee check) via `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which reconstructs a template `Transaction` whose outputs are built **only from `payments`** (`send.rs:85-93`, optionally plus `change` at `send.rs:95-99`). The actual transaction, however, also includes a caller-supplied `OP_RETURN` output pushed onto `tx_outs` before the weight calculation (`send.rs:194-202`). Additionally, the minimum-relay-fee comparison uses truncated integer division `(DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (`send.rs:211`), which floors the true `ceil(fee_rate * vbytes / 1000)` bound. Both are instances of the reported bug class: an accounting value computed on an inconsistent/incorrectly-scaled basis, where multiplication and division ordering (or a missing term) produces a value that does not match what the constructed artifact actually requires.

### Finding Description

In `SignableTransaction::new`:

1. `tx_outs` is populated with `payments` plus an `OP_RETURN` output when `data.is_some()` (`send.rs:188-202`).
2. `calculate_weight_vbytes` is then called with `payments` and `None`/`Some(&change)` — it builds a fresh `Transaction` whose `output` list contains only the payments (and change). The `OP_RETURN` output is never included (`send.rs:204`, `send.rs:225-226`).
3. `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`, `send.rs:227`) is therefore computed for a transaction smaller than the real one. Since `data` may be up to 80 bytes (`send.rs:171-173`), the true transaction is larger by roughly the serialized OP_RETURN output size (~9 + 1 + up to 80 bytes of script data, i.e., up to ~90+ vbytes on the stripped/base side — non-witness data counts fully toward vsize).
4. Because the actual fee paid is `sum(inputs) - sum(outputs)` (`send.rs:138-141`) while the transaction's real vsize is larger than the `vbytes` used for `needed_fee`, the effective fee rate of the broadcast transaction is strictly lower than `fee_per_vbyte`, and can fall below the network minimum relay fee even though the `TooLowFee` check passed.
5. Separately, the `TooLowFee` guard compares `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (`send.rs:211`). Integer division truncates toward zero, so when `DEFAULT_MIN_RELAY_TX_FEE * vbytes` is not divisible by 1000, a `needed_fee` equal to the floored value passes the check while the real minimum is `floor(...) + 1`. Combined with the missing OP_RETURN weight, the produced transaction can sit below `get_virtual_tx_size`-based relay policy entirely.

This is reachable by an unprivileged party: `data` is an external parameter to `SignableTransaction::new` — i.e., bytes the caller causes the threshold network to sign — and any non-empty `data` desynchronizes the accounting from the signed artifact.

### Impact Explanation

The threshold network signs and broadcasts a Bitcoin transaction whose fee rate is lower than requested and potentially below `DEFAULT_MIN_RELAY_TX_FEE` policy. Such a transaction will not propagate/is not mempool-acceptable, leaving the inputs (the multisig's UTXOs) effectively committed to a non-confirming transaction: the plan's outputs are not delivered, and the funds are neither spent as intended nor cleanly recoverable without reconstructing and re-signing a replacement at a higher fee. This is a funds-liveness/accounting-correctness failure produced by inconsistent computation bases — the direct analog of the Float Capital funding-accounting error, where a value was scaled/divided on a basis inconsistent with the quantity it was meant to represent.

### Likelihood Explanation

Triggered deterministically whenever `SignableTransaction::new` is called with `data.is_some()` — no race or attacker positioning required. Whether the resulting transaction actually falls below relay minimum additionally depends on `fee_per_vbyte` and transaction size; for small `fee_per_vbyte` values near the minimum (~1 sat/vbyte), an unaccounted ~90-vbyte OP_RETURN output makes the real fee rate materially lower, and the floored `/1000` check offers no margin. Medium severity: no direct theft, but committed multisig funds fail to move and require recovery intervention.

### Recommendation

- Compute weight/vbytes on the complete output set. Pass the OP_RETURN output (or its script length) into `calculate_weight_vbytes`, or better, call `tx.weight()`/`get_virtual_tx_size` on the final `Transaction` actually being built rather than a reconstructed template.
- Replace the truncated comparison with an exact one: `needed_fee.saturating_mul(1000) < u64::from(DEFAULT_MIN_RELAY_TX_FEE) * vbytes`, i.e., compare in the multiplied domain so no division truncation occurs (multiply before divide / avoid division entirely, per the report's guidance).
- Add a test asserting `fee() / actual_vsize >= fee_per_vbyte` for transactions constructed with non-empty `data`.

### Proof of Concept

Construct `SignableTransaction::new(inputs, payments, change, Some(data), fee_per_vbyte)` with `data` a 80-byte vector and `fee_per_vbyte = 1`:

- `calculate_weight_vbytes` returns `vbytes` for a tx without the OP_RETURN output.
- `needed_fee = vbytes` sats; the real transaction is ~90 vbytes larger, so `fee() / real_vbytes < 1` sat/vbyte → below `DEFAULT_MIN_RELAY_TX_FEE` → not relayed.
- Also, for `vbytes` such that `1000 * vbytes % 1000 != 0` in the min-fee formula (e.g., `DEFAULT_MIN_RELAY_TX_FEE * vbytes = X.5`-style remainders), `needed_fee` equal to the floored bound passes `TooLowFee` while being 1 sat short.

The discrepancy is directly observable by comparing `tx.weight()` of `self.tx` (built at `send.rs:246-251`, which includes the OP_RETURN output) against the `weight`/`vbytes` returned by `calculate_weight_vbytes` (`send.rs:62-127`, which omits it).
