## Confirmed: `zTokens` are priced via a `liquidity-index` (`lindex`) that is decoupled from the actual redeemable value of vault shares, which is computed via `total-assets / total-supply`

### Title
Oracle price for zTokens (`zSTX`/`zsBTC`/`zstSTX`/`zUSDC`/`zUSDH`/`zstSTXbtc`) diverges from actual redeemable value because it is derived from `lindex`, a variable that is not the mechanism that determines real share value - (`mainnet/contracts/utility/v0-1-data.clar`)

### Summary
Each vault (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, etc.) maintains two indexes: a borrow `index` and a liquidity `lindex`, both advanced by the *same* linear multiplier function `calc-multiplier-delta` [1](#0-0) , fed by different rates (`interest-rate` for `index`, `calc-liquidity-rate` for `lindex`) [2](#0-1) . However, the actual amount a zft holder can redeem is **not** derived from `lindex` at all - it is computed from the ERC4626-style ratio `total-assets/total-supply`, where `total-assets` is the vault's real token balance plus the *entire* uncollected debt interest (`debt - borrowed`) [3](#0-2) , and `total-supply` includes the treasury's preview-minted reserve shares [4](#0-3) [5](#0-4) . Meanwhile, `.v0-1-data` (the protocol's collateral/health-factor read-only aggregator) prices every zToken for collateral valuation purposes strictly as `underlying_price * lindex / INDEX-PRECISION` [6](#0-5) [7](#0-6) , using `get-vault-liquidity-index` only - never `total-assets`/`total-supply`.

### Finding Description
`lindex` and the exchange-rate accounting are two independent bookkeeping systems for the "value of interest earned by suppliers," and nothing in the vault contracts enforces that they stay in sync:

- `lindex` grows purely as a function of `calc-liquidity-rate` (derived from the interpolated borrow rate, utilization, and reserve factor) compounded linearly over elapsed time since `last-update` [8](#0-7) .
- The actual redeemable value of a zft share is `total-assets-preview / total-supply-preview`, where `total-assets` reflects the vault's *realized* debt growth (`total-debt - total-borrowed`) computed from the borrow `index`, not from `lindex` [9](#0-8) .
- Treasury share minting (`treasury-lp`) is computed from the debt-delta on the borrow index and is minted proportionally against `total-assets-preview`, again with no reference to `lindex` [10](#0-9) .

Because `lindex`'s growth rate (driven by `calc-liquidity-rate`, i.e. `borrow_rate × utilization × (1 - reserve_factor)`) is not mathematically tied to the growth of `total-assets/total-supply` (driven by actual accrued debt interest split between existing holders and freshly minted treasury shares), the two values will drift apart over time, especially as utilization, deposit/withdraw flow, and mint/redeem activity change the `total-supply` denominator independent of `lindex`. Yet `.v0-1-data`'s `get-asset-price` function - which feeds collateral valuation, `sum-collateral-usd`, and ultimately the health-factor/LTV computation used to gate borrows and determine liquidatability [11](#0-10)  - uses `lindex` exclusively as the "exchange rate" for zTokens used as collateral.

This is an in-code (not third-party oracle) pricing bug: the underlying feed prices (Pyth/DIA) are correct, but the protocol's own conversion of "underlying price" to "zToken price" via `lindex` uses a decoupled, unverified proxy for share value instead of the real, share-based redemption rate.

### Impact Explanation
If `lindex` overstates true redeemable share value relative to `total-assets/total-supply` (which is plausible given they are computed by unrelated formulas that will diverge under real usage, and specifically diverge upward because `lindex`'s continuous "linear" compounding is not offset by treasury minting the way the `total-assets/total-supply` ratio is), then any zToken posted as collateral is over-valued by the health-factor engine in `.v0-1-data`. This lets users borrow against collateral, or avoid liquidation, based on an inflated `health-factor`/`current-ltv` computed from an over-priced zToken, i.e. a wrong health verdict driven by a price attached to the wrong (proxy) value instead of the asset's real redeemable worth. This falls in the "permanent freezing of funds / theft of unclaimed yield" and, more directly, "wrong health verdict" pricing category: undercollateralized positions could be deemed healthy, or liquidatable positions could be deemed safe, exposing the protocol/lenders to bad debt - a Critical-adjacent impact (protocol insolvency risk) if it results in unbacked borrowing.

### Likelihood Explanation
This triggers under ordinary protocol operation - no attacker action or malicious configuration required. Every deposit/withdraw/borrow/repay cycle changes `total-supply` and `total-assets` independently from `lindex`'s time-based accrual, so divergence is a function of normal usage over time, not an edge case. It is directly analogous to the referenced Sherlock M-10 root cause (two independently-accruing interest representations that are expected but not proven to match), except here the second, decoupled "linear" index is actively used as an oracle-priced collateral factor rather than just an unclaimed-surplus bookkeeping artifact.

### Recommendation
Price zTokens using the same `convert-to-assets-preview` (i.e., `total-assets-preview * amount / total-supply-preview`) logic that governs actual redemption, rather than `lindex`, so the collateral value used for health-factor/LTV calculations always matches what a holder can actually redeem. Alternatively, if `lindex` must remain the pricing proxy for gas/read-only reasons, add an invariant check (or periodic reconciliation) ensuring `lindex` growth is mathematically pegged to `total-assets/total-supply` growth, and have `accrue` update `lindex` from realized `total-assets-preview`/`total-supply-preview` rather than from an independently-driven `calc-liquidity-rate`.

### Proof of Concept
Conceptual trace (exact numeric PoC would require the full test harness, `local-testing/tests/`, which was not inspected in depth in this pass):
1. Deposit into `v0-vault-usdc`, establishing `lindex = INDEX-PRECISION` and `total-assets/total-supply = 1:1`.
2. Borrow against it, causing utilization > 0; over time `index` grows via `calc-multiplier-delta` with the raw interpolated `interest-rate`, while `lindex` grows via `calc-multiplier-delta` with `calc-liquidity-rate` (which already nets out `reserve_factor` and `utilization`).
3. Call `accrue`: `treasury-lp` shares are minted into `total-supply` based on `debt-delta * fee-reserve / total-assets-preview`, which changes `total-supply` in a way not reflected by `lindex`'s independent formula.
4. Compare `get-asset-price(zUSDC)` (computed as `usdc-price * lindex / INDEX-PRECISION`) against `convert-to-assets-preview(1_zft)` (the real redemption value): the two values are not proven or enforced to be equal, and no code path re-derives `lindex` from `total-assets/total-supply`, so they diverge as deposits/withdraws/borrows occur across multiple blocks.

Note: I was not able to trace every call site that reads `get-vault-liquidity-index` (e.g. within `v0-4-market.clar`, 10 matches) within this pass; a full confirmation of the numeric magnitude of divergence would benefit from a Devin session with test execution to quantify the drift under realistic utilization/deposit/withdraw sequences.
