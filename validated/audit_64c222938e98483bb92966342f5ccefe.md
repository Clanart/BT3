### Title
`Close` on an `UpgradeableLoaderState::Uninitialized` account drains lamports with no signer/authority check - ([File: programs/bpf_loader/src/lib.rs])

### Summary
`process_instruction`'s handling of `UpgradeableLoaderInstruction::Close` branches on the loader-state of the account being closed. The `Buffer` and `ProgramData` branches route through `common_close_account`, which enforces that an authority is present, matches the passed-in key, and has signed. The `Uninitialized` branch does neither: it unconditionally drains the account's lamports to the caller-specified recipient with no authority/signer requirement at all.

### Finding Description
In the `Close` instruction handler: [1](#0-0) 

```
close_account.set_data_length(UpgradeableLoaderState::size_of_uninitialized())?;
match close_account_state {
    UpgradeableLoaderState::Uninitialized => {
        let mut recipient_account = instruction_context.try_borrow_instruction_account(1)?;
        recipient_account.checked_add_lamports(close_account.get_lamports())?;
        close_account.set_lamports(0)?;
        ic_logger_msg!(log_collector, "Closed Uninitialized {}", close_key);
    }
    UpgradeableLoaderState::Buffer { authority_address } => {
        ...
        common_close_account(&authority_address, &instruction_context, &log_collector)?;
    }
```

Compare this to `common_close_account`, which the `Buffer`/`ProgramData` cases use and which explicitly checks that an authority exists, matches, and signed: [2](#0-1) 

The `Uninitialized` case skips this entirely: any writable account owned by `bpf_loader_upgradeable` whose data deserializes to `UpgradeableLoaderState::Uninitialized` can be passed as account index 0, and any address (no signature required) can be named as the recipient at index 1. The runtime's generic `set_lamports` guard only blocks a lamport decrease when the account is not owned by the invoking program: [3](#0-2) 

Since the target account is owned by `bpf_loader_upgradeable` (the invoked program), this guard does not stop the drain — only an authority/signer check inside the loader itself would, and that check is missing for the `Uninitialized` branch.

This is the direct analog of the reported bug: an asset (there, an NFT; here, lamports in a loader-owned account) sits under program custody without an active protective structure (there, no `buyPrice`/auction; here, no authority on an `Uninitialized` state), and a generic/fallback code path assumes some other guard already validated the caller, when in fact none did.

`UpgradeableLoaderState::Uninitialized` legitimately occurs when: (1) a program allocates and assigns an account to `bpf_loader_upgradeable` (e.g., via `CreateAccount`/`CreateBuffer` flow) before `InitializeBuffer` runs, or (2) after a `Buffer`/`ProgramData` account is closed, `common_close_account` explicitly sets its state back to `Uninitialized`, and the account may not be immediately reclaimed by the system program in the same transaction/slot. Either way, any lamports sitting in the account become takeable by whoever calls `Close` on it, regardless of who created or funded it.

### Impact Explanation
This allows outright fund theft: any account in `Uninitialized` loader state, if it still holds lamports, can have those lamports transferred to an attacker-chosen recipient with zero authorization from the original owner/authority. This matches "fund theft/loss" in an unprivileged, non-malicious-peer scenario — any unprivileged user submitting an ordinary transaction can trigger it.

### Likelihood Explanation
Exploitation requires only a standard `Close` instruction (`UpgradeableLoaderInstruction::Close`) targeting any writable account owned by `bpf_loader_upgradeable` that currently deserializes as `Uninitialized` and has nonzero lamports — no signatures beyond the transaction fee payer are needed for that account. Such accounts are a natural byproduct of program-buffer creation/closing flows, making the precondition achievable without any privileged access, though its window of opportunity depends on how long such accounts remain funded and unswept by callers before being reclaimed.

### Recommendation
Require an explicit authorization for the `Uninitialized` branch as well — e.g., require the recipient/authority to co-sign, or require that the account signer matches the account being closed (mirroring the system program's pattern where an account controls itself via its own signature), instead of allowing any caller to name an arbitrary recipient and drain lamports from any `Uninitialized`-state loader account.

### Proof of Concept
1. Create account `A`, fund it with lamports, and assign it to `bpf_loader_upgradeable::id()` (e.g. via `system_instruction::create_account` with `space = UpgradeableLoaderState::size_of_uninitialized()`), without initializing it as a `Buffer`. Its state is `UpgradeableLoaderState::Uninitialized`.
2. Attacker submits `loader_v3_instruction::close_any(&A, &attacker_recipient, None, None)` (or the raw `UpgradeableLoaderInstruction::Close` with accounts `[A (writable), attacker_recipient (writable)]`).
3. In `process_instruction`, `close_account_state` matches `UpgradeableLoaderState::Uninitialized`; no signer/authority is checked; `attacker_recipient` receives all of `A`'s lamports: [4](#0-3) 
4. Result: attacker drains `A`'s lamports to their own account without ever having any authority over `A`.

```rust
fn common_close_account(
    authority_address: &Option<Pubkey>,
    instruction_context: &InstructionContext,
    log_collector: &Option<Rc<RefCell<LogCollector>>>,
) -> Result<(), InstructionError> {
    if authority_address.is_none() {
        ic_logger_msg!(log_collector, "Account is immutable");
        return Err(InstructionError::Immutable);
    }
    if *authority_address != Some(*instruction_context.get_key_of_instruction_account(2)?) {
        ic_logger_msg!(log_collector, "Incorrect authority provided");
        return Err(InstructionError::IncorrectAuthority);
    }
    if !instruction_context.is_instruction_account_signer(2)? {
        ic_logger_msg!(log_collector, "Authority did not sign");
        return Err(InstructionError::MissingRequiredSignature);
    }
```
