## Analog Found: Stale Copilot Conflict Resolution Silently Overwrites Newer On-Disk Content

### Title
Silent overwrite of user-edited conflicted files with stale Copilot-generated resolution content - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The ZetaChain bug is a case of an aggregate value (median gas price) being computed from a set of inputs that is no longer valid (inactive observers), because the code never re-validates freshness before using the cached votes. GitHub Desktop's AI-assisted merge conflict resolution has the same structural flaw: `IFileResolution.resolvedContent` is computed once from a snapshot of the conflicted file (`rawContent`) taken at the *start* of a long-running Copilot session, and it is written back to disk when the user confirms — without ever re-validating that the file on disk still matches the snapshot the resolution was derived from.

### Finding Description
`buildConflictContext` reads every conflicted file from disk exactly once and stores its full content in `IFileConflictContext.rawContent`: [1](#0-0) 

That snapshot is later used by `reassembleResolutions`/`reassembleResolvedFile` to splice the model's per-hunk output back into the *original* file content by line position, not by re-reading the file: [2](#0-1) 

The whole round trip (`resolveConflicts` → chunked, concurrent Copilot SDK turns) can run for minutes: each chunk has up to a 600-second timeout (`timeoutMs ?? 600_000`), and large conflict sets are split into multiple sequential batches of up to `MaxConcurrentChunks` (5) parallel turns: [3](#0-2) [4](#0-3) 

Results are stored in state and are *not* written to disk immediately — the user reviews them in a result dialog and confirms with "Continue Merge", which calls `_applyCopilotConflictResolutions`: [5](#0-4) 

The write path's only staleness guard checks whether the file is *still fully conflicted*: [6](#0-5) 

This guard only catches the case where the user fully resolved the file (no remaining `<<<<<<<`/`>>>>>>>` markers) — it treats `isConflictedFileStatus(...) && !hasUnresolvedConflicts(...)` as "hands off". It does **not** compare the current on-disk content (or a hash of it) against the `rawContent` that the stored resolution was reassembled from. If the user partially edits a conflicted file while Copilot's minutes-long resolution is still running or awaiting confirmation — fixing one hunk but leaving another marker block, or otherwise touching non-conflicted lines — the file is still reported as conflicted with unresolved markers, so the guard does not skip it. `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` then unconditionally overwrites the entire file with content reassembled from the *stale* snapshot, and the result is immediately `git add`-ed: [7](#0-6) 

This is exactly the ZetaChain pattern: a computed/cached value (median gas price / reassembled resolution) is built from a membership set (active observers / on-disk file state) that is allowed to change, and the code that consumes the cached result checks only a coarse, unrelated condition ("is there still a vote?" / "is the file still marked conflicted?") instead of validating freshness against the current state before using it.

### Impact Explanation
This is silent corruption of what the user commits/pushes: the user's most recent, intentional edits to a conflicted file (which they made specifically to fix or override the AI's suggestion, or to resolve additional issues surfaced after review) are discarded without warning and replaced by out-of-date content, which is then staged with `git add` and can be committed and pushed. Because the merge, rebase, or cherry-pick can originate from an attacker-controlled remote/branch (the source of the conflicting hunks that seeded the AI resolution), an attacker who can craft a conflicting commit is able to increase the chance that content they controlled (rather than the user's corrective edit) survives into the final commit — with no diff or confirmation shown against the file's *current* state at write time, only against the state gathered when resolution began.

### Likelihood Explanation
Requires no special privileges: any repository the user merges/rebases/cherry-picks against can produce a large or slow-to-resolve conflict set (Copilot resolution windows of up to several minutes per chunk, several chunks for many files), during which a user editing a file externally (or reopening manual resolution for one file while Copilot handles others) is a normal, expected interaction pattern the UI itself supports (`onResolutionDropdownClick` lets users flip between "Use Copilot's suggestion" and manual resolution per-file). The staleness window is therefore realistic and not a contrived race.

### Recommendation
Before writing `resolution.resolvedContent` in `_applyCopilotConflictResolutions`, re-read the current on-disk file (or compare a hash/mtime captured in `IFileConflictContext` against the current file) and skip (or re-prompt/re-diff) whenever the content has changed since the snapshot used to build the resolution — not just when the conflict has been fully resolved externally. Surface a clear warning/diff to the user when a stale resolution is about to be discarded or applied over changed content.

### Proof of Concept
1. Start a merge/rebase against a branch with several large conflicting files so Copilot conflict resolution runs across multiple chunks (multi-minute window).
2. While resolution is in progress (or after it finishes but before clicking "Continue Merge"), manually edit one conflicted file outside the app: resolve one of its multiple conflict hunks but leave another hunk's markers in place.
3. Wait for/return to the Copilot conflicts result dialog and click "Continue Merge".
4. Observe that `_applyCopilotConflictResolutions` finds the file `isConflictedFileStatus && hasUnresolvedConflicts` still true, does not skip it, and overwrites the file with the resolution reassembled from the original (pre-edit) `rawContent`, discarding the manual edit and staging the stale content via `git add`.

*Note: I was unable to fully retrieve the bodies of `hasUnresolvedConflicts`/`isConflictedFileStatus` from `app/src/lib/status.ts` and `app/src/models/status.ts` due to index limits, so I could not verify whether any edge case there (e.g. partial-hunk detection) narrows this gap further. If precise confirmation of those functions' exact semantics is needed, a full checkout of the repository would be required.*

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
