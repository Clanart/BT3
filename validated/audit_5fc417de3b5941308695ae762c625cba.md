### Title
Missing empty-pathspec guard in `checkoutPaths` causes whole-tree checkout that silently wipes uncommitted working-directory changes - (File: app/src/lib/git/checkout.ts)

### Summary
`checkoutPaths` builds a git invocation of the form `git checkout HEAD -- <paths...>` without ever checking whether `paths` is empty [1](#0-0) . Every sibling helper that spreads a caller-supplied path array into a git argument list explicitly special-cases the empty-array case as a no-op: `checkoutIndex` [2](#0-1) , `resetPaths` [3](#0-2) , and `updateIndex` [4](#0-3) . `checkoutPaths` is the one function in this family that omits the guard, so when it is called with a zero-length array the effective command becomes `git checkout HEAD --` with a bare, argument-less `--`, which git treats as an unrestricted pathspec rather than "no files" — checking out (overwriting) every tracked file in the working directory from `HEAD`, not the empty set the caller intended.

### Finding Description
The broken invariant is: "an empty `paths` array must mean 'operate on zero files'." All comparable helpers enforce this explicitly before invoking `git`; `checkoutPaths` does not, so passing it an empty array silently escalates the git-checkout scope from "restore N specific files" to "restore the entire working tree from HEAD."

One concrete caller is `GitStore.undoFirstCommit`, used when the user undoes the very first commit of a repository [5](#0-4) . It computes `deletedFilePaths` by filtering the current working-directory status for `AppFileStatusKind.Deleted` files, then calls `checkoutPaths(repository, deletedFilePaths)` before deleting `HEAD` and unstaging everything [6](#0-5) . If the working directory has no deleted files relative to the first commit (the common case — most users undoing an initial commit have only modified or added files, not deleted any), `deletedFilePaths` is `[]`. The subsequent `checkoutPaths` call then runs `git checkout HEAD -- ` with no pathspec, which restores every tracked file from `HEAD`, discarding any uncommitted modifications the user had made anywhere in the working directory — files completely unrelated to the "undo commit" the user asked for.

Existing guards do not stop this: `checkoutPaths` has no length check of its own, and its only caller shown here does not pre-filter for `paths.length === 0` before invoking it, unlike the parallel logic in `discardChanges`, which explicitly computes `necessaryPathsToCheckout` and routes through the length-guarded `checkoutIndex` instead [7](#0-6) .

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes": the user's uncommitted local changes across the whole repository can be silently discarded by an operation whose UI framing ("undo commit") implies a narrow, targeted effect (restoring files deleted by that one commit). There is no confirmation prompt describing "your entire working directory will be reset to HEAD" — the user only sees the generic undo-commit confirmation. Because the working tree is reset to `HEAD` rather than to some attacker payload, this is a data-loss/integrity bug rather than remote code execution, but it matches the class of "operation silently corrupts/discards what the user has produced" called out as valid in the impact criteria.

### Likelihood Explanation
The trigger condition (undoing the first commit of a repository while having no currently-deleted files staged/unstaged) is a very common, everyday scenario for anyone experimenting with a freshly initialized or freshly cloned repository, and requires no special permissions, malware, or social engineering — just normal use of the "Undo commit" feature that ships in the product.

### Recommendation
Add the same `if (!paths.length) { return }` guard to `checkoutPaths` that already exists in `checkoutIndex`, `resetPaths`, and `updateIndex` [8](#0-7) , so an empty path list is a true no-op rather than an unrestricted `git checkout HEAD --`.

### Proof of Concept
1. Initialize a new repository and make an initial commit that adds a file (no deletions).
2. Make further uncommitted edits to any tracked file (or add new untracked files) in the working directory.
3. In GitHub Desktop, choose "Undo commit" on that first commit.
4. `undoFirstCommit` computes `deletedFilePaths = []` (no deleted files exist relative to the first commit) and calls `checkoutPaths(repository, [])`, which executes `git checkout HEAD -- `.
5. Because no pathspec follows `--`, git checks out every tracked file from `HEAD`, discarding the uncommitted edits made in step 2 without any specific warning that this would happen.

Note: I was not able to fully enumerate the third call site of `checkoutPaths` reported by search (only the import and the `undoFirstCommit` call were directly inspected), so there may be additional affected flows beyond the one confirmed here.

  private async undoFirstCommit(
    repository: Repository
  ): Promise<true | undefined> {
    // What are we doing here?
    // The state of the working directory here is rather important, because we
    // want to ensure that any deleted files are restored to your working
    // directory for the next stage. Doing doing a `git checkout -- .` here
    // isn't suitable because we should preserve the other working directory
    // changes.

    const status = await this.performFailableOperation(() =>
      getStatus(this.repository)
    )

    if (status == null) {
      throw new Error(
        `Unable to undo commit because there are too many files in your repository's working directory.`
      )
    }

    const paths = status.workingDirectory.files

    const deletedFiles = paths.filter(
      p => p.status.kind === AppFileStatusKind.Deleted
    )
    const deletedFilePaths = deletedFiles.map(d => d.path)

    await checkoutPaths(repository, deletedFilePaths)

    // Now that we have the working directory changes, as well the restored
    // deleted files, we can remove the HEAD ref to make the current branch
    // disappear
    await deleteRef(repository, 'HEAD', 'Reverting first commit')

    // Finally, ensure any changes in the index are unstaged. This ensures all
    // files in the repository will be untracked.
    await unstageAllFiles(repository)
    return true
  }
