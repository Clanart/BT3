### Title
Malicious input token can permanently block `RedeemEscrow`/`RefundEscrow` settlement and lock all escrowed assets in the IntentGateway - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The `_withdraw` function in `IntentsBase.sol` (invoked from `onAccept` on `RedeemEscrow`/`RefundEscrow` messages) loops over an order's escrowed input tokens and transfers each one to the beneficiary using `safeTransfer`, with no isolation between tokens and no fallback/pull pattern. A single reverting token transfer (e.g. a blacklist token like USDC, a token that reverts on transfers to certain addresses, or a token that reverts on zero-amount transfers) aborts the entire settlement message, permanently blocking release of *all* other (unrelated, healthy) escrowed input tokens for that order. This is a direct local analog of the reported `_executeForeclosure` bug: a single token-transfer failure blocks the entire fund-release flow instead of being isolated via a pull/claim pattern.

### Finding Description
`_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:390-425`) is the shared internal routine that releases escrow for both `RedeemEscrow` (pay the solver) and `RefundEscrow` (refund the user) request kinds, called from `withdraw()`/`onAccept()` after `authenticate()` verifies the message came from a trusted peer gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol:620-626`). [1](#0-0) 

For each token in the withdrawal request it:
1. Decrements `_orders[commitment][token]`.
2. Directly calls `IERC20(token).safeTransfer(beneficiary, amount)` (or a native `.call`).

There is no `try/catch`, no per-token isolation, and no pending-withdrawal/pull-claim fallback — unlike the remediation pattern recommended in the source report. Because Solidity function execution is atomic, if *any* one of the (potentially multiple) input tokens escrowed for an order reverts on transfer to the beneficiary, the whole `_withdraw` call reverts, which reverts the whole `onAccept` call, which reverts the whole ISMP message-delivery transaction.

An order can escrow multiple distinct input tokens (`placeOrder` accepts `order.inputs` as an array, see `evm/src/apps/IntentGatewayV2.sol:162-343`), and the order creator (an unprivileged user) freely chooses which ERC20 contracts to include as inputs. A malicious order creator can escrow one legitimate, valuable token (e.g. USDC/WETH) alongside a purpose-built malicious ERC20 that behaves normally on `transferFrom` into escrow (at `placeOrder`) but unconditionally reverts on `transfer` out to any address other than the order creator itself (a "targeted-revert" token, functionally identical to a blacklist token that only allows transfers back to its deployer). A solver, unaware of this behavior, fills the order and delivers real value to the user's beneficiary on the destination chain. When the settlement message (`RedeemEscrow`, paying the solver) arrives via `onAccept`, the malicious token’s transfer to the solver reverts, which reverts the entire `_withdraw` call — meaning the solver never receives payment for either the malicious token *or* the legitimate token bundled in the same order, and the message can never be redelivered successfully because the token will always revert the same way. The escrowed funds become permanently stuck in the `IntentGatewayV2` contract with no pull/claim recovery path, while the solver has already irrevocably delivered value on the destination chain.

The `onGetResponse`/`_cancelFromSource`/`_cancelFromDest` refund paths (`withdraw(body, true)`) share the exact same `_withdraw`/`withdraw` code path, so the same blocking condition applies to refunds as well.

### Impact Explanation
This directly matches the bounty's "stealing or loss of funds" / "logic attacks" category: a solver's legitimately earned payment can be permanently locked by a malicious order creator's crafted input token, and escrowed assets (including healthy tokens bundled in the same order) become permanently unrecoverable since there is no fallback claim mechanism. This is not merely a griefing/DoS on gas — it is a fund-loss/fund-lock vector triggered entirely by an unprivileged user's public-entrypoint call (`placeOrder`), requiring no malicious relayer, prover, or admin.

### Likelihood Explanation
Likelihood is realistic: `placeOrder` lets any caller specify arbitrary ERC20 contracts as `order.inputs` (`evm/src/apps/IntentGatewayV2.sol:162-298`), and deploying a token contract with an address-conditional revert on `transfer` is trivial and requires no special privilege. The only requirement is that a solver fill the order without noticing the malicious token behavior at fill time — plausible for automated/bot solvers that just check output requirements, not full bytecode analysis of every input token.

### Recommendation
Apply the same fix pattern recommended in the source report: switch `_withdraw`'s per-token transfer to a pull-based design. Wrap each `safeTransfer` (and the native `.call`) in a `try/catch`; on failure, credit an internal `pendingWithdrawals[beneficiary][token] += amount` balance instead of reverting, and expose a `claim(token)` function for beneficiaries to withdraw manually. This ensures one bad token cannot block release of unrelated escrowed assets or of the transaction-fee payout in the same call.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer(to, amount)` succeeds only when `to == attacker`, and reverts otherwise.
2. Attacker calls `placeOrder` on the source chain, escrowing `1 EvilToken` + `1000 USDC` as `order.inputs` for a cross-chain order with attractive output terms.
3. A solver calls `fillOrder` on the destination chain, delivering the requested output tokens to the order's beneficiary, then the contract dispatches a `RedeemEscrow` message back to source (`evm/tron/contracts/apps/IntentGatewayV2.sol` fill flow / `IntentsBase.sol` equivalent).
4. When the `RedeemEscrow` message is delivered and `onAccept` → `withdraw`/`_withdraw` executes on the source chain, the loop reaches `EvilToken.transfer(solver, 1)`, which reverts.
5. The entire `_withdraw` call reverts, so `onAccept` reverts, and the ISMP message delivery transaction reverts. The 1000 USDC (and any relayer/tx fees) intended for the solver remain locked in `IntentGatewayV2` forever, since the message will fail identically on every redelivery attempt — the solver has already paid the output on the destination chain and cannot recover.     function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
