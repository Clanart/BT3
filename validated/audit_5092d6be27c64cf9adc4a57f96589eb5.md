## Analysis

The binding claimed broken: `kickoff_data.operator_xonly_pk == the operator that actually funded the confirmed payout` (enforced via the OP_RETURN payload written into the confirmed `Payout` tx, per `Verifier::is_kickoff_malicious` at [1](#0-0) ).

Tracing `Operator::withdraw`, the payout transaction is built by `create_payout_txhandler`, which places the operator's x-only pubkey in an OP_RETURN output at index 2, while the input is spent via `SpendPath::KeySpend` using the **user-supplied signature** `in_signature` [2](#0-1) . The critical fact is the sighash type used for that user signature: per the `.proto` comment and test helper, the required/expected sighash type is `SinglePlusAnyoneCanPay` [3](#0-2) [4](#0-3) . `Operator::withdraw` verifies the signature using whatever `sighash_type` is embedded in the caller-supplied `in_signature` object via `payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)` [5](#0-4)  — it does not appear to hard-reject sighash types other than `SinglePlusAnyoneCanPay` in the code I could inspect (only a wrapped error message hints at the expectation).

`SIGHASH_SINGLE | ANYONECANPAY` commits **only** to input index 0's outpoint/value/scriptPubkey and to the output at the *same index* (index 0, the user's payout output). It does **not** commit to any other input, to the anchor output (index 1), or to the OP_RETURN output (index 2) that carries the operator attribution. This means the user's signature is valid for *any* transaction that keeps input 0 and output 0 identical, regardless of what other inputs/outputs (including the OP_RETURN operator pubkey) are attached.

Once an operator broadcasts the Payout tx (visible in the mempool/chain), any observer can extract that witness and construct a competing transaction spending the same withdrawal outpoint with the identical signature and output 0, but with a **different OP_RETURN operator pubkey**, additional fee-funding inputs of the attacker's own, and a higher feerate. `add_tx_to_queue` inserts `TransactionType::Payout` with `FeePayingType::RBF` and empty `cancel_outpoints`/`cancel_txids` [6](#0-5) , so nothing at the txsender layer prevents or detects a second, independently-funded transaction spending the same withdrawal UTXO from being broadcast and potentially confirmed instead of the operator's own. Standard Bitcoin full-RBF/mempool replacement rules (higher absolute fee/feerate) then determine which one gets mined — the attacker fully controls fee (paying with their own BTC/UTXOs), so they can outbid the legitimate operator's original broadcast.

If the attacker's version confirms, `update_finalized_payouts`/`get_first_op_return_output` parses whatever OP_RETURN ends up in the confirmed tx and stores that as `payout_payer_operator_xonly_pk` [7](#0-6) . Later, `is_kickoff_malicious` compares this stored value against `kickoff_data.operator_xonly_pk` from the actual kickoff [1](#0-0) , so the operator who genuinely fronted the withdrawal (and paid for `output_txout`) gets mismatched/malicious-flagged if the attacker substituted their own (or no) OP_RETURN pubkey.

I could not fully verify within the available context whether `Operator::withdraw` (or the aggregator/verifier `withdraw` RPC path) hard-enforces `in_signature.sighash_type == SinglePlusAnyoneCanPay` and rejects other sighash flags — I found only the doc/error-message hints, not an explicit `if sighash_type != ... { return Err }` guard in the operator withdraw path. This point materially affects severity: if the sighash is *not* enforced to be non-committing, the finding is confirmed as designed-in malleability; if it silently only accepts that exact flag but the flag still doesn't commit to the OP_RETURN, the vulnerability still holds identically. Either way, the OP_RETURN operator-attribution output is outside the signed message under the sighash flag actually used by the protocol.

### Title
Payout OP_RETURN operator attribution is not covered by the user's `SinglePlusAnyoneCanPay` signature, enabling operator-attribution hijack via RBF replacement - (`core/src/builder/transaction/operator_reimburse.rs`, `core/src/tx_sender_queue.rs`)

### Summary
The user's withdrawal signature uses `SIGHASH_SINGLE | ANYONECANPAY`, which commits only to input 0 and output 0 of the payout transaction, leaving the OP_RETURN output that records the fronting operator's x-only pubkey completely unsigned. Combined with `add_tx_to_queue` inserting `Payout` transactions as plain `FeePayingType::RBF` with no `cancel_outpoints`, any party who observes a broadcast Payout tx can rebroadcast a fee-bumped replacement spending the same withdrawal UTXO with an arbitrary OP_RETURN payload.

### Finding Description
Broken binding: `payout_payer_operator_xonly_pk` (from the confirmed Payout tx's OP_RETURN, stored via `update_finalized_payouts`) must equal the operator that actually funded/broadcast the Payout tx and its `output_txout`. Because the OP_RETURN output (vout 2) sits outside the `SIGHASH_SINGLE|ANYONECANPAY` commitment of the input-0 signature (`create_payout_txhandler`, `operator_reimburse.rs:407-436`; sighash flag `SinglePlusAnyoneCanPay` per proto docs and `sign_withdrawal_output`), an attacker who obtains the broadcast tx's witness can rebuild a transaction that reuses the exact same input 0 (outpoint + signature) and output 0 (must be byte-identical to keep the SINGLE-covered output valid), while freely substituting: extra funding inputs (their own BTC), the anchor output, and the OP_RETURN payload (their own xonly pubkey, an unrelated pubkey, or no valid OP_RETURN at all). `add_tx_to_queue` routes `TransactionType::Payout` through `FeePayingType::RBF` with empty `cancel_outpoints`/`cancel_txids` (`tx_sender_queue.rs:92-105`), so no uniqueness/idempotency guard exists preventing two divergent Payout candidates for the same withdrawal outpoint from competing in the mempool. Standard RBF rules let whichever transaction pays a higher fee win/confirm; the attacker fully controls the fee they pay. Once the attacker's version confirms, `update_finalized_payouts` parses whatever operator xonly pk is embedded in the confirmed OP_RETURN and persists it as `payout_payer_operator_xonly_pk`. `is_kickoff_malicious` later compares this DB value against `kickoff_data.operator_xonly_pk` for the real operator's kickoff, and flags it malicious if they differ (or if no valid pubkey is present).

### Impact Explanation
The operator that genuinely fronted the withdrawal (paid `output_txout` to the user, funded the tx) becomes permanently unable to be reimbursed, because its later kickoff will be judged malicious by every verifier (`is_kickoff_malicious` returning `true`), matching the Critical category "an honest operator permanently unable to be reimbursed." This is repeatable per withdrawal/operator, since the flaw is structural (sighash coverage + unguarded RBF queueing), not tied to a specific deposit or operator key.

### Likelihood Explanation
No privileged access is required: the attacker only needs to observe the operator's broadcast Payout transaction (public mempool/chain data) and be able to fund a higher-fee replacement with their own BTC — both capabilities explicitly granted to the unprivileged attacker persona. The attack is feasible any time an operator calls `withdraw` and broadcasts before finality, which is the normal flow. Cost to the attacker is limited to the fee delta needed to win the RBF race.

### Recommendation
Bind the OP_RETURN operator-attribution output into the same signature that authorizes spending the withdrawal UTXO — e.g., require/verify the user signature (or an additional operator-committed signature) to use a sighash flag that commits to all outputs (`SIGHASH_ALL` or a custom covenant construction), or otherwise cryptographically bind the operator pubkey to the specific withdrawal before allowing it into the txsender queue. Additionally, add a DB-level uniqueness/first-writer-wins guard (and non-empty `cancel_outpoints`/idempotency check keyed on the withdrawal outpoint) in `add_tx_to_queue`/`insert_try_to_send` so that only the first valid Payout candidate for a given withdrawal outpoint can ever be queued or accepted as canonical, regardless of what confirms on-chain.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
