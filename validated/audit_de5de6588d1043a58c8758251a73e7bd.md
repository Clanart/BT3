### Title
Unvalidated `LookupInners` index in compressed ICS23 proof decompression causes RPC/relayer-triggered panic - ([File: sei-cosmos/ics23/compress.go])

### Summary
`decompressExist` in the ICS23 merkle-proof library indexes into a lookup table using an attacker-controlled `int32` taken directly from a submitted proof, with no bounds check. A malformed `CompressedBatchProof` containing an out-of-range step index causes an out-of-bounds slice access, which in Go panics (crashes the goroutine/node process) instead of returning an error — the same "decoder writes/reads more than the allotted structure size" root cause as the NTFS3 LZNT chunk-decompression bug (index out of bounds due to missing bound validation on attacker-supplied compressed data).

### Finding Description
`Decompress`/`decompressExist` reconstruct an `ExistenceProof.Path` from a `CompressedExistenceProof.Path []int32`, using each `step` value as a direct index into the shared `lookup []*InnerOp` slice: [1](#0-0) 

There is no check that `step` is within `[0, len(lookup))`. `lookup` comes from `CompressedBatchProof.LookupInners`, which is fully attacker-supplied protobuf data (both `Entries[].Path` indices and `LookupInners` length are controlled by whoever crafts the `CommitmentProof`). This function is invoked from the standard verification entry points: [2](#0-1) [3](#0-2) 

which unconditionally call `Decompress(proof)` before any other proof validation: [4](#0-3) 

Because `decompressExist` panics via a Go runtime slice-index-out-of-range error, the crash occurs before `ep.Verify(...)` ever runs, so none of the later cryptographic/structural checks protect against it.

### Impact Explanation
ICS23 `CommitmentProof` verification is reachable by any IBC relayer or transaction submitter constructing IBC messages (e.g., `MsgUpdateClient`/`MsgRecvPacket`/`MsgAcknowledgement`) that carry a merkle proof, and potentially by any public gRPC/query path that verifies a store proof. A crafted `CompressedBatchProof` with a `Path` entry referencing an index beyond `len(LookupInners)` triggers an unrecovered Go panic. If this call happens on a goroutine without a panic-recovery wrapper in the message-handling/ABCI path, it crashes the node process handling the transaction, causing a chain halt or repeated RPC node crash across all validators that process the same transaction — satisfying the "validator halt / block delay" or "crash of default-configuration RPC nodes" impact bar.

### Likelihood Explanation
Likelihood depends entirely on whether the calling ABCI/relayer message-handling stack wraps proof verification in a `recover()`. I was not able to confirm from the indexed code whether Cosmos-SDK's IBC message handlers or the ante/msg-service router install a panic recovery around `ics23.VerifyMembership`/`VerifyNonMembership`. If such a recovery wrapper exists (which is common in Cosmos-SDK's baseapp `runTx`), the panic would be caught and converted to a tx failure rather than a node crash, reducing this to a denial-of-service against a single transaction rather than the node. I could not verify this control from the available code, so likelihood/impact certainty is limited without further investigation of the calling stack (baseapp `runTx` recover, IBC keeper call sites).

### Recommendation
Add explicit bounds validation in `decompressExist` (and any other consumer of `CompressedExistenceProof.Path`) before indexing into `lookup`, returning an error/nil for any `step` outside `[0, len(lookup))`, mirroring upstream `cosmos/ics23` fixes that validate compressed-proof indices. Ensure the fix is applied to the vendored copy at `sei-cosmos/ics23/compress.go` and add a regression test with an out-of-range `Path` index.

### Proof of Concept
1. Construct a `CommitmentProof_Compressed` with `CompressedBatchProof.LookupInners = []` (empty) and `Entries[0].Exist.Path = [0]` (index 0, referencing a non-existent lookup entry).
2. Submit this proof through any code path that calls `ics23.VerifyMembership`/`VerifyNonMembership`/`BatchVerifyMembership` (e.g., an IBC packet-commitment proof in `MsgRecvPacket`).
3. `Decompress` → `decompressExist` executes `lookup[step]` with `step=0` and `len(lookup)=0`, causing `index out of range [0] with length 0` panic in `sei-cosmos/ics23/compress.go:154`. [5](#0-4)

```go
// Decompress will return a BatchProof if the input is CompressedBatchProof
// Otherwise it will return the input.
// This is safe to call multiple times (idempotent)
func Decompress(proof *CommitmentProof) *CommitmentProof {
	comp := proof.GetCompressed()
	if comp != nil {
		return &CommitmentProof{
			Proof: &CommitmentProof_Batch{
				Batch: decompress(comp),
			},
		}
	}
	return proof
}
```

```go
func decompressExist(exist *CompressedExistenceProof, lookup []*InnerOp) *ExistenceProof {
	if exist == nil {
		return nil
	}
	res := &ExistenceProof{
		Key:   exist.Key,
		Value: exist.Value,
		Leaf:  exist.Leaf,
		Path:  make([]*InnerOp, len(exist.Path)),
	}
	for i, step := range exist.Path {
		res.Path[i] = lookup[step]
	}
	return res
```

```go
// VerifyMembership returns true iff

func VerifyMembership(spec *ProofSpec, root CommitmentRoot, proof *CommitmentProof, key []byte, value []byte) bool {
	// decompress it before running code (no-op if not compressed)
	proof = Decompress(proof)
	ep := getExistProofForKey(proof, key)
	if ep == nil {
		return false
	}
	err := ep.Verify(spec, root, key, value)
	return err == nil
}
```
