### Title
Missing Upper Bound on Legacy/Fee-Delegated Tx `GasPrice` Allows Draining a FeePayer's Balance via Self-Chosen Fee - (File: `blockchain/tx_pool.go`)

### Summary
Kaia's transaction pool enforces only a **lower bound** on the `gasPrice` of legacy (and fee-delegated legacy) transactions once the Magma hard fork is active — it must be `>= baseFee` — but no upper bound is ever checked. For these transaction types `GasTipCap()`/`GasFeeCap()` are defined to simply return `GasPrice()`, so once the Kaia fork's `EffectiveGasPrice()`/`EffectiveGasTip()` logic is applied, the *actual* price charged for gas becomes exactly the sender-chosen `GasPrice()` value, unbounded above. For fee-delegated transactions, this fee is deducted from the **FeePayer's** balance, not the sender's, meaning a sender fully controls how much of the FeePayer's KAIA is consumed per unit of gas used — directly mirroring the reported `tx.gasprice`-based drain pattern, but against the fee-delegation counterparty instead of a batcher contract.

### Finding Description
In `blockchain/tx_pool.go`, `validateTx()` checks legacy-style transactions (non-EIP-1559 types, which include all Fee Delegated tx types) as follows: [1](#0-0) 

Only `pool.gasPrice.Cmp(tx.GasPrice()) > 0` (i.e., `tx.GasPrice() < baseFee`) is rejected; there is no upper-bound/sanity cap on how high `tx.GasPrice()` can be set by the sender.

For these tx types, `GasTipCap()` and `GasFeeCap()` both resolve to the raw `GasPrice()` field: [2](#0-1) 

Under the Kaia hard fork, `EffectiveGasPrice()` computes `tip = EffectiveGasTip(baseFee)` and returns `tip + baseFee`. Since `GasTipCap()==GasFeeCap()==GasPrice()` for these tx types, this reduces to `min(GasPrice, GasPrice - baseFee) + baseFee == GasPrice` — i.e., the effective price paid is exactly the attacker-chosen `GasPrice()`, capped only from below.

This effective price (`st.gasPrice`) is then used in `buyGas()` to compute the amount deducted from the account: [3](#0-2) 

Crucially, when sender ≠ feePayer (a fee-delegated transaction), the deduction (`mgval = gas * st.gasPrice`) is charged to `validatedFeePayer`, an address that is *not* the party who chose the `GasPrice` value used to compute the charge: [4](#0-3) 

The excess is later returned via `returnGas()`, again computed from the same attacker-influenced `st.gasPrice`, and any consumed gas is booked as fee to Coinbase/Rewardbase via `TransitionDb()`: [5](#0-4) 

In short: the sender of a fee-delegated legacy transaction unilaterally selects `GasPrice`, the protocol enforces no upper bound on it, and the resulting fee (`gasUsed * GasPrice`) is charged entirely to the FeePayer's account, not the sender's — this is the exact "attacker sets an absurdly high price, refund/fee logic uses that attacker-controlled price, and a third party's balance is drained" pattern described in the report, except here it targets the fee-delegation counterparty (sponsor) rather than a batcher contract balance.

Note: the FeePayer's signature (`HashFeePayer`) is computed over the full transaction content including `GasPrice` [6](#0-5) , so the FeePayer does cryptographically commit to whatever `GasPrice` value is present in the transaction at signing time. This means the practical exploitation path requires a FeePayer/relay service that automatically co-signs sender-submitted transactions without independently validating the `GasPrice` field against a sane ceiling (e.g., current suggested price) — a common pattern for "gasless"/sponsored-transaction relayers built on top of Kaia's fee-delegation feature. Because the protocol itself provides **no upper-bound enforcement whatsoever** for legacy-style `GasPrice`, all protection against this abuse is pushed onto the FeePayer's own application logic, with the chain layer offering no defense-in-depth.

### Impact Explanation
Any FeePayer/relay operator using Kaia's built-in fee-delegation transaction types (`TxTypeFeeDelegated*`, all of which are legacy-style and thus subject to the lower-bound-only check) to sponsor gas for users is exposed to unbounded fee drainage if their signing/relay logic does not independently cap the `GasPrice` before co-signing. A malicious "sponsored" sender can set `GasPrice` to any value ≥ baseFee (there is no ceiling, not even `params.UpperGasLimit`-style sanity check applied to price), multiplying the effective cost of every unit of gas used and directly draining the FeePayer's KAIA balance in a single transaction — a concrete, protocol-level fee/fee-delegation abuse.

### Likelihood Explanation
Medium. Exploitation requires a FeePayer/relayer that blindly signs sender-submitted transactions without validating `GasPrice` against a market-reasonable ceiling — a realistic but not universal deployment pattern for sponsored/gasless UX on Kaia. The chain protocol itself provides zero defense (no upper-bound check exists anywhere in `validateTx()` for legacy-style prices), so the residual risk depends entirely on external relay implementations, which the protocol should not assume are perfectly defensive.

### Recommendation
- Enforce a protocol-level upper bound on `GasPrice`/`GasFeeCap` for legacy and fee-delegated legacy transactions in `TxPool.validateTx()` (e.g., relative to `UpperBoundGasPrice`/`pset.UpperBoundBaseFee`, similar to the existing `LowerBoundGasPrice`/`UpperBoundGasPrice` API already exposed in `node/cn/api_backend.go`), instead of leaving it fully unbounded above `baseFee`.
- For fee-delegated transaction types specifically, consider requiring the FeePayer's signature/authorization to also encode an explicit maximum fee (or fee ratio ceiling) that is checked independently by the protocol at execution time, rather than relying solely on the FeePayer's off-chain diligence when co-signing.

### Proof of Concept
1. Let `baseFee` be the current KIP-71 base fee (e.g., 25 ston).
2. A malicious user constructs a `TxTypeFeeDelegated*` (legacy-style) transaction with `GasPrice = baseFee * 10000` (or any arbitrarily large value ≥ baseFee) and a large `Gas` limit.
3. The user obtains the FeePayer's co-signature (e.g., via an automated sponsor/relay service that signs incoming transactions without validating `GasPrice`) — the FeePayer signature is valid because `HashFeePayer` simply commits to whatever `GasPrice` is in the tx.
4. `TxPool.validateTx()` accepts the transaction because `tx.GasPrice() >= pool.gasPrice (baseFee)` is the only check performed [7](#0-6) .
5. During execution, `buyGas()` computes `mgval = gas * st.gasPrice` where `st.gasPrice == tx.GasPrice()` (via `EffectiveGasPrice`), and subtracts this entirely from the FeePayer's balance [8](#0-7) .
6. The FeePayer's account is drained by `gasUsed * (baseFee * 10000)` instead of the expected `gasUsed * baseFee`, with the excess fee distributed to Coinbase/Rewardbase per `TransitionDb()`.

func (tx *Transaction) EffectiveGasTip(baseFee *big.Int) *big.Int {
	// effectiveGasPrice - baseFee = min(baseFee + tipCap, feeCap) - baseFee = min(tipCap, feeCap - baseFee)
	if baseFee != nil {
		// For EthereumDynamicFee TxType: min(GasTipCap, Sub(GasFeeCap,baseFee))
		// For Non-EthereumDynamicFee TxType: min(GasPrice, Sub(gasPrice, baseFee)
		tip := math.BigMax(big.NewInt(0), new(big.Int).Sub(tx.GasFeeCap(), baseFee))
		return math.BigMin(tx.GasTipCap(), tip)
	}

	return new(big.Int).Set(tx.GasTipCap())
}

func (tx *Transaction) EffectiveGasPrice(header *Header, config *params.ChainConfig) *big.Int {
	if header == nil || header.BaseFee == nil {
		return new(big.Int).Set(tx.GasPrice())
	}
	if config.Rules(header.Number).IsKaia {
		tip := tx.EffectiveGasTip(header.BaseFee)
		return new(big.Int).Add(tip, header.BaseFee)
	}
	return new(big.Int).Set(header.BaseFee)
}

func (st *StateTransition) buyGas() error {
	var (
		validatedFeePayer = st.msg.ValidatedFeePayer()
		validatedSender   = st.msg.ValidatedSender()
		feeRatio, _       = st.msg.FeeRatio()
		isOsaka           = st.evm.ChainConfig().Rules(st.evm.Context.BlockNumber).IsOsaka
	)

	// mgval is the maximum gas fee that can actually be paid in the worst case (e.g., revert)
	// st.gasPrice = tx.gasPrice (before Magma) or effectiveGasPrice (since Magma)
	mgval := new(big.Int).Mul(new(big.Int).SetUint64(st.msg.Gas()), st.gasPrice)

	// feeCap is the maximum gas fee the sender was willing to pay
	// GasFeeCap = tx.maxFeePerGas (if exists) or tx.gasPrice
	feeCap := new(big.Int).Mul(new(big.Int).SetUint64(st.msg.Gas()), st.msg.GasFeeCap())

	if isOsaka {
		if blobGas := st.blobGasUsed(); blobGas > 0 {
			// Check that the user has enough funds to cover blobGasUsed * tx.BlobGasFeeCap
			blobFeeCap := new(big.Int).SetUint64(blobGas)
			blobFeeCap.Mul(blobFeeCap, st.msg.BlobGasFeeCap())
			feeCap.Add(feeCap, blobFeeCap)
			// Pay for blobGasUsed * actual blob fee
			blobFee := new(big.Int).SetUint64(blobGas)
			blobFee.Mul(blobFee, st.evm.Context.BlobBaseFee)
			mgval.Add(mgval, blobFee)
		}
	}

	if validatedFeePayer == validatedSender {
		// 1. Non fee-delegated tx
		// 2. FeeDelegatedWithRatio with sender == feePayer
		// 3. FeeDelegated          with sender == feePayer

		// Before Osaka, only the check of the amount to be deducted is applied.
		// Therefore, all options are false.
		checkOverflow, checkWithValue := false, false
		balanceCheck := mgval
		if isOsaka {
			// Overflow will be checked from osaka onwards.
			// A value check is also performed.
			checkOverflow, checkWithValue = true, true
			balanceCheck = feeCap
		}
		if err := st.checkFeePayerBalance(balanceCheck, checkOverflow, checkWithValue); err != nil {
			return err
		}
		st.state.SubBalance(validatedFeePayer, mgval)
