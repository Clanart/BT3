### Title
Payout tx malleability via mandatory `SIGHASH_SINGLE|ANYONECANPAY` lets an unprivileged withdrawer forge the OP_RETURN payer pubkey, framing the fronting operator as malicious and permanently freezing the withdrawal - ([File: core/src/verifier.rs])

### Summary
The payout transaction's user input is always signed with `TapSighashType::SinglePlusAnyoneCanPay`, which under BIP341 commits only to the signed input and the single output at the same index (output 0). Outputs 1 (anchor) and 2 (OP_RETURN operator pubkey) are never covered by the signature, so anyone who observes operator A's broadcast payout tx can reuse the exact same witness in a competing, differently-shaped transaction that changes output 2 to an arbitrary, unregistered x-only pubkey, and get it mined first.

### Finding Description
Binding claimed to hold: `withdrawals.payout_payer_operator_xonly_pk` for withdrawal `i` == the registered operator's xonly pk that actually funded output 0 of the mined payout tx for `i`.

Path:
- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds the payout tx with input 0 = user's withdrawal UTXO (`SpendPath::KeySpend`), output 0 = user payout, output 1 = anchor, output 2 = OP_RETURN with the fronting operator's xonly pk ` [1](#0-0) `.
- The user's signature is verified/used with `sighash_type` taken directly from the caller-supplied `in_signature.sighash_type` (`core/src/operator.rs:628-637`), with no enforcement that it must actually be `SinglePlusAnyoneCanPay` beyond a comment ` [2](#0-1) `.
- `calculate_pubkey_spend_sighash` uses `Prevouts::One` for the `*PlusAnyoneCanPay` variants (`core/src/builder/transaction/txhandler.rs:210-233`), i.e. standard BIP341 SIGHASH_SINGLE semantics: the sighash commits only to input 0 and output 0, not to outputs 1/2 ` [3](#0-2) `.
- `get_payout_txs_for_withdrawal_utxos` identifies "the payout tx" for withdrawal `i` purely by whichever transaction spends the exact `withdrawal_utxo_txid:vout`, with no check on outputs (`core/src/database/verifier.rs:170-196`) ` [4](#0-3) `.
- `update_finalized_payouts` then blindly parses the first OP_RETURN output of that transaction and stores whatever 32 bytes decode as an `XOnlyPublicKey`, with zero check that it belongs to a registered operator (`core/src/verifier.rs:2283-2353`) ` [5](#0-4) `.
- `is_kickoff_malicious` compares this stored pk to the actual kickoff sender's pk and flags a mismatch as malicious (`core/src/verifier.rs:1857-1915`) ` [6](#0-5) `.
- `PayoutCheckerTask`/`get_first_unhandled_payout_by_operator_xonly_pk` filters strictly by `operator.signer.xonly_public_key` (`core/src/database/verifier.rs:282-313`, `core/src/task/payout_checker.rs:39-51`) ` [7](#0-6) ` ` [8](#0-7) `.

Exploit flow: The withdrawing user (an unprivileged attacker per the rules) requests operator A to front the withdrawal, supplying a `SinglePlusAnyoneCanPay` signature as the protocol mandates. A funds and broadcasts the payout tx (input 0 = withdrawal UTXO, output 0 = user payout, output 2 = OP_RETURN with A's real xonly pk). Because the signature only commits to input 0 + output 0, the attacker (who already possesses the broadcast tx and the reusable witness) constructs an alternate transaction spending the identical input 0, with an identical output 0 (satisfying the committed sighash), but a different output 1/2 — in particular an OP_RETURN containing 32 attacker-chosen bytes that decode as a syntactically valid `XOnlyPublicKey` but correspond to no configured operator. The witness (schnorr signature) verifies unchanged for this new transaction because the SIGHASH_SINGLE|ANYONECANPAY sighash is identical. The attacker broadcasts this variant with a higher fee and gets it mined before A's original transaction, which is now rejected as a conflicting double-spend.

`update_finalized_payouts` records the unregistered pk against withdrawal `i`. When A's kickoff later arrives, `is_kickoff_malicious` sees `operator_xonly_pk (unregistered) != kickoff_data.operator_xonly_pk (A)` and returns `true`, triggering a Challenge against A's real, legitimate kickoff (`core/src/verifier.rs:1966-2024`). Simultaneously, no operator's `PayoutCheckerTask` will ever find withdrawal `i` via `get_first_unhandled_payout_by_operator_xonly_pk`, because the stored pk matches no registered operator's `signer.xonly_public_key`, so `mark_payout_handled`/`handle_finalized_payout`/Reimburse is permanently unreachable for that withdrawal.

None of the listed guards intervene: `Operator::is_profitable` only gates A's initial decision to front, `SECP.verify_schnorr` still passes (same message under SIGHASH_SINGLE), `Verifier::is_deposit_valid` is unrelated, and there is no uniqueness/consistency constraint tying the recorded OP_RETURN pk to the registered operator set for the deposit.

### Impact Explanation
- Operator A's collateral is burned via an unwarranted Challenge/Disprove even though A genuinely funded the user's withdrawal (matches "an honest operator's collateral burned").
- Withdrawal `i`'s Reimburse path becomes permanently unreachable by any operator since the DB-recorded payer pk matches no `signer.xonly_public_key` (matches "an honest operator permanently unable to be reimbursed" / effectively freezing that fronted-BTC recovery).
- Repeatable per withdrawal and per operator: any withdrawing user can execute this against whichever operator fronts their withdrawal, at negligible extra cost (just a slightly higher-fee alternate transaction reusing the same witness).

### Likelihood Explanation
- No privileged role is required: the attacker is simply the withdrawing user, who legitimately possesses the `SinglePlusAnyoneCanPay` signature the protocol requires them to produce, and who can observe A's broadcast payout tx in the mempool.
- Cost is minimal (one extra low-value transaction with a competitive fee bump); no key compromise, no majority hashrate, no TLS interception needed.
- The attack window exists any time between A broadcasting the payout tx and its confirmation, which is realistic given typical confirmation delays and RBF/fee markets.

### Recommendation
Do not rely on TapSighashType::SinglePlusAnyoneCanPay leaving outputs 1/2 unauthenticated as the source of truth for operator attribution. Either (a) require the payout tx be identified/validated by exact txid+full-tx match against what was actually funded/signed by the operator (not just outpoint-match), and/or (b) commit the fronting operator's xonly pk inside the portion of the transaction that is covered by the user's signature (e.g., via `SIGHASH_ALL` or by embedding operator pk commitment in output 0's script, or requiring a separate operator-signed commitment), and validate that the extracted OP_RETURN pk belongs to the deposit's registered operator set before ever writing `payout_payer_operator_xonly_pk`.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Returns the withdrawal indexes and their spending txid for the given
    /// block id.
    pub async fn get_payout_txs_for_withdrawal_utxos(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        block_id: u32,
    ) -> Result<Vec<(u32, Txid)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, TxidDB)>(
            "SELECT w.idx, bsu.spending_txid
             FROM withdrawals w
             JOIN bitcoin_syncer_spent_utxos bsu
                ON bsu.txid = w.withdrawal_utxo_txid
                AND bsu.vout = w.withdrawal_utxo_vout
             WHERE bsu.block_id = $1",
        )
        .bind(i32::try_from(block_id).wrap_err("Failed to convert block id to i32")?);

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        results
            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
                    txid.0,
                ))
            })
            .collect()
    }
