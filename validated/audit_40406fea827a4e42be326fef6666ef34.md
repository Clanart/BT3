### Title
Bitcoin deposit `origin` is attributed to the transaction's first input regardless of who actually funded the Serai output — (`processor/src/networks/bitcoin.rs:707-736`)

### Summary
When Serai's Bitcoin processor scans a block for payments to a multisig, it records a `presumed_origin` for every received output by reading the spent output of `tx.input[0]` and converting its `script_pubkey` into an address. This origin is then used as the refund/fallback identity for the deposit (`instruction.origin.or(presumed_origin)` in `instruction_from_output`). Because Bitcoin transactions can be jointly constructed (CoinJoin, PayJoin, batched payments), the first input need not belong to — or even be controlled by — the party funding the output to Serai. An unprivileged counterparty can therefore cause a deposit to be attributed to the wrong external address, misdirecting refunds and refund-fallback credit, exactly analogous to `PaymentMade` not recording the true depositor.

### Finding Description
In `Bitcoin::get_outputs` (`processor/src/networks/bitcoin.rs`), after `scanner.scan_transaction(tx)` finds outputs paying to a multisig script, the code computes a single `presumed_origin` for the entire transaction:

```rust
// processor/src/networks/bitcoin.rs:714-728
let spent_output = {
  let input = &tx.input[0];
  let mut spent_tx = input.previous_output.txid.as_raw_hash().to_byte_array();
  spent_tx.reverse();
  ...
  tx.unwrap().output.swap_remove(usize::try_from(input.previous_output.vout).unwrap())
};
Address::new(spent_output.script_pubkey)
```

This address is then stamped onto *every* output found in that transaction (`output.presumed_origin.clone_from(&presumed_origin)`, line 735), regardless of which input(s) actually funded them.

The origin flows into the protocol at `processor/src/multisigs/mod.rs:45-92`, where `instruction_from_output` resolves the refund identity via `instruction.origin.or(presumed_origin)` and pairs it with the `RefundableInInstruction` (`substrate/in-instructions/primitives/src/lib.rs:88-91`). Per `spec/integrations/Bitcoin.md:15-19`, `origin` is "automatically set to the transaction's first input's address" and drives refund behavior; if the origin isn't a recognized/spendable address, a failure "becomes a donation".

The implicit assumption — mirroring the Footium finding's assumption that `msg.sender` is the club owner — is that `tx.input[0]` identifies the depositor. It does not:

1. **Multi-party transactions**: In a PayJoin or CoinJoin, inputs come from multiple parties and input ordering is arbitrary/cooperative. A counterparty can arrange for *their* input to occupy index 0 while the victim's input funds the Serai output (or vice versa), so the deposit's refund origin is recorded as the attacker's address.
2. **Cross-output attribution**: A transaction can pay multiple Serai outputs funded by different logical depositors; all inherit `input[0]`'s origin.
3. **Non-address / exotic scripts**: `input[0]`'s spent output may be a P2WSH/P2SH/P2TR script (the code's own TODO at lines 708-713 notes it may identify "the P2WSH output *embedding the InInstruction* as the origin"). Refunds sent to such an origin may be unspendable or controlled by unrelated parties, causing loss of refunded funds.

### Impact Explanation
When an InInstruction fails or a refund is issued, Serai routes value back to `origin`. Misattribution means:

- A PayJoin/CoinJoin counterparty who places their input at index 0 receives the refund for a deposit funded by the victim — direct theft of refunded value.
- Deposits whose `input[0]` is an unrecognized or jointly-controlled script have refunds burned as "donations" or sent to addresses the depositor cannot spend from — funds reported received/refunded that are not spendable.
- Historical attribution of deposits is wrong, corrupting the on-chain/off-chain record of who paid, identical in class and consequence to the Footium `PaymentMade` misattribution.

### Likelihood Explanation
Reachable by any unprivileged party who can get a transaction into the Bitcoin blockchain — no validator, RPC, or collusion assumptions needed. The attacker must co-author a transaction with the victim (PayJoin and batched-payment flows exist specifically to do this) and control input ordering, which the Bitcoin protocol does not constrain. Requiring social cooperation keeps this at Medium rather than higher, matching the source finding's severity.

### Recommendation
Do not infer a single depositor from `tx.input[0]`:

- Attribute each output individually, or only treat the origin as trustworthy when the transaction has exactly one input, or when all inputs share the same `script_pubkey` (all inputs provably from the same address).
- Alternatively, require the depositor to explicitly declare `origin` in the `OP_RETURN` shorthand (`RefundableInInstruction.origin`) and treat `presumed_origin` as a best-effort hint that is dropped when inputs have heterogeneous source scripts — i.e., emit/record the actual funding evidence rather than an implicitly assumed identity.

### Proof of Concept
1. Victim V wants to deposit BTC into Serai, e.g. `Shorthand::transfer(None, serai_addr)` paying the multisig's external address.
2. Attacker A proposes a PayJoin: A contributes `input[0]` (an output paying to A's address); V contributes `input[1]` funding the Serai output plus the OP_RETURN shorthand.
3. The transaction confirms. In `get_outputs`, `tx.input[0]` resolves to A's spent output, so `Address::new(spent_output.script_pubkey)` = A's address, stamped onto V's deposit output.
4. The batch executes; when the instruction is refunded (or on refund fallback), `instruction_from_output` yields `origin = A's address` (`instruction.origin.or(presumed_origin)` with `origin = None`).
5. Refunded BTC goes to A, who never funded the deposit.
