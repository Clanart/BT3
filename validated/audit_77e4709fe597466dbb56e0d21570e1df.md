### Title
Denial-of-Claim via Reverting/Blacklisting Reward Token in `BaseRewardPool.getReward` - (File: rewards/BaseRewardPool.sol)

### Summary
`BaseRewardPool.getReward()` iterates over every registered reward token and performs a `safeTransfer` for each one in a single loop with no isolation between tokens. [1](#0-0)  If any single reward token in the array reverts on transfer to a given account (e.g., a blacklist-style token such as USDC/USDT refusing a specific recipient, or a token with a receiver-side callback that reverts), the whole call reverts, and none of the reward tokens for that pool — including perfectly transferable ones — can ever be claimed by that account. This is the same bug class as the reported `processWithdrawalQueue` issue: a single non-cooperative/blacklisted token or receiver causes an unconditional revert inside a loop that must fully succeed, permanently freezing unclaimed value for the affected account.

### Finding Description
`getReward` is called on behalf of an ordinary staker through the fully permissionless `MasterMagpie` claim entry points: `multiclaimSpec`, `multiclaimFor`, and `multiclaim`, all of which route into `_multiClaim` → `_claimBaseRewarder` → `IBaseRewardPool.getReward(_account, _receiver)`. [2](#0-1) [3](#0-2) 

Inside `getReward`, the reward tokens are processed unconditionally in a loop:
```solidity
uint256 length = rewardTokens.length;
for (uint256 index = 0; index < length; ++index) {
    address rewardToken = rewardTokens[index];
    uint256 reward = userRewards[rewardToken][_account];
    if (reward > 0) {
        userRewards[rewardToken][_account] = 0;
        IERC20(rewardToken).safeTransfer(_receiver, reward);
        emit RewardPaid(_account, _receiver, reward, rewardToken);
    }
}
``` [4](#0-3) 

There is no per-token try/catch and no mechanism to skip a failing transfer. Reward tokens are added by managers via `queueNewRewards` and pushed permanently into `rewardTokens`; there is no removal path in `BaseRewardPool`. [5](#0-4)  Once a reward token that can revert for a specific recipient (blacklist token, or a receiver contract set as `_receiver`) is part of a pool's `rewardTokens` array, that account's claim transaction for the entire pool always reverts, because `safeTransfer` for the bad token bubbles up and reverts the whole `getReward` call — including the transfers for all the other, otherwise-claimable reward tokens.

The identical unconditional-loop pattern also exists in `vlMGPBaseRewarder.getReward`/`getRewards`, which uses the same "loop must fully succeed" structure for `_sendReward` calls. [6](#0-5) 

Note: unlike the original report, withdrawal of the underlying staked principal via `MasterMagpie._withdraw` does not itself call `getReward` (it only calls `updateFor`/`_harvestBaseRewarder`, which updates accounting but does not transfer tokens), so principal withdrawal is not blocked. [7](#0-6) [8](#0-7)  The impact is therefore scoped to the reward/yield-claiming path, not to loss of deposited capital.

### Impact Explanation
Once a single reward token in a pool becomes non-transferable to a given account, that account permanently loses the ability to claim any accrued reward tokens from that pool (both the offending token's balance and the balances of all cooperative reward tokens bundled in the same loop), since `userRewards` for the good tokens is only zeroed inside the same atomic call that always reverts. This matches the accepted impact category of permanent freezing of unclaimed yield.

### Likelihood Explanation
Reachable by any ordinary wallet interacting with permissionless claim functions (`multiclaimSpec`, `multiclaimFor`, `multiclaim`); triggering requires only that one of the pool's registered reward tokens be a token type with recipient-conditional transfer failure (blacklist tokens are common in production, e.g. USDC/USDT), or that `_receiver` (an address the caller fully controls via `multiclaimFor`/compounder flows) be set to a contract designed to revert on a specific token's transfer hook. No privileged role or governance action is required to trigger the condition once such a token is present in `rewardTokens`.

### Recommendation
Wrap each reward-token transfer in `getReward`/`getRewards` (and the analogous loops in `vlMGPBaseRewarder`) with a low-level call and `try/catch` (or a raw `.call`) so a single failing transfer does not revert the entire batch; carry over the un-transferred amount in `userRewards` for later retry/removal instead of reverting the whole claim.

### Proof of Concept
1. Manager calls `queueNewRewards` to add a token `T` to a `BaseRewardPool`'s `rewardTokens` where `T` is a blacklist-capable ERC-20 (e.g. mocking USDC's `isBlacklisted` behavior) or any token that can be configured/exploited to revert transfers to a target address. [5](#0-4) 
2. User `Alice` stakes and accrues rewards in both `T` and another token `U` in the same pool.
3. `T`'s issuer (or attacker controlling a malicious token contract used as the reward token) blacklists/reverts transfers to `Alice`.
4. Alice calls `multiclaimSpec`/`multiclaim` for that pool; `_claimBaseRewarder` → `getReward` iterates `rewardTokens`, reaches `T`, `safeTransfer` reverts, and the entire transaction reverts. [3](#0-2) [4](#0-3) 
5. Alice can never claim her `U` rewards from this pool either, as long as `T` remains blacklisted for her and remains in `rewardTokens` (no removal mechanism exists), resulting in a permanent freeze of her accrued yield.
