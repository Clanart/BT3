## Finding: `aptos move verify-package` never actually verifies the on-chain bytecode

This is a legitimate local analog of the AAVE bug class: a function's name/documentation promises one guarantee ("verifies the bytecode") but the implementation silently checks a weaker surrogate (metadata fields) that can diverge from the real protected value (actual deployed module bytecode).

### Title
`VerifyPackage` CLI command claims to verify on-chain bytecode but only compares `PackageMetadata` fields, never fetching or diffing actual module bytecode - (File: `aptos-move/cli/src/commands.rs`, `aptos-move/cli/src/stored_package.rs`)

### Summary
The `aptos move verify-package` CLI command is documented as: "Downloads the package from onchain and verifies the bytecode matches a local compilation of the Move code" [1](#0-0) . In its implementation, it fetches the on-chain `PackageRegistry` with `with_bytecode = false`, meaning the actual compiled module bytes are never downloaded, and it calls `package.verify(&compiled_metadata)` which only compares `PackageMetadata` struct fields (`name`, `deps`, `modules` metadata, `manifest`, `upgrade_policy`, `extension`, `source_digest`) [2](#0-1) [3](#0-2) . None of these fields contain the actual compiled bytecode of the on-chain modules — `ModuleMetadata` only carries `name`, `source`, `source_map`, and `extension` [4](#0-3) , and `source_digest` is a hash over the *source text*, not the compiled bytes.

### Finding Description
`CachedPackageRegistry::create` optionally downloads real module bytecode via `client.get_account_module`, storing it in a `bytecode: BTreeMap<String, Vec<u8>>` only `if with_bytecode` [5](#0-4) . The `VerifyPackage::execute` implementation hardcodes `false` for this parameter: `CachedPackageRegistry::create(client, self.account, false).await?` [6](#0-5) . As a result `registry.bytecode` is always empty and `registry.get_bytecode(...)` is never invoked anywhere in the verify flow.

The subsequent `package.verify(&compiled_metadata)` call only performs field-by-field equality checks on the `PackageMetadata` struct (name, deps, module metadata, manifest, upgrade policy, extension, source digest) [7](#0-6) . Since `PackageMetadata`/`ModuleMetadata` do not carry the compiled module bytes at all (the actual bytecode is separately stored as an account module resource, not part of `0x1::code::PackageRegistry`), there is no code path in `VerifyPackage` that fetches or diffs the real deployed bytecode against a fresh local build. By contrast, `DownloadPackage` does correctly plumb through a `--bytecode` flag to actually retrieve and persist module bytes [8](#0-7) , showing the capability exists but is unused by `VerifyPackage`.

Because `PackageMetadata.source` and `PackageMetadata.source_digest` are self-reported by whoever last published the package (they are just fields inside the txn payload consumed by `code::publish_package_txn`, with no on-chain enforcement that the committed module bytecode was actually compiled from that source) [9](#0-8) , an attacker who controls a package's publish transaction can freely publish arbitrary bytecode alongside metadata/source claiming to be some innocuous or previously-audited source. Anyone who runs `aptos move verify-package` against that source will see "Successfully verified source of package" even though the actual on-chain bytecode was never inspected or compared.

### Impact Explanation
This breaks the specific code-safety invariant this tool exists to provide: a mismatch between "verified bytes, package metadata, dependency declarations, and committed module bytes" going completely undetected. Downstream consumers, auditors, or protocols that rely on `aptos move verify-package` as an integrity gate before trusting or depending on an on-chain package would receive false assurance that the deployed bytecode matches an audited/known-good source, while the actual executable module bytes could be arbitrary and malicious (backdoored logic, hidden admin functions, altered arithmetic, etc.). This is a supply-chain-style trust bypass directly in the code-verification/publish-trust pipeline described in the Publish Impact Gate ("Mismatch between verified bytes, package metadata, dependency declarations, and committed module bytes").

### Likelihood Explanation
High likelihood of triggering in practice: no special privilege or race condition is needed. Any package owner can publish arbitrary bytecode under a package name/source_digest of their choosing (nothing on-chain ties `source`/`source_digest` to the actual bytecode), and any user invoking the documented `verify-package` command will always get a false-positive "verified" result because the bytecode-fetch path is unconditionally disabled (`with_bytecode = false`) regardless of intent.

### Recommendation
In `VerifyPackage::execute`, call `CachedPackageRegistry::create(client, self.account, true)` (i.e., `with_bytecode = true`), and extend `CachedPackageMetadata::verify` (or a new function) to fetch each module's on-chain bytecode via `registry.get_bytecode(module_name)` and byte-compare it against the freshly compiled module bytes produced by `BuiltPackage::build_to`/`pack.extract_code()`. The command should fail loudly if any module's on-chain bytecode differs from the locally recompiled bytecode, not just when `PackageMetadata` fields differ.

### Proof of Concept
1. Publish a package `P` at address `A` where the `code` bundle passed to `code::publish_package_txn` is bytecode `B_malicious`, but `metadata.modules[i].source` / `metadata.source_digest` describe an unrelated, benign source file `S_benign` (the framework performs no check linking `source`/`source_digest` to `code`) [9](#0-8) .
2. A third party downloads `S_benign` (e.g., via `aptos move download-package`, or independently obtains what they believe is the source) and runs `aptos move verify-package --account A`.
3. `VerifyPackage::execute` builds `S_benign` locally, extracts its metadata, and calls `CachedPackageRegistry::create(client, A, false)` — never touching bytecode — then `package.verify(&compiled_metadata)` [10](#0-9) .
4. Since the on-chain `PackageMetadata` fields (source, source_digest, manifest, deps, upgrade_policy) were crafted to match `S_benign`'s locally-built metadata, `verify()` returns `Ok(())` and the CLI prints "Successfully verified source of package" [3](#0-2)  — despite the actually deployed, executing bytecode being `B_malicious`, entirely different from `S_benign`.

impl CachedPackageRegistry {
    /// Creates a new registry.
    pub async fn create(
        client: Client,
        addr: AccountAddress,
        with_bytecode: bool,
    ) -> anyhow::Result<Self> {
        // Need to use a different type to deserialize JSON
        let inner = client
            .get_account_resource_bcs::<PackageRegistry>(addr, "0x1::code::PackageRegistry")
            .await?
            .into_inner();
        let mut bytecode = BTreeMap::new();
        if with_bytecode {
            for pack in &inner.packages {
                for module in &pack.modules {
                    let bytes = client
                        .get_account_module(addr, &module.name)
                        .await?
                        .into_inner()
                        .bytecode
                        .0;
                    bytecode.insert(module.name.clone(), bytes);
                }
            }
        }
        Ok(Self { inner, bytecode })
    }
