### Title
Missing index fix-up on access-list slot removal corrupts `Slots`/`Addresses` mapping and can panic EVM execution - (File: x/evm/state/journal.go, x/evm/state/accesslist.go)

### Summary
This is a direct analog of the `Position::removeFungible` bug class: an array (`Slots`) and an index map (`Addresses`) must stay in sync, but a removal path shifts the array without updating the cached indexes of the *other* elements that moved.

### Finding Description
`accessList` stores, per warm address, an index into a parallel `Slots` slice of storage-key sets: [1](#0-0) 

When a nested call reverts and the last warm slot for an address is undone, `accessListAddSlotChange.revert` removes that address's entry from `Slots` by slicing it out and shifting all subsequent elements down by one, but it never updates the `Addresses` map for the other addresses whose slot-map moved: [2](#0-1) 

Compare this to the upstream go-ethereum implementation, which after the identical slice removal performs an explicit fix-up loop (`for addr, index := range al.addresses { if index > idx { al.addresses[addr] = index - 1 } }`) before setting the removed address's index to `-1`. That fix-up loop is entirely absent from the sei-chain fork in both `x/evm/state/journal.go` and the duplicated `giga/deps/xevm/state/journal.go`.

Consequence, mirroring the reported bug exactly: after `Slots[idx]` is removed and the slice shrinks, every address whose cached index was `> idx` now:
- points at the wrong slot-set (off-by-one, pointing to a different address's slots), and/or
- has an index that is `>= len(Slots)` (now out of range) if it previously pointed at the last element.

### Impact Explanation
`SlotInAccessList` performs `al.Slots[idx][slot]` using the (now stale) `Addresses[addr]` index without any bounds check: [3](#0-2) 

Two consequences follow from state desync:
1. **Wrong warm/cold accounting** — a query for one address can silently read another address's slot-set, causing `SLOAD`/`SSTORE` gas metering (EIP-2929/2930 warm/cold access costs) to be computed incorrectly. This can under- or over-charge gas within the same deterministic execution across all validators, i.e., every node computes the same wrong value, so it does not directly cause a chain split by itself, but it is an incorrect state-transition input.
2. **Out-of-range panic** — if an address's stale index is now `>= len(Slots)` (which happens whenever the address whose slots were removed was not the very last one in `Slots`), the unguarded index into `al.Slots[idx]` inside `SlotInAccessList` triggers a Go slice-index panic. Since `SlotInAccessList` is called from go-ethereum's EVM interpreter on essentially every `SLOAD`/`SSTORE`/`CALL`-family opcode to determine warm/cold gas cost, a crafted transaction that (a) warms multiple addresses' slots, then (b) triggers an internal revert (e.g., a sub-call that reverts) removing a non-last address's slot set, then (c) accesses a slot for an address whose index shifted out of range, will panic deep inside EVM execution. This is deterministically reproducible by any unprivileged EVM transaction sender and executes identically on every validator during block processing, making it a candidate for a consensus-wide panic/halt during `DeliverTx`/ante+message execution rather than a single-node crash, unless caught by a top-level recover in the message handler (not identified in the reviewed code paths).

### Likelihood Explanation
Triggering requires only standard EVM primitives available to any transaction sender: multiple addresses accumulating warm storage slots within one transaction (e.g., via `CALL` to several contracts that touch storage) followed by a reverting sub-call (`REVERT` opcode or a failed inner call) that empties one non-last address's slot set. This requires no special privileges, no validator collusion, and no malicious peer/node — it is reachable purely through a normal, attacker-crafted EVM contract call.

### Recommendation
Port the upstream go-ethereum fix-up logic into `accessListAddSlotChange.revert` (in both `x/evm/state/journal.go` and `giga/deps/xevm/state/journal.go`): after removing `slotsList[idx]`, iterate `Addresses` and decrement every index greater than `idx`, exactly as go-ethereum's `accessList.DeleteSlot` does, before marking the removed address's index as `-1`. Additionally, add a defensive bounds check in `SlotInAccessList`/`AddressInAccessList` to avoid an outright panic if inconsistent state is ever encountered.

### Proof of Concept
Conceptual repro (mirrors go-ethereum's `TestAccessListDeleteSlot`-style scenario, adapted to sei-chain's `DBImpl`):
1. `AddSlotToAccessList(addrA, slotA)` → `Addresses = {addrA: 0}`, `Slots = [{slotA}]`.
2. `AddSlotToAccessList(addrB, slotB)` → `Addresses = {addrA: 0, addrB: 1}`, `Slots = [{slotA}, {slotB}]`.
3. `AddSlotToAccessList(addrC, slotC)` → `Addresses = {addrA: 0, addrB: 1, addrC: 2}`, `Slots = [{slotA}, {slotB}, {slotC}]`.
4. Revert only the `addrA` journal entry (simulating an inner-call revert that only unwinds `addrA`'s access) → `accessListAddSlotChange.revert` deletes `slotA` from `Slots[0]`, sees it empty, and does `Slots = append(Slots[:0], Slots[1:]...)` → `Slots = [{slotB}, {slotC}]`, sets `Addresses[addrA] = -1`, but leaves `Addresses[addrB] = 1` and `Addresses[addrC] = 2` unchanged.
5. Now `Addresses[addrC] = 2` but `len(Slots) == 2` — calling `SlotInAccessList(addrC, slotC)` executes `Slots[2][...]`, which is out of range and panics; and `SlotInAccessList(addrB, slotB)` reads `Slots[1]`, which now actually holds `{slotC}` — a wrong warm/cold answer for `addrB`.

This scenario is directly reachable by any EVM transaction that touches ≥3 distinct addresses' storage inside nested calls where an inner call for the first-touched address reverts while later ones do not, a pattern trivially producible in a single crafted user-deployed contract call — no privileged access required. func (s *DBImpl) SlotInAccessList(addr common.Address, slot common.Hash) (addressOk bool, slotOk bool) {
```go
	s.k.PrepareReplayedAddr(s.ctx, addr)
	al := s.getCurrentAccessList()
	idx, addrOk := al.Addresses[addr]
	if addrOk && idx != -1 {
		_, slotOk := al.Slots[idx][slot]
		return addrOk, slotOk
	}
```

```go
func (e *accessListAddSlotChange) revert(s *DBImpl) {
	// since slot change always comes after address change, and revert
	// happens in reverse order, the address access list hasn't been
	// cleared at this point.
	idx, ok := s.tempState.transientAccessLists.Addresses[e.address]
	// If the address was already removed or has no slots (idx == -1),
	// there is nothing to revert.
	if !ok || idx == -1 {
		return
	}
	slotsList := s.tempState.transientAccessLists.Slots
	// Bounds check in case a prior revert already modified the slots slice.
	if idx >= len(slotsList) {
		return
	}
	slots := slotsList[idx]
	delete(slots, e.slot)
	if len(slots) == 0 {
		s.tempState.transientAccessLists.Slots = append(slotsList[:idx], slotsList[idx+1:]...)
		s.tempState.transientAccessLists.Addresses[e.address] = -1
	}
}
```
