### Title
Forfeiture bypass via same-block lock inflation of `getRewardablePercentWAD` - ([File: rewards/vlMGPBaseRewarder.sol], [File: VLMGP.sol])

### Summary
`vlMGPBaseRewarder._calExpireForfeit` computes the forfeited share of harvested MGP using `VLMGP.getRewardablePercentWAD(_account)`, which is evaluated live at the moment of the call rather than being time-weighted over the reward-accrual period. An attacker can temporarily inflate their `fullyInLock` balance by calling `lock()`/`lockFor()` immediately before triggering a harvest, artificially raising the rewardable percentage and reducing/zeroing the forfeiture that should apply to MGP rewards accrued while a larger share of their balance was in cooldown.

### Finding Description
`getRewardablePercentWAD` derives the rewardable percent from the user's *current* `getUserTotalLocked` and cooldown slot state: [1](#0-0) 

This percent is consumed synchronously inside `_calExpireForfeit`, which is called from `queueMGP` (MGP-lock reward harvest path) and `_sendReward` (other reward tokens): [2](#0-1) [3](#0-2) 

Because the ratio is a point-in-time snapshot with no historical/time-weighted accounting of the locked-vs-cooldown composition during the period the reward actually accrued, a user can manipulate it by calling `lock()`/`lockFor()` (guarded only by `whenNotPaused`/`nonReentrant`, no access control beyond owning MGP) right before triggering `MasterMagpie.multiclaim`/harvest, which flows into `queueMGP`/`getRewards` → `_sendReward` → `_calExpireForfeit`. This inflates `fullyInLock`, and thus `rewardablePercentWAD`, reducing the `forfeitAmount` computed for the entire pending reward amount — not just the portion notionally attributable to the newly locked tokens.

The extra locked amount is not permanently trapped: it can subsequently be moved into a fresh cooldown slot via `startUnlock`, which itself triggers another `multiclaimFor` call and does not require repaying anything atomically — it simply starts a new cooldown timer: [4](#0-3) 
After the cooldown period elapses, the principal is retrievable via `unlock`: [5](#0-4) 

None of `nonReentrant`, `whenNotPaused`, or reward-index updates prevent this because `lock`, `multiclaim`, and `startUnlock` are three independent top-level/external calls that can be sequenced atomically by an attacker's own contract within a single transaction; there is no reentrancy involved, and no check ties the forfeiture ratio to the state that existed when the reward accrued.

### Impact Explanation
This results in theft of unclaimed yield: MGP (and other reward tokens) that should be forfeited by a user with a large cooldown balance and redistributed to other honest vlMGP holders (via `_queueNewRewardsWithoutTransfer`) is instead paid out to the attacker because the forfeiture percentage is computed after an artificially inflated `fullyInLock` snapshot. This matches the Immunefi "theft of unclaimed yield" impact class, extracting value from the shared reward pool that other stakers would otherwise have received.

### Likelihood Explanation
- Requires the attacker to already have (or acquire) MGP capital to lock — true flash loans do not work here since `lock()` funds are not returned within the same call, only movable into a new cooldown slot via `startUnlock`, so the attacker's capital is tied up for at least one `coolDownInSecs` period.
- No privileged role is required; `lock`, `lockFor`, `startUnlock`, and `multiclaim` are all public/external functions callable by any EOA/contract.
- The precondition (an existing cooldown slot with `amountInCoolDown > 0`) is trivially satisfiable by any vlMGP holder who has already started an unlock.
- The exploit is repeatable each time the attacker has pending rewards to harvest and spare MGP to temporarily lock, bounded only by the cooldown duration for retrieving the extra principal.

### Recommendation
Compute (or track) the rewardable/forfeiture ratio based on a time-weighted or accrual-period snapshot of the user's locked-vs-cooldown composition (e.g., checkpoint the ratio at each reward accrual/update, similar to how `rewardPerToken` is checkpointed) instead of reading `getRewardablePercentWAD` live at harvest/claim time. Alternatively, apply a cooldown/lockup on state changes to `getUserTotalLocked` (e.g., require a minimum holding period before a newly locked balance counts toward the rewardable percentage) so it cannot be inflated immediately before a harvest transaction.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `vlMGPBaseRewarder`, and `MasterMagpie` with a mock MGP token, as configured in existing test setup.
2. Attacker locks an initial amount, waits, and calls `startUnlock` on part of it to create a cooldown slot (`amountInCoolDown > 0`), establishing the baseline `getRewardablePercentWAD`.
3. Accrue pending MGP rewards for the attacker in `vlMGPBaseRewarder` (via `queueNewRewards`/reward distribution) while the attacker's locked/cooldown ratio remains skewed toward cooldown.
4. Record baseline: call `_calExpireForfeit`(or trigger harvest without inflation) and capture `forfeitAmount_baseline`.
5. In a single transaction (attacker contract), sequence: `vlMGP.lock(extraAmount)` → `MasterMagpie.multiclaim`/`getRewards` (triggers `queueMGP`/`_sendReward`) → `vlMGP.startUnlock(extraAmount)`.
6. Assert `forfeitAmount` emitted/computed during step 5's harvest is materially lower than `forfeitAmount_baseline` (or zero), while the attacker's actual locked-vs-cooldown composition over the accrual period was unchanged except for the momentary inflation.
7. Assert the reward pool (`rewardInfo.historicalRewards`/`queuedRewards`) receives less forfeited MGP than expected, confirming yield diversion.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
