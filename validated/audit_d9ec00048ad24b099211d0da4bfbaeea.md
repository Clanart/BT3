### Title
Naive `---` substring splitting in `extract_frontmatter` silently downgrades `block` rules to `warn`/dropped when patterns contain embedded triple-dashes - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` locates the YAML frontmatter boundaries using a naive `content.split('---', 2)` on the raw file text instead of matching `---` only on its own line, as real YAML frontmatter delimiters require. If any frontmatter value (most plausibly a `pattern` written to detect secrets, certificates, or merge-conflict markers) contains the literal substring `---`, the split misidentifies the frontmatter boundary, truncating the frontmatter before fields like `action: block` are parsed. This causes `Rule.from_dict` to fall back to its default `action = "warn"`, or drop the rule's conditions/pattern entirely, silently turning a visually "blocking" rule file into a non-blocking (or non-matching) one.

### Finding Description
`extract_frontmatter` only checks `content.startswith('---')` and then does: [1](#0-0) 
This splits on the first two literal occurrences of the 3-character substring `---` anywhere in the file — not on lines that consist solely of `---`, which is how YAML frontmatter delimiters are supposed to be recognized. Common, legitimate rule content easily contains embedded `---` sequences, e.g. a security-oriented pattern such as `-----BEGIN (RSA )?PRIVATE KEY-----` (used to block committing private keys) or markers like `<<<<<<<`/`=======`/`>>>>>>>`-adjacent content, or a Markdown horizontal rule in the message body.

When such a pattern line appears before the true closing `---`, `content.split('---', 2)` treats the *embedded* dashes as the closing delimiter. Everything from that point onward — including the real `pattern` continuation, `action: block`, the real closing `---`, and the intended message — is shoved into `message = parts[2].strip()` as plain text rather than being parsed as YAML frontmatter.

Downstream, `Rule.from_dict` computes: [2](#0-1) 
Since `action` was never captured in `frontmatter` (it fell into the message text instead), it defaults to `"warn"` per `frontmatter.get('action', 'warn')` at line 81. Depending on exactly where truncation occurs, `pattern`/`conditions` may also be incomplete or missing, which makes `rule.conditions` empty; in `rule_engine.py`, `_rule_matches` explicitly refuses to match rules with no conditions: [3](#0-2) 
So the rule is either silently downgraded to a warning (operation proceeds after only a message) or silently never matches at all (fully inert), even though the human-visible file clearly specifies `action: block`.

No validation anywhere re-parses or sanity-checks that the visibly declared `action: block` was actually captured — `load_rule_file` only checks that `frontmatter` is non-empty, not that expected keys survived parsing: [4](#0-3) 
There is no schema/round-trip validation, so this discrepancy between the visible file and the parsed `Rule` object goes completely undetected.

Reachability: hookify rule files (`.claude/hookify.*.local.md`) are the artifacts generated by the `/hookify` command based on conversation/content analysis, and are documented in `plugins/hookify/commands/hookify.md` as containing fields exactly like `pattern:` and `action: block` used to detect dangerous commands (e.g. secret leakage, `rm -rf`, etc.) [5](#0-4) . Any repository content, issue/PR text, or conversation content that leads to a generated (or attacker-modified) rule file containing an embedded `---` in its pattern/value fields will trigger this parser flaw at `load_rules`/`load_rule_file` time, which is invoked from the PreToolUse/PostToolUse/Stop hooks on every subsequent tool call.

### Impact Explanation
This breaks the core security invariant that a `block` rule (used to prevent dangerous Bash commands, file edits leaking secrets, etc.) must never silently degrade to `warn` or become entirely inert. Because the rule file's frontmatter is human-authored and looks correct (`action: block` is visibly present in the file), a maintainer or user has no visual indication their block rule is not enforced — this is a genuine Security-control bypass that silently disables or routes around a blocking boundary, matching Immunefi's "security-control bypass" impact category for Claude Code.

### Likelihood Explanation
The trigger condition is not exotic: security-oriented regex patterns for detecting private keys (`-----BEGIN PRIVATE KEY-----`), certificates, or Markdown horizontal rules in the rule's message body are natural, expected content for a hook-writing tool whose whole purpose is to block dangerous operations. No special privileges are required beyond being able to influence the content of a generated/edited `.claude/hookify.*.local.md` file (via `/hookify`, direct edit, or a PR touching that file) — well within the "ordinary repository content / hook frontmatter parsing" attack surface. It is fully deterministic and 100% reproducible given the crafted input.

### Recommendation
Rewrite `extract_frontmatter` to only treat `---` as a delimiter when it appears alone on its own line (matching standard YAML frontmatter semantics), e.g. via `re.split(r'(?m)^---\s*$', content, maxsplit=2)` or by iterating line-by-line and only splitting on lines whose stripped content is exactly `---`. Additionally, `load_rule_file`/`Rule.from_dict` should validate that expected keys declared in the raw file text (e.g. via a lightweight sanity check comparing detected `action:` occurrences in the raw text vs. the parsed dict) are consistent, and should refuse to silently downgrade to `warn` when parsing anomalies are detected — instead treating malformed frontmatter as a hard error that surfaces to the user rather than fail-open.

### Proof of Concept
Add a unit test to `config_loader.py`'s test suite:
```python
def test_embedded_dashes_do_not_downgrade_block_rule():
    content = """---
name: block-private-key-leak
enabled: true
event: bash
pattern: "-----BEGIN (RSA )?PRIVATE KEY-----"
action: block
---

Blocking private key exposure!
"""
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)

    # Expected (invariant): the visibly-declared block action must survive parsing
    assert rule.action == "block"
    assert rule.pattern == "-----BEGIN (RSA )?PRIVATE KEY-----"

    # Demonstrate the bug: currently action is 'warn' (or pattern is truncated),
    # so a rule intended to BLOCK is instead treated as a warning or is inert.
```
Running this against the current `extract_frontmatter` implementation shows `rule.action == "warn"` (or `rule.pattern` truncated/missing), confirming the parser downgrades/loses the declared `block` action — violating the stated invariant. This can further be validated end-to-end by placing the crafted file at `.claude/hookify.block-private-key-leak.local.md` in a test repo and invoking `plugins/hookify/hooks/pretooluse.py` with a `Bash` tool call whose command contains a private key, and observing that `RuleEngine.evaluate_rules` returns a `systemMessage`-only warning (or no result) instead of a `permissionDecision: deny`.
