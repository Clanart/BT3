### Title
Gov deposits from a cast EVM address become permanently unrefundable and un-distributable after the address is later associated - ([File: sei-cosmos/x/gov/keeper/deposit.go])

### Summary
A user can deposit `usei` (or any coin) to a governance proposal from a "cast" Sei address (`sdk.AccAddress(evmAddr[:])`) that is fully payable at deposit time. If the same EVM address is later associated to a *different* true Sei address (an action any holder of that EVM private key can trigger via the normal association flow), the cast address permanently loses the ability to receive funds. `RefundDeposits` then leaves that specific deposit stuck in the governance module account forever, with no automated way for the depositor (or anyone else) to reclaim it — mirroring the reported NFT class of bug where an asset that was valid at deposit time becomes stuck due to a state change that happens *after* the deposit, with no bypass/refund mechanism.

### Finding Description
Governance deposits are refunded via `RefundDeposits`: [1](#0-0) 

The retention branch triggers whenever `bankKeeper.BlockedAddr(depositor)` is true or `bankKeeper.CanSendTo(ctx, depositor)` is false, and the code comment makes clear this is a *permanent* condition absent an out-of-band migration: "Retain the deposit so its record continues to account for the backing module balance. Recovering a permanently unreceivable deposit requires a migration."

`CanSendTo`'s underlying receivability rule for cast addresses is `CanAddressReceive`: [2](#0-1) 

A "cast address" (`sdk.AccAddress(evmAddr[:])`) is receivable only as long as the corresponding EVM address is unassociated, or is associated back to that exact cast address. The moment `SetAddressMapping` is called to associate the EVM address to a *different* true Sei address — which happens automatically during the standard `associatePubKey`/EVM-association flow reachable by any unprivileged user — the cast address permanently fails `CanAddressReceive`/`CanSendTo`: [3](#0-2) 

This exact mechanic is exercised and documented in the gov test suite, confirming the deposit is retained (not refunded, not burned, not redirected) once the depositor address becomes unpayable: [4](#0-3) 

The structural analogy to the reported issue is direct:
- Reported bug: an NFT is valid/whitelisted at deposit time; it is blacklisted later; `refundDeposit` has no bypass for the now-blacklisted asset and the depositor cannot reclaim it before an arbitrary expiration, while `claimNft` could still distribute it.
- Sei analog: a deposit is valid/payable at deposit time; the depositor's cast address becomes unpayable later (via a normal, attacker/self-triggerable association action); `RefundDeposits` has no bypass and permanently retains the coins in the module account requiring a governance-level migration to ever move them.

### Impact Explanation
The affected deposit amount is permanently locked in the `gov` module account with no automated recovery path — the code itself documents that recovery requires "a migration," i.e., an out-of-band, non-protocol operation. This satisfies the "permanent freezing" of user funds criterion. Any unprivileged user who deposits to a proposal from a not-yet-associated EVM cast address, and subsequently (or has someone else) associates that EVM address to a different Sei address, permanently loses access to that specific deposit through normal protocol mechanisms.

### Likelihood Explanation
This is reachable purely through standard, unprivileged transactions: (1) send `MsgDeposit`/`gov` deposit precompile call from a cast EVM address, (2) call the standard address-association flow (`associatePubKey` / any tx triggering `SetAddressMapping`) for that same EVM address to a different Sei address. Both actions are ordinary features exposed to any EVM/Sei user, requiring no special privilege, making the scenario straightforward to trigger — whether accidentally by a user re-associating their own wallet, or deliberately to grief a specific depositor address they control.

### Recommendation
When `RefundDeposits` detects an unrefundable depositor, provide an explicit, permissionless recovery path (e.g., allow the deposit to be reclaimed once the depositor becomes payable again, or allow the *originally intended* recipient — resolved via the current EVM association — to claim it) instead of leaving it stuck pending only a governance migration. Consistent with the audit's recommendation pattern, the safer design is to check payability at the time of proposal finalization and route unrefundable amounts to a recoverable location (e.g., let the newly associated true Sei address claim it) rather than silently freezing funds indefinitely.

### Proof of Concept
1. User controls EVM address `E` with no prior Sei association; the cast address `C = sdk.AccAddress(E[:])` is currently payable (`CanSendTo(C) == true`).
2. User funds `C` and submits `MsgDeposit` to an active proposal from `C`. `AddDeposit` succeeds, and `C` holds a recorded deposit entry in the gov store.
3. Before the proposal finalizes, the user (or anyone with knowledge of `E`) performs a standard association transaction that calls `SetAddressMapping(ctx, seiAddr, E)` where `seiAddr != C` (e.g., normal `associatePubKey` flow, or a Cosmos tx signed from a real Sei pubkey referencing `E`).
4. Now `CanAddressReceive`/`CanSendTo(C)` returns `false` permanently, as shown in `TestRefundDepositsLeavesInvalidRecipientPending`.
5. When the proposal is resolved (rejected/passed) and `RefundDeposits` runs, the branch at `sei-cosmos/x/gov/keeper/deposit.go:177-182` retains `C`'s deposit forever in the `gov` module account — it is never sent back to `C`, and there is no permissionless function to redirect it to the now-true owner `seiAddr` or to `E`'s new association.

```go
// RefundDeposits refunds deposits whose recipients can receive funds and deletes
// their records. Deposits for unpayable recipients remain recorded and backed by
// the governance module balance.
func (keeper Keeper) RefundDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		depositor := sdk.MustAccAddressFromBech32(deposit.Depositor)
		if keeper.bankKeeper.BlockedAddr(depositor) || !keeper.bankKeeper.CanSendTo(ctx, depositor) {
			// Retain the deposit so its record continues to account for the backing
			// module balance. Recovering a permanently unreceivable deposit requires
			// a migration.
			return false
		}

		err := keeper.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, depositor, deposit.Amount)
		if err != nil {
			panic(err)
		}

		store.Delete(types.DepositKey(proposalID, depositor))
		return false
	})
```

```go
func (k *Keeper) SetAddressMapping(ctx sdk.Context, seiAddress sdk.AccAddress, evmAddress common.Address) {
	store := ctx.KVStore(k.storeKey)
	store.Set(types.EVMAddressToSeiAddressKey(evmAddress), seiAddress)
	store.Set(types.SeiAddressToEVMAddressKey(seiAddress), evmAddress[:])
	if !k.accountKeeper.HasAccount(ctx, seiAddress) {
		k.accountKeeper.SetAccount(ctx, k.accountKeeper.NewAccountWithAddress(ctx, seiAddress))
	}
	ctx.EventManager().EmitEvent(sdk.NewEvent(
		types.EventTypeAddressAssociated,
		sdk.NewAttribute(types.AttributeKeySeiAddress, seiAddress.String()),
		sdk.NewAttribute(types.AttributeKeyEvmAddress, evmAddress.Hex()),
	))
}
```

```go
// A sdk.AccAddress may not receive funds from bank if it's the result of direct-casting
// from an EVM address AND the originating EVM address has already been associated with
// a true (i.e. derived from the same pubkey) sdk.AccAddress.
func (k *Keeper) CanAddressReceive(ctx sdk.Context, addr sdk.AccAddress) bool {
	directCast := common.BytesToAddress(addr) // casting goes both directions since both address formats have 20 bytes
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)
	return associatedAddr.Equals(addr) || !isAssociated // this means it's either a cast address that's not associated yet, or not a cast address at all.
}
```

```go
func TestRefundDepositsLeavesInvalidRecipientPending(t *testing.T) {
	app := seiapp.Setup(t, false, false, false)
	ctx := app.BaseApp.NewContext(false, tmproto.Header{})
	validDepositor := seiapp.AddTestAddrsIncremental(app, ctx, 1, sdk.NewInt(100))[0]

	proposal, err := app.GovKeeper.SubmitProposal(ctx, TestProposal)
	require.NoError(t, err)

	evmAddr := common.HexToAddress("0x0000000000000000000000000000000000000001")
	castDepositor := sdk.AccAddress(evmAddr[:])
	app.EvmKeeper.SetAddressMapping(ctx, castDepositor, evmAddr)
	require.NoError(t, app.BankKeeper.AddCoins(ctx, castDepositor, sdk.NewCoins(sdk.NewInt64Coin(sdk.DefaultBondDenom, 100)), true))

	castDeposit := sdk.NewCoins(sdk.NewInt64Coin(sdk.DefaultBondDenom, 40))
	validDeposit := sdk.NewCoins(sdk.NewInt64Coin(sdk.DefaultBondDenom, 30))
	_, err = app.GovKeeper.AddDeposit(ctx, proposal.ProposalId, castDepositor, castDeposit)
	require.NoError(t, err)
	_, err = app.GovKeeper.AddDeposit(ctx, proposal.ProposalId, validDepositor, validDeposit)
	require.NoError(t, err)

	app.EvmKeeper.SetAddressMapping(ctx, sdk.AccAddress(bytes.Repeat([]byte{2}, common.AddressLength)), evmAddr)
	require.False(t, app.BankKeeper.CanSendTo(ctx, castDepositor))

	app.GovKeeper.RefundDeposits(ctx, proposal.ProposalId)

	deposit, found := app.GovKeeper.GetDeposit(ctx, proposal.ProposalId, castDepositor)
	require.True(t, found)
	require.Equal(t, castDeposit, deposit.Amount)
	_, found = app.GovKeeper.GetDeposit(ctx, proposal.ProposalId, validDepositor)
	require.False(t, found)
	require.Equal(t, sdk.NewInt(100), app.BankKeeper.GetBalance(ctx, validDepositor, sdk.DefaultBondDenom).Amount)
	require.Equal(t, castDeposit, app.BankKeeper.GetAllBalances(ctx, app.AccountKeeper.GetModuleAddress(types.ModuleName)))
}
```
