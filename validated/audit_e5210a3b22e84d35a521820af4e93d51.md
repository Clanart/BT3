### Title
CR-CAT batched claim/authorization can be permanently griefed if a single credentialed output is blocked, halting distribution of all other legitimate outputs in the same bundle - ([File: chia/wallet/vc_wallet/cr_cat_wallet.py])

### Summary
Chia's Credential-Restricted CAT (CR-CAT) design requires every coin in a CAT "ring" to be validated and spent atomically in one `SpendBundle`, gated by a single Verifiable Credential (VC) proof. When a wallet batches several CR-CAT outputs together — e.g. claiming multiple pending-approval CR-CATs (`claim_pending_approval_balance`) or authorizing multiple CR-CAT outputs inside an offer (`add_vc_authorization`) — the entire batch fails if even one included coin's inner-conditions/credential check does not pass. This is directly analogous to the reported "one blacklisted USDC recipient reverts the whole reward distribution" bug class: the CAT ring/VC-authorization mechanism enforces an all-or-nothing push model instead of a pull model, so a single unauthorized/blocked participant can grief the settlement of everyone else batched with them.

### Finding Description
CR-CATs are spent using the standard CAT ring accounting (`unsigned_spend_bundle_for_spendable_cats`), where each coin's spend references the previous/next coin in the ring and the whole set must balance and validate together. [1](#0-0) 

`CRCAT.spend_many` builds exactly this kind of ring for a list of CR-CAT inner spends, all secured with one shared VC `proof_of_inclusions`/`provider_id`/`vc_launcher_id`: [2](#0-1) 

`CRCATWallet.claim_pending_approval_balance` uses this exact pattern to claim multiple pending CR-CAT coins (funds that were sent to a wallet while awaiting VC authorization, analogous to a batch of "reward" outputs) in a single atomic `WalletSpendBundle`, secured by one VC's proof: [3](#0-2) 

Separately, `VCWallet.add_vc_authorization` iterates over every CR-CAT spend found in an offer and validates each one's outputs (`outputs_ok`). If any single CR-CAT spend in the offer is not verifiable/authorized, the function raises and aborts authorization for the *entire* offer, not just the offending coin: [4](#0-3) [5](#0-4) 

The VC used to authorize a batch must satisfy the checker's flags for *all* coins in that batch; if the provider revokes/rotates proofs (the on-chain equivalent of "blacklisting" a participant under a restricted-transfer asset) so that one coin's `authorized_providers`/`proofs_checker` can no longer be satisfied, `get_vc_with_provider_in_and_proofs` fails outright for the whole call: [6](#0-5) 

This mirrors the reported bug class exactly: a "push"-style, all-or-nothing settlement of multiple recipients/outputs in one transaction, where blocking/revoking authorization for a single recipient (CR-CAT's credential mechanism is explicitly built to support provider-side blacklisting/restriction) prevents the honest recipients batched alongside them from receiving their funds in that transaction.

### Impact Explanation
Multiple legitimate CR-CAT recipients who happen to be aggregated into the same claim (`claim_pending_approval_balance`) or the same offer (`add_vc_authorization`) can have their fund distribution/settlement blocked entirely because one participant's credential is no longer valid. This is a real fund-availability/DoS impact scoped to Medium: no funds are stolen or inflated, but honest counterparties cannot complete a settlement they are otherwise entitled to until they re-batch around the blocked coin (if they even know which coin is the problem, since several of the failure paths are unhandled `RuntimeError`/`ValueError` with no partial-success fallback).

### Likelihood Explanation
This requires a CR-CAT deployment where the credential provider can revoke or change proofs for one holder (the intended design of CR-CATs) while other holders remain batched with them in a single wallet operation or offer — a realistic scenario for any credential-gated CAT asset (e.g., compliance-restricted stablecoins built with CR-CATs). The wallet code as written has no pull/partial-success fallback: it doesn't attempt to exclude the failing coin and settle the rest.

### Recommendation
- Avoid bundling unrelated CR-CAT holders' outputs into a single atomic settlement/claim whenever their credential validity is not jointly guaranteed; batch only coins secured by the same, currently-valid VC proof.
- In `claim_pending_approval_balance` and `add_vc_authorization`, detect and exclude coins whose VC/provider check fails instead of raising and aborting the whole operation, allowing the remaining valid coins to be claimed/authorized (a "pull"-style, per-coin fallback) rather than an all-or-nothing batch.
- Surface clearer errors identifying exactly which coin/provider caused the batch failure so wallets can automatically retry excluding it.

### Proof of Concept
1. Two CR-CAT recipients, A and B, both hold pending-approval CR-CATs restricted by the same credential provider/proof flags.
2. The wallet calls `claim_pending_approval_balance` with `coins={A_coin, B_coin}`; this builds one `CRCAT.spend_many` ring and one `WalletSpendBundle` authorized by a single VC (`chia/wallet/vc_wallet/cr_cat_wallet.py:721-752`).
3. Before the claim spend is signed/pushed, the credential provider updates its proof root such that A's flags are no longer satisfied by any available VC.
4. `get_vc_with_provider_in_and_proofs` (or the CR-CAT proof check inside `spend_many`) fails for A, causing the entire batched claim — including B's otherwise-valid coin — to fail to build/push, per `chia/wallet/vc_wallet/vc_wallet.py:610-625`.
5. B cannot claim their legitimate funds in this batch until the wallet is changed to retry excluding A, demonstrating the griefing of a shared "push" settlement by a single blocked participant.

    def spend_many(
        cls,
        inner_spends: list[tuple[Self, int, Program, Program]],  # CRCAT, extra_delta, inner puzzle, inner solution
        # CR layer solving info
        proof_of_inclusions: Program,
        proof_checker_solution: Program,
        provider_id: bytes32,
        vc_launcher_id: bytes32,
        vc_inner_puzhash: bytes32 | None,  # Optional for incomplete spends
    ) -> tuple[list[AssertCoinAnnouncement], list[CoinSpend], list[CRCAT]]:
        """
        Spend a multiple CR-CATs.

        This class will handle all of the CAT accounting information, the only necessary information is the inner
        puzzle/solution, and the proof of a valid VC being spent along side all of the coins. There is currently no
        support for multiple VCs being used across the spend.  There is also currently no support for minting/melting.
        """

        def next_index(index: int) -> int:
            return 0 if index == len(inner_spends) - 1 else index + 1

        def prev_index(index: int) -> int:
            return index - 1

        sorted_inner_spends: list[tuple[Self, int, Program, Program]] = sorted(
            inner_spends,
            key=lambda spend: spend[0].coin.name(),
        )

        all_expected_announcements: list[AssertCoinAnnouncement] = []
        all_coin_spends: list[CoinSpend] = []
        all_new_crcats: list[CRCAT] = []

        subtotal: int = 0
        for i, inner_spend in enumerate(sorted_inner_spends):
            crcat, extra_delta, inner_puzzle, inner_solution = inner_spend
            conditions: list[Program] = list(inner_puzzle.run(inner_solution).as_iter())
            output_amount: int = (
                sum(
                    c.at("rrf").as_int()
                    for c in conditions
                    if c.at("f").as_int() == 51 and c.at("rrf").as_int() != -113
                )
                - extra_delta
            )
            next_crcat, _, _, _ = sorted_inner_spends[next_index(i)]
            prev_crcat, _, _, _ = sorted_inner_spends[prev_index(i)]
            expected_announcements, coin_spend, new_crcats = crcat.do_spend(
                prev_crcat.coin.name(),
                LineageProof(
                    next_crcat.coin.parent_coin_info,
                    next_crcat.construct_cr_layer(
                        next_crcat.inner_puzzle_hash,  # type: ignore
                    ).get_tree_hash_precalc(next_crcat.inner_puzzle_hash),
                    uint64(next_crcat.coin.amount),
                ),
                subtotal,
                extra_delta,
                proof_of_inclusions,
                proof_checker_solution,
                provider_id,
                vc_launcher_id,
                vc_inner_puzhash,
                inner_puzzle,
                inner_solution,
                conditions=conditions,
            )
            all_expected_announcements.extend(expected_announcements)
            all_coin_spends.append(coin_spend)
            all_new_crcats.extend(new_crcats)

            subtotal = subtotal + crcat.coin.amount - output_amount

        return all_expected_announcements, all_coin_spends, all_new_crcats

    async def get_vc_with_provider_in_and_proofs(
        self, authorized_providers: list[bytes32], proofs: list[str]
    ) -> VerifiedCredential:
        vc_records: list[VCRecord] = await self.store.get_vc_records_by_providers(authorized_providers)
        if len(vc_records) == 0:  # pragma: no cover
            raise ValueError(f"VCWallet has no VCs with providers in the following list: {authorized_providers}")
        else:
            for rec in vc_records:
                if rec.vc.proof_hash is None:
                    continue  # pragma: no cover
                vc_proofs: VCProofs | None = await self.store.get_proofs_for_root(rec.vc.proof_hash)
                if vc_proofs is None:
                    continue  # pragma: no cover
                if all(proof in vc_proofs.key_value_pairs for proof in proofs):
                    return rec.vc
        raise ValueError(f"No authorized VC has the correct proofs: {proofs}")  # pragma: no cover
