### Title
Unauthenticated disclosure of encrypted emergency-stop transactions via `internal_get_emergency_stop_tx` on the aggregator's public port - (File: core/src/rpc/aggregator.rs)

### Summary
`AggregatorServiceImpl::internal_get_emergency_stop_tx` fetches rows from `emergency_stop_sigs` via `Database::get_emergency_stop_txs` and returns them to the caller with no authorization check inside the handler itself; all access control for "Internal*" RPCs is delegated to the `Interceptors::OnlyAggregatorAndSelf` gRPC interceptor, which only enforces the self/aggregator-cert restriction when that interceptor is actually installed on the server. The aggregator's own gRPC port is the one meant to accept public, unauthenticated calls from depositors/clients, so if it is served with `Interceptors::Noop` (as `is_internal`/leaf-cert logic requires the caller to go through `only_aggregator_and_self`, which `Noop` never invokes), any unprivileged party who can reach that port can request emergency-stop transaction bytes for an arbitrary move txid.

### Finding Description
The binding that should hold is: `caller_identity == self_or_aggregator_cert` for every RPC method whose name is prefixed `Internal` (enforced by `is_internal()` in `core/src/rpc/interceptors.rs`, lines 12-20, and `only_aggregator_and_self`, lines 36-77). This binding is enforced purely at the interceptor layer — `internal_get_emergency_stop_tx` itself (`core/src/rpc/aggregator.rs`) performs no additional authentication; it directly calls `db.get_emergency_stop_txs(None, txids)` (`core/src/database/aggregator.rs`, lines 33-61) and returns whatever rows exist in `emergency_stop_sigs`.

Because the protection lives entirely in the interceptor, the equality only holds if the *specific gRPC server exposing `AggregatorServiceImpl`* is configured with `Interceptors::OnlyAggregatorAndSelf`. The aggregator's open port, by design, must accept unauthenticated public calls (deposit setup, `NewDeposit`, etc.) from ordinary depositors, which is architecturally inconsistent with requiring every caller to present the aggregator's own leaf certificate. If that server is instead wired with `Interceptors::Noop` (`core/src/rpc/interceptors.rs`, lines 22-32, which simply returns `Ok(req)` without ever calling `is_internal` or `only_aggregator_and_self`), then the "Internal" naming convention provides zero real access control on that port — any caller with network access can invoke `InternalGetEmergencyStopTx{txids: [...]}` and receive the encrypted emergency-stop transaction bytes for any move txid already committed to `emergency_stop_sigs`, including for a deposit whose Challenge/Disprove/ChallengeNACK/Reimburse lifecycle has not completed. ### Impact Explanation
The direct consequence is disclosure, not fund movement: the attacker obtains the encrypted emergency-stop transaction bytes for a deposit before its intended reveal window, which the audit rules classify as High ("premature disclosure of a protocol commitment"). This is repeatable across every deposit/move txid that has an entry in `emergency_stop_sigs`, so the blast radius spans all in-flight deposits, not a single one. Whether this escalates to Critical (operator collateral burned by premature emergency-stop broadcast) depends entirely on whether the same unauthenticated caller can independently derive/obtain the decryption key elsewhere in the protocol — that key-recovery path was not confirmed within the available investigation (I was not able to trace the encryption/decryption key derivation code for `encrypted_emergency_stop_tx` in the time available), so I can only substantiate the High-severity disclosure claim, not the Critical escalation.

### Likelihood Explanation
Preconditions are exactly as stated in the question: `client_verification=false` (or, more precisely, the aggregator's own service being registered under `Interceptors::Noop` rather than `Interceptors::OnlyAggregatorAndSelf`), and an existing `emergency_stop_sigs` row for the targeted move txid (created during ordinary deposit/withdrawal setup, which is normal operator behavior, not attacker-controlled). The attacker only needs gRPC network access to the aggregator's public port and the honest deposit's move txid, which is public/derivable on-chain — no BTC cost, no fee payment, fully repeatable for every deposit.

### Recommendation
Do not rely solely on the interceptor layer for `Internal*` RPCs that live on a server intended to also serve public traffic. Add an explicit authorization check inside `internal_get_emergency_stop_tx` (and any other `Internal*` handler on `AggregatorServiceImpl`) that verifies the caller's identity independent of which interceptor happens to be installed, or split public and internal RPCs onto separate listeners/servers so the public aggregator port can never route to `Internal*` methods regardless of interceptor configuration.

    pub async fn get_emergency_stop_txs(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        move_txids: Vec<Txid>,
    ) -> Result<Vec<(Txid, Vec<u8>)>, BridgeError> {
        if move_txids.is_empty() {
            return Ok(Vec::new());
        }

        let mut query_builder = QueryBuilder::new(
            "SELECT move_txid, emergency_stop_tx FROM emergency_stop_sigs WHERE move_txid IN (",
        );

        let mut separated = query_builder.separated(", ");
        for txid in &move_txids {
            separated.push_bind(TxidDB(*txid));
        }
        query_builder.push(")");

        let query = query_builder.build_query_as::<(TxidDB, Vec<u8>)>();

        let results: Vec<(TxidDB, Vec<u8>)> =
            execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        Ok(results
            .into_iter()
            .map(|(txid, tx_data)| Ok((txid.0, tx_data)))
            .collect::<Result<_, eyre::Report>>()?)
    }
