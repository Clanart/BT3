### Title
Missing path-separator boundary check in `resolveWithin()` allows symlink-based escape from repository root to sibling directories - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` is GitHub Desktop's central guard used to ensure that a path derived from untrusted, repository-supplied data (conflict-resolution file paths, deep-link `filepath` parameters, etc.) stays inside the repository working directory before the app performs a filesystem write. The containment check uses a raw string-prefix comparison, `realResolved.startsWith(realRoot)`, with no trailing path-separator boundary. This is the same class of bug as the reported Solidity issue: a value used to *validate*/*compute* an outcome (`realRoot`, the canonicalized root) does not correspond exactly to the boundary that is actually enforced, letting a value that is “close enough” slip through where a stricter, correctly-bounded comparison would reject it.

### Finding Description
`_resolveWithin()` in [1](#0-0)  computes:

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`realResolved.startsWith(realRoot)` is a naive string-prefix test. It does not verify that `realResolved` is `realRoot` itself or `realRoot + path.sep + …`. Consequently, any sibling path whose name textually begins with the repository root’s full path string will pass the check even though it is a different directory entirely — e.g. `realRoot = "/Users/victim/Documents/GitHub/myrepo"` and `realResolved = "/Users/victim/Documents/GitHub/myrepo-secrets/token.txt"` satisfies `startsWith`, because `"myrepo-secrets"` starts with `"myrepo"`.

This is directly reachable from attacker-controlled repository content:
- `app/src/lib/stores/app-store.ts` uses `resolveWithin(repository.path, resolution.path)` to validate a path before writing AI/Copilot-generated conflict-resolution content with `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` [2](#0-1) .
- `app/src/lib/copilot-conflict-context.ts` uses the same guard to decide which files are safe to read into the AI conflict context [3](#0-2) .
- `app/src/ui/dispatcher/dispatcher.ts` uses it to validate `x-github-desktop://openRepo` deep-link `filepath` parameters before calling `shell.showItemInFolder(resolved)` [4](#0-3) .

The attacker primitive: a **cloned/fetched repository** can contain a symlink (git tree mode `120000`), a normal git object type, whose target — once resolved by `realpath` — points to a sibling directory that shares the repository directory name as a *string prefix* rather than an actual parent/child relationship. GitHub Desktop’s own worktree feature commonly creates exactly this kind of sibling naming pattern next to the main repository directory (e.g. `myrepo` and `myrepo-feature-x`), as seen in `app/src/ui/worktrees/add-worktree-dialog.tsx` where the worktree path is derived from `RepositoryPath`/`safeDirectoryName` and placed by the user typically alongside the source repo [5](#0-4) . The existing regression test suite only validates that fully-outside or back-in-bounds symlink targets are handled correctly; it never asserts the separator-boundary case [6](#0-5) , so this specific bypass is not covered and would not be caught by CI.

### Impact Explanation
If exploited via the Copilot conflict-resolution write path, an attacker who can get a victim to merge/fetch a branch containing a crafted symlink can cause GitHub Desktop to write AI-resolved file content outside the intended repository root into a same-prefixed sibling directory (e.g., another checked-out worktree, or a backup/staging directory adjacent to the repo). This is a silent corruption of a location the user did not intend to modify, and, depending on what sibling directory exists (e.g., another checkout of the same project used to build/deploy), it can escalate to code execution or corruption of what gets built/committed/pushed from that sibling checkout. This satisfies the “file write outside the repo” / “silent corruption” impact criteria.

### Likelihood Explanation
Likelihood is medium: it requires (1) the presence of a symlink checked out from attacker-controlled repository content, and (2) an on-disk sibling directory whose full path is a string-prefix superset of the repository root’s path (not merely sharing a parent directory). This is a realistic layout for developers who use GitHub Desktop’s built-in worktree feature (sibling directories are the norm), but is not guaranteed for every victim, so it is not universally exploitable without some knowledge or luck about the victim’s directory layout.

### Recommendation
Fix the boundary check in `_resolveWithin()` to require an exact match or a match followed by the platform path separator:

```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Apply the same fix to `resolveWithinPosix`/`resolveWithinWin32` variants, and add a regression test that creates a sibling directory named `${basename(root)}-evil` and confirms a symlink pointing into it is rejected.

### Proof of Concept
1. Attacker creates a git repository containing a symlink entry `payload -> ../victimrepo-worktree/secret.txt` (a valid git tree entry, mode `120000`), where `victimrepo-worktree` is a name that shares the victim's expected repo directory name as a prefix (a very plausible name for a Desktop-created worktree sibling directory).
2. Victim clones/fetches and merges this branch in GitHub Desktop, creating a conflict; Desktop’s Copilot conflict-resolution feature (`app/src/lib/stores/app-store.ts` around line 7233) calls `resolveWithin(repository.path, "payload")`.
3. `realpath("<repo>/payload")` resolves to `<siblings>/victimrepo-worktree/secret.txt`. Since `"<...>/victimrepo-worktree/secret.txt".startsWith("<...>/victimrepo")` is `true` (missing separator boundary), the guard incorrectly returns the resolved path as safe.
4. `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` writes AI-generated content to `secret.txt` inside the sibling worktree directory, outside the intended repository, without any warning to the user.

*Note: I was not able to execute this PoC in a live environment (no filesystem/terminal access in this mode); the analysis is based on static review of `app/src/lib/path.ts`, its call sites, and the existing test coverage in `app/test/unit/path-test.ts`.*

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```

```typescript
    const root = process.cwd()

    })

    it('succeeds for paths that traverse out, and then back into, the root', async () => {
      assert.equal(await resolveWithin(root, join('..', basename(root))), root)
    })

    it('fails for paths containing null bytes', async () => {
      assert((await resolveWithin(root, 'foo\0bar')) === null)
    })

    it('succeeds for absolute relative paths as long as they stay within the root', async () => {
      const parent = resolve(root, '..')
```
