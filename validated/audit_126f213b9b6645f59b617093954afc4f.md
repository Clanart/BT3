### Title
`ThresholdKeys::read`/`ThresholdKeys::new` never validate the reconstructed group key is usable — a "zero-address" group key receives funds that are permanently unspendable - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
The Symmio finding is a missing zero-address check on a deposit destination: funds are credited to an address nobody can spend from, and are lost forever. The Serai analog is the threshold-key deserialization path. `ThresholdKeys::read` (an explicitly in-scope sink for untrusted bytes) parses `t`, `n`, `i`, an interpolation method, a `secret_share`, and `n` verification shares, then calls `ThresholdKeys::new`. `ThresholdKeys::new` derives `group_key` as the Lagrange interpolation of `verification_shares[1..=t]` — but performs no validation whatsoever that (a) any share or the resulting group key is non-identity, (b) the supplied `secret_share` is consistent with `verification_shares[i]` (no `G * secret_share == verification_shares[i]` check), or (c) that anyone actually knows a discrete logarithm for the derived `group_key`. Attacker-controlled bytes therefore yield a `ThresholdKeys` whose `group_key()` is an arbitrary point with no known secret — the exact cryptographic equivalent of `address(0)`.

### Finding Description
- `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574–632) reads `t`, `n`, `i` (validated only via `ThresholdParams::new`, which checks `t>0`, `n>0`, `t<=n`, `i<=n`), then reads `n` points via `C::read_G` and delegates to `ThresholdKeys::new`.
- `ThresholdKeys::new` (lines 349–391) checks only the *count* of verification shares and that participant indexes are `<= n`. It then computes `group_key = Σ verification_shares[i] * interpolation_factor(i, [1..=t])` for `i` in `1..=t` (lines 376–378) and stores it unconditionally. There is no rejection of identity verification shares, no non-identity check on the resulting `group_key`, and no consistency check between `secret_share` and `verification_shares[i]`.
- The result is a fully "valid" `ThresholdKeys` whose group key is any point the input bytes encode (e.g., all identity shares → identity; arbitrary shares → a point whose discrete log nobody knows, including the submitter).
- Downstream, `networks/bitcoin/src/wallet/mod.rs` `tweak_keys` (line 46) and `Scanner::new` (line 162) happily build P2TR scriptPubKeys from this `group_key()`. `Scanner::scan_transaction` (lines 199–214) will then report outputs paying to that script as `ReceivedOutput`s — Bitcoin received to an address for which no FROST signing set exists. The outputs are provably unspendable: `SignableTransaction::new`/`multisig` can never produce a valid BIP-340 signature because no shares interpolate to a secret for the group key.
- This is precisely the reported bug class: a missing validity check on the destination of funds causes irreversible loss — funds are "deposited" (scanned as received) to a key that is the functional equivalent of `0x0000...0000`.

### Impact Explanation
Any flow that ingests untrusted `ThresholdKeys` bytes (the `ThresholdKeys::read` sink is explicitly in scope) can produce a multisig whose group key has no corresponding secret. Bitcoin (or any chain) sent to `external_address(group_key)` is scanned, recorded as received outputs, and permanently locked — no signing set exists that can satisfy the key. Loss of funds, matching the original report's impact exactly. Identity group keys additionally route through `x()`/`x_only()` (networks/bitcoin/src/crypto.rs:13–23) which panic on infinity, but the non-identity unknown-DL case silently produces a valid-looking, unspendable address.

### Likelihood Explanation
An unprivileged party only needs to get malformed bytes to `ThresholdKeys::read` — no collusion, no malicious validator, no key leakage. Any encoded `t/n/i` plus `n` arbitrary curve points passes all existing validation (`ThresholdParams::new`, share-count, `read_G` canonicality). The checks that would catch this (consistency of `secret_share` with its verification share, non-identity group key, proof of possession) are simply absent.

### Recommendation
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349), reject identity/`group_key` results and verify share consistency:
```rust
// after computing group_key
if bool::from(group_key.is_identity()) { Err(DkgError::ZeroParameter { .. })?; }
// verify the local share matches its verification share
if C::generator() * secret_share.deref() != verification_shares[&params.i()] {
  Err(DkgError::InvalidParticipant { .. })?;
}
```
At minimum, `read`/`new` must guarantee the group key is non-identity and self-consistent so that a loaded key corresponds to a signable address — the analog of `require(user != address(0))`.
