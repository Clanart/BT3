### Title
Unprivileged spend-bundle submitter can trigger an uncaught `OverflowError` in mempool fee computation via unchecked coin-value arithmetic - (File: `chia/full_node/mempool_manager.py`)

### Summary
`MempoolManager.validate_spend_bundle` computes `fees = uint64(removal_amount - addition_amount)` from unvalidated, attacker-controlled coin amounts before any check that additions cannot exceed removals. `uint64()` on a negative value raises `OverflowError` (confirmed by the project's own test for the `uint64`/`Coin` amount type), mirroring the fedimint pattern where an attacker-reachable, unauthenticated code path fed unvalidated amounts into narrow-width arithmetic that panics/raises rather than being rejected as an ordinary validation error.

### Finding Description
In `chia/full_node/mempool_manager.py`, `addition_amount` is accumulated from the `CREATE_COIN` conditions produced by executing the submitted spend bundle's puzzles, and `removal_amount` is the sum of the amounts of the coins actually being spent: [1](#0-0) [2](#0-1) 

Both `addition_amount` and `removal_amount` are plain Python `int`s built directly from CLVM-computed condition values and coin-record amounts (`removal_record.coin.amount`) with no bound relating them to each other before line 814: [3](#0-2) 

`fees = uint64(removal_amount - addition_amount)` will attempt to construct a `uint64` from a negative Python int whenever `addition_amount > removal_amount` (i.e., a spend bundle that tries to mint more value than it consumes). The project's own tests demonstrate that constructing a sized unsigned integer type from a negative value raises `OverflowError`: [4](#0-3) 

Crucially, the equivalent "can't mint value" guard (`removed < added` → `Err.MINTING_COIN`) exists only in the consensus block-validation path, not in the mempool admission path: [5](#0-4) 

There is no analogous check earlier in `validate_spend_bundle` before the `uint64(removal_amount - addition_amount)` cast at line 814, so a spend bundle whose `CREATE_COIN` outputs sum to more than its spent-coin inputs reaches this arithmetic unguarded, exactly analogous to the fedimint report's pattern of an unauthenticated/unprivileged caller supplying an unvalidated amount that is fed into overflow-sensitive arithmetic at "the single choke point" the request passes through, causing an exception instead of a clean rejection.

`validate_spend_bundle` is documented as needing to run "with the mempool ... locked ... (blockchain lock)" while it mutates no external state until it returns, but is invoked directly from `add_spend_bundle`, which is the entry point full_node uses when it receives a spend bundle from any peer (unprivileged wallet/transaction submitter) via `respond_transaction`/`new_transaction` handling: [6](#0-5) 

### Impact Explanation
Because this computation happens under the mempool/blockchain lock during unauthenticated spend-bundle admission, an uncaught `OverflowError` raised mid-function could:
- Propagate out of `add_spend_bundle`/`validate_spend_bundle` as an unhandled exception during processing of a single peer-submitted spend bundle, rather than being reported through the normal `Err`/`MempoolInclusionStatus` result path used for every other rejection reason in this function.
- Potentially leave the calling task/lock state in an unexpected condition if the exception is not caught with the same care as the many explicit `Err.*` returns nearby, since this is the only failure path in the function that surfaces as a raised exception instead of a typed `Err` result.

This matches the report's core bug class: an unvalidated, remotely-supplied amount reaching arithmetic that raises instead of being explicitly rejected via the mempool's normal error-reporting mechanism — a "spend-triggered transaction-processing" anomaly reachable by any unprivileged spend-bundle submitter, not requiring any block acceptance or malicious peer/node privilege.

### Likelihood Explanation
High reachability: any unprivileged party who can submit a spend bundle to a full node (e.g., via the wallet RPC or the transaction protocol) can craft coin spends whose `CREATE_COIN` conditions sum to more than the amounts of the coins being spent. This requires only a spend bundle with a valid signature over otherwise-arbitrary output amounts (or use of a puzzle the attacker controls) — it does not require controlling a farmer, timelord, or peer identity, and does not require the transaction to ever be accepted into a block.

### Recommendation
Add an explicit, pre-arithmetic minting check in `MempoolManager.validate_spend_bundle` mirroring `block_body_validation.py`'s `Err.MINTING_COIN` guard: reject with a proper `Err` value (e.g. `Err.MINTING_COIN`) as soon as `addition_amount > removal_amount`, before computing `fees = uint64(removal_amount - addition_amount)`. This keeps the failure on the same explicit `(Err, None, [])` return path used by every other validation failure in this function instead of allowing a raised `OverflowError` to escape from unvalidated arithmetic.

### Proof of Concept
1. Construct a `SpendBundle` spending a coin of amount `X` with a puzzle/solution that emits one or more `CREATE_COIN` conditions whose total amount is `Y > X` (still individually `<= MAX_COIN_AMOUNT` so it isn't rejected by the per-coin check during CLVM execution).
2. Submit the spend bundle to a full node as an ordinary, unprivileged transaction (e.g., via `respond_transaction`/wallet RPC).
3. `MempoolManager.validate_spend_bundle` computes `addition_amount` (`Y`) and `removal_amount` (`X`) and reaches `fees = uint64(removal_amount - addition_amount)` at `chia/full_node/mempool_manager.py:814`, i.e. `uint64(X - Y)` with `X - Y < 0`, raising `OverflowError` instead of returning a typed `Err.MINTING_COIN`/rejection result as every other invalid-spend-bundle path does.

*(Note: I was not able to trace, within the available tool budget, the exact exception-handling wrapper around `add_spend_bundle`'s caller in `chia/full_node/full_node.py` to confirm whether this `OverflowError` is caught gracefully at a higher layer or causes broader disruption — this should be verified directly against the full source of `full_node.py`'s transaction-handling call sites before treating this as a confirmed node-crashing DoS rather than a validation-logic gap.)*
