### Title
Unauthenticated `purchase()` for an arbitrary `app` allows anyone to grief-evict a victim app's prepaid Hyperbridge bandwidth via the capped FIFO `Allowance` queue - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth`'s `push_subscription` (invoked from the permissionless `on_accept` purchase path) appends to a per-`(app_chain, app)` FIFO list capped at `MAX_SUBSCRIPTIONS = 1024`, evicting the *oldest* entry once the cap is reached. The `app` field in a purchase message is attacker-controlled and unauthenticated against the actual application it credits — this is documented as an intentional "sponsorship" feature. Because eviction always removes the head of the queue regardless of `remaining_bytes`, a low-cost attacker can push cheap, minimal-tier purchases for a victim `(chain, app)` pair to evict the victim's legitimately-paid, high-value subscriptions before they are consumed, permanently destroying the prepaid bandwidth balance the victim already paid for. This is the same "coverage/queue-griefing" primitive as the external report: an attacker abuses a shared, third-party-writable bounded FIFO structure to force-drop another party's still-valid, paid-for entitlement.

### Finding Description
`modules/pallets/bandwidth/src/lib.rs` implements `push_subscription`: [1](#0-0) 

This function is called both from the admin-only `force_credit` extrinsic and — critically — from the permissionless `on_accept` handler that processes purchase messages arriving from any registered `BandwidthManager` on any source chain: [2](#0-1) 

The only authentication performed is that `request.from` matches the registered `BandwidthManager` contract address for that source chain — there is **no check that `msg.app` belongs to the caller**. The pallet's own module documentation confirms this is intentional "sponsorship": *"a payer chain can sponsor an app that lives elsewhere"* and the app key is taken directly from the purchase message body, not from `request.source`/`request.from` identity: [3](#0-2) 

Because `app` is fully attacker-specified, any unprivileged actor can call `purchase()` on `BandwidthManager.sol` targeting a victim's `(app_chain, app)` pair with the **cheapest configured tier** and a **minimal `months` value**, at negligible cost. Each such purchase enqueues a new `Subscription` onto the victim's `Allowance` list. Once the list is full (or even when it contains only the victim's few legitimate entries), each attacker purchase evicts the oldest entry unconditionally — by FIFO position, not by value:

```rust
let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
    Some(list.remove(0))
} else {
    None
};
let _ = list.try_push(new_sub);
```

The eviction event even documents the loss as a real, auditable financial loss: *"`lost_bytes` is what the user paid for and won't get to use"*: [4](#0-3) 

The `BandwidthGate::try_consume` path that apps rely on to send ISMP messages drains strictly from the head, so any subscription evicted before being drained is bandwidth the victim paid for but can never use, and the app becomes unable to dispatch ISMP requests once its balance is exhausted (`GateError::NoAllowance` / `GateError::Insufficient`), which will cause dispatch failures for the app's legitimate cross-chain messages: [5](#0-4) 

This mirrors the external report's broken invariant exactly: a shared, bounded, FIFO-ordered accounting structure keyed by a beneficiary/receiver-like identifier can be written to by an unrelated third party, and eviction policy (oldest-first) lets the attacker discard the victim's still-valid entitlement cheaply, causing denial-of-service/loss of a resource the victim already paid for — without needing a malicious relayer, prover, or admin.

### Impact Explanation
This directly falls under the explicitly protected invariant in the impact gate: *"Bridged assets, order escrow, refunds, paymaster balances, relayer rewards, and bandwidth balances must move exactly once and only to the rightful beneficiary and amount."* Here, bandwidth balance that a victim application paid for (potentially the $1000/8MB tier) can be destroyed by an attacker spending as little as the cheapest tier's price (as low as $50 for the smallest tier), for as few purchases as needed to exceed the victim's current queue depth. The consequence is: (a) direct financial loss — the app's paid bandwidth is unusable, and (b) denial of service — the app cannot dispatch ISMP messages through Hyperbridge once its allowance is drained/evicted, which can disrupt whatever cross-chain functionality depends on it (e.g., stalled cross-chain settlement, timeouts, or other app-critical dispatches gated by `BandwidthGate`).

### Likelihood Explanation
High. The attack requires only:
1. Calling the permissionless `purchase()` function on the publicly deployed `BandwidthManager.sol` for the target source chain.
2. Supplying the victim's `app` bytes (public knowledge — any deployed contract/app address) and the cheapest tier/lowest `months`.
3. Repeating it enough times to exceed the victim's live subscription count (not necessarily the full 1024 cap — only enough to push out the entries the victim currently holds).

No relayer collusion, no governance/admin access, and no race condition with legitimate consumption is required — the eviction happens unconditionally on push regardless of whether the victim's subscription has been touched by the gate yet.

### Recommendation
- Do not allow the FIFO eviction policy to discard subscriptions purely by insertion order when they are not the attacker's own purchase. Consider: (a) requiring `msg.sender`/an authenticated relationship between the payer and `app` for eviction-affecting pushes, or (b) evicting only subscriptions purchased by the same payer/source that is pushing a new entry, so third-party sponsorship purchases cannot force out the victim's own or previously sponsored allocations.
- Alternatively, increase `MAX_SUBSCRIPTIONS` cap enforcement to per-payer sub-lists, or track a minimum-value/least-recently-scheduled-to-expire eviction rather than strict oldest-first, so an attacker cannot cheaply displace a high-value, long-duration subscription with many cheap short ones.
- Emit and rate-limit/require a minimum tier value per purchase to raise the cost of griefing pushes, and/or add a per-`(source, app)` purchase cooldown to slow down mass cheap-tier pushes from arbitrary third parties.

### Proof of Concept
1. Victim app `V` (address `0xVictim`) on chain `EVM(8453)` legitimately purchases a `TierFour` (8MB) 6-month bandwidth subscription via `BandwidthManager.purchase({app: 0xVictim, tier: 4, months: 6, chain: "EVM-8453"})`. This lands one `Subscription` in `Allowance[EVM(8453)][0xVictim]`.
2. Attacker `A` (unrelated, unprivileged) observes `0xVictim`'s app address on-chain (public) and calls `BandwidthManager.purchase({app: 0xVictim, tier: 1, months: 1, chain: "EVM-8453"})` — the cheapest tier ($50), paid by the attacker, but crediting the victim's `(chain, app)` key.
3. Because the pallet only checks `request.from == BandwidthManager` and never checks that the caller of `purchase()` is `0xVictim` or authorized by it, `on_accept` calls `push_subscription(EVM(8453), 0xVictim, TierOne, ...)`.
4. If the victim's list already has entries (e.g., 1 from step 1) and the attacker keeps repeating cheap purchases enough times to reach/exceed the 1024 cap (or simply outnumber whatever count the victim currently holds relative to what's already been drained), each subsequent attacker purchase evicts the oldest entry — eventually evicting the victim's `TierFour` 8MB/6-month subscription before it's ever consumed, firing `SubscriptionEvicted { app_chain: EVM(8453), app: 0xVictim, tier: TierFour, lost_bytes: <full 8MB*6> }`.
5. `V`'s dispatches through Hyperbridge subsequently fail with `GateError::NoAllowance`/`Insufficient` in `BandwidthGate::try_consume`, even though `V` paid in full for the evicted allowance.

This scenario is directly exercised in the existing test harness pattern (`subscription_cap_evicts_oldest`), which confirms the eviction mechanics operate exactly as described — the only missing piece for the real-world attack is that `push_subscription` is reachable from the fully permissionless purchase flow with attacker-chosen `app`, not just from the admin-gated `force_credit` call used in that test: [6](#0-5)

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

	impl<T: Config> IsmpModule for Pallet<T> {
		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

/// The 1024-sub cap evicts the oldest entry. force_credit reuses the
/// same push path as purchase, so this also covers the purchase cap.
#[test]
fn subscription_cap_evicts_oldest() {
	new_test_ext().execute_with(|| {
		jump_to(T0);
		let cap = MAX_SUBSCRIPTIONS as u128;

		// Fill the list to exactly the cap. `bytes` encodes the index
		// so we can prove which one got evicted.
		for i in 0..cap {
			Bandwidth::force_credit(
				RuntimeOrigin::root(),
				ForceCreditParams {
					app_chain: APP_CHAIN,
					app: app_key(),
					tier: TIER1,
					bytes: i + 1,
					duration_secs: MONTH_SECS,
				},
			)
			.unwrap();
		}
		assert_eq!(sub_count(APP_CHAIN), cap as usize);
		assert_eq!(sub_at(APP_CHAIN, 0).unwrap().remaining_bytes, 1, "oldest is index 1");

		// One more push: evicts the oldest, appends the new one.
		Bandwidth::force_credit(
			RuntimeOrigin::root(),
			ForceCreditParams {
				app_chain: APP_CHAIN,
				app: app_key(),
				tier: TIER1,
				bytes: cap + 1,
				duration_secs: MONTH_SECS,
			},
		)
		.unwrap();

		assert_eq!(sub_count(APP_CHAIN), cap as usize, "still capped");
		assert_eq!(
			sub_at(APP_CHAIN, 0).unwrap().remaining_bytes,
			2,
			"former second-oldest is now front",
		);
		assert_eq!(
			sub_at(APP_CHAIN, (cap - 1) as usize).unwrap().remaining_bytes,
			cap + 1,
			"new sub is at the back",
		);
	});
}
