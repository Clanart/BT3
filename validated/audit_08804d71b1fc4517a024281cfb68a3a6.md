## Title
`discardChanges()` resolves attacker-influenced working-directory paths with unvalidated `Path.resolve`/`Path.join`, allowing file operations to escape the repository root - (File: `app/src/lib/stores/git-store.ts`)

## Summary
The codebase already has a hardened helper, `resolveWithin()` (and `resolveWithinPosix`/`resolveWithinWin32`), whose explicit purpose is to guarantee a path resolved from a repository-relative segment cannot escape the repo root — it normalizes, checks for null bytes, and additionally calls `realpath()` on both the root and the resolved path to defeat symlink-based escapes. [1](#0-0) 
This helper is used to sanitize filepaths coming from external/untrusted sources such as deep-link `x-github-client://openRepo` URLs. [2](#0-1) 

However, `GitStore.discardChanges()` — which is the analog of the "loop over untrusted/attacker-supplied data with no bound-checking" pattern from the report, just applied to path safety instead of gas — takes `file.path` values straight from parsed `git status` output and feeds them directly into `Path.resolve`/`Path.join` with **no `resolveWithin`/symlink check**: [3](#0-2) 

## Finding Description
`file.path` originates from `getStatus()` → `parsePorcelainStatus()`, which parses raw NUL-separated `git status --porcelain=2 -z` output. The parser's own comments explicitly note that, unlike the human-readable format, this machine format performs **no quoting or escaping of filenames**: [4](#0-3) 
and the untrusted `path`/`oldPath` fields are extracted with a permissive regex and returned as-is: [5](#0-4) 

These raw path strings flow into `WorkingDirectoryFileChange`, and ultimately into `discardChanges()`, which resolves them against the repository root using plain `Path.resolve`/`Path.join` — not `resolveWithin`: [6](#0-5) 

The invariant that is broken: "any path operation derived from repository content must stay confined to the repository root," which the app enforces elsewhere via `resolveWithin` (e.g. for deep-link file paths) but not here. If a cloned/fetched repository working tree contains a directory that is (or becomes, via a checked-out symlink) a symlink pointing outside the repository — e.g. `evil-dir -> /Users/victim/Library/Application Support` — and an untracked/modified file is reported under that path (`evil-dir/malicious-file`), `git status` will surface that path verbatim. When the user discards changes, Desktop calls `shell.moveItemToTrash(Path.resolve(repoPath, 'evil-dir/malicious-file'))` or `rm(Path.join(repoPath, ...))`, which the OS/Node resolves through the symlink to a location **outside the repository**, deleting or moving an arbitrary file the attacker chose. `Path.resolve`/`Path.join` perform only lexical path joining; they do not call `realpath()` and are therefore blind to symlink indirection, unlike `resolveWithin()` which explicitly guards against exactly this.

## Impact Explanation
This matches the accepted impact class "attacker controls a cloned/fetched repository... and the result is ... file write or read outside the repo." A malicious repository (delivered via clone URL, a shared repo, or a fork the victim adds as a remote) can plant a symlinked directory that, combined with normal Desktop usage ("Discard Changes" on files under that directory), causes deletion/move of files outside the working tree without any additional unnatural steps from the user — discarding changes is a routine, expected Desktop action.

## Likelihood Explanation
Likelihood is high for the setup (planting a symlink + tracked/untracked file under it in a git tree is straightforward and requires no special git server behavior — the attacker just crafts the repository content), and the trigger (`Discard Changes`) is a common Desktop action performed on any file shown as changed. The only prerequisite is that the victim opens/clones the malicious repository and invokes "Discard Changes" on the affected path, which does not require special or unnatural interaction beyond ordinary Desktop use.

## Recommendation
In `GitStore.discardChanges()`, replace the direct `Path.resolve(this.repository.path, file.path)` / `Path.join(this.repository.path, file.path)` calls with the existing `resolveWithin()` helper (already used for deep-link paths in `dispatcher.ts`) and abort/skip the discard for any path that resolves to `null` (i.e., escapes the repository root via traversal or symlink). Apply the same guard to `oldPath` used for renamed/copied entries.

## Proof of Concept
Conceptual PoC (cannot be executed here, but derivable from the cited code paths):
1. Craft a malicious repository containing a symlinked directory committed via git (e.g. `ln -s /Users/victim/Desktop evil-dir && git add evil-dir && git commit`), then add an untracked file `evil-dir/target-file` after checkout so that `git status --porcelain=2 -z` reports `evil-dir/target-file` as untracked.
2. Have the victim clone this repository in GitHub Desktop; the symlink is checked out, creating `evil-dir` → `/Users/victim/Desktop` on disk.
3. The victim opens the "Changes" pane, sees `evil-dir/target-file` listed, selects it, and clicks "Discard Changes."
4. `GitStore.discardChanges()` executes `shell.moveItemToTrash(Path.resolve(repoPath, 'evil-dir/target-file'))` [7](#0-6)  which the OS resolves through the symlink, moving/deleting `/Users/victim/Desktop/target-file` — a file entirely outside the cloned repository — into the trash, without any warning that the operation left the repo boundary.

Note: I was not able to execute this PoC in a live environment to confirm OS-level symlink-following behavior for `shell.trashItem`/`fs.rm` on all platforms; this is inferred from the code paths shown and the documented purpose of `resolveWithin`'s `realpath`-based guard, which strongly suggests the maintainers were already aware of this exact escape vector for other input paths but did not apply the same protection to `discardChanges`.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```

```typescript
  oldPath: string | undefined

    statusCode: match[1],
```
