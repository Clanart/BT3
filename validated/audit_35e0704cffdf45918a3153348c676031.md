### Title
Anyone can force the multisig to classify, schedule, and sign transactions over unsolicited outputs by sending ≥ dust to its deterministic internal scripts - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs), [processor/src/multisigs/scheduler/utxo.rs](processor/src/multisigs/scheduler/utxo.rs))

### Summary
The source report's bug class is "an unprivileged party performs an action that mutates state on behalf of, and to the detriment of, another party" (depositing for a victim to reset their lockout). The Serai analog lives in the Bitcoin scanning/scheduling path: the multisig's addresses are deterministic functions of the public group key (`p2tr_script_buf(key + G*offset)`), so anyone can compute and pay to them. The scanner accepts every on-chain output paying to any registered script with value `>= N::DUST` as a protocol-owned input, with no consent step. In particular, sending to the *internal* Branch script with an amount matching a key in `self.plans` causes `add_outputs` to pop a queued payment plan and immediately produce a transaction to be signed — i.e., attacker-crafted input bytes drive the signing of a transaction the protocol did not originate. At minimum, every ≥10,000-sat output forces `ScannerEvent::Block` emission, scheduler `schedule()`, UTXO aggregation plans, and threshold signing rounds, at a recurring attacker cost of dust plus fees.

### Finding Description
`Scanner::register_offset` builds a `scripts: HashMap<ScriptBuf, Scalar>` covering External, Branch, Change, and Forwarded addresses, all derived deterministically from the public group key (`processor/src/networks/bitcoin.rs` `scanner()`, `register` closure). `Scanner::scan_transaction` matches purely on `output.script_pubkey` and returns a `ReceivedOutput` for every match. `Bitcoin::get_outputs` then accepts any such output with `amount >= N::DUST` (10,000 sats) into `outputs`, and `Scanner::run` emits `ScannerEvent::Block` whenever `outputs` is non-empty, pushing the block onto `need_ack` and driving downstream `schedule()` calls.

No check ties an output to a user-initiated deposit flow or to an expected internal transaction. The scheduler consumes the result directly: `Scheduler::add_outputs` in `processor/src/multisigs/scheduler/utxo.rs` checks `utxo.kind() == OutputType::Branch` and, if `self.plans` contains an entry keyed by `utxo.balance().amount.0`, executes `self.execute(vec![utxo], payments, key_for_any_change)` — producing a Plan that is signed by the FROST threshold signing pipeline — using the attacker's output as the input. The branch addresses are never published as deposit targets, yet the code assumes only protocol-created transactions can pay them (the comment in `schedule` acknowledges only self-payments to one's own branch address are filtered, and only for payments, not for received outputs).

Additionally, because classification is by offset and kinds include Change and Forwarded, an attacker paying those scripts produces outputs whose handling (`ForwardedOutputDb::take_forwarded_output`, `created_output` amortization bookkeeping in `queued_plans`) presumes protocol provenance.

### Impact Explanation
- Signing of transactions not originated by the protocol: an attacker can trigger `add_outputs`'s branch-execution path, causing the multisig to spend an attacker-supplied input and execute queued payment plans out of the expected order/context.
- Sustained griefing analogous to the original finding's "cost = minDeposit each lockout period": each block, a ≥DUST payment to any of the four scripts forces a `ScannerEvent::Block` requiring multisig synchrony, scheduler runs, and threshold signing rounds (UTXO aggregation TXs), while the depositing funds remain attacker-owned value credited through the normal deposit path — the attacker primarily loses transaction fees.
- Accounting pressure: outputs misclassified as Change/Forwarded feed bookkeeping (`created_output`, `ForwardedOutputDb`) that assumes the output was protocol-created, enabling confusion between genuinely-created branch outputs and attacker-injected ones.

### Likelihood Explanation
The attack requires only sending standard Bitcoin transactions — no validator status, no keys. The scripts are computable by anyone from the public group key (`p2tr_script_buf` applied to `key + G*offset` for the four public `hash_to_F`-derived offsets). Cost per trigger is `N::DUST` (10,000 sats, recoverable as a credited deposit for the External script) plus miner fees, and it can be repeated every block. The branch-plan trigger additionally requires guessing an in-flight plan amount, which limits that variant; the forced-scanning/forced-signing variant is unconditional.

### Recommendation
Bind received outputs to expected protocol actions rather than to script alone. Concretely: only treat Branch/Change/Forwarded-script outputs as internal if their outpoint belongs to a transaction the multisig itself signed (checkable via the Eventuality/Plan registry, e.g. `ForwardedOutputDb` / created-output tracking), and drop or quarantine unsolicited outputs to internal scripts. For External outputs, consider requiring a valid `InInstruction` payload before admitting the output to `schedule()`/`add_outputs`, or at minimum rate-limiting blocks that produce `ScannerEvent::Block` solely from unsolicited dust deposits.

### Proof of Concept
1. Observe the multisig's public group key `K`. Compute the internal scripts locally via `Scanner::new(K)` + `register_offset(hash_to_F("Serai Bitcoin Output Offset", b"branch" | b"change" | b"forward"))` — identical derivation to `processor/src/networks/bitcoin.rs::scanner`.
2. Send a transaction paying `>= 10_000` sats to the External (or any internal) script every block. `Bitcoin::get_outputs` (`for tx in &block.txdata[1 ..]` → `scanner.scan_transaction(tx)` → `output.balance().amount.0 >= N::DUST`) accepts each output; `Scanner::run` emits `ScannerEvent::Block` and pushes to `need_ack`, forcing scheduling and signing work per block.
3. For the stronger variant, when a queued plan exists in `self.plans` keyed by amount `a`, send a branch-script output of exactly `a`. `Scheduler::add_outputs` hits `self.plans.get_mut(&amount)`, pops the queued payments, and calls `self.execute(vec![utxo], payments, key_for_any_change)`, producing a Plan the signers will threshold-sign — a transaction spending the attacker's input that the protocol never initiated.

Key code: `networks/bitcoin/src/wallet/mod.rs` (`Scanner::scan_transaction`, matching solely on `script_pubkey`), `processor/src/networks/bitcoin.rs` (`get_outputs`, `scanner()` registering all four offsets), `processor/src/multisigs/scanner.rs` (emitting `ScannerEvent::Block` on any non-empty `outputs`), `processor/src/multisigs/scheduler/utxo.rs` (`add_outputs` executing a queued plan for any Branch-kind output whose amount matches a key).
