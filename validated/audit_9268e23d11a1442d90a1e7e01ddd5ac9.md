### Title
OP_RETURN data is excluded from Bitcoin transaction weight and fee accounting - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` adds a caller-supplied OP_RETURN output but calculates transaction weight and required fee only from the declared payments, omitting the OP_RETURN output from both calculations. A transaction containing OP_RETURN data therefore pays less than the requested fee rate and can even fail Bitcoin's minimum relay-fee check despite passing the local check.

### Finding Description
`SignableTransaction::new` accepts up to 80 bytes of transaction data. [1](#0-0) 

When data is present, it appends a zero-value OP_RETURN output to `tx_outs`. [2](#0-1) 

The initial weight and virtual-size calculation nevertheless receives only `payments`, not the completed `tx_outs` list or the serialized OP_RETURN script. [3](#0-2) 

The same omission occurs when calculating size and fee with a change output, again passing only `payments`. [4](#0-3) 

`calculate_weight_vbytes` constructs the sizing transaction exclusively from the supplied `payments`, so an OP_RETURN output that was not included in that parameter has no effect on either weight or virtual size. [5](#0-4) 

The zero-value OP_RETURN is still present in the final transaction, while `fee()` computes the actual fee as inputs minus all transaction outputs. [6](#0-5) 

### Impact Explanation
Any OP_RETURN data increases the serialized transaction's weight and virtual size, but the attacker- or caller-controlled data contributes nothing to `needed_fee` or the minimum-relay-fee comparison. [7](#0-6) 

The produced transaction can consequently have an effective fee rate below `fee_per_vbyte`, and a sufficiently large OP_RETURN can make it fall below Bitcoin's default minimum relay fee even though `TooLowFee` was not returned. [8](#0-7) 

This is analogous to charging only for a compact transaction field while leaving separately supplied bytes and their verification/relay cost unpriced. [9](#0-8) 

### Likelihood Explanation
An unprivileged party able to supply the optional `data` field for a transaction signing request can trigger the discrepancy without malformed encodings or control over private key material. [10](#0-9) 

The condition is deterministic whenever `data` is `Some`, because the OP_RETURN output is appended before size accounting but is not represented in the payment list used for that accounting. [11](#0-10) 

Transactions near the requested fee-rate floor are the most likely to become non-relayable or remain unconfirmed. [8](#0-7) 

### Recommendation
Include the OP_RETURN output in `calculate_weight_vbytes`, either by passing the finalized `tx_outs` scripts and values or by explicitly modeling the OP_RETURN output. [5](#0-4) 

Recompute the final weight, virtual size, `needed_fee`, and minimum-fee check after all payment, data, and change outputs have been determined. [12](#0-11) 

### Proof of Concept
Construct a `SignableTransaction` with one funded input, one valid payment, no change, `fee_per_vbyte = 1`, and `data = Some(vec![0; 80])`. [13](#0-12) 

The function adds a zero-value OP_RETURN output containing the 80-byte push, which enlarges the final transaction by the output's amount field, script length, and script bytes. [2](#0-1) 

However, both the estimated virtual size and fee are calculated from a transaction containing only the payment output, so the OP_RETURN's roughly 90 additional weight units are charged zero satoshis. [7](#0-6) 

Because `fee()` remains `input - sum(outputs)` and the OP_RETURN has value zero, the transaction returns a fee equal to the too-small `needed_fee` while its actual size is larger. [6](#0-5) 

For example, if the OP_RETURN raises the transaction from approximately 58 vbytes to approximately 81 vbytes at one satoshi per vbyte, the local minimum check charges only 58 satoshis rather than approximately 81 satoshis, yielding a relay fee below the default minimum. [8](#0-7)
