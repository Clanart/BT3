### Title
Copilot conflict-resolution write path lacks a hard "resolved path must be one of the original conflicted files" gate before writing file content - (File: app/src/lib/stores/app-store.ts)

### Summary
When Copilot-assisted conflict resolution completes, the app iterates the model's `copilotResolutions` and, for every entry that isn't a delete-vs-modify conflict, calls `resolveWithin(repository.path, resolution.path)` and then unconditionally `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` unless an *on-disk file* happens to already exist at that path in a conflicted, unresolved state. [1](#0-0) 

### Finding Description
`validateResolutionPaths` is the only place that enforces "the model may only return paths that were part of the originally sent conflict context," and it is a parse-time check on the raw LLM JSON. [2](#0-1) 
By the time `applyCopilotConflictResolutions` (the write path at `app-store.ts:7171-7269`) runs, it no longer consults that expected-files set. Instead, for each resolution it only checks whether the path currently exists in the live `workingDirectory.files` list as an unresolved conflict, and if not found (`onDiskFile === undefined`), the `if` guard is false and execution falls straight through to `writeFile`: [3](#0-2) 
The only remaining safety net is `resolveWithin(repository.path, resolution.path)`, which prevents writes *outside* `repository.path` but does nothing to prevent writes to arbitrary paths *inside* the repository working tree — including `.git/hooks/*`, `.git/config`, or CI/config files like `.husky/*`, `package.json` scripts, etc. [4](#0-3) 
Since the content sent to the LLM (commit messages, PR titles/descriptions, conflicting hunks) is attacker-controlled when the conflict originates from merging a branch or PR authored by an untrusted contributor, and the model is documented to be steerable purely via that prompt content (no tool calls, JSON-only), a prompt-injection payload embedded in a conflicting file/commit message could cause the model to emit a `resolutions[].path` that: (a) was never one of the actual conflicted files, and (b) points at a sensitive in-repo path such as `.git/hooks/post-checkout` or `.git/hooks/pre-commit`. `resolveWithin` will happily resolve that path since `.git` lives under `repository.path`, and the code will write the model's `resolvedContent` there verbatim, then `git add` any staged conflict paths (hooks aren't tracked by git so they won't even show as a diff to the user).

### Impact Explanation
Writing attacker/LLM-influenced content into `.git/hooks/*` is a well-known git hook -> local code execution primitive: the next time the victim runs any git operation that triggers that hook from Desktop or the CLI (commit, checkout, merge, push), arbitrary shell commands execute with the user's privileges. This satisfies the "unprivileged attacker controls a cloned/fetched repository ... resulting in code execution" bar, and separately, even for non-hook targets (e.g. silently rewriting an unrelated tracked file that wasn't part of the conflict), it is a silent corruption of what the user ultimately commits/pushes, since the write happens without going through the normal per-file conflict review the manual-resolution UI provides.

### Likelihood Explanation
Requires: (1) the attacker to control a branch/PR that will be merged/rebased/cherry-picked, producing a genuine conflict, and (2) the victim to have Copilot conflict resolution enabled and to accept its output, and (3) successful prompt injection to elicit an out-of-scope path from the model. Model output is nondeterministic and the existing `validateResolutionPaths` check (used elsewhere in the pipeline) suggests the authors intended to close exactly this gap — but the write path shown here does not appear to call it, making this a real gap that a background agent should confirm by tracing the full call chain from `_generateCommitMessage`-style Copilot flow through to `applyCopilotConflictResolutions`/`writeFile` to see whether `validateResolutionPaths` (or an equivalent expected-file-set check) is actually invoked upstream of this exact code path. I was not able to fully confirm within this session whether `validateResolutionPaths` is called before `copilotResolutions` is populated in `multiCommitOperationState`, so this should be verified before treating this as a confirmed, unmitigated vulnerability.

### Recommendation
Before writing, re-validate `resolution.path` against the exact set of paths originally sent to the model for this conflict resolution run (the same `expectedFiles`/`fileContexts` set used by `validateResolutionPaths`/`reassembleResolutions`), not against the live `workingDirectory.files` snapshot, and reject/skip any resolution whose path isn't in that set. Additionally, explicitly deny any path under `.git/` (or matching other sensitive prefixes) as a defense-in-depth measure in `resolveWithin`-based write helpers used for AI-generated content.

### Proof of Concept
1. Attacker crafts a branch/PR whose conflicting file (or commit message/PR description used as LLM context) contains an injection payload instructing the model to also emit a resolution entry with `"path": ".git/hooks/post-checkout"` and shell-script `resolvedContent`.
2. Victim, using GitHub Desktop's Copilot conflict resolution, merges/rebases against that branch; a conflict is detected and Copilot is invoked.
3. If the model complies (or `validateResolutionPaths` is not actually enforced ahead of `applyCopilotConflictResolutions`), the loop in `app-store.ts:7196-7259` finds `onDiskFile === undefined` for `.git/hooks/post-checkout` (it's not a working-directory file), skips the "already resolved externally" guard, and calls `writeFile` on the resolved absolute path.
4. Next `git checkout` performed by the victim (including ones Desktop performs internally, e.g. branch switch) executes the attacker's script. [1](#0-0)

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
