Confirmed mechanism: `CanAddressReceive` (registered as the bank module's `RecipientChecker` in `app/app.go`) permanently blocks a "cast" address from receiving funds once its underlying EVM address gets explicitly associated with a *different* Sei address. This is reachable by an ordinary user through a single, unprivileged transaction (e.g., delegating/staking from an unassociated EVM-derived cast address, then later signing an Associate transaction, or having their EVM pubkey recovered under a different Sei address by any transaction). The staking module's unbonding-completion path does not defend against this, and — unlike the distribution module's `SetWithdrawAddr`/`AfterValidatorRemoved` guards that were hardened for exactly this class of issue — `CompleteUnbonding` has no such fallback, and the EndBlock queue-processing logic permanently drops the entry from its retry queue on failure.

### Title
Unbonding delegations to a de-authorized cast address are permanently stuck and unretrievable - (File: sei-cosmos/x/staking/keeper/val_state_change.go)

### Summary
`x/staking`'s `CompleteUnbonding` pays out matured unbonding delegations via `bankKeeper.UndelegateCoinsFromModuleToAccount`, which is gated by `CanSendTo`/`CanAddressReceive`. If the delegator address is a "cast" (byte-derived) Sei address whose corresponding EVM address later becomes explicitly associated with a *different* Sei address, `CanAddressReceive` permanently returns `false` for that cast address. When the unbonding delegation matures, `CompleteUnbonding` fails, and `BlockValidatorUpdates`/`DequeueAllMatureUBDQueue` silently `continue`s past the error — but it has already deleted the maturity-time-slice queue entry from the store. The underlying `UnbondingDelegation` record is retained, but nothing ever re-inserts it into the UBD queue, so the entry is never retried and the delegator's principal remains locked in the `NotBondedPool` module account forever.

### Finding Description
- `k.bankKeeper.CanAddressReceive` is registered as the bank module's recipient checker in `app/app.go`: `app.BankKeeper.RegisterRecipientChecker(app.EvmKeeper.CanAddressReceive)`. [1](#0-0) 
- `CanAddressReceive` returns `false` whenever an address is a direct EVM→Sei cast whose EVM counterpart has since been associated with a *different* Sei address — this is a one-way transition reachable purely by any user submitting an Associate/other signed transaction. [2](#0-1) 
- `BaseSendKeeper.AddWei`/`AddCoins`/`SendCoinsAndWei` all gate on `CanSendTo`, which runs every registered `RecipientChecker`. [3](#0-2) 
- `CompleteUnbonding` sends the matured principal to the delegator via `UndelegateCoinsFromModuleToAccount`, and returns an error (without side effects to the queue) if that send fails. [4](#0-3) 
- `BlockValidatorUpdates` first calls `DequeueAllMatureUBDQueue`, which unconditionally deletes each maturity time-slice from the store as soon as it's iterated, *before* `CompleteUnbonding` is ever invoked; if `CompleteUnbonding` then fails, the loop just `continue`s — the `UnbondingDelegation` record stays in state, but is permanently orphaned from the time-based retry queue. [5](#0-4) [6](#0-5) 
- This exact scenario is directly reproduced and asserted as "expected" (non-panicking) behavior in `TestEndBlockRetainsUnbondingForInvalidRecipient`: it sets up a delegator as a cast address, re-associates the underlying EVM address to a different Sei address (making `CanSendTo` return `false`), inserts a matured `UnbondingDelegation`, runs `EndBlocker`, and confirms the pool balance is unchanged, the delegator balance is zero, and the `UnbondingDelegation` is retained in state while removed from the queue iterator range. [7](#0-6) 

This is the structural analog of the reported Blueberry issue: a permanently-inaccessible payout target (there: a token-level blacklist; here: `CanAddressReceive`'s address-association rule) causes the payout of already-committed principal to fail with no recovery path, and no mechanism exists to change the "position owner" (i.e., re-target the withdrawal) for an already-queued unbonding delegation. Unlike the distribution module — which was specifically hardened with a `canReceiveWithdrawAddr` check in `SetWithdrawAddr` and a community-pool fallback in `AfterValidatorRemoved` for this exact same address-association hazard — staking's `CompleteUnbonding` has no equivalent guard or fallback.

### Impact Explanation
The delegator's staked principal becomes permanently locked in the `NotBondedPool` module account. There is no user-facing operation (no "redirect withdraw address" equivalent for unbonding payouts, and no automatic re-queue) to recover it. This is a genuine permanent freezing of funds triggered entirely by ordinary, unprivileged user transactions (staking from a not-yet-associated EVM-derived address, then associating that EVM address to a different Sei address, e.g. via any tx that recovers the pubkey under a different account, or an explicit Associate flow) — no validator or governance action is required.

### Likelihood Explanation
Address re-association from a cast address to a distinct associated address is an ordinary user-triggered event on Sei (any Cosmos- or EVM-signed transaction can trigger association of an EVM pubkey to a Sei address, and users routinely delegate/stake before ever having explicitly associated). Anyone who (a) delegates from a not-yet-associated cast address, and (b) undelegates, and (c) has their EVM address later associated to a *different* Sei address before the unbonding matures, will trigger this. Given cast addresses are a normal, documented address state on Sei (see `x/evm/AGENTS.md`'s Dual Address Model), this is readily reachable without any privileged action. [8](#0-7) 

### Recommendation
Mirror the mitigation already applied in `x/distribution` (`canReceiveWithdrawAddr` check plus a fallback path in `AfterValidatorRemoved`): in `x/staking/keeper/val_state_change.go`/`delegation.go`, if `CompleteUnbonding`'s payout fails because the delegator cannot receive funds, do not just `continue` and orphan the entry — either (a) re-insert the failed `DVPair` back into the UBD queue for retry at a later maturity time, or (b) provide a dedicated "claim to alternate address" / "redirect unbonding payout" message so the user can supply a currently-receivable address, analogous to `SetWithdrawAddr` for staking rewards.

// DequeueAllMatureUBDQueue returns a concatenated list of all the timeslices inclusively previous to
// currTime, and deletes the timeslices from the queue.
func (k Keeper) DequeueAllMatureUBDQueue(ctx sdk.Context, currTime time.Time) (matureUnbonds []types.DVPair) {
	store := ctx.KVStore(k.storeKey)

	// gets an iterator for all timeslices from time 0 until the current Blockheader time
	unbondingTimesliceIterator := k.UBDQueueIterator(ctx, ctx.BlockHeader().Time)
	defer func() { _ = unbondingTimesliceIterator.Close() }()

	for ; unbondingTimesliceIterator.Valid(); unbondingTimesliceIterator.Next() {
		timeslice := types.DVPairs{}
		value := unbondingTimesliceIterator.Value()
		k.cdc.MustUnmarshal(value, &timeslice)

		matureUnbonds = append(matureUnbonds, timeslice.Pairs...)

		store.Delete(unbondingTimesliceIterator.Key())
	}

	return matureUnbonds
}

// CompleteUnbonding completes the unbonding of all mature entries in the
// retrieved unbonding delegation object and returns the total unbonding balance
// or an error upon failure.
func (k Keeper) CompleteUnbonding(ctx sdk.Context, delAddr sdk.AccAddress, valAddr sdk.ValAddress) (sdk.Coins, error) {
	ubd, found := k.GetUnbondingDelegation(ctx, delAddr, valAddr)
	if !found {
		return nil, types.ErrNoUnbondingDelegation
	}

	bondDenom := k.GetParams(ctx).BondDenom
	balances := sdk.NewCoins()
	ctxTime := ctx.BlockHeader().Time

	delegatorAddress, err := sdk.AccAddressFromBech32(ubd.DelegatorAddress)
	if err != nil {
		return nil, err
	}

	// loop through all the entries and complete unbonding mature entries
	for i := 0; i < len(ubd.Entries); i++ {
		entry := ubd.Entries[i]
		if entry.IsMature(ctxTime) {
			ubd.RemoveEntry(int64(i))
			i--

			// track undelegation only when remaining or truncated shares are non-zero
			if !entry.Balance.IsZero() {
				amt := sdk.NewCoin(bondDenom, entry.Balance)
				if err := k.bankKeeper.UndelegateCoinsFromModuleToAccount(
					ctx, types.NotBondedPoolName, delegatorAddress, sdk.NewCoins(amt),
				); err != nil {
					return nil, err
				}

				balances = balances.Add(amt)
			}
		}
	}

	// set the unbonding delegation or remove it if there are no more entries
	if len(ubd.Entries) == 0 {
		k.RemoveUnbondingDelegation(ctx, ubd)
	} else {
		k.SetUnbondingDelegation(ctx, ubd)
	}

	return balances, nil
}

## Dual Address Model

Every account can have both a Sei (bech32) address and an EVM (hex) address. The module maintains a bidirectional mapping between them.

- **Explicit association** — users can link their addresses via an Associate transaction or by signing any Cosmos/EVM transaction (the EVM address is derived from their secp256k1 public key).
- **Default (cast) addresses** — when no explicit association exists, the module falls back to a deterministic byte-cast. Cast addresses have limitations on receiving funds compared to fully associated addresses.

- **Why** - cast addresses will result in two views of the same account (e.g. two balances, etc.)
