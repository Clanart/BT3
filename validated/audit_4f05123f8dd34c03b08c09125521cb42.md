### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s, and the spend pipeline never checks maturity - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external finding describes a value leak: a contract designed to receive an asset class (ERC1155) provides a withdrawal path (`rageQuit`) that only handles a subset of the assets it accepts (ETH/ERC20), so received funds become stranded. The Serai analog: `Scanner::scan_block` reports every output paying to a registered script - including outputs of the block's coinbase transaction, which are consensus-unspendable for 100 blocks - as ordinary `ReceivedOutput`s. The spending path (`SignableTransaction::new` / `TransactionMachine`) contains no maturity check, so the wallet reports funds as received that cannot actually be spent, and can build/sign transactions that Bitcoin consensus rejects.

### Finding Description
`Scanner::scan_block` iterates `block.txdata` including `txdata[0]` (the coinbase) and returns matching outputs as `ReceivedOutput`s [1](#0-0) . `scan_transaction` matches purely on `script_pubkey` and attaches only `offset`, `output`, and `outpoint` - there is no field or flag distinguishing a coinbase output [2](#0-1) . `ReceivedOutput` exposes only `offset()`, `output()`, `outpoint()`, `value()` - a consumer cannot even determine from the API that the output is maturity-bound [3](#0-2) .

`SignableTransaction::new` accepts any `Vec<ReceivedOutput>` and builds tx inputs unconditionally; nothing checks coinbase maturity [4](#0-3) . `multisig` only verifies the script matches the offset key, then produces a FROST signing machine that will generate a valid BIP-340 signature over a transaction consensus will reject [5](#0-4) .

The doc comment on `scan_block` acknowledges the issue ("If received outputs must be immediately spendable, a post-processing pass is needed"), but the suggested remediation is not implementable through the API: a `ReceivedOutput` carries no coinbase flag, and a txid alone does not reveal that its transaction is a coinbase (only its null-prevout input does, which requires re-fetching the tx). The processor-side caller independently skips the coinbase via `txdata[1 ..]` [6](#0-5) , confirming the default `scan_block` behavior is dangerous.

### Impact Explanation
Funds sent to a registered script via a coinbase output (any miner can do this - coinbase outputs pay arbitrary `script_pubkey`s) are reported by the scanner as received and spendable. A consumer that feeds them to `SignableTransaction` gets a fully signed transaction that every node rejects (BIP-30/BIP-34 coinbase maturity), burning signing rounds and producing stuck funds the wallet has already accounted as spendable balance. This is exactly the "funds reported received that are not spendable" impact class: the receive path accepts an asset/spend-type the spend path silently cannot execute.

### Likelihood Explanation
Low-to-moderate attacker reachability: it requires a miner to direct coinbase rewards to the target's P2TR script, which costs the miner nothing beyond choosing the payout script. Any miner can grief the wallet; accidental occurrence is unlikely since normal wallets don't pay to random scripts in coinbases.

### Recommendation
- In `scan_block`, skip `block.txdata[0]` (or skip any tx whose first input has a null previous outpoint) so immature coinbase outputs are never reported.
- Alternatively, add an `is_coinbase`/maturity field to `ReceivedOutput` and have `SignableTransaction::new` reject (or gate on confirmation depth) coinbase inputs, so the spend path cannot consume them.

### Proof of Concept
1. `let mut scanner = Scanner::new(group_key).unwrap();` then `scanner.register_offset(...)` for any desired scripts.
2. A miner mines a block whose coinbase contains `TxOut { value: X, script_pubkey: p2tr_script_buf(group_key).unwrap() }`.
3. `scanner.scan_block(&block)` returns a `ReceivedOutput` for it.
4. `SignableTransaction::new(vec![that_output], &payments, change, None, fee)` succeeds; `multisig(&keys)` produces machines; `preprocess`/`sign`/`complete` yield a signed `Transaction`.
5. Broadcasting fails: the input's `previous_output` is a coinbase outpoint < 100 blocks deep - `bad-txns-premature-spend-of-coinbase`. The scanner nonetheless reported the funds as spendable balance.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
