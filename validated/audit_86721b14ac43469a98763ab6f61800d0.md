### Title
`_fetchRefspec` bypasses the `isPushPullFetchInProgress` mutual-exclusion guard, allowing a concurrent git fetch/push/pull race that can silently corrupt refs - ([File: app/src/lib/stores/app-store.ts])

### Summary
GitHub Desktop serializes all network git operations (`push`, `pull`, `fetch`) through a single mutual-exclusion guard, `withPushPullFetch`, which checks/sets `state.isPushPullFetchInProgress` before invoking git. However, `_fetchRefspec` — the code path used when a user views a pull request from a fork — explicitly does **not** go through this guard, by design, per its own doc comment. This mirrors the reported bug class: one operation (`op::close`) trusted an invariant of exclusivity that another operation (`op::start_balance_sync`) was allowed to violate, causing a silent, unrecoverable state corruption.

### Finding Description
`withPushPullFetch` is the single choke point Desktop uses to prevent two git network operations from touching the same repository concurrently: [1](#0-0) 

Every other network entry point (`_pull`, `_push`, `_fetch`) is routed through it. `_fetchRefspec`, however, is explicitly exempted, with a comment acknowledging the tradeoff: [2](#0-1) 

`_fetchRefspec` is invoked when the user browses to a pull request originating from a fork (an attacker-controlled `GitHubRepository`/PR object) — Desktop fetches the PR's head ref directly into the local repo so the diff/checks can be shown. Because this fetch runs a real `git fetch` subprocess against the repository's `.git` directory without checking or setting `isPushPullFetchInProgress`, it can execute at the same time as a user-initiated `pull`/`push`/`fetch`, which *do* check the flag but have no way of knowing an unguarded fetch is already touching the same on-disk git state.

Concurrent `git fetch`/`push`/`pull` invocations against the same repository race on shared git internals — `FETCH_HEAD`, `packed-refs`, loose object writes, and `index.lock`/`ORIG_HEAD` — which are not designed to be safely mutated by two processes at once. The result can be a lock contention failure that aborts one operation partway (e.g., a push updates the remote but the local ref update is skipped or interleaved with the fork fetch's ref writes), silently desynchronizing the local branch/tracking ref from what was actually pushed or pulled.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." An attacker who authors a fork/PR that a victim views in Desktop can reliably trigger the unguarded `_fetchRefspec` git subprocess at a time of their choosing (repeated PR views/refreshes), increasing the odds of it landing in the same window as the victim's own push/pull. If the git ref/lock race manifests, the user's local repository state (branch ref, tracking info, or FETCH_HEAD) can end up corrupted or desynced from what was intended to be committed/pushed, without any error surfaced to the user, since Desktop's own concurrency guard reports no conflict for the guarded operation.

### Likelihood Explanation
Likelihood is limited by timing: the attacker doesn't control exactly when the victim pulls/pushes, only that viewing a PR from their fork will unconditionally start an unguarded fetch. This is a much narrower race window than the jetton contract's original bug (where the attacker could poll a public operation every block), so this should be treated as a lower-probability but concretely reachable analog, not a guaranteed corruption on every occurrence. I was not able to fully trace how dugite/git itself behaves under such concurrent invocation (e.g., whether git's own locking would simply cause one operation to fail loudly rather than corrupt state silently) — this would need to be verified in a live Desktop session to confirm the exact failure mode.

### Recommendation
- Short term: route `_fetchRefspec` through `withPushPullFetch` (or a dedicated, but still mutually-exclusive, lock) so it cannot run concurrently with `_pull`/`_push`/`_fetch`; if it must remain non-blocking for UX reasons, queue it behind any in-flight network operation instead of skipping the check entirely.
- Long term: audit all git subprocess call sites in `app-store.ts`/`git-store.ts` for whether they respect `isPushPullFetchInProgress`, and add a regression test asserting that no git-mutating call path bypasses this guard, mirroring the report's recommendation to track and test previously-identified race conditions so they aren't reintroduced.

### Proof of Concept
1. Attacker opens a PR from a fork against a repository the victim has cloned in GitHub Desktop.
2. Victim opens the PR view in Desktop, which triggers `_fetchRefspec(repository, 'refs/pull/<n>/head')` — an unguarded `git fetch` subprocess (`app/src/lib/stores/app-store.ts:5875-5885`).
3. Concurrently (e.g., the victim clicks "Pull" or Desktop's background fetch timer fires a push), Desktop calls `withPushPullFetch`, which only checks its own in-memory `isPushPullFetchInProgress` flag (`app/src/lib/stores/app-store.ts:5427-5450`) — it has no knowledge of the fetch already in flight from step 2.
4. Two `git` subprocesses now mutate the same `.git` directory concurrently; depending on timing, ref/lock writes can interleave, leaving the local branch ref, `FETCH_HEAD`, or tracking state inconsistent with what the user believes they just committed/pulled/pushed. [2](#0-1) [1](#0-0)

  private async withPushPullFetch(
    repository: Repository,
    fn: () => Promise<void>
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    // Don't allow concurrent network operations.
    if (state.isPushPullFetchInProgress) {
      return
    }

    this.repositoryStateCache.update(repository, () => ({
      isPushPullFetchInProgress: true,
    }))
    this.emitUpdate()

    try {
      await fn()
    } finally {
      this.repositoryStateCache.update(repository, () => ({
        isPushPullFetchInProgress: false,
      }))
      this.emitUpdate()
    }
  }

   * Fetch a specific refspec for the repository.
   *
   * As this action is required to complete when viewing a Pull Request from
   * a fork, it does not opt-in to checks that prevent multiple concurrent
   * network actions. This might require some rework in the future to chain
   * these actions.

   */
  public async _fetchRefspec(
    repository: Repository,
    refspec: string
  ): Promise<void> {
    return this.withRefreshedGitHubRepository(repository, async repository => {
      const gitStore = this.gitStoreCache.get(repository)
      await gitStore.fetchRefspec(refspec)

      return this._refreshRepository(repository)
    })
