### Title
Duplicate DKG encryption-key registration panics the participant via `assert!` in `Decryption::register` - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::register` / `Encryption::register` in the PedPoP DKG crate enforces "one encryption key per participant" with a hard `assert!` rather than a recoverable error. Any peer who can cause a second `EncryptionKeyMessage` to be processed for the same `Participant` index crashes the victim's DKG session with a panic — a remotely triggerable denial of service reachable purely from attacker-controlled protocol messages, analogous to the crash/hang class of CVE-2019-2694.

### Finding Description
During PedPoP key generation, every participant broadcasts an `EncryptionKeyMessage` carrying their per-participant ECDH public key (`enc_key`). The receiving side inserts each sender's key into a `HashMap<Participant, C::G>` in `Decryption::register`, which guards re-registration with a process-killing assertion rather than an error return:

```rust
// crypto/dkg/pedpop/src/encryption.rs:351-362
pub(crate) fn register<M: Message>(
  &mut self,
  participant: Participant,
  msg: EncryptionKeyMessage<C, M>,
) -> M {
  assert!(
    !self.enc_keys.contains_key(&participant),
    "Re-registering encryption key for a participant"
  );
  self.enc_keys.insert(participant, msg.enc_key);
  msg.msg
}
```

`EncryptionKeyMessage` is deserialized from untrusted bytes via `EncryptionKeyMessage::read` (`encryption.rs:57-59`, reading an arbitrary `M` plus a `C::read_G` point). The `Participant` key for the map entry is attacker-selected within the protocol's authenticated-channel model: PedPoP assumes an authenticated channel for *origin* of a message, but nothing cryptographically binds a sender to exactly one registration message per session. A malicious participant — or any party able to cause the victim to feed a second registration for the same index (e.g., replaying the same broadcast, delivering a stale message after a retry, or exploiting a protocol path where `register` is invoked per message rather than per deduplicated set) — reaches the `assert!` and aborts the process.

A related panic exists in the same file's blame path: `decrypt_with_proof` indexes `self.enc_keys[&decryptor]` (`encryption.rs:388`), which panics on a missing entry rather than returning `DecryptionError`, and `Encryption::encrypt` does `self.decryption.enc_keys[&participant]` (`encryption.rs:466`).

### Impact Explanation
An unprivileged DKG participant can crash every honest peer's PedPoP session (and the surrounding process — panic unwinds or aborts depending on build), permanently stalling distributed key generation and any downstream multisig/FROST operations that depend on it. This matches the CVE class precisely: low-privilege, network-reachable input causing a hang or repeatable crash. In a validator/coordinator context, crashing honest participants during the DKG can also reduce the effective threshold of who must remain online to complete (or block) a ceremony, and repeated triggering makes the protocol unable to ever produce keys while the attacker is present — a stronger impact than a single-session failure.

### Likelihood Explanation
Likelihood hinges on whether the caller deduplicates `EncryptionKeyMessage`s per `Participant` before invoking `register` — I could not fully confirm the `HashMap`-level dedup behavior in `pedpop/src/lib.rs` within available inspection. However: (a) the author clearly anticipated re-registration occurring, since they wrote an explicit assertion for it rather than letting `HashMap::insert` silently overwrite; (b) the DKG operates over an "assumed-to-exist external authenticated channel" (comment at `encryption.rs:300-301`), which authenticates origin but does not guarantee at-most-once delivery — replays, retries, and retransmissions are all consistent with that model; (c) any integrator iterating received messages and calling `register` per message hits the panic on the second message for one sender. No cryptographic work, key knowledge, or threshold collusion is required — just delivery of a second attacker-chosen message under the same participant index.

### Recommendation
Replace the `assert!` in `Decryption::register` with a recoverable error (e.g., return `Result<M, DecryptionError>` or a new `DkgError::DuplicatedParticipant`-style variant) and propagate it to the PedPoP caller so a duplicate registration rejects the message/session gracefully instead of aborting. Apply the same treatment to the unchecked `HashMap` indexing in `decrypt_with_proof` (`encryption.rs:388`) and `Encryption::encrypt` (`encryption.rs:466`) — use `.get()`/`.ok_or(...)` and surface errors rather than panicking on attacker-influenced map state. Serai's own stated invariant ("this library is expected not to panic", `crypto/frost/src/curve/mod.rs:88`) supports making all of these error-returning.
