### Title
Scanner reports uneconomical/zero-value outputs as received; SignableTransaction spends them at a net loss - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary

The external finding describes a mandatory "security deposit" that is locked/spent while providing no benefit — a pure loss of the caller's funds. The Serai analog lives in `bitcoin-serai`'s wallet pipeline: `Scanner::scan_transaction` reports every output paying to a registered script as a spendable `ReceivedOutput` with no minimum-value check, and `SignableTransaction::new` checks only that *payments* are ≥ `DUST` (546 sats) — never that *inputs* are. An unprivileged third party can send dust (or, in a crafted nonstandard tx, zero-value) outputs to the multisig's Taproot address; the wallet reports them as received funds, and any spend that includes them pays more in added fee weight than the input contributes — funds burned for nothing, exactly like the lost `msg.value`.

### Finding Description

`Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`) matches outputs solely on `output.script_pubkey` and pushes a `ReceivedOutput` regardless of `output.value`. `scan_block` (`mod.rs:221-227`) does the same across all transactions.

`SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`):

- `DUST` is defined (line 32) and enforced only on *payments*: `for (_, amount) in payments { if *amount < DUST { Err(DustPayment) } }` (lines 165-169).
- Inputs are summed unconditionally: `let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum()` (line 175), and each input adds a full `TxIn` weight in `calculate_weight_vbytes` (a Taproot input costs ~58 vbytes plus share of base weight — roughly 57–68 vbytes of fee).

So an input of value `v` is only worth including if `v > fee_per_vbyte * ~68`. For typical fee rates, any input below a few hundred sats — and every output below `DUST` — is a net loss: the processor's other (legitimate) inputs subsidize spending an output worth less than the fee it adds. At `v = 0`..`546`, the marginal contribution is negative; the transaction still succeeds because `input_sat >= payment_sat + needed_fee` is checked on the *sum*, masking the loss.

### Impact Explanation

An unprivileged attacker who knows the multisig's script_pubkey (public on-chain once used, or computable via `register_offset`/`p2tr_script_buf` which take only the public `ProjectivePoint`) can send dust outputs to it. The scanner credits them as received balance, and any spend built from them destroys value equal to `(added fee) − (input value)` per dust input. This is "funds reported received that are not spendable economically," and a direct loss of the multisig's funds to miners — the same bug class as a deposit taken that buys nothing.

### Likelihood Explanation

Anyone can create dust outputs to a known address at trivial cost (the dust itself, ~546 sats max). Whether the loss is realized depends on the integrator/scheduler including dust inputs in `SignableTransaction::new` inputs — but nothing in the crate warns, filters, or exposes a minimum-value API; `ReceivedOutput::value()` exists yet is never compared against a spendability threshold. Dust-spamming known addresses is a routine, cheap occurrence on Bitcoin.

### Recommendation

- In `Scanner` or at `SignableTransaction::new` time, drop/filter inputs whose value cannot cover their marginal fee (`value <= fee_per_vbyte * marginal_input_vbytes`), or at minimum reject inputs `< DUST` symmetric to the payment check.
- Document and/or expose a helper so callers can compute the marginal cost per input, mirroring `calculate_weight_vbytes`.

### Proof of Concept

```rust
// Attacker sends a 546-sat (or smaller, nonstandard) output to the multisig script.
// Processor side:
let mut scanner = Scanner::new(group_key).unwrap();
let received = scanner.scan_transaction(&attacker_tx); // dust output returned as ReceivedOutput
assert_eq!(received[0].value(), 100); // e.g. 100 sats, below DUST

// Later, the processor includes it while spending a legitimate UTXO:
let fee_per_vbyte = 10;
// Marginal cost of this input ≈ 68 vB * 10 = 680 sats > 100 sats contributed.
let stx = SignableTransaction::new(
  vec![legit_utxo, received[0].clone()],
  &payments,
  Some(change_script),
  None,
  fee_per_vbyte,
).unwrap();
// stx.fee() includes ~680 sats to spend a 100-sat input => ~580 sats burned for nothing.
```

The check at `send.rs:165-169` guards payments only; nothing rejects the dust input at `send.rs:175-185`, so the loss is silently folded into `sum(inputs) - sum(outputs)`.
