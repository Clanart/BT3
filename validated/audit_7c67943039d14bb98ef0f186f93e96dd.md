## Title
Shell command injection via unsanitized repository path in Cygwin launch - (File: `app/src/lib/shells/win32.ts`)

## Summary
`Win32.launch()`'s `Shell.Cygwin` case builds a `/bin/sh -lc '...'` command line by directly string-interpolating the repository's local filesystem path into a single-quoted, then double-quoted shell script, with no escaping of shell metacharacters. A repository whose local path contains a single quote (`'`) or a command-substitution sequence (`$( ... )`) — both legal in Windows/NTFS filenames — breaks out of the intended quoting and results in arbitrary command execution in the spawned Cygwin `sh`/`bash` process when the user selects "Open in Cygwin" for that repository.

## Finding Description
The Cygwin launch case is: [1](#0-0) 

```
case Shell.Cygwin:
  const cygwinPath = `"${foundShell.path}"`
  return spawn(
    cygwinPath,
    [`/bin/sh -lc 'cd "$(cygpath "${path}")"; exec bash'`],
    { shell: true, cwd: path }
  )
```

`path` (the repository's local directory) is spliced directly into the shell script with no escaping. Contrast this with the hooks-environment code path, which has a dedicated `bashEscape` helper that properly wraps and escapes single quotes for POSIX shells: [2](#0-1) 

No equivalent escaping is applied in `win32.ts`'s `launch()` for `Shell.Cygwin` (or `Shell.GitBash`, which has the same class of bug via `--cd="${path}"`).

An attacker can control the resulting repository path by controlling the repository *name* used to derive the local clone folder for non-GitHub ("generic") clone URLs. `parseRemote`/`parseRepositoryIdentifier` extract the repo `name` component from an arbitrary git URL using permissive regexes (`[^/]+`), which do not restrict shell-special characters: [3](#0-2) 

That name is passed through `sanitizeCloneName`, which only strips path separators/traversal segments and a trailing `.git`; it does not filter `'`, `$`, `(`, `)`, or other shell metacharacters: [4](#0-3) 

The sanitized name is then joined into the on-disk clone path via `Path.join` in the clone dialog: [5](#0-4) 

Since Windows/NTFS filenames forbid only `<>:"/\|?*`, characters like `'`, `$`, `(`, `)` are all valid in a folder name, so an attacker-supplied malicious clone URL (e.g., pointing at an attacker-controlled generic git host, or a crafted deep link that pre-fills the clone URL) can cause the victim's local clone directory to contain these characters.

Later, opening that repository's shell as Cygwin calls `_openShell(path)` → `launchShell` → `Win32.launch`: [6](#0-5) [7](#0-6) 

The unsanitized `path` is embedded into the Cygwin `sh -lc '...'` argument at that point.

**Exact wrong value:** the `path` argument interpolated at `app/src/lib/shells/win32.ts:537` is not escaped/quoted for POSIX-shell metacharacters before being embedded in the single-quoted `sh -lc` script, unlike the equivalent hooks logic in `app/src/lib/hooks/shell-escape.ts`.

## Impact Explanation
If the interpolated path contains a single quote, it terminates the outer `'...'` argument to `sh -lc`, and the remaining path bytes are interpreted as raw shell script — arbitrary command execution. If the path instead contains `$(...)`, it lands inside the nested double-quoted `cygpath "..."` command substitution, which does not suppress further command substitution — bash will still execute `$(...)` embedded in the path before calling `cygpath`, again yielding arbitrary command execution. This gives code execution on the victim's machine under the user's privileges, satisfying the program's "code execution" impact category, triggered purely by the victim opening a shell on a repository whose location/name was influenced by attacker-controlled remote/API data.

## Likelihood Explanation
Exploitation requires: (1) the victim clones a repository from an attacker-influenced source where the local folder name inherits attacker-chosen characters (feasible via a crafted "generic" clone URL / deep link that isn't restricted to GitHub.com naming rules), and (2) the victim has Cygwin installed and explicitly chooses "Open in Cygwin" for that repository. This is a real but non-default action requiring specific victim behavior (must have Cygwin installed and manually pick it), and requires the attacker to get their crafted URL in front of the user (e.g., via a clone deep link or a shared generic-URL clone). Likelihood is moderate-low but the path is genuinely reachable without any existing guard rejecting it — `sanitizeCloneName` explicitly only guards against directory traversal, not shell metacharacters.

## Recommendation
Apply proper POSIX shell escaping (equivalent to `bashEscape`/`shQuoteCommand` in `app/src/lib/hooks/shell-escape.ts`) to the repository path before interpolating it into the `Shell.Cygwin` (and `Shell.GitBash`) command strings in `app/src/lib/shells/win32.ts`, rather than naively wrapping in double quotes. Alternatively, pass the path via an environment variable or a separate `argv` element that Cygwin's `sh` receives without going through shell re-parsing.

## Proof of Concept
1. Craft a generic (non-GitHub) clone URL whose final path segment, once parsed by `parseRemote`, yields a name containing shell metacharacters usable on Windows filenames, e.g. `https://attacker.example/owner/x'; calc.exe #.git` — after `sanitizeCloneName` this can still retain the embedded `'` and text.
2. Have the victim clone this URL via GitHub Desktop's "Clone repository" → "URL" tab, producing a local folder such as `C:\Users\victim\Documents\GitHub\x'; calc.exe #`.
3. Victim right-clicks the repository and selects "Open in Cygwin".
4. `win32.ts` builds: `/bin/sh -lc 'cd "$(cygpath "C:\Users\victim\Documents\GitHub\x'; calc.exe #")"; exec bash'`. The embedded `'` terminates the intended single-quoted script early, and `calc.exe` (or any attacker command) executes in the shell context spawned by GitHub Desktop.

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}

/** Launch the given shell at the path. */
export async function launchShell(
  shell: AnyFoundShell,
  path: string,
  onError: (error: Error) => void
): Promise<void> {
  // We have to manually cast the wider `Shell` type into the platform-specific
  // type. This is less than ideal, but maybe the best we can do without
  // platform-specific build targets.
  const exists = await pathExists(shell.path)
  if (!exists) {
    const label = __DARWIN__ ? 'Settings' : 'Options'
    throw new ShellError(
      `Could not find executable for '${shell.shell}' at path '${shell.path}'.  Please open ${label} and select an available shell.`
    )
  }

  let cp: ChildProcess | null = null

  if (__DARWIN__) {
    cp = Darwin.launch(shell as FoundShell<Darwin.Shell>, path)
  } else if (__WIN32__) {
    cp = Win32.launch(shell as FoundShell<Win32.Shell>, path)
  } else if (__LINUX__) {
    cp = Linux.launch(shell as FoundShell<Linux.Shell>, path)
  }
