### Title
Pathspec-magic injection via attacker-controlled filenames converts scoped `git diff` into an unrestricted diff - (File: `plugins/security-guidance/hooks/gitutil.py`)

### Summary
`_diff_pathspec` (called from `get_git_diff`) turns repo-relative filenames straight into `git diff -- <pathspec>` arguments with no escaping of git's pathspec "magic" syntax. A file whose real name begins with `:` (e.g. `:(exclude)…`, `:!…`, `:(glob)…`) — trivially plantable by anyone who controls repo content the agent later touches — is parsed by git as a pathspec *directive*, not a literal filename, which can convert what is supposed to be a single-file-restricted diff into git's "match everything except X" behavior, i.e. an unrestricted diff.

### Finding Description
`get_git_diff` (`plugins/security-guidance/hooks/gitutil.py:391-427`) restricts the diff to the caller-supplied `paths` via `_diff_pathspec` (`gitutil.py:70-88`), which builds the pathspec list purely from `os.path.relpath(os.path.realpath(p), cwd_abs)` with no sanitization, and appends it after `--` to the `git diff` argv (`gitutil.py:414`).

These `paths` originate from `compute_v2_review_set` in `diffstate.py:353-438`, which derives filenames from `git status --porcelain=v1 -z` / `git diff --name-only -z` (`_git_status_porcelain`, `_git_name_only`) run with `-c core.quotePath=false`. That flag, combined with `-z`, deliberately preserves filenames byte-for-byte, including leading `:`/`!` characters and unicode — this is called out in the code comments as intentional (`gitutil.py:307-308`, `diffstate.py:330-331`).

The `--` argument only stops *option* parsing in git's argv, it does not disable pathspec *magic* parsing of the string itself. A pathspec beginning with `:` is interpreted using short/long magic signatures (`:(exclude)…`, `:!pattern`, `:(glob)…`, `:(icase)…`, etc.). Critically, when the *only* pathspec supplied is a negative one (`:!foo` / `:(exclude)foo`), git implicitly treats it as "match everything except foo" rather than "match nothing except an empty positive set." So if an attacker gets a file into the repo whose literal name is, say, `:!nonexistent`, and that file (or any file in the same dirty/untracked set) ends up in `review_set`/`paths`, the resulting `git diff -- ":!nonexistent"` returns the diff of the **entire working tree**, not just the intended file.

The code explicitly documents that an unrestricted diff is exactly the failure mode it is trying to prevent:
```
if paths and not pathspec:
    # ... an empty pathspec would mean an UNRESTRICTED diff — the bug this whole
    # change exists to fix.
    return ""
```
(`gitutil.py:406-412`) — but this guard only checks for the *empty-list* case; it does nothing to stop a non-empty pathspec whose *content* is itself magic and semantically unrestricted.

None of `_diff_pathspec`, `get_git_diff`, `_git_status_porcelain`, or `GIT_CMD` set `git -c core.literalPathspecs=true` or prefix entries with `:(literal)`, so there is no defense against this.

### Impact Explanation
This breaks the stated invariant ("git path scoping must never escape the intended repo target"): the diff sent onward for LLM security review (`review_api.py`) can silently expand to the whole working tree instead of the touched file(s). This can pull unrelated, sensitive in-repo content (other users' WIP diffs, secrets/config accidentally left dirty in the tree, tokens, etc.) into the payload sent to the review pipeline (a local or remote LLM sink), i.e. sensitive diff/code disclosure to an unintended sink — matching the "Sensitive code, prompt, token, diff, or local file disclosure" impact category. It does not escape the git repository boundary itself (realpath/relpath rejection in `_diff_pathspec` still blocks true out-of-repo paths), so the blast radius is confined to the repo's working tree, not arbitrary filesystem read.

### Likelihood Explanation
Feasible and repeatable: the attacker only needs to get a colon-prefixed filename into a repository that Claude Code will operate on (e.g., in a cloned/forked repo, a PR branch, or content introduced by the agent while acting on attacker-influenced instructions) and have it show up as dirty/untracked/changed alongside the file the review was meant to be scoped to. `core.quotePath=false -z` guarantees the name reaches `get_git_diff` unmangled. No special privilege is required beyond ordinary repo-content control, matching the described unprivileged attacker model.

### Recommendation
Neutralize pathspec magic before use:
- Add `-c core.literalPathspecs=true` to `GIT_CMD` (or specifically to the `git diff`/`git diff --name-only` invocations), forcing all pathspec arguments to be treated as literal paths, or
- Prefix every computed pathspec entry with the `:(literal)` magic signature in `_diff_pathspec` (e.g. `rel.append(":(literal)" + r)`), and audit `_git_name_only`/`_git_status_porcelain` outputs for the same treatment wherever they're later re-fed into another `git … -- <path>` call.

### Proof of Concept
Integration test plan:
1. In a temp git repo, create and commit a normal file `a.py`.
2. Create a second file literally named `:!a.py` (or `:(exclude)a.py`) with sensitive content, and leave it untracked/dirty alongside a real edit to `a.py`.
3. Call `compute_v2_review_set(cwd, baseline_sha, head_at_capture)` to get `review_paths` including both files, then call `get_git_diff(cwd, baseline_sha, paths=review_paths)`.
4. Assert (expected/fixed behavior): the returned diff text contains **only** the hunk for `a.py` and does not contain unrelated files that exist in the tree outside `review_paths`.
5. Current/vulnerable behavior: because `:!a.py` is treated as pathspec magic, `git diff` is invoked with an effectively "exclude a.py" pathspec, causing the diff to include the full working tree diff (including files never intended to be reviewed), demonstrating the pathspec-scope escape.
