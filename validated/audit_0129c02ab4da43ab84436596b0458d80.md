### Title
FROST preprocess seed reused via `CachedPreprocesses` keyed only on `(context)` — same nonces used to sign distinct messages, leaking the validator's secret share — (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` deterministically regenerates FROST nonces from a 32-byte seed stored in `CachedPreprocesses` keyed solely by `self.context` (`(b"DkgConfirmer", attempt)` for `DkgConfirmer`). The seed is never deleted or rotated after use: every call to `share_internal` → `preprocess_internal` → `AlgorithmSignMachine::from_cache` → `seeded_preprocess` re-derives identical nonces `d, e` from `ChaCha20Rng::from_seed(*seed.0)` (`crypto/frost/src/sign.rs:127-145`). The cache key binds the nonce to the *attempt number* but not to the participant set, the `removed` list, or the message — i.e., the one-time secret is "freed" (consumed by `sign`) and then used again, the direct analog of a use-after-free.

### Finding Description
In `signing_protocol.rs:123-145`, the cache lookup is `CachedPreprocesses::get(self.txn, &self.context)` where `context = (b"DkgConfirmer", self.attempt)` (`signing_protocol.rs:275`). Nothing in the key distinguishes the validator set, `self.removed`, or the `key_pair` being confirmed. Both `DkgConfirmer::share` (line 304) and `DkgConfirmer::complete` (line 312) call `share_internal`, which calls `preprocess_internal`, which rebuilds the sign machine from the same stored seed — so `sign()` is re-executed with byte-identical `nonces`/`commitments` (`crypto/frost/src/sign.rs:141`).

Two reuse paths exist without requiring a BFT violation:

1. `DkgConfirmer::new`/`share_internal` compute the message as `set_keys_message(&self.spec.set(), &self.removed..., key_pair)` (lines 271, 296-301). `removed` comes from `removed_as_of_dkg_attempt` and `key_pair` is a call-time argument. If `share` and a later `complete` (or a second `share` under a different `removed`/`key_pair` resolution for the same attempt) sign different messages, the nonces are identical.
2. `attempt` is a `u32` scoped to a DKG protocol run. Across distinct validator sets (set rotations), the DB persists and the same `("DkgConfirmer", attempt)` key can regenerate the same seed while `participants` and the message differ.

FROST signature shares are of the form `s_i = d_i + ρ_i·e_i + λ_i·x_i·c`. Two shares produced with the same `d_i, e_i` and the same preprocess set but different messages yield `s_1 - s_2 = λ_i·x_i·(c_1 - c_2)`; challenges `c` are publicly computable, so the validator's weighted secret share `λ_i·x_i` (its MuSig secret share) is recovered in one subtraction.

### Impact Explanation
Recovery of the coordinator's MuSig secret share for the validator set. Since this MuSig signature is the on-chain confirmation mechanism for DKG results (the validators' root-of-trust keys), share recovery enables forging validator signatures on `set_keys_message` and any other message signed under that set — arbitrary key-set confirmations and potentially validator-key compromise. This is analogous to the CVE's heap corruption primitive: a consumed secret is used again, converting a one-time-use assumption into key disclosure.

### Likelihood Explanation
Reuse requires the coordinator to execute `share_internal` more than once under the same `(context)` key with differing signed data. `share` and `complete` are separate public entry points that each re-run the full sign; `complete` explicitly re-derives the machine ("trying to complete a machine which failed to preprocess", line 323). The header comment (lines 25-51) acknowledges nonce reuse is unsafe and argues safety solely from BFT message ordering — but the cache key does not include `key_pair`, `removed`, or `participants`, so any code path or retried/rebuilt attempt that reaches signing twice under the same `attempt` with different finalized data (e.g., a re-proposed `KeyPair` within the same attempt, or the same attempt index in a later set) reuses the nonce. Additionally, a partial DB rebuild that retains `CachedPreprocesses` but replays signing — the exact "partial rebuild" scenario the comment says is merely "accepted" — triggers it. Reachability depends on coordinator call sequencing which I could not fully trace (callers in `handle.rs`/`substrate/mod.rs` were identified but not read), so likelihood is moderate rather than confirmed-trivial.

### Recommendation
- Include the full signing context in the cache key: `participants` (or their hash), `removed`, and a hash of the message/key_pair, so distinct signing contexts can never collide on one seed.
- Delete or tombstone `CachedPreprocesses` entries after a share is produced, and return an error instead of re-signing when a tombstoned context is requested.
- Persist a record of the produced `preprocess`/`share` per context (the comment's TODO at lines 50-54) and refuse to sign if a new request would produce a share for a different message under the same commitments.

### Proof of Concept
Conceptual: invoke `DkgConfirmer::share(preprocesses, key_pair_A)` producing share `s_A` for `set_keys_message(.., key_pair_A)`, then `DkgConfirmer::complete(preprocesses, key_pair_B, shares)` — `complete` re-executes `share_internal` with `key_pair_B`, and `preprocess_internal` reloads the identical seed from `CachedPreprocesses` (context `("DkgConfirmer", attempt)` unchanged), producing share `s_B` under the same nonces. Given the same preprocess set (same `ρ`, same `λ`), `x_share = (s_A - s_B) / (c_A - c_B)` recovers the validator's MuSig secret share, where `c_A, c_B` are computed from the public signature transcript.
