### Title
Unisolated Context Used for `onPacketTimeout` EVM Callback Breaks Atomicity/Gas Isolation Guarantees - (File: x/ibc/callbacks/keeper/keeper.go)

### Summary
`IBCOnTimeoutPacketCallback` documents that it should execute the destination contract's `onPacketTimeout` call inside a cached/isolated context with an infinite gas meter capped at the user-supplied `CommitGasLimit`, then commit only on success — mirroring the pattern correctly used in the sibling function `IBCOnAcknowledgementPacketCallback`. However, the actual `CallEVM` invocation for the timeout path passes the *original* `ctx` instead of the prepared `cachedCtx`.

### Finding Description
In `x/ibc/callbacks/keeper/keeper.go`, both `IBCOnAcknowledgementPacketCallback` and `IBCOnTimeoutPacketCallback` build an isolated `cachedCtx` via `ctx.CacheContext()` combined with `evmante.BuildEvmExecutionCtx(cachedCtx).WithGasMeter(evmtypes.NewInfiniteGasMeterWithLimit(cbData.CommitGasLimit))`, explicitly to avoid depleting the real gas meter and to allow reverting the callback's side effects on failure [1](#0-0) .

The acknowledgement path correctly uses `cachedCtx` for the actual EVM call: [2](#0-1) 

But the timeout path calls `CallEVM` with `ctx` instead of `cachedCtx`: [3](#0-2) 

Because the contract call executes directly against the live `ctx` (real multistore, real block gas meter) rather than the cache, two invariants documented in the function's own comments are broken:
1. **Gas isolation** — the contract runs against the actual remaining block/tx gas meter instead of the isolated `CommitGasLimit`-bounded infinite meter, contradicting the explicit rationale given in the surrounding code ("Skipping this causes the EVM gas estimation function to deplete all Cosmos gas").
2. **Atomicity/rollback** — any state mutations performed by the callback contract during `onPacketTimeout` are committed directly to `ctx` as they happen. The subsequent `writeFn()` call operates on the untouched `cachedCtx` snapshot and is a no-op with respect to the real mutations, so there is no actual mechanism to revert the callback's effects if a later check (e.g., the `ctx.GasMeter().IsOutOfGas()` check at line 432-434) fails.

### Impact Explanation
An IBC packet sender fully controls the `src_callback.address` and `src_callback.gas_limit` fields in the transfer memo and can deploy an arbitrary contract implementing `onPacketTimeout`. Because that call executes on the live `ctx` gas meter (not the isolated infinite meter), a contract that intentionally consumes more gas than what happens to be remaining on the real context can trigger a Cosmos SDK gas-meter panic (`ErrorOutOfGas`) inside `CallEVM`/`ctx.GasMeter()` during core IBC packet-timeout processing — a path that is not wrapped in the precompile framework's own recover-based `HandleGasError` (that pattern only exists in `precompiles/common/precompile.go` for direct precompile calls, not for this keeper-level `CallEVM` invocation). If unrecovered, this becomes a deterministic panic hit identically by every honest validator processing the same IBC timeout packet, i.e., a chain-halt condition triggerable by an ordinary, unprivileged IBC packet sender through the standard timeout-callback flow. Separately, even absent a panic, the broken atomicity means a callback contract's state changes are not guaranteed to be rolled back consistently with the acknowledgement path, undermining the "isolated execution" security guarantee the module documents for source-chain callbacks.

### Likelihood Explanation
Triggering requires only sending a normal ICS-20 transfer with a `memo.src_callback` pointing to an attacker-deployed contract and then allowing/forcing the packet to time out (achievable unilaterally by a sender who controls both ends, or by simply not having a relayer deliver the packet within the timeout window). No privileged access, validator collusion, or governance action is required.

### Recommendation
In `IBCOnTimeoutPacketCallback`, replace the `ctx` argument passed to `k.evmKeeper.CallEVM(...)` with `cachedCtx` (matching `IBCOnAcknowledgementPacketCallback`), and only call `writeFn()` after all post-call checks (gas consumption, `IsOutOfGas`) succeed, so that a failing or gas-exhausting callback cannot mutate live chain state and is safely isolated behind the intended infinite/capped gas meter.

### Proof of Concept
Exact reproduction steps were not fully verified due to the exhaustion of the tool budget; verification of whether `CallEVM`/the underlying gas meter panics without a recoverable boundary in this specific keeper call path (`x/vm/keeper/call_evm.go`) should be confirmed with a running Devin session that can trace `CallEVM` and `x/vm/ante/ctx.go:BuildEvmExecutionCtx` fully, and construct an end-to-end IBC timeout test with a gas-griefing `onPacketTimeout` contract to confirm whether the result is a panic (chain-halt) or merely a silent atomicity break (state-consistency bug). This should be treated as a confirmed code defect (wrong context object used) with likely-but-unconfirmed critical severity pending that trace.
