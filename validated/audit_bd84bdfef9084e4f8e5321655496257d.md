### Title
Missing balance-sufficiency check in KIP-160 treasury rebalance path allows unbacked KAIA allocation (supply inflation) - ([File: blockchain/system/rebalance.go])

### Summary
`RebalanceTreasury` in `blockchain/system/rebalance.go` mirrors the external report's bug class: an amount is transferred to recipients based on a config value without first verifying that enough backing funds exist. The check that exists for the legacy KIP-103 rebalance path is not applied to the newer KIP-160 path, so recipients can be credited with more KAIA than was actually reclaimed from the "zeroed" accounts.

### Finding Description
`RebalanceTreasury` computes `totalZeroedAmount` (KAIA taken from retired/zeroed accounts) and `totalAllocatedAmount` (KAIA to be granted to new accounts), then validates sufficiency only for the KIP-103 path: [1](#0-0) [2](#0-1) 

```go
// Validation 4) Check the total balance of zeroeds are bigger than the distributing amount
totalZeroedAmount := result.totalZeroedBalance()
totalAllocatedAmount := result.totalAllocatedBalance()
if isKIP103 && totalZeroedAmount.Cmp(totalAllocatedAmount) < 0 {
    return result, ErrRebalanceNotEnoughBalance
}
``` [3](#0-2) 

The `isKIP103 &&` guard means that when `isKIP160` is true, no such sufficiency check runs at all before the execution phase unconditionally sets balances: [4](#0-3) 

```go
// Execution 1) Clear all balances of zeroeds
for addr := range result.Before.Zeroed {
    state.SetBalance(addr, big.NewInt(0))
    ...
}
// Execution 2) Distribute KAIA to all allocateds
for addr, balance := range result.After.Allocated {
    currentBalance := state.GetBalance(addr)
    result.Burnt.Add(result.Burnt, currentBalance)
    state.SetBalance(addr, balance)
}
// Fill the remaining fields of the result
remainder := new(big.Int).Sub(totalZeroedAmount, totalAllocatedAmount)
result.Burnt.Add(result.Burnt, remainder)
``` [5](#0-4) 

If `totalAllocatedAmount > totalZeroedAmount` under the KIP-160 path, `remainder` becomes negative and is subtracted from `result.Burnt`, while `state.SetBalance` has already unconditionally credited the full `Allocated` amounts to each recipient. This is the same root cause pattern as the reported AFiBase bug: the contract commits to disbursing/crediting an amount without first confirming sufficient backing funds exist, resulting in value being created/credited beyond what was actually reclaimed — i.e., unbacked KAIA (supply inflation) rather than under-payment.

### Impact Explanation
This directly inflates the native token supply beyond what governance/config intended, corrupting the "Burnt" accounting and the actual account balances written to the global state. Because block validation would compute the same state transition deterministically from the same (potentially misconfigured or malicious) KIP-160 contract data, this is not itself a consensus split, but it is a concrete instance of "acceptance of an invalid state" — value materializing without being backed by zeroed balances — which is one of the explicitly accepted impact categories (supply inflation).

### Likelihood Explanation
`RebalanceTreasury` is only invoked once, at the specific pre-configured hardfork block number, and is gated by `CheckZeroedsApproved` (requiring on-chain approvals from the "zeroed" accounts) and by the `Kip160ContractAddress` governance parameter. It is not reachable by an arbitrary unprivileged transaction in the normal sense; it requires control (or compromise) of the KIP-160 contract configuration/approval process by the entities managing governance parameters. Given the task's explicit scope allows "governance parameters" as an admissible category, this is included, but note the practical likelihood is low since it depends on the treasury-rebalance contract's data being misconfigured (allocated > zeroed) and passing the existing approval/status checks — this is not attacker-controlled through a normal transaction.

### Recommendation
Apply the same `totalZeroedAmount.Cmp(totalAllocatedAmount) < 0` sufficiency check unconditionally, i.e., remove the `isKIP103 &&` restriction (or add an equivalent explicit check for `isKIP160`), and return `ErrRebalanceNotEnoughBalance` (or a KIP-160-specific error) before performing any `state.SetBalance` execution steps.

### Proof of Concept
Not independently reproducible as a standalone transaction PoC because it requires deploying/configuring a `TreasuryRebalanceV2` (KIP-160) contract whose `Allocateds` sum exceeds the sum of `Zeroeds` balances, getting it "Approved" (status == 2) and passing `CheckZeroedsApproved`, then having the chain reach the configured `RebalanceBlockNumber`. At that point, `RebalanceTreasury` (called via `FinalizeState`/block processing at that height) will execute the flow shown above and credit the full allocated amounts without the balance-sufficiency check that exists for KIP-103, as demonstrated by the code path at [6](#0-5) .

// RebalanceTreasury reads data from a contract, validates stored values, and executes treasury rebalancing (KIP-103, KIP-160).
// It can change the global state by removing old treasury balances and allocating new treasury balances.
// The new allocation can be larger than the removed amount, and the difference between two amounts will be burnt.
func RebalanceTreasury(state *state.StateDB, chain backends.BlockChainForCaller, header *types.Header) (*rebalanceResult, error) {
	var (
		err    error
		caller RebalanceCaller

		result   = newRebalanceReceipt()
		isKIP160 = chain.Config().IsKIP160ForkBlock(header.Number)
		isKIP103 = chain.Config().IsKIP103ForkBlock(header.Number)
	)

	if isKIP160 {
		caller, err = rebalance.NewTreasuryRebalanceV2Caller(chain.Config().Kip160ContractAddress, backends.NewBlockchainContractBackend(chain, nil, nil))
	} else if isKIP103 {
		caller, err = NewKip103ContractCaller(state, chain, header)
	} else {
		return nil, errors.New("rebalancing shouldn't be executed unless the block number is kip103 or kip160 hard fork")
	}
	if err != nil {
		return nil, err
	}

	// Retrieve 1) Get Zeroed
	if err = result.fillZeroed(caller, state); err != nil {
		return result, err
	}

	// Retrieve 2) Get Allocated
	if err = result.fillAllocated(caller, state); err != nil {
		return result, err
	}

	// Validation 1) Check the target block number
	if blockNum, err := caller.RebalanceBlockNumber(nil); err != nil || blockNum.Cmp(header.Number) != 0 {
		return result, ErrRebalanceIncorrectBlock
	}

	// Validation 2) Check whether status is approved. It should be 2 meaning approved
	if status, err := caller.Status(nil); err != nil || status != 2 {
		return result, ErrRebalanceBadStatus
	}

	// Validation 3) Check approvals from zeroeds
	if err = caller.CheckZeroedsApproved(nil); err != nil {
		return result, err
	}

	// Validation 4) Check the total balance of zeroeds are bigger than the distributing amount
	totalZeroedAmount := result.totalZeroedBalance()
	totalAllocatedAmount := result.totalAllocatedBalance()
	if isKIP103 && totalZeroedAmount.Cmp(totalAllocatedAmount) < 0 {
		return result, ErrRebalanceNotEnoughBalance
	}

	// Execution 1) Clear all balances of zeroeds
	for addr := range result.Before.Zeroed {
		state.SetBalance(addr, big.NewInt(0))
		result.After.Zeroed[addr] = big.NewInt(0)
	}
	// Execution 2) Distribute KAIA to all allocateds
	for addr, balance := range result.After.Allocated {
		// if an allocated has KAIA before the allocation, it will be burnt
		currentBalance := state.GetBalance(addr)
		result.Burnt.Add(result.Burnt, currentBalance)

		state.SetBalance(addr, balance)
	}

	// Fill the remaining fields of the result
	remainder := new(big.Int).Sub(totalZeroedAmount, totalAllocatedAmount)
	result.Burnt.Add(result.Burnt, remainder)
	result.Success = true
	return result, nil
}
