### Title
`BlameMachine::blame_internal` panics on unauthenticated participant index (missing map entry) - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
Analogous to CVE-2018-21015's NULL-pointer dereference (`cfg` used without a presence check), PedPoP's blame evaluation indexes `self.commitments[&sender]` directly. `sender` (and `recipient`) are attacker-supplied `Participant` values passed straight through `BlameMachine::blame` / `AdditionalBlameMachine::blame` with no check that they correspond to a DKG participant. Any index outside `1..=n` — or for `AdditionalBlameMachine`, any sender whose commitment message was absent — causes a `HashMap` index panic, crashing the calling process instead of returning an error or blame verdict.

### Finding Description
In `blame_internal`, after decrypting the disputed share, the code evaluates the share-verification statements with:

```rust
&self.commitments[&sender]
``` [1](#0-0) 

`commitments` is populated only for `Participant(1)..=Participant(n)` — either via `verify_r1` (which inserts `self.params.i()` plus validated peers) or `AdditionalBlameMachine::new` (which inserts `1..=n`). Neither `BlameMachine::blame` nor `AdditionalBlameMachine::blame` validates `sender`/`recipient` before the index: [2](#0-1) [3](#0-2) 

The `blame` API explicitly accepts an *accusation* — i.e., data describing an untrusted claim — and is specified to always identify a faulty party, yet a malformed accusation aborts the process via panic rather than returning blame. Note `sender`/`recipient` here are free-function arguments; nothing constrains them to the participant set, and `Participant::new` only rejects zero, not `> n`.

A closely related instance exists in `GeneratorPromotion::complete`, which unwraps `proofs.get(&i)` for every `i` in `1..=n` after only checking `proofs.len() == n - 1` and `key <= n`. A proofs map containing the victim's own index `params.i()` (or any duplicate-attributed proof) satisfies both checks yet omits a required participant, panicking at the unwrap: [4](#0-3) 

### Impact Explanation
An unprivileged counterparty who can trigger a blame evaluation — e.g., by causing a `VerifyBlame`-style request to be built with an out-of-range `accuser`/`accused` `Participant`, or by submitting a promotion proof attributed to the wrong index — crashes the victim's key-management process during DKG blame/promotion handling. In a threshold-signing deployment this is a denial of service against a signer mid-protocol: the process aborts while handling malformed accusation data, exactly the "missing presence check on optional data → crash" shape of CVE-2018-21015 (there a NULL `cfg`, here a missing `HashMap`/`Option` entry). Since blame evaluation is invoked precisely when a participant is suspected of misbehavior, the crash hits at the moment the protocol is under adversarial input.

### Likelihood Explanation
Triggering requires only that an attacker influence the `sender`/`recipient` arguments or the proof map keys — public, attacker-influenced inputs by design (blame adjudicates accusations about third parties, and `GeneratorPromotion::complete` consumes proofs keyed by claimed `Participant`). No secret material, valid proof, or honest behavior from the attacker is needed; they only need their message routed to the blame/complete path, which is the documented mechanism for handling faulty parties. Medium likelihood in deployments that map wire-level participant fields directly into these calls.

### Recommendation
- In `blame_internal`, replace `self.commitments[&sender]` with a checked `get`, treating an unknown `sender`/`recipient` as blame on whichever party supplied the invalid index (or returning a dedicated `PedPoPError::InvalidParticipant`).
- In `GeneratorPromotion::complete`, verify the proof map's key set equals `all_participant_indexes() \ {params.i()}` (e.g., reuse `validate_map`) before indexing, and return `PromotionError::InvalidParticipant` instead of unwrapping.
- Audit all `HashMap` indexing and `unwrap` on attacker-influenced keys in `crypto/dkg/*` (`self.commitments[&l]` in `calculate_share` is safe today only because `validate_map` precedes it — keep that invariant explicit).
