### Title
Webhook HMAC verification does not bind payload to the `X-Shopify-Shop-Domain` header, enabling cross-shop webhook forgery/replay - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
The webhook verification concern authenticates the raw POST body via HMAC but never validates that the `X-Shopify-Shop-Domain` header actually corresponds to the shop that produced the signed body. Any actor who can obtain one validly-signed webhook payload (e.g. a merchant who has the app installed on their own store and can observe/replay their own webhook traffic) can resend the identical body+HMAC directly to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header, causing the app to process/enqueue the webhook as if it belonged to a different shop. This is the same root-cause pattern as the "wrong user charged" report: an identifier that is trusted for a security-relevant operation (`proposer`/here `shop_domain`) is never validated against the entity that the verified data (bond/HMAC) actually belongs to.

### Finding Description
`ShopifyApp::WebhookVerification#verify_request` computes/validates HMAC only over `request.raw_post`: [1](#0-0) 

`hmac_valid?` in `PayloadVerification` only checks the body (`data`) against the shared app secret — the shop-identifying header is not part of the signed material: [2](#0-1) 

The `shop_domain` helper that the app is expected to trust for tenant scoping is read verbatim from the unauthenticated header: [3](#0-2) 

The gem's own documentation instructs developers to build custom webhook controllers that pass this `shop_domain` value straight into background jobs for shop-scoped processing: [4](#0-3) 

Because the HMAC only proves "this body was signed with the app secret," and the app secret is shared across every shop that has the app installed, any installed merchant can capture one legitimate signed webhook (body + HMAC) and resend it to the public webhook endpoint with a modified `X-Shopify-Shop-Domain` header pointing at a victim shop. The verification step passes (body/HMAC untouched), yet the shop attribution used downstream is completely attacker-controlled — exactly analogous to the audit finding where the `proposer` field in a `Dispute` was trusted without validating it against the actual response's proposer, letting an unrelated party be charged.

### Impact Explanation
A malicious merchant (any shop with the app installed) can cause the app to process/enqueue webhook-driven jobs (e.g., cart/order/product update jobs, or any custom job built per the documented pattern) under an arbitrary victim shop's domain. Depending on what the app does with `shop_domain` (data writes, cache invalidation, billing-adjacent side effects, notifications, etc.), this enables cross-shop data corruption or actions being falsely attributed to another tenant — a direct cross-shop/cross-user integrity violation using an accepted forged signed request.

### Likelihood Explanation
Any shop with the app installed already possesses one validly HMAC-signed webhook body (received legitimately from Shopify), and the app's shared secret is identical for all installs of that app. No secret material needs to be leaked or brute-forced; only header manipulation on replay is required, which is straightforward with any HTTP client. This makes the analog realistically reachable from an "unrelated-merchant" perspective as required by scope.

### Recommendation
- **Short term**: Do not trust the `X-Shopify-Shop-Domain` header for tenant scoping. Instead, parse the shop identity from the verified webhook body itself, or cross-check the header against a shop identity embedded in/derived from the signed payload before using it to route data or jobs. Update `ShopifyApp::WebhookVerification#shop_domain` and the generator/docs examples to reflect this.
- **Long term**: Add regression tests that specifically exercise "valid HMAC signature, mismatched shop header" scenarios to ensure the verification logic (and any consuming app code following the documented pattern) rejects or safely ignores the untrusted header.

### Proof of Concept
1. Merchant M has the app installed on `m-shop.myshopify.com` and legitimately receives a Shopify webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid, computed by Shopify using the app's shared secret), header `X-Shopify-Shop-Domain: m-shop.myshopify.com`.
2. M sends a POST directly to the app's `/webhooks/:type` endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `verify_request` (`lib/shopify_app/controller_concerns/webhook_verification.rb:15-21`) validates `H` against `B` successfully since the header is not part of the signed data.
4. Any downstream code using `shop_domain` (per `docs/shopify_app/webhooks.md:86-104` pattern) enqueues/processes the job attributing the payload to `victim-shop.myshopify.com`, even though the payload actually originated from M's shop.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
