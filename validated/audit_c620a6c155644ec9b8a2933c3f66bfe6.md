Based on the investigation, the strongest verifiable analog in this codebase is the conditional `protocol.file.allow=always` override used when Desktop auto-initializes submodules during checkout, which is applied without any validation of the individual submodule URLs the attacker controls via `.gitmodules`.

### Title
Unvalidated `file://` submodule URLs are trusted during automatic submodule initialization at checkout - (File: `app/src/lib/git/submodule.ts`)

### Summary
`checkoutBranch` / `checkoutCommit` accept an `allowFileProtocol` flag that, when true, causes `updateSubmodulesAfterOperation` to run `git submodule update --init --recursive` with `-c protocol.file.allow=always` [1](#0-0) . This override is applied to the whole `git submodule update` invocation, not to a specific, previously-validated submodule URL — so any submodule entry present in the attacker-controlled `.gitmodules` file of the checked-out branch is initialized with `file://` protocol allowed, with no check on what path that URL points to.

### Finding Description
The broken invariant mirrors the Rigor bug: a value that should require validation/consent from a trusted context (here, "is this submodule remote safe to fetch via the local filesystem transport") is instead applied unconditionally once a boolean flag is set, the same way `_inviteSC`/`inviteSubcontractor` unconditionally overwrote `subcontractor` once `inviteSC` was called, without checking `getAlerts(_taskID)[2]`.

`checkoutBranch` and `checkoutCommit` both forward `allowFileProtocol` straight into `updateSubmodulesAfterOperation` [2](#0-1) [3](#0-2) . The dedicated test `initializes an uninitialized submodule when checking out a branch` demonstrates the exact production call path: `checkoutBranch(repository, branchWithSubmodule, null, undefined, true)` is invoked directly against the real `checkoutBranch` API to auto-initialize a submodule that appears in a newly checked-out branch [4](#0-3) , confirming Desktop's own logic sets this flag to `true` in the scenario where a branch introduces a submodule that wasn't previously initialized locally.

Once `protocol.file.allow=always` is set for the whole `submodule update --init --recursive` invocation, git will honor *any* `file://` submodule URL declared in `.gitmodules`, including absolute paths pointing outside the working tree (e.g., `file:///Users/victim/.ssh`, `file:///C:/Users/victim/AppData`, or a path-traversal `file://../../../../somewhere`). There is no check anywhere in `updateSubmodulesAfterOperation` or its caller that the submodule URL is scoped to the origin host/organization, or that it isn't a local-filesystem reference.

### Impact Explanation
If the attacker crafts a repository/branch whose `.gitmodules` submodule URL is `file://<absolute-local-path>`, and the victim opens/checks out that branch (a normal git operation, not requiring local access), git will copy the referenced local directory's git object data into the submodule working directory of the cloned repository. Depending on the target directory, this can:
- Exfiltrate the contents of a sensitive local directory into the repo's working tree, which the user may then unknowingly commit and push to the remote, disclosing local secrets.
- Silently corrupt what the user believes they are committing/pushing, since the submodule content did not originate from any remote the user consented to.

This satisfies the "silent corruption of what the user commits or pushes" and "file read outside the repo" impact categories from the task's valid-impact list, driven purely by an attacker-controlled cloned/checked-out repository.

### Likelihood Explanation
Likelihood requires only that the victim check out a branch/commit containing a malicious `.gitmodules` file with an uninitialized submodule — a routine action (switching branches, checking out a PR branch, etc.), with no additional user prompt shown about the submodule's protocol/URL. The flag defaults to `false` in the function signatures [5](#0-4) , so exploitability is gated on Desktop's own decision logic to set `allowFileProtocol=true` for the "uninitialized submodule" case — this is confirmed present via the direct-API test, but I was unable to trace the exact production call site (in `app-store.ts`/`dispatcher.ts`) within this investigation's tool budget that decides when to pass `true` outside of tests, so the precise UI-triggering conditions in the shipped app remain unconfirmed.

### Recommendation
Before enabling `protocol.file.allow=always`, validate each submodule URL declared in `.gitmodules` (e.g., via `git config -f .gitmodules --get-regexp submodule\..*\.url`) and reject/prompt when any URL uses the `file://` scheme or resolves outside an expected trust boundary, rather than blanket-enabling the file transport for the whole `submodule update` invocation.

### Proof of Concept
1. Attacker creates a repo with a branch containing `.gitmodules` referencing a submodule at `file:///Users/victim/.ssh` (or any sensitive local path known/guessable on the victim's machine).
2. Victim clones the repo and switches to that branch in GitHub Desktop.
3. Desktop's checkout flow detects the uninitialized submodule and calls `checkoutBranch(repo, branch, remote, cb, true)`, which triggers `updateSubmodulesAfterOperation` with `-c protocol.file.allow=always` [6](#0-5) .
4. Git initializes the submodule from the local `file://` path, pulling its content into the working tree with no validation of the URL, matching the flow already exercised in `app/test/unit/git/checkout-test.ts` lines 150-189 but using an attacker-chosen sensitive path instead of a benign test fixture.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  // we return `true` here so `GitStore.performFailableGitOperation`
  // will return _something_ differentiable from `undefined` if this succeeds
  return true
}
