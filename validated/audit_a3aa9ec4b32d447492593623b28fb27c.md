### Title
Unbounded Python recursion in `PuzzleWithRestrictions.from_memo()` allows an attacker-crafted coin memo to crash wallet sync (analogous to CVE-2018-5336) - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` reconstructs a custody/MofN puzzle tree from a `Program` memo attached to a `CREATE_COIN` condition. When the memo indicates "further branching" (an `MofN` node), it recursively calls itself once per member, with no depth limit, mirroring the unbounded-recursion class of bug fixed for Wireshark's `tvbparse.c` (CVE-2018-5336): unauthenticated/attacker-controlled input can drive parser recursion deep enough to exhaust the interpreter stack.

### Finding Description
`PuzzleWithRestrictions.from_memo()` decodes a memo `Program` and, if it encodes an `MofN` member, recurses into `PuzzleWithRestrictions.from_memo()` once per member via `MofNHint.from_program()`: [1](#0-0) 

There is no recursion-depth or nesting-depth check anywhere in this parsing path (`from_memo`, `MofNHint.from_program`, or the mutual recursion between them). A coin's `memo_blob` is fully attacker-controlled data placed by whoever creates the coin (via a `CREATE_COIN` condition's memo list), and this exact parsing path is invoked by `PlotNFTPuzzle`/`PlotNFT.get_next_from_coin_spend()` when trying to recognize an unknown inner singleton puzzle from its memoization: [2](#0-1) 

Because `MofN.__post_init__` only validates `m`/`n` bounds and duplicate nodes at construction time (after parsing already succeeded), it does nothing to bound recursion depth *during* `from_memo()` parsing: [3](#0-2) 

An attacker who controls a spend (e.g., spending their own singleton/plotNFT-shaped coin, or crafting any coin whose puzzle reveal creates a child coin with a deeply nested `MofN` memo) can construct a memo with hundreds/thousands of nested `MofN` branches. When a victim's wallet later processes that coin spend through `PlotNFT.get_next_from_coin_spend()` (pool/plotNFT sync path), `from_memo()` recurses once per nesting level and will raise Python's `RecursionError` once it exceeds the interpreter's default recursion limit (commonly ~1000 frames), an unhandled exception in the wallet's sync/processing code.

This is directly analogous to CVE-2018-5336: an untrusted, attacker-supplied structure drives a parser's recursion depth with no explicit bound, and the fix pattern for that CVE was "limit the recursion depth." No equivalent bound exists here.

### Impact Explanation
An unhandled `RecursionError` raised deep inside wallet sync/processing code (`get_next_from_coin_spend`) can halt or crash that wallet coroutine/task, disrupting a wallet's ability to sync plotNFT/singleton state for the affected wallet client. This is a spend-triggered, attacker-reachable transaction-processing halt in the wallet layer — it doesn't corrupt consensus state or steal funds directly, but it is a concrete denial-of-service against wallet processing of otherwise valid on-chain data, satisfying the "spend-triggered transaction-processing halt" acceptance criterion. Severity is bounded by the fact this is wallet-side Python code (not full-node consensus validation), but it is reachable from any coin spend that a victim wallet chooses to track/sync (e.g., plotNFT pooling flows).

### Likelihood Explanation
Likelihood is high for any attacker willing to spend a coin with a crafted memo: constructing an arbitrarily deep, syntactically valid `MofN` memo tree costs the attacker only CLVM program construction effort (no signature or special privilege needed beyond spending a coin they control), and the recursive structure required (nested lists) is cheap to serialize. The main precondition is that a victim's wallet actually calls `PuzzleWithRestrictions.from_memo()` / `PlotNFT.get_next_from_coin_spend()` on the attacker's coin — this occurs during plotNFT/pool wallet sync of singleton state, a code path a victim wallet will exercise automatically when tracking pool/plotNFT coins.

### Recommendation
Add an explicit depth counter/limit to `PuzzleWithRestrictions.from_memo()` (and its mutual recursion via `MofNHint.from_program`), rejecting memos that exceed a sane maximum nesting depth (e.g., matching the maximum `MofN` fan-out/depth the module actually supports), and/or convert the recursive descent into an iterative, stack-based traversal (as already done for `sha256_treehash` in `chia/types/blockchain_format/tree_hash.py`, which was deliberately made non-recursive specifically to avoid Python stack limits). Wrap `from_memo()` call sites (e.g., in `chia/pools/plotnft_drivers.py`) to catch `RecursionError` and translate it into the existing `GetNextPlotNFTError`, rather than letting the exception propagate unhandled.

### Proof of Concept
1. Build a nested memo `Program` for `MofN` where each member's `PuzzleWithRestrictions` also wraps another `MofN` with a single further-nested member, repeated N times (N large, e.g. 2000), terminating in a leaf `UnknownMember`/`MemberHint`.
2. Serialize this as the `memo_blob` on a `CREATE_COIN` condition output by a coin spend that a victim wallet will process as a singleton/plotNFT state transition (matching the shape expected by `PlotNFT.get_next_from_coin_spend`).
3. Submit the spend bundle to the mempool/chain.
4. When a victim wallet syncs and calls `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())` (in `chia/pools/plotnft_drivers.py`), the recursive descent through `from_memo()`/`MofNHint.from_program()` exceeds Python's recursion limit and raises an unhandled `RecursionError`, disrupting that wallet's sync/processing task.
