### Title
Unauthenticated resource exhaustion via `ThresholdKeys::read` performing unbounded point deserialization before parameter validation - (File: crypto/dkg/src/lib.rs)

### Summary
The reference report describes a DoS where expensive work (PostgreSQL query planning/execution on `audit_logs`) is performed before the rejecting policy (RLS) is evaluated, letting unauthenticated callers burn resources on requests guaranteed to fail. The Serai analog is `ThresholdKeys::read`: it performs up to 65,535 elliptic-curve point decodings driven by an attacker-controlled `n` field before `ThresholdParams::new` validates `t`, `n`, and `i`, so malformed inputs that will inevitably be rejected still force the maximum amount of expensive work first.

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, and `i` from the byte stream, then unconditionally reads `n` verification-share points via `<C as Ciphersuite>::read_G` — each a full decompression and curve/canonicality check — plus `n` scalar reads for `Interpolation::Constant`. Only after all of that work does it call `ThresholdParams::new(t, n, i)`, which is where combinations such as `t > n`, `i > n`, `n == 0`, or `t == 0` are rejected [1](#0-0) . The `Participant::new` check on `i` only rejects index zero; there is no bound on `n` before it drives the read loops [2](#0-1) . `ThresholdKeys::new` then performs the group-key interpolation sum over `t` points before returning, another linear pass of scalar multiplications [3](#0-2) .

The result mirrors the Capgo flaw: a caller supplying a `ThresholdKeys` blob with `n = 0xFFFF` and `t = 0` (or `i > n`, or `t > n`) forces ~65k point decompressions and ~65k scalar decodes — the most expensive operation in the function — before the cheap parameter check that was always going to fail.

### Impact Explanation
`ThresholdKeys::read` is an explicit entry point for untrusted bytes under the engagement scope. An unprivileged party who can cause a node/processor to deserialize a `ThresholdKeys` blob (e.g., key material received during multisig registration/recovery flows) can force tens of thousands of variable-time point decompressions — roughly ~64× CPU amplification per input byte for a ~2 MB input — on requests that are guaranteed to be rejected. Repeated or concurrent submissions degrade or stall the victim's signing pipeline, an application-layer denial of service analogous to the statement-timeout exhaustion in the reference report.

### Likelihood Explanation
Exploitation requires only the ability to submit bytes that reach `ThresholdKeys::read`; no key material, valid signature, or validator status is needed, since the resource burn happens before any semantic rejection. The only mitigating factor is that the amplification is bounded by `u16::MAX` and linear in input size, keeping this at Medium rather than higher.

### Recommendation
Validate `ThresholdParams` (and the `interpolation` tag's relationship to `t`/`n`) immediately after reading `t`, `n`, `i` in `ThresholdKeys::read`, before any scalar/point reads. Additionally, cap `n` at the protocol maximum (`MAX_KEY_SHARES_PER_SET`) before the verification-share loop, matching the pre-allocation bounds checks used elsewhere (e.g., `SlashReport` length gating).

### Proof of Concept
Construct a byte string: `u32 id_len` + valid `C::ID`, then `t = 0x0000` (invalid: threshold zero), `n = 0xFFFF`, `i = 0x0001`, `interpolation = 1` (Lagrange), a 32-byte scalar, and 65,535 valid point encodings. `ThresholdKeys::read` decodes all 65,535 points — full decompression each — and only then calls `ThresholdParams::new(0, 65535, 1)`, which rejects the invalid threshold. All decode work is wasted on guaranteed-rejected input; looping this consumes CPU proportional to ~65k decompressions per request.
