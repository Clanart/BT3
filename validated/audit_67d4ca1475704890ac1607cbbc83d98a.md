### Title
Timing/front-running attack on `_provisionReward` allows sole/dust staker to capture entire `queuedRewards` at the 0→nonzero `totalStaked()` transition - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool._provisionReward` accumulates reward tokens into `queuedRewards` whenever `totalStaked() == 0`, and flushes the entire queued amount into `rewardPerTokenStored` based on `totalStaked()` at the moment of the *next* `_provisionReward` call (via `donateRewards` or `queueNewRewards`). Because `donateRewards` is a permissionless external function with no minimum-amount or time-weighting requirement, an attacker who becomes the sole (or dust) staker right when `totalStaked()` transitions from 0 to nonzero can trigger the flush themselves and claim the entire queued balance regardless of stake size or duration.

### Finding Description
`_provisionReward` in [1](#0-0)  works as follows:
- If `totalStaked() == 0`, the incoming reward is only added to `rewardInfo.queuedRewards` — no `rewardPerTokenStored` update occurs, because there is no supply to divide by.
- On any subsequent call to `_provisionReward` (from `donateRewards` at [2](#0-1)  or `queueNewRewards` at [3](#0-2) ) where `totalStaked() > 0`, the entire accumulated `queuedRewards` is folded into the new reward amount and distributed pro-rata over `totalStaked()` **as it exists at that instant**:
```
rewardInfo.rewardPerTokenStored += (_amountReward * 10**stakingDecimals()) / this.totalStaked();
```
`totalStaked()` reads `IERC20(stakingToken).balanceOf(operator)` [4](#0-3) , i.e. the live balance staked in `MasterMagpie` at call time — not a time-weighted or historical measure.

`donateRewards` has no access control beyond `isRewardToken[_rewardToken]` [2](#0-1) , so any unprivileged address can call it with an arbitrarily small amount purely to force the flush. `rewards` is a public mapping, so `queuedRewards` is observable on-chain by anyone waiting for an opportunity.

Exploit flow:
1. Last legitimate staker withdraws all stake → `totalStaked() == 0`.
2. If any reward provisioning happens (or has already happened, e.g. a manager `queueNewRewards` call landed while `totalStaked()==0`), that amount sits fully in `queuedRewards`, unattributed to any staker.
3. Attacker calls `MasterMagpie` deposit function to stake a dust amount (e.g. 1 wei) of `stakingToken`, becoming the sole staker (`totalStaked() == 1`).
4. Attacker (permissionlessly) calls `donateRewards(1, rewardToken)` (or waits for any `queueNewRewards` call) — this executes `_provisionReward` with `totalStaked() == 1`, converting the *entire* `queuedRewards` balance into `rewardPerTokenStored` divided by a supply of 1 wei.
5. Attacker's `earned()` — computed as `balanceOf(_account) * (rewardPerToken - paid) / 10**decimals` [5](#0-4)  — now reflects essentially the full queued reward amount, since the attacker holds effectively all of the (dust) supply.
6. Attacker calls `getReward` and withdraws, walking away with rewards that should have accrued to whichever stakers held balance during the period those rewards were generated (or should have been shared pro-rata with stakers who deposit afterward).

Existing checks (`onlyManager` on `queueNewRewards`, `updateReward`/`_updateFor` modifiers, `isRewardToken` check) do not prevent this because `donateRewards` itself is intentionally permissionless, and the reward-per-token math has no time-weighting or minimum-stake/duration requirement to gate the flush.

### Impact Explanation
This causes theft of unclaimed yield: reward tokens queued for the pool (deposited by managers via `queueNewRewards` or otherwise sitting in `queuedRewards`) are captured almost entirely by an attacker who stakes a negligible, momentary dust amount, at the expense of stakers who deposit shortly after or who staked before the pool was emptied. This matches the "theft of unclaimed yield" impact class. The magnitude of loss is bounded by however much reward value is queued at the moment `totalStaked()` was last zero.

### Likelihood Explanation
- Preconditions: `totalStaked()` must have hit zero with `queuedRewards > 0` (or become zero and then have a reward provisioned while empty) — this can happen naturally whenever a pool is thin or drained to zero (new pool launch, temporary full-withdrawal event, or low-TVL/experimental reward pools).
- Capital needed: negligible — 1 wei of staking token plus 1 wei (or minimal amount) of reward token to trigger the flush.
- Feasibility: fully permissionless; no special role needed, `donateRewards` and deposit are both open functions.
- Repeatability: repeatable any time the 0-total-staked condition recurs, though it requires the attacker to observe/front-run that specific state, making it opportunistic rather than always-available.

### Recommendation
Redesign `_provisionReward` to avoid granting the entire `queuedRewards` balance based on instantaneous `totalStaked()`:
- Distribute `queuedRewards` gradually (e.g. via a reward-rate/duration-based streaming mechanism rather than an instant `rewardPerTokenStored` bump) so a dust staker present only momentarily cannot claim the whole backlog.
- Alternatively, require a minimum stake duration/checkpoint before newly staked balance is eligible for previously-queued rewards, or snapshot `queuedRewards` distribution proportionally over time rather than at the discrete moment of the next `_provisionReward` call.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie` + `BaseRewardPool` with a reward token and staking token; register reward token.
2. Staker A deposits and stakes 100e18 tokens.
3. Manager calls `queueNewRewards(1000e18, rewardToken)` — verify `rewardPerTokenStored` updates normally (sanity baseline).
4. Staker A withdraws entire stake → assert `totalStaked() == 0`.
5. Call `donateRewards(500e18, rewardToken)` (simulating a legitimate/queued reward while empty) — assert `rewards[rewardToken].queuedRewards == 500e18` and `rewardPerTokenStored` unchanged.
6. Attacker deposits `1` wei of staking token → `totalStaked() == 1`.
7. Attacker calls `donateRewards(1, rewardToken)` to trigger flush.
8. Assert `rewards[rewardToken].queuedRewards == 0` and `earned(attacker, rewardToken) ≈ 500e18` (minus the 1 wei donated by attacker itself, netting ~500e18 profit for a 1-wei stake).
9. Assert that if Staker B then deposits 100e18 immediately after, `earned(stakerB, rewardToken) == 0` for the 500e18 despite arriving right after the queued rewards existed — demonstrating the misallocation/theft.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
