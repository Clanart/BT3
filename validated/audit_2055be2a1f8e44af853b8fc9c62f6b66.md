### Title
Reward-tier gaming via unrelated `mWomSV` locks lets attacker extract oversized MGP reward from `ArbWomUp3.incentiveDeposit` (non-lock branch) - ([File: wombat/ArbWomUp3.sol])

### Summary
In `ArbWomUp3.getRewardAmount`, the non-lock branch (`_lock == false`, i.e. `_mode != 2`) computes reward as `_amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR`, where `getUserTier` is based on the user's total balance already locked in `mWomSV` (`mWomSV.getUserTotalLocked`), not on the amount actually being converted in the current call. Since `mWomSV.lock()`/`mWomSV.lockFor()` are public, unrestricted external functions, an attacker can inflate their `mWomSV` locked balance independently of `ArbWomUp3`, then repeatedly call `incentiveDeposit` with small `_amount` values to receive the top-tier multiplier on each small conversion.

### Finding Description
The vulnerable code path: [1](#0-0) 

```solidity
function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
    uint256 mgpReward = 0;
    if (!_lock) {
        mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
    } else {
        ... // lock branch subtracts calDoubledCounted(_account)
    }
    ...
}
```

`getUserTier` reads `mWomSV.getUserTotalLocked(_account)` directly: [2](#0-1) 

`mWomSV.lock` and `mWomSV.lockFor` are public/external with no caller restriction beyond `whenNotPaused`/`nonReentrant`, and only require the caller to hold `mWOM` tokens: [3](#0-2) 

An attacker can:
1. Acquire/mint `mWOM` (via `mWOM.sol` deposit or open market) and call `mWomSV.lock(largeAmount)` directly — a path entirely unrelated to `ArbWomUp3`.
2. This raises `mWomSV.getUserTotalLocked(attacker)`, hence `ArbWomUp3.getUserTier(attacker)` returns a high tier index.
3. Call `ArbWomUp3.incentiveDeposit(_amount = small, _convertRatio, false, _mode = 1)` (non-lock branch, `_mode != 2`).
4. `getRewardAmount` applies the high-tier `rewardMultiplier` to the small `_amountToConvert`, producing MGP reward disproportionate to the amount actually converted through `ArbWomUp3`.
5. Unlike the `_lock == true` branch, which subtracts `calDoubledCounted(_account)` (itself also based on the same `mWomSV.getUserTotalLocked` value) to avoid re-rewarding the same locked balance, the non-lock branch has **no such deduction or tracking of cumulative rewarded principal** — each call re-evaluates the tier fresh and multiplies only the newly submitted `_amountToConvert`. The attacker can therefore repeat step 3 multiple times with small amounts, each time receiving the inflated multiplier, as long as MGP balance remains (`mgpleft` cap in `getRewardAmount` is the only limiter, and it is a shared pool, not a per-tx bound tied to invested capital).

No modifier or accounting in `incentiveDeposit`, `_deposit`, or `getRewardAmount` ties the multiplier lookup to the WOM actually being converted in that specific transaction; the tier lookup and the conversion amount are decoupled inputs the attacker independently controls.

### Impact Explanation
This breaks conservation: the reward paid out per unit of `_amountToConvert` should be bounded by tier progression tied to actual capital committed through `ArbWomUp3`, but instead is fully manipulable via cheap, unrelated `mWomSV` locking. The attacker extracts MGP tokens (vlMGP via `vlMGP.lockFor`) from the contract's finite MGP balance in excess of what their actual WOM conversion volume justifies — a direct theft of protocol-held MGP intended as incentive for genuine WOM-to-mWOM conversion volume. This matches the Immunefi "theft of funds / protocol insolvency (partial)" impact class, draining the incentive-program MGP reserve disproportionately.

### Likelihood Explanation
Feasibility is high: `mWomSV.lock`/`lockFor` are unprivileged, permissionless external functions requiring only ownership of `mWOM` tokens; no admin/operator role is needed. The attacker's capital requirement is only whatever amount of `mWOM` is needed to reach a high reward tier — which itself may later be partially recoverable via `mWomSV.startUnlock`/`unlock` after a cooldown, meaning the capital is not permanently spent, only temporarily locked. The exploit is repeatable across multiple `incentiveDeposit(_mode=1)` calls as long as `mgp` balance remains in `ArbWomUp3`. This is straightforwardly reproducible with a Foundry test.

### Recommendation
In the non-lock branch, base the tier lookup and multiplier accrual strictly on the amount converted through `ArbWomUp3` (mirroring the lock branch's accounting, e.g. tracking a dedicated `userWOMDeposited`/`userConvertedThroughArbWomUp3` mapping updated only by `_deposit`), rather than querying `mWomSV.getUserTotalLocked`, which can be freely manipulated by locking `mWOM` outside of the incentive program. Alternatively, remove the tier dependency on external, freely-mutable state and instead accumulate tier progress solely from `_amountToConvert` values passed through `incentiveDeposit`, applying the same double-counting protection (`calDoubledCounted`-style deduction) used in the lock branch.

### Proof of Concept
Foundry test plan:
1. Deploy `mWOM`, `mWomSV`, `MasterMagpie`, `ArbWomUp3`, `vlMGP`, and fund `ArbWomUp3` with a large MGP balance.
2. Set `rewardTier = [0, T1, T2]` and `rewardMultiplier = [m0, m1, m2]` with `m2 >> m0`.
3. Attacker mints/acquires `mWOM` amount `>= T2` and calls `mWomSV.lock(T2)` directly (no interaction with `ArbWomUp3`).
4. Assert `ArbWomUp3.getUserTier(attacker) == 2` (top tier) purely from this unrelated lock.
5. Attacker calls `ArbWomUp3.incentiveDeposit(_amount = 1 WOM, _convertRatio, false, _mode = 1)`.
6. Assert: `rewardToSend` (from `getRewardAmount(1e18, attacker, false)`) equals `1e18 * m2 / DENOMINATOR`, i.e. bounded by the top-tier multiplier applied to a trivial `_amount`, rather than any multiplier tier that would require actually depositing `T2` worth of WOM through `ArbWomUp3`.
7. Assert that repeating step 5 multiple times keeps yielding the same top-tier-multiplied reward per call (no cumulative deduction), draining `IERC20(mgp).balanceOf(address(ArbWomUp3))` disproportionately to the attacker's real conversion volume — demonstrating the conservation invariant violation (reward not bounded by `_amount`, but by unrelated pre-existing `mWomSV` balance).

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }
