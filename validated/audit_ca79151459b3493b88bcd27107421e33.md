### Title
Unguarded `updateEndRemainingAllocation()` allows repeated re-snapshotting of the bonus denominator, letting any claimant inflate their `getBonusAmount()` beyond their fair pro-rata share - ([File: rewards/Airdrop.sol])

### Summary
`Airdrop.updateEndRemainingAllocation()` is a `public` function with no access control and no one-time guard, only gated by `block.timestamp >= periodsEndTime[4]`. Because `claim()` only auto-invokes it when `totalEndRemainingAllocation == 0` [1](#0-0) , any address can directly call `updateEndRemainingAllocation()` again after the first snapshot has been set, each time overwriting `totalEndRemainingAllocation` with the *current* (shrinking) `totalRemainingAllocation` [2](#0-1) . Since `totalBonus` is never decremented as bonuses are paid out, re-lowering the denominator right before an attacker's own `claim()` inflates `getBonusAmount()` beyond the attacker's fair pro-rata share of `totalBonus`, breaking conservation and diverting funds meant for other still-unclaimed participants.

### Finding Description
The bonus mechanism is designed so that `totalEndRemainingAllocation` is snapshotted exactly once — at the moment `block.timestamp` first reaches `periodsEndTime[4]` — capturing the sum of allocations of all users who have not yet claimed. Each such user's bonus share is `userAllocation * totalBonus / totalEndRemainingAllocation` [3](#0-2) . If this denominator is fixed at that single point in time, the sum of all bonus payouts to the snapshotted cohort exactly equals `totalBonus` (conservation holds).

However, `updateEndRemainingAllocation()` itself has no access control and no "already set" guard beyond the time check:
```solidity
function updateEndRemainingAllocation() public {
    if (block.timestamp >= periodsEndTime[4]) {
        totalEndRemainingAllocation = totalRemainingAllocation;
    }
}
``` [4](#0-3) 

`claim()` only calls it conditionally (`if (totalEndRemainingAllocation == 0)`), which prevents *automatic* re-triggering from claim(), but does nothing to stop an attacker calling the public function directly at any later time [1](#0-0) .

Each time a user calls `claim()`, their allocation is removed from `totalRemainingAllocation`:
```solidity
uint256 userAllocation = allocations[msg.sender];
allocations[msg.sender] = 0;
totalRemainingAllocation -= userAllocation;
``` [5](#0-4) 

but `totalBonus` is only ever increased (from early forfeitures), never decreased when a bonus is paid out. So the pool numerator (`totalBonus`) stays fixed while the "fair" denominator shrinks naturally as legitimate claimants exit. An attacker who waits for several honest users to claim, then calls `updateEndRemainingAllocation()` again just before their own `claim()`, re-snapshots `totalEndRemainingAllocation` to the now-smaller `totalRemainingAllocation`. This inflates `getBonusAmount(attacker)` relative to what it should be under the original, correctly-scoped snapshot — the attacker receives more than their pro-rata share of `totalBonus`, at the expense of the remaining/other unclaimed participants, who will later find the contract under-funded (`claimableAmount > aidropToken.balanceOf(address(this))` reverting their `claim()` via `InsufficientBalance`) [6](#0-5) .

No modifier (`onlyOwner`, `nonReentrant`, one-time-set flag) protects this snapshot, so the exploit is directly reachable by any unprivileged address holding a nonzero `allocations[attacker]` entry.

### Impact Explanation
This is a direct theft of user funds: the attacker extracts more than their fair share of the shared `totalBonus` pool by manipulating a public, unguarded snapshot function, at the expense of other still-unclaimed airdrop participants. This falls under "Direct theft of user funds" and can also cause "funds frozen" for other legitimate claimants who later revert with `InsufficientBalance` once the contract's token balance is drained beyond what their fair share should have left.

### Likelihood Explanation
- Preconditions are trivial: attacker only needs a nonzero `allocations[attacker]` entry (any address registered by the airdrop owner, which is common for a public airdrop) and to wait until `block.timestamp >= periodsEndTime[4]`.
- No capital is required beyond gas — `updateEndRemainingAllocation()` and `claim()` are both public/external with no fee or stake requirement.
- The attack is fully repeatable by any and all claimants who claim later in the sequence, as each subsequent re-snapshot before a claim compounds the unfairness for whoever claims after them, versus whoever claimed before the manipulation.

### Recommendation
Snapshot `totalEndRemainingAllocation` exactly once and make it immutable thereafter, e.g., add a boolean flag (`bool public endRemainingAllocationSet`) and revert or no-op if already set:
```solidity
function updateEndRemainingAllocation() public {
    if (totalEndRemainingAllocation == 0 && block.timestamp >= periodsEndTime[4]) {
        totalEndRemainingAllocation = totalRemainingAllocation;
    }
}
```
Additionally, decrement `totalBonus` by the paid-out bonus portion in `claim()` to keep the numerator/denominator relationship consistent, or restrict `updateEndRemainingAllocation()` to be callable at most once via a dedicated flag rather than relying on the mutable `totalEndRemainingAllocation == 0` check (which is technically already a de-facto one-time guard for the *auto-call* path in `claim()`, but not for direct external calls).

### Proof of Concept
Foundry test plan:
1. Deploy `Airdrop` with `startTime = block.timestamp + 1`, register 3 users (A, B, Attacker) with equal allocations (e.g., 100e18 each) via `register()`.
2. Warp time to before `periodsEndTime[4]` and have user A claim early (partial period) to generate `totalBonus > 0` via forfeiture, then warp to `periodsEndTime[4]`.
3. Have user B call `claim()` — this triggers the auto-call of `updateEndRemainingAllocation()` inside `claim()`, snapshotting `totalEndRemainingAllocation` to the `totalRemainingAllocation` at that time (call this `snapshot0`), and record B's `bonusAmount` (`bonus_B = userAllocation_B * totalBonus / snapshot0`).
4. Have Attacker call `updateEndRemainingAllocation()` directly (no restriction) — this re-sets `totalEndRemainingAllocation` to the new, smaller `totalRemainingAllocation` (after B's allocation was already subtracted), call this `snapshot1 < snapshot0`.
5. Have Attacker call `claim()` and record `bonus_Attacker = userAllocation_attacker * totalBonus / snapshot1`.
6. Assert `bonus_Attacker > userAllocation_attacker * totalBonus / snapshot0` (i.e., strictly greater than the fair share computed against the original snapshot), demonstrating the attacker received more than their pro-rata share, and that `bonus_B + bonus_Attacker` (scaled to their respective allocations) exceeds the conservation bound implied by `totalBonus` and the original entitled cohort.
