### Title
`unvote` reverts for inactive pools, permanently locking a user's vlMGP voting power despite the docstring's explicit guarantee - ([File: wombat/WombatBribeManager.sol])

### Summary
`WombatBribeManager.unvote()` is documented to let a user withdraw their vote from a pool that has been deactivated ("This makes it so that deleting a pool, or changing a rewarder doesn't block users from withdrawing"), but the implementation does the opposite: it requires `pool.isActive == true` and reverts with `PoolNotActive()` otherwise. This is the same bug class as the referenced Rubicon finding — a state-mutating "cancel" style function silently fails/reverts for the exact records it was designed to release, permanently freezing user state that other core functions (`startUnlock` in `VLMGP`) depend on.

### Finding Description
`vote()` requires `pool.isActive` before recording a user's vote in `userVotedForPoolInVlmgp[msg.sender][lp]` and `userTotalVotedInVlmgp[msg.sender]`: [1](#0-0) 

`unvote()` is the designated escape hatch for pools that later become inactive, per its own comment, yet it enforces the identical `isActive` guard before allowing the vote to be released: [2](#0-1) 

Once a pool is set inactive (there is no code path that flips `isActive` back to `true` for the same lp after removal/replacement), a user who voted for that pool can never call `unvote(lp)` successfully — it will always revert with `PoolNotActive()`, and `userVotedForPoolInVlmgp[msg.sender][lp]` / `userTotalVotedInVlmgp[msg.sender]` can never be decremented for that pool.

This directly freezes the user's vlMGP lock: `VLMGP.startUnlock()` refuses to start an unlock for any amount that would bring the user's total locked MGP below their outstanding `userTotalVotedInVlmgp`: [3](#0-2) 

Since the stuck vote can never be reduced via `unvote`, any user whose entire (or majority) lock is tied up in votes for a now-inactive pool is permanently blocked from calling `startUnlock`/`unlock` for that portion of their locked MGP — mirroring exactly the "some offers can't be cancelled" pattern from the external report, where a `cancel`-style safety valve fails on precisely the record it was built to release.

### Impact Explanation
This causes a permanent (>24h, indefinite) freeze of a legitimate user's locked MGP (vlMGP), since there is no other function that reduces `userTotalVotedInVlmgp` for an inactive pool besides `unvote`/`vote` (both gated by the same `isActive` check) or `castVotes`/`voteAndCast` (which iterate only over currently active `pools` array entries and can't target a removed pool the user still has a stale vote for). This satisfies the "permanent freezing of funds" / "freezing of unclaimed yield and voting position" impact bar, and is reachable purely from an ordinary user's own prior `vote()` call plus a routine, non-malicious pool lifecycle event (deactivation/replacement), not any attacker-controlled or malicious-admin action.

### Likelihood Explanation
Pool deactivation/rotation is an expected, ordinary lifecycle event for a bribe/voting system (rewarder migrations, deprecated LPs, etc.), not a rare or adversarial admin act. Any user who has voted for a pool that is later deactivated is affected automatically the next time they try to `unvote` or `startUnlock` past their voted amount — no attacker action or coordination is required, making this highly likely to occur over the protocol's lifetime.

### Recommendation
Remove the `isActive` check from `unvote()` (or invert it to explicitly allow inactive pools) so unvoting/releasing a stale vote is always permitted regardless of the pool's active status, consistent with the function's own documented intent. Ensure `userVotedForPoolInVlmgp` and `userTotalVotedInVlmgp` can always be decremented independent of `pool.isActive`.

### Proof of Concept
1. User calls `vote([lpA], [1000])`, recording `userVotedForPoolInVlmgp[user][lpA] = 1000` and `userTotalVotedInVlmgp[user] = 1000`, using up all (or most) of their vlMGP lock capacity. [4](#0-3) 
2. Protocol owner performs a routine pool rotation — deactivates/removes `lpA` (`pool.isActive` becomes false / the pool is dropped from the active `pools` list).
3. User now wants to unlock their vlMGP: they first call `unvote(lpA)` to free their voting allocation — this reverts with `PoolNotActive()` because of the check at [5](#0-4) .
4. User calls `VLMGP.startUnlock(amount)` for the locked MGP; because `userTotalVotedInVlmgp[user]` still equals 1000 and can never be reduced, any unlock attempt that would drop `totalLockAfterStartUnlock` below 1000 reverts with `NotEnoughLockedMPG()` at [3](#0-2) .
5. The user's MGP tied to that vote allocation is permanently frozen — there is no functional path to reduce the stale vote count.
