### Title
Future-dated oracle timestamp permanently poisons the shared per-feed `last-update` state, causing indefinite DoS of price resolution - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`oracle-timestamp-fresh` treats any oracle publish-time that is greater than the current `stacks-block-time` as having zero staleness (always "fresh"), and `price-resolve` unconditionally persists that timestamp into the shared, per-feed `last-update` map whenever it's newer than the previous stored value. Since `last-update` is keyed only by `{type, ident}` — not by asset — a single anomalously future-dated price update for a feed (e.g. the STX/USD Pyth feed, shared by STX, stSTX, zSTX, zstSTX) permanently "poisons" that feed: every subsequent legitimately-timestamped price update will have `ts < prev` and fail the monotonicity check `(>= ts prev)`, reverting with `ERR-ORACLE-INVARIANT` for every asset that shares that feed identity, until real chain time catches up to the poisoned future timestamp.

### Finding Description
`oracle-timestamp-fresh` in `mainnet/contracts/market/v0-4-market.clar` (lines 365-371): [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

When `ts > stacks-block-time` (i.e. the oracle price's publish-time is in the future relative to the Stacks chain clock), `delta` is clamped to `u0`, which trivially satisfies `(<= delta max-staleness)`. There is no upper bound / sanity check that rejects a timestamp that is unreasonably far in the future — only the "too old" side is checked.

`price-resolve` then stores this timestamp as the new baseline for the feed: [2](#0-1) 

```clarity
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        ...
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        ...)
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
    (ok final-price)))
```

`last-update` is keyed only by `{type, ident}` — the raw oracle feed identity — not by asset ID. This means STX, stSTX (`CALLCODE-STSTX`), zSTX (`CALLCODE-ZSTX`), and zstSTX (`CALLCODE-ZSTSTX`) all resolve through the same `PYTH-STX` ident and therefore share exactly one `last-update` entry, confirmed by `resolve-callcode`: [3](#0-2) 

Once any single price update for that feed is accepted with a future timestamp, `last-update` is set to that future value. Every subsequent legitimately-timestamped update (`ts` close to real/chain time) will now be `< prev`, so `(>= ts prev)` fails and `price-resolve` returns `ERR-ORACLE-INVARIANT` for every asset sharing that feed key. Because `get-assets` → `price-multi-resolve` → `iter-price-multi` propagates any single failed resolution into `ERR-ORACLE-MULTI`, this locks up `borrow`, `collateral-add`/health checks, and `liquidate` for every position touching that feed's assets: [4](#0-3) [5](#0-4) 

`write-feeds` (called from `borrow`/`liquidate` with a user-supplied `price-feeds` list) is a permissionless path that lets any caller push arbitrary already-Guardian-signed Pyth VAAs on-chain; the underlying `pyth-storage-v4.write` only rejects updates that are *too old* relative to `latest-stacks-timestamp`, with no upper-bound/future check either — so a genuinely signed price with an outlier or clock-skewed publish-time can pass through to `market.clar` and get latched into `last-update`. The actual poisoning logic bug, independent of what Pyth returns, is in `oracle-timestamp-fresh`'s asymmetric clamp and in `price-resolve`'s unconditional persistence of any "fresher" timestamp without bounding how far in the future it may be.

### Impact Explanation
Once a feed's `last-update` is poisoned with a future timestamp, all pricing (and hence all health checks) for every asset sharing that feed identity revert with `ERR-ORACLE-INVARIANT` until the chain's `stacks-block-time` reaches the poisoned value. During this window:
- Borrowing against, or adding/removing, any affected collateral/debt asset is blocked.
- **Liquidations of unhealthy positions using the affected feed are also blocked** — if collateral prices crash during the DoS window, bad debt can accrue because liquidators cannot act, escalating from temporary freezing of funds toward protocol insolvency risk.

This lands in the in-scope **temporary freezing of funds** impact class (with a path to worse outcomes depending on poisoning duration and market conditions during the window).

### Likelihood Explanation
Reaching this state does not require any privileged access or DAO compromise — `write-feeds`/price submission paths are called permissionlessly from user-facing `borrow`/`liquidate` entry points, and pushing a valid, already-signed VAA with an outlier or skewed `publish-time` is sufficient. No upper bound exists anywhere in the chain of checks (`pyth-storage-v4.write`, `oracle-timestamp-fresh`) to prevent a future-dated timestamp from being accepted and persisted, making this a straightforward, low-cost trigger relative to the scope of impact (affecting every asset sharing the poisoned feed identity, not just one asset).

### Recommendation
- In `oracle-timestamp-fresh`, reject (rather than clamp to zero) any `ts` that exceeds `stacks-block-time` by more than a small allowed clock-skew tolerance, instead of treating all future timestamps as maximally fresh.
- Do not persist a timestamp into `last-update` until it has been validated against this bound.
- Consider scoping `last-update` by asset ID in addition to `{type, ident}` so that a single poisoned raw feed timestamp cannot simultaneously DoS all derived/callcode assets that share the underlying identifier.

### Proof of Concept
1. A caller (anyone) invokes `borrow` (or `liquidate`) supplying a `price-feeds` VAA batch containing a legitimately Pyth-Guardian-signed price update for the `PYTH-STX` feed whose `publish-time` is set far ahead of the current `stacks-block-time` (bounded only by Pyth's own signing/staleness rules on the "too old" side; no "too new" bound exists in `pyth-storage-v4.write` or in Zest's `oracle-timestamp-fresh`).
2. `write-feeds` → `pyth-storage-v4.write` accepts it (only checks against being *older* than allowed, not newer).
3. `price-resolve` computes `delta = 0` (via the `(> ts stacks-block-time)` branch) so `oracle-timestamp-fresh` returns true; `map-set last-update {type: TYPE-PYTH, ident: PYTH-STX} <future-ts>` persists the poisoned value.
4. Any subsequent, correctly-timed Pyth update for STX/USD has `ts < <future-ts>`, so `(>= ts prev)` in `oracle-timestamp-fresh` is false, and `price-resolve` returns `ERR-ORACLE-INVARIANT`.
5. All of `borrow`, `collateral-add`, health checks, and `liquidate` involving STX, stSTX, zSTX, or zstSTX now fail via `get-assets` → `price-multi-resolve` → `ERR-ORACLE-MULTI`, until `stacks-block-time` naturally advances past the poisoned future timestamp.
