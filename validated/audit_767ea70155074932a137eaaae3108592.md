### Title
Unconditional whole-balance sweep in `ManualCompound.compound()` lets any unprivileged caller steal reward-token dust/residual balances not earned by them - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` never tracks how much of each reward token was actually harvested for `msg.sender`; it simply reads `IERC20(_tokenAddress).balanceOf(address(this))` and forwards the entire contract balance to whoever calls the function [1](#0-0) . Combined with the fact that `multiclaimOnBehalf` silently no-ops for stakers/pools with zero stake instead of reverting [2](#0-1) , any unprivileged EOA can call `compound()` with `_lps`/`_rewards` (even empty arrays) unrelated to any stake they hold, and if the contract is holding any pre-existing reward-token balance (rounding dust from a previous conversion, an unswept remainder, or an accidental direct transfer), that balance is sent entirely to the attacker.

### Finding Description
`compound()` performs the following unconditional logic for every registered reward token, on every call, regardless of who called it or what `_lps`/`_rewards` were supplied:
```solidity
uint256 receivedBalance = IERC20(_tokenAddress).balanceOf(address(this));
if (receivedBalance > 0) { ... transfer/convert/lock the FULL balance to msg.sender ... }
``` [3](#0-2) 

There is no accounting of "balance before this call" vs "balance after `multiclaimOnBehalf`" — the entire live token balance of the contract is attributed to the caller. `multiclaimOnBehalf` (called with `_account = msg.sender`) is gated only by `_onlyCompounder`, which restricts which *contract* may invoke it (i.e., `ManualCompound` must be whitelisted), not which *user* the claim is performed for [4](#0-3) . Internally `_multiClaim` simply computes `claimableMgp` and `_claimBaseRewarder` amounts per staking token based on `user.amount`/`rewardDebt` for the supplied `_account`; if the account has zero stake in that pool, the computed reward is zero and the loop proceeds without reverting [5](#0-4) . Thus an attacker can pass `_lps = []`/`_rewards = []` (or arbitrary pools they don't hold) and the call proceeds normally to the sweep step.

Because of this, whenever the `ManualCompound` contract is left holding any positive balance of a reward token between calls — for example rounding dust left over after `IConverter.convertFor`/`ILocker.lockFor`/`ISimpleHelper.depositFor` doesn't consume the full approved amount, or tokens accidentally sent to the contract — the *next* caller of `compound()`, even one with zero stake and zero legitimate claim, will receive that entire leftover balance via the unconditional sweep.

Regarding the specific proof-of-concept mechanism proposed in the question (a first transaction that "partially fails after harvesting but before full sweep" leaving state for a second transaction to exploit): this is **not possible** on the EVM as described, because a Solidity transaction that reverts undoes *all* state changes made during that transaction, including any tokens received via `multiclaimOnBehalf`. There is no way for a reverted call to leave harvested tokens sitting in the contract's balance for a subsequent transaction to pick up — revert is fully atomic. So that specific "queue two txs, first reverts mid-way" framing described in the question is not exploitable.

The genuinely exploitable variant is the dust-sweep design flaw itself: no per-call accounting of "who deposited what," so any pre-existing balance (from rounding remainders across successfully-completed prior calls, or externally donated tokens) is entirely up-for-grabs by the next caller regardless of stake.

### Impact Explanation
An attacker with zero stake and zero legitimate claim can capture any reward-token dust/residue accumulated in the `ManualCompound` contract by simply calling `compound()` (potentially with empty `_lps`/`_rewards` arrays, incurring only gas cost). This constitutes theft of value that rightfully belongs to the protocol/legitimate compounders (the source of the accumulated dust), matching an "unclaimed yield theft" impact class, though the amounts involved are bounded to whatever rounding dust or stray transfers accumulate in the contract rather than an attacker-controlled unbounded amount.

### Likelihood Explanation
Exploitation requires no special capital or privileges — any EOA can call the public `compound()` function. However, the magnitude of the exploit depends entirely on how much residual balance the contract happens to hold at any given time, which is a function of rounding behavior in the `convertor`/`locker`/`helper` integrations rather than something the attacker can force to be large. The specific front-running/reverted-transaction scenario proposed in the question is not feasible due to EVM transaction atomicity.

### Recommendation
Track exact amounts harvested per call instead of reading `balanceOf(address(this))`: record the balance immediately before calling `multiclaimOnBehalf` and compute `receivedBalance = balanceAfter - balanceBefore` for each reward token, only forwarding the delta attributable to the current call. This prevents any pre-existing/residual balance from being swept to an unrelated caller.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, register `ManualCompound` as an allowed compounder, add a reward token to `ManualCompound.rewards`.
2. Simulate residual dust: directly transfer a small amount of the reward token to the `ManualCompound` contract address (representing rounding dust left after a prior legitimate `convertFor` call, or an accidental transfer).
3. From an attacker EOA with no stake in any pool, call `compound([], [], 0, 0, false)`.
4. Assert `multiclaimOnBehalf` executes without reverting (empty arrays), and assert the attacker's balance of the reward token increases by exactly the dust amount that was sitting in the contract, despite the attacker never having staked or earned any reward.
