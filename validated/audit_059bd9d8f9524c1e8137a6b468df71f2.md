### Title
Malformed rename/copy status entry from a crafted working tree causes `getStatus` to throw, blocking status refresh instead of skipping the bad entry - (File: `app/src/lib/status-parser.ts`)

### Summary
`parsePorcelainStatus` (`app/src/lib/status-parser.ts:55-99`) iterates over every NUL-separated token produced by `git status --porcelain=2 -z` and, for renamed/copied entries, unconditionally consumes the *next* token as the old path via `tokens[++i].toString()` (`app/src/lib/status-parser.ts:88`). If that field fails to match `changedEntryRe`, `renamedOrCopiedEntryRe`, or `unmergedEntryRe`, the parser functions throw a raw `Error` (`app/src/lib/status-parser.ts:110,133,161`) with no per-entry recovery. This throw propagates out of `parsePorcelainStatus` and up through `getStatus` (`app/src/lib/git/status.ts:233`), which has no try/catch around the parse call, so a single unparseable entry aborts the entire status computation instead of just being skipped.

### Finding Description
The same broken invariant from the report applies here: a single malformed item in a batch of otherwise-valid items should not be able to abort processing of the whole batch. In `getStatus`:
```
app/src/lib/git/status.ts:233
const parsed = parsePorcelainStatus(stdout)
```
there is no `try/catch`, and `parsePorcentainStatus` calls `parseChangedEntry`, `parsedRenamedOrCopiedEntry`, or `parseUnmergedEntry` for each token depending on its leading marker (`app/src/lib/status-parser.ts:85-95`). Each of those throws on regex mismatch: [1](#0-0) [2](#0-1) 

The content of these fields (status codes, mode bits, paths) is derived from the git working tree and index of the checked-out repository — i.e., it is influenced by whatever a cloned/fetched repository contains (file names, submodule state, and in particular the `-z` protocol's implicit assumption that a `RenamedOrCopiedEntryType` token is always followed by an old-path token). Since `entries.push(parsedRenamedOrCopiedEntry(field, tokens[++i].toString()))` blindly advances the index, a crafted repository state where a rename/copy header is the last token, or a submodule/mode field is malformed, is one path to an unmatched regex and thus an uncaught exception.

This directly mirrors the report's core flaw: "lack of validation/simulation" causing one bad batch item to revert the whole batch, with "no try and catch" around the per-item execution.

### Impact Explanation
When `getStatus` throws instead of returning, GitHub Desktop's status refresh — which drives the Changes list, what gets staged, and diff/commit UI — fails for that repository. Depending on the caller's error handling, this can:
- Repeatedly fail background status polling for a repository, effectively preventing the user from seeing/staging any changes (denial of service on core app functionality) for a repo whose working tree contains the malformed condition.
- More importantly, silently stale/incorrect status data being cached from a previous successful poll could be shown to the user while newer changes fail to be reflected because every subsequent refresh throws — risking the user committing/pushing based on stale status information (a "silent corruption of what the user commits" scenario) if any code path swallows the specific error and returns cached state instead of surfacing it.

The severity here is lower-confidence than the original Solidity finding because git status output is generated locally by the git binary reading the actual working tree of a cloned repository — it is not raw untrusted network input parsed byte-for-byte the way `offchainOrders` calldata is. The attacker's primitive is limited to crafting repository content (file paths, submodule configuration, git version skew, or unusual git status output) that the app's regexes don't anticipate.

### Likelihood Explanation
Likelihood is moderate-to-low: the regexes are reasonably permissive (`[\s\S]*?` for paths, broad character classes for status codes), and existing tests in `app/test/unit/status-parser-test.ts` cover renames, submodules, newlines in paths, and typechanges. I could not confirm in the index whether any caller of `getStatus` wraps it in a try/catch that gracefully degrades (e.g., `performFailableOperation`) — the `git-store.ts` matches for `getStatus`/`loadStatus` exist but I was not able to fully inspect that call site's error handling before running out of tool budget. This is a real gap in my analysis: **the actual blast radius depends entirely on whether the `git-store.ts` caller catches and gracefully handles a thrown error from `getStatus`, which I could not verify.**

### Recommendation
1. Wrap the per-entry parsing in `parsePorcelainStatus` in a try/catch, log the offending token, and `continue` to the next token rather than throwing for the whole batch — mirroring the report's suggested fix of skipping bad batch items instead of aborting the batch.
2. In `getStatus`, treat a caught parse failure as "status temporarily unknown" rather than letting it propagate as an unhandled exception, and avoid silently reusing stale cached status without surfacing the fact that a refresh failed.
3. Verify (in a Devin session, since I could not confirm this from the index) whether `git-store.ts`'s call into `getStatus` already has failure handling, and if not, add it.

### Proof of Concept
I could not construct/run an actual PoC without filesystem/terminal access. Conceptually: check out a repository (e.g., cloned from an attacker-controlled remote) with a working tree state that produces a `git status --porcelain=2 -z` token matching kind `'2'` (rename/copy) as the very last NUL-separated token with no trailing old-path token, or with a status-code combination outside `[MADRCUTX?!.]{2}`/`N...|S[C.][M.][U.]`. Running Desktop's status refresh against that repository would call `parsePorcelainStatus` → `parsedRenamedOrCopiedEntry`/`parseChangedEntry`, which throws, propagating out of `getStatus` uncaught. function parsedRenamedOrCopiedEntry(
  field: string,
  oldPath: string | undefined
): IStatusEntry {
  const match = renamedOrCopiedEntryRe.exec(field)

  if (!match) {
    log.debug(`parsedRenamedOrCopiedEntry parse error: ${field}`)
    throw new Error(`Failed to parse status line for renamed or copied entry`)
  }

  if (!oldPath) {
    throw new Error(
      'Failed to parse renamed or copied entry, could not parse old path'
    )
  }

  return {
    kind: 'entry',
    statusCode: match[1],
    submoduleStatusCode: match[2],
    oldPath,
    renameOrCopyScore: parseInt(match[8].substring(1), 10),
    path: match[9],
  }
}
