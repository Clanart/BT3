### Title
`_paused` flag in `IntentGatewayV2` is declared but never enforced, allowing fills, cancels, and withdrawals while the gateway is supposed to be paused - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase.sol` declares a persistent `_paused` boolean storage slot with a comment stating it was "Appended last to preserve existing storage slots," implying it is meant to gate gateway operations during an emergency/pause condition. [1](#0-0)  However, a repository-wide search shows `_paused` is referenced only at its declaration — it is never read or checked in any function, including `fillOrder`, `cancelOrder`, `_cancelSameChain`, `_cancelFromSource`, `_cancelFromDest`, or `_withdraw`. [2](#0-1) 

### Finding Description
This is the direct structural analog of the Notional `deleverageAccount` bug: a protocol-level pause/enabled flag exists to halt sensitive state-changing operations, but one or more critical entry points never check it. In Notional, `ENABLED=false` was supposed to block vault account actions, yet `deleverageAccount` bypassed the check. Here, `_paused` is clearly intended as an emergency kill-switch for `IntentGatewayV2` (per the storage-layout comment marking it as an appended pause flag), but no function in `IntrinsicIntents.sol`, `ExtrinsicIntents.sol`, or `IntentGatewayV2.sol` reads it. `fillOrder` (same-chain and cross-chain), `cancelOrder` (all three routes: same-chain, from-source, from-destination), and the underlying `_withdraw` escrow-release logic all execute unconditionally regardless of `_paused`'s value. [2](#0-1) [3](#0-2) 

Compare this to `EvmHost.sol`, where the analogous `FrozenStatus` mechanism is actively enforced via the `notFrozen` modifier on `dispatch()` and via `notFrozen(host)` in `HandlerV2.sol` for every handler entry point. [4](#0-3) [5](#0-4)  The IntentGateway's pause flag has no equivalent enforcement anywhere, so whatever operational purpose it serves (documented as an emergency stop for order fills/cancels/escrow movement) is entirely non-functional.

### Impact Explanation
If governance sets `_paused = true` in response to a detected vulnerability, active exploit, price-oracle manipulation, or other incident that requires halting new fills and settlements, an attacker (or any solver/user) can still call `fillOrder` and `cancelOrder` normally. This means escrowed funds can still move — solvers can still drain escrow via fills, and settlement/refund paths (`_withdraw`) remain fully active — during the exact window operators intended to freeze the system. This is a direct "unauthorized execution / logic attack" against the bounty's protected surface: bridged asset escrow custody and settlement moving when the protocol's own safety switch says it should not.

### Likelihood Explanation
High confidence this is a real gap: the flag exists in storage with an explicit comment about being appended for future pause functionality, but is dead code — it's never assigned (no setter was found either) nor checked. Any team relying on `_paused` as an incident-response lever would discover, only during an actual incident, that it does nothing, at which point exploitation is straightforward and requires no special privileges — any solver or user can act as normal.

### Recommendation
Add a `whenNotPaused` (or equivalent) modifier that checks `_paused` and apply it to `fillOrder`, `cancelOrder`, and any other order/escrow-affecting entry points in `IntrinsicIntents.sol` / `ExtrinsicIntents.sol`. Additionally, verify a governance-gated setter for `_paused` exists (none was found in the reviewed files) — if this flag has no setter either, it further confirms the feature was never completed and should be added end-to-end (setter + enforcement) or removed entirely.

2. Search the whole `evm/src` tree for any read of `_paused` outside its declaration — none exists (only the two matches at declaration/comment were found).
3. [6](#0-5) 
4. Therefore, setting `_paused = true` (however that would be done) has zero effect on the gateway's fill/cancel/settlement surface — unlike `EvmHost`'s `FrozenStatus`, which is properly enforced by `notFrozen`/`notFrozen(host)` on `dispatch` and all `HandlerV2` entry points. [4](#0-3) 

**Uncertainty note:** I could not locate a setter function for `_paused` within the files retrieved by the search (only its declaration in `IntentsBase.sol` was found). It's possible a setter exists in a file not surfaced by the index (e.g., an admin/governance module not returned by search), which would still not change the core finding — the flag is never *checked* anywhere in the fill/cancel paths that were inspected. A full repository grep via a Devin session would be needed to definitively rule out a setter or any check elsewhere in the codebase that the index did not surface.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }

    /**
     * @dev Cancels an existing order and initiates the refund of escrowed tokens.
     * Routes to the appropriate cancellation logic based on the order type and
     * the current chain:
     *
     * - Same-chain orders: Refunds escrow directly on this chain.
     * - Cross-chain, called from source: Dispatches a Hyperbridge GET request to
     *   verify the order was not filled on the destination chain.
     * - Cross-chain, called from destination: Marks the order as filled (preventing
     *   future fills) and dispatches a RefundEscrow message to the source chain.
     *
     * Reverts if the order has already been filled or if called from the wrong chain.
     *
     * @param order The order to cancel. Must match the exact order that was placed.
     * @param options Cancel options including proof height and relayer fee for cross-chain cancels.
     */
    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }
}
