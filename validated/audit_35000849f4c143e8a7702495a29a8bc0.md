### Title
`ThresholdKeys` deserialization never binds the secret share to the verification shares, allowing inconsistent key material that reports a controllable group key which is actually unspendable — (`crypto/dkg/src/lib.rs`)

### Summary
`ThresholdKeys::read` accepts serialized key material (params, interpolation coefficients, `secret_share`, and a map of `verification_shares`) and reconstructs the keys via `ThresholdKeys::new`. `new` derives the group key by interpolating verification shares `1..=t`, but it performs no check that the provided `secret_share` is consistent with `verification_shares[i]`, nor that the verification shares lie on a common polynomial. This is the same bug class as the UMA finding: two parameters that are supposed to agree (price identifier ↔ collateral; here `secret_share`/verification share map ↔ derived `group_key`) are accepted independently, so the effective key identity can mismatch the key material meant to control it.

### Finding Description
In `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349-391`), the only validations are:

- `verification_shares.len() == n`
- every participant index `<= n`
- `Constant` interpolation only when `t == n`

The group key is then computed as `Σ verification_shares[i] * interpolation_factor(i)` over `i ∈ 1..=t` (`crypto/dkg/src/lib.rs:376-378`). `secret_share` is stored verbatim (`crypto/dkg/src/lib.rs:384`) with no check against `verification_shares[params.i()]` (i.e., `C::generator() * secret_share == verification_shares[i]` is never asserted), and no check that the `n` verification shares interpolate to a coherent secret (e.g., that other subsets of `t` shares yield the same group key).

`ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`) feeds attacker-influenced bytes directly into this constructor: participant index `i`, interpolation coefficients, the `secret_share` scalar, and all `n` `read_G` points. An attacker can therefore craft serialized keys where `secret_share` does not correspond to `verification_shares[i]`, or where shares `1..=t` interpolate to a group key disjoint from the shares held by other participants.

The mismatch propagates into signing: `view()` (`crypto/dkg/src/lib.rs:463-533`) interpolates the loaded `secret_share` and verification shares under whatever `scalar`/`offset` the caller applies (e.g., the Taproot tweak in `networks/bitcoin/src/wallet/mod.rs:46-75`, `tweak_keys`). A signature share produced from the inconsistent `secret_share` will fail `verify_share` against the interpolated verification share only for that participant — the honest signers' shares against a group key derived from inconsistent verification shares may still fail, or worse, the *derived* `group_key` may equal a real deposit address while the holder's share belongs to a different polynomial.

Concrete failure modes:
1. `secret_share` swapped for a different scalar while `verification_shares` are left unchanged → holder loads keys, `group_key()` returns a plausible address, but every signature share the holder produces is invalid; any funds sent to `group_key()` (or its Taproot tweak) are permanently unspendable if the other participants' serialized shares were similarly corrupted — and the corruption is silent until signing is attempted.
2. `verification_shares` points altered so `1..=t` interpolate to a group key chosen by the attacker (any value the attacker wants displayed/used as the deposit address), while the real shares no longer reconstruct it → funds are reported as receivable/spendable at an address whose threshold private key does not exist under this key set.

### Impact Explanation
Funds are reported as controlled (a `group_key()` / derived Taproot address is presented and used for `Scanner`/`register_offset` in `networks/bitcoin/src/wallet/mod.rs:162-196`) while the loaded key material cannot produce valid threshold signatures for that key — deposits become unspendable. Equivalently, a silently corrupted `secret_share` causes the holder's valid-looking share to fail verification during every signing attempt, enabling targeted denial of service of a signing session (the holder is blamed/excluded). Because the inconsistency is only detectable at signing time, the corrupted keys can be distributed, backed up, and relied upon long before the failure surfaces.

### Likelihood Explanation
Exploitation requires an attacker to feed crafted bytes to `ThresholdKeys::read` — e.g., a compromised or malicious serialization channel for key backup/recovery, or an untrusted party distributing serialized `ThresholdKeys` (the recovery crate (`crypto/dkg/recovery`) exists precisely for share redistribution). The scope explicitly treats `ThresholdKeys::read` as an untrusted-bytes sink. Once accepted, the impact is deterministic. Medium likelihood, Medium impact → Medium.

### Recommendation
In `ThresholdKeys::new` (and therefore `read`):
1. Assert `C::generator() * *secret_share == verification_shares[&params.i()]` (adjusted for nothing — the share is pre-tweak) and reject otherwise.
2. Optionally validate that the verification shares are mutually consistent: compute the group key from a second distinct `t`-sized subset (or evaluate share `t+1` via interpolation and compare) to ensure all `n` shares lie on a single degree `t-1` polynomial, or bind `ThresholdKeys` to a transcript/commitment produced by the DKG so `read` can verify authenticity.
3. At minimum, document that `read` requires authenticated storage, and add an integrity tag (e.g., a MAC or the group key commitment) checked on deserialization.

### Proof of Concept
```rust
// Build a valid ThresholdKeys, then tamper with the serialized share.
let mut bytes = honest_keys.serialize();

// Locate the secret_share field (after ID, t, n, i, interpolation tag/coefs)
// and overwrite it with a different scalar s'.
// secret_share field offset: 4 + C::ID.len() + 2 + 2 + 2 + 1 (+32*n for Constant)
// For Lagrange: offset = 4 + C::ID.len() + 6 + 1, then 32 bytes of scalar.
let wrong = Scalar::from(42u64);
bytes[share_off .. share_off + 32].copy_from_slice(&wrong.to_bytes());

let keys = ThresholdKeys::<Secp256k1>::read(&mut &bytes[..]).unwrap(); // SUCCEEDS — no consistency check
// keys.group_key() is unchanged (derived from verification_shares), so deposit
// addresses / Scanner registration match the original key — yet every share this
// holder produces fails verify_share, and any solo/t=n usage cannot sign.
assert_eq!(keys.group_key(), honest_keys.group_key());
// verify_share(keys.view(included).unwrap(), sign_share(...)) -> Err
```

The key evidence is `crypto/dkg/src/lib.rs:355-390`: the constructor validates only shape (counts, index ranges, interpolation applicability) and never relates `secret_share` to `verification_shares`, so the deserialized "collateral" (the share) is never bound to the "identifier" (the derived group key).
