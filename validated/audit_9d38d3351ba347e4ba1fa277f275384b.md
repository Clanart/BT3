### Title
`WombatStaking.depositLP` mints receipt tokens for the full requested amount without verifying the actual LP tokens received - (File: `wombat/WombatStaking.sol`)

### Summary
`WombatStaking.depositLP()` transfers `_lpAmount` of the Wombat LP token from the caller and then mints `_lpAmount` of `receiptToken` unconditionally, without checking the LP token balance actually received by the contract before and after the transfer.

### Finding Description
In `depositLP`, the contract does: [1](#0-0) 
```
IERC20(poolInfo.lpAddress).safeTransferFrom(_for, address(this), _lpAmount);
_toMasterWomAndSendReward(_lpAddress, _lpAmount, true);
IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount);
```
It mints the receipt token equal to the requested `_lpAmount` rather than the delta of the contract's LP balance before/after the transfer. This is the same bug class as the referenced report: the code assumes the transferred amount equals the requested amount, and mints a claim token 1:1 against that unverified assumption. By contrast, the sibling `deposit()` function in the same contract correctly measures `lpReceived` via before/after balance deltas for the pool-deposit step: [2](#0-1) , showing the codebase is aware of this pattern but did not apply it to `depositLP`.

This function is reachable from an ordinary wallet: `WombatPoolHelperV2.depositLP` / `WombatPoolHelper.depositLP` (and `AnkrBNBPoolHelper.depositLP`) are external functions that any user can call, and they call `IWombatStaking(wombatStaking).depositLP(lpToken, _lpAmount, msg.sender)` [3](#0-2) , which internally performs the unchecked mint described above.

### Impact Explanation
If any LP token registered in a pool (`poolInfo.lpAddress`) has a fee-on-transfer/deflationary behavior, `WombatStaking` would receive less LP than `_lpAmount` but would mint the full `_lpAmount` of `receiptToken` to the caller. Since `receiptToken` is subsequently staked 1:1 in `MasterMagpie`/`BaseRewardPool` and used to track withdrawal entitlements, this creates a permanent shortfall between the LP tokens custodied by `WombatStaking` and the total receipt-token claims outstanding, causing insolvency: some users would be unable to withdraw their full entitlement, and the deficit would be paid out of other users' deposited funds.

### Likelihood Explanation
The `pools` mapping and the `lpAddress`/`depositToken` for each pool are registered by the contract owner (admin-controlled onboarding), as seen in the `Pool` struct and `PoolAdded` event [4](#0-3) . Wombat pool LP tokens (`IAsset`) are standard mintable/burnable ERC20 tokens without transfer fees in the currently deployed Wombat pools, so the deflationary-transfer precondition is not met by any token an admin would realistically list. The vulnerability is a genuine code defect (missing balance-delta check), but it requires an atypical token property that the project (per the referenced audit exchange) has already stated it will not support/document rather than fix. Given this depends on a hypothetical/unusual ERC20 behavior for a token whose selection is governed by contract owner, actual exploitability against real, currently-supported assets is low.

### Recommendation
In `depositLP` (and `deposit`), measure the actual LP tokens received via a before/after balance check on `poolInfo.lpAddress`, and mint `receiptToken` based on that measured delta rather than the requested `_lpAmount`, consistent with how `lpReceived` is already computed in `deposit()`.

### Proof of Concept
1. Admin lists a pool whose `lpAddress` is (hypothetically) a fee-on-transfer/deflationary ERC20.
2. User calls `WombatPoolHelperV2.depositLP(1000)`, which invokes `WombatStaking.depositLP(lpToken, 1000, user)`.
3. `safeTransferFrom(user, address(this), 1000)` transfers only 950 tokens to `WombatStaking` due to the token's transfer fee.
4. `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, 1000)` still mints 1000 receipt tokens.
5. The pool helper stakes the full 1000 receipt tokens into `MasterMagpie`, but `WombatStaking` only custodies 950 real LP tokens — a 50-token deficit that other depositors will bear when they attempt to withdraw. [1](#0-0) [3](#0-2)
