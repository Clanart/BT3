### Title
Unswept leftover reward-token balances in `ManualCompound.compound` can be stolen by any later caller - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` claims a caller's pending rewards via `MasterMagpie.multiclaimOnBehalf`, then sweeps the **entire current token balance** of the contract (via `balanceOf(address(this))`) to `msg.sender`, rather than only the amount attributable to that specific call. This mirrors the GoodEntry `RangeManager.initRange`/`cleanup()` bug class: any residual/refunded token balance left in the contract by a prior operation is not returned to its rightful owner and instead becomes claimable by whichever unprivileged user next triggers the sweep path.

### Finding Description
In `compound()`, both the "non-compoundable reward" sweep and the main reward-processing loop compute the amount to move using the live contract balance rather than a delta captured before/after the claim: [1](#0-0)

Exactly as in the GoodEntry report — where `TokenisableRange.init()` refunds unused underlying tokens to `RangeManager`, and `RangeManager.initRange` fails to forward that refund to the rightful party, leaving it to be later swept by an unrelated caller of `cleanup()` — `ManualCompound.compound()` reads `balanceOf(address(this))` for each reward/compoundable token and transfers/converts/locks the *entire* balance to `msg.sender`. If any dust or leftover balance from a previous `compound()` invocation remains in the contract (e.g., a downstream call such as `IConverter.convertFor`, `ILocker.lockFor`, or `ISimpleHelper.depositFor` does not consume 100% of the approved/transferred amount, leaving rounding residue, or a partial failure/short-transfer leaves tokens uncredited to the original caller), that residue is not tracked per-user anywhere in this contract — there is no accounting delta, only a raw balance check. The next unprivileged user who calls `compound()` with the same reward token in `_rewards`/`rewards` will have that stale balance swept into their own transfer/convert/lock call, i.e., they receive value that rightfully belonged to a previous caller's harvested rewards.

### Impact Explanation
This is a theft-of-unclaimed-yield vector: an ordinary wallet that happens to call `compound()` after a leftover-balance event silently receives another user's harvested reward tokens on top of its own, with no signature or authorization from the original claimant. Because the sweep is per-`compound()`-call rather than per-claim (no `before`/`after` balance delta as used correctly elsewhere in the codebase, e.g. `WombatStaking.deposit` and the pool helpers' `_deposit` functions which do compute `afterDeposit - beforeDeposit`), this contract lacks the safeguard that prevents comingling of unrelated balances.

### Likelihood Explanation
Likelihood depends on how reliably `multiclaimOnBehalf` and the downstream `convertFor`/`lockFor`/`depositFor` calls fully zero out the contract's balance for every involved token on every call. Any non-atomic rounding, fee-on-transfer reward token, or a call that reverts/partially executes in a way that still credits `historicalRewards`/claim status upstream but leaves tokens behind, creates the exploitable window; a subsequent unprivileged caller of `compound()` for the same token needs no special timing beyond calling after such an event. I could not fully confirm from the available context whether `multiclaimOnBehalf` and every registered convertor/locker/helper is guaranteed to leave zero residual balance in all cases — this would need further verification (e.g., whether any reward tokens are fee-on-transfer, or whether partial `convertFor` fills are possible).

### Recommendation
Replace all `balanceOf(address(this))` reads in `compound()` with a before/after balance delta scoped to the specific `multiclaimOnBehalf` call (as already done correctly in `WombatStaking._toMasterWomAndSendReward`-adjacent deposit flows and the pool helpers), so that only newly-received tokens attributable to the current caller are swept/converted/locked, and any genuinely stray balance is handled via an explicit, owner-gated sweep function rather than being silently claimable by the next caller.

### Proof of Concept
1. User A calls `compound()` for reward token `T`; downstream `convertor.convertFor(...)` or a fee-on-transfer/rounding effect leaves a small residual balance of `T` in the `ManualCompound` contract instead of fully consuming it.
2. User B (attacker), an ordinary unprivileged wallet with no rewards pending for `T`, calls `compound()` including `T` in `_rewards`/`rewards` list.
3. `receivedBalance = IERC20(T).balanceOf(address(this))` picks up User A's leftover residual balance together with (or instead of) User B's own freshly claimed amount.
4. The entire `receivedBalance` is transferred/converted/locked to `msg.sender` (User B), who thus receives User A's un-claimed leftover yield without authorization.
