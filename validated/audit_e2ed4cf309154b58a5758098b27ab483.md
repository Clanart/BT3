## Analysis

The Kaia `kaiax/gasless` module implements KIP‑247, where a block proposer *lends* gas fees to a sender (via a proposer‑funded `LendTx`) and expects repayment through the `GaslessSwapTx`. Because the lending mechanism trusts the sender's simple, non‑reentrant EOA behavior, the module explicitly restricts eligibility to senders **without contract code**: [1](#0-0) 

This restriction is enforced only once, at **transaction-pool admission time**, against a cached pre-block state snapshot: [2](#0-1) [3](#0-2) [4](#0-3) 

The only place this policy is invoked is `GetCheckBalance()`, called from `TxPool.validateTx` (admission) and `txList.Filter` (periodic re-filtering) — never from the actual state-transition/execution path that applies the transaction in a block: [5](#0-4) 

Meanwhile, Kaia's EIP‑7702 support lets a sender install delegated code on itself via a `SetCodeAuthorization` inside a normal `TxTypeEthereumSetCode` transaction, executed as part of ordinary per‑account nonce-ordered processing: [6](#0-5) 

The existing regression test only demonstrates the intended case where the code was installed in a **previously committed** block (so the pool's cached state already reflects it) — it does not cover code installed by a **not-yet-mined** `SetCodeTx` with an earlier nonce than the `SwapTx`, submitted to the pool at the same time: [7](#0-6) [8](#0-7) 

### Title
Gasless "no-code sender" restriction is a mempool-time-only check, bypassable by ordering a same-block EIP-7702 SetCodeTx before the SwapTx - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The KIP‑247 gasless module's `BalanceCheckLevelAll` "sender code check" — meant to restrict the proposer-funded lending flow to plain EOAs — is validated only against the current (pre-block) chain state at transaction-pool admission time, and is never re-checked at the point the `GaslessSwapTx` is actually executed within the block being built.

### Finding Description
`GetCheckBalance()` decides gasless-tx eligibility by calling `getCurrentHasCode(sender)` against `g.currentState`, a state snapshot cached by the pool, and this is only invoked from `TxPool.validateTx` (on tx submission) and the periodic `txList.Filter` cleanup — both of which run *before* the block containing the sender's other pending transactions is built. There is no re-verification of "no code" at `commitBundleTransaction`/`ApplyTransaction` time in `work/worker.go`.

Kaia's EIP‑7702 (`TxTypeEthereumSetCode`) allows a sender to add delegated code to their own EOA within an ordinary transaction (`applyAuthorization`/`validateAuthorization` in `blockchain/state_transition.go`), processed like any other transaction in strict per‑sender nonce order.

An attacker can therefore:
1. Submit a `TxTypeEthereumSetCode` transaction at nonce `N` that self‑delegates to malicious bytecode.
2. Submit a `GaslessSwapTx` (or `GaslessApproveTx`+`GaslessSwapTx`) at nonce `N+1` before the `SetCodeTx` is mined.
3. At submission time, `getCurrentHasCode(sender)` still returns `false` (delegation hasn't executed yet), so `checkBalanceForSwap`/`checkBalanceForApprove` pass the sender-code gate.
4. When the block is built, ordinary nonce ordering executes the `SetCodeTx` (nonce N) before the `SwapTx` (nonce N+1) in the same block, installing delegated code on the sender *before* the gasless flow (`LendTx`→`ApproveTx`→`SwapTx` bundle) runs.
5. The gasless bundle then executes with a sender that is now, in effect, a smart contract account — precisely the class of account the `ShouldCheckSenderCode` restriction was designed to exclude — while the module's admission-time gate never re-observes this fact.

This is structurally the same class of bug as the referenced TxPermissions issue: an "is this an EOA / not a distinguished actor" check is enforced only at the boundary of externally-submitted-transaction admission, and can be defeated by state changes achieved through other transactions ("internal"/precursor actions) that take effect before the actually-restricted operation executes.

### Impact Explanation
The proposer extends real KAIA value via `LendTx` on the assumption the recipient is a simple EOA that cannot implement arbitrary logic around receipt/repayment of the loan. Bypassing the sender-code gate lets an attacker use delegated contract logic while masquerading as an eligible gasless-swap EOA, undermining the anti-abuse assumption the check exists to enforce and exposing the proposer's lent KAIA and the KIP‑247 accounting (`repayAmount`/`lendAmount` in `kaiax/gasless/impl/getter.go`) to abuse by contract-controlled accounts — a "gasless settlement theft" style impact.

### Likelihood Explanation
The precondition is fully attacker-controlled and requires no privileged access: any address can craft and broadcast a `TxTypeEthereumSetCode` transaction and a subsequent `GaslessSwapTx` with sequential nonces to the public mempool. No validator/consensus collusion, and no cryptographic break, is required — only ordinary nonce sequencing and timing relative to the pool's cached state snapshot.

### Recommendation
Re-validate `ShouldCheckSenderCode` (and ideally the other `checkBalanceForApprove`/`checkBalanceForSwap` conditions) against the state immediately prior to executing the `LendTx`/`ApproveTx`/`SwapTx` bundle inside `ExtractTxBundles`/`commitBundleTransaction`, not only at pool admission, so that code installed earlier in the same block (e.g., via a preceding `SetCodeTx` from the same sender) is detected and the bundle is rejected.

### Proof of Concept
1. Generate a fresh EOA `S` with a starting balance sufficient for the swap flow but no code.
2. Craft `tx1 = TxTypeEthereumSetCode` from `S`, nonce `N`, with `AuthorizationList` self-delegating `S` to attacker-controlled bytecode (mirrors `sendSetCodeTx` helper in `tests/gasless_test.go`, but submitted, not yet mined).
3. Craft `tx2 = GaslessSwapTx` (`SwapForGas` call) from `S`, nonce `N+1`.
4. Submit `tx1` then `tx2` to the pool in quick succession (before `tx1` is mined) — `tx2` passes `checkBalanceForSwap`'s `getCurrentHasCode(S)` check because `g.currentState` still shows `S` as codeless.
5. Allow block building to proceed: nonce ordering executes `tx1` (installing delegated code on `S`) before `tx2` within the same block; the gasless bundle (`LendTx`, optional `ApproveTx`, `SwapTx`) for `S` then executes with `S` now behaving as a smart-contract account, contrary to the `BalanceCheckLevelAll` restriction that was supposed to block it.

func (g *GaslessModule) checkBalanceForApprove(approveArgs *ApproveArgs) error {
	token := approveArgs.Token
	bc := backends.NewBlockchainContractBackend(g.Chain, nil, nil)

	if g.GaslessConfig.ShouldCheckSenderCode() {
		if g.getCurrentHasCode(approveArgs.Sender) {
			return errors.New("sender with code is not allowed")
		}
	}

	if g.GaslessConfig.ShouldCheckToken() {
		tokenContract, err := sc_erc20.NewERC20(token, bc)
		if err != nil {
			return err
		}

		// tx.token.balanceOf(sender) > 0
		tokenBalance, err := tokenContract.BalanceOf(nil, approveArgs.Sender)
		if err != nil {
			return err
		}
		if tokenBalance.Sign() <= 0 {
			return fmt.Errorf("insufficient sender token balance: token=%s, have=%s, want=nonzero", token.Hex(), tokenBalance.String())
		}
	}
	return nil
}

func (st *StateTransition) applyAuthorization(auth *types.SetCodeAuthorization, rules params.Rules) (err error) {
	authority, err := st.validateAuthorization(auth)
	if err != nil {
		return err
	}

	// If the account already exists in state, refund the new account cost
	// charged in the initrinsic calculation.
	if st.state.Exist(authority) {
		// If the account is not AccountKeyTypeLegacy, setcode is not allowed.
		accountKeyType := st.state.GetKey(authority).Type()
		if !accountKeyType.IsLegacyAccountKey() {
			return fmt.Errorf("%w: %v", ErrAuthorizationNotAllowAccountKeyType, accountKeyType)
		}
		st.state.AddRefund(params.CallNewAccountGas - params.TxAuthTupleGas)
	}

	// Update nonce and account code.
	st.state.IncNonce(authority)
	delegation := types.AddressToDelegation(auth.Address)
	if common.EmptyAddress(auth.Address) {
		// Delegation to zero address means clear.
		st.state.SetCodeToEOA(authority, []byte{}, rules)
		return nil
	}

	// Otherwise install delegation to auth.Address.
	// We treat EOA and SCA as separate objects and therefore need to use
	// distinct methods.
	st.state.SetCodeToEOA(authority, delegation, rules)

	return nil
}

func sendSetCodeTx(t *testing.T, chain *blockchain.BlockChain, transactor bind.ContractBackend, sender *TestAccountType) {
	chainID, err := transactor.ChainID(context.Background())
	require.NoError(t, err)
	auth, err := types.SignSetCode(sender.Keys[0], types.SetCodeAuthorization{
		ChainID: *uint256.MustFromBig(chainID),
		Address: common.HexToAddress("0x000000000000000000000000000000000000aaaa"),
		Nonce:   sender.GetNonce() + 1,
	})
	require.NoError(t, err)

	valueMap := map[types.TxValueKeyType]interface{}{
		types.TxValueKeyNonce:             sender.GetNonce(),
		types.TxValueKeyTo:                common.HexToAddress("0x0000000000000000000000000000000000001111"),
		types.TxValueKeyAmount:            common.Big0,
		types.TxValueKeyData:              []byte{},
		types.TxValueKeyGasLimit:          uint64(100000),
		types.TxValueKeyGasFeeCap:         big.NewInt(50000000000),
		types.TxValueKeyGasTipCap:         big.NewInt(50000000000),
		types.TxValueKeyAccessList:        types.AccessList{},
		types.TxValueKeyAuthorizationList: []types.SetCodeAuthorization{auth},
		types.TxValueKeyChainID:           chainID,
	}
	tx, err := types.NewTransactionWithMap(types.TxTypeEthereumSetCode, valueMap)
	require.NoError(t, err)
	signer := types.LatestSignerForChainID(chainID)
	err = tx.SignWithKeys(signer, sender.Keys)
	require.NoError(t, err)

	err = transactor.SendTransaction(context.Background(), tx)
	require.NoError(t, err)

	receipt := waitReceipt(chain, tx.Hash())
	require.NotNil(t, receipt)
	require.Equal(t, types.ReceiptStatusSuccessful, receipt.Status)

	code, err := transactor.CodeAt(context.Background(), sender.Addr, nil)
	require.NoError(t, err)
	sender.Nonce += 2
	t.Logf("setcode complete: code=0x%x", code)
}
