### Title
False "pool reward" detection via parent_coin_info prefix check in `PlotNFT2Wallet.coin_added()` allows forged reward records / stuck claim state - (File: `chia/wallet/plotnft_wallet/plotnft_wallet.py`)

### Summary
`PlotNFT2Wallet.coin_added()` decides whether an incoming coin at the PlotNFT's `p2_singleton_puzzle_hash` is a genuine consensus block reward purely by checking that the first 16 bytes of its `parent_coin_info` equal the genesis-challenge prefix used by `pool_parent_id()` [2](#0-1) , mirroring the reported bug class where existence/authenticity is inferred from an easily-spoofable signal (a `balanceOf()`-style check) rather than a real proof (deployed bytecode / actual reserves).

### Finding Description
`pool_parent_id(block_height, genesis_challenge)` is defined as `genesis_challenge[:16] + block_height.to_bytes(16, "big")` [1](#0-0) . This value becomes the `parent_coin_info` of a legitimate consensus-farmed pool reward coin, and it is only used by the full node/consensus layer to *construct* legitimate reward coins — it is never independently verified against real block history by the wallet.

`PlotNFT2Wallet.coin_added()` treats any coin sent to `self.p2_singleton_puzzle_hash` whose `parent_coin_info[0:16]` matches the genesis-challenge prefix as a genuine pool reward and unconditionally records it via `plotnft2_store.add_pool_reward()` [2](#0-1) . Because `parent_coin_info` is a value the *sender* of a `CREATE_COIN` condition fully controls (it is simply whatever 32-byte value is passed as the coin's parent in the spend that creates it — analogous to attacker-controlled `balanceOf()` state in the EVM report), any wallet user can craft a spend bundle that creates a coin with:
- `puzzle_hash` = the victim's known, publicly-derivable `p2_singleton_puzzle_hash` (computable by anyone from the public `launcher_id`, à la the deterministic UniswapV2 pair address in the report), and
- `parent_coin_info` = `genesis_challenge[:16] + <arbitrary 16 bytes>`.

This coin is not a real reward (it wasn't farmed at that height, and its `parent_coin_info` doesn't correspond to any actual block), yet the check treats it as one, exactly mirroring the reported root cause: inferring existence/authenticity of a privileged entity from a value that "any address can hold/produce" rather than validating real structure (an actual consensus-created coinbase output tied to a genuine farmed block).

### Impact Explanation
This is a denial-of-service / broken-state analog to the reported issue rather than a fund-theft bug: forged "pool reward" records injected into `plotnft2_store` can corrupt the wallet's downstream reward-claim logic (`claim_rewards`/absorb flows depend on this store to identify claimable coins), causing legitimate claim/absorb spend construction to build spends referencing coins that do not exist on-chain as real rewards. When such a forged entry is used to build a spend (analogous to `getPathForTokens()` returning a bogus path), the resulting spend bundle will fail `ASSERT_COIN_ANNOUNCEMENT`/parent-lineage checks at broadcast or block-validation time, reverting the transaction and disrupting the plot-NFT reward-claim UX — the same "legitimate operation breaks because of attacker-planted state at a predictable address" pattern as the source report.

### Likelihood Explanation
Likelihood is limited by the fact that anyone can only *send* a spoofed value to `self.p2_singleton_puzzle_hash` — sending money there is exactly what the puzzle allows by design (it is the public pool-payment address for the singleton) — but the flaw is that the wallet does not perform any further cryptographic verification (no cross-check against `full_node`/consensus block history) that the coin claimed to be a "pool reward" was truly emitted by the genesis-challenge-tied consensus coinbase logic versus fabricated by an ordinary spend that merely reused the same 16-byte prefix. Constructing such a coin requires only a normal spend bundle with a `CREATE_COIN` condition, well within reach of any unprivileged spend-bundle submitter.

### Recommendation
Do not treat the `parent_coin_info[0:16] == GENESIS_CHALLENGE[0:16]` match alone as proof of a genuine pool reward. Cross-verify the coin against the full node/consensus block reward schedule (e.g., confirm a block was actually farmed at the height implied by `parent_coin_info[16:]`, and that the coin's amount matches `calculate_pool_reward(height)`), similar to how `create_absorb_spend()` reconstructs and asserts against `pool_parent_id(height, genesis_challenge)` from a known, externally-validated height rather than trusting an attacker-suppliable parent id at face value [3](#0-2) .
