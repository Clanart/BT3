### Title
`shell.openExternal` scheme check is computed but not enforced, allowing attacker-controlled GitHub API URLs to bypass protocol restriction - (File: `app/src/main-process/main.ts`)

### Summary
The `open-external` IPC handler in the main process derives a lower-cased copy of the requested path and checks whether it starts with `http://` or `https://`, but that computed boolean is used only to decide whether to emit a log line — the result is never used to gate the call to `shell.openExternal(path)`. This mirrors the reported bug class: a security-relevant value is calculated but never accounted for in the control flow that follows.

### Finding Description
In the main process: [1](#0-0) 

```
ipcMain.handle('open-external', async (_, path: string) => {
  const pathLowerCase = path.toLowerCase()
  if (
    pathLowerCase.startsWith('http://') ||
    pathLowerCase.startsWith('https://')
  ) {
    log.info(`opening in browser: ${path}`)
  }

  try {
    await shell.openExternal(path)
    return true
  } catch (e) {
    log.error(`Call to openExternal failed: '${e}'`)
    return false
  }
})
```

The `http(s)` check is computed but its result is discarded after the `if` block — there is no `else`/`return`/`throw` that blocks non-`http(s)` schemes. Whatever `path` is passed in is forwarded verbatim to `shell.openExternal`, regardless of scheme.

This handler is reachable from the renderer through `openExternal` in `app/src/ui/main-process-proxy.ts:146` and ultimately through `Dispatcher._openInBrowser` / `AppStore._openInBrowser`: [2](#0-1) 

Some callers of `dispatcher.openInBrowser` use URLs that originate directly from GitHub API objects without any scheme validation, e.g. check-run `htmlUrl`: [3](#0-2) [4](#0-3) 

`IRefCheck.htmlUrl` is typed as `string | null` and populated straight from the GitHub REST API (`IAPIRefCheckRun`) with no protocol allow-listing: [5](#0-4) 

By contrast, the sandboxed markdown renderer *does* enforce the scheme before invoking the same callback path (`onMarkdownLinkClicked` → `openExternal`): [6](#0-5) 

This shows the codebase's own established mitigation pattern (gate on `/^https?:/`) — the main-process `open-external` handler is the one place where the equivalent check is computed but not enforced, i.e. exactly the "dynamic fee calculated but not accounted for" pattern from the report: a safety check exists in the code but its result never influences execution.

### Impact Explanation
`shell.openExternal` in Electron does not restrict passed URLs to `http(s)`; it hands the string to the OS default-handler resolution. Passing schemes such as `file://`, `res://`, `microsoft-edge:`, `search-ms:`, or Windows UNC-style `\\host\share` paths, or the vendor-specific deep-link schemes registered by other installed applications, can result in local file execution, network share connection with credential leakage (SMB path), or invocation of a vulnerable third-party protocol handler — well documented Electron `openExternal` risk classes. Because a malicious/compromised GitHub or GitHub Enterprise API response (attacker-controlled check-run/status `html_url` field, or any other field flowing to `openInBrowser`) is never scheme-validated before reaching this handler, an attacker who controls repository CI check data or other API-sourced links displayed in Desktop can smuggle a dangerous scheme through a legitimate-looking "View on GitHub" action.

### Likelihood Explanation
Exploitation requires the victim to click a link/button in Desktop (e.g. "View check details," a notification, or similar UI element) that is populated from attacker-influenced API data — no local access, no admin rights, and no pre-existing malware are required. The renderer-side validation exists in one code path (markdown link interception) but not uniformly, meaning any call site that forwards an API-derived URL directly to `dispatcher.openInBrowser` (such as check-run `htmlUrl`) bypasses that protection entirely, and the last line of defense in the main process performs the check for logging purposes only.

### Recommendation
In `app/src/main-process/main.ts`, use the already-computed `isHttpOrHttps` result to gate the call: reject (return `false`/throw) for any `path` that does not start with `http://` or `https://` before calling `shell.openExternal`, mirroring the check already used in `sandboxed-markdown.tsx`. Additionally, validate/allow-list the scheme of any URL sourced from GitHub API objects (e.g. `IRefCheck.htmlUrl`) at the point of use in the UI layer, consistent with the pattern in `sandboxed-markdown.tsx`.

### Proof of Concept
1. A malicious or compromised GitHub/GHE server returns a check-run object whose `html_url` (or equivalent) is set to a non-`http(s)` URI, e.g. `file:///C:/Windows/System32/cmd.exe` or a crafted `search-ms:` / vendor deep-link payload, instead of a normal `https://...` URL.
2. Desktop surfaces this in the CI checks popover / PR checks-failed dialog; `IRefCheck.htmlUrl` is used as-is with no scheme check: see `ci-check-run-popover.tsx:152-169` and `pull-request-checks-failed.tsx:375-390`.
3. User clicks "View on GitHub" → `dispatcher.openInBrowser(url)` → `AppStore._openInBrowser` → `shell.openExternal` (renderer proxy) → main-process `open-external` handler.
4. In the handler, the `http(s)` check computes `false` for the malicious scheme but this result is not used to stop execution; `shell.openExternal(path)` is called with the attacker-supplied string regardless: `app/src/main-process/main.ts:581-597`.
5. The OS resolves and launches the handler for the attacker-chosen scheme with attacker-chosen content, outside of any Desktop sandboxing.
