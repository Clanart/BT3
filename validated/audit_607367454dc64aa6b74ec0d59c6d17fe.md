### Title
OP_RETURN data is omitted from Bitcoin fee and weight accounting - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary

`SignableTransaction::new` adds an arbitrary-data `OP_RETURN` output to the signed transaction, but calculates virtual size and fee using only the payment outputs. [1](#0-0)  Consequently, a transaction containing up to 80 bytes of caller-controlled data can pay substantially less than the requested fee rate and can even fall below Bitcoin's default relay minimum while the code believes it passed that check. [2](#0-1) [3](#0-2) 

### Finding Description

`calculate_weight_vbytes` builds the synthetic transaction's output list exclusively from `payments`, with only an optional change output added afterward. [4](#0-3)  `SignableTransaction::new` nevertheless inserts the `OP_RETURN` into `tx_outs` before invoking `calculate_weight_vbytes(tx_ins.len(), payments, None)`. [5](#0-4)  The change calculation repeats the omission by again passing only `payments` plus the candidate change script. [6](#0-5) 

The `OP_RETURN` output's amount field, compact-size script length, `OP_RETURN`, push opcode, optional `PUSHDATA1`, and payload all contribute to transaction weight, but none is present in either fee estimate. [7](#0-6) [8](#0-7)  Since the final transaction uses `tx_outs` while retaining the underestimated `needed_fee`, `SignableTransaction::fee` reports and pays the underestimated amount. [9](#0-8) [10](#0-9) 

### Impact Explanation

With a change output, the change value is calculated as `input_sat - payment_sat - fee_with_change`, so the signed transaction's actual fee remains the underestimated `fee_with_change` rather than growing to cover the `OP_RETURN` size. [6](#0-5)  The resulting transaction therefore has a lower effective sat/vbyte rate than requested and may be rejected by standard relay policy while producing an otherwise valid signed transaction. [3](#0-2) 

At a one-sat/vbyte rate, an input transaction estimated at roughly 114 vbytes without data can carry an approximately 90-byte `OP_RETURN` output and exceed roughly 200 actual vbytes, while paying only roughly 114 sats. [2](#0-1) [1](#0-0)  This makes requested fee accounting incorrect for publicly supplied `data` and can produce a transaction that is not relayed at the intended or minimum fee rate. [11](#0-10) 

### Likelihood Explanation

Any caller that supplies the documented `data` argument reaches the discrepancy; the constructor permits up to 80 bytes and always inserts that data into the final outputs. [12](#0-11) [2](#0-1)  The under-accounting is deterministic because both the no-change and with-change size calculations omit the already-created `OP_RETURN` output. [13](#0-12) 

The effect is largest relative to the total size when there is one input and few payments, and a large payload can reduce the actual fee rate materially. [14](#0-13) 

### Recommendation

Build fee/weight estimates from the same complete output list used for the signed transaction, including `data`, and test both the no-change and candidate-change variants. [5](#0-4)  Alternatively, extend `calculate_weight_vbytes` with a `data: Option<&[u8]>` argument and construct the identical `OP_RETURN` output inside its synthetic transaction. [15](#0-14)  The `NotEnoughFunds`, minimum-relay-fee, change-dust, and maximum-weight checks should all use the true transaction size after including every output. [16](#0-15) 

### Proof of Concept

```rust
use bitcoin::ScriptBuf;
use serai_bitcoin::wallet::{ReceivedOutput, SignableTransaction};

// `input` is a spendable ReceivedOutput worth 10_000 sats.
let payments = vec![(payment_script, 5_000)];
let change = Some(change_script);
let data = Some(vec![0u8; 80]);

let tx = SignableTransaction::new(
  vec![input],
  &payments,
  change,
  data,
  1, // requested sat/vbyte
).unwrap();

let actual_vbytes = tx.transaction().vsize() as u64;
let actual_fee = tx.fee();

assert!(actual_vbytes > tx.needed_fee());
assert!(actual_fee < actual_vbytes);
```

The assertion follows because `data` is pushed to `tx_outs` before the fee estimate, but `calculate_weight_vbytes` receives only `payments`, not `tx_outs` or `data`. [1](#0-0)  With a change script, the residual output fixes the paid fee to `fee_with_change`, which was computed without the `OP_RETURN`; thus `actual_fee / actual_vbytes` is below the requested one sat/vbyte and potentially below Bitcoin's default relay minimum. [6](#0-5)
