### Title
BIP-340 `Schnorr::verify` never normalizes an odd-Y group key, so it returns "valid" signatures Bitcoin nodes will reject - ([File: networks/bitcoin/src/crypto.rs])

### Summary
The Allo report describes a flag-gated branch (`useRegistryAnchor`) that leaves a required value (`recipientAddress`) at its default, so the function unconditionally reverts downstream — a reachable configuration that silently bricks the protocol. The analogous shape in Serai is in `Schnorr::verify` (`networks/bitcoin/src/crypto.rs:139-150`): BIP-340 has two parity-dependent adjustments — one for the nonce commitment `R` and one for the signing key `A` — but the code only performs the `R` adjustment (`sig.s = conditional_select(&sum, &-sum, needs_negation(&sig.R))`, line 146). The odd-Y `A` branch is missing entirely, so whenever the group key has odd Y, `verify` returns `Some(sig)` whose signature is unconditionally invalid under BIP-340/x-only verification.

### Finding Description
BIP-340 defines the secret key `d` as `n - d` when `has_even_y(P)` is false, because verification is performed against the x-only (even-Y) key. Equivalently, the produced `s` must be negated when the group key is odd.

In `frost_crypto::Schnorr`:

- `Hram::hram` correctly negates the challenge when `R` is odd (`crypto.rs:70-72`), covering the nonce-parity case.
- `verify` negates `s` only when `sig.R` is odd (`crypto.rs:146`). There is no `needs_negation(&group_key)` term anywhere in the algorithm.
- `sign_share` (`crypto.rs:128-136`) delegates to `IetfSchnorr::sign_share`, which computes `share = nonce + c * d_share` using the raw secret share corresponding to the actual (possibly odd) group key.

Concretely, if `group_key = A` is odd, the aggregated signature is `s = r + c·d` where `d·G = A`. A BIP-340 verifier checks `s·G == R_even + c·P_even` with `P_even = -A`. Then `s·G = R + c·A = R_even - c·P_even ≠ R_even + c·P_even` (for `c ≠ 0`), so every signature produced for an odd-Y group key fails on-chain verification.

The only compensation lives outside the algorithm: `tweak_keys` in `wallet/mod.rs:67-74` scales the keys by `-1` when the tweaked group key is odd, and `p2tr_script_buf` returns `None` for odd keys (`mod.rs:80-83`). But `Schnorr` is a public `Algorithm` (`pub use frost_crypto::*`, `crypto.rs:163`) whose doc comment (`crypto.rs:76-83`) states infinity-panic requirements yet never documents that the group key must be even-Y — just as `useRegistryAnchor`'s branch never documented/populated the required field. Worse, `verify` returns `Some(...)`, not `None`: the `AlgorithmSignatureMachine::complete` path (`crypto/frost/src/sign.rs:465-467`) treats the result as a good signature and returns it without ever discovering it is unspendable, exactly mirroring "the function returns/reverts unconditionally and nothing downstream can recover."

### Impact Explanation
Any FROST signing session over Secp256k1 whose group key has odd Y produces a structurally-invalid BIP-340 signature that every Bitcoin node rejects. Since `verify` reports success, the invalid signature is committed into a Bitcoin transaction (e.g., via `TransactionMachine`/send paths in `wallet/send.rs`) and the output becomes unspendable by that signature — funds received to the corresponding address cannot be moved. With ~50% of group keys being odd, any integrator that constructs `Schnorr` without externally negating the key is bricked half the time, matching the report's "core functionality completely bricked and unusable" impact.

### Likelihood Explanation
The odd-Y key state is reachable with public inputs only: the group key parity is determined by the DKG/`ThresholdKeys` output, which any participant or caller configuration can land on; and the `Schnorr` algorithm can be instantiated directly with any `ThresholdKeys<Secp256k1>` (no documented even-key precondition). It does not require a malicious validator — an honest caller following the public API hits it whenever parity is unfavorable. The deterministic failure (always-invalid signature) rather than probabilistic exploitation keeps it in the same Medium band as the original report rather than Critical/High: it is a guaranteed-brick under a common configuration, not a forgery or key recovery.

### Recommendation
Mirror the key-parity adjustment the same way the nonce parity is handled. Either:
- negate `s` when `needs_negation(&group_key)` is true (combining with the `R` parity, e.g. `s = conditional_select(&sum, &-sum, needs_negation(&sig.R) ^ needs_negation(&group_key))`), or
- have `hram`/`sign_share` treat `d` as `n - d` for odd `A`, and document the requirement.

Also document in `Schnorr`'s doc comment (`crypto.rs:76-83`) that the group key must be even-Y (as produced by `tweak_keys`), so callers cannot silently produce unspendable signatures.

Root cause confirmed in code:
- `verify` performs only the `R`-parity fixup: `sig.s = conditional_select(&sum, &-sum, needs_negation(&sig.R))` — `networks/bitcoin/src/crypto.rs:146`
- `hram` handles odd nonce but not odd key — `networks/bitcoin/src/crypto.rs:59-73`
- even-Y enforcement exists only in the optional `tweak_keys`/`p2tr_script_buf` helpers — `networks/bitcoin/src/wallet/mod.rs:67-85`
