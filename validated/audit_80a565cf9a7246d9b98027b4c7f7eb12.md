## Title
`_withdraw()`'s unguarded per-token transfer loop lets a single unretryable token failure permanently lock an order's entire multi-token escrow - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`_withdraw()` releases every escrowed input token for an order commitment in one unconditional loop, calling `IERC20(token).safeTransfer(beneficiary, amount)` for each entry with no failure isolation. Because the order's token list and beneficiary are fixed at placement time and can never be changed, a single permanently-failing transfer (e.g. a blacklist-capable stablecoin rejecting the fixed beneficiary, or a paused/malicious token among the escrowed inputs) makes the whole function revert forever, freezing every other (unrelated, healthy) token escrowed under the same commitment. This is the same bug class as `get_vault_borrowing_power()`: a loop over independently-controlled external calls where one bad element causes total function failure instead of only affecting the one problematic item.

### Finding Description
`_withdraw()` iterates `body.tokens` and transfers each escrowed token to `beneficiary` unconditionally: [1](#0-0) 

`beneficiary` and the commitment's token list are derived from the immutable `order` fields (`order.output.beneficiary` for fills, `order.user` for refunds) and cannot be altered after the order is placed. The function is reached from both cross-chain settlement (`onAccept` → `_withdraw` for `RedeemEscrow`/`RefundEscrow`) and same-chain fills, in `ExtrinsicIntents.sol` and `IntrinsicIntents.sol`: [2](#0-1) 

For any order with multiple escrowed input tokens (`order.inputs.length > 1` — a normal, supported configuration), if even one token's `transfer`/`transferFrom` to the fixed beneficiary reverts permanently (e.g., USDC/USDT-style blacklist hits the beneficiary address, a token pauses transfers, or a malicious/faulty token is one of the escrowed inputs), `safeTransfer` reverts, and the entire `_withdraw()` call reverts. Since this call is invoked from the ISMP `onAccept` path, the host's delivery wrapper deletes the receipt so the message *can* be retried — but retrying re-executes the exact same transfer to the exact same immutable beneficiary with the exact same token, so the failure is not transient and will repeat indefinitely. There is no per-token isolation (no try/catch, no partial-success bookkeeping, no way to skip the poisoned token and still release the others).

### Impact Explanation
All escrowed input tokens for that commitment — including entirely unrelated, healthy tokens that have nothing to do with the failing one — become permanently unreleasable. This is a direct loss/lock of user or solver funds: the user's other escrowed assets on a `RefundEscrow`, or the solver's earned inputs on a `RedeemEscrow`, are stuck forever behind one poisoned token/blacklisted beneficiary. Given the escrow is per-commitment and irreversible once created, there is no governance or user recovery path modeled in this contract to change the beneficiary or exclude the bad token and still release the rest.

### Likelihood Explanation
Multi-token orders are a first-class, documented feature (`order.inputs`/`order.output.assets` are arrays), so this isn't a contrived edge case. Any order that escrows a blacklist-capable stablecoin alongside other assets is exposed the moment the fixed beneficiary is later blacklisted (a routine compliance action outside the protocol's control) — no malicious relayer, prover, or governance action is required, only ordinary token-issuer behavior.

### Recommendation
Isolate per-token transfer failures inside `_withdraw()`'s loop (e.g., wrap each transfer in a low-level call/try-catch and account for undelivered tokens separately, allowing retry or alternate recovery per token) instead of letting one failing transfer revert release of all other tokens under the same commitment. Alternatively, support updating/escaping a poisoned beneficiary or excluding an individual bad token via a recovery path so the rest of the escrow can still be released.

### Proof of Concept
1. User places a cross-chain order with `order.inputs = [TokenA (healthy), TokenB (blacklist-capable stablecoin)]`, `order.output.beneficiary = X`.
2. A solver fills the order; the fill message eventually triggers `onAccept` → `_withdraw()` on the source chain to release `TokenA` and `TokenB` to the solver (or, in cancellation, back to `X`).
3. Before settlement lands, the issuer of TokenB blacklists address `X` (a normal compliance action, no protocol compromise needed).
4. `_withdraw()` iterates `body.tokens`: the `TokenA` transfer would succeed, but iteration order still runs `TokenB`'s `safeTransfer(X, amount)`, which reverts due to the blacklist, per: [3](#0-2) 
5. The whole `_withdraw()` call reverts; the host deletes the receipt for retry, but every retry hits the same permanent blacklist revert.
6. Result: `TokenA`, which has nothing to do with the blacklist, is permanently stuck in escrow under this commitment along with `TokenB`, with no code path to release it separately.
