### Title
Attacker-controlled git push-rejection text is parsed into an unvalidated "Bypass" URL that Desktop opens via `shell.openExternal` - ([File: app/src/ui/dispatcher/error-handlers.ts])

### Summary
The original report is about a smart-contract time-window guard (`isInCreationWindow`) that trusts unvalidated/attacker-influenceable input (`block.timestamp` / missing bounds on `config.marketTimes`) and silently lets the guard pass when it shouldn't. The Desktop analog is a similar "trust the untrusted input, skip validation, and let it flow into a security-relevant action" pattern: Desktop parses the raw stderr text returned by a `git push` rejection (which is fully attacker-controlled if the remote or a proxy in between is malicious) with a regex, and extracts a `bypassURL` field with **no validation of scheme or origin** before handing it to the UI as a clickable link that is opened with `shell.openExternal`.

### Finding Description
When a `git push` is rejected by (what is assumed to be) GitHub's secret-scanning push-protection feature, Desktop intercepts the `DugiteError.PushWithSecretDetected` error and calls `secretScanningPushProtectionErrorHandler`, which in turn calls `extractSecretScanningResults(remoteMessage)`: [1](#0-0) 

The `remoteMessage` string originates directly from the remote's stderr response to a `git push`: [2](#0-1) 

The regex captures a `bypassURL` group from that untrusted text with no scheme/host validation: [3](#0-2) 

That `bypassURL` is stored in `ISecretScanResult` and passed unchanged into `PushProtectionErrorDialog`, where, for secrets marked `requiresApproval`, it is rendered directly as the `uri` prop of a `LinkButton`: [4](#0-3) 

`LinkButton` performs no validation of the URI before invoking `shell.openExternal(uri)` on click: [5](#0-4) 

Just as the Sherlock finding shows a time-window check that can be forced into an always-pass state because the underlying data (timestamp/market hours) is unvalidated, here the "is this really GitHub's secret-scanning bypass URL" check simply doesn't exist — any remote (or MITM proxy sitting between Desktop and the real remote) that returns text matching the regex's expected format (`—— description ——... locations: - commit: <sha> path: <path>:<line> ... https://...`) can substitute an arbitrary URL for the bypass link, and Desktop will render it as if it were a trusted `github.com` "Bypass" action.

### Impact Explanation
Since the `bypassURL` is attacker-controlled and opened via `shell.openExternal` with no allow-listing visible at the `LinkButton` layer, an attacker who controls the remote a victim pushes to (or a network/proxy positioned to rewrite git-over-HTTP(S) responses) can substitute:
- A phishing page mimicking GitHub's sign-in/bypass page, aiming to harvest the victim's GitHub credentials or session/OAuth token, or
- Any other external URI that `shell.openExternal` is willing to hand off to the OS.

This satisfies the "attacker controls ... a git remote/proxy response ... link the user clicks" criterion and the resulting impact class of "credential/token exfiltration" via a spoofed link presented as an official GitHub UI element. I was not able to confirm whether `shell.openExternal`'s underlying implementation in `app/src/main-process/shell.ts` restricts allowed schemes (e.g., blocking `file://` or custom protocol handlers); if it does not, the impact could be more severe (e.g., interacting with Desktop's own registered `x-github-client://` protocol handler or local file access), but this is unverified.

### Likelihood Explanation
Likelihood is high for the core issue and requires no unusual user behavior: pushing to a remote is a routine Desktop action, and the flow only requires the remote (attacker-controlled repo/server, or an on-path proxy) to return stderr text that matches the existing regex format expected of GitHub's push-protection message — something entirely within the attacker's control, matching the "git remote/proxy response" attacker model allowed by this assessment. No admin rights, local access, or prior compromise of the victim's machine is needed.

### Recommendation
- Validate that `bypassURL` (and any other URL parsed out of untrusted git server output) has an expected, allow-listed origin (e.g., `https://github.com/...` or the account's configured GHE `htmlURL`) before rendering it as clickable or passing it to `shell.openExternal`.
- Apply the same origin/scheme validation used elsewhere in the app (see `enterprise-validate-url.ts`) to any URL sourced from git remote responses, not just user-typed enterprise endpoints.
- Consider treating the entire `remoteMessage` as untrusted content and only trust structured fields, not free-form embedded URLs, unless cryptographically tied to the known GitHub API response for the push.

### Proof of Concept
1. Set up a malicious git remote (or a proxy/MITM in front of a legitimate-looking remote) that, on `git push`, rejects the push and returns stderr formatted to match the `secretsRegex` pattern in `extractSecretScanningResults`, e.g.:
   ```
   —— Fake Secret ——
   locations:
     - commit: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
       path: config.js:12
   ... request an exemption ... https://evil.example.com/phishing-page
   ```
2. Victim adds/uses this remote in GitHub Desktop and attempts to push.
3. Desktop's `secretScanningPushProtectionErrorHandler` parses the message, extracts `bypassURL = https://evil.example.com/phishing-page`, sets `requiresApproval = true` (via the "request an exemption" substring check), and shows `PushProtectionErrorDialog`.
4. Victim clicks "Bypass" believing it's the official GitHub-hosted secret-scanning bypass flow; `LinkButton` calls `shell.openExternal('https://evil.example.com/phishing-page')`, opening the attacker's page in the system browser. [3](#0-2) [4](#0-3) [5](#0-4)

/**
 * Extracts secret scanning results from the provided `remoteMessage` string
 * from the git error provided when GitHub Secret Scanning detects a secret on
 * push..
 *
 * This function parses the output of a secret scanning tool to identify
 * secrets, their descriptions, locations in the codebase, and bypass URLs.
 */
function extractSecretScanningResults(
  remoteMessage: string
): ReadonlyArray<ISecretScanResult> {
  const secretsRegex =
    /—— (?<description>.*?) —+[\s\S]*?locations:(?<locationsGroup>(?:\s+- commit: [a-f0-9]{40}\s+path: [\s\S]*?)+).*?(?<bypassURL>https[\s\S]*?) /g

  const matches = [...remoteMessage.matchAll(secretsRegex)]

  const secrets: Array<ISecretScanResult> = []
  if (matches.length === 0) {
    return secrets
  }

  for (const match of matches) {
    if (match.groups === undefined || match.index === undefined) {
      continue
    }

    const { bypassURL, description, locationsGroup } = match.groups

    const locationsRegex =
      /- commit: (?<commitSha>[a-f0-9]{40})\s+path: (?<path>.*?):(?<lineNumber>\d+)/g
    const locationMatches = [...locationsGroup.matchAll(locationsRegex)]

    const locations: ISecretLocation[] = []

    locationMatches.forEach(locationMatch => {
      if (locationMatch.groups === undefined) {
        return
      }
      const { commitSha, path, lineNumber } = locationMatch.groups
      locations.push({
        commitSha,
        path,
        lineNumber: parseInt(lineNumber, 10),
      })
    })

    secrets.push({
      id: bypassURL.split('/').pop() || '',
      description,
      bypassURL,
      locations,
      requiresApproval: !!match.at(0)?.includes('request an exemption'),
    })
  }

  return secrets

export async function secretScanningPushProtectionErrorHandler(
  error: Error,
  dispatcher: Dispatcher
) {
  const e = asErrorWithMetadata(error)
  if (!e) {
    return error
  }

  const gitError = asGitError(e.underlyingError)
  if (gitError?.result.gitError !== DugiteError.PushWithSecretDetected) {
    return error
  }

  const remoteMessage = getRemoteMessage(coerceToString(gitError.result.stderr))
  const secrets = extractSecretScanningResults(remoteMessage)
