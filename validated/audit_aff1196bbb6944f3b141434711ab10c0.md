### Title
Working-directory image diff reads through symlinked paths, allowing off-repo file content to be exfiltrated into the renderer - (File: app/src/lib/git/diff.ts)

### Summary
`getWorkingDirectoryImage` builds the path to read with a bare `Path.join(repository.path, file.path)` and passes it straight to `readFile`, with no check that the resolved path stays inside the repository. If a malicious repository contains a symlink (a `WorkingDirectoryFileChange` whose `path` has an image-like extension but is actually a symlink pointing outside the repo, e.g. to an absolute path elsewhere on disk), Node's `readFile` follows that symlink transparently and returns the bytes of the external target. Those bytes are then base64-encoded and rendered as a data-URI `<img>` in the Diff panel, i.e. content from outside the repository becomes visible in the renderer. [1](#0-0) 

### Finding Description
`getWorkingDirectoryImage` is called from `getImageDiff` whenever the working-directory file is not marked `Deleted`: [2](#0-1) 

and `getImageDiff`'s result is what `app/src/ui/diff/index.tsx`'s `renderImage` consumes to build the `<img>` tag shown in the diff view (per the caller chain named in the question).

The sink itself does not validate that the resolved path stays under `repository.path`:

```
export async function getWorkingDirectoryImage(
  repository: Repository,
  file: FileChange
): Promise<Image> {
  const contents = await readFile(Path.join(repository.path, file.path))
  ...
``` [3](#0-2) 

The codebase already has a purpose-built helper, `resolveWithin`, that resolves a path relative to a root and rejects it (returns `null`) if the *real* (symlink-resolved) path escapes the root, exactly to defend against this class of attack: [4](#0-3) 

There is even a dedicated regression test proving the exact attack primitive works against paths that aren't protected by `resolveWithin`: [5](#0-4) 

`resolveWithin` is used to guard other reads of attacker-influenced, repository-relative paths, e.g. the Copilot conflict-resolution file reader: [6](#0-5) 

and deep-link driven "reveal in Finder/Explorer" handling: [7](#0-6) 

`getWorkingDirectoryImage`, however, was not updated to use this guard, nor were the structurally identical sinks `getResolutionDiff` and `getNewFileContent`: [8](#0-7) [9](#0-8) 

An attacker who authors/pushes a repository (or a branch the victim checks out/fetches) can commit a symlink entry (git blob mode `120000`) named with an image extension (e.g. `evil.png`) pointing to an absolute path outside the working directory (or using `../../` traversal to a sibling location). When the user opens the Changes/Diff view for that path in GitHub Desktop, `getWorkingDirectoryImage` reads through the symlink and the bytes of the external target are base64-encoded and displayed as an `<img>` in the Diff panel — a renderer-visible read of a file outside the repository.

### Impact Explanation
This meets the "read outside the repo" category from the valid-impact list: the victim's Desktop process reads and displays (in the DOM, as a rendered image, and inspectable via devtools/screenshot or, for non-image binary content, still base64-exposed) bytes of an arbitrary file reachable from the process's filesystem permissions, chosen by the symlink target committed by the attacker. The disclosure is silent — it happens automatically once the diff view is rendered for that file, without any special user action beyond viewing the change (which Desktop does automatically when files are listed in Changes).

### Likelihood Explanation
Requires only an attacker-controlled repository the victim clones/fetches/checks out — squarely within scope ("attacker controls a cloned/fetched repository"). No admin rights, local access, or malware needed. On platforms where Desktop honors `core.symlinks` and creates real filesystem symlinks on checkout (macOS/Linux, and Windows with symlink support/Developer Mode or admin), the symlink entry becomes a live filesystem symlink, and the working-directory scan will surface it as a New/Modified `WorkingDirectoryFileChange`; opening its diff triggers the vulnerable code path. The target path is fully attacker-chosen at commit time.

### Recommendation
Route `file.path` through `resolveWithin(repository.path, file.path)` (or equivalent realpath-based containment check) before calling `readFile` in `getWorkingDirectoryImage`, and apply the same fix to the other unguarded sinks (`getResolutionDiff`, `getNewFileContent` in `syntax-highlighting/index.ts`) that read working-directory paths built from `file.path`/`filePath` without containment validation.

### Proof of Concept
1. In an attacker-controlled repository, create `evil.png` as a symlink to a file outside the repo, e.g. `ln -s /Users/victim/Documents/secret.png evil.png` (or a relative traversal like `../../../secret.png`), then `git add -A && git commit`.
2. Victim clones/fetches this repository with GitHub Desktop and it appears (or is checked out) so `evil.png` is a working-directory entry with an image extension.
3. Open the Changes/History view in Desktop and select `evil.png`; the Diff panel calls `getImageDiff` → `getWorkingDirectoryImage(repository, file)`.
4. Unit-test style assertion: call `getWorkingDirectoryImage(repository, file)` directly and assert `current.contents` (base64) matches the base64 of `/Users/victim/Documents/secret.png` rather than any content committed inside the repository — demonstrating the returned bytes originate from outside the repo tree.

export async function getWorkingDirectoryImage(
  repository: Repository,
  file: FileChange
): Promise<Image> {
  const contents = await readFile(Path.join(repository.path, file.path))
  return new Image(
    contents.buffer,
    contents.toString('base64'),
    getMediaType(Path.extname(file.path)),

  )
}

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
