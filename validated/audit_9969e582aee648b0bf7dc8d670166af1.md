## Title
Unconditional eviction accounting in staked connection admission allows one-sided connection churn - (File: streamer/src/nonblocking/simple_qos.rs)

## Summary
`SimpleQos::try_add_connection` prunes a victim connection via `prune_random` and unconditionally records it in `stats.num_evictions_staked` before confirming that the new connection will actually be admitted via `cache_new_connection`. Because `cache_new_connection`'s underlying `ConnectionTable::try_add_connection` independently gates admission on the *attacker's own* per-key `max_connections_per_peer` limit, a staked attacker who is already at their own connection-slot limit can trigger repeated evictions of unrelated legitimate staked peers while their own new connection is rejected every time.

## Finding Description
In `try_add_connection` (`streamer/src/nonblocking/simple_qos.rs:310-346`), when the peer is `ConnectionPeerType::Staked(stake)`: if `connection_table_l.total_size >= self.config.max_staked_connections`, `prune_random(PRUNE_RANDOM_SAMPLE_SIZE, stake)` (`streamer/src/nonblocking/quic.rs:986-1006`) is invoked, which randomly samples entries and evicts the lowest-stake one below `stake`, entirely independent of the attacker's identity. The pruned count is immediately added to `self.stats.num_evictions_staked` at lines 323-325, and only afterward does the code check `total_size < max_staked_connections` and attempt `cache_new_connection` at line 329.

`cache_new_connection` ultimately calls `ConnectionTable::try_add_connection` (`streamer/src/nonblocking/quic.rs:1008-1051`), which computes `has_connection_capacity` from `connection_entry.len() + 1 <= max_connections_per_peer` for the entry keyed by the attacker's own `(remote_addr.ip(), remote_pubkey)`. This check is entirely independent of whatever `prune_random` did — if the attacker already occupies `max_connections_per_peer` slots (an attacker-controlled precondition, default 16 per `DEFAULT_MAX_QUIC_CONNECTIONS_PER_STAKED_PEER` in `streamer/src/quic.rs:44`), the admission fails and `try_add_connection` in `simple_qos.rs` returns `None` — but the prune of an unrelated victim's connection and the stats update have already occurred and are not rolled back.

Existing test coverage (`test_try_add_connection_max_staked_connections_no_pruning_possible`, lines 1035-1044) only checks the case where pruning itself is rejected (all sampled stakes too high); it does not cover the case where pruning succeeds but the subsequent insert fails for reasons unrelated to pruning outcome (own per-peer cap reached), confirming the gap.

## Impact Explanation
This falls under the QUIC/TPU non-RPC remote exhaustion/degradation category. A staked attacker can force repeated eviction of arbitrary other staked peers' connections (any peer whose sampled stake is below the attacker's, chosen at random from the table) without ever succeeding in adding a connection themselves, since their own insertion is independently blocked by their per-peer limit. This is a real, low-cost, repeatable disruption to legitimate validators' QUIC/TPU connectivity, causing them to reconnect and lose in-flight streams — a resource-bound/accounting correctness violation in the connection-table eviction logic, not merely a metrics inaccuracy, since it also alters `staked_connection_table` state (removing the victim's live connection).

## Likelihood Explanation
Requires only a single staked attacker (any nonzero stake) who opens `max_connections_per_peer` connections under their own key (self-imposed, entirely attacker-controlled) and then repeatedly issues new connection attempts. No race condition, no privileged access, and no cooperation from other nodes is needed; the exploit is a straightforward, deterministic sequencing bug in `try_add_connection`.

## Recommendation
Reorder the logic in `try_add_connection` (`streamer/src/nonblocking/simple_qos.rs:310-346`) so that the new connection's own admission feasibility (its per-peer capacity check) is evaluated before performing `prune_random` and before updating `num_evictions_staked`, or roll back the prune/stat update when `cache_new_connection` subsequently fails for a reason unrelated to table capacity.

## Proof of Concept
Extend `test_try_add_connection_max_staked_connections_with_pruning` (`streamer/src/nonblocking/simple_qos.rs:906-974`): configure `max_connections_per_peer: 1`; have the attacker key (`server_keypair2`/`client_keypair2`) first successfully occupy its single slot via one `try_add_connection` call; then issue a further `try_add_connection` from the same attacker key while the table is at `max_staked_connections`. Assert `result.is_none()` (attacker's own insertion fails due to per-peer capacity) while `stats.num_evictions_staked.load(Ordering::Relaxed)` has increased and the victim (`server_keypair1`) entry has been removed from `staked_connection_table`, demonstrating eviction of an unrelated peer occurred despite the attacker's own connection never being admitted.
