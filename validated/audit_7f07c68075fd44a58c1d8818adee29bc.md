# Cross-chain order double-payout via unguarded destination-side cancel overwriting a filled order — (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`ExtrinsicIntents._cancelFromDest` unconditionally overwrites `_filled[commitment]` and dispatches a `RefundEscrow` message to the source chain without first checking whether the order was already filled by a solver. Because fill (`_fillCrossChain`) and destination-side cancel (`_cancelFromDest`) both write to the same `_filled[commitment]` slot and both trigger independent cross-chain withdrawal messages (`RedeemEscrow` vs `RefundEscrow`) against the same source-chain escrow, a permissionless caller can race a solver's legitimate fill with a post-deadline cancel and cause the escrowed input tokens to be refunded to the user even though the solver already delivered the output tokens — a direct loss of funds for the solver, with no compensating mechanism.

### Finding Description
On the destination chain, `_fillCrossChain` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:89-171`) marks the order filled and pays the beneficiary immediately: [1](#0-0) 
then dispatches a `RedeemEscrow` request back to the source chain so the solver can be paid from escrow: [2](#0-1) 

Separately, `_cancelFromDest` allows anyone to trigger a refund once the deadline has passed: [3](#0-2) 

Critically, `_cancelFromDest` does **not** check whether `_filled[commitment]` is already non-zero (i.e., already filled by a solver) before overwriting it and dispatching `RefundEscrow`. Both `RedeemEscrow` and `RefundEscrow` messages independently call the same `_withdraw` routine on the source chain, which only checks that escrow is present, not which party is entitled to it: [4](#0-3) 

Since escrow is decremented to zero on first successful withdrawal, whichever of the two competing cross-chain messages (`RedeemEscrow` from the fill, or `RefundEscrow` from the cancel) lands first on the source chain wins the escrow. Cross-chain delivery for `RedeemEscrow` requires state-proof generation, consensus finality and the ISMP challenge period, giving a meaningful window during which a user (or anyone, post-deadline) can dispatch a competing `RefundEscrow` for the same commitment. If `RefundEscrow` is delivered/finalized first, the user reclaims the input-token escrow on the source chain while the solver has already unconditionally transferred the output tokens to the beneficiary on the destination chain in `_fillCrossChain`. The solver has no recourse: the later-arriving `RedeemEscrow` for the same commitment reverts with `UnknownOrder` once escrow is zeroed by `_withdraw`.

### Impact Explanation
This is a direct loss-of-funds / effectively a double-settlement of the same escrow to the wrong beneficiary: the solver pays out real output tokens on the destination chain but the corresponding input-token escrow is redirected to the user via the unguarded `RefundEscrow` path instead of being paid to the solver via `RedeemEscrow`. No relayer, prover, or admin compromise is required — an ordinary order creator (or, after the deadline, any address) can trigger this by calling the permissionless destination-side cancel path against an order they know has just been (or is being) filled.

### Likelihood Explanation
The attack requires only: (1) a solver filling a cross-chain order, and (2) the attacker calling the destination gateway's cancel-from-destination path for the same commitment before the fill's `RedeemEscrow` message is finalized on the source chain (a window governed by the ISMP challenge period, which can be minutes to hours). Orders with deadlines close to fill time make this trivially timeable by the order creator, and after the deadline the call is fully permissionless. I was not able to fully confirm from the retrieved code whether the public-facing `cancelOrder` entrypoint that calls `_cancelFromDest` adds an additional `_filled[commitment] == address(0)` guard before invoking it (that wrapper function was not returned in the available index); the internal `_cancelFromDest` function itself, as shown, contains no such check. This should be verified directly against the full file before treating the finding as conclusively exploitable end-to-end.

### Recommendation
In `_cancelFromDest` (and in the public `cancelOrder` entrypoint that routes to it), require `_filled[commitment] == address(0)` before allowing the destination-side cancel to proceed, mirroring the guard intent already present in `_fillCrossChain`/`_withdraw`'s "already filled" semantics. This ensures a `RefundEscrow` can never be dispatched once an order has already been filled, closing the race between `RedeemEscrow` and `RefundEscrow` for the same commitment.

### Proof of Concept
1. User places a cross-chain order with a near-term `deadline`.
2. A solver calls the fill entrypoint routing to `_fillCrossChain` at/near the deadline block: output tokens are sent to the beneficiary, `_filled[commitment] = solver`, and `RedeemEscrow` is dispatched to the source chain (pending proof + challenge period).
3. Once `_blockNumber() > order.deadline`, the user (or any address) calls the cancel entrypoint routing to `_cancelFromDest` for the same `commitment`: `_filled[commitment]` is overwritten to the user's address, and `RefundEscrow` is dispatched to the source chain with no dependency on or knowledge of the prior fill.
4. If `RefundEscrow` reaches and is processed by the source chain's `onAccept`/`_withdraw` before `RedeemEscrow` (plausible given independent proof-generation and delivery timing), the escrowed input tokens are transferred back to the user via `evm/src/apps/intentsv2/IntentsBase.sol:390-410`.
5. When `RedeemEscrow` for the same commitment is later processed, `_orders[commitment][token]` is already zero, so `_withdraw` reverts with `UnknownOrder` — the solver never receives compensation for the output tokens already delivered in step 2.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });
