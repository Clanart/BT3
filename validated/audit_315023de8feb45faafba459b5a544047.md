## Title
Silent commit corruption via stale line-indexed diff selection reapplied to a freshly regenerated patch - (File: `app/src/lib/patch-formatter.ts`, `app/src/lib/git/apply.ts`)

## Summary
The Fuji report's broken invariant is: an operation is executed against "current" state (the current provider) while the real state (debt/collateral) has silently drifted to be split across other providers, so a stale reference is used to compute a result that no longer reflects reality, causing silent loss. The GitHub Desktop analog is structurally identical for partial commits: Desktop stages a **stale, line-index-keyed selection** (`DiffSelection`) against a **freshly regenerated diff** of the working directory at commit time, with no check that the two still correspond to the same content.

## Finding Description
When a user makes a partial (line/hunk level) selection in the Changes diff viewer, that selection is stored as a `DiffSelection` on `WorkingDirectoryFileChange`, keyed purely by **absolute line index** (`hunk.unifiedDiffStart + lineIndex`) computed from whatever diff was loaded at selection time [1](#0-0) .

At commit time, `_commitIncludedChanges` takes the cached `workingDirectory.files` (with their possibly-stale `selection` objects) and passes them straight into `createCommit` → `stageFiles` → `applyPatchToIndex` without re-validating the selection against current disk content [2](#0-1) .

`applyPatchToIndex` then fetches a **fresh** diff of the file straight off disk and hands it to `formatPatch` together with the **stale** selection object: [3](#0-2) 

`formatPatch` blindly calls `file.selection.isSelected(absoluteIndex)` against the hunks of this brand-new diff, with no check that the diff it is walking is the same diff the selection was originally derived from: [4](#0-3) 

Desktop's own code acknowledges this exact class of drift elsewhere ("The diff might have changed dramatically since last we loaded it") but only handles the case where a previously-selected line index no longer exists (it prunes it via `withSelectableLines`); it does **not** detect the case where the index is still valid but now refers to semantically different content: [5](#0-4) 

## Impact Explanation
If a tracked file's content changes between the moment the user visually reviews/selects lines to commit and the moment "Commit" is clicked, Desktop can silently stage and commit lines the user never reviewed, or silently drop lines the user did select — without any warning, hash check, or diff-identity verification. This is exactly the "silent corruption of what the user commits or pushes" impact class: the resulting commit's actual diff does not match what was shown/approved in the UI, and the corrupted commit can subsequently be pushed.

## Likelihood Explanation
The window for content drift is real and attacker-influenceable without requiring local/physical access or leaked credentials: opening/checking out an attacker-supplied repository can run `post-checkout`/`post-merge` hooks, or trigger editor/linter file-watchers, that rewrite a tracked file shortly before the user commits. Desktop explicitly supports intercepting and running Git hooks as part of its workflow (`interceptHooks` in `commit.ts`, hook proxy infrastructure in `with-hooks-env.ts`/`hooks-proxy.ts`) [6](#0-5) , confirming that hook-driven file mutation around the commit lifecycle is an in-scope, already-instrumented behavior of the app, not a far-fetched scenario.

## Recommendation
Before calling `stageFiles`/`applyPatchToIndex`, re-diff each file with a pending partial selection and compare it (e.g., via content hash) to the diff the selection was computed from. If they differ, abort the commit for that file and force the user to re-review the new diff rather than mechanically replaying old line indices against new hunks.

## Proof of Concept
1. Open/clone a repository containing a `post-checkout` hook (or an editor/linter file-watcher) that appends a line to a tracked file.
2. In Desktop's Changes view, open the diff and select only specific lines (partial selection) to include.
3. Before clicking "Commit," let the hook/watcher modify the file on disk (no Desktop prompt occurs).
4. Click "Commit" — `_commitIncludedChanges` reuses the stale `selection`; `applyPatchToIndex` regenerates the diff fresh and `formatPatch` applies the old line indices to it.
5. Inspect the resulting commit: its content differs from what was visually selected/approved in step 2, with no warning shown.
