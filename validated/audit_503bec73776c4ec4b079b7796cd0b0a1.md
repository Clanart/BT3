### Title
Attacker-controlled participant index 0 in preprocess set panics the signing node via `unwrap()` on `ThresholdKeys::view` - (File: crypto/frost/src/sign.rs)

### Summary
In `AlgorithmSignMachine::sign`, the caller-supplied `preprocesses` map keys are merged into `included` and passed to `self.params.keys.view(included).unwrap()`. The bounds checks only reject indexes `> n`; a `Participant(0)` index is never rejected before `view` is unwrapped. This mirrors CVE-2025-39709's class: an externally-triggered event reaching code paths before the corresponding state/handler validity has been established, resulting in a crash.

### Finding Description
`crypto/frost/src/sign.rs:290-313` builds `included` from the untrusted `preprocesses` keys plus the local index `multisig_params.i()`. The validation is:

```rust
if u16::from(included[included.len() - 1]) > multisig_params.n() { ... }
for i in 0 .. (included.len() - 1) {
  if included[i] == included[i + 1] { ... }
}
let view = self.params.keys.view(included.clone()).unwrap();
validate_map(&preprocesses, &included, multisig_params.i())?;
```

Only the maximum element is range-checked; `Participant(0)` passes all checks (`validate_map` only verifies presence, not index validity — `crypto/frost/src/lib.rs:50-72`). The `FrostError::InvalidParticipant` message documents the valid domain as `0 < participant <= n` (`crypto/frost/src/lib.rs:32`), so `view`/`lagrange` for participant 0 is not a valid view and `view(...)` returns `Err`/`None`, making the `.unwrap()` panic. A malicious counterparty sends a preprocess under key `Participant(0)`; `read_preprocess` only parses bytes, so the poisoned map reaches `sign` and crashes the node before any cryptographic check rejects it.

### Impact Explanation
An unauthenticated/peer-level party supplying preprocess data can abort the signing process via panic (denial of service of the signer/validator process). Untrusted preprocess bytes and participant-keyed maps are exactly the attacker-controlled surface enumerated for FROST. Equivalent in effect to the kernel bug: a crash caused by a spurious input arriving before the input domain was established.

### Likelihood Explanation
Requires a counterparty able to submit a preprocess message (a co-signer in the threshold set or anyone feeding `sign`/`read_preprocess`-parsed data — the machine indexes `machines[0].read_preprocess` results into the same keyed map in the processors). Any participant-controlled preprocess submitted under index 0 triggers the panic deterministically.

### Recommendation
Reject `Participant(0)` (and any index where `ThresholdKeys::view` fails) before calling `view`: check `u16::from(included[0]) == 0` alongside the `> n` check and return `FrostError::InvalidParticipant`, and replace `view(...).unwrap()` with a fallible propagation. Validate participant index domain at `read_preprocess`/map-ingestion time, i.e., initialize/validate the "handler" (the participant set) before the "interrupt" (the preprocess payload) is registered into `included`.

### Proof of Concept
1. Construct `AlgorithmSignMachine` for a `t`-of-`n` `ThresholdKeys`.
2. Call `machine.sign(preprocesses, msg)` where `preprocesses` is a `HashMap` keyed with `Participant(0)` (plus enough valid participants so `included.len() >= t`), values being valid `Preprocess` encodings.
3. `included` becomes `[0, ...]`, no check rejects the zero index, and `self.params.keys.view(included).unwrap()` panics, crashing the signing routine.

Note: I was unable to read `crypto/dkg/src/lib.rs` internals to confirm `ThresholdKeys::view`/`lagrange` return `Err`/`None` rather than panic internally for index 0 — but either outcome produces a panic on the attacker-controlled path before domain validation, so the finding stands.
