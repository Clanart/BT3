## Analog Found

### Title
Copilot conflict resolution can silently corrupt the committed merge result when its two independent conflict-marker parsers disagree - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Sherlock report's broken invariant is: a value meant to be split across a list of caller-controlled entries (loan provisions) is applied by **count/position** rather than by verified identity, so an attacker who controls the entries can desynchronize the split from its intended target. The `ClaimFacet.sendInterests` bug divides `minInterestsToRepay` by `loan.nbOfPositions` and lets the attacker inflate that count.

The structural analog in this repo is `reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts`. Copilot's conflict-resolution feature extracts conflict hunks from a file (elsewhere, in `app/src/lib/copilot-conflict-context.ts`) to build the prompt ("Conflict 1 of N", "Conflict 2 of N"), sends them to the model, and gets back an **ordered array** of `IHunkResolution` objects with no identifying information beyond position: [1](#0-0) 

`reassembleResolvedFile` then walks the *raw on-disk file content* with its **own, independently implemented** marker-detection regexes and splices in `hunkResolutions[hunkIndex]` purely by the order in which it encounters well-formed marker blocks: [2](#0-1) 

The only safety check tying the two together is `validateResolutionPaths`, which compares the **count** of hunks the model returned against the count originally extracted by the context-building code — it does not verify that `reassembleResolvedFile`'s own independent marker walk finds the same number/order of blocks: [3](#0-2) 

### Finding Description
`reassembleResolvedFile` treats a `<<<<<<<` line as the start of a conflict block only if a later line matches `^={7}$` (a bare `=======`) followed by a line matching `^>{7}(?:\s|$)`; otherwise it is "copied through as regular content": [4](#0-3) 

This marker-detection logic is duplicated independently of whatever logic in `app/src/lib/copilot-conflict-context.ts` originally counted/extracted the hunks that were shown to the model and that `validateResolutionPaths` checks the count against. Because the file content being scanned is **the raw text of an actually-conflicted file coming from a merge/rebase/cherry-pick with a remote branch or PR** — content an attacker fully controls (e.g., a malicious PR whose branch is merged, or any fetched ref that later conflicts with the user's local changes) — the attacker can craft file contents where the two parsers disagree on hunk boundaries while still matching in total *count*:
- Embedding text that looks like `=======` or `>>>>>>> theirs` *inside* one side's own conflicting content, so that `reassembleResolvedFile`'s naive line-by-line scan closes a "block" earlier or later than the hunk boundaries the context/prompt code used.
- Placing extra `<<<<<<<`-looking lines (matched loosely by `^<{7}(?:\s|$)`) inside otherwise unconflicted regions in a way that the context extractor does not treat as a hunk boundary but the reassembly scanner does (or vice versa).

Because `validateResolutionPaths` only compares `resolution.hunks.length` to `expectedCount` (a scalar), and never re-validates against `reassembleResolvedFile`'s own count of blocks it finds when walking the raw text, a mismatch in *where* those N conflict blocks lie is invisible to the guard. The model's per-hunk resolved content is then spliced positionally (`hunkIndex`) into whichever "block" the naive scanner finds next — not necessarily the block the resolution was actually written for.

This mirrors the Kairos bug precisely: a shared numeric total (`nbOfPositions` / hunk count) is the only thing enforced as consistent, while the *individual allocation to entries* (interest per provision / resolved content per marker block) is not verified for correct correspondence, letting an adversarial input (self-created provisions / crafted conflicting file content) desynchronize allocation from intent.

### Impact Explanation
This falls into the "silent corruption of what the user commits or pushes" category. The reassembled content is written directly to the working tree as the resolution and is what the user is expected to review, stage, and commit/push. If hunk resolutions are spliced into the wrong marker blocks, code intended for one side of the conflict could be applied to a completely different, unrelated region of the file (e.g., dropping security-relevant changes, reintroducing removed code, or injecting one side's logic into another function), and the file would no longer contain conflict markers, so it looks fully resolved. This is exactly the kind of silent corruption class called out as valid impact, since the attacker (whoever authored the conflicting branch/PR) indirectly controls the raw file content that both parsers operate on.

### Likelihood Explanation
Exploitability depends on being able to reliably craft file content that causes the two independent parsers to diverge while keeping the reported hunk *count* identical (since `validateResolutionPaths` does check counts). This requires:
- The user must have Copilot conflict resolution enabled and actually run it on a conflict.
- The attacker needs some control of one side of the conflicting content (e.g., a branch or PR merged/rebased against), which is a realistic "cloned/fetched repository" attacker-controlled input per the task's valid-impact criteria.
- Crafting content that causes divergent marker-boundary detection between the (unverified, not directly inspected in this session) hunk-extraction code in `copilot-conflict-context.ts` and `reassembleResolvedFile`'s scanner requires knowledge of both implementations, but the pattern (loose regex `^<{7}(?:\s|$)` / strict `^={7}$` / loose `^>{7}(?:\s|$)`) is visible directly in the shipped source, making it discoverable via review of this file alone.

**Note on verification**: I was not able to fully read `app/src/lib/copilot-conflict-context.ts` (the code that originally extracts/counts hunks and builds the "Conflict N of M" prompt) in this session due to tool-call limits, so I cannot confirm with certainty that its marker-parsing logic differs from `reassembleResolvedFile`'s regexes in a way that's trivially triggerable — this is inferred from the fact that the two are clearly separate, independently-written implementations with only a scalar count cross-check, and from the explicit code comment acknowledging that malformed/stray markers are handled specially in `reassembleResolvedFile` but not further reconciled with the originally-parsed hunk list. A follow-up session with access to `copilot-conflict-context.ts`'s parser would be needed to construct a concrete divergent input and fully confirm exploitability.

### Recommendation
Do not match resolutions to conflict blocks by array order alone. Have `reassembleResolvedFile` use the *same* hunk-extraction routine (or exported hunk boundary offsets) that `copilot-conflict-context.ts` used to build the prompt, so the block the model resolved is guaranteed to be the block that gets replaced — e.g., pass hunk start/end line numbers (or a stable content-based anchor of the original marker block) through `IHunkResolution` and splice by that identity, and fail loudly (not silently pass through) if the reassembly scanner's block count/boundaries don't match the originally-extracted hunks exactly.

### Proof of Concept
Conceptual PoC (not fully verified against `copilot-conflict-context.ts`, see note above):
1. Attacker's branch/PR introduces, inside one side of a conflicting file, a line that itself matches the loose "theirs marker" regex `^>{7}(?:\s|$)` (e.g., a comment or string literal `>>>>>>> ` at the start of a line) without it being a real git conflict marker.
2. When the user merges/rebases against this branch, git produces a real conflict in the surrounding region; the file now contains the attacker's embedded `>>>>>>> `-like line in addition to the genuine markers.
3. `copilot-conflict-context.ts`'s hunk extractor (git-aware, presumably keyed off git's actual `<<<<<<<`/`=======`/`>>>>>>>` conflict regions) reports N real hunks and builds the prompt accordingly; the model returns N resolutions.
4. `reassembleResolvedFile`'s independent line-scanner, walking with its own loose regexes over the raw file, closes a conflict block early at the attacker's embedded fake marker (see loop at [5](#0-4) 
), shifting `hunkIndex` alignment for all subsequent real blocks in the file.
5. `validateResolutionPaths` only checks `resolution.hunks.length === expectedCount` (a total, not per-block boundaries), so this shift passes validation.
6. The reassembled file — with resolutions spliced into the wrong regions — is written out with no conflict markers remaining, and the user commits/pushes it, silently corrupting the merge result.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

// Conflict markers used by reassembleResolvedFile to locate marker blocks.
const reassemblyOursMarker = /^<{7}(?:\s|$)/
const reassemblySeparatorMarker = /^={7}$/
const reassemblyTheirsMarker = /^>{7}(?:\s|$)/

/**
 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *
 * A `<<<<<<<` line that is not followed by both a `=======` separator and
 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved
 */
export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
