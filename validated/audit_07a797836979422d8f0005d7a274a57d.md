### Title
Attacker-controlled participant count in serialized `ThresholdKeys` enables unbounded quadratic Lagrange interpolation and per-share point decompression (CPU DoS) - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `n` (a `u16` fully controlled by the input bytes) and then performs `n` point decompressions for verification shares, and — when the interpolation byte selects `Interpolation::Lagrange` — every subsequent `sign`/`view` computes Lagrange coefficients in O(t²) field operations over an unbounded threshold `t` up to 65535. A ~4 MB attacker-supplied serialization therefore forces ~65535 point decompressions at read time and ~4.3 × 10⁹ field operations per signing attempt, an extreme compute-amplification DoS analogous to feeding a parser truncated input that degenerates into unbounded work.

### Finding Description
In `ThresholdKeys::read`, `n` is read directly from the byte stream with no cap beyond `u16::MAX`:

```rust
let mut read_u16 = || -> io::Result<u16> { ... Ok(u16::from_le_bytes(value)) };
(read_u16()?, read_u16()?, Participant::new(read_u16()?)...)
``` [1](#0-0) 

The reader then unconditionally consumes `n` scalars (`Interpolation::Constant`) and `n` full point decompressions (`read_G`) into a `HashMap` keyed by `Participant(1..=n)`:

```rust
for _ in 0 .. n { res.push(C::read_F(reader)?); }
...
for l in (1 ..= n).map(Participant) {
  verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
}
``` [2](#0-1) 

`ThresholdParams::new(t, n, i)` only enforces internal consistency (`0 < t <= n`, `i <= n`), so `t = n = 65535` with `Interpolation::Lagrange` is accepted. When such keys are later used in `AlgorithmSignMachine::sign`, the `included` set can span all `n` participants:

```rust
let view = self.params.keys.view(included.clone()).unwrap();
``` [3](#0-2) 

Lagrange interpolation computes, for each of the `t` included participants, a coefficient that is a product over all `t-1` other participant indexes — inherently O(t²) field multiplications. With `t = 65535` this is ≈ 4.3 × 10⁹ field operations, before even counting the `n` `read_G` decompressions (each a full point decompression + canonicality re-encode, `crypto/ciphersuite/src/lib.rs:91-100`) at parse time.

### Impact Explanation
Any caller that feeds untrusted bytes into `ThresholdKeys::read` — a case explicitly in scope — can be driven into parsing a 65535-of-65535 Lagrange keyset. The read itself costs ~65535 point decompressions (~128 KB of framing controls ~4 MB of point data plus decompression work), and a single `sign`/`view` invocation with a full signing set burns billions of field operations, effectively stalling the thread indefinitely. This is a pure availability impact: no secret leakage, but an unprivileged party converts a few megabytes of input into multiple orders of magnitude more CPU work, mirroring the stb_image class where a small crafted file produces pathological processing time.

### Likelihood Explanation
Medium. Exploitation requires an integrator that accepts serialized `ThresholdKeys` from an untrusted source (key backup/restore, key-import RPC, or validator-provisioned key material). The bytes needed are modest (two `u16` fields set to 0xFFFF, an interpolation byte of `1`, and ~n·32 bytes of point encodings — which can even be repeating identity-adjacent garbage since `read_G` cost is paid before validity matters, though canonical non-identity points are needed to pass). The O(n²) blowup in Lagrange interpolation is deterministic and not probabilistic. Likelihood is limited by how many deployments deserialize `ThresholdKeys` from attacker-controlled input versus locally generated keys.

### Recommendation
Cap `t`/`n` at deserialization to the maximum validator-set size the protocol actually supports (e.g., a few hundred), rejecting larger values in `ThresholdKeys::read` before allocating or decompressing. Optionally bound `Vec::with_capacity(n)` and the verification-share loop by the same limit, and consider caching Lagrange denominators to reduce the quadratic cost for legitimately large sets.

### Proof of Concept
1. Construct serialized `ThresholdKeys` bytes: `C::ID` header, `t = 0xFFFF`, `n = 0xFFFF`, `i = 0x0001`, interpolation byte `1` (Lagrange), a valid scalar share, then 65535 canonical non-identity point encodings (e.g., `G`, `2G`, `3G`, ... precomputed).
2. Feed to `ThresholdKeys::<C>::read(&mut bytes)` — succeeds and performs 65535 decompressions.
3. Create `AlgorithmMachine::new(IetfSchnorr::ietf(), keys)`, preprocess, and call `sign` with preprocesses for all `n` participants; `self.params.keys.view(included)` computes 65535 Lagrange coefficients each requiring ~65534 field multiplications/inversions ≈ 4.3 × 10⁹ field ops — a hang from ~4 MB of input.
