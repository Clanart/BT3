## Finding

### Title
Spoofable `WWW-Authenticate` header lets a malicious git remote impersonate "GitHub Enterprise" and trigger an unwarranted sign-in/OAuth prompt - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
GitHub Desktop's credential-helper trampoline decides how to treat a remote endpoint (GitHub.com / GitHub Enterprise / generic) partly by trusting the `WWW-Authenticate` response header that Git forwards from the remote server. An attacker who controls any HTTPS git remote the user adds, clones, fetches, or reaches indirectly (submodule URL, LFS endpoint, or a redirected/proxied server) can set `WWW-Authenticate: realm="GitHub"` and cause Desktop to classify their arbitrary server as `enterprise`, which drives Desktop to invoke `promptForGitHubSignIn` for that attacker-controlled endpoint.

### Finding Description
The credential helper trampoline is invoked for the `get` command on every Git network operation (clone/fetch/pull/push/submodule update/LFS) through `createCredentialHelperTrampolineHandler` [1](#0-0) .

`getCredential` first tries to match a known GitHub account by strict origin comparison via `getGitHubCredential`/`findGitHubTrampolineAccount` [2](#0-1) . If no account matches, it calls `getEndpointKind` to classify the endpoint [3](#0-2) .

`getEndpointKind` inspects `wwwauth[...]` credential fields — which are populated directly from the remote server's HTTP response headers that Git relays to the credential helper — and treats any header containing `realm="GitHub"` as sufficient evidence that the host is GitHub Enterprise: [4](#0-3) 

The corrupted value is the `endpointKind` classification (`'enterprise'` vs `'generic'`). This classification is not derived from any Desktop-trusted source (a saved account endpoint, an explicit user enterprise-URL entry via `validateURL`, or a signed API response) — it comes solely from a header value fully controlled by whatever server the user's Git process happens to talk to for that operation. That server does not need to be the origin remote directly; it can be a submodule remote reached transitively during `git submodule update --init --recursive` [5](#0-4) , or a git host reached via a proxy resolved through `envForRemoteOperation`/`getFallbackUrlForProxyResolve` [6](#0-5) .

When `endpointKind !== 'generic'` and no matching account exists, Desktop does not fall back to `generic` credential handling — instead it surfaces a GitHub-branded sign-in prompt for that endpoint: [7](#0-6) 

Existing guards do not stop this path: `isGitHubHost` (network probe) is only reached as a last resort when the `wwwauth[` shortcut isn't hit, meaning the header-based heuristic is the *first-line, unauthenticated* classifier before any legitimacy check is done. There is no validation that the header actually came from an endpoint the user trusts or previously registered as Enterprise.

### Impact Explanation
This lets an attacker who merely controls a git remote (a public repo the victim adds, a compromised/typosquatted mirror, a submodule URL, or a MITM/rogue proxy) cause GitHub Desktop to present its own "sign in to GitHub Enterprise" UI (`ui.promptForGitHubSignIn(endpoint)`) for an attacker-chosen `endpoint` string, with no requirement that the user manually configured that Enterprise host. This is an unauthorized OAuth/account-binding primitive: a user who trusts the Desktop-native sign-in dialog may complete an OAuth/PAT flow believing they're authenticating to a legitimate GitHub Enterprise instance chosen by Desktop's own logic, when the endpoint was actually selected by attacker-controlled response content embedded in a git handshake, not by the user.

### Likelihood Explanation
Triggering the header requires no privileged access — any HTTPS server that answers Git's requests with a crafted `WWW-Authenticate: realm="GitHub"` header (a one-line addition to a git-http-backend or a proxy) will reach this code path the first time Desktop performs any network git operation against it (clone, fetch during background refresh, or transitively via a submodule). No local access, malware, or leaked credentials are required — only that the victim adds or clones from (or has a repo containing a submodule pointing to) the attacker's server.

### Recommendation
Do not use the `WWW-Authenticate` realm string alone to classify a host as GitHub Enterprise. Require corroboration from a source under Desktop's control — e.g., only trust the header hint for hosts already registered by the user as Enterprise accounts, or always perform the authenticated `isGitHubHost(endpoint)` API probe before offering an Enterprise-branded sign-in flow, rather than short-circuiting on header content from an unauthenticated peer.

### Proof of Concept
1. Attacker stands up an HTTP git server (or a submodule host) that, on any authentication challenge, responds with `WWW-Authenticate: realm="GitHub"`.
2. Victim adds/clones this URL in GitHub Desktop, or clones/fetches an unrelated repo that includes this URL as a `.gitmodules` submodule remote, and runs an operation that triggers `git submodule update --init --recursive` [8](#0-7) .
3. Git spawns the credential helper trampoline for the submodule host; `getEndpointKind` sees `wwwauth[...]` containing `realm="GitHub"` and returns `'enterprise'` [9](#0-8) .
4. Since no account exists for that endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)` for the attacker's host [10](#0-9) , presenting a Desktop-native "sign in" affordance for an endpoint the user never configured.

### Note on uncertainty
I was not able to trace the full downstream implementation of `ui.promptForGitHubSignIn` / `trampolineUIHelper` within the indexed portion of the codebase (it wasn't returned by search), so I cannot confirm the exact OAuth/device-flow wording shown to the user in that dialog, only that this code path is reached with an attacker-influenced `endpoint` argument. If more certainty on the exact dialog/OAuth binding behavior is needed, a Devin session with full repository access would be required to inspect `trampoline-ui-helper.ts` and the sign-in dialog implementation in full.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}

export function getFallbackUrlForProxyResolve(
  repository: Repository,
  currentRemote: IRemote | null
) {
  // We used to use account.endpoint here but we look up account by the
  // repository endpoint (see getAccountForRepository) so we can skip the use
  // of the account here and just use the repository endpoint directly.
  if (isRepositoryWithGitHubRepository(repository)) {
    return getHTMLURL(repository.gitHubRepository.endpoint)
  }

  // This is a carry-over from the old code where we would use the current
  // remote to resolve an account and then use that account's endpoint here.
  // We've since removed the need to pass an account down here but unfortunately
  // that means we need to pass the current remote instead. Note that ideally
  // this should be looking up the remote url either based on the currently
  // checked out branch, the upstream tracking branch of the branch being
  // checked out, or the default remote if neither of those are available.
  // Doing so by shelling out to Git here was deemed to costly and in order to
  // finish this refactor we've opted to replicate the previous behavior here.
  if (currentRemote) {
    return currentRemote.url
  }

  // If all else fails let's assume that whatever network resource
  // Git is gonna hit it's gonna be using the same proxy as it would
  // if it was a GitHub.com endpoint
  return 'https://github.com'
}
