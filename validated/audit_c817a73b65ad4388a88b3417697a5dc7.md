## Analysis

The cosign issue is a type-confusion / verification bug: `verify-attestation --type` reports success whenever *any* attestation with a valid signature exists, without confirming the attestation actually matches the requested predicate `--type`. Searching the Kaia codebase for a reachable analog — "a verification function that returns true because a valid signature exists somewhere, without confirming it corresponds to the specific role/type the caller actually needs" — turns up the `ValidateMember` family used by the public `kaia_recoverFromMessage` RPC.

### Title
Public `kaia_recoverFromMessage` RPC reports signature validity without checking the account-key role, enabling role type-confusion - (File: api/api_kaia_transaction.go)

### Summary
`KaiaTransactionAPI.RecoverFromMessage` is a public JSON-RPC method any caller can invoke to check whether a signature over an arbitrary message was produced by a key belonging to a given account. Internally it calls `AccountKey.ValidateMember`, which for `AccountKeyRoleBased` accounts returns `true` if the recovered public key matches **any** of the account's role-specific sub-keys (`RoleTransaction`, `RoleAccountUpdate`, `RoleFeePayer`), with no indication of which role matched.

### Finding Description
`RecoverFromMessage` recovers a public key from the signature and calls `key.ValidateMember(pubkey, address)`: [1](#0-0) 

For a role-based account, `ValidateMember` loops over all sub-keys of every role and returns `true` on the first match, discarding which role owns the key: [2](#0-1) 

The interface doc explicitly states this "any part" semantics: `ValidateMember` returns true if the account type contains the given public key **in any part** of its `AccountKey`: [3](#0-2) 

By contrast, the transaction-execution path (`ValidateSender`/`ValidateFeePayer`) correctly binds validation to the specific role required by the tx type via `GetRoleTypeForValidation` and `accountkey.ValidateAccountKey(..., roleType)`: [4](#0-3) [5](#0-4) 

This confirms the codebase's own design intent: role separation (`RoleTransaction`, `RoleAccountUpdate`, `RoleFeePayer`) is a security boundary — e.g., a `RoleFeePayer` key is meant only to authorize fee payment, not general account ownership, and `RoleAccountUpdate`/`RoleTransaction` keys are deliberately isolated: [6](#0-5) 

`RecoverFromMessage`, however, is a generic, publicly reachable RPC (no role parameter) that collapses this boundary: any caller can present a signature made by any one of the account's role-specific keys (e.g. a lower-trust `RoleFeePayer` key, which may be shared with relayers/fee-delegation counterparties) and the RPC will report it as a valid signer for the account, exactly as the cosign bug reports "verified" because *some* attestation exists rather than the *requested type* of attestation. Any off-chain integrator (exchange, custody service, dApp) relying on this RPC to authenticate "proof of account ownership" before releasing funds or authorizing an action cannot distinguish which role actually signed, and unknowingly accepts signatures from a role never meant to represent full account authority.

### Impact Explanation
This is reachable by any unauthenticated public RPC caller and can lead to authentication/authorization bypass in any system that uses `kaia_recoverFromMessage` as a proof-of-ownership check (e.g., off-chain withdrawal approval, custodial fund release, gasless/fee-delegation counterparty verification). A signature intentionally scoped to a narrow role (`RoleFeePayer`) is accepted as proof of full account control, potentially enabling unauthorized value movement or fund release decisions based on a false-positive "valid signer" result, mirroring the severity class of the cosign advisory (false positive verification with security-relevant scope).

### Likelihood Explanation
Likelihood is moderate-to-high: exploitation requires only that an account use a role-based key (a standard, supported Kaia account key type) with at least one lower-privilege role key (e.g. `RoleFeePayer`) different from `RoleTransaction`, and that some external system trust the RPC's boolean "is a valid signer" result without knowing it conflates all roles. No special privileges or transaction submission is needed — this is a pure read/verify RPC call.

### Recommendation
Add an explicit role parameter to `RecoverFromMessage` (or a variant of it) and have `AccountKeyRoleBased.ValidateMember` accept/validate against a specific `RoleType` rather than iterating over all roles, mirroring the tx-execution path's use of `GetRoleTypeForValidation`/`ValidateAccountKey`. At minimum, document loudly (and return role information) rather than a bare boolean, so integrators cannot mistake a `RoleFeePayer` or `RoleAccountUpdate` signature for full account ownership.

### Proof of Concept
1. Create an account with `AccountKeyRoleBased{RoleTransaction: keyA, RoleAccountUpdate: keyB, RoleFeePayer: keyC}` via `TxTypeAccountUpdate`.
2. Sign an arbitrary EIP-191/KIP-97-prefixed message with `keyC` (the `RoleFeePayer`-only key).
3. Call the public RPC `kaia_recoverFromMessage(address, data, sig, blockNumber)`.
4. Observe it returns the recovered address (success) via `key.ValidateMember(pubkey, address)` returning `true` at [7](#0-6) , identical to what a signature from `keyA` (the primary transaction-authority key) would produce — with no way for the caller to learn that the signature actually came from the fee-payer-only key.

func (a *AccountKeyRoleBased) ValidateMember(recoveredKey *ecdsa.PublicKey, from common.Address) bool {
	for _, rk := range *a {
		if rk.ValidateMember(recoveredKey, from) {
			return true
		}
	}
	return false
}

func GetRoleTypeForValidation(txType TxType) accountkey.RoleType {
	switch txType {
	case TxTypeAccountUpdate, TxTypeFeeDelegatedAccountUpdate, TxTypeFeeDelegatedAccountUpdateWithRatio:
		return accountkey.RoleAccountUpdate
	default:
		return accountkey.RoleTransaction
	}
}
