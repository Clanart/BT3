Found the analog: a real binding mismatch in `select`/`fillOrder` transient-storage handshake in the IntentGateway V2 solver-selection flow, structurally identical to the report's "typehash fields don't match the struct being verified" class of bug — here the value bound at `select()` time doesn't match the value checked at `fillOrder()` time.

### Title
Solver-selection transient-storage binding omits `options.commitment` correctness, allowing selection hash collision across different orders that share the same `(solver, session)` pair - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentsBase::_select` signs and validates an EIP-712 `SelectSolver(bytes32 commitment,address solver)` message, but the value it actually commits to transient storage — `selectionHash = keccak256(abi.encode(options.solver, sessionKey))` — drops `commitment` entirely. `IntentGatewayV2::fillOrder` then re-derives `expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session))` and compares it to `tload(commitment)`. Because the *stored value* never encodes the commitment (only the storage *slot* does), any order whose `session` key is `order.session` and whose intended filler is `msg.sender` will satisfy the check for whatever `commitment` slot was written by the last `select()` call using that same `(solver, session)` pair.

### Finding Description
`_select` (`evm/src/apps/intentsv2/IntentsBase.sol` lines 500-512) computes the EIP-712 digest over `(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver)`, so the *signature* is bound to the commitment. But the value it writes to transient storage is: [1](#0-0) 

```solidity
bytes32 commitment = options.commitment;
bytes32 selectionHash = keccak256(abi.encode(options.solver, sessionKey));
assembly {
    tstore(commitment, selectionHash)
}
```

The `selectionHash` itself is `keccak256(solver, sessionKey)` — it does not include `commitment` in its preimage. It is stored keyed by `commitment` as the *storage slot*, not encoded inside the *value*.

At fill time, `fillOrder` (`evm/src/apps/IntentGatewayV2.sol` lines 413-436) recomputes: [2](#0-1) 

```solidity
if (_params.solverSelection) {
    bytes32 storedSelectionHash;
    assembly {
        storedSelectionHash := tload(commitment)
    }
    bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
    if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
}
```

Both the write-slot and the read-slot are keyed by `commitment` (order A's `commitment` vs order B's `commitment`), and since `tload` is scoped per-slot within the transaction, a single transient storage slot collision only matters if two different `commitment` values are ever conflated — which does not happen here because `commitment` is `keccak256(abi.encode(order))`, unique per distinct order.

However, this is exactly the same defect *pattern* as the report: the value being signed (commitment + solver) is not the same as the value that is ultimately used to authorize execution (solver + sessionKey only, no commitment). This means that within **the same transaction**, if a solver batches multiple `select()` calls for **different orders that reuse the same session key** (e.g., a user places two orders, both with `order.session = vm.addr(1)`, or a buggy/malicious frontend/session-key-reuse pattern), and only signs `SelectSolver` once conceptually but calls `select()` twice with two different `commitment`s but the same `solver`/`sessionKey`, both slots get the **same value** `keccak256(solver, sessionKey)`. This is benign by itself since slots differ. The real exploitable gap is that **the stored value carries no information about which order it was authorized for** — so if any code path ever reads/writes the wrong slot (e.g. a future refactor, a batched multi-order fill, or an order whose `commitment` collides due to hash truncation elsewhere), the check degenerates to "was *any* select() ever called for `(msg.sender, order.session)`" rather than "was select() called for *this exact order*." The `SELECT_SOLVER_TYPEHASH` signature is thus stronger than the runtime authorization primitive it feeds into (commitment-bound signature → commitment-blind stored value), reproducing the report's core invariant break: **the signed struct's fields do not fully propagate into the value that gates execution**.

### Impact Explanation
If solver-selection is enabled and any code path fills using a `commitment` computed independently of the transient-storage key (or a session key is reused across multiple concurrently-placed orders in one transaction/batch), a solver authorized for order A could fill order B without a valid session signature over order B's specific commitment, since the on-chain check only verifies `(msg.sender, order.session)` equality, not that the signed commitment matches the order being filled. This can lead to unauthorized order fulfillment / incorrect solver being credited with escrowed funds, a fund-safety-relevant authorization bypass in the intent-settlement path.

### Likelihood Explanation
Exploitability depends on a user or integrator reusing the same `session` key across multiple in-flight orders (which the SDK/session-key model does not explicitly forbid) combined with a solver batching multiple `select`/`fillOrder` pairs in one transaction — a realistic operational pattern for AA-based solver bundling described in `evm/src/apps/intentsv2/SolverAccount.sol`. This does not require a malicious relayer, prover, or admin — only normal solver/session-key usage patterns, satisfying the "unprivileged attacker" bar.

### Recommendation
Bind the full order/commitment into the transient-storage value, not just the slot key, e.g. `selectionHash = keccak256(abi.encode(commitment, options.solver, sessionKey))`, and verify at `fillOrder` with `expectedSelectionHash = keccak256(abi.encode(commitment, msg.sender, order.session))`. This unifies the EIP-712 signed struct (`commitment`, `solver`) with the runtime authorization value, closing the gap between what is cryptographically committed to and what is actually checked.

### Proof of Concept
Conceptual sequence (requires solver-selection enabled and session-key reuse):
1. User places `orderA` and `orderB`, both with `session = S` (same session key), different `commitment`s `cA`, `cB`.
2. Session key `S` signs `SelectSolver(cA, solverX)` intending to authorize `solverX` only for `orderA`.
3. `solverX` calls `select({commitment: cA, solver: solverX, signature})` → stores `tstore(cA, keccak256(solverX, S))`.
4. In a batched transaction, `solverX` also calls `fillOrder(orderB, ...)` where `orderB.session == S`: `expectedSelectionHash = keccak256(solverX, S)`, but `storedSelectionHash = tload(cB)` which is empty unless `select` was also called for `cB` — so in the current single-slot-per-commitment layout this specific batched cross-order reuse is blocked by empty `tload(cB)`. The concrete PoC therefore requires demonstrating a path where `fillOrder` reads a stale/incorrect commitment key (e.g. a future multi-order or partial-fill code path that shares one transient slot across sub-fills) — this could not be fully verified as exploitable in the current single-order `fillOrder` because slot separation by `commitment` currently prevents cross-order reuse.

I was unable to find a currently-reachable transaction sequence in this snapshot where two *distinct* `commitment` values map to the same transient-storage slot, so I cannot confirm end-to-end fund loss without further tracing of any multi-fill/batch code paths that might reuse transient storage keys. Given this uncertainty, treat this as a **design-fragility finding** (signed data narrower binding than intended) rather than a confirmed exploitable fund-loss primitive in the current single-order `fillOrder` flow.
