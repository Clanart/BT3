### Title
Time-of-check/time-of-use bypass of hookify PreToolUse guardrails via toggling `enabled` on rule files - (File: plugins/hookify/core/config_loader.py)

### Summary
The `hookify` plugin implements a user-defined guardrail system (block/warn rules for Bash and file-edit operations) that is re-read from disk on every single tool invocation, with no session-level caching, no locking, and no tamper-evidence. This mirrors the RocketPool finding: just as a minipool owner could instantaneously switch `RocketMinipoolBase` delegate implementations around a `slash` call to avoid a state flag being set, an agent/session with `Write`/`Edit` access to `.claude/` can instantaneously flip a hookify rule's `enabled: true/false` (or delete/recreate the rule file) immediately before and after a single guarded operation, so the guard is effectively absent exactly when the dangerous action occurs but appears intact before and after — defeating the very purpose of the control while leaving the visible configuration state unchanged.

### Finding Description
`load_rules()` in [1](#0-0)  globs `.claude/hookify.*.local.md` and filters to only `rule.enabled` rules on **every** hook invocation — there is no caching of rule state across a turn, so the enabled/disabled decision is made fresh, from disk, at the exact moment the `PreToolUse` hook fires. The `PreToolUse` executor [2](#0-1)  loads rules and evaluates them per call with no memory of prior state, and any hook error causes it to fail-open (`sys.exit(0)`, operation allowed) as documented at [3](#0-2) .

Documentation explicitly advertises this as a feature: rules "take effect immediately on the next tool use," require "no restart," and can be toggled by simply editing `enabled: true/false` in the frontmatter [4](#0-3) , and the same is repeated for the interactive `/hookify:configure` command [5](#0-4) .

Because the model itself (Claude, acting via the Bash/Edit/Write tools it controls) is the entity that can create and edit these `.local.md` files, an agent operating under adversarial instructions (e.g., indirect prompt injection from a file it read, or a compromised/malicious skill) can:
1. Edit `.claude/hookify.<rule>.local.md`, setting `enabled: false` (or deleting the file) — disabling a `block`/`warn` guard the user configured, e.g., against `rm -rf`, editing `.env`, or exfiltrating secrets.
2. Immediately perform the guarded dangerous action — the `PreToolUse` hook re-reads the rule file at that exact call and sees it disabled, so no block/warn fires.
3. Restore `enabled: true` (or recreate the identical file), so `/hookify:list` and subsequent tool calls show the guard as active again, with no artifact indicating it was ever bypassed.

This is architecturally identical to the RocketPool issue: a controllable "implementation switch" (rule enabled/disabled state, analogous to delegate address) that takes effect instantly and is checked fresh at call time, allowing a single guarded call to be sandwiched between a disable and a re-enable, defeating a security-relevant flag/check without leaving evidence.

### Impact Explanation
Hookify is explicitly positioned as a security/guardrail mechanism ("prevent unwanted behaviors," block dangerous `rm -rf`, warn on secrets in `.env` edits, etc. — see `plugins/hookify/README.md` and `plugins/security-guidance`). If an attacker can inject instructions into the agent's context (a classic and acknowledged threat model for Claude Code — see the hardening note "Hardened the Agent tool against indirect prompt injection via content a subagent read" in the changelog), the agent can transparently disable the guard for exactly the single dangerous operation the guard exists to catch (e.g. destructive `rm -rf`, writing secrets to a committed file, or bypassing a "require tests before stop" rule), then silently restore the rule. This undermines user trust in the guardrail and can result in unauthorized destructive filesystem actions or secret disclosure without any visible trace, matching the "concrete approval bypass / unauthorized shell or file action" impact bar.

### Likelihood Explanation
Likelihood is moderate: it requires (a) the user to have configured hookify rules as their actual enforcement mechanism, and (b) some form of untrusted content influencing the agent's actions (prompt injection, malicious skill/plugin, or a compromised subagent) that specifically knows to toggle the rule file. Hookify is an optional, non-default plugin, and its rules are advisory conveniences rather than a hardened permission-system primitive (unlike `settings.json` `permissions.deny`), so the security expectation on it is lower than on core permission enforcement — but its README and skill docs frame it explicitly as a way to "prevent unwanted behaviors," which sets a security expectation that this design does not meet under adversarial control of the same session that manages the rules.

### Recommendation
- Do not treat `.claude/hookify.*.local.md` as a security boundary that the same agent session is trusted to edit; if hookify is meant to guard against the agent's own actions (including under prompt injection), rule files should not be freely writable by the Bash/Edit/Write tools without a permission prompt, or should be excluded from the agent's own write surface (similar to how `.claude/settings.json` changes are handled more carefully).
- Snapshot/cache the effective rule set at session start (or require an explicit `/reload-hookify`) rather than re-reading from disk on every tool call, so a rule cannot be disabled and re-enabled within the same turn/sandwiched around one operation.
- Log every rule enable/disable transition and every rule-file write to an append-only, tamper-evident audit trail so a "disable → act → re-enable" sequence is detectable after the fact, mirroring the client's fix for the RocketPool issue (moving the flag to an append-only, non-bypassable location).
- Treat edits to hookify rule files themselves as guarded operations (i.e., feed them through PreToolUse hooks/permission prompts) so a single dangerous action can't first neutralize its own guard.

### Proof of Concept
1. User creates `.claude/hookify.block-rm.local.md`:
```
---
name: block-rm
enabled: true
event: bash
pattern: rm\s+-rf
action: block
---
Blocked: dangerous rm -rf command.
```
2. Attacker-controlled content (e.g., a file the agent reads, or a malicious skill) instructs the agent, within the same turn/session:
   - Edit `.claude/hookify.block-rm.local.md` to set `enabled: false`.
   - Run `rm -rf /important/data` via the Bash tool — `pretooluse.py` calls `load_rules(event='bash')` [6](#0-5) , the rule is filtered out because `rule.enabled` is `False`, so `evaluate_rules` never blocks it.
   - Edit the file back to `enabled: true`.
3. `/hookify:list` and any later invocation of `rm -rf` will show the rule as active and blocking, with no record that it was disabled for the one call that mattered.

Note: I was not able to load `plugins/hookify/core/rule_engine.py` lines 1–96 (the tool call for it failed in the final iteration), so the exact JSON shape used for the `block` action's `permissionDecision: deny` output is not fully confirmed from source in this session — this detail should be verified directly in the repository, but it does not affect the core finding, which rests on `load_rules()`'s per-call, uncached, disk-truth `enabled` filtering shown above.

def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)

        except (IOError, OSError, PermissionError) as e:
            # File I/O errors - log and continue
            print(f"Warning: Failed to read {file_path}: {e}", file=sys.stderr)
            continue
        except (ValueError, KeyError, AttributeError, TypeError) as e:
            # Parsing errors - log and continue
            print(f"Warning: Failed to parse {file_path}: {e}", file=sys.stderr)
            continue
        except Exception as e:
            # Unexpected errors - log with type details
            print(f"Warning: Unexpected error loading {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
            continue

    return rules
```

def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)
```
