## Title
Address association marks account as "associated" before balance migration and pubkey setup complete, creating a reentrancy window with inconsistent state - (File: utils/helpers/associate.go)

### Summary
`AssociationHelper.AssociateAddresses` writes the Sei↔EVM address mapping via `SetAddressMapping` *before* it finishes setting the account pubkey and migrating balances from the cast address. This mirrors the Zephyr L2CAP bug class: an entity becomes externally "found"/dispatchable (there, a channel reachable via `bt_l2cap_br_lookup_rx_cid`; here, an address pair reachable via `GetEVMAddress`/`GetSeiAddress`) before its associated setup work — pubkey assignment and balance migration — has completed. [1](#0-0) 

### Finding Description
`AssociateAddresses` performs, in order:
1. `p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)` — this immediately makes `GetEVMAddress(ctx, seiAddr)`/`GetSeiAddress(ctx, evmAddr)` report the pair as associated.
2. Set pubkey on the Sei account if missing.
3. `p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)` — moves spendable coins and wei balance from the cast address (`sdk.AccAddress(evmAddr[:])`) to the real `seiAddr`. [2](#0-1) 

`MigrateBalance` calls `bankKeeper.SendCoins` and `SendCoinsAndWei`, which in the Sei Cosmos SDK bank module can synchronously invoke registered bank hooks (e.g., tokenfactory "before-send" hook contracts) as part of the transfer. If a hook contract is registered on a denom held by the cast address, that hook executes *while* the association mapping is already live but before the pubkey is set and before the wei portion of the balance has been migrated (usei is sent first, then wei separately). Any code executed in that window — including code that calls back into `GetEVMAddress`/`GetSeiAddress` or reads the account's balance — observes a half-initialized account: associated, but without a pubkey and with only part of its funds moved over.

This is the same bug shape as CVE-2026-15460: an object becomes "findable"/dispatchable by external callers (a channel by CID, here an address by association lookup) while internal setup fields it depends on (`rx.mode`/`rx.mps` there; pubkey/wei balance here) are not yet initialized, and the object is reachable and actionable from that half-initialized state.

This code path is reachable by any unprivileged user: `AssociateAddresses` is invoked from `EVMPreprocessDecorator.AnteHandle` (x/evm/ante/preprocess.go) automatically for every un-associated EVM sender, and from the public `addr` precompile's `associate`/`associatePubKey` methods, both directly callable by any transaction sender. [3](#0-2) [4](#0-3) 

### Impact Explanation
An attacker who controls a tokenfactory denom's before-send hook contract, and holds balance of that denom under their own cast address (`sdk.AccAddress(evmAddr[:])`), can trigger the association flow (e.g., by sending any EVM tx from an unassociated key) and have their hook contract execute reentrant logic mid-migration. At that point the hook can observe/act on an account that is reported as "associated" by `GetEVMAddress`/`GetSeiAddress` but has not yet received its wei balance and has no pubkey set — potentially enabling double-counting or diversion of the wei-denominated portion of funds during the migration, i.e., fund loss/duplication tied to the association process.

### Likelihood Explanation
Requires a bank hook to be registered on a denom (tokenfactory before-send hooks are a standard, permissionless-ish feature) and requires the attacker's own cast address to hold a balance in that denom, both of which are within reach of a normal user setting up their own attack scenario, then simply triggering their first EVM transaction to run the association path.

### Recommendation
Reorder `AssociateAddresses` so `SetAddressMapping` (and any pubkey assignment) is written only after `MigrateBalance` completes successfully, or perform the balance migration under a mechanism that prevents reentrant reads of `GetEVMAddress`/`GetSeiAddress` from observing a partially migrated account (e.g., stage the mapping write behind a completion flag, or move the mapping write after `MigrateBalance` returns without error).

### Proof of Concept
1. Register a tokenfactory denom `factory/attacker/evil` with a before-send hook contract that, when invoked, queries `getEvmAddr`/`getSeiAddr` (via the `addr` precompile) for the account currently being migrated.
2. Fund the attacker's cast address (`sdk.AccAddress(evmAddr[:])`) with both `usei`-denominated `evil` tokens and a wei balance.
3. Submit any EVM transaction from the unassociated EVM key so `EVMPreprocessDecorator.AnteHandle` calls `AssociateAddresses`.
4. During `MigrateBalance`'s `SendCoins` call for `evil`, the hook fires while `SetAddressMapping` has already executed but wei has not yet moved; the hook contract observes the account as associated and interacts with/exfiltrates value based on that inconsistent intermediate state.

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)
}
