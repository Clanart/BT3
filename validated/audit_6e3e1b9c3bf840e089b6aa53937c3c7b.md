### Title
Incomplete UTF-8 validation for Cord-backed string fields in `TcParser::MpVerifyUtf8` - (File: `src/google/protobuf/generated_message_tctable_lite.cc`)

### Summary
The mini-parse (`Mp`) string-field parsing path in the table-driven C++ parser (`TcParser::MpString`) validates UTF-8 for scalar string fields via `MpVerifyUtf8`, which is overloaded for the two possible field storage representations: `absl::string_view` (used for `ArenaStringPtr`/`MicroString` storage) and `absl::Cord` (used for `ctype=CORD` fields). The `string_view` overload actually performs `utf8_range::IsStructurallyValid` when `xform_val == kTvUtf8`, but the `Cord` overload unconditionally `return true;` for every `xform_val` value and only asserts the expected invariant (`xform_val == 0`) via `ABSL_DCHECK_EQ`, which compiles to a no-op in release (`NDEBUG`) builds.

### Finding Description
```cpp
bool TcParser::MpVerifyUtf8(const absl::Cord& wire_bytes,
                            const TcParseTableBase* table,
                            const FieldEntry& entry, uint16_t xform_val) {
  switch (xform_val) {
    default:
      ABSL_DCHECK_EQ(xform_val, 0);
      return true;
  }
}

Compare with the string overload, which enforces the invariant when `xform_val == kTvUtf8`:
```cpp
bool TcParser::MpVerifyUtf8(absl::string_view wire_bytes, ...) {
  if (xform_val == field_layout::kTvUtf8) {
    if (!utf8_range::IsStructurallyValid(wire_bytes)) { ... return false; }
    return true;
  }
  return true;
}
``` [2](#0-1) 

`MpString` dispatches to whichever overload matches the field's storage representation, including the `kRepCord` case, and unconditionally trusts the returned `is_valid` flag to decide whether to reject the parse:
```cpp
case field_layout::kRepCord: {
  ...
  ptr = InlineCordParser(field, ptr, ctx);
  if (!ptr) break;
  is_valid = MpVerifyUtf8(*field, table, entry, xform_val);
  break;
}
...
if (ABSL_PREDICT_FALSE(ptr == nullptr || !is_valid)) {
  PROTOBUF_MUSTTAIL return Error(PROTOBUF_TC_PARAM_NO_DATA_PASS);
}
``` [3](#0-2) 

This mirrors the reported OP Contracts Manager bug class exactly: the failed invariant ("UTF-8 must be validated for `kTvUtf8` string fields") is only checked along one of the equivalent code paths (`string_view` storage) and is silently assumed — rather than verified — to be unreachable along the other equivalent path (`Cord` storage). The "safety net" (`ABSL_DCHECK_EQ(xform_val, 0)`) is analogous to the report's suggestion to "ensure all contracts have the same address" — it is a developer-time assumption, not a runtime-enforced invariant, and it evaporates in release builds.

### Impact Explanation
If the field-layout generator (mini table construction) ever produces a UTF-8-validated (`kTvUtf8`) field entry for a `kRepCord`-represented field — e.g., a schema declaring a proto3 `string` field with the `ctype=CORD` option, which is a legitimate, trusted-schema combination that the wire-format layer is expected to support (the `string_view` overload proves the framework anticipates `kTvUtf8` xform values reaching string-kind fields) — an ordinary client sending a bounded, otherwise well-formed Protobuf message with structurally invalid UTF-8 bytes in that field would have those bytes silently accepted into the `Cord`, instead of the parse being rejected as required by proto3 string semantics. This breaks the UTF-8 validity guarantee that downstream code (string processing, serialization, security-sensitive comparisons) relies on for `string` fields, and is a real, if narrow, integrity gap in the wire-format layer — analogous in kind (not magnitude) to the OPCM finding: verification exists but only covers one of several equivalent representations.

### Likelihood Explanation
Medium-to-low likelihood in practice: it requires a trusted schema/generator configuration that produces a `kTvUtf8`-xformed field entry backed by Cord storage. I was not able to conclusively confirm, within the available searches, whether the current C++ code generator (`compiler/cpp/field_generators/string_field.cc`, `generated_message_tctable_gen.cc`) ever actually emits such a combination for user-facing proto3 string fields with `ctype=CORD`, or whether `ctype=CORD` is restricted to `bytes`/proto2 optional fields where UTF-8 validation is never requested (which would make `xform_val` always `0` and the current code technically correct, just fragile). This is the key open question that could not be fully resolved in the time available; further investigation into `generated_message_tctable_gen.cc`'s field-entry construction for `kRepCord` combined with `kTvUtf8` would be needed to definitively prove or disprove reachability.

### Recommendation
Make `TcParser::MpVerifyUtf8(const absl::Cord&, ...)` perform the same UTF-8 validation as the `string_view` overload when `xform_val == kTvUtf8` (e.g., by validating over the flattened/iterated Cord bytes), rather than relying on a debug-only assertion to guarantee that this code path is never exercised with UTF-8-required fields. This closes the gap regardless of whether the generator currently produces such field-entry combinations, and prevents future generator changes from silently reintroducing the missing check — directly mirroring the report's own recommendation to check all equivalent paths rather than assuming they must agree.

### Proof of Concept
Conceptual reproduction (bounded, trusted-schema, public-API):
1. Define a trusted `.proto` schema with a `string` field configured with `ctype = CORD` on a proto3 message (implicit presence, UTF-8-validated).
2. If the code generator emits a mini table field entry for this field with `rep == kRepCord` and `xform_val == kTvUtf8` (the specific detail I could not fully confirm from the generator source in this pass), construct a minimal wire-format payload: a length-delimited field with the correct tag/wire type whose payload bytes are not structurally valid UTF-8 (e.g., a lone continuation byte `0x80`).
3. Parse this payload via the public `MessageLite::ParseFromArray`/`ParseFromString` API using the generated message class.
4. Expected (per proto3 UTF-8 contract): parse should fail (`false`)/mark the field invalid, exactly as it would for the equivalent `string_view`-backed field.
5. Actual (per `MpVerifyUtf8(const absl::Cord&, ...)` unconditionally returning `true`): parse succeeds and the invalid UTF-8 bytes are stored in the `Cord` field, assuming the field-entry combination described above is reachable through the generator — a point that requires further confirmation in the generator code before this can be treated as a confirmed, exploitable defect rather than a defensive-coding gap.
