### Title
`SignableTransaction::new` omits the OP_RETURN output from the weight/vbytes used to compute the fee and change — the emitted transaction is larger than measured, so the actual fee rate is silently lower than requested and can fall below the relay minimum - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The bug class in the external report is a getter returning a quantity in the wrong denomination (share count used where an asset amount was required). The Serai analog lives in `SignableTransaction::new`: the transaction actually constructed contains an extra output (the `OP_RETURN` data output pushed at send.rs:194–202) which is *not* included in the `payments` list passed to `calculate_weight_vbytes` at send.rs:204 and send.rs:225–226. The computed `vbytes`/`needed_fee` therefore describe a smaller transaction than the one signed and broadcast — a size "denominated" in the wrong transaction shape, directly mirroring "balance denominated in shares used as assets".

### Finding Description
`SignableTransaction::new` builds `tx_outs` including the OP_RETURN output (send.rs:193–202), but fee/size accounting is done via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` and `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (send.rs:204, 225–226). `calculate_weight_vbytes` reconstructs a template `Transaction` whose `output` vector is built solely from `payments` plus the optional change output (send.rs:85–99). The `data`/`OP_RETURN` output is never part of that template.

Consequences, all derived from the same root cause:

1. `needed_fee = fee_per_vbyte * vbytes` (send.rs:206) is computed over a vbyte count that excludes the OP_RETURN output (up to ~80 bytes of data + ~10 bytes of output overhead ≈ up to ~90 vbytes).
2. The `TooLowFee` check at send.rs:211 compares the same underestimated `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the same underestimated `vbytes`, so it is self-consistent and cannot catch the error.
3. The change value is `input_sat - payment_sat - fee_with_change` (send.rs:228), again with `fee_with_change` too small, so change is over-credited by exactly the missing fee.
4. The actual fee paid is `sum(inputs) - sum(outputs)` (send.rs:138–141), which equals the underestimated `needed_fee`. Since the real serialized transaction is larger than the template, the *effective* sat/vbyte rate is below `fee_per_vbyte`, and can drop below `DEFAULT_MIN_RELAY_TX_FEE`.

### Impact Explanation
When `data` (untrusted/caller-supplied bytes, up to 80 bytes per the check at send.rs:171) is specified, the produced transaction pays a fee rate lower than the caller requested, and potentially below the network's minimum relay fee. A standard Bitcoin node will reject such a transaction (`min relay fee not met`), leaving the spend unbroadcastable — the inputs are locked into a constructed transaction that cannot confirm as built. Even when it does relay, the signer pays less than the intended fee rate without any indication, and `needed_fee()`/`fee()` report the wrong number relative to the real transaction size. This is an incorrect fee formula reachable purely through the `data: Option<Vec<u8>>` argument to the public constructor.

### Likelihood Explanation
Any caller passing `Some(data)` hits the path; the fee shortfall is `fee_per_vbyte * (OP_RETURN output size)` which is deterministic, not probabilistic. It only manifests when `data` is used, and only crosses the relay boundary when the shortfall pushes the effective rate below 1 sat/vbyte — most likely at low `fee_per_vbyte` values (e.g., 1 sat/vbyte, the floor enforced by `median_fee`'s `fee.max(1)`). Severity is Medium: fund loss is limited to stuck/delayed transactions and mispriced fees, not theft, but it is a silent, deterministic miscalculation of a security-critical quantity.

### Recommendation
Include the OP_RETURN output in the template transaction used by `calculate_weight_vbytes`. Concretely, either:
- Pass the fully-built `tx_outs` (or a `(ScriptBuf, u64)` list including the OP_RETURN entry) into `calculate_weight_vbytes` instead of `payments`, or
- Add a `data_size: usize` parameter to `calculate_weight_vbytes` and push a zero-valued `TxOut` with `ScriptBuf::new_op_return` of the correct length into the template.

Apply the same fix to both call sites (send.rs:204 and the change-aware call at send.rs:225–226) so `needed_fee`, the `TooLowFee` check, the `NotEnoughFunds` check, and the change computation all reflect the transaction actually signed.

### Proof of Concept
Conceptual trace (all line numbers in `networks/bitcoin/src/wallet/send.rs`):

```text
// Caller constructs:
SignableTransaction::new(inputs, &payments, change, Some(vec![0xAA; 80]), fee_per_vbyte = 1)

// send.rs:194-202 — tx_outs now contains payments + OP_RETURN output (~91 bytes:
// 8-byte value + ~1-byte script len + OP_RETURN opcode + push opcode + 80 bytes)

// send.rs:204 — vbytes computed WITHOUT the OP_RETURN output:
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
// inside calculate_weight_vbytes (send.rs:85-99): tx.output = payments only

// send.rs:206 — needed_fee = 1 * vbytes  (missing ~91 vbytes of fee)
// send.rs:211 — TooLowFee check: 1*vbytes >= 1000*vbytes/1000  → passes
// send.rs:228 — change = input_sat - payment_sat - needed_fee  (change ~91 sats too large)
// Final tx (send.rs:245-255) includes the OP_RETURN output → real vsize = vbytes + ~91
// Effective rate = needed_fee / real_vsize < 1 sat/vbyte → below DEFAULT_MIN_RELAY_TX_FEE
// → node rejects broadcast; fee()/needed_fee() report a fee inconsistent with tx size
```

A regression test mirroring `networks/bitcoin/tests/wallet.rs::test_send` but with `data = Some(vec![..; 80])` would show `tx.needed_fee() != tx.vsize() * FEE` (the invariant asserted at tests/wallet.rs:269 fails) and `send_raw_transaction` failing the relay check.
