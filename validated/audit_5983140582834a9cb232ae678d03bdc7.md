### Title
Unchecked u64 accumulation/addition of payment amounts makes the insufficient-funds guard misfire, corrupting change/fee accounting and producing an over-issued transaction for signing — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` accumulates attacker-influenced payment amounts into a `u64` `payment_sat` and then performs unchecked `u64` additions (`payment_sat + needed_fee`, `payment_sat + fee_with_change`) before the `checked_sub` that guards the change output. When the addition wraps, the solvency/`NotEnoughFunds` check and the change-creation check evaluate against a wrapped value, so the condition that should reject or correctly account the remainder never fires as intended — the exact same bug class as M-15 (a guard made unsatisfiable/misfiring by incorrect handling of a numeric conversion, silently skipping the accounting branch). The result is a `SignableTransaction` whose outputs can exceed its inputs, which is then signed by the FROST machines, and whose `fee()`/`needed_fee()` accounting diverges from reality (or panics via underflow).

### Finding Description
`payment_sat` is a plain wrapping `u64` sum of the `(ScriptBuf, u64)` payment amounts: [1](#0-0) 

The solvency check uses an unchecked addition: [2](#0-1) 

and the change branch also adds unchecked before `checked_sub`: [3](#0-2) 

In release builds these `u64` additions wrap. If the caller (building a withdrawal/spend from out-instructions, i.e. attacker-influenced transaction data the validator set signs) supplies payment amounts whose sum is near `u64::MAX`:

- `payment_sat + needed_fee` wraps small ⇒ `input_sat < ...` is false ⇒ `NotEnoughFunds` never triggers even though the payments vastly exceed the inputs.
- `payment_sat + fee_with_change` wraps ⇒ `input_sat.checked_sub(wrapped)` returns `Some(large_value)` ⇒ a change output credited `value` is added, so `tx.output` totals exceed `sum(inputs)`. The transaction object is then signed by `TransactionSignMachine::sign`/`TransactionSignatureMachine::complete` (send.rs lines 355-398, 413-428).
- `fee()` computes `sum(prevouts) - sum(outputs)` with a raw `u64` subtraction, so it underflows/panics, and `needed_fee` no longer reflects the true fee — i.e., the accounting the caller relies on is wrong.

This mirrors M-15 structurally: an arithmetic guard meant to reconcile accounting is made unreachable/misfiring by incorrect integer handling, so the accounting branch either never fires or fires on a corrupted value.

### Impact Explanation
- Inaccurate fee/change accounting: `fee()` underflows and `needed_fee` diverges from the actual fee the signed transaction would pay; change can be credited `value` that was never actually available, so downstream accounting that trusts `SignableTransaction`/`fee()` is wrong.
- Signing of a malformed transaction: a transaction whose outputs exceed its inputs is still passed through `multisig`, `preprocess`, `sign`, and `complete`, consuming FROST preprocess/signing rounds for a transaction Bitcoin will reject — an attacker-influenced payment amount can waste/burn signing sessions and panic nodes that call `fee()`.

### Likelihood Explanation
Reachability requires the transaction builder to place attacker-influenced amounts into `payments` without an upstream balance check bounding the sum below `u64::MAX - fee`. The inputs (`ReceivedOutput`s) come from the Scanner's real UTXOs, so honest callers wouldn't hit this, but an out-instruction carrying a crafted `u64` amount reaches `SignableTransaction::new` as-is; nothing in the constructor bounds `payment_sat`. That makes this a Medium-severity analog: it needs a specific (but attacker-reachable) numeric edge, not collusion or key access.

### Recommendation
Use checked/saturating arithmetic for all aggregations and additions of amounts:

```rust
let payment_sat: u64 = payments.iter().try_fold(0u64, |acc, p| acc.checked_add(p.1))
  .ok_or(TransactionError::TooMuchData)?; // or a dedicated Overflow variant

let needed_total = payment_sat.checked_add(needed_fee)
  .ok_or(TransactionError::NotEnoughFunds { inputs: input_sat, payments: payment_sat, fee: needed_fee })?;
if input_sat < needed_total { ... }

if let Some(value) = input_sat
  .checked_sub(payment_sat)
  .and_then(|r| r.checked_sub(fee_with_change)) { ... }
```

Also make `fee()` use `checked_sub` (or `saturating_sub`) and/or assert `sum(outputs) <= sum(inputs)` invariant before constructing `SignableTransaction`, so a mis-accounted transaction can never reach the signing machines.

### Proof of Concept
```rust
// networks/bitcoin/tests or a unit test over SignableTransaction::new
let inputs = vec![received_output_with_value(10_000)]; // 10k sats real UTXO
let payments = vec![
  (script_a.clone(), u64::MAX - 1000),
  (script_b.clone(), 2000), // payment_sat wraps to ~ 999
];
// payment_sat + needed_fee wraps < input_sat -> NotEnoughFunds guard never fires
// checked_sub(payment_sat + fee_with_change) returns Some(...) -> change credited wrongly
let tx = SignableTransaction::new(inputs, &payments, Some(change_script), None, 10).unwrap();
assert!(tx.fee() /* underflows/panics or returns garbage */);
// tx.transaction().output total > 10_000 sats yet it is signed by TransactionMachine
```
