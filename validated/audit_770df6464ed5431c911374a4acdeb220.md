### Title
`SchnorrAggregate::verify` accepts the empty/zero signature when `keys_and_challenges` is empty — (`crypto/schnorr/src/aggregate.rs`)

### Summary
Analogous to the external report (two redeem inputs both allowed to be zero, producing a silent no-op success), `SchnorrAggregate::verify` performs no check that at least one signature was actually aggregated. When `self.Rs` and `keys_and_challenges` are both empty and `s == 0`, the multiexp reduces to `(0 * G) == identity`, so `verify` returns `true` for a signature that attests to nothing.

### Finding Description
`SchnorrAggregate::read` reads a `u32` count of `Rs` points and then a scalar `s`, with no non-emptiness requirement [1](#0-0) . In `verify`, the only consistency check is `self.Rs.len() != keys_and_challenges.len()` [2](#0-1) . When both are zero, the `pairs` vector contains only `(-self.s, C::generator())`; with `s = 0` this is the identity, and `multiexp_vartime(&pairs).is_identity()` returns true [3](#0-2) . Notably, `SchnorrAggregator::complete` refuses to produce an empty aggregate (`None` if `self.sigs.is_empty()`), showing the library itself recognizes an empty aggregate as meaningless — yet the verifier accepts its byte serialization [4](#0-3) .

The reachable path is `Validators::verify_aggregate`: an attacker supplies an empty `signers` list and a 36-byte signature (`0x00000000` length prefix + 32 zero bytes). `SchnorrAggregate::read` yields `Rs = []`, `s = 0`; `signers.len() == aggregate.Rs().len() == 0` passes [5](#0-4) ; the challenges loop is empty; and `aggregate.verify(DST, &[])` returns true [6](#0-5) .

### Impact Explanation
Any caller of `SchnorrAggregate::verify` — a public `verify` API over untrusted bytes — receives `true` for a "signature" that binds no public key, no nonce, and no message. If a downstream consumer uses this to authorize an action gated on "the aggregate signature verified" without separately enforcing a non-empty signer set, the authorization is forged with trivially constructible bytes. In the tendermint usage the practical impact is bounded because an empty signer set carries zero voting weight and cannot reach quorum, so the reachable severity is Medium at best; the underlying verifier-formula defect is unconditional.

### Likelihood Explanation
Exploitation requires a caller that invokes `verify` with an empty `keys_and_challenges` slice while treating a `true` result as meaningful. In the tendermint path this requires a context where an empty validator/signer set is plausible (e.g., genesis edge cases or messages with no required signers). The probability of the zero-weight check occurring elsewhere is low (`s = 0` and empty `Rs` are freely attacker-controlled here — no hash grinding needed), so likelihood is driven entirely by whether any deployment accepts an empty signer set.

### Recommendation
Mirror the external report's fix: reject the degenerate case. Add at the top of `verify`:

```rust
if self.Rs.is_empty() || (self.s.is_zero().into() && self.Rs.iter().all(|R| bool::from(R.is_identity()))) {
  return false;
}
```

At minimum, `if self.Rs.is_empty() { return false; }` before the length-equality check, matching the `complete()` invariant that an aggregate of zero signatures does not exist. Additionally, `SchnorrAggregate::read` could reject `len == 0` so the invalid encoding never reaches `verify`.

### Proof of Concept
```rust
// For any ciphersuite C and any dst:
let bytes = [0u8; 36]; // len = 0, s = 0
let agg = SchnorrAggregate::<C>::read(&mut bytes.as_slice()).unwrap();
assert!(agg.verify(b"any dst", &[])); // passes despite signing nothing
```
Via tendermint: `verify_aggregate(&[], msg, &agg_bytes)` returns `true` for the same 36-byte payload.
