### Title
Cancellation/refund `withdraw()` reverts (permanent fund lock) when `protocolFeeBps > 0` because escrow is credited with post-fee amounts but refunded with pre-fee amounts - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
This is a local analog of the Backstop.sol bug class: a state-transition function (`Set.updateMarketState(TRIGGERED)` there, `withdraw()`/`cancelOrder()` here) becomes permanently unreachable under specific, non-privileged, production-reachable conditions because a guard/value that should match the actually-escrowed balance is missing. In `IntentGatewayV2.sol` on Tron, escrow accounting is credited with the **fee-reduced** input amount, but refund/cancellation paths transfer and decrement using the **original, pre-fee** amount, causing an unconditional underflow revert whenever `protocolFeeBps > 0`.

### Finding Description
In `placeOrder`, the escrow ledger `_orders[commitment][token]` is credited with the protocol-fee-adjusted amount: [1](#0-0) [2](#0-1) 

Both branches store `reducedInputs[i].amount` (post-fee), not `order.inputs[i].amount` (the full, pre-fee amount the user actually deposited/committed to in the order).

However, when the order is cancelled on the same chain, `withdraw()` is invoked with `body.tokens = order.inputs` — the original, full amounts: [3](#0-2) 

The cross-chain cancel/refund paths do the same, building the `WithdrawalRequest` from `order.inputs` rather than the reduced amounts: [4](#0-3) [5](#0-4) 

`withdraw()` then transfers `amount` (the full, pre-fee amount) to the beneficiary and decrements the escrow ledger by that same full amount: [6](#0-5) 

Since `_orders[commitment][token]` only ever holds the smaller, fee-reduced amount, `_orders[body.commitment][token] -= amount` underflows. Solidity ≥0.8 checked arithmetic reverts on underflow, so `withdraw()` — and therefore `cancelOrder()` and the `RefundEscrow`/`RedeemEscrow` `onAccept` handlers — permanently revert for any order placed with `protocolFeeBps > 0`. This is exactly analogous to the `Backstop.sol` pattern: a missing reconciliation between the amount used for accounting and the amount actually available/escrowed makes a critical state-transition function unconditionally revert once a normal, governance-configured condition (`protocolFeeBps > 0`) is present.

### Impact Explanation
Whenever the gateway's `protocolFeeBps` parameter (a normal, documented, governance-settable production parameter — see `testProtocolFeeWith10Percent`) is non-zero, **every order's cancellation and refund path becomes permanently unusable**. Users' escrowed principal (the reduced, post-fee amount) is placed in the contract, but it can never be recovered via `withdraw()` because the transfer/decrement always references the larger, pre-fee amount and underflows. This is a direct, unprivileged, protocol-level loss/lock of user funds — it requires no malicious relayer, prover, or admin, only the ordinary configuration state the fee mechanism was built for.

### Likelihood Explanation
High. `protocolFeeBps > 0` is an intended, tested production configuration (explicitly exercised by `testProtocolFeeWith10Percent` in the EVM test suite), not an edge case or misconfiguration. Any user who places an order under such a fee regime and later calls `cancelOrder()` (same-chain, cross-chain source, or destination path) or whose order settles via `RefundEscrow`/`RedeemEscrow` will trigger this revert deterministically — no attacker action or race condition needed beyond calling a standard public entrypoint.

### Recommendation
Ensure the amount used in `withdraw()` for both the token transfer and the `_orders[...] -= amount` decrement is the actually escrowed (post-fee) amount, not `order.inputs[i].amount`. Either (a) always route the fee-reduced amount through `WithdrawalRequest.tokens` in `cancelOrder`/`onAccept`, mirroring what `placeOrder` actually credited, or (b) read the current `_orders[commitment][token]` balance directly as the amount to withdraw instead of trusting the caller-supplied `amount`, analogous to clamping in `Backstop.claim()` (`balance_ < amount_ ? balance_ : amount_`), and guard the transfer with an `if (amount == 0) continue;`/balance check to avoid failures from revert-on-zero-value tokens as in the original report.

### Proof of Concept
1. Governance sets `protocolFeeBps = 1000` (10%) via `UpdateParams` — a supported, tested configuration.
2. User calls `placeOrder` escrowing `1000 USDC` as `order.inputs[0].amount`. `_orders[commitment][usdc]` is credited with `900` (the fee-reduced amount), per lines 434‑457.
3. User calls `cancelOrder(order, options)` on the same chain (or, cross-chain, the order later times out/cancels and `RefundEscrow` is delivered).
4. `withdraw()` is invoked with `body.tokens[0].amount = 1000` (from `order.inputs`), while `_orders[commitment][usdc] == 900`.
5. `_orders[body.commitment][token] -= amount` computes `900 - 1000`, which underflows and reverts under Solidity 0.8 checked arithmetic — the entire cancellation/refund transaction reverts, permanently, for this order (and for every order placed under this fee configuration).
