### Title
Out-of-bounds `IndexError` in `is_atom_canonical` on attacker-supplied truncated CLVM atom length prefix - (File: chia/full_node/mempool_manager.py)

### Summary
`is_atom_canonical()`, called via `is_clvm_canonical()` on every submitted spend bundle's `puzzle_reveal` and `solution`, reads a variable-length CLVM atom size prefix without ever checking that the declared `prefix_len` bytes actually exist in the buffer. This mirrors the reported torchvision GIF-decoder bug class: a length value taken from untrusted input is used to drive further reads without being clamped to the buffer's actual remaining size.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` determines a length-prefix width (`prefix_len`, 0–5 extra bytes) from the leading byte, then loops: [1](#0-0) 

```
atom_len = b & mask
for i in range(prefix_len):
    atom_len <<= 8
    offset += 1
    atom_len |= clvm_buffer[offset]
return 1 + prefix_len + atom_len, atom_len >= min_value
```

There is no bounds check ensuring `offset` stays `< len(clvm_buffer)` before the indexed read `clvm_buffer[offset]`. This function is invoked from `is_clvm_canonical()`: [2](#0-1) 

which itself is called directly on attacker-controlled bytes during spend-bundle admission in `validate_spend_bundle()`: [3](#0-2) 

```
if not is_clvm_canonical(bytes(coin_spend.puzzle_reveal)) or not is_clvm_canonical(
    bytes(coin_spend.solution)
):
    return Err.INVALID_COIN_SOLUTION, None, []
```

An unprivileged spend-bundle submitter can craft a `puzzle_reveal` or `solution` whose final bytes are a multi-byte atom-length-prefix marker (e.g. `0xFC`..) that is truncated right at (or before) the buffer end, so the prefix-consuming loop indexes past the end of `clvm_buffer`.

### Impact Explanation
In CPython, `bytes.__getitem__` with an out-of-range index raises `IndexError` rather than performing an unchecked native memory read — so this is not a memory-disclosure or heap-corruption vulnerability like the torchvision C++ `memcpy` bug. The practical effect here is an unhandled Python exception raised deep inside the mempool admission pipeline (`validate_spend_bundle` → `is_clvm_canonical` → `is_atom_canonical`) while processing a single submitted `SpendBundle`. Whether this only fails admission of that one spend bundle (bounded, low impact) or propagates further up the call chain to abort mempool/new-peak processing depends on exception handling in the callers of `validate_spend_bundle` (e.g. `add_spend_bundle`, `full_node.add_transaction`), which I was not able to fully confirm from the available context — I could not verify a surrounding `try/except` at every level in the remaining budget. If any of those intermediate layers lack a catch-all around this specific call, a single malformed spend bundle could raise an uncaught exception during transaction processing.

### Likelihood Explanation
Trivial to trigger: any unprivileged wallet/RPC caller can submit a `SpendBundle` with a coin spend whose `puzzle_reveal` or `solution` ends immediately after a multi-byte atom-length marker. No signature validity or special privileges are required to reach this code path, since `is_clvm_canonical` runs early in `validate_spend_bundle`, prior to full CLVM execution.

### Recommendation
Add explicit bounds checking in `is_atom_canonical` before indexing `clvm_buffer[offset]` in the prefix-consuming loop (raise/return a non-canonical result or a `ValueError` cleanly if `offset >= len(clvm_buffer)`), rather than relying on Python's exception mechanism, and confirm/add a catch for unexpected exceptions in the `validate_spend_bundle` call chain so malformed spend bundles are rejected as `INVALID_COIN_SOLUTION` rather than surfacing an uncaught exception in the mempool/transaction-processing path.

### Proof of Concept
Submit a `SpendBundle` with a `CoinSpend` whose `solution` (or `puzzle_reveal`) is set to a truncated CLVM buffer such as `bytes.fromhex("fc")` (a `0xFC` marker declaring a 6-byte length prefix with zero trailing bytes present). When `validate_spend_bundle` calls `is_clvm_canonical(bytes(coin_spend.solution))` → `is_atom_canonical(clvm_buffer, 0)`, the loop attempts `clvm_buffer[1]` on a 1-byte buffer, raising `IndexError` instead of returning a clean canonicality verdict.
