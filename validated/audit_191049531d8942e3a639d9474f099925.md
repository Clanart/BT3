### Title
Payout transaction's operator-attribution `OP_RETURN` is not covered by the user's withdrawal signature, letting anyone redirect reimbursement credit — ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The user's withdrawal-authorizing signature only commits to the payout input and the payout output (via `SIGHASH_SINGLE | ANYONECANPAY`). The `OP_RETURN` output that records *which operator fronted the withdrawal* — the sole piece of on-chain data later used to decide who gets reimbursed — is never covered by that signature. This mirrors the Llama `LlamaCore` bug: policyholders approve one thing (the payout amount/destination), while an unrelated, unauthenticated piece of data (here, the operator attribution, there, the call/delegate_call opcode) determines the actual execution semantics and can be altered by a party outside the original signer set.

### Finding Description
`create_payout_txhandler` builds the `Payout` transaction with three outputs: the user's payout output, an anchor output, and an `op_return_txout` that embeds the fronting operator's x-only public key: [1](#0-0) 

The single input is spent with the user's `taproot::Signature`, which is required to use `SinglePlusAnyoneCanPay`: [2](#0-1) 

`SIGHASH_SINGLE | ANYONECANPAY` only binds the signer's input to the output at the *same index* (index 0, the payout output). It does **not** bind the transaction's other outputs — the anchor and, critically, the `OP_RETURN` operator-attribution output — nor does it bind any other inputs that might be added. Any party in possession of the broadcast (unconfirmed) payout transaction can therefore build an alternative transaction reusing the identical signed input/output pair while substituting an arbitrary `OP_RETURN` value.

Later, `update_finalized_payouts` determines *who gets credited* for fronting the withdrawal purely by parsing whatever `OP_RETURN` ends up in the confirmed on-chain transaction: [3](#0-2) [4](#0-3) 

This value is then used to look up and mark the payout as handled for that specific operator, driving that operator's reimbursement/kickoff flow: [5](#0-4) 

The transaction is built with `NON_STANDARD_V3`, i.e. BIP 431 "v3" relay-policy transactions, which are opt-in replaceable regardless of the nSequence value used: [6](#0-5) 

**Binding that should hold:** `operator credited in confirmed payout tx == operator whose funds/collateral actually paid the user`. Because the `OP_RETURN` is unauthenticated by the user's signature, and the transaction is replaceable pre-confirmation, this binding is not enforced cryptographically — it depends only on which version of the transaction happens to confirm.

### Impact Explanation
If an unprivileged party observes an honest operator's broadcast (but unconfirmed) `Payout` transaction in the mempool, they can construct a replacement transaction that reuses the same signed input and payout output but swaps the `OP_RETURN` to name a different operator's x-only public key (their own operator identity, or any other operator's identity) and get it relayed/mined instead (v3 transactions are always replaceable per current relay policy). If it confirms:
- A different operator than the one who actually funded the payout will be credited by `update_finalized_payouts`/`payout_checker`, and its `handle_finalized_payout`/kickoff/reimbursement flow will proceed — i.e., **an operator is reimbursed for a payout it never funded**.
- The operator who genuinely fronted the withdrawal loses the confirmation race for its own transaction and is never credited for having paid the user — i.e., **an honest operator permanently unable to be reimbursed**.

This matches the Critical-impact categories in scope (misattributed reimbursement / operator credited vs. party that paid).

### Likelihood Explanation
The attack only requires observing a broadcast, unconfirmed payout transaction (public mempool data) and constructing a standard transaction reuse of the SIGHASH_SINGLE|ANYONECANPAY-signed input — no verifier, operator, watchtower, aggregator, or security-council role is required to *mount* the substitution itself. The main uncertainty (not fully verified with the available tooling) is whether the downstream reimbursement path (`get_first_unhandled_payout_by_operator_xonly_pk` / `handle_finalized_payout`) requires the named `OP_RETURN` key to belong to an already-registered, collateralized operator for the credit to have real effect; if so, the practical beneficiary of a misdirected credit is limited to keys corresponding to existing operators, but the "honest operator loses its own reimbursement" half of the impact holds regardless.

### Recommendation
Bind the operator attribution to the same signature that authorizes spending the withdrawal UTXO, e.g. by having the operator's identity/commitment covered under a full-input/output sighash to that operator (and let the user sign a session/commit hash that includes the specific operator xonly_pk if fronting is meant to be pre-agreed), or otherwise ensure a replacement transaction cannot swap the `OP_RETURN` without invalidating the user's authorization. At minimum, treat the payout transaction as unsafe to rely on for attribution until it reaches a fee-bumping/finality mechanism that is immune to third-party replacement of uncommitted outputs.

### Proof of Concept
1. Operator A broadcasts a `Payout` tx for withdrawal `W`: input = user's UTXO signed with `SinglePlusAnyoneCanPay`; output 0 = user's payout; output 1 = anchor; output 2 = `OP_RETURN(operator_A_xonly_pk)` (`core/src/builder/transaction/operator_reimburse.rs:407-436`).
2. Before it confirms, attacker B observes this transaction in the mempool (fully public: signature, input, and output 0 are visible).
3. B constructs Tx' reusing the exact same signed input and output 0 (valid because the signature only covers input 0 / output 0 under `SIGHASH_SINGLE|ANYONECANPAY`), but sets output 2 = `OP_RETURN(operator_B_xonly_pk)`.
4. Because the transaction uses `NON_STANDARD_V3` (opt-in-replaceable relay policy), Tx' can replace/out-compete Operator A's original transaction and confirm instead.
5. `update_finalized_payouts` parses the confirmed tx's `OP_RETURN` and records `operator_B_xonly_pk` as the payer (`core/src/verifier.rs:2319-2342`), so `payout_checker` credits and reimburses Operator B for a withdrawal it never funded, while Operator A's genuine payment is never attributed.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
