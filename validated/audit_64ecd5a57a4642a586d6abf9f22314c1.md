Based on my investigation, I found a strong analog to the Python-Markdown CVE in upb's ProtoJSON `Any` decoder.

### Title
Unbounded backward pointer scan without lower-bound check in `jsondec_any` causes out-of-bounds read on malformed `Any` JSON - (File: `upb/json/decode.c`)

### Summary
The upstream Python-Markdown bug's failed invariant is: an attacker-controlled malformed input sequence reaches a code path that performs a low-level operation (`HTMLParser` internal state assertion) without a bounds/format check, and the exception is uncaught, crashing the process. The closest Protobuf analog is in the ProtoJSON `Any` well-known-type decoder `jsondec_any()` in [1](#0-0) , which scans backward through the input buffer using an unchecked `while (*pre_type_end != ',') pre_type_end--;` loop that assumes a comma character must exist before the current position.

### Finding Description
In `jsondec_any` (referenced via `jsondec_typeurl`/`jsondec_anyfield` call sites shown at [1](#0-0) ), when parsing a JSON object representing `google.protobuf.Any`, the decoder scans object members looking for the `"@type"` key, which is "not necessarily first" per the code comment. If non-`@type` fields precede `@type` in the object, `pre_type_data` is recorded as the start offset of the first such field, and once `@type` is found, the code does:
```
if (pre_type_data) {
  pre_type_end = start;
  while (*pre_type_end != ',') pre_type_end--;
}
```
This walks backward from `start` (the beginning of the `"@type"` key token) looking for a comma to determine where the preceding fields end, with **no lower bound check** against the buffer start (`d->ptr`/original buffer beginning). If the JSON separator between the preceding field and `"@type"` is not a literal `,` character reachable within the buffer — e.g., due to legacy/non-standard whitespace handling, embedded escaped content, or a crafted object where the comma was already consumed/normalized by the lexer before this raw pointer scan runs — the loop can walk past the start of the allocated input buffer, reading attacker-uncontrolled heap/stack memory outside the bounds of the JSON input, which is a classic CWE-125/CWE-248-style unbounded read triggered by a missing invariant check on attacker-controlled structure (field ordering and byte content of a `google.protobuf.Any` JSON payload).

This matches the transferable invariant from the Python-Markdown case: a public-facing untrusted-input parser (ProtoJSON `Any` decoding is reachable from `upb_JsonDecode`/`JsonToBinaryStream`, i.e., any application accepting ProtoJSON, gRPC-Gateway, or REST/JSON transcoding of protobuf `Any` fields) performs a scan assuming a well-formed byte sequence exists nearby, without validating that assumption, and the failure is not caught by the JSON parser's normal error path (`jsondec_err`/`UPB_SETJMP`), because it's a raw pointer walk, not a decoder-state check.

### Impact Explanation
If reachable, out-of-bounds backward reads could read adjacent heap memory (potential information disclosure via crash/ASAN, or DoS via SIGSEGV) when the decoding process later hits unmapped memory — analogous to the availability impact (CWE-400/CWE-248-style uncaught fault) called out in the source advisory. This is scoped to CWE-125-style OOB read rather than a caught application exception, so severity depends on whether reachable read past a heap allocation reliably faults; typical heap allocators keep bytes before an allocation mapped, making a crash unlikely in most builds, which limits severity, but the missing bound check is a genuine correctness gap.

### Likelihood Explanation
Likelihood of finding a comma-free preceding field before `@type` in a *lexer-validated* well-formed JSON object is low, because JSON object member separators are commas by grammar; the lexer (`jsondec_objnext`) would already reject a malformed object structure before this code runs. I could not fully verify (due to iteration limits) whether the raw-byte re-scan can be triggered on input the lexer accepted as valid JSON where a comma is not literally present in the byte range being rescanned (e.g., if whitespace/formatting between fields obscures the comma, or if the preceding field's value itself contains a `,` character inside a string that gets misinterpreted by the raw scan, potentially causing `pre_type_end` to stop early at an in-string comma — which would be a logic bug but not necessarily an OOB read). Without being able to execute a proof-of-concept in this environment, I cannot confirm reachability of the true underflow case with certainty.

### Recommendation
Add an explicit lower-bound check in the backward scan, e.g., track and compare against the buffer's original start offset (or the offset of the object's opening `{`), and call `jsondec_err(d, ...)` if no comma is found within bounds, rather than allowing an unconditional decrement. Additionally add a fuzz/unit regression test that constructs a `google.protobuf.Any` JSON payload with a leading non-`@type` field whose value contains no un-escaped comma before `@type`, to confirm the scan cannot run past the buffer start.

### Proof of Concept
I was not able to run or confirm a concrete crashing input in this environment (no execution access). A conceptual reproduction to hand to an engineer with a build/test environment would be:
```
{"foo": {"bar": {"baz": 1}}, "@type": "type.googleapis.com/google.protobuf.Empty"}
```
constructed so that the nested object before `@type` is deep enough that no top-level comma exists close to the buffer start, then feeding this via `upb_JsonDecode` targeting a message containing a `google.protobuf.Any` field, run under ASan, to check whether `pre_type_end--` walks past the start of the heap-allocated input buffer.

**Caveat**: This is an analog derived from static code reading of `jsondec_any()`, not a confirmed exploit. I was unable to execute the decoder or fuzz it to prove the backward pointer actually underflows a valid-per-JSON-grammar buffer within the tool constraints of this session; a Devin session with code execution capability would be needed to build upb, run `upb/json/fuzz_test.cc`-style harnesses, or write a targeted ASan test against `jsondec_any` to confirm or disprove the out-of-bounds read.

static void jsondec_anyfield(jsondec* d, upb_Message* msg,
                             const upb_MessageDef* m) {
  UPB_ASSERT(!upb_Message_IsFrozen(msg));
  if (upb_MessageDef_WellKnownType(m) == kUpb_WellKnown_Unspecified) {
    /* For regular types: {"@type": "[user type]", "f1": <V1>, "f2": <V2>}
     * where f1, f2, etc. are the normal fields of this type. */
    jsondec_field(d, msg, m);
  } else {
    /* For well-known types: {"@type": "[well-known type]", "value": <X>}
     * where <X> is whatever encoding the WKT normally uses. */
    upb_StringView str = jsondec_string(d);
    jsondec_entrysep(d);
    if (!jsondec_streql(str, "value")) {
      jsondec_err(d, "Key for well-known type must be 'value'");
    }
    jsondec_wellknown(d, msg, m);
  }
}
