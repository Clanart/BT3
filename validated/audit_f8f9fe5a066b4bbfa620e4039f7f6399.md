### Title
Forfeit bypass via `cancelUnlock` before claim lets vlMGP cooldown holders avoid MGP forfeit penalty - (File: `rewards/vlMGPBaseRewarder.sol`)

### Summary
`queueMGP`'s forfeit calculation in `_calExpireForfeit` reads the account's *current* `vlMGP.getRewardablePercentWAD(_account)` at the moment of harvest, rather than a value that reflects the cooldown state over the period the pending MGP accrued. Because `cancelUnlock` (in `VLMGP.sol`) has no cooldown or restriction and does not itself trigger a harvest, any vlMGP holder can call `cancelUnlock` immediately before claiming to reset their percent to 100%, zero out the forfeit on the pending harvest, and then call `startUnlock` again to resume their unlock schedule.

### Finding Description
`queueMGP` computes `forfeitAmount = _calExpireForfeit(_account, _amount)`, and `_calExpireForfeit` derives the forfeit purely from the live `vlMGP.getRewardablePercentWAD(_account)`: [1](#0-0) 

`getRewardablePercentWAD` bases the rewardable percent on the account's *current* `getUserTotalLocked` vs `getUserAmountInCoolDown` split: [2](#0-1) 

`queueMGP` is invoked synchronously inside the same call stack as `MasterMagpie._multiClaim` → `_sendMGPForVlMGPPool` → `IvlmgpPBaseRewarder(vlMGPRewarder).queueMGP`, which is triggered by the account's own claim/harvest action (directly, or indirectly via `startUnlock`/`unlock` which call `multiclaimFor` first): [3](#0-2) [4](#0-3) 

`cancelUnlock` is unprivileged, callable by `msg.sender` on their own unlock slot, has no time restriction, and does not itself force a harvest before/after mutating cooldown state: [5](#0-4) 

The equivalent function exists in `VLMGP.sol` for vlMGP slots. Because there is no restriction preventing an account from calling `cancelUnlock()` and then immediately claiming (or bundling both calls atomically in a single transaction through a helper contract), a user who is mid-cooldown can:
1. Call `cancelUnlock(slotIndex)` — this sets `amountInCoolDown = 0` for that slot, restoring `getUserTotalLocked` to 100% of their balance, with no harvest triggered.
2. Call `multiclaim`/`getReward` (or any path reaching `_sendMGPForVlMGPPool` → `queueMGP`) in the same or immediately following transaction — `_calExpireForfeit` now reads 100% rewardable, so `forfeitAmount == 0` regardless of how long the pending MGP accrued while the account was actually in cooldown.
3. Call `startUnlock(...)` again to re-enter cooldown for the same amount, resuming their exit schedule with no economic penalty for the temporary cancel.

No existing modifier (`nonReentrant`, `onlyManager`, `whenNotPaused`) prevents this sequence, since every call in the sequence is legitimate and unprivileged, and the forfeit computation intentionally reads live on-chain state rather than a snapshot tied to the accrual period.

### Impact Explanation
The forfeit mechanism exists to redistribute MGP from users who are exiting (in cooldown) to users who remain fully locked, via `_queueNewRewardsWithoutTransfer` adding to `rewardPerTokenStored` for other stakers. By trivially bypassing forfeit through a self-serve `cancelUnlock` → claim → `startUnlock` sequence, a cooldown user avoids penalty during claims and denies the pool the redistributed forfeit yield that other, still fully-locked, honest stakers should receive. This matches the Immunefi impact class of theft of unclaimed yield belonging to other users, since the forfeit that should have flowed to `rewardPerTokenStored` (and hence to other stakers) is instead retained in full by the account performing the cancel/claim/restart pattern.

### Likelihood Explanation
This requires no capital, no privileged role, and no race condition against another actor — the same account performs all three calls (`cancelUnlock`, claim, `startUnlock`) with full control over ordering, either across two blocks or atomically inside a single transaction via a helper contract. It is fully repeatable on every harvest cycle for any vlMGP holder who has an active unlock slot, making it a systematic gaming vector rather than a one-off exploit.

### Recommendation
Base the forfeit percentage on a value that reflects the account's cooldown status integrated over the period the pending MGP accrued (e.g., snapshot/checkpoint the rewardable percent at each `updateFor`/pool-update boundary, or force a harvest inside `cancelUnlock`/`startUnlock` using the pre-mutation state before allowing any state change that affects `getRewardablePercentWAD`), rather than reading a live, freely-manipulable value at the moment of `queueMGP`.

### Proof of Concept
Foundry test plan:
1. Set up `VLMGP`, `MasterMagpie`, and `vlMGPBaseRewarder` with two users: `attacker` and `honestLocker`, both locking equal MGP.
2. Advance time so MGP rewards accrue in the vlMGP pool for both users.
3. `attacker` calls `startUnlock(halfOfBalance)` to enter cooldown (this triggers an initial `multiclaimFor` harvest to reset the baseline, per `startUnlock`'s internal call).
4. Advance time so more MGP accrues to `attacker.unClaimedMgp` while `attacker` is still mid-cooldown (`getRewardablePercentWAD` at this point should be < 100%).
5. In a single transaction (or a helper contract bundling calls): `attacker` calls `cancelUnlock(slotIndex)` then immediately calls `masterMagpie.multiclaim(...)` (which reaches `queueMGP`).
6. Assert `forfeitAmount == 0` in the `MGPHarvested` event / rewarder state, versus computing the expected forfeit if `_calExpireForfeit` had been evaluated while `attacker` was still mid-cooldown (non-zero).
7. Assert `honestLocker`'s claimable reward-per-token for MGP forfeit rewards did not increase by the amount it would have, confirming the redistributed yield was withheld.
8. `attacker` calls `startUnlock(halfOfBalance)` again to resume the exit schedule at no cost, demonstrating full repeatability.

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```

```text
    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
```
