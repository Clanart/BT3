### Title
Pausing and later resuming interest accrual back-applies interest/liquidity-index growth for the entire paused duration, producing a wrong ztoken price - (File: mainnet/contracts/vault/v0-vault-usdc.clar and equivalent vault contracts)

### Summary
This is an analog of the TOKE-20 class of bug: a rate/multiplier is applied over an elapsed-time window (`block.timestamp`/`stacks-block-time` minus a stored "last update" marker) without accounting for a sub-interval during which the value should not have advanced (there, the rewarder's `periodFinish`; here, the vault's `accrue` pause flag). In both cases the stale reference marker is not advanced while the rate-driving state has effectively stopped moving, so once the freeze ends the code multiplies the full-rate accrual by an elapsed duration that wrongly includes the frozen period, inflating the derived value.

### Finding Description
Each vault (`vault-usdc.clar`/`v0-vault-usdc.clar`, and the STX/sBTC/stSTX/USDH/stSTXbtc equivalents) tracks a `last-update` timestamp and computes new indexes as: [1](#0-0) 

```
(define-private (next-index)
  (let ((states (var-get pause-states))
        (idx (var-get index)))
    (if (get accrue states)
        idx
        (let (
            (rate (interest-rate))
            (time-delta (- stacks-block-time (var-get last-update)))
            ...
          (calc-index-next idx multiplier)))))

(define-private (next-liquidity-index)
  ... same pattern using time-delta = stacks-block-time - last-update ...)
```

`last-update` is only advanced inside the public `accrue()` entrypoint, and only when the index actually changes: [2](#0-1) 

```
(define-public (accrue)
  (let ((states (var-get pause-states)) ...)
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index)) (nliq (next-liquidity-index)) ...)
            ...
            (if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
                (var-set last-update stacks-block-time)
                false)
            (ok { index: next, lindex: nliq })))))
```

When `pause-states.accrue` is `true`, `accrue()` returns immediately without updating `last-update` — by design, the intent is that no interest/liquidity growth accrues while paused. However, `last-update` is *frozen at whatever value it had before the pause began* (i.e., the timestamp of the last successful, non-paused accrual). When the pause is later lifted and `accrue()` (or any state-mutating vault action that calls it, e.g. `system-borrow`/`system-repay`) is invoked, `next-index`/`next-liquidity-index` compute `time-delta = stacks-block-time - last-update`, which spans the *entire paused interval plus* any time before the pause. The code then applies the full interest/liquidity rate multiplier over that whole span — exactly as if the pause never happened — rather than stopping the clock during the pause and resuming it afterward.

This mirrors the reported bug precisely: `timeBetweenSnapshots`/`time-delta` is computed from a stored "last touched" timestamp to "now," but the intervening period during which the rate-driving quantity (`rewardPerToken` there, "should the index move" here) was frozen is not subtracted out. The result is a value (`safeTotalSupply` there, the liquidity index / ztoken price here) that reflects a rate applied over a longer window than actually occurred.

### Impact Explanation
The liquidity index directly determines the ztoken (e.g. zUSDC, zSTX, zsBTC, zUSDH, zstSTXbtc) price via the `resolve-ztoken` callcode transformation used throughout market pricing/health/liquidation logic: [3](#0-2) 

```
(define-private (resolve-ztoken (p uint) (aid uint))
  (let ((cached (unwrap! (get-cached-indexes aid) ERR-ORACLE-CALLCODE))
        (cached-lindex (get lindex cached))
        (scaled (* p cached-lindex)))
    (ok (div-down scaled INDEX-PRECISION))))
```

If a vault's `accrue` pause is lifted, the very next accrual step back-applies the full pending interest for the *entire paused window* in a single jump, rather than resuming the clock cleanly from the pause point. This produces a step-jump in the liquidity index (hence the ztoken's on-chain price) that is larger than warranted by real time elapsed with interest actually accruing, or — depending on how/when the pause was toggled relative to `last-update` refresh — a value inconsistent with the intended "freeze" semantics of the pause. Since ztoken price feeds directly into collateral valuation and debt valuation for every position, this can distort collateral value (over- or under-valuation) system-wide the moment accrual resumes, causing incorrect health-factor computations that could enable under-collateralized borrowing/withdrawal or incorrect liquidation determinations. This lands in the in-scope **temporary freezing of funds / theft of unclaimed yield** category (wrong index value skews yield distribution and can create a window of incorrect health verdicts), analogous to the "High" impact of the source finding on APR/valuation.

### Likelihood Explanation
Triggering this requires the DAO/operator to legitimately use the existing `set-pause-states`-style controls to pause `accrue` on a vault (a normal operational action, e.g. during an incident) and later unpause it — this is not an accidental/malicious registry misconfiguration, nor third-party oracle data, nor a flashloan/liquidation-of-disabled-collateral scenario; it is the vault's own accrual-timing arithmetic. Any accrual-triggering call after resuming (`accrue`, `system-borrow`, `system-repay`, deposit/withdraw paths) will exhibit the effect deterministically, so likelihood of occurrence following any accrue-pause/unpause cycle is high, though such cycles themselves may be infrequent operationally.

### Recommendation
When toggling `pause-states.accrue` (in the setter that flips the flag), also update `last-update` to `stacks-block-time` at the moment the pause is engaged (freezing the clock going forward) — or equivalently, when unpausing, reset `last-update` to `stacks-block-time` before any subsequent accrual runs `next-index`/`next-liquidity-index`. This ensures `time-delta` measured for rate application only spans periods during which accrual was actually active, mirroring the report's fix of capping/aligning `timeBetweenSnapshots` to the true active period rather than raw wall-clock elapsed time.

### Proof of Concept
1. At `t0`, vault's `last-update = t0`, `index = I0`.
2. Admin pauses accrual (`pause-states.accrue = true`) at `t1` (no code path resets `last-update`).
3. Time passes; at `t2` (`t2 - t0` large), admin unpauses (`pause-states.accrue = false`).
4. Any subsequent call to `accrue()` (or `system-borrow`/`system-repay`) computes `time-delta = t2 - t0` (spanning both the pre-pause and the entire paused interval) and applies `interest-rate` over that full span via `calc-multiplier-delta`, producing `next-index`/`next-liquidity-index` as if interest had continued accruing uninterrupted through the pause.
5. `lindex` jumps discontinuously; `resolve-ztoken` immediately reflects the inflated `cached-lindex` in the ztoken price used by the market for collateral valuation, skewing health-factor/liquidation calculations for every position holding that ztoken as collateral or debt.
