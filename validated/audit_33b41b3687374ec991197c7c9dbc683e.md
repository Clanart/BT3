### Title
Attacker-controlled participant count in `ThresholdKeys::read` enables amplified memory-allocation denial of service - (File: crypto/dkg/src/lib.rs)

### Summary
The buffer-overflow/DoS class in CVE-2024-28572 (untrusted input driving oversized work during parsing) maps onto Serai's `ThresholdKeys::<C>::read` in `crypto/dkg/src/lib.rs`. The deserialization trusts an attacker-supplied `n` (`u16`) from the byte stream and immediately performs `Vec::with_capacity(usize::from(n))` and a `1..=n` element read loop, without validating `n` against `t`, `i`, or the amount of data actually remaining in the reader. Any unprivileged party who can cause serialized `ThresholdKeys` bytes to be parsed can force disproportionate allocations from a handful of input bytes.

### Finding Description
`ThresholdKeys::read` parses header fields `(t, n, i)` directly from the reader via `read_u16` helpers, then, if the interpolation byte is `0` (`Interpolation::Constant`), executes:

```rust
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));
  for _ in 0 .. n {
    res.push(C::read_F(reader)?);
  }
  res
}),
```

and afterwards unconditionally iterates `for l in (1 ..= n).map(Participant)` calling `read_G` for each of `n` verification shares. `n` is only constrained to `u16::MAX = 65535` by its encoding; `ThresholdParams::new(t, n, i)` is only invoked at the very end, after all allocation and parsing work has occurred. Consequently a roughly 13-byte crafted prefix (curve-ID length + curve ID + `t` + `n` + `i` + interpolation byte `0x00`) with `n = 0xFFFF` triggers:

- an upfront `Vec::with_capacity(65535)` of `C::F` elements (~2 MiB for a 32-byte scalar),
- followed by a `HashMap` insertion loop over `65535` `Participant` keys each performing a `read_G` attempt.

The reads fail fast once the input is exhausted, but the capacity allocation already happened. This is the same defect shape as the FreeImage bug: a length/count field from attacker bytes drives allocation before any sanity bound relative to the real payload.

### Impact Explanation
Every invocation allocates up to ~2 MiB (curve-dependent; more for wider fields) plus a `HashMap` grown to `n` entries, triggered by ~13 attacker-controlled bytes — an amplification factor of roughly 10⁵ in memory terms. On any endpoint or service that repeatedly parses untrusted `ThresholdKeys` blobs (key-refresh messages, share recovery, blame/verification paths), an attacker can send a stream of tiny malformed messages to keep the allocator saturated, degrading or crashing the process. This is a remote-reachable availability loss matching the Medium severity of the source advisory.

### Likelihood Explanation
Reachability requires a caller to feed unauthenticated bytes into `ThresholdKeys::read` — one of the entry points the threat model explicitly keeps in scope (untrusted bytes into `ThresholdKeys::read`). The bug needs no malicious-validator or collusion assumptions: it is a pure deserialization robustness failure. The only mitigating factor is that the allocation is freed when `read_F` errors out, so exploitation requires sustained repetition rather than a single packet; this keeps it at Medium rather than higher.

### Recommendation
Bound work before allocating: validate `n` (and `t <= n`, `i <= n`) immediately after reading the header, before the interpolation branch. Replace `Vec::with_capacity(n)` with incremental `push` (or cap capacity at a protocol-defined maximum such as the validator-set size), and consider bounding `n` to the maximum legitimate participant count rather than the `u16` encoding limit.

### Proof of Concept
Serialize a minimal header and pass it to `ThresholdKeys::<Ristretto>::read`:

```rust
use std::io::Cursor;
use dkg::{ThresholdKeys, ThresholdParams, Participant};
use dalek_ff_group::Ristretto;
use ciphersuite::Ciphersuite;

let mut buf = vec![];
// Curve ID length + ID (must match <Ristretto as Ciphersuite>::ID)
buf.extend((<Ristretto as Ciphersuite>::ID.len() as u32).to_le_bytes());
buf.extend(<Ristretto as Ciphersuite>::ID);
// t = 1, n = 65535, i = 1
buf.extend(1u16.to_le_bytes());
buf.extend(65535u16.to_le_bytes());
buf.extend(1u16.to_le_bytes());
// Interpolation::Constant
buf.push(0);

// A single call allocates ~2 MiB (Vec::with_capacity(65535) of scalar-sized elements)
// before failing on the missing scalar bytes; looping this drives memory pressure.
let _ = ThresholdKeys::<Ristretto>::read(&mut Cursor::new(&buf));
```
