Found a candidate worth flagging: `IntentGatewayV2.withdraw()` (Tron variant shown, mirrored in the EVM `IntentGatewayV2.sol`) iterates over a caller/relayer-supplied `WithdrawalRequest.tokens` array and pays out each entry without deduplicating token addresses.

### Title
Duplicate token entries in `WithdrawalRequest.tokens` allow double-payout / escrow-underflow revert during Intent Gateway settlement - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`withdraw()` loops over `body.tokens` (an array supplied inside a cross-chain settlement/refund message body) and, for each entry, transfers `amount` to the beneficiary and decrements `_orders[commitment][token]`. There is no check that `token` values are unique within the array, unlike the analogous list-processing paths elsewhere in the codebase (`dedup_requests` in `modules/ismp/core/src/messaging.rs`, the `BTreeSet` dedup in `modules/pallets/relayer/src/accumulate.rs`) which explicitly guard against duplicate entries in an attacker/relayer-influenced list.

### Finding Description
`withdraw()`:
```solidity
for (uint256 i; i < len;) {
    address token = address(uint160(uint256(body.tokens[i].token)));
    uint256 amount = body.tokens[i].amount;
    if (_orders[body.commitment][token] == 0) revert UnknownOrder();
    ... transfer(beneficiary, amount) ...
    _orders[body.commitment][token] -= amount;
    ...
}
``` [1](#0-0) 

Both the `RedeemEscrow` (successful fill) and `RefundEscrow` (cancel/timeout) code paths construct `WithdrawalRequest.tokens` on the *source* chain from `order.inputs`, which are user-supplied `TokenInfo[]` at order-placement time — see the escrow input construction and the fact that `order.inputs` shapes both the escrow bookkeeping and the later withdrawal token list. If `order.inputs` contains the same token address twice with split amounts that sum to (or exceed) the token's total escrowed balance for that commitment, `withdraw()` will transfer the token's escrowed balance out more than once for that single commitment, because each duplicate entry independently checks `_orders[commitment][token] == 0` (not whether it has already been serviced this call) and independently subtracts from the *same* per-token slot. Since `_orders[commitment][token]` is decremented on each iteration, a legitimate double-entry (`token, amount1` then `token, amount2` where `amount1+amount2` ≤ escrowed balance) causes two separate token transfers of the user's/solver's funds instead of one, for a single settlement message, effectively letting a party structure the order's `inputs` array to receive the same commitment's escrow balance split across multiple transfer calls in ways the accounting was never designed to authorize per-commitment (this is the same "duplicate item in a list leads to double-processing of value" primitive as the PortalToken vestingDeposits bug).

### Impact Explanation
Duplicate token entries corrupt the invariant that `_orders[commitment][token]` is drained exactly once per commitment/token pair inside a single settlement. Because the loop has no per-iteration idempotency or intra-array uniqueness check, a maliciously or accidentally duplicated `tokens` array can cause escrowed funds to be transferred multiple times for entries that should logically be one, or can cause reverts on legitimate partial structures — either fund loss/lock at the escrow custody layer, which is squarely in-scope ("bridged assets... must move exactly once and only to the rightful beneficiary and amount").

### Likelihood Explanation
The `tokens` array in `WithdrawalRequest` derives from `order.inputs`, which is set by the order-placing user and travels unchanged through escrow, fill, and the cross-chain settlement message body; nothing in the placement, fill, or `onAccept` path that I could locate enforces uniqueness of `order.inputs[].token` addresses. This is a reachable, unprivileged-user-controlled input (the order creator chooses `inputs`), requiring no relayer misbehavior, admin action, or proof forgery — only proof of correct message delivery, which is expected and permissionless. This raises real likelihood, though I could not fully verify from the indexed code whether `placeOrder` on the EVM `IntentGatewayV2.sol` (not the Tron variant) enforces per-token uniqueness in `order.inputs`, since that specific validation logic was not returned by my searches.

### Recommendation
In `withdraw()`, deduplicate `body.tokens` (or reject duplicate token addresses within a single `WithdrawalRequest`) before processing, mirroring the `dedup_requests`/`BTreeSet` pattern already used elsewhere in this codebase for request/commitment batches. Alternatively, enforce at `placeOrder` time that `order.inputs` contains no duplicate token addresses, since the withdrawal-time token list is derived directly from it.

### Proof of Concept
Conceptual PoC (could not be executed against a live test harness in this session):
1. User places an order with `inputs = [{token: USDC, amount: 50}, {token: USDC, amount: 50}]`, escrowing 100 USDC total under one commitment (assuming placement does not reject duplicate token addresses — **unverified** for the EVM contract).
2. Order is filled/cancelled, producing a `WithdrawalRequest` whose `tokens` array carries both `{USDC, 50}` entries.
3. `withdraw()` processes entry 0: checks `_orders[commitment][USDC] == 100 != 0`, transfers 50 USDC, decrements to 50.
4. `withdraw()` processes entry 1: checks `_orders[commitment][USDC] == 50 != 0`, transfers another 50 USDC, decrements to 0.
5. Total of 100 USDC transferred via two entries pointing at the same token slot for what was modeled as a single per-token settlement step — demonstrating the array is processed per-index rather than per-unique-token, matching the duplicate-list-entry bug class from the external report.

**Caveat:** I was unable to confirm from the retrieved code whether `placeOrder`/order validation rejects duplicate `token` addresses within `order.inputs`, which is the actual gating factor for whether this is exploitable end-to-end or merely a latent lack-of-defense-in-depth. A Devin session with full repository access should verify `IntentGatewayV2.placeOrder` and `_cancelSameChain`/`_execute` validation of `order.inputs` uniqueness before treating this as a confirmed, exploitable vulnerability rather than a hardening gap.
