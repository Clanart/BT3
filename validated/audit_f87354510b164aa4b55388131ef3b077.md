## Title
`SweepDust` protocol-fee sweep permanently blockable by a single malicious-token/beneficiary entry, locking dust for every other token in the batch - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.onAccept()`'s `RequestKind.SweepDust` handler iterates over an array of `(token, amount)` entries and pushes each one to a single, governance-controlled `req.beneficiary` with a hard revert-on-failure guard, inside one non-isolated loop. [1](#0-0) 

### Finding Description
The `SweepDust` action decodes a list of `TokenInfo{token, amount}` entries and, for each one, either sends native ETH via a low-level `call` or invokes ERC-20 `transfer`, reverting the entire request if any single leg fails: [2](#0-1) 

This mirrors the `_claim()` reward-transfer bug class from the external report: an unconditional native-token push (`beneficiary.call{value: amount}("")`) whose failure reverts the entire settlement transaction, rather than a pull-based or isolated-failure design. The same anti-pattern also exists in `IntentsBase._withdraw()` (`evm/src/apps/intentsv2/IntentsBase.sol:404-409`) and in `EvmHost.withdraw()`/`HostManager` and `BandwidthManager` treasury withdrawals, but those single-beneficiary paths only self-DoS the party that controls the one beneficiary address and are already isolated at the ISMP dispatch layer: `EvmHost.dispatchIncoming()` explicitly swallows a failing `onAccept` call, deletes the request receipt, and returns without reverting the surrounding batch, so a bad beneficiary only blocks its own message and can be retried/timed out independently: [3](#0-2) 

`SweepDust`, however, is different: it is a *single* ISMP message whose body already contains an *array* of `(token, beneficiary_amount)` legs, all executed in one internal loop with no per-leg isolation and no pull-payment fallback. Because `dispatchIncoming` isolates failures only at the *message* level (not inside a message body), if `req.beneficiary` is any contract that rejects plain ETH transfers (deliberately or accidentally, e.g. a Gnosis Safe with no `receive()`, a paused pausable wallet, or a contract with a broken fallback), then:
- If the array contains a native-ETH (`token == address(0)`) leg, `InsufficientNativeToken()` reverts the whole `onAccept` call.
- The receipt is deleted (per `dispatchIncoming`'s retry logic) so it can be retried — but retrying the exact same message will hit the exact same revert forever, since the beneficiary and the token list are fixed by the original governance-signed sweep request.
- Every *other* token's dust in that same sweep batch (which could include multiple unrelated ERC-20 balances plus ETH) becomes permanently unsweepable through this message, because the revert is all-or-nothing across the loop.

### Impact Explanation
This is a treasury/fund-lock issue on the protocol's own accumulated dust rather than user funds directly, but it satisfies the "loss/lock of funds" criterion in the bounty gate: once a `SweepDust` request is dispatched with a poisoned or bricked beneficiary (or a beneficiary contract that later becomes non-payable, e.g. due to a proxy upgrade or a paused multisig), the entire batch of accumulated protocol fees across multiple tokens becomes permanently stuck in the `IntentGatewayV2` contract, with no code path to re-target a different beneficiary for the already-dispatched message (the beneficiary is embedded in the message body, authenticated as coming from Hyperbridge, and cannot be altered without dispatching a brand-new sweep — which does not free the tokens accounted as already "swept" if partial legs succeeded before the reverting leg, since the whole call reverts and none of the state changes, including `emit DustSwept`, are persisted, but the loop itself has no persisted partial-progress marker to skip already-attempted successful legs on retry, meaning the same failing leg blocks resubmission of the identical message indefinitely).

### Likelihood Explanation
This requires no attacker with privileged access to trigger on its own — `SweepDust` is governance-initiated (`only Hyperbridge` sender check, line 629's `keccak256(incoming.request.source) != keccak256(hyperbridge())`), so the likelihood of a malicious beneficiary is low under normal operation. However, the risk is realistic in a legitimate operational scenario: a treasury/multisig beneficiary address that is upgraded, paused, or has a `receive()`/`fallback()` that later reverts (e.g., a Safe module change, a paymaster-style contract with reentrancy guards, or a contract hitting a gas-stipend limit on `call`) would silently and permanently brick the dust-sweep functionality for every token bundled in that same request, with no admin recovery path other than a new dispatch that still must target a beneficiary capable of receiving all bundled amounts.

### Recommendation
- Make `SweepDust` leg processing failure-isolated (continue-on-error, like `dispatchIncoming` does at the message level) rather than reverting the whole loop on a single leg's failure, and emit a distinguishable event (e.g. `DustSweepFailed`) for legs that could not be delivered.
- Prefer a pull-based withdrawal pattern for the native-ETH leg (credit an internal balance mapping and let the beneficiary claim it, similar to the WETH-wrapping fix referenced in the external report) instead of pushing funds via `call{value:}` inside a batch that can be blocked by one bad recipient.
- Apply the same fix to the ETH legs in `IntentsBase._withdraw()`, `EvmHost.withdraw()`, and `BandwidthManager`'s native-withdraw path for consistency, even though those are currently limited to self-DoS by the per-message isolation in `dispatchIncoming`.

### Proof of Concept
1. Governance accumulates protocol dust in `IntentGatewayV2` across two tokens: native ETH and an ERC-20 (e.g., USDC).
2. Governance dispatches `RequestKind.SweepDust` via Hyperbridge with `outputs = [{token: address(0), amount: X}, {token: USDC, amount: Y}]` and `beneficiary = treasurySafe`.
3. Before the message is delivered, `treasurySafe` is reconfigured (e.g., a module upgrade, or the Safe is intentionally/accidentally made to reject bare ETH transfers via a fallback that reverts).
4. The relayer delivers the `SweepDust` message; `onAccept` executes the loop at `evm/tron/contracts/apps/IntentGatewayV2.sol:656-672`; the native-ETH leg's `req.beneficiary.call{value: amount}("")` fails, `InsufficientNativeToken()` is thrown, and the entire call — including the still-pending USDC leg — reverts.
5. Because the message's beneficiary and token list are immutable once dispatched, resubmitting the exact same ISMP message deterministically reverts again; the USDC dust (and any future dust of these tokens accumulated before a governance fix) remains permanently locked in `IntentGatewayV2` until a brand-new governance-signed `SweepDust` message targeting a different, ETH-compatible beneficiary is dispatched — an out-of-band remediation not guaranteed to recover the exact original batch composition or amounts if further dust has since accrued and mixed with it.
