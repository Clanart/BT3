### Title
NFT royalty rounding-down lets an offer taker underpay (or fully evade) creator royalties on offer acceptance - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
`compute_royalty_amount()` and `royalty_calculation()` in `chia/wallet/nft_wallet/nft_wallet.py` use floor (`//`) integer division to convert an offered/requested fungible amount into the royalty amount owed to an NFT's royalty address. Just as the reported ERC4626 `convertToShares` bug rounds a conversion in the caller's favor and causes value leakage, these functions always round the royalty payment down, and the split across multiple royalty-bearing NFTs (`royalty_split`) is applied before the percentage multiplication, compounding truncation. This structurally biases every NFT-offer settlement in favor of the party constructing/taking the offer and against the royalty recipient. [1](#0-0) [2](#0-1) 

### Finding Description
`compute_royalty_amount` computes `abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS`, i.e., it divides down twice (once by `royalty_split`, once by `10000`) with no rounding-up or remainder-carry logic. This function is the one actually used to build the real royalty `CreateCoin` payments inside `make_nft1_offer`, the code path that constructs the on-chain offer/settlement spend bundle for royalty-bearing NFTs: [3](#0-2) 

The companion `royalty_calculation` static method (used by the `nft_calculate_royalties` RPC that CLI/wallet UIs use to preview and confirm royalty amounts before creating an offer) computes the exact same floor-divided value: [4](#0-3) 

Both of these mirror the audited bug pattern exactly: a value that should be rounded up (or at minimum rounded consistently in favor of the party who is *owed* the value — the royalty recipient) is instead always rounded down in favor of the party who is *paying* (the offer taker / offering wallet). When multiple royalty-eligible NFTs are combined in a single offer, `royalty_split` (`offer_side_royalty_split` / `request_side_royalty_split`) divides the fungible amount among them before applying the percentage, so remainders are dropped at each NFT rather than being reconciled at the end. A `CHANGELOG.md` entry ("Resolved issues when offers involve small amounts and royalties round down to zero (fixes #14744)") confirms this exact rounding-to-zero failure mode has already been observed once in this codebase, and the current implementation still performs unconditional floor division — it merely added overflow/percentage-bound validation, not a rounding-direction fix (see the dedicated regression test `test_small_amount_truncates_to_zero`, which asserts the round-to-zero behavior is expected/tolerated rather than corrected): [5](#0-4) 

### Impact Explanation
Any unprivileged wallet user constructing or taking an NFT offer (`make_nft1_offer` / `respond_to_offer`) determines `royalty_split` and `offered_amount` values that are fully attacker-controlled inputs to `compute_royalty_amount`. By choosing offer amounts and NFT counts such that `amount // royalty_split * percentage // 10000` truncates to a value smaller than the "true" royalty (or exactly zero for small enough per-NFT amounts, or fractional-basis-point percentages), the taker/offerer can settle NFT trades while paying less royalty than the royalty percentage dictates, up to full evasion for small amounts. This is a real, repeatable value-extraction technique available to any offer counterparty against any royalty-enabled NFT creator, since the royalty computation is deterministic and the inputs (offer/request amounts, number of NFTs bundled) are chosen by the party constructing the offer.

### Likelihood Explanation
High likelihood: this requires no special privileges, no race condition, and no interaction with mempool/consensus internals — only crafting an offer (or a multi-NFT offer) with amounts chosen so the floor division truncates the royalty. The `CHANGELOG.md` shows this exact class of rounding-to-zero issue has already manifested in production once (#14744), and the currently-present unit test `test_small_amount_truncates_to_zero` demonstrates the truncation-to-zero condition is trivially reachable with ordinary integer inputs (percentage=100, amount=50).

### Recommendation
Round the royalty computation up (ceiling division) rather than down, or otherwise ensure any truncation strictly favors the royalty recipient rather than the payer, in both `compute_royalty_amount` and `royalty_calculation` in `chia/wallet/nft_wallet/nft_wallet.py`. For multi-NFT offers, avoid dividing the base amount by `royalty_split` before applying the percentage in a way that loses remainder value across NFTs; instead compute the total royalty first and then distribute remainders (e.g., largest-remainder allocation) so the sum paid never falls below the intended aggregate royalty.

### Proof of Concept
Using the existing unit test as a concrete demonstration of the reachable rounding-to-zero condition:
```python
from chia.wallet.nft_wallet.nft_wallet import compute_royalty_amount
# offered_amount = -50 mojos, royalty_split = 1, percentage = 100 (1%)
result = compute_royalty_amount(offered_amount=-50, royalty_split=1, percentage=100)
assert result == 0  # true royalty is 0.5 mojo; taker pays zero royalty
``` [5](#0-4) 
By constructing an offer with per-NFT-normalized amounts near this floor-division boundary (and/or bundling multiple royalty NFTs to shrink each per-NFT share via `royalty_split`), a taker can systematically reduce or eliminate the royalty owed on trades of any total size, since the truncation is applied per NFT/per fungible asset before totals are summed in `make_nft1_offer`. def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
