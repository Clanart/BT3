Given the exploit pattern in the report — an **unprivileged/automatic trigger** that consumes **attacker-influenceable input** and performs a **sensitive action without additional trust checks**, resulting in loss of protected assets — the closest verifiable analog in this codebase is the reintroduction of `protocol.file.allow=always` for submodule updates that run automatically as part of normal checkout/clone/pull flows.

### Title
Submodule updates re-enable `protocol.file.allow=always`, bypassing Git's local-file-read protection for attacker-controlled submodule URLs - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` in [1](#0-0)  conditionally injects `-c protocol.file.allow=always` before running `git submodule update --init --recursive`, gated only by a boolean `allowFileProtocol` flag. This function is invoked automatically after ordinary, unprivileged operations — `checkoutBranch` and `checkoutCommit` — as part of the normal user flow of switching branches or checking out a commit in a repository the user has cloned or fetched: [2](#0-1) [3](#0-2) .

### Finding Description
Git disables the `file://` protocol for submodules by default (`protocol.file.allow=user`/deny for recursive clones) specifically to stop a hostile upstream repository from declaring a submodule whose URL points at an arbitrary local filesystem path (e.g. `file:///home/victim/.ssh` or any absolute path) and having that path's contents copied into the working tree during an automated `submodule update --init --recursive`. Desktop's `updateSubmodulesAfterOperation` explicitly overrides that protection with `protocol.file.allow=always` whenever `allowFileProtocol` is `true` [4](#0-3) .

The `.gitmodules` file and submodule URLs are fully attacker-controlled content of a cloned/fetched repository — the exact "attacker controls a cloned/fetched repository" primitive named in the task's valid-impact list. If a repository containing a malicious `.gitmodules` (with a `file://` submodule URL targeting a sensitive local path) is opened, and Desktop performs a checkout/branch-switch with the file-protocol override enabled, git will read/copy that local path into the repository's submodule directory — a supported vector for the "file write or read outside the repo" impact class.

### Impact Explanation
If the file-protocol override is applied without a corresponding trust decision equivalent to Desktop's own "unsafe repository" ownership check (used elsewhere, e.g. [5](#0-4) ), a hostile repository can cause Desktop to read arbitrary local files/directories into the tracked working tree via a submodule pointing at a `file://` path, which can then be surfaced back to the attacker if the victim later commits/pushes, or simply exposes local file contents in the UI/diff. This corresponds to "file write or read outside the repo" and "silent corruption of what the user commits" in the accepted impact list.

### Likelihood Explanation
Exploitability hinges on how `allowFileProtocol` is set at the call sites in `app-store.ts`; I was unable to fully confirm (within the tool budget available) whether the boolean is gated behind an explicit user-trust decision (e.g., the same repository-ownership/"unsafe path" trust prompt used for bare/foreign-owned repositories) or is set unconditionally for checkout/clone flows. This is a real limitation in my verification and should be checked directly in `app/src/lib/stores/app-store.ts` (8 matches for `checkoutBranch(`/`checkoutCommit(`/`allowFileProtocol`) before treating this as confirmed-exploitable, since if the flag is only ever `true` after an explicit "I trust this repository owner" prompt, this finding would not qualify as unprivileged.

### Recommendation
Verify all call sites that set `allowFileProtocol = true` in `app-store.ts` are strictly conditioned on the repository having already passed Desktop's own "safe directory"/trust check (the same one used for bare/unsafe-repository warnings). If any automatic (non-prompted) code path can reach `updateSubmodulesAfterOperation` with `allowFileProtocol=true` for a freshly cloned/fetched untrusted repository, remove the override or require an explicit, separate confirmation before enabling `protocol.file.allow=always`.

### Proof of Concept
1. Attacker publishes a repository whose `.gitmodules` declares a submodule with `url = file:///path/to/sensitive/local/data` (or a path traversal into another local repo).
2. Victim clones/fetches the repository in Desktop and performs a normal, unprivileged action such as switching branches (`checkoutBranch`) or checking out a commit that includes the malicious `.gitmodules`.
3. If the reached call path sets `allowFileProtocol = true`, `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, causing git to clone the local path into the submodule directory inside the working tree — reading data the attacker did not otherwise have access to, and making it part of the repository, where it can be committed/pushed or inspected via the UI.

*Note: This analog is submitted with a confidence caveat on likelihood — full confirmation requires inspecting the exact predicate around `allowFileProtocol` in `app/src/lib/stores/app-store.ts`, which I could not fully retrieve in the available tool budget.*
