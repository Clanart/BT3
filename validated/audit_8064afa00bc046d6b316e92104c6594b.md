## Title
Silent redirection of a repository's `origin` remote to an unrelated (attacker-controlled) repository via `updateRemoteUrl` - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The `_sendToken`-style bug class is: a destination is recomputed from an untrusted/derived value without validating that it still refers to the *same identity* as before, so the artifact (tokens in the original report; a git remote in Desktop) silently ends up pointing at an unintended target. `updateRemoteUrl` reproduces this pattern: it rewrites a user's `origin` remote URL to whatever `clone_url` the GitHub API returns for `owner/name`, verifying only that the *protocol* and *previous remote* match — never that the repository's stable identity (its numeric GitHub id) is unchanged.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` re-resolves a tracked repository purely by `owner`/`name` string lookup: [1](#0-0) 

It calls `api.fetchRepository(owner, name)` — a plain `GET repos/{owner}/{name}` — and then feeds the result straight into `updateRemoteUrl`: [2](#0-1) 

`updateRemoteUrl` then decides whether to silently overwrite the local `origin` remote: [3](#0-2) 

The three guards are:
1. `protocolsMatch` — only compares `https:` vs `git@...` style protocol, not host/owner/name.
2. `remoteUrlUnchanged` — confirms the *current* local remote still matches the *previously cached* `cloneURL`, i.e. the user hasn't manually edited the remote.
3. `!urlsMatch` — requires the *new* URL to differ from the current one (this is what lets legitimate renames trigger the update).

None of these three checks validate that the repository returned by `repos/{owner}/{name}` is the *same repository* (same GitHub numeric id) as the one the user originally added. `GitHubRepository` (the local model) explicitly does **not** store the GitHub API's numeric id — only an internal `dbID` — so there is no way for `updateRemoteUrl` to detect that the API returned data for a different, unrelated repository: [4](#0-3) 

This design is intended to follow legitimate renames (GitHub returns a 301/redirected payload with a new `clone_url` for a renamed repo), but GitHub also permits repository **name-squatting**: after an owner renames or deletes `owner/repo`, anyone can create a brand-new, unrelated repository at that exact `owner/repo` path. The next time Desktop performs a background fetch/refresh (`_fetch` → `withRefreshedGitHubRepository` → `repositoryWithRefreshedGitHubRepository`), `fetchRepository(owner, name)` will resolve to the squatter's repository, and `updateRemoteUrl` — seeing a same-protocol, different-URL, "still-matching-prior-remote" state — will silently call `gitStore.setRemoteURL(...)` and repoint `origin` at the attacker's repository, with no user prompt or confirmation.

### Impact Explanation
This meets the report's valid-impact criterion of "silent corruption of what the user commits or pushes": the user's subsequent `git push` (and any `git fetch`/`git pull` that trusts `origin`) will silently target a repository the user never chose, controlled by an attacker who simply reserved the vacated `owner/name` slug. This can lead to private code being pushed to an attacker-owned repo, or the user unknowingly pulling/merging attacker-supplied history. The change happens with no UI confirmation — `updateRemoteUrl` runs as part of routine background/foreground fetch operations.

### Likelihood Explanation
The attacker's only requirement is registering a repository at a name that a victim's local remote already points to after the original owner deletes/renames/transfers it away — a normal, unprivileged GitHub action requiring no interaction with the victim beyond them having previously added the original repository in Desktop and Desktop performing a routine background fetch afterward. This fits the "attacker controls a GitHub API object" pathway explicitly called out as in-scope by the task.

### Recommendation
Track and verify the GitHub API's numeric repository `id` (not just `owner`/`name`/`cloneURL`) in the local `GitHubRepository`/database record, and have `updateRemoteUrl` (and `repositoryWithRefreshedGitHubRepository`) refuse to auto-update the remote (or auto-reassociate the `GitHubRepository`) unless the API-returned `id` matches the previously stored id. If the id differs, prompt the user explicitly before repointing `origin`, similar to how forks require an explicit `_convertRepositoryToFork` action.

### Proof of Concept
1. Victim adds `https://github.com/alice/foo` to GitHub Desktop; Desktop stores `GitHubRepository{owner: alice, name: foo, cloneURL: https://github.com/alice/foo}` and `origin` = the same URL.
2. Alice deletes or renames `alice/foo` away (a normal, permitted GitHub action).
3. Attacker (mallory) creates a brand-new, unrelated repository at `https://github.com/alice/foo` — not possible if alice controls the namespace, but easily reproduced with organization repos where a repo is deleted and re-created by any org member, or transferred and the name released — the point being the *name* `owner/name` is decoupled from identity.
4. On the victim's next background fetch, `performFetch`/`_fetch` → `withRefreshedGitHubRepository` → `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository('alice','foo')`, which now returns mallory's repo data including its `clone_url`.
5. `updateRemoteUrl` sees: protocol match (both `https:`), `remoteUrlUnchanged` true (origin still equals the last cached `cloneURL` for `alice/foo`), and `!urlsMatch` true (new clone_url differs superficially, e.g. different case or trailing slash is not required — any difference in the API's returned `clone_url` string vs. the current remote suffices) → it calls `gitStore.setRemoteURL('origin', <mallory's clone_url>)` without any prompt.
6. The victim's next `git push` on `origin` silently pushes to mallory's repository.

Note: I was unable to fully verify from the indexed code whether GitHub's actual repository-rename API behavior would return a *different* `clone_url` string in the squatting scenario described (versus an identical string, in which case `!urlsMatch` would suppress the update) — this depends on exact string formatting nuances of `clone_url` for renamed vs. newly created repos, which is an external GitHub API behavior not verifiable from the local codebase alone. The core code-level defect — absence of any repository-identity (numeric id) check in `updateRemoteUrl` — is confirmed directly in the cited source.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```
