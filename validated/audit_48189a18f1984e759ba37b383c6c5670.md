### Title
Missing "already spent" check on `deposit_outpoint` in `is_deposit_valid` allows N-of-N signatures on a second move-to-vault tx for an already-vaulted outpoint - (File: core/src/verifier.rs)

### Summary
`Verifier::is_deposit_valid` validates a `deposit_outpoint` only against the original deposit transaction's output value, script pubkey, and confirmation depth, but never checks whether that outpoint has already been consumed by a prior `move_to_vault_tx`. An attacker can submit a new `DepositData` (with a different `actors` set) referencing an outpoint that was already moved to the vault, and get verifiers to produce N-of-N partial signatures for a second move-to-vault transaction spending the same outpoint.

### Finding Description
The binding that should hold is: `deposit_outpoint` → exactly one unspent bridge-amount UTXO that verifiers will ever sign a move tx for. In `core/src/verifier.rs:673-731`, `is_deposit_valid` fetches the deposit transaction with `self.rpc.get_tx_of_txid(&deposit_txid)` [1](#0-0)  and reads `deposit_tx.output[vout]` to check `value == bridge_amount` [2](#0-1)  and `script_pubkey == expected_scriptpubkey` computed from the caller-supplied `DepositData` via `create_taproot_address(get_deposit_scripts(...))` [3](#0-2) , then checks the confirming block height via `get_raw_transaction_info`/`get_block_info` against `start_height` [4](#0-3) . None of these three checks, nor any other call in the function, queries whether the specific outpoint has already been spent (no `is_outpoint_spent`/`gettxout`-style call exists anywhere in `verifier.rs`). All queried data (`get_tx_of_txid`, `get_raw_transaction_info`) describes the *original* deposit transaction, which remains immutable and "valid-looking" regardless of whether its output has since been spent by a `move_to_vault_tx`. Consequently, a second `DepositData` object carrying the same `deposit_outpoint` but a different `actors` set (e.g., an attacker-controlled watchtower or operator set) passes every check in `is_deposit_valid` unchanged, and the verifier proceeds to produce partial N-of-N signatures for a brand-new move tx spending the same, already-vaulted, outpoint.

### Impact Explanation
This matches the explicitly listed Critical impact category "N-of-N partial signatures for an unauthorised spend": verifiers cryptographically commit signature shares to a move-to-vault transaction spending a UTXO that the protocol's binding says should only ever be spent once, and Citrea's Bridge contract (which tracks deposits by outpoint) never authorized a second spend. Although the actual Bitcoin network would reject broadcast of the second move tx once the first is confirmed (a double-spend), the security-relevant harm — verifiers signing for a spend they should never sign for — has already occurred, and is repeatable for every already-vaulted deposit outpoint in the system, requiring no privileged role, only knowledge of a `deposit_outpoint` and the ability to submit a `DepositData` via `new_deposit`.

### Likelihood Explanation
Any unprivileged party can reuse a publicly-known, already-completed deposit's outpoint (e.g., observed on-chain) and submit a `new_deposit` request through the aggregator with attacker-chosen `actors`. No BTC needs to be spent by the attacker for this specific request since the outpoint's value/script checks are satisfied by the *original* deposit transaction already on chain. The only preconditions are that a prior deposit's move tx has confirmed and the attacker can reach the aggregator's gRPC `new_deposit` endpoint, both of which fall squarely within the defined unprivileged attacker capabilities.

### Recommendation
Add an explicit "not yet spent" check in `is_deposit_valid` — e.g., query the outpoint via a UTXO-set lookup (`gettxout`/`is_outpoint_spent`) or check the verifier's own database for an existing signed/finalized deposit record for the same `deposit_outpoint`, and reject with `BridgeError::InvalidDeposit` if the outpoint is already spent or already has an associated deposit entry in the DB.
