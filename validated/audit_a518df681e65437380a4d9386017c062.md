## Analog Found

### Title
Slashing halts the chain when reward-withdrawal fails during redelegation unbonding - (File: `sei-cosmos/x/staking/keeper/slash.go`)

### Summary
`SlashRedelegation` unbonds shares from the redelegation's destination validator by calling `k.Unbond(slashCtx, delegatorAddress, valDstAddr, sharesToUnbond)` as part of processing a validator slash [1](#0-0) . `Unbond` fires the `BeforeDelegationSharesModified` staking hook, and the distribution module's implementation of that hook unconditionally calls `withdrawDelegationRewards` and `panic`s if it returns an error [2](#0-1) . `withdrawDelegationRewards` sends rewards via `k.bankKeeper.SendCoinsFromModuleToAccount` to the delegator's configured withdraw address and returns an error if that send fails [3](#0-2) . This mirrors the reported bug class exactly: a slashing operation embeds an unconditional "claim rewards" step, and if that claim reverts, the surrounding privileged/protective operation (here, slashing) fails too — except in sei-chain's Cosmos SDK fork this happens inside `BeginBlock`/evidence processing, so instead of merely blocking slashing it panics and halts consensus.

### Finding Description
The codebase itself already demonstrates awareness of this exact failure mode: `AfterValidatorRemoved` was hardened specifically because a withdraw address can become unable to receive funds (e.g., "an EVM address whose Sei mapping was re-associated to a different address"), and sending to it would otherwise panic in `EndBlock` and halt the chain [4](#0-3) . That fix checks `canReceiveWithdrawAddr` before attempting the send and diverts to the community pool instead of panicking. However, `BeforeDelegationSharesModified` — which is exactly the hook triggered mid-slash via `SlashRedelegation` → `Unbond` — was **not** given the same protection; it still calls `withdrawDelegationRewards` and panics directly on any error [5](#0-4) .

The staking module even added a dedicated slash-context marker (`WithSlashDelegationModification`/`IsSlashDelegationModification`) to let hooks behave differently when a delegation change happens as a side effect of slashing [6](#0-5) , and the gov module's staking hooks do check this marker to avoid unsafe work during slashing [7](#0-6) . The distribution module's `BeforeDelegationSharesModified`, by contrast, ignores this marker and always attempts the reward withdrawal/send, regardless of whether it's being invoked from a slash.

### Impact Explanation
A delegator can set their reward withdraw address to a Sei address derived from an EVM association, then re-associate that EVM address to a different Sei address, making the original withdraw address unable to receive funds (the exact scenario the `AfterValidatorRemoved` fix comments describe). If that delegator has a redelegation and the source validator is later slashed (e.g., for downtime or double-signing, a routine and expected event), `SlashRedelegation`'s call to `Unbond` will trigger `BeforeDelegationSharesModified`, which will attempt to pay out rewards to the now-unreceivable withdraw address, causing `SendCoinsFromModuleToAccount` to fail and `withdrawDelegationRewards`/the hook to panic. Since slashing runs deterministically as part of block processing (evidence/downtime handling in `BeginBlock`), this panic occurs identically on every validator processing that block, producing a chain-wide consensus halt — a validator/chain halt, which is an explicitly in-scope critical impact.

### Likelihood Explanation
The precondition (an unreceivable withdraw address via EVM re-association) is user-controllable and requires no special privilege — a normal account holder can set it up unilaterally. The triggering event (a validator slash) is a routine, expected occurrence on any live chain (downtime jailing happens regularly). The only additional requirement is that the attacker's account be a redelegator to the validator that eventually gets slashed, which the attacker fully controls by choosing to redelegate to a validator they intend to cause to be slashed or simply wait for. This makes the scenario realistically triggerable, not purely theoretical.

### Recommendation
Apply the same defensive pattern used in `AfterValidatorRemoved` to `BeforeDelegationSharesModified`: check `canReceiveWithdrawAddr` (or equivalent) before calling `SendCoinsFromModuleToAccount` inside `withdrawDelegationRewards`, and route funds to the community pool (or otherwise handle gracefully) instead of returning/propagating an error that leads to a panic. Alternatively, honor the existing `IsSlashDelegationModification` marker in the distribution hook to skip/soften reward withdrawal when the shares modification originates from a validator slash, consistent with how the gov module's staking hooks already treat that marker.

### Proof of Concept
1. Delegator `D` associates EVM address `E` to Sei address `S1`, sets `S1` as their distribution withdraw address (`SetWithdrawAddr`), and delegates/redelegates to validator `V2` (having previously delegated to `V1`, creating a `V1→V2` redelegation).
2. `D` re-associates `E` to a different Sei address `S2`, so `S1` can no longer be resolved as receivable (mirrors the condition described and fixed for `AfterValidatorRemoved`, see [8](#0-7) ).
3. Validator `V1` is slashed for downtime/double-sign in `BeginBlock`, invoking `Keeper.Slash` → `SlashRedelegation` → `k.Unbond(slashCtx, D, V2, sharesToUnbond)` [1](#0-0) .
4. `Unbond` fires `BeforeDelegationSharesModified`, distribution's hook calls `withdrawDelegationRewards`, the send to `S1` fails, and the hook panics [2](#0-1) .
5. The panic propagates out of `BeginBlock` processing on every node, halting the chain.

package types

import (
	"context"

	sdk "github.com/sei-protocol/sei-chain/sei-cosmos/types"
)

type slashDelegationModificationKey struct{}

// WithSlashDelegationModification marks delegation changes made while applying a validator slash.
func WithSlashDelegationModification(ctx sdk.Context) sdk.Context {
	return ctx.WithContext(context.WithValue(ctx.Context(), slashDelegationModificationKey{}, true))
}

// IsSlashDelegationModification reports whether a delegation change is part of a validator slash.
func IsSlashDelegationModification(ctx sdk.Context) bool {
	marked, _ := ctx.Context().Value(slashDelegationModificationKey{}).(bool)
	return marked
}
