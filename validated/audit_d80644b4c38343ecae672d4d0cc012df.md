Based on my research, I found a concrete Desktop analog to the Yearn "wrong base value used for a computation" bug class: computing a partial-commit patch from the wrong diff baseline for renamed files.

### Title
Partial commits for renamed files are built from a diff against the (mutable) index instead of HEAD, allowing the actually-committed content to silently diverge from what the user selected - ([File: app/src/lib/git/diff.ts])

### Summary
The Yearn report's root cause is generic: a value that should come from a fixed, trusted accounting source (`totalIdle`) is instead derived from a mutable, externally-influenceable source (`balanceOf`), so downstream math (asset/share conversion) can silently be wrong. GitHub Desktop has a structurally identical pattern in `getWorkingDirectoryDiff`: for `Renamed` files it deliberately diffs the working tree against the **index** instead of `HEAD`, a divergence the code comments explicitly flag as incorrect. Because line-selection state (`DiffSelection`) is captured as absolute line offsets against whichever diff happened to be computed, and the diff is recomputed a second time at commit time after the index has been reset, the two diffs can have different hunk layouts when the index has diverged from `HEAD`. The user's selection then gets silently reinterpreted against a different diff, and the wrong lines can end up in the commit.

### Finding Description
`getWorkingDirectoryDiff` branches on file status when building the `git diff` arguments: [1](#0-0) 

For `Renamed` files it diffs the working tree against the index (`git diff -- <path>`, i.e. no `HEAD` argument), instead of against `HEAD` as done for every other status kind. The comment in the code acknowledges this is wrong:
"NB: Technically this is incorrect, the best kind of incorrect. In order to show exactly what will end up in the commit we should perform a diff between the new file and the old file as it appears in HEAD. By diffing against the index we won't show any changes already staged to the renamed file which differs from our other diffs."

This same function is called twice in the partial-commit pipeline:
1. Once when the Changes list/diff viewer renders the file and the user makes line/hunk selections — this diff is computed against whatever the index currently is.
2. Again inside `applyPatchToIndex` when `formatPatch` builds the actual patch to apply to the index at commit time: [2](#0-1) 

`createCommit` runs `unstageAll` (`git reset -- .`) immediately before `stageFiles`, which resets the index to match `HEAD`: [3](#0-2) [4](#0-3) 

So diff #1 (used to build the UI and the user's `DiffSelection`) is computed against the *pre-commit index state* (whatever it happened to be — e.g. left over from a prior operation, a hook, a merge, or any external `git add`), while diff #2 (used by `formatPatch` to actually produce the patch that gets applied) is computed against the index *after* it has been reset to `HEAD`. `DiffSelection.isSelected(absoluteIndex)` in `formatPatch` blindly trusts that the hunk/line layout of diff #2 matches diff #1: [5](#0-4) 

If the index state at diff #1 time differs from `HEAD` in a way that shifts hunk boundaries or line counts (e.g., an extra staged line, a different set of staged hunks for that renamed file), the same absolute line index in diff #2 can correspond to a completely different physical line than what the user saw and selected in the UI, causing the wrong lines to be included/excluded from the final commit.

### Impact Explanation
This falls under "silent corruption of what the user commits" — the exact class of impact defined as valid. A user who deliberately selects a subset of lines to commit from a renamed file can end up with a commit whose actual diff does not match their selection, without any error or warning, because the line-selection indices are computed against one diff and consumed against a structurally different one.

### Likelihood Explanation
This requires that, at the time the user opens/interacts with the Changes view for a `Renamed` file, the git index for that path already differs from `HEAD` (i.e., the file has some pre-existing staged content, e.g. left over from `git mv` + manual `git add` outside Desktop, an interrupted previous partial-commit, or a merge/rebase in progress touching that path) in a way that changes hunk layout relative to a `HEAD`-based diff. This is a plausible but not universal repo state, so likelihood is moderate rather than high; it does not require any privileged access, only a repository (local or freshly cloned/checked-out) that happens to have this staged-vs-HEAD divergence for a renamed file when the user performs a partial-line commit.

### Recommendation
Make `getWorkingDirectoryDiff` for `Renamed` files diff against `HEAD` (consistent with all other status kinds) rather than the index, as the existing code comment already recommends. Alternatively, ensure the diff used to establish the `DiffSelection` line indices and the diff used by `formatPatch`/`applyPatchToIndex` at commit time are guaranteed to be structurally identical (e.g., by reusing the exact same diff object end-to-end instead of recomputing it after `unstageAll`/`stageFiles` mutate index state).

### Proof of Concept
1. Create a repo, commit `foo` with content `line1`.
2. `git mv foo bar`.
3. Manually stage a partial change to `bar` (outside Desktop) so the index for `bar` differs from `HEAD` (e.g. `echo line2 >> bar && git add bar`), then further modify `bar` in the working tree with `echo line3 >> bar`.
4. Open the repo in Desktop; the Changes list shows `bar` as `Renamed` and computes its diff via `getWorkingDirectoryDiff`, which diffs working tree vs. index (per `app/src/lib/git/diff.ts:379-390`), showing only the `line3` delta (the already-staged `line2` change against `HEAD` is hidden per the code's own comment).
5. Select only some of the visible hunk/lines for a partial commit and commit.
6. `createCommit` calls `unstageAll` (resets index to `HEAD`) then `stageFiles` → `applyPatchToIndex`, which recomputes the diff (now `HEAD` vs. working tree effectively includes both `line2` and `line3` deltas) and applies the user's previously-captured absolute-line-index selection against this new, differently-shaped diff via `formatPatch`.
7. Inspect the resulting commit's contents; because hunk boundaries differ between step 4's diff and step 6's diff, the committed content does not correspond to the lines the user actually selected in the UI.

  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++

          newCount++
        }
