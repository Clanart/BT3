### Title
Hardcoded `DUST` threshold applied to arbitrary `script_pubkey` lets `SignableTransaction` produce outputs that are dust under real network policy, burning funds or stalling payments - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` hardcodes `pub const DUST: u64 = 546` (send.rs:32) and uses it as a flat minimum for every payment amount regardless of the destination script, and as the cutoff for whether leftover value becomes a change output or is burned as fee. Bitcoin's dust limit is not a fixed constant: `GetDustThreshold` computes it as a function of the output's serialized size multiplied by the `dustRelayFee` rate, which is a policy parameter that has changed over time and differs per output type (e.g., ~2940 sat for bare multisig, 546 for P2PKH, 294 for P2TR at the default rate). A single hardcoded 546 therefore both under- and over-estimates the true spendability threshold depending on the script type and fee environment.

### Finding Description
Two concrete effects exist in `SignableTransaction::new`:

1. **Payment check (send.rs:165-169).** `if *amount < DUST { Err(DustPayment) }` treats 546 sat as sufficient for *any* `script_pubkey`. The payment destination is a caller-supplied `ScriptBuf`, so a withdrawal of, e.g., 600 sat to a bare-multisig script (true dust ~2940) or to a standard script under a raised `dustRelayFee` passes the check. The resulting transaction either contains a dust output (non-standard, rejected by default relay policy → the signed plan can never confirm, stalling the multisig's scheduled payment) or, if broadcast directly to miners, locks funds in an output that cannot be economically spent — effectively the same class of "value given out below the real cost basis" as the hardcoded loan-to-collateral ratio.

2. **Change decision (send.rs:223-235).** If `input_sat - payment_sat - fee_with_change >= 546`, the leftover is committed to a change output. While Serai's change is always P2TR (true dust 294 today), the check is against a static 546: if `dustRelayFee` is ever doubled (as has happened historically with policy shifts), change in the 294–587 range is still emitted, producing a non-standard transaction that cannot relay, or an unspendable change output.

Conversely, the flat check also *rejects* payments in the 294–545 range to P2TR outputs, which are perfectly spendable — a correctness issue, though not fund-losing.

### Impact Explanation
- Payments scheduled to script types whose real dust threshold exceeds 546 (or under an elevated relay fee) produce transactions that either cannot be broadcast (DoS on the plan) or send value into provably unspendable outputs — permanent loss of the payment amount. Because the check is compile-time constant, there is no administrative or dynamic path to correct it without redeploying the wallet code, exactly the rigidity defect in the reference finding.
- Change outputs near the boundary can likewise render the whole transaction non-standard.

Severity: Medium — reachable by an unprivileged party who controls a payment destination script and amount, but exploitation requires either a higher-dust script type or a relay-policy change, and per-instance loss is bounded by the output value.

### Likelihood Explanation
Payment amounts and destination scripts are public inputs to the wallet path; nothing restricts payments to Serai's own P2TR form. Reliance on stale policy constants is inherent (the code comments at send.rs:27-31 already acknowledge skipping SegWit differentiation), so drift is a matter of network policy evolution rather than attacker action alone.

### Recommendation
Compute the dust threshold dynamically per output: use the serialized size of each `TxOut` (`dust` via `TxOut::minimal_non_dust` / script-size-based calculation against a current `dustRelayFee`) rather than a global `DUST` constant, and apply the same per-script computation to the change output decision. Expose the relay-fee parameter so it can be adjusted without code changes.
