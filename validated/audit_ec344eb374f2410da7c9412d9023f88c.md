## Analysis

The report's broken invariant is: **a prefix/length-bounded byte comparison that fails to correctly bound the comparison window, causing values that only share a common prefix to be treated as "contained"/"equal" when they are not.**

The GitHub Desktop analog is the containment check in `resolveWithin` / `_resolveWithin`: [1](#0-0) 

```ts
const resolved = resolve(normalizedRoot, normalizedRelative)

const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)

return realResolved.startsWith(realRoot) ? resolved : null
```

### Title
Path containment check in `resolveWithin` uses raw string-prefix comparison without separator boundary, allowing sibling-directory escape - (`app/src/lib/path.ts`)

### Summary
`_resolveWithin` is the function GitHub Desktop relies on whenever it needs to guarantee that an attacker-influenced relative path (from a deep link, a repository's own contents, or PR data) resolves to a location *inside* a trusted root directory before it is used for file I/O. The final containment check, `realResolved.startsWith(realRoot)`, is a plain string-prefix comparison. Just like the ENS `BytesUtils.compare` bug where a length-bounded comparison masked the wrong characters and treated dissimilar strings as equal, this check masks the fact that `startsWith` does not stop at a path-separator boundary. A resolved path such as `/Users/victim/repo-evil/secret` legitimately "starts with" the root `/Users/victim/repo`, even though `repo-evil` is a sibling directory, not a subdirectory of `repo`.

### Finding Description
`resolveWithin(rootPath, ...pathSegments)` is documented to guarantee the returned path "reside[s] at, or underneath" `rootPath`: [2](#0-1) 

The guard against `..` traversal and symlink escape is implemented correctly for directory-traversal segments (verified via `realpath` plus `resolve`), but the final decision of "is this actually inside the root" is a bare `String.prototype.startsWith` call with no check that the next character after the root prefix is a path separator (or that the two paths are exactly equal). This is structurally identical to the ENS bug: the mask/length boundary that should delimit "relevant" characters is missing, so a value that merely shares a prefix with the trusted boundary is accepted as if it were truly contained by it.

Existing guards do not stop this path because:
- The null-byte check only rejects embedded NULs, not prefix collisions.
- `realpath` resolution correctly defeats symlink-based traversal, but it does not change the final string comparison.
- The traversal-segment resolution via `Path.resolve` prevents `..`-only escapes, but says nothing about sibling directories whose names happen to extend the root's name (`repo` vs `repo-evil`, `repo` vs `repository2`, etc.).

### Impact Explanation
`resolveWithin` is used to gate file access derived from attacker-influenced input:
- `dispatcher.ts`'s `openRepositoryFromUrl` uses it to validate a `filepath` supplied via a GitHub Desktop deep link (`x-github-client://openRepo/...&filepath=...`) before calling `shell.showItemInFolder(resolved)`: [3](#0-2) 
- It is also used in `copilot-conflict-context.ts` and `app-store.ts` (both reference `resolveWithin`), places that build file paths from repository/PR content that can be attacker-controlled (a cloned/fetched repository the user opens).

If the trusted root (e.g., the repository path or a designated conflict/session directory) happens to be a prefix of an unrelated, attacker-reachable sibling directory name, this check will incorrectly treat paths in that sibling as "inside" the root and allow them through. The consequence is a file-path check bypass: file reveal/open operations, or path construction for git/session operations, could operate on paths just outside the intended root — matching the "file write or read outside the repo" impact class explicitly listed as in-scope.

### Likelihood Explanation
This requires a specific but realistic coincidence: the trusted root path must be a literal string prefix of another directory that exists (or can be created) alongside it — e.g., a repository cloned as `myrepo` sitting next to a directory named `myrepo-backup` or `myrepository`, both reachable under the user's normal clone base directory. Given GitHub Desktop's default clone locations (e.g., `~/Documents/GitHub/`) commonly contain many repos side-by-side, and repo names are attacker-influenced when following a URL/deep-link based clone-and-open flow, this is a plausible, low-interaction condition rather than a contrived edge case. It does not require local/physical access, admin rights, or prior malware — only that the user click a deep link or open a maliciously-named/crafted repository.

### Recommendation
Replace the raw prefix check with a boundary-aware comparison, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
using the platform-appropriate separator from the `options` parameter (`join`/`normalize`/`resolve` already vary by platform, so the separator should too), to ensure the match only succeeds at a true path-segment boundary, exactly analogous to correcting `BytesUtils.compare`'s mask to only compare bytes within the true `shortest` length.

### Proof of Concept
1. Create two directories: `/Users/victim/Documents/GitHub/repo` (the trusted root passed to `resolveWithin`) and `/Users/victim/Documents/GitHub/repo-evil/secret.txt` (attacker-reachable, e.g., created by opening/cloning a similarly-named repository or a nested worktree).
2. Call `resolveWithin('/Users/victim/Documents/GitHub/repo', '../repo-evil/secret.txt')`.
3. `Path.resolve` computes `/Users/victim/Documents/GitHub/repo-evil/secret.txt`; `realpath` resolves both `realRoot` (`.../repo`) and `realResolved` (`.../repo-evil/secret.txt`).
4. `realResolved.startsWith(realRoot)` evaluates to `true` because `"...repo-evil/secret.txt"` starts with the substring `"...repo"`, even though `repo-evil` is not a subdirectory of `repo`. The function returns the resolved path instead of `null`, allowing a caller such as `openRepositoryFromUrl`'s deep-link handler to reveal/open a file outside the intended repository root. [4](#0-3)  confirms the existing unit tests only cover `..`-traversal and symlink cases, and do not test the sibling-prefix scenario described above — this gap is consistent with the bug going unnoticed, mirroring how the original ENS bug "might go unnoticed with any code that uses `compare`."
