### Title
SchnorrAggregate verification weights don't bind the nonces or keys, enabling universal forgery - ([File: crypto/schnorr/src/aggregate.rs])

### Summary
The referenced finding concerns a slippage check that validates a linear ratio of sums instead of the actual nonlinear constraint (the StableSwap invariant), so transactions violating the real constraint are accepted. The analogous flaw in Serai lives in `SchnorrAggregate::verify` (`crypto/schnorr/src/aggregate.rs:127-146`): the aggregate signature is checked as a single linear combination `Σ z_i·(R_i + c_i·K_i) − s·G = 0`, but the per-signature weights `z_i` are derived only from the challenges — never binding the `Rs` or the public keys. Because every attacker-controlled term (`Rs`, `s`) enters linearly with publicly computable coefficients, an attacker can solve the verification equation outright, forging a `SchnorrAggregate` that verifies for arbitrary keys and challenges without knowing any private key.

### Finding Description
In the half-aggregation scheme of https://eprint.iacr.org/2021/350, each signature's weight must be a hash bound to *all* aggregated nonces, public keys, and messages, precisely so the verifier's linear equation can't be rearranged after the weights are known. Here:

- `verify` builds a `DigestTranscript` over `dst` and appends only the challenges (`aggregate.rs:132-136`). The `Rs` from the signature and the public keys from `keys_and_challenges` are never transcribed.
- `weight` (`aggregate.rs:22-65`) then derives each `z_i` deterministically from that challenge-only digest.
- The final check is `multiexp_vartime` over `(z_i, R_i)`, `(z_i·c_i, K_i)`, and `(−s, G)` (`aggregate.rs:138-145`).

Since `z_i` is a deterministic public function of `(dst, challenges)` alone, an attacker computing the same weights can pick the group elements `R_i` to cancel the key terms: choose any scalars `r_i`, set `R_i = r_i·G − c_i·K_i`, and set `s = Σ z_i·r_i`. The statement collapses to `Σ z_i·r_i·G − s·G = 0` — identically true — while the attacker never knew `r_i + c_i·k_i` for any private key `k_i`. The honest aggregator (`SchnorrAggregator::complete`, `aggregate.rs:175-186`) produces `s = Σ z_i·s_i` consistent with this formula, so the scheme is internally consistent but not sound: `R_i` and `s` are attacker-chosen scalars/points with no binding committing them before `z_i` is fixed.

This is reachable purely from public inputs: `SchnorrAggregate::read` (`aggregate.rs:77-88`) accepts an arbitrary length-prefixed `Vec<C::G>` plus scalar from untrusted bytes, and `verify` takes only caller-supplied `(key, challenge)` pairs. No secret, trusted peer, or colluding threshold is required — exactly matching the accepted impact class of "a forged proof or signature" / "an incorrect verifier formula".

### Impact Explanation
Any consumer relying on `SchnorrAggregate::verify` to establish that a set of Schnorr signatures existed (e.g., Tendermint-style vote aggregation, where this crate's `SchnorrAggregate` is used in `coordinator/tributary`) can be presented a fully valid-looking aggregate for keys and challenges of the attacker's choosing, with zero signature shares actually produced. This is a signature forgery against every key included in `keys_and_challenges`.

### Likelihood Explanation
The forgery is deterministic and computable in milliseconds: the attacker computes `z_i` by replaying the public `weight` derivation over the public challenges, picks random `r_i`, and emits `R_i = r_i·G − c_i·K_i`, `s = Σ z_i·r_i` via `write`/`serialize`. It succeeds with probability 1 whenever `verify` is called on attacker-controlled bytes, requiring only that challenges be known to the attacker — which they always are, being public transcript outputs.

### Recommendation
Bind all attacker-controlled inputs into the weight derivation. In `verify`, append each `R_i` and each public key `K_i` (and ideally a domain-separated length/count) to `digest` before calling `weight`, and mirror the same ordering in `SchnorrAggregator::complete` — note `aggregate`/`complete` must commit to the `Rs` and keys as they are known, so the aggregator should take the public key per `aggregate` call (or commit to all `Rs` in a second pass before deriving weights, matching the paper's `z_i = H(R_1..R_n, keys, msgs, i)`). Alternatively, derive `z_i` from a transcript that first commits to the entire `Rs` vector and `keys_and_challenges`, breaking the attacker's ability to compute `z_i` before fixing `R_i`.

### Proof of Concept
For `keys_and_challenges = [(K_0, c_0), …, (K_{n-1}, c_{n-1})]` and any `dst`:

1. Reconstruct the verifier's digest: `DigestTranscript::<C::H>::new(dst)`, `domain_separate(b"signatures")`, `append_message(b"challenge", c_i.to_repr())` for each `i` (`aggregate.rs:132-136`).
2. For each `i`, draw `r_i` ← random scalar and call `weight::<_, C::F>(&mut digest)` to obtain `z_i`.
3. Set `R_i = r_i·G − c_i·K_i` and `s = Σ z_i·r_i`.
4. Emit `SchnorrAggregate { Rs: [R_0, …, R_{n-1}], s }` (e.g., via `write`, then feed through `SchnorrAggregate::read`).

Verification then computes:

```
Σ z_i·(R_i + c_i·K_i) − s·G
= Σ z_i·(r_i·G − c_i·K_i + c_i·K_i) − (Σ z_i·r_i)·G
= Σ z_i·r_i·G − Σ z_i·r_i·G = 0
```

`multiexp_vartime(&pairs).is_identity()` returns true (`aggregate.rs:144-145`), so `verify` accepts a forged aggregate for arbitrary keys and challenges with no private key material — the linear check passes while the underlying per-signature constraints (knowledge of `r_i + c_i·k_i`) are wholly unsatisfied, directly paralleling the M-17 linear-ratio slippage check accepting deposits that violate the actual StableSwap invariant.
