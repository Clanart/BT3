## Title
Partial-commit line selection is computed against a whitespace-hidden diff but applied to a full (non-hidden) diff, silently including/excluding unreviewed lines - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user enables "Hide Whitespace Changes" while reviewing a diff and then selects individual lines for a partial commit, GitHub Desktop records the selection as absolute line indices into the *whitespace-hidden* diff structure. At commit time, `applyPatchToIndex` re-fetches the diff for that file **without** the whitespace-hiding flag and reuses those same absolute indices to decide which lines belong in the patch. Because `-w`/`--ignore-all-space` changes hunk boundaries, context grouping and `unifiedDiffStart` offsets, the index recorded under one diff layout no longer points at the same logical line under the other layout. The result is a patch built from indices that silently map onto different content than what the user actually reviewed and selected.

### Finding Description
The commit path is:
1. User opens the Changes view with "Hide whitespace changes" enabled, which fetches the diff via `getWorkingDirectoryDiff(repository, file, hideWhitespaceInDiff)` [1](#0-0)  and the user makes a line selection based on that rendered (whitespace-collapsed) hunk layout.
2. `_commitIncludedChanges` takes the currently selected files, with whatever `DiffSelection` (absolute line indices) is attached, and hands them to `createCommit` without re-validating the selection against a freshly, consistently-generated diff [2](#0-1) .
3. `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff for the file, but this call omits the `hideWhitespaceInDiff` argument entirely, defaulting it to `false`: [3](#0-2) 
4. `formatPatch` then decides which lines to keep purely by `file.selection.isSelected(absoluteIndex)`, matching the stored index against the hunk/line layout of *this new* (non-whitespace-hidden) diff, with no verification that the line at that index is the same line the user actually saw and selected: [4](#0-3) 

Because `-w` merges/removes whitespace-only diff lines and can shift hunk start offsets, the same absolute index can reference a completely different line (or an entirely different hunk) once whitespace-hidden mode is turned off for the commit-time diff. Desktop's own code acknowledges that stale selection state versus a changed diff is a known, unresolved gap — it only trims selection to lines that still exist, without validating that the *content* at a given index is unchanged: [5](#0-4) . That safeguard runs against consecutive loads of the diff with the *same* whitespace setting, not against the mismatch introduced by `applyPatchToIndex` silently dropping the whitespace flag.

### Impact Explanation
This is a **silent corruption of what the user commits (and subsequently pushes)** — the exact category called out in the report's valid-impact list. An attacker who can influence the content of a file in a repository the victim clones (e.g., a contributor submitting a change with interleaved whitespace-only and substantive edits) can craft a diff where:
- Under "hide whitespace" view, a benign-looking line is selected by the victim at some absolute index N.
- Under the real (whitespace-shown) diff used to build the patch, index N maps to an unrelated line — potentially content the victim never reviewed or intended to include (or excludes content the victim did intend to include).

The victim ends up committing (and can push) content they did not knowingly select, without any error or warning.

### Likelihood Explanation
Requires the victim to be using partial/line-level selection together with "Hide Whitespace Changes" — a supported, discoverable Desktop feature, not an unnatural workflow. No local/admin access, no leaked credentials, and no separate host compromise are needed; the trigger is purely the content of the file being diffed, i.e., something an untrusted contributor/repository can shape. The existing guard (`app-store.ts:3480-3492`) only prunes now-nonexistent selectable lines, it does not detect or prevent index reinterpretation across the whitespace-hidden vs. full diff boundary, so it does not stop this path.

### Recommendation
`applyPatchToIndex` (and any other call site building a patch from a `DiffSelection`) must retrieve the diff using the **same** `hideWhitespaceInDiff` setting (or, better, always `false`/canonical) that was used when the selection indices were originally computed and stored, and that setting should be tracked alongside the selection state rather than being an ambient/global preference. Alternatively, `DiffSelection` should be keyed by content-stable anchors (e.g., line text + surrounding context hash) rather than purely by absolute index, so that a mismatch between the diff used for review and the diff used for staging is detected and rejected rather than silently applied.

### Proof of Concept
1. Create a file with a run of whitespace-only edits interleaved with a substantive one-line change.
2. In Desktop, open the Changes view for that file and enable "Hide whitespace changes" (`hideWhitespaceInChangesDiff`), which fetches the diff with `-w` and yields fewer/merged hunks.
3. Select (for partial commit) what appears, under the whitespace-hidden view, to be only the substantive line at absolute index N.
4. Commit. `applyPatchToIndex` re-fetches the diff without `-w` (`app/src/lib/git/apply.ts:60`), producing a diff with different hunk boundaries; `formatPatch` applies `isSelected(N)` against this different layout (`app/src/lib/patch-formatter.ts:157`), including/excluding lines the user never actually reviewed against the true diff.
5. Inspect the resulting commit content versus what was shown on screen prior to commit — they diverge with no warning to the user.
