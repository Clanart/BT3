## Finding: local analog identified

The ToB report's core broken invariant is: **an operation designed for partial state (a subset of debt/collateral) is used as if it represented the whole position, permanently stranding the remainder.** The direct Hyperbridge analog is in the same-chain intent fill path, where escrow release is silently truncated to the number of *output* assets instead of the full set of escrowed *input* assets.

### Title
Same-chain `fillOrder` truncates escrow release to `outputsLen`, permanently locking excess escrowed input tokens on multi-input orders - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntrinsicIntents._fillSameChain` builds the list of escrowed tokens to release using an array sized to `order.output.assets.length` (`outputsLen`), and populates it by iterating output assets and pairing each with `order.inputs[i]` at the same index. `_fillCrossChain`, by contrast, releases the *entire* `order.inputs` array regardless of how many output assets exist. This inconsistency shows multi-input orders (more input tokens than output tokens) are a supported shape, but the same-chain path only ever transfers/decrements the first `outputsLen` entries of `order.inputs`, even on a full fill that finalizes and locks the order.

### Finding Description [1](#0-0) 
`_fillSameChain` allocates `escrowedInputs` and `outputFills` sized to `outputsLen`, then loops `i` from `0` to `outputsLen`, reading `order.inputs[i]` at each step: [2](#0-1) 
On a full fill, this `escrowedInputs` array (length `outputsLen`) becomes the `WithdrawalRequest.tokens` passed to `_withdraw`: [3](#0-2) 
`_withdraw` only decrements `_orders[commitment][token]` for the tokens present in `body.tokens`: [4](#0-3) 
and `_filled[commitment]` is already set to `msg.sender` at the very top of `_fillSameChain`, finalizing the order: [5](#0-4) 

Compare this with the cross-chain fill path, which dispatches a `RedeemEscrow` message carrying the *full* `order.inputs` array, not truncated by `outputsLen`: [6](#0-5) 

This asymmetry demonstrates that `order.inputs.length != order.output.assets.length` is a legitimate order shape the protocol is built to support (e.g., a basket of several escrowed input tokens swapped for one output token). Nothing in the reviewed code path enforces `order.inputs.length == order.output.assets.length` before same-chain fills, and `_cancelSameChain` correctly iterates over the *full* `order.inputs` array when refunding an unfilled/partially-filled order: [7](#0-6) 
— but once the order is fully filled via `_fillSameChain`, `_filled[commitment]` is non-zero, `cancelOrder` will revert with `Filled()`, and there is no other path in `IntentsBase`/`IntrinsicIntents` that can decrement or release the un-swept `_orders[commitment][token]` balances for input indices `>= outputsLen`. Those tokens are permanently stuck in the gateway contract, exactly mirroring the ToB pattern of "payback/withdrawal operations that always interact with [a partial slice], which might not contain enough [context] to execute correctly."

### Impact Explanation
This causes direct, unrecoverable loss of user funds under the Hyperbridge Impact Gate's "stealing or loss of funds" category: for any same-chain order where the user escrows more input token types than the number of requested output token types, a solver's full fill will only release/account for the first `outputsLen` input entries. The remaining escrowed input tokens are neither transferred to the solver nor returned to the user, and become permanently locked once `_filled[commitment]` is set (no cancellation, no sweep path targets order-specific escrow — only protocol dust is sweepable via `_sweepDust`, which is unrelated user escrow).

### Likelihood Explanation
Likelihood depends on whether `placeOrder` (in `IntentGatewayV2.sol`) permits `order.inputs.length > order.output.assets.length`. I could not fully confirm the presence or absence of a length-equality check in `placeOrder` before running out of tool budget — this is the primary open question for verification. However, the fact that `_fillCrossChain` explicitly handles the full, unconstrained `order.inputs` array (not indexed by `outputsLen`) is strong circumstantial evidence that multi-input, single/fewer-output baskets are an intended, unrestricted order shape at the data-structure level, making the same-chain code path the outlier and the likely source of the bug. This can be triggered by any ordinary user placing an order and any solver filling it — no privileged actor, relayer, or malicious peer is required.

### Recommendation
- **Short term:** In `_fillSameChain`, size and populate `escrowedInputs` from `order.inputs.length`, not `order.output.assets.length`, ensuring all escrowed input tokens are accounted for and released proportionally (or fully, on full fill) regardless of how many distinct output assets the order requests. Alternatively, if a strict 1:1 input/output correspondence is intended, enforce `order.inputs.length == order.output.assets.length` in `placeOrder` and revert otherwise.
- **Long term:** Add an invariant test asserting that after any terminal same-chain fill (`isFullyFilled == true`), `_orders[commitment][token] == 0` for every token in `order.inputs`, not just the first `outputsLen` entries. Add a fuzz/property test with `order.inputs.length != order.output.assets.length` to same-chain fill flows, matching the parity already covered for cross-chain in `ExtrinsicIntents.sol`.

### Proof of Concept
1. User places a same-chain order with `order.inputs = [TokenA: 100, TokenB: 100, TokenC: 100]` and `order.output.assets = [TokenX: 100]` (3 inputs, 1 output) — escrowing all three tokens into `_orders[commitment][...]`.
2. Solver calls `fillOrder` providing `outputs = [TokenX: 100]`.
3. In `_fillSameChain`, `outputsLen = 1`, so the loop only processes `i = 0`, computing `escrowedInputs[0] = TokenInfo({token: order.inputs[0] (TokenA), amount: 100})`. `isFullyFilled = true` (since the single output pair is fully covered).
4. `_withdraw` releases only `TokenA`'s 100 units to the solver and decrements `_orders[commitment][TokenA]` to 0. `_orders[commitment][TokenB]` and `_orders[commitment][TokenC]` remain at 100 each.
5. `_filled[commitment]` is already set to the solver, so the order is finalized. Any subsequent `cancelOrder` call reverts with `Filled()` (checked in the caller before dispatching to `_cancelSameChain`).
6. `TokenB` and `TokenC` (200 units total) remain locked in the `IntentGatewayV2` contract indefinitely — unrecoverable by the user, the solver, or governance's dust-sweep (which only sweeps protocol-owned surplus, not user escrow keyed by `commitment`).

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;
