Audit Report

## Title
Unauthenticated RPC-pubsub WebSocket connections have no handshake/idle read timeout, enabling remote resource exhaustion - (File: rpc/src/rpc_pubsub_service.rs)

## Summary
`listen()` accepts unauthenticated TCP connections on the JSON-RPC pubsub port and spawns a `handle_connection` task per connection without any cap, and `handle_connection` awaits the WebSocket handshake and subsequent frame reads with no timeout. An attacker can open many TCP connections that stall at handshake or go idle after handshake, accumulating unbounded tasks/sockets/memory on the validator's pubsub service.

## Finding Description
`listen()` unconditionally accepts every incoming connection and spawns `tokio::spawn(handle_connection(...))`, using only a `TokenCounter` for metrics, which merely reports a count via `datapoint_info!` and enforces no limit or eviction [1](#0-0) [2](#0-1) . Inside `handle_connection`, the WebSocket handshake is awaited with no timeout wrapper: `server.receive_request().await?` followed by `server.send_response(&accept).await?` [3](#0-2) . After the handshake, the main loop's `select!` only races `receive_future` (client data), `broadcast_receiver.recv()`, and `tripwire` (shutdown) — none of which fire on pure client inactivity, so an idle connection blocks forever with no idle-read timeout branch [4](#0-3) . `PubSubConfig` contains fields for subscription counts and queue capacities but no max-concurrent-connection or per-connection idle-timeout field [5](#0-4) . This contrasts with `streamer/src/nonblocking/quic.rs`, which enforces connection-attempt timeouts, per-IP rate limiting, and a cap on concurrent connections [6](#0-5) , and with `net-utils/src/ip_echo_server.rs`, which enforces `MAX_CONCURRENT_CONNECTIONS`, a per-IP connection limit, and an I/O deadline (`IO_TIMEOUT`) on reads/writes [7](#0-6) [8](#0-7) .

## Impact Explanation
This is a remote resource-exhaustion vector reachable by any unprivileged, unauthenticated client with no protocol knowledge required beyond opening a raw TCP socket. Because there is no cap on concurrent connections, no per-IP limit, and no handshake/idle timeout, a client (or small set of clients) can accumulate unbounded server-side tokio tasks, sockets, and `DashMap`/broadcast-receiver state on the validator's RPC pubsub service, degrading or crashing it. This matches the allowed "single-client low-rate RPC crash/degradation" / non-RPC remote exhaustion impact category for the RPC/pubsub scope.

## Likelihood Explanation
Likelihood is high wherever the pubsub WebSocket endpoint is exposed: exploitation requires only opening TCP sockets and either stalling the handshake or going silent after it completes — no authentication, valid subscription, or protocol payload is needed, and it is trivially scriptable at scale from one or a few source IPs.

## Recommendation
Wrap the WebSocket handshake (`server.receive_request()`/`send_response()`) in `tokio::time::timeout`; add an idle-read timeout branch to the `select!` loop in `handle_connection` that closes connections receiving no client data within a bounded window; and enforce a maximum number of concurrent pubsub connections globally and per-IP, mirroring the protections in `streamer/src/nonblocking/quic.rs` and `net-utils/src/ip_echo_server.rs`.

## Proof of Concept
1. Start a validator/RPC node with the pubsub service enabled (`PubSubService::new`).
2. From an unprivileged client, open N raw TCP connections to the pubsub port without completing the WebSocket handshake, or complete it once and send nothing further.
3. Because the handshake await (line 356) and the main-loop `receive_future` await (lines 384–398) have no timeout, and `listen()` (lines 448–467) spawns an unbounded number of tasks, each connection persists indefinitely, consuming a tokio task, socket, and buffers.
4. Repeating at scale accumulates unbounded resource usage on the pubsub runtime, degrading or exhausting the validator's RPC pubsub service.
