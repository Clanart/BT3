### Title
Missing forfeiture logic in `mWOMSVBaseRewarder._calExpireForfeit` permanently prevents reward slashing/redistribution on early mWomSV exit - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` hardcodes `rewardableAmount = _amount`, making `forfeitAmount` always `0`, so `_sendReward` never routes any portion of a claiming user's reward into `_queueNewRewardsWithoutTransfer`. This is a departure from the analogous `vlMGPBaseRewarder._calExpireForfeit`, which computes the forfeitable share via `vlMGP.getRewardablePercentWAD(_account)` — a function that also exists on `mWomSV` (`getRewardablePercentWAD`) but is never called by the rewarder. As a result, a user who locks mWOM, accrues rewards, then unlocks, keeps 100% of accrued rewards instead of losing the penalized/forfeited share that should be redistributed (via `rewardPerTokenStored`) to remaining long-term lockers.

### Finding Description
`mWomSV.sol` implements `getRewardablePercentWAD(address _user)` [1](#0-0)  which computes a weighted "rewardable" percentage based on how much of a user's mWomSV balance is fully locked versus in cool-down or already past `endTime` (i.e., exited). This mirrors `VLMGP.getRewardablePercentWAD`, used by `vlMGPBaseRewarder._calExpireForfeit` to slash a portion of a claimant's pending reward when they are not fully locked: [2](#0-1) .

In contrast, `mWOMSVBaseRewarder._calExpireForfeit` never calls `mWOMSV.getRewardablePercentWAD(_account)`. It sets `rewardableAmount = _amount` unconditionally, so `forfeitAmount = _amount - rewardableAmount` is always `0`: [3](#0-2) .

This function is invoked from `_sendReward`, which is called on every `getReward`/`getRewards`/`multiclaim` path: [4](#0-3) . Because `forfeitAmount` is always `0`, the `if(forfeitAmount > 0) _queueNewRewardsWithoutTransfer(...)` branch is dead code — `_queueNewRewardsWithoutTransfer` (which would increase `rewardPerTokenStored` for remaining stakers, per `rewards/mWOMSVBaseRewarder.sol:330-346`) is never reached from this call site.

Attack path: an attacker claims mWOM from `ArbitrumMWomAirdrop.claim(..., isLock=true)`, which calls `locker.lockFor(claimable, msg.sender)` [5](#0-4) . This deposits into `mWomSV`, reflected as a MasterMagpie stake via `_lock` → `IMasterMagpie(masterMagpie).depositMWomSVFor` [6](#0-5) . The attacker then calls `startUnlock` and `unlock` (which trigger `multiclaimFor`) [7](#0-6) , and finally claims via `getReward`/`multiclaim`. At every claim point, regardless of the attacker's lock/cooldown/unlocked state, `_calExpireForfeit` returns `0`, so the attacker always receives 100% of `userRewards`, when the intended design (mirroring `vlMGPBaseRewarder`) would slash a proportional share for time spent unlocked/in-cooldown and recycle it to long-term lockers.

No existing modifier (`onlyMasterMagpie`, `updateRewards`, `nonReentrant`) prevents this — they gate access/reentrancy, not the forfeiture math, which is simply absent.

### Impact Explanation
This is a **theft/misappropriation of unclaimed yield** intended for long-term lockers: the recycling mechanism (`_queueNewRewardsWithoutTransfer` increasing `rewardPerTokenStored` for remaining stakers) never fires for mWomSV, so any lock-then-unlock cycle results in the exiting user retaining reward share that the protocol's own design (as evidenced by the parallel `vlMGPBaseRewarder` implementation and the existence of `mWomSV.getRewardablePercentWAD`) intended to forfeit and redistribute. This matches the Immunefi "theft or permanent freezing of unclaimed yield" impact class — the forfeitable share is permanently lost to the pool of long-term lockers, captured instead by short-cycle exiters, on every claim.

### Likelihood Explanation
High feasibility and full repeatability: no privileged role is required, the attacker only needs mWOM (obtainable via `ArbitrumMWomAirdrop.claim` or open-market purchase) and can freely call `lock`/`lockFor`, `startUnlock`, `unlock`, and `multiclaim`/`getRewards`, all public/external functions with no additional cost beyond the `coolDownInSecs` wait and gas. The bug is deterministic and triggers on every single claim by every user (not just attackers), meaning the "recycle to long-term lockers" mechanism for mWomSV effectively never functions at all.

### Recommendation
In `rewards/mWOMSVBaseRewarder.sol`, fix `_calExpireForfeit` to mirror `vlMGPBaseRewarder`'s implementation by computing the rewardable percentage from the locker:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    if (rewardableAmount > _amount) revert InvalidRewardableAmount();
    uint256 forfeitAmount = _amount - rewardableAmount;
    if (forfeitAmount < (_amount / 1000)) {
        forfeitAmount = 0;
        rewardableAmount = _amount;
    }
    return forfeitAmount;
}
```
This requires `getRewardablePercentWAD` be added to the `ILocker` interface (or the concrete `mWOMSV` type used) so `mWOMSVBaseRewarder` can call it.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `mWOMSVBaseRewarder`, `MasterMagpie` mock pool, and a reward token.
2. Fund two users: `attacker` and `longTermLocker`, each lock equal amounts of mWOM via `mWomSV.lock`.
3. Manager calls `queueNewRewards` to inject a fixed reward amount; verify `rewardPerTokenStored` updates for both users' pro-rata share.
4. `attacker` calls `startUnlock(fullAmount)`, waits `coolDownInSecs`, calls `unlock(slotIndex)`, then calls `getReward`/`multiclaim` to withdraw their full accrued reward.
5. Assert: `attacker` receives exactly the full pro-rata `userRewards` (unslashed) despite having exited the lock — i.e., `_calExpireForfeit` returns `0` and `ForfeitRewardAdded` event is never emitted.
6. Cross-check against `vlMGPBaseRewarder` with an equivalent lock/unlock/claim sequence, where `ForfeitRewardAdded` IS emitted with a nonzero amount and `rewardPerTokenStored` increases for remaining vlMGP holders — demonstrating the mWomSV path is missing the same conservation mechanism.
7. Invariant assertion: track cumulative `_queueNewRewardsWithoutTransfer` calls/amounts across N random lock/unlock/claim cycles in `mWOMSVBaseRewarder`; assert the sum is always `0`, proving redistribution to long-term lockers never occurs regardless of exit pattern.

        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

            if (userUnlocking[i].amountInCoolDown > 0) {

                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;

        }

        return percent;
