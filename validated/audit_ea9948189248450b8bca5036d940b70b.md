Based on my research, I found a genuine local analog: the Hyperbridge EVM deployment script hardcodes the challenge-period configuration to zero regardless of network target, which — combined with how the challenge-period value is consumed by the message-processing delay check — reproduces exactly the class of bug described in the external report (a deployment/migration script producing a configuration that silently disables a security dependency).

### Title
Mainnet deployment script hardcodes `challengePeriod: 0`, disabling the state-commitment challenge window - ([File: evm/script/DeployIsmp.s.sol])

### Summary
The `HostParams` struct exposes `challengePeriod` as "Minimum challenge period for state commitments in seconds" [1](#0-0) , and this value is consumed by the delay-elapsed check that gates when a freshly-verified state commitment becomes usable for request/response/timeout processing. In the Substrate/ISMP core, the equivalent gate treats a zero challenge period as "delay already passed," so commitments are immediately actionable: [2](#0-1) . `evm/script/DeployIsmp.s.sol`, the canonical deployment script used to wire up `EvmHost`, `HostManager`, consensus clients, and downstream apps, unconditionally sets `challengePeriod: 0` in the `HostParams` passed to `host.initialize(params)` — with no `isMainnet` branch to raise it for production: [3](#0-2) . This mirrors the external report's core class exactly: a Truffle/Foundry-style migration that fails to guarantee a "production-ready configuration programmatically," instead silently deploying with a value that defeats a protocol invariant.

### Finding Description
The challenge period exists to give the fraud-proof/monitoring machinery a window to detect and freeze a consensus client before any state commitment it produced can be relied upon by the request/response/timeout handling path. `verify_delay_passed` explicitly special-cases `delay_period.as_secs() == 0` to always return `true` [4](#0-3) , and `validate_state_machine` rejects proofs only when this delay has *not* elapsed [5](#0-4) . The EVM host's `HostParams.challengePeriod` is the same knob for the EVM side, feeding the analogous delay check consumed by `HandlerV2.sol`. Because `DeployIsmp.s.sol` sets this to `0` for every network (there is no `if (isMainnet) { challengePeriod = X }` branch, unlike other fields such as `feeToken`/`hyperbridge` which are correctly branched on `isMainnet`), any host deployed via this script — including a mainnet deployment — starts with the challenge window fully disabled. This is precisely the "deployments and post-deployment configuration adhere to the white paper" failure mode described in the source report: a dependency (the challenge-period safety mechanism) silently ends up unconfigured/misconfigured due to migration-script defaults rather than any on-chain access-control bug.

### Impact Explanation
With `challengePeriod == 0`, a state commitment becomes trusted and actionable the instant it's written by any accepted consensus client (SP1Beefy or EcdsaBeefy via `ConsensusRouter`), with zero window for off-chain observers to detect and freeze a faulty or compromised consensus update before requests/responses referencing that height are processed. This directly undermines the protocol invariant "Consensus proofs, state proofs, challenge periods, and state commitments must never let false remote state become trusted" — the challenge period is the only on-chain mechanism protecting against a delayed-detection fraud proof, and it is fully disabled by default deployment configuration. Any funds-moving flow gated on state-machine height validity (intent settlement fills, withdrawal proofs, response delivery) inherits this weakened trust assumption immediately post-deployment.

### Likelihood Explanation
This requires no attacker privilege at all beyond what any relayer/user already has to submit ISMP messages — it's a deployment-configuration defect, not an exploit requiring a malicious peer or admin. Any chain brought up with the unmodified `DeployIsmp.s.sol` script inherits `challengePeriod = 0` unless an operator manually overrides `HostParams` post-init via `updateHostParams`/`HostManager` governance. Given the script is the reference deployment path (also mirrored by the TRON migration flow using `challengePeriod: 0`, and the same pattern noted in `DeployHostUpdates.s.sol`), the likelihood of a real production deployment inheriting this misconfiguration without a dedicated review step is non-trivial — exactly the scenario the original report warns about.

### Recommendation
- **Short term:** Branch `challengePeriod` on `isMainnet` in `DeployIsmp.s.sol` (and any other deployment scripts / TRON migrations) with a nonzero production value, and add a post-deployment assertion/script check that reverts or warns if `EvmHost.hostParams().challengePeriod == 0` when `isMainnet == true`.
- **Long term:** Add automated deployment-validation tests (as the original report recommends) that assert critical `HostParams` invariants — nonzero challenge period, correct `hyperbridge` state machine id, correct `consensusClient` wiring — before a deployment is considered complete, so migrations fail loudly rather than producing a silently weakened configuration.

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}

/// This function does the preliminary checks for a request or response message
/// - It ensures the consensus client is not frozen
/// - Checks for frozen state machine is deprecated and malicious state machine commitment will be
///   deleted instead
/// - Checks that the delay period configured for the state machine has elapsed.
pub fn validate_state_machine<H>(
	host: &H,
	proof_height: StateMachineHeight,
) -> Result<Box<dyn StateMachineClient>, Error>
where
	H: IsmpHost,
{
	// Ensure consensus client is not frozen
	let consensus_client_id = host.consensus_client_id(proof_height.id.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized {
			consensus_state_id: proof_height.id.consensus_state_id,
		},
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	// Ensure client is not frozen
	host.is_consensus_client_frozen(proof_height.id.consensus_state_id)?;

	// Ensure delay period has elapsed
	if !verify_delay_passed(host, &proof_height)? {
		return Err(Error::ChallengePeriodNotElapsed {
			state_machine_id: proof_height.id,
			current_time: host.timestamp(),
			update_time: host.state_machine_update_time(proof_height)?,
		});
	}
