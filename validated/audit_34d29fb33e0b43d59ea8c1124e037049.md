Based on the investigation, I found a concrete analog: `ClementineAggregator::send_move_to_vault_tx` validates a submitted transaction's *outputs* against the generic bridge script (nofn + security council), but never checks that the transaction's *input* actually spends the `deposit_outpoint` supplied in the same request.

### Title
`send_move_to_vault_tx` accepts a `raw_tx`/`deposit_outpoint` pair without binding the input to the claimed outpoint - ([File: core/src/rpc/aggregator.rs])

### Summary
The MIMO report's bug class is a registry/factory that records or trusts an ownership/authorization mapping without actually enforcing that the mapping matches the real on-chain action performed. The Clementine analog is `send_move_to_vault_tx`, which records a `MoveToVault` transaction against a caller-supplied `deposit_outpoint` in the tx-sender database, but validates only the transaction's *outputs* (amount and taproot script), never verifying that `movetx.input[0].previous_output == deposit_outpoint`.

### Finding Description
In `send_move_to_vault_tx` (`core/src/rpc/aggregator.rs:1973-2102`), the handler:
1. Deserializes `raw_tx` and reads `deposit_outpoint` from the request separately.
2. Checks `movetx.input.len() == 1` and `movetx.output.len() == 2`.
3. Checks `movetx.output[0].value == bridge_amount` and `movetx.output[1].value == 0`.
4. Checks `movetx.output[0].script_pubkey == bridge_script_pubkey` (the taproot address built from the nofn aggregated key and the security council multisig — this address is **identical for every deposit**, since it does not encode the specific `deposit_outpoint` or deposit-specific data).
5. Then it calls `self.tx_sender.insert_try_to_send(..., TxMetadata { deposit_outpoint: Some(deposit_outpoint), ... }, &movetx, ...)`, tying the DB record's `deposit_outpoint` field to whatever value the caller passed — without ever checking `movetx.input[0].previous_output` against that `deposit_outpoint`.

Because the move-to-vault taproot output address is the same for all deposits (it only depends on the aggregated nofn key and the security council key, not on deposit-specific data), any validly-signed move-to-vault transaction (e.g., for deposit A) passes all the output checks, and can be submitted together with an unrelated `deposit_outpoint` (e.g., deposit B's outpoint) in the same request. The endpoint will happily broadcast/track it and record it in the DB as fulfilling deposit B's move-to-vault tx, even though the transaction's actual input spends deposit A's outpoint.

Equality broken: "a deposit presigned versus a deposit minted once" — the DB/tx-sender's belief `deposit_outpoint → movetx` no longer matches the actual on-chain input being spent by `movetx`.

### Impact Explanation
This breaks the binding between the deposit UTXO that funds a peg-in and the bookkeeping record that the system (and downstream consumers such as Citrea light client tooling / operators) uses to associate a move-to-vault transaction with a specific deposit outpoint. If any downstream logic trusts `TxMetadata.deposit_outpoint` (as recorded via this call) as proof that the given deposit outpoint was moved (e.g., for reimbursement bookkeeping, replacement-deposit tracking, double-deposit prevention), an operator or caller could cause the tracked outpoint-to-movetx association to be inconsistent with the actual chain state, potentially enabling duplicate-deposit or misattribution issues in the reimbursement/tracking pipeline.

However, I could not fully verify from the available context whether this record's `deposit_outpoint` field is later relied upon as an authoritative source of truth for reimbursement or fund-crediting decisions elsewhere in the codebase (e.g., by operators computing payouts) — the code excerpts show this is used for `insert_try_to_send`/DB bookkeeping, but I did not find the downstream consumer of `TxMetadata.deposit_outpoint` for this specific tx type within the accessible index. Additionally, this RPC is not literally "unauthenticated" — it is gated by the mTLS interceptor (`core/src/rpc/interceptors.rs`), which allows only the aggregator's own certificate or the entity's self certificate (not "Internal"-prefixed, so both self and aggregator can call it). I could not verify from available files exactly which interceptor configuration is applied to the Aggregator's own gRPC server (`create_aggregator_grpc_server`/`create_aggregator_unix_server` in `core/src/servers.rs`) to determine whether this endpoint is reachable by any party beyond the trusted backend service that normally calls it. Given the rules require an unauthenticated or unprivileged-attacker path, and I cannot confirm this endpoint is reachable by an unprivileged caller (it may only be reachable via the aggregator's own trusted client, e.g., "clementine-backend"), I am not confident this crosses the required authorization boundary.

### Likelihood Explanation
Low-to-uncertain: exploitability depends on (a) whether an attacker can reach `SendMoveToVaultTx` without being the trusted aggregator-client caller, and (b) whether the mismatched `deposit_outpoint` metadata is later used in a security-relevant decision (e.g., crediting a deposit, preventing double-spend of the same deposit outpoint) rather than being purely informational bookkeeping. I was unable to confirm either premise with certainty from the code available in the index.

### Recommendation
Add an explicit check in `send_move_to_vault_tx` that `movetx.input[0].previous_output == deposit_outpoint` before proceeding, so the recorded/broadcast transaction is provably bound to the claimed deposit outpoint, mirroring the report's fix theme of "disallow calling deploy/deployFor without proper checks binding caller to the tracked entity."

### Proof of Concept
1. Caller with permission to reach `SendMoveToVaultTx` (self or aggregator cert per `core/src/rpc/interceptors.rs:22-77`) submits a validly-signed move-to-vault raw tx for deposit A's outpoint.
2. In the same call, the caller supplies `deposit_outpoint = B` (a different, unrelated deposit's outpoint) instead of A.
3. `send_move_to_vault_tx` (`core/src/rpc/aggregator.rs:1998-2100`) checks only `movetx.output[...]` against the generic bridge script/anchor amount — both of which pass regardless of which deposit's input is actually being spent — and never checks `movetx.input[0].previous_output` against the supplied `deposit_outpoint`.
4. The transaction is inserted into `tx_sender` with `TxMetadata.deposit_outpoint = B`, creating a persisted record that misattributes A's move-to-vault transaction to deposit B. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

impl Interceptor for Interceptors {
    #[allow(clippy::result_large_err)]
    fn call(&mut self, req: Request<()>) -> Result<Request<()>, Status> {
        match self {
            Interceptors::OnlyAggregatorAndSelf {
                our_cert,
                aggregator_cert,
            } => only_aggregator_and_self(req, our_cert, aggregator_cert),
            Interceptors::Noop => Ok(req),
        }
    }
}

#[allow(clippy::result_large_err)]
fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
}
