### Title
Unrestricted `receive()` in WombatStaking permanently locks any native currency mistakenly sent by users - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking.sol` exposes an unguarded `receive() external payable {}` that accepts native currency from any address with no sender restriction and no accounting of who sent it or how much. [1](#0-0)  This mirrors the reported bug class where a handler's unrestricted `receive()` allows arbitrary senders to deposit native funds that the contract has no mechanism to track or return.

### Finding Description
The `receive()` function is intended only to allow the contract to accept native currency forwarded internally during bribe processing in `vote()`, where `Address.sendValue(payable(wbnb), rewardAmount)` is used to wrap received native bribe rewards into `wbnb`. [2](#0-1)  However, because `receive()` has no `msg.sender` check, any ordinary wallet or contract can send native currency directly to `WombatStaking` outside of this flow. Once received, that balance is not tied to the sender in any mapping or accounting structure — the contract only tracks ERC20 balances (`wom`, LP tokens, receipt tokens) via explicit before/after balance diffs in functions like `_toMasterWomAndSendReward` and `_sendRewards`. There is no function in the contract that allows a user to withdraw or reclaim native currency that was sent to the contract via `receive()`; the only native currency movement out of the contract is the internal `sendValue` call inside `vote()`, which is driven by `voter.vote()` return values, not by `address(this).balance`. As a result, native currency sent directly to the contract by an ordinary wallet is permanently stuck and unrecoverable, indistinguishable from bribe funds, and never returned to its original sender.

### Impact Explanation
Any native currency sent to `WombatStaking` outside of the legitimate bribe-forwarding path is permanently frozen with no recovery mechanism for the sender, resulting in a direct and irreversible loss of user funds — matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Triggering this requires nothing more than an ordinary wallet sending a native currency transfer directly to the `WombatStaking` contract address (e.g., through a wallet UI mis-click, a bot, or a wrapped-native withdrawal returning funds unexpectedly), the same fallible pattern flagged in the referenced report for `NativeHandler.sol`.

### Recommendation
Restrict `receive()` in `wombat/WombatStaking.sol` to only accept native currency from the specific approved contracts that are expected to send it (e.g., `wbnb`/wrapped native token contract, or the bribe/voter contract), using a `require(msg.sender == wbnb || msg.sender == address(voter), ...)` check, consistent with the referenced fix that added a sender check to the handler's `receive()`.

### Proof of Concept
```solidity
// Any EOA or contract, not related to bribes/voter/wbnb, can do:
(bool ok, ) = address(wombatStaking).call{value: 1 ether}("");
// ok == true, funds accepted into WombatStaking's balance
// No function exists to withdraw this balance back to the sender or track it
// The value is never returned and is not part of any user-claimable accounting
