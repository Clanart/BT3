Audit Report

## Title
Unbounded growth of `DuplicateShredHandler::consumed` HashMap via crafted `num_chunks` values decoupled from buffer-pruning trigger - (File: `gossip/src/duplicate_shred_handler.rs`)

## Summary
In `handle_shred_data`, `should_consume_slot` unconditionally inserts an entry into `self.consumed: HashMap<Slot, bool>` for any never-before-seen valid-range slot, *before* the `num_chunks`/`chunk_index` validation is performed. Because `Sanitize::sanitize` for `DuplicateShred` only checks `chunk_index < num_chunks` and never enforces `num_chunks <= MAX_NUM_CHUNKS (3)`, an attacker can submit a gossip `DuplicateShred` CRDS value (e.g. `num_chunks = 4`, `chunk_index = 0`) that passes sanitization, grows `consumed` by one entry per distinct slot, but is rejected before `self.buffer` is ever touched — decoupling `consumed`'s growth from the only pruning trigger, which is keyed on `buffer.len()`.

## Finding Description
`handle_shred_data` calls `should_consume_slot(chunk.slot)`, which internally calls the free function `should_consume_slot(slot, blockstore, consumed)` that does `consumed.entry(slot).or_insert_with(...)` — inserting an entry for any slot in the valid window regardless of the chunk's later validity. [1](#0-0) [2](#0-1) [3](#0-2) 

Only after this insertion does the code validate `num_chunks`/`chunk_index` against `MAX_NUM_CHUNKS = 3`; if this fails, the function returns `Err(InvalidChunkIndex)` before reaching the `self.buffer.entry(...)` line, so `buffer` never grows. [4](#0-3) 

The CRDS-layer `Sanitize` impl for `DuplicateShred` only rejects `chunk_index >= num_chunks`; it does not bound `num_chunks` by `MAX_NUM_CHUNKS`, so a crafted value with `num_chunks = 4, chunk_index = 0` passes sanitization. [5](#0-4) 

The only prune path for `consumed` is inside `maybe_prune_buffer`, gated exclusively on `self.buffer.len() >= BUFFER_CAPACITY * 2`. [6](#0-5) 

Since crafted-invalid chunks never populate `buffer`, this prune path never triggers, and `consumed` keeps growing as new distinct slots enter the valid window `last_root < slot < last_root + cached_slots_in_epoch`. [2](#0-1) 

Delivery path is confirmed: `DuplicateShredListener::recv_loop` continuously drains newly-inserted CRDS `DuplicateShred` values via a `Cursor` and calls `handler.handle(x)` for each, and `handle()` unconditionally calls `handle_shred_data` (aside from the Alpenglow-migration no-op branch). [7](#0-6) [8](#0-7) 

Existing guards are insufficient: the CRDS-table-level per-pubkey label limit (`MAX_DUPLICATE_SHREDS = 512`, keyed by `(index, pubkey)`) only bounds how many *concurrent* entries a pubkey can hold in the table, but each overwrite of an index still constitutes a new CRDS insertion with a new ordinal, which the cursor-based listener will re-deliver to the handler, so a single attacker keypair can cycle through arbitrarily many distinct crafted values over time. [9](#0-8) 

## Impact Explanation
This is unbounded, attacker-controlled memory growth in the gossip-processing path (`DuplicateShredListener`/`DuplicateShredHandler`), reachable from any unprivileged gossip peer via crafted `DuplicateShred` push/pull CRDS values. The exact corrupted resource bound is the `consumed: HashMap<Slot, bool>` field of `DuplicateShredHandler`, whose size is structurally decoupled from `buffer`, the only pruning trigger. Sustained abuse over the epoch-sliding valid window can grow `consumed` indefinitely, matching the in-scope "non-RPC remote exhaustion" impact category for gossip.

## Likelihood Explanation
The attack requires only sending gossip push/pull messages from a single unprivileged, unstaked peer, using a valid signature over otherwise-attacker-chosen fields (`slot`, `num_chunks=4`, `chunk_index=0`, small `chunk` payload). No privileged control, leaked keys, or malicious-validator assumptions are needed — this is a standard external gossip participant. The main throttle is general gossip push/pull rate limiting and CRDS per-pubkey label capacity (512 concurrent slots), but since each overwrite still produces a new deliverable cursor entry, growth is not capped by table size, only by message rate.

## Recommendation
Move the `consumed.entry(slot).or_insert_with(...)` bookkeeping to occur only after chunk validation succeeds (or after enforcing `num_chunks <= MAX_NUM_CHUNKS` earlier, e.g. in `Sanitize::sanitize` for `DuplicateShred`), so invalid-`num_chunks` proofs are rejected before any `consumed` insertion. Alternatively, track and cap `consumed`'s own size independently rather than relying solely on `buffer.len()` as the prune trigger.

## Proof of Concept
1. Craft a `DuplicateShred` CRDS value with `num_chunks = 4`, `chunk_index = 0`, and a small `chunk` payload, for many distinct slots `s_i` satisfying `last_root < s_i < last_root + cached_slots_in_epoch`, signed by a single attacker keypair.
2. Push these into gossip (via push or pull-response) so they land in the local CRDS table and get delivered through `DuplicateShredListener::recv_loop` to `DuplicateShredHandler::handle`.
3. In `handle_shred_data`, each call reaches `should_consume_slot` (inserting into `consumed`) then fails the `usize::from(num_chunks) > MAX_NUM_CHUNKS` check at line 115, returning `Err(InvalidChunkIndex)` before the `self.buffer.entry(...)` line at 121 executes.
4. Observe `consumed.len()` growing by one per distinct `s_i` while `buffer.len()` remains 0, confirming `maybe_prune_buffer`'s `buffer.len() >= BUFFER_CAPACITY*2` trigger never fires while `consumed` keeps growing — reproducible as a Rust unit test instantiating `DuplicateShredHandler` directly and calling `.handle()` in a loop with crafted `DuplicateShred` values, then asserting on internal map sizes (requires exposing/pub(crate) access to `consumed`/`buffer` for the test, as done in the existing `#[cfg(test)]` module).
