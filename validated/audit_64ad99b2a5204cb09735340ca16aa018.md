### Title
Deprecated `.transfer()` in WSEI's `withdraw()` Can Cause Reverted Unwraps and Denial of Funds Access - (File: contracts/src/WSEI.sol)

### Summary
The `WSEI` contract's `withdraw()` function unwraps wrapped native SEI by sending the underlying value to `msg.sender` using `payable(msg.sender).transfer(wad)`, which forwards a fixed 2300-gas stipend, mirroring the reported WSHIDO issue.

### Finding Description
`withdraw()` in `contracts/src/WSEI.sol` decrements the caller's `balanceOf` and then unwraps using the deprecated low-level primitive `.transfer()`: [1](#0-0) 
`.transfer()` (and `.send()`) hard-code a 2300 gas stipend to the recipient's fallback/receive path. Any `msg.sender` that is a smart contract (e.g., a multisig, an ERC-4337 smart account, a DeFi vault, or a proxy) whose `receive()`/`fallback()` requires more than 2300 gas to execute (e.g., it emits an event, writes storage, or performs any nontrivial logic) will have the transfer revert, causing the entire `withdraw()` call to revert.

This is the identical bug pattern as the WSHIDO/WETH-style contract described in the external report: WSEI is Sei's canonical wrapped-native-token contract, embedded into the chain binary at `x/evm/artifacts/wsei/WSEI.bin`/`WSEI.abi` via `x/evm/artifacts/wsei/artifacts.go`, and deployable on-chain through the `evm deploy-wsei` CLI command (`CmdDeployWSEI()`, wired in `x/evm/client/cli/tx.go`) or by any user deploying the same bytecode. Once deployed and adopted (as the officially provided/embedded wrapped-token implementation, it is expected to be widely used by DEXs, routers, and other DeFi contracts on Sei, similar to how `UniswapV2Router02.sol` interacts with WETH-style contracts elsewhere in the same repo), a contract holding a WSEI balance (e.g., a router or vault performing an intermediate wrap/unwrap as part of a swap) cannot reliably retrieve its underlying native SEI. [2](#0-1) 

### Impact Explanation
An unprivileged EVM contract deployer or any contract integrating with WSEI (e.g., a router/vault in a swap path) can have its native SEI permanently stuck inside the WSEI contract if its own receive/fallback logic exceeds the 2300 gas stipend forwarded by `.transfer()`. Because `balanceOf[msg.sender]` is already decremented before the `.transfer()` call reverts the whole transaction (state changes roll back), the practical effect is a denial-of-service on unwrapping rather than fund loss on a single call, but for contracts that can never reduce their receive-path gas cost (e.g., a fixed proxy or an account-abstraction wallet), the locked native SEI held by WSEI becomes effectively unrecoverable for that caller — a permanent freezing of funds for the affected contract.

### Likelihood Explanation
Likely to occur once WSEI is deployed and used as the canonical wrapped-SEI token, since many DeFi contracts (multisigs, smart-contract wallets, vaults, routers) implement nontrivial `receive()`/`fallback()` logic that exceeds 2300 gas. Any transaction sender that is such a contract and calls `withdraw()` will trigger a revert deterministically, requiring no adversarial conditions.

### Recommendation
Replace `payable(msg.sender).transfer(wad)` in `withdraw()` with a low-level `.call{value: wad}("")` and check the boolean success return, reverting explicitly on failure while forwarding all available gas — the same fix already applied in the codebase's own `TransferHelper.safeTransferETH` helper: [3](#0-2) 

### Proof of Concept
1. Deploy `WSEI.sol` (or use the chain-embedded bytecode from `x/evm/artifacts/wsei/WSEI.bin`).
2. Deploy an attacker/receiver contract implementing a `receive()` function that consumes more than 2300 gas (e.g., writes to a storage slot).
3. From that contract, call `WSEI.deposit{value: X}()`, then call `WSEI.withdraw(X)`.
4. Observe that `withdraw()` reverts due to out-of-gas in the forwarded 2300-gas stipend inside `.transfer()`, even though the contract has sufficient `balanceOf` and the WSEI contract holds sufficient native balance — the caller cannot unwrap its SEI. [1](#0-0)
