## Finding

### Title
`depositFor` in WombatPoolHelperV2 hardcodes minimumLiquidity slippage protection to zero, enabling MEV extraction from depositors - (File: wombat/WombatPoolHelperV2.sol)

### Summary
`WombatPoolHelperV2.depositFor` allows any unprivileged wallet to deposit stable tokens into a Wombat pool on behalf of a recipient, but it hardcodes the pool's `minimumLiquidity` slippage-protection parameter to `0` instead of exposing it as a caller-controlled argument, unlike every other deposit entry point in the same contract.

### Finding Description
`WombatPoolHelperV2` exposes several deposit paths into the underlying Wombat pool via `WombatStaking.deposit`, which ultimately calls `IWombatPool.deposit(token, amount, minimumLiquidity, to, deadline, shouldStake)`. The Wombat pool enforces a slippage check against `minimumLiquidity` when minting LP shares from a deposit, similar to the Uniswap V3 `amount0Min`/`amount1Min` checks referenced in the external report.

The standard `deposit(uint256 _amount, uint256 _minimumLiquidity)` and `depositNative(uint256 _minimumLiquidity)` functions correctly forward a caller-supplied `_minimumLiquidity` value: [1](#0-0) [2](#0-1) 

However, `depositFor` hardcodes this value to `0`, removing any slippage protection for the deposit: [3](#0-2) 

This value flows straight through `_deposit` into `WombatStaking.deposit`, and then into the Wombat pool's `deposit` call with `_minimumLiquidity` unconditionally `0`: [4](#0-3) 

Because `depositFor` is `external` with no access control, any wallet can call it directly to deposit `depositToken` and mint LP/receipt shares for any `_for` address, with the pool-side slippage check effectively disabled (`amount >= 0` always passes).

### Impact Explanation
Wombat pools price LP-share minting based on the pool's current cash/liability ratio, which can be manipulated by sandwiching a large swap immediately before the victim's `depositFor` call and reversing it afterward. With `minimumLiquidity` locked to `0`, the depositor has no way to bound the acceptable LP output, so an MEV actor can extract value by minting the depositor (and their `_for` recipient) a smaller quantity of LP/receipt tokens than the pool's true price would imply — a direct value transfer (theft) from the depositing wallet to the frontrunning attacker, mirroring the exact vulnerability confirmed by the Particle team in the referenced report.

### Likelihood Explanation
Any external, unprivileged wallet can call `depositFor` at any time with no restrictions; MEV searchers on the deployment chain routinely watch for exactly this style of value-sensitive transaction to sandwich. Given the function is public and slippage protection is unconditionally disabled, exploitation requires no special privileges and is straightforward to automate.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor` (mirroring `deposit`/`depositNative`) and forward the caller-supplied value through `_deposit` into `WombatStaking.deposit` instead of hardcoding `0`.

### Proof of Concept
1. Attacker monitors mempool for a pending `WombatPoolHelperV2.depositFor(amount, for)` transaction.
2. Attacker frontruns with a large swap against the same Wombat pool's `depositToken`/`lpToken` asset, skewing the cash/liability ratio unfavorably for new deposits.
3. Victim's `depositFor` executes: `_deposit(_amount, 0, _for, address(this))` passes `minimumLiquidity = 0` to `WombatStaking.deposit`, which passes it unchanged to `IWombatPool.deposit`; the pool mints a reduced amount of LP shares to `_for` because the slippage check `amount0 >= 0` always succeeds.
4. Attacker backruns by reversing the swap, restoring the pool ratio and capturing the value difference, while the victim's `_for` address is left holding fewer LP/receipt/staked shares than the deposit was actually worth.
