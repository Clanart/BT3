### Title
Flash-loan sandwich of `queueNewRewards` allows zero-duration reward sniping via `WombatPoolHelper.depositLP`/`withdraw` → `MasterMagpie.withdrawFor` → `BaseRewardPool.getReward` - (File: rewards/BaseRewardPool.sol)

### Summary
`BaseRewardPool` distributes rewards instantaneously by adding the whole `queueNewRewards` amount to `rewardPerTokenStored` in one step, instead of streaming it over time as in Synthetix-style `rewardRate * duration` designs. Because there is no time-weighting, any staker holding a balance at the exact moment `queueNewRewards` executes captures a full pro-rata share of that reward, even if they staked one block earlier and unstake immediately after.

### Finding Description
`WombatPoolHelper.depositLP` stakes on behalf of the caller via `MasterMagpie.depositFor`, which (via `_deposit`) calls `_harvestBaseRewarder` and then sets `user.amount`/`rewardDebt` [1](#0-0) . During that flow, `BaseRewardPool.getReward`'s `updateReward` modifier calls `_updateFor`, which fixes `userRewardPerTokenPaid[token][attacker] = rewardPerToken(token)` at the current (pre-reward) index [2](#0-1) .

`BaseRewardPool.queueNewRewards`/`_provisionReward` then adds the entire new reward to `rewardPerTokenStored` in a single, non-time-weighted step based on `totalStaked()` at that instant, with no `rewardRate`/`periodFinish` streaming mechanism: [3](#0-2) .

When the attacker then calls `WombatPoolHelper.withdraw`, it calls `_unstake` → `MasterMagpie.withdrawFor` → `_harvestAndUnstake` → `_harvestBaseRewarder` → `getReward`, whose `updateReward` modifier recomputes `earned` using the *current* (post-`queueNewRewards`) `rewardPerToken` minus the attacker's baseline recorded at deposit time, then pays it out via `IERC20.safeTransfer` [4](#0-3) . The withdraw/unstake path is defined in `WombatPoolHelper.sol`: [5](#0-4) [6](#0-5) .

Since `earned()` is purely `balanceOf(account) * (rewardPerToken - paid) / decimals` with no minimum staking duration or vesting curve, the attacker's momentary (single-block, flash-loan-funded) balance at the time reward is queued is enough to entitle them to a full pro-rata share of that reward: [7](#0-6) . `nonReentrant`/`_onlyPoolHelper` guards on `MasterMagpie.depositFor`/`withdrawFor` only prevent reentrancy within a single call, not sequential same-block transactions from an unprivileged EOA sandwiching the reward manager's public `queueNewRewards` transaction [8](#0-7) . The same design (immediate, non-streamed `rewardPerTokenStored` update) is repeated in `BaseRewardPoolV2.sol` and `vlMGPBaseRewarder.sol` [9](#0-8) [10](#0-9) .

### Impact Explanation
This constitutes theft of unclaimed yield from legitimate long-term stakers. Because `_provisionReward` divides the new reward by `totalStaked()` at the moment of `queueNewRewards`, the attacker's flash-inflated stake enlarges the denominator, diluting the per-token reward received by genuine long-term stakers while simultaneously entitling the attacker to `attackerStake / totalStakedAtQueueTime * rewardAmount` of the newly added reward with zero real economic holding time. This is a direct, repeatable transfer of yield value away from real depositors to the attacker's flash-loaned position, matching the "theft of unclaimed yield" impact class.

### Likelihood Explanation
The attack requires: (1) access to a flash loan for the deposit token or LP token accepted by the target pool helper (widely available for common stablecoins/LP tokens on most chains), (2) the ability to observe the reward manager's `queueNewRewards`/`harvest` transaction in the mempool and sandwich it in the same block (achievable via standard MEV/searcher bundling, no special protocol privilege needed), and (3) sufficient reward size relative to gas/flash-loan fee to be profitable. All actions (`depositLP`, `withdraw`) are public, unprivileged functions callable by any EOA/contract. This is repeatable every time a manager funds rewards, making it a realistic, recurring MEV opportunity rather than a one-off exploit.

### Recommendation
Replace the instantaneous reward accounting in `BaseRewardPool`/`BaseRewardPoolV2`/`vlMGPBaseRewarder` with a time-streamed model (e.g., Synthetix `StakingRewards`-style `rewardRate` and `periodFinish`, updating `rewardPerTokenStored` proportionally to elapsed time since `lastUpdateTime`), so that a staker's earned reward accrues linearly over the distribution period rather than being fully realizable by a single-block flash stake. Alternatively, enforce a minimum staking duration/cooldown before a user's stake becomes reward-eligible, or snapshot eligible balances prior to reward funding.

### Proof of Concept
Foundry test outline:
1. Deploy `MasterMagpie`, `BaseRewardPool` (or a Wombat LP pool set up with `WombatPoolHelper`), fund a legitimate long-term staker with LP tokens and have them `depositLP` and remain staked.
2. In a single block (using `vm.roll`/no block advance):
   a. Attacker takes a flash loan of LP/deposit tokens and calls `WombatPoolHelper.depositLP(_lpAmount)` (or `deposit`), staking a large amount relative to existing `totalStaked()`.
   b. Reward manager calls `BaseRewardPool.queueNewRewards(rewardAmount, rewardToken)`.
   c. Attacker calls `WombatPoolHelper.withdraw(_liquidity, _minAmount)`, which internally calls `getReward` and pays out `userRewards[rewardToken][attacker]`.
   d. Attacker repays the flash loan.
3. Assert: `IERC20(rewardToken).balanceOf(attacker) > 0` even though attacker's staking duration was zero seconds/one block, and assert this amount is proportional to `attackerStake / (attackerStake + totalStaked)` of `rewardAmount` — i.e., non-zero despite no time-weighted entitlement, and that the pre-existing staker's realized reward share is correspondingly reduced compared to a baseline run without the attacker's sandwich.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
