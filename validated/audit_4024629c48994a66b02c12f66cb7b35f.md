### Title
Direct token donation to MasterMagpie inflates `totalStaked()` and permanently dilutes `rewardPerTokenStored` for real stakers - (File: rewards/BaseRewardPoolV2.sol)

### Summary
`BaseRewardPoolV2.totalStaked()` derives the reward-accounting denominator from the raw ERC20 balance of the operator (`MasterMagpie`) rather than from the pool's internally tracked staked amount, while `balanceOf()` uses `MasterMagpie`'s separate `stakingInfo` accounting. An attacker can send `stakingToken` directly to `MasterMagpie` (bypassing `deposit()`), inflating `totalStaked()` without crediting any account, which permanently and irreversibly shrinks the `rewardPerTokenStored` increment computed on every subsequent `queueNewRewards`/`donateRewards` call, reducing real stakers' `earned()` forever.

### Finding Description
`totalStaked()` is defined as: [1](#0-0) 
returning `IERC20(stakingToken).balanceOf(operator)` — the *raw* token balance held by `MasterMagpie`, not an internally accounted sum of deposits.

In contrast, per-user balances used for reward accrual come from a completely separate internal mapping: [2](#0-1) 
`balanceOf(_account)` reads `IMasterMagpie(operator).stakingInfo(stakingToken, _account)`, which is only updated through the legitimate `deposit`/`withdraw` flow in `MasterMagpie`.

This mismatch is the root cause: `totalStaked()` (sum of raw balance) and the sum of all `balanceOf(account)` (sum of internal `stakingInfo` entries) are supposed to be equal, but nothing enforces that invariant. Any account can call `stakingToken.transfer(masterMagpieAddress, amount)` directly, which increases `IERC20(stakingToken).balanceOf(operator)` without touching `stakingInfo` for any account.

The reward math that consumes `totalStaked()` is in `_provisionReward`, called from `queueNewRewards`/`donateRewards`: [3](#0-2) 
`rewardInfo.rewardPerTokenStored += (_amountReward * 10**stakingTokenDecimals) / totalStaked();`

Because `totalStaked()` is inflated by the donated (non-accounted) tokens, this increment is diluted below what it should be relative to actually-staked tokens. `rewardPerTokenStored` is a monotonically-updated cumulative index (see `_earned`), so this dilution is permanent and compounds with every subsequent reward distribution as long as the donated tokens remain in `MasterMagpie`. There is no mechanism in the provided files to detect/skim non-accounted balances, and no `nonReentrant`/whitelist check prevents a raw `transfer` call to the operator contract — `onlyManager`/`onlyMasterMagpie` modifiers guard `queueNewRewards`/`getReward`, not the ERC20 transfer path itself, so they don't stop this.

### Impact Explanation
This is a real, permanent-dilution vulnerability matching the "theft or permanent freezing of unclaimed yield" impact class. All real stakers in the affected pool receive a permanently reduced `rewardPerTokenStored` growth rate for every future reward distribution as long as the donated balance sits in `MasterMagpie`, i.e. their `earned()` (computed via `_earned`, `rewards/BaseRewardPoolV2.sol:316-321`) is permanently lower than it should be. Note that the attacker cannot reclaim the donated tokens through the normal `withdraw` path (since no `stakingInfo` entry was credited to them), so this is primarily a griefing/permanent-freezing attack against other users' yield rather than a profit-extraction attack for the attacker — but the Immunefi "permanent freezing of unclaimed yield" class does not require attacker profitability, only that user funds/yield are permanently impaired.

### Likelihood Explanation
The attacker needs only: (1) capital equal to the token amount they intend to donate (which is lost/stuck, since there's no code path shown that lets them retrieve raw, non-accounted balances back out), and (2) a standard ERC20 `transfer` call, no special privileges. This is trivially repeatable against any `BaseRewardPoolV2`-based pool whose `stakingToken` is a standard transferable ERC20, and requires no reentrancy, flash loan, or governance action. The only cost/deterrent is the attacker permanently losing the donated principal (unless the token has some way to be swept back, which is not present in these files).

### Recommendation
Track `totalStaked()` via internal cumulative accounting (e.g., a `totalSupply` variable incremented/decremented in `stakeFor`/`withdrawFor`, as already done in `BribeRewardPool.totalStaked()` at `rewards/BribeRewardPool.sol:48-50`) instead of reading the raw `balanceOf(operator)`. This decouples the reward-per-token denominator from arbitrary/unsolicited token transfers to the operator contract.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `BaseRewardPoolV2` for a mock ERC20 `stakingToken`, register the pool.
2. Have "Alice" (real staker) call `deposit(stakingToken, amount)` through `MasterMagpie`, verify `pool.balanceOf(alice) == amount` and `pool.totalStaked() == amount`.
3. As "Attacker" (unprivileged EOA), call `stakingToken.transfer(address(masterMagpie), hugeAmount)` directly (no `deposit` call).
4. Assert `pool.totalStaked()` increased by `hugeAmount` while `pool.balanceOf(attacker) == 0`.
5. Call `pool.queueNewRewards(rewardAmount, rewardToken)` (as an approved manager) and record `rewardPerTokenStored` before/after.
6. Compare Alice's `earned(alice, rewardToken)` against the value it would have had absent the attacker's donation (compute expected `rewardAmount * 1e18 / aliceStakedOnly`). Assert Alice's actual earned amount is materially lower, demonstrating permanent dilution.
7. Attempt to have the attacker withdraw the donated `hugeAmount` via `MasterMagpie.withdraw` and confirm it reverts/returns 0, showing the loss to real stakers is permanent while the attacker cannot self-correct it.
