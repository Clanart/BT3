Found a strong analog: in `Bitcoin::get_outputs`, the `outputs` vector is declared outside the per-transaction loop, so the `data`/`presumed_origin` of the last matching transaction overwrites all previously collected outputs.

### Title
Cross-transaction data/presumed_origin pollution in `get_outputs` lets an attacker hijack other deposits' `InInstruction` and refund origin - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::get_outputs` scans every non-coinbase transaction in a block for outputs paying the multisig's scripts. The `outputs` accumulator is created once per block, but the loop that assigns `presumed_origin` and the embedded Serai `data` (`InInstruction`) is applied to *all* accumulated outputs — not just those found in the current transaction. Any unprivileged party can include a transaction paying dust to the vault's external address, ordered after a victim's deposit in the same block, causing the victim's output to be stamped with the attacker's `InInstruction` data and refund origin.

### Finding Description
In `processor/src/networks/bitcoin.rs`, `get_outputs` declares `let mut outputs = vec![]` before iterating `block.txdata[1 ..]`. For each transaction, scanned outputs are pushed onto this shared vector. After the per-tx push, the code checks `if outputs.is_empty() { continue }` — which only tests whether *any* output has been seen so far in the block — then computes `presumed_origin` from `tx.input[0]` and `data` from `Self::extract_serai_data(tx)`, and finally iterates `for output in &mut outputs`, overwriting `data` (for `OutputType::External`) and `presumed_origin` on every output collected from *previous* transactions as well.

Because the loop over `outputs` is not scoped to the current transaction, the last matching transaction in the block defines the `data` and `presumed_origin` for every scanned output in the entire block. These fields flow into `instruction_from_output` / refund handling in `processor/src/multisigs/mod.rs`, where `data` carries the `InInstruction` (destination for minted coins) and `presumed_origin` supplies the refund address when instruction parsing fails.

### Impact Explanation
An attacker who observes a victim's deposit transaction in the mempool (or simply front-runs/griefs any block containing deposits) can craft a transaction that (a) pays ≥ dust to the vault's external P2TR address and (b) embeds an `InInstruction` crediting the attacker's Serai account, with `input[0]` spending an output whose script_pubkey encodes an attacker-controlled refund address. Once mined in the same block after the victim's tx, the victim's `Output` is rewritten to carry the attacker's `data` and `presumed_origin`. The victim's deposited BTC then mints Serai assets to the attacker's instruction, or — if the instruction is invalid — refunds to the attacker's origin. This is theft of deposited funds reachable purely by sending a Bitcoin transaction.

### Likelihood Explanation
No privileges are required: external addresses are public, and block ordering can be influenced via fees (higher-fee attacker tx is typically ordered, and even without ordering guarantees the attack can be retried each block). The only requirement is that the attacker's dust output lands in the same block as a victim deposit; the attacker's cost is a dust output plus fees, recoverable if the mint redirection succeeds.

### Recommendation
Scope the `data`/`presumed_origin` assignment to only the outputs found in the current transaction:

```rust
for tx in &block.txdata[1 ..] {
  let scanned = scanner.scan_transaction(tx);
  if scanned.is_empty() {
    continue;
  }
  let presumed_origin = /* from tx.input[0] */;
  let data = Self::extract_serai_data(tx);
  for output in scanned {
    // set output.data / output.presumed_origin here
    outputs.push(output);
  }
}
```

Alternatively, index `&mut outputs[start_len ..]` where `start_len` is the vector length before scanning the current transaction.

### Proof of Concept
1. Victim broadcasts `tx_v` paying X BTC to the vault external address, embedding `InInstruction_v` (mint to victim).
2. Attacker broadcasts `tx_a` paying dust to the same external address, embedding `InInstruction_a` (mint to attacker), with `input[0]` referencing an attacker address.
3. Both confirm in block B with `tx_a` after `tx_v`.
4. `get_outputs(B)`: scanning `tx_v` pushes victim's `Output`; `outputs` is non-empty so `tx_a` also runs its assignment loop — `for output in &mut outputs` rewrites the victim's `data` to `InInstruction_a` and `presumed_origin` to the attacker's address before pushing the attacker's own dust output.
5. The processor reports the victim's deposit with the attacker's instruction; funds mint to (or refund to) the attacker.
