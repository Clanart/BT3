### Title
NFT royalty calculation truncates before multiplying, systematically underpaying creators - ([File: chia/wallet/nft_wallet/nft_wallet.py])

### Summary
`compute_royalty_amount()` and `NFTWallet.royalty_calculation()` compute royalty payments using integer division performed *before* the percentage multiplication, instead of multiplying first and dividing once at the end. This ordering discards remainder mojos at every intermediate step, so royalty recipients on NFT trade offers consistently receive less than the percentage they configured — and for small/low-value trades or offers involving multiple royalty-bearing NFTs, the shortfall can be total (rounds to zero). This mirrors the "simple interest calculation is not exact" class of bug: the deviation from the mathematically correct value is a function of how the calculation is split/ordered, not of a single rounding-safe division, and it silently and systematically favors the payer over the payee on every trade.

### Finding Description
`compute_royalty_amount()` computes:
```python
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
``` [1](#0-0) 

instead of the precision-preserving `abs(offered_amount) * percentage // MAX_ROYALTY_BASIS_POINTS // royalty_split`. The same truncate-then-multiply pattern is used again in the display/estimation helper `NFTWallet.royalty_calculation()`:
```python
"amount": abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS,
``` [2](#0-1) 

This function is invoked directly in the offer-construction path reachable by any unprivileged wallet user creating or taking an NFT offer, in `make_nft1_offer()`:
```python
extra_royalty_amount = compute_royalty_amount(amount, request_side_royalty_split, percentage)
payment_list.append((launcher_id, CreateCoin(address, extra_royalty_amount, [address])))
``` [3](#0-2) 

Additionally, the trade price fed into the on-chain transfer program is already floor-divided by the number of royalty-bearing NFTs on the offer side before the royalty percentage is even applied:
```python
trade_prices.append((uint64(amount // offer_side_royalty_split), settlement_ph))
``` [4](#0-3) 

Because there is no downstream mechanism that pays out the truncated remainder to the royalty recipient (the missing mojos are simply never minted into the royalty `CreateCoin`), every division performed before the final percentage application is an irrecoverable loss to the creator/royalty holder, not a rounding that nets out over time. The project's own tests document this: `test_small_amount_truncates_to_zero` shows a 100% "royalty" on an offered amount of 50 truncating entirely to 0, and `test_royalty_split_across_multiple_nfts` demonstrates the split-then-multiply ordering. [5](#0-4) 

### Impact Explanation
Royalty recipients (NFT creators) systematically receive less XCH/CAT than their configured `royalty_percentage` entitles them to whenever: (a) multiple royalty-bearing NFTs are traded together and the offered/requested amount doesn't divide evenly by `royalty_split`, or (b) the offered amount is small relative to `MAX_ROYALTY_BASIS_POINTS` (10000), causing the final `// 10000` to zero out a nonzero intended royalty. Because offers/trades are a core, high-volume user-facing flow (any wallet user or offer counterparty can trigger this simply by constructing or accepting an NFT offer), the aggregate value loss to creators across many trades can be non-trivial, particularly for lower-priced NFT collections or bundle/complex offers with several royalty NFTs — directly analogous to the referenced report's concern about suppliers "missing out" on value due to non-exact interest/percentage math in low-activity/low-value conditions.

### Likelihood Explanation
This is trivially and deterministically reachable by any wallet user constructing an NFT offer with royalty-bearing NFTs — no privileged access or malicious peer/node behavior is required. The truncation is guaranteed to occur (not merely possible) whenever the arithmetic doesn't divide evenly, which is the common case for arbitrary trade amounts, and is proven by the project's own unit tests (`test_small_amount_truncates_to_zero`, `test_royalty_split_across_multiple_nfts`) rather than speculation.

### Recommendation
Reorder the arithmetic in both `compute_royalty_amount()` and `NFTWallet.royalty_calculation()` to multiply by `percentage` first and perform the division(s) last, minimizing truncation to at most one final integer division:
```python
amount = abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)
```
Also avoid pre-dividing the on-chain `trade_prices` value by `offer_side_royalty_split` before royalty percentage is applied; instead apply the percentage to the full amount and divide once at the end. Consider tracking/paying out any remainder to avoid cumulative underpayment across split royalty distributions.

### Proof of Concept
Using the existing test helper directly demonstrates the loss:
```python
from chia.wallet.nft_wallet.nft_wallet import compute_royalty_amount

# 100% "royalty" on a 50-mojo offer truncates entirely to 0 instead of 50
result = compute_royalty_amount(offered_amount=-50, royalty_split=1, percentage=100)
assert result == 0  # creator receives nothing despite a configured percentage
``` [6](#0-5) 
For the multi-NFT case, an offered amount that isn't evenly divisible by `royalty_split` loses the remainder at the `//royalty_split` step before the percentage is even applied, e.g. offering 999,999 mojos split across 2 NFTs with `royalty_split=2` truncates to 499,999 before multiplying by `percentage`, discarding a mojo that would have survived with multiply-first ordering — and this compounds with the `//MAX_ROYALTY_BASIS_POINTS` truncation that follows. def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
