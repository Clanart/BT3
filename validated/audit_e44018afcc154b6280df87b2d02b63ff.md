Based on my research, I found a valid analog in the `GetProof` API (`eth_getProof` / `kaia_getProof`), which shares the exact same root cause pattern as the reported `eth_getRestorationProof` issue: unbounded, attacker-controlled input driving expensive trie proof computation on a public-by-default RPC namespace with no size cap or execution deadline.

### Title
Unbounded `storageKeys` in `eth_getProof`/`kaia_getProof` enables computational DoS on public RPC nodes - (File: `api/api_eth.go`)

### Summary
`doGetProof`, backing both `EthAPI.GetProof` (`eth_getProof`) and `KaiaBlockChainAPI.GetProof` (`kaia_getProof`), accepts a caller-supplied `storageKeys []string` slice and, for every element, opens a storage trie and performs a full Merkle-proof walk (`storageTrie.Prove`) plus a `state.GetState` read, with zero limit on the number of keys and no request timeout, on APIs that are registered `Public: true` on the default `eth` and `kaia` namespaces.

### Finding Description
`doGetProof` iterates over the full `storageKeys` array without any length cap: `storage/statedb` proof generation and `state.GetState` are executed once per key. [1](#0-0) 
For each key it opens/creates a `Trie` and calls `Prove`, which walks the trie from root to leaf collecting all intermediate nodes — a non-trivial disk/CPU cost that scales with trie depth (i.e., grows as the chain and its state grow, exactly the "longer chain → more work" dynamic the original report calls out). [2](#0-1) 
Both entry points forward directly to this function without any pre-validation of `len(storageKeys)`: [3](#0-2) [4](#0-3) 
These are registered on the `eth` and `kaia` namespaces with `Public: true`, meaning they are exposed by default whenever a node operator enables the standard `eth`/`kaia` API set — operators cannot selectively disable just this endpoint while keeping the rest of `eth`/`kaia` available, mirroring the exact operational constraint described in the original report. [5](#0-4) [6](#0-5) 

By contrast, other potentially heavy public APIs in this codebase (`eth_getLogs`/`kaia_getLogs`, `FeeHistory`) do enforce explicit caps (`GetLogsMaxItems`, `GetLogsDeadline`, `maxFeeHistory`, `maxQueryLimit`), confirming that bounding expensive public queries is the established pattern in this codebase — and that `GetProof` is a gap where that pattern was not applied. [7](#0-6) [8](#0-7) 

### Impact Explanation
A single unprivileged RPC caller can submit a `getProof` request with an arbitrarily large `storageKeys` array against a contract address, forcing the node to perform a proportionally large number of trie proof walks and state reads within one synchronous RPC call, with no cap and no execution deadline (unlike `getLogs`'s `GetLogsDeadline`). Because there is no way for a public-RPC operator to disable only this call while keeping the rest of the `eth`/`kaia` namespace enabled, repeated or concurrent requests can consume CPU/disk I/O disproportionate to the request cost, degrading service for legitimate users — a resource-exhaustion / availability impact on public RPC infrastructure.

### Likelihood Explanation
High feasibility: the request requires only a normal JSON-RPC call to a publicly exposed default-enabled API, no special privileges, no on-chain transaction, and no unusual chain state. The cost scales with attacker-supplied array size and with trie depth, which only grows as the chain ages, worsening over time exactly as in the original report.

### Recommendation
Enforce a maximum number of `storageKeys` per `GetProof`/`doGetProof` call (analogous to `GetLogsMaxItems`) and apply a request/context deadline around the proof-generation loop (analogous to `GetLogsDeadline`), returning an error when limits are exceeded, in both `api/api_eth.go` (`EthAPI.GetProof`) and `api/api_kaia_blockchain.go` (`KaiaBlockChainAPI.GetProof`).

### Proof of Concept
1. Deploy or pick a contract address with a non-trivial storage trie on a mature chain (so trie depth is realistic).
2. Send `eth_getProof(address, storageKeys, "latest")` where `storageKeys` is a very large array (e.g., tens of thousands of distinct hex keys).
3. Observe `doGetProof` executing a `Prove` call and a `GetState` read per key with no early termination, consuming CPU/IO proportional to array size and trie depth, and no configurable timeout aborting the call.
4. Repeat concurrently from multiple connections to amplify load on a public RPC node that cannot disable `getProof` without disabling the entire `eth`/`kaia` namespace.
