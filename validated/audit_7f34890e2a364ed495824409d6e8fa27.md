### Title
Unbounded participant count in threshold-key deserialization causes CPU exhaustion - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` trusts the serialized `n` field and processes up to 65,535 constant-interpolation scalars and 65,535 verification-share points without an application-level work limit. `ThresholdParams::new` permits any non-zero `t <= n`, so a fully valid serialized key can maximize this work. [1](#0-0) [2](#0-1) 

### Finding Description
The parser reads attacker-controlled `t`, `n`, and `i` fields, then loops `n` times to deserialize constant coefficients when interpolation byte `0` is selected, and loops another `n` times to deserialize verification shares. [3](#0-2)  Each verification share requires a canonical point decode, which deserializes the point and re-encodes it to verify canonicality. [4](#0-3) 

After deserialization, `ThresholdKeys::new` validates that constant interpolation is only used when `t == n`, then computes the group key by scalar-multiplying and summing the first `t` verification shares. [5](#0-4)  Setting `t = n = 65535` therefore causes approximately 65,535 scalar decodes, 65,535 point decodes, and 65,535 scalar multiplications in response to one serialized object. [6](#0-5) [7](#0-6) 

### Impact Explanation
An unprivileged party able to submit bytes to `ThresholdKeys::read` can consume disproportionate CPU and memory compared with a roughly 4 MiB serialized input for 32-byte scalar and point encodings. [1](#0-0)  Repeated submissions can exhaust worker capacity and make the caller unavailable, matching the large-loop denial-of-service class represented by CVE-2016-6511. [7](#0-6) 

### Likelihood Explanation
The serialized fields directly control the work: `n` controls both deserialization loops, while `t` controls the expensive group-key calculation. [3](#0-2) [7](#0-6)  Exploitation only requires syntactically valid canonical encodings; canonical identity points and small scalars are sufficient because the cost is incurred by iteration and group arithmetic rather than point validity beyond decoding. [8](#0-7)  The practical reachability depends on the application passing untrusted bytes to `ThresholdKeys::read`, which is a supported public deserialization API. [9](#0-8) 

### Recommendation
Impose a protocol-appropriate maximum `n` before allocation or deserialization, preferably during parameter decoding rather than after the vectors have been populated. [3](#0-2)  Alternatively, add a bounded `read` variant accepting a caller-supplied maximum participant count and reject inputs exceeding it before reading coefficients or verification shares. [10](#0-9) 

### Proof of Concept
For a ciphersuite with 32-byte scalar and point encodings, construct a serialized `ThresholdKeys` object with `t = n = i = 65535`, interpolation tag `0`, then repeat a canonical scalar encoding 65,535 times, append a canonical secret-share scalar, and repeat a canonical point encoding 65,535 times. [3](#0-2)

use dkg::{Participant, ThresholdKeys};
use ciphersuite::{Ciphersuite, group::{ff::PrimeField, GroupEncoding}};

fn dos_payload<C: Ciphersuite>() -> Vec<u8> {
  let n = u16::MAX;
  let mut payload = Vec::new();

  payload.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
  payload.extend(C::ID);
  payload.extend(n.to_le_bytes()); // t
  payload.extend(n.to_le_bytes()); // n
  payload.extend(Participant::new(n).unwrap().to_bytes()); // i

  payload.push(0); // Interpolation::Constant
  let scalar = C::F::ONE.to_repr();
  for _ in 0 .. n {
    payload.extend(scalar.as_ref());
  }

  payload.extend(scalar.as_ref()); // secret_share

  let point = C::G::identity().to_bytes();
  for _ in 0 .. n {
    payload.extend(point.as_ref());
  }

  payload
}
