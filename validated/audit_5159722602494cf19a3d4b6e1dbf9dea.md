## Finding

Based on the evidence gathered, GitHub Desktop hard-codes a value that disables a Git-native anti-exploitation safeguard on every clone of a user-supplied/attacker-supplied repository URL. [1](#0-0) 

### Title
Git clone symlink/hook protection is hard-coded `false` for every Desktop clone - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment passed to every invocation of `git clone --recursive`, regardless of the source or trustworthiness of the URL being cloned. [2](#0-1) 

### Finding Description
`GIT_CLONE_PROTECTION_ACTIVE` is the same-named environment variable Git itself introduced as an internal re-entrancy guard for the clone-time protections that were added to Git in response to the symlinked-`.git`/embedded-repository class of clone vulnerabilities (the fixes shipped with the April 2024 Git security releases, e.g. the family of issues around case-insensitive/case-sensitive filesystem `.git` collisions and hook execution during recursive clone of untrusted repositories/submodules). Git sets this variable to `true` internally while its own top-level clone protection check is running, and treats a caller-supplied `false` as "the protection has already run / skip it." By statically forcing this variable to `false` from application code before every clone, Desktop causes Git to believe the protective check has already executed and skips it, for both the top-level clone and — critically — for every recursively-fetched submodule clone triggered by `--recursive`, since the same env is inherited by the whole `git clone --recursive` process tree. [3](#0-2) 

The only defenses Desktop layers on top are `isClonePathSensitive()`, which merely blocks cloning *into* a small hard-coded list of sensitive destination directories (`~/.ssh`, `~/.gnupg`, `~/.config`, etc.), and does nothing to validate the *contents* of the remote repository being cloned. [4](#0-3) 

The clone path is reachable with a fully attacker-controlled remote URL: Desktop's URL-scheme handler resolves `x-github-client://openRepo/...` deep links and GitHub "Open in Desktop" links directly into a clone of the attacker-chosen URL via `openOrCloneRepository(url)` → `clone()`, with no repository allow-listing beyond the destination-path check. [5](#0-4) 

### Impact Explanation
If `GIT_CLONE_PROTECTION_ACTIVE=false` does in fact suppress Git's own top-level safety check (as its name and Git's use of the same variable strongly indicate), a malicious repository or submodule cloned through this code path — reachable from an untrusted URL a user clicks (deep link) or pastes into the "Clone repository" dialog — could exploit the exact class of bug that protection was designed to stop: files being written outside the intended working tree via crafted embedded/`.git`-colliding paths, or hook files exposed and later executed. That maps directly to the accepted impact categories: file write outside the repo and potential code execution from a crafted repository the user merely clones or opens via link.

### Likelihood Explanation
Likelihood is high for exposure (every single clone in the app takes this path, no opt-out) but the exploitability depends on details of the underlying Git-level check that could not be independently confirmed from the codebase alone — the app does not document *why* this flag is set, there's no comment, and no test in the suite (`app/test/unit/git/clone-test.ts`) exercises or asserts anything about `GIT_CLONE_PROTECTION_ACTIVE`, so the intent behind hard-coding it to `false` is not evidenced anywhere in-repo. [6](#0-5) 

### Recommendation
Remove the hard-coded `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override (or replace it with a named, documented constant explaining exactly why Git's own clone-time protection is being bypassed) and verify against the installed Git/dugite version whether this check should instead be left at its default (protection enabled). If the override exists to prevent recursion into nested clone processes spawned for submodules, that should be scoped precisely (e.g., only set on the child submodule-clone invocation) rather than applied uniformly to the parent clone that handles untrusted, attacker-supplied URLs.

### Proof of Concept
Concrete exploitation could not be fully validated from the static index alone — this requires confirming the exact behavior of `GIT_CLONE_PROTECTION_ACTIVE` in the bundled Git/dugite version and constructing a repository that trips the specific Git-side check it disables (e.g., a submodule or tree entry engineered to collide with `.git` on the target filesystem). I was unable to locate the corresponding Git binary/dugite vendoring code in this index to confirm the exact semantics, so this should be verified in a live environment (clone a crafted PoC repository — such as those published for the April 2024 Git clone-protection CVEs — through Desktop's "Clone repository" dialog and via an `x-github-client://openRepo` deep link) before treating this as confirmed exploitable, rather than merely a code-quality/hard-coded-constant issue.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
