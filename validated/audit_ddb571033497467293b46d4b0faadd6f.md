Based on the investigation, I found a structurally identical bug class in GitHub Desktop's deep-link URL parser: **a composite/multi-field input is partially validated — some fields are checked for dangerous characters, but a sibling field that flows to the same sink is not.** This mirrors the IBC report's core flaw (checking `revision_height` while skipping `revision_number` on the same timeout struct).

### Title
Missing character/path validation on the `filepath` query parameter in deep-link `open-repository-from-url` handling - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL()` handles the `x-github-client://openRepo/...` deep link (and its Windows/`github-mac` protocol variants) that is invoked whenever a user clicks a "Clone in Desktop" / "Open in Desktop" link on a web page or elsewhere. The handler extracts `pr`, `branch`, and `filepath` from the URL's querystring and packages them into an `IOpenRepositoryFromURLAction`. [1](#0-0)  While `pr` is validated with a strict digit regex and `branch` is validated with `testForInvalidChars()` (which rejects control characters, `..`, path separators like `:` `\` and trailing `/`), `filepath` is passed through completely unvalidated and unsanitized before being returned to the rest of the app. [2](#0-1) 

### Finding Description
The invalid-character/traversal check exists precisely because these string fields are attacker-controlled (they come straight from a URL any web page can construct and get a user to click) and are later used as filesystem-adjacent values once the target repository is cloned. `testForInvalidChars()`, shared with git ref sanitization, is deliberately applied to `branch` to strip out things like `..`, `/`,`\`, and control characters. [3](#0-2)  The same class of dangerous sequences (e.g. `../../../etc/passwd`, absolute paths, or embedded control characters) is never checked for `filepath`, even though `filepath` is documented as "the file to open after cloning the repository". [4](#0-3)  This is exactly the same "checked one field of the composite value but not the sibling field feeding the same downstream operation" pattern as the original report (checking `revision_height` but not `revision_number`).

### Impact Explanation
If `filepath` is later joined with the freshly-cloned repository's local path to open/reveal a file (the natural purpose of this field), an attacker-crafted deep link containing traversal sequences (`../../..`) or an absolute path could cause Desktop to open/read a file outside of the intended clone directory — a directory/path-traversal read, matching the "read outside the repo" category called out as valid impact. The attack requires only that the victim click a link (e.g. a "Open in Desktop" button on an attacker-controlled or attacker-modified web page), consistent with the accepted "link or deep link the user clicks" attacker model — no local access, malware, or leaked credentials needed.

### Likelihood Explanation
The likelihood is moderate-to-high for triggering the parser itself: the `open-repository-from-url` action and its `filepath` field are reachable directly from `handleAppURL` on both macOS (`open-url`) and Windows (`--protocol-launcher`) command-line argument parsing in `app/src/main-process/main.ts`. [5](#0-4) [6](#0-5)  The unit tests confirm `branch` is actively rejected for invalid characters (`branch=%3C%3E` → `unknown`), but there is no equivalent negative test for `filepath`, confirming the gap is unintentional rather than a deliberate design choice. [7](#0-6) 

I was not able to fully trace, within the remaining tool budget, the exact downstream consumer of `filepath` in `app/src/ui/dispatcher/dispatcher.ts` (I confirmed six references there but did not get to inspect the code using them) to verify precisely how the value is joined to a filesystem path — e.g., whether `Path.join`/`Path.resolve` is used in a way that a `..`-laden or absolute `filepath` would actually escape the repo directory, or whether some other guard exists further downstream. This is the piece needed to fully confirm exploitability versus a defense-in-depth gap only.

### Recommendation
Apply the same validation used for `branch` (or equivalent path-safe sanitization, e.g. rejecting absolute paths and `..` segments) to `filepath` in `parseAppURL()` before constructing the `IOpenRepositoryFromURLAction`, and verify that any consumer that joins `filepath` to the cloned repository's local path uses a traversal-safe join (reject resolved paths that escape the repo root), consistent with the traversal-safe design already used in `sanitizeCloneName()` for the repository name field. [8](#0-7) 

### Proof of Concept
1. Attacker hosts a link: `x-github-client://openRepo/https://github.com/attacker/repo?filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa`
2. Victim clicks the link; macOS `open-url` (or Windows protocol-launcher argv parsing) invokes `handleAppURL` → `parseAppURL`. [9](#0-8) 
3. `parseAppURL` validates `branch`/`pr` but returns `filepath = "../../../../.ssh/id_rsa"` unmodified in the resulting action. [1](#0-0) 
4. Depending on how the dispatcher consumes `filepath` after clone completes (unverified in this session), this traversal payload could cause Desktop to open/read a file outside the cloned repository.

Given the confirmed missing-validation gap but unverified downstream sink behavior, I present this as the strongest local analog with the caveat above rather than a fully proven exploit chain.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)

async function handleCommandLineArguments(argv: string[]) {
  const args = parseCommandLineArgs(argv, {
    boolean: ['protocol-launcher'],
  })

  // Desktop registers it's protocol handler callback on Windows as
  // `[executable path] --protocol-launcher "%1"`. Note that extra command
  // line arguments might be added by Chromium
  // (https://electronjs.org/docs/api/app#event-second-instance).

  if (__WIN32__ && args['protocol-launcher'] === true) {
    // On Windows we'll end up getting called with something like
    // `--protocol-launcher --allow-file-access-from-files x-github-client://..`
    // which minimist naturally interprets as
    // `--allow-file-access-from-files=x:/github-client`. This is due to
    // Chromium's hot take on parsing command line arguments, see:
    // https://github.com/electron/electron/issues/20322#issuecomment-534137321
    // So while we could add '--allow-file...' as a boolean we can't know for
    // sure that Chromium won't add more switches later on which is why we have
    // to resort to looking through all arguments looking for something that
    // appears to be an app url.
    const prefixes = Array.from(possibleProtocols, p => `${p}://`)
    const matchingUrl = argv.find(arg => {
      if (prefixes.some(p => arg.startsWith(p))) {
        try {
          new URL(arg)
          return true
        } catch (e) {
          log.error(`Unable to parse argument as URL: ${arg}`)
        }
      }
      return false
    })

    if (matchingUrl) {
      handleAppURL(matchingUrl)
    } else {
      log.error(`Encountered --protocol-launcher without app url`)
    }
    // If --protocol-launcher is present we always want to bail and not
    // risk a smuggled cli switch
    return
  }
