### Title
`aptos move verify-package` (`VerifyPackage`) never compares on-chain module bytecode, only source-derived metadata - (File: aptos-move/cli/src/stored_package.rs)

### Summary
The CLI's package-verification flow (`aptos move verify-package`) is documented as "Build the package locally and verify that the on-chain copy matches," but the underlying `CachedPackageMetadata::verify` routine only diffs `PackageMetadata`/`ModuleMetadata` fields that are derived from source (name, `source`, `source_map`, `manifest`, `deps`, `upgrade_policy`, `extension`, `source_digest`). It never downloads or hashes the actual on-chain compiled module bytes to compare them against a local recompilation's bytecode.

### Finding Description
`ModuleMetadata` (both the Move struct in `aptos-move/framework/aptos-framework/sources/code.move:56-65` and the Rust mirror in `aptos-move/framework/natives/src/code.rs:101-109`) stores only `name`, `source` (gzipped source text), `source_map`, and `extension`. It contains no bytecode hash field. [1](#0-0) 

`VerifyPackage::execute` in the CLI builds the package locally, extracts its metadata, fetches the on-chain `PackageRegistry` via `CachedPackageRegistry::create(client, self.account, false)` (note `with_bytecode = false`), and calls `package.verify(&compiled_metadata)`. [2](#0-1) 

`verify` only checks `name`, `deps`, `modules`, `manifest`, `upgrade_policy`, `extension`, and `source_digest` for equality — all of these are computed from the *source*, not from the compiled `.mv` bytes actually stored under the account's module resources. [3](#0-2) 

Because `with_bytecode` is `false` in this call path, `CachedPackageRegistry` never even fetches the `bytecode` map (`get_account_module` calls only happen when `with_bytecode` is true, as seen in `create`). [4](#0-3) 

This means `verify-package` treats source-text equality (and a `source_digest` hash of source files) as a proxy for bytecode equality. If the on-chain bytecode was compiled with a different toolchain version, different `optimize`/`bytecode-version` flags, was hand-patched, or if `source_digest`/`source` were forged or omitted (e.g., empty `source` fields, which the code explicitly tolerates: `module without code`), `verify-package` can report "Successfully verified source of package" while the deployed bytecode differs from what was actually reviewed/audited. There is no code path in the CLI verify command that fetches `get_account_module` bytes and recompiles-and-compares raw bytecode, or hashes it against the locally built `.mv` file.

### Impact Explanation
Downstream tools, auditors, and users rely on `aptos move verify-package` to confirm that on-chain code matches published/audited source. A false "verified" result creates a mismatch between what is *claimed* to be running on-chain (the reviewed source) and what actually executes, undermining code-safety/trust assumptions for permissionless or resource-account-deployed packages (`create_resource_account_and_publish_package`, object code deployment, etc.). This falls under "Mismatch between verified bytes, package metadata, dependency declarations, and committed module bytes." However, this is a client-side/tooling gap, not an on-chain protocol invariant break — the chain's actual `code::publish_package` / VM `validate_publish_request` still perform real bytecode verification and compatibility checks (`aptos-move/aptos-vm/src/aptos_vm.rs:1803-1863`) independent of this CLI tool. [5](#0-4) 

### Likelihood Explanation
Likely triggerable whenever `verify-package` is used against a package whose deployer supplied benign-looking source/metadata (e.g., minimal diffs in compiler options, empty `source` on some modules, or a `source_digest` computed to match a decoy source tree) but whose deployed bytecode differs functionally. No special privilege is needed — the deployer only needs control over what they publish (already true for any deployer) and needs a party to run `verify-package` and trust its output.

### Recommendation
Extend `VerifyPackage`/`CachedPackageMetadata::verify` to always fetch on-chain module bytecode (`with_bytecode = true`) and compare a hash (or full bytes) of the locally compiled `.mv` output for each module against the corresponding on-chain bytecode, in addition to the existing metadata/source checks. Bytecode equality should be a hard requirement, not an implied consequence of source/metadata equality.

### Proof of Concept
Not runnable in this analysis (no filesystem/build access), but conceptually:
1. Compile a package `P` producing bytecode `B1` and publish it on-chain with metadata containing `source_digest = D`, `source = S`.
2. Recompile the *same* source `S` with a different compiler flag/toolchain/bytecode version (or hand-patch `B1` into `B2` while re-serializing identical metadata fields), and publish `B2` under the same `PackageMetadata` (name, deps, manifest, `source_digest`, `modules[].source` unchanged).
3. Run `aptos move verify-package --account <addr>` locally against source `S`: the compiled local metadata matches on-chain metadata field-by-field (since only source-derived fields are compared), producing `"Successfully verified source of package"`, even though the deployed bytecode `B2` differs from what a bytecode-level rebuild of `S` would produce.
