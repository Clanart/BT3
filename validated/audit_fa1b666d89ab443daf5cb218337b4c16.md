### Title
`SignableTransaction::new` computes weight/fee on a stale transaction shape that omits the OP_RETURN output - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The `liquidate` bug class is "a decision is made with a value that is stale relative to the value used in the actual state transition" — the rate is read before accrued interest updates it. The analog in `SignableTransaction::new` is that the transaction's weight/vsize — the value that determines `needed_fee` and the minimum-relay-fee check — is computed from a template transaction that *omits* the OP_RETURN data output, even though that output has already been pushed into the real `tx_outs` before the weight calculation runs. All fee/dust/change decisions are therefore made on a stale, smaller transaction than the one actually signed and broadcast.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` first:

```rust
// networks/bitcoin/src/wallet/send.rs:194-202
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}
```

Only afterwards is the weight calculated — but `calculate_weight_vbytes` is passed `payments`, not `tx_outs`, so the template `tx` it weighs contains only the payment outputs (and optionally change), never the data output:

```rust
// networks/bitcoin/src/wallet/send.rs:204
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

Inside `calculate_weight_vbytes` the template's `output` is built solely from `payments` plus the optional change output (lines 85–99). The same stale `vbytes` then drives:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) — underestimates the required fee by up to ~90 vbytes (80-byte push + output overhead).
2. The minimum-relay-fee check `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (line 211) — validates against the understated vsize.
3. The `NotEnoughFunds` check and the change-amount computation `input_sat - (payment_sat + fee_with_change)` (lines 215–234), where `fee_with_change = fee_per_vbyte * vbytes_with_change` is also computed on a data-less template.

`needed_fee` is never recomputed after the data output exists; the final `SignableTransaction` carries the real `tx` (with OP_RETURN) paired with a fee sized for the smaller template (lines 245–255).

### Impact Explanation
- The signed transaction pays `fee_per_vbyte * vbytes` for a transaction whose real vsize is larger by the OP_RETURN output's size, so its *effective* fee rate is below the caller-requested `fee_per_vbyte` — the exact "computed at a lower rate than what is actually executed" shape of the reference bug.
- In the worst case the true fee rate falls under the default minimum relay fee even though the stale-vsize check passed, so the transaction will not propagate/confirm — funds are moved into a TX that is not spendable on the intended schedule, and the `TooLowFee` guard is bypassed.
- Conversely, when `change` is set, `fee_with_change` is undersized, so the change output is credited with `value = input_sat - payment_sat - fee_with_change` — slightly too large a change amount — meaning the transaction overpays the change and underpays the fee by the same margin. No consensus failure, but the accounting is wrong and downstream fee logic (`needed_fee()`, `fee()`) reports values inconsistent with the real transaction.

### Likelihood Explanation
Reachable by any caller of `SignableTransaction::new` that supplies `Some(data)` — the data path is exercised in-tree (`test_data` in `networks/bitcoin/tests/wallet.rs`) but only asserts the OP_RETURN contents, never that `tx.vsize() * FEE == needed_fee`, so the underpricing goes uncaught. The size of the error is bounded (~80–90 vbytes), and whether it crosses the relay minimum depends on the margin between `needed_fee` and `DEFAULT_MIN_RELAY_TX_FEE * actual_vsize / 1000`, so impact is fee-correctness / liveness rather than direct theft — consistent with a Medium-severity stale-value bug.

### Recommendation
Compute the weight after all outputs are known. Either move the `calculate_weight_vbytes` calls below the OP_RETURN insertion and include the data output in the template (pass a unified `tx_outs` list), or add the serialized size/weight of the OP_RETURN output to the computed `weight`/`vbytes` before deriving `needed_fee` and performing the minimum-relay-fee check. Similarly, `vbytes_with_change` in the change branch must include the data output's weight so the change amount and fee stay consistent.

### Proof of Concept
In `networks/bitcoin/tests/wallet.rs`, extend `test_data` (lines 290–325): after signing a `SignableTransaction` created with `Some(data)`, assert `tx.needed_fee() >= u64::try_from(tx.vsize()).unwrap() * FEE`. It fails — `tx.vsize()` counts the OP_RETURN output while `needed_fee` was computed from a template lacking it, so `needed_fee == FEE * (vsize - op_return_output_vsize)`. Setting `fee_per_vbyte` to the minimum relay rate yields a transaction that passes `TooLowFee` yet whose actual sat/vbyte is below `DEFAULT_MIN_RELAY_TX_FEE`, so bitcoind rejects it on broadcast.
