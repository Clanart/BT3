Confirmed vulnerability: `_orders[commitment][token]` in `_withdraw` (and in `IntrinsicIntents._fillSameChain`) is keyed only by `(commitment, token)`, not by output-pair index. When two output-asset pairs of the same order reference the same input token, a solver who fully fills the *first* pair triggers `escrowedAmount = _orders[commitment][token]` — reading and releasing the **entire remaining escrow balance for that token**, including the portion still reserved for the other, not-yet-filled pair.

### Title
Cross-pair escrow drain when an IntentGateway order has multiple output pairs sharing the same input token - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` computes each pair's released escrow independently by index `i`, but the escrow itself is stored globally per `(commitment, token)` in `_orders`. On a pair's completing fill, the code takes the *entire* remaining `_orders[commitment][token]` balance rather than only that pair's proportional share, so a solver can drain escrow intended for a different, still-open output pair that happens to share an input token.

### Finding Description
In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:116-121`):
```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```
`_orders` is declared as `mapping(bytes32 => mapping(address => uint256)) public _orders;` [1](#0-0)  — keyed strictly by `(commitment, token)`, with no per-output-pair partition. When `amountFilled == totalRequired` for pair `i` (this pair is now fully filled), the code takes the whole current balance of `_orders[commitment][token]` as the escrow to release for that pair, instead of only `order.inputs[i].amount` (that pair's originally allocated share). If a second output pair `j` (`j != i`) was defined with `order.inputs[j].token == order.inputs[i].token` (the same input asset funding two separate output legs — a normal construction for multi-output orders where the user funds both legs with the same token), completing pair `i` first drains all remaining escrow for that token, including the amount reserved to back pair `j`. `_withdraw` then blindly decrements and transfers `escrowedAmount`: `_orders[body.commitment][token] = escrowed - amount;` [2](#0-1) . When solver 2 later completes pair `j`, `_orders[commitment][token]` is empty and `_withdraw` reverts with `UnknownOrder`, or — worse — a colluding/careless solver captures the tokens meant to pay out pair `j` while pair `j`'s output was already delivered to the beneficiary in the same or an earlier transaction, since the beneficiary transfer happens *before* the escrow check has any relation to per-pair allocation.

This differs from the already-fixed "rounding dust" issue (`evm/tests/foundry/IntentGatewayV2SameChainTest.sol:1544-1657`), which only handles dust *within a single pair's own token* correctly by releasing the leftover balance to the final filler of *that* pair. That fix assumed each token in `_orders` belongs to exactly one output pair — an assumption that breaks the moment two pairs share an input token, exactly the "sqrt(x*y)"-style shared-pool assumption in the ElasticSwap bug that let one action drain value meant for another party.

### Impact Explanation
A solver filling one output leg of a multi-leg same-chain order can capture escrow that rightfully belongs to a different leg, causing either: (a) permanent fund loss/lock for the honest solver who fills the other leg (their `_withdraw` reverts with `UnknownOrder`, or they receive nothing despite having delivered the output tokens), or (b) if timing/ordering allows, a solver receiving more input tokens than they are entitled to for the output they actually provided — an unauthorized transfer of escrowed user funds to the wrong beneficiary/amount, matching the "stealing or loss of funds" and "transaction manipulation" impact categories.

### Likelihood Explanation
This requires only a user (or the frontend that builds `Order` structs) to place a same-chain order whose `output.assets` array contains two entries referencing the same underlying `inputs[i].token`/`inputs[j].token` — a configuration not blocked by any validation in `placeOrder` or `_fillSameChain`. No relayer, prover, admin, or governance action is needed; any unprivileged solver calling the public `fillOrder` entrypoint on an order with this (unvalidated) shape triggers the miscomputation.

### Recommendation
Track escrow per `(commitment, outputIndex)` or per `(commitment, inputIndex)` instead of per `(commitment, token)`, or explicitly validate at `placeOrder` time that no two `output.assets` entries map to input entries sharing the same token address (or fold them into a single pair). Alternatively, change the full-fill release to use `order.inputs[i].amount` (this pair's originally recorded input amount) minus previously-released proportional amounts, rather than reading the shared `_orders[commitment][token]` balance directly.

### Proof of Concept
1. User places a same-chain order with `inputs = [ {tokenA, 1000}, {tokenA, 500} ]` and `output.assets = [ {tokenB, 1000}, {tokenC, 500} ]` (two legs, both funded by `tokenA`, so `_orders[commitment][tokenA] = 1500` after `placeOrder`).
2. Solver 1 fully fills leg 0 (provides `1000 tokenB`). In `_fillSameChain`, `i=0`, `amountFilled == totalRequired`, so `escrowedAmount = _orders[commitment][tokenA] = 1500` (the full remaining balance, not just `1000`). `_withdraw` transfers all `1500 tokenA` to solver 1 and sets `_orders[commitment][tokenA] = 0`.
3. Solver 2 fills leg 1 (provides `500 tokenC`) expecting `500 tokenA` in return. `_withdraw` reads `_orders[commitment][tokenA] = 0`, reverts with `UnknownOrder` — solver 2's output tokens are delivered to the beneficiary but solver 2 receives no input tokens, while solver 1 walked away with 500 tokenA beyond their entitlement.

**Note on verification confidence**: I was not able to find an explicit `placeOrder`-time check rejecting duplicate input tokens across different output pairs within the time available — this analysis is based on `IntentsBase.sol` and `IntrinsicIntents.sol` as read; a Devin session with fuller repository access should confirm `placeOrder`'s validation logic (in `evm/src/apps/IntentGatewayV2.sol` / `evm/tron/contracts/apps/IntentGatewayV2.sol`) does not already reject this order shape before treating this as fully confirmed.
