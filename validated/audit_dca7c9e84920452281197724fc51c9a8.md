### Title
Aggregator gRPC server accepts state-changing and fund-moving calls from unauthenticated peers - (File: core/src/servers.rs, core/src/rpc/interceptors.rs)

### Summary
The Verifier and Operator gRPC servers restrict every RPC to callers presenting the aggregator's or the entity's own mTLS client certificate via the `OnlyAggregatorAndSelf` interceptor [1](#0-0) . The Aggregator server, however, is explicitly documented and implemented to skip this client-certificate check: "The aggregator does not enforce client certificates but does use TLS for encryption" [2](#0-1) . This mirrors the report's `setIDOLContract()` pattern: a state-changing entry point that should be gated to a specific privileged caller is instead reachable by anyone who can open a TLS connection.

### Finding Description
`create_aggregator_grpc_server` builds the aggregator's `ClementineAggregatorServer` and passes it straight into `create_grpc_server` [3](#0-2) . Inside `create_grpc_server`, the `InterceptedService` is only wired with the `OnlyAggregatorAndSelf` interceptor `if config.client_verification` is true; otherwise it falls back to `Noop`, which passes every request through unchecked [4](#0-3) . For the aggregator role this check is documented to be intentionally disabled ("aggregator does not enforce client certificates"), meaning `Noop` is the effective policy for the aggregator endpoint, while `OnlyAggregatorAndSelf` is the effective policy for verifier/operator endpoints (as demonstrated by `test_auth_interceptor`, which shows only cert-bearing clients reach `internal_end_round` on the operator server) [5](#0-4) .

This means any TLS client (not necessarily possessing the aggregator's or an entity's private key) can invoke aggregator RPCs, including `OptimisticPayout`, which parses withdrawal parameters, checks whether the withdrawal UTXO is already spent, and then proceeds to build/broadcast a payout transaction on behalf of the protocol [6](#0-5) . The proto also exposes other unauthenticated-by-cert aggregator methods such as `GetEntityStatuses` with a `restart_tasks` flag and `Vergen` [7](#0-6) .

### Impact Explanation
This matches the "High - an unauthenticated state-changing or broadcasting call" category. `OptimisticPayout` is a state-changing/broadcasting RPC that produces and forwards a raw signed payout transaction; if reachable without proof of aggregator identity, an unprivileged network peer could repeatedly probe/trigger payout construction flows on the aggregator, and depending on downstream validation in the verifiers it invokes, could attempt to race or grief the legitimate withdrawal-processing pipeline. At minimum it is a broken authentication boundary on a component meant to be restricted to the aggregator role's own operators/verifiers trust chain, directly analogous to `setIDOLContract()` being `public` when it should be restricted to the deployer.

### Likelihood Explanation
High. This isn't a hypothetical misconfiguration — it is the aggregator's shipped default behavior, explicitly called out in `docs/usage.md`: "The aggregator does not enforce client certificates but does use TLS for encryption" [8](#0-7) . Any party able to reach the aggregator's TCP/TLS port can dial in with any TLS client cert (or possibly none, depending on TLS config) and invoke its RPCs; no possession of the operator/verifier/aggregator private keys is required, only network reachability.

### Recommendation
Apply the same `OnlyAggregatorAndSelf`-style authentication to the aggregator's own inbound gRPC surface, distinguishing genuinely public, read-only RPCs (e.g., `Vergen`, health checks) from state-changing/fund-moving ones (`OptimisticPayout`, task-restart controls). At minimum, require verifiers/operators (or another explicit allow-list of client certs) to authenticate before the aggregator will act on payout-related or administrative RPCs, mirroring the fix applied to `Auction.sol`/`AuctionBoard.sol` in the source report (moving privileged setters/actions behind an explicit caller check rather than leaving them open).

### Proof of Concept
1. Deploy an Aggregator using default configuration where `client_verification` for the aggregator listener is effectively disabled per documented behavior.
2. From any machine with network access to the aggregator's TCP port, open a TLS connection using any client certificate (self-signed, unrelated to `aggregator_cert_path`/`client_cert_path`) since `Noop` interceptor performs no cert-identity check [4](#0-3) .
3. Call `ClementineAggregator/OptimisticPayout` with crafted `OptimisticWithdrawParams`; the handler proceeds directly into UTXO-spent checks and downstream compatibility/payout logic without verifying the caller's identity [6](#0-5) .

Note: I was not able to directly execute this against a live deployment (no filesystem/terminal/browser access in this mode), so the exploitability of step 3 beyond reaching the handler (e.g., what verifier-side checks ultimately block a fraudulent payout) should be validated by a hands-on session; the core issue — the aggregator gRPC listener lacking the same certificate-based interceptor as verifier/operator listeners — is confirmed directly from the code and docs cited above.

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}
