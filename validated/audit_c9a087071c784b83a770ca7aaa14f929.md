## Title
Unbounded memory allocation when rendering image diffs for attacker-controlled blobs via `git show` with `maxBuffer: Infinity` - (File: `app/src/lib/git/diff.ts`)

### Summary
GitHub Desktop's diff pipeline enforces explicit size caps before rendering *text* diffs (`MaxDiffBufferSize`, `MaxReasonableDiffSize`, `MaxCharactersPerLine`), but the *image* diff path — which is reached for any file whose extension is recognized as an image type (`.png`, `.jpg`, `.gif`, `.ico`, `.webp`, `.bmp`, `.avif`) — bypasses those guards entirely and reads the full blob into memory with no upper bound, mirroring the "unbounded length parameter" root cause from the Tally-import report.

### Finding Description
`buildDiff` in `app/src/lib/git/diff.ts` checks `isValidBuffer`/`isBufferTooLarge` before treating a diff as text, but for binary files with an image extension it unconditionally calls `getImageDiff`, bypassing all size checks: [1](#0-0) 

`getImageDiff` in turn calls `getBlobImage`, which reads the *entire* blob into memory and re-encodes it as base64 with no size check at all: [2](#0-1) 

`getBlobImage` calls `getBlobContents` (`app/src/lib/git/show.ts`), which shells out to `git show <commitish>:<path>` using `encoding: 'buffer'` and no `maxBuffer` override: [3](#0-2) 

Crucially, in `app/src/lib/git/core.ts`, the default `maxBuffer` is set to `Infinity` whenever `encoding === 'buffer'`: [4](#0-3) 

So there is no length limit analogous to `MaxDiffBufferSize`/`isValidBuffer` on the path used for image diffs — the "length parameter" (blob size returned by `git show`) is fully attacker-controlled via the contents of a cloned/fetched repository, exactly like the unbounded `message_length`/`signature_length`/`public_key_length` in the original report. A crafted repository can contain a huge file with an image extension (it does not even need to be a valid image — the code only checks the extension, not the actual content, before calling `getImageDiff`). Comparing this with the text-diff path (`buildDiff` at lines 861-868) confirms that size guards exist for one code path but were never applied to the other.

### Impact Explanation
When a user opens the Changes/History view for a commit or working-directory change that touches such a file, Desktop will:
1. Spawn `git show` with an effectively infinite `maxBuffer`, materializing the full multi-hundred-MB/GB blob in the Node/main process.
2. Base64-encode the entire buffer (`contents.toString('base64')`), roughly doubling memory usage.
3. Pass the resulting `Image` object across the IPC boundary to the renderer to display in an `<img>` data URI, causing further memory pressure in the renderer process.

This can exhaust process memory and crash the Electron app (main or renderer process), a low-effort attack for any repository the user clones or checks out (open-source contribution workflow, forked PR checkout, etc.) — the "attacker controls a cloned/fetched repository" precondition from the task's valid-impact list.

### Likelihood Explanation
No special privileges are required: any repository the user clones, fetches, or checks out a branch/PR from can contain such a file. The only requirement is naming a large file with a recognized image extension and having it show up as a diff (new file, modified file, or a commit in history) — a completely normal user action (opening the Changes tab or browsing history) triggers the vulnerable path.

### Recommendation
Apply the same size guards used for text diffs to the image-diff path:
- Use `getPartialBlobContents`/`maxBuffer` with a bound (as already done in `app/src/ui/diff/syntax-highlighting/index.ts` via `MaxHighlightContentLength`) instead of unconditionally calling `getBlobContents` with `maxBuffer: Infinity`.
- Check the blob size (e.g., via `git cat-file -s`) before deciding to render it as an image, and fall back to `DiffType.Unrenderable`/`LargeText` above a reasonable threshold, consistent with `isValidBuffer`/`isBufferTooLarge` used elsewhere in `app/src/lib/git/diff.ts`.

### Proof of Concept
1. Create a repository containing a file `huge.png` that is actually a ~1–2 GB blob of arbitrary bytes (extension only needs to match `imageFileExtensions`).
2. Commit it, and have the victim clone/fetch/checkout this repository in GitHub Desktop.
3. Open the commit or working-directory change containing `huge.png` in the Changes/History view.
4. Desktop calls `buildDiff` → detects binary + image extension → `getImageDiff` → `getBlobImage` → `getBlobContents` → `git show HEAD:huge.png` with `maxBuffer: Infinity`, loading the full ~1–2 GB blob into memory, then base64-encoding it (doubling memory) before sending it to the renderer — causing severe memory spikes/crash.

export async function getBlobImage(
  repository: Repository,
  path: string,
  commitish: string
): Promise<Image> {
  const extension = Path.extname(path)
  const contents = await getBlobContents(repository, commitish, path)
  return new Image(
    contents.buffer,
    contents.toString('base64'),
    getMediaType(extension),
    contents.length
  )
}
