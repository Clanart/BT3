### Title
Unvalidated `url` and `filepath` in `x-github-client://openRepo` Deep Link Enables Remote-Origin/Argument Injection - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` in `app/src/lib/parse-app-url.ts` handles the `openrepo` protocol action, which is fully attacker-controlled: any website can trigger it via `x-github-client://openRepo/<url>?branch=...&pr=...&filepath=...` and the user only has to click a link. While `branch` and `pr` are validated with regexes and `testForInvalidChars`, the `url` (remote repository location) and `filepath` (file to open after cloning) parameters are passed through with no validation against a trusted-host allowlist or path scheme check — the same "lack of whitelisting for destination/receiver" defect described in the `RequestOracle.request` report.

### Finding Description
`parseAppURL` builds an `IOpenRepositoryFromURLAction` where `url` is taken directly from the path portion of the incoming URL with no host/scheme restriction: [1](#0-0) 

Only `pr` and `branch` go through format checks (`/^\d+$/`, `/^pr\/\d+$/`, `testForInvalidChars`); `url` and `filepath` have none: [2](#0-1) 

This action is then dispatched straight into the clone/open flow: [3](#0-2) 

and, for the pull-request variant, `url` flows into `openOrCloneRepository(url)`/`fetchPullRequest(url, pr)` without any check that it targets github.com or a known/trusted host: [4](#0-3) 

This is structurally identical to the reported bug class: `_destinationDomain`/`receiver` in `RequestOracle.request` are attacker-supplied and unchecked, allowing dispatch to an arbitrary, unofficial target. Here the "destination" is the git remote (and the follow-on file path), and there is no equivalent of a `trustedMailBox`/whitelist — the analog of "utilize `trustedMailBox` instead of user-provided `_mailbox`" would be restricting `url` to `github.com`/known enterprise hosts before it is used to drive clone/fetch operations.

### Impact Explanation
Because `url` is not restricted to a trusted host or scheme, and Desktop's compare-URL/enterprise-URL validators (`enterprise-validate-url.ts`) are not applied here, a malicious webpage can craft an `x-github-client://openRepo/...` link that drives Desktop into cloning or fetching from an attacker-chosen remote with attacker-chosen ref/PR metadata, and — for the PR path — automatically fetches and checks out `pullRequest.head.repo.clone_url` / `pullRequest.head.ref` from whatever `url` claims that PR belongs to. If the eventual git clone/fetch call does not itself defend against argument-injection style values (e.g. a `url` beginning with `-` being interpreted as a git flag) or unexpected schemes, this can result in unauthorized git operations, silent corruption of the repository being opened, or execution of unintended local git configuration. I was not able to inspect the implementation of `openOrCloneRepository` within the available tool budget to confirm whether it separately sanitizes the `url` before invoking git, so the exact reachability of code execution/argument injection specifically is unconfirmed and should be verified directly.

### Likelihood Explanation
High for the "unvalidated destination" primitive itself — any attacker who can get a user to click a link (a webpage, email, chat message) can trigger `parseAppURL`'s `openrepo` handling with a fully attacker-chosen `url`/`filepath`, requiring no local access, credentials, or malware, matching the valid-impact criteria (link the user clicks, no unnatural steps).

### Recommendation
- Apply a whitelist/allowlist check to the `url` and `filepath` parameters in `parseAppURL` (or immediately in `dispatchURLAction`) analogous to the recommended `RequestOracle` fix: only accept `url` values whose host matches github.com or a configured/known GitHub Enterprise endpoint, mirroring the existing `enterprise-validate-url.ts` protocol/host checks.
- Extend `testForInvalidChars`-style sanitization to `url` and `filepath`, not just `branch`.
- Before invoking any git clone/fetch/open operation with `url`, reject values that don't parse as a well-formed `https://`/`git@` remote (reject values starting with `-` or containing shell/CLI-flag-like prefixes) to prevent argument injection.

### Proof of Concept
1. Host a page with a link: `<a href="x-github-client://openRepo/https://evil.example.com/attacker/repo?branch=main">Open in Desktop</a>`.
2. Victim with GitHub Desktop installed and the protocol handler registered clicks the link.
3. `parseAppURL` accepts the `evil.example.com` URL unchanged (no host whitelist) and returns `open-repository-from-url`: [5](#0-4) 
4. `dispatchURLAction` routes it to `openRepositoryFromUrl`, which will attempt to open/clone/fetch based on the attacker-controlled `url` with no destination validation: [3](#0-2)
