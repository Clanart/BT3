## Analysis

The external report's broken invariant is: *"a security check that should gate an operation touching attacker-influenced/external data is bypassed or defeated, and no fallback exists, causing silent corruption/failure of a security-sensitive action."* In the Sherlock report this is the unchecked `transfer()` return value; in GitHub Desktop, the closest structural analog is the explicit disabling of a Git-native anti-RCE safeguard during `clone`. [1](#0-0) 

### Title
`clone()` explicitly disables Git's clone-time submodule/symlink protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) for untrusted, attacker-controlled repositories - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` in [2](#0-1)  builds the environment for every `git clone` invocation and unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` before running `git clone --recursive ... -- url path`. This environment variable is Git's own opt-in safeguard (added upstream in response to the 2024 submodule/symlink RCE advisories) that makes `clone --recursive` refuse to check out a submodule structure that could smuggle a `.git` directory reference or symlink capable of escaping the intended checkout location on case-insensitive/case-preserving filesystems. GitHub Desktop turns this protection off for every clone, including clones initiated from fully attacker-controlled input such as an "Open in Desktop" deep link or a pasted clone URL.

### Finding Description
`clone()` accepts a `url` that is not necessarily typed by the user themselves — it can arrive via `x-github-client://openRepo?url=...`-style protocol handlers or "Open in Desktop" buttons on arbitrary web pages, meaning the remote content (including its submodule graph) is fully attacker-controlled. The function does add its own `isClonePathSensitive` guard against destination path traversal ( [3](#0-2) ), but that only protects the top-level clone *destination*, not the recursive submodule checkout that happens inside it.

The `--recursive` flag is always passed to `git clone` ( [4](#0-3) ), meaning submodules are automatically initialized and checked out without any additional prompt or review step. Git upstream ships `GIT_CLONE_PROTECTION_ACTIVE` (default active) precisely to prevent a hostile repository's `.gitmodules`/submodule tree — using symlinks or case-folding tricks — from placing files outside the intended working tree during this automatic recursive checkout. By forcing this variable to `'false'`, Desktop deliberately reverts to git's pre-hardening behavior for every clone it performs, regardless of how untrusted the source is.

Unlike the Sherlock report's `transfer()`, where the failure mode is an unchecked return value silently breaking functionality, here the "existing guard" (Git's own protection) is present in the dependency but is actively defeated by Desktop's own code — there is no compensating control in `app/src/lib/git/clone.ts` or `app/src/lib/git/submodule.ts` ( [5](#0-4)  shows subsequent submodule updates similarly running `submodule update --init --recursive` without restoring the protection env var).

### Impact Explanation
If the disabled Git-side check exists to stop a class of submodule/symlink-based path escapes during `--recursive` clone, unconditionally turning it off for all clones (especially ones triggered by external, attacker-supplied URLs via deep links) reintroduces that file-write-outside-the-repo / potential code-execution risk class that the upstream fix was designed to close. This matches the "attacker controls a cloned/fetched repository ... result is code execution [or] file write ... outside the repo" impact bucket.

### Likelihood Explanation
Likelihood is dependent on Desktop's Git dependency (`dugite`) actually bundling a Git version where `GIT_CLONE_PROTECTION_ACTIVE` gates the fixed behavior, and on there still existing a submodule/symlink construction that the protection would otherwise block. Assuming the bundled Git honors the variable as documented, any clone flow reachable with attacker-controlled `url`/repository content (deep link "Open in Desktop", clone-by-URL dialogs) exercises this disabled guard automatically, with no additional user action beyond initiating a normal clone.

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. Leave Git's default (active) protection in place for `clone` and the subsequent recursive `submodule update` calls in `app/src/lib/git/submodule.ts`, and only make narrow, justified exceptions (e.g., for local, already-trusted repositories) rather than a blanket disablement applied to every clone regardless of source trust.

### Proof of Concept
1. Craft a Git repository containing a submodule (or `.gitmodules` entry) shaped to exploit the case-folding/symlink condition that `GIT_CLONE_PROTECTION_ACTIVE` is designed to block (the same class of repository content used in the 2024 Git submodule RCE advisories).
2. Host it and trigger `x-github-client://openRepo?url=<attacker-repo>` (or have the victim paste the URL into Desktop's clone dialog).
3. Desktop calls `clone(url, path, options)`, which sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and runs `git clone --recursive -- url path` ( [6](#0-5) ).
4. Because the protection is disabled, Git performs the recursive submodule checkout without the upstream safeguard, allowing the crafted submodule content to be written to disk in a way the safeguard would otherwise have refused.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
