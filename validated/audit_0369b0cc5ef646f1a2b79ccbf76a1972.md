## #Vulnerability Found

### Title
Address re-association silently remaps an EVM address away from its existing Sei address without checking the reverse mapping, permanently orphaning the old Sei address and diverting its funds - ([File: utils/helpers/associate.go], [File: x/evm/keeper/address.go], [File: precompiles/addr/addr.go])

### Summary
This mirrors the n8n bug class: an automatic identity-linking mechanism overwrites an existing account binding whenever a caller-supplied identifier matches, without checking whether that identifier is already bound to someone else, and the resulting mis-linkage persists permanently. In sei-chain, the Sei↔EVM address association (`SetAddressMapping`) is the analogous "identity linkage." When a user re-associates their EVM key to a new Sei address (via the `addr` precompile's `associate`/`associatePubKey`, or through the EVM ante handler), only the forward direction (does the *target* Sei address already have an EVM mapping) is checked. The reverse direction (is this EVM address already bound to a *different* Sei address that depends on it, e.g. a validator operator or funded account) is never checked, so the old binding is silently orphaned.

### Finding Description
`SetAddressMapping` unconditionally overwrites both the `EVMAddressToSeiAddressKey` and `SeiAddressToEVMAddressKey` entries with no reciprocal check: [1](#0-0) 

Every caller of the association helper only guards the seiAddr→evmAddr direction: [2](#0-1) [3](#0-2) 

None of these paths call `GetSeiAddress(ctx, evmAddr)` to verify the EVM address isn't already bound to a *different* Sei address before overwriting. This is explicitly acknowledged in the codebase as a real risk for state depending on the "direct-cast" identity (e.g. a validator created under the byte-cast Sei address of an EVM key before that key was explicitly associated elsewhere): [4](#0-3) 

The consequence is directly demonstrated in a distribution-module test: once an EVM address is re-associated away from a Sei address it previously backed, that old Sei address (`castAddr`) can no longer receive funds via `CanAddressReceive`/`CanSendTo`, yet distribution logic (e.g. `GetDelegatorWithdrawAddr`) still resolves back to it: [5](#0-4) 

Because the withdraw address becomes permanently unreceivable, validator commission that should be paid out is instead irrecoverably diverted to the community pool: [6](#0-5) 

The `CanAddressReceive`/`CanSendTo` gate itself only recognizes an address as "still valid" if the *current* reverse mapping matches the address being checked, so once remapped, the old address is permanently locked out with no recovery path: [7](#0-6) 

The already-shipped mitigation only covers one specific trigger (EIP-7702 `SetCode` authorities are now pre-associated before EVM execution installs delegation code), but the general re-association path through the `addr` precompile (`associate` / `associatePubKey`) and the self-association performed in the Cosmos-tx ante handler (`EVMAddressDecorator.AnteHandle`) still has no reverse-mapping check: [8](#0-7) 

### Impact Explanation
Any Sei address that received funds, stake, or a validator/delegator role while implicitly using its direct-cast identity (i.e., before its EVM counterpart key was formally associated with it) can be permanently frozen out from receiving funds if the same EVM private key later associates (or is made to associate, e.g. via `associatePubKey`) with a different Sei address. This satisfies the "permanent freezing of funds" impact bar: withdraw addresses, commissions, and any subsequent transfers to the orphaned address are silently rerouted or rejected, and there is no on-chain path to reverse the reverse-mapping loss once overwritten.

### Likelihood Explanation
Re-association is a normal, unprivileged, permissionless operation available to any address holder through the public `addr` precompile (`associate`/`associatePubKey`) or simply by signing a fresh Cosmos-format transaction with the same EVM key while intending to bind a different Sei address. No special privileges, validator status, or governance action are required — a single transaction is sufficient to trigger the orphaning condition once a prior direct-cast dependency exists.

### Recommendation
Before calling `SetAddressMapping`, check `GetSeiAddress(ctx, evmAddr)` for an existing, different binding and either reject the re-association or migrate/clean up all dependent state (delegations, withdraw addresses, validator operator records) atomically. At minimum, extend the existing "pre-associate before it becomes load-bearing" fix (currently limited to `SetCode` authorities) to all association entry points (`associate`, `associatePubKey`, and the ante-handler self-association), and add an explicit guard rejecting re-association of an EVM address that is already bound to a distinct Sei address holding non-transferable state (validator operator, active delegations, locked coins).

### Proof of Concept
1. User controls EVM key `E`. Its direct-cast Sei address `A = sdk.AccAddress(E[:])` is used (without formal association) to run `MsgCreateValidator`, accumulating stake/commission at `A`.
2. Later, the same private key `E` is used to call the `addr` precompile's `associatePubKey`/`associate` with a signature that recovers to a *different* Cosmos pubkey `P2`, producing `seiAddr2 = hash(P2) != A`.
3. `associateAddresses` only checks `GetEVMAddress(ctx, seiAddr2)` (not found → proceeds) and calls `SetAddressMapping(ctx, seiAddr2, E)`, overwriting `EVMAddressToSeiAddressKey(E) -> seiAddr2` while leaving the stale entry `SeiAddressToEVMAddressKey(A) -> E`.
4. `CanAddressReceive(ctx, A)` now returns `false` because `GetSeiAddress(ctx, E)` resolves to `seiAddr2 != A`, per the logic in `x/evm/keeper/address.go:81-86`.
5. Any subsequent commission/reward payout or transfer targeting `A` fails and is redirected to the community pool (as reproduced by `TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator`), permanently freezing/losing funds owed to `A`.

func (k *Keeper) SetAddressMapping(ctx sdk.Context, seiAddress sdk.AccAddress, evmAddress common.Address) {
	store := ctx.KVStore(k.storeKey)
	store.Set(types.EVMAddressToSeiAddressKey(evmAddress), seiAddress)
	store.Set(types.SeiAddressToEVMAddressKey(seiAddress), evmAddress[:])
	if !k.accountKeeper.HasAccount(ctx, seiAddress) {
		k.accountKeeper.SetAccount(ctx, k.accountKeeper.NewAccountWithAddress(ctx, seiAddress))
	}
	ctx.EventManager().EmitEvent(sdk.NewEvent(
		types.EventTypeAddressAssociated,
		sdk.NewAttribute(types.AttributeKeySeiAddress, seiAddress.String()),
		sdk.NewAttribute(types.AttributeKeyEvmAddress, evmAddress.Hex()),
	))
}

// from an EVM address AND the originating EVM address has already been associated with

func (k *Keeper) CanAddressReceive(ctx sdk.Context, addr sdk.AccAddress) bool {
	directCast := common.BytesToAddress(addr) // casting goes both directions since both address formats have 20 bytes
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)
	return associatedAddr.Equals(addr) || !isAssociated // this means it's either a cast address that's not associated yet, or not a cast address at all.
}

// AssociateAuthorizationAuthorities pre-associates every EIP-7702 SetCode authorization
// authority in the transaction with its true (pubkey-derived) Sei address before EVM
// execution installs delegation code for it. Authorities are distinct accounts from the tx
// sender, so the sender association performed by the caller does not cover them. Without
// this, SetCode creates a mutable direct-cast EVM->Sei mapping that a later associatePubKey
// call can remap, orphaning any staking/distribution state created under the direct-cast
// identity (which can then halt the chain via the distribution validator-removal hook).
//
// This is the legacyabci counterpart of x/evm/ante's EVMPreprocessDecorator so both ante
// paths associate authorities identically. It is best-effort: only authorities whose
// authorization the EVM will actually apply are pre-associated — helpers.AuthorityToPreAssociate
// enforces the same chain-id/nonce/account-code checks go-ethereum uses, which also prevents
// replaying a publicly-visible authorization a user signed for another chain to force-associate
// them. Each association runs in its own cache context and is only committed on success, so an
// already-associated, skipped, or failing authority affects only itself and never rejects the
// transaction (matching go-ethereum, which would still accept it). Non-SetCode transactions

func (p *EVMAddressDecorator) AnteHandle(ctx sdk.Context, tx sdk.Tx, simulate bool, next sdk.AnteHandler) (sdk.Context, error) {
	sigTx, ok := tx.(authsigning.SigVerifiableTx)
	if !ok {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrTxDecode, "invalid tx type")
	}
	signers := sigTx.GetSigners()
	for _, signer := range signers {
		if evmAddr, associated := p.evmKeeper.GetEVMAddress(ctx, signer); associated {
			ctx.EventManager().EmitEvent(sdk.NewEvent(evmtypes.EventTypeSigner,
				sdk.NewAttribute(evmtypes.AttributeKeyEvmAddress, evmAddr.Hex()),
				sdk.NewAttribute(evmtypes.AttributeKeySeiAddress, signer.String())))
			continue
		}
		acc := p.accountKeeper.GetAccount(ctx, signer)
		if acc.GetPubKey() == nil {
			logger.Error("missing pubkey for signer", "signer", signer)
			ctx.EventManager().EmitEvent(sdk.NewEvent(evmtypes.EventTypeSigner,
				sdk.NewAttribute(evmtypes.AttributeKeySeiAddress, signer.String())))
			continue
		}
		pk, err := btcec.ParsePubKey(acc.GetPubKey().Bytes())
		if err != nil {
			logger.Debug("failed to parse pubkey for account, likely due to the fact that it isn't on secp256k1 curve", "account", acc.GetPubKey(), "err", err)
			ctx.EventManager().EmitEvent(sdk.NewEvent(evmtypes.EventTypeSigner,
				sdk.NewAttribute(evmtypes.AttributeKeySeiAddress, signer.String())))
			continue
		}
		evmAddr, err := helpers.PubkeyToEVMAddress(pk.SerializeUncompressed())
		if err != nil {
			logger.Error("failed to get EVM address from pubkey", "err", err)
			ctx.EventManager().EmitEvent(sdk.NewEvent(evmtypes.EventTypeSigner,
				sdk.NewAttribute(evmtypes.AttributeKeySeiAddress, signer.String())))
			continue
		}
		ctx.EventManager().EmitEvent(sdk.NewEvent(evmtypes.EventTypeSigner,
			sdk.NewAttribute(evmtypes.AttributeKeyEvmAddress, evmAddr.Hex()),
			sdk.NewAttribute(evmtypes.AttributeKeySeiAddress, signer.String())))
		p.evmKeeper.SetAddressMapping(ctx, signer, evmAddr)
		associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.evmKeeper.BankKeeper(), p.accountKeeper)
		if err := associationHelper.MigrateBalance(ctx, evmAddr, signer, false); err != nil {
			logger.Error("failed to migrate EVM address balance", "address", evmAddr, "err", err)
			return ctx, err
		}
	}
