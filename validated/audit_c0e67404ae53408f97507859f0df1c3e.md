Found a concrete, unguarded zero-divisor/rounding bug in `VWAPOracle.sol` that mirrors the report's core defect: an unprivileged party can drive a division-derived value that silently corrupts an on-chain aggregate the protocol relies on for pricing decisions, with no check that guards the degenerate (near-zero) case the way `beefy-consensus-proofs::position_reward` and `divCeil` do elsewhere in the same repo.

### Title
Unbounded solver-controlled amounts let `VWAPOracle.recordSpread` corrupt the cumulative spread average via truncating division - (File: `evm/src/apps/VWAPOracle.sol`)

### Summary
`VWAPOracle.recordSpread` computes a per-fill `spreadBps` with integer division and folds it into a running weighted average (`weightedSpreadSum / totalVolume`) that other contracts (`IIntentPriceOracle` consumers, e.g. pricing/risk logic in the Intent Gateway stack) read as a trusted signal. Unlike the analogous zero-divisor sites already hardened in this codebase (`position_reward`'s explicit `denom == 0` check, `divCeil`'s explicit `denominator <= 0` revert), `recordSpread`/`spread` only special-case an exactly-zero `totalVolume`/`inputAmountNormalized`, but never bound the *magnitude* of the caller-supplied `inputs`/`outputs` amounts. Because `recordSpread` is called by `IntentGateway` with attacker-influenced fill amounts, a solver can submit fills using dust-sized or wildly skewed `inputAmountNormalized` values that make the truncating division (`amountDiff * 10000 / inputAmountNormalized`) produce an extreme `spreadBps`, which then gets weighted into `_tokenSpreads` and permanently skews the cumulative on-chain average — the same "enforce a relation without validating the divisor/operand range" class of bug as the EraVM `mul/div` report, just moved from a zero-check to a magnitude-check gap.

### Impact Explanation
The oracle's `spread()` view is documented as `IIntentPriceOracle` — the mechanism other Hyperbridge components (or any external integrator) consult to price/validate intent fills based on historical solver behavior. Because the cumulative average is not floor/ceiling-clamped and normalization is entirely attacker-influenced (solver picks `inputs[i].amount`/`outputs[i].amount` for the fill), a solver can push `_tokenSpreads[chain][token]` to a wildly incorrect value using a single, cheap dust-sized fill, permanently distorting the on-chain price signal for that `(sourceChain, token)` pair until enough legitimate volume dilutes it (which, at extreme skew, may never fully recover given weighted averaging with unbounded per-fill weight-multiplied bps). Any downstream logic that trusts `spread()` to gate or price real capital flow inherits this manipulation — this is a "logic attack" / false-state-acceptance class outcome per the bounty scope, reachable without any relayer, prover, or admin compromise.

### Likelihood Explanation
High. `recordSpread` is invoked automatically as a side effect of every ordinary `fillOrder` call by any solver [1](#0-0) ; a solver only needs to construct one fill with an extreme ratio between `outputs[i].amount` and `inputs[i].amount` (or a tiny `inputAmountNormalized`) to trigger disproportionate weighting. No special privileges, front-running, or malicious relayer/prover assumptions are required — this is directly reachable through the public, unprivileged solver fill path.

### Recommendation
- Clamp `spreadBps` to a sane bound (e.g. ±`BPS_DENOMINATOR` or a governance-configured max) before folding it into `weightedSpreadSum`, the same way `position_reward` rejects unsafe curve ratios and `divCeil` rejects unsafe denominators.
- Consider requiring a minimum `inputAmountNormalized` (dust floor) before a fill is allowed to influence the cumulative spread, so low-volume fills cannot exert outsized leverage on the weighted average.
- Add an explicit invariant test mirroring the `set_reward_curve` zero/over-unity rejection tests already present for `beefy-consensus-proofs`, but for `VWAPOracle.recordSpread` with dust/extreme-ratio inputs.

### Proof of Concept
1. Solver places/fills an order through `IntentGatewayV2` with `inputs[i].amount` normalized to `1` wei-equivalent (after `_normalizeAmount`) and `outputs[i].amount` normalized to a large value (e.g. 10,000× the input).
2. `IntentGateway` calls `VWAPOracle.recordSpread(commitment, sourceChain, inputs, outputs)` [1](#0-0) .
3. Inside the loop: `inputAmountNormalized = 1`, `outputAmountNormalized = 10000e18` (arbitrary), so `amountDiff ≈ 10000e18`, and `spreadBps = (amountDiff * 10000) / 1` — an astronomically large value, weighted by `volume = 1` but still additive into `weightedSpreadSum` [7](#0-6) .
4. A subsequent read of `spread(sourceChain, token)` [4](#0-3)  returns a value dominated by the attacker's single dust fill rather than reflecting genuine aggregate solver behavior, since `weightedSpreadSum` carries the huge additive term forward indefinitely relative to `totalVolume`.
