### Title
Nested/recursive precompile calls cause double-application of bank balance events to the EVM StateDB, duplicating spendable balance - (File: precompiles/common/balance_handler.go, precompiles/common/precompile.go)

### Summary
The SiloAMO report is fundamentally about a permissionless code path that derives a critical value from mutable state that can be manipulated by an ordinary (non-privileged, non-flash-loan) sequence of the attacker's own legitimate transactions, causing accounting to diverge from the true invariant. The closest reachable Cosmos EVM analog is the `BalanceHandler` window-tracking mechanism (`prevEventsLen`) used to translate `x/bank` events into `StateDB.AddBalance`/`SubBalance` calls after every precompile call. When precompile calls are nested/recursive within a single EVM execution (a pattern the repo's own test suite proves is reachable by unprivileged contracts, e.g. `StakingReverter.sol`'s `performDelegation`/nested try-catch calls), the event-window bookkeeping can be corrupted, causing the same underlying bank ledger event to be re-applied to the EVM `StateDB` balance more than once (or skipped), producing a `StateDB` balance that no longer matches the real `x/bank`/`x/precisebank` balance backing it.

### Finding Description
`RunNativeAction`/`runNativeAction` in `precompiles/common/precompile.go` wraps every stateful precompile call: it snapshots the multi-store, executes the native `action`, and then — if a `BalanceHandlerFactory` is configured — calls `balanceHandler.BeforeBalanceChange(ctx)` before the action and `balanceHandler.AfterBalanceChange(ctx, stateDB)` after it. [1](#0-0) 

`AfterBalanceChange` reads `ctx.EventManager().Events()[bh.prevEventsLen:]` — i.e., only the events emitted *since* the handler's last recorded event-index — and converts `EventTypeCoinSpent`, `EventTypeCoinReceived`, and `EventTypeFractionalBalanceChange` into direct `stateDB.SubBalance`/`AddBalance` calls: [2](#0-1) 

This design assumes a single, sequentially-scoped `BeforeBalanceChange`/`AfterBalanceChange` pair per top-level bank-mutating operation. However, precompile calls in this system can nest — a Solidity contract can call one precompile whose native action internally triggers further EVM/precompile execution (or simply re-enter a precompile via `try/catch`, as demonstrated by the repo's own `StakingReverter.sol` test contract performing recursive delegate calls through nested try/catch blocks). [3](#0-2) 

The repository already contains an integration test explicitly built to reproduce this exact defect class: "the balance handler bug where recursive precompile calls share the same `BalanceHandler` instance, causing `prevEventsLen` to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB." The test triggers a recursive/nested precompile call sequence via a "debug precompile caller" contract and checks resulting event counts. [4](#0-3) [5](#0-4) 

The root cause: when an inner precompile call's `BeforeBalanceChange` records/overwrites the shared `prevEventsLen` marker (or a `NewBalanceHandler()` instance's marker is computed against a cumulative event log that an inner call has already consumed), the inner call's `AfterBalanceChange` applies a slice of bank events to `StateDB` balances. When control returns to the outer call and its own `AfterBalanceChange` runs, the outer handler's event-window boundaries can overlap with the range already consumed and applied by the inner handler, causing the same `EventTypeCoinReceived`/`EventTypeCoinSpent` event to be translated into a second `AddBalance`/`SubBalance` mutation on the `StateDB`. Because `x/bank`/`x/precisebank` was only mutated once (correctly, per the ledger), but `StateDB` is mutated twice, the EVM-visible balance diverges from the true bank-backed balance — this is a duplication of spendable value between the EVM balance view and the native ledger, exactly the type of dual-ledger desync `x/precisebank` and the `BalanceHandler` exist to prevent (see `precisebank`'s own invariant: `$a(n) = b(n) \cdot C + f(n)$`, "every `aatom` is fully backed by a `uatom`"). [6](#0-5) 

### Impact Explanation
This maps to the Critical Asset-representation invariant: "x/erc20, bank, ICS20 ... and werc20 flows must preserve 1:1 accounting between native coins, ERC20 views, escrows, and precompile-visible balances." A duplicated `StateDB.AddBalance` inflates the attacker's or a target account's EVM-visible native balance beyond what is actually backed in `x/bank`/`x/precisebank`, which is functionally equivalent to unauthorized minting/duplication of spendable value once that inflated `StateDB` balance is spent (e.g., transferred to another EVM account, or used to satisfy a subsequent EVM-level balance check), because the EVM state commit will persist the inflated balance while the bank ledger only reflects the single real transfer. Conversely, a missed application (window boundary skipping instead of double counting) would silently freeze/lose value from the EVM's view of an account balance while it's still present in the underlying bank ledger, or vice versa — both are Critical, irreversible accounting-corruption outcomes once committed to state.

### Likelihood Explanation
The trigger requires only an ordinary, unprivileged EVM transaction from a smart contract that performs nested/recursive precompile calls — no validator, relayer, or governance privilege is needed, and no flash loan is required (paralleling the "attacker's own funds, no flash loan" nature of the original Silo finding). The repository's own test fixtures (`StakingReverter.sol`'s nested try/catch delegation calls, and the dedicated `balance_handler_test.go` reproducing "recursive precompile calls share the same BalanceHandler instance") demonstrate that this call pattern is both realistic and already a recognized area of concern within the codebase, which increases confidence that the underlying event-window accounting is fragile under recursion.

### Recommendation
- Ensure each `BalanceHandler` instance's `prevEventsLen`/event-window tracking is strictly scoped per nested call frame (e.g., using a stack of watermark indices rather than a single mutable field), so that an inner call's event consumption cannot corrupt an outer call's replay window.
- Alternatively, process `AfterBalanceChange` only once at the outermost (non-nested) precompile call boundary, aggregating all events since the true start of the top-level call, and skip `Before/AfterBalanceChange` invocation for nested/re-entrant precompile calls detected via `stateDB.precompileCallsCounter` or an explicit call-depth marker.
- Add invariant checks (e.g., in CI/property tests) asserting that `sum(StateDB balances backed by bank denom)` equals `sum(x/bank + x/precisebank balances)` after arbitrary sequences of nested precompile calls, extending the existing `balance_handler_test.go` coverage to assert exact balance equality (not just event counts) after multi-level recursive precompile invocation.

### Proof of Concept
A definitive PoC requires executing the existing `TestRecursivePrecompileCallsWithDebugPrecompile` test (or an equivalent contract using `StakingReverter.sol`-style nested try/catch precompile calls) while asserting final `StateDB` balances against final `x/bank`/`x/precisebank` balances rather than only event counts, since the current test only checks `len(res.Events)` and a `debug_count`, not balance equality: [7](#0-6) 
I was unable to retrieve the full `BeforeBalanceChange` implementation in this session (tool call failure), so the precise line(s) where `prevEventsLen` is set/overwritten could not be directly cited; a follow-up code read of `precompiles/common/balance_handler.go` (lines before 59) and `precompiles/common/balance_handler_test.go` is recommended to pinpoint the exact faulty assignment and confirm whether this is a live bug or one already mitigated by the `NewBalanceHandler()` per-call instantiation seen in `runNativeAction`.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case precisebanktypes.EventTypeFractionalBalanceChange:
			addr, err := ParseAddress(event, precisebanktypes.AttributeKeyAddress)
			if err != nil {
				return fmt.Errorf("failed to parse address from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}
			if bh.bankKeeper.BlockedAddr(addr) {
				// Bypass blocked addresses
				continue
			}

			delta, err := ParseFractionalAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}

			deltaAbs, err := utils.Uint256FromBigInt(new(big.Int).Abs(delta))
			if err != nil {
				return fmt.Errorf("failed to convert delta to Uint256: %w", err)
			}

			if delta.Sign() == 1 {
				stateDB.AddBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			} else if delta.Sign() == -1 {
				stateDB.SubBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			}

		default:
			continue
		}
	}

	return nil
}

    /// @dev nestedTryCatchDelegations performs nested try/catch calls to precompile
    /// where inner calls revert intentionally. Only the successful delegations
    /// outside the reverting scope should persist.
    ///
    /// Expected successful delegations: 1 (before loop) + outerTimes (after each catch) + 1 (after loop)
    function nestedTryCatchDelegations(uint outerTimes, uint innerTimes, string calldata validatorAddress) external {
        // Initial successful delegate before any nested reverts
        STAKING_CONTRACT.delegate(address(this), validatorAddress, 10);

        for (uint i = 0; i < outerTimes; i++) {
            // Outer call that will revert and be caught
            try StakingReverter(address(this)).performDelegation(validatorAddress) {
                // no-op
            } catch {
                // After catching the revert, perform a successful delegate
                STAKING_CONTRACT.delegate(address(this), validatorAddress, 10);

                // Inner nested loop of reverting calls
                for (uint j = 0; j < innerTimes; j++) {
                    try StakingReverter(address(this)).performDelegation(validatorAddress) {
                        // no-op
                    } catch {}
                }
            }
        }

        // Final successful delegate after the loops
        STAKING_CONTRACT.delegate(address(this), validatorAddress, 10);
    }

In order to maintain consistency between the `aatom` supply and the `uatom` supply,
we add the constraint that each sub-atomic `aatom`, may only exist as part of an atomic `uatom`.
Every `aatom` is fully backed by a `uatom` in the `x/bank` module.

This is a requirement since `uatom` balances in `x/bank` are shared between the cosmos modules and the EVM.
We are wrapping and extending the `x/bank` module with the `x/precisebank` module to add an extra $10^{12}$ units
of precision. If $10^{12}$ `aatom` is transferred in the EVM, the cosmos modules will see a 1 `uatom` transfer
and vice versa. If `aatom` was not fully backed by `uatom`, then balance changes would not be fully consistent
across the cosmos and the EVM.
