Based on my investigation, the closest analog to the CometBFT bug ("app returns error on an ABCI call, but the caller doesn't treat it as fatal and continues") is in GitHub Desktop's stash-creation logic, where a Git error result is heuristically reclassified as "success" instead of being propagated, and the caller proceeds with a destructive branch checkout based on that false-positive.

### Title
Heuristic misclassification of failed `git stash push` as success leads to silent working-directory data loss during branch checkout - (File: `app/src/lib/git/stash.ts`)

### Summary
When GitHub Desktop needs to move a user's uncommitted changes to a new branch (`UncommittedChangesStrategy.MoveToNewBranch`), it calls `createDesktopStashEntry`, which shells out to `git stash push` and catches any resulting `GitError`. Instead of always propagating a Git-reported error (an "unrecoverable" signal, analogous to CometBFT's ABCI `CheckTx` error), the catch handler applies a fragile heuristic: if the exit code is `1` and stderr does not contain a line beginning with `error: `, it assumes the stash was actually created successfully and swallows the error.

### Finding Description
The relevant logic: [1](#0-0) 

The comment in the code itself acknowledges the fragility: `"Here be dragons... That didn't hold up to a quick read of the stash code"`, and gives a concrete counter-example where `git stash push` exits `1` with no `error:`-prefixed line yet **no stash was created** (unborn branch case). The same pattern of "guess whether it actually succeeded" exists in the sibling function `popStashEntry`, which infers success purely from `stderr.length === 0`: [2](#0-1) 

This mirrors the CometBFT flaw: the underlying tool (git / the ABCI app) reported an error, but the wrapping logic doesn't treat that as fatal/unrecoverable — instead it guesses at intent using an incomplete heuristic (presence/absence of a specific string prefix) and proceeds as if nothing went wrong.

The consumer of this function is `checkoutAndBringChanges` in `app-store.ts`, which treats a truthy return from `createStashEntry` as proof that the working directory is now safely stashed, and then immediately force-checks-out the target branch (discarding working-directory state) and later pops the (possibly non-existent) stash: [3](#0-2) 

If `createDesktopStashEntry` incorrectly reports `true` for a case where the stash was **not** actually created (e.g., unusual `git stash push` failure modes such as filter/hook errors introduced by an attacker-controlled `.gitattributes` clean/smudge filter, or locale/message variations that don't match the `error:`-prefix pattern), Desktop proceeds to `checkoutIgnoringChanges` — which force-checks-out the new branch — discarding the user's uncommitted changes with no real backup in the stash.

### Impact Explanation
This can result in **silent, unrecoverable loss of the user's uncommitted working-directory changes** — a case of "silent corruption of what the user commits," since the user believes their changes are safely stashed and recoverable, but they are actually discarded. The attacker primitive here is a maliciously crafted repository (e.g., via `.gitattributes` filters or hooks) that causes `git stash push` to fail in an unexpected, non-`error:`-prefixed way when the victim triggers the "bring changes to new branch" checkout flow.

### Likelihood Explanation
The stash push failure path is narrow and depends on unusual git output formats (locale, filter, or hook-driven error text) not matching the hardcoded `error:` regex. This requires the victim to have uncommitted changes and to hit a checkout that requires this specific `MoveToNewBranch` fallback path (triggered only after an initial checkout attempt fails due to local changes being overwritten), making this a plausible but narrow, low-to-medium likelihood path rather than a trivially reproducible one.

### Recommendation
Do not infer stash success/failure from string matching heuristics on stderr. Instead, verify success authoritatively (e.g., by checking `git rev-parse refs/stash` before/after, or comparing stash list contents) before proceeding with any destructive checkout operation. Any ambiguity should default to failing safe (treating it as an error and aborting the checkout), which mirrors CometBFT's fix of treating any unexpected app error as fatal.

### Proof of Concept
1. Prepare a repository with a `.gitattributes` clean filter or a `pre-commit`-adjacent hook that git's stash machinery might invoke, engineered to make `git stash push` exit with code `1` and print a message that does not start with `error: ` (e.g., a custom warning or a git version whose message wraps differently, as already demonstrated by the code's own documented "unborn branch" counter-example at [4](#0-3) ).
2. Have the victim clone this repository into Desktop, make local uncommitted changes, and switch to a branch under the `MoveToNewBranch` strategy, triggering `checkoutAndBringChanges`.
3. Because `git stash push` fails without producing an `error:`-prefixed stderr line, `createDesktopStashEntry` returns `true` even though no stash was created.
4. `checkoutAndBringChanges` proceeds to force checkout the new branch, discarding the user's uncommitted changes with no real stash backup to restore from.

      //
      // % git stash push -m foo ; echo $?
      // You do not have the initial commit yet
      // 1
      //
      // I'm not going to mess with this now but I felt the need to document
      // my findings should I or any other brave soul choose to tackle this in
      // the future.
      if (e instanceof GitError && e.result.exitCode === 1) {
        // search for any line starting with `error:` -  /m here to ensure this is
        // applied to each line, without needing to split the text
        const errorPrefixRe = /^error: /m

        const matches = errorPrefixRe.exec(coerceToString(e.result.stderr))
        if (matches !== null && matches.length > 0) {
          // rethrow, because these messages should prevent the stash from being created
          return Promise.reject(e)
        }

        // if no error messages were emitted by Git, we should log but continue because
        // a valid stash was created and this should not interfere with the checkout

        log.info(
          `[createDesktopStashEntry] a stash was created successfully but exit code ${result.exitCode} reported. stderr: ${result.stderr}`
        )
        return e.result
      }
      return Promise.reject(e)
    }

  private async checkoutAndBringChanges(
    repository: Repository,
    branch: Branch,
    currentRemote: IRemote | null
  ) {
    try {
      await this.checkoutIgnoringChanges(repository, branch, currentRemote)
    } catch (checkoutError) {
      if (!isLocalChangesOverwrittenError(checkoutError)) {
        throw checkoutError
      }

      const stash = (await this.createStashEntry(repository, branch))
        ? await getLastDesktopStashEntryForBranch(repository, branch)
        : null

      // Failing to stash the changes when we know that there are changes
      // preventing a checkout is very likely due to assume-unchanged or
      // skip-worktree. So instead of showing a "could not create stash" error
      // we'll show the checkout error to the user and let them figure it out.
      if (stash === null) {
        throw checkoutError
      }

      await this.checkoutIgnoringChanges(repository, branch, currentRemote)
      await popStashEntry(repository, stash.stashSha)

      this.statsStore.increment('changesTakenToNewBranchCount')
    }
