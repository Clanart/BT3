### Title
Melting a PlotNFT While Unclaimed Pool Rewards Are Outstanding Permanently Strands Those Rewards - (File: `chia/wallet/plotnft_wallet/plotnft_wallet.py`)

### Summary
`PlotNFT2Wallet.melt_plotnft()` / `PlotNFT.melt()` destroys (melts) the PlotNFT singleton with only a single guard — that the PlotNFT is not currently pooling — and performs no check for outstanding, already-farmed pool rewards sitting unclaimed at the `p2_singleton_puzzle_hash`. Because reward coins can only be claimed via a `SEND_MESSAGE` proof originating from the live PlotNFT singleton, destroying that singleton permanently forfeits any rewards that were not claimed first, with no sweep mechanism to recover them — closely mirroring the referenced report's root cause (an irreversible state transition that severs the link between an entity's authority and its already-accrued, unclaimed rewards, permanently stranding funds).

### Finding Description
`PlotNFT.melt()` only checks `self.pooling` before allowing the melt spend to proceed: [1](#0-0) 

It does not check the wallet's own `plotnft2_store` for any unclaimed `PoolReward` coins. `PlotNFT2Wallet.melt_plotnft()` similarly performs no such check before building and pushing the melt spend bundle: [2](#0-1) 

Reward coins farmed to a PlotNFT are locked behind a `RewardPuzzle`/`PoolReward` puzzle keyed to the PlotNFT's `singleton_id` (`launcher_id`), using a `SingletonMember` restriction that requires proof of authorization from the live singleton via `SEND_MESSAGE`: [3](#0-2) 

The only spend paths that can move these reward coins — `forward_pool_reward()` (while pooling) and `claim_pool_rewards()` (while self-custody) — both require `self.singleton_action_spend(...)`, i.e., a spend of the still-existing PlotNFT singleton coin: [4](#0-3) [5](#0-4) 

Once the singleton coin is melted (its lineage terminated, per the `melt()` spend which creates no successor singleton coin), there is no longer a live PlotNFT coin capable of producing the `SEND_MESSAGE` proof that `claim_pool_reward_dpuz`/`RewardPuzzle.solve()` requires. Any `PoolReward` coins recorded in `plotnft2_store` (via `coin_added()`'s `add_pool_reward` path) but not yet forwarded/claimed at melt time become permanently unspendable — the funds are locked at the `p2_singleton_puzzle_hash` forever, and there is no owner-callable sweep/recovery function anywhere in `plotnft_drivers.py` or `plotnft_wallet.py` to reclaim them. [6](#0-5) 

This is directly analogous to the referenced M-18 finding: an irreversible state transition (there, "shelter" enactment; here, singleton melt) that the user/owner can trigger, which severs the mechanism's ability to claim already-accrued-but-unclaimed rewards, with no sweep path to recover the stranded value.

### Impact Explanation
Any XCH value sitting in unclaimed pool-reward coins for a PlotNFT at the moment of melt is permanently and irrecoverably lost — this is a direct, concrete loss of user funds (block rewards), not merely lost future yield. Given block rewards can be substantial (`POOL_REWARD_AMOUNT` in tests is 1.75 XCH per block), a user who forgets to claim rewards before melting, or races a `claim_rewards`/`forward_pool_reward` transaction against a `melt_plotnft` transaction, can strand real value with no recovery path.

### Likelihood Explanation
This requires no privileged or malicious actor — an ordinary PlotNFT owner triggering `melt_plotnft` (e.g., via `chia plotnft` CLI or wallet RPC `melt`) is sufficient. The scenario is realistic: a user in self-custody with pending unclaimed rewards (as demonstrated by `test_plotnft_self_custody_claim`, which shows rewards can accumulate and sit unclaimed prior to being explicitly claimed) could melt the PlotNFT without first calling `claim_rewards`, or could race the two transactions. Since `melt()`'s only precondition is `not self.pooling`, nothing in the code path prevents this.

### Recommendation
Before allowing `PlotNFT.melt()` / `PlotNFT2Wallet.melt_plotnft()` to proceed, check `plotnft2_store.get_pool_rewards(plotnft_id=...)` for any outstanding unclaimed rewards and reject the melt (or require the caller to claim them atomically as part of the same transaction) if any exist. Consider also adding a recovery/sweep mechanism for reward coins whose singleton has already been melted, in case a race condition or a missed check allows the loss to occur regardless.

### Proof of Concept
1. Create a PlotNFT2 wallet and let it accumulate reward coins while self-custody (as in `test_plotnft_self_custody_claim`, which farms a `PoolReward` to the plotnft's `p2_singleton_puzzle_hash`): [7](#0-6) 
2. Instead of calling `claim_pool_rewards`, call `plotnft.melt(...)` (or `PlotNFT2Wallet.melt_plotnft()`), which only requires `not self.pooling`: [8](#0-7) 
3. After the melt spend confirms, the PlotNFT singleton coin no longer exists. Attempting to build a `claim_pool_rewards` spend for the previously farmed `PoolReward` coin is impossible because it requires `self.singleton_action_spend(...)` on a coin that has been melted — the reward coin at `p2_singleton_puzzle_hash` remains permanently unspent and unspendable, with no code path anywhere in the repo to sweep it.

class RewardPuzzle:

        self,
        *,
        action_scope: WalletActionScope,
        fee: uint64 = uint64(0),
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> None:
        plotnft = await self.get_current_plotnft()
        fee_hook = CreateCoinAnnouncement(msg=b"", coin_id=plotnft.coin.name())
        coin_spends = plotnft.melt(extra_conditions=(fee_hook, *extra_conditions))
        if fee > 0:
            await self.xch_wallet.create_tandem_xch_tx(

                extra_conditions=(fee_hook.corresponding_assertion(),),

                    wallet_id=self.id(),

                    fee=fee,

                    additions=[],
