### Title
Instantaneous stake/claim/unstake sandwiching `donateRewards`/`queueNewRewards` allows theft of rewards without time-weighted exposure - (File: rewards/BribeRewardPool.sol / rewards/BaseRewardPoolV2.sol)

### Summary
`BribeRewardPool` (via `BaseRewardPoolV2`) distributes rewards using a purely balance-weighted `rewardPerTokenStored` accumulator with no time-weighting, cooldown, or minimum staking duration. An attacker can front-run a `donateRewards`/`queueNewRewards` call by staking (via `stakeFor`, reachable from MasterMagpie's public `deposit`/`vote` entrypoints), letting the reward distribution increase `rewardPerTokenStored`, and immediately back-running with `withdrawFor(..., claim=true)` to capture a full pro-rata share of the newly injected reward despite zero time-at-risk.

### Finding Description
`_provisionReward` (rewards/BaseRewardPoolV2.sol:290-314) increases `rewardInfo.rewardPerTokenStored` by `_amountReward * 10**decimals / totalStaked()` at the moment of the donation/queue call, with no snapshotting delay or vesting period. `_earned`/`earned` (rewards/BaseRewardPoolV2.sol:316-321, 177-184) compute a user's owed reward strictly as `balanceOf(_account) * (rewardPerToken - userRewardPerTokenPaid)`, i.e., purely a function of the account's *current* balance at the time `rewardPerTokenStored` last changed — there is no requirement that the balance existed prior to the reward injection.

`stakeFor` (rewards/BribeRewardPool.sol:57-67) and `withdrawFor` (rewards/BribeRewardPool.sol:72-85) are gated `onlyOperator`, but the operator is MasterMagpie, whose public `deposit`/`vote`-driven entrypoints call these on behalf of any unprivileged EOA that owns the staking token / voting power. `donateRewards` (rewards/BaseRewardPoolV2.sol:255-260) is fully permissionless (only requires `isRewardToken[_rewardToken]`), so an attacker or an unrelated third party's donation can be sandwiched with a single-block or single-transaction sequence:

1. Attacker sees a pending/mempool `donateRewards`/`queueNewRewards` transaction.
2. Attacker calls `deposit`/`vote` on MasterMagpie/WombatBribeManager → triggers `stakeFor(attacker, amount)`, which invokes `updateRewards` and records `userRewardPerTokenPaid[token][attacker] = rewardPerToken(token)` (pre-donation value).
3. Donation transaction executes, increasing `rewardPerTokenStored`.
4. Attacker calls `withdrawFor(attacker, amount, claim=true)` (via MasterMagpie's withdraw entrypoint) in the same block or immediately after — `updateRewards` recomputes `_earned` using the attacker's full balance against the *new* `rewardPerTokenStored`, crediting the attacker the full pro-rata reward for that donation, then `_getReward` transfers it out immediately.

No modifier, reentrancy guard, or economic check prevents this: `updateRewards`/`updateReward` only refresh accounting, they do not check time-of-stake. Existing long-term stakers who were present the entire accrual period suffer dilution because their claim is spread evenly across `totalSupply`, including the attacker's newly and briefly added balance.

### Impact Explanation
This results in a direct transfer of value from legitimate long-term stakers to the attacker: bonus/bribe rewards intended to accrue proportional to time-weighted participation are instead captured disproportionately by a flash staker with zero time-at-risk, diluting/stealing yield from other depositors. This matches Immunefi's "theft of unclaimed yield" impact class.

### Likelihood Explanation
Feasibility is high: the attacker needs only enough of the staking token (or voting power) to call the public deposit/vote entrypoint, and the ability to front-run/back-run a donation transaction (mempool visibility or same-block bundling via a private relay). No special permissions are required. This is repeatable for every `donateRewards`/`queueNewRewards` call and scales with the attacker's capital, and `donateRewards` itself being permissionless means an attacker could even self-fund the donation as part of the same bundle if the amount is smaller than the reward they'd otherwise miss from other depositors' larger existing balances (i.e., pure dilution of pre-existing stakers' pending rewards without needing anyone else to donate).

### Recommendation
Introduce a time-weighting or minimum-holding-period mechanism before staked balance becomes eligible for newly queued rewards, e.g.:
- Snapshot `rewardPerTokenStored` at time of stake and only allow eligibility for rewards queued after a minimum delay (e.g., only rewards accrued in future accounting periods, not the one active at deposit block).
- Enforce a minimum lock/holding period between `stakeFor` and `withdrawFor` for the same account (e.g., disallow withdraw in the same block as deposit, or require N blocks/time elapsed).
- Alternatively, move to a streaming/linear-vesting reward-rate model (rewardRate over duration, as in classic `StakingRewards`) instead of instantaneous `rewardPerTokenStored` bumps, so newly staked balance cannot capture rewards for time it wasn't staked.

### Proof of Concept
Hardhat test plan:
1. Deploy `BribeRewardPool`/`BaseRewardPoolV2` with a mock `MasterMagpie` operator that exposes simple `deposit`/`withdraw` wrappers calling `stakeFor`/`withdrawFor`.
2. Have "LongTermStaker" call `deposit(1000)` and hold across multiple blocks.
3. Have "Attacker" call `deposit(1000)` in the block immediately preceding a `donateRewards(10000, rewardToken)` call (front-run).
4. Execute `donateRewards(10000, rewardToken)`.
5. Have "Attacker" immediately call `withdraw(1000, claim=true)` (back-run, same or next block).
6. Assert: Attacker's realized `RewardPaid` amount ≈ `10000 * 1000/2000 = 5000` (half the donation) despite having zero prior time-weighted exposure, equal to LongTermStaker's earned share for the same nominal balance held for the entire period — demonstrating rewards are balance-weighted only, not time-weighted, and that instantaneous stake captures full pro-rata share of a single donation event.

    modifier updateRewards(address _account, address[] memory _rewards) {
        uint256 length = _rewards.length;
        uint256 userShare = balanceOf(_account);
        
        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = _rewards[index];
            // if a reward stopped queuing, no need to recalculate to save gas fee
            if (userRewardPerTokenPaid[rewardToken][_account] == rewardPerToken(rewardToken))
                continue;
            userRewards[rewardToken][_account] = _earned(_account, rewardToken, userShare);
            userRewardPerTokenPaid[rewardToken][_account] = rewardPerToken(rewardToken);
        }
        _;
    }    
```

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }

    function _earned(address _account, address _rewardToken, uint256 _userShare) internal view returns (uint256) {
        return ((_userShare *
                (rewardPerToken(_rewardToken) -
                    userRewardPerTokenPaid[_rewardToken][_account])) /
                10**stakingTokenDecimals) + userRewards[_rewardToken][_account];
    }
```
