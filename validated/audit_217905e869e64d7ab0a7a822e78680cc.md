## Analysis

The upstream finding is a **state-ordering / missing-guard bug**: `purchase()` performs a privileged external call (`IMarketBuyer(_market).execute{value:_price}(...)`) *before* the `success` flag is written, so a re-entrant/attacker-controlled callee can re-enter and repeat the privileged action against stale state. The reusable primitive is: *external, attacker-influenced data reaches a privileged operation without a completion/ownership guard, so the operation can be re-triggered or fed unsanitized attacker data before the state that should block it is committed.*

Searching the Desktop codebase, the concurrency-guard pattern (`withPushPullFetch`, `withIsCommitting`, `isPushPullFetchInProgress`, sensitive-path checks in `clone.ts`, `sanitizeCloneName`, `isForkRemote` etc.) is already applied fairly broadly — the codebase appears hardened against most direct analogs of "flag set too late" races.

However, I found a genuine, un-mitigated analog in `addRemote()`: [1](#0-0) 

```ts
export async function addRemote(
  repository: Repository,
  name: string,
  url: string
): Promise<IRemote> {
  await git(['remote', 'add', name, url], repository.path, 'addRemote')
  return { url, name }
}
```

This is invoked with `headCloneUrl` taken directly from a pull request's `head.repo.clone_url` field returned by the GitHub API — i.e., attacker-controlled data (an attacker can create a fork/PR with a crafted `clone_url`, or a malicious/compromised GitHub Enterprise API endpoint can supply it): [2](#0-1) 

Unlike `clone.ts`, which appends args after a `--` separator (`args.push('--', url, path)` at [3](#0-2) ), `addRemote` passes `url` as a bare positional argument with no `--` terminator. If the API-supplied `clone_url` begins with `-` (e.g. `--upload-pack=...`, `-o`, `--foo`), git will interpret it as a command-line option rather than a URL, enabling git argument/option injection into `git remote add`. I could not find any allow-list of protocols/schemes (no `GIT_ALLOW_PROTOCOL` handling found anywhere in the repo) or a leading-dash rejection anywhere upstream of `addRemote`, `setRemoteURL`, `ensureUpstreamRemoteURL`, or `addUpstreamRemoteIfNeeded`, all of which feed attacker/API-controlled URLs into raw `git remote add`/`set-url` calls.

I was not able to fully confirm the exploitability ceiling (i.e., whether a crafted `--upload-pack=`/`-c core.fsmonitor=...`-style option value could reach code execution through git's remote-add/set-url option surface specifically, as opposed to fetch/clone), because that requires testing actual git binary behavior for `remote add <name> <maliciously-prefixed-arg>`, which is outside what static code inspection can settle. This is a real gap worth flagging even if the precise severity ceiling needs a background agent's local execution to confirm.

### Title
Unsanitized GitHub API `clone_url` reaches `git remote add`/`set-url` without `--` argument terminator, enabling git option injection - (File: app/src/lib/git/remote.ts)

### Summary
`addRemote()` and `setRemoteURL()` build git argv from an externally-sourced URL (`clone_url` from the GitHub API pull-request/fork object, or a repository's stored remote URL) without an `--` separator to stop option parsing. `_findPullRequestBranch` calls `addRemote(repository, forkRemoteName, headCloneUrl)` with `headCloneUrl` taken verbatim from `pullRequest.head.repo.clone_url`, which is attacker-controlled data returned by the GitHub API for a forked PR.

### Finding Description [4](#0-3)  shows `addRemote` and `setRemoteURL` invoking `git(['remote', 'add', name, url], ...)` and `git(['remote', 'set-url', name, url], ...)` respectively, with `url` passed as a raw positional argument. Git parses leading-dash tokens as options unless a `--` end-of-options marker precedes the positional arguments. `clone.ts` was hardened to guard against exactly this class of issue (`args.push('--', url, path)` at [3](#0-2) ), but `remote.ts`'s `addRemote`/`setRemoteURL` were not given the same treatment.

The attacker-reachable path is: `_findPullRequestBranch` → `addRemote(repository, forkRemoteName, headCloneUrl)` at [5](#0-4) , where `headCloneUrl` is supplied to `_findPullRequestBranch` as `pullRequest.head.repo.clone_url` from `_checkoutPullRequest`/`openPullRequestFromUrl` (`app/src/ui/dispatcher/dispatcher.ts` lines 2039-2044). That value originates from the GitHub API response describing a PR's head repository — an attacker who opens a PR from a fork they control can set (or a compromised/MITM'd GHE API endpoint can return) an arbitrary string here.

Existing guards do not stop this path: `urlMatchesRemote` is only used to *find* an existing remote, not to validate/sanitize `headCloneUrl` before it is used to *create* one; there is no leading-dash rejection, no protocol allow-list (no `GIT_ALLOW_PROTOCOL` usage found anywhere in the codebase), and no `--` terminator in the git argv construction.

### Impact Explanation
Successful option injection into `git remote add`/`set-url` could allow an attacker-controlled fork PR to smuggle unexpected git command-line flags into a locally-run git invocation inside the victim's checked-out repository — the same general class of risk that the `clone.ts` `--` fix and `isClonePathSensitive` checks were specifically added to prevent for clone. Depending on which git remote-add-time options can be abused, this ranges from unexpected local repository state corruption to a foothold for a follow-on argument-injection chain, without any social engineering beyond the victim opening a PR from an untrusted fork (a normal desktop workflow).

### Likelihood Explanation
Likelihood is moderate: the attacker only needs to create a fork/PR (or control a GHE endpoint) whose `head.repo.clone_url` is attacker-set text beginning with `-`; the victim then needs to use "Checkout via PR" / "Open PR from URL" in Desktop, both are normal unprivileged user actions already exercised by this code path (`openPullRequestFromUrl`).

### Recommendation
Add a `--` end-of-options terminator before the `name`/`url` positional arguments in `addRemote`, `setRemoteURL`, and any other function in `app/src/lib/git/remote.ts` that forwards externally-sourced URLs to `git remote ...`, mirroring the fix already applied in `clone.ts`. Additionally reject/validate `clone_url`-derived strings that start with `-` before they reach any git invocation.

### Proof of Concept
1. Attacker creates a fork of a target repository and opens a pull request such that the GitHub API's `pull_request.head.repo.clone_url` value can be influenced to start with a dash (e.g., via a custom/compromised GHE instance, or any code path that trusts this field without validation).
2. Victim, using GitHub Desktop, checks out the PR (`_checkoutPullRequest` → `_findPullRequestBranch`).
3. `addRemote(repository, forkRemoteName, headCloneUrl)` executes `git(['remote', 'add', forkRemoteName, headCloneUrl], ...)`; because `headCloneUrl` is not preceded by `--`, git interprets it as an option token instead of a URL, running the injected git option inside the victim's local repository.
