## Title
`IntrinsicIntents._fillSameChain`: unmatched `inputs`/`outputs` array lengths permanently strand escrowed principal - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`placeOrder` never enforces that `order.inputs.length == order.output.assets.length`. `_fillSameChain` iterates only over `output.assets.length` and indexes `order.inputs[i]` to compute the escrow release, so any input beyond the output array's length is never withdrawn on fill, yet the order is marked `_filled`, permanently blocking the only other exit path (`cancelOrder`). This mirrors the Sublime `LenderPool` bug class: an accounting loop keyed on the wrong bound (`totalSupply` in the report; `output.assets.length` here) silently diverges from the actual escrowed principal, leaving funds unreachable.

### Finding Description
`placeOrder` (`evm/src/apps/IntentGatewayV2.sol:162-163`) only checks `order.inputs.length == 0`; it never checks `order.inputs.length` against `order.output.assets.length`. Escrow is recorded per input index independently of the output count: [1](#0-0) [2](#0-1) 

In `_fillSameChain`, the fill/escrow-release loop is bounded by `outputsLen = order.output.assets.length`, but inside the loop it reads `order.inputs[i]` to compute the proportional/full escrow to release: [3](#0-2) [4](#0-3) 

If `order.inputs.length > order.output.assets.length`, only indices `0..outputsLen-1` are ever placed into `escrowedInputs` and passed to `_withdraw`. The extra escrowed tokens at `_orders[commitment][token]` for `i >= outputsLen` are never decremented or transferred out.

On a full fill, `_fillSameChain` sets `_filled[commitment] = msg.sender` before the loop and calls `_withdraw(..., finalize=true)`, which persists the filled marker: [5](#0-4) 

Once `_filled[commitment] != address(0)`, the top-level `cancelOrder` unconditionally reverts with `Filled()` for that commitment (per the documented contract rule), so the leftover escrow for the un-indexed inputs can never be recovered by `_cancelSameChain` either — there is no other function that reads `_orders[commitment][token]` for a filled order.

This is structurally identical to H-01: the withdrawal/release loop's bound (`totalSupply[id]` there, `output.assets.length` here) is not kept 1:1 with the actual escrowed principal set (`borrowLimit`-adjusted principal there, per-input escrow here), so the release calculation silently omits part of the real balance, and the funds become unreachable through any code path.

### Impact Explanation
Escrowed input tokens beyond the output array's length are permanently locked in the `IntentGateway` contract — neither the user (blocked by `Filled()`) nor the solver/filler (never included in `escrowedInputs`) can retrieve them. This is a direct loss-of-funds condition matching the bounty's "stealing or loss of funds" and "logic attacks" categories, reachable by any unprivileged user simply by constructing an order with more inputs than outputs and having it filled (fully, by any solver, which is normal permissionless behavior, not a malicious-peer requirement).

### Likelihood Explanation
`placeOrder` performs no validation that `inputs.length == output.assets.length`; both are ordinary `TokenInfo[]` arrays supplied entirely by the order-placing user. Any user (accidentally or via a malformed SDK client) can create such an order, and any solver calling `fillOrder`/`_fillSameChain` to fully satisfy the declared outputs will trigger the locking behavior without any special privileges, malicious relayer, or governance action — a normal placeOrder → fillOrder sequence suffices.

### Recommendation
Enforce `order.inputs.length == order.output.assets.length` in `placeOrder` (and any other order-construction/validation path, e.g. EIP-712 order hashing/verification), or change the escrow-release accounting in `_fillSameChain` to iterate independently over all `order.inputs` (e.g., release input `i` proportional to overall output fill progress rather than assuming a strict 1:1 index correspondence with `order.output.assets[i]`). At minimum, add a length-mismatch guard that reverts with `InvalidInput()` before escrow is created in `placeOrder`.

### Proof of Concept
1. Call `placeOrder` with `order.inputs` containing 2 `TokenInfo` entries (e.g., 1000 USDC and 1000 DAI) but `order.output.assets` containing only 1 entry (e.g., 900 USDT owed to the beneficiary). `placeOrder` accepts this because only `order.inputs.length == 0` is checked [1](#0-0) ; both inputs are escrowed under `_orders[commitment][token]` [2](#0-1) .
2. A solver calls `fillOrder` and fully satisfies the single output (900 USDT). `_fillSameChain`'s loop runs only for `i = 0` (`outputsLen = 1`), releasing only the first input (USDC) to the solver via `escrowedInputs[0]`; the second input (DAI) is never referenced [6](#0-5) .
3. Because the fill is full, `_filled[commitment]` is set and `isFullyFilled` finalizes the withdrawal [5](#0-4) ; `_orders[commitment][DAI]` still holds the escrowed 1000 DAI.
4. Calling `cancelOrder` for this commitment now reverts with `Filled()` per the documented gate check [7](#0-6) , and no other function exposes `_orders[commitment][DAI]` for withdrawal — the 1000 DAI is permanently stuck in the `IntentGatewayV2` contract.

function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
    bytes32 commitment = keccak256(abi.encode(order));
    if (_filled[commitment] != address(0)) revert Filled();

    bool isSameChain = keccak256(order.source) == keccak256(order.destination);
    if (isSameChain) {
        _cancelSameChain(order, commitment);
    } else if (currentChain == keccak256(order.source)) {
        _cancelFromSource(order, options, commitment);
    } else if (currentChain == keccak256(order.destination)) {
        _cancelFromDest(order, options, commitment);
    } else {
        revert WrongChain();
    }
}
