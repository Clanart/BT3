### Title
Manipulable spot price via `womMWomPool` combined with zero-slippage buyback swap in `smartConvert`/`_convertFor` allows extraction of mWOM at attacker-favorable rates - ([File: wombat/SmartWomConvert.sol])

### Summary
`smartConvert` decides whether to trigger a "buyback" swap and how large it is based on `currentRatio()` and `maxSwapAmount()`, both of which are derived from live, swappable state of `womMWomPool` (spot price and the pool's own `cash`/`liability`). The actual buyback swap in `_convertFor` is then executed with a hardcoded `0` minimum output, so a caller who first perturbs the pool's price/imbalance with a flash-loaned swap can force `smartConvert` to route through the buyback branch and execute it at an attacker-favorable price, extracting mWOM from the pool's reserves beyond what the WOM they deposited/converted actually justifies.

### Finding Description
`smartConvert` is `external` with **no access control** beyond the informal comment "should mainly used by wombat staking" [1](#0-0) , so any unprivileged address can call it directly.

Inside `smartConvert`, the buyback decision is driven purely by a spot-price read from `womMWomPool`: [2](#0-1) 
and the swap size cap `maxSwapAmount()` is derived from the same pool's live `cash`/`liability` accounting: [3](#0-2) 

Both of these are read at call time with no TWAP/oracle smoothing, so they can be pushed in the attacker's favor within the same transaction (e.g., via a flash-loaned swap on `womMWomPool` that dumps mWOM into the pool, depressing `mWomToWom`/`currentRatio()` below `buybackThreshold` and simultaneously shifting the WOM asset's `cash`/`liability` to enlarge `maxSwapAmount()`): [4](#0-3) 

Crucially, the actual buyback swap executed in `_convertFor` has **no slippage protection** — `minAmountOut` is hardcoded to `0`: [5](#0-4) 

So once the attacker manipulates the pool, `smartConvert`'s buyback swap executes at the manipulated (favorable) price, yielding more mWOM out of the pool's reserves per unit of WOM than the pool's unperturbed price would give, while the "backing" portion (`convertAmount`) still goes through the fair 1:1 `IMWom(mWom).deposit()` path. The mWOM obtained is transferred directly to `msg.sender` (mode `0`) or deposited/locked on their behalf (modes `1`/`2`): [6](#0-5) 

No modifier (`nonReentrant`, `onlyOperator`, etc.) restricts who can call `smartConvert` or bounds the acceptable execution price of the internal buyback swap, so nothing in the existing code prevents this price-manipulation-then-extract pattern.

### Impact Explanation
An attacker can extract mWOM from `womMWomPool`'s reserves at a rate more favorable than fair value, draining value from that pool's liquidity providers and reducing the amount of real WOM backing available to redeem mWOM at par elsewhere in the protocol. Repeated over time (or executed with large flash-loan capital), this degrades the WOM/mWOM peg and pool solvency, matching an Immunefi "protocol insolvency" / "theft of funds" impact class, since the extraction is a direct wealth transfer out of pooled reserves rather than newly, fairly minted backing.

### Likelihood Explanation
Exploitation requires: (1) capital or a flash loan to swap on `womMWomPool` to push `currentRatio()` below `buybackThreshold` and shift the relevant `cash`/`liability` state so `maxSwapAmount()` is non-trivial, and (2) holding WOM to pass into `smartConvert`. Both are attacker-controlled via public swap functions and flash loans; no privileged role is needed. The actual net profitability depends on Wombat's stableswap slippage/fee curve absorbing some of the manipulation cost, but the code path itself provides zero protection (no minimum-output check, no TWAP), so profitability is purely a function of pool depth/fees rather than any protocol safeguard — a solvable economic condition for a well-capitalized attacker, and repeatable across multiple blocks/transactions.

### Recommendation
- Add a caller-supplied and enforced minimum output (`_minRec`) for the internal buyback swap in `_convertFor` instead of hardcoding `0`.
- Base `currentRatio()`/buyback eligibility on a manipulation-resistant price source (TWAP or oracle) rather than an instantaneous `getAmountOut` call against a swappable pool.
- Consider restricting `smartConvert` to trusted callers (e.g., `WombatStaking`) if it is not intended for general use, consistent with the code comment.

### Proof of Concept
Foundry fork test plan:
1. Fork mainnet/arbitrum at a block where `SmartWomConvert`, `womMWomPool`, and `womAsset` are deployed.
2. Record baseline `currentRatio()` and `maxSwapAmount()`.
3. As the attacker contract: flash-loan mWOM (or use existing capital) and swap mWOM→WOM on `womMWomPool` via the router to push `currentRatio()` below `buybackThreshold` and inflate `maxSwapAmount()`.
4. Call `smartConvert(_amountIn, 0)` with attacker-held WOM; capture `obtainedmWomAmount`.
5. Reverse the initial swap (WOM→mWOM) to restore pool price and repay the flash loan.
6. Assert `obtainedmWomAmount` (mWOM received) valued in WOM at the pre-manipulation `currentRatio()` exceeds `_amountIn` (i.e., attacker extracted more value than deposited), and that `womMWomPool`'s mWOM reserves decreased by more than the fair-value equivalent of `_amountIn`, demonstrating extraction in excess of genuine 1:1 backing.

```text
    // should mainly used by wombat staking upon sending wom
    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
```
