### Title
`SendMoveToVaultTx` accepts a caller-declared `deposit_outpoint` that is never checked against the actual input the submitted transaction spends - ([File: core/src/rpc/aggregator.rs])

### Summary
`ClementineAggregator::SendMoveToVaultTx` lets a caller submit an arbitrary raw Bitcoin transaction plus a `deposit_outpoint` value. The handler validates the transaction's *shape* (input/output count) and its *output* script-pubkeys/amounts, but never checks that `movetx.input[0].previous_output` actually equals the supplied `deposit_outpoint`. The unchecked, caller-controlled `deposit_outpoint` is then persisted as the authoritative binding between "this deposit" and "this move-to-vault transaction" in `TxMetadata`, exactly mirroring the HackerOne report's pattern of an attacker-controlled field being trusted downstream without validating it against the real, underlying object it is supposed to describe.

### Finding Description
In `send_move_to_vault_tx`: [1](#0-0) 

the code deserializes the caller-supplied `raw_tx` and separately trusts the caller-supplied `deposit_outpoint`. It checks:
- `movetx.input.len() == 1 && movetx.output.len() == 2`
- `movetx.output[0].value == bridge_amount && movetx.output[1].value == 0`
- `movetx.output[0].script_pubkey == bridge_script_pubkey (nofn + security council)`
- `movetx.output[1].script_pubkey == anchor_output(...)` [2](#0-1) 

None of these checks tie `movetx.input[0].previous_output` to the `deposit_outpoint` argument. The `deposit_outpoint` is used solely as bookkeeping metadata when the tx is queued for broadcast: [3](#0-2) 

Because the two values are never cross-checked, a caller can submit a transaction that is a validly shaped/valid move-to-vault tx (structurally identical to what verifiers presign for some deposit A) while declaring an arbitrary, unrelated `deposit_outpoint` value B in the request. The aggregator will accept this and record `movetx.compute_txid()` as "the move-to-vault txid" for deposit outpoint B in its internal `TxMetadata`/`tx_sender` bookkeeping, even though the transaction does not actually spend deposit B's UTXO.

This breaks the binding the rules describe as "a deposit presigned versus a deposit minted once": the equality that should hold —

```
deposit_outpoint (declared in request) == movetx.input[0].previous_output (actual spent deposit UTXO)
```

— is never enforced, so the aggregator's own record of which move transaction belongs to which deposit can be poisoned by any caller who can reach this endpoint with a syntactically valid movetx.

### Impact Explanation
This corrupts the aggregator's canonical deposit → move-to-vault-transaction association used by downstream automation (`tx_sender`/state-manager bookkeeping keyed on `TxMetadata.deposit_outpoint`). If a caller substitutes an unrelated, real deposit's outpoint for their own transaction's declared metadata, the system's internal tracking for that other deposit becomes inconsistent with what is actually on-chain, which can misdirect the automated round/kickoff scheduling and reimbursement bookkeeping tied to that deposit outpoint — i.e., a misattributed record analogous to "an operator credited versus the party that paid" or "a deposit presigned versus a deposit minted once," per the specified impact categories.

### Likelihood Explanation
The endpoint is intended to be called by the "clementine-backend service" as part of the ordinary user-facing deposit flow (per the proto comment), not gated behind verifier/operator/security-council roles the way `ClementineVerifier`/`ClementineOperator` internal RPCs are (those use the `OnlyAggregatorAndSelf` interceptor). Reaching this RPC therefore does not clearly require a privileged bridge role, and constructing a request with mismatched `deposit_outpoint`/`raw_tx` requires no special capability beyond having a validly-signed movetx (e.g., from one's own legitimate deposit) and knowledge of another deposit's outpoint (public on-chain data).

### Recommendation
In `send_move_to_vault_tx`, explicitly verify `movetx.input[0].previous_output == deposit_outpoint` before accepting the request, in addition to the existing output-shape/value/script-pubkey checks.

### Proof of Concept
1. Complete a legitimate deposit flow to obtain a validly-signed move-to-vault transaction `movetx_A` for `deposit_outpoint_A` (own funds).
2. Identify another party's real deposit outpoint `deposit_outpoint_B` (public on-chain data).
3. Call `ClementineAggregator.SendMoveToVaultTx` with `raw_tx = movetx_A` (unchanged) but `deposit_outpoint = deposit_outpoint_B`.
4. Observe that `send_move_to_vault_tx` passes all its checks (input/output counts, output values, output script-pubkeys) — none of which reference the input previous_output — and inserts `TxMetadata { deposit_outpoint: Some(deposit_outpoint_B), tx_type: MoveToVault, .. }` bound to `movetx_A`'s txid, even though `movetx_A` does not spend `deposit_outpoint_B`.
