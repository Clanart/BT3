### Title
Deterministic cached FROST preprocess is reused across `generated_key_pair` calls, enabling nonce reuse and validator key recovery — (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The zAuction bug class — an updated reference taking effect immediately while artifacts issued under the old version remain valid, leaving two "versions" live in parallel — maps onto Serai's `DkgConfirmer` signing protocol. The coordinator deterministically regenerates the same FROST nonces from a DB-cached seed keyed only by `(b"DkgConfirmer", attempt)`, and `generated_key_pair` unconditionally overwrites the stored `KeyPair` for an attempt. Two calls with distinct key pairs produce two signature shares under identical nonces for different messages, allowing recovery of the validator's MuSig secret key.

### Finding Description
`SigningProtocol::preprocess_internal` caches a 32-byte seed under `CachedPreprocesses` keyed by `self.context`, and `share_internal` calls `preprocess_internal` again, rebuilding the *same* machine via `AlgorithmSignMachine::from_cache` every time it is invoked for a context. [1](#0-0)  `from_cache` re-derives nonces deterministically from the seed via `seeded_preprocess` (`ChaCha20Rng::from_seed(*seed.0)`), so every call for the same `(b"DkgConfirmer", attempt)` context reuses identical nonces `(d, e)`. [2](#0-1) 

`DkgConfirmer::share` signs `set_keys_message(set, removed, key_pair)` where `key_pair` is caller-supplied, and `DkgConfirmer::complete` calls `share_internal` again — a second signature generation with the same cached nonces. [3](#0-2)  In `generated_key_pair`, `DkgKeyPair::set` overwrites any previously stored pair without checking for an existing value, so nothing prevents a second, different `key_pair` being signed for the same attempt/context. [4](#0-3) 

The FROST spec and `CachedPreprocess` docs state reuse of a preprocess enables recovery of the private key share — the seed is never consumed/invalidated, and the same seed deterministically produces the same nonces. [5](#0-4) [6](#0-5) 

### Impact Explanation
A FROST signature share is `z_i = d_i + (e_i * rho_i) + lambda_i * s_i * c` (plus the algorithm's nonce combination). If the same `(d_i, e_i)` is used to sign two different messages, the resulting shares differ only in the challenge/binding terms, and two shares with the same nonce but different effective challenges let any observer solve for `lambda_i * s_i` — the validator's MuSig secret share over Ristretto. Since both `DkgConfirmed` shares and `set_keys` material are published on the public tributary, anyone observing two shares under identical commitments recovers the key share, compromising the validator set's signing key. This is secret key material recovery — a Critical/High impact under the rules. [7](#0-6) 

### Likelihood Explanation
Triggering requires `generated_key_pair` (or `share`/`complete`) to run twice for the same attempt with different `key_pair`s — e.g., a processor restart mid-confirmation producing a divergent key pair, or `share()` being invoked once with one key pair and `complete()` resolving a different stored pair. `DkgKeyPair::set` and `KeyToDkgAttempt::set` perform unconditional overwrites, so the "old version" remains signable in parallel with the new one — exactly the zAuction class where the stale reference still accepts calls after an update. The encryption key for the cached seed is derived only from `context || private_key`, so nothing binds the seed to a specific key pair or participant set. [8](#0-7) [9](#0-8) 

Caveat: I could not fully trace whether the processor can actually emit two distinct `key_pair`s for one attempt in normal operation; the vulnerability is that nothing at the signing layer enforces single-use, so any such divergence silently produces nonce reuse rather than an error.

### Recommendation
- Make the cached preprocess single-use: delete or tombstone `CachedPreprocesses` for a context when `share_internal` first consumes it, and have `complete` reuse the machine/state produced by `share` rather than re-deriving it.
- Alternatively, bind the cached seed to the signed message (e.g., key `CachedPreprocesses` by `(context, msg_hash)`) and refuse to sign a different message under a context whose seed was already used.
- Have `generated_key_pair` reject a second `key_pair` for an attempt once `DkgKeyPair` is set, instead of overwriting. [10](#0-9)

```rust
// Conceptual, against coordinator internals:
// Attempt N completes the DKG; processor emits key_pair_A.
generated_key_pair(txn, key, spec, &key_pair_a, attempt)?;
// -> DkgKeyPair::set(..., key_pair_a); share() signs set_keys_message(..., A)
//    with nonces (d, e) derived from CachedPreprocesses[("DkgConfirmer", attempt)].

// Processor restarts / re-derives and emits key_pair_B for the same attempt.
generated_key_pair(txn, key, spec, &key_pair_b, attempt)?;
// -> DkgKeyPair is overwritten; share_internal -> preprocess_internal rebuilds the
//    machine from_cache with the SAME seed => same nonces (d, e).
//    A second share for set_keys_message(..., B) is produced and published.

// An observer on the tributary sees two shares z1, z2 with identical nonce
// commitments but different challenges:
//   z1 - z2 = lambda_i * s_i * (c1 - c2)   (+ known offset/binding terms)
//   => s_i = (z1 - z2) / (lambda_i * (c1 - c2))
// The validator's MuSig secret share is recovered from public data.
```
The deterministic reuse is guaranteed because `from_cache`/`seeded_preprocess` derives `Commitments` purely from the cached seed, and `share_internal` invokes that path on every `share`/`complete` call for the same context. [11](#0-10) [12](#0-11)

```rust
  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))
  }
```

```rust
  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
```

```markdown
# Caching

modular-frost supports caching a preprocess. This is done by having all
preprocesses use a seeded RNG. Accordingly, the entire preprocess can be derived
from the RNG seed, making the cache just the seed.

Reusing preprocesses would enable a third-party to recover your private key
share. Accordingly, you MUST not reuse preprocesses. Third-party knowledge of
your preprocess would also enable their recovery of your private key share.
Accordingly, you MUST treat cached preprocesses with the same security as your
private key share.

Since a reused seed will lead to a reused preprocess, seeded RNGs are generally
frowned upon when doing multisignature operations. This isn't an issue as each
new preprocess obtains a fresh seed from the specified RNG. Assuming the
provided RNG isn't generating the same seed multiple times, the only way for
this seeded RNG to fail is if a preprocess is loaded multiple times, which was
already a failure point.
```
