### Title
Same-file-diff line-content matching in `filter_preexisting_from_diff` lets attacker-controlled duplicate lines evade the LLM security reviewer - ([File: plugins/security-guidance/hooks/gitutil.py])

### Summary
`filter_preexisting_from_diff` classifies an added `+` line as "pre-existing" purely by testing whether its `.strip()`ed text is a member of the set of all `-` lines removed anywhere in that file's diff, with no positional or occurrence-count pairing. Because a full-file `Write` rewrite removes and re-adds every line, an attacker who controls the rewritten file's content can duplicate one pre-existing (and therefore "removed") line's exact text at a brand-new location, causing that duplicated line to be silently downgraded to context and hidden from the LLM security reviewer, even though it is a distinct, newly-placed line that the reviewer was supposed to see.

### Finding Description
The function collects `removed_lines` as a `set` of stripped `-` line contents and `added_lines`/`added_lines_set` as stripped `+` line contents [1](#0-0) . It then rewrites the diff: any `+` line whose stripped text is `in removed_lines` is converted to a context line (space-prefixed), and any `-` line whose stripped text is `in added_lines_set` is dropped entirely [2](#0-1) .

This is a pure set-membership test, not a 1:1 line-occurrence pairing. The code's own comment concedes this: "the set lets one removal mask N additions of the same stripped text" [3](#0-2) . Consequently, if a full-file rewrite (as produced when the `Write` tool replaces a file's entire content, per the module docstring's stated purpose [4](#0-3) ) removes an original line L and the new content contains L twice — once at its original semantic position (the legitimate "unchanged" case this filter is designed to hide) and once at a new, attacker-chosen position — both occurrences match the set and both get downgraded to context. The second occurrence is a genuinely new line placed by the attacker/session, but it is hidden from `analyze_code_security`/`agentic_review`, which consume the filtered diff as "truly new code" per the function's docstring.

Exploit flow: an attacker who can influence what Claude writes (e.g., via prompt injection embedded in repository content, an issue/PR description, or other untrusted context that steers a `Write` tool call) crafts a full-file rewrite where a sensitive statement that already exists verbatim somewhere in the file (e.g., a `subprocess.run(cmd, shell=True)` line that is currently safe because `cmd` is hardcoded elsewhere) is duplicated at a new location where the surrounding, still-visible new code makes `cmd` attacker/user-controlled. The duplicated sink line itself gets masked as "pre-existing", so the LLM reviewer's attention is drawn only to the visibly-new supporting lines, degrading the odds that the actual dangerous statement is flagged.

No existing guard mitigates this: there is no positional diff alignment (e.g., using hunk line numbers or a proper LCS/diff match), no per-occurrence counting, and the "backstop" mentioned in the comment (the diff-review prompt's previous-findings recheck, used to avoid re-flagging previously-found issues across turns) does not address a same-turn duplication trick — it only deduplicates already-reported findings, not lines improperly reclassified as context within a single diff pass.

### Impact Explanation
This weakens the Stop-hook / commit-review / push-sweep security review pipeline described in `security_reminder_hook.py`, whose explicit purpose is to review "only code Claude actually changed" and surface concrete vulnerabilities via exit(2) findings [5](#0-4) . By exploiting the imprecise content-only matching, an attacker can cause specific newly-introduced sink/gadget lines to be excluded from the diff sent to the LLM reviewer, reducing detection of injected vulnerable code that a prompt-injection-driven `Write` could otherwise trigger. This is a trust-boundary bypass of a documented safety control (the "LLM reviewer only sees truly new code" invariant), not a direct RCE, but it lowers the reliability of the last line of defense against maliciously-steered code writes.

### Likelihood Explanation
Feasible whenever: (1) the attacker can influence the content Claude writes with the `Write` tool (already an assumed precondition per the audit prompt), and (2) the attacker can predict or read the exact pre-existing text of at least one line in the target file (trivially satisfiable — Claude/the attacker's steering prompt can read the file first). The attack needs no privilege escalation and is fully deterministic/repeatable — the match is exact-string based, so crafting a duplicate is straightforward. The scope is inherently line-level, so it does not hide an entire new function, but does reliably hide a chosen single line (e.g., a sink call) per collision.

### Recommendation
Replace set-membership matching with position-aware / occurrence-count-aware matching: track remaining counts (`Counter`) for removed vs. added stripped lines and only reclassify up to `min(count_removed, count_added)` matches, or better, use a proper diff/LCS alignment (e.g., `difflib.SequenceMatcher`) between the pre-image and post-image content so that only truly unchanged (same-position, same-content) lines are demoted to context. At minimum, cap the masking to one converted `+` line per matching `-` line rather than allowing an unbounded many-to-one match.

### Proof of Concept
Unit/fuzz test in a new test module exercising `filter_preexisting_from_diff` directly:
1. Build a synthetic full-file-rewrite diff for one file where the pre-image has N unique lines (e.g. `import os`, `def f(): pass`, …) and the post-image reproduces all N lines unchanged **plus** one attacker line M whose stripped text is identical to one of the N pre-existing lines (e.g. duplicate `import os` verbatim at a new location, distinguishable via a following sentinel-comment line to track position), giving the diff `-`=N lines, `+`=N+1 lines.
2. Call `filter_preexisting_from_diff([("f.py", diff_text)], cwd, "baseline")`.
3. Assert that the returned diff contains **two** context lines (space-prefixed) matching the duplicated content but the diff `+`/`-` counts show only N genuinely-new lines were expected to remain flagged — i.e., assert the count of lines still marked `+` in the output is less than the actual number of textually-distinct new lines in the post-image (fails, proving the duplicate/attacker line was hidden).
4. Generalize into a property/fuzz test: generate random pre-image line sets, randomly duplicate a subset of removed lines into new positions in the post-image, and assert the invariant "every line whose exact (non-stripped, position-tracked) origin is new must remain marked `+` in the filtered output" — the test should fail against current `filter_preexisting_from_diff`, confirming the vulnerability.

def filter_preexisting_from_diff(diff_files, cwd, baseline_sha):
    """
    Filter out pre-existing content from diff files.
    When a file is fully rewritten (Write tool replaces entire content),
    git shows all lines as removed (-) then re-added (+). This function
    detects such rewrites and strips lines from the + section that also
    appeared in the - section, so the LLM reviewer only sees truly new code.
    """
    if not baseline_sha:
        return diff_files

## How the git baseline works

On each UserPromptSubmit, the plugin runs `git stash create` to get a SHA representing
the current working tree state (HEAD + any uncommitted changes). This SHA is saved to
the session state file. When the Stop hook fires, it runs `git diff <baseline_sha>` to
get only the changes made since that snapshot. After analysis, the baseline is updated
so the next Stop hook iteration only sees new changes.

This means:
- Only code Claude actually changed is reviewed (not pre-existing code)
- Mid-session commits are handled correctly (diff is against the snapshot, not HEAD)
- Each turn only reviews new changes (baseline updates after each stop hook)
