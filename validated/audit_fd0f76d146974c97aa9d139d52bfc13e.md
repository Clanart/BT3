### Title
Emergency withdrawal from MasterMagpie skips BaseRewardPool accounting, leaving phantom reward balances - ([File: rewards/MasterMagpie.sol])

### Summary
`MasterMagpie.emergencyWithdraw()` returns a user's staked tokens but never notifies the associated `BaseRewardPool` rewarder, leaving the rewarder's internal balance/`totalSupply` accounting permanently out of sync with the real staked amount — the same class of bug as the Stargate `emergencyWithdrawToVault()` report, where `allocatedAmt` was not decremented after funds left the contract.

### Finding Description
`emergencyWithdraw()` reduces `user.available`, transfers the staking token back to the caller, and recomputes `user.amount`/`user.rewardDebt` purely in `MasterMagpie`'s own bookkeeping: [1](#0-0) 

Unlike the normal deposit/withdraw flow (`_deposit`/`_withdraw`, `multiclaim*`), which is expected to interact with the pool's `rewarder` (`IBaseRewardPool`) to keep the rewarder's own per-user balance and `totalSupply` in sync with `MasterMagpie`'s `UserInfo.amount`, `emergencyWithdraw()`'s doc comment explicitly says it withdraws "without caring about rewards" and contains no call into `pool.rewarder`. This mirrors the Stargate root cause exactly: principal leaves the contract (`IERC20(pool.stakingToken).safeTransfer(...)`), but a downstream accounting ledger (`BaseRewardPool`'s balance/`totalSupply`, analogous to `allocatedAmt`) is never decremented to reflect that withdrawal.

### Impact Explanation
Because the rewarder never learns that the user's stake was removed, the user's balance recorded in the `BaseRewardPool` remains at its pre-withdrawal (inflated) level while `totalSupply` in the rewarder is likewise never reduced. This produces a persistent, uncorrectable accounting inconsistency in emission math:
- The affected user retains a phantom reward-earning balance in the rewarder despite having already withdrawn their principal via `emergencyWithdraw`, allowing them to keep claiming MGP/vlMGP or auxiliary rewards they are no longer entitled to (theft of unclaimed yield from other stakers).
- Because `totalSupply` in the rewarder stays inflated relative to real staked capital, `rewardPerToken`/`accRewardPerShare` computations understate the true per-share reward rate for all other genuine stakers indefinitely, permanently diluting/freezing yield that should have accrued to them.

This satisfies the "theft or permanent freezing of unclaimed yield" bar.

### Likelihood Explanation
`emergencyWithdraw()` is callable by any user whenever the contract is paused (`whenPaused`) — pausing is a normal operational state (e.g., during upgrades or incident response), not a privileged-only action gate on the caller side; any wallet with an existing stake in a pool can trigger this path once the contract is paused, making the bug reachable without any special/admin privileges on the caller's part.

### Recommendation
In `emergencyWithdraw()`, before or after transferring `availableaAmount` back to the user, call the pool's rewarder (`IBaseRewardPool(pool.rewarder).withdraw(msg.sender, availableaAmount, ...)` or equivalent) to keep the rewarder's per-user balance and `totalSupply` consistent with the amount actually removed from `MasterMagpie`, mirroring the update that occurs in the normal `_withdraw` path.

### Proof of Concept
1. User deposits stake into a pool via `MasterMagpie.deposit`/`depositFor`, which also registers the deposit with `pool.rewarder` (BaseRewardPool), incrementing the rewarder's `totalSupply` and the user's rewarder balance.
2. Owner pauses the contract (a normal, non-malicious operational action).
3. User calls `emergencyWithdraw(_stakingToken)`: `user.available` and `user.amount` are zeroed/reduced in `MasterMagpie`, and the staking token is transferred back to the user — see [2](#0-1) .
4. The rewarder (`BaseRewardPool`) is never called, so its recorded balance for the user and its `totalSupply` remain unchanged.
5. Once unpaused, the user (or any user who used this path) can still `getReward`/`claim` from the rewarder based on the stale, inflated balance, extracting rewards they should no longer be entitled to, while genuine stakers' `rewardPerToken` share is permanently diluted by the phantom `totalSupply`.

**Caveat:** I could not fully trace the normal `_deposit`/`_withdraw` internal functions in `rewards/MasterMagpie.sol` within the available tool budget to show the exact rewarder call that `emergencyWithdraw()` omits; this is inferred from the function's own "without caring about rewards" documentation and the absence of any `pool.rewarder` reference in its body [1](#0-0) . A Devin session with full repo access would be needed to confirm the exact rewarder interface calls used in the standard withdraw path for a complete side-by-side comparison.

```text
    /// @notice Withdraw all available tokens without caring about rewards. EMERGENCY ONLY. 
    ///         Locked Token can not be emergent withdraw.
    /// @param _stakingToken Staking token of the pool
    /// @dev withdrawFor of the rewarder with the third param at false is an emergency withdraw
    function emergencyWithdraw(address _stakingToken) external whenPaused {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        UserInfo storage user = userInfo[_stakingToken][msg.sender];
        uint256 availableaAmount = user.available;
        user.available = 0;
        IERC20(pool.stakingToken).safeTransfer(address(msg.sender), availableaAmount);
        emit EmergencyWithdraw(msg.sender, _stakingToken, availableaAmount);
        user.amount = user.amount - availableaAmount;
        user.rewardDebt = (user.amount * pool.accMGPPerShare) / 1e12;
    }
```
