Based on my investigation, I found a genuine analog of the sUSX mintCap bug in this repository's IBC/ERC20 middleware stack — and it is more severe than the original because it silently reports success while permanently trapping user funds, with no code path for either automatic refund or admin recovery.

### Title
Cross-chain packet acknowledged as successful while ERC20 conversion silently fails, permanently trapping user funds - (File: x/erc20/v2/ibc_middleware.go)

### Summary
The v2 ICS20/ERC20 middleware's `OnRecvPacket` discards the result of the ERC20 conversion callback and always returns the original (already-successful) transfer result, even when the conversion step fails. Combined with the non-atomic, multi-step `ConvertCoinNativeERC20` routine — which escrows the recipient's Cosmos coins into the ERC20 module account *before* attempting the EVM-level token transfer and burn — any destination-side failure of the EVM `transfer` call (analogous to the original report's "destination mint cap reached", but here caused by conditions like a paused/blacklisting native ERC20 contract, insufficient module token balance, or any other legitimate EVM revert) leaves the user's coins permanently escrowed in the `erc20` module account, while the IBC packet is acknowledged as `Success`. Because the ack is success, the source chain never triggers a refund, and the destination chain has no code path to sweep the stranded coins back to the user.

### Finding Description
The v2 middleware wraps the underlying transfer app and the erc20 keeper's conversion logic: [1](#0-0) 

Note that `im.keeper.OnRecvPacket(ctx, packet, ack)` on line 89 is called but its return value is **not used**; `recvResult` (built purely from the underlying transfer app's successful result on line 73) is unconditionally returned. This differs from the v1 middleware, which does propagate the conversion callback's result: [2](#0-1) 

The conversion logic itself, for the "native ERC20 token" case, first checks `MintingEnabled` and then calls `ConvertCoinNativeERC20`: [3](#0-2) 

`ConvertCoinNativeERC20` performs `SendCoinsFromAccountToModule` (escrowing the recipient's bank coins into the `erc20` module account) **before** it attempts the EVM `transfer` call that releases the native ERC20 tokens, and only burns the escrowed coins if that EVM call and the post-call balance check both succeed: [4](#0-3) 

Since Cosmos SDK/IBC-go does not roll back state changes when a callback returns a failure `Acknowledgement` object (only a Go panic reverts the whole message), the `SendCoinsFromAccountToModule` step remains committed even if the subsequent `CallEVM` fails and the function returns an error. In the v1 path, this is at least surfaced as an error ack (though whether that unwinds correctly on the source chain is itself questionable). In the v2 path (`x/erc20/v2/ibc_middleware.go`), this failure is completely swallowed — the function returns the original successful `recvResult`, so the relayer and source chain see `PacketStatus_Success` and never attempt to refund. There is no keeper method that later sweeps or retries the trapped coins out of the module account.

### Impact Explanation
This produces a permanent, irrecoverable loss of user funds through an entirely ordinary, unprivileged transaction flow (an ICS20 v2 packet carrying a returning native ERC20 token). The failure trigger (a reverting/misbehaving destination ERC20 contract call, analogous to the original report's mint-cap revert) is outside the sender's control, and unlike the sUSX report — where the admin can raise the cap to unblock the user — here there is no recovery path at all: the ack is success, so the source chain will never refund; the destination-chain coins are locked in the `erc20` module account with no burn (breaking the intended escrow/burn invariant) and no sweep function. This matches the "Critical permanent freezing, locking ... of user funds" impact class in the Cosmos EVM Allowed Impact Gate.

### Likelihood Explanation
Reachable by any unprivileged relayer/user simply completing an ordinary IBC v2 transfer of a native ERC20 token back to its origin EVM chain; the only requirement is that the destination-side `transfer` EVM call in `ConvertCoinNativeERC20` fails after the coin escrow step has already committed (e.g., a token owner pauses/blacklists, or module ERC20 balance/allowance state is otherwise insufficient). No validator or admin collusion is required.

### Recommendation
- In `x/erc20/v2/ibc_middleware.go`'s `OnRecvPacket`, propagate the result of `im.keeper.OnRecvPacket` back to the caller instead of discarding it and always returning the original `recvResult`.
- Make `ConvertCoinNativeERC20` atomic with respect to the escrow step: use a cached context (`ctx.CacheContext()`) and only commit (write) the escrow/burn state changes once the EVM transfer has verifiably succeeded, otherwise leave state untouched and surface a genuine error acknowledgement so the source chain can refund the sender.

### Proof of Concept
1. Register/send a native ERC20 token pair from `evmChainA` to `chainB` (as in `evmd/tests/ibc/v2_ibc_middleware_test.go` `TestOnRecvPacketNativeERC20`), so tokens are escrowed on `evmChainA`.
2. Send the voucher back from `chainB` to `evmChainA` in a v2 packet.
3. Before/while `OnRecvPacket` processes the packet, cause the EVM `transfer` call inside `ConvertCoinNativeERC20` to fail (e.g., pause the ERC20 contract, or otherwise make the module's token balance/transfer revert) after `SendCoinsFromAccountToModule` has already escrowed the coins.
4. Observe: `recvResult.Status` returned by `x/erc20/v2/ibc_middleware.go` `OnRecvPacket` is `PacketStatus_Success` (line 73/91) despite the conversion having failed, the coins remain in the `erc20` module account (never burned), and no refund is ever triggered on the source chain. func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	sourceClient string,
	destinationClient string,
	sequence uint64,
	payload channeltypesv2.Payload,
	relayer sdk.AccAddress,
) channeltypesv2.RecvPacketResult {
	recvResult := im.app.OnRecvPacket(ctx, sourceClient, destinationClient, sequence, payload, relayer)
	if recvResult.Status == channeltypesv2.PacketStatus_Failure {
		return recvResult
	}
	packet, err := v2ToV1Packet(payload, sourceClient, destinationClient, sequence)
	if err != nil {
		return channeltypesv2.RecvPacketResult{
			Status: channeltypesv2.PacketStatus_Failure,
		}
	}
	var ack channeltypes.Acknowledgement
	if err := transfertypes.ModuleCdc.UnmarshalJSON(recvResult.Acknowledgement, &ack); err != nil {
		return channeltypesv2.RecvPacketResult{
			Status: channeltypesv2.PacketStatus_Failure,
		}
	}
	im.keeper.OnRecvPacket(ctx, packet, ack)
	return recvResult
}

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}
