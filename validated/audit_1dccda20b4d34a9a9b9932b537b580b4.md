### Title
Zero-operator deposit bypasses all N-of-N covenant signature requirements, permanently locking deposited BTC — (File: `core/src/builder/sighash.rs`)

---

### Summary

`get_num_required_nofn_sigs()` multiplies by `deposit_data.get_num_operators()`. When no operators have registered, this product is **0**, causing every downstream signature-count guard to pass trivially (`0 == 0`). A deposit finalized in this state produces a move-to-vault transaction with **zero pre-signed covenant transactions** (no payout, no challenge, no disprove, no reimburse), permanently locking the deposited BTC.

---

### Finding Description

**Root cause — `core/src/builder/sighash.rs`, lines 50–55:**

```rust
pub fn get_num_required_nofn_sigs(&self, deposit_data: &DepositData) -> usize {
    deposit_data.get_num_operators()          // ← 0 when no operators registered
        * self.protocol_paramset().num_round_txs
        * self.protocol_paramset().num_signed_kickoffs
        * self.get_num_required_nofn_sigs_per_kickoff(deposit_data)
}
```

`get_num_operators()` returns `self.actors.operators.len()` (`core/src/deposit.rs:171-173`). Before any operator has called `setup`, the aggregator's `fetch_operator_keys()` returns an empty `Vec`, so `deposit_data.actors.operators` is empty and the entire product collapses to **0**.

**Deposit construction — `core/src/rpc/aggregator.rs`, lines 1464–1473:**

```rust
let deposit_data = DepositData {
    actors: Actors {
        verifiers: self.fetch_verifier_keys().await?,
        watchtowers: vec![],
        operators: self.fetch_operator_keys().await?,  // empty vec → 0 operators
    },
    ...
};
```

**Downstream guards all pass with 0 — `core/src/rpc/aggregator.rs`, lines 1496–1651:**

```
needed_nofn_sigs = get_num_required_nofn_sigs(&deposit_data)  // = 0
```

- `nonce_aggregator`: `while sighash_stream.next()` yields nothing (no operators to iterate); sanity check `total_sigs != needed_nofn_sigs` → `0 != 0` → **false, no error**.
- `nonce_distributor`: `sig_count != needed_nofn_sigs` → `0 != 0` → **false, no error**.
- `signature_aggregator`: `sig_count != needed_nofn_sigs` → `0 != 0` → **false, no error**.

Similarly, `num_required_total_op_sigs = num_required_op_sigs * num_operators = 0`, so the operator-signature check in `core/src/rpc/verifier.rs:564-570` also passes trivially.

**Verifier's `is_deposit_valid` — `core/src/verifier.rs`, lines 603–658:**

```rust
let operators_in_db = self.db.get_operators(None).await?;   // empty
for (xonly_pk, ..) in operators_in_db.iter() { ... }        // loop body never executes
for operator_xonly_pk in operators_in_deposit_data { ... }  // loop body never executes
```

There is **no minimum-operator-count guard** anywhere in `is_deposit_valid`. The function returns `Ok(())` when both the DB and the deposit carry zero operators.

The deposit then proceeds to move-tx signing (which is separate from covenant signing), producing a valid signed move transaction — but with **no pre-signed kickoff, payout, challenge, disprove, or reimburse transactions** stored in the database.

---

### Impact Explanation

The N-of-N vault covenant works by pre-signing all future spending paths **before** BTC is moved into the vault. With `needed_nofn_sigs = 0`, none of those paths are pre-signed. The resulting vault UTXO:

- Has no payout path → withdrawals cannot be processed.
- Has no challenge/disprove path → operator fraud cannot be punished.
- Has no reimburse path → collateral cannot be recovered.

BTC deposited during the zero-operator window is **permanently locked** in the N-of-N taproot output with no spendable script path other than the N-of-N key path itself, which requires all verifiers to cooperate out-of-band.

**Severity: Critical** — permanent, irreversible loss of bridged BTC.

---

### Likelihood Explanation

The window exists from bridge deployment until the first operator completes `setup`. During integration, testing, or a staged rollout, this window can be minutes to hours. Any user who submits a deposit to the aggregator during this window triggers the path. The aggregator does not reject the request — it silently builds a zero-operator `DepositData` and proceeds.

---

### Recommendation

Add an explicit minimum-operator (and minimum-verifier) guard in `is_deposit_valid` (`core/src/verifier.rs`) and at the start of `new_deposit` (`core/src/rpc/aggregator.rs`):

```rust
// In is_deposit_valid:
if deposit_data.get_num_operators() == 0 {
    return Err(BridgeError::InvalidDeposit(
        "Deposit must include at least one operator".into()
    ));
}
if deposit_data.get_num_verifiers() == 0 {
    return Err(BridgeError::InvalidDeposit(
        "Deposit must include at least one verifier".into()
    ));
}
```

Additionally, add a debug-assert or hard error in `get_num_required_nofn_sigs` to catch the zero case:

```rust
pub fn get_num_required_nofn_sigs(&self, deposit_data: &DepositData) -> usize {
    let n = deposit_data.get_num_operators();
    assert!(n > 0, "Cannot compute required sigs with zero operators");
    n * self.protocol_paramset().num_round_txs
      * self.protocol_paramset().num_signed_kickoffs
      * self.get_num_required_nofn_sigs_per_kickoff(deposit_data)
}
```
