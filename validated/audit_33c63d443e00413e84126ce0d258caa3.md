### Title
OP_RETURN data is omitted from fee and weight accounting - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` adds the caller-controlled OP_RETURN output to `tx_outs`, but calculates the transaction's weight, virtual size, required fee, and standardness limit using only the payment outputs. A transaction containing OP_RETURN data can therefore be signed with less than the requested fee rate and may exceed Bitcoin's maximum standard transaction weight without being rejected.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:193-202`, the OP_RETURN output is appended to `tx_outs`. However, the subsequent call at `send.rs:204` invokes `calculate_weight_vbytes(tx_ins.len(), payments, None)`, omitting that output entirely. The same omission occurs in the change-accounting path at `send.rs:225-227`, which again passes only `payments`.

As a result:

- `needed_fee` is calculated from a virtual transaction size that excludes the OP_RETURN output.
- If change is created, its amount is selected so the absolute fee equals that underestimated `needed_fee`; adding the already-created OP_RETURN output does not add any corresponding fee.
- `weight` used for the `MAX_STANDARD_TX_WEIGHT` check excludes the OP_RETURN output, while the final transaction includes it.

This is the same incorrect-normalization bug class as the report: a value derived from the reserves/formula has the wrong scale because one input to the formula is omitted or represented at the wrong effective dimension.

### Impact Explanation
An unprivileged caller able to supply transaction data can cause the wallet to construct and sign a transaction whose actual fee rate is below the requested `fee_per_vbyte`. In boundary cases, a transaction intended to satisfy Bitcoin's minimum relay fee can be serialized below the required rate because the OP_RETURN output increases its real virtual size without increasing the fee.

The omitted weight also permits `SignableTransaction::new` to accept a transaction whose final serialized weight exceeds `MAX_STANDARD_TX_WEIGHT`. Such a transaction can complete the FROST signing flow but be rejected by standard Bitcoin relay policy, leaving the constructed spend unusable until a replacement is coordinated.

### Likelihood Explanation
The issue is directly reachable through the public `data` argument to `SignableTransaction::new`. Any non-empty OP_RETURN payload, including the documented maximum of 80 bytes, affects the actual transaction's size but not its calculated weight or required fee.

The most severe boundary cases require transaction sizing or fee-rate choices near relay-policy limits, so this does not unconditionally produce an invalid transaction. When triggered, however, the discrepancy is deterministic and does not depend on malicious validators, leaked keys, collusion, or malformed cryptographic encodings.

### Recommendation
Calculate weight and virtual size from the complete output list, including the OP_RETURN output. In particular, use `tx_outs`—or an equivalent representation containing payments plus the OP_RETURN output—when calling `calculate_weight_vbytes`.

The change path should similarly calculate `fee_with_change` and `weight_with_change` using all outputs that will exist in the final transaction. After the final `tx_outs` vector is complete, recalculate or verify the actual transaction weight before accepting it.

### Proof of Concept
The discrepancy can be demonstrated conceptually with:

```rust
SignableTransaction::new(
  inputs,
  &payments,
  Some(change_script),
  Some(vec![0; 80]),
  fee_per_vbyte,
)
```

Execution reaches these steps:

1. The OP_RETURN output is appended to `tx_outs`.
2. `calculate_weight_vbytes(tx_ins.len(), payments, None)` receives only `payments`, not `tx_outs`.
3. `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` also receives only `payments`.
4. The final `Transaction` contains `tx_outs`, including the OP_RETURN output.

Thus the signed transaction has more output bytes and weight than the transaction used for both fee sizing and the maximum-weight check.
