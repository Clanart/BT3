### Title
Sub-dust Bitcoin deposits are credited as spendable balance, producing plans that either panic the transaction builder or can never be fulfilled - (File: processor/src/networks/bitcoin.rs)

### Summary
The external report describes transfers performed without checking for a zero/degenerate amount, causing reverts and incorrect accounting. The Serai analog is the missing minimum-value (dust) check on *inbound* Bitcoin outputs: `Bitcoin::get_outputs` accepts any output paying to a Serai script regardless of value, yet downstream the same codebase treats sub-`DUST` amounts as a hard error (`TransactionError::DustPayment`, which `make_signable_transaction` converts into a `panic!`) or drops them to zero during fee amortization. An unprivileged depositor can therefore create a "funds reported received" state that is either unspendable or crashes the signing pipeline.

### Finding Description
`Bitcoin::get_outputs` (`processor/src/networks/bitcoin.rs:686-740`) scans every non-coinbase transaction and returns any output whose `script_pubkey` matches a registered Serai script via `scanner.scan_transaction`. `Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`) matches only on `script_pubkey` and clones the `TxOut` verbatim — no check that `output.value` is non-zero or above any threshold. The resulting `Output::balance()` reports `Amount(self.output.value())` (`processor/src/networks/bitcoin.rs:128-130`) as a credited deposit.

On the spend side, `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:165-169`) rejects any payment below `DUST` (546 sats) with `TransactionError::DustPayment`. `Bitcoin::make_signable_transaction` (`processor/src/networks/bitcoin.rs:446-470`) then maps this to `panic!("dust payment despite removing dust")`, assuming all sub-dust payments were already removed by fee amortization.

That assumption is violated by paths that bypass `payments()`/amortization: `Scheduler::refund_plan` and `Scheduler::shim_forward_plan`/`forward_plan` (`processor/src/multisigs/scheduler/utxo.rs:587-630`) construct a `Plan` whose single `Payment` carries `balance: output.balance()` verbatim — the raw deposited amount with no floor — with `change: None`. Even for plans that do pass through `amortize` in `processor/src/networks/mod.rs:497-530`, a payment below `N::DUST` (10,000 sats for Bitcoin, `processor/src/networks/bitcoin.rs:638`) is zeroed and dropped, leaving the input with no outputs and yielding `Ok(None)` — the credited deposit is silently stranded.

Additionally, `SignableTransaction::new` performs no per-input value check, so sub-dust UTXOs are aggregated into transactions as inputs whose contribution is less than the marginal fee their inclusion costs (`calculate_weight_vbytes`, `send.rs:62-127`), inflating `needed_fee` while crediting the depositor the full nominal amount.

### Impact Explanation
- A user-controlled deposit of ~330–545 sats (below `DUST = 546` in `send.rs:32`, relayable/mineable as P2TR has a ~330-sat standardness floor and consensus-valid at any positive value) is credited by `get_outputs` yet, when a refund or forward plan is built for it, reaches `BSignableTransaction::new` as a payment below 546 sats → `DustPayment` → `panic!` in `make_signable_transaction`, crashing/haltin­g the processor's signing loop for that multisig.
- A deposit of 546–9,999 sats (fully standard) is credited at face value but sits below `N::DUST = 10_000`, so amortization drops the corresponding payment to 0 (`mod.rs:497-530`); the plan produces no transaction and the funds are reported received yet can never be paid out — matching the "incorrect value of shares / funds reported received that are not spendable" consequence class of the original report.

### Likelihood Explanation
Any unprivileged party sending a Bitcoin transaction to a Serai deposit/branch/change/forward address controls the output amount. No authentication or validator collusion is required; the only constraint is getting a sub-546-sat output mined (standardness-limited but consensus-valid, and achievable via miners accepting sub-dust or via outputs to registered offset addresses). Deposits in the 546–9,999 range are trivially standard.

### Recommendation
Mirror the fix in the original report — validate the amount before acting on it:
- In `Bitcoin::get_outputs` (or at `scan_transaction` consumption), discard or flag outputs with `value < N::DUST` so sub-dust deposits are never credited as spendable balance.
- Defense in depth: in `Scheduler::refund_plan`/`shim_forward_plan`/`forward_plan` (`utxo.rs:587-630`), return `None` when `output.balance().amount.0 < N::DUST` instead of constructing an unfulfillable plan.
- In `SignableTransaction::new`, skip or reject inputs whose value is below the marginal fee their inclusion adds.

### Proof of Concept
1. Attacker sends a Bitcoin transaction paying 400 sats to a Serai multisig's P2TR script (consensus-valid; mineable despite standardness dust rules).
2. `Bitcoin::get_outputs` returns an `Output` with `balance = Amount(400)`; the deposit is recorded.
3. A refund (`refund_plan`) or multisig-rotation forward (`forward_plan`) builds `Plan { payments: [Payment { balance: 400, ... }], inputs: [output], change: None }`.
4. `Bitcoin::make_signable_transaction` calls `BSignableTransaction::new` with a 400-sat payment → `Err(DustPayment)` → `panic!("dust payment despite removing dust")` (`processor/src/networks/bitcoin.rs:460`), crashing the processor.
5. Variant: deposit 5,000 sats (standard). It is credited, but any plan carrying it has the payment zeroed by the dust filter in `processor/src/networks/mod.rs:497-530`; `tx_outs` becomes empty → `NoOutputs` → `Ok(None)`: the deposit is permanently unspendable while reported as received.

Caveat: whether refund/forward plans pass through the `payments()` amortization path in `mod.rs` before reaching `make_signable_transaction` was not fully traced within the available context; if they do, the sub-546 case strands funds instead of panicking. The 546–9,999 stranding case holds regardless, since `get_outputs` lacks any minimum-value gate while the spend pipeline enforces `N::DUST`.
