### Title
Quadratic Lagrange interpolation in `ThresholdKeys::read`/`ThresholdKeys::new` enables CPU exhaustion from untrusted bytes - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts attacker-controlled `t`/`n` values up to `u16::MAX` and deserializes `n` verification-share points, then calls `ThresholdKeys::new`, which recomputes the Lagrange `interpolation_factor` (an O(t) loop over `included`) once for each of the `t` participants. With `Interpolation::Lagrange`, this is O(t²) scalar multiplications/inversions — about 4.3 billion field operations for `t = n = 65535` — triggered by a serialized blob of only ~2 MiB. This mirrors the sqlparse report's class: repeated prefix/set recomputation over an input sized just under a parser cap, causing near-cap quadratic CPU consumption in a single call reachable via `ThresholdKeys::read`.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i` as raw `u16`s with no bound beyond `ThresholdParams::new`'s `t <= n` check, so `t` and `n` can both be `65535` [1](#0-0) . It then reads `n` `C::F`/`C::G` elements and calls `ThresholdKeys::new` [2](#0-1) .

`ThresholdKeys::new` computes the group key by evaluating `interpolation_factor` for every participant in `1..=t` [3](#0-2) . For `Interpolation::Lagrange`, each `interpolation_factor` call loops over the whole `included` set performing a multiply and an inversion per factor [4](#0-3) . Total cost is therefore Θ(t²) field multiplications plus `t` inversions.

The same quadratic pattern repeats in `ThresholdKeys::view`, which calls `interpolation_factor(*i, &included)` once per included participant [5](#0-4) , but `read` alone is sufficient: a single `ThresholdKeys::read` call on crafted bytes performs the full O(n²) work inside `new`.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (a listed reachable API, e.g., any component that loads/relays serialized threshold keys) supplies a `Lagrange`-tagged blob with `t = n = 65535`: `6 + 1 + 32 + 65535·32` ≈ 2 MiB of input produces ~4.3·10⁹ scalar multiplications and 65535 inversions, occupying a worker for many seconds to minutes. Repeated or concurrent submissions amplify this into throughput collapse / worker starvation, matching the report's CWE-407 availability impact. No memory blow-up is needed — the input stays small relative to the compute it induces.

### Likelihood Explanation
Reachable wherever serialized `ThresholdKeys` cross a trust boundary; the payload is trivially constructible (any `n` valid point encodings, `Lagrange` tag byte `1`, `t = n = u16::MAX`). The cap that would "reject quickly" — analogous to sqlparse's token cap — does not exist: `n` is bounded only by the `u16` width, and `ThresholdParams::new` accepts `t == n` [6](#0-5) . Medium severity per the report's rating: availability-only, opt-in reachability through consuming code.

### Recommendation
- Bound `n`/`t` to a protocol-meaningful maximum (e.g., the network's actual validator set size) inside `ThresholdKeys::read` before allocating or interpolating, rather than relying on `u16` range.
- Compute Lagrange factors in O(n) total via the standard prefix/suffix product trick (compute ∏(i − l) once, then per-participant numerators/denominators) in both `ThresholdKeys::new` and `ThresholdKeys::view`.
- Alternatively cache `interpolation_factor` results — note `Interpolation` is cloned into `ThresholdView` and factors are recomputed per call [7](#0-6) .

### Proof of Concept
Conceptual: build a byte string = `u32 LE len(C::ID)` ‖ `C::ID` ‖ `t = 0xFFFF` ‖ `n = 0xFFFF` ‖ `i = 0x0001` ‖ `0x01` (Lagrange) ‖ 32-byte scalar ‖ 65535 valid `C::G` encodings (e.g., the generator repeated). Pass to `ThresholdKeys::<C>::read(&mut bytes)`. `read` succeeds the linear parsing phase, then `ThresholdKeys::new` evaluates `interpolation_factor` 65535 times, each iterating up to 65535 `included` entries — ~4.3·10⁹ field multiplications and 65535 `invert()` calls — vs. ~0 work for a small honest `t = n = 16` key. Timing ratio scales as (65535/16)² ≈ 16.7M× for a ~150× larger input, demonstrating super-linear (quadratic) CPU growth on attacker-controlled input.
