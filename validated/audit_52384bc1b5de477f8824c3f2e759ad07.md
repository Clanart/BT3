### Title
Silent, unconfirmed rewrite of the `origin` remote URL from an untrusted GitHub API object - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
Foundation's `NFTMarketCreators`/`NFTMarketFees` trusted external, attacker-influenceable data (Royalty Registry entries) to silently redirect payment flow away from the legitimate seller, with no explicit confirmation step. The Desktop analog is `updateRemoteUrl()`, which trusts the `clone_url` field of a GitHub API repository object — fetched using only a string match on `owner`/`name`/`hostname` parsed off the *existing* local remote — to silently rewrite the user's `origin` remote, with no user confirmation, unlike the equivalent flow for the `upstream` remote which *does* prompt the user (`UpstreamAlreadyExists` dialog).

### Finding Description
`repositoryWithRefreshedGitHubRepository()` (invoked automatically during background refresh/fetch cycles and after operations like publish) resolves "which GitHub repo this is" purely via `matchGitHubRepository()`, a hostname + owner + name string match against the current `origin` remote URL: [1](#0-0) 

It then calls the GitHub API for that owner/name and, if a `gitHubRepository` association already exists, feeds the API response straight into `updateRemoteUrl()`: [2](#0-1) 

`updateRemoteUrl()` compares the API's `clone_url` against the locally stored `cloneURL` and, if the *local* remote still matches what Desktop previously cached (`remoteUrlUnchanged`) and protocols match, it calls `gitStore.setRemoteURL()` to overwrite the `origin` remote — **with no user prompt**: [3](#0-2) 

Contrast this with the sibling flow for the `upstream` remote of a fork, where the exact same class of decision (rewrite a remote based on API data) is explicitly gated behind a confirmation dialog telling the user "Current" vs "Expected" URL before making the change: [4](#0-3) 

No such guard exists for `origin`. The unit tests confirm the silent-write behavior is intentional design, not an oversight: [5](#0-4) 

### Impact Explanation
The corrupted value is the local git `origin` remote URL — the destination of every subsequent `git fetch`/`git push` for that repository. Because the lookup key is `owner + name + hostname` string equality rather than a stable repository ID, whenever the API returns a different `clone_url` for that same owner/name (e.g., following a repository/organization rename, transfer, or reclaiming of a vacated owner name on the same host — data entirely under the control of a GitHub-side actor, i.e. an "GitHub API object" per the report's threat model), Desktop will automatically retarget the user's push/fetch destination without any notice or opt-out, unlike the analogous upstream-remote case which does prompt. This matches the "silent corruption of what the user commits or pushes" impact category: a user's next `git push` can be silently redirected to a different remote than the one they configured, without the confirm-before-write pattern used elsewhere in the same codebase for materially identical risk.

### Likelihood Explanation
The precondition (`remoteUrlUnchanged` being true) is the common case — most users never hand-edit their `origin` remote after cloning, so the guard that's meant to preserve user customizations instead makes the auto-rewrite path the default path. The trigger (background refresh of `gitHubRepository` info) runs automatically as part of normal Desktop operation (`repositoryWithRefreshedGitHubRepository`), not requiring any unusual user action. The dependency on a rename/transfer/reclaim event on the GitHub side means the likelihood is bounded by how often such events legitimately or maliciously occur; I was not able to fully verify from the available code whether Desktop's `owner`/`name` matching keys off a stable repository ID anywhere upstream that would prevent misassociation after a rename — this uncertainty affects confidence in the end-to-end exploitability and should be validated further (e.g., against `IAPIRepository`'s `id` field usage across `RepositoriesStore`).

### Recommendation
- Require explicit user confirmation before rewriting the `origin` remote URL, mirroring the existing `UpstreamAlreadyExists` pattern used for the `upstream` remote.
- Key repository identity on the GitHub API's immutable numeric repository `id` rather than the mutable `owner`/`name` string pair, and treat an `id` mismatch as "this is a different repository" rather than silently accepting new metadata/clone URLs for it.

### Proof of Concept
Conceptual (not independently executed against a live Desktop instance):
1. User clones `https://github.com/owner/repo.git`; Desktop stores `gitHubRepository.cloneURL = https://github.com/owner/repo`.
2. The `owner`/`repo` name pairing on GitHub.com is later reassigned (rename, transfer, or account/name reclamation) such that `api.fetchRepository('owner','repo')` now returns a different underlying repository with a different `clone_url` (or the same owner/name but attacker-controlled content).
3. On the next background refresh, `repositoryWithRefreshedGitHubRepository()` fetches this new API object and passes it to `updateRemoteUrl()`.
4. Since the local `origin` remote still equals the last cached `cloneURL` (`remoteUrlUnchanged === true`) and protocols match, `gitStore.setRemoteURL('origin', apiRepo.clone_url)` executes silently, rewriting the push/fetch destination with no dialog shown to the user, unlike the equivalent `upstream` case.

**Note on confidence:** given the remaining ambiguity about how repository identity (`id`) is or isn't cross-checked elsewhere in `RepositoriesStore`/`app-store.ts`, this should be treated as a plausible but not fully proven end-to-end exploit chain; a Devin session with full repo access and the ability to run the test suite / trace `RepositoriesStore.upsertGitHubRepository` would be needed to confirm whether an `id` check exists anywhere that would block this.

/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)

      return repository

      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)

    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
