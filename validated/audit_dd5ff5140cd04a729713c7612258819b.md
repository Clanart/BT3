### Title
Optimistic payout `output_amount` is bounded only by `bridge_amount - anchor`, never checked against the Citrea-recorded withdrawal amount, even when `aggregator_verification_address` is set - (File: core/src/verifier.rs)

### Summary
`Verifier::sign_optimistic_payout` and `AggregatorServer::optimistic_payout` both accept an attacker-supplied `output_amount` and bound it only by an upper cap (`bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT`). Neither the aggregator's ECDSA co-signature nor the verifier's own logic ever queries Citrea (or the withdrawal UTXO's on-chain value) to confirm that `output_amount` equals the amount the withdrawal actually entitles the user to. The `aggregator_verification_address` gate at core/src/verifier.rs:1601-1623 only proves the ECDSA signature was produced by the configured aggregator key; it does not prove the signed `output_amount` is correct, so it cannot substitute for the missing binding.

### Finding Description
The correct binding should be: `output_amount == amount_recorded_for_deposit_id's_withdrawal_on_Citrea`. Instead, only `output_amount <= bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT` is enforced: [1](#0-0) 

The `aggregator_verification_address` check that precedes it only recovers the ECDSA signer address and compares it to the configured address — it re-derives nothing about the real Citrea amount, it merely re-hashes the same attacker-supplied `WithdrawParams` fields (`deposit_id`, `input_signature`, `input_outpoint`, `output_script_pubkey`, `output_amount`): [2](#0-1) [3](#0-2) 

The only additional check is that `input_outpoint` matches the outpoint Citrea recorded for this `deposit_id`'s withdrawal: [4](#0-3) 

But `get_withdrawal_utxo_from_citrea_withdrawal` / `collect_withdrawal_utxos` only ever record an `OutPoint`, never an amount, from Citrea: [5](#0-4) 

The same absence exists on the aggregator side: `AggregatorServer::optimistic_payout` verifies the Schnorr `input_signature` over the payout sighash and matches the outpoint, but never fetches or compares any Citrea-side entitled amount before driving N-of-N signing: [6](#0-5) 

Contrast this with `Operator::withdraw`, which at least checks `output_txout.value` against the *withdrawal input UTXO's own on-chain value* via `is_profitable`: [7](#0-6) 

`Verifier::sign_optimistic_payout` has no equivalent check against `withdrawal_prevout`'s value or any Citrea-attested amount — it fetches `withdrawal_prevout` only to build the transaction, never to bound `output_amount`: [8](#0-7) 

Exploit flow: attacker deposits into the bridge (creating a deposit with `bridge_amount`), calls the real Citrea Bridge contract's `withdraw` for a `withdrawal_id`, self-signs the payout input with `SIGHASH_SINGLE|ANYONECANPAY` (attacker controls the witness of the withdrawal UTXO they supply), and sends `OptimisticPayoutParams`/`OptimisticWithdrawParams` to the aggregator's public gRPC with `output_amount = bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT` and any `output_script_pubkey` they control. The aggregator obtains a valid ECDSA `verification_signature` for these exact bytes (its own logic has no cross-check per the companion finding at aggregator.rs:1010-1126), then relays the request to all verifiers, each of which passes the ECDSA gate (since the signature is validly produced over the attacker's inflated `output_amount`) and the upper-bound check (since it is set exactly at the cap), producing valid MuSig2 partial signatures that aggregate into a full N-of-N signature authorizing a full-`bridge_amount`-sized spend of the move-to-vault UTXO.

None of the listed guards close this gap: `SECP.verify_schnorr` only checks the attacker's own signature over their own withdrawal-UTXO input, not the payout amount's correctness; `is_deposit_valid` validates deposit structure, not withdrawal amount; there is no `verify_storage_proofs`/`lc_proof_verifier` call anywhere in this call path to independently derive the entitled amount from Citrea state; and the database uniqueness constraint on `(deposit_id -> withdrawal_utxo outpoint)` only prevents double-registration of a withdrawal, not amount forgery.

### Impact Explanation
An attacker can obtain N-of-N verifier signatures authorizing a full-`bridge_amount` optimistic payout from a move-to-vault UTXO while having only withdrawn/burned a much smaller (even dust) amount on Citrea L2. This is BTC leaving a move-to-vault UTXO without a matching fronted/entitled withdrawal — a Critical impact category explicitly listed. The attack is repeatable across every deposit for which the attacker can register any Citrea withdrawal, since the missing check is structural (present for every `deposit_id`), not a one-off bug tied to a specific value.

### Likelihood Explanation
Requires `aggregator_verification_address` to be configured (a supported, presumably common deployment mode) and simply requires the attacker to: (1) deposit BTC into the bridge to create a `deposit_id` (attacker already controls this deposit's move-to-vault amount = `bridge_amount`), (2) call Citrea's public `withdraw` for any amount, (3) sign the withdrawal UTXO input with `SIGHASH_SINGLE|ANYONECANPAY`, and (4) call the aggregator's public `OptimisticPayout` gRPC with `output_amount` set to the cap. No verifier/operator/aggregator privilege, key share, or collateral is needed — only normal deposit fees and the withdrawal itself. This is fully reproducible offline against a mocked `CitreaClientT`.

### Recommendation
Bind `output_amount` to the actual Citrea-recorded/entitled withdrawal amount rather than only an upper bound. Concretely: extend `CitreaClientT::collect_withdrawal_utxos` (or add a dedicated call) to also return the withdrawal's committed amount from the Citrea Bridge contract/light-client proof, store it alongside `withdrawal_utxo` in the verifier DB, and in `Verifier::sign_optimistic_payout` (and `AggregatorServer::optimistic_payout`) replace the `output_amount > bridge_amount - anchor` check with an equality check against this stored Citrea-derived amount before proceeding to nonce/partial-signature generation.

```rust
pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)
}
```
