### Title
Attacker-controlled `n` in `ThresholdKeys::read` causes a large up-front `Vec::with_capacity` allocation (input-to-memory amplification DoS) - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` reads the participant count `n` directly from untrusted bytes and immediately calls `Vec::with_capacity(usize::from(n))` for `Interpolation::Constant` before any of the `n` elements are actually present in the stream. A handful of header bytes therefore forces an allocation proportional to `n * size_of::<C::F>()` (up to 65535 field elements, ~2–4 MiB), an entity-expansion-style amplification analogous to XEE: a tiny input expands into a large memory commitment. This is the same bug class as CVE-2014-1868 (unbounded expansion of attacker-declared structure during deserialization).

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` parses `t`, `n`, and `i` as raw `u16`s from the reader (lines 591-602). It then reads the interpolation tag and, for `Interpolation::Constant`, executes:

```rust
let mut res = Vec::with_capacity(usize::from(n));
for _ in 0 .. n {
  res.push(C::read_F(reader)?);
}
``` [1](#0-0) 

The `with_capacity` performs the full heap allocation up front. `n` is a `u16` fully controlled by the input, so ~10 bytes of input (curve ID check + `t`/`n`/`i` + tag `0`) yields a ~2 MiB allocation for 32-byte fields (more for larger fields such as ed448's 56-byte `F`). The subsequent `read_F` loop fails fast on short input, but the allocation has already been committed and is only released when the error propagates and the partially-built `Vec` is dropped — an attacker issuing many concurrent/sequential reads can pin large amounts of memory with negligible bandwidth. The same `n` also drives the `verification_shares` loop over `1 ..= n` reading `n` group elements, but that work is input-bound; the amplification lives specifically in the speculative `with_capacity`. The codebase itself acknowledges this class elsewhere — `coordinator/src/tributary/transaction.rs` caps `commitments_len * each_commitments_len` against `TRANSACTION_SIZE_LIMIT` before allocating, and `coordinator/src/p2p.rs` caps the length before `vec![0; len]` — but `ThresholdKeys::read` performs no equivalent check. `ThresholdKeys::read` is on the permitted list of APIs reachable with untrusted bytes.

### Impact Explanation
An unprivileged party who can feed crafted bytes to `ThresholdKeys::read` (e.g., during key import/recovery flows in `dkg/promote`/`recovery` contexts) can cause a ~10-byte message to trigger multi-megabyte heap allocations. Repeated or parallelized, this exhausts process memory and denies service to the signing/verification node — a remote memory-amplification DoS, matching the Medium-severity XEE class.

### Likelihood Explanation
Exploitation requires only that the target deserialize attacker-supplied bytes via `ThresholdKeys::read`; no valid signatures, threshold collusion, or protocol participation is needed — the allocation happens before any validation (`ThresholdParams::new` runs only after all reads complete, at line 625-631). Likelihood is gated by how often the application exposes this deserialization path to untrusted input, which is moderate.

### Recommendation
Allocate incrementally (`Vec::new()` + `push`, which only commits memory as bytes are actually consumed, mirroring the chunked-read comment in `networks/ethereum/src/machine.rs` lines 51-60), or validate `n` against a sane bound (e.g., `ThresholdParams` limits / `n <= u16::MAX` is already implied but should also require `t <= n` semantics *before* allocating, and ideally check remaining input length) prior to `with_capacity`.

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ciphersuite;
use dkg::ThresholdKeys;
use ciphersuite_kp256::Secp256k1; // illustrative in-scope suite

fn main() -> io::Result<()> {
  let mut buf = vec![];
  // curve ID check passes
  buf.extend(u32::try_from(Secp256k1::ID.len()).unwrap().to_le_bytes());
  buf.extend(Secp256k1::ID);
  // t = 1, n = u16::MAX, i = 1
  buf.extend(1u16.to_le_bytes());
  buf.extend(u16::MAX.to_le_bytes());
  buf.extend(1u16.to_le_bytes());
  // Interpolation::Constant
  buf.push(0u8);
  // Truncate the stream here: ~15 bytes of input have already forced
  // Vec::with_capacity(65535) inside ThresholdKeys::read (~2 MiB committed)
  // before the first read_F fails with UnexpectedEof.
  let _ = ThresholdKeys::<Secp256k1>::read(&mut buf.as_slice());
  Ok(())
}
```

Each such ~15-byte input commits ~2 MiB of heap before erroring; issuing many in parallel exhausts memory despite minimal input bandwidth — the same small-input/large-allocation amplification as XML entity expansion.
