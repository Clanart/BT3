### Title
DID Recovery Attestation Uses a Non-Nonced, Non-Coin-Bound `AGG_SIG_UNSAFE` Message, Enabling Attestation Replay Across Different DIDs - ([File: chia/wallet/did_wallet/did_wallet_puzzles.py])

### Summary
The external report describes a replay-attack bug class: a multisig/oracle authorization message that omits a nonce or unique binding data, allowing the same signature to be reused to trigger an unintended state change repeatedly. The Chia codebase has a structurally identical pattern in the DID recovery attestation mechanism: the signed `AGG_SIG_UNSAFE` message used to attest to a DID recovery only commits to the new puzzle hash (`newpuz`), not to the specific recovering coin, DID launcher id, or any nonce.

### Finding Description
`create_recovery_message_puzzle()` builds the ephemeral "attestation" puzzle used when a backup DID authorizes recovery of another DID whose owner key was lost: [1](#0-0) 

The puzzle unconditionally reveals two conditions: `CREATE_COIN_ANNOUNCEMENT recovering_coin_id` and `AGG_SIG_UNSAFE pubkey newpuz`. Critically, the **signed message is `newpuz` alone** — it does not include `recovering_coin_id`, the DID's `launcher_id`, or any nonce. This is analogous to the vAMM bug: `handle::pause()`/`handle::unpause()` verified a multisig over only `(is_active, asset_id)` with no nonce, so the same signature could be replayed to redundantly trigger `op::open_market`/`op::close_market`.

In Chia's case, the backup DID's private key signs `AugSchemeMPL.sign(backup_sk, newpuz)`. Because the puzzle reveal (which contains `recovering_coin_id`) is not part of the signed payload, any spend bundle whose attestation puzzle is curried with the *same* `pubkey` and `newpuz` — but a *different* `recovering_coin_id` — will produce the identical `AGG_SIG_UNSAFE` `(pubkey, msg)` pair, and the previously-published signature will still verify. This is exactly the design hazard `AGG_SIG_UNSAFE` is named for: unlike `AGG_SIG_ME`/`AGG_SIG_PARENT`/etc., which the consensus layer domain-separates with per-coin data (`agg_sig_additional_data`, coin id/parent/puzzle/amount) as shown in `chia/consensus/condition_tools.py`, `AGG_SIG_UNSAFE` carries no implicit binding at all: [2](#0-1) 

The recovery-message construction relies entirely on the puzzle author to embed sufficient context in the signed bytes, and here it does not.

### Impact Explanation
If a single backup DID (or backup-recovery service) is listed as an authorized recoverer for two or more distinct DIDs, and it once produces a legitimate attestation for DID A targeting some `newpuz` (e.g., at the request of the true owner, or an attacker-controlled DID that lists this backup service), that attestation's `AGG_SIG_UNSAFE` signature becomes publicly visible on-chain once the DID A recovery spend is confirmed. An attacker can then reuse the exact same `(pubkey, signature)` pair inside a newly constructed attestation puzzle curried with a different `recovering_coin_id` pointing at DID B (which also lists the same backup entity), and DID B's recovery-mode inner puzzle will accept it as satisfying one recovery-threshold vote — because the signature check only validates `pubkey`/`newpuz`, and the puzzle's currying (which determines the announcement) is not attacker-constrained beyond needing the coin id of the DID being attacked. If the recovery threshold (`num_of_backup_ids_needed`) can be met using this reused vote plus other satisfied conditions, the attacker forcibly transfers DID B's ownership to `newpuz` without ever compromising the backup DID's private key. This is an unauthorized asset-ownership takeover (DID/NFT hijack via replayed recovery attestation), matching the report's "unauthorized coin movement / forged authorization" class.

### Likelihood Explanation
Exploitation requires: (1) a backup DID/service shared across multiple DIDs' `backup_ids` lists — a realistic and even encouraged pattern for third-party custodial-recovery providers; (2) at least one prior legitimate (or attacker-self-initiated) recovery attestation involving that backup entity being confirmed on-chain, making the signature bytes public; and (3) a victim DID whose recovery threshold can be satisfied by combining the replayed vote with other available votes/conditions. This is a moderate-likelihood scenario dependent on real-world backup-DID reuse patterns and threshold configuration, not requiring any privileged access — any unprivileged spend-bundle submitter with knowledge of a prior confirmed attestation can attempt it.

### Recommendation
Bind the `AGG_SIG_UNSAFE` message in `create_recovery_message_puzzle()` to unique, unforgeable context — at minimum the `recovering_coin_id` (and ideally the DID's `launcher_id`/singleton identity or a random nonce), e.g. sign `sha256(recovering_coin_id + newpuz)` instead of `newpuz` alone, so a given backup attestation can only ever satisfy recovery for the specific DID coin it was created for.

### Proof of Concept
Conceptual reproduction (not run against a live chain):
1. Backup entity `X` (pubkey `pkX`) is listed in `backup_ids` for both `DID_A` (attacker-controlled) and `DID_B` (victim).
2. Attacker requests legitimate recovery of `DID_A`, and `X` signs `AugSchemeMPL.sign(skX, newpuz_attacker)` via `create_recovery_message_puzzle(DID_A_coin_id, newpuz_attacker, pkX)`; the resulting spend bundle is confirmed on-chain, exposing `(pkX, newpuz_attacker, sig)`.
3. Attacker builds a new ephemeral puzzle via `create_recovery_message_puzzle(DID_B_coin_id, newpuz_attacker, pkX)` — same `pkX`/`newpuz_attacker`, different `recovering_coin_id` — and reuses `sig` from step 2 in a `create_spend_for_message`-style coin spend, since `AugSchemeMPL.verify(pkX, newpuz_attacker, sig)` still holds.
4. Attacker submits `DID_B`'s recovery spend along with this forged attestation (plus any other satisfiable votes) to hijack `DID_B`'s ownership to `newpuz_attacker`, without `X` ever having authorized `DID_B`'s recovery. [3](#0-2)

def create_recovery_message_puzzle(recovering_coin_id: bytes32, newpuz: bytes32, pubkey: G1Element) -> Program:
    """
    Create attestment message puzzle
    :param recovering_coin_id: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: Message puzzle
    """
    puzzle = Program.to(
        (
            1,
            [
                [ConditionOpcode.CREATE_COIN_ANNOUNCEMENT, recovering_coin_id],
                [ConditionOpcode.AGG_SIG_UNSAFE, bytes(pubkey), newpuz],
            ],
        )
    )
    return puzzle


def create_spend_for_message(
    parent_of_message: bytes32, recovering_coin: bytes32, newpuz: bytes32, pubkey: G1Element
) -> CoinSpend:
    """
    Create a CoinSpend for a atestment
    :param parent_of_message: Parent coin ID
    :param recovering_coin: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: CoinSpend
    """
    puzzle = create_recovery_message_puzzle(recovering_coin, newpuz, pubkey)
    coin = Coin(parent_of_message, puzzle.get_tree_hash(), uint64(0))
    solution = Program.to([])
    return make_spend(coin, puzzle, solution)
