### Title
Forfeit discount for cooldown mWOMSV stakers is dead code, allowing 100% reward-rate farming throughout cooldown - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder` accrues `rewardPerToken` against the user's full `balanceOf()` (which is `MasterMagpie.stakingInfo` amount, mirroring the raw `mWomSV.balanceOf` that includes tokens in cooldown), exactly as the question states. Unlike its sibling `vlMGPBaseRewarder`, whose `_calExpireForfeit` calls `vlMGP.getRewardablePercentWAD(_account)` to discount rewards for accounts partially in cooldown, `mWOMSVBaseRewarder._calExpireForfeit` never calls `mWomSV.getRewardablePercentWAD(_account)` at all — it is dead code that always returns `forfeitAmount = 0`, so the intended forfeit is never applied at accrual or at claim time.

### Finding Description
`mWOMSVBaseRewarder.balanceOf()` reads the user's full staked amount from `MasterMagpie.stakingInfo`, which includes the portion of `mWomSV` currently in cooldown (since `mWomSV.balanceOf = getUserTotalLocked + getUserAmountInCoolDown`, `mWomSV.sol:101-103`), and this full balance is used both for `rewardPerToken` accrual (`_earned`, `_updateFor`) and `totalStaked()`-based reward-rate calculations: [1](#0-0) [2](#0-1) 

`mWomSV.sol` itself exposes `getRewardablePercentWAD(_user)`, which computes a time-weighted, linearly-decaying entitlement percentage for amounts in cooldown — i.e. the *intended* mechanism to discount a cooling-down user's reward entitlement: [3](#0-2) 

The analogous `vlMGPBaseRewarder._calExpireForfeit` correctly applies this discount at claim time by calling `vlMGP.getRewardablePercentWAD(_account)` and computing `forfeitAmount = _amount - (_amount * rewardablePercentWAD / 1e18)`: [4](#0-3) 

However, `mWOMSVBaseRewarder._calExpireForfeit` never calls `mWOMSV.getRewardablePercentWAD(_account)`. It sets `rewardableAmount = _amount` unconditionally, so `forfeitAmount = _amount - rewardableAmount` is always `0`: [5](#0-4) 

This is invoked from `_sendReward`, which is called on every `getReward`/`getRewards` claim path (gated only by `onlyMasterMagpie`, which any staker reaches through normal claim flows), and it never withholds/recycles any forfeit via `_queueNewRewardsWithoutTransfer`: [6](#0-5) 

Net effect: a user who starts cooldown (moving mWomSV from "locked" to "in cooldown" state, while their MasterMagpie `stakingInfo` amount and hence `balanceOf()` in the rewarder is unchanged) continues to accrue `rewardPerToken * balance` at 100% weight for the entire cooldown duration, and at claim time no forfeit percentage is ever deducted — unlike the vlMGP path where the discount is (at least) applied at claim time. No existing modifier (`onlyManager`, `onlyMasterMagpie`, `nonReentrant`, `updateReward`) prevents this since the bug is a logic/computation defect, not an access-control gap.

### Impact Explanation
This causes permanent dilution of reward-per-token owed to fully-locked (non-cooldown) mWomSV stakers, since the reward pool's finite `rewardPerTokenStored` distribution is shared pro-rata by full raw balance including cooling-down amounts that should be discounted, and the intended forfeited share (which in the vlMGP design gets recycled back into the pool via `_queueNewRewardsWithoutTransfer`) is never recovered. This is a quantifiable theft/misallocation of unclaimed yield from honest long-term lockers to users who are mid-unlock, and it persists indefinitely since the defect is structural (not a one-off edge case). This matches the "theft or permanent freezing of unclaimed yield" Immunefi impact class.

### Likelihood Explanation
No special privileges, capital beyond normal staking, or complex setup are required. Any existing mWomSV staker (unprivileged EOA) can: stake mWom → convert to mWomSV → initiate cooldown/unlock (a normal public function) → continue calling `getReward`/`getRewards` throughout the entire cooldown window and receive full, undiscounted reward accrual. This is 100% reproducible and repeatable by any staker, and the loss to other stakers accumulates continuously with each reward distribution cycle over the cooldown period. Likelihood is high given it triggers on ordinary user action.

### Recommendation
Fix `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder._calExpireForfeit`: call `mWOMSV.getRewardablePercentWAD(_account)`, compute `rewardableAmount = _amount * rewardablePercentWAD / 1e18`, and derive `forfeitAmount = _amount - rewardableAmount` (with the existing dust-ignore threshold), then route `forfeitAmount` back into the pool via `_queueNewRewardsWithoutTransfer` as already wired in `_sendReward`.

### Proof of Concept
Foundry/Hardhat test plan:
1. Deploy `mWomSV`, `MasterMagpie`, and `mWOMSVBaseRewarder`; register a reward token.
2. User A locks `1000 mWomSV` (fully locked, not in cooldown); User B locks `1000 mWomSV` then immediately calls the unlock/cooldown-start function for the full amount (moving to `amountInCoolDown`, `mWomSV.getUserAmountInCoolDown(B) == 1000`, `getUserTotalLocked(B) == 0`).
3. Confirm via `MasterMagpie.stakingInfo(mWomSV, B)` that B's staked amount used by `mWOMSVBaseRewarder.balanceOf(B)` is unchanged at `1000` (i.e., includes the cooldown amount).
4. Fund the rewarder with `queueNewRewards(1000e18, rewardToken)`; assert `rewardPerToken` increases proportionally to `totalStaked()` (2000).
5. Immediately (block.timestamp == cooldown start) call `getReward` for both A and B; assert `earned(A) == earned(B)` (both receive 50% of rewards) despite B having 0% "fully rewardable" entitlement per `getRewardablePercentWAD` (expected near 0 at cooldown start under intended design).
6. Compute expected entitlement for B using `mWomSV.getRewardablePercentWAD(B)` and assert `toSend` in `_sendReward` for B should equal `earned(B) * rewardablePercentWAD / 1e18`, but actual code yields `toSend == earned(B)` (no forfeit), proving the discount is never applied.
7. Assert `forfeitAmount == 0` always from `_calExpireForfeit`, and that `_queueNewRewardsWithoutTransfer` (ForfeitRewardAdded event) is never emitted for `mWOMSVBaseRewarder`, contrasting with an equivalent `vlMGPBaseRewarder` test where a nonzero forfeit is correctly withheld and recycled.

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```

```text
    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
```
