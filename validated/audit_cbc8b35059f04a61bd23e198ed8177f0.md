### Title
Cross-Context Data Leakage via Shared Mutable Validation Fields on `*Transaction` - (File: blockchain/types/transaction.go)

### Summary
`Transaction` caches its per-validation-context results (`validatedSender`, `validatedFeePayer`, `validatedGas`) as instance fields directly on the transaction object rather than isolating them to the specific execution/validation call, guarded only by a single `mu sync.RWMutex` shared across all readers/writers of that object. [2](#0-1) 

### Finding Description
`AsMessageWithAccountKeyPicker` sets `tx.validatedSender`/`tx.validatedFeePayer`/`tx.validatedGas` on the `*Transaction` receiver itself as a side effect of message construction. [3](#0-2) 
Because a given `*Transaction` pointer is shared across multiple concurrent consumers — the tx pool's `all *txLookup`/`pending`/`queue` maps, the gasless module's `PostReset`/`isReady` checks over `knownTxs`, block execution/validator speculative execution (`ExecuteTransactions`), and RPC-facing paths (`ApplyTransaction`, `DoCall`, tracer APIs) — the same object can be validated concurrently against different `StateDB`/block-number contexts. [4](#0-3) [5](#0-4) 
Each call to `AsMessageWithAccountKeyPicker`/`ValidateSender`/`ValidateFeePayer` mutates the shared fields under `tx.mu`, but the *value* observed by any concurrent caller between its own write and its own subsequent read can be overwritten by another goroutine's concurrent validation for a completely different execution context (e.g., a different `AccountKeyPicker`/StateDB reflecting a different block state, or a re-validation during pool reset vs. block application). This mirrors the CVE-2026-63175 pattern exactly: state that should be scoped to one "capture"/validation call is instead stored mutably on a shared, reused object, so results (here, the resolved fee payer and sender addresses used to actually execute the transaction) from one context can bleed into another concurrent context.

### Impact Explanation
If a concurrent read of `validatedFeePayer`/`validatedSender` observes a value written by a different, unrelated validation pass (e.g., due to a race between the tx pool's `AddRemote` validation and the block-building `ApplyTransaction`/`ExecuteTransactions` path, or a gasless-module concurrent nonce/executability check), a transaction could be executed with a fee payer address or sender address that does not correspond to the current validation context. This can misattribute fee payment (fee-delegation abuse — one user's transaction billed to/executed with another's fee payer context) or cause incorrect sender attribution for a Kaia-specific fee-delegated transaction type, resulting in unauthorized value movement or fee-delegation abuse consistent with the Medium severity bucket the report targets.

### Likelihood Explanation
The codebase's own regression test, `TestRaceAsMessageWithAccountPickerForFeePayer`, demonstrates the maintainers were specifically concerned about "a fee payer may be inserted wrongly due to concurrent issue" for this exact code path, and constructs 10,000 concurrent iterations of two goroutines calling `AsMessageWithAccountKeyPicker` on the same shared object to check for corruption. [6](#0-5) 
This confirms the shared-mutable-field pattern is a known race-prone design; whether it is *fully* closed today depends on `tx.mu` correctly serializing all call sites (pool re-validation, gasless module, block execution, RPC) end-to-end, which was not fully verifiable from the available code slices in this session.

### Recommendation
Do not store per-validation-context results (`validatedSender`, `validatedFeePayer`, `validatedGas`) as mutable fields on the shared `*Transaction` object. Instead, return these as part of the `Message`/local result value from `AsMessageWithAccountKeyPicker` without mutating the source `Transaction`, or key any necessary cache by `(stateRoot/blockNumber, txHash)` so concurrent validations against different contexts cannot overwrite each other's results.

### Proof of Concept
Not independently reproduced beyond the codebase's own existing race test; `tests/race_test.go`'s `TestRaceAsMessageWithAccountPickerForFeePayer` already exercises two goroutines concurrently calling `tx.AsMessageWithAccountKeyPicker` on the same `*Transaction` with different `StateDB` snapshots and asserts `msg.ValidatedFeePayer()` remains correct — indicating the exact race condition class described above was previously observed/tested against this code path. [7](#0-6)
