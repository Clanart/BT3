### Title
Empty aggregate Schnorr signatures verify as valid - (File: crypto/schnorr/src/aggregate.rs)

### Summary

`SchnorrAggregate::read` accepts an aggregate containing zero `R` values, and `SchnorrAggregate::verify` treats an empty aggregate over an empty challenge list as valid when `s = 0`. This is analogous to assuming a header exists: the verifier assumes at least one statement is present and reduces verification of the empty statement to checking `0 * G == identity`.

### Finding Description

`SchnorrAggregate::read` reads a four-byte count and accepts `0` without requiring at least one signature. It then reads only `s`. [1](#0-0) 

During verification, matching `self.Rs.len()` against `keys_and_challenges.len()` permits both lists to be empty. The loop then adds no `R`/public-key statements, leaving only `(-self.s, C::generator())`. [2](#0-1) 

For the serialized empty aggregate with `s = 0`, that sole statement is `0 * G = identity`, so `multiexp_vartime(&pairs).is_identity()` returns true. [3](#0-2) 

Notably, the aggregation API explicitly refuses to produce an empty aggregate, but the verifier does not apply the same minimum-size invariant to deserialized aggregates. [4](#0-3) 

### Impact Explanation

An attacker can supply a syntactically valid serialized aggregate signature that verifies without proving possession of any private key or producing any component Schnorr signature. Any caller that invokes `verify` with an attacker-influenced empty expected-signature/challenge set can accept a forged aggregate signature for that batch.

This is not merely a vacuous mathematical result: the API exposes a signature object and returns `true`, while the signer-side aggregator intentionally treats zero signatures as unrepresentable. The verifier therefore accepts a signature encoding the signer side refuses to construct.

### Likelihood Explanation

Reachability requires an application to call `SchnorrAggregate::verify` with an empty `keys_and_challenges` list and attacker-controlled aggregate bytes. That can occur when the list is derived from a batch/session/transcript that ended up empty rather than being independently required to be non-empty.

The malicious encoding is deterministic: a zero count followed by the canonical encoding of scalar zero. No secret, curve relation, collision, malformed encoding, or privileged position is required. The practical severity is Medium because exploitation also depends on the caller allowing an empty expected-signature set to reach the verifier.

### Recommendation

Reject empty aggregates in `SchnorrAggregate::verify` before comparing lengths:

```rust
if self.Rs.is_empty() || self.Rs.len() != keys_and_challenges.len() {
  return false;
}
```

Optionally reject `Rs.is_empty()` in `SchnorrAggregate::read` as well, matching `SchnorrAggregator::complete`, so deserialization cannot construct a signature state that verification must specially handle.

### Proof of Concept

For a ciphersuite whose scalar serialization length is `SCALAR_LEN`, construct:

```text
aggregate_bytes =
  00 00 00 00                         // zero Rs
  || canonical encoding of scalar 0   // s = 0
```

Then:

```rust
let mut bytes = aggregate_bytes.as_slice();
let aggregate = SchnorrAggregate::<C>::read(&mut bytes).unwrap();

assert!(aggregate.verify(b"application-dst", &[]));
```

The verifier succeeds because it queues only `(-0) * G`, which is the identity.
