### Title
Quadratic CPU exhaustion in `ThresholdKeys` deserialization via attacker-controlled `t`/`n` — Lagrange interpolation is O(t²) over untrusted bytes - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::read` accepts untrusted bytes declaring threshold `t` and participant count `n` (both `u16`, up to 65535). `ThresholdKeys::new` then computes the group key by evaluating `interpolation_factor` for each of participants `1..=t`, and `Interpolation::Lagrange::interpolation_factor` itself loops over all `t` participants. The result is O(t²) field multiplications plus `t` field inversions — roughly 4.3 billion field multiplications and 65535 inversions at maximum `t` — triggered by deserializing only ~2 MB of attacker-controlled bytes. This is the Serai analog of the MongoDB `$trim` CPU-pinning bug: a small, well-formed input to an authenticated/unprivileged entry point causes CPU utilization to be pinned for an extended period.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i` directly from the byte stream with no cap other than `t <= n <= u16::MAX` (enforced in `ThresholdParams::new`), then reads `n` verification-share points and calls `ThresholdKeys::new` [1](#0-0) . Inside `ThresholdKeys::new`, the group key is computed as:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
``` [2](#0-1) 

For `Interpolation::Lagrange`, `interpolation_factor` performs a full inner loop over every element of `included` (here, all `t` participants), doing two field multiplications per element and one field inversion per call [3](#0-2) . Total work is therefore Θ(t²) field multiplications + Θ(t) inversions + Θ(t) point multiplications, all driven by two attacker-controlled `u16`s.

The same quadratic pattern is reachable at signing time through `ThresholdKeys::view`, which computes `interpolation_factor` once for the local secret share and again for every included signer's verification share — Θ(k²) field ops for a signing set of size `k` [4](#0-3) . `view` is invoked inside FROST `sign` whenever a participant signs with a given set, so any peer able to influence the signing set composition (e.g., by submitting preprocesses across a large validator set) amplifies the effect.

### Impact Explanation
An unprivileged party who can supply serialized `ThresholdKeys` (or otherwise induce deserialization of attacker-chosen `t`/`n`) causes the target to burn CPU proportional to the square of the declared participant count. At `t = n = 65535`, a single ~2 MB payload yields ~4×10⁹ field multiplications and 65535 sequential field inversions — minutes of a fully pinned core per request — with no memory blowup and no early-exit validation. Because the expensive path runs inside `read`/`new` before any semantic check on share validity, there is no cheap rejection. Repeated requests multiply the effect. This matches the reported bug class (post-auth CPU DoS via disproportionate work per input byte) and rates Medium.

### Likelihood Explanation
Requires an endpoint that feeds untrusted bytes to `ThresholdKeys::read` (or an attacker who can influence a multisig's `n` or the `included` set passed to `view`). The input is trivially constructed — no valid points or scalars are needed to reach the quadratic loop since the group-key computation precedes any proof-of-possession check, and `read` itself supplies all `n` points the attacker controls. Cost to the attacker is linear in bytes; cost to the victim is quadratic.

### Recommendation
- Cap `t`/`n` in `ThresholdParams::new` (e.g., a few hundred) — real validator sets are far smaller.
- Compute the group key via a single multiexponentiation/interpolation pass: batch the Lagrange denominators with one batch inversion (Montgomery trick) and accumulate numerators in O(t), turning group-key derivation into O(t log t) or O(t) instead of O(t²).
- In `ThresholdView`, compute all `interpolation_factor`s in one shared O(k) pass (prefix/suffix products) rather than a fresh O(k) loop per signer.
- Enforce a byte-size limit on inputs to `ThresholdKeys::read` so that `n` cannot exceed what the declared buffer plausibly contains before the O(t²) step runs.

### Proof of Concept
Construct a byte stream for `ThresholdKeys::<C>::read`:

```
u32 len(C::ID) || C::ID || t=0xFFFF || n=0xFFFF || i=0x0001 ||
interpolation tag = 1 (Lagrange) ||
32-byte secret_share ||
n × canonical encoded generator points
```

`ThresholdParams::new(65535, 65535, 1)` succeeds, `read` parses 65535 points (~2 MB total), and `ThresholdKeys::new` executes `interpolation_factor(i, [1..=65535])` for each of 65535 values of `i` — ~4.3×10⁹ field multiplications and 65535 inversions, pinning a core for minutes on a single request.
