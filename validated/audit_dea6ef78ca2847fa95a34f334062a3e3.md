## Analysis

I found a strong analog. The `reassembleResolvedFile` function in `app/src/lib/copilot-conflict-resolution.ts` reassembles a resolved file by walking the raw conflicted file content and splicing per-hunk AI resolutions in **by positional order, not by anchored identity** — the exact same broken-invariant pattern as the H-6 report (an "expected count/position" is assumed stable, but attacker-influenced content can desynchronize it, corrupting the trusted output silently).

### Title
Attacker-crafted conflict-marker-like lines in a merged branch desynchronize Copilot conflict reassembly, silently corrupting committed file content - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolvedFile` [1](#0-0)  walks the raw file content line-by-line and matches conflict blocks purely by regex on line prefixes (`<<<<<<<`, `=======`, `>>>>>>>`), splicing in the `hunkIndex`-th AI resolution for each block found — exactly analogous to HSG's assumption that "before" and "after" counts stay in lockstep. The function's own doc comment admits the resolutions are "matched by order, not by line number" [2](#0-1) . This ordering invariant can be desynchronized by content that an unprivileged party fully controls: the *incoming* branch/commit being merged (attacker-controlled fork, PR head, or fetched remote).

### Finding Description
The reassembly logic is:
1. Scan for a line matching `^<{7}(?:\s|$)` (the "ours" marker) [3](#0-2) .
2. Look ahead for a `=======` separator and a `>>>>>>>` closer to decide if it's a "well-formed" conflict block [4](#0-3) .
3. If well-formed, skip the whole block and splice in `hunkResolutions[hunkIndex]`, then increment `hunkIndex` [5](#0-4) .

The upstream code that builds `IFileConflictContext.hunks` (used to build the prompt and to validate hunk counts in `validateResolutionPaths`) presumably derives its count from `git`'s own conflict-hunk parsing. But `reassembleResolvedFile` re-derives conflict boundaries independently, from raw text, using only 7-character marker prefixes as its signal. If either side of the merge (a branch/commit/PR the user did not author, e.g. a forked PR head merged via Desktop, or content from a remote) contains **literal lines that happen to match the marker regexes** — for example a file that legitimately contains the strings `<<<<<<< HEAD`, `=======`, `>>>>>>> feature` as data (common in test fixtures, documentation about git conflicts, or diff/patch content embedded in a file) — this scanner will count a phantom or shifted conflict block that git's actual conflict-hunk count did not include.

This breaks the "N conflict hunks in equals N resolutions out" invariant that `validateResolutionPaths` enforces at the JSON level [6](#0-5) : that check only confirms the *counts* match between the model's raw hunk array and the *file-context* hunk count computed elsewhere — it does not confirm that `reassembleResolvedFile`'s independent, regex-based scan finds the same set/order of blocks in the raw text used for splicing. If the raw text contains an extra marker-like sequence not counted when building `IFileConflictContext.hunks`, `reassembleResolvedFile` will still find it, consume one entry from `hunkResolutions` for it, and this shifts every subsequent hunk's resolution by one position — silently splicing AI-generated resolution content for conflict *N* into the location of conflict *N+1* (or vice versa) for the remainder of the file, and/or dropping/duplicating a legitimate resolution.

Unlike HSG's Safe, where the mismatch causes a `revert`, here there is no post-hoc check that the reassembled output actually matches what the model believed it was resolving — the mismatched output is written to disk and can be committed as the merge resolution the user approves, unaware that a segment of one hunk's resolved code has silently landed in the wrong place in the file, or that trailing lines (including partially-resolved conflict content) end up interleaved incorrectly.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes," which is an explicitly valid impact category. The user believes they are committing the AI's evaluated resolution for each specific conflict, but the actual committed bytes can differ from what was reviewed/intended once counts desync, because the splice positions no longer correspond to the model's numbered hunks. In a security-sensitive file (e.g., an auth check, a dependency pin, a CI config) this could silently reintroduce vulnerable code, drop a fix, or merge attacker-supplied content into a location the user did not review as such.

### Likelihood Explanation
Requires an unprivileged party to control content that ends up as one side of a merge conflict Desktop processes with the Copilot conflict-resolution feature (e.g., a PR fork branch, a fetched remote branch) — squarely within the "attacker controls a cloned/fetched repository" scope. It also requires the user to actually invoke Copilot-assisted conflict resolution on that merge, and for the crafted lines to survive as raw hunk content that `reassembleResolvedFile` sees (i.e., not something git's own conflict marker generation already neutralizes). This is a real but non-trivial trigger condition — it depends on the feature being used and on the specific interplay between how `IFileConflictContext.hunks` is computed elsewhere versus this function's independent re-scan, which I was not able to fully verify due to the file being truncated by the index size limit before I could inspect the code that builds `IFileConflictContext`.

### Recommendation
Do not re-derive conflict block boundaries from raw text via marker regexes at splice time. Instead, have `reassembleResolvedFile` (or its caller) reuse the exact same hunk boundary data (`oursContent`/`theirsContent`/positions) that was used to build the prompt context for the model, so there is a single source of truth for what constitutes a "conflict hunk," and validate that the reassembly step finds exactly the same number of blocks as `IFileConflictContext.hunks.length` before splicing, failing closed (falling back to marking the file as skipped, per `ICopilotSkippedFile`) rather than silently proceeding on a mismatch.

### Proof of Concept
Conceptual PoC (not run against the app, since I could not execute code in this session):
1. Attacker opens a PR whose branch modifies a file to include literal text that matches the marker regexes as *data*, e.g. a Markdown/test file containing:
   ```
   <<<<<<< HEAD
   sample block
   =======
   sample block 2
   >>>>>>> feature
   ```
   as part of a code sample/documentation, not an actual git conflict.
2. The victim merges this branch locally in Desktop against a branch that has a real, unrelated conflict earlier in the same file, and invokes "Resolve with Copilot."
3. `IFileConflictContext.hunks` (built from git's real conflict-hunk parsing) reports N real hunks; the model returns N resolutions, and `validateResolutionPaths` accepts them because counts match against that N [6](#0-5) .
4. `reassembleResolvedFile`, however, scans the raw file text and additionally matches the attacker's literal `<<<<<<<`/`=======`/`>>>>>>>` lines as a well-formed conflict block, consuming one of the `hunkResolutions` entries for it and shifting the mapping for every subsequent real conflict block [7](#0-6) .
5. The final `resolvedContent` written to the file (and offered for commit) has the AI's per-hunk resolutions applied to the wrong locations, corrupting the merge result without any error surfaced to the user.

I could not fully verify how `IFileConflictContext.hunks` is computed (the file was truncated by the index before I reached that code), so I cannot confirm with certainty whether that upstream hunk-counting path is equally vulnerable to attacker-crafted marker-like content or uses a more robust boundary source; this is the main open uncertainty in the analysis.

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
