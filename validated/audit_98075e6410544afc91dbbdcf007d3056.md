### Title
Copilot merge-conflict resolution silently applies partial file writes to the working tree when staging fails mid-operation - ([File: app/src/lib/stores/app-store.ts])

### Summary
`_applyCopilotConflictResolutions` iterates over AI-generated conflict resolutions, writes each resolved file's content directly to disk with `writeFile`, and only afterwards runs a single `git add` over all successfully-written paths. There is no atomic guard: if any step after some files have already been written throws (a later `writeFile` failure, or the trailing `git add` failing/partially failing), the function throws and the caller aborts the merge continuation, but the files already overwritten on disk are never rolled back.

### Finding Description
In `_applyCopilotConflictResolutions`, the loop writes AI-resolved content to each conflicted file before any staging occurs: [1](#0-0) 

Only after the entire loop completes does the code run a single batched `git add`: [2](#0-1) 

There is no try/catch around the loop, no snapshot/rollback of previously-written file contents, and no re-verification that the files written in earlier iterations are still consistent with what actually got staged. The invariant that should hold — "either all Copilot resolutions are written to disk *and* staged together, or none are visibly applied to the working tree" — is broken. This mirrors the Cosmos EVM bug class: a multi-step state mutation (writing N files, then staging them) that is not wrapped in an atomic operation, so a failure partway through leaves committed-looking state (files with conflict markers replaced by unreviewed AI content) without the corresponding "commit" (staging) actually completing.

The call site treats any exception as an all-or-nothing failure and reverts UI state to "still resolving conflicts," which is misleading given the working directory has already been mutated: [3](#0-2) 

The only safety check present, `resolveWithin`, guards against path traversal outside the repository but does nothing to protect against partial application of writes: [4](#0-3) 

### Impact Explanation
Because the merge/rebase/cherry-pick flow assumes the "Continue" step either fully succeeds or fully fails, a partial failure (e.g., a permissions error, disk-full condition, or `git add` failing on a lock file after several `writeFile` calls already completed) leaves some working-directory files silently replaced with AI-resolved content that was never reviewed or staged, while the dialog reports the operation as not-yet-continued. If the user retries or manually resolves the merge afterward, they may unknowingly commit/push files whose content was silently swapped to the Copilot resolution rather than the resolution they believe is in effect, since the working tree no longer reflects the original conflict markers the manual conflict UI expects to find. This is a silent corruption of what the user ultimately commits/pushes, matching the "Valid Impact" criteria for this exercise.

### Likelihood Explanation
This requires a merge/rebase/cherry-pick against a repository the attacker controls (to produce a conflict) plus a transient failure during the write/stage phase (disk error, filesystem permission issue, concurrent lock on `.git/index` from another process, or a large resolution set where an intermediate file becomes momentarily inaccessible). Triggering the write path itself only requires the user to have Copilot conflict resolution enabled and to click "Continue" — no unnatural steps are needed. However, deterministically forcing the mid-loop failure (as opposed to relying on incidental I/O errors) is not fully demonstrated from static code alone, so likelihood is moderate rather than certain.

### Recommendation
Wrap the write-then-stage sequence in `_applyCopilotConflictResolutions` so it is atomic: buffer resolved contents, write them to temp files first, and only rename/overwrite the real paths and run `git add` if every write succeeded; on any failure, roll back any files already written back to their pre-resolution (conflicted) content before surfacing the error, so the working tree state matches what the UI reports to the user.

### Proof of Concept
1. Set up a repository with multiple files that conflict during a rebase, enable Copilot conflict resolution, and let it generate resolutions for files `a`, `b`, `c`.
2. Click "Continue" so `_applyCopilotConflictResolutions` begins writing: `a` and `b` succeed via `writeFile`.
3. Induce a failure before/at `c` (e.g., make the file read-only, or interrupt disk I/O) so `writeFile` throws for `c`, or make the subsequent `git add` fail (e.g., another process holds `.git/index.lock`).
4. Observe: files `a` and `b` on disk now contain Copilot's resolved content (conflict markers gone) but were never staged (since the failure occurred before or during the trailing `git add`), while the dialog reports the merge as still unresolved and reverts to the manual conflicts view — the working tree state is silently inconsistent with what the UI and git index report.   public async _applyCopilotConflictResolutions(
    repository: Repository
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    const { multiCommitOperationState } = state
    if (multiCommitOperationState === null) {
      return
    }

    const { copilotResolutions, step } = multiCommitOperationState
    if (copilotResolutions === null || copilotResolutions.length === 0) {
      return
    }

    // Respect any manual overrides the user chose in the result dialog
    const manualResolutions =
      step.kind === MultiCommitOperationStepKind.ShowCopilotConflicts
        ? step.conflictState.manualResolutions
        : new Map<string, ManualConflictResolution>()

    this.statsStore.increment('copilotConflictResolutionAcceptedCount')
    if (manualResolutions.size > 0) {
      this.statsStore.increment('copilotConflictResolutionWithOverridesCount')
    }

    const pathsToStage: string[] = []

    for (const resolution of copilotResolutions) {
      if (manualResolutions.has(resolution.path)) {
        continue
      }

      // Delete-vs-modify conflicts are resolved by setting a manual
      // resolution (ours/theirs) rather than writing file content.
      // The existing stageManualConflictResolution flow handles the
      // actual git checkout --ours/--theirs and staging at commit time.
      if (resolution.deleteConflictAction !== undefined) {
        const file = state.changesState.workingDirectory.files.find(
          f => f.path === resolution.path
        )
        if (file === undefined) {
          continue
        }
        const deletedSide = getDeletedSideFromStatus(file)
        if (deletedSide === undefined) {
          continue
        }
        // "keep" → choose the non-deleted side, "delete" → choose the deleted side
        const manualChoice =
          resolution.deleteConflictAction === 'keep'
            ? deletedSide === 'ours'
              ? ManualConflictResolution.theirs
              : ManualConflictResolution.ours
            : deletedSide === 'ours'
            ? ManualConflictResolution.ours
            : ManualConflictResolution.theirs
        this._updateManualConflictResolution(
          repository,
          resolution.path,
          manualChoice
        )
        continue
      }

      const absolutePath = await resolveWithin(repository.path, resolution.path)
      if (absolutePath === null) {
        log.warn(
          `Copilot resolution skipped: path outside repository: ${resolution.path}`
        )
        continue
      }

      // If the user resolved this file externally (e.g. in their editor) while
      // the result dialog was open, git status will report it with no remaining
      // conflict markers. Overwriting it with Copilot's stored content would
      // silently clobber their work, so skip it and let their resolution stand.
      // This mirrors how the manual conflicts dialog determines a file is
      // resolved (`hasUnresolvedConflicts`).
      const onDiskFile = state.changesState.workingDirectory.files.find(
        f => f.path === resolution.path
      )
      if (
        onDiskFile !== undefined &&
        isConflictedFileStatus(onDiskFile.status) &&
        !hasUnresolvedConflicts(onDiskFile.status)
      ) {
        continue
      }

      await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
      pathsToStage.push(resolution.path)
    }

    if (pathsToStage.length > 0) {
      await git(
        ['add', '--', ...pathsToStage],
        repository.path,
        'copilotConflictResolution'
      )
    }
  }

  private onContinue = async () => {
    this.setState({ isContinuing: true })
    try {
      // Write Copilot resolutions to disk before continuing the operation.
