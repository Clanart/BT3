## Title
Silent remote-URL rewrite after GitHub repo owner/name reassociation lets an attacker hijack push/fetch targets - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The C4 report describes a broken authorization invariant: the `builder` identity in Rigor is fixed at project creation and never re-derived from the actual NFT owner, so ownership and privilege silently diverge with no re-binding mechanism. The closest reachable Desktop analog is a similar "stale identity, silently re-trusted" pattern: Desktop associates a local `GitHubRepository` record by `(ownerID, name)` rather than GitHub's immutable numeric repository id, and then uses that association to silently rewrite the user's local git `origin` remote URL to whatever the GitHub API currently reports for that `(owner, name)` pair, with no user confirmation.

### Finding Description
`RepositoriesStore._upsertGitHubRepository` looks up (and reuses) the local `GitHubRepository` record purely by the composite key `[ownerID+name]`: [1](#0-0) 
It never checks GitHub's numeric repository `id` to confirm the record still refers to the *same* underlying repository. If the original repo at `owner/name` is deleted, renamed away, or transferred, and a different actor later creates/controls a *new* repository at that exact same `owner/name` path, the next refresh will treat it as a continuation of the previously tracked repo and overwrite `cloneURL`/`htmlURL` with the new repository's data: [2](#0-1) 

This refresh path is driven by `repositoryWithRefreshedGitHubRepository`, which calls `api.fetchRepository(owner, name)` (an authenticated, but URL/name-keyed lookup) and then calls `updateRemoteUrl`: [3](#0-2) 

`updateRemoteUrl` will silently `git remote set-url` the local `origin` to the new `clone_url` value returned by the API, as long as the protocol matches and the previously cached remote URL still matched the old cached `cloneURL` — it performs no ownership/identity check beyond string/host/owner/name comparison: [4](#0-3) 

Because the matching key is `(owner, name)` and not GitHub's stable repository id, this "auto-heal the remote when the repo moved" feature (intentionally added for legitimate renames, per changelog entry #8590) cannot distinguish "the same repository was renamed" from "a different, attacker-controlled repository now occupies the same owner/name slot." No guard rail (e.g., comparing GitHub's numeric `id` before trusting the new `clone_url`) exists to stop the second case. [5](#0-4) 

### Impact Explanation
If exploited, a user's local git configuration is silently rewritten so that subsequent `git push`/`git fetch` operations transparently target an attacker-controlled repository instead of the one the user originally cloned. This is a silent corruption of what the user pushes (their code/history could be exfiltrated to, or replaced with fetched content from, an attacker's repository) without any dialog, warning, or confirmation shown to the user — this falls squarely under the in-scope "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Exploitation requires: (1) an existing Desktop user tracking a repository at `owner/name`, (2) that original repository becoming unavailable at that path (deleted, or the user losing/renaming rights) and (3) an attacker being able to create/control a different repository re-using the exact same `owner/name` slug (e.g., via a squatted/reused personal repo name, an org repo deleted and slug reused by another org member, or a GitHub Enterprise instance where slug reuse is easier to arrange). This is a real-world reachable scenario but not always fully attacker-controlled end-to-end (name squatting timing depends on GitHub allowing reuse), so likelihood is moderate rather than trivial.

### Recommendation
- Track and match `GitHubRepository` records by GitHub's immutable numeric `id` in addition to (or instead of) `(ownerID, name)`.
- Before calling `updateRemoteUrl` to rewrite a local remote, verify the numeric `id` of the freshly fetched `apiRepo` matches the previously stored id for that `GitHubRepository` record; if it differs, treat it as a new/foreign repository and prompt the user rather than silently rewriting the remote.
- Consider surfacing a confirmation dialog any time Desktop automatically changes a remote URL, rather than performing it silently.

### Proof of Concept
1. User clones `https://github.com/victim-org/renamed-repo` in Desktop; Desktop stores a `GitHubRepository` DB row keyed by `(ownerID=victim-org, name=renamed-repo)` with `cloneURL` pointing at the legitimate repo.
2. The legitimate `victim-org/renamed-repo` repository is later deleted (or its slug becomes free some other way).
3. An attacker creates a new repository `victim-org-attacker-controlled/renamed-repo` is not directly possible unless attacker controls `victim-org` itself or an org member frees/renames a repo and an attacker (e.g. a malicious org collaborator) recreates a repository under the same `owner/name`.
4. On next repository refresh, `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository('victim-org', 'renamed-repo')`, which now resolves to the attacker's new repository object (different numeric `id`, different `clone_url`).
5. `_upsertGitHubRepository` matches the existing DB row by `(ownerID, name)` [1](#0-0)  and overwrites `cloneURL`/`htmlURL` with the attacker repository's values.
6. `updateRemoteUrl` sees `remoteUrlUnchanged` is true (local remote still equals the old cached `cloneURL`) and `urlsMatch` is false (new API `clone_url` differs), and protocols match, so it silently calls `gitStore.setRemoteURL('origin', updatedRemoteUrl)` [6](#0-5) , pointing the user's `origin` at the attacker's repository without any prompt.
7. The user's next `git push` sends their commits to the attacker's repository, or a `git fetch`/pull pulls attacker-supplied history/content into the user's working copy.

Note: Full exploitability depends on GitHub.com/GHE's actual name-reuse/redirect semantics for deleted or renamed repositories, which could not be verified from the local code alone; this should be validated experimentally (e.g., via a Devin session with live GitHub API access) before treating this as a confirmed, fully attacker-triggerable primitive.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
```
