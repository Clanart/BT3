### Title
Webhook `shop_domain` is read from an unverified header while HMAC binds only to the app secret, not the shop — enabling cross-shop webhook spoofing - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#shop_domain` returns the raw `X-Shopify-Shop-Domain` request header without any cryptographic binding to the verified payload. Since `hmac_valid?` in `PayloadVerification` validates the body against a single app-wide secret (`ShopifyApp.configuration.secret`/`old_secret`) shared by every shop using the app, a request with a validly-signed body (from any shop) can have its shop-domain header swapped, causing the webhook to be processed under an attacker-chosen shop.

### Finding Description
`verify_request` in `lib/shopify_app/controller_concerns/webhook_verification.rb` only checks `hmac_valid?(request.raw_post)`: [1](#0-0) 

`hmac_valid?` (in `PayloadVerification`) computes `HMAC-SHA256(secret, raw_post)` using the single app secret configured for the whole app (not a per-shop secret) and compares it to the `X-Shopify-Hmac-Sha256` header: [2](#0-1) 

`shop_domain` simply returns the unauthenticated header value with no relation to the signed body: [3](#0-2) 

The documented custom-controller pattern explicitly trusts this method to select the tenant for job dispatch: [4](#0-3) 

Because the app secret is identical for every shop installed on the app, any body+HMAC pair that validates for shop A also validates unchanged for shop B (the HMAC never includes the shop domain). An attacker who can obtain one validly signed webhook body (e.g., from their own shop's webhook deliveries, which they legitimately receive) can replay that exact body to the app's webhook endpoint while setting `X-Shopify-Shop-Domain` to a victim shop's domain. `verify_request` passes (HMAC checks out against the app secret), and any custom controller/job using `shop_domain` will process/store the replayed payload under the victim's tenant.

Note: the built-in `ShopifyApp::WebhooksController#receive` [5](#0-4)  delegates to `ShopifyAPI::Webhooks::Registry.process`, which is external gem code not in this repo and may perform its own shop derivation; the exposed, documented `shop_domain` method is directly reachable by any app that follows the `CustomWebhooksController` pattern shown in the docs.

### Impact Explanation
This allows cross-shop data confusion: a webhook payload legitimately signed by the app (for any tenant) can be redirected to be processed as if it belongs to a different shop, causing incorrect data to be written/attributed to an unrelated shop's records via the enqueued job (`shop_domain: shop_domain`). This matches Shopify's "Cross-shop / cross-tenant data exposure via forged webhook request" impact class, since no cryptographic binding exists between the verified payload and the tenant identifier used to route it.

### Likelihood Explanation
The precondition — possession of one validly HMAC-signed webhook body — is trivially satisfiable: an attacker's own shop (as a legitimate merchant with the app installed) will receive real webhooks signed with the same shared app secret, or a public test fixture/sample payload with a known signature could be reused. Because the secret is per-app rather than per-shop, forging a "victim domain" header on a replayed body requires no additional secret knowledge, making this fully repeatable by any unprivileged attacker who is a merchant with the app installed.

### Recommendation
Do not trust `request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]` as the tenant identifier. Derive the shop from data cryptographically bound to the verified request (e.g., extract and validate the shop from the parsed webhook body/topic via the `shopify_api` gem's `ShopifyAPI::Webhooks::Request`, which associates registered handlers with verified webhook metadata), or additionally verify that the header-provided shop domain corresponds to a shop with an existing, valid session/installation before using it to key any data writes. At minimum, document/require downstream job implementations to independently validate that `shop_domain` corresponds to an installed shop before trusting it for tenant-scoped writes.

### Proof of Concept
```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: params.except(:controller, :action).to_h)
    head :no_content
  end
end
```

```ruby
test "hmac validity does not bind to the shop domain header" do
  body = '{"foo":"bar"}'
  hmac = Base64.strict_encode64(
    OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyApp.configuration.secret, body)
  )

  # Attacker replays a validly-signed body but swaps the shop domain header
  post "/webhooks/carts_update",
    params: body,
    headers: {
      "CONTENT_TYPE" => "application/json",
      "HTTP_X_SHOPIFY_HMAC_SHA256" => hmac,
      "HTTP_X_SHOPIFY_SHOP_DOMAIN" => "victim-shop.myshopify.com", # attacker-chosen, unrelated to signer
    }

  assert_response :no_content # verify_request passes: HMAC only checks the app-wide secret
  # SomeJob is enqueued with shop_domain: "victim-shop.myshopify.com" despite the body
  # not originating from, nor being bound to, that shop.
end
```

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
