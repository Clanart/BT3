### Title
Unbounded participant count causes quadratic CPU exhaustion in threshold-key deserialization - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::read` accepts an attacker-controlled `n`/`t` pair and, for Lagrange interpolation, `ThresholdKeys::new` derives the group key by evaluating an O(t²) interpolation factor for every participant. A serialized key declaring `t = n = 65535` requires only about 2 MiB of input but causes billions of scalar operations and tens of thousands of scalar inversions and point multiplications.

### Finding Description
The deserializer reads `t`, `n`, and `i` directly from the input and then reads one verification share for each participant. [1](#0-0)  It then calls `ThresholdKeys::new`, which creates the participant list `1..=t` and calls `interpolation_factor` for each member. [2](#0-1)  For `Interpolation::Lagrange`, each `interpolation_factor` call loops over all included participants, making the total work quadratic in `t`. [3](#0-2)  `ThresholdParams::new` permits any nonzero `t <= n`, so `t = n = 65535` is accepted. [4](#0-3) 

### Impact Explanation
An unprivileged party supplying bytes to `ThresholdKeys::read` can cause CPU exhaustion with a relatively small serialized object. Repeated submissions can keep processors occupied long enough to delay or prevent threshold operations.

### Likelihood Explanation
The input format is attacker-controlled and does not impose a lower practical maximum participant count or bound the interpolation cost. The payload consists of approximately 65,535 compressed points plus a small header, while the resulting Lagrange work is approximately `65,535²` scalar operations.

### Recommendation
Reject serialized `ThresholdParams` above a deployment-specific maximum `n`, or perform Lagrange group-key derivation in O(t) after validating participant indexes. Alternatively, decode under a byte/time budget before constructing `ThresholdKeys`.

### Proof of Concept
```rust
use ciphersuite::{group::{ff::PrimeField, GroupEncoding}, Ciphersuite};
use dkg::{Participant, ThresholdKeys};
use frost::curve::Secp256k1 as C;

let mut bytes = Vec::new();
bytes.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
bytes.extend(C::ID);
bytes.extend(65535u16.to_le_bytes()); // t
bytes.extend(65535u16.to_le_bytes()); // n
bytes.extend(Participant::new(1).unwrap().to_bytes()); // i
bytes.push(1); // Interpolation::Lagrange
bytes.extend(<C as Ciphersuite>::F::ONE.to_repr().as_ref());
for _ in 0 .. 65535 {
  bytes.extend(C::generator().to_bytes().as_ref());
}

// Accepted as parameters, then performs O(t^2) Lagrange interpolation work.
let _ = ThresholdKeys::<C>::read(&mut bytes.as_slice());
```

The attack input is approximately `(65,535 * point_size)` bytes, yet it triggers billions of scalar field operations plus 65,535 inversions and point multiplications.
