### Title
CR-CAT holders are permanently unable to spend or redeem their tokens once their credential (VC) is revoked or de-authorized - (File: `chia/wallet/vc_wallet/cr_cat_wallet.py`)

### Summary
CR-CATs (credential-restricted CATs) require a valid `VerifiedCredential` (VC) issued by an authorized DID provider to be presented at spend time. The wallet-side spend-building logic (`_generate_unsigned_spendbundle` and `claim_pending_approval_balance`) unconditionally looks up a matching VC via `get_vc_with_provider_in_and_proofs` and hard-fails if none is found. If the DID provider revokes the user's VC (via `revoke_vc`/`activate_backdoor`) after the user already legitimately holds CR-CAT coins, the user has no path to move, sell, or "redeem" (convert back / spend) those already-held coins, since every future spend of that coin also requires a currently valid VC satisfying the same `authorized_providers`/`proofs_checker` constraints baked into the coin's puzzle. This mirrors the reported UXD issue: a check meant to gate *new* deposits/mints instead blocks *existing* holders from ever exiting their position once whitelist status is revoked.

### Finding Description
`CRCATWallet._generate_unsigned_spendbundle` fetches the CR-CAT's inner spend requirements, then requires a VC: [1](#0-0) 
and raises if none is found: [2](#0-1) 

Similarly, `claim_pending_approval_balance` — used to pull CR-CAT coins out of the "pending approval" puzzle state into the owner's normal balance — requires a VC: [3](#0-2) 

The VC itself can be revoked unilaterally by the DID provider that issued it, via `VCWallet.revoke_vc`, which spends the VC through its backdoor/revocation layer: [4](#0-3) 
using `VerifiedCredential.activate_backdoor`: [5](#0-4) 

The set of `authorized_providers` and the `proofs_checker` are permanently curried into the CR-CAT puzzle at mint time and are copied unchanged to every child coin on every subsequent spend: [6](#0-5) [7](#0-6) 

Because these parameters can never be changed for an already-minted CR-CAT lineage, the *only* way to satisfy the CR layer's solution requirements is to always present a currently-valid VC from one of the originally authorized providers with matching proofs (`get_vc_with_provider_in_and_proofs`): [8](#0-7) 

If that VC is revoked (or the provider's DID is later transferred/burned so no future VC can be re-issued with a live provider), the wallet code has no fallback: it simply raises and the coin can never again be included in a valid spend bundle. There is no exception path in `_generate_unsigned_spendbundle` or `claim_pending_approval_balance` analogous to the UXD report's request to "remove the check" for holders who already legitimately acquired the asset before revocation.

### Impact Explanation
A user who legitimately acquired CR-CAT tokens while properly credentialed can be permanently locked out of their own funds if the issuing DID provider revokes their VC (a normal, provider-controlled action documented and tested in `test_vc_wallet.py`'s `test_self_revoke`/VC revoke flows). Because the `authorized_providers` list is immutable per CR-CAT lineage, there is no way to obtain a new valid VC that satisfies the exact currently-required provider set once revoked (or once the provider DID itself is destroyed/transferred away, as also demonstrated in `test_self_revoke`). This is a direct denial-of-funds-movement analogous to the reported "cannot redeem UXD once asset is de-whitelisted" bug — the check that was meant to gate authorization at transaction time instead traps already-held balances.

### Likelihood Explanation
This is reachable by any normal wallet user with no special privileges beyond having received CR-CAT coins and a VC — a completely standard flow supported by the wallet RPC (`vc_mint`, `vc_revoke`, CR-CAT transfers). The provider (DID holder) merely needs to call the already-implemented `vc_revoke` RPC/CLI (`RevokeVCCMD`) at will; no protocol violation or malicious peer is required — it is intended provider functionality being used in a way that traps user funds indefinitely.

### Recommendation
Provide CR-CAT holders an escape/redeem path that does not depend on a live, matching VC — e.g., a CAT "melt"/exit mechanism allowing conversion of a CR-CAT back to a plain asset (or direct XCH) once the on-chain provider list associated with the coin can be proven permanently unusable, or allow spends when the presented VC used to be valid at any point the coin was received (grandfathering), rather than requiring perpetual, currently-valid authorization for coins already held. At minimum, document this trust assumption prominently and require issuers to consider revocation impact on token holders' existing balances before revoking.

### Proof of Concept
1. DID `D` mints VC `V` for wallet `W` (`vc_mint`).
2. `W` receives CR-CAT coins whose puzzle curries `authorized_providers = [D]` (`CRCAT.launch`, `cr_cat_drivers.py:181-271`).
3. `W` legitimately holds/transfers CR-CATs, always presenting `V` per `_generate_unsigned_spendbundle` (`cr_cat_wallet.py:489-572`).
4. `D` calls `revoke_vc` (`vc_wallet.py:376-410`), spending `V` via `activate_backdoor` (`vc_drivers.py:757-798`); `V` is destroyed on-chain.
5. `W` now has CR-CAT coins whose puzzle still requires a VC from `authorized_providers=[D]`; `get_vc_with_provider_in_and_proofs` finds nothing (`vc_wallet.py:610-625`) and any subsequent spend attempt raises `RuntimeError: No VC exists that can approve spends for CR-CAT wallet ...` (`cr_cat_wallet.py:569-572`, `717-718`), permanently blocking `W` from moving or redeeming those coins.

```python
    async def get_vc_with_provider_in_and_proofs(
        self, authorized_providers: list[bytes32], proofs: list[str]
    ) -> VerifiedCredential:
        vc_records: list[VCRecord] = await self.store.get_vc_records_by_providers(authorized_providers)
        if len(vc_records) == 0:  # pragma: no cover
            raise ValueError(f"VCWallet has no VCs with providers in the following list: {authorized_providers}")
        else:
            for rec in vc_records:
                if rec.vc.proof_hash is None:
                    continue  # pragma: no cover
                vc_proofs: VCProofs | None = await self.store.get_proofs_for_root(rec.vc.proof_hash)
                if vc_proofs is None:
                    continue  # pragma: no cover
                if all(proof in vc_proofs.key_value_pairs for proof in proofs):
                    return rec.vc
        raise ValueError(f"No authorized VC has the correct proofs: {proofs}")  # pragma: no cover
```
