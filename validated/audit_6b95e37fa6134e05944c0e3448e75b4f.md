### Title
Missing slippage protection in `WombatPoolHelperV2.depositFor` due to hardcoded `_minimumLiquidity = 0` - (File: wombat/WombatPoolHelperV2.sol)

### Summary
`WombatPoolHelperV2.depositFor` is an externally callable, unprivileged entry point that lets any wallet deposit stable tokens into a Wombat pool on behalf of another user. Unlike the sibling `deposit` function, which forwards a caller-supplied `_minimumLiquidity` for slippage protection, `depositFor` hardcodes this parameter to `0` when calling the internal `_deposit` helper, which ultimately reaches `WombatStaking.deposit` and `IWombatPool.deposit`.

### Finding Description
`deposit(uint256 _amount, uint256 _minimumLiquidity)` correctly lets the caller specify a minimum acceptable liquidity/LP amount to protect against price manipulation: [1](#0-0) 

However, `depositFor(uint256 _amount, address _for)` ignores slippage entirely and passes a hardcoded `0` for `_minimumLiquidity`: [2](#0-1) 

This flows into `WombatStaking.deposit`, where the `_minimumLiquidity` value is forwarded unchanged to the underlying `IWombatPool.deposit` call, and the actual `lpReceived` (which determines how many receipt tokens are minted to the depositor) is entirely dependent on the pool's cash/liability ratio at execution time: [3](#0-2) 

Because `_minimumLiquidity` is forced to `0`, `IWombatPool.deposit` (per its own documentation, "ensuring minimum amount required") provides zero protection here, matching the exact bug class described in the external report — hardcoded zero-slippage parameters on external AMM/pool calls: [4](#0-3) 

### Impact Explanation
An attacker monitoring the mempool can sandwich a `depositFor` transaction: front-run it with a trade or deposit that skews the pool's cash/liability ratio unfavorably, let the victim's deposit execute and mint fewer LP/receipt tokens than they should for the stable amount deposited, then back-run to restore the ratio and capture the difference. This is a direct, silent loss of value for the depositing user's minted receipt/staking-token position — the victim permanently receives less than fair value with no revert or recourse, unlike `deposit`/`depositNative` which allow the caller to protect themselves.

### Likelihood Explanation
`depositFor` is a plain external function with no access control (any wallet can call it for themselves or any `_for` address), and requires no privileged role or admin misbehavior — only an attacker with mempool visibility and capital to manipulate the pool ratio, which is a standard, low-cost MEV/sandwich setup.

### Recommendation
Add a `_minimumLiquidity` (or `minLpOut`) parameter to `depositFor` so callers can supply their own off-chain-computed slippage tolerance, mirroring the existing `deposit` function, instead of hardcoding `0`.

### Proof of Concept
1. Attacker observes a pending `depositFor(amount, for)` transaction in the mempool.
2. Attacker front-runs with a large swap/deposit into the same Wombat pool to shift cash/liability ratio unfavorably for new depositors.
3. Victim's `depositFor` executes with `_minimumLiquidity = 0`, so `IWombatPool.deposit` accepts any `lpReceived` amount regardless of how small.
4. `lpReceived` is minted to the victim as receipt tokens via `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, lpReceived)` — fewer than a fair-price deposit would have produced.
5. Attacker back-runs to restore the pool ratio and withdraws the extracted value, profiting at the depositor's expense.
