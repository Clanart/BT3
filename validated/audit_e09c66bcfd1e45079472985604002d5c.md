### Title
Stale in-memory conflict/working-directory snapshot lets Copilot-resolved conflict content silently overwrite unrelated on-disk changes made during the async write loop - ([File: app/src/lib/stores/app-store.ts])

### Summary
This is the same bug class as the external report: a snapshot of state is taken once, then used to gate a batch of write operations that execute asynchronously over time, while the real state can keep changing underneath. `_applyCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts:7169-7269`) captures `state = this.repositoryStateCache.get(repository)` a single time at the top of the function [1](#0-0) , and then, for every file in `copilotResolutions`, uses that one stale `state.changesState.workingDirectory.files` snapshot to decide whether it's safe to overwrite the file on disk, before doing an `await writeFile(...)` per file in a loop [2](#0-1) .

### Finding Description
The function's own comment states the intent of the on-disk check explicitly:

> "If the user resolved this file externally (e.g. in their editor) while the result dialog was open, git status will report it with no remaining conflict markers. Overwriting it with Copilot's stored content would silently clobber their work, so skip it..." [3](#0-2) 

But the check is performed against `state.changesState.workingDirectory.files`, a single object captured once at function entry (line 7172), not a status re-read per iteration. The loop then `await`s a `writeFile` for every resolution (`app/src/lib/stores/app-store.ts:7258`), and each `await` is a yield point where the renderer's event loop can run other async work (including further `_loadStatus`/`getStatus` calls from background refresh, or the user editing/saving a file) — but even so, none of that would update the local `onDiskFile` lookup used inside this same loop, because it keeps re-reading the *same* captured `state` for every remaining file. This is structurally identical to the reported flaw: `batchRewardsSnapshot.js` takes one snapshot at `endBlock` and then keeps trusting it for actions that happen afterward, allowing state to drift from reality between snapshot time and the time the snapshot is acted upon.

The write path itself has no re-validation: `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` unconditionally overwrites whatever is on disk for that path once the (stale) guard passes, and the file is then staged with `git add` (`app/src/lib/stores/app-store.ts:7262-7267`). There is no re-check of file content/hash/mtime immediately before the write, and no re-fetch of `getStatus()` inside the loop.

Because Copilot's `resolution.resolvedContent` is derived from an LLM turn seeded with attacker-influenceable repository content (the conflicting hunks come from files in the cloned/fetched repository, per `buildConflictContext`/`copilot-conflict-context.ts`), a maliciously crafted merge conflict can bias the model's output, and this stale-snapshot guard is the only thing standing between that output and silently clobbering a file the user has legitimately resolved in parallel (e.g., in their editor) during the (potentially long, this flow explicitly tracks turns running "over 60s"/"over 120s", see `copilotConflictResolutionOver60sCount`/`Over120sCount` at `app/src/lib/stores/app-store.ts:7101-7106`) Copilot turn.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A conflict resolution result that the user believes reflects Copilot's proposal (or, for a file they specifically fixed themselves in the interim) can instead write model-generated content over the user's own already-resolved fix, and that corrupted content is then staged (`git add`) and can be committed/pushed without further warning — the check that exists is explicitly there to *prevent* exactly this outcome but is undermined by relying on a stale, one-time snapshot instead of live state.

### Likelihood Explanation
The Copilot conflict-resolution flow is explicitly designed around long-running asynchronous model turns (tracked metrics for turns lasting 60–120+ seconds), which gives a realistic window for the user to resolve a conflicted file themselves while the assistant is still working, and for the eventual multi-file write loop to iterate past the point where the snapshot was taken. No local/admin access or leaked credentials are required — only normal use of the feature on a repository containing merge conflicts, which is squarely within Desktop's threat model for "attacker-influenced repository content."

### Recommendation
Re-fetch the authoritative on-disk/git status immediately before each `writeFile` in the loop (or right before staging), rather than relying on a single `state` snapshot taken before the loop starts. At minimum, re-check `hasUnresolvedConflicts`/conflict-marker presence on the file's *current* content just before overwriting it, mirroring the intent already documented in the code, and abort/skip per-file if the live check disagrees with the initial snapshot.

### Proof of Concept
1. Start a merge/rebase with multiple conflicted files and enable Copilot conflict resolution; the SDK turn runs for an extended period (as anticipated by the 60s/120s telemetry).
2. While the turn is in progress, manually resolve one of the conflicted files (`fileA`) in an external editor, removing all conflict markers, and save.
3. When the Copilot result arrives, `_applyCopilotConflictResolutions` reads `state` once at the top of the function — this snapshot may already reflect `fileA` as no-longer-conflicted if a refresh has occurred, or may still show it as conflicted if no refresh happened between the manual edit and the click on "Continue Merge" — the timing depends entirely on unrelated background refresh cycles, not on a fresh, authoritative check tied to the write itself.
4. Because the guard at lines 7247-7256 only consults this single captured snapshot for every file in the loop, and the loop can take multiple `await writeFile` cycles, any file resolved manually in the window between the snapshot and its own iteration's write is not protected — its content is silently overwritten by `resolution.resolvedContent` and staged via `git add`.
