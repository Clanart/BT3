### Title
Empty-scope session bypasses forced re-authentication (`covers_scopes?` fails open) - ([File: lib/shopify_app/access_scopes/user_strategy.rb])

### Summary
`ShopifyApp::AccessScopes::UserStrategy.covers_scopes?` treats a session whose `scope` is empty as if it *covers* every currently configured access scope, which lets `ShopifyApp::LoginProtection#activate_shopify_session` skip the forced re-authentication / session-clearing step it is supposed to perform whenever a session's granted scopes don't match the app's configured scopes.

### Finding Description
`ShopifyApp::LoginProtection#activate_shopify_session` is the gate that runs before every authenticated action in apps using the legacy (non token-exchange) session flow: [1](#0-0) 

When `config.reauth_on_access_scope_changes` is enabled, it calls `user_access_scopes_strategy.covers_scopes?(current_shopify_session)` and, if it returns `false`, clears the session and redirects to login (forcing re-auth so a properly-scoped token can be obtained). The intent is: if the stored session's scopes don't cover what the app currently requires, don't let the request proceed with the old/insufficient token.

The implementation of that check is: [2](#0-1) 

```ruby
def covers_scopes?(current_shopify_session)
  # NOTE: this not Ruby's `covers?` method, it is defined in ShopifyAPI::Auth::AuthScopes
  current_shopify_session.scope.to_a.empty? || current_shopify_session.scope.covers?(ShopifyAPI::Context.scope)
end
```

This is the direct analog of the reported bug class: instead of validating the quantity/permission and rejecting a degenerate "zero" value, the code special-cases the empty/zero condition (`scope.to_a.empty?`) and short-circuits to `true` ("covers everything"), the opposite of a fail-safe/fail-closed check. Just as `sellForLP` computed `lpAmount = 0` from a zero price and let the burn proceed anyway (loss of funds without validation), `covers_scopes?` treats "no recorded scopes" as "all scopes granted" and lets the authenticated action proceed without forcing a scope-refresh, even though a session with an empty scope list is the one case that most obviously needs re-verification.

### Impact Explanation
If a stored `ShopifyApp::SessionRepository` session ends up with a blank/empty `scope` attribute — for example due to a session storage migration, a partially-populated custom session model, a race in session persistence, or any code path that stores a session before scopes are recorded — the app will treat that session as fully authorized for every scope currently configured (`ShopifyAPI::Context.scope`), rather than forcing the merchant through OAuth to obtain a session with the correct, currently-required scopes. This can let requests proceed using a session that does not actually carry the access rights the app assumes it has, defeating the purpose of `reauth_on_access_scope_changes` and `ShopAccessScopesVerification`/`covers_scopes?` scope enforcement.

### Likelihood Explanation
This is not directly triggerable by an anonymous internet request with arbitrary input (the `scope` value comes from the persisted session, not a request parameter), so it requires an existing session record with an empty `scope` to exist. That said, it is a straightforward "fail open on empty/zero value" logic defect in a security-relevant authorization check, matching the reported bug class exactly (fail open when a security-relevant quantity is zero/absent), and it silently defeats the app's designed enforcement of access-scope changes whenever it triggers.

### Recommendation
Change `covers_scopes?` to fail closed instead of fail open when the session has no recorded scopes:
```ruby
def covers_scopes?(current_shopify_session)
  return false if current_shopify_session.scope.to_a.empty?
  current_shopify_session.scope.covers?(ShopifyAPI::Context.scope)
end
```
This forces re-authentication whenever scope information is missing, consistent with the "reject zero/degenerate value" remediation applied to the referenced `setPrice`/`sellForLP` bug.

### Proof of Concept
1. Configure an app with `config.reauth_on_access_scope_changes = true` and a non-empty `ShopifyAPI::Context.scope` (e.g. `read_products`).
2. Persist (or otherwise obtain) a `ShopifyApp::SessionRepository` session for a shop/user whose `scope` attribute is empty/blank (e.g. `ShopifyAPI::Auth::Session.new(shop: ..., access_token: ..., scope: nil)`).
3. Make a request to a controller including `ShopifyApp::LoginProtection` with that session active.
4. Observe `covers_scopes?` returns `true` at [2](#0-1)  so `activate_shopify_session` at [1](#0-0)  does not clear the session/redirect to login, and the action executes with a session that was never verified to actually hold the configured scopes.
