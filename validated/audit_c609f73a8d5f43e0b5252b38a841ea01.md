The kernel bug is a refcount bumped on a failing path — a resource acquired before validation, never rolled back. I need an in-scope analog in the crypto crates. Checking the batch verification and nonce derivation paths for state mutated before a fallible check.### Title
FROST preprocess seed is reused after a failed `sign()` attempt, enabling private key share recovery - (File: crypto/frost/src/sign.rs)

### Summary

The kernel bug class is "a resource is acquired/bumped before a fallible operation and never released on the error path" (`pm_runtime_get_sync` increments the refcount even when it fails). In Serai, the same shape exists in the FROST signing state machine: a preprocess seed is generated once, persisted to disk, and `sign()` is a fallible operation. When `sign()` fails (e.g., because an unauthenticated-bytes peer preprocess is malformed or invalid), the error path does not rotate or invalidate the persisted seed. The next attempt calls `from_cache`, which deterministically regenerates the **identical** nonce pair `(d, e)` — a classic nonce-reuse condition that leaks the signer's private key share.

### Finding Description

`AlgorithmSignMachine::from_cache` rebuilds the sign machine by calling `seeded_preprocess`, which derives all nonce material deterministically from the cached 32-byte seed [1](#0-0) . The nonce pair `(d, e)` used for each signing session is therefore a pure function of the seed [2](#0-1) .

The coordinator-side persistence writes the cache only once (`if CachedPreprocesses::get(...).is_none()`) and never deletes or rotates it, including after `share_internal`/`sign` returns an error: `machine.sign(preprocesses, msg)` returns `FrostError::InvalidPreprocess(p)` when a peer's preprocess fails `read_preprocess` or the internal nonce-commitment consistency check [3](#0-2) [4](#0-3) .

The signature share has the form `s = d + e·b + λ_i·x_i·c`. If the same `(d, e)` is used in two attempts where the binding factor `b` or challenge `c` differs (different preprocess set, different message), an observer holding both shares computes `e = (s₁ − s₂)/(b₁ − b₂)` over the field, then `d`, then solves for the secret share `x_i`. The library itself acknowledges this hazard ("Reuse of it enables recovery of your private key share") [5](#0-4) , but the retry machinery violates it because the error path — exactly like the leaked `pm_runtime` refcount — leaves the acquired resource live for reuse.

### Impact Explanation

An unprivileged party who can submit preprocess bytes to a validator (the `read_preprocess` input) can force `InvalidPreprocess` errors, causing the validator's cached seed — and hence its FROST nonces — to be reused across distinct signing attempts. Observing two resulting shares permits algebraic recovery of the victim's private key share; with a threshold of compromised/recovered shares the group's signing key is recoverable. This is key-share recovery, the highest-impact accepted class.

### Likelihood Explanation

The failure-triggering input is fully attacker-controlled: `Commitments::read` parses untrusted bytes and any malformed/invalid commitment yields `FrostError::InvalidPreprocess` [6](#0-5) . No special privileges are needed — a participant (or anyone able to inject preprocess data into the signing session) sends one bad preprocess to abort the attempt, then a valid one in the retry. Attempt counters/reattempt logic make retries routine, so the reuse condition is easy to hit. I was unable to fully verify within remaining budget whether `seeded_preprocess` mixes in attempt-specific entropy; if it did, the determinism would be broken and the finding weakened — but `from_cache` takes only `(algorithm, keys, cache)`, none of which vary between attempts of the same context, so identical nonces are produced [1](#0-0) .

### Recommendation

- Rotate or delete the cached preprocess seed whenever `sign()` fails or the attempt number increments — treat seed consumption like a nonce that must be burned on every entry into the signing round, success or failure (the `pm_runtime_resume_and_get` equivalent: only "keep" the acquisition on success).
- Alternatively, incorporate the attempt/context into `seeded_preprocess`'s RNG seed derivation inside `crypto/frost` so a reused cache cannot regenerate identical nonces.

### Proof of Concept

```text
1. Attacker (a signing participant) receives victim's preprocess broadcast for
   context C: commitments D = d·G, E = e·G (seed-derived, deterministic).
2. Attacker submits a malformed preprocess for themselves in attempt N.
   Victim's read_preprocess / sign() fails -> FrostError::InvalidPreprocess.
   Victim's CachedPreprocesses[C] seed is NOT deleted.
3. Retry (attempt N+1): victim calls from_cache(same seed) -> same (d, e).
   Attacker submits a *valid* but different preprocess set, producing
   binding factor b2 != b1 and/or different message m2.
4. Attacker collects victim's shares:
     s1 = d + e*b1 + l*x*c1   (broadcast before failure, or from a partial)
     s2 = d + e*b2 + l*x*c2
   Solves: e = (s1 - s2 - l*x*(c1-c2))/(b1-b2) — or with c known and using
   two sessions where c differs only by attacker-controlled msg, recover
   (d, e) then x from s = d + e*b + l*x*c.
5. Victim's threshold key share x is recovered.
```

Reachability note: even where the first share isn't broadcast before failure, repeating the abort after share broadcast (or inducing two distinct binding contexts over the same seed via participant-set differences) yields two shares under one `(d, e)`, which suffices.
