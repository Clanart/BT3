### Title
`IntentGatewayV2::instance()` defaults unregistered source chains to `address(this)`, allowing forged cross-chain settlement messages to drain escrow - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Bunni report's root cause is an access-control check that validates the wrong/insufficiently-scoped identity, letting calls pass (or in that case, fail) that should have been rejected differently. The local analog is in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `instance()` helper, which is used by `authenticate()` to gate `onAccept()`'s `RedeemEscrow`/`RefundEscrow` settlement paths. Instead of rejecting messages from state machines that have no registered gateway deployment, it silently falls back to trusting `address(this)` as the expected peer, which weakens the very check meant to bind message origin to a known, governance-registered instance.

### Finding Description
`onAccept()` is the single authenticated entrypoint (`onlyHost`) that processes settlement (`RedeemEscrow`/`RefundEscrow`) messages and releases escrowed tokens: [1](#0-0) 

For `RedeemEscrow`/`RefundEscrow`, the only binding check that a message actually originated from a trusted IntentGateway peer is `authenticate(request)`, which compares `request.from` against `instance(request.source)`: [2](#0-1) 

`instance()` is supposed to resolve the registered peer gateway address for a given `stateMachineId`, but its fallback is unsafe:

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}
```

For any `stateMachineId` that has never been registered via a `NewDeployment` governance message (i.e. `_instances[...] == address(0)`), this returns `address(this)` — the destination gateway's own address — instead of rejecting the source as unknown. This means `authenticate()` will accept any post request whose `from` field equals `address(this)`, from *any* state machine that Hyperbridge's host/consensus client considers valid but that this particular gateway hasn't explicitly registered a peer for. This weakens the "module/app identity binding" invariant the pivots call out explicitly (request/response paths must bind module identity on both Substrate and EVM).

Notably, the newer/rewritten intents module fixed exactly this pattern by reverting instead of defaulting: [3](#0-2) 

The Tron contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) still contains the unsafe fallback, showing this is a real regression/divergence between the two IntentGateway implementations rather than a hypothetical.

`withdraw()` (invoked once `authenticate()` passes) directly moves escrowed funds to an attacker-chosen beneficiary and marks the order filled: [4](#0-3) 

### Impact Explanation
If `authenticate()` accepts a forged `RedeemEscrow`/`RefundEscrow` message from an unregistered/attacker-influenced state machine whose dispatching contract address equals `address(this)`, the attacker can drain `_orders[commitment][token]` escrow for any legitimate order commitment to a beneficiary of their choosing — a direct "stealing of funds" / "false proof/state acceptance" / "unauthorized execution" outcome as defined by the bounty's impact gate. Because `withdraw()` also finalizes `_filled[commitment]`, this also creates a double-settlement/replay risk against legitimate user withdrawals for the same order.

### Likelihood Explanation
Exploitation requires the attacker's post request's `from` field (set by the source-chain ISMP host to the actual dispatching contract's address) to equal `address(this)` — the destination gateway's own address — on a source state machine that Hyperbridge's consensus client already trusts but for which this gateway has not yet called `_addDeployment`. Since Hyperbridge/IntentGateway contracts are commonly deployed via deterministic CREATE2 factories with identical bytecode+salt to obtain the same address across every EVM-compatible chain (a stated design goal reflected in `IntentsBase._blockNumber()`'s comment about "preserving deterministic CREATE2 deployment addresses across chains"), an unprivileged attacker can permissionlessly redeploy the same canonical bytecode+salt on a new/unregistered but Hyperbridge-supported chain and drive a settlement dispatch from that address — no malicious relayer, prover, or governance actor is required, only a supported-but-not-yet-onboarded state machine. This is a plausible, non-trivial but concretely realizable path, distinct from generic DoS or peer-compromise scenarios excluded by the impact gate.

### Recommendation
Change `instance()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to revert (e.g. `UnknownInstance`) when `_instances[keccak256(stateMachineId)] == address(0)`, matching the safer behavior already implemented in `IntentsBase._instance()` at `evm/src/apps/intentsv2/IntentsBase.sol:358-362`. Never default an identity-binding check to `address(this)` or any other implicit trust anchor for unregistered peers.

### Proof of Concept
1. Deploy the identical `IntentGatewayV2` bytecode via the same deterministic CREATE2 factory + salt used for the legitimate gateway, on any EVM-compatible chain that Hyperbridge's consensus client already trusts but for which the target destination gateway has not called `_addDeployment` (so `_instances[keccak256(sourceChainId)] == address(0)`). This deployment lands at the same address as the real gateway (`address(this)` on the destination chain).
2. From that instance, dispatch (via the source chain's `IDispatcher`) a `PostRequest` with `body = bytes.concat(RequestKind.RedeemEscrow, abi.encode(WithdrawalRequest({commitment: <existing real order commitment with nonzero escrow>, tokens: <real escrowed tokens/amounts>, beneficiary: <attacker address>})))`, targeting the real destination gateway's address as `to`.
3. A relayer submits the (legitimately provable, since the source chain is a valid state machine) ISMP proof to the destination `Host`, which calls `IntentGatewayV2.onAccept()`.
4. `authenticate()` computes `module = request.from` (attacker's colliding-address contract) and `instance(request.source)`, which — since `_instances[keccak256(request.source)] == 0` — returns `address(this)`, equal to `module`; the check passes.
5. `withdraw()` transfers the victim's escrowed tokens to the attacker's `beneficiary` and marks the real order as filled, blocking the legitimate solver/user claim.

    /**
     * @dev Checks that the request originates from a known instance of the IntentGateway.
     */
    function authenticate(PostRequest calldata request) internal view {
        if (request.from.length != 20) revert InvalidInput();
        address module = address(bytes20(request.from));
        // IntentGateway only accepts incoming assets from itself or known instances
        if (instance(request.source) != module) revert Unauthorized();
    }

     * @dev Resolves the IntentGateway instance address for a given state machine.
     * Reverts with `UnknownInstance` if no remote deployment has been registered for that chain.
     * @param stateMachineId The raw state machine identifier bytes.
     * @return The gateway address for the given state machine.
     */
    function _instance(bytes calldata stateMachineId) internal view returns (address) {
        address gateway = _instances[keccak256(stateMachineId)];
        if (gateway == address(0)) revert UnknownInstance();
