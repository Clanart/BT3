### Title
Unrestricted `file://`/local-path submodules on initial clone bypass Desktop's own file-protocol consent gate - (File: app/src/lib/git/clone.ts)

### Summary
Every submodule-related Git invocation added after the initial clone (checkout, branch switch, pull) in this codebase deliberately gates `protocol.file.allow` behind an explicit, presumably user-approved `allowFileProtocol` boolean that defaults to `false`. The initial `clone()` function, however, invokes `git clone --recursive` with no such gate and no explicit `protocol.file.allow` setting at all, so submodules recorded with `file://` or relative-path URLs in a malicious `.gitmodules` are resolved using whatever the ambient/default Git policy is — inconsistent with the app's own model that this decision should require confirmation.

### Finding Description
`app/src/lib/git/clone.ts` builds its arguments as: [1](#0-0) 
and never adds a `protocol.file.allow` config flag. Compare this to `updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts`, which treats file-protocol submodules as a decision that must be explicitly allowed: [2](#0-1) 
and to `checkoutBranch`/`checkoutCommit` in `app/src/lib/git/checkout.ts`, which both default `allowFileProtocol` to `false` and forward it through: [3](#0-2) 
This shows an explicit design intent elsewhere in the codebase to not silently resolve `file://`/local-path submodule URLs. The initial `--recursive` clone doesn't follow that same pattern, so a `.gitmodules` entry pointing at an arbitrary local path (or `file://` URL) on the victim's machine, or a maliciously crafted submodule URL, would be resolved during `git clone --recursive` subject only to the ambient Git version's own default `protocol.file.allow` policy rather than Desktop's application-level gate.

### Impact Explanation
If the ambient/default Git `protocol.file.allow` policy permits local-path submodule resolution during this specific invocation, an attacker who controls the content of a repository the user clones (a fully unprivileged, attacker-controlled-content scenario matching the "cloned/fetched repository" category) could point a submodule at another local directory on the victim's disk — potentially exfiltrating data by copying files from outside the intended repository into a location the user then commits and pushes, or by using local hardlinks/symlinks abused via nested `.git` structures. This would fall under "file write or read outside the repo" and "silent corruption of what the user commits or pushes."

### Likelihood Explanation
I could not verify from the available index whether this is currently exploitable in practice, because I could not confirm: (1) the exact ambient `protocol.file.allow` default in the bundled/embedded Git version Desktop ships, (2) whether `envForRemoteOperation` (used elsewhere) or some other global environment setting silently blocks `file://` protocol regardless of this gap, and (3) whether recent upstream Git CVE fixes (e.g., the 2022 submodule/`file://` protections) already neutralize this at the Git binary level regardless of Desktop's flag. Given that Desktop explicitly re-implements this same protection everywhere else in the code (`checkout.ts`, `submodule.ts`), the omission in `clone.ts` looks like a genuine inconsistency rather than an accepted risk, but I cannot confirm real-world exploitability without the ability to trace `envForRemoteOperation`/the embedded Git defaults further, which the current index does not fully expose.

### Recommendation
Apply the same `allowFileProtocol`-gated `-c protocol.file.allow=always`/default-deny pattern used in `submodule.ts` and `checkout.ts` to the initial `clone()` call in `clone.ts`, so that recursively-fetched submodules during the first clone are subject to the same explicit consent model as post-clone operations, rather than relying on ambient Git defaults.

### Proof of Concept
1. Attacker creates a public repository containing a `.gitmodules` file with an entry pointing to a local/relative path or `file://` URL targeting a sensitive local directory (e.g., a parent directory outside the intended clone target, or another repo on disk).
2. Victim uses GitHub Desktop's "Clone repository" flow, which calls `Dispatcher.clone` → `AppStore._clone` → `CloningRepositoriesStore` → ultimately `app/src/lib/git/clone.ts`'s `clone()` with `git clone --recursive` and no `protocol.file.allow` restriction. [4](#0-3) 
3. If the ambient Git default for this invocation permits local-path submodule resolution, the submodule is silently cloned into the new repository's working directory during the initial clone, without ever going through the `allowFileProtocol`-gated confirmation path used for later operations, and its content becomes part of what the user later stages/commits/pushes without any warning distinct from a normal submodule.

I was not able to fully confirm the exploitability boundary (embedded Git's exact default posture for this specific invocation), so this should be treated as a **verify-then-fix** finding rather than a confirmed, end-to-end proven exploit chain.
