### Title
DKG encryption-key registration lacks proof of possession, allowing a participant to redirect another participant's secret shares to a key controlled by an attacker - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to the xCAT zone flaw (credentials from one scope accepted in another without authorization checks), PedPoP's per-participant encryption key registration accepts any group element with no proof of possession or binding to the registering participant. A malicious participant can register a victim's encryption public key (or any key whose discrete log is known to the attacker) as their own, causing every other participant to encrypt that victim-slot's secret shares to the attacker's key.

### Finding Description
`Decryption::register` stores `msg.enc_key` for a `Participant` after only asserting the key wasn't registered twice — it performs no proof-of-possession check on the encryption key and no check that the key is bound to the claimed participant. [1](#0-0) 

The `EncryptionKeyMessage` wrapping `Commitments` contains only `{ msg, enc_key }` — no signature or PoK over `enc_key`. [2](#0-1) 

Round-1 verification (`SecretShareMachine::verify_r1`) validates the PoK inside `Commitments` (bound to context and participant `l`) and calls `self.encryption.register(l, msg)`, but the encryption key itself is never authenticated. [3](#0-2) 

Later, `Encryption::encrypt` derives the message key by ECDH against whatever point was registered: `ecdh(&key, to)` where `to = self.decryption.enc_keys[&participant]`. [4](#0-3) [5](#0-4) 

The PoP on each `EncryptedMessage` proves knowledge of the ephemeral per-message key — not ownership of the registered encryption key — so it does not catch the substitution. [6](#0-5) 

Blame does not save the victim: `decrypt_with_proof` verifies the accuser's DLEq against `self.enc_keys[&decryptor]`, i.e., the maliciously registered key, so the sender's proof validates and the decrypted share is revealed during blame, fully exposing it. [7](#0-6) 

### Impact Explanation
If participant B registers participant A's encryption public key `enc_pub_A` (whose discrete log `enc_key_A` is known to A, an accomplice, or is simply a key B generated), every sender encrypts B's secret share `f_j(B)` to A's key. A can then compute `ecdh(key_i, enc_pub_A) = msg.key_i * enc_key_A` and decrypt all `n-1` of B's shares, reconstructing B's full secret key share for the threshold key. Knowledge of a participant's secret share breaks the DKG's secrecy/rogue-key assumptions (e.g., enables share forgery in signing sessions where B is included, and reduces the effective security of the multisig). Additionally, B cannot decrypt their own shares and will issue blame; the blame proof validates correctly against the registered key, so honest senders are exonerated and the share value is disclosed publicly during blame resolution — a complete secret-share leak.

### Likelihood Explanation
Any single DKG participant can carry this out using only their public round-1 broadcast message (`EncryptionKeyMessage`), which is exactly the class of attacker-controlled input in scope (`Commitments::read` / `EncryptionKeyMessage` flow). No collusion, BFT break, or leaked key is required. The only mitigations are external: the caller must enforce one-commitment-per-participant (already required) and the channel must be authenticated per-participant so B cannot also impersonate A's key registration — but even with an authenticated channel, B legitimately controls their own registration slot and can insert A's key there.

### Recommendation
Bind the registered encryption key to the registering participant with a proof of possession: either (a) include `enc_key` inside the `Commitments`' signed `cached_msg` so the existing PoK over `commitments[0]` also covers it, or (b) add a dedicated Schnorr PoK over `enc_key` with a challenge binding context, participant index, and the key. Verify this proof in `Decryption::register`/`verify_r1` before inserting into `enc_keys`. Optionally also reject duplicate `enc_key` values across participants.

### Proof of Concept
1. Participants run `KeyGenMachine::new(params, context)`; participant A generates their `EncryptionKeyMessage` containing `enc_pub_A = G * enc_key_A`.
2. Malicious participant B broadcasts their own `EncryptionKeyMessage` but sets `enc_key = enc_pub_A` instead of their own. `Decryption::register` accepts it (only checks no double registration for B).
3. Each honest sender `j` calls `generate_secret_shares` → `encrypt(rng, l=B, share)` → `ecdh(&key_j, enc_pub_A)` and sends the `EncryptedMessage` to B.
4. A observes each ciphertext and computes `ecdh = msg.key_j * enc_key_A`, runs `cipher(context, &ecdh).apply_keystream(msg)`, and recovers B's share `f_j(B)` from every sender.
5. A sums the shares to obtain B's secret key share `s_B` for the threshold group key.
6. B fails to decrypt and calls `blame`; `decrypt_with_proof` verifies the sender's DLEq against `enc_keys[B] = enc_pub_A`, decryption succeeds, the share is revealed, and the honest sender is exonerated — confirming the key substitution was never detected.

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}
