## Analog Bug Found

### Title
Stale `GitHubRepository` association is re-used and overwritten by owner/name string match instead of persistent GitHub repository identity, corrupting cached permission/branch-protection trust data - (`File: app/src/lib/stores/app-store.ts`)

### Summary
The Move report's root cause is that a stale `name → owner` mapping is kept alive and blindly re-trusted after the underlying entity (domain owner) changes. Desktop has a structurally identical pattern: the association between a local `Repository` and its cached `GitHubRepository` record is re-derived purely from the **textual** `owner/name` pair parsed out of the git remote URL, never validated against GitHub's durable numeric repository `id`, and — per an explicit TODO in the code — is **never cleared**.

### Finding Description
`matchGitHubRepository` resolves identity solely from parsing the remote URL string: [1](#0-0) 

`repositoryWithRefreshedGitHubRepository` uses that match to fetch the "current" API repository for that `owner/name` and unconditionally merges it into the existing cached record with `upsertGitHubRepository`, and explicitly documents that stale associations are never invalidated: [2](#0-1) 

The lookup helper `matchGitHubRepository` (on `AppStore`) likewise only re-parses the remote string, never comparing against a previously-stored GitHub repo id: [3](#0-2) 

The persisted `gitHubRepositories` table enforces uniqueness only on `[ownerID+name]`, i.e., on the mutable owner-login/name pair, not on GitHub's immutable repository id: [4](#0-3) 

If the owner login backing `ownerID` is renamed away and later re-registered by a different (attacker-controlled) GitHub account, or the original repository is deleted/transferred and a new, unrelated repository is created at the same `owner/name` path, the `[ownerID+name]` key is reused. Desktop then silently overwrites the same cached `GitHubRepository` row — permissions, `private` flag, parent/fork chain, default branch — with data belonging to the attacker's repository, exactly as `name_to_addr`/`addr_to_name` in the Move contract kept resolving to the old identity after re-registration instead of being cleared/re-validated.

### Impact Explanation
The corrupted `GitHubRepository` record feeds security/trust-relevant decisions that are computed purely from the cached row, without any secondary identity check:
- `refreshBranchProtectionState` uses `gitHubRepo` to decide whether write access exists and whether branch-protection/API repo-rules checks run against the (now attacker-controlled) repo, silently substituting attacker data for the user's trust context: `app/src/lib/stores/app-store.ts:1484-1567`.
- Pull-request association, CI-check status (`commit-status-store.ts`), and permission-gated UI ("no write access" warning) are likewise derived from this same stale/attacker-overwritten record.

This is analogous to `get_address_from_name` returning the previous owner's stale identity after re-registration in the Move report: the mapping key (`owner/name` string / `abc.init`) is reused, the stale binding is authoritatively trusted, and no invalidation occurs, letting an unrelated (attacker) entity's data flow through the previously-established trust path.

### Likelihood Explanation
Reaching this state requires only actions the reported bug-class already assumes are attacker-reachable without local access: renaming/transferring a GitHub login or repository and having an attacker take over the vacated `owner/name` — a known, previously reported class of GitHub-side squatting. No local/physical access, admin rights, or pre-existing malware is required; the corrupting object is entirely attacker-controlled (a GitHub API repository object returned to `api.fetchRepository(owner, name)`), matching the "attacker controls a GitHub API object" criterion.

### Recommendation
- Store and verify GitHub's immutable numeric repository `id` (not just `[ownerID+name]`) as the primary identity for a cached `GitHubRepository`; if the `id` returned by `api.fetchRepository` differs from the one currently associated with the local `Repository`, treat the association as broken and either clear it or prompt the user, instead of merging in the new data.
- Address the acknowledged TODO (desktop/desktop#1144) by actually clearing `gitHubRepository` associations when the underlying identity can no longer be confirmed, mirroring the report's recommended mitigation of removing stale mappings at the point of re-registration rather than deferring cleanup indefinitely.

### Proof of Concept
1. Clone `https://github.com/alice/project`; Desktop stores a `GitHubRepository` row keyed by `[ownerID(alice)+"project"]` with `id=111`, `permissions.push=true`.
2. `alice` renames her account; the `alice` login becomes available and `mallory` registers it, creating a new repository `mallory(as alice)/project` (`id=999`) that mallory fully controls (private/public flags, permissions, parent/fork chain set at will).
3. On the next background refresh, `_refreshRepository` → `withRefreshedGitHubRepository`/`repositoryWithRefreshedGitHubRepository` (`app/src/lib/stores/app-store.ts:4874`) re-derives `owner="alice", name="project"` from the unchanged remote URL via `matchGitHubRepository` (`app/src/lib/repository-matching.ts:29`) and fetches `apiRepo` for that path — now `id=999`, mallory's data.
4. `repoStore.upsertGitHubRepository(endpoint, apiRepo)` merges/overwrites the same `[ownerID+name]` row without ever comparing the previous `id=111` to the new `id=999`.
5. `refreshBranchProtectionState` and PR/CI association code subsequently operate on mallory's repository metadata under the guise of the user's original, previously-trusted local repository, with no indication to the user that repository identity changed.

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo

  private async matchGitHubRepository(
    repository: Repository
  ): Promise<IMatchedGitHubRepository | null> {
    const gitStore = this.gitStoreCache.get(repository)

    if (!gitStore.defaultRemote) {
      await gitStore.loadRemotes()
    }

    const remote = gitStore.defaultRemote
    return remote !== null
      ? matchGitHubRepository(this.accounts, remote.url)
      : null
  }
