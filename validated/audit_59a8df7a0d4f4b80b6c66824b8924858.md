### Title
`SignableTransaction::new` omits the OP_RETURN `data` output from the fee/vsize calculation, underestimating `needed_fee` and producing transactions whose real fee rate is below the requested (and possibly below the minimum relay) rate - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to `rewardRate = amount / DURATION` being computed over a denominator that does not match the actual distribution period, `SignableTransaction::new` computes `needed_fee = fee_per_vbyte * vbytes` over a transaction weight that excludes the OP_RETURN output which is nevertheless appended to the real transaction. The "rate" (fee-per-vbyte) is applied to a smaller "duration" (vbytes) than reality, so the funded fee is insufficient for the transaction actually broadcast.

### Finding Description
In `SignableTransaction::new`, when `data` is `Some`, an OP_RETURN output is pushed to `tx_outs` at lines 194-202. However, the weight/vbytes used for the fee are computed via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204, which reconstructs a transaction containing only `payments` (and later `change` at lines 225-226) — never the OP_RETURN output. Consequently:

- `needed_fee` (line 206) is `fee_per_vbyte * vbytes` where `vbytes` is missing ~9-92 vbytes of OP_RETURN output (the data bound is 80 bytes at line 171).
- The change amount at lines 228-233 is `input_sat - (payment_sat + fee_with_change)`, where `fee_with_change` is also computed from a template lacking the OP_RETURN output.
- The minimum-relay-fee check at lines 211-213 uses the same underestimated `vbytes`, so a transaction with `fee_per_vbyte` exactly at the policy minimum can pass the check yet serialize to a larger transaction whose effective sat/vbyte is below `DEFAULT_MIN_RELAY_TX_FEE`.

The actual fee paid (`fee()`, lines 138-141, `sum(inputs) - sum(outputs)`) remains `needed_fee`, but the real transaction is larger, so the realized fee rate is strictly less than the caller-specified `fee_per_vbyte`.

### Impact Explanation
Any caller that attaches metadata (e.g., Serai's own `Shorthand`-style OP_RETURN burns/memos) produces a transaction that underpays relative to the requested fee rate. At the boundary, the produced transaction is below the minimum relay fee and will be rejected by the Bitcoin network despite `SignableTransaction::new` returning `Ok` — funds are not stolen but the transaction cannot propagate/confirm as constructed, a direct accounting-desync between the promised and actual fee rate. The defect is deterministic and reachable purely through public inputs: the `data`, `payments`, `inputs`, and `fee_per_vbyte` arguments to `SignableTransaction::new`.

### Likelihood Explanation
Triggering requires only calling `SignableTransaction::new` with `data.is_some()` — no protocol-party collusion or exotic state is needed. The underestimate occurs on every such call; whether the transaction actually fails relay depends on how close the chosen `fee_per_vbyte` is to the relay minimum and the size of `data`.

### Recommendation
Include the OP_RETURN output in the weight template. Pass the fully-built `tx_outs` (or equivalently `payments` plus the data output) into `calculate_weight_vbytes`, and re-check the minimum-fee bound against the final transaction's vbytes:

```rust
// build tx_outs (payments + OP_RETURN) first, then:
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), &tx_outs_as_scripts, None);
// or extend calculate_weight_vbytes to accept an extra output for `data`
```

Alternatively, compute the fee from `tx.vsize()` on the fully assembled transaction (including `data` and `change`) rather than a partial reconstruction.

### Proof of Concept
```rust
// Inputs: one ReceivedOutput worth 100_000 sats; payment of 50_000 sats;
// change address provided; 80 bytes of OP_RETURN data; fee_per_vbyte at the
// minimum relay rate boundary.
let tx = SignableTransaction::new(
    vec![input],                       // 100_000 sats
    &[(payment_script, 50_000)],
    Some(change_script),
    Some(vec![0xaa; 80]),              // OP_RETURN output
    fee_per_vbyte,                     // ~= DEFAULT_MIN_RELAY_TX_FEE / 1000
).unwrap();

// The signed transaction contains the OP_RETURN output...
let real_vsize = tx.transaction().vsize() as u64;
// ...but needed_fee was computed without it:
//   needed_fee == fee_per_vbyte * (real_vsize - ~92)
assert!(tx.needed_fee() < fee_per_vbyte * real_vsize);
// If fee_per_vbyte was chosen as the minimum viable rate, the real rate
// (tx.fee() / real_vsize) is below the minimum relay fee and the TX is
// non-relayable despite passing the TooLowFee check.
```
Root cause is at `networks/bitcoin/src/wallet/send.rs` lines 194-206 (OP_RETURN pushed after weight calc) and lines 225-233 (change/fee recomputed on a template still lacking the data output).
