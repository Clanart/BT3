### Title
PedPoP blame proofs leak ECDH keys before proof-of-possession verification - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
`KeyMachine::calculate_share` returns an `EncryptionKeyProof` for a malformed encrypted share before verifying the message’s proof of possession. A DKG peer can copy the ephemeral key from another encrypted share, substitute malformed ciphertext, and obtain the victim’s ECDH shared point through the returned blame proof. That point decrypts the originally copied ciphertext, exposing another participant’s secret share. [1](#0-0) [2](#0-1) 

### Finding Description
`Encryption::decrypt` queues the per-message `pop` for batch verification, but immediately computes `ecdh(self.enc_key, msg.key)`, decrypts the ciphertext, and returns an `EncryptionKeyProof` containing that ECDH point. [3](#0-2) 

`calculate_share` then attempts to parse the decrypted plaintext as a scalar. If parsing fails, it immediately returns `PedPoPError::InvalidShare` with `blame: Some(blame)`, before the queued PoP is ever checked by `batch.verify_with_vartime_blame`. [1](#0-0) [4](#0-3) 

The `EncryptionKeyProof` serializes the ECDH point directly as its `key` field, so returning it in an error exposes the shared decryption point. [5](#0-4) [6](#0-5) 

This bypasses the protection described by the implementation: the PoP exists specifically to prevent an attacker from claiming another message’s encryption key and inducing blame that reveals the original message. [7](#0-6) 

### Impact Explanation
An unprivileged DKG participant who can observe a victim-bound encrypted share can recover the secret share inside it without knowing its per-message private key. This is concrete key-share recovery and reduces the confidentiality expected from PedPoP’s encryption layer. [8](#0-7) 

### Likelihood Explanation
The attacker controls the `EncryptedMessage` supplied for their participant index and can repeatedly mutate the copied ciphertext until the decrypted bytes fail canonical scalar decoding. Because the vulnerable early return occurs before PoP verification, the invalid `pop` does not prevent disclosure of the blame proof. [1](#0-0) [4](#0-3) 

### Recommendation
Do not return an `EncryptionKeyProof` until the associated `pop` has been verified. Either synchronously verify `msg.pop` before scalar parsing and proof generation, or defer creating/returning the proof until after `batch.verify_with_vartime_blame` has established that the message is authentic. [9](#0-8) [4](#0-3) 

### Proof of Concept
1. Alice sends victim Bob a valid `EncryptedMessage<C, SecretShare<C::F>>` using ephemeral public key `X` and ciphertext `c`, where `c` encrypts Alice’s secret-share bytes under `ECDH(Bob.enc_key, X)`. [10](#0-9) 
2. Attacker Eve observes that message and submits her own `EncryptedMessage` containing the same `key = X` but mutated ciphertext bytes and an invalid `pop`. [11](#0-10) 
3. Bob’s `calculate_share` calls `Encryption::decrypt`, which queues—but does not verify—the invalid `pop`, calculates `ECDH(Bob.enc_key, X)`, decrypts the mutated bytes, and constructs an `EncryptionKeyProof` containing that ECDH point. [2](#0-1) 
4. If the mutated plaintext is not a canonical scalar, `calculate_share` returns `InvalidShare { blame: Some(proof) }` before batch verification can reject the invalid `pop`. [1](#0-0) 
5. Eve serializes the returned `EncryptionKeyProof` and extracts the first encoded point, which is `ECDH(Bob.enc_key, X)`. [6](#0-5) 
6. Eve derives the documented ChaCha20 keystream from the protocol context and that recovered ECDH point, applies it to the original ciphertext `c`, and recovers Alice’s secret-share bytes. [12](#0-11) [8](#0-7)

fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res
