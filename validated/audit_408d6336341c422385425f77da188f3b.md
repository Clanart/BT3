### Title
Spender can redeem more tokens than intended by front-running `CW20ERC20Pointer.approve()` allowance-delta recomputation - (File: contracts/src/CW20ERC20Pointer.sol)

### Summary
`CW20ERC20Pointer` is an EVM-facing pointer contract that lets any user's EVM address interact with an underlying CW20 token via the `IWasmd` precompile. Its `approve()` override does not directly set an absolute allowance; instead it re-queries the *current* CW20 allowance at execution time and issues an `increase_allowance`/`decrease_allowance` CosmWasm message for the delta. Because the "current allowance" is read from live on-chain state at the moment the transaction executes (not from the state at submission time), a spender can front-run an owner's `approve()` transaction with a `transferFrom()` that consumes the old allowance, causing the owner's subsequently-executed delta calculation to grant the spender additional allowance on top of what was already spent — letting the spender ultimately move more of the owner's tokens than the owner intended, exactly analogous to the classic ERC20 `approve()` race condition described in the external report.

### Finding Description
`CW20ERC20Pointer.approve()` is: [1](#0-0) 

It queries `allowance(msg.sender, spender)` live via the `WasmdPrecompile.query` call (executed synchronously within the same EVM transaction, reflecting whatever CW20 state exists at that point in the block), and then submits an `increase_allowance` or `decrease_allowance` CosmWasm execute message for the difference between the current on-chain allowance and the desired target amount: [2](#0-1) 

Because this "current allowance" is read fresh at execution time from the underlying CW20 contract (accessed through the `WasmdPrecompile` at `0x...1002`), a malicious spender can order their `transferFrom()` transaction to execute before the owner's `approve()` transaction within the same block (transaction ordering / front-running is fully controllable by any unprivileged party who observes the mempool and submits a transaction with sufficient priority/gas). Consider:

1. Alice has approved Bob for 100 tokens (via `increase_allowance` executed previously).
2. Alice decides to reduce Bob's allowance to 50 and calls `approve(bob, 50)`.
3. Bob front-runs by calling `transferFrom(alice, bob, 100)`, which succeeds because the on-chain CW20 allowance is still 100 at that point, spending all 100 tokens and setting the underlying CW20 allowance to 0.
4. Alice's `approve(bob, 50)` transaction now executes: it queries `allowance(alice, bob)`, which returns 0 (because Bob just spent it), and since `0 < 50`, it issues `increase_allowance(bob, 50)`.
5. The net result: Bob has already transferred 100 tokens, and now also holds a fresh 50-token allowance he can additionally redeem — a total of up to 150 tokens moved/available to Bob, when Alice's final intended state was "Bob may spend 50 tokens total."

This reproduces the exact bug class from the external report: the contract recomputes an allowance delta based on state that can be manipulated by the spender via front-running, rather than making the new approval atomic/independent of the spender's intervening actions.

### Impact Explanation
This is an unauthorized-transfer/fund-loss scenario reachable by any unprivileged EVM user who deploys or interacts with a `CW20ERC20Pointer` contract (these pointer contracts are a core, permissionless CW20<->EVM bridging primitive in sei-chain, callable by any public RPC client submitting an EVM transaction). A spender can extract more value from an owner's CW20 balance than the owner ever intended to authorize, directly causing fund loss for the token owner through the pointer/precompile bridge.

### Likelihood Explanation
Likelihood is high in permissionless environments: front-running approve-change transactions is a well-known and easily executed MEV/mempool-monitoring technique, requiring no special privileges — any address with a pending allowance can watch the mempool for an owner's `approve()` call adjusting its allowance downward (or even just updating it) and race a `transferFrom()` ahead of it, then benefit again from the pointer's delta-based re-approval logic.

### Recommendation
Do not compute the new CW20 allowance as a delta from a value re-read at execution time. Either:
- Set the underlying CW20 allowance directly to the desired absolute value in one atomic CW20 message if the CW20 standard interface supports it, or
- Have `approve()` first reset the underlying allowance to 0 (e.g., `decrease_allowance` by the full previously-known amount) in a way that fails safely if the current allowance has changed unexpectedly, or
- Adopt the standard mitigation pattern (`increaseAllowance`/`decreaseAllowance` as the only mutating entry points, with `approve()` restricted to transitions from/to zero), so that a front-run cannot cause the final allowance to diverge from the owner's intent regardless of intervening spends.

### Proof of Concept
1. Deploy a `CW20ERC20Pointer` for an existing CW20 token; Alice (owner) associates her EVM address and holds CW20 balance.
2. Alice calls `pointer.approve(bob, 100)` → underlying CW20 allowance becomes 100 (via `increase_allowance`).
3. Alice decides to reduce it and submits `pointer.approve(bob, 50)`.
4. Bob observes this in the mempool and submits `pointer.transferFrom(alice, bob, 100)` with higher gas price/priority so it lands first in the same block.
5. Bob's `transferFrom` succeeds (CW20 allowance was still 100), transferring 100 tokens and zeroing the CW20 allowance.
6. Alice's `approve(bob, 50)` executes next: `allowance(alice, bob)` now returns 0, so the contract computes `amount - currentAllowance = 50 - 0 = 50` and calls `increase_allowance(bob, 50)`.
7. Bob now can call `transferFrom(alice, bob, 50)` again, having moved a total of 150 tokens versus the 50 Alice intended to authorize after her adjustment. [3](#0-2)

    function allowance(address owner, address spender) public view override returns (uint256) {
        string memory o = _formatPayload("owner", _doubleQuotes(AddrPrecompile.getSeiAddr(owner)));
        string memory s = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
        string memory req = _curlyBrace(_formatPayload("allowance", _curlyBrace(_join(o, s, ","))));
        bytes memory response = WasmdPrecompile.query(Cw20Address, bytes(req));
        return JsonPrecompile.extractAsUint256(response, "allowance");
    }

    // Transactions
    function approve(address spender, uint256 amount) public override returns (bool) {
        // if amount is larger uint128 then set amount to uint128 max
        if (amount > type(uint128).max) {
            amount = type(uint128).max;
        }
        uint256 currentAllowance = allowance(msg.sender, spender);
        if (currentAllowance > amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(currentAllowance - amount)));
            string memory req = _curlyBrace(_formatPayload("decrease_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        } else if (currentAllowance < amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount - currentAllowance)));
            string memory req = _curlyBrace(_formatPayload("increase_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        }
        return true;
    }
