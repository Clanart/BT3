### Title
`ThresholdKeys::read`/`ThresholdKeys::new` accept attacker-controlled `t`, `n`, `i`, interpolation coefficients, `secret_share`, and `verification_shares` with no consistency check, letting deserialized bytes escape the intended key structure and yield an arbitrary, unspendable/mismatched group key - (File: crypto/dkg/src/lib.rs)

### Summary
The Helm CVE-2019-1000008 bug class is "untrusted archive bytes place data outside the intended boundary" (path traversal). The Serai analog is untrusted serialized bytes placing a key outside its intended constraint domain: `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) reads `t`, `n`, `i`, an interpolation-method selector, `n` attacker-chosen `Constant` coefficients, a `secret_share`, and `n` verification shares, then hands them to `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391), which computes `group_key` purely as `sum(verification_shares[i] * interpolation_factor(i))` over participants `1..=t` — without ever checking that `C::generator() * secret_share == verification_shares[params.i()]` or that the shares/co interpolate to anything meaningful. [1](#0-0) [2](#0-1) 

### Finding Description
`ThresholdParams::new` (lines 166-179) only enforces `0 < t <= n` and `i <= n`. `ThresholdKeys::new` only enforces the count and range of `verification_shares` and that `Constant` interpolation is used only when `t == n` (lines 355-374). Two escape hatches exist:

1. **secret_share never bound to verification_shares[i]**: the deserialized scalar `secret_share` is stored verbatim (line 618, 381-386). A crafted blob yields keys whose `group_key()` is derived from attacker points while `view()` interpolates a secret share unrelated to them, so any signature produced is for a key no one holds, or produces `InvalidShare` blame against honest participants.
2. **Constant interpolation with fully attacker-controlled coefficients**: when `t == n`, `interpolation_factor` returns `c[i-1]` directly (lines 226-248), so the group key is an arbitrary linear combination of attacker-chosen points with attacker-chosen scalars — the bytes "unpack" a group key outside any polynomial the DKG would have produced.

`view()` (lines 463-533) then happily interpolates using these parameters, applying scalar/offset tweaks, so downstream signing operates on the attacker-defined key geometry. [3](#0-2) [4](#0-3) 

### Impact Explanation
Any code path feeding untrusted bytes to `ThresholdKeys::read` (listed as an in-scope reachable API) accepts a key share inconsistent with its own verification shares. Consequences: funds sent to `group_key()` that is unspendable because the `secret_share` doesn't correspond to the verification shares (funds reported received that are not spendable), and signature shares that fail `verify` against the interpolated `verification_shares`, enabling framed-blame or liveness failure. Severity Medium: requires the caller to deserialize attacker-provided key material rather than locally generated DKG output.

### Likelihood Explanation
Requires a reachable path where a peer/attacker supplies serialized `ThresholdKeys`. The DKG itself distributes shares via PedPoP rather than full `ThresholdKeys` blobs, so reachability depends on integrators importing externally supplied keys (recovery/import flows), which keeps this at Medium rather than High.

### Recommendation
In `ThresholdKeys::new` (and therefore `read`), verify `C::generator() * secret_share == verification_shares[&params.i()]`, and for `Interpolation::Constant` verify the coefficients are the expected canonical ones (e.g., all-`ONE` for an additive resharing) or at minimum that the interpolated group key matches the shares under a documented relation. Reject blobs that fail consistency instead of silently constructing the key.

### Proof of Concept

// Craft ThresholdKeys bytes: t = n = i = 1, Constant interpolation with c[0] = 1,
// verification_shares[1] = G * 5, secret_share = 7.
let mut buf = vec![];
buf.extend(4u32.to_le_bytes());                       // C::ID len
buf.extend(C::ID);
buf.extend(1u16.to_le_bytes());                       // t
buf.extend(1u16.to_le_bytes());                       // n
buf.extend(1u16.to_le_bytes());                       // i
buf.push(0);                                          // Interpolation::Constant
buf.extend(C::F::ONE.to_repr().as_ref());             // coefficient
buf.extend(C::F::from(7).to_repr().as_ref());         // secret_share = 7
buf.extend((C::generator() * C::F::from(5)).to_bytes().as_ref());

let keys = ThresholdKeys::<C>::read(&mut buf.as_slice()).unwrap();
// group_key() == G*5, but the share secret is 7: any sign() produces a share that
// fails verification against verification_shares[1], and no party holds the
// discrete log of group_key(). read() accepts it with no error.

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }

  pub fn view(&self, mut included: Vec<Participant>) -> Result<ThresholdView<C>, DkgError> {
    if (included.len() < self.params().t.into()) ||
      (usize::from(self.params().n()) < included.len())
    {
      Err(DkgError::IncorrectAmountOfParticipants {
        t: self.params().t,
        n: self.params().n,
        amount: included.len(),
      })?;
    }
    included.sort();
    {
      let mut found = included[0] == self.params().i();
      for i in 1 .. included.len() {
        if included[i - 1] == included[i] {
          Err(DkgError::DuplicatedParticipant(included[i]))?;
        }
        found |= included[i] == self.params().i();
      }
      if !found {
        Err(DkgError::NotParticipating)?;
      }
    }
    {
      let last = *included.last().unwrap();
      if u16::from(last) > self.params().n() {
        Err(DkgError::InvalidParticipant { n: self.params().n(), participant: last })?;
      }
    }

    // The interpolation occurs multiplicatively, letting us scale by the scalar now
    let secret_share_scaled = Zeroizing::new(self.scalar * self.original_secret_share().deref());
    let mut secret_share = Zeroizing::new(
      self.core.interpolation.interpolation_factor(self.params().i(), &included) *
        secret_share_scaled.deref(),
    );

    let mut verification_shares = HashMap::with_capacity(included.len());
    for i in &included {
      let verification_share = self.core.verification_shares[i];
      let verification_share = verification_share *
        self.scalar *
        self.core.interpolation.interpolation_factor(*i, &included);
      verification_shares.insert(*i, verification_share);
    }

    /*
      The offset is included by adding it to the participant with the lowest ID.

      This is done after interpolating to ensure, regardless of the method of interpolation, that
      the method of interpolation does not scale the offset. For Lagrange interpolation, we could
      add the offset to every key share before interpolating, yet for Constant interpolation, we
      _have_ to add it as we do here (which also works even when we intend to perform Lagrange
      interpolation).
    */
    if included[0] == self.params().i() {
      *secret_share += self.offset;
    }
    *verification_shares.get_mut(&included[0]).unwrap() += C::generator() * self.offset;

    Ok(ThresholdView {
      interpolation: self.core.interpolation.clone(),
      scalar: self.scalar,
      offset: self.offset,
      group_key: self.group_key(),
      secret_share,
      original_verification_shares: self.core.verification_shares.clone(),
      verification_shares,
      included,
    })
  }
