### Title
`Scanner` reports dust/zero-value outputs as spendable `ReceivedOutput`s with no minimum-value check, and `SignableTransaction` counts them as available funds — ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
Analogous to `liquidity_lockbox::withdraw` hard-coding `token_min_a = token_min_b = 0` (so the slippage check `delta >= min` is vacuously true for any output), `Scanner::scan_transaction` accepts a `TxOut` into the wallet's tracked set purely on `script_pubkey` match — the "minimum acceptable value" is implicitly `0`, so the check `output.script_pubkey ∈ scripts` is the only gate and `output.value` is never bounded. Any output paying to a watched script — including a 0- or 1-satoshi output that costs more in fee to spend than it is worth — is returned as a spendable `ReceivedOutput`, and `SignableTransaction::new` then folds its value into `input_sat` as if it were economically usable funds.

### Finding Description
`Scanner::new`/`register_offset` build `scripts: HashMap<ScriptBuf, Scalar>` mapping each watched Taproot script to its scalar offset (`networks/bitcoin/src/wallet/mod.rs:162-196`). `scan_transaction` iterates `tx.output` and pushes a `ReceivedOutput` for every output whose `script_pubkey` is in the map (`mod.rs:199-213`). There is no check against `send::DUST` (546) or against the network-level `Bitcoin::DUST` (10,000, `processor/src/networks/bitcoin.rs:638`), and no check that the value is non-zero or exceeds the marginal fee cost of the input (~57 vbytes per input, per the comment at `bitcoin.rs:606-620`).

Downstream, `SignableTransaction::new` sums `inputs.iter().map(|input| input.output.value)` into `input_sat` (`send.rs:175`) and uses it to satisfy `payment_sat + needed_fee` (`send.rs:215-221`). `TransactionSignMachine::sign` then signs a `Prevouts::All` sighash committing to these prevouts (`send.rs:373-390`), so the FROST multisig will sign spends of outputs that are economically unspendable (spending a 100-sat input at any reasonable fee rate burns more than 100 sats — net loss absorbed into fee).

The dust predicate exists in the codebase (`DUST` is enforced for *payment* outputs at `send.rs:165-169` and for the *change* output at `send.rs:228-234`) but is never applied to *received* outputs — exactly the asymmetric-enforcement shape of the reference bug, where the underlying API (`decreaseLiquidity` / dust checks in `send.rs`) has a bound parameter that the higher-level path (`withdraw` / `Scanner`) fails to supply.

### Impact Explanation
An unprivileged third party can send a dust or zero-valued output to any of the wallet's watched script pubkeys (the base key script or any registered offset). The scanner reports it as a received output; coin selection treats its value as spendable balance, and the threshold group will sign transactions spending it. Every such input included imposes a net fee loss (~230 WU ≈ 57 vB each), and the scheduler/`prepare_send` accounting (`theoretical_change_amount`, `operating_costs` at `processor/src/networks/mod.rs:435-453`) is computed off this inflated balance — so funds are reported received that are not economically spendable, and each spend silently donates the shortfall to miners.

### Likelihood Explanation
Dusting a known Taproot address is cheap and permissionless — the script pubkeys are public on-chain once used, and `register_offset` scripts are derivable. Unlike the MEV/timing dependence that reduced the reference finding to Medium, this requires no ordering advantage: the attacker just broadcasts one dust output. The loss per attack is bounded (marginal input fee per dust input), consistent with Medium severity.

### Recommendation
In `Scanner::scan_transaction` (or at `ReceivedOutput` construction), filter `output.value` below `send::DUST` — or preferably a configurable minimum reflecting the marginal cost of spending an input — so economically unspendable outputs are not surfaced. Alternatively, have `SignableTransaction::new` reject or deprioritize inputs whose value is below the marginal fee they incur (`fee_per_vbyte * ~57`), rather than blindly summing all `input.output.value` into `input_sat`.

### Proof of Concept
```rust
// Given a Scanner for `key` and any registered offset script:
let mut scanner = Scanner::new(key).unwrap();
let offset = scanner.register_offset(Scalar::random(&mut OsRng)).unwrap();

// Attacker (no key material needed) builds a tx paying 1 sat to that script:
let dust_tx = Transaction {
    version: Version(2),
    lock_time: LockTime::ZERO,
    input: vec![/* attacker's input */],
    output: vec![TxOut {
        value: Amount::from_sat(1), // below DUST (546), below marginal spend cost
        script_pubkey: p2tr_script_buf(key + (ProjectivePoint::GENERATOR * offset)).unwrap(),
    }],
};

// Scanner reports it as a spendable output:
let outputs = scanner.scan_transaction(&dust_tx);
assert_eq!(outputs.len(), 1);
assert_eq!(outputs[0].value(), 1); // "received", but spending it is a net loss

// SignableTransaction then counts the 1 sat toward input_sat and signs a spend:
let st = SignableTransaction::new(
    vec![outputs[0].clone()], &payments, change, None, fee_per_vbyte,
); // succeeds if payments happen to fit; the dust input is committed via Prevouts::All
```

The check on `output.script_pubkey` at `mod.rs:205` is the only acceptance criterion — `output.value` is unconstrained, so `value = 0` or `1` passes identically, mirroring `token_min_a = token_min_b = 0` making `delta >= min` true for all deltas.
