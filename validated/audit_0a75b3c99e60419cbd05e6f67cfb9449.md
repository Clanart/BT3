### Title
`IntentGatewayV2.authenticate` accepts cross-chain messages from unregistered chains due to zero-mapping fallback to `address(this)` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` (Tron variant) authenticates incoming ISMP `PostRequest`s by comparing the encoded `request.from` address against `instance(request.source)`. When a source chain has never been registered as a peer, `_instances[keccak256(stateMachineId)]` is the Solidity default (`address(0)`), and `instance()` silently falls back to `address(this)` instead of reverting. An attacker who deploys the same deterministic-CREATE2 gateway bytecode on any Hyperbridge-supported but unregistered chain gets a contract at the identical address, satisfying `instance(request.source) == module` and bypassing the peer-authentication check — the exact same "default value collides with attacker-controlled value" pattern as the InfinityPool `vc.subject == 0` bug.

`instance()` is meant to resolve the trusted peer-gateway address for a given source chain, verified against `_instances`, a mapping populated only via governance-driven `NewDeployment` registration. But for any `stateMachineId` that was never registered, the Solidity default `address(0)` is mapped to `address(this)` instead of causing a revert or an `Unauthorized`/`UnknownInstance` error. `authenticate()` then simply checks that the attacker-supplied `request.from` bytes decode to this same value.

Because the gateway is deployed deterministically via CREATE2 with identical bytecode across chains — as documented in the sibling `evm/src/apps/IntentGatewayV2.sol` constructor comments — its own address is a known, fixed constant. Any chain that is technically reachable by the Hyperbridge network but has not yet been added to `_instances` (e.g., a newly onboarded chain before governance calls `NewDeployment`, or any chain that will never be a legitimate peer) lets an attacker deploy the exact same gateway bytecode via the public CREATE2 factory at that identical address, then dispatch a forged `PostRequest` whose `from` field equals `address(this)`. On the receiving/target chain, `instance(request.source)` returns `address(this)` (the zero-default fallback) which trivially equals the forged `module`, so `authenticate()` passes even though `request.source` was never a trusted, governance-registered peer.

This mirrors the InfinityPool bug precisely: `GetRoute.agentFactory(router).agents(msg.sender)` defaults to `0` for non-agents, and comparing it to an attacker-chosen `vc.subject = 0` bypassed `subjectIsAgentCaller`. Here, `_instances[...]` defaults to `address(0)`, which `instance()` remaps to `address(this)`, and comparing it to an attacker-chosen `request.from = address(this)` bypasses the peer-authentication gate.

### Impact Explanation
`authenticate()` gates the handling of privileged cross-chain `RequestKind`s such as `RedeemEscrow` and `RefundEscrow`, which release escrowed order funds (`_orders[commitment][token]`) to a beneficiary specified in the message body. An attacker who satisfies `authenticate()` from a forged, unregistered "peer" can dispatch a `RedeemEscrow`/`RefundEscrow` message that the target gateway treats as coming from a legitimate cross-chain peer, redirecting or draining escrowed order funds to an attacker-controlled beneficiary — direct fund loss/theft, matching the bounty's "stealing or loss of funds" and "unauthorized transaction or execution" categories.

### Likelihood Explanation
This requires only a permissionless CREATE2 deployment on an unregistered-but-Hyperbridge-supported chain and a normal ISMP message dispatch — no malicious relayer, prover, or governance actor is needed, since the message is genuinely and correctly relayed/proven; it is the destination-side identity check itself that is defective. The main precondition is the existence of at least one Hyperbridge-connected chain for which the gateway operator has not yet called `NewDeployment`/registered an instance, which is a normal, expected transient state during any multi-chain rollout.

### Recommendation
Make `instance()` fail closed instead of defaulting to `address(this)`: revert with an `UnknownInstance`/`Unauthorized` error when `_instances[keccak256(stateMachineId)] == address(0)`, exactly as the non-Tron `evm/src/apps/IntentGatewayV2.sol` variant already does via `_instance()` (which reverts with `UnknownInstance`). Apply the same fix to the Tron contract so no state machine can ever authenticate merely by matching the zero-default value.

### Proof of Concept
1. Identify a state machine ID supported by the Hyperbridge network but not yet present in `_instances` on the target `IntentGatewayV2` deployment (e.g., a chain pending onboarding).
2. Using the same CREATE2 factory, salt, and init bytecode as the legitimate `IntentGatewayV2`, deploy the contract on that unregistered chain — it lands at the identical `address(this)` as the real gateway on other chains.
3. From this attacker-controlled deployment, dispatch a `PostRequest` to the target chain's gateway with `body` encoding `RequestKind.RedeemEscrow` (or `RefundEscrow`) for a known order commitment, and `from = abi.encodePacked(address(this))`.
4. On `onAccept`, `authenticate()` computes `module = address(this)` and `instance(request.source)`; since `request.source` is unregistered, `instance()` returns `address(this)`, so `instance(request.source) == module` and the check passes.
5. The forged request is processed as if from a trusted peer, releasing escrowed funds to the attacker's specified beneficiary.

     * @dev Checks that the request originates from a known instance of the IntentGateway.

    function authenticate(PostRequest calldata request) internal view {
        if (request.from.length != 20) revert InvalidInput();
        address module = address(bytes20(request.from));
        // IntentGateway only accepts incoming assets from itself or known instances
        if (instance(request.source) != module) revert Unauthorized();
    }
