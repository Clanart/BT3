### Title
CR-CAT `claim_pending_approval_balance` permanently halts when the only matching VC is revoked - (File: chia/wallet/vc_wallet/cr_cat_wallet.py)

### Summary
`CRCATWallet.claim_pending_approval_balance()` requires locating a currently-valid `VerifiedCredential` whose provider is in `self.info.authorized_providers` before it can release funds that were deferred into the "pending approval" puzzle state. If a DID provider revokes the only VC that satisfies this lookup (an action entirely outside the CR-CAT holder's control, analogous to EigenLayer removing a strategy from its deposit whitelist), the claim path always raises and the funds become permanently unclaimable — exactly the "external whitelist entry disappears, protocol code has no fallback and always reverts" pattern from the reference report.

### Finding Description
CR-CAT ("Credential Restricted CAT") coins can be put into a "pending approval" custody state via `construct_pending_approval_state()` [2](#0-1)  when the sender doesn't have (or defers to) a VC-holding party. Recovering these funds requires `CRCATWallet.claim_pending_approval_balance()`:

```
vc: VerifiedCredential | None = await vc_wallet.get_vc_with_provider_in_and_proofs(
    self.info.authorized_providers, self.info.proofs_checker.flags
)
if vc is None:  # pragma: no cover
    raise RuntimeError(f"No VC exists that can approve spends for CR-CAT wallet {self.id()}")
``` [3](#0-2) 

`self.info.authorized_providers` is the fixed, wallet-level set of DIDs that are trusted to issue proofs for this CR-CAT asset (mirroring the CAT's on-chain `authorized_providers` curried into `construct_cr_layer()` at mint time) [4](#0-3) . A DID that is a listed provider can unilaterally destroy/revoke any VC it issued at any time via `VCWallet.revoke_vc()`, which spends the VC through `vc.activate_backdoor(...)` [5](#0-4) . Once revoked, `get_vc_with_provider_in_and_proofs` can no longer find that VC record (it is deleted from the store the moment its coin is spent/removed, per `remove_coin()` [6](#0-5) ). If this revoked VC was the wallet's only credential satisfying `authorized_providers`/`proofs_checker`, then every future call to `claim_pending_approval_balance()` for that CR-CAT wallet permanently raises `RuntimeError`, exactly like the reported EigenLayer scenario where `depositBalanceIntoEigenLayer` always reverts once the strategy is removed from Eigenlayer's whitelist, with no code path checking availability up front or falling back gracefully.

Similarly, ordinary CR-CAT spends via `_generate_unsigned_spendbundle()` have the identical hard dependency and identical unguarded failure mode:
```
if vc is None:  # pragma: no cover
    raise RuntimeError("Spending no cat coins is not an appropriate use of _generate_unsigned_spendbundle")
``` [7](#0-6) [8](#0-7) 

Both call sites are marked `# pragma: no cover`, indicating the authors never exercised or hardened this failure branch — the same "no prior check on whether the resource is still valid" gap flagged in the original report.

### Impact Explanation
Once the sole qualifying VC is revoked, funds sitting in a CR-CAT wallet's "pending approval" state (`CoinType.CRCAT_PENDING`) become permanently frozen — the holder cannot construct any valid spend to move them, because the code path that would authorize the spend always raises before a `CoinSpend`/`SpendBundle` can even be built. This is a spend-triggered transaction-processing halt for the affected wallet: no amount of retrying, fee-bumping, or resubmission can succeed, since the failure occurs in wallet-side spend-bundle construction, not merely at mempool/consensus validation.

### Likelihood Explanation
Reaching this state requires: (1) a CR-CAT with `authorized_providers` containing a small/limited set of DIDs (which is the normal, intended configuration for credential-restricted assets), (2) an amount of that CR-CAT parked in "pending approval" state (a normal, intended custody path for CR-CAT transfers/offers), and (3) the provider DID choosing to revoke the VC that had been backing that approval. Because `revoke_vc()` is a first-class, permissionless action available to any DID acting as a provider, and CR-CAT designs commonly have few authorized providers, this is readily triggerable without any privileged or malicious-peer access — it only requires normal use of documented wallet RPCs (`vc_revoke`/`cat_spend` claim flows).

### Recommendation
Before revocation is finalized, or in the claim/spend code path, add a check for outstanding pending-approval balances tied to the VC's provider set, and either block/queue the revocation until claims are settled, or extend `claim_pending_approval_balance()`/`_generate_unsigned_spendbundle()` to search across *all* wallet VCs (not just those from the currently authorized/live provider set) or provide a documented recovery path (e.g., allow claiming via any historically valid VC proof, or via a timeout/escape hatch) so that a provider's unilateral revocation cannot permanently strand user funds.

                assert isinstance(wallet, DIDWallet)
                if bytes32.fromhex(wallet.get_my_DID()) == vc.proof_provider:
                    did_wallet = wallet

        else:
            await self.generate_signed_transaction(
                [uint64(1)],
                [await action_scope.get_puzzle_hash(self.wallet_state_manager)],
                action_scope,
                fee,
                vc_id=vc.launcher_id,
                self_revoke=True,
            )
            return

        # Generate spend specific nonce
        coins = {await did_wallet.get_coin()}
        coins.add(vc.coin)
        if fee > 0:
            coins.update(await self.standard_wallet.select_coins(fee, action_scope))
        sorted_coins: list[Coin] = sorted(coins, key=Coin.name)

            interface.side_effects.extra_spends.append(WalletSpendBundle([vc_spend], G2Element()))
