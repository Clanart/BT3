## Title
Symlink following in `getResolutionDiff` allows arbitrary local file read into conflict-diff view - (File: `app/src/lib/git/diff.ts`)

## Summary
`getResolutionDiff` reads the working-tree file at an attacker-influenced conflicted path with plain `fs.readFile`, which transparently follows symlinks, and does not use the repository's own `resolveWithin` symlink/traversal guard that is applied to the *same* conflicted-file-path input elsewhere in the Copilot conflict-resolution feature.

## Finding Description
`getResolutionDiff` computes the "base" (old) side of the resolution diff directly from disk: [1](#0-0) 

`filePath` here is `file.path`, the repository-relative path of a conflicted `WorkingDirectoryFileChange`, passed straight through from the UI without any validation: [2](#0-1) 

`Path.join(repository.path, filePath)` only guarantees the *literal* path string stays under the repo; it does nothing to stop the OS from following a symlink placed at that path. Node's `fs.readFile` dereferences symlinks by default. Git can track symlinks (mode `120000`), so a malicious repository can add a conflicting entry whose working-tree content, after checkout/merge, is a symlink pointing at an arbitrary absolute path (e.g. `~/.ssh/id_rsa`, `/etc/passwd`, or an app credential file). Because the path is "conflicted," it will be selected in the Copilot conflicts dialog and `getResolutionDiff` will be invoked for it, at which point `baseContent` becomes the *target* file's contents instead of the repo blob's contents.

Notably, this exact class of attack is already anticipated and mitigated in the sibling code path that gathers conflict context for Copilot itself, `buildConflictContext`, which explicitly calls `resolveWithin` before reading the same kind of conflicted-file path: [3](#0-2) 

`resolveWithin` calls `fs.realpath` on both the root and the resolved path and rejects anything whose real (symlink-resolved) path escapes the repository root: [4](#0-3) 

`getResolutionDiff` performs no equivalent check before its `readFile` call, so the exact same "conflicted file path" input is unsafe in one code path and safe in the other.

## Impact Explanation
The result of `getResolutionDiff` (`oldContents`) is used to build `IFileContents` for the diff renderer, i.e., it is rendered as the "old" side of the conflict diff shown to the user in the Copilot Conflicts "Changes" tab: [5](#0-4) 

An attacker who controls a repository (or a branch merged into it) can cause the app to read and display the contents of an arbitrary file on the victim's disk that the OS user account can access — a file-read-outside-the-repo primitive triggered purely by cloning/fetching and merging an untrusted repository, which matches the program's valid-impact category. I did not find evidence that this specific function's output is transmitted over the network to the Copilot API (that data path goes through `buildConflictContext`/`resolveWithin`, which is protected); the disclosure here is to the renderer UI within the local app, but that is still an unauthorized read of file contents outside the intended repository sandbox.

## Likelihood Explanation
Requires the victim to open a merge/rebase/cherry-pick with conflicts against an attacker-influenced branch/repo and to open the Copilot Conflicts dialog with "ours"/"theirs"/Copilot resolution selected for the malicious path — a plausible, low-interaction scenario for GitHub Desktop's stated threat model (untrusted cloned/merged repository content). No special local privileges are needed beyond what the app process itself already has.

## Recommendation
Before the `readFile` call in `getResolutionDiff` (`app/src/lib/git/diff.ts`, lines 460–463), resolve `filePath` with the existing `resolveWithin(repository.path, filePath)` helper (as already done in `app/src/lib/copilot-conflict-context.ts`) and reject/handle `null` results (path escapes the repo or cannot be resolved), instead of joining and reading the path directly.

## Proof of Concept
1. Create repo `A` with file `secret-link` on branch `main`.
2. On a branch `evil`, replace `secret-link` with a symlink (`ln -s /etc/passwd secret-link`, mode `120000`) and commit.
3. Merge `evil` into `main` such that `secret-link` is reported as conflicted (e.g., also modify it differently on `main` to force a conflict, or use a type-change conflict).
4. After checkout, the working-tree entry at `secret-link` is the symlink to `/etc/passwd`.
5. Open the Copilot Conflicts dialog, select `secret-link`, choose "ours"/"theirs" resolution to trigger `getResolutionDiff(repository, 'secret-link', { stage: 'ours' })`.
6. Assert: `oldContents` (and the rendered diff) equals the contents of `/etc/passwd`, not the repo-tracked content, confirming the missing symlink/escape check.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
