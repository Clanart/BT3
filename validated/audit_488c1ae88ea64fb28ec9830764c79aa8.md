## Analysis

The external report's core broken invariant: crediting internal accounting with a *calculated* amount instead of the *actual* amount received from a token transfer with variable/lossy transfer semantics (fee-on-transfer, rate slippage), causing paper accounting to diverge from real custody.

The main EVM `IntentGatewayV2.sol` fixed exactly this class of bug — it snapshots balances before/after transfers and mutates `order.inputs[i].amount` to the actual received amount before computing fees/commitment/escrow (see `evm/src/apps/IntentGatewayV2.sol:260-298`). However, the parallel Tron deployment target still contains the unfixed pattern.This confirms the vulnerable pattern is complete: `withdraw()` blindly debits `_orders[commitment][token] -= amount` and pushes tokens to the beneficiary without any check that the contract's actual token balance covers the ledger, exactly the same class of bug the external report flags (accounting value diverges from actual custody, with no reconciliation before payout).

### Title
Escrow ledger credited with pre-fee-on-transfer amount instead of actual received tokens in Tron `IntentGatewayV2.placeOrder`, causing escrow insolvency and fund loss/lock on withdrawal - (`evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In the Tron deployment of `IntentGatewayV2.sol`, `placeOrder()` credits the internal `_orders[commitment][token]` escrow ledger with `reducedInputs[i].amount` — a value computed purely from the user-declared `order.inputs[i].amount` minus the protocol fee — without verifying how many tokens the contract actually received via `safeTransferFrom`. This is the same broken invariant as the SecuritizeVault report: a value derived from a formula is used for accounting/payout instead of the measured, actual balance change from an external token interaction.

`reducedInputs[i].amount` is derived from the *requested* `order.inputs[i].amount` (see `evm/tron/contracts/apps/IntentGatewayV2.sol:342-379`), not from any post-transfer balance measurement. If `token` is a fee-on-transfer / rebasing token (or any ERC20 whose `transferFrom` delivers less than the nominal amount — behavior the codebase itself explicitly anticipates and tests for in the fixed sibling contract, e.g. `FeeOnTransferToken` in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2502`), the gateway's actual token balance increases by less than `reducedInputs[i].amount`, yet the ledger is credited with the full `reducedInputs[i].amount`.

Contrast this with the corresponding, fixed logic in the primary EVM contract, which snapshots `balBefore`/`balAfter` and mutates `order.inputs[i].amount` to the true received amount before any fee/commitment/escrow math is done: [2](#0-1) 

The Tron contract never received this fix. Because `_orders` is a shared pooled-balance ledger against the contract's single token balance (not segregated per-commitment vaults), the shortfall from one order's fee-on-transfer input directly reduces the real tokens backing *every other* order's escrow entries in that token. Withdrawal via `onAccept`/`withdraw()` performs no balance sufficiency check — it only checks `_orders[commitment][token] != 0` before blindly calling `token.transfer(beneficiary, amount)`: [3](#0-2) 

### Impact Explanation
This produces a pooled-accounting insolvency: the sum of all `_orders[*][token]` ledger balances can exceed the contract's actual token balance. Consequences:
- Whichever beneficiary claims (settles/refunds) first drains real tokens that other commitments' escrow entries still logically claim, meaning a later legitimate beneficiary's `withdraw()` call reverts (`TransferFailed`) because the pooled balance is exhausted — a direct loss/lock of escrowed user or solver funds belonging to someone else's already-accounted-for order.
- This matches the bounty's "stealing or loss of funds" / unauthorized value transfer class: value that should be exclusively earmarked for one commitment is fungibly consumed by another, with no malicious peer, relayer, or admin required — only a normal user placing an order with a standard fee-on-transfer token (a widely deployed token category) via the completely public, unprivileged `placeOrder` entrypoint.

### Likelihood Explanation
`placeOrder` is a permissionless, unauthenticated public entrypoint; no relayer, prover, or governance action is needed. The only precondition is that the order's input token charges a transfer fee or otherwise delivers less than the nominal `safeTransferFrom` amount — a property visible on-chain and controllable simply by which token an order specifies. The bug is deterministic once such a token is used, not probabilistic.

### Recommendation
Mirror the fix already applied in `evm/src/apps/IntentGatewayV2.sol`: measure `balanceOf(address(this))` before and after each `safeTransferFrom`, use the actual delta to recompute `order.inputs[i].amount`, and derive `reducedInputs`/`commitment`/escrow credits from that measured amount rather than the caller-declared amount, for both the predispatch and direct-transfer branches of the Tron contract.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a fee-on-transfer ERC20 (e.g., 1% fee) as a supported input token, protocol fee = 0 for simplicity.
2. User A calls `placeOrder` with `inputs[0].amount = 1000`. Gateway actually receives `990` tokens via `safeTransferFrom`, but `_orders[commitmentA][token] += 1000` (full nominal amount, since `reducedInputs == order.inputs` when `protocolFeeBps == 0`).
3. Gateway's real token balance is `990`, but ledger claims `1000` owed to commitment A alone.
4. Repeat with User B placing a second order with the same token, amount `1000`: gateway receives another `990` (total real balance `1980`), ledger now shows `1000 + 1000 = 2000` owed across A and B.
5. Solver fills order A and later triggers `withdraw()`/`onAccept` `RedeemEscrow` for commitment A with `amount = 1000`: `token.transfer(beneficiary, 1000)` succeeds (contract holds 1980), `_orders[commitmentA][token]` zeroed.
6. Solver then attempts to redeem commitment B for `amount = 1000`, but the contract only holds `980` tokens left — `token.transfer` reverts with `TransferFailed`, permanently reverting/locking commitment B's legitimately-escrowed settlement, while commitment A's beneficiary received tokens that were partly backed by B's principal.
