## Title
OS-level certificate trust exception is not scoped to the originating host, breaking per-host TLS trust boundary — (`File: app/src/ui/app.tsx`, `app/src/main-process/app-window.ts`)

## Summary
When a user clicks "Always trust" in the `UntrustedCertificate` dialog, GitHub Desktop calls `showCertificateTrustDialog(certificate, message)` which is forwarded over IPC to the main process and ultimately to Electron's native `dialog.showCertificateTrustDialog(window, { certificate, message }, callback)`. At no point in this call chain is the originating URL/hostname passed along or used to scope the trust decision — the trust exception is created purely from the `Electron.Certificate` object at the OS level (macOS Keychain / Windows certificate store).

## Finding Description
The flow is:

1. Main process TLS handler intercepts `certificate-error`, forwards `certificate`, `error`, `url` to renderer: [1](#0-0) 

2. Renderer shows the `UntrustedCertificate` popup with the `url` (used only to render the hostname in the dialog text) and the `certificate`: [2](#0-1) 

3. On the user's "Always trust" action, only the `certificate` object is passed forward — the `url`/host is dropped entirely: [3](#0-2) [4](#0-3) 

4. `showCertificateTrustDialog` (renderer→main IPC) and the underlying `RequestChannels['show-certificate-trust-dialog']` signature only carry `certificate` and `message`, with no host parameter: [5](#0-4) 

5. In the main process, the handler invokes Electron's native `dialog.showCertificateTrustDialog`, again with only `certificate` and `message`: [6](#0-5) [7](#0-6) 

Electron's `dialog.showCertificateTrustDialog` API itself takes no URL/host argument — it exists specifically to add a certificate to the OS-level trust store (macOS Keychain trust settings, or the Windows certificate store via the native cert UI), which is a system-wide, certificate-identity-based trust decision, not a per-host/per-origin one. GitHub Desktop's implementation does not perform any additional host binding (e.g., recording "trust this certificate fingerprint only for host X" and re-validating hostname+certificate pairing on subsequent connections) before or after invoking this dialog.

The only per-URL mechanism that exists in the codebase, `isCertificateErrorSuppressedFor`/`suppressCertificateErrorFor` in `app/src/lib/suppress-certificate-error.ts`, is a simple in-memory `Set<string>` of URLs used to suppress showing the dialog again for the *same exact URL string* during a session (e.g. for endpoint-probing requests) — it is not used to scope or gate the actual OS trust decision made via `showCertificateTrustDialog`, and it doesn't tie the trust decision to a specific certificate at all. [8](#0-7) 

Consequently, once a certificate is trusted this way, the OS validates future TLS handshakes against its trust store by certificate identity, independent of which host presented it. Any subsequent HTTPS connection — from Git operations, LFS, or GitHub.com API/token requests performed by the app or even other OS processes that rely on the same trust store — that encounters the identical certificate (e.g., a network-position attacker reusing the same leaf cert against a different hostname, since the app performs no hostname-binding check itself) will be accepted as trusted, rather than the exception being confined to the single host under REQUIRED_STATE for which the user made the trust decision.

## Impact Explanation
If an attacker who already has some network interception capability (e.g., a malicious/compromised proxy in the git remote traffic path, matching the "git remote/proxy response" attacker model in scope) can get the user to accept a certificate for a malicious host, and later intercepts traffic to `api.github.com` (or GHE) presenting that same trusted certificate, GitHub Desktop's underlying networking (Chromium/Electron net stack and/or Node https for API calls) would treat that connection as trusted, enabling interception of GitHub API requests and OAuth/PAT credentials — a credential-exfiltration outcome that is explicitly in the Valid Impact list.

## Likelihood Explanation
Exploitation still requires the attacker to have a network man-in-the-middle position for the secondary (GitHub.com) connection, in addition to controlling the initial malicious git remote/host. This is not purely a passive "clone a malicious repo" scenario — it requires the attacker to also intercept subsequent HTTPS traffic and present the exact same certificate object that was trusted. It is a real architectural gap (no host binding on the trust exception) rather than a directly, trivially remotely-triggerable exploit purely from repository content.

## Recommendation
- Do not rely solely on Electron's OS-wide `showCertificateTrustDialog`. Instead, maintain an app-level, in-memory (session-scoped) map of `(host, certificate fingerprint)` pairs that were explicitly trusted by the user, and consult this map in the `certificate-error` handler (`app/src/main-process/main.ts`) before allowing the connection — i.e., call `callback(true)` only if the specific host+fingerprint pair was previously approved, instead of delegating trust entirely to the OS store.
- Pass the `url`/hostname through `onContinueWithUntrustedCertificate` and the `show-certificate-trust-dialog` IPC channel so any additional validation/logging can bind the decision to the origin.
- Consider warning users more explicitly that "Always trust" adds a system-wide certificate exception (not scoped to GitHub Desktop or to this host) so they understand the actual blast radius before consenting.

## Proof of Concept
1. Set up a malicious git server ("Host A") presenting a self-signed certificate, and add it as a remote in GitHub Desktop; trigger a fetch/clone so the `certificate-error` dialog appears, click "Always trust".
2. Confirm via OS certificate store (Keychain Access on macOS, `certmgr.msc` on Windows) that the certificate was added to system-wide trust, with no association to Host A's hostname recorded anywhere in GitHub Desktop's own state.
3. Set up a second endpoint ("Host B", e.g. simulate `api.github.com` via hosts-file redirection in a controlled test) serving the *same* certificate/key pair used for Host A.
4. Trigger a GitHub Desktop request to Host B (e.g., an API/token request) and observe that no `certificate-error` is raised and the connection succeeds/trusts the certificate, despite the user only ever having agreed to trust Host A's certificate — demonstrating the trust boundary is bound to the certificate object, not the host, at the `showCertificateTrustDialog` call in [4](#0-3)  and [6](#0-5) .

const suppressedUrls = new Set<string>()

export function suppressCertificateErrorFor(url: string) {
  suppressedUrls.add(url)
}

export function clearCertificateErrorSuppressionFor(url: string) {
  suppressedUrls.delete(url)
}

export function isCertificateErrorSuppressedFor(url: string) {
  return suppressedUrls.has(url)
}
