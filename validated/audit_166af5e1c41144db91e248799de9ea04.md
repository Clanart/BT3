## Finding

### Title
Previous DID owner retains unrevoked recovery authority after DID transfer, enabling asset theft via stale `backup_ids` - (File: `chia/wallet/did_wallet/did_wallet.py`)

### Summary
When a DID is transferred to a new owner, the DID's `backup_ids` (recovery list) are carried over into the new owner's inner puzzle unless the seller explicitly clears them. Because DID recovery mode allows any party controlling a quorum of `backup_ids` to reassign the DID's `p2_puzzle` (i.e., seize spend authority) without the current owner's signature, a malicious seller can leave their own keys in the recovery list before selling, then later use the recovery-attestation flow to steal the DID (and any NFTs/assets bound to that DID) from the buyer — the same "unrevoked approval" bug class as the Footium escrow report, adapted to Chia's DID recovery mechanism instead of ERC20-style `approve()`.

### Finding Description
A DID singleton's inner puzzle is curried with a `recovery_list` (`backup_ids`) and a `num_of_backup_ids_needed` threshold [1](#0-0) . This recovery mechanism lets designated "backup" identities recreate the DID coin with a new `p2_puzzle` (i.e., take over ownership) by producing an attestment message signed via `AGG_SIG_UNSAFE`, independent of the current owner's spend key [2](#0-1) .

When a DID is transferred to a new owner via `transfer_did`, the code explicitly re-uses the existing `backup_ids`/`num_of_backup_ids_needed` from `self.did_info` to construct the new owner's inner puzzle, rather than clearing them: [3](#0-2) 

The related helper `get_innerpuz_for_new_innerhash` makes the danger explicit in its own comment: the recovery list is *kept* across ownership change and must be manually cleaned by the seller before transfer: [4](#0-3) 

This is the direct Chia analog of the Footium finding: instead of an ERC20/NFT `approve()` call that a malicious seller leaves un-revoked, the malicious seller leaves their own (or colluding) DID(s) in the `backup_ids` recovery list. After a sale, if the seller retains any control over those backup-list identities, they can trigger the DID's recovery path and reassign the DID's owner puzzle hash to themselves — recovering control of the DID and anything tied to it (NFT ownership, DID-gated CR-CATs, VC proof-provider identity, etc.) without the buyer's cooperation or signature.

The codebase itself independently acknowledges this exact risk pattern elsewhere for a similar situation — when identifying a DID whose recovery list was reset, it logs a warning noting "the previous owner" reset the list, showing this is a recognized attack surface for DID ownership transfer flows [5](#0-4) .

### Impact Explanation
A buyer who purchases a DID (directly, or bundled as an NFT whose ownership is tied to a DID) without independently verifying and forcing a reset of the recovery list can be silently rugged: the seller (or an accomplice acting as one of the stale backup ids) can later execute the DID recovery flow and reclaim spend authority over the DID coin. This is equivalent to "unrevoked approval" theft — the seller extracts control of an asset the buyer believed they now owned exclusively. This can lead to loss of the DID identity itself and cascading loss of control over any assets (NFTs, DID-gated CATs, VC-based credentials) that rely on that DID for authorization.

### Likelihood Explanation
Exploitation requires the seller to deliberately leave manipulable `backup_ids` in place (e.g., their own alternate keys) prior to sale — this is a seller-initiated, not attacker-initiated, condition, similar to the original Footium report where the previous owner is the attacker. Given that `transfer_did` and `get_innerpuz_for_new_innerhash` preserve the recovery list by default and rely on the seller "cleaning the recovery list" out-of-band, an unsophisticated seller (or a malicious one) can easily leave this attack vector open, and a buyer has no on-chain guarantee it was cleared unless they explicitly inspect and require an empty recovery list before accepting the DID.

### Recommendation
- Require (or default to) clearing `backup_ids`/setting `num_of_backup_ids_needed` to 0 whenever a DID transfer is initiated via `transfer_did`, rather than relying on the seller to opt in to clearing the list.
- Surface a clear warning/blocking check in offer-acceptance / DID-transfer wallet RPCs when a DID being purchased still has a non-empty recovery list, forcing explicit buyer acknowledgment.
- Consider versioning the recovery configuration so buyers can verify cryptographically that no residual recovery authority exists at the time of purchase.

### Proof of Concept
1. Seller creates a DID with `backup_ids = [seller_backup_id]`, `num_of_backup_ids_needed = 1`.
2. Seller lists/sells the DID (or an NFT owned by the DID) to Buyer via an offer; `transfer_did` is used, which re-curries the inner puzzle with the same `backup_ids` [6](#0-5) .
3. Buyer receives the DID, unaware the recovery list still lists the seller's backup id.
4. Seller creates a recovery attestment message spend using `create_spend_for_message` with their `seller_backup_id`'s key, satisfying the recovery threshold [7](#0-6) .
5. Seller completes the DID recovery spend, reassigning the DID's `p2_puzzle` to themselves, reclaiming control of the DID and any bound assets — without Buyer's signature.

def uncurry_innerpuz(puzzle: Program) -> tuple[Program, Program, Program, Program, Program] | None:
    """
    Uncurry a DID inner puzzle
    :param puzzle: DID puzzle
    :return: Curried parameters
    """
    r = puzzle.uncurry()
    if r is None:
        return r
    inner_f, args = r
    if not is_did_innerpuz(inner_f):
        return None

    p2_puzzle, id_list, num_of_backup_ids_needed, singleton_struct, metadata = list(args.as_iter())
    return p2_puzzle, id_list, num_of_backup_ids_needed, singleton_struct, metadata

def create_recovery_message_puzzle(recovering_coin_id: bytes32, newpuz: bytes32, pubkey: G1Element) -> Program:
    """
    Create attestment message puzzle
    :param recovering_coin_id: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: Message puzzle
    """
    puzzle = Program.to(
        (
            1,
            [
                [ConditionOpcode.CREATE_COIN_ANNOUNCEMENT, recovering_coin_id],
                [ConditionOpcode.AGG_SIG_UNSAFE, bytes(pubkey), newpuz],
            ],
        )
    )
    return puzzle


def create_spend_for_message(
    parent_of_message: bytes32, recovering_coin: bytes32, newpuz: bytes32, pubkey: G1Element
) -> CoinSpend:
    """
    Create a CoinSpend for a atestment
    :param parent_of_message: Parent coin ID
    :param recovering_coin: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: CoinSpend
    """
    puzzle = create_recovery_message_puzzle(recovering_coin, newpuz, pubkey)
    coin = Coin(parent_of_message, puzzle.get_tree_hash(), uint64(0))
    solution = Program.to([])
    return make_spend(coin, puzzle, solution)
