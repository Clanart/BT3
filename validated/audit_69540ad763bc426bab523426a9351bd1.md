### Title
Unauthenticated on-chain "mirror" URLs force DataLayer nodes into attacker-controlled outbound HTTP requests (SSRF-style RESTLESS analog) - ([File: chia/data_layer/data_layer_wallet.py])

### Summary
Chia's DataLayer mirror mechanism lets any spend-bundle submitter create a `CREATE_COIN` output to the fixed `create_mirror_puzzle()` puzzle hash with a memo containing an arbitrary `launcher_id` and arbitrary URL strings. Any wallet tracking that `launcher_id` will ingest the URL as a legitimate mirror server and the DataLayer service will later issue outbound HTTP GET requests to it during subscription sync, without any check that the submitter owns or controls the referenced store. This mirrors the CVE-2018-12907 "RESTLESS" pattern: an externally supplied, unvalidated URL field is trusted and used to trigger outbound network requests from the victim node.

### Finding Description
`create_mirror_puzzle()` returns `P2_PARENT.curry(Program.to(1))`, a puzzle with no signature/ownership binding to the `launcher_id` [4](#0-3) . Any spend bundle can create a coin at this puzzle hash with memos `[launcher_id, url1, url2, ...]`, and `get_mirror_info()` extracts the `launcher_id`/URLs purely from the `CREATE_COIN` condition memo, with no proof that the spender is authorized for that `launcher_id` [5](#0-4) .

When a wallet observes such a coin via `coin_added`, it only checks that the `launcher_id` is tracked locally (`is_launcher_tracked`) before persisting the mirror record — there is no check that the submitter is the store owner or that the URL is well-formed/safe [2](#0-1) .

`DataLayer.update_subscriptions_from_wallet()` pulls these mirror URLs directly from wallet RPC and feeds them into the local subscription table with no filtering [6](#0-5) . The periodic `fetch_and_validate()` loop then selects one of these URLs and calls `insert_from_delta_file()` → `download_file()` → `http_download()`, which performs an unrestricted `aiohttp` `GET` to `server_info.url + "/" + filename` [3](#0-2) . There is no allowlist, no restriction on internal/loopback/link-local addresses, and no validation of the URL's origin/scheme beyond what `aiohttp` itself enforces.

The result: an unprivileged actor who merely knows a victim's public `launcher_id` (store id) — trivially discoverable since DataLayer store roots and singleton data are on-chain/public — can submit an ordinary, otherwise-valid spend bundle that creates a mirror coin advertising a malicious URL for that store. Every node that syncs/subscribes to that store (any DataLayer client tracking that dataset) will then automatically issue outbound HTTP requests to the attacker-chosen URL on its normal sync interval, with no operator/owner action required.

### Impact Explanation
This lets an unprivileged spend-bundle submitter cause other users' DataLayer nodes to make network requests to attacker-chosen destinations (including internal-network or loopback addresses reachable from the victim host), on a recurring background schedule. This is a classic SSRF/RESTLESS primitive: it can be used to probe internal network topology/services from the victim's vantage point, to perform request-based DoS/amplification against third parties by directing many DataLayer nodes to hit one URL simultaneously, or to fingerprint/target machines behind NAT. Because the trigger is a normal, unsigned-with-respect-to-victim spend condition (no signature over the victim's `launcher_id` is required), any wallet-owning attacker can mount this against arbitrary tracked stores. This satisfies "spend-triggered transaction-processing" reachability and network-request side effects from a single submitted spend bundle.

### Likelihood Explanation
High likelihood of exploitability: creating a `CREATE_COIN` output with an arbitrary puzzle hash and memo list is a completely standard, always-available spend bundle operation requiring no special conditions, cost budget, or privileged keys — only a `launcher_id` value, which is public. The mirror-ingestion and subscription-sync code paths run unconditionally as part of normal DataLayer operation (`periodically_manage_data()` → `update_subscription()` → `fetch_and_validate()`), so any node subscribing to or owning the targeted store will eventually process the malicious mirror without any user interaction.

### Recommendation
- Require that `add_mirror`/`create_new_mirror` bind the mirror coin to proof of ownership or authorization of the `launcher_id` (e.g., require the mirror coin's creation to be part of a spend that also proves control of the corresponding DataLayer singleton, or otherwise sign/attest the mirror to the store owner) rather than trusting bare memo data from any spend.
- Validate mirror URLs before storing/using them: enforce scheme allowlists (http/https only), reject loopback/link-local/private IP ranges (or make this configurable and default-deny), and cap the rate/number of distinct mirrors accepted per store.
- Consider requiring explicit user confirmation/opt-in per mirror URL (or per new mirror-URL host) before the DataLayer service will issue outbound requests to it.

### Proof of Concept
1. Attacker learns any victim-tracked DataLayer `launcher_id` (public on-chain data).
2. Attacker constructs and submits a standard spend bundle whose spend includes a `CREATE_COIN` condition to `create_mirror_puzzle().get_tree_hash()` with `amount>=1` and memo `[launcher_id, b"http://169.254.169.254/latest/meta-data/", ...]` (or any attacker-controlled callback URL) — see `create_mirror_puzzle()`/`get_mirror_info()` for the expected memo shape [1](#0-0) .
3. Once the spend bundle is included in a block, any wallet tracking that `launcher_id` ingests the mirror via `coin_added()` with no ownership check [2](#0-1)  and the DataLayer service will pick it up via `update_subscriptions_from_wallet()` [6](#0-5) .
4. On the next `periodically_manage_data()`/`fetch_and_validate()` cycle, the victim's DataLayer process issues an HTTP GET to the attacker-supplied URL via `http_download()` [3](#0-2) , confirming outbound request delivery to attacker infrastructure/target without any action by the victim's operator beyond normal store subscription/ownership.

```python
def create_mirror_puzzle() -> Program:
    return P2_PARENT.curry(Program.to(1))


MIRROR_PUZZLE_HASH = create_mirror_puzzle().get_tree_hash()


def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
```

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
```
