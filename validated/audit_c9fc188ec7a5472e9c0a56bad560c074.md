### Title
Cached FROST preprocess seed reused across signing attempts enables private share recovery via nonce reuse (ROS/parallel-session) — (`coordinator/src/tributary/signing_protocol.rs`)

### Summary
The coordinator caches a FROST preprocess seed keyed only by `context`, then deterministically regenerates the same nonces from that seed via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` on every call to `preprocess_internal`. Because `share_internal` calls `preprocess_internal` again, any retry of the signing round — including one triggered by a malicious participant submitting a different preprocess set — reuses identical nonces under a different binding factor, allowing recovery of the secret share. This mirrors the "ghost domain" bug class: stale cached state kept alive and reused past its intended single-use lifetime, where the fix requires invalidating/revalidating the cached value rather than trusting it.

### Finding Description
- `preprocess_internal` stores `CachedPreprocesses` keyed by `self.context` only; once set, the same 32-byte seed is XOR-decrypted and fed to `AlgorithmSignMachine::from_cache` on every subsequent invocation ( [1](#0-0) ).
- `from_cache` calls `seeded_preprocess`, which seeds `ChaCha20Rng` solely from `seed.0` and derives `nonces`/`commitments` deterministically — the same seed always yields the same nonces `d, e` ( [2](#0-1) [3](#0-2) ).
- `share_internal` calls `self.preprocess_internal(participants).0` fresh for every share round, so each attempt signs with the same `d, e` but a potentially different `included`/preprocess map — hence a different binding factor `rho_i` and different message — while producing `share = d + e·rho + λ·s·c` ( [4](#0-3) ).
- The spec and code comments explicitly state a preprocess "MUST only be used once. Reuse will enable third-party recovery of your private key share" ( [5](#0-4) [6](#0-5) ).

### Impact Explanation
Two observed shares `s₁ = d + e·ρ₁ + λ·x·c₁` and `s₂ = d + e·ρ₂ + λ·x·c₂` over the same nonces `d,e` but different `ρ`/`c` give two equations letting the attacker solve for `x` (the validator's threshold secret share). Combined with `t−1` known shares or further ROS grinding, this compromises the tributary/validator signing key — full key-share recovery, the worst outcome for FROST.

### Likelihood Explanation
An unprivileged counterparty (any participant in the signing set) can submit invalid or varying preprocess bytes; each failure/retry path (`InvalidPreprocess` → coordinator re-attempt, or multiple `CoordinatorMessage::Preprocesses` rounds under the same context id) re-runs `share_internal`, regenerating identical nonces. No reboot or DB corruption is needed — only a repeated signing attempt under the same cached context, which is the designed recovery path.

### Recommendation
Bind the cache entry to one-shot use: delete `CachedPreprocesses` after the first `share_internal` consumes it, or key the cache by `(context, participants, attempt)` and refuse regeneration after a completed `sign`. Alternatively, mix a per-attempt counter or the sorted `included` set into the ChaCha20 seed so retries cannot reproduce identical nonces.

### Proof of Concept
1. Participant A observes round 1: honest validator V runs `share_internal`, producing share `s₁` over preprocess set P₁ → binding `ρ₁`, challenge `c₁`.
2. A triggers a retry (invalid preprocess, new attempt under same `context`) with a modified preprocess set P₂. `preprocess_internal` returns the same `CachedPreprocess` seed → identical `d,e` → share `s₂` over `ρ₂, c₂`.
3. A computes `(s₁−s₂) = e(ρ₁−ρ₂) + λx(c₁−c₂)`; with `e` known from V's commitments and `λ` computable, solve for `x` — V's secret share is recovered.

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }

Reusing preprocesses would enable a third-party to recover your private key
share. Accordingly, you MUST not reuse preprocesses. Third-party knowledge of
your preprocess would also enable their recovery of your private key share.
Accordingly, you MUST treat cached preprocesses with the same security as your
private key share.

Since a reused seed will lead to a reused preprocess, seeded RNGs are generally
frowned upon when doing multisignature operations. This isn't an issue as each
new preprocess obtains a fresh seed from the specified RNG. Assuming the
provided RNG isn't generating the same seed multiple times, the only way for
this seeded RNG to fail is if a preprocess is loaded multiple times, which was
already a failure point.
