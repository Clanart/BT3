### Title
Hardcoded `BRIDGE_CONTRACT_ADDRESS` in `CitreaClient` Ignores Configurable Field, Breaking All Deposit/Withdrawal Detection and Storage-Proof Fetching on Any Non-Default Deployment — (`core/src/citrea.rs`)

---

### Summary

`core/src/citrea.rs` declares a hardcoded compile-time constant `BRIDGE_CONTRACT_ADDRESS = "0x3100000000000000000000000000000000000002"` and uses it unconditionally inside `CitreaClient::new()` and `get_storage_proof()`. The `CitreaClientT::new()` trait signature accepts no `bridge_contract_address` parameter, so the configurable `BridgeConfig::bridge_contract_address` field — which is correctly read from the environment and config files — is silently discarded and never applied. Every deposit scan, withdrawal scan, nofn-correctness check, and EIP-1186 storage-proof fetch always targets the hardcoded address, regardless of what the operator configured.

---

### Impact Explanation

Every bridge-critical operation that goes through `CitreaClient` is affected:

| Operation | Method | Effect of wrong address |
|---|---|---|
| Deposit detection | `collect_deposit_move_txids` via `self.contract` | Returns empty or wrong deposit list; deposits never finalized |
| Withdrawal detection | `collect_withdrawal_utxos` via `self.contract` | Returns empty or wrong withdrawal list; payouts never triggered |
| N-of-N key correctness | `check_nofn_correctness` via `self.contract` | Checks wrong contract; may pass or fail incorrectly |
| Storage proof for assert | `get_storage_proof` | Fetches EIP-1186 proof from wrong contract; proof is invalid for the actual bridge state |

If the bridge contract is deployed at any address other than `0x3100000000000000000000000000000000000002` — which is expected for mainnet, a fresh testnet deployment, or any multi-instance setup — the bridge silently operates against the wrong contract. Deposits are never collected, withdrawals are never paid out, and storage proofs submitted in assert transactions are fetched from the wrong account, making them invalid for the actual bridge circuit verification. This constitutes a complete liveness failure for all bridged BTC.

---

### Likelihood Explanation

The `0x3100000000000000000000000000000000000002` address is a Citrea-specific precompile/genesis address used in regtest and testnet4 configurations. On mainnet or any deployment where the bridge contract is at a different address, the bug is triggered automatically on startup with no special attacker action required. The operator has no way to override it at runtime because the config field is silently ignored.

---

### Recommendation

1. Add `bridge_contract_address: String` (or `alloy::primitives::Address`) as a parameter to `CitreaClientT::new()`.
2. In `CitreaClient::new()`, parse and use the passed address instead of the hardcoded constant.
3. In `get_storage_proof()`, use `self.contract.address()` (already stored in the contract binding) instead of the bare `BRIDGE_CONTRACT_ADDRESS` constant.
4. Remove or make the `BRIDGE_CONTRACT_ADDRESS` constant test-only (`#[cfg(test)]`).
5. At all call sites, pass `config.bridge_contract_address` when constructing `CitreaClient`.

---

### Proof of Concept

1. Deploy the bridge contract at address `0xDeAdBeEf...` (any address ≠ `0x3100000000000000000000000000000000000002`).
2. Set `BRIDGE_CONTRACT_ADDRESS=DeAdBeEf...` in the operator's environment.
3. Start the operator. `BridgeConfig::bridge_contract_address` is correctly parsed as `0xDeAdBeEf...`.
4. `CitreaClient::new()` is called — it ignores the config and binds `self.contract` to `0x3100000000000000000000000000000000000002`.
5. `collect_deposit_move_txids()` queries `depositTxIds()` on the wrong contract; the call reverts or returns stale data.
6. `get_storage_proof()` calls `eth_getProof` against `0x3100000000000000000000000000000000000002`; the returned Merkle proof is for the wrong account and will fail bridge-circuit storage-proof verification.
7. No deposits are ever finalized and no withdrawals are ever paid out — complete bridge liveness failure with all bridged BTC permanently locked.
