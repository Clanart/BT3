### Title
`ThresholdKeys::read` accepts a crafted key blob whose `secret_share` is never validated against `verification_shares`, letting attacker-chosen bytes instantiate a fully attacker-controlled group key - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to GHSA-q92j-grw3-h492 (crafted schema input instantiates objects with attacker-chosen semantics), `ThresholdKeys::read` reconstructs a `ThresholdKeys` object entirely from untrusted bytes — a tag byte selects the `Interpolation` variant, and `secret_share`, `params`, and `verification_shares` are all deserialized verbatim. `ThresholdKeys::new` validates count/index/invariant boilerplate but never checks the fundamental consistency relation `secret_share * G == verification_shares[i]`, and never checks that the interpolated `group_key` corresponds to any party's share. A crafted blob therefore instantiates a "threshold key" whose group public key the attacker knows the discrete logarithm for.

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) reads:
- a curve ID check,
- `t`, `n`, `i` (validated by `ThresholdParams::new`/`Participant::new`),
- a one-byte tag selecting `Interpolation::Constant(Vec<F>)` (n scalars) or `Interpolation::Lagrange`,
- `secret_share` via `C::read_F`,
- `n` verification shares via `read_G`,

then calls `ThresholdKeys::new` (lib.rs:349-391). `new` only checks `verification_shares.len() == n`, participant indexes ≤ n, and `Constant` ⇒ `t == n`. It computes `group_key = Σ_{i=1..=t} verification_shares[i] * interpolation_factor(i)` with **no check that `C::generator() * secret_share == verification_shares[i]`** and no proof tying the deserialized shares to the derived group key.

Like the GraphQL flaw — where untrusted JSON selected which Ruby classes/objects to instantiate — the tag byte selects the interpolation implementation (`Constant` with attacker-supplied coefficient vector vs `Lagrange`), and every field of the resulting object is attacker-dictated.

### Impact Explanation
Whoever feeds these bytes into `ThresholdKeys::read` (key backup/restore, key import, `dkg-recovery` output ingestion) receives a `ThresholdKeys` where:
- `secret_share` is a scalar the attacker chose,
- `group_key()` is `Σ attacker-chosen verification shares` — a point whose discrete log the attacker knows by construction (e.g., set all `verification_shares[l] = G * a_l` with known `a_l`; then `group_key = G * (Σ a_l · λ_l)`),
- `view()` will happily produce `ThresholdView`s and the victim will perform FROST `sign`/`complete` rounds under this key.

The resulting "threshold group" is a 1-of-1 key the attacker fully controls: they can produce the complete signature for any message without any honest participation, i.e., every signature the victim co-produces under this group key is forged/forgable by the attacker, and any funds under that `group_key` are spendable only by the attacker. Conversely, `secret_share` need not be consistent with `verification_shares[i]` at all, so a crafted blob also silently replaces the victim's true share.

### Likelihood Explanation
Reachable whenever serialized `ThresholdKeys` originate from an untrusted or transportable source (backup files, key-recovery blobs, `crypto/dkg/recovery` artifacts) rather than purely in-memory DKG output — exactly the class of inputs the scope rules admit for `ThresholdKeys::read`. It requires an attacker to supply the blob, which is a lower-probability path than a live protocol message, hence High rather than Critical.

### Recommendation
In `ThresholdKeys::new` (or at the end of `read`), enforce `C::generator() * secret_share == verification_shares[&params.i()]`, and document/verify that the deserialized `interpolation`/`verification_shares` reproduce the expected `group_key`. Reject blobs failing the check before constructing `ThresholdCore`.

### Proof of Concept
1. Attacker picks scalars `a_1..a_n` and sets `verification_shares[l] = G * a_l`.
2. Sets interpolation tag to `0x01` (Lagrange), `secret_share` to any scalar `x`.
3. Serializes: `u32(C::ID.len()) || C::ID || t || n || i || 0x01 || x || G·a_1 .. G·a_n`.
4. `ThresholdKeys::read` succeeds; `group_key() = G * (Σ a_l · λ_l(0))` — discrete log known to attacker.
5. Victim imports the blob and runs FROST `sign`/`complete`; the attacker unilaterally produces the same group signature for any message (or observes the victim's partial shares inconsistent with `verification_shares`, since `x` was unconstrained).
