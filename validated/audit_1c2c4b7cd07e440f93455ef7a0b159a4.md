### Title
Reward-tier double-counting in `getRewardAmount`/`calDoubledCounted` inflates vlMGP reward beyond real mWomSV backing for `_mode=2` deposits - ([File: wombat/ArbWomUp3.sol])

### Summary
`incentiveDeposit` with `_mode == 2` only locks **half** of the deposited WOM into `mWomSV` (the other half is swapped via `smartWomConvert`), but `getRewardAmount`'s `accumulated` value adds the **full** `_amountToConvert` to the previous `mWomSV.getUserTotalLocked(_account)` balance when computing the tier reward. Because `calDoubledCounted` later subtracts the "already rewarded" amount using only the real (half-sized) `mWomSV` balance, each successive `mode=2` deposit credits more MGP than the actual WOM backing locked, letting an attacker repeatedly call `incentiveDeposit(..., true, 2)` to mint more locked MGP via `vlMGP.lockFor` than their real staked/locked WOM entitles them to.

### Finding Description
In `wombat/ArbWomUp3.sol`: [1](#0-0) 

`getRewardAmount` computes, for `_lock == true`:
```
accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account)
```
and derives a tiered `rewardAmount`, then subtracts `calDoubledCounted(_account)`, which recomputes the tiered reward using only the account's *current real* `mWomSV.getUserTotalLocked(_account)` balance: [2](#0-1) 

The subtraction is only correct if a prior deposit's `accumulated` figure equals the actual amount subsequently locked into `mWomSV`. That assumption breaks for `_mode == 2`, where `_deposit` only locks half the WOM into `mWomSV`: [3](#0-2) 

Concretely, `getRewardAmount` is called *before* `_deposit` executes in `incentiveDeposit`: [4](#0-3) 

So on the first `mode=2` call, `accumulated` uses the **full** deposit amount even though only half will actually be locked. On the second call, `calDoubledCounted` bases its "already counted" subtraction on the real (half-sized) `mWomSV` balance, understating what was previously credited. This mismatch causes systematic over-crediting on every successive `mode=2` deposit by the same account, with no reentrancy or race condition needed — just two sequential `incentiveDeposit(amount, ratio, true, 2)` calls by the same address.

Numeric example (tier0: 0–1000 @ multiplier 100, tier1: >1000 @ multiplier 200, DENOMINATOR=10000):
- Call 1 with amount=1000: `accumulated=1000`, undoubled reward=10, mode-2 doubles → 20 vlMGP minted. Real `mWomSV` lock added = 500.
- Call 2 with amount=1000: `accumulated=1000+500=1500`, raw reward=20, minus `calDoubledCounted(500)=5` → 15, doubled → 30 vlMGP minted. Real `mWomSV` lock added = another 500.

Total minted: 50 vlMGP-equivalent MGP for a final real `mWomSV` backing of only 1000 WOM-equivalent, whereas the fair single-shot reward for 1000 locked is only 20. The attacker extracts an extra 30 units of MGP reward unsupported by actual staked backing — nothing in `incentiveDeposit`, `getRewardAmount`, or `calDoubledCounted` prevents this because the double-count guard (`calDoubledCounted`) does not account for the 50/50 split performed by `_deposit` under `_mode == 2`.

### Impact Explanation
This is a direct theft of unclaimed MGP yield: `vlMGP.lockFor` mints locked MGP to the attacker in excess of what their real WOM/`mWomSV` stake backs, draining the `mgp` balance held by `ArbWomUp3` faster than intended and diluting the reward pool available to legitimate depositors. This matches the "theft of unclaimed yield" impact class.

### Likelihood Explanation
Fully feasible by any unprivileged WOM holder: only requires calling the public `incentiveDeposit` function twice (or more) with `_mode = 2` and `_lock = true`, using only WOM tokens the attacker already owns. No special privileges, front-running of other users, or reentrancy is actually required — the loophole is present even in two ordinary sequential transactions since `getRewardAmount` is evaluated before `_deposit`'s partial lock takes effect each time. Repeatable across many small deposits to further compound the double-count gain (subject to available `mgp` balance in the contract, capped by `mgpleft` check).

### Recommendation
Track and compare against the real cumulative amount actually locked into `mWomSV` rather than re-deriving `accumulated` from `_amountToConvert` under `_mode == 2`. Specifically:
- In mode-2 flows, use the amount that will actually be locked (`_amount / 2`) when computing `accumulated` and when crediting `calDoubledCounted`.
- Alternatively, call `getRewardAmount` after `_deposit` has updated `mWomSV`'s locked balance, and have `calDoubledCounted` persist a stored "already rewarded" tier watermark per account (rather than re-deriving it purely from current `mWomSV` balance), ensuring the subtraction always matches what was actually credited previously.

### Proof of Concept
Foundry test outline:
1. Deploy `ArbWomUp3`, `mWomSV` mock/locker, `vlMGP` mock/locker, `smartWomConvert` mock, and WOM/MGP tokens; fund the `ArbWomUp3` contract with MGP and fund attacker with WOM.
2. Configure `rewardTier = [0, 1000]`, `rewardMultiplier = [100, 200]` via `setMultiplier`.
3. Attacker approves WOM and calls `incentiveDeposit(1000, ratio, true, 2)` — record `vlMGP.getUserTotalLocked(attacker)` (expect 20).
4. Attacker calls `incentiveDeposit(1000, ratio, true, 2)` again — record new `vlMGP.getUserTotalLocked(attacker)` delta (expect +30, total 50).
5. Assert `mWomSV.getUserTotalLocked(attacker) == 1000` (real backing).
6. Assert `vlMGP.getUserTotalLocked(attacker) (50) > getRewardAmount` computed directly for `accumulated = mWomSV.getUserTotalLocked(attacker)` in a single call (20), proving over-crediting relative to real stake/backing.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);

        uint256 accuIn1 = mWomSV.getUserTotalLocked(_account);
        uint256 rewardAmount = 0;
        uint256 i = 1;
        while (i < rewardTier.length && accuIn1 > rewardTier[i]) {

            i++;
