### Title
Attacker-controlled participant count in `ThresholdKeys::read` forces tens of thousands of sequential point decompressions and HashMap insertions from a single small message — (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` trusts a 2-byte `n` field from the input stream and then performs `n` scalar reads, `n` point decodings (each including a decompress + re-encode canonicality check), `n` `HashMap` inserts, and a `ThresholdKeys::new`/`ThresholdParams::new` validation pass — all before the caller has any chance to bound the work. `n` can be up to 65535 regardless of the real multisig size, letting a single untrusted serialization burn CPU and memory disproportionate to its size, analogous to the crafted-traffic CPU/memory exhaustion class of CVE-2024-23836.

### Finding Description
In `ThresholdKeys::read` the deserialization is:

```rust
let (t, n, i) = (read_u16()?, read_u16()?, Participant::new(read_u16()?)...);
// Interpolation::Constant => n × C::read_F(reader)
// then:
let mut verification_shares = HashMap::new();
for l in (1 ..= n).map(Participant) {
  verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
}
ThresholdKeys::new(ThresholdParams::new(t, n, i)?, ...)
``` [1](#0-0) 

Each iteration of the `verification_shares` loop calls `C::read_G`, which is a full `GroupEncoding::from_bytes` decompress **plus** a re-serialization comparison for canonicality (`point.to_bytes().as_ref() != encoding.as_ref()`): [2](#0-1) 

`n` is a raw `u16` read from the wire with no cap relative to the actual validator set. A message encoding `n = 65535` therefore triggers:

- 65535 elliptic-curve point decompressions, each followed by a re-encoding comparison — the dominant cost, and it is *expensive curve work*, not memcpy;
- 65535 `HashMap` insertions with hashing and growth reallocation;
- `ThresholdParams::new(t, n, i)` and `ThresholdKeys::new` executing over a 65535-participant parameter set (verification-share iteration / interpolation setup scales with `n`);
- `Vec::with_capacity(n)` allocation in the `Interpolation::Constant` branch before a single payload byte is validated. [3](#0-2) 

The same pattern exists in `Commitments::read` in PedPoP (`for _ in 0 .. params.t() { read_G()? }`), but there `t` is the caller's own protocol parameter; in `ThresholdKeys::read` the loop bound comes from the *attacker's bytes*.

### Impact Explanation
`ThresholdKeys::read` is explicitly on the untrusted-input surface (it is listed among the deserialization entry points fed by remote data). A malicious peer or any party that can get a victim to deserialize a crafted `ThresholdKeys` blob can pin a CPU core for a sustained period: ~65k decompressions at tens of microseconds each is on the order of seconds of CPU per message, plus tens of MB of `HashMap`/vector memory. Repeated messages make this a practical denial of service against signing nodes — the same "far more CPU/memory than needed for the traffic" shape as the Suricata advisory. Caveat: the loop is bounded by bytes actually present (`read_exact` fails on truncation), so the attacker must send ~`n × point_size` bytes (~2–4 MB) rather than a few bytes; the amplification is CPU-per-byte (decompress+re-encode plus HashMap churn), not memory-per-byte.

### Likelihood Explanation
Reachable by any unprivileged party able to supply serialized `ThresholdKeys` (e.g., during key-share/distribution handling or any protocol path that deserializes peer-supplied key material). No collusion, no valid shares, and no authenticated role is required — the parsing happens before `ThresholdKeys::new` can reject the parameters, and `ThresholdParams::new` runs *after* the expensive loop, not before. The only reason the attack stops at 65535 iterations is the width of the length field, not a semantic bound.

### Recommendation
Validate `ThresholdParams::new(t, n, i)` **before** allocating or looping — derive `n` from the params, reject `n` exceeding the protocol's real maximum (e.g., `MAX_KEY_SHARES_PER_SET`-style bound as done for `SlashReport` in `Transaction::read`, which caps `len` before allocating `vec![0u32; len]`). At minimum, bound the `verification_shares` loop and the `Interpolation::Constant` vector length by the validated parameter, not the raw stream value.

### Proof of Concept
```rust
// Craft a ThresholdKeys blob for C = Ristretto with n = 0xFFFF
let mut buf = vec![];
buf.extend(u32::try_from(Ristretto::ID.len()).unwrap().to_le_bytes());
buf.extend(Ristretto::ID);
buf.extend(1u16.to_le_bytes());      // t = 1 (keeps polynomial/interp trivial)
buf.extend(0xFFFFu16.to_le_bytes()); // n = 65535 — attacker-chosen
buf.extend(1u16.to_le_bytes());      // i = 1
buf.push(1);                          // Interpolation::Lagrange (no scalar loop)
buf.extend(Ristretto::read_F::\/* any valid scalar repr *\/);
for _ in 0 .. 65535u32 {
  buf.extend(<point encoding>.as_ref()); // 65k compressed points
}
// Victim-side:
// ThresholdKeys::<Ristretto>::read(&mut buf.as_ref())
//   → 65,535 read_G decompressions + canonicality re-encodes
//   → 65,535 HashMap inserts
//   → ThresholdKeys::new over a 65535-member parameter set
```
Each `read_G` runs `from_bytes` plus `to_bytes` comparison (`crypto/ciphersuite/src/lib.rs:91-100`), so the victim pays ~65k curve decompressions for a single ~4 MB message, and the work occurs before `ThresholdParams::new` can reject the oversized `n` (`crypto/dkg/src/lib.rs:620-631`).
