### Title
Fee and weight calculation omits the OP_RETURN output, producing underpriced transactions that fall below the minimum relay fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The analog to "hardcoded constant causes the computed value to silently be wrong" is in `SignableTransaction::new`: the transaction weight/`vbytes` — and therefore `needed_fee` and the minimum-relay-fee check — are computed from a template transaction that contains only the payment outputs (and optionally change). The `data` OP_RETURN output is pushed onto `tx_outs` but is never included in the size template used by `calculate_weight_vbytes`, so every transaction carrying data is built with a fee calibrated to a smaller transaction than the one actually signed and broadcast.

### Finding Description
`SignableTransaction::new` accepts an optional `data: Option<Vec<u8>>` of up to 80 bytes and appends an OP_RETURN output to `tx_outs` (`networks/bitcoin/src/wallet/send.rs:194-202`). However, both calls to `Self::calculate_weight_vbytes` (lines 204 and 225-226) are passed only `tx_ins.len()`, `payments`, and `change` — the `data` output is absent from the template transaction whose `tx.weight()` is measured (lines 67-99). Consequently:

- `needed_fee = fee_per_vbyte * vbytes` (lines 206, 227) is computed on a `vbytes` that under-counts by roughly `9 + data.len()` bytes (~89 vbytes for a full 80-byte payload, since OP_RETURN outputs have no witness discount).
- The minimum relay fee check `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (line 211) also uses the understated `vbytes`, so it validates a fee rate that the real, larger transaction will not actually achieve.
- The `weight > MAX_STANDARD_TX_WEIGHT` check (line 241) can pass while the real signed transaction exceeds the standardness limit.

When a `change` output is created, the change amount is set to `input_sat - payment_sat - fee_with_change` (lines 228-230), meaning the *actual* fee paid equals exactly `fee_with_change`. The real transaction, which is larger by the OP_RETURN output, therefore has an effective feerate strictly below the caller-specified `fee_per_vbyte`. With `fee_per_vbyte = 1` (the minimum the function permits), a modest number of inputs plus an 80-byte payload yields a real feerate of ~0.7 sat/vbyte — below `DEFAULT_MIN_RELAY_TX_FEE` — so the signed transaction is rejected by the Bitcoin P2P network despite `new` returning `Ok`.

### Impact Explanation
An unprivileged caller supplying `data` (the parameter exists precisely for external use, e.g., anchoring data into the transaction) causes the threshold signing group to produce a transaction whose real feerate is lower than requested — potentially below the relay minimum, making the signed transaction unbroadcastable, or overweight per `MAX_STANDARD_TX_WEIGHT`. Funds are not directly stolen, but payments are silently dropped/stalled: the multisig signs a transaction that cannot confirm as constructed, and the entire signing round (nonces, shares) is consumed on a doomed transaction. Because the underestimation is proportional to attacker-influenced `data` length, the effect is deterministic and reproducible rather than a rounding edge case.

### Likelihood Explanation
Triggering requires only calling `SignableTransaction::new` with a non-`None` `data` argument — a documented public input of the wallet API. No malicious validator, leaked key, or internal access is needed. Note the in-repo caller in `processor/src/networks/bitcoin.rs` currently passes `None` for `data`, so the buggy path is only exercised by direct consumers of the wallet library; that bounds real-world likelihood but the defect is unconditional whenever `data` is used.

### Recommendation
Include the OP_RETURN output (and any other outputs actually emitted) in the template transaction inside `calculate_weight_vbytes`, or compute the weight once from the final `tx_outs` after change resolution instead of from `payments` alone. Concretely, restructure `new` so that weight/vbytes/fee are computed against the exact `Vec<TxOut>` that will appear in the signed transaction, and re-run the minimum-fee and `MAX_STANDARD_TX_WEIGHT` checks against that final weight.

### Proof of Concept
```rust
// networks/bitcoin wallet API usage
let data = vec![0u8; 80]; // maximum permitted payload
let st = SignableTransaction::new(
    inputs,                      // e.g., a single P2TR ReceivedOutput
    &[(payment_script, 10_000)], // one payment above DUST
    Some(change_script),         // force change so fee == needed_fee exactly
    Some(data),
    1,                           // fee_per_vbyte = 1 sat/vb (minimum allowed)
).unwrap();

// needed_fee was computed WITHOUT the ~89-byte OP_RETURN output:
//   needed_fee = 1 * vbytes(payments + change)
// but the signed tx contains payments + change + OP_RETURN.
// actual feerate = st.fee() / real_vsize < 1 sat/vb
//   => below DEFAULT_MIN_RELAY_TX_FEE (1000 sat/kvB), rejected by relay policy,
// yet `new` returned Ok and the TooLowFee check passed because it also used
// the understated vbytes.
assert_eq!(st.fee(), st.needed_fee()); // fee paid is exactly the underpriced estimate
```
