### Title
Uncontrolled Recursion in Nested Outer-Puzzle Driver Matching Causes Wallet Crash on Malicious Offer/Coin - ([File: chia/wallet/outer_puzzles.py], [File: chia/wallet/cat_wallet/cat_outer_puzzle.py], [File: chia/wallet/nft_wallet/ownership_outer_puzzle.py], [File: chia/wallet/nft_wallet/metadata_outer_puzzle.py], [File: chia/wallet/vc_wallet/cr_outer_puzzle.py], [File: chia/wallet/nft_wallet/singleton_outer_puzzle.py])

### Summary
The Wireshark CVE-2025-1492 bug class is uncontrolled recursion in a dissector that parses attacker-supplied, deeply-nested framing, causing a stack-overflow crash. The chia-blockchain wallet has an analogous unbounded-recursion pattern in its "outer puzzle" driver matching code, which recursively descends through curried puzzle layers (CAT → Ownership → Metadata → CR → Singleton, and back into CAT, etc.) with no depth limit, while walking a puzzle structure whose nesting depth is fully attacker-controlled (via a crafted coin spend / offer puzzle reveal).

### Finding Description
`match_puzzle()` in [1](#0-0)  iterates over `driver_lookup` and calls each driver's `.match()` method on an `UnknownPuzzle`. Each outer-puzzle driver (`CATOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, `CROuterPuzzle`, `SingletonOuterPuzzle`) implements `match()` so that, if the outer layer pattern matches, it recursively calls `self._match(...)` (which is `match_puzzle` again) on the puzzle's inner puzzle to look for further nested "also" layers: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

There is no recursion-depth check anywhere in this chain. Because `Program.curry()` supports arbitrary nesting depth of CLVM layers (e.g. `CAT(CAT(CAT(...CAT(ACS)...)))`), an attacker can construct a puzzle reveal (a `CoinSpend.puzzle_reveal`) with hundreds or thousands of nested recognized-outer-puzzle layers. When wallet code calls `match_puzzle()` on such a puzzle — e.g. during coin identification in `CATWallet.identify()` (`chia/wallet/cat_wallet/cat_wallet.py`) when the wallet syncs coin states, or when constructing/parsing driver info for an `Offer` counterparty exchange (`chia/wallet/trading/offer.py`, which imports and relies on `match_puzzle`/`construct_puzzle`/`get_inner_puzzle` from `chia.wallet.outer_puzzles`) — the recursive `match()`/`get_inner_puzzle()`/`construct()` chain will recurse once per nesting layer.

Python's default recursion limit (~1000 frames) means a sufficiently deep chain of nested curried layers will raise `RecursionError` (or, in worse cases, cause a native stack overflow via deep CPython frame chains), crashing the wallet's spend-bundle processing / offer-parsing path — directly analogous to the Wireshark Bundle Protocol/CBOR dissector's uncontrolled recursion causing a DoS crash on crafted input.

This is distinct from, and not mitigated by, the deliberately-iterative `sha256_treehash()` implementation in `chia/types/blockchain_format/tree_hash.py` (which explicitly notes it avoids Python recursion limits) — that protection was never extended to the outer-puzzle driver matching code path.

### Impact Explanation
A wallet user or offer counterparty can supply a spend bundle / offer file whose puzzle reveal contains a deeply nested chain of recognized outer-puzzle wrappers (CAT/singleton/ownership/metadata/CR layers). When the victim wallet processes this puzzle reveal (identifying an incoming coin, inspecting an offer, or constructing a response spend), the recursive `match_puzzle`/`get_inner_puzzle`/`construct_puzzle` calls will exceed Python's recursion limit and crash the wallet process (uncaught `RecursionError`), halting transaction/coin processing for that wallet — a spend-triggered processing halt, matching the "Accept" criteria of the task (spend-triggered transaction-processing halt).

### Likelihood Explanation
Constructing arbitrarily deep curried nesting with `Program.curry()` is trivial and cheap for an attacker (no signatures or special privileges required to build the puzzle reveal bytes themselves). The affected code paths (`CATOuterPuzzle.match`, `OwnershipOuterPuzzle.match`, `MetadataOuterPuzzle.match`, `CROuterPuzzle.match`, `SingletonOuterPuzzle.match`, and their `get_inner_puzzle`/`construct` counterparts) are reachable from wallet-side processing of externally supplied puzzle reveals (offer counterparty puzzle inspection, coin identification during sync). The likelihood of reachability is high; however, I was not able to fully trace, within the available tool budget, whether mempool/full-node admission itself calls `match_puzzle` on unvalidated spend bundles before the CLVM cost limit would otherwise reject an oversized generator — this is a caveat on the exact reachability path for full-node-side impact versus wallet-side impact. The wallet-side offer/coin-identification path is confirmed reachable via direct code citations above.

### Recommendation
- Convert the recursive `match()`/`get_inner_puzzle()`/`get_inner_solution()`/`construct()`/`solve()` chains in `chia/wallet/outer_puzzles.py` and all driver implementations (`CATOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, `CROuterPuzzle`, `SingletonOuterPuzzle`) to an iterative (stack-based) implementation, similar to the pattern already used in `sha256_treehash()`.
- Alternatively/additionally, impose an explicit maximum nesting depth (e.g., a small constant reflecting realistic legitimate puzzle stacking) and raise a clean `ValueError` when exceeded, rather than allowing unbounded Python recursion.
- Audit other callers of `Program.uncurry()`/`match_puzzle()` chains (e.g., `recursive_uncurry_dump` in `chia/wallet/util/debug_spend_bundle.py`) for the same unbounded-recursion pattern.

### Proof of Concept
Conceptual PoC (not executed, due to read-only analysis constraints):
1. Build an innermost puzzle `ACS = Program.to(1)`.
2. Repeatedly wrap it thousands of times using `construct_cr_layer(...)`, `construct_cat_puzzle(...)`, `puzzle_for_ownership_layer(...)`, and `puzzle_for_metadata_layer(...)` in rotation, each time feeding the previous result in as the new inner puzzle — mirroring the "double_cr_puzzle"/"double_cat_puzzle" nesting pattern already exercised (at depth 2) in the existing test suite: [7](#0-6) [8](#0-7) 
3. Wrap the resulting deeply-nested puzzle in a `CoinSpend`/spend bundle (or an `Offer`) and deliver it to a victim wallet (e.g., as an incoming coin during sync, or as an offer file to accept).
4. When the wallet calls `match_puzzle(UnknownPuzzle(known_program=deeply_nested_puzzle))`, the recursive `_match` chain recurses once per layer; at depth exceeding Python's recursion limit, a `RecursionError` is raised and crashes the wallet's processing of that spend/offer.

    for driver in driver_lookup.values():
        potential_info: PuzzleInfo | None = driver.match(puzzle)
