### Title
Wrong price feed used for `stSTXbtc`/`zstSTXbtc` in `get-asset-price` reports incorrect health/liquidatability - ([File: mainnet/contracts/utility/v0-1-data.clar])

### Summary
In `get-asset-price`, the branches for `stSTXbtc` and `zstSTXbtc` fetch `PYTH-STX` (the STX/USD feed) while labeling the result and treating it as a BTC-denominated price, instead of using `PYTH-BTC`. [3](#0-2)  This causes `get-user-position`'s `total-collateral-usd`/`total-debt-usd`/`health-factor`/`is-liquidatable` fields to be computed with the wrong asset's price whenever a position holds `stSTXbtc` or `zstSTXbtc`. [4](#0-3) [5](#0-4) 

### Finding Description
`get-asset-price(aid)` is a big `if`-chain that maps each asset id to its price. Every other branch correctly matches asset to feed (`STX`→`PYTH-STX`, `sBTC`→`PYTH-BTC`, `USDC`→`PYTH-USDC`, `USDH`→DIA), but the `stSTXbtc` and `zstSTXbtc` branches read `PYTH-STX` even though the code comments and local variable names (`btc-price`) claim it is the BTC price:
```
(if (is-eq aid stSTXbtc) (default-to u0 (get-pyth-price PYTH-STX))
...
(if (is-eq aid zstSTXbtc)
    (let ((btc-price (default-to u0 (get-pyth-price PYTH-STX))) ...
``` [3](#0-2) 
This is exactly the report's bug class ("valid evidence for one context reused to misrepresent another"): a price legitimately fetched for one feed (STX) is silently substituted for a different asset's valuation (a BTC-pegged wrapped/staked BTC token), analogous to `PheasantNetworkBridgeChild.withdraw()` accepting evidence tied to one trade to satisfy a check for a different, unrelated trade.

`sum-collateral-usd` / `sum-debt-usd` (used by `get-user-position`) call `get-asset-price` directly for whichever asset ids are in the user's position, so any position containing `stSTXbtc`/`zstSTXbtc` collateral or debt gets its USD value computed against the STX price rather than the BTC price. [4](#0-3) [6](#0-5)  `health-factor` and `is-liquidatable` are then derived from these corrupted totals. [7](#0-6) 

### Impact Explanation
This contract only exposes `define-read-only` functions and does not itself move funds, gate borrows, or execute liquidations — the actual fund-moving market contract (`v0-4-market.clar`) resolves prices per-asset via the registered oracle `ident` in the assets registry (`resolve-price-feed`/`price-resolve`), which was verified to correctly separate feeds by asset configuration rather than by this hardcoded switch. [8](#0-7) [9](#0-8)  Since BTC and STX prices diverge continuously and are not pegged, any liquidator, dashboard, or bot relying on this utility's `health-factor`/`is-liquidatable` output for positions containing `stSTXbtc`/`zstSTXbtc` would misjudge solvency — potentially delaying legitimate liquidations (protocol insolvency risk if depended on by automated liquidators) or triggering false liquidation attempts. However, because the on-chain enforcement path in `v0-4-market.clar` does not appear to reuse this specific buggy function, the exploitable impact is bounded to whatever off-chain systems trust this read-only report, and I could not confirm within the available context that any fund-moving code path calls `get-asset-price` from this file.

### Likelihood Explanation
Low-to-moderate: the bug is deterministic and triggers on any position holding `stSTXbtc` or `zstSTXbtc`, requiring no attacker action — it's a static coding defect, not something to be actively exploited by a third party in the way the bridge relayer scenario describes. Its severity depends entirely on whether any privileged off-chain component (liquidation bot, keeper) treats this contract as authoritative rather than independently resolving prices.

### Recommendation
Fix the `stSTXbtc` and `zstSTXbtc` branches in `get-asset-price` to call `get-pyth-price PYTH-BTC` instead of `PYTH-STX`, matching the comments/variable naming and the correct economic denomination of these assets.

### Proof of Concept
1. A user deposits `stSTXbtc` as collateral and/or borrows `zstSTXbtc`.
2. Call `get-user-position(account)` on `v0-1-data.clar`.
3. Observe that `total-collateral-usd`/`total-debt-usd` (and derived `health-factor`, `is-liquidatable`) are computed using the current STX/USD price rather than BTC/USD, producing a materially wrong valuation whenever STX/USD and BTC/USD diverge (which they always do, being unrelated assets). (define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
