### Title
Zero-amount `WithdrawalRequest.tokens` bypasses escrow-existence check in `_withdraw`, allowing unbacked order finalization - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
The external report's core defect is that a "decrease" operation (destroying/settling a position) is executed without first proving the position actually exists, so an attacker can drive the settlement path with no real backing state. The direct local analog is in `IntentsBase._withdraw`, the function that finalizes escrow release/refund for both same-chain fills/cancels and cross-chain `RedeemEscrow`/`RefundEscrow` messages. It validates escrow existence per token only when `amount != 0`, and unconditionally marks the order `_filled` when `finalize == true`, before any of those checks run.

### Finding Description
`_withdraw` iterates the `WithdrawalRequest.tokens` array and only performs the "does escrow exist" check inside the loop body, which is skipped entirely for zero-amount entries: [1](#0-0) 

Note that `_filled[body.commitment] = beneficiary;` executes unconditionally when `finalize` is true, *before* any per-token escrow check, and the loop's only existence guard (`if (escrowed == 0) revert UnknownOrder();`) is gated behind `if (amount == 0) continue;`. If every entry in `body.tokens` has `amount == 0` (or the array is empty), the function never touches `_orders[body.commitment][token]` at all, so it can never revert with `UnknownOrder`, and the finalize branch (marking the commitment filled/refunded and emitting `EscrowReleased`/`EscrowRefunded`) completes successfully for a commitment that has no escrow record whatsoever.

This is reachable through the cross-chain path: `_cancelFromDest` in `ExtrinsicIntents.sol` lets the order creator (fully controlling every field of `Order`, including `order.inputs`) build a `WithdrawalRequest` directly from `order.inputs` and dispatch a `RefundEscrow` (or, on fill, `RedeemEscrow`) message to the counterpart gateway: [2](#0-1) 

Because the attacker chooses `order.inputs` when calling `placeOrder`/`cancelOrder`, they can set every input amount to zero. On the receiving chain, `onAccept` authenticates only that the message came from the registered peer gateway (`_authenticate`), not that the referenced order was ever actually escrowed: [3](#0-2) 

so `_withdraw(body, ..., true)` runs to completion and finalizes an order commitment that was never backed by escrow — the exact "missing existence validation before a decrease/settlement operation" pattern described in the report, just manifesting as unconditional state finalization instead of an underflow revert (Solidity 0.8's checked arithmetic elsewhere prevents the underflow variant, but the existence check itself is bypassable).

### Impact Explanation
This breaks the invariant that `_filled`/settlement events only ever reflect orders that had real escrow, i.e. "false state acceptance" for the intent-settlement bookkeeping. It allows an unprivileged actor to force `EscrowRefunded`/`EscrowReleased` events and `_filled` writes for commitments of their choosing without ever locking funds, polluting the on-chain event/state trail that off-chain indexers, solvers, and the SDK rely on to determine order status. It does not directly move real escrowed tokens for a *different* victim's order (the check on tokens with non-zero amounts, and the fact that `commitment` incorporates the exact `inputs` values, still prevents redirecting someone else's real escrow to a new beneficiary), so this analog lands as a logic/state-integrity defect rather than a direct fund-theft primitive.

### Likelihood Explanation
High to trigger (any order creator can set `order.inputs` amounts to zero and drive the cross-chain cancel/fill path), but the exploitable value is limited because the attacker can only "finalize" commitments derived from orders of their own construction — they cannot force through arbitrary amounts against another order's escrow due to the commitment binding inputs to their exact amounts.

### Recommendation
In `_withdraw`, require that `body.tokens` is non-empty and validate escrow existence unconditionally (not gated by `amount != 0`) before allowing `finalize` to set `_filled` and emit settlement events; alternatively, require an explicit separate existence check on `body.commitment` (e.g., presence in `_orders` for any token) prior to the loop, mirroring the recommended fix from the source report ("add a position/order existence check before processing").

### Proof of Concept
1. Attacker calls `placeOrder` on the destination chain (or wherever `_cancelFromDest`/fill path originates) with an `Order` whose `inputs` array contains only zero-amount entries (or is empty), producing a valid `commitment = keccak256(abi.encode(order))` with no real matching escrow on the source chain.
2. Attacker calls `cancelOrder` → `_cancelFromDest`, which builds `WithdrawalRequest{ commitment, tokens: order.inputs, beneficiary: order.user }` and dispatches a `RefundEscrow` Hyperbridge POST to the source-chain gateway. [4](#0-3) 
3. On delivery, `onAccept` authenticates the peer and calls `_withdraw(body, true, true)`.
4. Inside `_withdraw`, every token entry has `amount == 0`, so `continue` skips the `escrowed == 0` check for all iterations; the loop exits without ever reverting.
5. `_filled[body.commitment] = beneficiary` was already set unconditionally at function entry, and the `EscrowRefunded` event fires — finalizing a commitment that was never escrowed, at zero cost to the attacker. [5](#0-4)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
