## Title
Divergent conflict-marker parsing between Copilot context extraction and file reassembly causes silent off-by-one misassignment of AI-resolved content and leftover raw conflict markers in committed files - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Copilot merge-conflict-resolution feature parses conflict markers twice with two *different* algorithms: once to build the hunks sent to the model (`extractConflictHunks`) and once to splice the model's per-hunk answers back into the file (`reassembleResolvedFile`). The two parsers disagree on what counts as a well-formed conflict block whenever a real conflict's "ours"/"theirs" content contains a line that merely *looks like* a `>>>>>>>` marker (7 `>` characters followed by whitespace or end-of-line). This is directly analogous to the reported bug class: one code path records/relies on a certain "amount" (here, the count/order of resolved hunks) while the actual operation (splicing) consumes a different amount, silently corrupting the final state.

### Finding Description
`extractConflictHunks` ( [1](#0-0) ) collects "ours" content by scanning forward and only stopping at a `baseMarker` or `separatorMarker` — a stray line matching the `theirsMarker` pattern (`^>{7}(?:\s|$)`) inside the ours region is treated as ordinary text and pushed into `oursLines`. As a result, extraction correctly finds the real closing marker later and reports one well-formed hunk.

`reassembleResolvedFile`'s lookahead ( [2](#0-1) ) instead scans forward line-by-line and stops at the *first* line matching the `theirsMarker` pattern, regardless of whether a `separatorMarker` has been seen yet:
```
for (let j = i + 1; j < lines.length; j++) {
  if (reassemblySeparatorMarker.test(lines[j])) { hasSeparator = true }
  else if (reassemblyTheirsMarker.test(lines[j])) { closingIndex = j; break }
}
```
If the ours-side content contains a line matching `^>{7}(?:\s|$)` (e.g. a markdown nested-blockquote fragment, ASCII art, or literal text like `>>>>>>> example`) *before* the real `=======` separator, this loop breaks early with `hasSeparator === false`, so the block is classified as **malformed** and copied through verbatim ( [3](#0-2) ) instead of being replaced. Because the outer walking loop only ever tests `reassemblyOursMarker` to detect block starts ( [4](#0-3) ), the real `=======` and closing `>>>>>>>` marker lines of that same block are also copied through as ordinary text — leaving raw git conflict-marker syntax embedded in the file.

Since `hunkIndex` ( [5](#0-4) ) is only incremented for blocks the reassembler considers well-formed, this single mismatched hunk is *silently skipped*, and every subsequent hunk in the file is spliced with the **wrong** `hunkResolutions[i]` entry (shifted by one) — i.e. hunk _k+1_ receives the model's resolution intended for hunk _k_, and so on.

The mismatch is never detected or reported: `reassembleResolutions` ( [6](#0-5) ) has no hunk-count/consistency check between the raw model response and the reassembled output, unlike other explicit validation paths in the same module (e.g. `CopilotValidationError` on missing raw content). The corrupted `resolvedContent` is then written straight to disk and staged when the user accepts the resolution: [7](#0-6) .

### Impact Explanation
This causes silent corruption of what the user commits/pushes: leftover raw `<<<<<<</=======/>>>>>>>` conflict-marker text becomes part of the tracked file content, and unrelated hunks' resolutions get swapped into the wrong locations of the file. This is fully attacker-reachable content — an attacker who contributes a branch/PR/commit that a victim later merges, rebases, or cherry-picks against only needs one line resembling a `>>>>>>>` marker inside a genuinely conflicting region of a file, which is trivial and unremarkable-looking (e.g. quoted text, ASCII banners, log excerpts, or markdown blockquotes) — no privileged access or social engineering beyond a normal merge/PR review workflow is required.

### Likelihood Explanation
Requires the victim to (a) have a real conflict where the attacker-influenced side contains a line matching `^>{7}(?:\s|$)`, and (b) use the "Resolve with Copilot" feature and accept the presented resolution. Given how commonly such 7+ character sequences of `>` can appear in ordinary quoted/log/documentation content, and that the feature is specifically marketed to let users skip careful manual review of conflicts, this is a realistic, low-effort trigger for anyone who can influence one side of a future merge (e.g. via a normal external contribution/PR).

### Recommendation
Make `reassembleResolvedFile`'s block-boundary detection structurally identical to `extractConflictHunks` (ideally share a single parsing routine), require the ours-collection scan to skip over lines that aren't a *bona fide* boundary (i.e. don't stop at a `theirsMarker` before a `separatorMarker` has been seen), and add an explicit consistency check in `reassembleResolutions` that the number of well-formed conflict blocks found on disk exactly matches `raw.hunks.length`, throwing a `CopilotValidationError` (falling back to manual conflict resolution) rather than silently proceeding on mismatch.

### Proof of Concept
1. Set up a merge where the same file conflicts in two places, and craft the content on the "ours" side of the first conflict to include a line like `>>>>>>> quoted output` (mimicking, e.g., quoted terminal output) before the block's real `=======`/`>>>>>>>` markers:
```
<<<<<<< HEAD
some code
>>>>>>> quoted output line
more ours code
=======
their code
>>>>>>> feature
```
2. `extractConflictHunks` parses this as one well-formed hunk (ours = "some code\n>>>>>>> quoted output line\nmore ours code", theirs = "their code") and a second real hunk further down in the file — both sent to and resolved by the model.
3. In `reassembleResolvedFile`, the lookahead for this first block hits `>>>>>>> quoted output line` before any `=======`, sets `closingIndex` there with `hasSeparator === false`, and classifies the block malformed. The block is left completely untouched (raw markers remain in the output), and `hunkIndex` is not incremented.
4. The second real hunk in the file is spliced with `hunkResolutions[0]` (the resolution the model produced for the *first* hunk) instead of `hunkResolutions[1]`.
5. `_applyCopilotConflictResolutions` writes this reassembled content to disk and `git add`s it; if the user confirms, the corrupted content (leftover markers + swapped resolution) is committed and can be pushed. [1](#0-0) [4](#0-3) [6](#0-5) [8](#0-7)

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
