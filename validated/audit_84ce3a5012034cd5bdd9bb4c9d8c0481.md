### Title
Unbounded recursion in `Offer`/outer-puzzle driver matching allows a malicious offer to crash a wallet via Python stack exhaustion - ([File: chia/wallet/outer_puzzles.py])

### Summary
Parsing an untrusted offer (`Offer.from_bytes`/`from_bech32`) walks the puzzle-reveal layer stack of every coin spend through `match_puzzle()`, which mutually recurses with each `DriverProtocol.match()` implementation (CAT, singleton, ownership, metadata, CR) once per matched layer, with no depth limit. An offer counterparty can construct a spend whose puzzle reveal nests one of these recognized outer-puzzle mods (e.g. `CAT_MOD`) arbitrarily deep, forcing the recipient wallet's Python call stack to recurse proportionally when it merely inspects the offer.

### Finding Description
`match_puzzle()` iterates over `driver_lookup` and calls `driver.match(puzzle)` [1](#0-0) . Each driver's `match()` (e.g. `CATOuterPuzzle.match()`, `OwnershipOuterPuzzle.match()`, `SingletonOuterPuzzle.match()`, `CROuterPuzzle.match()`, `MetadataOuterPuzzle.match()`) recognizes its own curried mod shape and, if matched, recursively calls `self._match(UnknownPuzzle(known_program=inner_puzzle))` — which is bound back to `match_puzzle` itself — to keep walking inward: [2](#0-1) . This mutual recursion (`match_puzzle` → `driver.match` → `match_puzzle` → ...) has no maximum-depth guard anywhere in the call chain.

Because these outer-puzzle mods (e.g. `CAT_MOD`) can trivially be curried around another instance of themselves — exactly as demonstrated in the test helper that builds a `double_cat_puzzle` by currying `CAT_MOD` with an inner puzzle that is itself another `CAT_MOD` curry [3](#0-2)  — an attacker can cheaply build a puzzle reveal with thousands of nested nested CAT (or singleton/ownership/CR) layers. Constructing this deep nesting is O(N) work with `curry()`, but it costs the recipient O(N) Python stack frames just to *inspect* the offer, well before any CLVM execution or cost accounting applies.

The entry point for an unprivileged offer counterparty is `Offer.from_spend_bundle()`, which is invoked from `Offer.from_bytes()`/`Offer.from_bech32()`/`Offer.try_offer_decompression()` when a wallet loads or evaluates an offer file, and directly calls `match_puzzle()` on every coin spend's puzzle reveal: [4](#0-3) . This is reached long before any run-time CLVM cost limit (`MAX_BLOCK_COST_CLVM`) is applied — those limits only bound `compute_spend_hints_and_additions`/`run_with_cost` in `__post_init__`/`conditions()`, not the earlier `match_puzzle` recursion in `from_spend_bundle`: [5](#0-4) .

There is no `sys.setrecursionlimit` adjustment or iterative rewrite guarding this path (unlike `sha256_treehash`, which the codebase deliberately made non-recursive specifically to avoid "blowing out the python stack" [6](#0-5) ). The same non-recursive design intent does not extend to `match_puzzle`/outer-puzzle `.match()` chains.

### Impact Explanation
This is directly analogous to the reported Go `io/fs.Glob` bug class: uncontrolled recursion driven by attacker-supplied structure (there, path separators; here, nested puzzle-reveal layers) leading to stack exhaustion and an unhandled crash/panic. Here, a wallet user opening, summarizing, or attempting to accept a maliciously crafted offer file from an untrusted counterparty triggers unbounded Python recursion in `match_puzzle`, which raises an uncaught `RecursionError` (or corrupts/crashes the process if recursion propagates through native `chia_rs`/CLVM FFI calls made inside `.match()`, e.g. via `Program.get_tree_hash()`/uncurry calls on Rust-backed objects). This halts wallet offer-processing for that request and can be trivially triggered by any offer sender, without requiring the victim to accept the offer — merely parsing/summarizing it is enough. This matches the "spend-triggered transaction-processing halt" acceptance criterion.

### Likelihood Explanation
High likelihood: constructing deeply nested CAT/singleton/ownership/CR puzzle layers is cheap and requires no special privileges — an attacker only needs standard `curry()` calls, exactly like the pattern already exercised in the test suite for a single extra nesting level. Any wallet that loads an externally supplied offer (via RPC `take_offer`, `get_offer_summary`, `check_offer_validity`, or CLI/GUI offer import) is exposed, since `Offer.from_bytes`/`from_bech32` unconditionally calls `from_spend_bundle` → `match_puzzle` on attacker-controlled puzzle reveals before any cost-based defenses apply.

### Recommendation
- Add an explicit maximum recursion/nesting depth to `match_puzzle()` and each `DriverProtocol.match()`/`get_inner_puzzle()`/`get_inner_solution()`/`solve()`/`construct()` implementation, rejecting offers whose outer-puzzle layer stack exceeds a sane bound (e.g. a few dozen layers).
- Alternatively, rewrite the outer-puzzle layer walk as an iterative loop (pushing/popping an explicit stack) rather than mutual Python recursion, mirroring the approach already used in `sha256_treehash`.
- Enforce a byte-size or curried-argument nesting limit on puzzle reveals accepted during offer parsing (`Offer.from_bytes`/`from_spend_bundle`) before invoking `match_puzzle`.

### Proof of Concept
Conceptually (not executed here, to be validated by the assigned engineer):
1. Build `inner = ACS` (any simple accept puzzle).
2. Loop N times (N ≈ 2000–5000, above Python's default recursion limit of 1000, accounting for the ~2 stack frames per layer from `match_puzzle` ↔ `driver.match`): `inner = construct_cat_puzzle(CAT_MOD, tail, inner)` (or repeat with `puzzle_for_singleton`/`puzzle_for_ownership_layer`/`construct_cr_layer`), analogous to the two-layer construction in `test_cat_outer_puzzle` [3](#0-2) .
3. Wrap `inner` in a `CoinSpend`/`WalletSpendBundle`, serialize as an `Offer` via `Offer.to_bech32()`/`bytes()`.
4. Send the resulting offer file/bech32 string to a victim wallet; have it call `Offer.from_bytes()`/`from_bech32()` (e.g. through `get_offer_summary`/`check_offer_validity`/`take_offer` RPCs).
5. Observe `match_puzzle` recursing once per nested layer inside `from_spend_bundle`, exhausting the Python call stack and raising an unhandled `RecursionError` (or a native stack overflow if CLVM FFI calls are made mid-recursion), halting offer processing for that request.

def match_puzzle(puzzle: UnknownPuzzle) -> PuzzleInfo | None:
    for driver in driver_lookup.values():
        potential_info: PuzzleInfo | None = driver.match(puzzle)
        if potential_info is not None:
            return potential_info
    return None

    @classmethod
    def from_spend_bundle(cls, bundle: WalletSpendBundle) -> Offer:
        # Because of the `to_spend_bundle` method, we need to parse the dummy CoinSpends as `requested_payments`
        requested_payments: dict[bytes32 | None, list[NotarizedPayment]] = {}
        driver_dict: dict[bytes32, PuzzleInfo] = {}
        leftover_coin_spends: list[CoinSpend] = []
        for coin_spend in bundle.coin_spends:
            driver = match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))
            if driver is not None:
                asset_id = create_asset_id(driver)
                assert asset_id is not None
                driver_dict[asset_id] = driver
            else:
                asset_id = None
            if coin_spend.coin.parent_coin_info == bytes32.zeros:
                notarized_payments: list[NotarizedPayment] = []
                for payment_group in Program.from_serialized(coin_spend.solution).as_iter():
                    nonce = bytes32(payment_group.first().as_atom())
                    payment_args_list = payment_group.rest().as_iter()
                    notarized_payments.extend(
                        [NotarizedPayment.from_condition_and_nonce(condition, nonce) for condition in payment_args_list]
                    )

                requested_payments[asset_id] = notarized_payments
            else:
                leftover_coin_spends.append(coin_spend)

        return cls(
            requested_payments, WalletSpendBundle(leftover_coin_spends, bundle.aggregated_signature), driver_dict
        )
