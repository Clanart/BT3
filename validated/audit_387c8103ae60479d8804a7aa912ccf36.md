### Title
Submodule `file://` protocol override (`protocol.file.allow=always`) can be leveraged by an attacker-controlled `.gitmodules` to copy arbitrary local files into the working tree during checkout/pull - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` runs `git submodule update --init --recursive` and, when its `allowFileProtocol` argument is `true`, prepends `-c protocol.file.allow=always` to the git invocation before executing it against the repository's `.gitmodules` file. [1](#0-0) 
This flag is threaded straight through from `checkoutBranch` / `checkoutCommit` in `app/src/lib/git/checkout.ts`, which accept an `allowFileProtocol` parameter (defaulting to `false`) and pass it unmodified into `updateSubmodulesAfterOperation` after every branch/commit checkout. [2](#0-1) [3](#0-2) 

### Finding Description
Git upstream added a protection (CVE-2022-39253) that disallows submodules from being cloned via the `file://` protocol by default, precisely to stop a malicious repository from declaring a submodule whose URL is `file:///path/to/anything-on-disk`, which git would otherwise happily "clone" (i.e., copy) into the working tree. Desktop's code deliberately reverses that protection with `-c protocol.file.allow=always` whenever `allowFileProtocol` is `true`.

The `.gitmodules` file — including the `submodule.<name>.url` value — is ordinary tracked content of a cloned/fetched repository, so it is entirely attacker-controlled: a malicious repo (or a malicious branch/PR the user checks out) can commit a `.gitmodules` entry such as:
```
[submodule "x"]
    path = x
    url = file:///Users/victim/.ssh
```
If a code path in the app calls `checkoutBranch`/`checkoutCommit` (or the underlying `updateSubmodulesAfterOperation`) with `allowFileProtocol = true` while operating on such a repository, git will copy the contents of the attacker-chosen local path into the submodule directory `x` inside the user's working tree — an arbitrary local file/directory read that lands inside the repo. If the user subsequently stages/commits/pushes (a very natural next action after "the app updated my submodules"), the exfiltrated content (SSH keys, cloud credentials, etc.) is silently pushed to whatever remote the attacker controls, satisfying the "silent corruption of what the user commits or pushes" / "credential exfiltration" impact class from the report.

This is a direct structural analog to the `safeFunctionCall` report: just as `safeFunctionCall` lets an approved-but-unbounded `target`/payload combination be executed with the consumer's privileges, `allowFileProtocol=true` lets an attacker-supplied `.gitmodules` URL be executed (as a `file://` "clone") with the local file-system privileges of the Desktop process, in a code path that is reachable purely by getting the victim to check out/pull a hostile branch or repository — no local access, malware, or leaked credentials required.

### Impact Explanation
If reachable with attacker-controlled input, this allows reading arbitrary files/directories from the local filesystem (limited only by OS file permissions of the Desktop process) into the repository's working directory, and does so as a side effect of an ordinary checkout/pull. Because the copied content ends up as ordinary working-tree files, the user can unintentionally commit and push it, turning a local file-read primitive into remote credential/secret exfiltration. This matches the report's flagged risk categories: "unnecessary exposure," "future risk via convenient wrapper for underlying logic," and here materializes as file read outside repo scope plus potential credential exfiltration and corruption of what gets committed/pushed.

### Likelihood Explanation
The severity of this issue depends entirely on which call sites in the application pass `allowFileProtocol = true` to `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation`. The function signatures default the parameter to `false`, and the test fixtures show `protocol.file.allow=always` being used deliberately for legitimate local-submodule scenarios. I was not able to fully enumerate every production call site that sets this flag to `true` (e.g., automatic submodule refresh after pulling from a remote, or after checking out a PR/fork branch) before running out of tool budget, so I cannot confirm with certainty that an *untrusted, remote-originated* checkout/pull path passes `true`. This is the key open question that determines whether the vulnerability is currently exploitable end-to-end or is properly gated to trusted/explicit-consent flows only.

### Recommendation
- Audit every call site of `checkoutBranch`, `checkoutCommit`, and `updateSubmodulesAfterOperation` to confirm `allowFileProtocol` is `true` only for flows where the user has explicitly and knowingly opted into a local-path submodule (e.g., the "trust this local directory" flow), never for ordinary checkout/pull/PR-checkout of remote or forked content.
- Prefer git's own default (`protocol.file.allow=user` or unset) for any checkout/pull triggered by content that originates from a remote the user does not fully control (forks, PRs, arbitrary clone URLs).
- If a legitimate need exists to allow `file://` submodules, restrict the allowed base path to a subtree of the parent repository (or a small allow-list) rather than globally re-enabling `protocol.file.allow=always`.
- Add regression tests asserting that checkout/pull of a branch containing a `.gitmodules` `file://` URL pointing outside the repository does **not** copy content when the operation originates from an untrusted/remote source.

### Proof of Concept
1. Attacker creates/publishes a repository (or a branch/PR against a repo the victim already has open in Desktop) containing a `.gitmodules` file:
   ```
   [submodule "leak"]
       path = leak
       url = file:///Users/victim/.ssh
   ```
2. Victim, using GitHub Desktop, checks out this branch/PR (a normal, unprompted action a Desktop user routinely performs).
3. `checkoutBranch`/`checkoutCommit` runs, then calls `updateSubmodulesAfterOperation` with the effective `allowFileProtocol` flag for that flow. [4](#0-3) 
4. If that flag is `true`, `git -c protocol.file.allow=always submodule update --init --recursive` is executed, causing git to "clone" `/Users/victim/.ssh` into `leak/` inside the working tree. [5](#0-4) 
5. The victim's SSH keys now appear as ordinary tracked/untracked files under the repository; a subsequent `git add`/commit/push (or Desktop's own "publish branch" action) exfiltrates them to the attacker's remote.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  // we return `true` here so `GitStore.performFailableGitOperation`
  // will return _something_ differentiable from `undefined` if this succeeds
  return true
}
