Found a concrete decimal-precision bug analogous to the M-9 report, in `convert_to_balance`/`convert_to_erc20` of `pallet-hyper-fungible-token`.

### Title
Incorrect decimal conversion when `erc_decimals < local_decimals` allows amount inflation/truncation in `pallet-hyper-fungible-token` - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_balance` and `convert_to_erc20` compute the scaling exponent using `erc_decimals.saturating_sub(local_decimals)` (and the mirror `local_decimals.saturating_sub(erc_decimals)` is never used). This is only correct when `erc_decimals >= local_decimals`. When the EVM-side token has fewer decimals than the local Substrate asset (`erc_decimals < local_decimals`), `saturating_sub` clamps to `0`, so the scale factor becomes `10^0 = 1` instead of the required upscale/downscale factor, silently producing a value off by the true decimal difference rather than reverting or erroring.

### Finding Description
`convert_to_balance` (used in `on_accept` in `module.rs:82-91`) is supposed to convert an inbound ERC20 `U256` amount (denominated in `erc_decimals`) to the local asset's balance (denominated in `local_decimals`): [1](#0-0) 

The exponent is always `erc_decimals.saturating_sub(local_decimals)`. If `erc_decimals < local_decimals` (e.g., a USDC-style ERC20 with 6 decimals bridging to a local asset registered with 18 decimals — a valid, admin-configurable combination via `register_token`/`update_token` and the per-chain `Precisions` map), `saturating_sub` returns `0`, so the divisor collapses to `1`. Instead of scaling the raw `U256` amount up by `10^(local_decimals - erc_decimals)`, the code passes the raw value straight through unscaled, which is then parsed directly into the local balance type.

The same flaw mirrors in `convert_to_erc20` (used in the outbound `send` extrinsic and in `on_timeout`'s refund path): [2](#0-1) 

Both `on_accept` (mint/transfer path) and `on_timeout` (refund path) rely on this helper for the amount that actually moves funds: [3](#0-2) [4](#0-3) 

This is the same broken-invariant class as the referenced Pool.sol M-9 report: a decimal-precision assumption (`erc_decimals >= local_decimals`) baked into a subtraction that is not actually guaranteed, causing the wrong-magnitude value to be used for a fund-moving operation instead of reverting or correctly rescaling.

### Impact Explanation
If a local asset is configured with more decimals than its paired EVM contract (a legitimate, non-adversarial configuration — nothing in `register_token`/`update_token` enforces `local_decimals <= erc_decimals`), every inbound `Send` message is credited to the beneficiary using the raw ERC20 integer amount instead of the correctly upscaled amount — i.e., beneficiaries receive `10^(local_decimals - erc_decimals)` times *less* than intended (severe under-crediting, effectively locking/losing bridged value), or in the mirrored `convert_to_erc20` direction (outbound `send`/timeout-refund), the ERC20-side amount is under-computed relative to what was escrowed/burned locally, mismatching the two ledgers. Either direction results in incorrect amounts moving to the beneficiary — falling squarely under "unauthorized transaction or execution / transaction manipulation" and "false state acceptance" for the bounty's fund-movement invariant. This is triggered purely by a legitimate decimal configuration difference, not by any malicious relayer/prover — it is a deterministic protocol bug reachable by any registered asset pair with `local_decimals > erc_decimals`.

### Likelihood Explanation
Likelihood depends entirely on whether any registered `(AssetId, StateMachine)` pair in `Precisions` has `local_decimals > erc_decimals`. Since `register_token`/`update_token` accept arbitrary `Precisions` entries with no validation that `erc_decimals >= local_decimals`, and it is common for Substrate-native assets to use 18 decimals while paired ERC20s use fewer (6, 8, etc.), this is a realistic configuration outcome rather than a contrived edge case — no attacker action beyond a normal cross-chain send/receive is required to trigger silent mis-scaling.

### Recommendation
Fix the scaling logic to handle both directions explicitly instead of relying on `saturating_sub` to signal "no-op":
```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let scaled = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    };
    scaled.to_string().parse::<B>()
}
```
Apply the symmetric fix to `convert_to_erc20`. Add unit tests covering `local_decimals > erc_decimals`, `local_decimals < erc_decimals`, and `local_decimals == erc_decimals`.

### Proof of Concept
1. Governance registers asset `X` with `local_decimals = 18` (native Substrate asset) and `Precisions::<T>::insert(X, EVM_CHAIN, 6)` (paired ERC20 token uses 6 decimals) via `register_token`.
2. A user sends `1_000_000` raw units (i.e., `1.0` token at 6 decimals) from the EVM contract to the pallet via a `Send` message.
3. `on_accept` calls `convert_to_balance(U256::from(1_000_000), 6, 18)`. Since `erc_decimals (6) < local_decimals (18)`, `erc_decimals.saturating_sub(local_decimals) == 0`, so the divisor is `10^0 = 1`, yielding `amount = 1_000_000` instead of the correct `1_000_000 * 10^12 = 1_000_000_000_000_000_000`.
4. The beneficiary is minted/transferred only `1_000_000` local-decimal units (`0.000000000000000001` of the intended `1.0` token) — a ~10^12x under-credit, with the difference effectively lost from the bridge's accounting versus what was escrowed/burned on the EVM side.
