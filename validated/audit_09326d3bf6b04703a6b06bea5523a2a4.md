### Title
Missing Zero-Address Validation on User-Supplied `_for` Parameter Permanently Locks Deposited Funds - ([File: wombat/WombatPoolHelperV2.sol])

### Summary
`WombatPoolHelperV2.depositFor()` lets any unprivileged wallet deposit tokens on behalf of an arbitrary `_for` address, but neither this function nor the downstream calls in `WombatStaking.deposit()` or `MasterMagpie.depositFor()`/`_deposit()` validate that `_for` is a non-zero, valid account. This mirrors the reported bug class: an address-typed user input is accepted and propagated into critical logic (here, fund custody accounting) without any format/sanity validation.

### Finding Description
`depositFor(uint256 _amount, address _for)` pulls `_amount` of `depositToken` from `msg.sender`, deposits it into the Wombat pool, and credits the resulting LP/receipt-token stake to `_for` via `MasterMagpie.depositFor` [1](#0-0)  and the internal `_stake`/`_deposit` helpers [2](#0-1) .

No layer in this call chain checks `_for != address(0)`:
- `WombatPoolHelperV2.depositFor`/`_deposit` — no check.
- `WombatStaking.deposit(_lpAddress, _amount, _minimumLiquidity, _for, _from)` — no zero-address check on `_for` [3](#0-2) .
- `MasterMagpie.depositFor`/`_deposit(_stakingToken, _account, _amount, _isVlmgp)` — credits `user.amount`/`user.available` for `_account` with no zero-address validation [4](#0-3) [5](#0-4) .

If `_for` resolves to `address(0)` (e.g., due to a client-side bug, a wallet-connection race condition, an unresolved ENS name, or any other unsanitized address input feeding this parameter — precisely the class of defect described in the external report), the deposited principal is transferred out of the caller's wallet, LP/receipt tokens are minted, and the internal staking balance is recorded against `address(0)` in `MasterMagpie`'s `userInfo` mapping. Since no private key exists for `address(0)`, nobody can ever call `withdraw`/`withdrawFor` to retrieve that balance, permanently freezing the deposited funds and the LP tokens minted against them.

### Impact Explanation
Funds routed through `depositFor` with an unvalidated zero (or otherwise unresolvable) `_for` address become permanently unrecoverable — this is a direct permanent freezing of user funds, one of the accepted high-impact categories, occurring in the WombatStaking LP custody / MasterMagpie accounting path.

### Likelihood Explanation
`depositFor` is a fully public, unprivileged entry point specifically designed to let a caller specify an arbitrary recipient address, so it is easily reachable. The lack of any address validation across `WombatPoolHelperV2`, `WombatStaking`, and `MasterMagpie` means a single unsanitized/incorrect address value reaching this parameter (e.g., from any front-end, script, or integrator that doesn't validate the target address, mirroring the original snap's unsanitized `walletAddress` input) results in unrecoverable loss with no on-chain safeguard.

### Recommendation
Add an explicit `require(_for != address(0))` (or equivalent custom error) check at the entry of `WombatPoolHelperV2.depositFor`, `WombatStaking.deposit`/`depositLP`, and `MasterMagpie.depositFor`/`_deposit`, consistent with the zero-address guards already present elsewhere in the codebase (e.g., `Airdrop.sol` and `MGPRelease.sol` reject `address(0)` in `register`) [6](#0-5) [7](#0-6) .

### Proof of Concept
1. A user (or an integrating front-end that fails to validate an address input, analogous to the unsanitized `walletAddress` in the external report) calls `WombatPoolHelperV2.depositFor(amount, address(0))`.
2. `depositToken` is pulled from the caller via `safeTransferFrom` [8](#0-7) .
3. `_deposit` forwards `_for = address(0)` to `WombatStaking.deposit`, which mints receipt tokens and forwards `_for` to `MasterMagpie.depositFor` [9](#0-8) .
4. `MasterMagpie._deposit` credits `userInfo[stakingToken][address(0)].amount` with the deposited amount [10](#0-9) .
5. No wallet controls `address(0)`, so `withdraw`/`withdrawFor` can never be called for this balance — the principal and any receipt tokens are permanently locked in the protocol.
