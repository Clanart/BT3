### Title
Deserialization of `ThresholdKeys` never binds `secret_share` to the claimed `verification_shares`/`group_key`, letting untrusted imported bytes mint a key set whose group key is attacker-controlled - (File: crypto/dkg/src/lib.rs)

### Summary
The analog to the Superset flaw (an unprivileged actor "importing" data that creates a privileged resource without validation) is `ThresholdKeys::read` / `ThresholdKeys::new`. A participant that *imports* a serialized key set — exactly like a user importing charts — gets a `ThresholdKeys` whose `secret_share` is never checked against the `verification_shares` map that determines `group_key()`. Any party able to feed bytes to `ThresholdKeys::read` (an explicitly in-scope untrusted-input API) can therefore "create" a Serai key set whose reported group key is attacker-chosen, while the stored secret share cannot produce valid signatures for it — or worse, whose group key the attacker knows the discrete log of.

### Finding Description
`ThresholdKeys::new` validates only structural properties: the count of `verification_shares` equals `n`, participant indexes are `<= n`, and `Constant` interpolation requires `t == n`. It then derives `group_key` purely from `verification_shares` for participants `1..=t`:

- `crypto/dkg/src/lib.rs` lines 355-365: only quantity/index checks.
- `crypto/dkg/src/lib.rs` lines 376-378: `group_key = sum(verification_shares[i] * interpolation_factor(i, 1..=t))` — computed from attacker-supplied points with no relation to `secret_share`.
- `crypto/dkg/src/lib.rs` lines 380-390: the inconsistent `secret_share` is stored alongside.

`ThresholdKeys::read` (lines 574-632) reconstructs `t`, `n`, `i`, an arbitrary `Interpolation::Constant` factor vector, the `secret_share`, and all `verification_shares` from the byte stream and passes them straight to `ThresholdKeys::new`. There is no check that `C::generator() * secret_share == verification_shares[params.i()]` (nor that the shares interpolate to a key anyone controls). Note that `FROST`'s `complete` itself acknowledges this gap: "The only known way to cause this... is to deserialize a semantically invalid FrostKeys" (`crypto/frost/src/sign.rs` lines 491-494) — the inconsistency is detectable but never checked at import time.

An attacker who supplies the imported bytes can pick `verification_shares` such that the interpolated `group_key` equals `G * x` for a known `x`, while setting `secret_share` to anything. The victim's software then treats `group_key()` as the multisig/deposit key (e.g., `Scanner::new(key)` / `scanner()` in `processor/src/networks/bitcoin.rs` lines 314-347 registers scripts for `key` and its branch/change/forward offsets, and `get_outputs` credits outputs paying to those scripts).

### Impact Explanation
- Funds reported as received that are not spendable: outputs scanned against the imported `group_key` and its derived offset addresses are credited to the validator set, yet the stored `secret_share` cannot participate in valid FROST signatures for that key (`sign`/`complete` will fail or produce an invalid aggregate).
- If the attacker chose `verification_shares` with a known interpolation to a known-DL key, the deposited funds are directly spendable by the attacker — integrity loss of the vault key material equivalent to the Superset integrity impact ("incorrectly create resources"), with direct fund loss possible.
- The bug is a missing authorization/consistency check at the "import" boundary: no proof is required that the importer-controlled public material corresponds to the claimed secret share.

### Likelihood Explanation
Requires the victim to deserialize `ThresholdKeys` from bytes an unprivileged party influenced (key backup restore, DB snapshot import, coordinator-supplied serialization, etc.). That is a plausible integration pattern — the `read`/`serialize` pair is the library's persistence API — but it does require the attacker to reach that byte supply, hence Medium rather than High.

### Recommendation
In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` (the pre-scalar identity), rejecting imported key sets that fail it. Alternatively, mark `read` as requiring trusted input and provide a separate `read_trusted`/`verify` path, and validate consistency after `scale`/`offset` application in `view`.

### Proof of Concept
```rust
// Attacker crafts bytes for ThresholdKeys::<Secp256k1>::read:
//   t = n = 2, i = 1, Interpolation::Constant([1, 1])  (t==n so it passes)
//   secret_share = arbitrary s
//   verification_shares[1] = G * x1, verification_shares[2] = G * x2
//   => group_key() = G * (x1 + x2), fully attacker-known
let keys = ThresholdKeys::<Secp256k1>::read(&mut attacker_bytes).unwrap(); // succeeds
// Victim scans deposits under keys.group_key(); deposits are credited but
// sign/complete can never produce a valid signature for G*(x1+x2) from `s`,
// while the attacker knows x1+x2 and sweeps them.
```

Root cause: `ThresholdKeys::new` accepts `secret_share` and `verification_shares` as independent inputs and derives the group key only from the latter, so the "imported" resource (the key set/address) is created without proving the importer actually holds the corresponding share — the same improper-authorization shape as CVE-2023-27526, where an import feature created resources the caller wasn't entitled to establish.
