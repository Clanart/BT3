## Title
Silent, Single-Step Rewrite of the Git Remote URL from Unverified GitHub API Data - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

## Summary
The River contract bug involved a privileged address (the admin/owner) being changeable in a single step from attacker-controlled input, with no second-step confirmation. GitHub Desktop has a structurally identical pattern for the `origin` remote URL — the trust anchor that determines where a user's `git push`/`git fetch` traffic (and, indirectly, credentials matched to that host) goes. `updateRemoteUrl` silently executes `git remote set-url` in one step, driven entirely by data returned from the GitHub API, with no user-visible confirmation step.

## Finding Description
`updateRemoteUrl` compares the local `origin` remote URL against `apiRepo.clone_url`, a field taken directly from a GitHub API response, and if a small set of conditions hold, calls `gitStore.setRemoteURL` immediately: [1](#0-0) 

The guard conditions (`protocolsMatch` and `remoteUrlUnchanged`) only prevent clobbering a *manually customized* remote — they do nothing to confirm with the user that the *new* URL is one they intend to push/fetch to. Once satisfied, the change is applied unconditionally and silently: [2](#0-1) 

This function is invoked automatically as part of background repository refresh, not from any user-initiated "save" action in Repository Settings: [3](#0-2) 

`repositoryWithRefreshedGitHubRepository` (which calls `updateRemoteUrl`) runs every time a repository is selected or the active account changes: [4](#0-3) [5](#0-4) 

Contrast this with the *intentional* user-driven path for changing the remote, `RepositorySettings.onSubmit`, which requires the user to open Repository Settings, edit the field, and click Save: [6](#0-5) 

The underlying git primitive itself is also a single, unconfirmed operation: [7](#0-6) 

**Broken invariant:** the value that decides where the user's commits are pushed and from where fetched content is merged should only change via an explicit, user-confirmed action. Instead it is silently rewritten as a side effect of a background API refresh, based on a field (`clone_url`) that is controlled by whoever can rename/transfer the upstream repository (the repository owner/org — which is exactly the kind of external, potentially-compromised or malicious party the report's threat model covers, i.e. "an attacker-controlled ... GitHub API object").

**Why existing guards don't stop it:** `remoteUrlUnchanged` only checks that the *previous* API-known clone URL still matches the current remote (i.e., "the user hasn't customized this remote"); it places no restriction on what the *new* URL is allowed to be, and there is no UI confirmation, banner, or opt-out surfaced to the user before the `git remote set-url` runs.

## Impact Explanation
If the upstream repository the user has cloned is renamed or transferred to a different owner (deliberately by a malicious/compromised account, or as a supply-chain-style takeover), the next automatic repository/account refresh (which happens routinely, e.g., on every repository selection) silently repoints `origin` to the new location — with no confirmation dialog. Consequences:
- Silent corruption of what the user pushes: subsequent commits/pushes go to a different remote than the one the user believes they are working with.
- Subsequent fetches/pulls silently bring attacker-influenced content from the new remote into the user's local working tree, which the user may build on or further commit.

This matches the "silent corruption of what the user commits or pushes" impact category, driven purely by an attacker-controlled/attacker-influenced GitHub API object, requiring no local access, no prior malware, and no leaked credentials.

## Likelihood Explanation
This path fires automatically in the background on ordinary app usage (repository selection, account refresh) — no unusual user action is required beyond normal use of Desktop with a GitHub-connected repository. The only precondition is that the attacker (or a compromised upstream account) can cause the API's `clone_url` for the tracked owner/name to change, which is a realistic scenario for repository transfers/renames/takeovers, and the change requires zero interaction or confirmation from the victim.

## Recommendation
Apply the same two-step principle used to fix the River contract issue:
1. Never call `gitStore.setRemoteURL` automatically from `updateRemoteUrl`. Instead, surface a dismissible, explicit prompt/banner informing the user that the associated GitHub repository's location has changed and asking them to confirm before Desktop updates `origin`.
2. Only allow automatic reconciliation when the underlying repository identity (e.g., GitHub repository ID) is confirmed unchanged, rather than trusting `clone_url` string comparisons alone.

## Proof of Concept
1. User A clones `https://github.com/legit-owner/repo` with GitHub Desktop; `origin` is set to that URL and `GitHubRepository.cloneURL` is cached with the same value.
2. The GitHub-side repository is later transferred/renamed to `https://github.com/attacker-owner/repo` (e.g., via account compromise or the org owner acting maliciously), while `owner`/`name` used for the API match remain resolvable.
3. On next repository selection or account refresh, Desktop calls `repositoryWithRefreshedGitHubRepository` → `api.fetchRepository(owner, name)` → `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` (`app/src/lib/stores/app-store.ts:4890-4906`).
4. Inside `updateRemoteUrl`, `protocolsMatch` is true (same `https`) and `remoteUrlUnchanged` is true (user never manually edited the remote), so `gitStore.setRemoteURL('origin', apiRepo.clone_url)` executes immediately (`app/src/lib/stores/updates/update-remote-url.ts:42-44`), running `git remote set-url origin https://github.com/attacker-owner/repo` with no dialog shown to User A.
5. User A's next `git push` silently sends their commits to `attacker-owner/repo`; their next `git pull` silently merges content from that repository.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
```

```typescript
export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
```
