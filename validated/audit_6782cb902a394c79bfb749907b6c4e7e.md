### Title
Webhook `shop_domain` is trusted from an HMAC-unprotected header, allowing forged/cross-shop webhook job dispatch - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` only computes the HMAC over `request.raw_post` (the request body), never over any headers. The concern nonetheless exposes a `shop_domain` helper that reads `request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]` directly, and the gem's own documentation instructs developers to use this unauthenticated header value to route/tag background jobs (e.g. `SomeJob.perform_later(shop_domain: shop_domain, ...)`). Because the header is not part of the signed payload, a request whose HMAC validly authenticates the *body* can carry an attacker-chosen `shop_domain` (and topic) header, similarly to how `cancelOrder` emitted an `OrderCancelled` event carrying an order hash unrelated to what was actually invalidated by the `BitInvalidator` path — the “verified” signal (HMAC pass / event emission) does not actually correspond to the data attached to it.

### Finding Description
`hmac_valid?` in `PayloadVerification` only signs/verifies `data` derived from `request.raw_post`: [1](#0-0) 

`WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)` and, separately, exposes `shop_domain`, which is read straight from a request header that is not covered by that HMAC: [2](#0-1) 

The gem's own documentation instructs developers building custom webhook controllers to trust this `shop_domain` value once `verify_request` passes, and to use it to enqueue a background job: [3](#0-2) 

Because only the body is signed, the `X-Shopify-Shop-Domain` (and topic) headers can be modified in transit/replay without invalidating the HMAC check, so a request that "passes verification" can still deliver a `shop_domain` value that does not correspond to the shop that actually produced the signed body — directly analogous to the reported bug class where an event/signal is emitted (or trusted) without it truly correlating to the underlying validated data.

### Impact Explanation
If an attacker can influence or replay the `X-Shopify-Shop-Domain` header on a request whose body+HMAC pair is valid (e.g. a proxy, shared infrastructure, or replay of a captured webhook delivery), the receiving app will process/queue background work attributing the payload to an attacker-chosen shop. Any app that follows the documented pattern (`shop_domain: shop_domain`) can end up performing cross-shop data writes/lookups or misattributed side effects, since the shop context used by the job comes from an unauthenticated header rather than any Shopify-signed field.

### Likelihood Explanation
Requires the attacker to either control an intermediary capable of rewriting headers on a legitimately-signed delivery, or replay a previously observed valid body+HMAC pair while altering the shop-domain header, since headers are not part of the signed payload. This is a lower-likelihood, non-trivial exploitation path (it does not enable arbitrary forgery without ever seeing a valid signed body), but it is a real gap between what verification actually proves (body integrity) and what the API/documentation implies is verified (payload origin/shop).

### Recommendation
- Do not expose or document `shop_domain` (or topic) as trusted data derived purely from headers once `hmac_valid?` succeeds.
- If shop context is required, prefer using `ShopifyAPI::Webhooks::Registry.process` handler callbacks (which resolve `shop:` internally via the official gem) rather than the raw header helper, or include the relevant header values in the HMAC-signed material before trusting them.
- Update `docs/shopify_app/webhooks.md` guidance to clarify that `shop_domain` is not authenticated by `verify_request`'s HMAC check.

### Proof of Concept
1. Build a custom webhook controller as shown in `docs/shopify_app/webhooks.md`, including `ShopifyApp::WebhookVerification` and using `shop_domain` to enqueue a job.
2. Capture (or otherwise obtain) one legitimately Shopify-signed webhook body and its matching `X-Shopify-Hmac-Sha256` value for shop A.
3. Resend the identical body and HMAC header to the same endpoint, but set `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) to shop B.
4. `verify_request` passes (`hmac_valid?(request.raw_post)` is unaffected by header values), and the controller enqueues the job with `shop_domain` = shop B, even though the signed payload never originated for shop B.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
