### Title
Fixed, unbounded-loop gas limit for CW→EVM synthetic-receipt event translation can be exhausted, panicking `DeliverTx` after state mutation and causing non-deterministic/failed post-processing - ([File: app/receipt.go])

### Summary
`app.AddCosmosEventsToEVMReceiptIfApplicable`, registered as a `DeliverTxHook`, translates Cosmos wasm events into synthetic EVM receipt logs whenever a transaction that touches a CW20/CW721/CW1155 pointer contract succeeds. It runs this translation under a context whose gas meter is capped by the governance-configurable but small, fixed parameter `DeliverTxHookWasmGasLimit` (default `300_000`, see `x/evm/types/params.go:34`), while iterating an attacker-influenced, unbounded number of wasm events with no sanity check on event count. This mirrors the External Report's root cause exactly: a hardcoded gas budget for post-processing an unbounded, caller-controlled loop of "transfer" work, which can be exhausted, causing the intended follow-up action to fail. [1](#0-0) 

### Finding Description
`AddCosmosEventsToEVMReceiptIfApplicable` is only invoked after the underlying Cosmos message(s) already succeeded and were committed (`msCache.Write()` runs before the hook is called in `app/legacyabci/deliver_tx.go`). [2](#0-1) 

Inside the hook, a brand-new gas meter is installed with a hardcoded, tiny limit taken from `GetDeliverTxHookWasmGasLimit` (default `300_000` — comparable in spirit to the report's `callbackGasLimit = 100_000`), and the function then loops over every wasm event in the transaction's execution, doing pointer lookups (`GetERC20CW20Pointer`, `GetERC721CW721Pointer`, `GetERC1155CW1155Pointer`) and log translation (`translateCW20Event`, `translateCW721Event`, `translateCW1155Event`) for each one — with no bound or sanity check on the number of wasm events processed: [3](#0-2) 

The code's own comment acknowledges the exact defect: *"Note: txs with a very large number of WASM events may run out of gas due to additional gas consumption from EVM receipt generation and event translation"* [4](#0-3) . A single EVM/Cosmos transaction that invokes a CW20/CW721/CW1155 pointer/wrapper contract capable of emitting many wasm module events (e.g., repeated mint/transfer/approve sub-actions, or `send_batch`/`burn_batch` messages that emit large per-item event sets as seen in `CW1155ERC1155Pointer.sol`'s `safeBatchTransferFrom`/`burnBatch`) can generate enough wasm events to exceed the fixed 300k gas budget during translation, regardless of how much gas the transaction itself was allotted.

Unlike the CardAllocationPool report, where the VRF callback failing merely stranded card NFTs, here an out-of-gas panic inside the hook propagates up through `DeliverTx`'s top-level `recover()`/`processRecovery` path (installed at the very top of the function, so it also covers the `evmHook` call at line 135), converting an already state-committed, successful transaction into a returned error from `DeliverTx`. This is a documented, load-bearing gas-DoS surface reachable purely by submitting an ordinary transaction that triggers many wasm events through a pointer/wrapper contract — no privileged access required.

### Impact Explanation
This does not create fund loss by itself, but it does create a chain of correctness problems for a public-RPC-reachable code path processing every DeliverTx: an attacker can craft a single transaction (batch mint/transfer/burn through a CW1155/CW721/CW20 pointer or wrapper) that generates enough wasm events to blow through the fixed `DeliverTxHookWasmGasLimit`, causing the post-commit receipt-translation hook to panic with out-of-gas after the underlying message state changes have already been applied. Because the panic is caught by the outer recovery middleware and converted into a transaction error, this can desynchronize the recorded EVM receipt/log state from the actual committed Cosmos state (the transfer/mint/burn already happened, but the synthetic EVM receipt logs for it may never be produced, and the transaction may be reported as failed to EVM RPC clients despite state having changed). This is a correctness/DoS issue on the EVM JSON-RPC surface and receipt/log generation pipeline rather than a direct fund-loss primitive, matching the same "impact class" (broken/failed post-processing due to an under-provisioned fixed gas budget for an unbounded loop) as the External Report.

### Likelihood Explanation
Likelihood is Medium: it requires an attacker to construct a transaction that causes a large number of wasm events to be emitted from a single Cosmos message that interacts with a CW20/CW721/CW1155 pointer or wrapper contract (e.g., large batch mint/transfer/burn operations, which are natively supported by the CW1155 pointer's `safeBatchTransferFrom`/`burnBatch` and by CW20/CW721 wrapper flows). This requires no special privileges, only normal contract usage with a sufficiently large batch size, and the 300k gas ceiling is well within reach of realistic batch sizes given the per-event pointer lookups, JSON allowance queries (`translateCW20Event`'s `QuerySmart` call for allowance changes), and log construction performed per event.

### Recommendation
- Add an explicit sanity check/cap on the number of wasm events (or the size of `wasmEvents`) processed by `AddCosmosEventsToEVMReceiptIfApplicable` before attempting translation, and skip/truncate synthetic log generation gracefully (emitting a partial-log warning) rather than letting the gas meter panic.
- Recover from out-of-gas specifically within this hook (as is already done in `translateCW20Event`, see its `defer recover()` at `app/receipt.go:148-151`) so a translation failure degrades to "no synthetic logs for this tx" instead of surfacing as a `DeliverTx`-level panic/error after state has already committed.
- Reconsider whether `DeliverTxHookWasmGasLimit` should scale with the actual number of wasm events/gas consumed by the underlying message rather than being a small, fixed constant independent of the number of loop iterations it must cover.

### Proof of Concept
1. Deploy/obtain a CW1155 pointer contract for an existing CW1155 collection (per `contracts/src/CW1155ERC1155Pointer.sol`).
2. Mint/hold a large number of distinct token IDs for a single owner in the underlying CW1155 contract.
3. Submit a single Cosmos/EVM transaction that invokes `burnBatch` (or `safeBatchTransferFrom`) with a large `ids`/`amounts` array, causing the underlying CW1155 contract to emit one wasm module event per batch item (see `execute_send_batch`/burn_batch handling in `example/cosmwasm/cw1155/src/contract.rs:124-170`, and the batch payload construction in `CW1155ERC1155Pointer.sol:78-129,159-191`).
4. Once the number of resulting wasm events is large enough that per-event pointer lookups and log construction in `AddCosmosEventsToEVMReceiptIfApplicable`'s loop (`app/receipt.go:72-104`) exceed the fixed 300k gas budget installed at `app/receipt.go:51-52`, the gas meter panics with out-of-gas; this propagates to `DeliverTx`'s top-level recover (`app/legacyabci/deliver_tx.go:61-71`), converting an already-state-committed transaction into a reported error and/or missing synthetic EVM receipt/log data.

Note: I was unable to fully trace how `err` returned from `legacyabci.DeliverTx` in this failure mode ultimately affects the ABCI response and consensus-level determinism (e.g., whether `ms`/`msCache.Write()` at line 117 is fully final or itself later discarded by the caller on error) using static analysis alone — verifying the exact end-to-end state/receipt divergence would require running this scenario against a live/test node.

func (app *App) AddCosmosEventsToEVMReceiptIfApplicable(ctx sdk.Context, tx sdk.Tx, checksum [32]byte, response sdk.DeliverTxHookInput) {
	// hooks will only be called if DeliverTx is successful
	wasmEvents := GetEventsOfType(response, wasmtypes.WasmModuleEventType)
	if len(wasmEvents) == 0 {
		return
	}
	logs := []*ethtypes.Log{}
	// Note: txs with a very large number of WASM events may run out of gas due to
	// additional gas consumption from EVM receipt generation and event translation
	wasmToEvmEventGasLimit := app.EvmKeeper.GetDeliverTxHookWasmGasLimit(ctx.WithGasMeter(sdk.NewInfiniteGasMeter(1, 1)))
	wasmToEvmEventCtx := ctx.WithGasMeter(sdk.NewGasMeterWithMultiplier(ctx, wasmToEvmEventGasLimit))
