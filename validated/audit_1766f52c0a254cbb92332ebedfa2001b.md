### Title
Untrusted `ReceivedOutput` deserialization can bind wallet-owned script data to a foreign outpoint - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary

`ReceivedOutput::read` accepts a scalar offset, `TxOut`, and `OutPoint` as three independent serialized fields, but does not verify that the outpoint exists or that its on-chain contents equal the supplied `TxOut` [1](#0-0) . `SignableTransaction` then trusts the embedded `TxOut` for the input value and the embedded `OutPoint` for the transaction input [2](#0-1) . The later `multisig` check only verifies that the claimed script matches the locally derived key, not that the referenced UTXO actually contains that script [3](#0-2) .

### Finding Description

A `ReceivedOutput` is represented as an offset, a complete claimed previous output, and an arbitrary claimed outpoint [4](#0-3) . During deserialization, `offset`, `output`, and `outpoint` are decoded independently and returned without cross-field or chain-state validation [5](#0-4) .

The transaction builder derives the input list from `input.outpoint`, while accounting and Taproot sighash data use `input.output` [2](#0-1) [6](#0-5) . The only ownership-style check compares `prevouts[i].script_pubkey` with the key produced by applying `offsets[i]`; it does not compare the claimed `TxOut` with the UTXO identified by `previous_output` [3](#0-2) .

Therefore, an attacker can serialize a record containing:

1. A valid offset and script for the victim wallet.
2. An arbitrary value.
3. A nonexistent outpoint, or an outpoint whose real output does not contain the claimed `TxOut`.

### Impact Explanation

The wallet can report or retain an apparently spendable `ReceivedOutput` that is not spendable at the referenced outpoint. If used, the wallet constructs and signs a transaction whose input references the attacker's chosen outpoint while its Taproot sighash commits to the attacker-supplied `TxOut` [2](#0-1) [6](#0-5) . Bitcoin consensus validation will reject the transaction if the referenced UTXO does not exist or does not match the committed prevout, so the represented funds cannot actually be spent.

This is an integrity failure in the wallet's received-output object: untrusted bytes can bind wallet-authorized key material to a foreign or fabricated UTXO identifier, analogous to binding an object to an attacker-selected resource identifier without ownership validation.

### Likelihood Explanation

The condition is reachable wherever `ReceivedOutput::read` is used to import data controlled by another process, service, or peer [1](#0-0) . The attacker only needs to know or obtain a wallet script/address, which is public transaction information. Exploitation does not require validator privileges, threshold collusion, key compromise, or malicious RPC access, though the impact is limited to creating misleading or unusable spend records rather than directly obtaining signatures for a valid theft transaction.

### Recommendation

Do not treat a deserialized `ReceivedOutput` as authenticated chain evidence. Either:

- remove the public untrusted deserialization path for `ReceivedOutput`, or
- revalidate it before use by querying the referenced outpoint and requiring its consensus-decoded `TxOut` to equal the embedded `TxOut` byte-for-byte.

At minimum, `SignableTransaction::new` should reject any `ReceivedOutput` whose `outpoint` cannot be resolved to exactly the stored `TxOut`; preserving attacker-controlled prevout data in `prevouts` is unsafe even when the script matches the wallet key [7](#0-6) .

### Proof of Concept

```rust
use bitcoin::{
  consensus::encode::serialize,
  hashes::Hash,
  Amount, OutPoint, ScriptBuf, TxOut, Txid,
};
use k256::Scalar;
use serai_bitcoin::wallet::ReceivedOutput;

fn forged_received_output(victim_script: ScriptBuf) -> ReceivedOutput {
  // Serialization layout used by ReceivedOutput::read:
  // scalar || consensus TxOut || consensus OutPoint.
  let mut bytes = Vec::new();

  // Zero corresponds to the scanner's base-key registration.
  bytes.extend(Scalar::ZERO.to_bytes());

  // Claim that the referenced output pays 100,000 sats to the victim's key.
  bytes.extend(serialize(&TxOut {
    value: Amount::from_sat(100_000),
    script_pubkey: victim_script,
  }));

  // Bind that claim to an attacker-chosen/nonexistent outpoint.
  let fake_outpoint = OutPoint {
    txid: Txid::from_byte_array([0x41; 32]),
    vout: 0,
  };
  bytes.extend(serialize(&fake_outpoint));

  ReceivedOutput::read(&mut bytes.as_slice()).unwrap()
}
```

`ReceivedOutput::read` returns this forged object successfully because it never checks whether `fake_outpoint` resolves to the supplied `TxOut` [5](#0-4) . Passing it to `SignableTransaction::new` creates an input referring to `fake_outpoint`, while balance accounting and signing use the fabricated 100,000-sat `TxOut` [2](#0-1) [6](#0-5) .
