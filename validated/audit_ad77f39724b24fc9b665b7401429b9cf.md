### Title
Stale line-selection indices applied to a freshly re-fetched diff during partial commit staging can silently commit/stage unintended lines - ([File: app/src/lib/git/apply.ts])

### Summary
`DiffSelection` stores selected/deselected lines purely as abstract line-index numbers with no binding to the diff content or hunk boundaries that produced them [1](#0-0) . When a partial commit is staged, `applyPatchToIndex()` re-fetches the working-directory diff independently at staging time via `getWorkingDirectoryDiff()` and immediately builds a patch from it using the file's existing `selection` object, without re-validating that the selection's line indices still correspond to the same content [2](#0-1) . This is structurally the same class of bug as the OUSD report: a previously captured/cached value (the line-selection index set, analogous to `_assetsHandledByArchimedes`) is combined with a freshly queried current value (the new diff, analogous to `totalAssets()`) without a consistency check, and the mismatch is silently used rather than rejected.

### Finding Description
In the app's UI flow, a user reviews a diff and selects specific lines/hunks to include in a commit. That `DiffSelection` is attached to the `WorkingDirectoryFileChange` and stored in `repositoryStateCache` [3](#0-2) . The app does try to keep the selection roughly in sync with the diff whenever it explicitly reloads the diff for display purposes, using `withSelectableLines()` to drop indices that no longer exist [3](#0-2) .

However, the actual commit path does not go through that same reconciliation. `_commitIncludedChanges()` passes the currently selected `WorkingDirectoryFileChange` objects (with whatever `selection` they carry) straight to `createCommit()` [4](#0-3) , which calls `stageFiles()` [5](#0-4) , which for any file with a partial selection calls `applyPatchToIndex()` [6](#0-5) .

`applyPatchToIndex()` re-runs `getWorkingDirectoryDiff()` to obtain a *brand-new* diff of the file at the moment of staging [7](#0-6) , and then calls `formatPatch(file, diff)`, which walks the new diff's hunks and lines and decides what to include based purely on `file.selection.isSelected(absoluteIndex)` — an index into the *old* diff [8](#0-7) . `DiffSelection.isSelected()` has no way to detect that the underlying content changed; it just tests set membership for a numeric line index [9](#0-8) .

If the working-directory content of a tracked file changes between the time the user made their line selection (e.g. viewed the diff and picked specific lines) and the time the commit button is pressed — for instance because a build tool, background `git checkout`, external editor autosave, or (per the attacker model) a hook/merge/checkout triggered by an untrusted cloned/fetched repository state modifies the file — the hunk layout and absolute line indices shift. `formatPatch` will then interpret the stale indices against the new hunk structure, selecting/deselecting different logical lines than the user intended, but git will accept the resulting patch as long as it's a syntactically valid unified diff for the current index/working tree pairing. The result is a "successful" commit whose actual diff content does not match what the user reviewed and consented to — a silent corruption of what the user commits, analogous to `_takeRebaseFees()` acting on a mismatched pair of values without validating that both operands still describe the same state.

This differs from the guard that already exists for the *display* path (`updateChangesWorkingDirectoryDiff` intersects selection against `selectableLines` before rendering) — that reconciliation is never invoked again before `applyPatchToIndex` builds the actual git patch used for staging.

### Impact Explanation
This falls in the "silent corruption of what the user commits or pushes" category explicitly called out as valid impact. A user could unknowingly commit and push lines they explicitly chose to exclude (e.g. secrets, debug code, or content from a merge/checkout that ran between selection and commit), or exclude lines they meant to include, with no error surfaced by the tool — the commit appears to succeed normally.

### Likelihood Explanation
The race window exists any time the working tree is mutated by something other than the Desktop UI action currently in flight (a hook, an editor auto-save, a background job, another git client, or a triggered checkout/merge as part of interacting with a malicious/fetched repository) between the moment a partial selection is made and the moment `_commitIncludedChanges` executes staging. Desktop performs several asynchronous steps (status refresh, diff refresh, user interaction) between these points, all of which are await points where such external mutation could occur.

### Recommendation
Before calling `formatPatch`/`applyPatchToIndex`, re-validate the file's `DiffSelection` against the diff that is about to be staged (the same reconciliation already applied in `updateChangesWorkingDirectoryDiff` via `withSelectableLines`), and abort/re-prompt the commit if the previously-selected lines no longer align with the current diff's selectable-line set, rather than silently applying possibly-mismatched indices to a newly fetched diff.

### Proof of Concept
Conceptual/needs full-repo verification (this analysis is based on static code reading only, no live git commit was performed to confirm the timing window in a running Desktop instance):
1. Open a repository in Desktop and modify a tracked file so it has multiple hunks.
2. In the Changes view, deselect specific lines (e.g., a debug `console.log` line) so only unrelated lines are included; do not commit yet.
3. Before committing, have an external process append/insert lines earlier in the same file (simulating a hook, editor autosave, or another tool touching the file), shifting hunk line numbers.
4. Click Commit. `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` fetches a brand-new diff and applies the old `DiffSelection` indices to it via `formatPatch` (`app/src/lib/patch-formatter.ts:157`), potentially including the previously-deselected debug line (or excluding intended content) without any warning to the user.       return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
