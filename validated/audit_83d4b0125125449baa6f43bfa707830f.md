### Title
Automatic remote-URL rewrite from unverified GitHub API `clone_url` silently redirects future pushes/fetches - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`erc721DecreaseIsolateSupplyOnLiquidate()` failed to clear a stale `lockerAddr`, so downstream code kept trusting outdated per-token state instead of re-validating it, letting an unrelated later operation act on data it should never have accepted. The same pattern exists in GitHub Desktop's GitHub-repository association: Desktop "currently never clear[s] GitHub repository associations" (an explicit TODO in the code) and, worse, uses that stale/unvalidated association as the basis for automatically rewriting the user's local git remote URL from data returned by the GitHub(.com/Enterprise) API, with no user confirmation and no host-trust check.

### Finding Description
`repositoryWithRefreshedGitHubRepository()` fetches repository metadata from the API and, if the repository already has a `gitHubRepository` association, calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`: [1](#0-0) 

The `TODO` right above that flow explicitly documents the missing-invalidation problem this report is about — the cached `gitHubRepository` association is never cleared/re-validated even when the underlying remote or account state changes: [2](#0-1) 

`updateRemoteUrl()` then compares the *current* local remote against the *cached* `gitHubRepository.cloneURL` to decide whether the user has "manually changed" the remote. If they look consistent, it blindly calls `git remote set-url` with whatever `clone_url` the API just returned — with only a protocol-family check, no ownership/host-authorization check: [3](#0-2) 

Because the association object being compared against (`gitHubRepository`) is stale/never invalidated, and because the API response itself is trusted implicitly, a malicious or compromised GitHub Enterprise Server (or any MITM/proxy sitting in front of it, since Desktop's guard here is only "protocol matches," not "host/owner matches") can return an `IAPIRepository.clone_url` pointing at an attacker-controlled repository/host. Desktop will silently execute `gitStore.setRemoteURL(...)` and rewrite the tracked remote — the exact "corrupted value" being `defaultRemote.url`, which subsequently governs where the next `git fetch`/`git push` goes.

This mirrors the report's broken invariant precisely: a piece of state (`lockerAddr` / `gitHubRepository` association) that should be authoritative-cleared/re-validated on change is instead left stale, and a security-relevant guard downstream (`validateWithdrawERC721`'s `lockerAddr == address(0)` check / `updateRemoteUrl`'s "has the user manually changed the remote" check) is evaluated against that stale value, producing an unintended, silent state transition.

### Impact Explanation
This satisfies "silent corruption of what the user commits or pushes": the user's next push/fetch is transparently redirected to a URL supplied by an untrusted API response, without any dialog, confirmation, or diff shown to the user. Depending on the attacker's chosen `clone_url` host, this can also cause credential exposure if the trampoline credential helper later matches the new remote's host to a signed-in account endpoint (`findGitHubTrampolineAccount` in `app/src/lib/trampoline/find-account.ts`), sending that account's token to the attacker-controlled remote during the redirected fetch/push. [4](#0-3) 

### Likelihood Explanation
`repositoryWithRefreshedGitHubRepository()` runs on ordinary, unprompted flows (repository selection, account-change refresh) rather than requiring any unusual user action, and the check in `updateRemoteUrl()` performs no verification that the new `clone_url`'s host/owner is consistent with anything the user actually trusts — only that the URL *scheme* (http vs ssh) is unchanged. Anyone able to influence the API response for a configured GitHub Enterprise endpoint (compromised/malicious GHES instance, or a network position with a trusted-but-compromised TLS termination point) can trigger this without any local access, admin rights, or social engineering of the Desktop user.

### Recommendation
Treat the cached `gitHubRepository` association as untrusted/stale by default: re-derive and validate it against the actual current remote (owner+name+host, not just protocol) before ever using API-supplied data to mutate git config. `updateRemoteUrl()` should require that the API's `clone_url` matches the *same* host/owner/name family already associated with the repository (or explicit user confirmation) before calling `setRemoteURL`, closing the same class of gap the report calls out for `lockerAddr`: clear/re-validate cached association state on every change instead of reusing it as an implicit trust anchor.

### Proof of Concept
1. User has Desktop signed in to a GitHub Enterprise Server endpoint `https://ghe.corp.example`, and has a local repository whose `gitHubRepository` association and remote both point at `owner/repo` on that endpoint.
2. Attacker compromises (or MITMs, if TLS trust is anchored to an org-managed CA) the GHES instance and responds to the `fetchRepository(owner, name)` API call with an `IAPIRepository` whose `clone_url` is `https://ghe.corp.example/attacker/repo.git` (same protocol, different owner).
3. On the next repository selection/refresh, `repositoryWithRefreshedGitHubRepository()` → `updateRemoteUrl()` sees `protocolsMatch === true`, `remoteUrlUnchanged === true` (cached association was never invalidated so it still matches the old remote), and `urlsMatch === false` (new clone_url differs) — triggering `gitStore.setRemoteURL(...)` to silently rewrite the local remote to `attacker/repo.git`.
4. The user's subsequent `git push` sends their commits to the attacker's repository instead of their intended one, with no warning shown. [5](#0-4)

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo
  }

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
