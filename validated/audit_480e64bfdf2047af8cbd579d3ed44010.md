### Title
CPI byte-translation costs round down to zero for small account/instruction data due to unguarded floor division by `cpi_bytes_per_unit` - (File: `program-runtime/src/cpi.rs`)

### Summary
The Nouns Builder bug shows that flooring `value * bps / 10_000` allows the result to be silently truncated to `0` when `value` is below the divisor, letting operators bypass a supposedly enforced minimum. Agave's CPI cost accounting has the same structural flaw: several `checked_div(cpi_bytes_per_unit)` calls that price per-byte data-translation work during cross-program invocation have no minimum-cost floor, so any data length smaller than `cpi_bytes_per_unit` (default `250`, [1](#0-0) ) is charged **zero** compute units for that portion of work, even though the host still performs the translation/validation/copy.

### Finding Description
`cpi_bytes_per_unit` is meant to convert bytes processed during CPI into compute units (`compute_units = bytes / cpi_bytes_per_unit`). Multiple call sites in `program-runtime/src/cpi.rs` implement this with plain floor division and no minimum floor, unlike the memory-op syscalls (`mem_ops.rs`) and sysvar syscalls (`sysvar.rs`), which explicitly clamp the result with `.max(mem_op_base_cost)`:

- Per-account CPI data length cost: [2](#0-1) 
- Instruction data + account-meta translation cost (Rust ABI): [3](#0-2) 
- Instruction data + account-meta translation cost (C ABI): [4](#0-3) 
- Account-infos array translation cost: [5](#0-4) 
- Executable account data cost: [6](#0-5) 
- Caller-account length translation cost: [7](#0-6) 

Compare with the deliberately floored versions elsewhere:
- `mem_op_consume` uses `compute_cost.mem_op_base_cost.max(n / cpi_bytes_per_unit)`: [8](#0-7) 
- `SyscallGetSysvar` uses `sysvar_base_cost + ... + max(sysvar_buf_cost, mem_op_base_cost)`: [9](#0-8) 

Because the CPI-path divisions above lack this `.max(...)` floor, every account (or instruction/meta payload) whose relevant byte length is below `250` bytes contributes `0` compute units toward the byte-processing cost, regardless of how many such accounts/instructions are processed. Only the flat, per-call costs (`invoke_units`, `syscall_base_cost`, etc.) are charged; the actual host work of translating, bounds-checking, and copying each sub-250-byte account/instruction payload is performed for free.

### Impact Explanation
This is analogous to the Nouns Builder finding: floor division against a fixed divisor makes small quantities round to `0`, defeating the intended proportional cost. Here it means a program invoking CPI with many small accounts (a very common real-world pattern, e.g., token/oracle/registry programs with dozens of small PDAs) has its true per-account translation work under-billed to zero for the byte-count component on every one of those accounts, while the flat per-invocation cost stays constant. This directly matches the "materially underpriced compute" acceptance criterion: the compute meter does not reflect the real amount of host CPU work (memory translation/copy for every account) actually performed on the CPI path.

### Likelihood Explanation
This is reachable by any unprivileged BPF program simply by invoking CPI with account infos/instruction data below the 250-byte threshold — no special privileges, unusual runtime configuration, or malicious snapshot needed, and it triggers on the ordinary, hot CPI code path used by nearly every real Solana program.

### Recommendation
Apply the same minimum-floor pattern already used in `mem_ops.rs` and `sysvar.rs` to all byte-based CPI cost calculations in `program-runtime/src/cpi.rs`: clamp each `checked_div(cpi_bytes_per_unit)` result with a minimum charge (e.g., `.max(mem_op_base_cost)` or an equivalent per-account minimum) so that translating any non-zero amount of data always consumes a non-zero, proportionally meaningful number of compute units, consistent with the intent of the `cpi_bytes_per_unit` cost model.

### Proof of Concept
1. Deploy a program that performs a CPI (`invoke`/`invoke_signed`) passing `N` accounts, each with `data.len() < 250` bytes (e.g., 32-byte PDAs), and instruction data `< 250` bytes.
2. Observe that in `translate_instruction_rust`/`translate_instruction_c`, `total_cu_translation_cost` evaluates to `0` for both the instruction-data term and the account-meta term because `data.len() / 250 == 0` and `(N * 34) / 250 == 0` for reasonably small `N` ( [3](#0-2) ).
3. Similarly, in `translate_account_infos` and the per-account-info loop, `account_infos_bytes / cpi_bytes_per_unit` and `data.len() / cpi_bytes_per_unit` are `0` for the same small sizes ( [5](#0-4)  and [2](#0-1) ).
4. The only CU charge incurred is the flat `invoke_units` (946) at `program-runtime/src/cpi.rs` line 785-786; repeating the CPI with many small accounts inflates the host-side translation work performed per CU charged, without the compute meter accounting for the additional data processed.
