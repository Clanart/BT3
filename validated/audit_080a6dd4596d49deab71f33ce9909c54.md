### Title
Scanner reports immature coinbase outputs as spendable `ReceivedOutput`s — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates over every transaction in a block, including the coinbase (`block.txdata[0]`), and emits any matching output as a `ReceivedOutput` — a type documented as "A spendable output." Coinbase outputs are consensus-immature and cannot be spent for 100 blocks, yet they are reported identically to normal spendable outputs. This is the Serai analog of the reference bug: accounting records funds as received/vested even though the underlying value cannot actually be moved, leading to accounting in excess of spendable balance.

### Finding Description
`scan_block` at `networks/bitcoin/src/wallet/mod.rs:221-227` calls `scan_transaction` for every `tx` in `block.txdata` with no exception for the coinbase transaction. `scan_transaction` (lines 199-213) matches outputs purely by `script_pubkey` against the registered offset table and pushes a `ReceivedOutput` carrying the matched `offset`, the `TxOut`, and its `OutPoint`. There is no flag on `ReceivedOutput` distinguishing an immature coinbase credit from a normal one — the caller cannot tell the difference without re-fetching the block and checking `txdata[0]` itself.

The severity of this is confirmed by Serai's own consumer: `processor/src/networks/bitcoin.rs:690-691` has to deliberately work around the library by skipping the coinbase — `// Skip the coinbase transaction which is burdened by maturity` — before calling `scan_transaction` per-transaction. That workaround exists precisely because `scan_block`/`scan_transaction` otherwise report unspendable funds as spendable. Any other caller of the in-scope `Scanner::scan_block` API that lacks this workaround ingests immature outputs.

### Impact Explanation
A `ReceivedOutput` is a claim of spendable funds. If an immature coinbase output paying to a registered offset script (the base key, or any `register_offset` script) is fed into the scheduler/batching path, the system records a balance that cannot be spent and may attempt to build/sign a transaction spending the outpoint, which Bitcoin consensus rejects until maturity — mirroring the reference bug where `MultiFeeDistribution` vests RDNT that was never transferred, producing accounting in excess of real balance and protocol insolvency/stall.

### Likelihood Explanation
An attacker must mine a block whose coinbase pays to the Serai multisig's P2TR script (or a registered offset script). This requires winning a block, so it is not free on mainnet, but it requires no cooperation from Serai, no secret material, and the resulting output is indistinguishable from a normal deposit to the scanner. On low-difficulty environments it is trivial.

### Recommendation
Have `scan_block` skip `block.txdata[0]` (or take a flag/height and filter immature coinbase outputs), so every `ReceivedOutput` it returns is genuinely spendable — matching the revert-on-insufficient-reserve fix class rather than returning a phantom amount. At minimum, mark coinbase-derived `ReceivedOutput`s so callers can defer them.

### Proof of Concept
1. `Scanner::new(key)` for an even `key` registers the base P2TR script at offset 0 (lines 162-165).
2. A miner creates a block whose coinbase has an output paying to `p2tr_script_buf(key)`.
3. `scanner.scan_block(&block)` returns a `ReceivedOutput` with `outpoint = (coinbase_txid, vout)` and the full subsidy `value()` — asserted spendable by the type's contract (line 88: "A spendable output"), despite consensus forbidding the spend for 100 blocks.
4. `processor/src/networks/bitcoin.rs:690-691` demonstrates the latent bug: production code must bypass `scan_block` and manually skip `txdata[0]` to avoid ingesting the phantom output. [1](#0-0) [2](#0-1) [3](#0-2)

  /// Scan a block.
  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
  }
