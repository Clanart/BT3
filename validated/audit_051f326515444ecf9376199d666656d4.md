## Analysis

The nodejs/build report is about **off‑by‑slash path‑containment checks**: a location string (`/metrics`) is compared against an alias (`/home/dist/metrics/`) without accounting for the separator, so a path like `/metrics../` passes the "is this inside /metrics/" test even though it resolves to the parent directory.

The exact same bug class exists in GitHub Desktop's path‑containment primitive.

### Finding Description

`resolveWithin()` — the function Desktop relies on throughout the app to guarantee that an attacker‑influenced relative path cannot escape a trusted root directory — performs its final containment check with a bare `String.prototype.startsWith()`, with no trailing separator appended to the root: [1](#0-0) 

```ts
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

Because `realRoot` has no trailing separator, this check treats any sibling path that merely shares the root's string as a *prefix* as "inside" the root. For example, if `realRoot` is `/Users/victim/Documents/GitHub/myrepo`, then `/Users/victim/Documents/GitHub/myrepo-secrets/token.txt` satisfies `.startsWith(realRoot)` even though it is a completely different, sibling directory — this is the textbook off‑by‑slash flaw from the report, just implemented in TypeScript string comparison instead of Nginx `location`/`alias` matching.

This helper is the *only* boundary check protecting several attacker‑reachable call sites, most notably the custom‑protocol/deep‑link handler: [2](#0-1) 

```ts
private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
  const { url, pr, branch, filepath } = action
  ...
  if (filepath !== null) {
    if (isAbsolute(filepath)) {
      log.error(`Refusing to open absolute path: ${filepath}`)
      return
    }
    const resolved = await resolveWithin(repository.path, filepath)
    if (resolved !== null) {
      shell.showItemInFolder(resolved)
    } else {
      log.error(`Prevented attempt to open path outside of the repository root: ${filepath}`)
    }
  }
}
```

`filepath` here originates from an `x-github-client://openRepo/...&filepath=...` URL — fully attacker‑controlled content that fires purely because the user clicked a link. The `isAbsolute()` check only blocks fully-qualified paths; a relative `filepath` containing `..` segments is still passed to `resolveWithin`, whose only remaining defense is the flawed prefix check above.

The existing regression tests only exercise `..`-traversal and symlink-escape scenarios, but never test the sibling-directory/off-by-slash boundary case, so the gap is unguarded: [3](#0-2) 

### Impact Explanation

If a repository directory has any sibling on disk whose name is prefixed by the repository's own directory name (a very common pattern — e.g. `myrepo` next to `myrepo-old`, `myrepo.bak`, `myrepo-secrets`, `myrepo.wiki`, or Desktop's own auto‑deduplicated clone folders like `myrepo-1`, `myrepo-2` created when cloning a same‑named repo twice), a maliciously crafted deep link can walk `filepath` with `../` segments so that the final resolved path lands inside that sibling instead of inside the intended repository, while still passing the broken containment check. The result is `shell.showItemInFolder()` being invoked on a file outside the repository the user opened — an unprompted, click‑triggered disclosure of a path/file location outside the intended repository root, matching "file... read outside the repo" in the impact criteria.

### Likelihood Explanation

Moderate. It requires: (1) the victim clicking a malicious `x-github-client://openRepo` link (a normal, low-friction Desktop feature, not physical/local access), and (2) a same‑prefixed sibling directory existing next to the target repository, which is a common real-world layout (Desktop itself creates `repo-1`, `repo-2` suffixes on clone name collisions). No credentials, admin rights, or prior malware are needed — only the reachable deep‑link handler and the `resolveWithin` helper's incorrect boundary check.

### Recommendation

Fix `_resolveWithin` in `app/src/lib/path.ts` to require an exact match or a path‑separator boundary, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This closes the off-by-slash gap for every caller of `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32`, including the deep‑link `filepath` handler in `dispatcher.ts` and the Copilot conflict-context file reader.

### Proof of Concept

1. Clone/open a repository at `/Users/victim/Documents/GitHub/myrepo`, and ensure a sibling directory `/Users/victim/Documents/GitHub/myrepo-secrets/token.txt` exists (e.g., created by a previous clone-name collision or any user-created folder).
2. Craft `x-github-client://openRepo/https://github.com/owner/myrepo?filepath=..%2Fmyrepo-secrets%2Ftoken.txt` (relative, not absolute, so it bypasses the `isAbsolute` check).
3. Victim clicks the link; `openRepositoryFromUrl` resolves the repository, then calls `resolveWithin(repository.path, filepath)`.
4. `resolve()` yields `/Users/victim/Documents/GitHub/myrepo-secrets/token.txt`; `realResolved.startsWith(realRoot)` is `true` because `realRoot` (`.../myrepo`) is a literal string-prefix of `.../myrepo-secrets/...`, even though it is a different directory.
5. `shell.showItemInFolder(resolved)` reveals the sibling file to the attacker-directed link, outside of the opened repository's directory tree.

  describe('resolveWithin', () => {
    const root = process.cwd()

    it('fails for paths outside of the root', async () => {
      assert((await resolveWithin(root, join('..'))) === null)
      assert((await resolveWithin(root, join('..', '..'))) === null)
    })

    it('succeeds for paths that traverse out, and then back into, the root', async () => {
      assert.equal(await resolveWithin(root, join('..', basename(root))), root)
    })

    it('fails for paths containing null bytes', async () => {
      assert((await resolveWithin(root, 'foo\0bar')) === null)
    })

    it('succeeds for absolute relative paths as long as they stay within the root', async () => {
