### Title
Fee/vbyte calculation omits the OP_RETURN output, producing an under-priced transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an OP_RETURN output carrying caller-supplied `data` to `tx_outs` (send.rs:194-202), but computes the transaction's weight, vbytes, `needed_fee`, the minimum-relay-fee check, and the change amount using `Self::calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which builds the measurement transaction from `payments` only and never includes the data output (send.rs:204-235, 85-99). This is the same bug class as the external report: a quantity is computed with one denomination/measure of inputs while the value actually committed to is constructed with a different measure, yielding an incorrect result. Here the "reserves" equivalent is vbytes: the calculated vbytes understate the real transaction by the serialized size of the OP_RETURN output (~11 + data_len bytes, up to ~91 bytes / ~91+ vbytes), so `needed_fee = fee_per_vbyte * vbytes` and the `TooLowFee` comparison are both computed against the wrong, smaller size.

### Impact Explanation
The signed transaction's actual fee (`sum(inputs) - sum(outputs)`, send.rs:138-141) equals `needed_fee`/`fee_with_change`, which was priced for a smaller transaction. Consequently the achieved fee rate is strictly below the requested `fee_per_vbyte`, and can fall below `DEFAULT_MIN_RELAY_TX_FEE` even though the check at send.rs:211 passed — because both sides of that comparison use the understated `vbytes`. The resulting transaction may be rejected by node mempools, leaving the spent inputs' funds unmovable by this transaction and requiring out-of-band re-signing. In the extreme the change output is also over-valued by the unpaid fee difference. This constitutes signing of a transaction whose economics (fee rate, change amount) do not match what the API contract promises.

### Likelihood Explanation
Reachable whenever `SignableTransaction::new` is invoked with `data: Some(..)` — any caller that causes a transaction with an OP_RETURN payload to be signed supplies these bytes directly. No trusted role is required to trigger the miscalculation; it is purely a function of public transaction parameters. However, the processor-side call site (`make_signable_transaction`, processor/src/networks/bitcoin.rs:446-451) currently always passes `None` for data, so within the in-tree scheduler flow the bug is latent; it affects other users of the wallet library or any future path that forwards user data. Severity Medium.

### Recommendation
Include the OP_RETURN output in the size estimation: extend `calculate_weight_vbytes` to take the full output list (payments plus the serialized `ScriptBuf::new_op_return` output and the change output), or equivalently pass `data`/`tx_outs` into it, so `vbytes`, `needed_fee`, the `TooLowFee` check, and `fee_with_change` are all computed over the transaction that will actually be signed. Alternatively, perform a final assertion that the constructed `tx`'s real `vsize()` satisfies `fee >= fee_per_vbyte * tx.vsize()` and the minimum relay fee before returning the `SignableTransaction`.
