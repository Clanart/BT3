### Title
`ThresholdKeys::read` accepts semantically inconsistent key material, letting crafted bytes impose an attacker-known group key - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `t`, `n`, `i`, the interpolation coefficients, the `secret_share`, and all `verification_shares` from an untrusted byte stream, then calls `ThresholdKeys::new`. `ThresholdKeys::new` validates counts, participant bounds, and interpolation applicability — but it never checks that the deserialized `secret_share` actually corresponds to `verification_shares[params.i()]` (i.e., that `secret_share * G == verification_shares[i]`). The `group_key` is computed purely from `verification_shares[1..=t]` times the interpolation factors, so an attacker who supplies the serialized bytes fully controls the resulting group key independently of the victim's secret share.

### Finding Description
The deserialization path in `ThresholdKeys::read` reads the secret share via `C::read_F` and the `n` verification shares via `C::read_G`, then constructs the keys via `ThresholdKeys::new` [1](#0-0) . `ThresholdKeys::new` only checks `verification_shares.len() == n`, participant bounds, and that `Constant` interpolation is only used when `t == n`; it then computes `group_key = Σ_{i=1..=t} verification_shares[i] * interpolation_factor(i)` without any consistency check between `secret_share` and `verification_shares[i]` [2](#0-1) . All scalar/point encodings are canonically checked (`read_F`/`read_G`), so this is not a malformed-encoding issue — it is a semantically invalid, fully canonical object that no other code path can produce: PedPoP's `calculate_share`, MuSig's `musig`, dealer key gen, and generator promotion all derive verification shares as `G * share`, guaranteeing `secret_share * G == verification_shares[i]` for honest keys [3](#0-2) . The serialization format is fixed and externally reproducible — the test suite itself hand-crafts byte streams that `ThresholdKeys::read` accepts [4](#0-3) . Downstream, FROST signing uses `view()`/`verification_share()` for per-share blame verification and `group_key()` for the aggregate check [5](#0-4) , so inconsistent shares are only caught at signing time — by which point the wrong group key has already been reported/used.

### Impact Explanation
An attacker who supplies the serialized `ThresholdKeys` blob (e.g., via a malicious backup, provisioning service, or any channel feeding `ThresholdKeys::read`) picks `verification_shares[1..=t]` as `G * a_i` for scalars `a_i` they know, and sets `secret_share = a_i` for the victim's index. The deserialized object passes all validation; `group_key()` is a key whose discrete log (`Σ a_i·λ_i`) is known to the attacker. Every signature the victim co-produces is valid yet signs for a key the attacker controls outright — the attacker can sign alone and unilaterally move any funds sent to `group_key`, while the victim's "share" provides zero security. Equivalently, if the attacker makes `secret_share` inconsistent with `verification_shares[i]`, every signing attempt fails blame checks, giving a targeted denial of key usage. Either way, an unprivileged party controlling the input bytes obtains either unilateral control of the threshold key or the ability to have funds credited to a key the victim cannot spend from.

### Likelihood Explanation
The format is trivially forgeable (concatenated u16s, a tag byte, canonical scalars and points) and every field is attacker-controlled. No signature, PoK, or self-consistency proof is embedded in the serialization. The only prerequisite is that the attacker's bytes reach `ThresholdKeys::read` — an explicitly in-scope untrusted-input surface. Since group-key/verification-share consistency is enforced by construction everywhere keys are legitimately produced, the absence of the check in `new`/`read` means the malicious object is indistinguishable from a real one until funds are at risk.

### Recommendation
In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise. Additionally consider embedding a Schnorr proof of possession or a checksum binding `group_key` to the serialized payload so semantically inconsistent key material cannot be imported silently.

### Proof of Concept
1. Attacker picks random scalars `a_1..a_n`, computes `V_i = G * a_i`, sets `secret_share = a_i` for victim index `i`, chooses any `t ≤ n`.
2. Serialize: `u32(C::ID.len()) || C::ID || t || n || i || 0x01 (Lagrange) || a_i.to_repr() || V_1..V_n` — the exact layout consumed by `ThresholdKeys::read` [6](#0-5) .
3. `ThresholdKeys::read` succeeds; `keys.group_key() = Σ_{j=1..=t} V_j·λ_j` is known to the attacker as `G * Σ a_j·λ_j`.
4. The victim runs FROST signing: the victim's share verifies against `V_i` (since `secret_share = a_i`), `complete()` returns a valid signature for the attacker-known key. Any deposit to `group_key` is spendable by the attacker alone.
5. Variant: set `secret_share ≠ a_i` — each `verify_share` fails, and `complete()` reports the victim's own signing as faulty while the group key remains attacker-chosen, bricking the imported key set.

impl<C: Ciphersuite> ThresholdKeys<C> {
  /// Create a new set of ThresholdKeys.
  pub fn new(
    params: ThresholdParams,
    interpolation: Interpolation<C::F>,
    secret_share: Zeroizing<C::F>,
    verification_shares: HashMap<Participant, C::G>,
  ) -> Result<ThresholdKeys<C>, DkgError> {
    if verification_shares.len() != usize::from(params.n()) {
      Err(DkgError::IncorrectAmountOfVerificationShares {
        n: params.n(),
        shares: verification_shares.len(),
      })?;
    }
    for participant in verification_shares.keys().copied() {
      if u16::from(participant) > params.n() {
        Err(DkgError::InvalidParticipant { n: params.n(), participant })?;
      }
    }

    match &interpolation {
      Interpolation::Constant(_) => {
        if params.t() != params.n() {
          Err(DkgError::InapplicableInterpolation("constant interpolation for keys where t != n"))?;
        }
      }
      Interpolation::Lagrange => {}
    }

    let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
    let group_key =
      t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();

    Ok(ThresholdKeys {
      core: Arc::new(Zeroizing::new(ThresholdCore {
        params,
        interpolation,
        secret_share,
        group_key,
        verification_shares,
      })),
      scalar: C::F::ONE,
      offset: C::F::ZERO,
    })
  }

  fn complete(
    self,
    mut shares: HashMap<Participant, SignatureShare<C>>,
  ) -> Result<A::Signature, FrostError> {
    let params = self.params.multisig_params();
    validate_map(&shares, self.view.included(), params.i())?;

    let mut responses = HashMap::new();
    responses.insert(params.i(), self.share);
    let mut sum = self.share;
    for (l, share) in shares.drain() {
      responses.insert(l, share.0);
      sum += share.0;
    }

    // Perform signature validation instead of individual share validation
    // For the success route, which should be much more frequent, this should be faster
    // It also acts as an integrity check of this library's signing function
    if let Some(sig) = self.params.algorithm.verify(self.view.group_key(), &self.Rs, sum) {
      return Ok(sig);
    }

    // We could remove blame_entropy by taking in an RNG here
    // Considering we don't need any RNG for a valid signature, and we only use the RNG here for
    // performance reasons, it doesn't feel worthwhile to include as an argument to every
    // implementor of the trait
    let mut rng = ChaCha20Rng::from_seed(self.blame_entropy);
    let mut batch = BatchVerifier::new(self.view.included().len());
    for l in self.view.included() {
      if let Ok(statements) = self.params.algorithm.verify_share(
        self.view.verification_share(*l),
        &self.B.bound(*l),
        responses[l],
      ) {
        batch.queue(&mut rng, *l, statements);
      } else {
        Err(FrostError::InvalidShare(*l))?;
      }
    }

    if let Err(l) = batch.verify_vartime_with_vartime_blame() {
      Err(FrostError::InvalidShare(l))?;
    }

    // If everyone has a valid share, and there were enough participants, this should've worked
    // The only known way to cause this, for valid parameters/algorithms, is to deserialize a
    // semantically invalid FrostKeys
    Err(FrostError::InternalError("everyone had a valid share yet the signature was still invalid"))
  }
