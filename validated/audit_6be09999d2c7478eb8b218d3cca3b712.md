### Title
Send-on-closed-channel panic in `BidPool` due to unsynchronized `stop()`/`AddBid()` race - (File: kaiax/auction/impl/bid_pool.go)

### Summary
`AuctionAPI.SubmitBid`, reachable by any unprivileged RPC caller (auction bidder), calls `BidPool.AddBid`, which checks a `running` flag and then unconditionally sends the bid on `bp.newBidCh`. Concurrently, `AuctionModule.Stop()` → `BidPool.stop()` closes that same channel without any coordination with in-flight `AddBid` calls, creating a check-then-act race analogous to the Linux `atmci_remove` bug: cleanup (closing resources / channels) proceeds while another path (an RPC handler) is still actively using those resources, leading to a crash.

### Finding Description
`BidPool.AddBid` performs a `running` check and then sends on `bp.newBidCh`: [1](#0-0) 

`BidPool.stop()` clears the pool and closes `bp.bidMsgCh` / `bp.newBidCh`, guarded only by the `stopped` CAS flag, with no lock or drain against concurrent senders: [2](#0-1) 

The sequence:
1. Goroutine A (RPC handler for `SubmitBid`) calls `AddBid`, passes the `atomic.LoadUint32(&bp.running) == 0` check while `running == 1`.
2. Goroutine B (module lifecycle, e.g. node shutdown / auction module restart via `AuctionModule.Stop()` → `bp.stop()`) sets `running = 0`, then calls `close(bp.bidMsgCh)` and `close(bp.newBidCh)`.
3. Goroutine A proceeds past `insertBid`/`getBidTxGasLimit` and executes `bp.newBidCh <- bid` on the now-closed channel, causing a runtime panic ("send on closed channel").

This mirrors the kernel bug class: a stop/cleanup path releases/dismantles a resource (closing a channel, freeing memory) while another concurrently-triggered path (interrupt handler / work item in the kernel case, RPC handler here) is still using it, because no synchronization/cancellation barrier exists between the "in-flight use" and "teardown" phases. There is also no `sync.WaitGroup`/lock protecting senders vs. the channel-close in `stop()`, so `handleBidMsg`'s `bid, ok := <-bp.bidMsgCh` consumer loop is safe (it checks `ok`), but the producer side (`AddBid`, called directly and synchronously from the RPC path, not from a controlled goroutine) is not protected at all against the close happening between the `running` load and the channel send.

`AuctionModule.Start()`/`Stop()` are node lifecycle-triggered (e.g., `bidPool.start()`/`bidPool.stop()`), and `AddBid` is directly reachable from the public (through the node's exposed private-namespace but externally invocable via a configured RPC endpoint) `auction_submitBid` RPC method: [3](#0-2) [4](#0-3) 

### Impact Explanation
A panic in the node process caused by an ordinary RPC call racing with module stop/restart is a denial-of-service against the node process handling auction bids — an unprivileged caller can trigger a crash under specific timing (e.g., during governance-driven auction parameter/auctioneer changes that recreate the pool, or during node shutdown/restart windows) with no special privileges beyond calling the `SubmitBid` RPC.

### Likelihood Explanation
Triggering requires the send to occur exactly in the window between `stop()`'s `running` CAS and the channel `close()` calls, which is a narrow window under normal conditions but can be widened/forced whenever `Stop()`/`start()` is invoked (module restart paths, node shutdown) while bid traffic is flowing; the auctioneer/auction module lifecycle functions are exercised during normal chain configuration updates (`updateAuctionInfo` clears the pool but does not stop/start channels, so this specifically needs an actual `Stop()`/`Start()` cycle). Given the narrow race window, likelihood is Medium.

### Recommendation
Do not close `bp.bidMsgCh`/`bp.newBidCh` in `stop()` while producers may still be sending. Options: (1) never close producer-side channels used by external callers — only stop the internal consumer goroutines via a separate `quit` channel and let `AddBid` select on that quit channel instead of unconditionally sending; (2) guard the send in `AddBid` with the same lock/flag used by `stop()` so that a `running==0` check-and-send is atomic with the close; or (3) use a `sync.WaitGroup`/refcount so `stop()` waits until no `AddBid` call is in the send region before closing the channels.

### Proof of Concept
1. Start node with auction module enabled.
2. In one goroutine, repeatedly call `auction_submitBid` RPC with a validly-formed bid.
3. Concurrently call `AuctionModule.Stop()` (e.g., during a module restart triggered by admin/lifecycle code) so `bp.stop()` runs.
4. Under sufficient iteration/timing, `AddBid`'s `bp.newBidCh <- bid` executes after `close(bp.newBidCh)`, causing `panic: send on closed channel` and crashing the process. [5](#0-4)

func (bp *BidPool) start() {
	// Start the bid pool.
	// running will be set 1 once it's ready in the PostInsertBlock.

	// If channels are closed, recreate them
	if atomic.CompareAndSwapUint32(&bp.stopped, 1, 0) {
		bp.bidMsgCh = make(chan *auction.Bid, bidChSize)
		bp.newBidCh = make(chan *auction.Bid, bidChSize)
	}

	bp.wg.Add(2)
	go bp.handleBidMsg()
	go bp.handleNewBid()
}

func (bp *BidPool) stop() {
	// Stop the bid pool.
	atomic.CompareAndSwapUint32(&bp.running, 1, 0)
	bp.clearBidPool()

	// Only close channels if they haven't been closed before
	if atomic.CompareAndSwapUint32(&bp.stopped, 0, 1) {
		close(bp.bidMsgCh)
		close(bp.newBidCh)
	}
	bp.wg.Wait()
}

func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)

	bp.newBidCh <- bid

	return bid.Hash(), nil

func (api *AuctionAPI) SubmitBid(ctx context.Context, bidInput BidInput) RPCOutput {
	numBidRequestCounter.Inc(1)
	if api.a.IsDisabled() {
		return makeRPCOutput(EMPTY_HASH, auction.ErrAuctionDisabled)
	}

	//  1. directly send target transaction
	targetTx, errTxDecode := toTx(bidInput.TargetTxRaw)
	if errTxDecode != nil {
		return makeRPCOutput(EMPTY_HASH, errTxDecode)
	}
	if targetTx.Hash() != bidInput.TargetTxHash {
		return makeRPCOutput(EMPTY_HASH, auction.ErrInvalidTargetTxHash)
	}
	errTargetTxSend := api.a.Backend.SendTx(ctx, targetTx)
	// ignore known transaction related errors against target tx validation
	if errTargetTxSend != nil && !(strings.HasPrefix(errTargetTxSend.Error(), "known transaction:") || errors.Is(errTargetTxSend, gasless_impl.ErrUnableToAddKnownBundleTx)) {
		return makeRPCOutput(EMPTY_HASH, errTargetTxSend)
	}

	// 2. add bid
	bid := ToBid(bidInput)
	bidHash, errValidateBid := api.a.bidPool.AddBid(bid)
	return makeRPCOutput(bidHash, errValidateBid)
}
