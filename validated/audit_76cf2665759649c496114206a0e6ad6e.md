### Title
Daemon WebSocket command dispatch exposes all local-admin operations (keychain, service control, keyring passphrase, service registration) to any TLS-authenticated daemon client with no per-command authorization scoping - ([File: chia/daemon/server.py])

### Summary
The Ceph CVE (`BIT-ceph-2020-10736`) describes `ceph-mon`/`ceph-mgr` failing to restrict access after authentication, letting an already-authenticated but lower-privileged client reach configuration operations it should not be able to modify. The chia-blockchain analog is `chia/daemon/server.py`'s `WebSocketServer`, the local daemon/keychain RPC boundary reachable by any process that holds the shared daemon private cert (any locally running Chia service, GUI, or CLI). Once a websocket completes the daemon TLS handshake, `handle_message()` dispatches to the *entire* command surface — keychain management, keyring passphrase set/remove/unlock, arbitrary `start_service`/`stop_service`, and `register_service` — with no additional authorization check binding the caller's actual role/service identity to the commands it is allowed to invoke.

### Finding Description
`WebSocketServer.handle_message()` routes every incoming command from any connected websocket into one flat dispatch table with no distinction between "trusted operator/admin" and "ordinary service client" callers: [1](#0-0) 

The full set of privileged commands available to any authenticated connection includes keyring passphrase mutation (`set_keyring_passphrase`, `remove_keyring_passphrase`, `unlock_keyring`), arbitrary child-process control (`start_service`, `stop_service`), and free-form service registration: [2](#0-1) 

Keychain-scoped commands are further weakened: `KeychainServer.get_keychain_for_request()` selects which keychain (i.e., which user's key store) to operate on purely from caller-supplied `kc_user`/`kc_service` fields in the request body, with no verification that the connecting client is authorized to act as that user/service: [3](#0-2) 

This means any client that can complete the daemon's mutual-TLS handshake — which uses one shared private CA/cert set issued to every local service (`full_node`, `wallet`, `farmer`, `harvester`, `timelord`, `crawler`, `data_layer`, `daemon`) — is treated as fully privileged for all daemon operations, including keychain add/delete-all-keys, keyring passphrase changes, and starting/stopping arbitrary allow-listed services, rather than being scoped to only the operations appropriate for its own service role: [4](#0-3) 

Additionally, `register_service` lets any connected client register under any service name string, which then makes that connection a routing target for daemon-relayed traffic and state-change fanout (e.g. `wallet_ui`), a further authorization gap noted in the module's own documentation: [5](#0-4) [6](#0-5) 

### Impact Explanation
This is a local/admin-boundary authorization gap, not a P2P vulnerability, so the exposure is limited to whatever can reach the daemon's TLS websocket (default `daemon_port`), which requires possession of a private-CA-signed cert. Within that boundary, however, there is no further scoping: a compromised or lower-trust local service holding a valid daemon private cert (e.g., `data_layer`, `farmer`, `harvester`, `crawler`) can invoke `set_keyring_passphrase`/`remove_keyring_passphrase`/`unlock_keyring`, delete or add keys for arbitrary `kc_user`/`kc_service` scopes, and start/stop other services, escalating from a narrowly-scoped local client into full keychain and process control — mirroring the Ceph bug class of an authenticated-but-restricted party gaining access to configuration/administrative resources beyond its intended scope. This satisfies "unsigned/unauthorized coin movement precondition" only indirectly (via keychain/private-key exposure or passphrase takeover, which can lead to unauthorized signing of spends), which keeps it Medium/High rather than a direct fund-theft path.

### Likelihood Explanation
Likelihood is moderate: the attacker must already run a process capable of establishing a daemon-private-cert TLS connection, which in a normal single-machine install is available to every local Chia service and the GUI. There is no code path here reachable purely from an external spend bundle or wallet-RPC caller; it is scoped to local processes/services that already trust the daemon boundary. Given the module's own documentation explicitly flags this pattern as "security-relevant even though this is not P2P traffic," and the flat, unscoped dispatch table, likelihood of the underlying design gap being exploitable given any local code-execution/service-compromise foothold is high, but the overall reachability by an "unprivileged spend-bundle submitter" or purely remote actor is low.

### Recommendation
Introduce per-connection authorization scoping in `WebSocketServer.handle_message()`/`get_command_mapping()` so that commands are gated by the registered/authenticated service identity of the calling connection, not just successful TLS handshake. Specifically:
- Restrict `set_keyring_passphrase`, `remove_keyring_passphrase`, `unlock_keyring`, `delete_all_keys`, `delete_key_by_fingerprint`, `start_service`, and `stop_service` to explicitly trusted callers (e.g., the daemon's own CLI/GUI service identity), not any service holding a private daemon cert.
- Validate `kc_user`/`kc_service` in `KeychainServer.get_keychain_for_request()` against the caller's actual registered identity rather than trusting caller-supplied values.
- Require `register_service` names to match an allow-list tied to the connecting certificate/service, preventing arbitrary registration as `wallet_ui` or other routing-privileged names.

### Proof of Concept
1. Obtain any valid daemon private cert (available to every local Chia service by default, e.g. `data_layer` or `crawler`'s private cert under `config/ssl/`).
2. Open a websocket TLS connection to `wss://<self_hostname>:<daemon_port>` using that cert, matching the test harness pattern used in `chia/_tests/core/daemon/test_daemon_register.py`: [7](#0-6) 
3. Send a `set_keyring_passphrase`/`remove_keyring_passphrase` or `delete_all_keys`/`get_all_private_keys` command payload through this connection; because `handle_message()` and `KeychainServer.handle_command()` apply no per-caller authorization check beyond the shared daemon TLS handshake, the command succeeds and returns/mutates the keychain, as exercised generically in `chia/_tests/core/daemon/test_daemon.py`'s `test_passphrase_apis`: [8](#0-7)

    def get_keychain_for_request(self, request: dict[str, Any]) -> Keychain:
        """
        Keychain instances can have user and service strings associated with them.
        The keychain backends ultimately point to the same data stores, but the user
        and service strings are used to partition those data stores. We attempt to
        maintain a mapping of user/service pairs to their corresponding Keychain.
        """
        user = request.get("kc_user", self._default_keychain.user)
        service = request.get("kc_service", self._default_keychain.service)
        if user == self._default_keychain.user and service == self._default_keychain.service:
            keychain = self._default_keychain
        else:
            key = (user or "unnamed") + (service or "")
            if key in self._alt_keychains:
                keychain = self._alt_keychains[key]
            else:
                keychain = Keychain(user=user, service=service)
                self._alt_keychains[key] = keychain
        return keychain
```

- There are two parallel trust domains. Public certs are signed by the bundled Chia CA and are used for ordinary public peer connections. Private certs are signed by the user's private CA and are used where the peer must be one of the user's trusted services.
- Private certs are generated for `full_node`, `wallet`, `farmer`, `harvester`, `timelord`, `crawler`, `data_layer`, `daemon`, and `solver`. Public certs are generated for `full_node`, `wallet`, `farmer`, `introducer`, `timelord`, `data_layer`, and `solver`.
- `ChiaServer.create()` encodes the operational matrix: harvesters use private certs as clients; harvester/farmer/wallet/data_layer servers require private-CA client certs; other peer servers use the public Chia CA. Changing generation lists or config paths without updating this matrix can silently break service startup or peer admission.
- Daemon and RPC traffic use daemon private certs with the private CA. This is a local/admin trust boundary, distinct from public peer TLS.
```
