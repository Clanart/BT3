### Title
Instant reward-per-token snapshot allows same-block vote reallocation to snipe bribes - (File: wombat/WombatBribeManager.sol, rewards/BaseRewardPoolV2.sol)

### Summary
`castVotes()` triggers `wombatStaking.vote()` which harvests bribes for every pool in the same call in which the voter's `stakeFor`/`withdrawFor` balance changes from `vote()` have already been applied. Because reward accounting in `BaseRewardPoolV2._provisionReward` distributes the entire harvested bribe instantly and proportionally to `totalStaked()` at that single block (no time-weighting/streaming), a caller who reallocates votes into a pool immediately before `castVotes()` harvests it captures a full share of that pool's whole-epoch bribe with zero time exposure.

### Finding Description
`vote()` updates `pool.totalVoteInVlmgp`, `userVotedForPoolInVlmgp`, and immediately calls `IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, delta)` / `withdrawFor(...)` [1](#0-0) . `voteAndCast()` calls `vote()` then `castVotes()` back to back in one transaction [2](#0-1) . `castVotes()` computes the delta votes to push to Wombat and calls `wombatStaking.vote(...)`, which (per the passed `rewarders` array) is responsible for harvesting bribes for each pool into its `BribeRewardPool` [3](#0-2) .

In `BribeRewardPool.stakeFor`, the `updateRewards` modifier snapshots the account's reward-per-token debt using the balance *before* the stake, then `totalSupply`/`_balances` are updated [4](#0-3) . Crucially, `BaseRewardPoolV2._provisionReward` distributes an entire incoming bribe in one shot: `rewardPerTokenStored += amount * 1e_dec / totalStaked()` [5](#0-4) . There is no time-weighting, streaming (`rewardRate`/`periodFinish`), or checkpoint mechanism — whoever holds the largest share of `totalStaked()` at the instant `_provisionReward` executes captures the largest share of that reward, regardless of how long they've actually held that stake.

Because `vote()`'s `stakeFor`/`withdrawFor` calls execute strictly before the bribe-harvesting call inside `castVotes()`/`wombatStaking.vote()`, an attacker can, in a single transaction, move their existing voting weight into whichever pool is about to receive the largest harvested bribe (and pull it out of another pool), then trigger the harvest in the same call. Passing offsetting deltas (`totalUserVote == 0`) means `userTotalVotedInVlmgp[msg.sender]` is unchanged, so the `getUserVotable` cap check in `vote()` trivially passes [6](#0-5)  — no additional locked vlMGP is required. This lets an unprivileged voter siphon a disproportionate share of a pool's bribe epoch from other voters who accrued their share over the full period, purely by timing their reallocation to the block that also triggers `castVotes()`.

Note: I was not able to fully confirm the exact internal call path inside `WombatStaking.vote()` (its source was not inspected in this session) that queues harvested bribes into each pool's `BribeRewardPool` via `queueNewRewards`; the conclusion above is inferred from the `rewarders` parameter being passed into `wombatStaking.vote()` and the architecture of `BaseRewardPoolV2`/`BribeRewardPool`. This should be verified directly against `wombat/WombatStaking.sol` before finalizing severity.

### Impact Explanation
This does not break the `userTotalVotedInVlmgp` vs `getUserTotalLocked` accounting invariant (that check still holds correctly for net-zero deltas — it is not "broken", it is simply satisfied trivially because no new capital is required). The concrete, exploitable impact is theft of unclaimed bribe yield: an attacker with existing locked vlMGP voting power can reallocate votes into a pool right before its bribe harvest and capture a share of the whole epoch's bribe that rightfully belongs (pro-rata over time) to voters who had capital committed to that pool for the entire accrual period. This matches "theft of unclaimed yield" rather than a Critical direct-theft-of-principal bug, since the attacker needs pre-existing genuine vote weight (not flash-loanable, since vlMGP votes derive from locked/non-transferable balances) and the loss is bounded to bribe yield reallocation, not principal.

### Likelihood Explanation
Feasible for any voter who already holds locked vlMGP and can observe/trigger (or front-run) the block in which `castVotes()`/`voteAndCast()` harvests a pool with a large pending bribe. No special privileges are required. Repeatable each epoch/cast cycle. Requires monitoring pending bribe amounts per pool (`previewBribes`) which is a public view function, making the attack easy to automate.

### Recommendation
Time-weight bribe distribution instead of instantly snapshotting `totalStaked()` at harvest time — e.g., stream bribes over the interval since the last cast (`lastCastTime`) via a `rewardRate`/`periodFinish` model (as in Synthetix StakingRewards), or checkpoint stake changes so that reward accrual is proportional to time-weighted balance rather than balance at the harvest instant. Alternatively, disallow `vote()` reallocations from taking effect for reward-accrual purposes within the same block/transaction as `castVotes()`.

### Proof of Concept
Hardhat test plan:
1. Deploy `WombatBribeManager`, `BribeRewardPool`s for pools A and B, mock `vlMGP`/`VLMGP`, and mock `WombatStaking` whose `vote()` harvests a large fixed bribe for pool A and calls `queueNewRewards` on pool A's rewarder before returning.
2. Set up two long-term voters, `Alice` and `Bob`, each with locked vlMGP already voted into pool A for many blocks/epochs prior (accruing time exposure).
3. Attacker (`Mallory`) locks a modest amount of vlMGP and initially votes fully into pool B (no exposure to pool A's pending bribe).
4. In a single transaction, Mallory calls `voteAndCast([poolA, poolB], [+X, -X], false)` — moving her entire vote into pool A and out of pool B in the same tx that triggers the harvest for pool A.
5. Assert: `userTotalVotedInVlmgp[Mallory]` is unchanged before/after (delta nets to zero) and `getUserVotable(Mallory)` check passes — confirming the reallocation bypass.
6. Assert: `IBribeRewardPool(rewarderA).earned(Mallory, bribeToken)` after the harvest is non-zero and proportionally large relative to `X / totalStaked(poolA)`, despite Mallory having zero prior time-weighted exposure to pool A's bribe accrual period, while Alice/Bob's `earned()` is diluted relative to what their time-weighted share should have been.
7. Expected result confirming the bug: Mallory's captured bribe share for pool A is disproportionate to her actual accrual time, demonstrating instant/non-time-weighted reward capture via same-transaction vote reallocation.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
