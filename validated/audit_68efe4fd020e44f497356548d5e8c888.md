## Title
`IntentGatewayV2` (Tron) Withdraw/Sweep Paths Don't Verify ERC20 Return Value, Allowing Escrow to Be Marked Settled Without Funds Reaching the Beneficiary - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` deviates from the rest of the codebase (which consistently uses OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`) and instead manually builds ERC20 `transfer` calldata and dispatches it with a raw low-level `.call()`, treating a non-reverting call as a successful transfer. This is the same broken invariant as the `RewardsClaimer` report: the boolean success value actually returned by the ERC20 token is never inspected, only whether the low-level call itself reverted.

### Finding Description
In `withdraw()` and in the `SweepDust` branch of `onAccept()`, token payouts are performed like this: [1](#0-0) 

and [2](#0-1) 

Both call sites do `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` and only check the outer `success` boolean from the low-level `.call`. `success` is `true` whenever the call does not revert — it says nothing about the ERC20's own returned boolean. Any token that signals failure by returning `false` (rather than reverting), a common and standards-compliant pattern (and especially plausible for TRC20 tokens on Tron, where ERC20-style ABI encoding is used but token implementations vary widely), will make this code treat a failed transfer as a success.

Meanwhile the rest of the codebase already fixed exactly this class of bug: `EvmHost.withdraw()` uses `IERC20(params.token).safeTransfer(...)` [3](#0-2) , and the EVM `IntentGatewayV2`/`IntentsBase` input-pulling paths use `safeTransferFrom` [4](#0-3) . The Tron `withdraw`/`SweepDust` paths are the outlier that regressed to the unchecked pattern the M-05 report warns about.

Critically, `withdraw()` mutates escrow accounting and marks the order filled *unconditionally* right after the (unchecked) transfer attempt: [5](#0-4) 

`_filled[body.commitment] = beneficiary` is set at the top of the function, and `_orders[body.commitment][token] -= amount` decrements escrow regardless of whether the beneficiary actually received tokens (i.e., regardless of the ERC20's true return value).

### Impact Explanation
If a token used in an order silently returns `false` on transfer failure (e.g., insufficient balance in an edge state, blacklist/pause logic, or any TRC20 token that doesn't revert on failure), the `withdraw()` path will still: (1) record the order as filled/refunded, (2) decrement/zero-out the escrow balance for that commitment, and (3) emit `EscrowReleased`/`EscrowRefunded` — all while the beneficiary receives nothing. The escrowed tokens remain stuck in the contract with no accounting pointing to them (the commitment's escrow entry is already decremented), effectively causing permanent loss of the intent-settlement funds for the legitimate beneficiary. This is a direct "loss of funds" / "false settlement acceptance" impact matching the bounty's accepted impact classes (intent settlement, bridge custody).

### Likelihood Explanation
This path is reached through the normal, unprivileged cross-chain settlement flow — `onGetResponse`/timeout-triggered `withdraw()` and governance-driven `SweepDust` — using tokens the intent creator/solver chooses for `order.inputs`/`order.output`. No malicious relayer, prover, or admin is required; the only requirement is that the token used with this Tron deployment be one whose `transfer()` can return `false` instead of reverting, which is a realistic assumption on Tron's token ecosystem given how inconsistently TRC20 contracts implement the ERC20 interface.

### Recommendation
Replace the manual `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in both `withdraw()` and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer()`, consistent with the rest of the codebase (`EvmHost.withdraw`, `IntentsBase`, `WrappedHyperFungibleToken`). This ensures the actual ERC20 return value (when present) is checked, and that non-standard tokens returning no data are still handled correctly by `SafeERC20`.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a token `T` whose `transfer()` implementation returns `false` on failure instead of reverting (e.g., transfer amount exceeds a per-tx cap enforced by `T`, or `T` is paused and returns `false`).
2. Create and escrow an order using `T` as an input/output token via the normal `newOrder`/fill flow, so `_orders[commitment][T] = amount`.
3. Trigger the response/timeout path that calls internal `withdraw(body, ...)` for that commitment while `T.transfer` would return `false` (e.g., token temporarily paused or over some internal limit at settlement time).
4. Observe: `token.call(...)` returns `success = true` (the call itself didn't revert) even though `T`'s internal `transfer` logic returned `false` and moved no tokens.
5. `_filled[commitment]` is set and `_orders[commitment][T] -= amount` proceeds, `EscrowReleased`/`EscrowRefunded` is emitted — yet the beneficiary's `T` balance is unchanged, and the tokens are now unrecoverable through any code path since the escrow accounting has already been zeroed.
