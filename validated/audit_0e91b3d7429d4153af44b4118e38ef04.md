### Title
Missing slippage protection in `ArbWomUp3.incentiveDeposit` (mode 2) exposes users to sandwich attacks via unprotected `SmartWomConvert.convert` call - (File: `wombat/ArbWomUp3.sol`)

### Summary
`ArbWomUp3._deposit()` mode 2 calls `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)`, hardcoding `_minRec` to `0`. [1](#0-0) 
This is the same bug class as the referenced Sherlock finding: a user-callable function that moves through a real AMM swap without allowing the caller to specify a minimum-received protection, leaving the transaction fully exposed to price manipulation/partial-fill-style value loss.

### Finding Description
`incentiveDeposit()` is a public, unprivileged entry point that any wallet can call with an arbitrary `_amount` and `_mode`. [2](#0-1) 
When `_mode == 2`, `_deposit()` splits the deposited WOM: half is deposited 1:1 into `mWOM`, and the other half is routed through `SmartWomConvert.convert()`:
```solidity
IERC20(wom).safeApprove(smartWomConvert, toSwap);
IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0);
``` [3](#0-2) 
`SmartWomConvert.convert()` forwards `_minRec` unchanged into `_convertFor()`, which performs a real Wombat-pool swap (`buybackAmount`) via `IWombatRouter.swapExactTokensForTokens`, using an internal `amountRec` as part of the output, and only reverts if `convertAmount + amountRec < _minRec`: [4](#0-3) 
Because `ArbWomUp3` hardcodes `_minRec = 0`, this check is a no-op — `0 < convertAmount + amountRec` is always true regardless of how bad the actual swap execution price is. The router call itself is also invoked with `0` as its own minimum-out parameter: [5](#0-4) 
This is functionally identical to the Sherlock M-1 root cause: a user-triggered on-chain swap/order-fill operation with no way for the caller (or the calling contract, `ArbWomUp3`) to enforce a minimum acceptable output, so an attacker can sandwich the swap (front-run to worsen the pool price, let the zero-slippage-protected swap execute at that bad price, then back-run) and capture the difference from the depositing user's funds.

### Impact Explanation
A user calling `incentiveDeposit(..., _mode == 2)` deposits real WOM tokens that get irrevocably transferred and swapped; if sandwiched, the resulting `mWomBal` that gets locked into `mWomSV` on the user's behalf is reduced, and the difference in value is captured by the attacker. This is direct theft of user funds through MEV/sandwich extraction enabled purely by the missing slippage parameter, matching the accepted impact class of the referenced report (fund loss to the user during a supposed one-shot rebalancing/conversion operation).

### Likelihood Explanation
The path is reachable by any unprivileged wallet with no special conditions required — simply calling `incentiveDeposit()` with `_mode == 2` and a nonzero `_amount` triggers the unprotected swap. Sandwich bots monitoring the Wombat WOM/mWOM pool can trivially detect and front-run this pending transaction since `_minRec` is always `0`, making exploitation straightforward and repeatable for every mode-2 deposit.

### Recommendation
Add a caller-supplied `_minRec` (or equivalent minimum-mWOM-out) parameter to `incentiveDeposit()`/`_deposit()` in `ArbWomUp3.sol` and pass it through to `IConverter(smartWomConvert).convert(toSwap, _convertRatio, _minRec, 0)` instead of hardcoding `0`, so the resulting `_minRec` check in `SmartWomConvert._convertFor()` provides real protection against adverse price movement/sandwiching.

### Proof of Concept
1. Attacker monitors mempool for `ArbWomUp3.incentiveDeposit(_amount, _convertRatio, _bullMode, _mode=2)` transactions.
2. Attacker front-runs by swapping WOM→mWOM (or vice versa) on the same Wombat pool used internally by `SmartWomConvert` (`womMWomPool`) to skew the price unfavorably for the pending `buybackAmount` swap.
3. Victim's transaction executes `_deposit()` → `SmartWomConvert.convert(toSwap, _convertRatio, 0, 0)` → `_convertFor()`, which swaps `buybackAmount` WOM for mWOM via `IWombatRouter.swapExactTokensForTokens(..., 0, ...)`, receiving a reduced `amountRec` at the manipulated price; the `_minRec == 0` check never reverts. [6](#0-5) 
4. Attacker back-runs to restore the pool price and realizes the extracted value; the victim's locked `mWomSV` position is smaller than it should have been for the WOM they deposited.
