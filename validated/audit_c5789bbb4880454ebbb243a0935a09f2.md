### Title
Splitting stake across multiple reward addresses lets a staker bypass the Gini fairness adjustment and gain disproportionate proposer-selection weight - (File: kaiax/staking/staking_info.go, kaiax/valset/impl/getter_proposers.go)

### Summary
The `SelectWeightedRandomProposer` mechanism applies a concave power-law adjustment (`S_i = Round(S_i^(1/G))`) to each validator's staking amount before computing its share of the block-proposer lottery, in order to reduce the dominance of large stakers (fairness/anti-centralization goal). Because staking amounts are consolidated by `RewardAddr` before the exponent is applied, a staker who instead registers multiple AddressBook entries under **distinct reward addresses** (splitting one large economic stake into several smaller nominal stakes) receives a strictly larger combined adjusted weight than if the same total stake were consolidated under one identity. This directly mirrors the FEI bug class: a nonlinear (here concave, there quadratic-convex) formula intended to penalize/scale with size can be gamed by splitting a single large input into many smaller inputs processed independently.

### Finding Description

and implemented in: [2](#0-1) 

The exponent `1/(1+gini)` is always in `(0,1]`, making `f(x)=x^(1/(1+G))` a strictly concave function of the staking amount (for `G>0`). For any concave `f` with `f(0)=0`, splitting a quantity into parts and summing `f` of each part yields a value **greater than or equal to** applying `f` to the whole (e.g., `f(1)+f(1) ≥ f(2)` when `f(x)=x^0.5`). The whole design intent of applying the Gini exponent is the opposite — to *shrink* large stakes' influence relative to small stakes so that concentrated stake does not dominate proposer selection.

Staking amounts are consolidated into a single node only when multiple AddressBook entries share the same `RewardAddr`: [3](#0-2) [4](#0-3) 

If instead a staking entity registers N separate AddressBook entries with N *different* reward addresses (each holding `StakingAmount/N`, each independently meeting `MinimumStake`), each entry is treated as its own `consolidatedNode` and independently gets `Round((StakingAmount/N)^(1/(1+G)))` applied, then summed for the total weight calculation in `generateProposerListWeighted`: [5](#0-4) 

Because of concavity, `N · (StakingAmount/N)^(1/(1+G)) > StakingAmount^(1/(1+G))` for `N>1`, so the split entity's aggregate adjusted weight (and therefore aggregate percentile weight `W_i` and proposer-list slot count) exceeds what a single, honestly-consolidated identity with the same total stake would receive. This lets a staker with a fixed amount of capital obtain more expected proposer slots than an equally-capitalized, non-splitting staker — the opposite of the Gini mechanism's intended fairness effect.

This is directly analogous to the FEI `UniswapIncentive` bug: there, a convex penalty function meant to discourage large single actions was defeated by splitting the action into many small pieces; here, a concave "de-concentration" adjustment meant to discourage a single large stake is defeated by the mirror-image trick — splitting the stake into many small pieces to inflate the *sum* of the concave transform.

### Impact Explanation
Being selected more frequently as block proposer confers direct, concrete value: control over transaction ordering/inclusion within a block (MEV extraction), eligibility to win the block-building auction slot (`kaiax/auction`), and block/staking rewards tied to proposer duty. A staker who splits an otherwise-dominant stake across multiple nominal reward identities can obtain a materially higher proposer-selection probability than the Gini mechanism intends to permit for that amount of capital, undermining the governance-configured fairness parameter (`reward.useginicoeff`) and enabling reward/opportunity redirection disproportionate to actual economic stake. This qualifies as reward redirection / unfair value capture reachable purely through normal (non-malicious-node, non-consensus-message) staking registration actions.

### Likelihood Explanation
Exploitability requires only that the actor control enough capital to run multiple qualified validator/staking-contract registrations (each meeting `MinimumStake`) with distinct reward addresses — a normal staker action, not a privileged or consensus-breaking one. The benefit scales predictably with the number of splits and is deterministic given the Gini/exponent formula, making the strategy straightforward to execute and to model for profit-maximizing stakers on chains where `UseGiniCoeff` governance option is enabled. The main constraint is `MinimumStake` per split entry, which bounds how finely a given stake can be divided but does not eliminate the effect for stakers with capital well above several multiples of `MinimumStake`.

### Recommendation
Compute the Gini coefficient and the concave exponent adjustment over an economic entity's *total* controlled stake rather than per `RewardAddr`-consolidated entry, or otherwise design the weighting function so that the sum of the transform over any partition of an entity's total stake is bounded by (or equal to) the transform applied to the total. Alternatively, apply the adjustment only after aggregating stake by beneficial owner/operator (if identifiable) rather than by reward address, or use a globally re-normalized concave adjustment that is provably partition-invariant (e.g., always applied to the full ordered vector of "true" economic stakeholders rather than allowing self-selected splitting of identities).

### Proof of Concept
Given `G` (gini coefficient) and exponent `e=1/(1+G)`:
1. A staker with total stake `S` registers as a single AddressBook entry (single `RewardAddr`): adjusted weight = `S^e`.
2. The same staker instead registers `N` AddressBook entries, each with staking amount `S/N` and a distinct `RewardAddr` (all above `MinimumStake`): combined adjusted weight = `N·(S/N)^e`.
3. For `e<1` (i.e., whenever `G>0`, which is the normal case for any non-uniform validator set — see test expectations of nonzero Gini values in [6](#0-5)  and [7](#0-6) 
), `N·(S/N)^e > S^e` strictly, e.g., for `S=4, N=4, e=0.5`: split sum = `4·1^0.5 = 4` vs. unsplit = `4^0.5 = 2` — a 2x weight increase for identical capital, translating directly into `W_i` (percentile weight) and proposer-list slot count via [8](#0-7) .

// generateProposerList generates a proposer list at a certain block (i.e. proposer update interval),
// whose qualified validators are `qualified`, staking amounts are in `si`, parameters are `pset` and its block hash is `blockHash`.
func generateProposerListWeighted(qualified *valset.AddressSet, si *staking.StakingInfo, useGini bool, blockHash common.Hash) []common.Address {
	var (
		addrs          = qualified.List()
		stakingAmounts = collectStakingAmounts(addrs, si)
		gini           = computeGini(stakingAmounts) // si.Gini is computed over every CN. But we want gini among validators, so we calculate here.
		exponent       = 1.0 / (1 + gini)
		totalStakes    = float64(0)
	)

	// Adjust staking amounts and calculate the sum
	if useGini {
		for addr, amount := range stakingAmounts {
			stakingAmounts[addr] = math.Round(math.Pow(float64(amount), exponent))
			totalStakes += stakingAmounts[addr]
		}
	} else {
		for _, amount := range stakingAmounts {
			totalStakes += amount
		}
	}

	// Calculate percentile weights
	weights := make(map[common.Address]uint64)
	if totalStakes > 0 {
		for _, addr := range addrs {
			weight := uint64(math.Round(stakingAmounts[addr] * 100 / totalStakes))
			if weight <= 0 {
				weight = 1
			}
			weights[addr] = weight
		}
	} else {
		for _, addr := range addrs {
			weights[addr] = 0
		}
	}

	// Generate weighted repeated list
	proposerList := make([]common.Address, 0)
	for _, addr := range addrs {
		for i := uint64(0); i < weights[addr]; i++ {
			proposerList = append(proposerList, addr)
		}
	}

// consolidatedNode is the refined staking information suitable for proposer selection.
// Sometimes a node would register multiple NodeIds in AddressBook,
// in which each entry has different StakingAddr and same RewardAddr.
// We treat those entries with common RewardAddr as one GC node.
//
// For example,
//
//	NodeIds          = [N1, N2, N3]
//	StakingContracts = [S1, S2, S3]
//	RewardAddrs      = [R1, R1, R3]
//	StakingAmounts   = [A1, A2, A3]
//
// can be consolidated into
//
//	CN1 = {[N1,N2], [S1,S2], R1, A1+A2}
//	CN3 = {[N3],    [S3],    R3, A3}
//
// If the node has CLStakingInfo, it will be added to the consolidatedNode.
type consolidatedNode struct {
	NodeIds          []common.Address
	StakingContracts []common.Address
	RewardAddr       common.Address // The common RewardAddr
	StakingAmount    uint64         // Sum of the staking amounts from CNStaking

	CLStakingInfo *CLStakingInfo // The CLStakingInfo if any
}

func (si *StakingInfo) consolidateNodes() *[]consolidatedNode {
	// because Go map is not ordered, rList keeps track of the occurrence order of RewardAddrs.
	// to later arrange the consolidatedNodes.
	cmap := make(map[common.Address]*consolidatedNode)
	rList := make([]common.Address, 0, len(si.RewardAddrs))
	nToR := make(map[common.Address]common.Address)

	for i, n := range si.NodeIds {
		r := si.RewardAddrs[i]
		// Unique nodeId is guaranteed by AddressBook.
		nToR[n] = r
		if cn, ok := cmap[r]; ok {
			cn.NodeIds = append(cn.NodeIds, n)
			cn.StakingContracts = append(cn.StakingContracts, si.StakingContracts[i])
			cn.StakingAmount += si.StakingAmounts[i]
		} else {
			cmap[r] = &consolidatedNode{
				NodeIds:          []common.Address{n},
				StakingContracts: []common.Address{si.StakingContracts[i]},
				RewardAddr:       r,
				StakingAmount:    si.StakingAmounts[i],
			}
			rList = append(rList, r)
		}
	}
