## Finding: Live re-querying of asset `decimals` (not snapshotted) breaks the send/receive/timeout precision round-trip

### Summary
`send`, `on_accept`, and `on_timeout` in `pallet-hyper-fungible-token` each independently re-query the local asset's decimals via `<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(asset_id)` at the moment they execute, rather than using a value that was fixed/snapshotted for the registered token or for the specific in-flight message [1](#0-0) . The `erc_decimals >= local_decimals` invariant is only checked once, at `register_token`/`update_token` time, against whatever `decimals` value the asset reports at that instant [2](#0-1) . It is never re-validated in `send`, `on_accept`, or `on_timeout`.

### Finding Description
The scaling functions use `saturating_sub` between `erc_decimals` and `local_decimals`: [3](#0-2) 

If `local_decimals` reported by the `Assets` pallet changes between the time a `send` locks/burns funds and the time the corresponding `on_timeout` (or, for a different message, `on_accept`) runs on the same chain, the two conversions use different `local_decimals` values even though they refer to the exact same on-chain ERC20 amount encoded in the message body. Because:

- `send` locks/burns `params.amount` (raw local units) and separately encodes `erc20_amount = convert_to_erc20(amount, erc_decimals, decimals_at_send_time)` into the outbound message [4](#0-3) .
- `on_timeout` decodes that same `erc20_amount` from the message body and converts it back with `convert_to_balance(erc20_amount, erc_decimals, decimals_at_timeout_time)` to determine the refund amount [5](#0-4) .
- `on_accept` does the same live lookup for inbound receives [6](#0-5) .

If `decimals_at_timeout_time` (or `decimals_at_accept_time`) differs from `decimals_at_send_time`, the reconstructed local amount will not equal the amount originally escrowed/burned. Because `local_decimals` is only bounded to be `<= erc_decimals` at registration time and is never re-checked afterward, an increase in the asset's reported decimals between send and timeout/accept shifts the divisor down, inflating the recovered local amount — e.g., original decimals 6 vs erc 18 (100 units → encoded as `100 * 10^12`); if decimals is later changed to 12 (still ≤ 18, so no re-check would catch it), `on_timeout` divides by `10^6` instead of `10^12`, producing a refund of `100 * 10^6` — a million-fold inflation relative to what was actually escrowed for that message. This drains the pallet's shared escrow account (`pallet_account()`), affecting all other users' locked/escrowed balances for that asset, not just the attacker's own funds.

Whether this is practically triggerable depends on whether `T::Assets`'s decimals metadata is mutable by an account that is not privileged relative to the bridge (e.g., in `pallet-assets`, `set_metadata` is callable by the asset's `Owner`, which for a permissionlessly-created asset can be an ordinary user, not root/governance). I was not able to fully confirm from the indexed files which concrete `Assets` implementation and asset-ownership model is wired into the production `gargantua`/`nexus` runtimes (the runtime config files for `pallet_assets::Config` were not available in the index) — the caller could not verify whether decimals are truly mutable post-registration in the deployed runtime, or whether asset metadata is locked/frozen by governance before a token is registered for bridging. If decimals are immutable once set, or if only a privileged origin can alter them, this issue would fall outside the "unprivileged attacker" requirement of the bounty scope.

### Impact Explanation
If exploitable, this allows the escrow account (or the mint/burn accounting for non-native assets) to become inconsistent with the total amount that was ever locked/burned across in-flight sends, letting an attacker who controls the underlying asset's metadata trigger over-sized refunds via `on_timeout` (or over-sized credits via `on_accept`), draining pooled escrow funds belonging to other users. This matches the "Critical: wrongful mint, unlock, withdrawal, refund" impact category.

### Likelihood Explanation
Requires: (1) governance/`CreateOrigin` registering a token whose underlying asset's decimals metadata is mutable by a non-privileged account after registration, and (2) the attacker being able to change decimals metadata and then trigger/wait for a `send` + `on_timeout` (or `on_accept`) round trip with different decimals observed at each step. This is a real design gap (missing snapshot/pinning of decimals per registered token or per in-flight message) but its exploitability is contingent on the concrete `Assets` pallet configuration and asset-ownership policy in the deployed runtime, which I could not fully confirm from the available code.

### Recommendation
Snapshot `local_decimals` (and `erc_decimals`) at `send` time and store them keyed by the request commitment (or embed them in the message/receipt), so `on_accept`/`on_timeout` use the exact decimals pair that was valid when the funds were escrowed/burned, instead of re-querying live, mutable asset metadata. Alternatively, re-validate `erc_decimals >= local_decimals` (and reject/queue for review if it no longer holds) whenever `send`/`on_accept`/`on_timeout` execute, and disallow further metadata changes to decimals on any asset once it has been registered for bridging.

### Proof of Concept
Not runnable without confirming the deployed runtime's `pallet_assets::Config` ownership/metadata-mutability policy, which the available index does not contain. A concrete PoC would: (1) register an asset with `decimals=6` and bridge config `erc_decimals=18`; (2) call `send` with `amount=100`, escrowing 100 units and encoding `erc20_amount = 100 * 10^12`; (3) as the asset owner, call the underlying `Assets` pallet's metadata-update extrinsic to change `decimals` to `12`; (4) trigger `on_timeout` for the original request, observing the refund is `100 * 10^6` instead of `100`, exceeding the amount that was ever escrowed for that message. pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
