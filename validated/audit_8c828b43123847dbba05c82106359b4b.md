### Title
Missing non-zero validation on `Kip71GasTarget` governance parameter causes divide-by-zero panic in `NextMagmaBlockBaseFee` - (File: `params/kip71_config.go`, `kaiax/gov/param.go`)

### Summary
The KIP-71 (Magma) dynamic base-fee governance parameter `GasTarget` is validated with a `noopFormatChecker` that accepts any `uint64` value, including `0`. `Kip71GasTarget`'s sibling parameter, `Kip71BaseFeeDenominator`, explicitly rejects `0` (`v != 0`) precisely because it is later used as a divisor [1](#0-0) , but `Kip71GasTarget` has no equivalent guard [2](#0-1) . `GasTarget` is also used as a divisor in `NextMagmaBlockBaseFee`, so a governance-set value of `0` produces an unconditional `big.Int` division-by-zero panic, analogous to the `serial_update_parameters` divide-by-zero described in CVE-2016-8669.

### Finding Description
`NextMagmaBlockBaseFee` computes the next block's base fee whenever `parentGasUsed != gasTarget`. In both the "above target" and "below target" branches it divides an accumulator by `gasTarget`: [3](#0-2) [4](#0-3) 

If `gasTarget == 0`, and `parentGasUsed` is anything other than `0` (the "equal" shortcut at line 90-91 only avoids the divide when `parentGasUsed == gasTarget`), then `x.Div(x, new(big.Int).SetUint64(gasTarget))` divides by zero. Go's `math/big.Int.Div` panics on divide-by-zero, unlike normal float or hardware integer semantics, so this is a hard process crash rather than a silent wraparound.

Unlike `Kip71BaseFeeDenominator`, which is guarded against `0` in the parameter table, `Kip71GasTarget` uses `noopFormatChecker`, meaning the governance module accepts and commits a `GasTarget = 0` value without rejecting it: [5](#0-4) 

This function is invoked pervasively across node subsystems that must remain live for ordinary transaction processing, not just consensus/header verification:
- Header validation (`VerifyMagmaHeader`) for every block [6](#0-5) 
- Tx pool admission logic (`blockchain/tx_pool.go`)
- Block assembly (`work/worker.go`)
- Fee-history RPC (`node/cn/gasprice/feehistory.go`, lines 111-112) [7](#0-6) 
- Gas price suggestion (`node/cn/gasprice/gasprice.go`)

So once `GasTarget=0` is committed to the chain configuration (via a governance vote), every node computing the next base fee for tx-pool admission, block building, header validation, or serving `eth_feeHistory`/`eth_gasPrice` RPC calls will panic and crash, since these code paths are triggered by ordinary unprivileged transaction submission and public RPC calls, not just by the governance actor itself.

### Impact Explanation
This is a chain-wide liveness/availability bug: once the invalid parameter is committed, any subsequent unprivileged transaction submission (tx pool admission) or public RPC call (`eth_feeHistory`, `eth_gasPrice`) on any honestly-running node will hit the same divide-by-zero and crash the process. This can knock every full node in the network offline simultaneously, which is a severe denial-of-service far exceeding the resource-exhaustion class explicitly excluded by the scan rules — it is a full process-crash defect reachable by ordinary users after the (privileged) parameter change, matching CVE-2016-8669's crash characteristics (divide-by-zero causing full process crash) rather than a mere resource-exhaustion issue.

### Likelihood Explanation
Setting `GasTarget = 0` requires success of a governance parameter change (privileged actor, akin to the original CVE's `PR:H`), but the validation gap is entirely unenforced code-side: nothing in `kaiax/gov/param.go` or `paramset.go` rejects `0` for this specific parameter, so the only barrier is process/social convention. Given the presence of an explicit non-zero check on the closely related `BaseFeeDenominator` parameter, the omission of the same guard for `GasTarget` appears to be an oversight rather than an intentional design decision, making accidental or malicious governance misconfiguration realistic.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` that rejects `0` (mirroring `Kip71BaseFeeDenominator`'s `v != 0` check) in `kaiax/gov/param.go`, and/or add a defensive zero-check inside `NextMagmaBlockBaseFee` in `params/kip71_config.go` that clamps or rejects a zero `GasTarget` before performing the divisions, so that a bad governance value cannot crash consensus-critical and RPC-serving code paths.

### Proof of Concept
1. Via governance vote, set `Kip71GasTarget` to `0` (currently accepted because `FormatChecker: noopFormatChecker` in `kaiax/gov/param.go` line 326 performs no validation).
2. Once the parameter takes effect, produce a block where `parentGasUsed != 0` (trivially achieved by any regular transaction being included, since `parentGasUsed = 0` would only occur for an empty block).
3. On the next block, `NextMagmaBlockBaseFee(parentHeaderNumber, parentBaseFee, parentGasUsed)` is invoked with `gasTarget = 0`; since `parentGasUsed > 0 == gasTarget`, execution takes the "above target" branch at `params/kip71_config.go` lines 99-103, calling `x.Div(x, new(big.Int).SetUint64(0))`, which panics with "division by zero" inside `math/big`.
4. This function is called from `blockchain/tx_pool.go` on every transaction admission and from `work/worker.go` during block assembly, so every full node crashes as soon as it tries to admit a transaction or build/validate the next block.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
