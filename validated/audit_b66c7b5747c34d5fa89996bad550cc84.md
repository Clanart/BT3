## Analysis

The Wildcat report's core broken invariant: a per-account ledger entry is recorded as a fixed amount at deposit time, while the actual custodied token balance can drift from the sum of ledger entries (rebasing token), and withdrawal logic pays out the fixed ledger value rather than checking against real custody. Hyperbridge's IntentGatewayV2 has a structurally identical pattern in its escrow accounting.

### Title
Commingled per-token escrow pool with fixed ledger amounts causes cross-order insolvency/fund loss for elastic-supply input tokens - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._orders[commitment][token]` records a fixed escrowed amount per order at placement time, but all orders sharing the same input `token` draw from one commingled contract balance. `_withdraw()` blindly transfers the recorded `amount` to the beneficiary without ever checking the contract's actual token balance against the sum of outstanding escrow obligations for that token. If the token's held balance can fall below the sum of recorded escrow entries — as happens with rebasing/elastic-supply tokens, negative-rebase events, or any token whose balance can change independently of transfers into/out of the gateway — earlier withdrawals succeed by consuming other orders' principal, and later legitimate claimants permanently lose access to their escrowed funds.

### Finding Description
`placeOrder` escrows tokens per order and records the amount in a per-commitment map: [1](#0-0) 

All escrowed tokens for all orders live together in the gateway contract's own balance — there is no per-order token custody, no vault, and no accounting of the token's live balance versus the sum of all `_orders[*][token]` entries.

`_withdraw()` (called from both `fillOrder`'s cross-chain settlement path and `RefundEscrow`/`RedeemEscrow` `onAccept` handling) only checks that the specific order's escrow entry is non-zero, then transfers the fixed recorded `amount`: [2](#0-1) 

There is no invariant check that `IERC20(token).balanceOf(address(this)) >= sum of all outstanding _orders[*][token]` before or after the transfer. The gateway already demonstrates awareness of balance-vs-ledger divergence for fee-on-transfer tokens — it measures actual received balance at deposit time and stores the reduced amount: [3](#0-2) 

but this only fixes divergence *at deposit*. Nothing protects against divergence that occurs *after* deposit while tokens sit in escrow (which can be for the full `order.deadline` window, i.e. many blocks). Any elastic-supply/rebasing token, or any token whose balance the gateway holds can decrease independent of an explicit transfer out (negative rebase, protocol-level slashing, token migration, etc.), will desynchronize the commingled contract balance from the sum of `_orders` ledger entries. Because settlement pays out of the shared pool using the stale fixed ledger value, whichever order's `RedeemEscrow`/`RefundEscrow`/fill executes first drains real tokens that other still-pending orders' ledger entries are counting on.

### Impact Explanation
This is a direct "loss of funds" vector matching the Hyperbridge impact gate: legitimate users/solvers with valid, unfilled/uncancelled escrow entries can have their `_orders[commitment][token]` balance become uncollectable because the contract's actual token balance has fallen below the sum of all outstanding entries for that token. `safeTransfer` in `_withdraw()` will revert once the shared pool is insufficient, permanently locking out later claimants even though their on-chain ledger entry says they are owed tokens — no admin, relayer, or malicious peer action is needed; only ordinary use of an elastic-supply token as `order.inputs[i].token` is required. Earlier claimants effectively receive value at the expense of later ones purely due to FIFO settlement order, not fault.

### Likelihood Explanation
Likelihood is moderate: it requires a market/order using a token type outside the "well-behaved constant-balance ERC-20" assumption (rebasing, elastic supply, yield-bearing wrapper with mutable exchange rate, etc.). The protocol does not restrict which tokens can be used as `order.inputs[i].token` — `placeOrder` accepts arbitrary ERC-20 addresses — so this is reachable by any ordinary unprivileged user simply placing/settling orders with such a token, with no attacker cooperation from relayers, provers, or governance required.

### Recommendation
- Track escrow per-token in a way that is resilient to balance drift, e.g. maintain a running sum of outstanding escrow per `token` and assert `IERC20(token).balanceOf(address(this)) >= outstandingEscrow[token]` invariant is never violated, or isolate custody per order (not commingled).
- Alternatively, explicitly disallow/blacklist rebasing and elastic-supply tokens as intent inputs, and document that markets/orders are not compatible with such tokens, mirroring the Wildcat remediation.
- Consider snapshotting actual balance-based accounting (measure real balance delta) not just at deposit (as already done for fee-on-transfer) but also at withdrawal time, so any positive/negative drift is handled deterministically rather than allowing first-mover advantage to drain shared custody.

### Proof of Concept
1. Deploy `IntentGatewayV2` and register token `T` (an elastic-supply/rebasing ERC-20) as a valid input token — no allowlist prevents this (`evm/src/apps/IntentGatewayV2.sol` `placeOrder` path, e.g. lines 331-343).
2. User A places `OrderA` with `input = 1000 T`; gateway records `_orders[commitmentA][T] = 1000` and holds `1000 T` (minus any protocol fee).
3. User B places `OrderB` with `input = 1000 T`; gateway now holds `2000 T` total, with `_orders[commitmentB][T] = 1000`.
4. Token `T` undergoes a negative rebase (or any balance-reducing event not routed through the gateway's transfer functions) reducing the gateway's actual balance of `T` to `1200 T`, while the ledger still records `1000 + 1000 = 2000` owed.
5. Solver fills `OrderA` first; cross-chain settlement calls `_withdraw` for `commitmentA`, which succeeds, transferring `1000 T` out (gateway balance now `200 T`).
6. Solver attempts to fill/cancel `OrderB`; `_withdraw` for `commitmentB` attempts `safeTransfer(beneficiary, 1000)` against a real balance of only `200 T` — the ERC-20 transfer reverts, and User B's `1000 T` escrow entry remains permanently unredeemable even though `_orders[commitmentB][T]` still shows `1000` owed.     function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
