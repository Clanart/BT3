### Title
Operator-attribution OP_RETURN output in `payout_tx` is not covered by the user's withdrawal signature, allowing reimbursement credit to be hijacked from the operator who actually paid - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The withdrawal fronting flow determines *which operator gets bridge-funded reimbursement* by parsing an OP_RETURN output in the confirmed `payout_tx` that is never covered by the user's withdrawal signature. Because the user signs the payout with a `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY`-style signature (only binding input 0 and output 0), the OP_RETURN output that records `operator_xonly_pk` is fully malleable by any third party who observes the broadcast transaction, exactly mirroring the reported bug class: a value used for a downstream custody/attribution decision (`priceTarget` in the original report; here `payout_payer_operator_xonly_pk`) is derived inconsistently from — and unauthenticated relative to — the value that was actually checked/signed.

### Finding Description
`create_payout_txhandler` builds the operator payout transaction with a single, user-signed input and three outputs: [1](#0-0) 

Only input 0 is signed via `set_p2tr_key_spend_witness(&user_sig, 0)`, and this is the same withdrawal signature whose expected type is documented elsewhere in the codebase as `SinglePlusAnyoneCanPay`: [2](#0-1) 

A `SIGHASH_SINGLE|ANYONECANPAY` signature commits only to input 0 and to the output whose index matches the signed input (output 0, the user payout). It does **not** commit to output 1 (anchor) or output 2 (the OP_RETURN carrying `operator_xonly_pk`). This means anyone who observes the raw signature, input UTXO, and output (all of which must be public once the operator broadcasts the transaction to the Bitcoin network to get it confirmed) can construct an alternative, still-validly-signed transaction that spends the same input, pays the same user output, but substitutes a different `operator_xonly_pk` in the OP_RETURN output, and replace/out-race the original with a higher-fee variant (the tx uses `NON_STANDARD_V3`/default sequence, i.e. RBF-capable).

Downstream, the *confirmed* transaction's OP_RETURN is the sole source of truth for who gets credited as the fronting operator: [3](#0-2) 

This attribution is then used to select which operator's unhandled-payout queue the reimbursement path advances: [4](#0-3) [5](#0-4) 

and to gate the operator's own reimbursement-tx-generation logic: [6](#0-5) 

Because the value that decides "who gets reimbursed" (`payout_payer_operator_xonly_pk`, read from the OP_RETURN of whichever transaction ends up confirmed) is not bound by the same cryptographic authorization that permitted the withdrawal to be spent (the user's SINGLE|ANYONECANPAY signature), the custody/attribution binding `operator credited == party that actually got its payout tx confirmed and will later be reimbursed` can be broken by any third party — exactly the "operator credited versus the party that paid" pattern called out as in-scope.

### Impact Explanation
An attacker (which could be a rival operator, or any unprivileged party who can observe transactions announced to the Bitcoin P2P network/mempool before confirmation) can:
1. Observe a legitimate operator's broadcast `payout_tx` (input 0 = withdrawal UTXO with valid `SIGHASH_SINGLE|ANYONECANPAY` user signature, output 0 = user payout).
2. Rebuild an alternative transaction reusing the same signed input and output 0, but with a different OP_RETURN output claiming a different `operator_xonly_pk` (their own, or an arbitrary operator's key), and a competitive fee for the anchor (CPFP/RBF).
3. Get their variant confirmed instead of (or as a replacement of) the original.
4. The verifier's `update_finalized_payouts` records the *attacker-chosen* operator as `payout_payer_operator_xonly_pk` for that withdrawal index.
5. `PayoutCheckerTask`/`handle_finalized_payout` then drives the reimbursement (kickoff → reimburse) flow for that attacker-chosen operator, i.e., "an operator reimbursed for a payout it never funded", while the operator who actually incurred the fronting/latency cost and originally broadcast the transaction is denied credit and cannot be reimbursed for a withdrawal it processed ("an honest operator permanently unable to be reimbursed").

This maps to the Critical impact category: an operator reimbursed for a payout it never funded / an honest operator permanently unable to be reimbursed.

### Likelihood Explanation
The attack requires only: (a) visibility of a broadcast, unconfirmed `payout_tx` (public once relayed on the Bitcoin network), and (b) the ability to submit a conflicting/RBF transaction with a higher fee — both of which are available to any unprivileged network participant, not just a verifier/operator/aggregator/watchtower. No key compromise, majority hashrate, or privileged role is required, only that the malleable output (OP_RETURN) is outside the sighash coverage, which is a direct, deterministic consequence of the chosen signature type for this transaction.

### Recommendation
Bind the operator attribution to the same signature that authorizes spending the withdrawal UTXO, e.g.:
- Use a sighash type that covers all outputs (e.g., `SIGHASH_ALL`) for the withdrawal signature used in `create_payout_txhandler`, or
- Have the operator additionally co-sign (or have the user's signature additionally commit to) a hash of the full output set including the OP_RETURN `operator_xonly_pk`, so no output of `payout_tx` can be altered post-signature without invalidating the signature.

### Proof of Concept
1. User creates and signs a withdrawal (`WithdrawParams`) for `withdrawal_utxo` with signature type `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY`, intended output 0 = user's payout address/amount.
2. Operator A calls `withdraw`/`InternalWithdraw`, which builds `payout_tx_A` via `create_payout_txhandler` (input 0 signed; output 0 = user payout; output 1 = anchor; output 2 = OP_RETURN(Operator A xonly pk)), and broadcasts it. [1](#0-0) 
3. Attacker observes `payout_tx_A` in the mempool, extracts the same signed input (0) and output (0), and builds `payout_tx_B`: identical input 0/witness, identical output 0, but output 2 OP_RETURN replaced with Operator B's (attacker-controlled) xonly pubkey, with a higher fee/anchor bump enabling RBF replacement.
4. `payout_tx_B` confirms instead of `payout_tx_A`.
5. `update_finalized_payouts` reads `payout_tx_B`'s OP_RETURN and stores `payout_payer_operator_xonly_pk = Operator B`. [7](#0-6) 
6. `PayoutCheckerTask` picks up the unhandled payout keyed to Operator B and drives `handle_finalized_payout`, letting Operator B claim reimbursement for a withdrawal it did not originate. [5](#0-4) [4](#0-3) 

**Note on confidence:** I confirmed the `SinglePlusAnyoneCanPay` sighash convention is explicitly referenced for the withdrawal signature verification path in `core/src/rpc/aggregator.rs`, and that `create_payout_txhandler`'s single signed input structurally cannot cover the OP_RETURN output regardless of exact sighash flags chosen, since SIGHASH_SINGLE (if used) binds only the output at the same index as the signed input (index 0), never output 2. I was not able, within the available tool budget, to pull the exact call site in `core/src/operator.rs` that parses/enforces `in_signature.sighash_type` for the non-optimistic `withdraw` path to double-check it isn't coerced to `SIGHASH_ALL` there; if it is instead hardcoded to `SIGHASH_ALL` for that specific path, this analog would not apply to `create_payout_txhandler`'s flow (though it would still apply to any tx type sharing this signing pattern). This should be verified directly against `core/src/operator.rs`'s `withdraw` function before treating this as fully confirmed.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }

    /// For a deposit_id checks that the payer for that deposit is the operator, and the payout blockhash and kickoff txid are set.
    async fn validate_payer_is_operator(
        &self,
        dbtx: Option<DatabaseTransaction<'_>>,
        deposit_id: u32,
    ) -> Result<(BlockHash, Txid), BridgeError> {
        let (payer_xonly_pk, payout_blockhash, kickoff_txid) = self
            .db
            .get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id(dbtx, deposit_id)
            .await?;

        tracing::info!(
            "Payer xonly pk and kickoff txid found for the requested deposit, payer xonly pk: {:?}, kickoff txid: {:?}",
            payer_xonly_pk,
            kickoff_txid
        );

        // first check if the payer is the operator, and the kickoff is handled
        // by the PayoutCheckerTask, meaning kickoff_txid is set
        let (payout_blockhash, kickoff_txid) = match (
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid,
        ) {
            (Some(payer_xonly_pk), Some(payout_blockhash), Some(kickoff_txid)) => {
                if payer_xonly_pk != self.signer.xonly_public_key {
                    return Err(eyre::eyre!(
                        "Payer is not own operator for deposit, payer xonly pk: {:?}, operator xonly pk: {:?}",
                        payer_xonly_pk,
                        self.signer.xonly_public_key
                    )
                    .into());
                }
                (payout_blockhash, kickoff_txid)
            }
            _ => {
                return Err(eyre::eyre!(
                    "Payer info not found for deposit, payout blockhash: {:?}, kickoff txid: {:?}",
                    payout_blockhash,
                    kickoff_txid
                )
                .into());
            }
        };

        tracing::info!(
            "Payer xonly pk, payout blockhash and kickoff txid found and valid for own operator for the requested deposit id: {}, payer xonly pk: {:?}, payout blockhash: {:?}, kickoff txid: {:?}",
            deposit_id,
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid
        );

        Ok((payout_blockhash, kickoff_txid))
    }
