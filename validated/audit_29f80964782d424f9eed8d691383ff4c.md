## Analysis

The seed report's core broken invariant: an admin action that reconfigures which token maps to which vault/config entry, without accounting for value already escrowed under the old mapping, permanently strands funds and desyncs accounting.

The local analog is in `pallet-hyper-fungible-token`. `send` escrows/burns a user's asset and dispatches a cross-chain `PostRequest` whose `to` field is the current EVM contract address for `(destination, asset_id)`, and whose refund path on timeout is *not* keyed by the original `asset_id` — it is re-derived from the reverse map `ContractToAsset` using only `(dest, to)`. `update_token` can silently repoint or remove that mapping while requests are in flight, so the same `(chain, contract)` key can flip to a different asset (or disappear) before the original request resolves. `on_timeout` and `on_accept` both trust `ContractToAsset` at settlement time, not at dispatch time.

### Title
Stale `ContractToAsset` reverse mapping lets in-flight transfers be refunded/settled as the wrong asset or permanently locked - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`update_token` mutates `TokenContracts` / `ContractToAsset` / `Precisions` for a `(StateMachine, contract)` pair with no check for in-flight requests still referencing the old binding, and no protection against a new `add_chains` entry reusing a contract address already bound to a different `asset_id`. Settlement (`on_accept`) and refund (`on_timeout`) both re-derive the asset purely from the *current* `ContractToAsset` state at call time rather than from the state that was valid when the request was dispatched.

### Finding Description
- `send` reads the current mapping to build the outgoing `PostRequest.to`, then escrows/burns `asset_id` [1](#0-0) .
- `update_token`'s `add_chains` loop unconditionally inserts `ContractToAsset::<T>::insert(chain, token_contract, update.asset_id)`, overwriting any prior entry for that `(chain, token_contract)` key without checking whether it was already bound to a *different* asset, and its `remove_chains` loop deletes the mapping entirely [2](#0-1) .
- On timeout, the refund path looks up the asset solely from the *current* `ContractToAsset::<T>::get(dest, &to)` and uses whatever asset/decimals/native-flag it finds now, not what was true when the request was sent [3](#0-2) , then transfers/mints that asset to the sender [4](#0-3) .
- `on_accept` has the same pattern: it authenticates purely via the live `ContractToAsset` lookup and mints/transfers whatever asset that currently resolves to [5](#0-4) .

Because the mapping can change between dispatch and settlement (a routine `update_token` operation, e.g. redeploying a token contract or onboarding a second asset), the pallet has no per-request record binding the request to the asset/decimals it was created with.

### Impact Explanation
- If `update_token` remaps `(chain, contract)` to a different `asset_id` while a request is in flight, `on_timeout` refunds the sender in the **wrong asset** (potentially minting a non-native asset for free, or draining the new asset's native-custody escrow) while the original escrowed/burned asset is never released — a direct fund-loss / wrong-asset payout matching "Bridged assets ... must move exactly once and only to the rightful beneficiary and amount."
- If `update_token` instead removes the chain (`remove_chains`), `on_timeout`'s `ContractToAsset::<T>::get` returns `None`, the call errors with `UnknownContractOnTimeout`, and the escrowed/burned funds behind that request become **permanently locked** with no recovery path — the same "token would be locked" outcome as the seed report.
- This breaks custody accounting exactly like the original `removeToken` bug: the pallet's escrow account balance stops matching outstanding request obligations.

### Likelihood Explanation
`update_token`/`register_token` are gated by `T::CreateOrigin` [6](#0-5) , so triggering the remap itself needs a governance call — but this is a normal, expected operational action (e.g., redeploying/upgrading an EVM-side token contract, or onboarding a second token), not a malicious/compromised-governance scenario. Any unprivileged user's ordinary `send` that happens to be in flight when such a routine update lands is affected; no attacker collusion with governance is required, only ordinary timing.

### Recommendation
Snapshot the resolved `asset_id`, decimals, and native-flag into the dispatched request's own state (e.g., store a `RequestId -> AssetContext` record at `send` time, or encode the asset context in the request commitment) and use that snapshot in `on_accept`/`on_timeout`, instead of re-resolving via the mutable `ContractToAsset`/`TokenContracts`/`Precisions` maps at settlement time. Additionally, `update_token`'s `add_chains` should reject reusing a `token_contract` address that is already bound to a different `asset_id` on that chain, and `remove_chains` should be disallowed (or require draining escrow) while requests referencing that binding are still outstanding.

### Proof of Concept
1. Alice calls `send` with `asset_id = TokenA`, `destination = Evm(X)`; `TokenContracts[(Evm(X), TokenA)] = C`. Her `TokenA` is escrowed/burned and a `PostRequest{ to: C, dest: Evm(X) }` is dispatched [7](#0-6) .
2. Before the request resolves, governance runs a routine `update_token` for `TokenB` with `add_chains = {Evm(X): ChainConfig{token_contract: C, ...}}`. This overwrites `ContractToAsset[(Evm(X), C)]` from `TokenA` to `TokenB`, while `TokenContracts[(Evm(X), TokenA)]` still equals `C` [8](#0-7) .
3. Alice's original request times out. `on_timeout` looks up `ContractToAsset::<T>::get(Evm(X), C)`, now returns `TokenB`, and mints/transfers `TokenB` to Alice instead of refunding `TokenA` [9](#0-8) .
4. Alice's `TokenA` remains permanently escrowed/burned with no accounting entry pointing back to it — funds lost/misdirected, and (if `TokenB` is non-native) new `TokenB` supply was minted without backing.
