### Title
Copilot conflict resolution splices resolved hunks into files by positional order with no cross-check against the original hunk content, allowing an attacker-controlled merge conflict to cause silent misapplication of resolved content - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
This is structurally the same bug class as the PA1D report: a value (here, a per-hunk resolution string) is propagated and substituted into a result without validating that it actually corresponds, in identity and position, to the object it is being applied to. In PA1D, a raw basis-point value was used where an 18-decimal percentage was expected, with no cross-check against the invariant the consumer (Zora Market) relied on. In Desktop's Copilot merge-conflict resolver, `hunkResolutions[hunkIndex]` is spliced into the `hunkIndex`-th `<<<<<<<...>>>>>>>` block found by `reassembleResolvedFile`, matched purely "by order, not by line number" [1](#0-0) , while the only integrity check performed beforehand, `validateResolutionPaths`, verifies solely that the *count* of hunks matches per file [2](#0-1)  — it never verifies that resolution *i* was generated from hunk *i*'s actual `oursContent`/`theirsContent`.

### Finding Description
`extractConflictHunks` parses a conflicted working-directory file into an ordered list of `IConflictHunk` objects using the ours/base/separator/theirs marker regexes [3](#0-2) . This ordered list, containing attacker-influenced content (the "theirs" side comes directly from the incoming/attacker-controlled branch or PR being merged), is what gets sent to the Copilot model as prompt context.

The model's JSON response is validated only for path membership, no duplicates, no missing files, and a matching *hunk count* per file via `validateResolutionPaths` [4](#0-3) . There is no check that `resolutions[i].hunks[j]` was derived from `expectedFiles[i].hunks[j]`'s actual content — the model is free (and, since the "theirs" content is attacker-supplied text sent verbatim into the model's context/prompt, an attacker-crafted conflict can attempt to influence the model to reorder, omit, or misdirect its resolutions) to return hunks whose count matches but whose order or content is otherwise scrambled or steered, and nothing catches this.

`reassembleResolvedFile` then walks the raw on-disk file, and for the `hunkIndex`-th well-formed `<<<<<<< ... >>>>>>>` block it encounters, blindly splices in `hunkResolutions[hunkIndex].resolvedContent` [5](#0-4) . Because matching is purely positional, if the model's hunk ordering does not correspond 1:1 to the file's on-disk hunk ordering (which the count-only validation cannot detect), resolved content intended for one conflict block silently lands in a different, unrelated conflict block in the file that Desktop will then present to the user as fully resolved and stage/commit.

### Impact Explanation
This falls into "silent corruption of what the user commits or pushes": a user merging a branch/PR from an untrusted or malicious contributor (an attacker-controlled repository object, satisfying the required attacker-controls-a-fetched/cloned-repo primitive) and using Copilot's automatic conflict resolution could have resolved content misapplied to the wrong hunk in the same file, or (if the attacker manages to steer the count-matching-but-scrambled output) end up committing code the user never reviewed as being the resolution for that specific conflict. Because Desktop's UI presents the reassembled file as the model's resolution and offers a single "Continue" action, a misapplied hunk is not obviously visible without diffing hunk-by-hunk against the original ours/theirs content.

### Likelihood Explanation
This requires the model's response ordering/content to diverge from the file's real hunk order while keeping the per-file hunk count identical — a condition `validateResolutionPaths` cannot detect since it never checks per-hunk provenance. The likelihood depends on how reliably an attacker-crafted conflicted file (steering LLM output through injected text in "theirs"/context) can produce a count-preserving but positionally-wrong resolution list; the code's own comments acknowledge the ordering is assumed ("matched by order, not by line number") rather than enforced, so this is a design gap rather than a proven exploited path in the code I could inspect. I was not able to trace the full call site that writes `reassembleResolutions`' output to disk/stages it for commit within the tool budget available, so the final write path (and whether any additional review step exists before commit) is unverified.

### Recommendation
Have `validateResolutionPaths` (or a new validation step before `reassembleResolvedFile`) bind each returned hunk resolution to an explicit hunk identifier (e.g., an index or content hash of `oursContent`/`theirsContent`/`baseContent`) rather than relying on array order and count alone, and reject/flag any resolution whose hunk identifiers don't match the original extraction 1:1 before splicing content into the file.

### Proof of Concept
1. Set up a repository merge where the incoming ("theirs") branch is attacker-controlled and contains a conflicted file with two hunks, each crafted so that the surrounding text (comments, prompt-injection-style content in a nearby hunk) attempts to induce the model to return hunk resolutions whose *count* matches but whose *order relative to the file* is swapped, or to place the more "dangerous" resolution into a hunk the model returns second when the file actually presents it first.
2. Trigger Desktop's Copilot conflict resolution on this file; `extractConflictHunks` extracts the two hunks in file order and sends them to the model.
3. The model returns 2 hunk resolutions (matching count) but in the wrong logical order.
4. `validateResolutionPaths` passes because `resolution.hunks.length === expectedCount` [6](#0-5) .
5. `reassembleResolvedFile` splices `hunkResolutions[0]` into the file's first `<<<<<<<...>>>>>>>` block and `hunkResolutions[1]` into the second, purely by position [7](#0-6) , resulting in content being committed for a hunk it wasn't actually generated for, with no cross-check to catch the mismatch.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
