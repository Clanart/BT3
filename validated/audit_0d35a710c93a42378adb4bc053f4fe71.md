### Title
Attacker-controlled scalar `offset` in `ReceivedOutput::read` selects the wrong spend key, making a reported-received output unspendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary

The NVIDIA report's class (CWE-426, untrusted search path: an attacker-chosen value selects which resource/code is used) maps onto Serai's `ReceivedOutput` deserialization. `ReceivedOutput` couples three fields — a declared scalar `offset`, the `TxOut`, and the `OutPoint` — and `ReceivedOutput::read` accepts all three from raw bytes with no consistency check between the declared `offset` and the actual `script_pubkey` of the output [1](#0-0) . The `offset` is effectively a search path: downstream code uses it to locate which group key owns the output and which tweaked key must sign for it. Because the offset is freely chosen by whoever supplies the bytes, it can be made inconsistent with the on-chain output.

### Finding Description

When `Scanner::scan_transaction` produces a `ReceivedOutput`, `offset` is correct by construction: it is the value looked up in `self.scripts` under the key `output.script_pubkey`, i.e. `script = P2TR(group_key + offset·G)` [2](#0-1) . That invariant — `offset` is the discrete log path from `key` to the output's script key — is exactly what makes the output spendable and correctly attributed.

`ReceivedOutput::read` breaks the invariant: it reads `offset` via `Secp256k1::read_F`, then a `TxOut` and `OutPoint`, and returns them verbatim. Nothing recomputes `p2tr_script_buf(key + offset·G)` or compares it to `output.script_pubkey` [3](#0-2) .

The inconsistency propagates through two dependent computations:

- **Ownership attribution**: `Output::key()` recovers the owning key as `script_key - offset·G` [4](#0-3) . A forged `offset` shifts the recovered key to an arbitrary point, so the output is attributed to a different (possibly nonexistent) key, and `kinds[offset]` classification in `get_outputs` resolves the output kind from the untrusted scalar [5](#0-4) .
- **Spend key selection**: `SignableTransaction`/`multisig` re-keys `ThresholdKeys` by `output.offset()` (via `ThresholdKeys::offset`, which adds the scalar to `included[0]`'s share in `view()` [6](#0-5) ). The resulting BIP-340 signature is valid only for `group_key + declared_offset·G`. If the real outpoint pays to `group_key + true_offset·G` with `declared_offset != true_offset`, the threshold signature does not verify against the output's taproot key — the input can never be spent.

### Impact Explanation

An attacker who can feed crafted bytes to `ReceivedOutput::read` (or `Output::read`, which embeds it [7](#0-6) ) can register an output referencing a real, confirmed UTXO paying a genuine Serai address — e.g. the external address at offset `ZERO`, or the deterministic `branch`/`change`/`forward` scripts derived from public `hash_to_F(KEY_DST, ...)` offsets [8](#0-7)  — while declaring a mismatched `offset`. The protocol treats real funds as received (the balance is credited from `output.value()` [9](#0-8) ), but any transaction built on that input produces a threshold signature under the wrong tweaked key. The signature fails Bitcoin consensus verification, so the reported-received funds are not spendable and the signing attempt stalls on an invalid transaction. This is a concrete integrity/availability failure of the exact "funds reported received that are not spendable" shape, caused by an untrusted scalar selecting the cryptographic path.

### Likelihood Explanation

Likelihood is bounded by how `ReceivedOutput`/`Output` bytes reach `read`. Outputs legitimately originate from the local `Scanner`, which sets `offset` correctly, so exploitation requires a path where serialized output bytes are supplied or mutated by an unprivileged party (e.g. output descriptors relayed between components rather than produced by the local scan). The attacker needs to know only the group key and the public offset-derivation constants (`KEY_DST`, `"branch"`/`"change"`/`"forward"`), all computable off-chain. No collusion, key access, or validator status is needed beyond delivering the malformed bytes. Where the sink is reachable, exploitation is deterministic — no races or probabilistic elements.

### Recommendation

In `ReceivedOutput::read`, or in `Output::read` once the group key is known, verify the binding between `offset` and `output.script_pubkey`: recompute `p2tr_script_buf(script_key)` where `script_key` is parsed from `output.script_pubkey`, and confirm `script_key == group_key + offset·G` for the expected key (equivalently, that `output.script_pubkey` equals one of the registered scanner scripts mapping to `offset`). Reject the encoding otherwise. Alternatively, make `offset` non-serializable — derive it exclusively by `scripts.get(&output.script_pubkey)` at scan time — so the search path can never come from untrusted bytes.

### Proof of Concept

1. Let `K` be the multisig group key (post-`tweak_keys`). The real external address is `S0 = P2TR(K)` with true offset `0`; the branch script is `Sb = P2TR(K + hash_to_F(KEY_DST,"branch")·G)` — all publicly derivable.
2. Attacker broadcasts a Bitcoin transaction paying `V` sats to `S0`. The UTXO `(txid, vout)` is real and confirmed.
3. Attacker crafts `ReceivedOutput` bytes: `offset = hash_to_F(KEY_DST,"branch")` (or any nonzero scalar `d`), `output = TxOut{value: V, script_pubkey: S0}`, `outpoint = (txid, vout)`, and feeds them to `ReceivedOutput::read` / `Output::read`.
4. Deserialization succeeds (`read` performs no consistency check). `Output::key()` returns `S0_key - d·G ≠ K`, and the output is classified/credited as a received balance of `V` sats.
5. A `SignableTransaction` spending this input re-keys the threshold keys by `d`, so the FROST signature verifies under `K + d·G`, not under `S0`'s key `K`. Bitcoin script validation rejects the witness; the transaction is invalid and the credited funds are unspendable.

Root cause: `ReceivedOutput` serializes the search path (`offset`) independently of the resource it selects (`script_pubkey`), and `read` trusts the pair. Fix by validating or eliminating the serialized path.

Caveat: I verified the deserialization and downstream `offset` usage; I did not fully trace every call site feeding untrusted bytes into `Output::read` (the processor/coordinator plumbing beyond `processor/src/networks/bitcoin.rs` was not exhaustively confirmed within scope), so the severity is Medium conditional on a reachable untrusted-bytes path.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

const KEY_DST: &[u8] = b"Serai Bitcoin Output Offset";
static BRANCH_OFFSET: OnceLock<Scalar> = OnceLock::new();
static CHANGE_OFFSET: OnceLock<Scalar> = OnceLock::new();
static FORWARD_OFFSET: OnceLock<Scalar> = OnceLock::new();

// Always construct the full scanner in order to ensure there's no collisions
fn scanner(
  key: ProjectivePoint,
) -> (Scanner, HashMap<OutputType, Scalar>, HashMap<Vec<u8>, OutputType>) {
  let mut scanner = Scanner::new(key).unwrap();
  let mut offsets = HashMap::from([(OutputType::External, Scalar::ZERO)]);

  let zero = Scalar::ZERO.to_repr();
  let zero_ref: &[u8] = zero.as_ref();
  let mut kinds = HashMap::from([(zero_ref.to_vec(), OutputType::External)]);

  let mut register = |kind, offset| {
    let offset = scanner.register_offset(offset).expect("offset collision");
    offsets.insert(kind, offset);

    let offset = offset.to_repr();
    let offset_ref: &[u8] = offset.as_ref();
    kinds.insert(offset_ref.to_vec(), kind);
  };

  register(
    OutputType::Branch,
    *BRANCH_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"branch")),
  );
  register(
    OutputType::Change,
    *CHANGE_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"change")),
  );
  register(
    OutputType::Forwarded,
    *FORWARD_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"forward")),
  );

  (scanner, offsets, kinds)
}
