### Title
Hookify PreToolUse block rules fail open (allow) when rule evaluation throws — ([File: plugins/hookify/hooks/pretooluse.py])

### Summary
The Kakarot finding describes a case where a called-contract panic isn't gracefully handled, causing the enclosing transaction to abort instead of returning a controlled failure — with the practical effect that a security-relevant code path (the DualVmToken call) can be crashed by attacker-controlled input, undermining the caller's expectations. The closest unprivileged-user analog in this repo is in the `hookify` plugin's `PreToolUse` hook: any unhandled exception raised while evaluating a user's `block` rule causes the hook to **fail open and allow the tool call**, silently defeating the block decision the rule was meant to enforce.

### Finding Description
`plugins/hookify/hooks/pretooluse.py` wraps rule loading and evaluation in a blanket `try/except Exception`, and unconditionally exits `0` (allow) in the `finally` block regardless of what happened inside: [1](#0-0) 

`RuleEngine.evaluate_rules` (called from `main()`) only returns a `permissionDecision: deny` response if it completes without raising. `RuleEngine._extract_field` handles `MultiEdit` by assuming every element of `tool_input['edits']` is a dict and calling `.get()` on it: [2](#0-1) 

If a `MultiEdit` tool call's `edits` array contains a non-dict element (e.g. a string, integer, or `null`), `e.get('new_string', '')` raises `AttributeError` inside `evaluate_rules`. This exception propagates all the way up through `RuleEngine.evaluate_rules` → `main()` in `pretooluse.py`, is caught by the outer `except Exception`, and the hook prints a generic error message and **exits 0 with no `permissionDecision: deny`/block output** — meaning the tool call is allowed to proceed exactly as if no rule had matched, even if the user configured a `.claude/hookify.*.local.md` rule with `action: block` on `MultiEdit` content (e.g. blocking edits that introduce secrets, dangerous file writes, etc.).

This mirrors the structural bug class in the report: a downstream evaluation failure (panic/exception) is not turned into a graceful "deny/fail-safe" result — it is instead swallowed in a way that silently reverts to the permissive default, breaking the caller's safety invariant.

### Impact Explanation
Any user-authored `block` rule targeting `MultiEdit` (or any other field path that can hit a non-string/non-dict-shaped value in `_extract_field`) can be bypassed if the tool call's `edits` list contains a malformed element. Since Claude's own tool-use JSON is influenced by the model's output — which can itself be steered by prompt injection from untrusted file/tool content the agent is processing — an attacker who can influence the shape of a `MultiEdit` call (or other hookify-covered tool) can cause the guard hook to throw and thus bypass an operator's blocking rule, allowing an operation the user explicitly configured to be denied (e.g., editing a sensitive file, injecting `console.log`/secrets, etc., depending on the configured rule). The severity is bounded by whatever the user's own block rules are meant to prevent, but it directly defeats the `hookify` plugin's core promise ("Set `action: block` for dangerous operations ... Claude will not be allowed to execute these commands").

### Likelihood Explanation
Requires: (1) the user has a hookify `block` rule configured for `MultiEdit` (or another vulnerable field path), and (2) the tool call's `tool_input` is malformed in a way not defensively checked by `_extract_field` (e.g., a non-dict entry in `edits`). Malformed tool-call shapes are plausible via prompt-injection-influenced model output or a buggy/adversarial MCP tool wrapper feeding into the same tool schema; likelihood is moderate rather than trivial since it depends on rule configuration and a specific malformed-input shape.

### Recommendation
Harden `RuleEngine._extract_field` (and any other field-extraction helper) to defensively type-check every `tool_input` sub-structure (e.g. `isinstance(e, dict)` before calling `.get()` on `edits` entries) and raise/return a safe sentinel instead of throwing. More importantly, change the hook's failure semantics: on any unexpected exception during rule evaluation, a `PreToolUse` hook that has *any* enabled `block` rules for the current event should fail closed (deny) rather than fail open (allow), or at minimum should not silently swallow the exception with an unconditional allow — this preserves the intended security guarantee even when the evaluation logic panics on unexpected input, analogous to the recommended fix in the report (handle failure gracefully rather than let it propagate into a default/permissive outcome).

### Proof of Concept
1. Configure a blocking rule, e.g. `.claude/hookify.block-multiedit.local.md`:
```
---
name: block-multiedit
enabled: true
event: file
tool_matcher: MultiEdit
conditions:
  - field: content
    operator: contains
    pattern: SECRET_KEY
action: block
---
Blocked: MultiEdit contains a secret.
```
2. Trigger a `PreToolUse` call for `MultiEdit` where `tool_input.edits` is `[null]` (or any non-dict element) instead of the expected list of `{old_string, new_string}` dicts — feasible if the agent's tool call is manipulated via injected content, or by simulating the hook input directly:
```bash
echo '{"tool_name":"MultiEdit","tool_input":{"file_path":"x.py","edits":[null]}}' \
  | CLAUDE_PLUGIN_ROOT=plugins/hookify python3 plugins/hookify/hooks/pretooluse.py
```
3. Observe the hook prints a `Hookify error: ...` `systemMessage` and exits `0` with no `permissionDecision: deny` — the operation is allowed even though the configured `block` rule would have matched had evaluation completed normally.

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```
