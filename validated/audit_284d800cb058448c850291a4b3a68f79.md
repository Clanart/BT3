### Title
ReceivedOutput::read deserializes an unverified spendability claim, letting forged bytes report unreceivable funds — ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
Analogous to `MarketRegistry._revokeStakeholderViaDelegation`, which performed a privileged state change while the signature check was commented out, `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs` constructs a "spendable output" record from raw bytes while omitting the ownership/tweak verification that the only legitimate producer (`Scanner`) performs. Any party able to feed bytes into `ReceivedOutput::read` can fabricate a `ReceivedOutput` with an arbitrary `offset`, `TxOut`, and `OutPoint`, causing the wallet layer to report funds as received that are not actually spendable by the threshold key.

### Finding Description
`ReceivedOutput` claims: "this `output` at `outpoint` is spendable by the scanner's key after applying `offset`" (`networks/bitcoin/src/wallet/mod.rs:88-97`). The only verified constructor is `Scanner::scan_transaction`, which matches `output.script_pubkey` against the map built by `register_offset`, where each registered script is provably `p2tr(key + offset*G)` with even Y (`mod.rs:180-214`).

`ReceivedOutput::read` performs none of this. It reads a scalar via `Secp256k1::read_F`, consensus-decodes a `TxOut` and an `OutPoint`, and returns the triple unconditionally (`mod.rs:122-134`). There is no check that `p2tr_script_buf(key + offset*G) == output.script_pubkey`, nor that the `outpoint` exists or commits to `output`. The verification step — the analog of the missing `tellerAS.revokeByDelegation` signature check — is simply absent.

The deserialization surface also under-validates in a second way: `BufReader::with_capacity(0, r)` is created over the shared reader and `TxOut`/`OutPoint` are decoded from it, but nothing asserts the buffer was fully consumed per field, so a `TxOut` encoding can be crafted to shift the `OutPoint` boundary. The primary defect, however, is the missing spendability proof.

### Impact Explanation
A `ReceivedOutput` produced by `read` is consumed downstream as a spendable UTXO (value via `value()`, spending via `send.rs` which applies `offset` to `ThresholdKeys`). A forged blob yields:

- Funds reported received that are not spendable: arbitrary `script_pubkey`/`value`/`outpoint` combinations are accepted with a meaningless `offset`, so balance accounting credits outputs the multisig cannot sign for (or that don't exist on-chain).
- If an untrusted `offset` is mixed into `ThresholdKeys::offset` during a spend (`send.rs` signs after `tweak_keys`/`offset`), an attacker choosing the offset influences the effective signing key, enabling rogue-key-style attacks on the aggregated signature for inputs that *are* real.

### Likelihood Explanation
Reachability depends on an integration feeding untrusted bytes into `ReceivedOutput::read` (e.g., receiving serialized outputs from a peer/coordinator rather than scanning locally — the precise analog of MarketRegistry's externally-callable delegated revocation). Within the in-scope rules, untrusted bytes to `ReceivedOutput::read` are an accepted attack surface, and no authentication of the blob occurs anywhere in the function. Confirmed directly from the source; no speculative claims needed.

### Recommendation
Either make `ReceivedOutput` unconstructible except via `Scanner` (remove `read` or gate it), or have `read` take the scanner's base `key` and verify `p2tr_script_buf(key + offset*G) == output.script_pubkey`, returning an error otherwise. Additionally, reject decodes where `BufReader` retains undecoded bytes.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs
// ReceivedOutput::read (lines 122-134) accepts:
let mut bytes = vec![];
bytes.extend(Scalar::ONE.to_bytes());            // arbitrary offset
bytes.extend(serialize(&TxOut {                   // arbitrary output we don't control
  value: Amount::from_sat(1_000_000),
  script_pubkey: victim_script,                   // not p2tr(key + 1*G)
}));
bytes.extend(serialize(&OutPoint::null()));       // nonexistent outpoint
let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
// forged.value() == 1_000_000, reported as spendable, yet key + 1*G
// does not authorize victim_script and OutPoint::null() doesn't exist.
```
Compared with `Scanner::scan_transaction` (lines 199-214), which only emits a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` hits — a check `read` omits entirely.

Caveat I could not fully verify within the available iterations: whether any in-scope consumer pipes untrusted bytes into `ReceivedOutput::read` end-to-end (e.g., `send.rs` flows or coordinator sync). The defect in `read` itself — the omitted verification — is confirmed; the severity assumes the untrusted-bytes reachability the scope rules grant for this API.
