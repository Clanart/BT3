## Analysis

I found a strong analog to the auction bug's core pattern (a security-relevant decision computed from a value at time T, then acted upon at time T+Δ against a *different* re-derived value, with no re-validation gate) in GitHub Desktop's partial-commit staging path.

### Title
Stale line-index diff selection applied to a freshly re-fetched working directory diff can silently stage/commit content the user never selected - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user partially stages a file (selecting individual lines/hunks in the Changes view), Desktop stores the selection as an index-based bitset (`DiffSelection`) tied to line offsets of the diff that was rendered in the UI. At commit time, `applyPatchToIndex` does **not** reuse that already-rendered diff. It re-invokes `getWorkingDirectoryDiff` to fetch a brand-new diff from disk and then applies the old, offset-based selection to this new diff via `formatPatch`. If the file's on-disk content differs between "diff rendered to user" and "diff fetched for staging" (e.g. changed by an external process, editor auto-format-on-save, background build/watch tooling, or any writer racing with the commit), the line offsets no longer correspond to the same content the user reviewed and selected.

### Finding Description
- The UI computes a diff for display via `updateChangesWorkingDirectoryDiff` in `app/src/lib/stores/app-store.ts` (calls `getWorkingDirectoryDiff`), and builds a `DiffSelection` bit-vector indexed by `hunk.unifiedDiffStart`/absolute line index of *that* diff. [1](#0-0) 
- `_commitIncludedChanges` passes the `WorkingDirectoryFileChange` objects (which carry that stale `selection`) straight to `createCommit` → `stageFiles` → `applyPatchToIndex`. [2](#0-1) [3](#0-2) 
- `applyPatchToIndex` re-fetches the diff independently, right before generating the patch that is `git apply --cached`'d into the index: [4](#0-3) 
- `formatPatch` blindly trusts `file.selection.isSelected(absoluteIndex)` against the **new** diff's line indices, with no check that the diff content/hash matches what generated the selection: [5](#0-4) 

The existing guard that *does* exist for this exact class of problem — re-checking state before/after an async diff load — is only applied to the read path (`updateChangesWorkingDirectoryDiff`, and similarly `_changeFileSelection` / `updateChangesStashDiff`), which compare `stateBeforeLoad` vs `stateAfterLoad` before committing UI state: [6](#0-5) [7](#0-6) 
No equivalent check exists on the **commit/staging path** — there is no verification that the diff used to build `file.selection` is still the diff being staged.

### Impact Explanation
This breaks the invariant that "what the user visually selected in the diff view is exactly what gets committed." Because `formatPatch` maps the selection bit-vector onto whatever hunks/line-count the newly fetched diff happens to have, a content change between render-time and commit-time causes:
- **Silent corruption of what the user commits** — lines the user explicitly deselected (e.g. a stray secret/debug line, or unfinished code) could be included in the resulting commit, or lines the user intended to include could be silently dropped, with the UI showing no indication that this happened, since the file's checked/rendered diff is not the one that produced the final patch.
- Because Desktop's partial-commit UX is specifically marketed as a security/review control ("selectively stage only what you reviewed"), any divergence directly undermines the tool's core commit-review guarantee, matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
This is a genuine TOCTOU: `stageFiles`/`applyPatchToIndex` runs asynchronously after the user clicks "commit," and any writer to the working tree in that window (build watcher, formatter-on-save extension, linter auto-fix, or another git-integrated tool) changes hunk boundaries and shifts absolute line indices used by `DiffSelection`. The likelihood is bounded by needing *some* concurrent writer to the file during the commit window — this is a realistic condition for developers using file watchers/auto-formatters/IDEs alongside Desktop, but it is **not** a purely remote/repo-content-only trigger (I could not identify a way for a hostile git remote, hook, or `.gitattributes` filter to reliably force this race, since Desktop always passes `--no-ext-diff` in `getWorkingDirectoryDiff`, which would suppress attacker-supplied external diff filters as a forcing function). This is the main uncertainty in this analog: I was not able to confirm a purely "attacker controls the cloned repo" trigger without an additional local/concurrent-process assumption, so the "unprivileged, repo-content-only" bar from the prompt is only partially met.

### Recommendation
- Before applying `file.selection` in `applyPatchToIndex`, re-verify that the diff fetched for staging matches the diff that was current when the selection was made (e.g., compare a content hash/blob OID or the raw diff text captured at selection time) and abort/refresh the selection if it has changed, mirroring the `stateBeforeLoad`/`stateAfterLoad` reconciliation pattern already used in `app-store.ts` for the read path.
- Alternatively, thread the exact `IDiff` object used to build the selection through to `stageFiles`/`applyPatchToIndex` instead of re-fetching it, eliminating the possibility of hunk/line-index drift entirely.

### Proof of Concept
Conceptual reproduction (requires a concurrent writer, not yet confirmed as remotely triggerable):
1. Open a modified file in Desktop's Changes view; Desktop renders diff D1 and the user selects only specific lines (building `DiffSelection` indexed against D1).
2. Before clicking "Commit," a background process (formatter/build watcher already running on the developer's machine) rewrites the file, changing hunk boundaries/line counts.
3. User clicks "Commit." `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches diff D2 (`getWorkingDirectoryDiff`) and applies the D1-indexed `file.selection` to D2 via `formatPatch`.
4. The resulting patch (and therefore the commit) includes/excludes different lines than what the user saw and selected, with no warning shown. [8](#0-7) [9](#0-8)

```typescript
export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })
```
