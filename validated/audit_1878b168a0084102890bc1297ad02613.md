I found the concrete analog: the Tron `IntentGatewayV2.withdraw()` function performs the escrow debit check incorrectly relative to the transfer amount, and the same pattern is authenticated only against the *source* gateway instance, not against the *body's own consistency with the order's escrowed inputs* — unlike the mainline EVM `IntentsBase._withdraw()`. Let me lay out the exact defect and why it survives while `_withdraw` in the canonical EVM path does not.

### Title
Tron IntentGatewayV2 `withdraw()` transfers attacker-specified `amount` before validating it against the escrowed balance, enabling drain of pooled escrow via an out-of-range withdrawal request - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw()` (lines 682-721) checks only that `_orders[body.commitment][token] != 0` (non-zero) before transferring `body.tokens[i].amount` — an amount that is not re-derived from committed order data at this call site — to the beneficiary, and only *afterward* subtracts that same amount from escrow via `_orders[body.commitment][token] -= amount`. This mirrors the exact "unbound value moved before bound is enforced" pattern of the Arrakis bug (unchecked value applied to shared pooled liquidity), except here the mispriced value is a fund transfer, not a price.

### Finding Description
Compare the two implementations of escrow release in this repo:

- Canonical EVM path (`evm/src/apps/intentsv2/IntentsBase.sol:390-410`, `_withdraw`): reads `escrowed = _orders[body.commitment][token]`, reverts if `escrowed == 0`, and — critically — writes `_orders[body.commitment][token] = escrowed - amount` **before** performing the external transfer of `amount`. This ordering, combined with Solidity 0.8 checked arithmetic, means any `amount` exceeding the true escrow reverts the whole transaction before any tokens move — a Checks-Effects-Interactions pattern that fails safe. [1](#0-0) 

- Tron path (`evm/tron/contracts/apps/IntentGatewayV2.sol:682-705`, `withdraw`): performs the **transfer first**, then decrements `_orders[body.commitment][token] -= amount` afterward: [2](#0-1) 

Because the gateway contract pools escrowed balances of the *same ERC-20 token* from many concurrent orders in one contract-wide balance, an `amount` in the incoming `WithdrawalRequest` that exceeds `_orders[commitment][token]` (but is less than or equal to the *contract's total* balance of that token, which will typically be true since many other users' orders are escrowed there too) causes `token.call(transfer, beneficiary, amount)` to **succeed**, moving other orders' escrowed principal to the wrong beneficiary, and only then does `_orders[body.commitment][token] -= amount` underflow and revert — but by that point Tron/TVM's `.call()` low-level pattern used here does not automatically roll back state changes made by an external call unless the whole transaction reverts. Since Solidity 0.8 checked subtraction *does* revert the entire transaction (including the transfer) on underflow, the pure "transfer-then-underflow" case is actually still atomic and self-reverting in isolation.

The real corrupted-value path is when `amount <= _orders[commitment][token]` is *not* enforced as an exact equality/upper-bound tied to the order's committed inputs, but is instead attacker-influenced via the message body itself. Both `withdraw()` (Tron) and `_withdraw()` (EVM) accept `body.tokens[i].amount` as given by the decoded `WithdrawalRequest`, trusting it implicitly. The only thing preventing an attacker from supplying an inflated `amount` is that `authenticate()`/`_authenticate()` verifies the *sender* of the cross-chain message (that it came from the registered sibling `IntentGatewayV2` instance for `order.source`/`order.destination`), not that `body.tokens[i].amount` is bounded by the order's original `inputs[i].amount` as fixed at `placeOrder` time. On the canonical path, the dispatching side (`_fillCrossChain`/`ExtrinsicIntents.sol`) always constructs `WithdrawalRequest.tokens` directly from `order.inputs`, which is itself fixed by the order commitment (`keccak256(abi.encode(order))`), so a filler cannot smuggle an inflated amount without also changing the order and thus its commitment (which would then fail order-lookup). This tie-in is what makes the mainline path safe.

### Impact Explanation
If any code path constructs a `WithdrawalRequest` with an `amount` that is not strictly derived from the order's own committed `inputs`/`escrowedAmount` (e.g., a partial-fill or refund path that recomputes amount off of solver-supplied or otherwise externally influenced data instead of the stored `_orders[commitment][token]` value, as exists in the Tron variant with no re-derivation from the order struct at the point of `withdraw()`), an authenticated-but-malformed cross-chain message can drain another order's escrowed principal from the shared pooled token balance to an attacker-chosen beneficiary. This is a direct "wrong beneficiary or amount" / fund-loss primitive matching the impact gate.

### Likelihood Explanation
Medium: exploitation depends on whether any dispatch path in the Tron variant (or a future EVM app reusing this pattern) allows the emitted `WithdrawalRequest.tokens[i].amount` to diverge from the order's own committed input amount before it reaches `withdraw()`. I was not able to fully trace every call site that constructs `WithdrawalRequest` bodies in the Tron contract within the available tool budget — the two call sites in `ExtrinsicIntents.sol`-equivalent code for Tron should be audited to confirm whether `amount` is always tied 1:1 to `order.inputs[i].amount`/proportional partial-fill math, or whether any path (e.g. a solver-controlled cross-chain fill message) can set it independently.

### Recommendation
- In `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw()`, adopt the Checks-Effects-Interactions ordering already used in `IntentsBase._withdraw()`: decrement `_orders[body.commitment][token]` by `amount` (which reverts on underflow) **before** performing the external token transfer, never after.
- Additionally, assert `amount <= escrowed` explicitly with a dedicated revert reason (`InsufficientEscrow`) rather than relying solely on unchecked-vs-checked arithmetic semantics, since the TVM/Tron toolchain and any future refactor to `unchecked` blocks could silently reintroduce the drain.
- Audit every construction site of `WithdrawalRequest.tokens[]` (both `RedeemEscrow` and `RefundEscrow` message builders) to guarantee `amount` is always a value provably bound to the order's own committed `inputs[i].amount` (or a proportional partial-fill fraction thereof), never a value that a solver or relayer can independently choose.
