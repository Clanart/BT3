### Title
Payout tx `OP_RETURN` operator attribution is unauthenticated, allowing any unprivileged party to credit an arbitrary operator with a payout it never funded - ([File: core/src/verifier.rs])

### Summary

### Finding Description
The bridge determines which operator "fronted" a withdrawal purely from a self-declared, unsigned `OP_RETURN` output embedded in the on-chain payout transaction, with no cryptographic binding to the party who actually funded the payout. `create_payout_txhandler` appends the operator's x-only pubkey as plain `OP_RETURN` data, unsigned and not committed to by the user's presigned input signature (the user only signs the input and their own payout output via `SinglePlusAnyoneCanPay`, per `withdraw()`'s sighash check): [1](#0-0) 

Any party — not necessarily the operator whose key is embedded — can supply the extra funding inputs via their own wallet, sign, and broadcast this transaction, since only the withdrawal input and user output are constrained by the user's ANYONECANPAY signature; the `OP_RETURN` byte string is entirely attacker-controlled and never re-validated against who actually paid.

`update_finalized_payouts` then reads this unauthenticated `OP_RETURN` field directly off the chain and writes it into the DB as the "payer" of the withdrawal, with no check that the embedded operator is the one whose wallet actually funded the transaction: [2](#0-1) 

This value is persisted via `update_payout_txs_and_payer_operator_xonly_pk`: [3](#0-2) 

The operator's own `PayoutCheckerTask` polls for withdrawals credited to its own key and, upon finding one, unconditionally proceeds through the reimbursement pipeline (`handle_finalized_payout`, `end_round`, `mark_payout_handled`) with no re-verification that this operator itself actually broadcast/funded the payout transaction: [4](#0-3) 

Later, `validate_payer_is_operator` (used by `get_reimbursement_txs`) and `is_kickoff_malicious` only check that the DB-recorded `payer_xonly_pk` equals `self.signer.xonly_public_key` — i.e., they check consistency with the DB record, not that the credited operator was the true funder of the payout: [5](#0-4) [6](#0-5) 

The equality that should hold is: `operator credited as payer == operator whose funds actually left their wallet to pay the user`. Because the `OP_RETURN` is unsigned, unprivileged data, this binding is broken: **any unprivileged party who fully funds the withdrawal input/output from their own wallet can write an arbitrary registered operator's x-only pubkey into `OP_RETURN`**, making that operator the recorded "payer" even though it never called `withdraw()`, never ran `is_profitable`, and never spent its own funds.

### Impact Explanation
Once credited, the named operator's own automation (`PayoutCheckerTask`) will automatically walk the full reimbursement path (kickoff → challenge-timeout → ready-to-reimburse → reimburse) and ultimately receive the `move_to_vault` UTXO's BTC via `create_reimburse_txhandler`, even though that operator never fronted the withdrawal: [7](#0-6) 

This is a direct instance of the Critical class "an operator reimbursed for a payout it never funded." It also completely bypasses the operator's own `is_profitable` safety check that the legitimate `withdraw()` RPC enforces before an operator agrees to front a withdrawal: [8](#0-7) 

Beyond misattributed reimbursement, this also forces the targeted operator into consuming a kickoff/round slot and entering the challenge-response window involuntarily, without their consent or awareness.

### Likelihood Explanation
The attack requires no privileged role: the attacker needs only enough BTC to cover the difference between the user's input UTXO and the required payout amount (`withdrawal_diff`) plus fees — the same amount a legitimate operator would need to front the payout. The `OP_RETURN` output is not covered by the user's `SinglePlusAnyoneCanPay` signature and is not otherwise authenticated anywhere in the verifier or bridge-circuit path (`get_first_op_return_output` / `parse_op_return_data` simply trust whatever bytes are present). Any operator running the automated `PayoutCheckerTask` will pick up such a credited payout without further checks, so exploitation is straightforward and reliably reproducible.

### Recommendation
Do not treat the `OP_RETURN` operator field as authoritative proof of who funded the payout. Either:
1. Require the credited operator to co-sign or otherwise cryptographically commit to the payout transaction (e.g., via a taproot key-path signature from the operator over the full transaction, not just an unsigned data push), so that the `OP_RETURN` claim cannot be forged by a third party; or
2. Before entering the reimbursement flow, have the operator's `PayoutCheckerTask`/`handle_finalized_payout` independently verify that the additional funding inputs of the payout transaction actually originate from that operator's own wallet/UTXO set (e.g., checking against operator-controlled UTXOs used during `fund_raw_transaction`), rejecting the payout as "not mine" if the funding source cannot be attributed to the operator.

### Proof of Concept
1. Citrea emits a withdrawal request for `withdrawal_utxo` (user-controlled UTXO) with a valid `SinglePlusAnyoneCanPay` user signature over a fixed output (`out_script_pubkey`, `out_amount`), as accepted in `Operator::withdraw` (`core/src/operator.rs:560-637`).
2. Instead of calling the `withdraw()` gRPC on the target operator, an unprivileged attacker independently builds the same `payout_tx` structure (`create_payout_txhandler`, `core/src/builder/transaction/operator_reimburse.rs:407-436`): input = the withdrawal UTXO with the valid user signature, output = the required user payout, and an `OP_RETURN` output containing the x-only pubkey of a victim operator `X` (who never agreed to this withdrawal).
3. The attacker funds the transaction's fee/difference from their own wallet, signs their own inputs, and broadcasts it.
4. Once finalized, `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) parses the `OP_RETURN` and records operator `X` as `payout_payer_operator_xonly_pk` in the `withdrawals` table.
5. Operator `X`'s `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) picks up the "unhandled payout" for its own key, calls `handle_finalized_payout`, `end_round`, and `mark_payout_handled`.
6. Operator `X` proceeds through kickoff/round/reimburse and ultimately receives the `move_to_vault` UTXO funds via `create_reimburse_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:341-384`) — reimbursement for a payout `X` never funded, bypassing `is_profitable` and `X`'s own consent entirely.

pub fn create_reimburse_txhandler(
    move_txhandler: &TxHandler,
    round_txhandler: &TxHandler,
    kickoff_txhandler: &TxHandler,
    kickoff_idx: usize,
    paramset: &'static ProtocolParamset,
    operator_reimbursement_address: &bitcoin::Address,
) -> Result<TxHandler, BridgeError> {
    let builder = TxHandlerBuilder::new(TransactionType::Reimburse)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::Reimburse1,
            move_txhandler.get_spendable_output(UtxoVout::DepositInMove)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::Reimburse2,
            kickoff_txhandler.get_spendable_output(UtxoVout::ReimburseInKickoff)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::OperatorSighashDefault,
            round_txhandler.get_spendable_output(UtxoVout::ReimburseInRound(
                kickoff_idx,
                paramset.num_kickoffs_per_round,
            ))?,
            builder::script::SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        );

    Ok(builder
        .add_output(UnspentTxOut::from_partial(TxOut {
            value: move_txhandler
                .get_spendable_output(UtxoVout::DepositInMove)?
                .get_prevout()
                .value,
            script_pubkey: operator_reimbursement_address.script_pubkey(),
        }))
        .add_output(UnspentTxOut::from_partial(
            builder::transaction::anchor_output(paramset.anchor_amount()),
        ))
        .finalize())

            DEFAULT_SEQUENCE,

        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

    /// Checks if the withdrawal amount is within the acceptable range.
    fn is_profitable(
        input_amount: Amount,
        withdrawal_amount: Amount,
        bridge_amount_sats: Amount,
        operator_withdrawal_fee_sats: Amount,
    ) -> bool {
        // Use checked_sub to safely handle potential underflow
        let withdrawal_diff = match withdrawal_amount
            .to_sat()
            .checked_sub(input_amount.to_sat())
        {
            Some(diff) => Amount::from_sat(diff),
            None => {
                // input amount is greater than withdrawal amount, so it's profitable but doesn't make sense
                tracing::warn!(
                    "Some user gave more amount than the withdrawal amount as input for withdrawal"
                );
                return true;
            }
        };

        if withdrawal_diff > bridge_amount_sats {
            return false;
        }

        // Calculate net profit after the withdrawal using checked_sub to prevent panic
        let net_profit = match bridge_amount_sats.checked_sub(withdrawal_diff) {
            Some(profit) => profit,
            None => return false, // If underflow occurs, it's not profitable
        };

        // Net profit must be bigger than withdrawal fee.
        // net profit doesn't take into account the fees, but operator_withdrawal_fee_sats should
        net_profit >= operator_withdrawal_fee_sats
    }
