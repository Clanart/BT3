### Title
Double-application of bank balance-change events onto EVM StateDB during nested/recursive precompile calls corrupts account balances - (File: `precompiles/common/precompile.go`, `precompiles/common/balance_handler.go`)

### Summary
The Caviar `Pair.sol` bug class is a check-effects-interactions violation where an external call (ERC777 hook) lets an attacker re-enter before internal reserve accounting is updated, letting stale/duplicated state be exploited across nested calls. Cosmos EVM has a structurally identical bug in how `BalanceHandler` reconciles bank-module events into the EVM `StateDB` around stateful-precompile execution: it slices the shared `ctx.EventManager()` event log using a length recorded *before* the precompile's native action runs, but does not account for the fact that a nested/recursive precompile invocation triggered from within that action shares the same growing event log and independently commits its own slice to `StateDB` first. This causes the outer call to replay (double-apply) the same bank events that a nested precompile call already applied.

### Finding Description
Every stateful precompile (`bank`, `staking`, `distribution`, `gov`, `slashing`, `erc20`, `ics20`, `werc20`) embeds `common.Precompile` and executes via `RunNativeAction` → `runNativeAction`: [1](#0-0) 

For each precompile call, a fresh local `*BalanceHandler` is created and bracketed around the native action:
1. `BeforeBalanceChange(ctx)` records `prevEventsLen = len(ctx.EventManager().Events())`.
2. `action(ctx)` executes the precompile logic (which may itself trigger further EVM calls, e.g. `CallEVMWithData`, that recurse into another stateful precompile or contract).
3. `AfterBalanceChange(ctx, stateDB)` re-reads `ctx.EventManager().Events()` and applies **every** `coin_spent`/`coin_received`/`fractional_balance_change` event from `events[prevEventsLen:]` to `stateDB.AddBalance`/`SubBalance`: [2](#0-1) 

Because the `sdk.Context`'s `EventManager` is shared/propagated across nested cache contexts (this is normal Cosmos SDK behavior, needed so nested-call events bubble up to the tx receipt), a nested precompile call's own `BeforeBalanceChange`/`AfterBalanceChange` pair operates on the *same monotonically growing* event slice as the outer call. The nested (inner) call finishes first and applies `events[M:]` to `stateDB`. When execution returns to the outer action and eventually reaches the outer's own `AfterBalanceChange`, it slices `events[N:]` where `N < M`, which **still includes** the events the inner call already consumed and applied to `stateDB`. Those events get applied a second time, inflating (or, depending on ordering, corrupting) the `StateDB` balances that do not match the true bank-module ledger balances.

This exact bug is already reproduced by an in-repo integration test that documents it as "the balance handler bug": [3](#0-2) [4](#0-3) 

The test uses a debug-only precompile (`evmd/tests/testdata/debug/debug.go`) to force recursive precompile self-calls via `CallEVMWithData`, but the vulnerable code path (`runNativeAction`/`BalanceHandler`) is identical, unconditional production code used by every real stateful precompile shipped in the chain (bank, staking, distribution, gov, slashing, erc20, ics20, werc20). Any contract flow where a stateful precompile call synchronously triggers a nested call into another (or the same) balance-handler-backed precompile — e.g. a contract's fallback/hook invoked mid-precompile-call that itself calls the `bank`, `staking`, `distribution`, or `erc20` precompile — hits this same shared-event-log replay path. The existing `StakingReverter.sol` / `Reverter.sol` test-utility contracts in the repo demonstrate that nested/re-entrant precompile calls via contract self-calls are a reachable, unprivileged pattern already exercised by the test suite: [5](#0-4) [6](#0-5) 

### Impact Explanation
The bug causes `StateDB` (the EVM-visible account balance) to diverge from the true `x/bank` ledger balance by double-crediting/double-debiting the native-denom balance of accounts involved in nested precompile-triggered coin movements. Since `StateDB` balances are what the EVM uses for subsequent transfers/`CALL` value checks within the same transaction/block, an attacker who can force this nested-call pattern (e.g., via a contract that receives value in the middle of a precompile call and re-enters another balance-affecting precompile) can inflate their EVM-visible balance beyond what is actually escrowed in the bank module — a critical, unauthorized duplication of spendable value and an EVM/bank accounting divergence. This matches the in-scope "Critical unauthorized minting/duplication/irreversible accounting corruption of spendable user value across native balances ... precompile-mediated assets" impact.

### Likelihood Explanation
Reachability requires only an ordinary (unprivileged) EVM transaction from a smart contract that: (1) calls a stateful precompile that emits bank events, and (2) within that precompile's execution, synchronously triggers another balance-handler-backed precompile call (directly, or via a callback into a user contract that itself calls a precompile). This is a normal, permission-less usage pattern (any of `bank`, `staking`, `distribution`, `gov`, `erc20`, `ics20`, `werc20` can be composed by a contract), and the repository's own test suite (`balance_handler_test.go`, `StakingReverter.sol`, `Reverter.sol`, `ERC20RecursiveNonRevertingPrecompileCall.sol`) already exercises this exact recursive-precompile-call shape, indicating it is a realistic and already-known-triggerable condition.

### Recommendation
`BalanceHandler` bookkeeping must not be shared/overlapping across nested precompile invocations operating on the same `EventManager`. Options:
- Track a globally unique, monotonically-advancing cursor on the `StateDB`/journal itself (not a per-call local variable) so that once a slice of events has been consumed by any (nested) `AfterBalanceChange`, an outer call cannot re-consume it.
- Alternatively, snapshot and truncate/mark consumed events immediately after they are applied, so nested and outer calls partition the event log disjointly.
- Add an invariant check (e.g., compare cumulative `StateDB` native-balance deltas against `x/bank` `SendCoins`/`MintCoins`/`BurnCoins` deltas for the same execution) and fail the precompile call if they diverge, similar to the existing `ErrBalanceInvariance` checks already used in `x/erc20/keeper/msg_server.go`.
- Add integration tests covering nested calls across *different* real precompiles (not just the debug precompile) to confirm the fix holds for production precompile compositions.

### Proof of Concept
The existing repository test already demonstrates the root cause end-to-end: [7](#0-6) 
It deploys a caller contract that invokes the debug precompile's `callback` method, which internally performs a nested `CallEVMWithData` back into the same precompile address: [8](#0-7) 
Each nested invocation creates its own local `BalanceHandler` (via `precompiles/common/precompile.go:99-106`) that races/overlaps on the same `ctx.EventManager()` event slice, and the test's own comment states it "demonstrates the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB" — confirming the finding. To produce a Critical, fund-impacting instance of this bug against a *production* precompile (not the debug one), a background engineer should extend this test to use two real balance-handler-backed precompiles (e.g., `staking`/`distribution` or `bank`/`erc20`) in a nested call chain via a Solidity contract analogous to `StakingReverter.sol`/`ERC20RecursiveNonRevertingPrecompileCall.sol`, and assert that the resulting EVM `StateDB` balance for the attacker/contract address exceeds (or otherwise diverges from) the corresponding `x/bank` ledger balance after the transaction commits.

// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

// AfterBalanceChange processes the recorded events and updates the stateDB accordingly.
// It handles the bank events for coin spent and coin received, updating the balances
// of the spender and receiver addresses respectively.
//
// NOTES: Balance change events involving BlockedAddresses are bypassed.
// Native balances are handled separately to prevent cases where a bank coin transfer
// initiated by a precompile is unintentionally overwritten by balance changes from within a contract.

// Typically, accounts registered as BlockedAddresses in app.go—such as module accounts—are not expected to receive coins.
// However, in modules like precisebank, it is common to borrow and repay integer balances
// from the module account to support fractional balance handling.
//
// As a result, even if a module account is marked as a BlockedAddress, a keeper-level SendCoins operation
// can emit an x/bank event in which the module account appears as a spender or receiver.
// If such events are parsed and used to invoke StateDB.AddBalance or StateDB.SubBalance, authorization errors can occur.
//
// To prevent this, balance changes from events involving blocked addresses are not applied to the StateDB.
// Instead, the state changes resulting from the precompile call are applied directly via the MultiStore.
func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()
}
