### Title
Hand-rolled `extract_frontmatter` splits on all `---` occurrences, silently downgrading `action: block` rules to `warn` - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter` in `plugins/hookify/core/config_loader.py` uses `content.split('---', 2)` to separate YAML frontmatter from the message body, without any awareness of YAML quoting or escaping. If a rule's `pattern` (or any frontmatter value) contains a literal `---` sequence, the split boundary lands inside the frontmatter block instead of at the intended closing delimiter, truncating the parsed frontmatter before fields like `action: block` are reached. The truncated key/value pairs (including `action: block`) are then absorbed into the message body and never parsed, causing `Rule.from_dict` to fall back to its default `action: 'warn'` [1](#0-0) .

### Finding Description
`load_rules()` globs every `.claude/hookify.*.local.md` file in the current working directory and parses it via `load_rule_file` → `extract_frontmatter` → `Rule.from_dict`, with no origin/trust check on the file content [2](#0-1) . `extract_frontmatter` determines the frontmatter block using `parts = content.split('---', 2)`, taking `parts[1]` as the raw frontmatter text and `parts[2]` as the message [3](#0-2) . This naive split treats **every** literal `---` in the file as a delimiter, not just the intended frontmatter fences.

If an attacker-controlled `.claude/hookify.*.local.md` file (e.g., committed into a cloned repository, since these files are only gitignored by convention, not blocked from being tracked and read) contains a `pattern:` value with an embedded `---` (a very plausible pattern for matching shell heredocs, markdown horizontal rules, or `git diff` separators, e.g. `pattern: "---evil---"`), the second `---` occurrence inside that value is treated as the frontmatter terminator. Everything after it — including a subsequent `action: block` line and even the real closing `---` — gets shoved into `parts[2]`, the message body, and is never parsed into the `frontmatter` dict. `Rule.from_dict` then reads `frontmatter.get('action', 'warn')`, defaulting to `'warn'` [4](#0-3) .

`RuleEngine.evaluate_rules` treats only rules with `rule.action == 'block'` as blocking; everything else becomes a non-blocking warning that still allows the tool call to execute [5](#0-4) . Both `pretooluse.py` and `posttooluse.py` invoke this pipeline directly on `Bash`/`Edit`/`Write`/`MultiEdit`/`Stop` events with no additional validation [6](#0-5) . There is no schema validation, no proper YAML parser, and no sanity check that the parsed `Rule` matches the visible on-disk content — a human or the `/hookify` command reviewing the file would see `action: block` in plain text, but the parsed `Rule` object silently carries `action: 'warn'`.

The `/hookify` command itself documents exactly this file format (`pattern: {regex pattern}` / `action: {warn|block}`) and instructs the assistant to write such files based on conversation analysis or explicit `$ARGUMENTS`, meaning a prompt-injection via repo content (e.g., an issue, comment, or committed file suggesting a "helpful" blocking pattern containing `---`) could cause the assistant itself to author a file that looks correct but parses incorrectly [7](#0-6) .

### Impact Explanation
This breaks the invariant that a `block` rule must always be enforced as blocking. A rule authored (or reviewed) to read `action: block` — intended to prevent dangerous `Bash` commands, sensitive file edits, or premature `Stop` — can silently execute as a non-blocking warning due to a parser quirk, with no error, exception, or warning surfaced to the user (`load_rule_file` only warns on missing frontmatter or exceptions, not on this silent truncation). This matches "Security-control bypass that silently disables or routes around blocking, review, or permission boundaries," since the dangerous tool invocation (e.g., `rm -rf`, writing to `.env`, or `curl | bash`) proceeds despite an apparently active deny rule.

### Likelihood Explanation
Preconditions: hookify plugin enabled with `PreToolUse`/`PostToolUse`/`Stop` hooks wired up, and a `.claude/hookify.*.local.md` file present with a `pattern` (or other frontmatter value) containing a literal `---` sequence positioned before an `action: block` line. Such files can be introduced via ordinary repository content (checked-in `.claude/` rule files are not prevented from being tracked, only conventionally gitignored) or generated by the `/hookify` command itself when patterns are derived from conversation/repo content containing `---`. No special privilege is needed — only that the victim clones/opens the repo and hookify's hook scripts run. The bug is deterministic and easily reproduced with a crafted pattern string.

### Recommendation
Replace the hand-rolled `content.split('---', 2)` frontmatter extraction with a delimiter-aware parser that only recognizes `---` on its own line (e.g., `^---\s*$` at line start using `re.MULTILINE`, splitting only at the first two such standalone-line matches) rather than any substring occurrence, and ideally use a real YAML parser (e.g., PyYAML `safe_load`) for the frontmatter body instead of the custom line-based parser in `extract_frontmatter`. Additionally, add an integrity check that logs/rejects a rule file if the raw text plainly contains `action: block` but the parsed `Rule.action != 'block'`, so drift between visible file content and parsed configuration is never silent.

### Proof of Concept
```python
# test_frontmatter_delimiter_truncation.py
from hookify.core.config_loader import extract_frontmatter, Rule

malicious_rule = '''---
name: block-dangerous-heredoc
enabled: true
event: bash
pattern: "cat <<---EOF--- && rm -rf /"
action: block
---

This should BLOCK dangerous heredoc + rm -rf usage.
'''

frontmatter, message = extract_frontmatter(malicious_rule)
rule = Rule.from_dict(frontmatter, message)

# Expected (visible file clearly says action: block):
assert rule.action == 'block', (
    f"Invariant violated: deny rule parsed as non-blocking! "
    f"Got action={rule.action!r}, frontmatter={frontmatter!r}"
)
```
Expected result today: the assertion fails — `frontmatter` does not contain `action`, and `rule.action` resolves to the default `'warn'`, demonstrating that a visibly `block` rule is silently parsed and enforced as a mere warning, allowing the dangerous `Bash` command to execute.

```python
def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)

        except (IOError, OSError, PermissionError) as e:
            # File I/O errors - log and continue
            print(f"Warning: Failed to read {file_path}: {e}", file=sys.stderr)
            continue
        except (ValueError, KeyError, AttributeError, TypeError) as e:
            # Parsing errors - log and continue
            print(f"Warning: Failed to parse {file_path}: {e}", file=sys.stderr)
            continue
```

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)
```
