### Title
Unchecked type assertion on attacker-controlled CosmWasm query response causes panic in `pointer` precompile - (File: precompiles/pointer/pointer.go)

### Summary
The `pointer` precompile's `AddCW20`, `AddCW721`, and `AddCW1155` handlers query an arbitrary, caller-supplied CosmWasm contract address and then perform unchecked Go type assertions (`formattedRes["name"].(string)`, `formattedRes["symbol"].(string)`) on the unmarshalled JSON response, without first verifying the key exists or is of the expected type. This mirrors the CVE-2025-56364 bug class: accessing an "optional"/untyped value without checking its presence/shape before use, leading to a panic reachable from a single externally supplied input.

### Finding Description
`AddCW20` (and the CW721/CW1155 equivalents) accept a `cwAddr` argument fully controlled by the caller, query it via `p.wasmdKeeper.QuerySmart`/`QuerySmartSafe` with `{"token_info":{}}` or `{"contract_info":{}}`, unmarshal the raw JSON into a `map[string]interface{}`, and then do: [1](#0-0) 

If the queried contract's response omits the `name`/`symbol` keys, or returns them as `null`/non-string JSON types (e.g. a number or object), `formattedRes["name"]` yields `nil` and the type assertion `.(string)` panics with `interface conversion: interface {} is nil, not string`. Since `cwAddr` is any address the caller chooses, an unprivileged EVM account can deploy their own minimal CosmWasm contract that responds to the `token_info`/`contract_info` smart query with a malformed payload (missing/invalid `name`/`symbol`), then call `addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer` on the pointer precompile at `0x100b` pointing at that contract. This same unchecked pattern is duplicated across every legacy version of the precompile: [2](#0-1) [3](#0-2) 

### Impact Explanation
During normal block execution (`DeliverTx`/OCC execution paths), this panic is caught by top-level recover handlers in `app.go` (e.g. `ProcessBlock`, `ProcessTxsSynchronousGiga`), which convert it into an `ErrPanic` result instead of crashing the node: [4](#0-3) [5](#0-4) 

However, the same code path is reachable through the public `eth_call`/`eth_estimateGas`/`eth_createAccessList` JSON-RPC surface via `SimulationAPI` in `evmrpc/simulate.go`, which recovers panics only at the top of each RPC handler and converts them to a generic error string rather than propagating a crash: [6](#0-5) 

Given the recover wrappers present at both the block-execution and RPC layers in this codebase, the panic is very likely to be caught and surfaced as a failed transaction / RPC error rather than causing a genuine node crash or consensus halt. I could not find a code path where this panic escapes all recover wrappers to actually crash a default-configuration RPC node or validator process — the impact is most likely limited to a single failed transaction (denial of that specific call) rather than the "crash of default-configuration RPC nodes" threshold required by the validation rules.

### Likelihood Explanation
Trivial to trigger: any user can deploy a CosmWasm contract that replies to `token_info`/`contract_info` queries with a JSON object lacking a `name` or `symbol` field (or with a non-string value), then invoke `addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer` at precompile address `0x100b` pointing to it. No special privileges required.

### Recommendation
Replace the unchecked type assertions with the two-value form and return a proper error instead of panicking, e.g.:
```go
name, ok := formattedRes["name"].(string)
if !ok {
    return nil, 0, fmt.Errorf("contract token_info response missing/invalid name field")
}
```
Apply the same fix for `symbol` across `precompiles/pointer/pointer.go` and all `precompiles/pointer/legacy/vXXX/pointer.go` variants.

### Proof of Concept
1. Deploy a CosmWasm contract whose `QuerySmart` handler for `{"token_info":{}}` returns `{"decimals":6}` (omitting `name`/`symbol`), or returns `{"name":null,"symbol":null,...}`.
2. From any EVM account, call `addCW20Pointer(cwAddr)` on the pointer precompile (`0x100000000000000000000000000000000000100b`) with `cwAddr` set to the deployed contract's bech32 address.
3. Observe `formattedRes["name"].(string)` panics with `interface conversion: interface {} is nil, not string` inside `AddCW20`.
4. Repeat via `eth_call`/`eth_estimateGas` against the same target to observe the RPC-layer panic recovery behavior.

Given the strong recover coverage found at both block-processing and RPC layers, I was **unable to confirm** this reaches the "crash of default-configuration RPC nodes" or any other required High/Critical impact bar in the rules — this should be treated as a low-confidence/uncertain finding pending confirmation of whether any call path to these precompile methods (e.g. via the giga executor or a tracer path) lacks a recover wrapper.
