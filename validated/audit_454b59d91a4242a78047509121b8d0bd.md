### Title
Payout tx OP_RETURN is unauthenticated by the SinglePlusAnyoneCanPay user signature, letting an attacker RBF-replace a genuine payout so `Verifier::is_kickoff_malicious` burns the honest operator's collateral - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` places the operator's x-only pubkey in output 2 (OP_RETURN) of the `payout_tx`, but the user's authorizing signature (`in_signature`, enforced to be `TapSighashType::SinglePlusAnyoneCanPay`) only commits to input 0 and the matching output 0. Anything observing the mempool can reuse that signature/witness to build and RBF-broadcast a competing transaction that keeps output 0 intact but replaces/corrupts the OP_RETURN, causing `Verifier::update_finalized_payouts` to record `None` for the payer, which `Verifier::is_kickoff_malicious` treats as automatically malicious.

### Finding Description
The claimed binding is:
`recorded_operator_xonly_pk (from withdrawals.payout_payer_operator_xonly_pk) == funder_pk (Some(operator A's xonly pk))`

Trace:
- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds `payout_tx` with input 0 = withdrawal UTXO (`SpendPath::KeySpend`), output 0 = user payout, output 1 = anchor, output 2 = `op_return_txout(operator_xonly_pk.serialize())`. [1](#0-0) 
- `Operator::withdraw` verifies the user's signature against `payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)` using `SECP.verify_schnorr`, and the error message explicitly documents the sighash requirement. [2](#0-1) 
- `parse_withdrawal_sig_params` enforces the sighash flag must be `TapSighashType::SinglePlusAnyoneCanPay`. [3](#0-2) 
- `calculate_pubkey_spend_sighash`/Taproot semantics for `SinglePlusAnyoneCanPay` only commit to input 0's own prevout (`Prevouts::One`) and output 0 (the SIGHASH_SINGLE output at the same index as the signed input); outputs 1 (anchor) and 2 (OP_RETURN) are **not** covered by this signature. [4](#0-3) 
- The operator explicitly sends the payout via fee-bumpable/RBF flow: `self.rpc.fund_raw_transaction(...)` with the surrounding comment "send payout tx using RBF". [5](#0-4) 
- Once the operator's payout_tx (or its witness/signature) is visible pre-confirmation, any unprivileged actor can construct a replacement transaction reusing input 0 with the identical witness (a valid signature under ANYONECANPAY is reusable by anyone, not just the signer), preserving output 0 exactly (required by the SINGLE commitment), but substituting output 1/2 arbitrarily — including a corrupted/short OP_RETURN — and add their own fee-paying inputs, then broadcast with a higher fee as a BIP125 replacement.
- On confirmation, `Verifier::update_finalized_payouts` looks for the first OP_RETURN output and tries `parse_op_return_data`; if it fails or the bytes aren't a valid 32-byte x-only key, `operator_xonly_pk` is stored as `None`. [6](#0-5) 
- `Verifier::is_kickoff_malicious` treats a `None` payer pk as an automatic "assume malicious" verdict regardless of who actually authorized/funded the payout. [7](#0-6) 
- This flows into `handle_kickoff`, which fires the `Challenge` transaction against operator A's kickoff, burning A's collateral. [8](#0-7) 

The root cause is that the OP_RETURN output—the sole piece of on-chain data the protocol relies on to attribute a payout to a specific operator—is entirely outside the scope of the only signature (`SinglePlusAnyoneCanPay`) that authorizes spending the withdrawal UTXO. No other guard (`is_deposit_valid`, `is_profitable`, `only_aggregator_and_self`) constrains the shape of outputs 1/2 of the mined transaction; those checks only run at RPC-call time on the operator's *intended* transaction, not on whatever transaction actually gets mined.

### Impact Explanation
If an attacker's replacement transaction (with an unparsable/altered OP_RETURN) gets confirmed instead of the operator's own broadcast, an honest operator who genuinely fronted the withdrawal (same output 0, correct amount/destination) is later flagged as malicious by every verifier for that withdrawal, and a `Challenge`/`Disprove` sequence burns that operator's collateral — squarely the "Critical: an honest operator's collateral burned" impact category. This is repeatable per withdrawal/operator: any payout transaction sitting unconfirmed in the mempool is vulnerable during that window, and the cost to the attacker is only the marginal RBF fee bump, not the withdrawal amount itself (they don't need to fund the payout — they just need to win the confirmation race for the same already-signed input/output 0).

### Likelihood Explanation
- Preconditions match the operator's own code path exactly: `Operator::withdraw` builds the payout with a `SinglePlusAnyoneCanPay`-only-authorized input and sends it via an RBF-enabled `fund_raw_transaction` flow, so RBF replaceability is a design default, not an unusual configuration.
- The attacker cost is only a modest fee bump plus their own dust/funding UTXO; they never need to control the withdrawal amount.
- Feasibility depends on the attacker observing the operator's payout_tx (or its witness) prior to confirmation and mempool relay/RBF policy accepting the replacement (higher absolute fee and feerate per BIP125), both of which are attacker-controlled/standard mempool behavior, matching the question's stated preconditions.
- Repeatable across any withdrawal being fronted by any operator during the confirmation window.

### Recommendation
Bind the operator's identity/OP_RETURN commitment to the transaction using a signature scope that the attacker cannot detach from — e.g., require the user's signature (or an operator co-signature) to cover the OP_RETURN output (use `AllPlusAnyoneCanPay` or add an operator-signed covenant over all outputs), or otherwise attribute payer identity via a channel the attacker cannot rewrite (e.g., have the operator's own presigned/covenant-bound kickoff attest which UTXO+outputs it services, rather than relying purely on a freely replaceable OP_RETURN in an unauthenticated-output payout transaction).

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub fn calculate_pubkey_spend_sighash(
        &self,
        txin_index: usize,
        sighash_type: TapSighashType,
    ) -> Result<TapSighash, BridgeError> {
        let prevouts_vec: Vec<&TxOut> = self
            .txins
            .iter()
            .map(|s| s.get_spendable().get_prevout())
            .collect();
        let mut sighash_cache: SighashCache<&bitcoin::Transaction> =
            SighashCache::new(&self.cached_tx);
        let prevouts = match sighash_type {
            TapSighashType::SinglePlusAnyoneCanPay
            | TapSighashType::AllPlusAnyoneCanPay
            | TapSighashType::NonePlusAnyoneCanPay => {
                bitcoin::sighash::Prevouts::One(txin_index, prevouts_vec[txin_index])
            }
            _ => bitcoin::sighash::Prevouts::All(&prevouts_vec),
        };

        let sig_hash = sighash_cache
            .taproot_key_spend_signature_hash(txin_index, &prevouts, sighash_type)
            .wrap_err("Failed to calculate taproot sighash for key spend")?;
