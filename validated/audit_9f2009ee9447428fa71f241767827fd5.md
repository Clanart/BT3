### Title
Quadratic, unmetered CPU cost in CPI account translation due to per-account linear scan — ([File: program-runtime/src/cpi.rs])

### Summary
`translate_accounts_common` in `program-runtime/src/cpi.rs` performs an `O(n*m)` linear scan (`account_info_keys.iter().position(...)`) for every instruction account in a CPI call, but the CPI's compute-unit charge (`invoke_units`, a fixed `DEFAULT_INVOCATION_COST`) plus the byte-based charge for the account-infos slice do not scale with this quadratic work. This mirrors the reported TangleStaking `_unstake` issue: an expensive per-element loop operation whose true cost is not reflected in what the caller is charged, creating a cheap way to make the runtime do disproportionate CPU work.

### Finding Description
When a program performs a CPI, `cpi_common` (program-runtime/src/cpi.rs:773-840) charges a fixed `invoke_units` cost [1](#0-0) , then calls `S::translate_accounts`, which eventually calls `translate_account_infos` (charges CU proportional to the number of `account_infos` bytes only) [2](#0-1)  and then `translate_accounts_common`.

Inside `translate_accounts_common`, for every entry in `next_instruction_accounts` (the instruction's account metas, which can be as large as the CPI instruction account-meta limit, e.g. 255 per the CU-usage test constants) the code performs a linear `position()` search over `account_info_keys` (the account-infos array, itself up to the CPI account-info limit, e.g. 64 or 255) to find the matching caller account: [3](#0-2) 

This produces `O(instruction_accounts_len * account_infos_len)` pubkey comparisons per single CPI call — potentially tens of thousands of comparisons — yet the only compute charges taken in this path are: (1) the fixed `invoke_units` cost per CPI, and (2) a charge proportional to `account_infos_len` bytes (not to the product of both lengths) [4](#0-3) . The SBF test harness explicitly documents that CPI with 255 account metas and 255 account infos costs a small, roughly fixed number of compute units (~1176 CU) [5](#0-4) , confirming that the CU charge does not scale with the quadratic account-matching work actually performed.

This is directly analogous to the TangleStaking `_unstake` bug: a for-loop containing a costly per-iteration operation (there, a storage write; here, a linear key comparison scan) whose cost is not proportionally billed to the caller, letting an attacker force the runtime to perform much more work than it pays for.

### Impact Explanation
A malicious on-chain program can issue CPI calls with the maximum allowed number of instruction accounts and account-infos repeatedly (nested/looped CPIs within the compute-unit budget for other, cheaper operations) to force validators to execute a disproportionately large number of pubkey comparisons relative to the CU actually deducted. Because this is CPU work rather than metered compute, it constitutes materially underpriced compute: attacker cost (CU consumed) does not match validator cost (CPU cycles spent), enabling a class of compute-DoS/replay-slowdown across the cluster when many such transactions are packed into a block within the true compute budget while performing far more wall-clock work than intended.

### Likelihood Explanation
The path is fully reachable by any unprivileged BPF program via the standard `invoke`/`invoke_signed` syscalls (`SyscallInvokeSignedRust`/`SyscallInvokeSignedC` in `syscalls/src/cpi.rs`), requires no special privileges, and the account/instruction size limits are large enough (up to 255 in the existing test harnesses) to produce a meaningful quadratic blow-up. No malicious snapshot, multiple RPC calls, or validator-role access is needed — a single crafted transaction can trigger it repeatedly within a block.

### Recommendation
Build a hash map (or otherwise index) `account_info_keys` once per CPI call instead of doing a `position()` linear scan per instruction account, reducing the operation to `O(n + m)`. Alternatively, explicitly charge compute units proportional to `instruction_accounts_len * account_infos_len` (or to the actual number of comparisons performed) so that the cost is properly metered if the linear-scan approach is retained.

### Proof of Concept
Not independently executable from static analysis alone; the quadratic cost is demonstrated structurally by the code and by the existing CU-usage regression tests (`TEST_CU_USAGE_MAX` in `programs/sbf/c/src/invoke/invoke.c:969-1006` and `programs/sbf/rust/invoke/src/lib.rs:1614-1647`) which show that scaling both `account_infos_len` and instruction account-meta count to 255 only adds ~61 CU relative to the baseline case, despite the `position()` scan work scaling quadratically with these sizes. A concrete PoC would require instrumenting/benchmarking `translate_accounts_common` with maximal account-info/account-meta counts across repeated CPI calls within a transaction to measure wall-clock CPU time versus CU charged — this was not run as part of this analysis.
