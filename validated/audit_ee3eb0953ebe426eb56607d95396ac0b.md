## Title
Discarding changes follows attacker-planted symlinks to delete/move files outside the repository - (File: `app/src/lib/stores/git-store.ts`)

### Summary
`GitStore.discardChanges()` resolves each changed file's path with a plain `Path.resolve(this.repository.path, file.path)` / `Path.join(this.repository.path, file.path)` and then deletes or trashes it, with no verification that the resolved path actually stays inside the repository. Other, newer code paths in this same codebase (Copilot conflict resolution, `openRepositoryFromUrl`) route every repo-relative path through `resolveWithin()`, which resolves symlinks via `realpath` and rejects any path that escapes the repository root. `discardChanges` never applies that guard, so a symlink committed by an attacker-controlled repository can redirect a "discard" operation to a file anywhere on disk.

### Finding Description
`resolveWithin()` in `app/src/lib/path.ts` was written specifically to defend against "path traversal and symlink escapes (cross-platform)" by calling `realpath` on both the root and the resolved path and checking that the real, symlink-resolved path is still under the real root: [1](#0-0) 

This guard is used when writing AI/Copilot conflict resolutions to disk and when opening a `x-github-client://` deep-link file path: [2](#0-1) [3](#0-2) 

`GitStore.discardChanges`, however, resolves the on-disk path for every file to be trashed/deleted with an unguarded `Path.resolve`/`Path.join`, using `file.path` as reported by `git status` — a value that is entirely determined by the content of the cloned/fetched repository: [4](#0-3) 

Because Node's `fs` "move to trash" / `rm` operations follow symlinks in intermediate path components, if the repository contains a tracked symlinked directory (e.g. `link -> /Users/victim/Documents` or `link -> ../../..`) and the working tree subsequently contains an untracked/modified entry that `git status` reports as `link/some-file`, `Path.resolve(repository.path, 'link/some-file')` produces a path whose parent component is a symlink pointing outside the repository. `discardChanges` sends that resolved path straight to `this.shell.moveItemToTrash(...)` (or `rm(...)` when the "always discard permanently" fallback is engaged), operating on whatever real file the symlink points to — outside the repository root — with no `resolveWithin`-style containment check.

### Impact Explanation
This lets an attacker who controls the contents of a repository the victim clones/fetches (a normal, unprivileged scenario for GitHub Desktop) cause the victim's own "Discard changes"/"Discard this file" action to delete or trash an arbitrary file outside the repository, chosen by the attacker via the symlink target (e.g. files under the user's home directory, `.ssh`, application config, etc.). This is a file-deletion-outside-repo primitive triggered by ordinary Desktop UI actions (discarding changes), matching the required impact class of "file write/delete outside the repo caused by an attacker-controlled cloned/fetched repository."

### Likelihood Explanation
The victim only needs to clone/open the malicious repository, make (or have) any change reported under the symlinked path, and click "Discard changes" — a very common, everyday Desktop workflow. No local/physical access, admin rights, prior malware, or leaked credentials are required, and the codebase itself shows that this exact "symlink escape" scenario is a recognized threat model (it's precisely what `resolveWithin` was built to stop for other flows), but that fix was not applied to `discardChanges`.

### Recommendation
Route every path used in `discardChanges` (for `moveItemToTrash` and the manual `rm` fallback) through `resolveWithin(this.repository.path, file.path)` (and `file.status.oldPath` for renames/copies), refusing to trash/delete when the resolved real path escapes the repository root, mirroring the containment check already used in `copilot-conflict-context.ts` and `dispatcher.ts`.

### Proof of Concept
1. Attacker creates a repository containing a tracked symlink `evil -> ../../../` (or an absolute path such as the victim's home directory) and commits it.
2. Victim clones the repository with GitHub Desktop.
3. Attacker's repository (or a subsequent fetch/pull) introduces a working-directory entry that `git status` reports as `evil/some-file` (e.g., an untracked file placed through the symlink, or a modified tracked file whose path traverses the symlink).
4. Victim selects that file in the Changes list and clicks "Discard changes".
5. `GitStore.discardChanges` computes `Path.resolve(repository.path, 'evil/some-file')`, which resolves through the symlink to a location outside the repository, and calls `this.shell.moveItemToTrash(...)` on it — moving/deleting a file the victim never intended to touch, outside the repository boundary.
