### Title
Flash-lock manipulation of referral boost factor lets attacker capture disproportionate referral reward share - (rewards/ReferralStorage.sol, VLMGP.sol)

### Summary
`ReferralStorage._calBoosted` computes a referrer's boosted reward percentage using `userInfos[_account].factor`, which is derived from `IVLMGP.getUserTotalLocked` at the exact moment `updateTotalFactor` is called, with no time-weighting or minimum lock duration. An attacker can lock a large MGP amount into `VLMGP` immediately before triggering a referee reward claim, causing `trigger()` to compute an inflated `boostesd` value and credit an outsized `refererAmount`, then unlock the principal afterward.

### Finding Description
`trigger()` reads the referrer's boost using a purely instantaneous snapshot: [1](#0-0) 

`_calBoosted` and `updateTotalFactor` use the referrer's *current* locked amount with no historical/time-weighted average and no cooldown/vesting requirement before the factor counts: [2](#0-1) [3](#0-2) 

`updateTotalFactor` is invoked synchronously from `VLMGP._lock` on every `lock`/`lockFor` call, so the factor update and the subsequent referee claim can happen back-to-back in adjacent transactions controlled entirely by the attacker: [4](#0-3) 

The referee's claim path (`multiclaimFor` → `_multiClaim`) calls `trigger(_user, totalReward)` using the referrer's *current* boost at the moment of the claim: [5](#0-4) 

Exploit flow:
1. Attacker calls `registerCode()` (permissionless, tier defaults to 1).
2. Attacker's second wallet (referee) calls `useCode()` to link to the attacker's code.
3. Referee accrues pending MGP reward in some MasterMagpie pool over time.
4. Immediately before referee calls `multiclaimFor`, attacker calls `VLMGP.lock(largeAmount)`, which invokes `updateTotalFactor(attacker)`, spiking `userInfo.factor = sqrt(largeAmount)` and `totalBoostFactor`.
5. Referee calls `multiclaimFor` → `trigger()` computes `boostesd` using the just-inflated factor, crediting the attacker (referer) an oversized `refererAmount` relative to any sustained lock commitment.
6. Attacker calls `startUnlock`/waits cooldown to reclaim the locked MGP principal; the referral bonus was already credited in step 5 and is unaffected by subsequent unlocking.

No modifier, `nonReentrant` guard, or reward-index mechanism prevents this because the factor is a spot read with no minimum holding period, and `trigger()`/`updateTotalFactor` have no time-weighting logic. This is purely reachable via permissionless functions (`registerCode`, `useCode`, `lock`, `multiclaimFor`, `startUnlock`) — no owner/admin action is needed. Note: I could not locate in the indexed code the exact mechanism by which `ReferralStorage`'s MGP balance is funded (no deposit function was found in the searched files); this is worth clarifying in a full session, as it determines whether the extra payout drains a shared/finite treasury or is otherwise bounded.

### Impact Explanation
This allows theft of unclaimed referral yield: the attacker captures a share of the referral bonus pool (`refererAmount`) disproportionate to their actual sustained vlMGP commitment, effectively diluting/stealing value intended to reward genuine long-term lockers. This matches the "theft of unclaimed yield" Immunefi impact class. The magnitude of loss is proportional to `largeAmount` locked at trigger time relative to `totalBoostFactor` and to the size of `_amount` (the referee's total claimed reward) at the moment of the attack.

### Likelihood Explanation
- Fully permissionless: requires only `registerCode`, `useCode`, `VLMGP.lock`, and a `multiclaimFor` call — all attacker-controlled operations, no privileged role needed.
- Attacker needs capital equal to the flash-locked amount, but it is not consumed — only temporarily locked and later withdrawn via `startUnlock`/cooldown, making the attack essentially free besides opportunity cost of the cooldown period.
- Fully repeatable for every referee claim event; attacker can time their own lock transaction immediately before any referee's `multiclaimFor` call since both are attacker-initiated (self-referral works, using two attacker-controlled wallets).
- No front-running of a third party is required since both the lock and the claim are attacker-triggered transactions.

### Recommendation
Replace the spot-value boost factor with a time-weighted or minimum-duration-locked measure (e.g., require a minimum lock age before it counts toward `factor`, or use a time-weighted average of locked balance) so that momentary flash-locks cannot influence `boostesd`. Alternatively, snapshot the referrer's factor at a fixed cadence (e.g., once per epoch) rather than reading it live at claim time.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `VLMGP`, `ReferralStorage`, and MGP token in a test harness; wire `referral`/`referralStorage` addresses.
2. Fund `ReferralStorage` with MGP as the reward pool (using whatever legitimate funding path exists) and `setTier(1, basicPercentage)`.
3. Attacker (`referrer`) calls `registerCode(codeA)`.
4. Referee wallet (attacker's second EOA) calls `useCode(codeA)`, then deposits/stakes to accrue a large pending MGP reward in some MasterMagpie pool.
5. Baseline measurement: compute `refererAmount` that *would* result from `trigger()` if referrer's factor reflected only a small, long-held lock (fair value based on sustained lock).
6. Attack sequence: `referrer` calls `VLMGP.lock(largeAmount)`; immediately after, `referee` calls `MasterMagpie.multiclaimFor(...)`, triggering `ReferralStorage.trigger()`.
7. Assert `refererInfo.rewardAmount` (queryable via `userInfos(referrer)`) is significantly higher than the baseline fair value computed in step 5, proportional to `sqrt(largeAmount)/totalBoostFactor`.
8. `referrer` calls `startUnlock(largeAmount)` to begin reclaiming principal (subject to `coolDownInSecs`), demonstrating principal recoverability while the inflated reward remains credited and later claimable via `claimReward()`.
9. Assertion: `refererAmount_received / referrer_effective_time_weighted_lock` ratio exceeds the ratio for a legitimate, sustained locker with the same peak locked amount held for the full period, proving disproportionate capture.
