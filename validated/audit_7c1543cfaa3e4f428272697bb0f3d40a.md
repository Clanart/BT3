### Title
Auction `BidPool` rejects legitimate rebids from the current winning sender even for the same target, causing bidders to lose auction slots - (File: kaiax/auction/impl/bid_pool.go)

### Summary
The BendDAO report describes a pattern where a one-time "lock" check (`tokenData.lockerAddr == address(0)`) prevents the same actor from updating/appending to a position they already registered, forcing them into an unnecessarily destructive path (repay/lose fees) instead of allowing a legitimate update. The Kaia `auction` module's bid-admission logic (`kaiax/auction/impl/bid_pool.go`) has the same shape of defect: once a sender is recorded as the current block's bid winner, any subsequent bid from that same sender that is not byte-for-byte identical to the recorded bid is rejected with `ErrBidSenderExists`, even when the new bid targets the exact same transaction and is a legitimate self-improvement (e.g., raising `Bid` to protect against being outbid).

### Finding Description
`validateBid` and `insertBid` both call `senderHasDifferentWinner`: [1](#0-0) 
```go
func (bp *BidPool) senderHasDifferentWinner(bid *auction.Bid) bool {
	hash, ok := bp.bidWinnerMap[bid.BlockNumber][bid.Sender]
	if !ok {
		return false
	}
	return !bid.Equals(bp.bidMap[hash])
}
```
This helper checks only whether the *entire* bid object (`Equals`) matches the previously recorded winning bid for that sender — it does **not** compare `TargetTxHash`, as the module's own documented rule intends: [2](#0-1) 
```
1. The `bid.Sender` must not be in the winner list of the same block number if the new bid doesn't have the same target block and hash as the previous bid.
```

Because `senderHasDifferentWinner` is checked first and it depends on full-struct equality rather than target-hash equality, a sender who already won for a block cannot submit an updated (e.g., higher) bid for the *same target* unless the resubmitted bid is exactly identical to the one already stored — any change to `Bid`, `Data`, `CallGasLimit`, nonce/signature, etc. makes `Equals` return `false` and the improved bid is rejected as `ErrBidSenderExists`, identical in structure to `ASSET_ALREADY_LOCKED_IN_USE` blocking append in the original report.

### Impact Explanation
A searcher/bidder who has already won the block's auction slot cannot legitimately raise or otherwise refine their own bid for the same target transaction in response to new information (e.g., a competitor's near-miss bid, updated gas conditions, or corrected call data), because the "already a winner" guard fires before the same-target replace-if-better logic is reached. This causes the searcher to either lose their improved bid opportunity (economic loss, analogous to the "losing handling fee" impact in the original report) or be forced to wait for a fresh block/target, disrupting the intended flexible, replace-if-better auction design described in the module's own README.

### Likelihood Explanation
This path is reached on every call to `auction_submitBid`/`HandleBid` from any bidder (searcher, via the Auctioneer-countersigned bid) once a sender has already had one accepted winning bid in the target block, making it easy to trigger unintentionally in normal high-frequency bidding/competition scenarios described by the auction module itself.

### Recommendation
Align `senderHasDifferentWinner` with the documented rule by comparing `TargetTxHash` (and ideally block number) rather than the entire bid object, so that a sender's improved bid for the same target passes into the existing "replace if better" (`bidTargetMap`) logic instead of being rejected outright:
```go
func (bp *BidPool) senderHasDifferentWinner(bid *auction.Bid) bool {
	hash, ok := bp.bidWinnerMap[bid.BlockNumber][bid.Sender]
	if !ok {
		return false
	}
	existing := bp.bidMap[hash]
	return existing.TargetTxHash != bid.TargetTxHash
}
```

### Proof of Concept
1. Searcher S submits `Bid{BlockNumber: N, TargetTxHash: T, Bid: 10}`; it is accepted and recorded as `bidWinnerMap[N][S] = hash1`.
2. Searcher S later wants to raise their own bid for the same target T (e.g., `Bid{BlockNumber: N, TargetTxHash: T, Bid: 20}`), submitting through the Auctioneer again.
3. `validateBid`/`insertBid` call `senderHasDifferentWinner`, which finds `bidWinnerMap[N][S]` set and compares the new bid to the old one via `Equals` — since `Bid` differs, `Equals` returns `false`, so the function returns `true`.
4. The improved bid is rejected with `auction.ErrBidSenderExists` before ever reaching the `bidTargetMap[N][T]` "replace if better" branch, even though this is exactly the case the branch (and the README rule) was designed to allow.

Note: This analog was found via static code review of the current `insertBid`/`senderHasDifferentWinner`/README logic; I was unable to run the module's tests interactively in this session to confirm the exact runtime rejection message users would see, so this should be validated with a live unit test asserting the rejection of a same-sender/same-target improved bid before merging any fix.
