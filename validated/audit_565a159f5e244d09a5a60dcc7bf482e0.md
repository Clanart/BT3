## Finding: `HostManager.onAccept` authorizes privileged host actions by source **chain** only, not by source **module**

### Title
`HostManager.onAccept` fails to verify `request.from`, allowing any Hyperbridge-chain module to trigger `withdraw`/`updateHostParams` - (File: `evm/src/core/HostManager.sol`)

### Summary
`HostManager` is the sole `IApp` authorized to call the privileged `IHostManager` functions `withdraw()` and `updateHostParams()` on `EvmHost` (both gated with `restrict(_hostParams.hostManager)`). The only authentication `HostManager.onAccept` performs on an *incoming* cross-chain governance message is that `msg.sender == host` and that `request.source` equals the Hyperbridge parachain's state-machine id. It never inspects `request.from` — the address/module identifier of the account that actually dispatched the request on the Hyperbridge chain. [1](#0-0) 

### Finding Description
`HostManager` is designed as the single trusted relay for cross-chain governance: it decodes an incoming `PostRequest.body` into either a `Withdraw` or `SetHostParam` action and forwards it, unmodified, to the privileged `EvmHost.withdraw`/`updateHostParams` functions: [1](#0-0) 

The only check performed before trusting and forwarding the decoded payload is:
```solidity
if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();
```
This validates that the request *chain of origin* is the Hyperbridge parachain, but it does not validate `request.from` — i.e., which pallet/module on that chain dispatched the message. `EvmHost.dispatchIncoming`, which invokes `onAccept` on the destination module, itself performs no module-identity check either; it only checks that the destination contract has code before delegating trust entirely to the destination module (`HostManager`) to authenticate the message: [2](#0-1) 

`EvmHost.updateHostParams` and `EvmHost.withdraw` are both `restrict(_hostParams.hostManager)`-gated, i.e., they place *complete* trust in `HostManager` to have verified the origin correctly before forwarding: [3](#0-2) [4](#0-3) 

Because `HostManager.onAccept` checks only the chain-level `source` field and never the module-level `from` field, any pallet/account on the Hyperbridge relay chain that is capable of dispatching an ISMP POST request addressed `to` this `HostManager` contract's address on the destination EVM chain — regardless of whether that dispatcher is the intended governance/treasury module — will have its request accepted and executed as an authenticated governance action (arbitrary `HostParams` overwrite, including `admin`, `hostManager`, `consensusClient`, `handler`, `feeToken`; or an arbitrary token/native withdrawal to any `beneficiary`).

### Impact Explanation
If any module identity check on the Hyperbridge chain side is bypassed, is more permissive than intended, or a chain-side dispatch path exists where `from` is attacker-influenced while `source` remains the Hyperbridge id, then this EVM-side gap directly enables:
- Draining the host contract's collected protocol revenue to an arbitrary `beneficiary` via a forged `Withdraw` action, and/or
- Overwriting `HostParams` (including `admin`, `hostManager`, `consensusClient`, `handler`) to fully hijack the host's trust roots — i.e., false-state acceptance and unauthorized execution across the entire bridge.

This falls squarely under "cross-chain admin or host-management effects reachable through... wrong module bindings" since the EVM contract enforces chain-level authentication only and relies entirely on an implicit, unenforced assumption that only the governance pallet's account is `from`-bound to messages targeting `HostManager`.

### Likelihood Explanation
This is a defense-in-depth gap: the Solidity trust boundary (`HostManager`/`EvmHost`) does not independently bind the accepted governance action to a specific module identifier on the source chain, deferring entirely to chain-side dispatch conventions that are not verifiable from the EVM contracts. Exploitability depends on whether the Hyperbridge chain enforces `from == governance-pallet` at dispatch time for messages destined to `HostManager`-registered addresses; the EVM-side code alone provides no such guarantee, meaning it is not defense-in-depth for this critical privileged path.

### Recommendation
Add an explicit check of `request.from` (or a similarly bound module identifier configured on `HostManager`, analogous to how `TokenGateway`/`IntentGateway` modules bind counterpart addresses) in `HostManager.onAccept`, so that only messages originating from the known Hyperbridge governance/treasury module are accepted, rather than trusting any message whose `source` chain matches Hyperbridge.

### Proof of Concept
1. Any pallet/account on the Hyperbridge parachain dispatches an ISMP `PostRequest` with `dest` = target EVM chain, `to` = `HostManager` contract address, `source` = Hyperbridge state-machine id (satisfied automatically since it originates from that chain), `from` = attacker-controlled/non-governance module, and `body` = `abi.encodePacked(uint8(OnAcceptActions.Withdraw), abi.encode(WithdrawParams({beneficiary: attacker, amount: hostBalance, token: feeToken})))`.
2. Relayer delivers the message; `EvmHost.dispatchIncoming` finds `HostManager` has code and calls `onAccept` with no `from` validation. [2](#0-1) 
3. `HostManager.onAccept` validates only `request.source.equals(hyperbridge())`, which passes, decodes the `Withdraw` action, and calls `IHostManager(host).withdraw(withdrawParams)`. [1](#0-0) 
4. `EvmHost.withdraw` executes because `msg.sender == _hostParams.hostManager` (the `HostManager` contract itself, which is always the caller of this internal path), transferring the entire host token balance to the attacker's `beneficiary` address. [5](#0-4)

```text
    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }
```

```text
     * @dev withdraws host revenue to the given address, can only be called by cross-chain governance
     * @param params, the parameters for withdrawal
     */
    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
```
