## Title
Divide-by-zero panic in reward finalization when proposer's CN staking amount and CL staking amount are both zero - (File: kaiax/reward/impl/getter.go)

### Summary
`specWithProposerAndFunds` and `specWithProposerAndFundsFlex` unconditionally call `consolidatedNode.Split(proposer)` for the block proposer's consolidated node whenever it has a non-nil `CLStakingInfo` after the Prague hardfork, without verifying that the total stake (CNStaking + CLStaking) is non-zero. `Split()` divides by `totalAmount = cnAmountBig + clAmountBig`, causing a divide-by-zero panic (`big.Int.Div` on a zero divisor) if both amounts are zero.

### Finding Description
`consolidatedNode.Split()` computes the proportional split between CN and CL staking: [1](#0-0) 
The divisor `totalAmount` is `cnAmountBig + clAmountBig`. Unlike the staking-reward distribution paths (`assignStakingRewards`, `assignStakingRewardsFlex`), which only call `cn.Split()` for validators whose stake exceeds a minimum/threshold (guaranteeing a positive divisor), the proposer-reward finalization path has no such guard: [2](#0-1) 
and analogously in the flex variant: [3](#0-2) 
Here, the loop only checks `cn.RewardAddr == config.Rewardbase` and `cn.CLStakingInfo != nil`; it never verifies `cn.StakingAmount > 0` or `cn.CLStakingInfo.CLStakingAmount > 0`. `consolidatedNode.StakingAmount` is derived directly from `si.StakingAmounts` in `consolidateNodes()` [4](#0-3) , which reflects the on-chain CNStaking contract balance and can legitimately be zero (e.g., if a validator's CNStaking balance has been fully withdrawn) while still being registered in the AddressBook and possibly having a zero/near-zero `CLStakingAmount` reported by the CL registry.

### Impact Explanation
If the current block proposer is a registered AddressBook validator with `StakingAmount == 0` and a linked `CLStakingInfo.CLStakingAmount == 0` after the Prague hardfork, `Split()` divides by zero and the node panics inside block finalization (`FinalizeState`) or when computing rewards via `kaia_getReward`. Since this is triggered during standard state-transition/reward-distribution logic that runs on every node processing the block, it causes a chain-wide crash / halt (denial of service) rather than an isolated computation error — any full/consensus node reaching this code path for that block will panic identically, so this is a state-transition correctness/availability issue reachable purely through normal block production by an under-staked/zero-CL validator, not requiring any malicious network message.

### Likelihood Explanation
This requires: (1) Prague hardfork active, (2) a validator registered in the AddressBook whose reward address matches the block proposer, (3) that validator's CNStaking contract balance is 0 (fully withdrawn while still registered), and (4) its consolidated CL staking amount is also 0. This is a plausible operational state (a validator can withdraw its full CN stake without being removed from the AddressBook, and consensus-liquidity delegation is optional/can be zero), making the divide-by-zero reachable without any privileged access — merely by a validator letting its proposer node's stake fall to zero while remaining the proposer for a block (e.g., during the round-robin/committee window before it's evicted).

### Recommendation
In `consolidatedNode.Split()`, guard against `totalAmount.Sign() == 0` by returning `(amount, big.NewInt(0))` (or similarly attributing the full amount to the CN) when both staking amounts are zero, mirroring how `assignStakingRewards`/`assignStakingRewardsFlex` already exclude zero-stake entries from division. Alternatively, add an explicit check in `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` before calling `cn.Split(proposer)` to skip the split (falling through to `newSpec.IncRecipient(config.Rewardbase, proposer)`) when `cn.StakingAmount == 0 && cn.CLStakingInfo.CLStakingAmount == 0`.

### Proof of Concept
1. Enable Prague hardfork (`config.Rules.IsPrague = true`) with `si.CLStakingInfos` non-nil.
2. Construct a `StakingInfo` where the current block's proposer (`config.Rewardbase`) maps to a `consolidatedNode` with `StakingAmount = 0` and an associated `CLStakingInfo{CLStakingAmount: 0}`.
3. Call `getDeferredRewardFullKore`/`getDeferredRewardFullFlex` → `specWithProposerAndFunds`/`specWithProposerAndFundsFlex`, which reaches `cn.Split(proposer)` at [5](#0-4)  with `cn.StakingAmount == 0` and `cn.CLStakingInfo.CLStakingAmount == 0`.
4. Inside `Split()` at [6](#0-5) , `totalAmount` is `big.NewInt(0)`, and `clAmount.Div(clAmount, totalAmount)` panics with "division by zero", crashing the node during `FinalizeState`/reward computation for that block.

func (si *StakingInfo) consolidateNodes() *[]consolidatedNode {
	// because Go map is not ordered, rList keeps track of the occurrence order of RewardAddrs.
	// to later arrange the consolidatedNodes.
	cmap := make(map[common.Address]*consolidatedNode)
	rList := make([]common.Address, 0, len(si.RewardAddrs))
	nToR := make(map[common.Address]common.Address)

	for i, n := range si.NodeIds {
		r := si.RewardAddrs[i]
		// Unique nodeId is guaranteed by AddressBook.
		nToR[n] = r
		if cn, ok := cmap[r]; ok {
			cn.NodeIds = append(cn.NodeIds, n)
			cn.StakingContracts = append(cn.StakingContracts, si.StakingContracts[i])
			cn.StakingAmount += si.StakingAmounts[i]
		} else {
			cmap[r] = &consolidatedNode{
				NodeIds:          []common.Address{n},
				StakingContracts: []common.Address{si.StakingContracts[i]},
				RewardAddr:       r,
				StakingAmount:    si.StakingAmounts[i],
			}
			rList = append(rList, r)
		}
	}

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
