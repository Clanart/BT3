## Analysis

The external report's core broken invariant: a **failed/queued cross-chain message retains its "trusted source" attribution from the time it was queued, but the retry path re-executes it without re-checking whether that source is still trusted at retry time.**

The local analog is in `HyperbridgeLzEndpoint.sol`, Hyperbridge's LayerZero-compatibility adapter, which routes LZ-style messages through ISMP.

### Root cause

`onAccept()` validates that an inbound message's `srcEid` matches the *current* `_stateMachineToEid` mapping for the claimed ISMP `request.source` before delivering to the OApp: [1](#0-0) 

If the OApp's `lzReceive` reverts, the payload is retained keyed only by `(receiver, srcEid, sender, nonce)`: [2](#0-1) 

The owner can reassign or revoke an `eid → stateMachineId` binding at any time via `setEidMapping()`, which explicitly documents that this is meant to prevent a revoked source from "impersonating" that eid: [3](#0-2) 

However, `retryPayload()` — the permissionless recovery entrypoint — never re-checks `_eidToStateMachine`/`_stateMachineToEid` at all. It only verifies the stored payload hash matches, then directly calls `lzReceive` on the destination OApp: [4](#0-3) 

This is precisely the `retryMessage()`/`_nonblockingLzReceive()` gap from the Venus report: the trust check happens only at initial receipt, but the retained/failed-message replay path skips it entirely.

### Title
Stale trust binding allows delivery of queued LayerZero-adapter payloads after their source eid mapping is revoked/reassigned - (`sdk/packages/lz-endpoint/contracts/HyperbridgeLzEndpoint.sol`)

### Summary
`HyperbridgeLzEndpoint.onAccept()` binds an inbound message's `srcEid` to a specific ISMP `stateMachineId` at receipt time via `_stateMachineToEid`, but a failed delivery is only cached as `(receiver, srcEid, sender, nonce) → payloadHash`. `retryPayload()`, `clear()`, `skip()`, `nilify()`, and `burn()` never re-derive or re-validate that binding — they operate purely on the numeric `srcEid` stored at receipt time.

### Finding Description
When `onAccept()` receives a message and the OApp's `lzReceive` reverts, the message is cached keyed by the numeric `srcEid` that was valid *at that moment*: [5](#0-4) 

The owner can later call `setEidMapping(lzEid, newStateMachineId)` to revoke the old chain's binding to that `lzEid` and reassign the same `lzEid` to a different (or no) ISMP state machine — exactly the scenario the code comments describe as preventing impersonation "going forward": [3](#0-2) 

But any already-queued failed payload for the old binding remains fully retriable, since `retryPayload()` performs no trust check at all beyond the stored-hash match: [6](#0-5) 

The comment on `retryPayload` even states it "mirrors {onAccept}'s direct call," but it omits the `expectedEid`/`_stateMachineToEid` re-check that `onAccept` performs — it mirrors only the delivery call, not the trust gate.

Since `retryPayload` is explicitly permissionless ("anyone may push a stuck payload through"), an attacker does not need to compromise a relayer, node, or admin — they only need a previously-queued failed payload from a source that has since been revoked/reassigned, which they can push through at will once the destination OApp becomes callable again (e.g., unpaused, recipient un-blocklisted).

### Impact Explanation
The destination OApp receives an `lzReceive` call carrying `Origin{srcEid, sender, nonce}` that no longer corresponds to any currently-trusted ISMP source. If the OApp's own peer-authorization model keys off `srcEid` (the standard LZ OApp pattern of validating `origin.sender == peers[origin.srcEid]`), reassigning an eid to a new legitimate chain while a stale, attacker-influenced payload from the old (now revoked) chain sits in the queue lets that stale payload be delivered under the *new* chain's identity once retried — an unauthorized execution with the wrong provenance. At minimum, this permanently defeats the intended purpose of `setEidMapping`'s revocation semantics, allowing execution of messages from a source the protocol operator explicitly cut off.

### Likelihood Explanation
Requires: (1) an OApp `lzReceive` that reverts at least once (routine — insufficient gas, temporary pause, blocklist, cap checks, all called out in the code's own comments as expected revert causes), and (2) the operator later calling `setEidMapping` to revoke or reassign that eid (a normal, expected admin operation, not a compromise). No malicious relayer, prover, or governance actor is needed — the retry call itself is fully permissionless and requires only a previously-stored failed payload.

### Recommendation
Re-validate trust at retry time: `retryPayload` (and `clear`/`skip`/`nilify`/`burn`) should re-derive the expected `stateMachineId` for `origin.srcEid` via `_eidToStateMachine[origin.srcEid]` and confirm it still resolves to the same source that was valid at receipt time (or store the `stateMachineId` hash alongside the payload hash at `onAccept` time and compare it at retry time), rejecting the retry if the binding has since changed or been cleared.

### Proof of Concept
1. Owner calls `setEidMapping(5, chainA)` binding eid `5` to `chainA`.
2. A message is relayed from `chainA` through ISMP; `onAccept` validates `srcEid==5` matches `_stateMachineToEid[chainA]==5`, then calls `lzReceive` on `receiver`, which reverts (e.g., transient pause). Payload is cached at `_inboundPayloadHashes[receiver][5][sender][nonce]`.
3. Operator determines `chainA`'s light client/state machine should no longer be trusted (or is migrating), and calls `setEidMapping(5, chainC)`, which clears `_stateMachineToEid[chainA]` and reassigns eid `5` to `chainC` per the intended revocation design.
4. Anyone calls `retryPayload(receiver, Origin(5, sender, nonce), guid, message)`. No check against `_eidToStateMachine[5]` (now `chainC`) or the original `chainA` binding is performed; `lzReceive` executes on `receiver` with `origin.srcEid = 5`, which the OApp's peer model now associates with `chainC`, granting the stale/revoked `chainA` message the trust level of `chainC`.

    /**
     * @notice Registers a bidirectional mapping between a LZ eid and an ISMP state machine ID.
     * @dev Pass empty `stateMachineId` to disable the EID. Re-mapping an EID clears the prior
     * state machine's reverse entry so revoked sources cannot keep impersonating the EID.
     * @param lzEid The LayerZero endpoint ID
     * @param stateMachineId The ISMP state machine identifier (e.g., StateMachine.evm(1))
     */
    function setEidMapping(uint32 lzEid, bytes calldata stateMachineId) external onlyOwner {
        if (lzEid == 0) revert InvalidEid();
        bytes memory previous = _eidToStateMachine[lzEid];
        if (previous.length != 0) {
            delete _stateMachineToEid[keccak256(previous)];
        }
        _eidToStateMachine[lzEid] = stateMachineId;
        if (stateMachineId.length != 0) {
            _stateMachineToEid[keccak256(stateMachineId)] = lzEid;
        }
    }

    function retryPayload(
        address receiver,
        Origin calldata origin,
        bytes32 guid,
        bytes calldata message
    ) external payable {
        bytes32 stored = _inboundPayloadHashes[receiver][origin.srcEid][origin.sender][origin.nonce];
        if (stored == bytes32(0) || stored == NIL_PAYLOAD_HASH || stored != keccak256(abi.encode(guid, message))) {
            revert InvalidPayloadHash();
        }

        // Clear first; if the retry reverts, this deletion rolls back with the rest of the tx and
        // the payload remains recoverable.
        delete _inboundPayloadHashes[receiver][origin.srcEid][origin.sender][origin.nonce];

        ILayerZeroReceiver(receiver).lzReceive{value: msg.value}(origin, guid, message, msg.sender, "");
        emit InboundPayloadResolved(receiver, origin.srcEid, origin.sender, origin.nonce);
    }
