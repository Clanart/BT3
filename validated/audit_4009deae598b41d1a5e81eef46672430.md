Based on the evidence gathered, I found a concrete on-chain analog to the report's slippage/sandwich pattern in `IntentGatewayV2.placeOrder()`'s native-fee path.

### Title
Unprotected exact-output AMM swap for solver fees during `placeOrder` exposes users to sandwich manipulation - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The external report's core broken invariant is: *a price-dependent conversion with no attacker-supplied slippage bound, executed live on-chain, lets an attacker manipulate the price around the victim's transaction to extract value*. `IntentGatewayV2.placeOrder()` contains the same pattern: when a user pays `order.fees` with native token (`msgValue > 0`), the contract performs a **live Uniswap V2 exact-output swap** (`swapETHForExactTokens`) to acquire the fee token, with no user-supplied minimum-input / slippage parameter at all.

### Finding Description
In `placeOrder`, whenever the caller funds fees in native currency, the contract does: [1](#0-0) 

```solidity
if (order.fees > 0) {
    address feeToken = IDispatcher(hostAddr).feeToken();
    if (msgValue > 0) {
        address uniswapV2 = IDispatcher(hostAddr).uniswapV2Router();
        address WETH = IUniswapV2Router02(uniswapV2).WETH();
        address[] memory path = new address[](2);
        path[0] = WETH;
        path[1] = IDispatcher(hostAddr).feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
            order.fees, path, address(this), block.timestamp
        );
    } ...
```

`order.fees` is the fixed **output** amount (analogous to the fixed `BUSDamount`/target amount in `buydPNM`), and `msgValue` is the maximum ETH the caller is willing to spend. There is no `slippage` or `minAmountIn` argument exposed to the user; the router simply pulls whatever ETH the live WETH/feeToken pool price demands, up to `msgValue`. This is a mandatory, unconditional swap embedded in a normal user-facing entrypoint — `placeOrder` is callable by any unprivileged user, and the swap executes synchronously within that same transaction, making it directly front-runnable/sandwichable like an AMM trade with no price-protection argument, exactly the bug class in the report.

### Impact Explanation
An attacker can sandwich a victim's `placeOrder` call: front-run to skew the WETH→feeToken pool price so more ETH is required to buy the fixed `order.fees` in fee token, then back-run to restore the price and capture the extracted value as arbitrage profit. Because the amount-in is unbounded up to the entire `msgValue` the user attached, and there is no `minAmountIn`/slippage guard the user can set, the attacker can capture value up to the difference between the honest price and `msgValue`, directly reducing the ETH available to the user (increasing the ETH actually spent versus the fair-market cost) or forcing more of the attached native token into the swap than the fair fee cost. This maps to the "logic attacks / transaction manipulation" and "unauthorized value extraction" categories in the Hyperbridge Impact Gate, since it's a public entrypoint reachable by any unprivileged attacker without a malicious relayer, prover, or governance actor.

### Likelihood Explanation
Likelihood is high wherever this fee-token acquisition path is exercised: any `placeOrder` call funding `order.fees` in native token against a WETH/feeToken pool with realistic on-chain liquidity is sandwichable using standard MEV tooling (mempool front-running or same-block bundling on chains without private mempools). No special privileges, relayer collusion, or governance access are required — only capital to move the pool price temporarily.

### Recommendation
Add a caller-supplied slippage/maximum-input parameter to the fee-swap path (mirroring the report's suggested fix), e.g., accept a `maxNativeIn` or `slippageBps` argument in `placeOrder`/`Order`, and validate that the swap's actual `amountIn` (returned by `swapETHForExactTokens`) does not exceed a computed bound derived from an oracle-referenced or user-specified maximum, reverting the whole `placeOrder` transaction if the live pool price has moved unfavorably beyond that tolerance — consistent with the slippage-bound pattern already used elsewhere in the codebase (e.g., `SimplexPaymaster.swapAndDeposit`'s oracle-derived `amountOutMin` with `swapSlippageBps`, at [2](#0-1) ).

### Proof of Concept
1. Attacker monitors mempool/pending block for a `placeOrder` call that sets `order.fees > 0` and attaches native `msg.value` to cover it.
2. Attacker front-runs with a swap that shifts the WETH/feeToken pool price so more WETH is needed to buy `order.fees` units of fee token.
3. Victim's `placeOrder` executes `swapETHForExactTokens{value: msgValue}(order.fees, [WETH, feeToken], address(this), block.timestamp)` at the manipulated price, consuming more of the victim's attached ETH than the fair-market rate (or reverting if it exceeds `msgValue`, causing DoS, or succeeding with worse economics silently since no minInputAmount check exists in this code path).
4. Attacker back-runs to restore the pool price and pockets the price-impact profit extracted from the victim's transaction.

If a Devin session is used to pursue this further, it should diff `evm/src/apps/IntentGatewayV2.sol` against the Tron variant to confirm whether the same unguarded swap exists in the primary EVM deployment path, and trace where any refunded/leftover native value ends up.
