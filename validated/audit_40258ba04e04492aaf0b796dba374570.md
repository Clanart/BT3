**Reasoning:**

The claim rests on the assumption that a single publish transaction's writes (module bytes, metadata, owner record) could be split across two `StateSummary::update()` invocations with an intermediate root exposed. This is factually incorrect based on the code.

`StateUpdateRefs::index` splits updates into `for_last_checkpoint` and `for_latest` batches strictly by **version index**, using `all_checkpoint_indices` to determine a checkpoint boundary between whole versions/transactions — never within a single version's write set: [1](#0-0) . A transaction's entire write set (all keys written by that one transaction, including module bytes, metadata, and owner writes for a publish) is indexed at exactly one `version` and therefore is placed entirely inside a single `PerVersionStateUpdateRefs`/`BatchedStateUpdateRefs` bucket, which becomes the input to exactly one `StateSummary::update()` call: [2](#0-1) .

`LedgerStateSummary::update` then calls the private `StateSummary::update` at most twice per invocation (once for `for_last_checkpoint_batched()`, once for `for_latest_batched()`), but these two batches contain disjoint, non-overlapping sets of *whole versions* — a version (and thus a whole transaction's write set) can only belong to one of the two: [3](#0-2) . The private `StateSummary::update` method itself processes a `BatchedStateUpdateRefs` — a fully deduplicated, per-key-map batch covering all versions in that segment in one shot, using `rayon::join` to fold hot and global state trees together before returning the new summary: [4](#0-3) .

Therefore, there is no code path where a single transaction's constituent writes (module bytes + metadata + owner record) can be split across two separate `update()` calls with an intermediate, partially-updated root exposed to provers. `root_hash()` is only meaningful after a full `update()` call folds the complete batch for that version segment, and a publish transaction's writes cannot straddle a checkpoint boundary since checkpoint indices split at version granularity, not sub-transaction granularity.

Beyond the technical inaccuracy, this claim does not describe a publish/code-safety impact under the required scope (unauthorized publish, upgrade, freeze, ownership change, verifier bypass, or metadata/bytecode mismatch). It is a hypothetical about internal state-summary bookkeeping/proof consistency, not a mechanism by which unprivileged input could alter what code is published, verified, or executed on chain.
