### Title
Schnorr half-aggregation weights are not bound to the nonces, enabling universal aggregate signature forgery - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` derives its per-signature weights `z_i` from a `DigestTranscript` that commits **only to the challenges** — it never transcripts the attacker-supplied nonce points `R_i`. Per <https://eprint.iacr.org/2021/350> (the scheme this implements), the aggregation weight must bind each signature's `R`; otherwise the verification equation degenerates to a linear system the attacker solves trivially. Any party that can feed bytes to `SchnorrAggregate::read` (e.g., an aggregate signature presented to a verifier) can forge a passing aggregate over any set of public keys and challenges.

### Finding Description
`verify` builds the digest at `crypto/schnorr/src/aggregate.rs:132-136`:

```rust
let mut digest = DigestTranscript::<C::H>::new(dst);
digest.domain_separate(b"signatures");
for (_, challenge) in keys_and_challenges {
  digest.append_message(b"challenge", challenge.to_repr());
}
```

Only `challenge` values are appended. The weights `z = weight(&mut digest)` (line 140) are therefore a deterministic function of `dst` and the challenges alone — fully computable by the attacker before choosing `Rs` or `s`. The verification equation at lines 139-145 is:

```
Σ_i z_i·R_i + Σ_i z_i·c_i·A_i - s·G = 0
```

Because `z_i` does not depend on `R_i`, a forger sets `R_i = -c_i·A_i` for every signer `i` and `s = 0`. Every pair then contributes `z_i·(-c_i·A_i) + z_i·c_i·A_i = 0`, and the final term is `0·G = 0`, so `multiexp_vartime` returns identity and `verify` returns `true`. `SchnorrAggregate::read` (lines 77-88) imposes no validity constraint that would block this: each `R_i` is read via `C::read_G` and `s` via `C::read_F`; `R_i = -c_i·A_i` is a canonical, non-identity point, and `s = 0` is a canonical scalar encoding.

By contrast, the aggregator side (`SchnorrAggregator::aggregate`, lines 169-172) has the same omission — it also only appends challenges — so honest-produced aggregates remain consistent, but the scheme's unforgeability property is void.

### Impact Explanation
This is a universal forgery: an unprivileged attacker who knows the public keys and the per-signature challenges (which are public functions of key, nonce, and message in every caller — e.g., `challenge(genesis, key, R_i, msg)` in `coordinator/tributary/src/tendermint/mod.rs:192,217`) can produce `SchnorrAggregate` bytes that verify for **any** signer set and **any** message, with no secret knowledge and no interaction. Any consensus or multisig path relying on `SchnorrAggregate::verify` accepts attacker-fabricated agreement. No preprocessing, collusion, or valid signature is needed — the forged aggregate passes without any real signer participating.

### Likelihood Explanation
Triggering requires only that the attacker submit an aggregate signature to a verifier that calls `SchnorrAggregate::verify`. The `keys_and_challenges` inputs are derived by the verifier from public data (validator IDs, message, and the attacker's own supplied `Rs` used to compute challenges). The forger computes `z_i` locally (the digest is deterministic), solves for `R_i = -c_i·A_i`, serializes `len || Rs || s=0`, and submits. Deterministic, single-shot, no probabilistic element. Severity: High.

### Recommendation
Bind each nonce into the weight transcript before deriving `z_i`. In `verify`, append `self.Rs[i]` inside the loop; in `SchnorrAggregator::aggregate`, append the signature's `R` identically so prover and verifier transcripts stay synchronized:

```rust
digest.append_message(b"nonce", self.Rs[i].to_bytes());
// and/or include the challenge as today
```

With `z_i = H(dst, challenges, R_i)`, setting `R_i = -c_i·A_i` changes `z_i` itself, and the forgery reduces to solving a hash-fixed-point equation, restoring the eprint.iacr.org/2021/350 security argument. Note this changes the aggregate signature format's verification semantics — existing aggregates remain parseable but any verification is now correctly bound.

### Proof of Concept
```rust
// For any keys_and_challenges [(A_i, c_i)] and dst:
let mut digest = DigestTranscript::<C::H>::new(dst);
digest.domain_separate(b"signatures");
for (_, c) in &keys_and_challenges {
    digest.append_message(b"challenge", c.to_repr());
}
let mut forged = vec![];
forged.extend(u32::try_from(keys_and_challenges.len()).unwrap().to_le_bytes());
for (A_i, c_i) in keys_and_challenges {
    let _z = weight::<_, C::F>(&mut digest); // weights known before choosing R
    let R_i = -(*c_i) * A_i;                // each term z_i*(R_i + c_i*A_i) == 0
    forged.extend(R_i.to_bytes().as_ref());
}
forged.extend(C::F::ZERO.to_repr().as_ref()); // s = 0

let agg = SchnorrAggregate::<C>::read(&mut forged.as_slice()).unwrap();
assert!(agg.verify(dst, &keys_and_challenges)); // FORGERY ACCEPTED
```

Root cause confirmed at `crypto/schnorr/src/aggregate.rs:132-145`: `weight()` inputs contain only `challenge` values, not `self.Rs`, so the multiexp sum `Σ z_i·(R_i + c_i·A_i) - s·G` is satisfied by the trivial solution `R_i = -c_i·A_i, s = 0`, chosen after the weights are already fixed.
