### Title
`internal_withdraw` RPC bypasses the aggregator's ECDSA verification-signature check enforced by `withdraw` - (File: core/src/rpc/operator.rs)

### Summary
The `ClementineOperator` service exposes two gRPC methods that both trigger a Bitcoin withdrawal payout from the same underlying `operator.withdraw(...)` logic: `withdraw` and `internal_withdraw`. `withdraw` enforces that the caller supplies a valid EIP-712 ECDSA "verification signature" from the aggregator's authorized address before invoking the payout, but `internal_withdraw` invokes the identical payout logic without any such check.

### Finding Description
`withdraw` parses the withdrawal parameters and, when `self.operator.config.aggregator_verification_address` is configured, requires and validates a `verification_signature` recovered via `recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>` against the configured aggregator address before calling `self.operator.withdraw(...)`: [1](#0-0) 

`internal_withdraw`, however, parses the same withdrawal parameters and calls `self.operator.withdraw(...)` directly, with no verification-signature parameter, no config check, and no gate analogous to the `cfg!(test)` guard used by other "internal_" methods (e.g. `internal_finalized_payout` explicitly rejects non-test callers): [2](#0-1) [3](#0-2) 

This mirrors exactly the ChainPort-analog concern raised in the report: a message/action needs to be scoped so a signature (or the requirement for one) intended for one code path cannot be satisfied — or skipped — via a different action/entry point. Here, the entry point itself (`internal_withdraw`) omits the authorization check altogether rather than accepting a mis-scoped signature, but the effect is the same class of bug: the state-changing "withdraw" action is reachable through a path that does not enforce the binding between "party authorized to request payout" (the aggregator) and "party that actually triggers the payout."

### Impact Explanation
If `aggregator_verification_address` is configured (i.e., the operator intends to require aggregator authorization before releasing a payout), any caller able to reach the operator's gRPC endpoint can call `internal_withdraw` with attacker-chosen `input_signature`/`input_outpoint`/`output_script_pubkey`/`output_amount` and have the operator construct and return a signed payout transaction without ever presenting the aggregator's verification signature. This is an unauthenticated state-changing/broadcasting call: it creates (and can lead to broadcast of) an operator-funded payout transaction that was not authorized by the aggregator, matching the "unauthenticated state-changing or broadcasting call" High-impact category.

### Likelihood Explanation
Exploitability depends entirely on network/gRPC reachability of the operator's RPC surface (no additional secret, key compromise, or privileged role is required beyond calling the exposed method), and the check is skipped unconditionally for this method regardless of configuration — there is no code path in `internal_withdraw` that consults `aggregator_verification_address` at all, unlike `withdraw`.

### Recommendation
Either remove `internal_withdraw` from the externally reachable `ClementineOperator` service (restrict to an internal-only interface/feature flag consistent with `internal_finalized_payout`'s `cfg!(test)` gating), or make it perform the exact same `aggregator_verification_address` / `verification_signature` check that `withdraw` performs before calling `self.operator.withdraw(...)`.

### Proof of Concept
1. Deploy an operator with `aggregator_verification_address` configured (i.e., in the intended configuration where payouts require aggregator sign-off).
2. Call the operator's `internal_withdraw` gRPC method directly with a `WithdrawParams` message (withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount) — no `verification_signature` field exists on this RPC's request type at all.
3. Observe that `core/src/rpc/operator.rs:169-190` calls `self.operator.withdraw(...)` and returns a signed payout transaction, whereas doing the same through `withdraw` (lines 192-258) would fail with `BridgeError::ECDSAVerificationSignatureMissing` absent a valid aggregator signature.

        tracing::warn!("Called internal_withdraw with withdrawal id: {:?}, input signature: {:?}, input outpoint: {:?}, output script pubkey: {:?}, output amount: {:?}", withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount);

            .operator
            .withdraw(
                withdrawal_id,
                input_signature,
                input_outpoint,
                output_script_pubkey,
                output_amount,
            )
            .await?;

        Ok(Response::new(RawSignedTx::from(&payout_tx)))
    }
