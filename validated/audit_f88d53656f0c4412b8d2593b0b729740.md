### Title
Out-of-range blame participant causes processor panic - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`BlameMachine::blame` and `AdditionalBlameMachine::blame` accept arbitrary non-zero `Participant` values for `sender` and `recipient` without checking that they are within the DKG’s `1..=n` range. When a supplied message has a valid proof-of-possession and a blame proof is present, `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` directly, panicking if `decryptor` is outside the registered participant set. An unprivileged participant can reuse a valid encrypted share message—whose PoP binds the sender and ciphertext but not the recipient—and supply an out-of-range accused participant to crash the processing path. [1](#0-0) [2](#0-1) 

### Finding Description
`Participant::new` only rejects zero; it does not bound the value to the configured participant count. [3](#0-2) 

`AdditionalBlameMachine::new` populates `Decryption::enc_keys` only for participants `1..=n`. [4](#0-3) 

However, `AdditionalBlameMachine::blame` forwards caller-provided `sender` and `recipient` values directly to `blame_internal`, without validating them against that map. [1](#0-0) 

If the encrypted message’s Schnorr proof-of-possession verifies and `proof` is `Some`, `decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` while constructing the DLEq verification inputs. [5](#0-4) 

Because `HashMap` indexing panics for an absent key, a `recipient` such as `n + 1` causes an immediate panic before the proof can be rejected. [6](#0-5) 

### Impact Explanation
This is a remotely triggerable denial of service analogous to CVE-2015-1379’s externally induced process crash. A single malformed blame submission can terminate the task or process evaluating blame, aborting key-generation handling and potentially requiring restart or recovery. [2](#0-1) 

### Likelihood Explanation
The attacker only needs to cause blame evaluation with a syntactically valid `EncryptedMessage`, any non-`None` `EncryptionKeyProof`, and an out-of-range accused `Participant`. The encrypted-message PoP challenge commits to the context, sender, key, nonce, and ciphertext, but not the recipient, so a valid message may be reused for an invalid `decryptor`. [5](#0-4) [7](#0-6) 

The DLEq proof does not need to be valid: the vulnerable map lookup is evaluated before `DLEqProof::verify` is called. [6](#0-5) 

### Recommendation
Validate both `sender` and `recipient` in `BlameMachine::blame` and `AdditionalBlameMachine::blame` before calling `blame_internal`. Return an error or deterministic blame result when either participant is absent from `commitments`/`enc_keys`. Replace indexing such as `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with checked lookups. [8](#0-7) [2](#0-1) 

### Proof of Concept
```rust
// Assume:
// - n = 2
// - `machine` is an AdditionalBlameMachine initialized for participants 1 and 2
// - `msg` is a valid EncryptedMessage whose PoP was created by participant 1
// - `proof` is any syntactically valid EncryptionKeyProof

let sender = Participant::new(1).unwrap();
let out_of_range_recipient = Participant::new(3).unwrap();

// This reaches self.enc_keys[&Participant(3)] and panics.
let _ = machine.blame(
    sender,
    out_of_range_recipient,
    msg,
    Some(proof),
);
```

The panic occurs while evaluating the DLEq verification arguments, specifically at `self.enc_keys[&decryptor]`. [6](#0-5)
