## Analysis: Native ETH overpayment lost to `EvmHost` in `dispatch()` / `fundRequest()`

The Putty bug class is "a payable function receives ETH on a path that doesn't fully use it, and the excess is never returned to the sender." I found a direct structural analog in `EvmHost.sol`'s native-fee swap path, which differs from how `IntentGatewayV2` handles the same problem (it explicitly tracks and refunds unspent `msg.value`).

### Title
Excess native ETH sent to `EvmHost.dispatch()` / `fundRequest()` is permanently lost instead of refunded to the caller - (`evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all forward the entire `msg.value` into `swapETHForExactTokens`, requesting only `post.fee` (or `amount`) worth of `feeToken` output. Any unused ETH from that swap is refunded by the router **to the caller of the router**, which is `EvmHost` itself — not the original transaction sender. `EvmHost` never captures or forwards this refund back to `_msgSender()`/`post.payer`, so it is stranded in the host contract. [1](#0-0) [2](#0-1) 

### Finding Description
In `dispatch(DispatchPost)`:
```solidity
if (msg.value > 0) {
    ...
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
```
This is an "exact-output" swap: the function requests exactly `post.fee` units of `feeToken`, but supplies the *entire* `msg.value` as the maximum input. Only the amount actually needed is consumed; the rest is refunded by the swap router's own refund logic. In this repo's own Uniswap-V2-compatible wrapper (`UniV3UniswapV2Wrapper.sol`), that refund is sent to `msg.sender` — the address that called the router, i.e. `EvmHost` itself:
```solidity
if (spent < msg.value) {
    uint256 refund = msg.value - spent;
    IWETH(weth).withdraw(refund);
    (bool success,) = msg.sender.call{value: refund}("");
    if (!success) revert RefundFailed();
}
``` [3](#0-2) 

Back in `EvmHost.dispatch()`/`fundRequest()`, the return value of `swapETHForExactTokens` (and any ETH sent back via `receive()`) is never captured or transferred onward to `_msgSender()`/`post.payer`. There is no `require(msg.value == expectedCost)` guard and no post-swap refund step, unlike `IntentGatewayV2`, which deliberately tracks `msgValue` through the whole function and refunds any residue to `msg.sender` at the end:
```solidity
// Refund any unspent native tokens to the user.
if (msgValue > 0) {
    (bool sent,) = msg.sender.call{value: msgValue}("");
    if (!sent) revert InsufficientNativeToken();
}
``` [4](#0-3) 

`EvmHost.dispatch()`/`fundRequest()` have no equivalent refund path, and since the actual ETH price of `post.fee` worth of `feeToken` fluctuates with market conditions (a caller cannot know the exact ETH amount in advance without a fresh on-chain quote, and even a quote can go stale between quoting and execution), any caller who sends slightly more ETH than the instantaneous exact requirement permanently loses the difference to the `EvmHost` contract's balance.

### Impact Explanation
This is a direct loss-of-funds bug reachable by any unprivileged user calling `dispatch()`, `dispatch(DispatchGet)`, or `fundRequest()` with native ETH, which are all standard, documented, publicly advertised payment paths (see `docs/content/developers/evm/messaging/post-requests.mdx`). Overpayment (even by a small margin, which is normal/expected behavior when users don't have a live price oracle for the exact swap output) results in ETH being stuck in `EvmHost` with no user-facing recovery mechanism, matching the "stealing or loss of funds" impact category.

### Likelihood Explanation
High. Any caller using the native-ETH payment method for `dispatch()`/`fundRequest()` who doesn't send the *exact* minimal ETH amount for the swap (which is realistically almost always, since routers/AMM prices move and the caller cannot predict the exact optimal `msg.value` without perfectly replicating the swap simulation at the exact block) will lose the difference. No malicious actor, relayer, or privileged role is required — it is triggered by completely normal usage.

### Recommendation
Capture the return value of `swapETHForExactTokens` (or the actual ETH balance delta before/after the call) in `dispatch()`, `dispatch(DispatchGet)`, and `fundRequest()`, and refund any unspent ETH back to `_msgSender()` (or `post.payer`) at the end of each function, mirroring the pattern already used in `IntentGatewayV2._fillSameChain`/`_fillCrossChain`/`placeOrder`.

### Proof of Concept
1. User calls `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` only requires `0.9 WETH`-equivalent of ETH at the current pool price.
2. `swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), block.timestamp)` executes; the router only consumes the ETH-equivalent needed to produce `post.fee` in `feeToken`.
3. The router refunds the unused ETH to its caller, `EvmHost` (per the wrapper logic shown above; the standard UniswapV2Router02 has equivalent trailing-ETH-refund behavior for `swapETHForExactTokens`).
4. `EvmHost.dispatch()` returns normally, having consumed the user's entire `1 ether` from their wallet, but only forwarded/used a fraction of it for the fee; the residual ETH sits in `EvmHost`'s balance.
5. No function exists for the user to reclaim that residual ETH — it is permanently lost to them. [5](#0-4)
