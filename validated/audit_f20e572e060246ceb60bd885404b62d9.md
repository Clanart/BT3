Based on my research, I found a strong structural analog to the BACnet OOB-read pattern in `chia/full_node/mempool_manager.py`'s canonical-CLVM-encoding checker.

### Title
Uncaught out-of-bounds buffer read in `is_clvm_canonical`/`is_atom_canonical` from attacker-supplied spend bundle bytes - (File: chia/full_node/mempool_manager.py)

### Summary
`is_clvm_canonical()` and its helper `is_atom_canonical()` walk a raw CLVM byte buffer using a `while True` loop driven entirely by length-prefix bytes taken from the buffer itself, without ever checking `offset` against `len(clvm_buffer)` before the next dereference [1](#0-0) . This mirrors the reported BACnet bug class: a length/offset value parsed from untrusted input is trusted to compute the next read position without a bounds check against the actual buffer size.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads `b = clvm_buffer[offset]` and then, for multi-byte length prefixes, advances `offset` and reads further bytes in a loop purely based on the prefix-length bits decoded from `b`, again with no check that `offset` stays within `len(clvm_buffer)` [2](#0-1) . It then returns `1 + prefix_len + atom_len`, where `atom_len` is fully attacker-controlled (derived from the buffer's own bytes).

`is_clvm_canonical()` uses that return value to advance its own `offset` and immediately loops back to `b = clvm_buffer[offset]` without validating that the new `offset` is still less than `len(clvm_buffer)` [3](#0-2) . A single crafted byte such as `0x84` (interpreted as a 6-bit length prefix declaring an atom of length 4) in a buffer that is only 1 byte long causes `is_atom_canonical` to report `atom_len=5` as "canonical," after which `is_clvm_canonical` computes `offset = 5` on a 1-byte buffer and dereferences `clvm_buffer[5]` on the next loop iteration — an out-of-bounds index, analogous to `npdu_is_expected_reply` indexing `reply_pdu[offset+…]` past the actual PDU length after a permissive size check.

Per the project's own documentation, this canonical-form check gates DEDUP-eligible spends and is invoked on solution bytes coming from spend bundles submitted to the mempool [4](#0-3) .

### Impact Explanation
In Python, an out-of-bounds `bytes` index raises `IndexError` rather than causing memory corruption, so this differs from the C-level UB in the original report. If that `IndexError` is not caught somewhere in the mempool-item validation call chain, a single malformed (but otherwise well-formed at the byte level) solution submitted in a `SpendBundle` could raise an unhandled exception during dedup-eligibility processing of that item, which is the kind of "spend-triggered transaction-processing halt" this analysis is scoped to accept as impact.

### Likelihood Explanation
I was not able to fully confirm, within the available tool budget, the exact call site inside `pre_validate_spendbundle()`/mempool item processing that invokes `is_clvm_canonical()`, nor whether that call site wraps it in a try/except that downgrades a raised `IndexError` into an ordinary per-item mempool rejection (`Err.INVALID_CONDITION`/etc.) rather than propagating to crash the mempool-manager task. Given that uncertainty, I cannot confirm the practical severity — if it's caught, this is a low-impact input-validation quirk with no security consequence; if uncaught, it is a real remotely-triggerable DoS via a single spend bundle submission. I was unable to grep the direct caller within my remaining iterations to settle this.

### Recommendation
Add an explicit bounds check (`offset < len(clvm_buffer)`, and specifically `offset + prefix_len < len(clvm_buffer)` before consuming prefix bytes) in both `is_atom_canonical()` and `is_clvm_canonical()` and return `False`/raise a well-defined, caught exception rather than allowing `IndexError` to propagate. Additionally, confirm the caller of `is_clvm_canonical()` explicitly catches any parsing exception and converts it to a controlled mempool rejection.

### Proof of Concept
```python
from chia.full_node.mempool_manager import is_clvm_canonical

# 0x84 declares a 6-bit-length-prefix atom of length 4,
# but the buffer is only 1 byte long.
is_clvm_canonical(b"\x84")  # raises IndexError: index out of range

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

## Canonical serialization

**Location**: `mempool_manager.py:185`

### `is_clvm_canonical(clvm_buffer)`

Checks that a CLVM program uses shortest-form atom encoding:

- No unnecessary length prefix bytes
- No back-references (`0xFE` byte)
- No trailing garbage

### When enforced

Required for DEDUP-eligible spends. Without canonical form, identical
solutions could have different serializations, breaking dedup.

### `is_atom_canonical(clvm_buffer, offset)`

Validates a single atom's length prefix encoding. The CLVM format uses
variable-length prefixes (1-6 bytes) based on atom size. Each prefix
length has a minimum atom size threshold.
