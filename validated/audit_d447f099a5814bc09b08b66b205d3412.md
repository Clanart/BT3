### Title
Attacker-controlled `ThresholdKeys` deserialization materializes arbitrary group key and secret share without semantic validation - (File: crypto/dkg/src/lib.rs)

### Summary

The e107 bug class is "deserialization performs only a superficial format check (a prefix comparison) before evaluating stored data into a trusted object whose effects run automatically." The Serai analog is `ThresholdKeys::read` in `crypto/dkg/src/lib.rs`: it validates only the curve-ID header (the equivalent of the `'array'` prefix check), the `t/n/i` bounds via `ThresholdParams::new`, and the interpolation tag — then materializes a fully operational `ThresholdKeys` from attacker-supplied `secret_share` and `verification_shares`. Neither `read` nor `ThresholdKeys::new` ever checks that `C::generator() * secret_share == verification_shares[i]`, i.e. that the secret share actually corresponds to the participant index and verification-share set being claimed.

### Finding Description

`ThresholdKeys::read` performs these checks and nothing more:

- A curve-ID prefix check: `id_len` must equal `C::ID.len()` and `id` must equal `C::ID` — a superficial format gate exactly analogous to `e_array::unserialize()` checking only that the string starts with `'array'` (lines 575-589).
- `Participant::new` rejects index 0, and `ThresholdParams::new` enforces `t <= n` and `i <= n` (lines 166-179, 591-602).
- The interpolation byte must be 0 or 1; `ThresholdKeys::new` additionally requires `t == n` for `Constant` (lines 604-616, 368-374).
- `group_key` is then computed purely from `verification_shares[1..=t]` (lines 376-378), and `secret_share` is stored verbatim (line 384) with no consistency check against `verification_shares[i]`.

The code itself acknowledges the consequence: `AlgorithmSignatureMachine::complete` returns `InternalError("everyone had a valid share yet the signature was still invalid")` and notes "The only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys" (`crypto/frost/src/sign.rs:491-494`). So the crate authors know deserialized keys can be semantically inconsistent — but still place no binding check at the deserialization boundary.

Attack: an unprivileged party who can get serialized bytes fed to `ThresholdKeys::read` (the threat model the scan rules explicitly permit, mirroring e107's "out-of-band database write to `user_prefs`") supplies a crafted blob:

- `t = 1, n = 1, i = 1`, `Interpolation::Lagrange`, `secret_share = x` (attacker-known scalar), `verification_shares = {1: G*x}`.
- `read` returns a fully valid `ThresholdKeys` whose `group_key()` is `G*x` — a key the attacker fully controls — and every downstream API (`view`, `AlgorithmMachine::sign`/`complete`, `original_group_key`, key-registration paths that consume `group_key()`) treats it as authentic key material.

More subtly, the attacker can set `i` and `secret_share` independently of `verification_shares`, or keep the honest `verification_shares` (preserving the real `group_key`) while substituting a different `secret_share`, producing keys that "load fine" yet deterministically emit invalid signature shares — a silent corruption of signing state that surfaces only at `complete()`.

### Impact Explanation

- **Key substitution**: the deserialized keys' `group_key()` is attacker-chosen. Any consumer that derives a receive address, registers the group key, or signs with these keys operates on attacker-controlled key material. Deposits attributed to `group_key()` are spendable by the attacker, not the threshold group — funds reported received that are effectively stolen or unspendable by the legitimate operator.
- **Corrupted signing state**: with honest `verification_shares` but a mismatched `secret_share`, every signing session yields an invalid aggregate. Worse, `view()` and `sign()` succeed; the failure mode is an opaque `InternalError` after signature assembly, indistinguishable from library bugs and unblamable to any participant.
- **Automatic effect on load**: exactly like e107's `eval` firing on `e_user_pref::load()`, the mere act of materializing the stored blob — `ThresholdKeys::read` — installs the attacker's values into a live signing object; no user interaction beyond loading is required.

### Likelihood Explanation

- The check that exists (`C::ID` header) is a format gate, not an integrity or authenticity check — precisely the "prefix check before eval" pattern.
- Reachability requires a path where serialized key material crosses a trust boundary (restored backups, promoted/recovered key blobs, operator-supplied key files, or any store an attacker can write, which is the same prerequisite class as the e107 report's `PR:L` DB-write requirement). The scan scope explicitly designates untrusted bytes into `ThresholdKeys::read` as in-scope input.
- Exploitation needs no cryptographic break: with `t = n = 1` Lagrange, the interpolation factor is 1, `group_key = verification_shares[1]`, and the attacker simply embeds a self-consistent `(x, G*x)` pair they generated.

### Recommendation

- In `ThresholdKeys::read` (or `ThresholdKeys::new`), enforce the semantic invariant: reject the blob unless `C::generator() * secret_share == verification_shares[&params.i()]`. This binds the secret share to the claimed participant index and share set, the same way the e107 fix replaced the prefix check with a strict decoder.
- Consider authenticating serialized `ThresholdKeys` at rest (MAC or signature under an operator key), since deserialization alone cannot detect a wholly self-consistent attacker key set — a parity caveat to note: the scalar/point binding check fixes the *inconsistent* case; the *consistent-substitution* case requires authenticity of the blob itself.

### Proof of Concept

```rust
// Attacker generates a self-consistent key pair
let x: Zeroizing<C::F> = Zeroizing::new(C::random_nonzero_F(&mut rng));
let gx = C::generator() * x.deref();

// Crafted blob: id_len || C::ID || t=1 || n=1 || i=1 || interp=1 (Lagrange)
//             || x.to_repr() || gx.to_bytes()
let mut blob = vec![];
blob.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
blob.extend(C::ID);
blob.extend(1u16.to_le_bytes()); // t
blob.extend(1u16.to_le_bytes()); // n
blob.extend(1u16.to_le_bytes()); // i
blob.push(1);                    // Lagrange
blob.extend(x.to_repr().as_ref());        // secret_share (attacker-known)
blob.extend(gx.to_bytes().as_ref());      // verification_shares[1]

// "eval" on load: no consistency check is ever performed
let keys = ThresholdKeys::<C>::read::<&[u8]>(&mut blob.as_ref()).unwrap();
assert_eq!(keys.group_key(), gx);          // attacker-controlled group key installed
assert_eq!(keys.params().i(), Participant::new(1).unwrap());

// Variant B: honest verification_shares (real group_key) + attacker secret_share
// — read() succeeds, view()/sign() succeed, complete() deterministically fails
// with InternalError, silently corrupting the real threshold group's signing.
```

Every claim rests on observed code: the absence of any `generator() * secret_share` comparison in `ThresholdKeys::new` (lines 349-391), the header-only gate in `read` (lines 575-632), and the codebase's own admission at `crypto/frost/src/sign.rs:491-494` that semantically invalid deserialized keys are a live failure path.
