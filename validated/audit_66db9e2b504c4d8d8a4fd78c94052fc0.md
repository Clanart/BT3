Audit Report

## Title
Block-revenue-share reward distribution mints `block_reward` lamports into stake accounts without ever deducting the source amount from the vote account's `pending_delegator_rewards` / balance - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

## Summary
Under SIMD-0123 block-revenue-sharing, `deposit_delegator_rewards` transfers real lamports into a vote account and increments `VoteStateV4::pending_delegator_rewards` via `add_pending_delegator_rewards`, which only ever adds to the counter and never subtracts it [1](#0-0) . Each epoch, `calculate_block_reward` reads the vote account's full, unmodified `pending_delegator_rewards` value and computes each stake account's proportional share purely for calculation purposes, with no side effect on the vote account state [2](#0-1) , and `build_updated_stake_reward` credits that share directly into the stake account via `checked_add_lamports` [3](#0-2) .

## Finding Description
A search across `programs/vote/src/vote_state/handler.rs`, `programs/vote/src/vote_state/mod.rs`, and the `runtime/src/bank/partitioned_epoch_rewards` module found only one function that mutates `pending_delegator_rewards` — `add_pending_delegator_rewards`, which strictly adds — and no corresponding subtract/reset function or call site anywhere in `runtime/` [1](#0-0) . The capitalization bookkeeping in `distribute_epoch_rewards_in_partition` only adjusts `capitalization` for `stake_reward_lamports_minted` (inflation) and subtracts `block_reward_lamports_burned` (the failure/burn case); `block_reward_lamports_distributed` — the lamports actually minted into stake accounts via `checked_add_lamports` — is passed only to `update_epoch_rewards_sysvar` for bookkeeping/reporting purposes and is never subtracted from any account balance or added to `capitalization` to reflect the newly materialized lamports [4](#0-3) . Since `pending_delegator_rewards` is never decremented after a distribution, the same deposited pool remains fully "pending" and available to be paid out again as a full share in every subsequent epoch's `calculate_block_reward` invocation, compounding the divergence between `sum(lamports)` and `Bank::capitalization` indefinitely for any validator with active block-revenue sharing.

## Impact Explanation
This breaks the fund/accounting-correctness invariant `sum(all account lamports) == Bank::capitalization` that Agave's capitalization tracking and bank-hash computations rely on. Each epoch a nonzero block reward is distributed, real, spendable lamports are created in stake accounts (`checked_add_lamports` in `build_updated_stake_reward`) without any matching debit from the vote account or increase to `capitalization`, and because `pending_delegator_rewards` is never drawn down, the same pool re-qualifies for a fresh distribution every following epoch. This is unbacked fund creation/dilution and would trip any capitalization-consistency check during snapshot verification or bank-hash computation, matching the "false acceptance / consensus halt" and fund-theft impact categories.

## Likelihood Explanation
The flow runs automatically every epoch in which the `block_revenue_sharing` feature is active and a validator has deposited delegator rewards through the ordinary leader-fee path (`deposit_delegator_rewards`). No privileged actor, malicious peer, or race condition is required — it fires deterministically at each epoch-reward boundary for any validator using block-revenue sharing, and the effect compounds every epoch thereafter.

## Recommendation
When crediting `block_reward` to stake accounts in `build_updated_stake_reward` / the stake-storage path, symmetrically debit the same amount from the originating vote account's lamport balance and decrement `pending_delegator_rewards` by the total distributed for that vote account. Additionally, ensure `distribute_epoch_rewards_in_partition` accounts for `block_reward_lamports_distributed` in `capitalization` bookkeeping (or nets it explicitly against the vote-account debit) so `sum(lamports) == capitalization` remains an enforced invariant.

## Proof of Concept
1. Call `VoteInstruction::deposit_delegator_rewards` for a vote account, transferring `D` lamports and setting `pending_delegator_rewards = D` [5](#0-4) .
2. Let an epoch elapse with `block_revenue_sharing` active; `calculate_block_reward` computes each delegator's share of `D` based on `stake / total_active_stake` [2](#0-1) .
3. `build_updated_stake_reward`/distribution credits each computed share into the corresponding stake account's lamports via `checked_add_lamports`, while the vote account's lamport balance and `pending_delegator_rewards` remain unchanged [3](#0-2) .
4. Repeat step 2 in the following epoch: `pending_delegator_rewards` still reports `D`, so stakers are paid a second full share of `D` from the same undecremented pool, while `capitalization` was never incremented for the first distribution — demonstrating the compounding `sum(lamports)` vs. `capitalization` divergence, verifiable via a Rust integration test asserting bank capitalization consistency across two consecutive block-reward epochs on a single vote/stake pair.

```rust
/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
```
