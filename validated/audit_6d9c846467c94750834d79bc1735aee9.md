### Title
Sybil-splitting vlMGP locks inflates aggregate `_calBoosted` share via `sqrt` concavity, diluting honest referrers' boosted rewards - (File: rewards/ReferralStorage.sol)

### Summary
`updateTotalFactor` sets a referrer's `factor` to `DSMath.sqrt(getUserTotalLocked(_account))` and adds it to the global `totalBoostFactor`, and `_calBoosted` awards each referrer `BoostPoint * factor / totalBoostFactor`. Because `sqrt` is concave, splitting a fixed vlMGP amount `X` across `N` addresses (`N*sqrt(X/N) = sqrt(N)*sqrt(X) > sqrt(X)`) lets an attacker acquire a strictly larger combined numerator relative to the shared denominator `totalBoostFactor` than a single honest locker of the same total capital, whenever other referrers already contribute to `totalBoostFactor` (`T>0`).

### Finding Description
`updateTotalFactor` is called from `VLMGP.startUnlock` (and analogously on lock via `_lock`, per the `IReferralStorage(referralStorage).updateTotalFactor` pattern seen at [1](#0-0) ) whenever a user's locked vlMGP amount changes: [2](#0-1) 

`_calBoosted` computes each referrer's boosted percentage purely from its own `factor` against the *global* `totalBoostFactor`, which aggregates every registered referrer's `sqrt(lockedAmount)`: [3](#0-2) 

This boosted percentage feeds directly into referral reward math in `trigger`, which distributes real MGP token rewards to both referrer and referee: [4](#0-3) 

Both `registerCode` (permissionless, any address) and vlMGP `lock`/`lockFor` (permissionless) require no special privilege: [5](#0-4) [6](#0-5) 

Mathematically, let `T` be the pre-existing `totalBoostFactor` contributed by other (honest) referrers, and `X` be the attacker's total vlMGP capital.
- Single account: attacker factor = `sqrt(X)`, share = `sqrt(X) / (T + sqrt(X))`.
- N-way Sybil split (`X/N` each): aggregate attacker factor = `N * sqrt(X/N) = sqrt(N) * sqrt(X)`, aggregate share = `sqrt(N)*sqrt(X) / (T + sqrt(N)*sqrt(X))`.

For `k = sqrt(N) > 1` and `T > 0`, `k*a/(T+k*a) > a/(T+a)` always holds (cross-multiplying gives `k*a*T > a*T`, true since `k>1`). Thus, whenever the referral system already has other participants contributing to `totalBoostFactor` (the realistic, non-degenerate case), an attacker strictly increases their combined boosted share — and therefore their combined boosted MGP reward payout via `trigger` — by splitting identical locked capital across more Sybil-controlled referrer accounts. This simultaneously dilutes the `_calBoosted` share (and thus reward payout) of every other honest referrer in the system, since `totalBoostFactor` is a shared denominator across all participants. No existing modifier (`_onlyVlMGP`, `nonReentrant`, `whenNotPaused`) prevents this, because the exploit does not require reentrancy or privilege — it only requires normal permissionless calls to `registerCode` and `lock`/`lockFor` from multiple attacker-controlled addresses.

### Impact Explanation
This is a theft/dilution of unclaimed referral yield: honest referrers' `_calBoosted()` percentage (and hence their MGP reward payout from `trigger`) is permanently reduced whenever a Sybil attacker inflates `totalBoostFactor` disproportionately relative to their own locked principal. The attacker gains a larger-than-proportional share of the boosted reward pool for the same locked capital, effectively transferring value from honest referrers to the Sybil attacker on every `trigger` call. This matches the Immunefi "theft of unclaimed yield" impact class.

### Likelihood Explanation
- Preconditions: `totalBoostFactor` must already be non-zero from other referrers (a realistic steady-state condition in a live referral program).
- Capital needed: only gas cost for deploying/using N addresses; the total vlMGP principal locked is unchanged (attacker doesn't need extra capital, just splits existing capital).
- Feasibility: `registerCode` and `lock`/`lockFor` are both fully permissionless with no rate-limiting, minimum-lock, or per-address code restrictions found in the reviewed code.
- Repeatability: the attacker can repeat/adjust the split (increase N) at any time to further inflate their share, and can re-lock/re-split as `totalBoostFactor` from other users changes.

### Recommendation
Do not let an attacker's own aggregate boosted share benefit from concavity of `sqrt` applied per-address. Options:
- Track and cap boosted factor per unique beneficial owner (e.g., require KYC-free but Sybil-resistant identity, or aggregate by referrer's linked wallet cluster) — not generally enforceable on-chain.
- Replace the per-account `sqrt(lockedAmount)` factor model with a linear factor (`factor = lockedAmount`) so that `_calBoosted` share becomes strictly proportional to locked capital regardless of splitting (`sum(X/N) = X`, no concavity gain).
- Alternatively, keep `sqrt` but compute it once over the *sum* of amounts locked by addresses that are provably linked (impractical on-chain), or apply `sqrt` only at the `totalBoostFactor` level (e.g., `factor = lockedAmount`, and only take `sqrt` of the total pool once) rather than per-user, eliminating the incentive to split identities.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `ReferralStorage`, mock `MGP` token; initialize with a nonzero `BoostPoint` and set `totalBoostFactor` baseline `T` by having a few "honest" referrer addresses `registerCode` and `lock` some vlMGP (e.g., total `Y` MGP, contributing `sqrt(Y)` to `totalBoostFactor`).
2. Scenario A (single locker): attacker address `A1` calls `registerCode`, then `lock(X)`; call/trigger `updateTotalFactor(A1)` (via `startUnlock` or lock hook); record `_calBoosted(A1)` (exposed via a harness or computed from `factor`/`totalBoostFactor` getters).
3. Scenario B (Sybil split, N=10): reset state (or use a fresh fork/deployment with identical baseline `T`); create 10 addresses `A1..A10`, each `registerCode` then `lock(X/10)`, each triggering `updateTotalFactor`. Sum each address's `_calBoosted` value.
4. Assert `sum(_calBoosted_B) > _calBoosted_A` for identical total locked `X` and identical baseline `T > 0`, demonstrating the aggregate boosted percentage — and thus the aggregate MGP payout via a simulated `trigger()` call with a fixed `_amount` — is materially higher for the Sybil-split case.
5. Optionally show the honest referrers' `_calBoosted` value strictly decreases from baseline (before attacker) to Scenario B (after Sybil split), confirming dilution of their reward share.

    function updateTotalFactor(address _account) external override _onlyVlMGP {
        UserInfo storage userInfo = userInfos[_account];
        if (userInfo.myCode == bytes32(0)) return; // user did not activate referral feature
        
        totalBoostFactor -= userInfo.factor;
        uint256 vlMGPLockedAmoubnt = IVLMGP(vlMGP).getUserTotalLocked(_account);
        userInfo.factor = DSMath.sqrt(vlMGPLockedAmoubnt);

        totalBoostFactor += userInfo.factor;
    }
