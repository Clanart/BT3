### Title
Fee/weight estimation omits the OP_RETURN data output, producing transactions that underpay the requested fee rate - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` appends an `OP_RETURN` output when `data` is supplied, but both calls to `calculate_weight_vbytes` are passed `payments` — not the final `tx_outs` list — so the data output's weight (up to ~90 bytes / ~360 WU) is never included in the vbyte count used to derive `needed_fee` or in the `MAX_STANDARD_TX_WEIGHT` check. The built transaction therefore pays a lower effective sat/vbyte than the caller-requested `fee_per_vbyte`, analogously to the report's PNL estimation that diverges from the authoritative calculation because it omits a term.

### Finding Description
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150-256`):

1. The `OP_RETURN` output is pushed onto `tx_outs` when `data` is present (`send.rs:194-202`).
2. The weight/vbyte estimate is computed as `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (`send.rs:204`), where `calculate_weight_vbytes` builds its dummy transaction from `payments` only (`send.rs:85-93`). The already-created `tx_outs` (including the OP_RETURN output) is ignored.
3. `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) and the minimum-relay-fee check (`send.rs:211`) both use this underestimated vbytes.
4. The change path repeats the mistake: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (`send.rs:226`) again omits the OP_RETURN output, so `fee_with_change` and the change amount `input_sat - payment_sat - fee_with_change` (`send.rs:228-230`) are computed against a too-small fee target.
5. The `weight > MAX_STANDARD_TX_WEIGHT` standardness check (`send.rs:241`) uses the underestimated `weight`, so a transaction that is actually non-standard can pass.

The actual fee is `sum(inputs) - sum(outputs)` (`fee()`, `send.rs:138-141`), which equals `needed_fee` — but the real transaction is ~10-90 vbytes larger than estimated, so the realized fee rate is strictly below `fee_per_vbyte`.

### Impact Explanation
Any caller that supplies `data` produces a transaction whose effective fee rate is lower than requested and possibly below the relay minimum, even though the `TooLowFee` guard passes (the guard itself uses the underestimated vbytes). Because `needed_fee()` is exposed publicly (`send.rs:133-135`) as "the fee necessary for this transaction to achieve the fee rate specified at construction," upstream accounting that amortizes `needed_fee` across payments will consistently under-charge the true cost of carrying the data output, and transactions can stall unconfirmed or be rejected as non-standard (oversized) despite passing the library's own checks.

### Likelihood Explanation
The divergence is deterministic whenever `data` is `Some` — it does not depend on attacker-crafted edge cases, only on the presence of an OP_RETURN output. The magnitude grows with `data` length (up to 80 bytes plus output overhead), so a full-size data payload shifts the real vsize by roughly 80-90 vbytes while the fee was priced for the smaller transaction. Exploitation requires an integrator or caller that uses the `data` field; when `data` is `None` the estimate is exact.

### Recommendation
Compute weight/vbytes from the actual output list. Either move the `OP_RETURN` push before estimation and pass `tx_outs` (or an equivalent iterator including it) into `calculate_weight_vbytes`, or add the serialized size of the data output (`8 + varint(script_len) + script_len`) to the weight calculation. Apply the same fix to the change-path estimation so `fee_with_change`, the change amount, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the true transaction.

// networks/bitcoin/src/wallet/send.rs logic
// Assume: 1 input of 100_000 sats, no payments, change = Some(addr),
// data = Some(vec![0u8; 80]), fee_per_vbyte = 10.

// Step 1: tx_outs gets the OP_RETURN output (~91 bytes: 8 value + ~83 script).
// Step 2: vbytes = calculate_weight_vbytes(1, &[], None)
//         -> dummy tx has ZERO outputs. OP_RETURN output not counted.
// Step 3: needed_fee = 10 * vbytes(no-opreturn, no-change)
// Step 4: change path -> vbytes_with_change counts only the change output.
//         change = 100_000 - fee_with_change
// Result: final tx contains 2 outputs (OP_RETURN + change) but the fee
//         was priced for 1. Realized sat/vbyte < 10.
//         With a large enough data payload relative to tx size, the true
//         fee rate can fall below the relay minimum while TooLowFee
//         never triggers.
