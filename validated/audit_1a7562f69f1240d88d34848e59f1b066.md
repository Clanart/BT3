### Title
Counterparty-controlled `proofs` map causes panic (DoS) in `GeneratorPromotion::complete` - (File: crypto/dkg/promote/src/lib.rs)

### Summary
`GeneratorPromotion::complete` validates only the *length* of the peer-supplied `proofs` map (`proofs.len() == n - 1`) and that every key is `<= n`. It never checks that the map is keyed by the *other* participants. If the map contains an entry keyed under our own `params.i()` (or otherwise omits a needed participant), `proofs.get(&i).unwrap()` at line 146 panics, crashing the caller — an availability analog of CVE-2023-21877's remotely-triggered crash class, reachable from untrusted peer input.

### Finding Description
In `crypto/dkg/promote/src/lib.rs:120-167`: [1](#0-0) 

The checks are:
1. `proofs.len() == params.n() - 1` — count only, not identity of keys.
2. Each `u16::from(i) <= params.n()` — no check that `i != params.i()` and no check that every participant in `1..=n` (excluding self) is present.

The loop then iterates `1 ..= params.n()`, skips `params.i()`, and calls `proofs.get(&i).unwrap()`. A map of size `n - 1` that includes our own index necessarily omits some other participant `j`; when the loop reaches `j`, `proofs.get(&j)` returns `None` and `.unwrap()` panics.

The proof bytes themselves are fully attacker-controlled: `GeneratorProof::read` deserializes a point (`C::read_G`) and a `DLEqProof` (`DLEqProof::read`, two `read_scalar` calls) from arbitrary bytes with no authentication (lines 72-77), and the map keys are attacker-chosen `Participant` values.

### Impact Explanation
Any peer in a generator-promotion ceremony can deterministically crash every honest participant's `complete` call by supplying a well-formed `GeneratorProof` map that contains a proof keyed under the victim's own `Participant` index instead of a genuine missing party's. Since `complete` panics rather than returning `PromotionError`, the caller cannot distinguish this from a bug and cannot gracefully blame the faulty participant — the promotion session aborts by crash, denying availability of the key-promotion (and any downstream signing/rotation flow built on it). This matches the CVE class: a remote, low-complexity input causing a repeatable crash (A:H).

### Likelihood Explanation
The trigger requires only that a counterparty send a `proofs` map whose keys are valid participants but do not cover `1..=n \ {params.i()}`. All checks that precede the panic pass trivially for such input (`len == n - 1`, all keys `<= n`). No cryptographic work is needed — the attacker doesn't even need a valid DLEq proof for the substituted slot. `Participant` keys are `u16` indices fully chosen by the sender. Reachable with public/peer inputs via the `complete` API.

### Recommendation
Replace the count-only validation with exact-set validation before iterating:

```rust
// crypto/dkg/promote/src/lib.rs, in complete()
let expected: std::collections::HashSet<_> =
    (1 ..= params.n()).map(Participant).filter(|i| *i != params.i()).collect();
if proofs.keys().copied().collect::<std::collections::HashSet<_>>() != expected {
    Err(PromotionError::IncorrectAmountOfParticipants { ... })?;
}
```

Equivalently, keep the length check and additionally reject `proofs.contains_key(&params.i())`, and return `PromotionError::InvalidParticipant`/a new `MissingParticipant` variant instead of `proofs.get(&i).unwrap()` at line 146 — e.g. `let proof = proofs.get(&i).ok_or(PromotionError::InvalidParticipant { n: params.n(), participant: i })?;`.

### Proof of Concept
```rust
// Setup: 3-of-3 ThresholdKeys via dealer, we are participant 1.
let keys = dkg_dealer::key_gen::<_, Ristretto>(&mut OsRng, 3, 3).unwrap();
let our_keys = keys[&Participant::new(1).unwrap()].clone();

let (promotion, our_proof) =
    GeneratorPromotion::<_, AltGenerator<Ristretto>>::promote(&mut OsRng, our_keys);

// Attacker (or a buggy/malicious peer aggregator) supplies n - 1 = 2 proofs,
// but keys one of them under OUR index instead of participant 3's.
let mut proofs = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), our_proof);   // our own index!
proofs.insert(Participant::new(2).unwrap(), /* any GeneratorProof, e.g. peer 2's */);

// Passes both validations: len == 2 == n-1, all keys <= 3.
// Loop reaches i = 3, proofs.get(&Participant(3)) == None -> .unwrap() panics.
promotion.complete(&proofs); // thread panics at crypto/dkg/promote/src/lib.rs:146
```

The panic occurs deterministically at `proofs.get(&i).unwrap()` (crypto/dkg/promote/src/lib.rs:146) for any `proofs` map of size `n - 1` whose keys do not equal `{1..=n} \ {params.i()}`.
