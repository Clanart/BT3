### Title
Missing zero-value validation for `kip71.gastarget` governance parameter causes division-by-zero panic in base fee calculation - (File: `kaiax/gov/param.go`, `params/kip71_config.go`)

### Summary
The `Kip71GasTarget` governance parameter uses `noopFormatChecker`, which performs no validation on the submitted value, unlike its sibling parameter `Kip71BaseFeeDenominator` which explicitly rejects zero (`v != 0`). `GasTarget` is later used as a divisor in `KIP71Config.NextMagmaBlockBaseFee`, which computes every block's base fee (KIP-71/Magma dynamic gas pricing). A governance vote setting `kip71.gastarget` to `0` would cause a division-by-zero panic on every subsequent block whose gas usage differs from the target.

### Finding Description
`Kip71GasTarget` is defined with a no-op format checker that always returns `true`, meaning any `uint64` value, including `0`, passes validation: [1](#0-0) 

By contrast, `Kip71BaseFeeDenominator`, which is used the same way (as a divisor) in the same function, explicitly guards against a zero value both at the vote-format-check layer and defensively inside `NextMagmaBlockBaseFee`: [2](#0-1) [3](#0-2) 

`GasTarget`, however, has no equivalent runtime fallback. It is used directly as a `big.Int` divisor in both the "gas used above target" and "gas used below target" branches of `NextMagmaBlockBaseFee`: [4](#0-3) 

If `gasTarget == 0` and `parentGasUsed != 0` (i.e., `parentGasUsed != gasTarget`), the code enters one of the branches and executes `x.Div(x, new(big.Int).SetUint64(gasTarget))`, which panics on division by zero in Go's `math/big` package.

Votes on `kip71.gastarget` are accepted through the standard header-governance voting path (`NewVoteData`), which only checks `Canonicalizer` and `FormatChecker` — both of which accept `0` for this parameter: [5](#0-4) 

`NextMagmaBlockBaseFee` / `VerifyMagmaHeader` is invoked from core consensus-critical paths including block validation, block assembly (worker), the transaction pool, and gas price estimation, so a governance-set `GasTarget = 0` would be evaluated by every full node processing the chain.

### Impact Explanation
Setting `kip71.gastarget` to `0` via a governance vote causes an unrecoverable panic in `NextMagmaBlockBaseFee`, which is called during block validation (`blockchain/block_validator.go`), block assembly (`work/worker.go`), transaction pool base-fee checks (`blockchain/tx_pool.go`), and gas price estimation (`node/cn/gasprice/gasprice.go`, `feehistory.go`). This would crash all validating/proposing nodes identically once the parameter takes effect and a block with `gasUsed != 0` is processed, halting the network. This is a governance-parameter-driven full-chain liveness failure rather than value theft, fund loss, or state divergence between honest nodes (since all nodes compute the same panic deterministically).

### Likelihood Explanation
Governance votes require a validator/governing-node to submit the vote, so this is not exploitable by an arbitrary unprivileged transaction sender — it requires access to the governance voting mechanism (an allowed analog category per the review scope, but with reduced likelihood since it needs a validator or the governing node to cast/approve the vote, depending on the chain's `GovernanceMode`). No additional safety net exists once the vote passes: unlike `BaseFeeDenominator`, there is no fallback default for `GasTarget == 0` inside `NextMagmaBlockBaseFee`.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally `Kip71MaxBlockGasUsedForBaseFee`, which also participates in the same computation via `min(parentGasUsed, upperGasLimit)`) that rejects `0`, mirroring the `Kip71BaseFeeDenominator` check (`v != 0`). Additionally, add a defensive fallback in `NextMagmaBlockBaseFee` (similar to the existing `baseFeeDenominator` zero-guard) so that `gasTarget == 0` cannot reach the `big.Int.Div` call regardless of how the value was introduced (vote, genesis config, or direct chain-config edit).

### Proof of Concept
1. Submit/approve a governance vote setting `kip71.gastarget` to `0` (accepted because `noopFormatChecker` always returns true, per `kaiax/gov/param.go` lines 324-334, and `NewVoteData` in `kaiax/gov/headergov/vote.go` performs no additional validation).
2. Once the vote takes effect at the target epoch/block, any subsequent block whose `GasUsed != 0` (virtually every real block) triggers `NextMagmaBlockBaseFee` in `params/kip71_config.go`.
3. Since `parentGasUsed (>0) != gasTarget (0)`, execution enters the `parentGasUsed > gasTarget` branch and calls `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` with a zero-value `big.Int`, causing `big.Int.Div` to panic (`division by zero`).
4. All nodes computing/verifying the next base fee (block validator, worker, tx pool, gas price oracle) panic identically, halting block production/validation network-wide.

func NewVoteData(voter common.Address, name string, value any) VoteData {
	param, ok := gov.Params[gov.ParamName(name)]
	if !ok {
		param, ok = gov.ValidatorParams[gov.ParamName(name)]
		if !ok {
			logger.Error("Invalid vote name", "name", name)
			return nil
		}
	}

	cv, err := param.Canonicalizer(value)
	if err != nil {
		logger.Error("Canonicalize error", "name", name, "value", value, "err", err)
		return nil
	}

	if !param.FormatChecker(cv) {
		logger.Error("Format check error", "name", name, "value", value)
		return nil
	}

	return &voteData{
		voter: voter,
		name:  gov.ParamName(name),
		value: cv,
	}
}
