### Title
Unbounded per-denom loop in cast-address balance migration lets a tokenfactory denom-spammer permanently block a victim's Cosmos/EVM address association - ([File: utils/helpers/associate.go])

### Summary
The reported bug class (attacker-inflated, externally-controlled loop bound over reward tokens causing unbounded gas and permanent inability to complete a state-changing operation) maps to `AssociationHelper.MigrateBalance` in sei-chain. This function is invoked from the ante-handler pipeline on essentially every first-time-associated address, and iterates over `SpendableCoins`, whose length is fully attacker-controlled via permissionless tokenfactory denom creation.

### Finding Description
`MigrateBalance` calls `p.bankKeeper.SpendableCoins(ctx, castAddr)` and then `SendCoins` over the full `sdk.Coins` result, with no cap on the number of distinct denominations: [1](#0-0) 

This is invoked unconditionally from `AssociateAddresses`, which itself is called from two places reachable by ordinary users:

1. `EVMPreprocessDecorator.AnteHandle` — runs for every EVM transaction from an address that is not yet associated, under an **infinite gas meter** (`ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))`): [2](#0-1) 

2. `EVMAddressDecorator.AnteHandle` — runs in the **standard Cosmos ante chain for every signed Cosmos transaction**, for every signer that is not yet associated, also unconditionally calling `MigrateBalance`: [3](#0-2) 

The "cast address" for any EVM/Sei address pair is deterministically derivable off-chain (`sdk.AccAddress(evmAddr[:])`), so an attacker can pre-compute the cast address of any target before that target ever transacts. Because `x/tokenfactory` denom creation is permissionless (`MsgCreateDenom`, `x/tokenfactory/keeper/msg_server.go`), an attacker can create an arbitrarily large number of distinct denoms and send a minimal amount of each to the target's cast address. When the target subsequently submits their very first Cosmos or EVM transaction, the ante-handler-triggered `MigrateBalance` must iterate and transfer every one of those denoms in a single atomic step before the transaction can proceed, with no bound on iteration count and (in the EVM ante path) no gas metering at all protecting against the cost.

### Impact Explanation
- If the number of spammed denoms is large enough, the account-association step becomes computationally expensive enough to either fail to complete within realistic processing time or to noticeably delay block production for every node validating/executing that transaction (a state-transition-critical, deterministic operation run by all full nodes) — a chain-wide, not just single-node, cost.
- Because association is a one-time, unavoidable, non-optional gate (an address cannot use Cosmos or EVM features on Sei without it), a victim whose cast address has been pre-polluted with enough denoms may be effectively unable to ever complete their first transaction, permanently freezing their ability to use funds sent to that Sei/EVM identity pair — directly analogous to "users may not be able to withdraw reward tokens forever" in the source report, but here applied to first-time account association/fund unlock rather than a reward claim.
- This is reachable by any unprivileged tokenfactory denom creator/public-RPC client with no special privileges, satisfying the reachable-actor requirement.

### Likelihood Explanation
Denom creation on `x/tokenfactory` is permissionless and cheap per denom (bounded by the module's creation fee/gas, not by any anti-spam limit tied to future victims). An attacker only needs to know or guess a target's EVM address (widely available for exchange deposit addresses, contract deployers, or any known public key) to precompute its cast address and begin sending funds under many denoms well in advance of the victim ever transacting. No cooperation or race condition is required, and the attack can be executed at any time before the victim's first transaction.

### Recommendation
- Cap the number of denominations migrated in a single `MigrateBalance` call (e.g., migrate only a bounded/paginated subset per invocation, or defer migration of "long-tail" denoms to a separate, gas-metered, user-initiated call).
- Alternatively, gas-meter the association/migration step even within the EVM ante's infinite-gas-meter context so a pathological number of denoms causes a bounded, attributable cost/failure rather than unbounded validator-side work.
- Consider disallowing/deprioritizing transfers of newly created tokenfactory denoms directly to un-associated cast addresses, or requiring a minimum balance/whitelist before such transfers count toward `SpendableCoins` during migration.

### Proof of Concept
1. Attacker learns or predicts a target's EVM address `E` (e.g., from a known deployer key or exchange withdrawal address) and computes `castAddr = sdk.AccAddress(E[:])`.
2. Attacker permissionlessly creates N tokenfactory denoms (`MsgCreateDenom`) and sends a minimal amount of each denom to `castAddr` (`x/tokenfactory` mint/send flow), for N large (e.g., tens of thousands).
3. Target later submits their first Cosmos-signed transaction or EVM transaction from `E`/the corresponding Sei address.
4. The ante pipeline (`EVMAddressDecorator.AnteHandle` for Cosmos txs, `EVMPreprocessDecorator.AnteHandle` for EVM txs) detects the address is unassociated and calls `AssociateAddresses` → `MigrateBalance`, which calls `SpendableCoins(ctx, castAddr)` and iterates/transfers all N denoms in one step: [1](#0-0) .
5. With sufficiently large N, this single ante-handler step becomes prohibitively expensive to execute within block-time budgets, or (in the EVM path, which uses an infinite gas meter) executes with no bound on real compute/state-write cost, blocking the target's transaction from completing and freezing their access to funds under that identity.

Note: I was unable to fully verify the concrete per-iteration cost (i.e., whether `SendCoins`/`SpendableCoins` for tokenfactory denoms triggers additional expensive per-denom logic such as hooks) within the available search budget; a Devin session with full repository access would be needed to benchmark the exact N required to cause a meaningful block-time delay.

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}

func (p *EVMPreprocessDecorator) AnteHandle(ctx sdk.Context, tx sdk.Tx, simulate bool, next sdk.AnteHandler) (sdk.Context, error) {
	msg := evmtypes.MustGetEVMTransactionMessage(tx)
	if err := Preprocess(ctx, msg, p.evmKeeper.ChainID(ctx), p.evmKeeper.EthBlockTestConfig.Enabled); err != nil {
		return ctx, err
	}

	// use infinite gas meter for EVM transaction because EVM handles gas checking from within
	ctx = ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))

	derived := msg.Derived
	seiAddr := derived.SenderSeiAddr
	evmAddr := derived.SenderEVMAddr
	ctx.EventManager().EmitEvent(sdk.NewEvent(evmtypes.EventTypeSigner,
		sdk.NewAttribute(evmtypes.AttributeKeyEvmAddress, evmAddr.Hex()),
		sdk.NewAttribute(evmtypes.AttributeKeySeiAddress, seiAddr.String())))
	pubkey := derived.PubKey
	isAssociateTx := derived.IsAssociate
	associateHelper := helpers.NewAssociationHelper(p.evmKeeper, p.evmKeeper.BankKeeper(), p.accountKeeper)
	_, isAssociated := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if isAssociateTx && isAssociated {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrInvalidRequest, "account already has association set")
	} else if isAssociateTx {
		// check if the account has enough balance (without charging)
		if !p.IsAccountBalancePositive(ctx, seiAddr, evmAddr) {
			assocErr := evmtypes.NewAssociationMissingErr(seiAddr.String())
			evmAnteMetrics.associationError.Add(ctx.Context(), 1, otelmetric.WithAttributes(attribute.String("scenario", "associate_tx_insufficient_funds"), attribute.String("type", assocErr.AddressType())))
			return ctx, sdkerrors.Wrap(sdkerrors.ErrInsufficientFunds, "account needs to have at least 1 wei to force association")
		}
		if err := associateHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false); err != nil {
			return ctx, err
		}

		return ctx.WithPriority(antedecorators.EVMAssociatePriority), nil // short-circuit without calling next
	} else if isAssociated {
		// noop; for readability
	} else {
		// not associatedTx and not already associated
		if err := associateHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false); err != nil {
			return ctx, err
		}
		if p.evmKeeper.EthReplayConfig.Enabled {
			p.evmKeeper.PrepareReplayedAddr(ctx, evmAddr)
		}
	}

//nolint:revive
func (p *EVMAddressDecorator) AnteHandle(ctx sdk.Context, tx sdk.Tx, simulate bool, next sdk.AnteHandler) (sdk.Context, error) {
	sigTx, ok := tx.(authsigning.SigVerifiableTx)
	if !ok {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrTxDecode, "invalid tx type")
	}
	signers := sigTx.GetSigners()
	for _, signer := range signers {
		if evmAddr, associated := p.evmKeeper.GetEVMAddress(ctx, signer); associated {
			ctx.EventManager().EmitEvent(sdk.NewEvent(evmtypes.EventTypeSigner,
				sdk.NewAttribute(evmtypes.AttributeKeyEvmAddress, evmAddr.Hex()),
				sdk.NewAttribute(evmtypes.AttributeKeySeiAddress, signer.String())))
			continue
		}
		acc := p.accountKeeper.GetAccount(ctx, signer)
		if acc.GetPubKey() == nil {
			logger.Error("missing pubkey for signer", "signer", signer)
			ctx.EventManager().EmitEvent(sdk.NewEvent(evmtypes.EventTypeSigner,
				sdk.NewAttribute(evmtypes.AttributeKeySeiAddress, signer.String())))
			continue
		}
		pk, err := btcec.ParsePubKey(acc.GetPubKey().Bytes())
		if err != nil {
			logger.Debug("failed to parse pubkey for account, likely due to the fact that it isn't on secp256k1 curve", "account", acc.GetPubKey(), "err", err)
			ctx.EventManager().EmitEvent(sdk.NewEvent(evmtypes.EventTypeSigner,
				sdk.NewAttribute(evmtypes.AttributeKeySeiAddress, signer.String())))
			continue
		}
		evmAddr, err := helpers.PubkeyToEVMAddress(pk.SerializeUncompressed())
		if err != nil {
			logger.Error("failed to get EVM address from pubkey", "err", err)
			ctx.EventManager().EmitEvent(sdk.NewEvent(evmtypes.EventTypeSigner,
				sdk.NewAttribute(evmtypes.AttributeKeySeiAddress, signer.String())))
			continue
		}
		ctx.EventManager().EmitEvent(sdk.NewEvent(evmtypes.EventTypeSigner,
			sdk.NewAttribute(evmtypes.AttributeKeyEvmAddress, evmAddr.Hex()),
			sdk.NewAttribute(evmtypes.AttributeKeySeiAddress, signer.String())))
		p.evmKeeper.SetAddressMapping(ctx, signer, evmAddr)
		associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.evmKeeper.BankKeeper(), p.accountKeeper)
		if err := associationHelper.MigrateBalance(ctx, evmAddr, signer, false); err != nil {
			logger.Error("failed to migrate EVM address balance", "address", evmAddr, "err", err)
			return ctx, err
		}
	}
