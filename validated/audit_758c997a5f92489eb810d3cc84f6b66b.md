## Finding

### Title
`CallDispatcher.dispatch()` has no caller/initiator restriction, letting anyone drain any funds transiently held by the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
The external report's core defect is that a callback/execution entry point does not authenticate *who* initiated the call, letting an unrelated party invoke the execution path against funds/state it shouldn't control. The local analog is `CallDispatcher.dispatch()`, an `external` function with **no access control at all** — no `onlyHost`, no `msg.sender` allow-list, nothing — even though it is the exact mechanism apps use to move funds it is currently holding.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes an array of `Call{to, value, data}` and executes each one via `to.call{value: call.value}(call.data)`, with `address(this)` (the `CallDispatcher`) as the caller context: [1](#0-0) 

There is no restriction on who may call `dispatch()`, and `receive()` is unconditionally payable: [2](#0-1) 

`CallDispatcher` is used as a shared, persistent contract across apps: `HyperFungibleToken.onAccept` mints tokens directly to the dispatcher and then invokes `dispatch(message.data)`: [3](#0-2) 

`WrappedHyperFungibleToken.onAccept` does the same with unlocked/unwrapped ERC20 or native ETH: [4](#0-3) 

and `IntentGatewayV2` routes order-input tokens (native and ERC20) into the same dispatcher address before calling `dispatch()` for the predispatch calls: [5](#0-4) 

The documentation confirms this is a single, reused, well-known address ("CALL_DISPATCHER") intended to "hold and forward native tokens" across many independent send/unlock operations: [6](#0-5) 

Because `dispatch()` has no authentication of the caller (unlike `onAccept` implementations, which are all gated by `onlyHost`/`restrict(_params.host)`, e.g. `HyperApp.onAccept` and `HostManager.onAccept`): [7](#0-6) [8](#0-7) 

any address in the world may call `CallDispatcher.dispatch()` directly with an arbitrary `Call[]` targeting `{to: <ERC20 or self>, value: <balance>, data: transfer(attacker, balance)}` — sweeping out whatever ERC20 or native balance the dispatcher currently holds, regardless of which app or chain flow put it there.

### Impact Explanation
This is an unauthenticated public entry point that can move any funds the shared `CallDispatcher` instance is holding to an arbitrary attacker-controlled address — direct theft of bridged tokens/ETH. Since multiple production apps (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2`) route beneficiary funds through the same dispatcher instance before it executes attacker-defined calldata, any window in which the dispatcher holds a nonzero balance (ETH pushed via unconditional `receive()`, ERC20 dust from a predispatch call that doesn't consume the entire balance, or tokens delivered by a reentrant/hook-bearing ERC20 mid-flow) is directly stealable by anyone racing to call `dispatch()` first.

### Likelihood Explanation
No privileged role, relayer, prover, or malicious peer is required — this is callable by any unprivileged EOA at any time the dispatcher holds a balance. The `receive()` function alone guarantees the contract can accept stray ETH from anyone, and it is a shared/reused address referenced explicitly in the SDK docs as a fixed target for multiple independent flows, increasing the chance of a nonzero balance existing at some point in its lifetime.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allow-list (e.g., only the specific `IApp`/gateway contracts authorized to use it), or make the dispatcher a strictly ephemeral, per-call, freshly-deployed contract (e.g. via `CREATE2`/minimal proxy per operation) so no state or balance can persist between unrelated calls. At minimum, pass and verify an initiator/caller identity analogous to how flashloan callbacks authenticate `msg.sender`, matching the pattern already used by `onlyHost` in `onAccept` implementations.

### Proof of Concept
1. Any user sends ETH directly to the `CallDispatcher` address (accepted unconditionally by `receive()`), or a legitimate `HyperFungibleToken`/`IntentGatewayV2` flow leaves a nonzero token/ETH balance in the dispatcher (e.g., a predispatch `Call[]` that doesn't fully drain what was transferred in).
2. An attacker calls `CallDispatcher.dispatch(abi.encode(calls))` directly (no relation to any `onAccept`/host call), where `calls = [Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, dispatcherBalance)})]` or `Call({to: attacker, value: address(dispatcher).balance, data: ""})`.
3. `dispatch()` executes the call with no check on `msg.sender`, transferring the dispatcher's balance to the attacker.

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
