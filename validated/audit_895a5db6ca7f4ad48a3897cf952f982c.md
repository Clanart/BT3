## Analysis

The Aptos report's broken invariant: a trust-boundary decision (blocklist check) silently substitutes the destination of a value transfer with an attacker/admin-controlled value instead of failing, and the caller has no way to detect or prevent it. The closest analog in GitHub Desktop is not a fund transfer but the equivalent "silent destination substitution" pattern applied to a Git remote URL: `updateRemoteUrl()` autonomously rewrites the user's `origin` remote based on unauthenticated, attacker-influenceable data (the GitHub API's `clone_url` for an owner/name pair), without any user confirmation, whenever a loose heuristic match succeeds.

### Title
Automatic Remote-URL Rewrite From GitHub API `clone_url` Can Silently Redirect Push/Fetch Destination - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
`repositoryWithRefreshedGitHubRepository()` re-resolves the owner/name of a locally tracked repository against the GitHub API on nearly every repository refresh (selecting a repo, fetching, pushing, publishing, background fetch, etc.) via `matchGitHubRepository()` + `api.fetchRepository(owner, name)`, and then calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`. That helper compares the freshly fetched `apiRepo.clone_url` against the locally configured remote and, if the protocol matches and the remote still matches the last stored `cloneURL`, silently executes `git remote set-url origin <apiRepo.clone_url>` with no user prompt or confirmation. [1](#0-0) [2](#0-1) 

### Finding Description
`matchGitHubRepository` derives `owner`/`name` purely from the shape of the existing remote URL string, and matches the account solely by hostname — there is no repository ID pinning at this stage. [3](#0-2) 

`repositoryWithRefreshedGitHubRepository` then calls `api.fetchRepository(owner, name)` and, whenever `repository.gitHubRepository` is already set, unconditionally feeds the API response into `updateRemoteUrl`: [4](#0-3) 

`updateRemoteUrl` guards the rewrite with three checks — protocol match, "remote URL still matches the *previously stored* `gitHubRepository.cloneURL`", and "current remote differs from the freshly fetched `clone_url`" — and if all three hold it calls `gitStore.setRemoteURL()`, which runs `git remote set-url origin <url>` with no user interaction: [5](#0-4) [6](#0-5) 

None of these guards validate that the *identity* of the repository at `owner/name` is unchanged — they only compare URL string shape (via `urlMatchesRemote`, which is a case-insensitive hostname/owner/name string comparison, not a repository-ID check). [7](#0-6) 

GitHub allows an `owner/name` path to be vacated (via rename, transfer, or deletion) and then reoccupied by an unrelated (attacker-controlled) repository at the same path. Once this happens, the next automatic refresh (background fetch, pull, push, or simply reselecting the repository in the sidebar — all of which route through `_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository` or `withRefreshedGitHubRepository`) will fetch the attacker's repository object from the API for that same `owner/name`, and since the user's locally configured remote still textually matches the old `cloneURL` (unchanged), Desktop will silently rewrite `origin` to the attacker's `clone_url`. [8](#0-7) [9](#0-8) 

This mirrors the Move bug's core flaw exactly: a background reconciliation routine treats a look-alike/attacker-supplied identifier as authoritative and performs an irreversible redirect (transfer destination in Move; git remote destination in Desktop) without reverting or prompting, and the existing "guard" (protocol match / previous-URL match) is a shape check, not an identity/ownership check, so it does not prevent the substitution.

### Impact Explanation
Once `origin` is silently repointed, the user's subsequent `git push` (triggered from the Desktop UI, which uses this same remote) sends their commits — and, depending on transport, credentials in the request — to the attacker-controlled repository instead of their intended one, and subsequent `git fetch`/`pull` pulls attacker-supplied history/commits into the user's local repository without any warning banner (Desktop only shows the explicit `UpstreamAlreadyExists` dialog for the upstream-fork-mismatch case, not for this default-remote auto-rewrite path). [10](#0-9) 
This is a silent corruption of what the user pushes/fetches, satisfying the described impact class (repo/remote content manipulation without user awareness).

### Likelihood Explanation
The rewrite path is reached passively and frequently: any background fetch, repository selection, publish, or explicit fetch/pull triggers `repositoryWithRefreshedGitHubRepository`/`withRefreshedGitHubRepository`, which is on the normal hot path of the application (not a rare code path). [11](#0-10) 
The precondition — an `owner/name` slot becoming available and then reoccupied by a different repository — is a normal, GitHub-permitted lifecycle event (rename/transfer/delete-then-recreate) that requires no privileged access, credential theft, or local/physical access; it only requires the attacker to control the target GitHub repository object returned for that path, matching the "attacker controls a GitHub API object" trigger described in scope.

### Recommendation
Pin repository identity across refreshes using the GitHub API's stable repository `id` (already stored on `GitHubRepository`) rather than relying solely on `owner`/`name` string matching and URL-shape comparison. `updateRemoteUrl` should refuse to auto-rewrite the remote (or should require explicit user confirmation, similar to the existing `UpstreamAlreadyExists` dialog) whenever the newly fetched `apiRepo.id` differs from the previously stored `GitHubRepository.dbID`/id, since that is a strong signal the `owner/name` path now refers to a different repository altogether.

### Proof of Concept
1. User clones `https://github.com/victim-org/example` into Desktop; Desktop stores `gitHubRepository.cloneURL` accordingly.
2. `victim-org` renames or deletes `example` (freeing the `victim-org/example` path), and an attacker creates a new repository at that same path (`https://github.com/victim-org/example`), which they control.
3. Desktop performs a routine background refresh (`startBackgroundFetching` → eventual `withRefreshedGitHubRepository`/`repositoryWithRefreshedGitHubRepository`) and calls `api.fetchRepository('victim-org', 'example')`, receiving the attacker's repository object with the attacker's `clone_url` (same string shape as before if attacker also configures the same-looking URL, which is trivially satisfied since owner/name are identical).
4. `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true` (local remote still equals the old, now-stale `cloneURL`), and `urlsMatch === false` only if the attacker's clone_url differs in host/case in some subtle way — in the common case where the attacker's repo occupies the exact same `owner/name`, the clone URL is textually identical, so no rewrite is even needed to redirect: the user is *already* pointed at the attacker's repo the moment the name is reoccupied, and any residual check in `updateRemoteUrl` provides no protection since it never validates the underlying repository ID.
5. User's next `git push`/`git fetch` in Desktop silently interacts with the attacker's repository at `origin`, corrupting the destination of pushed work without warning. [12](#0-11)

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
