### Title
Fee and weight calculation omits the OP_RETURN `data` output, producing under-priced or unbroadcastable transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` builds `tx_outs` including an OP_RETURN output carrying caller-supplied `data`, but `calculate_weight_vbytes` — which computes both the transaction `weight` used for the `MAX_STANDARD_TX_WEIGHT` check and the `vbytes` multiplied by `fee_per_vbyte` to obtain `needed_fee` — is invoked with only `payments` and `change`. The OP_RETURN output (up to 80 bytes of pushdata plus output overhead) is never included in the weight/vsize accounting. This is the same bug class as the reference finding: a total-value/size calculation that silently omits one component of the thing being measured.

### Finding Description
In `SignableTransaction::new`, the `data` argument causes an extra output to be appended to `tx_outs` at lines 194–202 of `networks/bitcoin/src/wallet/send.rs`. However, the fee/size estimate is computed at line 204 via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, and inside `calculate_weight_vbytes` (lines 68–99) the mock transaction's `output` vector is built solely from `payments` plus the optional `change` output — the `data` OP_RETURN output is never represented. The same omission occurs in the change-recomputation path at lines 225–227, which again passes only `payments` and `Some(&change)`.

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` underestimates the true serialized size by the size of the OP_RETURN output (roughly 11 + len(data) bytes of output plus witness-free weight, up to ~91+ bytes / ~364+ weight units / ~91+ vbytes). The transaction will pay a lower effective fee rate than the `fee_per_vbyte` the caller specified.
2. The `TooLowFee` guard at line 211 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the *same underestimated* `vbytes`, so a transaction can pass this check while its *actual* fee rate is below the minimum relay rate. For small transactions with a large `data` payload, the actual vsize can nearly double, cutting the effective sat/vbyte roughly in half.
3. The `TooLargeTransaction` guard at line 241 uses `weight` from the same incomplete estimate, so a transaction that is actually over `MAX_STANDARD_TX_WEIGHT` once the OP_RETURN output is serialized can be accepted and signed.

### Impact Explanation
A `SignableTransaction` constructed with `data` can be emitted whose real fee rate is lower than requested — potentially below the network's minimum relay fee — or whose real weight exceeds the standardness limit. Such a transaction will be signed by the threshold signing path (the signature itself is valid over the real sighash) yet be rejected by Bitcoin nodes on broadcast, leaving the intended spend unconfirmable and requiring reconstruction. Where the caller relies on `needed_fee()` to bound the fee, the reported fee does not cover the actual transaction size.

### Likelihood Explanation
The defect is deterministic and triggers on every call that passes `Some(data)` to `SignableTransaction::new` — no adversary cooperation is needed. It is only avoided today because the processor's `make_signable_transaction` in `processor/src/networks/bitcoin.rs` hardcodes `None` for the `data` argument; any consumer of `bitcoin-serai`'s wallet API that uses the documented `data` feature hits the miscalculation unconditionally, with the error magnitude growing with the payload size.

### Recommendation
Include the `data` OP_RETURN output in the mock transaction built by `calculate_weight_vbytes` (e.g., pass the already-constructed `tx_outs`, or append a `TxOut` with `ScriptBuf::new_op_return(...)` inside `calculate_weight_vbytes`) so that `vbytes`, `needed_fee`, the `TooLowFee` bound, and the `TooLargeTransaction` weight check all account for the data output. The change-path recomputation should likewise include it.

### Proof of Concept
From `networks/bitcoin/src/wallet/send.rs`:

```rust
// data output IS added to the real transaction
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

// ...but the size estimate does NOT include it
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` builds `tx.output` only from `payments` and `change`:

```rust
output: payments.iter().map(|payment| TxOut {
  value: Amount::from_sat(payment.1),
  script_pubkey: payment.0.clone(),
}).collect(),
```

Reproduction: call `SignableTransaction::new(inputs, &payments, None, Some(vec![0; 80]), fee_per_vbyte)` with `fee_per_vbyte` set to exactly the minimum relay rate. The function returns `Ok` (the `TooLowFee` check uses the underestimated `vbytes`), yet the resulting `tx` — which includes an ~91-byte OP_RETURN output absent from the estimate — has an actual fee rate below the minimum relay fee and will be rejected as nonstandard when broadcast. Similarly, with enough inputs/payments, `weight` can pass the `MAX_STANDARD_TX_WEIGHT` check while the real transaction exceeds it. [1](#0-0) [2](#0-1) [3](#0-2)
