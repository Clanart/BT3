### Title
Map overwrite (instead of addition) in staking-reward allocation causes silent loss of a validator's CN reward when `RewardAddr` collides with a `CLPoolAddr` - (File: kaiax/reward/impl/getter.go)

### Summary
The Sherlock finding in Flayer's `_distributeFees()` stems from a fee-split routine that assumes the "beneficiary" recipient and the "current pool" recipient are always distinct, so when they happen to coincide, part of the computed fee is silently dropped instead of being credited. The Kaia reward module has an analogous root cause: `assignStakingRewards` and `assignStakingRewardsFlex` compute a CN reward (`cnAmount`) and a Consensus-Liquidity reward (`clAmount`) for the same validator and write them into a `map[common.Address]*big.Int` using **plain key assignment (`=`)** rather than the accumulation helper (`IncRecipient`) used everywhere else in the reward spec. If a validator's `RewardAddr` and its `CLStakingInfo.CLPoolAddr` ever coincide (or collide with another validator's key in the same map), the second assignment silently overwrites the first, and the overwritten amount is lost — it was already subtracted from `remaining`/`budget` but never actually credited to any address.

### Finding Description
`assignStakingRewardsFlex` (Flex/Osaka rule) and `assignStakingRewards` (Kore/Prague rule) split a CN's staking reward between the CN reward address and its consensus-liquidity pool address: [1](#0-0) [2](#0-1) 

Both functions build the result in a local `alloc map[common.Address]*big.Int` using direct assignment:
```
alloc[cn.RewardAddr] = cnAmount
alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
```
Unlike the canonical accumulation method `RewardSpec.IncRecipient`, which explicitly adds to any existing balance for an address: [3](#0-2) 

these two functions never call `IncRecipient` while building `alloc`; the map is only merged into the final `RewardSpec` via `IncRecipient` afterward, in `getDeferredRewardFullFlex`/`getDeferredRewardFullKore`: [4](#0-3) [5](#0-4) 

By the time that merge happens, if `cn.RewardAddr == cn.CLStakingInfo.CLPoolAddr` (or an address collision occurs across different consolidated nodes' `RewardAddr`/`CLPoolAddr`), the second `alloc[...] = ...` assignment inside `assignStakingRewards[Flex]` has already clobbered the first value in the `alloc` map — only one of `cnAmount`/`clAmount` survives to be passed to `IncRecipient`. The other amount was already subtracted from `remaining`/`budget` (`remaining.Sub(remaining, reward)`), so it is deducted from the distributable pool but never paid to anyone.

`CLPoolAddr` and `RewardAddr` are independently configurable values coming from the AddressBook/CL-registry data ingested into `StakingInfo`: [6](#0-5) [7](#0-6) 

Nothing in `parseCallResult`/`parsePermissionlessCallResult` (which populate `RewardAddrs` and `CLStakingInfos` from on-chain AddressBook/CL registry contract calls) enforces that a validator's `CLPoolAddr` differs from its own `RewardAddr`, or from any other validator's `RewardAddr`: [8](#0-7) 

This mirrors the Flayer M-11 pattern precisely: a fee/reward split routine computes two conceptually distinct shares for two "recipients" that the code assumes are always different, and when the underlying identifiers coincide, one share is silently discarded rather than being folded into the surviving share.

### Impact Explanation
This causes state divergence risk and direct reward loss:
- The affected validator loses part of its legitimately earned staking/CL reward every block in which the collision persists, with no compensating credit to any party (not the proposer, not the burnt-fee accounting, not KIF/KEF/KPF).
- `RewardSpec.Validate()` only checks for negative amounts, not for total-sum invariants, so this discrepancy would not be caught by existing sanity checks and would silently corrupt the total token-supply accounting used by `kaia_getReward`/`governance_getRewardsAccumulated` APIs.
- Because reward computation must be deterministic and identical across all full nodes for consensus/state-transition correctness, any code path that depends on Go map iteration/assignment ordering combined with colliding addresses is a latent correctness bug in the reward accounting module, which is squarely in the state-transition/reward-distribution category.

### Likelihood Explanation
- The collision requires a validator (or its operator, a staker who legitimately participates in the network) to register (via the legitimate AddressBook/CL-registry contracts) a `CLPoolAddr` equal to its own `RewardAddr`, or equal to another validator's `RewardAddr`/`CLPoolAddr`. Setting these values is a standard operator action reachable without any special/privileged access beyond normal validator/staking operations — no malicious node, consensus-message tampering, or key leak is required.
- Because there is no validation anywhere in `parseCallResult`, `parsePermissionlessCallResult`, or `consolidateNodes` preventing such an address collision, the condition is trivially triggerable by any CN operator's own configuration, whether by accident or deliberately (e.g., to test/exploit the bug), making the likelihood at least moderate.

### Recommendation
Change `assignStakingRewards` and `assignStakingRewardsFlex` to accumulate rather than overwrite when building `alloc`, e.g.:
```go
addAlloc := func(addr common.Address, amt *big.Int) {
    if _, ok := alloc[addr]; !ok {
        alloc[addr] = big.NewInt(0)
    }
    alloc[addr].Add(alloc[addr], amt)
}
...
addAlloc(cn.RewardAddr, cnAmount)
addAlloc(cn.CLStakingInfo.CLPoolAddr, clAmount)
```
Additionally, consider adding a sum-invariant check in `RewardSpec.Validate()` (total distributed == minted + fee − burnt) to catch this class of accounting bug at the reward-spec level, and validating in the staking module that `CLPoolAddr` does not collide with any `RewardAddr` in the same `StakingInfo`.

### Proof of Concept
1. Construct a `StakingInfo` where a validator's `RewardAddr` (`R1`) is also used as its `CLStakingInfo.CLPoolAddr`, e.g.:
   ```go
   si := &staking.StakingInfo{
       NodeIds: []common.Address{n1}, RewardAddrs: []common.Address{r1},
       StakingContracts: []common.Address{s1}, StakingAmounts: []uint64{minStake+100},
       CLStakingInfos: staking.CLStakingInfos{{CLNodeId: n1, CLPoolAddr: r1, CLStakingAmount: 500}},
   }
   ```
2. Call `getDeferredRewardFullKore`/`getDeferredRewardFullFlex` (Prague rules active) with this `si`.
3. Inside `assignStakingRewards`, for this CN: `cnAmount, clAmount := cn.Split(reward)`; then `alloc[cn.RewardAddr] = cnAmount` followed by `alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount` — since `cn.RewardAddr == cn.CLStakingInfo.CLPoolAddr == r1`, the second write overwrites the first: `alloc[r1] == clAmount` only, `cnAmount` is lost.
4. `remaining.Sub(remaining, reward)` was already decremented by the full `reward` (`cnAmount+clAmount`), so `remaining` (returned as the "kip82Remainder"/leftover added to proposer) does not include the lost `cnAmount`, and no one ends up receiving it — the final `RewardSpec.Rewards[r1]` sums to less than the total minted+fee-burnt reward, breaking the reward-conservation invariant.
