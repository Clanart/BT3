Based on the available code, this describes a genuine design flaw, though I could not fully verify the funding mechanism for `ReferralStorage`'s MGP balance due to tool limits on this final iteration.

### Title
`trigger()` credits both referrer and referee rewards additively on top of the referee's own claim, inflating total MGP owed without a corresponding funding source - (File: rewards/ReferralStorage.sol)

### Summary
`ReferralStorage.trigger()` is called by `MasterMagpie` whenever a user claims MGP rewards via `multiclaimFor`, and it computes `refererAmount` and `refereeAmount` as percentages of the referee's `_amount` claimed, then adds both amounts as new claimable balances (`refererInfo.rewardAmount += refererAmount; refereeInfo.rewardAmount += refereeAmount;`) rather than carving them out of the amount the referee already received. [1](#0-0)  Each referred claim therefore increases total MGP owed by the protocol by `refererAmount + refereeAmount` on top of the already-paid `_amount`, with no code path in `trigger()` reducing the referee's or any other pool's balance to compensate.

### Finding Description
The call chain is: `MasterMagpie.multiclaimFor` computes `totalReward` for a user across pools, pays it out via `_sendMGP`/`_sendVlMGPFor`/`_sendMGPForVlMGPPool`, and then unconditionally calls `IReferralStorage(referral).trigger(_user, totalReward)` [2](#0-1) . Inside `trigger()`, if the claimer (`_referee`) has a registered referrer, the function computes:
```
refererPercentage = (basic + boosted) * (DENOMINATOR - sharePercent) / DENOMINATOR
refereePercentage = (basic + boosted) * sharePercent / DENOMINATOR
refererAmount = _amount * refererPercentage / DENOMINATOR
refereeAmount = _amount * refereePercentage / DENOMINATOR
``` [3](#0-2) 
Both `refererAmount` and `refereeAmount` are added to `rewardAmount` balances that are later paid out via `claimReward()`, which does a plain `MGP.safeTransfer` from `ReferralStorage`'s own token balance [4](#0-3) . Since `MGP` is a fixed-supply, non-mintable ERC20 (`Mgp.sol` mints total supply once to a recipient at deployment) [5](#0-4) , any additional `rewardAmount` credited without a matching deposit into `ReferralStorage`'s MGP balance is an unbacked IOU. `multiclaimFor` is permissionless (any address can trigger claims for any set of `_stakingTokens`/users depending on access control I could not verify further), and each claim that has an active `myReferer` mapping entry triggers this unfunded increment, so repeated claims (e.g., looping deposit/claim or using many referred accounts) scale the shortfall.

I was unable to fully confirm, due to running out of tool iterations, whether `ReferralStorage`'s MGP balance is periodically topped up by governance/admin from an emissions budget that already accounts for this referral overhead (which would mitigate but not eliminate the issue) — this should be verified against the deployment/funding scripts or admin functions before treating the insolvency as guaranteed at any point in time. However, the on-chain accounting logic itself is unambiguous: nothing in `trigger()` reduces `_amount`/`totalReward` before crediting the referral bonuses, confirming the arithmetic is additive rather than a split of the claim.

### Impact Explanation
If `ReferralStorage`'s MGP holdings are not continuously replenished at a rate matching referral accrual, `claimReward()` calls will eventually revert due to insufficient balance for legitimate referrers/referees, or — if MasterMagpie and ReferralStorage share a common MGP balance/allowance — this could let credited-but-unbacked reward claims race honest claims for the same limited MGP pool, effectively enabling first-claimers to drain funds meant for other users. This matches "Protocol insolvency" if the deficit is confirmed structurally, but the severity depends on the (unverified) funding source for `ReferralStorage`.

### Likelihood Explanation
The precondition is only that an attacker sets up a referral code, gets an account to use it (`useCode`), and then calls `multiclaimFor` for that referred account — all permissionless actions requiring no privileged role and no significant capital. Repeating this across many referred accounts/blocks scales the unbacked accrual linearly, requiring no flash loans or races, only gas.

### Recommendation
Change `trigger()` to derive `refererAmount`/`refereeAmount` as a portion of `_amount` that is deducted before/instead of being added on top (i.e., the referee's `totalReward` transferred by MasterMagpie should be reduced by the amount redirected to referral rewards, or MasterMagpie should mint/reserve the referral portion explicitly), and ensure `ReferralStorage`'s available MGP balance is provably sufficient to cover all outstanding `rewardAmount` entries (e.g., via an accounting invariant checked at `trigger()` time, or funding referral rewards from a share of `mgpPerSec` emissions rather than as a bonus on top of it).

### Proof of Concept
1. Deploy `MGP`, `MasterMagpie`, `VLMGP`, `ReferralStorage` with a small fixed `MGP` balance transferred to `ReferralStorage` (e.g., 0 or a small seed amount).
2. Register a referral code as `referrer`, have `referee` call `useCode()`.
3. Have `referee` stake into a MasterMagpie pool and accrue claimable MGP.
4. Call `MasterMagpie.multiclaimFor([stakingToken], referee, ...)` from an unprivileged EOA, repeated across multiple referred accounts/blocks.
5. Assert: sum of `userInfos[referrer].rewardAmount + userInfos[referee].rewardAmount` credited by `trigger()` exceeds `MGP.balanceOf(address(ReferralStorage))`, and that a subsequent `claimReward()` call reverts with `InsufficientRewardBalance` or an ERC20 transfer failure — demonstrating the credited liability outpaces the actual token backing.
