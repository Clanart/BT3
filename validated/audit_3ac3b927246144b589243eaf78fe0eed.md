Found a genuine analog: `GeneratedMessageLite.parseExtension` in the Java Lite runtime silently drops packed-enum repeated extension values without recording them anywhere — not even as unknown fields — once an out-of-range enum value is encountered inside a packed run, unlike the equivalent full-runtime/C++ paths which always preserve or account for the rejected/skipped data.

### Title
Packed enum extension values silently dropped mid-stream without being recorded as unknown fields (Java Lite runtime) - ([File: java/core/src/main/java/com/google/protobuf/GeneratedMessageLite.java])

### Summary
In `GeneratedMessageLite.FieldSet`'s extension parsing path (`parseExtension`), when a **packed repeated enum extension** is being decoded and an out-of-range enum value is encountered partway through the packed run, the method returns immediately (`return true;`) without popping the limit, without recording the encountered value (or the remaining unparsed bytes of the packed block) as unknown data, and without preserving the input stream position invariant. All values already read from this specific packed block before the unrecognized value are added, but the offending value and any bytes after it inside the current field are simply discarded — not written to `unknownFields`, not returned via `mergeVarintField`, not surfaced anywhere. This mirrors the DeFi report's core failure mode: input that reaches a specific validated branch (`asset == weth`) is accepted, but data that doesn't fit that branch (`msg.value` sent when `asset != weth`) is silently swallowed rather than being rejected or recorded, leaving no trace that anything was lost.

### Finding Description
`GeneratedMessageLite.parseExtension` at [1](#0-0)  decodes a packed enum extension field by looping `while (input.getBytesUntilLimit() > 0)`, reading a raw enum value each iteration, and mapping it to a value via `findValueByNumber`. When that lookup fails (`value == null`), the code does:

```java
if (value == null) {
  // If the number isn't recognized as a valid value for this
  // enum, drop it (don't even add it to unknownFields).
  return true;
}
```

This is an explicit, self-documented drop: the comment literally states "don't even add it to unknownFields." Crucially, this `return true` occurs **before** `input.popLimit(limit)` is called (line 733 in the non-error path), so the packed sub-message limit that was pushed at line 712 is left un-popped when this early return fires. The caller (`parseUnknownField`/dispatch loop in the generated message's `mergeFrom`) will continue reading from `input` with a limit still active from the abandoned packed block, silently truncating everything that comes after this field in the original wire stream for the remainder of the message — an integrity failure that is a stronger and reachable analog of "sent data not recorded."

Compare this to the equivalent non-Lite/full-runtime and C++ code paths, which never drop unmatched packed enum data without either raising it to unknown fields or explicitly rejecting the whole message:
- Full-runtime Java `MessageReflection.mergeFieldFrom` records rejected packed enum values into `unknownFields.mergeVarintField` before continuing: [2](#0-1) 
- C++ `WireFormat::_InternalParseAndMergeField` records the rejected packed enum value into `reflection->MutableUnknownFields(msg)`: [3](#0-2) 

Only the Lite-runtime extension path breaks this invariant, both by dropping the value with no record and — more seriously — by leaking the still-open packed-field byte limit, since the `popLimit` call is skipped on that return path: [4](#0-3) 

### Impact Explanation
Because the packed-field `CodedInputStream` limit is left pushed when the method returns early, subsequent field parsing in the enclosing message operates under an incorrect (too-small) byte limit for the remainder of the message. This can cause the parser to interpret bytes belonging to legitimate, later, unrelated fields as if they were still constrained inside the abandoned packed extension block, leading to premature "limit reached" truncation of the message, corrupted parsing of subsequent fields, or spurious parse failures — a data-integrity issue reachable purely from an attacker-controlled, otherwise well-formed packed enum extension payload containing a single out-of-range value that is not last in the packed run. This is a stronger and directly attacker-triggerable analog of the report's "silently dropped, unrecorded data" pattern, since it doesn't just lose data — it corrupts subsequent parsing state in a way the caller cannot detect (no exception is thrown; `parseExtension` returns `true`, signaling success).

### Likelihood Explanation
Any consuming application that (a) uses the Lite runtime (proto3 lite / Android or lite-optimized generated code), (b) registers an `ExtensionRegistryLite` with the appropriate enum extension, and (c) parses attacker-supplied bytes will trigger this path whenever a packed enum extension contains a value the enum doesn't recognize followed by more encoded varints in the same packed block. This is a bounded, single, ordinary `parseFrom`/`mergeFrom` call — no privileged access, hostile schema, or huge input required — matching the report's threat model of an ordinary client sending a bounded payload through a supported public parse API.

### Recommendation
In `GeneratedMessageLite.parseExtension`, on encountering an unrecognized packed enum value, either (a) call `input.popLimit(limit)` before returning, and record the unrecognized value plus the remaining packed bytes into unknown fields (mirroring `MessageReflection.mergeFieldFrom`'s use of `unknownFields.mergeVarintField`), or (b) continue the loop instead of returning, accumulating unrecognized values separately and popping the limit normally at loop end. The `popLimit` must always execute for any control-flow path that exits the packed-parsing loop.

### Proof of Concept
1. Define a lite proto2 message with a registered repeated enum extension, packed, with valid values `{0, 1}`.
2. Craft a wire payload for that extension field: packed length-delimited bytes containing varints `[0, 99 (invalid), 1]`, followed immediately by a subsequent, unrelated valid field belonging to the same message.
3. Call `Message.parseFrom(bytes, extensionRegistry)` where `extensionRegistry` contains the enum extension.
4. Observe: `parseExtension` reads `0` (added), then reads `99`, fails `findValueByNumber`, and returns `true` immediately — `input.popLimit(limit)` at line 733 is never executed, leaving the previously-pushed packed-field limit active.
5. Parsing of the subsequent unrelated field (step 2) will read against the stale, too-small limit, producing either a truncated/incorrect field value or an unexpected `InvalidProtocolBufferException`, depending on exact offsets — confirming both loss of the `99` value (never recorded anywhere, matching the report's "will not be recorded") and corruption of subsequent parsing (a stronger, directly demonstrable integrity failure).
