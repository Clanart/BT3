### Title
Stale in-memory working-directory status allows Copilot conflict resolution to silently overwrite a user's manual conflict fix - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`AppStore._applyCopilotConflictResolutions` is designed to avoid clobbering a file the user has manually resolved while the (long-running, async) Copilot conflict-resolution turn was in flight. It does this by checking `hasUnresolvedConflicts` against `state.changesState.workingDirectory.files`, which is an in-memory cache rather than a fresh, synchronous re-check of disk/git status at the moment of the write. If that cache is stale relative to the user's on-disk edits, the guard silently fails and the code proceeds to overwrite the user's manually-resolved file with the model's stored `resolvedContent`.

The comment above the check explicitly states the intent — "Overwriting it with Copilot's stored content would silently clobber their work, so skip it and let their resolution stand" — but the check reads from `state.changesState.workingDirectory.files`, the cached `RepositoryStateCache` snapshot, not a freshly-queried git status taken immediately before the `writeFile` call. This mirrors the original report's core defect: a value (`endBalance`/`startBalance`) that is assumed to represent "current truth" but actually reflects the wrong point in time/branch, so a guard/comparison built on it silently produces the wrong result instead of failing loudly.

The write itself uses `resolution.resolvedContent`, which was computed earlier (possibly minutes earlier, given LLM latency) via `reassembleResolvedFile`, splicing model output into the original on-disk snapshot captured when the Copilot session started: [2](#0-1) [3](#0-2) 

Because the guard relies on a state cache that may not have been refreshed since the user made their manual edit (there is no visible synchronous `git status` call in this function immediately preceding the write), the "let their resolution stand" protection is not reliably enforced.

### Impact Explanation
If the guard fails to detect the user's manual fix due to stale cache state, `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` executes and overwrites the user's already-resolved file with Copilot's (older, possibly different) resolution, and the file is then staged with `git add`: [4](#0-3) 
This is a silent corruption of what the user is about to commit/push — their intentional, hand-resolved conflict content is discarded without any warning, and a different (LLM-generated) version is committed in its place.

### Likelihood Explanation
This requires no attacker-controlled network input beyond what's already part of normal use — a merge/rebase with real conflicts (which can originate from a fetched branch/PR, i.e. attacker-influenced content) and the user briefly editing a conflicted file directly (e.g., in an external editor) while waiting for the Copilot dialog to finish, then clicking "Continue Merge" without an explicit manual override for that file. Given that resolving multi-file conflicts with an LLM is not instantaneous, and users commonly poke at files mid-merge, this is a plausible, unprivileged interaction sequence rather than a contrived edge case.

### Recommendation
- Before writing `resolution.resolvedContent` for a given path, re-read the file's current conflict-marker state directly (or perform a fresh `git status`/read of the file) rather than relying on the cached `changesState.workingDirectory.files` snapshot.
- Treat the "already resolved externally" check as authoritative only if it is computed at write-time from the actual current disk contents, not from a cache whose freshness is not guaranteed.
- Consider comparing a content hash/mtime captured when the Copilot resolution context was built against the file's current state, and skip (or re-prompt) if they differ, rather than relying solely on marker-presence heuristics.

### Proof of Concept
1. Trigger a merge/rebase with a conflicting file `foo.ts` (the conflicting branch/PR can come from a fetched remote).
2. Start the Copilot conflict-resolution flow; while it is processing, manually resolve `foo.ts` in an external editor and save (removing markers).
3. Before the app's in-memory `changesState.workingDirectory.files` cache is refreshed to reflect the manual edit, click "Continue Merge" in the Copilot results dialog without adding a manual override for `foo.ts`.
4. `_applyCopilotConflictResolutions` reads the stale cached status, `hasUnresolvedConflicts` evaluates against outdated data, the guard at lines 7250-7256 is bypassed, and `writeFile` overwrites the user's manual resolution with Copilot's stored `resolvedContent`, which is then staged via `git add`.

**Uncertainty:** I could not fully confirm (due to tool-call budget) whether `dispatcher.ts` or the surrounding call path performs a synchronous `git status`/working-directory refresh immediately before invoking `_applyCopilotConflictResolutions`, which would narrow or close this race window. This should be verified directly in `app/src/ui/dispatcher/dispatcher.ts` and the refresh logic in `app-store.ts` before treating this as fully confirmed exploitable rather than a latent race condition.
