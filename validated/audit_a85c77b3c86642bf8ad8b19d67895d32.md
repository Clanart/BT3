### Title
Copilot conflict resolution silently discards resolved content and commits leftover conflict markers when a spurious `>>>>>>>`-shaped line appears inside a hunk's "ours" section - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
GitHub Desktop's "Resolve with Copilot" feature uses two independently-written, non-equivalent conflict-marker parsers on the same file: `extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` (used to build the prompt sent to the model and to compute the "expected hunk count" for validation) and `reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` (used later to splice the model's per-hunk resolutions back into the on-disk file). Because these two functions decide hunk boundaries differently when a line that looks like a `>>>>>>>` marker occurs before the real `=======` separator, they can disagree on how many/which conflict blocks exist in the same file. When they disagree, the model's resolution passes validation (hunk counts match what `extractConflictHunks` found) but `reassembleResolvedFile` fails to recognize the same block as a conflict at all, silently drops the model's resolved content, and copies the raw, still-conflicted lines straight into the file that Desktop then treats as resolved and stages/commits.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) walks a conflicted file using three separate phases:
- an "ours" phase that stops only on `baseMarker` (`^\|{7}`) or `separatorMarker` (`^={7}$`) [1](#0-0) 
- an optional "base" phase that stops only on `separatorMarker`
- a "theirs" phase that stops only on `theirsMarker` (`^>{7}`) [2](#0-1) 

Crucially, the "ours"/"base" phases never test for `theirsMarker`, so a line that begins with seven `>` characters occurring before the real `=======` separator is simply absorbed as ordinary content of `oursLines`, and the hunk is only closed by whatever `>>>>>>>`-shaped line appears **after** the real separator.

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) instead does a single flat lookahead from the opening `<<<<<<<` line, and closes the block at the **first** line matching `reassemblyTheirsMarker` regardless of whether a separator has been seen yet:
```
for (let j = i + 1; j < lines.length; j++) {
  if (reassemblySeparatorMarker.test(lines[j])) { hasSeparator = true }
  else if (reassemblyTheirsMarker.test(lines[j])) { closingIndex = j; break }
}
if (!hasSeparator || closingIndex === -1) { /* treat as malformed, copy through verbatim */ }
``` [3](#0-2) 

If a `>>>>>>>`-shaped line appears in the "ours" section before the real `=======`, `reassembleResolvedFile`'s lookahead breaks on that spurious line before `hasSeparator` becomes true, so `hasSeparator` is `false` and the whole block is judged **malformed** and copied through unchanged — even though `extractConflictHunks` judged the very same block **well-formed** and generated exactly one hunk for it. The two parsers thus disagree about whether the block is a conflict at all.

`validateResolutionPaths` (`app/src/lib/copilot-conflict-resolution.ts:473-521`) only checks that the *number* of hunks returned by the model matches the count computed by `extractConflictHunks` — it never re-derives or cross-checks the count against what `reassembleResolvedFile` will actually find in the raw content. So a model resolution that is perfectly valid with respect to `extractConflictHunks`'s hunk count sails through validation, and `reassembleResolutions` (`app/src/lib/copilot-conflict-resolution.ts:609-642`) calls `reassembleResolvedFile(ctx.rawContent, raw.hunks)` on the same raw content — which now finds zero (or a different number of) well-formed blocks — and therefore never splices in the resolved content, silently leaving the original conflict-marker text in place. [4](#0-3) 

There is no guard anywhere in this pipeline that verifies the reassembled output no longer contains conflict markers before it is written to disk and staged/committed by the multi-commit-operation flow — the app trusts that "the model resolved N hunks, N matched the expected count, therefore the file is resolved."

### Impact Explanation
This is silent corruption of what the user commits: the UI reports the file as resolved by Copilot (with a plausible-looking "reasoning" string from the model), but the file actually written to disk and staged for the merge/rebase/cherry-pick still contains raw `<<<<<<<`/`=======`/`>>>>>>>` conflict-marker text mixed into program or documentation content. If the user does not manually re-diff every "resolved" file before completing the operation, this broken content gets committed and potentially pushed, breaking the build or embedding garbage/marker text in the shipped artifact — with no error, warning, or diff shown that would tip the user off, since the app's own success signal (hunk-count validation) passed. The trigger requires nothing more than a conflicting file whose contents happen to contain a line starting with seven `>` characters ahead of an actual `=======` separator — plausible in any file that itself documents or contains example git conflict markers (tutorials, patch files, generated diffs, changelog snippets, etc.), which an attacker collaborating on or contributing to a repository can deliberately craft into a branch to sabotage a victim who later resolves a conflict against it using this AI feature.

### Likelihood Explanation
Exploitation only requires the victim to (a) have a conflicting merge/rebase/cherry-pick against attacker-influenced content and (b) click the built-in "Resolve with Copilot" button — both are normal, expected user actions, not unnatural steps. The attacker does not need local access, credentials, or malware; they only need to get specific text into a file that ends up in a merge conflict (e.g., via a normal pull request). The exact reproduction requires crafting a line beginning with seven `>` characters followed by whitespace/EOL inside the "ours" side of a real conflict block, which is a narrow but realistic and fully attacker-controllable condition.

### Recommendation
- Make `reassembleResolvedFile` use the exact same state-machine/phase logic as `extractConflictHunks` (or better, have `extractConflictHunks` return hunk boundary offsets and have `reassembleResolvedFile` consume those offsets directly instead of re-parsing the file independently), so both stages always agree on hunk boundaries and counts.
- After reassembly, scan `resolvedContent` for leftover conflict-marker regexes (`^<{7}`, `^={7}$`, `^>{7}`) and treat any match as a hard failure (throw `CopilotValidationError`) rather than silently writing the content — mirroring the existing "still contains conflict markers" check already applied to individual `resolvedContent` strings at `app/src/lib/copilot-conflict-resolution.ts:444-448`, which currently only checks the model's own hunk text, not the final reassembled file.
- Surface a clear error/skip state to the user rather than silently marking the file resolved when reassembly cannot confidently match hunk boundaries.

### Proof of Concept
1. Set up a merge/rebase conflict on a file whose content is:
```
<<<<<<< HEAD
>>>>>>> spurious
=======
their change
>>>>>>> feature
```
2. Trigger "Resolve with Copilot" on this conflict. `extractConflictHunks` will report exactly 1 hunk for this file (`oursContent = ">>>>>>> spurious"`, `theirsContent = "their change"`), so the prompt sent to the model asks for 1 resolved hunk, and `validateResolutionPaths` will accept a 1-hunk response.
3. When `reassembleResolutions` calls `reassembleResolvedFile` on the same raw content, its lookahead from the opening `<<<<<<<` immediately hits the `>>>>>>> spurious` line and sets `closingIndex` before ever seeing the real `=======`, so `hasSeparator` remains `false` and the block is classified malformed. `reassembleResolvedFile` copies every line through unchanged, and `hunkIndex` never advances — the model's resolved content is discarded.
4. The resulting "resolved" file content is byte-for-byte identical to the original conflicted content (still containing all conflict markers), yet the app reports the file as successfully resolved by Copilot with the model's reasoning text, and the multi-commit-operation flow proceeds to stage/commit this broken file content.
