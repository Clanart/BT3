### Title
Attacker-forged payout OP_RETURN lets an unrelated party front a withdrawal and have an honest operator credited/reimbursed for it - (File: core/src/verifier.rs, core/src/operator.rs)

### Summary
The payout transaction's user input is signed with `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` [1](#0-0) , which only commits to input 0 and the matching output 0; the OP_RETURN output (index 2) that records the "payer" is never covered by the signature [2](#0-1) . Any unprivileged holder of the withdrawal UTXO's key/signature can therefore build and broadcast an entirely different transaction that reuses the signed input/output pair, funds the shortfall themselves, and stamps an arbitrary honest operator's xonly public key in the OP_RETURN. `update_finalized_payouts` blindly trusts that OP_RETURN byte content as the "payer" [3](#0-2) , and `validate_payer_is_operator` only compares this untrusted value against the operator's own key with no re-derivation of who actually funded the payout [4](#0-3) .

### Finding Description
The claimed binding is: `payout_payer_operator_xonly_pk (DB column, sourced from payout tx OP_RETURN) == operator who actually fronted the withdrawal shortfall in BTC`. Tracing the code shows these two are never actually tied together.

1. A withdrawing party (the attacker, fully unprivileged per the threat model) creates a dust UTXO they control and signs it with `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` — this is explicitly required/enforced: `SECP.verify_schnorr(...).wrap_err("... Ensure the signature uses SinglePlusAnyoneCanPay sighash type.")` [1](#0-0) .
2. `create_payout_txhandler` builds the payout tx with input 0 = user's dust UTXO, output 0 = user payout, output 1 = anchor, output 2 = OP_RETURN(`operator_xonly_pk`) [2](#0-1) . Under BIP-341 `SIGHASH_SINGLE|ANYONECANPAY`, only input 0's prevout and output 0 are committed to by the signature — outputs 1 and 2 (including the OP_RETURN that names the "payer") and any *additional* inputs are outside the signed message.
3. Because of this, the attacker does not need to go through any operator's gRPC endpoint at all: they can independently construct their own transaction, spend the same registered withdrawal UTXO (with the same reusable signature) into the committed user-payout output, add their own extra funding input to cover the shortfall (satisfying `is_profitable`'s value check, which only bounds amounts, not who pays them [5](#0-4) ), and set the OP_RETURN to an arbitrary honest operator O's xonly public key, then broadcast it themselves (attacker can broadcast Bitcoin transactions per the threat model).
4. Verifier's Bitcoin syncer records this transaction purely by which outpoint it spends, with no author/broadcaster tracking: `save_transaction_spent_utxos` indexes every input's `previous_output` regardless of source [6](#0-5) ; `get_payout_txs_for_withdrawal_utxos` then just joins on the registered withdrawal outpoint [7](#0-6) .
5. `update_finalized_payouts` parses whatever OP_RETURN exists in that tx and stores it as `payout_payer_operator_xonly_pk` with no check that the named operator actually authored, signed, or fronted the transaction [8](#0-7) .
6. `Operator::validate_payer_is_operator` (called from `get_reimbursement_txs`) reads this attacker-set value and compares it only to `self.signer.xonly_public_key`; on match, it happily returns the payout blockhash/kickoff txid and lets the operator's automation proceed through the full Round/Kickoff/Reimburse sequence [9](#0-8) [10](#0-9) .

Existing guards do not catch this: `is_kickoff_malicious` only checks that the *kickoff sender's* operator key matches the OP_RETURN key [11](#0-10) , which trivially holds because it's genuinely O's own automation submitting the kickoff (having been misled by step 6) — it never checks whether O actually broadcast/funded the underlying payout transaction. `is_profitable` only bounds amounts, not the source of funds. No component re-derives the funding source from the payout transaction's actual extra inputs.

### Impact Explanation
An honest operator O can be tricked into believing it fronted a withdrawal it never funded. O's automation (`get_reimbursement_txs` / `PayoutCheckerTask` / round-advance logic) is driven to submit real Round/Kickoff/Reimburse transactions and ultimately pays O's own `wallet_reimburse_address` / `operator_reimbursement_address` from the deposit's MoveToVault UTXO [12](#0-11) , while O's own BTC balance shows no debit matching the withdrawal. This is repeatable per deposit/withdrawal and against any operator whose xonly public key is known publicly (all operator keys are public protocol parameters). This matches the Critical category: "an operator reimbursed for a payout it never funded."

### Likelihood Explanation
No privileged role is required. The attacker only needs to be a normal Citrea withdrawer: they choose the withdrawal UTXO bytes and its signature (both explicitly permitted attacker capabilities), fund the shortfall themselves (their own BTC, which they will do anyway since it's their withdrawal), and broadcast a transaction directly to Bitcoin instead of using any operator's gRPC endpoint. This requires no majority hashrate, no key compromise, and no TLS interception — only standard fee-paying Bitcoin transaction construction, which is well within the described unprivileged attacker's capability. The attack is deterministic and repeatable for every withdrawal.

### Recommendation
Do not derive "which operator fronted the payout" solely from an unauthenticated OP_RETURN push in a transaction whose signature does not cover that output. Bind the payer identity to something the payer signs, e.g.: require the payout transaction to be constructed and signed under a sighash type that covers the OP_RETURN output (e.g. `SIGHASH_ALL` for the operator's own additional input(s), or a separate operator signature over the OP_RETURN commitment), or require the operator to authenticate the payout via its own gRPC `withdraw` call with a signature the aggregator verifies before the tx is even broadcast, and treat any tx not produced through that flow as unattributed/optimistic (`operator_xonly_pk = None`) rather than trusting arbitrary OP_RETURN content found on-chain.

Plan:
1. Set up two operators O (honest) and configure a raw Bitcoin RPC to act as "attacker".
2. Perform a normal deposit and register a withdrawal (`insert_withdrawal_utxo`) with a dust UTXO controlled by an attacker-owned key, signed `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY`.
3. Instead of calling O's `withdraw` gRPC, directly build a payout transaction (mirroring `create_payout_txhandler`) that: spends the dust UTXO with the pre-made signature into the committed payout output, adds an attacker-funded extra input to cover the shortfall, and sets the OP_RETURN to `O`'s `xonly_public_key`. Broadcast it via `rpc.send_raw_transaction`.
4. Mine to finality; run the verifier's finalized-block handling so `update_finalized_payouts` records `payout_payer_operator_xonly_pk = O`.
5. Assert `db.get_payout_info_from_move_txid(...).0 == Some(O.xonly_public_key)` (LHS of the broken binding) while asserting O's Bitcoin wallet balance shows no debit equal to the shortfall amount (RHS/true funder is the attacker) — the two sides diverge.
6. Call `O.get_reimbursement_txs(deposit_outpoint)` and assert it succeeds (does not error at `validate_payer_is_operator`), eventually returning a `Reimburse` tx paying `O.operator_reimbursement_address`, proving O is driven to claim reimbursement for a payout it never funded.

        input_amount: Amount,
        withdrawal_amount: Amount,
        bridge_amount_sats: Amount,
        operator_withdrawal_fee_sats: Amount,
    ) -> bool {
        // Use checked_sub to safely handle potential underflow
        let withdrawal_diff = match withdrawal_amount
            .to_sat()
            .checked_sub(input_amount.to_sat())
        {
            Some(diff) => Amount::from_sat(diff),
            None => {
                // input amount is greater than withdrawal amount, so it's profitable but doesn't make sense
                tracing::warn!(
                    "Some user gave more amount than the withdrawal amount as input for withdrawal"
                );
                return true;
            }
        };

        if withdrawal_diff > bridge_amount_sats {
            return false;
        }

        // Calculate net profit after the withdrawal using checked_sub to prevent panic
        let net_profit = match bridge_amount_sats.checked_sub(withdrawal_diff) {
            Some(profit) => profit,
            None => return false, // If underflow occurs, it's not profitable
        };

        // Net profit must be bigger than withdrawal fee.
        // net profit doesn't take into account the fees, but operator_withdrawal_fee_sats should
        net_profit >= operator_withdrawal_fee_sats
    }

        tracing::info!(

        // first check if the payer is the operator, and the kickoff is handled
        // by the PayoutCheckerTask, meaning kickoff_txid is set

                    .into());
                }
                (payout_blockhash, kickoff_txid)
            }
            _ => {
                return Err(eyre::eyre!(
                    "Payer info not found for deposit, payout blockhash: {:?}, kickoff txid: {:?}",
                    payout_blockhash,
                    kickoff_txid
                )
                .into());
            }
        };

        tracing::info!(
            "Payer xonly pk, payout blockhash and kickoff txid found and valid for own operator for the requested deposit id: {}, payer xonly pk: {:?}, payout blockhash: {:?}, kickoff txid: {:?}",
            deposit_id,
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid
        );

        Ok((payout_blockhash, kickoff_txid))

/// Creates a [`TxHandler`] for the `reimburse_tx`.
///
/// This transaction is sent by the operator if no challenge was sent, or a challenge was sent but no disprove was sent, to reimburse the operator for their payout.
///
/// # Inputs
/// 1. MoveToVaultTx: Utxo containing the deposit
/// 2. KickoffTx: Reimburse connector utxo in the kickoff
/// 3. RoundTx: Reimburse connector utxo in the round (for the given kickoff index)
///
/// # Outputs
/// 1. Reimbursement output to the operator
/// 2. Anchor output for CPFP
///
/// # Arguments
/// * `move_txhandler` - The move-to-vault transaction handler for the deposit.
/// * `round_txhandler` - The round transaction handler for the round.
/// * `kickoff_txhandler` - The kickoff transaction handler for the kickoff.
/// * `kickoff_idx` - The kickoff index of the operator's kickoff.
/// * `paramset` - Protocol parameter set.
/// * `operator_reimbursement_address` - The address to reimburse the operator.
///
/// # Returns
/// A [`TxHandler`] for the reimburse transaction, or a [`BridgeError`] if construction fails.
pub fn create_reimburse_txhandler(
    move_txhandler: &TxHandler,
    round_txhandler: &TxHandler,
    kickoff_txhandler: &TxHandler,
    kickoff_idx: usize,
    paramset: &'static ProtocolParamset,
    operator_reimbursement_address: &bitcoin::Address,
) -> Result<TxHandler, BridgeError> {
    let builder = TxHandlerBuilder::new(TransactionType::Reimburse)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::Reimburse1,
            move_txhandler.get_spendable_output(UtxoVout::DepositInMove)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::Reimburse2,
            kickoff_txhandler.get_spendable_output(UtxoVout::ReimburseInKickoff)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::OperatorSighashDefault,
            round_txhandler.get_spendable_output(UtxoVout::ReimburseInRound(
                kickoff_idx,
                paramset.num_kickoffs_per_round,
            ))?,
            builder::script::SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        );

    Ok(builder
        .add_output(UnspentTxOut::from_partial(TxOut {
            value: move_txhandler
                .get_spendable_output(UtxoVout::DepositInMove)?
                .get_prevout()
                .value,
            script_pubkey: operator_reimbursement_address.script_pubkey(),
        }))
        .add_output(UnspentTxOut::from_partial(
            builder::transaction::anchor_output(paramset.anchor_amount()),
        ))
        .finalize())
}

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    db: &Database,
    dbtx: DatabaseTransaction<'_>,
    tx: &bitcoin::Transaction,

    let txid = tx.compute_txid();

            input.previous_output.vout as i64,
        )

    }

    Ok(())
}
