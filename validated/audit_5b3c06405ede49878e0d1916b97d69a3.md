### Title
`DLEqProof::verify` accepts a forged proof for an empty statement set - (File: crypto/dleq/src/lib.rs)

### Summary
`DLEqProof::verify` checks only that `generators.len() == points.len()`, then builds the challenge from the transcript and compares it to the supplied proof scalar. When both slices are empty, no nonce or point is transcripted, so a publicly submitted `DLEqProof { c: expected_empty_challenge, s: arbitrary }` verifies successfully. `DLEqProof::read` places attacker-controlled `c` and `s` values directly into that path.

### Finding Description
The verifier does not require at least one generator/point pair before accepting a proof.

For `generators = []` and `points = []`, the loop appends nothing to the transcript after the `b"dleq"` domain separator. The expected challenge is therefore a deterministic public value. Because no `(generator, nonce, point)` statement is checked, `s` is unconstrained. An attacker can serialize `c = challenge(domain_separated_empty_transcript)` together with any scalar `s`; `DLEqProof::read` will parse it and `verify` will return `Ok(())`.

- Empty generator/point equality is the only cardinality validation: [1](#0-0) 
- No statements are appended when the slices are empty: [2](#0-1)

### Impact Explanation
A party can forge a DLEq proof for the vacuous zero-statement relation. If an integrator accepts attacker-selected generator/point vectors, this produces a proof that appears cryptographically valid without proving knowledge of any discrete logarithm. This is a forged proof rather than merely malformed input being rejected late.

### Likelihood Explanation
The attack requires a reachable verification call where the statement vectors can be empty. The proof bytes themselves are fully attacker-controlled through `DLEqProof::read`, and computing the expected empty-statement challenge requires no secret or infeasible work. Exploitability depends on whether the surrounding protocol permits an empty statement list; the primitive itself does not prevent it.

### Recommendation
Reject `generators.is_empty()` or `points.is_empty()` in `DLEqProof::verify` before transcripting. Prefer validating `!generators.is_empty() && generators.len() == points.len()` so the function only accepts proofs over at least one concrete statement. Add a regression test that deserializes a crafted proof and verifies it against empty slices.

### Proof of Concept
```rust
use transcript::{Transcript, RecommendedTranscript};
use dleq::DLEqProof;

fn forge_empty_proof<G>() -> DLEqProof<G>
where
  G: group::prime::PrimeGroup<Scalar: ff::PrimeField + zeroize::Zeroize>,
{
  // Reproduce the verifier's transcript for an empty statement list.
  let mut transcript = RecommendedTranscript::new(b"application context");
  transcript.domain_separate(b"dleq");

  // Compute the same deterministic challenge the verifier will compute.
  let c = dleq::challenge::<_, G::Scalar>(&mut transcript);

  // Any canonical s is valid because no statement constrains it.
  DLEqProof { c, s: G::Scalar::ZERO }
}
```

```rust
  pub fn verify<T: Transcript>(
    &self,
    transcript: &mut T,
    generators: &[G],
    points: &[G],
  ) -> Result<(), DLEqError> {
    if generators.len() != points.len() {
      Err(DLEqError::InvalidProof)?;
    }

    transcript.domain_separate(b"dleq");
    for (generator, point) in generators.iter().zip(points) {
      Self::verify_statement(transcript, *generator, *point, self.c, self.s);
    }

    if self.c != challenge(transcript) {
      Err(DLEqError::InvalidProof)?;
    }
```
