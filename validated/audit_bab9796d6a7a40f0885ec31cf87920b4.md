### Title
Malformed DKG commitments stored unvalidated in `CommitmentsDb` cause a processor panic when a later `VerifyBlame` unconditionally re-parses them — (File: processor/src/key_gen.rs)

### Summary

The vLLM bug class is "validate a partial property (`ndim`) but not the full shape, then crash at use." The Serai analog: per-participant DKG commitment bytes are forwarded opaquely by the coordinator, written to `CommitmentsDb` **before** validation, and later re-deserialized with `.unwrap()` inside `CoordinatorMessage::VerifyBlame` handling. A participant who submits malformed `EncryptionKeyMessage::<C, Commitments<C>>` bytes in a `Transaction::DkgCommitments` causes every processor evaluating a subsequent blame accusation to panic.

### Finding Description

In `processor/src/key_gen.rs`, on `CoordinatorMessage::Commitments`, the processor stores the raw per-participant byte blobs unconditionally, then calls `secret_share_machines`:

- `CommitmentsDb::set(txn, &id, &commitments)` stores the map at `key_gen.rs:359` before `secret_share_machines` runs at `key_gen.rs:361`.
- Inside `secret_share_machines` (`key_gen.rs:263-281`), `EncryptionKeyMessage::<_, Commitments<_>>::read(&mut commitments, params)` failing for participant `i` is turned into `ProcessorMessage::InvalidCommitments` — a graceful error — but the malformed bytes remain persisted in `CommitmentsDb`.

Later, `CoordinatorMessage::VerifyBlame` (`key_gen.rs:504-533`) loads that same DB and **unwraps** the parse:

```rust
let commitments = CommitmentsDb::get(txn, &id).unwrap();
for (i, commitments) in commitments {
  let mut commitments = commitments.as_slice();
  substrate_commitment_msgs
    .insert(i, EncryptionKeyMessage::<_, _>::read(&mut commitments, params).unwrap());
  network_commitment_msgs
    .insert(i, EncryptionKeyMessage::<_, _>::read(&mut commitments, params).unwrap());
}
```

On the coordinator side, `Transaction::DkgCommitments` (`coordinator/src/tributary/transaction.rs:275-301`) treats each participant's commitment blob as opaque `Vec<u8>` — only `commitments_len * each_commitments_len` is bounded; contents are never deserialized. So malformed inner bytes (e.g., a non-canonical point encoding failing `C::read_G`, or a truncated `SchnorrSignature`) pass through to processors untouched.

`Commitments::read` (`crypto/dkg/pedpop/src/lib.rs:110-128`) and `EncryptionKeyMessage::read` (`crypto/dkg/pedpop/src/encryption.rs:57-59`) return `Err` on such bytes — which is exactly the path that is `.unwrap()`ed at `key_gen.rs:530-532`.

Reachability: any validator can submit a `DkgCommitments` transaction containing garbage bytes for their own slot, and any validator can submit `InvalidDkgShare` (`transaction.rs:341+`) which drives the coordinator to emit `VerifyBlame`. Both are ordinary untrusted tributary messages — no threshold or collusion required.

### Impact Explanation

Any processor evaluating `VerifyBlame` for the affected key-gen session panics at the `unwrap()` on `EncryptionKeyMessage::read`. Since blame verification is executed deterministically by processors, this is a repeatable crash of the processor on demand — a denial of service mirroring the vLLM "crash the engine with a partially-validated input" impact. It also sabotages the blame protocol itself: the crash prevents `ProcessorMessage::Blame` from being produced, so a malicious participant can both poison `CommitmentsDb` and crash anyone asked to adjudicate a subsequent accusation.

### Likelihood Explanation

Requires only that a DKG session exists and that one participant submits malformed commitment bytes (kept by `CommitmentsDb::set` regardless of the `InvalidCommitments` outcome) and that any `VerifyBlame` for that session is later processed — triggerable by a single unprivileged validator submitting an `InvalidDkgShare` transaction. No honest-behavior assumptions about the attacker are needed.

Caveat I could not fully verify within the available context: whether the coordinator's accumulation layer emits `Commitments`/`VerifyBlame` messages keyed to a session even when a participant's commitment bytes were already rejected by `secret_share_machines`. The DB is written unconditionally at `key_gen.rs:359` before validation, and `VerifyBlame` reads it unconditionally at `key_gen.rs:526`, so the poisoned entry persists regardless.

### Recommendation

In `VerifyBlame` handling, replace the `.unwrap()`s on `EncryptionKeyMessage::read` (`key_gen.rs:530`, `key_gen.rs:532`) with error handling consistent with the rest of the function — e.g., return `ProcessorMessage::Blame { id, participant: i }` blaming the participant whose stored commitments fail to deserialize, or at minimum return `ProcessorMessage::Blame { id, participant: accused }` on any parse failure. Alternatively, validate `EncryptionKeyMessage` structure at `CommitmentsDb::set` time so only well-formed blobs are persisted.

### Proof of Concept

1. Validator `V` publishes `Transaction::DkgCommitments` whose `commitments[0]` blob is truncated to fewer bytes than `t` points plus a Schnorr signature require (e.g., a single zero byte). The transaction passes coordinator checks (`commitments_len * each_commitments_len` bounded only by `TRANSACTION_SIZE_LIMIT`).
2. Each processor's `CoordinatorMessage::Commitments` handler stores the blob via `CommitmentsDb::set`, then `secret_share_machines` returns `InvalidCommitments { faulty: V }` — session may fault, but the malformed bytes are persisted under that `KeyGenId`.
3. Any participant publishes `Transaction::InvalidDkgShare` accusing anyone in that session; the coordinator emits `CoordinatorMessage::VerifyBlame`.
4. The processor executes `key_gen.rs:526-533`: `CommitmentsDb::get` succeeds, and `EncryptionKeyMessage::<Ristretto, _>::read(&mut V's blob, params)` returns `Err`, hitting `.unwrap()` → panic, crashing the processor.
