### Title
Unbounded future oracle timestamp permanently poisons the per-feed monotonic floor, causing denial-of-service on price resolution - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`price-resolve` in `v0-4-market.clar` accepts a Pyth/DIA `publish-time` that lies in the future relative to `stacks-block-time` as automatically "fresh" (forcing `delta` to `u0`), then unconditionally raises the per-feed monotonic floor `last-update` to that value with no upper bound and no recovery path, exactly mirroring the CometBFT ASA-2025-001 pattern where a peer reports an inflated target height that the node cannot recover from.

### Finding Description
`oracle-timestamp-fresh` computes staleness as:
```
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
``` [1](#0-0) 

If `ts > stacks-block-time` (the reported publish time is ahead of the current Stacks block time), `delta` is forced to `u0`, which trivially satisfies `<= delta max-staleness`. There is no upper bound check rejecting timestamps that are unreasonably far in the future — only a floor (`>= ts prev`) is enforced.

`price-resolve` then unconditionally persists any accepted, newer timestamp as the new monotonic floor for that feed:
```
(if (> timestamp last-update-time)
    (map-set last-update key timestamp)
    false)
``` [2](#0-1) 

`last-update` is a bare map keyed by `{type, ident}` with no admin/governance setter or reset function anywhere in the contract — the only writer is this single `map-set` inside `price-resolve`. [3](#0-2) 

Once a single wildly-future `timestamp` (e.g. from Pyth relay jitter, DIA's ms→s conversion edge cases, or any anomalous publish-time) is accepted and written to `last-update`, every subsequent legitimate call to `price-resolve` for that feed must satisfy `(>= ts prev)` against this inflated floor. Since genuine timestamps advance in real time but the floor was jumped arbitrarily far ahead, all future price resolutions for that feed fail `oracle-timestamp-fresh` and revert with `ERR-ORACLE-INVARIANT`:
```
(asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
          ERR-ORACLE-INVARIANT)
``` [4](#0-3) 

This is the same bug class as ASA-2025-001: a single anomalous, unvalidated high value becomes the new baseline with no mechanism to detect the anomaly or recalculate/reset it, permanently blocking further legitimate progress for that feed.

### Impact Explanation
Once poisoned, every borrow, withdraw, health-check, and liquidation path that needs to price the affected asset via `price-resolve`/`price-multi-resolve` reverts with `ERR-ORACLE-INVARIANT`. Since liquidations of undercollateralized positions using that asset as collateral or debt become impossible, and users cannot exit positions denominated in that asset, this results in temporary freezing of user funds tied to that asset (and blocks liquidation of unhealthy positions, risking protocol insolvency if prices move against frozen positions in the interim). No governance function exists in this contract to reset `last-update`, so recovery requires the real-world clock/block time to catch up to the poisoned timestamp or a contract upgrade — this can persist for a long time given how far in the future a single bad `publish-time` could be.

### Likelihood Explanation
The vulnerable check accepts any `ts > stacks-block-time` as unconditionally fresh (`delta = u0`), with no sanity/ceiling check. This can be triggered either by a single malicious/compromised relay pushing one high `publish-time` through Pyth's or DIA's write path, or by ordinary clock skew between off-chain publishers and the Stacks block timestamp being large enough on one occasion. Only one anomalous write per feed is required to permanently corrupt that feed's `last-update` floor; the underlying Pyth/DIA storages do not themselves cap `publish-time` against a future bound at the market's resolve layer, so this is a code-level gap in `v0-4-market.clar`'s freshness gating rather than pure oracle data trust.

### Recommendation
Add an explicit upper-bound (ceiling) check in `oracle-timestamp-fresh` rejecting any `ts` that exceeds `stacks-block-time` by more than a small allowed clock-skew tolerance, instead of clamping `delta` to `u0`. Additionally, provide a DAO-gated administrative function to reset/repair `last-update` for a feed in case an anomalous timestamp is ever accepted, so the monotonic floor is recoverable without a contract upgrade.

### Proof of Concept
1. Pyth (or DIA) relay submits, for feed `X`, a price update with `publish-time = T_future` where `T_future` is far ahead of the current `stacks-block-time` (e.g., due to relay bug, clock skew, or a single malicious/compromised update).
2. A user or protocol call triggers `price-resolve` for feed `X` with this data. `oracle-timestamp-fresh` computes `delta = 0` (since `ts > stacks-block-time`), passes the staleness check, and passes `(>= ts prev)` because `prev` is the older legitimate floor. `map-set last-update key T_future` executes. [5](#0-4) 
3. On the next legitimate price update for feed `X`, the real `publish-time` is far less than `T_future`. `(>= ts prev)` now fails, so `oracle-timestamp-fresh` returns `false`, and `price-resolve` reverts with `ERR-ORACLE-INVARIANT` for every future call to this feed.
4. All market operations (borrow, withdraw, liquidate, health checks) referencing feed `X` now permanently revert until `stacks-block-time` naturally advances past `T_future`, freezing any positions dependent on that asset's price.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
