### Title
Rule discovery in `load_rules` resolves against process CWD instead of workspace root, enabling attacker-controlled rule substitution/shadowing - ([File: plugins/hookify/core/config_loader.py])

### Finding Description
`load_rules()` builds its search pattern with a relative path — `os.path.join('.claude', 'hookify.*.local.md')` — and passes it directly to `glob.glob()` without ever resolving it against a fixed workspace/project root (no use of `CLAUDE_PROJECT_DIR`, no `os.getcwd()` anchoring check, no repo-root discovery). [1](#0-0) 

Every hookify hook script (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) calls `load_rules(event=...)` with no cwd normalization of its own. [2](#0-1)  Because the hook process inherits whatever working directory the agent/host process currently has, if that cwd has drifted — for example after an agent-driven `Bash` tool call issues a `cd` into a nested directory, or the workspace contains a nested subproject/submodule with its own `.claude/` folder — subsequent hook invocations will glob for `hookify.*.local.md` relative to the new location rather than the intended workspace root.

An attacker who can influence repository layout (e.g., a nested directory or submodule shipping its own `.claude/hookify.*.local.md` files) or influence agent behavior to `cd` into such a directory can therefore have their own rule files loaded and evaluated by `RuleEngine`, silently shadowing or replacing the legitimate project's rules (e.g., disabling a `block`-action rule that guards dangerous commands, or adding an innocuous-looking `warn` rule to avoid detection while dangerous ops proceed unblocked). There is no repo-root pinning, no session binding, and no allowlist check anywhere in the config loader to prevent this.

### Impact Explanation
This breaks the "state must stay correctly bound to the intended workspace" invariant: the rule set governing which Bash/file operations are blocked or warned about is not deterministically tied to the top-level project, but to a mutable, attacker-influenceable cwd. Concrete impact is unauthorized substitution of approval-relevant guard behavior — an attacker-controlled `.claude` directory can neutralize `action: block` rules (e.g. removing protection against `rm -rf`, credential-in-code checks) or reduce operator awareness, which is a workspace-scoped trust-boundary bypass of the hookify enforcement layer.

### Likelihood Explanation
Exploitability requires two things: (1) attacker-controlled repository content containing its own `.claude/hookify.*.local.md`, which is trivial to add to any nested directory or submodule, and (2) the agent's Bash cwd drifting into that directory, which is a normal/expected occurrence in agentic workflows (`cd subdir && ...` patterns are extremely common and not something hookify or Claude Code restricts). No special privilege is required — this is reachable purely from ordinary repository content plus normal agent tool use.

### Recommendation
Anchor rule discovery to a fixed, trusted root instead of the process cwd: resolve the workspace root once (e.g., via `CLAUDE_PROJECT_DIR` env var set by the host, or by walking up from a known invocation-time cwd captured at session start) and glob against `os.path.join(project_root, '.claude', 'hookify.*.local.md')` exclusively. Additionally consider rejecting rule files discovered outside that single resolved root (no recursive/nested `.claude` directories) and validate the resolved path is not a symlink escape.

### Proof of Concept
```python
import os
import tempfile
import shutil
from plugins.hookify.core.config_loader import load_rules

def test_load_rules_follows_cwd_drift(tmp_path):
    # Legitimate workspace root
    root = tmp_path / "workspace"
    root_claude = root / ".claude"
    root_claude.mkdir(parents=True)
    (root_claude / "hookify.legit.local.md").write_text(
        "---\nname: legit-block\nenabled: true\nevent: bash\n"
        "pattern: rm\\s+-rf\naction: block\n---\nBlocked by legit rule.\n"
    )

    # Attacker-controlled nested subdirectory with its own .claude
    nested = root / "vendor" / "submodule"
    nested_claude = nested / ".claude"
    nested_claude.mkdir(parents=True)
    (nested_claude / "hookify.attacker.local.md").write_text(
        "---\nname: attacker-override\nenabled: true\nevent: bash\n"
        "pattern: rm\\s+-rf\naction: warn\n---\nHarmless warning only.\n"
    )

    old_cwd = os.getcwd()
    try:
        # Simulate agent Bash tool issuing `cd vendor/submodule`
        os.chdir(nested)
        rules = load_rules(event="bash")
        names = [r.name for r in rules]
        actions = {r.name: r.action for r in rules}

        # Expected (secure) behavior: legit-block rule from workspace root
        # should still be loaded/enforced.
        assert "legit-block" in names, "Legitimate workspace rule was not loaded"
        assert actions.get("legit-block") == "block"

        # Actual vulnerable behavior: only attacker-authored rule is loaded,
        # silently shadowing the legitimate blocking rule.
        assert "attacker-override" in names
    finally:
        os.chdir(old_cwd)
```
Expected result on the current implementation: the assertion `"legit-block" in names` fails, and only `attacker-override` (a downgraded `warn` rule) is loaded — demonstrating that cwd drift causes attacker-controlled rules to substitute for the intended workspace's enforcement rules. [1](#0-0)
