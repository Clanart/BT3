## Finding: Missing `--` end-of-options guard in `reset()`/`resetModeToArgs` — argument injection via crafted ref

### Summary
`app/src/lib/git/reset.ts` builds the argv for `git reset` in two different ways. The path-based function `resetPaths` and the helper `unstageAll` both correctly insert a `--` end-of-options marker before any untrusted string is placed on the command line: [1](#0-0) [2](#0-1) 

However, the plain `reset()` entrypoint (used for hard/soft/mixed reset to an arbitrary `ref`) calls `resetModeToArgs`, which places `ref` directly on the argv **without** a preceding `--`: [3](#0-2) 

### Finding Description
`resetModeToArgs` produces `['reset', '--hard', ref]`, `['reset', ref]`, or `['reset', '--soft', ref]`. If `ref` is a string that begins with `-` (e.g. a maliciously-crafted branch or tag name such as `--upload-pack=/malicious/script` or a git option like `-x`), `git` will interpret it as an option rather than as an inert revision operand, because there is no `--` separator between the reset-mode flag and `ref`. This is the exact class of argument-injection issue the codebase elsewhere defends against — note that `resetPaths` and `unstageAll` in the very same file deliberately add `--` before untrusted path lists, showing the pattern is known and intentionally applied elsewhere but omitted here.

### Impact/Likelihood caveats (uncertainty)
I could not, within the available tool budget, fully trace every call site of `reset()` in `app/src/lib/stores/app-store.ts` and `app/src/lib/stores/git-store.ts` to confirm whether `ref` values reaching this function can, in practice, be attacker-controlled repository text (e.g., a branch/tag name from a cloned/fetched repo) as opposed to internally-derived, trusted values like `'HEAD'`, `HEAD~N`, or a commit SHA resolved via `rev-parse`. This matters because:
- Git's `check-ref-format` rules restrict valid ref names, and many call sites likely pass fixed literals or SHAs rather than raw user/remote-supplied branch names.
- If the actual callers only ever pass hardcoded refs or resolved SHAs, this gap would not be reachable by attacker-controlled text, reducing/eliminating exploitability despite the missing guard.

Because of this remaining uncertainty about reachability from attacker-controlled input at the current investigation depth, this should be treated as a **defense-in-depth gap confirmed at the code level**, with exploitability contingent on further verification of `reset()` call sites.

### Recommendation
Add a `--` separator before `ref` in `resetModeToArgs`, mirroring the pattern already used in `resetPaths`/`unstageAll`:
```ts
case GitResetMode.Hard:
  return ['reset', '--hard', '--', ref]
```
This closes the gap regardless of whether current callers happen to pass only trusted values, and prevents future regressions if a caller is added that forwards branch/tag names sourced from repository content.

### Proof of Concept
A unit test analogous to `app/test/unit/git/reset-test.ts` demonstrating the issue:
```ts

await reset(repository, GitResetMode.Hard, maliciousRef)
// Expect git to fail with "unknown option" or, if a similarly-shaped option exists,

function resetModeToArgs(mode: GitResetMode, ref: string): string[] {
  switch (mode) {
    case GitResetMode.Hard:
      return ['reset', '--hard', ref]
    case GitResetMode.Mixed:
      return ['reset', ref]
    case GitResetMode.Soft:
      return ['reset', '--soft', ref]
    default:
      return assertNever(mode, `Unknown reset mode: ${mode}`)
  }
}

/** Reset with the mode to the ref. */
export async function reset(
  repository: Repository,
  mode: GitResetMode,
  ref: string
): Promise<true> {
  const args = resetModeToArgs(mode, ref)
  await git(args, repository.path, 'reset')
  return true
}
