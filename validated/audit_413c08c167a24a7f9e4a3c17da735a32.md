### Title
Deep-link `branch` parameter bypasses leading-dash stripping, enabling git argument injection during `openRepo` checkout - (File: app/src/lib/parse-app-url.ts)

### Summary
The `x-github-client://openRepo/...` deep-link handler validates the `branch` query parameter with `testForInvalidChars()` before passing it, unmodified, all the way to a `git checkout <branch>` invocation. That validator only rejects a fixed set of illegal ref characters; it does **not** strip or reject a leading `-`/`+`, unlike the sibling function `sanitizedRefName()` in the same file, which explicitly does (`.replace(/^[-\+]*/g, '')`). This mirrors the original report's root cause: two code paths that are supposed to enforce the same invariant on the same kind of value diverge, and the security-relevant path is the one missing the check.

### Finding Description
`parseAppURL()` in `app/src/lib/parse-app-url.ts` accepts an attacker-controlled `branch` query string from an `openRepo` deep link: [1](#0-0) 

It only rejects the branch if `testForInvalidChars(branch)` returns true: [2](#0-1) 

`invalidCharacterRegex` blocks control characters, `~^:?*[\|"<>`, `@{`, consecutive/leading/trailing dots, `.lock` suffix, and trailing `/`, but it has no rule against a leading `-` (or `+`). The companion function `sanitizedRefName()`, defined right next to it, explicitly strips a leading `-`/`+` after applying the same regex — showing the authors were aware that leading dashes need separate handling, but that stripping/rejection was never wired into `testForInvalidChars`, the function actually used to gate the deep-link value.

The validated `branch` value flows straight into `IOpenRepositoryFromURLAction`, then into `dispatcher.openRepositoryFromUrl` → `openBranchNameFromUrl`, which calls `checkoutLocalBranch(repository, branchName)`: [3](#0-2) 

If the branch checkout code path (in the git wrapper invoked from `checkoutLocalBranch`) constructs a `git checkout <branchName>` (or `git checkout -b <branchName> <ref>`) argument list without a `--` end-of-options separator before the ref/branch positional argument, a value like `--upload-pack=/bin/sh -c ...` or other dash-prefixed strings supplied via the deep link would be interpreted by the git CLI as an option rather than a ref name — the classic "argument injection via attacker-controlled ref name" pattern that has affected many git GUI clients. This is the exact same bug class as the report: a single missing/incomplete validation on a value that is later trusted to correlate safely with a privileged operation.

### Impact Explanation
If reachable, this allows an attacker who merely gets a victim to click a crafted `x-github-client://openRepo/...&branch=...` link to inject arguments into the underlying `git` invocation used for checkout, potentially achieving code execution or corrupting repository state, entirely without local access, admin rights, or prior compromise — matching the "attacker controls a deep link the user clicks" and "results in code execution / silent corruption" impact criteria.

### Likelihood Explanation
Medium: the missing leading-dash rejection in `testForInvalidChars` is confirmed and directly reachable from the deep-link parser used for the `openRepo` handler that is registered with the OS (`open-url` in `main.ts`). What is **not confirmed** from the available index is whether the git command wrapper that `checkoutLocalBranch`/`_checkoutBranch` ultimately calls always inserts a `--` separator before the branch argument (which would fully neutralize the injection). That file (the actual `git checkout` spawn call, e.g. under `app/src/lib/git/checkout.ts`) was not available to confirm in this pass, so the exploitability hinges on that unverified detail.

### Recommendation
Make `testForInvalidChars` (or add a dedicated check in `parseAppURL`) reject ref names beginning with `-` or `+`, matching the stripping behavior already implemented in `sanitizedRefName`, so both validators enforce the same invariant. Additionally, verify/ensure all git invocations that take a branch/ref name (checkout, branch creation, etc.) always place `--` before the ref argument as defense in depth.

### Proof of Concept
1. Craft a deep link: `x-github-client://openRepo/https://github.com/some/repo?branch=--upload-pack=%2Ftmp%2Fevil.sh`
2. `parseAppURL` accepts it because `-`/leading dash is not in `invalidCharacterRegex`, unlike `sanitizedRefName`'s explicit stripping: [4](#0-3) 
3. The action reaches `openBranchNameFromUrl` → `checkoutLocalBranch(repository, branchName)`: [5](#0-4) 
4. If the underlying git spawn does not prefix the ref with `--`, the dash-prefixed string is parsed as a git option rather than a branch name.

Note: step 4 could not be fully verified against the actual git-checkout spawn code within the available index; confirming or ruling out the `--` separator in that specific git wrapper is required to establish full exploitability.

```typescript
// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
```

```typescript
  private async openBranchNameFromUrl(

  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps

    // if the repo has a remote, fetch before switching branches to ensure
```
