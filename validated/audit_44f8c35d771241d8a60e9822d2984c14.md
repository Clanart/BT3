Based on my investigation, the closest structural analog to the "broken if/else-if chain that stops after the first check, skipping proper handling of subsequent cases" pattern is in `getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts`. It's not a literal role-revocation bug, but the same root cause — an early-exit conditional chain that trusts the first matching branch instead of applying the authoritative check — is present, and it feeds directly into an OAuth sign-in decision for a git remote that's fully attacker-controlled.

### Title
Attacker-Controlled `WWW-Authenticate` Header Bypasses GitHub-Host Verification and Triggers Enterprise Sign-In Flow for Arbitrary Remotes - (File: app/src/lib/trampoline/trampoline-credential-helper.ts)

### Summary
`getEndpointKind` classifies a git remote endpoint by walking a chain of checks (`isGist`, `isDotCom`, `isGHE`, then a loop over `wwwauth[...]` credential fields, then falling back to the authoritative `isGitHubHost(endpoint)` network probe). The `wwwauth[...]` branch short-circuits and returns `'enterprise'` purely based on a string in a header that git forwarded to the credential helper — a value that comes straight from the HTTP response of whatever server the user is talking to, with **no real verification**. This is functionally the same defect class as the reported "only the first branch is honored, later/authoritative checks are skipped" bug: the cheap, spoofable check pre-empts the strong, authoritative one (`isGitHubHost`) that exists later in the same function.

Git captures `WWW-Authenticate` response headers from the remote server and passes them to the credential helper as `wwwauth[N]=...` fields. `cred` is fully derived from what the remote server (attacker-controlled host, or a MITM/malicious proxy sitting in front of any `http(s)://` remote the user cloned/added) returned. If that value simply contains the substring `realm="GitHub"`, `getEndpointKind` returns `'enterprise'` immediately, bypassing the real `isGitHubHost(endpoint)` check that would otherwise make an authenticated request and look for GitHub-specific response signals (see the `X-GitHub-Request-Id` check pattern used elsewhere in `app/src/lib/api.ts` lines 1843-1854). No certificate, hostname, or API round-trip validation is performed for the `wwwauth` short-circuit path.

That misclassification then feeds `getCredential`: [2](#0-1)

```
...
```

Because `endpointKind` is `'enterprise'` and no account is registered against this arbitrary host, Desktop invokes `ui.promptForGitHubSignIn(endpoint)`, which — per `trampoline-ui-helper.ts` — routes non-`github.com` hostnames into `dispatcher.beginEnterpriseSignIn(cb)` and `dispatcher.setSignInEndpoint(origin)`, initiating the full GitHub Enterprise sign-in machinery (`SignInStore`, `fetchUser`, OAuth/basic-auth calls) against the attacker's `origin`, not github.com.

### Impact Explanation
This lets a malicious or compromised HTTP git remote (or a network attacker able to inject an HTTP response header on any `http://` remote) get Desktop to treat it as a GitHub Enterprise server and open the enterprise sign-in dialog scoped to that attacker's origin. Depending on which auth path is taken, this can result in the app performing OAuth/basic authentication requests carrying the app's OAuth `ClientID`/`ClientSecret` (as used elsewhere, e.g. `deleteToken` in `app/src/lib/api.ts` lines 2214-2231, or Basic-auth PAT flows) or a bearer of the user's PAT/username/password to the attacker-controlled endpoint, since the "enterprise" sign-in flow subsequently addresses requests to `endpoint`/`origin` as taken from the untrusted remote. At minimum it is a phishing/trust-confusion primitive: the user is shown GitHub-branded sign-in UI for a host that was never verified to be GitHub, which can be used to harvest PATs or trigger unwanted account/endpoint binding.

### Likelihood Explanation
Triggering this requires only that the user add/clone/fetch a git repository over HTTP(S) whose server (or an intermediary) returns a `WWW-Authenticate` header containing `realm="GitHub"` — no local access, no admin rights, no pre-existing malware, and no unnatural steps beyond adding a remote/cloning, which is exactly the normal Desktop workflow. This satisfies the "attacker controls a git remote/proxy response" impact criterion.

### Recommendation
Remove the `wwwauth[...]` short-circuit's ability to positively classify a host as `'enterprise'` without also passing the authoritative `isGitHubHost(endpoint)` check (or at minimum require the `wwwauth` heuristic to line up with a successful `isGitHubHost` probe before trusting it). At most it should be used as a hint to prioritize which prompt/copy to show, never as a substitute for validating server identity before initiating a sign-in flow or sending credentials/secrets.

### Proof of Concept
1. Attacker stands up an HTTP git server (e.g., using `git http-backend`) reachable at `http://evil.example.com/repo.git`, configured so any request receives `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim clones or adds this remote in GitHub Desktop.
3. Git invokes Desktop's credential helper (`createCredentialHelperTrampolineHandler`), forwarding `wwwauth[0]=Basic realm="GitHub"` in the credential input.
4. `getEndpointKind` returns `'enterprise'` without ever contacting `evil.example.com` to verify GitHub-ness.
5. `getCredential` sees no matching account for this endpoint and calls `ui.promptForGitHubSignIn('http://evil.example.com')`.
6. Desktop shows the "Sign in" popup and routes to `beginEnterpriseSignIn`, targeting the attacker's origin, exposing the user to a spoofed GitHub Enterprise sign-in flow scoped to the attacker's server.

Note: I was not able to fully trace what specific data (client secret vs. only PAT) is transmitted once `beginEnterpriseSignIn`/`SignInStore` proceeds against an arbitrary attacker `origin`, since that depends on which sub-flow (OAuth-in-browser vs. basic-auth PAT entry) is selected at runtime and I did not have access to run the full flow. This should be verified by a Devin session with full repo/runtime access before treating the credential-exfiltration severity as confirmed; the header-trust bypass of `isGitHubHost` itself, however, is clearly demonstrated in the code above.

```typescript
const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
```
