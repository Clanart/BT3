### Title
Unauthenticated coin sent to a PlotNFT's p2_singleton address raises an unhandled `ValueError` in `PlotNFT2Wallet.coin_added`, halting wallet sync - (File: `chia/wallet/plotnft_wallet/plotnft_wallet.py`)

### Summary
This finding is analogous to the sDAO bug class in one specific respect: an external, unprivileged actor can trigger an on-chain state (a coin arriving at a known/derivable address) that the victim's own accounting code does not validate strictly enough, and the resulting mismatch is handled by throwing an unhandled exception rather than being safely rejected/ignored. In sDAO the flaw was a business-logic/accounting check that could be desynchronized by an attacker-controlled transfer; here the analogous weak spot is the PlotNFT2 pool-reward acceptance check in `coin_added`, which only checks a 16-byte prefix of `parent_coin_info` against `GENESIS_CHALLENGE[0:16]` instead of fully validating the reward coin the way `WalletStateManager.is_pool_reward()` does.

### Finding Description
Every PlotNFT2 wallet subscribes to its own `p2_singleton_puzzle_hash`, a value that is a pure, publicly-computable function of the plotNFT's `launcher_id` (`RewardPuzzle(singleton_id=self.plotnft_id).puzzle_hash()`), so any third party can compute another user's plotNFT's p2_singleton address: [1](#0-0) 

When wallet sync sees a *new, unspent* coin whose puzzle hash matches a wallet's interested puzzle hash and it cannot be classified as `PlotNFT` coin data, `WalletStateManager.coin_added()` unconditionally forwards it to the specific wallet's `coin_added()` with no surrounding `try/except`: [2](#0-1) 

`PlotNFT2Wallet.coin_added()` handles this "unknown coin sent to my p2_singleton" case with a strict, unconditional `raise`: [3](#0-2) 

The acceptance test performed here — `coin.parent_coin_info[0:16] == GENESIS_CHALLENGE[0:16]` — is a much weaker version of the real pool-reward-coin identity check used elsewhere in the wallet (`WalletStateManager.is_pool_reward`), which recomputes the exact 32-byte `pool_parent_id(height, genesis_challenge)` for a window of recent heights and requires an exact match plus a reward-amount sanity check: [4](#0-3) 

Because a normal spend can never legitimately produce a coin whose `parent_coin_info` equals `pool_parent_id(...)` (that value is a synthetic identifier only the consensus code ever uses when farming block rewards, and is not derivable by grinding a spend in a computationally feasible way), any ordinary XCH payment sent by an unprivileged spend-bundle submitter to a target's `p2_singleton_puzzle_hash` will *always* fail the prefix check and hit the `else` branch, raising `ValueError` from inside `coin_added`.

Because the call site at `wallet_state_manager.py:1793` has no exception handling, this exception propagates out of `WalletStateManager.coin_added()` into `_add_coin_state()`, and from there into whatever wraps wallet-sync coin-state processing (`add_coin_states`/`add_states_from_peer`). Depending on how far up the call stack the exception is caught, this can abort processing of the remaining coin-state batch for that peer/sync cycle, effectively creating a spend-triggered halt of wallet transaction/coin processing for the affected user's node — until the offending coin is somehow filtered out (it cannot be, since it is a real, permanently-existing on-chain coin matching a subscribed puzzle hash).

### Impact Explanation
This is a low-cost, unauthenticated denial-of-service vector against any wallet node running a PlotNFT2 (Plot NFT) wallet: an attacker who observes a target's plotNFT launcher id (visible on-chain / in wallet RPC) can derive the `p2_singleton_puzzle_hash` and send an arbitrarily small amount of XCH to it from any coin they control. When the victim's wallet syncs and encounters that unspent coin, the wallet's own `coin_added()` handler raises unconditionally. This falls under the accepted impact category of "a spend-triggered transaction-processing halt," disrupting normal wallet operation (sync, balance updates, further coin processing) for the targeted wallet with a trivial-cost spend.

### Likelihood Explanation
High likelihood of triggering: the p2_singleton puzzle hash is deterministic and public, the attack requires only a single standard, unprivileged spend of any coin the attacker owns for a minimal amount, and the check that raises the exception is unconditional in the "coin_data is None" / non-`GENESIS_CHALLENGE`-prefix path. No special privileges, timing, or race conditions are needed. The only uncertainty is how far the exception propagates before being caught (I could not fully trace the exact caller of `_add_coin_state`/`add_coin_states` end-to-end within available time), which affects whether this halts sync entirely versus only the current coin-state batch/peer — but even the weaker outcome (dropping/failing to process a batch, per-peer retry loops) is a disruption of a legitimate spend-triggered process.

### Recommendation
In `PlotNFT2Wallet.coin_added()` (`chia/wallet/plotnft_wallet/plotnft_wallet.py:651-657`), replace the unconditional `raise ValueError` with a defensive, non-fatal handling path: log and ignore (or explicitly track as an unrelated/spam coin) any coin sent to the p2_singleton address that does not pass full pool-reward validation, mirroring the rigor of `WalletStateManager.is_pool_reward()` (exact `pool_parent_id` match across the candidate height window plus reward-amount check) rather than a partial 16-byte prefix comparison. Additionally, ensure `WalletStateManager.coin_added()` at `chia/wallet/wallet_state_manager.py:1793` wraps the per-wallet `coin_added` dispatch in exception handling so that a single misbehaving/unexpected coin cannot abort processing of an entire coin-state batch during sync.

### Proof of Concept
1. Identify a victim's PlotNFT2 wallet `launcher_id` (visible via public chain data / RPC once created).
2. Compute `p2_singleton_puzzle_hash = RewardPuzzle(singleton_id=launcher_id).puzzle_hash()` using the same public formula the wallet uses.
3. As an ordinary unprivileged wallet, submit a standard spend bundle that creates a coin of any amount with `puzzle_hash == p2_singleton_puzzle_hash` (a plain `CREATE_COIN` condition from any coin the attacker owns).
4. Once the block confirms, the victim's wallet node syncs this new coin. Because `coin.puzzle_hash` matches the wallet's `p2_singleton_puzzle_hash` but `coin.parent_coin_info` is the id of the attacker's spent coin (not matching `GENESIS_CHALLENGE[0:16]`), `PlotNFT2Wallet.coin_added()` executes the `else` branch and raises `ValueError("A non-pooling reward coin was paid to PlotNFT with id: ...")`, propagating unhandled from `WalletStateManager.coin_added()`.
