### Title
Unchecked u64 overflow in `SignableTransaction::new` payment/fee summation bypasses the insufficient-funds check, producing a signed but consensus-invalid transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` sums attacker-influenced payment amounts into `payment_sat` and adds `needed_fee` using unchecked `u64` addition (`payment_sat + needed_fee`). If the wrapped sum is small enough, the `NotEnoughFunds` check is bypassed and a transaction whose outputs exceed its inputs is constructed and handed to the FROST signing machine, which will produce valid Schnorr signatures over a transaction Bitcoin consensus will reject.

### Finding Description
In `SignableTransaction::new`, each payment amount is only validated against the dust floor (`*amount < DUST`); there is no upper bound, `MAX_MONEY` check, or overflow-checked accumulation. `payment_sat` is computed with a plain `.sum::<u64>()` and then compared via `input_sat < (payment_sat + needed_fee)`. Both the sum and the addition can wrap modulo 2^64. An attacker who supplies payments whose amounts sum to e.g. `2^64 - k` causes `payment_sat + needed_fee` to wrap to a small value, so `input_sat < wrapped_sum` is false and `TransactionError::NotEnoughFunds` is not raised even though the actual outputs far exceed the inputs. The change calculation uses `checked_sub`, which correctly yields `None`, so no change output is added — but the oversized payment outputs remain. The resulting `SignableTransaction` is passed to `TransactionSignMachine::sign`, which computes `taproot_key_spend_signature_hash` and produces real signature shares for a transaction the network can never accept.

This mirrors the reported bug class: a missing range/validity validation on a caller-supplied numeric parameter lets arithmetic produce an outcome the rest of the logic assumes impossible.

### Impact Explanation
The threshold group signs a transaction that is provably unbroadcastable (`sum(outputs) > sum(inputs)`, and individual outputs may exceed `MAX_MONEY`). Depending on the caller, this can waste a signing round on a doomed transaction, be used to grief participants into revealing signature shares for an invalid TX, and in any accounting layer that trusts `txid()`/`fee()` before broadcast, cause funds to be recorded as spent when they are not — or, conversely, reported received-but-unspendable. `fee()` itself subtracts `sum(outputs)` from `sum(inputs)` with unchecked subtraction, which panics (debug) or wraps (release) for these crafted payments, corrupting any downstream fee accounting.

### Likelihood Explanation
`payments` is a caller-supplied `&[(ScriptBuf, u64)]` with no bound on the number of entries or per-payment value beyond `>= DUST`. Crafting amounts that sum to overflow `u64` is trivial (two payments of `u64::MAX / 2 + DUST` each). Reachability depends on the integrator forwarding untrusted payment requests into `SignableTransaction::new`; within the bitcoin-serai API surface itself, no guard exists, so any consumer passing untrusted payment data is exposed.

### Recommendation
- Accumulate payments with `checked_add` / `try_fold` and reject on overflow.
- Enforce `amount <= MAX_MONEY` (21M BTC in sats) per payment and reject `Amount` values exceeding it.
- Use `payment_sat.checked_add(needed_fee)` in the `NotEnoughFunds` comparison, and use `checked_sub`/`saturating_sub` in `fee()`.

### Proof of Concept
```rust
// Two payments whose sum wraps u64
let huge = u64::MAX / 2 + DUST;
let payments = vec![
  (recipient_script.clone(), huge),
  (recipient_script.clone(), huge),
];
// payment_sat wraps to ~2*DUST; payment_sat + needed_fee stays small,
// so `input_sat < (payment_sat + needed_fee)` is false and
// TransactionError::NotEnoughFunds is skipped despite inputs << outputs.
let tx = SignableTransaction::new(inputs, &payments, Some(change), None, fee_rate);
// tx Ok(..) — a TX with ~u64::MAX sats of outputs, which every node rejects.
// TransactionSignMachine::sign still emits valid Schnorr shares for it.
// Calling tx.fee() underflows u64.
```
