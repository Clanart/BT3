### Title
Heap/index-based buffer over-read in `is_atom_canonical` CLVM atom-length-prefix parsing on attacker-controlled spend bundle data - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_atom_canonical()` parses the variable-length atom-size prefix of a serialized CLVM buffer (puzzle reveal or solution) supplied in a `SpendBundle` by reading successive bytes from `clvm_buffer` at increasing `offset` values without ever checking that `offset` stays within the buffer's length. This mirrors the CVE-2018-18481 bug class in libopencad's `ReadCHAR`: a length/tag byte determines how many additional bytes must be consumed, and the parser blindly reads that many bytes without bounds-checking against the actual buffer size, leading to an out-of-bounds read/crash on truncated/malformed input.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` inspects the leading byte to determine `prefix_len` (0–5 extra bytes) based on its high bits, then loops `prefix_len` times, each time incrementing `offset` and indexing `clvm_buffer[offset]`: [1](#0-0) 

There is no check that `offset < len(clvm_buffer)` before or during this loop. If the buffer ends immediately after (or within) the multi-byte length-prefix tag — e.g. a 1-byte buffer `b"\xc0"` that signals a 5+8-bit prefix needing one more byte that isn't present — the loop indexes past the end of `clvm_buffer`, causing an unhandled exception during parsing of attacker-supplied data.

This function is invoked from `is_clvm_canonical()`, which itself is called directly on the raw bytes of every `coin_spend.puzzle_reveal` and `coin_spend.solution` in `MempoolManager.validate_spend_bundle()`: [2](#0-1) 

`validate_spend_bundle()` is reached from `add_spend_bundle()`, which is the standard mempool-admission path for any spend bundle submitted by an unprivileged wallet/RPC caller: [3](#0-2) 

This is directly analogous to the `ReadCHAR` bug: a length-controlling byte read from untrusted input drives further byte reads without validating that the underlying buffer actually contains that many bytes.

### Impact Explanation
Any unprivileged spend-bundle submitter can trigger this by crafting a puzzle reveal or solution whose serialized bytes end exactly on (or truncate) a multi-byte atom length-prefix tag. Since `is_clvm_canonical`/`is_atom_canonical` are exercised for every coin spend during mempool admission — before signature/CLVM cost validation completes — an attacker-controlled buffer can raise an unhandled `IndexError` inside `validate_spend_bundle()`. Depending on how far up the call stack this propagates and whether it is caught, this can manifest as a spend-triggered halt of transaction processing for the mempool manager (denial of service against the "mempool admission" code path), which the rules explicitly recognize as a qualifying impact class ("a spend-triggered transaction-processing halt").

### Likelihood Explanation
Likelihood is high for reaching the vulnerable code: `is_clvm_canonical` runs unconditionally on every submitted coin spend's puzzle reveal and solution bytes as part of normal mempool validation, requiring no special privileges — only a single crafted `SpendBundle` submission (e.g. via `push_tx` RPC or peer gossip of a transaction). Constructing the specific truncated/malformed byte pattern that triggers the out-of-range index is straightforward given the documented atom-length-prefix encoding.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before each indexed read of `clvm_buffer[offset]`, raising a controlled/caught error (or returning "not canonical") whenever `offset` would exceed `len(clvm_buffer)`, mirroring the defensive length checks already used elsewhere in the codebase (e.g. `chia/full_node/full_block_utils.py`'s `skip_bytes`/`skip_list`, which explicitly compare prefix/length values against `len(buf)` before consuming). Additionally, ensure any exception raised while validating CLVM canonicality is caught in `validate_spend_bundle`/`add_spend_bundle` and translated into a `MempoolInclusionStatus.FAILED` / `Err.INVALID_COIN_SOLUTION` result rather than propagating an unhandled exception.

### Proof of Concept
```python
from chia.full_node.mempool_manager import is_atom_canonical, is_clvm_canonical

# A single byte 0xc0 signals "5 + 8 bits length prefix" (prefix_len = 1),
# meaning one more byte is expected, but the buffer has no more bytes.
truncated_buffer = bytes.fromhex("c0")

# This raises an unhandled IndexError instead of returning a clean
# "not canonical" / validation-error result:
is_atom_canonical(truncated_buffer, 0)
```
Submitting a `CoinSpend` whose `puzzle_reveal` or `solution` serializes to such a truncated buffer and pushing it as part of a `SpendBundle` via the standard mempool-admission path (`MempoolManager.add_spend_bundle` → `validate_spend_bundle` → `is_clvm_canonical(bytes(coin_spend.puzzle_reveal))`) reaches this code with attacker-controlled bytes.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```
