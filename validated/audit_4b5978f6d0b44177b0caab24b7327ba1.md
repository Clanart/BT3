### Title
Keychain user/service identity collision via unsanitized string concatenation enables cross-user keychain access - (File: `chia/daemon/keychain_server.py`)

### Summary
`KeychainServer.get_keychain_for_request()` builds a cache key for per-user/per-service `Keychain` instances by concatenating the caller-supplied `kc_user` and `kc_service` strings with no delimiter. Two different, legitimate `(user, service)` identity pairs can be crafted to produce the same concatenated string, causing the daemon to hand back (or create and later serve) the wrong cached `Keychain` object to a caller. This is the same bug class as the Apache NiFi CVE-2017-5636 issue: an untrusted identity value that feeds into an internal identity/routing decision without proper boundary handling, letting one principal be conflated with another.

`kc_user` and `kc_service` come directly from the JSON payload of a daemon-websocket request (`request["data"]`), fully controlled by whichever local client is connected to the daemon (`chia/daemon/keychain_proxy.py` `format_request()` shows these fields are simply attacker-settable strings placed into the request dict). There is no separator between `user` and `service` when forming the cache key, so distinct identity pairs such as `("ab", "cd")` and `("a", "bcd")` (or `("alice", "bob")` vs `("al", "icebob")`) collapse to the identical cache key `"abcd"`/`"alicebob"`.

Because `_alt_keychains` is a long-lived dict on the running `KeychainServer` instance, once one client establishes a keychain under a given `(user, service)` pair, any other local daemon client that crafts `kc_user`/`kc_service` to produce the same concatenated key is transparently routed to that same cached `Keychain` object — an object backed by a different, unrelated identity's key storage partition. Subsequent keychain commands (`get_all_private_keys`, `get_key_for_fingerprint`, `get_key`, `delete_key_by_fingerprint`, `add_key`, etc., all dispatched through `handle_command()` at lines 174-209) then operate on the victim identity's key material instead of the caller's own.

This mirrors the NiFi CVE-2017-5636 root cause: an externally supplied identity string is trusted to disambiguate/route a privileged operation without cryptographic separation, allowing crafted input to make the system conflate two different principals.

### Impact Explanation
This breaks the intended isolation between multiple keychain identities served by one daemon (the `kc_user`/`kc_service` partitioning exists specifically to keep different users'/services' key material separate). A local process that can talk to the daemon under one identity can force the daemon to serve it another identity's cached `Keychain`, exposing that identity's private keys via `get_all_private_keys`/`get_key_for_fingerprint`/`get_key`, or mutate/delete that identity's keys via `add_key`/`delete_key_by_fingerprint`/`delete_all_keys`. Exposure or corruption of another identity's private keys is a direct path to unauthorized signing and coin movement for that identity's wallet, which satisfies "unsigned or unauthorized coin movement."

### Likelihood Explanation
Exploitation requires only the ability to open a daemon websocket connection (the existing local daemon TLS boundary that any legitimate local RPC caller has) and to choose `kc_user`/`kc_service` string values in an otherwise ordinary keychain command — no privilege escalation, race condition, or additional bug is needed. The collision strings are trivial to construct deterministically (e.g., shift a boundary character from `service` into `user`). The main constraint is that both the victim and attacker identity must have been used against the same running daemon process so the collision entry exists in `_alt_keychains`, which is exactly the intended multi-user/multi-service use case this cache was built for.

### Recommendation
Use a collision-free composite key, e.g. a tuple `(user, service)` or a delimiter-safe encoding such as `f"{len(user)}:{user}:{service}"`, instead of naive string concatenation, when indexing `_alt_keychains`. Alternatively, key the cache with a hash of a length-prefixed encoding of both fields so no two distinct `(user, service)` pairs can ever map to the same cache entry.

### Proof of Concept
1. Client A connects to the daemon and issues `get_all_private_keys` with `kc_user="ab"`, `kc_service="cd"`. `KeychainServer` creates `Keychain(user="ab", service="cd")`, caches it under key `"abcd"`, and returns Client A's keys.
2. Client B (a different local caller) issues `get_all_private_keys` with `kc_user="a"`, `kc_service="bcd"`. The computed cache key is also `"abcd"` (`"a" + "bcd" == "ab" + "cd"`), so `get_keychain_for_request()` returns the already-cached `Keychain(user="ab", service="cd")` object instead of creating/using `Keychain(user="a", service="bcd")`.
3. Client B's `get_all_private_keys` response therefore contains Client A's private key entropy, i.e., Client B obtains Client A's private keys despite never providing Client A's actual identity strings. [1](#0-0) [2](#0-1) [3](#0-2)

```python
    def get_keychain_for_request(self, request: dict[str, Any]) -> Keychain:
        """
        Keychain instances can have user and service strings associated with them.
        The keychain backends ultimately point to the same data stores, but the user
        and service strings are used to partition those data stores. We attempt to
        maintain a mapping of user/service pairs to their corresponding Keychain.
        """
        user = request.get("kc_user", self._default_keychain.user)
        service = request.get("kc_service", self._default_keychain.service)
        if user == self._default_keychain.user and service == self._default_keychain.service:
            keychain = self._default_keychain
        else:
            key = (user or "unnamed") + (service or "")
            if key in self._alt_keychains:
                keychain = self._alt_keychains[key]
            else:
                keychain = Keychain(user=user, service=service)
                self._alt_keychains[key] = keychain
        return keychain
```

```python
    async def get_all_private_keys(self, request: dict[str, Any]) -> dict[str, Any]:
        all_keys: list[dict[str, Any]] = []
        if self.get_keychain_for_request(request).is_keyring_locked():
            return {"success": False, "error": KEYCHAIN_ERR_LOCKED}

        private_keys = self.get_keychain_for_request(request).get_all_private_keys()
        for sk, entropy in private_keys:
            all_keys.append({"pk": bytes(sk.get_g1()).hex(), "entropy": entropy.hex()})

        return {"success": True, "private_keys": all_keys}
```
