### Title
Potential unhandled assertion in mempool spend-bundle validation on crafted duplicate coin IDs - (File: chia/full_node/mempool_manager.py)

### Summary
CVE-2016-1284 is a REQUIRE/assertion-failure DoS in BIND9 triggered by crafted flag values reaching an internal invariant check that the attacker-facing input path did not fully validate beforehand. The analogous pattern in `chia-blockchain` is the bare Python `assert` in `MempoolManager.validate_spend_bundle()` that encodes an invariant about the shape of attacker-supplied data (a submitted `SpendBundle`) without it being enforced earlier by a proper `Err`-returning check.

### Finding Description
In `MempoolManager.validate_spend_bundle()`, after computing `SpendBundleConditions` (`conds`) from the Rust CLVM/BLS validator, the code builds a dict keyed by coin id from `conds.spends`, then asserts that the count matches the number of raw `CoinSpend`s in the submitted bundle: [1](#0-0) 

This assertion assumes a one-to-one relationship between `new_spend.coin_spends` (the raw list submitted by the caller) and `conds.spends` (list produced by the Rust validator, deduplicated implicitly by `coin_id` when placed into the `spend_conditions` dict). If a submitted bundle could produce two `CoinSpend` entries whose computed `coin_id` (`parent_id`, `puzzle_hash`, `amount`) collide, `conds.spends` — and hence the dict — would end up with fewer distinct keys than `len(new_spend.coin_spends)`, making the `assert` false. Since this is a bare Python `assert` (no `Err`/`ValidationError` raised), if it fires it raises an unhandled `AssertionError` inside the mempool admission path reached directly from spend-bundle submission (`add_spend_bundle` → `validate_spend_bundle`), which is invoked whenever any unprivileged client submits a spend bundle via RPC or peer transaction relay: [2](#0-1) 

The same function also contains additional bare `assert` statements enforcing implicit invariants on attacker-influenced state, e.g. `assert self.peak.timestamp is not None`: [3](#0-2) 

### Impact Explanation
If any of these invariants can be violated by a crafted spend bundle (e.g., a bundle with a computed coin-id collision that the Rust condition parser does not itself reject with a distinct `Err`), the resulting unhandled `AssertionError` would propagate out of the mempool-admission call chain. Depending on how far up the call stack it is caught, this could either fail closed for a single transaction (low impact) or, in the worst case, crash the asyncio task/loop processing incoming transactions — a spend-triggered transaction-processing halt analogous to the BIND9 daemon-exit DoS. This is a Medium-severity, reachability-from-untrusted-input concern (single submitted spend bundle), not a memory-safety or fund-theft bug.

### Likelihood Explanation
**Unverified / low-to-moderate confidence.** I could not confirm within the available index whether:
1. The Rust `validate_clvm_and_signature` / condition-generation path already rejects spend bundles containing two `CoinSpend`s with colliding computed `coin_id`s before returning `conds` (which would make this `assert` unreachable), or
2. Whether `add_spend_bundle`/`validate_spend_bundle`'s caller (in `full_node.py`, e.g. the transaction-relay/RPC handler) wraps the call in a broad `try/except Exception` that would catch and safely convert an `AssertionError` into a rejected transaction rather than crashing the node.

Both of these are plausible mitigations that are standard in Chia's consensus code, and the search for `full_node.py`'s exception handling around spend-bundle submission returned matches but I was not able to read the exact `try/except` scope before running out of iterations. Given the strict "no root cause without exact support" requirement, I cannot confirm this assert is externally reachable with unsanitized input, only that the code pattern (Python-level `assert` used as a consensus/mempool invariant on attacker-shaped data) structurally resembles the BIND9 REQUIRE-assertion bug class.

### Recommendation
- Confirm whether chia_rs's spend-bundle condition validator can produce `conds.spends` with duplicate `coin_id`s for a crafted bundle; if so, replace the bare `assert len(new_spend.coin_spends) == len(spend_conditions)` with an explicit `Err`-returning check (e.g., `Err.DUPLICATE_OUTPUT`/`Err.INVALID_SPEND_BUNDLE`) so malformed bundles are rejected via the normal `MempoolInclusionStatus.FAILED` path instead of raising.
- Audit `add_spend_bundle`/`validate_spend_bundle` callers in `chia/full_node/full_node.py` to ensure `AssertionError` is caught alongside `ValidationError`/`ValueError` around transaction ingestion, preventing any single crafted spend bundle from being able to crash or hang transaction processing.
- More broadly, audit other bare `assert` statements in `mempool_manager.py` that encode invariants over attacker-supplied `SpendBundle` data (e.g., `assert self.peak.timestamp is not None`) and convert consensus-relevant ones into proper error returns.

### Proof of Concept
Not constructed — I do not have concrete evidence of a crafted `SpendBundle` that causes `conds.spends` to contain duplicate `coin_id`s while `new_spend.coin_spends` remains longer, because the Rust-side condition parser's duplicate-coin handling was not verifiable from the indexed code. A concrete PoC would need to: (1) submit two `CoinSpend`s in a single `SpendBundle` whose `(parent_coin_info, puzzle_hash, amount)` tuples are identical (or otherwise cause `conds.spends` deduplication), and (2) observe whether `chia.full_node.mempool_manager.MempoolManager.validate_spend_bundle` raises an uncaught `AssertionError` rather than returning a `FAILED`/`Err` result. This should be verified directly against the running code rather than assumed.
