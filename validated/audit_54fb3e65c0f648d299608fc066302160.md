### Title
Incomplete Bid equality check in `senderHasDifferentWinner` allows overwriting a winning bid's terms without re-validating the "different winner" guard - (File: kaiax/auction/bid.go, kaiax/auction/impl/bid_pool.go)

### Summary
The auction bid pool enforces a "one active winning bid per sender per block" invariant using `Bid.Equals`, which only compares `BlockNumber` and `TargetTxHash`. Any other field of the bid (`Bid` amount, `To`, `Data`, `CallGasLimit`, `Nonce`) is not part of the sameness check, similarly to how JBSplitsStore's locked-split check omitted `preferClaimed`/`preferAddToBalance`.

### Finding Description
`BidPool.senderHasDifferentWinner` decides whether a new bid conflicts with the sender's already-recorded winning bid for a block: [1](#0-0) 

It uses `bid.Equals(bp.bidMap[hash])`, which is defined as: [2](#0-1) 

Because `Equals` checks only `BlockNumber` and `TargetTxHash`, a second, distinct bid (different `Bid` amount, `Data`, `CallGasLimit`, `To`, or `Nonce`) targeting the same `TargetTxHash`/`BlockNumber` is treated as "the same bid" for the purposes of `senderHasDifferentWinner`, so the sender-conflict guard is bypassed. That bid then proceeds to `insertBid`, which only re-checks the bid amount (`existingBid.Bid.Cmp(bid.Bid)`) to decide whether to replace the stored bid for that `(blockNumber, targetTxHash)` slot: [3](#0-2) 

This mirrors the reported bug class exactly: a sameness/guard check that is supposed to gate mutation of a committed value inspects only a subset of the struct's fields, so an attacker (here, the Auctioneer submitting on behalf of/alongside a searcher) can submit a "same" bid (per the incomplete `Equals`) that actually carries different `Data`, `To`, `CallGasLimit`, or `Nonce` while only needing a marginally higher `Bid` amount to have it silently swapped in as the block's winning bid for that target transaction.

### Impact Explanation
Because `To`, `Data`, `CallGasLimit`, and `Nonce` are not part of the equality check, a bid that appears "the same" to the sender-guard can actually encode a completely different action to execute right after the target transaction (per KIP-249 auction semantics). This allows the recorded winning bid for a slot to be swapped for one with different call data/target while bypassing the guard intended to prevent a sender from having conflicting/multiple entries recognized as distinct competing bids. Combined with the low bar of only needing `bid.Bid.Cmp(existingBid.Bid) > 0` in `insertBid`, this enables settlement-time bid substitution/griefing where the value ultimately executed on-chain diverges from what other participants believe was locked in, i.e., fee/settlement abuse in the auction module reachable from a submitted bid via the `auction_submitBid` RPC / bid-gossip path.

### Likelihood Explanation
Likelihood is moderate-to-high: any party able to submit bids to the bid pool (auction module's public entry point, reachable via RPC or peer bid propagation, subject to Auctioneer/Searcher signature checks but not subject to any check tying the "same bid" decision to the actual execution payload) can trigger this path. No validator, node-operator, or consensus-level privilege is required — only a validly signed bid needs to be crafted with a different payload but same `BlockNumber`/`TargetTxHash`.

### Recommendation
Extend `Bid.Equals` to compare all economically/behaviorally significant fields of the bid — at minimum `Sender`, `To`, `Data`, `CallGasLimit`, `Nonce`, and `Bid` amount (or hash the entire `BidData` and compare hashes) — so that `senderHasDifferentWinner` correctly identifies any bid that differs in its execution semantics as a "different" bid, restoring the intended per-sender single-winning-bid invariant.

### Proof of Concept
1. Auctioneer/searcher submits Bid A: `{Sender: S, BlockNumber: N, TargetTxHash: H, To: X, Data: D1, CallGasLimit: G1, Bid: V}` — accepted, becomes the winner for `(N, H)`.
2. Same sender `S` submits Bid B: `{Sender: S, BlockNumber: N, TargetTxHash: H, To: Y, Data: D2, CallGasLimit: G2, Bid: V+1}` (different `To`/`Data`/`CallGasLimit`, only bid value slightly higher).
3. `senderHasDifferentWinner` calls `bidA.Equals(bidB)` → returns `true` (since only `BlockNumber`/`TargetTxHash` match), so the guard treats bid B as "the same" and does not reject it via `ErrBidSenderExists`.
4. `insertBid` then compares `bid.Bid` only (`V+1 > V`) and replaces bid A with bid B in `bidTargetMap`/`bidWinnerMap`, silently changing the actual call target/data/gas that will execute post-target-tx, even though the two bids are materially different.

// senderHasDifferentWinner reports whether a different bid from the same sender
// already exists in the winner list for this block. Caller must hold bidMu.
func (bp *BidPool) senderHasDifferentWinner(bid *auction.Bid) bool {
	hash, ok := bp.bidWinnerMap[bid.BlockNumber][bid.Sender]
	if !ok {
		return false
	}
	return !bid.Equals(bp.bidMap[hash])
}
