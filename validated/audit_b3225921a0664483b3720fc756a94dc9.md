## Finding

Chia has a direct analog to the Helm JSON-Schema stack-overflow bug: `PuzzleWithRestrictions.from_memo()` performs unbounded recursive parsing of attacker-controlled memo data, and this path is reached automatically when wallets sync PlotNFT/pool coins from chain.

### Title
Unbounded Recursive Memo Parsing In `PuzzleWithRestrictions.from_memo()` Allows A Malicious Coin Memo To Crash Syncing Wallets Via Python Stack Overflow - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively descends into nested `MofN` hint structures without any depth limit. Any unprivileged spend-bundle submitter can create a coin whose memo encodes a `MofN` hint chain nested thousands of levels deep, cheaply (nesting cost grows linearly, not combinatorially, in bytes). When another node/wallet later parses this memo — which happens automatically for pool/PlotNFT coins in `PlotNFT.get_next_from_coin_spend()` — the unbounded Python recursion exceeds the interpreter's call-stack limit and crashes/aborts wallet sync, mirroring the Helm CVE-2025-32387 bug class (uncontrolled recursion parsing untrusted structured input, CWE-121/CWE-674).

### Finding Description
`PuzzleWithRestrictions.from_memo()` is defined at [1](#0-0)  as a classmethod that:
1. Validates a namespace tag on the memo `Program`.
2. If `further_branching` is set, parses a `MofNHint` and recursively calls `PuzzleWithRestrictions.from_memo(memo)` **for every member memo** inside the hint — with no bound on nesting depth, no iteration cap, and no cost/CLVM-execution accounting (this is pure Python object traversal, not gated by mempool/CLVM cost limits).

Each `MofN` member is itself a `PuzzleWithRestrictions`, whose `puzzle` field can again be a `MofN` with its own members — so an attacker can construct a memo that is `MofN(members=[MofN(members=[MofN(...)])])` nested arbitrarily deep. Encoding N levels of nesting costs only O(N) bytes in the memo (a small constant number of CLVM list conses per level), far cheaper than the deeply-nested JSON-Schema `$ref` chains in the Helm advisory, but functionally identical in effect: recursive descent proportional to attacker-chosen nesting depth, unguarded by any depth check.

This parser is not test-only or CLI-only. It is invoked in production wallet/pool sync logic: `PlotNFT.get_next_from_coin_spend()` calls `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())` directly on the memo of a coin created by an on-chain spend, with no prior sanitization: [2](#0-1) . Any coin-creating condition (`CREATE_COIN` with hints/memos) reachable from an ordinary spend bundle can populate `memo_blob`, so an unprivileged spend-bundle submitter fully controls the bytes that reach `from_memo()`.

Contrast this with the module's own documented design intent: `sha256_treehash()` and CLVM parsing elsewhere in the codebase are deliberately implemented non-recursively "so we don't have to worry about blowing out the python stack" [3](#0-2) , and `Program.from_bytes()` intentionally routes through the Rust/CLVM parser rather than Python recursion for the same robustness reason [4](#0-3) . `PuzzleWithRestrictions.from_memo()` breaks that established robustness property by doing plain recursive Python calls over attacker-supplied structure.

### Impact Explanation
A wallet or pool client that processes an incoming/observed coin containing a maliciously deep `MofN` memo chain will recurse until it exhausts the Python call stack, raising `RecursionError` (or crashing the interpreter outright depending on platform stack limits). Because this code path runs during normal PlotNFT/pool coin-state processing rather than behind any privileged interface, this is a spend-triggered denial-of-service against any wallet/service that tracks pool NFTs and encounters the malicious coin — matching the "spend-triggered transaction-processing halt" impact class called out in the validation criteria.

### Likelihood Explanation
Likelihood is high for any node/wallet that tracks PlotNFT/pool coins: constructing the malicious memo requires no special privilege, only a normal spend bundle that creates a coin with a deeply nested `MofN` memo hint, and the cost to the attacker scales linearly (not exponentially) with recursion depth, making deep nesting cheap to produce.

### Recommendation
Rewrite `PuzzleWithRestrictions.from_memo()` (and `MofN.from_memo`-related parsing) to use an explicit iterative work-stack instead of Python recursion, following the pattern already used in `sha256_treehash()`, and/or enforce an explicit maximum nesting depth before recursing, rejecting memos that exceed it.

### Proof of Concept
1. Construct a memo `Program` via nested `MofNHint`/`PuzzleWithRestrictions.memo()` calls to synthesize N (e.g. 50,000) levels of `MofN` nesting, each wrapping a single member.
2. Encode this as the `memo_blob` on a `CREATE_COIN` condition inside an ordinary, validly-signed spend bundle and submit it to the mempool; the coin is created on-chain like any other.
3. Any wallet/pool client that later calls `PlotNFT.get_next_from_coin_spend()` (or otherwise calls `PuzzleWithRestrictions.from_memo()`) on this coin's memo triggers unbounded recursion in `from_memo()` at [5](#0-4) , exhausting the call stack and crashing that process.
