### Title
Permanent freeze of staked principal via mandatory reward transfer in `withdraw()` - (File: `rewards/MasterMagpie.sol`, `rewards/BaseRewardPool.sol`)

### Summary
`MasterMagpie.withdraw()`/`unstake()` paths unconditionally harvest and transfer *all* accrued reward tokens to the withdrawing user before returning the staked principal. If the transfer of any single reward token to that user reverts (e.g., the user is blacklisted by that reward token's contract, such as a USDC-style reward), the entire withdraw transaction reverts, permanently locking the user's staked principal with no non-privileged escape hatch (`emergencyWithdraw` only works while the whole protocol is paused, which is an admin action, not something the user controls).

### Finding Description
`MasterMagpie._withdraw` calls `_harvestAndUnstake`, which unconditionally calls `_harvestBaseRewarder(_stakingToken, _account)` before adjusting `user.amount`/`user.available` and only then transfers the staking token back to the caller: [1](#0-0) 

`_harvestBaseRewarder` ultimately calls `BaseRewardPool.getReward(_account, _receiver)`, which loops over *every* registered reward token for the account and does a `safeTransfer` to `_receiver` for each one with a nonzero balance: [2](#0-1) 

Because the loop transfers all reward tokens in a single call, and Solidity reverts the whole transaction on any failed `safeTransfer`, a single reward token that reverts transfers to the account (blacklist, paused token, transfer-fee/hook revert, etc.) makes `getReward` — and therefore `_harvestAndUnstake` and `withdraw()` — permanently revert for that account, for every pool that shares that reward token, even though the principal staking token itself is completely unrelated and otherwise transferable.

This is structurally the same root cause as the Cooler `repay()` bug: a mandatory token transfer to a party that can become untransferable-to blocks an unrelated, otherwise-valid asset-return operation (there: collateral return blocked by debt-token transfer failure; here: principal-token return blocked by reward-token transfer failure).

The only bypass, `emergencyWithdraw`, is gated by `whenPaused`, i.e., it requires the admin to pause the entire protocol — not something an ordinary user can trigger themselves: [3](#0-2) 

### Impact Explanation
Any user whose reward-token transfer reverts (self-blacklist, or blacklisted by an external stablecoin issuer for unrelated reasons, or a malicious/faulty reward token added via `queueNewRewards`) permanently loses access to their staked principal in `MasterMagpie`, since every withdraw path forces a harvest of all reward tokens first and there is no permissionless way to skip a single problematic reward token. This is a permanent freeze of user funds reachable by an ordinary wallet performing a normal `withdraw()` call.

### Likelihood Explanation
Likelihood is moderate: it requires either (a) an externally-controlled reward token (e.g., a stablecoin with a blacklist function) being added as a reward token via `queueNewRewards`/`BribeManager`, and the affected account being blacklisted by that token issuer, or (b) a malicious/self-inflicted setup where a user deliberately gets blacklisted to grief themselves is unlikely, but an innocuous scenario — a legitimate reward token operator blacklisting an address for unrelated compliance reasons — is realistic given reward tokens are added dynamically and not vetted for this failure mode in the reviewed code.

### Recommendation
Do not make principal withdrawal conditional on successful transfer of every reward token. Either: (1) wrap each reward token transfer in `getReward`/`_sendReward` in a try/catch (or low-level call) so a failure in one reward token doesn't block others or the withdraw path, crediting the failed amount to an internal "pending"/`withdrawBalance`-style mapping the user can later pull once un-blacklisted; or (2) decouple harvesting from withdrawing, allowing principal withdrawal to proceed even if reward harvesting fails, with rewards recorded for later claim.

### Proof of Concept
1. Admin/bribe manager registers a reward token `RT` (e.g., a compliant stablecoin) as a reward for a `MasterMagpie` pool via `queueNewRewards`. [4](#0-3) 
2. User Alice deposits staking token `ST` into the pool via `MasterMagpie.deposit`.
3. `RT`'s issuer blacklists Alice's address (for reasons unrelated to the protocol, or because Alice herself requests/causes it).
4. Alice calls `withdraw(ST, amount)`. This triggers `_withdraw` → `_harvestAndUnstake` → `_harvestBaseRewarder` → `BaseRewardPool.getReward(Alice, Alice)`, which attempts `RT.safeTransfer(Alice, reward)`. [5](#0-4) 
5. The `RT` transfer reverts due to the blacklist, reverting the entire `withdraw` transaction.
6. Alice cannot withdraw her `ST` principal through any normal, permissionless path; `emergencyWithdraw` is unavailable unless the protocol admin pauses the whole contract, which Alice cannot trigger herself. Her staked funds are permanently frozen.

        UserInfo storage user = userInfo[_stakingToken][msg.sender];
        uint256 availableaAmount = user.available;

    }
