### Title
BTC sent to an odd-Y group key's x-only P2TR output is permanently unspendable — (`networks/bitcoin/src/wallet/mod.rs`)

### Summary
Serai's Bitcoin wallet refuses to handle Taproot outputs whose key has an odd Y coordinate: `p2tr_script_buf` returns `None` for odd keys, `Scanner::new` propagates that `None`, and `SignableTransaction::multisig` aborts when the check fails. Because every P2TR output key is x-only, any external party can construct a valid, consensus-acceptable output paying the x-coordinate of an odd-Y group key — with standard Bitcoin tooling, without any interaction with Serai. Serai can neither scan nor sign for such an output, so the funds are locked forever. This is the direct analog of the SwapperImpl `payback()` issue: a value-receiving path exists on-chain while the implementation lacks any code path to move the funds.

### Finding Description
`p2tr_script_buf` in `networks/bitcoin/src/wallet/mod.rs:80-86` returns `None` whenever the key's SEC1 tag is not `CompressedEvenY`, i.e., for ~50% of all possible group keys. `Scanner::new` (mod.rs:162-166) returns `None` in that case, so no `Scanner` can ever be constructed for an odd group key and `scan_transaction`/`scan_block` can never yield a `ReceivedOutput` for it.

The lock is confirmed on the spend side: `SignableTransaction::multisig` (`networks/bitcoin/src/wallet/send.rs:273-285`) computes `keys.offset(self.offsets[i]).group_key()` and requires `p2tr_script_buf(...) == prevout.script_pubkey`; for an odd effective key `p2tr_script_buf` returns `None`, the `?` propagates, and `multisig` returns `None` — no `TransactionMachine` is created and no signature can ever be produced.

Meanwhile `register_offset` (mod.rs:180-196) only guarantees even keys for *registered* offsets; nothing prevents a third party from funding the raw x-only key. On Bitcoin, `OP_1 <x-only-key>` is a valid output for any 32-byte x-coordinate; the key-path spend requires the discrete log of the even-Y point with that x-coordinate, which is the *negation* of the threshold secret. The codebase's only negation logic (`needs_negation` in `networks/bitcoin/src/crypto.rs:26-28`, applied to the nonce/challenge in `Hram::hram` at crypto.rs:59-73 and to `sig.s` in `verify` at crypto.rs:145-149) handles nonce parity, never group-key parity — so even a hand-constructed `ReceivedOutput` cannot be signed for.

### Impact Explanation
Permanent loss of funds. For any multisig whose FROST group key has odd Y (~50% of keys), an output paying `x(group_key)` exists on-chain, is spendable under Bitcoin consensus (by `secret = -x_multisig`), but is categorically unspendable by Serai: scanning rejects the key at construction and the signing machine refuses at the `multisig()` script check. The sender need not be malicious — anyone deriving the "obvious" deposit address from the published group key with standard tools (e.g., `bitcoin-cli`/`rust-bitcoin` `new_p2tr` on the x-only key) produces exactly this locked output. This matches the report's class: funds accepted by a path the implementation cannot ever release.

### Likelihood Explanation
Medium-low likelihood, Medium+ impact. It requires (a) an odd-Y group key (50% per multisig) and (b) someone funding the un-tweaked x-only key rather than an offset address Serai actually advertises. Serai-generated addresses go through `register_offset`/`p2tr_script_buf`, so Serai itself never produces this address — but the group key is public and the x-only output is independently derivable by any sender, analogous to accidentally calling `payback()` on the base contract. No threshold collusion or privileged access is needed; a single ordinary transaction triggers it irreversibly.

### Recommendation
Support odd-Y keys end-to-end rather than rejecting them: when the effective spend key is odd, negate the secret share (equivalently, offset the signing view by the required parity correction) inside `TransactionMachine` construction, and let `Scanner`/`p2tr_script_buf` emit the x-only script with a parity flag stored alongside the `Scalar` offset in `ReceivedOutput`. At minimum, `Scanner::new` and the processor should detect and loudly reject odd group keys at multisig creation time, and document that raw x-only funding of odd keys burns funds — though only full parity support actually removes the lock.

### Proof of Concept
1. DKG completes with group key `P` where `P.to_encoded_point(true).tag() == CompressedOddY` (`needs_negation(P) == 1`).
2. Any external party runs: `ScriptBuf::new_p2tr_tweaked(TweakedPublicKey::dangerous_assume_tweaked(XOnlyPublicKey::from_slice(&x(P))))` — or equivalently pays `x(P)` with any wallet — and broadcasts a funding transaction.
3. The output confirms on-chain and is consensus-spendable by `-(secret)`; Serai's `Scanner::new(P)` returns `None` (mod.rs:162-166), so the output is never reported.
4. Even if the outpoint is fed manually into `SignableTransaction::new` with `offset = Scalar::ZERO`, `multisig(keys)` evaluates `p2tr_script_buf(keys.offset(0).group_key())` → `None` at send.rs:277, returning `None` — no signature is possible. The BTC is permanently locked.
