### Title
OP_RETURN data outputs are excluded from the transaction weight/fee calculation, undercharging data-carrying transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the Royco bug where `fillLPOrder` omitted the `protocolFee` charged by `fillIPOrder`, `SignableTransaction::new` computes `needed_fee` from a mock transaction that contains only the payment outputs. An OP_RETURN output carrying user-supplied `data` is appended to `tx_outs` *before* the weight calculation, but is never passed to `calculate_weight_vbytes`, so its serialized bytes are never charged for — in both the no-change and with-change paths.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` when `data` is `Some` (lines 193–202). However, the subsequent weight/vbytes computation at line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, and `calculate_weight_vbytes` (lines 85–99) builds its mock transaction's `output` vector solely from `payments` plus an optional `change` output — the OP_RETURN output is never represented. The same omission occurs in the change branch at lines 225–227.

As a result, a transaction can carry up to 80 bytes of arbitrary `data` (checked at line 171) in an extra output costing roughly 9 + 1 + (1 + 80) ≈ 91 serialized bytes (~91 vbytes under SegWit discount rules for the non-witness portion), none of which is charged via `fee_per_vbyte * vbytes` at line 206. Additionally, the `MAX_STANDARD_TX_WEIGHT` check at line 241 uses `weight` from the same incomplete mock, so a transaction can silently exceed the standardness weight limit.

### Impact Explanation
A user who attaches `data` to a withdrawal/plan pays a fee computed as if the OP_RETURN output did not exist. Two concrete consequences:

1. **Underpaid fee / unrelayable transaction**: if `fee_per_vbyte` is near the minimum, the real transaction's effective feerate (`fee() / actual_vbytes`) falls below `DEFAULT_MIN_RELAY_TX_FEE` even though the check at line 211 passed, since the check uses the underestimated `vbytes`. The signed transaction the threshold network produces can then be rejected by Bitcoin Core's mempool, leaving funds committed to inputs that cannot be spent until a new transaction is coordinated — a liveness/availability loss for the user's funds.
2. **Fee avoidance**: the added bytes are transferred for free, shifting the marginal cost onto the protocol/fee budget.

### Likelihood Explanation
`data` is a caller-controlled input to `SignableTransaction::new` (up to 80 bytes, line 171), so any plan specifying an OP_RETURN payload deterministically triggers the undercharge. No special ordering or adversarial timing is required — the miscalculation occurs on every invocation where `data.is_some()`.

### Recommendation
Include the OP_RETURN output in the weight mock: either pass the already-built `tx_outs` (or a `payments`-like slice including the OP_RETURN `ScriptBuf`) into `calculate_weight_vbytes`, or append `TxOut { value: Amount::ZERO, script_pubkey: op_return_script }` inside `calculate_weight_vbytes` for both the no-change and with-change computations. The `MAX_STANDARD_TX_WEIGHT` check must use the weight of the full output set as well.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// Construct two otherwise-identical SignableTransactions:
let without_data = SignableTransaction::new(
    inputs.clone(), payments, None, None, fee_per_vbyte,
).unwrap();
let with_data = SignableTransaction::new(
    inputs.clone(), payments, None, Some(vec![0xAA; 80]), fee_per_vbyte,
).unwrap();

// needed_fee ignores the ~91-byte OP_RETURN output entirely:
assert_eq!(without_data.needed_fee(), with_data.needed_fee());
// Yet with_data.transaction().vsize() > without_data.transaction().vsize(),
// so its effective feerate is strictly lower than fee_per_vbyte.
```
Root cause: the OP_RETURN push at `send.rs:194-202` precedes, but is invisible to, the fee estimation at `send.rs:204-227`, which is built exclusively from `payments` (`send.rs:85-99`).
