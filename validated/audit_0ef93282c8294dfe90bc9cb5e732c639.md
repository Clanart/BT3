## Title
Stale line-index partial-selection state can silently commit/exclude the wrong content when the working directory diff changes between selection and commit - (File: `app/src/lib/patch-formatter.ts`, `app/src/lib/stores/app-store.ts`)

## Summary
Coinbase's `removeOwnerAtIndex` bug removed the wrong owner because ownership was tracked by positional index, and the entity at that index could silently change between when a signature/intent was created and when it was executed, with no check that the index still pointed to the intended entity. GitHub Desktop has a structurally identical invariant break in its partial-commit (line-level staging) feature: a user's line selection is tracked purely as a set of numeric line indices (`DiffSelection`), and those indices are re-applied against a *freshly recomputed* diff at commit/patch-apply time, with no validation that the content at that index is still the content the user actually selected.

## Finding Description
`DiffSelection` (`app/src/models/diff/diff-selection.ts`) stores only which absolute line indices diverge from the default selection — it has no notion of line *content*, only line *position*: [1](#0-0) 

When a partial commit is created, `formatPatch` walks the diff hunks and decides whether to include each line purely by asking `file.selection.isSelected(absoluteIndex)` — an index lookup, not a content lookup: [2](#0-1) 

That diff is not the one the selection was originally computed against — `applyPatchToIndex` recomputes the diff live, at staging time, from the current working directory: [3](#0-2) 

Desktop's own code acknowledges this is unsafe. In `updateChangesWorkingDirectoryDiff`, when a file's diff is reloaded, the comment explicitly states that the app does **not** validate that previously selected lines still correspond to the same content — it only prunes lines that no longer exist in the new diff's `selectableLines` set: [4](#0-3) 

Because `DiffSelection.withSelectableLines` only removes selection state for indices that fall outside the new selectable set (it does not compare old vs. new line *content*), any index that is still "in range" after the diff changes is treated as still valid — even if a completely different line now occupies that index: [5](#0-4) 

**The broken invariant:** "line index N is selected" is assumed to mean "the specific content the user reviewed at index N is selected," but the guard code only checks "does index N still exist," not "does index N still refer to the same content." This is exactly analogous to `removeOwnerAtIndex` trusting "owner at index N" without checking "owner at index N is still who I intended."

## Impact Explanation
If the working directory diff for a file changes between the time the user reviews/selects lines and the time the commit is actually created — e.g., because a concurrent `git pull`/fetch-and-merge, checkout, or externally-modified file (any of which can be influenced by a malicious collaborator pushing to a shared branch/remote the user has open) shifts hunks in the same file — the line indices the user selected can now point to entirely different content:

- Lines the user intentionally excluded (e.g., a debug string, secret, or suspicious code the attacker introduced) could shift into a previously-selected index and get silently included in the commit/push.
- Lines the user intended to include could shift out and be silently dropped, corrupting the commit without any user-visible confirmation, since the confirmation UI only shows the diff at selection time, not necessarily re-diffed content-for-content at apply time.

This matches the "silent corruption of what the user commits or pushes" impact category directly, without requiring local/physical access, admin rights, or pre-existing malware — only a git remote/collaborator that can change file content concurrently with the user's review-and-select workflow.

## Likelihood Explanation
This requires a specific but realistic race: the user must have a partial (line-level) selection pending on a file while an operation (pull/fetch+merge, or a background refresh of the diff) mutates the same file's diff before the commit is finalized. GitHub Desktop performs background refreshes and supports concurrent fetch/pull while the Changes view is open, and the codebase comment at `app-store.ts:3480-3486` demonstrates the maintainers are aware the diff "might have changed dramatically" while a selection is pending — indicating this is a known, reachable scenario rather than a purely theoretical one. It requires no unusual user steps beyond ordinary usage (having a partial selection open while a fetch/pull happens), but it does require timing/collaboration conditions to align, which lowers likelihood relative to a fully deterministic exploit.

## Recommendation
Rather than tracking selection purely by absolute line index, associate selection state with content-derived anchors (e.g., hash of hunk header + line text, or diff-line identity token) so that when the diff is recomputed, selection can be revalidated by content match rather than blind index reuse. At minimum, before applying a patch from a stale selection, Desktop should re-diff the file and reject/re-prompt if the hunks touching selected indices have changed content since the selection was captured, rather than silently proceeding with `formatPatch` against a newly-fetched diff.

## Proof of Concept
1. User A opens GitHub Desktop on a shared branch and modifies `file.txt`, producing a diff with hunks H1 (lines 10–15) and H2 (lines 40–45).
2. User A selects only specific added lines within H1 for a partial commit (leaving other lines unstaged), building a `DiffSelection` keyed on absolute indices 10–15.
3. Before user A clicks "Commit", a collaborator (attacker) pushes a commit to the same branch/remote that the app auto-fetches and merges, or the user manually pulls, changing the file such that new lines are inserted above line 10, shifting content so that the "same" indices 10–15 in the new diff now correspond to attacker-controlled lines instead of the user's originally-reviewed lines.
4. `updateChangesWorkingDirectoryDiff` reloads the diff and calls `withSelectableLines` on the new diff; because the indices are still within the new selectable range, they remain selected — no content comparison is performed (`app-store.ts:3478-3497`, `diff-selection.ts:230-282`).
5. User A clicks "Commit"; `applyPatchToIndex` re-fetches the current diff and `formatPatch` includes whatever content now sits at the previously selected indices (`apply.ts:60-81`, `patch-formatter.ts:143-171`), silently committing/pushing content the user never reviewed or intended to include.
