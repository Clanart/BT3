## Analog Found: Use-After-Free via Python-C++ Map-Field Wrapper Dangling After `MergeFrom`

### Title
Dangling Python `CMessage` wrapper after C++ map-value overwrite during `MergeFrom` — (File: `python/google/protobuf/pyext/message.cc`)

### Summary
The reported Chrome/Mojo CVE is a UAF where a C++ object is freed while a live reference to it is retained and later dereferenced. The transferable invariant is: *any wrapper/handle object that caches a raw pointer into an arena/heap-owned C++ structure must be invalidated whenever that structure is deallocated by a subsequent operation, or the wrapper must be excluded from that operation's fast path.* In this Protobuf checkout (`pyext`, the CPython C-extension binding), this invariant is enforced for oneof-switch fields during `MergeFrom` but is explicitly *not* enforced for message-valued map fields, even though the code comments acknowledge the same overwrite-and-free behavior occurs for maps.

### Finding Description
Protobuf's Python C++ implementation (`pyext`) keeps a `CMessage::CompositeFieldsMap` (`composite_fields`) of live Python wrapper objects that hold raw pointers into the parent's C++ `Message`. When `MergeFrom` is called from an ordinary trusted client on a message whose incoming payload contains a `map<K, Message>` field with a key that already exists in the destination, the underlying C++ map merge logic (`MapFieldBase::MergeFrom` → `UntypedMapBase::UntypedMergeFrom`, `src/google/protobuf/map_field.cc:36-38`, `src/google/protobuf/map.cc:38-93`) replaces/overwrites the existing map entry node in place, which invalidates the C++ submessage previously exposed to Python.

The UAF-prevention logic added for exactly this class of bug, `MaybeReleaseOneofBeforeMerge` (`python/google/protobuf/pyext/message.cc:757-807`), walks `composite_fields` and detaches any cached Python wrapper whose underlying oneof member is about to be destroyed by the merge. Critically, this function filters candidates with: [1](#0-0) 
which explicitly excludes `is_repeated()` fields — and map fields are represented internally as repeated message fields. The comment on the same lines states the author was aware of the risk ("For message map with same keys, it is overwrite") but the exclusion condition (`!descriptor->is_repeated()`) still filters map fields out of protection.

`MergeFrom`/`MergeFromStringImpl` then unconditionally call `message->MergeFrom(*other)` (`python/google/protobuf/pyext/message.cc:2008`, `2161`) without detaching any previously-obtained Python wrapper for a map value at the same key.

This exact scenario is documented as a known, unfixed hazard in the project's own Python conformance test suite: [2](#0-1) 
The test explicitly notes: *"During the call to MergeFrom(), the C++ implementation will have deallocated the underlying message... The line below is likely to cause a segmentation fault"* — and the assertion validating the stale wrapper's value is skipped specifically `if api_implementation.Type() != 'cpp'`, i.e., the crash path is real for the C++ extension and only suppressed for the pure-Python implementation in the test.

This differs from the already-fixed oneof case (validated by `testOneofSwitchMergeUAF`, `python/google/protobuf/internal/message_test.py:2184-2202`), which explicitly documents that oneof-switch UAF *was* fixed via `MaybeReleaseOneofBeforeMerge`. The map-field case sits directly adjacent to that fix but is carved out of it.

### Impact Explanation
This is a use-after-free of heap/arena-owned C++ memory reachable purely by:
1. A trusted application obtaining a Python message wrapper for a value in a `map<K, Message>` field (e.g. `msg.some_map[key]`), and
2. Merging in a second, attacker-controlled serialized Protobuf payload (via `MergeFrom`/`MergeFromString`/`ParseFromString`) that contains an entry with the same map key.

After the merge, the old Python wrapper object retains a stale C++ pointer into memory that has been overwritten/reused by the map's node-replacement logic. Any subsequent field access on that wrapper (`old_map_value.c` in the test) reads or writes through a dangling pointer — the same bug class as the Mojo CVE (heap corruption / potential further memory corruption via a crafted message), reachable without any privileged access, custom schema, or malicious code — only a legitimate client application pattern (cache a map submessage handle, then merge new data) combined with attacker-supplied bytes.

### Likelihood Explanation
The trigger requires only two ordinary, widely-used API calls (`map_field[key]` then `MergeFrom`/`MergeFromString`) with a map field of message type — a very common schema pattern. No special build flags, unsafe APIs, or malformed/invalid wire data are needed; the second payload is a completely valid Protobuf message. The bug is deterministic and already codified as expected behavior in the project's own test file (guarded only by an implementation-type check to avoid crashing CI), which strongly indicates it is a real, currently-reachable condition in the C++-backed Python extension, not a hypothetical.

### Recommendation
Extend `MaybeReleaseOneofBeforeMerge` (or add a parallel pre-merge scan) in `python/google/protobuf/pyext/message.cc` to also detect and detach/release composite-field wrappers for message-valued map entries whose keys exist in both `self` and `other`, before calling `message->MergeFrom(*other)`. This mirrors the existing oneof-switch protection but must walk the map field's entries (not just the top-level `composite_fields` singular/oneof descriptors) since map value wrappers are keyed by container object, not directly by `FieldDescriptor`. Add a regression test analogous to `testOneofSwitchMergeUAF` for the map case, and remove/replace the `api_implementation.Type() != 'cpp'` guard in `testMergeFrom` once fixed so the C++ backend is verified too.

### Proof of Concept
Existing project test demonstrates the exact reachable condition (already present in the repo, with the crash-causing assertion currently disabled only for the C++ backend): [3](#0-2) 
```python
msg2 = map_unittest_pb2.TestMap()
msg2.map_int32_foreign_message[222].c = 15
msg2.map_int32_foreign_message[222].d = 20
old_map_value = msg2.map_int32_foreign_message[222]   # cache Python wrapper -> C++ submessage

msg2.MergeFrom(msg)  # msg also has key 222; C++ map entry for 222 is overwritten/freed

# For api_implementation.Type() == 'cpp': accessing old_map_value.c here dereferences
# freed C++ memory (documented in the test as "likely to cause a segmentation fault").
```
This does not require crafting invalid wire data or bypassing any parser checks — both `msg` and `msg2` are valid protobuf messages; the vulnerability is in the object-lifetime handling of the Python/C++ boundary during a supported public `MergeFrom` API, directly analogous to the Mojo UAF's "valid message triggers premature free of a still-referenced object" pattern.

**Uncertainty note:** I was not able to fully trace the exact low-level free/reuse path inside `NodeBase`/`KeyMapBase::InsertOrReplaceNode` (i.e., whether the old node's `Message` destructor runs immediately or is deferred to arena reset) within the tool budget available; this affects only the precise memory-corruption primitive (immediate free vs. delayed/arena-scoped free) but does not change the core finding that the Python wrapper becomes stale and unprotected relative to the sibling oneof fix. A background engineer with build/test access should confirm the exact free timing with an ASan-instrumented run of `testMergeFrom` against the C++ `pyext` backend.
