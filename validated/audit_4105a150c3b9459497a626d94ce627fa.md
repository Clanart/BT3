### Title
Operator reimbursement is attributed purely from an attacker-controlled OP_RETURN in the transaction that spends `withdrawal_utxo`, with no check that the credited operator actually funded the payout - ([File: core/src/verifier.rs])

### Summary
`Verifier::update_finalized_payouts` credits a withdrawal to whichever `operator_xonly_pk` appears in an OP_RETURN output of *any* transaction that spends the registered `withdrawal_utxo`, without verifying that this transaction actually paid the withdrawal beneficiary the committed amount/script, or that the named operator supplied any funds. Since `withdrawal_utxo` is a plain single-sig P2TR output solely controlled by the withdrawer's own key, the withdrawer can spend it themselves (e.g., a near-zero self-payment) while embedding an arbitrary operator's pubkey in the OP_RETURN, causing that operator to be credited as payer and become eligible for reimbursement from deposit D's move-to-vault UTXO.

### Finding Description
The claimed binding is: `withdrawals.payout_payer_operator_xonly_pk` for withdrawal *i* == the operator whose Bitcoin actually reached the outpoint(s) owed to withdrawal *i*'s beneficiary.

Trace:
- `withdraw()`/Citrea registers a `withdrawal_utxo` (an `OutPoint`) per withdrawal index, stored via `update_withdrawal_utxo_from_citrea_withdrawal` [1](#0-0) .
- This UTXO is a plain user-owned P2TR single-sig output, e.g. as constructed in test helpers [2](#0-1) . The user separately produces a `SinglePlusAnyoneCanPay` signature that *off-chain* commits a specific output (script/amount) for operators to use when constructing the real payout tx [3](#0-2) . Nothing prevents the key-holder (the withdrawer) from instead crafting and broadcasting a brand-new, differently-signed transaction spending this same UTXO (e.g. SIGHASH_ALL, paying themselves), since it is a normal Bitcoin single-sig output, not a script enforcing that specific pre-committed output.
- `Verifier::update_finalized_payouts` scans each finalized block for transactions that spend a tracked `withdrawal_utxo` (`get_payout_txs_for_withdrawal_utxos`), then unconditionally parses the *first OP_RETURN output* of that spending transaction to extract an `operator_xonly_pk`, and writes it to `withdrawals.payout_payer_operator_xonly_pk` — with no check on the transaction's other outputs (amount/script paid to the beneficiary) [4](#0-3) .
- `get_first_unhandled_payout_by_operator_xonly_pk` later selects unhandled withdrawals purely by matching this attacker-supplied `payout_payer_operator_xonly_pk` to an operator's own key [5](#0-4) , and `PayoutCheckerTask::run_once` automatically calls `handle_finalized_payout` and proceeds toward kickoff/Reimburse for that operator [6](#0-5) .
- `Verifier::is_kickoff_malicious`, the only later gate for whether a kickoff is legitimate, checks only that `payout_op_xonly_pk == kickoff_data.operator_xonly_pk` and that the committed payout blockhash matches — it never verifies that any of the payout transaction's outputs actually paid the withdrawal's intended beneficiary the registered amount/script [7](#0-6) .
- The bridge circuit (`bridge_circuit`, `verify_storage_proofs`) similarly only checks that the payout tx's input at `payout_input_index` matches the `withdrawal_utxo` (txid/vout) recorded on Citrea and that an operator xonly-pk is embedded in an OP_RETURN — it never checks the output amount/script paid to the user [8](#0-7) , and the storage proof itself only exposes the withdrawal input outpoint/vout and move_txid, not any commitment to output amount/script [9](#0-8) .

Root cause: attribution of "who funded this withdrawal" is derived solely from an attacker-controlled OP_RETURN byte string in whichever transaction happens to spend `withdrawal_utxo`, with no cryptographic or value-based binding to a genuine payment reaching the withdrawal's beneficiary, and no requirement that the named operator is the one who broadcast/funded that transaction.

Exploit flow: the withdrawer (attacker) registers a legitimate small withdrawal against deposit D (`withdrawal_utxo` U). Rather than waiting for an operator to front the payout, the attacker signs and broadcasts a new transaction spending U, sending the (small/dust) value back to themselves, and appends an OP_RETURN containing an arbitrary/target operator's x-only pubkey. Once finalized, `update_finalized_payouts` records that operator as `payout_payer_operator_xonly_pk`. That operator's `PayoutCheckerTask` (if the named operator is real and running automation) or a manually-triggered reimbursement flow will treat this as a legitimate, already-fronted payout and proceed through kickoff → Reimburse, spending deposit D's real move-to-vault UTXO to pay the operator the full `bridge_amount`, despite no BTC ever having reached the withdrawal's intended beneficiary.

### Impact Explanation
This breaks the ATTRIBUTION↔CUSTODY binding: an operator becomes eligible to claim the full `bridge_amount` reimbursement for a withdrawal it never funded, while the deposit's move-to-vault UTXO is the only place real value ever leaves the vault. This matches the Critical category "an operator reimbursed for a payout it never funded." It is repeatable per withdrawal/deposit index that a colluding or oblivious withdrawer controls (any withdrawer, since anyone can register a `withdrawal_utxo` via `withdraw()`), and can be aimed at any operator's public x-only key (public information) — the blast radius spans all deposits/operators in the system, since the check is generic and not operator-specific in any authenticating way. Note: this does *not* require the named operator's cooperation — the operator's own automated `PayoutCheckerTask` picks it up automatically based purely on the DB row, meaning the operator would be pushed into wrongly claiming a reimbursement it never earned (which could itself later be disputed/challenged since it did not fund a payout, but the current code path contains no check that would catch this before the operator commits to a kickoff and spends real fee/collateral resources, and per the question's framing, the Reimburse transaction is asserted to succeed).

### Likelihood Explanation
Preconditions: an attacker only needs to be a normal withdrawer (unprivileged) with a small legitimate withdrawal registered against some deposit D, and access to broadcast Bitcoin transactions — both explicitly within scope of the unprivileged attacker model. Cost is a single dust-value self-spend transaction plus mining fee. No key compromise, no majority hashrate, no verifier/operator/aggregator privileges are required. The only external dependency is that automation (`PayoutCheckerTask`, gated by the `automation` feature) or manual reimbursement flow processes the erroneous DB row for a named operator — which is standard operation, not an unusual configuration.

### Recommendation
`update_finalized_payouts` (and/or the bridge circuit's storage-proof/payout binding) must independently verify that the transaction spending `withdrawal_utxo` actually pays the withdrawal's committed beneficiary output (script_pubkey and amount, as originally registered/exchanged at `withdraw()` time) before attributing `payout_payer_operator_xonly_pk`. Concretely: (1) persist the user's committed `output_script_pubkey`/`output_amount` at withdrawal-registration time, (2) when scanning a spending transaction, require that one of its outputs (at a fixed/verifiable index, e.g. matching the same index as the withdrawal input per the SIGHASH_SINGLE scheme) matches that committed script/amount exactly, and only then trust the OP_RETURN operator attribution; otherwise mark the withdrawal as unresolved/optimistic rather than crediting any operator.

pub fn verify_storage_proofs(
    storage_proof: &StorageProof,
    state_root: [u8; 32],
) -> (WithdrawalOutpointTxid, u32, MoveTxid) {
    let utxo_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_utxo)
            .expect("Failed to deserialize UTXO storage proof");

    let vout_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_vout)
            .expect("Failed to deserialize vout storage proof");

    let deposit_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_deposit_txid)
            .expect("Failed to deserialize deposit storage proof");

    let storage_address: U256 = {
        let mut keccak = Keccak256::new();
        keccak.update(UTXOS_STORAGE_INDEX);
        let hash = keccak.finalize();
        U256::from_be_bytes(
            <[u8; 32]>::try_from(&hash[..]).expect("Hash slice has incorrect length"),
        )
    };

    let storage_key_utxo: alloy_primitives::Uint<256, 4> =
        storage_address + U256::from(storage_proof.index * 2);

    let storage_key_vout: alloy_primitives::Uint<256, 4> =
        storage_address + U256::from(storage_proof.index * 2 + 1);

    let storage_address_deposit: U256 = {
        let mut keccak = Keccak256::new();
        keccak.update(DEPOSIT_STORAGE_INDEX);
        let hash = keccak.finalize();
        U256::from_be_bytes(
            <[u8; 32]>::try_from(&hash[..]).expect("Hash slice has incorrect length"),
        )
    };

    let deposit_storage_key: alloy_primitives::Uint<256, 4> =
        storage_address_deposit + U256::from(storage_proof.index);

    let deposit_storage_key_bytes = deposit_storage_key.to_be_bytes::<32>();

    if deposit_storage_key_bytes != deposit_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid deposit storage key. left: {:?} right: {:?}",
            deposit_storage_key_bytes,
            deposit_storage_proof.key.as_b256().0
        );
    }

    if storage_key_utxo.to_be_bytes() != utxo_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid withdrawal UTXO storage key. left: {:?} right: {:?}",
            storage_key_utxo.to_be_bytes::<32>(),
            utxo_storage_proof.key.as_b256().0
        );
    }

    if storage_key_vout.to_be_bytes() != vout_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid withdrawal vout storage key. left: {:?} right: {:?}",
            storage_key_vout.to_be_bytes::<32>(),
            vout_storage_proof.key.as_b256().0
        );
    }

    storage_verify(&utxo_storage_proof, state_root);

    storage_verify(&deposit_storage_proof, state_root);

    storage_verify(&vout_storage_proof, state_root);

    let buf: [u8; 32] = vout_storage_proof.value.to_be_bytes();

    // ENDIANNESS SHOULD BE CHECKED THIS FIELD IS 4 BYTES in the contract
    let vout = u32::from_le_bytes(
        buf[28..32]
            .try_into()
            .expect("Vout value conversion failed"),
    );
