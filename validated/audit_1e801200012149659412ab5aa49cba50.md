### Title
Yield/bribe rewards in `BaseRewardPool`/`BaseRewardPoolV2` can be stolen via JIT sandwich around permissionless `castVotes()` - (File: `rewards/BaseRewardPool.sol`, `rewards/BaseRewardPoolV2.sol`, `wombat/WombatBribeManager.sol`, `wombat/WombatStaking.sol`)

### Summary
Bribe rewards harvested through `WombatBribeManager.castVotes()` are pushed into the LP-staking `BaseRewardPool`/`BaseRewardPoolV2` for each Wombat pool via `queueNewRewards`, which instantly bakes the entire reward amount into `rewardPerTokenStored` based on the pool's `totalStaked()` at that exact block. Because staking/unstaking into these pools (through `WombatStaking`/`WombatPoolHelper` → `MasterMagpie`) has no lock-up, cooldown, or exit fee, and `castVotes()` is a public, permissionless, unauthenticated function, an ordinary wallet can front-run the harvest with a large deposit and back-run it with an immediate withdrawal, capturing a disproportionate share of the freshly harvested bribe rewards that rightfully belong to the LPs who were staked while the votes/bribes accrued.

### Finding Description
`WombatBribeManager.castVotes()` is `public` with no access control and is explicitly designed to be called by any user (a caller fee is paid as an incentive): [1](#0-0) 

It calls `wombatStaking.vote(...)`, which for every pool with pending bribe rewards immediately calls `queueNewRewards` on the pool's rewarder contract: [2](#0-1) 

`queueNewRewards` → `_provisionReward` folds the entire incoming reward amount into `rewardPerTokenStored` in a single step, dividing by `totalStaked()` measured *at the moment of the call*: [3](#0-2) [4](#0-3) 

`balanceOf`/`totalStaked` for these pools are read live from `MasterMagpie`'s staking info, and `MasterMagpie.deposit`/`withdraw` (or the corresponding `WombatPoolHelper` deposit/withdraw wrappers) have no lock, cooldown, or exit fee — a user's share of the pool changes and is fully liquid within the same block-pair: [5](#0-4) [6](#0-5) 

Because reward distribution is instantaneous and proportional to the balance held at the time of the `queueNewRewards` call, and because staking that balance carries no cost or delay, this is the same JIT/sandwich pattern as the original `LiquidityReserve` finding: bribes accrued over the voting period (which should belong to the LPs who were staked/exposed during that period) can be captured by an attacker who only holds a balance for the single transaction in which `castVotes()` executes.

### Impact Explanation
An attacker who observes (or self-triggers, since `castVotes` is public and callable at will) a pending bribe harvest can:
1. Deposit a large `stakingToken` amount into the target Wombat pool (via `WombatPoolHelper`/`WombatStaking` → `MasterMagpie.deposit`), inflating their share of `totalStaked()`.
2. Call/allow `castVotes()` to execute, which calls `queueNewRewards` and instantly credits `rewardPerTokenStored` proportional to current stake.
3. Immediately `withdraw` from `MasterMagpie`, having captured a share of the bribe reward disproportionate to any real economic exposure or time staked, at the expense of genuine long-term liquidity providers.

This constitutes theft of unclaimed yield belonging to legitimate stakers, with no time-locking or fee mechanism (e.g., no linear vesting of rewards, no withdrawal fee, no minimum staking duration) to prevent it. This mirrors the accepted-as-High root cause in the referenced report: JIT capital that provides no real service to the protocol (unlike JIT liquidity in an AMM swap) can be used risk-free to intercept freshly distributed rewards.

### Likelihood Explanation
`castVotes()` is explicitly designed to be publicly callable (with a caller fee incentive), meaning execution is predictable/triggerable and visible in the mempool, making the sandwich straightforward to execute for any pool with meaningful bribe volume and no minimum staking duration. The lack of any lock, cooldown, or exit penalty on deposit/withdraw in `MasterMagpie`/`WombatPoolHelper` removes the only friction that would otherwise deter this attack.

### Recommendation
- Stream newly queued rewards over a fixed duration (e.g., linear vesting per block/second) instead of crediting the full amount to `rewardPerTokenStored` in a single instant, similar to Synthetix-style `rewardRate`/`periodFinish` designs.
- Introduce a minimum staking duration or withdrawal cooldown before a user's balance is eligible to receive newly queued rewards.
- Alternatively, snapshot `totalStaked()`/user balances prior to the block in which `queueNewRewards` is called, so that same-block deposits cannot receive a portion of that reward tranche.

### Proof of Concept
1. Attacker monitors the mempool for a pending call to `WombatBribeManager.castVotes()` (or `voteAndCast`/`castVotesAndClaimBribes`), which is unrestricted and callable by anyone: [1](#0-0) 
2. Attacker front-runs with a large `MasterMagpie.deposit`/`WombatPoolHelper` deposit into the targeted pool, inflating `totalStaked()`'s attacker share for that pool's `BaseRewardPool`.
3. `castVotes()` executes, triggering `WombatStaking.vote` → `IBaseRewardPool.queueNewRewards`, which folds the harvested bribe reward into `rewardPerTokenStored` based on the current (attacker-inflated) `totalStaked()`: [7](#0-6) [3](#0-2) 
4. Attacker immediately calls `MasterMagpie.withdraw` to exit the position, having captured a disproportionate share of the bribe reward relative to actual time-weighted exposure, while diluting the earnings legitimate long-term LPs should have received.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
