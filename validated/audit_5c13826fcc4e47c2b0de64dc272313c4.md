### Title
`ReceivedOutput::read` performs no consistency validation between `offset` and `output.script_pubkey`, allowing unspendable outputs to be accepted as received funds — ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput` is the structure representing a spendable Bitcoin output owned by the threshold key: it pairs a scalar `offset` (used to derive the spendable tweaked key `key + G*offset`) with the `TxOut`/`OutPoint` being spent. The Bitcoin `Scanner` guarantees this consistency at production time — it only emits a `ReceivedOutput` when `output.script_pubkey` matches a registered `p2tr_script_buf(key + G*offset)` mapping (`scan_transaction`, `networks/bitcoin/src/wallet/mod.rs:199-214`). However, `ReceivedOutput::read` (the deserialization path explicitly exposed to untrusted bytes) accepts `offset`, `output`, and `outpoint` independently and never verifies that the `TxOut`'s `script_pubkey` is even a P2TR output, let alone that it equals the script derived from the declared `offset` (`networks/bitcoin/src/wallet/mod.rs:120-134`). This is the same bug class as the DODO finding: a field that should be constrained to a small set of valid relationships is trusted blindly, and the invalid relationship results in funds being treated as spendable when they are not.

### Finding Description
The read path performs only structural decoding:

- `offset` is read as an arbitrary scalar via `Secp256k1::read_F`
- `output` is consensus-decoded as any `TxOut` — no `is_p2tr()` check, no comparison against `p2tr_script_buf(key + G*offset)`
- `outpoint` is consensus-decoded with no existence/ownership check

By contrast, every legitimate construction of a `ReceivedOutput` goes through `Scanner::register_offset`/`scan_transaction`, which builds the `scripts: HashMap<ScriptBuf, Scalar>` map so that `offset` and `script_pubkey` are bound together by construction (`networks/bitcoin/src/wallet/mod.rs:153-196`). The deserializer discards this invariant entirely: a crafted byte stream can claim any `TxOut` (e.g., an attacker-owned P2PKH output, an OP_RETURN burn output, or a P2TR key the multisig does not control) paired with any `offset`, and it will be accepted as a `ReceivedOutput` indistinguishable from a genuinely scanned one. Downstream spending code trusts `output.offset()` to derive the tweaked signing key and `output.output()` as the prevout committed by the BIP-341 sighash, so the inconsistency is only discovered — if at all — when the produced transaction is unspendable or invalid.

### Impact Explanation
An attacker who feeds crafted bytes to `ReceivedOutput::read` can cause the wallet/processor layer to record funds as received that are not actually spendable by the multisig: the declared `offset` does not derive a key matching the claimed `script_pubkey`, so no valid signature can ever be produced for that input. This yields balance/accounting corruption (value reported as held that can never be spent) and can additionally induce the threshold signing protocol to produce signatures over a transaction committing to an unspendable or foreign-controlled prevout — burning the real fees and other real inputs committed alongside it under `Prevouts::All`. Analogously to the DODO report, unchecked input lets value be directed into a state from which it is unrecoverable.

### Likelihood Explanation
The vulnerability requires attacker-controlled bytes to reach `ReceivedOutput::read` rather than the honest `Scanner` path; on-chain transactions alone cannot trigger it because `scan_transaction` enforces the script↔offset binding. Severity is therefore bounded by the exposure of the deserialization entry point (persisted output records, `Output::read` wrapping it, or any RPC/wire ingestion of serialized `ReceivedOutput`s), but where reachable the failure is deterministic — no race or cryptographic assumption is needed.

### Recommendation
Validate the invariant at deserialization, matching what the `Scanner` guarantees at production:

```rust
// networks/bitcoin/src/wallet/mod.rs, ReceivedOutput::read
let offset = Secp256k1::read_F(r)?;
let output: TxOut = /* consensus decode */;
let outpoint: OutPoint = /* consensus decode */;

// Reject non-P2TR scripts
if !output.script_pubkey.is_p2tr() {
  Err(io::Error::other("received output was not P2TR"))?;
}
// Bind offset to script_pubkey: script must equal p2tr(key + G*offset)
// for the key this wallet scans (requires passing/expecting the base key),
// or at minimum verify the embedded x-only key parses to an even point.
```

Ideally `read` should take the base `ProjectivePoint` (or the `Scanner`'s script map) so it can reconstruct and compare `p2tr_script_buf(key + GENERATOR * offset)` against `output.script_pubkey`, rejecting any input where the two disagree — mirroring the enum/explicit-validation fix recommended in the original report.

### Proof of Concept
```rust
use bitcoin_serai::wallet::ReceivedOutput;
use bitcoin::{
  absolute::LockTime, transaction::Version, Amount, OutPoint, ScriptBuf, Transaction, TxIn, TxOut, Txid,
};
use k256::{elliptic_curve::group::Group, ProjectivePoint, Scalar};

// An attacker crafts a ReceivedOutput claiming funds were received to a script
// which does NOT correspond to key + G*offset (here: an arbitrary OP_RETURN / foreign script).
let mut bytes = vec![];
bytes.extend(Scalar::ZERO.to_bytes()); // offset: claims "no tweak"
let txout = TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: ScriptBuf::new_op_return(&[0xde, 0xad]), // unspendable, not P2TR
};
bytes.extend(bitcoin::consensus::serialize(&txout));
bytes.extend(bitcoin::consensus::serialize(&OutPoint {
  txid: Txid::all_zeros(),
  vout: 0,
}));

// Accepted without error despite the script being unspendable and inconsistent
// with ANY offset-derived key.
let output = ReceivedOutput::read::<&[u8]>(&mut bytes.as_ref()).unwrap();
assert_eq!(output.offset(), Scalar::ZERO);
assert_eq!(output.value(), 100_000); // reported as 100k sats of received funds
// Any downstream spend attempt will derive key + G*0, fail to match the
// script_pubkey, and produce an invalid/unspendable transaction — while the
// balance was already recorded as received.
```
