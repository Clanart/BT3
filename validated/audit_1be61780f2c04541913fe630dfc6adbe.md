## Title
Fee-on-transfer tokens cause escrow over-crediting and cross-order insolvency in Tron `IntentGatewayV2.placeOrder` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` computes the escrowed amount (`reducedInputs[i].amount`) purely from the caller-declared `order.inputs[i].amount` minus the protocol fee, and credits that computed value into `_orders[commitment][token]` **without ever measuring the token balance actually received** via `safeTransferFrom`. This is the direct analog of the reported ACOToken `_transferFromERC20` bug: if the escrowed ERC20 charges a transfer fee, the gateway receives less than the accounted amount, yet the contract's internal ledger and later withdrawal both use the unadjusted, higher nominal amount.

### Finding Description
In `placeOrder` [1](#0-0) , `reducedInputs[i].amount` is derived solely from `order.inputs[i].amount` (the user-supplied nominal amount) and the protocol fee bps — it is computed and the `commitment` is hashed **before** any tokens are moved.

The actual transfer then happens with no balance check: [2](#0-1) 
```
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
...
_orders[commitment][token] += reducedInputs[i].amount;
```
`safeTransferFrom` only guarantees the call itself does not revert and (via OpenZeppelin's `SafeERC20`) that the token contract returned success — it does **not** verify that the recipient's balance actually increased by `order.inputs[i].amount`. If the escrowed token charges any transfer fee (fee-on-transfer / deflationary token), the gateway's real token balance increases by less than `order.inputs[i].amount`, yet `_orders[commitment][token]` is credited with the full `reducedInputs[i].amount` computed from the nominal, pre-fee amount.

This is exactly the bug class from the external report: `_transferFromERC20`'s `require` on `success` does not protect against the recipient actually receiving less than requested, because ERC20-compliant fee-charging tokens still return `true`.

Contrast this with the canonical EVM implementation in `evm/src/apps/IntentGatewayV2.sol`, which explicitly guards against this by snapshotting balance before/after the transfer and mutating `order.inputs[i].amount` to the actual received delta before computing the commitment and escrow credit: [3](#0-2) 
```
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
```
The Tron contract lacks this safeguard entirely — for the predispatch path, the balance sweep does check `balance < requiredAmount` [4](#0-3)  but the *direct* (non-predispatch) transfer path at line 453 has no such check, and even the predispatch path still credits `_orders[commitment][token] += reducedInputs[i].amount` (the nominal reduced amount) rather than the measured `balance` actually swept.

At withdrawal time, `withdraw()` blindly transfers `body.tokens[i].amount` (set from the same nominal, over-credited `_orders` accounting) out to the beneficiary: [5](#0-4) 

### Impact Explanation
Because `_orders[commitment][token]` is credited with more than the contract's actual token balance increase, the gateway's internal accounting becomes unbacked by real funds for that fee-on-transfer token. When a solver fills the order and the settlement/`RedeemEscrow` path (`withdraw()`) pays out the escrowed amount, the contract will pay the nominal (over-stated) amount, drawing on token balance that in reality belongs to other users' escrowed orders using the same token — leading to insolvency where later legitimate withdrawals for unrelated orders revert or under-pay because the pooled token balance was already drained by an earlier over-credited order. This matches the bounty's "stealing or loss of funds" / "wrong beneficiary or amount" impact class: escrowed funds move in an amount not backed by what was actually deposited, extractable by any ordinary unprivileged user simply by placing an order with a fee-charging ERC20 as input.

### Likelihood Explanation
Any user can trigger this by placing an order (`placeOrder`) using any ERC20 that charges a transfer fee (or has similarly non-standard-but-compliant transfer semantics) as an input token — no relayer, prover, admin, or governance action required. This is a pure public-entrypoint path reachable by an unprivileged caller. The only precondition is that the deployment's supported token set includes (or later includes) a fee-on-transfer/rebasing-on-transfer ERC20, which is a realistic operational risk the same way it was flagged for ACOToken.

### Recommendation
Mirror the balance-delta pattern already used in `evm/src/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` before calling `safeTransferFrom`, compute the actual received delta after, and base both the commitment hash and the `_orders` escrow credit on that measured received amount rather than the caller-declared `order.inputs[i].amount`. Apply the same fix to the predispatch sweep path so `_orders[commitment][token]` is incremented by the measured swept `balance`, not `reducedInputs[i].amount`.

### Proof of Concept
1. Admin/deployer supports a fee-on-transfer ERC20 `FOT` (e.g. 1% fee) as a valid input token on the Tron `IntentGatewayV2` deployment.
2. User A calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`. The gateway actually receives only `990e18` FOT (1% fee deducted by the token), but `_orders[commitmentA][FOT]` is credited with `reducedInputs[0].amount` computed from `1000e18` (minus any protocol fee), i.e. an amount greater than what was actually received — see the transfer/credit at [6](#0-5) .
3. User B similarly places an order with the same `FOT` token, depositing real balance into the shared contract holdings.
4. When Order A settles via `withdraw()` (either `RedeemEscrow` from a cross-chain fill, or `cancelOrder` same-chain refund), the contract pays out the over-stated escrowed amount for A using pooled `FOT` balance that includes User B's real deposit, per [7](#0-6) .
5. User B's later withdrawal for their own order finds insufficient `FOT` balance remaining in the contract — their legitimate escrow is partially or fully lost, demonstrating fund loss/insolvency caused purely by placing orders with a standard-but-fee-charging ERC20.
