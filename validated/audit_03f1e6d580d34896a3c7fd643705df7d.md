### Title
Single Reverting Token in Multi-Asset Order Settlement Permanently Locks All Escrowed Funds - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
The `_withdraw()` function in `IntentsBase.sol` atomically releases *every* escrowed token for an order (inputs, native ETH, and the fee token) in a single loop. If any one of these transfers reverts — e.g. because the destination token blacklists the beneficiary (USDT-style), implements a reverting/gas-consuming transfer hook, or the beneficiary is a contract that rejects ETH — the entire `_withdraw()` call reverts, and with it every other, otherwise-uncomplicated token release for that order. There is no per-token processing, retry, or privileged-discard path, so the whole order's escrow (including tokens/fees unrelated to the failing transfer) becomes permanently stuck. This is the same bug class as the external report ("a single failed token transfer DoS's the rest of the queue") applied to Hyperbridge's intent-settlement escrow release instead of a withdrawal queue.

### Finding Description
`_withdraw()` is the single internal function used both to release a filled order to its beneficiary and to refund a cancelled/timed-out order back to the user: [1](#0-0) 

Key mechanics:
- `address beneficiary = address(uint160(uint256(body.beneficiary)))` — attacker/solver-influenced in the fill flow, or the original order-placer in the refund flow.
- The `for` loop at lines 394-410 iterates over *all* `body.tokens` for the order and performs either a native `.call{value: amount}("")` or `IERC20(token).safeTransfer(beneficiary, amount)` for each one, decrementing `_orders[commitment][token]` as it goes.
- Immediately after, if `finalize` is true, the accumulated protocol/transaction fee (`TRANSACTION_FEES`) is also transferred to the same beneficiary (lines 412-417).
- None of these calls are wrapped in a try/catch or otherwise isolated — a revert in `safeTransfer` for token `i` reverts the whole function, undoing state changes for tokens `0..i-1` as well (since Solidity reverts roll back all storage writes in the call), and prevents settlement of tokens `i+1..len-1` and the fee, forever, because there is no alternate code path to bypass token `i`.
- This affects both `IntrinsicIntents` (same-chain fills) and `ExtrinsicIntents` (cross-chain fills/refunds), since both compose on `IntentsBase._withdraw`, and the Tron variant (`evm/tron/contracts/apps/IntentGatewayV2.sol`) has the identical pattern: [2](#0-1) 

### Impact Explanation
An order that escrows multiple assets (e.g., a multi-input order, or any order that also escrows a `TRANSACTION_FEES` amount) can have **all of its escrowed value permanently frozen** if just one leg of the settlement reverts. This qualifies as "loss/lock of funds" and a "logic attack" under the bounty's accepted-impact list: an unprivileged party (the beneficiary itself, or anyone who can cause the beneficiary's token transfer to revert — e.g., a blacklisted/paused ERC-20, or a malicious receiving contract for the ETH leg) can render the entire order's escrow unwithdrawable, with no admin/governance recovery path defined in this contract. Unlike the original report's queue (where later withdrawals were merely delayed until the stuck one was fixed), here the funds belong to a *specific, already-determined* commitment with a fixed beneficiary and fixed escrowed tokens — once one leg is permanently un-transferable (e.g., beneficiary is blacklisted on that token forever), the *other legitimate assets in the same order are trapped too*, since there's no way to split the multi-token release.

### Likelihood Explanation
This does not require a malicious relayer, prover, or admin — only an ordinary ERC-20 with blacklist/pausable semantics (common, e.g. USDT/USDC) being used as one of several `TokenInfo` entries in an order, combined with the beneficiary being (or becoming) blacklisted for that specific token, or the beneficiary being a contract that reverts on receiving ETH for the native-token leg. Both are realistic, unprivileged conditions reachable through the normal `placeOrder`/`fillOrder`/refund flow, which are all public entry points.

### Recommendation
Decouple per-token settlement so a single failing transfer cannot block release of the other escrowed assets:
- Process each token transfer independently (e.g., wrap each transfer in a low-level call and record failures instead of reverting the whole function), or
- Move any failed-transfer amount into a separate "claimable/stuck balance" mapping that the beneficiary (or a privileged role) can retry or redirect later, mirroring the recommendation in the referenced report (accept a per-item identifier / allow discarding a single compromised leg rather than an atomic loop over unrelated assets).

### Proof of Concept
1. Attacker (as `user`) places a multi-input order via `placeOrder` where `order.inputs` includes both a normal ERC-20 (e.g., DAI) and a blacklist-capable token (e.g., USDT), plus `order.fees > 0` (escrowed as `TRANSACTION_FEES`).
2. A solver fills the order; `beneficiary` in `IntentsBase._withdraw`'s `WithdrawalRequest` is set to the solver's address (or, in the refund path, the original depositor's address).
3. Before settlement/refund executes, the beneficiary address gets blacklisted on the USDT-like token (a routine external event outside the protocol's control — e.g., an unrelated compliance action, or the attacker deliberately funds/uses an address they know will be blacklisted).
4. `_withdraw()` is invoked (via `fillOrder`'s internal call, or via the refund/timeout path). The loop reaches the USDT leg, `IERC20(token).safeTransfer(beneficiary, amount)` reverts (blacklisted receiver).
5. The entire transaction reverts: the DAI leg (which would have succeeded) is never transferred, and the escrowed `TRANSACTION_FEES` are never paid out either. `_orders[commitment][*]` remains unchanged, and every subsequent call to fill/refund/finalize this order will hit the exact same revert — the order's DAI and fee escrow are permanently locked alongside the blacklisted USDT amount, with no code path in `IntentsBase`/`IntentGatewayV2` to skip or discard the failing leg.
