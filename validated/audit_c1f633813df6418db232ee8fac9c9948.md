### Title
Empty `SchnorrAggregate` with `s = 0` verifies as a valid signature — "no signers" interpreted as valid ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
Analogous to CVE-2022-22941 (where Salt interpreted "no valid targets" as a valid target set), `SchnorrAggregate::verify` treats an aggregate covering zero signatures — with `s = 0` — as valid. An attacker-supplied encoding of `Rs = []` and `s = 0` passes verification whenever the verifier is invoked with an empty `keys_and_challenges` list, producing a forged "aggregate signature" attested by nobody.

### Finding Description
`SchnorrAggregate::read` accepts a `u32` count of `R` points followed by a scalar `s`, with no lower bound on the count — an empty `Rs` vector deserializes fine [1](#0-0) .

`verify` then only checks `self.Rs.len() == keys_and_challenges.len()` and evaluates `Σ z·R_i + Σ z_i·c_i·key_i − s·G == 0` via `multiexp_vartime` [2](#0-1) . When both lists are empty and `s = 0`, the only remaining pair is `(−0, G)`, which is the identity — so `verify` returns `true`. The transcript machinery never runs (`weight` is never invoked), so nothing binds the proof to any public key, nonce, or message.

Contrast with the prover side, which correctly refuses to emit an empty aggregate: `SchnorrAggregator::complete` returns `None` when `self.sigs.is_empty()` [3](#0-2) . The verifier does not enforce the same invariant on attacker-controlled input — exactly the "empty set accepted as valid" asymmetry from the Salt advisory.

### Impact Explanation
Any caller that verifies a `SchnorrAggregate` against a dynamically-constructed `keys_and_challenges` list (e.g., filtering signer/claim pairs extracted from the same untrusted payload as the aggregate) will accept a signature that no party produced whenever that list ends up empty. This is a signature-forgery primitive: the attacker controls the serialized proof bytes end-to-end via `SchnorrAggregate::read`, chooses the trivial forgery `len = 0, s = 0`, and wins without any private key. It converts "zero authorizations" into "authorized", the same permission-bypass shape as the Salt bug.

### Likelihood Explanation
Exploitation requires the verifying application to reach `verify` with an empty claim set — plausible in designs where claims are parsed out of attacker-provided data or filtered (e.g., claims for an unknown domain/network are dropped, leaving an empty list). The required proof bytes are 6 bytes total (`u32 = 0`, scalar `0`), so the attacker's cost is trivial whenever the trigger condition occurs.

### Recommendation
Reject empty aggregates in `verify`: return `false` when `self.Rs.is_empty()` (equivalently when `keys_and_challenges.is_empty()`), mirroring `SchnorrAggregator::complete`'s refusal to produce one. Optionally also reject `Rs.is_empty()` in `read` so the forgery fails at deserialization.

// Forged aggregate: zero R points, s = 0
let mut buf = vec![];
buf.extend(0u32.to_le_bytes());        // Rs.len() == 0
buf.extend(C::F::ZERO.to_repr());      // s == 0
let forged = SchnorrAggregate::<C>::read::<&[u8]>(&mut buf.as_ref()).unwrap();

// verify returns true: pairs reduces to (-0 * G) which is identity
assert!(forged.verify(b"some_dst", &[]));
```

Root cause lines: `read` imposes no non-empty constraint [4](#0-3)  and `verify` performs no empty-set rejection before the multiexp collapses to `(−s)·G` [5](#0-4) .

  pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
    if self.Rs.len() != keys_and_challenges.len() {
      return false;
    }

    let mut digest = DigestTranscript::<C::H>::new(dst);
    digest.domain_separate(b"signatures");
    for (_, challenge) in keys_and_challenges {
      digest.append_message(b"challenge", challenge.to_repr());
    }

    let mut pairs = Vec::with_capacity((2 * keys_and_challenges.len()) + 1);
    for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() {
      let z = weight(&mut digest);
      pairs.push((z, self.Rs[i]));
      pairs.push((z * challenge, *key));
    }
    pairs.push((-self.s, C::generator()));
    multiexp_vartime(&pairs).is_identity().into()
  }
```
