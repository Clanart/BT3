### Title
Malformed empty per-input signature-share vector panics during Bitcoin transaction completion - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`TransactionSignatureMachine::complete` trusts every participant-provided `Vec<SignatureShare<Secp256k1>>` to contain one share for each transaction input and calls `shares.remove(0)` without checking that the vector is non-empty, causing an out-of-bounds panic on an empty share vector. [1](#0-0) 

### Finding Description
For Bitcoin transactions, `SignMachine::SignatureShare` is a vector containing one Schnorr share per transaction input. [2](#0-1)  The completion routine iterates over every transaction input, removes the first element from each supplied per-participant vector, and passes the resulting scalar shares into the per-input FROST completion routine. [3](#0-2)  If a participant supplies an empty vector, `Vec::remove(0)` panics before the malformed input can be rejected as a FROST error. [3](#0-2)  This is the same zero-count followed by first-element-access pattern as the external report: the malformed message parses or reaches the completion boundary successfully, while the crash occurs when the first expected element is accessed.

### Impact Explanation
A participating signer can abort transaction completion on the local node by submitting an empty per-input share vector instead of a vector containing one `SignatureShare` per input. [1](#0-0)  Because the panic occurs while the signer is attempting to complete a Bitcoin spend, this can deny availability of the threshold wallet’s signing path until the process is restarted or the malformed peer input is discarded. [4](#0-3) 

### Likelihood Explanation
The malformed state is representable in the public `complete` API because its `SignatureShare` type is only `Vec<SignatureShare<Secp256k1>>` and the routine does not validate its length before indexing. [5](#0-4)  The crate’s own `read_share` helper parses exactly one scalar per input, so a byte stream decoded exclusively through that helper cannot normally produce this truncated vector. [6](#0-5)  An integration that receives or constructs the public nested share message through another transport encoding can nevertheless expose the panic path, making this a reachable malformed-message denial of service rather than merely an internal invariant violation. [2](#0-1) [1](#0-0) 

### Recommendation
Validate every supplied share vector’s length against `self.tx.input.len()` before calling `remove(0)`, and return `FrostError` instead of panicking on a short or empty vector. [1](#0-0)  Prefer consuming a fixed-size or explicitly validated representation, or replace `remove(0)` with fallible access such as checking `is_empty()`/`get(0)` before constructing the per-input map. [3](#0-2)

The panic site is the unconditional `shares.remove(0)` performed once for each input when building the per-input completion map. [3](#0-2)

pub struct TransactionSignatureMachine {
  tx: Transaction,
  sigs: Vec<AlgorithmSignatureMachine<Secp256k1, Schnorr>>,
}

impl SignatureMachine<Transaction> for TransactionSignatureMachine {
  type SignatureShare = Vec<SignatureShare<Secp256k1>>;

  fn read_share<R: Read>(&self, reader: &mut R) -> io::Result<Self::SignatureShare> {
    self.sigs.iter().map(|sig| sig.read_share(reader)).collect()
  }

  fn complete(
    mut self,
    mut shares: HashMap<Participant, Self::SignatureShare>,
  ) -> Result<Transaction, FrostError> {
    for (input, schnorr) in self.tx.input.iter_mut().zip(self.sigs.drain(..)) {
      let sig = schnorr.complete(
        shares.iter_mut().map(|(l, shares)| (*l, shares.remove(0))).collect::<HashMap<_, _>>(),
      )?;

      let mut witness = Witness::new();
      witness.push(sig);
      input.witness = witness;
    }

    Ok(self.tx)
  }
