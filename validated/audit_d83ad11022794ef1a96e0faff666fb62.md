### Title
Zero-valued `kip71.gastarget` governance parameter causes division-by-zero panic in `KIP71Config.NextMagmaBlockBaseFee` - ([File: params/kip71_config.go])

### Summary
`NextMagmaBlockBaseFee` divides by the governance-controlled `GasTarget` parameter when computing the next block's base fee under Magma/KIP-71 dynamic pricing. Unlike the sibling parameter `Kip71MaxBlockGasUsedForBaseFee` (whose value `0` is explicitly rejected in tests), `Kip71GasTarget` uses `noopFormatChecker`, which accepts any `uint64` including `0`. A `GasTarget` of `0` causes a division by zero (Go `big.Int.Div` panic) in the consensus-critical base-fee calculation, executed by every node when validating or building any block whose parent used more than zero gas.

### Finding Description
`Kip71GasTarget` is registered with `FormatChecker: noopFormatChecker`, which always returns `true`: [1](#0-0) [2](#0-1) 

`checkConsistency` in the header governance module explicitly allows `gov.Kip71GasTarget` votes to pass through with no additional value checks beyond the (no-op) format check: [3](#0-2) 

This contrasts with `Kip71MaxBlockGasUsedForBaseFee`, where the test suite explicitly asserts that `value: 0` is a **bad** vote (rejected), showing zero-rejection was consciously implemented for that parameter but not for `GasTarget`: [4](#0-3) 

The actual computation in `NextMagmaBlockBaseFee` uses `gasTarget := kc.GasTarget` directly as a divisor with no zero-check: [5](#0-4) [6](#0-5) 

If `GasTarget == 0` and `parentGasUsed > 0` (true for essentially any real block that uses gas), the code takes the "usage above target" branch, computes `gasUsedDelta := parentGasUsed - gasTarget`, then calls:
```go
y := x.Div(x, new(big.Int).SetUint64(gasTarget)) // gasTarget == 0 → panic
```
This is a division by zero on a `big.Int`, which panics the Go process (unlike Solidity's `revert`, a Go panic in this path — if unrecovered — crashes the node process or, if recovered somewhere up the call stack, at minimum aborts block processing).

This function is invoked from consensus-critical code paths: header verification (`VerifyMagmaHeader`, called from `blockchain/block_validator.go`) and block building (`work/worker.go`), meaning both the block proposer and every validating/full node performs this calculation for every block once the governance parameter takes effect.

### Impact Explanation
Because `GasTarget` is a live governance parameter votable via `kip71.gastarget` (as confirmed by the vote serialization/format tests accepting arbitrary `uint64` values including small ones), a single successful governance vote setting it to `0` would cause **all nodes** (validators and full nodes) to panic identically when computing/validating the base fee for the next block that has nonzero gas usage. This is a chain-halting event, not a "no impact" bug — it would either crash node processes network-wide or, if callers recover the panic, cause inconsistent/rejected blocks and validator downtime, both of which are explicit target impacts (invalid transaction/block acceptance issues and state divergence risk) under the analog criteria.

### Likelihood Explanation
The trigger requires only a normal governance vote flow — the same mechanism used to legitimately update `GasTarget`, `LowerBoundBaseFee`, etc. There is no additional access control preventing a governing entity (single-mode governing node, or council majority in ballot mode) from voting `GasTarget = 0`; the format checker is a no-op and `checkConsistency` performs no extra range validation for this parameter (unlike `LowerBoundBaseFee`/`UpperBoundBaseFee`, which do have explicit consistency checks). Given normal blocks almost always have nonzero gas usage, the panic would trigger on the very next block after the vote takes effect, making this a high-likelihood, low-complexity governance-parameter DoS once such a vote is cast.

### Recommendation
Add an explicit zero-check for `GasTarget` in `NextMagmaBlockBaseFee`, mirroring the existing zero-guard already implemented for `BaseFeeDenominator`: [7](#0-6) 
e.g., fall back to `DefaultGasTarget` (or reject with a safe non-panicking default) when `kc.GasTarget == 0`. Additionally, add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0`, consistent with the existing rejection of `0` for `Kip71MaxBlockGasUsedForBaseFee`, and add a corresponding consistency check in `checkConsistency` (`kaiax/gov/headergov/impl/header.go`) to reject `GasTarget == 0` votes at the header-verification stage before they can be committed to chain governance state.

### Proof of Concept
1. Submit/pass a governance vote setting `kip71.gastarget = 0` (accepted because `noopFormatChecker` returns `true` for any `uint64`, and `checkConsistency` performs no extra validation for `Kip71GasTarget`).
2. Once the vote is committed and applied at the next epoch, the `GasTarget` in the effective `KIP71Config` becomes `0`.
3. On the very next block after the vote takes effect, any block with `parentGasUsed > 0` causes `NextMagmaBlockBaseFee` to execute:
   ```go
   gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - 0) // = parentGasUsed
   x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
   y := x.Div(x, new(big.Int).SetUint64(0)) // panic: division by zero
   ```
   This is confirmed directly by the code at `params/kip71_config.go:100-102` (and the symmetric branch at lines 118-120), with no existing test covering `gasTarget == 0` (the `TestEvenBaseFee` table in `params/kip71_config_test.go` never sets `gasTarget: 0`, while it does test `lowerBoundBaseFee: 0` and `upperBoundBaseFee: 0`, indicating this specific zero case was not defended against).

Note: I could not fully trace the exact call chain from `work/worker.go`/`blockchain/block_validator.go` into `NextMagmaBlockBaseFee` due to tool/iteration limits, but the two call sites were confirmed to exist via `grep_search`, and the function is package-level exported logic clearly designed to run on both header-verification and block-building paths.
