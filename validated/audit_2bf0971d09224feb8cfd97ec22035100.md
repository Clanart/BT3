Confirmed: `registerERC20` (in `x/erc20/keeper/proposals.go`) performs no validation against fee-on-transfer, deflationary, or rebasing ERC20 semantics — any arbitrary ERC20 contract can be permissionlessly registered via `MsgRegisterERC20` as long as it exposes standard metadata. This confirms the attack precondition: an attacker/user can register a fee-on-transfer ERC20 as a native token pair, then trigger the vulnerable code path.

### Title
Permanent loss of user IBC funds when fee-on-transfer/rebasing native ERC20 token pairs fail the strict balance-invariance check in `ConvertCoinNativeERC20` during IBC ack/timeout auto-conversion - (File: x/erc20/keeper/msg_server.go, x/erc20/keeper/ibc_callbacks.go)

### Summary
`ConvertCoinNativeERC20` escrows a user's bank coins into the `x/erc20` module account *before* verifying that the equivalent amount of ERC20 tokens was actually unescrowed to the receiver. It enforces exact equality (`balanceTokenAfter.Cmp(exp) != 0`) between the token amount and observed ERC20 balance delta. For any fee-on-transfer, deflationary, or rebasing ERC20 token registered as a native token pair, this check always fails, causing the function to return an error *after* the coins have already been irreversibly escrowed — but *before* they are burned or refunded. When this function is invoked from the IBC acknowledgement/timeout refund path (`ConvertCoinToERC20FromPacket`), the caller silently swallows the error (emits an event and returns `nil`), permanently trapping the user's just-refunded IBC funds in the module account with no compensating mint, burn, or refund.

### Finding Description
`ConvertCoinNativeERC20` at [1](#0-0)  performs, in order:
1. `SendCoinsFromAccountToModule` — escrows the user's native coins into the `erc20` module account.
2. `CallEVM(... "transfer" ...)` — attempts to unescrow the equivalent ERC20 tokens from the module to the receiver.
3. A strict balance check: `if r := balanceTokenAfter.Cmp(exp); r != 0 { return ErrBalanceInvariance }` at [2](#0-1) .
4. Only if step 3 passes does it `BurnCoins` the escrowed coins.

For a fee-on-transfer or rebasing ERC20 (which `registerERC20` does not filter out, per [3](#0-2) ), the `transfer()` call in step 2 delivers less (or more, for rebasing/inflationary tokens) than `amount` to the receiver, so the strict equality check in step 3 always fails. The function returns an error, **but step 1's escrow already happened and is not rolled back within this function**, and step 4 (burn) never runs — the coins are simply stuck in the module account.

This function is invoked from `ConvertCoinToERC20FromPacket` at [4](#0-3) , which is the automatic coin→ERC20 conversion run after an IBC transfer fails (error acknowledgement) or times out. In this flow, the ICS20 transfer module has *already* refunded the original sender's escrowed source-chain tokens back into their bank balance. The erc20 middleware then attempts to auto-convert those refunded bank coins into the ERC20 representation for convenience. When this conversion hits the balance-invariance failure described above, `ConvertCoinToERC20FromPacket` catches the error, emits `EventTypeFailedConvertERC20`, and returns `nil` — i.e., it treats the failure as a soft/no-op event rather than restoring the coins to the sender. Because the coin escrow in step 1 already occurred and is not undone, and burn never happens, the user's refunded IBC funds are irrecoverably locked in the `erc20` module account, with no code path that returns them to the user or reconverts them later.

The same strict/asymmetric-fee-blind check exists in `convertERC20IntoCoinsForNativeToken` (`ConvertERC20`, msg-initiated path) at [5](#0-4) , but there the whole `MsgConvertERC20` fails atomically inside a normal transaction, so no state is committed. The critical divergence is specifically the IBC ack/timeout auto-conversion path, where the surrounding caller intentionally swallows the error to avoid failing the overall packet-lifecycle handler, exposing the already-mutated (escrowed) state as a permanent loss.

### Impact Explanation
This is a **Critical, permanent freezing/locking of user funds** matching the required impact gate: an unprivileged user can permissionlessly register (`MsgRegisterERC20`) any fee-on-transfer/rebasing ERC20 contract as a native token pair (no filtering exists per `registerERC20`/`CreateCoinMetadata`), and any IBC transfer of that token pair's denom that times out or errors will result in the sender's refunded coins being escrowed into the `erc20` module account and never burned, minted as ERC20, or returned — a real, irreversible loss of spendable user value.

### Likelihood Explanation
Likelihood is high given: (1) ERC20 registration is permissionless per `RegisterERC20`/`registerERC20`, requiring no code audit or fee-on-transfer detection; (2) any user can trigger an IBC transfer timeout/error ack simply by using a channel/counterparty that fails or times out, which is routine and does not require a malicious relayer; (3) the vulnerable code path executes automatically as IBC middleware without any special privilege.

### Recommendation
- Compute the expected receiver balance delta accounting for potential transfer fees/rebasing rather than assuming an exact 1:1 transfer, or reject registration of token pairs whose ERC20 contracts behave non-standardly (verify actual vs. expected balances during `RegisterERC20`).
- In `ConvertCoinNativeERC20`, if the post-transfer balance check fails, refund the escrowed coins back to the original owner before returning the error, so no state remains "escrowed but neither burned nor refunded."
- In `ConvertCoinToERC20FromPacket`, do not silently swallow `ConvertCoinNativeERC20` errors as a no-op event; ensure the underlying coins remain (or are restored) in the user's spendable balance whenever the ERC20 conversion does not complete successfully.

### Proof of Concept
1. Permissionlessly register a fee-on-transfer ERC20 contract (e.g., one that deducts 1% on `transfer`) via `MsgRegisterERC20`, creating a native token pair (`registerERC20`, no fee-on-transfer validation).
2. A user (or the same attacker) sends an IBC transfer of the token-pair's coin denom outbound; the source chain escrows the coin normally via the standard ICS20 transfer app.
3. Cause the packet to time out or receive an error acknowledgement (e.g., target chain doesn't have the denom registered, or relay is delayed past timeout — both are ordinary, unprivileged conditions).
4. `OnTimeoutPacket`/`OnAcknowledgementPacket` triggers `ConvertCoinToERC20FromPacket`, which first lets the ICS20 transfer module refund the sender's coins, then calls `ConvertCoinNativeERC20` to auto-convert them to ERC20.
5. `ConvertCoinNativeERC20` escrows the just-refunded coins into the `erc20` module account, calls `transfer()` on the fee-on-transfer ERC20 (receiver gets 99% of `amount`), then the strict equality check `balanceTokenAfter.Cmp(exp) != 0` fails, returning `ErrBalanceInvariance` without burning the escrowed coins.
6. `ConvertCoinToERC20FromPacket` catches the error, emits `EventTypeFailedConvertERC20`, and returns `nil` — the transaction succeeds, but the user's refunded coins are now permanently held (never burned, never re-credited) in the `erc20` module account with no available recovery path.

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

	// Check unpackedRet execution
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return err
		}
		if !unpackedRet.Value {
			return sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute unescrow tokens from user")
		}
	}

	// Check expected Receiver balance after transfer execution
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceTokenAfter == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	exp := big.NewInt(0).Add(balanceToken, amount.BigInt())

	if r := balanceTokenAfter.Cmp(exp); r != 0 {
		return sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v", exp, balanceTokenAfter,
		)
	}

	// Burn escrowed Coins
	err = k.bankKeeper.BurnCoins(ctx, types.ModuleName, coins)
	if err != nil {
		return sdkerrors.Wrap(err, "failed to burn coins")
	}

	return nil
}

func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
}
