### Title
Forfeit calculation in `mWOMSVBaseRewarder._calExpireForfeit` is a dead check that always returns zero forfeiture, letting stakers claim full rewards while bypassing the early-withdrawal/lock-duration penalty - (File: `rewards/mWOMSVBaseRewarder.sol`)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` is supposed to compute how much of a user's accrued reward should be forfeited based on their "rewardable percent" (i.e., how much of the lock period the user actually respected), analogous to what `vlMGPBaseRewarder._calExpireForfeit` does. Instead, the function sets the rewardable amount equal to the full claimed amount before performing the comparison, making the guard and subtraction vacuous — this mirrors the reported bug class where a check is rendered always-true/false because the value being validated is mutated (here: pre-assigned) before the meaningful comparison happens.

### Finding Description
In `rewards/mWOMSVBaseRewarder.sol`: [1](#0-0) 

```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();

    uint256 forfeitAmount = _amount - rewardableAmount;
    ...
}
```

`rewardableAmount` is assigned `_amount` directly instead of being derived from the user's actual unlock/lock status (e.g. via `mWOMSV.getRewardablePercentWAD(_account)`). Because of this, `rewardableAmount > _amount` can never be true, and `forfeitAmount = _amount - rewardableAmount` is always `0`. This is functionally the same defect class as the Pico report: a constraint/check is defeated because the compared value has already been forced to satisfy it before the check runs.

The correct pattern exists in the sibling contract `rewards/vlMGPBaseRewarder.sol`, which actually computes the rewardable share from the locker before comparing: [2](#0-1) 

This confirms `mWOMSVBaseRewarder` diverged from the intended design and lost the forfeit mechanism entirely.

The forfeited amount is meant to be re-queued into the reward pool for other continuing stakers via `_queueNewRewardsWithoutTransfer`, as seen in `_sendReward`: [3](#0-2) 

Since `forfeitAmount` is always `0`, this re-queuing never happens — the yield that should be forfeited by early/partial unlockers and redistributed to other unprivileged mWOMSV holders is instead paid out in full to the withdrawing user.

### Impact Explanation
Any ordinary wallet holding mWOMSV and claiming rewards through this rewarder bypasses the intended penalty for not fully honoring the cooldown/lock schedule, and receives 100% of accrued rewards regardless of `getRewardablePercentWAD`. This directly causes permanent loss of unclaimed yield that should have accrued to other continuing stakers (theft of yield that belongs to other unprivileged users in the pool), since the amount that should be requeued as `ForfeitRewardAdded` never materializes.

### Likelihood Explanation
High likelihood — this path is triggered on every normal reward claim/harvest by any staker in the mWOMSV reward pool, requires no privileged role, and does not depend on any external/oracle condition. It is a straightforward "off" invariant baked into every claim.

### Recommendation
Fix `_calExpireForfeit` in `rewards/mWOMSVBaseRewarder.sol` to compute `rewardableAmount` from the account's actual rewardable percentage (mirroring `vlMGPBaseRewarder`'s use of `getRewardablePercentWAD`), e.g.:
```solidity
uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
```
so the subsequent comparison and forfeiture logic operate on the intended, non-trivial value.

### Proof of Concept
1. A user stakes mWOMSV in `mWOMSVBaseRewarder`, accrues rewards, and is only partially through their unlock cooldown (i.e., `getRewardablePercentWAD` for the underlying `mWomSV` locker would be less than 100%).
2. User calls the claim path that leads to `_sendReward` → `_calExpireForfeit(_account, userRewards[...])`.
3. Because `rewardableAmount = _amount` is set unconditionally, `forfeitAmount` computed at line 390 is always `0`, so `toSend = userRewards[...] - 0` — the user receives the full reward.
4. `_queueNewRewardsWithoutTransfer` is never invoked with a nonzero forfeit, so the yield that should have been redistributed to other stakers (per protocol design, as demonstrated by the correct implementation in `vlMGPBaseRewarder.sol`) is instead fully paid to the early/partial unlocker, permanently denying that yield to the rest of the pool.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
