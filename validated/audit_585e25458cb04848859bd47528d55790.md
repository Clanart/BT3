### Title
Uncaught integer-underflow exception in `MempoolManager.validate_spend_bundle()` fee calculation allows a minting spend bundle to crash mempool admission instead of being cleanly rejected - (File: `chia/full_node/mempool_manager.py`)

### Summary
`MempoolManager.validate_spend_bundle()` computes the transaction fee as `fees = uint64(removal_amount - addition_amount)` without first verifying that the sum of removed (spent) coin amounts is at least the sum of added (created) coin amounts. If a submitted spend bundle creates more total value than it consumes (an inflationary/minting bundle), the subtraction goes negative and the `uint64()` constructor raises instead of the code returning a controlled `Err` value, mirroring the reported `LinearMath._toNominal()` underflow-revert-when-it-should-produce-a-defined-result class of bug.

### Finding Description
In consensus block-body validation, the same arithmetic is guarded explicitly: [1](#0-0) 
`if removed < added: return Err.MINTING_COIN` is checked *before* `fees = removed - added` is computed, so the subtraction can never underflow there.

However, in the mempool admission path (`MempoolManager.validate_spend_bundle()`, which is the function that processes every spend bundle submitted by an unprivileged caller via `push_tx`), no equivalent check exists before the fee is computed: [2](#0-1) 

`removal_amount` and `addition_amount` are accumulated directly from the coin spends and their `CREATE_COIN` conditions: [3](#0-2) [4](#0-3) 

There is no `if removal_amount < addition_amount: return Err.MINTING_COIN` (or similar) guard before the `uint64(removal_amount - addition_amount)` cast, unlike the equivalent consensus-level check. `uint64` here is `chia_rs.sized_ints.uint64`, a bounds-checked integer type that raises on construction from a negative value rather than saturating or returning an error code.

An unprivileged user can submit a spend bundle whose `CREATE_COIN` outputs sum to more than the sum of the amounts of the coins being spent (this is otherwise a normal, well-formed spend bundle from a CLVM/cost perspective — it simply attempts to mint value, something the code is *supposed* to detect and reject with a clean error, not crash on).

### Impact Explanation
This is the mempool-admission analog of the reported bug class: a computation on attacker-controlled inputs performs an unguarded subtraction expecting the invariant `removal_amount >= addition_amount` to always hold, but the check that would normally establish that invariant (present in `block_body_validation.py`) is missing at this call site. Instead of a bounded `Err.MINTING_COIN` rejection, the code path raises an unhandled Python exception from the `uint64()` constructor while validating a spend bundle. Depending on how far up the call stack this exception is caught, this can disrupt processing of that spend-bundle validation call in the mempool manager, which is reachable by any unprivileged spend-bundle submitter through the public transaction-submission RPC.

### Likelihood Explanation
High reachability: any wallet user or offer counterparty can construct a spend bundle whose puzzle reveal issues `CREATE_COIN` conditions summing to more than the coin's amount (there's nothing in CLVM puzzle execution itself preventing this; it is exactly the case the consensus layer's `MINTING_COIN` check exists to catch) and submit it via `push_tx`. No special privileges, signatures matching a real minting condition, or malicious node/peer behavior are required — it is a pure client-side crafted bundle.

### Recommendation
Add an explicit guard in `MempoolManager.validate_spend_bundle()` mirroring the consensus check in `block_body_validation.py`:
```python
if removal_amount < addition_amount:
    return Err.MINTING_COIN, None, []
fees = uint64(removal_amount - addition_amount)
```
This makes the mempool-admission path fail closed with a defined `Err` code instead of relying on an uncontrolled exception from the `uint64` constructor.

### Proof of Concept
1. Construct a spend bundle spending a coin of amount `X`.
2. Have its puzzle reveal emit `CREATE_COIN` conditions whose amounts sum to `Y > X` (e.g., spend a 100-mojo coin but create a 1000-mojo coin — trivially expressible with any puzzle the submitter controls, e.g., the standard "anyone can spend" test puzzle used in the codebase's own tests).
3. Submit this spend bundle through the wallet/RPC `push_tx` path so it reaches `MempoolManager.validate_spend_bundle()`.
4. At [5](#0-4)  `removal_amount - addition_amount` evaluates to a negative Python int, and `uint64(...)` raises instead of the function returning `Err.MINTING_COIN` as intended by the analogous consensus-level check at [6](#0-5) .
