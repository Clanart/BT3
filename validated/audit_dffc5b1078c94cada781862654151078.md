### Title
Spoofed `OutputType` via publicly derivable offset addresses causes output type confusion and mishandled funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
CVE-2017-11862 was a type confusion where a code path failed to handle a node variant, so an object was interpreted as the wrong type. The analog in Serai is the classification of scanned Bitcoin outputs: an output's `OutputType` (`External`, `Branch`, `Change`, `Forwarded`) is inferred solely from which registered offset produced the matching `script_pubkey`, and all of those offset addresses are publicly derivable from the multisig group key. Any unprivileged party can therefore craft an output that the processor interprets as an internal type, causing funds to be dropped or internal state (pending forwards) to be consumed spuriously.

### Finding Description
`Scanner` maps `script_pubkey` → offset, and nothing else. `scan_transaction` classifies any output whose script equals a registered P2TR script as belonging to that offset, with no witness/origin distinction. [1](#0-0) 

The processor then maps the recovered offset back to an `OutputType` via the `kinds` table. The offsets for `Branch`, `Change`, and `Forwarded` are deterministic: `Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch" | b"change" | b"forward")`, incremented until the resulting tweaked key is even-Y. [2](#0-1)  Since `register_offset` documents that offsets are surjective and derived from a fixed DST, any observer who knows the group key can compute all internal addresses — `forward_address` even returns them openly. [3](#0-2)  An `External` deposit sent to one of these scripts is then tagged `Branch`/`Change`/`Forwarded` instead of `External`. [4](#0-3) 

Downstream, `scanner_event_to_multisig_event` handles kinds distinctly: `Forwarded` outputs trigger `ForwardedOutputDb::take_forwarded_output(txn, output.balance())` — which pops a pending instruction purely by matching the balance amount — and non-`External`, non-forwarded outputs are dropped entirely via `outputs.retain(|o| o.kind() == OutputType::External)`. [5](#0-4) 

### Impact Explanation
Two concrete harms from public inputs (anyone can send a Bitcoin transaction):

1. **Funds received but never credited/spendable.** A depositor (or attacker paying to a known-internal script) sends to the `Change`/`Branch` address. The output is scanned, tagged non-`External`, dropped by the retain filter, and never produces an instruction — the funds sit at a script the processor ignores as a deposit, effectively lost from the user's accounting even though they are on-chain.
2. **Spurious forwarding confirmation.** An output sent to the `Forwarded` script with an amount matching a pending instruction's recorded balance causes `take_forwarded_output` to consume that pending instruction and emit it as though the multisig's own forward transaction completed — type confusion between "our forward succeeded" and "someone paid the forward address," corrupting instruction flow.

### Likelihood Explanation
The internal scripts are deterministic functions of the public group key and a fixed DST — no secret is needed to compute them. Any Bitcoin user can craft such a transaction at the cost of the output value. The matching-amount requirement for forward spoofing bounds its profitability, but deposit misclassification is trivially reachable. Medium severity.

### Recommendation
Distinguish output provenance, not just script: for `Forwarded`/`Change`/`Branch` matches, require the spending transaction to have been authored by the multisig (e.g., only accept internal-kind outputs from transactions whose inputs spend known multisig outpoints), and treat pays to internal scripts from foreign transactions as `External` deposits or explicitly reject/alert rather than silently dropping them.

### Proof of Concept
1. Observe the multisig group key `K` (public on the coordinator).
2. Compute `branch_offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch")`, incremented until `p2tr_script_buf(K + G*offset)` returns `Some` (replicating `register_offset` at `networks/bitcoin/src/wallet/mod.rs:180-196`).
3. Send a transaction paying to that script in a confirmed block.
4. `get_outputs` tags it `OutputType::Branch`; `scanner_event_to_multisig_event` drops it — no instruction is emitted and the deposit is never credited.

    let mut res = Vec::new();

      // If the vout index exceeds 2**32, stop scanning outputs

          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res

const KEY_DST: &[u8] = b"Serai Bitcoin Output Offset";
static BRANCH_OFFSET: OnceLock<Scalar> = OnceLock::new();
static CHANGE_OFFSET: OnceLock<Scalar> = OnceLock::new();
static FORWARD_OFFSET: OnceLock<Scalar> = OnceLock::new();

// Always construct the full scanner in order to ensure there's no collisions
fn scanner(
  key: ProjectivePoint,
) -> (Scanner, HashMap<OutputType, Scalar>, HashMap<Vec<u8>, OutputType>) {
  let mut scanner = Scanner::new(key).unwrap();
  let mut offsets = HashMap::from([(OutputType::External, Scalar::ZERO)]);

  let zero = Scalar::ZERO.to_repr();
  let zero_ref: &[u8] = zero.as_ref();
  let mut kinds = HashMap::from([(zero_ref.to_vec(), OutputType::External)]);

  let mut register = |kind, offset| {
    let offset = scanner.register_offset(offset).expect("offset collision");
    offsets.insert(kind, offset);

    let offset = offset.to_repr();
    let offset_ref: &[u8] = offset.as_ref();
    kinds.insert(offset_ref.to_vec(), kind);
  };

  register(
    OutputType::Branch,
    *BRANCH_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"branch")),
  );
  register(
    OutputType::Change,
    *CHANGE_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"change")),
  );
  register(
    OutputType::Forwarded,
    *FORWARD_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"forward")),
  );

  (scanner, offsets, kinds)
}
