### Title
Empty DLEq statement list accepts a forged proof - ([File: crypto/dleq/src/lib.rs](crypto/dleq/src/lib.rs))

### Summary
`DLEqProof::verify` only checks that `generators.len() == points.len()` before evaluating the Fiat-Shamir challenge. When both lists are empty, no group statement is appended to the transcript, so an attacker can set the serialized `c` value to the deterministic challenge and make verification succeed without proving any discrete-logarithm relationship.

### Finding Description
`DLEqProof::read` accepts two canonical scalars, `c` and `s`, without semantic validation [1](#0-0) . Verification checks only the lengths of `generators` and `points`, iterates over zero statements when both are empty, and then compares `self.c` with the transcript challenge [2](#0-1) . The root cause is analogous to accepting an uploaded object without validating that it satisfies the expected object type: the API accepts an empty statement domain even though a proof over zero generators proves nothing.

`MultiDLEqProof::verify` has the same boundary issue for a zero-length `generators`/`points` pair after checking only their lengths [3](#0-2) .

### Impact Explanation
This is a forged-proof condition: a proof decoded from attacker-controlled bytes can verify while establishing no equality of discrete logarithms. The concrete security effect depends on the caller: any production protocol path that lets public input select an empty generator/point list would accept a proof of a false statement. In Serai's in-scope promotion code, `GeneratorPromotion::complete` supplies fixed two-element generator and point arrays, so that path is not reachable with this empty-list condition [4](#0-3) .

### Likelihood Explanation
An unprivileged caller can supply arbitrary bytes to `DLEqProof::read`; canonical scalar parsing does not prevent choosing `c`. Exploitation requires the verifier to evaluate `DLEqProof::verify` with empty `generators` and `points` slices. If no production caller permits that state, the reachable impact is limited to misuse of the generic API; the identified in-scope callers investigated use fixed non-empty statement lists.

### Recommendation
Reject empty statement sets at the API boundary. In `DLEqProof::verify`, return `InvalidProof` when `generators.is_empty()` or `points.is_empty()` before transcript processing. Apply the same check to each series and the outer list in `MultiDLEqProof::verify`, and add regression tests asserting that empty proofs cannot verify.

### Proof of Concept
Conceptually, for any transcript initialization `T`:

1. Build `transcript = T`.
2. Apply `transcript.domain_separate(b"dleq")`.
3. Compute `expected_c = challenge(&mut transcript)` using the same transcript and challenge-reduction logic as `DLEqProof::verify`.
4. Serialize `DLEqProof { c: expected_c, s: 0 }`.
5. Parse it with `DLEqProof::read`.
6. Call `verify(&mut T::new(...), &[], &[])`.

The verifier checks `0 == 0`, performs no `verify_statement` calls, derives the same deterministic `expected_c`, and returns `Ok(())` even though no discrete logarithm was bound to the proof.

    if generators.len() != points.len() {
      Err(DLEqError::InvalidProof)?;

  pub fn verify<T: Transcript>(
    &self,
    transcript: &mut T,
    generators: &[Vec<G>],
    points: &[Vec<G>],
  ) -> Result<(), DLEqError> {
    if points.len() != generators.len() {
      Err(DLEqError::InvalidProof)?;
    }
    if self.s.len() != generators.len() {
      Err(DLEqError::InvalidProof)?;
    }

    transcript.domain_separate(b"multi_dleq");
    for (i, (generators, points)) in generators.iter().zip(points).enumerate() {
      if points.len() != generators.len() {
        Err(DLEqError::InvalidProof)?;
      }

      transcript.append_message(b"discrete_logarithm", i.to_le_bytes());
      for (generator, point) in generators.iter().zip(points) {
        DLEqProof::verify_statement(transcript, *generator, *point, self.c, self.s[i]);
      }
    }

    if self.c != challenge(transcript) {
      Err(DLEqError::InvalidProof)?;
    }

    Ok(())
