### Title
CEI violation in `withdraw()` allows escrow-balance decrement to be bypassed via reentrant hookable token during cross-chain settlement - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2`'s internal `withdraw()` function transfers escrowed tokens to the beneficiary via a raw low-level `token.call(...)` **before** decrementing the corresponding `_orders[commitment][token]` escrow-accounting entry, mirroring exactly the check-effect-interact violation described in the external Basket.sol `mintTo`/`burn` report (external call before state update, exploitable when the token has transfer callbacks).

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` (triggered from `onAccept` for `RedeemEscrow`/`RefundEscrow` messages, and from `onGetResponse` for source-side cancellations) processes each escrowed token as: [1](#0-0) 

```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();

if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

The `_orders[commitment][token]` decrement happens **after** the raw `.call` transfer — this is the same ordering defect flagged in Basket.sol. Only `_filled[body.commitment]` is set up-front (line 684), which blocks reentry into the order-level public functions (`fillOrder`, `cancelOrder`) for that specific commitment, but it does **not** protect the per-token escrow accounting itself. Since `order.inputs` (the escrowed token list) is fully attacker-controlled at `placeOrder()` time — the "user" placing the order chooses which token contracts to escrow — an attacker can escrow a token contract they control that implements a transfer hook (ERC-777-style `tokensToSend`/`tokensReceived`, or simply a malicious `transfer()` implementation), triggering arbitrary code during the low-level `.call`.

This is a materially weaker CEI pattern than the already-corrected version of the same logic in the main EVM contract, `IntentsBase.sol::_withdraw()`, which explicitly decrements escrow **before** transferring: [2](#0-1) 

```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    ...
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
```

The `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol` suite explicitly documents that this exact CEI ordering was previously broken and was fixed for the mainline EVM contracts by moving `_filled[commitment]` assignment (and escrow decrement) before external calls: [3](#0-2) 

The Tron variant of `withdraw()` was not updated to apply the same fix to the `_orders` mapping decrement, leaving the raw external `.call` ahead of the state write.

### Impact Explanation
If a malicious/hookable token contract is used as an order input (`order.inputs`), its transfer hook executes while `_orders[commitment][token]` for that token (and any other tokens in the same `body.tokens` array still pending in the loop) has not yet been decremented. Any code path that inspects this specific mapping value as an authorization or accounting check during that reentrant window would observe stale (pre-decrement) escrow balances. This is a fund-accounting integrity defect matching the "bridged assets ... must move exactly once" pivot: the escrow ledger is not defense-in-depth consistent with the actual token balance at the moment external code runs, unlike the corrected mainline contract.

### Likelihood Explanation
Medium-low. Exploitation requires an attacker to place an order using a token contract they control that implements a callback during `transfer()`/`transferFrom()` (feasible since `order.inputs` tokens are attacker-chosen at `placeOrder`), and requires a further reachable state-dependent action during the callback window that reads the not-yet-decremented `_orders[commitment][token]` value. The `_filled[commitment]` guard being set at the very top of `withdraw()` closes off the most direct double-redemption paths through `fillOrder`/`cancelOrder` for the same commitment, which reduces — but does not eliminate — the practical severity, since the CEI ordering itself remains objectively incorrect and inconsistent with the fixed mainline implementation.

### Recommendation
Apply the same fix used in `IntentsBase.sol::_withdraw()` to the Tron `withdraw()` function: decrement `_orders[body.commitment][token]` (and the transaction-fee entry) **before** performing the external token/native transfer call, so escrow accounting reflects the post-payout state prior to any external code execution.

### Proof of Concept
1. Attacker calls `placeOrder()` on the source chain escrowing a custom ERC-20-like token `M` they control, whose `transfer()` implementation calls back into arbitrary logic before returning `true`.
2. Order is filled (or cancelled) normally, triggering the cross-chain `RedeemEscrow`/`RefundEscrow` message and eventually `onAccept()` → `withdraw()` on the source chain.
3. Inside `withdraw()`'s loop, `token.call(transfer(beneficiary, amount))` for token `M` invokes attacker-controlled code **before** `_orders[commitment][M] -= amount` executes.
4. During this window, `_orders[commitment][M]` (and any other tokens later in `body.tokens`) still reflect pre-payout escrow balances, violating the check-effects-interact invariant that the mainline `IntentsBase.sol` explicitly relies on to prevent reentrant fund misaccounting. [4](#0-3)
