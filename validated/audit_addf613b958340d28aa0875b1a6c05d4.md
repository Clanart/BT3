### Title
Cached FROST preprocess is reused across `share`/`complete` calls that can sign distinct messages, enabling secret share recovery - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
The Cooler bug class is "an update is accepted but a stale value persists and is used under the new terms." The direct analog lives in `SigningProtocol::preprocess_internal`: the FROST preprocess (the ChaCha20 seed deriving both FROST nonces `d` and `e`) is cached in `CachedPreprocesses` keyed only by `context`, written only when absent, and never invalidated. Every subsequent signing action under the same context regenerates the identical nonces, even when the message or signing set being signed has changed. Two signature shares produced with the same nonces but different challenges leak the signer's secret share linearly.

### Finding Description
In `preprocess_internal`, the seed is stored the first time a context is seen and unconditionally reloaded afterwards (`coordinator/src/tributary/signing_protocol.rs:123-145`):

```rust
if CachedPreprocesses::get(self.txn, &self.context).is_none() {
  // generate and store encrypted seed
}
let cached = CachedPreprocesses::get(self.txn, &self.context).unwrap();
let (machine, preprocess) =
  AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached));
```

`AlgorithmMachine::seeded_preprocess` then deterministically regenerates nonces and commitments from that seed (`crypto/frost/src/sign.rs:121-144`), so the same `context` always yields the same `d, e` and the same `D, E` commitments. The FROST docs explicitly warn reuse enables third-party recovery of the private key share (`crypto/frost/src/sign.rs:85-87`, `spec/cryptography/FROST.md:51-53`).

For `DkgConfirmer`, `context = (b"DkgConfirmer", attempt)` (`signing_protocol.rs:275`). Within a single attempt the cached seed is consumed by **three independent signing operations**:

1. `preprocess()` via `dkg_confirmation_nonces` (`handle.rs:36-45`).
2. `share(preprocesses, key_pair)` via `generated_key_pair` (`handle.rs:47-60`), which signs `set_keys_message(set, removed, key_pair)` (`signing_protocol.rs:296-301`).
3. `complete(preprocesses, key_pair, shares)` in `Transaction::DkgConfirmed` handling (`handle.rs:508-546`), which internally calls `share_internal` **again**, re-signing with the same seed (`signing_protocol.rs:321-326`).

The signed message and the participant remapping both depend on `removed` and `key_pair`, which are re-derived at each call site:

- `share` uses the `key_pair` argument supplied by the processor and `removed` captured at `DkgConfirmer::new`.
- `complete` re-reads `removed` via `removed_as_of_dkg_attempt` (`handle.rs:520`) and `key_pair` via `DkgKeyPair::get` (`handle.rs:529`), and `generated_key_pair` blindly overwrites `DkgKeyPair`/`KeyToDkgAttempt` on each invocation (`handle.rs:54-55`).

If the `removed` set or the `key_pair` seen by `complete` differs from what `share` signed — e.g. a participant is removed mid-attempt, or `generated_key_pair` is invoked a second time with a distinct `KeyPair` after a blame/restart path — the identical FROST nonces are used to sign a **different** challenge/message. Each emitted share is `z_i = d + e·ρ_i + λ_i·s·c_i`; with `(d, e)` reused and `c_1 ≠ c_2` (the FROST challenge binds `msg` and the commitment set), `s = (z_1 − z_2) / (λ·(c_1 − c_2))` recovers the MuSig secret key outright.

This is exactly the Cooler shape: the "rolled" session (new `removed`/`key_pair`/preprocess set) is accepted, but the stale cached term (the nonce seed) is kept instead of being refreshed, so the old value is applied under new conditions.

### Impact Explanation
Reuse of FROST nonces across two distinct challenges yields the signer's secret share `s` in closed form — here, the coordinator's MuSig/Ristretto key used for `set_keys` confirmation. Compromise of that key lets an attacker forge the confirmation signature path and breaks the tributary's validator-set key authentication. This is "key share recovery," an accepted impact class.

### Likelihood Explanation
Requires the `share` and `complete` invocations for the same attempt to observe different `removed`/`key_pair` inputs. The code itself acknowledges ordering fragility (the `key_pair` fetch at `handle.rs:527-532` carries a timing TODO, and `DkgKeyPair` is overwritten unconditionally). Whether `removed_as_of_dkg_attempt` can change within one attempt depends on removal timing semantics I could not fully confirm; if it is frozen per-attempt and the DKG output is unique, the divergence window narrows to the `key_pair` overwrite path. Rated Medium rather than High for that reason.

### Recommendation
Bind the cached preprocess to the full signing inputs, not just `(label, attempt)`: extend `context` to include the `removed` set hash and `key_pair` (or store the seed keyed by `set_keys_message` digest), and delete `CachedPreprocesses` once `complete` succeeds. Alternatively, pass the produced share through instead of re-running `share_internal` inside `complete`, so a given seed can only ever sign one message.

### Proof of Concept
1. In attempt `a`, `generated_key_pair` is invoked with `key_pair_A`; `share` signs `m_A = set_keys_message(set, removed_A, key_pair_A)` under seed `S`, emitting share `z_A`.
2. Before `DkgConfirmed` accumulation completes, `DkgKeyPair` is overwritten via a second `generated_key_pair` call with `key_pair_B` (or `removed` changes via a `RemoveParticipantDueToDkg` slash), so `complete` signs `m_B ≠ m_A` under the same seed `S`.
3. Nonces `d, e` are identical; the FROST challenge `c` differs since it binds `msg`. From the two published shares `z_A, z_B`, compute `s = (z_A − z_B)·(λ·(c_A − c_B))⁻¹` and recover the coordinator's MuSig secret key.

Key lines: `signing_protocol.rs:123-145` (sticky cache), `sign.rs:127-145` (deterministic nonce regeneration), `signing_protocol.rs:321-326` + `handle.rs:529-535` (`complete` re-signs with freshly-derived inputs).
