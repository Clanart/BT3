### Title
Scanner credits immature coinbase outputs as spendable received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class in the external report is a low-level call reporting `success` despite the target not satisfying a precondition (contract existence). The Serai analog is `Scanner::scan_block`, which reports outputs as `ReceivedOutput` — i.e., funds received and presumed spendable — without checking a precondition on the transaction carrying them: that it is not an immature coinbase. An unprivileged miner can send a coinbase transaction paying to the Serai multisig's P2TR script, and the scanner will report the output as received even though the Bitcoin consensus rules make it unspendable for 100 blocks.

### Finding Description
`Scanner::scan_transaction` iterates `tx.output` and pushes a `ReceivedOutput` for any output whose `script_pubkey` matches a registered script (`self.scripts.get(&output.script_pubkey)`), with no check on the nature of the transaction itself [1](#0-0) . `Scanner::scan_block` then calls `scan_transaction` over `block.txdata` in full, which includes `txdata[0]`, the coinbase transaction [2](#0-1) .

The doc comment acknowledges the hazard — coinbase outputs are "bound by maturity" and "a post-processing pass is needed" to remove them [3](#0-2)  — yet the function still unconditionally scans and returns them as `ReceivedOutput`, the exact same type produced for normal spendable payments. There is no `is_coinbase` check, no maturity tracking, and no distinction in the returned `ReceivedOutput` (which contains only `offset`, `output`, `outpoint`) that would let a consumer detect it [4](#0-3) . Like the Solidity `.call` returning `success` for a non-existent contract, the scanner reports success (funds received) where the precondition for actually using the result (spendability) is absent.

### Impact Explanation
A `ReceivedOutput` for an immature coinbase output represents funds reported received that are not spendable. If the downstream scheduling/signing pipeline treats it as a normal external output, two consequences follow:

- The deposit can be credited (an `InInstruction`/mint) while the underlying output cannot be moved until maturity, creating a window where reported reserves are illiquid.
- Any transaction built spending that `ReceivedOutput` as an input is consensus-invalid until the coinbase matures, causing the signed plan to be rejected by the network and potentially stalling the batch.

### Likelihood Explanation
Any miner can place arbitrary outputs in their coinbase transaction, including a P2TR output to Serai's registered script, at no cost beyond normal block reward redirection. This requires no privileged position beyond mining a block and is reachable purely through a Bitcoin transaction an unprivileged party sends. Its occurrence depends on a miner choosing to do so and on downstream code consuming `scan_block` results without an additional maturity filter, so it is not guaranteed on every block — consistent with Medium severity.

### Recommendation
In `Scanner::scan_block`, skip `block.txdata[0]` (or check `tx.is_coinbase()` inside `scan_transaction`/`scan_block`) so that coinbase outputs are never returned as `ReceivedOutput`. If scanning coinbases is genuinely desired, `ReceivedOutput` should carry an immaturity marker, or `scan_block` should track and only surface the output once it is mature, rather than relying on an undocumented post-processing obligation on every caller.

### Proof of Concept
Conceptual:

1. Serai registers its group key; `Scanner::new(key)` inserts `p2tr_script_buf(key)` into `scripts` [5](#0-4) .
2. A miner mines a block whose coinbase transaction contains a `TxOut` with `script_pubkey == p2tr_script_buf(key)` and some value `v`.
3. `scan_block(&block)` is called; the loop over `block.txdata` includes the coinbase, and `scan_transaction` matches the script, returning `ReceivedOutput { offset: ZERO, output, outpoint }` [2](#0-1) .
4. The output is reported as received despite consensus rules forbidding spending it for 100 blocks; a spend plan using it produces a transaction that full nodes reject.

Note: this assessment is based on the in-scope scanner code alone; whether any caller performs the maturity post-processing the doc comment requires could not be verified within the permitted scope.

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```
