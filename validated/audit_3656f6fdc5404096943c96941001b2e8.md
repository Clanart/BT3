Duplicate (already-consumed) outpoints can be "reminted" as inputs — `SignableTransaction::new` never deduplicates `ReceivedOutput`s, double-counting their value (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The referenced finding concerns an NFT mint that lets callers pick `tokenID`, so a burned identifier can be minted again because the contract never records consumed IDs. The same class exists in `SignableTransaction::new`: each `ReceivedOutput` carries a unique identifier (its `OutPoint`) that must be consumed at most once, yet the constructor builds `tx_ins` and sums `input_sat` straight from the caller-supplied `inputs` vector with no check that an outpoint was already seen/spent. A `ReceivedOutput` that has already been spent ("burned") — or the same output listed twice — is silently accepted, and its satoshi value is counted again as if freshly minted.

### Finding Description
`SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-256):

- `input_sat` is computed as `inputs.iter().map(|input| input.output.value.to_sat()).sum()` (line 175). Duplicated entries inflate this sum with phantom value.
- `tx_ins` is built with `previous_output: input.outpoint` for every entry (lines 177-185); there is no `HashSet<OutPoint>` or equivalent "consumed ID" check anywhere in the constructor.
- The solvency gate `input_sat < payment_sat + needed_fee` (line 215) and the change computation `input_sat - payment_sat - fee_with_change >= DUST` (lines 228-234) both operate on the inflated sum, so a transaction paying out more than its real inputs will pass all local validation.
- `multisig` (lines 273-285) verifies each input's offset key against `prevouts[i].script_pubkey`; a duplicated `ReceivedOutput` passes this trivially since both copies are identical.
- `TransactionSignMachine::sign` (lines 355-397) then has every FROST participant produce a signature share over `taproot_key_spend_signature_hash(i, Prevouts::All(&self.tx.prevouts), ...)` per input — i.e., the threshold formally signs the double-spending transaction.

`ReceivedOutput` is reachable from untrusted bytes via `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs), which is a documented untrusted-input entry point; any component that deserializes attacker-influenced `ReceivedOutput`s (e.g., data carried alongside `InInstruction`/refund paths) and feeds them into `SignableTransaction::new` exposes this path.

### Impact Explanation
Two consequences:

1. **Consensus-invalid signed transaction**: Bitcoin rejects any transaction spending the same outpoint twice or spending an already-spent outpoint. The threshold signature is correctly formed for `sighash` purposes but the transaction can never confirm. If this occurs inside a payout/burn plan, the plan's payments and change are locked behind a transaction that can never be mined — a funds-liveness failure requiring re-planning and re-signing.
2. **Value inflation**: because `input_sat` double-counts, `needed_fee`, payment feasibility, and the change output amount are all computed against money that doesn't exist. The change `TxOut` (line 230) can be assigned satoshis exceeding the real input total, meaning the "spent" output is effectively reminted inside the transaction's own accounting — exactly the "burned ID reminted" bug shape.

This matches the original finding's structure: an identifier assumed unique (tokenID / outpoint) is not recorded as consumed, so a consumed value is re-created and re-counted.

### Likelihood Explanation
Likelihood is lower than the source finding because `inputs` are normally produced by `Scanner::scan_transaction`, which emits distinct outpoints from on-chain data. However, the constructor is a public API over deserializable, attacker-influenced `ReceivedOutput` bytes, and nothing in the crate enforces the uniqueness invariant — the safety depends entirely on every caller having deduplicated inputs. Any path where output selection is influenced by external data (e.g., refunded/forwarded outputs queued from network messages, or a caller retrying with an output already spent by a prior plan) triggers the bug. Reachability is plausible; consistency of impact is guaranteed once reached. Severity: Medium, in line with the source finding.

### Recommendation
Track consumed outpoints in `SignableTransaction::new` and reject duplicates — the direct analog of the report's "record the burned tokenID and check it when minting" recommendation:

```rust
// networks/bitcoin/src/wallet/send.rs, in SignableTransaction::new
let mut seen = std::collections::HashSet::new();
for input in &inputs {
  if !seen.insert(input.outpoint) {
    Err(TransactionError::DuplicateInput)?;
  }
}
```

Additionally, callers that aggregate `ReceivedOutput`s from deserialized or network-sourced data should verify the outpoint is still unspent on the canonical chain before constructing a `SignableTransaction`.

### Proof of Concept

```rust
// Same ReceivedOutput supplied twice to SignableTransaction::new
let output: ReceivedOutput = /* any scanned or deserialized output */;

// Succeeds: input_sat counts output.value() twice, passing NotEnoughFunds

// The resulting tx has two TxIns with identical previous_output
assert_eq!(tx.transaction().input[0].previous_output,
           tx.transaction().input[1].previous_output);

// multisig() and sign() proceed normally; the threshold signs a transaction
// Bitcoin consensus will reject as a double-spend.
let machines: Vec<_> = keys.values().map(|k| tx.clone().multisig(&k.clone()).unwrap()).collect();
```
