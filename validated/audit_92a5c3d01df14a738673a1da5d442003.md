### Title
Block-revenue-sharing rewards can become permanently stuck in a vote account whose delegated stake is zero, mirroring the "guarded index update" bug class — ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`calculate_block_reward` computes the share of a vote account's `pending_delegator_rewards` to mint to each staker, but the whole distribution is gated by `total_active_stake == 0`. When that guard is true, the function unconditionally returns `0` and no lamports are minted to stakers for that epoch. `pending_delegator_rewards`, however, is a value that can only ever be increased (`add_pending_delegator_rewards`) — no decrement path exists outside the proportional-distribution flow that is itself gated by `total_active_stake > 0`. The vote program's `withdraw` instruction also explicitly refuses to let the authorized withdrawer take out lamports below `pending_delegator_rewards` while it is non-zero. This is structurally identical to the reported Beedle bug: an accounting value (`pending_delegator_rewards`) accumulates deposits, but the code path that would ever "spend" it (the reward distribution) is skipped whenever a guard condition (`total_active_stake == 0`, analogous to `totalSupply == 0`) holds, and nothing else drains or refunds it.

### Finding Description
`calculate_block_reward` in [1](#0-0)  looks up `total_active_stake` for the vote account from `reward_epoch_delegated_stakes`, and if it is `0`, returns `0` — i.e., no block reward is computed/distributed to any staker for that vote account this epoch, even though `pending_delegator_rewards` may be non-zero: [2](#0-1) 

`pending_delegator_rewards` itself is only ever *increased* — via `add_pending_delegator_rewards`, invoked from the `DepositDelegatorRewards` instruction handler: [3](#0-2) [4](#0-3) 

No corresponding subtraction of `pending_delegator_rewards` was found anywhere outside the stake-reward distribution path that is gated by `total_active_stake > 0`. Meanwhile, `withdraw()` explicitly locks any amount below `pending_delegator_rewards` from being withdrawn by the authorized withdrawer, and blocks closing the account entirely while `pending_delegator_rewards > 0`: [5](#0-4) 

The net effect: if a vote account's identity has zero delegated/active stake for a rewarded epoch (`total_active_stake == 0`), the `pending_delegator_rewards` amount is *not* reduced that epoch, and there is no other mechanism that ever removes it — the guard that protects the "divide by total stake" computation from a division-by-zero-style condition also silently disables the only spend path for the accumulated balance, exactly like the Beedle `Staking.claim()`/`update()` interaction where caching `balance` while `totalSupply == 0` permanently desynchronizes the reward index from the WETH balance.

### Impact Explanation
Lamports deposited into a vote account's `pending_delegator_rewards` (via `DepositDelegatorRewards`, SIMD-0123) can become permanently locked if that vote account never has delegated stake at reward-calculation time: they cannot be distributed to stakers (guard returns `0`), and they cannot be withdrawn by the authorized withdrawer (blocked by the `withdraw` check). This is a fund-loss condition — value is deposited but becomes unspendable/undistributable, matching the "stuck rewards" impact class from the original report.

### Likelihood Explanation
This requires a vote account with `pending_delegator_rewards > 0` and `total_active_stake == 0` in the epoch's delegated-stake snapshot (e.g., a validator identity that currently has no delegators, or between validator setup and first stake delegation, or after all delegators have fully deactivated). Given rewards continue to flow to `pending_delegator_rewards` via `DepositDelegatorRewards` independent of whether any stake is currently delegated, and vote accounts can legitimately have zero active stake for extended periods (new validators, fully un-staked validators), this is a realistic, non-malicious-actor scenario rather than a contrived edge case.

### Recommendation
Ensure `pending_delegator_rewards` cannot get durably orphaned from its only spend path: either (a) allow `withdraw()` to release `pending_delegator_rewards` when `total_active_stake` for that vote account is durably zero (no delegators to ever claim it), or (b) redirect/refund the deposited amount when there is no active stake to distribute to, or (c) explicitly document/enforce (with a hard invariant check) that `DepositDelegatorRewards` cannot be used, or has no effect, when the target vote account has zero currently-delegated active stake, preventing the accumulation of an undistributable balance.

### Proof of Concept
1. Create a new vote account with no delegated stake (`total_active_stake == 0` for the relevant `rewarded_epoch` in `RewardEpochDelegatedStakes`).
2. Call `DepositDelegatorRewards` (per SIMD-0123) to increase `pending_delegator_rewards` on that vote account — this succeeds unconditionally as shown in `deposit_delegator_rewards` ( [4](#0-3) ).
3. At epoch boundary, `calculate_block_reward` is invoked for any stake delegated to this vote account; since `total_active_stake == 0`, it returns `0` for every delegation, so nothing is minted from `pending_delegator_rewards` ( [1](#0-0) ), and `pending_delegator_rewards` is left unchanged.
4. Attempt `Withdraw` on the vote account for an amount that would bring the balance below `rent_exempt + pending_delegator_rewards`: it fails with `InstructionError::InsufficientFunds` ( [6](#0-5) ).
5. As long as the vote account never receives delegated stake, the deposited lamports remain locked indefinitely — neither distributable nor withdrawable.

Note: I was unable to find, within the indexed portion of the codebase, any code path that decrements or refunds `pending_delegator_rewards` outside the stake-distribution flow gated on `total_active_stake > 0`. Given index size limits, it is possible such a path exists elsewhere in the repo that was not surfaced by search; a full-repository review (e.g., via a Devin session with complete file access) would be needed to conclusively rule out an alternate drain/refund mechanism before treating this as a confirmed, unmitigated bug.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
