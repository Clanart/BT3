## Analysis

The Move bug is a **map-keying collision**: `vec_map::insert` aborts (or, in a JS `Map`, silently overwrites) when a second entry with the same key is inserted, letting attacker-controlled data with a duplicate key corrupt or block a state transition that should have merged/rejected properly. The strongest structural analog in this codebase is `buildStatusMap` in `app/src/lib/git/status.ts`, which folds `git status --porcelain=2 -z` entries into a `Map<string, WorkingDirectoryFileChange>` keyed purely by `entry.path`, with `files.set(entry.path, ...)` silently overwriting any prior entry for that path [1](#0-0) . This map ultimately becomes `workingDirectory.files`, the exact list of files/selections a user reviews and commits from [2](#0-1) .

### Title
Duplicate-path collapsing in `buildStatusMap` can silently drop a file's change from the commit review list - (File: `app/src/lib/git/status.ts`)

### Summary
`getStatus()` parses `git status --porcelain=2 -z` output into discrete entries and reduces them into a `Map` keyed only by `entry.path` via `buildStatusMap`. If `git status` (fed by an attacker-controlled/fetched repository, index, or worktree state) ever reports two distinct status records that resolve to the same string path, the second `files.set(entry.path, ...)` call unconditionally overwrites the first, exactly mirroring the Move bug's "second insert wins/loses" invariant break — except here it fails silently instead of aborting.

### Finding Description
`parsePorcelainStatus` produces a flat list of `IStatusEntry` records purely from regex-parsed NUL-delimited fields, trusting the `path`/`oldPath` values verbatim from the git process output [3](#0-2) . `getStatus` then reduces these entries with `buildStatusMap`, keyed only by `entry.path`, with no uniqueness check: `files.set(entry.path, new WorkingDirectoryFileChange(entry.path, appStatus, selection))` [4](#0-3) . There is already an intentional overwrite/delete path baked in for the "untracked + staged delete on same path" case [5](#0-4) , showing the authors know collisions can occur — but the general case has no defense: any two records sharing the same `path` (e.g., via rename/copy entries whose `to`-path collides with another entry's path, or Unicode-normalization/case differences that git or the filesystem can collapse) result in one `WorkingDirectoryFileChange` being discarded without any log or warning.

Because `workingDirectory.files` (built from `[...files.values()]`, see `WorkingDirectoryStatus.fromFiles`) is the sole source of truth for what the Changes panel displays and what gets diffed/selected/committed, an entry lost at this stage means the corresponding real git change is invisible to the user's review UI even though it still exists in the actual git index/working tree, or, conversely, the user may believe a certain diff is being committed when the map only retains the *other* colliding entry's status/selection object.

### Impact Explanation
This matches the requested impact class of "silent corruption of what the user commits or pushes": one of the two colliding paths never appears in the Changes list, so the user cannot review, deselect, or partially stage/commit it correctly — they will commit blind to real changes staged in the index (or a rename/copy operation could mask a still-outstanding modification), the same fail-mode as the Move report where `vec_map::insert` prevented the state from reflecting all valid registrations.

### Likelihood Explanation
Uncertain/unverified: I could not confirm within this codebase a concrete git status output shape that guarantees two `IStatusEntry` records for genuinely different underlying changes resolve to an *identical* `path` string (e.g., via rename-score races, git's own path-quoting edge cases, or filesystem Unicode normalization on checkout of an attacker-crafted clone). This would require deeper testing against `dugite`/git internals and file-system behavior (HFS+/APFS NFD-normalization vs git's stored NFC bytes) that is outside what static code search can establish. The existing special-case handling in `buildStatusMap` (lines 320-326) is circumstantial evidence the maintainers are aware collisions are possible in at least one scenario, but I cannot assert this is currently exploitable without live git repro.

### Recommendation
Given the confirmed uncertainty, do not treat this as a fully proven finding — it is presented as the closest structural analog found in the local index. If pursued, the fix would mirror the Move remediation ("restrict duplicate keys"): detect when `buildStatusMap` is about to overwrite an existing map entry for a path from a *different* underlying `IStatusEntry.kind`/status combination (not the known untracked-vs-staged-delete case) and either keep both entries under a composite key, log a diagnostic, or fail closed rather than silently dropping one.

### Proof of Concept
Not established. I was unable to construct, from local code inspection alone, a concrete `git status --porcelain=2 -z` output (or attacker-controlled repository state) that provably yields two entries with an identical `path` outside the already-handled untracked/staged-delete case. Confirming exploitability would require live experimentation with git's rename detection, submodule status codes, and filesystem normalization — best done in a Devin session with terminal/git access rather than static search.

```typescript
function buildStatusMap(
  files: Map<string, WorkingDirectoryFileChange>,
  entry: IStatusEntry,
  conflictDetails: ConflictFilesDetails
): Map<string, WorkingDirectoryFileChange> {
  const status = mapStatus(
    entry.statusCode,
    entry.submoduleStatusCode,
    entry.renameOrCopyScore
  )

  if (status.kind === 'ordinary') {
    // when a file is added in the index but then removed in the working
    // directory, the file won't be part of the commit, so we can skip
    // displaying this entry in the changes list
    if (
      status.index === GitStatusEntry.Added &&
      status.workingTree === GitStatusEntry.Deleted
    ) {
      return files
    }
  }

  if (status.kind === 'untracked') {
    // when a delete has been staged, but an untracked file exists with the
    // same path, we should ensure that we only draw one entry in the
    // changes list - see if an entry already exists for this path and
    // remove it if found
    files.delete(entry.path)
  }

  // for now we just poke at the existing summary
  const appStatus = convertToAppStatus(
    entry.path,
    status,
    conflictDetails,
    entry.oldPath
  )

  const initialSelectionType =
    appStatus.kind === AppFileStatusKind.Modified &&
    appStatus.submoduleStatus !== undefined &&
    !appStatus.submoduleStatus.commitChanged
      ? DiffSelectionType.None
      : DiffSelectionType.All

  const selection = DiffSelection.fromInitialSelection(initialSelectionType)

  files.set(
    entry.path,
    new WorkingDirectoryFileChange(entry.path, appStatus, selection)
  )
  return files
```

```typescript
function parsedRenamedOrCopiedEntry(
  field: string,
  oldPath: string | undefined
): IStatusEntry {
  const match = renamedOrCopiedEntryRe.exec(field)

  if (!match) {
    log.debug(`parsedRenamedOrCopiedEntry parse error: ${field}`)
    throw new Error(`Failed to parse status line for renamed or copied entry`)
  }

  if (!oldPath) {
    throw new Error(
      'Failed to parse renamed or copied entry, could not parse old path'
    )
  }

  return {
    kind: 'entry',
    statusCode: match[1],
    submoduleStatusCode: match[2],
    oldPath,
    renameOrCopyScore: parseInt(match[8].substring(1), 10),
    path: match[9],
  }
}
```
