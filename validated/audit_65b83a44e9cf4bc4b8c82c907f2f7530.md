### Title
Reward dilution via direct stakingToken donation to MasterMagpie inflating `totalStaked()` - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool.totalStaked()` computes the reward denominator from `IERC20(stakingToken).balanceOf(operator)` instead of from an internal ledger of amounts actually staked in this pool. An unprivileged attacker can transfer `stakingToken` directly to the `operator` (MasterMagpie) address, inflating this balance without registering any stake via `stakeFor`, which understates `rewardPerTokenStored` growth on the next `queueNewRewards`/`donateRewards` call and permanently dilutes legitimate stakers' yield.

### Finding Description
`totalStaked()` reads the raw ERC20 balance of the operator contract rather than tracking staked shares internally: [1](#0-0) 

In contrast, `balanceOf(_account)` (the numerator used in `earned()`) is derived from MasterMagpie's own staking ledger via `stakingInfo`, which is only updated through legitimate `stakeFor`/`withdrawFor` flows: [2](#0-1) 

`_provisionReward` (called by both `queueNewRewards` and the permissionless `donateRewards`) divides the incoming reward by `this.totalStaked()`: [3](#0-2) 

Since `stakingToken` is a standard ERC20 (per the constructor, any non-zero address is accepted), an attacker can simply call `stakingToken.transfer(operator, X)` — a plain, permissionless external ERC20 transfer that does not go through `MasterMagpie.stake`/`stakeFor` and therefore is never reflected in `stakingInfo`. This inflates `balanceOf(operator)` (the denominator) while leaving the numerator (`stakingInfo`-derived balances used in `earned()`) unchanged for all real stakers. When a manager (or anyone, via `donateRewards`) subsequently provisions rewards, `rewardPerTokenStored` increases by `(_amountReward * 10**decimals) / totalStaked()`, which is now smaller than the value that would correctly compensate the actual staked principal. The reward tokens are already pulled into the contract (`safeTransferFrom`) but the corresponding `rewardPerTokenStored` increment permanently understates true stakers' entitlement — the shortfall is not recoverable by any existing mechanism (no sweep/rebalance function corrects `totalStaked()` against `stakingInfo`), so it is permanently lost to legitimate stakers' unclaimed yield.

No existing modifier or check prevents this: `_provisionReward` has no reentrancy or balance-consistency assertion tying `totalStaked()` to the sum of `stakingInfo` balances, and any address can perform the donation since ERC20 `transfer` requires no permission from MasterMagpie or the pool.

### Impact Explanation
This causes permanent dilution/loss of unclaimed yield for all legitimate stakers in the affected pool: excess `stakingToken` sitting in `operator`'s balance is counted in the reward-per-token denominator forever (or until manually corrected, which there is no mechanism for), so every future `queueNewRewards`/`donateRewards` call distributes proportionally less reward per staked unit than it should. This matches the Immunefi impact class of "theft or permanent freezing of unclaimed yield."

### Likelihood Explanation
Low capital and no special privileges are required — any attacker holding (or able to acquire) even a small/moderate amount of `stakingToken` can send it directly to the `operator` address at any time before a reward provisioning transaction. It is fully repeatable and can be front-run ahead of expected `queueNewRewards` calls to maximize dilution effect relative to the current true staked total. The main precondition (stated in the question) is that MasterMagpie has no sweep/recovery protection isolating this pool's `stakingToken` balance from arbitrary inbound transfers, which is consistent with the code inspected — no such protection is present in `BaseRewardPool.sol`.

### Recommendation
Replace `totalStaked()`'s reliance on raw ERC20 `balanceOf(operator)` with an internal ledger updated exclusively by `stakeFor`/`withdrawFor` calls (mirroring how `balanceOf(_account)` already tracks per-account amounts via `stakingInfo`). This ensures the reward-per-token denominator only reflects tokens actually staked through the tracked accounting path, immune to arbitrary direct-transfer donations.

### Proof of Concept
Foundry test outline:
1. Deploy `MasterMagpie`, `BaseRewardPool` for a mock ERC20 `stakingToken`, and a mock reward token.
2. Have staker A `stake` a known amount `S` through the legitimate `MasterMagpie.stake` path (registers in `stakingInfo`).
3. Baseline: manager calls `queueNewRewards(R, rewardToken)`; record `rewardPerTokenStored` and `earned(A, rewardToken)`.
4. Reset state (or run as a second scenario with identical initial stake `S`), then have an unprivileged attacker call `stakingToken.transfer(operator, D)` directly (no `stake` call), inflating `IERC20(stakingToken).balanceOf(operator)` by `D` without changing `stakingInfo`.
5. Manager calls `queueNewRewards(R, rewardToken)` again with the same `R`.
6. Assert `rewardPerTokenStored` growth in step 5 is strictly less than in step 3 (scaled by `S/(S+D)` vs `S/S`), and `earned(A, rewardToken)` after step 5 is less than the baseline `earned(A, rewardToken)` from step 3, despite A's actual staked principal being unchanged.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
