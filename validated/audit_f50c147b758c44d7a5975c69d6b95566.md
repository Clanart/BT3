### Title
BTC received below the processor's DUST threshold is permanently locked with no recovery path - (File: processor/src/multisigs/scanner.rs)

### Summary
Analogous to "no way to withdraw ETH received by a payable function," any unprivileged user can send a Bitcoin output under `Bitcoin::DUST` (10,000 sats) to a Serai deposit/change/branch address. `Scanner::scan_transaction` detects the output regardless of value, but the processor silently drops it at scan time. No mechanism exists anywhere in the pipeline to ever credit, consolidate, or spend that output again — the value is stranded at a threshold-controlled address forever, exactly mirroring value permanently stuck in `XChainController`.

### Finding Description
`Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs:199-214` returns every output whose `script_pubkey` matches a registered key, with no minimum-value check — so small deposits are fully detected and spendable in principle (the multisig key controls them). However, the processor-level scan in `processor/src/multisigs/scanner.rs:564` applies `if output.balance().amount.0 >= N::DUST` and discards everything below. `N::DUST` for Bitcoin is 10,000 sats (`processor/src/networks/bitcoin.rs:638`).

Once dropped, the output is never recorded, never scheduled, and never reconsidered — the scheduler only operates on `Output`s produced by the scanner (`processor/src/multisigs/scheduler/utxo.rs`), and the signing path (`SignableTransaction::multisig`, `networks/bitcoin/src/wallet/send.rs:273-285`) can only spend `ReceivedOutput`s handed to it. There is no "sweep" or manual-recovery API analogous to a hypothetical `withdrawBalance()`. The script_pubkey is also permanently bound in `Scanner.scripts`, so re-scanning does not help.

### Impact Explanation
Funds sent by any user to a valid Serai address below 10,000 sats (well above Bitcoin's own 546-sat dust limit and trivially sendable by mistake, e.g. a small test deposit or a payment shrunk by fee amortization) become permanently unspendable through the protocol, despite being controlled by the multisig key. This is the Serai analogue of ETH stuck in a contract with no withdrawal method: value is received but there is no path to move it.

### Likelihood Explanation
Reachable by any unprivileged external party sending a Bitcoin transaction — the allowed public input class. No attacker sophistication required; an ordinary under-sized deposit suffices. The trigger probability is high since the threshold (10,000 sats) is ~18x Bitcoin's actual dust rule.

### Recommendation
Either keep dropped outputs in a recoverable set so a later consolidation transaction can sweep them once their aggregate exceeds the fee cost, or emit an explicit refund/recovery event for sub-dust outputs rather than silently discarding them at `processor/src/multisigs/scanner.rs:564`.

### Proof of Concept
1. User sends 5,000 sats to the Serai P2TR deposit script (`p2tr_script_buf(key)`, registered in `Scanner::new`, `mod.rs:162-166`).
2. `Scanner::scan_transaction` returns the `ReceivedOutput` (mod.rs:199-214).
3. Processor filter at `scanner.rs:564` drops it (`5000 < 10_000`).
4. No code path ever re-creates an `Output`/`ReceivedOutput` for that outpoint; `SignableTransaction::multisig`/`TransactionSignMachine` can only sign inputs it is given. The 5,000 sats are locked at the multisig address indefinitely.

Caveat: this is a deliberate economic policy documented on `Network::DUST` ("minimum output value which will be handled"), so it sits on the boundary between design decision and vulnerability — but like the source finding, the received value has no withdrawal path, and no recovery mechanism is documented or implemented.
