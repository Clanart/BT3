### Title
`BlameMachine::blame` / `AdditionalBlameMachine::blame` lets any party get an innocent recipient declared faulty by omitting the decryption proof - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
The bug class of the reference report — a function affecting a party's assets/standing that can be executed by anyone without verifying the caller is the affected party — maps directly onto PedPoP's blame arbitration. `blame_internal` trusts the caller-supplied `(sender, recipient)` pair and the optional `EncryptionKeyProof`. When `proof` is `None`, `decrypt_with_proof` returns `DecryptionError::InvalidProof` and `blame_internal` declares the **recipient** faulty — yet the function never requires the accuser to actually be that recipient. Any observer of a valid `EncryptedMessage` from `sender` to `recipient` can invoke `blame(sender, victim, msg, None)` and have the honest `victim` blamed.

### Finding Description
In `BlameMachine::blame` / `AdditionalBlameMachine::blame`, the arbitration logic is:

```rust
// crypto/dkg/pedpop/src/lib.rs
let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
  Ok(share_bytes) => share_bytes,
  Err(DecryptionError::InvalidSignature) => return sender,
  Err(DecryptionError::InvalidProof) => return recipient,   // <-- recipient blamed
};
```

`decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs:366-397`) first verifies the per-message proof-of-possession, which is bound to the claimed `sender` via `pop_challenge(context, R, key, from, msg)`. If the message is a *genuine* share message from `sender` to `recipient`, the PoP verifies. Then, because `proof` is `None`, it returns `Err(InvalidProof)`, and the recipient is blamed — even though the only entity capable of producing a valid `EncryptionKeyProof` (which proves the ECDH key) is the real `recipient`, who holds `enc_key` (`Encryption::decrypt` produces it via `DLEqProof::prove(..., &self.enc_key)` at `crypto/dkg/pedpop/src/encryption.rs:487-500`).

There is no binding between the caller/accuser and `recipient`. The docstring only says the message "must have been authenticated as actually having come from the sender" — nothing authenticates that the accusation originates from the recipient who could have supplied the proof. `AdditionalBlameMachine::new` even explicitly supports callers "regardless of if the caller was a member in the DKG protocol" (`crypto/dkg/pedpop/src/lib.rs:639-648`).

Downstream (`processor/src/key_gen.rs:543-563`), the blamed participant is emitted as `ProcessorMessage::Blame`, which causes a fatal abort/slash of that participant.

### Impact Explanation
An unprivileged party can cause an honest DKG participant to be publicly declared faulty, forcing a DKG abort and (in the Serai deployment) a slash/fatal penalty against an innocent validator — a direct analog of "spending/draining on behalf of another user without authorization," here draining reputation/stake rather than tokens. Additionally, per `complete()` semantics, any blame prevents protocol completion, so a single forged-by-omission accusation griefs the entire DKG.

### Likelihood Explanation
The encrypted share messages are transmitted through the coordinator/tributary layer and are observable to participants and to anyone evaluating blame (`AdditionalBlameMachine::new` is designed for non-participants). An attacker needs only a copy of a legitimately-formed `EncryptedMessage` between two parties — no secrets, no valid shares, no threshold control. Submitting `(sender, victim, msg, None)` deterministically yields `victim` as the faulty party whenever the message's PoP is well-formed (which honest messages are).

### Recommendation
Bind the accusation to the accuser's identity: require the accuser to prove they are `recipient`, e.g., require a non-`None` `EncryptionKeyProof` *produced by the recipient's encryption key* (already verified against `self.enc_keys[&decryptor]` in `decrypt_with_proof`) — i.e., treat `proof: None` as "sender's PoP was invalid" blame against `sender`, never against `recipient`. The `None` case should only be reachable when the PoP itself failed verification, which already returns `sender` before the proof check. Structurally: reorder so that a missing proof on a PoP-valid message cannot fault the recipient, or require the accuser to authenticate (e.g., sign the accusation with their registered encryption key).

### Proof of Concept
```rust
// After a normal PedPoP run where participant ONE sends an encrypted
// SecretShare to participant TWO (the honest victim):
// msg = secret_shares[&ONE][&TWO]  // a *valid* EncryptedMessage

// Any third party (or AdditionalBlameMachine built only from public
// commitment messages) executes:
let machine = AdditionalBlameMachine::new(CONTEXT, PARTICIPANTS, commitment_msgs).unwrap();
let blamed = machine.blame(
  ONE,        // genuine sender
  TWO,        // honest recipient we want framed
  msg.clone(),
  None,       // omit the decryption proof only TWO could produce
);
assert_eq!(blamed, TWO); // honest TWO is declared faulty
```

Root cause: `decrypt_with_proof` (crypto/dkg/pedpop/src/encryption.rs:381-396) returns `InvalidProof` when `proof.is_none()`, and `blame_internal` (crypto/dkg/pedpop/src/lib.rs:586-587) maps that to `recipient` without any check that the accuser is the recipient or that a proof was ever solicited from them.
