### Title
Deterministic CachedPreprocess reuse leaks the FROST secret share when a signing round is repeated under the same context - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` derives a FROST preprocess deterministically from a `CachedPreprocess` seed stored in the DB keyed only by `self.context`, and reuses that same seed on every call. Any repeat of the signing round for the same context — different participant set, different `msg`, or a retried attempt — causes the same nonces/commitments to be published and consumed again, enabling recovery of the validator's secret share from its two signature shares. This is the Serai analog of the reported bug class: private data (here, the threshold key share, equivalent to the admin's private digest) is leaked through publicly observable output (the broadcast preprocess and signature share) once an attacker-influenced round is replayed under unchanged context.

### Finding Description
In `preprocess_internal`, the flow is:

1. Build an encryption key from `context || key` (lines 107-114).
2. If `CachedPreprocesses::get(txn, context)` is empty, generate a fresh preprocess and store `machine.cache()` XORed with that key (lines 123-134).
3. Load the cached seed and call `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))` (lines 137-145).

`from_cache` calls `seeded_preprocess`, which seeds `ChaCha20Rng` with the stored 32-byte seed (`crypto/frost/src/sign.rs:121-144`). The seed fully determines the nonces and the broadcast `Preprocess`. Therefore, **every** invocation of `share_internal` for the same `self.context` produces the identical preprocess and identical internal nonces.

`share_internal` (lines 150-181) then calls `machine.sign(preprocesses, msg)` with whatever `serialized_preprocesses` and `msg` are supplied for this round. In `sign` (`crypto/frost/src/sign.rs:283-398`), the binding factor `rho` is computed over `group_key`, `hash_msg(msg)`, and the transcript of all participants' preprocesses, and the signature share is `d + e*rho` combined with the (lagrange-scaled) secret share via `sign_share`.

If the round is ever run twice under the same context — e.g., a first attempt aborts after shares are exchanged and the protocol retries with a different signer set or a different `msg` — the signer emits two shares `s1 = d + e*rho1 + c1*share` and `s2 = d + e*rho2 + c2*share` built on the same nonce `d + e*rho_i`. Since `rho` and the challenge `c` are publicly derivable, the observer solves a 2x2 linear system and recovers `d + e*rho` and then the secret share. This is the exact nonce-reuse key-recovery the `CachedPreprocess` documentation warns about (`crypto/frost/src/sign.rs:216-224`), but the persistence layer itself guarantees the reuse: the cache entry is never invalidated, rotated, or bound to the specific signing attempt's participant set/message.

Nothing in `preprocess_internal` mixes the participant set, attempt counter, or message into the seed lookup; the DB key is `self.context` alone (lines 123, 137). The in-memory `AlgorithmSignMachine` is consumed by `sign`, but a fresh call to `share_internal` reconstructs a machine from the same stored seed, defeating the single-use protection entirely.

### Impact Explanation
The secret share of a tributary validator's threshold key is leaked to anyone who observes the two rounds' public messages (preprocesses and signature shares are broadcast). For the substrate-side Ristretto key this compromises the validator's MuSig/FROST share; repeated across validators it enables full group-key recovery. This is a direct private-data leak triggered by an untrusted party causing a repeat of the signing session (e.g., submitting a conflicting preprocess set or forcing a retry), matching the severity of the reference report's private-information disclosure.

### Likelihood Explanation
The leak requires the signing flow to invoke `share_internal`/`preprocess_internal` more than once under one `context`. Signing protocols commonly retry rounds when a participant set changes or a round fails; the whole purpose of the cached-preprocess DB entry (surviving reboots mid-session) means reuse across such repetitions is expected, not exceptional. An unprivileged participant in the Tributary set can influence whether a round is repeated (e.g., by withholding or varying their preprocess), and the leaked shares are computable purely from broadcast data.

### Recommendation
Bind the cache key to the full signing session, not just `context`: include the sorted participant set and `hash_msg(msg)` (or a per-attempt nonce) in the `CachedPreprocesses` lookup, and delete/rotate the entry after first use. Alternatively, reject any call to `share_internal` whose `(context, participants, msg)` differs from the session that created the cached preprocess.

### Proof of Concept
1. Validator V calls `share_internal(participants_A, preprocesses_1, msg_1)` for context C; it stores seed S under C and emits share `s1` over nonce `d + e*rho1`, challenge `c1`.
2. The round fails (e.g., an invalid share from a peer). V retries: `share_internal(participants_B, preprocesses_2, msg_2)` under the same context C. `CachedPreprocesses::get` returns S, `from_cache` regenerates identical nonces `(d, e)`.
3. Observer computes `rho1`, `rho2` from the public rho transcript (`group_key`, `hash_msg(msg_i)`, preprocess commitments) and `c1`, `c2` via `Hram`. From `s1 - s2 = e*(rho1 - rho2) + share*(c1 - c2)`... in the standard Schnorr case both equations also share `d`, giving `s1 - s2 = e*(rho1 - rho2) + c*share*(lagrange deltas)`; with differing participant sets the Lagrange coefficients differ, so the two equations in the unknowns `(d, e, share)` reduce to a solvable linear system over the scalar field. Even in the simplest case where only `msg` changes, `c1 != c2` while the nonce `d + e*rho` is reused, yielding `share = (s1 - s2 - e*(rho1 - rho2)) / (c1 - c2)` after solving for `e` — standard FROST nonce-reuse key recovery as documented in `crypto/frost/src/sign.rs:211-213`.
