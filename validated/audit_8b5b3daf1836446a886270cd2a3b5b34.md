### Title
Wrong Price Feed Attached to stSTXbtc/zstSTXbtc Asset in `get-asset-price` — ([File: mainnet/contracts/utility/v0-1-data.clar])

### Summary
`get-asset-price` in `v0-1-data.clar` prices the `stSTXbtc` and `zstSTXbtc` assets using the **STX/USD** Pyth feed instead of the **BTC/USD** feed, despite the code comment explicitly stating "BTC price." This is the same bug class as the referenced Kona MPT fix: a value is extracted/attached using the wrong identifier — here a price is bound to the wrong asset feed — producing a silently wrong result rather than a panic.

### Finding Description
In `get-asset-price`, every other asset branch correctly matches its underlying oracle feed to its economic value (STX→`PYTH-STX`, sBTC→`PYTH-BTC`, USDC→`PYTH-USDC`, etc.). The `stSTXbtc` and `zstSTXbtc` branches break this pattern: [1](#0-0) 

```clarity
;; stSTXbtc - BTC price (liquid staked STX with BTC yield)
(if (is-eq aid stSTXbtc) (default-to u0 (get-pyth-price PYTH-STX))
;; zstSTXbtc - stSTXbtc price x liquidity index
(if (is-eq aid zstSTXbtc)
    (let ((btc-price (default-to u0 (get-pyth-price PYTH-STX)))
          (lindex (get-vault-liquidity-index stSTXbtc)))
      (mul-div-down btc-price lindex INDEX-PRECISION))
```

The comment says "BTC price," and the local variable is even named `btc-price`, but the actual oracle call is `get-pyth-price PYTH-STX` (the STX/USD feed), not `PYTH-BTC`. STX trades several orders of magnitude below BTC, so the USD value computed for any stSTXbtc/zstSTXbtc position is wrong by that same multi-order-of-magnitude factor.

This value flows directly into the position-health helpers: [2](#0-1) [3](#0-2) 

`sum-collateral-usd` and `sum-debt-usd` both call `get-asset-price` and multiply by amount/decimals to build the USD totals used to derive `current-ltv`, `health-factor`, and `is-liquidatable` (see the enclosing struct at lines 481-486).

### Impact Explanation
Because STX/USD ($≈1) is used in place of BTC/USD ($≈60,000+), any position involving `stSTXbtc`/`zstSTXbtc` as collateral will be reported as drastically **under-collateralized** (its true BTC-denominated value is collapsed to STX-scale), while any position using it as debt will be reported as having negligible outstanding debt. This is a "wrong health verdict" exactly in scope: it can cause healthy `stSTXbtc` collateral positions to appear liquidatable (temporary freezing/incorrect liquidation of funds) or, conversely, mask real insolvency for positions borrowing `stSTXbtc`/`zstSTXbtc` (protocol insolvency risk) if any downstream consumer (liquidation bots, frontends, or off-chain risk tooling) relies on this reported health data to decide whether/whom to liquidate.

### Likelihood Explanation
The bug is deterministic and always triggers whenever `get-asset-price` is invoked for `aid = stSTXbtc` or `aid = zstSTXbtc` — no attacker action or oracle manipulation is required. The severity in practice hinges on whether this `v0-1-data.clar` pricing path is consumed by any state-changing/liquidation-gating logic versus being a purely off-chain/read-only reporting utility; I was not able to fully confirm within the available context whether `mainnet/contracts/market/v0-4-market.clar`'s own liquidation path (which resolves prices via the per-asset oracle registry rather than these hardcoded constants) is affected the same way, so this should be verified before treating it as fund-at-risk.

### Recommendation
Change both occurrences of `(get-pyth-price PYTH-STX)` in the `stSTXbtc` and `zstSTXbtc` branches of `get-asset-price` to `(get-pyth-price PYTH-BTC)`, matching the existing comments/variable naming, and add a regression test asserting `get-asset-price(stSTXbtc)` tracks the BTC feed rather than the STX feed.

### Proof of Concept
1. Set Pyth STX/USD = $1.00 and BTC/USD = $60,000.
2. Call the read-only position/health query that invokes `sum-collateral-usd`/`sum-debt-usd` for a user holding `stSTXbtc` collateral.
3. Observe the computed USD collateral value uses the $1.00 STX price rather than the $60,000 BTC price — off by ~60,000x — directly skewing the reported `current-ltv`/`health-factor`/`is-liquidatable` fields. [1](#0-0)
