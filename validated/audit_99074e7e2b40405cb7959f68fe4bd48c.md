### Title
Premature double division in `calc-liquidity-rate` truncates supplier yield accrual - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, replicated in all vault contracts)

### Summary
The vault contracts compute the liquidity rate (the rate at which the liquidity index, and therefore the value of z-tokens paid to depositors, grows) by chaining two independent truncating divisions instead of performing a single combined division. This is the same "premature division" bug class as the reported `GaugeController::_calculateReward` issue: intermediate rounding is applied before the final result is produced, magnifying rounding-down loss and permanently underpaying depositor yield.

### Finding Description
`calc-liquidity-rate` computes the supplier APR from the variable borrow rate, utilization, and reserve factor: [1](#0-0) 

```
(define-private (mul-bps-down (x uint) (y uint)) 
  (/ (* x y) BPS))
...
(define-private (calc-liquidity-rate (var-borrow-rate uint) (util-pct uint) (reserve-factor-bps uint))
  (let ((util-applied (mul-bps-down var-borrow-rate util-pct))
        (one-minus-rf (- BPS reserve-factor-bps)))
    (mul-bps-down util-applied one-minus-rf)))
```

This mirrors exactly the flawed pattern in the external report: `gaugeShare = weight*PRECISION/total` then `reward = emission*gaugeShare*typeShare/(PRECISION*PRECISION)`. Here, `util-applied = (var-borrow-rate * util-pct) / BPS` is rounded down to an integer *before* it is multiplied again by `one-minus-rf` and divided by `BPS` a second time. The mathematically correct single-division form would be:

`liquidity-rate = (var-borrow-rate * util-pct * one-minus-rf) / (BPS * BPS)`

Because the first `mul-bps-down` truncates `util-applied` to an integer in BPS units (a much coarser precision than the final combined denominator `BPS*BPS`), the truncation error is carried into the second multiplication and amplified, exactly as in the reported PoC where dividing by `WEIGHT_PRECISION` twice lost more value than dividing once by the product of denominators.

`calc-liquidity-rate`'s output is consumed by `calc-multiplier-delta` and `calc-index-next` to grow the vault's liquidity index every accrual, which is the value that determines how much underlying each z-token share (`zUSDC`, `zSTX`, etc.) is redeemable for: [2](#0-1) 

Since the liquidity index compounds every block/period the vault is touched, this rounding loss is applied repeatedly and compounds over the life of the vault, systematically underpaying every depositor's yield relative to the mathematically correct accrual.

### Impact Explanation
The direction of the error always favors under-payment (both `mul-bps-down` calls round down), so depositors across `v0-vault-usdc`, `v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-usdh`, and `v0-vault-ststxbtc` (the same helper is duplicated in each) are chronically underpaid unclaimed yield. No single party profits directly (the "lost" yield is simply never minted into the index rather than being redirected to an attacker), but the effect is a protocol-wide, permanent under-accrual of interest owed to lenders — this falls under "theft of unclaimed yield ... or permanent freezing of unclaimed yield" for depositors.

### Likelihood Explanation
This triggers on every single interest-accrual call (deposit, withdraw, borrow, repay, or any state-mutating vault call) since `calc-liquidity-rate` is on the hot path for computing the liquidity index delta. It requires no attacker action or special conditions — it happens deterministically on normal protocol usage, and the error compounds over time, making the eventual aggregate loss significant even though the loss per single call is small.

### Recommendation
Restructure `calc-liquidity-rate` to defer division until after all multiplications, similar to the reported fix for `GaugeController`:

```diff
-(define-private (calc-liquidity-rate (var-borrow-rate uint) (util-pct uint) (reserve-factor-bps uint))
-  (let ((util-applied (mul-bps-down var-borrow-rate util-pct))
-        (one-minus-rf (- BPS reserve-factor-bps)))
-    (mul-bps-down util-applied one-minus-rf)))
+(define-private (calc-liquidity-rate (var-borrow-rate uint) (util-pct uint) (reserve-factor-bps uint))
+  (let ((one-minus-rf (- BPS reserve-factor-bps)))
+    (/ (* var-borrow-rate util-pct one-minus-rf) (* BPS BPS))))
```

### Proof of Concept
Using the same style of numeric demonstration as the external report (values in BPS, `BPS = 10000`):

```
var-borrow-rate = 1234
util-pct        = 6666
reserve-factor  = 500 -> one-minus-rf = 9500

Original (double division):
util-applied = (1234 * 6666) / 10000 = 822 (rounded down from 822.6444)
result       = (822 * 9500) / 10000  = 780 (rounded down from 780.9)

Improved (single division):
result = (1234 * 6666 * 9500) / (10000 * 10000)
       = 781 (rounded down from 781.1157...)
```

The double-division path yields `780` vs the mathematically correct `781` — a 1 bps-unit loss per calculation that recurs on every accrual and compounds through the liquidity index across the vault's lifetime, analogous to the reported gauge reward truncation.
