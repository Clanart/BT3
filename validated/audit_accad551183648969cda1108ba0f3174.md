### Title
Destination-side IBC callback commits token approval/transfer before final balance validation, enabling fund duplication on callback failure - (File: x/ibc/callbacks/keeper/keeper.go)

### Summary
The external report's core lesson is: a contract restricts fund-moving functions to calls from a single, factory-selectable "router" address, so any address (even non-trusted or buggy) can be wired in as that privileged intermediary, and once that intermediary misbehaves, user funds move (or become stuck) with no fallback. The Cosmos EVM analog is `x/ibc/callbacks/keeper.ContractKeeper.IBCReceivePacketCallback`, which lets an **unprivileged IBC packet sender** name an arbitrary EVM contract address (`dest_callback.address` in the packet memo) as the "router" that receives an ERC20 `approve()` for the full received amount and is then invoked with attacker-controlled calldata, before final invariant checks are performed.

### Finding Description
In `IBCReceivePacketCallback` [1](#0-0) , the destination callback contract address is taken directly from the packet's memo (fully attacker/sender controlled, since anyone can be the source-chain sender of an ICS-20 transfer) and only checked for having code, not for being trustworthy: [2](#0-1) 

The keeper then approves the full token amount from the isolated receiver account to this arbitrary contract, and calls it with the sender-supplied calldata: [3](#0-2) 

Critically, `writeFn()` — which commits all state changes made in the cached context (the `approve` call and the callback contract execution, including any token transfers/precompile balance mutations it performed) — is invoked **before** the final safety check that verifies the isolated receiver's leftover balance is zero: [4](#0-3) 

If the balance check fails (contract didn't fully drain the approved balance via `transferFrom`), the function returns an error — but the mutations already performed inside `cachedCtx` were already written to `ctx` via `writeFn()`. Whether this results in duplicated value depends on what happens at the outer layer (ibc-go's callbacks middleware `ProcessCallback`) when `IBCReceivePacketCallback` returns a non-nil error: if the outer caller responds with an error acknowledgement (causing the source chain to refund/un-escrow the sender's original tokens) while the destination-side `writeFn()` has already durably committed a partial transfer of the coin's ERC20 representation to the attacker-specified contract, then the same asset value exists both back on the source chain (refunded to the original sender) and on the destination chain (in the malicious contract), which is a duplication of spendable value — the same accounting-invariant break as the `DAOfiV1Pair`/router bug where trusting an unvalidated intermediary breaks fund custody.

The `README` explicitly documents the invariant intent behind this design: "This check is here to prevent funds from getting stuck in the isolated address, since they would become irretrievable," and requires the callback contract to fully drain the approved allowance — but the check is performed only after the potentially problematic state has already been written back.

### Impact Explanation
If the ordering allows the error path to leave the destination-side transfer effects committed while the acknowledgement causes a source-side refund, this is a critical, unauthorized duplication of spendable value across chains — an unprivileged party (the IBC packet sender, who fully controls the destination-callback contract address and calldata in the packet memo) can mint value out of thin air by pointing the callback at a contract designed to only partially drain its approved allowance, matching the "Critical unauthorized minting/duplication of spendable user value across ... IBC escrows" allowed-impact category.

### Likelihood Explanation
I could **not conclusively verify** whether the outer ibc-go `callbacks` middleware (`ProcessCallback`, from the `cosmos/ibc-go/v10/modules/apps/callbacks` package, which is a dependency, not local code) actually reverts the packet-processing state changes when `IBCReceivePacketCallback` returns an error, or whether that revert only affects the middleware's own tracking (e.g. gas accounting) rather than the already-`writeFn()`-committed EVM/bank state. This repository does not vendor that middleware's `ProcessCallback` implementation, so the exact rollback semantics are outside the indexed code and could not be traced further. This is the key open question that determines whether the ordering bug is actually exploitable for duplication, or is merely a defense-in-depth ordering flaw that is masked by an outer transactional boundary. Given this uncertainty, this should be treated as a **plausible but unconfirmed** critical finding pending verification.

### Recommendation
Move the final safety check (verifying the isolated receiver's residual ERC20 balance is zero) to **before** calling `writeFn()`, so that if the destination callback contract fails to fully drain the approved allowance, none of the `cachedCtx` mutations (the `approve` call and the callback contract's execution effects) are committed to `ctx`. This guarantees that a failing/malicious callback contract cannot leave any committed effects on the destination chain while the source chain treats the packet as failed. Additionally, consider not granting `approve` for the full amount atomically with execution; instead, either revert the whole cached context on any failure of the invariant check, or restructure so `writeFn()` is only called after all invariants (including the balance-drain check) pass.

### Proof of Concept
1. Attacker sends an ICS-20 transfer to the Cosmos EVM chain with `memo.dest_callback.address` set to an attacker-deployed malicious contract `M`, and `dest_callback.calldata` crafted to call a benign-looking function.
2. `M` implements a function matching the expected `transferFrom(isolatedAddr, M, partialAmount)` semantics, but only pulls, say, 90% of the approved allowance (leaving 10% in the isolated receiver's balance) — while `M`'s logic already forwards the pulled ERC20 balance out to attacker-controlled addresses within the same call (or in a subsequent block, since the balance was already committed via `writeFn()`).
3. `IBCReceivePacketCallback` executes: approves `M` for full `amount`, calls `M`'s calldata (which transfers only 90%), then `writeFn()` commits these effects to `ctx`.
4. The post-`writeFn()` check finds `receiverTokenBalance != 0` (10% left) and returns an error.
5. If the outer IBC callbacks middleware treats this error as "callback failed" and returns an error acknowledgement without reverting the already-`writeFn()`-committed EVM state, the source chain un-escrows/refunds the sender's original tokens, while 90% of the equivalent value already left the destination chain into attacker's control via `M` — duplicating value across the two chains.

*(Note: step 5's premise — that the outer middleware does not revert already-committed destination-chain state on this error path — is the unverified assumption central to this finding; confirming or refuting this requires access to the `cosmos/ibc-go/v10/modules/apps/callbacks` `ProcessCallback` implementation, which is outside this repository's indexed source.)*

func (k ContractKeeper) IBCReceivePacketCallback(
	ctx sdk.Context,
	packet ibcexported.PacketI,
	ack ibcexported.Acknowledgement,
	contractAddress string,
	version string,
) error {
	data, err := transfertypes.UnmarshalPacketData(packet.GetData(), version, "")
	if err != nil {
		return err
	}

	cbData, isCbPacket, err := callbacktypes.GetCallbackData(data, version, packet.GetDestPort(), ctx.GasMeter().GasRemaining(), ctx.GasMeter().GasRemaining(), callbacktypes.DestinationCallbackKey)
	if err != nil {
		return err
	}
	if !isCbPacket {
		return nil
	}

	// `ProcessCallback` in IBC-Go overrides the infinite gas meter with a basic gas meter,
	// so we need to generate a new infinite gas meter to run the EVM executions on.
	// Skipping this causes the EVM gas estimation function to deplete all Cosmos gas.
	// We re-add the actual EVM call gas used to the original context after the call is complete
	// with the gas retrieved from the EVM message result.
	cachedCtx, writeFn := ctx.CacheContext()
	cachedCtx = evmante.BuildEvmExecutionCtx(cachedCtx).
		WithGasMeter(evmtypes.NewInfiniteGasMeterWithLimit(cbData.CommitGasLimit))

	// receiver := sdk.MustAccAddressFromBech32(data.Receiver)
	receiver, err := sdk.AccAddressFromBech32(data.Receiver)
	if err != nil {
		return errorsmod.Wrapf(types.ErrInvalidReceiverAddress,
			"acc addr from bech32 conversion failed for receiver address: %s", data.Receiver)
	}
	receiverHex, err := utils.HexAddressFromBech32String(receiver.String())
	if err != nil {
		return errorsmod.Wrapf(types.ErrInvalidReceiverAddress,
			"hex address conversion failed for receiver address: %s", receiver)
	}

	// Generate secure isolated address from sender.
	isolatedAddr := types.GenerateIsolatedAddress(packet.GetDestChannel(), data.Sender)
	isolatedAddrHex := common.BytesToAddress(isolatedAddr.Bytes())

	acc := k.authKeeper.NewAccountWithAddress(ctx, receiver)
	k.authKeeper.SetAccount(ctx, acc)

	// Ensure receiver address is equal to the isolated address.
	if receiverHex.Cmp(isolatedAddrHex) != 0 {
		return errorsmod.Wrapf(types.ErrInvalidReceiverAddress, "expected %s, got %s", isolatedAddrHex.String(), receiverHex.String())
	}

	contractAddr := common.HexToAddress(contractAddress)

	// Check if the contract address contains code.
	// This check is required because if there is no code, the call will still pass on the EVM side,
	// but it will ignore the calldata and funds may get stuck.
	if !k.evmKeeper.IsContract(ctx, contractAddr) {
		return errorsmod.Wrapf(types.ErrContractHasNoCode, "provided contract address is not a contract: %s", contractAddr)
	}
