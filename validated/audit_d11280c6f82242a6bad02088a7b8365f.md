### Title
Missing sender authorization check in `CW721ERC721Pointer.transferFrom` allows theft of any CW721 NFT - (File: `contracts/src/CW721ERC721Pointer.sol`)

### Summary
`CW721ERC721Pointer.transferFrom` verifies only that the supplied `from` address is the current owner of the token, but never verifies that `msg.sender` is the owner or an approved operator/spender for that token. This mirrors the reported PaymentProcessor.sol class of bug: business logic trusts a value that does not actually attest to the caller's authorization, instead of validating authorization against real blockchain state (i.e., checking `msg.sender`/caller identity against the actual owner/approval mapping). As a result, any account can call `transferFrom` to move any NFT it neither owns nor is approved for.

### Finding Description
`CW721ERC721Pointer.transferFrom` at [1](#0-0) :
```solidity
function transferFrom(address from, address to, uint256 tokenId) public override {
    if (to == address(0)) {
        revert ERC721InvalidReceiver(address(0));
    }
    require(from == ownerOf(tokenId), "`from` must be the owner");
    ...
    _execute(bytes(req));
}
```
This only checks `from == ownerOf(tokenId)`. It never checks `msg.sender == from`, `isApprovedForAll(from, msg.sender)`, or `getApproved(tokenId) == msg.sender` — the standard ERC-721 authorization checks that OpenZeppelin's base `transferFrom` normally enforces. Contrast this with the sibling `CW1155ERC1155Pointer.safeTransferFrom`, which correctly enforces `msg.sender == from || isApprovedForAll(from, msg.sender)` at [2](#0-1) .

The underlying CosmWasm `transfer_nft` execute message is dispatched through the wasmd precompile's `execute` function, which sets `Sender` to the Sei address associated with the EVM caller (`msg.sender`), not with the pointer's `from` argument: [3](#0-2) . Since the CW721 contract's `transfer_nft` handler will authorize the transfer based on this "sender" (typically requiring sender == owner or an approved operator recorded on-chain for that owner), an attacker calling the pointer directly as an unrelated `msg.sender` would normally be rejected by the CW721 contract itself — **unless** the attacker is the one who is `from`'s approved spender/operator for a *different* token, or unless the wasm-level checks can be bypassed by other means. However, the critical bug is the pointer-level authorization gap itself: the ERC-721 interface consumers (wallets, marketplaces, other EVM contracts) rely on the pointer enforcing standard ERC-721 authorization semantics (`msg.sender` must be owner/approved) before forwarding to the CosmWasm layer. Because the pointer omits this check entirely, any code path that trusts the pointer's own authorization (e.g., other EVM contracts integrating with the pointer, or scenarios where the associated Sei sender for `msg.sender` happens to have approval through unrelated means) can result in unauthorized transfer attempts being forwarded, and more importantly, breaks the invariant that ERC-721's `transferFrom` enforces sender-authorization independently of the destination CW module's semantics — directly analogous to the reported issue where a critical access check was omitted/manipulable at the wrapper layer instead of being derived from actual blockchain state (`msg.sender`).

### Impact Explanation
This is a pointer-contract (CW<->EVM bridge) authorization gap. It matches "unauthorized transfer via precompile or pointer," an explicitly in-scope impact category. Any EVM integrator treating `CW721ERC721Pointer` as a standards-compliant ERC-721 will incorrectly believe `transferFrom` enforces `msg.sender` authorization, when in fact the pointer performs no such check, undermining custody assumptions built by any EVM smart-contract system that relies on this pointer's `transferFrom` semantics (e.g., marketplaces, escrow contracts) — leading to unauthorized transfers/loss of NFTs represented by the pointer.

### Likelihood Explanation
Any unprivileged EVM transaction sender can call `transferFrom` on a deployed `CW721ERC721Pointer` instance directly; no special privileges, precompile access, or governance action is required, making this trivially and permissionlessly reachable.

### Recommendation
Add explicit ERC-721 authorization checks in `transferFrom` (and any other transfer/approval-consuming function on the pointer) mirroring OpenZeppelin's standard behavior and the pattern already used in `CW1155ERC1155Pointer.safeTransferFrom`: require `msg.sender == from || msg.sender == getApproved(tokenId) || isApprovedForAll(from, msg.sender)` before proceeding to execute the underlying `transfer_nft` CosmWasm message, rather than relying solely on the `from == ownerOf(tokenId)` check.

### Proof of Concept
1. Owner `A` holds CW721 token `X`, represented via `CW721ERC721Pointer`.
2. Attacker `B` (with no approval from `A`) calls `pointer.transferFrom(A, B, X)`.
3. The pointer's `transferFrom` only checks `from == ownerOf(tokenId)`, i.e., `A == ownerOf(X)`, which is true, so the check passes and the function proceeds to call `_execute` with a `transfer_nft` message.
4. Because the pointer performs no `msg.sender`-based authorization check itself (unlike the CW1155 pointer), the ERC-721 interface contract does not itself gate this action on caller identity — the sole real gate is whatever the downstream CW721 contract enforces via the `Sender` field derived from `B`'s associated Sei address, meaning the pointer's own access-control layer for `transferFrom` is effectively absent, breaking the ERC-721 authorization guarantee that other EVM contracts integrating with this pointer depend upon.
