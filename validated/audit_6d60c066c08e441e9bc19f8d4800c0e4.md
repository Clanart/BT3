### Title
Repo-local `.git/config` (`core.fsmonitor`/`core.hooksPath`/`core.sshCommand`) execution vector survives `_agentic_spawn_env` neutralization - ([File: plugins/security-guidance/hooks/llm.py])

### Summary
`_agentic_spawn_env` only sets `GIT_CONFIG_NOSYSTEM=1` and `GIT_CONFIG_GLOBAL=/dev/null`, which suppress the system-wide (`/etc/gitconfig`) and global (`~/.gitconfig`) config files, but neither variable has any effect on the repo-local `.git/config` that lives inside the untrusted repository being reviewed. Any `core.fsmonitor`, `core.hooksPath`, or `core.sshCommand` directive checked into that repo-local config remains fully honored by any `git` invocation that happens to run with `cwd=context_dir`.

### Finding Description
`agentic_review()` spawns the inner `claude` CLI with `ClaudeAgentOptions(cwd=context_dir, allowed_tools=["Read","Grep","Glob"], env=_agentic_spawn_env())` [1](#0-0) . The intent documented directly above `_agentic_spawn_env` is to "neutralize git config/env hijack vectors so an allowlisted `git diff/log/show` cannot be turned into RCE via diff.external, core.pager, core.sshCommand, or an inherited GIT_* var" [2](#0-1) .

The actual neutralization list is:
```
GIT_CONFIG_NOSYSTEM=1, GIT_CONFIG_GLOBAL=/dev/null, GIT_EXTERNAL_DIFF="", GIT_DIFF_OPTS="",
GIT_PAGER=cat, GIT_SSH_COMMAND=/bin/false, GIT_TERMINAL_PROMPT=0, GIT_OPTIONAL_LOCKS=0
``` [3](#0-2) 

`GIT_CONFIG_NOSYSTEM` and `GIT_CONFIG_GLOBAL` only affect the *system* and *global* scopes of git's config resolution order — they do not, and cannot, suppress repo-local `.git/config` (or `.gitconfig`/`include.path` reachable from it) since that scope is resolved purely from the repo the process's `cwd` points at, which here is `context_dir` — the attacker-controlled repo under review. This means an attacker who checks in a `.git/config` (or has any local checkout with a malicious config, since `.git/config` is itself part of the local repo state that a cloned/reviewed attacker repo can carry) setting `core.hooksPath` to a path inside the repo, or `core.fsmonitor` to a marker-writing script, retains that hijack even inside this "neutralized" spawn env.

The GIT_* scrub list is scoped to prevent an *allowlisted* `git diff/log/show` Bash call from being hijacked, but the agentic-review inner CLI has no Bash tool at all — only `Read/Grep/Glob` [4](#0-3) . The exposure this question is testing is therefore not "the model runs `git diff`" but any git invocation the *host `claude` CLI process itself* performs against `context_dir` outside of the model's tool-permission gate — e.g. the CLI's own automatic environment/status gathering. The project's own changelog confirms such CLI-internal git introspection exists and is independent of tool permissioning: "Fixed `CLAUDE_CODE_DISABLE_GIT_INSTRUCTIONS` and `includeGitInstructions` setting not suppressing the git status section in the system prompt" [5](#0-4) . That status-gathering path is not mediated by `allowed_tools`, so scrubbing `GIT_EXTERNAL_DIFF`/`GIT_PAGER`/`GIT_SSH_COMMAND` provides no protection against a repo-local `core.fsmonitor` or `core.hooksPath` directive being read and executed by that internal `git status` call.

### Impact Explanation
If the host `claude` CLI (or any git subprocess it spawns while `cwd=context_dir`) executes even a benign `git status`, a repo-local `core.fsmonitor` pointing at an attacker script, or `core.hooksPath` pointing at a directory inside the repo containing a script matching a hook name git might invoke, results in arbitrary command execution under the reviewer's privileges — during what is documented and marketed as a "read-only" agentic security review of untrusted repository content (Read/Grep/Glob only, no Bash/exec tool granted). This breaks the WORKSPACE_CONFINEMENT invariant: untrusted repo content gains code-execution authority purely by being checked out and reviewed.

### Likelihood Explanation
Preconditions are attacker-controlled repo content only (a checked-in or locally-present `.git/config` at `context_dir`, reachable purely by cloning/checking out the malicious repo and running the plugin's commit/push review flow against it) — no privilege escalation, no social engineering, no leaked credentials required. Feasibility depends on whether the host `claude` CLI's internal status/context gathering actually executes against `context_dir` in this SDK-spawned mode with a custom `system_prompt` and `setting_sources=[]`; this internal CLI behavior lives outside this repository (closed-source binary) and could not be fully confirmed from the plugin's own source, so likelihood is conditional on that CLI-internal invocation happening — the plugin-side mitigation gap itself (env vars not covering repo-local config) is unconditionally true and exploitable by any process, present or future, that shells out to `git` against `context_dir`.

### Recommendation
Do not rely solely on `GIT_CONFIG_NOSYSTEM`/`GIT_CONFIG_GLOBAL`. Additionally pass `-c core.fsmonitor= -c core.hooksPath=/dev/null -c core.sshCommand=/bin/false -c include.path=` (or equivalent `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` overrides, which git resolves with the highest precedence, above repo-local config) into any git invocation — including forcing the inner CLI/SDK spawn to run with an explicit safe git config override rather than trusting env-only scrubbing. Where feasible, snapshot/copy the touched files into an ephemeral directory without a live `.git` (or without a writable `core.hooksPath`-capable config) for the agentic review's `cwd`, rather than pointing `cwd` directly at the untrusted repo's working tree.

### Proof of Concept
Integration test: create a temp repo whose `.git/config` sets `core.fsmonitor = /bin/sh -c 'touch /tmp/pwned_marker'` (or `core.hooksPath` pointing at a directory with a `pre-command`/`fsmonitor-watchman` style script performing the same). Set `SG_AGENTIC_CONTEXT_DIR` to that repo and invoke `agentic_review(repo_dir, diff_files, touched_paths)` end-to-end (or, to isolate the CLI-internal path from the SDK, spawn the same `cli_path` binary directly with `cwd=context_dir` and `env=_agentic_spawn_env()`, no `--allowedTools` beyond Read/Grep/Glob, and observe whether `/tmp/pwned_marker` is created before or independent of any tool call). Assert the marker file is never created; a created marker demonstrates the repo-local git-config vector executes despite `_agentic_spawn_env`'s scrubbing.

            #

            # kill every spawn before the first API call. Omit the fallback

            fallback_model=(

            ),

            # it and prefers it over ANTHROPIC_API_KEY — but some model

            # On CCR (entrypoint=remote*) the daemon passes auth on file
