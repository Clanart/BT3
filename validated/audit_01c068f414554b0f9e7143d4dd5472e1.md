## Analysis

The original report's pattern is a **validation/normalization function that silently fails to enforce the invariant its name promises**, and that broken guarantee flows into a downstream security-critical operation. The strongest analog in GitHub Desktop is the branch-name validator used for the `x-github-client://openRepo` deep-link flow.

`app/src/lib/sanitize-ref-name.ts` defines two related functions built on the same character class: [1](#0-0) 

`sanitizedRefName` (used elsewhere to build ref names) explicitly strips leading `-`/`+` characters via `.replace(/^[-\+]*/g, '')`, but `testForInvalidChars` — which is the one actually used to *gate* attacker-supplied branch names coming from a deep link — only checks the character class and never rejects a leading dash. ### Title
Deep-link branch validation (`testForInvalidChars`) fails to reject leading-dash values, enabling git argument injection via `checkoutLocalBranch` - (File: `app/src/lib/sanitize-ref-name.ts`)

### Summary
`testForInvalidChars`, the sole guard applied to the `branch` query parameter of the `openRepo` deep link, is supposed to reject any unsafe ref name before it is used to check out a branch. It does not reject leading `-`/`+`, unlike its sibling function `sanitizedRefName` which strips them. As a result an attacker-controlled deep link can smuggle a value that looks like a git command-line flag (e.g. `--upload-pack=...`, `-b`, `--orphan`) straight into the checkout path.

### Finding Description
`parseAppURL` treats `testForInvalidChars(branch) === false` as proof the branch name is safe [5](#0-4) , but the regex used, `invalidCharacterRegex`, only blocks control characters, `~^:?*[\|"<>`, `@{`, consecutive dots, leading/trailing dot, `.lock` suffix, and trailing `/` [6](#0-5) . A leading `-` is legal by that regex, even though the codebase already recognizes leading `-`/`+` as dangerous — the parallel `sanitizedRefName` function strips it explicitly [7](#0-6) . This is the exact broken-invariant pattern from the seed report: the function that downstream code trusts to "validate" does not actually enforce the property its name implies.

The corrupted value (`branch`) is then passed unchanged to `openBranchNameFromUrl` and on to `checkoutLocalBranch` [8](#0-7) , with no `--` separator visible at this call site to defend against option-injection style values reaching the underlying `git` invocation.

### Impact Explanation
If the underlying git checkout invocation does not itself insert a `--` separator before the ref argument, a crafted branch value beginning with `-` can be interpreted by git as a command-line option rather than a ref name (e.g. forcing `-b`/`--orphan` semantics, or other checkout flags), silently altering what gets checked out/created in the victim's repository — matching the "silent corruption of what the user commits" impact class. This is triggered purely by the victim clicking an attacker-supplied `x-github-client://openRepo/...?branch=...` deep link, with no local access or credentials needed.

### Likelihood Explanation
Medium: exploitation requires (1) the victim to click a malicious deep link, and (2) the actual `git checkout`/`git branch` invocation behind `checkoutLocalBranch` to lack an independent `--` guard. I was not able to inspect `app/src/lib/git/checkout.ts` (or equivalent) within the available tool budget to confirm whether a `--` separator is present there, so this should be verified before treating it as a confirmed exploitable chain rather than a validation-layer defect. Regardless of that downstream mitigation, the validator itself is demonstrably inconsistent with the sibling sanitizer and is the wrong place to rely on for safety.

### Recommendation
Make `testForInvalidChars` reject (or have `parseAppURL` additionally reject) any branch value starting with `-` or `+`, mirroring the stripping logic already present in `sanitizedRefName`. Additionally, audit every call site that consumes attacker-supplied ref/branch strings (`checkoutLocalBranch`, `dispatchCLIAction`'s `clone-url` branch, etc.) to ensure a `--` separator precedes the ref argument in the actual git invocation, regardless of the validator's outcome, since defense-in-depth is warranted for attacker-influenced arguments.

### Proof of Concept
1. Craft a deep link: `x-github-client://openRepo/https://github.com/octocat/Hello-World?branch=--upload-pack%3D%2Ftmp%2Fevil.sh`
2. `parseAppURL` parses `branch = "--upload-pack=/tmp/evil.sh"`; `testForInvalidChars` returns `false` because none of the characters `- = / . _` are in `invalidCharacterRegex`, so the action is returned as `open-repository-from-url` with this branch value intact [9](#0-8) .
3. Victim clicks the link; `main.ts`'s `handleAppURL` forwards it to the renderer, which calls `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl(url, branchName)` → `checkoutLocalBranch(repository, branchName)` [10](#0-9) .
4. Depending on how `checkoutLocalBranch`'s underlying git call is constructed, the attacker-controlled string is interpreted as a git flag rather than a ref, potentially altering the checkout behavior without the user's knowledge.

const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }
