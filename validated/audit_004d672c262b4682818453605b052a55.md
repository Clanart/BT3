## Analysis

The M‑01 report's core broken invariant is: **external call executed before the state that guards it is finalized** (CEI violation), enabling double-spend on re-entry. I found a direct structural analog in `IntentGatewayV2`'s escrow redemption path, which already has a documented history of this exact bug class in this repo (see `IntrinsicIntentsReentrancyTest.sol`, which fixed the same pattern in `_fillSameChain` but the `withdraw()` function used for the cross-chain `RedeemEscrow`/`RefundEscrow` path was left with the unsafe ordering).

### Title
Escrow redemption in `withdraw()` performs external token/native transfers before decrementing escrow accounting, violating CEI - (File: `evm/src/apps/IntentGatewayV2.sol` / `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()`, invoked from `onAccept()` for `RequestKind.RedeemEscrow` and `RequestKind.RefundEscrow`, loops over `body.tokens` and for each entry performs a raw external call (`beneficiary.call{value: amount}("")` for native token, or `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` for ERC20) and only *afterwards* decrements the corresponding escrow balance `_orders[body.commitment][token] -= amount`. The same ordering defect applies to the transaction-fee payout, where `feeToken.call(...)` executes before `delete _orders[body.commitment][TRANSACTION_FEES]`. [1](#0-0) 

### Finding Description
The only guard against re-redeeming a given token slot is the pre-condition check `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` — a check-then-effect pattern where the "effect" (`_orders[...] -= amount`) is placed *after* the external interaction rather than before it, exactly the anti-pattern the original report flags in `HolyPaladinToken`'s `transferFrom`. Both `order.inputs[].token` (the escrowed input token) and `beneficiary` (`order.user`) are attacker-supplied values at `placeOrder()` time, so an attacker fully controls the code that executes during the external call:
- If `token == address(0)`, the low-level `.call{value: amount}("")` hands control directly to attacker-chosen `beneficiary` contract code.
- For ERC20 legs, `token.call(...)` invokes the token contract itself, which is also attacker-supplied at order creation.

The repo's own regression test explicitly documents that this exact ordering was previously exploitable in `_fillSameChain` ("Before the fix: `_filled` was set only inside `_withdraw(finalize=true)`, so a malicious beneficiary could re-enter and steal the escrowed tx fees") and had to be fixed by moving `_filled[commitment] = msg.sender` to the top of the function, before any transfers. [2](#0-1) 

`withdraw()` does set `_filled[body.commitment] = beneficiary` before the loop, which blocks the *global* double-invocation of `withdraw` for that commitment, but it does **not** protect the per-token escrow balance (`_orders[commitment][token]`) or the fee balance (`_orders[commitment][TRANSACTION_FEES]`) from being read again in a still-nonzero state during a reentrant call that occurs mid-loop, before the corresponding `-=`/`delete` executes. [3](#0-2) 

### Impact Explanation
If reachable, this allows an attacker to redeem the same escrowed token/fee amount more than once from a single `withdraw()` invocation — direct loss of bridged/escrowed funds from the gateway's balance, matching the bounty's "stealing or loss of funds" / "double-claim/double-settlement" categories.

### Likelihood Explanation
Medium-to-low confidence on exploitability specifically through this entry point: `withdraw()` is only reachable via `onAccept()`, which is `onlyHost`-gated, so a reentrant call would need to land back inside the gateway's own attacker-controlled surface (e.g. other public entrypoints like `placeOrder`/`cancelOrder`) rather than `onAccept` itself, since `onAccept` cannot be re-entered by an unprivileged caller directly. I could not fully verify, within the available index, whether the host's message-dispatch call stack permits a nested/re-entrant invocation that lands back in `withdraw` for the same or another commitment before the decrement completes. What is locally provable and unambiguous is that the CEI ordering itself is present and was already fixed elsewhere in the same contract family for the identical bug class, which is strong evidence this code path was overlooked.

### Recommendation
Apply the same fix already used in `_fillSameChain`: move all state mutations (`_orders[commitment][token] -= amount`, `delete _orders[commitment][TRANSACTION_FEES]`) before the corresponding external `.call()`/transfer within `withdraw()`, so that any reentrant call observes already-zeroed escrow state and reverts via `UnknownOrder`.

### Proof of Concept
Not independently confirmed end-to-end due to the `onlyHost` gate on `onAccept`; the concrete, locally verifiable defect is the code ordering itself:
1. `withdraw()` reads `_orders[body.commitment][token]` (non-zero check) — CHECK.
2. `withdraw()` performs `token.call(...)` / `beneficiary.call{value: amount}("")` — INTERACTION (attacker-controlled code for attacker-chosen token/beneficiary).
3. `withdraw()` performs `_orders[body.commitment][token] -= amount` — EFFECT, applied last. [4](#0-3) 

This Check→Interaction→Effect ordering is the same defect class as the M‑01 report and the same class the project's own test suite (`IntrinsicIntentsReentrancyTest.sol`) confirms was previously exploitable in a sibling function of this exact contract.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
