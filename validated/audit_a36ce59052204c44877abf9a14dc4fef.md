## Finding

### Title
Silent corruption of partially-committed changes due to diff/selection desynchronization between UI selection time and staging time - (File: `app/src/lib/git/apply.ts`)

### Summary
The Velodrome bug is fundamentally a **stale-state-used-for-a-state-changing-action** problem: reward accounting is computed against outdated data because the balance-changing function `withdrawToken()` can execute without the reward-sync step that its wrapper normally performs first. The same broken invariant exists in GitHub Desktop's partial/line-level commit flow: the *selection* the user makes (which lines to stage) is bound to line indices of a specific diff snapshot, but the code path that actually stages those lines fetches a **new, independent** diff of the file at commit time and blindly re-applies the old index-based selection to it, without verifying the two diffs still match.

### Finding Description
When a user partially stages a file (selects only some lines/hunks to commit), the selection is stored as a set of **absolute line indices** in a `DiffSelection` object [1](#0-0) , computed against whatever diff was rendered in the Changes view at that time.

`_commitIncludedChanges` in `app-store.ts` does not recompute or validate the diff before committing — it simply takes the files whose cached `selection` is non-empty from repository state and passes them straight to `createCommit`: [2](#0-1) 

`createCommit` unconditionally clears the index and calls `stageFiles`: [3](#0-2) 

`stageFiles` routes any file with a partial selection to `applyPatchToIndex`: [4](#0-3) 

`applyPatchToIndex` then fetches a **brand-new** diff of the file's current on-disk state, completely decoupled from the diff the user actually looked at when building the selection, and hands it straight to `formatPatch` together with the (potentially stale) selection: [5](#0-4) 

`formatPatch` treats the selection purely by numeric line index (`hunk.unifiedDiffStart + lineIndex`) against whatever hunks the freshly-fetched diff happens to contain — it has no way to tell that the file content shifted since the selection was recorded: [6](#0-5) 

There is a similar re-validation step for the *UI display* diff (`updateChangesWorkingDirectoryDiff`) which explicitly acknowledges this exact class of problem — "The diff might have changed dramatically since last we loaded it" — but this reconciliation only trims/re-maps *selectable* lines for redisplay purposes; it is never invoked on the commit path and does nothing to protect the actual staged content: [7](#0-6) 

In other words, exactly like `withdrawToken()` bypassing `_updateRewardForAllTokens()`, the commit path bypasses the diff-selection reconciliation step that exists elsewhere in the code for a different purpose, and stages/creates a commit using a selection whose indices are no longer guaranteed to correspond to the same lines in the diff being patched.

### Impact Explanation
If the tracked file's content on disk changes between the moment the user visually selects specific lines to include and the moment `applyPatchToIndex` fetches its diff for staging (e.g., a build tool, formatter, linter, file watcher, or any other process bundled/documented by a malicious or compromised repository rewrites the file while the user is reviewing/selecting), the line indices the user selected will be silently reapplied to a structurally different diff. This can cause:
- Unintended lines being included in the commit that the user never selected.
- Selected lines being silently dropped or misapplied to unrelated hunks.
- A commit (and subsequent push) whose content does not match what the user believed they approved — with no error, warning, or diff re-confirmation shown.

This is a direct instance of "silent corruption of what the user commits or pushes," matching the report's valid-impact category.

### Likelihood Explanation
Partial/line-level staging is a common Desktop workflow (`describe('createCommit partials'`) confirms it's a first-class, tested feature: [8](#0-7) . Any workflow where the working tree is being actively modified by tooling while the user reviews and stages (auto-formatters, watch-mode builds, generated files, or a repository-provided script the user is told to run) creates the race window. No special privileges, physical access, or leaked credentials are required — only that the file changes between the selection and the click on "Commit," which is a realistic occurrence in normal development, especially in a repository designed by an attacker to encourage such concurrent tooling.

### Recommendation
- Before staging (`applyPatchToIndex`/`stageFiles`), re-fetch the diff for each partially-selected file and validate that the file's content/hash is unchanged since the selection was recorded (or reconcile hunks the same way `updateChangesWorkingDirectoryDiff` already does for display).
- If the diff has changed, abort the commit for that file and force the user to re-review/re-select before staging, rather than silently applying old indices to new content.
- Consider capturing a content hash or diff fingerprint alongside `DiffSelection` so that `formatPatch`/`applyPatchToIndex` can reject (rather than silently apply) a selection computed from a diff that no longer matches.

### Proof of Concept
1. Open a repository in GitHub Desktop and modify a tracked file so it produces a multi-hunk diff.
2. In the Changes view, select only specific lines from hunk 1 for partial commit (this records absolute line indices in `DiffSelection`, see `app/src/models/diff/diff-selection.ts`).
3. Before clicking "Commit," have an external process (e.g., a repository-provided npm script, formatter-on-save, or file watcher) rewrite the file so the diff hunks shift (lines added/removed above the originally selected region).
4. Click "Commit." `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` fetches the *new* diff (`app/src/lib/git/apply.ts` line 60) and applies the old absolute-index selection (`formatPatch`, `app/src/lib/patch-formatter.ts` line 157) to it.
5. Inspect the resulting commit: it contains different lines than what the user visually selected in step 2, with no warning shown at any point.
