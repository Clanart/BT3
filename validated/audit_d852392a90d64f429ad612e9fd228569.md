### Title
Attacker-controlled `WWW-Authenticate` realm header spoofs GitHub Enterprise sign-in, bypassing origin-based account matching in the credential trampoline - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The reported OriginationCalculator bug is a class of "shortcut path skips a check that the primary path performs" — `_prepareRepay()` correctly deducts `principalFee`, but the alternate `rolloverLoan`/reroll path (`_calculateRolloverAmounts`) omits that same deduction, letting colluding parties siphon funds the protocol was owed. The GitHub Desktop analog is in `getEndpointKind()` in `app/src/lib/trampoline/trampoline-credential-helper.ts`: the primary/strict paths determine "is this really a GitHub endpoint" via strict hostname allow-lists (`isDotCom`, `isGHE`, `isGitHubHost`), but a secondary "happy path" branch trusts an attacker-suppliable `WWW-Authenticate` response header (`realm="GitHub"`) without any origin verification, and that classification result drives `promptForGitHubSignIn()` to launch an Enterprise sign-in flow bound to the attacker's URL.

### Finding Description
`getEndpointKind()` [1](#0-0)  is the single source of truth used by `getCredential`, `storeCredential`, and `eraseCredential` to decide whether an authentication endpoint is GitHub-owned (`'enterprise'`/`'github.com'`/`'ghe.com'`) or a third-party generic host. Its "strict" checks — `isGist`, `isDotCom`, `isGHE`, matching an existing stored account, and finally `isGitHubHost` (an actual network probe) — are all reasonable authoritative checks. But before falling back to the network probe, the function contains this bypass:

```
// When Git attempts to authenticate with a host it captures any
// WWW-Authenticate headers and forwards them to the credential helper. We
// use them as a happy-path to determine if the host is a GitHub host without
// having to resort to making a request ourselves.
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
      return 'generic'
    }
  }
}
``` [2](#0-1) 

`cred` here is parsed directly from Git's credential-helper protocol stdin (`parseCredential(command.stdin)`) [3](#0-2) , and Git populates the `wwwauth[]` entries verbatim from the HTTP response headers returned by whatever server is on the other end of the configured remote — i.e., **fully attacker-controlled content** if the user has a remote pointing at, or is redirected/proxied to, an attacker's server. Unlike `isGitHubHost`, which performs an actual network probe against the claimed host, this branch performs zero verification that the responding host is actually GitHub-affiliated; it just pattern-matches a string the remote chose to send.

When `getCredential()` sees `endpointKind !== 'generic'` and no existing account matches `apiEndpoint`, it calls:
```
const account = await ui.promptForGitHubSignIn(endpoint)
``` [4](#0-3) 

`promptForGitHubSignIn` inspects only the hostname to decide dotcom vs enterprise, and for anything other than `github.com` it invokes `beginEnterpriseSignIn` and points the sign-in flow's endpoint at the **attacker's origin**:
```
const { hostname, origin } = new URL(endpoint)
if (hostname === 'github.com') {
  this.dispatcher.beginDotComSignIn(cb)
} else {
  this.dispatcher.beginEnterpriseSignIn(cb)
  await this.dispatcher.setSignInEndpoint(origin)
}
``` [5](#0-4) 

This is the direct analog of the reported bug's broken invariant: the "authoritative" checks (`isDotCom`/`isGHE`/`isGitHubHost` — analogous to `_prepareRepay()`'s correct fee deduction) are bypassed by a secondary, less-scrutinized code path (the `wwwauth` heuristic — analogous to `_calculateRolloverAmounts()` skipping `principalFee`) that an adversary can trigger by controlling input (a fee-bearing party controlling loan terms vs. here, a remote/proxy controlling HTTP response headers).

### Impact Explanation
A malicious or compromised git remote/proxy (HTTPS git server the user has added as a remote, or a man-in-the-middle/corporate-proxy able to inject an HTTP 401 response with a crafted `WWW-Authenticate: Basic realm="GitHub"` header) can force GitHub Desktop's credential trampoline to classify the endpoint as GitHub Enterprise and pop the "Sign in to GitHub Enterprise" dialog bound to the attacker's URL, without the user having configured any GitHub/Enterprise account for that host. This can be used to:
- Trick the user into entering their GitHub Enterprise credentials/PAT into a dialog that is contextually presented as though Desktop verified the host is a legitimate GitHub instance, when in fact classification relied only on a spoofable header — this is unauthorized account binding at minimum.
- Cause the app to complete an OAuth/device or PAT sign-in flow against the attacker-controlled endpoint, after which the resulting `Account`/token is stored and, in later `getGitHubCredential` calls for the same `origin`, is fed back out to Git for that same attacker host (`findGitHubTrampolineAccount` + `credWithAccount`) [6](#0-5)  — i.e., the harvested credential is durably associated with, and re-sent to, the attacker's endpoint by Desktop itself going forward.

This matches the report's "unauthorized OAuth or account binding" / "credential exfiltration" categories and does not require local access, admin rights, prior malware, or leaked credentials — only that the attacker control the remote/proxy response, exactly as allowed by the task's valid-impact criteria.

### Likelihood Explanation
The trigger requires no unusual user action beyond doing an ordinary git operation (fetch/pull/push/clone) against an attacker-controlled or attacker-influenced (e.g. MITM'd/corporate-proxied) HTTP git remote that returns a `401` with a spoofed `WWW-Authenticate` header — something entirely within a malicious server operator's control and not "social engineering" of the user. Unlike `isGitHubHost` (network probe) and `isDotCom`/`isGHE` (fixed allow-lists), this heuristic branch has no origin/host verification whatsoever, so it fires deterministically whenever the header is present, making exploitation reliable once a user adds/fetches from the attacker's remote.

### Recommendation
Do not let the unauthenticated `wwwauth[]` header alone elevate an arbitrary host to `'enterprise'` status. Either:
1. Remove the happy-path shortcut entirely and always fall back to the network-verified `isGitHubHost(endpoint)` check, or
2. Use the header only as a hint to prioritize the request order, but still require `isGitHubHost` (or equivalent authoritative verification, e.g. checking the actual GitHub API meta endpoint) to succeed before returning `'enterprise'` and before invoking `promptForGitHubSignIn`, mirroring how `_prepareRepay()` in the reported contract bug always deducts `principalFee` regardless of the code path taken.

### Proof of Concept
1. Set up a malicious HTTP git server (or a proxy in front of one) that responds to Git's credential probe with:
   ```
   HTTP/1.1 401 Unauthorized
   WWW-Authenticate: Basic realm="GitHub"
   ```
2. In GitHub Desktop, add this server as a remote (e.g. `https://evil.example.com/foo/bar.git`) and perform a `fetch`.
3. Git captures the header and forwards it via the credential-helper protocol as `wwwauth[]=Basic realm="GitHub"` to Desktop's trampoline (`command.stdin`).
4. `getCredential` → `getEndpointKind` matches the `realm="GitHub"` pattern at [7](#0-6)  and returns `'enterprise'` without any host verification.
5. Since no stored account matches `apiEndpoint` for `evil.example.com`, `ui.promptForGitHubSignIn('https://evil.example.com')` is invoked, which calls `beginEnterpriseSignIn` and `setSignInEndpoint('https://evil.example.com')` [8](#0-7) , presenting the user with a GitHub Enterprise sign-in dialog pointed at the attacker's server.

Note: I was unable to trace the full downstream OAuth/device-flow implementation (`sign-in-store.ts`) to definitively confirm how much of the credential material reaches the attacker's server directly versus GitHub's real API during the sign-in handshake itself; this final leg would benefit from deeper review in a full Devin session with complete file access, given index size limits may have truncated some of `sign-in-store.ts` and `dispatcher.ts`.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
