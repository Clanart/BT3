### Title
GaslessSwapRouter's owner-adjustable `commissionRate` is unlocked at settlement, letting the owner extract user swap proceeds during KIP-247 gasless swaps - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
The KIP-247 `GaslessSwapRouter` contract exposes an owner-only `updateCommissionRate(uint256)` function that can change `commissionRate()` at any time [1](#0-0) . This commission is deducted from a gasless-swap user's DEX output when `swapForGas` executes on-chain, producing `Commission` and `FinalUserAmount` values reported in the `SwappedForGas` event [2](#0-1) . The node-side admission checks in the gasless tx-pool module (`kaiax/gasless`) validate the swap parameters against the *current* on-chain state (including the current commission-dependent `getAmountIn`) only at the time the transaction is admitted/promoted, not at the time it is actually executed in a block [3](#0-2) . This mirrors the reported Teller pattern exactly: a privileged party controls a fee parameter that is applied at settlement time, while the counterparty's transaction parameters were fixed/validated against an earlier fee snapshot.

### Finding Description
In the Teller report, `MarketRegistry.setMarketFeePercent()` lets a market owner change the fee applied in `lenderAcceptBid()` with no lock-in from `submitBid()`, letting the owner grab the borrower's principal. The same structural bug exists in Kaia's gasless-swap system contract:

- `GaslessSwapRouter.updateCommissionRate()` is an owner-gated setter with no timelock or restriction tied to pending swap transactions [4](#0-3) .
- A gasless user's `SwapArgs` (`AmountIn`, `MinAmountOut`, `AmountRepay`, `Deadline`) are fixed when the `GaslessSwapTx` is signed and only re-validated against **current** chain state at tx-pool admission time via `checkBalanceForSwap`, which queries `GetAmountIn` (a router view function whose result depends on `commissionRate`) [5](#0-4) .
- Actual settlement happens later, inside the block-building bundle (`[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]`), when `swapForGas` runs on-chain and applies whatever `commissionRate` is active at execution time, computing `Commission`/`FinalUserAmount` from the *current* rate [6](#0-5) .
- Because there is a time gap between admission-time validation (which snapshots the fee) and block-inclusion-time execution (which uses the live fee), the owner of `GaslessSwapRouter` can raise `commissionRate` between those two points to redirect a larger share of the swap output to the commission pool, at the expense of `FinalUserAmount` paid to the unprivileged swap sender.
- The only hard, on-chain guarantee visible from the exported test flow is `minAmountOut >= amountRepay`, enforced as a node-side/tx-pool string check ("insufficient minAmountOut") rather than demonstrably an atomic, single-transaction on-chain revert condition tied to the *actual* post-commission output [7](#0-6) . Whether the on-chain `swapForGas` itself reverts if `finalUserAmount < minAmountOut` after commission deduction could not be confirmed because the contract's Solidity source is not present in this repository (only the compiled bytecode/bindings are available) — this is a real limitation of the analysis and should be verified directly against the actual `GaslessSwapRouter.sol` source.

### Impact Explanation
If the on-chain contract does not strictly enforce `finalUserAmount (post-commission) >= minAmountOut` atomically within the same transaction, a malicious/compromised router owner can inflate `commissionRate` right before a pending gasless-swap bundle lands in a block, causing the swapper to receive less KAIA than intended (down to zero in the extreme, analogous to the 100%-fee theft in the original report) while the owner's commission balance grows. This is a direct value-extraction path against an unprivileged, ordinary user transaction (a gasless swap sender), which fits the "fee-delegation/gasless settlement theft" category explicitly in scope.

### Likelihood Explanation
Likelihood depends entirely on router-owner behavior and timing, which is analogous to the original finding's likelihood profile (a privileged fee-setter unilaterally changing a value that is applied to a counterparty's pending transaction). Given `updateCommissionRate` has no cooldown, no cap enforcement visible in the bindings, and no evidence that swap parameters lock in the commission rate at signing time, the owner could plausibly perform this ahead of any known pending gasless-swap bundle (which is visible in the public mempool as raw approve/swap transactions before block inclusion).

### Recommendation
- Have `GaslessSwapTx` (or the `GaslessSwapRouter.swapForGas` call) capture/lock the commission rate to be applied at the moment the swap transaction is signed/submitted (e.g., pass `commissionRate` as a signed parameter and require it to match or be no worse than expected), or
- Enforce an atomic on-chain check in `swapForGas` that reverts unless `finalUserAmount >= minAmountOut` computed **after** commission deduction (not just before), and
- Add a timelock/rate-cap or a maximum commission ceiling to `updateCommissionRate` so it cannot be weaponized against transactions already broadcast to the mempool.

### Proof of Concept
1. Attacker deploys/owns `GaslessSwapRouter` and calls `commissionRate()` to observe the current low rate, e.g. 1% [8](#0-7) .
2. A user broadcasts a `GaslessApproveTx` + `GaslessSwapTx` pair with `MinAmountOut`/`AmountRepay` computed against the 1% rate; the node's tx-pool admission check (`checkBalanceForSwap`) validates it successfully against current state [9](#0-8) .
3. Before the bundle is selected for block inclusion, the owner calls `updateCommissionRate()` to raise the rate sharply (e.g. to 99%) [4](#0-3) .
4. The bundle (`LendTxGenerator`, `GaslessApproveTx`, `GaslessSwapTx`) is included and `swapForGas` executes using the now-inflated commission rate, producing a `SwappedForGas` event with a drastically reduced `FinalUserAmount` and inflated `Commission` [2](#0-1) .
5. Whether step 4 reverts (protecting the user) or succeeds with a diminished payout depends on the exact Solidity logic of `swapForGas`, which is not present as source in this repository and should be manually verified against the deployed `GaslessSwapRouter.sol` before treating this as confirmed exploitable.

func (g *GaslessModule) checkBalanceForSwap(swapArgs *SwapArgs, swapNonce uint64) error {
	token := swapArgs.Token
	bc := backends.NewBlockchainContractBackend(g.Chain, nil, nil)

	g.gaslessInfoMu.RLock()
	swapRouter := g.swapRouter
	g.gaslessInfoMu.RUnlock()

	// tx.minAmountOut >= tx.amountRepay
	minAmountOut := swapArgs.MinAmountOut
	amountRepay := swapArgs.AmountRepay
	if minAmountOut.Cmp(amountRepay) < 0 {
		return fmt.Errorf("insufficient minAmountOut: minAmountOut=%s, amountRepay=%s", minAmountOut.String(), amountRepay.String())
	}

	if g.GaslessConfig.ShouldCheckSenderCode() {
		if g.getCurrentHasCode(swapArgs.Sender) {
			return errors.New("sender with code is not allowed")
		}
	}

	if g.GaslessConfig.ShouldCheckSwapAmount() {
		// tx.amountIn >= gsr.getAmountIn(minAmountOut)
		routerContract, err := kip247.NewGaslessSwapRouterCaller(swapRouter, bc)
		if err != nil {
			return err
		}
		// Required token amountIn, given the current exchange rate and the declared minAmountOut.
		requiredAmountIn, err := routerContract.GetAmountIn(nil, token, minAmountOut)
		if err != nil {
			return err
		}
		if swapArgs.AmountIn.Cmp(requiredAmountIn) < 0 {
			return fmt.Errorf("insufficient amountIn: have=%s, want=%s", swapArgs.AmountIn.String(), requiredAmountIn.String())
		}
	}

### Block building rules

Upon detection of GaslessTxs, the following logics are executed:

- Per sender, if exists, GaslessApproveTx is relocated before GaslessSwapTx.
- LendTxGenerator is prepended before GaslessApproveTx.
- A new bundle is generated which contain either `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]` or `[LendTxGenerator, GaslessSwapTx]`
- If the bundle has conflict with any previous bundles, it is excluded from the returned bundle list.
