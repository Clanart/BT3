### Title
Division-by-zero panic in `consolidatedNode.Split` during proposer reward distribution crashes all nodes finalizing a block - ([File: kaiax/reward/impl/getter.go])

### Summary
`consolidatedNode.Split()` in `kaiax/staking/staking_info.go` divides a reward amount by `totalAmount = StakingAmount + CLStakingAmount` without checking that this sum is non-zero. This split is invoked unconditionally for the block's *proposer* node in `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` (`kaiax/reward/impl/getter.go`) whenever the chain is post-Prague and the proposer's consolidated node has a registered `CLStakingInfo`. Because the codebase explicitly documents and tests that validators can remain "qualified" (and thus eligible to be selected as proposer) with **zero staking amount**, a validator that (a) registers a CL (Consensus Liquidity) pool but never deposits into it (`CLStakingAmount == 0`) and (b) withdraws its CNStaking down to zero, while still remaining in the qualified validator set, will trigger a `big.Int` division by zero the moment it is selected as block proposer. This is directly analogous to the reported TensorFlow `Conv2D` CWE-369 division-by-zero: an all-zero/degenerate input reaches an unguarded division on a hot path.

### Finding Description
`consolidatedNode.Split` computes: [1](#0-0) 

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}
	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)
	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)   // <-- panics if totalAmount == 0
	...
```

`totalAmount` is only guarded to be non-zero in the callers that use it for *staker* reward allocation (`assignStakingRewards`/`assignStakingRewardsFlex`, in `kaiax/reward/impl/getter.go`), where the loop explicitly `continue`s any node whose excess stake (over `minStake`/threshold) is `<= 0`, guaranteeing that whenever `Split` is called there, the combined amount is positive: [2](#0-1) [3](#0-2) 

However, the **proposer**'s own reward split has no such guard: [4](#0-3) 

```go
newSpec.Proposer = proposer
if !config.Rules.IsPrague || si.CLStakingInfos == nil {
    newSpec.IncRecipient(config.Rewardbase, proposer)
    return newSpec
}
cns := si.ConsolidatedNodes()
for _, cn := range cns {
    if cn.RewardAddr != config.Rewardbase {
        continue
    }
    if cn.CLStakingInfo == nil {
        break
    }
    cnAmount, clAmount := cn.Split(proposer)   // unconditional call, no zero-stake check
    ...
```

The identical unguarded pattern exists in `specWithProposerAndFundsFlex` for the flex-reward path used after Osaka.

Crucially, the codebase explicitly documents and tests that a validator can be "qualified" — and therefore eligible to be selected as block proposer under RoundRobin/Sticky policies (which don't consider stake at all) or under WeightedRandom when *all* validators are understaked — while holding **zero** staking amount: [5](#0-4) 

```go
{
    desc:         "zero stakes",
    qualified:    numsToAddrs(0, 1, 2, 3), // Note: validators can be qualified with zero stakes, if all are understaked.
    amounts:      []uint64{0, 0, 0, 0},
    ...
``` [6](#0-5) 

Combined with the fact that `CLStakingInfo` is populated as soon as a node registers a CL pool (`CLNodeId` found in the AddressBook), *before* any actual CL deposit occurs (i.e. `CLStakingAmount == 0` at registration), a validator that has withdrawn all of its CNStaking to zero, has a registered but empty CL pool, and remains in the council/qualified set, produces `cn.StakingAmount == 0 && cn.CLStakingInfo.CLStakingAmount == 0`. When this node is selected as proposer of a Prague-active block, `cn.Split(proposer)` divides by zero, and Go's `big.Int.Div` panics with "division by zero".

This reward computation runs on the block finalization / reward-distribution path (`kaiax/reward` module's `BlockState`/`GetBlockReward`/`GetDeferredReward`), which every full node executes when processing (or finalizing) that block — meaning the panic is not confined to a single malicious actor's node but crashes **every honest node** that finalizes the block, exactly analogous to the TensorFlow Conv2D floating-point-exception DoS.

### Impact Explanation
A crash triggered deterministically in block-reward computation on the finalization path causes all nodes (not just the attacker) to panic when processing that specific block, resulting in a chain-wide halt/denial of service — a High-impact "unbounded consensus divergence/crash" analog to the CWE-369 report (there, a division-by-zero DoS; here, the same primitive but hitting the reward/staking accounting layer that runs on every node for every block). This qualifies as a concrete state-divergence/availability failure reachable from an unprivileged staker's ordinary on-chain actions (staking withdrawal + CL pool registration), matching the allowed "staking and reward distribution" scope.

### Likelihood Explanation
The precondition (a qualified validator with zero total stake) is explicitly acknowledged as reachable in this codebase's own tests and documentation ("validators can be qualified with zero stakes, if all are understaked"), and CL pool registration inherently starts at zero stake before any deposit. A validator operator (staker) fully controls their own CNStaking/CLStaking withdrawal timing, and simple proposer policies (RoundRobin/Sticky) do not filter by stake at all, so reaching the zero-stake-proposer condition does not even require the "all validators understaked" corner case for WeightedRandom — it is trivially achievable under RoundRobin/Sticky policy. This makes exploitation feasible without any privileged access, purely through normal staking/unstaking operations timed around a validator's own proposer turn.

### Recommendation
In `consolidatedNode.Split` (`kaiax/staking/staking_info.go`), guard against `totalAmount.Sign() == 0` and short-circuit to returning `(amount, big.NewInt(0))` (or another well-defined degenerate split) before performing the division, mirroring the safety pattern already used for the `CLStakingInfo == nil` case. Additionally, audit all call sites in `kaiax/reward/impl/getter.go` (`specWithProposerAndFunds`, `specWithProposerAndFundsFlex`) to ensure they cannot pass a zero-total-stake node into `Split` unguarded, consistent with the existing safeguards in `assignStakingRewards`/`assignStakingRewardsFlex`.

### Proof of Concept
1. Deploy/operate a validator node `V` in the council under a chain with `istanbul.policy` = RoundRobin (or Sticky), with the Prague hardfork active.
2. Register `V`'s node in the CL Registry (creating a `CLStakingInfo` entry with `CLPoolAddr` set) without ever depositing into the CL pool (`CLStakingAmount` remains `0`).
3. Withdraw all of `V`'s CNStaking balance to `0`, while keeping `V` in the council/qualified validator set (`Council` membership is governed by add/remove-validator votes, independent of staking balance, and RoundRobin/Sticky qualification does not filter by stake — see `kaiax/valset/README.md` lines 49–50).
4. Wait for `V`'s turn to be selected as block proposer (deterministic under RoundRobin/Sticky).
5. When the block is finalized, `getDeferredRewardFullKore`/`Flex` → `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` calls `cn.Split(proposer)` for `V`'s `consolidatedNode`, where `cn.StakingAmount == 0` and `cn.CLStakingInfo.CLStakingAmount == 0`, causing `totalAmount == 0` and a division-by-zero panic in `big.Int.Div`, crashing every node processing that block.

Note: I was unable to fully trace the exact call site that invokes `GetBlockReward`/`GetDeferredReward` from the consensus `FinalizeState` path (`kaiax/reward/impl/blockstate.go`) within the available iterations, so I cannot cite the precise line confirming this executes synchronously during block finalization versus only lazily on RPC query (`kaia_getReward`). If it is only computed lazily via RPC/API (`kaiax/reward/impl/api.go`), the impact would be reduced to a public-RPC-triggerable node crash rather than a full consensus halt — still a valid Medium/High DoS via public RPC, but I recommend verifying `kaiax/reward/impl/blockstate.go` and `kaiax/system/impl/blockstate.go` call chains to confirm which severity tier applies.
