## Analysis

The report's underlying flaw is a **dual-tracking / reconciliation defect**: one data structure is the source of truth for "does this belong to entity X", another is authoritative at write time, and the reconciliation logic that's supposed to keep them in sync silently drops entries whenever a bypassing code path changes the tracked key. In `SHToken` that key was the wallet address bypassing `userBalances`; in GitHub Desktop the same pattern exists for **per-file commit-inclusion state**, keyed by a computed `FileChange.id`.

### Title
Working-directory file-selection state is silently reset to "included" when git status reclassifies a file, causing unintended file content to be committed - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
GitHub Desktop tracks whether a changed file is included in the next commit via a `DiffSelection` stored on each `WorkingDirectoryFileChange`, keyed by `FileChange.id`, which is derived from `${status.kind}+path(+oldPath)` [1](#0-0) . Every status refresh reconciles the new git status against the previous state by matching on this `id` [2](#0-1) . If a file's status *kind* changes between refreshes (e.g. Modified → Renamed/Copied, or Untracked → Added), its `id` changes and the reconciliation loses the previously-saved selection, silently falling back to the default selection computed fresh from git status. That default is "fully included" for the overwhelming majority of file kinds [3](#0-2) . `_commitIncludedChanges` later reads exactly this per-file `selection` field, with no independent cross-check against what the user actually chose, to decide what gets staged and committed [4](#0-3) .

### Finding Description
This mirrors the `SHToken` bug class exactly: two logically-linked pieces of state (the per-file `id`-keyed selection map, and the "authoritative" list rebuilt from live `git status`) are supposed to stay bound together, but the binding key (`FileChange.id`) is not stable across all operations that can legitimately occur on a cloned/fetched repository. `WorkingDirectoryStatus` itself documents this fragility: `includeAll` "need[s] to track this separately to the file list selection and perform two-way binding manually when this changes" [5](#0-4) .

The `id` is not a stable file identity — it embeds the file's *current status kind* and, for renames/copies, the `oldPath` [1](#0-0) . Anything that flips a file's git-status classification between two refreshes (a background hook, an LFS smudge/clean filter, a submodule state change, or ordinary rename-detection threshold shifts caused by further edits to a file the user deliberately deselected) produces a *new* id. `updateChangedFiles` then cannot find the `existingFile` for that id and just keeps the freshly-parsed entry as-is [6](#0-5) , which was constructed with the default selection from `buildStatusMap` — `DiffSelectionType.All` unless it's specifically an uncommitted submodule change [3](#0-2) . No warning is surfaced to the user that a file they excluded has reappeared as "included."

### Impact Explanation
This is a silent-corruption-of-what-the-user-commits primitive, an explicitly listed valid impact category. A user can deliberately uncheck/exclude a file (e.g. a file containing secrets, local config, or work-in-progress content they don't want pushed), and content from an attacker-influenced repository operation (hook scripts shipped in a cloned/fetched repo, LFS filters, submodule status changes) can cause that file to be re-included and pushed to the remote without any further explicit action or confirmation from the user, because `_commitIncludedChanges` trusts `file.selection` at commit time with no reconciliation against the user's last explicit intent beyond the id-keyed map [7](#0-6) .

### Likelihood Explanation
Desktop refreshes working-directory status automatically and frequently (on window focus, after operations, periodically) via `_refreshRepository` → `refreshChangesSection` → `_loadStatus` [8](#0-7) , so the reconciliation path in `updateChangedFiles` runs constantly in the background without any special user action. Any repository content or hook that changes a deselected file's status kind between two such refreshes — entirely plausible from a cloned/fetched repository providing its own hooks, `.gitattributes` filters, or files positioned to trip rename-detection — will trigger the id-mismatch and reset that file's selection to "included" before the user notices and clicks Commit.

### Recommendation
Do not key committed-selection persistence on a status-derived `FileChange.id`. Track selection against a stable identity (e.g., path independent of status kind, or an explicit separate map from path→selection) so that a git-status reclassification cannot silently discard a user's exclusion choice. Additionally, `updateChangedFiles` should default newly (re)appearing files that previously existed under a different id to "not included" rather than "all," and/or `_commitIncludedChanges` should re-verify selection against a user-confirmed set at commit time rather than trusting the reconciled `workingDirectory.files` state unconditionally.

### Proof of Concept
1. In a cloned repository, modify `secret.txt` and uncheck it in the Changes list (`selection = None`); its id becomes `modified+secret.txt`.
2. Trigger, via a repo-provided mechanism (e.g., a `post-checkout`/`pre-commit` hook, an LFS clean filter, or further edits that push git's rename-similarity score over threshold), a change that makes git report `secret.txt` as `renamed` (e.g. by causing >50% content overlap with a newly created file) rather than `modified`.
3. On the next automatic status refresh, `buildStatusMap` produces a new `WorkingDirectoryFileChange` with id `renamed+secret.txt+oldpath`, defaulting to `DiffSelectionType.All` [3](#0-2) .
4. `updateChangedFiles` cannot find `renamed+secret.txt+oldpath` in the previous `filesByID` map (which only has `modified+secret.txt`), so it keeps the new file's default "All" selection [6](#0-5) .
5. The user, believing `secret.txt` is still excluded (UI may not draw their attention to the reclassified row), clicks Commit; `_commitIncludedChanges` includes it because `selection.getSelectionType() !== DiffSelectionType.None` [9](#0-8) , silently committing content the user explicitly opted out of.
