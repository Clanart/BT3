### Title
Unbonding delegation permanently stuck (funds frozen forever) when the delegator address cannot receive funds at completion time - ([File: sei-cosmos/x/staking/keeper/val_state_change.go])

### Summary
`BlockValidatorUpdates` (the staking `EndBlocker` entry point) dequeues all mature `UnbondingDelegation` time-slice entries unconditionally, then calls `CompleteUnbonding` for each. If `CompleteUnbonding` fails (its only failure path is the `bankKeeper.UndelegateCoinsFromModuleToAccount` call to the delegator), the code simply does `continue` — it does not re-insert the entry into the time-based queue. The underlying `UnbondingDelegation` record is left in the store, but it can never be reprocessed because the only mechanism that walks pending unbondings is the time-slice queue, and that queue entry was already deleted.

### Finding Description
`Undelegate` creates an `UnbondingDelegation` record and inserts a `DVPair` into a time-keyed queue via `InsertUBDQueue`: [1](#0-0) 

Each block, `BlockValidatorUpdates` calls `DequeueAllMatureUBDQueue`, which unconditionally deletes matured time-slice entries from the store, and then calls `CompleteUnbonding` for each dequeued pair. If `CompleteUnbonding` returns an error, the loop just `continue`s without any further action: [2](#0-1) 

`CompleteUnbonding` returns an error whenever `bankKeeper.UndelegateCoinsFromModuleToAccount` (ultimately `SendCoins`) fails to pay the delegator — e.g. `BlockedAddr`/`CanSendTo` rejecting the recipient. Critically, if the send fails, the function returns before removing the entry or calling `SetUnbondingDelegation`, so the `UnbondingDelegation` object is left as-is in the main store: [3](#0-2) 

There is no other code path in the codebase that re-inserts a `DVPair` into the `UBDQueueTimeSlice` for a pending `UnbondingDelegation`, and there is no user-facing message to manually retry/claim a completed unbonding — `InsertUBDQueue` is only called from `Undelegate`. Once the time-slice entry is dequeued and deleted (which happens unconditionally, before the send is attempted), the `UnbondingDelegation` record becomes orphaned: it exists in the store but will never be visited by `EndBlock` again.

This is confirmed by the project's own regression test, `TestEndBlockRetainsUnbondingForInvalidRecipient`, which shows the `UnbondingDelegation` is retained in the main store (`found == true`) while the corresponding queue-time iterator is empty (`iterator.Valid() == false`) — i.e., the record survives but is permanently detached from any future processing: [4](#0-3) 

This mirrors the reported bug class exactly: a single blocked/unpayable recipient ("blocked from transfer") causes an operation (here, unbonding completion, analogous to liquidation) that batches/loops over independent obligations to permanently fail for that entry with no retry path, leaving funds and shares frozen forever in the `NotBondedPool` module account — this is state that no future transaction or governance action can unwind, since `SetWithdrawAddr`-style guard rails don't apply to plain delegator addresses (only distribution's withdraw-address flow has such a check).

By contrast, other subsystems in this same codebase that faced the identical risk were hardened to *retain retryability* rather than orphaning the record:
- `x/gov` `RefundDeposits` explicitly checks `CanSendTo`/`BlockedAddr` first and, if unpayable, simply returns without deleting the deposit record, so a future call can retry: [5](#0-4) 
- `x/distribution`'s `AfterValidatorRemoved` hook checks receivability first and reroutes to the community pool instead of attempting (and panicking on) an unpayable send: [6](#0-5) 

The staking unbonding-completion path has no equivalent safeguard: the queue entry is destroyed regardless of whether the payout will succeed, so failure permanently orphans the underlying record instead of leaving it retryable.

### Impact Explanation
Any address that becomes unable to receive funds after initiating an `Undelegate` (e.g., an EVM-associated address whose Sei mapping was re-associated away — as demonstrated by the test's own setup pattern of calling `SetAddressMapping` twice to make `CanSendTo` false, or a coinbase-prefixed address, or any future denom/address blocking mechanism) will have its unbonding tokens permanently locked in the `NotBondedPool` module account with no way to retrieve them. This is a fund-freezing bug of unbounded value (up to the full unbonding amount of any affected delegator), matching the Sherlock report's "serious bad debt / permanent freezing" class of issue, and is reachable by any staking delegator through the ordinary, permissionless `MsgUndelegate` transaction combined with subsequent (also permissionless, via EVM `associate`) address re-mapping.

### Likelihood Explanation
On Sei, `CanSendTo`/address-receivability for a delegator's cast Sei address can genuinely change between the time `Undelegate` is submitted and the unbonding period matures — the project's own tests (`TestEndBlockRetainsUnbondingForInvalidRecipient`, `TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator`) demonstrate this exact scenario is realistically reachable via EVM address re-association, which is a normal, permissionless user action (`associatePubKey`). Given the unbonding period is fixed (e.g., 21 days) and any user can re-associate their EVM address at will during that window, this is a straightforward, single-transaction-reachable path with no privileged access required.

### Recommendation
When `CompleteUnbonding` fails because the delegator cannot receive funds, do not let `BlockValidatorUpdates` treat the dequeue as final. Either:
1. Re-insert the `DVPair` into a future time slice (e.g., retry next block or after a cooldown) so the record remains retryable, mirroring the "retain, don't finalize" approach used in `x/gov`'s `RefundDeposits`, or
2. Reroute the tokens to a recoverable destination (e.g., community pool or a per-delegator escrow claimable once the address becomes receivable again) analogous to `x/distribution`'s `AfterValidatorRemoved` fallback, or
3. Add a "claim stuck unbonding" message that lets the affected delegator (or governance) complete the payout to a valid alternate address once one becomes available, similar to how `SetWithdrawAddr` allows redirecting distribution rewards.

### Proof of Concept
The existing test `TestEndBlockRetainsUnbondingForInvalidRecipient` is effectively the PoC already present in the codebase:
1. Associate an EVM address to a Sei address (`delegator`), then re-associate the same EVM address to a different Sei address (`SetAddressMapping` called twice) — this is exactly what the permissionless `associatePubKey` EVM flow does, and results in `CanSendTo(ctx, delegator) == false`.
2. Fund the `NotBondedPool` and create a matured `UnbondingDelegation` for `delegator`, inserting it into the UBD queue via `InsertUBDQueue`.
3. Call `staking.EndBlocker(ctx, app.StakingKeeper)`.
4. Observe: the pool balance is unchanged (funds not paid out), the delegator balance is zero (never received), the `UnbondingDelegation` record still exists (`found == true`), but the UBD time-slice queue no longer contains this entry (`iterator.Valid() == false`) — confirming the record is permanently orphaned from future processing. func TestEndBlockRetainsUnbondingForInvalidRecipient(t *testing.T) {
	_, app, ctx := createTestInput(t)
	maturity := time.Unix(1, 0).UTC()
	ctx = ctx.WithBlockTime(maturity)
	evmAddr := common.HexToAddress("0x3333333333333333333333333333333333333333")
	delegator := sdk.AccAddress(evmAddr[:])
	app.EvmKeeper.SetAddressMapping(ctx, delegator, evmAddr)
	app.EvmKeeper.SetAddressMapping(
		ctx,
		sdk.AccAddress(common.HexToAddress("0x4444444444444444444444444444444444444444").Bytes()),
		evmAddr,
	)
	validator := sdk.ValAddress(seiapp.AddTestAddrsIncremental(app, ctx, 1, sdk.NewInt(10000))[0])
	amount := sdk.NewInt(40)
	bondDenom := app.StakingKeeper.BondDenom(ctx)
	notBondedPool := app.StakingKeeper.GetNotBondedPool(ctx)
	coins := sdk.NewCoins(sdk.NewCoin(bondDenom, amount))

	require.NoError(t, apptesting.FundModuleAccount(
		app.BankKeeper,
		ctx,
		notBondedPool.GetName(),
		coins,
	))

	unbonding := types.NewUnbondingDelegation(delegator, validator, 0, maturity, amount)
	app.StakingKeeper.SetUnbondingDelegation(ctx, unbonding)
	app.StakingKeeper.InsertUBDQueue(ctx, unbonding, maturity)
	require.False(t, app.BankKeeper.CanSendTo(ctx, delegator))

	poolBalanceBefore := app.BankKeeper.GetBalance(ctx, notBondedPool.GetAddress(), bondDenom)
	require.NotPanics(t, func() {
		staking.EndBlocker(ctx, app.StakingKeeper)
	})

	poolBalanceAfter := app.BankKeeper.GetBalance(ctx, notBondedPool.GetAddress(), bondDenom)
	require.Equal(t, poolBalanceBefore, poolBalanceAfter)
	require.True(t, app.BankKeeper.GetBalance(ctx, delegator, bondDenom).IsZero())
	retained, found := app.StakingKeeper.GetUnbondingDelegation(ctx, delegator, validator)
	require.True(t, found)
	require.Equal(t, unbonding, retained)

	iterator := app.StakingKeeper.UBDQueueIterator(ctx, maturity)
	require.False(t, iterator.Valid())
	require.NoError(t, iterator.Close())
}

// RefundDeposits refunds deposits whose recipients can receive funds and deletes
// their records. Deposits for unpayable recipients remain recorded and backed by
// the governance module balance.
func (keeper Keeper) RefundDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		depositor := sdk.MustAccAddressFromBech32(deposit.Depositor)
		if keeper.bankKeeper.BlockedAddr(depositor) || !keeper.bankKeeper.CanSendTo(ctx, depositor) {
			// Retain the deposit so its record continues to account for the backing
			// module balance. Recovering a permanently unreceivable deposit requires
			// a migration.
			return false
		}

		err := keeper.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, depositor, deposit.Amount)
		if err != nil {
			panic(err)
		}

		store.Delete(types.DepositKey(proposalID, depositor))
		return false
	})
