## Analysis

The strongest local analog to the "insufficient hostname-whitelist" bug class (CVE-2021-22884) is in `getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts`, specifically its fallback to `isGitHubHost()` (defined in `app/src/lib/api.ts`).

### Title
Credential-helper GitHub-host classification is vulnerable to a DNS-rebinding TOCTOU, allowing OAuth token disclosure to an attacker-controlled server - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`getEndpointKind` decides whether a git remote credential request should be answered with the user's stored GitHub OAuth token. When no cached account or `WWW-Authenticate` hint is available, it falls back to `isGitHubHost(endpoint)` [1](#0-0) , which makes a single `fetch()` HEAD request and trusts the presence of an `x-github-request-id` response header to conclude the host is a real (Enterprise) GitHub instance [2](#0-1) . If that check succeeds, `getEndpointKind` returns `'enterprise'`, and the actual `git` credential-fill step in `getCredential` will hand the user's stored `Account` token/login for the matching endpoint to the `git` process for that host [3](#0-2) .

### Finding Description
The check (`isGitHubHost`'s `fetch()`) and the use (the actual `git` HTTPS connection driven by the native git binary) are two **separate DNS resolutions and two separate TCP/TLS connections** made at different times using different network stacks (Electron/Chromium's networking for `fetch`, versus the OS resolver used by the `git` process). Nothing pins the IP address resolved during the trust check to the IP address subsequently used by `git` to actually send the `Authorization`/credential data. This is the same broken invariant as the Node.js `--inspect` bug: a hostname-based allow/trust decision made once is later relied upon for a different network operation, and an attacker who controls DNS resolution for the target hostname (a classic DNS-rebinding attacker) can present the "real" GitHub Enterprise response during the check (or arrange for the WWW-Authenticate `realm="GitHub"` fallback to be satisfied) and then rebind the name to their own server before/while `git` performs the credentialed request.

Concretely, the flow is:
1. The user clones/fetches from `https://ghe.evil-attacker.example/...` (a URL the attacker fully controls, e.g. supplied via a malicious remote, a forked repo's `.git/config`, or a link that adds a remote).
2. `getEndpointKind` has no cached account and no `WWW-Authenticate` header yet, so it calls `isGitHubHost(endpoint)` [1](#0-0) .
3. `isGitHubHost` resolves the hostname and gets a response with `x-github-request-id` present (attacker can simply proxy a real GHE/GitHub.com response, or DNS-rebind to a real GitHub IP for the duration of this check) [4](#0-3) .
4. `getEndpointKind` now believes the endpoint is `'enterprise'`, and since no account exists yet for it, `getCredential` calls `ui.promptForGitHubSignIn(endpoint)` [5](#0-4)  — or, if the user already has *any* GHE account cached from a previous legitimate host and `findGitHubTrampolineAccount` matches by some looser criteria, the OAuth token for that account is attached via `credWithAccount` and returned to `git`.
5. Because DNS for the attacker's hostname is rebound (short TTL) between the `isGitHubHost` check and the moment `git` itself performs the HTTPS request, the credential-laden HTTP request from `git` is delivered to the attacker's server instead of the legitimate GitHub Enterprise host.

The existing guards do not stop this: `isKnownThirdPartyHost` only excludes a fixed list of non-GitHub SaaS domains [6](#0-5) , and the certificate-error suppression / `redirect: 'error'` options in `isGitHubHost` only protect the *check* request itself, not the subsequent independent `git` request [7](#0-6) . There is no mechanism pinning the resolved IP from the check to the later git operation, and no re-validation once the credential is about to be sent.

### Impact Explanation
If exploited, an attacker who controls a git remote URL a victim adds (e.g., via a crafted `.gitmodules`, a shared clone URL, or a malicious fork prompting the victim to add a remote) and who can perform DNS rebinding against that hostname, can trick GitHub Desktop into classifying the host as a trusted GitHub Enterprise endpoint and subsequently cause `git` to send the victim's cached GitHub OAuth credentials to the attacker's server. This matches the report's required impact class: "credential/token exfiltration" resulting from a "git remote/proxy response" the attacker controls.

### Likelihood Explanation
Exploitation requires: (1) the victim to add/use a git remote whose hostname the attacker controls DNS for (a realistic scenario for anyone routing traffic through a compromised/malicious DNS resolver, open Wi-Fi, or a misconfigured internal DNS), and (2) fast/short-TTL DNS rebinding tooling, which is well documented and used in the original CVE. It does not require local/physical access, admin rights, or pre-existing malware — it only requires network path/DNS control over one hostname, consistent with the report's threat model. However, it also requires either an existing cached account collision or the user to complete a sign-in prompt pointed at the attacker's host, which may reduce practical likelihood somewhat compared to the original inspector bug (which required no user interaction beyond visiting a page).

### Recommendation
- Do not rely on a point-in-time `fetch()`/header check to classify a git remote as a trusted GitHub host for credential-release purposes; instead pin/re-resolve and re-validate the destination immediately before releasing credentials, or perform the trust check over the exact same connection/IP that `git` will use.
- Restrict the DNS-rebinding attack surface by resolving the hostname once, validating the IP is stable, and only trusting the classification for that resolved IP within a short window (or requiring the account's cached endpoint to already match, rather than trusting a fresh unauthenticated HTTP header check).
- Consider requiring explicit user confirmation before releasing OAuth credentials to any host not already an established account endpoint, regardless of what `isGitHubHost` reports.

### Proof of Concept
Conceptual (network-level, not exploitable purely from local code reading — requires DNS control):
1. Victim adds git remote `https://gh-mirror.example.com/org/repo.git`, where attacker controls DNS for `gh-mirror.example.com` with a short TTL.
2. Victim runs `git fetch`; GitHub Desktop's trampoline credential helper invokes `getEndpointKind`, which has no account/WWW-Authenticate hit and calls `isGitHubHost('https://gh-mirror.example.com/...')`.
3. Attacker's DNS first resolves `gh-mirror.example.com` to a real GitHub Enterprise IP (or attacker proxies a real GHE `/meta` response) so `isGitHubHost` observes `x-github-request-id` and returns `true` [8](#0-7) .
4. DNS TTL expires; attacker rebinds `gh-mirror.example.com` to their own IP.
5. `getCredential`/`git` performs the actual authenticated HTTPS request to `gh-mirror.example.com`, which now resolves to the attacker's server, which receives the victim's GitHub token in the request (via prompted sign-in or credential fill) [9](#0-8) .

This is not verifiable end-to-end from static code alone (it depends on runtime DNS behavior and timing), but the code path shows no mechanism preventing the described TOCTOU between the host-trust check and the actual credentialed connection.

async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

const knownThirdPartyHosts = new Set([
  'dev.azure.com',
  'gitlab.com',
  'bitbucket.org',
  'amazonaws.com',
  'visualstudio.com',
])

const isKnownThirdPartyHost = (hostname: string) => {
  if (knownThirdPartyHosts.has(hostname)) {
    return true
  }

  for (const knownHost of knownThirdPartyHosts) {
    if (hostname.endsWith(`.${knownHost}`)) {
      return true
    }
  }

  return false
}
