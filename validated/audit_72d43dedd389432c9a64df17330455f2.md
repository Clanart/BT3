Confirmed: `harvest(address _lpToken)` in `WombatStaking.sol` is permissionless (only gated by `_onlyActivePool`, not caller-restricted), and it feeds into `_toMasterWomAndSendReward`, which ultimately calls `queueNewRewards`/`donateRewards` on `BaseRewardPool`. That function applies newly harvested rewards **instantly** to `rewardPerTokenStored` based on `totalStaked()` at that exact block, with no vesting/streaming period.

### Title
Instant, un-streamed reward-per-token updates allow front-running harvests to capture disproportionate yield by staking only momentarily - (File: rewards/BaseRewardPool.sol, wombat/WombatStaking.sol)

### Summary
`BaseRewardPool._provisionReward` (and the identical logic in `BaseRewardPoolV2._provisionReward`) applies any newly queued/donated reward immediately and in full to `rewardPerTokenStored`, proportional to whoever is staked (`totalStaked()`) in that exact block [1](#0-0) . Reward accrual into this pool is triggered by `WombatStaking.harvest(address _lpToken)`, a permissionless, unauthenticated external function gated only by `_onlyActivePool` (no caller restriction), which calls `_toMasterWomAndSendReward` to pull pending WOM/bonus rewards from the underlying Wombat pool and push them into the rewarder [2](#0-1) [3](#0-2) .

### Finding Description
This is the same bug class as the reported mStable SAVE issue: a user can deposit into the pool momentarily, immediately trigger (or front-run) a rate/reward update, and capture yield accrued over a much longer period without having genuinely contributed liquidity for that period, then withdraw right after.

In this codebase, the mechanism differs slightly but the exploitable property is the same — reward accounting has no time-weighting or vesting, so a single instantaneous state transition (the harvest) can retroactively reward whoever happens to be staked in that same/adjacent block:

1. A large amount of pending WOM/bonus rewards accrues at the underlying Wombat pool over time (e.g., hours/days) while previous LP stakers hold their positions.
2. Anyone can call the permissionless `harvest()` on the relevant `PoolHelper` (e.g. `WombatPoolHelper.harvest()` / `WombatPoolHelperV2.harvest()` / `AnkrBNBPoolHelper.harvest()`), which forwards to `WombatStaking.harvest(_lpToken)` [4](#0-3) .
3. An attacker deposits LP/staking tokens into the pool (via `WombatPoolHelper.deposit`/`depositLP`, which stakes into `MasterMagpie` and registers with the `BaseRewardPool`) immediately before calling `harvest()`.
4. `_toMasterWomAndSendReward` pulls the full backlog of pending rewards and calls `queueNewRewards`/`donateRewards` on `BaseRewardPool`, which immediately increments `rewardPerTokenStored` by `_amountReward * 10**decimals / totalStaked()` [5](#0-4) .
5. Because the attacker's stake is already counted in `totalStaked()` at that moment, their `earned()` value jumps immediately to include a full pro-rata share of rewards that accrued while they held no position [6](#0-5) .
6. The attacker can then withdraw and claim in the same or next transaction, having captured yield without providing sustained liquidity — diluting long-term stakers exactly as in the mStable analog, where a user staked momentarily around a rate update to capture yield unfairly.

This differs from a legitimate/no-impact "flash loan reward sniping" pattern only in that the reward source itself (harvested WOM emissions) is a real yield stream meant to compensate time-weighted liquidity providers; instant, non-streamed application of `_provisionReward` breaks that time-weighting entirely, and since `harvest()` is callable by anyone at any time, the attack is fully reachable from an unprivileged EOA with no admin/oracle dependency.

### Impact Explanation
This results in **theft of unclaimed yield** belonging to long-term stakers: an attacker who stakes only for the duration of one transaction (deposit → harvest → claim → withdraw) can extract a disproportionate share of rewards that should have accrued to users who held their stake throughout the accrual period. Repeated across every harvest cycle, this systematically dilutes/steals yield from genuine LPs in the `BaseRewardPool` reward pools tied to `WombatStaking`/`MasterMagpie`, matching the "theft or permanent freezing of unclaimed yield" impact category.

### Likelihood Explanation
High: `harvest()` is explicitly permissionless (`_onlyActivePool` only checks pool status, not caller) [2](#0-1) , deposits/withdrawals into `MasterMagpie`/`WombatPoolHelper` are open to any wallet, and there is no cooldown, vesting, or minimum staking-duration check anywhere in `BaseRewardPool`/`BaseRewardPoolV2`. Any wallet can monitor pending Wombat rewards off-chain and time a deposit immediately before calling (or front-running someone else's call to) `harvest()`.

### Recommendation
Introduce time-weighted reward accrual for `BaseRewardPool`/`BaseRewardPoolV2`, e.g., stream newly queued rewards linearly over a fixed duration (similar to a `periodFinish`/`rewardRate` model, as already used in `wombat/WomUp.sol`) instead of crediting `rewardPerTokenStored` instantly in `_provisionReward`. Alternatively, enforce a minimum staking duration before a user's balance counts toward `totalStaked()` for reward-distribution purposes, or restrict/rate-limit who can trigger `harvest()` relative to deposits in the same block.

### Proof of Concept
1. Wait until a `Pool` in `WombatStaking` (e.g., `pools[_lpAddress]`) has accumulated substantial pending WOM rewards from `masterWombat` over time.
2. Call `WombatPoolHelper.deposit(_amount, _minimumLiquidity)` (or `depositLP`) to stake into `MasterMagpie`'s corresponding `BaseRewardPool`, becoming part of `totalStaked()`.
3. Immediately call `WombatPoolHelper.harvest()` → `WombatStaking.harvest(_lpToken)` → `_toMasterWomAndSendReward` → `BaseRewardPool.queueNewRewards`, which instantly raises `rewardPerTokenStored` based on current `totalStaked()` [1](#0-0) .
4. Call `MasterMagpie.multiclaimSpec`/`_claimBaseRewarder` to claim the now-inflated `earned()` reward share.
5. Call `WombatPoolHelper.withdraw()` to exit the position, having captured yield accrued before the attacker ever staked.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
