### Title
Argument/flag injection into `git remote add` via attacker-controlled PR fork clone URL - (File: app/src/lib/git/remote.ts)

### Summary
When a user opens a pull request from a fork (via the "Open in Desktop" deep link or the PR list UI), Desktop calls `_findPullRequestBranch`, which calls `addRemote(repository, forkRemoteName, headCloneUrl)` with `headCloneUrl` taken straight from the GitHub API's `pullRequest.head.repo.clone_url` (or `pull_request.head.gitHubRepository.cloneURL`) without validating that it is a well-formed `https://`/`git://`/`ssh://` URL or rejecting values beginning with `-`.

### Finding Description
`addRemote` executes: [1](#0-0) 
Note the array `['remote', 'add', name, url]` has no `--` before `url`. Git's `remote add` subcommand accepts flags such as `--mirror=fetch`, `--mirror=push`, `-t <branch>`, `-m <master>`; if `url` starts with a `-`, dugite/git will interpret it as an option rather than a positional URL argument instead of failing safely.

This value flows from an untrusted source: `dispatcher.ts`'s `openPullRequestFromUrl` and `checkoutPullRequest` pass `pullRequest.head.repo.clone_url` (raw API field) or `pullRequest.head.gitHubRepository.cloneURL` (persisted from the API) into `_checkoutPullRequest` → `_findPullRequestBranch` → `addRemote`: [2](#0-1) [3](#0-2) 

Compare this to the contemporaneous hardening already applied elsewhere in the same codebase: `clone()` explicitly separates the url with `--` and blocks sensitive destination paths ( [4](#0-3) ), and `checkoutBranch`/`checkoutPaths`/`checkoutConflictedFile` all append a `--` terminator before user-influenced positional arguments ( [5](#0-4) [6](#0-5) ). `addRemote`, `setRemoteURL`, and `removeRemote` in `remote.ts` do not have this same protection — none of `['remote', 'add', name, url]`, `['remote', 'set-url', name, url]` use a `--` separator.

### Impact Explanation
Whether this is exploitable to genuine impact (rather than a hardening gap) depends on whether git's `remote add`/`set-url` accept a dangerous, single-token flag that can be smuggled through the API-sourced `clone_url` field without the app or GitHub's own URL validation rejecting it first. I could not fully verify from the indexed code alone (1) whether GitHub's API ever actually serves a `clone_url` that isn't a normal `https://…` string, and (2) whether any upstream validation (e.g., `parseRepositoryIdentifier`/`remoteRegexes` in `remote-parsing.ts`) is applied to `headCloneUrl` before it reaches `addRemote`. From what was found, `_findPullRequestBranch` uses `headCloneUrl` directly for `urlMatchesRemote` comparisons and then straight into `addRemote` with no equivalent to `parseRemote`/`sanitizeCloneName` validation. If an attacker-influenced clone_url could begin with `-`, the missing `--` separator would let git interpret it as a remote-add option, which is a corrupted-invariant/broken-guard pattern, but I cannot confirm a concrete RCE/file-write payload reachable purely through the GitHub API's `clone_url` field.

### Likelihood Explanation
Low-to-moderate confidence overall. The attacker path (open a PR from a fork, or reflect a crafted PR through "Open in Desktop") is realistic and requires no local access, matching the valid-impact criteria, but the actual reachability of a hazardous `-`-prefixed value through `clone_url` is unconfirmed given the information available in this index.

### Recommendation
Add a `--` separator before the URL argument in `addRemote` and `setRemoteURL` (mirroring `clone.ts`'s pattern), and validate `headCloneUrl`/`clone_url` values with `parseRemote`/`sanitizeCloneName` (from `remote-parsing.ts`) before they are used in any git remote-management or checkout code path originating from PR/API data.

### Proof of Concept
Not independently verified end-to-end (would require confirming that GitHub's API can be made to return/echo a `-`-prefixed `clone_url` for a PR's head repo, and that `git remote add` with a `-`-prefixed positional argument causes a meaningful side effect). Conceptually: `addRemote(repo, 'pr-fork', '--mirror=push')` would run `git remote add pr-fork --mirror=push`, which git would parse as a flag rather than a URL, producing an unexpected outcome rather than the intended remote configuration.

Given the uncertainty above, I present this as the strongest lead found, but note it does not meet the "concrete Desktop issue with exact, confirmed exploit path" bar with full confidence — the missing `--` separator is real and inconsistent with the rest of the codebase's hardening, but a full proof of triggerable impact from attacker-controlled `clone_url` data could not be established from the available code index.
