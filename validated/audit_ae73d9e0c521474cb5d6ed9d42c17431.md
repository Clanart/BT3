### Title
Copilot conflict-resolution reassembly can silently splice AI output around a *truncated* conflict hunk, leaving attacker-controlled leftover text (including a literal `>>>>>>>` marker) baked into the committed merge - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
The seed report's broken invariant is: a percentage-based split of a fixed total leaves "dust" that a downstream equality check either fails on, or (worse) is never checked at all. The GitHub Desktop analog is in the Copilot conflict-resolution pipeline: `extractConflictHunks` (which slices a conflicted file into hunks that get sent to the model) and `reassembleResolvedFile` (which splices the model's per-hunk answers back into the file) both locate the closing `>>>>>>>` marker of a hunk by taking the **first line that matches the marker regex**, with no invariant that guarantees the two passes consumed the exact same span of attacker-supplied "theirs" content. If the incoming (attacker-controlled) branch content contains a line that incidentally matches the closing-marker regex before the real `>>>>>>>` line, both the extraction and reassembly walk stop early at that decoy line. The remainder of the conflict block - including the *real* `>>>>>>> branch` marker text and any trailing "theirs" content - is never recognized as part of a hunk and is copied through verbatim into the final file that GitHub Desktop writes and lets the user commit, with no post-reassembly check that no conflict-marker text remains.

### Finding Description
`extractConflictHunks` uses simple regexes to find markers: [1](#0-0) 

When collecting the "theirs" side of a hunk, it stops at the *first* line matching the theirs-marker regex: [2](#0-1) 

`reassembleResolvedFile` independently re-walks the same raw file using the same "first match wins" strategy to find `hasSeparator`/`closingIndex`, then blindly skips through to `closingIndex + 1` and splices in the model's `resolvedContent` for that hunk: [3](#0-2) 

Both functions treat *any* line beginning with 7 `>` characters (optionally followed by whitespace or EOL) as a closing marker - `reassemblyTheirsMarker = /^>{7}(?:\s|$)/` - the same pattern used in extraction: [4](#0-3) 

The attacker only needs to control the "theirs" side of a merge (a branch/PR/commit the victim merges, cherry-picks, or rebases onto - this is exactly the "attacker controls a fetched/cloned git object" primitive called out as valid). If that content contains, anywhere before the true `>>>>>>> branch` line, a line of exactly seven `>` characters (e.g. deeply nested markdown blockquotes, an ASCII banner, or a comment block many projects use), `extractConflictHunks` will:
- Cut the `theirsContent` short at that decoy line (`hunkEnd` is set there), so the model never sees the true tail of theirs content or the real closing marker.
- Resume its outer scan *after* the decoy line, meaning the real `>>>>>>> branch-name` marker and everything up to it is now ordinary, non-hunk file content that is never touched again.

`reassembleResolvedFile`, walking the *same untouched raw file* independently, reproduces the identical premature stop (same regex, same "first match" semantics), splices the model's (necessarily incomplete) `resolvedContent` in at the decoy line, and then simply copies the leftover real marker text (`>>>>>>> branch-name` plus any content that was never sent to the model) through unchanged via `resultLines.push(lines[i])`, because that leftover text no longer matches `reassemblyOursMarker` and is therefore treated as ordinary code: [5](#0-4) 

Crucially there is **no invariant check anywhere** (unlike the Solidity `balanceOf(...) == 0` check in the seed report) verifying that the reassembled output no longer contains any `<<<<<<<`/`=======`/`>>>>>>>` marker lines. `validateResolutionPaths` only checks that the number of returned hunks matches the number of *extracted* hunks - it cannot detect that a hunk's boundaries were computed incorrectly, since both sides agree on "1 hunk" while disagreeing on where that hunk actually ends: [6](#0-5) 

### Impact Explanation
This results in silent corruption of what the user commits: the final file written to disk/staged by the Copilot conflict-resolution feature can contain a leftover literal `>>>>>>> branch-name` conflict marker and un-reviewed raw "theirs" content spliced in the middle of otherwise-resolved code, with the dialog reporting the conflict as fully resolved. Depending on file type this can silently break builds, reintroduce dead/vulnerable code that appeared "dropped" in the reasoning shown to the user, or (for config/manifest files) alter security-relevant settings without the user noticing, since the diff shown to the user is generated from the model's summary/reasoning, not from a marker-free validation of the actual bytes written.

### Likelihood Explanation
The trigger only requires that an attacker's incoming branch/PR/commit content contain a single line of exactly seven `>` characters (optionally trailed by whitespace) somewhere inside a conflicting hunk - not an unusual pattern in Markdown (nested `>` quoting), changelogs, ASCII banners, or minified diff-like text checked into a repo. The victim needs to merge/rebase/cherry-pick that content and use the built-in "resolve with Copilot" feature, which is a normal, expected workflow, not an unnatural user step.

### Recommendation
- Make `extractConflictHunks` and `reassembleResolvedFile` share a single marker-scanning implementation instead of two independently-maintained regex walks, so they can never disagree on hunk boundaries.
- After reassembly, assert that the output contains no residual lines matching the ours/base/separator/theirs marker regexes; if it does, fail closed (treat the file as unresolved / surface an error) rather than silently writing the result.
- Consider disambiguating real markers from incidental look-alikes (e.g. requiring the closing marker to be followed by the exact branch label used in the opening marker, as `git` itself emits) rather than matching on 7-character run alone.

### Proof of Concept
1. Set up a merge where the "theirs" side of a conflicting file contains, inside the conflicting hunk, a line consisting of exactly `>>>>>>>` (e.g. from nested markdown quoting) followed further down by the real closing marker `>>>>>>> feature`:
```
<<<<<<< HEAD
our change
=======
some legitimate theirs content
>>>>>>>
more theirs content that git actually wants merged
>>>>>>> feature
after-conflict content
```
2. `extractConflictHunks` (app/src/lib/copilot-conflict-context.ts:228-237) stops `theirsLines` collection at the decoy `>>>>>>>` line, setting `hunkEnd` there; `theirsContent` sent to the model becomes only `"some legitimate theirs content"`.
3. Copilot returns one hunk resolution (count matches, so `validateResolutionPaths` passes).
4. `reassembleResolvedFile` (app/src/lib/copilot-conflict-resolution.ts:560-598), scanning the same raw text, independently finds the same decoy `closingIndex`, splices in the model's answer there, then falls through to plain-line copying for `more theirs content that git actually wants merged` and the literal `>>>>>>> feature` marker - both end up verbatim in the "resolved" file that Desktop writes and offers to commit.

I could not fully trace the downstream write/commit code path (e.g. where `IFileResolution.resolvedContent` gets written to disk and staged) within the available iterations, so the exact file-write call site is not cited here; a background agent with full repository access should confirm that no additional marker-scrubbing or diff-based sanity check exists between `reassembleResolutions` and the actual file write/stage/commit step before treating this as fully validated.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}
