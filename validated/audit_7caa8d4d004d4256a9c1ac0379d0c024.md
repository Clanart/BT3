### Title
Persistent, unscoped `safe.directory` trust exception is never revoked after establishing repository ownership - (File: `app/src/lib/git/config.ts`, `app/src/ui/missing-repository.tsx`, `app/src/ui/add-repository/add-existing-repository.tsx`)

### Summary
Git's `safe.directory` mechanism exists specifically to stop a repository from auto-executing content (hooks, `core.fsmonitor`, etc.) when it's owned by a different user than the current process — a classic sign of a maliciously planted or synced folder (network share, container mount, restored backup, symlink swap). GitHub Desktop's "Trust Repository" UI (`onTrustDirectory` in `app/src/ui/missing-repository.tsx:35` and `app/src/ui/add-repository/add-existing-repository.tsx:69`) calls `addSafeDirectory(path)` once, and that grant is stored **globally and permanently** in the user's git config with no corresponding revoke path anywhere in the codebase.

### Finding Description
`addSafeDirectory` [1](#0-0)  appends the path to the global `safe.directory` multi-value config using `addGlobalConfigValueIfMissing`. This is invoked from two UI entry points when Desktop detects Git's "unsafe repository" (differing-owner) warning:

- `MissingRepository.onTrustDirectory` [2](#0-1) 
- `AddExistingRepository.onTrustDirectory` [3](#0-2) 

Like `_src.approve(address(ambientSwapDex), _maxPaidAmount)` in the original report, this is a state-mutating "approval" grant made for the purpose of a single interaction (getting past the current unsafe-owner check). But unlike a proper one-shot allowance, there is no `removeGlobalConfigValue('safe.directory', path)` call anywhere in the repo (verified via `removeConfigValue`/`removeGlobalConfigValue` in `app/src/lib/git/config.ts:237-256`, which exist as a generic API but are never wired to `safe.directory`). The grant is keyed only by filesystem path string, not by repository identity (remote URL, commit history, or content hash).

### Impact Explanation
Because the trust is path-scoped and permanent, an attacker who can cause *any* content to later occupy that same path — e.g. by replacing the directory contents on a shared/synced folder, restoring an older/malicious snapshot at the same location, or exploiting the fact that Desktop's own re-clone/"Clone Again" flow (`MissingRepository.cloneAgain`, `app/src/ui/missing-repository.tsx:169-188`) recreates content at the previously-trusted path — inherits the trust silently. Git's hook-execution and `core.fsmonitor`-style auto-run protections for that path are permanently disabled without any further user consent, which can lead to arbitrary code execution when Desktop or a subsequent `git` invocation processes the directory (hooks, submodule "protocol.file.allow", etc.). This directly maps to the report's "residual approval enabling later unintended state" pattern, but here the residual authorization is a security boundary (owner-mismatch protection), not a token allowance, making exploitation higher-impact.

### Likelihood Explanation
Medium: `safe.directory` bypass requires the attacker to control content that ends up at a path the user previously (and knowingly) trusted — this is realistic for shared drives, mounted archives, restored VM snapshots, or CI checkout directories reused across builds, all scenarios Desktop explicitly supports (the changelog even references "Support trusting repositories on network shares (Windows)" [4](#0-3) , confirming network-share reuse is an intended, common workflow). No admin rights or pre-existing malware on the host are required; the attacker only needs write access to the shared location at some point after the user trusts it.

### Recommendation
Scope the trust grant more tightly than a bare path, and provide a revoke path:
- Bind the safe-directory exception to the repository identity actually verified at trust-time (e.g., store alongside the resolved `.git` dir's initial commit or remote URL) rather than a bare filesystem path string.
- Add a `removeSafeDirectory`/`removeGlobalConfigValue('safe.directory', path)` call triggered when: the repository is removed from Desktop, the path is deleted, or Desktop detects the directory's git object database has been swapped out from under it.
- Surface currently-trusted paths in Settings so users can audit/revoke them, mirroring how `_src.approve(..., 0)` explicitly clears residual approval in the original finding.

### Proof of Concept
1. User adds a repository on a network share/synced folder at path `P`; Git flags it unsafe (different owner) and Desktop shows "Trust Repository."
2. User clicks Trust → `addSafeDirectory(P)` writes `safe.directory=P` to the *global* gitconfig permanently [1](#0-0) .
3. Time passes; the legitimate repo at `P` is removed (e.g., user removes it from Desktop, or the share is repurposed).
4. Attacker (anyone with write access to that shared path, e.g., another user on the same NAS/VM host) places a malicious git repository — including hooks — at the exact same path `P`.
5. User re-adds/re-opens the repository at `P` in Desktop (or Desktop's own `cloneAgain` recreates content there per `app/src/ui/missing-repository.tsx:169-188`). Because `safe.directory=P` is still present in global config, Git's owner-mismatch protection is bypassed with no new prompt, and any hook/auto-run content in the attacker's repository executes under the trust previously granted to a different repository.

Note: I could not find any code path that clears or scopes the `safe.directory` entry, nor tests covering revocation — this gap is confirmed by the absence of matches beyond the two `onTrustDirectory` call sites and the generic `removeConfigValue` API that is never applied to `safe.directory`. If a revocation/scoping mechanism exists outside what the index surfaced (e.g., in native trampoline binaries not covered by the search index), a live Devin session would be needed to fully confirm this gap across the whole repository.

export async function addGlobalConfigValueIfMissing(
  name: string,
  value: string
): Promise<void> {
  const { stdout, exitCode } = await git(
    ['config', '--global', '-z', '--get-all', name, value],
    __dirname,
    'addGlobalConfigValue',
    { successExitCodes: new Set([0, 1]) }
  )

  if (exitCode === 1 || !stdout.split('\0').includes(value)) {
    await addGlobalConfigValue(name, value)
  }
}
