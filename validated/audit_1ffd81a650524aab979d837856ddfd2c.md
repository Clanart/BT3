### Title
Invalid-scalar share path publishes the ECDH blame key before the message's proof-of-possession is verified, leaking honest participants' secret shares - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` returns a blame proof (`EncryptionKeyProof` containing the ECDH shared key and a DLEq proof over the recipient's static encryption key) immediately when a decrypted share fails scalar deserialization — before the batched Schnorr proof-of-possession on `msg.key` is ever verified. The PoP exists specifically to prevent an attacker from reusing a victim's per-message encryption key and thereby tricking a recipient into revealing the ECDH key for the victim's message. The early return reintroduces exactly that attack, allowing an unprivileged DKG participant to recover the ECDH shared key protecting an honest sender's secret share and decrypt it — a direct analog of "key material extraction leads to funds drained" from the Poloniex incident.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs:476-492`, the loop over received shares does:

1. `self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes)` — this *queues* the PoP verification into `batch` (it is not verified yet), then computes `key = ecdh(&self.enc_key, msg.key)` and returns `blame = EncryptionKeyProof { key, dleq }` where `dleq` proves `key = enc_key * msg.key` against the recipient's registered `enc_pub_key` (`encryption.rs:479-500`).
2. If `C::F::from_repr(share_bytes.0)` fails, the function returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` at `lib.rs:480-482` — unwinding before `batch.verify_with_vartime_blame()` at `lib.rs:493` ever checks the queued `BatchId::Decryption(l)` PoP.

The in-code rationale for the PoP states the threat precisely (`crypto/dkg/pedpop/src/encryption.rs:84-90`): without it, "Eve could observe Alice encrypt to Bob with key X, then send Bob a message also claiming to use X … Bob would then use this to create a blame argument against Eve. When they do, they'd reveal bX, revealing Alice's message to Bob." Because the non-canonical-scalar error path bypasses PoP verification entirely, Eve can replay Alice's `msg.key` (`key: C::G`, read verbatim in `EncryptedMessage::read` at `encryption.rs:171-176`), attach any garbage ciphertext that decodes to a non-canonical scalar, and use arbitrary `pop` bytes. Bob's `calculate_share` then emits a publicly consumable `EncryptionKeyProof` revealing `bX` = `ecdh(bob_enc_key, alice_msg_key)` — the ChaCha20 key for Alice's real share message to Bob (`cipher` at `encryption.rs:101-133` derives the keystream solely from `context || ecdh`).

The blame proof is verified by third parties via `BlameMachine::blame` / `AdditionalBlameMachine::blame` (`lib.rs:582-608`), and in the processor it is relayed on-chain through `VerifyBlame` (`processor/src/key_gen.rs:504-549`), so the revealed ECDH key is public.

### Impact Explanation
Critical. A single malicious DKG participant who observes the authenticated share messages (which Serai publishes/relays for blame purposes) can, for each honest sender `l`, submit a forged share message to victim Bob reusing Alice's `msg.key`. Bob publishes `EncryptionKeyProof` revealing the ECDH key for that `msg.key`, which decrypts Alice's actual secret share to Bob. Repeating for every sender yields all of Bob's incoming shares; their sum is Bob's FROST secret share (`self.secret += share` at `lib.rs:484`). Recovery of a participant's secret share breaks the threshold-key security assumption and, combined with the attacker's own shares, reduces the effective threshold — the same terminal outcome as the Poloniex key compromise (secret key material extracted → control of funds).

### Likelihood Explanation
Fully attacker-controlled with public inputs: the attacker chooses `msg.key` (copied from an observed honest `EncryptedMessage`), a ciphertext whose plaintext under the resulting keystream is a non-canonical scalar (trivially satisfiable — they cannot pick the decrypted bytes, but a random garbage ciphertext fails `from_repr` with overwhelming probability, and they can also brute-force/retry per attempt since each DKG attempt is a fresh `context`), and any `pop` bytes since the signature is never checked on this path. One forged message per honest sender per DKG attempt suffices; no collusion, no key access, no validator privileges required. The only requirement is that the attacker is a DKG participant delivering shares to a victim, which is the normal threat model PedPoP's blame system is designed for.

### Recommendation
Do not release a blame proof until the message's PoP has been verified. In `calculate_share` (crypto/dkg/pedpop/src/lib.rs), when `C::F::from_repr` fails, the code should still verify the queued `BatchId::Decryption(l)` PoP statement (e.g., run `batch.verify_with_vartime_blame()` first, or verify that single signature inline via `msg.pop.verify(...)`) and return `blame: None` when the PoP is invalid. Equivalently, `Encryption::decrypt` could verify the PoP before computing/returning the `EncryptionKeyProof`, ensuring `bX` is only ever disclosed for messages with a proven-valid proof-of-possession.

### Proof of Concept
1. Participants run PedPoP DKG. Honest Alice sends Bob `EncryptedMessage { key: X = xG, pop: σ_A, msg: Enc_{bX}(share_A→B) }` over the authenticated channel. Eve (participant) observes `X`.
2. Eve constructs `EncryptedMessage { key: X, pop: arbitrary_bytes, msg: garbage_32_bytes }` and sends it to Bob as her secret share.
3. In Bob's `KeyMachine::calculate_share` (`lib.rs:476-482`):
   - `decrypt` queues Eve's (invalid) PoP under `BatchId::Decryption(eve)`, computes `key = ecdh(bob_enc_key, X) = bX`, decrypts garbage, and returns `blame = EncryptionKeyProof { key: bX, dleq }`.
   - The garbage plaintext fails `C::F::from_repr`, so the function returns `Err(InvalidShare { participant: eve, blame: Some(blame) })` — the batch containing the PoP check is dropped.
4. Bob publishes `blame` (the protocol's intended action for faulty shares), which the coordinator/other participants accept via `AdditionalBlameMachine::blame` since the DLEq is valid for `bX`.
5. Eve computes `cipher(context, bX)` and decrypts Alice's real ciphertext to Bob, recovering `share_A→B`. Repeating steps 2–4 with every sender's `msg.key` recovers all shares to Bob; Eve sums them to obtain Bob's secret share — the exact side effect the PoP comment at `encryption.rs:84-90` says it exists to prevent.   pub fn blame_vartime(&self) -> Option<Id> {
    let mut slice = self.0.as_slice();
    while slice.len() > 1 {
      let split = slice.len() / 2;
      if multiexp_vartime(&flat(&slice[.. split])).is_identity().into() {
        slice = &slice[split ..];
      } else {
        slice = &slice[.. split];
      }
    }

    slice
      .first()
      .filter(|(_, value)| !bool::from(multiexp_vartime(value).is_identity()))
      .map(|(id, _)| *id)
  }
