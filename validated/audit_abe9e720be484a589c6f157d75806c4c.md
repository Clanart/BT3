## Summary

The Badger Citadel bug is: a "flag" mechanism is used to gate an unsafe value, but *clearing* the flag doesn't restore a *correct* replacement value — it just re-enables consumption of whatever stale value happens to be sitting in storage. The local Hyperbridge analog is in `EvmHost.sol`'s state-commitment veto path: when a fraudulent/latest state commitment is deleted, the "latest height" pointer used to gate future consensus updates is not rolled back to the actual last-known-good height — it is unconditionally reset to a hardcoded sentinel (`1`). This is a real divergence from the Substrate pallet's equivalent logic, which explicitly tracks and restores a `PreviousStateMachineHeight`.

### Title
Vetoing the latest EVM state commitment resets the height watermark to a hardcoded sentinel instead of the true prior height, reopening acceptance of stale/superseded consensus heights - (File: `evm/src/core/EvmHost.sol`)

### Summary
When a fisherman proves a state commitment is fraudulent and it gets deleted via `deleteStateMachineCommitmentInternal`, the code resets `_latestStateMachineHeight[stateMachineId]` to the literal value `1` if the vetoed height was the current latest, rather than restoring the previously valid height, unlike the Substrate implementation.

### Finding Description
`EvmHost.sol` maintains `_latestStateMachineHeight[stateMachineId]` as the watermark gating which new consensus-derived heights may be accepted. On veto of the latest commitment: [1](#0-0) 

```solidity
function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
    StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
    delete _stateCommitments[height.stateMachineId][height.height];
    delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
    // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
    if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
        _latestStateMachineHeight[height.stateMachineId] = 1;
    }
    ...
```

This hardcodes the fallback to `1` — it does **not** look up or restore the actual prior verified height. Compare this to the Substrate pallet, which explicitly tracks a `PreviousStateMachineHeight` on every store and is exercised in tests specifically to confirm rollback restores the correct, real prior height rather than a sentinel: [2](#0-1) [3](#0-2) 

The Rust consensus handler's admission rule for new heights is "only accept a height greater than the last committed one, skip duplicates already stored": [4](#0-3) 

The analogous gating on the EVM side relies on `_latestStateMachineHeight` being an accurate "current safe floor." By collapsing it to `1` instead of the true last-good height, any height strictly between `1` and the real previous height is no longer treated as "already superseded" — it becomes newly acceptable again, exactly the effect of using a stale/incorrect value once a corrective flag-clearing operation (the veto) has run, mirroring the Funding.sol bug where clearing `citadelPriceFlag` re-enabled use of an unvalidated stale value instead of the actually-verified one.

### Impact Explanation
The height watermark is a core admission-control input for state-commitment acceptance: it exists specifically to prevent already-superseded/duplicate heights from being reprocessed. Collapsing it to `1` on veto removes that protection for the entire range between `1` and the true previous height, for the affected `stateMachineId`. This can allow a stale — but validly-signed at time of original issuance — consensus update to be resubmitted and accepted as if it were new, effectively letting untrusted/outdated remote state back into the accepted-state set for that state machine, which downstream request/response verification and settlement paths (`verify_delay_passed`, request/response proof checks) treat as trustworthy. This is a false-state-acceptance class impact directly in scope of the bounty (state proofs/commitments "must never let false remote state become trusted").

### Likelihood Explanation
Triggering the reset only requires one legitimate veto of the latest commitment (an intended, permissionless-with-proof fisherman action, not an admin/governance/malicious-peer assumption) — after that, the corrupted watermark (`1`) persists for that state machine until overwritten by a new consensus update, and any account can submit a `ConsensusMessage`/equivalent handler call carrying an old but structurally valid proof for a height in the reopened range. Exploitability depends on an attacker being able to obtain/replay a consensus proof for one of those intermediate heights that is still cryptographically acceptable to the concrete consensus client's `verify_consensus` (e.g., within an unbonding/validator-rotation window) — this is plausible but not proven in-index for every consensus-client implementation, so likelihood is assessed as medium rather than certain.

### Recommendation
Mirror the Substrate pallet's behavior: track and persist the actual previous verified height per `stateMachineId` (e.g., a `_previousStateMachineHeight` mapping updated alongside `storeStateMachineCommitment`), and have `deleteStateMachineCommitmentInternal` restore `_latestStateMachineHeight` to that recorded previous height rather than the hardcoded `1` sentinel.

### Proof of Concept
1. Consensus updates land legitimate commitments for `stateMachineId = X` at heights `10`, `11`, `12`; `_latestStateMachineHeight[X] = 12`.
2. A fisherman proves height `12`'s commitment is fraudulent and calls the veto path, which invokes `deleteStateMachineCommitmentInternal(height={X,12}, fisherman)`. [5](#0-4) 
3. Since `12 == _latestStateMachineHeight[X]`, the code sets `_latestStateMachineHeight[X] = 1` — not `11` (the actual last-good height).
4. Any account resubmits a consensus proof/update for a stale height in `[2, 11]` for `X` (already superseded and previously rejected by the "only accept greater than previous height" rule). With the watermark now at `1`, that update no longer looks like a duplicate/regression and can be accepted, reinstating stale state as current for `X`.
