### Title
`threshold_i_map_to_keys_and_musig_i_map` removes our entry using the wrong index domain (threshold index vs. MuSig index), causing a panic/Err whenever the signer set is a strict subset - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The DKG-confirmation MuSig signer re-keys the incoming `HashMap<Participant, Vec<u8>>` (keyed by each validator's threshold index in the full validator set) into a map keyed by each signer's rank (`musig_i = position + 1`) within the *submitted* signer list. After rebuilding the map it removes the local placeholder with `map.remove(&our_threshold_i)` — using the *threshold* index against a map keyed by *MuSig* indexes. Like the escrow bug where `buyer` can be aliased to `seller`, two different identity domains are conflated. Whenever the set of submitted preprocesses/shares does not contain every validator below us (i.e., our threshold index != our rank among present signers), the wrong entry is removed or `unwrap()` panics.

### Finding Description
In `threshold_i_map_to_keys_and_musig_i_map` (coordinator/src/tributary/signing_protocol.rs:208-250):

1. Our own threshold index is inserted into the input map: `map.insert(our_threshold_i, vec![])` (line 219). At this point keys are threshold indexes — correct.
2. The map is then rebuilt keyed by rank: `musig_i = raw_i + 1` over the *sorted present* threshold indexes, inserted as `Participant::new(musig_i)` (lines 241-245).
3. `map.remove(&our_threshold_i).unwrap()` (line 247) removes using the threshold index, not the MuSig index.

Our MuSig index equals `rank(our_threshold_i among submitted signers) + 1`, which equals `our_threshold_i` only when all validators with smaller threshold indexes also submitted. Example: validators 1..=5, we are validator 5, signers {1,2,3,5} → our `musig_i` is 4, `map.remove(&5)` hits `None` → `unwrap()` panics. If another signer happens to occupy `musig_i == our_threshold_i`, *their* preprocess/share is removed instead and our empty `vec![]` entry remains, so `read_preprocess` in `share_internal` fails on the empty slice (lines 160-168) — or `sign`/`complete` hit `unreachable!()` on `DuplicatedParticipant`/`InvalidSigningSet` (lines 172-176, 195-199).

Both `DkgConfirmer::share` and `DkgConfirmer::complete` route through this function (lines 294-295, 318-319), and the protocol is explicitly designed for supermajority (subset) signing per the module comment.

### Impact Explanation
Any attempt to confirm a DKG (`set_keys` MuSig) where the preprocess/share set is a strict subset whose rank ordering differs from threshold ordering — the normal case the moment any validator is offline or hasn't yet submitted — deterministically panics the coordinator or returns `Err`, aborting share production/completion. This is a liveness failure of the DKG-confirmation path reachable via ordinary missing contributions, and a validator can trigger it deliberately simply by withholding its preprocess. The crash on `unreachable!()`/`.unwrap()` takes down the coordinator task handling confirmation.

### Likelihood Explanation
The bug triggers whenever `our_threshold_i` does not equal our rank among submitted signers — i.e., any submitted set missing a lower-indexed validator, or any set smaller than `our_threshold_i`. Since `share`/`complete` are invoked with whatever preprocesses/shares were ordered on-chain, and the design explicitly tolerates subsets ("validators which aren't specified as removed while still satisfying a supermajority"), this is reachable in normal operation, not just adversarially.

### Recommendation
Remove our entry by our MuSig index, not our threshold index. Compute `our_musig_i = Participant::new(rank)` where `rank` is our position in the sorted `threshold_is` (equivalently, record `raw_i + 1` when `threshold_i == our_threshold_i` during the rebuild loop) and call `map.remove(&our_musig_i)`. Also replace `.unwrap()`/the `unreachable!()` mappings with graceful error handling so a malformed/missing set cannot panic the coordinator.

### Proof of Concept
Conceptual trace with validators V1..V5 (threshold indexes 1..5), local node = V5, submitted `preprocesses` keyed `{1,2,3}` (V4 absent):

1. Line 219: map becomes `{1,2,3,5→[]}` (threshold-keyed).
2. Sorted `threshold_is` = `[1,2,3,5]`; rebuild assigns `musig_i` 1→V1, 2→V2, 3→V3, 4→V5(`[]`).
3. Line 247: `map.remove(&Participant(5))` → `None` → `unwrap()` panics.

Variant where V4 also submitted (`{1,2,3,4,5}` all present): no bug (rank == index). Variant with signers `{1,2,4,5}`, we are V5: `musig_i(V5)=4`, `map.remove(&5)` → `None` → panic. With signers `{2,3,5}`, we are V3: `our_threshold_i=3`, `musig_i` map is `{1→V2, 2→V3, 3→V5}`; `map.remove(&3)` deletes V5's real preprocess and leaves V3's `vec![]`, which `read_preprocess` rejects → `Err(Participant(2))`, mis-blaming V2.
