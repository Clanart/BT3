### Title
Persistent, unrevocable `safe.directory` trust grant enables permanent Git command execution once a path is later re-owned by an attacker - (File: `app/src/lib/git/config.ts`)

### Summary
GitHub Desktop lets a user "trust" a repository path that Git flags as having dubious/different ownership by writing that path into the **global** `safe.directory` Git config entry. This grant, once made, is permanent and global (applies to *every* future Git invocation at that path, by Desktop or any other Git client on the machine) and there is no code path anywhere in the app to remove it. This mirrors the Visor `nftApprovals` bug: an approval is granted once, is never cleared, and there is no mechanism to revoke it — so if control of the underlying resource (the NFT / the directory path) later passes to someone untrusted, the old approval is silently honored again.

### Finding Description
`addSafeDirectory()` appends the path to the global `safe.directory` config value if not already present: [1](#0-0) 

This is invoked from two UI entry points whenever Desktop detects Git's "dubious ownership" protection has been tripped (i.e., the path is/was owned by a different OS user than the current one): [2](#0-1) [3](#0-2) 

The unsafe/dubious-ownership state itself is detected via `getRepositoryType()`, which parses Git's `fatal: detected dubious ownership in repository at '<path>'` error: [4](#0-3) 

Once the user clicks "Trust Repository," the path is added to `safe.directory` and never removed:
- No `removeSafeDirectory` (or equivalent) function exists anywhere in the codebase — a repo-wide search for `removeSafeDirectory` returns zero implementations.
- `_removeRepository()` in `app-store.ts`, which handles deleting a repository from Desktop (including moving it to trash), does not touch `safe.directory` at all: [5](#0-4) 
- `_relocateRepository()` similarly never revokes trust for the old path when a repository moves: [6](#0-5) 

Git's dubious-ownership check exists specifically to stop an attacker who can create/control a directory at a path a victim will later `cd` into (shared machines, mapped/removable drives, temp directories, container bind-mounts, CI runner workspaces, restored backups, etc.) from planting a malicious `.git` (hooks, `core.fsmonitor`, `include.path`, etc.) that executes when the victim's Git client operates on that path. The whole point of the check is to be re-evaluated based on *current* ownership. Desktop's UI explicitly warns about this: "Adding untrusted repositories may automatically execute files in the repository," in the same dialog that offers the permanent bypass: [7](#0-6) 

By writing the path into the **global** `safe.directory` list with no expiry, scoping, or revoke UI, Desktop permanently disables this safeguard for that path — for every future Git operation, not just the one that prompted the trust decision, and not just from within Desktop (any `git` invocation on the machine consults the same global config).

### Impact Explanation
- **Path reuse after trust grant leads to code execution.** If a user ever trusts a path (e.g. `D:\`, a network share, `/tmp/build`, a container-mounted volume, a re-imaged machine's user profile path) and that same path is later repopulated by a different/untrusted owner — a very plausible occurrence on shared machines, CI runners, redirected profile folders, or removable media reused across users — Git will silently treat any repository placed there as trusted going forward. This defeats the dubious-ownership protection's entire purpose and can lead to execution of attacker-controlled Git hooks/config when the victim's Desktop (or any Git tool) subsequently interacts with that path.
- **No user awareness or control.** There is no settings surface listing trusted directories, and no way to un-trust a directory once granted — the user cannot even audit, let alone revoke, prior trust decisions.
- This matches the report's "Impact 1" pattern exactly: an approval that should be scoped/temporary is instead permanent, so a later change in control of the resource (NFT owner → attacker-controlled vault re-entry; directory owner → attacker-controlled directory content) silently re-triggers the dangerous capability without any new consent.

### Likelihood Explanation
Moderate-to-high. It requires only that:
1. The user, at some point, legitimately encountered a "dubious ownership" warning and clicked "Trust Repository" (a normal, encouraged action in the current UI flow for legitimate multi-user/shared setups), and
2. The same path is later reused by an untrusted party (shared workstation, VM/container image reuse, removable/mapped drive reassignment, CI/build agent workspace reuse, restored disk image) — all realistic, non-privileged, no-malware-on-host scenarios explicitly in scope.

No admin rights, no local malware, and no social engineering beyond the ordinary "click Trust to add a repo" flow are required — the vulnerable condition is purely the missing revocation mechanism combined with a subsequent, attacker-controlled write to a path the user already trusted.

### Recommendation
- Track trusted directories with additional binding beyond the raw path (or store them scoped/associated with a specific repository identity Desktop already knows), and re-validate at each session rather than relying solely on Git's global, permanent `safe.directory` list.
- Provide an explicit UI (e.g., in Preferences/Settings) that lists all `safe.directory` entries added by Desktop and lets the user remove them individually — implement a `removeSafeDirectory(path)` counterpart to `addSafeDirectory(path)` in `app/src/lib/git/config.ts`.
- Automatically prune the corresponding `safe.directory` entry when a repository is removed from Desktop (`_removeRepository`) or relocated (`_relocateRepository`), instead of leaving a stale global trust grant behind.
- Consider re-prompting trust confirmation if the on-disk ownership/identity of a previously trusted path appears to have changed since the grant (e.g., compare owner SID/UID at grant time vs. current).

### Proof of Concept
1. On a shared/multi-user Windows or Linux machine (or any environment where a path can later be re-created by a different account — VM snapshot restore, container volume reuse, CI workspace reuse, removable drive), User A adds an existing repository at path `P` that Git flags as "dubious ownership."
2. User A clicks "Trust Repository," triggering `onTrustDirectory` → `addSafeDirectory(P)`, which runs `git config --global --add safe.directory P`. [2](#0-1) [8](#0-7) 
3. User A later removes the repository from Desktop via "Remove" (`_removeRepository`), or the directory is deleted/unmounted. The global `safe.directory` entry for `P` is **not** removed — nothing in `_removeRepository` calls any config-removal function. [5](#0-4) 
4. An untrusted party gains control of path `P` (e.g., reassigned drive letter, reused container mount, or another OS account writes to the same shared path) and places a malicious Git repository there (malicious hooks, `core.fsmonitor` command, or `include.path` pointing to attacker content).
5. User A's Desktop (or any Git CLI on that machine) later interacts with path `P` again (e.g., via `_addRepositories`, `getRepositoryType`, or simply because Desktop still remembers/rescans the path). Because `P` is still listed in the global `safe.directory` config, Git skips the dubious-ownership check entirely and executes the attacker-controlled repository content. [9](#0-8)

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}

export async function getRepositoryType(path: string): Promise<RepositoryType> {
  if (!(await directoryExists(path))) {
    return { kind: 'missing' }
  }

  try {
    const result = await git(
      ['rev-parse', '--is-bare-repository', '--show-cdup', '--git-dir'],
      path,
      'getRepositoryType',
      { successExitCodes: new Set([0, 128]) }
    )

    if (result.exitCode === 0) {
      // Bare repositories will not include gitdir so we handle that separately
      if (result.stdout.startsWith('true\n')) {
        return { kind: 'bare' }
      }

      // --is-bare-repository and --show-cdup each produce a single line but
      // --git-dir could theoretically contain newlines so we parse the known
      // fields first and treat the remainder as the git dir. We use [\s\S]*
      // instead of .* for the git dir capture group because .* doesn't match
      // newlines whereas [\s\S]* matches any character including newlines.
      const match = result.stdout.match(/^(true|false)\n(.*)\n([\s\S]*)\n$/)

      if (match) {
        const [, isBare, cdup, gitDir] = match

        return isBare === 'true'
          ? { kind: 'bare' }
          : {
              kind: 'regular',
              topLevelWorkingDirectory: resolve(path, cdup),
              gitDir: resolve(path, gitDir),
            }
      }
    }

    const unsafeMatch =
      /fatal: detected dubious ownership in repository at '(.+)'/.exec(
        result.stderr
      )
    if (unsafeMatch) {
      return { kind: 'unsafe', path: unsafeMatch[1] }
    }

  public async _relocateRepository(repository: Repository): Promise<void> {
    const path = await showOpenDialog({ properties: ['openDirectory'] })

    if (path === null) {
      return
    }

    const rt = await getRepositoryType(path)

    if (rt.kind === 'regular') {
      // The repository has moved, so any main worktree we recorded before now
      // points at where it used to be. Resolve it again from the new location.
      await this.repositoriesStore.updateRepositoryPath(
        repository,
        rt.topLevelWorkingDirectory,
        rt.gitDir,
        await this.findMainWorktreePath(rt.topLevelWorkingDirectory)
      )
    } else if (rt.kind === 'unsafe') {
      // Git refuses to run in a repository it considers unsafe, so there's no
      // resolving the main worktree here. Drop the recorded path rather than
      // keep one we know is stale.
      await this.repositoriesStore.updateRepositoryPath(
        repository,
        path,
        undefined,
        undefined,
        true
      )
    } else {
      this.emitError(new Error(this.getInvalidRepoPathsMessage([path])))
    }
  }

  public async _removeRepository(
    repository: Repository | CloningRepository,
    moveToTrash: boolean
  ): Promise<void> {
    try {
      if (moveToTrash) {
        try {
          await shell.moveItemToTrash(repository.path)
        } catch (error) {
          log.error('Failed moving repository to trash', error)

          this.emitError(
            new Error(
              `Failed to move the repository directory to ${TrashNameLabel}.\n\nA common reason for this is that the directory or one of its files is open in another program.`
            )
          )
          return
        }
      }

      if (repository instanceof CloningRepository) {
        this._removeCloningRepository(repository)
      } else {
        await this.repositoriesStore.removeRepository(repository)
      }
    } catch (err) {
      this.emitError(err)
      return
    }

    const allRepositories = await this.repositoriesStore.getAll()
    if (allRepositories.length === 0) {
      this._closeFoldout(FoldoutType.Repository)
    } else {
      this._showFoldout({ type: FoldoutType.Repository })
    }
  }
