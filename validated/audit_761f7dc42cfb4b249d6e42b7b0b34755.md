### Title
Outputs paying the protocol's hardcoded internal offset addresses are classified as internal kinds and stripped of their `InInstruction` data, locking externally sent funds - ([File: processor/src/networks/bitcoin.rs])

### Summary
The LiFi report concerns funds becoming unrecoverable because the destination (recovery) address is hardcoded rather than caller-chosen. The Bitcoin processor analog: the `Branch`, `Change`, and `Forwarded` scriptPubKeys are hardcoded deterministic offsets (`Secp256k1::hash_to_F(KEY_DST, ...)`) of the multisig key, `scan_transaction` matches outputs by `script_pubkey` alone, and `get_outputs` then hardcodes the output's `kind` from the offset and only attaches the transaction's `InInstruction`/`data` when `kind == OutputType::External`. Any third-party transaction paying one of the internal-kind scripts produces an `Output` the processor reports as received, but with `data` empty — so no instruction is ever associated with it and the scheduler treats it as protocol-internal liquidity.

### Finding Description
`scanner()` deterministically derives three internal offsets — `BRANCH_OFFSET`, `CHANGE_OFFSET`, `FORWARD_OFFSET` — via `Secp256k1::hash_to_F(KEY_DST, ...)` with a fixed public domain separator, and registers them in a `Scanner` keyed purely on `script_pubkey` (`processor/src/networks/bitcoin.rs:308-347`, `networks/bitcoin/src/wallet/mod.rs:180-196`). `Scanner::scan_transaction` returns a `ReceivedOutput` for any output whose `script_pubkey` collides with a registered script, with no authentication of who sent it or why (`networks/bitcoin/src/wallet/mod.rs:199-214`).

In `get_outputs`, every match is mapped through `kinds[offset_repr]` to `OutputType::{External, Branch, Change, Forwarded}`, but the Serai `data` payload extracted from the transaction (`Self::extract_serai_data`) is copied onto the output only when `kind == OutputType::External` (`processor/src/networks/bitcoin.rs:686-735`):

```rust
for output in &mut outputs {
  if output.kind == OutputType::External {
    output.data.clone_from(&data);
  }
  output.presumed_origin.clone_from(&presumed_origin);
}
```

The internal-kind addresses — most notably `forward_address`, which is publicly derivable for any group key — are fixed destinations under network control, exactly the "hardcoded recovery address" shape: a sender paying one of them has their BTC received by the multisig while the accompanying instruction bytes are dropped, so the output is scheduled as internal (e.g., queued/branch/change UTXO feeding `Scheduler.plans`/`utxos` in `processor/src/multisigs/scheduler/utxo.rs`) and never credited to any depositor or routed per the sender's intent.

### Impact Explanation
Funds are reported as received by the processor (an `Output` is emitted and persisted/scanned into the scheduler's UTXO set) but carry no `data`, so no user-level instruction can ever claim or direct them. Like the hardcoded `recovery: msg.sender` case, the fixed destination is not one the sender controls or that the protocol will refund to: the value is absorbed into protocol-internal UTXOs, effectively locked away from the depositor. Additionally, a misclassified `Forwarded`/`Branch` output can be swept into `queued_plans`/`plans` keyed only by amount, letting an unrelated payment fund or interfere with scheduled protocol payments.

### Likelihood Explanation
Reaching the path requires only that an unprivileged party broadcast a Bitcoin transaction paying one of the deterministic internal scripts — the offsets are computable by anyone from `KEY_DST`/`hash_to_F` and the current group key, and `forward_address` is exposed as a network API. However, exploitation requires a user (or integrator) to actually send funds to an internal-kind address while relying on the dropped `data`, or to deliberately grief the scheduler — the protocol's intended flow routes user deposits to the `External` script, so this is an edge-case rather than the default path. Medium likelihood, Medium impact.

### Recommendation
Treat the recovery/destination analogously to LiFi's fix — don't hardcode classification solely by script. Options: (a) require the `InInstruction`/data to be present and well-formed before emitting any output, regardless of kind, and copy `data` onto all matched outputs (or at least `Forwarded`) so the sender's intent is preserved; (b) reject or quarantine outputs paying internal-kind scripts that arrive in transactions not created by the scheduler (e.g., verify the spending prevouts belong to the multisig); (c) make `forward_address` carry an explicit recoverable path so unsolicited payments can be attributed via `presumed_origin` instead of silently absorbed.

### Proof of Concept
1. Derive the protocol's internal scripts for the active group key `K`: `branch = p2tr(K + G*hash_to_F("Serai Bitcoin Output Offset","branch"))`, likewise `change` and `forward` — all public constants.
2. An external wallet sends `X` sats to `forward_address(K)` in a transaction that also embeds an OP_RETURN `InInstruction` naming a refund/destination.
3. `Bitcoin::get_outputs` scans the block, `scan_transaction` matches the script, `kinds[offset]` yields `OutputType::Forwarded`, and the `kind == External` gate drops the `InInstruction` (`processor/src/networks/bitcoin.rs:691-735`).
4. Result: the multisig received `X` sats which the scheduler now owns as an internal output, but no instruction credits or directs them — the sender's funds are locked under protocol control with no recovery path, mirroring the LiFi locked-recovery finding.

Caveat: I was unable to fully trace the downstream handling of `OutputType::{Branch, Change, Forwarded}` in `processor/src/multisigs/scheduler` within the available search iterations, so the exact disposition (absorbed into `utxos` vs. consumed by `queued_plans`) is inferred from the scheduler structure at `processor/src/multisigs/scheduler/utxo.rs:36-44` rather than confirmed end-to-end.
