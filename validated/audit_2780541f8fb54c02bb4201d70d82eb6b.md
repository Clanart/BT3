### Title
Unvalidated `html_url`/`avatar_url` fields from GitHub API objects passed to `shell.openExternal` via `LinkButton` allow arbitrary URI-scheme invocation - (File: `app/src/ui/lib/link-button.tsx`)

### Summary
`LinkButton.onClick` calls `shell.openExternal(uri)` with no protocol allow-list, unlike the markdown link interceptor in `sandboxed-markdown.tsx` which explicitly requires `/^https?:/`. Several call sites feed `uri` directly from GitHub API response fields (`user.html_url`, `comment.html_url`, `review.html_url`) that are echoed from data associated with a pull request — data that is influenced by whichever account/repository is involved in that PR notification flow.

### Finding Description
`LinkButton.onClick` in `app/src/ui/lib/link-button.tsx:76-92` does: [1](#0-0) 
No scheme/protocol validation is performed before calling `shell.openExternal(uri)`.

This is used with API-sourced fields in `app/src/ui/notifications/pull-request-comment-like.tsx:117-123` (`user.html_url`, `externalURL`) and in `app/src/ui/notifications/pull-request-comment.tsx:128` / `pull-request-review.tsx:133` (`comment.html_url`, `review.html_url`): [2](#0-1) [3](#0-2) 

Compare this to `sandboxed-markdown.tsx`, which explicitly guards navigation with a protocol allow-list before forwarding a link click: [4](#0-3) 

The IPC handler that ultimately performs the action, `open-external` in `app/src/main-process/main.ts:581-597`, also does not enforce a protocol restriction — it only logs when the string happens to start with `http://`/`https://`, but calls `shell.openExternal(path)` unconditionally for any other value: [5](#0-4) 

The broken invariant: the code base clearly intends (and enforces elsewhere, e.g. `sandboxed-markdown.tsx`) that only `http(s)` links reach `shell.openExternal`, but this invariant is not enforced uniformly at the two layers (`LinkButton` in the renderer, and `open-external` in the main process) that handle GitHub-API-sourced URL fields for PR notification dialogs.

### Impact Explanation
`shell.openExternal` in Electron will invoke the OS's default handler for whatever URI scheme is supplied. Historically this has been abused (in Electron apps generally) to reach OS-level protocol handlers that can lead to local file execution or other dangerous OS behavior (e.g., Windows `search-ms:`/`ms-search:` handlers, custom-registered protocol handlers on the victim's machine, or `file://` disclosure of local resources). If a GitHub user (any account, including an untrusted PR author or an attacker who can influence how these fields are populated/returned by GHE/GitHub API responses) can set their profile/comment `html_url` to a non-`http(s)` URI, a Desktop user who has a PR-review-notification dialog opened and clicks the "author"/"time"/"Open in Browser" link would have that URI passed straight to `shell.openExternal` without protocol filtering — unlike identical-looking links rendered through the markdown path, which are filtered.

### Likelihood Explanation
Likelihood is limited by the fact that `html_url`/`avatar_url` fields normally originate from GitHub's own API and are expected to be canonical `https://` URLs generated server-side, so under normal operation exploitation requires either a compromised/malicious GHE server response, a man-in-the-middle able to alter API JSON, or some GitHub-side inconsistency that allows a user-controlled URL to populate these specific fields verbatim. I was not able to fully verify from the indexed code whether any of these `html_url`/`avatar_url` values can, in practice, be attacker-set to a non-http(s) value through any legitimate GitHub/GHE flow — this would need to be confirmed against the live API/GHE data model, which is outside what I can validate from the client-side code alone.

### Recommendation
Add the same protocol allow-list used in `sandboxed-markdown.tsx` (`/^https?:/`) to `LinkButton.onClick` before calling `shell.openExternal`, and enforce the same restriction server-side in the `open-external` IPC handler in `app/src/main-process/main.ts` (reject/refuse non-`http(s)` schemes rather than only logging), so that the invariant is enforced at both call sites regardless of which UI component initiates the request.

### Proof of Concept
Because this depends on confirming that a GitHub/GHE API response can actually populate `user.html_url`, `comment.html_url`, or `review.html_url` with a non-`https` value under attacker influence — which I could not verify from the indexed client-side code alone — I cannot provide a fully concrete, end-to-end PoC with certainty. A Devin session with access to the full repository and to GitHub's API schemas would be needed to confirm reachability of these fields with attacker-controlled non-`http(s)` values before treating this as a confirmed, exploitable Desktop issue.
