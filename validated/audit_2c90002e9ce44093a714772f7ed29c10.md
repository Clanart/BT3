### Title
Unbounded EIP-7702 authorization-list processing causes CPU exhaustion during EVM ante-handling (CheckTx/DeliverTx), before any gas or fee is charged - (File: app/ante/evm_checktx.go)

### Summary
The ALPINE-CVE-2025-14831 bug class is "cheap-to-submit input containing an unbounded number of entries forces the validator to perform expensive per-entry cryptographic/validation work before rejecting it, causing CPU/memory DoS." The analogous reachable path in sei-chain is the EIP-7702 `SetCodeTx` authorization list (`AuthList`), which is walked once per entry doing ECDSA public-key recovery and multiple state lookups, and this walk happens in the ante pipeline *before* intrinsic gas or fees are validated for that work.

### Finding Description
`EvmStatelessChecks` in `app/ante/evm_checktx.go:78-159` does compute `core.IntrinsicGas` and compares it against `etx.Gas()`, and `x/evm/types/ethtx/semantic_validation.go:50-72` (`validateAuthList`) only checks that the auth list is non-empty and that each entry's field lengths are within RLP-signature bounds — there is no cap on the *number* of entries in `AuthList`. [1](#0-0) 

Both `EvmCheckTxAnte` (mempool/CheckTx path) and `EvmDeliverTxAnte` (DeliverTx path) call `AssociateAuthorizationAuthorities`, which iterates every authorization in the transaction and, for each one, performs full ECDSA signature recovery via `RecoverAddressesFromAuthorization` plus additional `Authority()` recovery, code/nonce/association state lookups: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

Critically, in `EvmCheckTxAnte` this per-authorization recovery loop (`AssociateAuthorizationAuthorities`, line 65) runs **before** `EvmCheckAndChargeFees` / `BuyGas` (line 66), and the whole call runs under an infinite gas meter installed just above it: [6](#0-5) 

The `x/evm/ante.EVMPreprocessDecorator` path used for the main `evmAnteDecorators` chain has the same ordering problem: `associateAuthorizationAuthorities` (which recovers every authorization) runs inside `EVMPreprocessDecorator.AnteHandle`, which executes *before* `NewBasicDecorator` (the decorator that performs the `core.IntrinsicGas` check that accounts for `SetCodeAuthorizations()` cost): [7](#0-6) [8](#0-7) [9](#0-8) 

So a `SetCodeTx` with a very large `AuthList` (each entry only ~100 bytes of RLP: chain id, address, nonce, v, r, s) forces every full node's CheckTx (mempool admission) and DeliverTx ante-handling to perform one full secp256k1 recovery (twice: once in `RecoverAddressesFromAuthorization`, once via `auth.Authority()` cross-check) plus several state reads per authorization entry, all before the node has verified the sender can even pay for the tx (fees/BuyGas happens afterward) and before the true intrinsic-gas-based cost of the auth list is enforced relative to this specific expensive work.

### Impact Explanation
This is directly comparable to the GnuTLS CVE's impact class: excessive CPU/memory consumption from processing an unbounded number of entries in attacker-supplied structured data. Here, an attacker can craft a single `SetCodeTx` with thousands of bogus (or even self-consistent but pointless) authorizations. Every validator/full node that receives this transaction in its mempool (`CheckTx`) or during block execution (`DeliverTx`) will perform the expensive `RecoverAddressesFromAuthorization`/`Authority()` ECDSA recovery for each entry before any fee is deducted or the transaction is rejected for insufficient balance. Broadcasting such transactions repeatedly (they need not even be included in a block, or can be cheaply cycled through nonces/rejected) can degrade node CPU across the network, delaying block production and potentially exceeding the 2.5s block-time threshold, which is an explicitly in-scope impact.

### Likelihood Explanation
Reachability is straightforward: any unprivileged EVM transaction sender can construct and sign a `SetCodeTx` with an arbitrarily long `AuthList` (bounded only by generic tx-size/mempool byte limits, not by any auth-count-specific cap), and broadcast it via the public JSON-RPC surface. No special privileges, precompile access, or governance action is required — this is a stock EIP-7702 transaction shape accepted by the module's `SetCodeTx` handling (`x/evm/types/ethtx/set_code_tx.go`), and `validateAuthList` performs no bound on the number of authorizations.

### Recommendation
- Enforce an explicit maximum authorization-list length in `validateAuthList` (`x/evm/types/ethtx/semantic_validation.go`), consistent with reasonable per-tx bounds (e.g., proportional to a sane per-entry gas/CPU budget), independent of generic tx byte-size limits.
- Reorder ante-handler execution so that intrinsic-gas / fee-affordability checks (which already account for `SetCodeAuthorizations()` cost via `core.IntrinsicGas`) are performed and enforced **before** `AssociateAuthorizationAuthorities`/`associateAuthorizationAuthorities` perform any per-authorization ECDSA recovery, in both `EvmCheckTxAnte` (`app/ante/evm_checktx.go`) and `EVMPreprocessDecorator` (`x/evm/ante/preprocess.go`).
- Consider charging (or metering against a bounded, non-infinite gas meter) the authorization-recovery loop itself, mirroring the calldata-decode gas-charging pattern already used for precompiles (`precompiles/common/precompiles.go` `chargeDecodeGas`), so the cost is paid for by the submitter rather than absorbed unconditionally by every node.

### Proof of Concept
1. Generate N (e.g., 50,000) random ECDSA keypairs and sign an `ethtypes.SetCodeAuthorization` for each (chain ID = local chain, arbitrary target address, nonce = 0) — this mirrors the pattern in `app/setcode_authority_test.go:33-52`.
2. Build a single `SetCodeTx` (`ethtypes.SetCodeTx`) with `AuthList` containing all N authorizations, signed by a funded sponsor account, as in `x/evm/ante/preprocess_test.go:67-83`.
3. Submit the transaction to a node's `CheckTx` (mempool) endpoint repeatedly (with incrementing nonce or as a `ReCheckTx` replay). Each call routes through `EvmCheckTxAnte` → `AssociateAuthorizationAuthorities`, which performs N full ECDSA recoveries and N sets of state lookups before `EvmCheckAndChargeFees` even runs.
4. Measure CPU time per `CheckTx` call versus a baseline transaction with an empty/short auth list; observe that cost scales linearly (and unbounded) with N, entirely outside of any gas/fee accounting, and is incurred by every node that receives the tx over gossip.

Note: I was not able to independently confirm the exact mempool/tx byte-size cap enforced by the Tendermint/CometBFT layer in this codebase (e.g., `max_tx_bytes` config), which determines the practical upper bound on N per transaction; this would need to be checked in a live/full checkout to size the worst-case N precisely.

func validateAuthList(authList AuthList) error {
	if len(authList) == 0 {
		return fmt.Errorf("auth list cannot be empty")
	}
	for _, auth := range authList {
		if auth.ChainID == nil {
			return fmt.Errorf("auth list chain id cannot be nil")
		}
		if err := validateHexAddress("auth list address", auth.Address); err != nil {
			return err
		}
		if err := validateSignatureValue("auth list v", auth.V, 1); err != nil {
			return err
		}
		if err := validateSignatureValue("auth list r", auth.R, 32); err != nil {
			return err
		}
		if err := validateSignatureValue("auth list s", auth.S, 32); err != nil {
			return err
		}
	}
	return nil
}

func AssociateAuthorizationAuthorities(ctx sdk.Context, ek *evmkeeper.Keeper, etx *ethtypes.Transaction) {
	auths := etx.SetCodeAuthorizations()
	if len(auths) == 0 {
		return
	}
	associateHelper := helpers.NewAssociationHelper(ek, ek.BankKeeper(), ek.AccountKeeper())
	for _, auth := range auths {
		evmAddr, seiAddr, pubkey, ok := helpers.AuthorityToPreAssociate(ctx, ek, auth)
		if !ok {
			continue
		}
		cacheCtx, write := ctx.CacheContext()
		if err := associateHelper.AssociateAddresses(cacheCtx, seiAddr, evmAddr, pubkey, false); err == nil {
			write()
		}
	}
}

func AuthorityToPreAssociate(ctx sdk.Context, k AuthorizationStateReader, auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, bool) {
	// Chain ID must be null or match the local chain.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(k.ChainID(ctx)) != 0 {
		return common.Address{}, nil, nil, false
	}
	// Nonce must not overflow (EIP-2681).
	if auth.Nonce+1 < auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	evmAddr, seiAddr, pubkey, err := RecoverAddressesFromAuthorization(auth)
	if err != nil {
		return common.Address{}, nil, nil, false
	}
	// Cross-check against go-ethereum's authoritative recovery so we only ever act on the
	// exact address SetCode would target during execution.
	if authAddr, aerr := auth.Authority(); aerr != nil || authAddr != evmAddr {
		return common.Address{}, nil, nil, false
	}
	// Authority must have no code, or only an existing delegation designator.
	if code := k.GetCode(ctx, evmAddr); len(code) != 0 {
		if _, ok := ethtypes.ParseDelegation(code); !ok {
			return common.Address{}, nil, nil, false
		}
	}
	// Authority account nonce must match the authorization nonce.
	if k.GetNonce(ctx, evmAddr) != auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	// Already-associated authorities need no pre-association (and cannot be re-mapped).
	if _, associated := k.GetEVMAddress(ctx, seiAddr); associated {
		return common.Address{}, nil, nil, false
	}
	return evmAddr, seiAddr, pubkey, true
