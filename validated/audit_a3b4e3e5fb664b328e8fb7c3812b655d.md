## Analog Found

### Title
Security-review baseline silently advances past unreviewed edits when the Stop-hook fire limit is hit - ([File: plugins/security-guidance/hooks/security_reminder_hook.py])

### Summary
The `security-guidance` plugin tracks a git `baseline_sha` (captured on `UserPromptSubmit`) that the `Stop` hook diffs against to decide what code to LLM-review. This mirrors the Volt oracle's `startTime`/`oraclePrice` pair: `baseline_sha` is the "start of interval" marker, and the diff-based LLM review is the "compounding" step that must complete before the marker is allowed to move forward. Just like `requestCPIData` resetting `startTime` before `fulfill` had accumulated the true price delta, `handle_user_prompt_submit` (`security_reminder_hook.py` lines 446-515) advances `baseline_sha` on the next turn unless `touched_paths` is still non-empty on disk — but the `Stop` hook (`handle_stop_hook`, lines 1700-1839) unconditionally clears `touched_paths` via `consume_stop_state` (`diffstate.py` lines 74-113) as soon as it fires, before the review has actually completed.

### Finding Description
`consume_stop_state` snapshots `touched_paths`/`baseline_sha`/`previous_findings` and clears `touched_paths` on disk under a single lock, *before* any LLM review work happens [1](#0-0) . The design intentionally has a `restore_unreviewed_stop_state` escape hatch for cases where the review is skipped for a transient reason — e.g., `api.anthropic.com` unreachable calls `_skip(10, restore=True)` [2](#0-1) , and `restore_unreviewed_stop_state` re-arms the preservation guard by writing `touched_paths` and `baseline_sha` back [3](#0-2) .

However, the fire-limit skip path does not restore:
```
if MAX_STOP_HOOK_FIRINGS > 0 and fire_count >= MAX_STOP_HOOK_FIRINGS:
    debug_log(f"Stop hook: already fired {fire_count} times (max {MAX_STOP_HOOK_FIRINGS}), skipping")
    _skip(2)
``` [4](#0-3) 

`_skip(2)` calls `_skip(reason, restore=False, **extra)` by default [5](#0-4) , so it does **not** call `restore_unreviewed_stop_state`. `touched_paths` was already wiped from disk by `consume_stop_state` at the top of `handle_stop_hook`. On the very next `UserPromptSubmit`, `handle_user_prompt_submit`'s preservation guard checks `state.get("touched_paths") and state.get("baseline_sha")` — with `touched_paths` empty, this is `False`, so the guard does not fire and `baseline_sha` is unconditionally overwritten to the fresh stash SHA [6](#0-5) .

The net effect: any edits made during the turn(s) that exhausted `MAX_STOP_HOOK_FIRINGS` (default 3, comment describes an "asyncRewake loop (vuln→exit(2)→fix→Stop again)" [7](#0-6) ) are never diffed and never sent to the LLM security reviewer, and the baseline moves past them permanently — exactly the "resets before compounding/fulfillment completes" bug class from the report, applied to a security-control accumulator instead of a price accumulator.

### Impact Explanation
This is a hook-bypass of the code's only late-stage security control. The `Stop` hook is described in the plugin's own docs as "the only surface for uncommitted edits" (comment at line 1831) — i.e., it is the backstop that catches vulnerabilities pattern-rules missed. An agent (or a user, or a compromised subagent/prompt-injection payload) that keeps triggering `exit(2)`-forcing edit/fix cycles for 3+ Stop-hook firings in a single turn (a plausible, easily reachable pattern given the documented "vuln→exit(2)→fix→Stop again" loop) causes the final unresolved diff — potentially the actual vulnerable code — to be dropped from review with no `restore=True`, and the next turn's baseline capture then makes that code invisible to all future reviews for the rest of the session. This is a silent, permanent security-guidance bypass, not a crash or false-positive; it degrades the intended “Claude always gets its final diff LLM-reviewed” guarantee documented at the top of the file (lines 24-35).

### Likelihood Explanation
Reachable without any special privilege: it only requires normal Claude Code usage of the security-guidance plugin with the default `MAX_STOP_HOOK_FIRINGS=3` and an interaction pattern where the Stop hook fires findings 3 times in one turn (iterative fix loop) — a scenario the code's own comments say is expected/designed-for. No malicious server, no dependency bug, and no mocked-only path is required; it's a straightforward state-machine bug in first-party hook code that ships with the repo.

### Recommendation
Treat the fire-limit skip the same as the other "review didn't happen" skip paths: call `_skip(2, restore=True)` (or otherwise route through `restore_unreviewed_stop_state`) so `touched_paths`/`baseline_sha` are restored when `MAX_STOP_HOOK_FIRINGS` is hit, ensuring the next turn's `UserPromptSubmit` preserves the old baseline and the still-unreviewed diff is retried (or at minimum flagged) rather than silently absorbed into the new baseline. Add a regression test asserting that content written during a fire-limit-exhausted turn is still present in `review_paths`/diff on the following turn.

### Proof of Concept
1. Configure the security-guidance plugin with default settings (`MAX_STOP_HOOK_FIRINGS=3`).
2. In a single turn, have Claude/agent make an edit that trips a finding, get `exit(2)`, "fix" trivially (or not truly fix), repeat until `stop_hook_fire_count` reaches 3 within `STOP_LOOP_STATE_TTL_SEC` (120s) — the 4th `Stop` firing hits `_skip(2)` at line 1768, wiping `touched_paths` without restore.
3. Submit the next user prompt. `handle_user_prompt_submit`'s preservation guard sees empty `touched_paths` and overwrites `baseline_sha` to the fresh stash SHA (lines 493-497).
4. Any subsequent `Stop` hook now diffs from the new baseline forward; the vulnerable code from step 2 is permanently excluded from `compute_v2_review_set`'s `changed_since` set and is never reviewed again for the rest of the session.

(Note: I was unable to execute this end-to-end in a live Claude Code session — this analysis is based on static code review of the hook logic and its documented invariants; the `_skip(2)`/`restore=False` gap versus the explicit `restore=True` pattern used elsewhere in the same function is the concrete, verifiable root cause.)

def restore_unreviewed_stop_state(session_id, paths, baseline_sha):
    """Put consumed touched_paths back so the next Stop reviews them.

    consume_stop_state cleared touched_paths on disk; if Stop then exits
    early for a transient reason (CCR API unreachable, Haiku HTTP error)
    the next UPS would see an empty list, fall through the preservation
    guard, and re-baseline past the unreviewed edits. Restoring keeps the
    guard armed. Prepend+dedupe so any concurrent next-turn PostToolUse
    appends survive.
    """
    if not paths:
        return

    def _restore(state):
        existing = state.get("touched_paths", [])
        merged = list(dict.fromkeys(list(paths) + list(existing)))
        if len(merged) > 200:
            merged = merged[:200]
        state["touched_paths"] = merged
        if baseline_sha and not state.get("baseline_sha"):
            state["baseline_sha"] = baseline_sha
    with_locked_state(session_id, _restore)
```
