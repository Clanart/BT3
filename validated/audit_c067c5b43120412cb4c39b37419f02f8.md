This is the same class of bug as `isAmmPair`: a single narrow, unmanaged check (which value is treated as the "real" input amount for fee purposes) that a user can steer around to avoid paying the protocol fee that is supposed to apply on every asset movement through the gateway. ### Title
Protocol fee bypass via fee-on-transfer tokens in Tron `IntentGatewayV2.placeOrder` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron port of `IntentGatewayV2.placeOrder` computes both the protocol-fee deduction and the amount credited to escrow from the caller-supplied `order.inputs[i].amount`, instead of the amount actually received by the contract after `safeTransferFrom`. The mainline EVM `IntentGatewayV2.sol` explicitly guards against this by re-reading the token balance before/after the transfer and overwriting `order.inputs[i].amount` with the delta before fee calculation, precisely to prevent fee-on-transfer or deflationary tokens from letting users under-report (or manipulate) the amount subject to the protocol fee.

### Finding Description
In the canonical EVM `IntentGatewayV2.sol`, the non-predispatch escrow branch measures `balBefore`/after and sets `order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore` prior to computing `protocolFeeBps` and the escrowed `reducedInputs` amount: [4](#0-3) 

This ensures the protocol fee (and the resulting escrow/commitment) is always based on tokens the gateway actually custodies.

In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the equivalent branch performs `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then adds `reducedInputs[i].amount` (computed from the original, pre-transfer `order.inputs[i].amount`) directly into `_orders[commitment][token]`, with no balance-delta re-measurement: [5](#0-4) 

`reducedInputs`/`commitment` are likewise derived earlier straight from the nominal `order.inputs[i].amount` supplied by the caller: [2](#0-1) 

Since `_orders[commitment][token]` is credited with `reducedInputs[i].amount` — a value derived from the nominal amount, not the amount the contract actually received — this creates two divergent failure modes, analogous to the `isAmmPair` "unmanaged configuration" bug: the fee-relevant value (here, "amount transferred") is not kept consistent/complete across the code the way it is on the audited mainline branch. A fee-on-transfer token, or any token whose `transferFrom` delivers less than the nominal amount, causes escrow accounting to diverge from actual custodied balance without correction — the protocol fee is computed and dust/fee accounting is emitted against numbers that don't reflect the real transfer, and downstream escrow claims can be inflated relative to what the contract holds.

### Impact Explanation
This falls under "logic attacks" / accounting manipulation on custodied bridge funds — the same bug class as the referenced report ("users avoid fees due to unmanaged configuration checks"), but here manifesting as the gateway crediting escrow for tokens it never received, or basing protocol fee on the wrong figure, which can undercollect fees or leave insufficient token balance backing declared escrow (a fund-accounting integrity failure directly touching bridge custody).

### Likelihood Explanation
Requires only an unprivileged user placing an order with a fee-on-transfer/deflationary ERC-20 as input — no relayer, prover, or admin involvement, and no malformed proof is needed since this is a pure escrow-accounting bug in `placeOrder` itself. The mainline `IntentGatewayV2.sol` explicitly hardens exactly this scenario (see its "Reject duplicate input tokens" / fee-on-transfer tests such as `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`), confirming the project itself treats this as a live threat model that the Tron variant fails to replicate. [6](#0-5) 

### Recommendation
Mirror the mainline `IntentGatewayV2.sol` pattern in the Tron contract: measure the actual token balance delta on `address(this)` immediately after each `safeTransferFrom` and use that measured amount (not the caller-supplied `order.inputs[i].amount`) as the basis for protocol-fee computation, commitment hashing, and escrow crediting.

### Proof of Concept
1. Deploy `evm/tron/contracts/apps/IntentGatewayV2.sol` with a nonzero `protocolFeeBps`.
2. Attacker places an order using a fee-on-transfer token as input, specifying `order.inputs[0].amount = 1000e18`, while the token's `transferFrom` actually delivers only `950e18` to the gateway (5% transfer tax).
3. `placeOrder` computes `protocolFee` and `reducedInputs[0].amount` from the nominal `1000e18`, then calls `safeTransferFrom(msg.sender, address(this), 1000e18)` which only moves `950e18` in.
4. `_orders[commitment][token] += reducedInputs[i].amount` credits escrow based on the nominal (uncorrected) amount, so the pallet believes it custodies more tokens than it actually received — diverging from the actual on-chain token balance and corrupting the fee/escrow accounting for that commitment.

**Uncertainty note:** I could not fully verify at what deployment stage `evm/tron/contracts/apps/IntentGatewayV2.sol` is used in production (mainnet Tron vs. staging) — this affects whether the impact is "production bridge custody" or limited to a non-primary EVM-compatible chain deployment. Given index size limits, I was unable to pull the full file to confirm whether a balance-delta correction exists elsewhere in that file (e.g. in the `predispatch` branch, which does use `balance` checks) that might partially mitigate the non-predispatch path shown above. A Devin session with full repo access would be needed to confirm this is the only escrow-crediting code path and to check whether the Tron contract is actively deployed to a production bridge.
