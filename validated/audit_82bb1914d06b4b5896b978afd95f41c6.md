Based on the evidence gathered, I've identified a legitimate analog to the reported bug class — a broken attribution binding where the entity credited with funding a payout is not cryptographically bound to what was actually authorized.

### Title
Payout Attribution (OP_RETURN Operator Pubkey) Is Unsigned, Allowing Reimbursement Credit Hijacking - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` builds the `Payout` transaction with a `SinglePlusAnyoneCanPay` witness that covers only input #0 and the matching-index output (the user's payout output). The second output (anchor) and, critically, the third output — an `OP_RETURN` embedding the fronting operator's x-only pubkey — are **not covered by the user's signature**. The bridge later trusts this unsigned `OP_RETURN` field as the sole source of truth for "which operator fronted this withdrawal" when granting reimbursement eligibility, breaking the binding: `operator credited == operator that actually authorized/funded the payout`.

### Finding Description
`create_payout_txhandler` constructs the payout with `SpendPath::KeySpend` and `NormalSignatureKind::NotStored`, sets the witness with only the user's `taproot::Signature`, and the sighash type is enforced to `SinglePlusAnyoneCanPay` in `parse_withdrawal_sig_params`: [1](#0-0) 

`SinglePlusAnyoneCanPay` binds the signature to input #0 and only the output at the *same index* (index 0, the user's payout output). The anchor output (index 1) and the `OP_RETURN` output (index 2) embedding `operator_xonly_pk` are unsigned and can be freely substituted by anyone re-assembling the transaction: [2](#0-1) 

`Operator::withdraw` verifies the user's signature only against the sighash of input #0 (via `SECP.verify_schnorr`), never validating or committing to the `OP_RETURN` operator attribution output itself: [3](#0-2) 

Once such a payout transaction confirms on-chain, `update_finalized_payouts` (run by every verifier during Citrea/Bitcoin sync) extracts `operator_xonly_pk` purely by parsing the `OP_RETURN` bytes of whatever transaction happened to spend the tracked withdrawal UTXO — with no check that this pubkey corresponds to any signature, input, or actual funding party of that transaction: [4](#0-3) 

This value is persisted directly as `payout_payer_operator_xonly_pk`: [5](#0-4) 

...and is subsequently used as the sole authority to (a) let the named operator claim reimbursement via `PayoutCheckerTask`/`get_first_unhandled_payout_by_operator_xonly_pk`, and (b) validate a kickoff as non-malicious in `is_kickoff_malicious`, which simply compares this DB value to `kickoff_data.operator_xonly_pk`: [6](#0-5) [7](#0-6) 

Because a specific withdrawal UTXO can only ever be spent once on Bitcoin, whoever confirms first controls the `OP_RETURN` content and thus permanently controls the `payout_payer_operator_xonly_pk` attribution for that withdrawal — with no signature enforcing that the named operator is the one who broadcast/funded it.

### Impact Explanation
An unprivileged party who obtains the user's `SinglePlusAnyoneCanPay` payout signature (exchanged off-chain to operators, and trivially extractable once any operator's payout transaction is broadcast/relayed on the P2P network prior to confirmation) can reassemble and broadcast a competing transaction with the identical input/output-0 pair but an arbitrary `OP_RETURN` operator pubkey — either: (1) naming themselves/a colluding operator as the fronting party while contributing no independent capital, letting that operator later claim genuine bridge reimbursement it never funded, or (2) naming a victim honest operator (or an invalid/garbage key), permanently denying that operator any path to reimbursement for a withdrawal it may have actually intended to front, since the withdrawal UTXO is now spent and `payout_payer_operator_xonly_pk` is fixed to the attacker's chosen value. This matches the Critical-severity classes "an operator reimbursed for a payout it never funded" and "an honest operator permanently unable to be reimbursed."

### Likelihood Explanation
The exploit requires no privileged role (no verifier/operator/aggregator/security-council key) — only visibility of a broadcast/mempool transaction's witness data or of the off-chain-shared user signature, and the ability to submit a replacing/competing raw transaction (a standard RBF race), both of which are attacker capabilities inherent to any public Bitcoin mempool. The `OP_RETURN` output is explicitly never signed by any party in the current design.

### Recommendation
Bind the `operator_xonly_pk` (and any other reimbursement-attribution data) to the same signature that authorizes the payout, e.g., by using `TapSighashType::All`/`SinglePlusAnyoneCanPay` semantics that also commit to the `OP_RETURN` output, or by having the operator co-sign/commit to the full transaction (all outputs) rather than relying on unauthenticated data extracted post-hoc from confirmed transactions.

### Proof of Concept
1. Operator A obtains a valid user payout signature `user_sig` (SinglePlusAnyoneCanPay) for withdrawal UTXO `U` and output `O` and broadcasts (or it is otherwise observable in the mempool) a payout tx: `input=U (sig=user_sig)`, `output[0]=O`, `output[1]=anchor`, `output[2]=OP_RETURN(A_pubkey)`.
2. Before this transaction confirms, attacker crafts `tx'`: same `input=U (sig=user_sig)`, same `output[0]=O` (so the SIGHASH_SINGLE|ANYONECANPAY commitment is satisfied and the witness remains valid), but replaces `output[2]` with `OP_RETURN(Attacker_or_Victim_pubkey)`, and pays a higher fee to win the RBF/mempool race.
3. `tx'` confirms instead of Operator A's transaction.
4. During Bitcoin sync, `update_finalized_payouts` parses `tx'`'s `OP_RETURN` and sets `payout_payer_operator_xonly_pk = Attacker_or_Victim_pubkey` in the `withdrawals` table via `update_payout_txs_and_payer_operator_xonly_pk`.
5. `PayoutCheckerTask` for the attacker-named operator now finds this as an unhandled payout via `get_first_unhandled_payout_by_operator_xonly_pk` and proceeds to grant it a kickoff/reimbursement path — despite that operator having contributed nothing to `tx'` — while Operator A, who actually intended to front the withdrawal, has no recorded credit and cannot be reimbursed.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
