### Title
PedPoP blame adjudication blames a caller-chosen `recipient` without verifying they are the accuser, enabling arbitrary participants to be declared faulty - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
Analogous to CVE-2025-28409 (an `add` endpoint failing to validate the caller's rights over a caller-supplied `parentId`), PedPoP's blame path (`BlameMachine::blame`, `AdditionalBlameMachine::blame`, `Decryption::decrypt_with_proof`) accepts a caller-supplied `recipient` participant index and returns that `recipient` as the faulty party whenever the supplied `EncryptionKeyProof` is missing or fails verification — without ever checking that `recipient` is actually the party making the accusation, that `recipient` was the intended decryptor of `msg`, or that `recipient` even holds an encryption key for the sender. Any unprivileged party who obtains any well-formed `EncryptedMessage` (its PoP only needs to verify against the message's claimed `from`) can cause an arbitrary honest participant to be blamed, which in Serai's usage aborts the DKG and marks the blamed party for slashing.

### Finding Description
`blame_internal` at crypto/dkg/pedpop/src/lib.rs:575-609 resolves faults as:

- `msg.pop.verify(msg.key, pop_challenge::<C>(context, msg.pop.R, msg.key, from, msg.msg...))` failing → returns `sender`.
- Otherwise, if `proof` is `None` or its DLEq fails → returns `recipient` (crypto/dkg/pedpop/src/encryption.rs:374-396 and lib.rs:582-588).

Two gaps make this exploitable:

1. **`recipient` is trusted, not authenticated.** `blame(sender, recipient, msg, proof)` has no `accuser` parameter and no check that `recipient` is the caller or the true recipient. `pop_challenge` binds `context`, `R`, `key`, `from` (sender), and the ciphertext — but never a recipient identity (encryption.rs:376). So the PoP proves "someone who knows `key` made this message," not "this message was intended for `recipient`."

2. **A missing proof blames `recipient`, not the accuser.** In `decrypt_with_proof`, `proof: None` maps to `Err(DecryptionError::InvalidProof)` (encryption.rs:394-396), which `blame_internal` maps to `return recipient` (lib.rs:586-588). The only use of `recipient` before that verdict is `self.enc_keys[&decryptor]` inside the DLEq verify — which is skipped entirely when `proof` is `None`.

So `AdditionalBlameMachine::new(context, n, commitment_msgs)` — explicitly usable by a non-participant (lib.rs:639-649) — plus `blame(any_sender, victim, any_msg_with_valid_pop, None)` deterministically returns `victim` as faulty.

### Impact Explanation
`blame` exists to "prevent completion of the machine, forcing an abort of the protocol" (lib.rs:611-613), and downstream code (processor/src/key_gen.rs:504-563, `CoordinatorMessage::VerifyBlame`) converts the blamed participant into `ProcessorMessage::Blame`, which slashes/removes that validator. A Byzantine party — or any observer with the published commitment messages and one intercepted/copyable `EncryptedMessage` — can:

- Name an honest validator as `recipient` and get them declared faulty with a withheld or junk proof, forcing abort and punishing a non-faulty party (the exact "request validated against a user-controlled identifier rather than the caller's authority" shape of the RuoYi bug).
- Re-run the same blame repeatedly via `AdditionalBlameMachine` (which by design processes the same statement multiple times), amplifying false blames across participants.

The accuser who supplied the bogus `recipient`/`proof` is never themselves at fault under this code path — blame lands wholly on the unauthenticated `recipient` parameter.

### Likelihood Explanation
Reachable entirely with public inputs: `AdditionalBlameMachine::new` is a public constructor requiring only `context`, `n`, and the commitment messages (which are broadcast/transcripted in the DKG); `msg` can be any `EncryptedMessage` whose PoP verifies under its claimed `from` (e.g., a real share message observed on the wire, or one the attacker generated with their own per-message key via `encrypt`); `proof` can simply be `None` or unparsable bytes (key_gen.rs:538-541 already tolerates `EncryptionKeyProof::read` failure to `None`). No collusion, no leaked keys, no malicious infra required. The only prerequisite is a pending blame/verification flow — which Serai exposes via `VerifyBlame` — making this a practical, deterministic misblame rather than a probabilistic one. Rated High-relevant (integrity of blame attribution; availability of the DKG; potential wrongful slashing).

### Recommendation
- Bind the intended recipient into the per-message proof-of-possession: extend `pop_challenge` in crypto/dkg/pedpop/src/encryption.rs to include the `to`/`decryptor` participant index (and verify against `enc_keys[recipient]` even when no proof is supplied).
- In `blame`/`blame_internal` (crypto/dkg/pedpop/src/lib.rs:575-632), treat `recipient` as the accuser: require the caller to prove they are `recipient` (e.g., require a valid `EncryptionKeyProof` for the `msg`→`recipient` ECDH before `recipient` can be blamed; when `proof` is `None` and the PoP is valid, blame the accuser or reject rather than the recipient).
- In `Decryption::decrypt_with_proof`, when `proof` is absent or invalid after a valid PoP, return a distinct error meaning "accusation unsubstantiated" rather than a verdict against `recipient`, and have callers map that to the accuser.

### Proof of Concept
```rust
// crypto/dkg/pedpop context, Ristretto, n = PARTICIPANTS.
// Setup: honest participant ONE generated shares; VICTIM = TWO is an honest
// recipient. Attacker is any party (even a non-participant) holding the
// public commitment messages.

// 1) Obtain any well-formed EncryptedMessage whose PoP verifies under `from`.
//    This can be a real share message ONE sent to anyone, observed or relayed:
let msg: EncryptedMessage<Ristretto, SecretShare<Fr>> = shares[&ONE][&SOMEONE].clone();

// 2) Build a blame machine purely from the public commitment messages:
let machine =
  AdditionalBlameMachine::<Ristretto>::new(CONTEXT, PARTICIPANTS, commitment_msgs).unwrap();

// 3) Blame VICTIM by naming them as `recipient` and withholding the proof.
//    - pop.verify(...) succeeds (msg genuinely came from ONE).
//    - proof == None => DecryptionError::InvalidProof.
//    - blame_internal returns `recipient` == VICTIM.
let blamed = machine.blame(ONE, VICTIM, msg, None);

assert_eq!(blamed, VICTIM); // an innocent participant is declared faulty;
                            // DKG aborts / downstream slashing targets VICTIM,
                            // while the accuser is never penalized.
```

Root cause is exact: crypto/dkg/pedpop/src/lib.rs:582-588 maps `DecryptionError::InvalidProof` to `recipient`, and crypto/dkg/pedpop/src/encryption.rs:381-396 produces `InvalidProof` for a missing/failed proof without binding `recipient` to the message or the accuser.
