### Title
Heap-out-of-bounds read via attacker-controlled DDS mip-map offset/length in `convertDDSImage` - (File: `app/src/ui/diff/image-diffs/dds-converter.ts`)

### Summary
The external report describes a classic "trust length/offset fields embedded in file metadata without validating them against the actual buffer size" bug in `exif_iif_add_value`. The closest reachable analog in GitHub Desktop is `convertDDSImage`, which parses a `.dds` texture file taken directly from a cloned/fetched repository (or the working directory) and uses attacker-influenced offset/length fields from the parsed header to slice into the raw file buffer before handing that slice to WebGL.

### Finding Description
When a diff involves a `.dds` file, Desktop reads the raw bytes of the blob/working-directory file and wraps them in an `Image` model carrying `rawContents: ArrayBufferLike` [1](#0-0) . These bytes come straight from `getBlobContents`/`readFile` on attacker-controlled repository content [2](#0-1) .

`ImageContainer.loadImage` forwards `image.rawContents` unmodified to `convertDDSImage` whenever `mediaType === 'image/vnd-ms.dds'` [3](#0-2) .

`convertDDSImage` calls the third-party `parse-dds` parser on the raw, untrusted bytes and then trusts the `offset`/`length` fields it returns to build a view directly over the original `ArrayBuffer`:

```
export function convertDDSImage(contents: ArrayBufferLike) {
  const ddsData = parseDDS(contents)
  const [image] = ddsData.images
  const [imageWidth, imageHeight] = image.shape
  const imageData = new Uint8Array(contents, image.offset, image.length)
  ...
``` [4](#0-3) 

`image.offset`, `image.length`, `imageWidth`, and `imageHeight` are all derived from header fields inside the attacker-supplied DDS file (mip-map count, pitch/linear-size, width/height, pixel-format), the same class of "attacker-controlled length field drives a buffer slice" primitive as the EXIF IFD entry count/offset in the original report. There is no check anywhere in `convertDDSImage` or its caller that `image.offset + image.length` is consistent with `contents.byteLength`, nor that `imageWidth`/`imageHeight` match the number of bytes actually sliced. The resulting `Uint8Array` is then fed straight into `gl.compressedTexImage2D` as compressed texture data [5](#0-4) , which uploads it to the GPU driver for decompression based on the declared `width`/`height`/`format`, not on `imageData.length`. A crafted mip-map header (e.g., declaring a `width`/`height` that requires more compressed bytes than `image.length` actually contains, or declaring an `offset` near the end of a short file) causes the GPU driver's DXT decompressor to read past the end of the uploaded buffer — the same "read length computed from crafted header, not validated against actual data size" defect as `exif_iif_add_value`, just moved from libexif's C heap into the WebGL/GPU-driver texture-upload path.

### Why existing guards don't stop the path
- `Uint8Array(contents, image.offset, image.length)` only guards against slicing past the *JS* `ArrayBuffer` boundary (it throws `RangeError` if `offset+length > contents.byteLength`); it performs no validation that `image.length` is sufficient/consistent for the declared `imageWidth`/`imageHeight`/DXT block format. A header that declares a small `width`/`height` but a large corresponding `length` (or vice versa) sails through this check.
- The only wrapper is a generic `try { … } catch` in `ImageContainer.loadImage` that catches JS-level exceptions and falls back to no image [3](#0-2) ; it cannot catch or prevent OOB reads that occur inside the native WebGL/GPU driver during `compressedTexImage2D`.
- `enableImagePreviewsForDDSFiles()` gates the feature behind beta/dev channels today [6](#0-5) , but the code path itself has no additional bounds validation independent of that flag, so once the feature ships to stable it is fully reachable by simply viewing a diff for a `.dds` file in any cloned/fetched repository.

### Impact Explanation
An attacker who controls the contents of a repository the victim clones/fetches (or a `.dds` file the victim adds/receives in a PR) can craft a `.dds` file whose header lies about its own dimensions/mip-map extents. When the victim opens the file's diff in Desktop, the app slices and uploads attacker-controlled byte ranges to the GPU based on unvalidated header fields, causing the native GPU driver's texture decompressor to read outside the bounds of the intended buffer. Depending on the GPU driver, this can lead to information disclosure (leaked adjacent heap/GPU memory rendered into the canvas/PNG data URL, which the app then re-serializes and could be exfiltrated) or a renderer/GPU-process crash — squarely in the "attacker-controls a cloned/fetched repository → out-of-bounds read" impact class named in the task.

### Likelihood Explanation
Moderate. Exploitation requires: (1) the DDS preview feature being enabled (currently beta/dev-gated), (2) the victim opening a diff view for the malicious `.dds` file — an entirely normal, expected Desktop workflow (no unusual user steps), and (3) a GPU driver that doesn't itself bound-check compressed texture uploads (historically a real class of driver bugs). No local access, admin rights, or social engineering beyond "clone a repo and view a file diff" is needed.

### Recommendation
- Validate `image.offset`/`image.length` against both `contents.byteLength` and the block-size formula for the declared DXT format/`width`/`height` before constructing the `Uint8Array`, rejecting/erroring out on any mismatch.
- Reject unreasonable `width`/`height`/mip-map counts before calling `gl.compressedTexImage2D`.
- Keep the DDS preview behind the feature flag until such validation exists, and consider sandboxing/limiting the WebGL2 context used for untrusted texture decoding.

### Proof of Concept
1. Build a minimal `.dds` file with a valid magic/header but a manipulated pixel-format/mip-map descriptor so that `parse-dds` computes an `image.length` smaller than what the declared `imageWidth`/`imageHeight`/DXT format actually require (e.g., truncate the pixel payload while keeping `width`/`height` large).
2. Commit this file with a `.dds` extension to a repository and have the victim clone/fetch it (or open a PR containing it).
3. In GitHub Desktop (with `enableImagePreviewsForDDSFiles` active), select the commit/working-directory change for the file so the diff view renders it as an image, triggering `ImageContainer.loadImage` → `convertDDSImage` → `gl.compressedTexImage2D` with the under-sized/mismatched buffer [4](#0-3) .
4. Observe GPU-driver level out-of-bounds read/crash (or leaked memory pixels) is the expected outcome, depending on driver behavior, since no JS-level guard validates the offset/length against the declared image dimensions.

function drawToCanvas(
  canvas: HTMLCanvasElement,
  format: string,
  width: number,
  height: number,
  imageData: ArrayBufferView
) {
  canvas.width = width
  canvas.height = height
  const gl = canvas.getContext('webgl2', { preserveDrawingBuffer: true })
  if (!gl) {
    throw new Error('Failed to get webgl2 context')
  }

  gl.bindTexture(gl.TEXTURE_2D, gl.createTexture())
  gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_MAG_FILTER, gl.LINEAR)
  gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_MIN_FILTER, gl.LINEAR)
  const ext = gl.getExtension('WEBGL_compressed_texture_s3tc')
  if (!ext) {
    throw new Error('Failed to get WEBGL_compressed_texture_s3tc extension')
  }

  const internalFormat = getFormat(ext, format)
  gl.compressedTexImage2D(
    gl.TEXTURE_2D,
    0,
    internalFormat,
    width,
    height,
    0,
    imageData
  )

  const program = compileProgram(gl, vert, frag)
  gl.useProgram(program)

  gl.viewport(0, 0, width, height)
  triangle(gl)
}
