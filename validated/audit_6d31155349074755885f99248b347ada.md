### Title
Silent, unconfirmed rewrite of local git `origin` remote based on trusted GitHub API `clone_url` field - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts` automatically executes `git remote set-url` against the user's `origin` remote whenever a background refresh of a repository's metadata from the GitHub API reports a different `clone_url` for the same tracked `GitHubRepository` record. This mirrors the "manager can quietly change a security-relevant config value" pattern from the OtterSec report: an object under a third party's control (here, the GitHub-side repository record, mutable via rename/ownership transfer by anyone with admin rights on that repo) is trusted to silently overwrite a value (the local remote URL) that governs where the user's future pushes/fetches go, with no user confirmation step.

### Finding Description
`updateRemoteUrl` is invoked with the cached `GitHubRepository` (containing the previously observed `cloneURL`) and a freshly fetched `IAPIRepository` (`apiRepo`) from the GitHub API: [1](#0-0) 

The function decides to rewrite the remote if:
1. The URL protocol (https/ssh) is unchanged, and
2. The current local remote URL still matches the *previously cached* `gitHubRepository.cloneURL` (i.e., the user hasn't manually diverged from what Desktop last knew), and
3. The new `apiRepo.clone_url` does **not** match the current local remote. [2](#0-1) 

If all three hold, it calls `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)`, which shells out to `git remote set-url origin <url>` with no user-facing confirmation, diff, or warning dialog: [3](#0-2) 

The matching logic (`urlMatchesRemote`/`repositoryMatchesRemote`) only compares hostname/owner/repo-name tuples parsed from the URL strings — it has no notion of "is this still the same underlying repository object" beyond string equality, and it has no way to detect that the *identity* behind `owner/name` changed hands: [4](#0-3) 

Because the trigger condition is simply "the API's `clone_url` for this tracked repo differs from what the local remote currently points to", any change that alters the API-reported `clone_url` for a repo the victim already has cloned (e.g., the repo being renamed or transferred to a different owner by whoever controls it) causes Desktop to silently repoint the user's `origin` to the new location the next time repository metadata is refreshed — without the user reviewing or approving the change. Unit tests confirm this "happy path" auto-rewrite is intentional current behavior when the old cached URL still matches and protocols agree: [5](#0-4) 

This is directly analogous to the report's broken invariant: a value the user's operation depends on (in Solvent, `cooldown_period_sec`; here, `origin`'s URL) is mutated by an external, less-trusted party (the farm manager; here, whoever administers/owns the GitHub repository) between the time the user set up their expectation and the time the client acts on it, and the client has no guard checking that the value is still what the user originally consented to.

### Impact Explanation
If a repository is renamed or transferred by its owner/maintainer (an "unprivileged" party relative to the victim's machine — they only need control of the GitHub repository object, not the victim's device), Desktop will, on its own background refresh cycle, rewrite the victim's `origin` remote to the new location without any user prompt. Subsequent `git push`/`git fetch`/`git pull` operations then silently target wherever the API now says `clone_url` points, which is exactly the "silent corruption of what the user commits or pushes" impact category: the user believes they are pushing to the repository they originally added, but Desktop has redirected `origin` based on an externally-controlled API field.

### Likelihood Explanation
This does not require local access, admin rights, prior malware, leaked credentials, or unnatural user steps — it only requires that the repository the victim has open in Desktop undergo a legitimate-looking rename/transfer server-side, which any repo owner/org admin can trigger unilaterally at any time while the victim's Desktop client is periodically refreshing repository state in the background. The refresh path and the silent `set-url` call are both existing, reachable, non-test code paths, and the accompanying unit test explicitly validates the auto-update branch as intended behavior, indicating no additional confirmation gate exists.

### Recommendation
Do not perform `git remote set-url` automatically based solely on the GitHub API's `clone_url` field changing. At minimum:
- Surface a confirmation prompt/dialog to the user before rewriting `origin`, showing old vs. new URL.
- Bind the "is this still the same repo" check to a stable identifier (e.g., the repository's numeric `id`) rather than relying purely on owner/name string matching, so renames can be validated against the same underlying `id`, but any change should still require explicit user acknowledgment before being applied to the working copy's git configuration.

### Proof of Concept
1. Victim clones and adds `https://github.com/alice/foo` in GitHub Desktop; Desktop caches `gitHubRepository.cloneURL = https://github.com/alice/foo`.
2. Alice (owner of `foo`, not an attacker with any access to the victim's machine) renames the repository or transfers it to `https://github.com/alice/bar` (or to a different owner entirely) — a normal GitHub feature available to any repo admin.
3. On Desktop's next background metadata refresh, the GitHub API returns the repository object with `clone_url: https://github.com/alice/bar`.
4. `updateRemoteUrl` sees: protocols match, the local remote still equals the previously cached `cloneURL` (`.../alice/foo`), and the new API `clone_url` (`.../alice/bar`) doesn't match the local remote — condition satisfied.
5. Desktop silently executes `git remote set-url origin https://github.com/alice/bar` with no dialog shown to the user.
6. The victim's next `git push`/`fetch` now targets `alice/bar` instead of the repository they originally set up, without any explicit consent, demonstrating silent corruption of the push/fetch destination. [6](#0-5)

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
