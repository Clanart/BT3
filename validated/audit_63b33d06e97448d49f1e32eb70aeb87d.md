### Title
Attacker-controlled `n` in `ThresholdKeys::read` causes up-front heap allocation before any data is validated — (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes a `u16` participant count `n` supplied entirely by the caller and immediately calls `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient vector, then loops `1 ..= n` deserializing group elements into a `HashMap`. The capacity reservation happens before a single byte of the claimed data is verified to exist, mirroring CVE-2023-32247's class: resource consumption driven by an attacker-supplied length field with no independent bound.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` reads `t`, `n`, and `i` from the untrusted stream: [1](#0-0) 

For `interpolation == 0` it preallocates a vector sized by the raw attacker value `n`: [2](#0-1) 

and then reads `n` group elements into a `HashMap`: [3](#0-2) 

`n` is attacker-controlled up to `u16::MAX` (65535). With `Interpolation::Constant`, `Vec::with_capacity(65535)` reserves roughly 2 MiB of heap (~32-byte field element each) immediately, even if the stream contains only the ~15 bytes of header. Only afterward does `ThresholdParams::new(t, n, i)` reject `i == 0`, `t > n`, or `i > n` — i.e., the allocation precedes all semantic validation in `ThresholdKeys::new`: [4](#0-3) 

`ThresholdKeys::read` is explicitly part of the untrusted-input surface (keys/deserialization feeds from peers during DKG/signing setup). No size check, no chunked read, and no bound exists on `n` beyond the `u16` type. Compare with the codebase's own awareness of this class elsewhere — `Call::read` in `networks/ethereum/src/machine.rs` (out of scope) explicitly reads length-prefixed data in 1 KB chunks with the comment "A valid DoS would be to claim a 4 GB data is present for only 4 bytes", and the `coordinator/src/p2p.rs` codec enforces `MAX_LIBP2P_REQRES_MESSAGE_SIZE`. `ThresholdKeys::read` has neither mitigation.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (e.g., via a serialized `ThresholdKeys` blob in a DKG/multisig setup flow) forces a ~2 MiB heap reservation per call from a handful of input bytes — an amplification factor of roughly 10^5. Issued concurrently, this produces rapid memory exhaustion (OOM kill of the process), a denial of service. There is additionally a secondary CPU cost: `ThresholdKeys::new` at `crypto/dkg/src/lib.rs:376-378` interpolates over participants `1..=t` summing verification shares, so a crafted payload declaring large `t = n` with fully-supplied shares imposes O(n) scalar multiplications before any additional validation.

Impact is bounded per-call by the `u16` width (~2 MiB transient for `Constant`, plus the `HashMap` growth which is gated by actually-present point data), so this is a Medium-severity availability analog rather than an unbounded 4 GiB single-shot allocation.

### Likelihood Explanation
Reachability requires only that untrusted bytes reach `ThresholdKeys::read` — a listed API in the threat model (serialized keys exchanged between multisig participants). The malicious input is trivially constructed: `id_len || C::ID || t || n = 0xFFFF || i = 1 || interpolation byte 0x00`, ~15 bytes total. No authentication, valid share, or collusion is needed; deserialization itself performs the allocation before rejecting anything. The only mitigating factor is the `u16` cap, which keeps the per-request reservation modest and requires request volume for OOM.

### Recommendation
- In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs`), validate `t <= n`, `i` in range, and `n <= MAX_PARTICIPANTS` (a sane constant such as 1024) *before* any allocation keyed on `n`.
- Replace `Vec::with_capacity(n)` with incremental `push` (capacity grows only as real bytes are consumed), or read the stream chunked as `Call::read` does.
- Apply the same ordering fix to the `verification_shares` loop so declared counts cannot outpace actual stream contents.

### Proof of Concept
```rust
use std::io;
use dkg::{ThresholdKeys, Participant};
// Any in-scope Ciphersuite, e.g. frost::curve::Ed25519
use frost::curve::Ed25519 as C;

fn main() {
    let mut buf: Vec<u8> = Vec::new();
    let id = <C as frost::curve::Curve>::ID;
    buf.extend((id.len() as u32).to_le_bytes());
    buf.extend(id.as_bytes());                 // curve ID must match
    buf.extend(1u16.to_le_bytes());            // t = 1
    buf.extend(u16::MAX.to_le_bytes());        // n = 65535  <-- attacker-controlled
    buf.extend(1u16.to_le_bytes());            // i = 1 (valid)
    buf.push(0u8);                             // Interpolation::Constant
    // NO coefficient data follows.

    // ~15 input bytes -> Vec::with_capacity(65535) reserves ~2 MiB of
    // C::F heap space inside Interpolation::Constant before the first
    // read_F fails. Repeating this concurrently exhausts memory.
    let _ = ThresholdKeys::<C>::read(&mut buf.as_slice());
}
```
