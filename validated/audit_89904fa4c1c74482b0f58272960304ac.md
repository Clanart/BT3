## Title
Working-directory diff re-fetched at commit time lets an externally-modified file silently corrupt a partial commit's content - (`File: app/src/lib/git/apply.ts`)

### Summary
`TricryptoLPStrategy.compound` trusts a "before/after" delta (`crvBalanceAfter - crvBalanceBefore`) that assumes nothing else can mutate the tracked value between the two reads; an attacker who front-runs the second read (via `claim_rewards`) breaks that assumption and silently drops the yield. GitHub Desktop has a structurally identical pattern in its partial-commit pipeline: the user's line selection is computed against one snapshot of a file's diff, but the patch that is actually applied to the index is built from a *freshly re-fetched* diff taken at commit time. If the file on disk changes between those two points, the line-index-based selection is silently replayed against different content.

### Finding Description
When a user stages only some lines/hunks of a file, the UI stores a `DiffSelection` keyed by absolute line indices from the diff that was rendered when the user made the selection (see `updateChangesWorkingDirectoryDiff` in `app/src/lib/stores/app-store.ts:3404-3513`, which produces `selectableLines` from a `diff` object and attaches it to the `WorkingDirectoryFileChange`).

When the commit actually happens, `_commitIncludedChanges` (`app/src/lib/stores/app-store.ts:3680-3711`) passes the `WorkingDirectoryFileChange` objects (carrying that same `selection`) straight into `createCommit` → `stageFiles` (`app/src/lib/git/update-index.ts:109-169`) → `applyPatchToIndex` (`app/src/lib/git/apply.ts:12-84`).

Critically, `applyPatchToIndex` does **not** reuse the diff the user reviewed. It calls `getWorkingDirectoryDiff(repository, file)` again at line 60, generating a brand-new diff of the current on-disk file, and then calls `formatPatch(file, diff)` (line 80) using the *old* selection object against this *new* diff. `formatPatch` (`app/src/lib/patch-formatter.ts:129-232`) walks the new diff's hunks and lines and decides whether to include each line purely by checking `file.selection.isSelected(absoluteIndex)` (line 157) — i.e., by numeric line-offset, with no validation that the new diff's line at that offset is the same line the user actually selected.

This mirrors the Curve bug exactly: a value computed from an assumed-stable state (`crvBalanceBefore`, or here, the diff/line-offsets at selection time) is compared/reused against a second, independently-obtained read (`crvBalanceAfter`, or here, the freshly fetched `getWorkingDirectoryDiff` at apply time) without re-validating that nothing changed in between. Where the Curve guard `crvAmount = after - before` breaks silently to zero, here the guard is simply absent — `formatPatch` has no equivalent "still consistent" check at all before applying the stale selection to new content.

### Impact Explanation
If a file is modified on disk (e.g., by a build tool, a `post-checkout`/file-watcher script from a cloned repository, an editor auto-format action, or any other process running concurrently with Desktop) after the user reviews a diff and selects specific lines, but before the commit button's async chain reaches `applyPatchToIndex`, the line offsets in `DiffSelection` may now refer to different content in the newly-fetched diff. The resulting patch applied to the index — and therefore the actual committed/pushed content — can silently diverge from what the user visually reviewed and approved in the Changes view. This is exactly the "silent corruption of what the user commits or pushes" impact category: no error is shown, and the user has no indication that the bytes they are about to push differ from the diff they inspected.

### Likelihood Explanation
Desktop already has a guard for the analogous "diff selection" read in the *UI* path (`updateChangesWorkingDirectoryDiff` explicitly recomputes `selectableLines` and discards no-longer-valid selections when the diff changes while loading), showing the team is aware this race exists. However, that safety net only runs when refreshing the UI's displayed diff — it is not re-applied at the moment `applyPatchToIndex` fetches its own independent diff just before invoking `git apply --cached`. Any legitimate, common workflow (auto-save extensions, linters/formatters running on save, build watchers, files changing due to a symlink/submodule update) that touches the selected file between selection and the commit's git call is sufficient to trigger the divergence — no privileged access or social engineering is required.

### Recommendation
- In `applyPatchToIndex` (`app/src/lib/git/apply.ts`), do not perform a second, independent `getWorkingDirectoryDiff` call detached from the diff/selection the user acted on. Either pass the already-loaded diff through from the caller, or re-validate (e.g., via file mtime/hash or the same `selectableLines` reconciliation logic used in `updateChangesWorkingDirectoryDiff`) that the freshly fetched diff is unchanged before reusing the old `DiffSelection` offsets.
- If the file has changed since the selection was made, abort the partial-commit for that file and surface an error/refresh to the user rather than silently applying a stale, offset-based selection to new content.

### Proof of Concept
1. Modify a tracked file so it has multiple hunks; open it in Desktop's Changes view and partially select only some lines (creating a `DiffSelection` keyed to specific absolute line offsets from the currently displayed diff).
2. Before clicking "Commit", have an external process (editor auto-format, build/watch script, `post-checkout` hook, etc.) append/remove lines earlier in the file so hunk offsets shift, without the user re-opening/re-reviewing the diff.
3. Click "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` runs `getWorkingDirectoryDiff` fresh (`app/src/lib/git/apply.ts:60`) and calls `formatPatch(file, diff)` using the stale `file.selection` against the new hunk layout (`app/src/lib/patch-formatter.ts:157`).

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
}
