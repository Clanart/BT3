### Title
Stale line-index diff selection can silently commit/push different content than reviewed - (File: `app/src/lib/git/apply.ts`)

### Summary
The perpetuals bug is a classic TOCTOU: a request is validated/created against one state, then executed later against a possibly-different state, letting the actor benefit from the drift. GitHub Desktop's partial-commit ("stage selected lines") feature has the same broken invariant: the user's line selection (`DiffSelection`) is captured as bare integer offsets against a diff snapshot shown at review time, but the actual patch used to stage/commit is generated from a **freshly re-fetched diff** at commit time, with only partial reconciliation of the stale indices.

### Finding Description
`DiffSelection` records selected/deselected lines purely as `Set<number>` offsets (`divergingLines`) with no reference to the text or hash of the line content that was selected — see `isSelected()` in `app/src/models/diff/diff-selection.ts:122-136`. When the user views a file's diff in the Changes pane, `updateChangesWorkingDirectoryDiff` re-fetches the diff and attempts to keep the selection valid, but it only recomputes `selectableLines` (which offsets are still add/delete lines) and drops indices no longer selectable — it does **not** verify that a still-selectable index still refers to the same line content [1](#0-0) .

Then, when the user clicks Commit, `_commitIncludedChanges` passes the (possibly stale) `WorkingDirectoryFileChange` objects — carrying their `selection` — straight into `createCommit` → `stageFiles` [2](#0-1) . For partially-selected files, `applyPatchToIndex` calls `getWorkingDirectoryDiff(repository, file)` **again, independently**, producing a brand-new diff object that may not be the one the reconciliation logic (or the user) last saw, and then blindly applies `file.selection` line indices to it via `formatPatch` [3](#0-2) [4](#0-3) .

There is no check anywhere in this path that the diff used to build the commit patch is the same diff (by hash/content) that the selection indices were derived from. If the working-tree file content shifts between the time the user reviews a diff and selects lines and the moment `createCommit` actually runs (e.g. due to background `git status`/diff polling triggering another `updateChangesWorkingDirectoryDiff` refresh, a slow commit click, or content rewritten by tooling that operates on the checked-out tree such as an editor auto-format/auto-save, a repo-provided build/watch script, or line-ending/`clean` filter reprocessing), the same numeric line indices can now correspond to entirely different lines. `formatPatch` will then happily stage whatever text sits at those offsets in the new diff, without the user ever reviewing it.

### Impact Explanation
This can result in **silent corruption of what the user commits and pushes** — a line the user explicitly excluded (e.g., a secret, debug code, or an unrelated unrelated change) can be included, or a line they intended to include can be silently dropped/swapped for different content, because the patch construction trusts stale positional state instead of the actual reviewed content. This matches the explicitly valid impact category "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Exploitability depends on the working tree changing between diff-review and commit-time patch generation. This is most plausible in a cloned/attacker-influenced repository combined with normal Desktop behavior (periodic file-watcher-driven status/diff refreshes already exist in the codebase, shown by the reconciliation logic that anticipates the diff "might have changed dramatically" between loads — see comment at `app/src/lib/stores/app-store.ts:3480-3485`). However, I was not able to fully verify, given the available indexed code, whether Desktop's background refresh cadence realistically creates a window between the last diff shown/reconciled to the user and the diff re-fetched inside `applyPatchToIndex` during an actual commit, or whether some other guard (not surfaced by search) prevents this. This nuance should be validated with the full source before treating this as a confirmed, exploitable bug.

### Recommendation
Bind `DiffSelection` (or the commit flow) to a content fingerprint of the diff/file it was derived from (e.g., hash of the working-tree blob or of the diff text) and refuse/re-validate the selection if that fingerprint doesn't match the diff fetched at `applyPatchToIndex` time, mirroring the report's own recommendation to track "the slot" (here, a content version) at request time and check it at execution time.

### Proof of Concept
Conceptual (could not be executed in this environment):
1. Open a repository in Desktop; modify a tracked file with two independent hunks.
2. In the Changes view, view the diff and deselect hunk B (keep only hunk A selected) — `DiffSelection.divergingLines` now stores raw indices for hunk B.
3. Before clicking Commit, cause the working file to change in a way that shifts line offsets but keeps the file "selectable" set structurally similar (e.g., an external process/editor reformats or a background poll re-diffs after further edits), so `updateChangesWorkingDirectoryDiff`'s reconciliation preserves the stale indices as still "selectable" but pointing at different content.
4. Click Commit. `applyPatchToIndex` re-fetches the diff and `formatPatch` applies the old indices to the new hunks, staging different content than what was shown/reviewed, which then gets committed and can be pushed without further review. [5](#0-4) [1](#0-0) [3](#0-2) [4](#0-3) [6](#0-5)
