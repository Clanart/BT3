### Title
Just-in-time (JIT) deposit around `queueNewRewards`/`donateRewards` lets an attacker capture a pro-rata share of freshly-distributed rewards with zero holding time, diluting legitimate long-term stakers' yield - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool` distributes 100% of any donated/queued reward instantly into a single scalar `rewardPerTokenStored`, weighted only by the *current* `totalStaked()` and read live via `balanceOf(_account)` in `earned()`. Because there is no time-weighting, vesting, or reward-rate streaming, any account that deposits stake in the same block immediately before a reward injection (whether via the privileged `queueNewRewards` or the unprivileged `donateRewards`) and then claims and withdraws in the same block captures a full pro-rata slice of that reward for zero economic exposure, diluting the yield legitimately accrued by stakers who held their position over time.

### Finding Description
`earned()` computes reward using the *live* `balanceOf(_account)` (fetched from `MasterMagpie.stakingInfo`) multiplied by the delta between the current `rewardPerToken` and the last checkpoint `userRewardPerTokenPaid`: [1](#0-0) 

`_updateFor` re-checkpoints `userRewards`/`userRewardPerTokenPaid` using this same live balance: [2](#0-1) 

Crucially, `MasterMagpie._deposit` calls `_harvestBaseRewarder` (which triggers `rewarder.updateFor(_account)`, checkpointing the account at its **pre-deposit** balance/`rewardPerToken`) *before* `user.amount` is increased and before the staking tokens are even transferred in: [3](#0-2) 

Any reward injection - via the manager-only `queueNewRewards` or the fully unprivileged `donateRewards` - immediately updates the global `rewardPerTokenStored` scaled by `totalStaked()` at that instant: [4](#0-3) 

Exploit flow in one block:
1. Attacker calls `MasterMagpie.deposit(stakingToken, amount)`. This checkpoints the attacker's `userRewardPerTokenPaid` at the pre-deposit `rewardPerTokenStored` and increases `user.amount`/token balance.
2. Reward injection happens (manager's `queueNewRewards`, front-run via mempool, or attacker's own `donateRewards`). `rewardPerTokenStored` jumps up, weighted by `totalStaked()` which already includes the attacker's freshly-deposited amount.
3. Attacker triggers `getReward` indirectly (it's `onlyMasterMagpie`) through `MasterMagpie.multiclaim`/`multiclaimSpec`, which calls `_claimBaseRewarder` → `rewarder.getReward`: [5](#0-4) 
`getReward`'s `updateReward` modifier recomputes `earned()` using the attacker's **full, just-deposited** live `balanceOf`, multiplied by the entire reward-per-token increase that just occurred - even though the attacker held zero stake when the reward period began: [6](#0-5) 
4. Attacker calls `MasterMagpie.withdraw` to pull the principal back out, again same block: [7](#0-6) 

No modifier prevents this: `nonReentrant`/`whenNotPaused` guard against reentrancy/pausing, not against same-block JIT staking; there is no minimum holding period, cooldown, or time-weighted accrual anywhere in `BaseRewardPool`/`MasterMagpie`. The root cause is architectural: reward-per-token is a single global scalar updated atomically on injection, with no linear vesting (unlike a `periodFinish`/`rewardRate` model), so whoever holds the largest balance at the instant of injection captures a proportional share regardless of duration held.

### Impact Explanation
This does not touch other users' deposited principal (withdraw amounts remain conserved 1:1), but it does allow theft of unclaimed yield: a JIT depositor captures `D/(S+D)` of any reward injected at that moment (where `D` is the attacker's flash-in stake and `S` is pre-existing stake), which otherwise would have accrued entirely to the pre-existing long-term stakers. When exploited against a manager-triggered `queueNewRewards` (real bribes/incentives, front-run via mempool observation - an explicitly allowed attacker capability), this is a direct, repeatable transfer of yield from legitimate stakers to an opportunistic flash-depositor with no holding-period risk. This maps to the Immunefi impact class "theft of unclaimed yield."

### Likelihood Explanation
- No special privileges are required: `deposit`/`withdraw`/`multiclaim` are public, and `donateRewards` is explicitly unprivileged.
- The only capital requirement is enough stake to temporarily dominate `totalStaked()` for one block (attacker can flash-loan the staking token if it is loanable, or simply use owned capital sized relative to pool TVL).
- The attack is fully atomic (single transaction/multicall), so it can be repeated every time a reward is queued, and is front-runnable against any manager `queueNewRewards` call visible in the mempool.
- Feasibility depends on the staking token's liquidity for flash-borrowing and on `queueNewRewards`/`donateRewards` transactions being visible pre-confirmation, both realistic conditions on public chains.

### Recommendation
Introduce time-weighted or streamed reward distribution instead of instantaneous scalar updates, e.g.:
- Add a `rewardRate`/`periodFinish` (Synthetix-style `StakingRewards`) model so donated/queued rewards vest linearly over a duration rather than being fully credited to instantaneous stake.
- Alternatively, require a minimum staking duration (cooldown) before a deposit's stake counts toward `earned()`/`rewardPerToken` allocation, or checkpoint stake balances with a snapshot taken strictly before the block in which a reward is queued.
- Consider disallowing/rate-limiting `donateRewards` from being combined with deposits in the same block, and ensure `_harvestBaseRewarder`/`updateFor` ordering doesn't allow a mismatched pre/post-deposit reward checkpoint to be exploited.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, a `BaseRewardPool` (or `BaseRewardPoolV2`) pool for a mock staking token, and a mock ERC20 reward token; register the pool via `add`.
2. Seed pool with an existing long-term staker `Alice` who deposits `S` tokens and waits (simulate `N` blocks/time passing, no reward yet).
3. In a single transaction/test block:
   a. Attacker `Bob` calls `MasterMagpie.deposit(stakingToken, D)` (`D` large relative to `S`, e.g. `D = 10*S`, using flash-borrowed or pre-funded tokens).
   b. Bob calls `rewarder.donateRewards(R, rewardToken)` (approving reward tokens first) - standing in for a manager's `queueNewRewards(R, rewardToken)` that Bob front-ran.
   c. Bob calls `MasterMagpie.multiclaim([stakingToken])`, triggering `getReward` for himself.
   d. Bob calls `MasterMagpie.withdraw(stakingToken, D)`.
4. Assert: `rewardToken.balanceOf(Bob) - R_donated_by_bob ≈ D/(S+D) * R` (Bob recovers a non-trivial share of the reward despite zero holding duration), and Alice's `earned(Alice, rewardToken)` is reduced to `S/(S+D) * R` versus the `R` (or higher share) she would have received had Bob not JIT-staked.
5. Assert Bob's principal `D` is fully returned (conservation of principal holds, confirming this is a yield-dilution exploit, not a principal-theft exploit).

    function _updateFor(address _account) internal {
        uint256 length = rewardTokens.length;
        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = rewardTokens[index];
            userRewards[rewardToken][_account] = earned(_account, rewardToken);
            userRewardPerTokenPaid[rewardToken][_account] = rewardPerToken(rewardToken);
        }
    }

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
