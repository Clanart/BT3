Found a genuine analog: the secp256k1/ed25519/secp256r1 precompile `verify()` functions loop `for i in 0..num_signatures` doing expensive cryptographic operations (ECDSA recovery, Ed25519 `verify_strict`, or full OpenSSL P-256 verification) **before any per-signature compute-unit metering occurs**, because precompile verification is charged a flat, count-independent cost rather than metered per-iteration inside the loop.

### Title
Precompile signature-verification loops (secp256k1/ed25519/secp256r1) execute unmetered per-signature crypto work inside an unbounded count-driven loop - (File: precompiles/src/secp256k1.rs, precompiles/src/ed25519.rs, precompiles/src/secp256r1.rs)

### Summary
This mirrors the FCNProduct bug class: a loop whose iteration count is attacker-controlled and whose cost is not charged incrementally, only implicitly bounded by an outer, coarse limit (transaction size / a flat per-signature cost constant used purely for block-cost accounting, not for runtime metering).

### Finding Description
Each precompile's `verify()` function reads an attacker-supplied count byte from instruction data (`num_signatures`/`count`) and then loops that many times performing real cryptographic work:
- `precompiles/src/secp256k1.rs:31-102` — loop does `libsecp256k1::recover` (ECDSA public-key recovery) and a Keccak hash per iteration. [1](#0-0) 
- `precompiles/src/ed25519.rs:30-77` — loop does `ed25519_dalek::PublicKey::verify_strict` per iteration. [2](#0-1) 
- `precompiles/src/secp256r1.rs:59-138` — loop does a full OpenSSL EC-group P-256 ECDSA verification (`EcPoint::from_bytes`, `Verifier::verify`) per iteration; this is explicitly capped at `num_signatures > 8` reject. [3](#0-2) 

Critically, `secp256k1` and `ed25519` have **no upper bound on `num_signatures`** other than it being a single byte (max 255) and the implicit requirement that `data.len() >= expected_data_size` (so the instruction's own data must be large enough to hold that many `SignatureOffsets` structs). Only `secp256r1` caps `num_signatures` at 8. [4](#0-3) [5](#0-4) 

The cost model does account for a fixed constant per signature (`SECP256K1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, `SECP256R1_VERIFY_COST`) multiplied by the number of instruction signatures for **block cost accounting**, using the count read from `instruction.data.first()`: [6](#0-5) [7](#0-6) 

This cost is applied at the transaction-scheduling/block-cost-limit layer (`MAX_BLOCK_UNITS`), not as a live, per-iteration compute-meter charge inside `verify()` itself (unlike ordinary syscalls, e.g. `SyscallBigModExp`, which explicitly call `invoke_context.compute_meter.consume_checked(cost)` before doing expensive work). [8](#0-7) 

### Impact Explanation
Because ECDSA recovery (secp256k1) and Ed25519 strict verification are relatively expensive cryptographic primitives, and `num_signatures` can be up to 255 in a single precompile instruction (limited only by needing `255 * SIGNATURE_OFFSETS_SERIALIZED_SIZE` bytes of instruction data, which fits comfortably within Solana's packet/transaction size limit), an unprivileged transaction sender can construct a transaction that forces every processing validator's leader/replay pipeline to perform up to 255 secp256k1 recoveries or Ed25519 verifications per instruction, and multiple such instructions per transaction/block. Since this happens during `process_precompile` inside `process_message` — which executes before/independent of BPF CU metering — it can inflate the CPU time spent per transaction well beyond what the flat per-signature cost constant in the cost model was designed to reflect, potentially causing outsized processing latency relative to the block-cost budget charged, which is the core "loop scales with attacker-controlled count without incremental metering, causing excess resource consumption" pattern from the report. This is a possible non-RPC remote CPU-exhaustion vector against the leader/replay pipeline rather than fund theft, but it does not on its own break consensus, since all validators execute the identical transaction and pay identical (if under-metered) cost.

### Likelihood Explanation
Medium-low confidence: the actual severity depends on whether the flat `*_VERIFY_COST` cost-model constants (already calibrated per operation, e.g. `SECP256K1_VERIFY_COST = 30*223`) sufficiently reflect real wall-clock cost of `libsecp256k1::recover`/`ed25519_dalek::verify_strict`/OpenSSL P-256 verify. I was not able to find or verify any measurement/benchmark data confirming the cost model constants are miscalibrated for this repository's precompile implementations, nor find any explicit maximum for `num_signatures` in secp256k1/ed25519 beyond the natural instruction-data-size constraint. This is a plausible efficiency/DoS concern rather than a confirmed, exploitable break — it requires further empirical CU-cost benchmarking (outside the scope of static code search) to establish whether it crosses into an actual crash/degradation vulnerability under the stated impact criteria.

### Recommendation
- Verify (via benchmarking) that `SECP256K1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, and `SECP256R1_VERIFY_COST` accurately upper-bound the real per-iteration cost of `precompiles/src/secp256k1.rs`, `precompiles/src/ed25519.rs`, and `precompiles/src/ed25519.rs`'s loops on production hardware, including worst-case inputs (invalid curve points/max-length messages) that maximize verification failure-path cost.
- Add an explicit upper bound on `num_signatures`/`count` for `secp256k1` and `ed25519`, consistent with the `secp256r1` precompile's `num_signatures > 8` cap, rather than relying only on incidental instruction-data-size constraints.
- Consider metering these precompile loops incrementally via the invoke context's compute meter rather than only via the separate cost-model pre-block-inclusion estimate.

### Proof of Concept
Construct a transaction containing a `secp256k1_program` (or `ed25519_program`) instruction whose first data byte (`count`/`num_signatures`) is set to a large value (up to 255), with `expected_data_size` bytes of following `SecpSignatureOffsets`/`Ed25519SignatureOffsets` structures (all pointing at valid offsets, e.g. self-referencing garbage signatures that will fail validation quickly only if malformed, or to maximize cost, valid-format-but-failing signatures forcing full `recover`/`verify_strict` computation for all N entries): [9](#0-8) [10](#0-9) 
Submit repeated such transactions to observe leader/replay CPU time versus the compute-unit cost charged by `cost-model/src/cost_model.rs`'s `get_signature_cost`.

            .saturating_mul(SIGNATURE_COST)
