### Title
mWOMSVBaseRewarder._calExpireForfeit is dead code and always returns forfeitAmount == 0, permanently preventing prorated forfeiture of unclaimed yield from cooldown holders - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` sets `rewardableAmount = _amount` unconditionally and never queries `mWomSV`'s cooldown/lock state, so the subsequent `forfeitAmount = _amount - rewardableAmount` is always `0`. This is in contrast to the analogous `vlMGPBaseRewarder._calExpireForfeit`, which multiplies `_amount` by `vlMGP.getRewardablePercentWAD(_account)` to correctly prorate rewards for accounts in cooldown. Since `wombat/mWomSV.sol` itself exposes a `getRewardablePercentWAD` function that is never called from the rewarder, the forfeiture logic for mWOMSV stakers is non-functional.

### Finding Description
`getReward()` → `_sendReward()` → `_calExpireForfeit(_account, userRewards[...])` in `rewards/mWOMSVBaseRewarder.sol:362-398`. Compare the two implementations:

`rewards/vlMGPBaseRewarder.sol:386-390`: [1](#0-0) 
computes `rewardableAmount = _amount * vlMGP.getRewardablePercentWAD(_account) / 1e18`, i.e., it queries the lock contract for the account's actual rewardable percentage based on cooldown state, and only pays out that prorated share.

`rewards/mWOMSVBaseRewarder.sol:385-398`: [2](#0-1) 
instead sets `rewardableAmount = _amount` directly, never calling `mWOMSV.getRewardablePercentWAD(_account)` (a function that demonstrably exists on `wombat/mWomSV.sol`, confirmed by grep matches there and in `VLMGP.sol`/`vlMGPBaseRewarder.sol`). The `if (rewardableAmount > _amount) revert` check is therefore unreachable dead code, and `forfeitAmount` is always `0`, so `_queueNewRewardsWithoutTransfer` in `_sendReward` (`rewards/mWOMSVBaseRewarder.sol:362-376`) is never invoked with a non-zero amount.

Any attacker holding mWOMSV, initiating `unlock()` on the underlying locker to enter cooldown, and then calling `getReward()` while in cooldown receives their full reward with zero forfeiture — a state that should instead prorate a share of their yield back to non-cooldown lockers via `_queueNewRewardsWithoutTransfer`. No modifier, nonReentrant, or index update in `updateReward`/`updateRewards` compensates for this, since the bug lives entirely within the forfeiture calculation itself, which is called unconditionally by every `getReward()` invocation.

### Impact Explanation
This causes permanent loss of the forfeiture mechanism, meaning: (1) unclaimed/cooldown-holder yield that is supposed to be redirected to remaining committed lockers is instead fully retained by the cooldown user, and (2) remaining lockers who should benefit from `queueNewRewards`/forfeiture inflows permanently lose that yield. This matches the Immunefi impact class "theft of unclaimed yield" — funds that should flow to other stakers are diverted to (or retained by) the cooling-down user, with no way to recover once each `getReward()` call executes.

### Likelihood Explanation
The vulnerability requires no special privileges — any mWOMSV holder can lock, call `unlock()` to start cooldown, and then call `getReward()` (routed through `masterMagpie`, which is a normal user-facing flow) to reap full rewards with zero forfeiture. This is 100% reproducible on every call by every user in cooldown, requiring no capital beyond holding mWOMSV and going through a normal lock/unlock lifecycle.

### Recommendation
Fix `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder._calExpireForfeit`: query `mWOMSV.getRewardablePercentWAD(_account)` (already present on `wombat/mWomSV.sol`) and compute `rewardableAmount = _amount * rewardablePercentWAD / 1e18` before deriving `forfeitAmount`.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `mWOMSVBaseRewarder`, and required mocks (masterMagpie, reward token).
2. Lock mWOM for `accountA` and `accountB`; fund the rewarder with reward tokens via `queueNewRewards`/`_provisionReward`.
3. Call `unlock()` for `accountA` to place it into cooldown at time `t0`.
4. At time `t0 + k` (still within cooldown), call `mWomSV.getRewardablePercentWAD(accountA)` directly and assert it returns `< 1e18` (i.e., a genuine prorated percentage below 100%).
5. Call `mWOMSVBaseRewarder.calExpireForfeit(accountA, rewardToken)` and assert it returns `0` regardless of step 4's result — demonstrating the forfeit calculation ignores cooldown state.
6. As a differential check, replicate the same lock/cooldown timeline using `VLMGP`/`vlMGPBaseRewarder` and assert `vlMGPBaseRewarder.calExpireForfeit` returns a non-zero forfeit amount proportional to `(1e18 - getRewardablePercentWAD)`.
7. Call `mWOMSVBaseRewarder.getReward(accountA, accountA)` and assert `accountA` receives 100% of `earned()` with no `ForfeitRewardAdded` event emitted, confirming the missing forfeiture flow to `_queueNewRewardsWithoutTransfer`.

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();
```

**File:** rewards/mWOMSVBaseRewarder.sol (L385-398)
```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```
