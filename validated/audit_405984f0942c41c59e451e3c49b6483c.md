## Title
Stale absolute-line indices in `DiffSelection` after hunk expansion cause partial-commit selection to silently apply to the wrong lines - (File: `app/src/ui/diff/text-diff-expansion.ts`, `app/src/lib/patch-formatter.ts`, `app/src/models/diff/diff-selection.ts`)

## Summary
Diff line selection state used to build a partial commit is tracked as a `Set<number>` of *absolute* line indices in `DiffSelection` (`divergingLines`), computed as `hunk.unifiedDiffStart + lineIndex`. When a user expands a hunk (`Expand Up`/`Expand Down`/`Expand Whole File`), `expandTextDiffHunk` recomputes `unifiedDiffStart`/`unifiedDiffEnd` for the expanded hunk and shifts every subsequent hunk's indices by the number of newly inserted lines, but it never remaps or invalidates the existing `DiffSelection` held by the file. The same absolute index that used to identify one diff line now identifies a different line. Since `formatPatch`/`formatPatchToDiscardChanges` (the code that builds the actual git patch used for `git apply --cached`) re-derives `absoluteIndex` from the (now expanded) hunk layout and queries the *old* selection object with it, a user's selected/deselected lines can silently shift onto different content than what they reviewed and chose.

## Finding Description
`DiffSelection.isSelected(lineIndex)` and `withRangeSelection` treat line identity purely as an integer index with no relationship to the actual diff content: [1](#0-0) 

That index is produced everywhere in the UI/patch code as `hunk.unifiedDiffStart + lineIndex` (or `+ index` within the hunk), e.g. in `formatPatch`: [2](#0-1) 

and identically in `formatPatchToDiscardChanges`: [3](#0-2) 

`expandTextDiffHunk` (invoked by `onExpandHunk`/`expandHunk` in `side-by-side-diff.tsx`) inserts new context lines into a hunk and then re-numbers every following hunk by adding `numberOfNewDiffLines` to their `unifiedDiffStart`/`unifiedDiffEnd`: [4](#0-3) [5](#0-4) 

`expandHunk` only swaps the component's local `diff` state and never touches the file's `DiffSelection`, which lives in the working-directory file model owned by `AppStore`/`changesState`: [6](#0-5) 

The only place `DiffSelection` gets reconciled against a changed diff (`withSelectableLines`) merely intersects the existing `divergingLines` set with the new set of selectable absolute indices — it does not shift/remap indices to follow the lines they used to point to: [7](#0-6) 

Consequently, after any expansion that inserts `N` new lines before a hunk (`isExpandingUp` path, or a preceding hunk being expanded down/merged), every absolute index recorded in `divergingLines` for lines at or after that point becomes a "off-by-N" reference: it now happens to fall on a different diff line (or a freshly inserted context line) than the one the user actually selected/deselected. Because context lines are always force-included by `formatPatch` regardless of selection, and because real change lines can land on the shifted indices that used to belong to other change lines, the set of lines that actually get written into the outgoing patch (and thus committed/staged) can silently diverge from the lines the user visually selected before expanding.

## Impact Explanation
This breaks the core invariant of Desktop's partial-commit/"stage-by-line" feature: *the lines that end up in the commit/patch must be exactly the lines the user selected in the diff view.* If an attacker controls the content of a file in a fetched/cloned/pulled branch (e.g., a malicious pull request the user is reviewing locally, or a remote/proxy that alters diff content), they can craft a file with multiple hunks such that:
1. The victim deliberately deselects a specific dangerous/injected line (e.g., excludes a suspicious added line from being committed after reviewing a diff), and
2. Before committing, the victim expands an earlier hunk for additional context (a completely normal, expected Desktop action, exposed via the "Expand Up/Down"/"Expand Whole File" buttons),

causing the previously-excluded line's absolute index to now be occupied by a different line, so the malicious line the user thought was excluded gets silently included in the patch that is staged/committed/pushed — without any additional UI warning that the selection mapping changed. This is a silent corruption of what the user commits or pushes, matching the "broken invariant" bug class from the source report (computing/tracking a derived value via an index/formula that is invalidated by a structural change elsewhere, producing a result the user does not expect and has no way to detect).

## Likelihood Explanation
The trigger path requires only normal, unprivileged user interaction with Desktop's built-in diff-expansion UI (no local/admin access, no malware, no credentials) on a diff that an attacker fully controls the shape of (number/position of hunks, gaps between them). Any repository with a multi-hunk diff and small gaps between hunks (making expansion/merging routine) is a candidate. The only extra step required of the victim is to click "Expand" on a hunk after adjusting the selection — a plausible, common workflow when reviewing large diffs before committing. However, whether the *exact* corrupted index actually lands on another selectable/change line (as opposed to a context line, where it would have no visible effect) depends on the specific hunk layout, so a concrete PoC would need a diff crafted with the right hunk sizes/gaps to guarantee the collision; I was not able to run this against a live app-store integration to confirm end-to-end that no other reconciliation step (e.g., a `withSelectableLines` call keyed to the specific `WorkingDirectoryFileChange` component) intervenes before `formatPatch` is invoked, so likelihood should be treated as plausible but unverified end-to-end.

## Recommendation
When a hunk is expanded (or merged), remap the associated file's `DiffSelection` indices in lock-step with the shift applied to `unifiedDiffStart`/`unifiedDiffEnd`, rather than leaving the `divergingLines` set keyed to stale absolute positions. Concretely: `expandTextDiffHunk`/`expandWholeTextDiff` (or their callers in `side-by-side-diff.tsx`/`app-store.ts`) should return enough information (e.g., an insertion offset and position) to let the caller produce an updated `DiffSelection` where every diverging index at or beyond the insertion point is shifted by the same delta, instead of relying solely on `withSelectableLines` set-intersection. Add regression tests that select/deselect specific lines, expand a hunk before them, and assert that `formatPatch` output still reflects the originally intended lines.

## Proof of Concept
Conceptual PoC (index shift, verifiable via existing test infrastructure in `app/test/unit/text-diff-expansion-test.ts` and `app/test/unit/patch-formatter-test.ts`):
1. Create/parse a diff with two hunks with a small gap, e.g. via `parseDiff`, mirroring the pattern in `app/test/unit/patch-formatter-test.ts` and `prepareDiff` helper used in `text-diff-expansion-test.ts` (`prepareDiff(100, [20, 10])`), which the tests confirm gets merged on expansion.
2. Build a `DiffSelection` (`DiffSelection.fromInitialSelection(DiffSelectionType.All).withRangeSelection(...)`) that deselects one specific change line in the *second* hunk, using its absolute index (`hunk.unifiedDiffStart + lineIndex`) computed against the *original* diff.
3. Call `expandTextDiffHunk(diff, diff.hunks[0], 'down', newContentLines)` — per the existing test at [8](#0-7) 
this merges the first two hunks and shifts indices.
4. Call `formatPatch(file, expandedDiff)` using the *same, unmodified* `DiffSelection` object from step 2 (as would happen in the app because `expandHunk` never touches `file.selection`).
5. Diff the resulting patch text against what the user intended: the line originally deselected by absolute index no longer corresponds to the same source line in the merged/expanded hunk, so the emitted patch either includes the intended-to-exclude line or excludes an unrelated one — demonstrating the same class of "computed value from stale components no longer matches the true delta" defect as the Panoptic fee-accounting bug, here manifesting as silent commit/patch corruption rather than fee over-payment.
