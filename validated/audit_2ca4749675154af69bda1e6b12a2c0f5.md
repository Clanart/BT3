### Title
`open-external` IPC handler forwards attacker-controlled URLs to `shell.openExternal` with no scheme allowlist enforcement - (File: `app/src/main-process/main.ts`)

### Summary
The `_authorizeUpgrade` report's broken invariant is "a sensitive, dangerous operation should be gated by a single, well-defined trust check, not a check that looks like it restricts access but doesn't." The Desktop analog is the `open-external` IPC handler: it inspects the URL scheme only to decide whether to *log* it, and then unconditionally calls `shell.openExternal(path)` regardless of scheme. The apparent guard gives the impression that only `http(s)` links are handled, but it enforces nothing, so any renderer-reachable code path that builds a URL from repository/GitHub-API/commit data can hand an arbitrary-scheme string to the OS shell.

### Finding Description
The main-process handler for `open-external` is: [1](#0-0) 

The scheme check (`pathLowerCase.startsWith('http://')...`) is only used for a `log.info` call — it is not a conditional gate that rejects other schemes. Whatever string reaches this handler is passed straight into `shell.openExternal`.

This handler is exposed to the renderer without any argument sanitization at the IPC boundary itself; the only IPC-level restriction is on the *sender* (`isTrustedIPCSender`), not on the *content* of the argument: [2](#0-1) 

`shell.openExternal` is wrapped in `app-shell.ts`, which explicitly documents that other shell methods (`openPath`, `showFolderContents`) must not be used with "non-validated paths" — but no equivalent warning or validation exists for `openExternal`: [3](#0-2) 

From the renderer side, `_openInBrowser` forwards any string directly to this shell wrapper with no scheme/host validation: [4](#0-3) 

`_openInBrowser`/`openInBrowser` is the terminal sink for numerous URLs that are constructed from GitHub API objects and repository metadata rather than from user-typed input — e.g. commit/PR mention links built from `repository.endpoint`, `repository.owner.login`, and `repository.name`: [5](#0-4) 

and "View on GitHub" flows that build URLs from `gitHubRepository.htmlURL`: [6](#0-5) [7](#0-6) 

Because `gitHubRepository.htmlURL`, PR bodies, issue/commit markdown content, and other GitHub-API-sourced fields are rendered as clickable links and eventually flow into `openInBrowser` → `open-external` → `shell.openExternal`, an attacker who controls a GitHub API response, a linked repository's metadata, or content the user clicks (link/deep link) can supply a non-`http(s)` URI scheme. Electron's `shell.openExternal` will hand that URI to the OS shell/registered protocol handler. This is the well-documented Electron "unrestricted openExternal" primitive that has previously enabled local file execution and OS command-injection-like behavior on Windows/macOS via crafted protocol handlers (e.g., abusing custom URI schemes registered by other installed applications, or `file:`/UNC-style paths).

### Impact Explanation
If a scheme other than `http`/`https` reaches `shell.openExternal` unfiltered, the OS resolves it via the registered protocol handler for that scheme. Depending on the platform and installed software, this can lead to local code execution, execution of a locally reachable file, or launching an application with attacker-controlled arguments (a known Electron `openExternal` risk class). Because the URL can originate from GitHub API objects (repository/PR/commit metadata) or from content rendered from a repository the user has cloned/linked, this satisfies the "attacker controls a GitHub API object" / "link user clicks" precondition without requiring local access, admin rights, or social engineering beyond a normal in-app click.

### Likelihood Explanation
Medium: exploitation requires the attacker's malicious scheme/URI to survive whatever construction logic builds the href (e.g., via a crafted repository name/owner, PR/issue/commit body, or `htmlURL` field from the GitHub API) and for the user to click the resulting rendered link — a normal, expected interaction in Desktop. The check in `main.ts:583-588` gives a false sense that only `http`/`https` are permitted, so there is no additional development-time safeguard blocking other schemes from reaching the shell.

### Recommendation
Make the scheme check in the `open-external` handler an actual authorization gate, not a logging-only branch: reject (return `false`/throw) for any URL whose scheme is not `http:` or `https:` before calling `shell.openExternal`, mirroring how the smart-contract report recommends collapsing multi-role upgrade authorization into a single, enforced check. Apply the same allowlist validation at the point where URLs are constructed from GitHub API data/markdown filters, not only at the final IPC hop.

### Proof of Concept
1. Attacker controls (or compromises) content that flows into a link Desktop renders from repository/GitHub API data — e.g., a PR/issue/commit body rendered via the markdown filters, or a `gitHubRepository.htmlURL`-derived link.
2. That link's `href` is set to a non-`http(s)` URI, e.g. a custom-registered protocol string, instead of a normal `https://github.com/...` URL.
3. The user clicks the link inside Desktop (expected/normal interaction); this dispatches to `_openInBrowser`/`openInBrowser`. [4](#0-3) 
4. The renderer invokes the `open-external` IPC channel, which reaches: [1](#0-0) 
5. Since only `http/https` are special-cased for logging (not enforcement), the crafted scheme is passed unmodified to `shell.openExternal(path)`, and the OS shell/protocol handler processes it — potentially executing code or a file outside the repository, depending on what handler is registered on the victim's machine for that scheme.

I could not fully trace every markdown-filter → `openInBrowser` call site within the available indexed context (some files like `issue-link-filter.ts` were only partially inspected), so I cannot enumerate every exact injection point beyond the ones cited above.
