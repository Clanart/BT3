### Title
Duplicate-key detection in JSON map parsing operates on raw JSON key strings, not canonical decoded values, letting different string spellings of the same numeric key create physically duplicate map entries - ([File: src/google/protobuf/json/internal/parser.cc])

### Summary
The AdapterVault report's root cause is a broken uniqueness invariant: the code assumes each accounting "key" (asset) maps to exactly one entry, but the actual add-path never enforces that, so two entries can silently alias the same key and get summed twice. The closest transferable Protobuf analog is in the ProtoJSON map parser: `ParseMap` deduplicates map keys by comparing the *raw JSON string* seen for each key, while the actual map key that gets stored is the *canonical decoded numeric value* produced later by `ParseMapKey`. Two syntactically different JSON strings that decode to the same numeric key (e.g. `"0"` and `"-0"` for a signed integer key type) bypass the duplicate check and both get appended as separate physical map entries via `Traits::NewMsg`, which unconditionally *adds* a new repeated map-entry submessage rather than checking for an existing key.

### Finding Description
`ParseMap` builds a `keys_seen` set keyed on the literal JSON text of the map key and rejects only *exact string* repeats: [1](#0-0) 

The actual key that ends up on the wire is computed afterward by `ParseMapKey`, which uses `absl::SimpleAtoi` to decode the string into the field's canonical numeric type (int32/int64/uint32/uint64/etc.): [2](#0-1) 

Each map entry is created by `ParseMapEntry`, which calls `Traits::NewMsg` to *append* a brand-new map-entry submessage to the field, with no check for whether that decoded key already exists among previously-appended entries in this same parse: [3](#0-2) 

`Traits::NewMsg`/`SetInt32` etc. for a map (repeated) field go through the reflection `Add*` path, i.e. always append rather than "insert-or-replace": [4](#0-3) 

Consequently, a JSON payload such as `{"map_int32_int32": {"0": 1, "-0": 2}}` passes the `keys_seen` check (two distinct strings) but yields two map-entry submessages that both encode key `0` in the underlying repeated representation. Protobuf's map storage explicitly documents and tests that having duplicate keys in the raw repeated representation (state `STATE_MODIFIED_REPEATED`) is a real, previously-buggy divergence between the deduplicated map view and repeated-field view: [5](#0-4) [6](#0-5) 

This is the direct structural analog of the AdapterVault bug: an operation that is supposed to guarantee "one canonical key -> one entry" (`_addAdapter()` for assets, `keys_seen` for map keys) checks the wrong identity (the strategy's asset vs. the raw JSON string) instead of the canonical value that downstream accounting/iteration logic actually keys off of (`totalAssets()` iterating adapters vs. any code iterating the raw repeated map-entry list before it is synced/deduplicated to the canonical map).

### Impact Explanation
Any consumer that reads the parsed message via repeated-field/reflection APIs before the map is synchronized (or via internal size/serialize code paths that use the `STATE_MODIFIED_REPEATED` representation) will observe two entries for what should be a single logical key. As shown in the historical regression test, this divergence has previously caused `ByteSizeLong()` to overcount relative to the actual serialized/map data, and application code that sums or otherwise aggregates per-key values from the raw repeated representation would double-count the value for the aliased key - the same overinflated-accounting failure mode described in the report, just manifesting through JSON parsing's key-uniqueness check rather than a smart-contract strategy list.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires (1) a message containing an integer-keyed map field, (2) an ordinary client sending ProtoJSON with two different string spellings of the same canonical integer (only `"0"`/`"-0"` reliably collide for signed types without other validation rejecting them), and (3) downstream code that reads the field's raw repeated/entry-list representation rather than always going through the canonical, deduplicating map accessor. This is a narrower trigger surface than the vault's "any adapter added by an admin," but it is fully reachable through the public ProtoJSON parsing API on bounded, otherwise-valid input with a trusted schema.

### Recommendation
`ParseMap`'s duplicate-key check in `src/google/protobuf/json/internal/parser.cc` should perform the comparison on the *decoded, canonical* map key (post `ParseMapKey`) rather than on the raw pre-decode JSON string, so that syntactically different but semantically equal keys (`"0"` vs `"-0"`, leading `+`/zero-padding variants, etc.) are correctly rejected as duplicates before a second map-entry submessage is appended.

### Proof of Concept
For a message with a field `map<int32, int32> map_int32_int32`, parse the following ProtoJSON via the public `JsonToBinary`/`Parse` entry point:
```json
{"map_int32_int32": {"0": 1, "-0": 2}}
```
Trace: `ParseMap` computes `keys_seen = {"0", "-0"}` (both accepted, no "repeated map key" error) at `src/google/protobuf/json/internal/parser.cc:767-776`; each key is independently passed to `ParseMapKey`, which decodes both `"0"` and `"-0"` to the same `int32_t` value `0` via `absl::SimpleAtoi` at `src/google/protobuf/json/internal/parser.cc:608-616`; each call to `ParseMapEntry` unconditionally appends a new map-entry submessage via `Traits::NewMsg`/reflection `Add*` at `src/google/protobuf/json/internal/parser.cc:753-758` and `parser_traits.h:176-182`. The resulting message's `map_int32_int32` repeated representation therefore contains two entries with key `0` (values `1` and `2`) before any map-sync step normalizes it - reproducing, on the wire/parse level, the exact "two entries alias the same logical key" condition that the AdapterVault report flags as the root cause of double counting.

                           Msg<Traits>& parent_msg,

  bool is_map_of_enums = false;
  RETURN_IF_ERROR(Traits::WithFieldType(
      map_field, [&is_map_of_enums](const Desc<Traits>& desc) {
        is_map_of_enums = Traits::FieldType(Traits::ValueField(desc)) ==
                          FieldDescriptor::TYPE_ENUM;
        return absl::OkStatus();
      }));

  // Special case for map<*, enum> due to handling of unknown enum values.
  // See comments above ParseMapOfEnumsEntry for details.
  if (is_map_of_enums) {
    return ParseMapOfEnumsEntry<Traits>(lex, map_field, parent_msg, key);
  }

  return Traits::NewMsg(
      map_field, parent_msg,
      [&](const Desc<Traits>& type, Msg<Traits>& entry) -> absl::Status {
        RETURN_IF_ERROR(ParseMapKey<Traits>(type, entry, key));
        return ParseSingular<Traits>(lex, Traits::ValueField(type), entry);
      });

template <typename Traits>
absl::Status ParseMap(JsonLexer& lex, Field<Traits> field, Msg<Traits>& msg) {
  if (lex.Peek(JsonLexer::kNull)) {
    return lex.Expect("null");
  }

  absl::flat_hash_set<std::string> keys_seen;
  return lex.VisitObject(
      [&](LocationWith<MaybeOwnedString>& key) -> absl::Status {
        lex.path().NextRepeated();
        auto insert_result = keys_seen.emplace(key.value.AsView());
        if (!insert_result.second) {
          return key.loc.Invalid(absl::StrFormat(
              "got unexpectedly-repeated repeated map key: '%s'",
              key.value.AsView()));
        }
        return ParseMapEntry<Traits>(lex, field, msg, key);
      });
