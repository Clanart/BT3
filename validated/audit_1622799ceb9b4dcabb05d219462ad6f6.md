### Title
NFT royalty rounding truncates to zero, letting an offer counterparty avoid paying creator royalties - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
Chia's NFT royalty mechanism computes the royalty payment owed to an NFT's creator using integer division. When the offered/requested fungible amount is small relative to the royalty percentage or the number of NFTs being split across (`royalty_split`), the division truncates to zero, and no royalty coin is created at all. This is the same integer-rounding root cause as the Niftyswap "Blue Dragons" bug: instead of the participant losing dust, here the *royalty recipient* (the NFT creator/collection) silently receives 0 payment even though a royalty was contractually due, and the trade otherwise proceeds and settles normally.

### Finding Description
Two related code paths compute royalty amounts using floor (`//`) integer division without any minimum-amount floor or rejection of underflow-to-zero results:

- `NFTWallet.royalty_calculation()`, used for royalty *summary/estimation* (e.g. shown to the user in `chia/cmds/wallet_funcs.py`), computes:
`abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS` [1](#0-0) 

- `compute_royalty_amount()`, used in `make_nft1_offer()` to build the actual royalty `CreateCoin` payments embedded in the offer's notarized-payment/settlement puzzle, is called per-asset and per-royalty-recipient: [2](#0-1) 

The project's own unit tests confirm the truncate-to-zero behavior is accepted, not rejected, by this function: [3](#0-2) 
and that splitting a royalty payment across multiple NFTs (`royalty_split`) further divides the numerator before applying the percentage, compounding truncation: [4](#0-3) 

Because the royalty amount is computed once by whichever wallet is constructing the offer (`make_nft1_offer`) and simply skips coin creation when the sum of royalty payments for an asset is zero: [5](#0-4) 
an offer maker or taker that controls the requested/offered amount and/or bundles many royalty-bearing NFTs into a single offer (increasing `request_side_royalty_split`/`offer_side_royalty_split`) can drive the per-recipient royalty computation below 1 mojo, causing it to floor to 0. The trade still settles fully (the NFT and the base asset both change hands) with zero royalty paid to the creator, even though the puzzle/percentage says a nonzero royalty is owed.

### Impact Explanation
This lets any offer counterparty structure a trade (small settlement amount, or bundling many royalty-bearing NFTs together to inflate `royalty_split`) to unilaterally reduce the enforced creator royalty to zero, diverting value that should go to the NFT collection/creator to themselves. This is a concrete instance of "offer settlement theft" — value that the CLVM offer protocol is designed to guarantee to a specific party (the royalty address) is not paid due to a rounding defect in wallet-side amount computation, and the chain has no way to reject the resulting spend because syntactically the offer is self-consistent (zero royalty payments simply aren't included in the notarized payments).

### Likelihood Explanation
The condition is easy to trigger deterministically: any offer with a fungible request amount smaller than `MAX_ROYALTY_BASIS_POINTS / royalty_percentage`, or with several royalty-bearing NFTs bundled together (increasing the divisor `royalty_split`), reliably produces a zero royalty. No cryptographic, timing, or race condition is required, and the behavior is already demonstrated by the project's own test suite (`test_small_amount_truncates_to_zero`), showing it is a reachable and reproducible code path.

### Recommendation
Apply the same remediation used for the analogous Niftyswap issue: define a minimum royalty amount (or reject/require adjustment of offers whose computed royalty would round to zero when a nonzero percentage is configured), and/or use rounding-up (ceiling) semantics for royalty computation instead of floor division, particularly when splitting across multiple royalty-bearing NFTs in `royalty_calculation()` and `compute_royalty_amount()`. Document the minimum viable trade size/royalty-split combination for royalty-bearing NFTs so wallets and users are aware that below certain thresholds royalties are not enforced.

### Proof of Concept
1. Create/offer an NFT with `royalty_percentage` (in basis points) such that `abs(offered_amount) * percentage // MAX_ROYALTY_BASIS_POINTS == 0` (e.g., `offered_amount=-50`, `percentage=100` → `compute_royalty_amount` returns `0`, as shown directly in `test_small_amount_truncates_to_zero`) [3](#0-2) .
2. Alternatively, bundle multiple royalty NFTs into one offer/take so `request_side_royalty_split`/`offer_side_royalty_split` grows, dividing the requested fungible amount by that count before applying the percentage in `make_nft1_offer()` [2](#0-1) .
3. Submit the resulting offer/take via `TradeManager`/`respond_to_offer`; the trade settles, the NFT transfers, and the royalty-payment step in `make_nft1_offer()` is skipped because `sum(p.amount for _, p in payments) == 0` [5](#0-4) , resulting in zero mojos ever reaching the intended royalty address.

```python
    @staticmethod
    def royalty_calculation(
        royalty_assets_dict: dict[Any, tuple[Any, uint16]],
        fungible_asset_dict: dict[Any, uint64],
    ) -> dict[Any, list[dict[str, Any]]]:
        summary_dict: dict[Any, list[dict[str, Any]]] = {}
        for id, royalty_info in royalty_assets_dict.items():
            address, percentage = royalty_info
            summary_dict[id] = []
            for name, amount in fungible_asset_dict.items():
                summary_dict[id].append(
                    {
                        "asset": name,
                        "address": address,
                        "amount": abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS,
                    }
                )

        return summary_dict
```
