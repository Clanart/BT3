### Title
PedPoP blame evaluation trusts attacker-supplied `sender`/`recipient` indexes — out-of-range participant panics every verifier, and in-range recipient spoofing misattributes blame to an honest party - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The analog of CVE-2019-11555 (missing reassembly-state validation → NULL-deref DoS) in Serai is missing *participant-state* validation in PedPoP's blame path. `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` and `blame_internal` indexes `self.commitments[&sender]` with `Participant` values taken verbatim from the blame request, without checking they are members of the DKG (`1..=n`) or that the `recipient` is the party the `EncryptedMessage` was actually addressed to. An out-of-range index panics via `HashMap` indexing (the Rust equivalent of the NULL-deref process termination), and an in-range-but-wrong `recipient` causes the blame to be attributed to an innocent participant.

### Finding Description
`BlameMachine::blame` / `AdditionalBlameMachine::blame` (crypto/dkg/pedpop/src/lib.rs:623-632, 674-682) forward the caller-supplied `sender` and `recipient` directly into `blame_internal` (lib.rs:575-609). Inside `Decryption::decrypt_with_proof`:

```rust
// crypto/dkg/pedpop/src/encryption.rs
proof.dleq.verify(
  &mut encryption_key_transcript(self.context),
  &[C::generator(), msg.key],
  &[self.enc_keys[&decryptor], *proof.key],   // line 388: unchecked index
)
```

and in `blame_internal`:

```rust
// crypto/dkg/pedpop/src/lib.rs
multiexp_vartime(&share_verification_statements::<C>(
  recipient,
  &self.commitments[&sender],               // line 599: unchecked index
  ...
))
```

`Decryption::register` / `AdditionalBlameMachine::new` only populate `enc_keys` and `commitments` for `Participant(1..=n)` (encryption.rs:351-362, lib.rs:656-660). Nothing validates `sender`/`recipient` against that set. Because `Participant` is any non-zero `u16` (dkg/src/lib.rs:29-35), a blame request can name `sender`/`recipient` > n, producing an indexing panic — no error type exists for this case.

Additionally, the recipient binding is implicit: the `EncryptedMessage`'s PoP (`pop_challenge`, encryption.rs:374-379) binds only `from` (the claimed sender), the ephemeral key and the ciphertext — never the intended recipient. So `decrypt_with_proof` will happily evaluate `msg` against `enc_keys[recipient]` for any `recipient` the accuser chooses. If the accuser names an honest participant `j` as `recipient`, the supplied (or absent) `EncryptionKeyProof` will not match `enc_keys[j]`, `decrypt_with_proof` returns `DecryptionError::InvalidProof`, and `blame_internal` returns `recipient` as faulty (lib.rs:585-588) — an honest party is blamed/slashed for a message that was never addressed to them.

### Impact Explanation
- DoS (direct analog): a single participant's blame request with `recipient` (or `sender`) outside `1..=n` panics every node/library instance evaluating the blame — identical in effect to the CVE's process-terminating NULL dereference on an unexpected protocol state.
- Blame misattribution: an accuser can frame any in-range `recipient` by submitting a share message (possibly self-encrypted, with a valid PoP since the accuser controls `msg.key` and signs the challenge containing `from = accused`) together with no valid `EncryptionKeyProof`, causing `recipient` to be returned as the faulty party. In Serai this feeds `ProcessorMessage::Blame` and slashing decisions.

### Likelihood Explanation
Reachable with public inputs: `blame` takes `msg: EncryptedMessage<C, SecretShare<C::F>>` (read via `EncryptedMessage::read`, an explicitly listed untrusted-bytes sink) plus `Option<EncryptionKeyProof>` (`EncryptionKeyProof::read`), and the `sender`/`recipient`/`Participant` fields travel with the accusation. Any single DKG participant can issue an accusation naming arbitrary indexes — no threshold collusion, no honest-majority break, and no privileged position is required; the crash/misattribution occurs in *every* honest party that verifies the blame, not just the accuser.

### Recommendation
- In `Decryption::decrypt_with_proof` and `blame_internal`, replace `self.enc_keys[&decryptor]` / `self.commitments[&sender]` with `get(...)` lookups returning a new `DecryptionError`/`PedPoPError` variant (e.g. `UnknownParticipant`) instead of panicking.
- In `BlameMachine::blame`/`AdditionalBlameMachine::blame`, validate `sender` and `recipient` are within `1..=n`, that `sender != recipient`, and — where the machine knows its own identity — that `recipient` corresponds to a registered decryptor for that message before evaluating proofs.
- Consider binding the intended recipient into `pop_challenge` (e.g. `transcript.append_message(b"to", to.to_bytes())`) so a share message cannot be re-targeted at a different participant during blame evaluation.

### Proof of Concept
```rust
// Setup: honest DKG with n participants produced BlameMachine via calculate_share.
// Attacker (any participant) submits a blame evaluation request with an
// out-of-range recipient:

let attacker = Participant::new(1).unwrap();
let oob      = Participant::new(u16::MAX).unwrap(); // > n

// A syntactically valid EncryptedMessage with a valid PoP for `from = sender`
// (the attacker controls msg.key, so they can sign pop_challenge(context, R,
//  key, from, msg) for any `from`).
let msg: EncryptedMessage<C, SecretShare<C::F>> = encrypt(
  &mut OsRng, context, /* from = */ accused, attacker_key, Zeroizing::new(SecretShare([0; 32]))
);
// Equivalently, deserialize attacker bytes via EncryptedMessage::read.

// This reaches decrypt_with_proof -> self.enc_keys[&oob] -> panic!()
// Every honest evaluator of this blame crashes (DoS).
blame_machine.blame(accused, oob, msg, Some(attacker_proof));

// Variant 2 (misattribution, no panic): recipient = honest participant j.
// pop verifies (attacker's key signs the challenge), the EncryptionKeyProof
// cannot match enc_keys[j] -> InvalidProof -> `blame` returns `j` as faulty.
blame_machine.blame(accused, honest_j, msg, None);
```
