### Title
Trampoline credential-helper leaks signed-in GitHub token to any process spawned during a git operation (malicious hook/filter) - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
The Solidity report's broken invariant is that `borrow()` remains callable in phases where the caller ("solver") no longer controls the outcome, because the phase-check that should gate it isn't actually enforced at the point of call. The equivalent broken invariant in Desktop is in the trampoline credential system: Desktop configures `credential.helper=desktop` for the *entire* git process tree of an operation via `GIT_CONFIG_PARAMETERS`/`DESKTOP_TRAMPOLINE_TOKEN` in `withTrampolineEnv`, but the credential-fetch handler that answers `git credential fill` requests never verifies that the request actually originates from the top-level remote operation the user initiated — it only trusts whatever `host`/`url` fields are present in the credential payload. [1](#0-0) 

### Finding Description
`withTrampolineEnv` sets `GIT_CONFIG_PARAMETERS` to force `credential.helper=desktop` for the whole invocation of `git`, and passes `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` in the environment. Because this is an environment variable (not a one-off CLI argument), it propagates to every child process git spawns during that single operation — including repository-defined hooks (`post-checkout`, `post-merge`, `pre-push`, etc.) and filter/smudge/clean processes (e.g. Git LFS or custom `.gitattributes` filters) that ship inside a cloned/fetched repository. [2](#0-1) 

The trampoline token is validated only for well-formedness (`isValidTrampolineToken`), not for *which* remote/host the credential request is being made about: [3](#0-2) 

The `get` credential handler (`getCredential` in `trampoline-credential-helper.ts`) resolves the account purely from the `host`/`url`/`protocol` fields inside the request body, which is fully attacker-controlled input if the request comes from a hook script rather than from git's own HTTP(S) transport code: [4](#0-3) [5](#0-4) 

There is no check anywhere in this path that ties the credential request's `host` back to the URL/remote that the original Desktop-initiated `git` command (`clone`, `fetch`, `pull`, `push`) was actually operating on. As long as the requester supplies `host=github.com` (or any endpoint for which the signed-in user has a stored `Account`), `findGitHubTrampolineAccount` will happily return that account's real OAuth token, merged into the credential response.

### Impact Explanation
A malicious or compromised repository that a user clones/fetches into GitHub Desktop can embed a git hook (e.g. `post-checkout`) or a smudge/clean filter that, while running inside the still-active trampoline environment of that operation, issues its own `git credential fill` (or talks to the trampoline socket directly using `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` from its environment) with `host=github.com`. The Desktop-side handler will return the current signed-in user's GitHub token, exfiltrating the credential to attacker-controlled code that ships with the repository — without any additional user interaction beyond the normal clone/fetch/checkout that Desktop already performs. This is credential/token exfiltration from an unprivileged, attacker-controlled repository, matching the report's "solver griefed"/unbonding-bypass class: a sensitive action (token issuance) remains reachable from a context (arbitrary hook/filter subprocess) that should not have been permitted to invoke it.

### Likelihood Explanation
Requires only that the victim clone or fetch/pull a repository containing a crafted hook or filter — an action GitHub Desktop performs routinely and is the core use case of the app. No local access, no admin rights, and no unusual user steps beyond opening/cloning a repository are needed; the malicious payload rides inside ordinary repository content (hooks/`.gitattributes` filters) as long as Desktop invokes `git` with hooks/filters enabled for that operation, which the current trampoline design does not selectively disable or otherwise scope by target host.

### Recommendation
Scope credential responses to the specific remote/host that the top-level Desktop-initiated git operation is targeting (analogous to retaining the "phase"/execution context at the appropriate layer, as recommended in the Atlas fix). Concretely: bind the expected host(s) to the trampoline token when it is created in `withTrampolineEnv`/`requestTrampolineToken`, and have `getCredential`/`getGitHubCredential` reject or generic-ize any request whose `host` doesn't match the operation's originating remote, rather than trusting the `host` field supplied in the credential payload unconditionally.

### Proof of Concept
1. Attacker publishes a repository containing a `post-checkout` hook (or an `.gitattributes` `clean`/`smudge` filter) that, when executed, reads `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN` from its environment and runs `git credential fill` (or speaks the trampoline protocol directly) with `protocol=https`, `host=github.com`.
2. Victim clones or fetches this repository in GitHub Desktop while signed in with a GitHub account.
3. During the clone/fetch, git invokes the hook/filter as a child process, inheriting the trampoline environment set up in `withTrampolineEnv`.
4. The hook's credential request reaches `createCredentialHelperTrampolineHandler` → `getCredential` → `getGitHubCredential`, which finds the signed-in account for `host=github.com` and returns the real OAuth token to the hook process, which can then exfiltrate it over the network. [6](#0-5) 

Note: I could not directly verify in the indexed code whether Desktop applies any additional restriction (e.g., `core.hooksPath` sandboxing or hook-disabling flags) specifically during `clone`/`fetch` that would prevent hook execution altogether; this would need to be confirmed against the full git invocation options (`app/src/lib/git/clone.ts`, `core.ts`) in a live environment, since the index may not include every call site that sets git config for hook execution.
