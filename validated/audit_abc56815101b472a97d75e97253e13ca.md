### Title
UserPromptSubmit rebaselines past unreviewed Bash-authored commits, permanently excluding the dangerous change from Stop-hook review - (File: `plugins/security-guidance/hooks/diffstate.py`)

### Summary
`capture_git_baseline`, invoked from `handle_user_prompt_submit` on every `UserPromptSubmit`, snapshots the current git tree as the new review baseline via `git stash create` / `HEAD`. The baseline-preservation guard that is supposed to stop this snapshot from advancing past unreviewed edits only fires when `touched_paths` is non-empty, but `touched_paths` is populated by `record_touched_path` for Edit/Write-style tool use, not for arbitrary `git commit`s made through Bash. A user-driven Bash-only turn that commits dangerous code and is interrupted before `Stop` fires causes the next `UserPromptSubmit` to silently rebase `baseline_sha`/`head_at_capture` past that commit, permanently removing it from `compute_v2_review_set`'s diff scope.

### Finding Description
`handle_user_prompt_submit` (`plugins/security-guidance/hooks/security_reminder_hook.py:446-515`) calls `capture_git_baseline(cwd)` (`plugins/security-guidance/hooks/diffstate.py:163-204`) on every prompt to capture a new `baseline_sha`/`head_at_capture` pair. Before overwriting, it checks a "preservation guard":

```
if state.get("touched_paths") and state.get("baseline_sha"):
    preserved["value"] = True
    return
``` [1](#0-0) 

This guard exists specifically to stop the baseline from moving past edits the Stop hook has not yet reviewed. However, `touched_paths` is only appended to by `record_touched_path`, which (per its docstring and the Stop-consumption logic in `consume_stop_state`) is driven by file-edit tool use, not by arbitrary `git commit` invocations run via the Bash tool. `compute_v2_review_set` (`plugins/security-guidance/hooks/diffstate.py:353-438`) itself acknowledges this exact gap in its own docstring:

> "Known limitation: a Bash-only turn that's interrupted before Stop fires leaves touched_paths empty, so the next UPS re-baselines past those edits." [2](#0-1) 

Exploit flow:
1. Attacker (an ordinary user of Claude Code operating in a cloned repo — no admin/maintainer/credential assumptions) prompts Claude to write and commit a dangerous change purely through Bash (e.g. `echo "<vulnerable code>" > file && git commit -am "..."`), avoiding the Edit/Write tools that populate `touched_paths`.
2. The attacker submits a follow-up prompt (or otherwise interrupts the turn) before the asyncRewake `Stop` hook has run and consumed state via `consume_stop_state`.
3. On the new `UserPromptSubmit`, `capture_git_baseline` computes a fresh `sha` (`git stash create`, falling back to `HEAD`) that already includes the just-created dangerous commit. Because `touched_paths` is empty, the preservation guard does not fire, so `state["baseline_sha"]` and `state["head_at_capture"]` are overwritten to point at (or past) the dangerous commit.
4. All subsequent `compute_v2_review_set` calls diff against this new baseline; the dangerous commit is now inside the baseline rather than the diff, so `changed_since` never includes it and the file is never sent for LLM security review or flagged in `Stop`.

This breaks the invariant that the review set must stay bound to the correct baseline and all Claude-authored changes — a change is misclassified as "pre-existing" purely because of turn-interruption timing, not because it was actually reviewed.

### Impact Explanation
This is a logic-level bypass of the plugin's core security guarantee: dangerous code written and committed by Claude during a session can permanently escape the Stop-hook's LLM vulnerability review and the commit-review pipeline's coverage assumptions, because the baseline used for diffing silently absorbs the malicious commit. This matches "Logic-level service disruption caused by bypassing a required guard or misbinding security state" — the guard (`touched_paths`-gated baseline preservation) is bypassed, and the security state (`baseline_sha`/`head_at_capture`) becomes misbound to the wrong commit.

### Likelihood Explanation
The precondition is narrow but fully attacker-controllable without any elevated privilege: the attacker only needs to (a) get Claude to author/commit a change via Bash rather than Edit/Write, and (b) interrupt/resubmit before `Stop` consumes state — both are normal, always-available interactions available to any user chatting with Claude Code. The code's own docstring at `plugins/security-guidance/hooks/diffstate.py:368-370` documents this exact scenario as a known limitation, indicating it is reproducible and already understood by the maintainers (though rationalized as "no worse than v1," it is still a real, demonstrable review-bypass window in the v2 diff scheme).

### Recommendation
Extend `record_touched_path` (or an equivalent marker) to also fire on Bash tool invocations that perform `git commit`/`git add`+write operations, so the preservation guard in `handle_user_prompt_submit` recognizes Bash-authored, uncommitted-to-Stop changes. Alternatively, gate baseline advancement on whether `Stop` has actually consumed the prior baseline (e.g. a `stop_consumed` flag set only inside `consume_stop_state`) rather than solely on `touched_paths` being non-empty, since `touched_paths` is an incomplete proxy for "there exist unreviewed changes."

### Proof of Concept
Integration test plan (pytest, exercising `handle_user_prompt_submit` + `capture_git_baseline` + `compute_v2_review_set`):
1. Initialize a temp git repo with one commit.
2. Simulate turn 1: call `handle_user_prompt_submit({"cwd": repo, "session_id": "s1"})` to capture initial baseline; assert `baseline_sha` stored.
3. Simulate a Bash-only tool action: write a file containing a dangerous pattern (e.g. `os.system(user_input)`) and `git commit -am "danger"` directly via subprocess, WITHOUT calling `record_touched_path` (mirrors Bash tool path).
4. Do NOT invoke `consume_stop_state`/Stop hook (simulating interruption).
5. Simulate turn 2: call `handle_user_prompt_submit({"cwd": repo, "session_id": "s1"})` again.
6. Assert: `load_baseline_sha("s1")` now equals a SHA that includes the dangerous commit (i.e., `git diff <old_baseline>..<new_baseline>` contains the dangerous file), demonstrating the baseline silently advanced.
7. Call `compute_v2_review_set(repo, new_baseline_sha, new_head_at_capture, {})` and assert the dangerous file path is **absent** from the returned `review_paths`, proving the invariant "the review set must stay bound to ... the dangerous change" is violated — expected/desired assertion (currently failing) is that the dangerous file **should** still appear in `review_paths`.
