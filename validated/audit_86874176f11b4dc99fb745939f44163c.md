## Analog Found: Git's built-in recursive-clone symlink/hook protection is explicitly disabled

### Title
Disabling Git's `GIT_CLONE_PROTECTION_ACTIVE` safeguard during recursive clone enables malicious-repository code execution - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` in `app/src/lib/git/clone.ts` always performs `git clone --recursive` and explicitly forces the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` for every clone operation, regardless of the source of the URL. [1](#0-0)  This mirrors the report's underlying pattern: a security-relevant, protocol/tool-level enforcement mechanism (Git's own clone-recursion protection, analogous to the SPL "token standard" royalty enforcement) is being unconditionally overridden by application code rather than left to be enforced, and the override is applied even when the input (the clone URL / resulting repository content) is fully attacker-controlled.

### Finding Description
`GIT_CLONE_PROTECTION_ACTIVE` is a Git-internal environment variable used by Git itself to guard the recursive submodule-clone path against maliciously crafted repositories that abuse nested `.git` directories, symlinks, or case-insensitive/short-name collisions to write files (including hooks) outside of the intended submodule boundary during `git clone --recursive` (the class of issue fixed upstream in Git's clone/submodule hardening, e.g. GHSA-related fixes for clone/submodule path confusion). Desktop's `clone()` function does not merely fail to set this protection — it actively forces it off:

```ts
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
  '-c',
  `init.defaultBranch=${defaultBranch}`,
  'clone',
  '--recursive',
]
``` [1](#0-0) 

This code path is reached for every user-initiated clone, including cloning of arbitrary, attacker-supplied URLs entered via the "Clone repository" UI (`app/src/ui/clone-repository/clone-repository.tsx`, which trims and forwards the URL directly to `cloneImpl`/`clone`) [2](#0-1) , and via the `x-github-client://openRepo/...` deep-link / CLI `--cli-clone` flow that ultimately calls the same `clone()` path (`app/src/lib/parse-app-url.ts`, `app/src/main-process/main.ts`). [3](#0-2) [4](#0-3)  None of these entry points validate or sanitize the *content* of the remote repository (submodule structure, symlinks, nested `.git` paths) — only the destination path is checked (`isClonePathSensitive`) [5](#0-4) , and only the resulting basename is sanitized elsewhere (`sanitizeCloneName` in `remote-parsing.ts`). [6](#0-5)  None of these guards address what a malicious repository's own tree/submodule contents can do once Git's own recursion protection is disabled.

### Impact Explanation
If the target repository (or any of its recursively-cloned submodules) is crafted to exploit the class of bug that `GIT_CLONE_PROTECTION_ACTIVE` exists to stop, disabling it converts an ordinary "clone/fork a public repo" action in Desktop into a potential arbitrary file write outside the intended submodule directory (e.g., into `.git/hooks`), which can be leveraged for local code execution once any subsequent Git operation invokes hooks. This satisfies the "attacker controls a cloned/fetched repository ... result is code execution [or] file write ... outside the repo" impact criteria.

### Likelihood Explanation
Likelihood is high for any user cloning an untrusted or malicious repository — this is one of Desktop's core, most frequently exercised operations, reachable via the UI, CLI flags, and deep links, and the protective flag is unconditionally disabled with no compensating validation of submodule/symlink structure elsewhere in the clone path.

### Recommendation
Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `app/src/lib/git/clone.ts` so that Git's built-in protection for recursive/submodule clones remains active, unless there is a well-documented compatibility reason for disabling it — in which case an equivalent, actively-maintained safeguard (e.g., pinning to a Git version with the fix, validating submodule paths post-clone, or refusing symlinked/nested `.git` paths) should be implemented instead of blanket-disabling the upstream protection.

### Proof of Concept
1. Attacker publishes a public GitHub repository containing a submodule (or nested repository reference) engineered to exploit the recursive-clone path-confusion class of bug that `GIT_CLONE_PROTECTION_ACTIVE` is designed to prevent (e.g., a submodule path that resolves, via symlink or case-insensitive collision, into the parent repository's `.git/hooks` directory).
2. Victim uses GitHub Desktop's "Clone repository" dialog (or an `x-github-client://openRepo/...` deep link, or `--cli-clone`) to clone the attacker's repository.
3. `clone()` runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE` forced to `'false'`, disabling Git's own defense during the recursive submodule clone. [7](#0-6) 
4. The crafted submodule content escapes its intended boundary and writes/overwrites a hook file in the victim's repository.
5. The next Git operation Desktop performs in that repository (commit, checkout, merge, etc.) executes the planted hook, achieving code execution on the victim's machine.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
