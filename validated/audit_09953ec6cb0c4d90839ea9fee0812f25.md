### Title
Scanner reports immature coinbase outputs as spendable funds, enabling construction of invalid spends - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` scans every transaction in a block, including the coinbase (`block.txdata[0]`), and returns matching outputs as `ReceivedOutput`s indistinguishable from regular spendable outputs. Coinbase outputs cannot be spent until they are 100 blocks deep, yet they carry the full output value and a valid key offset. Downstream, `SignableTransaction::new` treats every `ReceivedOutput` as immediately spendable input value, so a transaction can be built (and signed via `TransactionSignMachine::sign`, which commits to all prevouts with `Prevouts::All`) that spends an immature coinbase. Such a transaction is non-standard/consensus-invalid and will never confirm, while the wallet's accounting counts those funds as received.

### Finding Description
`scan_block` iterates `block.txdata` with no special-casing of the coinbase transaction (`mod.rs:221-227`), and `scan_transaction` matches purely on `script_pubkey` (`mod.rs:205`) with no maturity context. A `ReceivedOutput` (`mod.rs:89-97`) records only `offset`, `output`, and `outpoint` — there is no field tracking spendability/maturity. `SignableTransaction::new` (`send.rs:175-185`) then sums `input.output.value` and builds `TxIn`s for every output, and `sign` (`send.rs:373-390`) produces signatures committing to these prevouts via `Prevouts::All`. Nothing anywhere verifies the referenced outpoint isn't an immature coinbase. An external miner (an unprivileged party) can direct a coinbase output to a scanned script — or a naturally occurring coinbase can pay to the key — causing the scanner to report funds as received that cannot actually be spent for 100 blocks.

This mirrors the report's bug class: an accounting primitive omits a component of the true position (here, the maturity/spendability status of owned outputs), leading to an overestimate of available funds and the protocol committing to spends it cannot settle — the Bitcoin-side analog of overlending against illusory liquidity.

### Impact Explanation
Funds are reported received that are not spendable. Any `SignableTransaction` incorporating an immature coinbase `ReceivedOutput` produces a fully-signed transaction that the Bitcoin network rejects (consensus rule: coinbase maturity), stalling FROST signing sessions that consumed preprocesses and burning coordinator effort. In a bridge setting, this means accounted balance overstates spendable balance, and spends depending on those funds fail — a liquidity/settlement failure analogous to being unable to redeem funds that were counted as available.

### Likelihood Explanation
Requires a coinbase output paying to a registered script, which occurs whenever the key receives mining rewards — plausible for a pool/bridge address — and a caller using `scan_block` rather than `scan_transaction`. Reachable with only on-chain data an unprivileged miner controls. Severity is Medium: the transaction fails publicly rather than silently draining funds, and the file's doc comment partially warns about maturity, but no enforcement or spendability flag exists in the API.

### Recommendation
Track per-output spendability: mark outputs derived from `block.txdata[0]` (or transactions `is_coinbase()`) as immature in `ReceivedOutput`, either by adding a maturity-height field populated by a `scan_block` variant that accepts the block height, or by skipping the coinbase in `scan_block` outright. `SignableTransaction::new` should reject `ReceivedOutput`s flagged immature so `input_sat` never includes unspendable value.

### Proof of Concept
1. Miner mines block B whose coinbase `txdata[0]` pays 6.25 BTC to `p2tr_script_buf(scanner.key)`.
2. `scanner.scan_block(&B)` returns a `ReceivedOutput` for that coinbase (`mod.rs:221-227`, matching at `mod.rs:205`).
3. Wallet calls `SignableTransaction::new(vec![received], payments, change, None, fee)` — `input_sat` counts the full coinbase value (`send.rs:175`), no maturity check exists.
4. `multisig`/`preprocess`/`sign` produce a signed transaction whose input references the immature coinbase; broadcast fails with `bad-txns-premature-spend-of-coinbase`. The funds were reported received but were not spendable.
