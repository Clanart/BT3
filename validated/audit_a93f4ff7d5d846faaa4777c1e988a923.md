### Title
Untrusted `ReceivedOutput::read` allows crediting non-existent/mismatched UTXOs that pass all spend validation - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` deserializes an `(offset, TxOut, OutPoint)` triple from attacker-controlled bytes with no consistency check that the `outpoint` refers to a real on-chain output paying `output.script_pubkey` with `output.value`. The only validation performed downstream, in `SignableTransaction::multisig`, checks that `keys.offset(offsets[i]).group_key()` maps to `prevouts[i].script_pubkey` — it cannot and does not verify the outpoint exists or that the claimed amount matches the real UTXO. An unprivileged party can therefore feed fabricated bytes to `ReceivedOutput::read` and have Serai treat phantom or mis-valued outputs as received, spendable funds.

### Finding Description
`ReceivedOutput::read` at `networks/bitcoin/src/wallet/mod.rs:122-134` reads a scalar `offset`, a `TxOut`, and an `OutPoint` from an arbitrary `Read` implementor and returns them as a structurally-valid `ReceivedOutput`. There is no binding between the three fields beyond what the caller asserts.

The intended producer is `Scanner::scan_transaction` (`mod.rs:199-214`), which builds a `ReceivedOutput` from an actually-observed transaction, pairing the registered `offset` for a matched `script_pubkey` with the real `OutPoint`/`TxOut`. The deserialization path bypasses this entirely: any peer who can get bytes into `ReceivedOutput::read` (e.g., by submitting a claimed output/BRP payload to a processor) fabricates the triple.

Downstream validation does not catch the forgery. `SignableTransaction::multisig` (`send.rs:273-285`) only checks:

```rust
let offset = keys.clone().offset(self.offsets[i]);
if p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey {
  None?;
}
```

So an attacker must merely pick any `offset`/`script_pubkey` pair consistent with the threshold key (trivially done by copying a real registered script and pairing it with a fictitious `outpoint`, or using `offset = 0` with the base key's P2TR script from `p2tr_script_buf`). `SignableTransaction::new` then treats `input.output.value` as real balance in its `input_sat` accounting (`send.rs:175`) and the `NotEnoughFunds`/change logic (`send.rs:215-235`), and `TransactionSignMachine::sign` produces valid FROST signature shares over `Prevouts::All(&self.tx.prevouts)` committing to the fabricated amounts (`send.rs:373-390`).

Two distinct failure modes result:

1. **Phantom deposit credited.** If the claimed outpoint doesn't exist (or pays a different script/amount), the signature is produced but the transaction is unconfirmable — while any accounting that credited the `ReceivedOutput` as a deposit now shows funds "received" that are not spendable. The group can then be induced to sign outgoing transactions against this phantom balance, draining real funds to attackers.
2. **Inflated value → invalid spend; deflated value → fee burn.** Because BIP-341 sighashes commit to all prevout amounts, a `value` exceeding the real UTXO value yields an unconfirmable transaction after a full threshold signing round; a `value` below the real UTXO value is rejected by sighash too, but if received via the script-consistent path the delta between real and claimed value also corrupts `fee()`/`needed_fee` accounting (`send.rs:137-141`).

### Impact Explanation
A remote, unprivileged party supplies serialized `ReceivedOutput` bytes claiming an output exists that does not (or with an inflated amount). Serai's bookkeeping can record the deposit as received, and `SignableTransaction`/`TransactionMachine` will happily construct and threshold-sign a transaction spending the fake UTXO. The result is funds reported as received which are not spendable, potential loss of real funds if phantom deposits are converted to real withdrawals, and forced signature rounds producing unbroadcastable transactions. This is the same shape as the referenced incident: attacker-injected "value" (borrowed funds in the flash-loan case, fabricated prevout data here) is treated as real within a single atomic operation before validity can be established.

### Likelihood Explanation
Requires an attacker to reach a code path that feeds untrusted bytes to `ReceivedOutput::read` rather than obtaining `ReceivedOutput`s solely from `Scanner::scan_transaction`/`scan_block`. The struct exposes `read`/`serialize`/`write` precisely so `ReceivedOutput`s can cross trust boundaries (processor↔coordinator, DB reload, peer messages), and no field-level integrity (hash commitment, MAC, or re-derivation via `Scanner`) is enforced. Any consumer that trusts the deserialized value/amount without re-scanning the transaction on-chain is exploitable. Where re-scanning does occur, impact degrades to a wasted signing round / DoS rather than fund loss.

### Recommendation
- Do not trust `ReceivedOutput::read` output as proof of a deposit. Re-validate any deserialized `ReceivedOutput` against the chain: confirm `outpoint` exists, pays `output.script_pubkey`, and carries `output.value` (e.g., re-run `Scanner` over the containing transaction/block and require membership in its result set).
- Bind the fields cryptographically where transport is needed: derive `offset` from `outpoint`/context rather than accepting it as an independent field, or authenticate the whole triple with a keyed MAC so only scanner-produced outputs can round-trip.
- In `SignableTransaction::new`, document that `prevouts` must be chain-verified and consider requiring the caller to supply the block/tx proof enabling local verification.

### Proof of Concept
```rust
use bitcoin::{
  OutPoint, TxOut, Txid, Amount, ScriptBuf,
  consensus::encode::serialize, hashes::Hash,
};
use k256::Scalar;
use serai_bitcoin::wallet::{ReceivedOutput, SignableTransaction, p2tr_script_buf};

// Attacker learns any registered P2TR script_pubkey Q for the group key
// (script_pubkeys are public on-chain / derivable via Scanner).
let group_key_script: ScriptBuf = /* a script Scanner registered for the key */;
let claimed_value: u64 = 10_000_000; // 0.1 BTC that doesn't exist

// Fabricate a ReceivedOutput for a non-existent outpoint paying Q.
// offset = 0 is consistent whenever `group_key_script` is the base-key
// P2TR script; for a registered offset script, copy the real offset.
let mut buf = vec![];
buf.extend(Scalar::ZERO.to_bytes()); // offset
let txout = TxOut {
  value: Amount::from_sat(claimed_value),
  script_pubkey: group_key_script.clone(),
};
buf.extend(serialize(&txout));
let fake_outpoint = OutPoint {
  txid: Txid::from_slice(&[0x41; 32]).unwrap(), // never existed
  vout: 0,
};
buf.extend(serialize(&fake_outpoint));

// Feed to a component deserializing untrusted bytes
let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
assert_eq!(forged.value(), claimed_value);

// multisig() accepts it: p2tr_script_buf(key.offset(0).group_key())
// == group_key_script, so the fake prevout passes the only check.
// SignableTransaction::new counts `claimed_value` toward input_sat,
// and sign() produces shares over Prevouts::All committing to the
// fabricated amounts — a fully-signed yet unspendable "deposit".
```
