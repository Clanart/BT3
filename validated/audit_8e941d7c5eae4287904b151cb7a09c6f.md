### Title
Denial of Service via Unhandled AssertionError When Parsing Malformed CREATE_COIN Puzzle-Hash in Offer/Trade Processing - (File: chia/wallet/util/compute_hints.py)

### Summary
The CVE describes a Wireshark dissector crashing (OOB read/DoS) because it assumed a fixed-format field (a MAC address) without validating its actual shape before reading it. The closest analog in this codebase is `compute_spend_hints_and_additions` in `chia/wallet/util/compute_hints.py`, which assumes the first argument of a `CREATE_COIN` condition returned from running a puzzle is always a CLVM atom (the fixed 32-byte puzzle hash) and enforces this only with a bare `assert`, which is an uncaught, crash-causing exception rather than a handled `ValidationError`.

### Finding Description
`compute_spend_hints_and_additions` runs an untrusted `CoinSpend`'s puzzle/solution and iterates the resulting conditions. For `CREATE_COIN` it does: [1](#0-0) 
`condition.at("rf").atom` returns `None` if the first argument of `CREATE_COIN` is a cons pair (list) instead of an atom — which is fully legal, attacker-controllable CLVM output from a crafted inner puzzle. In that case the bare `assert rf is not None` fires. Unlike the `ValidationError` raised elsewhere in the same function for cost overruns, an `AssertionError` here is not a `ValidationError` and is not caught by callers, so it propagates as an unhandled exception.

This function is invoked on offer/trade spend bundles supplied by an untrusted counterparty via `TradeManager.calculate_tx_records_for_offer`, which is used when validating an incoming offer (`validate=True`) before acceptance: [2](#0-1) 
An offer counterparty fully controls the puzzle reveal/solution of the coins being offered (via `Offer._bundle`), and can construct an inner puzzle whose `CREATE_COIN` condition returns a pair (e.g., `(51 (1 . 2) 100)`) instead of an atom for the puzzle-hash slot. When the receiving wallet calls `calculate_tx_records_for_offer(offer, validate=True)` to compute hints/additions for the offer, `condition.at("rf").atom` is `None`, and the subsequent `assert rf is not None` raises `AssertionError`.

### Impact Explanation
This crash occurs during wallet-side processing of an offer received from another party, before any spend is broadcast or accepted — i.e., it is reachable by any "offer counterparty" as permitted by scope. Because the exception is an `AssertionError` (not a handled `ValidationError`), it is not gracefully converted into a rejected/invalid-offer state; it is a spend-triggered halt of the offer-processing routine in the victim's wallet, satisfying the "spend-triggered transaction-processing halt" impact class allowed by the validation rules. It does not by itself allow unauthorized coin movement, but repeated malicious offers could be used to reliably crash wallet code paths that call this function on attacker-supplied bundles.

### Likelihood Explanation
Likelihood is high for triggering the crash: constructing a spend whose `CREATE_COIN` condition emits a pair instead of an atom for its first argument is trivial in CLVM (e.g., quote a cons cell), requires no special privileges, and only requires that the victim wallet run `calculate_tx_records_for_offer(offer, validate=True)` on the attacker-provided offer bundle, which is a standard step when evaluating/accepting an incoming offer.

### Recommendation
Replace the bare `assert rf is not None` in `compute_spend_hints_and_additions` with a proper `ValidationError`/`Err.INVALID_CONDITION` raise (consistent with the `BLOCK_COST_EXCEEDS_MAX` handling already in the function), and audit `compute_memos_for_spend`/`compute_additions_with_cost` and related helpers for the same "assume atom, crash on non-atom" pattern when processing conditions derived from untrusted puzzle/solution pairs (offers, DL, CAT/NFT flows).

### Proof of Concept
1. Craft a coin whose puzzle, when run with an attacker-chosen solution, returns the condition list `((51 (81 . 73) 100))` — i.e., `CREATE_COIN` whose first argument is the cons pair `(81 . 73)` rather than a 32-byte atom.
2. Package this coin spend into an `Offer` (`chia/wallet/trading/offer.py`) as the offered/requested coin and send it to a victim wallet as a normal offer file.
3. When the victim wallet calls `TradeManager.calculate_tx_records_for_offer(offer, validate=True)` — which internally calls `compute_spend_hints_and_additions(spend)` for each coin spend in the offer bundle — `condition.at("rf").atom` evaluates to `None`, and `assert rf is not None` raises an unhandled `AssertionError`, terminating the offer-evaluation call path. def compute_spend_hints_and_additions(
    cs: CoinSpend,
    *,
    max_cost: int = DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM,
) -> tuple[dict[bytes32, HintedCoin], int]:
    cost, result_program = run_with_cost(cs.puzzle_reveal, max_cost, cs.solution)

    hinted_coins: dict[bytes32, HintedCoin] = {}
    for condition in result_program.as_iter():
        if cost > max_cost:
            raise ValidationError(Err.BLOCK_COST_EXCEEDS_MAX, "compute_spend_hints_and_additions() for CoinSpend")
        atoms = condition.as_iter()
        op = next(atoms).atom
        if op in {
            ConditionOpcode.AGG_SIG_PARENT,
            ConditionOpcode.AGG_SIG_PUZZLE,
            ConditionOpcode.AGG_SIG_AMOUNT,
            ConditionOpcode.AGG_SIG_PUZZLE_AMOUNT,
            ConditionOpcode.AGG_SIG_PARENT_AMOUNT,
            ConditionOpcode.AGG_SIG_PARENT_PUZZLE,
            ConditionOpcode.AGG_SIG_UNSAFE,
            ConditionOpcode.AGG_SIG_ME,
        }:
            cost += ConditionCost.AGG_SIG.value
            continue
        if op != ConditionOpcode.CREATE_COIN.value:
            continue
        cost += ConditionCost.CREATE_COIN.value

        rf = condition.at("rf").atom
        assert rf is not None

        coin: Coin = Coin(cs.coin.name(), bytes32(rf), uint64(condition.at("rrf").as_int()))
