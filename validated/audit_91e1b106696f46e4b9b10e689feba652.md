## Analog Found

### Title
Delisting a state machine from `HostParams.stateMachines` never clears `_latestStateMachineHeight`, so consensus proofs and requests from a delisted chain remain permanently accepted - ([File: evm/src/core/EvmHost.sol])

### Summary
The external report's core defect is: a whitelist-off action (`setWhitelistedRouters(..., false)`) does not reset the derived state (`routerTypes`, `swapInfos`) that gates a privileged code path, so the delisted entity remains fully functional. The exact same pattern exists in `EvmHost.updateHostParamsInternal()`: removing a state machine from `HostParams.stateMachines` never clears `_latestStateMachineHeight[id]`, which is the actual gate used by `HandlerV2.handleConsensus()` to decide whether new state commitments may be stored for that chain.

### Finding Description
`EvmHost.updateHostParamsInternal()` only ever *adds* entries to `_latestStateMachineHeight`: [1](#0-0) 

There is no corresponding removal/reset when a state machine id present in the *old* `_hostParams.stateMachines` is absent from the *new* `params.stateMachines` supplied via governance (`updateHostParams`, only callable by `hostManager`/cross-chain governance). The getter itself documents the intended semantics: [2](#0-1) 

i.e. `0` is supposed to mean "unsupported". But delisting a chain from `stateMachines` never resets its entry back to `0` — the value simply stays at whatever height it last reached.

That stale, non-zero value is exactly the gate `HandlerV2.handleConsensus()` uses to decide whether to persist a *new* state commitment for an intermediate state during a consensus update: [3](#0-2) 

Since `latestHeight != 0` remains true forever for any chain that was ever whitelisted, anyone can continue to submit legitimate consensus proofs (consensus submission is permissionless — `handleConsensus` has no source-restriction beyond `notFrozen`) and the host will keep storing fresh `stateMachineCommitment` entries for a chain that governance explicitly removed from `stateMachines`.

Downstream, `handlePostRequests` never re-checks the `stateMachines` whitelist array at all — it only checks that a stored commitment exists at the claimed height: [4](#0-3) 

So once a delisted chain's commitment is (still) refreshable, requests originating from that "removed" state machine continue to be accepted and dispatched to local modules as if it were still trusted.

### Impact Explanation
Removing a state machine from `HostParams.stateMachines` is the mechanism by which cross-chain governance revokes trust in a chain (e.g., after a compromise, a chain being deprecated, or a consensus-client migration). Because the derived `_latestStateMachineHeight` gate is never cleared, that revocation is silently ineffective: the delisted chain's consensus updates and post/get requests continue to be accepted and processed by `EvmHost`/`HandlerV2`, i.e. false remote state remains trusted and unauthorized execution of requests from an explicitly de-trusted chain remains possible — directly matching the bounty's "false proof/state acceptance" and "unauthorized transaction or execution" categories.

### Likelihood Explanation
No privileged/malicious actor is required beyond the normal, expected governance action of delisting a chain (a routine host-management operation, not an attack). Submission of consensus proofs and requests is permissionless by design (`handleConsensus`/`handlePostRequests` have no caller restriction other than `notFrozen`), so any relayer/user can keep the "removed" chain's state alive indefinitely after delisting, defeating the intent of the governance action.

### Recommendation
In `updateHostParamsInternal`, compute the set difference between the previous `_hostParams.stateMachines` and the new `params.stateMachines`, and explicitly reset `_latestStateMachineHeight[id] = 0` (and ideally clear any stored `_stateCommitments`/`_stateCommitmentsUpdateTime` for that id, subject to migration considerations) for every id removed from the whitelist, mirroring the approach already used to add newly-whitelisted ids.

### Proof of Concept
1. Governance calls `updateHostParams` with `stateMachines = [2000]`; `_latestStateMachineHeight[2000]` becomes `1` (per `testCanAddwhitelistedStateMachines` in `evm/tests/foundry/EvmHostTest.sol`).
2. A relayer submits `handleConsensus` proofs over time, advancing `_latestStateMachineHeight[2000]` and storing `stateMachineCommitment` entries for chain `2000`.
3. Governance calls `updateHostParams` again with `stateMachines = [2001]` (removing `2000`) to revoke trust in chain `2000`.
4. `_latestStateMachineHeight[2000]` is left untouched (non-zero) because `updateHostParamsInternal` only adds entries, never removes them.
5. A relayer submits another `handleConsensus` proof containing an `IntermediateState` for `stateMachineId = 2000`; since `latestHeight != 0`, `host.storeStateMachineCommitment` is executed and a new commitment is stored for the "removed" chain.
6. Requests from chain `2000` can then be delivered via `handlePostRequests`, since it only checks `stateMachineCommitment(...).overlayRoot != 0`, with no re-check against the current `stateMachines` whitelist.
