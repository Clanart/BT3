### Title
Cross-transaction metadata overwrite misattributes Bitcoin deposits and can redirect refunds - ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
`Bitcoin::get_outputs` accumulates `outputs` across the entire block but applies the current transaction’s presumed origin and Serai instruction data to every previously accumulated output. An attacker who places any later transaction in the same block can overwrite an earlier deposit’s `data` and `presumed_origin`, causing its instruction to be dropped or replaced and potentially refunding the victim’s funds to the attacker.

### Finding Description
`get_outputs` appends every matching output to a block-wide `outputs` vector. After processing each transaction, if that vector is non-empty, it derives `presumed_origin` from the **current transaction’s first input**, extracts the **current transaction’s** Serai data, then iterates over all accumulated outputs rather than only outputs produced by the current transaction. [1](#0-0) 

Consequently, a later transaction that does not pay Serai at all still triggers the metadata-population path whenever an earlier transaction deposited to Serai. Its first input becomes the earlier deposit’s `presumed_origin`, and its data replaces the earlier deposit’s `data`. [2](#0-1) 

The corrupted fields are security-relevant: `instruction_from_output` reads `output.data()` as SCALE-encoded `Shorthand`, converts it to a `RefundableInInstruction`, and uses `instruction.origin.or(presumed_origin)` as the refund origin. Invalid or overwritten data causes the instruction to be skipped while retaining the corrupted presumed origin. [3](#0-2) 

### Impact Explanation
A victim can broadcast a Bitcoin deposit containing a valid Serai instruction. An attacker can arrange for a later ordinary Bitcoin transaction—one which does not pay Serai—to appear in the same block. When the later transaction is processed, `get_outputs` overwrites the victim output’s instruction data with the attacker transaction’s data and sets its presumed origin to the attacker-controlled source address.

If the overwritten data is empty or invalid, the original instruction is discarded. The attacker-controlled `presumed_origin` can then be used as the refund destination for funds the attacker did not deposit. This maps directly to the reported class: a later auxiliary result incorrectly overwrites state belonging to an earlier operation, leaving user funds unavailable for their intended action and potentially directing them elsewhere.

### Likelihood Explanation
The attacker only needs to get a transaction confirmed after the victim’s transaction within the same block. No validator compromise, malformed curve input, leaked key, or invalid Bitcoin transaction is required. Bitcoin transactions are public in the mempool, so an attacker can observe a qualifying deposit and attempt to position a following transaction. The exact block ordering depends on miner inclusion, but the attack requires only ordinary public transaction submission and no cooperation from the victim.

### Recommendation
Process transaction metadata locally rather than applying it to the block-wide output vector. For each transaction, populate only the outputs scanned from that transaction.

A regression test should include two transactions in one block: the first paying a Serai external output with valid instruction data, and the second unrelated transaction spending an attacker-controlled input. The first output must retain its original data and origin.
