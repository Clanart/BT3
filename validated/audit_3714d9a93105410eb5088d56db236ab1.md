### Title
Unrecovered panic in CW1155 wasm-to-EVM event translation crashes block execution on malformed `token_ids`/`amounts` - (File: app/receipt.go)

### Summary
The matrix-js-sdk advisory describes a logic error where improperly formed (attacker/adversary-supplied) event data disrupts the SDK's normal processing pipeline, causing availability problems. `sei-chain` has an analogous "malformed event disrupts processing" pattern in the wasm→EVM synthetic-log translation pipeline, but with more severe consequences: a deterministic, unrecovered Go panic that halts block execution.

### Finding Description
`app.AddCosmosEventsToEVMReceiptIfApplicable` in `app/receipt.go` scans every wasm module event emitted during `DeliverTx`, and for contracts that have a registered CW1155↔ERC1155 pointer, calls `translateCW1155Event`: [1](#0-0) 

`translateCW1155Event` builds `Action` structs from event attributes via `GetActionsFromWasmEvent`, which parses `token_ids`/`amounts` CSV strings into `[]*big.Int` using `safeBigIntFromString`, a helper that **returns `nil`** for any entry that fails to parse: [2](#0-1) [3](#0-2) 

For the `transfer_batch`/`mint_batch`/`burn_batch` case, the code only checks that the slices are non-empty — it does **not** check that individual elements are non-nil — before packing them into ABI-encoded log data: [4](#0-3) 

Contrast this with `translateCW20Event`, which explicitly wraps its logic in a `recover()` specifically because malformed wasm event data was recognized as a crash risk: [5](#0-4) 

`translateCW721Event` and `translateCW1155Event` have **no equivalent `recover()`**. If a wasm contract that is registered as the underlying token for a CW1155→ERC1155 pointer emits a `wasm` event with `action=transfer_batch` (or `mint_batch`/`burn_batch`) and a `token_ids` or `amounts` attribute containing a mix of valid and invalid numeric substrings (e.g. `"1,notanumber,3"`), one or more elements of `action.TokenIds`/`action.Amounts` will be `nil`. These nil `*big.Int` values are then passed to `cw1155.GetParsedABI().Events["TransferBatch"].Inputs.NonIndexed().Pack(...)`, which invokes go-ethereum ABI packing routines that call methods on the `*big.Int` values (e.g. bit-length/sign checks) and will panic on a nil pointer dereference.

### Impact Explanation
Because `AddCosmosEventsToEVMReceiptIfApplicable` runs as part of the deterministic `DeliverTx`/`FinalizeBlock` hook path (`app/receipt.go`), a panic here occurs identically on every validator processing the same block/transaction. Unlike a normal Cosmos SDK message handler panic (which is typically recovered per-message by the baseapp runTx recovery middleware), this hook path lacks a matching `recover()` in the CW1155/CW721 branches, unlike the CW20 branch which was explicitly hardened. If the panic escapes any outer recovery boundary, it results in a crash of the node process during block finalization — a consensus-critical, chain-wide halt, since every validator hits the same deterministic panic on the same transaction. This matches the "validator halt" impact category.

### Likelihood Explanation
Any account that can deploy a CosmWasm contract and register it as the backing contract for a CW1155→ERC1155 pointer can fully control the wasm events it emits, including crafting `token_ids`/`amounts` attribute values with invalid numeric substrings. This requires only standard CosmWasm deployment/contract-execution privileges plus pointer registration (a permissionless, user-facing EVM/CW bridge operation per `x/evm/AGENTS.md`'s "Pointer Contracts" description), making the trigger reachable from a single, unprivileged submitted transaction.

I was not able to fully confirm within the available context (a) whether the outer `DeliverTx`/`FinalizeBlock` call stack has a higher-level `recover()` that would catch this panic before it crashes the process (I found `app/legacyabci/recovery.go`, which likely wraps some paths, but did not verify it covers this specific hook invocation), and (b) the exact permission model for CW1155 pointer registration (whether it validates the underlying contract's interface before allowing registration). These should be verified before treating this as conclusively exploitable to a full halt versus a per-transaction failure recovered elsewhere.

### Recommendation
- Add nil-element validation for `action.TokenIds` and `action.Amounts` in `translateCW1155Event` (and equivalent tokenId nil-checks already present should be extended to reject/skip batches containing any nil element) before calling `dataArgs.Pack(...)`.
- Add a `recover()` guard around `translateCW721Event` and `translateCW1155Event`, mirroring the existing guard in `translateCW20Event`, so malformed synthetic wasm events degrade gracefully (e.g., by skipping the log) instead of crashing block processing.
- Audit `GetActionsFromWasmEvent`/`safeBigIntFromString` usages more broadly for other unchecked nil `*big.Int` consumers.

### Proof of Concept
1. Deploy a CosmWasm contract and register it via `MsgRegisterPointer` as the backing contract for a CW1155→ERC1155 pointer.
2. Have the contract, on any execute call, emit a wasm event with attributes `action=transfer_batch`, `sender=<addr>`, `token_ids="1,notanumber,3"`, `amounts="1,1,1"`.
3. Submit a transaction invoking this contract method.
4. During `DeliverTx`, `AddCosmosEventsToEVMReceiptIfApplicable` → `translateCW1155Event` parses `token_ids` into `[]*big.Int{1, nil, 3}` and calls `dataArgs.Pack(action.TokenIds, action.Amounts)`, panicking on the nil element with no local `recover()`, on every validator processing the block.
