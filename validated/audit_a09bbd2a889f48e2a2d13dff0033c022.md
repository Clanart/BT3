### Title
`SignableTransaction::new` calculates the fee on a weight that omits the committed OP_RETURN output - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
In `SignableTransaction::new`, the OP_RETURN output carrying `data` is pushed onto `tx_outs` before the fee is calculated, but `calculate_weight_vbytes` builds its estimation transaction only from `payments` (and later `change`). The output used to derive `needed_fee` therefore has strictly less weight than the transaction actually signed, so the fee is charged on a smaller base than the real transaction - the same bug class as the PredictDotLoan finding, where the protocol fee was applied to `debt` (net) instead of the gross fulfilled amount.

### Finding Description
`SignableTransaction::new` constructs the real output set first:

- `networks/bitcoin/src/wallet/send.rs:187-202` builds `tx_outs` from `payments` and unconditionally appends the OP_RETURN output when `data` is `Some`.

It then computes the fee on a *different*, smaller transaction:

- `networks/bitcoin/src/wallet/send.rs:204-206` calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` and sets `needed_fee = fee_per_vbyte * vbytes`.
- `networks/bitcoin/src/wallet/send.rs:67-99` shows `calculate_weight_vbytes` materializes a dummy `Transaction` whose `output` vector contains only the payments (plus an optional change output). The `data` argument of `SignableTransaction::new` is never passed in, so the OP_RETURN bytes are absent from the weight/vbytes estimate.
- The same omission occurs on the change path: `networks/bitcoin/src/wallet/send.rs:225-232` recomputes `fee_with_change` from `payments` plus `change`, still excluding the data output, and computes the change amount as `input_sat - (payment_sat + fee_with_change)`.

The result mirrors the external report: the fee is proportional to a base that is smaller than the amount it is actually charged on. With `data` present, every vbyte occupied by the OP_RETURN output is unaccounted for in `needed_fee`.

### Impact Explanation
Two concrete consequences:

1. When a change output exists, the change value is `input_sat - payment_sat - fee_with_change`, so the missing data-output weight is folded into the change, and the *effective* fee rate paid is `needed_fee / actual_vsize < fee_per_vbyte`. The transaction is signed and broadcast paying a lower feerate than the caller requested.
2. The minimum-feerate guard at `send.rs:211` compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes(estimated) / 1000`. Because the estimated vbytes understate the true size, a transaction can pass this check while its actual feerate is below the relay minimum, producing a signed transaction that will not propagate/confirm - the signed inputs are effectively stuck until a replacement is constructed.

For a fee rate of `r` and an OP_RETURN of ~`10 + data_len` bytes (output base + pushdata), the underpayment is `r * (10 + len + output_size)` sats; with up to 80 bytes of data this is ~`r * ~120` sats of undercharged weight per transaction, and the feerate shortfall grows with the configured `fee_per_vbyte` - directly proportional to the fee, exactly as in the reference bug.

### Likelihood Explanation
Medium. The defect triggers whenever `SignableTransaction::new` is invoked with `data.is_some()`. The `data` parameter is a documented, length-checked (`TooMuchData` at `send.rs:171`) feature of this API - the transaction explicitly commits to the OP_RETURN output, so this is not integrator misuse; the function simply fails to price what it constructs. Within this repository the sole production caller (`processor/src/networks/bitcoin.rs:446-451`) currently passes `None`, which limits present-day exploitability, but the wallet is a standalone library whose other callers (rotation/anchored-output flows that embed data) would silently produce under-priced transactions.

### Recommendation
Include the data output in the weight estimation: pass a representation of the OP_RETURN output (or the assembled `tx_outs`) into `calculate_weight_vbytes` so that `vbytes` and `vbytes_with_change` reflect the true transaction. Equivalently, build the full `tx_outs` vector first and derive weight from it, rather than reconstructing a partial output set inside the estimator. Alternatively, remove the `data` parameter if no caller requires it.

### Proof of Concept
```rust
// Conceptual: in networks/bitcoin/tests/wallet.rs, modify test_send to pass
// data = Some(vec![0xAA; 80]) and a change output.
let tx = SignableTransaction::new(
  vec![output.clone()],
  &payments,
  Some(change_addr.clone()),
  Some(vec![0xAA; 80]), // OP_RETURN ~90+ bytes incl. base
  FEE,
).unwrap();
let signed = sign(&keys, &tx);
// tx.needed_fee() == FEE * vsize_without_op_return
// signed.vsize() > that estimate, so
// tx.fee() / signed.vsize() < FEE  -> effective feerate below requested rate
assert!(tx.fee() < FEE * signed.vsize() as u64);
```
The signed transaction includes the OP_RETURN output (`tx_outs.push` at `send.rs:194-201`), while `needed_fee` was computed from a transaction that does not (`send.rs:204-206`, `send.rs:225-227`), so `fee() / actual_vsize < fee_per_vbyte`.
