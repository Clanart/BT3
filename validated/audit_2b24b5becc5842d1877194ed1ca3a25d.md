### Title
Contract instantiation can be permanently DoS'd by pre-funding the deterministic next contract address - ([File: sei-wasmd/x/wasm/keeper/keeper.go])

### Summary
The CosmWasm `instantiate` flow in the sei-wasmd fork derives the new contract's account address deterministically from the code ID and a monotonically-increasing, publicly-readable instance sequence number, then aborts instantiation if an account already exists at that address. Because both the code ID and the current sequence value are queryable on-chain, any unprivileged account can predict the exact address the next `MsgInstantiateContract` (or `Instantiate2`/CW-pointer/EVM `wasmd` precompile `instantiate`) call will produce and pre-create a `BaseAccount` there (e.g. via a plain `bank send`) before the legitimate instantiate transaction lands, causing it to fail with `ErrAccountExists`. This mirrors the reported `pump-science` bug class in which an attacker front-runs the creation of a deterministically-derived account to cause the legitimate creation instruction to fail (DoS).

### Finding Description
`Keeper.instantiate` computes the contract address up front and immediately checks account existence: [1](#0-0) 

`generateContractAddress` derives the address from `codeID` and the module's global auto-increment instance sequence (`BuildContractAddress(codeID, instanceID)`), which is confirmed deterministic/testable: [2](#0-1) 

Both the `codeID` (public, since anyone can query stored code or has just uploaded it) and the instance sequence counter are ordinary, non-secret module state incremented on every successful instantiation across the whole chain. An attacker can:
1. Observe (or predict) the current global instance sequence value.
2. Compute `BuildContractAddress(codeID, nextInstanceID)` for the `codeID` a victim intends to instantiate.
3. Submit an ordinary `bank send` (or any message that creates a `BaseAccount`, e.g. via `AccountKeeper.SetAccount`/`NewAccountWithAddress` side effects) to that predicted address before the victim's instantiate transaction is included.
4. When the victim's `MsgInstantiateContract` executes, `k.accountKeeper.GetAccount(ctx, contractAddress)` returns the attacker's pre-created account, and the instantiate call reverts with `ErrAccountExists`, exactly as in the referenced report where the pre-created `lockEscrow` PDA caused `create_lock_escrow` to fail.

This is reachable through the EVM `wasmd` precompile's `instantiate` method as well, since it forwards directly to `p.wasmdKeeper.Instantiate`: [3](#0-2) 

and through the native `MsgInstantiateContract` handler: [4](#0-3) 

Because the sequence counter is global (shared by all code IDs), the attacker only needs to win a single race against the victim's transaction inclusion — repeatable at negligible cost (one bank-send tx) each time the victim retries, since the victim's retry lands at the next sequence value which the attacker can again predict and pre-empt.

### Impact Explanation
A malicious, unprivileged actor can permanently and repeatedly block instantiation of any specific CosmWasm contract (including CW20/CW721 contracts used to back `AddCW20Pointer`/`AddCW721Pointer`, DeFi/DEX contracts, or any dApp's CosmWasm deployment) with a trivial bank-send transaction. This is a griefing/DoS vector against a core reachable operation (contract deployment via a standard Cosmos message or the EVM `wasmd` precompile), not merely a wasted-gas inconvenience: because the attacker controls exactly which address gets squatted and can re-squat on every retry, the victim cannot get their contract instantiated at all without a keeper-level fix, resulting in a persistent denial of service for CosmWasm deployment on the affected code ID.

### Likelihood Explanation
Likelihood is high: the sequence counter and code ID are both public on-chain state, requiring no special access — any wallet with minimal funds for a `bank send` (or any account-creating message) can execute the attack. It requires only observing mempool/recent block activity (or simply spamming pre-creation for a range of near-future sequence numbers) to win the race, which is a well-known and cheap front-running pattern on any chain with observable pending transactions.

### Recommendation
In `Keeper.instantiate` (`sei-wasmd/x/wasm/keeper/keeper.go`), do not treat a pre-existing account at the predicted contract address as a hard failure. Instead:
- If an account exists at `contractAddress` but is a plain `BaseAccount` with no public key set and zero locked/vesting balance (i.e., clearly not a real user account, analogous to the direct-cast reuse logic already used in `AssociationHelper.AssociateAddresses`), allow instantiation to proceed and overwrite/adopt it as the contract account.
- Alternatively, derive the contract address using a scheme that incorporates a value unpredictable to third parties (e.g., include the sender's account number/sequence or a creator-supplied salt combined with a value only known at execution time), rather than a purely deterministic public sequence number.
- At minimum, add an explicit test verifying instantiation succeeds even if funds were sent to the predicted address beforehand (similar to the existing "reuse empty cast account" test pattern used for address association).

### Proof of Concept
1. Query the current global wasm instance sequence and note `codeID` of the target contract to be instantiated (e.g. the victim announces or is expected to instantiate code `X` next).
2. Compute `predictedAddr = BuildContractAddress(codeID, currentSequence+1)` using the same derivation as `sei-wasmd/x/wasm/keeper/keeper_test.go` `TestBuildContractAddress`.
3. Submit a `bank send` of a minimal amount to `predictedAddr`, creating a `BaseAccount` there before the victim's `MsgInstantiateContract` is included.
4. When the victim's instantiate transaction executes, `k.accountKeeper.GetAccount(ctx, contractAddress)` at `sei-wasmd/x/wasm/keeper/keeper.go:300-303` returns the attacker's account, and the call returns `types.ErrAccountExists`, aborting the victim's deployment.
5. Repeat for any subsequent retry, since the sequence counter and target `codeID` remain publicly predictable.

```go
func (m msgServer) InstantiateContract(goCtx context.Context, msg *types.MsgInstantiateContract) (*types.MsgInstantiateContractResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	senderAddr, err := sdk.AccAddressFromBech32(msg.Sender)
	if err != nil {
		return nil, sdkerrors.Wrap(err, "sender")
	}
	var adminAddr sdk.AccAddress
	if msg.Admin != "" {
		if adminAddr, err = sdk.AccAddressFromBech32(msg.Admin); err != nil {
			return nil, sdkerrors.Wrap(err, "admin")
		}
	}

	ctx.EventManager().EmitEvent(sdk.NewEvent(
		sdk.EventTypeMessage,
		sdk.NewAttribute(sdk.AttributeKeyModule, types.ModuleName),
		sdk.NewAttribute(sdk.AttributeKeySender, msg.Sender),
	))

	contractAddr, data, err := m.keeper.Instantiate(ctx, msg.CodeID, senderAddr, adminAddr, msg.Msg, msg.Label, msg.Funds)
	if err != nil {
		return nil, err
	}

	return &types.MsgInstantiateContractResponse{
		Address: contractAddr.String(),
		Data:    data,
	}, nil
}
```
