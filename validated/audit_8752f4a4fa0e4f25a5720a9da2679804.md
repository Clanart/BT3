## Title
Secp256k1 precompile accepts non-canonical (malleable) ECDSA signatures, allowing a signature-hash preimage to be forged for the same authorized message - (File: `precompiles/src/secp256k1.rs`)

### Summary
Agave's built-in `secp256k1` precompile (`precompiles/src/secp256k1.rs`), which every unprivileged on-chain program relies on to authenticate secp256k1/Ethereum-style signatures, does not reject non-canonical (high-S) ECDSA signatures. This is the exact bug class described in the external report: a validly-verifying signature is not unique per signed message, so any downstream logic that uses the *signature bytes* (or a hash of them) as a "seen/used" identifier for replay protection can be bypassed by flipping the S value (and recovery id) to produce a second, distinct byte sequence that verifies successfully for the identical message and public key.

### Finding Description
`precompiles/src/secp256k1::verify` parses `(r, s, recovery_id)` from the instruction data and recovers a public key/eth-address from it, but performs no check that `s` is in the canonical low-half of the curve order: [1](#0-0) 

Compare this with the sibling `secp256r1` precompile, which explicitly enforces the canonical low-S range before accepting a signature: [2](#0-1) 

The lack of this check in the secp256k1 path is not accidental oversight caught only in theory — it is explicitly demonstrated (and accepted, via `.unwrap()`) by the crate's own test, which flips the `s` value and recovery id and shows both signatures verify successfully for the same message/eth-address: [3](#0-2) 

The Ed25519 precompile, by contrast, uses `ed25519_dalek`'s `verify_strict`, which is malleability-resistant: [4](#0-3) 

Because the secp256k1 precompile is a first-class primitive exposed to every unprivileged Solana program (via the `secp256k1_program` builtin, invoked as an ordinary instruction in a transaction, processed by `agave_precompiles::secp256k1::verify` from `precompiles/src/lib.rs`), any program that treats "verified secp256k1 signature bytes" as a unique, non-malleable credential — e.g., hashing `(r, s, recovery_id)` to mark an authorization "used" instead of hashing the signed message/nonce — inherits the malleability weakness directly from the platform's precompile, exactly as described in the external report for the zNS/zAuction Solidity contracts (`hashOfSig`/`randUsed` patterns).

### Impact Explanation
An attacker who observes one valid secp256k1-authenticated instruction (e.g., an authorization/bid/claim message signed off-chain and submitted with the secp256k1 program) can derive a second, bit-for-bit different but equally valid signature encoding for the exact same message and signer by negating `s` and flipping the recovery id. If a program built on top of this precompile keys its replay-protection or "already processed" tracking off the raw signature bytes (or their hash) rather than off the signed message/nonce, the attacker can resubmit the semantically identical authorization under the different signature encoding and have it accepted again, defeating the intended single-use guarantee (e.g., re-executing a privileged action, double-claiming a payout, or replaying a bid). This is a forged/duplicated acceptance of an authorization due to signature malleability at the precompile layer that all unprivileged callers depend on.

### Likelihood Explanation
Likelihood is moderate-to-high for any downstream unprivileged program that uses the secp256k1 precompile's guarantees for anti-replay by hashing signature bytes rather than the signed payload — this is a commonly seen (and exactly what the external report flags as bad practice) pattern, and Agave's own precompile does nothing to prevent it, unlike its secp256r1 sibling which was hardened against the same class of issue. No special privileges are required; any user can craft the malleated instruction data offline and submit it as an ordinary transaction.

### Recommendation
Add a canonical low-S (and/or low-order recovery-id) check to `precompiles/src/secp256k1::verify`, mirroring the check already present in `precompiles/src/secp256r1.rs` (reject `s > order/2`), so that only one canonical byte encoding is accepted per valid `(message, pubkey)` pair. This removes the malleability primitive at the platform level so that any unprivileged program built on top of the secp256k1 precompile — even ones that incorrectly key anti-replay off signature bytes — is not exposed to forged-signature replay.

### Proof of Concept
The existing unit test in the codebase is itself a proof of concept that the malleated signature is accepted: [5](#0-4) 
Sign a message once, then compute `alt_signature.s = -signature.s` and `alt_recovery_id = recovery_id ^ 1`. Both `(signature, recovery_id)` and `(alt_signature, alt_recovery_id)` pass `agave_precompiles::secp256k1::verify` for the identical `message` and `eth_address`, yielding two distinct valid `(r, s, v)` byte sequences — and therefore two distinct hashes of those bytes — for the same authorization.

    #[test]
    fn test_malleability() {
        agave_logger::setup();

        let secret_bytes: [u8; 32] = rand::random();
        let secret_key = libsecp256k1::SecretKey::parse(&secret_bytes).unwrap();
        let public_key = libsecp256k1::PublicKey::from_secret_key(&secret_key);
        let eth_address = eth_address_from_pubkey(&public_key.serialize()[1..].try_into().unwrap());

        let message = b"hello";
        let message_hash = {
            let mut hasher = keccak::Hasher::default();
            hasher.hash(message);
            hasher.result()
        };

        let secp_message = libsecp256k1::Message::parse(message_hash.as_bytes());
        let (signature, recovery_id) = libsecp256k1::sign(&secp_message, &secret_key);

        // Flip the S value in the signature to make a different but valid signature.
        let mut alt_signature = signature;
        alt_signature.s = -alt_signature.s;
        let alt_recovery_id = libsecp256k1::RecoveryId::parse(recovery_id.serialize() ^ 1).unwrap();

        let mut data: Vec<u8> = vec![];
        let mut both_offsets = vec![];

        // Verify both signatures of the same message.
        let sigs = [(signature, recovery_id), (alt_signature, alt_recovery_id)];
        for (signature, recovery_id) in sigs.iter() {
            let signature_offset = data.len();
            data.extend(signature.serialize());
            data.push(recovery_id.serialize());
            let eth_address_offset = data.len();
            data.extend(eth_address);
            let message_data_offset = data.len();
            data.extend(message);

            let data_start = 1 + SIGNATURE_OFFSETS_SERIALIZED_SIZE * 2;

            let offsets = SecpSignatureOffsets {
                signature_offset: (signature_offset + data_start) as u16,
                signature_instruction_index: 0,
                eth_address_offset: (eth_address_offset + data_start) as u16,
                eth_address_instruction_index: 0,
                message_data_offset: (message_data_offset + data_start) as u16,
                message_data_size: message.len() as u16,
                message_instruction_index: 0,
            };

            both_offsets.push(offsets);
        }

        let mut instruction_data: Vec<u8> = vec![2];

        for offsets in both_offsets {
            let offsets = bincode::serialize(&offsets).unwrap();
            instruction_data.extend(offsets);
        }

        instruction_data.extend(data);

        test_verify_with_alignment(
            verify,
            &instruction_data,
            &[&instruction_data],
            &FeatureSet::all_enabled(),
        )
        .unwrap();
    }
