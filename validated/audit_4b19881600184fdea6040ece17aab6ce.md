## Analysis Summary

Confirmed vulnerability: `EvmHost.dispatchIncoming(GetResponse memory response, address relayer)` pays the relayer fee out of `_requestCommitments[commitment]` but never deletes that mapping entry, while every sibling code path (`dispatchTimeOut(GetRequestTimeout)`, `dispatchTimeOut(PostRequestTimeout)`) explicitly deletes `_requestCommitments[commitment]` as "replay protection" before acting. This asymmetry allows the same escrowed fee to be paid out twice for one GET request: once to the relayer on successful response delivery, and again to the original payer if a `GetRequestTimeout` is later proven for the same commitment (since `meta.sender != address(0)` still holds).

### Title
Double payment of GET request relayer fee due to missing `_requestCommitments` cleanup - (File: `evm/src/core/EvmHost.sol`)

### Summary
`dispatch(DispatchGet)` escrows the relayer fee in `_requestCommitments[commitment]` [1](#0-0) . On successful delivery, `dispatchIncoming(GetResponse, relayer)` reads `_requestCommitments[commitment].fee` and pays it to the relayer, but never deletes the entry [2](#0-1) . Every other consumer of this same mapping (`dispatchTimeOut(GetRequestTimeout)`, `dispatchTimeOut(PostRequestTimeout)`) treats reading-then-acting on it as requiring an upfront delete for "replay protection" [3](#0-2) [4](#0-3) . Because `dispatchIncoming(GetResponse,...)` skips this, the fee metadata (`sender`, `fee`) remains fully intact after the response has already been paid out.

### Finding Description
The GET-request lifecycle on `EvmHost` is:
1. `dispatch(DispatchGet)` stores `_requestCommitments[commitment] = FeeMetadata({sender: msg.sender, fee: get.fee})` [5](#0-4) .
2. On response delivery, `HandlerV2.handleGetResponses` checks `host.responseReceipts(...)` for duplicates (a *different* mapping, `_responseReceipts`) and calls `host.dispatchIncoming(leaf.response, relayer)` [6](#0-5) .
3. `dispatchIncoming(GetResponse,...)` sets `_responseReceipts[commitment]` and, on success, pays `_requestCommitments[commitment].fee` to `relayer` — but leaves `_requestCommitments[commitment]` populated [7](#0-6) .
4. Separately, `HandlerV2.handleGetRequestTimeouts` allows a GET request to be timed out by proving *non-membership* of a response-receipt entry in a proven Hyperbridge state root at some height, and only checks `host.requestCommitments(commitment).sender != address(0)` as its "known request" guard [8](#0-7) . Since step 3 never clears `_requestCommitments[commitment]`, this guard still passes even after the response was already delivered and paid.
5. `dispatchTimeOut(GetRequestTimeout,...)` then refunds `meta.fee` a second time — to `meta.sender` — from the host's fee-token balance [3](#0-2) .

The result: the exact same escrowed fee amount for one GET request commitment can leave the host contract twice — once as relayer payment, once as "timeout" payer refund — a double-settlement of a single escrowed value, funded entirely from `EvmHost`'s feeToken balance (which is shared custody for all pending requests/responses across the host).

### Impact Explanation
This is direct loss of protocol/host funds: the `feeToken()` balance held by `EvmHost` backs every pending request/response on that host. A double payout for one commitment drains funds that should remain reserved for other pending requests' fees/refunds, degrading solvency of the escrow and potentially causing legitimate future refunds/payouts to fail (insufficient balance) or be paid from other users' funds — a fund-loss / double-claim class matching the bounty's explicit "double-claim/double-settlement" impact category.

### Likelihood Explanation
Exploitability depends on being able to submit a valid non-membership proof for `RESPONSE_RECEIPTS_STORAGE_PREFIX+commitment` at a Hyperbridge state height where `state.timestamp` has already passed the request's `timeoutTimestamp`, *after* the corresponding `GetResponse` was already delivered and paid on the EVM host. Whether such a height (pre-recording-of-response-on-Hyperbridge but post-timeout-deadline) is reliably obtainable depends on Hyperbridge's coprocessor-side response-recording timing relative to the timeout deadline — a detail this analysis could not fully verify from the EVM/Rust code alone (it depends on `pallet-ismp`/coprocessor internals not indexed here). Regardless of the exact timing window's width, the root cause — `dispatchIncoming(GetResponse,...)` never clearing `_requestCommitments[commitment]` — is an unconditional code defect present on every successful GET response, and is the exact structural counterpart of the reference bug (a fee-accounting code path silently omitting state necessary to prevent double payment).

### Recommendation
In `EvmHost.dispatchIncoming(GetResponse memory response, address relayer)`, delete `_requestCommitments[commitment]` immediately after (or as part of) paying the relayer fee, mirroring the pattern used in `dispatchTimeOut(GetRequestTimeout)` and `dispatchTimeOut(PostRequestTimeout)`. This ensures a subsequently-submitted timeout proof for the same commitment fails the `meta.sender == address(0)` / `UnknownMessage` guard in `HandlerV2.handleGetRequestTimeouts`, preventing double payment.

### Proof of Concept
Conceptual sequence (verification of exact timing constraints requires the pallet-ismp/coprocessor source, which was not available in this scan):
1. User calls `dispatch(DispatchGet)` on `EvmHost`, escrowing `fee` in `_requestCommitments[commitment]` [9](#0-8) .
2. A relayer legitimately delivers the response via `HandlerV2.handleGetResponses` → `EvmHost.dispatchIncoming(GetResponse,...)`, which pays `fee` to the relayer but leaves `_requestCommitments[commitment]` untouched [10](#0-9) .
3. Any party constructs a state-trie non-membership proof for `RESPONSE_RECEIPTS_STORAGE_PREFIX+commitment` at a Hyperbridge height whose `state.timestamp >= request.timeout()`, and calls `HandlerV2.handleGetRequestTimeouts` [11](#0-10) .
4. Because `host.requestCommitments(commitment).sender != address(0)` (never cleared in step 2), the check passes, and `EvmHost.dispatchTimeOut(GetRequestTimeout,...)` refunds `fee` a second time to the original payer [12](#0-11) .

This yields a total payout of `2 * fee` for a single escrowed `fee`, from the host's shared fee-token balance.

        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,

            return;

            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});

    function handleGetRequestTimeouts(IHost host, GetTimeoutMessage calldata message) external notFrozen(host) {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            GetRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            bytes32 commitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(commitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(RESPONSE_RECEIPTS_STORAGE_PREFIX, commitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(GetRequestTimeout(request, _msgSender()), meta, commitment);
        }
    }
