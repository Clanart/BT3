### Title
Attacker-controlled `out_script_pubkey` can shadow the operator's OP_RETURN in the payout transaction, corrupting `operator_xonlypk` binding in the bridge circuit journal - ([File: circuits-lib/src/bridge_circuit/mod.rs])

### Summary
`create_payout_txhandler` always places the operator's real OP_RETURN (containing `operator_xonly_pk`) at output index 2, but `get_first_op_return_output`/`parse_op_return_data` locate the operator commitment by scanning for the *first* OP_RETURN-shaped output rather than a fixed index. Because the withdrawer's `out_script_pubkey` (output index 0) is never validated to be a non-OP_RETURN, standard script type on the operator's regular `withdraw` gRPC path, an unprivileged withdrawer can craft `out_script_pubkey` as an OP_RETURN script, causing every downstream consumer of `get_first_op_return_output` to bind the wrong (attacker-controlled) bytes as `operator_xonlypk`.

### Finding Description
The broken binding: `operator_xonlypk_extracted_from_payout_tx == kickoff_tx.signer_xonly_pubkey` (the operator that actually fronted the payout and is claiming reimbursement).

`create_payout_txhandler` builds the payout transaction with a fixed, but not index-enforced, structure: output[0] = `output_txout` (attacker-controlled `out_script_pubkey`), output[1] = anchor, output[2] = `op_return_txout(operator_xonly_pk.serialize())` (the operator's real commitment). [1](#0-0) 

`Operator::withdraw` builds `output_txout` directly from the attacker-supplied `out_script_pubkey` with no check on its script type (unlike the optimistic-payout path). [2](#0-1) 

`parse_withdrawal_sig_params`, which parses the gRPC `WithdrawParams` for this same code path, only validates the signature's sighash type; it does not restrict `output_script_pubkey` to a standard, non-OP_RETURN script. [3](#0-2) 

By contrast, the aggregator's `optimistic_payout` path *does* reject non-standard script pubkeys (OP_RETURN would fail this check), showing the validation is known to be necessary but is missing from the operator's normal `withdraw` path used for BitVM-backed payouts/reimbursement. [4](#0-3) 

The user's `SinglePlusAnyoneCanPay` signature covers input 0 and output 0 only, so the withdrawer fully controls and self-signs `out_script_pubkey`, including making it `OP_RETURN <arbitrary bytes>`.

`get_first_op_return_output` picks the first output in iteration order whose script is `is_op_return()`, with no index or content constraint: [5](#0-4) 

This function is used to extract `operator_xonlypk` for `deposit_constant` in the actual bridge circuit: [6](#0-5) 

...and in the host-side journal precomputation: [7](#0-6) 

...and in the verifier's payout bookkeeping, which records which operator "paid" a withdrawal: [8](#0-7) 

Exploit flow:
1. Attacker requests a withdrawal on Citrea and is assigned a withdrawal UTXO/outpoint.
2. Attacker calls the operator's `withdraw`/`internal_withdraw` gRPC with `output_script_pubkey` set to `OP_RETURN <32+ arbitrary bytes>` and a valid `SinglePlusAnyoneCanPay` self-signature over that exact output.
3. `parse_withdrawal_sig_params` and `Operator::withdraw` accept it (no script-type check); `create_payout_txhandler` produces a payout tx with output[0] = attacker OP_RETURN, output[2] = real operator OP_RETURN.
4. Operator broadcasts and it gets mined.
5. Any later computation of `deposit_constant`/journal (bridge-circuit-host, `circuits_lib::bridge_circuit::bridge_circuit`, or `Verifier::update_finalized_payouts`) calls `get_first_op_return_output`, which returns output[0] (attacker's), not output[2] (operator's real key). `parse_op_return_data`/`try_into::<[u8;32]>` then either errors (if attacker's push isn't exactly 32 bytes, causing `InvalidOperatorPubkey`/panic denial of the real operator's proof) or succeeds with attacker-chosen 32 bytes, producing a `deposit_constant`/journal that encodes the wrong "operator" identity.

No existing guard catches this: `Verifier::is_deposit_valid`, `SPV::verify`, `verify_storage_proofs`, `lc_proof_verifier`, and `total_work_and_watchtower_flags` verify chain/L2 linkage and watchtower signatures but never assert which output index carries the operator commitment, and none of them constrain `out_script_pubkey`'s script type.

### Impact Explanation
The honest operator that actually fronted the payout is the one who broadcasts this attacker-shaped transaction (since it comes from the withdrawer, not the operator, and the operator has no reason to inspect/reject a standard-looking withdrawal script). Once mined, every downstream consumer that resolves "which operator paid this withdrawal" via `get_first_op_return_output` gets a wrong or unparsable answer:
- `Verifier::update_finalized_payouts` will record a bogus or `None` payer-operator xonly pubkey for the withdrawal in the verifiers' database.
- The bridge circuit's `deposit_constant`/journal computed for that deposit encodes the wrong `operator_xonlypk`, breaking the binding between the journal and `kickoff_tx.signer_xonly_pubkey` of the operator that actually funded the payout.

This can make the honest operator's kickoff/reimbursement claim fail to match the expected succinct-proof statement, i.e. an honest operator becomes permanently unable to be reimbursed for a payout it genuinely funded, and/or is flagged/challenged as malicious because the committed operator identity in the proof no longer matches the kickoff's signer, potentially leading to the honest operator's collateral being burned. This is repeatable per withdrawal/deposit by any withdrawer against any operator, since it only requires crafting one's own withdrawal output script, giving a broad blast radius across all deposits/operators using the standard `withdraw` flow.

### Likelihood Explanation
- Preconditions: an operational deposit and a withdrawal request on Citrea (which any user, i.e. the unprivileged attacker, can create by depositing and calling Citrea's `withdraw`); no operator, verifier, or aggregator collusion required.
- Attacker cost: normal Bitcoin fees for the withdrawal dust UTXO and the deposit's minimum bridge amount; no special hardware, key compromise, or majority hashrate needed.
- Feasibility: the attacker fully controls `out_script_pubkey` and self-signs it (`SinglePlusAnyoneCanPay`); no operator-side or gRPC-side validation currently blocks an OP_RETURN-shaped script at output index 0.
- Repeatable across every withdrawal handled through `Operator::withdraw`/`internal_withdraw`, independent of which operator services it.

### Recommendation
Do not locate the operator's commitment by "first OP_RETURN in iteration order." Instead:
1. Reject `out_script_pubkey` in `Operator::withdraw`/`parse_withdrawal_sig_params` if it is `OP_RETURN` (or otherwise non-standard), mirroring the check already done in `core/src/rpc/aggregator.rs` for `optimistic_payout`.
2. Additionally harden `get_first_op_return_output`/`bridge_circuit` to read the operator commitment from a fixed, protocol-defined output index (index 2, matching `create_payout_txhandler`'s construction) instead of searching for the first OP_RETURN-shaped script, and assert there is exactly one OP_RETURN output at that index.

### Proof of Concept
```rust
// circuits-lib/src/bridge_circuit/mod.rs (or a new test module)
#[test]
fn test_attacker_forged_op_return_shadows_operator_commitment() {
    // Build a payout-shaped tx: output[0] = attacker OP_RETURN, output[1] = anchor,
    // output[2] = real operator OP_RETURN with genuine 32-byte xonly pk.
    let real_operator_xonlypk: [u8; 32] = [0xAB; 32];
    let attacker_bytes: [u8; 32] = [0x11; 32];

    let attacker_op_return = op_return_txout(PushBytesBuf::try_from(attacker_bytes.to_vec()).unwrap());
    let anchor = anchor_output(NON_EPHEMERAL_ANCHOR_AMOUNT);
    let real_op_return = op_return_txout(PushBytesBuf::try_from(real_operator_xonlypk.to_vec()).unwrap());

    let tx = Transaction {
        version: Version::non_standard(3),
        lock_time: LockTime::ZERO,
        input: vec![/* dummy withdrawal input */],
        output: vec![attacker_op_return, anchor, real_op_return],
    };
    let circuit_tx = CircuitTransaction(tx);

    let found = get_first_op_return_output(&circuit_tx).unwrap();
    let extracted: [u8; 32] = parse_op_return_data(&found.script_pubkey).unwrap().try_into().unwrap();

    // Demonstrates the mismatch: extracted commitment is the attacker's, not the operator's.
    assert_eq!(extracted, attacker_bytes);
    assert_ne!(extracted, real_operator_xonlypk);

    // Compute deposit_constant with both values and show they differ,
    // i.e. the journal no longer binds to the real operator.
    let dc_attacker = deposit_constant(extracted, 0, &[], [0u8;32], [0u8;32], 0, [0u8;32]);
    let dc_real = deposit_constant(real_operator_xonlypk, 0, &[], [0u8;32], [0u8;32], 0, [0u8;32]);
    assert_ne!(dc_attacker, dc_real);
}
```
This test runs entirely within `circuits-lib` with no mainnet or live Citrea dependency, and demonstrates that `get_first_op_return_output`/`parse_op_return_data` extract the attacker's forged commitment instead of the genuine operator's, breaking the `operator_xonlypk_in_journal == kickoff_tx.signer_xonly_pubkey` binding used throughout `bridge_circuit`, `host_deposit_constant`, and `Verifier::update_finalized_payouts`.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

#[allow(clippy::result_large_err)]
pub fn parse_withdrawal_sig_params(
    params: WithdrawParams,
) -> Result<(u32, taproot::Signature, OutPoint, ScriptBuf, Amount), Status> {
    let mut input_signature =
        taproot::Signature::from_slice(&params.input_signature).map_err(|e| {
            Status::invalid_argument(format!("Can't convert input to taproot Signature - {e}"))
        })?;

    // If the Taproot sighash type is Default (no explicit type attached; i.e. a 64-byte
    // signature without a sighash flag), normalize it to SinglePlusAnyoneCanPay.
    // Prior to v0.5 this was Clementine's implicit behavior; we retain it here for
    // backwards compatibility when a 64-byte signature is provided.
    if input_signature.sighash_type == TapSighashType::Default {
        tracing::warn!(
            "Input signature for withdrawal {} has sighash type default, setting to SinglePlusAnyoneCanPay", params.withdrawal_id,
        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }

    let input_outpoint: OutPoint = params
        .input_outpoint
        .ok_or_else(error::input_ended_prematurely)?
        .try_into()?;

    let users_intent_script_pubkey = ScriptBuf::from_bytes(params.output_script_pubkey);

    Ok((
        params.withdrawal_id,
        input_signature,
        input_outpoint,
        users_intent_script_pubkey,
        Amount::from_sat(params.output_amount),
    ))
}
