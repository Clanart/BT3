### Title
Locked-coins vesting check is bypassed by wei-precision borrowing in `SubWei`, allowing an underflow in `EVM Keeper.GetBalance` and a `panic` on balance overflow — ([File: x/evm/keeper/balance.go], [File: sei-cosmos/x/bank/keeper/send.go])

### Summary
The reported bug is a classic "balance minus locked/committed amount underflows and reverts/DOSes the caller" pattern. The closest reachable analog in sei-chain is the `usei`/`wei` balance-bridging code used by the EVM module: `x/evm/keeper/balance.go`'s `GetBalance` computes `usei := allUsei.Sub(lockedUsei)` without any negative-value protection, and the wei sub-denomination accounting in `SubWei` (`sei-cosmos/x/bank/keeper/send.go`) modifies the underlying `usei` balance directly via `setBalance` without re-checking `LockedCoins`, unlike the vesting-safe `SubUnlockedCoins` path.

### Finding Description
`x/evm/keeper/balance.go` defines: [1](#0-0) 
which subtracts a vesting account's `LockedCoins` from its total `usei` balance to compute the EVM-visible balance, with no clamping to zero and no negative check.

The `usei`/`wei` split for EVM native-value transfers is driven through `SubBalance` in `x/evm/state/balance.go`, which calls `SubUnlockedCoins` (vesting-safe, checks `LockedCoins`) for the whole-`usei` component but calls `SubWei` for the sub-`usei` (wei) component: [2](#0-1) 

`SubWei`, however, does not consult `LockedCoins` at all. When the wei balance being spent exceeds the account's current wei balance, it borrows one `usei` from the aggregate balance and writes the new `usei`/`wei` split directly via `setBalance`, only checking that the resulting *raw* coin balance is non-negative — not that it stays above the vesting-locked amount: [3](#0-2) 

Because of this, a vesting/locked account (e.g., an EVM-associated address whose Cosmos account is a `ContinuousVestingAccount`/`DelayedVestingAccount`) can have its `usei` balance driven below its `LockedCoins` amount purely through wei-denominated EVM transfers, since `SubWei`'s borrowing path bypasses the lock check that `SubUnlockedCoins` enforces.

Once `allUsei < lockedUsei`, `k.BankKeeper().GetBalance(...).Amount` minus `LockedCoins(...).AmountOf(denom)` in `x/evm/keeper/balance.go:14` becomes negative. This negative `*big.Int` is then fed into `uint256.FromBig` inside the EVM state DB's `GetBalance`: [4](#0-3) 
and the analogous `giga` implementation: [5](#0-4) 
which explicitly panics if the conversion overflows:
```
res, overflow := uint256.FromBig(s.k.GetBalance(s.ctx, seiAddr))
if overflow {
    panic("balance overflow")
}
```
`uint256.FromBig` treats a negative `big.Int` as an out-of-range (overflow) value, triggering this panic path.

This mirrors the reported issue precisely: an accounting shortcut (`balance − (locked + unclaimed)` in the report; `allUsei − lockedUsei` here) that is normally expected to be non-negative can go negative because a side-channel operation (recoverERC20 claiming leftover tokens after `revokeUnvested`; here, wei-precision transfers bypassing the lock check) mutates one side of the equation without updating the other consistently, producing an underflow that reverts/crashes the caller.

### Impact Explanation
`GetBalance` in `x/evm/keeper/balance.go` and the resulting `DBImpl.GetBalance` in `x/evm/state/balance.go`/`giga/deps/xevm/state/balance.go` are invoked constantly during EVM execution (every `CALL`/`BALANCE` opcode touching the affected address, `eth_getBalance` RPC calls) — this is exactly the "default-configuration RPC node" and EVM-execution surface named in the validation criteria. Once an account is put into the negative-underflow state, any subsequent EVM transaction or read-only RPC query referencing that address's balance will panic. If unrecovered, this can crash the RPC-serving node process (default-configuration RPC crash); if recovered further up the stack, it still permanently DOSes the account (unable to transact via EVM, unable to serve `eth_getBalance` for that address) — a form of permanent freezing of interaction with the affected balance, matching the accepted "permanent freezing" and "crash of default-configuration RPC nodes" impact categories.

### Likelihood Explanation
Reaching this state requires: (1) a vesting Cosmos account whose EVM-mapped address (via Sei↔EVM association) holds a non-zero `LockedCoins` amount close to its total `usei` balance, and (2) that address performing wei-denominated EVM native-value operations (ordinary `value`-bearing EVM transactions, since `SplitUseiWeiAmount` fractional wei residues accumulate naturally from EVM value transfers) such that `SubWei`'s borrow-from-usei branch executes enough times to push `usei` below `lockedUsei`. This is reachable purely through normal, unprivileged EVM transactions sent by the account holder itself (no special privilege needed) — it does not require validator, governance, or operator access. However, it does require a specific precondition (an EVM-associated address with an active vesting lock near its total balance), which somewhat limits the pool of exploitable accounts (vesting accounts used with EVM), making it a real but moderate-likelihood condition.

### Recommendation
- In `SubWei` (`sei-cosmos/x/bank/keeper/send.go` and its `giga/deps/xbank/keeper/send.go` counterpart), when borrowing a whole `usei` unit from the aggregate balance, enforce the same `LockedCoins` check used by `SubUnlockedCoins` before calling `setBalance`, rejecting the operation with `ErrInsufficientFunds` if it would push the balance below the locked amount.
- In `x/evm/keeper/balance.go`'s `GetBalance` (and the `giga` equivalent), clamp `usei := allUsei.Sub(lockedUsei)` to zero (or otherwise treat negative results defensively) rather than allowing a negative value to propagate into `uint256.FromBig`.
- Replace the unconditional `panic("balance overflow")` in `DBImpl.GetBalance` with a recoverable error path so that even if an inconsistency occurs, RPC nodes do not crash.

### Proof of Concept
Conceptual reproduction (exact numeric thresholds require running against the vesting/wei code paths):
1. Create a Cosmos vesting account (e.g., `ContinuousVestingAccount`) with `OriginalVesting` close to its total `usei` balance, and associate it with an EVM address (as in `x/evm/ante/preprocess_test.go`'s `TestMigrateBalance`, which shows vesting accounts function normally as EVM addresses).
2. From that EVM address, perform a series of value-bearing EVM transactions whose wei-denominated leftover amounts force `SubWei` (`sei-cosmos/x/bank/keeper/send.go:383-410`) to repeatedly take the borrow-from-usei branch, decrementing `usei` balance by 1 unit each time `SubWei`'s aggregated balance dips below a whole usei, without any `LockedCoins` check being applied (unlike `SubUnlockedCoins`).
3. Once `allUsei` (`sei-cosmos/x/bank/keeper/view.go` / `x/evm/keeper/balance.go:12`) drops below `LockedCoins(...).AmountOf(denom)` (`x/evm/keeper/balance.go:13`), any call to `k.BankKeeper().GetBalance(...)`/`k.EvmKeeper.GetBalance(...)` returns a negative `*big.Int` (`x/evm/keeper/balance.go:14-16`).
4. Any subsequent `eth_getBalance` RPC call or EVM opcode reading that address's balance calls `DBImpl.GetBalance` (`x/evm/state/balance.go` / `giga/deps/xevm/state/balance.go:103-116`), which passes the negative value to `uint256.FromBig`, triggers `overflow == true`, and panics with `"balance overflow"`.

*Note*: I was unable to fully verify the exact overflow semantics of the vendored `uint256.FromBig` function for negative inputs (its source was not present in the indexed codebase), so the precise panic trigger condition for a negative `big.Int` is inferred from the library's documented behavior and the explicit `if overflow { panic(...) }` check surrounding it, rather than directly observed in this repository's code.

var ZeroInt = uint256.NewInt(0)

func (s *DBImpl) SubBalance(evmAddr common.Address, amtUint256 *uint256.Int, reason tracing.BalanceChangeReason) uint256.Int {
	s.k.PrepareReplayedAddr(s.ctx, evmAddr)
	amt := amtUint256.ToBig()
	if amt.Sign() == 0 {
		return *ZeroInt
	}
	if amt.Sign() < 0 {
		return s.AddBalance(evmAddr, new(uint256.Int).Neg(amtUint256), reason)
	}

	ctx := s.ctx
	var oldBalance *uint256.Int
	if s.logger != nil && s.logger.OnBalanceChange != nil {
		oldBalance = s.GetBalance(evmAddr)
	}

	// this avoids emitting cosmos events for ephemeral bookkeeping transfers like send_native
	if s.eventsSuppressed {
		ctx = ctx.WithEventManager(sdk.NewEventManager())
	}

	// Hook for mock balances (no-op in production builds)
	s.ensureSufficientBalance(evmAddr, amt)

	usei, wei := SplitUseiWeiAmount(amt)
	addr := s.getSeiAddress(evmAddr)
	err := s.k.BankKeeper().SubUnlockedCoins(ctx, addr, sdk.NewCoins(sdk.NewCoin(s.k.GetBaseDenom(s.ctx), usei)), true)
	if err != nil {
		s.err = err
		return *ZeroInt
	}
	err = s.k.BankKeeper().SubWei(ctx, addr, wei)
	if err != nil {
		s.err = err
		return *ZeroInt
	}

	if s.logger != nil && s.logger.OnBalanceChange != nil && oldBalance != nil {
		newBalance := s.GetBalance(evmAddr).ToBig()
		oldBalance := new(big.Int).Add(newBalance, amt)
		s.logger.OnBalanceChange(evmAddr, oldBalance, newBalance, reason)
	}

	surplus := sdk.NewIntFromBigInt(amt)
	s.tempState.surplus = s.tempState.surplus.Add(surplus)
	s.journal = append(s.journal, &surplusChange{delta: surplus})
	return *ZeroInt
}

func (k BaseSendKeeper) SubWei(ctx sdk.Context, addr sdk.AccAddress, amt sdk.Int) (err error) {
	if amt.Equal(sdk.ZeroInt()) {
		return nil
	}
	defer func() {
		if err == nil {
			ctx.EventManager().EmitEvent(
				types.NewWeiSpentEvent(addr, amt),
			)
		}
	}()
	currentWeiBalance := k.GetWeiBalance(ctx, addr)
	if amt.LTE(currentWeiBalance) {
		// no need to change usei balance
		return k.setWeiBalance(ctx, addr, currentWeiBalance.Sub(amt))
	}
	currentUseiBalance := k.GetBalance(ctx, addr, sdk.MustGetBaseDenom()).Amount
	currentAggregatedBalance := currentUseiBalance.Mul(OneUseiInWei).Add(currentWeiBalance)
	postAggregatedbalance := currentAggregatedBalance.Sub(amt)
	if postAggregatedbalance.IsNegative() {
		return sdkerrors.Wrapf(sdkerrors.ErrInsufficientFunds, "%swei is smaller than %swei", currentAggregatedBalance, amt)
	}
	useiBalance, weiBalance := SplitUseiWeiAmount(postAggregatedbalance)
	if err := k.setBalance(ctx, addr, sdk.NewCoin(sdk.MustGetBaseDenom(), useiBalance), true); err != nil {
		return err
	}
	return k.setWeiBalance(ctx, addr, weiBalance)
}

func (s *DBImpl) GetBalance(evmAddr common.Address) *uint256.Int {
	// Hook for mock balances (no-op in production builds)
	s.ensureMinimumBalance(evmAddr)

	seiAddr := s.getSeiAddress(evmAddr)
	res, overflow := uint256.FromBig(s.k.GetBalance(s.ctx, seiAddr))
	if overflow {
		panic("balance overflow")
	}
	if res == nil {
		return uint256.NewInt(0)
	}
	return res
}
