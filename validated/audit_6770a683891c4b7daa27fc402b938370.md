### Title
Excess native token sent to `placeOrder` fee-swap on Tron is permanently trapped instead of refunded - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` forwards the caller's entire remaining `msg.value` into `swapETHForExactTokens` when solver fees are paid in native token, but — unlike the canonical EVM implementation — never tracks how much of that value was actually consumed by the swap, and never refunds the leftover to the user. The result mirrors the external report's root cause: `msg.value` sent beyond what is strictly required for the operation is silently absorbed by the contract instead of being returned to its rightful owner.

### Finding Description
In the canonical EVM `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol`), the fee-swap branch captures the Uniswap return value and decrements `msgValue` accordingly, then refunds any leftover native token to `msg.sender`: [1](#0-0) 

The Tron port of the same function (`evm/tron/contracts/apps/IntentGatewayV2.sol`) performs the same `swapETHForExactTokens{value: msgValue}(...)` call, but does not capture the `amounts` return value, does not decrement `msgValue`, and has no final refund step after the fee block — the function proceeds straight to emitting `OrderPlaced` and returns: [2](#0-1) 

`swapETHForExactTokens` only consumes as much of the forwarded `value` as needed to obtain the exact `order.fees` output amount and refunds any excess ETH to its immediate caller — which is the `IntentGatewayV2` contract itself, not the end user, since the contract calls the router directly. Because the Tron contract has a `receive() external payable` fallback, that refunded excess is accepted into the contract's own balance with no code path that returns it to `msg.sender`. This is the same broken invariant as the external report: the contract only validates that enough native value is present to cover the priced-in cost (here, `order.fees` via the swap), and any surplus `msg.value` supplied by the caller is retained by the contract rather than returned or rejected.

### Impact Explanation
Any user who overestimates the native token needed to cover the solver-fee swap in `placeOrder` (e.g., providing headroom for price slippage, as the SDK/documentation explicitly recommends doing for the `nativeValue` fee-swap leg) permanently loses the unspent portion of `msg.value` on Tron deployments. This is a direct, unconditional loss of user funds for legitimate, expected usage patterns, not a synthetic edge case — the sibling EVM implementation's own test suite (`testPlaceOrder_FeeSwap_RefundsExcessNativeToken`) demonstrates that "send extra ETH to cover slippage" is an intended supported flow, but that refund guarantee is absent in the Tron codepath.

### Likelihood Explanation
The bug requires no privileged actor, relayer, prover, or malicious peer — any ordinary user calling `placeOrder` with `order.fees > 0` and a native-token fee payment on the Tron deployment overpays `msg.value` (which is normal/expected to account for swap slippage, per the documented placement flow) and loses the difference. The affected function is a public, unauthenticated entry point exercised on every native-fee order placement.

### Recommendation
Mirror the canonical EVM implementation: capture `amounts[0]` returned from `swapETHForExactTokens` and subtract it from `msgValue`, then add a final `if (msgValue > 0) { (bool sent,) = msg.sender.call{value: msgValue}(""); if (!sent) revert InsufficientNativeToken(); }` refund step in the Tron `placeOrder`, matching the pattern already present at `evm/src/apps/IntentGatewayV2.sol` lines 356 and 365-368.

### Proof of Concept
1. User calls `IntentGatewayV2.placeOrder{value: X}(order, graffiti)` on the Tron deployment with an ERC-20 input token and `order.fees > 0`, intentionally sending `X` ETH larger than what the fee swap requires (to tolerate price movement), exactly as documented for the sibling EVM chain.
2. Execution reaches the fee block at `evm/tron/contracts/apps/IntentGatewayV2.sol:465-482`; `msgValue = X` is fully forwarded to `swapETHForExactTokens{value: msgValue}(order.fees, ...)`.
3. The router only pulls the ETH actually required to buy `order.fees` worth of fee tokens and refunds the rest to the calling contract (`IntentGatewayV2`), which accepts it via `receive()`.
4. `placeOrder` returns without ever reading the swap's return `amounts` or refunding `msg.sender`; the surplus ETH remains stuck in the contract's balance with no function that returns it to the user, permanently freezing their overpayment — the direct Tron analog of the ETH-loss finding in the external report.
