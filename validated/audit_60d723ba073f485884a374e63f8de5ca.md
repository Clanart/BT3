### Title
Panic on unregistered `recipient` index in DKG blame evaluation enables remote crash - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
`Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` directly. `decryptor` is the `recipient`/`accuser` `Participant` passed by the caller into `BlameMachine::blame` / `AdditionalBlameMachine::blame`. `Participant::new` only rejects zero, so any `u16` index outside the registered set (e.g., `n+1`, or an index whose `EncryptionKeyMessage` was never registered) causes a `HashMap` index panic — a repeatable crash reachable with attacker-controlled protocol messages carrying a valid (self-made) proof-of-possession. This is the Serai analog of CVE-2019-2617: a network-reachable, frequently repeatable crash (complete DoS) of the component evaluating blame.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `decrypt_with_proof` first verifies `msg.pop` (a Schnorr signature over `pop_challenge(context, R, key, sender, msg)`), then evaluates the blame DLEq with the accuser's registered encryption key:

```rust
proof
  .dleq
  .verify(
    &mut encryption_key_transcript(self.context),
    &[C::generator(), msg.key],
    &[self.enc_keys[&decryptor], *proof.key],
  )
```

`enc_keys` is only populated by `Decryption::register`, which is called for each `i in 1..=n` in `AdditionalBlameMachine::new` (crypto/dkg/pedpop/src/lib.rs) and for each participant in `verify_r1`. Any `decryptor` not in that map makes `self.enc_keys[&decryptor]` panic. The `sender`/`recipient` arguments to `blame`/`blame_internal` are never range-checked against `params.n()` or the registered set:

```rust
pub fn blame(&self, sender: Participant, recipient: Participant, msg: ..., proof: ...) -> Participant {
  self.0.blame_internal(sender, recipient, msg, proof)
}
```

Downstream, the processor's `VerifyBlame` handler constructs `AdditionalBlameMachine::new(context, params.n(), ...)` and calls `.blame(accuser, accused, share, blame)` where `accuser` and `accused` are `Participant` fields taken directly from the `CoordinatorMessage::VerifyBlame` protocol message — attacker-influenced bytes.

### Impact Explanation
A single crafted blame message referencing an out-of-set accuser index panics the thread evaluating blame. Repeated submission produces the CVE's "frequently repeatable crash (complete DOS)" of the node running PedPoP blame evaluation, stalling key-gen abort/slashing handling for that session. This is an availability impact only — no secret leakage — consistent with the source CVE's `A:H`-only vector, and it requires only public inputs (a blame message and a self-signed `EncryptedMessage`), not a leaked key or broken BFT assumption.

### Likelihood Explanation
Reachability requires passing the PoP check in `decrypt_with_proof`, which is easy: the attacker generates an arbitrary scalar `k`, sets `key = k*G`, and signs the correct `pop_challenge` themselves (the challenge binds `sender`, `context`, and `msg`, all known). With `proof = Some(...)` (any bytes parseable by `EncryptionKeyProof::read`), evaluation reaches `self.enc_keys[&decryptor]` and panics before the DLEq result matters. The only precondition is that the host routes a `blame` call with an attacker-influenced `recipient` index — which `AdditionalBlameMachine::blame`'s public API accepts unchecked. If the deployment validates `accuser ∈ 1..=n` before calling `blame` (not visible in the in-scope code), the reachability narrows, but the library itself performs no such check.

### Recommendation
Replace `self.enc_keys[&decryptor]` with a fallible lookup (`get`), mapping a missing decryptor to `DecryptionError::InvalidProof` (or a dedicated `UnknownParticipant` error returned as `recipient` blame). Additionally validate `sender`/`recipient` in `BlameMachine::blame` and `AdditionalBlameMachine::blame` against `1..=n` before processing, since panicking inside library code violates the crate's stated expectation of not panicking.

### Proof of Concept
```rust
// Params: t = 1, n = 2 for curve C (e.g. Ristretto)
// Build commitment messages for participants 1 and 2 via KeyGenMachine::generate_coefficients.
let machine = AdditionalBlameMachine::<C>::new(context, 2, commitment_msgs).unwrap();

// Attacker crafts an EncryptedMessage with a *valid* PoP under their own key:
let k = Zeroizing::new(C::random_nonzero_F(&mut rng));
let key = C::generator() * k.deref();
let nonce = Zeroizing::new(C::random_nonzero_F(&mut rng));
let R = C::generator() * nonce.deref();
// pop_challenge(context, R, key, sender = Participant(1), msg_bytes) is computable by anyone;
// sign it with (k, nonce) -> valid pop for an arbitrary plaintext `msg`.

// Trigger: accuser/recipient index 5 was never registered in `enc_keys` (only 1..=2 were).
// blame_internal -> decrypt_with_proof: pop.verify passes, then
// `self.enc_keys[&Participant(5)]` panics on HashMap index.
let faulty = machine.blame(Participant::new(1).unwrap(), Participant::new(5).unwrap(), msg, Some(proof));
```

Expected: panic `"index out of bounds"`/missing-key panic inside `decrypt_with_proof` instead of a returned `Participant`.
