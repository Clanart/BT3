### Title
Integer underflow in `AccountKeyWeightedMultiSig.SigValidationGas` when signature count is zero, causing signature-verification gas cost to wrap to an unpredictable value - (File: blockchain/types/accountkey/account_key_weighted_multi_sig.go)

### Summary
`SigValidationGas` computes the gas cost of validating a multisig transaction as `uint64(numSigs-1) * params.TxValidationGasPerKey` when the Istanbul fork is active [1](#0-0) . This is the same bug class as the reported TensorFlow `EditDistance` vulnerability: a count value that can legitimately be `0` is decremented by `1` without a prior zero-check, producing an integer underflow (`-1` cast to `uint64` becomes `18446744073709551615`), which is then multiplied by a constant. In Go this multiplication silently wraps modulo 2^64 instead of panicking, so the final gas amount charged for signature validation becomes an attacker-influenced, effectively arbitrary `uint64` value rather than the intended `(numSigs-1) * TxValidationGasPerKey`.

### Finding Description
`SigValidationGas` is invoked from `Transaction.ValidateSender` with `numSigs = len(pubkey)`, where `pubkey` is the list of public keys recovered from the transaction's `TxSignatures` via `RecoverPubkey` [2](#0-1) . `TxSignatures.RecoverPubkey` builds `pubkeys := make([]*ecdsa.PublicKey, len(t))` and returns it unmodified for `len(t) == 0` [3](#0-2) , i.e., the pubkey slice length directly mirrors the number of RLP-encoded signature triplets `(V,R,S)` attached to the transaction.

Crucially, `SigValidationGas` is called *before* `accountkey.ValidateAccountKey` in `ValidateSender` [4](#0-3) , so the gas-cost computation runs on `numSigs` before the actual key/threshold-validation logic (which does perform a `numSigs > len(a.Keys)` bound check) ever executes. The zero-guard inside `SigValidationGas` only protects `numKeys == 0` [5](#0-4) ; there is no corresponding `numSigs == 0` guard before the subtraction on line 175.

This exactly parallels the reported bug class: TensorFlow's `EditDistance` computed `hypothesis_shape_t->NumElements() - 1` without checking for `NumElements() == 0`, causing an integer underflow that corrupted downstream loop bounds. Here, `numSigs - 1` is computed without checking `numSigs == 0`, causing an integer underflow that corrupts the downstream gas computation for AccountKeyWeightedMultiSig signature verification — a component directly reachable by any account that has a `WeightedMultiSig` key and submits (or receives, in fee-delegated contexts) a Kaia-typed transaction.

### Impact Explanation
`SigValidationGas`'s return value directly determines how much gas is deducted for validating the account-key signatures of a Kaia-typed transaction (AccountUpdate, FeeDelegated variants, etc.) sent from a `WeightedMultiSig` account. If `numSigs` can be `0` at the point this function is called, the wrapped `uint64` result could be:
- An enormous number, causing the transaction to be rejected for out-of-gas even though it should have been cheap/free (denial-of-service against the specific account), or
- Depending on `TxValidationGasPerKey`'s value and the modulo-2^64 wraparound arithmetic, a small or zero value, meaning the network under-charges for signature validation compute — a fee/gas-accounting integrity violation analogous to "acceptance of an invalid transaction" pricing, since the computation cost incurred (however small, since there are zero signatures to check) is decoupled from the gas actually charged.

The severity depends on whether the wrapped value can be driven low enough to matter economically; because the multiplication is by a fixed per-key gas constant and wraps modulo 2^64, an attacker cannot finely control the final value, limiting practical exploitation to unpredictable gas costs / potential DoS rather than a reliably reproducible drain of funds.

### Likelihood Explanation
Exploitability hinges entirely on whether a transaction with zero attached `(V,R,S)` signature entries can reach `ValidateSender` for a `WeightedMultiSig`-keyed account. Earlier-stage sanity checks exist elsewhere in the codebase — `SanityCheckSignatures` explicitly rejects `len(sigs) == 0` [6](#0-5)  and `RecoverTxSender` also rejects empty signature lists [7](#0-6)  — but these functions are used for **legacy/Ethereum-typed** transaction signature recovery in `RecoverTxSender`, whereas `ValidateSender` for non-Ethereum (Kaia) typed transactions calls `SenderPubkey` → `RecoverPubkey`, which has **no** length check at all (it simply builds a possibly-zero-length slice and returns success). I was not able to fully confirm within the available tool budget whether an upstream RLP-decoding or tx-pool sanity check unconditionally rejects a Kaia-typed transaction with an empty `TxSignatures` list before it reaches `Transaction.ValidateSender`. This is the key open question for confirming exploitability and should be verified directly against `tx_pool.go`'s `validateTx`/`ValidateSender` call chain and the RLP decode path for `TxSignatures` type.

### Recommendation
Add an explicit `numSigs == 0` check in `SigValidationGas` (mirroring the existing `numKeys == 0` check) before computing `uint64(numSigs-1) * params.TxValidationGasPerKey`, returning a defined error (e.g. `kerrors.ErrZeroLength`) instead of allowing the subtraction to underflow. Additionally, verify — and if necessary enforce — that any transaction reaching `Transaction.ValidateSender` for non-Ethereum-typed Kaia transactions has already been confirmed to carry at least one signature (analogous to `SanityCheckSignatures`), closing the gap between `RecoverPubkey`'s unchecked zero-length path and the account-key gas/validation logic that assumes `numSigs >= 1`.

### Proof of Concept
Conceptual reproduction (requires confirming the zero-signature transaction can bypass earlier sanity checks, per the caveat above):
1. Construct a Kaia-typed transaction (e.g., `TxTypeAccountUpdate` or `TxTypeFeeDelegatedValueTransfer`) whose `from` address has an installed `AccountKeyWeightedMultiSig` account key.
2. Craft/RLP-encode the transaction's `TxSignatures` field as an empty list (`[]`) instead of at least one `(V,R,S)` tuple.
3. Submit the transaction so it reaches `Transaction.ValidateSender`, where `pubkey, _ := SenderPubkey(signer, tx)` yields `len(pubkey) == 0`.
4. `accKey.SigValidationGas(currentBlockNumber, role, 0)` is invoked; under Istanbul rules this executes `uint64(0-1) * params.TxValidationGasPerKey`, i.e., `uint64(-1) * TxValidationGasPerKey`, which underflows/wraps to an unintended `uint64` gas amount instead of erroring out [1](#0-0) .
5. Observe the resulting gas charged/consumed for the transaction diverges from the intended `(numSigs-1) * TxValidationGasPerKey` semantics, demonstrating the underflow.

	var err error

	pubkeys := make([]*ecdsa.PublicKey, len(t))
	for i, s := range t {
		pubkeys[i], err = s.RecoverPubkey(txhash, homestead, vfunc)

		}
	}
