### Title
Denial of Service via Unhandled `IndexError` in CLVM Canonical-Encoding Check on Attacker-Supplied Spend Bundle Solutions - (File: `chia/full_node/mempool_manager.py`)

### Summary
`chia/full_node/mempool_manager.py` implements `is_clvm_canonical()` / `is_atom_canonical()` to validate that a spend's serialized solution uses canonical (shortest-form) CLVM atom encoding before the spend is treated as DEDUP-eligible. These functions walk a raw `bytes` buffer using an `offset` index derived entirely from attacker-controlled length-prefix bytes inside the buffer, without ever checking that `offset` stays within `len(clvm_buffer)` before dereferencing it. A maliciously crafted (truncated or malformed) solution can drive `offset` past the end of the buffer, triggering an unhandled `IndexError`. This is conceptually the same bug class as CVE-2023-46847 (Squid): attacker-supplied data with an embedded length field is trusted to walk/allocate a buffer without validating that the declared length stays within the actual buffer bounds, producing unrestricted out-of-bounds access from unauthenticated/untrusted input.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads `b = clvm_buffer[offset]` and then, based on the top bits of `b`, computes a `prefix_len` and iterates `for i in range(prefix_len): ... offset += 1; atom_len |= clvm_buffer[offset]`. Nothing in this loop verifies `offset < len(clvm_buffer)` before the indexing operation. [1](#0-0) 

`is_clvm_canonical(clvm_buffer)` drives this by walking the buffer atom-by-atom: for pair markers (`0xFF`) it just increments `offset` and continues the `while True` loop with `tokens_left` tracking; for atoms it calls `is_atom_canonical()` and advances `offset` by the returned `atom_len`. The loop only terminates when `tokens_left == 0`; there is no explicit bound based on `len(clvm_buffer)` protecting each `clvm_buffer[offset]` access inside the loop. [2](#0-1) 

Because the length-prefix byte(s) and any pair markers are attacker-controlled bytes inside the submitted spend bundle's solution, an attacker can construct a solution whose declared atom length or nesting depth causes `offset` to exceed the buffer length, causing `clvm_buffer[offset]` to raise `IndexError` instead of returning `False`/an error result. Per the module's own documentation, this canonical-form check is invoked while building `BundleCoinSpend`/DEDUP eligibility handling for spends inside `MempoolManager` during spend-bundle admission — a path reachable directly from an untrusted, unauthenticated `push_tx`/`send_transaction` submission. [3](#0-2) 

This mirrors the Squid CVE's root cause pattern: a length value taken from untrusted attacker input is used to index/walk a buffer without confirming the length stays inside the buffer's real bounds, so malformed input can push the read pointer out of range. In this Python codebase that manifests as an unhandled exception rather than heap memory corruption, but the reachability and DoS impact are directly analogous.

### Impact Explanation
If the resulting `IndexError` is not caught somewhere along the mempool admission call chain, a single crafted spend bundle submitted by any unprivileged network participant (via `push_tx` RPC or the p2p `send_transaction` path) could raise an uncaught exception during spend-bundle processing, halting or crashing transaction processing for the full node that receives it — a spend-triggered denial of service. This matches the "spend-triggered transaction-processing halt" impact category explicitly in scope.

### Likelihood Explanation
Likelihood is moderate to high in principle: constructing a solution program with an out-of-range length prefix or unbalanced pair markers is straightforward and requires no special privileges — any spend bundle submitter can shape their solution bytes arbitrarily. The main uncertainty (which I could not fully resolve without further tracing) is whether the specific call site(s) that invoke `is_clvm_canonical()`/`is_atom_canonical()` wrap the call in a broad `try/except` that would convert the `IndexError` into a normal validation-failure return rather than propagating and crashing the process. I was not able to locate the exact call site(s) within the available search budget to confirm whether such exception handling exists.

### Recommendation
Add explicit bounds checks (`offset < len(clvm_buffer)`, and similarly before each incremental read in the atom-length loop) in both `is_atom_canonical()` and `is_clvm_canonical()`, returning `False` (non-canonical) or raising a well-defined, caught validation error rather than allowing a raw `IndexError` to escape. Additionally, audit all call sites to ensure any exception from this canonical-encoding check is caught and converted into a normal spend-bundle rejection rather than propagating up through spend-bundle admission.

### Proof of Concept

Craft a `CoinSpend` solution whose serialized CLVM bytes end with an atom whose length-prefix byte declares a multi-byte length (e.g., the `0b11000000` pattern indicating a 5+8 bit length prefix) positioned at the very last byte of the buffer, so that the prefix-length loop in `is_atom_canonical()` attempts to read one or more bytes past the end of `clvm_buffer`.
2. Submit a `SpendBundle` containing this `CoinSpend` via `push_tx` (`chia/full_node/full_node_rpc_api.py:push_tx`) or the wallet `send_transaction` protocol path. [4](#0-3)

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

```python
def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```

```markdown
## Canonical serialization

### `is_clvm_canonical(clvm_buffer)`

Checks that a CLVM program uses shortest-form atom encoding:

- No unnecessary length prefix bytes
- No back-references (`0xFE` byte)
- No trailing garbage

### When enforced

Required for DEDUP-eligible spends. Without canonical form, identical
solutions could have different serializations, breaking dedup.

### `is_atom_canonical(clvm_buffer, offset)`

Validates a single atom's length prefix encoding. The CLVM format uses
variable-length prefixes (1-6 bytes) based on atom size. Each prefix
length has a minimum atom size threshold.
```
