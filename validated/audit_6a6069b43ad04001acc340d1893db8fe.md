## Title
Global, retroactive `challengePeriod` reduction lets pending state commitments bypass their fisherman-veto window - ([File: evm/src/core/HandlerV2.sol](evm/src/core/HandlerV2.sol), [File: evm/src/core/EvmHost.sol](evm/src/core/EvmHost.sol))

### Summary
The external report's core invariant break is: a duration meant to give observers time to react to a *pending* state change is read at *use-time* rather than fixed at *proposal-time*, so shortening the global duration retroactively strips protection from changes that are already in flight. The same pattern exists in Hyperbridge's `challengePeriod`, which is supposed to give fishermen a fixed window to veto a specific state commitment before requests/timeouts anchored to that commitment are processed.

### Finding Description
`challengePeriod` is a single global `HostParams` field, not a value captured per state-machine height when the commitment is stored: [1](#0-0) 

Every request/timeout handler validates the challenge period by reading the *current* `host.challengePeriod()` and comparing it against `block.timestamp - stateMachineCommitmentUpdateTime(height)`: [2](#0-1) [3](#0-2) 

`challengePeriod` can be updated at any time via `updateHostParams`, which is validated for structural correctness (non-zero handler/consensus client/etc.) but has **no minimum-value check and no protection for already-pending commitments** — unlike `unStakingPeriod`, which enforces a `1 days` floor: [4](#0-3) 

Because the check always uses the live `challengePeriod()` value rather than the value that was in effect when a given `StateMachineHeight`'s commitment was stored, lowering `challengePeriod` (e.g. from 7 days to a few seconds/zero) instantly matures *every already-stored, still-pending* commitment across all heights. Fishermen who were relying on the originally-configured window to detect and veto a fraudulent commitment (per the documented flow) lose that window without warning, and relayers can immediately submit `handlePostRequests`/`handleGetRequestTimeouts` messages referencing that commitment: [5](#0-4) 

This is the exact analog of the `quitPeriod` bug: the safety window is a mutable global parameter checked at consumption time instead of being snapshotted per pending item at creation time, so a routine parameter update (not requiring any malicious actor) retroactively collapses protection that users/fishermen were told they had.

### Impact Explanation
If a fraudulent or contested `StateCommitment` is stored while `challengePeriod` is large (e.g. 7 days, as intended for fishermen to cross-check L2 state via multiple RPC providers), and governance subsequently issues a routine `updateHostParams` that lowers `challengePeriod`, all currently pending commitments — including the fraudulent one still within its intended review window — instantly satisfy `challengePeriod > delay == false`, allowing `handlePostRequests`/`handleGetRequestTimeouts`/other handler paths to process messages anchored to unreviewed/fraudulent state. This can lead to false state acceptance and downstream fund loss for any application relying on that state commitment, since fishermen never got the window they were promised to veto it.

### Likelihood Explanation
No malicious relayer, prover, or compromised key is required — a single, ordinary `updateHostParams` call (the documented, legitimate mechanism for adjusting protocol parameters, analogous to the `owner` in the Vault report) is sufficient. The bug is a straightforward missing-invariant: `challengePeriod` should be a property of the specific `StateMachineHeight`/commitment, not a live global value re-read on every handler call.

### Recommendation
Snapshot the effective challenge period at the moment a `StateCommitment` is stored (alongside `_stateCommitmentsUpdateTime`), and have `handlePostRequests`/`handleGetRequestTimeouts`/other consumers compare `delay` against that stored per-height value instead of the live `host.challengePeriod()`. Alternatively, apply new `challengePeriod` values only to commitments stored after the update, leaving already-pending commitments bound to the challenge period in effect when they were created — mirroring the report's "apply the duration when the change is proposed" mitigation.

### Proof of Concept
1. Consensus proof anchors a new `StateCommitment` at height `H` while `challengePeriod = 7 days` (`EvmHost._hostParams.challengePeriod`, `_stateCommitmentsUpdateTime[H] = t0`).
2. A fisherman begins its standard multi-RPC cross-check of the L2 state, expecting the full 7-day window before relayers can act on `H`.
3. At `t0 + 1 hour`, governance (via `HostManager.onAccept` → `IHostManager.updateHostParams`) submits an otherwise-legitimate parameter update that sets `challengePeriod = 0` (or a few seconds) — no check prevents this, and no distinction is made for commitments already pending.
4. A relayer immediately calls `handlePostRequests` (or `handleGetRequestTimeouts`) for a request anchored at height `H`:
   - `delay = block.timestamp - stateMachineCommitmentUpdateTime(H) ≈ 1 hour`
   - `challengePeriod = 0` (just updated)
   - `challengePeriod != 0 && challengePeriod > delay` evaluates `false`, so the check at [6](#0-5)  passes.
5. The request is dispatched and processed even though the fisherman's promised 7-day review window for height `H` never elapsed, letting a still-unverified (potentially fraudulent) state commitment be acted upon.

    function updateHostParamsInternal(HostParams memory params) internal {
        // check the params to prevent the host from getting bricked.
        if (
            params.hostManager == address(0) || address(params.hostManager).code.length == 0
                || !IERC165(params.hostManager).supportsInterface(type(IApp).interfaceId)
        ) {
            // otherwise cannot process new cross-chain governance requests
            revert InvalidHostManager();
        }

        if (
            params.handler == address(0) || address(params.handler).code.length == 0
                || !IERC165(params.handler).supportsInterface(type(IHandlerV2).interfaceId)
        ) {
            // otherwise cannot process new datagrams
            revert InvalidHandler();
        }

        if (
            params.consensusClient == address(0) || address(params.consensusClient).code.length == 0
                || !IERC165(params.consensusClient).supportsInterface(type(IConsensusV2).interfaceId)
        ) {
            // otherwise cannot process new consensus datagrams
            revert InvalidConsensusClient();
        }

        // otherwise cannot process new cross-chain governance requests
        if (keccak256(params.hyperbridge) == keccak256(bytes(""))) revert InvalidHyperbridgeId();

        // otherwise cannot process new datagrams
        uint256 stateMachinesLen = params.stateMachines.length;
        if (stateMachinesLen == 0) revert InvalidStateMachinesLength();

        // otherwise cannot process new datagrams
        if (1 days > params.unStakingPeriod) revert InvalidUnstakingPeriod();

        address oldFeeToken = feeToken();
        if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
            uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
            if (balance != 0) revert CannotChangeFeeToken();

        // safe to emit here because invariants have already been checked
        // and don't want to store a temp variable for the old params

        _hostParams.feeToken = params.feeToken;

        _hostParams.challengePeriod = params.challengePeriod;
