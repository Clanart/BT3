## Title
Fee-on-transfer ERC20 tokens break value accounting in `BridgeTransferERC20`, enabling cross-chain reserve drain - (File: `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary
`BridgeTransferERC20.requestERC20Transfer` and the internal `_requestERC20Transfer`/`_payERC20FeeAndRefundChange` flow assume that the `_value` (plus `_feeLimit`) requested by the caller is exactly the amount the bridge contract actually receives via `transferFrom`. This is the same root-cause pattern as the referenced report: no before/after balance check is performed around the token transfer, so a deflationary/fee-on-transfer ERC20 will cause the bridge's actual token balance to diverge from the `_value` it emits in `RequestValueTransfer` and later honors in `handleERC20Transfer`.

### Finding Description
`requestERC20Transfer` pulls tokens from the caller using the declared amount, not the amount actually received: [1](#0-0) 

This declared `_value` is then propagated verbatim into the cross-chain request: [2](#0-1) 

On the counterpart chain, `handleERC20Transfer` — reached only after `onlyOperators` quorum voting via `_voteValueTransfer` — releases (or mints) the full requested `_value` to the recipient, trusting the `RequestValueTransfer` event without any way to verify that this amount was truly escrowed on the origin chain: [3](#0-2) 

If the registered ERC20 token charges a transfer fee (or otherwise delivers less than the nominal amount on `transferFrom`), the bridge actually escrows `_value + _feeLimit - fee%` but still requests release/mint of the full `_value` on the other chain. This is the identical bug class as the external report: an amount `x` is assumed to be received, when the actual received amount is `< x`.

### Impact Explanation
Because the honest operator quorum releases the full declared `_value` based solely on the emitted event (not on-chain verification of the bridge's actual balance change), every fee-on-transfer-token deposit under-collateralizes the bridge's reserve while still entitling the counterpart-chain recipient to the full nominal amount. Repeated use drains the shared token reserve funded by other users' deposits (in lock-and-release mode) or can cause insufficient balance during `ERC20Burnable(_tokenAddress).burn(_value)` in mint-burn mode, corrupting bridge accounting and enabling unauthorized value extraction/service insolvency for other legitimate depositors. This mirrors the "no issue for current collaterals but breaks with future token additions" caveat from the original report — the bridge's registered-token list can be extended, and any accidental/malicious registration of a fee-on-transfer/rebasing token turns this into an exploitable value-extraction path reachable by any ordinary token holder issuing `requestERC20Transfer`.

### Likelihood Explanation
Exploitation requires only that a fee-on-transfer (or otherwise non-standard) ERC20 be registered as a bridge token (an operator-governed action, analogous to a DeFi protocol adding a new collateral type) — after that, any unprivileged sender holding such tokens can trigger the mismatch with a single `requestERC20Transfer` call. No malicious operator, validator, or consensus behavior is required; the honest operator quorum unknowingly perpetuates the accounting error because it only observes the emitted `_value`, not the bridge's real balance delta.

### Recommendation
In `_requestERC20Transfer`/`requestERC20Transfer` (and the mint-burn burn path), measure the bridge's token balance immediately before and after `safeTransferFrom`, and use the observed delta (rather than the caller-declared `_value`/`_feeLimit`) for fee accounting, the `RequestValueTransfer` event, and the burn amount, so cross-chain release amounts always match what was actually escrowed.

### Proof of Concept
1. Bridge operators register a fee-on-transfer ERC20 token `T` (e.g., 2% fee on transfer) via the existing token-registration/voting flow.
2. Attacker (or any normal user) calls `requestERC20Transfer(T, to, value=1000, feeLimit=0, extraData)`.
3. `safeTransferFrom` pulls `1000` nominal tokens from the caller, but due to the 2% fee, the bridge contract's actual `T` balance only increases by `980`. [4](#0-3) 
4. `RequestValueTransfer` is emitted with `_value = 1000` regardless of the shortfall.
5. Operators on the counterpart chain vote and call `handleERC20Transfer(..., _value=1000, ...)`, releasing/minting the full `1000` `T` to `_to`. [5](#0-4) 
6. The bridge's reserve is now short by `20` tokens per such request; repeating this drains the shared reserve funded by other depositors' escrowed tokens.
