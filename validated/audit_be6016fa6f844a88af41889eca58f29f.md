### Title
Address (re-)association silently strips and blocks funds already accumulated under an EVM address's direct-cast Sei identity - (File: utils/helpers/associate.go)

### Summary
The Symfony bug allowed a session-bound user identity to be silently switched to another identity's session state without accounting for prior state tied to the original identity. Sei-chain has a structurally similar hazard in its EVM↔Sei "dual address" model: a `sdk.AccAddress` derived by direct-casting an EVM address (`sdk.AccAddress(evmAddr[:])`) can accumulate real state (balances, staking/distribution positions) before that EVM address is formally "associated" with its true pubkey-derived Sei address. When association later occurs — via `Associate`/`AssociatePubKey` precompile calls, a signed Cosmos tx, or an EVM tx from that key — `AssociateAddresses`/`MigrateBalance` moves the spendable balance to the true address and, if `LockedCoins` on the cast address happens to be zero, deletes the cast account outright [1](#0-0) . From that point on, `CanAddressReceive` permanently blocks the cast address from receiving any further funds because it is now “associated” with a different (true) Sei address [2](#0-1) .

### Finding Description
`SetAddressMapping` unconditionally rewrites the bidirectional EVM↔Sei mapping [3](#0-2) , and `AssociateAddresses` only guards against the *target* Sei address already being associated — it does not inspect whether the EVM address's pre-existing direct-cast identity (`sdk.AccAddress(evmAddr[:])`) holds module state beyond spendable/wei balances and vesting `LockedCoins` [4](#0-3) . `MigrateBalance` only moves `SpendableCoins`/wei and deletes the account if `LockedCoins` is zero [1](#0-0) ; it has no awareness of staking delegations, unbonding queue entries, or distribution reward records that could be keyed by the cast address bytes, since those aren't tracked via `LockedCoins`.

The code base itself acknowledges this exact class of bug for one specific path — EIP-7702 `SetCode` authorities — and patches it by pre-associating authorities to their true address before `SetCode` can create a mutable cast mapping, explicitly citing the risk of "orphaning any staking/distribution state created under the direct-cast identity (which can then halt the chain via the distribution validator-removal hook)" [5](#0-4) , with a dedicated regression test [6](#0-5) . That fix, however, is narrowly scoped to `SetCode` authorization authorities. The general precompile/ante-handler association paths (`addr.associateAddresses`, `EVMPreprocessDecorator.AnteHandle`, `EVMAddressDecorator.AnteHandle`) apply the same unconditional `SetAddressMapping` + `MigrateBalance` logic to *any* address whose cast identity may already have accrued delegator/distribution state, without the same protective pre-check [7](#0-6) [8](#0-7) [9](#0-8) .

Once the true association is recorded, `CanAddressReceive` permanently rejects payments to the now-orphaned cast address unless the associated true address happens to equal it [2](#0-1) , mirroring the distribution module's own defensive comment about this exact risk (added specifically to stop a panic/halt from a delegator's withdraw address becoming unpayable after association) [10](#0-9) .

### Impact Explanation
An unprivileged EVM/Cosmos user who lets funds, delegations, or reward accruals build up under the raw byte-cast Sei address of an EVM key they control (a routine occurrence, since many wallets/tools transact using the cast address before ever calling `associate`) can have that state effectively frozen the moment the address is formally associated: the cast address becomes blocked from receiving further transfers (`CanAddressReceive` returns false) and its `BaseAccount` may be deleted, while staking/distribution records that reference the cast address bytes as delegator/withdraw address are not migrated. This matches the “permanent freezing of funds” impact criterion, and the distribution keeper's own code confirms upstream awareness that an address becoming unpayable in this way can even panic/halt block production during validator-removal payouts if not specifically guarded (as it now is only for that one hook) [10](#0-9) .

### Likelihood Explanation
Reachable purely through normal user activity — no privileged access needed: (1) send/receive/delegate using an EVM address's cast Sei form before formally associating, then (2) trigger association via any ordinary Cosmos-signed tx, EVM tx, or `addr.associate`/`associatePubKey` precompile call. The maintainers' own fix and test for the `SetCode`-authority variant demonstrate this is a known, previously-triggered bug class in this exact subsystem, and the general (non-SetCode) association code paths were not shown to carry the equivalent protection.

### Recommendation
Extend the same proactive/defensive-association approach already applied to `SetCode` authorities to all identity-association entry points: before allowing `SetAddressMapping`/`AssociateAddresses` to remap an EVM address's true Sei identity, check for and migrate (or reject the association until resolved) any staking delegations, unbonding entries, or distribution/withdraw-address records still keyed by the direct-cast address, not just spendable balance and vesting `LockedCoins`.

### Proof of Concept
Conceptual reproduction (not independently executed, given index/tool constraints):
1. Generate an EVM keypair; compute `castAddr = sdk.AccAddress(evmAddr[:])` without ever calling `associate`.
2. Fund `castAddr` and delegate stake from it to a validator using ordinary Cosmos delegate messages (delegator address = `castAddr`), or set it as a distribution withdraw address for some other delegator.
3. Using the EVM private key, submit any ordinary signed transaction (EVM tx or Cosmos tx) or call `addr.associate`/`associatePubKey`, triggering `AssociateAddresses`/`SetAddressMapping` as shown in `x/evm/ante/preprocess.go` and `precompiles/addr/addr.go`.
4. Observe that `castAddr`'s spendable balance moves to the new true Sei address and the account may be deleted, while the delegation/withdraw-address records remain keyed to `castAddr`; subsequent payouts to `castAddr` are blocked by `CanAddressReceive` (`x/evm/keeper/address.go`), freezing those funds.

**Note on completeness:** I could not, within the remaining tool budget, trace the exact staking/distribution module code paths that key records by delegator/withdraw address to confirm definitively whether a downstream safeguard (analogous to the `AfterValidatorRemoved` fallback already found in `sei-cosmos/x/distribution/keeper/keeper.go`) exists for delegation records themselves. This finding is built on strong, directly-cited evidence of the mechanism and the maintainers' own acknowledgment of the bug class for one specific path (`SetCode` authorities), but the blast radius for the general association path is inferred rather than fully proven end-to-end in the staking module.

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil

func (k *Keeper) SetAddressMapping(ctx sdk.Context, seiAddress sdk.AccAddress, evmAddress common.Address) {

		types.EventTypeAddressAssociated,
		sdk.NewAttribute(types.AttributeKeySeiAddress, seiAddress.String()),
		sdk.NewAttribute(types.AttributeKeyEvmAddress, evmAddress.Hex()),
	))

// from an EVM address AND the originating EVM address has already been associated with

func (k *Keeper) CanAddressReceive(ctx sdk.Context, addr sdk.AccAddress) bool {
	directCast := common.BytesToAddress(addr) // casting goes both directions since both address formats have 20 bytes
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)
	return associatedAddr.Equals(addr) || !isAssociated // this means it's either a cast address that's not associated yet, or not a cast address at all.
}

func (p *EVMAddressDecorator) AnteHandle(ctx sdk.Context, tx sdk.Tx, simulate bool, next sdk.AnteHandler) (sdk.Context, error) {
	sigTx, ok := tx.(authsigning.SigVerifiableTx)
	if !ok {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrTxDecode, "invalid tx type")
	}
	signers := sigTx.GetSigners()
	for _, signer := range signers {
		if evmAddr, associated := p.evmKeeper.GetEVMAddress(ctx, signer); associated {
			ctx.EventManager().EmitEvent(sdk.NewEvent(evmtypes.EventTypeSigner,
				sdk.NewAttribute(evmtypes.AttributeKeyEvmAddress, evmAddr.Hex()),
				sdk.NewAttribute(evmtypes.AttributeKeySeiAddress, signer.String())))
			continue
		}
		acc := p.accountKeeper.GetAccount(ctx, signer)
		if acc.GetPubKey() == nil {
			logger.Error("missing pubkey for signer", "signer", signer)
			ctx.EventManager().EmitEvent(sdk.NewEvent(evmtypes.EventTypeSigner,
				sdk.NewAttribute(evmtypes.AttributeKeySeiAddress, signer.String())))
			continue
		}
		pk, err := btcec.ParsePubKey(acc.GetPubKey().Bytes())
		if err != nil {
			logger.Debug("failed to parse pubkey for account, likely due to the fact that it isn't on secp256k1 curve", "account", acc.GetPubKey(), "err", err)
			ctx.EventManager().EmitEvent(sdk.NewEvent(evmtypes.EventTypeSigner,
				sdk.NewAttribute(evmtypes.AttributeKeySeiAddress, signer.String())))
			continue
		}
		evmAddr, err := helpers.PubkeyToEVMAddress(pk.SerializeUncompressed())
		if err != nil {
			logger.Error("failed to get EVM address from pubkey", "err", err)
			ctx.EventManager().EmitEvent(sdk.NewEvent(evmtypes.EventTypeSigner,
				sdk.NewAttribute(evmtypes.AttributeKeySeiAddress, signer.String())))
			continue
		}
		ctx.EventManager().EmitEvent(sdk.NewEvent(evmtypes.EventTypeSigner,
			sdk.NewAttribute(evmtypes.AttributeKeyEvmAddress, evmAddr.Hex()),
			sdk.NewAttribute(evmtypes.AttributeKeySeiAddress, signer.String())))
		p.evmKeeper.SetAddressMapping(ctx, signer, evmAddr)
		associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.evmKeeper.BankKeeper(), p.accountKeeper)
		if err := associationHelper.MigrateBalance(ctx, evmAddr, signer, false); err != nil {
			logger.Error("failed to migrate EVM address balance", "address", evmAddr, "err", err)
			return ctx, err
		}
	}
	return next(ctx, tx, simulate)

func (p PrecompileExecutor) associateAddresses(ctx sdk.Context, method *abi.Method, evmAddr common.Address, seiAddr sdk.AccAddress, pubkey cryptotypes.PubKey) (ret []byte, remainingGas uint64, err error) {
	// Check that address is not already associated
	_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if found {
		return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
	}

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)
	err = associationHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err

func (k Keeper) SetWithdrawAddr(ctx sdk.Context, delegatorAddr sdk.AccAddress, withdrawAddr sdk.AccAddress) error {
	// Reject any address the bank keeper would block from receiving funds, not just
	// the module-account blocklist: BlockedAddr also covers dynamically-derived

	// delegator from parking an unpayable withdraw address that would later make the

	if k.blockedAddrs[withdrawAddr.String()] || k.bankKeeper.BlockedAddr(withdrawAddr) {
		return sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive external funds", withdrawAddr)
	}

	if !k.GetWithdrawAddrEnabled(ctx) {
		return types.ErrSetWithdrawAddrDisabled
	}

	if !k.bankKeeper.CanSendTo(ctx, withdrawAddr) {
		return sdkerrors.Wrapf(sdkerrors.ErrInvalidRecipient, "%s is not allowed to receive external funds", withdrawAddr)
	}
