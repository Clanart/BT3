### Title
CW721→ERC721 pointer NFT transfers use unsafe `transferFrom`, permanently freezing NFTs sent to non-receiving contracts - (File: x/evm/client/wasm/query.go)

### Summary
The Sei EVM/CW pointer bridge that moves ERC-721 NFTs on behalf of a CosmWasm caller builds the transfer calldata using the unsafe `transferFrom` selector rather than `safeTransferFrom`, mirroring the exact root cause in the referenced report (`closeLoan()` using `transferFrom` instead of `safeTransferFrom`).

### Finding Description
`HandleERC721TransferPayload` in `x/evm/client/wasm/query.go` packs an ABI call to `transferFrom(from, to, tokenId)` on the target ERC-721 contract, which is used to build the transfer payload a CosmWasm contract submits to move a wrapped/pointed ERC-721 token to a Sei-associated EVM recipient address. [1](#0-0) 

This same unsafe pattern is used directly in the Solidity `CW721ERC721Pointer.transferFrom()` when a `transfer_nft` CW message is executed against the CW721-backed pointer contract — it calls the underlying CW721 `transfer_nft` execute message, which (unlike ERC-721 `safeTransferFrom`) has no notion of verifying the recipient can handle the asset before completing the transfer, and the Solidity-side `transferFrom` override never performs an `onERC721Received`-style check on the `to` address for EVM-side pointer usage: [2](#0-1) 

Standard ERC-721 `transferFrom` (as opposed to `safeTransferFrom`) does not verify that the recipient contract implements `IERC721Receiver`. As per EIP-721, a wallet/broker/contract that wants to safely accept NFTs must implement the receiver interface, and callers relying on `safeTransferFrom` get that protection — callers relying on plain `transferFrom` do not, and any transfer to a contract address that has no code path to move the NFT out again will freeze it forever.

### Impact Explanation
If a Sei EVM address that resolves to a smart-contract account (e.g., a contract that never implemented ERC-721 handling, or a not-yet-associated Sei address whose EVM address later resolves to a contract) is passed as the recipient of an NFT transfer through this CW→EVM transfer-payload path or through the `CW721ERC721Pointer.transferFrom` execution path, the underlying ERC-721 token becomes permanently locked in that contract with no way to retrieve it, since the transfer bypasses the `onERC721Received` safety check that `safeTransferFrom` would have enforced. This is a permanent freezing-of-funds condition for an NFT asset, reachable by any user/CosmWasm contract performing a standard `transfer_nft` operation through the pointer bridge.

### Likelihood Explanation
Likelihood is moderate: it requires the transfer recipient to be an address whose associated EVM address is a contract lacking NFT-handling logic — a realistic but not default scenario for ordinary EOA-to-EOA transfers. It does not require any privileged, malicious-validator, or off-chain condition; a single CosmWasm `transfer_nft`/`send_nft` execute message submitted by an ordinary user is sufficient to trigger the vulnerable code path.

### Recommendation
Change `HandleERC721TransferPayload` to pack `safeTransferFrom(address,address,uint256)` instead of `transferFrom`, and update `CW721ERC721Pointer.transferFrom`/related pointer transfer logic to perform (or delegate to) a receiver-interface check on `to` before finalizing cross-domain NFT transfers, consistent with EIP-721 safe-transfer semantics.

### Proof of Concept
1. Deploy or use an existing `CW721ERC721Pointer` (or the CW721→ERC721 wasm-binding transfer payload) for an NFT collection.
2. As a normal user, execute a `transfer_nft`/`send_nft` CW message (or call `HandleERC721TransferPayload`-derived calldata) where the `recipient`/`to` resolves to a smart-contract EVM address with no logic to move ERC-721 tokens (e.g., a contract that never calls `transferFrom`/`safeTransferFrom` on tokens it holds, and does not implement `onERC721Received`).
3. The transfer succeeds because `transferFrom` is used, moving the NFT into the contract.
4. The NFT is now permanently stuck: the contract has no function to transfer it back out, and its owner has no way to invoke `transferFrom`/`approve` from that contract's address.

func (h *EVMQueryHandler) HandleERC721TransferPayload(ctx sdk.Context, from string, recipient string, tokenId string) ([]byte, error) {
	abi, err := cw721.Cw721MetaData.GetAbi()
	if err != nil {
		return nil, err
	}
	fromEvmAddr, found := h.k.GetEVMAddress(ctx, sdk.MustAccAddressFromBech32(from))
	if !found {
		return nil, types.NewAssociationMissingErr(from)
	}
	toEvmAddr, found := h.k.GetEVMAddress(ctx, sdk.MustAccAddressFromBech32(recipient))
	if !found {
		return nil, types.NewAssociationMissingErr(recipient)
	}
	t, ok := sdk.NewIntFromString(tokenId)
	if !ok {
		return nil, errors.New("invalid token ID for ERC721, must be a big Int")
	}
	bz, err := abi.Pack("transferFrom", fromEvmAddr, toEvmAddr, t.BigInt())
	if err != nil {
		return nil, err
	}
	res := bindings.ERCPayloadResponse{EncodedPayload: base64.StdEncoding.EncodeToString(bz)}
	return json.Marshal(res)
}

    function transferFrom(address from, address to, uint256 tokenId) public override {
        if (to == address(0)) {
            revert ERC721InvalidReceiver(address(0));
        }
        require(from == ownerOf(tokenId), "`from` must be the owner");
        string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
        string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(tokenId)));
        string memory req = _curlyBrace(_formatPayload("transfer_nft", _curlyBrace(_join(recipient, tId, ","))));
        _execute(bytes(req));
    }
