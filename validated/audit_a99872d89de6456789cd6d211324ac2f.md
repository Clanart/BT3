### Title
Permanent loss of BUSD incentive reward when contract balance is insufficient - ([File: wombat/ArbWomUp2.sol])

### Summary
`ArbWomUp2.incentiveDeposit()` computes a user's BUSD reward via `getRewardAmount()`, which silently caps the reward to the contract's current BUSD balance instead of reverting or tracking the shortfall. Because the "already paid" amount used in future reward calculations (`calDoubledCounted`) is derived purely from the user's cumulative WOM deposit tier position rather than the amount actually transferred, any BUSD shortfall is never recovered — the user permanently loses that portion of their entitled reward.

### Finding Description
`incentiveDeposit()` calls `getRewardAmount()` to determine `rewardToSend`, then immediately records `claimedReward[msg.sender] += rewardToSend` and transfers `rewardToSend` to the user: [1](#0-0) 

`getRewardAmount()` explicitly caps the computed reward to the contract's current BUSD balance: [2](#0-1) 

The subtraction of "already rewarded" amounts for future deposits (`calDoubledCounted`) is computed purely from the tier structure applied to `userWOMDeposited[_account]` — i.e., it assumes the user was already paid in full for their prior deposits, regardless of what was actually transferred: [3](#0-2) 

If the contract's BUSD balance is insufficient at the time of a deposit (e.g., depleted by earlier users' claims, since there's no owner-only-gated top-up guarantee before each deposit), the reward is silently truncated to `busdleft`. However, `userWOMDeposited[_account]` is still incremented by the full deposited WOM amount, and future calls to `calDoubledCounted` will treat the user's entire tier position as "already fully rewarded," permanently erasing the shortfall — analogous to the reported bug where `_safeClaimTransfer` silently caps the transferred amount to the available balance while the accounting (`hasClaimed`/vesting schedule) proceeds as if the full amount had been paid.

### Impact Explanation
Users who deposit WOM when the contract's BUSD balance is insufficient receive less than their entitled incentive reward and have no mechanism to reclaim the difference later — the shortfall is silently and permanently lost. This constitutes a permanent freezing/loss of user-owed yield, reachable via a normal unprivileged call to `incentiveDeposit()`.

### Likelihood Explanation
This does not require any admin misbehavior — it only requires the BUSD balance to run low relative to outstanding tiered rewards, which is plausible under normal operation as multiple users claim from a finite reward pool during the arbitrum airdrop incentive period, making it a realistic occurrence rather than a contrived edge case.

### Recommendation
Do not silently cap the reward transfer to the available balance while advancing the user's reward-tier accounting as if fully paid. Either revert the transaction when the contract lacks sufficient BUSD (forcing the admin to top up before further deposits), or track the actual amount paid to each user separately from the tier-based "already rewarded" calculation so shortfalls can be redeemed once the contract is refunded.

### Proof of Concept
1. Owner configures reward tiers via `setMultiplier` and funds the contract with a limited BUSD balance.
2. User A deposits WOM, `getRewardAmount` computes a reward `R` that exceeds the current BUSD balance `B`; `getRewardAmount` returns `B` (capped), which is fully transferred and `claimedReward[A] += B`, while `userWOMDeposited[A]` is increased by the full deposit amount.
3. If User A (or any user whose position moves through the same tier bracket) deposits again later, `calDoubledCounted` recomputes the "already paid" amount based on the tier formula applied to `userWOMDeposited`, assuming the full `R` (not the actually-paid `B`) was already disbursed.
4. The difference `R - B` is never paid out in any future call — it is permanently lost, even though the user was contractually entitled to it based on their WOM deposit and the tier schedule.

    function getRewardAmount(uint256 _amount, address _account) external view returns (uint256) {
        if (_amount == 0 || rewardMultiplier.length == 0) return 0;
        uint256 accumulated = _amount + userWOMDeposited[_account];

        uint256 rewardAmount = 0;
        uint256 i = 1;
        while (i < rewardTier.length && accumulated > rewardTier[i]) {
            rewardAmount +=
                (rewardTier[i] - rewardTier[i - 1]) *
                rewardMultiplier[i - 1];
            i++;
        }
        rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];

        uint256 busdReward = (rewardAmount / DENOMINATOR) - this.calDoubledCounted(_account);
        uint256 busdleft = IERC20(busd).balanceOf(address(this));

        return busdReward > busdleft ? busdleft : busdReward;
    }
