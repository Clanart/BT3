### Title
Git argument injection via attacker-controlled branch/ref name in `checkoutBranch()` - (File: `app/src/lib/git/checkout.ts`)

### Summary
The signature-mint bug's broken invariant is: **an attacker-controlled value that should be bound to a fixed semantic meaning (a specific claimable ticket) is instead accepted positionally/loosely, letting the attacker redirect what it actually means.** The Desktop analog: a branch/ref name that is meant to be an *opaque identifier* passed to `git checkout` is placed on the command line **before** the `--` end-of-options marker, so a ref name that a hostile remote can legitimately create (starting with `-`) is parsed by git as a **command-line flag** instead of a ref. The attacker fully controls this value because it comes from a cloned/fetched remote (a fork) or from a "Open in Desktop" deep link `branch` query parameter.

### Finding Description
Desktop builds the checkout argument vector in `getBranchCheckoutArgs`: [1](#0-0) 

```
async function getBranchCheckoutArgs(branch: Branch) {
  return [
    branch.name,
    ...(branch.type === BranchType.Remote ? ['-b', branch.nameWithoutRemote] : []),
    '--',
  ]
}
```

`branch.name` is placed **before** the `--` terminator, so git will still try to interpret it as an option if it starts with `-`. This is invoked from `checkoutBranch()`: [2](#0-1) 

Git ref names are allowed to start with `-` (only control chars, space, `~^:?*[\\|"<>`, `@{`, consecutive dots, leading/trailing dot, `.lock` suffix, and trailing `/` are rejected — see `invalidCharacterRegex`): [3](#0-2) 

Note that `sanitizedRefName` (used for *user-typed* branch names in the UI) explicitly strips leading `-`/`+` via `.replace(/^[-\+]*/g, '')`, but `testForInvalidChars` — used to validate the `branch` parameter that arrives from a **remote-controlled deep link** — does **not** perform that same stripping: [4](#0-3) 

So a `x-github-client://openRepo/<url>?branch=-<flag>` deep link, or a real branch on an attacker's fork whose name starts with `-`, both bypass the only guard on this path. From there the dispatcher fetches the attacker's remote and, if a local/remote branch with that literal name exists, checks it out without ever re-validating that the string can't be interpreted as a flag: [5](#0-4) [6](#0-5) 

Existing guards do not stop this path because:
- `testForInvalidChars` only rejects the character classes in `invalidCharacterRegex`; it never checks for a leading `-` (unlike `sanitizedRefName`, which is used only in the UI text box, not in the deep-link parser).
- `getBranchCheckoutArgs` never inserts `--` before `branch.name`; the terminator is appended only at the *end* of the arg list, which is too late to protect the ref-name argument itself.
- `checkoutLocalBranch` only checks that the local branch list contains a branch whose `nameWithoutRemote` equals the untrusted string — it doesn't validate that the string is unambiguously a ref rather than an option.

### Impact Explanation
An attacker who controls a cloned/fetched repository (a malicious fork) can create a real branch whose name begins with `-`, then lure the victim into opening that fork/PR or clicking a "Open in Desktop"/`x-github-client://openRepo` link with a matching `branch=` parameter. When Desktop performs the automatic checkout, the crafted string is placed in the `git checkout` argument list ahead of the `--` separator and is parsed as an option rather than a positional ref. This can alter the semantics of the checkout (e.g., forcing conflict-resolution mode, forcing an orphan branch, or otherwise diverging from the ref the user believed they were checking out), i.e. silent corruption of the working tree/what the user subsequently commits, without any local access, admin rights, or social engineering beyond a normal link click / opening a PR from a fork — both are supported, expected Desktop workflows.

### Likelihood Explanation
Moderate-to-high: the entry points (`x-github-client://openRepo` deep link and "Open in Desktop"/checkout-from-fork flows) are reachable by any user who clicks a link crafted by an attacker or opens a repository/PR from an untrusted fork, which is exactly the "unprivileged...attacker controls a cloned/fetched repository...or a link the user clicks" scenario called out as in-scope. No special git configuration or privileges are required; only a remote branch name starting with `-` (a value forbidden nowhere in `invalidCharacterRegex`).

### Recommendation
- In `getBranchCheckoutArgs` (and any other place building git argument arrays from ref names, e.g. `checkoutConflictedFile`, `checkoutPaths`), always place `--` immediately **before** the ref/path argument, not merely at the end of the array.
- In `parse-app-url.ts`, reuse the same leading `-`/`+` rejection that `sanitizedRefName` applies (or explicitly reject/require quoting for ref names starting with `-`) inside `testForInvalidChars`, so untrusted `branch` values from deep links can't reach git as ambiguous, flag-like tokens.
- Apply the same "must be preceded by `--`" pattern uniformly across all git command builders that consume branch/ref names originating from remotes or URLs (`clone.ts`'s `-b`/branch handling should also be checked).

### Proof of Concept
1. Attacker creates/forks a public repository and pushes a branch literally named `--orphan=pwned` (or any dash-prefixed value that is a valid ref per `git-check-ref-format` but happens to collide with a `git checkout` flag).
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/attacker/repo?branch=--orphan%3Dpwned`.
3. `parseAppURL` (`app/src/lib/parse-app-url.ts:98-117`) accepts the branch value because `testForInvalidChars` does not reject a leading `-`.
4. Victim clicks the link in Desktop; `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl` clones/fetches the attacker repo and calls `checkoutLocalBranch(repository, "--orphan=pwned")` (`app/src/ui/dispatcher/dispatcher.ts:1975-1996`, `2188-2212`).
5. Because the fetched branch's `nameWithoutRemote` literally equals `"--orphan=pwned"`, `checkoutBranch` is invoked, and `getBranchCheckoutArgs` (`app/src/lib/git/checkout.ts:28-36`) yields `["--orphan=pwned", "--"]`, producing the final command `git checkout --progress --orphan=pwned --`, which git parses as the `--orphan` flag rather than a ref-name checkout — diverging from the checkout the user expected and silently altering repository state.

Note: I could not further trace `_checkoutPullRequest`'s exact argument construction for the PR-from-fork variant of this flow within the remaining budget, so it is unverified whether that specific call site shares the same `--` placement bug or a different code path; the `openBranchNameFromUrl`/`checkoutLocalBranch`/`checkoutBranch` chain above is fully verified from local code.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

    const state = this.repositoryStateManager.get(repository)
    const branches = state.branchesState.allBranches

    const { tip } = state.branchesState

    if (tip.kind === TipState.Valid) {
      shouldCheckoutBranch = tip.branch.nameWithoutRemote !== branch

    // to remove the support for string branch names the behavior
    // was moved up to this method to not alter the current behavior.

    // https://youtu.be/IjmtVKOAHPM
    if (shouldCheckoutBranch && localBranch !== undefined) {
      await this.checkoutBranch(repository, localBranch)
