## Analog Identification

The Solidity report flags a check that *looks* like a safety guard but does not actually validate the invariant it claims to protect (`require(_balanceFrom.sub(_amount) >= 0)` is tautological because of built-in overflow protection, so it silently fails to guard "sufficient balance"). The GitHub Desktop analog is the `_resolveWithin` boundary check in the path-containment utility, which is used to decide whether an attacker-influenced path from a deep link is allowed to escape the intended repository directory. The check *looks* like a strict boundary test but is actually a naive string-prefix test, so it does not perform the role its name and doc comment promise. [1](#0-0) 

### Title
Path-traversal guard `resolveWithin` uses naive string-prefix comparison, allowing escape into sibling directories via deep-link `filepath` - (File: `app/src/lib/path.ts`)

### Summary
`_resolveWithin()` is documented to guarantee the resolved path "reside[s] at, or underneath" the given root path, but it validates this with `realResolved.startsWith(realRoot)`, a plain string comparison with no trailing path-separator check.

### Finding Description
The core guard is:
```
return realResolved.startsWith(realRoot) ? resolved : null
``` [2](#0-1) 

`startsWith` treats `/Users/name/Documents/GitHub/repo2/secret.txt` as being "within" root `/Users/name/Documents/GitHub/repo` because the string `repo2...` textually begins with `repo`, even though `repo2` is a completely different, sibling directory. The documented invariant — "resolved path is guaranteed to reside at, or underneath root" — is therefore not actually enforced; the check passes for any sibling whose folder name happens to share the root folder name as a prefix (a common situation, since Desktop itself appends suffixes like `-1`, `-2`, ` (copy)` when cloning a repo with a name collision, or when users manually rename backups such as `repo-old`, `repo.bak`, `repo-backup`).

This function is the guard used by `openRepositoryFromUrl` in the dispatcher when handling the `x-github-desktop://openRepo/...?filepath=...` deep-link action: an absolute path is rejected, but relative segments (e.g. containing `..`) are still passed through `resolveWithin(repository.path, filepath)`, whose result is trusted to be inside the repo before being handed to `shell.showItemInFolder`. [3](#0-2) 

Because the "is-inside-root" check is a tautological prefix match rather than a real boundary test, a `..`-relative `filepath` can resolve to a same-prefix sibling directory and still pass the guard, defeating the stated purpose of `resolveWithin` exactly as the Solidity check failed to guard the balance invariant.

### Impact Explanation
An attacker who gets a victim to click a `x-github-desktop://openRepo/<url>?filepath=../<sibling-prefix>/<file>` deep link can cause Desktop to reveal (via `shell.showItemInFolder`) files located outside the intended repository, in any sibling folder whose name is prefixed by the repository's folder name. This is a genuine violation of the "stay within repo root" invariant that the function is supposed to enforce, and matches the class of externally-triggerable/deep-link-driven, guard-defeating bugs called out as in-scope (attacker controls a link/deep link, resulting in file access outside the repo).

### Likelihood Explanation
Exploitation requires: (1) the victim to click a maliciously crafted `x-github-desktop://` URL — the standard entry vector for this class of Desktop bug — and (2) a suitably-named sibling directory to exist next to the target repository. Because Desktop itself commonly creates such prefix-colliding directories when cloning repositories with duplicate names, and users frequently keep `-old`/`-backup`/`.bak` copies beside working repos, the precondition is plausible without requiring local/admin access or pre-existing malware. This lowers likelihood compared to an unconditional bypass, but it is a real, reachable path through legitimate application logic — I could not fully verify from the index which of the other two call sites (`app-store.ts`, `copilot-conflict-context.ts`) also rely on `resolveWithin` for higher-impact operations (e.g., file reads/writes rather than just `showItemInFolder`), so the worst-case impact of this same guard weakness elsewhere in the codebase is uncertain and would need direct file inspection.

### Recommendation
Fix `_resolveWithin` in `app/src/lib/path.ts` to require an exact match or a match followed by the platform path separator, e.g.:
```ts
const withSep = realRoot.endsWith(sep) ? realRoot : realRoot + sep
return realResolved === realRoot || realResolved.startsWith(withSep) ? resolved : null
```
This closes the prefix-matching gap while preserving the function's documented contract that the resolved path must be "at, or underneath" the root.

### Proof of Concept
1. Victim has cloned a GitHub repo to `~/Documents/GitHub/desktop`, and a sibling directory `~/Documents/GitHub/desktop-secrets` exists (e.g., a stale duplicate clone or backup folder).
2. Attacker sends the victim a link: `x-github-desktop://openRepo/https://github.com/desktop/desktop?filepath=..%2Fdesktop-secrets%2Fcredentials.txt`.
3. `parseAppURL` accepts the relative `filepath` (not absolute, no invalid ref chars), producing an `open-repository-from-url` action. [4](#0-3) 
4. `openRepositoryFromUrl` calls `resolveWithin(repository.path, filepath)`; `path.resolve` normalizes `../desktop-secrets/credentials.txt` into `~/Documents/GitHub/desktop-secrets/credentials.txt`, which `startsWith('~/Documents/GitHub/desktop')` evaluates to `true`, so the guard incorrectly returns the resolved path instead of `null`.
5. Desktop calls `shell.showItemInFolder(resolved)`, revealing the file outside the intended repository to the user/attacker-influenced flow. [5](#0-4)
