## Title
DID recovery backup-list persists across DID transfer/sale, letting the seller's backup DIDs steal the DID after transfer - ([File: chia/wallet/did_wallet/did_wallet.py])

### Summary
The Footium bug is a class of "stale/persistent authorization survives asset transfer" issue: an `approve`/`setApprovalForAll` grant made by the original owner is not cleared when the underlying NFT/escrow is sold, letting the seller later drain the asset from the new owner. Chia's `DIDWallet` has a structurally identical pattern: the DID's `backup_ids` / `num_of_backup_ids_needed` recovery configuration is curried into the DID inner puzzle and, unless explicitly reset, is silently carried over when a DID is transferred (sold) to a new owner. The seller (or their chosen backup DIDs) retain the ability to trigger a DID "recovery" spend and redirect the DID coin to a puzzle hash of their choosing, bypassing the new owner's key.

### Finding Description
When a DID is transferred via `DIDWallet.transfer_did()`, the new inner puzzle is built with the *existing* `backup_ids`/`num_of_backup_ids_needed` unless the recovery list was already reset beforehand: [1](#0-0) 

`get_innerpuz_for_new_innerhash`, used when preparing a DID for handoff to a new owner, keeps the recovery list by design and only comments that "the seller should clean the recovery list" before transferring: [2](#0-1) 

The recovery/backup mechanism itself is intentional (lost-key recovery), but because `backup_ids` and `num_of_backup_ids_needed` are curried directly into the DID's on-chain puzzle hash and are *not* automatically cleared on ownership transfer, a seller who forgets (or deliberately chooses not) to reset the recovery configuration before selling/consigning a DID retains a standing, on-chain-enforced ability to move the DID coin to an address they control — exactly analogous to `FootiumEscrow`'s `setApprovalForERC20/ERC721` remaining valid after a club/NFT sale. The CLI/RPC even exposes a `reset_recovery` / `with_recovery_info` flag specifically because this state is not cleared by default: [3](#0-2) 

The buyer of a DID (or anything relying on that DID, e.g. an NFT wallet keyed off DID ownership) has no way to observe or independently verify that the recovery list was reset unless they inspect the DID's curried recovery hash themselves; a marketplace/exchange flow trusting "current DID owner" is vulnerable the same way Bob trusted "the exchange now owns ClubA."

### Impact Explanation
If a seller transfers/sells a DID without clearing `backup_ids`, the seller's designated backup DIDs can later co-sign a recovery spend and redirect the singleton's control (and, transitively, any NFTs/assets whose ownership is gated by that DID) to a puzzle hash the seller controls, causing unauthorized coin movement/asset theft from the new owner. This matches the "concrete unsigned or unauthorized coin movement" acceptance criterion.

### Likelihood Explanation
This requires only a single malicious/careless DID seller and no attacker cooperation from full nodes, farmers, or other privileged actors — it is entirely reachable through the standard wallet's `did_transfer_did`/`transfer_did` RPC/CLI path, matching a normal offer/trade flow. The default behavior of `transfer_did` preserves recovery info (`with_recovery_info=True`/`reset_recovery=False` default), making the vulnerable configuration the default unless the user explicitly opts to reset.

### Recommendation
Make clearing/rotating the recovery list (`backup_ids`/`num_of_backup_ids_needed`) a mandatory, verifiable part of any DID transfer/sale path rather than an opt-in flag, and provide buyers/marketplaces with an explicit on-chain-verifiable signal (e.g. requiring `num_of_backup_ids_needed == 0` or an empty backup list) before accepting a DID as "safely transferred," analogous to recommending escrow contracts clear approvals before completing a trade.

### Proof of Concept
1. Alice creates DID `D` with `backup_ids = [Alice_backup_did]`, `num_of_backup_ids_needed = 1`.
2. Alice calls `did_transfer_did` with `reset_recovery=False` (the default) to transfer `D` to Bob's puzzle hash — see `DidTransferDidCMD` default at `chia/cmds/wallet.py:862-864` and `DIDWallet.transfer_did` at `chia/wallet/did_wallet/did_wallet.py:805-837`, which keeps `self.did_info.backup_ids` in the new inner puzzle.
3. Bob accepts the DID (and any NFTs bound to it), believing full control has moved to him.
4. Alice's `Alice_backup_did` initiates a recovery spend against `D`'s current coin (satisfying `num_of_backup_ids_needed`), producing a new DID coin with a puzzle hash Alice controls, moving the DID (and its associated ownership rights) away from Bob without his signature. [2](#0-1)

    async def get_innerpuz_for_new_innerhash(self, pubkey: G1Element) -> Program:
        """
        Get the inner puzzle for a new owner
        :param pubkey: Pubkey
        :return: Inner puzzle
        """
        # Note: the recovery list will be kept.
        # In a selling case, the seller should clean the recovery list then transfer to the new owner.
        assert self.did_info.origin_coin is not None
        return did_wallet_puzzles.create_innerpuz(
            p2_puzzle_or_hash=puzzle_for_pk(pubkey),
            recovery_list=self.did_info.backup_ids,
