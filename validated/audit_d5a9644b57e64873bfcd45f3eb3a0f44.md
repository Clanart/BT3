### Title
Zero-signature Schnorr aggregate is accepted as valid - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` accepts an aggregate containing zero signatures when supplied with an empty `keys_and_challenges` list, even though `SchnorrAggregator::complete` explicitly refuses to produce an empty aggregate. An attacker can therefore serialize a malformed aggregate with `Rs.len() == 0` and `s == 0` and have it pass verification. [1](#0-0) [2](#0-1) 

### Finding Description
`SchnorrAggregate::read` trusts the attacker-controlled 32-bit count, reads that many nonce points, and then reads `s`. [3](#0-2) 

When `Rs` and `keys_and_challenges` are both empty, the length check succeeds, no per-signature statements are added, and the sole verification term is `(-0) * G`, the identity. [1](#0-0) 

This differs from aggregate construction, where `SchnorrAggregator::complete` returns `None` if no signatures were aggregated. [4](#0-3) 

### Impact Explanation
A verifier which accepts an attacker-selected aggregate for an empty authorization set treats an encoding the aggregator cannot legitimately produce as a valid signature. The resulting forgery does not prove possession of any private key or authorization of any message; it only satisfies the verifier’s vacuous zero-statement equation. [5](#0-4) 

### Likelihood Explanation
The malicious input is deterministic and requires only a zero length followed by a canonical zero scalar. Exploitation requires the calling protocol to permit an empty `keys_and_challenges` set and to interpret successful verification of that set as meaningful. [3](#0-2) [6](#0-5) 

### Recommendation
Reject empty aggregates in both `SchnorrAggregate::read` and `SchnorrAggregate::verify`, matching the existing producer-side invariant in `SchnorrAggregator::complete`. Verification should return `false` when `keys_and_challenges.is_empty()` before evaluating the multiexp. [3](#0-2) [2](#0-1) 

### Proof of Concept
For a ciphersuite with a canonical 32-byte zero-scalar encoding, construct:

```text
00 00 00 00                                      // Rs length = 0
00 ... 00                                        // s = 0, canonical scalar encoding
```

These bytes deserialize as `SchnorrAggregate { Rs: [], s: 0 }`. Calling `verify(dst, &[])` passes the length check, appends only `(-0) * G` to the statement list, and `multiexp_vartime` evaluates to the identity. [3](#0-2) [7](#0-6)
