### Title
Python C-extension `MergeFrom`/`MergeFromString` allowed use-after-free of oneof submessage wrappers on oneof-switch during merge - (File: `python/google/protobuf/pyext/message.cc`)

### Summary
The Kakarot `RIPEMD160` bug is a "stale-handle-across-resource-switch" defect: the Cairo code caches a pointer (`start`) to a dict *before* the dict is discarded and replaced by a brand-new dict, then later uses the stale pointer to finalize the new dict, producing a segment mismatch and a crash. The closest Protobuf analog with the same failed invariant — a long-lived handle captured before an internal resource is torn down/replaced, then dereferenced afterward — is the (now-fixed) use-after-free in the CPython protobuf extension's oneof-merge path: a Python wrapper object caches a raw pointer to a C++ submessage that lives inside a oneof; a subsequent `MergeFrom`/`MergeFromString()` call whose *source* message sets a different member of the same oneof causes the C++ layer to delete the old submessage object as part of the oneof switch, while the Python wrapper still holds (and can dereference) the now-freed pointer.

### Finding Description
`CMessage` objects cache Python wrapper objects for message-typed submessage fields in `composite_fields`. When a submessage field lives inside a `oneof`, calling `.MergeFrom()`/`.MergeFromString()`/`.ParseFromString()` on the *destination* message with a payload that sets a *different* member of the same oneof causes the underlying C++ message's oneof-switch logic (`Reflection`-driven merge, and at the tc-parser level `TcParser::ChangeOneof`, see `src/google/protobuf/generated_message_tctable_lite.cc:1989-2053`) to delete the previously active oneof submessage object: [1](#0-0) 

Before the fix present in this checkout, the Python wrapper object (`sub_ref` in the test) retained a raw pointer to that now-deleted C++ `Message` and dereferencing it (e.g., reading `.bb`) would read/write freed memory — exactly analogous to the Cairo bug's `start` pointer referencing a discarded dict segment. The invariant violated in both cases is: *"a handle/pointer captured before a resource is replaced must not be dereferenced against the new resource, and if the old resource is destroyed, all outstanding handles to it must be invalidated or the destruction must be deferred."* In Kakarot, the mitigation is to finalize the *original* dict properly (matching `start` to the resource it actually describes). In Protobuf, the mitigation added is to detect the incoming oneof switch *before* the C++-level merge deletes the old submessage, and either release/detach the outstanding Python wrapper or reuse the temporary-message pattern so the switch happens off of a throwaway object: [2](#0-1) [3](#0-2) [4](#0-3) 

The attacker-controlled value is the wire-format oneof field number/tag embedded in the bytes passed to `MergeFrom`/`MergeFromString`, which determines whether the destination's existing oneof member is torn down. The missing check (pre-fix) was: no reconciliation between the C++ oneof-switch deletion and any live Python wrapper that had already cached a pointer into the old submessage.

### Impact Explanation
A successful trigger causes a Python-level use-after-free: the cached wrapper (`sub_ref`) dereferences freed heap memory belonging to the deleted C++ submessage. This can lead to memory corruption, information disclosure of unrelated heap contents, or a crash, depending on what has since reallocated that memory — a materially more severe outcome than the Kakarot report's revert-only DoS, since this is native memory corruption reachable purely through the public parsing/merge API (`MergeFrom`, `MergeFromString`) with attacker-supplied bytes, requiring only that the consuming application retain a reference to a oneof submessage across a merge call (a common, non-exotic usage pattern, e.g. caching `msg.oneof_field` and later calling `msg.MergeFromString(new_bytes)`).

### Likelihood Explanation
Likelihood is bounded by the precondition that application code must hold a live Python reference to a oneof submessage (`m.oneof_nested_message`) across a subsequent merge/parse call that switches the oneof to a different member — a realistic but not universal usage pattern. The trigger itself requires only two ordinary, otherwise-valid serialized protobuf messages differing in which oneof member is set; no malformed/attacker-crafted wire tricks beyond normal use of the oneof field are needed. The fix is present in this checkout, indicating the bug was real and reachable via the public `MergeFrom`/`ParseFromString`/`MergeFromString` APIs before the mitigation landed.

### Recommendation
Confirm (and keep passing) the regression test that reproduces this exact scenario, and ensure the `MaybeReleaseOneofBeforeMerge` / `FixupMessageAfterMerge` reconciliation is invoked on every code path that can switch a oneof case during merge (including nested submessages reached transitively, `ParseFromString`, `MergeFromString`, and `MergeFrom` from another `CMessage`). Additionally, audit other language bindings (Ruby, PHP, Java's JNI/Kotlin-less wrapper caches, C#) for the same "wrapper caches raw pointer into a oneof member, native layer deletes on switch" pattern, since a fix was only located for the CPython extension.

### Proof of Concept
This is directly reproduced by the existing regression test in this checkout, which explicitly documents the pre-fix UAF: [5](#0-4) 

Steps: (1) create `m`, set `m.oneof_nested_message.bb = 42`, serialize to `data1`; (2) create `m2`, `m2.ParseFromString(data1)`, then cache `sub_ref = m2.oneof_nested_message` (a Python wrapper holding a raw pointer into `m2`'s internal oneof submessage); (3) create `m3`, set a *different* oneof member `m3.oneof_uint32 = 100`, serialize to `data2`; (4) call `m2.MergeFromString(data2)` — this causes `m2`'s C++ layer to detect the oneof switch and (pre-fix) delete the old nested-message object referenced by `sub_ref`; (5) accessing `sub_ref.bb` afterward dereferences freed memory pre-fix, but is safe post-fix because `MaybeReleaseOneofBeforeMerge`/`FixupMessageAfterMerge` detach/reconcile the wrapper beforehand.

int MaybeReleaseOneofBeforeMerge(CMessage* self, const Message& other) {
  CMessage::CompositeFieldsMap* composite_fields =
      self->composite_fields.TryGet();
  if (!composite_fields) {
    return 0;
  }

  Message* message = AssureWritable(self);
  if (message == nullptr) return -1;
  const Reflection* reflection = message->GetReflection();
  PyMessageFactory* factory = GetFactoryForMessage(self);
  std::vector<const FieldDescriptor*> fields_to_release;
  std::vector<std::pair<const FieldDescriptor*, ScopedPyObjectPtr>>
      nested_message_fields;
  composite_fields->ForEach([&](const void* key, PyObject* value) {
    const FieldDescriptor* descriptor =
        reinterpret_cast<const FieldDescriptor*>(key);
    if (descriptor->cpp_type() == FieldDescriptor::CPPTYPE_MESSAGE &&
        // For normal repeated message, MergeFrom will append the messages.
        // For message map with same keys, it is overwrite
        !descriptor->is_repeated() &&
        reflection->HasField(*message, descriptor)) {
      if (reflection->HasField(other, descriptor)) {
        Py_INCREF(value);
        nested_message_fields.emplace_back(descriptor, value);
      } else {
        // Release oneof message if the other message has set a different oneof
        const OneofDescriptor* oneof = descriptor->containing_oneof();
        if (oneof && reflection->HasOneof(other, oneof)) {
          fields_to_release.push_back(descriptor);
        }
      }
    }
  });

  for (const auto& [field, value] : nested_message_fields) {
    if (MaybeReleaseOneofBeforeMerge(
            reinterpret_cast<CMessage*>(value.get()),
            reflection->GetMessage(other, field, factory->message_factory)) <
        0) {
      return -1;
    }
  }

  for (const FieldDescriptor* field : fields_to_release) {
    if (InternalReleaseFieldByDescriptor(self, field) < 0) {
      return -1;
    }
  }
  return 0;
}

static PyObject* MergeFromStringImpl(CMessage* self, PyObject* arg,
                                     bool is_cleared) {
  Py_buffer data;
  if (PyObject_GetBuffer(arg, &data, PyBUF_SIMPLE) < 0) {
    return nullptr;
  }
  auto cleanup_data = absl::MakeCleanup([&data] { PyBuffer_Release(&data); });

  Message* message = AssureWritable(self);
  if (message == nullptr) {
    return nullptr;
  }

  // We parse into a temporary message first to detect oneof switches before
  // modifying the target message. This allows us to release the wrappers
  // for switching oneof fields in the target message before they are deleted
  // by C++ during the merge, preventing use-after-free bugs.
  // We use heap allocation (nullptr arena) for the temporary message so that
  // it is collected immediately after the merge, avoiding wasting arena memory.
  std::unique_ptr<Message> temp_message;
  Message* merge_dst;

  if (is_cleared) {
    // Check that it is really empty.
    ABSL_DCHECK_EQ(message->ByteSizeLong(), 0);
    merge_dst = message;
  } else {
    temp_message.reset(message->New(nullptr));
    merge_dst = temp_message.get();
  }

  PyMessageFactory* factory = GetFactoryForMessage(self);
  int depth = allow_oversize_protos
                  ? INT_MAX
                  : io::CodedInputStream::GetDefaultRecursionLimit();
  const char* ptr;
  internal::ParseContext ctx(
      depth, false, &ptr,
      absl::string_view(static_cast<const char*>(data.buf), data.len));

  ctx.data().pool = factory->pool->pool->get();
  ctx.data().factory = factory->message_factory;

  ptr = merge_dst->_InternalParse(ptr, &ctx);

  if (is_cleared) {
    // If we merged into the final destination, fix up now before we might have
    // an early exit.
    FixupMessageAfterMerge(self);
  }
