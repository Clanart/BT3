### Title
`Scanner::register_offset` silently aliases distinct requested offsets to an existing `script_pubkey` entry, so outputs intended for a later offset are reported under an earlier registration - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary

Analogous to `Token::setReservedUntilTokenId()` updating a base parameter without re-deriving the dependent `tokenRecipient[]` assignments, `Scanner::register_offset` lets a newly requested scalar offset collapse onto an already-registered `script_pubkey` without recording the distinct offset the caller asked for. The `scripts` map (script → offset) is the Serai equivalent of `tokenRecipient[]`: it is the sole mapping used at scan time to decide which key-derivation offset a received output belongs to.

### Finding Description

`Scanner` stores `scripts: HashMap<ScriptBuf, Scalar>` (`mod.rs:155`), mapping a P2TR script to the scalar offset needed to derive the spending key. `register_offset` (`mod.rs:180-196`) takes a caller-chosen `offset`, computes `key + offset*G`, and if that point is odd (unusable for P2TR) it increments `offset` until an even point yields a `script`. If the resulting `script` is already a key in `self.scripts`, the function returns `None` (`mod.rs:187-189`) — the requested offset is discarded entirely and the pre-existing offset remains bound to that script.

This makes offsets **surjective, not bijective** (acknowledged in the doc comment, `mod.rs:174-175`): the order and values of previously registered offsets determine whether a later, distinct offset is usable. `scan_transaction` (`mod.rs:199-214`) then emits a `ReceivedOutput { offset: *offset, ... }` looked up solely by `script_pubkey` (`mod.rs:205`). When two distinct logical offsets converge to the same derived point/script, every output paying that script is stamped with whichever offset was registered first — the newer logical offset has no entry anywhere.

### Impact Explanation

Any consumer that registered offset `o_b` (receiving `Some(used)` where `used != o_b`, or `None` on collision) and later relies on `ReceivedOutput::offset()` to attribute or spend the output will see outputs attributed to the earlier offset's identity. Because the offset is serialized into `ReceivedOutput` (`mod.rs:91-92`, `mod.rs:138`) and is the only handle the signer has for reconstructing the spend key (`keys.offset(...)` / `tweak_keys`, `mod.rs:46-75`), a collision means:

- funds sent to an address derived for the rejected/incremented offset are reported as belonging to the colliding registration, or
- if the caller ignores the `None`/`Some(used)` distinction (nothing in the API forces reconciliation between requested and used offset), the output is effectively unspendable for the purpose it was derived for — mirroring the Nouns bug where founders' token IDs were never re-mapped.

The unprivileged reachability is via `scan_transaction`/`scan_block` fed arbitrary Bitcoin transactions (`mod.rs:199-227`): outputs observed on-chain are only as attributable as the `scripts` map is injective, and it is not.

### Likelihood Explanation

Each derived point is odd with ~50% probability, so increments are common (`mod.rs:181-184`). A collision requires the incremented offset to land on a previously registered point — low probability for random offsets, but the API documents that offsets are caller/integrator-chosen, and sequential or structured offset schemes (e.g., `o`, `o+1`, `o+2`) make consecutive-integer collisions systematic: registering `o` then `o+1` collides whenever `key + (o+1)*G` needed no increment but equals a stored point, or when `o` incremented *into* `o+1`'s slot first. The failure is also silent (`None`), so integrators must explicitly check the return value — an unenforced contract identical in shape to the Nouns setter that silently left stale assignments.

Caveat: the severity of misattribution depends on downstream consumers (outside the in-scope file) that reconcile `ReceivedOutput::offset()` with registered offsets; within the indexed code I verified the collision and the misattributed `offset` field, but could not fully trace every consumer.

### Recommendation

- Have `register_offset` return a distinct error/`None` variant distinguishing "offset unusable" from "script collision", and/or store all requested offsets that converge on a script so callers can reconcile.
- At minimum, when `used != requested`, surface the divergence loudly; when a collision occurs, either reject earlier at key-derivation time or record the mapping `(requested_offset → used_offset)` so `ReceivedOutput` can carry the caller's logical offset rather than only the stored scalar.
- Alternatively, use a BIP-32-style index or transcript-derived offset scheme guaranteeing injectivity, rather than caller-supplied scalars that are silently incremented.

### Proof of Concept

```rust
// networks/bitcoin/src/wallet/mod.rs semantics
let key = ProjectivePoint::GENERATOR * scalar_base;
let mut scanner = Scanner::new(key).unwrap();

// Register offset o1; suppose key + o1*G is odd, so it increments to o1+1
// and registers script S = p2tr(key + (o1+1)*G), storing offset o1+1.
let used1 = scanner.register_offset(o1).unwrap(); // may return o1+1

// Later, a second logical purpose registers o2 = o1 + 1 directly.
// Its derived point equals the already-stored point -> script S already in map.
let res2 = scanner.register_offset(o1 + 1); // returns None, offset dropped

// Any on-chain output paying script S is now reported by scan_transaction
// with `offset: o1+1` from the first registration, never attributable to
// the second logical purpose, even though the depositor derived the
// address intending the second offset.
```
