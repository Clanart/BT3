### Title
GitHubRepository records are keyed by mutable `[ownerID+name]` and silently replaced/overwritten instead of GitHub's immutable numeric repo id, allowing an attacker-controlled API repository object to swap a trusted repo's clone/upstream URL - (File: `app/src/lib/stores/repositories-store.ts`)

### Summary
`RepositoriesStore` stores GitHub repository metadata (`cloneURL`, `htmlURL`, `parentID`, `permissions`) in a Dexie table whose uniqueness constraint is `[ownerID+name]` [1](#0-0) , not GitHub's own immutable numeric repository id. `_upsertGitHubRepository` looks up any "existing" row solely by that `[ownerID+name]` key and then unconditionally `put()`s the new API data over it, replacing `cloneURL`/`htmlURL`/`permissions`/`parentID` [2](#0-1) [3](#0-2) . This is functionally the same "deterministic address, no collision guard" pattern as the `PoolFactory.createPool` bug: the (owner, name) tuple acts like `create2`'s `(base, fyToken)` salt — whoever can produce an API repository object whose owner login + name resolve to an existing key can force Desktop to replace what that key points to, with no check that the underlying GitHub repository is actually the same entity.

### Finding Description
- The composite key used for dedup/lookup is `[ownerID+name]` [4](#0-3) , both of which are attacker-influenceable: `name` and `owner.login` come directly from GitHub API repository objects that Desktop fetches automatically (e.g. when refreshing a repo, resolving a PR's `head.repo`, or matching a repo from a URL/deep link) — see `_upsertGitHubRepository` being fed `IAPIRepository`/`IAPIFullRepository` objects sourced from `pullRequest.head.repo`, `fetchRepository`, etc. [5](#0-4) [6](#0-5) .
- Because `owners.put()` matches only on the case-insensitive `key` (endpoint+login) and `gitHubRepositories.put()` matches only on `[ownerID+name]`, if the same owner login later has a different underlying repository with the same name (e.g. the original repo was deleted/renamed and a new one created, or an attacker registers/renames a repo to collide with a name Desktop already cached for that owner), the stale local record is silently overwritten with the new repository's `cloneURL`/`htmlURL`/`parentID` via `db.gitHubRepositories.put(updatedGitHubRepo)` [7](#0-6) . There is no check comparing GitHub's actual numeric repository `id` (only the DB's own auto-increment `id` is tracked, which is reused via `existingRepo.id`) [8](#0-7) .
- This cached `GitHubRepository` (specifically its `cloneURL` and `parent`) directly drives security-relevant, silent git operations:
  - `findUpstreamRemote`/`addUpstreamRemoteIfNeeded`/`updateExistingUpstreamRemote` add or repoint the `upstream` remote to `parent.cloneURL` without prompting [9](#0-8) [10](#0-9) .
  - `cloneAgain`/"Clone in Desktop" re-clone flows use `gitHubRepository.cloneURL` as the source URL for a fresh clone [11](#0-10) [12](#0-11) .
  - `getNonForkGitHubRepository` picks the fork's `parent` as the effective contribution target used to compute push/pull targets [13](#0-12) .

### Impact Explanation
If the cached `[ownerID+name]` record is silently swapped to point at a different (attacker-controlled) repository, Desktop can be made to add/repoint an `upstream` remote, or re-clone a "missing" repository, toward a URL the user never explicitly reviewed. Because these operations run without additional confirmation (`addUpstreamRemoteIfNeeded`, `cloneAgain`), this can silently corrupt what the user pulls/pushes from — the exact "existing ownership/target silently replaced" class of bug the source report describes, adapted to Desktop's repository-identity cache rather than a smart-contract factory.

### Likelihood Explanation
Exploitation requires only:
1. An unprivileged GitHub-side action (deleting/renaming/recreating a repository under an owner login Desktop has already cached, or crafting API repository objects surfaced through PR fork metadata that Desktop consumes automatically), and
2. The victim previously having interacted with that owner/name pair in Desktop (fork tracking, PR-based repo caching, or a prior "Open in Desktop"/clone).

No local access, admin rights, or pre-existing malware is required — the update path (`repositoryWithRefreshedGitHubRepository`, PR/fork/`open-repository-from-url` flows) runs automatically in the background whenever Desktop is open, using ordinary GitHub API responses that a repository owner or fork-relationship can influence.

### Recommendation
Track and key GitHub repository records by GitHub's own immutable numeric repository id (`IAPIRepository.id`) rather than (or in addition to and authoritative over) `[ownerID+name]`. Before overwriting an existing `IDatabaseGitHubRepository` row, verify the incoming API object's numeric id matches the previously stored id; if it doesn't, treat it as a new repository (insert a new row / prompt the user) instead of mutating the existing record's `cloneURL`/`parentID` in place. Additionally, consider warning the user before automatically repointing an `upstream` remote or re-using a cached `cloneURL` for re-cloning when the underlying repository identity has changed.

### Proof of Concept
1. User forks/contributes to `github.com/alice/project` in Desktop; Desktop caches an `owners` row keyed by `endpoint+alice` and a `gitHubRepositories` row keyed by `[ownerID(alice)+"project"]` with `cloneURL`/`parentID` set via `_upsertGitHubRepository` [7](#0-6) .
2. `alice` later deletes `project` and creates a brand-new repository also named `project` (a different, attacker-controlled repository with a new numeric GitHub id).
3. Any background refresh path that re-fetches repository info for that owner/name (e.g. `repositoryWithRefreshedGitHubRepository`, PR fork resolution in `openPullRequestFromUrl`) calls `upsertGitHubRepository`/`_upsertGitHubRepository` again with the new API object [6](#0-5) .
4. Because the lookup only matches `[ownerID+name]`, the existing DB row is found and `put()`-overwritten with the new repo's `cloneURL`/`htmlURL`/`parentID`, with no numeric-id comparison [2](#0-1) .
5. If the user's local repo was "missing" and clicks "Clone again," or if Desktop calls `addUpstreamRemoteIfNeeded`, the new (attacker-controlled) `cloneURL` is used to clone/add a remote without further confirmation [11](#0-10) [14](#0-13) .

    // and since it's possible that the user has both the fork and the parent
    // repositories in the app we don't want to overwrite the permissions hash
    // in the parent repository if we can help it or else we'll end up in a
    // perpetual race condition where updating the fork will clear the
    // permissions on the parent and updating the parent will reinstate them.
    const permissions =
      getPermissionsString(gitHubRepository) ??
      existingRepo?.permissions ??
      undefined

    // If we're told to ignore the parent then we'll attempt to use the existing
    // parent and if that fails set it to null. This happens when we want to
    // ensure we have a GitHubRepository record but we acquired the API data for
    // said repository from an API endpoint that doesn't include the parent
    // property like when loading pull requests. Similarly even when retrieving
    // a full API repository its parent won't be a full repo so we'll never know
    // if the parent of a repository has a parent (confusing, right?)
    //
    // We do all this to ensure that we only set the parent to null when we know
    // that it needs to be cleared. Otherwise we could have a scenario where
    // we've got a repository network where C is a fork of B and B is a fork of
    // A which is the root. If we attempt to upsert C without these checks in
    // place we'd wipe our knowledge of B being a fork of A.
    //
    // Since going from having a parent to not having a parent is incredibly
    // rare (deleting a forked repository and creating it from scratch again
    // with the same name or the parent getting deleted, etc) we assume that the
    // value we've got is valid until we're certain its not.
    const parentID = ignoreParent
      ? existingRepo?.parentID ?? null
      : parent?.dbID ?? null

    const updatedGitHubRepo: IDatabaseGitHubRepository = {
      ...(existingRepo?.id !== undefined && { id: existingRepo.id }),
      ownerID: owner.id,
      name: gitHubRepository.name,
      private: gitHubRepository.private,
      htmlURL: gitHubRepository.html_url,
      cloneURL: gitHubRepository.clone_url,
      parentID,
      lastPruneDate: existingRepo?.lastPruneDate ?? null,
      issuesEnabled: gitHubRepository.has_issues,
      isArchived: gitHubRepository.archived,
      permissions,
    }

    if (existingRepo !== undefined) {
      // If nothing has changed since the last time we persisted the API info
      // we can skip writing to the database and (more importantly) avoid
      // telling store consumers that the repo store has changed.
      if (shallowEquals(existingRepo, updatedGitHubRepo)) {
        return this.toGitHubRepository(existingRepo, owner, parent)
      }
    }

    const id = await this.db.gitHubRepositories.put(updatedGitHubRepo)
    this.emitUpdatedRepositories()
    return this.toGitHubRepository({ ...updatedGitHubRepo, id }, owner, parent)

export function findUpstreamRemote(
  parent: GitHubRepository,
  remotes: ReadonlyArray<IRemote>

  const upstream = remotes.find(r => r.name === UpstreamRemoteName)

export function getNonForkGitHubRepository(
  repository: RepositoryWithGitHubRepository
): GitHubRepository {
  if (!isRepositoryWithForkedGitHubRepository(repository)) {
    // If the repository is not a fork, we don't have to worry about anything.
    return repository.gitHubRepository
  }

  const forkContributionTarget = getForkContributionTarget(repository)

  switch (forkContributionTarget) {
    case ForkContributionTarget.Self:
      return repository.gitHubRepository
    case ForkContributionTarget.Parent:
      return repository.gitHubRepository.parent
    default:
      return assertNever(
        forkContributionTarget,
        'Invalid fork contribution target'
      )
  }
