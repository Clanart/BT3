### Title
`isGitHubHost` misclassifies attacker‑controlled hostnames as trusted GitHub Enterprise endpoints via an incomplete hostname pattern - ([File: app/src/lib/api.ts])

### Summary
`getEndpointKind` in the git credential-helper trampoline decides whether a remote host should be treated as a first‑party GitHub endpoint (`github.com`/`enterprise`) or a `generic` third‑party host, and that decision gates whether Desktop uses its internal GitHub sign-in flow versus the generic credential path. [1](#0-0)  The final fallback of that decision relies on `isGitHubHost`, which — like the `_isRestrictedFunction` selector allowlist in the report — enumerates only a few known-good/known-bad hostname patterns instead of exhaustively deriving trust from a canonical source. In particular it treats any hostname matching `/(^|\.)(github)\./` as a trusted GitHub host, before ever reaching the network-based verification step. [2](#0-1) 

### Finding Description
`isGitHubHost(url)` is a "best effort" classifier used to short‑circuit an actual network probe. It runs, in order:
1. Direct check for `github.com`/`api.github.com` or a configured GHE endpoint (`isDotCom`/`isGHE`).
2. A `isKnownThirdPartyHost` deny‑list check (`dev.azure.com`, `gitlab.com`, `bitbucket.org`, `amazonaws.com`, `visualstudio.com`, and subdomains). [3](#0-2) 
3. A regex heuristic: `if (/(^|\.)(github)\./.test(hostname)) return true` — intended to catch enterprise hosts like `github.example.com`. [4](#0-3) 
4. Only after all of that fails does it perform an actual network request to `${endpoint}/meta` and check for the `x-github-request-id` response header, which is the only step that genuinely proves the host is GitHub. [5](#0-4) 

Exactly like the `_isRestrictedFunction` bug (an enumerated, non‑exhaustive selector list used for a security decision), step 3 is an enumerated pattern that an attacker fully controls: any hostname where `github.` appears as, or immediately after, a label boundary — e.g. `github.attacker-domain.com`, `sub.github.attacker-domain.com`, or `github.co` — satisfies the regex and returns `true` immediately, **without ever reaching the network verification in step 4**. The check does not verify that `github` is the actual registered domain, only that a label named `github` exists somewhere left of a dot.

This function feeds directly into `getEndpointKind` in the trampoline credential helper: when none of the direct/`WWW-Authenticate`/cached-account checks apply, `getEndpointKind` calls `isGitHubHost(endpoint)` and, if it returns `true`, classifies the credential request as `'enterprise'` rather than `'generic'`. [6](#0-5)  That classification changes downstream behavior in `getCredential`: for a `generic` endpoint, Desktop uses the generic-credential/external-helper path and only stores/prompts credentials scoped to that specific host. [7](#0-6)  For a non‑generic (`enterprise`) endpoint with no matching stored account, Desktop instead calls `ui.promptForGitHubSignIn(endpoint)`, i.e. it invokes Desktop's first‑party "Sign in to GitHub Enterprise" UI/OAuth flow against the attacker's hostname, and any resulting account/token gets bound to that host as if it were a legitimate GitHub Enterprise server. [8](#0-7) 

### Impact Explanation
The attacker primitive here is a git remote/proxy response: an attacker who controls a remote URL a user clones/fetches/pushes to (e.g. `https://github.ci-attacker.example.com/...`, added via a malicious clone URL, submodule, or an existing remote silently altered) can cause Desktop's credential helper to classify their host as a trusted GitHub Enterprise endpoint purely by virtue of the string `github.` appearing in the hostname — no real GitHub response is required and the actual network verification (`/meta` request checking `x-github-request-id`) is bypassed entirely. This corrupts the trust decision (`endpointKind`) that governs whether Desktop treats a git host as first‑party GitHub (with its own sign‑in/account‑binding UX) or as an untrusted third party. The practical consequence is that Desktop's GitHub sign‑in flow — normally reserved for real GitHub/GHE hosts — gets invoked against attacker infrastructure, and any account bound during that flow is now associated with the attacker's host in Desktop's account store, which is the kind of "unauthorized OAuth or account binding" outcome called out as valid impact.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the user to interact with a git remote whose hostname is crafted to contain a `github.`-labeled component (fully attacker-controlled, e.g. via a spoofed clone URL, malicious fork remote, or DNS-controlled subdomain such as `github.attacker.tld`), and it only matters when none of the earlier, stronger checks (`isDotCom`, `isGHE`, cached account match, `WWW-Authenticate` realm) already resolve the classification — i.e., when Desktop has no prior relationship with that host. This mirrors the report's own "Low" likelihood rating for a narrow but concretely reachable case in a security-relevant enumeration/allowlist.

### Recommendation
Remove the heuristic regex short-circuit in `isGitHubHost` (`app/src/lib/api.ts:2451-2454`) — or at minimum require it to still be corroborated by the network `/meta` + `x-github-request-id` check — so that hostname classification for GitHub Enterprise cannot be spoofed by simply embedding the label `github` in an attacker-controlled domain. Restrict trust decisions in `getEndpointKind`/`isGitHubHost` to verified sources: exact `isDotCom`/`isGHE` matches, previously-established accounts, or a genuinely verified `/meta` response — never a bare substring/regex match on the hostname.

### Proof of Concept
1. Attacker stands up a server at `https://github.malicious-example.com` that does not need to emit `x-github-request-id`.
2. Victim adds/clones this URL as a remote in Desktop (e.g., via a crafted clone link, a compromised `.git/config`, or a fork whose upstream remote is swapped).
3. When git authenticates against this remote, Desktop's credential helper trampoline invokes `getCredential` → `getEndpointKind(cred, store)`. [9](#0-8) 
4. None of `isGist`, `isDotCom`, `isGHE`, cached `WWW-Authenticate` realms, or `findGitHubTrampolineAccount` match, so control falls through to `isGitHubHost(endpoint)`. [10](#0-9) 
5. Inside `isGitHubHost`, the hostname `github.malicious-example.com` matches `/(^|\.)(github)\./`, so the function returns `true` immediately without making the `/meta` network request. [4](#0-3) 
6. `getEndpointKind` returns `'enterprise'`; since no stored account matches this endpoint, `getCredential` calls `ui.promptForGitHubSignIn(endpoint)`, launching Desktop's GitHub Enterprise sign-in UI against the attacker's host and binding any resulting account to it. [8](#0-7) 

Note: I was unable to fully inspect `trampoline-ui-helper.ts`'s `promptForGitHubSignIn` implementation (ran out of tool iterations), so the exact downstream UX (e.g., whether it initiates a real OAuth authorization request to the attacker's URL, or only a generic-looking dialog) is not fully confirmed — this should be verified in a live session before treating this as fully weaponized, but the misclassification of the hostname itself is confirmed directly from the code.

async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

const knownThirdPartyHosts = new Set([
  'dev.azure.com',
  'gitlab.com',
  'bitbucket.org',
  'amazonaws.com',
  'visualstudio.com',
])

const isKnownThirdPartyHost = (hostname: string) => {
  if (knownThirdPartyHosts.has(hostname)) {
    return true
  }

  for (const knownHost of knownThirdPartyHosts) {
    if (hostname.endsWith(`.${knownHost}`)) {
      return true
    }
  }

  return false
}
