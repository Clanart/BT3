### Title
Line-based partial-commit patch generated from a stale diff, silently committing wrong hunks when disk content changes between selection and commit - (File: app/src/lib/git/apply.ts)

### Summary
`applyPatchToIndex` builds the per-file patch for a partial (line-level) commit by calling `getWorkingDirectoryDiff(repository, file)` **at staging time**, and then feeds that freshly-computed diff into `formatPatch`, which applies the user's previously-recorded `DiffSelection` (line indices) against it. [1](#0-0) [2](#0-1) 
There is no check that the diff used to build the selection (the one the user visually reviewed in the UI) is the same diff being staged. The selection is purely index-based (`hunk.unifiedDiffStart + lineIndex`) and is silently reapplied to whatever hunks exist in the newly-fetched diff.

### Finding Description
`DiffSelection` in `WorkingDirectoryFileChange` is preserved across working-directory refreshes purely by carrying over the selection object (`existingFile.selection`) onto the newly-parsed file entry, without any correlation to diff content: [3](#0-2) 

When the user commits, `_commitIncludedChanges` reads `state.changesState.workingDirectory.files` (with whatever selection was last set) and passes them straight to `createCommit`: [4](#0-3) 

`createCommit` resets the index and calls `stageFiles`, which for any file with a partial selection calls `applyPatchToIndex`: [5](#0-4) [6](#0-5) 

`applyPatchToIndex` re-reads the working-directory diff from disk *right before* building the patch: [1](#0-0) 

`formatPatch` then walks this brand-new diff's hunks and, for every line, calls `file.selection.isSelected(absoluteIndex)` where `absoluteIndex` is simply `hunk.unifiedDiffStart + lineIndex` from the *new* diff: [7](#0-6) 

If the file's content on disk changes between the moment the user visually selected lines in the diff viewer and the moment `_commitIncludedChanges` actually runs (e.g. because a build tool, formatter, `.gitattributes` filter, editor autosave, or any file-system event modifies the file after the diff was rendered but before the click registers/executes — including content pulled in by a background `checkout`/`pull`/LFS smudge triggered from a remote/fetch that races with the user's commit action), the hunk boundaries and line ordering in the newly fetched diff can differ substantially from the diff the user reviewed. Since the selection is reapplied by raw index rather than by content-identity, `formatPatch` can select/deselect entirely different lines than what the user intended, and `git apply --cached` will happily apply that patch. There is no re-validation step comparing the diff used to build the selection against the diff used to build the patch — no hash, no line-content, no hunk-signature check.

The `changes-state.ts` diff-invalidation logic only clears the cached `diff` shown in the UI when the file selection changes or a different file is selected; it does not invalidate or re-derive the line `DiffSelection` itself when the underlying diff content changes for the *same* file id: [8](#0-7) 

### Impact Explanation
This allows silent corruption of what the user commits and pushes: content the user never reviewed or explicitly selected can be staged and committed under a message the user wrote for different, previously-reviewed content. Because Desktop stages via `git apply --cached` using this synthesized patch rather than `git add -p`'s interactive re-diff-and-confirm cycle, there is no secondary confirmation that the applied hunks match user intent. In a supply-chain-relevant scenario (a build/lint pre-commit hook, an editor plugin, or content rewritten as a side effect of a fetched/pulled remote change touching the same file) an attacker who can trigger a file rewrite on disk between diff-render and commit-click can cause GitHub Desktop to include or exclude lines the user did not authorize, without any diff mismatch warning shown before the commit is created.

### Likelihood Explanation
Medium: it requires a window between the user viewing/selecting a partial diff and the commit action executing, and something (not the attacker's UI interaction) changing the file's content within that window — realistic via auto-formatters/hooks/LFS smudge filters/background file watchers tied into a repository whose content is attacker-influenced (e.g., a cloned/fetched repo carrying a build step or `.gitattributes` filter that rewrites tracked files). It does not require local/physical access, admin rights, or leaked credentials — only content that Desktop already trusts and processes automatically (files in the working copy of a repo the user opened).

### Recommendation
Before calling `applyPatchToIndex`/`formatPatch` in `stageFiles`, re-fetch and compare the diff against the one used when the user's `DiffSelection` was created (e.g., by hashing hunk headers/line content or storing a diff fingerprint alongside the `DiffSelection`). If the diff has changed since the selection was made, abort the partial stage for that file and force the UI to reload the diff and require the user to reselect, rather than silently reapplying stale line indices to new content.

### Proof of Concept
1. Open a repository in Desktop and modify a tracked text file so it has several hunks.
2. In the Changes view, partially select specific lines/hunks to include in the commit (this populates `DiffSelection` with absolute line indices tied to the currently rendered diff) — see `onDiffLineIncludeChanged`/`changeFileLineSelection` flow feeding `DiffSelection`.
3. Before clicking "Commit", have an external process (simulating an auto-formatter/hook/background rewrite triggered by repo content, e.g. a `post-checkout`/`post-merge` hook bundled in the cloned repository) rewrite the same file, shifting/altering hunks (e.g., reordering lines or adding/removing lines above the selected hunk).
4. Click "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-reads the diff from disk via `getWorkingDirectoryDiff` [1](#0-0)  and `formatPatch` reapplies the old `DiffSelection` indices to the new hunks [7](#0-6) .
5. Inspect the resulting commit with `git show`: it contains lines the user never saw or selected, while the commit message still reflects the originally-reviewed change — demonstrating silent corruption of the committed content with no warning surfaced to the user.
