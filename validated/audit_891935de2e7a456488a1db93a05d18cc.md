### Title
`ThresholdKeys::read` accepts attacker-supplied secret share, interpolation coefficients, and verification shares without proving `secret_share * G == verification_shares[i]`, letting a crafted key file implant a group key whose discrete log is known to the attacker - (File: crypto/dkg/src/lib.rs)

### Summary
The analog of CVE-2014-10402 (incomplete restriction of `f_dir`) is incomplete validation at deserialization: `ThresholdKeys::read` checks the curve ID, parameter bounds, and canonical encodings, but never checks the one invariant that matters — that the deserialized secret share actually corresponds to the deserialized verification share. Every field that determines `group_key` (the `Constant` interpolation coefficients and the `verification_shares` map) is attacker-controlled in the byte stream.

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) reads `t`, `n`, `i`, an interpolation method (for `Constant`, `n` attacker-chosen scalars), `secret_share`, and `n` verification shares via `Ciphersuite::read_G` — which, unlike `Curve::read_G` (crypto/frost/src/curve/mod.rs:125-131), does not reject the identity point. It then calls `ThresholdKeys::new`, which only validates share count, participant range, and `t == n` for `Constant` interpolation (crypto/dkg/src/lib.rs:355-374). The group key is computed as `sum(verification_shares[i] * interpolation_factor(i))` over `1..=t` (line 376-378) with no consistency check between `secret_share` and `verification_shares[params.i()]`; `sign_share` later uses the interpolated `secret_share` (crypto/dkg/src/lib.rs:494-498), and `complete` verifies the aggregate against `view.group_key()` (crypto/frost/src/sign.rs:465).

An attacker who supplies the key blob can set `t = n = 1`, `Constant([1])`, `verification_shares[1] = G*x`, `secret_share = x` for an `x` they chose. All structural checks pass, `group_key = x*G` is a key whose discrete log the attacker knows, and every subsequent FROST signing session produces valid signatures for `x*G`.

### Impact Explanation
Key-substitution: any node/wallet that loads `ThresholdKeys` from bytes an untrusted party can influence (provisioning, backup restore, share distribution) will operate a validator/wallet whose group key is fully controlled by the attacker. Funds sent to the address derived from that group key are spendable by the attacker and not recoverable by the victim, and all signatures produced authorize whatever the attacker wants under that key. This directly mirrors the CVE class: the deserializer "checks the directory" (field formats, canonical encodings, parameter bounds) but fails to constrain the input to the *intended* key — the secret share is not bound to the verification share, so an unintended key slips through the incomplete fix.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to cause a victim to deserialize a malicious `ThresholdKeys` blob, which is a provisioning/supply path rather than a pure network message. However, `ThresholdKeys::read` is a public deserialization API explicitly designed for loading key material, and no accompanying integrity mechanism (MAC, signature, or consistency proof) exists in the format — the code itself acknowledges the failure mode ("deserialize a semantically invalid FrostKeys", crypto/frost/src/sign.rs:491-494) without preventing it. The undetected variant (self-consistent attacker key) is worse than the "semantically invalid" case the code comments on, since every signature verifies.

### Recommendation
- In `ThresholdKeys::new`, verify `C::generator() * secret_share == verification_shares[&params.i()]` (rejects mismatched shares and makes a self-consistent blob still require the attacker to *not* know the dlog gap — combine with the next point).
- Reject identity verification shares: use `Curve::read_G`-style identity rejection or check `is_identity()` in `ThresholdKeys::new`/`read`.
- Ideally authenticate serialized key material (e.g., encrypt/MAC under an operator key, or store a commitment to the expected group key alongside the blob and compare `group_key()` after `new`).
- At minimum, document that `ThresholdKeys::read` input must be authenticated and integrity-protected.

### Proof of Concept
```rust
// Attacker chooses x, builds a blob for ThresholdKeys::<C>::read
let x = C::F::random(&mut rng);              // attacker knows dlog of group key
let mut blob = vec![];
blob.extend((C::ID.len() as u32).to_le_bytes());
blob.extend(C::ID);
blob.extend(1u16.to_le_bytes());             // t = 1
blob.extend(1u16.to_le_bytes());             // n = 1
blob.extend(1u16.to_le_bytes());             // i = 1
blob.push(0u8);                              // Interpolation::Constant
blob.extend(C::F::ONE.to_repr().as_ref());   // coefficient 1
blob.extend(x.to_repr().as_ref());           // secret_share = x
blob.extend((C::generator() * x).to_bytes().as_ref()); // verification_shares[1] = x*G

let keys = ThresholdKeys::<C>::read(&mut blob.as_slice()).unwrap();
assert_eq!(keys.group_key(), C::generator() * x); // attacker-controlled group key
// keys.params() == (t=1, n=1, i=1); any FROST sign session now signs under x*G,
// and funds sent to the address derived from keys.group_key() are spendable
// by the attacker (dlog x) but not by the victim.
```
