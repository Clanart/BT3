## Analysis

This report's bug class — a token wrapper trusting a caller-supplied `amount` instead of verifying the actual balance delta before/after a transfer — has a direct analog in sei-chain's CW20-pointer-for-ERC20 contract, which wraps an arbitrary (potentially fee-on-transfer or rebasing) ERC20 token as a CW20 token.

### Title
CW20-for-ERC20 pointer's `Send`/`SendFrom` trust the caller-supplied amount instead of the ERC20's actual transferred balance - ([File: example/cosmwasm/cw20/src/contract.rs])

### Summary
The CW20 pointer contract that wraps an arbitrary ERC20 token (deployed via the pointer precompile's `AddCW20` path, e.g. [1](#0-0) ) forwards `transfer`/`transfer_from` calls to the underlying ERC20 with a delegatecall carrying the caller-specified `amount`, and then reports that same nominal `amount` to downstream CosmWasm contracts via `Cw20ReceiveMsg`, without ever checking the recipient's actual balance change.

### Finding Description
`transfer` and `transfer_from` in the pointer contract build a `DelegateCallEvm` message that calls the wrapped ERC20's `transfer`/`transferFrom` with the exact `amount` argument, and unconditionally attach that `amount` as an attribute/return value: [2](#0-1) [3](#0-2) 

`execute_send` and `execute_send_from` go further: they take that same nominal `amount` and embed it in a `Cw20ReceiveMsg` that is dispatched to the recipient contract as a Cosmos message: [4](#0-3) [5](#0-4) 

By CW20 convention, a receiving contract (e.g. a vault, AMM, or lending pool) trusts the `amount` field in `Cw20ReceiveMsg` as the actual number of tokens it received, and credits the sender proportionally (mints shares, records a deposit, etc.) without independently re-querying its own balance before/after. Because the underlying ERC20 is attacker-controllable (any deployer can register an arbitrary ERC20 address as the wrapped token via `AddCW20`, see [6](#0-5) ), an attacker can deploy a fee-on-transfer or rebasing ERC20, wrap it with this pointer, and call `Send`/`SendFrom` against a victim CW20-consuming contract. The pointer will report the full nominal `amount` even though the ERC20's `transfer` silently delivered less (fee-on-transfer) or the recipient's real balance changed non-linearly (rebase) — the pointer never validates `balanceOf(recipient)` before and after the delegatecall.

### Impact Explanation
A victim contract that consumes CW20 deposits (vault, AMM pool, lending protocol) via this pointer and trusts the `Cw20ReceiveMsg.amount` field can be tricked into crediting shares/collateral/debt-reduction for more tokens than it actually received, resulting in direct fund loss to other depositors/LPs once the attacker withdraws against the over-credited amount. This is a concrete fund-loss vector reachable by an unprivileged EVM/CosmWasm user who both deploys the malicious ERC20 and registers/uses the pointer.

### Likelihood Explanation
Likelihood is moderate: it requires (1) deploying or finding a fee-on-transfer/rebasing ERC20, (2) registering it via the permissionless `AddCW20` pointer precompile call, and (3) a downstream contract that accepts CW20 `Send`/`SendFrom` deposits from arbitrary CW20 tokens and trusts the reported amount without balance verification. The pointer creation itself is fully permissionless and reachable by any transaction sender, and the pattern (trusting reported transfer amount) is a common integration mistake for CW20 receivers, making exploitation plausible wherever such an integration exists.

### Recommendation
Before finalizing `Send`/`SendFrom` (and ideally `Transfer`/`TransferFrom`), query the recipient's actual ERC20 balance immediately before and after issuing the delegatecall, and use the observed delta as the authoritative amount attached to `Cw20ReceiveMsg` and returned/emitted in attributes, rather than trusting the caller-supplied `amount`.

### Proof of Concept
1. Deploy a fee-on-transfer (or rebasing) ERC20 `EvilToken` where `transfer(to, amount)` actually delivers `amount - fee` to `to`.
2. Call the pointer precompile's `addCW20Pointer(EvilToken)` to deploy the CW20 wrapper pointing at `EvilToken` (`AddCW20` in `precompiles/pointer/...`).
3. Fund an attacker account with `EvilToken`/its CW20 pointer balance.
4. Call `Send { contract: <victim_vault>, amount: X, msg: <deposit> }` on the CW20 pointer.
5. The pointer delegatecalls `EvilToken.transfer(victim_vault, X)`, which actually delivers `X - fee` to `victim_vault`, but the pointer still emits `Cw20ReceiveMsg{ amount: X, ... }` to `victim_vault`.
6. If `victim_vault` mints shares/credits deposit based on the received `Cw20ReceiveMsg.amount` (`X`) instead of its own balance delta, the attacker is credited for more than was actually transferred, enabling later over-withdrawal at other depositors' expense.

fn transfer(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

pub fn transfer_from(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    owner: String,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&owner)?;
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_from_payload(owner.clone(), recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", owner)
        .add_attribute("to", recipient)
        .add_attribute("by", info.sender)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

// ERC20 -> CW20
func (k *Keeper) SetERC20CW20PointerWithVersion(ctx sdk.Context, cw20Address string, addr common.Address, version uint16) error {
	if k.cwAddressIsPointer(ctx, cw20Address) {
		return ErrorPointerToPointerNotAllowed
	}
	err := k.setPointerInfo(ctx, types.PointerERC20CW20Key(cw20Address), addr[:], version)
	if err != nil {
		return err
	}
	return k.setPointerInfo(ctx, types.PointerReverseRegistryKey(addr), []byte(cw20Address), version)
}
