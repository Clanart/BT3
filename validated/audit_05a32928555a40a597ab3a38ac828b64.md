### Title
Payout attribution OP_RETURN is not covered by the SIGHASH_SINGLE|ANYONECANPAY signature, letting an unprivileged party rewrite/corrupt it to frame the honest operator as malicious - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` signs only input 0 with a `SinglePlusAnyoneCanPay` witness, which under BIP341/BIP143 rules commits only to input 0 and the output at the *same index* (output 0, the user payout). The anchor output (index 1) and, critically, the OP_RETURN attribution output (index 2, carrying the operator's x-only pubkey) are completely unsigned. Anyone who observes the honest operator's payout transaction in the mempool can rebroadcast a conflicting, higher-fee transaction that keeps output 0 byte-for-byte identical (so the user is still paid and the signature still verifies) while replacing the OP_RETURN with garbage, causing `Verifier::is_kickoff_malicious` to flag the honest operator's later kickoff as malicious.

### Finding Description
The binding this exploit breaks: `stored_attribution_for_withdrawal_i (Option<XOnlyPublicKey>) == Some(honest_operator_xonly_pk)`, where `honest_operator_xonly_pk` is the operator who actually funded output 0 of the confirmed payout tx.

`create_payout_txhandler` builds the payout tx with output 0 = user payout, output 1 = anchor, output 2 = OP_RETURN(operator_xonly_pk), and signs only input 0 with the sighash type supplied by the caller (expected to be `SinglePlusAnyoneCanPay`, per the explicit error text in both `core/src/operator.rs` and `core/src/rpc/aggregator.rs`): [1](#0-0) [2](#0-1) 

`SIGHASH_SINGLE | ANYONECANPAY` commits only to input 0 and the output with the same index (output 0). Outputs 1 and 2 — including the OP_RETURN operator attribution — are not covered by the signature at all, so any party can construct a *different* valid transaction that keeps output 0 unchanged (preserving the verified user signature) while supplying arbitrary bytes, a malformed length, or a completely different operator pubkey in output 2, and arbitrary additional funding inputs (permitted by ANYONECANPAY).

On confirmation, `Verifier::update_finalized_payouts` reads whichever transaction actually spent the withdrawal UTXO, extracts the first OP_RETURN output, and calls `parse_op_return_data`; if this fails or the bytes aren't a valid x-only pubkey, the stored attribution becomes `None`: [3](#0-2) [4](#0-3) 

`Verifier::is_kickoff_malicious` treats a `None` attribution (or a mismatched xonly pk) as automatically malicious, with no fallback check of who actually funded output 0: [5](#0-4) 

Because the DB row for withdrawal i is now `None`, `PayoutCheckerTask::run_once`'s `get_first_unhandled_payout_by_operator_xonly_pk(honest_operator_pk)` never finds this withdrawal, so the honest operator can never call `handle_finalized_payout` for it: [6](#0-5) 

The honest operator's later `Kickoff` referencing this withdrawal is then evaluated by `is_kickoff_malicious`, which sees `None`/mismatch and returns `true`, causing `handle_kickoff` to queue a `Challenge` tx against the honest operator: [7](#0-6) 

No existing guard prevents this: `is_kickoff_malicious` only compares the stored (attacker-corruptible) OP_RETURN pubkey against `kickoff_data.operator_xonly_pk` and the committed payout blockhash — it never re-derives who funded output 0 from the transaction's actual spend. `SECP.verify_schnorr` in `withdraw`/optimistic-payout flows only validates the user's signature over input 0 (and thus output 0), not the OP_RETURN.

### Impact Explanation
This lets an unprivileged party — anyone who can observe the mempool and pay a marginally higher fee — permanently and unilaterally deny the honest operator its correct payout attribution, without ever needing a key, collateral, or protocol role. Once attribution is lost, the operator cannot call `handle_finalized_payout`, cannot later prove the payout during a Disprove challenge, and is flagged malicious purely from data an attacker controls. This matches the Critical category "an honest operator permanently unable to be reimbursed" / "an honest operator's collateral burned," since the flagged-malicious kickoff proceeds down the Challenge/assert/Disprove path with the operator unable to produce a valid payout proof. The attack is repeatable per withdrawal and per operator, and does not require compromising any operator, verifier, or aggregator secret.

### Likelihood Explanation
Preconditions: an operator's payout tx must be visible pre-confirmation (standard for mempool-based fee bumping/RBF flows), and the withdrawal UTXO spend must allow a conflicting transaction to replace it (BIP125 RBF or a race to first confirmation). The attacker cost is only the fee delta needed to outbid the operator's payout tx fee rate plus funding their own replacement inputs — no bridge collateral or deposit is required, and the operator's own payout output (paying the withdrawing user) remains intact so the replacement is not obviously invalid to full nodes. This is realistically executable by any user monitoring the mempool for Payout transactions, which are recognizable by their fixed 3-output structure (user payout, anchor, OP_RETURN).

### Recommendation
Cover the OP_RETURN attribution output in the payout signature (e.g., switch to `SIGHASH_ALL` for the payout keypath spend, or add a `SIGHASH_SINGLE|ANYONECANPAY`-safe commitment scheme that also binds output 2), or otherwise ensure the operator xonly pubkey attribution used by `is_kickoff_malicious` cannot be altered without invalidating the user's signature. Alternatively, derive attribution from cryptographic proof of funding (e.g., require the fee-paying/change input to be provably controlled by the claiming operator) rather than trusting an unauthenticated OP_RETURN.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

/// Parses the OP_RETURN data from a Bitcoin script. It retrieves the first data push after an OP_RETURN.
pub fn parse_op_return_data(script: &Script) -> Option<&[u8]> {
    let mut instructions = script.instructions();
    if let Some(Ok(Instruction::Op(opcodes::all::OP_RETURN))) = instructions.next() {
        if let Some(Ok(Instruction::PushBytes(data))) = instructions.next() {
            return Some(data.as_bytes());
        }
    }
    None
}
