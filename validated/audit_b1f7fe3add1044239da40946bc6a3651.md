## Finding: Analog of the Holograph "gas-locked job" bug — commit-before-validate ordering breaks atomicity of IBC callback token transfers

### Title
Approve-then-validate ordering in `IBCReceivePacketCallback` permanently commits an ERC20 allowance to an attacker-controlled contract before the atomicity check can revert it - ([File: x/ibc/callbacks/keeper/keeper.go])

### Summary
The Holograph bug is fundamentally about a state machine that performs an irreversible, singleton-gated action (job execution) whose safety condition (gas price bound) is checked *before* commit, but the design assumes an all-or-nothing outcome that in practice leaves funds in a state that cannot be recovered by anyone else. The Cosmos EVM analog is in the IBC destination callback flow (`x/erc20`/ICS-20 memo-driven contract calls): the code commits EVM state changes (an ERC20 `approve`) to the real chain state via `writeFn()` *before* running the invariant check meant to guarantee atomicity, so a failing/malicious callback still leaves a persistent, exploitable ERC20 allowance behind.

### Finding Description
`IBCReceivePacketCallback` in [1](#0-0)  executes an EVM `approve` and then an arbitrary contract call (whose address and calldata are taken directly from the ICS-20 packet memo — an untrusted, sender-controlled field, as the module's own docs warn: [2](#0-1) ) inside a `CacheContext()`.

The critical ordering bug is here: [3](#0-2) 

1. `approve(contractAddr, amountInt)` is executed and, if it doesn't error, is left in the cached context.
2. The arbitrary `calldata` call is executed against `contractAddr`.
3. `writeFn()` is called at line 227, **permanently committing** both the approval and any effects of the calldata call to the real `ctx` (not a further outer cache that would be discarded — this is the actual packet-processing context of a committed IBC receive).
4. **Only after** that irreversible commit does the code check `receiverTokenBalance != 0` (lines 234–239) — the very safety check whose stated purpose ("This check is here to prevent funds from getting stuck in the isolated address, since they would become irretrievable") is supposed to guarantee atomicity.

If the check fails, the function returns an error — but the `approve()` allowance already exists on-chain. Since the callback contract address is attacker-influenced via the memo, a contract can be crafted to accept the approval and either not call `transferFrom` at all, or only partially drain it, while still returning successfully from its top-level call (no revert). The atomicity check then fires and the callback is marked "failed," but the `approve` is not revoked — it remains a standing allowance from the isolated receiver address to that attacker-controlled contract, which can later call `transferFrom` in a completely separate transaction to drain the isolated address's remaining (and potentially future) balance.

This mirrors the Holograph root cause structurally: a guard/check that is intended to preserve an invariant ("no operator gets slashed if job can't complete safely" / "funds can't get stuck") is evaluated too late relative to an already-committed side effect, so the very state the check is meant to guard against becomes permanently reachable.

### Impact Explanation
This breaks the 1:1 asset-representation and escrow invariant this repo is scoped to protect: an unprivileged attacker who merely crafts the memo of a legitimate ICS-20 transfer (relayed by anyone) can obtain a durable ERC20 `approve` over user funds held at the deterministic isolated address (`GenerateIsolatedAddress(channel, sender)`), and later extract those funds via `transferFrom` outside of any atomic guarantee the module claims to provide. This is unauthorized extraction of token-pair-backed user value — a Critical impact per the allowed impact gate.

### Likelihood Explanation
The trigger requires no privileged access: any account can send an ICS-20 transfer with a `dest_callback` memo pointing at a contract they control, deploy a contract that accepts the `approve` but returns success without fully calling `transferFrom`, and later call `transferFrom` themselves. The isolated receiver address is deterministic and reusable across packets from the same sender/channel, increasing the value that can accumulate and later be drained.

### Recommendation
Perform the post-condition check (`receiverTokenBalance == 0`) against the *cached* context **before** calling `writeFn()`, and only commit the cached context if the invariant holds. If the invariant fails, discard the cached context entirely (do not call `writeFn()`), or explicitly reset the ERC20 allowance to zero within the same cached context before committing, so that no approval to the target contract survives a failed/aborted callback.

### Proof of Concept
1. Attacker sends (or has someone else relay) an ICS-20 transfer to Cosmos EVM chain with `memo.dest_callback.address` = attacker's `EvilCallback` contract, `calldata` = arbitrary bytes, sender = attacker-controlled counterparty account.
2. `IBCReceivePacketCallback` runs: `approve(EvilCallback, amount)` succeeds; the calldata call into `EvilCallback` executes and returns successfully without calling `transferFrom` (or only partially).
3. `writeFn()` commits the approval into real chain state at [4](#0-3) .
4. The subsequent balance check at [5](#0-4)  fails and returns `ErrEVMCall`, but the approval persists.
5. In a later, independent transaction, `EvilCallback` calls `transferFrom(isolatedAddr, attacker, amount)` using the still-valid allowance and drains the isolated address's ERC20 balance.

func (k ContractKeeper) IBCReceivePacketCallback(
	ctx sdk.Context,
	packet ibcexported.PacketI,
	ack ibcexported.Acknowledgement,
	contractAddress string,
	version string,
) error {
	data, err := transfertypes.UnmarshalPacketData(packet.GetData(), version, "")
	if err != nil {
		return err
	}

	cbData, isCbPacket, err := callbacktypes.GetCallbackData(data, version, packet.GetDestPort(), ctx.GasMeter().GasRemaining(), ctx.GasMeter().GasRemaining(), callbacktypes.DestinationCallbackKey)
	if err != nil {
		return err
	}
	if !isCbPacket {
		return nil
	}

	// `ProcessCallback` in IBC-Go overrides the infinite gas meter with a basic gas meter,
	// so we need to generate a new infinite gas meter to run the EVM executions on.
	// Skipping this causes the EVM gas estimation function to deplete all Cosmos gas.
	// We re-add the actual EVM call gas used to the original context after the call is complete
	// with the gas retrieved from the EVM message result.
	cachedCtx, writeFn := ctx.CacheContext()
	cachedCtx = evmante.BuildEvmExecutionCtx(cachedCtx).
		WithGasMeter(evmtypes.NewInfiniteGasMeterWithLimit(cbData.CommitGasLimit))
