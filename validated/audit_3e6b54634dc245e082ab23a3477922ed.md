### Title
Reward transfer/watermark desync lets a sustained `ReputationAsset::mint_into` failure cause unbounded, repeated treasury payouts for the same commitment span - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`Pallet::<T>::process_message` transfers the treasury reward to the relayer, deposits the event, *then* mints reputation, and only *after* a successful mint does it advance the `LastRewardedHeight` watermark. If the mint step fails, the function short-circuits with `?` before the watermark update ever runs, but the currency transfer already executed and is not rolled back (the error is swallowed by the caller with `let _ = ...`). If that mint failure recurs across several consensus updates, `calculate_reward`'s baseline stays frozen while `latest_commitment_height` keeps advancing, so each subsequent call re-prices the reward from the same stale baseline instead of the actually-unpaid span — repeatedly re-paying blocks that were already paid.

If `mint_into` returns `Err`, the `?` on line 68 aborts `process_message` immediately, skipping the watermark advance — but the transfer has *already* taken effect and is not reverted, since this is a plain function call with no explicit storage-transaction wrapper.

Given the precondition stated in the question — that `mint_into` keeps failing for the relayer account across several real consensus updates — the watermark `LastRewardedHeight` is frozen at its pre-failure value while `latest_commitment_height` (fed by the honest chain) keeps increasing. Each new `process_message` call recomputes `blocks = latest_height - frozen_baseline`, which grows every time and is *never reduced* by the amounts already paid out in prior calls (since those payouts didn't move the watermark). The pallet therefore pays the same "old" blocks over and over, plus the newly accrued ones, each time the reward is (re)triggered — the treasury transfer at line 53-59 fires on every call as long as `reward` is non-zero.

### Impact Explanation
This breaks the core reward invariant documented in the pallet ("Rewards only ever cover the span above this watermark, so a height that is revisited ... is not paid for twice", see `LastRewardedHeight` doc comment) — the treasury pays out cumulative sums of `(h_i - baseline) * cost_per_block` for each call `i`, which mathematically exceeds the true owed amount `(h_final - baseline) * cost_per_block` by an ever-growing multiple as more calls occur while the mint keeps failing. This directly matches the bounty's reward-accounting/asset-movement impact class: relayer rewards moving in the wrong amount, draining treasury balances that belong to the protocol. [6](#0-5) 

### Likelihood Explanation
The severity is conditional on the premise stated in the question — that `mint_into` failure can be *sustained* across multiple `process_message` invocations for the relayer's account, which is a precondition inherited from a separate transfer/mint ordering issue rather than something demonstrated here to be independently, repeatedly attacker-triggerable at will. I was not able to fully verify within the available index what conditions make `ReputationAsset::mint_into` (backed by `pallet-assets`, per `parachain/runtimes/gargantua/src/lib.rs`) fail in a way an unprivileged relayer can reliably reproduce and sustain across several blocks (e.g., account freezing is typically an admin-only `pallet-assets` operation, not self-inflictable by an ordinary account). Given the analysis is explicitly built "assuming the precondition holds," the code-level mechanism (transfer commits, watermark update does not, error swallowed) is confirmed and real, but real-world exploitability depends on an attacker's ability to independently and repeatedly force that precondition, which is not established here.

### Recommendation
- Make the watermark update happen unconditionally after a successful transfer, independent of the reputation mint outcome — e.g., advance `LastRewardedHeight` immediately after (or atomically with) the `Currency::transfer`, and treat the reputation mint as best-effort (log-and-continue, as `messaging-incentives` already does), rather than gating the watermark advance behind mint success.
- Alternatively, wrap the whole reward-and-mint sequence in `frame_support::storage::with_transaction` so a mint failure reverts the transfer as well, keeping "transfer + mint + watermark" atomic.
- Do not swallow `process_message` errors silently in `on_executed`; at minimum, emit a distinguishable event/log so operators can detect and pause on repeated mint failures before treasury drain accumulates.

### Proof of Concept
1. Configure `StateMachinesCostPerBlock` for a state machine and drive its `LastRewardedHeight` to some baseline `B` via a normal, successful consensus update (mint succeeds, watermark set to `B`).
2. Induce a sustained `ReputationAsset::mint_into` failure for the relayer account (per the question's stated precondition).
3. Submit further honest `ConsensusMessage`s that legitimately advance `latest_commitment_height` to `B+10`, `B+25`, `B+40`, etc., each dispatched through `on_executed` → `process_message`.
4. Observe: on every call, `T::Currency::transfer` at lines 53-59 succeeds and drains `(latest_height - B) * cost_per_block` from the treasury (10, 25, 40 blocks-worth respectively), because `LastRewardedHeight` never advances past `B` (the mint failure aborts before line 70-72 each time).
5. Sum of transferred rewards = `(10 + 25 + 40) * cost_per_block = 75 * cost_per_block`, versus the true single unpaid span of `40 * cost_per_block` — a >1.8x overpayment that grows without bound as more calls occur while the mint keeps failing. [7](#0-6)
