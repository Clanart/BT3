### Title
Untrusted `offset` in `ReceivedOutput::read` resolves the spending key outside the output's authorized key set, accepting outputs that cannot be spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput` pairs a `TxOut`/`OutPoint` (claimed received funds) with a scalar `offset` that determines which key — `group_key + offset*G` — is authorized to spend it. `Scanner::scan_transaction` only ever emits `ReceivedOutput`s whose `offset` was proven to map to `output.script_pubkey` via the registered `scripts` table (mod.rs:205). `ReceivedOutput::read` (mod.rs:122-134), however, deserializes all three fields from untrusted bytes independently and performs no binding between them — analogous to `hftp` resolving a caller-supplied path without confining it to the intended root. The `offset` is trusted purely because it was carried alongside the output.

### Finding Description
In `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134), the `offset` is read with `Secp256k1::read_F` and the `output`/`outpoint` are consensus-decoded, and the struct is returned without checking that `p2tr_script_buf(key + offset*G) == output.script_pubkey`. The only place this binding is ever enforced is downstream in `SignableTransaction::multisig` (send.rs:273-285), which returns `None` on mismatch — i.e., the inconsistency is discovered only after the output has been ingested and treated as a received, spendable input by `SignableTransaction::new`, which sums `input.output.value` into `input_sat` (send.rs:175) to authorize payments and fees.

### Impact Explanation
An unprivileged party supplying bytes to `ReceivedOutput::read` can cause a `ReceivedOutput` to be accepted where the scalar offset does not derive the key owning `output.script_pubkey` — the "file outside the directory root." Consequences:

- Funds reported received are not spendable: the output's value is counted toward `input_sat` and used to fund payments/fees (send.rs:175, 215-221), yet `multisig()` can never produce a valid signature for that input, so any `SignableTransaction` incorporating it fails outright (send.rs:277-279), burning the other honest inputs' attempt.
- Worse, an offset can point *into* another branch of the offset space: because `offset` is unconstrained, a crafted `ReceivedOutput` can reference an `outpoint`/`output` that legitimately belongs to a different registered offset, while the supplied `offset` is the one `keys.offset(...)` applies — causing the multisig to attempt spending under a key context the scanner never associated with that output, or an honest input to be paired with a foreign outpoint.

Severity: Medium. No secret key material is leaked and honest signers won't produce an invalid transaction (the check in `multisig` catches the mismatch), but attacker-controlled deserialization diverts the resolved spending key outside the authorized set and renders accounted funds unspendable.

### Likelihood Explanation
The trigger is any path where `ReceivedOutput` bytes cross a trust boundary — coordinator-supplied plans, restarted/restored scan state, or peer-provided output data fed to `ReceivedOutput::read`. The bug is deterministic (no probabilistic condition) and requires only control of the serialized bytes. Exploitation is bounded by the fact that `multisig()` refuses rather than mis-signs, capping impact at unspendable/misattributed funds rather than theft.

### Recommendation
Bind the offset to the output at deserialization time: `ReceivedOutput::read` should take the scanner's base `key` (or the `Scanner` should expose a `read`/`verify` helper) and reject any output where `p2tr_script_buf(key + GENERATOR*offset) != output.script_pubkey`, mirroring the check in `SignableTransaction::multisig` (send.rs:277). Alternatively, drop the serialized `offset` entirely and re-derive it from `self.scripts` at read time so the trusted mapping cannot be overridden by input bytes.
