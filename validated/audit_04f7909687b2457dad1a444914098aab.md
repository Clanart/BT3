## Title
Deep-link `openRepo` URL is passed unvalidated into `CloneRepository` popup, bypassing all scheme checks - (`app/src/ui/dispatcher/dispatcher.ts`)

### Summary
`parseAppURL` only checks that the deep link has a hostname/pathname and validates `pr`/`branch` query values; it performs **no validation whatsoever on the URL scheme/transport** of the `openrepo` action's `url` field. [1](#0-0) 

This unfiltered `url` is passed straight through `openOrCloneRepository` into the `CloneRepository` popup as `initialURL`. [2](#0-1) 

### Finding Description
The `CloneGenericRepository` component that renders/edits this URL is a plain text field with no client-side scheme allowlist. [3](#0-2) 

Downstream, `updateUrl`/`resolveCloneInfo`/`clone` in `clone-repository.tsx` only use `parseRepositoryIdentifier`/`parseRemote` to derive an owner/name pair for GitHub API lookups and to compute a safe local directory name via `sanitizeCloneName` — they never reject the URL if it fails to match a known `https`/`ssh`/`git` pattern; on failure `parseRepositoryIdentifier` simply returns `null` and the raw, untouched `url` is passed straight to `cloneImpl`. [4](#0-3) [5](#0-4) 

The `remote-parsing.ts` regexes (`remoteRegexes`) are only used for *identification/matching* (owner/name extraction, matching against known repos) — they are not used as a gate that blocks cloning when a URL doesn't match any pattern. [6](#0-5) 

So, confirmed in this codebase: **neither `parseAppURL` nor the `CloneRepository`/`CloneGenericRepository` UI enforces an allowlist of git transport schemes** (e.g., rejecting `ext::`, `file://`, `fd::`, etc.) before the value reaches the clone action.

### Impact Explanation
If the actual `git clone` subprocess invocation (in `app/src/lib/git/clone.ts`, which I was not able to inspect in this session) does not independently restrict allowed transports (e.g., via a `GIT_ALLOW_PROTOCOL` environment variable or `-c protocol.ext.allow=never`), then a URL such as `ext::sh -c calc` (or `ext::sh -c "curl ... | sh"`) passed to `git clone` will execute the given command in the transport-helper role, i.e., unrestricted local code execution as the Desktop app's user, triggered purely by the victim clicking a `x-github-client://openRepo?url=ext::...` link — no separate confirmation of an unusual protocol is shown to the user.

### Likelihood Explanation
Likelihood is high assuming no independent mitigation in the git-process invocation layer, since:
- The deep link requires only a single click by the victim.
- No dialog/warning distinguishes `ext::`/`file://` URLs from ordinary `https://`/`ssh://` URLs.
- The URL field is pre-filled and the user only needs to press "Clone".

I was unable to verify, within the tool-call budget of this session, whether `app/src/lib/git/clone.ts` (or a shared git-environment helper) sets `GIT_ALLOW_PROTOCOL` or otherwise restricts transports for the actual `git clone` subprocess call — this is the standard mitigation GitHub Desktop has historically used for this exact class of issue, and if it is present there, the vulnerability is effectively closed at the sink even though the UI/deep-link layer has no validation. This should be checked directly in `app/src/lib/git/clone.ts` before treating this as fully exploitable.

### Recommendation
- Add explicit scheme validation in `parseAppURL` (reject `openrepo` URLs whose scheme is not one of `http`, `https`, `ssh`, `git`) before constructing the `open-repository-from-url` action.
- Additionally/independently, ensure `app/src/lib/git/clone.ts` invokes `git clone` with `GIT_ALLOW_PROTOCOL` restricted to `http:https:ssh:git` (defense in depth, protecting manually-typed URLs too).
- Surface a clear warning/confirmation in the `CloneRepository` UI when the URL scheme is not one of the expected transports.

### Proof of Concept
1. Craft `x-github-client://openRepo?url=ext::sh%20-c%20calc`.
2. Have the victim click the link; `parseAppURL` returns `{ name: 'open-repository-from-url', url: 'ext::sh -c calc', ... }` with no scheme check. [7](#0-6) 
3. `openOrCloneRepository` opens the `CloneRepository` popup with `initialURL: 'ext::sh -c calc'`. [8](#0-7) 
4. User clicks "Clone" in the pre-filled dialog; `clone()` calls `cloneImpl(url.trim(), path, defaultBranch)` with the unmodified `ext::` URL. [9](#0-8) 
5. Verify in `app/src/lib/git/clone.ts` whether the resulting `git clone` subprocess call restricts protocols; if not, the `ext::` transport helper executes `sh -c calc`.

      this.setSelectedTabState({ error })
