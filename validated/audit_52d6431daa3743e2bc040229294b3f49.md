### Title
Negative Pyth prices cause unrecoverable transaction aborts instead of the intended graceful oracle-error path, blocking liquidations and freezing user positions - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`normalize-pyth` converts a signed Pyth price (`int`) to `uint` using Clarity's `to-uint`, without first checking whether the price is negative. Because Clarity's `to-uint` runtime-aborts the entire transaction when given a negative `int` (the Clarity analog of Solidity's `SafeCast.toUint256` revert), a negative Pyth price never reaches the protocol's intended, catchable price-validation check (`oracle-price-legal`/`ERR-ORACLE-INVARIANT`). Instead it kills the whole call unconditionally, exactly mirroring the GMX finding where `SafeCast.toUint256` reverted with a plain string instead of being classified as a recoverable oracle error.

### Finding Description
`normalize-pyth` is defined as: [1](#0-0) 

```clarity
(define-private (normalize-pyth (p int) (expo int))
  (let ((adj (+ expo 8))
        (inkind? (asserts! (not (is-eq adj 0)) (to-uint p)))
        (res (if (> adj 0)
                (* p (pow 10 adj))
                (/ p (pow 10 (- adj))))))
    (to-uint res)))
```

Both the early-return branch (`(to-uint p)` when `adj` is `0`, i.e. when Pyth's `expo` is exactly `-8`) and the final branch (`(to-uint res)`) call `to-uint` on a value derived directly from the raw signed Pyth `price` field, with no preceding sign check. Pyth's `price` field is a signed `int128` and can legitimately be negative for real-world assets with negative carrying cost/negative yield, or transiently due to oracle/relay glitches.

This `normalize-pyth` result flows into `resolve-pyth`: [2](#0-1) 

which is called from `resolve-price-feed` → `price-resolve`: [3](#0-2) 

`price-resolve` is designed so that bad prices are caught via `(asserts! (and (oracle-price-legal final-price) ...) ERR-ORACLE-INVARIANT)` — a controlled `(err ...)` response that callers such as `price-multi-resolve`/`iter-price-multi` explicitly `unwrap!` and handle as a recoverable failure: [4](#0-3) 

However, a negative price never gets the chance to be checked by `oracle-price-legal`, because `to-uint` inside `normalize-pyth` aborts the transaction before `price-resolve`'s `asserts!` logic ever runs. This is the same root-cause pattern as the GMX bug: a sign-conversion step (`SafeCast.toUint256` in GMX, `to-uint` in Clarity/Zest) throws an uncatchable/uncategorized failure instead of surfacing as the dedicated "bad price" error path the protocol already built (`isEmptyPriceError()` in GMX, `oracle-price-legal`/`ERR-ORACLE-INVARIANT` in Zest).

### Impact Explanation
`price-resolve`/`price-multi-resolve` back nearly every price-dependent operation in the market: `get-assets`, `get-asset-value`, `get-notional-evaluation`, and critically `liquidate`: [5](#0-4) 

If the STX, sBTC, or USDC Pyth feed used by any asset in an at-risk position ever reports a negative price (even momentarily), every call that needs to resolve that asset's price — including `liquidate`, `borrow`, and `withdraw`/health checks for any position that includes that asset — will abort outright instead of failing gracefully. This directly blocks liquidators from closing undercollateralized positions during the window the price is negative/anomalous, which is a temporary freezing of user/protocol funds (unliquidatable bad debt, collateral and debt positions stuck) — matching the in-scope "temporary freezing of funds" impact class. If the malfunction persists or coincides with a real liquidation opportunity, unliquidated bad debt can also threaten protocol insolvency.

### Likelihood Explanation
Pyth price feeds are signed values and Pyth itself does not guarantee that a feed can never publish a negative price (e.g., interest-rate-adjacent or exotic underlying assets, or a temporary relay/computation glitch). The condition requires no attacker action or DAO misconfiguration — it is purely a function of oracle input data crossing zero, so likelihood is low but plausible, and impact when triggered is severe and covers the entire market contract, not just one asset.

### Recommendation
Add an explicit, catchable sign check on the raw Pyth `price` before calling `to-uint`, e.g. return an `(err ERR-ORACLE-NEGATIVE-PRICE)` (or route it through the existing `oracle-price-legal`-style check before any `to-uint` conversion) instead of letting `to-uint` panic. This ensures a negative price feeds into the same graceful `try!`/`asserts!`-based error propagation (`ERR-ORACLE-INVARIANT`/`ERR-ORACLE-MULTI`) that `price-resolve`/`price-multi-resolve` already use for other invalid-price conditions, rather than aborting the entire transaction unconditionally.

### Proof of Concept
1. Pyth publishes (or a compromised/anomalous relay causes `pyth-storage-v4` to store) a price update for `PYTH-STX` with `price = -100000000`, `expo = -8`.
2. A liquidator calls `liquidate` on an eligible undercollateralized position that holds STX as collateral or debt.
3. `liquidate` → `get-assets` → `price-multi-resolve` → `price-resolve` → `resolve-pyth` → `normalize-pyth` executes `(to-uint p)` (since `adj = expo + 8 = 0`) on `p = -100000000`.
4. Because `p` is negative, `to-uint` triggers a Clarity runtime abort; the transaction reverts with a low-level runtime error, not `ERR-ORACLE-INVARIANT`.
5. The liquidation transaction fails unconditionally; every other operation depending on the STX price (borrow, withdraw, health checks) for any position touching STX also reverts, freezing those operations for as long as the negative price persists.

        (ident (get ident data))
        (key { type: type, ident: ident })

        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; update timestamp if newer

        false)
