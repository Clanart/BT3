### Title
Deterministic cached FROST nonces are reused across attacker-influenced sign calls, enabling ROS-style share/key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` caches a single FROST preprocess (nonce pair) per `context` in `CachedPreprocesses`, and every call to `share_internal` (and transitively `complete`, which re-invokes `share_internal` at line 322) re-instantiates a signing machine from that *same* nonce via `AlgorithmSignMachine::from_cache`. The nonce is never rotated or marked consumed. Each call signs over a caller-supplied map of counterparty preprocesses (`serialized_preprocesses`), which determines the included signer set, the `rho` binding factors, and the challenge `c`. Two executions of `share`/`complete` under the same `context` but with different preprocess sets therefore produce two signature shares under one reused nonce — the classic ROS/parallel-session precondition for extracting the signer's MuSig secret share, and from it the validator key.

### Finding Description
- `preprocess_internal` stores `CachedPreprocess` keyed only by `context` (`("DkgConfirmer", attempt)`), and `share_internal` → `preprocess_internal` regenerates the identical nonce commitments every time (lines 123–147). There is no consumed-flag or nonce rotation.
- The bytes driving divergence are fully attacker-controlled: `serialized_preprocesses: HashMap<Participant, Vec<u8>>` is parsed by `read_preprocess` (line 165) and dictates `included`, the per-participant binding factors `rho` (`BindingFactor::calculate_binding_factors`, `crypto/frost/src/nonce.rs:161-173`), and ultimately the challenge. A share is `d + e·rho_i + λ_i·s·c`; two distinct `(rho_i, c)` pairs over the same `(d, e)` yield a linear system revealing `d`, `e`, and `s`.
- The code's own safety argument (lines 25–54) explicitly concedes reuse occurs whenever "`sign` would have to be called again" with distinct received messages, and relies solely on BFT ordering plus a full rebuild — but BFT ordering does not prevent multiple distinct, validly-ordered transactions within one `attempt` from each triggering `share`/`complete` with different preprocess maps. `complete` alone unconditionally re-signs via `share_internal` (line 322), so a `share` followed by a `complete` carrying a modified preprocess set already constitutes a second signing under the same nonce.
- The analogous interpretation-conflict element: the same logical "preprocess" input can be fed as different byte strings (different signer subsets, reordered/extra entries in the `HashMap`, or trailing bytes ignored by `read_preprocess`, which never checks `reader` exhaustion), and the protocol treats each parse as a fresh signing request rather than recognizing the nonce as spent.

### Impact Explanation
Recovery of a validator's MuSig secret share for the validator set's Ristretto key — the root of trust used to confirm DKG results on Substrate via `set_keys_message`. Combined with threshold-many other compromised shares (or for n-of-n MuSig, equivalently degrading the aggregate), this can lead to forgery of `set_keys` confirmations, i.e., signing of an unintended message attesting to attacker-chosen key pairs. At minimum it is irreversible compromise of a long-lived validator private key share.

### Likelihood Explanation
Reachable by any counterparty able to get a distinct preprocess set finalized into a second tributary transaction for the same attempt (i.e., a protocol participant submitting different bytes to `share`/`complete`), and by any path that calls `share` and later `complete` with non-identical preprocesses. It requires the victim to execute `share_internal` twice under one context — the design explicitly re-executes from DB state, so crashes, retries, or multiple confirmation transactions within an attempt all qualify. No secrecy or malformed curve encodings are needed; only control over the preprocess map bytes.

### Recommendation
- Record a `Signed`/`SharesPublished` flag per `context` in `SigningProtocolDb` and refuse to produce a second share unless the preprocess map and message are byte-identical to the first (store a hash of `serialized_preprocesses` + `msg` alongside the cached nonce).
- Implement the TODO already noted at lines 51–54: verify the coordinator's published preprocess matches the presumed deterministic preprocess before publishing shares.
- Make `read_preprocess` reject trailing bytes (`reader.read_to_end` must be empty) so one logical preprocess cannot have multiple serializations.
- Prefer generating fresh nonces per signing attempt over deterministic caching where feasible.

### Proof of Concept
1. Validator V calls `DkgConfirmer::preprocess()` for `attempt = k`, publishing nonce commitments `(D, E)` derived from the cached seed under context `("DkgConfirmer", k)`.
2. Transaction A is finalized carrying preprocess set P₁ = {participants 1,2,…,t}; V's `share` produces `s₁ = d + e·ρ₁ + λ·x·c₁` where `c₁` binds aggregate nonce `R₁`.
3. Transaction B (a second confirmation/share tx, or a `complete` invocation) is finalized carrying a different preprocess set P₂ (e.g., including an additional signer or different counterparty preprocess bytes — trivially achievable since `read_preprocess` ignores trailing bytes). V's `share_internal` loads the same `CachedPreprocess`, so `d, e` are identical, but ρ₂ and `c₂` differ.
4. Attacker solves `s₁ − s₂ = e·(ρ₁ − ρ₂) + λ·x·(c₁ − c₂)` together with the share-verification relation `s_i·G = D + ρ_i·E + λ·c_i·Y_i` to recover `e`, `d`, and then V's MuSig secret share `x`, forging the validator's participation in arbitrary `set_keys` signatures.
