## Title
Commit hooks can silently rewrite staged content without Desktop re-diffing or warning the user, causing the pushed commit to differ from the reviewed diff - (`app/src/lib/git/commit.ts`)

## Summary
The Code4rena finding is fundamentally about a **stale-data / TOCTOU gap**: the user approves an action based on a value they saw, but by the time the action actually executes, the underlying state has changed, and nothing in the system re-verifies that the executed result still matches what the user approved. The closest structural analog in GitHub Desktop is the commit flow: the user reviews a diff and selects specific lines/hunks to commit, but the actual commit is created by staging files and then letting Git hooks run — and Desktop never re-diffs the result to confirm the final commit matches what the user reviewed.

## Finding Description
`createCommit` stages the user-selected files and then invokes `git commit`, explicitly intercepting `pre-commit`, `prepare-commit-msg`, `commit-msg`, and `post-commit` hooks: [1](#0-0) 

These hooks run with the user's full privileges and are able to modify the index/working tree content between the moment the user reviewed the diff (via `getWorkingDirectoryDiff`) and the moment `git commit` actually finalizes the commit object. After the commit completes, `_commitIncludedChanges` only records stats and triggers a generic repository refresh — it never re-fetches the resulting commit's diff and compares it against what the user selected/approved: [2](#0-1) 

The partial-commit/line-selection UX is built entirely on a diff snapshot taken before the commit executes (`DiffSelection` computed from `getWorkingDirectoryDiff`/`getTextDiff` hunks), and `createCommit` simply stages whatever `WorkingDirectoryFileChange.selection` says at execution time: [3](#0-2) 

Nothing recomputes or displays the actual diff of the newly created commit for user confirmation. If a hook silently rewrites file contents (e.g., a `prepare-commit-msg`/`pre-commit` hook that appends/removes code) that action is committed and (via `_refreshRepositoryAfterCommit`) treated as a successful, faithful commit of the reviewed changes: [4](#0-3) 

## Impact Explanation
This mirrors the "sandwich" broken invariant: the value the user reviewed (the diff/selection) is not guaranteed to equal the value that is actually finalized (the resulting commit). A cloned repository that ships tooling which installs a hook (a very common real-world pattern, e.g. Husky/Lefthook `prepare` scripts run by `npm install`) can leverage this gap to silently smuggle unreviewed changes into a commit that Desktop's UI still reports as matching the user's selection, and the user may push it without ever noticing the discrepancy — i.e., silent corruption of what the user commits/pushes.

## Likelihood Explanation
Moderate. It requires a hook to already be installed in `.git/hooks` (commonly done via routine project setup steps like `npm install`, which is a normal, expected developer workflow rather than "malware already on the host"). Once installed, every subsequent commit via Desktop is affected without any additional attacker interaction, and Desktop provides no post-commit verification step to catch the divergence.

## Recommendation
After `createCommit` completes (especially when hooks were intercepted and ran), re-diff the resulting commit against the pre-hook staged tree the user approved, and surface a clear warning/confirmation to the user if the hook modified content beyond what was selected in the UI, similar to the existing `DiffContentsWarning` pattern used for hidden bidi characters/line-ending changes.

## Proof of Concept
1. Clone a repository containing a `prepare-commit-msg` (or `pre-commit`) hook that appends attacker-controlled content to a staged file (e.g. via `git commit --amend`-like index manipulation inside the hook) or modifies the commit message trailers.
2. Open the repo in Desktop, make an innocuous change, review the diff in the Changes pane, select specific lines to commit.
3. Click "Commit" — `createCommit` (`app/src/lib/git/commit.ts`) stages the selection and runs `git commit`, during which the hook silently modifies the index/content.
4. Desktop's `_commitIncludedChanges`/`_refreshRepositoryAfterCommit` (`app/src/lib/stores/app-store.ts`) report success without re-diffing the final commit; the user pushes believing the commit matches exactly what they reviewed, but the actual committed tree differs.

  private async _refreshRepositoryAfterCommit(
    repository: Repository,
    newCommitSha: string,
    amendedCommit: Commit | null
  ) {
    await this._refreshRepository(repository)

    const amendedCommitSha = amendedCommit?.sha

    if (amendedCommitSha !== undefined && newCommitSha !== amendedCommitSha) {
      const newState = this.repositoryStateCache.get(repository)
      const newTip = newState.branchesState.tip
      if (newTip.kind === TipState.Valid) {
        this._addBranchToForcePushList(repository, newTip, amendedCommitSha)
      }
    }
  }
