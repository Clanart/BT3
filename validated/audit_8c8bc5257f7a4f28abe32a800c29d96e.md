Based on my research, I found a strong analog to the "inconsistent guard enforcement" bug class: the `parseAppURL` deep-link handler validates the `branch` and `pr` parameters from an `x-github-client://openRepo` URL, but leaves the `filepath` parameter completely unvalidated before it is handed off downstream, exactly mirroring the Ammplify pattern where one code path (`removeMaker`/`adjustMaker`) enforces a safety check while a sibling path (`collectFees`) with equivalent power over the same resource skips it.

### Title
Unsanitized `filepath` parameter in `x-github-client://openrepo` deep link bypasses the validation applied to sibling fields - ([File: app/src/lib/parse-app-url.ts])

### Summary
`parseAppURL` is the entry point for handling `x-github-client://` deep links (e.g. GitHub's "Open in Desktop" button). For the `openrepo` action it extracts three attacker-controlled query parameters — `pr`, `branch`, and `filepath` — and returns them as an `IOpenRepositoryFromURLAction` that the app later acts on (cloning the target repo and opening the given file). [1](#0-0) 

### Finding Description
Two of the three attacker-supplied fields are guarded:
- `pr` must match `/^\d+$/`.
- `branch` must match `/^pr\/\d+$/` (when a PR is present) and is also passed through `testForInvalidChars`. [2](#0-1) 

`filepath`, however, is read straight from the query string with `getQueryStringValue` and returned with **no validation whatsoever** — no character allow-list, no traversal check, no bounding to the eventual repository directory. [3](#0-2) 

This is structurally the same defect as the `collectFees` bug: the invariant "attacker-controlled input reaching a filesystem/repo-affecting operation must be validated" is enforced on the `branch` sibling field but is silently dropped for `filepath`, even though both originate from the same untrusted deep link and both eventually influence a file-system operation (checking out a branch vs. opening a file inside the resulting repository). Just as `collectFees` reused the same underlying settlement machinery as `removeMaker`/`adjustMaker` without the guard those functions apply, `filepath` reuses the same deep-link action object as `branch`/`pr` without the sanitation those fields receive.

### Impact Explanation
`filepath` is documented as "the file to open after cloning the repository". If it is later joined to the freshly cloned repository's path (e.g., via `Path.join(repository.path, filepath)`) without a realpath/`startsWith` containment check, a value such as `../../../../.ssh/id_rsa` or an absolute path would let a link clicked by the user cause Desktop to open (and potentially read or reveal in the OS shell/Explorer) a file outside the cloned repository — matching the "attacker controls ... a link or deep link the user clicks" primitive and the "file read outside the repo" impact class called out as valid.

### Likelihood Explanation
The `openrepo` protocol handler is reachable simply by getting a user to click a crafted `x-github-client://openrepo?url=...&filepath=...` link (e.g., embedded on a web page or GitHub Pages site), requiring no local access, no admin rights, and no prior compromise — consistent with the "unprivileged" requirement. The asymmetry is visible directly in the source: `branch` and `pr` get explicit regex/character checks while `filepath` gets none, in the same function, on the same trust boundary.

### Recommendation
Apply the same defensive treatment to `filepath` that `branch` receives: reject values containing path traversal sequences (`..`), reject absolute paths, and resolve the final path against the target repository's root before use, verifying with `path.resolve`/`startsWith` that it stays within the repository directory — the same principle recommended for `collectFees` (apply the missing guard before the sensitive operation, don't just special-case it after the fact).

Note: I was able to verify the asymmetric validation in `parseAppURL` (`app/src/lib/parse-app-url.ts`) directly, but I could not, within my tool budget, trace the exact downstream consumer of the `filepath` field (likely in `app/src/ui/dispatcher/dispatcher.ts` or `app/src/ui/app.tsx`, both of which reference `open-repository-from-url`) to confirm whether a containment check exists there. This should be verified with a full read of those files before treating the impact as fully confirmed; the finding as stated is scoped to the missing input-side validation, which is a concrete and provable code fact:

```ts
// app/src/lib/parse-app-url.ts
if (actionName === 'openrepo') {
  const pr = getQueryStringValue(query, 'pr')
  const branch = getQueryStringValue(query, 'branch')
  const filepath = getQueryStringValue(query, 'filepath') // <-- no validation at all

  if (pr != null) {
    if (!/^\d+$/.test(pr)) { return unknown }
    if (branch != null && !/^pr\/\d+$/.test(branch)) { return unknown }
  }
  if (branch != null && testForInvalidChars(branch)) { return unknown } // branch is checked

  return { name: 'open-repository-from-url', url: parsedPath, branch, pr, filepath }
}
```
