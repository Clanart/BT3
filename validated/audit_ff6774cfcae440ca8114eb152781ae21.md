### Title
Partial-commit patch generation re-fetches the diff at commit time but replays a stale line-selection bitmap against it, silently committing content the user never reviewed - (File: `app/src/lib/git/apply.ts`)

### Summary
Teller's bug is a broken invariant: the value checked ("borrower owns the collateral") is not the value used later ("collateral actually transferred"), so it can be mutated by the attacker in the gap between check and use. The GitHub Desktop analog is structurally identical for partial commits: the "value checked" is the diff a user reviews and selects lines from in the UI, but the "value used" is a *freshly re-fetched* working-directory diff read again at patch-application time in `applyPatchToIndex`. If the tracked file's on-disk content changes between the moment the user reviews/selects hunks and the moment the commit is actually executed, Desktop applies the old, stale line-selection indices to the new diff structure and stages/commits whatever that produces — without re-showing the diff to the user or detecting the mismatch.

### Finding Description
`applyPatchToIndex` in `app/src/lib/git/apply.ts` re-runs `getWorkingDirectoryDiff(repository, file)` at line 60, i.e. it computes the diff against the current, live working directory content at the moment the patch is generated for `git apply --cached`: [1](#0-0) 

That freshly computed diff is then fed into `formatPatch(file, diff)`, which walks the *new* diff's hunks and consults `file.selection.isSelected(absoluteIndex)` where `absoluteIndex` is derived from `hunk.unifiedDiffStart` of the *current* diff: [2](#0-1) 

The `file.selection` bitmap, however, is a `DiffSelection` object built earlier, when the user reviewed a *different* rendering of the diff (produced by an earlier call to `getWorkingDirectoryDiff` / `getTextDiff` used to populate the Changes UI). `DiffSelection` only stores selected/unselected line indices — it has no notion of hunk identity, content hash, or file mtime, so there is no guard that stops line index `N` in the old diff from being silently re-interpreted as line index `N` in a structurally different new diff. `formatPatch` documents the assumption that the file "must have at least one selected addition or deletion" matching `file.selection` but never validates that the diff passed in is the same diff the selection was computed against.

Contrast this with the more careful pattern in `app/src/ui/diff/seamless-diff-switcher.tsx`, which explicitly checks `isSameFile` / `isSameDiff` before applying loaded file contents, and bails out if "the file has changed while we've been reading it": [3](#0-2) 

No equivalent check exists on the commit path: `stageFiles` → `applyPatchToIndex` (in `app/src/lib/git/update-index.ts`) never compares the diff used to build `file.selection` against the diff it re-fetches for patch generation: [4](#0-3) 

### Impact Explanation
This is a "silent corruption of what the user commits" primitive from the accepted impact list. A working directory can be modified by processes an attacker controls indirectly through a hostile/cloned repository — e.g. a build tool, watcher, formatter, or IDE plugin invoked as part of normal repo tooling (triggered by a checkout, or configured in the repository itself) that rewrites a tracked file's content asynchronously while the user is reviewing a diff and selecting specific hunks/lines to commit. Because Desktop recomputes the diff at apply time but blindly replays the old selection indices, the user can end up staging and committing lines they never selected, or missing lines they did select, without any warning. In the worst case this lets a hostile actor get unreviewed content silently included in a commit that later gets pushed, which is exactly the "corrupts what the user commits or pushes" outcome called out as valid impact.

### Likelihood Explanation
Requires a window between diff-review and commit during which the underlying file content changes (hunk boundaries shift). This is plausible in normal developer workflows (auto-formatters, linters-on-save, build watchers, git hooks triggered by background fetches) and does not require local/physical access, admin rights, or leaked credentials — it only requires the file to be modified by a process associated with the cloned/opened repository while Desktop's UI still holds a stale `DiffSelection`. It's a race/staleness condition rather than a guaranteed one-click exploit, so likelihood is moderate rather than high, but it does not rely on any unnatural user action beyond normal partial-staging usage.

### Recommendation
Before calling `formatPatch`/`applyPatchToIndex`, re-validate that the diff used to build `file.selection` is still consistent with the diff about to be applied (e.g., compare hunk headers/line counts or content hashes, similar to the `isSameDiff`/`isSameFile` guard already used in `seamless-diff-switcher.tsx`). If they diverge, refuse the partial commit and force the UI to reload the diff and require the user to re-select lines, rather than silently reusing stale indices against new hunk structure.

### Proof of Concept
Exact reproduction steps could not be fully verified within the available tool budget (I could not confirm the precise UI call path from `_commitChanges` in `app/src/lib/stores/app-store.ts` down to `stageFiles`/`applyPatchToIndex` due to running out of search iterations). Conceptually:
1. Open a repository in Desktop and modify a tracked file so it has multiple hunks.
2. In the Changes view, select only specific lines/hunks for the commit (partial selection), but do not commit yet.
3. While the commit dialog is open, have an external process (e.g., a formatter, git hook, or file watcher tied to the repository) rewrite the file so the hunk boundaries/line offsets shift.
4. Click "Commit". `applyPatchToIndex` re-fetches the diff (now different) and applies the old `file.selection` indices against the new hunk layout via `formatPatch`.
5. Inspect the resulting commit: it may include lines the user never selected in step 2, or omit lines the user intended to include — with no warning shown to the user. [1](#0-0) [5](#0-4)
