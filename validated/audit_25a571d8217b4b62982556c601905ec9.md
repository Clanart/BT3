### Title
Panic on out-of-range participant index in PedPoP blame evaluation causes denial of service - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
The SparseConcat advisory is a `CHECK`-fail: attacker-controlled "dimension" values are fed into a constructor that aborts instead of returning an error. The Serai analog is `Decryption::decrypt_with_proof` (and `BlameMachine::blame_internal`), which index participant-keyed `HashMap`s with an unvalidated, attacker-supplied `Participant` index, panicking instead of returning a blame verdict.

### Finding Description
`BlameMachine::blame` / `AdditionalBlameMachine::blame` accept `sender`, `recipient`, an `EncryptedMessage`, and an optional `EncryptionKeyProof` — all publicly supplied values (`EncryptedMessage::read`/`EncryptionKeyProof::read` deserialize from untrusted bytes, and `AdditionalBlameMachine::new` explicitly supports non-participants evaluating blame). These flow into `blame_internal` (crypto/dkg/pedpop/src/lib.rs:575) which calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)` (crypto/dkg/pedpop/src/lib.rs:582).

Inside `decrypt_with_proof` (crypto/dkg/pedpop/src/encryption.rs:366-397), after the message's proof-of-possession signature verifies, the code executes `self.enc_keys[&decryptor]` (encryption.rs:388), where `decryptor` is the attacker-chosen `recipient`. `enc_keys` is only populated for participants `1..=n` (encryption.rs:360, lib.rs:656-659). `Participant::new` only rejects index 0 (crypto/dkg/src/lib.rs:121-125); any nonzero value such as `n+1` or `u16::MAX` is a valid `Participant`. Indexing a `HashMap` with an absent key panics.

So a blame accusation naming `recipient = Participant(n + 1)` — accompanied by any authentic `EncryptedMessage` from `sender` (whose PoP challenge binds `sender` but not `recipient`, per `pop_challenge` at encryption.rs:302-324) and any `Some(proof)` — panics the evaluating party instead of returning a blame result. The same class of unchecked indexing exists at `self.commitments[&sender]` (crypto/dkg/pedpop/src/lib.rs:599) and `self.decryption.enc_keys[&participant]` (encryption.rs:466), though the `enc_keys[&decryptor]` path is the one trivially reachable since `recipient` is unconstrained by the PoP.

### Impact Explanation
Like the TensorFlow `CHECK`-fail, this converts untrusted input into a process abort. Any node evaluating a blame claim — including non-participant observers using `AdditionalBlameMachine` — crashes (or the panic unwinds through the protocol handler) rather than returning the faulty party's identity. Since blame evaluation is the abort/slashing path of the DKG, a party can also weaponize it: by naming an out-of-range recipient, an accuser crashes honest evaluators instead of having their invalid accusation adjudicated.

### Likelihood Explanation
Reachability requires: (1) a valid `EncryptedMessage` attributable to `sender` — the PoP signature must verify, which any authentic share message from a real participant satisfies (the accuser legitimately holds messages sent to them, and PoP does not bind the claimed recipient); (2) `proof` set to `Some` (content irrelevant — the panic precedes DLEq verification); (3) `recipient` set to any participant index in `(n, u16::MAX]`. No collusion, key material, or malformed crypto is needed. Severity is bounded by panic containment: if the host catches panics this degrades to a dropped claim, hence Medium rather than High.

### Recommendation
Validate `sender` and `recipient` against `enc_keys`/`commitments` membership at the top of `blame_internal` and `decrypt_with_proof`, returning a defined error (e.g., treating an unknown party as the faulty/invalid input) rather than indexing. Replace `self.enc_keys[&decryptor]` with `get(&decryptor)` plus an error path, and `self.commitments[&sender]` similarly.

### Proof of Concept
```rust
// Participant 1-of-n runs a completed PedPoP DKG and holds a BlameMachine,
// or any third party constructs:
let abm = AdditionalBlameMachine::<Ristretto>::new(context, n, commitment_msgs)?;

// Any authentic EncryptedMessage sent by participant `j` (e.g., the share
// message j sent to us) — its PoP verifies under sender=j.
let msg: EncryptedMessage<Ristretto, SecretShare<_>> =
  EncryptedMessage::read(&mut msg_bytes.as_slice(), params)?;

// Any proof bytes that deserialize; contents are never reached.
let proof = Some(EncryptionKeyProof::read(&mut proof_bytes.as_slice())?);

// Recipient index n+1 is a valid Participant (Participant::new only rejects 0)
// but was never registered in enc_keys (only 1..=n are).
let bogus_recipient = Participant::new(n + 1).unwrap();

// decrypt_with_proof: pop.verify(msg.key, ...) passes since the PoP binds
// `sender` (j) and the message, not `recipient`.
// Then `self.enc_keys[&decryptor]` at encryption.rs:388 indexes a missing key
// -> panic (HashMap index out of bounds), aborting blame evaluation.
abm.blame(j, bogus_recipient, msg, proof);
```
The panic occurs at `self.enc_keys[&decryptor]` (crypto/dkg/pedpop/src/encryption.rs:388) because `pop_challenge` (encryption.rs:302-324) binds `sender` and `msg` but never `decryptor`, so the signature check passes for a genuine message while `decryptor` remains fully attacker-controlled.
