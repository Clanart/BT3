### Title
Anyone can front-run `NewDeposit` to permanently block a user's legitimate deposit - (File: `core/src/database/operator.rs`)

### Summary
`ClementineAggregator::new_deposit` [1](#0-0)  accepts a `Deposit` message containing a caller-chosen `deposit_outpoint` (the Bitcoin UTXO of the deposit) with no authentication or ownership check tying the caller to that outpoint. The aggregator's gRPC server is publicly reachable (unlike the verifier/operator servers, which are restricted to `OnlyAggregatorAndSelf`), so any unauthenticated party can call `NewDeposit`, or the verifier/operator gRPC endpoints could be reached with attacker-controlled `evm_address`/`recovery_taproot_address` fields for that same outpoint.

### Finding Description
`new_deposit` builds `DepositData` purely from request-supplied fields (`evm_address`, `recovery_taproot_address`, `deposit_outpoint`) plus the current verifier/operator sets, and immediately drives verifiers to sign and persist this via `insert_deposit_data_if_not_exists` [2](#0-1) . This function's binding invariant is "first write for a `deposit_outpoint` wins; every later write must match exactly," enforced by the `DepositDataMismatch` check [3](#0-2) .

Because a deposit's `deposit_outpoint` is deterministic from the Bitcoin UTXO the user is about to spend into (derivable from the P2TR deposit address, which is itself derived from public info: verifier set, network, and the intended EVM/recovery address a user might reuse or that an attacker can guess/observe once the deposit transaction is broadcast to the mempool but not yet confirmed by the aggregator), an attacker who observes an unconfirmed deposit transaction can race the depositor by calling `new_deposit` first with a *different* `evm_address` or `recovery_taproot_address` for the same `deposit_outpoint`. The verifiers will sign and durably store this attacker-supplied deposit data as `deposit_id`'s permanent record for that outpoint. When the legitimate depositor's `new_deposit` request later arrives with the correct data, `insert_deposit_data_if_not_exists` detects the mismatch against the already-stored (attacker) row and returns `BridgeError::DepositDataMismatch`, permanently rejecting the honest deposit for that outpoint. There is no way to overwrite or correct the record — the equality `stored_deposit_data == depositor_intended_data` is broken and cannot be re-established, exactly like the DKIM report's front-run of `checkTimelock`: an unprivileged caller pre-empts a state-setting call to permanently block the legitimate actor's later, otherwise-valid call.

### Impact Explanation
This breaks the "deposit presigned versus deposit minted once" binding: the deposit outpoint that the honest user actually funds gets bound (in the bridge's off-chain bookkeeping and covenant signatures) to attacker-chosen EVM/recovery address data instead of the depositor's own, or is permanently blocked from being recorded correctly. Since Clementine's deposit_id/deposit_data record is a one-time, non-overwritable commitment gating which verifiers sign and how funds are credited on Citrea, an attacker can permanently deny an honest user the ability to register their deposit correctly, leaving BTC that lands in the move-to-vault UTXO with no way to be matched to a correct EVM credit for that depositor — a permanently frozen/misattributed vault UTXO.

### Likelihood Explanation
High. `new_deposit` requires no signature proving the caller controls the `deposit_outpoint`'s private key at call time — it is unauthenticated, and the deposit address/outpoint becomes visible once the depositor broadcasts (or even before confirmation, in the mempool). Any observer capable of front-running a mempool transaction with a call to the public aggregator RPC can trigger the attack, mirroring the "high likelihood... anyone can execute this attack by front-running" characterization in the source report.

### Recommendation
Require the depositor to authenticate ownership of the `deposit_outpoint` as part of `new_deposit` (e.g., a signature from the recovery/user key over the deposit parameters, verified before the first `insert_deposit_data_if_not_exists` write), or make the deposit address itself binding to the specific `evm_address`/`recovery_taproot_address` such that only the intended depositor's funding transaction can occupy that outpoint's deposit slot with correct data.

### Proof of Concept
1. Attacker monitors the Bitcoin mempool/node and observes user Alice's unconfirmed deposit transaction to deposit address `D`, revealing `deposit_outpoint = O`.
2. Attacker calls the public `ClementineAggregator::new_deposit` RPC with `deposit_outpoint = O` but attacker-controlled `evm_address`/`recovery_taproot_address`, before Alice's own `new_deposit` call lands.
3. Verifiers sign and `insert_deposit_data_if_not_exists` persists the attacker's deposit data for `deposit_id` bound to `O` [4](#0-3) .
4. Alice's legitimate `new_deposit(O, her_evm_address, her_recovery_address)` call now hits the mismatch branch and is rejected forever [5](#0-4) , permanently blocking her from correctly registering the deposit she is about to (or already did) fund.

    pub async fn insert_deposit_data_if_not_exists(
        &self,
        mut tx: Option<DatabaseTransaction<'_>>,
        deposit_data: &mut DepositData,
        paramset: &'static ProtocolParamset,
    ) -> Result<u32, BridgeError> {
        // compute move to vault txid
        let move_to_vault_txid = create_move_to_vault_txhandler(deposit_data, paramset)?
            .get_cached_tx()
            .compute_txid();

        let query = sqlx::query_as::<_, (i32,)>(
            "INSERT INTO deposits (deposit_outpoint, deposit_params, move_to_vault_txid)
                VALUES ($1, $2, $3)
                ON CONFLICT (deposit_outpoint) DO NOTHING
                RETURNING deposit_id",
        )
        .bind(OutPointDB(deposit_data.get_deposit_outpoint()))
        .bind(DepositParamsDB(deposit_data.clone().into()))
        .bind(TxidDB(move_to_vault_txid));

        let result =
            execute_query_with_tx!(self.connection, tx.as_deref_mut(), query, fetch_optional)?;

        // If we got a deposit_id back, that means we successfully inserted new data
        if let Some((deposit_id,)) = result {
            return Ok(u32::try_from(deposit_id).wrap_err("Failed to convert deposit id to u32")?);
        }
