### Title
Scanner credits unspendable outputs as received payments without verifying spendability — unchecked "receive" result analogous to unchecked `transferFrom` (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
The external report describes a call (`transferFrom`) whose boolean failure return is ignored, so a trade is queued although no fee was actually received. In Serai's Bitcoin crate, the analogous shape is the Scanner/`ReceivedOutput` flow in `networks/bitcoin/src/wallet/mod.rs` (with `ReceivedOutput::read` and the `scan`/`register_offset` machinery): an output is reported as "received" based solely on matching the expected `script_pubkey`, without checking that the output is actually spendable by the network — i.e., the "transfer succeeded" signal is trusted without verification of the conditions that make the funds real and spendable.

### Finding Description
The Bitcoin wallet's scanner identifies payments to the FROST/Taproot group key by matching a transaction output's `script_pubkey` against the key's expected tweaked script. That match is treated as conclusive evidence of payment. However, `script_pubkey` equality alone does not establish spendability:

- An output to the correct script can be a coinbase (immature < 100 confirmations) output, or a dust output below the economic spendability threshold given prevailing feerates.
- The matched output may be spent in a later transaction; a scanner that keys "received" state purely on script matching without tracking spend/maturity state reports value that cannot be (or is no longer) moved.
- Because the internal key tweak is deterministic (`x_only`/`needs_negation` in `networks/bitcoin/src/crypto.rs`), anyone can compute the deposit script and send an output to it — there is no authentication of the sender's intent or of a minimum amount bound to a `register_offset`-tracked commitment. An attacker can therefore manufacture "payments" that scan as received but whose satoshis are unspendable (dust whose fee-to-spend exceeds value, or deliberately timelocked/immature coinbase outputs).

Just as `initiateTrade` ignored `transferFrom`'s `false` return and proceeded to queue the trade as if the fee had arrived, the scanner proceeds on the weak "script matches" signal and reports funds received that are not spendable.

### Impact Explanation
Funds are reported received that are not spendable — a payment the protocol accounts as real value that the threshold key cannot actually co-sign to move economically (dust) or legally (immature coinbase). An unprivileged party only needs to broadcast a Bitcoin transaction paying to the (publicly derivable) group-key script; no trusted input is required. Downstream accounting that trusts `ReceivedOutput` events can release value (e.g., credit a deposit) against outputs the validator set can never consolidate.

### Likelihood Explanation
Medium. Deriving the deposit `script_pubkey` requires only the group key and standard TapTweak math (`x_only`, `needs_negation` in `networks/bitcoin/src/crypto.rs`), which any observer of the network can compute. Producing a non-spendable or uneconomical output (dust under the spend fee, or a miner-crafted coinbase) requires only sending a transaction — no collusion, no leaked key, no malicious peer. The missing check is structural (script-only matching), so triggering it costs only transaction fees.

### Recommendation
Wrap the "received" determination in a spendability precondition, mirroring the recommendation to wrap `transferFrom` in `require(...)`: before a `ReceivedOutput` is reported, verify (a) the output is not an immature coinbase, (b) its value exceeds a dust/economic-spendability threshold computed from the current feerate and the spend transaction's weight, and (c) the output is still unspent when consumed. Consider also binding the reported output to its `register_offset` commitment context so that an output can only satisfy one registered intent.

### Proof of Concept
1. Obtain the Serai validator set's Bitcoin group key (public).
2. Compute its Taproot-tweaked `script_pubkey` via `x_only(key + H_taptweak(key)*G)` (the same `x_only`/`needs_negation` helpers in `networks/bitcoin/src/crypto.rs` used by `register_offset`).
3. Broadcast a transaction paying an output to that script with a value below the spend-fee dust threshold (e.g., a few hundred sats), or arrange it as a coinbase output so it is immature for 100 blocks.
4. The Scanner reports the output as a received payment; the reported funds are not spendable by any threshold signature the set can economically produce — the protocol has credited a transfer that effectively returned "false".
