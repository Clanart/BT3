### Title
Missing-key panic in `Decryption::decrypt_with_proof` / `Encryption::encrypt` via untrusted `Participant` index — (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP encryption helpers keep a `HashMap<Participant, C::G>` of registered per-participant encryption keys and index it with `self.enc_keys[&decryptor]` / `self.decryption.enc_keys[&participant]` (the `[]` indexing operator) rather than a checked `get`. When blame/decryption is exercised with a `Participant` that never registered an `EncryptionKeyMessage` — a value fully determined by attacker-supplied bytes read via `EncryptionKeyMessage::read`/`EncryptedMessage::read`/`EncryptionKeyProof::read` — the map lookup evaluates to "absent" and `HashMap`'s `Index` impl panics. This is the direct Serai analog of the `@commercial/subtext` prototype-pollution class: an attacker-influenced key selects a map entry that was never populated (the "null prototype"), and accessing the "payload" produces an unhandled exception.

### Finding Description
`Decryption::register` only inserts into `enc_keys` and asserts against re-registration; nothing guarantees every participant in `params` registered a key before `decrypt_with_proof` or `encrypt` runs:

- `crypto/dkg/pedpop/src/encryption.rs:388` — `self.enc_keys[&decryptor]` inside `decrypt_with_proof`. `decryptor` comes from the call site handling a decryption/blame for a message read with `EncryptedMessage::read` (encryption.rs:171-177), and `proof` is deserialized with `EncryptionKeyProof::read` (encryption.rs:267-269). If `decryptor` was never `register`ed, this indexing panics.
- `crypto/dkg/pedpop/src/encryption.rs:466` — `self.decryption.enc_keys[&participant]` inside `encrypt`, same unchecked index.
- `Decryption::register` (encryption.rs:351-362) only enforces *no duplicate* registration; it does not check `participant <= n` against `ThresholdParams`, nor enforce that all expected participants registered before later use. An attacker can simply withhold or omit a registration (or have their claimed key message rejected upstream for an unrelated reason), then trigger a code path that indexes the missing entry.

Because all of `EncryptedMessage::read`, `EncryptionKeyMessage::read`, and `EncryptionKeyProof::read` are byte-level deserializers of unauthenticated DKG-channel input, an untrusted party controls which `Participant` values flow into the blaming/decryption logic. The panic is an unconditional `panic!` from `HashMap::index`, unwinding (or aborting) the calling thread — matching the advisory's "prototype evaluates to null → unhandled exceptions when the request payload is accessed" failure mode.

### Impact Explanation
A remote, unauthenticated-by-design DKG participant can crash the PedPoP key-generation/decryption path in the target process by causing `decrypt_with_proof` (blame handling) or `encrypt` to be invoked for a participant index with no registered key. In a coordinator/processor context running key generation, an uncaught panic aborts the DKG session at best and takes down the task/thread handling it at worst — an availability denial of service reachable purely through crafted/omitted DKG messages, with no valid key compromise required. Severity: Medium — no secret material is leaked (the ECDH keys stay inside `enc_key`), but a single attacker message deterministically panics the victim.

### Likelihood Explanation
The PedPoP DKG explicitly assumes only an *authenticated*, not *honest*, channel, and the code comments acknowledge participants "are faulty and should be presumed malicious". Triggering requires only that the attacker omit their `EncryptionKeyMessage` registration (or get it dropped for any reason) and then participate in a flow that reaches `decrypt_with_proof` with their (or another absent) `Participant` index — e.g., an accusation/blame round where decryption proofs are processed. No races, thresholds, or collusion needed; the panic is deterministic once the index is absent.

### Recommendation
Replace the unchecked `HashMap` index operations with presence-checked lookups:

- In `decrypt_with_proof`, use `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?` (or a dedicated `UnknownParticipant` error).
- In `encrypt`, return a `Result`/panic-free path: `self.decryption.enc_keys.get(&participant).copied().ok_or(...)` instead of `[&participant]`.
- Optionally, at `Decryption::new`/`register` time, validate `participant <= params.n()` and require all `n` keys registered before enabling `encrypt`/`decrypt_with_proof`, so a missing key is a protocol error rather than a panic site.

### Proof of Concept
```rust
// Conceptual, within crypto/dkg/pedpop
// Assume ThresholdParams { t, n, i } where participant P never sent an
// EncryptionKeyMessage, so `decryption.enc_keys` has no entry for P.

let mut enc = Encryption::<C>::new(context, i, &mut rng);
// Other participants register, P does not.

// Blame path: a decryption proof is processed for an EncryptedMessage
// whose alleged decryptor is P.
let msg = EncryptedMessage::<C, Share>::read(&mut attacker_bytes, params)?; // valid PoP + ciphertext
let proof = EncryptionKeyProof::<C>::read(&mut attacker_proof_bytes)?;      // attacker-crafted DLEq

// encryption.rs:388  ->  self.enc_keys[&P]  with no entry for P
// std HashMap Index impl: panic!("HashMap key not found" / index out of bounds)
let _ = enc.into_decryption().decrypt_with_proof(from, P, msg, Some(proof));
// => thread panics; DKG/blame handling aborted
```

Note on scope: I verified the unchecked `HashMap` indexing in `encryption.rs` directly. I could not fully trace every upstream call site of `decrypt_with_proof`/`encrypt` in `pedpop/src/lib.rs` within the available context, so the exact dispatch that feeds an unregistered `Participant` into these functions is inferred from the PedPoP message flow (registration → encrypt → decrypt/blame) rather than confirmed line-by-line at the caller. The panic primitive itself is unambiguous.
