### Title
Unhandled `UnicodeDecodeError` when decoding DID metadata from an untrusted coin can crash wallet DID processing - ([File: chia/wallet/did_wallet/did_wallet_puzzles.py])

### Summary
`did_program_to_metadata()` decodes the key/value bytes stored in a DID singleton's curried metadata argument as UTF‑8 with no exception handling. A DID coin (or any spend that a wallet uncurries as a DID puzzle) can embed arbitrary bytes in that metadata slot. If those bytes are not valid UTF‑8, `str(val, "utf-8")` raises `UnicodeDecodeError`, which propagates uncaught out of wallet code that processes untrusted, attacker-controlled puzzle reveals — the same bug class as the OctoRPKI advisory, where a single malformed field (there, a `NUL` byte in an ROA; here, a non‑UTF‑8 byte sequence in DID metadata) caused an unhandled crash while parsing untrusted repository/coin data.

### Finding Description
`did_program_to_metadata` iterates the metadata program's key/value pairs and blindly decodes every value as UTF‑8: [1](#0-0) 

This function is invoked from wallet code paths that reconstruct a DID's state from an on-chain coin spend that the local wallet does not control and did not create — e.g. `manual_did_search()` and `find_lost_did()` in `WalletStateManager`, which uncurry a coin spend's puzzle reveal via `match_did_puzzle()` and then call `did_program_to_metadata(metadata)` on the curried metadata `Program` taken directly from that puzzle reveal: [2](#0-1) [3](#0-2) 

`did_wallet.py` also calls `did_program_to_metadata` on metadata derived from a spend/coin that is not necessarily wallet-originated. None of these call sites wrap the metadata decode in a `try/except`, so any DID coin whose curried metadata slot contains a value atom that is not valid UTF‑8 will raise `UnicodeDecodeError` when a wallet processes that coin (via `manual_did_search`, `find_lost_did`, or normal DID discovery/recovery code paths built on the same helper).

This mirrors the CWE‑20 (improper input validation) root cause of the referenced OctoRPKI advisory: a parser assumes well-formed encoded content from an external/untrusted source and has no defensive handling for malformed bytes, so a single crafted value causes an unhandled exception instead of a graceful rejection.

### Impact Explanation
An attacker can create/broadcast a DID singleton (or otherwise get a victim wallet to observe/spend a DID coin) whose metadata program contains a non‑UTF‑8 byte string in any key's value. When the victim wallet runs `manual_did_search`, `find_lost_did`, or other DID-metadata-processing code over that coin — paths reachable by a normal wallet user recovering/searching DIDs on chain, or by wallet sync code that consumes attacker-supplied singleton state — the uncaught `UnicodeDecodeError` will propagate and can halt/crash the wallet's processing task for that coin/DID. This is a spend-triggered transaction/data-processing halt against a wallet, matching the "unauthenticated crash from malformed data" class in the referenced advisory, though scoped to wallet-side DID metadata handling (not full-node consensus or mempool admission).

### Likelihood Explanation
Likelihood is moderate: any party can mint a DID or otherwise craft a spend with an arbitrary metadata value, and a victim wallet only needs to call one of the affected helper functions on that coin's puzzle reveal (a normal recovery/search operation) to trigger the crash. No signature or special privilege is required to construct the malformed metadata value — it only needs to be embedded in a puzzle reveal that a victim wallet chooses to uncurry as a DID.

### Recommendation
Wrap the per-value decode in `did_program_to_metadata` in a try/except (or validate/sanitize bytes before decoding, e.g. `str(val, "utf-8", errors="replace")` or skip/flag non-decodable entries) so that malformed metadata from an untrusted DID coin cannot raise an unhandled exception in wallet code paths (`WalletStateManager.manual_did_search`, `find_lost_did`, and any other caller in `did_wallet.py`).

### Proof of Concept
1. Construct a DID singleton puzzle whose curried metadata argument is a CLVM list containing a key/value pair where the value atom is a byte string that is invalid UTF‑8 (e.g. a lone continuation byte such as `0x80` or `0xFF`).
2. Get this coin observed by a target wallet (e.g. spend it on-chain, or have the wallet uncurry the puzzle reveal via `manual_did_search`/`find_lost_did`).
3. When the wallet calls `did_program_to_metadata(metadata)` on the extracted metadata `Program`, `str(val, "utf-8")` raises `UnicodeDecodeError`, propagating uncaught and aborting the wallet operation processing that coin.

**Note on verification limits:** I confirmed the unhandled decode and its two call sites (`wallet_state_manager.py`, `did_wallet.py`) via search, but could not fully trace every invocation of `did_program_to_metadata` inside `did_wallet.py` (e.g., whether it also runs unconditionally during normal background wallet sync of any observed DID coin, versus only on-demand recovery commands) within the available tool budget. Confirming the exact automatic-sync reachability would benefit from a full read of `chia/wallet/did_wallet/did_wallet.py`.

```python
def did_program_to_metadata(program: Program) -> dict[str, str]:
    """
    Convert a program to a metadata dict
    :param program: Chialisp program contains the metadata
    :return: Metadata dict
    """
    metadata = {}
    for key, val in program.as_python():
        metadata[str(key, "utf-8")] = str(val, "utf-8")
    return metadata
```
