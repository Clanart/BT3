### Title
GET request timeout refunds ignore `DispatchGet.payer`, sending relayer-fee refunds to the wrong beneficiary - (File: `evm/src/core/EvmHost.sol`)

### Summary
This is the same class of bug as the report: contradictory/ignored field semantics around fee accounting cause funds to move to the wrong party. In the OFT adapter, `send`'s strict `msg.value != fee` check contradicted `_payNative`'s `<` check. In Hyperbridge's `EvmHost`, the `DispatchGet` struct explicitly documents a `payer` field ("Account responsible for paying the fees... if different from msg.sender"), mirroring `DispatchPost.payer` which is honored correctly in `dispatch(DispatchPost)`. But `dispatch(DispatchGet)` silently drops `get.payer` and stores `_msgSender()` as the refund recipient instead.

### Finding Description
Compare the two dispatch functions:

- `dispatch(DispatchPost memory post)` correctly records `_requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee})` — honoring the caller-supplied `payer`. [3](#0-2) 

- `dispatch(DispatchGet memory get)` instead records `_requestCommitments[commitment] = FeeMetadata({sender: _msgSender(), fee: get.fee})`, discarding `get.payer` entirely even though the struct field exists and is documented identically to `DispatchPost.payer`. [4](#0-3) 

This `FeeMetadata.sender` value is later used as the exclusive beneficiary of the relayer-fee refund when a GET request times out:
```solidity
if (meta.fee != 0) {
    // refund relayer fee
    IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
}
``` [5](#0-4) 

Any contract built on `HyperApp` that dispatches a GET request on behalf of a different `payer` (this is an explicitly documented, supported pattern per the interface docs, and shown in the docs' `readRemoteState`/`dispatchWithFeeToken` examples using a `payer` parameter distinct from `msg.sender`) will have its fee refund permanently misdirected to whatever contract/EOA happens to be `_msgSender()` at dispatch time instead of the intended fee payer. [6](#0-5) 

### Impact Explanation
This is a fund-misdirection bug reachable via a fully public, unprivileged entrypoint (`IDispatcher.dispatch(DispatchGet)`), matching the bounty's "unauthorized transaction... wrong beneficiary or amount... fund loss" criteria. Any intermediary/relaying HyperApp contract (e.g. anything wrapping `dispatchWithFeeToken` for GET requests with a distinct `payer`) loses the ability to have the true fee payer refunded on timeout — the funds instead go to `_msgSender()` (the calling contract), which may have no mechanism to forward that refund back to the real payer, effectively locking or misappropriating the fee token.

### Likelihood Explanation
High for any composed application that reuses the `payer` field for GET dispatch as its docs suggest is valid usage; the bug requires no malicious actor, relayer, or governance action — it triggers purely from correct, documented use of `DispatchGet.payer` followed by a natural request timeout.

### Recommendation
Change `dispatch(DispatchGet)` in `EvmHost.sol` to honor `get.payer` for `FeeMetadata.sender`, consistent with `dispatch(DispatchPost)`:
```solidity
_requestCommitments[commitment] = FeeMetadata({sender: get.payer, fee: get.fee});
```

### Proof of Concept
1. Contract `A` (a HyperApp) calls `dispatch(DispatchGet)` on `EvmHost`, setting `get.payer = userB` while `msg.sender` (from the Host's perspective, `_msgSender()`) resolves to contract `A` itself (e.g. because `A` is itself invoked via a relayer forwarding pattern, or `A` calls `dispatch` while intending `userB`, the original caller, to be refundable).
2. `EvmHost.dispatch(DispatchGet)` stores `FeeMetadata({sender: address(A), fee: get.fee})`, ignoring `userB`. [4](#0-3) 
3. The GET request times out; `dispatchTimeOut` (or the analogous GET-timeout handling path) refunds `meta.fee` in `feeToken()` to `address(A)`. [5](#0-4) 
4. `userB`, the documented fee payer, never receives the refund; funds settle at the wrong beneficiary (contract `A`), which may have no logic to forward them.
