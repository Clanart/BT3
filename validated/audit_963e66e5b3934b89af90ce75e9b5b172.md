### Title
Panic on attacker-controlled preprocess causing signer DoS via empty nonce-sum indexing — ([File: crypto/frost/src/algorithm.rs])

### Summary
The generic `Algorithm` implementation for Schnorr signatures indexes `nonce_sums[0][0]` and `nonces[0][0]` without checking that the bound nonce vector is non-empty. These vectors are built from `BindingFactor`, which is populated entirely from peer-supplied `Preprocess` messages (`Commitments::read` / `read_preprocess`). If a peer sends a preprocess whose commitments yield an empty per-nonce generator/commitment list (or a `BindingFactor` whose `nonces()` output is shorter than the algorithm's `nonces()` spec), the signer panics inside `sign_share` (`algorithm.rs:208`), or the completer panics inside `verify` (`algorithm.rs:215`) / `verify_share` (`algorithm.rs:226`). This is the direct Serai analog of CVE-2022-39400: untrusted input to a routine (here, a signature-share preprocessing routine instead of a query optimizer) that reaches a repeatable crash/DoS rather than an error return.

### Finding Description
`AlgorithmSignMachine::sign` constructs `Rs = B.nonces(&nonces)` from the merged peer preprocesses and passes `&Rs` into `sign_share` [1](#0-0) . `Schnorr::sign_share` then blindly does `nonce_sums[0][0]` [2](#0-1) . Likewise `complete` calls `algorithm.verify`, which evaluates `nonces[0][0]` [3](#0-2) , and `verify_share` does the same [4](#0-3) . There is no bounds check or `FrostError` path guarding a zero-length outer or inner `Vec<C::G>`; a malformed preprocess produces a panic (abort of the signing task/thread) rather than `FrostError`.

### Impact Explanation
An unprivileged participant (or any party able to submit a serialized preprocess to `read_preprocess`/`sign`) can cause a repeatable crash of a signing node. In a threshold network, crashing signers mid-protocol halts signing sessions (availability loss), matching the CVE's "hang or frequently repeatable crash" availability-only impact. Panics across an `await`/task boundary in production hosts typically take down the whole signing service.

### Likelihood Explanation
Reachability requires that `Commitments::read`/`BindingFactor` not fully enforce the shape dictated by `algorithm.nonces()` — i.e., that a peer-committed nonce list can be empty or shorter than the local specification while still being accepted into `B`. The panic sites themselves are unconditional index expressions on peer-influenced data; where a length mismatch is possible the crash is deterministic and trivially repeatable. I could not fully confirm whether `Commitments::read` enforces the expected nonce-commitment count, so the likelihood hinges on that deserialization path permitting a structurally short preprocess; if it does not, the crash is still reachable via any future `Algorithm` whose `nonces()`/`BindingFactor` plumbing yields empty sums.

### Recommendation
Replace indexing with checked access in `Schnorr::sign_share`, `verify`, and `verify_share` (e.g., `nonce_sums.first().and_then(|v| v.first()).ok_or(())`-style), returning `FrostError`/`None` instead of panicking. Additionally validate in `AlgorithmSignMachine::sign` that every `Preprocess.commitments` contributes exactly `algorithm.nonces().len()` nonce entries before building `B`.

### Proof of Concept
1. Initialize an `AlgorithmMachine` with `IetfSchnorr` and valid `ThresholdKeys` (t-of-n, n ≥ 2).
2. From a peer slot, craft a serialized `Preprocess` whose `Commitments` deserializes successfully via `read_preprocess` but carries zero `NonceCommitments` (or fewer than `nonces()` = `[[G]]` expects), then pass it in the `commitments` map to `sign`.
3. `sign` builds `Rs` via `B.nonces(&nonces)` yielding an empty/short vector, then `Schnorr::sign_share` executes `nonce_sums[0][0]` → index-out-of-bounds panic, aborting the signing session. The same panic triggers in `complete` via `algorithm.verify` if the empty-sum preprocess reaches finalization.
