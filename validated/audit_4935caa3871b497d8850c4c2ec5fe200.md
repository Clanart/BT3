### Title
Signature-wrapping in `addr` precompile's `associate()` allows unauthorized forced association and fund migration via cross-context signature replay - (File: precompiles/addr/addr.go)

### Summary
The onelogin/php-saml advisory is a signature-wrapping class bug: a cryptographic signature is verified as valid without the verifier confirming the signature was produced *for the specific context/message it is being used to authorize*, letting an attacker "wrap" a signature meant for one purpose into an unrelated trusted operation. Sei-chain's `Associate` EVM precompile method reproduces this pattern: it verifies only that `(v,r,s)` recovers to a valid secp256k1 pubkey over `keccak256(customMessage)` — with no EIP-191/personal-sign prefix, no chain ID, no contract address, and no purpose tag binding the signature to "I want to associate my Sei/EVM addresses." Any raw digest signature the victim ever produced elsewhere, whose signer supplies the same raw bytes as `customMessage`, is accepted here and triggers an irreversible, fund-moving state transition.

### Finding Description
`associate()` in `precompiles/addr/addr.go` recovers a pubkey directly from caller-supplied `v, r, s` and a `customMessageHash` computed as a raw `keccak256` of an arbitrary caller-supplied string, with no domain separation: [1](#0-0) 

The recovered pubkey derives both `evmAddr` and `seiAddr`, and is passed to `associateAddresses`, which is callable by anyone (no `msg.sender` binding requirement) as long as they can supply a valid signature over some `customMessage`: [2](#0-1) 

Because the signed digest is a raw `keccak256(customMessage)` with no personal-sign prefix (`\x19Ethereum Signed Message:\n...`), no chain ID, and no "associate" purpose tag, this is structurally identical to any other raw-hash ECDSA signature scheme (e.g., legacy Ethereum transaction signing, where the sighash is also `keccak256` of RLP-encoded data). If a victim ever produces a raw-digest ECDSA signature elsewhere whose signed byte-string is knowable/reconstructable by an attacker (for example, a previously broadcast/observed raw transaction, or any other protocol that signs raw `keccak256(bytes)` digests with the same secp256k1 key), an attacker can resupply those exact bytes as `customMessage` along with the harvested `(v,r,s)` to this precompile. The verification step only checks "is this a valid signature over this hash" — it never checks that the signature was created with the intent of invoking the Sei address-association precompile, exactly mirroring the SAML signature-wrapping root cause (checking signature validity while failing to bind it to the intended, wrapped context).

Once accepted, `associateAddresses`/`AssociateAddresses` performs an irreversible, state-changing operation: [3](#0-2) 
It sets the permanent Sei↔EVM address mapping, installs the pubkey on the account, and — critically — migrates all funds (spendable coins, wei balance) from the `castAddr` (direct EVM→Sei cast address) into the resolved `seiAddr`, and can also remove the previously-existing empty cast account: [4](#0-3) 

This is reachable by any unprivileged EVM caller (public RPC → EVM tx → `Associate` precompile call), matching the required "single submitted transaction/contract call" reachability.

### Impact Explanation
A successful wrapped-signature replay lets an attacker force an association and fund migration for a victim's address pair without the victim's consent or awareness, at a time and in a way the victim did not intend. Because `MigrateBalance` moves *all* spendable coins and wei from the cast address to the derived Sei address and can delete the cast account, an attacker could use this to front-run or grief a victim's intended association flow, or to move funds out of a `castAddr` the victim was still using as an independent account, causing unexpected fund relocation. This satisfies the "unauthorized transfer via precompile" and "fund loss/relocation" impact bar, since the transfer of custody (cast address → derived Sei address) occurs due to a signature accepted outside its intended context.

### Likelihood Explanation
Exploitation requires the attacker to possess a raw ECDSA `(v,r,s)` signature from the victim over a digest computable as `keccak256(rawBytes)`, plus knowledge of `rawBytes` to resupply as `customMessage`. This is plausible whenever a victim has ever signed a raw digest with the same secp256k1 key in a context where the signed bytes are public or knowable (e.g., prior broadcast transactions, other raw-hash-signing protocols, or reused test/demo keys), since `keccak256` domain separation is exactly what's missing here. The likelihood is Medium: it requires a specific but realistic precondition (victim reusing a key for raw, un-prefixed digest signing elsewhere) rather than a universal, always-exploitable flaw, but the underlying design flaw (no domain separation / purpose binding on the signed message) is undisputable and directly analogous to the CVE's root cause.

### Recommendation
Add explicit domain separation to the `associate` signing scheme: prefix the hashed message with a fixed, chain-specific, purpose-specific tag before hashing (e.g., `keccak256("SeiAssociate:" || chainID || customMessage)`), or require EIP-191 personal-sign formatting so wallet-signed messages cannot collide with raw-digest signatures from unrelated protocols. Additionally, consider requiring `customMessage` to embed a nonce/expiry or the caller's intended `seiAddr`/`evmAddr` pair to prevent any signature reuse across contexts.

### Proof of Concept
1. Victim signs a raw digest `h = keccak256(m)` in an unrelated protocol using their secp256k1 key, producing `(v, r, s)`, where the raw bytes `m` are publicly observable (e.g., a broadcast RLP-encoded transaction, or a message from another dApp with no domain separation).
2. Attacker submits an EVM transaction calling `Associate(v, r, s, m)` on the `addr` precompile at `0x0000000000000000000000000000000000001004`.
3. `associate()` recomputes `customMessageHash = keccak256(m)`, matching `h`, recovers the victim's pubkey via `helpers.GetAddresses`, and derives `evmAddr`/`seiAddr`.
4. `associateAddresses` proceeds because no prior association exists, permanently sets the Sei↔EVM mapping and triggers `MigrateBalance`, moving all funds from `castAddr` to `seiAddr` — all without the victim ever calling or authorizing this transaction. [5](#0-4) [6](#0-5)

func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)

func (p PrecompileExecutor) associateAddresses(ctx sdk.Context, method *abi.Method, evmAddr common.Address, seiAddr sdk.AccAddress, pubkey cryptotypes.PubKey) (ret []byte, remainingGas uint64, err error) {
	// Check that address is not already associated
	_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if found {
		return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
	}

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)
	err = associationHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}
