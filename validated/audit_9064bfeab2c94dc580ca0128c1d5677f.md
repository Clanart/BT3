### Title
Unauthenticated `InternalSendTx` broadcast when aggregator runs with `client_verification=false` - ([File: core/src/rpc/interceptors.rs], [File: core/src/rpc/aggregator.rs])

### Summary
`is_internal()` (used to restrict `Internal*`-prefixed RPCs to the aggregator's own certificate) is only evaluated inside `only_aggregator_and_self`; when the server is configured with `client_verification=false`, `create_grpc_server` selects `Interceptors::Noop`, whose `call` implementation returns `Ok(req)` unconditionally with no certificate or authorization check at all. This lets any network caller invoke `InternalSendTx` and have the aggregator broadcast an attacker-chosen raw transaction.

### Finding Description
The claimed binding is: *a caller reaching `internal_send_tx` (an aggregator method that broadcasts a transaction) == a party holding the aggregator's own TLS certificate*. That equality is enforced only by `only_aggregator_and_self`'s `is_internal` check [1](#0-0) , but `Interceptors::call` dispatches to that function only for the `OnlyAggregatorAndSelf` variant; the `Noop` variant simply returns `Ok(req)` with zero checks [2](#0-1) .

`create_grpc_server` in `core/src/servers.rs` selects `Noop` whenever `config.client_verification` is `false`, and in that branch the TLS config is built without `client_ca_root`, i.e. the server does not require any client certificate at all [3](#0-2) .

The actual `internal_send_tx` handler (found at `core/src/rpc/aggregator.rs`, not `extended_bitcoin_rpc.rs` as the question states) takes the request's `raw_tx` bytes, decodes them into a `bitcoin::Transaction`, and inserts it directly into `self.tx_sender` for broadcast/fee-management, with no validation binding the bytes to any known presigned transaction, deposit, or protocol state: [4](#0-3) .

Consequently, when the aggregator is deployed with `client_verification=false`, any unprivileged network caller who can reach the gRPC port can call `InternalSendTx` with arbitrary `raw_tx` bytes, and the aggregator's `tx_sender` will attempt to broadcast/fee-bump it using the aggregator's own fee-paying infrastructure — with no signature-chain-of-custody, no `is_internal` gate in effect, and no other authorization check in `internal_send_tx` itself.

### Impact Explanation
This matches the explicitly listed High-severity category "an unauthenticated state-changing or broadcasting call." An attacker can cause the aggregator to repeatedly broadcast arbitrary transactions, consuming the aggregator's fee-paying UTXOs/wallet for transactions it never intended to send (griefing the fee wallet), and there is no check anywhere in `internal_send_tx` that ties the raw bytes to a legitimate presigned bridge transaction. This is repeatable per call and not limited to a single deposit or operator, since `internal_send_tx` has no association to `deposit_id`/`kickoff`/`operator` context at all.

### Likelihood Explanation
The vulnerability is entirely gated on the deployment configuration `client_verification=false`. If an operator deploys the aggregator with this flag disabled (the code emits only a `tracing::warn!` and continues, `core/src/servers.rs:306-308`), the Noop interceptor is installed and there is no defense-in-depth check at the RPC-handler level for `internal_send_tx`. Attacker cost is limited to establishing a TLS connection to the port (no client certificate required in this mode) and constructing a raw Bitcoin transaction; no BTC outlay is strictly required to trigger a broadcast attempt.

### Recommendation
Do not rely solely on the interceptor layer for the `Internal*` RPC family. Add an explicit authorization/self-check inside `internal_send_tx` (and other `Internal*` handlers) independent of which `Interceptors` variant is active, or refuse to start the aggregator's gRPC server with `Noop`/`client_verification=false` in any non-test build (e.g., gate `Noop` behind `cfg!(test)`, matching the precedent already used for missing peer certs in `only_aggregator_and_self`).

### Proof of Concept
```
cargo test -p core --features automation -- internal_send_tx_noop_unauthenticated
```
Test plan: start an aggregator gRPC server via `create_aggregator_grpc_server` with a `BridgeConfig` that has `client_verification = false`; connect a plain client with no client TLS certificate presented (or a self-signed unrelated cert); call `InternalSendTx(RawSignedTx{raw_tx: <arbitrary valid tx bytes>})`; assert the call returns `Ok` and that `tx_sender`'s queue/database contains the attacker-supplied transaction (i.e., `insert_try_to_send` succeeded), demonstrating that no `is_internal`/certificate check was applied before broadcast was attempted.
