### Title
Payout transaction's OP_RETURN operator-attribution field is not covered by the SIGHASH_SINGLE|ANYONECANPAY signature, allowing reimbursement credit to be reassigned away from the operator who actually fronted the withdrawal - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The `create_payout_txhandler` in `core/src/builder/transaction/operator_reimburse.rs` builds the payout transaction with an OP_RETURN output that records which operator's x-only pubkey fronted the peg-out, but the user's payout signature only uses `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY`. That sighash flag commits only to the single spent input and the single output sharing its index; the anchor output and, critically, the OP_RETURN attribution output are left completely unauthenticated. Anyone who observes the signed input (e.g. in the mempool, or via the aggregator's fan-out of the withdrawal request to all operators) can rebuild an equivalent, still-validly-signed payout transaction with a different or garbage OP_RETURN payload and get it confirmed instead, silently reassigning (or erasing) which operator is credited with reimbursement for a payout it never funded.

### Finding Description
`create_payout_txhandler` [1](#0-0)  constructs the payout transaction with:
1. output[0]: the user's payout (value/script committed by the sighash),
2. output[1]: an anchor,
3. output[2]: `op_return_txout(operator_xonly_pk.serialize())` - the attribution of which operator fronted the withdrawal.

`Operator::withdraw` explicitly documents and enforces that the input signature must use `SinglePlusAnyoneCanPay`: [2](#0-1) . Under `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY`, the signature commits only to the spent input and the single output at the same index; every other input/output (including the anchor and, decisively, the OP_RETURN attribution output) is left completely unconstrained and can be swapped by any party holding the raw signature and outpoint, without invalidating the signature.

Later, when the block-syncer processes a confirmed payout, `update_finalized_payouts` blindly trusts whatever OP_RETURN ended up on-chain to determine which operator gets credited: [3](#0-2) 

This value is persisted as `payout_payer_operator_xonly_pk` and used downstream by each operator's own `PayoutCheckerTask`, which looks for unhandled payouts filtered strictly by its own `xonly_public_key`: [4](#0-3) 

If the OP_RETURN is altered to a different operator's pubkey, or to an unparsable/garbage value (parsed as `None`, treated like an optimistic payout), the operator that actually funded the withdrawal from its own funds will never match this filter, and can never trigger `handle_finalized_payout` for that withdrawal - it is permanently unable to be reimbursed for a payout it did fund, while the withdrawal `idx` (uniquely bound to one deposit/one payout) is already consumed, so the honest operator cannot ever get a `kickoff_txid` created for it either. This breaks the intended equality "operator credited == operator who actually paid," matching the report's core failure pattern of an unenforced completion/attribution state that a third party can rewrite to hijack or nullify ownership of an already-settled action.

### Impact Explanation
This is a Critical-impact issue per the defined categories: an honest operator can be made permanently unable to be reimbursed for a payout it genuinely fronted with its own capital, because reimbursement-credit attribution is derived from an unauthenticated OP_RETURN field rather than from a value actually bound by the user's signature. The same mechanism also allows an unrelated operator xonly pubkey (attacker-controlled or arbitrary) to be substituted into the credited field, i.e. an operator being "reimbursed" for a payout it never funded, if that operator's automation later manages to claim it through `handle_finalized_payout`/`get_unused_and_signed_kickoff_connector` [5](#0-4) .

### Likelihood Explanation
Exploitability requires only observing the raw signed payout input (available in the mempool once any operator broadcasts the original payout, or distributed to all operators by the aggregator's `withdraw` fan-out [6](#0-5) ) and rebuilding an equivalent transaction with a different OP_RETURN, then getting it mined first (e.g., via a higher fee/CPFP on the anchor output). No verifier/operator/watchtower key compromise or majority hashrate is needed - only network-level transaction replacement/race, which is within scope of "an unauthenticated state-changing or broadcasting call."

### Recommendation
Bind the operator-attribution OP_RETURN output into the committed part of the payout transaction, e.g., by using a different sighash flag that covers all outputs, or by having the aggregator/verifiers co-sign (or otherwise authenticate) the specific operator pubkey associated with a withdrawal before the payout is accepted as final, and by validating on settlement that the OP_RETURN operator pubkey matches the operator that was actually authorized/expected to front that specific withdrawal (deterministically assigned, not free-form data any broadcaster can set).

### Proof of Concept
1. Operator A (or the user via the aggregator) broadcasts a valid `payout_tx` for withdrawal `W`, signed with `SIGHASH_SINGLE|ANYONECANPAY`, with OP_RETURN = Operator A's xonly pubkey [7](#0-6) .
2. Before confirmation, any party (having seen the mempool tx or the signature via the aggregator's broadcast to all operators [6](#0-5) ) rebuilds a transaction reusing the same signed input and the same output[0] (required by SIGHASH_SINGLE), but with a modified anchor/OP_RETURN, e.g. OP_RETURN = garbage bytes or Operator B's pubkey, and gets it confirmed first (higher fee/CPFP).
3. `update_finalized_payouts` parses the confirmed OP_RETURN and stores `payout_payer_operator_xonly_pk` accordingly (garbage → `None`, or Operator B) [3](#0-2) .
4. Operator A's `PayoutCheckerTask::get_first_unhandled_payout_by_operator_xonly_pk` never matches this withdrawal (wrong/`None` pubkey stored) [4](#0-3) , so Operator A - who actually paid the user - can never trigger `handle_finalized_payout` for this withdrawal index, permanently losing its reimbursement path for that payout.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
