### Title
`SignableTransaction` omits the OP_RETURN output from its fee/vsize estimate, so transactions carrying `data` pay a lower fee rate than requested and may fail to relay - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The reported bug class is "fee computed on a crude/incorrect estimate of the transaction's actual cost, rather than the real bytes." In `bitcoin-serai`, `SignableTransaction::new` computes `vbytes` and `needed_fee` from `payments` only, even though an attacker- or user-controlled `data` parameter adds an OP_RETURN output of up to 80 bytes to the actual transaction. The estimate therefore systematically mismatches the signed transaction's real weight whenever `data` is set.

### Finding Description
`SignableTransaction::new` accepts `data: Option<Vec<u8>>` (up to 80 bytes) and appends an OP_RETURN output to `tx_outs` (lines 193–202). However, the weight/vbytes used for fee computation are derived only from `payments`:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```
`networks/bitcoin/src/wallet/send.rs:204-206`

`calculate_weight_vbytes` builds a dummy `Transaction` whose outputs are exactly `payments` (plus optional `change`), with no OP_RETURN output (lines 68–99). The same omission occurs in the change branch at lines 225–227, which again calls `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` ignoring `data`.

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` prices a transaction that is ~90+ vbytes smaller than the real one (8-byte amount + compactsize + script length + up to 82 bytes of OP_RETURN script).
- The minimum-relay-fee guard at line 211 (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) also validates against the underestimated size, so a caller can pass it while the *actual* fee rate falls below 1 sat/vbyte — making the resulting transaction non-standard under Bitcoin Core policy and unrelayable.
- The produced, signed transaction's real fee rate is strictly lower than the `fee_per_vbyte` the caller specified, violating the documented contract "the fee necessary for this transaction to achieve the fee rate specified at construction" (`needed_fee`, lines 129–135).

The reachability matches the bug-class filter: `data` is arbitrary public input supplied by whoever constructs the `SignableTransaction` (`new` is a public API), and the miscalculation lands in the transaction the threshold group then signs via `TransactionSignMachine::sign`.

### Impact Explanation
A transaction carrying `data` is signed and broadcast paying less than the intended fee rate. At worst (low `fee_per_vbyte`, large `data`), the signed transaction falls under the mempool minimum relay fee and cannot propagate, so funds intended to move are stuck until an entirely new signing round produces a corrected transaction — a liveness/funds-unspendable impact on signed outputs, not merely an economic preference. Even when relayable, every user of the `data` field silently underpays relative to the negotiated fee rate.

### Likelihood Explanation
Deterministic whenever `data.is_some()`; no adversarial precondition beyond supplying non-empty `data` to `SignableTransaction::new`. The bug triggers on any network conditions since the estimate simply never accounts for the OP_RETURN output.

### Recommendation
Include the OP_RETURN output in the size estimate — e.g., extend `calculate_weight_vbytes` to take the full output list (or `data: Option<&[u8]>`) and construct the dummy `TxOut` with `ScriptBuf::new_op_return(...)` the same way `new` does at lines 195–202, both for the no-change estimate (line 204) and the with-change estimate (line 226).

### Proof of Concept
```rust
// networks/bitcoin crate; demonstrates needed_fee is computed without the OP_RETURN output.
let data = vec![0u8; 80];
let st_no_data = SignableTransaction::new(
    inputs.clone(), &payments, change.clone(), None, fee_per_vbyte)?;
let st_data = SignableTransaction::new(
    inputs, &payments, change, Some(data), fee_per_vbyte)?;

// Both report the same needed_fee, but st_data's transaction is strictly larger:
assert_eq!(st_no_data.needed_fee(), st_data.needed_fee());
assert!(st_data.transaction().weight() > st_no_data.transaction().weight());
// => st_data's real fee rate < fee_per_vbyte; with fee_per_vbyte == 1 it can drop
//    below DEFAULT_MIN_RELAY_TX_FEE and become non-standard/unrelayable.

    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
