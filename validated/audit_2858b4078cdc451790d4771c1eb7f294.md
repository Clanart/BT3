### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates over **all** transactions in a block, including `block.txdata[0]` (the coinbase), via `scan_transaction`. The returned `ReceivedOutput` values are indistinguishable from normal outputs — they carry only `offset`, `output`, and `outpoint`, with no maturity flag — yet coinbase outputs are unspendable for 100 blocks per Bitcoin consensus rules (COINBASE_MATURITY). [1](#0-0) [2](#0-1) 

### Finding Description
`scan_transaction` matches untrusted chain data (`tx.output[*].script_pubkey`) against the registered script map and emits a `ReceivedOutput` for every match [3](#0-2) . `scan_block` then feeds it every transaction in the block, coinbase included [4](#0-3) .

`ReceivedOutput` exposes `value()` and `outpoint()` but nothing indicating the output comes from a coinbase [5](#0-4) . A downstream consumer treating a scanned output as a confirmed, spendable balance (e.g., crediting a deposit or queueing it for `SignableTransaction`) will incorporate a `TxIn` referencing an immature coinbase outpoint. Any transaction spending it is consensus-invalid: Bitcoin rejects `bad-txns-premature-spend-of-coinbase` until the coinbase is 100 blocks deep. The only documented mitigation is a doc comment stating "a post-processing pass is needed" — but the API provides no field or method on `ReceivedOutput` to distinguish coinbase outputs, so the check must be re-derived externally by comparing `outpoint.txid` against `block.txdata[0]`.

This maps the bug class (memory-unsafe handling of untrusted parsed content) onto Serai's real shape: untrusted block data is parsed into a structure that misrepresents the spendability of funds.

### Impact Explanation
Funds are reported received that are not spendable — an impact class explicitly in scope. An integration that feeds `scan_block` results into accounting or signing pipelines can (a) credit a deposit that cannot be moved, and (b) construct transactions that will be rejected by the network, stalling the signing pipeline. Additionally, coinbase outputs are uniquely vulnerable to being invalidated by shallow reorgs during the immaturity window, amplifying the discrepancy between reported and actual balance.

### Likelihood Explanation
Any miner can create a coinbase paying the scanner's P2TR script; miners are unprivileged third parties relative to the wallet. The condition requires only that a coinbase output pays to a registered script — trivially achievable, and it also arises naturally on regtest/self-mined setups. Medium likelihood: the exposure depends on the consumer failing to re-implement maturity filtering that the API itself does not support.

### Recommendation
- Skip `block.txdata[0]` inside `scan_block`, or require the caller to pass a flag/slice explicitly (e.g., scan `&block.txdata[1..]` internally and document that coinbase is excluded).
- Alternatively, add a `maturity`/`is_coinbase` field to `ReceivedOutput` so consumers can programmatically filter, and gate spending-selection code on it.

### Proof of Concept
```rust
// Any miner crafts a coinbase paying to the scanned P2TR output.
let mut block = rpc.get_block(&hash).unwrap();
// txdata[0] is the coinbase; give it an output matching scanner's script:
// block.txdata[0].output[0].script_pubkey == p2tr_script_buf(key)

let outputs = scanner.scan_block(&block);
// outputs[0] is a ReceivedOutput for the coinbase output
assert_eq!(outputs[0].outpoint().txid, block.txdata[0].compute_txid());

// outputs[0] is indistinguishable from a spendable output:
// ReceivedOutput { offset, output, outpoint } has no coinbase/maturity marker.
// Spending it immediately produces a tx rejected with
// "bad-txns-premature-spend-of-coinbase" for 100 blocks.
```

Note: the doc comment at lines 218–220 acknowledges this caveat, which weakens severity — but the API still cannot express the distinction on `ReceivedOutput`, so the "post-processing pass" it demands is not actually implementable from the returned data alone.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  /// Scan a block.
  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
  }
}
