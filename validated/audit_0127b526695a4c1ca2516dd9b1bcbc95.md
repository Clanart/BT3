### Title
Attacker-controlled participant count `n` in `ThresholdKeys::read` causes disproportionate allocation and unbounded deserialization work - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to the Monero `tree_hash` report (an untrusted count drives a memory allocation far larger than the supplied data), `ThresholdKeys::read` takes a `u16` `n` directly from the input stream and immediately uses it to size `Vec::with_capacity(n)` and to drive two `n`-iteration deserialization loops (`read_F`, `read_G`) plus a `HashMap` insertion loop — all before `ThresholdParams::new`/`ThresholdKeys::new` ever validate `n`. `ThresholdKeys::read` is one of the explicitly reachable untrusted-byte sinks. [1](#0-0) 

### Finding Description
In `ThresholdKeys::read`, the header parsing reads `t`, `n`, and `i` as raw `u16`s with no bound. `n` can therefore be `65535`. When `interpolation == 0` (Constant), the code executes `Vec::with_capacity(usize::from(n))` — allocating ~`n * size_of::<C::F>()` bytes (≈2 MB for a 32-byte scalar at `n = 0xFFFF`) — having consumed only ~10 bytes of attacker input. It then loops `n` times calling `C::read_F`, and afterwards loops `1 ..= n` calling `C::read_G` and inserting into a `HashMap`. Each `read_G` performs point decompression, so a ~5 MB crafted buffer forces ~65k scalar reads plus ~65k point decompressions and hash-map insertions. Validation of `n` against any sane bound only happens inside `ThresholdParams::new`/`ThresholdKeys::new` at the very end, after all allocation and parsing work is done — and even there, `n = 65535` is accepted (the only checks are zero/`t <= n`/`i <= n`; the `n <= 150` bound exists only in the coordinator, not in this crate).

Contrast with the out-of-scope coordinator code, which does guard allocation (`commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT` in `Transaction::read`); the in-scope `dkg` crate performs no equivalent pre-allocation sanity check.

### Impact Explanation
Uncontrolled resource consumption reachable from untrusted bytes:

- **Memory amplification**: a ~10-byte prefix (`t`, `n = 0xFFFF`, `i`, `interpolation = 0`) forces a ~2 MB `Vec::with_capacity` allocation before any payload bytes are required. Repeated calls cause allocation churn; concurrent calls multiply transient memory pressure.
- **CPU amplification**: a fully-formed ~5 MB payload forces ~65k `read_G` decompressions and hash-map insertions per message, then succeeds — producing a `ThresholdKeys` claiming 65535 participants that downstream code (interpolation, `verification_shares` iteration) will continue to operate on at O(n) or worse cost.
- If any caller retains the resulting `ThresholdKeys`, each malicious input permanently inflates memory by ~5 MB plus `HashMap` overhead.

### Likelihood Explanation
`ThresholdKeys::read` is listed as an untrusted-input sink. Any deployment path that loads serialized `ThresholdKeys` from an unprivileged or partially trusted channel (resynchronization, key backup/restore, a malicious participant's contributed bytes during setup flows that deserialize keys) exposes this. The attacker needs no privileges, no valid signature, and only ~10 bytes to trigger the allocation, or ~5 MB to trigger the full deserialization/insertion workload.

### Recommendation
- Validate `n` before allocating or looping: enforce a protocol-level maximum participant count (e.g. 255/150 consistent with coordinator limits) and reject `n` above it in `ThresholdKeys::read`/`ThresholdParams::new`.
- Avoid `Vec::with_capacity(n)` on unvalidated input; either drop the pre-reservation or cap it.
- Similarly, bound the `1 ..= n` `read_G` loop so deserialization cost cannot exceed a fixed budget regardless of the declared `n`.
