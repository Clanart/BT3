### Title
Stale diff-selection indices applied to a freshly-fetched diff can silently mis-stage/mis-commit lines — ([File: app/src/lib/git/apply.ts])

### Summary
`applyPatchToIndex` builds the patch that is staged/committed from a **freshly fetched** working-directory diff, but reuses the file's `DiffSelection` (a set of line indices) that was computed against a **previously rendered** diff. If the file's on-disk hunk layout changes between the moment the user reviews/selects lines in the UI and the moment the commit is actually created, the cached line-index selection is applied to different underlying content without being revalidated, silently changing what gets staged and committed — the same "cached value applied to changed state" pattern described in the Paladin `votesDifference` report.

### Finding Description
When staging a partially-selected file, `stageFiles` calls `applyPatchToIndex`, which re-fetches the diff at apply time: [1](#0-0) 

That fresh `diff` is then passed to `formatPatch(file, diff)`, which decides what to include in the outgoing patch purely by checking `file.selection.isSelected(absoluteIndex)` against the *new* diff's hunk/line indices: [2](#0-1) 

`file.selection`, however, is populated earlier by `_selectWorkingDirectoryFiles` / `updateChangesWorkingDirectoryDiff`, which itself documents that it does not verify semantic equivalence of previously-selected indices when the diff is reloaded — it only prunes indices that are no longer valid line positions: [3](#0-2) 

So the invariant that is broken is: *"the line indices in `DiffSelection` always refer to the same logical change in the diff that will actually be applied."* Just like `pledgeParams.votesDifference` was cached at pledge-creation time and then reused unchanged against a receiver balance that could differ later, `file.selection` is cached against the diff shown at review time and reused unchanged against a diff re-fetched at commit time (`applyPatchToIndex` -> `getWorkingDirectoryDiff`). Nothing recomputes or re-validates that a given `absoluteIndex` still corresponds to the same content the user intended to (de)select — the existing mitigation in `app-store.ts` only removes indices that literally no longer exist as includeable lines; it does not detect indices that still exist structurally but now point at different content because the hunk shifted (e.g., another process inserted/removed lines elsewhere in the file, or hunk boundaries realigned).

### Impact Explanation
If the working tree content changes between the diff render and the actual `git apply --cached`/commit step (e.g., a build tool, editor autosave, a git hook triggered by another Desktop operation, or content rewritten by a smudge/clean filter defined by a cloned/attacker-controlled repository's `.gitattributes`), the stale selection can cause `git apply --cached` to stage/commit lines the user never reviewed or explicitly deselected, or omit lines the user believed were included. This is a silent corruption of what the user commits (and subsequently pushes), matching the "silent corruption of what the user commits or pushes" impact category — no error is surfaced because `git apply` succeeds against the new diff, it simply encodes the wrong intent.

### Likelihood Explanation
This requires the file content to change between diff generation and patch application — a window that exists on every partial commit, and can be widened/triggered by repository-controlled mechanisms (filters, hooks) or concurrent tooling rather than requiring local/admin access or leaked credentials. It does not require unnatural user steps: partial staging via the diff view is a normal Desktop workflow. I was not able to fully trace the exact call path from `_commitIncludedChanges` inside the time budget, so the precise timing window between diff review and `applyPatchToIndex`'s re-fetch (and whether Desktop re-renders the diff to the user before committing) is unconfirmed — this should be verified by a Devin session with full read access to `app/src/lib/stores/app-store.ts`'s commit flow and `dispatcher.ts`.

### Recommendation
Before building the patch in `applyPatchToIndex`, compare the freshly fetched diff's hunk headers/line content against the diff on which `file.selection` was computed; if they differ, force a re-render of the diff and require re-confirmation of the selection instead of silently applying stale indices. Alternatively, snapshot and pass through the exact diff object used for selection instead of re-fetching a new diff at apply time.

### Proof of Concept
1. Open a file in the Changes view with several independent hunks and partially select some added/deleted lines (not "select all").
2. Before the resulting patch is applied (e.g., during the async window opened by `stageFiles`/`applyPatchToIndex` at [4](#0-3) ), have another process (a build script, formatter-on-save, or a repository-defined git hook/filter) modify the same file, shifting line numbers/hunks while keeping some `absoluteIndex` positions structurally valid.
3. Trigger the commit. `getWorkingDirectoryDiff` returns the new diff; `formatPatch` re-applies the stale `file.selection.isSelected(absoluteIndex)` bitmap from step 1 to the new hunks at [5](#0-4) , producing and applying a patch that includes/excludes different content than what the user reviewed and selected, with no warning shown to the user.
