`place_bid` derives both the onchain map key (`Bids::<T>::insert(&commitment, &filler, deposit)`) and the offchain storage key (`Self::offchain_bid_key(&commitment, &filler)`) from the exact same `(commitment, filler)` tuple, computed once per call and written synchronously within the same extrinsic execution [1](#0-0) . The offchain key generation is a pure deterministic function of `commitment` and the SCALE-encoded filler account id [2](#0-1) [3](#0-2) , so there is no attacker-controlled binding field that can cause the onchain marker and offchain payload to key to different bidder/commitment contexts — both always reference the identical bidder and commitment within one call.

`retract_bid` performs the same pairing: it reads the deposit from `Bids` keyed by `(commitment, filler)`, unreserves it, removes the onchain entry, and clears the offchain entry using the identically-derived key, all in the same atomic transaction [4](#0-3) . There is no intermediate step where one store could authenticate an "old" context while another consumes a "new" one — no proof verification, no cross-chain message, and no two-phase commit exists in this call path; it is a single synchronous storage mutation.

The only "replace" semantics are within `place_bid` itself: if a bid already exists for `(commitment, filler)`, the old deposit is unreserved before the new deposit is reserved and both the onchain deposit value and offchain `Bid` (which stores `filler` and `user_op`) are overwritten together using the same key [5](#0-4) . There's no path where an attacker-supplied `user_op` or filler value can decouple the two stores, since the filler is derived from `ensure_signed(origin)` (not attacker-suppliable as an arbitrary account for someone else's bid) and the commitment is a single opaque `H256` used consistently in both operations. The scope-limit's "mixing bytes valid in one context but interpreted in another" pattern (e.g., cross-chain replay, signature domain confusion) doesn't apply here, as `place_bid`/`retract_bid` involve no proof or cross-domain byte reinterpretation — only local runtime storage keyed on values fixed at call time.
