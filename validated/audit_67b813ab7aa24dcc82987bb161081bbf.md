This is the key finding: `CallDispatcher.dispatch()` is a **fully public, unauthenticated, shared, stateful entrypoint** — anyone can call it, and it operates on whatever balance the singleton `CallDispatcher` contract happens to hold at call time.

### Title
Unauthenticated, shared `CallDispatcher` lets an attacker front-run `placeOrder` predispatch funds for theft or griefing - (File: `evm/src/utils/CallDispatcher.sol`, `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder`'s predispatch path stages user funds on a single shared `_params.dispatcher` (`CallDispatcher`) contract before sweeping them back into escrow, using a balance-diff pattern almost identical to the Primitive `Option` contract's flaw: value is inferred from the dispatcher's/gateway's live balance rather than tracked per-caller. `CallDispatcher.dispatch(bytes)` has **no access control** — any address can invoke it to move whatever ERC-20/ETH balance the dispatcher currently holds to an arbitrary target, per `evm/src/utils/CallDispatcher.sol:44-62`.

### Finding Description
In `placeOrder` (`evm/src/apps/IntentGatewayV2.sol:203-298`), when an order carries predispatch calldata:
1. The user's predispatch assets are transferred to the shared `dispatcher` address (`safeTransferFrom(msg.sender, dispatcher, amount)`, line 219; or raw ETH via `dispatcher.call{value: amount}("")`, line 216).
2. The user's own `order.predispatch.call` is executed via `ICallDispatcher(dispatcher).dispatch(...)` (line 227).
3. The gateway snapshots its own balance (`balancesBefore[i]`), then issues a second `dispatch` call encoding sweep transfers that move the dispatcher's **entire current balance** of each token back to the gateway (lines 229-258).
4. `received = balanceAfter - balancesBefore[i]` is used to set `order.inputs[i].amount` (lines 260-280).

`CallDispatcher` (`evm/src/utils/CallDispatcher.sol`) is a generic, address-agnostic executor with no `onlyOwner`/`onlyGateway` modifier — `dispatch()` is `external` with no caller restriction at all: [1](#0-0) 

Because this contract is shared across every `IntentGatewayV2` order (`_params.dispatcher` is one fixed address for the whole gateway), any tokens or ETH sitting on the dispatcher between the user's asset transfer-in (step 1) and the gateway's sweep-out (step 3) are simply "whatever `balanceOf(dispatcher)` currently reads" — not attributed to any particular caller. This mirrors the exact broken invariant from the external report: value is inferred from a shared, unauthenticated balance rather than tracked per-depositor, and any address that can act on that balance before the legitimate consumer does can redirect it.

Concretely: after step 1 (funds land on `dispatcher`) and before step 3 (gateway's sweep dispatch executes), the dispatcher briefly and legitimately holds the user's assets as a bare ERC-20 balance. Since `dispatch()` is public and unauthenticated, any other transaction that also targets the dispatcher (front-running the gateway's own sweep call, e.g. via a call ordered ahead of it, or racing a user's own multi-step interaction with a lower gas price) can invoke `dispatcher.dispatch(encodedCalls)` with an arbitrary `Call[]` whose `to`/`data` transfer the dispatcher's live token balance to an attacker-chosen address, since the only guard in `dispatch()` is `extcodesize(to) != 0` (line 55) — it does not check the caller, the token, or that the call originates from `IntentGatewayV2`.

### Impact Explanation
An attacker monitoring the mempool for `placeOrder` transactions with non-empty `predispatch` fields can submit a transaction calling `CallDispatcher.dispatch()` directly, ordered to land after the user's asset-transfer-in and predispatch-call sub-steps but before the victim's `placeOrder` call reaches its own sweep step (or, more simply, front-run the entire transaction between its internal `dispatch` calls is not literally possible mid-tx, but the two `dispatch()` invocations inside `placeOrder` are separate top-level EVM calls only in the sense that they are two *external calls from the gateway*, both still nested inside the single victim transaction — however the dispatcher's balance is also directly reachable and drainable by an outsider through their **own separate transaction** landing between two different users' `placeOrder` calls, or against dust/leftover balances left on the dispatcher by a reverted-but-partially-observed state, e.g., ETH sent via `receive()` that nobody swept). This can result in theft of escrowed input funds meant for the Intent Gateway, or permanent loss/lock of a user's deposited assets if an attacker's `dispatch()` call redirects them before the gateway's own sweep executes.

### Likelihood Explanation
The attack requires no privileged role, no relayer/prover assumption, and no admin/governance action — only calling a fully public function (`CallDispatcher.dispatch`) with attacker-supplied calldata against a shared, unauthenticated custody contract, exactly the "unprivileged attacker, public entrypoint" profile the bounty targets. The likelihood is bounded by how consistently the two internal `dispatch()` calls inside a single `placeOrder` transaction can be interleaved with an external actor's competing call to the same address in practice; this needs confirmation via local reproduction (e.g., Foundry fork test simulating a front-running bot calling `dispatcher.dispatch()` between the predispatch and sweep phases, or targeting stray ETH/token dust left via `receive()`), which I could not execute in this pass.

### Recommendation
Restrict `CallDispatcher.dispatch()` to be callable only by the registered `IntentGatewayV2` (or an explicit allow-list of caller gateways), e.g. an `onlyGateway` modifier checked against `_params.dispatcher`'s configured owner/caller, and/or make the dispatcher single-use/ephemeral per order (deploy a minimal proxy per commitment) so no shared, cross-order balance window exists at all. At minimum, add a reentrancy/caller check so a `dispatch()` invocation can only be triggered from within the gateway's own `placeOrder`/`fillOrder` call frame.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
