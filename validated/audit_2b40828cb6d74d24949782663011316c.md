Audit Report

## Title
Dust pre-funding bypasses the SIMD-0232/0392 rent-exemption gate for commission/fee collector accounts via `Bank::collector_type_checked` - (File: runtime/src/bank/fee_distribution.rs)

## Summary
`Bank::collector_type_checked` waives the SIMD-0232 rent-exemption requirement for a commission/fee collector account whenever `pre_lamports != 0`, using raw nonzero balance as a proxy for "already legitimately funded." This is weaker than the correct SIMD-0392 relaxation criterion used elsewhere in the codebase, which requires the account's pre-execution rent state to have actually been `RentState::RentExempt`. Any unprivileged actor can pre-fund a future collector address with 1 lamport via an ordinary `SystemInstruction::Transfer` (no recipient signature required), permanently satisfying `pre_lamports != 0` and disabling rent-exemption enforcement for all subsequent commission/fee deposits to that address.

## Finding Description
`collector_type_checked` is invoked both from `deposit_fees` (per-slot transaction fee deposits) and from `load_and_reward_commission_accounts` (epoch commission payouts): [1](#0-0) [2](#0-1) 

The vulnerable check is: [3](#0-2) 

When `relax_post_exec_min_balance_check` (SIMD-0392) is active, the rent-exemption requirement is bypassed whenever `pre_lamports != 0`, regardless of whether the account was ever actually rent-exempt. Since `pre_lamports` is read directly from account state on every call and deposits only add lamports, once any nonzero balance is observed the check is permanently disabled for that address.

This is inconsistent with the correct SIMD-0392 relaxation logic implemented elsewhere, which gates relaxation on the account having previously been in `RentState::RentExempt`, not merely nonzero: [4](#0-3) [5](#0-4) 

The system program's `transfer` instruction only requires the sender to sign, not the recipient, so anyone can pre-fund an arbitrary pubkey: [6](#0-5) 

The existing test suite demonstrates the exact flawed behavior: an account with a nonzero but sub-rent-exempt pre-balance (`rent_exempt_minimum - 2`) is accepted for deposit when `relax_post_exec_min_balance_check` is enabled, confirming the check keys off "nonzero" rather than "was rent-exempt": [7](#0-6) 

## Impact Explanation
This breaks the invariant that non-vote-account commission/fee collectors must be, and remain, rent-exempt per SIMD-0232 — a guarantee whose purpose is to ensure reward/fee lamports accumulate only in accounts guaranteed to persist. Once bypassed via a 1-lamport pre-fund, a collector address can indefinitely receive inflation-reward commission, block-revenue commission, and priority-fee deposits while staying below the rent-exempt minimum, constituting a false acceptance of a collector account that the enforced rules should reject/burn deposits to.

## Likelihood Explanation
The setup action — sending 1 lamport to a known pubkey via an ordinary unsigned-recipient `Transfer` — is cheap, unprivileged, and requires no special conditions beyond acting before the target address's first deposit while it is not yet rent-exempt. Commission-collector pubkeys become public once submitted via `UpdateCommissionCollector`/`InitializeAccountV2`, making them plausible targets to pre-fund ahead of their first real deposit.

## Recommendation
Replace the `pre_lamports == 0` proxy in `collector_type_checked` with a check on whether the account's pre-execution state was actually rent-exempt (e.g., using `rent.is_exempt(pre_lamports, data_len)`, or reusing `get_pre_exec_account_rent_state`/`get_post_exec_account_rent_state` from `svm/src/rent_calculator.rs`), so only accounts that were genuinely already rent-exempt are grandfathered, and accounts that never reached rent-exemption continue to be rejected regardless of dust pre-funding.

## Proof of Concept
1. Attacker identifies/observes a pubkey `C` a validator intends to designate as `block_revenue_collector`/`inflation_rewards_collector`.
2. Before `C` is ever used as a collector and before it is rent-exempt, attacker sends 1 lamport to `C` via a normal `SystemInstruction::Transfer` (no signature needed from `C`).
3. When the validator's commission/fee is later deposited via `deposit_fees` or the epoch commission path, `pre_lamports` for `C` reads as `1` instead of `0`.
4. `collector_type_checked` takes the `relax_post_execution_balance_checks` branch and returns `Ok(ExternalCollectorType::SystemAccount)` even though `C` is not rent-exempt, as reproduced by the existing `test_deposit_or_burn_fee_respects_relaxed_post_exec_min_balance_check` test's `InitializedToSubRentExemptMinimum` case, which succeeds under this feature despite a sub-rent-exempt balance.

pub fn get_post_exec_account_rent_state(
    account_lamports: u64,
    account_size: usize,
    min_balance: u64,
    pre_rent_state: &RentState,
    pre_exec_balance: u64,
    relax_rent_exempt_criteria: bool,
) -> RentState {
    if !relax_rent_exempt_criteria {
        return get_account_rent_state(account_lamports, account_size, min_balance);
    };

    match (account_lamports, &pre_rent_state) {
        (0, _) => RentState::Uninitialized,
        (post_balance, _) if post_balance >= min_balance => RentState::RentExempt,
        (post_balance, RentState::RentExempt) if post_balance >= pre_exec_balance => {
            RentState::RentExempt
        }
        (post_balance, _) => RentState::RentPaying {
            data_size: account_size,
            lamports: post_balance,
        },
    }
}
