## Title
Unbounded EIP-7702 authorization list is fully processed (ECDSA recovery + state writes) before fee/gas checks in the EVM ante pipeline - ([File: x/evm/ante/preprocess.go])

### Summary
The reported bug class is an unbounded, attacker-controlled array (`SellOrder.whitelist`) that is iterated with real per-element cost, letting an attacker force disproportionate gas/CPU consumption. The analogous construct in this codebase is the `AuthList` of an EIP-7702 `SetCodeTx`: `EVMPreprocessDecorator.AnteHandle` iterates over every authorization in the list and performs signature recovery plus a state read/write for each one, and this loop runs *before* any decorator checks that the sender can pay for it (intrinsic gas, fee sufficiency, or block-gas limits).

### Finding Description
`EVMPreprocessDecorator.AnteHandle` switches the context to an infinite gas meter (because "EVM handles gas checking from within") and then, for `SetCode` transactions, calls `associateAuthorizationAuthorities`, which loops over every entry in `ethTx.SetCodeAuthorizations()`: [1](#0-0) [2](#0-1) 

Each iteration calls `helpers.AuthorityToPreAssociate` (which recovers the signer address from the authorization signature) and, for authorizations that pass the chain-id/nonce checks, `associateHelper.AssociateAddresses` inside a fresh `CacheContext` (an account-keeper read plus a conditional KV write).

Crucially, `EVMPreprocessDecorator` is placed *before* `BasicDecorator` (which performs the `core.IntrinsicGas` check that prices each authorization, and the `etx.Gas() > block.MaxGas` check) and before `EVMFeeCheckDecorator` (which verifies the sender can actually pay) in the EVM ante chain: [3](#0-2) [4](#0-3) 

Because the association loop runs under an infinite gas meter and ahead of any gas/fee validation, the number of authorizations processed is bounded only by the raw transaction/mempool size limits, not by the gas the sender is willing or able to pay. A transaction can be filled with thousands of `SetCodeAuthorization` entries (~100+ bytes each), all of which get ECDSA-recovered and looked up against state on every node processing the transaction (`CheckTx` and `DeliverTx`), before the transaction is ultimately rejected for insufficient intrinsic gas or insufficient fee.

This mirrors the report's root cause exactly: an unbounded, user-supplied list is walked with non-trivial per-element cost with no upfront bound tied to what the caller pays.

### Impact Explanation
Every full node (validators and RPC/mempool nodes admitting the tx into `CheckTx`) is forced to perform expensive, unpriced cryptographic recovery and state I/O work proportional to the size of the attacker-chosen authorization list, for a transaction the sender may not even be able to pay fees for. A single such transaction submitted network-wide (or repeatedly, since it can be rejected cheaply by the submitter and resubmitted) can degrade block-proposal/validation throughput across the validator set, risking block-time delay, and can be used to degrade public RPC node availability by flooding `CheckTx`.

### Likelihood Explanation
Reachable by any unprivileged user submitting a single EVM `SetCodeTx` (EIP-7702) — no special privileges, governance, or account balance are required, since the costly loop executes before the fee-sufficiency check. The only constraint is the mempool/tx-size limit, which still permits a large number of authorization entries.

### Recommendation
Move (or duplicate) the intrinsic-gas and block-max-gas checks from `BasicDecorator`, and a fee-sufficiency pre-check, ahead of `EVMPreprocessDecorator`'s authorization-association loop, or cap the number of authorizations processed per transaction before doing any signature recovery/state work, so the cost of processing `SetCodeAuthorizations` is always bounded by what the sender has already been shown able to pay for.

### Proof of Concept
1. Craft a `SetCodeTx` with a very large `AuthList` (as many `SetCodeAuthorization` entries as fit within the node's max tx-size limit), each with a distinct random signer key (so each requires a fresh EC recovery) and either an insufficient `Gas` value or a sender with insufficient balance to actually pay for the tx.
2. Submit the transaction via the public JSON-RPC / `CheckTx` endpoint.
3. Observe that `EVMPreprocessDecorator.AnteHandle` → `associateAuthorizationAuthorities` (`x/evm/ante/preprocess.go:122-147`) performs ECDSA recovery and state lookups for every authorization before `BasicDecorator` rejects the tx for insufficient intrinsic gas (`x/evm/ante/basic.go:51-57`) or `EVMFeeCheckDecorator` rejects it for insufficient fee — i.e., the full cost is paid by the node even though the transaction is guaranteed to be rejected.

func (p *EVMPreprocessDecorator) associateAuthorizationAuthorities(ctx sdk.Context, msg *evmtypes.MsgEVMTransaction, associateHelper *helpers.AssociationHelper) {
	txData, err := evmtypes.UnpackTxData(msg.Data)
	if err != nil {
		return
	}
	setCodeTx, ok := txData.(*ethtx.SetCodeTx)
	if !ok {
		// Only SetCode (EIP-7702) transactions carry authorizations.
		return
	}
	ethTx := ethtypes.NewTx(setCodeTx.AsEthereumData())
	for _, auth := range ethTx.SetCodeAuthorizations() {
		// Only pre-associate authorities whose authorization the EVM will actually apply
		// (matching chain id, nonce, and account state). This prevents replaying a
		// publicly-visible authorization a user signed for another chain to force-associate
		// them, which the EVM would skip but which still recovers a valid authority.
		evmAddr, seiAddr, pubkey, ok := helpers.AuthorityToPreAssociate(ctx, p.evmKeeper, auth)
		if !ok {
			continue
		}
		cacheCtx, write := ctx.CacheContext()
		if err := associateHelper.AssociateAddresses(cacheCtx, seiAddr, evmAddr, pubkey, false); err == nil {
			write()
		}
	}
}
