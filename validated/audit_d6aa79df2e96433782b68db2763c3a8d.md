### Title
Webhook shop attribution is derived from an unauthenticated header not covered by the HMAC signature - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#shop_domain` returns the caller-supplied `X-Shopify-Shop-Domain` request header, while `verify_request` validates authenticity of a webhook only over `request.raw_post` via HMAC. The header is never included in the HMAC computation, so the “who is this webhook for” value is unauthenticated and independent from the “is this data authentic” check — the same class of flaw as the referral report, where the caller-supplied identity used as the map key/target is never bound to the party the signature actually authenticates.

### Finding Description
`hmac_valid?` computes the HMAC exclusively over the raw request body: [1](#0-0) 

`verify_request` gates the action solely on that body HMAC: [2](#0-1) 

`shop_domain`, the value the gem's own documentation instructs developers to use as the tenant/shop key for downstream processing, is read straight from the header and is never part of the signed payload: [3](#0-2) 

The officially documented custom-controller pattern passes this unauthenticated value directly into job dispatch as the tenant key: [4](#0-3) 

The generator-produced job templates then use that `shop_domain` to look up and mutate a specific shop's record, e.g. destroying the shop or acting on its session: [5](#0-4) [6](#0-5) 

Because the HMAC only proves the *body bytes* were signed with the app secret at some point (by Shopify, for some installed shop) and never binds that signature to the `X-Shopify-Shop-Domain` header, any party who can obtain one legitimately-signed webhook body/HMAC pair (trivially available to any merchant who installs the app on a shop they control and triggers an event) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary victim shop domain in the header. `verify_request` still passes because the body is unmodified and validly signed; the forged header is then trusted as the shop identity for all downstream processing.

### Impact Explanation
An attacker (any merchant who can install the app on a shop of their own) can force shop-scoped side effects to be attributed to and executed against an unrelated victim shop's record, by replaying a validly-HMAC'd body with a spoofed `X-Shopify-Shop-Domain` header. Depending on which webhook/job is targeted, this enables:
- Cross-shop data corruption/DoS: e.g. `Shop.find_by(shopify_domain: shop_domain).destroy` in the `app/uninstalled` job template being triggered for a victim shop, deleting their stored session/access token and forcing re-authentication.
- Cross-shop redact/processing actions being run against a victim's record using an attacker-controlled body.

This mirrors the report's root cause: a mapping/attribution key that should be tied to the verified identity is instead accepted from an untrusted, unauthenticated field, letting an unprivileged caller set the "target" of a privileged operation.

### Likelihood Explanation
Reachable by an anonymous/unrelated party: anyone can create a development/trial shop, install the target app, and trigger any webhook they choose to capture a valid raw body + HMAC pair, since the app's webhook secret is shared across all shops of that app (it's the app's client secret, not shop-specific). No dependency on leaked secrets, no host-operator access, and no special privilege on the victim shop is required — only the ability to POST directly to the app's public webhook endpoint with a modified header, which any developer app builder using the documented pattern is directly exposed to.

### Recommendation
Do not trust `X-Shopify-Shop-Domain` (or any header) as the authenticated tenant identity. Instead:
- Include the shop domain inside the HMAC-signed payload verification (e.g., derive shop from the JSON body / `ShopifyAPI::Webhooks::Request` parsed body fields that Shopify includes in the signed payload, not from headers), or
- Recompute/verify that the header value is consistent with an independently-trusted source (e.g., cross-check against the shop for which the webhook subscription was registered) before using it to key any database lookup or destructive action.
Update `ShopifyApp::WebhookVerification#shop_domain` and the accompanying documentation/generator templates so the tenant key used for job dispatch is provably bound to the same data covered by the HMAC.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they control) and triggers any subscribed webhook topic (e.g. `app/uninstalled`), capturing the exact `raw_post` body and the `X-Shopify-Hmac-Sha256` header Shopify sends.
2. Attacker replays this exact captured request to the app's custom webhook endpoint (built per `docs/shopify_app/webhooks.md`'s documented pattern using `ShopifyApp::WebhookVerification`), keeping body and HMAC identical but changing the header:
   `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `verify_request` (`lib/shopify_app/controller_concerns/webhook_verification.rb:15-21`) validates the (unchanged) body's HMAC successfully.
4. The controller/job dispatches using `shop_domain` = `victim-shop.myshopify.com` (from the forged header), e.g. `AppUninstalledJob.perform_later(shop_domain: "victim-shop.myshopify.com", ...)`, causing `Shop.find_by(shopify_domain: "victim-shop.myshopify.com").destroy` to run against the victim's stored session/token, even though the signed payload actually corresponded to the attacker's own shop's event.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end

class AppUninstalledJob < ActiveJob::Base
  extend ShopifyAPI::Webhooks::WebhookHandler

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end
end
