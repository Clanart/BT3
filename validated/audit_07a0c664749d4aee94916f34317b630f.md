### Title
Attacker-Controlled `WWW-Authenticate` Header Forces Enterprise-Sign-In Prompt for Arbitrary Git Remote, Enabling OAuth Phishing - (File: app/src/lib/trampoline/trampoline-credential-helper.ts)

### Summary
The credential-helper trampoline classifies a remote's authentication scheme (`getEndpointKind`) partly by trusting a `WWW-Authenticate` header value (`wwwauth[]`) forwarded by Git from the remote server response. A malicious/compromised git remote or a MITM proxy can return `realm="GitHub"` for any HTTP(S) host, forcing GitHub Desktop to treat an arbitrary attacker-controlled host as a GitHub Enterprise endpoint and automatically pop up the native "sign in" (OAuth) flow pointed at that attacker host.

### Finding Description
`getEndpointKind()` in [1](#0-0)  inspects credential-helper stdin fields supplied by Git. Git forwards any `WWW-Authenticate` response header it receives from the remote as `wwwauth[]=...` to the credential helper. The code trusts this value directly:

```
for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } ...
``` [2](#0-1) 

This value originates from the HTTP response of the remote the user is fetching/pushing/cloning from — i.e., attacker-controlled server content, not something Desktop itself validates (e.g., no certificate/known-host check tying the claimed "GitHub" realm to an actual GitHub-owned domain).

When `getEndpointKind` returns `'enterprise'` (or `'github.com'`) and no existing account matches the endpoint, `getCredential()` calls `ui.promptForGitHubSignIn(endpoint)`: [3](#0-2) 

`promptForGitHubSignIn` then calls `dispatcher.beginEnterpriseSignIn(cb)` and `dispatcher.setSignInEndpoint(origin)` using the **attacker's own host** as the enterprise `origin`, then shows the sign-in popup: [4](#0-3) 

That popup, if the user proceeds, drives `SignInStore.authenticateWithBrowser()`, which opens the system browser at `getOAuthAuthorizationURL(endpoint, csrfToken)` — again using the attacker-supplied `endpoint`: [5](#0-4) 

Because the "endpoint" driving the entire enterprise OAuth/PAT flow is derived from data an attacker fully controls (a header on their own HTTP server), the user can be steered into an authentication flow whose destination is the attacker's site while the Desktop UI presents it as a legitimate "GitHub Enterprise sign in" prompt triggered organically by a normal `git fetch`/`clone`/`push` failure — no unusual user action required beyond the ordinary auth retry dialog. This breaks the invariant that only officially known/validated GitHub or GHE endpoints should ever trigger the OAuth sign-in / credential-store flow.

### Impact Explanation
This can be used to phish GitHub Enterprise (or GitHub.com-style) credentials/PATs from users: a repository/remote controlled by an attacker (which the target has innocently added or is fetching from, e.g., via a spoofed corporate GHE mirror or MITM proxy) can force Desktop's normal "authentication failed, please sign in" UX to authenticate against an attacker-chosen origin. Successful phishing yields account takeover/token exfiltration, satisfying the "unauthorized OAuth or account binding" / "credential exfiltration" impact class from a remote/proxy-controlled response — no local access, malware, or leaked credentials required.

### Likelihood Explanation
Likelihood is moderate: it requires the user to already be interacting with an attacker-controlled or MITM'd remote (e.g., cloning from a malicious mirror, or a network-level attacker on an insecure/misconfigured HTTPS connection able to inject the header) and requires the user to actually go through the resulting sign-in prompt. The header-based classification heuristic itself is explicitly acknowledged in the code comment as a "happy-path" without stronger verification, and no origin allow-list or TLS/hostname pinning is applied before triggering the enterprise/GitHub sign-in UI.

### Recommendation
Do not let a raw, remote-supplied `WWW-Authenticate` realm value alone route the flow to the trusted-looking "sign in with GitHub" OAuth path. At minimum: only use the `wwwauth[]` heuristic to *suggest* trying credential lookup, but require an independent verification step (e.g., hitting a known GitHub/GHE API discovery endpoint, matching against user-approved enterprise endpoints, or explicit user confirmation naming the exact host) before opening the OAuth/browser sign-in flow, and always surface the literal endpoint host prominently and unambiguously in the sign-in dialog so users can detect spoofed enterprise domains.

### Proof of Concept
1. Attacker stands up an HTTPS git server at `https://evil.example.com/attacker/repo.git` (or performs a MITM on an insecure clone) configured to respond to Git's HTTP auth challenge with `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim in GitHub Desktop clones/fetches/pushes to that remote. Git invokes the credential helper (`git credential fill`) and forwards the header as `wwwauth[0]=Basic realm="GitHub"` on stdin.
3. `getEndpointKind` in `trampoline-credential-helper.ts` matches `realm="GitHub"` and returns `'enterprise'` for `evil.example.com`.
4. Since no existing account matches `evil.example.com`, `getCredential` calls `ui.promptForGitHubSignIn('https://evil.example.com/...')`.
5. `promptForGitHubSignIn` sets the sign-in endpoint to `https://evil.example.com` and shows the "Sign in to GitHub Enterprise" dialog; on proceeding, `SignInStore.authenticateWithBrowser` opens the OS browser at an OAuth authorize URL built from that attacker host.
6. The victim is now driven through an authentication flow originating at, and controllable by, the attacker's server, disguised as a normal Desktop authentication prompt.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
