Based on the investigation, the strongest analog to the sequencer's "unvalidated/mismanaged attacker-supplied value" bug class in GitHub Desktop is the `filepath` parameter of the `x-github-client://openrepo/...` deep-link handler, which — unlike its sibling parameters `pr` and `branch` — receives no validation before being propagated through the URL-action pipeline.

### Title
Unsanitized `filepath` Parameter From `openrepo://` Deep Link Bypasses Validation Applied to Sibling Parameters - (File: app/src/lib/parse-app-url.ts)

### Summary
`parseAppURL()` parses the `x-github-client://openrepo/...` protocol-handler URL (registered as a default protocol handler on Windows/macOS) into an `IOpenRepositoryFromURLAction`. The `pr` and `branch` query parameters are explicitly validated with a numeric regex and `testForInvalidChars()` respectively before being trusted, but the `filepath` query parameter is extracted with `getQueryStringValue()` and passed straight through to the returned action object with zero sanitization.

### Finding Description [1](#0-0) 

`pr` is checked against `/^\d+$/` and `branch` is checked with `testForInvalidChars()`, but `filepath` has no equivalent guard — it is taken verbatim from the attacker-controlled URL and returned as `filepath` on the action object that is later dispatched via `dispatchURLAction` / `openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts`. Because this deep link is reachable from any external link a user clicks (browser, email, chat client) — Desktop registers itself as the OS handler for the `x-github-client`/`github-mac`/`github-windows` protocols in `app/src/main-process/main.ts` — the `filepath` value is fully attacker-controlled at the point of parsing, with no upstream trust boundary.

### Impact Explanation
This matches the requested attacker primitive: "a link or deep link the user clicks" driving unsanitized data into application logic. If the consumer of `filepath` (the file-open code invoked after cloning, in `dispatcher.ts`) resolves it relative to the newly cloned repository directory without re-validating for `..` traversal sequences, a crafted `openrepo://` link could cause Desktop to open/read a file outside the intended repository directory — satisfying the "file... read outside the repo" impact category from a single user click on an attacker-supplied link.

### Likelihood Explanation
Likelihood is limited by two facts I could not fully verify given the available index: (1) I was unable to read the exact consuming code path in `app/src/ui/dispatcher/dispatcher.ts` that dereferences `filepath` to confirm whether it performs its own path-containment check before use, and (2) confirming whether the eventual sink is a benign "reveal in Explorer/Finder" versus something with a higher-impact outcome (e.g., loading the file's contents into a renderer) requires seeing that call site, which I could not retrieve before the tool budget ended.

### Recommendation
Apply the same defense-in-depth already used for `pr` and `branch`: validate `filepath` in `parseAppURL()` to reject absolute paths, `..` traversal segments, and null bytes, and additionally re-validate/resolve the final path against the cloned repository root (`path.resolve` + prefix check) at the point of consumption in the dispatcher before performing any file-system read or "reveal" operation.

### Proof of Concept
Given the missing validation shown in `app/src/lib/parse-app-url.ts:101-124`, a link such as:
```
x-github-client://openrepo/https://github.com/some/repo?filepath=../../../../etc/passwd
```
would parse successfully into `{ name: 'open-repository-from-url', filepath: '../../../../etc/passwd', ... }` with no rejection, whereas an equally malformed `branch` or `pr` value would be caught and downgraded to `unknown`. I was not able to confirm from the retrieved code whether the downstream consumer in `dispatcher.ts` neutralizes this before use — this would need to be verified by reading the full `openRepositoryFromUrl` implementation, which was not available within my remaining tool budget.

**Confidence caveat:** This finding is based on confirmed lack of input validation at the parsing layer; I could not verify the final sink behavior in `dispatcher.ts` due to running out of tool iterations, so the actual exploitability (read-outside-repo vs. benign no-op) is unconfirmed and should be validated against the live source before treating this as a confirmed vulnerability.
