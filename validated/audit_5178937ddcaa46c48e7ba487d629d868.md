### Title
Reward double-counting in `incentiveDeposit` can be bypassed by draining `mWomSV` balance via `startUnlock` - ([File: wombat/ArbWomUp3.sol])

### Summary
`getRewardAmount`/`calDoubledCounted` in `wombat/ArbWomUp3.sol` compute the "already rewarded" amount by reading `mWomSV.getUserTotalLocked(_account)` live instead of storing a monotonic record of MGP already paid to a user. Because `mWomSV.startUnlock()` immediately reduces `getUserTotalLocked` (moving locked balance into cooldown), a user can repeatedly deposit via `incentiveDeposit(_amount, _convertRatio, _bullMode, 2)`, then call `mWomSV.startUnlock` to lower their tracked locked balance, and re-claim the same reward tier bracket again on the next `incentiveDeposit` call.

### Finding Description
`incentiveDeposit` with `_mode == 2` calls `getRewardAmount(_amount, msg.sender, true)`, which computes a `rewardAmount` for the cumulative bracket `_amountToConvert + mWomSV.getUserTotalLocked(_account)` and subtracts `calDoubledCounted(_account)`: [1](#0-0) 

`calDoubledCounted` recomputes the reward corresponding to `mWomSV.getUserTotalLocked(_account)` at call time — a value with no persisted floor/high-water-mark: [2](#0-1) 

`mWomSV.getUserTotalLocked` is defined as `stakingInfo(this,_user) amount - getUserAmountInCoolDown(_user)`, so it strictly decreases whenever the user calls `mWomSV.startUnlock`, which moves part of the locked balance into a cooldown slot: [3](#0-2) [4](#0-3) 

Exploit flow:
1. Attacker calls `incentiveDeposit(_amount, _convertRatio, false, 2)`. Half of `_amount` is deposited into `mWomSV` via `lockFor`, raising `getUserTotalLocked`. The reward for the new tier bracket is computed, doubled (`rewardToSend * 2` at `ArbWomUp3.sol:96-97`), and locked into `vlMGP` for the attacker.
2. Attacker calls `mWomSV.startUnlock(x)` to push a portion of their `mWomSV` balance into cooldown, which lowers `getUserTotalLocked(attacker)` without requiring the cooldown to finish or unlocking any token.
3. Attacker calls `incentiveDeposit` again with a small `_amount`. Because `calDoubledCounted` now reads a smaller `getUserTotalLocked`, the "already rewarded" amount subtracted is smaller than what was truly already paid, so the same tier bracket reward is recomputed and paid out again (doubled again for `_mode==2`).
4. Steps 2–3 can be repeated (subject to `maxSlot` cooldown slots and `bracketRewarded` being unused/dead state variable, confirmed by the comment `// not in use` at `ArbWomUp3.sol:47`), extracting MGP reward tokens for the same underlying locked-WOM bracket multiple times.

The only backstop is `mgpleft` (contract's own MGP balance) at `ArbWomUp3.sol:127-128`, which caps a single call's payout to the contract's balance but does not prevent repeated draining across multiple transactions until the contract's MGP reserve is exhausted. This breaks the intended invariant that a user's already-rewarded amount is a persisted, monotonic record — instead it is derived from a balance the user fully controls and can lower at will via a normal, permissionless `mWomSV.startUnlock` call.

### Impact Explanation
This allows an unprivileged attacker who deposits WOM (their own market-bought tokens) to claim the vlMGP reward for the same locked-balance bracket multiple times, draining the `ArbWomUp3` contract's MGP reserves disproportionately to the WOM/mWom actually contributed. This is a direct theft of protocol reward funds (MGP), matching a Critical/High impact class (theft of user/protocol funds), since the doubling (`_mode==2`) compounds the amount stolen per iteration.

### Likelihood Explanation
The precondition is trivial: any EOA with WOM tokens can call `incentiveDeposit` and `mWomSV.startUnlock`, both permissionless with no special role required. The attack is fully repeatable within `mWomSV.maxSlot` limits on cooldown slots, and `cancelUnlock` can even be used to un-cooldown funds without waiting, allowing rapid repetition to re-inflate `getUserTotalLocked` for the next legitimate deposit cycle if desired. The only limiting factor is available MGP balance in the `ArbWomUp3` contract, but this simply bounds total loss, not exploitability.

### Recommendation
Store a persisted, monotonically-increasing record per user of the cumulative reward tier basis already paid (e.g. actually use the existing but unused `bracketRewarded` mapping, updating it inside `incentiveDeposit`/`getRewardAmount` after each payout) instead of deriving "already rewarded" from `mWomSV.getUserTotalLocked`, which the user can decrease via `startUnlock`. The reward computation should key off this persisted high-water mark, not a live, user-controllable balance.

### Proof of Concept
Foundry test plan:
1. Deploy `ArbWomUp3`, `mWomSV`, `mWom`, mock `MasterMagpie`, and mock `mgp`/`wom` tokens; fund `ArbWomUp3` with MGP reserves; configure `rewardTier`/`rewardMultiplier` via `setMultiplier`.
2. Attacker acquires WOM tokens and approves `ArbWomUp3`.
3. Call `incentiveDeposit(amount1, ratio, false, 2)`; record `rewardToSend_1` from the `VLMGPRewarded` event and attacker's locked vlMGP amount.
4. Call `mWomSV.startUnlock(partialAmount)` as attacker to reduce `getUserTotalLocked(attacker)`.
5. Call `incentiveDeposit(amount2, ratio, false, 2)` again with a small `amount2`; record `rewardToSend_2`.
6. Assert that `rewardToSend_2` reflects reward for a bracket that overlaps with what was already paid in step 3 (i.e., `calDoubledCounted(attacker)` after step 4 is lower than after step 3, despite no reward being "unclaimed" or "returned"), and assert attacker's cumulative vlMGP reward exceeds what a single monotonic calculation over `amount1+amount2` total locked would yield.
7. Assert `ArbWomUp3`'s MGP balance decreased by more than the amount that should correspond to the true incremental locked-bracket delta, demonstrating a net extraction of protocol MGP funds beyond the intended reward curve.

        uint256 mgpReward = 0;

        return mgpReward > mgpleft ? mgpleft : mgpReward;
