### Title
Stale line-selection indices are silently reapplied to a freshly-fetched diff during partial commit staging, allowing content the user never reviewed to be committed - (File: app/src/lib/git/apply.ts)

### Summary
`applyPatchToIndex` re-fetches the working-directory diff from disk at the moment of staging [1](#0-0)  and then blindly reuses the `WorkingDirectoryFileChange.selection` object — a set of *absolute line indices* the user chose while looking at a possibly older rendering of the diff — to build the patch via `formatPatch(file, diff)` [2](#0-1) . Nothing ties the selection's line indices to the identity/content of the diff that is actually fetched at commit time. This is structurally the same class of bug as the VADER report: a value computed in one context (an index/ratio derived from diff/price snapshot A) is reused as-is in a different context (diff/price snapshot B) whose semantics have changed, producing a silently wrong result.

### Finding Description
`WorkingDirectoryFileChange.selection` (`DiffSelection`) tracks selected/deselected lines purely as a `Set<number>` of "diverging" absolute line indices (`hunk.unifiedDiffStart + lineIndex`) [3](#0-2) . These indices only have meaning relative to the specific `ITextDiff` they were computed against (the diff whose hunks/line offsets were shown to the user in the UI).

When the user commits, `_commitIncludedChanges` collects files with non-`None` selections [4](#0-3)  and calls `createCommit` → `stageFiles` → `applyPatchToIndex` for any partially-selected file [5](#0-4) . Critically, `applyPatchToIndex` does **not** use the diff that is cached in `changesState.selection.diff` (the one the user actually looked at in the Changes/Diff view) — it independently calls `getWorkingDirectoryDiff(repository, file)` again right before formatting the patch [6](#0-5) , then feeds `file.selection` (computed against the old/displayed diff) into `formatPatch(file, diff)` where `diff` is this newly-read diff [7](#0-6) .

The only place the app reconciles selection state against diff changes is `updateChangesWorkingDirectoryDiff`, which runs during background refreshes of the *displayed* diff, and even there it only intersects `divergingLines` with a freshly computed `selectableLines` set — it does not validate that a given index still refers to the same textual content, just that the index is still "includeable" in the new diff [8](#0-7) . This reconciliation is not invoked at all on the commit path in `apply.ts`; `applyPatchToIndex` reads the file from disk fresh and independently, with zero connection to whatever diff (if any) validation happened in the changes state.

Because `git status`/diff generation is asynchronous and the working tree is fully attacker-influenceable by anything that can write into the repo (build tools invoked by npm scripts, a malicious `.git/hooks` entry, editor auto-format-on-save, or any other process/tool acting on the cloned/fetched repository), a file can be modified between the moment the user visually reviews and selects lines in Desktop's diff viewer and the moment they click "Commit". If the underlying line/hunk layout shifts (e.g. lines added/removed above the hunk, or a hunk split/merged), the *same absolute index* in the newly-fetched diff can now correspond to entirely different textual content than what the user selected.

### Impact Explanation
This falls into "silent corruption of what the user commits or pushes." A user could deliberately deselect a hunk (e.g. a secret they don't want committed, or a debug statement) based on the diff shown in the UI, yet — if the file changes on disk in between (via an npm postinstall/build script, editor autosave, file watcher, or other locally-running-but-repo-triggered tooling) — the stale index could end up selecting/including different content than what was reviewed, or omitting content the user believed was included. Because commit staging happens with no re-validation or user-visible warning, the corruption is silent: the commit succeeds, and the diff the user reviewed no longer matches what was actually staged and committed/pushed.

### Likelihood Explanation
The race window is real but narrow: it requires a file write to land between diff rendering (user reviews/selects lines) and the user's click on "Commit," and it requires the resulting diff's hunk layout to shift enough that stale absolute line indices land on different content. Desktop does not re-fetch/lock the diff at commit time to protect against this, and nothing informs the user that the diff has changed since their selection was made when going through the commit flow specifically (only the general "Changes" view refresh path attempts any reconciliation, and that reconciliation is bounds-only, not content-based). Practical triggers include build tooling, git hooks, linters/formatters run by `npm install`/`postinstall` scripts inside a cloned/fetched repo, or any other repo-controlled automation that touches tracked files during a normal workflow — none of which require local/physical access or elevated privileges beyond what a repository/its tooling already has.

### Recommendation
- Before staging (`applyPatchToIndex`/`stageFiles`), use the same diff object the user actually reviewed and validated their selection against (`changesState.selection.diff`), or re-diff and re-validate line-by-line content equality for every previously selected index against the newly-fetched diff before trusting the selection.
- If the newly-fetched diff differs materially (hash/line-content mismatch) from the diff the selection was computed against, refuse to stage/commit that file and surface a clear "the file changed since you reviewed it, please re-review" error rather than silently reapplying stale indices.
- Consider keying `DiffSelection` divergence not just by index but by a content fingerprint of the corresponding line, so a mismatch can be detected deterministically at patch-formatting time (mirroring the C4 recommendation to "run both branches"/perform the conversion in the correct, validated context rather than assuming stale state is still valid).

### Proof of Concept
1. Modify a tracked file with several distinct hunks; open it in Desktop's Changes view so a diff with, e.g., 3 hunks is rendered.
2. In the UI, deselect (uncheck) hunk #2 only (the "sensitive" hunk), leaving hunks #1 and #3 selected. This creates `file.selection` with diverging indices pointing at hunk #2's absolute line range in the *currently rendered* diff.
3. Before clicking "Commit," have some other process (e.g. an npm `postinstall`/build script, a git hook, or an editor auto-formatter watching the file) rewrite the same file such that line offsets shift (e.g., insert new lines above the original hunk #2, or reflow existing hunks) — this is realistic in real projects where `npm install`/build tasks run as part of normal workflows and can be triggered by files fetched from an untrusted remote.
4. Click "Commit." `applyPatchToIndex` calls `getWorkingDirectoryDiff` again [6](#0-5)  and gets a diff whose hunk boundaries have shifted relative to what was shown to the user, but `formatPatch` reuses the old absolute indices from `file.selection` unchanged [9](#0-8) .
5. Inspect the resulting commit: the staged/committed hunks no longer correspond 1:1 to the hunks the user actually reviewed and selected in the UI — content the user meant to exclude can be included (or vice versa) with no warning shown to the user.
