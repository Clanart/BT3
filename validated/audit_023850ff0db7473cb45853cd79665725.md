### Title
Stale in-memory conflict snapshot lets attacker-influenced merge content bypass the "externally resolved" guard in `_applyCopilotConflictResolutions` - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_applyCopilotConflictResolutions` writes Copilot's AI-generated merge-conflict resolutions to disk, but the "is this file still actually conflicted" safety check is evaluated once against a single snapshot of `repositoryStateCache` taken at function entry and then reused, unchanged, for every file in the write loop [1](#0-0) [2](#0-1) . This mirrors the `BathToken._deposit()` pattern in the seed report: a "before" state is captured, an unbounded/attacker-influenced external step happens (there an ERC777 hook, here the long-running Copilot LLM turn and the intervening `await writeFile` calls per file), and the code trusts the stale snapshot instead of re-checking live state at the moment of the state-changing action.

### Finding Description
The guard is intended to prevent Copilot from clobbering a file the user has *already* resolved outside of Desktop while the result dialog was open:
```
// If the user resolved this file externally (e.g. in their editor) while
// the result dialog was open, git status will report it with no remaining
// conflict markers. Overwriting it with Copilot's stored content would
// silently clobber their work, so skip it and let their resolution stand.
``` [3](#0-2) 

But `state` is captured a single time via `this.repositoryStateCache.get(repository)` at the very top of the function [4](#0-3) , and the `for...of` loop that follows performs one `await writeFile(...)` per conflicted file, potentially many files sequentially, without ever re-reading `repositoryStateCache` or live git status between iterations [5](#0-4) . Every file's "already resolved externally" check (`onDiskFile`) is evaluated against that same first snapshot, not the working tree as it exists right before each individual write.

The resolutions being written (`resolution.resolvedContent`) were themselves computed earlier, asynchronously, from conflicted content in the two merging branches — one of which can be entirely attacker-controlled (a malicious contributor's branch/PR that the victim fetches and merges/rebases, feeding attacker-authored conflict text and commit/PR context directly into the Copilot prompt, see `ConflictResolutionSystemPrompt` and `gatherConflictResolutionContext`) [6](#0-5) . Because the LLM turn and the subsequent user "Continue Merge" click can both take an arbitrary amount of time, and because the write loop iterates over multiple files using one stale check, there is a window in which file-level conflict state legitimately changes (e.g., a background refresh, another queued operation, or a second file in the same loop finishing its own git-status-affecting write) without the per-file guard re-validating against it. The result is that Copilot-authored content — content shaped by attacker-supplied branch/commit data — can be written to a file whose on-disk/staged state no longer matches what was verified when the snapshot was taken, silently corrupting what ends up staged and ultimately committed/pushed.

### Impact Explanation
This does not require local/physical access, admin rights, prior malware, or leaked credentials. The corrupted value is the working-tree file content that gets `git add`-ed and later committed [7](#0-6) ; the loop stages every file it wrote without a final live re-verification pass. Since the attacker only needs to be the author of a conflicting branch/PR that the victim merges through the AI-assisted flow, this falls squarely in the "attacker controls a cloned/fetched repository ... result is silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Moderate/low-to-moderate. It requires: (1) the victim to use the "Resolve with Copilot" feature on a merge/rebase/cherry-pick involving multiple conflicted files, (2) the victim to click "Continue Merge" while some file-level status changes occur between the initial snapshot and individual writes, and (3) attacker-controlled branch content that produces the desired resolved text. The existing per-run ownership guard (`ownsCurrentRun`) and the "externally resolved" check show the developers are already defending against a related race, but the fix only guards against the *first* file checked against a single stale snapshot, not against drift across the rest of the loop.

### Recommendation
Re-fetch `repositoryStateCache`/live git status immediately before each individual file write inside the loop (or perform a fresh `getStatus`/conflict check right before `writeFile` for that specific path) instead of reusing one `state` object captured before the loop began. Alternatively, serialize the whole apply operation behind a single atomic "read current status → diff against expected conflicted set → write only files still in that exact state" transaction, analogous to adding a reentrancy/consistency guard around the entire before/after comparison in the original Solidity report.

### Proof of Concept
1. Victim opens a repository and starts a merge/rebase against a branch authored by the attacker (a normal PR from an external contributor) that produces conflicts in several files, including `a.txt` and `b.txt`.
2. Victim clicks "Resolve with Copilot"; the tool gathers context (including attacker-authored commit messages/content) and later returns resolutions for both files. `_applyCopilotConflictResolutions` runs and captures `state` once at the top [4](#0-3) .
3. While the loop is writing `a.txt`, some other repository event legitimately changes the on-disk conflict state of `b.txt` (e.g. it was manually resolved in-editor by the user, or another queued app operation touches it). Because the `onDiskFile` check for `b.txt` still reads from the original stale `state` object, the guard does not detect this and the loop proceeds to `writeFile` for `b.txt`, silently overwriting the resolution the user actually intended and staging it via `git add` in the same pass [8](#0-7) .

Note: I could not fully trace `reassembleResolvedFile`'s hunk-matching implementation within the available tool budget, so I cannot rule out an additional, more directly attacker-triggerable splicing/indexing issue in that function — this should be reviewed separately in a follow-up session with full file access.
