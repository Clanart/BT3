## Analysis

The reported bug class — a contract that can receive native currency but has no way to withdraw it, permanently locking any funds sent to it — has a direct analog in `contracts/src/MultiSender.sol`.

### Title
Overpaid native SEI sent to `MultiSender` is permanently locked - (File: `contracts/src/MultiSender.sol`)

### Summary
`MultiSender.batchTransferEqualAmount` and `MultiSender.batchTransfer` are `payable` functions that only check `msg.value >= totalAmount` rather than requiring exact payment, and the contract has no function to withdraw or refund any excess balance it accumulates.

### Finding Description
Both public entry points accept an arbitrary `msg.value` and only validate a lower bound: [1](#0-0) [2](#0-1) 

Any wei/usei sent above `totalAmount` (the sum distributed to recipients) stays in the contract's balance. There is no `receive()`/`withdraw()` mechanism, no owner sweep function, and no refund-the-excess logic anywhere in the contract — the entire file contains only these two functions.

### Impact Explanation
Any caller who mistakenly (or due to a client bug/race on `amount`/`amounts` vs. `msg.value`) sends more native SEI than the computed `totalAmount` permanently loses the difference: it becomes stuck in the `MultiSender` contract balance with no code path to retrieve it. This is a direct fund-loss/permanent-freezing analog to the "ETH cannot be withdrawn" report class, reachable by any unprivileged EVM transaction sender calling this contract directly.

### Likelihood Explanation
This requires only a normal user error (overestimating `msg.value`) or an integrating dApp computing `msg.value` incorrectly relative to `amount * recipients.length` (or the sum of `amounts`). Because the check uses `>=` instead of `==`, no unusual conditions are needed — any overpayment silently strands funds. Given `MultiSender` is a general-purpose utility contract intended for batch payouts, overpayment is a plausible/likely operational mistake.

### Recommendation
- Change the value checks to require exact payment: `require(msg.value == totalAmount, ...)`.
- Or explicitly refund the excess (`msg.value - totalAmount`) back to `msg.sender` at the end of each function.
- Alternatively, add an owner-only (or sender-only) sweep/withdraw function so any stuck balance can be recovered.

### Proof of Concept
1. Deploy `MultiSender`.
2. Call `batchTransferEqualAmount(recipients, amount)` with `msg.value = amount * recipients.length + 1`.
3. The extra `1` wei (or any larger delta) remains in the contract's balance after execution; there is no function in the contract that can move it back out.
4. Repeat with `batchTransfer` and `msg.value` greater than `sum(amounts)` — same result. [3](#0-2)

// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.0;

contract MultiSender {
  event SendSuccessful(
    address indexed sender,
    address recipient,
    uint256 amount
  );

  function batchTransferEqualAmount(
    address[] calldata recipients,
    uint256 amount
  ) external payable {
    uint256 totalAmount = amount * recipients.length;
    require(msg.value >= totalAmount, "Insufficient amount sent");

    for (uint256 i = 0; i < recipients.length; i++) {
      bool success = payable(recipients[i]).send(amount);
      require(success, "Failed to send Ether");
      emit SendSuccessful(msg.sender, recipients[i], amount);
    }
  }

  function batchTransfer(
    address[] calldata recipients,
    uint256[] calldata amounts
  ) external payable {
    require(
      recipients.length == amounts.length,
      "Recipients and amounts do not match"
    );
    uint256 totalAmount = 0;
    for (uint256 i = 0; i < amounts.length; i++) {
      totalAmount += amounts[i];
    }

    require(msg.value >= totalAmount, "Insufficient amount sent");

    for (uint256 i = 0; i < recipients.length; i++) {
      bool success = payable(recipients[i]).send(amounts[i]);
      require(success, "Failed to send Ether");
      emit SendSuccessful(msg.sender, recipients[i], amounts[i]);
    }
  }
}
