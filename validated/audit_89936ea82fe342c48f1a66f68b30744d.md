### Title
Unauthenticated DKG encryption key substitution enables secret-share recovery - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
An unprivileged party can replay a victim participant’s valid `Commitments<C>` message while replacing the unauthenticated `enc_key` field in `EncryptionKeyMessage<C, Commitments<C>>` with a public key for a scalar they control. The PedPoK verification authenticates the participant, nonce, and polynomial commitments, but not the separately serialized encryption key, so the substituted key is registered for the victim participant. Other participants then encrypt that victim’s DKG shares to the attacker-controlled key, allowing the attacker to recover the victim’s resulting secret share.

### Finding Description
`EncryptionKeyMessage` parses `msg` and `enc_key` as adjacent but otherwise independent fields, with no signature or proof binding `enc_key` to the claimed participant or committed polynomial. [1](#0-0)  `Decryption::register` directly inserts `msg.enc_key` under the externally supplied `participant` index and returns only the inner message for further verification. [2](#0-1) 

The PedPoP proof challenge covers `context`, `participant`, the Schnorr nonce, and `cached_msg`, where `cached_msg` contains only the serialized polynomial commitments. [3](#0-2) [4](#0-3)  During verification, `msg.enc_key` has already been consumed by `register`, and only `msg.sig`, `msg.commitments[0]`, and `msg.cached_msg` are used to verify the proof of knowledge. [5](#0-4) 

After registration, `Encryption::encrypt` selects the recipient’s registered key through `self.decryption.enc_keys[&participant]`. [6](#0-5)  The sender derives the ChaCha20 key from `k * recipient_public_key`, while the party knowing the recipient private scalar can derive the same point as `recipient_private * msg.key`. [7](#0-6) [8](#0-7) 

### Impact Explanation
For a DKG with participant `v`, an attacker supplies the tuple `(v, victim_commitments || attacker_enc_key || victim_pok)`. Because the victim’s proof verifies and `attacker_enc_key = e_a * G` is accepted without authentication, every other participant encrypts `f_i(v)` to `attacker_enc_key`. [5](#0-4) [2](#0-1)  The attacker decrypts each `EncryptedMessage` using `e_a`, recovers every peer’s polynomial evaluation at index `v`, and sums those evaluations to obtain the victim’s final threshold secret share `sum_i f_i(v)`. [9](#0-8)  This is secret-share recovery from only public protocol inputs and a substituted public key, and it also prevents the victim from completing the DKG with the shares intended for it.

### Likelihood Explanation
The attack requires only replaying a broadcast `Commitments<C>` payload and appending an attacker-controlled group element in place of the victim’s `enc_key`; no discrete-log knowledge for the victim key is needed. [10](#0-9)  The substituted object is structurally valid because `EncryptionKeyMessage::read` accepts arbitrary valid point encodings for `enc_key`, and registration accepts the key before the inner commitments proof is checked. [10](#0-9) [2](#0-1)  Any transport path that allows an untrusted party to submit or transform the encoded message assigned to participant `v` exposes this issue.

### Recommendation
Bind the encryption key to the participant identity and commitments before accepting it. The `Commitments` proof transcript should include `enc_key`, or `EncryptionKeyMessage` should contain a separate proof of possession/challenge covering `context || participant || commitments || enc_key`. [3](#0-2)  `Decryption::register` should reject an encryption-key message unless that expanded proof verifies for the claimed participant, rather than storing the field unconditionally. [2](#0-1)

// Attacker-controlled replacement key: enc_key_a = e_a * G.
let e_a = Zeroizing::new(C::random_nonzero_F(&mut rng));
let forged = EncryptionKeyMessage {
  msg: victim_msg.msg.clone(),              // replayed victim commitments/PoK
  enc_key: C::generator() * e_a.deref(),    // attacker key replaces victim key
};

let mut forged_bytes = vec![];
forged.write(&mut forged_bytes).unwrap();

// A receiver associates these untrusted bytes with participant v.
let decoded = EncryptionKeyMessage::<C, Commitments<C>>::read(
  &mut forged_bytes.as_slice(),
  params,
).unwrap();
let mut received = HashMap::new();
received.insert(v, decoded);

// The replayed commitments pass the victim participant's PoK, while
// Decryption::register stores attacker_enc_key under v.
key_machine.generate_secret_shares(&mut rng, received).unwrap();

// Each honest sender now encrypts f_i(v) to attacker_enc_key.
// The attacker computes e_a * msg.key, derives the ChaCha20 key,
// decrypts every share for v, and sums them to recover v's secret share.

The decisive point is that the Schnorr challenge is calculated over `v`, `R`, and the commitments bytes, not over `forged.enc_key`. [11](#0-10)  The later encryption path then uses that same unauthenticated registered key as the recipient ECDH public key. [6](#0-5)

/// Wraps a message with a key to use for encryption in the future.
#[derive(Clone, PartialEq, Eq, Debug, Zeroize)]
pub struct EncryptionKeyMessage<C: Ciphersuite, M: Message> {
  msg: M,
  enc_key: C::G,
}

// Doesn't impl ReadWrite so that doesn't need to be imported
impl<C: Ciphersuite, M: Message> EncryptionKeyMessage<C, M> {
  pub fn read<R: io::Read>(reader: &mut R, params: ThresholdParams) -> io::Result<Self> {
    Ok(Self { msg: M::read(reader, params)?, enc_key: C::read_G(reader)? })
  }

  pub fn write<W: io::Write>(&self, writer: &mut W) -> io::Result<()> {
    self.msg.write(writer)?;
    writer.write_all(self.enc_key.to_bytes().as_ref())
  }

// leaked.
fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {

  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce

  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());

    let mut coefficients = Vec::with_capacity(t);
    let mut commitments = Vec::with_capacity(t);
    let mut cached_msg = vec![];

    for i in 0 .. t {
      // Step 1: Generate t random values to form a polynomial with
      coefficients.push(Zeroizing::new(C::random_nonzero_F(&mut *rng)));
