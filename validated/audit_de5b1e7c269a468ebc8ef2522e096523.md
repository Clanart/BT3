### Title
Duplicate Input Token Escrow Merging Enables Over-Release of Order Funds in Tron `IntentGatewayV2.placeOrder` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron/TVM port of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) is missing the duplicate-input-token and duplicate-output-token rejection checks that exist in the canonical EVM contract (`evm/src/apps/IntentGatewayV2.sol`). Those checks were added specifically as a fix for a documented bug class: "same-chain partial fills over-release repeated input escrow." Because the Tron contract silently merges (`+=`) escrow for repeated input tokens instead of rejecting the order, the same underlying "consolidate-instead-of-validate" flaw described in the external Vault report (merging into an existing bucket bypasses a validation invariant) is reproducible here, and it results in over-release of escrowed input tokens to a solver during same-chain partial fills.

### Finding Description
In the canonical EVM `IntentGatewayV2.placeOrder`, two guards were added to prevent an order from declaring the same token twice:

- Duplicate **output** tokens are rejected via transient-storage tracking: [1](#0-0) 

- Duplicate **input** tokens are rejected explicitly before crediting escrow: [2](#0-1) 

The test suite documents these as regression fixes for a real fund-safety bug: [3](#0-2) [4](#0-3) 

The Tron contract's `placeOrder`, however, has no such checks. It unconditionally accumulates escrow per token with `+=`, for both the predispatch and direct-transfer paths: [5](#0-4) [6](#0-5) 

This is structurally identical to the bug class in the report: an existing/matching entry (here, `_orders[commitment][token]` for a repeated token) is silently merged into rather than validated against, and the invariant that depends on per-leg uniqueness (one input leg maps to one output leg) is broken without the caller ever hitting a revert.

The downstream damage surfaces in `IntrinsicIntents._fillSameChain`, which is shared by the Tron port and computes escrow release per output leg index `i`. On a **full** fill of a leg, it releases the *entire* current balance of `_orders[commitment][token]` for that token, not just leg `i`'s proportional share: [7](#0-6) 

If a user places an order with two input legs of the same token (allowed on Tron because the duplicate-input check is missing), both legs' amounts are merged into a single `_orders[commitment][token]` bucket. A solver who fully fills the output leg corresponding to *either* input leg triggers `escrowedAmount = _orders[commitment][token]`, releasing the **combined** escrow of both legs to that single solver in one fill — the other output leg is left with no matching escrow, so its solver either gets nothing (fund loss to the second filler and no compensation to the user for that leg) or, depending on fill order, the first solver walks away with tokens that were meant to pay a different, later fill. Either way, funds move to the wrong beneficiary/amount, i.e., an over-release of escrowed order funds.

### Impact Explanation
This falls squarely under "stealing or loss of funds" and "transaction manipulation" in the bounty's impact set: escrowed user funds move to an unintended amount/beneficiary as a direct, deterministic consequence of an unprivileged, ordinary user's `placeOrder` call (the order creator themselves can construct this order; no relayer, prover, or admin compromise is required). It is exploitable by any user of the Tron intent gateway deployment and requires no malicious peer assumption.

### Likelihood Explanation
The trigger requires nothing more than crafting an `Order` with two `TokenInfo` entries in `order.inputs` sharing the same `token` — a completely ordinary, permissionless call. Since the main EVM contract needed a dedicated regression test to guard exactly this scenario, and the Tron contract is a near-line-for-line fork that omits the guard, the likelihood of this being reachable in the live Tron deployment is high, contingent only on that Tron contract being deployed/used in production (this could not be independently confirmed from the index; the file's presence under `evm/tron/contracts/apps/` and its parity with the audited EVM contract otherwise strongly suggests it is a shipped chain-specific port).

### Recommendation
Port the same duplicate-token guards from `evm/src/apps/IntentGatewayV2.sol` (lines ~165-189 for output tokens using transient storage or an equivalent Tron-compatible mechanism, and line ~337 for input tokens) into `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, so that an order containing repeated input or output tokens reverts with `InvalidInput()` before any escrow is credited, exactly matching the fixed EVM behavior.

### Proof of Concept
1. On the Tron IntentGatewayV2 deployment, a user calls `placeOrder` with:
   - `order.inputs = [ {token: USDC, amount: 1200}, {token: USDC, amount: 1000} ]`
   - `order.output.assets = [ {token: DAI, amount: 500}, {token: DAI, amount: 1000} ]` (two output legs, each meant to correspond to one input leg)
2. `placeOrder` succeeds (no duplicate-token revert exists), and `_orders[commitment][USDC]` accumulates to `2200` (merged), matching the `+=` accumulation shown in [6](#0-5) .
3. A solver calls `fillOrder` providing exactly `500 DAI` for output leg 0 (a full fill of that leg, since `totalRequired = 500`).
4. In `_fillSameChain`, `amountFilled == totalRequired` for leg 0, so `escrowedAmount = _orders[commitment][USDC]` = the full `2200` merged bucket (see [7](#0-6) ), which is transferred entirely to this solver.
5. A second solver then attempts to fill output leg 1 (`1000 DAI`); `_orders[commitment][USDC]` is now `0`, so the escrow they should receive for delivering `1000 DAI` is gone — they either receive nothing (fund loss) or the transaction's accounting is left inconsistent, and the user's second output leg is effectively paid for by escrow that was already drained to the first solver.

This exact scenario is what the EVM regression test `testRevert_PlaceOrder_DuplicateInputTokens` (comment: "previously merged into one escrow bucket") was written to prevent — that fix was not carried over to the Tron contract.
