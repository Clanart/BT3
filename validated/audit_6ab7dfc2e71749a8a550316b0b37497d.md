### Title
Line-index-based partial commit selection is silently re-applied to a freshly re-fetched diff at staging time, allowing corrupted/unintended content to be committed - ([File: app/src/lib/git/apply.ts])

### Summary
GitHub Desktop lets users stage a subset of lines from a file's diff for a commit (partial/line-level staging). The selection is stored as *line indices* (`DiffSelection`) that were computed against a specific diff snapshot the user reviewed in the UI. When the commit is actually created, `applyPatchToIndex` does **not** reuse that reviewed diff — it independently re-fetches a brand-new diff from disk (`getWorkingDirectoryDiff`) and blindly re-applies the old line-index selection to it via `formatPatch`. If the file's on-disk content changes between the time the user reviewed/selected lines and the time the commit is finalized, the line indices no longer correspond to the same content, and the generated patch can silently include lines the user never selected (or omit lines they did select) — without any error, without any prompt, and without the user being aware.

### Finding Description
The staging pipeline is:

1. UI review: `updateChangesWorkingDirectoryDiff` in `app/src/lib/stores/app-store.ts` (~L3404-3497) loads a diff for the selected file and the user builds a `DiffSelection` (`withRangeSelection`/`withLineSelection`, `app/src/models/diff/diff-selection.ts`) using **absolute line indices** into that diff.
2. Commit: `_commitIncludedChanges` (`app/src/lib/stores/app-store.ts` L3681-3714) reads the current `WorkingDirectoryFileChange` objects (which only carry the `DiffSelection`, not the diff text) and calls `createCommit` → `stageFiles` → `applyPatchToIndex`.
3. `applyPatchToIndex` (`app/src/lib/git/apply.ts` L60) does:
   ```
   const diff = await getWorkingDirectoryDiff(repository, file)
   ...
   const patch = await formatPatch(file, diff)
   ```
   This is a **fresh** `git diff` computed at staging time, not the diff the user actually looked at when making the selection.
4. `formatPatch` (`app/src/lib/patch-formatter.ts` L129-232) walks the *new* diff's hunks and calls `file.selection.isSelected(absoluteIndex)` — reusing the old line indices against the new hunk layout with **no verification** that the diff content/line count/hash matches what the selection was computed against.

Other async flows in the same codebase (e.g. `updateChangesWorkingDirectoryDiff` itself, `updateStatus` in `merge-choose-branch-dialog.tsx`, `_loadChangedFilesForCurrentSelection`) explicitly guard against exactly this kind of staleness by re-checking `selectedFileIDsBeforeLoad`/`selectionBeforeLoad` equality after an `await`. `applyPatchToIndex`/`formatPatch` has no equivalent guard — it never compares the diff used to build the selection against the diff used to build the patch.

### Impact Explanation
If tracked file content changes between the moment the user picks which lines to include (in the Changes view) and the moment they click "Commit" (staging happens then, not earlier), Desktop will silently generate and commit a patch that does not match the diff the user reviewed. This is a **silent corruption of what the user commits** — lines the user explicitly excluded can end up in the commit, or lines they included can be dropped/mangled, without any warning, error, or diff-mismatch detection. Because commit content directly becomes permanent history that may be pushed to a shared remote, this can leak unreviewed content (e.g., secrets, debug code, or lines a reviewer explicitly excluded) or drop intended fixes, and it happens with no attacker interaction visible to the user at commit time.

### Likelihood Explanation
The window is small (between diff-render and clicking Commit) and requires the working tree file to change during that window — this can occur naturally via file watchers/build tools/auto-formatters that are commonly bundled and auto-run from within a cloned repository's own tooling (e.g., `npm run watch`, format-on-save scripts, code generators) — content an attacker distributing a malicious repository can supply, without requiring the user to take any unusual action beyond normal editing/reviewing/committing while such tooling runs, which many projects instruct users to run. Likelihood is Low/Medium: it depends on timing and on the user actually running such tooling, but no privileged access, malware, or leaked credentials are required, and existing guards elsewhere in the same store confirm this class of race was recognized as a real risk that was mitigated in most places — but not here.

### Recommendation
Before generating the patch in `applyPatchToIndex`/`formatPatch`, verify that the diff used to build `file.selection` is still valid against the freshly-fetched diff (e.g., compare a content hash/line count/hunk signature captured when the selection was made, similar to the `selectedFileIDsBeforeLoad`/`selectionBeforeLoad` staleness checks already used elsewhere in `app-store.ts`). If the underlying diff has changed, abort staging that file and force the UI to refresh the diff and require the user to re-confirm the selection before committing, rather than silently applying stale line indices to new content.

### Proof of Concept
Not independently executed (index-based static analysis only); reasoning is based on directly reading the staging pipeline:
1. Open a file with several hunks in Desktop's Changes view and select only some lines/hunks for the commit (leaving others unselected) — this fixes `DiffSelection` against the diff currently rendered.
2. Before clicking "Commit", let an external process modify the same file on disk in a way that shifts or changes line numbers within a hunk (e.g., a build/format script rewriting the file, or simply editing it in another editor) without Desktop re-rendering the diff for that selection.
3. Click "Commit". `applyPatchToIndex` (`app/src/lib/git/apply.ts` L60) fetches a new diff via `getWorkingDirectoryDiff`, and `formatPatch` (`app/src/lib/patch-formatter.ts`) applies the old `DiffSelection`'s absolute line indices to this new hunk layout.
4. Inspect the resulting commit: it will not correspond to the previously reviewed line selection — lines that shifted position may now be included/excluded contrary to the user's original intent, with no warning shown. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })

  // If we get into this state we should never have been called in the first
  // place. Someone gave us a faulty diff and/or faulty selection state.
  if (!patch.length) {
    log.debug(`formatPatch: empty path for ${file.path}`)
    throw new Error(`Could not generate a patch, no changes`)
  }

  patch = formatPatchHeaderForFile(file) + patch

  return patch
}

    })

            onHookProgress: this.onHookProgress(repository),
            onHookFailure: this.onHookFailure(() => (aborted = true)),

                ...state,
                subscribeToCommitOutput,
              }))

            signOff: state.signOffCommits,
            allowEmpty: state.allowEmptyCommit,

        },

/**
 * Stage all the given files by either staging the entire path or by applying
 * a patch.
 *
 * Note that prior to stageFiles the index has been completely reset,
 * the job of this function is to set up the index in such a way that it
 * reflects what the user has selected in the app.
 */
export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
}
