### Title
Arbitrary token drain from `ManualCompound` via unvalidated `_rewards` parameter - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` lets any unprivileged wallet specify an arbitrary `address[][] _rewards` array that is never validated against what `MasterMagpie.multiclaimOnBehalf` actually claimed, and the function then unconditionally sweeps and sends to `msg.sender` the full balance of any address supplied there that isn't in the `compoundableRewards` whitelist.

### Finding Description
`compound()` accepts caller-supplied `_lps` and `_rewards` arrays with no cross-check that `_rewards[i][j]` corresponds to a reward token the pool at `_lps[i]` actually pays, or that the amount transferred came from the claim just performed: [1](#0-0) 

After calling `multiclaimOnBehalf`, the loop does:
```
if (!compoundableRewards[_rewards[i][j]]) {
    uint256 rewardBalance = IERC20(_rewards[i][j]).balanceOf(address(this));
    if (rewardBalance > 0)
        IERC20(_rewards[i][j]).safeTransfer(msg.sender, rewardBalance);
}
```
This transfers the entire on-contract balance of whatever token address the caller names in `_rewards`, as long as that token is not on the `compoundableRewards` whitelist (set only via the owner-only `addReward`) [2](#0-1) . Because the check is purely "is this token whitelisted," not "was this token actually claimed for this `_lps[i]` in this call," an attacker can pass any non-whitelisted ERC20 address (e.g., a token that happens to sit in the `ManualCompound` contract due to residual dust, a stuck reward transfer, or a race with another user's in-flight `compound()` transaction) and drain it to themselves. The contract holds no reentrancy guard around this external-call-heavy function, and `_lps`/`_rewards` are entirely attacker-controlled with no length/consistency validation against the LPs' registered reward tokens.

### Impact Explanation
Any balance of a non-whitelisted ERC20 token sitting in `ManualCompound` (which can arise from partial harvests, leftover dust, or reward tokens claimed but not yet processed by a concurrent transaction) can be stolen outright by an unprivileged caller, constituting direct theft of user/protocol funds held by this contract.

### Likelihood Explanation
This requires the contract to be holding some balance of a token outside the whitelist at the time of the call, which is a realistic operating condition given that `multiclaimOnBehalf` can be invoked with any reward token set and reward tokens are only whitelisted individually via `addReward`. No special privileges are needed by the attacker — a single external call with attacker-chosen `_rewards` is sufficient.

### Recommendation
Do not trust caller-supplied `_rewards` values for balance sweeps. Instead, derive the exact set/amounts of tokens claimed for each `_lps[i]` directly from `MasterMagpie`'s return data (or from a delta of `balanceOf` recorded strictly around the `multiclaimOnBehalf` call), and only forward amounts that are provably part of the current claim, never an unconditional `balanceOf(address(this))` sweep of an attacker-named address.

### Proof of Concept
1. Ensure `ManualCompound` holds a nonzero balance of some ERC20 token `X` that is not registered via `addReward` (e.g., residual dust from a previous partial compound, or a token accidentally sent to the contract).
2. Attacker calls `compound(_lps, _rewards, ...)` with `_lps` set to any valid LP list (can even be an LP the attacker has zero stake in) and `_rewards[i]` containing the address of token `X`.
3. Since `compoundableRewards[X] == false`, the loop at [3](#0-2)  transfers the full `balanceOf(address(this))` of `X` to `msg.sender`, regardless of whether `X` was actually claimed in this transaction.
