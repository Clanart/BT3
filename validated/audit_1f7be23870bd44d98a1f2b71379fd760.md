### Title
Unbounded future-timestamp allowance in `oracle-timestamp-fresh` permanently poisons the monotonic price-feed watermark - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`oracle-timestamp-fresh` treats any oracle timestamp that is ahead of `stacks-block-time` as automatically "fresh" (`delta = u0`) with no upper bound on how far ahead it may be [1](#0-0) . Because the same function also enforces monotonicity (`>= ts prev`), any single price update whose timestamp lands far in the future is accepted and written into the per-feed watermark `last-update`, after which no legitimate, correctly-timed price can ever satisfy `>= ts prev` again [2](#0-1) . This is the same bug class as the referenced GHSA regression: a timestamp/block that is "far ahead" of the expected sequence gets misattributed as valid-and-current, corrupting all subsequent state that depends on strict forward progress.

### Finding Description
`price-resolve` fetches a `{value, timestamp}` pair from Pyth/DIA, applies the callcode transform, then gates it with:
```
(asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness)) ERR-ORACLE-INVARIANT)
(if (> timestamp last-update-time) (map-set last-update key timestamp) false)
``` [2](#0-1) 

`oracle-timestamp-fresh` computes `delta` as `u0` whenever `ts > stacks-block-time`, i.e. it special-cases "the oracle is ahead of the chain" as unconditionally within `max-staleness`, instead of bounding how far ahead `ts` may legally be [1](#0-0) . There is no symmetric check like `(<= (- ts stacks-block-time) max-staleness)` for the future direction — only the past direction is bounded.

Once a single update is accepted with an inflated `ts` (e.g. via upstream clock skew, replay of a delayed batch, or any other path that lets a future-dated publish-time reach `resolve-pyth`/`resolve-dia`), `map-set last-update key timestamp` permanently raises the feed's watermark [3](#0-2) . From that point forward, every subsequent, correctly-timed oracle update has `ts < prev` (the real chain clock has not caught up to the poisoned watermark) and fails `(>= ts prev)`, so `price-resolve` reverts with `ERR-ORACLE-INVARIANT` for that asset indefinitely. This is structurally identical to the "far-ahead attribution" defect: a value that is far ahead of where it should be is accepted as the new baseline, and the monotonic invariant designed to reject regressions instead permanently locks out all correct future data.

### Impact Explanation
Because `price-resolve`/`price-multi-resolve` are on the critical path for every price-dependent market operation (borrow, withdraw, health checks, liquidation) [4](#0-3) , a permanently-reverting price feed for an asset freezes all operations gated on that asset's price. Positions using the frozen asset can no longer be liquidated even if they become undercollateralized (frozen bad debt / insolvency risk), and users cannot withdraw or have accurate health computed for that collateral (permanent freezing of funds). This lands in the **Critical** impact bucket (protocol insolvency / permanent freezing of funds).

### Likelihood Explanation
The trigger only requires one out-of-bound future timestamp to reach `price-resolve` for a given `{type, ident}` feed key — there is no cap on how far ahead of `stacks-block-time` a timestamp may be before it is rejected, so even ordinary clock-skew/latency conditions between the upstream publisher and the Stacks chain are sufficient to eventually poison a feed; no privileged access or third-party data corruption is required to reach the vulnerable comparison, only for the resulting `ts` to exceed `stacks-block-time` at the moment of ingestion.

### Recommendation
Bound the future-timestamp case symmetrically with the past-timestamp case, e.g.:
```
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time) (- ts stacks-block-time) (- stacks-block-time ts))))
    (and (<= delta max-staleness) (>= ts prev))))
```
so that timestamps too far in the future are rejected exactly like timestamps too far in the past, preventing any single update from irrecoverably poisoning the monotonic watermark.

### Proof of Concept
1. A price update for feed `{type, ident}` arrives with `timestamp = stacks-block-time + N` for arbitrarily large `N` (e.g. due to clock drift/latency at the source, or any path that lets an inflated `publish-time` through `resolve-pyth`/`resolve-dia`).
2. `oracle-timestamp-fresh` computes `delta = u0` (future branch), so `(<= delta max-staleness)` is trivially true, and `(>= ts prev)` passes since `ts` is far larger than the current watermark [1](#0-0) .
3. `price-resolve` accepts the price and sets `last-update[{type, ident}] = stacks-block-time + N` [3](#0-2) .
4. Every subsequent honest update has real `ts ≈ stacks-block-time' < stacks-block-time + N = prev`, so `(>= ts prev)` fails and `price-resolve` returns `ERR-ORACLE-INVARIANT` for that asset from then on, freezing all borrow/withdraw/liquidation flows that depend on that asset's price.

**Uncertainty**: I could not fully trace, within the tool budget, the exact upstream conditions under which `resolve-pyth`/`resolve-dia` would forward a `publish-time` sufficiently ahead of `stacks-block-time` to trigger this without relying on a privileged/compromised oracle writer (which would fall outside this scope per the "privileged addresses" exclusion). The root-cause defect — the missing upper bound in `oracle-timestamp-fresh` itself — is confirmed directly in the code, but confidence in a fully non-privileged trigger path is moderate rather than certain.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
```
