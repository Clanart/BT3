### Title
Attacker-supplied serialized `ThresholdKeys` are fully trusted on load — a writable key file yields total, unauthenticated control of the group key and signing context - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes a complete key set — threshold params `(t, n, i)`, interpolation mode, the secret share, and all `n` verification shares — purely from attacker-controllable bytes, and `ThresholdKeys::new` derives the group key directly from the supplied `verification_shares[1..=t]` without any binding to a trusted value (e.g., an expected group key, a digest of a legitimate DKG transcript, or even a consistency check that `C::generator() * secret_share == verification_shares[i]`). This is the exact analog of CVE-2025-49148 (DLL hijacking): a low-privilege party who can write the file/path that a higher-privilege context loads gets arbitrary "code" — here, arbitrary key material — executed as trusted state.

### Finding Description
The load path is: [1](#0-0) 

`read` accepts any `t, n, i` (bounded only by `ThresholdParams::new`), any interpolation variant, any `secret_share`, and `n` canonical points, then calls `ThresholdKeys::new`. Inside `new`: [2](#0-1) 

The group key is `sum(verification_shares[i] * interpolation_factor(i, 1..=t))` — entirely determined by the bytes on disk. Critically:

1. No check that `secret_share` corresponds to `verification_shares[i]` (`generator() * secret_share == verification_shares[&i]` is never tested anywhere in `new`/`read`).
2. No check that the resulting `group_key` matches any externally-anchored value.
3. `Participant::new` only rejects `0`, so `i` can be any index `<= n`.

An attacker fabricates a consistent key set offline (pick a known group secret `x`, derive shares, compute all verification shares and the secret share), serializes it via the public `write`/`serialize` format, and drops it where the victim process reads it — precisely the "writable directory shadowing the real artifact" primitive of the report.

### Impact Explanation
The resulting `ThresholdKeys` produce valid FROST signatures: `sign` uses `view()` built from these shares, `BindingFactor` binds to `self.params.keys.group_key()` which is the attacker's key, and `complete()`'s whole-signature check passes since all shares are mutually consistent. Consequences:

- The victim signs valid signatures under a group key whose **full discrete log the attacker knows** — every output/funds addressed to that group key is immediately spendable by the attacker alone, regardless of `t`/`n`.
- If the victim's existing key blob is overwritten mid-operation, signatures for the *real* group key silently become signatures under the attacker's key, redirecting funds.
- Alternatively, an inconsistent `secret_share` vs. `verification_shares[i]` yields shares that fail `complete()` (the `InternalError` path noted at crypto/frost/src/sign.rs:491-494), a persistent DoS — but the fully-consistent variant above has no such mitigation.

Severity: High — silent, complete control of the threshold identity from a single attacker-writable file.

### Likelihood Explanation
Key blobs are exactly the kind of local state that sits in a service's working/data directory — the same threat model as ClipShare loading `CRYPTBASE.dll` from its install dir. Any lower-privileged process/user able to write that file or the path it's read from (backup restore, config management, shared volume, world-writable dir) triggers it on next load. No cryptographic attack is needed; the attacker computes a valid Shamir sharing themselves. The only prerequisite is file-write access, identical to the report's "can write to the folder containing the binary."

### Recommendation
1. In `ThresholdKeys::new`, verify `C::generator() * secret_share == verification_shares[&i]` and reject otherwise.
2. Bind loaded keys to an authenticated group key: store/require an externally-anchored expected `group_key` (or a hash commitment to the DKG transcript that produced the shares) and compare before constructing `ThresholdKeys` — i.e., do not derive identity solely from the same untrusted file.
3. Treat the serialized blob as untrusted input at rest: integrity-protect it (e.g., MAC/signature over `serialize()` output) or restrict file permissions, so an unprivileged writer cannot substitute it.

### Proof of Concept
1. Attacker picks `x ∈ F` and `t = n = 1` (or any params consistent with the victim's expected `t/n`), computes `group_key = x·G`, sets `verification_shares[1] = x·G`, `secret_share = x`, `i = 1`, `Interpolation::Lagrange`.
2. Serialize with the public `write` format: `C::ID` header, `t/n/i` u16s, interpolation byte `1`, `x` repr, `x·G` encoding.
3. Victim calls `ThresholdKeys::read` on the planted file → returns keys with `group_key = x·G`.
4. Victim's `AlgorithmMachine::sign`/`complete` emits valid FROST signatures under `x·G`; the attacker, knowing `x`, forges/spends unilaterally.

  pub fn read<R: io::Read>(reader: &mut R) -> io::Result<ThresholdKeys<C>> {
    {
      let different = || io::Error::other("deserializing ThresholdKeys for another curve");

      let mut id_len = [0; 4];
      reader.read_exact(&mut id_len)?;
      if u32::try_from(C::ID.len()).unwrap().to_le_bytes() != id_len {
        Err(different())?;
      }

      let mut id = vec![0; C::ID.len()];
      reader.read_exact(&mut id)?;
      if id != C::ID {
        Err(different())?;
      }
    }

    let (t, n, i) = {
      let mut read_u16 = || -> io::Result<u16> {
        let mut value = [0; 2];
        reader.read_exact(&mut value)?;
        Ok(u16::from_le_bytes(value))
      };
      (
        read_u16()?,
        read_u16()?,
        Participant::new(read_u16()?).ok_or(io::Error::other("invalid participant index"))?,
      )
    };

    let mut interpolation = [0];
    reader.read_exact(&mut interpolation)?;
    let interpolation = match interpolation[0] {
      0 => Interpolation::Constant({
        let mut res = Vec::with_capacity(usize::from(n));
        for _ in 0 .. n {
          res.push(C::read_F(reader)?);
        }
        res
      }),
      1 => Interpolation::Lagrange,
      _ => Err(io::Error::other("invalid interpolation method"))?,
    };

    let secret_share = Zeroizing::new(C::read_F(reader)?);

    let mut verification_shares = HashMap::new();
    for l in (1 ..= n).map(Participant) {
      verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
    }

    ThresholdKeys::new(
      ThresholdParams::new(t, n, i).map_err(io::Error::other)?,
      interpolation,
      secret_share,
      verification_shares,
    )
    .map_err(io::Error::other)
  }
