### Title
Forfeited vlMGP-pool reward redistribution lets a large staker partially reclaim its own forfeiture - (`rewards/vlMGPBaseRewarder.sol`)

### Summary
`_sendReward` zeroes `userRewards[_rewardToken][_account]` and forwards the forfeited slice into `_queueNewRewardsWithoutTransfer`, which bumps `rewardPerTokenStored` using `totalStaked()` without excluding `_account`. Because `userRewardPerTokenPaid` for the forfeiting account was snapshotted *before* the requeue increased `rewardPerTokenStored`, the very next `getReward()` call credits the account with its pro-rata share of the reward it just forfeited, lowering its effective forfeiture rate below the nominal percentage.

### Finding Description
`getReward()` is guarded by the `updateReward(_account)` modifier [1](#0-0) , which calls `_updateFor` once, at entry, to set `userRewards[token][account] = _earned(...)` and `userRewardPerTokenPaid[token][account] = rewardPerToken(token)` using the rewardPerToken value **before** this call's forfeiture is processed [2](#0-1) .

The function body then loops over `rewardTokens` and calls `_sendReward`, which computes `forfeitAmount`, sends `toSend` to the receiver, zeroes `userRewards[token][account]`, and requeues `forfeitAmount` via `_queueNewRewardsWithoutTransfer` [3](#0-2) . That requeue increases `rewardInfo.rewardPerTokenStored` by `forfeitAmount * 1e18 / totalStaked()` [4](#0-3) , and `totalStaked()` is simply `vlMGP.totalSupply()` — it does not exclude `_account`'s own balance [5](#0-4) .

Since `userRewardPerTokenPaid[token][account]` was fixed *before* this increase, the account is now "owed" a delta equal to `balanceOf(account) * (new rewardPerTokenStored - old paid) / 1e18`, which materializes on the immediate next `getReward()`/`getRewards()` call (same or later block), crediting the account a `share = balanceOf(account)/totalStaked()` fraction of its own just-forfeited amount. Repeating the harvest-forfeit cycle converges the user's realized loss to `p * (1 - s) / (1 - s*p)` of the original earned amount `E` (where `p` is the forfeiture percent from `_calExpireForfeit` and `s` is the user's stake share), which is strictly less than the nominal `p` whenever `s > 0`. For large `s` (the stated precondition, e.g. 50%), this materially blunts the intended forfeiture penalty.

Nothing in the code path stops this: `getReward` is `onlyMasterMagpie`-gated but not `nonReentrant`, there is no exclusion of `_account` from the redistribution base, and `_calExpireForfeit` is deterministic on-chain state (`vlMGP.getRewardablePercentWAD`) that does not change merely from calling `getReward` twice in short succession, so the same forfeit percentage applies on the reclaimed slice as well — it does not prevent the geometric “leakage” back to the forfeiting staker.

### Impact Explanation
This is a partial theft/dilution of unclaimed yield: reward tokens meant to be forfeited to *other* stakers as a penalty are partially returned to the forfeiting staker itself, reducing the effective penalty rate proportional to the staker's share of `totalStaked()`. This matches the "theft or permanent freezing of unclaimed yield" impact class — other stakers receive a smaller-than-intended share of the redistributed forfeiture pool because part of it round-trips back to the account that was supposed to be penalized.

### Likelihood Explanation
Exploitability requires only that the attacker be a legitimate, unprivileged vlMGP staker who is currently subject to a nonzero forfeiture percentage (`_calExpireForfeit` returns > 0, i.e., `rewardablePercentWAD < 1e18` per `vlMGP.getRewardablePercentWAD`) and that they call `getReward`/`getRewards` (or masterMagpie's harvest wrapper) at least twice in short succession. No special privileges, flash loans, or reentrancy are needed — repeatability and magnitude scale directly with the attacker's share `s` of `totalStaked()`, so it is most impactful for a whale (as the question specifies, ~50% of stake), but even smaller holders leak a proportional amount every harvest cycle. The dependency on `getReward` being callable multiple times through `masterMagpie`'s public harvest entrypoint(s) is the main outstanding question, but this is a call-sequencing detail rather than a barrier requiring privilege.

### Recommendation
Exclude the forfeiting account's own stake from the base used to redistribute its forfeited amount, or snapshot/settle the account's `userRewardPerTokenPaid` again *after* the forfeiture requeue in the same call so the account cannot re-earn against the reward-per-token increase it just caused. A simpler mitigation: route forfeited rewards to a separate pool/rewardPerToken index that only newly-non-forfeiting participants (or a distinct pool) can draw from, or set `userRewardPerTokenPaid[_rewardToken][_account] = rewardPerToken(_rewardToken)` again immediately after `_queueNewRewardsWithoutTransfer` inside `_sendReward`, ensuring the forfeiting account cannot claim against its own just-added redistribution in a later call.

### Proof of Concept
Foundry test outline:
1. Deploy `vlMGPBaseRewarder`, a mock `vlMGP`/`masterMagpie` where `getRewardablePercentWAD` returns a fixed `p` (e.g., 50% forfeiture) for the attacker and 100% (no forfeiture) for other stakers.
2. Set up two stakers: Attacker with `balanceOf = 50%` of `totalStaked()`, Other with the remaining 50%.
3. Queue reward `E` via `queueNewRewards`.
4. Call `getReward(attacker, attacker)` through the mocked `masterMagpie` — assert attacker receives `0.5*E` (nominal 50% forfeiture), and `forfeitAmount = 0.5*E` is requeued, raising `rewardPerTokenStored`.
5. Immediately call `getReward(attacker, attacker)` again (same block) — assert attacker's `userRewards` is now nonzero (`share * forfeitAmount`) and receives an additional `(1-p) * s * forfeitAmount` payout.
6. Repeat several iterations (or compute the closed-form limit) and assert total received by attacker converges to `E*(1-p)/(1-s*p)`, which is strictly greater than the intended `E*(1-p)` — i.e., effective forfeiture `< p*E`, confirming the self-reclaim.

```text
    function _queueNewRewardsWithoutTransfer(uint256 _amountReward, address _rewardToken) internal
    {
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards = rewardInfo.historicalRewards + _amountReward;
        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**vlMGPDecimal) / totalStaked();
        }
        emit ForfeitRewardAdded(_amountReward, _rewardToken);
    }
```

```text
    function _updateFor(address _account) internal {
        uint256 length = rewardTokens.length;
        uint256 userVlMGPAmount = balanceOf(_account);

        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = rewardTokens[index];
            if (userRewardPerTokenPaid[rewardToken][_account] == rewardPerToken(rewardToken))
                continue;

            userRewards[rewardToken][_account] = _earned(_account, rewardToken, userVlMGPAmount);
            userRewardPerTokenPaid[rewardToken][_account] = rewardPerToken(rewardToken);
        }
    }
```

```text
    function _sendReward(address _rewardToken, address _account, address _receiver) internal {
        uint256 forfeitAmount = _calExpireForfeit(_account, userRewards[_rewardToken][_account]);
        uint256 toSend = userRewards[_rewardToken][_account] - forfeitAmount;


        userRewards[_rewardToken][_account] = 0;
            
        if (toSend > 0) {
            IERC20(_rewardToken).safeTransfer(_receiver, toSend);
            emit RewardPaid(_account, _receiver, toSend, _rewardToken);
        }

        if(forfeitAmount > 0)
            _queueNewRewardsWithoutTransfer(forfeitAmount, _rewardToken);
    }
```
