### Title
`SignableTransaction` silently drops the change output after `amortize_fee` already deducted its value — the remainder is burned as miner fee while operating costs are marked recouped - (File: networks/bitcoin/src/wallet/send.rs; processor/src/networks/mod.rs)

### Summary
The Zaros bug is asymmetric accounting: fees were deducted when computing PNL, but never paid out in the positive-PNL branch. The Serai analog is the change-output path in `networks/bitcoin/src/wallet/send.rs` combined with the scheduler's fee amortization in `processor/src/networks/mod.rs`: when `change.is_some()`, the scheduler deducts `tx_fee + operating_costs` from every payment and records the operating costs as fully recouped, but `SignableTransaction::new` only actually creates the change output if the leftover is `>= DUST`. When it isn't, no change output exists, the entire leftover becomes miner fee, and the costs the scheduler believes were "recouped" were in fact burned — value deducted in one branch but never delivered in the other.

### Finding Description
In `processor/src/networks/mod.rs` (lines ~458–546), `amortize_fee` computes `total_fee = tx_fee + operating_costs` whenever a change address is provided, subtracts that total from the user payments, and returns `operating_costs = 0` on the reasoning that "since the change is some, and we successfully amortized, the operating costs were recouped". The resulting reduced payments are then passed to `BSignableTransaction::new` in `processor/src/networks/bitcoin.rs` (`make_signable_transaction`, lines ~446–452) with `change = Some(...)`.

Inside `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:224–235), the change output is conditional:

```rust
if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) {
  if value >= DUST {
    tx_outs.push(TxOut { value: ..., script_pubkey: change });
    needed_fee = fee_with_change;
  }
}
```

If `input_sat - payment_sat - fee_with_change < DUST` (546 sats), `tx_outs` gets no change output, yet the transaction still spends `input_sat` and only outputs `payment_sat`. The actual fee paid (`SignableTransaction::fee()`, lines 137–141, `sum(inputs) - sum(outputs)`) silently becomes `input_sat - payment_sat`, which can be arbitrarily larger than `needed_fee` — up to `needed_fee + DUST - 1` per transaction, plus all the operating costs that had been folded into `total_fee` and marked as recouped.

So the two layers disagree on what was paid: the scheduler charged users for `tx_fee + operating_costs` expecting the leftover to return to Serai via the change output, but the wallet layer dropped that output and handed the leftover to miners. The "recouped" accounting is wrong in exactly the branch where the change output is not created.

### Impact Explanation
- Serai's multisig pays an excess miner fee equal to the would-be change value whenever the change lands below `DUST`, instead of recovering those funds.
- Operating costs accrued from input aggregation and multisig rotations are recorded as fully amortized/recouped (`operating_costs = 0`) while the coins meant to recoup them were burned as fees — Serai eats the loss while still having deducted the cost from users' burn outputs. Either way, funds that accounting treats as received/returned are not actually spendable.
- Reachability: burn/payment amounts are driven by external users (anyone burning `sriBTC` sets `payment` amounts), and anyone can send dust-sized deposits to Serai's scanned addresses, shifting `input_sat`. An unprivileged party can therefore steer `input_sat - payment_sat - fee_with_change` into the `[0, DUST)` window to repeatedly force the silent drop, griefing Serai's fee budget on every withdrawal plan.

### Likelihood Explanation
The trigger is a numeric boundary condition (`0 <= leftover < 546`), not a cryptographic edge case, and the window is reachable because both sides of the subtraction are externally influenceable (input selection from scanned outputs, payment amounts from burns). It does not require a malicious validator, collusion, or leaked keys — only public transactions and crafted amounts. The per-event loss is bounded (~the sub-dust change plus the operating costs folded into that plan), which keeps this at Medium rather than High.

### Recommendation
Make the two layers agree on whether change exists before accounting for it: `SignableTransaction::new` (or a pre-check in `make_signable_transaction`) should return a distinct error/flag when the change output would be dropped (`checked_sub` fails or value `< DUST`), and `amortize_fee` in `processor/src/networks/mod.rs` should only add `operating_costs` to `total_fee` and zero the accrued costs when a change output will actually be created. Alternatively, charge only `tx_fee` against payments and handle sub-dust change by explicitly crediting it as operating-cost recovery rather than letting it become an unbounded fee overpayment.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs::SignableTransaction::new
// inputs = 100_000 sats, payments = [(script, 90_000)], change = Some(..),
// fee_per_vbyte chosen so fee_with_change = 9_900
// -> value = 100_000 - (90_000 + 9_900) = 100 < DUST(546)
// Result: no change output pushed; fee() = 10_000 sats paid to miners,
// while needed_fee = 9_900 - DUST was silently forfeited.
// Upstream (processor/src/networks/mod.rs), operating_costs were already
// added to total_fee and reported as recouped.
```
