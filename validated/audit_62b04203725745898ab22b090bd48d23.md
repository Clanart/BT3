### Title
Schnorr half-aggregation uses deterministic, publicly-computable weights enabling forged aggregate signatures - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` derives the per-signature aggregation weight `z_i` deterministically from a transcript over the verifier-supplied challenges. Because the weights are fully predictable to whoever constructs the aggregate, an attacker can craft `Rs`/`s` that cancel a victim entry (`R_v + c_v·A_v`) against an attacker-controlled entry, producing an aggregate signature that verifies for a public key whose owner never signed.

### Finding Description
In `crypto/schnorr/src/aggregate.rs:139-144`, verification computes

```
Σ_i z_i·R_i + z_i·c_i·A_i − s·G = 0
```

where `z_i = weight(&mut digest)` is drawn sequentially from `DigestTranscript::new(dst)` seeded only with the challenges (`aggregate.rs:132-136`). The same public derivation is used in `SchnorrAggregator::complete` (`aggregate.rs:181-184`), so the weights are known to any party building an aggregate — there is no secret/random weight unknown at forgery time.

Since `s` is a single attacker-supplied scalar and the `R_i` are attacker-supplied points, the attacker can satisfy the linear relation without a valid individual signature. For a victim entry with key `A_v` and challenge `c_v` (which the verifier derives binding `A_v`, `R_v`, and the message), the attacker:

1. Picks arbitrary `R_v = T` for the victim slot (the verifier computes `c_v` over it).
2. Computes the public weights `z_v`, `z_a`.
3. For their own slot with key `A_a` (any key, including `A_a = G·a` they own or even `A_v` with a different message/challenge `c_a`), sets
   `R_a = y·G − (z_v/z_a)·(T + c_v·A_v) − c_a·A_a`
   for arbitrary `y`.
4. Sets `s = z_a·y`.

Then `z_v·T + z_v·c_v·A_v + z_a·R_a + z_a·c_a·A_a = z_a·y·G = s·G`, so `multiexp_vartime(&pairs).is_identity()` holds and `verify` returns `true`, despite no valid signature existing for the victim key.

Note that `BatchVerifier`'s first-weight-is-`ONE` pattern (`crypto/multiexp/src/batch.rs:46-47`) is the analogous mitigation point: batch verification relies on *random* weights precisely because deterministic weights enable cross-statement cancellation; `SchnorrAggregate` lacks that protection by design of `weight()`.

### Impact Explanation
Any consumer that accepts a `SchnorrAggregate` as evidence that each `(key, challenge)` pair was individually signed can be presented a forged aggregate attesting to a signature under an arbitrary victim public key. This is a signature forgery reachable entirely with public inputs (`SchnorrAggregate::read` bytes plus the verifier's own key/challenge list) — an unprivileged party can forge "the victim signed message m" for any key they choose to include in the aggregate.

### Likelihood Explanation
Exploitation requires only that a verifier accepts aggregates containing entries the attacker influenced (i.e., the attacker is one of the aggregated signers or controls the aggregator) and that the verifier computes the victim's challenge over attacker-chosen `R` — the documented API shape. The computation needed is a few field/scalar operations after deriving public weights; no collusion, key leakage, or protocol-level faults are required. Feasibility hinges on the integrator's challenge binding `R_i`; if challenges instead bind the signer's committed nonce externally, the attacker still chooses `R_v` before the challenge is computed in the standard signing flow, keeping the attack viable wherever the aggregate is produced after challenges are known — which is exactly when `SchnorrAggregator` produces it.

### Recommendation
Derive each weight over the full committed aggregate content, not just the challenges: transcript all `R_i` values and all `(key, challenge)` pairs before squeezing `z_i` in both `verify` and `complete`. This makes `z_i` unpredictable at the time `R_i`/`s` are committed... more precisely, it binds the weights to the final `Rs`, preventing the cancellation trick where `R_a` is chosen as a function of `z_v`/`z_a`. Additionally, document that aggregate verification only proves the *sum* relation and that entries must be challenged with weights unknown to signers, or include a per-signature proof of possession.

### Proof of Concept
```rust
// Crypto: ciphersuite C with field F, generator G.
// Verifier's list: [(A_v, c_v_computed_over(R_v, A_v, m_v)), (A_a, c_a)].
// Attacker procedure:
// 1. Choose T = random point; set R_v = T. Verifier derives c_v = H(R_v, A_v, m_v).
// 2. Replay weight() over the challenge sequence to recover z_v, z_a.
// 3. Choose y random; set R_a = y*G - (z_v/z_a)*(T + c_v*A_v) - c_a*A_a.
// 4. Set s = z_a * y. Aggregate = SchnorrAggregate { Rs: [R_v, R_a], s }.
// 5. verify(dst, [(A_v, c_v), (A_a, c_a)]) reduces to
//    z_v*(T + c_v*A_v) + z_a*(R_a + c_a*A_a) - s*G
//      = z_v*(T + c_v*A_v) + z_a*y*G - z_v*(T + c_v*A_v) - z_a*y*G = 0  // accepts
// Forgery: no scalar a_v or valid (R_v, s_v) under A_v was ever used.
```
