Confirmed: there is no dedicated symlink/type-change handling anywhere in the diff or commit UI — `mapStatus` is the only place these codes are interpreted, and it silently downgrades any `T`-containing status code to a generic "modified" file.

### Title
Git type-change status codes (e.g. regular file ↔ symlink) are silently collapsed to "Modified", allowing crafted repositories to hide symlink swaps from the commit UI - (File: `app/src/lib/status-parser.ts`)

### Summary
`git status --porcelain=2` reports file **type changes** (mode 100644 ↔ 120000, i.e. regular file ↔ symlink, or ↔ gitlink) using the status letter `T` (e.g. `.T`, `T.`, `MT`, `TM`, `AT`, `TD`). GitHub Desktop's `parsePorcelainStatus` correctly parses these codes (verified by the existing test `parses a typechange` for `.T`), but `mapStatus` in [1](#0-0) never checks for any `T`-containing code, and every branch from `.M`/`M.` through `UU` enumerates only `M/A/D/R/C/U` combinations [2](#0-1) . Any status code containing `T` falls through to the generic fallback: [3](#0-2) 

This returns `{ kind: 'ordinary', type: 'modified', submoduleStatus }` with **no `index`/`workingTree` fields**, which `convertToAppStatus` then maps to a plain `AppFileStatusKind.Modified` [4](#0-3) , indistinguishable from an ordinary content edit.

### Finding Description
This is the same bug class as the ERC1155 report: the code enumerates a fixed set of known "types" (M/A/D/R/C/U status codes) and silently mishandles anything outside that set instead of explicitly supporting or rejecting it. Here, the missed "type" is a Git type-change (`T`), which specifically represents a file switching between regular file, symlink, and gitlink (submodule) on disk.

Concretely, an attacker who controls a remote/cloned repository can commit a change that converts a previously-plain, trusted-looking tracked file (e.g. `scripts/build.sh`) into a symlink pointing outside the working directory (e.g. `../../../../etc/some-file` or to a sensitive path within the user's home directory), or vice versa converts a tracked symlink into a regular file. When the victim fetches/pulls this and Desktop runs `git status --porcelain=2`, the entry status code will be `.T` (working-tree only) or `MT`/`TM` (index+worktree). `parsePorcelainStatus` extracts this correctly as `IStatusEntry.statusCode = '.T'`/etc. [5](#0-4) , but `mapStatus` drops the type-change semantics entirely and reports it as an ordinary `modified` file [3](#0-2) .

`buildStatusMap` then determines the initial diff-selection using only `AppFileStatusKind` and `submoduleStatus` [6](#0-5) : since a plain type-change has no `submoduleStatus`, it defaults to `DiffSelectionType.All`, i.e. selected for commit by default — same as any normal edit.

Nothing downstream (the changes list, the diff renderer at `app/src/ui/diff/index.tsx`, the commit-message placeholder logic at `app/src/ui/changes/filter-changes-list.tsx`) has any symlink/type-change-aware code path — a grep across the repo for `symlink`/`120000` handling shows only path-sanitization and CLI-installer code, none of it in the status/diff/commit pipeline.

### Impact Explanation
The user sees the file listed as an ordinary "Modified" entry with a normal text/binary diff (or possibly no diff at all if git treats it as a binary-like change), with no indication that the underlying git object type changed. This lets a malicious collaborator/repo:
- Smuggle a symlink into a directory that used to hold a plain file the user trusts and routinely commits/pushes without close inspection, silently corrupting what the user commits (the committed tree entry mode silently flips to `120000` even though the UI only ever said "Modified").
- Conversely, replace a symlink with a regular file surreptitiously, defeating any workflow that relied on the symlink for pointing elsewhere.

This matches the "silent corruption of what the user commits or pushes" impact class explicitly called out as valid.

### Likelihood Explanation
Any attacker who can push a type-changing commit to a branch/PR the victim fetches (an “attacker controls a cloned/fetched repository” scenario) can trigger this with a trivial `git update-index --chmod` / `git rm --cached && ln -s` sequence — no unusual git plumbing or unnatural user action is required, and the victim only needs to run normal Desktop operations (fetch, check status, view changes). The bug is deterministic: every status code containing `T` is affected, not just an edge case.

### Recommendation
Add explicit handling in `mapStatus` for all `T`-containing porcelain v2 status codes (`.T`, `T.`, `MT`, `TM`, `AT`, `TD`, `DT`, `RT`, `TR`, etc.), returning a distinguishable status (e.g. a new `type-changed` `FileEntry` kind or at minimum an `AppFileStatusKind` that the changes list/diff UI can flag explicitly, e.g. "Type changed" with a warning icon), rather than silently coercing to `modified`. The diff renderer should also surface an explicit warning when a file's mode transitions to/from a symlink so the user can inspect it before committing/pushing.

### Proof of Concept
1. Attacker creates/controls a repo with a tracked file `payload.txt` (mode `100644`).
2. Attacker replaces it with a symlink to an out-of-repo path and commits: `git rm --cached payload.txt && ln -sf /etc/passwd payload.txt && git add payload.txt && git commit`.
3. Victim, in GitHub Desktop, fetches/pulls this branch into an existing working copy where `payload.txt` still exists as the old regular file (so `git status --porcelain=2` reports `.T` for a worktree-only type change, or `MT`/`TM` after merge for index+worktree).
4. `parsePorcelainStatus` returns an entry with `statusCode` containing `T` — confirmed reachable via the existing unit test `parses a typechange` [7](#0-6) .
5. `mapStatus` hits the fallback branch and reports the file as ordinary `Modified` [3](#0-2) ; the Changes list shows "Modified", `DiffSelectionType.All` is pre-checked, and the user commits/pushes the symlink without any indication that the file type changed.
