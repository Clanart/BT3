### Title
Attacker-controlled blame recipient crashes PedPoP blame resolution - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`BlameMachine::blame` accepts caller-controlled `sender` and `recipient` participant IDs without validating that `recipient` belongs to the DKG participant set. When an `EncryptionKeyProof` is supplied, `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]`. For a nonexistent participant, this `HashMap` indexing operation panics, producing a repeatable denial of service.

### Finding Description
`BlameMachine::blame` forwards externally supplied participant identifiers to `blame_internal`, which calls `Decryption::decrypt_with_proof` in `crypto/dkg/pedpop/src/lib.rs:575-588`. If `proof` is `Some`, `decrypt_with_proof` verifies the encrypted message signature and then evaluates the DLEq verification arguments. One argument is `self.enc_keys[&decryptor]` in `crypto/dkg/pedpop/src/encryption.rs:388`.

`enc_keys` only contains participants registered during `verify_r1` through `Decryption::register`. `blame` and `blame_internal` do not check that `recipient` is a registered participant before this lookup. `Participant::new` only enforces nonzero, so any participant ID above `n`, including `u16::MAX`, is representable. A caller can provide a validly signed `EncryptedMessage`, an arbitrary parseable `EncryptionKeyProof`, and an unregistered recipient index to force a panic.

### Impact Explanation
This is a remotely triggerable crash if blame processing is exposed as part of DKG fault handling. A single malformed accusation aborts the thread or process handling blame resolution, preventing completion of the DKG and repeatedly crashing retries.

### Likelihood Explanation
The attacker only needs the ability to submit a blame accusation and choose the accused/recipient participant IDs. The encrypted message must have a valid proof-of-possession to pass the initial signature check, but a valid message obtained or generated as a protocol participant is sufficient. The `EncryptionKeyProof` itself does not need to verify because the missing-participant lookup occurs while constructing the DLEq verification input, before `DLEqProof::verify` can reject it.

### Recommendation
Validate `sender` and `recipient` in `BlameMachine::blame` or `blame_internal` before decryption. In particular, return deterministic blame or an error when either participant is absent from `self.commitments`/`self.encryption.enc_keys`. Replacing `self.enc_keys[&decryptor]` with `get` and mapping `None` to a controlled result prevents the panic.

### Proof of Concept
```rust
use dkg_pedpop::Participant;
use std::collections::HashMap;

// `blame_machine` is a KeyMachine::calculate_share result.
// `msg` is a valid EncryptedMessage from `sender`, such as one received during
// the normal secret-share round.
// `proof` is any syntactically valid EncryptionKeyProof, potentially obtained
// through EncryptionKeyProof::read.
let invalid_recipient = Participant::new(u16::MAX).unwrap();

// Participant::new only rejects zero. If invalid_recipient was not registered,
// decrypt_with_proof evaluates `self.enc_keys[&invalid_recipient]` and panics.
let _ = blame_machine.blame(sender, invalid_recipient, msg, Some(proof));
```

The vulnerable sequence is:

```text
BlameMachine::blame
  -> blame_internal
  -> Decryption::decrypt_with_proof
  -> self.enc_keys[&decryptor]
  -> panic on missing participant
```
