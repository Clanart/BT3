## Analysis

The Party contract bug is fundamentally: **a later, authoritative user action can be silently reverted by a stale/attacker-influenced value that a separate code path re-applies without checking that the user has since made an explicit, conflicting choice.** The closest real analog in GitHub Desktop is not credential/SSH-token handling (those are correctly scoped per-operation via `trampoline-tokens.ts`'s per-call UUID and cleaned up in `trampoline-environment.ts`'s `finally` block), but the **automatic remote-URL rewrite driven by GitHub API metadata** in `updateRemoteUrl`.

### Title
Unattended remote URL rewrite trusts attacker-influenced GitHub API `clone_url`, silently redirecting future pushes - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
When Desktop refreshes a repository's associated GitHub metadata, `updateRemoteUrl` compares the locally configured `origin` URL against the previous known API `clone_url`, and if they still match, it silently overwrites the git remote with whatever new `clone_url` the API response now reports — with no user confirmation, similar to how `mint()` blindly re-applied a delegate value without checking whether the owner had since made an explicit, more-recent choice.

### Finding Description
`repositoryWithRefreshedGitHubRepository` periodically re-fetches repository metadata from the API and feeds it straight into `updateRemoteUrl`: [1](#0-0) 

`updateRemoteUrl` then decides whether to rewrite the local remote based solely on whether the *previously cached* `clone_url` still matches the current remote — it does not require the user to have opted in, and does not re-verify the endpoint/host beyond a protocol-scheme comparison: [2](#0-1) 

If the conditions hold, it calls `gitStore.setRemoteURL`, which directly executes `git remote set-url`: [3](#0-2) [4](#0-3) 

The check only guards against the case where the *user* manually edited the remote (via `remoteUrlUnchanged`), and only requires the URL scheme (`http:`/`ssh:`) to match — it does not pin the host/owner identity of the returned `clone_url` to anything the user actually verified. Just like `mint()` assumed the delegate parameter it was handed was authoritative and clobbered the value `delegateVotingPower()` had just set, `updateRemoteUrl` assumes the API-supplied `clone_url` is authoritative and clobbers the git remote without asking the user, based purely on a stale-vs-current URL diff rather than any true attacker-independent validation.

### Impact Explanation
Because the `git remote set-url` happens transparently in the background refresh path, an attacker who can cause the GitHub API (`repos/{owner}/{name}`) to report a different `clone_url` for a repository the victim already has cloned — e.g., by renaming/transferring the repo, or via a compromised/malicious GitHub Enterprise Server endpoint the user is authenticated against — can silently redirect the victim's `origin` remote to an attacker-controlled git host. Subsequent `git push`/`fetch` operations initiated from Desktop's UI (which reads `gitStore.defaultRemote`/`currentRemote`) would then target that attacker host, potentially exfiltrating code, and — depending on credential-helper behavior — leaking Git credentials/tokens for that host. This matches the report's "silent corruption of what the user commits/pushes" impact category.

### Likelihood Explanation
This does not require local/physical access, admin rights, or pre-existing host compromise: the attacker only needs the ability to control a GitHub API object (`clone_url` in the repository response) — e.g., by renaming a repo they control that the victim has cloned, or through a compromised/rogue GHES instance, both of which are within the described "attacker controls a GitHub API object" scope. It is a background operation (`repositoryWithRefreshedGitHubRepository` runs during routine repository refreshes), so no unusual user interaction is required, mirroring the "exotic but plausible" ordering scenario that the C4 judges accepted as Medium severity for the original finding.

### Recommendation
Do not silently rewrite the git remote from background API refreshes. At minimum:
- Require explicit user confirmation before changing `origin`'s URL based on API data (similar to the existing `UpstreamAlreadyExists` dialog pattern for upstream remotes: [5](#0-4) ).
- Validate that the new `clone_url`'s host matches the account's configured endpoint before trusting it, rather than only comparing protocol scheme.
- Track a "last explicitly confirmed by user" timestamp/flag for the remote URL, and never let an automated refresh overwrite a value the user set more recently than the last API-driven update, analogous to the timestamp-based mitigation suggested for the original delegate bug.

### Proof of Concept
1. Victim clones `origin` = `https://github.com/victim-org/example`, so `gitHubRepository.cloneURL` is cached as this URL.
2. Attacker (owner/admin of `victim-org` or operator of a compromised GHES instance) renames/transfers the repo such that `repos/victim-org/example` now returns `clone_url: https://attacker-host.example/victim-org/example` (same protocol scheme).
3. Desktop's periodic refresh invokes `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`; since the user never manually touched the remote, `remoteUrlUnchanged` is `true`, `protocolsMatch` is `true`, and `urlsMatch` is `false`, so the guard is satisfied.
4. `gitStore.setRemoteURL('origin', 'https://attacker-host.example/victim-org/example')` executes silently — see [6](#0-5)  and [7](#0-6) .
5. The victim's next push (or credential-helper based fetch) goes to `attacker-host.example`, without any dialog or confirmation.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```

```typescript
export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
```
