## Title
Untrusted `git worktree list` metadata is matched against trusted repository paths using plain string equality (no symlink/realpath resolution), allowing worktree-identity spoofing during `open-repository` CLI/deep-link handling — (`app/src/ui/dispatcher/dispatcher.ts`, `app/src/lib/repository-matching.ts`, `app/src/lib/git/worktree.ts`)

### Summary
When Desktop handles an `open-repository` CLI action (which is what `x-github-client://openLocalRepo` ultimately dispatches into), it falls back to running `git worktree list --porcelain -z` **inside the user-supplied path** and trusts the paths reported there to decide whether that path is a linked worktree of an already-tracked repository. The comparison used, `matchExistingRepository`, is pure string/path equality with no filesystem canonicalization (no `fs.realpath`, no symlink resolution, only lower-casing on Windows), so a repository that an attacker controls can forge its own `.git/worktrees/*` metadata (or a symlink inside it) to claim a `worktree <path>` entry equal to the path of a repository the user already has tracked in Desktop.

### Finding Description
In `dispatchCLIAction`'s `open-repository` branch: [1](#0-0) 

1. `path` is resolved via `getRepositoryType(action.path)` (top-level working directory if it's a regular repo, otherwise the raw path).
2. `matchExistingRepository(repositories, path)` is tried first — if it fails to find an exact tracked repo, Desktop proceeds to the worktree-sharing fallback.
3. `listWorktrees(path)` executes `git worktree list --porcelain -z` **with the untrusted, attacker-supplied `path` as the working directory**: [2](#0-1) 
The resulting worktree paths are derived entirely from that repository's own `.git`/worktree administrative files (`.git/worktrees/<name>/gitdir`), which are ordinary files under the attacker's repository content and are therefore attacker-controlled.
4. Desktop then checks whether any *already-tracked* repository's `path` matches one of those attacker-reported worktree paths:
```
const sharedCommonDirRepository = repositories.find(
  r => matchExistingRepository(worktrees, r.path) !== undefined
)
```
5. The matching primitive itself performs no canonicalization beyond `Path.normalize` (and case-folding on Win32 only) — no symlink resolution, no verification that the claimed worktree path is actually backed by the same git common directory: [3](#0-2) 
6. If both the opened path (matched among its own worktree listing) and a shared/trusted repository are found, Desktop calls `switchWorktree(sharedCommonDirRepository, worktree)`.

Because step 3 executes `git worktree list` inside a directory fully controlled by the attacker, and step 5/6's matching is naive string equality, an attacker can craft a decoy repository whose worktree metadata falsely claims to share a common `.git` directory with a legitimate, already-tracked repository on the victim's disk (or, per the proof-of-concept idea, uses a symlink so that the *decoy's* listed worktree path resolves post-symlink to a real tracked repository's path). This drives Desktop into the `switchWorktree` code path using attacker-influenced worktree-identity claims rather than a verified filesystem/git relationship.

I was not able to fully read the implementation of `switchWorktree` in this session (only its call sites were confirmed) to state definitively which repository record ends up being mutated/redirected as a result. This is a gap: the exact blast radius (whether Desktop starts treating the decoy directory as a worktree of the trusted repo, or silently reassigns the trusted repo's tracked location) requires reading `switchWorktree`'s body and the `AppStore`/`RepositoriesStore` persistence logic it calls into, and I would flag this for further verification rather than asserting the precise end-state with certainty.

### Impact Explanation
If confirmed, this allows a maliciously crafted local repository (reached via a deep link the user clicks, per the accepted attack surface) to cause Desktop to conflate its identity with an already-trusted repository purely by forging git worktree administrative metadata, bypassing the intended "same underlying repo" invariant that the worktree feature depends on. Depending on `switchWorktree`'s exact effect (not fully verified here), this could result in Desktop performing git operations against, or displaying state for, a different filesystem location than the one the user believes they opened — a repository/path-confusion issue.

### Likelihood Explanation
Requires the user to already have at least one repository tracked in Desktop whose local path the attacker can predict (e.g., a common default clone directory) and to open a decoy directory via `open-repository`/`x-github-client://openLocalRepo`. Moderate likelihood: predicting exact paths on a victim's machine is a nontrivial but not unrealistic step (default GitHub Desktop clone locations are commonly `~/Documents/GitHub/<name>` or similar, sometimes discoverable from public repo names).

### Recommendation
- Do not trust worktree path claims (`git worktree list` output) reported by an unverified/untracked directory when deciding whether it corresponds to an existing tracked repository.
- When matching worktree entries to tracked repositories, verify equivalence via the git common directory (e.g., compare canonicalized `.git` common dir contents/`git rev-parse --git-common-dir` output run independently against both locations) rather than comparing worktree-reported path strings.
- In `matchExistingRepository`, resolve paths with `fs.realpath`/canonicalization before comparison to eliminate symlink-based spoofing.

### Proof of Concept
1. Attacker distributes a folder `decoy/` containing a `.git` directory with forged `worktree`-style administrative metadata such that `git worktree list --porcelain -z` run inside `decoy/` reports:
   - `worktree decoy/` (main entry, matching itself)
   - `worktree /Users/victim/Documents/GitHub/real-trusted-repo` (a symlink placed by the attacker, or a directly forged path string) — a path that matches an already-tracked repository in the victim's Desktop `repositories` list.
2. Victim clicks a link such as `x-github-client://openLocalRepo?path=decoy/`.
3. `dispatchCLIAction` resolves `path = decoy/`, fails the initial `matchExistingRepository` check, then calls `listWorktrees(decoy/)`, which returns the two attacker-forged entries.
4. `sharedCommonDirRepository` resolves to the victim's tracked `real-trusted-repo` because its `path` string-matches one of the forged worktree entries.
5. `switchWorktree(sharedCommonDirRepository, worktree)` is invoked using attacker-controlled worktree-identity data instead of a verified git relationship.

*(Note: full confirmation of the concrete post-`switchWorktree` state change was not completed in this review due to not having read `switchWorktree`'s implementation; this should be verified before treating impact as fully established.)*

export function matchExistingRepository<T extends { readonly path: string }>(
  repos: ReadonlyArray<T>,
  path: string
): T | undefined {
  // Windows is guaranteed to be case-insensitive so we can be a bit less strict
  const normalize = __WIN32__
    ? (p: string) => Path.normalize(p).toLowerCase()
    : (p: string) => Path.normalize(p)

  const needle = normalize(path)
  return repos.find(r => normalize(r.path) === needle)
}
