### Title
`InternalGetEmergencyStopTx` is reachable by any unauthenticated caller when the aggregator runs with the `Noop` interceptor - ([File: core/src/servers.rs])

### Summary
The "Internal"-prefix protection for aggregator RPCs (such as `internal_get_emergency_stop_tx`) is enforced *only* inside the `OnlyAggregatorAndSelf` interceptor variant. That variant is selected exclusively when `config.client_verification == true`; when it is `false`, `create_grpc_server` wires in `Interceptors::Noop`, which passes every request through unconditionally, with no certificate check and no `is_internal` gating at all. In that configuration, `ClementineAggregator::internal_get_emergency_stop_tx` becomes callable by any gRPC client that can reach the aggregator's public port, breaking the caller-authority binding the method's name/design implies.

### Finding Description
Binding claimed: `caller_identity_of(internal_get_emergency_stop_tx) == our_cert` (i.e., only the aggregator's own internal loopback caller, gated behind mutual TLS, may invoke `Internal*` RPCs).

Code path:
- `core/src/servers.rs::create_grpc_server` decides the interceptor purely from `config.client_verification`: [1](#0-0) 
- `Interceptors::Noop` performs no check whatsoever: [2](#0-1) 
- The only place that enforces "Internal*" methods require `leaf_cert == our_cert` is inside `only_aggregator_and_self`, which is never invoked when `Noop` is selected: [3](#0-2) 

There is no secondary, in-handler authorization check independent of the interceptor layer that would re-verify caller identity before `internal_get_emergency_stop_tx` reads the DB-stored, already-signed emergency-stop transaction and returns its bytes. Because `create_aggregator_grpc_server` merely warns ("Client verification is enabled...") when `client_verification` is true but does nothing extra to protect `Internal*` methods when it is false, the entire authorization model for this class of RPCs collapses to a single config flag, and that flag also controls unrelated (external) methods. This is a real, non-test code path: it does not depend on `cfg!(test)` — it is a deployment-configuration branch present in the production `create_grpc_server` function.

Exploit flow: an attacker who is aware of an existing deposit's move-to-vault outpoint calls `InternalGetEmergencyStopTx` against an aggregator instance deployed with `client_verification = false`, receives the fully N-of-N-signed emergency-stop transaction bytes, and can broadcast that transaction directly to the Bitcoin network (the attacker is explicitly permitted to broadcast Bitcoin transactions and pay fees), triggering the emergency-stop path for a deposit before the security council intends it.

### Impact Explanation
If broadcast prematurely, the emergency-stop transaction diverts/locks the move-to-vault UTXO outside of the normal deposit/withdrawal lifecycle, which the security-council mechanism is designed to reserve for genuine emergencies. Forcing this on an otherwise healthy deposit denies the depositor/operator the normal payout path for that UTXO — this maps to the Critical category "a move-to-vault UTXO permanently frozen," and at minimum constitutes "premature disclosure of a protocol commitment" (High), since the council's intended timing and discretion over revealing/broadcasting the tx is bypassed entirely. The attack is repeatable against every deposit for which `insert_signed_emergency_stop_tx_if_not_exists` has populated the DB, and against any aggregator instance run with `client_verification = false`.

### Likelihood Explanation
The precondition is purely a deployment/configuration one: the aggregator operator must have set `client_verification = false` (or otherwise be running an aggregator whose gRPC port applies the `Noop` interceptor). Whether this is the *default* or a commonly-used mode could not be fully confirmed from the code inspected here — I was not able to check the default value of `client_verification` in the config schema/examples before running out of tool iterations, so I cannot state with certainty how likely this configuration is in real deployments. If `client_verification` defaults to or is commonly set to `true` in production, the exploit path in this finding does not apply, and only the (test-gated, out-of-scope) `cfg!(test)` bypass inside `only_aggregator_and_self` would exist, which explicitly does not compile into release builds.

### Recommendation
Do not tie the "Internal*" method authorization to the same flag that gates general TLS client verification. Enforce the "Internal" caller check (`leaf_cert == our_cert`) unconditionally for any RPC whose gRPC method name is prefixed `Internal`, regardless of the `Noop`/`OnlyAggregatorAndSelf` selection, or fail closed (reject) when TLS client identity cannot be established for such methods even if general client verification is disabled for other endpoints.

### Proof of Concept
This could not be fully validated end-to-end within the available tool budget because the default value of `config.client_verification` and the full body of `core/src/rpc/aggregator.rs::internal_get_emergency_stop_tx` were not inspected. A `cargo test` to confirm would need to:
1. Start an aggregator via `create_aggregator_grpc_server`/`create_aggregator_unix_server` with `config.client_verification = false` (forcing `Interceptors::Noop`).
2. Perform a normal deposit flow so `insert_signed_emergency_stop_tx_if_not_exists` populates the DB with a signed emergency-stop tx for a real move-to-vault outpoint.
3. From a plain (no client cert) gRPC client, call `InternalGetEmergencyStopTx` with that deposit's identifier.
4. Assert the response contains the raw signed transaction bytes (assert `caller_identity == our_cert` is NOT enforced, i.e., the call succeeds despite the caller presenting no certificate matching `our_cert`).

Given the residual uncertainty about the default/typical `client_verification` setting, this finding should be treated as **conditionally valid**, contingent on confirming that `client_verification = false` is a supported/realistic production configuration for aggregator deployments.
