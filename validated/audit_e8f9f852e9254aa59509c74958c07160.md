## Analog Found

### Title
Copilot conflict-resolution path equality checks use raw string comparison instead of canonical resolution, allowing silent overwrite of a user's manual conflict fix - (File: app/src/lib/stores/app-store.ts)

### Summary
The Sherlock finding is a missing-equality-invariant bug: `onSponsorWindowOpened` never checks `stake != asset`, so two values that the rest of the contract assumes are distinct can collide, and the code path built for the "different" case silently drops value when they're equal. The Desktop analog is in `_applyCopilotConflictResolutions`, which decides whether to overwrite a conflicted file with an AI-generated resolution by comparing the LLM-returned `resolution.path` against the working-directory file's `path` and against the `manualResolutions` map using plain string equality (`===`, `Map.has`), rather than resolving both to a canonical filesystem identity the way the file-write step does.

### Finding Description
When Copilot proposes a resolution, the model's raw path passes through `normalizeLLMPath` and validation in `parseCopilotConflictResolution`/`validateResolutionPaths`, which only guarantee the string is non-empty, matches the expected file set, and isn't duplicated: [1](#0-0) [2](#0-1) . Nothing in that validation normalizes the string to the same canonical form the working-directory model uses (e.g. separator style, case, `./` prefixes).

Later, when the user clicks "Continue Merge," `_applyCopilotConflictResolutions` decides per file whether to skip writing (because the user manually chose a resolution, or already fixed the conflict outside Desktop) purely via string identity: [3](#0-2) 

The "already resolved externally" guard is explicitly there to prevent clobbering the user's own edits, per the surrounding comment, but it relies on `f.path === resolution.path` — the same class of "assume these are equal, never verify equal" gap `stake != asset` is validating for in the Sherlock report. If the AI-echoed `path` string doesn't exactly match the working-directory path's string form (e.g. due to how `normalizeLLMPath` handles separators/case vs. how the git status parser populates `file.path`, or a model-introduced formatting difference in an unusual file/branch name that an attacker-controlled repository can set up to confuse the LLM), the guard fails open: the file is treated as still-conflicted and Copilot's stale content is written over the user's real resolution at line 7258, then staged and included in the next commit/push.

By contrast, the actual file-write target is computed with a real filesystem-canonicalizing resolver, `resolveWithin`, which normalizes and realpath-resolves both sides before comparing: [4](#0-3) . That rigor is applied for the write-location safety check but not for the "does this resolution still apply / has the user already fixed it" identity check — an inconsistency in how strictly the two logically-equivalent-should-be-checks are validated, mirroring how `settle()` in the original finding checks `stake != asset` in one place but `onSponsorWindowOpened` omits the equivalent check.

### Impact Explanation
If the equality check is bypassed, Desktop silently overwrites content the user already resolved (manually or via their own editor) with Copilot's earlier, possibly stale or conflict-marker-laden suggestion, then stages it with `git add` and lets it flow into the user's commit: [5](#0-4) . This is silent corruption of what the user commits/pushes — the exact impact category called out as valid (no confirmation dialog re-appears; the user believes their own fix was kept).

### Likelihood Explanation
Reaching this requires: (1) a merge/rebase/cherry-pick against a repository an attacker can influence (branch content, file/dir naming, PR/commit descriptions fed into the Copilot prompt) that produces an unusually-formatted path echoed by the model, and (2) the user invoking "Resolve with Copilot" and then editing/fixing that file another way before clicking "Continue Merge." This is a realistic but non-trivial path — it depends on the LLM's non-deterministic path echoing rather than a deterministically attacker-controlled string, so likelihood is moderate rather than high. I was not able to retrieve the exact implementation of `normalizeLLMPath` within the available tool budget to confirm precisely which formatting differences it does or doesn't correct for; this is a gap in my verification and worth confirming directly in the source before treating this as fully proven.

### Recommendation
Compare paths through the same canonicalization used for the write-path safety check (e.g. resolve both `resolution.path` and `file.path` via `resolveWithin`/`normalize` before equality checks), or normalize all paths to one canonical separator/case form immediately after parsing the Copilot response and before any subsequent `===`/`Map.has` comparison in `_applyCopilotConflictResolutions`.

### Proof of Concept
1. Trigger a merge/rebase with a conflicting file whose repository-relative path, when echoed back through the LLM in `parseCopilotConflictResolution`, is normalized differently than the string `file.path` uses in the working-directory status list (e.g. differing separator or case after `normalizeLLMPath`).
2. Run "Resolve with Copilot," then externally resolve that same file outside Desktop (removing conflict markers) before clicking "Continue Merge."
3. Because `onDiskFile !== undefined && ... f.path === resolution.path` fails to match due to the string-format mismatch (see guard at [6](#0-5) ), the "already resolved" skip is not taken.
4. `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` at [7](#0-6)  silently overwrites the user's externally-applied fix, and the stale/Copilot content is staged and committed.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
