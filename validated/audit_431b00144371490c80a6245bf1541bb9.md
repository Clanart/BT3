### Title
Non-CEI escrow decrement in Tron `IntentGatewayV2.withdraw` reintroduces the fixed reentrancy pattern - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The mainline EVM intents contracts (`evm/src/apps/intentsv2/IntentsBase.sol`) were patched against a reentrancy class where a malicious beneficiary's native-token `receive()` (or hooked-token callback) could re-enter escrow-paying code before escrow debt was decremented, stealing multi-output/fee escrow. The fix applies checks-effects-interactions: `_filled[commitment]` and `_orders[commitment][token] = escrowed - amount` are both written *before* the external `.call`/`safeTransfer`, as documented and regression-tested in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`. The Tron port of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, still contains the pre-fix ordering in its `withdraw()` function: the escrow decrement `_orders[body.commitment][token] -= amount;` executes *after* the external `.call` that pays out `amount`, for every token in the loop.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` (lines 682-721): [1](#0-0) 

sets `_filled[body.commitment] = beneficiary;` up front, but the per-token loop only guards `_orders[body.commitment][token] == 0` (existence, not amount-accuracy) before performing the payout, and defers the escrow-debt reduction to *after* the transfer:
```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    ...
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    ...
}
_orders[body.commitment][token] -= amount;   // <-- state updated AFTER external call
```

This is the exact ordering the team fixed elsewhere. Compare to `evm/src/apps/intentsv2/IntentsBase.sol`: [2](#0-1) 
which computes `_orders[body.commitment][token] = escrowed - amount;` *before* the `.call`/`safeTransfer`, and the regression suite in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol` explicitly documents that the pre-fix version ("`_filled` was set only inside `_withdraw(finalize=true)`... a malicious beneficiary could re-enter and steal the escrowed tx fees") was exploitable and is now blocked by CEI ordering: [3](#0-2) 

The Tron `withdraw()` did not receive this fix: the escrow ledger (`_orders[commitment][token]`) for the *token currently being paid* is still live/unreduced during the external call the attacker (as `beneficiary`) controls when `token == address(0)` (native TRX/ETH-style call) or when the token itself invokes a callback on transfer.

### Impact Explanation
If reachable, this allows the escrow beneficiary to re-enter before its own debt entry is decremented, enabling double-payout of a single escrowed amount (direct fund loss from the gateway's custody, i.e. the exact bug class the AntePool report describes: state mutated to reflect settlement *after*, not *before/atomically with*, the fund-moving external call). This maps directly to the bounty's "stealing or loss of funds" / "double-settlement" categories for bridge custody in `IntentGatewayV2`.

### Likelihood Explanation
I could not fully confirm a complete unprivileged end-to-end trigger within the remaining investigation budget. `withdraw()` is only reachable via `onAccept()`, which is `onlyHost`-gated, and `EvmHost.dispatchIncoming` records `_requestReceipts[commitment] = relayer` (replay protection) *before* invoking the app callback, while `HandlerV2.handlePostRequests` also rejects duplicate leaves before dispatch — both of which would need to be bypassed to re-enter `onAccept`/`withdraw` for the same request from outside. I was not able to verify (within the tool budget) whether the Tron variant has an alternate same-chain fill/withdraw path that calls `withdraw()` directly from a user-reachable entrypoint (as `IntrinsicIntents._fillSameChain` does on the mainline EVM side, which is exactly what made the original bug exploitable there). Given the mainline contract's identical code shape *was* proven exploitable via a directly-reachable same-chain fill path, and the Tron file is structured as a near-verbatim port, the likelihood that an equivalent unprivileged trigger exists is significant, but this needs confirmation against the full Tron contract (particularly its fill/cancel functions) before treating it as fully proven.

### Recommendation
Apply the same CEI fix used in `evm/src/apps/intentsv2/IntentsBase.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw()`: compute and write `_orders[body.commitment][token] -= amount` (or `= escrowed - amount`) immediately after reading `escrowed` and before performing the native/ERC20 transfer for that token, and audit any other Tron-specific fund-movement function for the same pre/post-fix ordering. Add a Tron-specific reentrancy regression test mirroring `IntrinsicIntentsReentrancyTest.sol`.

### Proof of Concept
Conceptual (requires confirming a user-reachable path into `withdraw`, analogous to the mainline `_fillSameChain` path that the existing PoC in `IntrinsicIntentsReentrancyTest.sol` targets):
1. Attacker places/receives an order such that `beneficiary` = an attacker-controlled contract and `order.inputs`/escrow includes a native-token (`address(0)`) entry.
2. When escrow is released/refunded and `withdraw()` executes, the `.call{value: amount}("")` to the attacker's `receive()` fires while `_orders[commitment][address(0)]` is still un-decremented.
3. If any user-reachable function that reads/mutates `_orders[commitment][...]` for the same commitment can be invoked from that `receive()` callback (the exact condition that made the mainline pre-fix bug exploitable via `_fillSameChain`), the attacker drains the escrow twice before the single decrement finally applies.
4. This mirrors `IntrinsicIntentsReentrancyTest.sol`'s `testReentrancy_FeeTheft` / `testReentrancy_EscrowTheft_MultiOutput`, which should be ported to the Tron contract to confirm/deny exploitability precisely.
