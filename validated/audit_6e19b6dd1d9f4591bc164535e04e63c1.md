### Title
Excessive Authority Permissions in ERC20 and FeeMarket Modules - ([File: x/erc20/keeper/msg_server.go](x/erc20/keeper/msg_server.go), [File: x/feemarket/keeper/msg_server.go](x/feemarket/keeper/msg_server.go))

### Summary
The `x/erc20` and `x/feemarket` modules exhibit a lack of segregation of duties by granting the `authority` address (typically the governance module account) the power to unilaterally update critical system parameters, register token pairs, and toggle conversions without proper checks or time-locks. Specifically, the `authority` can bypass permissionless registration settings in the `x/erc20` module and manipulate the `feemarket` parameters, which can lead to accounting corruption or unauthorized extraction of value if the governance account is compromised or misused.

### Finding Description
In the `x/erc20` module, the `RegisterERC20` and `ToggleConversion` methods are protected by a `validateAuthority` check that ensures the caller is the module's `authority`. [1](#0-0) [2](#0-1)  While this is intended for governance, the `authority` address has the power to register any ERC20 contract as a token pair, even if `PermissionlessRegistration` is disabled. [3](#0-2)  This allows the `authority` to create native Cosmos coin representations for arbitrary ERC20 tokens, which can then be minted or burned via the `ConvertERC20` and `ConvertCoin` flows. [4](#0-3) [5](#0-4) 

Similarly, the `x/feemarket` module allows the `authority` to update all parameters, including the `BaseFee` and `MinGasMultiplier`, which are critical for the EIP-1559 gas pricing logic and preventing BaseFee manipulation. [6](#0-5) [7](#0-6) 

The excessive permissions of the `authority` address mirror the "excessive owner permissions" described in the external report, where a single powerful actor can bypass standard contract system enforcements.

### Impact Explanation
The impact is critical because an authorized but malicious or compromised `authority` account can:
1. **Unauthorized Minting/Burning**: By registering a malicious ERC20 contract via `RegisterERC20`, the `authority` can trigger the minting of native Cosmos coins that have no real value backing, corrupting the chain's accounting. [8](#0-7) 
2. **Chain Halt/AppHash Divergence**: Manipulation of `feemarket` parameters like `BaseFee` can lead to non-deterministic gas calculations or intentional chain halts by setting impossible fee requirements. [9](#0-8) 
3. **Theft of Funds**: If the `authority` toggles conversion for a legitimate token pair at a critical moment, it could freeze user funds or facilitate unauthorized extraction during conversion flows. [10](#0-9) 

### Likelihood Explanation
The likelihood is low as it requires control over the governance module account (the `authority`). However, the lack of segregation and the "out-of-band" nature of these permissions make the system vulnerable to governance-level exploits or administrative errors, which is the exact bug class identified in the seed report.

### Recommendation
1. **Segregation of Duties**: Introduce separate roles for token registration, parameter updates, and emergency halts.
2. **Time-locks**: Implement a mandatory time-lock for any state-changing operations performed by the `authority`.
3. **Multi-sig/Governance Enforcement**: Ensure that the `authority` is always a decentralized governance body or a highly secure multi-sig contract, and explicitly document the capabilities of this address to manage user expectations.
4. **Refine Modifiers**: Use more descriptive modifiers than a generic `authority` check to clearly depict "who can do what" in the system.

### Proof of Concept
1. An attacker gains control of the address designated as `authority` in the `x/erc20` module.
2. The attacker calls `MsgRegisterERC20` with a malicious ERC20 contract address. [11](#0-10) 
3. The module registers the pair and creates a new native Cosmos coin denom. [12](#0-11) 
4. The attacker then uses `MsgConvertERC20` to "convert" malicious ERC20 tokens (which they can mint at will in their contract) into real native Cosmos coins. [4](#0-3) 
5. The chain's total supply of native value is now corrupted by the unbacked coins.

func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
}
