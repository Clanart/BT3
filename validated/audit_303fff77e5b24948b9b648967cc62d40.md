### Title
Excess native-token payment in `EvmHost.dispatch()` is swept to the host contract instead of the caller, permanently trapping user funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
The seed report flags a broken invariant: value that cannot be attributed to a specific beneficiary is left stranded in a contract with no accounting for who owns it and no path to recover it. The same broken invariant exists in `EvmHost.dispatch(DispatchPost)`, where any native-token overpayment above the exact swap requirement is not returned to the caller who sent it, but is captured by the Uniswap router's own refund-to-`msg.sender` behavior — and the router's `msg.sender` here is the `EvmHost` contract itself, not the original payer.

### Finding Description
`EvmHost.dispatch()` accepts payment for cross-chain message fees either in the fee token directly, or in native ETH which it swaps to the fee token via Uniswap V2: [1](#0-0) 

When `msg.value > 0`, it calls `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. Per the standard UniswapV2Router02 implementation, `swapETHForExactTokens` computes the exact ETH input required to produce `post.fee` output tokens and **refunds any leftover ETH back to `msg.sender` of the router call** — which, since `EvmHost` itself calls the router, is `address(EvmHost)`, not the account or contract that originally called `EvmHost.dispatch()` (`_msgSender()`, captured as `post.payer`/`request.from`).

There is no logic afterward that:
- computes the leftover ETH balance received back from the swap, or
- forwards/refunds that leftover ETH to `post.payer` / `_msgSender()`.

The result is that any native-token overpayment beyond the exact fee requirement is retained by the `EvmHost` contract as un-attributed ETH. Unlike the fee-token bookkeeping (`_requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee})`), which precisely tracks who paid and how much for later relayer-fee refunds on timeout, no equivalent tracking exists for the native-token overpayment path. This mirrors exactly the seed bug class: tokens end up custodied by a contract with no documented owner and no transfer mechanism back to the rightful party — here, real user funds, not a governance-controlled remainder.

### Impact Explanation
Any user or application contract (e.g. `IntentGatewayV2`, which calls `IDispatcher(hostAddr).dispatch{value: msg.value}(request)` when the caller supplies native value) that overestimates the ETH needed to cover the swap will have the difference permanently stuck in `EvmHost`, unrecoverable by the payer. Because `dispatch()` is a public entry point reachable by any account/app without special privilege, this is a direct, unprivileged path to loss of user funds — matching the bounty's "stealing or loss of funds" category. There is no sweep/withdraw function surfaced in the reviewed portion of `EvmHost.sol` for this stranded ETH tied back to depositors, so the funds are effectively locked forever (or only recoverable through a privileged/undocumented mechanism, if any exists at all).

### Likelihood Explanation
Likelihood is high in practice: exact fee quoting against a live Uniswap pool is imprecise (price can move between quote and execution), so callers naturally attach a safety margin of ETH to `dispatch()` calls to avoid reverting on `INSUFFICIENT_INPUT_AMOUNT`-type failures during volatile periods. Every such safety margin is silently lost. No malicious relayer, prover, admin, or governance actor is required — a normal, unprivileged user or integrating app triggers the loss simply by sending slightly more ETH than the exact swap needs.

### Recommendation
After the `swapETHForExactTokens` call, capture the actual ETH refunded to `address(this)` (e.g., via balance-before/balance-after delta or `address(this).balance` reconciliation) and forward it back to `_msgSender()` (or `post.payer`) within the same transaction. Alternatively, quote/compute the exact required `amountIn` off-chain and require `msg.value == amountIn`, reverting on any excess, so no unspent value is ever transferred to the router. Document explicitly who owns any residual native balance the host contract does hold, and ensure it is always reachable through a defined transfer path.

### Proof of Concept
1. Attacker/user (or an app such as `IntentGatewayV2`) calls `EvmHost.dispatch(post)` with `msg.value` set higher than the ETH actually required to purchase `post.fee` fee-tokens at current pool price (a normal slippage buffer, e.g. +5-10%).
2. Inside `dispatch()`, `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` executes: it pulls only the ETH needed to buy exactly `post.fee` tokens and refunds the remainder ETH to its caller, `EvmHost`.
3. `EvmHost.dispatch()` has no code path that reads this returned/refunded ETH and forwards it to `_msgSender()`; execution proceeds directly to constructing the `PostRequest` and emitting `PostRequestEvent`.
4. The leftover ETH remains in `EvmHost`'s balance permanently, with no corresponding entry in `_requestCommitments` or any other storage tying it back to the original payer, and no function found in the reviewed `EvmHost.sol` to withdraw it back to that payer.
