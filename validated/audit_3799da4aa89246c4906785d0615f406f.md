### Title
Attacker-controlled `n` in `ThresholdKeys::read` triggers disproportionate memory allocation and point-decompression work, crashing the host process - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes a serialized threshold key set by first reading attacker-controlled `t`, `n`, and `i` as raw `u16`s, then immediately allocating `Vec::with_capacity(n)` (for `Interpolation::Constant`) and looping `n` times calling `C::read_G` to decompress full group elements — all before any semantic validation occurs in `ThresholdKeys::new`. A roughly 10-byte input therefore forces allocation of up to 65,535 field elements plus up to 65,535 point decompression operations, analogous to the polkit file-descriptor exhaustion flaw (CVE-2021-4115): an unprivileged party supplying untrusted bytes causes resource exhaustion and process termination.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` reads `t`, `n`, `i` directly from the stream with no bound other than `u16` width:

```rust
// crypto/dkg/src/lib.rs:591-602
let (t, n, i) = {
  let mut read_u16 = || -> io::Result<u16> {
    let mut value = [0; 2];
    reader.read_exact(&mut value)?;
    Ok(u16::from_le_bytes(value))
  };
  (
    read_u16()?,
    read_u16()?,
    Participant::new(read_u16()?).ok_or(io::Error::other("invalid participant index"))?,
  )
};
```

If the interpolation tag is `0` (`Constant`), it allocates `Vec::with_capacity(usize::from(n))` and reads `n` scalars; unconditionally it then loops `1..=n` performing `read_G` per index into a `HashMap`:

```rust
// crypto/dkg/src/lib.rs:604-623
let mut interpolation = [0];
reader.read_exact(&mut interpolation)?;
let interpolation = match interpolation[0] {
  0 => Interpolation::Constant({
    let mut res = Vec::with_capacity(usize::from(n));
    for _ in 0 .. n {
      res.push(C::read_F(reader)?);
    }
    res
  }),
  1 => Interpolation::Lagrange,
  _ => Err(io::Error::other("invalid interpolation method"))?,
};

let secret_share = Zeroizing::new(C::read_F(reader)?);

let mut verification_shares = HashMap::new();
for l in (1 ..= n).map(Participant) {
  verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
}
```

Only after all of this work is `ThresholdParams::new(t, n, i)` / `ThresholdKeys::new` invoked, which is where `t <= n` sanity would be checked — far too late. When `read` is fed an infinite/large source (a network stream), a peer keeps sending point encodings and the loop performs 65,535 decompressions; even on truncated input, the `Vec::with_capacity(n)` allocation (~2 MB of scalars) and the HashMap growth happen before the reader hits EOF. With a streaming reader there is no EOF bound at all — allocation and CPU scale linearly with bytes the attacker is willing to send, because `read_G` keeps succeeding until the stream ends.

### Impact Explanation
This is the Serai equivalent of the polkit fd-exhaustion crash: a caller that deserializes `ThresholdKeys` from untrusted bytes (the documented `ThresholdKeys::read` surface) can be driven to (a) allocate megabytes per sub-10-byte message, (b) burn 65,535 curve-point decompressions per message, and (c) with a non-terminating reader, consume memory/CPU proportional to attacker bandwidth with no protocol-level bound. Repeated messages cause memory exhaustion and process abort (OOM kill or `Vec` allocation panic), taking down the signing/key-management component — an availability failure identical in class to CVE-2021-4115.

### Likelihood Explanation
The function is `pub` and documented as the deserialization entry point for keys; any component that accepts a serialized `ThresholdKeys` blob over an untrusted channel (or iterates over a sequence of them) is exposed. Triggering requires only writing `0x00` interpolation tag plus `n = 0xFFFF` — no valid shares, proof, or signature needed, since allocation/looping precede all validation.

### Recommendation
Validate `t`, `n` (`t <= n`, `n <= u16::MAX` but also a sane upper bound) via `ThresholdParams::new` immediately after reading the header, before any allocation. Read `Constant` coefficients and verification shares into structures built without pre-sizing from the attacker-controlled `n` (or cap `with_capacity` to a small constant), and error out early if the reader cannot supply the expected bytes. Alternatively, prefix serialized keys with a total byte length so `read` can bound input before allocating.
