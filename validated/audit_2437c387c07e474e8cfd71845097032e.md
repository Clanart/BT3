### Title
Missing `chainId` in EIP-712 Domain Allows Cross-Network Replay of Withdrawal Authorization Signatures — (`core/src/rpc/ecdsa_verification_sig.rs`)

### Summary

The `CLEMENTINE_EIP712_DOMAIN` used to sign and verify `OperatorWithdrawalMessage` and `OptimisticPayoutMessage` authorization signatures omits the `chainId` field. Because the domain separator is network-agnostic, a valid `verification_signature` obtained on one Bitcoin/Citrea network (e.g., testnet4 or signet) can be replayed verbatim on any other network (e.g., mainnet) to bypass the aggregator-authorization gate that guards both the operator payout path and the verifier optimistic-payout co-signing path.

---

### Finding Description

`CLEMENTINE_EIP712_DOMAIN` is defined as:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

EIP-712 specifies that the domain separator **should** include `chainId` to prevent cross-chain replay. The field is intentionally absent here. Both message structs that use this domain are identical in layout and contain no network-binding field of their own:

```rust
struct OptimisticPayoutMessage { uint32 withdrawal_id; bytes input_signature; bytes32 input_outpoint_txid; uint32 input_outpoint_vout; bytes output_script_pubkey; uint64 output_amount; }
struct OperatorWithdrawalMessage { /* identical fields */ }
``` [2](#0-1) 

The signing hash is computed and the recovered address is compared to `aggregator_verification_address` in two production code paths:

**Path 1 — Operator withdrawal** (`ClementineOperator::withdraw`):

```rust
if let Some(address_in_config) = self.operator.config.aggregator_verification_address {
    ...
    let address_from_sig =
        recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>(...)?;
    if address_from_sig != address_in_config {
        return Err(BridgeError::InvalidECDSAVerificationSignature).map_to_status();
    }
}
``` [3](#0-2) 

**Path 2 — Verifier optimistic-payout co-signing** (`Verifier::sign_optimistic_payout`):

```rust
if let Some(address_in_config) = self.config.aggregator_verification_address {
    if let Some(verification_signature) = verification_signature {
        let address_from_sig =
            recover_address_from_ecdsa_signature::<OptimisticPayoutMessage>(...)?;
        if address_from_sig != address_in_config {
            return Err(BridgeError::InvalidECDSAVerificationSignature);
        }
    }
}
``` [4](#0-3) 

The recovery function itself passes the domain-separator-less hash directly:

```rust
let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);
let address = signature.recover_address_from_prehash(&eip712_hash)...;
``` [5](#0-4) 

Because `CLEMENTINE_EIP712_DOMAIN` has no `chainId`, the EIP-712 hash of any `(withdrawal_id, input_signature, input_outpoint_txid, input_outpoint_vout, output_script_pubkey, output_amount)` tuple is **identical** on every network. A signature that passes verification on testnet4 will pass the same check on mainnet with the same tuple.

---

### Impact Explanation

When `aggregator_verification_address` is configured (the intended production hardening), the `verification_signature` is the sole gate preventing an unauthorized party from instructing operators to execute payout transactions or instructing verifiers to co-sign optimistic-payout transactions.

**Operator withdrawal path:** The operator fronts the withdrawal by spending bridge-controlled BTC from the move-to-vault UTXO and paying the user. A replayed testnet signature that passes the authorization check causes the operator to execute a payout on mainnet without a legitimate mainnet aggregator approval, potentially draining operator-fronted BTC for a withdrawal that has no valid mainnet backing.

**Optimistic payout path:** Verifiers co-sign the optimistic payout transaction. A replayed signature causes verifiers to contribute partial MuSig2 signatures to a payout that was never authorized on mainnet, enabling the aggregator to finalize and broadcast a payout transaction spending the bridge vault UTXO.

Both outcomes represent unauthorized spending of bridge-controlled or operator-controlled BTC.

---

### Likelihood Explanation

Exploitation requires:

1. **Same `aggregator_verification_address` across networks** — Ethereum addresses are derived from the same key regardless of network; operators and aggregators routinely reuse the same key on testnet and mainnet. This condition is highly likely in practice.

2. **Same `(withdrawal_id, input_outpoint, ...)` tuple on both networks** — `withdrawal_id` is a sequential Citrea counter starting from 0, so overlap is guaranteed for any withdrawal index that exists on both networks. The `input_outpoint` is the withdrawal UTXO stored in the DB from Citrea state; an attacker who controls the same Bitcoin key on both networks (or who can arrange the same UTXO to appear on both) satisfies this condition.

3. **Ability to observe a valid testnet signature** — The `verification_signature` is transmitted over gRPC. An attacker with network access or who is themselves a participant on testnet can capture it.

These conditions are realistic in a multi-network deployment scenario (testnet4 → mainnet migration or parallel operation).

---

### Recommendation

Add `chain_id` to `CLEMENTINE_EIP712_DOMAIN`, sourced from the configured Citrea/EVM chain ID at runtime:

```rust
pub fn clementine_eip712_domain(chain_id: u64) -> Eip712Domain {
    alloy_sol_types::eip712_domain! {
        name: "ClementineVerification",
        version: "1",
        chain_id: chain_id,
    }
}
```

Pass the domain built from the live chain ID into `recover_address_from_ecdsa_signature` and into the signing utility `sign_withdrawal_verification_signature`. This ensures a signature produced on testnet4 (chain ID ≠ mainnet chain ID) will recover a different address and fail the `address_from_sig != address_in_config` check on mainnet.

---

### Proof of Concept

1. Deploy Clementine on testnet4 and mainnet with the same `aggregator_verification_address` (same Ethereum key).
2. On testnet4, initiate a withdrawal with `withdrawal_id = N` and `input_outpoint = X`. The aggregator signs a `verification_signature` over `(N, sig, X, vout, script, amount)` using `CLEMENTINE_EIP712_DOMAIN`.
3. On mainnet, arrange for `withdrawal_id = N` to have `input_outpoint = X` in the DB (attacker controls the same Bitcoin UTXO on mainnet).
4. Submit the testnet4 `verification_signature` to the mainnet operator's `withdraw` RPC with the same params.
5. `recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>` computes the identical EIP-712 hash (no `chainId` in domain), recovers the same address, and the check passes.
6. The operator executes the payout transaction on mainnet without a legitimate mainnet aggregator authorization.
