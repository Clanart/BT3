### Title
Denial of service via attacker-controlled `n` in `ThresholdKeys::read` forcing quadratic Lagrange interpolation work - (crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` takes `t`, `n`, and `i` directly from untrusted bytes. `n` is a `u16`, so a maliciously crafted serialization can claim up to 65,535 participants. The reader then reads `n` scalars (constant interpolation) and `n` group elements, and `ThresholdKeys::new` computes the group key by evaluating a Lagrange `interpolation_factor` for each of participants `1..=t`, each factor itself being a product over `t` terms — O(t·n) field work plus `n` point decompressions, all triggered by only ~6 bytes of length fields and a bounded amount of attacker data.

### Finding Description
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:591-631`):

- `t`, `n` are read as raw `u16`s with no sanity bound against the actual remaining input length beyond the reads themselves.
- For `Interpolation::Constant`, `Vec::with_capacity(n)` is allocated and `n` scalars are read (`crypto/dkg/src/lib.rs:607-613`).
- `n` verification shares are read via `C::read_G` (`crypto/dkg/src/lib.rs:620-623`), each requiring a full point decompression/canonicity check.
- `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349-391`) then computes `group_key` as the sum over `1..=t` of `verification_shares[i] * interpolation.interpolation_factor(i, &t)`, where each Lagrange factor is a product over all `t` indices — O(t²) field multiplications/inversions in aggregate, i.e. up to ~4×10⁹ scalar operations for `t = n = 65535`, all driven by a payload of at most ~4 MB (and the allocation/parse failures occur only after `Vec::with_capacity(65535)` and the point reads).

This is the direct analog of CVE-2021-45115: an input parameter (`n`) controls work that is quadratic/excessive relative to the small comparison inputs, and the reader never validates that the declared size is reasonable before incurring the cost.

### Impact Explanation
Any code path that feeds adversarially supplied bytes into `ThresholdKeys::read` (or equivalently `SecretShare`/`EncryptedMessage`/`EncryptionKeyMessage::read` with attacker-influenced `ThresholdParams`, and FROST `read_preprocess`/`read_share` flows that deserialize participant-count-derived structures) lets an unprivileged peer force a node to burn CPU on ~65k point decompressions and O(t·n) interpolation work per message. Repeated submissions stall the victim's signing/DKG processing — a remote, unauthenticated CPU-exhaustion DoS on a validator/processor.

### Likelihood Explanation
Reachable whenever serialized key/share material crosses a trust boundary — processor DB reload paths, tributary transaction payloads carrying DKG material, or any peer-supplied bytes deserialized via the `read` APIs listed above. The attacker only needs to flip two `u16` length fields; the heavy work is performed unconditionally during deserialization/validation, before any authentication of the payload's semantics.

### Recommendation
- Bound `n`/`t` in `ThresholdParams::new`/deserialization against a protocol maximum (e.g. the actual participant count of the session) before allocating or reading.
- Validate `commitments_len * each_commitments_len`-style products against a message-size limit everywhere — the pattern already used for `DkgCommitments` (`TRANSACTION_SIZE_LIMIT`) but missing for e.g. `DkgShares` and `SignData` piece counts.
- Prefer streaming reads without `Vec::with_capacity(n)` preallocation based on untrusted lengths.

### Proof of Concept
```rust
// Craft a ThresholdKeys serialization with t = n = 65535.
// Only ~10 header bytes are needed to trigger:
//   Vec::with_capacity(65535) + 65535 read_G decompressions +
//   O(t * n) Lagrange interpolation work in ThresholdKeys::new.
let mut buf = vec![];
buf.extend(&(C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(&u16::MAX.to_le_bytes()); // t
buf.extend(&u16::MAX.to_le_bytes()); // n
buf.extend(&1u16.to_le_bytes());     // i
buf.push(1);                         // Interpolation::Lagrange
buf.extend(vec![0u8; /* secret_share repr */]);
// Feed buf (plus minimal point bytes) to ThresholdKeys::<C>::read(&mut buf.as_slice())
// → multi-GB-equivalent scalar-op work from a tiny input.
```
