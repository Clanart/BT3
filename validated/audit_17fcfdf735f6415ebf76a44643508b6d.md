## Finding

The reported Balancer bug is a case of "derive a security-relevant value from raw input using a naive comparison that doesn't account for how the value can be manipulated, then trust that derived value downstream." The `min` price is computed from raw per-token quotes without normalizing them to a common reference (the rate), so an attacker who controls the relative "shape" of the inputs can skew the result.

GitHub Desktop has a structurally identical flaw in how it extracts the **hostname** from a remote URL, which is then trusted to decide which GitHub account/OAuth token to associate with a repository.

### Title
Hostname mis-extraction in `parseRemote()` allows a crafted remote URL to spoof account/host matching - (`app/src/lib/remote-parsing.ts`)

### Summary
`parseRemote()` extracts `{ hostname, owner, name }` from a git remote URL using a regex with two adjacent greedy groups: an optional userinfo group `(?:.+@)?` and the hostname group `(.+)`. Because both are greedy and unanchored to actual URL syntax (no real URL parser is used), a URL containing an extra `@` can cause the "userinfo" group to swallow the real host and leading path, while the hostname group captures an attacker-chosen string that looks like a trusted host (e.g. `github.com`). [1](#0-0) 

### Finding Description
The HTTPS regex is:
```
^https?://(?:.+@)?(.+)/([^/]+)/([^/]+?)(?:/|\.git/?)?$
``` [2](#0-1) 

For an input such as `https://attacker.evil/@github.com/owner/name`, the greedy optional group `(?:.+@)?` consumes `attacker.evil/@` (everything up to and including the only `@`), leaving `github.com/owner/name` to be matched by `(.+)/([^/]+)/([^/]+?)`. The result is `hostname: "github.com"`, `owner: "owner"`, `name: "name"` — even though the string never actually names `github.com` as a real authority component and the connection Git will actually make is to `attacker.evil`.

This forged `hostname` is exactly what downstream account-matching logic trusts:
- `findAccountForRemoteURL()` compares `parsedURL.hostname` against each signed-in account's real endpoint hostname to decide which `Account` (and its OAuth token) is "the" account for a URL/repository. [3](#0-2) 
- `matchGitHubRepository()` performs the identical hostname comparison to bind a cloned/added repository to a `GitHubRepository` model tied to that account. [4](#0-3) 

Both call sites use the regex-derived `hostname`, not a real `URL`/`URL.parse()` authority, so the malformed input is never rejected — it just silently resolves to the wrong host, the same failure mode as the Solidity bug picking `min` from unnormalized values.

### Impact Explanation
If a repository is added/cloned using a URL of this shape (e.g. copied from a malicious README, issue, or a link a user is told to paste into "Clone repository" or "Add existing repository"), GitHub Desktop's app-level logic will treat the repository as belonging to `github.com` and will associate the user's real GitHub.com account with it (`GitHubRepository.endpoint`), even though the string never legitimately named `github.com` as the connecting authority. Downstream features that key off `GitHubRepository`/account association — API calls, PR/CI metadata fetches, avatar/asset requests that attach `Authorization: token <token>` based on origin matching — could be pointed at attacker-controlled infrastructure disguised behind the confusing path, risking exposure of API responses/metadata tied to the wrong trust boundary, and definitely causing the app to silently mis-attribute the repository/account relationship (analogous to "silent corruption" of what the user believes they are pushing/pulling to).

### Likelihood Explanation
Requires only that the user add or clone a specially crafted URL string — no local access, no prior compromise, no elevated privileges. This satisfies the "attacker controls a git remote" trigger class. The regex has been part of `remote-parsing.ts` unchanged in its greedy-group structure and is exercised by both `find-account.ts` and `repository-matching.ts`, both of which lack any secondary validation (e.g., re-parsing with `new URL()` and comparing `.hostname`) to catch the mismatch.

### Recommendation
Replace the ad-hoc regex-based hostname/userinfo extraction in `parseRemote()` with an actual URL parser (`new URL()`) for the `https`/`ssh://` forms, and validate that the parsed `.hostname` matches expectations before treating it as authoritative for account/repository matching. At minimum, reject inputs where the "userinfo" segment itself contains additional `/` or `@` characters that indicate parser confusion, and add a regression test mirroring the report's technique (extra `@` embedding a lookalike host after it).

### Proof of Concept
```ts
import { parseRemote } from '../src/lib/remote-parsing'

const result = parseRemote('https://attacker.evil/@github.com/owner/name')
console.log(result)
// { protocol: 'https', hostname: 'github.com', owner: 'owner', name: 'name' }
// Actual connecting host is attacker.evil, but Desktop believes it is github.com
```
Feeding this URL through `findAccountForRemoteURL()` or `matchGitHubRepository()` will select the user's real `github.com` account for a repository whose remote does not actually point at GitHub.com. [5](#0-4) 

**Uncertainty**: I could not fully trace every consumer of `GitHubRepository.endpoint`/account association set via this path (e.g., exact call sites in `app-store.ts`, `clone-repository.tsx`, `infer-last-push-for-repository.ts`) within the available indexed content, so the full blast radius (which specific network requests would carry the token to the wrong host) is not fully confirmed. A Devin session with full repo access would be needed to trace every downstream `Authorization` header attachment keyed off this hostname/endpoint value to confirm the credential-exfiltration path is reachable end-to-end.

const remoteRegexes: ReadonlyArray<{ protocol: GitProtocol; regex: RegExp }> = [
  {
    protocol: 'https',
    regex: new RegExp(
      '^https?://(?:.+@)?(.+)/([^/]+)/([^/]+?)(?:/|\\.git/?)?$'
    ),
  },
  {
    protocol: 'ssh',
    regex: new RegExp('^git@(.+):([^/]+)/([^/]+?)(?:/|\\.git)?$'),
  },
  {
    protocol: 'ssh',
    regex: new RegExp(
      '^(?:.+)@(.+\\.ghe\\.com):([^/]+)/([^/]+?)(?:/|\\.git)?$'
    ),
  },
  {
    protocol: 'ssh',
    regex: new RegExp('^git:(.+)/([^/]+)/([^/]+?)(?:/|\\.git)?$'),
  },
  {
    protocol: 'ssh',
    regex: new RegExp('^ssh://git@(.+)/(.+)/(.+?)(?:/|\\.git)?$'),
  },
]

/** Parse the remote information from URL. */
export function parseRemote(url: string): IGitRemoteURL | null {
  for (const { protocol, regex } of remoteRegexes) {
    const match = regex.exec(url)
    if (match !== null && match.length >= 4) {
      return { protocol, hostname: match[1], owner: match[2], name: match[3] }
    }
  }

  return null
}

export async function findAccountForRemoteURL(
  urlOrRepositoryAlias: string,
  accounts: ReadonlyArray<Account>,
  canAccessRepository: RepositoryLookupFunc = canAccessRepositoryUsingAPI
): Promise<Account | null> {
  const allAccounts = [...accounts, Account.anonymous()]

  // We have a couple of strategies to try to figure out what account we
  // should use to authenticate the URL:
  //
  //  1. Try to parse a remote out of the URL.
  //    1. If that works, try to find an account for that host.
  //    2. If we don't find an account move on to our next strategy.
  //  2. Try to parse an owner/name.
  //    1. If that works, find the first account that can access it.
  //  3. And if all that fails then throw our hands in the air because we
  //     truly don't care.
  const parsedURL = parseRemote(urlOrRepositoryAlias)
  if (parsedURL) {
    const account =
      allAccounts.find(a => {
        const htmlURL = getHTMLURL(a.endpoint)
        const parsedEndpoint = URL.parse(htmlURL)
        return parsedURL.hostname === parsedEndpoint.hostname
      }) || null

    // If we find an account whose hostname matches the URL to be cloned, it's
    // always gonna be our best bet for success. We're not gonna do better.
    if (account) {
      return account
    }
  }

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
