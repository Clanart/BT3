### Title
Unvalidated `head.repo.clone_url` from GitHub API PR object passed to `git remote add` / `git fetch`, enabling remote-helper argument/command injection - (File: `app/src/lib/stores/app-store.ts`, `app/src/lib/git/remote.ts`)

### Summary
The `isApprovedOrOwner()` bug is a case of trusting an attacker-influenced value as if it had already passed an authorization/sanity check. The Desktop analog is `_findPullRequestBranch()` in `app-store.ts`, which takes a `headCloneUrl` string that ultimately originates from a GitHub API pull-request object (`pull_request.head.repo.clone_url`) — a value fully controlled by whoever opens the pull request or crafts the deep link — and forwards it unchecked into `git remote add` and `git fetch`.

### Finding Description
`_checkoutPullRequest` / `_findPullRequestBranch` receive `headCloneUrl` straight from an `IAPIPullRequest` object: [1](#0-0) 
This value is passed unmodified to `addRemote`, which shells out to `git remote add <name> <url>` with no scheme/format validation: [2](#0-1) 
and then to `_fetchRemote`, which performs the actual network fetch against that remote: [3](#0-2) 

Two attacker-controlled entry points feed this path:
1. The "Open PR from Desktop" deep link handler, where both the target repository `url` and PR number `pr` are attacker-supplied and used to fetch the PR object, then its `head.repo.clone_url` is passed directly into `_checkoutPullRequest`: [4](#0-3) 
2. Any normal PR list checkout flow, where `pullRequest.head.gitHubRepository.cloneURL` (populated from the API `clone_url` field for the head repo of a PR — which can be any fork, including one created by the attacker) is used the same way: [5](#0-4) 

Git supports a `ext::<command>` remote helper transport, which executes the given command directly. A codebase-wide search found no `GIT_ALLOW_PROTOCOL` allowlist, no protocol/scheme validation, and no use of `--` or protocol restriction anywhere `addRemote`/`git remote add`/`git fetch` is invoked. The only sibling guard I could find in this codebase is the strict host/owner/name equality check in `urlsMatch`/`urlMatchesRemote` used for *matching* existing repositories (`app/src/lib/repository-matching.ts`), and the `resolveWithin` path-containment guard (`app/src/lib/path.ts`) — neither of which is a protocol/scheme validator, so neither is exercised on this path. This mirrors the original bug pattern: a check exists nearby for a *different* purpose, but the actual value that reaches the sensitive operation (`clone_url`) is never itself validated before being trusted.

### Impact Explanation
If a `clone_url` value of the form `ext::sh -c 'touch /tmp/pwned'` (or any OS command via the `ext::` helper, or a `-`-prefixed value that git interprets as a flag) reaches `git remote add` followed by `git fetch`, it results in arbitrary command execution on the victim's machine — outside any git/repo sandbox — triggered purely by the victim opening a crafted pull request or clicking a deep link, i.e., unprivileged attacker control of a GitHub API object leading to code execution. This satisfies the "attacker controls a fetched GitHub API object … resulting in code execution" impact class from the report's own criteria.

### Likelihood Explanation
Exploitability requires only that the attacker (a) open a pull request whose head repository's `clone_url` is attacker-influenced, or (b) get the victim to click a `x-github-client://openRepo?...&pr=...` deep link pointing at a PR the attacker controls. Both require no local access, no leaked credentials, and no unusual user action beyond opening/clicking a PR link — actions Desktop explicitly designs for ("Open PR from Desktop"). Whether GitHub.com's own API rejects non-`https`/`git`/`ssh` `clone_url` values server-side (which would mitigate this) could not be confirmed from this repository alone; that server-side validation is outside the Desktop codebase and was not verifiable with the tools available here.

### Recommendation
Before calling `addRemote`/`git fetch` with any URL derived from API/PR data, validate that the URL's scheme is restricted to an explicit allowlist (`https:`, `ssh:`, `git:`) and reject anything else (in particular `ext::`, `fd::`, or values beginning with `-`). Consider also invoking git fetch/remote operations with `-c protocol.ext.allow=never` (or the equivalent `GIT_ALLOW_PROTOCOL` environment restriction) as defense in depth, matching the pattern already used for the `resolveWithin`/`sanitizeCloneName` guards on the filesystem side.

### Proof of Concept
1. Attacker crafts a GitHub PR (or a `x-github-client://openRepo?url=...&pr=...` deep link) whose `head.repo.clone_url` — as returned in the API PR object consumed by `openPullRequestFromUrl` — is set to `ext::sh -c "touch$IFS/tmp/pwned"` (if the GitHub API itself does not reject the format) or otherwise influences the string reaching `addRemote`.
2. Victim clicks "Checkout PR" in Desktop, or opens the deep link.
3. `openPullRequestFromUrl` / `checkoutPullRequest` call `_checkoutPullRequest(repository, prNumber, headRepoOwner, headCloneUrl, headRefName)` with the attacker-supplied `headCloneUrl`.
4. `_findPullRequestBranch` finds no existing remote matching the URL and calls `addRemote(repository, forkRemoteName, headCloneUrl)`, running `git remote add <name> "ext::sh -c ..."`.
5. `_fetchRemote` is then invoked on that remote, causing git to invoke the `ext::` helper and execute the embedded command on the victim's machine. [6](#0-5)

  private async openPullRequestFromUrl(
    url: string,
    pr: string
  ): Promise<RepositoryWithGitHubRepository | null> {
    const pullRequest = await this.appStore.fetchPullRequest(url, pr)

    if (pullRequest === null) {
      return null
    }

    // Find the repository where the PR is created in Desktop.
    let repository: Repository | null =
      this.getRepositoryFromPullRequest(pullRequest)

    if (repository !== null) {
      await this.selectRepository(repository)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      log.warn(
        `Open Repository from URL failed, did not find or clone repository: ${url}`
      )
      return null
    }
    if (!isRepositoryWithGitHubRepository(repository)) {
      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`
      )
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    if (pullRequest.head.repo === null) {
      return null
    }

    await this.appStore._checkoutPullRequest(
      repository,
      pullRequest.number,
      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,
      pullRequest.head.ref
    )
