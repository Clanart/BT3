### Title
Per-transaction deposit metadata (`data`, `presumed_origin`) overwritten by later transactions in the same block — deposits credited with another transaction's `InInstruction` data - (File: processor/src/networks/bitcoin.rs)

### Summary
Analogous to `depositFor` crediting the vault while failing to notify/accrue into `LockedManagedReward` (deposit recorded, per-user accounting lost), `Bitcoin::get_outputs` accumulates scanned outputs across every transaction in a block, then overwrites the accounting metadata (`data` = the Serai InInstruction payload, and `presumed_origin`) of **all previously collected outputs** with the metadata of each subsequent transaction. A deposit's credited instruction data is therefore bound to the wrong transaction.

### Finding Description
In `Bitcoin::get_outputs`, the `outputs` vector is declared once before the per-transaction loop:

```rust
// processor/src/networks/bitcoin.rs:689-700
let mut outputs = vec![];
for tx in &block.txdata[1 ..] {
  for output in scanner.scan_transaction(tx) {
    ... outputs.push(output);
  }
  if outputs.is_empty() {
    continue;
  }
  ...
  let data = Self::extract_serai_data(tx);
  for output in &mut outputs {            // mutates ALL accumulated outputs
    if output.kind == OutputType::External {
      output.data.clone_from(&data);      // overwrites earlier txs' data
    }
    output.presumed_origin.clone_from(&presumed_origin);
  }
}
``` [1](#0-0) 

Two defects compound here:

1. `if outputs.is_empty() { continue }` checks the *cumulative* vector, not the outputs scanned from `tx`. Once any transaction in the block produced an output, every later transaction — even one with no vault-bound outputs — triggers the metadata-assignment block, deriving `presumed_origin` from `tx.input[0]` and `data` from `Self::extract_serai_data(tx)` of that unrelated transaction.
2. `for output in &mut outputs` iterates the cumulative vector, so `output.data` and `output.presumed_origin` of outputs scanned from earlier transactions are overwritten by the last relevant transaction processed.

`data` is the decoded Serai `InInstruction` attached to `OutputType::External` outputs (the deposit path that tells Serai how to credit the deposited funds), and `presumed_origin` is recorded for attribution/recovery [2](#0-1) . Both are attacker-influenceable transaction fields: the data is extracted from the transaction via `extract_serai_data`, and the origin is derived from `tx.input[0].previous_output` [3](#0-2) . The scanner itself only binds the `script_pubkey` to the offset, carrying no per-output binding to the correct `data` [4](#0-3) .

### Impact Explanation
Any `External` output (a user deposit into the Serai vault) shares a block with a later transaction that also produces a scanned output — or with any transaction at all once `outputs` is non-empty — will have its `data` (InInstruction, which controls where/how the deposit is credited on Serai) and `presumed_origin` replaced by the later transaction's values. The deposited funds arrive and are reported received, but they are credited under the *wrong instruction data* — the exact analog of rewards locked in `VotingEscrow` but never accrued to `LockedManagedReward`: the value transfer succeeds while the accounting record attached to it is wrong/attributed elsewhere. Depending on how the processor consumes `data`, this enables theft/misrouting of deposits (crediting the attacker's specified destination instead of the depositor's) and corrupts `presumed_origin` used for refund/attribution.

### Likelihood Explanation
Reachable by a fully unprivileged party: they need only get a Bitcoin transaction paying a Serai-registered P2TR script (the vault's external/branch/change scripts are publicly derivable via `scanner(key)` [5](#0-4) ) mined in the same block as a victim deposit, ordered after it, with attacker-chosen `InInstruction` data. Alternatively, since the `outputs.is_empty()` guard never resets, *any* transaction in the block after the first scanned output rewrites earlier outputs' `presumed_origin` — no vault payment needed for that half. Bitcoin transactions are public mempool data, so spotting a pending victim deposit and back-running it within the same block is realistic.

### Recommendation
Scope the metadata assignment to the current transaction only: collect `let mut tx_outputs = scanner.scan_transaction(tx)` inside the loop, `continue` when `tx_outputs.is_empty()`, apply `data`/`presumed_origin` to `tx_outputs` only, then `outputs.extend(tx_outputs)`. This restores the "notification" being bound to the correct deposit, i.e. each scanned output retains the instruction data of the transaction that actually created it.

### Proof of Concept
Block containing two transactions:

- `tx1`: victim deposit → 1 BTC to the Serai external address, `InInstruction` data crediting `victim_serai_address`. `scan_transaction(tx1)` yields `outputs[0]` (kind `External`, `data = victim_data`).
- `tx2` (later in the same block): attacker sends dust to the same Serai script with `data = attacker_instruction` (or any tx after `outputs` became non-empty).

Execution in `get_outputs`:

1. Iteration `tx1`: pushes victim output; `outputs` non-empty → assigns `data = victim_data`, `presumed_origin = victim_origin`. Correct so far.
2. Iteration `tx2`: pushes attacker output; `outputs` still non-empty → `for output in &mut outputs` overwrites `outputs[0].data` with `attacker_instruction` and `outputs[0].presumed_origin` with `tx2`'s input origin.

Result: `outputs[0]` — the victim's 1 BTC deposit — is returned to `processor/src/multisigs/scanner.rs`'s output reporting path carrying the *attacker's* instruction data and a falsified `presumed_origin`. The deposit is genuinely received on-chain (the vault got the BTC) but is processed under the wrong accounting payload — mirroring how claimed rebase rewards were deposited into the managed NFT yet never accrued in `LockedManagedReward`, leaving the rightful party unable to claim what was theirs.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
