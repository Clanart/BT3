### Title
Governance can set KIP-71 `gasTarget` to zero, causing a division-by-zero panic in `NextMagmaBlockBaseFee` and consensus-halting node crash - (File: params/kip71_config.go)

### Summary
`Kip71GasTarget` governance parameter lacks a non-zero validation (`noopFormatChecker`) unlike its sibling parameter `Kip71BaseFeeDenominator`, which explicitly rejects zero. If `gasTarget` is set to `0` via governance vote, every full node computing the next block's base fee via `NextMagmaBlockBaseFee` performs an unguarded `big.Int` division by the `gasTarget` value, which panics in Go and crashes the node process — mirroring the exact bug class of the referenced CVE (unguarded division that should have been prevented, as fixed for the sibling `BaseFeeDenominator`).

### Finding Description
`KIP71Config.NextMagmaBlockBaseFee` computes the base fee delta using `gasTarget` as a divisor in two branches (gas used above and below target): [2](#0-1) 

Both branches call `x.Div(x, new(big.Int).SetUint64(gasTarget))`. Go's `math/big.Int.Div` panics with `division by zero` when the divisor is zero — this is not a case handled by any defer/recover in the base-fee-calculation path (verification pipeline of block headers).

Contrast this with `BaseFeeDenominator`, which the code explicitly guards against being zero: [3](#0-2) 

But the `Kip71GasTarget` parameter definition in the governance parameter table uses a `noopFormatChecker`, meaning **no validation** is performed when a governance vote sets this value: [1](#0-0) 

This is inconsistent with the explicit `v != 0` check applied to `Kip71BaseFeeDenominator`: [4](#0-3) 

`NextMagmaBlockBaseFee` is called during header verification/preparation for every block after the Magma hardfork (`VerifyMagmaHeader`), meaning **every full node** (not just the proposer) re-executes this computation on every incoming block: [5](#0-4) 
This function is also used in the public `eth_feeHistory` RPC handler path, further extending exposure to any RPC caller once the parameter is poisoned: [6](#0-5) 

### Impact Explanation
If `reward.kip71.gastarget` (governance param `Kip71GasTarget`) is voted to `0` and accepted, the very next block after the vote takes effect causes **every node in the network** (validators and full nodes alike) computing `NextMagmaBlockBaseFee` to panic and crash simultaneously, since the divisor `gasTarget` is `0` in `new(big.Int).SetUint64(gasTarget)` used in `x.Div(x, ...)`. This is a network-wide liveness/DoS condition — a chain halt — triggered by a single governance parameter update, not merely a resource-only bug. Because the calculation is deterministic and mandatory for header verification post-Magma, there is no way for the network to produce or validate further blocks once this state is reached, without manual intervention/patch.

### Likelihood Explanation
This requires a governance vote to succeed in setting `gastarget` to `0`, which is gated by whatever governance access-control mode is configured (single-governance node or on-chain governance voting). It is not directly triggerable by an arbitrary unprivileged transaction sender, but it is a governance-parameter admission gap: the code path that is supposed to sanitize governance inputs (the format-checker table) fails to reject an obviously invalid value that would crash the network, unlike the neighboring parameter which is explicitly protected. This is analogous to the CVE class (an unguarded division that should have had an explicit zero-check, exactly as done for the sibling denominator field).

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `v == 0`, consistent with `Kip71BaseFeeDenominator`'s existing check. Additionally, consider adding a defensive zero-check inside `NextMagmaBlockBaseFee` itself (mirroring the existing `if kc.BaseFeeDenominator == 0 { ... }` fallback) so that even if an invalid `gasTarget` reaches this function (e.g., via genesis misconfiguration or future governance-table changes), the node degrades gracefully instead of panicking.

### Proof of Concept
1. Configure/vote governance parameter `reward.kip71.gastarget` (i.e., `Kip71GasTarget`) to `0`. Since `FormatChecker` is `noopFormatChecker`, the vote is accepted without rejection. [1](#0-0) 
2. Once the parameter takes effect at the next epoch/param-set boundary, any node processing the subsequent block calls `kip71Config.NextMagmaBlockBaseFee(parentNumber, parentBaseFee, parentGasUsed)` during header prep/verification. [5](#0-4) 
3. Inside `NextMagmaBlockBaseFee`, since `parentGasUsed != gasTarget (0)` almost certainly holds, execution enters either the `>` or `else` branch, both of which execute `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0`. [7](#0-6) 
4. `big.Int.Div` panics with "division by zero", crashing the calling goroutine/node process — reproducible directly via a unit test calling `NextMagmaBlockBaseFee(parentNum, parentBaseFee, parentGasUsed)` with a `KIP71Config{GasTarget: 0, ...}`.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
