### Title
Malicious preprocess commitments force aggregate nonce `R` to the point at infinity, panicking the BIP-340 `Hram::hram`/`x()` path and crashing honest signers - (File: networks/bitcoin/src/crypto.rs)

### Summary
The bug class of CVE-2024-28571 — attacker-controlled input reaching an unchecked memory/state access that aborts the process — maps onto `bitcoin-serai`'s FROST `Schnorr` algorithm: `x()` unconditionally calls `.expect("point at infinity")` on the encoded x-coordinate of `R` and the group key `A`. A FROST participant's preprocess commitments enter the aggregate nonce `R` additively with publicly computable binding factors, so a malicious participant can deterministically set `R` to the identity point, converting a routine `sign_share`/`verify` call into a panic (denial of service of the signing node) rather than a `FrostError`.

### Finding Description
`x()` extracts the x-coordinate via `key.to_encoded_point(true).x().expect("point at infinity")` — an unconditional panic on infinity [1](#0-0) . It is invoked by `Hram::hram` on both `R` and `A` for every signature-share computation and verification [2](#0-1) . The doc comment admits the panic exists but claims a "negligible probability ... even with malicious participants" [3](#0-2) .

That assumption is wrong. In `AlgorithmSignMachine::sign`, the aggregate nonce is `Σ_i (commitments_base_i + rho_i * commitments_actual_i)` via `B.nonces(&nonces)` [4](#0-3) . The `rho` binding factors are computed deterministically from `group_key`, `hash_msg(msg)`, and the transcript of *all* preprocesses (`B.calculate_binding_factors(&rho_transcript)`) [5](#0-4) . A malicious participant who sees the honest preprocesses (they must be broadcast before `sign` is called) can compute every `rho_i` locally and simply choose their own commitment points as `D = -(1/rho_i) · Σ_{j≠i} bound_j`, forcing `R = identity`. `Commitments::read`/`read_preprocess` place no identity check on the commitment points on this path [6](#0-5)  — contrast with `Signed::read`, which explicitly rejects identity `R` precisely because it would otherwise be reachable [7](#0-6) .

`sign` then calls `self.params.algorithm.sign_share(&view, &Rs, nonces, msg)` [8](#0-7) , which reaches `Hram::hram` → `x(&R)` → panic. Even if the panic does not fire inside `sign_share`, `complete` invokes `algorithm.verify(...)` which evaluates the same HRAM on the same `Rs` [9](#0-8) .

### Impact Explanation
A single malicious (or merely Byzantine-faulty) participant in a Bitcoin multisig signing session can abort the entire `sign()`/`complete()` execution of every honest signer by panic — a thread/executor crash rather than a catchable `FrostError::InvalidShare`. For a threshold network coordinating Bitcoin custody this is a persistent, repeatable denial of service: the attacker can force `R = identity` in every session they join, indefinitely preventing signature production. This is the direct analog of `fill_input_buffer` crashing the decoder on attacker-supplied bytes: attacker-supplied commitments reach an unchecked `expect` instead of a graceful error path.

### Likelihood Explanation
Reachability is public-input-only: the attacker needs only to be a signing-set participant and send a crafted preprocess message (canonical, validly-encoded points — the only check on this path is canonicality in `read_G` [10](#0-9) ). Cost is a few scalar inversions/multiplications; no grinding is needed because all `rho_i` are deterministic and computable before submitting commitments in a single session (the attacker reveals commitments last, or the aggregate is computed after all preprocesses are collected). Certainty caveat: I could not fully read `crypto/frost/src/nonce.rs` (`B.nonces`/`Commitments::read` internals) within this session to confirm no identity rejection occurs there; however the documented `Algorithm` contract ("verify/verify_share MUST be called after sign_share ... MAY panic"; "negligible probability" framing rather than a hard check) indicates identity `R` is not rejected before `x()`.

### Recommendation
Reject identity commitments in `Commitments::read`/`read_preprocess` and reject identity aggregate `Rs` before evaluating the HRAM, returning `FrostError::InvalidParticipant`/`InvalidShare` instead of panicking. Alternatively, make `x()`/`x_only()` return `Option`/`io::Result` and propagate failure from `Hram::hram`, so malformed-but-canonical attacker input can never unwind the process. At minimum, remove the "negligible probability" justification — the input space is adversarially controlled, not random.

//      -> x(&R_sum) -> to_encoded_point(true).x() == None
//      -> expect("point at infinity") -> PANIC
