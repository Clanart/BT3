### Title
Quadratic interpolation in `ThresholdKeys::new` reachable via `ThresholdKeys::read` with attacker-controlled `t = n = u16::MAX` - (File: crypto/dkg/src/lib.rs)

### Summary
The dparse advisory is a ReDoS: attacker-controlled input forcing superlinear CPU work in a parsing path. The Serai analog is algorithmic-complexity denial of service in `ThresholdKeys` deserialization: a `u16` participant count `n` read from untrusted bytes is used to drive an `O(t²)` Lagrange interpolation inside `ThresholdKeys::new`, with no bound on `t`/`n` beyond `u16::MAX`.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from the input stream, then reads `n` group elements into `verification_shares` and calls `ThresholdKeys::new` [1](#0-0) . `ThresholdParams::new` only enforces `t <= n` and `t, n != 0`, so `t = n = 65535` is accepted [2](#0-1) . `ThresholdKeys::new` then computes the group key by evaluating `interpolation_factor` for every participant `1..=t`, and each `Interpolation::Lagrange` factor evaluation loops over the full `included` slice of length `t`, performing field multiplications and an inversion [3](#0-2) [4](#0-3) . The result is `O(t²)` field operations — roughly 4.3 billion multiplications plus 65k inversions — triggered by an input of only ~2 MB (65535 encoded points). The same quadratic pattern exists in `ThresholdKeys::view`, which calls `interpolation_factor` once per member of `included` [5](#0-4) , though `view` is gated by the local signing set rather than raw bytes.

### Impact Explanation
An unprivileged party who can supply serialized `ThresholdKeys` bytes (per the engagement model, untrusted bytes fed to `ThresholdKeys::read`) can stall the parsing/verifying node for a duration quadratic in `n`, with no early rejection. This is the same attacker-controlled-work amplification class as the dparse regex: small input, disproportionate CPU. Because the multiplication happens inside the trusted key-loading path before any signature/proof check, it denies service to the host process regardless of the key's validity.

### Likelihood Explanation
Triggering requires only that the application deserialize `ThresholdKeys` from data influenced by an untrusted party (e.g., a peer-supplied key share blob during DKG/recovery flows). The crafted payload is ~2 MB of syntactically valid encodings with `t = n = 0xFFFF`; all internal checks (`t <= n`, `i <= n`, share count == n) are satisfiable by the attacker. If `ThresholdKeys::read` is only ever called on locally generated, self-serialized keys, the reachable severity drops sharply — that deployment question is the main uncertainty in this finding.

### Recommendation
- Impose a protocol-appropriate upper bound on `n`/`t` (e.g., a few hundred participants) inside `ThresholdParams::new` or `ThresholdKeys::read`, rejecting larger values before allocation/interpolation.
- Alternatively, compute the Lagrange factors over `1..=t` with an `O(t)` prefix/suffix-product formulation (batch inversion), so even large `n` cannot force quadratic work.
- Apply the same bound to any path that constructs `Interpolation::Constant`/`Lagrange` views from deserialized parameters.

### Proof of Concept
Serialize a `ThresholdKeys` payload for a `Ciphersuite` `C`:
- `id_len`/`id` matching `C::ID`
- `t = 0xFFFF`, `n = 0xFFFF`, `i = 0x0001`
- interpolation byte `0x01` (Lagrange)
- 32 bytes for `secret_share`
- `65535` encoded group elements (any valid encodings, e.g., generator repeated)

Feed it to `ThresholdKeys::<C>::read`. Parsing the points is linear (~65k decompressions), then `ThresholdKeys::new` performs `t` iterations of `interpolation_factor`, each scanning all `t` participants — ≈4.3×10⁹ field multiplications and 65k field inversions — before returning, pinning a core far beyond what a ~2 MB input should cost.

Caveat: I verified the quadratic loop and the absence of an `n` bound in the shown code; I could not enumerate every caller of `ThresholdKeys::read` within the in-scope crates to confirm a live network-reachable call site, so the exploitability rating depends on that integration detail.
