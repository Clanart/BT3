### Title
Bitcoin `OP_RETURN` outputs bypass the transaction fee and size bound - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` accepts up to 80 bytes of caller-controlled data and appends it as an `OP_RETURN` output before calculating the transaction fee. [1](#0-0)  However, both the initial and change-output fee calculations pass `payments` rather than the complete `tx_outs`, so the added `OP_RETURN` output contributes no weight or vbytes to `needed_fee`. [2](#0-1) [3](#0-2)  This creates a Medium-severity underpriced-transaction condition reachable through public transaction data supplied to the Bitcoin wallet API.

### Finding Description
The constructor validates each payment amount, limits `data` to 80 bytes, and appends the resulting zero-value `OP_RETURN` output to `tx_outs`. [4](#0-3) [5](#0-4)  It then calculates `weight` and `vbytes` with only `inputs` and `payments`, omitting the `OP_RETURN` output already staged in `tx_outs`. [2](#0-1) 

The minimum-relay check and input-sufficiency check therefore use an understated `vbytes` and `needed_fee`. [6](#0-5)  The same stale output list is used when calculating `fee_with_change`, so the change calculation also understates the true transaction size. [7](#0-6)  Finally, the stale `weight` is checked against `MAX_STANDARD_TX_WEIGHT`, while the returned transaction includes the omitted `OP_RETURN` output. [8](#0-7) 

For an 80-byte payload, the added output serializes as an 8-byte value, a compact script length, and an 83-byte script consisting of `OP_RETURN`, `PUSHDATA1`, the payload-length byte, and the 80-byte payload. [9](#0-8)  This adds approximately 92 base bytes and therefore approximately 92 vbytes, none of which is included in `needed_fee`. [10](#0-9) [2](#0-1) 

### Impact Explanation
A caller can make the threshold wallet sign a transaction whose actual fee rate is lower than the requested `fee_per_vbyte` and potentially below Bitcoin’s default relay minimum. [11](#0-10)  Because the `OP_RETURN` output has zero value, `fee()` remains `sum(inputs) - sum(outputs)` and does not reveal the omitted size in the input total. [12](#0-11)  The resulting `SignableTransaction` can be passed directly into `multisig`, causing the FROST signing flow to authorize the malformed fee transaction. [13](#0-12) 

If the input value exactly equals `payments + needed_fee`, the signed transaction pays only the fee estimated for the smaller transaction despite serializing with the additional `OP_RETURN` output. [14](#0-13)  At `fee_per_vbyte = 1`, an added 92-vbyte output reduces the effective fee rate to roughly `estimated_vbytes / (estimated_vbytes + 92)`, which can be below the 1 sat/vbyte default relay floor. [15](#0-14)  The transaction can consequently fail relay or remain unconfirmed even though the constructor accepted it and reported `needed_fee()` as sufficient. [16](#0-15) 

### Likelihood Explanation
The vulnerability only requires control of the public `data` argument, the payment list, inputs, change selection, and requested fee rate exposed by `SignableTransaction::new`. [17](#0-16)  An 80-byte payload maximizes the discrepancy and is explicitly accepted by the constructor. [1](#0-0)  The issue is deterministic and does not depend on miner behavior, although exploitation requires a caller or integration path that uses the wallet API’s optional data-output feature. [18](#0-17) 

### Recommendation
Calculate `weight`, `vbytes`, `needed_fee`, `fee_with_change`, and the maximum-standard-weight check from the complete candidate output list, including every `OP_RETURN` output and any change output. [19](#0-18) [7](#0-6)  Alternatively, extend `calculate_weight_vbytes` to accept the data payload or the already-constructed `tx_outs`, then validate the final transaction’s actual `vsize()` and `fee()` against both the requested fee rate and `DEFAULT_MIN_RELAY_TX_FEE` before returning the `SignableTransaction`. [20](#0-19) [21](#0-20) 

### Proof of Concept
The following test-shaped pseudocode demonstrates the bound failure by funding the input with exactly `payment + needed_fee`, where `needed_fee` was calculated without the 80-byte data output.

```rust
// Helpers produce a valid spendable ReceivedOutput and P2TR destination.
let payment = 10_000;
let data = vec![0u8; 80];
let fee_rate = 1;

let probe = SignableTransaction::new(
    vec![funding_output(u64::MAX / 4)],
    &[(destination(), payment)],
    None,
    Some(data.clone()),
    fee_rate,
).unwrap();

let understated_fee = probe.needed_fee();
let exact_input = funding_output(payment + understated_fee);

let tx = SignableTransaction::new(
    vec![exact_input],
    &[(destination(), payment)],
    None,
    Some(data),
    fee_rate,
).unwrap();

assert_eq!(tx.fee(), understated_fee);
assert_eq!(tx.fee() * 1000, understated_fee * 1000);

// The actual transaction is larger than the estimated transaction, so the
// effective feerate is below 1 sat/vbyte and below the default relay minimum.
assert!(tx.transaction().vsize() as u64 > understated_fee);
assert!(tx.fee() * 1000 < (tx.transaction().vsize() as u64) * 1000);
```

This succeeds because `needed_fee` is derived from `payments`, while the returned transaction serializes `tx_outs`, including the omitted `OP_RETURN` output. [22](#0-21) [23](#0-22)
