### Title
Missing duplicate-input-token guard allows double-credit of escrow mapping in Tron `IntentGatewayV2.placeOrder()` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`SpigotedLoan`'s bug was a collection (`unusedTokens[token]`) being incremented twice for the same value because two independent code paths both wrote to it for the same token. The local Hyperbridge analog is the Tron port of `IntentGatewayV2.placeOrder()`, where the escrow accounting mapping `_orders[commitment][token]` is credited with `+=` for every input leg with **no duplicate-token check**, unlike the canonical EVM contract which explicitly reverts on duplicate input tokens. This reintroduces a previously-identified and fixed bug class ("same-chain partial fills over-release repeated input escrow") in a sibling contract that never received the fix.

### Finding Description
`evm/src/apps/IntentGatewayV2.sol` credits escrow per input token with a strict single-assignment guard: [1](#0-0) 
```
        // Phase 3: Credit escrow.
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            // Reject duplicate input tokens
            if (_orders[commitment][token] != 0) revert InvalidInput();
            _orders[commitment][token] = reducedInputs[i].amount;
```

The Tron fork of the same contract instead accumulates the same mapping with `+=` in both the predispatch and non-predispatch escrow branches, with no equivalent duplicate check anywhere before the write: [2](#0-1) [3](#0-2) 

A regression test on the fixed EVM contract shows this exact defect was previously present and is now guarded against, with the test explicitly documenting the impact as "same-chain partial fills over-release repeated input escrow": [4](#0-3) 

Because the Tron variant lacks this guard, an order placer can submit an `Order` whose `inputs` array contains the same token address in multiple `TokenInfo` entries. Each entry independently transfers real funds into escrow (via `safeTransferFrom` or `msgValue` deduction) and then adds its `reducedInputs[i].amount` into the *same* `_orders[commitment][token]` bucket. This mirrors the `SpigotedLoan` pattern exactly: a single logical value (escrow-per-token) is derived from two (or more) independent update sites that were not designed to be composed, producing an accounting collection whose recorded value diverges from — or is manipulable relative to — the intended per-asset semantics that downstream release/fill logic (same-chain partial fills, cross-chain `withdraw()`) relies on to compute solver payouts and beneficiary transfers.

### Impact Explanation
`_orders[commitment][token]` is the authoritative escrow ledger consumed by `fillOrder` to determine how much of a given token to release to a solver (full or proportional partial release). A corrupted/duplicated bucket for that mapping can misalign the escrow-per-input-leg accounting from the actual per-leg intent encoded in the order commitment, enabling wrong-amount releases (over-release to a solver or gateway insolvency for other users' escrowed funds) — matching the bounty's "logic attacks" / "wrong beneficiary or amount" / "stealing or loss of funds" categories on the Tron deployment of the Intent Gateway.

### Likelihood Explanation
This requires no privileged actor, relayer, prover, or governance action — it is triggerable by any ordinary user calling the public `placeOrder()` entrypoint with a self-crafted `Order.inputs` array containing a repeated token address, which is exactly the same unprivileged, single-transaction primitive class as the original `claimAndTrade()` bug report.

### Recommendation
Port the duplicate-input-token guard from `evm/src/apps/IntentGatewayV2.sol` (`if (_orders[commitment][token] != 0) revert InvalidInput();` with a single `=` assignment) into `evm/tron/contracts/apps/IntentGatewayV2.sol`'s escrow-crediting loops (both the predispatch and non-predispatch branches), and add the equivalent regression test (`testRevert_PlaceOrder_DuplicateInputTokens`) to the Tron test suite to prevent regressions.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` contract and a test ERC20 token.
2. As a user, construct an `Order` with `inputs = [{token: USDC, amount: A}, {token: USDC, amount: B}]` (same token twice, distinct outputs to satisfy no other validation).
3. Approve the gateway for `A + B` and call `placeOrder(order, graffiti)`.
4. Observe `_orders[commitment][USDC]` equals `reducedA + reducedB` (double-credited from two independent loop iterations) — compare against `evm/src/apps/IntentGatewayV2.sol`, which would revert this exact order with `InvalidInput()` at the second iteration.
5. Follow with `fillOrder`/partial-fill logic (as exercised in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`) to demonstrate the inflated escrow bucket drives an incorrect release amount to the solver relative to the order's actual intended per-leg amounts.
