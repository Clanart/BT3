### Title
Unreliable ETH refund in `WSEI.withdraw()` due to use of `transfer()` instead of `call()` - (File: contracts/src/WSEI.sol)

### Summary
`WSEI.withdraw()` uses the deprecated `payable(msg.sender).transfer(wad)` pattern to return native SEI (wei) to callers unwrapping their WSEI balance, matching the exact bug class from the external report (use `call()` instead of `transfer()`).

### Finding Description
The `withdraw` function debits the caller's WSEI balance and then sends the equivalent native value using Solidity's `transfer()`, which hard-codes a 2300 gas stipend to the recipient: [1](#0-0) 
This contract is compiled and shipped as `x/evm/artifacts/wsei/WSEI.bin`/`WSEI.abi` and can be deployed on-chain by any user via the `deploy-wsei` CLI command: [2](#0-1) 
Once deployed, any EVM account (including smart-contract wallets, multisigs, or other contracts) can call `deposit()`/`withdraw()`. If the caller is a contract whose `receive()`/`fallback()` requires more than 2300 gas (e.g. it emits an event, writes storage, or forwards to a proxy), the `transfer()` call unconditionally reverts, permanently trapping that account's SEI inside the WSEI contract with no alternative withdrawal path (no `call()`-based fallback, no `withdrawTo` variant).

### Impact Explanation
Because `withdraw()` is the only mechanism to redeem underlying SEI from WSEI, any smart-contract holder whose receive logic exceeds the 2300 gas stipend permanently loses access to its wrapped funds — this is a permanent freezing of funds for affected accounts, which satisfies the Medium-severity fund-freezing bar. This also risks becoming SEI's canonical WSEI/wrapped-native contract referenced by other pointer/bridge contracts, amplifying impact if integrators build on top of it assuming standard WETH9-style behavior with `call()`-safe withdrawal.

### Likelihood Explanation
Likelihood is limited to accounts that are contracts with gas-heavy fallback/receive logic; ordinary EOAs are unaffected since EOAs need no more than 2300 gas to accept a plain value transfer. However, given WSEI is meant to interoperate with arbitrary EVM contracts (DeFi protocols, proxies, multisigs) on Sei, encountering such contracts is realistic in normal usage, and the same pattern is duplicated in the test/mirrored `evmrpc/solidity/ERC20.sol` and `evmrpc/tests/solidity/ERC20.sol` artifacts.

### Recommendation
Replace the `transfer()` call in `WSEI.withdraw()` with a checks-effects-interactions-safe `call()`:
```solidity
function withdraw(uint wad) public {
    require(balanceOf[msg.sender] >= wad);
    balanceOf[msg.sender] -= wad;
    (bool success, ) = payable(msg.sender).call{value: wad}("");
    require(success, "WSEI: ETH transfer failed");
    emit Withdrawal(msg.sender, wad);
}
```
Apply the equivalent fix to `evmrpc/solidity/ERC20.sol` and its test mirror if those are also used as deployable artifacts.

### Proof of Concept
1. Deploy `WSEI` via `deploy-wsei` CLI (`x/evm/client/cli/tx.go` `CmdDeployWSEI`).
2. Deploy an attacker contract `C` whose `receive()` function performs a costly operation (e.g., `SSTORE` to a new slot, consuming >2300 gas).
3. From `C`, call `WSEI.deposit()` with some value, then call `WSEI.withdraw(wad)`.
4. The internal `payable(msg.sender).transfer(wad)` call from `WSEI` to `C` reverts due to insufficient gas stipend, causing the entire `withdraw` transaction to revert.
5. `C`'s WSEI balance remains locked forever since no alternative withdrawal path exists, demonstrating permanent freezing of funds.
