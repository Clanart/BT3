### Title
Missing point-at-infinity check in `x()` lets a crafted FROST preprocess crash every signer (`crypto.rs`) - (File: `networks/bitcoin/src/crypto.rs`)

### Summary
Analogous to CVE-2024-26881 — where hardware could set a "timestamp valid" bit for a PTP device that was never registered, causing a NULL dereference — `x()` in `networks/bitcoin/src/crypto.rs:13-16` unconditionally `expect`s its input point to be non-infinity. The point is attacker-influenceable through `Hram::hram`, which hashes `x(R)` where `R` is the aggregate FROST nonce built from remote participants' `Preprocess`/`Commitments` bytes accepted via `read_preprocess`.

### Finding Description
`Hram::hram` (`networks/bitcoin/src/crypto.rs:59-73`) computes `x(R)` and `x(A)` before hashing. `x()` calls `encoded.x().expect("point at infinity")`, so any call with `R` (or `A`) equal to the secp256k1 identity panics the entire process — the Rust equivalent of the kernel NULL dereference.

The aggregate nonce `R` is `Σ (D_j + ρ_j·E_j)` over all `included` participants, with `D_j`, `E_j` taken verbatim from each participant's `Preprocess.commitments` (parsed by `Commitments::read` inside `AlgorithmSignMachine::read_preprocess`, `crypto/frost/src/sign.rs:276-281`). `Secp256k1::read_G` uses `G::from_bytes`, which accepts the SEC1 identity encoding (`0x00`), and `Commitments::read` performs no identity rejection.

A participant submitting a preprocess can therefore set both nonce commitments to values that force the aggregate `R` to identity: they observe all other preprocesses first, then choose `E_i = identity` (killing their binding-factor term, so no hash fixed point needs solving) and `D_i = -(Σ contributions of others)`. Both are validly-encoded points. Every honest signer then evaluates `hram(R=∞, A, msg)` inside `sign_share` (`crypto/frost` IetfSchnorr) and inside `AlgorithmSignatureMachine::complete → algorithm.verify` (`crypto/frost/src/sign.rs:465`), panicking in all of them. `TransactionSignMachine::sign`/`complete` in `networks/bitcoin/src/wallet/send.rs:383-397, 417-425` inherits this via the `Schnorr` algorithm wrapper.

### Impact Explanation
One crafted preprocess message aborts every signing node processing it (panic across `sign_share` and `complete`), permanently halting threshold signing for that session and any `TransactionMachine` attempt — a network-reachable denial of service of the whole validator set's Bitcoin signing path, matching the kernel-crash severity of the reference bug.

### Likelihood Explanation
The attacker only needs to be a signing-set participant able to deliver preprocess bytes (explicitly an in-scope untrusted input via `read_preprocess`); no key material, collusion, or privileged position is required, and the commitment forgery is a trivial linear combination once peers' preprocesses are known.

### Recommendation
Reject the identity point in `Commitments::read`/`read_G` usage for nonce commitments, and/or return `FrostError` instead of panicking in `x()`/`x_only()` and `Hram::hram` when `R` or `A` is infinity.

### Proof of Concept
Participant `i` waits for all peers' `Preprocess` messages, computes `S = Σ_{j≠i}(D_j + ρ_j·E_j)`, then submits `Preprocess { commitments: { D_i = −S, E_i = identity } }` (identity encoded as `0x00`). `machines[0].read_preprocess` accepts it; on `sign()`, each node's aggregate `R` is the point at infinity and `Hram::hram` panics at `crypto.rs:15` (`expect("point at infinity")`), crashing the signer.

Note: reachability depends on `Secp256k1::read_G`/`Commitments::read` accepting the SEC1 identity encoding without rejection — consistent with `G::from_bytes` behavior shown at `crypto/dleq/src/cross_group/mod.rs:55-63`, though I could not re-verify `Commitments::read`'s internals in this session. If identity commitments are rejected there, `E_i = identity` fails but the panic path remains for any aggregate `R = ∞`.
