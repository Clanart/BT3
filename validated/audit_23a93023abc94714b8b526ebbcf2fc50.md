### Title
ThresholdKeys deserialization accepts a secret share inconsistent with its verification shares, producing keys that fail signing and misattribute blame to the honest holder - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::new` (and therefore `ThresholdKeys::read`, which parses fully attacker-controlled bytes) validates participant indexes and counts but never checks that `secret_share` actually corresponds to `verification_shares[params.i()]` (`generator * secret_share`). The returned keys are structurally valid yet cryptographically inconsistent: the holder signs with a share that does not match its declared verification share. Analogous to CVE-2024-47766, where a permission check was evaluated against the wrong scope, the consistency check that should bind a participant's private share to its public commitment is simply absent, so invalid keys are "authorized" into the signing protocol.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i`, an interpolation method, a `secret_share` scalar, and `n` verification shares from the wire, then calls `ThresholdKeys::new` (crypto/dkg/src/lib.rs:574-632). `ThresholdKeys::new` only checks:

- `verification_shares.len() == n` (lines 355-360)
- each key `<= n` (lines 361-365)
- interpolation applicability (lines 367-374)

It computes `group_key` by interpolating `verification_shares[1..=t]` (lines 376-378) but never verifies `C::generator() * secret_share == verification_shares[&params.i()]`.

When such a key is used in FROST signing (`crypto/frost/src/sign.rs`), `view()` interpolates the bogus `secret_share` and `sign_share` produces a share inconsistent with the verification share the rest of the group expects for this participant. In `complete()`:

1. `algorithm.verify(group_key, Rs, sum)` fails because the summed share is wrong (line 465).
2. The blame pass verifies every participant's share with `verify_share(view.verification_share(l), B.bound(l), responses[l])` (lines 475-485). The holder's own share fails against `verification_shares[i]`, so the machine returns `FrostError::InvalidShare(own_i)` — the honest node is reported as the faulty party — or, if crafted shares happen to verify individually yet interpolate to a different group key, the code reaches `FrostError::InternalError("everyone had a valid share yet the signature was still invalid")` (line 494).

Callers (e.g. `processor/src/signer.rs`, `coordinator`) propagate `InvalidShare`/`InvalidParticipant` to the consensus layer, where participant-blame leads to slashing — i.e., a malformed key blob causes fault to be attributed to a participant that did nothing wrong, and any funds under the group key are unspendable while the corrupted keys are in use.

### Impact Explanation
An attacker who can influence the serialized `ThresholdKeys` bytes a node loads (e.g., via a compromised/malicious coordinator or any path delivering untrusted bytes to `ThresholdKeys::read`) can:

- render the victim unable to produce valid signatures (liveness/availability loss; group key funds unspendable), and
- cause the blame protocol to identify the *victim* as the faulty signer (`InvalidShare(self)`), the direct analog of the CVE's wrong-scope authorization check.

This is reachable purely through `read`/`verify`-surface inputs and requires no collusion or validator privileges.

### Likelihood Explanation
Requires the attacker to feed crafted bytes to `ThresholdKeys::read` and have those keys used for a signing session. The format is fully attacker-controlled (t, n, i, interpolation, secret share, verification shares are all read verbatim), and no checksum/signature binds share to commitments. Exploitation needs only delivery of the blob plus one signing attempt; impact then deterministically triggers (invalid signature plus self-blame).

### Recommendation
In `ThresholdKeys::new`, enforce `C::generator() * secret_share == verification_shares[&params.i()] * interpolation_factor(i, 1..=t)` (or the appropriate share-to-verification-share relation for the interpolation method), returning a `DkgError` on mismatch. This binds each participant's secret share to its public verification share at construction/deserialization time, preventing inconsistent keys from entering the signing state machine.

### Proof of Concept
```rust
// Craft a ThresholdKeys blob for t=1, n=1, i=1 where verification_shares[1]
// is an honest group's real share/key but secret_share is a random scalar.
let mut bytes = vec![];
bytes.extend((C::ID.len() as u32).to_le_bytes());
bytes.extend(C::ID);
bytes.extend(1u16.to_le_bytes()); // t
bytes.extend(1u16.to_le_bytes()); // n
bytes.extend(Participant::new(1).unwrap().to_bytes()); // i
bytes.push(1); // Lagrange
let bogus_share = C::F::random(&mut rng);
bytes.extend(bogus_share.to_repr().as_ref());
// verification_shares[1] = honest victim's verification share (or any
// point != G * bogus_share, e.g. a victim group key)
bytes.extend(victim_verification_share.to_bytes().as_ref());

let keys: ThresholdKeys<C> =
    ThresholdKeys::read(&mut bytes.as_slice()).unwrap(); // accepted

// keys.group_key() == victim_verification_share, yet secret_share is bogus.
// keys.view([P1]) succeeds; FROST sign() produces an invalid share;
// complete() then returns InvalidShare(P1) — blaming the honest holder —
// or InternalError("everyone had a valid share yet the signature was still invalid").
```
