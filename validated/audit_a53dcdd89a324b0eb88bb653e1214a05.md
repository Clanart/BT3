### Title
Hookify `_extract_field` only recognizes Edit's `new_string` key for the `new_text` field alias, letting malicious `Write` tool content silently bypass block rules - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._extract_field` documents `new_text` as a generic field name usable with the `Edit|Write` tool matcher, but its implementation for `tool_name in ['Write', 'Edit']` only reads `tool_input.get('new_string', '')` for that field, never `tool_input.get('content', '')` which is the key actually used by the `Write` tool. Any hookify block rule written with `field: new_text` (or `field: new_string`) and `tool_matcher: "Edit|Write"` therefore always evaluates against an empty string for `Write` operations, causing dangerous file-write content to never match the rule's pattern.

### Finding Description
`_extract_field` (`plugins/hookify/core/rule_engine.py:182-254`) special-cases `field == 'content'` correctly by falling back across both tool schemas: [1](#0-0) 
but the very next branch for the documented alias `new_text`/`new_string` only checks the `Edit`-specific key: [2](#0-1) 
The `Write` tool's schema never populates `new_string` — it only has `content` and `file_path`. So when `tool_name == 'Write'` and a rule condition targets `field: new_text` (a field explicitly documented in the function's own docstring as a supported field name): [3](#0-2) 
`_extract_field` returns `''` instead of `None`. Back in `_check_condition`, the `is None` short-circuit does not trigger (empty string passes it), so the operator is evaluated against an empty string: [4](#0-3) 
`regex_match('', pattern)` and `contains` both fail to match any real dangerous content, and `_rule_matches` returns `False`, so `evaluate_rules` never places the rule in `blocking_rules`: [5](#0-4) 
An attacker who can influence repository/prompt content that drives Claude Code to prefer the `Write` tool over `Edit` for a file mutation (both are ordinary, unprivileged tool choices the agent makes routinely) can cause a security operator's `field: new_text` block rule to silently never fire, while the semantically identical `Edit` invocation with `new_string` would have been correctly blocked. The tool_matcher gate (`_matches_tool`) correctly admits both tools into rule evaluation, but the field-extraction layer treats only one of the two tool representations of "the content being written" as valid, breaking the intended invariant that a matching block rule reliably denies the protected operation regardless of which of the two equivalent tools is used.

### Impact Explanation
This breaks the hookify plugin's core security guarantee: an operator-authored block rule intended to prevent dangerous file writes (e.g., writing secrets, malicious scripts, or files outside an approved path) can be defeated purely by the operation arriving via `Write` instead of `Edit`, with zero attacker privilege beyond normal repository/prompt content that steers tool selection. The result is unauthorized file writes proceeding despite an active, matching block rule — directly matching the stated Immunefi impact of unauthorized file read/write outside the user-approved workspace or target scope.

### Likelihood Explanation
High feasibility and fully repeatable: the bug is a static, deterministic logic error (dictionary key mismatch), not a race condition or environment-dependent behavior. It only requires: (1) a hookify rule using `field: new_text` (or `new_string`) with a `tool_matcher` including `Write`, which is a documented and reasonable rule-authoring choice given the function's own docstring, and (2) the `Write` tool being invoked instead of `Edit`. No special privileges, timing, or bypass of other checks is needed.

### Recommendation
Fix `_extract_field` so the `new_text`/`new_string` branch (and symmetrically `old_text`/`old_string`) falls back across both tool representations the same way `content` already does, e.g.:
```python
elif field == 'new_text' or field == 'new_string':
    return tool_input.get('new_string') or tool_input.get('content', '')
```
Additionally, consider normalizing tool_input field extraction into a single per-tool mapping table (rather than ad hoc per-field branches) to prevent future drift between aliases, and add regression tests asserting that identical dangerous content triggers the same rule outcome regardless of whether it arrives via `Write` or `Edit`.

### Proof of Concept
Add a unit test to `plugins/hookify/core/rule_engine.py`'s test harness (or a pytest file) that defines a block rule using the generic `new_text` field and asserts consistent blocking across `Write` and `Edit`:

```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

rule = Rule(
    name="block-secret-write",
    enabled=True,
    event="all",
    tool_matcher="Edit|Write",
    conditions=[Condition(field="new_text", operator="contains", pattern="AWS_SECRET_ACCESS_KEY")],
    action="block",
    message="Blocked: secret material in write content",
)
engine = RuleEngine()

# Edit path: correctly blocked today
edit_input = {"tool_name": "Edit", "tool_input": {"file_path": "x.py", "old_string": "a", "new_string": "AWS_SECRET_ACCESS_KEY=abc"}}
assert engine.evaluate_rules([rule], edit_input).get("hookSpecificOutput", {}).get("permissionDecision") == "deny"

# Write path: SAME dangerous content, but tool uses 'content' key
write_input = {"tool_name": "Write", "tool_input": {"file_path": "x.py", "content": "AWS_SECRET_ACCESS_KEY=abc"}}
result = engine.evaluate_rules([rule], write_input)
# BUG: this currently returns {} (no block) instead of denying, proving the bypass
assert result == {}, "Expected bug reproduction: Write bypasses the new_text block rule"
```
Expected behavior after fix: both assertions on `permissionDecision == "deny"` pass identically for `Edit` and `Write`.
