### Title
First-locker reward sniping via instantaneous, non-time-weighted `rewardPerTokenStored` flush of accumulated `queuedRewards` after a zero-`totalStaked()` period - (File: rewards/vlMGPBaseRewarder.sol)

### Summary
`queueNewRewards`/`_queueNewRewardsWithoutTransfer` accumulate incoming rewards into `rewardInfo.queuedRewards` whenever `totalStaked() == 0`, and only convert that bucket into `rewardPerTokenStored` the next time a reward is queued while `totalStaked() > 0`, using the **current** `totalStaked()` as the denominator. Because this update is a single instantaneous snapshot rather than a time-weighted stream, whoever holds the (possibly trivial) `totalStaked()` balance at the moment the flush happens captures the entire multi-epoch queued bucket.

### Finding Description
In `rewards/vlMGPBaseRewarder.sol`:

```solidity
if (totalStaked() == 0) {
    rewardInfo.queuedRewards += _amountReward;
} else {
    if (rewardInfo.queuedRewards > 0) {
        _amountReward += rewardInfo.queuedRewards;
        rewardInfo.queuedRewards = 0;
    }
    rewardInfo.rewardPerTokenStored =
        rewardInfo.rewardPerTokenStored +
        (_amountReward * 10**vlMGPDecimal) / totalStaked();
}
``` [1](#0-0) 

`rewardPerToken()` simply returns the stored value, and `_earned()` computes a user's reward purely as `balance * (rewardPerTokenStored - userRewardPerTokenPaid) / 1e18` — there is no time-integral / streaming rate mechanism like a `periodFinish`/`rewardRate` model: [2](#0-1) 

Because the conversion of `queuedRewards` into `rewardPerTokenStored` happens as a single atomic jump using whatever `totalStaked()` is at that exact call, an attacker can:
1. Wait for (or simply observe) a period where `totalStaked() == 0` (e.g., a new pool before anyone locks, or after all lockers exit) while `rewardManager` continues calling `queueNewRewards`, accumulating multiple epochs of rewards into `queuedRewards`.
2. Call `vlMGP.lock()` (unprivileged, public) with a minimal amount right before the next `queueNewRewards` call, making themselves the sole/dominant holder of `totalStaked()`.
3. When `rewardManager.queueNewRewards(largeAmount, token)` executes, the entire `queuedRewards` bucket plus the new `largeAmount` is divided by the current (attacker-dominated, trivially small) `totalStaked()`, producing a huge `rewardPerTokenStored` jump.
4. Attacker's `earned()` = `balance * delta / 1e18` ≈ the entire flushed bucket, since `balance ≈ totalStaked()` at that instant.
5. Attacker calls `getReward`/`getRewards` (routed through `masterMagpie`, itself callable by any user) to claim the reward immediately, without having contributed any meaningful stake-time.

No existing check mitigates this: there is no minimum lock duration required before earning, no time-weighting of `rewardPerTokenStored` updates, and `updateReward`/`updateRewards` only snapshot balances at call time rather than accounting for how long a balance was held.

### Impact Explanation
This allows theft of previously-queued, would-be-shared yield: legitimate future lockers who contributed to `totalStaked()` over time are diluted or entirely excluded, while the attacker who staked a nominal amount for a moment captures rewards that accrued (or were queued) during a period when they had no real economic exposure. This matches the Immunefi "theft of unclaimed yield" impact class, and can also be leveraged to permanently disadvantage genuine long-term lockers whose share of the pool is arbitrarily diluted by a JIT locker capturing the entire flushed bucket.

### Likelihood Explanation
Requires: (a) `totalStaked() == 0` at least once (natural at pool launch or plausible after exits), (b) `rewardManager` (a normal, expected, non-malicious operational actor) continuing to call `queueNewRewards` during/after that period, and (c) attacker front-running/timing a minimal `lock()` call before the next `queueNewRewards` transaction. Capital required is minimal (dust-level lock amount). This is fully repeatable at every pool launch or whenever `totalStaked()` transiently returns to zero, and requires no privileged role — only public `lock`/`getReward` calls plus transaction-ordering awareness (mempool observation / same-block sequencing), which is standard MEV-style front-running available to any unprivileged actor.

### Recommendation
Replace the instantaneous "queue-and-flush" accounting with a time-weighted reward-rate/duration model (e.g., Synthetix-style `rewardRate` + `periodFinish` + `lastUpdateTime`), so rewards accrue continuously per unit stake-time rather than being dumped in a single snapshot based on `totalStaked()` at an arbitrary instant. At minimum, when converting `queuedRewards` into `rewardPerTokenStored`, require a minimum bonding/lock duration before a balance is eligible for previously-queued rewards, or distribute queued rewards pro-rata over a vesting window instead of instantly.

### Proof of Concept
Foundry test outline (`vlMGPBaseRewarder.t.sol`):
1. Deploy `vlMGPBaseRewarder`, `vlMGP`, `masterMagpie` mocks/stubs as normally wired in existing tests.
2. Ensure `totalStaked() == 0` (no lockers, or all existing lockers withdraw).
3. As `rewardManager`, call `queueNewRewards(amount1, rewardToken)` two or three times across simulated "epochs" — assert `rewards[rewardToken].queuedRewards` accumulates to `amount1*N` and `rewardPerTokenStored` stays `0`.
4. As attacker, call `vlMGP.lock(dustAmount)` so `totalStaked() == dustAmount`.
5. As `rewardManager`, call `queueNewRewards(largeAmount, rewardToken)`.
6. Assert `rewardPerTokenStored` jumped by `(amount1*N + largeAmount) * 1e18 / dustAmount`.
7. Call `getReward`/`getRewards` for attacker via `masterMagpie` and assert `earned(attacker, rewardToken)` (and the amount actually transferred) equals essentially the full `amount1*N + largeAmount` bucket, despite the attacker having staked only `dustAmount` for a single block/transaction.
8. Assert any genuine long-term locker who joins after step 6 receives none of the previously queued rewards, demonstrating the dilution/theft of yield.
