## Finding

`updateSubmodulesAfterOperation()` in `app/src/lib/git/submodule.ts` accepts an `allowFileProtocol` flag that, when `true`, prepends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation: [1](#0-0) 

This function is called from `app/src/lib/git/checkout.ts` (7 references), i.e. it runs automatically as part of Desktop's branch-checkout flow whenever the checked-out tree contains a `.gitmodules` file with uninitialized/changed submodules.

### Title
Desktop bypasses Git's `protocol.file.allow` safeguard when auto-initializing submodules on checkout, enabling arbitrary local file exposure from a malicious repository - (File: app/src/lib/git/submodule.ts)

### Summary
Git added `protocol.file.allow` (default `user`, restricted to `never` for submodules) specifically to stop malicious repositories from using `file://`-scheme submodule URLs in `.gitmodules` to make `git submodule update` clone from arbitrary local paths (the class of bug fixed as CVE-2022-39253, where a crafted local-clone submodule can hardlink/expose files from outside the intended repository). GitHub Desktop's checkout flow deliberately re-enables this disabled protection via `-c protocol.file.allow=always` when `allowFileProtocol` is set, undermining the very guard Git ships by default.

### Finding Description
`updateSubmodulesAfterOperation()` is invoked after checking out a branch (`app/src/lib/git/checkout.ts`) so that any submodules referenced by the new tree get initialized: [2](#0-1) . Test fixtures show Desktop's own test helpers routinely need `protocol.file.allow=always` to add/update local-path submodules (e.g. `app/test/helpers/repositories.ts:288-321`, `app/test/unit/git/pull/pull-test.ts:38-53`), confirming that the "normal" default (`never`) would otherwise block such operations — Desktop chooses to override it. The `.gitmodules` file (and the submodule commit each branch points to) is fully attacker-controlled content coming from a cloned/fetched repository: an attacker can craft a branch whose `.gitmodules` declares a submodule with a `file://` (or bare local-path) URL pointing at a sensitive directory on the victim's disk (e.g. `~/.ssh`, `~/.aws`, or another unrelated repository containing secrets). When the victim opens that branch in GitHub Desktop, `checkoutBranch` triggers `updateSubmodulesAfterOperation` with `allowFileProtocol=true`, and Git executes `submodule update --init --recursive` with the safeguard disabled, happily "cloning" the local target path into the submodule directory inside the victim's working tree.

### Impact Explanation
Because the resulting clone lands inside the user's working directory, its contents become visible in Desktop's Changes/History views and can be committed and pushed by the user — silently exfiltrating file contents from outside the intended repository to wherever the user later pushes (including to a remote controlled by the attacker, if the repo is later synced back). This matches the "file read outside the repo" / "silent corruption of what the user commits" impact classes: the user is not warned that submodule initialization reached outside the project, and the checked-out submodule content is not obviously distinguishable from legitimate submodule content.

### Likelihood Explanation
Triggering this only requires the victim to clone/fetch and check out a branch supplied by an untrusted party — a completely ordinary Desktop workflow, with no local access, admin rights, or social engineering beyond "check out this branch," which is exactly the trust boundary Desktop is meant to protect (the app already warns users about untrusted repositories elsewhere, e.g. `app/src/ui/missing-repository.tsx` and `add-existing-repository.tsx`, confirming this is a recognized threat model). The exact conditions under which `allowFileProtocol` is set to `true` versus `false` at each `checkout.ts` call site could not be fully enumerated in this pass (7 call sites were found but not individually inspected), so it is not confirmed whether every checkout path enables this flag or only some — this should be verified against `app/src/lib/git/checkout.ts` before treating this as unconditionally exploitable.

### Recommendation
Do not pass `protocol.file.allow=always` when initializing submodules for content that originates from an untrusted/remote-controlled `.gitmodules` (i.e., normal checkout of a fetched branch). If local-path submodules must be supported for legitimate local development workflows, gate `allowFileProtocol` behind an explicit, per-repository user opt-in (mirroring the existing "trust this directory" pattern in `missing-repository.tsx`) rather than enabling it implicitly during checkout, and warn the user before initializing a submodule whose URL uses `file://` or a bare local path.

### Proof of Concept
1. Attacker creates a repository/branch containing a `.gitmodules` entry: `[submodule "leak"] path = leak url = file:///home/victim/.ssh` (or an equivalent absolute path known/guessed on the target).
2. Victim clones/fetches this repository in GitHub Desktop and checks out the malicious branch.
3. `checkoutBranch` → `updateSubmodulesAfterOperation(..., allowFileProtocol: true)` runs `git -c protocol.file.allow=always submodule update --init --recursive`, cloning `/home/victim/.ssh` into `leak/` inside the working directory.
4. The victim now has the contents of `~/.ssh` inside their tracked working directory, visible in Desktop's Changes view and stageable/committable/pushable like any other file.

*(Note: exact reachability of `allowFileProtocol=true` for a standard branch-switch checkout versus other flows was not fully confirmed within the available tool calls — verifying the call sites in `app/src/lib/git/checkout.ts` is recommended to confirm the precise trigger conditions.)*
