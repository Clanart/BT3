### Title
Server-Side Request Forgery via unvalidated on-chain DataLayer mirror URLs - (File: chia/data_layer/download_data.py)

### Summary
Any wallet holder can publish arbitrary mirror URLs on-chain for a DataLayer store via the `dl_new_mirror` RPC. Any other node subscribed to that store's DataLayer singleton will later fetch those URLs directly with `aiohttp` in `http_download`, with zero validation of scheme, host, or IP address — a strictly worse SSRF exposure than the CVE-2022-0766 calibreweb bug, which at least attempted an (incomplete) blacklist.

### Finding Description
A wallet owner calls `dl_new_mirror` (`chia/wallet/wallet_rpc_api.py`, dispatched to `DataLayerWallet.create_new_mirror`), which creates an on-chain mirror coin whose puzzle memos encode an arbitrary list of URL bytes with no format or host restriction: [1](#0-0) 

These URLs round-trip through coin memos (`get_mirror_info`) and are persisted by any node's `dl_wallet_store.add_mirror` without validation: [2](#0-1) 

The DataLayer service periodically reads these mirrors and merges them into its subscription server list unfiltered: [3](#0-2) 

During `fetch_and_validate`, it randomly picks one of these server URLs and calls `insert_from_delta_file` → `download_file` → `http_download`, which performs a raw `aiohttp` GET against the attacker-controlled URL with no scheme/host allow-list, no `is_localhost`/private-IP check, and no DNS-resolution guard: [4](#0-3) [5](#0-4) 

Chia already has host-validation helpers (`is_localhost`, `is_in_network`, `is_trusted_cidr` in `chia/util/network.py`), but they are never invoked on this path — confirmed by the absence of any such check in `chia/data_layer/*.py` outside the unrelated S3 plugin. The only existing tests explicitly exercise `127.0.0.1` URLs as valid mirror/server targets: [6](#0-5) [7](#0-6) 

This mirrors the calibreweb CVE-2022-0766 root cause exactly: user-supplied URL data is consumed by an outbound HTTP client without any blacklist/allow-list on target host, enabling SSRF against localhost, link-local metadata endpoints (e.g., `169.254.169.254`), `0.0.0.0`, or internal-network services reachable from the DataLayer node.

### Impact Explanation
Any wallet user (not just node operators) can force every other DataLayer node that subscribes to (or auto-tracks) that store's singleton to make outbound HTTP GET requests to attacker-chosen destinations, including internal-only services, cloud metadata endpoints, or loopback-bound RPC/admin interfaces on the victim's own host. Because `http_download` writes the response body to disk under the DataLayer's server-files directory and feeds it into `insert_into_data_store_from_file`, this is a full SSRF primitive with attacker-controlled response content reaching disk on the victim node — a Critical-severity issue analogous to the referenced CVE.

### Likelihood Explanation
High. Creating a mirror coin only requires normal wallet spend capability (a `dl_new_mirror` transaction, no elevated permission), and any peer tracking the corresponding store's launcher id (which can happen automatically via subscription/offer flows) will eventually attempt to download from the published mirror URL during its normal `periodically_manage_data` loop.

### Recommendation
Before dialing out to any mirror/server URL in `http_download`/`download_file`/`get_downloader`, validate the parsed hostname: reject loopback, link-local, and private/reserved IP ranges (and their string aliases like `0.0.0.0`/`localhost`) using the existing `is_localhost`/`is_in_network` helpers, resolve DNS names first and re-check the resolved IP, and restrict allowed schemes to `http`/`https`. Apply the same validation when persisting mirror URLs (`update_subscriptions_from_wallet`, `dl_wallet_store.add_mirror`) so untrusted URLs never enter the download candidate list at all.

### Proof of Concept
1. Wallet A calls `dl_new_mirror(launcher_id=<store>, urls=["http://169.254.169.254/latest/meta-data/"])` and confirms the transaction on chain.
2. Wallet/DataLayer node B (any node that owns or subscribes to `<store>`) runs `update_subscriptions_from_wallet`, pulling the malicious URL into its server list.
3. On B's next `fetch_and_validate`/`periodically_manage_data` cycle, `http_download` issues a GET to `http://169.254.169.254/latest/meta-data/` with no host-based restriction, as shown in `chia/data_layer/download_data.py:311-319`, exfiltrating/probing internal network resources from node B.
