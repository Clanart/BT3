### Title
Server-controlled repository metadata silently rewrites the local `origin` remote URL, redirecting future pushes/fetches - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
Desktop periodically re-fetches the GitHub API record for a repository's matched account/owner/name and uses the API's `clone_url` to automatically call `git remote set-url` on the user's `origin` remote, with no user confirmation. This mirrors the RealityCards finding: a "parameter update" (the API-reported `clone_url`) is propagated into a critical downstream component (the local git remote configuration) automatically, without an explicit user-approved boundary check, and the guard conditions that exist are insufficient to stop a same-name/owner repository swap from being trusted.

### Finding Description
`updateRemoteUrl` compares the current `defaultRemote.url` against `apiRepo.clone_url` and, if the protocol matches and the previously stored `gitHubRepository.cloneURL` still equals the current remote, silently rewrites the remote: [1](#0-0) 

This function is invoked from `repositoryWithRefreshedGitHubRepository`, which matches the repository to a GitHub account purely by hostname (via `matchGitHubRepository`, which only checks that the remote's hostname matches an account's endpoint hostname) plus owner/name parsed from the existing remote, then calls `api.fetchRepository(owner, name)` and feeds the result straight into `updateRemoteUrl`: [2](#0-1) 

The matching logic itself never re-validates repository identity beyond owner+name string equality: [3](#0-2) 

If the `owner/name` pair on the remote GitHub host is deleted and re-created by a different, attacker-controlled account (a well-known GitHub "repo name squatting" scenario after a rename/deletion/ownership transfer), or if the original repository is renamed and GitHub's redirect resolves `owner/name` to a different actual `clone_url`, the next background refresh will fetch an `IAPIFullRepository` for that `owner/name` whose `clone_url` differs from what's currently configured. Because `remoteUrlUnchanged` only checks that the *previously stored* `gitHubRepository.cloneURL` still matches the local remote (i.e., the user hasn't manually customized the remote) and `protocolsMatch` only checks URL scheme, none of the existing guards verify that the *new* `clone_url` still points to the same underlying repository/owner identity that the user originally trusted. `setRemoteURL` then performs a real `git remote set-url origin <new_url>` with no user prompt or diff shown: [4](#0-3) [5](#0-4) 

This is the direct analog of the report's "parameter updates not propagated" class: the top-level trust decision (user's original clone/add of a specific `origin`) is silently overridden by a downstream automatic sync path that trusts server-reported metadata for an `owner/name` tuple without re-validating ownership continuity.

### Impact Explanation
A successful swap causes silent corruption of the user's outbound git operations: subsequent `git fetch`/`git pull`/`git push` from the Desktop UI operate against the attacker's repository instead of the legitimate one, without any dialog or explicit confirmation shown to the user (the change happens inside a background refresh path, `repositoryWithRefreshedGitHubRepository`, that runs as part of routine repository refresh cycles). Depending on workflow, this can lead to the user pushing commits (and possibly credentials embedded in commit history, CI secrets, etc.) to an attacker-controlled destination, or fetching/pulling attacker-supplied refs and commits into their local checkout.

### Likelihood Explanation
This requires no local access, no admin rights, and no prior malware — only that the attacker control the GitHub `owner/name` namespace once vacated (a real, previously-documented risk class for repo-name reuse/squatting) and that the victim's Desktop background refresh runs against that repository. The `remoteUrlUnchanged` guard reduces likelihood by requiring the user has never manually customized the remote, and `protocolsMatch` restricts cross-protocol swaps — but neither check validates the *actual* repository identity behind the new `clone_url`, so likelihood is moderate rather than trivial, and depends on the specific rename/deletion/re-creation timing on the GitHub side.

### Recommendation
Do not automatically call `setRemoteURL` based solely on API `clone_url` comparison. Instead:
- Compare a stable, unforgeable repository identifier (e.g., GitHub repository `id`) recorded at initial association time against the `id` returned by `fetchRepository`, and refuse to auto-update if the `id` differs even when `owner/name` still match.
- If the `id` differs (repository swap detected), surface an explicit, blocking prompt to the user before ever mutating `origin`, rather than silently invoking `git remote set-url`.
- Treat `updateRemoteUrl`'s automatic remote rewriting as a security-sensitive operation and require user confirmation, consistent with the way explicit remote URL edits in `repository-settings.tsx` behave.

### Proof of Concept
1. User clones `https://github.com/victim-org/example-repo` in Desktop; Desktop stores `gitHubRepository.cloneURL` matching this URL.
2. `victim-org` deletes/renames `example-repo`, and an attacker registers `victim-org/example-repo` is not directly reproducible without org control, so the more realistic path is: repository owner renames the repo, then a different user/org claims the freed `owner/name`, or the same owner recreates the repo pointing to a different underlying `clone_url` (e.g., after a GitHub migration/redirect resolution) — in either case `api.fetchRepository(owner, name)` in `repositoryWithRefreshedGitHubRepository` returns a fresh `IAPIFullRepository` with a `clone_url` different from the one originally stored.
3. On the next periodic repository refresh, `repositoryWithRefreshedGitHubRepository` calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`; since `remoteUrlUnchanged` and `protocolsMatch` both hold true (user never touched the remote, same `https` scheme) and `urlsMatch` is false (URL literally changed), the condition at `update-remote-url.ts:42` is satisfied and `gitStore.setRemoteURL(...)` executes `git remote set-url origin <attacker_clone_url>` with no dialog shown to the user.
4. The user's next `git push`/`git fetch` in Desktop silently operates against the new, unverified `clone_url`. [6](#0-5)

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
