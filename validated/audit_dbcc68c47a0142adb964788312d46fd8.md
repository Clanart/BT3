### Title
Argument injection via unsanitized remote URL in `addRemote`/`setRemoteURL` — (File: `app/src/lib/git/remote.ts`)

### Summary
`app/src/lib/git/remote.ts` builds `git remote add <name> <url>` and `git remote set-url <name> <url>` argument arrays and passes the attacker-influenced `url` value straight to `git` as a positional argument, with no `--` separator and no check that it doesn't start with `-`. This is the same class of bug as the reported Lido `DepositSecurityModule.addGuardian` issue: an externally-controlled value (there, a guardian address; here, a remote URL sourced from the GitHub API) is accepted and used in a security-sensitive operation without a basic validation guard, unlike the sibling function `clone()` in `app/src/lib/git/clone.ts`, which does insert a `--` separator before its URL argument (`args.push('--', url, path)`, `app/src/lib/git/clone.ts:123`) precisely to prevent this class of problem.

### Finding Description
`addRemote` and `setRemoteURL` are: [1](#0-0) [2](#0-1) 

Both pass `url` as a bare positional argument to `git`, with no `--` delimiter separating options from operands. Git's `remote add`/`remote set-url` subcommands accept flags such as `-f`, `-t <branch>`, `-m <master>`, `--mirror=fetch`/`--mirror=push`, `--tags`/`--no-tags`. If the value bound to `url` begins with `-`, `dugite`/git will parse it as an option rather than a URL, changing the semantics of the remote-management operation (e.g., silently making the remote a `--mirror=fetch` remote, or triggering an immediate `-f` fetch as part of “adding a remote”) instead of failing safely.

This function is reachable with values that originate from the GitHub API, not from the local user:
- `GitStore.addUpstreamRemoteIfNeeded` calls `addRemote(this.repository, UpstreamRemoteName, url)` where `url` is `parent.cloneURL`, sourced from the parent-repository object returned by the API: [3](#0-2) 
- `AppStore._findPullRequestBranch` calls `addRemote(repository, forkRemoteName, headCloneUrl)` where `headCloneUrl` is `pull_request.head.repo.clone_url` from the GitHub API pull-request payload: [4](#0-3)  and is invoked from the "open PR in Desktop" deep-link flow via `dispatcher.ts`'s `openPullRequestFromUrl`: [5](#0-4) 

Both of these values are attacker-controllable: anyone can create a fork/PR whose head repository's `clone_url` is whatever string the GitHub API will accept for a repo clone URL field, and a malicious PR link opened via the `x-github-client://openrepo/...pr=...` protocol handler will flow this value into `addRemote` without validation. The check that exists elsewhere in the codebase — e.g., `clone.ts`'s explicit `--` separator, or `parse-app-url.ts`'s `testForInvalidChars` guard on `branch` — is absent here, meaning `remote.ts` is the analog of the "guardian added without validating the address" bug: an externally-sourced string is trusted and consumed by a sensitive subsystem operation without the guard that its sibling code paths already apply.

### Impact Explanation
Successful argument injection into `git remote add`/`git remote set-url` lets an attacker (as the author of a forked repo / PR, without any credentials or local access) alter Desktop's git remote configuration semantics for a victim who simply opens a PR link or lets Desktop create the "upstream"/fork remote automatically. At minimum this corrupts the invariant that "the remote we add points only to the URL we intended" (silent corruption of remote configuration), and depending on the exact flag accepted by the installed git version, it can change fetch behavior (e.g. `--mirror=fetch`) for that remote, which is used immediately afterward for `_fetchRemote` calls in the same flow (`app-store.ts:8686`). This falls within the "silent corruption of what the user commits/pushes/fetches" category from the accepted-impact list, and stems from a git remote/API response the attacker controls.

### Likelihood Explanation
Medium: it requires no special user action beyond opening a fork/PR link or checking out a PR, both are normal Desktop workflows. It requires the attacker to control a forked repository's `clone_url` field is normally just a GitHub-hosted repo path, so full arbitrary-flag values may be constrained by what GitHub accepts as a repo clone URL, but self-hosted/GHES setups or crafted API responses proxied through a malicious/rogue remote or interception increase feasibility. The lack of a guard is a genuine gap relative to the pattern used elsewhere in the same file's sibling `clone.ts`.

### Recommendation
Add the same defense already used in `clone.ts`: insert a `--` separator before the URL argument in both `addRemote` and `setRemoteURL` (e.g. `['remote', 'add', name, '--', url]` is not valid git syntax for this subcommand order — instead validate/reject values starting with `-`):
```ts
if (url.startsWith('-')) {
  throw new Error('Invalid remote URL')
}
```
Apply this check (or equivalent) in `addRemote` and `setRemoteURL` in `app/src/lib/git/remote.ts`, mirroring the zero-address-style guard recommended in the original report.

### Proof of Concept
1. Attacker creates a public fork whose repository object, when read back through the GitHub API `clone_url`/PR `head.repo.clone_url` field, is a string beginning with `-` (e.g., via a crafted/self-hosted GitHub Enterprise instance or a man-in-the-middle on the API response, since GitHub.com itself normally emits well-formed HTTPS URLs, constraining this to non-standard endpoints or response tampering).
2. Attacker sends the victim a "Open in GitHub Desktop" PR link (`x-github-client://openrepo/...&pr=...`) pointing at this PR.
3. Victim's Desktop calls `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch`, which calls `addRemote(repository, forkRemoteName, headCloneUrl)` with the malicious value: [4](#0-3) 
4. `git(['remote', 'add', name, url], ...)` executes with `url` parsed as a git option rather than a remote URL, silently altering the remote's configuration/fetch behavior instead of erroring out cleanly. [1](#0-0) 

Note: I could not fully verify from the index which git versions/flag combinations are accepted for `remote add`'s URL position (this affects exact severity), and I did not find a live exploit chain to code execution — the confirmed, concrete issue is the missing input-validation guard on an API-derived URL used as a positional git argument, mirroring the reported bug class exactly.
