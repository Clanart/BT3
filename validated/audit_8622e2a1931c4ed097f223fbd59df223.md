### Title
Webhook HMAC verification does not bind the `X-Shopify-Shop-Domain` header, allowing forged cross-shop webhook replay - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

### Summary
The `ExecutionParams`/`Validation` bug in the referenced report is a case of a signature scheme covering the wrong (or incomplete) data structure, so the signature verifies but does not actually bind all the fields that are later trusted. `ShopifyApp::WebhookVerification` has the same class of flaw: the HMAC signature is computed and checked only over the raw request body, while the `shop_domain` value that downstream jobs treat as authenticated/trusted is taken from an unsigned HTTP header.

### Finding Description
`ShopifyApp::PayloadVerification#hmac_valid?` computes the HMAC solely over `request.raw_post`: [1](#0-0) 

`ShopifyApp::WebhookVerification#verify_request` uses exactly that check as the sole authentication gate for webhook requests, and separately exposes `shop_domain` read directly from the `X-Shopify-Shop-Domain` header, which is not part of the signed data at all: [2](#0-1) 

Generated webhook jobs (`AppUninstalledJob`, `ShopRedactJob`, `CustomersRedactJob`, etc.) receive this same unauthenticated `shop`/`shop_domain` value and use it directly to look up and mutate shop-scoped state: [3](#0-2) [4](#0-3) 

The declarative webhook controller template wires the raw body and headers straight into `ShopifyAPI::Webhooks::Request`, whose `shop` value is likewise derived from the (unsigned) header, then passed to the job: [5](#0-4) 

Because the app's webhook secret is the app's shared client secret — identical for every shop that installs the app — any merchant that installs the app receives genuinely-HMAC-valid webhooks from Shopify for their own shop's events. Since the header carrying the target shop is excluded from the signed structure, that merchant can replay the same (still-HMAC-valid) request body while substituting an arbitrary `X-Shopify-Shop-Domain` header value naming a different, victim shop that also has the app installed. `hmac_valid?` still returns `true` because the body it hashes hasn't changed, and the app will process the webhook and dispatch the shop-scoped job as if it originated from the victim shop.

### Impact Explanation
An attacker who is merely one of many merchants using the app (not the app operator, not the victim) can forge the shop-domain "identity" of a webhook while keeping a Shopify-issued valid HMAC. Depending on which webhook body/topic is captured and replayed, this allows cross-shop side effects triggered under a victim shop's identity — e.g. replaying an `app/uninstalled` body with the victim's domain drives `AppUninstalledJob#perform` to `Shop.find_by(shopify_domain: shop_domain).destroy` for the victim's shop record/session, and similarly for the redact jobs which call `shop.with_shopify_session`. This is a cross-shop unauthorized-action / session-destruction vector traceable to signed-data/consumed-data mismatch, the same root cause class as the EIP-712 report (verification checks a narrower structure than what is actually relied upon).

### Likelihood Explanation
Reachable from any HTTP request to the app's webhook endpoint with just a body+HMAC pair the attacker legitimately received for their own shop, plus a forged header — no secret compromise, no privileged access, and no interaction with the victim required. The only precondition is that both the attacker's shop and the victim shop have the app installed (so both share the same app client secret used for HMAC), which is the normal operating condition for any multi-tenant Shopify app.

### Recommendation
Bind the shop identity into the authenticated structure instead of trusting an unsigned header: verify the `X-Shopify-Shop-Domain` (or the `shop` value returned by `ShopifyAPI::Webhooks::Request`) against a value derived from/verified with the signed payload (or otherwise cross-check it against the previously stored, legitimate session/shop record before dispatching shop-scoped side effects), and update `ShopifyApp::WebhookVerification`/`PayloadVerification` and the generator job templates so `shop_domain` cannot be supplied independently of the HMAC-covered content.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; Shopify sends a legitimately HMAC-signed webhook (e.g. `app/uninstalled`) with headers `X-Shopify-Hmac-Sha256: <valid>` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Capture the raw POST body and the `X-Shopify-Hmac-Sha256` value.
3. Resend the identical body/HMAC to the app's webhook endpoint, replacing only `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
4. `hmac_valid?(request.raw_post)` in `lib/shopify_app/controller_concerns/payload_verification.rb` returns `true` (body unchanged), `verify_request` passes, and the controller/job processes the webhook using `shop_domain = "victim.myshopify.com"`, e.g. `AppUninstalledJob#perform` destroys the victim's `Shop` record.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

class AppUninstalledJob < ActiveJob::Base
  extend ShopifyAPI::Webhooks::WebhookHandler

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end
