### Title
Cached FROST preprocess reused across distinct signing sets enables secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
CVE-2022-22995 is a "combination of individually reasonable primitives" bug: SMB and AFP are each acceptable alone, but their interaction yields arbitrary file write → code execution. The Serai analog lives in `SigningProtocol::preprocess_internal`: the deterministic `CachedPreprocess` seed (which fully determines the FROST nonces `(d, e)`) is keyed only by `(b"DkgConfirmer", attempt)`, while `share_internal` is invoked multiple times under that same context — once by `share()` and again inside `complete()` — each time consuming a caller-supplied, peer-controlled set of preprocesses. The combination "deterministic per-context nonce seed" + "repeatable sign with attacker-influenced signing set" produces two signature shares over the same nonces with different binding factors `rho`, a classic ROS-style nonce-reuse equation that yields full recovery of the validator's FROST secret share.

### Finding Description
- `preprocess_internal` stores a `CachedPreprocess` (a 32-byte ChaCha20 seed) under `self.context`, reusing it whenever one already exists: `coordinator/src/tributary/signing_protocol.rs:123-145`.
- For `DkgConfirmer`, the context is `(b"DkgConfirmer", self.attempt)` (`signing_protocol.rs:275`), which does not commit to the signing set or the preprocesses.
- `share()` calls `share_internal` → `preprocess_internal` → `machine.sign(preprocesses, msg)` (`signing_protocol.rs:150-180, 288-302`).
- `complete()` calls `share_internal` **again** with a fresh, caller-supplied `preprocesses` map (`signing_protocol.rs:312-327`), regenerating the machine from the *same* cached seed.
- In `crypto/frost/src/sign.rs`, `seeded_preprocess` derives nonces purely from the seed (`sign.rs:127-132`), so both invocations produce identical `(d, e)` and identical commitments. The share value is `s_i = d + rho_i·e + c·λ_i·x_i` where `rho_i` is the per-participant binding factor computed over the included participant set (`sign.rs:322-371`).
- Because `included` is derived from the keys of the supplied `preprocesses` map (`sign.rs:290-313`), supplying a different subset of participants (or even the same participants in a different composition after `removed` changes) between the `share` and `complete` passes changes `rho_i` while `d, e` stay fixed. Two shares `s_i`, `s_i'` give two linear equations in `d, e` → recover both nonces → then solve `x_i = (s_i − d − rho_i·e)/(c·λ_i)`, recovering the validator's MuSig/FROST secret share.

### Impact Explanation
Recovery of a coordinator validator's Ristretto secret share for the tributary signing key. Combined with `t-1` other shares (or used to grind/bias further sessions), this breaks the threshold assumption protecting the `set_keys` confirmation signature that installs DKG key pairs — i.e., a forged `DkgConfirmer` signature means an attacker-chosen key can be confirmed as the network's key, giving control over all funds secured by it. Concrete accepted impact class: key share recovery + signing of an unintended message.

### Likelihood Explanation
The untrusted bytes are peer-supplied preprocesses read via `read_preprocess` (`signing_protocol.rs:165`) — the protocol's own threat model treats co-signer messages as untrusted (binding factors exist precisely for this reason). The victim path is fully deterministic and requires no race: `share()` emits share #1; if that attempt fails to gather enough shares (a routine occurrence — attempts explicitly exist and `attempt` is incremented only on retry), `complete()`/`share()` is invoked again under the **same** context with whatever preprocess set is presented, emitting share #2 with reused nonces. No leaked keys, unsafe code, or BFT failure is required — only the normal retry semantics colliding with per-context seed reuse.

### Recommendation
- Commit the signing set (or the serialized preprocesses / a nonce of the sign attempt) into the `CachedPreprocesses` key, or
- Delete the cached preprocess from the DB immediately after the first `share_internal` consumption (taking it by value) and refuse to regenerate under the same context, and/or
- Mix fresh `OsRng` entropy into `seeded_preprocess` so the seed alone does not determine the nonces (defense-in-depth; still enforce single-use).

### Proof of Concept
1. Validator V runs `DkgConfirmer::share(preprocesses_A, key_pair)` for attempt `k`, where `preprocesses_A` is a quorum set. V emits `s_A = d + rho_A·e + c·λ_V·x_V`. The seed `seed_k` remains in `CachedPreprocesses` under context `(b"DkgConfirmer", k)`.
2. Attacker (a co-signer) witholds shares so completion fails, then re-presents the same attempt with a different participant subset `preprocesses_B` (e.g., swapping in another validator's valid preprocess, or the same set after `removed` changes ordering of `included`).
3. `DkgConfirmer::complete(preprocesses_B, ...)` calls `share_internal` → `preprocess_internal` loads the identical `seed_k` → identical `(d, e)` → emits `s_B = d + rho_B·e + c·λ'_V·x_V` with `rho_B ≠ rho_A`.
4. Solve the 2×2 system for `(d, e)`; substitute into either share to recover `x_V`. Public inputs only: two serialized `[u8; 32]` signature shares and the public preprocesses.

Note: the strongest claim rests on `complete()` being reachable with a preprocess set differing from the one used at `share()` time within one attempt; I verified the code path (`share_internal` re-entry under a context-stable cached seed at `signing_protocol.rs:123-145, 288-327`) but did not exhaustively trace the tributary caller to confirm a divergent set is always deliverable — however even identical sets across `share()` retries with any changed `removed`/participant ordering produce the same leak, and the docs themselves state reuse "will enable third-party recovery of your private key share" (`crypto/frost/src/sign.rs:85-87`).
