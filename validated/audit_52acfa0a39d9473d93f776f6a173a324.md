### Title
`CitreaClient` Ignores `bridge_contract_address` Config Field, Always Uses Hardcoded Constant — (`core/src/citrea.rs`)

---

### Summary

`CitreaClient::new()` and `get_storage_proof()` unconditionally use the compile-time constant `BRIDGE_CONTRACT_ADDRESS` instead of the `bridge_contract_address` field present in `BridgeConfig`. The `CitreaClientT::new()` trait signature does not accept a contract address parameter at all. Any operator who configures `bridge_contract_address` in their environment or TOML file believes they are controlling which contract is queried, but the value is silently discarded. If the bridge contract address ever differs from the hardcoded constant — due to a redeployment, network migration, or misconfiguration — all deposit tracking, withdrawal tracking, and EVM storage proof fetching will silently target the wrong contract.

---

### Finding Description

In `core/src/citrea.rs`, a module-level constant is declared:

```rust
pub const BRIDGE_CONTRACT_ADDRESS: &str = "0x3100000000000000000000000000000000000002";
``` [1](#0-0) 

`CitreaClient::new()` instantiates the on-chain contract binding using this hardcoded constant, not the caller-supplied configuration:

```rust
let contract = BRIDGE_CONTRACT::new(
    BRIDGE_CONTRACT_ADDRESS
        .parse()
        .expect("Correct contract address"),
    provider,
);
``` [2](#0-1) 

The same constant is used again in `get_storage_proof()` when fetching EVM storage proofs:

```rust
let response: serde_json::Value = self
    .client
    .get_proof(
        BRIDGE_CONTRACT_ADDRESS,
        vec![...],
        ...
    )
    .await
``` [3](#0-2) 

Meanwhile, `BridgeConfig` exposes a fully configurable `bridge_contract_address: String` field: [4](#0-3) 

This field is read from the environment variable `BRIDGE_CONTRACT_ADDRESS` and from TOML config files: [5](#0-4) 

But the `CitreaClientT::new()` trait method signature accepts only `citrea_rpc_url`, `light_client_prover_url`, `chain_id`, `secret_key`, and `timeout` — no `bridge_contract_address` parameter: [6](#0-5) 

The `Verifier::new()` call site passes `config.citrea_rpc_url`, `config.citrea_light_client_prover_url`, and `config.citrea_chain_id` to `CitreaClient::new()`, but `config.bridge_contract_address` is never forwarded: [7](#0-6) 

---

### Impact Explanation

The `CitreaClient` is the sole source of truth for three bridge-critical data paths:

1. **`collect_deposit_move_txids`** — reads deposit txids from the bridge contract. If the wrong contract is queried, no deposits are returned, causing all pending deposits to be permanently missed and BTC to be locked in the deposit address. [8](#0-7) 

2. **`collect_withdrawal_utxos`** — reads withdrawal UTXOs from the bridge contract. If the wrong contract is queried, no withdrawals are returned, halting all payout processing. [9](#0-8) 

3. **`get_storage_proof`** — fetches EVM storage proofs that are embedded in the operator's assert transactions and verified inside the bridge circuit. If the proof is fetched from the wrong contract address, the state root and storage slots will not match the actual bridge state, making every assert transaction trivially disprovable by a challenger, exposing the operator's full collateral to slashing. [10](#0-9) 

---

### Likelihood Explanation

The hardcoded address `0x3100000000000000000000000000000000000002` matches the current deployment. However:

- The existence of `bridge_contract_address` in `BridgeConfig` — read from env and TOML — signals that the developers intended this to be runtime-configurable. The field is present in every config file and example. [11](#0-10) [12](#0-11) 

- Any operator who sets `BRIDGE_CONTRACT_ADDRESS` to a non-default value (e.g., for a testnet deployment, a contract upgrade, or a multi-network setup) will silently receive no effect. The system will continue querying the hardcoded address with no error, no warning, and no indication that the configured value is being ignored.

- The discrepancy is a latent correctness bug that becomes a fund-impacting failure the moment the live contract address diverges from the compile-time constant.

---

### Recommendation

1. Add `bridge_contract_address: String` as a parameter to `CitreaClientT::new()` and pass `config.bridge_contract_address` at every call site.
2. Use the passed address — not the module-level constant — when constructing `BRIDGE_CONTRACT::new(...)` and when calling `get_proof(...)`.
3. Remove or demote `BRIDGE_CONTRACT_ADDRESS` to a test-only default, or eliminate it entirely in favor of the config-supplied value.

---

### Proof of Concept

1. Set `BRIDGE_CONTRACT_ADDRESS=0xdeadbeefdeadbeefdeadbeefdeadbeefdeadbeef` in the environment.
2. Start a verifier or operator node.
3. Observe that `CitreaClient::new()` still binds to `0x3100000000000000000000000000000000000002` (the hardcoded constant), not the configured address.
4. All calls to `collect_deposit_move_txids`, `collect_withdrawal_utxos`, and `get_storage_proof` target the hardcoded address, silently ignoring the operator's configuration.
5. On a deployment where the actual bridge contract lives at the configured address, deposits and withdrawals are never detected, and storage proofs are fetched from an address with no relevant state, causing every operator assert to be disprovable and operator collateral to be slashable.

    async fn collect_deposit_move_txids(
        &self,
        last_deposit_idx: Option<u32>,
        to_height: u64,
    ) -> Result<Vec<(u64, Txid)>, BridgeError> {
        let mut move_txids = vec![];

        let mut start_idx = match last_deposit_idx {
            Some(idx) => idx + 1,
            None => 0,
        };

        loop {
            let deposit_txid = self
                .contract
                .depositTxIds(U256::from(start_idx))
                .block(BlockId::Number(BlockNumberOrTag::Number(to_height)))
                .call()
                .await;
            match deposit_txid {
                Err(e) if e.to_string().contains("execution reverted") => {
                    tracing::trace!("Deposit txid not found for index, error: {:?}", e);
                    break;
                }
                Err(e) => return Err(e.into()),
                Ok(_) => {}
            }
            tracing::info!("Deposit txid found for index: {:?}", deposit_txid);

            let deposit_txid = deposit_txid.expect("Failed to get deposit txid");
            let move_txid = Txid::from_slice(deposit_txid._0.as_ref())
                .wrap_err("Failed to convert move txid to Txid")?;
            move_txids.push((start_idx as u64, move_txid));
            start_idx += 1;
        }
        Ok(move_txids)
    }

    async fn collect_withdrawal_utxos(
        &self,
        last_withdrawal_idx: Option<u32>,
        to_height: u64,
    ) -> Result<Vec<(u64, OutPoint)>, BridgeError> {
        let mut utxos = vec![];

        let mut start_idx = match last_withdrawal_idx {
            Some(idx) => idx + 1,
            None => 0,
        };

        loop {
            let withdrawal_utxo = self
                .contract
                .withdrawalUTXOs(U256::from(start_idx))
                .block(BlockId::Number(BlockNumberOrTag::Number(to_height)))
                .call()
                .await;
            match withdrawal_utxo {
                Err(e) if e.to_string().contains("execution reverted") => {
                    tracing::trace!("Withdrawal utxo not found for index, error: {:?}", e);
                    break;
                }
                Err(e) => return Err(e.into()),
                Ok(_) => {}
            }
            let withdrawal_utxo = withdrawal_utxo.expect("Failed to get withdrawal UTXO");
            let txid = withdrawal_utxo.txId.0;
            let txid =
                Txid::from_slice(txid.as_ref()).wrap_err("Failed to convert txid to Txid")?;
            let vout = withdrawal_utxo.outputId.0;
            let vout = u32::from_le_bytes(vout);
            let utxo = OutPoint { txid, vout };
            utxos.push((start_idx as u64, utxo));
            start_idx += 1;
        }
        Ok(utxos)
    }
