## Analysis Result

I found a concrete analog. The `create_payout_txhandler` builds the operator-fronted payout tx with the user's `SinglePlusAnyoneCanPay`-signed input (only input 0), and adds an unsigned OP_RETURN output containing an arbitrary `operator_xonly_pk` that is never authenticated by that operator's key. The `SinglePlusAnyoneCanPay` sighash only commits the withdrawer's signature to input 0 and the output at the same index, so any third party can fund/complete this transaction and attach any operator's x-only pubkey to the OP_RETURN. The bridge (`update_finalized_payouts` / `is_kickoff_malicious`) reads that OP_RETURN value as the "party who fronted the withdrawal" and credits that operator with reimbursement rights — without ever checking a signature from the claimed operator. ### Title
Unauthenticated operator attribution in payout OP_RETURN allows crediting an operator that never fronted the withdrawal - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` embeds `operator_xonly_pk` into an OP_RETURN output that is not covered by any signature (the only signature present is the withdrawer's `SinglePlusAnyoneCanPay` signature over input 0), so anyone funding/broadcasting the payout transaction can name any operator as the payer.

### Finding Description
The payout tx has: input 0 = the withdrawer's dust UTXO signed with `SinglePlusAnyoneCanPay`, output 0 = user's payout, an anchor output, and an OP_RETURN output carrying `operator_xonly_pk.serialize()` [4](#0-3) . `SinglePlusAnyoneCanPay` commits only to the signed input and the corresponding-index output; it does not commit to the OP_RETURN output or to any additional funding inputs added later (e.g. by `fund_raw_transaction`/RBF in `Operator::withdraw`) [5](#0-4) . Any actor who has (or intercepts) the user's presigned withdrawal signature and outpoint can therefore construct and broadcast an equivalent transaction that pays the user from their own funds but stamps a different operator's x-only pubkey into the OP_RETURN.

The verifier's block sync then parses this OP_RETURN to attribute the payout to an operator and persists it as `payout_payer_operator_xonly_pk` [6](#0-5) . That value is later used to authorize `handle_finalized_payout`/kickoff reimbursement for that operator and to validate kickoffs via `is_kickoff_malicious`, which explicitly trusts the OP_RETURN-embedded pubkey as proof of who paid [3](#0-2) . Nothing in this path requires a signature from the named operator; the equality the protocol implicitly relies on — "operator named in OP_RETURN == operator who actually fronted the funds" — is not enforced cryptographically.

### Impact Explanation
Breaks the "operator credited versus the party that paid" custody binding. If exploited, an operator (or any funder) can be credited for a peg-out reimbursement it never funded, or conversely a party can grief a rival operator by attributing a self-funded payout to that operator's pubkey, causing them to be treated (for kickoff/challenge purposes) as the payer without having advanced any funds, or preventing the true funder from claiming the vault's reimbursement. This matches the Critical criterion "an operator reimbursed for a payout it never funded."

### Likelihood Explanation
Requires knowledge of the user's off-chain presigned withdrawal signature/outpoint (available to any operator that receives it, or to anyone who can observe/relay it, since it is handed to operators off-chain per the withdrawal flow) and the ability to broadcast a Bitcoin transaction — no privileged role, key compromise, or majority stake is needed. This is a plausible unprivileged-attacker path (or rival-operator griefing path) once the withdrawal signature is known.

### Recommendation
Require the named operator to sign (or otherwise cryptographically authenticate, e.g. via a covering signature over the whole transaction/OP_RETURN, or a separate operator signature checked at DB-sync time) the claim that it fronted a given payout, instead of trusting an unauthenticated OP_RETURN field. Alternatively, bind the OP_RETURN commitment inside the SIGHASH_ALL portion signed by the actual funding operator.

### Proof of Concept
1. Obtain a withdrawal's presigned `input_signature`/`input_outpoint` (as given to operators in the normal withdraw flow, see `Operator::withdraw` at `core/src/operator.rs:560-637`).
2. Construct a payout transaction using `create_payout_txhandler` logic but pass an arbitrary `operator_xonly_pk` (e.g. a rival operator's key) instead of your own.
3. Fund the transaction (add your own additional input(s) covering fees/amount) and broadcast it; the `SinglePlusAnyoneCanPay` signature on input 0 remains valid because it does not cover the OP_RETURN output or the extra funding input.
4. Once finalized, `update_finalized_payouts` records the named (rival) operator as `payout_payer_operator_xonly_pk` [7](#0-6) , and later kickoff/reimbursement logic treats that operator as the legitimate payer [3](#0-2) , despite them never having funded the payout.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
