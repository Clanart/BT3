### Title
`SignableTransaction` trusts the declared `TxOut` value inside deserialized `ReceivedOutput`s instead of the UTXO's real value - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The GlmRouter bug treated a raw token amount as its real value without consulting the authoritative price. The same class exists in `networks/bitcoin`: `SignableTransaction::new` treats the `value` field embedded in each `ReceivedOutput` — bytes that may originate from `ReceivedOutput::read` over an untrusted stream — as the real amount locked in the referenced UTXO. That declared value drives the solvency check (`NotEnoughFunds`), change/dust computation, and, critically, the BIP-341 sighash that the FROST multisig signs via `Prevouts::All`. No code in `networks/bitcoin/src/wallet` ever reconciles `output.value` against the actual on-chain prevout amount.

### Finding Description
`ReceivedOutput::read` deserializes `output` as an arbitrary `TxOut` (`networks/bitcoin/src/wallet/mod.rs:122-133`), so `output.value` is fully attacker-controlled and is not bound to the `outpoint` it accompanies. `SignableTransaction::new` then sums `inputs.iter().map(|input| input.output.value.to_sat())` into `input_sat` (`send.rs:175`) and uses it to decide solvency (`send.rs:215`) and the change amount (`send.rs:228-234`). The same fabricated `TxOut`s are stored in `self.prevouts` (`send.rs:253`) and committed into every input's signature via `cache.taproot_key_spend_signature_hash(i, &Prevouts::All(&self.tx.prevouts), ...)` (`send.rs:373-390`). The `multisig` constructor only verifies `prevouts[i].script_pubkey` matches the offset group key (`send.rs:277`) — the amount is never authenticated.

Concretely, an attacker who can feed bytes to `ReceivedOutput::read` (or otherwise supply a `ReceivedOutput` to `SignableTransaction::new`) declares `value = X` while the real UTXO holds `Y`:

- `X > Y`: the `NotEnoughFunds` gate is bypassed, a change output may be created that doesn't exist in reality, and the threshold signature commits to a prevout amount the chain rejects — the resulting transaction can never confirm, yet its `txid()` is the `Eventuality` tracked by the processor.
- `X < Y`: same — the sighash commits to a wrong amount and the signed transaction is invalid, while inputs are consumed from the plan.

Either way the multisig produces a threshold signature over a sighash whose `hash_amounts` preimage does not reflect the real value of the coins — the direct analog of "the amount used for the check does not represent the real value".

### Impact Explanation
An unprivileged party that supplies a crafted `ReceivedOutput` causes the threshold set to produce Schnorr/FROST signature shares and a final signed transaction committing to fabricated input amounts. The transaction is unbroadcastable (consensus verifies the committed amounts against the actual prevouts), so the inputs are burned from the scheduler/eventuality perspective — `signable_transaction` derives the `Eventuality` from `signable.txid()` (`processor/src/networks/bitcoin.rs:828-833`) — permanently stalling those funds and the associated payments until manual recovery. This satisfies "concrete signing of an unintended message": validators sign a message asserting prevout values that do not exist.

### Likelihood Explanation
Reachability requires untrusted bytes reaching `ReceivedOutput::read` / `SignableTransaction::new`. `Output::read` in `processor/src/networks/bitcoin.rs:145-166` wraps `ReceivedOutput::read`, and serialized outputs cross processor/coordinator boundaries in plan inputs; the report rules explicitly classify `ReceivedOutput::read` bytes as untrusted. The honest path (`Scanner::scan_transaction`) copies the real on-chain `TxOut`, so the flaw only triggers on the untrusted-deserialization path — consistent with Medium severity: no direct theft (the signature is only valid for the fabricated amounts, which cannot match a different profitable spend), but reliable signing of an invalid message and fund stalling.

### Recommendation
Bind the declared amount to reality before signing: either (a) verify each input's `TxOut` against the chain (fetch the prevout by `outpoint` and compare `value`/`script_pubkey`) inside `SignableTransaction::new` or `multisig`, or (b) treat `ReceivedOutput` as attestable only when produced by `Scanner` and refuse deserialization-originated inputs in the signing path — e.g., carry an authenticity tag that `read` clears and `multisig` requires. At minimum, document that `SignableTransaction::new` must only be called with chain-verified `ReceivedOutput`s.

### Proof of Concept
```rust
// A real UTXO exists at outpoint `op` worth 100_000 sats, paying to the
// multisig's P2TR script for offset ZERO.
let real: ReceivedOutput = scanner.scan_transaction(&tx).swap_remove(0);
assert_eq!(real.value(), 100_000);

// Attacker crafts bytes claiming the same outpoint/script but 1 sat.
let mut forged = real.clone();
forged.output.value = Amount::from_sat(1);          // declared ≠ real
let bytes = forged.serialize();
let input = ReceivedOutput::read(&mut bytes.as_slice()).unwrap(); // accepted

// Solvency/change math uses the declared value.
let stx = SignableTransaction::new(
    vec![input],
    &[(p2tr_script_buf(attacker_addr).unwrap(), 600)], // DustPayment: 600 >= 546
    None, None, 20,
);
// With claimed value 1 this errors NotEnoughFunds; with claimed value
// u64::MAX it produces a "valid" SignableTransaction...
let mut huge = real.clone();
huge.output.value = Amount::from_sat(1_000_000_000);
let stx = SignableTransaction::new(vec![huge], &payments, Some(change), None, 20).unwrap();

// The multisig signs a sighash committing to 1_000_000_000 sats for a
// 100_000-sat UTXO: a valid FROST signature over a message that asserts
// value which does not exist; the resulting tx can never confirm, yet
// `stx.txid()` is registered as the plan's Eventuality.
let _signed = sign(&keys, &stx); // consumes inputs, emits signature shares
```
