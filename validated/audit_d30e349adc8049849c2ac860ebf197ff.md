### Title
Unhandled type-cast exception when parsing an untrusted offer crashes wallet offer processing - (File: chia/wallet/trading/offer.py)

### Summary
`Offer.from_spend_bundle` (invoked transitively by `Offer.from_bytes`, `Offer.from_bech32`, and thus by `TakeOffer.parsed_offer`, `WalletRpcApi.take_offer`, `TradeManager.check_offer_validity`, and any code that inspects an offer received from a counterparty) blindly casts the first element of each "payment group" in a settlement-payment coin spend's solution to an atom via `bytes32(payment_group.first().as_atom())`. Because the offer/spend-bundle bytes are fully attacker-controlled (a malicious offer-file creator crafts their own dummy settlement coin spend inside the offer), `payment_group.first()` can be a cons-pair instead of an atom, causing `Program.as_atom()` to raise an unhandled `ValueError`. This mirrors the Mattermost bug class: untrusted structured input contains a field that is assumed to be one type (string/atom) but isn't, and the unhandled type-cast failure crashes the code path that processes it (here, wallet offer parsing rather than a webapp render).

### Finding Description
`Offer.from_spend_bundle` in `chia/wallet/trading/offer.py` parses the “requested payments” portion of an offer by iterating the solution of each dummy coin spend whose parent is `bytes32.zeros`: [1](#0-0) 

For each `payment_group` in `Program.from_serialized(coin_spend.solution).as_iter()`, the code does: [2](#0-1) 

`nonce = bytes32(payment_group.first().as_atom())` assumes `payment_group.first()` is always a CLVM atom. `Program.as_atom()` is defined to raise `ValueError("expected atom")` whenever the node is a pair rather than an atom: [3](#0-2) 

There is no `try/except` around this specific line in `from_spend_bundle`, unlike the deliberately defensive parsing seen elsewhere in the codebase for similarly untrusted CLVM data (e.g. `chia/wallet/util/compute_memos.py` explicitly checks `type(condition[3]) is not list` before using it, and `chia/wallet/conditions.py`'s `CreateCoin.from_program` wraps its parsing in a `try/except ValueError`). Because an offer file is fully attacker-authored serialized CLVM (the "dummy" settlement coin spend and its solution are chosen entirely by the offer creator), the offer creator can set `payment_group` to `((<pair> . <rest>) ...)` so that `.first()` returns a pair, not an atom, triggering the unhandled exception the moment any code calls `Offer.from_bytes`/`Offer.from_bech32` on that data.

This parsing path is reached by, at minimum:
- `TakeOffer.parsed_offer` (`cached_property` used by the wallet RPC `take_offer` endpoint) — [4](#0-3) 
- `TradeManager`/`WalletRpcApi` offer-summary and offer-validity flows that call `Offer.from_bytes`/`Offer.from_bech32` on offer strings supplied by a counterparty or read from disk/CLI.
- Data Layer's `take_offer` flow, which also parses a caller-supplied `offer_bytes` via `TradingOffer.from_bytes` (analogous parsing) before processing.

### Impact Explanation
Any wallet user, CLI operator, or GUI client that attempts to inspect, validate, or take an offer supplied by an untrusted counterparty can be handed a crafted offer file that raises an unhandled `ValueError` deep inside `Offer.from_bytes`. Depending on the call site, this manifests as:
- An unhandled exception surfacing through the wallet RPC endpoint (`take_offer`, offer-summary style endpoints), producing a request failure/500-style error for that RPC call and potentially destabilizing the async task processing wallet state if not caught by an outer handler.
- A crash of CLI tooling (`chia wallet take_offer`/`get_offer_summary`) that a user runs against an untrusted offer file.

This is a genuine "spend/offer processing halt" analogous to the Mattermost webapp crash: an unprivileged offer counterparty can hand a victim a single crafted (but otherwise well-formed) offer file/bech32 string that halts normal transaction-processing UX for that offer without requiring any signature validity or actual on-chain broadcast. It does not by itself allow theft or fund loss, which keeps it at Medium severity, consistent with the CVSS profile of the source advisory (availability impact only, no confidentiality/integrity impact).

### Likelihood Explanation
High likelihood of triggering: constructing an offer with a non-atom first element in a payment group requires only assembling CLVM by hand (no cryptographic signature is required for the "requested_payments" portion of an offer, since it's simply a solution to a leftover dummy `OFFER_MOD` coin spend with parent `zeros`). Any user willing to send/share an offer file (a normal, expected trading interaction) can trigger this in any counterparty that opens/inspects/takes the offer.

### Recommendation
Harden `Offer.from_spend_bundle` (and any equivalent Data Layer `TradingOffer.from_bytes` path) to validate CLVM shapes before casting:
- Check `payment_group.first().atom is not None` (or wrap the `bytes32(...as_atom())` call in a `try/except ValueError`) before constructing `nonce`, mirroring the defensive pattern already used in `chia/wallet/util/compute_memos.py` and `CreateCoin.from_program`'s `try/except ValueError`.
- On failure, raise a clear, caught `ValueError`/`ValidationError` (e.g., "Invalid offer: malformed payment group") at the API boundary (`take_offer`, `get_offer_summary`, CLI commands) so it is reported as a normal validation error rather than an unhandled exception, and ensure wallet RPC handlers uniformly catch and translate such parsing exceptions into RPC error responses instead of letting them propagate.

### Proof of Concept
1. Construct a `WalletSpendBundle` containing one "dummy" `CoinSpend` whose `coin.parent_coin_info == bytes32.zeros` and whose `puzzle_reveal` is any accepted settlement/offer puzzle (`OFFER_MOD` or a CAT/NFT-wrapped variant recognized by `match_puzzle`).
2. Set that coin spend's `solution` to serialized CLVM of the form `(((0x1122 . 0x3344) (<puzzle_hash> <amount>)))` — i.e., a list containing one `payment_group` whose `.first()` is a cons pair `(0x1122 . 0x3344)` rather than a plain atom.
3. Serialize the bundle to bytes / bech32 (`offer.compress()`/`to_bech32()` equivalent, or directly craft the raw bytes matching `WalletSpendBundle.from_bytes` format) and hand it to a victim as an "offer" (e.g., via `chia wallet take_offer` or the `take_offer`/`get_offer_summary` RPC).
4. When the victim's wallet calls `Offer.from_bytes(offer_bytes)` → `Offer.from_spend_bundle(bundle)`, the line `nonce = bytes32(payment_group.first().as_atom())` executes `payment_group.first().as_atom()` on the crafted pair node, raising `ValueError: expected atom` (from `chia/types/blockchain_format/program.py` lines 224-228), which is unhandled in `from_spend_bundle`, crashing/erroring the offer-processing call.
