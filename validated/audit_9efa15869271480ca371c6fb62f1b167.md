### Title
Wildcard-allowance/asset-name collision lets `restrict-assets?`/`as-contract?` allowances for one real fungible/non-fungible token silently authorize movement of a differently-named token whose name happens to be the literal `*` sentinel - (File: clarity/src/vm/functions/post_conditions.rs)

### Summary
`check_allowances` represents "allow any asset in this contract" using a synthetic `AssetIdentifier` whose `asset_name` field is the literal string `*`, built via `ClarityName::from_literal("*")`. Because Clarity's name grammar explicitly permits `*` as a stand-alone valid token name (`^[-+=/*]$` in `CLARITY_NAME_REGEX_STRING`), a contract can define a real fungible or non-fungible token whose actual `asset_name` is `*`. The allowance-matching code then cannot distinguish "wildcard meaning any asset" from "the literal asset literally named `*`" because both are represented by the same `AssetIdentifier` value and looked up from the same `HashMap` key.

### Finding Description
In `check_allowances` (`clarity/src/vm/functions/post_conditions.rs`), FT allowances are indexed by `AssetIdentifier` in `ft_allowances: HashMap<AssetIdentifier, Vec<(usize, u128)>>`, and lookups for a moved asset first check the exact `AssetIdentifier`, then separately check a synthesized wildcard key with `asset_name: ClarityName::from_literal("*")` for the same contract: [4](#0-3) 
The same pattern is used for NFTs: [5](#0-4) 

The `HashMap` key is a plain `AssetIdentifier { contract_identifier, asset_name }` — there is no separate `is_wildcard` flag distinguishing "the allowance author wrote `*` as a wildcard" from "the allowance author's or contract's asset happens to be named `*`". If a contract exposes (or an attacker deploys) a fungible/non-fungible token whose real `asset_name` is the single character `*` — which the grammar in `clarity-types/src/representations.rs` line 52 explicitly allows — then:
- An `Allowance::Ft`/`Allowance::Nft` entry for the *real* asset named `*` and a synthetic wildcard entry for *all other assets in the same contract* become indistinguishable at the `HashMap` key level, since both produce the identical `AssetIdentifier{contract_identifier, asset_name: "*"}`.
- Consequently, a `restrict-assets?`/`as-contract?` allowance that a contract author intends to authorize only transfer of the specific token named `*` will, due to the merge logic in `check_allowances`, also be treated as authorizing movement of *every other* fungible/non-fungible asset in that same contract (because the code path that inserts the wildcard-keyed entry is reached whenever `nft_allowances`/`ft_allowances` contains an entry under the literal `*` key, regardless of whether that entry was created via genuine wildcard allowance syntax or via an allowance for the real token literally named `*`).

### Impact Explanation
This breaks the equality that "an asset moves only up to what its allowance/post-condition explicitly authorized" — the core guarantee `restrict-assets?`/`as-contract?` allowances (and, by extension, everything gating transfers inside a protected scope) are supposed to provide. A contract or attacker-controlled token contract that defines an asset named `*` can cause an allowance intended for one specific token to be silently broadened to cover all fungible/non-fungible assets transferred within that contract during the protected scope, letting assets move past what the post-condition/allowance was meant to restrict. This matches the "asset moving past its post-conditions" High/Critical impact category.

### Likelihood Explanation
Exploitability requires a contract (attacker-deployed or otherwise) to define a token literally named `*`, which the Clarity grammar permits without restriction, and for a `restrict-assets?`/`as-contract?` allowance list to reference that same contract with an `allow-ft`/`allow-nft` naming the `*` token specifically or generically. This is a narrow but concrete precondition entirely reachable by any unprivileged contract deployer — no miner, signer, or other account's key is required.

### Recommendation
Represent the "any asset in this contract" wildcard as a distinct enum discriminant / sentinel type rather than overloading a valid `ClarityName` value, so it can never collide with a legitimately-named asset. Alternatively, reject `*` as a valid `asset_name` for genuine token definitions, or use a `HashMap` keyed on `(AssetIdentifier, is_wildcard: bool)` so wildcard and exact-name allowances cannot alias each other.

### Proof of Concept
1. Deploy a SIP-010/SIP-009 contract `evil.clar` that defines a fungible token via `(define-fungible-token * u1000000)` (or similarly named NFT) — valid per `CLARITY_NAME_REGEX_STRING`'s `^[-+=/*]$` branch.
2. Also define a second, unrelated fungible token `(define-fungible-token real-token u1000000)` in the same contract.
3. Write a caller contract using `(as-contract? ((allow-ft 'SP...evil.* u10)) (contract-call? .evil ...))`, granting an allowance for the token literally named `*`.
4. Inside the protected scope, transfer `real-token` (not `*`) from the contract in an amount exceeding what any legitimate allowance would authorize.
5. Observe via `check_allowances` in `clarity/src/vm/functions/post_conditions.rs` (lines 598-626) that the transfer of `real-token` is matched against the wildcard-keyed `ft_allowances` entry (because it was inserted under the same `AssetIdentifier{asset_name:"*"}` key as the `*`-named token's genuine allowance) and passes the check, even though no allowance for `real-token` was ever granted.

*Note: full exploitability depends on the exact wildcard-entry insertion path in the (truncated) remainder of `check_allowances` and on `AssetMap`/`to_table` behavior in `clarity/src/vm/contexts.rs`, which could not be fully traced within the available tool budget — a Devin session with full read access should confirm the exact insertion semantics before treating this as fully proven.*
