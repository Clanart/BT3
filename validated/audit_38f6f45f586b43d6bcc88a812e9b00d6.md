### Title
Shared `BalanceHandler` instance corrupts StateDB balance accounting on nested/recursive precompile calls - (File: precompiles/common/balance_handler.go)

### Summary
This is the Cosmos EVM analog of the "check before accrual" ordering bug from the Union Finance report. In `UToken.borrow`, a stale value (borrow balance/credit limit) was read *before* the state that determines its correctness (`accrueInterest`) was updated, letting later logic act on outdated data. In this repository, `precompiles/common/BalanceHandler` records a checkpoint (`prevEventsLen`) via `BeforeBalanceChange` and later consumes bank events *after* that checkpoint via `AfterBalanceChange` to reconcile the EVM `StateDB` balances with the actual `x/bank` balance changes performed during a precompile call. Because the `BalanceHandler` is a single instance held on the `Precompile` struct (not created fresh per call), nested/recursive precompile invocations within the same EVM call stack overwrite the shared `prevEventsLen` checkpoint, causing the outer call's balance-changing events to be silently skipped when `AfterBalanceChange` finally runs for the outer call.

### Finding Description
`BalanceHandler` is created once via `BalanceHandlerFactory.NewBalanceHandler()` and retrieved through `p.GetBalanceHandler()` on the `Precompile` struct, which is registered once per address in the EVM keeper (`RegisterStaticPrecompile`) and reused across all calls to that precompile. [1](#0-0) 

Each precompile `Run` invocation calls:
```
p.GetBalanceHandler().BeforeBalanceChange(ctx)   // records len(events) as prevEventsLen
...precompile execution, may emit bank events, may recursively re-enter a precompile...
p.GetBalanceHandler().AfterBalanceChange(ctx, stateDB) // replays events[prevEventsLen:] onto stateDB
``` [2](#0-1) 

`BeforeBalanceChange` simply stores the current event count as instance state: [3](#0-2) 

`AfterBalanceChange` slices `events[bh.prevEventsLen:]` to determine which bank events belong to *this* call, and uses them to `AddBalance`/`SubBalance` on the `StateDB`: [4](#0-3) 

If a precompile call recursively/nestedly invokes the same precompile (or the caller contract calls into the same precompile address again during execution, e.g. through internal contract calls or the `EVM.Call` re-entry paths), the inner call's `BeforeBalanceChange` overwrites `bh.prevEventsLen` to a *later* index than where the outer call actually began. When the inner call finishes, its `AfterBalanceChange` correctly processes events for the inner scope and does not restore the outer call's original checkpoint. When the outer call later invokes `AfterBalanceChange`, it uses the now-stale (advanced) `prevEventsLen`, causing bank events emitted by the *outer* call before the nested call started to be skipped entirely — they are never replayed onto the `StateDB`.

This is functionally the same root-cause pattern as the seed report: a checkpoint/snapshot value is captured and consumed asynchronously relative to interleaved state changes, so downstream logic operates on stale/incorrect bookkeeping data instead of accruing/consuming all relevant deltas in order.

The repository itself documents this exact defect in an existing test explicitly named to describe the bug: [5](#0-4) 

### Impact Explanation
When `SubBalance`/`AddBalance` calls corresponding to real `x/bank` `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` events are skipped due to the clobbered checkpoint, the EVM-visible `StateDB` balance for an account can diverge from the actual native/bank balance that was moved. Concretely: if an outer precompile call's `CoinSpent` event (funds actually leaving an account in the bank keeper) is skipped because of the nested-call checkpoint bug, the EVM `StateDB` will not reflect that the funds were spent — the account retains a higher EVM balance than it should. Since the EVM balance is what subsequent `CanTransfer`/transfer logic within the same or later calls relies on, this creates a duplication of spendable value: the real coins are already moved/escrowed in `x/bank`, yet the EVM `StateDB` still shows them as available, permitting the same value to be spent again through the EVM path. This satisfies the "Critical unauthorized minting/duplication/accounting corruption of spendable user value across native balances, EVM balances ... or precompile-mediated assets" impact class.

### Likelihood Explanation
The precompile system explicitly supports and tests nested precompile calls (via `try/catch` reentry patterns and recursive debug-precompile calls), meaning nested/recursive invocation of a precompile within a single EVM transaction is a normal, permissionless code path reachable by any user deploying a contract that calls a precompile which itself triggers another precompile call (directly or via callback/hook). The bug is already reproduced and named by the repository's own test (`TestRecursivePrecompileCallsWithDebugPrecompile`), which explicitly states it "demonstrates the balance handler bug by triggering recursive calls that share the same BalanceHandler instance," indicating the root cause is known but the guarantee that the shared handler is safe across nested calls is not actually enforced in the current implementation.

### Recommendation
Make the balance-change checkpoint call-scoped instead of instance-scoped: either (a) instantiate a fresh `BalanceHandler` per `Run` invocation (per call frame) rather than reusing one bound to the `Precompile` struct, or (b) maintain a stack of `prevEventsLen` checkpoints (push on `BeforeBalanceChange`, pop on `AfterBalanceChange`) so nested calls do not clobber the outer call's checkpoint, ensuring every bank event is attributed to exactly the correct call frame and none are skipped.

### Proof of Concept
The existing test demonstrates the mechanics of the bug (shared instance across recursive precompile calls): [6](#0-5) 

A conceptual exploit path:
1. Deploy a contract that calls a stateful precompile (e.g., staking `delegate`) which is registered with a shared `BalanceHandler`.
2. Within that precompile call, before it returns, trigger a nested/recursive call back into the same precompile address (as demonstrated by the `callback` pattern in the debug precompile test, or any contract flow that re-enters a precompile mid-execution).
3. The inner call's `BeforeBalanceChange` overwrites `prevEventsLen`, advancing past the outer call's own `CoinSpent`/`CoinReceived` events.
4. When the outer call finishes and its `AfterBalanceChange` runs, it will not see or apply the outer call's own bank events to `StateDB`, leaving the EVM balance out of sync with the real bank balance — allowing that stale/inflated EVM balance to be spent again in a subsequent operation within the same or later transactions.

Because I could not directly inspect `precompiles/common/precompile.go` to confirm the exact struct field lifetime (only referenced it via grep, not read fully), the precise scope (per-precompile-address singleton vs. per-EVM-keeper singleton) is not fully confirmed here — this should be verified by reading `precompiles/common/precompile.go` and the precompile registration code (`RegisterStaticPrecompile`) to confirm instance lifetime before remediation.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
