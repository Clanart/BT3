### Title
Scanner reports immature coinbase outputs as spendable received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` scans every transaction in a block, including `block.txdata[0]` (the coinbase), and returns any output matching a registered `script_pubkey` as an ordinary `ReceivedOutput` carrying a signing `offset`. Coinbase outputs are consensus-unspendable for 100 blocks (`COINBASE_MATURITY`), so the scanner hands callers a "trusted" receipt for funds that cannot actually be spent — the analog of the report's "unauthenticated artifact consumed as if valid".

### Finding Description
- `scan_block` iterates all of `block.txdata` and calls `scan_transaction` on each (`networks/bitcoin/src/wallet/mod.rs` lines 221–227).
- `scan_transaction` matches solely on `output.script_pubkey` and builds `ReceivedOutput { offset, output, outpoint }` with no distinction for coinbase provenance (`mod.rs` lines 199–214).
- A miner or any party arranging a coinbase paying to a Serai P2TR script produces a `ReceivedOutput` indistinguishable from a normal deposit. `SignableTransaction::new` and `multisig` will construct and FROST-sign a spend of that outpoint (`wallet/send.rs` lines 273–285, 373–397); the resulting transaction is consensus-invalid until maturity and will be rejected.
- The only safeguard is a doc comment on `scan_block` stating a post-processing pass is needed or that callers should use `scan_transaction` on `block.txdata[1 ..]` (`mod.rs` lines 216–220). The API itself performs no maturity check and `ReceivedOutput` carries no marker; correctness depends on every caller replicating the skip.

### Impact Explanation
An unprivileged party can cause funds to be "reported received" that are not spendable: a matching coinbase output is credited by the scanner exactly like a spendable deposit, and any flow feeding it into `SignableTransaction` yields a signed transaction that cannot confirm for 100 blocks. This is reachable purely via public inputs (a Bitcoin transaction/block delivered to the scanner).

### Likelihood Explanation
Requires only that a coinbase pay to a registered script — the base key's script is always registered, so any miner payout/donation to a Serai address, or a deliberate malicious miner, triggers it. The processor's own `get_outputs` happens to skip `txdata[0]`, but the in-scope library API remains a trap for any other consumer of `scan_block`.

### Recommendation
Have `Scanner::scan_block` skip `block.txdata[0]`, or record coinbase provenance/height on `ReceivedOutput` so callers can enforce COINBASE_MATURITY before the output is accepted as spendable.

### Proof of Concept
```rust
// A block whose coinbase pays the Serai tweaked key
let block: Block = mined_block_with_coinbase_paying(p2tr_script_buf(key).unwrap());
let outputs = scanner.scan_block(&block); // returns a normal ReceivedOutput (offset ZERO)
// SignableTransaction::new + multisig() accept it and FROST-signs a spend,
// yet every node rejects the tx as immature for 100 blocks.
let tx = SignableTransaction::new(outputs, &payments, None, None, FEE).unwrap();
```
