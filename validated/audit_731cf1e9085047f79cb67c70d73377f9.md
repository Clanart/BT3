## Analog Found

### Title
Tokenfactory `MsgChangeAdmin` performs an atomic, single-step admin transfer with no two-step confirmation, permanently locking denom control on a typo/wrong-address input - (File: `x/tokenfactory/keeper/msg_server.go`)

### Summary
The tokenfactory module's `ChangeAdmin` message handler transfers admin authority over a `factory/{creator}/{subdenom}` denom to a new address in a single atomic step, exactly mirroring the reported `Timelock.changeOwner()` pattern: the current admin supplies a `NewAdmin` address and the change takes effect immediately with no acceptance/confirmation step from the new admin.

### Finding Description
`msgServer.ChangeAdmin` validates only that the sender is the current admin and that the new admin differs from the current one, then immediately calls `server.setAdmin(ctx, msg.Denom, msg.NewAdmin)`: [1](#0-0) 

`MsgChangeAdmin.ValidateBasic` only checks that `NewAdmin` is a syntactically valid bech32 address — it does not (and cannot) verify that the address is reachable/controllable by anyone, and the module explicitly supports setting the admin to an address with no corresponding key (or even to `""` to permanently disable admin control, which is a deliberate but separate feature): [2](#0-1) 

This is architecturally identical to the reported `Timelock.changeOwner()` issue: authority over an asset is reassigned atomically, with no `transferOwnership`/`acceptOwnership` two-step pattern that would let an erroneous transfer be caught and rolled back before it takes effect. The module docs confirm the admin is the sole gate for `Mint`, `Burn`, `ChangeAdmin`, and `SetDenomMetadata` going forward: [3](#0-2) [4](#0-3) 

### Impact Explanation
If a tokenfactory denom admin submits `MsgChangeAdmin` with a mistyped or otherwise uncontrolled `NewAdmin` address (a bech32-valid but unowned/unreachable address, or an address whose private key was never generated/is lost), all future administrative control over that denom (`Mint`, `Burn`, further `ChangeAdmin`, `SetDenomMetadata`) is permanently and irrecoverably lost — there is no recovery path since the new admin can never sign a corrective transaction. This is a permanent freezing of the denom's administrative capability, matching the report's core impact category. The blast radius is scoped to the specific denom controlled by that admin (not chain-wide), since each `factory/{creator}/{subdenom}` denom has its own independently managed `AuthorityMetadata.Admin`.

### Likelihood Explanation
Any account can become a tokenfactory admin permissionlessly via `MsgCreateDenom`, and the `ChangeAdmin` action is reachable directly by that admin (an ordinary, unprivileged tokenfactory denom creator) as described in the in-scope actor list. No special privilege beyond being the current denom admin is required to trigger the loss — a single fat-fingered address argument in a `change-admin` transaction is sufficient, as demonstrated by the CLI flow: [5](#0-4) 

### Recommendation
Introduce a two-step admin transfer for tokenfactory denoms: add a `MsgProposeNewAdmin` (or similar) that sets a pending-admin field on `AuthorityMetadata`, and require a new `MsgAcceptAdmin` signed by the pending admin to finalize the change, mirroring OpenZeppelin's `Ownable2Step` pattern referenced in the original report. Retain the existing single-step `""`-clearing behavior only as an explicit, clearly-labeled "renounce admin" action if that is still desired.

### Proof of Concept
1. Attacker/user creates a denom: `seid tx tokenfactory create-denom mydenom --from admin` (admin becomes the sole authority).
2. Admin runs `seid tx tokenfactory change-admin factory/{admin}/mydenom sei1<mistyped-or-unowned-address> --from admin`, matching the flow exercised in the test suite: [6](#0-5) 
3. `msgServer.ChangeAdmin` accepts the message since the address passes bech32 validation, and immediately overwrites `AuthorityMetadata.Admin`.
4. No account controls the new admin address; `Mint`, `Burn`, `ChangeAdmin`, and `SetDenomMetadata` for that denom are permanently inaccessible, as enforced by the sender-equals-admin check in each handler: [4](#0-3)

```go
func (server msgServer) ChangeAdmin(goCtx context.Context, msg *types.MsgChangeAdmin) (*types.MsgChangeAdminResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	// Validate new admin we change to should be different from current admin
	if msg.NewAdmin == authorityMetadata.GetAdmin() {
		return nil, types.ErrAdminAlreadyExists
	}

	err = server.setAdmin(ctx, msg.Denom, msg.NewAdmin)
	if err != nil {
		return nil, err
	}
```

```go
func (m MsgChangeAdmin) ValidateBasic() error {
	_, err := sdk.AccAddressFromBech32(m.Sender)
	if err != nil {
		return sdkerrors.Wrapf(sdkerrors.ErrInvalidAddress, "Invalid sender address (%s)", err)
	}

	_, err = sdk.AccAddressFromBech32(m.NewAdmin)
	if err != nil {
		return sdkerrors.Wrapf(sdkerrors.ErrInvalidAddress, "Invalid address (%s)", err)
	}

	_, _, err = DeconstructDenom(m.Denom)
	if err != nil {
		return err
	}

	return nil
}
```

```go
// NewChangeAdminCmd broadcast MsgChangeAdmin
func NewChangeAdminCmd() *cobra.Command {
	cmd := &cobra.Command{
		Use:   "change-admin [denom] [new-admin-address] [flags]",
		Short: "Changes the admin address for a factory-created denom. Must have admin authority to do so.",
		Args:  cobra.ExactArgs(2),
		RunE: func(cmd *cobra.Command, args []string) error {
			clientCtx, err := client.GetClientTxContext(cmd)
			if err != nil {
				return err
			}

			txf := tx.NewFactoryCLI(clientCtx, cmd.Flags()).WithTxConfig(clientCtx.TxConfig).WithAccountRetriever(clientCtx.AccountRetriever)

			msg := types.NewMsgChangeAdmin(
				clientCtx.GetFromAddress().String(),
				args[0],
				args[1],
			)

			return tx.GenerateOrBroadcastTxWithFactory(cmd.Context(), clientCtx, txf, msg)
		},
	}

	flags.AddTxFlagsToCmd(cmd)
	return cmd
}
```
