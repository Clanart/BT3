## Finding

The question's framing (lack of `caseInsensitiveEquals`) isn't itself the bug — strict `===` in `urlsMatch` is actually *more* strict than case-insensitive comparison, so casing alone can't cause a false positive. However, the underlying premise — that two distinct URLs can be normalized by `parseRepositoryIdentifier`/`parseRemote` into an identical `{hostname, owner, name}` tuple despite pointing at different network endpoints — is correct, and it does allow `urlMatchesCloneURL`/`urlsMatch` to falsely match an attacker-controlled remote against a legitimate `gitHubRepository.cloneURL`.

### Root cause
`parseRemote` in [1](#0-0)  uses the regex:
```
^https?://(?:.+@)?(.+)/([^/]+)/([^/]+?)(?:/|\.git/?)?$
```
The `(?:.+@)?` userinfo-stripping group is greedy over the **entire remaining string**, not scoped to the authority component (the substring before the first `/`). Per RFC 3986, a userinfo `user@` marker is only meaningful before the first path `/`; anything after the first `/` is path, not authority. This regex ignores that boundary.

As a result, `https://attacker.evil/owner@github.com/owner/repo.git` is parsed as hostname=`github.com`, owner=`owner`, name=`repo` — identical to the legitimate `https://github.com/owner/repo.git` — even though the real network endpoint (per RFC 3986/actual HTTP client behavior) is `attacker.evil`, with `owner@github.com/owner/repo.git` as path.

Because `urlsMatch` ( [2](#0-1) ) only compares the parsed tuple, not the raw URL/actual authority, it returns `true` for this attacker-crafted URL versus the real `cloneURL`, and `urlMatchesCloneURL` ( [3](#0-2) ) inherits the false-positive match.

### Reachability via `findRemoteBranchName`
`findRemoteBranchName` ( [4](#0-3) ) calls `urlMatchesCloneURL(remote.url, gitHubRepository)` where `remote.url` comes from the local git config (`git remote -v`), which is attacker-influenceable if the user adds/clones a remote pointing at attacker infrastructure, or if a submodule/fork config sets it. When the crafted URL collides with the tuple, the function trusts `tip.branch.upstreamWithoutRemote` as if it came from the genuine GitHub remote.

### Impact
The concrete, currently-confirmed effect through `findRemoteBranchName` is limited: it only changes which branch-name string is used for a subsequent branch-protection-related lookup, not a credential or code-execution sink by itself. I was not able to fully trace, within the available context, whether the same `urlsMatch`/`parseRemote` collision is exploited elsewhere (e.g. `pull-request-matching.ts`, `find-upstream-remote.ts`, or `repositoryMatchesRemote` consumers in `app-store.ts`) in a way that reaches a credential-exfiltration or push-corruption sink — those call sites exist (per `grep_search`) but I did not have remaining iterations to inspect their downstream use of the match result. This should be verified before treating it as a critical/high-impact issue; as scoped to `findRemoteBranchName` alone, the confirmed impact is a benign identity-confusion of branch naming, not a direct credential/code-execution/write vulnerability.

### Recommendation
Fix `parseRemote`'s HTTPS regex to only strip userinfo within the authority component, e.g. anchor the `@`-stripping to occur before the first `/` after `://`, or better, parse with a proper URL parser (`url.parse`/`URL`) and only treat `.username`/`.password` as userinfo, using `.hostname` for the host comparison — rather than a hand-rolled greedy regex spanning the whole remainder of the string.

export function urlsMatch(url1: string, url2: string) {
  const firstIdentifier = parseRepositoryIdentifier(url1)
  const secondIdentifier = parseRepositoryIdentifier(url2)

  return (
    firstIdentifier !== null &&
    secondIdentifier !== null &&
    firstIdentifier.hostname === secondIdentifier.hostname &&
    firstIdentifier.owner === secondIdentifier.owner &&
    firstIdentifier.name === secondIdentifier.name
  )
}

export function findRemoteBranchName(

  remote: IRemote | null,
  gitHubRepository: GitHubRepository
