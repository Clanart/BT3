## Title
Ancestor-hashes duplicate/pruned-fork repair resolves on a fixed count-based sample instead of stake weight, letting a validator-count minority (not necessarily a stake majority) force a "duplicate confirmed" repair decision - (File: core/src/repair/duplicate_repair_status.rs)

### Summary
The `LightClient.force` bug is a case where a liveness fallback allows a decision that is normally gated by a stake-weighted supermajority to instead be finalized from a much smaller, minimum-participant sample. Agave's `AncestorHashesService`/`AncestorRequestStatus` has a structurally similar fallback: when a slot is dead or a pruned fork looks "popular," the validator samples a **fixed count** of `ANCESTOR_HASH_REPAIR_SAMPLE_SIZE = 21` peers and finalizes a repair decision as soon as `get_minimum_ancestor_agreement_size()` (`21.div_ceil(2) = 11`) of them return the *same* response - a raw headcount agreement, not a stake-weighted supermajority check. ### Finding Description
Everywhere else in Agave's consensus/repair stack (`DUPLICATE_THRESHOLD`, `SWITCH_FORK_THRESHOLD`, `VOTE_THRESHOLD_SIZE`, `FREEZE_THRESHOLD`) decisions about which fork is canonical are gated on **stake-weighted** percentages of total epoch stake. [3](#0-2) [4](#0-3) 

The ancestor-hashes repair path, however, is the exception: it is triggered when a slot is dead or when a pruned fork is observed to be "popular" (weight-based heuristic, not confirmed), and then it resolves *which ancestor hash is correct* using a fixed-size random/latency-based peer sample and a headcount majority of that sample (11 of 21 responses matching), independent of how much stake those 21 sampled peers actually represent: [5](#0-4) 

The code's own comment acknowledges the assumption this relies on - that no more than ~20% of *validators* (not stake) are malicious - and treats disagreement as a signal to just retry rather than as a hard security boundary: [6](#0-5) 
```
// Even assuming 20% of validators malicious, the chance that >= 11 of the
// ANCESTOR_HASH_REPAIR_SAMPLE_SIZE = 21 validators is malicious is roughly 1/1000.
```

This assumption is only sound if "validator" sampling roughly correlates with stake, and if a targeted denial-of-service against the sampled/legitimate high-stake responders can't happen. If honest responders for a given slot are unavailable (e.g., network partition, targeted DoS of the popular/well-connected relayers/validators analogous to the "Telepathy provers" in the original report, or simply because a low-stake attacker floods the pool of nodes willing/able to answer `AncestorHashesRepairType` requests within the 5-second retry window), the 21-peer sample can become dominated by a validator-count minority that nonetheless controls the *response*. Because agreement is judged purely by matching `Vec<(Slot, Hash)>` content and headcount (not signed stake-weighted votes), the responders are unauthenticated as to correctness — any 11 colluding/DoS-favored peers that happen to fall into the random sample can supply a consistent (fabricated) ancestor chain and hash set, which is accepted as `EarliestMismatchFound`/`EarliestPrunedMismatchFound`, and drives `ReplayStage` to dump-and-repair the "mismatching" ancestor with the sampled (potentially wrong) hash. [7](#0-6) [8](#0-7) 

This mirrors the `LightClient.force` pattern precisely: a fallback path designed for liveness under adverse conditions (few responders / delayed finality) drops the normal stake-weighted safety threshold down to a small, fixed-count of participants, which can be dominated during a targeted disruption of the honest majority's availability.

### Impact Explanation
If the fixed-size sample is captured by a validator-count (not necessarily stake-weight) minority during a period when honest high-stake nodes are slow/unavailable to respond (e.g., targeted network disruption), the node performing ancestor-hashes repair can be steered into dumping a correct/frozen ancestor bank and replacing it with an attacker-chosen `(Slot, Hash)` from the "agreed" sample, causing that node to diverge from the actual canonical chain. If this repair path is triggered broadly across a subset of the cluster (rather than a single node), it could cause nodes to accept an incorrect ancestor/hash for a slot, contributing to non-rooting or false-acceptance conditions on the affected node(s), rather than a network-wide consensus violation, since final voting/rooting still requires actual stake-weighted votes elsewhere in the pipeline.

### Likelihood Explanation
This is a **medium/low-confidence structural analog**, not a fully proven exploit chain. Determining true exploitability requires knowing: how `repair_request_ancestor_hashes_sample_peers` selects the 21 candidates (weighted by stake/`ClusterSlots` reputation vs. uniform-random) — I was unable to fully read `core/src/repair/serve_repair.rs` before running out of iterations — and how strongly the sampling favors high-stake/known-good responders. If sampling is stake- or reputation-weighted, the practical likelihood of an attacker dominating the sample is much lower than the raw "20% of validators" comment suggests. This limitation should be verified directly in the repository.

### Recommendation
- Verify (in `core/src/repair/serve_repair.rs::repair_request_ancestor_hashes_sample_peers`) whether peer sampling for ancestor-hashes repair is stake-weighted; if it is uniform/random over known validator identities, weight it by stake or restrict eligible responders to peers with meaningful stake.
- Consider requiring the agreeing sample in `AncestorRequestStatus::add_response` to represent a minimum fraction of *total stake* among responders, not just a fixed headcount, consistent with `DUPLICATE_THRESHOLD`/`SWITCH_FORK_THRESHOLD` elsewhere in the codebase.
- Explicitly document the liveness/safety trade-off of the ancestor-hashes repair fallback, similar to the recommendation given for `LightClient.force`.

### Proof of Concept
Not independently reproducible from static analysis alone; would require: (1) confirming the peer-sampling weighting in `serve_repair.rs`, (2) simulating a scenario where a validator marks a slot dead/pruned-popular, (3) targeting or waiting out honest high-stake responders so that ≥11 of the 21 sampled peers are attacker-influenced, and (4) supplying a consistent fabricated `(Slot, Hash)` ancestor chain from those 11 peers to trigger `EarliestMismatchFound`. Full confirmation requires running Agave's local-cluster test harness (e.g., extending `test_ancestor_hashes_service_manage_ancestor_requests` in `core/src/repair/ancestor_hashes_service.rs`) against a modified sampling function, which was not verified within the scope of this analysis.

// Number of validators to sample for the ancestor repair
// We use static to enable tests from having to spin up 21 validators
static ANCESTOR_HASH_REPAIR_SAMPLE_SIZE: AtomicUsize = AtomicUsize::new(21);

pub fn get_ancestor_hash_repair_sample_size() -> usize {
    ANCESTOR_HASH_REPAIR_SAMPLE_SIZE.load(Ordering::Relaxed)
}

pub fn set_ancestor_hash_repair_sample_size_for_tests_only(sample_size: usize) {
    ANCESTOR_HASH_REPAIR_SAMPLE_SIZE.store(sample_size, Ordering::Relaxed);
}

// Even assuming 20% of validators malicious, the chance that >= 11 of the
// ANCESTOR_HASH_REPAIR_SAMPLE_SIZE = 21 validators is malicious is roughly 1/1000.
// Assuming we send a separate sample every 5 seconds, that's once every hour.

// On the other hand with a 52-48 split of validators with one version of the block vs
// another, the chance of >= 11 of the 21 sampled being from the 52% portion is
// about 57%, so we should be able to find a correct sample in a reasonable amount of time.
pub fn get_minimum_ancestor_agreement_size() -> usize {
    get_ancestor_hash_repair_sample_size().div_ceil(2)
}

    /// Record the response from `from_addr`. Returns Some(DuplicateAncestorDecision)
    /// if we have finalized a decision based on the responses. We can finalize a decision when
    /// one of the following conditions is met:
    /// 1. We have heard from all the validators
    /// 2. Or >= MINIMUM_ANCESTOR_AGREEMENT_SIZE have agreed that we have the correct versions
    ///    of nth ancestor, for some `n>0`, AND >= MINIMUM_ANCESTOR_AGREEMENT_SIZE have
    ///    agreed we have the wrong version of the `n-1` ancestor.
    pub fn add_response(
        &mut self,
        from_addr: &SocketAddr,
        response_slot_hashes: Vec<(Slot, Hash)>,
        blockstore: &Blockstore,
    ) -> Option<DuplicateAncestorDecision> {
        // If this is not a response from one of the sampled validators, return.
        let did_get_response = self.sampled_validators.get_mut(from_addr)?;
        if *did_get_response {
            // If we've already received a response from this validator, return.
            return None;
        }
        // Mark we got a response from this validator already
        *did_get_response = true;
        self.num_responses += 1;

        let validators_with_same_response = self
            .ancestor_request_responses
            .entry(response_slot_hashes.clone())
            .or_default();
        validators_with_same_response.push(*from_addr);

        // If we got enough of the sampled validators to respond, we are confident
        // this is the correct set of ancestors
        if validators_with_same_response.len()
            == get_minimum_ancestor_agreement_size().min(self.sampled_validators.len())
        {
            // When we reach MINIMUM_ANCESTOR_AGREEMENT_SIZE of the same responses,
            // check for mismatches.
            return Some(
                self.handle_sampled_validators_reached_agreement(blockstore, response_slot_hashes),
            );
        }

        // If everyone responded and we still haven't agreed upon a set of
        // ancestors, that means there was a lot of disagreement and we sampled
        // a bad set of validators.
        if self.num_responses
            == get_ancestor_hash_repair_sample_size().min(self.sampled_validators.len())
        {
            info!(
                "{} return invalid sample no agreement",
                self.requested_mismatched_slot
            );
            return Some(DuplicateAncestorDecision::InvalidSample);
        }

        None
    }
