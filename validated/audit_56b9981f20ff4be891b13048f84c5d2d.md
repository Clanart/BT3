### Title
SignableTransaction's weight/fee "preview" omits the OP_RETURN output the action actually commits — underpriced fee produces a non-relayable/under-funded transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The audit finding class is a preview function computing a value with one code path while the action executes with a different one. `SignableTransaction` exhibits the same shape: `calculate_weight_vbytes` "previews" the transaction weight using only `payments` (and optionally `change`), but `SignableTransaction::new` pushes an additional OP_RETURN output into `tx_outs` before estimating the weight. The resulting `needed_fee` — used to decide change creation, fund sufficiency, and the minimum-relay-fee check — is systematically lower than the fee the real transaction requires at the requested `fee_per_vbyte`.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` when `data` is present:

```rust
// networks/bitcoin/src/wallet/send.rs:194-202
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}
```

But both weight estimates are computed over `payments` only:

```rust
// networks/bitcoin/src/wallet/send.rs:204
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
// line 225-226
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
```

`calculate_weight_vbytes` builds its mock transaction's `output` vector exclusively from `payments` (lines 85-93) plus the optional change output (lines 95-99). The OP_RETURN output — up to ~83 bytes of scriptPubKey plus the 8-byte value and compact-size overhead, roughly 95+ vbytes — is invisible to the preview. Every downstream decision then uses the understated `vbytes`:

- `needed_fee = fee_per_vbyte * vbytes` (line 206)
- the `TooLowFee` check against `DEFAULT_MIN_RELAY_TX_FEE` (line 211)
- the `NotEnoughFunds` check (line 215)
- the change decision `input_sat.checked_sub(payment_sat + fee_with_change)` and `value >= DUST` (lines 228-233)

Yet the action — the actual `Transaction` stored in `SignableTransaction.tx` and signed in `TransactionSignMachine::sign` via `SighashCache::new(&self.tx.tx)` with `Prevouts::All` (lines 373-386) — contains the OP_RETURN output. The fee actually paid is `sum(inputs) - sum(outputs)` (see `fee()`, lines 138-141), which lands exactly at the underestimated `needed_fee`/`fee_with_change` whether or not change is created.

### Impact Explanation
A caller requesting `fee_per_vbyte` gets a transaction paying a lower effective fee rate. If `fee_per_vbyte` is near the network minimum (e.g., 1 sat/vB), the preview passes the `TooLowFee` check while the real transaction's rate falls below `DEFAULT_MIN_RELAY_TX_FEE` once the OP_RETURN output's ~95+ vbytes are included. The signed transaction is then non-standard/unbroadcastable by default policy: the threshold signatures are valid, but the resulting outputs are not spendable through this transaction as intended — the direct analog of "the user sees a discrepancy between the previewed and executed result." Additionally, the `TooLargeTransaction` check uses `weight` computed without the OP_RETURN output, and `fee()`/`needed_fee()` diverge from the true required fee for every `data`-carrying transaction.

### Likelihood Explanation
Any `SignableTransaction::new` caller that passes `data: Some(...)` triggers the miscalculation deterministically — no attacker cooperation or threshold collusion is required; it is a deterministic formula error in the estimate path. The unprivileged reachability depends on whether an external party can influence `payments`/`data` in the transaction the network builds (e.g., withdrawal instructions carrying metadata); even absent that, the produced transaction's fee rate is lower than the integrator explicitly requested, so the mismatch exists on every OP_RETURN-bearing spend.

### Recommendation
Make the preview match the action: pass the full output list (including the OP_RETURN output, with its real script length) to `calculate_weight_vbytes`, or add a `data: Option<&[u8]>` parameter so the mock transaction appends the same `ScriptBuf::new_op_return` output the final `tx_outs` receives. Recompute `needed_fee`, `TooLowFee`, `NotEnoughFunds`, the change decision, and the `MAX_STANDARD_TX_WEIGHT` check from that corrected weight.

### Proof of Concept
```rust
// In SignableTransaction::new, with data = Some(vec![0u8; 80]):
// 1. tx_outs gains an OP_RETURN output (~91 bytes script + 8 bytes value + 1 byte count).
// 2. vbytes = calculate_weight_vbytes(inputs, payments, None) — counts only payments.
// 3. needed_fee = fee_per_vbyte * vbytes  // missing ~100 vB of OP_RETURN
// 4. With change: change = input_sat - payment_sat - fee_with_change
//    actual outputs = payments + OP_RETURN + change
//    actual fee paid = fee_with_change, but actual vsize = vbytes_with_change + ~100
//    effective rate = needed_fee / actual_vsize < fee_per_vbyte
// 5. With fee_per_vbyte = 1 and OP_RETURN present, actual rate < 1 sat/vB:
//    fee (e.g., 250 sat) / actual vsize (e.g., ~350 vB) < 1 sat/vB → below
//    DEFAULT_MIN_RELAY_TX_FEE despite TooLowFee passing, so the signed
//    transaction cannot be relayed and the prevouts remain unspent by it.
```

Concrete check: for `inputs = [100_000 sats]`, `payments = [(addr, 50_000)]`, `data = Some([0u8; 80])`, `fee_per_vbyte = 1` — `vbytes` is computed over 1 payment + change, yielding `needed_fee ≈ vbytes` sats, while the serialized transaction is ~100 vB larger, so `fee() / actual_vsize < 1` and the node rejects the broadcast.
