### Title
Consensus-incentive reward misattributed to the first message's signer when a single extrinsic batches consensus messages for multiple state machines - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::on_executed` derives the reward recipient from **only `messages.get(0)`** and then pays that single relayer for **every** `StateMachineUpdated` event present in the whole batch, regardless of which underlying consensus message actually produced each state-machine advance. [1](#0-0) 

### Finding Description
`on_executed` extracts a single `relayer_account` from `messages[0]` (the first `Message::Consensus` entry it can decode/verify), then iterates over *all* `StateMachineUpdated` events emitted during the batch, collapses them per `state_machine_id` to the highest `latest_height`, and pays the block-cost reward for **every** state machine that advanced — all credited to that one signer:

```rust
let maybe_relayer_account = messages.get(0).and_then(|first_message| { ... });
...
for (state_machine_id, latest_height) in highest_per_state_machine {
    let _ = Self::process_message(state_machine_height, state_machine_id, relayer_account.clone().into());
}
``` [1](#0-0) 

The comment at lines 125-132 shows the author already fixed the "same state machine updated twice in one batch" double-payment case, but the fix only deduplicates *per state machine* — it does not address the case where the batch's `messages` vector contains **independent `Message::Consensus` entries for different state machines, submitted by different signers**, in a single call to the ISMP message handler. Since Hyperbridge consensus proofs are explicitly public and permissionless artifacts ("These proofs can be generated by anyone, as they are freely provided by its connected chains" — see `docs/content/explore/nexus/relayer.mdx` line 8), any account can pick up an already-broadcast, still-unsubmitted consensus proof for chain B (produced/found by relayer B) and bundle it into the same extrinsic as its own trivial/cheap consensus message for chain A, submitting the whole batch itself. `FeeHandler::on_executed` is invoked once per successfully-processed batch with the full `messages`/`events` vectors for that batch [2](#0-1) , and nothing in `calculate_reward`/`process_message` binds the reward for state machine B's height advance to the account that actually authored/originated the message that advanced it — it only ever uses the signer recovered from `messages[0]`.

### Impact Explanation
This is a "wrong beneficiary" bug in a fund-moving path: the treasury-funded reward (`T::Currency::transfer` from `TreasuryAccount` plus reputation-asset minting) for updating potentially many state machines in one batch is paid entirely to whichever account happens to be `messages[0]`'s signer, not to the relayer(s) who actually did the consensus-proof work for the other state machines. An unprivileged actor can therefore redirect legitimate relayers' `$BRIDGE` block-cost rewards to themselves by resubmitting public proof data alongside their own cheap message, at no cost beyond gas and needing only one valid (even minimal) consensus message of their own as the first element.

### Likelihood Explanation
Requires only: (1) ability to observe/collect already-public consensus proofs for other state machines (explicitly permitted/expected by design), and (2) ability to submit a batched ISMP message call containing multiple `Message::Consensus` entries — a normal, unprivileged relayer capability, not a compromised relayer/prover/admin assumption. No governance, no malicious peer collusion, and no front-running of unconfirmed transactions is needed; it just exploits the flawed all-or-nothing attribution logic on legitimately-processed batches.

### Recommendation
Attribute and pay the reward per `StateMachineUpdated` event using the signer recovered from the **specific consensus message that produced that event**, not a single signer taken from `messages[0]`. Concretely, build a map from `state_machine_id` (or from whichever consensus message index/proof produced each `StateMachineUpdated`) to its own verified signer, and call `process_message` with that per-event signer instead of a single batch-wide `relayer_account`.

### Proof of Concept
1. Relayer B broadcasts (or otherwise makes available) a valid consensus proof `msg_B` that advances state machine `SM_B`'s commitment height (this proof is public by protocol design).
2. Attacker A crafts and submits a single ISMP `handle` extrinsic containing `messages = [msg_A, msg_B]`, where `msg_A` is attacker A's own trivially-valid consensus message (e.g., for a cheap/irrelevant or even the same chain with minimal height advance) placed first, and `msg_B` is the copied proof for `SM_B`.
3. `pallet-ismp` verifies both messages independently and successfully advances both `SM_A` (if applicable) and `SM_B`'s commitment heights, emitting `StateMachineUpdated` events for both.
4. `FeeHandler::on_executed` is invoked once with `messages = [msg_A, msg_B]` and `events` containing both `StateMachineUpdated` events; `maybe_relayer_account` is derived solely from `messages[0]` = attacker A's signer [3](#0-2) .
5. The loop over `highest_per_state_machine` pays the `block_cost`-based reward for **both** `SM_A` and `SM_B`'s height advances to attacker A's account [4](#0-3) , even though relayer B did the work (and possibly the bulk of the cost/weight) for `SM_B`'s update.

Note: I was not able to fully trace, within the remaining tool budget, the exact call site in `modules/pallets/ismp/src/lib.rs` that invokes `FeeHandler::on_executed` to confirm whether a single extrinsic can indeed carry `Message::Consensus` entries with different embedded `signer` fields authored by different accounts in one batch (vs. the pallet enforcing a single overall submitter across the whole `messages` vec). This is the one open verification point; the reward-attribution logic itself (`messages[0]`-only signer paying for all state machines in the batch) is directly confirmed in the code above.
