### Title
Deserialized `ReceivedOutput` bypasses even-parity key check, producing outputs the signer cannot spend - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Bitcoin wallet enforces that spendable Taproot outputs correspond to even-Y internal keys at scan/registration time (`Scanner::new` returns `None` for odd keys, `register_offset` increments offsets until the tweaked key is even via `p2tr_script_buf`). However, `ReceivedOutput::read` deserializes an arbitrary `offset` and `TxOut` with no parity check. A `ReceivedOutput` whose `key + G*offset` is odd decodes successfully, yet `SignableTransaction::multisig` returns `None` for it because `p2tr_script_buf(offset.group_key())` yields `None`, making the reported-received output unspendable by the signing pipeline. This mirrors the audit issue class: the code path intends to handle value (carry/spend a received output) but the deserialization entry point silently accepts a value-bearing state that the spend path categorically rejects.

### Finding Description
`Scanner::new` inserts the zero-offset script only if `p2tr_script_buf(key)` is `Some`, i.e., the key is even. `register_offset` loops `offset += ONE` until `p2tr_script_buf(self.key + GENERATOR*offset)` is `Some`, guaranteeing every registered script maps to an even tweaked key. In contrast, `ReceivedOutput::read` reads `offset = Secp256k1::read_F(r)` plus a consensus-decoded `TxOut`/`OutPoint` and returns it without recomputing `p2tr_script_buf(group_key + G*offset)` or checking parity. Downstream, `SignableTransaction::multisig` computes `keys.clone().offset(self.offsets[i])` and does `p2tr_script_buf(offset.group_key())?` — returning `None` both when the prevout script mismatches and when the tweaked key is odd. Since BIP-340/341 key-spend requires an even-Y internal key (the signer must conditionally negate the secret), an odd tweaked key means the machine has no valid scalar for the committed `script_pubkey`, so no signature can ever be produced.

### Impact Explanation
An unprivileged party supplying bytes to `ReceivedOutput::read` (an accepted untrusted input path) can inject an output that is treated as received value — it carries a valid `TxOut`, `OutPoint`, and `value()` — yet is permanently unspendable: `multisig` returns `None`, so no FROST signing session can be created for it. Funds reported received cannot be spent, matching the "function intended to transfer value cannot actually receive/handle it" bug class at Medium severity.

### Likelihood Explanation
Any consumer that reconstructs `ReceivedOutput`s from serialized bytes (network sync, DB reload via `read`, or peer-supplied data) rather than exclusively from `Scanner::scan_transaction` accepts attacker-influenced offsets. Only a ~50% crafted offset is needed (any offset yielding an odd point), and the failure only manifests at spend time, after the value has been accounted.

### Recommendation
In `ReceivedOutput::read` (or in a validation step before the output is accepted), recompute `p2tr_script_buf(key + GENERATOR*offset)` and reject if it is `None` or does not match `output.script_pubkey`. Alternatively, store the group key in `ReceivedOutput` and enforce the same even-parity invariant `Scanner` enforces, so deserialized outputs cannot reach states the signer refuses.

### Proof of Concept
Construct bytes `scalar_bytes || consensus(TxOut) || consensus(OutPoint)` where `scalar_bytes` encodes an offset `o` such that `group_key + G*o` has odd Y (e.g., pick `o` so `to_encoded_point(true).tag() != Tag::CompressedEvenY`), and `TxOut.script_pubkey` arbitrary. `ReceivedOutput::read` succeeds. Building `SignableTransaction::new(vec![output], payments, change, None, fee)` succeeds (value/fee checks pass), then `.multisig(&keys)` hits `p2tr_script_buf(offset.group_key())?` → `None`, so the output can never be signed for despite being reported as spendable received value.
