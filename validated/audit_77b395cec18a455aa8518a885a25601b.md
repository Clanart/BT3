## Analysis

The reported bug class (division by zero due to an unchecked divisor governance/config value) maps directly onto Kaia's KIP-71 dynamic base fee (Magma) calculation.

### Root cause

`KIP71Config.NextMagmaBlockBaseFee` divides by the `GasTarget` governance parameter without any zero check: [1](#0-0) 

Specifically, when `parentGasUsed != gasTarget` (true for virtually every non-empty block), the code computes `x.Div(x, new(big.Int).SetUint64(gasTarget))` (both in the "increase" branch and the "decrease" branch), which panics in Go's `math/big` if `gasTarget == 0`.

The `kip71.gastarget` governance parameter has **no format check preventing zero**: [2](#0-1) 

and its `FormatChecker` is `noopFormatChecker`, which always returns `true`: [3](#0-2) 

The header-governance vote consistency checker (`checkConsistency`) also performs no zero-check for `Kip71GasTarget` — it falls into the default "no-op" case that simply returns `nil`: [4](#0-3) 

Only `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` have explicit relational checks; `Kip71GasTarget` has none, so a value of `0` passes `NewVoteData`, `VerifyVote`, and `checkConsistency` unchallenged. The same holds for the on-chain `GovParam` contract governance path (`contractgov`), which ignores only deprecated params, not out-of-range ones (`ParseContractCall`/`GetParamSet` apply no `FormatChecker` at all before calling `ParamSet.Set`): [5](#0-4) 

Once `GasTarget = 0` becomes the active parameter (via header-vote ratification at the next epoch, or via `GovParam.setParamIn`), every node calling `NextMagmaBlockBaseFee` — both for `VerifyMagmaHeader` during block validation and for building the next block's base fee — panics on the very next block with non-zero gas usage. Because this is deterministic consensus-critical code executed by all nodes, it is a network-wide chain halt (DoS), not merely a local resource-only bug.

### Title
Division-by-zero panic in KIP-71 `NextMagmaBlockBaseFee` due to unchecked zero `GasTarget` governance parameter - (File: params/kip71_config.go)

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by the governance-controlled `GasTarget` parameter without validating it is non-zero. The `kip71.gastarget` parameter accepts `0` through both header-vote governance and on-chain `GovParam` contract governance because its `FormatChecker` is `noopFormatChecker` and no additional consistency check exists for it, unlike `LowerBoundBaseFee`/`UpperBoundBaseFee`.

### Finding Description
`NextMagmaBlockBaseFee` (`params/kip71_config.go:58-129`) computes the delta to the previous block's base fee by dividing by `gasTarget` in both the "gas used above target" branch (`x.Div(x, new(big.Int).SetUint64(gasTarget))` at line 102) and the "gas used below target" branch (line 120). If governance sets `GasTarget = 0`, and the parent block's gas usage is non-zero (the common case), the function reaches one of these branches and panics with a native Go division-by-zero on `*big.Int`.

`GasTarget` is fully attacker/validator-controllable: the format checker registered for `Kip71GasTarget` in `kaiax/gov/param.go:324-333` is `noopFormatChecker`, which unconditionally returns `true`, and `checkConsistency` in `kaiax/gov/headergov/impl/header.go:214-220` performs no additional validation for this parameter (unlike `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`, which are explicitly bounded relative to each other). The same unchecked path exists via the on-chain `GovParam` contract (`kaiax/gov/contractgov/impl/getter.go`), which applies no per-parameter format validation before calling `ParamSet.Set`.

### Impact Explanation
`NextMagmaBlockBaseFee` is invoked by every node both to verify incoming block headers (`VerifyMagmaHeader`) and to construct new blocks' base fee. A panic here crashes block processing network-wide as soon as the zero `GasTarget` value takes effect and a block with non-zero gas usage is processed — a full chain halt / consensus-critical DoS, not a localized or resource-only issue.

### Likelihood Explanation
Reaching this requires a governance vote (or `GovParam.setParamIn` contract call by the contract owner) to set `kip71.gastarget` to `0`. This is within the explicitly in-scope "governance parameters" category. Given the complete absence of format/consistency checks specifically for this parameter (in contrast to the two bound parameters which are protected), a single malicious or careless governing entity/validator vote is sufficient to trigger it, and it propagates deterministically to all nodes at the next epoch/param-activation block.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` that rejects `0` (mirroring the existing relational checks for `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`), and/or add a defensive zero-check inside `NextMagmaBlockBaseFee` (similar to the existing `BaseFeeDenominator == 0` fallback at `params/kip71_config.go:71-76`) so a misconfigured/malicious `GasTarget` cannot crash block processing.

### Proof of Concept
1. A validator submits a header vote (or the `GovParam` contract owner calls `setParamIn`) for `kip71.gastarget` with value `0`.
2. `NewVoteData`/`VerifyVote`/`checkConsistency` accept the vote (no format or consistency check rejects zero, per `kaiax/gov/param.go:324-333` and `kaiax/gov/headergov/impl/header.go:214-220`).
3. At the next epoch/activation block, `GetParamSet` returns `GasTarget = 0`.
4. On the following block with `parentHeaderGasUsed != 0`, `NextMagmaBlockBaseFee` (`params/kip71_config.go:99-102` or `:117-121`) executes `big.Int.Div(x, 0)`, panicking every node that processes or builds that block, halting the chain.

func (c *contractGovModule) GetParamSet(blockNum uint64) gov.ParamSet {
	m, err := c.contractGetAllParamsAt(blockNum)
	if err != nil {
		return *gov.GetDefaultGovernanceParamSet()
	}

	ret := *gov.GetDefaultGovernanceParamSet()
	for k, v := range m {
		err = ret.Set(k, v)
		if err != nil {
			return *gov.GetDefaultGovernanceParamSet()
		}
	}

	return ret
}
