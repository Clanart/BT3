### Title
Underpriced, unmetered ELF verification during program deployment allows CPU-time DoS - ([File: program-runtime/src/deploy.rs])

### Summary
Deploying or upgrading a BPF program via the upgradeable loader charges only a fixed, size-independent compute-unit fee, while the actual ELF parsing, relocation/symbol resolution, and bytecode verification (`RequisiteVerifier`) performed in `deploy_program()` scale with the size of the submitted program (up to the max program/account size, ~10 MiB via loader-v3 `ExtendProgramData`). This mirrors the reported MilkyWay bug class: a fixed/flat charge is paid while the validator performs unbounded, attacker-sized work in an unmetered code path.

### Finding Description
`process_instruction_inner()` in `programs/bpf_loader/src/lib.rs` charges a single flat fee, `UPGRADEABLE_LOADER_COMPUTE_UNITS`, before dispatching to `process_loader_upgradeable_instruction()`: [1](#0-0) 

That instruction path (e.g. `DeployWithMaxDataLen` / `Upgrade`) eventually invokes the `deploy_program!` macro, which calls `deploy_program()`: [2](#0-1) 

Inside `deploy_program()`:
1. `Executable::<InvokeContext>::load(programdata, ...)` parses and loads the ELF (relocations, section headers, function registry lookups) — cost scales with program size and number of relocations/symbols.
2. `executable.verify::<RequisiteVerifier>()` walks every instruction in the program's bytecode performing static verification (jump target validation, opcode legality, register usage, etc.) — cost scales with the number of instructions in the program.

Neither of these steps consumes anything from `invoke_context.compute_meter`; the only CU charge for the whole instruction is the flat `UPGRADEABLE_LOADER_COMPUTE_UNITS` charged once in `process_instruction_inner()`. The size of the program that can be pushed through this path is bounded only by `MAX_PERMITTED_DATA_LENGTH` (referenced throughout `programs/bpf_loader/src/lib.rs` and `cli/src/program.rs`), which permits multi-megabyte programs via repeated `Write`/`ExtendProgramData` instructions.

This is structurally the same bug class as the reported MilkyWay issue: a size-dependent, unmetered workload (there: `GetAllBalances` iterating attacker-inflated denom lists in `BeginBlock`; here: ELF loading + `RequisiteVerifier` iterating attacker-inflated bytecode/relocations during `BeginBlock`-equivalent transaction processing) is billed at a flat/size-independent rate rather than scaled to the actual work performed.

### Impact Explanation
Any unprivileged user can submit a maximally-sized buffer (populated via ordinary `Write`/`ExtendProgramData` instructions, which are cheap, size-scaled-fee) and then issue a single `DeployWithMaxDataLen` or `Upgrade` instruction referencing that buffer. Each leader/validator that processes this transaction pays for ELF parsing and instruction-by-instruction verification of the entire multi-megabyte payload, but the transaction is billed the same flat CU cost as deploying a tiny program. This is "materially underpriced compute": the attacker can force disproportionate CPU/verification time per unit of fee paid, and because deployment happens synchronously in `process_instruction_inner()` before the program is cached, this work cannot be amortized or skipped. Repeated submission of maximal-size deploy/upgrade transactions (which is cheap for the attacker, being bound only by normal per-slot fee/CU budget, not by verification cost) can be used to consume outsized leader/validator processing time relative to compute units charged.

### Likelihood Explanation
Reaching this path requires no special privileges — any account can create a buffer, fill it up to the max permitted account data size via ordinary system/loader instructions, and submit a `DeployWithMaxDataLen`/`Upgrade` instruction. The relevant test harnesses already show how a full-size ELF deploy instruction is constructed and processed with only a fixed CU allocation (`programs/sbf/tests/programs.rs:494-525`, `core/tests/scheduler_cost_adjustment.rs:318-360`), confirming that the deployment path's CU accounting is independent of program size.

### Recommendation
Meter the `deploy_program()` steps against `invoke_context.compute_meter` proportionally to the size of `programdata` (and/or the number of instructions/relocations discovered while loading the ELF), similar to how CPI account-info and data-copy costs are charged per byte in `program-runtime/src/cpi.rs` (`cpi_bytes_per_unit`). At minimum, add a compute charge scaled to `programdata.len()` before or during `Executable::load()`/`verify::<RequisiteVerifier>()` in `program-runtime/src/deploy.rs`, so verification cost is priced commensurately with the actual CPU work, preventing underpriced, attacker-sized deploy/upgrade transactions from imposing disproportionate validator load.

### Proof of Concept
Conceptual reproduction (cannot execute in this environment, but structurally supported by existing test infrastructure):
1. Create a buffer account and repeatedly issue `Write`/`ExtendProgramData` instructions until it holds a program payload close to `MAX_PERMITTED_DATA_LENGTH`.
2. Submit a single `DeployWithMaxDataLen` (or `Upgrade`) instruction pointing at this buffer, as done in `programs/sbf/tests/programs.rs:494-525` and `runtime/src/bank/tests.rs:6349+` (`test_bpf_loader_upgradeable_deploy_with_max_len`), but scaled to the maximum allowed size instead of a small test ELF.
3. Observe (e.g. via the `LoadProgramMetrics.verify_code_us`/`load_elf_us` instrumentation already present in `program-runtime/src/deploy.rs`) that ELF load + verification time scales with payload size, while the CU charge recorded by `core/tests/scheduler_cost_adjustment.rs` remains the constant `solana_bpf_loader_program::UPGRADEABLE_LOADER_COMPUTE_UNITS` regardless of program size.
