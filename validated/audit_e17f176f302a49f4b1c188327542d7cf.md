### Title
`Scanner::scan_block` returns immature coinbase outputs as spendable `ReceivedOutput`s - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`scan_block` iterates over `block.txdata` including `txdata[0]`, the coinbase transaction, and reports any matched outputs as `ReceivedOutput`s indistinguishable from normal spendable outputs. Coinbase outputs are unspendable for 100 blocks (BIP-34/consensus maturity rule). This is the same bug class as the reference report: an ordering/precondition invariant ("output must have matured before being spendable") that the producer fails to enforce, so downstream consumers operating on the assumption "returned output == spendable input" produce transactions that are rejected by the network.

### Finding Description
`Scanner::scan_transaction` pushes any output whose `script_pubkey` is registered into `res` as a `ReceivedOutput`, and `scan_block` extends that over every transaction in `block.txdata`, including index 0 (the coinbase) [1](#0-0) . The doc comment acknowledges the issue — "This will also scan the coinbase transaction which is bound by maturity" — but the function still returns such outputs with no maturity flag, height field, or type distinction [2](#0-1) .

`ReceivedOutput` carries only `offset`, `output`, and `outpoint` — nothing records that the outpoint belongs to a coinbase [3](#0-2) . A miner can pay a registered P2TR address (base key or any `register_offset`-derived address) directly in the coinbase; any external party can also grind a block whose coinbase pays the multisig's script. That output then flows to consumers as a spendable input. If it is fed into `SignableTransaction::new` / `multisig` signing (as `send_and_get_output` + `sign` do in the test harness, mining 100 blocks first as a workaround) [4](#0-3) , the resulting transaction is consensus-invalid and rejected — while a victim aggregator may have already credited the deposit.

This mirrors the reference finding exactly: `setEpoch` stored `epochCreation = block.timestamp` while assuming `epochCreation < epochBegin`, causing every deposit to revert; here, the scanner stores an output while assuming "scanned ⇒ spendable", causing every spend attempt to be rejected.

### Impact Explanation
An output reported as received is not spendable. If a consumer credits the depositor and later includes the `ReceivedOutput` in a `SignableTransaction`, the built transaction is invalid at the consensus layer (immature coinbase spend) and is rejected on broadcast — funds effectively locked/unusable until maturity, and any logic depending on spend-now semantics (refunds, scheduled payments, forward outputs) is broken for that input. A miner (or anyone able to influence coinbase content, e.g., via a mining pool payout address) can deliberately create this condition against a victim's registered address.

### Likelihood Explanation
Any coinbase transaction paying a scanned script triggers it; miners routinely pay arbitrary addresses, and a pool can point its payout at the victim's P2TR script. The in-repo processor's `get_outputs` already demonstrates the correct workaround (`for tx in &block.txdata[1 ..]`, skipping the coinbase) [5](#0-4) , but `scan_block` remains a public trap for any other caller — including the test's own usage, which had to "Mine until maturity" to make the output spendable [4](#0-3) .

### Recommendation
Enforce the invariant at production time rather than documenting it, mirroring the report's `if (_epochBegin < uint40(block.timestamp)) revert;` fix:

- Change `scan_block` to skip `block.txdata[0]` (the coinbase), or
- Add an `immature: bool` / `OutPoint`-level marker to `ReceivedOutput` so consumers can filter, and reject immature outpoints in `SignableTransaction::new` by checking `txid` against known coinbase rules is not feasible — so the cleanest fix is skipping the coinbase in `scan_block` and providing a separate explicit `scan_coinbase` for callers that track maturity themselves.

### Proof of Concept
```rust
// regtest: miner pays serai's P2TR script in the coinbase itself
let block = rpc.get_block(&hash).await.unwrap();
let outputs = scanner.scan_block(&block);
// txdata[0] is the coinbase; its output to our script is returned
assert_eq!(outputs[0].outpoint().txid, block.txdata[0].compute_txid());
// outputs[0] is indistinguishable from a normal ReceivedOutput, yet any
// SignableTransaction spending it is consensus-invalid for 100 blocks.
```
This is precisely what the existing test avoids by mining 100 additional blocks before calling `scan_block` [6](#0-5) .

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  /// Scan a block.
  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
  }
