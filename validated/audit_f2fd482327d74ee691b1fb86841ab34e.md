### Title
Gasless swap admission (`checkBalanceForSwap`) trusts a live, single-transaction-manipulable DEX quote to gate proposer-funded gas lending — (File: `kaiax/gasless/impl/tx_pool.go`)

### Summary
`GaslessModule.checkBalanceForSwap` (`kaiax/gasless/impl/tx_pool.go`, lines 107-182) validates a user's `GaslessSwapTx` by calling `GaslessSwapRouter.GetAmountIn(token, minAmountOut)` and comparing it against the user-declared `AmountIn`. This call reads the router's/DEX's *current, spot* reserves at the moment of tx-pool admission, exactly the same class of "raw pool balance used as price" issue described in the Balancer report: a value derived from mutable, single-block-manipulable AMM reserves is used as the sole gate for accepting an obligation (here, the proposer's gas-lending obligation via `LendTxGenerator`), with no TWAP, no re-validation at inclusion time guarantee, and no protection against reserve manipulation between admission and block building.

### Finding Description
The gasless flow (KIP-247) works as follows: a block proposer lends gas to a user by prepending a `LendTxGenerator` transaction ahead of the user's `GaslessApproveTx`/`GaslessSwapTx` bundle (see `kaiax/gasless/README.md` lines 7-35 and `kaiax/gasless/impl/builder.go` `ExtractTxBundles`, lines 28-72). The user is expected to repay the lent gas out of the swap's output token via `AmountRepay`, and admission logic is supposed to ensure the promised `AmountIn`/`MinAmountOut` are economically consistent with the DEX's exchange rate before the proposer commits to lending gas.

That economic check is done in `checkBalanceForSwap`: [1](#0-0) 

```
requiredAmountIn, err := routerContract.GetAmountIn(nil, token, minAmountOut)
...
if swapArgs.AmountIn.Cmp(requiredAmountIn) < 0 {
    return fmt.Errorf("insufficient amountIn: ...")
}
```

`GetAmountIn` on `GaslessSwapRouter` (and the underlying `UniswapV2Router02`/pair) is a `view` function computed directly from the pair's live reserves — i.e., a spot AMM price, structurally identical to Balancer's `getPrice()` reading raw `Vault.getPoolTokens()` balances. This value:
- Can be pushed in either direction within a single transaction/block by anyone who can trade against the underlying pool (no permission needed, no delay, no TWAP).
- Is evaluated once, at tx-pool admission/promotion time (`GetCheckBalance` is invoked when the sender's balance/collateral state is (re-)checked; see `kaiax/gasless/impl/tx_pool.go` lines 62-72), using whatever chain state is current at that moment.
- Has no guarantee of matching the state that exists when the bundle is actually built and executed in a later block, since a proposer/searcher fully controls transaction ordering within the block they assemble (`ExtractTxBundles`).

Because the check is purely a spot-quote comparison with no minimum observation window, staleness guard, or reference to a manipulation-resistant price, an adversary can:
1. Submit (or wait for) a trade that transiently shifts the DEX pair reserves so that `GetAmountIn(token, minAmountOut)` returns an artificially low `requiredAmountIn` at the moment `checkBalanceForSwap` runs.
2. Get a `GaslessSwapTx` admitted/promoted with an `AmountIn`/`MinAmountOut` pair that is not economically sound against the pool's honest price.
3. Have the proposer commit gas via `LendTxGenerator` ahead of the bundle, i.e., before the real swap executes and can fail or return less value than the repay obligation requires.

This mirrors the analog's core defect class: "uses [a] balance/spot value as price and can be steered by anyone," and "any address can decide when the snapshot/quote should be observed," enabling the reference value used for a critical protocol decision (lending gas, in this case) to be detached from an honest market price.

### Impact Explanation
If the on-chain swap execution itself does not independently re-derive and enforce `MinAmountOut`/repayment sufficiency against actual settled reserves in a way that fully protects the proposer (this repo indexes the Go bindings for `GaslessSwapRouter` but the Solidity source of `swapForGas`'s internal invariant checks was not retrievable via the indexed code, see caveat below), the admission-time spot-price gate is the primary economic safeguard preventing proposers from lending gas against under-collateralized swaps. Bypassing it via reserve manipulation could let an attacker:
- Get gas lent by the proposer (`LendTxGenerator`) for a swap that cannot actually produce `AmountRepay` once the manipulated reserves revert to the honest price, causing the proposer to pay real KAIA gas fees with no compensating repayment — direct fee-delegation abuse / value extraction from the proposer.
- Repeat this pattern across multiple gasless bundles (rate-limited only by `MaxBundleTxsInPending`/`MaxBundleTxsInQueue`), amplifying loss.

This is a Medium/High-severity fee-delegation abuse vector reachable by any unprivileged transaction sender (or a searcher colluding with a sender) who can trade on the underlying pool referenced by `GaslessSwapRouter.DexAddress(token)`.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a whitelisted token/pool with movable liquidity, (b) precise timing so the manipulated reserve state is observed exactly when `checkBalanceForSwap` executes (which happens at tx-pool promotion, potentially multiple times as the pool re-validates pending transactions), and (c) that the final on-chain swap does not fully re-validate the repay sufficiency independent of the admission check. Because DEX price manipulation within a single block/transaction is a well-understood, cheap, and repeatable primitive (flash-loan or self-funded sandwich), and the admission check is entirely permissionless and stateless with respect to time-weighting, the precondition for triggering the bug is easy for any transaction sender to reach.

### Recommendation
- Do not gate proposer gas-lending decisions on a live spot AMM quote (`GetAmountIn`) alone. Require a manipulation-resistant reference price (e.g., a genuine TWAP oracle, or bound the accepted quote to a moving-average with a maximum deviation) before honoring `LendTxGenerator`.
- Re-validate the swap's ability to repay at the exact point of inclusion in the block (using the state right before the swap executes in the same block, not merely at tx-pool admission), and ensure the on-chain `swapForGas` (or equivalent) function reverts atomically and refuses to release the loaned gas value unless `AmountRepay` is proven from the transaction's actual, executed output — not from a value that was only checked against a stale pool snapshot.
- Consider adding a maximum single-block price-impact/staleness bound to `checkBalanceForSwap`'s router quote, analogous to fixing the Balancer oracle by rejecting `updatePrice()`/`getPrice()` calls that deviate too far, too fast, from a longer-window reference.

### Proof of Concept
A full instrumented PoC (deploying the `GaslessSwapRouter`/Uniswap pair, moving reserves, then submitting a `GaslessSwapTx` right at the manipulated point, and observing that `checkBalanceForSwap` accepts an `AmountIn` that would fail against the honest reserves) was not executed here — the reasoning is derived from static analysis of the indexed code paths cited above. **Caveat:** the exact on-chain `swapForGas` implementation of `GaslessSwapRouter.sol` (the real safety net that might already prevent the proposer's loss even if `checkBalanceForSwap` is fooled) was not present in the indexed codebase snapshot; only its Go ABI bindings (`contracts/bindings/kip247/GaslessSwapRouter.go`) were retrievable. Confirming the full severity requires inspecting that contract's source to see whether repayment sufficiency is independently enforced atomically during execution. If the Solidity code does fully re-check sufficiency using post-swap actual output (not a pre-computed quote), the vulnerability would be downgraded to a denial-of-service/wasted-gas issue rather than direct value theft — this should be verified in a Devin session with full repository access.
