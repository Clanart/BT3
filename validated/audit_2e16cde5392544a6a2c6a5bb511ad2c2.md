## Analysis

The reported pattern is a **validation gap**: some fields get a strict equality/format check while an adjacent, security-relevant field only gets the loosest possible check ("something is non-empty" instead of "this matches exactly what is expected"). Looking for this shape in GitHub Desktop, `parseAppURL` in `app/src/lib/parse-app-url.ts` is the closest analog: it strictly validates the `pr` and `branch` query parameters (regex format, `testForInvalidChars`) but performs **no validation whatsoever** on the `url` value that is later used as the git remote to clone — this is the field an attacker fully controls via a `x-github-client://openRepo/<url>` deep link.

### Title
Unvalidated remote URL from `x-github-client://openRepo/` deep link is passed straight to Git clone - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` rigorously validates the `pr` and `branch` parameters of an "Open in Desktop" protocol URL but accepts the `url` (the git remote to clone) with no validation at all beyond it being non-empty, mirroring the "too soft check" pattern in the seed report where one critical value is checked far more loosely than sibling values that matter just as much.

### Finding Description
`parseAppURL` extracts the `openrepo` action's parameters from an externally supplied protocol URL: [1](#0-0) 

Note the asymmetry:
- `pr` must match `/^\d+$/`.
- `branch` must match `/^pr\/\d+$/` (fork case) and is checked against `testForInvalidChars`, which rejects control characters, `~^:?*[\|"<>`, `@{`, `..`, leading/trailing dots, and `.lock` suffixes — i.e., a real git-ref-format allowlist: [2](#0-1) 
- `url` (`parsedPath`, taken verbatim from the deep-link path) has **no equivalent check**. It is not required to be `https://`/`ssh://`/`git@`, may start with `-` (git option-injection) or use the `ext::` git transport helper, and is passed straight through as `IOpenRepositoryFromURLAction.url`.

This URL is the sole value ultimately used to invoke `git clone`. Git's `ext::` remote helper executes an arbitrary shell command as part of cloning (`git clone "ext::sh -c 'touch /tmp/pwned'" x`), and dash-prefixed remote strings can be interpreted as options by `git clone` itself (the class of bug fixed upstream as CVE-2017-1000117). Because Desktop's `parseAppURL` treats `pr`/`branch` as security-sensitive but `url` as free text, any of these payloads sail through unchanged into the clone path.

### Impact Explanation
An attacker who gets a victim to click a single link (`x-github-client://openRepo/ext::sh%20-c%20%27...%27`, delivered via a web page, email, or GitHub itself) can have GitHub Desktop invoke `git clone` with a remote string that is not a normal git transport, achieving arbitrary command execution on the victim's machine outside of any repository sandbox — satisfying the "code execution via a link the user clicks" impact class explicitly called out as valid.

### Likelihood Explanation
No local access, credentials, or social engineering beyond "click a link" is required; `x-github-client://` is registered as Desktop's default protocol handler at install time (see `possibleProtocols` handling in `app/src/main-process/main.ts`), so the OS itself routes such links straight into `handleAppURL` → `parseAppURL`, requiring nothing more from the user than a normal click.

### Recommendation
Add the same class of validation applied to `branch`/`pr` to `url`: enforce an allowlist of transport schemes (`https:`, `http:`, `ssh:`, `git:`, or the bare `user@host:path` SCP form) and explicitly reject values starting with `-` or using `ext::`/`fd::`/other local-helper transports before constructing the clone action, or route the value through the existing `parseRemote`/remote-parsing validators before it is ever handed to `git`.

### Proof of Concept
1. Attacker hosts/sends a link: `x-github-client://openRepo/ext::sh%20-c%20%27touch%20/tmp/pwned%27`
2. Victim (with GitHub Desktop installed) clicks the link.
3. OS invokes Desktop with the URL; `handleAppURL` → `parseAppURL` classifies it as `open-repository-from-url` with `url = "ext::sh -c 'touch /tmp/pwned'"`, since no check rejects this value (unlike `branch`/`pr`).
4. Desktop proceeds to clone using this attacker-controlled remote string, triggering execution of the embedded shell command via git's `ext::` transport.

**Caveat:** I was not able to trace, within the available index, the exact downstream code in `dispatcher.ts` that consumes `IOpenRepositoryFromURLAction.url` and constructs the actual `git clone` invocation (e.g., whether it goes through `parseRemote`/`parseRepositoryIdentifier` first, which could mitigate this). The unvalidated field in `parse-app-url.ts` itself is confirmed; whether a downstream layer already re-validates the URL before reaching `git clone` needs verification with a Devin session that can execute/trace the full clone flow. // See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
