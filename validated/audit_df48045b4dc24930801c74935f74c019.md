### Title
Fee-on-transfer / non-standard ERC20 accounting mismatch in `requestERC20Transfer` - ([File: contracts/service_chain/bridge/BridgeTransferERC20.sol])

### Summary
`BridgeTransferERC20.requestERC20Transfer()` pulls tokens from the caller with `safeTransferFrom` using the caller-supplied `_value + _feeLimit` amount, then unconditionally emits a `RequestValueTransfer` event (and burns `_value` in mint/burn mode) using that same stated amount, without ever measuring the bridge's actual token balance change. If the registered token has non-standard transfer semantics (fee-on-transfer, rebasing, or otherwise returns less than the nominal amount), the bridge's cross-chain accounting will be based on an amount larger than what it actually received.

### Finding Description
`requestERC20Transfer` is a public, unprivileged-caller function: [1](#0-0) 

It calls `IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit))` and then immediately calls the internal `_requestERC20Transfer`, which emits `RequestValueTransfer` with the nominal `_value` (and, in mint/burn mode, burns `_value` tokens) — all without verifying the bridge's actual balance delta: [2](#0-1) 

Because `SafeERC20.safeTransferFrom` only checks the call succeeded (and optionally the boolean return value), it does not protect against tokens that deduct a fee or otherwise deliver fewer tokens than requested: [3](#0-2) 

The counterpart chain's bridge (`handleERC20Transfer`) will mint or unlock the full nominal `_value` to the recipient on the other side, based solely on the `RequestValueTransfer` event emitted here — regardless of how many tokens the source-chain bridge actually retained: [4](#0-3) 

This is the same root-cause pattern flagged in the external report: `transferFrom`/`safeTransferFrom` is used with the stated amount instead of measuring the actual balance delta before crediting/accounting downstream.

### Impact Explanation
If a token with fee-on-transfer, rebasing, or other non-standard transfer behavior is registered on the bridge (via `registerToken`, an operator/admin action), any ordinary user calling `requestERC20Transfer` for that token causes:
- In lock/unlock mode: the bridge locks less than `_value` tokens but the counterpart chain unlocks the full `_value` to the recipient, progressively draining the bridge's token reserve (value inflation / theft of locked liquidity) as more such transfers occur.
- In mint/burn mode: `ERC20Burnable(_tokenAddress).burn(_value)` will revert or burn from bridge balance that was never actually received in full, causing operational failure or (if the token has an internal quirk allowing burn beyond received balance) accounting divergence between chains.

This is unauthorized value movement / cross-chain supply inflation reachable from a single unprivileged transaction, matching the required impact criteria.

### Likelihood Explanation
Exploitability depends on an operator registering a fee-on-transfer/non-standard ERC20 token via `BridgeTokens`/`registerToken` (an admin-gated action), after which any unprivileged user can trigger the mismatch by simply calling `requestERC20Transfer`. Likelihood is therefore Medium: it requires an admin/governance decision to onboard such a token (not enforced against by the contract), but once such a token is registered, exploitation requires no special privilege and is straightforward and repeatable.

### Recommendation
In `requestERC20Transfer` (and `onERC20Received`), measure the bridge's own token balance before and after the `safeTransferFrom` call, and use the observed balance delta — not the caller-supplied `_value + _feeLimit` — as the basis for fee accounting, burning, and the emitted `RequestValueTransfer` amount. Alternatively, explicitly document/enforce (e.g., via a registration-time check or governance policy) that only strictly standard-compliant ERC20 tokens (no transfer fees, no rebasing) may be registered with `BridgeTokens.registerToken`.

### Proof of Concept
1. Governance/operator registers a fee-on-transfer ERC20 token `T` (e.g., 2% fee on transfer) via `BridgeTokens.registerToken`.
2. User approves the bridge for `T` and calls `requestERC20Transfer(T, to, value=100, feeLimit=0, extraData)`.
3. `safeTransferFrom(msg.sender, address(this), 100)` actually delivers only 98 `T` to the bridge (2 burned as fee), but the bridge's balance increases by only 98.
4. `_requestERC20Transfer` nonetheless emits `RequestValueTransfer(..., _value=100, ...)` and (in burn mode) attempts `ERC20Burnable(T).burn(100)`, which either reverts (burning more than owned) or, in lock/unlock mode, causes the operator on the counterpart chain to unlock 100 `T` to `to` based on the event, while the source bridge only ever custodied 98 `T` — a 2-token shortfall accruing per transfer that drains bridge reserves over repeated calls.
