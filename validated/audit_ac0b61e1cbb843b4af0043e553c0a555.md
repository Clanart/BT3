### Title
Persisted `CachedPreprocess` seed is reloaded and re-signed after consumption, enabling nonce reuse and validator key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The Envoy report is a use-after-free: QUICHE continued operating on a stream after `StopReading()` logically destroyed it. The Serai analog is continued use of a *cryptographically consumed* one-shot resource. `SigningProtocol` stores the FROST preprocess seed in the `CachedPreprocesses` DB table and never deletes it; every call to `preprocess_internal`/`share_internal`/`complete` re-derives identical nonces from the same seed and signs again. `DkgConfirmer::complete` re-invokes `share_internal` with a `key_pair` fetched fresh from `DkgKeyPair`, which is overwritten unconditionally by `generated_key_pair` — so the same nonce can be used over a different message. Two shares under one nonce yield the validator's MuSig secret key.

### Finding Description
`preprocess_internal` loads the seed from `CachedPreprocesses` (created once, at lines 123-134) and rebuilds deterministic nonces via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` (`crypto/frost/src/sign.rs:121-144`), which seeds `ChaCha20Rng` from the cached bytes. Nothing deletes the entry after `sign` consumes the nonces (`signing_protocol.rs:137-145, 156`).

The file's own safety argument (lines 25-54) states safety holds only because re-execution always signs the identical message under BFT. That invariant is not enforced for the message itself:

- `generated_key_pair` (`coordinator/src/tributary/handle.rs:47-60`) calls `DkgKeyPair::set` unconditionally — overwriting any prior key pair — then signs `set_keys_message(..., key_pair)` via `DkgConfirmer::share` (`signing_protocol.rs:296-309`).
- `DkgConfirmer::complete` (`signing_protocol.rs:312-327`) calls `share_internal` again, producing a second signature share, but the `key_pair` used is whatever `DkgKeyPair::get` returns at that moment (`handle.rs:529-535`), not necessarily the one already signed.
- The signed message also embeds the `removed` set (`signing_protocol.rs:296-300`), which is re-resolved per call via `removed_as_of_dkg_attempt`; late `RemoveParticipantDueToDkg` votes or a changed removal set between calls changes the message while the nonce stays fixed.
- The code explicitly admits the missing guard: "we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)" (line 51) and a TODO to verify the on-chain preprocess matches before publishing shares (lines 53-54).

If `share`/`complete`/`preprocess` are re-invoked after the seed was already used to produce a published share — e.g., a partial rebuild/re-execution (which the design explicitly supports by keeping state in the DB rather than memory, lines 16-23) with a different `key_pair` or `removed` set — the same nonce `k` signs two distinct messages. Since the preprocess commitment `R` is identical and public on the tributary, any observer computes `k` from the two shares and recovers the validator's `Ristretto` secret key.

### Impact Explanation
Recovery of a validator's MuSig secret key undermines the DKG-confirmation root of trust: the attacker (or anyone reading the public tributary shares) can forge `set_keys` signatures attributable to that validator, contributing to installation of attacker-chosen threshold keys. Shares are published on-chain via `Transaction::DkgConfirmed`, so both shares needed for extraction are publicly observable. This is key-share recovery of the validator's signing key, not merely a signature forgery.

### Likelihood Explanation
Exploitation requires `share`/`complete` to run a second time under the same `(b"DkgConfirmer", attempt)` context with a different message. The design deliberately re-executes from the DB on reboot (lines 16-23), and `generated_key_pair` overwrites `DkgKeyPair` without checking whether a share for a different key pair was already issued (`handle.rs:54-59`). A partial rebuild, a re-invocation after the processor regenerated the key pair, or a `removed`-set change between `share` and `complete` suffices — no malicious validator, broken BFT, or leaked key is required; ordinary operational re-execution paths trigger it whenever the message inputs drift. The missing on-chain-preprocess check is acknowledged as unimplemented.

### Recommendation
- Bind the consumed nonce to the exact message signed: store a hash of `set_keys_message` output alongside the cached seed, and refuse to sign any different message under the same context.
- Delete or tombstone `CachedPreprocesses` once a share is produced, and treat re-requested signing under the same context as an error rather than a silent re-derivation.
- Make `DkgKeyPair::set` reject overwriting a distinct key pair for an attempt that already produced a share.
- Implement the acknowledged TODO: before publishing a share, verify the on-chain preprocess/commitments match the presumed preprocess.

### Proof of Concept
1. DKG attempt `N` completes; `generated_key_pair(kp1)` runs: `DkgKeyPair::set(attempt=N, kp1)`, then `DkgConfirmer::share` loads seed `s` from `CachedPreprocesses["DkgConfirmer", N]`, derives nonce `k`, and publishes share `σ1 = k - H(R‖K‖m1)·s_i` on the tributary.
2. The coordinator partially rebuilds (DB persists, so `s` survives) or the processor re-emits `GeneratedKeyPair` with `kp2 ≠ kp1` — or `removed` changes — before `complete`/a re-run of `share`.
3. `share_internal`/`complete` reload `s` (it was never deleted), re-derive the identical `k` and `R`, and sign `m2 = set_keys_message(..., kp2)` producing `σ2`.
4. With `σ1`, `σ2`, identical `R`, and public `H(R‖K‖mi)`: `k = (σ1 - σ2)/(c1 - c2)`-style recovery, then `s_i = (k - σ1)/c1` — the validator's MuSig secret key is recovered from public data only. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
