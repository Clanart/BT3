### Title
`SignableTransaction` omits the OP_RETURN output from weight/fee calculation, defeating the minimum-fee and maximum-weight checks - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` validates a minimum relay fee and a maximum standard weight, but computes both on a *hypothetical* transaction built only from `payments` (and optionally `change`). The OP_RETURN `data` output — whose bytes are attacker-influenced via the `data` field attached to external outputs/instructions — is pushed into `tx_outs` before the weight calculation yet is never included in the transaction used to derive `weight` and `vbytes`. The result: the signed, broadcast transaction is strictly larger than the one the fee/weight checks were performed against, so an attacker can cause the multisig to sign a transaction whose real fee rate falls below the Bitcoin relay minimum (or that marginally exceeds standard weight), leaving treasury funds stuck in an unbroadcastable/unconfirmable transaction.

### Finding Description
In `crypto/bitcoin`'s analog of "a security parameter not accounting for user input," the fee and weight invariants are computed by `calculate_weight_vbytes(inputs, payments, change)`:

- `payments` and `change` are used to construct the measuring transaction (`send.rs:85–99`).
- The OP_RETURN output is appended to `tx_outs` at `send.rs:194–202` **before** the call at `send.rs:204`, but `calculate_weight_vbytes` never receives `tx_outs` — only `payments` — so the data output contributes nothing to `vbytes` or `weight`.
- `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) and the minimum-relay-fee check `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (`send.rs:211`) therefore understate the real transaction size by up to ~90 bytes (~360 WU / ~91 vbytes for a max-length 80-byte payload plus output overhead).
- The `weight > MAX_STANDARD_TX_WEIGHT` check at `send.rs:241` uses the same incomplete `weight`.

Because `inputs`, `payments`, and `data` are ultimately driven by on-chain deposit data (`Output.data` populated from `extract_serai_data` / instructions that an unprivileged depositor can craft, see `processor/src/networks/bitcoin.rs:730–736`), the size gap is attacker-controlled: an attacker can attach up to 80 bytes of data to force the signed transaction to be larger than what the fee guarantees were computed for.

### Impact Explanation
The protocol's stated invariant — "the actual fee this transaction will use is `sum(inputs) - sum(outputs)`" and the implicit guarantee that the produced transaction pays at least `fee_per_vbyte` and passes the default minimum relay fee — is violated for the real serialized transaction. When `fee_per_vbyte` is near the relay minimum (which `median_fee` clamps to `fee.max(1)`, i.e. exactly the regime where 1 sat/vbyte is paid), the true fee rate drops below `DEFAULT_MIN_RELAY_TX_FEE` once the uncounted OP_RETURN output is serialized, and the transaction will be rejected by the relay/mempool or fail to confirm. Funds committed to `tx_ins` are then locked in an outpoint-committed transaction that cannot be broadcast — i.e., outputs the scanner treats as spendable that are not, in practice, spendable without rebuilding/resigning the transaction. This matches the "funds reported received that are not spendable" impact class and is worth Medium severity: it requires a low-fee environment plus a data-bearing transaction, but is reachable purely via public on-chain input.

### Likelihood Explanation
Reachable by any user who deposits with an attached `data` payload (a normal, unprivileged operation — `get_outputs` copies `Self::extract_serai_data(tx)` into external outputs at `processor/src/networks/bitcoin.rs:730–733`). Exploitation requires the scheduled fee rate to be close to the relay minimum so the ~91-vbyte shortfall tips the actual rate below it; `median_fee` explicitly floors at 1 sat/vbyte (`processor/src/networks/bitcoin.rs:414`), so this regime is routine on a quiet mempool. The weight check bypass is marginal and mostly only relevant when combined with many inputs/payments.

### Recommendation
Include the OP_RETURN output in the transaction used by `calculate_weight_vbytes` (e.g., pass the final `tx_outs`, or add `data` as a parameter to `calculate_weight_vbytes` and include a `TxOut` with the OP_RETURN `script_pubkey` in the measuring transaction). Apply the same correction inside the change-handling branch so `vbytes_with_change` also accounts for the data output. Recompute both `needed_fee` and the `MAX_STANDARD_TX_WEIGHT` check against the complete output set.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// SignableTransaction::new(vec![output], &[], Some(change), Some(vec![0u8; 80]), fee_per_vbyte)
//
// 1. tx_outs gets the OP_RETURN pushed at lines 194-202.
// 2. calculate_weight_vbytes(tx_ins.len(), payments=&[], None) at line 204
//    builds a tx with only the (optional) change output - no OP_RETURN.
// 3. needed_fee = fee_per_vbyte * vbytes(without data output).
//    With fee_per_vbyte = 1 and vbytes ~ 154 (1-in/1-out P2TR),
//    needed_fee passes the DEFAULT_MIN_RELAY_TX_FEE check for the
//    *smaller* tx, but the real tx (~245 vbytes) pays the same fee,
//    i.e. ~0.63 sat/vbyte < 1 sat/vbyte relay minimum.
// 4. After signing, send_raw_transaction is rejected ("min relay fee not met"),
//    and the prevouts are locked to a tx that cannot propagate.
```
The discrepancy is directly observable: `tx.weight()` on `self.tx` at the end of `SignableTransaction::new` exceeds the `weight` variable the check at line 241 was performed against, by exactly the serialized size of the OP_RETURN output.
