### Title
Silent swallowing of parse-validation errors during lazy-field merge causes invalid data to be indistinguishable from valid data - (File: `java/core/src/main/java/com/google/protobuf/LazyFieldLite.java`)

### Summary
`LazyFieldLite`, the mechanism backing lazily-parsed sub-messages in Java Lite (and heavy) generated messages, silently discards `InvalidProtocolBufferException`s raised while merging attacker-supplied bytes into an already-parsed value. The caller's builder ends up with a "successfully merged" message that in fact only contains the previously-good value (or an empty default instance) with no indication that part of the input was invalid. This mirrors the LibreSSL CVE-2022-48437 invariant failure: an installed "continue on error" verification path (here, the catch blocks that swallow `InvalidProtocolBufferException` and proceed) discards the error state instead of recording/propagating it, so the ultimate caller receives an incorrect "success" signal for data that actually failed validation.

### Finding Description
`LazyFieldLite.mergeFrom(CodedInputStream, ExtensionRegistryLite)` and the private helper `mergeValueAndBytes` both catch `InvalidProtocolBufferException` and continue execution without recording the failure to any caller-visible state: [1](#0-0) [2](#0-1) 

Similarly, `ensureInitialized` (invoked from `getValue()`/`getValue(defaultInstance)`) catches the same exception when lazily parsing `delayedBytes`, sets a private `corrupted` flag, and substitutes the default instance — but `corrupted` is only exposed via a package-private `isCorrupted()` accessor, not through any public parsing API (`parseFrom`, `mergeFrom`, `getValue`): [3](#0-2) [4](#0-3) 

The class's own unit test documents this as intentional "swallowing": [5](#0-4) 

**Invariant transfer**: In the CVE, `x509_verify_ctx_add_chain` fails to store the error that occurred while verifying the leaf certificate, so when a caller's verification callback says "continue anyway," the eventual returned error/verdict for the chain no longer reflects the actual failure that occurred — the caller can be misled about what happened. In `LazyFieldLite`, the analogous invariant is: *when a merge/parse operation encounters invalid wire data, the fact of that failure must not be silently absorbed if it can affect the caller's belief about the correctness of the resulting message.* The `catch (InvalidProtocolBufferException e) { /* nothing logged, no exception thrown */ }` blocks are the direct analog of the missing error-store call in `x509_verify_ctx_add_chain`: both discard a should-be-recorded error and let the caller proceed with a result that appears successful.

### Impact Explanation
This is an integrity-of-error-reporting issue: a client that calls a public merge/parse API (e.g., `Message.Builder.mergeFrom(CodedInputStream, ExtensionRegistry)` on a message with a lazily-parsed extension/field) can receive a `MessageLite` that silently omits or reverts part of the second message's contents when that second chunk's bytes fail to parse, with no exception and no error surfaced through any public getter. This differs from the normal `parseFrom` contract, where invalid input is expected to throw `InvalidProtocolBufferException`. Downstream code that relies on "no exception thrown => the merged data is exactly what was supplied" can silently operate on stale/incomplete data. This is a logic/data-integrity defect rather than memory corruption or RCE, consistent with a Medium-severity classification, matching the CVE's own Medium/5.3 rating and its own confinement to "integrity: low."

### Likelihood Explanation
The path is reachable purely through a supported public API: an ordinary client sends binary protobuf bytes to `mergeFrom`/`parseFrom` for a message type that has a message-typed field/extension using `LazyFieldLite` (e.g. `MessageSet`-style or `lazy=true` fields, or the generic `LazyFieldLite` construction paths used by `GeneratedMessageLite`), where the field is merged a second time with malformed trailing bytes. No privileged access or hostile schema is required — an attacker-controlled bounded byte sequence with a corrupt lazily-parsed sub-field is sufficient to trigger the swallow path in `mergeValueAndBytes`/`mergeFrom`. The likelihood of exploitation in the sense of "attacker forces a discrepancy between what was sent and what the receiving app believes was parsed" is realistic and low-effort.

### Recommendation
- Do not silently swallow `InvalidProtocolBufferException` in `mergeValueAndBytes` and `LazyFieldLite.mergeFrom`; either propagate the exception to the caller (matching normal `mergeFrom` semantics) or reliably surface the corrupted/partial state through a public, documented API so callers can detect it, mirroring how `ensureInitialized` at least records `corrupted` internally.
- Expose the existing `corrupted` flag (or an equivalent) through a public accessor on the containing message so that "parse succeeded, but with data silently dropped" is distinguishable from a fully successful parse.
- Add regression tests asserting that a merge/parse call that encounters invalid embedded bytes in a `LazyFieldLite` either throws or leaves observable evidence of the failure, rather than asserting (as `testMergeInvalid` currently does) that the exception is expected to be swallowed.

### Proof of Concept
Not independently executed in this session (read-only analysis of the checkout). A minimal reproduction outline, based on the existing test `LazyFieldLiteTest.testMergeInvalid`:
1. Build a valid `TestAllTypes` message `message` and wrap it: `LazyFieldLite valid = LazyFieldLite.fromValue(message);`.
2. Construct `LazyFieldLite invalid = new LazyFieldLite(extensionRegistry, ByteString.copyFromUtf8("invalid"));` — bytes that are not valid `TestAllTypes` wire format.
3. Call `invalid.merge(valid);` and then `invalid.getValue(TestAllTypes.getDefaultInstance())`.
4. Observe: no exception is thrown at any point, and the returned value equals `message` (the merge from bytes silently failed and fell back to the previously-parsed value) — as already asserted by the existing test at: [5](#0-4) 
This confirms the invalid-data path is reachable via the public `merge`/`getValue` surface and produces no caller-visible signal that the merge partially failed, which is the direct analog of the CVE's unrecorded verification error.

  private static MessageLite mergeValueAndBytes(
