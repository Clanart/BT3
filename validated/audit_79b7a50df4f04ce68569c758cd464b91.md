### Title
Attacker-controlled nested conflict markers cause Copilot conflict-resolution to silently splice raw conflict-marker text into the committed file - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
The bug-class in the source report is "an untrusted, attacker-shaped list is parsed by loosely-matching logic that doesn't validate structural invariants (no duplicate/ordering checks), so the accounting done over that list silently diverges from reality and the difference is paid out/committed as if it were legitimate." The Desktop analog is the "Resolve conflicts with Copilot" feature: the file content that is scanned for conflict markers is *attacker-controlled* (it comes from merging/rebasing/cherry-picking a branch or PR the user fetched), and the code that decides where a conflict "hunk" begins and ends uses a naive line-scanning marker matcher with no defense against nested or malformed marker sequences, and no closing validation that the final reassembled file contains no residual markers.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) walks the file line by line; once it sees a `<<<<<<<` line it treats the *next* line matching the bare `=======` regex as the hunk's separator and the *next* line matching `>>>>>>>` as the closing marker — regardless of whether those lines are actually the closing markers of the same block or belong to a different, nested/malformed marker sequence embedded by the attacker inside the "ours" section: [1](#0-0) 

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) independently re-walks the *same* raw content later, using the same permissive "first `=======`, first `>>>>>>>`" matching to decide hunk boundaries when splicing the model's per-hunk resolution back into the file: [2](#0-1) 

Because a merge/rebase/cherry-pick can leave `<<<<<<<`/`=======`/`>>>>>>>` looking sequences that are not the true conflict boundaries (e.g. a file whose "ours" or "theirs" side legitimately contains text that itself looks like a marker triple — trivial for an attacker to engineer via a crafted branch/PR that collides with the victim's branch), both parsers get fooled identically: they close the "hunk" at the first nested `=======`/`>>>>>>>` pair instead of the real ones. The model is shown a truncated/misattributed hunk (`Conflict 1 of N` no longer matches the real content), and `reassembleResolvedFile` splices the model's resolution into that same wrong boundary, leaving the *true* remainder of the block — including a literal `=======` / real "theirs" text / a real `>>>>>>> feature` marker line — as ordinary content that gets copied straight through to `resultLines` untouched: [3](#0-2) 

No guard exists to stop this: `validateResolutionPaths` only checks that the *count* of hunks the model returned per file matches the count `extractConflictHunks` computed for that same (already miscounted) file, so counts agree and validation passes: [4](#0-3) 

The only marker check performed anywhere, `parseCopilotConflictResolution`'s `resolvedContent` scan, checks each *individual model-returned hunk string* for leftover markers — it never re-scans the fully reassembled file that `reassembleResolutions` produces before it is written to disk and presented to the user for commit: [5](#0-4) [6](#0-5) 

### Impact Explanation
This is silent corruption of what the user commits: a literal, real `>>>>>>> <branch>` (or `=======`) line — and possibly a chunk of the legitimately conflicting "theirs" content — ends up embedded verbatim in the resolved file that the app tells the user is "fully resolved by Copilot." Depending on the file type this can break the build silently, or — more dangerously — let an attacker who controls the merged-in branch smuggle content into the resolved file that the AI never actually reasoned over and that a user reviewing only the AI's summary/diff card is unlikely to notice, since the tool's own guarantee ("all non-conflicted code is preserved exactly") is violated without any error being raised. This matches the "silent corruption of what the user commits or pushes" impact category from an attacker-controlled fetched/merged repository.

### Likelihood Explanation
Requires the victim to (a) merge/rebase/cherry-pick a branch or PR whose content was crafted by an attacker to contain marker-look-alike text inside a real conflicting hunk, and (b) use the "Resolve with Copilot" feature on the resulting conflict. No special privileges are needed beyond the attacker's ability to have their branch/PR content merged into the conflict (a normal collaborative-repo scenario), and crafting the nested-marker payload requires no local access, admin rights, or credentials — only ordinary contribution to the repository. This makes it a realistic, moderate-likelihood path for an opt-in feature.

### Recommendation
- Have `extractConflictHunks` reject/flag (rather than silently mis-parse) any `=======`/`>>>>>>>`-looking line encountered while still inside an already-open marker section that hasn't been closed by its own well-formed triple, instead of treating the first match of the right regex as authoritative regardless of nesting.
- Make `reassembleResolvedFile` use the exact same, single, shared marker-boundary detection function as `extractConflictHunks` (not a re-implemented parallel scanner), so the two can never disagree about hunk boundaries for the same content.
- After reassembly, scan the final `resolvedContent` for any residual `<<<<<<<`, `|||||||`, `=======`, `>>>>>>>` marker lines and throw a `CopilotValidationError` (fail closed) if any remain, instead of only checking each model-returned hunk snippet in isolation.

### Proof of Concept
1. Attacker pushes/PRs a branch where a file's real conflicting region contains an embedded fake marker triple inside the "ours" text, e.g. the file ends up on disk (after a normal git merge attempt) as:
```
<<<<<<< HEAD
<<<<<<< nested
fakeOurs
=======
fakeTheirs
>>>>>>> nested
=======
theirs real (attacker payload)
>>>>>>> feature
```
2. Victim runs the merge/rebase in Desktop, gets a conflict on this file, and clicks "Resolve with Copilot."
3. `extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) reports exactly 1 hunk, with `oursContent = "<<<<<<< nested\nfakeOurs"`, `theirsContent = "fakeTheirs"`, ending at the *first* `>>>>>>>` it finds (`>>>>>>> nested`).
4. The model resolves that single (bogus) hunk; `validateResolutionPaths` sees 1 expected / 1 returned hunk and passes.
5. `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) independently re-derives the same wrong boundary, splices the model's resolution there, and then copies the remaining lines — `=======`, `theirs real (attacker payload)`, `>>>>>>> feature` — through **verbatim** as ordinary file content because none of them match `reassemblyOursMarker`.
6. The dialog reports the file fully resolved; the user commits/pushes a file containing a literal `=======`/`>>>>>>> feature` conflict-marker line and unreviewed attacker content.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
