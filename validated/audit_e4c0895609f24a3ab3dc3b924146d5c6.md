## Analysis

The Sherlock report's broken invariant is: **a value the user implicitly relied on when approving an action can be changed by an adversary between approval and execution (TOCTOU), with no re-validation, causing the user to commit to something other than what they reviewed.**

Mapping that primitive onto Desktop's local commit pipeline (not the fee-market example, which has no analog): the Changes view shows a diff computed once, the user selects individual lines/hunks to include (`DiffSelection`, stored as *absolute line indices* into that diff), and then on "Commit" Desktop **recomputes the diff from disk again** and re-applies the old index-based selection to the new diff content, with no check that the file is unchanged in between. [1](#0-0) [2](#0-1) [3](#0-2) 

### Title
Stale-diff TOCTOU allows silent corruption of partially-staged commits - (File: app/src/lib/git/apply.ts)

### Summary
When a user selects specific lines/hunks of a modified file to include in a commit, Desktop stores that selection as absolute line indices into the diff that was rendered in the UI. At commit time, instead of reusing that reviewed diff, `applyPatchToIndex` re-fetches a brand-new diff straight from the working directory and reapplies the old index-based selection to it before generating the patch that is applied to the index.

### Finding Description
`_commitIncludedChanges` takes the currently selected `WorkingDirectoryFileChange` objects (each carrying a `DiffSelection` computed against the diff last rendered in the Changes view) and passes them into `createCommit` → `stageFiles` → `applyPatchToIndex`: [3](#0-2) 

`applyPatchToIndex` does not reuse the diff the user actually looked at and clicked checkboxes against. It calls `getWorkingDirectoryDiff(repository, file)` again, live, to produce a fresh diff of the file's *current* on-disk contents, then feeds the *stale* `file.selection` (line indices from the earlier render) into `formatPatch`: [1](#0-0) [4](#0-3) 

`formatPatch` walks the *new* diff's hunks and lines, and for each line calls `file.selection.isSelected(absoluteIndex)` where `absoluteIndex` is `hunk.unifiedDiffStart + lineIndex` of the **new** diff: [5](#0-4) 

If the file's on-disk content changes between the moment the UI diff/selection was computed and the moment the user presses "Commit" (e.g. a build tool, formatter/linter, IDE autosave, a background script, another process, or a symlinked/shared file being modified — none of which require "malware already on the host" or elevated privileges, just something writing to a file under the repo while Desktop is open), the hunk boundaries and line indices in the new diff no longer line up with what the user actually selected. `DiffSelection.isSelected` has no notion of content identity, only positional index, so it will silently include/exclude the wrong lines relative to what the user intended and reviewed on screen.

There is no re-validation step anywhere in this path — no mtime/hash check comparing the diff used to build the patch against the diff that was rendered and selected against; a search for staleness guards in this flow (`stale`, `mtime`, "diff out of date") returned nothing relevant to this commit path.

### Impact Explanation
This falls squarely into "silent corruption of what the user commits or pushes" — one of the explicitly valid impact categories. A user who carefully reviewed a diff and selected only certain lines to commit can end up committing different content than what they approved, without any error or warning, because the line-selection model is positional rather than content-addressed and the patch used for staging is regenerated from live disk state instead of the reviewed diff. This can leak content the user explicitly deselected (privacy/secrets exposure) or omit content the user intended to include, and the corrupted commit can then be pushed.

### Likelihood Explanation
Likelihood is moderate: it requires the working file to change between diff render and commit click. This is realistic in ordinary developer workflows without any attacker needing local/admin access or malware — background tools (linters/formatters/watchers), editors with autosave, or another concurrently running Git operation on the same working tree are enough. No unnatural user steps are required beyond normal usage (leave the Changes view diff open, let a background process touch the file, then commit).

### Recommendation
- Bind `DiffSelection` to content rather than raw positional indices, or re-diff and re-validate the file's content/hash immediately before staging and compare against the hash used when the selection was made.
- If the file has changed since the diff was rendered, refuse to stage/commit and force the UI to refresh the diff and require the user to re-review/re-select before allowing commit, mirroring the existing "selection changed mid-load" bail-out pattern already used elsewhere in `app-store.ts` (e.g. `updateChangesWorkingDirectoryDiff`'s check that the selected file/diff hasn't changed before applying results) but applying it to the commit path itself.
- At minimum, in `applyPatchToIndex`, verify that the diff used to build the patch is the same diff the selection was derived from (e.g., via a diff/content checksum stored on `WorkingDirectoryFileChange`) before calling `git apply --cached`.

### Proof of Concept
1. Modify a tracked file with two clearly separated hunks (A and B).
2. Open the file in the Changes view; Desktop renders a diff and the user selects only hunk A for inclusion (unchecking hunk B).
3. Before clicking "Commit", have another process (e.g. a save-on-focus-loss editor, a file watcher, `prettier --write`, or a script under the user's control that runs periodically) rewrite the file, shifting hunk boundaries/line counts (e.g., adding a blank line before hunk A, or reformatting whitespace) while leaving the visual diff shown in Desktop's UI unrefreshed.
4. Click "Commit" without reopening/re-rendering the diff.
5. Observe that `applyPatchToIndex` re-diffs the now-modified file and applies the stale `DiffSelection` indices to the new hunk layout, causing `git apply --cached` to stage lines that do not correspond to what was visually checked in step 2 (verified by inspecting `git show --stat`/`git diff --cached` immediately after commit vs. what was displayed/selected in the UI).

**Uncertainty**: I could not fully inspect `app/src/models/diff.ts` (the `DiffSelection`/`isSelected` implementation) due to index limits, so the exact indexing semantics (e.g., whether it's a bitset over absolute indices, as implied by usage in `patch-formatter.ts`) are inferred from call sites rather than the class definition itself. A Devin session with full repository access would be needed to confirm the precise selection representation and validate the PoC end-to-end.
