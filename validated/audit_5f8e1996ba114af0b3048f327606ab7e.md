### Title
Unbounded buffer index read in `is_atom_canonical`/`is_clvm_canonical` causes crash on malformed spend-bundle CLVM buffer - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_clvm_canonical()` and its helper `is_atom_canonical()` in `chia/full_node/mempool_manager.py` parse an untrusted, attacker-controlled CLVM byte buffer (a coin spend's `puzzle_reveal` and `solution`) without validating that the current read `offset` stays within the buffer bounds before indexing into it. This mirrors the CVE-2019-11373 bug class: a length-prefix/atom parser that reads past the end of an untrusted buffer, causing an out-of-bounds read and a crash.

### Finding Description
`is_clvm_canonical` is called directly on every coin spend's serialized `puzzle_reveal` and `solution` during mempool admission: [1](#0-0) 

Both `is_clvm_canonical` and `is_atom_canonical` read `clvm_buffer[offset]` in a loop, advancing `offset` based on attacker-supplied length/pair bytes, but never check `offset < len(clvm_buffer)` before indexing except for a single `assert clvm_buffer != b""` guard at the very start: [2](#0-1) 

`is_atom_canonical` similarly advances `offset` while reading the multi-byte length-prefix without any bound check: [3](#0-2) 

Because a CLVM pair token (`0xFF`) increments `tokens_left` and advances `offset` without requiring any following bytes to actually exist, a single-byte buffer such as `b"\xff"` causes the very next loop iteration to index `clvm_buffer[1]` on a length-1 buffer, raising an unhandled `IndexError`. The same class of issue applies to the atom length-prefix path in `is_atom_canonical`, where declaring a large prefix length but not backing it with enough bytes causes `clvm_buffer[offset]` to run off the end while consuming prefix bytes.

`is_clvm_canonical` is reached from `validate_spend_bundle`, which is called by `add_spend_bundle`, itself invoked from `add_transaction` in the full-node transaction pipeline reachable by any wallet's `send_transaction` or any peer's `respond_transaction`: [4](#0-3) [5](#0-4) 

The transaction-processing task wraps this call in a broad `except Exception` and closes/bans the offending peer, so a single malicious/malformed spend bundle from an unprivileged submitter would trigger this handler: [6](#0-5) 

This means the practical impact is contained to that specific transaction-processing task raising an unhandled `IndexError` (not caught by the `ValidationError`-specific branch), being logged via `self.log.exception`, and the submitting peer being banned — rather than a full node crash. However, it is still an uncaught, unexpected exception path in consensus-adjacent transaction validation code that departs from the codebase's otherwise careful bounds-checked parsing (as seen everywhere else, e.g. `chia/util/streamable.py`'s `parse_bytes`/`parse_list`, and `chia/full_node/full_block_utils.py`'s `skip_bytes`/`skip_list`, all of which explicitly check remaining buffer length before indexing).

### Impact Explanation
An unprivileged spend-bundle submitter (wallet RPC `send_transaction` or a P2P peer via `respond_transaction`) can trigger an unhandled `IndexError` inside the mempool admission path by submitting a spend whose `puzzle_reveal` or `solution` contains a truncated CLVM buffer (e.g., a bare `0xFF` pair opcode with no following bytes, or a length-prefixed atom opcode with insufficient trailing bytes). This is a spend-triggered exception in transaction-processing code, distinguishing it from a benign validation rejection: instead of returning `Err.INVALID_COIN_SOLUTION` cleanly, the code raises `IndexError`, which is caught generically and results in peer banning and an exception being logged rather than a clean validation failure. This is a lower-severity variant of the reported bug class (crash-on-malformed-buffer) rather than the CVSS 6.5 memory-safety crash of the original C++ report, since Python bounds-checks the indexing and raises a catchable exception instead of reading arbitrary process memory.

### Likelihood Explanation
High likelihood of reachability: any wallet or peer can submit a spend bundle with an arbitrary `puzzle_reveal`/`solution` byte string, and `is_clvm_canonical` is unconditionally invoked on both fields for every coin spend during mempool admission before any CLVM execution occurs, so a crafted 1-2 byte buffer is trivial to construct.

### Recommendation
Add explicit bounds checks in `is_clvm_canonical` and `is_atom_canonical` before indexing `clvm_buffer[offset]`, mirroring the pattern used elsewhere in the codebase (`chia/full_node/full_block_utils.py`'s `skip_bytes`/`skip_list`, or `chia/util/streamable.py`'s `parse_bytes`), and return "not canonical" (or raise a caught `ValidationError`) instead of allowing an `IndexError` to propagate out of the parser.

### Proof of Concept
Submit a `CoinSpend` whose `solution` (or `puzzle_reveal`) is the single byte `b"\xff"`:
1. `is_clvm_canonical(b"\xff")` starts with `offset=0`, `tokens_left=1`.
2. `b = clvm_buffer[0] == 0xFF` → pair token → `tokens_left=2`, `offset=1`, loop continues.
3. Next iteration: `b = clvm_buffer[1]` → `IndexError: index out of range` on a length-1 `bytes` object, raised from inside `validate_spend_bundle` (called via `add_spend_bundle`/`add_transaction`), uncaught by the `ValidationError`-specific handler in `_handle_one_transaction`, landing in the generic `except Exception` branch that logs and bans the submitting peer.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

```python
def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```

```python
            response = wallet_protocol.TransactionAck(spend_name, uint8(MempoolInclusionStatus.SUCCESS), None)
            return make_msg(ProtocolMessageTypes.transaction_ack, response)
        high_priority = self.is_trusted(peer)
        queue_entry = TransactionQueueEntry(request.transaction, spend_name, None, test)
        try:
            self.full_node.transaction_queue.put(queue_entry, peer_id=peer.peer_node_id, high_priority=high_priority)
        except TransactionQueueFull:
            return make_msg(
                ProtocolMessageTypes.transaction_ack,
                wallet_protocol.TransactionAck(
                    spend_name, uint8(MempoolInclusionStatus.FAILED), "Transaction queue full"
                ),
            )
        try:
            with anyio.fail_after(delay=45):
                status, error = await queue_entry.done.wait()
        except TimeoutError:
            response = wallet_protocol.TransactionAck(spend_name, uint8(MempoolInclusionStatus.PENDING), None)
        else:
            error_name = error.name if error is not None else None
            if status == MempoolInclusionStatus.SUCCESS:
                response = wallet_protocol.TransactionAck(spend_name, uint8(status.value), error_name)
            # If it failed/pending, but it previously succeeded (in mempool), this is idempotence, return SUCCESS
            elif self.full_node.mempool_manager.get_spendbundle(spend_name) is not None:
```
