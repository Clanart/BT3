## Title
Deep-link `branch` parameter bypasses hyphen-stripping and reaches `git checkout` as an unguarded positional argument, enabling git option injection - (File: `app/src/lib/parse-app-url.ts`, `app/src/lib/git/checkout.ts`)

### Summary
The `setFee` report's core defect is "attacker/owner-controlled value accepted without the bounds check that other code paths rely on." The equivalent defect in GitHub Desktop is in the `x-github-client://openRepo/...?branch=` deep-link handler: the `branch` value is validated with `testForInvalidChars` only, while the function that actually *sanitizes* ref names for safe use (`sanitizedRefName`) additionally strips a leading `-`/`+` — a step the deep-link path skips entirely. That unstripped value is later placed as the first positional argument to `git checkout`, a slot where a leading `-` is interpreted as a CLI flag rather than as a ref name.

### Finding Description
`parseAppURL` accepts the `branch` query parameter from an `openRepo` deep link and only rejects it if `testForInvalidChars` matches: [1](#0-0) 

`testForInvalidChars` reuses `invalidCharacterRegex`, which blocks control characters, spaces, `~^:?*[\|"<>`, and a few structural sequences (`@{`, `..`, leading/trailing `.`, `.lock`, trailing `/`) — but it does **not** block a leading `-`: [2](#0-1) 

Notice `sanitizedRefName` (the function meant to make a ref name *safe*) explicitly strips leading `-`/`+` via `.replace(/^[-\+]*/g, '')`, but the deep-link validator (`testForInvalidChars`) never calls this stripping step — it only runs the regex `.test()`. This is exactly the "bounds check exists elsewhere but isn't enforced on this input path" pattern described in the fee report.

The branch string then flows: `dispatcher.openRepositoryFromUrl` → `openBranchNameFromUrl` → checkout of the branch name, ultimately reaching `getBranchCheckoutArgs`, which places `branch.name` as a bare positional argument immediately after `checkout`, with `--` only appended *after* it: [3](#0-2) [4](#0-3) 

Because `--` comes *after* the branch value instead of before it, a value such as `--orphan`, `--detach`, or `--track` is not protected: git's argv parser sees `git checkout --orphan --` and treats `--orphan` as a flag, not as the (nonexistent) branch `--orphan`. This lets a crafted branch string change what `git checkout` does rather than simply naming a ref — a form of git argument/option injection triggered purely by clicking an attacker-supplied link, with no local access, admin rights, or prior compromise required.

### Impact Explanation
An attacker who gets a victim to click a crafted `x-github-client://openRepo/<url>?branch=--orphan` (or similar flag-shaped value) link causes Desktop to run `git checkout` with attacker-chosen options instead of the intended read-only ref checkout. Depending on the flag, this can silently change repository state that the user goes on to commit/push (e.g., `--orphan` creates a disconnected root history, `--track`/`-b` semantics get reinterpreted), which matches the "silent corruption of what the user commits or pushes" impact bucket. It also demonstrates that Desktop's deep-link input validation is inconsistent with its own designated sanitizer (`sanitizedRefName`), the same "guard exists but isn't applied uniformly" defect class as the reported `setFee` bug.

### Likelihood Explanation
Medium. The attacker primitive (getting a user to click a link) is realistic and explicitly listed as in-scope ("a link or deep link the user clicks"). The exact severity of the injected flag's effect depends on which `git checkout` option is chosen and current repository state (e.g., whether there are uncommitted changes), so not every crafted value produces a high-impact outcome, but the underlying validation gap is unconditional and deterministic — `testForInvalidChars` will accept any branch string starting with `-` as long as it avoids the small blocked character set.

### Recommendation
In `parseAppURL`, reject (or sanitize via `sanitizedRefName`) any `branch` value that starts with `-`/`+` before returning it in `IOpenRepositoryFromURLAction`, mirroring the stripping already performed by `sanitizedRefName`. Additionally, harden `getBranchCheckoutArgs` to place the `--` end-of-options marker *before* the branch name (or otherwise ensure branch/ref arguments can never be parsed as options), independent of what upstream validation does, so this class of issue can't recur via a different entry point.

### Proof of Concept
1. Attacker crafts and distributes: `x-github-client://openRepo/https://github.com/<owner>/<repo>?branch=--orphan`
2. Victim (who has GitHub Desktop installed and registered as the protocol handler) clicks the link.
3. `parseAppURL` returns `{ name: 'open-repository-from-url', url: '...', branch: '--orphan', pr: null, filepath: null }` because `testForInvalidChars('--orphan')` returns `false` (no blocked characters present). [5](#0-4) 
4. `dispatcher.openRepositoryFromUrl` routes to `openBranchNameFromUrl(url, '--orphan')`, which clones/opens the repo and checks out the "branch." [4](#0-3) 
5. The checkout call ultimately runs `git(['checkout', '--orphan', '--'], ...)` per `getBranchCheckoutArgs`, causing git to execute an orphan checkout instead of failing with "branch not found," silently altering the repository state the user will subsequently work from.

Note: I was not able to fully trace `checkoutLocalBranch` in `dispatcher.ts` end-to-end within this session (the exact intermediate function that turns the raw string into a `Branch` object before calling `checkoutBranch` was not retrieved), so the final git invocation shape should be re-verified against that function before treating this as fully confirmed.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }
