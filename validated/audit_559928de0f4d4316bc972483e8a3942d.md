### Title
`SignableTransaction::new` omits the `OP_RETURN` output from fee and weight calculations - ([File: `networks/bitcoin/src/wallet/send.rs`])

### Summary

`SignableTransaction::new` appends the attacker-influenced `OP_RETURN` output to `tx_outs`, but then calculates the transaction weight and required fee using only `payments`, without that output. The same stale output set is used when calculating the fee with change, so the resulting signed transaction can have a materially lower feerate than requested and can fall below Bitcoin's minimum relay feerate. [1](#0-0) [2](#0-1) 

### Finding Description

The constructor allows up to 80 bytes of caller-provided `data` and converts it into a zero-valued `OP_RETURN` output before constructing the transaction. [3](#0-2) 

Despite adding that output, the initial call to `calculate_weight_vbytes` passes only `tx_ins.len()`, `payments`, and `None`; `tx_outs`, including the newly appended `OP_RETURN`, is not used. [4](#0-3) 

`calculate_weight_vbytes` builds its synthetic transaction directly from the supplied `payments` and optional `change`, so omitting `data` causes both `weight` and `vbytes` to be calculated for a smaller transaction than the one ultimately signed. [5](#0-4) 

The change path repeats the stale calculation by passing `payments` and `change`, again without the `OP_RETURN`; the resulting change amount is then calculated using the under-estimated `fee_with_change`. [2](#0-1) 

The minimum-feerate check is also performed against the stale `vbytes`, so an 80-byte payload can move a transaction that nominally satisfies `DEFAULT_MIN_RELAY_TX_FEE` below the minimum after the output is serialized. [6](#0-5) 

### Impact Explanation

A caller can cause the threshold wallet to construct and sign a transaction whose actual serialized size is larger than the size used to derive its fee. With `fee_per_vbyte` selected to barely satisfy the requested or minimum relay rate, the final transaction's effective feerate will instead be below that threshold. [7](#0-6) 

When change is present, the wallet commits to the under-estimated `fee_with_change` by assigning all remaining value to the change output, so the signed transaction does not merely overpay safely; it retains the incorrect absolute fee while carrying the additional output. [2](#0-1) [8](#0-7) 

The resulting sighash commits to the incorrect fee/output construction through `Prevouts::All`, and every threshold participant signs that stale-fee transaction rather than one satisfying the caller-specified `fee_per_vbyte`. [9](#0-8) 

This can make a correctly authorized spend unrelayable or stuck until reconstructed, preventing the multisig's funds from being moved as intended. The omitted weight is also not included in the `MAX_STANDARD_TX_WEIGHT` check, so a large `OP_RETURN` can push an otherwise boundary-sized transaction over the standardness limit. [10](#0-9) 

### Likelihood Explanation

The bug is reachable through ordinary use of the public `SignableTransaction::new` API whenever `data` is `Some`; no malicious validator, private-key access, malformed encoding, or special chain state is required. [11](#0-10) 

The function explicitly accepts up to 80 bytes of data, and every such transaction follows the stale-weight path. [12](#0-11) 

For an 80-byte payload, the omitted serialized cost is approximately an entire additional output, including its eight-byte value, script length, `OP_RETURN`, push operation, and payload; this is enough to reduce a boundary feerate below the relay minimum. [13](#0-12) 

### Recommendation

Calculate weight and virtual size from the complete `tx_outs` after the `OP_RETURN` has been appended, rather than from `payments`.

Concretely, either extend `calculate_weight_vbytes` to accept the complete output list, or pass an output list containing `tx_outs` plus the candidate change output. Recalculate `needed_fee`, minimum-relay eligibility, funding sufficiency, change, and `MAX_STANDARD_TX_WEIGHT` against that complete transaction shape. [14](#0-13) 

The change calculation should also compare the post-change remainder against a fee derived from the transaction containing both the `OP_RETURN` and change outputs. [2](#0-1) 

### Proof of Concept

The construction demonstrates the stale calculation without requiring private-key access:

```rust
// Conceptual PoC against networks/bitcoin/src/wallet/send.rs.

let data = vec![0xaa; 80];

let tx = SignableTransaction::new(
    vec![received_output],
    &[(payment_script, payment_amount)],
    Some(change_script),
    Some(data),
    1, // fee_per_vbyte, equal to the default minimum relay rate
)?;
```

`SignableTransaction::new` creates an `OP_RETURN` output from `data`, but obtains `vbytes` from a transaction containing only `payments`. [13](#0-12) 

With `fee_per_vbyte == 1`, `needed_fee` equals the stale `vbytes`; after serialization, however, `tx.vsize()` is larger because the `OP_RETURN` output is present in `tx.output`. [7](#0-6) [8](#0-7) 

The same stale fee is committed to the change output when change is enabled, and the transaction is then signed using `Prevouts::All`, producing a fully signed transaction whose actual feerate is below the caller-specified and minimum relay rate. [2](#0-1) [9](#0-8)

          script_pubkey: payment.0.clone(),
        })
        .collect(),

      // the value is fixed size (so any value could be used here)
