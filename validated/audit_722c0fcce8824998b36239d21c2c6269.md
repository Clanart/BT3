### Title
Vote weight recorded in `WombatBribeManager` is not re-validated against the user's current `vlMGP` locked balance, allowing free-riding on bribe rewards after unlocking - (File: wombat/WombatBribeManager.sol)

### Summary
`WombatBribeManager.vote()` only checks that a user's cumulative recorded vote (`userTotalVotedInVlmgp`) does not exceed their currently locked `vlMGP` balance (`getUserVotable`) **at the moment `vote()` is called**. This is the same "stale accounting" bug class as the Olympus report: a value that should track a dynamic, ever-changing quantity (the user's real backing balance) is instead pinned at the time of the triggering transaction and never re-checked or re-synced when the underlying balance later shrinks.

### Finding Description
`vote()` enforces the sufficiency check only inline: [1](#0-0) 

`getUserVotable()` reads the user's *current* locked amount from `VLMGP`: [2](#0-1) 

`VLMGP.getUserTotalLocked()` is dynamic — it derives the locked amount from `MasterMagpie`'s staking info minus whatever is currently in a cool-down/unlock slot: [3](#0-2) 

Once `vote()` succeeds and calls `IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, delta)`, the reward-pool balance (`_balances[msg.sender]`) and the aggregate accounting variables `pool.totalVoteInVlmgp` / `totalVlMgpInVote` are updated and then **persist independently of the user's actual lock**: [4](#0-3) 

There is no hook from `VLMGP`'s unlock/cool-down flow back into `WombatBribeManager` to reduce `userVotedForPoolInVlmgp` / `userTotalVotedInVlmgp` / `pool.totalVoteInVlmgp` / `totalVlMgpInVote` or to call `withdrawFor` on the reward pool when a user starts or completes an unlock. The only path that decrements these values is an explicit, voluntary call to `vote()` (with a negative delta) or `unvote()`: [5](#0-4) 

Because the check `userTotalVotedInVlmgp[msg.sender] > getUserVotable(msg.sender)` only runs during a fresh `vote()` call, a user can lock MGP, vote with the full locked amount, then unlock/withdraw the MGP from `VLMGP` entirely (reducing `getUserTotalLocked` to zero) while their recorded vote and their `BribeRewardPool` stake balance remain unchanged forever, unless they voluntarily call `unvote()`.

### Impact Explanation
- `pool.totalVoteInVlmgp` and `totalVlMgpInVote` remain permanently inflated by votes that no longer have real locked MGP behind them, which is used directly to compute the proportional WOM vote sent to Wombat in `castVotes()`: [6](#0-5) 
  This misallocates real WOM voting power/bribe direction away from what actual current lockers hold.
- The user's stake in `DelegateVoteRewardPool`/`BribeRewardPool` (`_balances[msg.sender]`) is untouched by the unlock, so the free-riding user keeps earning bribe rewards pro-rata to a balance that no longer corresponds to any locked MGP, diluting the rewards legitimately earned by other, still-locked voters — this is a permanent, ongoing theft of unclaimed yield from genuine lockers.
- This is reachable purely through an ordinary wallet's own transactions (lock → vote → unlock), with no privileged role required.

### Likelihood Explanation
High — any user can trigger this by simply calling `vote()` and then unlocking through the normal `VLMGP` unlock flow; there is no economic barrier or special timing required, and the discrepancy persists indefinitely until (if ever) the user calls `unvote()`.

### Recommendation
Enforce synchronization between `VLMGP` lock changes and `WombatBribeManager` vote accounting: have `startUnlock`/`unlock`/`forceUnlock` in `VLMGP` (or a wrapper) automatically reduce/settle the caller's outstanding votes and reward-pool stake proportionally, or require `WombatBribeManager` to re-validate `userTotalVotedInVlmgp[user] <= getUserVotable(user)` on every reward claim/harvest, reverting or auto-adjusting stale entries down to the current locked balance before paying out rewards.

### Proof of Concept
1. User locks `1000` MGP via `VLMGP`, so `getUserTotalLocked(user) == 1000`.
2. User calls `WombatBribeManager.vote([poolA], [1000])`. This sets `userVotedForPoolInVlmgp[user][poolA] = 1000`, `userTotalVotedInVlmgp[user] = 1000`, `totalVlMgpInVote += 1000`, `poolA.totalVoteInVlmgp += 1000`, and `BribeRewardPool(poolA).stakeFor(user, 1000)` sets `_balances[user] = 1000`. The check `userTotalVotedInVlmgp[user] (1000) > getUserVotable(user) (1000)` is false, so it passes.
3. User calls `VLMGP.startUnlock(1000)` and, after the cool-down, `unlock()`, withdrawing all MGP. `getUserTotalLocked(user)` is now `0`.
4. `userTotalVotedInVlmgp[user]` is still `1000`; nothing in the unlock path calls back into `WombatBribeManager`.
5. User keeps calling `claimBribe`/`claimAllBribes` and continues to receive bribe rewards proportional to `_balances[user] = 1000` in `poolA`'s `BribeRewardPool`, and `poolA.totalVoteInVlmgp`/`totalVlMgpInVote` remain permanently inflated, skewing `castVotes()` allocation, indefinitely diluting rewards for legitimate lockers.

    function unvote(address _lp) public {

        uint256 currentVote = userVotedForPoolInVlmgp[msg.sender][pool.poolAddress];
        if(!pool.isActive)

            totalVlMgpInVote -= currentVote;

    }
