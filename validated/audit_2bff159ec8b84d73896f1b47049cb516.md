### Title
Ankr time-lock (`unlockTime`/`lockedAmount`) can be bypassed by calling `MasterMagpie.withdraw()` directly, since the lock is enforced only in `AnkrBNBPoolHelper` and not on the underlying stake - (File: wombat/AnkrBNBPoolHelper.sol)

### Summary
`AnkrBNBPoolHelper.withdraw()` enforces `unlockTime`/`lockedAmount[msg.sender]` only inside its own code path [1](#0-0) , but the actual position it is guarding is an ordinary `MasterMagpie` stake of `stakingToken` keyed by `userInfo[stakingToken][msg.sender]` [2](#0-1) . `MasterMagpie` exposes a fully permissionless `withdraw(address _stakingToken, uint256 _amount)` entrypoint that any user can call directly on their own position, with no notion of `unlockTime` or `lockedAmount` at all [3](#0-2) . An attacker who received a locked position via `batchDepositLPFor` (which sets `lockedAmount[_for[i]]` and stakes via `depositFor`) [4](#0-3)  can simply call `MasterMagpie.withdraw(stakingToken, amount)` directly, completely skipping `AnkrBNBPoolHelper.withdraw()` and its lock check.

### Finding Description
The lock state (`unlockTime`, `lockedAmount`) lives only in `AnkrBNBPoolHelper` [5](#0-4) . The actual custody of the locked value is the user's `userInfo[stakingToken][msg.sender].amount`/`.available` inside `MasterMagpie`, populated via `depositFor` (only callable by the registered pool `helper` via `_onlyPoolHelper`) [6](#0-5) .

However, unstaking is not similarly restricted: `MasterMagpie.withdraw()` is public/external, restricted only by `whenNotPaused`/`nonReentrant`, and operates on `msg.sender`'s own position with zero knowledge of any external helper's lock bookkeeping [3](#0-2) . Internally `_withdraw` -> `_harvestAndUnstake` only checks `user.available < _amount` [7](#0-6) , then transfers `stakingToken` straight to `msg.sender` [8](#0-7) .

Exploit flow:
1. A user is granted a locked position via `AnkrBNBPoolHelper.batchDepositLPFor`, which sets `lockedAmount[user] += amount` and calls `IMasterMagpie(masterMagpie).depositFor(stakingToken, amount, user)` [9](#0-8) .
2. Before `unlockTime`, the user does **not** call `AnkrBNBPoolHelper.withdraw()` (which would correctly block them via the `lockedAmount[msg.sender] > rest` check) [10](#0-9) .
3. Instead, the user calls `MasterMagpie.withdraw(stakingToken, amount)` directly. This function has no awareness of `AnkrBNBPoolHelper.lockedAmount`/`unlockTime` and unconditionally transfers the `stakingToken` (the receipt token representing the locked wombat LP position) back to the caller once `user.available >= amount` [3](#0-2) .
4. The user now holds the raw `stakingToken`/receipt token outside of any lock enforcement, fully bypassing the 1-year Ankr compensation lock.

This confirms the audited invariant violation: the time restriction is enforced only inside the optional front-end contract (`AnkrBNBPoolHelper`), not at the level where the position actually lives (`MasterMagpie`'s `userInfo` and the corresponding `stakingInfo`). No existing modifier, `nonReentrant`, or `whenNotPaused` check in `MasterMagpie.withdraw()` reconciles against `AnkrBNBPoolHelper.lockedAmount`, so the restriction is trivially bypassable without going through the wombat pool at all (the sandwich/`_minimumLiquidity`-based framing in the question is unnecessary — a much simpler direct call to `MasterMagpie.withdraw()` achieves full bypass).

### Impact Explanation
Any recipient of an Ankr-locked, time-restricted compensation position can withdraw their entire "locked" `stakingToken` balance immediately, regardless of `unlockTime`, and regardless of `lockedAmount` bookkeeping in `AnkrBNBPoolHelper`. This defeats the entire purpose of the one-year lock mechanism designed to protect compensation funds, matching a Critical severity impact class ("bypass of a designed vesting/lock restriction leading to unauthorized early withdrawal of funds meant to be time-locked").

### Likelihood Explanation
This requires no special capital, no sandwich attack, no flash loan, and no privileged role — only an unprivileged EOA holding a locked position calling a fully public function (`MasterMagpie.withdraw`) that already exists in the deployed contract. It is deterministic and repeatable by every affected locked-position holder at any time before `unlockTime`.

### Recommendation
Enforce the lock at the position layer, not only in the helper: e.g., add a lock/available-amount check directly inside `MasterMagpie._withdraw`/`withdraw` (or a dedicated lock registry consulted by `MasterMagpie`) so that any withdrawal path — whether through `AnkrBNBPoolHelper` or the direct `MasterMagpie.withdraw`/`emergencyWithdraw` — respects `unlockTime`/`lockedAmount`. Alternatively, mark Ankr-locked `stakingToken` positions as "locked" (non-`available`) in `MasterMagpie.userInfo` until `unlockTime`, so `withdraw()`'s existing `user.available < _amount` check naturally blocks early withdrawal without relying on the helper being used.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `MasterMagpie`, `WombatStaking`, `AnkrBNBPoolHelper` with a future `unlockTime` (e.g., `block.timestamp + 365 days`), and register `AnkrBNBPoolHelper` as the pool `helper` for `stakingToken` in `MasterMagpie`.
2. As `ankrOperator`, call `AnkrBNBPoolHelper.batchDepositLPFor(lpAmount, [attacker], [100000])`, which sets `lockedAmount[attacker] = lpAmount` and stakes `lpAmount` into `MasterMagpie` on `attacker`'s behalf via `depositFor`.
3. Assert `AnkrBNBPoolHelper.balance(attacker) == lpAmount` and `MasterMagpie.stakingInfo(stakingToken, attacker) == (lpAmount, lpAmount)`.
4. As `attacker` (unprivileged EOA, no special role), call `AnkrBNBPoolHelper.withdraw(lpAmount, 0)` — assert this **reverts** with `NotAllowed` because `unlockTime > block.timestamp` and `lockedAmount[attacker] > rest`.
5. As `attacker`, instead call `MasterMagpie.withdraw(stakingToken, lpAmount)` directly — assert this **succeeds**, `stakingToken` is transferred to `attacker`, and `MasterMagpie.stakingInfo(stakingToken, attacker).amount == 0`, even though `block.timestamp < unlockTime` and `AnkrBNBPoolHelper.lockedAmount[attacker] == lpAmount` was never reset.
6. Assert the invariant violation: `IERC20(stakingToken).balanceOf(address(AnkrBNBPoolHelper)) delta` does not match any accounting inside `AnkrBNBPoolHelper`, and the locked position was fully liquidated bypassing the one-year restriction.

        if (msg.sender != ankrOperator) revert NotAllowed();
        if (_for.length != _ratios.length) revert LengthMisMatch();
        
        uint256 totalRatio=0;
        for(uint256 i=0; i<_ratios.length; ++i){
            totalRatio+=_ratios[i];
        }
        if(totalRatio != DENOMINATOR) revert NotAllowed();

        uint256 beforeDeposit = IERC20(stakingToken).balanceOf(address(this));
        IWombatStaking(wombatStaking).depositLP(lpToken, _lpAmount, msg.sender);
        uint256 lpAmount = IERC20(stakingToken).balanceOf(address(this)) - beforeDeposit;

        IERC20(stakingToken).safeApprove(masterMagpie, lpAmount);

            uint256 amount = lpAmount * _ratios[i] / DENOMINATOR;
            lockedAmount[_for[i]] += amount;
            IMasterMagpie(masterMagpie).depositFor(stakingToken, amount, _for[i]);
            emit NewBatchDeposit(_for[i], amount);
        }
    }
