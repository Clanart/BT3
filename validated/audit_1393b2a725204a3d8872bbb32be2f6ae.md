### Title
Early-return in `KeyMachine::calculate_share` emits a blame proof (revealing the ECDH shared key) before the message's proof-of-possession is verified — ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
Analogous to CVE-2020-18972 (exposure of sensitive information to an unauthorized actor via untrusted-input handling), `KeyMachine::calculate_share` returns an `EncryptionKeyProof` — which contains the recipient's ECDH shared key `key = enc_scalar * msg.key` plus a DLEq — when a decrypted share fails `C::F::from_repr`, *before* the batch containing the message's `pop` Schnorr PoP is ever verified. This re-enables exactly the key-reuse attack the PoP was added to prevent, letting a participant force disclosure of the ECDH key for a per-message key they do not own and thereby decrypt another sender's secret-share message.

### Finding Description
`Encryption::decrypt` computes `key = ecdh(&self.enc_key, msg.key)`, applies the ChaCha20 cipher, queues `msg.pop` into the batch verifier, and unconditionally returns `(msg.msg, EncryptionKeyProof { key, dleq })` [1](#0-0) .

In `KeyMachine::calculate_share`, the loop immediately errors out with `PedPoPError::InvalidShare { blame: Some(blame) }` if the decrypted bytes are not a canonical scalar — this happens *before* `batch.verify_with_vartime_blame()` runs, so a failure of `msg.pop` under `BatchId::Decryption(l)` is never observed on this path [2](#0-1) .

The `EncryptedMessage::pop` field exists specifically to stop this: the comment explains that without it, Eve can copy Alice's per-message key `X` into Eve's own message to Bob; Bob's blame then reveals `bX`, decrypting Alice's message to Bob [3](#0-2) . Because the blame is emitted on the `from_repr` early-return without verifying the PoP, Eve can attach *any* `pop` bytes — verification failure is only detected in the batch, which is never reached.

The `Decryption::decrypt_with_proof` path used for blame adjudication does check `msg.pop.verify` first [4](#0-3) , so the published blame will correctly attribute fault to Eve — but by then Bob has already broadcast `bX`, and the secret share Alice encrypted to Bob is permanently disclosed.

### Impact Explanation
The published `EncryptionKeyProof.key` is `b·X` where `b` is Bob's registered encryption scalar and `X` is the per-message key Alice used when encrypting a FROST/PedPoP secret share to Bob. Anyone holding the public blame can run `cipher(context, bX)` and recover Alice's share contribution to Bob. Combined with other leaked/observed shares, this enables recovery of participants' threshold key shares — key share recovery, which is within the accepted impact classes. This mirrors the CVE's class: parsing/handling untrusted input leaks secret material to an unauthorized party.

### Likelihood Explanation
Requires Eve to be a DKG participant (sending a `shares` map entry to Bob) and to have observed an `EncryptedMessage` Alice sent to Bob — per the design these messages traverse authenticated but observable channels, and the code's own comments treat observation of `key X` as the threat model. The early return only fires when `bX`-decrypted bytes are non-canonical (~50% for a 255-bit field over 32 bytes); since the PoP is never checked on this path, Eve can simply retry with fresh garbage ciphertexts until Bob emits `blame: Some(..)`. Bob then publishes the blame via `ProcessorMessage::InvalidShare` [5](#0-4) . Eve is blamed after the fact, but the leak is already irreversible — a rational adversary trading their slash for another participant's share may still profit.

### Recommendation
Do not release an `EncryptionKeyProof` for a message whose `pop` has not been verified. Concretely, in `KeyMachine::calculate_share`, verify `msg.pop` (or the `BatchId::Decryption` result) *before* returning `blame: Some(..)` on the `from_repr` error — e.g., run the batch verification first and return `blame: None` for any `l` whose PoP is invalid, or check `msg.pop.verify` inline inside `Encryption::decrypt` and withhold the proof. Alternatively, withhold blame publication until PoP validity is confirmed for that message.

### Proof of Concept
1. Alice (`ONE`) runs `generate_secret_shares`, producing `EncryptedMessage` to Bob (`TWO`) with per-message key `X = C::generator() * x`; ciphertext `c = share_alice XOR ChaCha20(H(bX))`.
2. Eve (`THREE`) observes `X` (it is the public `key` field). Eve constructs `EncryptedMessage { key: X, pop: <arbitrary bytes>, msg: <random 32 bytes> }` — no knowledge of `x` needed since PoP is never verified on the failing path — and sends it to Bob as her share.
3. Bob's `calculate_share` calls `self.encryption.decrypt`, queuing the invalid `pop` into the batch and computing `key = bX`; the keystream decrypts Eve's garbage `msg`.
4. With probability ~1/2, `C::F::from_repr` fails and `calculate_share` returns `InvalidShare { participant: THREE, blame: Some(EncryptionKeyProof { key: bX, dleq }) }` — returned before `batch.verify_with_vartime_blame()` is ever invoked, so Eve's invalid PoP is never detected. Otherwise Eve retries.
5. Bob publishes the blame (`ProcessorMessage::InvalidShare`). `AdditionalBlameMachine::blame` correctly blames Eve (`pop` fails in `decrypt_with_proof`), but `bX` is now public.
6. Anyone computes `cipher::<C>(context, bX).apply_keystream(c)` and recovers Alice's secret share to Bob — the exact disclosure the PoP comment describes as "a massive side effect," achieved because the PoP is unverified when the blame is produced.
