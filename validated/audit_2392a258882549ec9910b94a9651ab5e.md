## Confirmed staleness-based analog found

### Title
Copilot conflict resolution writes a stale reassembled file, silently discarding on-disk changes made during the AI round trip - (File: `app/src/lib/stores/app-store.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The C4 report's broken invariant is: a value captured at *initiation* (the penalty fee) is applied unmodified at *completion* time even though it may have drifted, and the contract has no mechanism to detect or reject that drift. The same pattern exists in Desktop's Copilot-assisted merge/rebase/cherry-pick conflict resolution: the "ours" file content used to reconstruct the final resolved file is captured once when the AI request starts, and is spliced/written back verbatim when the user accepts — with only a narrow staleness check that doesn't cover the actual corrupted value.

### Finding Description
`buildConflictContext` reads each conflicted file from disk once and stores its full text in `rawContent` on `IFileConflictContext` [1](#0-0) , explicitly documented as being "used after the model responds to reassemble the resolved file by splicing per-hunk resolutions into the original content" [2](#0-1) .

This `rawContent` snapshot is later used, potentially long after (the AI call is asynchronous and can take a while, plus the user can review the result dialog before accepting), by `reassembleResolutions`/`reassembleResolvedFile` to reconstruct the "final" file content purely from the stale snapshot plus the model's hunk outputs — it never re-reads the file from disk at this point [3](#0-2) .

When the user accepts the resolution, `_applyCopilotConflictResolutions` (around app-store.ts lines 7171-7270) only guards against one specific case — a file that has been *completely* resolved externally (no conflict markers left) is skipped [4](#0-3) . It does **not** check whether the file still has conflict markers but its content otherwise diverged from the `rawContent` snapshot (e.g. the user made an edit outside the markers, a build tool/formatter touched the file, or another Desktop-triggered git operation altered it while the network round trip to Copilot was in flight). In that case `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` unconditionally overwrites the current on-disk file with content reconstructed from the earlier snapshot, silently discarding whatever changed in the meantime [5](#0-4) .

This is structurally identical to the SecondSwap bug: a "price" (here, the authoritative file content used to satisfy the conflict) is fixed at the start of an operation, and is applied at settlement time (`writeFile`) without re-validating that it is still current, and the only existing guard checks a narrow, unrelated condition ("are there still markers at all?") rather than "has the underlying value the transaction depends on changed?"

### Impact Explanation
The result is silent corruption of what the user commits/pushes: the app writes file content the user never actually approved for the file's *current* state, and then stages it (`git add`) so it becomes part of the merge/rebase/cherry-pick commit [6](#0-5) . Any manual edits or non-conflict-marker changes made to the working tree between the moment the Copilot request started and the moment the user clicks "Accept" are silently discarded and replaced by the stale, model-derived version — without any diff/warning shown to the user. This matches the "silent corruption of what the user commits or pushes" impact category directly.

### Likelihood Explanation
This is reachable in the normal, unprivileged product flow (any multi-commit operation with conflicts where the user opts into Copilot resolution), requires no special repository content, and the window between context capture and file write is naturally non-trivial (network round trip to an LLM, plus user review time in the result dialog before clicking Accept). The existing "already resolved" check demonstrates the developers were aware of *a* staleness risk but only closed the fully-resolved case, leaving the partially-diverged case open.

### Recommendation
Before writing `resolution.resolvedContent`, re-read the current on-disk file and verify the "outside-hunk" regions and the still-present conflict markers still match what was captured in `rawContent` (e.g. hash the `rawContent` at context-build time and compare against a fresh hash of the on-disk file, not just checking `hasUnresolvedConflicts`). If they differ, skip the write and surface it as a per-file skip/conflict in the result dialog, mirroring the existing "resolved externally" handling.

### Proof of Concept
1. Start a rebase/merge with a conflicted file, opt in to "Resolve with Copilot".
2. While the request is in flight (or while the result dialog is open, before clicking Accept), manually edit a *non-conflicted* line in the same file (still leaving the conflict markers intact) — e.g. fix a typo elsewhere in the file.
3. Click "Accept" in the result dialog.
4. Observe: `_applyCopilotConflictResolutions` finds the file still has unresolved-conflict status (guard at lines 7250-7256 doesn't trigger), and calls `writeFile` with `resolvedContent` built from the pre-edit `rawContent` snapshot [7](#0-6)  — the manual typo fix made in step 2 is silently lost, and the committed file matches the stale, pre-edit snapshot instead of the user's latest working-tree state.

```typescript
export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
```
