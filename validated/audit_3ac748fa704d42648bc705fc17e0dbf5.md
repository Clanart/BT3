### Title
BIP-340 FROST algorithm omits group-key parity negation — signatures under an odd-Y group key are invalid and funds become unspendable - (File: networks/bitcoin/src/crypto.rs)

### Summary
`networks/bitcoin/src/crypto.rs` implements a BIP-340-compatible FROST `Algorithm`. It correctly handles the BIP-340 even-Y requirement for the nonce commitment `R` (negating the challenge in `Hram::hram` and negating `s` in `verify`), but never applies the required parity normalization to the **secret key / group key**. BIP-340 defines verification against the x-only key lifted to even Y, i.e. the effective secret is `-a` when `A = aG` has odd Y. Because the internal pre-check `self.0.verify(group_key, ...)` verifies against the raw (possibly odd-Y) `group_key`, the algorithm emits a signature it considers valid that fails on-chain BIP-340 verification for any key whose x-only pubkey has odd Y.

### Finding Description
The parity handling that exists is incomplete — a partial application of the parity fix, mirroring the CVE class where a required fix is only partially present:

- `Hram::hram` negates `c` when `R` is odd, so signers effectively compute `r - ca` for odd `R`: [1](#0-0) 
- `verify` negates the summed `s` when `R` is odd, producing `s = -r + ca` matching the even-Y `R`: [2](#0-1) 
- `sign_share` delegates to the generic FROST Schnorr path using `params.secret_share()` and `params.group_key()` unmodified: [3](#0-2) [4](#0-3) 
- The internal validity check in `verify` uses `SchnorrSignature::verify(group_key, c)` against the raw `group_key` point, not the even-Y lift `x(A)`, so the inconsistency is never detected before the signature is returned: [5](#0-4) 

There is no `needs_negation(&group_key)` call anywhere on the secret-share/group-key path — `needs_negation` is only ever applied to `R`: [6](#0-5) 

### Impact Explanation
For any threshold group key `A` with odd Y (~50% of randomly generated DKG keys), every emitted 64-byte signature fails BIP-340 verification: the signer produces `sG = -R + cA` while a BIP-340 verifier checks `sG = R_even + c·lift_x(x(A)) = -R + c·(-A)`. These are equal only when `A` already has even Y. Taproot spends signed by this algorithm would be rejected by consensus, and the failure is deterministic per key — retries cannot help, so funds controlled by an odd-Y threshold key are unspendable through this signing path. The internal `verify` gate in `AlgorithmSignatureMachine::complete` passes, so the invalid signature is returned as if successful: [7](#0-6) 

### Likelihood Explanation
Reachability requires only that the aggregated FROST group key has odd Y, an unbiased coin flip per key set. No attacker action is needed; this is a correctness/consensus failure of the verifier formula rather than an exploit requiring malicious input. It qualifies as an incorrect verifier formula / funds-not-spendable analog. Caveat: the wallet layer (`networks/bitcoin/src/wallet/mod.rs`) does reference `needs_negation`/`offset`, and if the wallet unconditionally offsets keys to even-Y parity before invoking this `Algorithm`, the reachable impact is reduced — that interaction could not be fully verified within the search budget.

### Recommendation
In `frost_crypto::Schnorr`, normalize the key parity the same way the nonce parity is handled: when `needs_negation(&group_key)` is set, the effective secret share must be negated (e.g., apply the negation inside `sign_share`/`verify_share` via a conditional select on the share, or document and enforce that callers only use even-Y group keys with a check that rejects odd-Y keys). The internal `verify` should check `sG == R_even + c·lift_x(A)` so the self-check matches on-chain BIP-340 semantics.

### Proof of Concept
1. Run PedPoP/FROST DKG to produce `ThresholdKeys` whose `group_key()` has odd Y (repeat until parity is odd; ~2 attempts).
2. Sign any message with `frost_crypto::Schnorr::new()`. `complete` returns a `Some([u8; 64])` signature because `SchnorrSignature::verify(group_key, c)` passes against the raw odd-Y `A`.
3. Feed `(x(A), sig)` to a standard BIP-340 verifier (e.g., `bitcoin::key::XOnlyPublicKey::verify` or libsecp256k1 `schnorrsig_verify`). Verification fails because `sG = R_even + cA` but the verifier checks `sG = R_even + c·(-A)`.
