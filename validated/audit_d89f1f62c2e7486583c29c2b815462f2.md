### Title
Fee/vbytes computed over mismatched output set — OP_RETURN data output omitted from `calculate_weight_vbytes` - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report describes a "mismatched data type" bug: a function computed/returned a value whose contents didn't match what the caller expected, producing an incorrect result. The Serai analog lives in `SignableTransaction::new`: the transaction weight and vbyte calculation is performed over the `payments` slice, but the OP_RETURN `data` output — which is appended to `tx_outs` — is never included in that calculation. The expected input to the size computation (all outputs that will be in the transaction) doesn't match the actual input (payments only), so `needed_fee`, `vbytes`, the minimum-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` check are all computed against a transaction that is smaller than the one actually produced.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` before the weight/vbytes are computed:

```rust
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` is invoked with `payments`, which does **not** contain the OP_RETURN output. Consequently:

- `vbytes` (and `weight`) understate the real transaction by the size of the OP_RETURN output (~9 bytes fixed overhead + ~34-byte script + up to 80 bytes of pushed data, i.e., up to ~113 vbytes / ~452 WU).
- `needed_fee = fee_per_vbyte * vbytes` is therefore smaller than the fee required to actually achieve `fee_per_vbyte` on the final transaction.
- The minimum-relay-fee guard `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` is evaluated against the understated `vbytes`, so it can pass while the *realized* fee rate of the broadcast transaction is below the network minimum relay fee.
- The `weight > MAX_STANDARD_TX_WEIGHT` check is evaluated against the understated weight.

The change-output path correctly recomputes weight with `Some(&change)` (`fee_with_change`), confirming the intended invariant is "compute size over the complete output set" — the data output simply escaped that invariant.

### Impact Explanation
When a non-empty `data` payload is supplied, the produced transaction systematically pays a lower effective fee rate than the caller requested. In the worst case, a transaction constructed right at the relay-fee boundary will be created that no default-policy node will relay or mine — the funds are committed to a transaction that is economically/broadcast-stuck until replaced (which requires a fresh signing round). Since the fee is `sum(inputs) - sum(outputs)` and the change output was sized using the same understated vbytes, the shortfall cannot be absorbed retroactively. This is a liveness/DoS-style impact on the signing pipeline for any transaction carrying OP_RETURN data, reachable purely from the transaction-construction inputs.

### Likelihood Explanation
Any caller of `SignableTransaction::new` that passes `Some(data)` triggers the miscalculation; the severity of the consequence depends on how close `fee_per_vbyte` is to the minimum relay fee. With a large `data` payload (up to 80 bytes) and a low fee rate, the discrepancy is largest. It requires no malicious counterparty — only the ordinary code path of constructing a data-carrying transaction.

### Recommendation
Include the OP_RETURN output in the size/fee calculation. Either build the complete `payments`/`tx_outs` list (payments + OP_RETURN + optional change) before calling `calculate_weight_vbytes`, or pass the OP_RETURN output into `calculate_weight_vbytes` so `vbytes`, `needed_fee`, the min-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction actually emitted. Alternatively, expose a variant that takes the fully formed `Vec<TxOut>` so the fee input can never diverge from the signed transaction.

### Proof of Concept
```rust
// Conceptual: SignableTransaction::new with data produces a tx whose
// real vsize exceeds the vbytes used to compute needed_fee.
let data = vec![0u8; 80];
let stx = SignableTransaction::new(
    vec![input],                       // ReceivedOutput
    &[(payment_script, payment_amt)],
    Some(change_script),
    Some(data),                        // OP_RETURN output added to tx
    fee_per_vbyte,
).unwrap();

// needed_fee was computed over a transaction WITHOUT the OP_RETURN output:
//   actual_vsize(tx) = vbytes_used + ~90..113
//   realized_rate    = needed_fee / actual_vsize < fee_per_vbyte
// If needed_fee ≈ (DEFAULT_MIN_RELAY_TX_FEE * vbytes)/1000,
// the real fee rate is below the relay minimum and the tx won't propagate.
```
Concrete evidence in the code: the OP_RETURN output is pushed at `send.rs` L194–202, while `calculate_weight_vbytes(tx_ins.len(), payments, None)` at L204 only receives `payments` — the mismatch — and `needed_fee` at L206 and the `MAX_STANDARD_TX_WEIGHT` check at L241 inherit the understated size.
