### Title
Out-of-bounds map indexing in PedPoP blame evaluation panics on attacker-chosen participant indexes - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to CVE-2018-19839 (an out-of-bounds read reachable via crafted input, yielding denial of service), `Decryption::decrypt_with_proof` and `BlameMachine::blame_internal` index `HashMap`s with `Participant` values supplied by the caller of `blame()` without checking membership. A blame accusation naming a `sender` or `recipient` index outside the registered set (any non-zero `u16` not in `1 ..= n`) causes an unconditional panic (`HashMap` index operator), crashing the node that evaluates the blame proof.

### Finding Description
`AdditionalBlameMachine::new` registers encryption keys only for participants `1 ..= n` (`crypto/dkg/pedpop/src/lib.rs`, lines 656-660) and stores commitments under the same keys. Later, `blame()` accepts arbitrary `sender`/`recipient` `Participant` values and calls `blame_internal` (`crypto/dkg/pedpop/src/lib.rs`, lines 575-609), which calls `Decryption::decrypt_with_proof`. Inside `decrypt_with_proof`, the expression `self.enc_keys[&decryptor]` (`crypto/dkg/pedpop/src/encryption.rs`, line 388) panics when `decryptor` was never registered. If the accusation instead uses a valid `recipient` but a `sender` not in `self.commitments`, `self.commitments[&sender]` in `blame_internal` (`crypto/dkg/pedpop/src/lib.rs`, line 599) panics the same way.

Neither `BlameMachine::blame` nor `AdditionalBlameMachine::blame` validates that `sender`/`recipient` are within `1 ..= n`; `Participant::new` accepts any non-zero `u16`, so out-of-range indexes are well-formed inputs. In Serai's deployment, blame accusations are relayed to other parties (and evaluated by `AdditionalBlameMachine`, explicitly designed "regardless of if the caller was a member in the DKG protocol"), so the evaluating node processes attacker-influenced `sender`/`recipient` values directly.

### Impact Explanation
Any party able to submit a blame accusation (a DKG participant, or anyone able to invoke the blame-evaluation path with a crafted accusation) can crash the evaluating node by naming a participant index not present in the registered maps. This is an availability loss comparable in class and severity to the heap over-read DoS in the referenced CVE: a small crafted input triggers an out-of-bounds access. In Rust the access becomes a panic rather than a silent over-read, but the effect — denial of service of the process handling untrusted protocol messages — is the same, and it aborts the DKG/blame adjudication mid-protocol.

### Likelihood Explanation
Triggering requires only choosing a `Participant` index `> n` (or a participant whose commitments were rejected) in a blame accusation — trivially craftable. The precondition is that the node runs the blame path, which only occurs when a fault was alleged during a DKG; an attacker who participates in or disrupts a DKG can arrange this. No secret or privileged position is needed.

### Recommendation
Replace map indexing with fallible lookups and return a defined result for out-of-set parties. Specifically, in `crypto/dkg/pedpop/src/encryption.rs` change `self.enc_keys[&decryptor]` to `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?` (or a dedicated `UnknownParticipant` error), and in `crypto/dkg/pedpop/src/lib.rs` `blame_internal` check `self.commitments.get(&sender)` before use, treating an unregistered `sender`/`recipient` as the accuser's fault or a defined error rather than panicking.

### Proof of Concept
```rust
// crypto/dkg/pedpop context, after a DKG round-1 where only parties 1..=n registered.
// Build an AdditionalBlameMachine for n=2:
let mut msgs = HashMap::new();
msgs.insert(Participant::new(1).unwrap(), commitments_msg_1);
msgs.insert(Participant::new(2).unwrap(), commitments_msg_2);
let machine = AdditionalBlameMachine::<Ed25519>::new(context, 2, msgs).unwrap();

// Crafted accusation: recipient 5 was never a participant.
// decrypt_with_proof evaluates self.enc_keys[&Participant(5)] -> HashMap index panic.
machine.blame(
  Participant::new(1).unwrap(),          // sender
  Participant::new(5).unwrap(),          // recipient: out of set, non-zero so valid Participant
  any_encrypted_message,                 // EncryptedMessage<C, SecretShare<C::F>>
  Some(any_encryption_key_proof),        // proof must be Some to reach the enc_keys index
);
// Result: thread panic at crypto/dkg/pedpop/src/encryption.rs:388 -> node crash (DoS).
```

Note: I verified the panic sites directly at `crypto/dkg/pedpop/src/encryption.rs:388` and `crypto/dkg/pedpop/src/lib.rs:599`, and confirmed `AdditionalBlameMachine::new` only registers keys for `1 ..= n` (`crypto/dkg/pedpop/src/lib.rs:656-660`). I did not trace the exact coordinator/processor call graph feeding attacker-controlled `sender`/`recipient` into `blame()` beyond `processor/src/key_gen.rs`'s share-fault reporting; if blame evaluation is only ever invoked on locally-known in-set participants, the reachability is reduced, but the library API itself permits the panic on untrusted input.
