## Finding: Native ETH swap-refund dust becomes permanently stuck in `EvmHost` with no recovery path

### Title
Uniswap V2 native-ETH swap refunds accumulate as unrecoverable dust in `EvmHost` - (File: `evm/src/core/EvmHost.sol`)

### Summary
The external report's core invariant is: *a contract that legitimately holds ETH for cross-chain fee payment has no admin/owner method to recover ETH once it becomes stranded.* The closest locally-provable analog is `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()`, which all accept `msg.value` and route it through `IUniswapV2Router02.swapETHForExactTokens` to buy an exact amount of `feeToken()`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`swapETHForExactTokens` on Uniswap V2's router computes the exact ETH input needed for the requested output (`post.fee` / `get.fee` / `amount`) and refunds any leftover `msg.value` back to the address that called the router — i.e., `EvmHost` itself, since `EvmHost` is the direct caller of the router, not the original end user. Any user who supplies `msg.value` greater than the ETH cost of the requested fee (common due to price movement between quote and execution, or simple overestimation/rounding by frontends and SDKs) has that dust permanently deposited into `EvmHost`'s own balance rather than refunded to the caller.

Unlike the `BandwidthManager`/`BandwidthPallet` pattern, which explicitly supports `dispatch_withdraw` with `token == address(0)` for native ETH recovery, `EvmHost`'s governance-facing recovery path (`IHostManager`) is keyed to `feeToken()` — an ERC20 — for revenue withdrawal, not native ETH: [4](#0-3) 

The relayer pallet's cross-chain withdrawal path likewise sends `params.fee_token` (the ERC20 fee token), not a generic/native-capable token field: [5](#0-4) 

No `withdraw`/`sweep`/`recoverETH` function was found in `EvmHost.sol` for the admin, host manager, or any privileged role to move stray native ETH out of the contract.

### Impact Explanation
Every dispatch/fundRequest call that overpays `msg.value` versus the actual Uniswap-quoted cost leaves the surplus permanently locked in `EvmHost`. Over the life of a chain deployment this is a continuous drip of unrecoverable ETH — a direct, protocol-wide loss-of-funds condition matching the bounty's "loss of funds" impact category, since neither the depositor nor governance can ever retrieve it.

### Likelihood Explanation
This requires no malicious actor, relayer, or compromised key — it is triggered by completely ordinary usage (any `msg.value` above the router's computed input amount, which is routine given slippage/estimation in frontends/SDKs) via the fully public `dispatch()` and `fundRequest()` entrypoints. It is high likelihood and will recur on every EVM deployment of the host that accepts native-token payment.

### Recommendation
Add an admin-gated (or `IHostManager`-gated) `sweepNativeToken(address beneficiary, uint256 amount)` function to `EvmHost`, mirroring the `token == address(0)` handling already implemented in `BandwidthManager`'s `Withdrawal` action, so that native ETH — including router refund dust — can be recovered by governance the same way stale `feeToken` balances already are.

### Proof of Concept
1. Attacker/user calls `EvmHost.dispatch(DispatchPost)` supplying `msg.value` intentionally higher than the ETH required to buy `post.fee` units of `feeToken` (e.g., 2x the quoted amount, easily done since there is no upper-bound check on `msg.value`).
2. `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` executes; the router refunds the unused ETH to `address(this)` (`EvmHost`), not to the caller. [1](#0-0) 
3. Repeat across many dispatches/fundRequest calls (self-inflicted or simply organic overpayment across the user base); `EvmHost`'s native balance grows.
4. Confirm no function in `EvmHost.sol` or the `IHostManager` withdrawal interface accepts `token == address(0)` / native ETH for recovery — only `feeToken` (ERC20) balances are governed by `IHostManager.withdrawFunds`-style calls, unlike the explicit `address(0)` handling implemented for `BandwidthManager`. [6](#0-5) 

**Note on completeness**: I was not able to fully read `HostManager.sol`'s complete withdrawal function signature within the available search budget (only its `receive()` declaration count was confirmed) to conclusively rule out a hidden native-ETH sweep path there; if `HostManager` does expose such a path it would materially weaken this finding, and a full read of `evm/src/core/HostManager.sol` is recommended to close that gap.
