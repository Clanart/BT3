### Title
Inverted blame arguments cause the honest accuser to be slashed when reporting an invalid DKG share - (File: processor/src/key_gen.rs)

### Summary
The PedPoP blame-verification path in the processor calls `AdditionalBlameMachine::blame`/`BlameMachine::blame` with `(accuser, accused)`, but `blame`'s contract is `(sender, recipient)` — i.e., the accused sender first, the accusing recipient second. As a result, every blame adjudication mis-attributes fault: the reporting (honest) participant is blamed while the faulty sender escapes.

### Finding Description
`BlameMachine::blame` / `AdditionalBlameMachine::blame` are documented and implemented as `blame(sender, recipient, msg, proof)` where `sender` is the accused party whose `EncryptedMessage`'s proof-of-possession is bound to `sender` via `pop_challenge`'s `"sender"` transcript field, and `recipient`/`decryptor` is the accuser whose registered encryption key the `EncryptionKeyProof` DLEq is checked against (`self.enc_keys[&decryptor]`). The pedpop tests confirm this convention: `test_blame` calls `machine.blame(ONE, TWO, msg)` for a message from `ONE` to `TWO`, expecting the sender `ONE` blamed.

In `processor/src/key_gen.rs`, the `CoordinatorMessage::VerifyBlame` handler instead calls:

```rust
.blame(accuser, accused, substrate_share, substrate_blame)  // lines ~549, ~556
```

with `accuser` mapped to `sender` and `accused` mapped to `recipient`. Concretely, in `decrypt_with_proof`:

- `pop_challenge(context, msg.pop.R, msg.key, from = accuser, ...)` is verified, but the message's PoP was generated by the actual sender (`accused`), so the Schnorr PoP verification fails → `DecryptionError::InvalidSignature` → `blame_internal` returns `sender` = `accuser`.
- Even if the PoP check were reached, the DLEq is checked against `self.enc_keys[&accused]` (the sender's enc key) instead of the accuser's, so a valid `EncryptionKeyProof` would fail with `InvalidProof` → returns `recipient` = `accused` — but that arm is unreachable because PoP verification fails first.

Then `processor/src/key_gen.rs` lines ~558–563: since `substrate_blame`/`network_blame` return `accuser` (≠ `accused`), the handler emits `ProcessorMessage::Blame { participant: accuser }`.

This mirrors the advisory's bug class: an authorization/attribution check that silently operates on the wrong identity (guest `user_id: nil` matching others' rows), so an unprivileged party can act on / harm another participant's standing.

### Impact Explanation
When any participant receives an invalid encrypted share and emits `ProcessorMessage::InvalidShare` (a normal, reachable event — `handle_machine` produces it from `PedPoPError::InvalidShare`), the resulting `VerifyBlame` adjudication deterministically blames the *accuser*. An honest validator who correctly reports a malicious peer's bad share is fatally slashed, and the malicious sender goes unpunished. This inverts the entire accountability property the PedPoP blame system exists to provide, and lets an attacker slash honest validators by simply sending them malformed shares.

### Likelihood Explanation
Triggering requires only a participant sending a corrupted `EncryptedMessage` share (fully within the threat model — blame exists precisely for this) to any honest peer during `CoordinatorMessage::Shares` handling. The victim's normal fault-reporting path then causes their own slashing. No cryptographic break, collusion, or privileged position is needed.

### Recommendation
Swap the arguments in both `AdditionalBlameMachine::blame` calls in the `VerifyBlame` handler to `.blame(accused, accuser, share, blame)`, matching the `blame(sender, recipient, msg, proof)` contract, and add a regression test asserting the accused (not the accuser) is blamed for an invalid share.

### Proof of Concept
1. During DKG, malicious participant `M` sends participant `H` a validly-PoP'd but invalid share (e.g., `invalidate_msg` as in `invalid_ecdh_blame`).
2. `H`'s `calculate_share` returns `InvalidShare { participant: M, blame: Some(proof) }`; `H` reports `InvalidShare`, coordinator issues `VerifyBlame { accuser: H, accused: M, share, blame }`.
3. Each processor calls `AdditionalBlameMachine::blame(H, M, msg, proof)`. `decrypt_with_proof(from=H, decryptor=M, ...)` verifies `msg.pop` against `pop_challenge(..., sender = H, ...)` while the PoP was created by `M` → `InvalidSignature` → returns `H`.
4. Processor emits `Blame { participant: accuser = H }`; `H` is slashed, `M` is exonerated.

Uncertainty note: whether `ProcessorMessage::Blame` maps to a fatal slash is determined downstream (coordinator/substrate), which is outside the in-scope crates; however the processor-level mis-attribution itself is fully verified above.
