## Analog Assessment

The Fusion Swap bug reduces to one invariant break: **an identifier that should be permanently retired after "close" can be silently rebound to new, attacker-controlled data, and code that only checks the identifier (not the underlying identity) will act on the wrong data.** In Solana the identifier is the `(maker, order_id)` PDA; in Desktop the closest analog is the **on-disk repository `path`**, which `RepositoriesStore` uses as the primary lookup key for a tracked repository's persisted identity — including which `gitHubRepositoryID` (account/API/permission context) it is bound to.

### Title
Repository identity keyed by filesystem path allows silent rebinding of a tracked GitHub repository's account/API context to a different repository - (File: app/src/lib/stores/repositories-store.ts)

### Summary
`RepositoriesStore.addRepository()` and `RepositoriesStore.switchWorktree()` resolve a tracked repository's persisted record purely by `path` on disk, and if a row already exists at that path they return/reuse it as-is — including its stored `gitHubRepositoryID` link, `workflowPreferences`, and tutorial/worktree flags — without re-validating that the repository currently on disk at that path is still the same repository (e.g., by comparing remote URL or the linked GitHub repo identity).

### Finding Description
`addRepository` looks up an existing DB row solely by `path`: [1](#0-0) 
If found, it returns that pre-existing row (with its old `gitHubRepositoryID` association) instead of creating a fresh, unlinked record for whatever git repository actually lives at that path now.

Likewise, `switchWorktree` reuses whatever repository row is already registered at the target path instead of updating/validating identity: [2](#0-1) 

`removeRepository` does delete the DB row for a repository (the equivalent of `close_escrow` freeing the PDA): [3](#0-2) 
but nothing prevents the *path* from later being reused by a completely different repository (attacker-supplied clone, folder deleted and replaced, symlink swap, or moved directory) before Desktop is told to forget it, or in any race between disk state changing and Desktop's tracking being updated. When that happens, `addRepository`/`switchWorktree` re-attach the old `gitHubRepositoryID` (and thus the previously associated GitHub account/API endpoint, workflow preferences, and any downstream logic keyed off `Repository.gitHubRepository`) to the new, attacker-controlled content — exactly mirroring how the Solana program let a cancelled order's PDA be silently reinitialized with new data while the taker's transaction still treated it as the original order.

### Impact Explanation
Any feature that trusts `Repository.gitHubRepository` to represent "the same logical GitHub repo the user originally added" is now operating on a confused identity: PR/issue association, workflow preferences (e.g. auto-behaviors tied to that repo), Copilot/account-scoped settings surfaced via the linked repository, and commit-URL/API calls built from the stale `gitHubRepository` (endpoint/owner/name) will be evaluated against or sent to the wrong logical repository. This is a data-integrity/confused-deputy issue rather than direct code execution, but it is a genuine "identifier reuse without re-validating identity" defect of the same class as the reported bug.

### Likelihood Explanation
Requires a path-reuse scenario a user could plausibly hit unassisted (deleting a tracked repo's folder and cloning/adding a different repository — including one the user was steered to via a README/link — into the identical path) without any local/physical access, admin rights, or pre-existing malware. Compared to the original critical fund-theft bug this is much lower severity/likelihood because no direct token/asset theft is enabled, and I could not fully trace which downstream consumers of `gitHubRepositoryID` produce a security-relevant effect (only partial exploration of `pull-request-store.ts` / `issues-store.ts` consumers was possible within available searches).

### Recommendation
Do not treat filesystem `path` alone as a stable repository identity for reusing a persisted `gitHubRepositoryID`/settings record. On `addRepository`/`switchWorktree`, when a row already exists at the target path, verify the on-disk repository's remote/origin (or `.git` identity) still matches what was previously recorded before reusing the stored GitHub linkage; otherwise create a fresh unlinked record, mirroring the fix pattern used in the reported issue (retire the identifier permanently rather than allowing silent reinitialization).

### Proof of Concept
1. User adds/clones `github.com/victim-org/private-repo` to `~/Projects/app`; Desktop stores a DB row `{path: ~/Projects/app, gitHubRepositoryID: X}` [4](#0-3) .
2. User deletes the `~/Projects/app` folder from disk directly (outside Desktop), leaving the DB row (or the removal from Desktop's list races/fails before disk state changes).
3. User is directed (e.g., via a link or instructions on an attacker's page) to clone `github.com/attacker/evil-repo` into the same path `~/Projects/app`.
4. Desktop's `addRepository(path)` finds the existing row for that path and returns it unchanged [5](#0-4) , so the attacker's repository is now silently presented under `victim-org/private-repo`'s GitHub identity/settings.

  public async addRepository(
    path: string,
    gitDir: string | undefined,
    opts?: AddRepositoryOptions
  ): Promise<Repository> {
    const repository = await this.db.transaction(
      'rw',
      this.db.repositories,
      this.db.gitHubRepositories,
      this.db.owners,
      async () => {
        const existing = await this.db.repositories.get({ path })

        if (existing !== undefined) {
          return await this.toRepository(existing)
        }

        const dbRepo: IDatabaseRepository = {
          path,
          gitHubRepositoryID: null,
          missing: opts?.missing ?? false,
          lastStashCheckDate: null,
          alias: null,
          gitDir,
        }
        const id = await this.db.repositories.add(dbRepo)
        return this.toRepository({ id, ...dbRepo })
      }
