### Title
`open-external` IPC handler checks URL protocol only for logging, never enforces it — attacker-controlled CI/API URLs reach `shell.openExternal` unrestricted - ([File: app/src/main-process/main.ts])

### Summary
The bug class in the C4 report is a validation/enforcement mismatch: one layer computes a check against a threshold, but a different, more permissive path is actually used to execute the operation, so the intended guard never fires. The same pattern exists in GitHub Desktop's external-link opening pipeline. The renderer enforces a strict `https?:` protocol allow-list in exactly one place — the sandboxed markdown click interceptor — but many other producers of URLs (including URLs sourced from the GitHub API, i.e. attacker-influenced when the API object comes from a repo/PR/CI the user doesn't control) call `dispatcher.openInBrowser()` → `_openInBrowser()` → `shell.openExternal()` directly, and the main-process IPC handler that ultimately performs the action does not enforce any protocol restriction at all.

### Finding Description
`app/src/ui/lib/sandboxed-markdown.tsx` restricts markdown-rendered links before invoking the `onMarkdownLinkClicked` callback: [1](#0-0) 

This is the only enforcement point that actually rejects non-`http(s)` protocols. But the value it protects (`shell.openExternal`) is also reachable from many other code paths that skip this check entirely:

- `AppStore._openInBrowser` passes the URL straight through with zero validation: [2](#0-1) 

- The main-process IPC handler `open-external`, which is the actual sink invoked by the renderer via preload/dispatcher, computes a protocol check but only uses it to decide whether to log — it calls `shell.openExternal(path)` unconditionally regardless of the result: [3](#0-2) 

That `if (pathLowerCase.startsWith('http://') || pathLowerCase.startsWith('https://'))` block is dead validation — exactly the same shape as `CLFactory.getSwapFee`'s check that is computed but whose result is discarded, letting an out-of-range value flow to an unguarded default/path. Here, any string handed to `open-external` — `file://`, `javascript:` (blocked by Electron in some cases but not universally validated here), custom protocol handlers, or platform-specific URI schemes — is passed to `shell.openExternal` without a Desktop-side allow-list.

Several UI surfaces feed API-derived, effectively repository/PR/CI-controlled strings into this exact call chain, e.g. `dispatcher.openInBrowser` invocations for check-run/CI details (`app/src/ui/check-runs/ci-check-run-popover.tsx`, `ci-check-run-list-item.tsx`) which use `htmlUrl`/`html_url` fields sourced from the GitHub Checks API — a value that, for pull requests from forks, can be populated by a third-party CI app/workflow the PR author (attacker) controls, not by GitHub itself. [4](#0-3) 

### Impact Explanation
If any of these htmlUrl-bearing API objects (check run URLs, PR/comment metadata, etc.) can carry a non-`https` value — e.g. a `file://` URI pointing at a local path, or a Windows/macOS-registered custom URI scheme — clicking "View on GitHub"/"Open in browser" style actions for that item calls `shell.openExternal()` with that value. On Windows in particular, `shell.openExternal` on unusual schemes has historically enabled command execution via registered protocol handlers; at minimum it enables local file access/exfiltration primitives disclosed to a page/handler outside the user's expectation. Because the enforcement exists only in the markdown-click path, this is a silent corruption of the security invariant "Desktop only auto-opens http(s) links" — the invariant looks enforced when reading `sandboxed-markdown.tsx`, but is not actually enforced at the real sink.

### Likelihood Explanation
Likelihood depends on whether any upstream GitHub API response field consumed by these `openInBrowser` call sites can, in practice, contain a non-`https` URL (e.g., a malicious/misconfigured third-party CI app's `details_url`/`html_url` on check runs for a forked PR). This is plausible because GitHub's Checks API `details_url` is an arbitrary string supplied by the check-run creator (a GitHub App), and Desktop performs no scheme validation before it reaches `shell.openExternal`. I could not fully confirm within the indexed code whether every `htmlUrl` field is pre-validated elsewhere (e.g., at API deserialization) before reaching the UI, so likelihood is moderate rather than confirmed to be directly reachable end-to-end; this warrants live verification of `app/src/lib/api.ts` deserialization for check-run `details_url`.

### Recommendation
- Move protocol enforcement to the actual sink: validate the scheme (`http:`/`https:` only, or an explicit allow-list) inside the `open-external` IPC handler in `app/src/main-process/main.ts` before calling `shell.openExternal`, and reject/log-and-drop otherwise — mirroring the report's "revert instead of silently falling back" mitigation.
- Apply the same validation inside `AppStore._openInBrowser` so all dispatcher-level callers are covered independent of the IPC boundary.
- Audit all `htmlUrl`/`html_url`/`details_url` fields sourced from the GitHub API (check runs, PR comments, etc.) and validate their scheme at deserialization time in `app/src/lib/api.ts`, not just at the markdown-render boundary.

### Proof of Concept
Not independently executed (ask-only mode / index-only access); reasoning is based on static code paths:
1. A forked-repo PR triggers a third-party CI app to report a check run whose `details_url` is `file:///Users/<victim>/Library/...` or a registered custom scheme URI.
2. User opens the PR's checks in Desktop and clicks "View on GitHub" / check details in `ci-check-run-popover.tsx`.
3. This calls `dispatcher.openInBrowser(url)` → `AppStore._openInBrowser(url)` → renderer IPC → main process `open-external` handler.
4. `main.ts`'s `open-external` handler computes `pathLowerCase.startsWith('http://')`/`'https://'` only for a log line, then calls `shell.openExternal(path)` unconditionally — the non-`https` URL is opened without the protection that exists in `sandboxed-markdown.tsx`'s link interceptor.

    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
