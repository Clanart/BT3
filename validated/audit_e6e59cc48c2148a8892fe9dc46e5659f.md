### Title
Unbounded initial deposit lets a `grantProposalAuthorization` delegate drain the granter's balance via `MsgSubmitProposal` — analogous to the `swap_margin()` unlimited-slippage drain (File: `precompiles/gov/gov.go`)

### Summary
The `MarginDex.swap_margin()` bug lets a trusted delegate move a victim's funds using an attacker-controlled, unbounded parameter (`_min_amount_out=0`) that the authorization check never validates. The Sei gov precompile's proposal-authorization flow has the same structural weakness: a `grantProposalAuthorization` grant lets a grantee submit `MsgSubmitProposal` on the granter's behalf, and the `InitialDeposit` amount is a completely attacker-controlled, unbounded parameter that `GenericAuthorization` never limits (unlike `StakeAuthorization.MaxTokens` or `SendAuthorization.SpendLimit`, which do bound the authorized amount).

### Finding Description
`grantProposalAuthorization` in `precompiles/gov/gov.go` creates a `GenericAuthorization` for `MsgSubmitProposal`: [1](#0-0) 

`submitProposalWithAuthorization` builds the `MsgSubmitProposal` via `prepareSubmitProposal` (with the granter as `proposer`) and dispatches it through `pcommon.ExecuteAuthorization`: [2](#0-1) 

`prepareSubmitProposal` sets `InitialDeposit` from `HandlePaymentUsei`, and constructs `MsgSubmitProposal{Proposer: proposer, InitialDeposit: initialDeposit, ...}`: [3](#0-2) 

Critically, the native (non-EVM) `MsgExec` path for this same grant type debits the deposit from the granter's own liquid balance with **no cap**, which the code's own doc comment explicitly warns about: [1](#0-0) 

Unlike `StakeAuthorization` (bounded by `MaxTokens`, enforced in `Accept`) or `SendAuthorization` (bounded by `SpendLimit`): [4](#0-3) 

`GenericAuthorization` performs no amount check at all — it simply authorizes the message type. This means a grantee holding a proposal-submission grant can construct a native `MsgExec` (or, for a compromised/malicious delegate flow, coordinate the same effect) specifying an arbitrarily large `InitialDeposit`, taken entirely from the granter's spendable balance, with no `_min_amount_out`-style bound the way `SendAuthorization`/`StakeAuthorization` provide.

### Impact Explanation
Governance deposits in the Cosmos SDK are locked for the deposit/voting period and can be **burned** if the proposal is rejected with sufficient `NoWithVeto` votes (per the module's `BurnVoteVeto`/veto-threshold parameter), or otherwise remain locked for the full voting period. A malicious or compromised grantee holding only a `grantProposalAuthorization` grant (which a user might issue for a narrow, seemingly low-risk purpose — just "submit proposals for me") can submit a proposal with an initial deposit equal to the granter's entire liquid `usei` balance, then ensure (via collusion, whale voting power, or waiting for organic veto) that the proposal is vetoed, permanently burning the granter's funds. This is a direct parallel to the `swap_margin()` finding: a narrowly-scoped delegation is exploited via an unbounded, attacker-supplied amount parameter to cause fund loss to the victim who granted trust for something else.

### Likelihood Explanation
Exploitation requires only that a user has granted `grantProposalAuthorization` (or the message-authorization equivalent) to some other account/contract — a normal, expected workflow (e.g., DAOs delegating proposal-submission rights). No node, validator, or governance majority collusion is required to inflict loss; even without achieving veto-burn, the attacker can lock up 100% of the granter's spendable balance for the entire voting period, which is itself an availability/fund-freezing impact. The precompile authors were aware of this risk (see the explicit doc-comment warning), indicating the unbounded-amount design is real and current in the codebase, not hypothetical.

### Recommendation
Add an amount-bounding authorization type for `MsgSubmitProposal` deposits (analogous to `SendAuthorization.SpendLimit` / `StakeAuthorization.MaxTokens`), or require the grantor to specify a maximum deposit at grant time, and enforce it in `submitProposalWithAuthorization` / the corresponding native `Accept` logic before dispatching the message. Alternatively, restrict `submitProposalWithAuthorization` to caller-funded deposits only (as already documented as the safer EVM behavior) and disable/restrict the analogous unbounded-deposit path for native `MsgExec` grants of this authorization type.

### Proof of Concept
1. Victim `V` runs `GOV_CONTRACT.grantProposalAuthorization(delegateAddr, expiration)`, granting `delegate` a `GenericAuthorization` for `MsgSubmitProposal` scoped to `V`'s account (see grant creation at [1](#0-0) ).
2. `delegate` (as grantee) submits a native `authz.MsgExec` wrapping `MsgSubmitProposal{Proposer: V, InitialDeposit: <V's entire usei balance>}`.
3. Because `GenericAuthorization` has no spend-limit check (contrast with `StakeAuthorization.Accept`'s `MaxTokens` enforcement, [4](#0-3) ), the message is dispatched and the deposit is debited from `V`'s account without limit.
4. `delegate`/colluding voters cast `NoWithVeto` to trigger deposit burn under the gov module's veto-threshold rules, permanently destroying `V`'s funds — mirroring the `swap_margin()` scenario where an unchecked, delegate-controlled amount parameter drains the victim.

**Note:** I was unable to fully trace the exact deposit-burn code path (`x/gov/keeper/tally.go` / `deposit.go`) within the available search budget to confirm the precise burn conditions and percentage in this fork's gov module parameters; a Devin session with full repository access would be needed to verify the exact veto/burn mechanics and confirm whether burn-on-veto is enabled by default in this chain's genesis parameters.

func (p PrecompileExecutor) submitProposalWithAuthorization(ctx sdk.Context, method *abi.Method, caller common.Address, args []interface{}, value *big.Int, hooks *tracing.Hooks, evm *vm.EVM) ([]byte, uint64, error) {
	if err := pcommon.ValidateArgsLength(args, 2); err != nil {
		return nil, 0, err
	}

	grantee, err := pcommon.GetSeiAddressByEvmAddress(ctx, caller, p.evmKeeper)
	if err != nil {
		return nil, 0, err
	}
	proposer, err := pcommon.GetSeiAddressFromArg(ctx, args[0], p.evmKeeper)
	if err != nil {
		return nil, 0, err
	}
	msg, err := p.prepareSubmitProposal(ctx, proposer, args[1].(string), value, hooks, evm)
	if err != nil {
		return nil, 0, err
	}

	execRes, err := pcommon.ExecuteAuthorization(ctx, p.authzMsgServer, grantee, msg)
	if err != nil {
		return nil, 0, err
	}
	if len(execRes.Results) != 1 {
		return nil, 0, fmt.Errorf("expected one submit proposal authorization result, got %d", len(execRes.Results))
	}
	var submitRes govtypes.MsgSubmitProposalResponse
	if err := submitRes.Unmarshal(execRes.Results[0]); err != nil {
		return nil, 0, err
	}

	bz, err := method.Outputs.Pack(submitRes.ProposalId)
	if err != nil {
		return nil, 0, err
	}
	return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), nil
}

// prepareSubmitProposal builds the exact Cosmos message used by both direct
// and authorized submission, so the two entry points cannot drift in parsing,
// payment, or proposal-content behavior.
func (p PrecompileExecutor) prepareSubmitProposal(ctx sdk.Context, proposer sdk.AccAddress, proposalJSON string, value *big.Int, hooks *tracing.Hooks, evm *vm.EVM) (*govtypes.MsgSubmitProposal, error) {
	var proposal Proposal
	if err := json.Unmarshal([]byte(proposalJSON), &proposal); err != nil {
		return nil, fmt.Errorf("failed to parse proposal JSON: %w", err)
	}

	initialDeposit, err := pcommon.HandlePaymentUsei(
		ctx,
		p.evmKeeper.GetSeiAddressOrDefault(ctx, p.address),
		proposer,
		value,
		p.bankKeeper,
		p.evmKeeper,
		hooks,
		evm.GetDepth(),
	)
	if err != nil {
		return nil, err
	}

	content, err := p.createProposalContent(ctx, proposal)
	if err != nil {
		return nil, err
	}
	msg, err := govtypes.NewMsgSubmitProposalWithExpedite(content, sdk.NewCoins(initialDeposit), proposer, proposal.IsExpedited)
	if err != nil {
		return nil, err
	}
	if err := msg.ValidateBasic(); err != nil {
		return nil, err
	}
	return msg, nil
}
