### Title
DID recovery/backup list persists across ownership transfer, allowing a seller to retain a covert recovery path back to a "sold" DID (and its associated NFTs) - (File: chia/wallet/did_wallet/did_wallet.py)

### Summary
This is a strong analog of the reported bug class: an owner leaves a self-controlled "backdoor" credential active on an asset before transferring it, letting them reclaim control after the sale. In Footium, the club owner leaves `setApprovalForAll` active on the escrow before selling the club. In chia-blockchain, the DID wallet's `backup_ids` (recovery list) is explicitly **not cleared** by default when transferring inner-puzzle ownership, and the code comments acknowledge this is a seller-driven exploit vector.

### Finding Description
When a DID's inner puzzle is regenerated for a new owner via `get_innerpuz_for_new_innerhash`, the code explicitly keeps the existing `backup_ids` (recovery list) intact: [1](#0-0) 

The docstring/comment states: *"Note: the recovery list will be kept. In a selling case, the seller should clean the recovery list then transfer to the new owner."* This means the security-relevant decision to strip old recovery authorities is left entirely to the seller's discretion/front-end behavior rather than being enforced by the protocol or wallet code. If a malicious seller sets themselves (or a colluding address) as a `backup_id` with `num_of_backup_ids_needed` satisfied before transferring the DID's p2 puzzle to a buyer, the DID inner puzzle (`DID_INNERPUZ_MOD`, curried with `recovery_list_hash` / `num_of_backup_ids_needed`) still recognizes that backup identity as authorized to perform a recovery spend after the sale completes. [2](#0-1) 

The DID's ownership determines which `NFTWallet` (and thus NFTs) are associated with it — NFTs minted "provenant" to a DID are tracked and re-associated purely based on `owner_did`/`did_id`, matching Footium's "club owner has admin control that outlives club ownership → drains club's players" pattern: [3](#0-2) 

Because the recovery list and verification threshold are curried directly into the on-chain puzzle and are not reset automatically on ownership transfer, a buyer of a DID (and any NFTs later assigned/associated to that DID) has no on-chain guarantee that the previous owner cannot still exercise a `backup_ids`-based recovery to seize control of the DID's current inner puzzle (and thereby redirect any coins/NFTs controlled through that DID).

### Impact Explanation
If exploited, a seller retains the ability to execute a DID-recovery spend after "selling" the DID, potentially reclaiming control of the DID coin and any associated provenant NFTs or funds sent to it, without the buyer's consent — analogous to unauthorized asset seizure/theft in the original report. This is a Medium/High-severity trust-model gap: the victim (buyer) has paid for an asset that appears fully transferred (new p2 puzzle/pubkey), but the seller can retain latent authority via a curried recovery list they controlled prior to sale.

### Likelihood Explanation
The likelihood depends entirely on the buyer/front-end never inspecting the curried `recovery_list_hash` / `num_of_backup_ids_needed` on the DID's current inner puzzle before accepting a transfer — exactly the same failure mode called out in the original report ("normally a user does not check if any approvals... are set"). Since the wallet code itself documents this as a known caveat rather than enforcing recovery-list clearing, a malicious/careless seller can trivially leave a viable self-recovery path, and typical wallet UIs are unlikely to warn buyers about a non-empty recovery configuration on a DID they're acquiring.

### Recommendation
- When transferring DID ownership (`transfer_did` / `get_innerpuz_for_new_innerhash`), default to clearing `backup_ids` and resetting `num_of_backup_ids_needed` unless the new owner explicitly opts to keep an existing recovery configuration.
- Surface the current `recovery_list_hash` / `num_of_backup_ids_needed` prominently in wallet RPC/CLI output when inspecting or accepting a DID transfer or an offer involving a DID, so buyers can verify no stale recovery authority remains.
- Consider adding a wallet-level check that refuses to treat a DID transfer as "safe" unless the recovery list has been reset to empty (or to buyer-specified values) as part of the same spend that changes the p2 puzzle.

### Proof of Concept
1. Owner A creates a DID with `backup_ids = [A_control_id]`, `num_of_backup_ids_needed = 1` (or leaves a pre-existing recovery list from creation, per `did_wallet.py` `create_new_did_wallet`).
2. Owner A transfers the DID to buyer B using `transfer_did`, which calls `get_innerpuz_for_new_innerhash` — this keeps `self.did_info.backup_ids` unchanged as documented at [4](#0-3) , producing a new inner puzzle still curried with A's recovery list via `did_wallet_puzzles.create_innerpuz`.
3. Buyer B receives the DID and, believing they solely control it, assigns NFTs to it via `set_nft_did` (provenant NFTs tied to `did_id`), as seen in [5](#0-4) .
4. Owner A, still present in the curried `backup_ids`, initiates a DID recovery spend (per `create_recovery_message_puzzle`/attestment flow in `did_wallet_puzzles.py`) to redirect the DID's current inner puzzle to a p2 puzzle A controls, regaining control of the DID coin and its associated NFT wallet identity — without B's cooperation.

Note: I was unable to fully trace the exact end-to-end recovery-spend transaction-building function name (the DID recovery/attestment consumption logic, likely `recovery_spend`-style code) within the available index due to file-size/indexing limits, so the last step of the PoC (the precise call sequence that finalizes an on-chain recovery spend) could not be independently confirmed by reading the full spend-construction code. def create_innerpuz(
```python
    p2_puzzle_or_hash: Program | bytes32,
    recovery_list: list[bytes32],
    num_of_backup_ids_needed: uint64,
    launcher_id: bytes32,
    metadata: Program = Program.to([]),
    recovery_list_hash: Program | None = None,
) -> Program:
    """
    Create DID inner puzzle
    :param p2_puzzle_or_hash: Standard P2 puzzle or hash
    :param recovery_list: A list of DIDs used for the recovery
    :param num_of_backup_ids_needed: Need how many DIDs for the recovery
    :param launcher_id: ID of the launch coin
    :param metadata: DID customized metadata
    :param recovery_list_hash: Recovery list hash
    :return: DID inner puzzle
    Note: Receiving a standard P2 puzzle hash wouldn't calculate a valid puzzle, but
    that can be useful if calling `.get_tree_hash_precalc()` on it.
    """
    backup_ids_hash: Program | bytes32 = Program.to(recovery_list).get_tree_hash()
    if recovery_list_hash is not None:
        backup_ids_hash = recovery_list_hash
    singleton_struct = Program.to((SINGLETON_TOP_LAYER_MOD_HASH, (launcher_id, SINGLETON_LAUNCHER_PUZZLE_HASH)))
    return DID_INNERPUZ_MOD.curry(
        p2_puzzle_or_hash, backup_ids_hash, num_of_backup_ids_needed, singleton_struct, metadata
    )
```
