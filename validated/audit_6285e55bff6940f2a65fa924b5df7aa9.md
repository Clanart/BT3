### Title
mWOMSVBaseRewarder._calExpireForfeit never applies cooldown forfeiture, letting unlimited unforfeit reward claims - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` (rewards/mWOMSVBaseRewarder.sol:385-398) computes `rewardableAmount = _amount` and never queries `mWOMSV.getRewardablePercentWAD(_account)`, so `forfeitAmount` is always `_amount - _amount = 0`. The sibling contract `vlMGPBaseRewarder._calExpireForfeit` (rewards/vlMGPBaseRewarder.sol:386-400) correctly multiplies `_amount` by `vlMGP.getRewardablePercentWAD(_account)` to compute the forfeitable share for users mid-cooldown. Because the mWOM version is dead/no-op code, every mWOMSV holder — including those who have called `startUnlock()` and are in cooldown — receives 100% of accrued rewards via `getReward`/`getRewards`, with zero redistributed to remaining lockers.

### Finding Description
`mWomSV.sol` implements `getRewardablePercentWAD(address _user)` (wombat/mWomSV.sol:181-206), which reduces a user's rewardable share while tokens are mid-cooldown (partial credit based on elapsed cooldown time) — mirroring `VLMGP.sol:193-218`. The `mWOMSVBaseRewarder` contract even holds a reference to the locker (`ILocker public mWOMSV;`, rewards/mWOMSVBaseRewarder.sol:22), so wiring the call was clearly intended.

However, `_calExpireForfeit` in `mWOMSVBaseRewarder.sol` (lines 385-398) is:
```
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();
    uint256 forfeitAmount = _amount - rewardableAmount;
    if (forfeitAmount < (_amount / 1000)) {
        forfeitAmount = 0;
        rewardableAmount = _amount;
    }
    return forfeitAmount;
}
```
`rewardableAmount` is hardcoded to `_amount`, so `forfeitAmount` is always `0` and the `mWOMSV.getRewardablePercentWAD` call is never invoked — the `mWOMSV` state variable is otherwise unused in the forfeiture path. This function is called from `_sendReward` (line 363) during every `getReward`/`getRewards` claim path (`onlyMasterMagpie`, reachable when a user claims through `MasterMagpie`), meaning forfeiture never occurs regardless of a user's lock/cooldown state.

By contrast, `vlMGPBaseRewarder._calExpireForfeit` (rewards/vlMGPBaseRewarder.sol:386-400) correctly computes `rewardableAmount = _amount * vlMGP.getRewardablePercentWAD(_account) / 1e18`, applying real forfeiture for users partway through cooldown.

No modifier, nonReentrant guard, or other check compensates for this — the missing multiplication is a straightforward logic omission, not a config issue, and is reachable purely via normal `lock()`/`startUnlock()`/`getReward()` flows available to any unprivileged mWOM staker.

### Impact Explanation
This causes systemic misallocation of yield: forfeited amounts that should be redistributed to remaining lockers (via `_queueNewRewardsWithoutTransfer`, called only when `forfeitAmount > 0`) are never generated in the mWOMSV reward pool. Any mWOMSV holder — whether or not they ever call `startUnlock()` — always receives their full pro-rata reward instead of a reduced share during cooldown, so users who exit early are never penalized, and users who never exit correspondingly never receive the redistributed forfeited yield the protocol design intends. This matches Immunefi's "theft of unclaimed yield" / permanent economic value misallocation impact class: it's a protocol-wide accounting invariant break with no exploit precondition, entirely eliminating the yield-redistribution guarantee documented by the mirrored vlMGP mechanism.

### Likelihood Explanation
This requires no special capital or attacker skill: any existing or new mWOMSV staker who calls `startUnlock()` (a completely normal, permissionless action) and then claims rewards through `getReward`/`getRewards` immediately benefits from zero forfeiture, every single time, deterministically. It is 100% reproducible and always triggered on every claim during cooldown — not a probabilistic or race-condition bug.

### Recommendation
Update `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder._calExpireForfeit`:
```
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();
    uint256 forfeitAmount = _amount - rewardableAmount;
    if (forfeitAmount < (_amount / 1000)) {
        forfeitAmount = 0;
        rewardableAmount = _amount;
    }
    return forfeitAmount;
}
```

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
