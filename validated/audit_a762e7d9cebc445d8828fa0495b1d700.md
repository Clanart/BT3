### Title
Ours/Theirs conflict-resolution labels not remapped for rebase, causing silent misapplication of conflict resolution choices - (File: `app/src/ui/multi-commit-operation/dialog/copilot-resolution-helpers.ts`)

### Summary
This is the closest Desktop analog to the `give_coin`/flow-direction bug: a place where a *direction/side flag* (`ours` vs `theirs`) is used without accounting for the fact that its real-world meaning flips depending on the git operation in progress. In the Sui code, `add_flow_out` was used for what was really an inbound transfer. In Desktop, `ManualConflictResolution.ours`/`theirs` is treated as a fixed "Current branch" vs "Incoming branch" mapping everywhere it's surfaced to the user and passed to git, but git itself swaps the meaning of "ours"/"theirs" during a rebase (upstream = ours, the commit being replayed = theirs) — a fact the codebase's own documentation calls out but that the label/resolution helper does not account for.

### Finding Description
`ManualConflictResolution` is a two-value enum (`ours`/`theirs`) whose string values are passed directly as `--ours`/`--theirs` to `git checkout`: [1](#0-0) 

`checkoutConflictedFile` forwards the resolution literally to git with no adjustment for the current operation type: [2](#0-1) 

The UI copy that tells the user what "ours"/"theirs" mean is generated by `getOursTheirsLabels` / `getDeleteConflictLabels`, which unconditionally labels `ours` as "current"/local branch and `theirs` as "incoming": [3](#0-2) [4](#0-3) 

None of these functions take the current `MultiCommitOperationKind` (merge vs. rebase vs. cherry-pick) into account, even though `CopilotConflictsDialog` (the caller) has `operationKind` available as a prop: [5](#0-4) 

Crucially, the codebase's own diff-generation code explicitly documents that git's `ours`/`theirs` meaning inverts during a rebase, and states that *callers* — not this shared low-level helper — are responsible for correcting the mapping: [6](#0-5) 

That is exactly the invariant that is broken here: `getOursTheirsLabels`/`getDeleteConflictLabels`/`getDeleteConflictChoiceLabel` are the single shared place that produces the user-facing "Current"/"Incoming"/"Keep"/"Delete" labels for every manual-resolution dropdown and delete/modify conflict, and they never check `operationKind` to flip the labels for a rebase. If a user selects "Use current file" (which they read as "keep my own file") while a rebase is in progress, the dropdown maps that choice to `ManualConflictResolution.ours`, which is then passed straight through to `git checkout --ours` — but during a rebase, `--ours` resolves to the *upstream* content (the side the report calls the analogous "wrong direction" flow), not the user's own commit's content. The result is that the file silently ends up containing the opposite side's content from what the label told the user, and this gets baked into the rebased commit that is then pushed.

### Impact Explanation
This causes silent corruption of what the user commits/pushes: a rebase involving an attacker-controlled upstream branch or commit (e.g., a shared feature branch, a PR the user is rebasing onto, or content fetched from a remote) can end up silently overwriting the user's own conflicting changes with the attacker's content, or vice versa, while the UI tells the user the opposite happened. Since this operates on ordinary git conflict resolution during interchain/interactive operations that Desktop already supports (rebase continuation with manual resolution), no local/physical access, admin rights, or social engineering beyond "the user rebases onto an attacker-influenced branch and resolves a conflict" is required.

### Likelihood Explanation
Medium: rebasing is a common Desktop workflow, and the code path exists specifically to drive user-facing resolution choices from these label/direction values. Exploitability depends on whether `operationKind`/rebase context is actually threaded through to `getOursTheirsLabels` elsewhere in the call chain — I was not able to fully trace whether `CopilotConflictsDialog` or its ancestor components pass an adjusted `ours`/`theirs` pairing specifically for rebase before reaching these helpers, due to running out of investigation budget. The helper functions themselves, as authored, take no such parameter, and the sibling `diff.ts` code explicitly flags this exact class of bug as something "the caller is responsible for" — strongly suggesting the shared label helper is not doing that remapping.

### Recommendation
Thread the active `MultiCommitOperationKind` (or an explicit `isRebase` boolean) into `getOursTheirsLabels`, `getDeleteConflictLabels`, and `getDeleteConflictChoiceLabel`, and swap the "Current"/"Incoming" (and Keep/Delete) label assignment when the operation is a rebase, matching git's own inverted `ours`/`theirs` semantics for that operation — mirroring the `stage: 'ours' | 'theirs'` mapping guidance already documented in `getResolutionDiff`.

### Proof of Concept
Verification of the labeling behavior itself is straightforward to reproduce:
1. Start a rebase (`git rebase upstream-branch`) that produces a conflicting file.
2. In Desktop's conflict dialog, open the resolution dropdown for the conflicted file; the label reads "Use current file" for `ours` regardless of operation type, per `getOursTheirsLabels`. [7](#0-6) 
3. Selecting it stores `ManualConflictResolution.ours`, which is passed unmodified to `git checkout --ours -- <path>`. [2](#0-1) 
4. Per git semantics during rebase (`ours` = upstream, `theirs` = the commit being replayed) and per the project's own documentation of this exact caveat, the file content applied is the upstream side, not the user's local branch content the label implied. [6](#0-5) 

I was unable to confirm with full certainty (within the available tool budget) whether some intermediate layer between `CopilotConflictsDialog` and these helpers already compensates for rebase before invoking them; this should be verified directly in the running app (start a rebase with a real conflict and confirm dropdown-selected content vs. resulting file content) before treating this as a confirmed, exploitable finding rather than a strong candidate.

export function getDeleteConflictLabels(
  status: ManualConflict,
  ourBranch?: string,
  theirBranch?: string
): { readonly oursLabel: string; readonly theirsLabel: string } {
  const deletedSide = getDeletedSide(status)

  if (deletedSide === 'ours') {
    const keepSuffix = theirBranch ? ` from ${theirBranch}` : ''
    const deleteSuffix = ourBranch ? ` on ${ourBranch}` : ''
    return {
      oursLabel: `Delete file${deleteSuffix}`,
      theirsLabel: `Keep file${keepSuffix}`,
    }
  }

  const keepSuffix = ourBranch ? ` from ${ourBranch}` : ''
  const deleteSuffix = theirBranch ? ` on ${theirBranch}` : ''
  return {
    oursLabel: `Keep file${keepSuffix}`,
    theirsLabel: `Delete file${deleteSuffix}`,
  }
}

/**
 * Returns the ours/theirs dropdown labels for a conflicted file, handling
 * both delete-vs-modify and regular text conflicts.
 */
export function getOursTheirsLabels(
  status: ConflictedFileStatus | undefined,
  ourBranch?: string,
  theirBranch?: string
): { readonly oursLabel: string; readonly theirsLabel: string } {
  if (status !== undefined && isDeleteConflictFile(status)) {
    return getDeleteConflictLabels(status, ourBranch, theirBranch)
  }

  const oursLabel = ourBranch
    ? `Use current file from ${ourBranch}`
    : 'Use current file'
  const theirsLabel = theirBranch
    ? `Use incoming file from ${theirBranch}`
    : 'Use incoming file'
  return { oursLabel, theirsLabel }
}
