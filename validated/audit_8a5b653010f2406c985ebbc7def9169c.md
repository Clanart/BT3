### Title
`SignableTransaction` calculates fee and weight on a stale transaction template that omits the OP_RETURN data output — (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
Analogous to the Fei oracle bug (reading a value without first updating it), `SignableTransaction::new` computes `needed_fee`, the minimum-relay-fee check, the change amount, and the `MAX_STANDARD_TX_WEIGHT` check against a transaction skeleton built only from `payments` — after the caller-supplied `data` OP_RETURN output has already been decided but before it is included in the weight/vsize template. The fee and weight figures are therefore computed on an outdated version of the transaction and are wrong whenever `data` is present.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` pushes the OP_RETURN output into `tx_outs` at lines 194-202, but then calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204. `calculate_weight_vbytes` (lines 62-127) reconstructs a fresh `Transaction` whose `output` list is built *only* from `payments` (and optionally `change`) — the `data`/OP_RETURN output is never represented:

```rust
// line 85-94: outputs built only from `payments`
output: payments
  .iter()
  .map(|payment| TxOut { ... })
  .collect(),
```

Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) undercounts by the vsize of the OP_RETURN output (up to ~91 bytes for the allowed 80 bytes of data plus output overhead).
2. The `TooLowFee` minimum-relay check (line 211) validates the fee against the stale, smaller `vbytes`, so a transaction can pass the check while its *actual* fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` once the data output is included.
3. The change-arm path repeats the same stale read: `fee_with_change` at line 227 is again computed without the data output, and the change amount (line 230) is set from it, so the actual fee paid (`fee()`, lines 138-141) is a stale-computed value that does not achieve the intended `fee_per_vbyte`.
4. The `MAX_STANDARD_TX_WEIGHT` check (line 241) uses the stale `weight`, undercounting the real transaction weight.

### Impact Explanation
The transaction that is actually signed by `TransactionSignMachine::sign` (lines 373-397) includes the OP_RETURN output, so its real vsize/weight exceed the values used for fee calculation. The result is a signed transaction whose effective fee rate is strictly lower than the `fee_per_vbyte` requested — for small transactions with near-maximal data (80 bytes), the underestimate is on the order of tens of percent of total vsize. If the requested rate was set to the relay minimum, the broadcast transaction will be below the minimum relay fee and rejected by the network, leaving inputs unspendable as signed until the signing flow is re-run. `needed_fee()` also reports an incorrect value to callers (e.g., the processor reconciling expected vs. actual fees). Since `data` is derived from user-submitted InInstructions, an unprivileged depositor controls whether this stale-fee path is exercised and how large the discrepancy is.

### Likelihood Explanation
Any `SignableTransaction` constructed with `Some(data)` hits the bug; the `data` field is populated from externally supplied Bitcoin InInstruction payloads, so reaching it requires only sending a deposit/forwarding transaction with attached data. The miscalculation is deterministic — no race or threshold collusion is needed. Severity is bounded to Medium: the fee shortfall is at most ~91 vbytes and the weight-check bypass is small relative to `MAX_STANDARD_TX_WEIGHT`, so the impact is an under-fee/non-relaying transaction (funds temporarily unspendable, forced re-signing) rather than theft.

### Recommendation
Update the template before reading from it: pass the OP_RETURN output into `calculate_weight_vbytes` (e.g., extend its signature to accept the full output list, or accept `data: Option<&[u8]>` and construct the `ScriptBuf::new_op_return` output inside it) so that `vbytes`, `needed_fee`, the `TooLowFee` check, `fee_with_change`, the change amount, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the final transaction. Alternatively, compute weight from the fully assembled `tx_outs` vector instead of reconstructing a parallel transaction skeleton.

```rust
// data = Some(vec![0; 80]), fee_per_vbyte = 1

// Line 211: needed_fee = 1 * vbytes_stale; TooLowFee check uses vbytes_stale.

// After signing, the broadcast tx contains the OP_RETURN output.
// actual_vsize = vbytes_stale + ~91

```
The same stale-read pattern exists for the `weight > MAX_STANDARD_TX_WEIGHT` check at line 241, which omits the data output's weight.
