### Title
Attacker-controlled `Interpolation::Constant` coefficients / `verification_shares` in deserialized `ThresholdKeys` define an arbitrary group key inconsistent with the loaded secret share - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts untrusted bytes describing a threshold key, including the interpolation method, a vector of `Constant` coefficients, the local `secret_share`, and all `verification_shares`. `ThresholdKeys::new` then *evaluates* these attacker-supplied parameters — `group_key = Σ verification_shares[i] * interpolation_factor(i)` — without ever checking that the secret share is consistent with the verification shares (`G * secret_share == verification_shares[i]`). This is the Serai analog of evaluating an attacker-supplied expression: the `Constant(Vec<F>)` coefficient vector is a small "program" that the deserializer executes over attacker-chosen points to compute the group key the victim will use.

### Finding Description
- `ThresholdKeys::read` reads `t`, `n`, `i`, an interpolation tag, `n` scalars for `Interpolation::Constant`, a `secret_share`, and `n` verification shares directly from the reader (crypto/dkg/src/lib.rs lines 604-631).
- `ThresholdKeys::new` only checks that the number of shares equals `n`, participant indexes are `<= n`, and — for `Constant` — that `t == n` (lines 355-374). It then derives `group_key` from participants `1..=t` using the supplied coefficients (lines 376-378).
- `interpolation_factor` for `Constant` indexes `c[i - 1]` — i.e., fully attacker-chosen weights (lines 226-228).
- No code anywhere in this path verifies `C::generator() * secret_share == verification_shares[i]` or that the interpolated public key corresponds to the loaded secret. `view()` (lines 463-533) happily produces `secret_share`/`verification_shares` for signing under `group_key()`.
- Downstream, `Schnorr::sign_share` / `complete` (crypto/frost/src/algorithm.rs:201-217, crypto/frost/src/sign.rs:447-495) and bitcoin-serai's BIP-340 `Schnorr` algorithm (networks/bitcoin/src/crypto.rs:128-150) sign under `view.group_key()`, which is the attacker-defined point.

### Impact Explanation
An unprivileged party who can feed crafted bytes to `ThresholdKeys::read` can set `verification_shares[1]` to a public key `A` whose discrete log they know (e.g., `t = n = 1`, `i = 1`, tag `0`, coefficient `c = 1`), causing `group_key()` to equal `A` while `secret_share` is unrelated garbage. Any system that derives a deposit address/script from `group_key()` (bitcoin-serai's `x_only`/script_pubkey path) will direct funds to a key the attacker fully controls — theft — or, if `A` is random garbage, to an unspendable key — permanent loss. This satisfies the "funds reported received that are not spendable" / key-substitution acceptance criteria.

### Likelihood Explanation
Requires the victim to deserialize `ThresholdKeys` from attacker-influenced bytes (the rules explicitly allow `ThresholdKeys::read` as an untrusted-byte sink). Where key material is strictly locally generated, likelihood is low; wherever serialized keys are transported, restored, or exchanged, it is exploitable with no further preconditions.

### Recommendation
In `ThresholdKeys::new`, verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise; additionally reject `Interpolation::Constant` in `read` unless callers explicitly opt in, or validate that interpolated coefficients reproduce a self-consistent key (e.g., require the constant coefficients to be the known-valid Lagrange-derived values for `t == n`).

### Proof of Concept
Serialize a `ThresholdKeys<Secp256k1>` blob by hand: `id_len || Secp256k1::ID || t=1 || n=1 || i=1 || tag=0 || c=[1] || secret_share=0x01 || verification_shares[1]=A_attacker`. `ThresholdKeys::read` succeeds, `keys.group_key() == A_attacker` (since `A * 1`), while `G * secret_share != A`. The victim's signer produces shares that can never aggregate to a valid signature for `A_attacker`, and any funds sent to the address derived from `A_attacker` are controlled by the attacker.

Uncertain: whether in-scope callers actually pass adversarial bytes to `ThresholdKeys::read` rather than treating serialized keys as trusted local state — the finding's likelihood hinges on that deployment detail; the missing-consistency-check root cause is confirmed in the code regardless.
