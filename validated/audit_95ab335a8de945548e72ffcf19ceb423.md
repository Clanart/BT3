### Title
Deterministic cached nonces are re-signed across distinct FROST sessions under a single context, enabling secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` derives the FROST preprocess from a seed stored in `CachedPreprocesses`, keyed solely by `context = (b"DkgConfirmer", attempt)`. Every call under the same context reconstructs the *same* nonces via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` → `ChaCha20Rng::from_seed(seed)` → `Commitments::new`. `share()` and `complete()` each invoke `share_internal`, which calls `machine.sign(preprocesses, msg)` — a fresh FROST signature — every time it runs. If the `preprocesses` map or `msg` differs between two invocations under one `(attempt)` context, the validator produces two Schnorr signature shares over the *same* nonce with different binding factors/challenges, which is classic nonce reuse: the secret share is linearly recoverable. This is the parallel-session/cached-preprocess determinism bug class the FROST spec explicitly warns about ("a reused seed will lead to a reused preprocess … recovery of your private key share").

### Finding Description
In `preprocess_internal` (`coordinator/src/tributary/signing_protocol.rs:100-148`):

```rust
if CachedPreprocesses::get(self.txn, &self.context).is_none() {
  let (machine, _) = AlgorithmMachine::new(...).preprocess(&mut OsRng);
  ...
  CachedPreprocesses::set(self.txn, &self.context, &cache.0);
}
let cached = CachedPreprocesses::get(self.txn, &self.context).unwrap();
...
let (machine, preprocess) =
  AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached));
```

`from_cache` → `seeded_preprocess` (`crypto/frost/src/sign.rs:121-144`) regenerates identical `nonces` and `commitments` for a given seed. `share_internal` then signs (`signing_protocol.rs:156-180`):

```rust
let machine = self.preprocess_internal(participants).0;
...
let (machine, share) = machine.sign(preprocesses, msg)...
```

The signing path is invoked at least twice per context: `DkgConfirmer::share` (`signing_protocol.rs:304-310`) and `DkgConfirmer::complete`, which *re-executes* `share_internal` internally (`signing_protocol.rs:312-327`). Both calls accept externally supplied `preprocesses` and `key_pair`:

- `msg` is `set_keys_message(set, removed, key_pair)` (`signing_protocol.rs:296-300`) — it varies with `key_pair` and `removed`.
- `preprocesses` is whatever map was finalized for that call and remapped by `threshold_i_map_to_keys_and_musig_i_map`; nothing enforces that the set presented to `share()` equals the set presented to `complete()`, nor that `share()` is invoked only once per context.

The header comment itself states the safety invariant: "In order for nonce re-use to occur, the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again" — and admits this fails if "a logical flaw exists, letting new messages over write prior messages." Here, no overwrite is needed: `share()` and `complete()` are *distinct* signing invocations over independently supplied message maps under one nonce context. There is no check that the `preprocesses`/`key_pair` given to `complete()` are byte-identical to those used by `share()` (the file even notes a TODO: "check the commitments generated from the decided nonces are in fact its commitments on-chain" — unimplemented).

### Impact Explanation
Each `machine.sign` yields a Schnorr share `s_i = d + (b·ρ_i)·e·λ_i·x · c_i`-style linear equation in the same nonce `(d, e)` but with binding factors/challenges determined by the (distinct) commitment set and message. Two distinct shares over identical `(D, E)` commitments let an observer solve for the signer's secret share `x` — full recovery of the validator's MuSig/FROST private key share. Combined with threshold-many compromised shares this is threshold key compromise; for MuSig confirmation signing it enables forging validator-set confirmations. Severity: Medium–High (key share recovery, but requires two divergent signing invocations under one context).

### Likelihood Explanation
The divergence is reachable without any byzantine behavior: `share()` executes when our share is produced over the then-available preprocess map; `complete()` runs later over the finalized preprocess/share set. Any difference in the preprocess collection (e.g., additional confirmation-preprocess transactions finalized between the two calls) or a differing `key_pair`/`removed` derivation produces a second signature under reused nonces. Because the seed is persisted in `CachedPreprocesses` keyed only on `(b"DkgConfirmer", attempt)`, a process restart or any re-invocation of `share`/`complete` under the same attempt deterministically reuses the nonce — the DB cache makes reuse *guaranteed*, not probabilistic. Reachability caveat: the preprocess messages originate from validator-signed tributary transactions, so triggering divergence with attacker-chosen bytes requires a validator; however honest-validator timing/ordering divergence suffices for the leak.

### Recommendation
- Bind the full signed preimage to the cached seed: store `(seed, preprocesses_digest, msg_digest)` and refuse to `sign` if a subsequent invocation presents different inputs under the same context.
- Alternatively, derive the nonce seed as `H(context || serialize(preprocesses) || msg)` so distinct sessions get distinct nonces.
- Implement the noted TODO: before publishing a share, verify on-chain that the commitments derived from the cached seed match this node's published preprocess, and abort if the session inputs changed.

### Proof of Concept
1. Attempt N of the DKG confirmer: `share(preprocesses_A, key_pair)` is called. `preprocess_internal` loads seed `S` from `CachedPreprocesses[b"DkgConfirmer"||N]`, re-derives nonces `(d, e)`, and `share_internal` produces share `s_1 = f(d, e, x, ρ_A, c_A)` where `c_A` binds commitment set A and `msg_A = set_keys_message(..., key_pair)`.
2. Later, `complete(preprocesses_B, key_pair', shares)` is called with `B ≠ A` (e.g., an extra validator's preprocess finalized, or a different `key_pair` claim). `share_internal` re-runs: same seed `S` → same `(d, e)`, but `sign` computes different binding factors `ρ_B` and challenge `c_B`, emitting share `s_2`.
3. Observer collects `s_1, s_2` and the published commitments `(D, E)`. Since `(d, e)` are identical, the two-share system is linearly solvable for the secret share `x` (standard Schnorr/FROST nonce-reuse algebra: `x = (s_1 − s_2 + …)/(λ·(c_1·…− c_2·…))` over the known binding terms).
