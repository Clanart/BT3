### Title
Reused FROST nonces via never-invalidated `CachedPreprocesses` enable secret share recovery — ([File: coordinator/src/tributary/signing_protocol.rs])

### Summary
The reported bug class is an interaction performed before the state mutation that should make it non-repeatable (a payout sent before gOHM is burned, enabling reentry). Serai's `SigningProtocol::preprocess_internal` exhibits the same structural flaw: it consumes a cached FROST preprocess seed to emit a signature share (the "interaction"), yet never deletes or rotates `CachedPreprocesses` (the missing "effect"). Every subsequent call for the same `context` deterministically rebuilds the same nonces, so multiple distinct shares can be issued on one nonce pair.

### Finding Description
In `preprocess_internal`, the DB entry `CachedPreprocesses::get(self.txn, &self.context)` is read, XOR-decrypted, and passed to `AlgorithmSignMachine::from_cache`, but no `remove`/`delete` is ever issued — the seed persists for the lifetime of `context`. `from_cache` routes to `seeded_preprocess`, which seeds `ChaCha20Rng::from_seed(*seed.0)` and regenerates identical `(nonces, commitments)`. `share_internal` calls `preprocess_internal` again and then `machine.sign(preprocesses, msg)`, so each invocation of `share`/`complete` under the same context signs with the same `(d, e)` nonces while `msg`, the included participant set, or the key pair may differ. `share` is parameterized by `key_pair` (msg = `set_keys_message(..., key_pair)`), and `complete` re-runs `share_internal` with caller-supplied `preprocesses`; differing sets or messages produce shares bound to different binding factors `rho` and challenges `c` on the same nonce — exactly the condition FROST's docs warn leaks the private key share ("Reusing preprocesses would enable a third-party to recover your private key share").

### Impact Explanation
Given two shares over the same nonces but different `rho`/`c` (different included sets, attempts sharing a context, or different `key_pair`s), an observer solves a linear system for the signer's secret share `s`, collapsing the MuSig threshold to `t-1` and ultimately recovering the coordinator's signing key for the set. Shares and preprocesses are broadcast data, so the attack requires only triggering a second `sign` under a reused context — no privileged access.

### Likelihood Explanation
Reachability hinges on the coordinator invoking `share`/`complete` more than once per `(b"DkgConfirmer", attempt)` context with differing inputs — e.g., a retry after an invalid-participant error followed by a successful sign with a different preprocess set, or confirming more than one `KeyPair` per attempt. `sign` computes `rho` over the transcripted participant set and `hash_msg`, so any variation in either makes the second share linearly independent and leaks the share. I verified the seed is never deleted and nonces are fully deterministic from the seed; I could not fully enumerate handle.rs call multiplicity, so reachability of a *distinct* second sign under one context is the uncertain link — the cryptographic precondition itself is concretely present.

### Recommendation
Delete `CachedPreprocesses` entry immediately after `from_cache` consumes it (consume-on-use), and/or mix a per-invocation nonce or the serialized preprocess set into the seed/context so repeated calls cannot regenerate identical nonces. Additionally, refuse to `sign` twice under one context.

### Proof of Concept
1. Attacker (a threshold validator) submits a preprocess set A for a `DkgConfirmer` attempt; coordinator emits share `s_1 = d + b·e·rho_1 + λ_1·s·c_1` (or errors and retries).
2. Attacker causes a second `share`/`complete` call for the same attempt context with a different participant set or different `key_pair` → share `s_2 = d + b·e·rho_2 + λ_2·s·c_2` over identical `(d, e)` since `CachedPreprocesses` was never cleared and `from_cache` reseeds `ChaCha20Rng` identically.
3. From the two public shares and publicly computable `rho_i, c_i, λ_i`, solve for `s`.
