## Analysis

The Pyth report's core broken invariant: a signed exponent (`price.expo`) was scaled using its **magnitude only** (`-price.expo` when negative), losing the sign information needed to know whether to multiply or divide — producing values off by the square of the true scale factor.

The same broken invariant exists in Hyperbridge's `hyper-fungible-token` pallet decimal-conversion helpers, which use `saturating_sub` on unsigned `u8` decimal counts instead of a signed difference: [1](#0-0) 

`erc_decimals.saturating_sub(local_decimals)` silently clamps to `0` whenever `erc_decimals < local_decimals` — exactly the "negative exponent" case the Pyth bug mishandled. The doc comments even admit the function only works in one direction ("Divides ... to scale **down** from ERC20 precision", "Multiplies ... to scale **up**"), with no handling for the reverse case.

Both helpers are used directly in the ISMP module callback that mints/refunds tokens on inbound cross-chain messages: [2](#0-1) [3](#0-2) 

### Title
Wrong-direction decimal scaling in `convert_to_balance`/`convert_to_erc20` causes silent fund mis-mint - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_balance` and `convert_to_erc20` compute the decimal scale factor via `erc_decimals.saturating_sub(local_decimals)` (and its symmetric counterpart), which is only correct when `erc_decimals >= local_decimals`. When the source ERC20 token has **fewer** decimals than the local Substrate asset (e.g., a 6-decimal token bridged into an 18-decimal local asset), the subtraction saturates to `0`, and no scaling is applied at all — mirroring the Pyth report's failure to respect a negative/reverse-direction exponent.

### Finding Description
`convert_to_balance` is called in `on_accept` (minting/transferring to a beneficiary on an inbound bridge message) and `on_timeout` (refunding the original sender), using `erc_decimals` read from the governance-configured `Precisions` storage and `local_decimals` from the local asset's metadata. Both directly feed the amount that is minted or transferred: [4](#0-3) 

If `erc_decimals < local_decimals` (a legitimate, common configuration — many real tokens use 6 or 8 decimals while Substrate assets commonly use higher precision), `saturating_sub` returns `0`, so `convert_to_balance` divides by `10^0 = 1` instead of multiplying by `10^(local_decimals - erc_decimals)`. The raw small-decimal ERC20 amount is minted as-is into the large-decimal local asset, producing a beneficiary balance up to `10^n` times smaller than the value actually deposited — silent, massive value loss for the user, exactly analogous to the Pyth report's "5e-5 recorded as 5e5" deviation.

The symmetric helper `convert_to_erc20` has the identical flaw in the opposite direction: [5](#0-4) 

Here, in the same `erc_decimals < local_decimals` scenario, the multiplier collapses to `10^0 = 1`, so a local balance denominated in the *larger*-decimal precision is passed straight through as an ERC20 amount that the destination chain interprets in *smaller*-decimal precision — inflating the released/minted ERC20 amount by the same factor, which is a fund-drain vector against the custodial escrow rather than a mere value-loss for the user.

Existing guards do not stop this: there is no check anywhere in `convert_to_balance`/`convert_to_erc20` or their call sites (`on_accept`, `on_timeout`) that `erc_decimals >= local_decimals`; `Precisions` is simply looked up and trusted without validating decimal ordering against the actual token/asset pair.

### Impact Explanation
Depending on which direction is exercised, this causes either:
- Silent underpayment to bridge recipients (funds effectively lost/locked when `erc_decimals < local_decimals` on the mint/refund path), or
- Overpayment/over-release of ERC20 value relative to the custodied balance on the burn/withdraw path (`convert_to_erc20`), draining the pallet's custodial reserves beyond what was actually escrowed.

Either outcome is a direct, unauthorized fund-loss/fund-drain condition matching the bounty's "stealing or loss of funds" and "transaction manipulation" categories, triggered purely by normal bridging with a realistic decimal configuration — no malicious relayer, prover, or governance actor is required.

### Likelihood Explanation
This is reachable by any user bridging a token whose ERC20 decimals are lower than the corresponding local asset's decimals (a routine, foreseeable configuration difference, not an edge case) — every inbound transfer for such an asset pair triggers the flawed conversion deterministically. No race condition, front-running, or privileged access is needed.

### Recommendation
Replace the `saturating_sub`-based unsigned scale computation with a signed comparison that multiplies or divides based on which of `erc_decimals`/`local_decimals` is larger, e.g.:
```rust
if erc_decimals >= local_decimals {
    value / 10^(erc_decimals - local_decimals)
} else {
    value * 10^(local_decimals - erc_decimals)
}
```
applied symmetrically in both `convert_to_balance` and `convert_to_erc20`, and add an invariant/test asserting round-trip correctness for `erc_decimals < local_decimals` configurations.

### Proof of Concept
1. Governance configures `Precisions::<T>::insert(local_asset_id, source_contract, 6)` for a local asset whose metadata decimals is `18` (a realistic pairing, e.g. bridging 6-decimal USDC into an 18-decimal local representation).
2. A user sends an inbound ISMP post request depositing `1_000_000` raw units (i.e., 1.0 USDC at 6 decimals).
3. `on_accept` calls `convert_to_balance(1_000_000, erc_decimals=6, local_decimals=18)`.
4. `erc_decimals.saturating_sub(local_decimals) = 0`, so the divisor is `10^0 = 1`, giving `amount = 1_000_000`.
5. The beneficiary is minted/transferred `1_000_000` units of an 18-decimal asset — i.e. `0.000000000001` tokens instead of the intended `1.0` token equivalent, a ~10^12x value loss versus the deposited amount.

(Note: I was unable to inspect the outbound `lib.rs` extrinsic that calls `convert_to_erc20` directly within the available iterations, so the overpayment/drain direction is inferred from the symmetric, equally-flawed helper definition rather than a directly traced call site — this should be verified against `modules/pallets/hyper-fungible-token/src/lib.rs`.)

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
