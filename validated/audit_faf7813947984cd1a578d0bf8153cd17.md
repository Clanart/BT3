### Title
All-or-nothing batch price resolution blocks liquidation of insolvent positions when any unrelated asset's oracle feed is stale - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`price-multi-resolve`/`iter-price-multi` fold over every asset a borrower has enabled, and abort the *entire* batch with `ERR-ORACLE-MULTI` if a single feed fails `oracle-price-legal`/`oracle-timestamp-fresh`, mirroring the reported `PaymentSplitter._release_all` flaw where one bad item blocks all others.

### Finding Description
`get-assets` builds the price list for a position by calling `price-multi-resolve` over every collateral/debt asset enabled for the account's mask: [1](#0-0) 

`price-multi-resolve` folds `iter-price-multi` over that list, and once any single entry's `price-resolve` fails (stale timestamp, `>max-staleness`, or non-monotonic timestamp), `valid` flips to `false` for the whole accumulator, and every subsequent item is skipped via `(asserts! valid acc)`: [2](#0-1) 

The caller then does `(asserts! (get valid response) ERR-ORACLE-MULTI)` and `get-assets` wraps the whole thing in `unwrap-panic`, so a single unresolvable price anywhere in the mask panics the entire call — there is no partial/best-effort path analogous to `release()`'s per-payee pull mechanism.

`liquidate` calls `(get-assets mask)` unconditionally before computing the borrower's health and liquidating a specific `coll-aid`/`debt-aid` pair: [3](#0-2) 

Because `mask` includes *all* of the borrower's enabled collateral and debt (not just the two assets the liquidator cares about), a single stale/unresolvable feed for an unrelated asset the borrower happens to hold blocks the entire liquidation call, exactly like `_release_all` reverting for all payees because one payee's release amount was already zero.

### Impact Explanation
This is a temporary freezing of funds / protocol solvency risk: an undercollateralized borrower holding even a small amount of an asset whose oracle feed goes stale (network delay, feed update lag, DIA/Pyth publisher outage) becomes unliquidatable for every collateral/debt pair, not just the affected asset, until that specific feed is refreshed. This can let bad debt accumulate protocol-wide, which lands on the in-scope "temporary freezing of funds" / potential insolvency impact class, directly analogous to the report's "whole transaction reverts because of unrelated payee" bug class (confidence/staleness gating category explicitly in scope).

### Likelihood Explanation
Any borrower who enables a low-liquidity or slow-updating asset (or a feed nearing its `max-staleness` boundary) as one of several collaterals/debts can trigger this simply by the feed not updating within the window — no attacker action is required to create the condition, and a griefer/borrower could deliberately enable an asset with a feed they know is thinly updated to shield an otherwise liquidatable position, similar to any user calling the removed `_release_all` with a zero-releasable payee.

### Recommendation
Scope `get-assets`/`price-multi-resolve` calls used inside `liquidate` (and similar health-check paths) to only the specific `coll-aid`/`debt-aid` pair (plus whatever minimal set is required for the LTV computation), or make `iter-price-multi` degrade gracefully per-asset (skip/zero-out the unresolved asset for health purposes rather than aborting the whole fold), so a stale feed on one asset cannot block liquidation/health evaluation of a position via other, perfectly fresh, feeds.

### Proof of Concept
1. Borrower opens a position with two collaterals: STX (price feed healthy) and a smaller, thinly-traded asset X whose Pyth feed silently stops updating.
2. Borrower's STX debt becomes undercollateralized (LTV crosses `ltv-liq-partial`), making the position liquidatable purely based on STX/debt-asset prices.
3. A liquidator calls `liquidate` targeting the STX collateral and the debt asset; `liquidate` still calls `(get-assets mask)` covering all enabled assets, including X.
4. X's feed timestamp now exceeds `max-staleness` (or violates monotonicity), so `iter-price-multi` sets `valid: false`; `price-multi-resolve` asserts `ERR-ORACLE-MULTI`; `get-assets`'s `unwrap-panic` panics.
5. `liquidate` reverts entirely, even though the STX/debt pair's prices were fresh and the position was genuinely liquidatable — bad debt accrues until X's feed recovers.

(define-private (price-multi-resolve
  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))
  (let ((init { output: (list), valid: true, aids: aids, idx: u0 })
        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
    (ok (get output response))))
