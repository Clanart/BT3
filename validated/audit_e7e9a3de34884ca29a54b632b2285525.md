### Title
Tokenfactory denom admin can update the allow list to permanently freeze existing holders' funds - ([File: sei-cosmos/x/bank/keeper/msg_server.go])

### Summary
The reported bug class is: a whitelist/asset-listing mechanism blocks users from moving funds they already legitimately hold once the asset (or their address) falls off the whitelist, with no bypass or grandfathering for existing balances. Sei-chain has a directly analogous mechanism in the tokenfactory/bank denom allow-list feature: `MsgUpdateDenom` lets a tokenfactory denom's admin freely rewrite the `AllowList` for that denom at any time, and both `MsgSend` and `MsgMultiSend` reject the transfer if **either** the sender or the recipient is not on the current allow list for that denom.

### Finding Description
`x/tokenfactory/keeper/msg_server.go`'s `UpdateDenom` handler lets the denom admin call `SetDenomAllowList` at will, replacing the allow list for the denom with an arbitrary new list: [1](#0-0) 

`SetDenomAllowList`/`GetDenomAllowList`/`IsInDenomAllowList` are implemented in the bank keeper: [2](#0-1) 

Both `Send` and `MultiSend` message handlers enforce this allow list on **both** the sender and receiver before allowing any transfer of a tokenfactory denom: [3](#0-2) [4](#0-3) 

Because the check is applied to the **sender** address (`from`) as well as the recipient, any account that already holds balances of the tokenfactory denom becomes permanently unable to move (or "redeem"/transfer out) those funds the moment the denom admin issues an `UpdateDenom` that omits that address from the new allow list, or shrinks/replaces the list. There is no carve-out for addresses that already hold a balance prior to the allow-list change — the check is purely a live lookup on the current allow list at send time: [5](#0-4) 

This mirrors the UXDController pattern exactly: an asset (denom) being "delisted" (removed from allow list) after a user has already deposited/acquired it blocks that user's ability to redeem/transfer their holdings, with no fallback path.

### Impact Explanation
Funds are not burned or stolen, but they become **permanently frozen** for any holder excluded from an allow-list update, since the denom admin's action is retroactive and irrevocable from the affected user's perspective (they cannot self-remedy; only the admin can restore their inclusion). Bank transfer, and by extension any protocol relying on `bank.Send`/`MultiSend` for this denom (e.g., DEXs, pointer contracts, lending markets), stops working for those addresses. This satisfies the "permanent freezing of funds" impact criterion for a Medium-severity finding — it is not full loss (admin can restore the list), but it is an unbounded freeze fully in the hands of a single admin account, applied retroactively to already-held balances rather than just future recipients.

### Likelihood Explanation
Any tokenfactory denom creator/admin can trigger this via a single `MsgUpdateDenom` transaction — this requires no special chain permission beyond being the admin of a denom they created, which is a normal, unprivileged tokenfactory workflow. No governance or validator collusion is needed. The likelihood of a user being caught by such an update is entirely dependent on denom admin behavior (could be malicious or accidental, e.g. an admin trying to add one address to the list and inadvertently dropping previously-approved holders because `MsgUpdateDenom`'s `AllowList` fully replaces rather than merges the existing list).

### Recommendation
- Do not enforce the sender-side allow-list check (`IsInDenomAllowList` on `from`/inputs) retroactively against balances acquired before an allow-list update, or provide an explicit exit/redeem path unaffected by allow-list membership (e.g., allow removed addresses to send back to the admin or burn, even if disallowed from sending elsewhere).
- Alternatively, only enforce allow-list checks on the *recipient* side (controlling who can newly receive the denom) rather than blocking existing holders from moving/disposing of balances they already hold, and clearly document/design `UpdateDenom` as additive rather than a full replace, or require it to always include existing holders unless deliberately blacklisting them.
- Consider emitting a warning/event and requiring an explicit flag when an `UpdateDenom` allow-list change would newly exclude any address currently holding a non-zero balance of the denom, to prevent accidental griefing.

### Proof of Concept
1. Attacker (or any user) calls `MsgCreateDenom` to create `factory/{sender}/COIN`, optionally with no allow list, and mints/distributes tokens to `userA`.
2. `userA` acquires/holds a balance of `factory/{sender}/COIN` (e.g., via `MsgMint` to themselves or `MsgSend` from admin) — see denom admin flow in `x/tokenfactory/keeper/msg_server.go` `Mint`/`Burn` at [6](#0-5) .
3. Denom admin calls `MsgUpdateDenom` with an `AllowList` that does not include `userA`'s address: [7](#0-6) 
4. `userA` attempts `MsgSend` of their `factory/{sender}/COIN` balance to any address. The check `IsInDenomAllowList(ctx, from, ...)` fails because `userA` is not in the current allow list, and the transaction reverts with `"... is not allowed to send funds"`: [3](#0-2) 
5. `userA`'s balance of `factory/{sender}/COIN` is now permanently locked/unspendable unless the admin issues another `MsgUpdateDenom` restoring `userA` to the list — a decision solely in the admin's hands, exactly mirroring the reported "asset no longer listed → can't redeem" bug class. This is confirmed by the existing repo test `TestSendReceiverNotInAllowList` (analogous on the receiver side) at [8](#0-7) , which the sender-side path in `msg_server.go` line 43-45 mirrors symmetrically for the sender.

func (server msgServer) UpdateDenom(goCtx context.Context, msg *types.MsgUpdateDenom) (*types.MsgUpdateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.validateUpdateDenom(ctx, msg)
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	updateDenomEvent := sdk.NewEvent(
		types.TypeMsgUpdateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeUpdatedTokenDenom, denom),
	)

	if msg.AllowList != nil {
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		updateDenomEvent = updateDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		updateDenomEvent,
	})

	return &types.MsgUpdateDenomResponse{}, nil
}

func (server msgServer) Mint(goCtx context.Context, msg *types.MsgMint) (*types.MsgMintResponse, error) {

	// pay some extra gas cost to give a better error here.
	_, denomExists := server.bankKeeper.GetDenomMetaData(ctx, msg.Amount.Denom)
	if !denomExists {
		return nil, types.ErrDenomDoesNotExist.Wrapf("denom: %s", msg.Amount.Denom)

	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	err = server.mintTo(ctx, msg.Amount, msg.Sender)
	if err != nil {
		return nil, err
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgMint,
			sdk.NewAttribute(types.AttributeMintToAddress, msg.Sender),
			sdk.NewAttribute(types.AttributeAmount, msg.Amount.String()),
		),
	})

	return &types.MsgMintResponse{}, nil
}

func (k BaseSendKeeper) SetDenomAllowList(ctx sdk.Context, denom string, allowList types.AllowList) {
	store := ctx.KVStore(k.storeKey)
	denomAllowListStore := prefix.NewStore(store, types.DenomAllowListKey(denom))

	m := k.cdc.MustMarshal(&allowList)
	denomAllowListStore.Set([]byte(denom), m)
}

func (k BaseSendKeeper) GetDenomAllowList(ctx sdk.Context, denom string) types.AllowList {
	store := ctx.KVStore(k.storeKey)
	store = prefix.NewStore(store, types.DenomAllowListKey(denom))

	bz := store.Get([]byte(denom))
	if bz == nil {
		return types.AllowList{}
	}

	var allowList types.AllowList
	k.cdc.MustUnmarshal(bz, &allowList)

	return allowList
}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}
