### Title
Bank Precompile `sendNative` Bypasses `BlockedAddr` Protection Enforced by MsgSend/MultiSend - ([File: precompiles/bank/bank.go])

### Summary
The Cosmos `x/bank` message handlers enforce a `BlockedAddr` check before allowing any transfer to complete, but the EVM bank precompile's `sendNative` method calls the lower-level `SendCoinsAndWei` keeper primitive directly, skipping that check entirely. This mirrors the PraisonAI bug class: a protection mechanism (attribute/address blocklist enforcement) is implemented only at one call path and is bypassed via an alternate path that reaches the same privileged operation.

### Finding Description
`x/bank`'s `MsgSend` and `MsgMultiSend` handlers explicitly reject transfers to any address for which `BlockedAddr` returns true before calling the underlying `SendCoins`/`InputOutputCoins` keeper methods: [1](#0-0) [2](#0-1) 

`BlockedAddr` is documented to cover not just module accounts but also dynamically-derived addresses such as the EVM coinbase addresses: [3](#0-2) 

However, the EVM bank precompile's `sendNative` method (reachable from any EVM transaction sender at precompile address `0x0000000000000000000000000000000000001001`) decodes an arbitrary caller-supplied bech32 address and calls `p.bankKeeper.SendCoinsAndWei` directly, entirely bypassing the `BlockedAddr` gate that `MsgSend`/`MsgMultiSend` enforce: [4](#0-3) 

By contrast, the precompile's `send` method (for tokenfactory/ERC20-pointer denoms) does go through `p.bankMsgServer.Send`, which does perform the `BlockedAddr`/allow-list checks: [5](#0-4) 

This is the same bug class as the PraisonAI advisory: the security enforcement (attribute filtering / address blocklist) exists at one interception point (AST `ast.Attribute` check / `MsgSend` handler) but a semantically-equivalent alternate access path (`type.__getattribute__` / direct `SendCoinsAndWei` keeper call from the EVM precompile) reaches the same sensitive operation without being checked.

### Impact Explanation
`BlockedAddr` in sei-chain's bank keeper is used to protect module accounts and other protocol-reserved addresses — including dynamically-derived `evm_coinbase`-prefixed addresses used for per-transaction EVM fee/coinbase accounting — from receiving externally-initiated transfers, as called out in the `distribution` keeper's `SetWithdrawAddr`/`canReceiveWithdrawAddr` comments referencing the exact same blocklist: [6](#0-5) 

Because `sendNative` skips this check, any EVM caller can send `usei`/wei directly to a blocked address, including a computed `evm_coinbase`-prefixed address for an arbitrary transaction index, or to protected module accounts. This can corrupt invariants that the deferred EndBlock coinbase-sweep/fee-accounting logic relies on (assuming coinbase balances are only ever populated by the protocol's own fee-crediting flow), potentially leading to fee/accounting corruption or unexpected reverts/panics during block finalization when balances don't match expectations. This is a protection-mechanism failure with concrete fund-routing/accounting impact reachable from a single unprivileged EVM transaction.

### Likelihood Explanation
High likelihood: `sendNative` is a public, permissionless method on a well-known precompile address callable by any EOA or contract in a single transaction with no special privileges, and the missing check is a straightforward code-path omission (present in `send`, absent in `sendNative`).

### Recommendation
Add an explicit `p.bankKeeper.BlockedAddr(receiverSeiAddr)` (and, if applicable, `IsInDenomAllowList`) check in `sendNative` before calling `SendCoinsAndWei`, mirroring the checks performed in `msgServer.Send`/`MultiSend`, so that all coin-transfer entry points — including EVM precompile paths — enforce the same address-blocking invariant consistently rather than relying on a single call site.

### Proof of Concept
1. An attacker deploys or calls an EVM contract that invokes the bank precompile at `0x0000000000000000000000000000000000001001` with method `sendNative(string receiverAddr)` and a non-zero `value`.
2. Set `receiverAddr` to the bech32 encoding of a blocked address, e.g. an `evm_coinbase`-prefixed address (`keeper.CoinbaseAddressPrefix` + an 8-byte tx index) or a module account address that `BlockedAddr` would normally reject.
3. Because `sendNative` (precompiles/bank/bank.go) calls `p.bankKeeper.SendCoinsAndWei` directly rather than going through `msgServer.Send`, the transfer succeeds even though the equivalent `MsgSend` for the same recipient would be rejected with `"is not allowed to receive funds"`.

Note: I was not able to inspect the full body of `SendCoinsAndWei` in `sei-cosmos/x/bank/keeper/send.go` (only its signature location was located before tool budget ran out), so I cannot rule out that a `BlockedAddr` check exists inside that specific function itself rather than at the message-handler layer. If `SendCoinsAndWei` does perform this check internally, the bypass described above would not apply and this finding should be treated as unconfirmed pending that verification.

// SetWithdrawAddr sets a new address that will receive the rewards upon withdrawal
func (k Keeper) SetWithdrawAddr(ctx sdk.Context, delegatorAddr sdk.AccAddress, withdrawAddr sdk.AccAddress) error {
	// Reject any address the bank keeper would block from receiving funds, not just
	// the module-account blocklist: BlockedAddr also covers dynamically-derived
	// addresses such as the EVM coinbase addresses. Rejecting them here prevents a
	// delegator from parking an unpayable withdraw address that would later make the
	// force-withdraw in AfterValidatorRemoved panic during EndBlock.
	if k.blockedAddrs[withdrawAddr.String()] || k.bankKeeper.BlockedAddr(withdrawAddr) {
		return sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive external funds", withdrawAddr)
	}

		return nil, 0, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())

	}

	if err != nil {
		return nil, 0, err
	}
	receiverSeiAddr, err := p.accAddressFromArg(ctx, args[1])
	if err != nil {
		return nil, 0, err
	}

	msg := &banktypes.MsgSend{
		FromAddress: senderSeiAddr.String(),

	err = msg.ValidateBasic()

		return nil, 0, err
	}
