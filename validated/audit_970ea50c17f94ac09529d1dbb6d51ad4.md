### Title
Fail-open branch protection check on API/network failure - ([File: app/src/lib/api.ts])

### Summary
`fetchPushControl()` is Desktop's analog of the "oracle" in the referenced report: it is the single source of truth the app queries to decide whether the current user is allowed to push, force-push, or delete a branch that may be protected. Like the Canto TWAP oracle, it has no resilience story for the case where the upstream data source (here, the GitHub `push_control` API) is unreachable, slow, rate-limited, or intercepted — and instead of refusing to answer or flagging the result as stale/unreliable, it silently returns the most permissive possible answer.

### Finding Description
`fetchPushControl()` in [1](#0-0)  calls the GitHub branch `push_control` endpoint to determine push/force-push/deletion permissions and required status checks/reviews for a branch. On any failure — network downtime, DNS/TLS interception by a malicious proxy sitting between Desktop and the API, rate limiting, or an unexpected error — the `catch` block does not propagate an error, retry with backoff, or return a "state unknown" sentinel. It unconditionally returns a hard-coded object granting full access:
```
allow_actor: true,
allow_deletions: true,
allow_force_pushes: true,
required_status_checks: [],
required_approving_review_count: 0,
``` [2](#0-1) 

This result flows directly into `isBranchPushable()` in [3](#0-2) , which treats `allow_actor !== false` combined with zero required checks/reviews as "pushable," and into `refreshBranchProtectionState()` in [4](#0-3) , which sets `currentBranchProtected = false` whenever `isBranchPushable()` returns true — i.e., exactly the fail-open branch caused by the API error.

This is architecturally identical to the reported bug class: there is no tracking of "how long has it been since we last got a trustworthy answer," no distinction between "confirmed unprotected" and "couldn't check," and — unlike the precedent the auditors called out in the Canto codebase (refusing to return a sample) — Desktop does the opposite of the recommended mitigation: it actively manufactures a permissive answer instead of refusing to answer or flagging staleness/uncertainty.

### Impact Explanation
`currentBranchProtected` (derived from this fail-open value) is consumed purely as a UI advisory signal — it drives warning banners in the commit sidebar/changes list [5](#0-4)  and in `filter-changes-list.tsx`, and it is *not* what actually enforces branch protection (GitHub's server does that independently). This materially limits the severity compared to the oracle report: an attacker who can force this fail-open path (e.g., by running a malicious proxy that the user's git/HTTP traffic passes through, or simply during a genuine GitHub outage) cannot bypass real server-side protections or force a push through — GitHub will still reject an unauthorized force-push/deletion attempt server-side.

What is lost is the user-facing safety net: Desktop will silently suppress the "this branch is protected" warning and the associated friction (e.g., confirmation dialogs gated on `currentBranchProtected` in the commit workflow) that would normally make a user pause before attempting a potentially destructive force-push/rebase against what they believe is an unprotected branch. This can lead the user to attempt a force-push/rebase they would not otherwise have attempted, increasing the chance of an accidental local-history rewrite being pushed and of confusing failure UX, but it does not, on its own, achieve code execution, credential exfiltration, an OAuth/account-binding bypass, a sandbox/IPC escape, or an actual write past what GitHub itself would already reject.

### Likelihood Explanation
The failure path is trivially reachable: any GitHub API error (`ghRequest` throwing, a timeout, a 5xx, a malformed response body causing `parsedResponse` to throw) reaches this same `catch` and returns the permissive default — see the broad `try { ... } catch (err) { ... }` wrapping the whole request in [6](#0-5) . An on-path attacker (malicious/compromised proxy, captive portal, or a targeted network partition against api.github.com while leaving git operations reachable) can deterministically trigger this by simply breaking or delaying the `push_control` request, without needing to compromise the user's machine or credentials — consistent with the "remote/proxy response" attacker model. Genuine GitHub outages/rate-limiting will also trigger it non-adversarially, as the original report anticipated with its DOS/downtime scenario.

### Recommendation
Do not fail open. On request failure, `fetchPushControl()` should return a distinguishable "unknown" state (e.g. `null`/`undefined` or a tagged union) rather than a synthetic fully-permissive `IAPIPushControl`. Callers (`refreshBranchProtectionState`, `isBranchPushable`) should treat "unknown" conservatively — either keep the last known-good protection state (with an age/staleness indicator, mirroring the audit's suggested mitigation of tracking observation age) or default `currentBranchProtected` to `true`/"show warning" rather than `false` when the check could not be completed, and surface this uncertainty to the user instead of silently suppressing the branch-protection warning.

### Proof of Concept
1. Set up a git remote/proxy (or use a network in which `api.github.com` push_control requests are blocked/delayed while git object transfer over HTTPS/SSH still functions, e.g. via a MITM proxy or firewall rule targeting the API host only).
2. In Desktop, open a repository with a protected default branch and make a local commit that diverges from the remote (e.g., via `git commit --amend` or a rebase).
3. Trigger `refreshBranchProtectionState()` (this runs automatically after fetch/push in [7](#0-6)  and [8](#0-7) ) while the `push_control` API call is failing.
4. Observe that `fetchPushControl()` swallows the error and returns the permissive default in [9](#0-8) , causing `isBranchPushable()` to return `true` and `currentBranchProtected` to be set to `false`, so Desktop shows no branch-protection warning even though the branch is in fact protected on GitHub.

  public async fetchPushControl(
    owner: string,
    name: string,
    branch: string
  ): Promise<IAPIPushControl> {
    const path = `repos/${owner}/${name}/branches/${encodeURIComponent(
      branch
    )}/push_control`

    const headers: any = {
      Accept: 'application/vnd.github.phandalin-preview',
    }

    try {
      const response = await this.ghRequest('GET', path, {
        customHeaders: headers,
      })
      return await parsedResponse<IAPIPushControl>(response)
    } catch (err) {
      log.info(
        `[fetchPushControl] unable to check if branch is potentially pushable`,
        err
      )
      return {
        pattern: null,
        required_signatures: false,
        required_status_checks: [],
        required_approving_review_count: 0,
        required_linear_history: false,
        allow_actor: true,
        allow_deletions: true,
        allow_force_pushes: true,
      }
    }

export function isBranchPushable(pushControl: IAPIPushControl) {
  const {
    allow_actor,
    required_status_checks,
    required_approving_review_count,
  } = pushControl

  // See https://github.com/desktop/desktop/issues/9054#issuecomment-582768322
  // We'll guard against this being undefined until we can determine the
  // root cause and fix that.
  const requiredStatusCheckCount = Array.isArray(required_status_checks)
    ? required_status_checks.length
    : 0

  // If user is admin and branch is not admin-enforced,
  // required status checks and reviews get zeroed out in API response (no merge requirements).
  // If user is admin and branch is admin-enforced,
  // required status checks and reviews do NOT get zeroed out in API response.
  // If user is allowed to push based on `Restrict who can push` setting, they must still
  // respect the merge requirements, and can't push if checks or reviews are required for merging
  const noMergeRequirements =
    requiredStatusCheckCount === 0 && required_approving_review_count === 0

  // We check for !== false so that if a future version of the API decides to
  // remove or rename that property we'll revert to assuming that the user
  // _does_ have access rather than assuming that they _don't_.
  return allow_actor !== false && noMergeRequirements
}

  private async refreshBranchProtectionState(repository: Repository) {
    const { tip, currentRemote } = this.gitStoreCache.get(repository)

    if (tip.kind !== TipState.Valid || repository.gitHubRepository === null) {
      return
    }

    const gitHubRepo = repository.gitHubRepository
    const branchName = findRemoteBranchName(tip, currentRemote, gitHubRepo)

    if (branchName !== null) {
      const account = getAccountForEndpoint(this.accounts, gitHubRepo.endpoint)

      if (account === null) {
        return
      }

      // If the user doesn't have write access to the repository
      // it doesn't matter if the branch is protected or not and
      // we can avoid the API call. See the `showNoWriteAccess`
      // prop in the `CommitMessage` component where we specifically
      // test for this scenario and show a message specifically
      // about write access before showing a branch protection
      // warning.
      if (!hasWritePermission(gitHubRepo)) {
        this.repositoryStateCache.updateChangesState(repository, () => ({
          currentBranchProtected: false,
          currentRepoRulesInfo: new RepoRulesInfo(),
        }))
        this.emitUpdate()
        return
      }

      const name = gitHubRepo.name
      const owner = gitHubRepo.owner.login
      const api = API.fromAccount(account)

      const pushControl = await api.fetchPushControl(owner, name, branchName)
      const currentBranchProtected = !isBranchPushable(pushControl)

      let currentRepoRulesInfo = new RepoRulesInfo()
      if (useRepoRulesLogic(account, repository)) {
        const slimRulesets = await api.fetchAllRepoRulesets(owner, name)

        // ultimate goal here is to fetch all rulesets that apply to the repo
        // so they're already cached when needed later on
        if (slimRulesets?.length) {
          const rulesetIds = slimRulesets.map(r => r.id)

          const calls: Promise<IAPIRepoRuleset | null>[] = []
          for (const id of rulesetIds) {
            // check the cache and don't re-query any that are already in there
            if (!this.cachedRepoRulesets.has(id)) {
              calls.push(api.fetchRepoRuleset(owner, name, id))
            }
          }

          if (calls.length > 0) {
            const rulesets = await Promise.all(calls)
            this._updateCachedRepoRulesets(rulesets)
          }
        }

        const branchRules = await api.fetchRepoRulesForBranch(
          owner,
          name,
          branchName
        )

        if (branchRules.length > 0) {
          currentRepoRulesInfo = await parseRepoRules(
            branchRules,
            this.cachedRepoRulesets,
            repository
          )
        }
      }

      this.repositoryStateCache.updateChangesState(repository, () => ({
        currentBranchProtected,
        currentRepoRulesInfo,
      }))
      this.emitUpdate()
    }
