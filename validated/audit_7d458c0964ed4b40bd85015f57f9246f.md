### Title
Stale diff line-selection indices can cause GitHub Desktop to silently commit unintended lines when repository content shifts between diff render and commit - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop lets a user select individual lines/hunks of a file's diff for a partial commit. The selection is stored as a set of **absolute line indices** (`DiffSelection`, keyed by `hunk.unifiedDiffStart + lineIndex`) computed against the diff hunks that were on screen at selection time. When the commit is actually created, Desktop re-fetches a **fresh** diff (`getWorkingDirectoryDiff`) and reuses the old index-based selection against the new hunk layout, with no validation that the semantic lines still match.

### Finding Description
`applyPatchToIndex` fetches a brand-new diff right before staging, then formats a patch from it using the (potentially stale) selection object: [1](#0-0) [2](#0-1) 

`formatPatch` walks the new diff's hunks and asks `file.selection.isSelected(absoluteIndex)` for each line, where `absoluteIndex` is purely positional (`hunk.unifiedDiffStart + lineIndex`): [3](#0-2) 

`DiffSelection` stores only a `Set<number>` of diverging line positions, with no reference to the actual line content/hash of the diff it was created against: [4](#0-3) 

Desktop's own code acknowledges this exact problem but only partially addresses it (it recomputes which line positions are still "selectable" after a diff refresh, it does **not** verify that a given index still corresponds to the same source line): [5](#0-4) 

That reconciliation only runs for the background "diff refresh" path that updates UI state; it is not run again inside `applyPatchToIndex`, which independently re-fetches the diff at commit time and blindly reuses `file.selection`. If the tracked file's content changes between the moment the user picks lines to include and the moment `createCommit` → `stageFiles` → `applyPatchToIndex` runs (e.g. because a `.gitattributes` clean/smudge filter, a `post-checkout`/other git hook, an LFS smudge process, or any external tool triggered by opening/interacting with a cloned repository rewrites the file), the hunk boundaries and line offsets can shift. The old positional selection set will then apply to different lines than the ones the user actually reviewed and checked, so `git apply --cached` stages a patch that does **not** match what the user saw and approved.

### Impact Explanation
This is a silent corruption of what the user commits: lines the user deliberately excluded can be silently included in the commit (and later pushed), or lines the user wanted included can be silently dropped, with no error or warning. Because commit creation does not fail (`git apply --cached` succeeds against a still-valid patch, just for the wrong lines), the user has no signal that the outcome differs from their intent. An attacker who controls a cloned/fetched repository (via `.gitattributes` filters, hooks, or LFS content) is in a natural position to trigger file rewrites between diff render and commit without any unnatural user action.

### Likelihood Explanation
The window between diff generation/selection and actual commit is not vanishingly small in an interactive Electron app — selection can persist across several UI updates before the user clicks "Commit". Any legitimate git mechanism that mutates working-tree file content outside of Desktop's own staging path (filters, hooks, LFS smudge, external formatters run by editor integrations) is sufficient to shift line offsets. Desktop's code comments in `app-store.ts` show the developers were already aware that diffs "might have changed dramatically" between refreshes, but the guard they added only prunes now-invalid indices from the *displayed* selection state — it does not stop `applyPatchToIndex` from re-deriving a fresh diff and reapplying the old index set at commit time.

### Recommendation
Before staging a partial selection, `applyPatchToIndex` (and `getFilesDiffText`/`formatPatch` callers generally) should verify that the diff used to build the selection is still current — e.g., by comparing a content hash/mtime of the file (or the diff text itself) captured when the selection was made against the file state at commit time, and refuse/re-prompt the user if they differ, rather than silently reusing positional indices against a newly fetched diff.

### Proof of Concept
1. Clone a malicious repository that defines a `.gitattributes` clean/smudge filter (or a `post-checkout`/other hook) which rewrites lines of a tracked file shortly after checkout/interaction (e.g., inserting/removing a line near the top of the file).
2. In Desktop, open the file's diff and select only specific lines/hunks to include in the commit (leave others unstaged).
3. Before clicking "Commit", let the filter/hook fire and shift the file's line offsets (this can happen automatically, e.g. via a background `git status`/`diff` triggered smudge, or via any process that touches the file).
4. Click "Commit". `applyPatchToIndex` re-fetches the diff (now with shifted hunks) and applies the old positional `DiffSelection` against it.
5. Inspect the resulting commit: it contains different lines than what was visually selected by the user — proving silent corruption of the committed content.

Note: I could not directly trace the full commit dispatch path (`_commitIncludedChanges` in `app-store.ts`) within the available context/tooling to confirm whether any additional freshness check exists between UI selection and `applyPatchToIndex` invocation; based on the code paths found (`apply.ts`, `patch-formatter.ts`, `diff-selection.ts`, and the explicit comment in `app-store.ts`), no such check appears to exist, but this should be verified against the full commit dispatcher code before treating this as fully confirmed.
