### Title
Out-of-range participant index in PedPoP blame verification panics on `self.enc_keys[&decryptor]` — (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`BlameMachine::blame` / `AdditionalBlameMachine` accept a `sender`/`recipient` pair of `Participant` indexes plus an attacker-supplied `EncryptedMessage` and `EncryptionKeyProof`. Inside `Decryption::decrypt_with_proof`, once the per-message proof-of-possession signature verifies, the code indexes `self.enc_keys[&decryptor]` directly (crypto/dkg/pedpop/src/encryption.rs:388). A `decryptor` index with no registered encryption key (e.g. an index `> n`, or any participant whose `EncryptionKeyMessage` was never registered) causes a `HashMap` index panic — a remote crash (denial of service) from crafted input bytes, the same bug class as CVE-2017-9928's `get_fileinfo` overflow.

### Finding Description
PedPoP is explicitly designed to tolerate faulty/malicious DKG participants — the entire `BlameMachine`/`AdditionalBlameMachine` API exists so honest parties can adjudicate accusations without aborting unsafely. Despite that, `decrypt_with_proof` performs an unchecked map lookup on a participant-controlled index:

```rust
// crypto/dkg/pedpop/src/encryption.rs
proof.dleq.verify(
  &mut encryption_key_transcript(self.context),
  &[C::generator(), msg.key],
  &[self.enc_keys[&decryptor], *proof.key],   // <-- panics if decryptor not registered
)
```

The `EncryptedMessage` is fully attacker-controlled: the sender reads arbitrary bytes via `EncryptedMessage::read` (crypto/dkg/pedpop/src/encryption.rs:171-177) and can produce a valid `pop` Schnorr signature over `pop_challenge(context, R, key, from, msg)` for any `from` index, since it only requires knowledge of the ephemeral key the sender itself chose (`encrypt`, encryption.rs:135-168). After the PoP check passes (encryption.rs:374-379), evaluating `self.enc_keys[&decryptor]` panics when `decryptor` was never registered in `Decryption::register` (encryption.rs:351-362), which only inserts keys for participants actually present in the commitments map.

In the consuming processor, `CoordinatorMessage::VerifyBlame` forwards the on-chain `accuser`/`accused` fields straight into `AdditionalBlameMachine::new(...).blame(accuser, accused, substrate_share, substrate_blame)` (processor/src/key_gen.rs:504-549), so both indexes originate from a serialized message (`Participant::new(u16)` only rejects zero, coordinator/src/tributary/transaction.rs:346-354).

### Impact Explanation
Any party able to submit a blame/accusation message (a DKG participant submitting an `InvalidDkgShare`/`VerifyBlame` flow, naming an `accused` index outside the registered set, e.g. `Participant(n+1)` or a participant whose commitments weren't registered) can crash the node evaluating the blame. This is a remotely triggerable panic — availability loss — directly analogous to the crafted-file stack overflow DoS in lrzip. It also subverts the protocol's own fault-handling machinery: the blame path meant to safely identify faulty participants instead kills the honest node adjudicating it. Severity: Medium (availability only, unauthenticated-index trigger but requires a valid PoP-bearing `EncryptedMessage`, which any participant can trivially construct).

### Likelihood Explanation
- Reachable from public/untrusted inputs: `blame` takes `msg: EncryptedMessage` (deserializable via `EncryptedMessage::read`) and `proof: Option<EncryptionKeyProof>` (`EncryptionKeyProof::read`), plus two raw participant indexes.
- The PoP signature check is not a barrier: the accuser signs with an ephemeral key they control; `pop_challenge` binds only `context`, `from`, `R`, `key`, and ciphertext — all attacker-chosen.
- Triggering requires only that `decryptor` be absent from `enc_keys` — an index `> n` or a participant omitted from `commitment_msgs` suffices.
- Caveat: I could not fully verify whether the processor validates `accused` against `params.n()` before constructing the `AdditionalBlameMachine`; the coordinator's `InvalidDkgShare` parser only rejects `Participant(0)`, so index `n+1` reaching `blame` appears plausible but depends on the caller. If upstream code filters `accused` to `1..=n` and `enc_keys` is always populated for all `1..=n`, reachability is reduced — the panic remains latent for any caller that doesn't perform that filtering (the library itself performs no check).

### Recommendation
Replace the indexing operations with checked lookups and return a deterministic blame result instead of panicking:

- In `Decryption::decrypt_with_proof` (crypto/dkg/pedpop/src/encryption.rs:388), use `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?` (or a dedicated `UnknownParticipant` error).
- Similarly audit `self.commitments[&sender]` in `BlameMachine::blame_internal` (crypto/dkg/pedpop/src/lib.rs:599) and `self.commitments[&l]` in `calculate_share` (lib.rs:490) — both index participant-keyed maps on values derived from attacker input.
- Reject `sender`/`recipient` indexes `> params.n()` at the `blame` entry points, and have the processor validate `accuser`/`accused` against `params` before invoking the blame machine.

### Proof of Concept
1. Set up a PedPoP `KeyMachine`/`BlameMachine` with `n = 3` (`AdditionalBlameMachine::new(context, 3, commitment_msgs)` registers `enc_keys` for participants 1-3 only).
2. As the accuser, construct `EncryptedMessage { key: g*k, pop: SchnorrSignature::sign(k, r, pop_challenge(ctx, R, key, from=accuser, ciphertext)), msg: <32 bytes> }` — the PoP verifies.
3. Call `blame(accuser, Participant::new(4).unwrap(), msg, Some(encryption_key_proof))`.
4. `decrypt_with_proof` passes the PoP check, evaluates `self.enc_keys[&Participant(4)]` at encryption.rs:388, and panics with `HashMap` index-out-of-bounds — crashing the process. The same crash occurs via `ProcessorMessage::VerifyBlame` with an `accused` index of 4.

Uncertain aspects: whether upstream processor/coordinator layers clamp `accused` to `<= n` before this call (the transaction parser only rejects 0); if they do, the vulnerability is a latent panic in a public library API rather than a directly exploitable remote crash.
