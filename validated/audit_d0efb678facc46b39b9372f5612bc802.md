### Title
`addRemote()`/`setRemoteURL()` accept attacker-controlled clone URLs from PR fork metadata without the argument-injection guard applied to `clone()` - ([File: app/src/lib/git/remote.ts])

### Summary
`git remote add` and `git remote set-url` are invoked with the URL as the final positional argument and no `--` end-of-options marker, unlike `clone()` in the same codebase, which explicitly protects against this class of issue. The URL used in the PR-checkout flow (`headCloneUrl` / `pullRequest.head.repo.clone_url`) originates from GitHub API data supplied by the author of a fork/PR, i.e. an untrusted third party, and flows unsanitized into `addRemote()`.

### Finding Description
`clone()` in `app/src/lib/git/clone.ts` was hardened with an explicit sensitive-path check and an option-terminator: [1](#0-0) 
By contrast, the sibling remote-mutation helpers in the same module family do not apply the same `--` protection before the attacker-influenced URL: [2](#0-1) [3](#0-2) 

This is the same broken-invariant shape as the Fenix report: a guard exists on one state-changing entry point (`vote()`/`clone()`) but is missing on a semantically equivalent sibling entry point (`reset()`/`addRemote()`+`setRemoteURL()`) that mutates the same underlying critical state (vote weight / stored remote URL that later git invocations trust).

The attacker-controlled value reaches `addRemote()` here, driven entirely by data returned from the GitHub API for a pull request's head repository, which is under the PR author's control (they can rename/fork/re-point their repository, and Desktop trusts `clone_url` as reported by the API): [4](#0-3) 

`envForRemoteOperation()`/`envForProxy()` only special-case `http(s)` for proxy resolution and otherwise pass the URL through untouched; there is no `GIT_ALLOW_PROTOCOL` allow-list enforced anywhere in this code path to restrict which git transports may be used: [5](#0-4) 

Because Git supports remote-helper transports selected purely by URL scheme (e.g. `ext::`, `fd::`, and other helper schemes), a crafted `clone_url` value stored as a remote via `addRemote()` is persisted into the repository's git config, and any code path that later exercises that remote (fetch, `git ls-remote`, push, submodule init, credential resolution) will invoke the corresponding transport for that URL scheme.

### Impact Explanation
If the URL is accepted into git config unvalidated and no `protocol.*.allow`/`GIT_ALLOW_PROTOCOL` restriction is enforced elsewhere in the process environment used for these git invocations, this can lead to command execution when the crafted remote is later fetched from — the same "no code changed, but the checked-out/committed data or executed commands are attacker-controlled" outcome class described in the report, except the corrupted value here is the *stored remote URL* rather than a vote tally. Even absent full RCE, at minimum this allows argument-confusion errors and unexpected git behavior driven entirely by PR metadata the victim never manually reviewed, matching the "silent corruption of what the user commits or pushes / attacker controls a GitHub API object" impact category.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the victim to click "Checkout" on a PR from a malicious fork inside Desktop (an ordinary, expected user action, not "unnatural steps"), and the attacker fully controls `head.repo.clone_url` by simply creating/renaming a fork. Whether this is exploitable as full RCE depends on the effective `protocol.*.allow`/`GIT_ALLOW_PROTOCOL` configuration and Desktop's bundled Git defaults, which I was not able to fully verify from the indexed code — Desktop may rely on git's own default-disabled transports for `ext`/`fd` unless the local system config re-enables them. This uncertainty should be resolved before treating this as confirmed RCE; regardless, the structural inconsistency (guard present in `clone()`, absent in `addRemote()`/`setRemoteURL()`) is a real, verifiable gap.

### Recommendation
- Apply the same defensive pattern used in `clone()` to `addRemote()` and `setRemoteURL()` in `app/src/lib/git/remote.ts`: insert a `--` before the URL argument, e.g. `git(['remote', 'add', name, '--', url], ...)` (verify dugite/git version support for this exact placement) and reject or explicitly allow-list acceptable URL schemes (`https:`, `ssh:`, `git:`) before ever calling `addRemote`/`setRemoteURL` with API-derived (`headCloneUrl`) values.
- Explicitly set `GIT_ALLOW_PROTOCOL` (or `protocol.*.allow=never` for `ext`, `fd`, `file` as appropriate) in `envForRemoteOperation()` for all remote-touching invocations so that even if a malicious URL is stored, subsequent git commands refuse unexpected transports.
- Validate `pullRequest.head.repo.clone_url` against the expected `https://`/`git://`/`ssh://` GitHub host pattern in `_findPullRequestBranch` before calling `addRemote`.

### Proof of Concept
1. Attacker forks a public repository and, via the GitHub API/UI, ensures their fork's reported `clone_url` metadata is a crafted value such as `ext::sh -c "touch /tmp/pwned"` (exact feasibility depends on whether GitHub's API allows/preserves such a value for `clone_url`; if not directly settable via UI, an equivalent effect could be achieved by a malicious GitHub Enterprise/API-compatible endpoint returning attacker-controlled `clone_url` fields to Desktop).
2. Attacker opens a PR from this fork against a repository the victim has open in Desktop.
3. Victim clicks "Checkout" on the PR review UI in Desktop, triggering `dispatcher.ts` → `_checkoutPullRequest` → `_findPullRequestBranch`: [6](#0-5) 
4. `addRemote(repository, forkRemoteName, headCloneUrl)` runs `git remote add <name> <maliciousUrl>` with no `--` separator and no scheme allow-list, storing the crafted URL in the repo's `.git/config`.
5. The subsequent fetch of that remote (`this._fetchRemote(repository, remote, ...)`) invokes git against the crafted URL/transport, whose actual code-execution impact depends on the git transport allow-list in effect on the victim's machine (unverified from the indexed source — recommend a Devin session with full repo/checkout access to test the bundled `dugite` Git binary's default `protocol.*.allow` settings to confirm exploitability end-to-end).
