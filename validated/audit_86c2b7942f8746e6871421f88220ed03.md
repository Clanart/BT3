Based on my investigation, I found a concrete analog of this bug class in `MasterMagpie.sol`'s emission accounting.

### Title
Direct token transfer to MasterMagpie inflates LP supply used for reward accounting and permanently locks the sender's tokens - (File: rewards/MasterMagpie.sol)

### Summary
`MasterMagpie` computes the accumulated MGP-per-share rate for a pool using an internal helper `_calLpSupply()`, which for regular staking tokens (i.e., anything other than `vlmgp`/`mWomSV`) is simply the raw ERC20 balance of the staking token held by the `MasterMagpie` contract, not a value tracked purely through the `deposit`/`depositFor` accounting path: [1](#0-0) 

### Finding Description
`MasterMagpie` tracks each user's staked amount in `UserInfo.amount`, updated only through `_deposit`/`_withdraw`, which pull tokens via `safeTransferFrom` [2](#0-1) . However, the pool-wide reward-rate calculation relies on `_calLpSupply(_stakingToken)`, which for ordinary staking (LP/receipt) tokens returns `IERC20(_stakingToken).balanceOf(address(this))` — i.e., the contract's raw token balance — rather than a sum of tracked `user.amount` values [1](#0-0) .

This mirrors the reported bug class: an ordinary, unprivileged wallet can call `transfer()` on the staking/receipt token directly to the `MasterMagpie` contract address, bypassing the `deposit`/`depositFor` entry points entirely. This directly inflates the balance-based `lpSupply` figure used when the pool's `accMGPPerShare` is advanced (analogous to `MasterWombatMockRewardPersec`'s `updatePool`, which computes `accRewardPerShare += (tokenReward * PRECISION) / lpSupply` from the same raw-balance pattern) [3](#0-2) . Because `user.amount` is never incremented for tokens sent this way, the sender's tokens are not attributed to any account and cannot be withdrawn through `_withdraw`, which requires `user.amount >= _amount` [4](#0-3) . No rescue/sweep function for stuck ERC20 tokens exists in `MasterMagpie.sol` (only `WomUp.sol` contains such a pattern, unrelated to this contract) — so recovery requires a contract upgrade, exactly matching the reported impact.

### Impact Explanation
Two concrete harms result: (1) the transferred tokens become permanently locked in `MasterMagpie` with no accounting path to recover them without a protocol upgrade (permanent freeze of user funds), and (2) since the same inflated raw balance is used as the divisor for the pool's per-second MGP emission, the `accMGPPerShare` growth rate is diluted for every legitimate staker in that pool for as long as the extra balance remains — a theft/freezing effect on other users' unclaimed yield.

### Likelihood Explanation
This requires no privileged role and no special conditions — any wallet holding the relevant staking/receipt token (e.g., a WombatStaking receipt token or LP token registered as a `MasterMagpie` pool) can trigger it with a single standard ERC20 `transfer()` call to the `MasterMagpie` contract address, whether by accident or intentionally to dilute rewards for other stakers.

### Recommendation
Do not derive pool-wide LP supply for reward accounting from `IERC20(stakingToken).balanceOf(address(this))`. Instead, maintain and use an explicit `pool.totalStaked` counter incremented/decremented only inside `_deposit`/`_withdraw`, matching the accounting used for `vlmgp`/`mWomSV` (which correctly rely on `totalSupply()` of the locker token rather than a transferable balance). Additionally, consider adding a guarded rescue function that allows recovering accidentally-transferred tokens that are not the pool's tracked staking token, or reconciling excess balance against no specific user (e.g., sweeping it to a treasury) rather than allowing it to distort reward math indefinitely.

### Proof of Concept
1. Assume pool `P` for staking token `T` is registered in `MasterMagpie` with non-zero `allocPoint`.
2. Alice (ordinary user) calls `T.transfer(masterMagpieAddress, X)` directly, without calling `deposit`/`depositFor`.
3. `MasterMagpie`'s `UserInfo[T][alice].amount` remains unchanged (still `0` or whatever it was); the tokens are now part of `IERC20(T).balanceOf(masterMagpie)`.
4. On the next `updatePool(T)` call (triggered by any other user's deposit/withdraw/harvest), `_calLpSupply(T)` returns the inflated balance including Alice's `X` tokens, decreasing the computed `accMGPPerShare` increment for all stakers in pool `T` relative to what it should be.
5. Alice's `X` tokens can never be withdrawn via `_withdraw`, since `require(user.amount >= _amount)` fails for her — the funds are stuck permanently absent a contract upgrade.
