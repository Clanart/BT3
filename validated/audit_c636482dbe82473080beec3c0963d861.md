### Title
Panic on point-at-infinity nonce sum in BIP-340 HRAm allows a malicious signing participant to crash `sign_share`/`verify` - ([File: networks/bitcoin/src/crypto.rs](networks/bitcoin/src/crypto.rs))

### Summary
The muhammara/hummus bug class is an unchecked failure return that is later dereferenced, crashing the process when fed crafted input. The Serai analog lives in `networks/bitcoin/src/crypto.rs`: `x()` calls `key.to_encoded_point(true).x().expect("point at infinity")`, which panics when passed the point at infinity. `x()` is invoked from `Hram::hram` on the aggregate nonce `R` and the group key `A`. A single malicious FROST participant can force `R` to the point at infinity by choosing their nonce commitments as the negation of the aggregate of all other participants' contributions, causing a panic (DoS) inside `IetfSchnorr::sign_share`/`Schnorr::verify` — a code path documented as "expected not to panic" elsewhere in the crate.

### Finding Description [1](#0-0)  `x()` extracts the x-coordinate of a `ProjectivePoint` and `expect`s it to exist. For the identity point, `to_encoded_point(true).x()` returns `None`, so `x()` panics. The same applies to `x_only()`.

`Hram::hram` feeds `R` (the aggregate nonce point) and `A` (the group key) into `x()` unconditionally: [2](#0-1) 

`R` is computed by the FROST `Algorithm`/`SignMachine` as `Σᵢ (Dᵢ + ρᵢ·Eᵢ)` over the nonce commitments supplied by all included participants, which are read via `TransactionSignMachine`'s `read_preprocess` / `sign` path: [3](#0-2) 

`Curve::read_G` only rejects an *individual* identity encoding; it does not prevent a linear combination of validly-encoded commitments from summing to identity: [4](#0-3) 

Because all preprocesses are exchanged before `sign`, the last-moving participant knows every other commitment and every ρᵢ, and can select their `(D, E)` pair so the total `R = identity` (e.g., choose `E` arbitrarily, solve `D = −(Σⱼ≠ᵢ(Dⱼ + ρⱼEⱼ)) − ρᵢEᵢ`). When `sign_share` or `Schnorr::verify` evaluates `hram(&R, &A, msg)`, `x(R)` hits `expect("point at infinity")` and panics — the Rust analogue of an unchecked NULL return being dereferenced.

The panic also reaches `Schnorr::verify` directly, which calls `needs_negation(&sig.R)` → `to_encoded_point` → `x()` on the same attacker-influenced `R`: [5](#0-4) 

### Impact Explanation
A single malicious (or compromised) member of a signing set can deterministically panic every honest participant's `TransactionSignMachine::sign`/`complete` path for the Bitcoin wallet, halting withdrawal signing. This is a denial of service matching the CVE's impact (CWE-690, availability), reachable purely by feeding crafted preprocess bytes to `read_preprocess`/`sign`. In processes using the relayer-style panic hook (`std::process::exit(1)` on task panic), one crafted nonce commitment kills the node.

### Likelihood Explanation
Requires only that the attacker be one participant in a signing session (not a threshold collusion) and submit their preprocess last — trivially achievable since preprocess ordering/aggregation is performed by the coordinator. Deterministic, no probabilistic conditions. Severity: Medium (session/node DoS only; no signature forgery or key leakage results, since the panic occurs before any share is emitted).

### Recommendation
Make `x()`/`x_only()` return `Option`/`io::Result` and propagate, or check `R.is_identity()` in `Hram::hram` (and in `Schnorr::verify` before `needs_negation`) and return a failure/`FrostError` blaming the offending participant. Alternatively, have the FROST `Algorithm` reject an aggregate `R` that is the point at infinity before invoking the HRAm, analogous to how `Curve::read_G` already rejects identity encodings.

### Proof of Concept
1. Set up an n-of-n (or t-of-n) `TransactionMachine` signing session for a `SignableTransaction`.
2. All honest participants broadcast valid `Preprocess` commitments `(Dᵢ, Eᵢ)`.
3. Attacker computes ρᵢ for all i per `Curve::hash_binding_factor`, picks arbitrary `Eₐ`, sets `Dₐ = −Σⱼ≠ₐ(Dⱼ + ρⱼEⱼ) − ρₐEₐ`, and broadcasts `(Dₐ, Eₐ)` — both individually non-identity, so they pass `Curve::read_G`.
4. `TransactionSignMachine::sign` aggregates `R = identity`, calls `IetfSchnorr::sign_share` → `Hram::hram(&R, &A, sighash)` → `x(&R)` → `expect("point at infinity")` panics on every honest signer.
5. Same panic occurs in `Schnorr::verify` at `networks/bitcoin/src/crypto.rs:146` via `needs_negation(&sig.R)`.

Caveat: I could not fully trace `IetfSchnorr::sign_share` in `crypto/frost/src/sign.rs` to confirm `hram` is invoked before the share is produced and that no prior identity check exists; the panic site in `crypto.rs` and the unconstrained commitment-sum path are confirmed.
