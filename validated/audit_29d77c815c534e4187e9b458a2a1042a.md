### Title
Deserialized `ThresholdKeys` can contain an identity group key, enabling universally forged Schnorr signatures - (File: crypto/dkg/src/lib.rs)

### Summary

`ThresholdKeys::read` accepts serialized verification shares without rejecting the group identity. For a `t=1, n=1` key set, an attacker can encode the identity as participant 1's verification share, causing the resulting `group_key()` to also be the identity. Under the generic Schnorr verifier, any signature `(R = sG, s)` verifies for an identity public key because the public-key term disappears from the verification equation. This allows an attacker who can supply untrusted serialized `ThresholdKeys` bytes to cause signature acceptance without knowing any private key.

### Finding Description

`ThresholdKeys::read` reads `n` verification shares using only `C::read_G`, which enforces canonical point encoding but does not reject the identity element. It then passes those shares to `ThresholdKeys::new`. [1](#0-0) 

`ThresholdKeys::new` computes the group key as the interpolated sum of the first `t` verification shares. With `t = 1`, the group key is exactly `verification_shares[Participant(1)]`, so encoding that share as identity produces an identity group key. [2](#0-1) 

The Schnorr verification equation is `R + cA - sG == 0`. When `A` is the identity, `cA` is identity for every challenge, so `(R = sG, s)` verifies for any message or challenge. [3](#0-2) 

### Impact Explanation

An attacker can create serialized `ThresholdKeys` that deserialize successfully and report an identity group key, then present universally valid-looking Schnorr signatures for that key. Any protocol path that treats attacker-controlled serialized threshold keys or identity public keys as valid public inputs can accept signatures not produced by the claimed threshold group.

This is analogous to the missing-principal-token bug class: a zero-like sentinel is accepted as a valid object and later causes an unconditional verification success.

### Likelihood Explanation

The attack requires a reachable path where untrusted bytes are passed to `ThresholdKeys::read` or where an identity group key is otherwise accepted as a signer. Deserialization itself does not perform this rejection, and no private-key knowledge or threshold collaboration is needed.

### Recommendation

Reject identity group elements when deserializing or constructing `ThresholdKeys`, or at minimum reject an identity `group_key` in `ThresholdKeys::new`/`ThresholdKeys::read`. Additionally, consider rejecting identity public keys in `SchnorrSignature::verify` as defense in depth.

### Proof of Concept

```rust
use zeroize::Zeroizing;
use frost::{
  Participant,
  curve::{Ciphersuite, Curve, Secp256k1},
};
use frost::dkg::{Interpolation, ThresholdKeys, ThresholdParams};
use schnorr::SchnorrSignature;

let p1 = Participant::new(1).unwrap();

// A 1-of-1 ThresholdKeys object whose only verification share is identity.
let keys = ThresholdKeys::<Secp256k1>::new(
  ThresholdParams::new(1, 1, p1).unwrap(),
  Interpolation::Lagrange,
  Zeroizing::new(<Secp256k1 as Ciphersuite>::F::ZERO),
  [(p1, <Secp256k1 as Ciphersuite>::G::identity())].into_iter().collect(),
)
.unwrap();

assert!(bool::from(keys.group_key().is_identity()));

// For A = identity, choose R = sG. Then:
// R + cA - sG = sG + c*identity - sG = identity.
let s = <Secp256k1 as Ciphersuite>::F::ONE;
let forged = SchnorrSignature::<Secp256k1> {
  R: <Secp256k1 as Ciphersuite>::generator() * s,
  s,
};

let arbitrary_challenge = <Secp256k1 as Ciphersuite>::F::ONE;
assert!(forged.verify(keys.group_key(), arbitrary_challenge));
```

The same result is reachable through serialization by encoding `t = 1`, `n = 1`, `i = 1`, Lagrange interpolation, any valid secret-share scalar, and the canonical encoding of the identity point as participant 1's verification share before calling `ThresholdKeys::read`.
