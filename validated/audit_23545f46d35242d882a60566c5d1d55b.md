### Title
Unvalidated Condition Opcode Byte in `parse_sexp_to_condition` Causes Uncaught `ValueError` During Wallet Puzzle/Solution Parsing - (File: `chia/consensus/condition_tools.py`)

### Summary
`parse_sexp_to_condition` validates that a condition's opcode atom is exactly one byte long, but never validates that the byte value is actually a member of `ConditionOpcode` before constructing the enum, mirroring the Wireshark HiQnet bug class of missing data-type validation on attacker-controlled input.

### Finding Description
`parse_sexp_to_condition` extracts the first element of a parsed CLVM condition as the opcode atom and only checks that it is a single byte: [1](#0-0) 

It then unconditionally constructs `ConditionOpcode(op)`: [2](#0-1) 

If `op` is a single byte that is not one of the defined `ConditionOpcode` enum values, this raises a raw `ValueError` from the enum constructor instead of the expected, caller-handled `ConsensusError`. This function is invoked (via `parse_sexp_to_conditions`) from `conditions_for_solution`: [3](#0-2) 

`conditions_for_solution` only catches `Program.EvalError` and converts it to `ConsensusError`; it does not catch `ValueError`, so the unvalidated-opcode `ValueError` propagates uncaught to callers. `conditions_for_solution`/`conditions_dict_for_solution` are called from wallet-side puzzle-driver code that processes puzzle reveals and solutions supplied by counterparties or observed on-chain, including CAT utilities (`chia/wallet/cat_wallet/cat_utils.py`), clawback drivers (`chia/wallet/puzzles/clawback/drivers.py`), and `chia/wallet/wallet_signer.py`.

### Impact Explanation
A wallet processing a coin spend, offer, or clawback puzzle/solution that contains a condition opcode byte outside the known `ConditionOpcode` range hits an unhandled `ValueError` deep in condition parsing rather than a controlled `ConsensusError`. Depending on the call site, this can abort wallet-side spend-bundle construction, CAT/clawback driver processing, or signing flows, i.e., a spend/puzzle-triggered halt of transaction processing for the affected wallet — the same "crafted input causes unhandled type-validation failure and processing crash" bug class as the CVE, adapted to Chia's wallet-side condition parsing.

### Likelihood Explanation
Reaching this path only requires supplying a crafted puzzle reveal/solution (e.g., in an offer, clawback coin, or CAT-related spend) containing a single-byte atom that is not a valid `ConditionOpcode` value in the position `parse_sexp_to_condition` treats as the opcode. This is fully attacker-controlled content (any spend bundle or puzzle a wallet is asked to interpret), making it straightforward to trigger from an unprivileged wallet counterparty or offer participant.

### Recommendation
In `parse_sexp_to_condition`, explicitly validate that `op` is a recognized `ConditionOpcode` value before constructing the enum (e.g., `if op not in ConditionOpcode._value2member_map_: raise ConsensusError(Err.INVALID_CONDITION, ["unknown opcode"])`), and/or have `conditions_for_solution` also catch `ValueError` and re-raise as `ConsensusError` so callers get a consistent, handled error instead of an unhandled exception.

### Proof of Concept
1. Construct a CLVM solution/puzzle whose output condition list contains a condition of the form `(0xFF arg1 arg2)`, where `0xFF` (or any single byte not defined in `ConditionOpcode`) is the opcode atom.
2. Have a wallet process this puzzle reveal/solution through a path that calls `conditions_for_solution`/`conditions_dict_for_solution` (e.g., CAT solution parsing, clawback driver parsing, or `wallet_signer.py` condition inspection during signing of an incoming offer/spend).
3. Observe that `parse_sexp_to_condition` raises an unhandled `ValueError` from `ConditionOpcode(op)` (line 45) instead of the expected `ConsensusError`, propagating out of `conditions_for_solution` since only `Program.EvalError` is caught there (lines 176–180), halting the wallet's processing of that spend.
