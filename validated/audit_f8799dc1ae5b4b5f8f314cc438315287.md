## Finding

### Title
Bank precompile's `sendNative` bypasses `BlockedAddr`/`IsSendEnabledCoins` checks enforced on the equivalent `send` path - (File: precompiles/bank/bank.go)

### Summary
The Deno advisory describes a permission gate (`--allow-net`) that is correctly enforced for one API surface (`fetch()`) but silently skipped for an equivalent surface (`node:http`/`node:https`) that reaches the same underlying network primitive. The sei-chain bank precompile has the same class of bug: two EVM-reachable methods both move native `usei`/wei balances between accounts, but only one of them is routed through the guarded Cosmos message-server path.

### Finding Description
`precompiles/bank/bank.go`'s `send` method (the ERC20-pointer-gated native-token transfer) builds a `banktypes.MsgSend` and dispatches it through `p.bankMsgServer.Send(...)`, which is the guarded Cosmos bank message handler: [1](#0-0) 

That message-server handler (`sei-cosmos/x/bank/keeper/msg_server.go`) is where the `BlockedAddr` and `IsInDenomAllowList` permission checks actually live: [2](#0-1) 

In contrast, the precompile's `sendNative` method — reachable by any EVM caller sending `value` to the bank precompile address `0x...1001` — calls the low-level keeper primitive `p.bankKeeper.SendCoinsAndWei(...)` directly, never touching `bankMsgServer`: [3](#0-2) 

`BaseSendKeeper.SendCoins`/`SendCoinsWithoutAccCreation` (the sibling of `SendCoinsAndWei`) contains no `BlockedAddr` or `IsSendEnabledCoins` check itself — those checks are performed only by the higher-level `msgServer.Send`/`MultiSend` and by helpers like `SendCoinsFromModuleToAccount`, which explicitly re-check `BlockedAddr` before calling `SendCoins`: [4](#0-3) [5](#0-4) 

`BlockedAddr` guards addresses (typically module accounts such as fee collector, distribution, gov, etc.) that must never receive a direct, out-of-band transfer because other invariants/accounting rely on funds only arriving there through specific, tracked code paths. Because `sendNative` skips this check entirely, an EVM caller can send `usei`/wei straight into any blocked module account.

### Impact Explanation
This lets any unprivileged EVM transaction sender transfer native `usei` to addresses the chain explicitly disallows as transfer targets (module accounts registered as blocked), which the "send" path (and the native Cosmos `MsgSend`/`MsgMultiSend`) correctly reject. Depending on which module accounts are in the blocked-address set, this can corrupt module-account accounting invariants that assume balances only change through specific instructions (mint/burn/fee-collection paths), which the fee/refund and module-accounting logic depends on for correctness. This matches the rules' "fee or refund abuse" / "unauthorized transfer via precompile" bug classes.

### Likelihood Explanation
Trivially reachable: any address can call the bank precompile's `sendNative` payable method with `msg.value` and a target address string, no association or special permission required — precisely the same low bar as invoking `send`. The only difference is which internal Go function is invoked, which is not something a caller controls or can be warned about; it is a code-path asymmetry, not a user error.

### Recommendation
Route `sendNative` through the same guarded path as `send` (i.e., check `BlockedAddr(receiverSeiAddr)` — and ideally `IsSendEnabledCoins`/`IsInDenomAllowList` for parity — before calling `bankKeeper.SendCoinsAndWei`), or move the guard checks into `SendCoinsAndWei`/`SendCoins` itself so all callers get the same protection regardless of entry point.

### Proof of Concept
1. Identify a blocked module account address (e.g., one returned as blocked by `BankKeeper.BlockedAddr`).
2. From any funded EVM account, call the bank precompile (`0x0000000000000000000000000000000000001001`) method `sendNative(receiverSeiAddrString)` with `msg.value` set to the desired wei amount, where `receiverSeiAddrString` is the bech32 address of the blocked module account.
3. Observe the transfer succeeds via `sendNative`, while attempting the equivalent transfer with the ERC20 `send` method or a native `MsgSend` to the same address fails with `"... is not allowed to receive funds"`.

Note: I could not fully verify at what specific module accounts are registered as "blocked" in this deployment (that set is configured in `app.go`/`BankKeeper` initialization, which I did not inspect), so the concrete severity of "which accounts get funds landing where they shouldn't" is asserted based on the standard Cosmos SDK `BlockedAddr` mechanism rather than a fully traced genesis/app-wiring confirmation.

```go
func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}
```

```go
func (k BaseSendKeeper) SendCoins(ctx sdk.Context, fromAddr sdk.AccAddress, toAddr sdk.AccAddress, amt sdk.Coins) error {

	//
	// NOTE: This should ultimately be removed in favor a more flexible approach

	if !accExists {
		defer func() {
			recordNewAccounts(ctx.Context(), 1)
		}()
		k.ak.SetAccount(ctx, k.ak.NewAccountWithAddress(ctx, toAddr))
	}

	return nil
}
```

```go
// SendCoinsFromModuleToAccount transfers coins from a ModuleAccount to an AccAddress.
// It will panic if the module account does not exist. An error is returned if
// the recipient address is black-listed or if sending the tokens fails.
func (k BaseKeeper) SendCoinsFromModuleToAccount(
	ctx sdk.Context, senderModule string, recipientAddr sdk.AccAddress, amt sdk.Coins,
) error {

	senderAddr := k.ak.GetModuleAddress(senderModule)
	if senderAddr == nil {
		panic(sdkerrors.Wrapf(sdkerrors.ErrUnknownAddress, "module account %s does not exist", senderModule))
	}

	if k.BlockedAddr(recipientAddr) {
		return sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", recipientAddr)
	}
	return k.SendCoins(ctx, senderAddr, recipientAddr, amt)
}
```
