### Title
Clone Path Traversal Protection Is Disabled via Hardcoded `GIT_CLONE_PROTECTION_ACTIVE: 'false'` - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` in `app/src/lib/git/clone.ts` hardcodes the environment variable `GIT_CLONE_PROTECTION_ACTIVE: 'false'` for every clone operation, unconditionally disabling a security control that upstream Git added specifically to protect against malicious repositories during clone. [1](#0-0) 

### Finding Description
The bug class in the source report is "a value that should encode/enforce something meaningful is hardcoded to a value that discards the protection/benefit it was designed to provide" (referral hardcoded to `address(0)` instead of a real referrer, silently discarding the economic benefit). The closest real analog in this codebase is not economic but security-relevant: a git security *protection flag* is hardcoded to the value that disables the protection, instead of being left at its secure default or set dynamically based on trust in the remote.

```ts
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
``` [1](#0-0) 

`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git itself introduced as part of the CVE-2024-32004 mitigation, which hardens `git clone --recursive` against attacker-controlled repository content (e.g., malicious hooks/config reachable through crafted submodules or repo layout) that could otherwise be leveraged to run arbitrary commands on the machine performing the clone. Desktop calls `clone` with `'--recursive'` on every clone, precisely the scenario this protection exists for. [2](#0-1) 

Desktop does add its own defense-in-depth check, `isClonePathSensitive()`, which blocks cloning into a small hardcoded list of sensitive directories (home dir, `.ssh`, `.gnupg`, `.config`, `.gitconfig`, `AppData` on Windows). [3](#0-2) 

That check only validates the destination *path* the user chose; it does nothing to validate the *contents* of the attacker-controlled remote repository being cloned. It cannot substitute for Git's own upstream clone-protection mechanism, which is specifically about content coming from the remote (submodule paths, `.git` directory contents, hooks), not about the local destination path. By forcing `GIT_CLONE_PROTECTION_ACTIVE=false`, Desktop re-opens exactly the class of vulnerability upstream Git patched, for every `--recursive` clone it performs — regardless of whether the remote is a GitHub-hosted repo the user trusts or an arbitrary attacker-controlled URL (e.g., from an "Open in Desktop" deep link or a manually entered clone URL).

### Impact Explanation
If the underlying bundled Git binary is a version where this protection matters, an attacker who controls the content of a repository (via a malicious clone URL, deep link, or a compromised/malicious upstream) can craft a repository whose submodule/hook layout would normally be blocked by Git's clone protection, but is not blocked in Desktop because the protection has been explicitly turned off. Depending on the exact Git version and payload this can range from unexpected hook execution to code execution during clone, which is within the report's valid-impact bucket ("attacker controls a cloned/fetched repository ... result is code execution").

### Likelihood Explanation
Likelihood depends entirely on which git version is bundled and whether that version's clone-protection default is actually being neutralized here — I could not verify the bundled git version or confirm from the local repo whether the vulnerable code paths guarded by `GIT_CLONE_PROTECTION_ACTIVE` are still reachable in that version, since this information is not present in the indexed files I could inspect. The clone path is reached on every `git clone --recursive` invocation triggered by normal user actions (cloning from the UI, "Open in Desktop" URLs), so the trigger surface is broad and requires no unusual user behavior, but the actual exploitability hinges on git-internal behavior outside this repo.

### Recommendation
Do not hardcode `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. Either omit the variable entirely (leaving Git's own secure default active) or set it to `'true'`/leave unset, and rely on Desktop's `isClonePathSensitive()` purely as a supplementary, path-based control rather than a replacement for Git's content-based clone protections.

### Proof of Concept
1. In `app/src/lib/git/clone.ts`, observe that every call to `clone()` builds `env` with `GIT_CLONE_PROTECTION_ACTIVE: 'false'` unconditionally, before the `args.push('--', url, path)` and `git(args, __dirname, 'clone', opts)` call that actually invokes `git clone --recursive`. [4](#0-3) 
2. This means any code path that calls `clone()` — including `CloningRepositoriesStore.clone()` used by the app when a user clones a repo or follows an "Open in Desktop" deep link — performs the clone with Git's clone-protection env var explicitly disabled. [5](#0-4) 
3. Because the disabling is unconditional and independent of whether the remote URL is trusted, a crafted malicious repository URL supplied to the clone flow is cloned with this protection off, reproducing the exact hardening gap that `GIT_CLONE_PROTECTION_ACTIVE` was introduced to close upstream.

Note: I was unable to determine the exact bundled `dugite`/git version from the indexed files, so I cannot confirm with certainty that a concrete exploit payload (e.g., malicious submodule causing hook execution) succeeds against the currently bundled Git binary — this would need to be verified in a full checkout/build environment.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
