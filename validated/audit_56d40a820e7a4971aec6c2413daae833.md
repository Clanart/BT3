### Title
No unprivileged path to `mWOM.mint` exists - ([File: wombat/mWOM.sol])

### Summary
`mWOM.mint(address,uint256)` at [1](#0-0)  is gated by `onlyOwner` and is not reachable from any other function in the contract. The only paths that call the internal `_mint` are `_convert` (invoked by `convert`, `convertAndStake`, `deposit`, `incentiveDeposit`) and the constructor-time initial mint, both of which are strictly WOM-backed 1:1 mints, not unbacked mint vectors.

### Finding Description
`_mint` is called in exactly three places in `wombat/mWOM.sol`: once in `__mWom_init` for the initial owner mint [2](#0-1) , and twice inside `_convert`, always preceded by `IERC20(wom).safeTransferFrom(msg.sender, ...)` which pulls the equivalent amount of WOM from the caller before minting mWOM [3](#0-2) . `incentiveDeposit` (the function referenced in the audit question) calls `_convert` first — which requires the caller to transfer WOM in — and only afterward calls `IVLMGP(vlMGP).lockFor(vlMGPAmount, msg.sender)` to reward the caller with locked MGP [4](#0-3) . This is a one-way external call from `mWOM` into `vlMGP`; there is no callback mechanism from `vlMGP.lockFor` back into `mWOM`, so even if an attacker could point `vlMGP` at an arbitrary malicious contract, that contract has no way to re-enter `mWOM.mint` or `mWOM._mint` — `_mint`/`mint` are simply never called by anything other than the code paths already enumerated. Additionally, `vlMGP` can only be changed via `setVlmgp`, which is `onlyOwner` and enforces the target be a contract [5](#0-4) , so an unprivileged attacker cannot substitute their own "malicious vlMGP-like" contract in the first place.

### Impact Explanation
None. `mint` is inherently protected by the standard OpenZeppelin `onlyOwner` modifier, and no other function in `mWOM.sol` provides an indirect or reentrant path to it. There is no unbacked-mint vector reachable by an unprivileged actor.

### Likelihood Explanation
Not applicable — the described attack requires either owner privileges (to call `setVlmgp`) or a callback mechanism that does not exist in the contract. No capital or transaction sequence available to an unprivileged EOA/contract can reach `mint`.

### Recommendation
No fix required for this specific concern; the existing `onlyOwner` modifier on `mint` and the one-directional nature of the `lockFor` call are sufficient. (General hardening, such as adding an explicit reentrancy guard on `incentiveDeposit`/`_convert` against `vlMGP`, is unrelated to this specific reachability question since `_convert` already carries `nonReentrant`.)

### Proof of Concept
Foundry test plan (expected to confirm the negative result):
1. Deploy `mWOM`, `VLMGP`, mock `wom`/`mgp` tokens, initialize normally.
2. From a non-owner EOA, call `mWOM.mint(attacker, 1e18)` and assert revert with `"Ownable: caller is not the owner"`.
3. From a non-owner EOA, call `mWOM.setVlmgp(maliciousContract)` and assert the same revert.
4. Deploy a `MaliciousVlmgp` mock whose `lockFor` attempts to call back into `mWOM.mint` or `mWOM._convert`; since `setVlmgp` cannot be called by the attacker, this contract can never be wired in as `vlMGP`, so no further test is needed to prove the callback is unreachable.
5. Fuzz-call all external functions of `mWOM` (`convert`, `convertAndStake`, `deposit`, `incentiveDeposit`, `pause`, `unpause`, `setHelper`, `setWombatStaking`, `setWomUp`, `lockAllWom`, `setRewardRatio`, `setVlmgp`, `transferMGPDust`, `mint`) from non-owner callers and assert: (a) admin functions revert with `Ownable`, (b) `_mint` invocations that succeed (`convert`/`deposit`/`incentiveDeposit`) are always preceded by an equal `safeTransferFrom` of `wom` from `msg.sender`, confirming 1:1 backing and no unbacked mint.
