### Title
Unchecked negative-fee subtraction before `uint64` cast in mempool spend-bundle validation causes an uncaught exception / node processing halt on inflating spend bundles - ([File: chia/full_node/mempool_manager.py])

### Summary
In `MempoolManager.validate_spend_bundle()`, the fee is computed as `fees = uint64(removal_amount - addition_amount)` before any check that `addition_amount <= removal_amount`. A spend bundle whose declared `CREATE_COIN` outputs sum to more than the amount of coins it spends (an inflation/minting attempt) makes `removal_amount - addition_amount` negative, and casting a negative Python `int` to the `chia_rs` `uint64` type raises an exception rather than returning a clean `Err`. [1](#0-0) 

### Finding Description
This is structurally analogous to the Zcash GHSA-g4x5-crjh-29ff bug: a value-balance quantity is computed via unchecked subtraction before being range-checked, so a value that should be "cleanly rejected" instead crashes/aborts processing.

The addition amount for a spend bundle is accumulated from each coin spend's `CREATE_COIN` conditions: [2](#0-1) 

and the removal amount is accumulated from the coin records of the spent coins: [3](#0-2) 

Then the fee is computed directly: [4](#0-3) 

`chia_rs`'s `uint64(...)` conversion raises when given a negative value — this is demonstrated directly in the test suite for the analogous `compute_block_fee` helper, which raises `ValueError("does not fit into uint64")` for a negative difference: [5](#0-4) 

Contrast this with `validate_block_body()` in consensus, which is the code path that validates a fully-formed block (not a raw spend bundle at mempool-admission time). There, the equivalent "did this transaction try to mint value" check is performed with plain Python integers and explicitly gated **before** any typed cast: [6](#0-5) 

Line 542 returns `Err.MINTING_COIN` before ever computing `fees = removed - added` (an untyped Python `int`, so no cast exception is possible even if this ordering were somehow bypassed). The mempool spend-bundle admission path in `mempool_manager.py`, however, has no equivalent “additions <= removals” guard prior to the `uint64(...)` cast at line 814 — the ordering-correction that exists in block validation was not mirrored in mempool admission.

### Impact Explanation
`validate_spend_bundle()` is invoked directly from `add_spend_bundle()`, which is the core entry point used whenever a spend bundle is submitted to a full node's mempool (from RPC `push_tx`, wallet transaction submission, or gossip from a peer relaying a transaction) — i.e., reachable by any unprivileged spend-bundle submitter, exactly matching the reachable-actor requirement. If the exception raised by the invalid `uint64` cast is not caught somewhere in the call chain leading up to this function, it propagates as an unhandled exception inside the node's transaction-processing path, which can halt the processing of that request/task and is a direct analog of the "node aborts" behavior described in the referenced Zcash advisory (a would-be-rejected transaction instead causing an uncontrolled runtime failure rather than a clean `Err.MINTING_COIN`/`Err.INVALID_BLOCK_FEE_AMOUNT`-style rejection).

### Likelihood Explanation
Constructing a spend bundle whose `CREATE_COIN` outputs exceed the value of the coins being spent requires no special privileges, only a syntactically valid CLVM solution producing `CREATE_COIN` conditions with an output sum greater than input coin amounts — this is trivial for any wallet-level attacker to construct and submit. However, I could not fully verify within the available context whether an earlier signature/condition check (e.g. the AGG_SIG/cost-validation performed by the Rust `conds` computation prior to `validate_spend_bundle`) would already reject an inflating spend bundle before reaching line 814, nor could I confirm whether the exception is caught by a wrapping `try/except` somewhere between the RPC/gossip handler and `add_spend_bundle`. This uncertainty affects confidence in real-world exploitability and should be verified with a concrete proof-of-concept spend bundle run against `MempoolManager.pre_validate_spendbundle`/`add_spend_bundle`.

### Recommendation
Add an explicit `if addition_amount > removal_amount: return Err.MINTING_COIN, None, []` (or equivalent) check in `MempoolManager.validate_spend_bundle()` in `chia/full_node/mempool_manager.py` immediately before the `fees = uint64(removal_amount - addition_amount)` line, mirroring the ordering already used in `chia/consensus/block_body_validation.py` (`if removed < added: return Err.MINTING_COIN` before subtracting). This guarantees the value is always non-negative before the `uint64` cast, eliminating the possibility of an uncaught exception on this path.
