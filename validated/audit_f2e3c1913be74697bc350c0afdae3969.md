## Title
SSH credential storage/lookup keyed on unauthenticated ssh-prompt text, allowing a malicious SSH server to trigger silent credential reuse/exfiltration - (File: `app/src/lib/ssh/ssh-credential-storage.ts`)

### Summary
The SSH password store is keyed purely on the string parsed out of the local `ssh` process's askpass prompt (`user@host`), with no verification that this string corresponds to the actual host the git operation is currently connecting to. Because that prompt text is not fully controlled by the trusted `ssh` binary itself in every authentication method (in particular under `keyboard-interactive` auth, where the *prompt text is supplied by the remote server*), a malicious/attacker-controlled SSH server can forge a prompt that lexically matches a key already used to store a legitimate credential (e.g. `git@some-other-host`), causing GitHub Desktop to silently look up and hand over the previously-stored password to the malicious/attacker-controlled server, without any additional user prompt.

### Finding Description
`SSHCredentialEntry.key` is defined as an opaque string ("username or hash") with no host binding: [1](#0-0) 

The key is populated straight from a regex match on the raw text of the trampoline's askpass prompt: [2](#0-1) 

If a password is already present for that exact key, it is returned immediately and silently, without any dialog/user confirmation: [3](#0-2) 

This handler is invoked for any trampoline command whose parameter ends with `"'s password: "`: [4](#0-3) 

The password returned by this callback is fed back to the running `ssh` process (via `SSH_ASKPASS`), which then transmits it over the network to whatever host it is currently talking to: [5](#0-4) 

Nowhere in this path is the `key`/`username` cross-checked against the actual remote host/IP of the current git operation. For the plain "password" authentication method OpenSSH itself generates this string locally (`user@host`) from the real destination, which somewhat limits spoofing. However, OpenSSH's `keyboard-interactive` authentication method allows the *remote server* to supply arbitrary prompt text (per RFC 4256), and when no TTY is available OpenSSH falls back to invoking `SSH_ASKPASS` with that server-supplied prompt text verbatim. Because Desktop's handler only pattern-matches on `"'s password: "` suffix with no additional validation, a malicious SSH server can send a keyboard-interactive prompt whose text is crafted to look like `<username>@<other-real-host>'s password: `, i.e. impersonate a completely different host than the one actually being connected to.

### Impact Explanation
If the user has previously stored an SSH password for some host/user combination (e.g., a self-hosted Git server using SSH password auth), an unrelated malicious SSH endpoint (reached e.g. via a submodule URL or remote pointing at an attacker-controlled server present in attacker-controlled repository content) can forge a keyboard-interactive prompt matching that stored key's exact string and receive the stored password automatically — with zero additional UI prompt to the user — resulting in credential/token exfiltration to an attacker-controlled server.

### Likelihood Explanation
Exploitation requires:
1. The user to have previously stored a "remembered" SSH password for at least one host/user via `SSHUserPassword` dialog.
2. The user to connect to a new attacker-controlled SSH endpoint (e.g., from repository/submodule content), which does require passing through the existing `handleSSHHostAuthenticity` host-key confirmation dialog for unknown hosts (an existing partial mitigation, though commonly clicked through by users).
3. The attacker's SSH server to correctly guess/know the exact `user@host` key string previously stored by the victim.

Because of constraint (3), broad automatic exploitation is limited to guessable/well-known host strings, reducing likelihood, but the underlying design flaw (no cryptographic/host binding on the credential lookup key) is a genuine weakness independent of guessing difficulty.

### Recommendation
Bind stored SSH credentials to a verified identifier of the actual remote endpoint of the current git operation (e.g., the resolved host/port from the git remote URL associated with the `operationGUID`/trampoline token, or the SSH host key fingerprint), rather than trusting the raw prompt text emitted by the `ssh` subprocess. At minimum, cross-check that the host portion of the parsed `user@host` matches the host of the git remote URL for the operation in progress before performing a silent TokenStore lookup, and require an explicit user-visible re-confirmation whenever the two do not match.

### Proof of Concept
1. Attacker publishes a repository whose `.gitmodules` (or a remote the user is induced to add) points to `ssh://attacker.example.com/repo.git`.
2. Victim, who has previously saved an SSH password for `git@internal-git.company.com`, fetches/clones the repo. Desktop's `AddSSHHost` dialog appears for the unknown `attacker.example.com` host; user accepts.
3. Attacker's SSH server offers only `keyboard-interactive` authentication and sends a single prompt whose text is exactly `git@internal-git.company.com's password: `.
4. OpenSSH (no TTY, `SSH_ASKPASS` set) invokes Desktop's trampoline askpass handler with that exact string as `command.parameters[0]`.
5. `handleSSHUserPassword` in `app/src/lib/trampoline/trampoline-askpass-handler.ts` matches the regex, extracts `username = "git@internal-git.company.com"`, finds a stored password via `getSSHUserPassword`, and returns it — silently sending the victim's real credential for `internal-git.company.com` to `attacker.example.com`. async function handleSSHUserPassword(operationGUID: string, prompt: string) {
```typescript
  const promptRegex = /^(.+@.+)'s password: $/

  const matches = promptRegex.exec(prompt)
  if (matches === null || matches.length < 2) {
    return undefined
  }

  const username = matches[1]

  const storedPassword = await getSSHUserPassword(username)
  if (storedPassword !== null) {
    // Keep this stored password around in case it's not valid and we need to
    // delete it if the git operation fails to authenticate.
    setMostRecentSSHUserPassword(operationGUID, username)
    return storedPassword
  }
```
