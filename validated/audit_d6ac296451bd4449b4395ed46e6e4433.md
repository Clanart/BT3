### Title
Missing `params.i()` exclusion check in `GeneratorPromotion::complete` causes unreachable-code panic on attacker-controlled proof set (DoS) - (File: crypto/dkg/promote/src/lib.rs)

### Summary
`GeneratorPromotion::complete` validates only the count and the upper bound of participant indexes in the attacker-supplied `proofs` map, then iterates `1 ..= n` skipping only `params.i()` and blindly calls `proofs.get(&i).unwrap()`. If the submitted map of `n - 1` distinct valid participants happens to contain our own index `params.i()` (and therefore omits some other required index `j`), both validation loops pass and the `unwrap()` panics. This is a remotely triggerable, repeatable crash — the same class as CVE-2017-3453 (low-privileged attacker causes a complete DoS via crafted input), mapped onto Serai's DKG generator-promotion path.

### Finding Description
In `crypto/dkg/promote/src/lib.rs`, `complete` performs two checks on the incoming `proofs: &HashMap<Participant, GeneratorProof<C1>>`:

```rust
// crypto/dkg/promote/src/lib.rs:125-136
if proofs.len() != (usize::from(params.n()) - 1) { ... }
for i in proofs.keys().copied() {
  if u16::from(i) > params.n() { ... }
}
```

Then it consumes the map:

```rust
// crypto/dkg/promote/src/lib.rs:140-146
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() { continue; }
  let proof = proofs.get(&i).unwrap();   // panics if i not in map
```

The validation guarantees: `proofs` has exactly `n - 1` entries, all keys are nonzero (`Participant` enforces this by construction, `crypto/dkg/src/lib.rs:29-35`) and ≤ `n`. It never checks that `params.i()` is absent or that every `1..=n, i != params.i()` is present. A `HashMap` cannot hold duplicate keys, so a map of `n - 1` distinct valid participants that *includes* `params.i()` necessarily omits exactly one `j != params.i()`. Both checks pass; the loop then hits `proofs.get(&j)` → `None` → panic.

### Impact Explanation
`proofs` is built from `GeneratorProof::read` (`crypto/dkg/promote/src/lib.rs:72-77`), which deserializes untrusted bytes (`read_G` + `DLEqProof::read`) sent by other participants — data an unprivileged counterparty controls. Any participant (or anyone able to inject a malformed proof set for a given index) can supply `n - 1` well-formed `GeneratorProof`s whose key set includes the victim's own `params.i()` instead of some other required participant's. The victim's `complete` call panics instead of returning `PromotionError`, crashing the thread/process performing generator promotion. This is a complete, reliably repeatable availability loss of the node — matching the CVE-2017-3453 impact profile (unauthorized hang/repeatable crash, availability-only impact). The `.unwrap()` at `promote/src/lib.rs:165` (`ThresholdKeys::new(...).unwrap()`) is a similar latent panic but is only reachable after the proofs verify; the line-146 unwrap is directly reachable.

### Likelihood Explanation
Triggering requires only control over which participant indexes accompany the `n - 1` proofs fed to `complete` — the attacker does not need to forge any proof, only mislabel the map keys, which are untrusted inputs. The panic occurs before any expensive verification for the missing index, so the crash is deterministic. A single malicious (or colluding-adjacent, yet reachable by one) participant in a promotion ceremony can repeatedly crash every counterparty that processes its message set. The attacker's own proof still verifies correctly when used by honest parties for *their* index, so the attacker's cost is minimal.

### Recommendation
Replace the `unwrap()` with an error and validate completeness up front, e.g. in `crypto/dkg/promote/src/lib.rs`:

```rust
// Reject our own index being present, and require exactly the other participants
if proofs.contains_key(&params.i()) {
  Err(PromotionError::InvalidParticipant { n: params.n(), participant: params.i() })?;
}
```

or defensively at the lookup site:

```rust
let proof = proofs.get(&i)
  .ok_or(PromotionError::InvalidParticipant { n: params.n(), participant: i })?;
```

Mirroring the `validate_map` helper used elsewhere (`crypto/frost/src/lib.rs:50-73`) would make the required/expected set explicit.

### Proof of Concept
```rust
// Params: t = 2, n = 3, our index i = 1
let params = ThresholdParams::new(2, 3, Participant::new(1).unwrap()).unwrap();

// Attacker supplies n - 1 = 2 proofs, but keys them as participants {1, 2}
// (includes OUR index 1, omits required index 3). All keys are valid Participants <= n.
let mut proofs = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), attacker_proof_a); // our own index!
proofs.insert(Participant::new(2).unwrap(), attacker_proof_b);

// Checks pass: proofs.len() == 2 == n - 1; all keys <= 3.
// Loop: i = 2 -> verify ok; i = 3 -> proofs.get(&3) == None -> unwrap() PANICS.
let _ = promotion.complete(&proofs); // thread panics instead of Err
```

Root cause is the missing "must not contain `params.i()` / must contain every other index" invariant between `crypto/dkg/promote/src/lib.rs:125-136` (validation) and `crypto/dkg/promote/src/lib.rs:146` (unchecked `unwrap`).
