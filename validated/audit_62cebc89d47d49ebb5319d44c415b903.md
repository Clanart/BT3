### Title
Non-conformant JSON parser silently accepts duplicate/conflicting field and oneof keys, causing "last one wins" divergence from the strict-mode / spec-conformant interpretation - (File: src/google/protobuf/json/internal/parser.cc)

### Summary
The Tornado bug is a "double declaration of framing" (two `Transfer-Encoding` headers) that the parser silently mis-resolves, so the request's true boundary is interpreted differently by a proxy and Tornado, enabling smuggling. The nearest structural analog in this Protobuf checkout is the ProtoJSON parser's handling of **duplicate keys / duplicate oneof-member keys**, which is controlled by a legacy compatibility flag (`allow_legacy_nonconformant_behavior`) that changes whether a duplicate is an error or is silently resolved with "last value wins" [1](#0-0) .

### Finding Description
`ParseField` computes a `SeenState` via `RecordAsSeen` (`kFirstSeen`, `kOneofAlreadySeen`, `kFieldAlreadySeen`) to detect a field or oneof member that has already been populated earlier in the same JSON object [2](#0-1) . Whether a second occurrence of the *same* field name is rejected depends on `lex.options().allow_legacy_nonconformant_behavior`: only `kOneofAlreadySeen` is unconditionally an error; `kFieldAlreadySeen` is only rejected when the "legacy nonconformant" compatibility mode is *not* enabled [1](#0-0) . When the legacy mode is on (this is documented as the "current default legacy mode" in code comments), duplicate keys are accepted and the message/repeated-field state is cleared only on first sight, so a second occurrence effectively overwrites/merges over the first, producing "last one wins" semantics that are unspecified by the JSON RFC (JSON objects with duplicate keys have no defined meaning) [3](#0-2) .

This mirrors the Tornado bug's core defect class: an *ambiguous, attacker-controlled* input construct (repeated/duplicate declaration of the same logical field) whose resolution is implementation-defined and mode-dependent, rather than uniformly and strictly rejected. If two systems in a pipeline interpret the same JSON payload with different settings of `allow_legacy_nonconformant_behavior` (e.g., a Java `GSON`-backed frontend validator using the lenient default noted in `JsonFormatTest.testParserRejectDuplicatedFields` comments, versus a strict-mode backend, or vice versa), they can disagree about which value a field or oneof case ultimately holds [4](#0-3) .

### Impact Explanation
This is a genuine but narrower analog than HTTP smuggling: it can produce a **decode differential** between two conformant-vs-legacy consumers of the identical byte stream, potentially causing one system to authorize/act on field A's value while another later-stage consumer (re-parsing the same JSON with different options, or a different language binding) resolves to field B's value. That is a `CWE-436`/`CWE-444`-style interpretation inconsistency confined to trusted-schema ProtoJSON decoding, not memory corruption. However, unlike Tornado's smuggling (which desyncs a TCP-level HTTP proxy boundary and enables full request smuggling / cache poisoning across a trust boundary), this JSON case only affects logical field-value resolution *within a single decoded message*, and the divergent behavior is a documented, intentional compatibility toggle rather than a silent protocol violation, which meaningfully weakens the impact.

### Likelihood Explanation
Low-to-Medium. The attacker (an ordinary client submitting ProtoJSON) fully controls whether a payload contains duplicate keys/oneof members, and the differing outcome only manifests if downstream application logic actually re-parses the same bytes with two different `allow_legacy_nonconformant_behavior` settings (e.g., across library versions or between a validating gateway and the real service) — a scenario dependent on consuming-application architecture that Protobuf itself does not control or guarantee. This is explicitly called out as legacy/compat behavior rather than a defect, and conformant strict mode already rejects the ambiguous case.

### Recommendation
Not filing this as a distinct vulnerability against Protobuf's public parsing API. The behavior is intentional, documented, and gated by the `allow_legacy_nonconformant_behavior` option with a strict mode available; there is no unchecked bypass of an existing security invariant analogous to Tornado's silent double-`Transfer-Encoding` framing ambiguity. If pursued at all, the actionable recommendation would be limited to documentation guidance: warn integrators that mixing `allow_legacy_nonconformant_behavior` settings across trust-boundary components that re-parse the same JSON can produce inconsistent field resolution, and recommend uniformly enabling strict (non-legacy) parsing wherever ProtoJSON crosses a trust/authorization boundary.

### Proof of Concept
Not applicable as a standalone vulnerability. Conceptually: encode `{"oneofInt32": 1, "oneofNullValue": null}` (or any duplicate-field JSON) and parse it once with default/legacy options and once with `allow_legacy_nonconformant_behavior=false`; the two parses return different `has_field`/`oneof_case` results, matching the divergence already exercised by `testParserRejectDuplicatedFields` and `testNullFirstInDuplicateOneof`/`testNullLastInDuplicateOneof` [5](#0-4) . No production-code reproduction demonstrating an actual authorization bypass or corruption was found; this is presented as the closest structural analog only, with materially lower severity than the reported Tornado issue.

enum class SeenState {
  kFirstSeen,
  kOneofAlreadySeen,
  kFieldAlreadySeen,
};

using ::google::protobuf::internal::WireFormatLite;

// See the comment in json_util2_parser.cc for more information.
//
// The type traits in this file  describe how to parse to a protobuf
// representation used by the JSON API, either via proto reflection or by
// emitting wire format to an output stream.

// Helper alias templates to avoid needing to write `typename` in function
// signatures.
template <typename Traits>
using Msg = typename Traits::Msg;

struct ParseProto2Descriptor : Proto2Descriptor {
  // A message value that fields can be written to, but not read from.
  class Msg {
   public:
    explicit Msg(Message* msg) : msg_(msg) {}

   private:
    friend ParseProto2Descriptor;
    Message* msg_;
    // Because `msg` might already have oneofs set, we need to track which were
    // set *during* the parse separately.
    absl::flat_hash_set<int> parsed_oneofs_indices_;
    absl::flat_hash_set<int> parsed_fields_;
  };

  /// Functions for writing fields. ///

  // Marks a field as having been "seen". This will return a SeenState
  // indicating whether it is first seen, duplicate field seen, or oneof
  // conflict seen.
  static SeenState RecordAsSeen(Field f, Msg& msg) {
    if (f->real_containing_oneof() != nullptr) {
      int oneof_index = f->real_containing_oneof()->index();
      bool oneof_inserted =
          msg.parsed_oneofs_indices_.insert(oneof_index).second;
      if (!oneof_inserted) {
        // Oneof takes precedent over Field in the case of "this is in a oneof
        // and the field is set"
        return SeenState::kOneofAlreadySeen;
      }
    }

    bool field_inserted = msg.parsed_fields_.insert(f->number()).second;
    if (!field_inserted) {
      return SeenState::kFieldAlreadySeen;
    }

    return SeenState::kFirstSeen;
  }
