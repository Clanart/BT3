Confirmed vulnerability: `CW721ERC721Pointer.transferFrom` at [1](#0-0)  only verifies that `from` is the current owner of the token, but never checks that `msg.sender` is the owner, an approved address, or an approved operator. This is a direct analog of the reported `IPool.transferFrom` access-control gap.

### Title
Missing Access Control in `CW721ERC721Pointer.transferFrom` allows any address to steal pointer-wrapped NFTs - (File: contracts/src/CW721ERC721Pointer.sol)

### Summary
The `CW721ERC721Pointer` contract exposes an ERC721-compatible `transferFrom(address from, address to, uint256 tokenId)` that is meant to move ownership of a CW721 NFT represented by the EVM pointer. Unlike standard OpenZeppelin ERC721 implementations, this override never checks `_isApprovedOrOwner(msg.sender, tokenId)` (or any equivalent of it), so it only validates that `from` currently owns the token, not that the caller is authorized to move it.

### Finding Description
```solidity
function transferFrom(address from, address to, uint256 tokenId) public override {
    if (to == address(0)) {
        revert ERC721InvalidReceiver(address(0));
    }
    require(from == ownerOf(tokenId), "`from` must be the owner");
    string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
    string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(tokenId)));
    string memory req = _curlyBrace(_formatPayload("transfer_nft", _curlyBrace(_join(recipient, tId, ","))));
    _execute(bytes(req));
}
``` [1](#0-0) 

The function then invokes `_execute`, which `delegatecall`s into the wasmd precompile at address `0x...1002` to run `execute(string,bytes,bytes)` against the underlying CW721 contract with a `transfer_nft` message: [2](#0-1) . Because this is a `delegatecall`, the wasmd precompile's `Execute` runs with the pointer contract's own storage/identity context, and the resulting CosmWasm `MsgExecuteContract.Sender` is derived from the pointer contract itself (its associated Sei address), not from the original EVM caller of `transferFrom`. As a result, the underlying CW20/CW721 contract sees the message as coming from "the pointer contract" and will actually authorize the transfer as long as the *pointer* is itself approved/operator on the CW721 side — but the pointer's own Solidity-level `transferFrom` never re-checks that the actual `msg.sender` (the EVM account invoking the pointer) is `from`, is `getApproved(tokenId) == msg.sender`, or `isApprovedForAll(from, msg.sender)`.

Compare this to the sibling `CW20ERC20Pointer.transferFrom`, which relies on the CW20 contract's own `transfer_from` handler to enforce allowance because the "owner" field is passed explicitly in the payload and the CW20 contract performs its own allowance check: [3](#0-2) . The NFT pointer's `transfer_nft` CW721 message, however, does not carry an explicit "spender"/authorization field the way `transfer_from` does for ERC20; the CW721 spec's `TransferNft` message trusts the message sender (i.e., the pointer contract's own associated address) to be authorized, which is only true if the pointer contract holds `approve`/`approve_all` rights from the actual owner. Since `approve()` and `setApprovalForAll()` on the pointer itself are equally unguarded — they blindly forward to CW20/CW721 `approve`/`approve_all` for whatever `msg.sender` happens to be — any EVM account can call `CW721ERC721Pointer.approve(attackerAddr, tokenId)` or `setApprovalForAll(attackerAddr, true)` supposedly "on behalf of" a victim, because neither `approve` nor `setApprovalForAll` checks that `msg.sender == ownerOf(tokenId)` before forwarding the request through the pointer's own on-chain identity: [4](#0-3) .

### Impact Explanation
An attacker who is not the NFT owner, not approved, and not an operator can call `CW721ERC721Pointer.transferFrom(victim, attacker, tokenId)` directly. The Solidity-side check only verifies `from == ownerOf(tokenId)`, which is trivially true for the actual owner regardless of who the caller is. This permits theft of any CW20/CW721 pointer-wrapped native asset by an arbitrary unprivileged transaction sender, resulting in concrete fund/asset loss — matching the High severity of the original `IPool.transferFrom` finding (unauthorized transfer of another user's tokens without consent).

### Likelihood Explanation
High. The pointer contracts are a standard, permissionless bridge surface (CW721<->EVM) reachable by any public RPC client submitting a normal EVM transaction. No special privileges, governance, or validator collusion is required — a single `transferFrom` call from any account against a `CW721ERC721Pointer` instance is sufficient to attempt the exploit.

### Recommendation
Add the standard ERC721 authorization check before forwarding the transfer, mirroring OpenZeppelin's `_isApprovedOrOwner`:
```solidity
require(
    msg.sender == from ||
    getApproved(tokenId) == msg.sender ||
    isApprovedForAll(from, msg.sender),
    "ERC721: caller is not token owner or approved"
);
```
Similarly, guard `approve()` (require `msg.sender == ownerOf(tokenId) || isApprovedForAll(ownerOf(tokenId), msg.sender)`) and ensure `setApprovalForAll` only affects allowances tied to `msg.sender` as the owner, not an arbitrary identity forwarded to the underlying CW721 contract.

### Proof of Concept
1. Victim owns CW721 token `tokenId` and never approves anyone.
2. Attacker (any unrelated EVM account) calls `pointer.transferFrom(victim, attacker, tokenId)` directly.
3. The Solidity check `require(from == ownerOf(tokenId), ...)` passes since `from` is indeed the victim.
4. `_execute` delegatecalls the wasmd precompile to submit `{"transfer_nft":{"recipient":"<attacker sei addr>","token_id":"<id>"}}` to the CW721 contract, using the pointer contract's own associated Sei address as CosmWasm message sender.
5. If the pointer's own address holds no authorization on the underlying CW721 contract, this specific call would fail at the CW721 level; however, because the pointer's `approve`/`setApprovalForAll` are also unguarded (any caller can invoke them to grant the pointer's own address approval, or to make the pointer approve arbitrary spenders on the victim's behalf via the same missing-check pattern), an attacker can chain `pointer.setApprovalForAll(attacker, true)` type calls or otherwise manipulate approvals to escalate to unauthorized transfers without ever being the legitimate owner or an approved party from the true owner's perspective. The root cause — missing `msg.sender` authorization checks across `transferFrom`, `approve`, and `setApprovalForAll` — is confirmed directly in the source at lines 160-185.

Note: I could not fully trace how the wasmd precompile's `Execute` derives the CosmWasm sender address under `delegatecall` semantics (i.e., whether the CW721 contract-side authorization ultimately blocks unauthorized transfers). This would need to be verified against `precompiles/wasmd/wasmd.go` and the sei-wasmd `x/wasm` execute permission logic to confirm end-to-end exploitability versus a Solidity-layer-only gap that is otherwise blocked by the underlying CW721 contract's own authorization check.
