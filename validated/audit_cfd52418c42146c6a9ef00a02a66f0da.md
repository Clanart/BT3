### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s with no maturity/height data — ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
The external report describes an authorization flag (invoice/documents complete) that is set once and never expires, so a stale credential is accepted indefinitely. The analog in `bitcoin-serai` is a validity condition — coinbase maturity — that is permanently erased at scan time: `Scanner::scan_block` returns `ReceivedOutput`s for coinbase transactions with no coinbase flag or block height, so the "is this output spendable" check can never be performed downstream. The output is treated as authorized-for-spend forever, immediately.

### Finding Description
`ReceivedOutput` (`mod.rs:90-97`) stores only `offset`, `output`, and `outpoint` — no block height, no `is_coinbase` flag, and no maturity field. `scan_block` (`mod.rs:221-227`) iterates `block.txdata` including `txdata[0]` (the coinbase) and emits identical `ReceivedOutput`s for it. `scan_transaction` (`mod.rs:199-214`) has no way to distinguish coinbase inputs since it matches only `script_pubkey`.

Bitcoin consensus requires coinbase outputs to have 100 confirmations before being spent (COINBASE_MATURITY). Because `ReceivedOutput` drops all maturity-relevant data at production time, any consumer feeding these outputs into `Transaction` construction in `send.rs` will build a transaction spending an immature coinbase output, which the network rejects — or worse, in a federated signing context the coordinator may solicit a threshold signature over a sighash that can never confirm.

This mirrors the report precisely: just as `setInvoiceComplete` stores a bare bool with no expiry so a stale authorization is accepted, `scan_block` produces outputs with no maturity metadata so an immature (not-yet-valid) coin is accepted as spendable. In both cases the datum required to check validity is never recorded.

### Impact Explanation
Outputs scanned via `scan_block` are reported as received spendable funds when they are not spendable for 100 blocks. A processor using `scan_block` to determine balance/inputs can construct and threshold-sign a transaction the Bitcoin network will reject (`bad-txns-premature-spend-of-coinbase`), locking the batch or burning fees on an unconfirmable transaction — "funds reported received that are not spendable," an accepted consequence class.

### Likelihood Explanation
`scan_block` is a public API over fully attacker/publisher-influenced data (any mined block). Coinbase outputs paying to a scanned script are plausible whenever the monitored key receives miner payouts or any block is scanned. The failure requires only that a consumer call `scan_block` rather than manually skipping `txdata[0]` — the default, convenient path. Severity is Medium: the mis-signed transaction is rejected by consensus rather than stolen, but it wastes a signing session and reports false balance.

### Recommendation
Track maturity in `ReceivedOutput`: add a `block_height: Option<u64>` or `is_coinbase: bool` field set by `scan_block`/`scan_transaction`, and have `scan_block` skip `txdata[0]` or mark coinbase outputs so callers can defer them until `current_height - block_height >= 100`. Alternatively, remove coinbase scanning from `scan_block` entirely, matching the documented workaround (`block.txdata[1 ..]`).
