### Title
Unbounded recursive RLP decoding of `AccountKeyRoleBased` via the public `kaia_decodeAccountKey` RPC allows CPU/memory exhaustion from a single crafted call - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`KaiaAPI.DecodeAccountKey`, a public JSON-RPC method reachable by any unauthenticated RPC caller, RLP-decodes arbitrary attacker-supplied bytes into an `AccountKeySerializer` with no depth, size, or composite-nesting restriction applied before or during decoding. Because `AccountKeyRoleBased.DecodeRLP` recursively decodes each of its elements as a fresh `AccountKeySerializer` (which can itself be another `AccountKeyRoleBased`), an attacker can construct a deeply/widely nested RLP payload that causes exponential recursive decode work and allocation, analogous to the React Server Components DoS where crafted requests to a request-reachable decode/parsing routine trigger unbounded CPU/memory consumption.

### Finding Description
The RPC entry point: [1](#0-0) 

takes raw `hexutil.Bytes` directly from the RPC caller and calls `rlp.DecodeBytes` with no pre-check on nesting depth, key-type composition, or overall structural complexity.

The decode path recurses through `AccountKeySerializer.DecodeRLP`, which reads a key type and then dispatches to the concrete `AccountKey.DecodeRLP` for that type: [2](#0-1) 

When the key type is `AccountKeyTypeRoleBased`, `AccountKeyRoleBased.DecodeRLP` decodes a list of byte-strings and then, for *each* element, independently invokes `rlp.DecodeBytes` on a fresh `AccountKeySerializer`, which can again resolve to `AccountKeyRoleBased`: [3](#0-2) 

Critically, the composite-nesting restriction (`roleBasedKey cannot contain a roleBasedKey as a role key`) is enforced only in `checkAccountKeyZeroValues`/`CheckInstallable`, both of which are invoked from `EncodeAccountKey` and the account-update transaction validation path — but **not** from `DecodeAccountKey`: [4](#0-3) 

Because `DecodeAccountKey` never calls `CheckInstallable`/`checkAccountKeyZeroValues`, an attacker can submit RLP bytes encoding arbitrarily deep or wide nesting of `AccountKeyRoleBased → AccountKeySerializer → AccountKeyRoleBased → …`. Each level triggers additional `rlp.DecodeBytes` calls, slice allocations (`make([]AccountKey, len(enc))`), and recursive stack usage, with no depth counter or key-count limit analogous to `MaxNumKeysForMultiSig` (which exists only for `AccountKeyWeightedMultiSig`, not for `AccountKeyRoleBased` nesting): [5](#0-4) 

The only outer bound on the attack payload is the HTTP/JSON-RPC request body size limit (`common.MaxRequestContentLength`), which still permits a request large enough (a few hundred KB to several MB, depending on configuration) to encode many recursive levels/branches of nested lists, each multiplying decode work — the same "excessive CPU usage / out-of-memory" bug class described in the React Server Components advisory (CWE-400/CWE-770), where a crafted request to a server-reachable parsing endpoint causes unbounded resource consumption.

### Impact Explanation
Any unauthenticated public RPC caller can send a single `kaia_decodeAccountKey` request with a specially crafted nested `AccountKeyRoleBased` RLP payload to cause the node to perform excessive recursive decoding/allocation work, potentially exhausting CPU or memory on the RPC-serving node process. Because JSON-RPC endpoints are typically shared with block-processing/validation logic in the same node process, this can degrade or crash the node, affecting availability for all users relying on that node (a Denial-of-Service impact, matching the CVSS `AV:N/AC:L/PR:N/UI:N/S:U/A:H` profile of the referenced advisory).

### Likelihood Explanation
High likelihood: the endpoint requires no authentication, no fee payment, no gas, and no on-chain transaction — a single crafted HTTP/WS JSON-RPC call is sufficient. The vulnerable code path (`AccountKeyRoleBased.DecodeRLP` → recursive `AccountKeySerializer` decode) is reachable directly from `DecodeAccountKey` without any of the depth/composite checks that exist elsewhere in the codebase (e.g., `CheckInstallable`'s `IsCompositeType` rejection, `MaxNumKeysForMultiSig`).

### Recommendation
- Enforce nesting-depth and composite-type restrictions (mirroring the existing `roleBasedKey cannot contain a roleBasedKey` rule in `checkAccountKeyZeroValues`) inside `AccountKeyRoleBased.DecodeRLP` itself, before or during recursive decode, rather than only at `CheckInstallable` time.
- Add an explicit recursion-depth counter or maximum key-count guard (similar to `MaxNumKeysForMultiSig`) for `AccountKeyRoleBased` decoding.
- Apply the same validation (`checkAccountKeyZeroValues`/`CheckInstallable`) to `DecodeAccountKey` as is already applied to `EncodeAccountKey`, or otherwise bound the total decode work for RPC-supplied account-key bytes.

### Proof of Concept
Conceptually (exact byte-level PoC would require constructing nested RLP manually, which was not verified by execution in this environment):
1. Construct `AccountKeySerializer` RLP bytes encoding `keyType = AccountKeyTypeRoleBased` with N sub-keys, each sub-key itself being a full `AccountKeySerializer` of `keyType = AccountKeyTypeRoleBased` with N further sub-keys, repeated to a chosen depth D (e.g., N=10, D=10 already yields 10^10 nested decode operations if unbounded, though bounded practically by the RLP encoding size needed — a smaller N/D combination tuned to just under `MaxRequestContentLength` can still multiply decode cost significantly beyond input size).
2. Call the public RPC method `kaia_decodeAccountKey` with the resulting bytes as `encodedAccKey`.
3. Observe CPU/memory usage of the node process spike disproportionately to the request payload size, since `DecodeAccountKey` performs no depth or composite-nesting validation prior to or during decode (unlike `EncodeAccountKey`/`CheckInstallable`).

Note: I was unable to execute or size-verify this PoC in this environment (no code execution tools available), so the exact amplification factor and whether it crosses a "High" DoS severity threshold for a given `MaxRequestContentLength` configuration should be empirically validated in a live environment before treating this as confirmed-exploitable at High severity.

func (s *KaiaAPI) DecodeAccountKey(encodedAccKey hexutil.Bytes) (*accountkey.AccountKeySerializer, error) {
	dec := accountkey.NewAccountKeySerializer()
	if err := rlp.DecodeBytes(encodedAccKey, &dec); err != nil {
		return nil, err
	}
	return dec, nil
}

// checkAccountKeyZeroValues returns errors if the input account key contains zero values of threshold or weight.
func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}
	return nil

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}
