## Analysis

`PullRequestReview` does **not** render `review.body` through raw HTML injection — the comment body flows through `PullRequestCommentLike` → `SandboxedMarkdown`, which uses `marked` + `DOMPurify.sanitize(...)` inside a `sandbox="allow-same-origin"` iframe served via a `data:` URI, and link clicks are gated by `/^https?:/.test(a.protocol)` before `onMarkdownLinkClicked` fires. [1](#0-0) [2](#0-1) 

However, `PullRequestReview.renderFooterContent` passes the API-supplied `review.html_url` (untrusted, attacker-controllable if the API object is spoofed/MITM'd) straight into `LinkButton`'s `uri` prop with no scheme validation: [3](#0-2) 

`LinkButton.onClick` calls `shell.openExternal(uri)` unconditionally — there is no `https?:` check here, unlike the markdown link interceptor: [4](#0-3) 

That call goes through `app-shell.ts`'s `openExternal`, proxied over IPC to the main process handler `open-external` in `main.ts`: [5](#0-4) 

Critically, that main-process handler only uses the `http(s)://` prefix check to decide whether to **log** the URL — it does **not** use it to block or allow the call. `shell.openExternal(path)` (Electron's real API, which can invoke arbitrary registered URL-scheme handlers, `file://` targets, or on Windows UNC/executable paths) is invoked for **any** string regardless of scheme: [5](#0-4) 

`ValidNotificationPullRequestReview` is just `IAPIPullRequestReview` narrowed by `state`, with no sanitization/validation of `html_url`'s scheme or shape performed anywhere in the notification pipeline: [6](#0-5) 

**Where this breaks down**: markdown *body* rendering is properly sandboxed and DOMPurify-sanitized, and markdown link clicks are gated to `http(s)` in `SandboxedMarkdown.setupLinkInterceptor`. But the "Open in Browser" `LinkButton` bound to `review.html_url` bypasses that same-scheme discipline entirely, and the IPC handler on the main-process side that ultimately calls Electron's `shell.openExternal` performs no allowlisting either — it only conditionally logs. So if an attacker can control the `html_url` field of a PR review object returned from (or spoofed as) the GitHub API — a scenario explicitly listed as in-scope ("the attacker controls a...GitHub API object") — they can set it to a non-`http(s)` value and reach the unfiltered `shell.openExternal` call once the user clicks "Open in Browser."

This is a real gap, but note the impact is bounded by the semantics of Electron's `shell.openExternal`: it does not directly execute arbitrary code from a URL string by itself; on most platforms it invokes the OS's URL-scheme dispatch (e.g., `mailto:`, custom app protocol handlers) or opens `file://` targets in the default file-associated app. This can be abused for local file disclosure/UNC-path or protocol-handler attacks depending on OS/installed handlers, but it is not itself a Node/IPC/JS execution primitive inside the Electron renderer sandbox — the "escape" here is a missing-URL-scheme-allowlist bug in a privileged capability (`shell.openExternal`), not a markdown/DOM sanitizer bypass.

### Title
Missing URL-scheme validation lets attacker-controlled `html_url` from a PR review reach `shell.openExternal` unfiltered - (File: `app/src/main-process/main.ts`, `app/src/ui/lib/link-button.tsx`, `app/src/ui/notifications/pull-request-review.tsx`)

### Summary
`PullRequestReview`'s "Open in Browser" button binds directly to the API-provided `review.html_url` via `LinkButton`, which calls `shell.openExternal()` with no scheme check. The main-process `open-external` IPC handler also does not enforce an `http(s)` allowlist — it merely logs when the scheme happens to be `http(s)`, but calls Electron's `shell.openExternal` regardless of scheme.

### Finding Description
`review.html_url` originates from the GitHub API PR-review payload and is treated as trusted display data. `renderFooterContent` in `PullRequestReview` passes it straight to `<LinkButton uri={review.html_url}>`. `LinkButton.onClick` calls `shell.openExternal(uri)` unconditionally with no protocol check, unlike `SandboxedMarkdown`'s link interceptor which restricts to `/^https?:/`. The renderer-side `shell.openExternal` wrapper proxies to IPC channel `open-external`, whose main-process handler in `main.ts` checks for the `http://`/`https://` prefix only to decide whether to write a log line, then unconditionally calls Electron's `shell.openExternal(path)`.

### Impact Explanation
If the API object (`review.html_url`) can be manipulated by an attacker (compromised/malicious GitHub API response, proxy MITM, or a similarly crafted notification payload), a non-`http(s)` value (e.g. a registered custom protocol, or a `file://` path) would reach `shell.openExternal` unfiltered when the user clicks "Open in Browser." Depending on installed protocol handlers/OS behavior this can enable local file exposure or protocol-handler abuse. This does not directly grant JS/Node execution inside the renderer sandbox and is not itself an IPC-injection primitive — it's a missing-allowlist issue in a privileged capability.

### Likelihood Explanation
Requires the attacker to control the `html_url` field of a `PullRequestReview` API object and the user to click "Open in Browser" — a single explicit user action on attacker-supplied notification content, which fits the described threat model of "the attacker controls ... a GitHub API object."

### Recommendation
Enforce an `http(s)`-only scheme allowlist consistently everywhere `shell.openExternal` is reachable from untrusted content: validate `review.html_url` (and other API-supplied `*_url` fields) before passing into `LinkButton`, and make the `open-external` IPC handler in `main.ts` reject (not just log) non-`http(s)` schemes, mirroring the check already used in `SandboxedMarkdown.setupLinkInterceptor`.

### Proof of Concept
1. Serve/spoof a `PullRequestReview` notification payload where `html_url` is set to a non-`http(s)` value (e.g., a registered custom protocol URI or `file://` path).
2. Trigger the review notification dialog so `PullRequestReview` renders with this `review`.
3. Click "Open in Browser" in the footer, which calls `LinkButton.onClick` → `shell.openExternal(uri)` → IPC `open-external` → Electron's `shell.openExternal(path)` with no scheme gating.
4. Observe the value is passed to the OS handler dispatch without validation, unlike the `https?:`-gated path used for in-body markdown links.

import { IAPIPullRequestReview } from './api'

export type ValidNotificationPullRequestReviewState =
  | 'APPROVED'
  | 'CHANGES_REQUESTED'
  | 'COMMENTED'

export type ValidNotificationPullRequestReview = IAPIPullRequestReview & {
  state: ValidNotificationPullRequestReviewState
}

/**
 * Returns whether or not the given review is valid from a notifications point
 * of view: in order to get a notification from a review, it must be approved,
 * changes requested, or commented.
 */
export function isValidNotificationPullRequestReview(
  review: IAPIPullRequestReview
): review is ValidNotificationPullRequestReview {
  return (
    review.state === 'APPROVED' ||
    review.state === 'CHANGES_REQUESTED' ||
    review.state === 'COMMENTED'
  )
}
