### Title
Attacker-controlled preprocess/share vector length causes out-of-bounds indexing and panic in Bitcoin `TransactionSignMachine` - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The OpenEXR advisory describes a decoder that computes element offsets from attacker-influenced sizes and then indexes outside the allocated backing store. The analog in Serai's in-scope code is in `TransactionSignMachine::sign` and `TransactionSignatureMachine::complete`, which index into a per-participant `Vec<Preprocess>` / `Vec<SignatureShare>` supplied entirely by a remote signer. The length of that vector is never checked against `self.sigs.len()` (the number of transaction inputs), so a participant who supplies a short vector causes an out-of-bounds `Vec` index (`commitments[c]`) or a `remove(0)` on an empty `Vec`, panicking the local signing node mid-protocol.

### Finding Description
`TransactionSignMachine::read_preprocess` forwards to each per-input `AlgorithmSignMachine` and returns `Vec<Preprocess<Secp256k1, ()>>`, whose length is whatever the sender encoded — there is no length field tying it to the input count. In `sign`, the code re-buckets the per-participant vectors by input index and indexes them blindly: `commitments.iter().map(|(l, commitments)| (*l, commitments[c].clone()))` for `c in 0 .. self.sigs.len()` [1](#0-0) . If any participant's preprocess vector has fewer than `self.sigs.len()` elements, `commitments[c]` panics with an out-of-bounds index before any share is produced.

The same unchecked-length pattern exists in `TransactionSignatureMachine::complete`, which does `shares.iter_mut().map(|(l, shares)| (*l, shares.remove(0)))` once per input [2](#0-1) . A participant returning a `Vec<SignatureShare>` with fewer than the input count (or an empty vector) makes `remove(0)` panic.

Like the OpenEXR bug, a length/quantity the decoder never validated is used to index storage sized by a different quantity; here the consequence is a panic (Rust bounds check) rather than a wrapped-pointer write, but the root cause — trusting an attacker-controlled element count against an independently-sized container — is identical.

### Impact Explanation
Any participant in a Bitcoin threshold-signing session can send a malformed preprocess or share vector and deterministically crash every honest signer that calls `sign`/`complete`, aborting the signing attempt. In a threshold multisig where signing machines may hold ephemeral nonce state, a panic mid-`sign` can also strand nonces (though nonce reuse does not result, since the protocol aborts). This is an availability impact on the in-scope `networks/bitcoin` wallet path reachable purely with untrusted bytes fed to `read_preprocess`/`read_share` and the `sign`/`complete` APIs, matching the unprivileged reachability requirement. Severity: Medium — no key material, forged signature, or incorrect verification results; the effect is a reachable denial of service of the signing protocol.

### Likelihood Explanation
Triggering requires only that a signing participant — who is already able to submit arbitrary preprocess/share blobs — send a truncated vector. No collusion, no honest-party misbehavior, and no control over the transaction is needed. However, the effect is bounded to aborting that signing attempt and panicking the processing task, so likelihood of meaningful damage beyond a retryable DoS is moderate.

### Recommendation
Validate the vector length before indexing: in `sign`, check `commitments.values().all(|v| v.len() == self.sigs.len())` and return a `FrostError` instead of indexing; in `complete`, verify `shares.len() == self.sigs.len()` per participant before `remove(0)`. Alternatively, iterate with `get(c)`/`pop()` and map `None` to a `FrostError::InvalidShare`-style error so malformed input yields a blameable protocol error rather than a panic.

### Proof of Concept
```rust
// A malicious participant in a t-of-n SignableTransaction::multisig session
// serializes a preprocess Vec with 0 elements instead of one per input:
let mut buf = vec![];
// Vec<Preprocess<Secp256k1, ()>> with len < tx.input.len(), e.g. empty
buf.extend(&0u32.to_le_bytes()); // however each Preprocess is framed, simply truncate

// The victim reads it via TransactionSignMachine::read_preprocess, then calls sign().
// Inside sign (send.rs:364-371):
//   for c in 0 .. self.sigs.len() { ... commitments[c].clone() ... }
// commitments[c] indexes out of bounds -> panic ("index out of bounds").
//
// Same for complete(): a share Vec with len 0 makes shares.remove(0) panic
// ("removal index (is 0) should be < len (is 0)").
```

Caveat: I could not fully confirm the serialization framing of `Preprocess`/`SignatureShare` vectors (whether `AlgorithmMachine::read_preprocess` reads a length prefix per participant or a fixed sequence); the panic path at `send.rs:368` and `send.rs:419` is unconditional on a length mismatch regardless of framing, but the exact wire bytes to produce the short vector depend on that framing.
