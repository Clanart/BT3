### Title
CW20-wrapper-for-ERC20 pointer contract does not validate the boolean return value of `transfer`/`transferFrom` on the underlying ERC20, allowing weird-ERC20 tokens to desync CW20 accounting - (File: example/cosmwasm/cw20/src/contract.rs)

### Summary
The Sei CW20-wraps-ERC20 pointer contract forwards `transfer`/`transferFrom` calls to the wrapped ERC20 token via an `EvmMsg::DelegateCallEvm` submessage, but only checks that the delegatecall did not revert. It never decodes/validates the ABI-encoded `bool` return value that ERC20 requires for success. Any ERC20 token that returns `false` instead of reverting on a failed transfer (a well-known "weird ERC20" pattern, e.g. tokens with blacklists, pausable transfers, or non-standard implementations) will cause the wrapper to treat the operation as successful even though no tokens moved.

### Finding Description
`transfer()` and `transfer_from()` in `example/cosmwasm/cw20/src/contract.rs` build the ABI payload for the wrapped ERC20's `transfer`/`transferFrom` and wrap it in `EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload }`, then immediately return a `Response` with `from`/`to`/`amount` attributes and add the message: [1](#0-0) [2](#0-1) 

The `DelegateCallEvm` message is routed through `MsgInternalEVMDelegateCall` and executed by `Keeper.HandleInternalEVMDelegateCall` → `Keeper.CallEVM`. That path only surfaces failure when the EVM message actually **reverts** (`res.Err != nil`); it returns the raw `ReturnData` bytes to the caller without any interpretation of a `bool` return value: [3](#0-2) 

Because CosmWasm's `wasmkeeper` message handling only fails a submessage on revert/error (not on the semantic content of a successful call's return data), a CW20 `transfer`/`transferFrom` call that internally invokes a non-compliant ERC20 (one that returns `false` on failure instead of reverting, similar to the tokens mentioned in the referenced report — USDT-style, or any custom "weird" ERC20 deployed on Sei EVM and subsequently wrapped as a CW20 pointer via the public `RegisterPointer`/`AddCW20`-style flow) will succeed at the EVM level while the actual token balance is unchanged. The CW20 wrapper contract emits `transfer`/`transfer_from` attributes and completes the wasm execution as if the transfer had occurred, with no reconciliation against the real ERC20 balance.

This mirrors the exact bug class from the referenced Footium report: contracts treating a `transfer`/`transferFrom` call as successful purely because the call did not throw, without checking the boolean return, is unsafe for ERC20 implementations that signal failure via return value rather than revert.

### Impact Explanation
Any user can deploy or interact with an ERC20 token on Sei's EVM that implements non-standard transfer semantics (returns `false` instead of reverting on failure, e.g., blacklist/pause/insufficient-balance edge cases) and then register/interact with the CW20 wrapper pointer for that token. Because the wrapper's `transfer`/`transferFrom` submessages are considered successful whenever the delegatecall does not revert, downstream CW20 consumers (other contracts, DEXes, integrations relying on the wrapper's event/attribute output) will believe a transfer succeeded when no value actually moved. This can lead to accounting desync between the CW20 wrapper's advertised state and the real ERC20 balances, enabling fund loss for counterparties who rely on the wrapper's success signal (e.g., crediting a trade, releasing an escrow, or minting cross-token value) without the underlying tokens having actually moved.

### Likelihood Explanation
Reachable by any unprivileged EVM/CosmWasm user: deploy or use an existing non-standard ERC20 contract, wrap it via the ERC20-wraps-as-CW20 example pointer contract path, and call `transfer`/`transfer_from`/`send`/`send_from`. No privileged access or governance action is required — only a public transaction and a token whose `transfer` returns `false` on failure rather than reverting.

### Recommendation
In the CW20 wrapper's `transfer`/`transfer_from` (and `send`/`send_from`) handlers, after issuing the `DelegateCallEvm`, decode the ABI `bool` return value from the ERC20 call and fail the CosmWasm execution (return an error / reply-and-check pattern) if the returned value is `false` or if the return data is malformed, following the SafeERC20-style pattern (treat empty return data linked with a successful call as success only when the token has no return value, otherwise require an explicit `true`). Alternatively, verify actual balance deltas (query the ERC20 balance before and after the delegatecall) before considering the transfer successful.

### Proof of Concept
1. Deploy a "weird" ERC20 contract on Sei's EVM whose `transfer(address,uint256)` and `transferFrom` return `false` (do not revert) when, e.g., the recipient is blacklisted or the transfer otherwise fails internally.
2. Wrap this ERC20 as a CW20 using the CW20-wraps-ERC20 pointer pattern (`example/cosmwasm/cw20`), storing the ERC20 address via `ERC20_ADDRESS` in `instantiate`.
3. Call `ExecuteMsg::Transfer { recipient, amount }` where the underlying ERC20 `transfer` call returns `false` for that recipient (e.g., recipient blacklisted).
4. Observe that `transfer()` in `contract.rs` still returns `Ok(res)` with `action = "transfer"` attributes and the `DelegateCallEvm` submessage does not revert (confirmed via `CallEVM` in `x/evm/keeper/evm.go`, which only errors on `res.Err != nil`), even though the real ERC20 balance for the sender/recipient did not change — demonstrating the accounting desync. fn transfer(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

pub fn transfer_from(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    owner: String,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&owner)?;
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_from_payload(owner.clone(), recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", owner)
        .add_attribute("to", recipient)
        .add_attribute("by", info.sender)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

func (k *Keeper) CallEVM(ctx sdk.Context, from common.Address, to *common.Address, val *sdk.Int, data []byte) (retdata []byte, reterr error) {
	if ctx.IsEVM() && !ctx.EVMEntryViaWasmdPrecompile() {
		return nil, errors.New("sei does not support EVM->CW->EVM call pattern")
	}
	if to == nil && len(data) > params.MaxInitCodeSize {
		return nil, fmt.Errorf("%w: code size %v, limit %v", core.ErrMaxInitCodeSizeExceeded, len(data), params.MaxInitCodeSize)
	}
	if to != nil && to.Cmp(common.HexToAddress(solo.SoloAddress)) == 0 {
		return nil, errors.New("cannot call Solo precompile via CosmWasm")
	}
	value := utils.Big0
	if val != nil {
		if val.IsNegative() {
			return nil, sdkerrors.ErrInvalidCoins
		}
		value = val.BigInt()
	}
	// This call was not part of an existing StateTransition, so it should trigger one
	executionCtx := ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx)).WithEVMEntryViaWasmdPrecompile(false)
	stateDB := state.NewDBImpl(executionCtx, k, false)
	gp := k.GetGasPool()
	evmMsg := &core.Message{
		Nonce:     stateDB.GetNonce(from), // replay attack is prevented by the AccountSequence number set on the CW transaction that triggered this call
		GasLimit:  k.getEvmGasLimitFromCtx(ctx),
		GasPrice:  utils.Big0, // fees are already paid on the CW transaction
		GasFeeCap: utils.Big0,
		GasTipCap: utils.Big0,
		To:        to,
		Value:     value,
		Data:      data,
		From:      from,
	}
	// should not increment nonce since this isn't a transaction
	res, err := k.applyEVMMessage(ctx, evmMsg, stateDB, gp, false)
	if err != nil {
		return nil, err
	}
	k.consumeEvmGas(ctx, res.UsedGas)
	if res.Err != nil {
		return nil, res.Err
	}
