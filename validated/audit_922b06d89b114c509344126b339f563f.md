### Title
Payout OP_RETURN operator-attribution is not covered by the withdrawal signature, letting anyone null out `payout_payer_operator_xonly_pk` and permanently freeze a deposit - (`core/src/verifier.rs::update_finalized_payouts`, `core/src/task/payout_checker.rs::PayoutCheckerTask::run_once`)

### Summary
The payout transaction's OP_RETURN (which records which operator fronted a withdrawal) is not covered by the user's withdrawal signature, because that signature uses `TapSighashType::SinglePlusAnyoneCanPay`, which only commits to input 0 and output 0. Anyone can therefore build a competing transaction that reuses the user's signature/input0/output0 but omits or corrupts the OP_RETURN, get it confirmed instead of the operator's, and cause `payout_payer_operator_xonly_pk` to be permanently `NULL` for that withdrawal index, which no operator's reimbursement query (and no optimistic-payout retry, since input0 is now spent) can ever match.

### Finding Description
The binding that must hold is: **for every withdrawal index `i` whose on-chain payout output0 pays the committed user amount, exactly one identifiable party (an operator xonly_pk, or "optimistic/none") must be recorded as `payout_payer_operator_xonly_pk`, and that identity must remain reachable by some settlement path** (`operator reimbursement` via kickoff, or `optimistic_payout`).

`Operator::withdraw` builds the payout tx via `create_payout_txhandler`, which adds output0 (user payout), an anchor, and an OP_RETURN output carrying the operator's xonly pubkey [1](#0-0) . The *only* consensus-enforced signature on this transaction is the user's `SinglePlusAnyoneCanPay` signature over input0, which per `calculate_pubkey_spend_sighash` commits solely to `Prevouts::One(txin_index, ...)` and, under `SIGHASH_SINGLE` semantics, only the output at the same index (output0) [2](#0-1) [3](#0-2) . The anchor and OP_RETURN outputs, and any additional funding inputs, are not committed to by this signature at all.

Consequently, anyone holding the mempool-visible signed input0+output0 pair can build their own transaction: input0 (with the reused signature) + their own funding input(s) → output0 (identical, required by SIGHASH_SINGLE) + no OP_RETURN or a malformed one, and get it confirmed instead of/ahead of the operator's broadcast. When the block syncer processes this transaction in `update_finalized_payouts`, it looks for the first OP_RETURN output and parses it with `parse_op_return_data`/`XOnlyPublicKey::from_slice`; if missing or invalid, `operator_xonly_pk` becomes `None`, and `payout_payer_operator_xonly_pk` is stored as `NULL` in the `withdrawals` row for that index [4](#0-3) [5](#0-4) .

`PayoutCheckerTask::run_once` then queries `get_first_unhandled_payout_by_operator_xonly_pk` filtered by `WHERE payout_payer_operator_xonly_pk = $1`, which can never match `NULL` [6](#0-5) [7](#0-6) . No operator ever calls `handle_finalized_payout`/`mark_payout_handled` for that index, so no kickoff is ever produced, and the `Reimburse` transaction (which requires the kickoff's `ReimburseInKickoff` output as an input) can never be constructed for that deposit [8](#0-7) .

Because the withdrawal's dust input (input0) is now already spent by the attacker's transaction, the alternative settlement path, `create_optimistic_payout_txhandler`, which also spends the same `input_utxo` outpoint, can no longer be broadcast either — that outpoint is gone [9](#0-8) . With both the operator-kickoff route and the optimistic-payout route foreclosed, the deposit's `MoveToVault`/`DepositInMove` UTXO can never be spent by any legitimate transaction in the protocol — it is permanently frozen.

Existing guards do not stop this: `SECP.verify_schnorr` only checks the user's signature over input0/output0 (by design, to allow fee-bumping of the payout), and there is no on-chain commitment binding the OP_RETURN/operator identity to that signature. No uniqueness constraint or re-check prevents the confirmed transaction's OP_RETURN from being empty or corrupt.

### Impact Explanation
This is Critical: a legitimate deposit's move-to-vault UTXO becomes permanently unspendable, since neither the operator-reimbursement path (kickoff→reimburse) nor the optimistic-payout path can ever be completed for that withdrawal index once the malformed transaction confirms and consumes the withdrawal UTXO. The attack is repeatable per withdrawal (each withdrawal index is an independent target), so an attacker could apply it to every payout they observe in flight, permanently freezing the corresponding vault funds and denying the operator (or verifiers via optimistic payout) any way to settle that specific withdrawal.

### Likelihood Explanation
The attacker needs to observe an operator's unconfirmed payout transaction (or any withdrawal signature broadcast off-chain to operators, if leaked/observed), extract input0's signature (valid under `SinglePlusAnyoneCanPay`), and craft a competing transaction with their own funding input(s) to cover output0's value, then get it mined ahead of/instead of the honest transaction. This requires the attacker to front the same BTC value as output0 themselves (paid to the withdrawing user, not to themselves) plus fees, and to win a race for confirmation (e.g., via a higher fee or full-RBF-enabled relay), which is a real cost but not otherwise prevented. It requires no special privileges, keys, or majority hashrate — only broadcasting a valid Bitcoin transaction, matching the stated unprivileged attacker capabilities.

### Recommendation
Bind the operator/settlement identity to the same signature that authorizes spending the withdrawal UTXO, e.g., require `AllPlusAnyoneCanPay` (or `Default`/`All`) so the OP_RETURN output is covered by the user's signature, or otherwise commit to the OP_RETURN's presence/content as part of what the withdrawal signature protects. Alternatively, treat "OP_RETURN missing/invalid" as an actionable error path rather than silently downgrading to `NULL`/optimistic in `update_finalized_payouts`, and provide a recovery mechanism (e.g., permit reimbursement/optimistic payout to proceed keyed off the spending transaction and its inputs, verified against pre-registered withdrawal commitments, rather than solely off a mutable OP_RETURN).

### Proof of Concept

1. Set up a test DB and insert a `withdrawals` row for index `i` with a real `withdrawal_utxo` (as in `update_get_payout_txs_from_citrea_withdrawal`) [10](#0-9) .
2. Build a payout tx `tx_honest` spending that UTXO with an OP_RETURN encoding operator O's xonly_pk in output index 2 (mirroring `create_payout_txhandler`) and record it via `insert_spent_utxo`/mock block cache as the payout for idx `i`.
3. Build a second transaction `tx_attacker` spending the *same* withdrawal outpoint with the same output0 (user payout, identical script/amount), but no OP_RETURN (or an invalid one) instead of `tx_honest`.
4. Feed `tx_attacker` (not `tx_honest`) into `update_finalized_payouts`'s block cache and call it directly (or call `update_payout_txs_and_payer_operator_xonly_pk` with `operator_xonly_pk = None` for idx `i`, matching what `update_finalized_payouts` would compute since `get_first_op_return_output`/`parse_op_return_data` fails).
5. Assert: `db.get_first_unhandled_payout_by_operator_xonly_pk(None, O_xonly_pk).await` returns `None` even though `withdrawals.idx = i` has `payout_txid IS NOT NULL` and the spent UTXO's output0 matches the amount O was supposed to front — i.e., `payout_payer_operator_xonly_pk` (actual: `NULL`) ≠ `O_xonly_pk` (expected binding), demonstrating idx `i` is excluded forever from O's (and every other operator's) unhandled-payout queue, with no code path to recover it.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
