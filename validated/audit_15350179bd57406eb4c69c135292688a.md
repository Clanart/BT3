### Title
Unauthenticated on-chain mirror records force DataLayer nodes into attacker-controlled SSRF fetches - (File: `chia/data_layer/data_layer_wallet.py`)

### Summary
`DataLayerWallet.create_new_mirror()` lets any wallet holder create a DataLayer "mirror" coin for *any* `launcher_id` (store id), including stores they do not own, with an arbitrary list of URLs, and no ownership or URL validation is performed before broadcasting it on-chain. Once confirmed, every DataLayer node that is subscribed to that store id will pull the mirror's URLs from wallet RPC and automatically issue outbound HTTP requests to them during its periodic sync loop. This lets any unprivileged spend-bundle submitter force other users' DataLayer services to make arbitrary outbound HTTP requests (SSRF) simply by paying the mirror-coin fee/amount — no relationship to the targeted store is required.

### Finding Description
`create_new_mirror()` builds and signs a standard coin spend that creates a mirror coin whose memo encodes `launcher_id` and the caller-supplied `urls`, with **no check that `launcher_id` belongs to the caller**: [1](#0-0) 

Compare this to `batch_insert()`, which *does* enforce store ownership before allowing local mutation: [2](#0-1) 

No equivalent ownership check exists for mirror creation anywhere in the RPC path (`dl_new_mirror` → `create_new_mirror`): [3](#0-2) 

Once the mirror coin is confirmed, any DataLayer node subscribed to that `launcher_id` pulls the URLs unconditionally via `update_subscriptions_from_wallet()`: [4](#0-3) 

and stores them as candidate servers, which `fetch_and_validate()` later randomly selects and connects to via `http_download()`: [5](#0-4) [6](#0-5) 

`http_download()` performs a plain `aiohttp` GET against `server_info.url + "/" + filename` with no restriction on scheme, host, or port (no blocking of loopback/link-local/metadata addresses), so an attacker-chosen URL is dereferenced directly by the victim's DataLayer process.

### Impact Explanation
Any unprivileged wallet user can, for the cost of a mirror-coin fee, cause every DataLayer node that syncs a *targeted store id* (which may belong to someone else) to issue outbound HTTP requests to attacker-chosen destinations, including internal/loopback addresses, cloud metadata endpoints, or other services reachable from the victim's network. This is a classic SSRF primitive triggered purely by broadcasting a spend bundle, matching the report's underlying bug class (CWE-74/CWE-436: attacker-controlled network target reached through a trusted client due to missing validation/authorization of the destination). It does not require compromising the store owner, the wallet, or any peer — only submitting a standard transaction.

### Likelihood Explanation
Likelihood is high: creating a mirror coin is a normal, permissionless wallet operation (`dl_new_mirror`/`create_new_mirror`), requires only a small fee/amount, and does not require the caller to own or interact with the targeted store in any other way. Any DataLayer service subscribed to (or replicating) that store will automatically attempt the fetch during its regular `periodically_manage_data()` cycle.

### Recommendation
- Enforce that the caller-supplied `launcher_id` in `create_new_mirror()`/`dl_new_mirror` is owned/tracked appropriately, or otherwise rate-limit/validate mirror URLs before they are trusted as fetch targets.
- In `http_download()`/`fetch_and_validate()`, validate and restrict destination URLs (scheme allow-list, DNS re-resolution/pinning, blocking of private/loopback/link-local/metadata ranges) before making outbound requests derived from on-chain mirror data.
- Treat mirror URLs as fully untrusted network input (as already documented in the module's own fragility notes) and apply the same SSRF hardening used for other externally supplied server locations.

### Proof of Concept
1. Attacker wallet calls `dl_new_mirror` (via RPC or CLI) with `launcher_id` set to a victim store id they do not own, `urls=["http://169.254.169.254/latest/meta-data/"]` (or any internal address), and pays the required fee/amount.
2. The transaction confirms; a mirror coin now exists on-chain associating the victim's store id with the attacker URL, as shown in `test_mirrors`: [7](#0-6) 
3. Any DataLayer node subscribed to the victim's store id runs `update_subscriptions_from_wallet()` and picks up the new URL, then `fetch_and_validate()`/`http_download()` issues an outbound `GET` request to that URL as part of normal sync — with no ownership or destination validation performed anywhere in this path.

    async def dl_new_mirror(
        self,
        request: DLNewMirror,
        action_scope: WalletActionScope,
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> DLNewMirrorResponse:
        """Add a new on chain message for a specific singleton"""
        if self.service.wallet_state_manager is None:
            raise ValueError("The wallet service is not currently initialized")

        dl_wallet = await self.service.wallet_state_manager.get_dl_wallet()
        async with self.service.wallet_state_manager.lock:
            await dl_wallet.create_new_mirror(
                request.launcher_id,
                request.amount,
                Mirror.encode_urls(request.urls),
                action_scope,
                fee=request.fee,
                extra_conditions=extra_conditions,
            )

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
