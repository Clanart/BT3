### Title
Insufficient validation in `ThresholdKeys::read` allows injection of inconsistent threshold state with an attacker-chosen group key - (File: crypto/dkg/src/lib.rs)

### Summary

Analogous to CVE-2022-2619 (insufficient validation of untrusted input allowing injection into a privileged context), `ThresholdKeys::read` deserializes attacker-supplied bytes into a privileged key object without validating that the components are mutually consistent. Specifically, it never checks that `secret_share` corresponds to the claimed verification share for this participant (`secret_share * G == verification_shares[i]`), and `ThresholdKeys::new` computes `group_key` solely from `verification_shares[1..=t]`, leaving the remaining shares entirely unconstrained.

### Finding Description

`ThresholdKeys::read` reads `t`, `n`, `i`, an interpolation method, a `secret_share` scalar, and `n` verification-share points, then calls `ThresholdKeys::new` (crypto/dkg/src/lib.rs:574-632). `ThresholdKeys::new` validates only:

- `verification_shares.len() == n` and indices `<= n` (lib.rs:355-365)
- `t == n` when `Interpolation::Constant` is used (lib.rs:367-374)
- `t <= n`, `i <= n`, nonzero params via `ThresholdParams::new` (lib.rs:166-179)

It then derives `group_key` as `sum_{j=1..=t} verification_shares[j] * interpolation_factor(j)` (lib.rs:376-378). Missing validations:

1. **No secret-share/verification-share binding.** Nowhere is `secret_share * C::generator() == verification_shares[i]` checked. A crafted blob can set `secret_share = x` and `verification_shares[i] = y*G` for `x != y`, producing keys whose own share is inconsistent with the declared public share.
2. **Verification shares for participants `t+1..=n` are never bound to the group key or to any polynomial commitment.** An attacker can declare arbitrary points there, silently redefining who the other participants are and what their public shares are, without affecting `group_key`.
3. **No global consistency check.** The code itself acknowledges the gap: `AlgorithmSignatureMachine::complete` can return `FrostError::InternalError("everyone had a valid share yet the signature was still invalid")`, documented as only reachable by "deserializing a semantically invalid FrostKeys" (crypto/frost/src/sign.rs:491-494) — i.e., the signing code knows deserialized keys can be semantically invalid, yet deserialization performs no semantic validation.

Because `read_F`/`read_G` only enforce canonical encodings (crypto/ciphersuite/src/lib.rs:74-101), every field of the blob is attacker-malleable within canonical form, and the crafted state is then injected into the privileged signing/scanning context: `group_key()`, `view()`, `offset()`, and downstream Bitcoin `Scanner`/output matching all operate on the attacker-defined group key.

### Impact Explanation

An unprivileged party who supplies untrusted bytes to `ThresholdKeys::read` (e.g., a key blob or checkpoint restored into a validator/processor) can inject a `ThresholdKeys` whose `group_key` does not correspond to any real threshold sharing:

- **Funds reported received that are not spendable.** Any address/scanner registration derived from the forged `group_key()` credits deposits to a key that no quorum of real shares can sign for, since the declared `secret_share`/verification shares don't form a consistent Shamir sharing. Deposits are permanently locked.
- **Attacker-biased group key.** An attacker can choose `verification_shares[1..=t]` so that `sum V_j * l_j = A*G` for a discrete log `A` they know, making the apparent group key attacker-controlled. Whether the honest holder's share verifies under the forged `verification_shares[i]` depends on the setup, but in the worst case the attacker also writes a self-consistent `secret_share`/`verification_shares[i]` pair, fully determining the effective signing secret while the honest operator believes they hold an independent share of a different key.
- **Subverted participant set.** Arbitrary `verification_shares[t+1..=n]` let the attacker define fictitious co-signers; combined with `view()`'s per-set interpolation (lib.rs:463-533), signatures can be produced for quorums that never participated in any real DKG.

### Likelihood Explanation

Exploitation requires the attacker to supply (or tamper with) serialized `ThresholdKeys` consumed by a victim node — the rules explicitly scope untrusted bytes to `ThresholdKeys::read` as reachable. All serialized fields are canonically encoded scalars/points that `read_F`/`read_G` accept, so crafting the blob is trivial; no cryptographic break is needed, only the absence of a consistency check. The resulting state is silently accepted (`ThresholdKeys::new` returns `Ok`) and only fails later at signature completion, if it ever does. Rated Medium, matching the source advisory.

### Recommendation

In `ThresholdKeys::new` (or `ThresholdKeys::read`), add semantic validation:

1. Check `secret_share * C::generator() == verification_shares[&i]` and reject otherwise.
2. For Lagrange interpolation, either bind all `n` verification shares to a polynomial commitment or document/derive the group key consistently from the full share set rather than only `1..=t`; at minimum, verify shares are mutually consistent (e.g., all lying on a degree `t-1` polynomial) so that participants `> t` cannot be arbitrary.
3. Reject identity/zero verification shares and zero `secret_share`, which are currently accepted since `read_G`/`read_F` permit them.

### Proof of Concept

```rust
use std::io::Read;
use ciphersuite::Ciphersuite;
use dkg::{ThresholdKeys, Participant};
use zeroize::Zeroizing;

// C: any in-scope Ciphersuite, e.g. dalek_ff_group::Ed25519
fn forge<C: Ciphersuite>() -> ThresholdKeys<C> {
    let t: u16 = 2;
    let n: u16 = 2;

    let mut buf = vec![];
    buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
    buf.extend(C::ID);
    buf.extend(t.to_le_bytes());
    buf.extend(n.to_le_bytes());
    buf.extend(1u16.to_le_bytes());      // i = 1
    buf.push(1);                          // Interpolation::Lagrange

    // secret_share inconsistent with verification_shares[1]
    let x = C::F::from(7u64);
    buf.extend(x.to_repr().as_ref());

    // verification_shares[1] = y*G with y != x; crafted so that
    // V1 * l1 + V2 * l2 = A*G for a known A (attacker-chosen group key)
    let l1 = C::F::from(2u64) * C::F::from(1u64).invert().unwrap(); // Lagrange for set {1,2}
    let l2 = C::F::from(1u64) * (-C::F::ONE).invert().unwrap();
    let a = C::F::from(9u64);              // attacker-known group secret
    let v1 = C::generator() * C::F::from(5u64);
    let v2 = (C::generator() * a - v1 * l1) * l2.invert().unwrap();
    buf.extend(v1.to_bytes().as_ref());
    buf.extend(v2.to_bytes().as_ref());

    let keys = ThresholdKeys::<C>::read::<&[u8]>(&mut buf.as_ref()).unwrap();
    // Accepted despite: secret_share*G != verification_shares[1]
    assert_eq!(keys.group_key(), C::generator() * a);
    keys
}
```

The resulting `keys` deserialize successfully, report `group_key() == a*G` for attacker-known `a`, yet fail or misbehave at signing time — the exact condition `AlgorithmSignatureMachine::complete` admits is reachable only via "deserializing a semantically invalid FrostKeys" (crypto/frost/src/sign.rs:491-494).
