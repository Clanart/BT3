### Title
Excess native `msg.value` sent to `EvmHost.dispatch()` for POST/GET requests is permanently stuck, never refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary

### Finding Description
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` allow a caller to pay the relayer fee in native token by forwarding `msg.value` and letting the contract swap it into `feeToken()` via Uniswap V2: [1](#0-0) 

Both functions call `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` (and the analogous call for `get.fee`), passing the *entire* `msg.value` as the swap budget while only `post.fee`/`get.fee` worth of tokens is actually required: [2](#0-1) 

`UniswapV2Router02.swapETHForExactTokens` only consumes the ETH needed to produce the exact `amountOut` and refunds any unused ETH — but that refund goes to `msg.sender` of the router call, which is `EvmHost` itself (since `EvmHost` is the one calling the router with `{value: msg.value}`), not to the original transaction caller. `EvmHost.dispatch` never captures the router's return value, never computes the leftover, and never forwards any surplus back to `_msgSender()`.

This is the direct analog of the reported bug: a caller sends native value intending to cover a specific target amount, the underlying execution consumes only part of it, and the difference is retained by the contract instead of being refunded to the payer.

By contrast, the codebase demonstrates the correct pattern elsewhere: `IntentGatewayV2.sol` explicitly captures `amounts[0]` from `swapETHForExactTokens` and refunds the unspent `msgValue` back to `msg.sender`: [3](#0-2) 

`EvmHost.dispatch` for POST/GET requests has no equivalent refund step, confirming this is a real, local, missed-refund path rather than a systemic protocol design choice.

### Impact Explanation
Any user or contract dispatching a Hyperbridge POST/GET request and paying in native token (a documented, supported payment method) who supplies `msg.value` greater than what is strictly needed to purchase `post.fee`/`get.fee` units of the fee token loses the difference permanently to `EvmHost`. Since Uniswap V2 swap output amounts and required input ETH fluctuate with pool price at execution time, callers cannot know the exact required `msg.value` in advance and commonly overprovide as a safety margin (exactly the scenario in the original report, where a limit/price-dependent execution consumes less than the amount sent). The lost ETH accumulates in the host contract with no mechanism in `dispatch()` to return it to depositors. This is unauthorized retention of user funds — a genuine "loss of funds" impact aligned with the bounty scope.

### Likelihood Explanation
Likelihood is high for any unprivileged, ordinary user calling `dispatch()` with native payment, since Uniswap swap pricing is non-deterministic between quote-time and execution-time (block time delay, slippage, MEV). No malicious relayer, prover, or admin is required — this is triggered purely by a normal user/integrator using the documented native-payment dispatch flow with a safety margin on `msg.value`, exactly as the original Router.sol bug required only a normal trader setting a limit price.

### Recommendation
Capture the return value of `swapETHForExactTokens` (`amounts[0]`, the ETH actually spent) in both `dispatch(DispatchPost)` and `dispatch(DispatchGet)`, and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2.sol`.

### Proof of Concept
1. Alice calls `EvmHost.dispatch(DispatchPost{... fee: 100 (feeToken units) ...})` with `msg.value = 1 ether`, expecting the market rate to require roughly 1 ether worth of ETH for 100 feeToken.
2. `EvmHost` calls `IUniswapV2Router02.swapETHForExactTokens{value: 1 ether}(100, [WETH, feeToken], address(this), deadline)`.
3. The pool only requires 0.7 ETH to produce exactly 100 feeToken; the router refunds the remaining 0.3 ETH to `msg.sender` of the swap call, i.e., to `EvmHost`.
4. `EvmHost.dispatch` returns without ever inspecting the swap's actual ETH cost or forwarding the 0.3 ETH surplus back to Alice — it becomes permanently locked in the `EvmHost` contract's balance.
5. Repeating this across dispatch calls (POST or GET) accumulates unrecoverable ETH inside `EvmHost`, with no refund path to any of the original payers. [1](#0-0) [2](#0-1)
