### Title
PedPoP DKG accepts participant encryption keys without proof of possession, enabling share disclosure and misattributed blame - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The Jenkins advisory (CWE-295) is a missing identity-validation bug: a peer's claimed identity (TLS hostname) was never bound to the credential presented. The same shape exists in PedPoP: `EncryptionKeyMessage.enc_key` — the long-term encryption public key a participant claims for the whole DKG — is registered and trusted with no proof of possession binding it to that `Participant`. The Schnorr PoP in `EncryptedMessage` covers only the *per-message* ephemeral `key`, not the registered `enc_key`. A malicious participant can therefore register a victim's (or third party's) encryption public key as their own.

### Finding Description
- `EncryptionKeyMessage::read` deserializes `enc_key: C::G` with no accompanying PoK [1](#0-0) .
- `Encryption::register` → `Decryption::register` inserts `msg.enc_key` into `enc_keys[participant]` unconditionally [2](#0-1) .
- `Encryption::encrypt` encrypts each secret share under `self.decryption.enc_keys[&participant]` — whatever key the peer claimed [3](#0-2) .
- The `pop` field's challenge binds `from`, `msg.key`, and the ciphertext, but never `enc_key` [4](#0-3) ; it is generated fresh by the sender, so it proves nothing about ownership of the registered key [5](#0-4) .
- The code comments acknowledge the related per-message-key co-option attack and mitigate only that case [6](#0-5) , leaving the registration key unauthenticated.

### Impact Explanation
A malicious DKG participant A registers victim V's `enc_pub_key` in its `Commitments` message. Every honest participant then encrypts `share_j(A)` under V's key in `generate_secret_shares` [7](#0-6) .

1. **Key share recovery:** V (who need not be A) can decrypt every `EncryptedMessage` addressed to A and recover A's complete secret share — i.e., A's full threshold-signing capability is leaked to a party who was never entitled to it. If the attacker registers keys of parties it controls, it still achieves misdirection; if it registers an external victim's key, the victim learns A's share.
2. **Misattributed blame / forced abort:** A cannot decrypt its shares and triggers `calculate_share` failure → blame. In `blame_internal`, the honest recipient's DLEq is checked against `self.enc_keys[&decryptor]` (the recipient's real key), which does not match the ciphertext encrypted to V's key, so decryption produces gibberish and the honest *sender* is blamed and removed [8](#0-7) [9](#0-8) .

Both consequences match the accepted impact classes (key share recovery; incorrect blame causing honest-party exclusion).

### Likelihood Explanation
Reachable by any unprivileged DKG participant with public inputs: they simply place a foreign `enc_key` in their broadcast `EncryptionKeyMessage`. No collusion threshold, no broken BFT, no leaked keys required — only the ability to send a malformed registration message, which is exactly the adversary model the DKG's blame machinery exists for. Medium severity: it requires a DKG round and a third party willing/able to observe the misdirected ciphertexts, and share leakage is limited to the impersonating participant's own share unless multiple attackers repeat it.

### Recommendation
Require a Schnorr proof of possession of `enc_key` inside `EncryptionKeyMessage`, bound to `context` and the claimed `Participant` (extend `challenge`/`pop_challenge` style), and verify it in `Decryption::register`/`verify_r1` before inserting into `enc_keys`. Alternatively, derive `enc_key` deterministically from the participant's PoK'd commitment (`commitments[0]`) so the key is cryptographically bound to identity by construction.

### Proof of Concept
Conceptual (within `crypto/dkg/pedpop`):

```rust
// Attacker is participant `a`; victim participant `v` already broadcast its
// EncryptionKeyMessage containing v's enc_pub_key.
let mut forged = victim_msg.clone();          // EncryptionKeyMessage<Commitments>
forged.enc_key = victim_msg.enc_key;          // same key, claimed by `a`
// attacker also supplies its own valid Commitments PoK (it knows coefficient 0)
// verify_r1 registers a -> v's enc_pub_key with no ownership check
secret_share_machine.generate_secret_shares(&mut rng, map_with(a, forged));
// Every honest j encrypts share_j(a) to v's key; v decrypts all of them and
// reconstructs a's secret share. a reports InvalidShare; blame names an
// honest sender because a's message genuinely decrypts to gibberish under j's key.
```

The acceptance test exists already in the codebase's own threat model: `invalidate_msg` shows PoP validity is orthogonal to which `enc_key` was registered [10](#0-9) ; no code path validates `enc_key` ownership at registration.

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}
