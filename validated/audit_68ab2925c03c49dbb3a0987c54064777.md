### Title
Division-by-zero panic in `consolidatedNode.Split` can crash all nodes during block finalization when a validator's total (CN + CL) stake is zero - ([File: kaiax/staking/staking_info.go])

### Summary
`kaiax/staking/staking_info.go`'s `consolidatedNode.Split()` divides by `totalAmount := cnAmount + clAmount` without checking whether that sum is zero. This function is invoked unconditionally (guarded only by `CLStakingInfo != nil`, not by non-zero stake) from the reward-distribution code path (`specWithProposerAndFunds`/`specWithProposerAndFundsFlex`) that runs on every block's `FinalizeState`, which every full node executes as part of consensus state transition.

### Finding Description
`Split()` is defined as: [1](#0-0) 

It computes `totalAmount = cnAmountBig + clAmountBig` and then does `clAmount.Div(clAmount, totalAmount)`. If both the consolidated node's `StakingAmount` (CNStaking) and its `CLStakingInfo.CLStakingAmount` are `0`, `totalAmount` is `0`, and `big.Int.Div` panics on division by zero (Go's `big.Int` division panics for a zero divisor, unlike `Quo`).

The guard for calling `Split()` only checks `cn.CLStakingInfo != nil`, not that the amounts are non-zero: [2](#0-1) [3](#0-2) 

`CLStakingInfo` is attached to a consolidated node purely based on `CLNodeId` matching an AddressBook `NodeId`, independent of the node's staking amount: [4](#0-3) 

And `CLStakingAmount` itself can legitimately be `0` (e.g., rounded down from an amount smaller than 1 KAIA, or if the CL pool has been fully withdrawn): [5](#0-4) 

`cn.StakingAmount` can also be `0` if the validator's CNStaking contract balance is below 1 KAIA (rounded down) while it remains registered in the AddressBook: [6](#0-5) 

`specWithProposerAndFunds`/`specWithProposerAndFundsFlex` are invoked from `getDeferredRewardFullLegacy`/`Kore`/`Flex`, which are called by `GetDeferredReward`, which is invoked every block from `FinalizeState`: [7](#0-6) 

`FinalizeState` runs on the consensus-critical block-processing path (both when a node mines/proposes a block and when it validates an incoming block), with no `recover()` wrapping this specific computation anywhere in `blockchain/state_processor.go`, `kaiax/reward`, or `kaiax/staking`. A single block whose designated proposer happens to be a validator with both zero CNStaking and zero CL stake (a state reachable simply by unstaking/withdrawing from CL, actions any staker/CL depositor can trigger) would cause every honest full node processing that block to panic and crash simultaneously.

This is directly analogous to the referenced Osmosis bug: an unguarded arithmetic operation tied to a per-block/per-epoch consensus liquidity accounting step panics on an edge-case input (there, in `AfterEpochEnd`; here, in `FinalizeState`'s CL-aware reward split), taking down the chain.

### Impact Explanation
A panic inside block finalization is unrecoverable in the current code path and crashes the node process. Because `FinalizeState` executes identically and deterministically on every honest node for every block (both proposer and validators), this results in a chain-wide halt (all nodes crash on the same block), which is a Critical-severity liveness failure requiring a hotfix/rollback to recover, analogous in effect to the original Osmosis panic that this hotfix (#6231) targeted.

### Likelihood Explanation
The precondition — a proposer-eligible validator whose CNStaking balance is below 1 KAIA (rounds to 0) while it also has a CL pool with CL stake below 1 KAIA (rounds to 0), but the validator is still selected to propose a block due to stale/cached `StakingInfo` from the staking-update interval — is a plausible, self-triggerable edge case for any Consensus Node operator or CL depositor who withdraws stake down toward zero rather than an obviously adversarial action, making it moderately likely to be hit in practice, especially as more validators adopt consensus liquidity (Prague/KIP-226).

### Recommendation
Add a zero-check guard in `consolidatedNode.Split()` before dividing by `totalAmount` (return `(amount, big.NewInt(0))` or `(big.NewInt(0), big.NewInt(0))` when `totalAmount.Sign() == 0`), and/or guard call sites in `getter.go` to skip the CL split when both `cn.StakingAmount` and `cn.CLStakingInfo.CLStakingAmount` are zero, mirroring the osmosis fix pattern of defensively handling the zero-stake edge case before it can panic on the consensus path.

### Proof of Concept
1. A Consensus Node registers a CL pool via CLRegistry (`CLStakingInfo` created) and later withdraws essentially its entire staking-contract balance so CNStaking rounds down to `0` KAIA, and the CL pool balance also rounds down to `0` KAIA.
2. Due to the staking-update interval / "previous block" caching rule described in `kaiax/staking/README.md`, this validator's stale `StakingInfo` entry can still be used for a subsequent block, and under `istanbul.policy == 2` (WeightedRandom) it can still be selected as proposer for that block (or simply be the fixed `config.Rewardbase` recipient for proposer/staker funds in `specWithProposerAndFunds`).
3. When any full node calls `FinalizeState` → `GetDeferredReward` → `getDeferredRewardFullKore`/`Legacy`/`Flex` → `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` → `cn.Split(proposer)` for this validator's `consolidatedNode` (`cn.StakingAmount == 0`, `cn.CLStakingInfo.CLStakingAmount == 0`), `totalAmount` is `0`, and `clAmount.Div(clAmount, totalAmount)` panics with a division-by-zero runtime error inside `kaiax/staking/staking_info.go:181`.
4. Every honest node processing this block panics identically, halting the chain.

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}

// Distribute the deferred rewards at the end of block processing.
func (r *RewardModule) FinalizeState(header *types.Header, state *state.StateDB, txs []*types.Transaction, receipts []*types.Receipt) error {
	if r.GovModule.GetParamSet(header.Number.Uint64()).ProposerPolicy == uint64(istanbul.WeightedRandom) && common.EmptyHash(header.Root) {
		qualified, err := r.ValsetModule.GetQualifiedValidators(header.Number.Uint64())
		if err != nil {
			return err
		}
		useRewardAddress := valset.NewAddressSet(qualified).Contains(r.NodeAddress)

		if rewardAddr := r.GetRewardAddress(header.Number.Uint64(), r.NodeAddress); useRewardAddress && rewardAddr != (common.Address{}) {
			header.Rewardbase = rewardAddr
			logger.Trace("Use reward address for nodeValidator", "header.Number", header.Number.Uint64(), "nodeAddress", r.NodeAddress, "rewardbase", header.Rewardbase)
		} else {
			logger.Trace("No reward address for nodeValidator. Use node's rewardbase.", "header.Number", header.Number.Uint64(), "nodeAddress", r.NodeAddress, "rewardbase", header.Rewardbase)
		}
	}

	spec, err := r.GetDeferredReward(header, txs, receipts)
	if err != nil {
		return err
	}
	if err := spec.Validate(); err != nil {
		return err
	}
	for addr, amount := range spec.Rewards {
		state.AddBalance(addr, amount)
	}
	return nil
}
