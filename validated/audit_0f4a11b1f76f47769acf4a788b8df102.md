### Title
Scanner reports immature coinbase outputs as spendable funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates over `block.txdata` including `txdata[0]`, the coinbase transaction. Any output paying to a registered script is returned as a `ReceivedOutput`, which downstream code treats as a spendable input. Coinbase outputs cannot be spent for 100 blocks (COINBASE_MATURITY), and under a 51%-style reorg the coinbase — and therefore the credited deposit — can also vanish entirely. A miner (an unprivileged party) can therefore cause Serai to report received funds that are not spendable.

### Finding Description
`scan_block` at `networks/bitcoin/src/wallet/mod.rs:221-227` calls `scan_transaction` on every transaction in the block, including the coinbase at index 0. `scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`) matches `output.script_pubkey` against registered scripts and emits a `ReceivedOutput` with no check on whether the producing transaction is a coinbase, and no concept of confirmations or maturity. The doc comment acknowledges the issue — "This will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed" — but the API itself returns these outputs as indistinguishable, spendable `ReceivedOutput`s.

`SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150-256`) consumes `Vec<ReceivedOutput>` without any maturity awareness, so an immature coinbase `ReceivedOutput` produces a fully signed transaction that any Bitcoin node will reject as non-standard/invalid (`bad-txns-premature-spend-of-coinbase`).

### Impact Explanation
An unprivileged miner (or a majority-hash entity performing a reorg, as in the Grin incident) can mine a block whose coinbase pays to Serai's P2TR script. `scan_block` returns a `ReceivedOutput` for it, indistinguishable from a normal deposit. If credited, this creates funds "received" that cannot be spent for 100 blocks — and if the block is reorged out (trivially possible for the attacker controlling the work), the credited funds never exist at all while Serai may already have signed/acknowledged a batch against them. This is a "funds reported received that are not spendable" primitive reachable purely by sending a Bitcoin block/transaction.

### Likelihood Explanation
Medium. Exploitation requires mining a block (or renting hashpower/Nicehash, exactly the Grin scenario), which has real cost, and the maturity caveat is documented — though nothing enforces the required filtering, and `scan_transaction` is separately exposed for the coinbase case as well. The failure mode is deterministic once an attacker's coinbase output is scanned.

### Recommendation
In `scan_block`, skip `block.txdata[0]` (coinbases can never carry meaningful payments to scanned keys anyway) or mark `ReceivedOutput`s derived from coinbase transactions so they cannot be fed to `SignableTransaction`. At minimum, make maturity/finality a first-class property rather than a doc-comment caveat, and do not treat any output as confirmed from a single block.

### Proof of Concept
```rust
// Miner crafts a block whose coinbase pays Serai's key.
let mut block: Block = attacker_mined_block;
block.txdata[0].output[0].script_pubkey =
    p2tr_script_buf(serai_group_key).unwrap();

let outputs = scanner.scan_block(&block);
// outputs[0] is a ReceivedOutput indistinguishable from a real deposit,
// yet it is an immature coinbase (unspendable for 100 blocks) and may be
// reorged away by a >50% hashpower entity.
let tx = SignableTransaction::new(outputs, &payments, None, None, 1);
// Produces a signed tx every node rejects: bad-txns-premature-spend-of-coinbase.
```
