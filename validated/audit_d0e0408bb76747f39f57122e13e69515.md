### Title
`ReceivedOutput::read` accepts a spend offset that does not regenerate the output's `script_pubkey` - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The audit finding's bug class is a missing sanity check on a security-critical value (zero-address `owner`) and a state transition applied without validating preconditions (`setPaused` blindly overwriting). The direct analog in Serai is `ReceivedOutput::read`, which deserializes an attacker-supplied `(offset, TxOut, OutPoint)` triple and never performs the one check that makes the record meaningful: that `key + G*offset` actually maps to `output.script_pubkey` under `Scanner`'s registered offsets. The result is a `ReceivedOutput` that reports funds as received-and-spendable when they are not.

### Finding Description
`Scanner` is the sole component that decides whether a Bitcoin output belongs to the wallet. It maintains `scripts: HashMap<ScriptBuf, Scalar>`, mapping each registered P2TR script to the scalar offset needed to spend it (`register_offset`, lines 180–196), and `scan_transaction` only emits a `ReceivedOutput` when `output.script_pubkey` is present in that map, pairing it with the correct offset (lines 199–214).

`ReceivedOutput::read` (lines 122–134) reconstructs this security-critical invariant from raw bytes:

```rust
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  let output;
  let outpoint;
  {
    let mut buf_r = BufReader::with_capacity(0, r);
    output = TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
    outpoint = OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
  }
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

It performs three byte-format checks (canonical scalar, decodable `TxOut`, decodable `OutPoint`) and zero semantic checks. `offset` is an arbitrary scalar; `output.script_pubkey` is arbitrary. Nothing ties them together, and nothing ties `outpoint` to a real UTXO. Compare with the producer side: `Scanner::scan_transaction` derives `offset` *from* `script_pubkey` via the `scripts` map; `ReceivedOutput::read` inverts that relationship and trusts both fields independently.

This mirrors the reported bug exactly: like `__initPausable` accepting an unchecked `owner_` that permanently defines control, `ReceivedOutput::read` accepts an unchecked `offset` that permanently defines spendability. And like `setPaused` writing state without checking the transition is meaningful, the reader emits a `ReceivedOutput` whose implied state transition ("we received N sat spendable via `offset`") is never validated against the script the offset is supposed to unlock.

### Impact Explanation
Downstream, the value of a `ReceivedOutput` is exactly that `key + G*offset` equals the tweaked key in `output.script_pubkey` (that is how `register_offset`/`scan_transaction` construct it, lines 185 and 205–210). If that relation does not hold:

- A spender signing with `keys.offset(offset)` produces a key whose signature does not satisfy the output's script; the reported funds are unspendable — the explicitly accepted impact "funds reported received that are not spendable."
- An attacker can point `outpoint`/`output` at a third party's P2TR output (or a dust output) and claim it as wallet funds, corrupting balance accounting and any fee/change/dust math in `send.rs` that selects inputs.
- Because `scan_block`/`scan_transaction` are the trusted producers, a forged `ReceivedOutput` bypasses the script_pubkey matching that is the wallet's entire incoming-payment authorization check.

### Likelihood Explanation
Reachability requires attacker-controlled bytes reaching `ReceivedOutput::read`. The prompt's threat model explicitly lists untrusted bytes fed to `ReceivedOutput::read` as an in-scope input surface, so a peer or data path that can supply serialized outputs (synced state, coordinator/peer-provided output lists, restored-but-tampered data) reaches this with a single `read_F` + two consensus-decodes — no key material, no threshold collusion, no malicious validator required. Severity is Medium: it causes incorrect funds reporting and wasted signing attempts rather than direct key recovery.

### Recommendation
Bind the three fields together at deserialization or first use:

1. Store the scanner's base key (or a hash of the registered `script_pubkey` set) alongside `ReceivedOutput`, and in `ReceivedOutput::read` — or in a `verify(&Scanner)`/constructor — recompute `p2tr_script_buf(scanner.key + G*offset)` and require `Some(script) == output.script_pubkey`, rejecting otherwise.
2. Alternatively, serialize only `(outpoint)` and re-derive `offset`/`output` through `Scanner` on load, removing the trust in the serialized `offset` entirely.
3. Independently, `outpoint` should be confirmed against chain data (existence and that `output` matches the indexed `vout`) before the output is treated as received.

### Proof of Concept
```rust
use bitcoin::{OutPoint, ScriptBuf, TxOut, Amount, Txid, hashes::Hash};
use k256::Scalar;
use bitcoin_serai::wallet::ReceivedOutput;

// Attacker crafts bytes: offset = 5, output paying to an arbitrary third-party
// P2TR script, outpoint pointing at any real or fake UTXO.
let mut bytes = Scalar::from(5u64).to_bytes().to_vec();
bytes.extend(bitcoin::consensus::encode::serialize(&TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: ScriptBuf::new_p2tr_tweaked(
    bitcoin::key::TweakedPublicKey::dangerous_assume_tweaked(
      bitcoin::XOnlyPublicKey::from_slice(&[2u8; 32]).unwrap()
    ),
  ),
}));
bytes.extend(bitcoin::consensus::encode::serialize(
  &OutPoint::new(Txid::all_zeros(), 0),
));

// Succeeds: no check that key + G*offset matches script_pubkey.
let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(forged.value(), 100_000); // Reported as spendable; signature with
                                     // .offset(5) cannot satisfy the script.
```
