## Title
Silent redirection of a repository's `origin` remote to an attacker-controlled host in `updateRemoteUrl` due to a missing hostname check - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The bridge report's broken invariant is: a security-relevant comparison is bound to the *wrong* value from a data structure that has two distinct "destination" fields (`dstChainId` for acknowledgment vs. `liqDstChainId` for the actual order), so the authority check silently passes/fails against a context that doesn't match where funds actually end up. The Desktop analog is structurally identical: `updateRemoteUrl` decides whether to silently rewrite the local git `origin` URL using an equality check that only validates the **protocol** component of the URL and never validates the **hostname**, even though hostname is the field that actually determines where future fetch/push traffic (and therefore the user's code) goes.

### Finding Description
`updateRemoteUrl` is responsible for keeping a repository's `origin` remote URL in sync with the `clone_url` reported by the GitHub API for the linked `GitHubRepository`: [1](#0-0) 

The guard that authorizes the silent rewrite is:

```
const protocolsMatch =
  parsedRemoteUrl.protocol !== null &&
  parsedUpdatedRemoteUrl.protocol !== null &&
  parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol
...
if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
  await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
}
``` [2](#0-1) 

`protocolsMatch` only checks that `URL.parse(remoteUrl).protocol === URL.parse(updatedRemoteUrl).protocol` (e.g. `https:` === `https:`). It never compares `hostname`. The only other conditions are `remoteUrlUnchanged` (the *previous* stored `clone_url` still matches the current local remote) and `!urlsMatch` (the *new* `clone_url` differs from the current local remote) — both of which are satisfied by construction whenever the API-reported `clone_url` value changes at all, including a change of host. `urlMatchesRemote`, the function used for both of these checks, is a strict structural comparison of hostname/owner/name and therefore is expected to be false whenever the host changes — it does not serve as a host allow-list here: [3](#0-2) 

This is functionally the same bug pattern as the DeBridge report: a value that is supposed to gate a security-relevant action against the *correct* destination reference (hostname here, `liqDstChainId` there) is instead checked against an *unrelated but similarly-shaped* value (protocol here, `dstChainId` there), so an attacker-influenced field silently satisfies the wrong invariant.

The unit tests confirm the code accepts a URL where only the path segment differs and is asserted to overwrite the remote, showing the intended behavior is to trust the API-provided `clone_url` almost unconditionally as long as scheme matches: [4](#0-3) 

The test suite never exercises a cross-host `clone_url`, and the code has no logic path that would reject one.

### Impact Explanation
`gitStore.setRemoteURL` rewrites the actual `origin` remote in the user's local `.git/config` with no user prompt, confirmation dialog, or visible diff in the UI. Because the check only validates protocol and not hostname, any `clone_url` value returned for the linked `GitHubRepository` — sourced from a GitHub API response object which is exactly the "GitHub API object" attacker surface named in the task's Valid Impact list — that points to a different host but the same scheme (`https`) will pass the guard and be written verbatim as the new `origin` URL. Once redirected, all future `fetch`/`push` operations for that repository silently target the attacker-controlled remote instead of the legitimate one, matching the "silent corruption of what the user commits or pushes" impact category: the user believes they are pushing to their GitHub-hosted repository while their commits (potentially containing proprietary source, secrets, or credentials embedded in code) are actually sent to a host the attacker controls.

### Likelihood Explanation
The trigger condition only requires the stored `GitHubRepository.cloneURL` to become stale relative to a fresh `clone_url` field on a subsequent API repository refresh (a routine background operation any time the app refreshes repository metadata), and for that new `clone_url` value to differ in host while sharing the same URL scheme. I could not fully verify, given index limits, whether the `IAPIFullRepository`/`clone_url` field is sourced strictly from a single hard-coded per-account API host in all code paths, or whether there is any path (e.g., repository parents/forks, enterprise-connect installations, or a compromised/MITM'd GHE endpoint) where a `clone_url` for a different host could legitimately flow into this function for a given `GitHubRepository` record. This uncertainty affects how easily an external attacker (vs. a network-privileged/MITM attacker) can supply the malicious value, so likelihood should be treated as suggestive rather than confirmed without further investigation of every caller that populates `GitHubRepository`/`IAPIFullRepository` objects into the store.

### Recommendation
Extend the guard in `updateRemoteUrl` to require that the hostname of `updatedRemoteUrl` matches the hostname of `remoteUrl` (or matches an allow-listed host for the account's endpoint, e.g. via `parseRemote`/`urlMatchesRemote`'s hostname field) before calling `gitStore.setRemoteURL`. At minimum:
```
const hostnamesMatch = parseRemote(remoteUrl)?.hostname === parseRemote(updatedRemoteUrl)?.hostname
if (protocolsMatch && hostnamesMatch && remoteUrlUnchanged && !urlsMatch) {
  await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
}
```
If a legitimate cross-host update (e.g., repository transferred to a different GitHub Enterprise instance) needs to be supported, surface it to the user for explicit confirmation rather than rewriting silently.

### Proof of Concept
1. User has a repository whose `origin` remote is `https://github.com/victim/legit-repo.git`, linked to a `GitHubRepository` record with `cloneURL = https://github.com/victim/legit-repo.git`.
2. On a subsequent repository metadata refresh, the API-backed `IAPIFullRepository.clone_url` returned for that repository record becomes `https://attacker.example.com/victim/legit-repo.git` (same `https:` protocol, different hostname) — reachable via the "attacker controls a GitHub API object" scenario named in scope.
3. `updateRemoteUrl` computes:
   - `remoteUrlUnchanged = true` (old stored `cloneURL` still equals the current `origin`),
   - `urlsMatch = false` (new URL differs from current `origin`),
   - `protocolsMatch = true` (both `https:`).
4. All three conditions hold, so `gitStore.setRemoteURL('origin', 'https://attacker.example.com/victim/legit-repo.git')` executes without any prompt, per the same code path exercised in the existing test: [4](#0-3) 
5. Subsequent `git push`/`git fetch` operations from Desktop now target `attacker.example.com`, silently exfiltrating or corrupting the user's commit history without any indication in the UI that `origin` has changed.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
```
