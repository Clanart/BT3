### Title
Deserialized empty aggregate signatures verify successfully despite honest aggregation refusing to produce them - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregator::complete` encodes “no signatures” as `None`, but `SchnorrAggregate::read` accepts an encoded aggregate containing zero nonces and a zero scalar as a concrete signature object. [1](#0-0) [2](#0-1)  `SchnorrAggregate::verify` then accepts that object for an empty `keys_and_challenges` list because its only multiexp term is `-0 * G`, which evaluates to the identity. [3](#0-2) 

### Finding Description
An honest aggregator refuses to emit an aggregate when `self.sigs.is_empty()` by returning `None`. [4](#0-3)  The parser does not enforce that same invariant: it reads a caller-controlled `u32`, permits it to be zero, and returns `SchnorrAggregate { Rs: [], s }` for any canonical scalar `s`, including zero. [2](#0-1)  When `keys_and_challenges` is empty and `s == 0`, verification queues only `(-s, C::generator())`, evaluates that sum to the identity, and returns `true`. [5](#0-4) 

This creates a second, serialization-only representation of an empty aggregate: `None` from the constructor, versus a byte-derived `Some(SchnorrAggregate)` that verifies successfully. [1](#0-0) [2](#0-1) 

### Impact Explanation
An unprivileged party can supply the serialized form of an empty aggregate and have it accepted by `SchnorrAggregate::verify` whenever the verifier’s expected signature list is empty. [3](#0-2)  Because honest aggregation deliberately refuses to create that value, accepting it deserializes a state outside the API’s intended representation and can let a caller treat an unsigned request as carrying a valid aggregate signature. [4](#0-3)  The impact is a forged aggregate-signature acceptance in protocols that interpret a returned object plus `true` as proof that the associated operation was signed. [3](#0-2) 

### Likelihood Explanation
The malicious input is only four zero bytes for the nonce count followed by the canonical encoding of scalar zero, so it is trivially reachable through public bytes passed to `SchnorrAggregate::read`. [2](#0-1)  Exploitation requires the caller to invoke `verify` with an empty `keys_and_challenges` list and to treat a successful result as meaningful authorization. [3](#0-2)  That contextual requirement limits the likelihood, but the constructor’s explicit empty-set rejection shows this state was intended to be impossible. [4](#0-3) 

### Recommendation
Reject zero-length aggregates in `SchnorrAggregate::read`, matching `SchnorrAggregator::complete`’s refusal to produce one. [2](#0-1) [4](#0-3)  As defense in depth, `SchnorrAggregate::verify` should also return `false` when `keys_and_challenges` is empty so manually constructed or otherwise deserialized empty aggregates cannot verify. [3](#0-2) 

### Proof of Concept
For any `C: Ciphersuite`, provide these bytes to `SchnorrAggregate::<C>::read`:

```text
00 00 00 00                                      // Rs length = 0
00 ... 00                                        // canonical encoding of scalar 0
```

The read succeeds with `Rs.len() == 0` and `s == 0`. [2](#0-1)  Calling `verify(dst, &[])` produces only the pair `(-0, C::generator())`, whose multiexp is the identity, causing verification to return `true`. [5](#0-4)  An honest `SchnorrAggregator` cannot produce this accepted encoding because `complete` returns `None` when no signatures were aggregated. [4](#0-3)
