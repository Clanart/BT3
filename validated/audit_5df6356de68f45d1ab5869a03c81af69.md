### Title
Bank precompile `sendNative` transfers native SEI/wei without enforcing the `SendEnabled` (transfer-disabled) parameter - (File: precompiles/bank/bank.go)

### Summary
The Shopware advisory shows a class of bug where a feature flag (`core.cart.enableOrderRefunds`) is enforced by one code path (the UI/normal controller flow) but not by another reachable code path (`CancelOrderRoute`), letting an unprivileged user bypass the disabled feature. The Sei bank module has an analogous flag, `SendEnabled`/`DefaultSendEnabled`, that is supposed to gate all token transfers via `IsSendEnabledCoins`. The standard transfer paths (`MsgSend` via `bankMsgServer.Send`, and CosmWasm's `BankCoinTransferrer.TransferCoins`) explicitly call `IsSendEnabledCoins` before moving funds. The EVM bank precompile's `sendNative` method, however, moves usei/wei balances directly through `bankKeeper.SendCoinsAndWei` without going through that enforcement path.

### Finding Description
`precompiles/bank/bank.go`'s `send` method (ERC20-pointer-gated token send) routes through `p.bankMsgServer.Send`, the standard `MsgSend` handler, which enforces `SendEnabled` checks. [1](#0-0) 

By contrast, `sendNative`, reachable by any EVM caller sending native SEI value to the bank precompile at `0x...1001`, resolves the sender/receiver Sei addresses and calls `p.bankKeeper.SendCoinsAndWei` directly, bypassing `bankMsgServer.Send` and any explicit `IsSendEnabledCoins` gate: [2](#0-1) 

The `SendKeeper` interface exposes `SendCoinsAndWei` as a separate, distinct method from `SendCoins`/`IsSendEnabledCoin(s)`, confirming these are independent code paths rather than one calling into the other's enforcement logic: [3](#0-2) 

The CosmWasm contract-execution path shows the intended, correctly-enforced behavior for comparison: `BankCoinTransferrer.TransferCoins` explicitly calls `IsSendEnabledCoins` before doing the transfer, and the wasmd test suite confirms that disabling `SendEnabled`/`DefaultSendEnabled` causes contract-triggered transfers to error out: [4](#0-3) [5](#0-4) 

This is the same bug class as the Shopware advisory: a chain-wide "transfers disabled" setting is enforced in one execution surface (`MsgSend`, wasmd `TransferCoins`) but not in another reachable surface (`sendNative` on the bank precompile), letting an unprivileged EVM caller move native funds even when transfers/`SendEnabled` have been turned off by governance/params.

### Impact Explanation
If a chain operator or governance disables `DefaultSendEnabled` (or a specific denom's `SendEnabled`) — e.g., during an incident, a controlled migration, or a compliance freeze — any EVM account can still move native usei/wei value by calling `sendNative` on the bank precompile, completely defeating the transfer restriction. This is a fund-movement/authorization-bypass bug (CWE-862 analog): unauthorized transfer that the chain's own parameter is supposed to prevent, reachable from a single unprivileged EVM transaction.

### Likelihood Explanation
Likelihood is high whenever `SendEnabled`/`DefaultSendEnabled` is set to `false` for usei (or the operator relies on it to halt transfers): any address can call the bank precompile's payable `sendNative` method with EVM `value` set, with no privilege beyond having a Sei/EVM account, and the check is silently absent from that one path while present everywhere else.

### Recommendation
Add an explicit `IsSendEnabledCoins` (or equivalent) check in `sendNative` (and any other precompile method that moves funds via `SendCoinsAndWei`/direct balance mutation instead of `bankMsgServer.Send`) before performing the transfer, mirroring the check already performed by `BankCoinTransferrer.TransferCoins` and the standard `MsgSend` handler.

### Proof of Concept
1. Governance/operator sets `x/bank` params so `DefaultSendEnabled = false` (or disables the `usei` denom specifically) to halt native transfers.
2. An unprivileged user submits an EVM transaction calling `sendNative(receiver)` on the bank precompile at address `0x0000000000000000000000000000000000001001`, with EVM `value` set to the amount to transfer.
3. `precompiles/bank/bank.go`'s `sendNative` resolves sender/receiver Sei addresses and calls `p.bankKeeper.SendCoinsAndWei(ctx, senderSeiAddr, receiverSeiAddr, usei, wei)` directly.
4. Because this path never calls `IsSendEnabledCoins`, the transfer succeeds despite `SendEnabled` being disabled chain-wide — contrasted with an equivalent `MsgSend` or CosmWasm bank-send attempt, which would correctly fail per the `TestExecuteWithDeposit` "coin transfer with all transfers disabled" case.

func (p PrecompileExecutor) sendNative(ctx sdk.Context, method *abi.Method, args []interface{}, caller common.Address, callingContract common.Address, value *big.Int, readOnly bool, hooks *tracing.Hooks, evm *vm.EVM) ([]byte, uint64, error) {
	if readOnly {
		return nil, 0, errors.New("cannot call sendNative from staticcall")
	}
	if ctx.EVMPrecompileCalledFromDelegateCall() {
		return nil, 0, errors.New("cannot delegatecall sendNative")
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	if value == nil || value.Sign() == 0 {
		return nil, 0, errors.New("set `value` field to non-zero to send")
	}

	senderSeiAddr, ok := p.evmKeeper.GetSeiAddress(ctx, caller)
	if !ok {
		return nil, 0, errors.New("invalid addr")
	}

	receiverAddr, ok := (args[0]).(string)
	if !ok || receiverAddr == "" {
		return nil, 0, errors.New("invalid addr")
	}

	receiverSeiAddr, err := sdk.AccAddressFromBech32(receiverAddr)
	if err != nil {
		return nil, 0, err
	}

	usei, wei, err := pcommon.HandlePaymentUseiWei(ctx, p.evmKeeper.GetSeiAddressOrDefault(ctx, p.address), senderSeiAddr, value, p.bankKeeper, p.evmKeeper, hooks, evm.GetDepth())
	if err != nil {
		return nil, 0, err
	}

	if err := p.bankKeeper.SendCoinsAndWei(ctx, senderSeiAddr, receiverSeiAddr, usei, wei); err != nil {
		return nil, 0, err
	}
	accExists := p.accountKeeper.HasAccount(ctx, receiverSeiAddr)
	if !accExists {
		defer metrics.RecordBankNewAccount(ctx.Context())
		p.accountKeeper.SetAccount(ctx, p.accountKeeper.NewAccountWithAddress(ctx, receiverSeiAddr))
	}

	if hooks != nil {
		newCtx := ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))
		remainingGas := pcommon.GetRemainingGas(newCtx, p.evmKeeper)
		if hooks.OnEnter != nil {
			hooks.OnEnter(evm.GetDepth()+1, byte(vm.CALL), caller, p.evmKeeper.GetEVMAddressOrDefault(newCtx, receiverSeiAddr), []byte{}, remainingGas, value)
		}
		defer func() {
			if hooks.OnExit != nil {
				hooks.OnExit(evm.GetDepth()+1, []byte{}, 0, nil, false)
			}
		}()
	}

	bz, err := method.Outputs.Pack(true)
	return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}

// TransferCoins transfers coins from source to destination account when coin send was enabled for them and the recipient
// is not in the blocked address list.
func (c BankCoinTransferrer) TransferCoins(parentCtx sdk.Context, fromAddr sdk.AccAddress, toAddr sdk.AccAddress, amount sdk.Coins) error {
	em := sdk.NewEventManager()
	ctx := parentCtx.WithEventManager(em)
	if err := c.keeper.IsSendEnabledCoins(ctx, amount...); err != nil {
		return err
	}
	if c.keeper.BlockedAddr(toAddr) {
		return sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", toAddr.String())
	}

	sdkerr := c.keeper.SendCoins(ctx, fromAddr, toAddr, amount)
	if sdkerr != nil {
		return sdkerr
	}
