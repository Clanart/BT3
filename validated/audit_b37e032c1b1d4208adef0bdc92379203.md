### Title
Funds sent to deterministic non-External multisig addresses (Branch/Change/Forwarded) are silently dropped and become unspendable - (File: processor/src/multisigs/mod.rs + processor/src/networks/bitcoin.rs)

### Summary
Analogous to the USDT-in-escrow finding — where funds matching a valid on-chain destination but not the exact expected interface become permanently stuck — Serai's Bitcoin scanner accepts *any* P2TR output whose `script_pubkey` matches a registered script, classifies it by which offset produced it (`OutputType::{External, Branch, Change, Forwarded}`), and then discards every non-`External` output that isn't part of a known forwarding flow. Since the Branch/Change/Forwarded addresses are deterministic functions of the public group key, any unprivileged party can send BTC to them; the output is scanned, classified, and dropped before ever reaching the scheduler, so the coins sit at a script the multisig controls but will never include in a spending Plan.

### Finding Description
- `Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs` matches outputs purely on `output.script_pubkey` against the registered script map (`networks/bitcoin/src/wallet/mod.rs:199-214`). Any output paying to *any* registered script — including the deterministic Branch/Change/Forwarded offset scripts — produces a `ReceivedOutput`.
- `Bitcoin::get_outputs` in `processor/src/networks/bitcoin.rs:686-700` scans every non-coinbase transaction and assigns `output.kind` from the offset-to-kind map, pushing all such outputs into the scanner event.
- In `scanner_event_to_multisig_event` (`processor/src/multisigs/mod.rs:837`), the block handler retains only `outputs.retain(|output| output.kind() == OutputType::External)` after handling `Forwarded` outputs via `ForwardedOutputDb::take_forwarded_output` — which only acts if a *previously saved* forwarded output exists (`mod.rs:829`). An attacker-initiated deposit to the Forwarded address has no matching DB entry, and Branch/Change deposits are removed by the retain outright.
- The Branch/Change/Forwarded addresses are not secret: `Bitcoin::branch_address`, `Bitcoin::change_address`, and `Bitcoin::forward_address` (`processor/src/networks/bitcoin.rs:671-674` and siblings) are pure functions of the group key via the deterministic `scanner(key)` offset table, so anyone who knows the public group key can derive them and send funds to them.
- Dropped outputs never enter `plans`/`instructions`, so the multisig scheduler never learns of them and never constructs a `SignableTransaction` spending them. The sats remain locked at a tweaked group-key script with no recorded `offset` in any spendable output set.

### Impact Explanation
BTC sent to the deterministic internal addresses becomes permanently unspendable: it is provably controlled by the multisig key (key-path spendable in principle), yet no code path ever re-registers or re-scans those UTXOs into a plan. This mirrors the reported bug exactly — an asset conforming to the on-chain destination but not to the *expected input classification* is irrevocably stranded. A griefing attacker can also inflate the apparent TVL/balance of a multisig with funds that can never move.

### Likelihood Explanation
Any external user only needs the public group key to compute `change_address`/`branch_address`/`forward_address` and broadcast a transaction. No validator collusion, no malformed cryptography, no privileged access is required — just an ordinary Bitcoin transaction to a valid P2TR script. Medium severity: it requires an explicit (if inadvertent or malicious) send to a non-deposit address, and funds at the main `External` address are unaffected.

### Recommendation
Treat all scanned outputs as spendable funds rather than dropping by `kind`. Either (a) report non-External outputs as External when no forwarding DB entry exists, or (b) persist every scanned UTXO keyed by outpoint with its offset so the scheduler can include them in future Plans. Alternatively, add a documented recovery path that re-derives the offset from `script_pubkey` and emits a refund plan for unknown-kind outputs.

### Proof of Concept
1. Obtain the multisig group key (public). Compute `N::change_address(key)` — deterministic via `scanner(key)`'s fixed offset table.
2. Send a normal Bitcoin transaction paying ≥ dust to that address.
3. `get_outputs` returns it with `kind == OutputType::Change`; `scanner_event_to_multisig_event` drops it at `outputs.retain(|o| o.kind() == OutputType::External)` (`processor/src/multisigs/mod.rs:837`). No instruction or plan is created, no balance is credited, and no subsequent code path can spend the UTXO.

Caveat: I was not able to read the full `scanner(key)` helper to confirm the offset table is fully deterministic from the key alone; the public `change_address`/`branch_address`/`forward_address` signatures taking only `key` strongly indicate it is, but if offsets incorporate private state, reachability is reduced and this finding would not hold.
