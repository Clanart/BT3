### Title
Panic-based Denial of Service in PedPoP blame path via out-of-range `Participant` indexing - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The external report describes a DoS where attacker-controlled input (an overlong URL echoed into `X-Up-Location`) forces a downstream component to fail. The analogous Serai bug class is attacker-controlled input that drives an unguarded panic. In the PedPoP DKG blame path, `AdditionalBlameMachine::blame` / `BlameMachine::blame` take `sender` and `recipient` as untrusted `Participant` values and index `HashMap`s keyed by participant with no bounds check, causing a panic on out-of-range or absent indexes. Any unprivileged party who can submit a blame accusation (or convince a node to evaluate one) with `sender`/`recipient` greater than `n` crashes the process evaluating the blame.

### Finding Description
`BlameMachine::blame` delegates to `blame_internal`, which calls `Decryption::decrypt_with_proof`. Inside `decrypt_with_proof`, the decryption key map is indexed directly: `self.enc_keys[&decryptor]` in `crypto/dkg/pedpop/src/encryption.rs:388` panics via `HashMap`'s `Index` impl if `decryptor` is not a registered participant (e.g., `recipient > n`, which is a constructible `Participant` since `Participant::new` only rejects `0`). Similarly, in `crypto/dkg/pedpop/src/lib.rs:599`, `self.commitments[&sender]` panics if `sender` is not among the registered commitments.

Two reachable variants:

1. **Bogus recipient**: the accuser supplies a valid-looking `EncryptedMessage` — the attacker can construct one themselves since the PoP signature is over the attacker's own ephemeral key (see `encrypt` in `encryption.rs:135-168`, and `pop_challenge` at `encryption.rs:302` which binds only `context`, `nonce`, `key`, `sender`, `msg` — no proof that `sender` is a real participant index bound to the encryption key registration). With `proof: Some(_)` and `recipient > n`, `decrypt_with_proof` verifies the PoP successfully (attacker controls both key and signature), then panics at `self.enc_keys[&decryptor]` before the DLEq check completes — the indexing happens at `encryption.rs:388` during argument evaluation of `verify`.

2. **Bogus sender**: `AdditionalBlameMachine::new` (`lib.rs:649`) builds `commitments` only for `1 ..= n`. If `blame` is called with `sender > n` and a message with a valid PoP plus a valid `EncryptionKeyProof` (which an attacker can honestly generate against any registered `decryptor`), execution reaches `self.commitments[&sender]` at `lib.rs:599` and panics.

Neither path is guarded: `Participant` values up to `u16::MAX` are accepted, and there is no `sender <= n` / `recipient <= n` or `contains_key` check anywhere in `blame_internal`, `blame`, or `decrypt_with_proof`.

### Impact Explanation
A panic in `blame`/`decrypt_with_proof` aborts the blame evaluation and, since these crates do not catch panics, propagates to crash the calling process. For a node or coordinator evaluating blame accusations submitted by counterparties, one malformed accusation (wrong `sender` or `recipient` index) permanently kills that evaluation attempt — and, since `BlameMachine::blame` consumes `self`, a panicking call also destroys the blame state, preventing the honest party from ever obtaining blame resolution or completing the DKG. This is an availability loss reachable entirely from untrusted protocol inputs (`Participant` indexes and an `EncryptedMessage`/`EncryptionKeyProof` the attacker serializes), matching the Medium-severity DoS class of the reference advisory.

### Likelihood Explanation
The attacker needs to cause a node to call `blame`/`AdditionalBlameMachine::blame` with attacker-influenced `sender`/`recipient`/`msg`. Per the API docs, `blame` is invoked on accusations received from other parties, and the `msg` "must have been authenticated as actually having come from the sender" — but nothing constrains `sender`/`recipient` to `1 ..= n`, and constructing a `msg` with a valid PoP only requires knowledge of the per-message key, which the attacker generates. So an attacker can either (a) submit an accusation naming a non-existent `recipient` alongside a message they crafted, or (b) supply a message claiming a non-existent `sender`. Both are reachable with public inputs only. The crash is deterministic (Rust `HashMap` indexing panics on absent keys). Likelihood is therefore high wherever blame evaluation is exposed to network-sourced accusations; it is bounded to DoS only (no secret leakage), consistent with Medium.

### Recommendation
Before indexing, validate that `sender` and `recipient` are within `1 ..= n` (or that `enc_keys`/`commitments` `contains_key`) in `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:575`) and in `Decryption::decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs:366`), returning a `DecryptionError`/`PedPoPError` instead of panicking. Consider also validating `Participant` arguments against `ThresholdParams` in `AdditionalBlameMachine::blame`.

### Proof of Concept
```rust
// After a completed/aborted DKG with params n = 3, an attacker constructs:
let bogus_recipient = Participant::new(999).unwrap(); // > n
let attacker = Participant::new(1).unwrap();

// Attacker creates a well-formed EncryptedMessage with their own ephemeral key
// (encrypt() is exercised with attacker-controlled key, producing a valid PoP).
let msg: EncryptedMessage<C, SecretShare<C::F>> = attacker_crafted_message();

// Attacker supplies an EncryptionKeyProof whose DLEq they honestly proved
// (key = enc_key * msg.key for any registered decryptor), or simply relies on
// path 1 where the panic fires during verify() argument evaluation.
let proof: Option<EncryptionKeyProof<C>> = Some(attacker_crafted_proof());

// Node evaluates the accusation:
//   blame_machine.blame(attacker, bogus_recipient, msg, proof)
// -> decrypt_with_proof(...) verifies the PoP, then evaluates
//      &[self.enc_keys[&decryptor], *proof.key]
//    where decryptor == Participant(999) is absent from enc_keys
// -> std::collections::HashMap Index impl panics: "no entry found for key"
// The process aborts; blame resolution is impossible.
```

Uncertainty note: I verified the panic sites and argument flow, but could not trace every upstream caller (e.g., in `processor/`/`coordinator/`) to confirm how `sender`/`recipient` are sourced in production; the panic is reachable whenever these values derive from untrusted accusations, which the API contract explicitly anticipates.
