### Title
Unbounded recursion in AccountKey RLP decoding allows stack-overflow DoS via crafted RoleBased AccountKey - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each role sub-key by calling `rlp.DecodeBytes` into a fresh `AccountKeySerializer`, which in turn calls `NewAccountKey` and `s.Decode(serializer.key)`. If the resulting sub-key is itself `AccountKeyTypeRoleBased`, this chain repeats with no depth or visited-set limit, mirroring the missing depth-check bug class described in the MVG/ImageMagick report (CVE-2026-48734).

### Finding Description
`AccountKeySerializer.DecodeRLP` decodes a `keyType` and dispatches to `NewAccountKey(serializer.keyType)` followed by `s.Decode(serializer.key)`: [1](#0-0) 

When the decoded key type is `AccountKeyTypeRoleBased`, control passes to `AccountKeyRoleBased.DecodeRLP`, which decodes a list of raw byte strings and, for every element, independently RLP-decodes it back into another `AccountKeySerializer` via `rlp.DecodeBytes(b, &serializer)`: [2](#0-1) 

This creates a mutually-recursive decode cycle: `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → ... with **no depth counter, no nesting limit, and no visited/composite-type check at decode time**. The only nested-composite-type guard (`IsCompositeType()`) is enforced in `CheckInstallable`/`CheckUpdatable`, which run *after* decoding completes: [3](#0-2) 

Because a RoleBased key's sub-entries are self-contained RLP byte strings, an attacker can nest a RoleBased-key-inside-RoleBased-key payload to an arbitrary depth with modest, roughly linear growth in encoded size (small per-level overhead: a 1-byte key type field plus small list/string headers), driving the decoder into deep, unbounded Go-level recursion before any validation runs.

### Impact Explanation
This decode path is reachable through the public `DecodeAccountKey` RPC method, which decodes attacker-controlled bytes directly with no size/depth pre-check: [4](#0-3) 

The same `AccountKeySerializer`/`AccountKeyRoleBased` RLP decode path is also invoked when decoding the `AccountKey` field of `TxTypeAccountUpdate` and fee-delegated account-update transactions from the wire/tx-pool, meaning a crafted transaction submitted by any unprivileged sender can trigger the same unbounded recursive decode on every node that processes/validates the transaction (tx pool ingestion and block validation), before the post-decode `CheckInstallable`/`CheckUpdatable` composite-type rejection ever executes. A sufficiently deep payload can exhaust the Go goroutine stack, crashing the processing node (RPC server or full node) — a denial-of-service impacting either a single public RPC endpoint or, if propagated via the tx pool, multiple nodes on the network.

### Likelihood Explanation
Likelihood is high for the RPC-only vector (`DecodeAccountKey` takes raw bytes directly from any caller, no economic cost, no gas metering, no size limits enforced before decode). The tx-pool/block vector requires the payload to be data (with gas costs for the RLP payload), but the per-level nesting overhead is small enough that meaningful recursion depth is achievable within realistic transaction data-size limits. No special privilege, prior authorization, or on-chain state is required — a single submitted transaction or single RPC call is sufficient to reach the vulnerable path.

### Recommendation
Add an explicit depth (or byte-nesting) counter passed through `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP` (e.g., a `maxAccountKeyNestDepth` constant, rejecting decode once exceeded), and/or reject nested `AccountKeyTypeRoleBased` sub-keys at decode time (mirroring the existing `IsCompositeType()`/`ErrNestedCompositeType` check) rather than only after the value has already been fully decoded. Apply the same guard to the JSON `UnmarshalJSON` recursive path for consistency.

### Proof of Concept
Conceptually: construct a `AccountKeySerializer` RLP blob where `keyType = AccountKeyTypeRoleBased` and its single role entry is itself another such RLP-encoded blob (`keyType = AccountKeyTypeRoleBased` wrapping another, and so on), nested N times. Submit this via:
1. `kaia_decodeAccountKey` RPC call with the raw bytes, or
2. an `AccountUpdate` transaction whose `AccountKey` field is this payload.

Increasing N (each level adding only a few bytes) drives `AccountKeySerializer.DecodeRLP`/`AccountKeyRoleBased.DecodeRLP` into N nested Go calls with no depth check, eventually exhausting the goroutine stack and crashing the process before `CheckInstallable` can reject the nested composite type.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
