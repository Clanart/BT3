### Title
Hookify PreToolUse/PostToolUse hooks fail open on any error, silently disabling the security boundary - (File: plugins/hookify/hooks/posttooluse.py, plugins/hookify/hooks/pretooluse.py)

### Summary
The `main` functions in `plugins/hookify/hooks/posttooluse.py` and `plugins/hookify/hooks/pretooluse.py` wrap all rule evaluation in a broad `try/except Exception`, and always call `sys.exit(0)` in a `finally` block regardless of whether an error occurred. Any exception during rule loading/evaluation — including one triggerable by attacker-controlled hook JSON or repo content — results in the hook printing only a `systemMessage` and exiting 0 (allow), rather than blocking the underlying `Bash`/`Edit`/`Write`/`MultiEdit` tool call.

### Finding Description
Both hooks import `load_rules` and `RuleEngine`; if that import fails, the top-level `except ImportError` handler prints an error message and calls `sys.exit(0)`, allowing the operation to proceed with no rule enforcement at all [1](#0-0) . Inside `main()`, `input_data = json.load(sys.stdin)` reads attacker/tool-controlled JSON (the same JSON channel described in the question as attacker-controlled via PreToolUse/PostToolUse/Stop/UserPromptSubmit events), then `load_rules(event=event)` and `engine.evaluate_rules(rules, input_data)` are called inside a `try` block that catches all `Exception`s [2](#0-1) . If `load_rules` or `evaluate_rules` raises for any reason (malformed rule file, malformed `input_data` fields causing a `KeyError`/`TypeError` inside the rule engine, encoding errors, etc.), the `except Exception` branch only emits a `systemMessage` JSON object with no `decision`/`permissionDecision` field, and the `finally: sys.exit(0)` always fires — this is explicitly commented "ALWAYS exit 0 - never block operations due to hook errors" [3](#0-2) . Because Claude Code's hook protocol treats exit 0 with no explicit deny decision as an allow, any parse/runtime error collapses the security decision to "allow" instead of preserving a deny-by-default posture. The identical pattern exists in `posttooluse.py`'s `main` [4](#0-3) . There is no code path that distinguishes "rule evaluation errored" from "no rule matched" — both look identical to the caller (plain JSON with only a message, exit 0), so any bug or malformed configuration/input silently disables the enforcement point for `Bash`, `Edit`, `Write`, and `MultiEdit` tool calls.

### Impact Explanation
Since the hook is the mechanism gating potentially sensitive operations (arbitrary Bash execution, file edits/writes), causing it to error out via crafted rule files or malformed `tool_name`/`tool_input` JSON removes the sole guard rail without any visible failure to the operator beyond a benign-looking `systemMessage`. This matches the "Sensitive code, prompt, token, diff, or local file disclosure to an unintended local or remote sink" impact category, since an attacker who can influence repository content that feeds hookify rule files or the tool_input JSON evaluated by `evaluate_rules` can force an exception and have their otherwise-blocked Bash/Edit/Write/MultiEdit call proceed.

### Likelihood Explanation
Feasibility depends on being able to trigger an exception inside `load_rules`/`evaluate_rules` (e.g., via a malformed `.claude/hookify.*.local.md` rule file committed to a repo, or unusual `tool_input` shapes) — I could not fully verify the exact exception-triggering primitives because `hookify/core/config_loader.py` and `hookify/core/rule_engine.py` internals were not inspected in this session (only `evaluate_rules`'s existence was confirmed). The fail-open design itself, however, is confirmed directly in code and is unconditional: it triggers on *any* exception type, so the attack surface for reaching it is broad and repeatable (any malformed rule or edge-case input in a cloned repo). This is a design-level fail-open bug rather than a narrow one-off bug, making it consistently reproducible once any triggering error condition is found.

### Recommendation
Change the failure semantics so that hook errors fail closed (or at minimum surface a clear blocking decision) rather than defaulting to allow: on `ImportError` or any `Exception` during rule loading/evaluation, return an explicit deny/ask decision (or a distinct non-zero exit code recognized by Claude Code as "block") instead of `sys.exit(0)` with only a `systemMessage`. At minimum, add a configuration option to choose fail-closed behavior for security-sensitive rules, and ensure the emitted JSON clearly distinguishes "error occurred, defaulting to allow" from "evaluated normally, no rule matched" so operators can detect enforcement gaps.

### Proof of Concept
Unit/integration test plan:
1. Craft a `.claude/hookify.bash.local.md` (or equivalent) rule file with malformed syntax expected to raise inside `load_rules`, or craft `tool_input` JSON for a `Bash` call with a type mismatch expected to raise inside `evaluate_rules` (e.g., `tool_input` as a list instead of dict, if the rule engine indexes it as a dict).
2. Pipe that JSON via stdin to `python plugins/hookify/hooks/pretooluse.py` and separately to `posttooluse.py`.
3. Assert: process exit code is `0`, stdout JSON contains only `systemMessage` (no deny/ask decision field), confirming the tool call would be allowed.
4. Compare against a known-valid deny rule (unmalformed) to confirm that under normal conditions the same input is denied — demonstrating that introducing the malformed rule/input flips the outcome from deny to allow purely due to the exception handling, not because the rule logic evaluated the request as safe.

```python
def main():
    """Main entry point for PostToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type based on tool
        tool_name = input_data.get('tool_name', '')
        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0
        sys.exit(0)
```
