### Title
Cached FROST preprocess seed is reused across distinct signing invocations, enabling nonce reuse and private share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` caches the FROST preprocess seed in `CachedPreprocesses` keyed only by `context` (e.g. `(b"DkgConfirmer", attempt)`), and re-derives identical nonces from that seed on every subsequent call via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` (`ChaCha20Rng::from_seed`). The cache entry is never consumed/invalidated after use, mirroring the reported bug class: a stale state (the seed/preprocess) is not refreshed before a new "update" (a new signing round under the same context). Because FROST nonces are deterministic functions of the seed, any two `share_internal`/`complete` invocations that sign different messages under the same context reuse the same `(d, e)` nonces, and the two public shares suffice to recover the signer's private key share.

### Finding Description
- `crypto/frost/src/sign.rs:121-144` — `seeded_preprocess` derives `nonces` and `commitments` purely from `ChaCha20Rng::from_seed(*seed.0)`; same seed ⇒ identical nonces and identical broadcast preprocess.
- `crypto/frost/src/sign.rs:216-224` — `from_cache` documents that after use "the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share."
- `coordinator/src/tributary/signing_protocol.rs:123-145` — `preprocess_internal` checks `CachedPreprocesses::get(self.txn, &self.context)`; if present it decrypts and calls `from_cache` with the stored seed, but never removes or rotates the entry.
- `coordinator/src/tributary/signing_protocol.rs:150-181` — `share_internal` calls `preprocess_internal` again and signs `msg` with the reused nonces.
- `coordinator/src/tributary/signing_protocol.rs:304-327` — `DkgConfirmer::share` and `DkgConfirmer::complete` each invoke `share_internal` for context `(b"DkgConfirmer", self.attempt)`. The signed message is `set_keys_message(set, removed, key_pair)`, where `removed = removed_as_of_dkg_attempt(...)` is re-evaluated at `DkgConfirmer::new` (line 271) and `key_pair` is supplied by the caller (`handle.rs:47-60`, `handle.rs:529-535`). If the removed set or the reported `key_pair` changes between `generated_key_pair`'s share production (line 59) and a later call (`complete`, or a repeated `generated_key_pair` for the same attempt), the same nonces sign two different messages.

### Impact Explanation
With two shares `s₁ = (d + e·ρ₁) − λ·c₁·x` and `s₂ = (d + e·ρ₂) − λ·c₂·x` over the same nonce commitments (so identical `ρ`, identical `d + e·ρ` only when the preprocess set is identical — but even when ρ differs, `d` and `e` individually repeat), an observer can solve for the secret share `x` because the underlying scalars `d, e` are byte-identical across both sessions. All preprocesses and shares are broadcast on the public tributary, so any observer (unprivileged) who sees a validator sign two distinct `set_keys_message` payloads under the same `(attempt)` context recovers that validator's Ristretto private key — the very key the spec says cached preprocesses must be guarded like. Compromise of the coordinator signing key enables forging tributary signatures.

### Likelihood Explanation
The path requires the same context to be used for two messages that differ. `share` and `complete` both run `share_internal`; `removed_as_of_dkg_attempt` accumulates removals over time, and `generated_key_pair` unconditionally overwrites `DkgKeyPair`/`KeyToDkgAttempt` and produces a fresh share for whatever `key_pair` the processor reports (`handle.rs:54-59`). A retry, re-report of a differing key pair for the same attempt, or a crash/replay between `share` and `complete` after a new `RemoveParticipantDueToDkg` removal finalizes yields two signatures over distinct messages with reused nonces. The shares are published publicly on-tributary, so no privileged access is needed to exploit — only to trigger the second, divergent signing, which normal protocol evolution (removals, processor re-reports) can cause.

### Recommendation
Invalidate `CachedPreprocesses` for `context` immediately after loading the seed in `preprocess_internal` (delete-then-use, not use-then-keep), and/or mix a fresh per-invocation entropy or the message hash into the seed before `from_cache`. Additionally, refuse to produce a second share under `(topic, attempt)` if a share was already emitted for different message bytes.

### Proof of Concept
1. Attempt `a` of the DKG for set `S`. All validators publish confirmation nonces; `ConfirmationNonces` is stored.
2. Validator V calls `generated_key_pair(attempt=a, key_pair=K₁)` → `share` signs `set_keys_message(S, removed₀, K₁)`; nonces `d,e` derive from cached seed `σ`.
3. Before `DkgConfirmed` completes, a removal finalizes (or the processor reports `K₂ ≠ K₁` for the same attempt via a second `generated_key_pair` call). `DkgConfirmer::new` recomputes `removed₁ ≠ removed₀` (or `K₂` differs), so `share_internal` signs `msg₂ ≠ msg₁` — but `preprocess_internal` finds `CachedPreprocesses["DkgConfirmer", a]` still present and regenerates the identical `d,e` via `from_cache`.
4. Two shares `(s₁, s₂)` with identical nonce commitments `(D,E)` are public on the tributary. With `s_i = (d + e·ρ) − λ·c_i·x` (same `included` set, same `ρ` since commitments are identical), `x = (s₁ − s₂) / (λ·(c₂ − c₁))`, recovering V's private key. Even with differing `included` sets, `d` and `e` repeat, so the system of two equations over shared nonces still yields `x` via standard nonce-reuse algebra.
