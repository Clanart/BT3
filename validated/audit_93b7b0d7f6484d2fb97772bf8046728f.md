### Title
`SignableTransaction::new` excludes the OP_RETURN data output from fee, minimum-relay-fee, and weight checks, producing signed transactions that pay less than the intended/relayed fee rate or exceed standard weight - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
The original report describes a swap whose effective minimum output is derived on-chain at execution time, i.e. no real bound on the produced result. The Serai analog lives in `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`), the code that computes the fee bound and standardness bound for the transaction the threshold group will sign. When the caller supplies `data`, an OP_RETURN output (up to ~83 bytes) is appended to `tx_outs`, but `calculate_weight_vbytes` is invoked with only `payments`, so the OP_RETURN output is never counted. Every downstream bound — `needed_fee`, the `TooLowFee` minimum-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` check — is computed on a transaction that is smaller than the one actually signed.

### Finding Description
The data output is pushed onto `tx_outs` before the weight/vbyte calculation, but the calculation itself only sees `payments`:

```rust
// tx_outs already contains the OP_RETURN output here
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}
// ... yet only `payments` is measured:
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;
}
``` [1](#0-0) 

`calculate_weight_vbytes` builds its measurement transaction solely from `payments` plus an optional `change` output — the OP_RETURN output is structurally invisible to it: [2](#0-1) 

Consequences:

1. **Fee-rate bound not enforced on the real transaction.** `needed_fee = fee_per_vbyte * vbytes` uses `vbytes` that omits the OP_RETURN output (~90 base bytes ≈ 360 weight units ≈ 90 vbytes). The signed transaction's actual vsize is larger, so `actual_fee / actual_vsize < fee_per_vbyte`. When `fee_per_vbyte` is at/near the minimum relay rate, the `TooLowFee` check passes on the underestimated size while the real transaction falls below `DEFAULT_MIN_RELAY_TX_FEE` and is rejected by relaying nodes.
2. **Standardness bound not enforced.** The `weight > MAX_STANDARD_TX_WEIGHT` check uses the underestimated `weight`, so a transaction near the 400,000 WU limit can be pushed over it by the uncounted OP_RETURN output, making it non-standard and unrelyable regardless of fee.

The resulting `SignableTransaction` is then signed by `TransactionSignMachine::sign`, which commits all participants' signatures to this exact transaction via `Prevouts::All` — the under-bounded transaction is the message being signed. Its `Eventuality` is the txid, which will never confirm. [3](#0-2) 

### Impact Explanation
Same class as the report: a bound that is supposed to protect the produced output is computed on values that do not reflect the actual output. Here the "minimum output" is the guaranteed fee rate / standardness of the signed Bitcoin transaction. Because the OP_RETURN output is excluded from the measurement, the protocol can produce and threshold-sign a transaction that the Bitcoin network will not relay or mine. The inputs committed via `Prevouts::All` are locked to a txid that can never confirm; payments stall and the inputs must be re-spent through a newly coordinated signing round, or funds sit unspendable if the plan cannot be regenerated. Impact: loss of liveness of funds (stuck/unsendable payments); High-severity shape, conservatively Medium given the recovery path of re-signing.

### Likelihood Explanation
Requires `data` to be specified (the in-scope API explicitly supports up to 80 bytes, and Serai's protocol uses OP_RETURN `Shorthand` data for transfers on Bitcoin) combined with a near-boundary fee rate or transaction weight. Fee rates near the relay minimum are common for cost-minimizing batch transactions, and the underestimation is deterministic — whenever data is present, the real fee rate is strictly lower than requested. Medium.

### Recommendation
Include the OP_RETURN output in the measured transaction. Pass the fully-formed `tx_outs` (or the `data` length) into `calculate_weight_vbytes` so that `vbytes`, `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction that will actually be signed and broadcast. Alternatively, compute the fee/weight bounds against `tx_outs` after all outputs (payments, OP_RETURN, change) are finalized.

Root cause: `calculate_weight_vbytes` is called with `payments` at `networks/bitcoin/src/wallet/send.rs:204` and `:226` while the OP_RETURN output pushed at `:194-202` is never measured, so neither `needed_fee` nor the weight check at `:241` covers the transaction actually signed at `:373-390`.
