Confirmed vulnerability: `resolveWithin()` in `app/src/lib/path.ts` uses a bare `String.prototype.startsWith()` check instead of a boundary-aware comparison to decide whether a resolved path is contained within the intended root.

### Title
Path-containment check in `resolveWithin()` accepts sibling directories that share a path prefix - (File: app/src/lib/path.ts)

### Summary
`resolveWithin()` is Desktop's shared guard for confining an attacker/API-controlled relative path (deep-link `filepath`, Copilot conflict-resolution paths, etc.) to a specific root directory. The final containment check is `realResolved.startsWith(realRoot)`, which is a broken invariant: it does not verify that `realResolved` is `realRoot` itself or that it continues with a path separator, so any sibling directory whose name has `realRoot` as a string prefix (e.g. `realRoot` = `/Users/victim/Documents/GitHub/repo`, `realResolved` = `/Users/victim/Documents/GitHub/repo-secrets/token`) passes the check even though it is a completely different directory outside the intended repository tree.

### Finding Description
`_resolveWithin()` [1](#0-0)  resolves a caller-supplied relative path against a root, canonicalizes both with `realpath()` to defeat symlink tricks, and then performs the actual security decision with:
```
return realResolved.startsWith(realRoot) ? resolved : null
``` [2](#0-1) 

`startsWith` is a pure string-prefix comparison. It does not require that the byte immediately following `realRoot` in `realResolved` be a path separator (or that the strings be exactly equal). Consequently, if `realRoot` happens to be a prefix of another sibling directory's name, that sibling directory (and anything under it) is treated as "inside" the root and the function returns a non-null resolved path instead of rejecting it.

This function is the sole containment guard used by `openRepositoryFromUrl()` in the deep-link handler:
```
const resolved = await resolveWithin(repository.path, filepath)
if (resolved !== null) {
  shell.showItemInFolder(resolved)
} else {
  log.error(`Prevented attempt to open path outside of the repository root: ${filepath}`)
}
``` [3](#0-2) 

`filepath` originates from a `x-github-client://openRepo/...?filepath=...` URL — i.e., attacker-controlled input reachable by tricking a user into clicking a crafted link, or embedded in a GitHub PR/notification that GitHub Desktop parses via `parseAppURL` [4](#0-3) . The only other check performed before calling `resolveWithin` is that `filepath` isn't an absolute path [5](#0-4) ; relative traversal is expected to be neutralized entirely by `resolveWithin`'s prefix check.

The existing unit tests for `resolveWithin` only cover exact-root traversal and symlink escape cases [6](#0-5) ; there is no test exercising a sibling directory whose name extends the root's name as a string, which is exactly the gap the prefix-only check leaves open.

### Impact Explanation
An attacker who controls (or can predict) the layout next to a victim's cloned repository directory (e.g., a `repo` folder alongside a `repo-private` or `repo.bak` folder created by backup tools, other clones, or the attacker convincing the victim to create such a folder) can craft a `x-github-client://openRepo/<repo-url>?filepath=../repo-secrets/creds.txt`-style deep link. Because `resolveWithin` only checks a string prefix and not a directory-boundary, the function returns a path outside the repository, and Desktop calls `shell.showItemInFolder()` on it — revealing/opening files outside the repository working tree that the user never intended to expose via this flow. This matches the "attacker-controlled deep link results in file access outside the repo" impact class.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to click a maliciously crafted `x-github-client://` link (Desktop's registered custom protocol) and requires a same-prefix sibling directory to exist next to the target repository — a scenario that is common in practice (e.g., `project` and `project-old`, `project` and `project.bak`, or repos cloned with suffixes). No local access, admin rights, or prior malware are required — only that the user clicks the deep link.

### Recommendation
Fix `_resolveWithin()`'s final check to be boundary-aware, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the appropriate `options.sep`/platform separator for the `win32`/`posix` variants), so that only exact matches or genuine sub-paths of `realRoot` are accepted.

### Proof of Concept
1. Victim has a cloned repository at `/Users/victim/Documents/GitHub/repo` and, unrelated, a folder `/Users/victim/Documents/GitHub/repo-secret/token.txt`.
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/owner/repo?filepath=..%2Frepo-secret%2Ftoken.txt`.
3. `parseAppURL` extracts `filepath = ../repo-secret/token.txt` (relative, so it passes the `isAbsolute` check) and calls `openRepositoryFromUrl` → `resolveWithin('/Users/victim/Documents/GitHub/repo', '../repo-secret/token.txt')`.
4. `resolve()` produces `/Users/victim/Documents/GitHub/repo-secret/token.txt`; `realpath` of both root and resolved path leave the strings unchanged (no symlinks needed).
5. `realResolved.startsWith(realRoot)` evaluates `'/Users/victim/Documents/GitHub/repo-secret/token.txt'.startsWith('/Users/victim/Documents/GitHub/repo')` → `true`, even though `repo-secret` is not inside `repo`.
6. `resolveWithin` returns the out-of-repo path instead of `null`, and `shell.showItemInFolder()` opens/reveals `token.txt`, which is outside the repository the deep link claimed to target.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
