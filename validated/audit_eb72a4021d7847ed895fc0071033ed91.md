### Title
Scanner reports dust outputs as received funds that are uneconomical/unspendable, enabling dust-spam griefing - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Debita M-16 bug class is the absence of a minimum size on attacker-creatable objects (loans/offers), letting an unprivileged party fragment one logical position into countless tiny pieces that grief the victim with tracking burden and costs. The Serai analog lives in `Scanner::scan_transaction`: any transaction output paying to a registered `script_pubkey` is reported as a `ReceivedOutput` with **no minimum-value check**. An attacker can send arbitrarily many dust outputs (down to 1 sat) to a Serai multisig address; each is reported as funds received, yet spending such an input costs more in fees than its value.

### Finding Description
`Scanner::scan_transaction` iterates every output of every scanned transaction and emits a `ReceivedOutput` whenever `output.script_pubkey` matches a registered script, unconditionally — there is no lower bound on `output.value`: [1](#0-0) 

The same holds for `scan_block`, which forwards all transaction outputs to `scan_transaction` (only the coinbase-maturity caveat is documented, not a value floor): [2](#0-1) 

Notably, `SignableTransaction::new` enforces a `DUST = 546` minimum on *payments* (`TransactionError::DustPayment`), and `MAX_STANDARD_TX_WEIGHT` caps the spend transaction — but it places **no minimum on the value of inputs it will consume**: [3](#0-2) [4](#0-3) 

So the wallet layer itself acknowledges a minimum-viable-output concept for sends while the receive path accepts zero/dust. The protocol-level consequence is visible in the downstream processor, which had to bolt on the missing check externally: `output.balance().amount.0 >= N::DUST` (with `Bitcoin::DUST = 10_000`) is applied in the multisig scanner loop, and a `COST_TO_AGGREGATE` flat fee of `2 *` the merge-TX fee is deducted per input precisely because tiny attacker-created outputs force aggregation transactions. The spec (`spec/processor/UTXO Management.md`, "Attacks by a Malicious Miner") documents this as the intended mitigation for the exact griefing vector — yet the in-scope `Scanner` returns every matching output with no floor, so any consumer of `scan_transaction`/`scan_block` that does not re-implement an external dust filter will report and attempt to spend uneconomical dust.

### Impact Explanation
An unprivileged party can send an arbitrary number of dust-valued outputs (e.g., hundreds of 1–546 sat outputs in one transaction) to a Serai multisig or offset address. `scan_block`/`scan_transaction` will report each as `ReceivedOutput` — funds reported received that are not economically spendable: a P2TR input adds ~57 vbytes (per the `MAX_INPUTS` weight analysis in `processor/src/networks/bitcoin.rs`), so at any positive fee rate an input worth under ~285–10,000 sats costs more to spend than it returns. The victim must either burn fees merging these inputs or permanently track unspendable UTXOs — the same griefing impact as M-16 (countless tiny positions the victim must pay to manage). If the dust filter exists only in a specific integrator (the processor), any other consumer of this library is unprotected.

### Likelihood Explanation
The attack requires only sending Bitcoin transactions to a publicly known multisig address — the address is necessarily public for deposits. Cost to the attacker is the sum of dust sent (recoverable in principle) plus miner fees, while each output creates an asymmetric tracking/fee burden on the receiver. The Serai authors evidently considered this vector real enough to specify the `2 * COST_TO_AGGREGATE` flat fee and the `>= N::DUST` filter downstream; the gap is that the wallet `Scanner` API — the canonical "what did we receive" primitive — performs no such filtering and reports the outputs as bona fide `ReceivedOutput`s.

### Recommendation
Apply a minimum-value floor inside `Scanner::scan_transaction` itself: skip outputs whose `output.value.to_sat()` is below a dust/spendability threshold (e.g., the same `DUST` constant or the fee-scaled spendability bound used by the processor's `N::DUST`). Alternatively, have `Scanner` expose the threshold at construction so every consumer inherits a minimum received size rather than relying on each downstream caller to re-implement the check. This mirrors the M-16 mitigation: enforce a minimum size on the object an attacker can force the victim to track.

### Proof of Concept
1. Build a `Scanner` for a group key (`Scanner::new(key)`).
2. Construct a transaction with, say, 500 `TxOut`s of `Amount::from_sat(1)` each paying `p2tr_script_buf(key)` (consensus-valid; not relay-dust since policy only applies to *standard* relay, and miners may still include it — the processor spec explicitly models attacker-controlled blocks).
3. `scanner.scan_transaction(&tx)` returns 500 `ReceivedOutput`s, each reported as received funds.
4. Passing any of these as an input to `SignableTransaction::new` succeeds (inputs are not dust-checked), and the input contributes 1 sat while adding ~57 vbytes — a net-negative input the wallet will track forever unless externally filtered.

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```
