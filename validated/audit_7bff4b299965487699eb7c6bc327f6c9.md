## Analysis



### Title
Unscoped, permissionless `CallDispatcher.dispatch()` allows any address to sweep residual native ETH/ERC20 left in the shared dispatcher by other users' cross-chain transfers - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is a fully public function with no caller restriction, no linkage to a specific HyperFungibleToken transfer, and no binding to the request/commitment that funded it. `HyperFungibleToken`/`WrappedHyperFungibleToken.onAccept` route unlocked tokens/ETH to this single shared contract and then invoke `dispatch()` with calldata supplied by the original cross-chain sender. Any native ETH left over in `CallDispatcher` — e.g., DEX-router refunds from `swapETHForExactTokens` (a pattern demonstrated in the project's own documentation) — remains in the shared contract and can be swept by an unrelated, unprivileged caller simply by invoking `dispatch()` directly, since nothing scopes execution rights to the party whose transfer produced that balance.

### Finding Description
`CallDispatcher.dispatch()` decodes an arbitrary `Call[]` and executes each call against any target with any value/calldata, without any `msg.sender` check: [1](#0-0) 

`CallDispatcher` is a **shared singleton** used by every `HyperFungibleToken`/`WrappedHyperFungibleToken` deployment. `onAccept` unlocks/mints tokens to a beneficiary (which may itself be the `CallDispatcher` address) and then forwards the message's `data` field — fully controlled by whoever called `send()` on the source chain — to `dispatch()`: [2](#0-1) 

The project's own documentation demonstrates the intended flow: unlock/unwrap ETH into `CallDispatcher`, then have `CallDispatcher` forward it via `Call.value` into a Uniswap swap (`swapETHForExactTokens`), a function that **refunds any unspent ETH to `msg.sender`** — i.e., back into `CallDispatcher` itself: [3](#0-2) 

Because `CallDispatcher.receive()` accepts ETH unconditionally and `dispatch()` has no access control or commitment binding, any ETH refunded into the dispatcher this way (slippage buffers, exact-out swap remainders, partial fills, or any other future integration that leaves dust) sits in a **shared pool** available to every future caller. There is no mechanism restricting who may call `dispatch()` next or requiring that the caller be the same request/commitment/beneficiary that produced the residual balance — the exact same class of gap as the Spigot bug, where a security-relevant decision (which calls are permitted) is made without scoping it to the specific context (a revenue contract there; a specific cross-chain transfer/commitment here).

An unprivileged attacker who observes (or causes, since transaction data is public in the mempool/finalized state) a residual balance in `CallDispatcher` can call:
```solidity
Call[] memory steal = new Call[](1);
steal[0] = Call({ to: attacker, value: address(callDispatcher).balance, data: "" });
callDispatcher.dispatch(abi.encode(steal));
```
This directly forwards the entire native balance of the shared `CallDispatcher` to the attacker. The same applies to any ERC20 tokens the dispatcher might hold (e.g., a `mint`-to-dispatcher pattern where the follow-up call only spends part of the minted amount, or reverts leaving a partial balance from a prior unrelated `onAccept`).

### Impact Explanation
This is a direct loss-of-funds vector on a live, production, publicly-callable contract:
- Any native ETH left in the shared `CallDispatcher` (from router refunds, partial fills, or any calldata-execution flow that doesn't consume 100% of the forwarded value) belongs to no one in particular from the contract's point of view, and is drainable by any unrelated third party.
- It requires no relayer, prover, admin, or governance compromise — a bare EOA calling a public function is sufficient, satisfying the impact gate's "unauthorized transaction/execution" and "stealing or loss of funds" categories.
- Because `CallDispatcher` is shared across all `HyperFungibleToken`/`WrappedHyperFungibleToken` deployments that use it, the blast radius spans every integration that routes calldata-execution through this dispatcher, not just a single token.

### Likelihood Explanation
Likelihood is tied to how often calldata-execution flows leave non-zero residual balances in `CallDispatcher`. The documentation's own showcased example (Uniswap `swapETHForExactTokens`) is a standard "exact-out" swap pattern that virtually always refunds some dust ETH to the caller (the dispatcher) due to price movement between quote and execution — making this not a hypothetical edge case but the expected behavior of a documented integration pattern. Any attacker can trivially monitor the dispatcher's balance and front-run/back-run to claim it, requiring no privileged position.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to be callable only by the specific `HyperFungibleToken`/`WrappedHyperFungibleToken` instance (or a registered set of authorized callers) that is actively delivering a request, ideally passing the caller/commitment through so unspent residual value is swept back to the correct beneficiary rather than left in a shared pool.
- Alternatively, make `CallDispatcher` non-shared (deploy one per token/app instance) so any residual balance is only ever reachable in the context of that instance's own trusted `onAccept` flow, and add an explicit sweep-to-beneficiary step for any leftover `msg.value` after executing the batch.
- Add a check that reverts if `dispatch()` leaves any unspent native balance in the contract post-execution (forcing full consumption or explicit refund to the intended beneficiary within the same transaction), eliminating any window where funds sit unscoped and unprivileged-drainable.

### Proof of Concept
1. A `WrappedHyperFungibleToken.onAccept` delivers tokens to `CallDispatcher`, then calls `dispatch()` with a batch that unwraps WETH and calls `UniswapV2Router.swapETHForExactTokens{value: amount}(usdcOut, path, recipient, deadline)` as shown in the documented example.
2. Due to price movement, the router consumes less than `amount` of ETH and refunds the difference to `msg.sender`, which is `CallDispatcher` (per `receive()` in `evm/src/utils/CallDispatcher.sol` lines 36-39).
3. That refunded ETH remains in `CallDispatcher`'s balance after the `onAccept` transaction completes.
4. Any external, unrelated address calls:
```solidity
Call[] memory steal = new Call[](1);
steal[0] = Call({to: attackerAddress, value: address(callDispatcher).balance, data: ""});
callDispatcher.dispatch(abi.encode(steal));
```
5. `dispatch()` (lines 44-62 of `CallDispatcher.sol`) performs `attackerAddress.call{value: ...}("")` with no check that `msg.sender` is the token contract, the original beneficiary, or has any relationship to the funds — the attacker receives ETH that belonged to the legitimate cross-chain transfer's slippage refund.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
```
