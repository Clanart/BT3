## Finding: Payout attribution relies on unauthenticated OP_RETURN data, allowing reimbursement misattribution

### Title
Payout-payer attribution trusts an unauthenticated OP_RETURN field, letting anyone front a withdrawal and get an arbitrary operator credited/reimbursed for a payout it never funded - (File: `core/src/verifier.rs`, `core/src/builder/transaction/operator_reimburse.rs`, `core/src/task/payout_checker.rs`)

### Summary
The protocol determines which operator is entitled to reimbursement for a withdrawal purely by reading an `OP_RETURN` push-data field from the confirmed payout transaction, and never verifies that the named operator is the one who actually supplied the funds. Because the user's authorization signature over the payout input uses `SIGHASH_SINGLE|ANYONECANPAY`, it commits only to input 0 and output 0; anyone observing the (still-unconfirmed, RBF-replaceable, publicly broadcast) payout transaction can rebuild it with their own funding input while writing an arbitrary registered operator's x-only public key into the `OP_RETURN` output. The named operator's own automation later treats this OP_RETURN value as ground truth for "who paid," and drives that operator through the kickoff/reimbursement flow — reimbursing an operator that never funded the withdrawal.

### Finding Description
`create_payout_txhandler` builds the payout transaction with a user-signed input (key-spend, `SinglePlusAnyoneCanPay`) and appends an `OP_RETURN` output carrying `operator_xonly_pk`, which is only whatever value the constructor of the transaction chooses to write — it is not signed by anyone and not bound to the funding input: [1](#0-0) 

`operator.rs::withdraw` verifies only that the *user's* signature is valid over input 0/output 0; it never verifies that the operator broadcasting is uniquely entitled to write its own key into `OP_RETURN`: [2](#0-1) 

Because the sighash type is `SinglePlusAnyoneCanPay`, the signature commits only to input 0 and output 0 (the user's payment) — nothing prevents a third party from constructing a competing (RBF) transaction that reuses this same signed input/output pair while substituting arbitrary additional funding inputs and an arbitrary `OP_RETURN` payload naming any registered operator.

On the verifier side, `update_finalized_payouts` extracts the "payer" purely from that `OP_RETURN` field of the confirmed transaction with no cryptographic check that the named operator actually contributed the funding input: [3](#0-2) 

This value is persisted and later consumed by each operator's own automated `PayoutCheckerTask`, which unconditionally acts on any payout whose `payout_payer_operator_xonly_pk` matches its own key — with no verification that it, in fact, funded the payout: [4](#0-3) [5](#0-4) 

The subsequent malicious-kickoff check (`is_kickoff_malicious`) only verifies that the kickoff's `operator_xonly_pk` equals the payout's OP_RETURN `operator_xonly_pk` — both of which can be the *same, real* operator's key, since that operator's own honest automation is what performs the (cryptographically valid) kickoff once it observes the spoofed attribution: [6](#0-5) 

Root cause: the binding `payout_payer_operator_xonly_pk == the operator that actually funded the withdrawal payout` is never enforced — it is inferred solely from unauthenticated OP_RETURN push data on a transaction whose only cryptographic signature (the user's) does not cover that field or any of the funding inputs.

### Impact Explanation
This breaks a core custody/attribution binding of the bridge: BTC held for a specific deposit's reimbursement is released to whichever operator's public key an unprivileged party chooses to write into the payout's OP_RETURN, independent of who actually funded the withdrawal. This matches the explicitly listed Critical impact "an operator reimbursed for a payout it never funded" — the reimbursement flow (kickoff → round → reimburse, all driven automatically by `PayoutCheckerTask` and `get_reimbursement_txs`) pays out the move-to-vault-derived reimbursement UTXO to an operator with no on-chain proof that operator supplied the withdrawal funds.

### Likelihood Explanation
No privileged role is required to construct the competing/attributed transaction: the withdrawal-authorizing signature only commits to input 0/output 0, so anyone monitoring the Bitcoin mempool (or receiving the withdrawal request as one of potentially many operators contacted by the aggregator) can build and (via RBF) broadcast a transaction that fronts the exact same payment while attributing it to a different, arbitrary registered operator's public key, which is public information. The named operator's automation (`PayoutCheckerTask`) then acts on this without any additional authorization check, so the exploitation path is fully automatic once the spoofed transaction confirms.

### Recommendation
Do not derive payout attribution solely from an unauthenticated `OP_RETURN` field. Bind the credited operator cryptographically to the actual funding of the payout transaction — e.g., require the operator's funding input(s) to be signed with (or otherwise provably controlled by) the operator's key, and have verifiers validate that the claimed `operator_xonly_pk` corresponds to an input that actually contributed value to the payout, not just a value copied into an OP_RETURN output.

### Proof of Concept
1. User signs a withdrawal payout with `SinglePlusAnyoneCanPay` over `(withdrawal_utxo, user_output)`, as required by `create_payout_txhandler`.
2. Operator A (or the aggregator on behalf of multiple operators) broadcasts payout `TX1`: input = signed withdrawal UTXO, output0 = user payment, `OP_RETURN` = A's xonly pubkey, funding input = A's own wallet UTXO. `TX1` is RBF-eligible and sits unconfirmed in the mempool (publicly visible).
3. An unprivileged attacker observes `TX1` in the mempool, extracts the user-signed witness for input 0 (valid without any secret), and constructs `TX2` with: the same input 0/output0 (satisfying the `SINGLE` sighash constraint), attacker's own funding input covering the payment, and `OP_RETURN` = operator B's (a different, honest, registered operator) xonly pubkey.
4. Attacker fee-bumps and broadcasts `TX2`, which replaces `TX1` and confirms.
5. `update_finalized_payouts` records `payout_payer_operator_xonly_pk = B` for this withdrawal.
6. Operator B's `PayoutCheckerTask` observes the unhandled payout tagged with its own key and automatically drives the kickoff/reimbursement flow (`is_kickoff_malicious` passes, since B's kickoff key matches the OP_RETURN key), and B is ultimately reimbursed from the move-to-vault UTXO for a withdrawal it never funded.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
