### Title
Deterministic per-context nonce reuse in `SigningProtocol` lets one validator force multiple signature shares over the same FROST nonce pair, enabling key-share recovery - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
`SigningProtocol::preprocess_internal` derives the FROST preprocess deterministically from a cached seed keyed only by `self.context` (`(b"DkgConfirmer", attempt)` for `DkgConfirmer`). Every call to `share` or `complete` within the same attempt therefore re-executes `sign` with the *same* nonce pair `(d, e)`, while the caller-supplied preprocess map and message determine the binding factors `rho` and challenge. A validator that can cause `share`/`complete` to be re-executed over a different preprocess set or different `key_pair` message obtains a second signature share under reused nonces — the classic FROST nonce-reuse / ROS-style share-reuse condition that yields recovery of the MuSig/FROST secret share.

### Finding Description
- `preprocess_internal` loads `CachedPreprocesses[context]` and rebuilds the sign machine via `AlgorithmSignMachine::from_cache`, which feeds the cached 32-byte seed into `ChaCha20Rng` in `seeded_preprocess` (`crypto/frost/src/sign.rs:121-144`). Same context ⇒ identical nonces and identical commitments.
- `share_internal` (line 156) calls `preprocess_internal` again and then `machine.sign(preprocesses, msg)`, where `preprocesses` and `msg` come from externally supplied data: `share(preprocesses, key_pair)` and `complete(preprocesses, key_pair, shares)` both take the full preprocess map and the `KeyPair` as arguments (`signing_protocol.rs:288-327`).
- In `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:283-380`), the binding factors `rho_i` are derived from the rho transcript covering `group_key`, `hash_msg(msg)`, and a hash of the *entire* preprocess set. Any difference in the preprocess bytes or in `msg` (which is `set_keys_message(set, removed, key_pair)`) changes `rho` and the signing challenge — while our nonces `d, e` stay fixed.
- `DkgConfirmer::share` and `DkgConfirmer::complete` are two separate entry points, each internally invoking `share_internal`. Nothing enforces that the `preprocesses`/`key_pair` passed to `complete` are identical to those passed to `share`; `complete` just re-runs `share_internal` with its own arguments (lines 312-327). The header comment (lines 25-54) explicitly acknowledges this design relies on BFT ordering so that "the received nonce commitments (or the message to be signed)" can never be distinct across re-executions — but it also lists the unmitigated holes: a "logical flaw letting new messages overwrite prior messages" and rebuilds following a distinct chain. Within one attempt/context, any path that re-invokes `share` or `complete` with validator-supplied bytes that differ from the first call re-signs with the same nonce pair.

A FROST share has the form `z = d + e·rho + λ·s·c`. Two shares issued under the same `(d, e)` but different `(rho, c, λ)` give linear equations in `d`, `e`, and `s·λ`. A small number of such reused-nonce shares (a ROS-style set of parallel executions, trivially satisfiable here since `share` and `complete` alone provide two executions per attempt) lets the attacker solve for the secret share `s`. This is precisely the misuse the code comments warn "will presumably cause the signer to leak their secret share" (`sign.rs:217-219`), reached not through integrator misuse but through the protocol's own deterministic re-execution combined with attacker-influenced inputs.

### Impact Explanation
Recovery of a validator's Ristretto secret share — the root-of-trust key used for DKG confirmation via MuSig. With enough validators' shares recovered (each validator runs the same vulnerable `DkgConfirmer`), the attacker reconstructs the validator-set signing capability and can forge `set_keys` confirmations, i.e., register attacker-controlled key pairs for a set. Severity: High — key-share recovery reachable through repeated signing requests.

### Likelihood Explanation
Triggering requires two `share`/`complete` evaluations under the same `(b"DkgConfirmer", attempt)` context whose preprocess sets or `key_pair` differ. The preprocess bytes and the `KeyPair` being confirmed are both supplied by protocol participants on-chain, so a validator controls part of the rho transcript directly. Whether BFT finalization actually prevents two distinct finalized inputs within one attempt depends on the surrounding transaction handling (`handle.rs`), which the code itself flags as relying on invariants and TODOs ("we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)", line 51). Absent that check, a single validator submitting conflicting preprocess data, or a rebuild following a distinct finalized view, suffices. Medium likelihood given the BFT guard but the acknowledged gaps.

### Recommendation
- Bind the cached preprocess to the exact inputs before signing: store alongside `CachedPreprocesses[context]` a commitment to the preprocess set and `msg`, and abort if a subsequent `share`/`complete` presents different bytes (the TODO at line 51 already gestures at this).
- Never sign twice from one seed: make `complete` reuse the `AlgorithmSignatureMachine` produced by `share` (persisted or passed in) rather than re-executing `share_internal` — i.e., eliminate the re-execution model for the signing step.
- If re-execution is kept, include the full serialized preprocess map and `key_pair` hash in the `CachedPreprocesses` key so divergent inputs necessarily derive divergent nonces.

### Proof of Concept
1. Validator V is a participant in `DkgConfirmer` for attempt `a`, context `("DkgConfirmer", a)`.
2. Attempt `a` finalizes a `share` call over preprocess set `P₁` and `key_pair` `K₁`: the coordinator derives seed `S` from `CachedPreprocesses[("DkgConfirmer", a)]`, computes nonces `(d, e)`, and emits share `z₁ = d + e·rho₁ + λ·s·c₁`.
3. Via a conflicting finalized view/rebuild or an overwrite path (both enumerated in the file's own threat discussion, lines 38-51), a second evaluation occurs — e.g., `complete` invoked over a preprocess set `P₂` where V's preprocess bytes differ, or a different `key_pair` `K₂`. `share_internal` reloads the same seed `S`, regenerates `(d, e)`, and emits `z₂ = d + e·rho₂ + λ'·s·c₂`.
4. V collects `z₁, z₂` (and further shares across additional divergent executions — each supplies one more equation in the three unknowns `d`, `e`, `λ·s`). With `rho₁ ≠ rho₂` known publicly, V solves the linear system and recovers the coordinator's MuSig secret share `s`.
5. Repeated across coordinators, V recovers enough shares to forge the `set_keys` MuSig signature for the validator set.

Minimal reproduction harness: instantiate two `AlgorithmSignMachine`s via `from_cache` with the same `CachedPreprocess` seed, call `sign` on each with preprocess maps differing in one participant's bytes, collect both `SignatureShare`s, and solve `z₁ − z₂ = e(rho₁ − rho₂) + s(λc₁ − λ'c₂)`; with a third execution the system is determined and `s` falls out — directly exercising `seeded_preprocess` determinism in `crypto/frost/src/sign.rs:121-144` and the fixed-seed reload in `signing_protocol.rs:137-147`.
