### Title
Payout tx's SIGHASH_SINGLE|ANYONECANPAY leaves the operator-attribution OP_RETURN unsigned, letting anyone re-spend the withdrawal input to permanently freeze the vault UTXO - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary

### Finding Description
`create_payout_txhandler` builds the payout transaction with a single input (the user's withdrawal UTXO) and three outputs: the user payout (`vout 0`), an anchor (`vout 1`), and an OP_RETURN carrying the fronting operator's x-only pubkey (`vout 2`), and finalizes it with `set_p2tr_key_spend_witness(&user_sig, 0)`. [1](#0-0) 

The user's signature is required (and documented) to use `SinglePlusAnyoneCanPay`. [2](#0-1) 

`SIGHASH_SINGLE|ANYONECANPAY` at input index 0 only commits the user to input 0's outpoint and to output 0 (the payout amount/address). It does **not** commit to any other input, nor to output 1 (anchor) or output 2 (the operator-attribution OP_RETURN). `operator.withdraw()` then funds this exact tx handler with `fund_raw_transaction(..., replaceable: None, ...)`, i.e. arbitrary additional funding inputs are appended after the user already signed. [3](#0-2) 

Because the OP_RETURN output and the extra funding inputs are outside the signed scope, anyone who obtains the raw signed input (visible the moment any operator's payout tx enters the mempool/mines, since only one output and one input are pinned) can construct their own competing transaction reusing that same witness, keep output 0 unchanged (so the withdrawer is still paid correctly), replace the funding input(s) with their own, and replace/blank the OP_RETURN. If this transaction is the one that gets mined instead of the legitimate operator's, `update_finalized_payouts` will parse the OP_RETURN and, if it does not contain a valid pubkey, will store `payout_payer_operator_xonly_pk = NULL`: [4](#0-3) 

`get_first_unhandled_payout_by_operator_xonly_pk` only surfaces payouts to an operator whose xonly pubkey exactly matches `payout_payer_operator_xonly_pk`; a `NULL` value is never matched by any operator, so `handle_finalized_payout`/kickoff is never triggered for this withdrawal. [5](#0-4) 

The only alternate recovery path, the optimistic payout (which atomically spends both the withdrawal UTXO and the `MoveToVault` output together via N-of-N signature), explicitly refuses to proceed once the withdrawal UTXO is already spent: [6](#0-5) 

so it cannot be used after the malicious replacement transaction confirms.

### Impact Explanation
The withdrawal is fulfilled correctly for the user (output 0 is protected by the signature), but no operator is ever credited with having fronted the payout, and the vault's `MoveToVault` UTXO can no longer be released through either the normal kickoff/reimburse flow (no operator query matches a `NULL` payer) or the optimistic-payout flow (input already spent). This meets the Critical bar of "a vault UTXO permanently frozen" - the deposited BTC becomes permanently unreachable by the protocol even though the withdrawer was paid.

### Likelihood Explanation
Exploiting this requires only: (1) observing a broadcast (unconfirmed) payout transaction in the mempool - a public, unprivileged action - and (2) constructing/broadcasting a competing transaction that reuses the untouched `SIGHASH_SINGLE|ANYONECANPAY` witness with attacker-controlled funding inputs and a stripped/garbage OP_RETURN, winning the confirmation race (aided by `replaceable: None` leaving RBF policy to the node's default, and by the fact only a single output/input pair is pinned by the signature). No verifier, operator, watchtower, or aggregator role, and no key compromise, is required - any bystander with bitcoin available to front the same payout amount can perform this.

### Recommendation
Extend the sighash type used by the user (or restructure the payout transaction) so that all economically/protocol-relevant outputs, including the operator-attribution OP_RETURN output, are committed by the user's signature (e.g. use `SIGHASH_ALL|ANYONECANPAY` bound to a template that fixes the OP_RETURN position/content, or otherwise commit the OP_RETURN content cryptographically to the signed message) so a third party cannot swap in an unauthenticated/garbage OP_RETURN while reusing the same pre-signed input.

### Proof of Concept
1. User signs a withdrawal payout with `SinglePlusAnyoneCanPay` over `(input#0, output#0)` only, as required by `operator.withdraw()` verification. [2](#0-1) 
2. Honest operator A calls `withdraw`, which builds and funds the payout tx (`create_payout_txhandler`, then `fund_raw_transaction`) with operator A's xonly pubkey in the OP_RETURN, and broadcasts it (unconfirmed). [1](#0-0) [3](#0-2) 
3. An unprivileged observer copies the untouched input-0 witness and output-0, adds its own funding input(s), removes/garbles the OP_RETURN output, and gets this variant confirmed instead (e.g. via fee-bumping/race, since `replaceable` funding option is left `None`).
4. `update_finalized_payouts` scans the block, fails to parse a valid xonly pubkey from the OP_RETURN, and stores `payout_payer_operator_xonly_pk = NULL` for this withdrawal. [4](#0-3) 
5. `get_first_unhandled_payout_by_operator_xonly_pk` never returns this withdrawal to any operator (query filters on a specific `operator_xonly_pk`), so `handle_finalized_payout`/kickoff/reimburse is never triggered. [5](#0-4) 
6. `sign_optimistic_payout` rejects signing because the withdrawal UTXO is already spent, closing off the only remaining path to release the `MoveToVault` funds. [6](#0-5) 

Note: I was not able to fully verify the exact default RBF behavior of `fund_raw_transaction` when `replaceable: None` is passed (this depends on the underlying Bitcoin Core node's wallet configuration, which is outside this repository), so the precise confirmation-race mechanics (RBF vs. plain double-spend race) could not be conclusively confirmed from the code alone; however, the core vulnerability - that the OP_RETURN output and additional funding inputs fall outside the user's signed commitment - is confirmed directly from the transaction-building and signature-verification code cited above.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
