### Title
Deprecated-TokenGateway blacklist is enforced only at the nexus router layer, not inside the trusted mint/transfer function it protects - ([File: parachain/runtimes/nexus/src/ismp.rs], [File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
This is a structural analog of the Rubic finding: a safety blacklist against a known-dangerous counterparty is wired into one calling context but not into the actual privileged function that performs the sensitive action. In Rubic, `ERC20Proxy` calls were blacklisted inside `RubicMultiProxy`/`LibSwap` but not inside `Executor`, which held the same calling permission. In Hyperbridge, the `DEPRECATED_TOKEN_GATEWAY_ADDRESSES` blacklist that rejects messages from retired/compromised `TokenGateway` deployments is implemented only inside `ProxyModule::on_accept` in the **nexus** runtime's ISMP router, not inside `pallet_hyper_fungible_token::Pallet::on_accept`, which is the actual function that trusts `from` and mints/transfers real assets to a beneficiary.

### Finding Description
`ProxyModule::on_accept` in the nexus runtime checks the incoming `PostRequest.from` field against a hardcoded list of deprecated `TokenGateway` addresses before routing the message onward: [1](#0-0) 

This check happens in the router/module-dispatch wrapper, not in the pallet that actually performs the trust decision. The real trust anchor is `pallet_hyper_fungible_token::Pallet::on_accept`, which authenticates purely via the `ContractToAsset::<T>::get(source, &from)` mapping and then unconditionally mints or transfers real assets to whatever beneficiary the message encodes: [2](#0-1) [3](#0-2) 

Nothing inside this pallet function itself checks `DEPRECATED_TOKEN_GATEWAY_ADDRESSES`. That constant and its guard function `is_deprecated_token_gateway` exist exclusively in `parachain/runtimes/nexus/src/ismp.rs` — a targeted `grep_search` across the whole repository confirms these identifiers appear nowhere else, including in the sibling `gargantua` runtime, which has its own `ismp.rs` router: [4](#0-3) 

Because the guard is bolted onto the nexus `ProxyModule` closure rather than into the pallet's `on_accept`, any other calling context that reaches `pallet_hyper_fungible_token::Pallet::on_accept` for the same `(source, from)` pair that is still registered in `ContractToAsset` — such as another parachain runtime hosting the same pallet, or any future/alternate `IsmpRouter` implementation wired to this pallet without duplicating the blacklist — will mint or transfer real assets on trust of a `from` address that governance has already deemed unsafe. This mirrors exactly the Rubic bug's broken invariant: the blacklist is a router-level courtesy check, not an intrinsic property of the privileged function, so it silently disappears wherever the router differs.

### Impact Explanation
If the deprecated `TokenGateway` contract addresses were retired specifically because of a discovered exploit that lets an unauthorized party forge/originate a POST message claiming to be `from` that address (the exact reason such addresses get deprecated), then any code path that dispatches into `pallet_hyper_fungible_token::on_accept` without first applying the nexus-specific blacklist will still honor that forged message and mint/transfer real, rightful-beneficiary-designated assets to an attacker-controlled account. This is unauthorized minting/transfer of bridged assets to the wrong beneficiary — a direct funds-loss impact matching the bounty's "unauthorized execution" / "false proof/state acceptance" categories.

### Likelihood Explanation
The `ContractToAsset` mapping is pallet-level storage, not runtime-scoped, so if a deprecated `TokenGateway` address is still registered there (deprecation of the on-chain contract does not automatically imply its `ContractToAsset` entry was purged), the only thing preventing exploitation on nexus is the router-level check — and that check is provably absent from any other consumer of this pallet in this repository. This requires no privileged actor, relayer collusion, or governance action from the attacker's side; it only requires that a message purporting to originate from the deprecated address reach a routing path lacking the guard, which is a pure code-organization gap rather than a defense actually enforced by the pallet's own authentication logic.

### Recommendation
Move the `is_deprecated_token_gateway` check (or an equivalent revocation registry) directly into `pallet_hyper_fungible_token::Pallet::on_accept`, gated on the `(source, from)` pair looked up via `ContractToAsset`, so that the safety property is guaranteed by the pallet itself regardless of which runtime or router calls into it — analogous to fixing `LibSwap`'s blacklist so it applies wherever ERC20Proxy-calling permission is granted, not just in one caller.

### Proof of Concept
1. Confirm a deprecated `TokenGateway` address (e.g. `0xFd413e3AFe560182C4471F4d143A96d3e259B6dE`) still has a live entry in `ContractToAsset::<T>::get(source, from)` for some `local_asset_id`.
2. Construct/relay a `PostRequest` with `from` = that deprecated address and `to` = the HFT pallet's `ModuleId`, encoding a `Message` with an attacker-controlled `beneficiary` and `amount`.
3. Route this request through any `IsmpModule`/router implementation that dispatches directly to `pallet_hyper_fungible_token::Pallet::on_accept` without first calling `is_deprecated_token_gateway` (i.e., any context other than nexus's `ProxyModule::on_accept`, such as the `gargantua` runtime's router if it also instantiates this pallet, or any future router).
4. Observe that `on_accept` proceeds past `ContractToAsset::get` (line 55) with no blacklist check, decodes the message, and mints/transfers real assets to the attacker's `beneficiary` (lines 93-117) — exactly the outcome the nexus-level blacklist was designed to prevent.

Note: I was unable to fully verify, within tool-call limits, whether `gargantua`'s router currently registers `pallet_hyper_fungible_token` as a destination module (i.e., whether this exact path is *currently* live end-to-end there). What is verified directly from source is that the blacklist is implemented solely in the nexus `ProxyModule` wrapper and is completely absent from the pallet's own `on_accept`, which is the shared, reusable trust boundary — the same structural flaw as the Rubic report.

/// Deprecated TokenGateway contract addresses whose incoming ISMP Post requests
/// must be rejected unconditionally by the nexus runtime.
/// Any [`PostRequest`] whose `from` field matches any of these 20-byte addresses
/// is rejected in [`ProxyModule::on_accept`] before any other processing — the
/// message is neither dispatched locally nor forwarded onwards.
pub const DEPRECATED_TOKEN_GATEWAY_ADDRESSES: &[[u8; 20]] = &[
	// Ethereum / Arbitrum / Optimism / Base / BSC / Gnosis TokenGateway
	hex_literal::hex!("Fd413e3AFe560182C4471F4d143A96d3e259B6dE"),
	// Polygon / Unichain TokenGateway
	hex_literal::hex!("8b536105b6Fae2aE9199f5146D3C57Dfe53b614E"),
	// Soneium TokenGateway
	hex_literal::hex!("Ce304770236f39F9911BfCC51afBdfF3b8635718"),
];

/// Returns `true` if `from` is exactly one of the deprecated TokenGateway
/// contract addresses in [`DEPRECATED_TOKEN_GATEWAY_ADDRESSES`].
fn is_deprecated_token_gateway(from: &[u8]) -> bool {
	DEPRECATED_TOKEN_GATEWAY_ADDRESSES.iter().any(|deprecated| deprecated == from)
}

impl IsmpModule for ProxyModule {
	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		// Permanently reject any request originating from a deprecated TokenGateway
		// deployment, regardless of destination. This short-circuits both the
		// forwarding path (dest != host) and the locally-dispatched path below.
		if is_deprecated_token_gateway(&request.from) {
			return Err(anyhow!(
				"rejecting request from deprecated TokenGateway address {:?} on {:?}",
				request.from,
				request.source,
