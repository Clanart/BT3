Based on my research, the strongest analog to the reported SWC-101-style arithmetic issue is a missing bounds check after timezone-offset arithmetic in Protobuf's own C++ JSON `Timestamp` parser — the same class of bug (an arithmetic adjustment applied to a bounded value with no post-adjustment range validation, silently accepting a value that should be rejected).

### Title
Missing post-offset range validation allows out-of-spec `Timestamp` to be silently accepted by ProtoJSON parser - (File: `src/google/protobuf/json/internal/parser.cc`)

### Summary
The Sherlock report's failure mode is: a value is derived by adding/subtracting an attacker-influenced offset to a bounded quantity (`block.timestamp + threshold`), and the code that is supposed to reject out-of-range results does not, because the final bounds check is missing/wrong. The Protobuf analog is `ParseTimestamp` in `src/google/protobuf/json/internal/parser.cc`, which computes `secs` from the RFC3339 date fields and then applies a `[+-]hh:mm` timezone offset (`secs += (neg ? offset : -offset)`) but never validates the final `secs` against the documented valid `Timestamp` range before storing it into the message. [1](#0-0) 

### Finding Description
`google.protobuf.Timestamp` is documented (and enforced elsewhere in the codebase) to only be valid in the range `[-62135596800, 253402300799]` seconds (`0001-01-01T00:00:00Z` to `9999-12-31T23:59:59.999999999Z`): [2](#0-1) 

`TimeUtil::FromString` (a separate, non-default utility) explicitly enforces this after parsing: [3](#0-2) 

However, the primary ProtoJSON parsing path used by `util::JsonStringToMessage` (`ParseTimestamp` in `parser.cc`) only validates that year/month/day digit groups are individually non-zero and correctly delimited; it computes `secs` from the calendar fields, then adds the signed timezone offset, and immediately writes the result via `Traits::SetInt64` with **no check that the resulting `secs` still lies within `[kTimestampMinSeconds, kTimestampMaxSeconds]`**: [4](#0-3) 

This mirrors the audit report's underflow pattern exactly: a boundary value (`9999-12-31T23:59:59`) combined with an attacker-controlled offset (`-00:01`) pushes the true UTC instant past the maximum supported year, and a boundary value (`0001-01-01T00:00:00`) combined with `+00:01` pushes it before the minimum supported year — both of which should be rejected but currently are not blocked by any check in this function. The upb JSON decoder (`upb/json/decode.c`, `jsondec_timestamp` / mirrored in `ruby-upb.c`) shows the asymmetry even more clearly: it checks only the **lower** bound (`if (seconds.int64_val < -62135596800) jsondec_err(...)`) and has **no upper-bound check at all**, so an over-large positive `secs` (e.g., from a `+9999-12-31...` plus a negative offset) is accepted silently: [5](#0-4) 

The upstream conformance suite explicitly requires rejection of these boundary cases as `REQUIRED` tests (`TimestampJsonInputOffsetBoundaryOverflow`, `TimestampJsonInputOffsetBoundaryUnderflow`, plus the paired `ExpectSerializeFailureForJson` cases for out-of-range proto-side seconds): [6](#0-5) [7](#0-6) 

I was not able to confirm within available tool calls whether these two specific boundary-offset test cases are currently listed as *known, tracked* exceptions in `conformance/failure_list_cpp.txt` / `upb/conformance/conformance_upb_failures.txt` (both files contain multiple Timestamp-related entries, but I could not read their exact line contents in the remaining iterations). This is a material open question: if these exact tests are already tracked as expected failures upstream, this finding is a known issue rather than a new one, which would lower its priority but not its underlying validity as a genuine gap.

### Impact Explanation
A message produced by `JsonStringToMessage` can end up with a `Timestamp.seconds` value outside the documented valid range while parsing succeeds without error. Any downstream consuming application that trusts "successfully parsed ProtoJSON implies a spec-valid `Timestamp`" (a reasonable assumption given the field's documented contract) may perform arithmetic, comparisons, or serialization based on an out-of-range value, producing corrupted or non-round-trippable data (e.g., serializing back to JSON/RFC3339 could produce an invalid or wrapped-around string, or trigger `DCHECK`/`EXPECT_DEATH`-style range assertions elsewhere in the codebase such as `TimeUtil` that assume the invariant holds). This is a data-integrity violation of a well-known type's documented contract, not a crash or memory-safety issue.

### Likelihood Explanation
The trigger requires only a bounded, well-formed ProtoJSON string with a boundary-adjacent date/time and a small timezone offset — no huge inputs, no privileged access, and it is reachable through the standard public `JsonStringToMessage` / upb JSON decode API on any schema containing a `google.protobuf.Timestamp` field. This satisfies the "ordinary client sending bounded ProtoJSON through a supported public parse API" threat model. Likelihood is Medium: the input is trivial to construct, but the resulting corrupted value is a boundary-of-range issue (seconds off by a small amount), not an arbitrarily attacker-controlled or unbounded quantity.

### Recommendation
After computing the offset-adjusted `secs` in `ParseTimestamp` (`parser.cc`), and after computing `seconds.int64_val` in `jsondec_timestamp` (`upb/json/decode.c` and its `ruby-upb.c`/`php-upb.c` mirrors), validate the final value against both `kTimestampMinSeconds` (`-62135596800`) and `kTimestampMaxSeconds` (`253402300799`) and return a parse error (`str->loc.Invalid(...)` / `jsondec_err(...)`) if out of range, matching the check already present in `TimeUtil::FromString`.

### Proof of Concept
Using the C++ JSON parser (`google::protobuf::util::JsonStringToMessage` on a message with an `optional_timestamp` field), feed:
```json
{"optionalTimestamp": "9999-12-31T23:59:59-00:01"}
```
Per the conformance suite this must be a `REQUIRED` parse failure (`TimestampJsonInputOffsetBoundaryOverflow`), because the true UTC instant (`10000-01-01T00:00:00Z`) exceeds `kTimestampMaxSeconds`. Tracing `ParseTimestamp`, no code path between the offset arithmetic at line 916-917 and the final `Traits::SetInt64` at line 931 rejects an out-of-bounds `secs`, so the call is expected to incorrectly succeed and store an out-of-range value; I was not able to execute the actual test binary in this environment to capture a live "did not fail as expected" trace (analogous to the Foundry log in the source report), so this should be confirmed by running `conformance/binary_json_conformance_suite.cc`'s `TimestampJsonInputOffsetBoundaryOverflow`/`Underflow` cases against the C++ and upb backends before treating this as fully confirmed.

bool TimeUtil::FromString(absl::string_view value, Timestamp* timestamp) {
  int64_t seconds;
  int32_t nanos;

    return false;

  // Validate before CreateNormalizedTimestamp, which has a DCHECK on range.

    return false;
  }
  *timestamp = CreateNormalizedTimestamp(seconds, nanos);
  if (!IsTimestampValid(*timestamp)) {
    timestamp->Clear();
    return false;
  }
  return true;
