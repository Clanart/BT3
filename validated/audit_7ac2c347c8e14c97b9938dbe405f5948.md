### Title
Payout tx's OP_RETURN operator-attribution output (idx2) is not covered by the SIGHASH_SINGLE|ANYONECANPAY user signature, letting anyone rewrite which operator is credited for a payout - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` builds the payout transaction as `[user_output(idx0), anchor(idx1), OP_RETURN(idx2)]` and signs only input 0 with `user_sig` via a single taproot key-spend witness. `Verifier::update_finalized_payouts` later trusts whatever OP_RETURN appears in the transaction that actually gets mined at that outpoint, with no check that the named operator xonly_pk is cryptographically tied to that specific transaction.

### Finding Description
Binding claimed to hold: `withdrawals.payout_payer_operator_xonly_pk` (as written by `Verifier::update_finalized_payouts`) == xonly_pk of the operator who actually funded/broadcast the mined payout for that withdrawal index.

Code path:
- `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) builds: output0 = user payout, output1 = anchor, output2 = `op_return_txout(operator_xonly_pk)`, and calls `txhandler.set_p2tr_key_spend_witness(&user_sig, 0)` — a single witness for input 0. [1](#0-0) 
- If `user_sig` carries `SIGHASH_SINGLE|ANYONECANPAY`, the Taproot sighash for input 0 commits only to input 0 and output 0 (BIP341 rules for SINGLE/ANYONECANPAY); outputs 1 (anchor) and 2 (OP_RETURN with `operator_xonly_pk`) are **not** covered by that signature.
- `Verifier::update_finalized_payouts` (core/src/verifier.rs:2283-2353) looks up whichever transaction is actually confirmed for the tracked payout txid, extracts the first OP_RETURN via `get_first_op_return_output`/`parse_op_return_data`, and writes the parsed xonly_pk straight into the DB via `update_payout_txs_and_payer_operator_xonly_pk` (core/src/database/verifier.rs:198-251) with **no verification** that this xonly_pk corresponds to a party who actually signed or authored that output. [2](#0-1) 

Exploit flow: an attacker (any party who can observe the mempool/off-chain-relayed `user_sig`, or capture an honest operator's broadcast-but-unconfirmed payout tx) copies input 0's exact witness (same `user_sig`) onto a new transaction with the same input outpoint and same output0, but replaces outputs 1/2 with an arbitrary anchor and a forged OP_RETURN naming any xonly_pk (a rival operator's key, or a non-existent key). Since the signature does not commit to outputs 1/2, this new transaction is validly signed. The attacker pays a higher fee and gets it mined (via RBF or a race) instead of the honest operator's original broadcast.

Why guards fail: no code path re-verifies operator authorship of the OP_RETURN content; the only signature present is `user_sig`, whose sighash flags explicitly exclude outputs 1 and 2 from commitment. `SECP.verify_schnorr`/musig session checks are not invoked for output construction here, and `update_finalized_payouts` performs a pure syntactic parse of whatever landed on-chain.

### Impact Explanation
`get_first_unhandled_payout_by_operator_xonly_pk`, used by `PayoutCheckerTask` (core/src/task/payout_checker.rs:41-47), filters strictly on `payout_payer_operator_xonly_pk == self.operator.signer.xonly_public_key`. If the attacker's forged OP_RETURN names a different key than the honest operator who actually caused the payout, that honest operator's query never returns this withdrawal, so it can never call `handle_finalized_payout`/kickoff for the corresponding deposit — an honest operator becomes permanently unable to be reimbursed. If the forged key does not belong to any real registered operator, no operator will ever match it, and the deposit's move-to-vault UTXO becomes permanently unreimbursable/frozen. Both outcomes map to Critical impact categories ("an honest operator permanently unable to be reimbursed" / "a move-to-vault UTXO permanently frozen"). The attack is repeatable per withdrawal and requires no special privileges — only fee-paying capability and mempool visibility.

### Likelihood Explanation
Preconditions: the payout tx's user signature must use `SIGHASH_SINGLE|ANYONECANPAY` (as stated in the question's preconditions) and be visible before confirmation (via mempool broadcast by the honest operator, or via off-chain relay of the signature to multiple operators, which the code comments explicitly describe: "the signature given to operators off-chain"). Attacker cost is only Bitcoin transaction fees needed to win an RBF/mining race; no BTC value needs to be risked since the attacker doesn't need to fund the output itself (output 0 is fixed by the committed sighash). This is feasible for any unprivileged party monitoring the mempool and is repeatable across every withdrawal that reaches this stage.

### Recommendation
Bind the operator-attribution output cryptographically to the funding operator, e.g. require the user signature to use `SIGHASH_DEFAULT`/`SIGHASH_ALL` (covering the anchor and OP_RETURN outputs) so no output can be altered post-signature, or have the operator additionally co-sign a commitment to their own xonly_pk before the payout is accepted. Additionally, `update_finalized_payouts` should not trust an unauthenticated OP_RETURN for attribution; require an operator-signed claim (e.g., a separate confirmation tied to the operator's own key) before crediting `payout_payer_operator_xonly_pk`.
