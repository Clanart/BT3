## Analysis Result: Valid — Cross-Flow Signature/Nonce Collision Confirmed

I verified the byte-level collision the question hypothesizes actually exists, and it is not merely theoretical — it is a genuine flaw in how the two message-hashing functions are constructed and how the shared `Nonce` double-map is consumed.

### Root cause

`withdrawal.rs::message()` and `accumulate.rs::beneficiary_message()` produce **identical** `keccak256` digests for identical `(nonce, state_machine, beneficiary)` inputs: [1](#0-0) [2](#0-1) 

Both hash a SCALE-encoded tuple `(u64, StateMachine, bytes)`. SCALE's `Encode` for `Vec<u8>` and `&[u8]` produce the same compact-length-prefixed byte layout for identical content, so `message(nonce, chain, Some(beneficiary))` and `beneficiary_message(nonce, chain, &beneficiary)` are byte-for-byte identical when the tuple values match. (Only the `None`-beneficiary branch of `message()`, which hashes a 2-tuple, differs.)

Both flows also key the shared `Nonce<T>` double-map by `(signer_address, state_machine)`:
- `withdraw()` reads/increments `Nonce::<T>::get(address, dest_chain)` where `address` is the signer recovered directly from the supplied `Signature`. [3](#0-2) [4](#0-3) 
- `accumulate()` reads/increments `Nonce::<T>::get(delivery_address, state_machine)` where `delivery_address` is derived from the proven ISMP delivery receipt (must equal the recovered signer). [5](#0-4) 

Because both extrinsics (`withdraw_fees`, `accumulate_fees`) are dispatched as **unsigned** transactions validated only by `ValidateUnsigned::validate_unsigned`, any unprivileged party can submit either call with attacker-supplied payload data — the pallet does not check that a signature was produced for a specific call type: [6](#0-5) 

### Impact

An attacker who observes a `beneficiary_message(N, X, B)` signature (created by relayer `A` to authorize a *future* fee redirect via `accumulate_fees`) can repackage the same bytes as `WithdrawalInputData { signature, dest_chain: X, beneficiary: Some(B) }` and submit it directly to `withdraw_fees`. Since `message(N, X, Some(B)) == beneficiary_message(N, X, B)`, signature verification passes, and this:

1. Immediately dispatches an ISMP withdrawal of **all currently accumulated `Fees::<T>[X][A]`** to `B`, zeroing the balance — a fund-moving action `A` never authorized for that timing/amount, only for a specific `accumulate_fees` batch claim. [7](#0-6) 
2. Consumes `Nonce(A, X)`, incrementing it past the value embedded in the not-yet-submitted `accumulate_fees` proof, causing the *legitimate* `accumulate_fees` call to fail signature verification (`Error::InvalidSignature`), since its embedded nonce no longer matches current state. [8](#0-7) 

The reverse direction (using a `withdraw` signature to satisfy `accumulate`'s `beneficiary_details`) is also possible when `withdrawal_data.beneficiary` is `Some`, subject to `accumulate()`'s additional constraint that the signer must match a proven `delivery_address` for that batch.

Note: because the beneficiary address is embedded inside the hashed message, the attacker **cannot redirect funds to themselves** — funds still go to whatever beneficiary `A` originally specified. The concrete damage is (a) forced/unauthorized premature execution of a real fund transfer outside its intended context, and (b) desynchronization of the shared nonce that breaks the counterpart flow's expected/pre-signed nonce, per the "broken ... reward accounting" and "unauthorized execution" criteria in the Impact Gate.

### Existing tests only cover within-flow replay

The test suite verifies that a `beneficiary_message` signed for one *chain* cannot be replayed on another chain within `accumulate_fees` itself: [9](#0-8) [10](#0-9) 

There is no test guarding the **cross-flow** case (a `beneficiary_message` accepted by `withdraw_fees`, or vice versa), confirming the gap.

### Title
Cross-Flow Signature Confusion Between `withdraw()` and `accumulate()` via Identical Message Encoding and Shared Nonce - (File: `modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`withdrawal::message(nonce, dest_chain, Some(beneficiary))` and `accumulate::beneficiary_message(nonce, state_machine, beneficiary)` hash identical SCALE-encoded tuples, producing identical digests for the same `(nonce, chain, beneficiary)` triple. Both `withdraw_fees` and `accumulate_fees` are permissionless (unsigned) extrinsics that consume the same `Nonce<T>` double-map keyed by `(address, state_machine)`. A signature a relayer produced to authorize a fee-accumulation beneficiary redirect can be repackaged and submitted to `withdraw_fees` (or vice versa), triggering the other flow's on-chain effects and consuming its nonce.

### Finding Description
See root cause analysis above — the two message constructors are format-compatible and the nonce namespace is shared without any domain separator (e.g., a purpose tag) distinguishing "withdraw" from "accumulate-redirect" intents.

### Impact Explanation
An unprivileged actor can force an unauthorized, out-of-context execution of `withdraw_fees` using a signature only intended to authorize a specific `accumulate_fees` beneficiary redirect (or the reverse), causing an unintended immediate fund transfer and desynchronizing the shared nonce so the legitimately intended call fails signature verification, breaking the relayer's fee-accounting/settlement flow.

### Likelihood Explanation
Requires only that an attacker observe a previously-broadcast/pending signed message (these are transmitted as plain call data in unsigned extrinsics, e.g. via mempool or on submitted transactions) and resubmit it with a different call wrapper before the intended call lands — feasible for any unprivileged network participant, no compromised infrastructure required.

### Recommendation
Domain-separate the two signed payloads, e.g. by prefixing each hash with a distinct constant/tag (`b"WITHDRAW"` vs `b"BENEFICIARY_REDIRECT"`) before hashing, or by using distinct nonce namespaces (separate double-maps) for `withdraw()` and `accumulate()`'s beneficiary redirect so a signature valid in one context can never be replayed in the other.

### Proof of Concept
Unit test outline (as suggested by the question): construct `withdrawal::message(5, StateMachine::Evm(1), Some(beneficiary_bytes))` and `accumulate::beneficiary_message(5, StateMachine::Evm(1), &beneficiary_bytes)` and assert equality of the returned `[u8;32]` — they are equal because SCALE encoding of `Vec<u8>` and `&[u8]` are identical for the same content, confirmed by direct inspection of [1](#0-0)  and [2](#0-1) . A follow-up integration test would sign this shared digest, submit it via `withdraw_fees`, and then attempt the pre-built `accumulate_fees` call with the same nonce — the second call fails with `Error::InvalidSignature` due to the nonce increment from the first, demonstrating the desync.
