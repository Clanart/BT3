### Title
Stale line-index-based partial commit selection can silently commit unintended content after concurrent working-directory mutation - (File: app/src/lib/stores/app-store.ts, app/src/models/diff/diff-selection.ts)

### Summary
GitHub Desktop's partial-commit ("stage hunk/line") accounting tracks which lines of a file are staged purely by **numeric line index**, not by line content or diff hash. This index-based selection is preserved across independent, asynchronous status/diff refresh cycles by matching on file path (`id`) alone. If the working-directory file content changes between the time a diff is loaded/selected and the time the commit is executed (e.g., due to a fetch/checkout/merge/rebase driven by an attacker-controlled remote, or another process editing the file), the previously selected line indices are silently reapplied to the *new* content at commit time, without the user ever seeing or re-confirming the actual lines being committed.

### Finding Description
`_commitIncludedChanges` reads whatever `file.selection` is currently stored in `repositoryStateCache` at the moment `Commit` is clicked and passes it straight to `createCommit` [4](#0-3) . That `selection` object is a `DiffSelection` that records "diverging lines" purely as line-number indices [5](#0-4) .

Whenever a background status refresh occurs (triggered by file-system watcher events, fetch, pull, checkout, or `RepositoryIndicatorUpdater`-style periodic refresh), `updateChangedFiles` merges the new working-directory status with the old one by looking the file up by `id` (path) and simply carrying the **old** `DiffSelection` object forward onto the **new** `WorkingDirectoryFileChange`, unconditionally: `return file.withSelection(existingFile.selection)` [6](#0-5) . There is no check that the file's underlying diff/content is the same as when the selection was made.

The diff itself is reloaded separately and later, in `updateChangesWorkingDirectoryDiff`, which recomputes the set of "selectable" line indices from the *new* diff and calls `withSelectableLines` on the *stale* selection object [7](#0-6) . As the code comment itself acknowledges: *"The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines"* [8](#0-7) . `withSelectableLines` only intersects indices; it does not diff old vs. new content to invalidate positions whose content changed but index still exists [1](#0-0) .

Because the diff reload (`getWorkingDirectoryDiff`) and the eventual commit action run asynchronously and independently, there is a window where: (1) user selects specific lines of a file for partial commit, (2) the working tree content at those same line indices changes (via a background git operation such as an automatic fetch+merge/rebase, a stash pop, a checkout, or any external process touching the file while Desktop is not focused), (3) status/diff refresh recomputes selectable line indices but reuses the old diverging-line index set, and (4) the user clicks Commit before/without noticing the diff view has silently changed content at those indices. The resulting commit is created from `selectedFiles` whose `DiffSelection` no longer corresponds to what the user actually reviewed and intended to stage [9](#0-8) .

This directly parallels the reported bug class: an internal accounting structure (line-selection bitmap here; share/deposit tracking there) is updated/maintained independently of the authoritative source of truth (the live diff content here; the gauge's balance there), and events that change the authoritative state (content changes here; deposits/withdrawals there) are not reliably reflected back into the accounting structure, producing a silent mismatch that is only exposed at the moment of a state-changing action (commit here; reward accrual there).

### Impact Explanation
If exploitable, this results in silent corruption of what the user actually commits and pushes — lines that were never reviewed by the user in their current form can be included in (or excluded from) a commit without any warning, matching the "silent corruption of what the user commits or pushes" impact category. This could be leveraged by an attacker who can influence content changes to a working file at the right moment (e.g., a malicious pre/post-checkout or post-merge hook rewriting a file, or a background sync tool) to smuggle unreviewed content into a commit that the user believes only contains their manually-selected lines.

### Likelihood Explanation
Exploitation requires precise timing between a content-changing event and the user's commit action, and depends on Desktop's asynchronous refresh cadence, so likelihood is limited but the window is real and repeatedly triggered on every status refresh cycle while a partial selection exists. No local/physical access or elevated privileges are needed beyond ordinary use of Desktop with a repository whose content or hooks can be influenced (e.g., cloned/fetched from an attacker-controlled remote that runs a hook or triggers a background operation). I was not able to fully verify from static code alone whether existing UI safeguards (e.g., disabling the Commit button during refresh, or forcing synchronous diff reconciliation before commit) fully close this window — this would require dynamic/runtime verification of `withIsCommitting` and refresh scheduling that I could not trace end-to-end within the available context.

### Recommendation
Bind partial-selection state to diff content identity (e.g., a hash of the diff/hunk content or line text) rather than raw line indices, and invalidate/re-derive the selection whenever the underlying diff has changed rather than merely re-intersecting selectable indices. Alternatively, force a synchronous, up-to-date diff/status reconciliation immediately before `_commitIncludedChanges` executes, and abort/reprompt the user if the file's diff has changed since the selection was last confirmed.

### Proof of Concept
Not independently verified end-to-end at runtime; the concrete reproduction would require: (1) partially select lines 1–3 of a file, (2) trigger an external content change to the same file at those line indices via a background git operation (e.g., an automated `post-checkout`/`post-merge` hook from a fetched branch, or a concurrent file write) before Desktop's next status/diff refresh completes, (3) observe that `updateChangedFiles` carries forward the old `DiffSelection` object [6](#0-5)  and that `updateChangesWorkingDirectoryDiff` reapplies it to the new diff via `withSelectableLines` without content validation [7](#0-6) , then (4) commit and inspect the resulting commit diff for content the user did not knowingly review at commit time.
