## Finding: Stale line-selection indices are trusted against a freshly re-fetched diff, allowing partial commits to include unintended content

### Title
Partial-commit line selection is validated by index existence only, not content identity, causing silent corruption of committed hunks - (File: `app/src/lib/stores/app-store.ts`, `app/src/lib/patch-formatter.ts`, `app/src/lib/git/apply.ts`)

### Summary
The reported Derby bug is a "stale value trusted without re-validation" class: a deadline check is skipped, so a swap executes against an outdated price and a bystander can exploit the window between price observation and execution. The closest verifiable analog in GitHub Desktop's local code is the partial-commit ("stage some lines") feature: the user's line selection is captured as a set of *absolute diff indices* against one diff snapshot, but at commit/apply time Desktop re-fetches a fresh diff from disk and reconciles the old selection with the new diff by checking only whether the index still exists as an "includeable" line — not whether it still corresponds to the same textual change the user actually reviewed and clicked on.

### Finding Description
When a file is selected in the Changes pane, Desktop loads a diff and the UI records the user's line-level selections as absolute indices into that diff's hunks (`file.selection.isSelected(absoluteIndex)`), consumed later in `formatPatch`: [1](#0-0) 

If the working directory changes in the background (e.g. another process, an editor autosave, a build/lint step, or a git filter/hook triggered by a different git operation on the same repo) while the diff is being reloaded, `updateChangesWorkingDirectoryDiff` explicitly acknowledges it does not re-validate that previously selected lines are still semantically the same lines — it only drops indices that no longer exist: [2](#0-1) 

Separately, `applyPatchToIndex` (used to stage partial selections) re-fetches the diff from disk immediately before building the patch, decoupled from whatever diff the user visually reviewed when making the selection: [3](#0-2) 

The commit path (`_commitIncludedChanges` → `createCommit` → `stageFiles`/`applyPatchToIndex`) filters files purely by `file.selection.getSelectionType()` and passes the in-memory selection through to the patch builder without re-diffing against what the user last visually confirmed: [4](#0-3) 

The broken invariant: the UI's selection (an index-based approximation of "what the user wants to commit") is treated as still valid at commit time as long as the index still points to *some* includeable line in the freshly-fetched diff — regardless of whether that line's actual content matches what the user saw and intentionally selected.

### Impact Explanation
If the working tree is mutated between the moment the user reviews/selects lines and the moment they click "Commit" — a scenario a malicious or misbehaving repository can help trigger (e.g. via a `clean`/`smudge` filter defined in `.gitattributes`, a `post-checkout`/`post-merge` hook run by a concurrent git operation, or an automated formatter/build step wired into the repo's tooling) — the user may unknowingly commit (and subsequently push) content different from what they reviewed and explicitly selected. This is a silent corruption of what the user commits, which is one of the explicitly accepted impact categories.

### Likelihood Explanation
This requires a background/concurrent modification of tracked files while the Changes pane's diff is stale relative to disk — a narrow race window, but one Desktop's own code comment (`app-store.ts` line 3480-3485) acknowledges is not properly handled ("the diff might have changed dramatically... but for now we'll settle on just updating the selectable lines"). It does not require local/physical access beyond the user's normal workflow of cloning/opening an untrusted repository that ships filters or hooks capable of rewriting tracked files.

### Recommendation
Before applying a partial-selection patch or committing, re-diff the file and validate that each selected line's *content* (not just its index) matches the content in the diff snapshot the selection was derived from; if mismatched, invalidate the stale selection and force the user to re-review before allowing the commit, rather than silently normalizing to "still includeable."

### Proof of Concept
Conceptual PoC (cannot be executed without a live Desktop build/test harness):
1. Open a repository in Desktop with a modified file and expand its diff; select only specific added lines by index (partial commit selection).
2. Before clicking "Commit", trigger a background rewrite of the same file on disk (e.g., a `clean` filter, an editor autosave, or an external script) that changes line content but keeps the same number/position of includeable lines.
3. Click "Commit". `applyPatchToIndex` re-fetches the diff fresh from disk and `formatPatch` reapplies the old absolute-index selection against this new diff.
4. The resulting commit includes different textual content than what the user visually selected, without any warning, because `updateChangesWorkingDirectoryDiff`'s reconciliation only checks index existence, not content identity.

I could not verify at runtime how frequently/likely this race actually is exploited in practice (e.g., exact timing windows in `updateChangesWorkingDirectoryDiff` vs. the debounce before commit), since this requires live testing beyond static code review.
