### Title
Session-scope-covers check silently bypasses forced reauthentication when the stored session has an empty scope - ([File: lib/shopify_app/access_scopes/user_strategy.rb])

### Summary
The reported bug class is: an owner/operator changes a configuration parameter without accounting for pre-existing state, causing that state to silently escape the mechanism meant to govern it. The `UserStrategy.covers_scopes?` method in `lib/shopify_app/access_scopes/user_strategy.rb` exhibits the same class of flaw in the "access scope checks" surface: when the app owner turns on `reauth_on_access_scope_changes` (raising the bar for what scopes a session must carry) sessions with an empty/blank stored scope are treated as automatically satisfying *any* required scope set, instead of being forced to re-authenticate.

### Finding Description
`login_protection.rb`'s `activate_shopify_session` is the gate used by `EnsureHasSession`/`EnsureAuthenticatedLinks` to authorize every authenticated request: [1](#0-0) 

It only forces re-login when `user_access_scopes_strategy.covers_scopes?` returns `false`. The default strategy used when `reauth_on_access_scope_changes` is enabled is `UserStrategy`: [2](#0-1) 

`covers_scopes?` is implemented as: [3](#0-2) 

```ruby
def covers_scopes?(current_shopify_session)
  # NOTE: this not Ruby's `covers?` method, it is defined in ShopifyAPI::Auth::AuthScopes
  current_shopify_session.scope.to_a.empty? || current_shopify_session.scope.covers?(ShopifyAPI::Context.scope)
end
```

If `current_shopify_session.scope` is empty (`.to_a.empty?` is `true`), the method short-circuits to `true` regardless of what scopes `ShopifyAPI::Context.scope` (the app's currently configured/required scopes) demands. This mirrors the reported bug class exactly: the operator/host raises a requirement (`max_slot`/required scopes) after the fact, but the code doesn't check whether pre-existing state (bids in truncated slots / stored sessions with an empty scope) is compatible with the new requirement — it just lets that state continue to be honored as if nothing changed.

Any session whose `scope` attribute is empty (e.g., legacy sessions created before scope was tracked, a session where the storage layer/subclass fails to populate `scope`, or any session object constructed with a blank scope) will pass `covers_scopes?` unconditionally and be activated by `activate_shopify_session` without being forced through the OAuth flow to re-grant the scopes the app now requires. This defeats the entire purpose of `reauth_on_access_scope_changes`.

### Impact Explanation
The impact is a logic bypass of the scope-enforcement/reauthentication mechanism: a stored session that should be considered "insufficiently scoped" (empty scope) is instead treated as fully covering the app's current requirements, and the request is allowed to proceed with an activated session that may lack the necessary Shopify API permissions the app's authorization model assumes are present. This can let API calls execute against Shopify with a token whose actual granted scopes may no longer match what the app's business logic assumes was verified, similar to how leftover un-truncated bids in the original report kept operating under stale assumptions.

### Likelihood Explanation
Reachable in a fully unprivileged way by any request that carries a valid (but scope-empty) session cookie/session-token for `EnsureHasSession`-protected controllers, once the app operator has `reauth_on_access_scope_changes = true`. The precondition (`scope` being empty on the stored session) is realistic for legacy/older sessions or any code path that persists a session object without setting `scope`, and does not require any special access beyond holding a previously valid session.

### Recommendation
`covers_scopes?` should not treat an empty scope as satisfying every possible required-scope set. Instead of `current_shopify_session.scope.to_a.empty? || ...`, an empty scope should be treated as *not* covering the configured scopes (i.e., force reauthentication), unless the app is explicitly running with no configured scopes at all (in which case `ShopifyAPI::Context.scope` would itself be empty and `covers?` would naturally return true).

### Proof of Concept
1. App operator sets `config.reauth_on_access_scope_changes = true` and configures `ShopifyAPI::Context` with `scope: ["read_orders", "write_orders"]`.
2. A stored `ShopifyAPI::Auth::Session` exists (e.g., a legacy session, or one persisted through a path that never populated `scope`) with `session.scope` empty.
3. A request carrying this session's cookie/session-token hits a controller including `EnsureHasSession` → `activate_shopify_session`.
4. `ShopifyApp.configuration.user_access_scopes_strategy.covers_scopes?(current_shopify_session)` is invoked; because `current_shopify_session.scope.to_a.empty?` is `true`, it returns `true` immediately.
5. The check at `lib/shopify_app/controller_concerns/login_protection.rb:37-41` is skipped, the session is activated via `ShopifyAPI::Context.activate_session`, and the request proceeds — even though the session's actual granted scopes (empty) do not cover `["read_orders", "write_orders"]`, and no reauthentication is forced.
