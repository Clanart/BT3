## Finding [1](#0-0) 

The Scroll "lack of refunds" bug (funds stuck when a post-transfer callback reverts) has a more severe analog in this codebase: instead of funds simply being *stuck*, an unrelated post-transfer failure causes the transferred value to be **duplicated** across both chains.

### Title
Native ERC20 IBC round-trip token duplication via erroneous Error Acknowledgement after already-committed unescrow — (`x/erc20/ibc_middleware.go`, `x/erc20/keeper/ibc_callbacks.go`)

### Summary
`IBCMiddleware.OnRecvPacket` first delegates to the base ICS20 transfer module (`im.Module.OnRecvPacket`), which unescrows/mints the Cosmos coin to the receiver directly against the real (uncached) `ctx` and returns a success acknowledgement. The middleware then invokes `k.OnRecvPacket`, an auxiliary post-processing step that tries to auto-convert the received Cosmos coin into its ERC20 representation. If this auxiliary conversion fails for any reason (disabled bank send, minting restrictions, self-destructed ERC20 contract, decimals mismatch, etc.), the middleware discards the already-successful ack and instead returns a brand-new `channeltypes.NewErrorAcknowledgement(err)`. [2](#0-1) 

### Finding Description
The base transfer's unescrow/mint to the receiver is not rolled back — it was already committed against the live context before the ERC20 conversion step even runs. The test suite explicitly documents and validates this behavior: [3](#0-2) 

The comment "SendEnabled=false will cause the conversion of bank tokens to erc20 tokens to fail, **but not send them back to escrow**" and the subsequent assertion that a "trapped" balance equal to `recvAmt` lands in an isolated address confirms that the receiving chain keeps (delivers) the transferred value even though it returns a failure acknowledgement. [4](#0-3) 

Because the acknowledgement is what governs the sending (source) chain's `OnAcknowledgementPacket`/refund logic, a returned `Acknowledgement_Error` on this packet will cause the **source chain to refund/re-credit the original sender** as if the transfer failed — even though the destination chain has already irreversibly delivered the corresponding value to the receiver (or the isolated receiver address used for callback processing). The middleware conflates two independent outcomes — "did the ICS20 transfer succeed" and "did the optional ERC20 auto-conversion succeed" — into a single acknowledgement value, when only the former should determine packet success/failure.

### Impact Explanation
This breaks the fundamental 1:1 accounting invariant between escrowed/native balances across chains, matching the Critical impact category of "unauthorized... duplication... of spendable user value across native balances, EVM balances, ERC20 representations, IBC escrows". An attacker (or even an innocent user under specific conditions like a paused/disabled `SendEnabled` denom, a token pair with minting disabled, or a self-destructed underlying ERC20 contract) can trigger a state where:
1. The destination chain delivers real value to the receiver (unescrowed native coin, later converted or claimable).
2. The source chain treats the packet as failed and refunds/re-credits the sender the same amount.

This effectively duplicates the transferred amount across two independently controlled accounts on two chains.

### Likelihood Explanation
The precondition (auxiliary ERC20 conversion failing after the underlying transfer succeeds) is not artificial — it is directly reachable by an unprivileged actor through ordinary conditions such as `SendEnabled=false` for the denom, `MintingEnabled` returning an error, or `ConvertCoinNativeERC20` failing due to a self-destructed/broken ERC20 contract, all of which are explicitly tested and acknowledged code paths in this repository.

### Recommendation
Decouple the ICS20 transfer success/failure semantics from the auxiliary ERC20 auto-conversion step. If the underlying transfer already succeeded (unescrow/mint committed), the acknowledgement returned to the counterparty chain must remain a success ack regardless of whether the auxiliary ERC20 conversion succeeds; on conversion failure, the code should fall back to leaving the Cosmos-coin representation with the receiver (as already partially implemented) without also signaling a packet-level failure that triggers a source-chain refund.

### Proof of Concept
Reference `evmd/tests/ibc/ibc_middleware_test.go`'s `TestOnRecvPacketNativeErc20` "withCallback" case: disable `SendEnabled` for the native ERC20 denom, relay a return packet, and observe that `OnRecvPacket` both unescrows tokens into an isolated/receiver address (per `checkEscrow`/trapped-balance assertions) AND returns `ack.Success() == false`. Extending this test to actually relay the resulting error acknowledgement back to the source chain (instead of asserting locally) would show the source chain independently refunding the sender, completing the duplication. func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}
