### Title
Path‑containment check in `resolveWithin()` uses an unanchored `startsWith`, allowing sibling‑directory escape when validating attacker‑controlled paths from deep links and merge‑conflict resolutions - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` is GitHub Desktop's single security primitive for answering "is this resolved path actually inside the repository root?" before the app opens or writes a file at a path that originates from untrusted input (a deep‑link `filepath` query parameter, or a conflicted file path reported for a repository being merged). The containment check is implemented as a raw string `startsWith()` comparison between the real (symlink‑resolved) target and the real root, with no verification that a path separator immediately follows the root in the resolved string. This is analogous to the original report's core flaw: two values that are assumed to be expressed in a compatible/normalized form (18‑decimals vs. arbitrary decimals) are compared directly, and the comparison silently "passes" when the invariant it's supposed to enforce doesn't actually hold.

### Finding Description
The containment logic: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` performs a raw character‑prefix comparison, not a path‑segment comparison. If `realRoot` is `/Users/victim/Documents/GitHub/foo` and a sibling directory `/Users/victim/Documents/GitHub/foo-secrets` exists on disk, then a resolved path such as `/Users/victim/Documents/GitHub/foo-secrets/config.json` will satisfy `realResolved.startsWith(realRoot)` even though it is not inside `foo` at all — it is a sibling whose name merely shares the same string prefix. The function returns this path as "safely resolved" instead of `null`.

This primitive is reused verbatim to gate two attacker‑reachable code paths:

1. **Deep‑link `filepath` handling** — `parseAppURL()` accepts an unvalidated `filepath` query parameter from `x-github-client://`/`github-mac://openRepo` URLs (a link the user clicks), which `dispatcher.openRepositoryFromUrl()` resolves against the freshly cloned/selected repository path: [2](#0-1) 
The repository name itself is attacker‑chosen (it comes from the attacker's own `url` in the link, then sanitized only for traversal characters, not for prefix‑collision), so an attacker can pick a repo name that is a documented prefix of a folder the victim is known/likely to already have cloned (e.g. targeting a common naming convention like `<org>` vs `<org>-secrets`, or `app` vs `app-config`), then set `filepath=../<sibling>/<target-file>`.

2. **Copilot AI merge‑conflict resolution file write** — after computing an AI‑generated resolution for a conflicted file, the app resolves the target path with the same primitive and then writes content to it: [3](#0-2) 
Here the destination is built from `repository.path` (attacker‑influenceable via the cloned repo's name/location) plus `resolution.path` (derived from file paths present in the working tree during a merge/rebase against attacker‑controlled remote content). If the resolved path lands in a sibling directory due to the prefix bug, `writeFile()` silently corrupts a file outside the intended repository instead of the guard rejecting it.

The existing unit tests for `resolveWithin()` only cover `../` traversal and symlink escapes — both of which are correctly blocked — but do not test the sibling‑prefix case, so the gap is unexercised and unnoticed: [4](#0-3) 

### Impact Explanation
A successful sibling‑prefix collision causes the file‑write/open guard to accept a path outside the repository it was supposed to constrain. Depending on the reachable call site this can:
- Cause the Copilot conflict‑resolution feature to write resolved file content to a file outside the current repository (silent corruption of an unrelated tracked file the user did not intend to touch).
- Reveal/operate on a file outside the intended repository via the deep‑link `filepath` flow.

This matches the requested impact class of "silent corruption of what the user commits" and "file write... outside the repo," reached purely through a clicked deep link or attacker‑influenced repository/merge content, with no local/physical access or prior compromise required.

### Likelihood Explanation
Exploitation requires a pre‑existing sibling directory on the victim's filesystem whose name is a superstring of the repository's directory name (e.g., two related repos cloned side‑by‑side, a common pattern for GitHub orgs/monorepo companions). This is a real but not universal precondition, so likelihood is moderate rather than trivial — it depends on the victim's existing clone layout, which an attacker cannot directly control but can reasonably predict for common naming schemes.

### Recommendation
Fix `_resolveWithin()` in `app/src/lib/path.ts` to require a path‑separator boundary (or exact equality) after the root prefix, e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add a regression test asserting that a sibling directory sharing a string prefix with the root (e.g. root `/tmp/foo`, target `/tmp/foo-evil/x`) is rejected.

### Proof of Concept
1. Victim has cloned two repositories side by side: `~/Documents/GitHub/foo` and `~/Documents/GitHub/foo-secrets`.
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/attacker/foo?filepath=../foo-secrets/secret.txt`.
3. Victim clicks the link; Desktop resolves/opens `foo`, then calls `resolveWithin(repoPathForFoo, "../foo-secrets/secret.txt")`.
4. `realResolved` = `.../GitHub/foo-secrets/secret.txt`, `realRoot` = `.../GitHub/foo`; `realResolved.startsWith(realRoot)` is `true` because the string `"foo-secrets"` starts with `"foo"`.
5. The guard returns the path as valid, and `shell.showItemInFolder()` (or, in the Copilot‑resolution path, `writeFile()`) operates on a file outside the `foo` repository. [5](#0-4) [6](#0-5) [3](#0-2)

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```

```typescript
  describe('resolveWithin', () => {
    const root = process.cwd()

    it('fails for paths outside of the root', async () => {
      assert((await resolveWithin(root, join('..'))) === null)
      assert((await resolveWithin(root, join('..', '..'))) === null)
    })

    it('succeeds for paths that traverse out, and then back into, the root', async () => {
      assert.equal(await resolveWithin(root, join('..', basename(root))), root)
    })

    it('fails for paths containing null bytes', async () => {
      assert((await resolveWithin(root, 'foo\0bar')) === null)
    })

    it('succeeds for absolute relative paths as long as they stay within the root', async () => {
      const parent = resolve(root, '..')
      assert.equal(await resolveWithin(parent, root), root)
```
