### Title
Reward re-mint via live `mWomSV` balance re-read in `calDoubledCounted` - ([File: wombat/ArbWomUp3.sol])

### Summary
`incentiveDeposit` computes the MGP reward for a `mode == 2` (lock) deposit by subtracting `calDoubledCounted(_account)`, which is derived on the fly from `mWomSV.getUserTotalLocked(_account)` [1](#0-0) . Because a user can call `mWomSV.startUnlock` at any time to move part of their locked balance into cooldown, `getUserTotalLocked` drops immediately [2](#0-1) [3](#0-2) , resetting the "already rewarded" baseline the contract relies on and allowing the same tier bracket to be rewarded repeatedly.

### Finding Description
`getRewardAmount` with `_lock == true` computes the full tier-based reward for `accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account)` and then subtracts `calDoubledCounted(_account)`, which recomputes the tier-based reward solely from the current `mWomSV.getUserTotalLocked(_account)` [4](#0-3) . The comment `mapping(address => uint) public bracketRewarded; // not in use` shows the developers had originally intended a persisted, monotonic "amount already rewarded" record but replaced it with this live re-derivation [5](#0-4) .

Exploit flow:
1. Attacker calls `incentiveDeposit(_amount, _convertRatio, false, 2)`. `getRewardAmount` is evaluated with the attacker's current `mWomSV` locked balance (0 in the given precondition), `calDoubledCounted` returns 0, and the full tier reward for `_amount` is granted, doubled by the `_mode == 2` branch (`rewardToSend = rewardToSend * 2`) [6](#0-5) . `_deposit` then locks half of `_amount` worth of `mWom` into `mWomSV` for the attacker [7](#0-6) , raising `getUserTotalLocked(attacker)`.
2. Attacker calls `mWomSV.startUnlock(amountJustLocked)` on the `mWomSV` contract directly. This is a public, unprivileged function; it immediately reduces `getUserTotalLocked` back toward (or to) zero by moving the balance into a cooldown slot [2](#0-1) [3](#0-2) .
3. Attacker calls `incentiveDeposit` again with the same/similar `_amount`. Since `mWomSV.getUserTotalLocked(attacker)` is now back at (or near) zero, `calDoubledCounted` again returns close to 0, so the same reward tier bracket is granted again — the contract has no memory that this bracket was already paid out; it only inspects the live, attacker-controlled `mWomSV` balance.
4. This can be repeated in a loop (deposit → startUnlock → deposit → startUnlock …) to keep re-claiming the same low tier bracket's reward multiplier, as long as `mgp` balance in the contract (`mgpleft` cap in `getRewardAmount`) is not exhausted [8](#0-7) .

The only backstop is the `mgpleft = IERC20(mgp).balanceOf(address(this))` cap, which limits total drain to the contract's MGP balance, but does not prevent an attacker from draining that entire balance by repeatedly re-claiming the same bracket instead of it being reserved for legitimate net-new tier progression across all users. There is no `nonReentrant`-adjacent replay protection or persisted "already rewarded" bookkeeping (the `bracketRewarded` mapping exists but is unused) to stop this.

### Impact Explanation
An attacker can repeatedly re-claim MGP rewards for the same mWomSV lock bracket by cycling `incentiveDeposit(mode=2)` and `mWomSV.startUnlock`, draining the contract's MGP reward balance far beyond what legitimate WOM deposit volume should earn. This is a direct theft of protocol-held/reward funds (MGP intended to be distributed proportionally to genuine new locked volume), matching the Critical - Direct theft of user/protocol funds category, bounded only by the total MGP balance held by `ArbWomUp3`.

### Likelihood Explanation
- No privileged role is required; `incentiveDeposit` and `mWomSV.startUnlock` are both public/external functions callable by any EOA.
- Capital needed is minimal — the attacker only needs enough WOM to perform a deposit cycle (and can reuse the same WOM/mWom repeatedly since `startUnlock`+`unlock` returns the underlying `mWom`/`wom` eventually, or the attacker can simply keep cycling smaller amounts within the lower tier bracket).
- The exploit is fully repeatable within one transaction sequence or across multiple transactions, limited only by cooldown timing for actually withdrawing `mWom` back out (though `startUnlock` alone, without waiting for `unlock`, is sufficient to reduce `getUserTotalLocked` and trigger the double-count reset for the next `incentiveDeposit` call).
- This is a straightforward, mechanically reproducible sequence with no dependency on market conditions, oracle manipulation, or race-condition timing.

### Recommendation
Replace the live `mWomSV.getUserTotalLocked`-based `calDoubledCounted` with a persisted, monotonically increasing per-account record of MGP rewards already granted (e.g., actually use the existing `bracketRewarded` mapping, or track cumulative `mWom` ever locked via this contract rather than currently-locked balance). The reward computation should never decrease as a result of the user's own unrelated actions (like `startUnlock`) on an external contract; it must be based on state fully owned and monotonically updated by `ArbWomUp3` itself.

### Proof of Concept
Hardhat test plan:
1. Deploy `ArbWomUp3`, `mWomSV`, `mWom`, `wom`, mock `smartWomConvert`, and mock `MasterMagpie` (for `mWomSV.getUserTotalLocked`/`depositMWomSVFor`/`withdrawMWomSVFor`).
2. Set up `rewardTier = [0, T1, T2]`, `rewardMultiplier = [M0, M1, M2]` via `setMultiplier`, and fund `ArbWomUp3` with a fixed MGP balance `B`.
3. Attacker (unprivileged EOA) approves and calls `incentiveDeposit(A, ratio, false, 2)` where `A` keeps `accumulated` inside tier 0 (below `T1`), with attacker's initial `mWomSV.getUserTotalLocked == 0`. Record `rewardToSend_1` from the `VLMGPRewarded` event and the attacker's `mWomSV` locked balance after (`L1 = A/2` locked via `_deposit`).
4. Attacker calls `mWomSV.startUnlock(L1)` directly, reducing `getUserTotalLocked(attacker)` back to 0.
5. Attacker calls `incentiveDeposit(A, ratio, false, 2)` again with the same `A`. Record `rewardToSend_2`.
6. Assert `rewardToSend_2 ≈ rewardToSend_1 > 0` even though the attacker's net new "amount ever locked" beyond the first deposit is zero (they only re-locked funds already counted once), demonstrating the same bracket is rewarded twice — i.e., `calDoubledCounted` after step 4 returns the same (near-zero) baseline as before step 3, rather than reflecting that `A` was already used to claim a reward.
7. Repeat steps 4–5 in a loop `N` times and assert cumulative MGP paid out (`sum(rewardToSend_i)`) exceeds what a single monotonic bracket-reward record would allow, up to draining `mgpleft` to 0, confirming unbounded re-claim of the same bracket bounded only by the contract's MGP balance.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }
