## Title
Missing slippage protection in `WombatPoolHelperV2.depositFor` enables front-running/sandwich attack on Wombat pool deposits - (File: `wombat/WombatPoolHelperV2.sol`)

### Summary
`WombatPoolHelperV2.depositFor` hardcodes the `_minimumLiquidity` parameter to `0` when depositing into the underlying Wombat pool, unlike the sibling `deposit()` function which lets the caller supply a real minimum. This removes slippage protection for any unprivileged caller using this deposit path, matching the reported bug class of always-zero minimum-output parameters (`min_dy`, `but_expected`, `limits[-1]`) passed to swap/AMM operations.

### Finding Description
`depositFor` is a public, unprivileged, un-gated entry point: [1](#0-0) 

It calls the internal `_deposit` helper with a literal `0` for `_minimumLiquidity`: [2](#0-1) 

That value flows unchanged into `WombatStaking.deposit`, which forwards it directly as the `_minimumLiquidity` argument to the underlying `IWombatPool.deposit` call: [3](#0-2) 

Wombat's stableswap-style pools compute deposit output (LP minted) based on pool coverage ratios and can apply haircuts/bonuses depending on how imbalanced the pool is at execution time. Because `_minimumLiquidity` is hardcoded to `0` in `depositFor`, there is no on-chain guarantee about how many LP/receipt/staking tokens the depositor will actually receive — the receipt token minted to the user is based on whatever `lpReceived` the pool returns (`IERC20(poolInfo.lpAddress).balanceOf(address(this)) - beforeBalance`), with no minimum floor enforced from the depositor's perspective.

This is the same root cause identified in the external report: a swap/deposit-style operation into an AMM pool that always passes a `0` minimum-output value, which by itself provides no protection against adverse price movement engineered by another actor in the same block (front-running/sandwiching).

### Impact Explanation
An attacker monitoring the mempool can front-run a `depositFor` call by swapping into the Wombat pool to worsen its coverage ratio (increasing the haircut applied to new deposits), let the victim's `depositFor` execute and receive a reduced amount of receipt/staking tokens for their input, then back-run by reversing their swap to restore the pool and capture the haircut difference. The depositing user's funds are directly diminished relative to fair value — this is a direct extraction of value from an unprivileged user's deposit, reachable purely through public, unprivileged transactions against `WombatStaking`'s LP-custody/receipt-token deposit flow.

### Likelihood Explanation
`depositFor` is a normal, unauthenticated external function with no owner/role restriction and no reentrancy or time-lock barrier; any address can call it for any `_for` recipient at any time, and the exploit only requires the ability to submit surrounding transactions in the same block (a routine capability for MEV searchers). The `deposit()` counterpart already demonstrates that a non-zero minimum parameter is the intended safe usage pattern, confirming the `0` in `depositFor` is a genuine gap rather than an intentional design choice.

### Recommendation
Remove the hardcoded `0` in `WombatPoolHelperV2.depositFor` (`wombat/WombatPoolHelperV2.sol:106`) and instead accept a caller-supplied `_minimumLiquidity` parameter (as `deposit()` and `depositNative()` already do), then pass that value through `_deposit` to `WombatStaking.deposit`.

### Proof of Concept
1. Attacker observes a pending `depositFor(amount, victim)` transaction in the mempool.
2. Attacker front-runs with a swap into the target Wombat pool that worsens the pool's coverage ratio for `depositToken`, increasing the deposit haircut.
3. Victim's `depositFor` executes with `_minimumLiquidity = 0`, so it cannot revert regardless of how few LP/receipt tokens are minted; `lpReceived` (and thus the staking/receipt tokens credited to the victim) is reduced.
4. Attacker back-runs by reversing the initial swap, restoring the pool and capturing the haircut fee differential extracted from the victim's deposit. [1](#0-0) [4](#0-3)
