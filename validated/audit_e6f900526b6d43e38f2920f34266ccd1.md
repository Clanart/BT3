### Title
Bitcoin scanner binds transaction metadata to every previously scanned output, allowing instruction substitution and deposit theft - (File: processor/src/networks/bitcoin.rs) [1](#0-0) 

### Summary

`Bitcoin::get_outputs` accumulates outputs across all transactions in a block, but applies each subsequent transaction’s `presumed_origin` and `data` to every accumulated output rather than only the outputs produced by that transaction. [2](#0-1)  An unprivileged Bitcoin user can place a transaction paying the multisig later in the same block, causing its embedded Serai instruction and presumed origin to overwrite those of earlier deposits. [3](#0-2) 

### Finding Description

`outputs` is initialized outside the loop over `block.txdata[1 ..]`, while the metadata-population block is inside that loop. [4](#0-3)  On every transaction after the first matching output, `extract_serai_data(tx)` is called once and `output.data` is updated for every `OutputType::External` in the entire accumulated vector. [5](#0-4)  The same loop also replaces every accumulated output’s `presumed_origin` with the current transaction’s first-input address. [6](#0-5) 

`instruction_from_output` then decodes `output.data()` as `Shorthand`, converts it into a `RefundableInInstruction`, pairs the decoded instruction with that output’s full balance, and uses the overwritten presumed origin as the fallback refund address. [7](#0-6)  External outputs are subsequently converted into instructions through `instruction_from_output`, and valid decoded instructions are pushed into the block’s batch. [8](#0-7) 

### Impact Explanation

An attacker can cause a victim’s deposit to execute the attacker’s `InInstruction` for the victim’s amount, such as a transfer or DEX instruction crediting an attacker-controlled destination. [9](#0-8)  The overwrite also changes the refund origin for invalid instructions, potentially directing a victim’s refunded funds to an attacker-controlled Bitcoin address. [10](#0-9)  This produces an incorrect binding between funds and transaction-embedded instructions and can redirect externally deposited value. [11](#0-10) 

### Likelihood Explanation

Any party can broadcast an ordinary Bitcoin transaction paying the multisig’s external address and containing an OP_RETURN instruction. [3](#0-2)  The attack succeeds when the attacker’s matching transaction appears later in the same finalized block than a victim’s matching transaction, which can be attempted by observing pending deposits and competing for inclusion in that block. [12](#0-11)  No validator privileges, key material, malformed Bitcoin transaction, or invalid block is required. [13](#0-12) 

### Recommendation

Process metadata transaction-by-transaction: either keep a separate `tx_outputs` vector inside the loop and populate only those outputs, or retain the transaction index/current output range and update only the outputs appended for that transaction. [14](#0-13)  Add a regression test containing two external-payment transactions in one block with distinct OP_RETURN instructions and assert each `Output` retains the data and presumed origin from its own transaction. [5](#0-4) 

### Proof of Concept

```rust
// Block ordering:
// txdata[0]: coinbase
// txdata[1]: victim_tx
//   output[0]: large payment to Bitcoin::external_address(multisig_key)
//   output[1]: OP_RETURN = Shorthand transfer to VICTIM_SERAI_ACCOUNT
// txdata[2]: attacker_tx
//   output[0]: payment >= N::DUST to Bitcoin::external_address(multisig_key)
//   output[1]: OP_RETURN = Shorthand transfer to ATTACKER_SERAI_ACCOUNT

let outputs = bitcoin.get_outputs(&block, multisig_key).await;
```

During `victim_tx`, the victim output is appended and initially receives the victim instruction. [14](#0-13)  During `attacker_tx`, the attacker output is appended, but the loop at lines 731–735 iterates over both accumulated outputs and copies the attacker transaction’s data onto the earlier victim output. [15](#0-14)  `instruction_from_output` therefore decodes `ATTACKER_SERAI_ACCOUNT` for the victim output while retaining the victim output’s larger `balance()`. [16](#0-15)  The resulting batch contains an attacker-selected instruction backed by the victim’s deposited funds. [17](#0-16)
