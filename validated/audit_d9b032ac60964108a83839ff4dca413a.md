Based on the code I was able to examine, I found a strong local analog to the `maxPrizeCount` bug class in `pallet-beefy-consensus-proofs`.

### Title
Mutable `RewardCurve` breaks position-indexed uncle-prover reward accounting after provers have already been recorded - (File: `modules/pallets/beefy-consensus-proofs/src/lib.rs`)

### Summary
The pallet accepts consensus proofs from multiple provers per parachain height, tracking each prover's *position* via `ProverCount<T>` and `AcceptedProvers<T>`, and later pays each position a reward fraction taken from `RewardCurve<T>` — a value the admin origin can change at any time via `set_reward_curve`, independent of in-flight heights that already have provers recorded.

### Finding Description
`ProverCount<T>` (a per-height counter) and `AcceptedProvers<T>` (a per-height bounded list of accepted submitter hashes) are populated incrementally as proofs for a given `latest_height` arrive, with each new prover's position being `ProverCount` at time of insertion: [1](#0-0) 

The reward paid to a position is looked up from `RewardCurve<T>`, which the admin origin can overwrite at any time: [2](#0-1) 

Because `RewardCurve` is a single global `StorageValue` (not checkpointed per height), the fraction applied to a given prover position is whatever the curve holds *at the moment their reward is settled*, not what it was when the height's first proof (position 0) was accepted and other uncles began queuing up positions. This is structurally the same bug as `maxPrizeCount`: a mutable, globally-scoped configuration value is read at claim/settlement time rather than being pinned to the round/height it applies to, so an update made after positions have already been assigned changes the payout for positions that were established under the old configuration. Specifically:
- If the curve is shrunk (fewer entries) after several uncle positions have already been recorded in `AcceptedProvers` for an in-flight height, any uncle whose position index is now `>= curve.len()` falls back to the "empty curve" uncle default of zero reward per the documented fallback behavior: [3](#0-2) 
- Because `record_uncle_metadata`/eviction logic explicitly treats missed uncle bookkeeping as non-fatal and irreversible ("Skipping the record cannot mint a second reward... A missed reward is the cheaper loss, so log and carry on"), there is no retry or backfill path once a height's provers have been accepted with one curve and rewards are eventually computed with another: [4](#0-3) 

The `require(_maxPrizeCount != ...)`-style safeguard suggested in the external report (checkpointing config to the unit of work it governs, i.e., per-round in ThrusterTreasure / per-height here) does not exist for `RewardCurve` in this pallet.

### Impact Explanation
A prover who submitted an uncle proof for a given height under one reward curve can have their payout silently reduced to zero or altered if the admin updates `set_reward_curve` before that height's rewards are actually settled, because the position→reward mapping is resolved lazily against current global state rather than pinned at submission time. This is a loss-of-funds / wrong-amount defect for legitimate provers, matching the "stealing or loss of funds" and "logic attacks" impact categories.

### Likelihood Explanation
This requires only the `AdminOrigin`-controlled `set_reward_curve` call to be exercised in the normal course of operational tuning (adjusting uncle reward economics), combined with proofs for a height still being in-flight (multiple provers submitting concurrently within the same block/height window before final settlement) — a realistic operational sequence rather than a contrived one, since `set_reward_curve` has no guard preventing changes while heights have outstanding, unpaid `AcceptedProvers` entries.

### Recommendation
Snapshot the `RewardCurve` (and any other position-dependent reward parameters) at the time a height's first proof is accepted, storing it alongside `ProofContext<T>` for that height, and use that snapshot — not the live `RewardCurve<T>` value — when computing rewards for every position at that height. Alternatively, follow the same fix accepted for the analogous ThrusterTreasure bug: disallow `set_reward_curve` while any height has pending, unsettled `AcceptedProvers`/`ProverCount` entries.

### Proof of Concept
1. Admin sets `RewardCurve = [(1,1), (1,2), (1,4)]` (3 slots: full, half, quarter).
2. Height `H`'s first proof lands; position 0 prover is paid immediately at full reward (via `pay_position_reward` in the same extrinsic call, per the code at lines 563-581).
3. An uncle proof for height `H` lands, recorded via `record_uncle_metadata`, taking position 1 in `AcceptedProvers<H>` and `ProverCount<H> = 2`.
4. Before this uncle's reward is settled/paid, admin calls `set_reward_curve` with a shorter curve `[(1,1)]` (only position 0 defined).
5. When the position-1 uncle's reward is eventually computed against the now-truncated curve, it falls back to the documented "zero for uncles" default described at lines 215-217, even though the uncle proof was legitimately submitted and recorded under the original 3-slot curve.
6. The uncle prover receives no reward for work performed under different, prior reward-curve terms, and per the non-fatal "log and carry on" design at lines 563-581, there is no retry mechanism to correct this — an irreversible reward loss caused purely by an unrelated admin config change. 		pub fn set_reward_curve(
			origin: OriginFor<T>,
			curve: BoundedVec<(u32, u32), MaxStoredProvers<T>>,
		) -> DispatchResult {
			<T as Config>::AdminOrigin::ensure_origin(origin)?;
			// `numerator > denominator` would multiply the base reward above 100% for that
			// position, turning a fat-fingered curve into a treasury drain. Reject it
			// outright — uncle positions are meant to *decrease* from the position-0 base.
			if curve.iter().any(|(num, denom)| *denom == 0 || num > denom) {
				Err(Error::<T>::InvalidRewardCurve)?
			}
			RewardCurve::<T>::put(curve);
			Self::deposit_event(Event::RewardCurveUpdated);
			Ok(())
		}
