Based on the code I reviewed, the reported behavior is real and reproducible in `_extract_field`/`Rule.from_dict`.

### Title
Legacy `pattern:` field on `event: stop` rules silently infers unresolvable `content` field, making stop-guard rules permanently inert - (File: plugins/hookify/core/config_loader.py)

### Summary
`Rule.from_dict` infers `field='content'` for any legacy-style rule whose `event` is not `bash` or `file`, including `stop`. `RuleEngine._extract_field` never resolves `field == 'content'` for Stop events (it only handles `reason`, `transcript`, `user_prompt`, and tool-specific branches gated on `tool_name in ['Write','Edit']`/`'MultiEdit'`, which are empty/absent for Stop events), so it falls through to `return None`, causing `_check_condition`/`_rule_matches` to always return `False`.

### Finding Description
In `plugins/hookify/core/config_loader.py` (`Rule.from_dict`, lines 56-73), when a rule uses the legacy `pattern:` frontmatter key instead of `conditions:`, the field name is inferred purely from `event`: [1](#0-0) 
For `event: stop` (or any event other than `bash`/`file`), this produces a `Condition(field='content', operator='regex_match', pattern=<user pattern>)`.

In `plugins/hookify/core/rule_engine.py`, `_extract_field` (lines 182-254) is the sole resolver of `condition.field` to an actual string value. For Stop events, `tool_input` is `{}` and `tool_name` is `''` (Stop events carry `reason`/`transcript_path`, not tool_input), so:
- `if field in tool_input:` is `False` (empty dict).
- The Stop-specific block only recognizes `field == 'reason'`, `'transcript'`, `'user_prompt'` — not `'content'`.
- The `tool_name == 'Bash'` / `tool_name in ['Write','Edit']` / `'MultiEdit'` branches don't apply since `tool_name` is empty.
- Function falls through to `return None`.

Back in `_check_condition` (lines 157-160): `if field_value is None: return False`. Since `_rule_matches` requires all conditions to match, the rule can never match, and `evaluate_rules` will never surface a block/warning for this rule — regardless of stop reason or transcript content.

This is a parser/interpreter differential: a user authoring a rule file such as:
```
---
name: no-lazy-stop
enabled: true
event: stop
pattern: "TODO|incomplete"
action: block
---
```
reasonably expects it to guard against Stop events containing "TODO"/"incomplete" in `reason`/`transcript`, matching the pattern used for `bash`/`file` legacy rules. Instead the rule is silently loaded successfully (no error, no warning in `load_rule_file`) and is permanently a no-op.

### Impact Explanation
This does not enable command execution or data exfiltration by itself, but it creates a false sense of security: a user (or an attacker who can plant/modify a rule file, e.g. via a malicious PR touching `.claude/hookify.*.local.md`, or a shared/community rule template using the legacy `pattern:` shorthand for stop-guards) believes an active stop-guard/blocking safeguard exists, while it silently never fires. Any security-relevant automation relying on this "block" rule for Stop events (e.g., preventing session termination when dangerous state is detected) is bypassed 100% of the time with no error surfaced. This matches an "unauthorized action allowed due to safety-guard bypass" class of impact — the enforcement layer users trust is dead code for this specific legacy configuration path.

### Likelihood Explanation
High feasibility and fully deterministic: any user (or attacker distributing a rule template) who writes a Stop rule using the legacy `pattern:` key instead of `conditions:` triggers this every time, with no exception, log warning, or lint check flagging the field-inference mismatch. No special privileges are needed — only the ability to author/commit a `.claude/hookify.*.local.md` file, which is normal repository content.

### Recommendation
- In `Rule.from_dict`, when inferring the legacy field for `event == 'stop'` (or any non-bash/file event), map to a Stop-compatible field such as `'reason'` (or `'transcript'`) instead of the generic `'content'`.
- Alternatively, extend `_extract_field` to treat `'content'` as an alias for `'reason'`/`'transcript'` on Stop events.
- Add a load-time validation/warning in `load_rule_file` that checks whether the inferred/declared condition field is resolvable for the given `event`, and surfaces a clear warning (not silent success) when a legacy `pattern:` rule cannot possibly match.

### Proof of Concept
Unit test in `plugins/hookify` test suite:
```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

def test_legacy_pattern_stop_rule_never_matches():
    frontmatter = {
        "name": "no-lazy-stop",
        "enabled": True,
        "event": "stop",
        "pattern": "TODO|incomplete",
        "action": "block",
    }
    rule = Rule.from_dict(frontmatter, "Stop blocked: incomplete work detected")

    # Confirm field was inferred as 'content' (the bug)
    assert rule.conditions[0].field == "content"

    engine = RuleEngine()
    input_data = {
        "hook_event_name": "Stop",
        "reason": "TODO: incomplete work, do not stop",
        "tool_name": "",
        "tool_input": {},
    }
    # Expected per user intent: True (should block). Actual: always False.
    assert engine._rule_matches(rule, input_data) is False
    result = engine.evaluate_rules([rule], input_data)
    assert result == {}  # no block/warning ever emitted
```
This demonstrates the rule is loaded without error yet never triggers regardless of `reason`/`transcript` content, confirming the documentation-vs-implementation gap.
