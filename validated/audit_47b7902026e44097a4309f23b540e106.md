### Title
Flash-loan / JIT-staking manipulation of `BaseRewardPoolV2` reward distribution steals yield from honest stakers - (File: `rewards/BaseRewardPoolV2.sol`)

### Summary
`BaseRewardPoolV2._provisionReward` distributes an entire reward donation instantly and proportionally to the *current* `totalStaked()` snapshot, with no time-weighting or vesting. Since `MasterMagpie.deposit`/`withdraw` have no lock-up or cooldown, an attacker can flash-loan/acquire a large amount of a pool's staking token, deposit it immediately before a reward injection (`donateRewards` or `queueNewRewards`) lands, capture a share of that reward proportional to their flash-inflated balance, and withdraw right after — diluting and stealing yield from genuine long-term stakers. This is the same root-cause pattern as the referenced report: a share/weight value used for reward or governance accounting is derived from an instantaneously-manipulable balance rather than a time-resistant measure.

### Finding Description
`BaseRewardPoolV2.balanceOf` and `totalStaked` are read directly from `MasterMagpie`'s live `userInfo`/staking-token balance: [1](#0-0) 

Reward injections apply immediately to the whole staked base with no streaming/vesting: [2](#0-1) 

`donateRewards` is a **public, permissionless** entry point that anyone can call to trigger this instant redistribution for any already-registered reward token: [3](#0-2) 

`queueNewRewards` (called by the manager, e.g. after harvesting bribes/fees) has the identical instant, non-vested distribution behavior: [4](#0-3) 

`MasterMagpie._deposit`/`_withdraw` have no lock, cooldown, or minimum holding period — a user can deposit and withdraw a stakingToken within the same block/transaction: [5](#0-4) 

Because `rewardPerTokenStored` is bumped by `_amountReward * 10**decimals / totalStaked()` at the moment of the call, and a depositor's `userRewardPerTokenPaid` baseline is captured only via `_harvestBaseRewarder`→`updateFor` right before the deposit increases `user.amount`, an attacker who deposits immediately before a reward injection captures the full proportional share of the *increase* in `rewardPerTokenStored`, exactly as if they had been staked the whole accrual period — even though they were present for only one block. This mirrors the `getPoolShareWeight` flaw in the referenced report: a share/weight used for value distribution is computed from a balance that can be inflated in the same transaction/block as the payout event, with no time-delay defense as suggested in the report's own mitigation ("record timestamp ... force new weight to take effect only after a period").

### Impact Explanation
This results in **theft of unclaimed yield** from legitimate long-term stakers: a JIT staker captures reward tokens (MGP, WOM, bribe tokens, etc.) that should have accrued to users who were staked throughout the relevant period, diluting `rewardPerTokenStored` gains for everyone else. This falls under the explicitly accepted impact "theft or permanent freezing of unclaimed yield," reachable purely via ordinary unprivileged wallet transactions (deposit → wait for/trigger reward injection → withdraw), no privileged role required.

### Likelihood Explanation
Likelihood is significant for pools whose staking token is a liquid, flash-loanable/cheaply-acquirable asset (e.g., an LP token or WOM-related token with deep liquidity elsewhere), and where reward injections (`queueNewRewards` from harvested bribes/fees, or `donateRewards`) are predictable or visible in the mempool. Since `donateRewards` is permissionless, an attacker can even orchestrate the timing themselves in a single atomic transaction (flash-loan → deposit → donateRewards is called by someone else in same block, or attacker bundles/front-runs the manager's `queueNewRewards` call) — no special access or governance manipulation is needed.

### Recommendation
Introduce a time-weighted or vesting mechanism for reward distribution instead of instant full-amount crediting based on a point-in-time `totalStaked()` snapshot — e.g., stream rewards over time (as `MasterMagpie.updatePool` already does for `accMGPPerShare` using elapsed seconds) rather than injecting the entire amount at once via `_provisionReward`. Alternatively, enforce a minimum staking duration (or a deposit/withdraw cooldown) before a user's balance counts toward `rewardPerToken` accrual, consistent with the mitigation recommended in the referenced report (delay effect of balance changes by at least one block/epoch).

### Proof of Concept
1. Attacker flash-loans/acquires a large amount of `stakingToken` registered in `MasterMagpie`.
2. Attacker calls `MasterMagpie.deposit(stakingToken, largeAmount)` (`rewards/MasterMagpie.sol:337-339`), which calls `BaseRewardPoolV2.updateFor` (capturing baseline `userRewardPerTokenPaid` at the pre-deposit rate) before incrementing `user.amount`.
3. In the same block, a reward injection occurs via `queueNewRewards`/`donateRewards` (`rewards/BaseRewardPoolV2.sol:255-286`), which updates `rewardPerTokenStored` using the now-inflated `totalStaked()` that includes the attacker's flash-loaned balance.
4. Attacker calls `MasterMagpie.withdraw` (`rewards/MasterMagpie.sol:344-346`), harvesting the reward share attributable to the large `largeAmount * (rewardPerTokenStored_new - rewardPerTokenStored_old)` delta, then repays the flash loan — net profit equal to the diluted rewards taken from genuine stakers, minus flash-loan fees.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
