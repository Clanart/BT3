### Title
`pallet-hyper-fungible-token::on_accept` silently coerces a 20-byte EVM recipient into a 32-byte `AccountId` by zero-padding, sending funds to an unowned/unspendable account - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
The reported ZetaChain bug (M-14) was caused by the Solana gateway blindly accepting an address in the wrong chain's format (a Solana `Pubkey` where an EVM address was required) and truncating/converting it without validating that the result is actually spendable by anyone — permanently losing the aborted funds. Hyperbridge's `pallet-hyper-fungible-token` contains the same class of bug: when accepting an inbound cross-chain transfer whose `to` field is a 20-byte EVM address, the pallet does not perform a canonical/verified EVM→Substrate address derivation. Instead it just zero-pads the 20 bytes into a 32-byte value and treats that as the destination `AccountId`, with no guarantee that any private key controls the resulting account.

### Finding Description
In `on_accept` [1](#0-0) :

```rust
// Convert recipient bytes to substrate AccountId
// If 32 bytes: use directly. If 20 bytes: left-pad with zeros.
let mut beneficiary_bytes = [0u8; 32];
let to_bytes = message.to.as_ref();
if to_bytes.len() == 32 {
    beneficiary_bytes.copy_from_slice(to_bytes);
} else if to_bytes.len() == 20 {
    beneficiary_bytes[12..].copy_from_slice(to_bytes);
} else {
    Err(HftError::InvalidRecipientLength(to_bytes.len()))?;
}
let beneficiary: T::AccountId = beneficiary_bytes.into();
```

This is the receiving half of the same `Message { from, to, amount, data }` ABI shared with the Solidity `HyperFungibleToken`/`WrappedHyperFungibleToken` contracts [2](#0-1) . On the EVM side, `to` is simply an arbitrary `bytes` value the *sender* controls (`abi.encodePacked(recipientAddress)`), with no on-chain semantic tying its length/format to how the destination chain will interpret it [3](#0-2) .

When the destination is this Substrate pallet, a 20-byte value is accepted and zero-padded into a 32-byte `AccountId`. Substrate `AccountId32` values are (in the general case) sr25519/ed25519 public keys — essentially random 32-byte values whose private key an attacker/user must actually hold. Left-padding an EVM address with zeros produces an `AccountId32` of the form `0x000000000000000000000000<20-byte-addr>`, which is *not* a real public key derived from any private key (unless the specific runtime happens to implement a matching, intentional H160→AccountId20-style padding convention as its canonical account-mapping scheme, which is not verified or enforced anywhere in this pallet or its tests). No component in the repository validates that the destination runtime's account scheme actually treats this zero-padded value as spendable — the padding is invented locally by this pallet with no accompanying `AccountIdConversion`/`HashedAddressMapping`-style trait bound.

This mirrors the M-14 root cause exactly: an address is silently reinterpreted into a different chain's address space with an ad hoc conversion, with no guarantee the resulting bytes correspond to a controllable account, and funds are minted/transferred to it anyway.

### Impact Explanation
Any relayer delivering a legitimate cross-chain `send()` from an EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract whose recipient is passed as a raw 20-byte value (the exact and documented calling convention shown for EVM→EVM sends: `abi.encodePacked(recipientAddress)` [4](#0-3) ) into a Substrate destination will have the minted/transferred tokens delivered to a zero-padded pseudo-account that generally has no corresponding private key on that Substrate chain. Since `on_accept` unconditionally mints/transfers to this derived `beneficiary` [5](#0-4) , the funds are permanently and irrecoverably lost — the same "loss of funds via wrong-format address" impact as M-14.

### Likelihood Explanation
This is trivially reachable by any ordinary user/dApp integrator, not just a malicious actor: nothing in the SDK, contracts, or pallet enforces that a `to` value routed to a Substrate destination must be a genuine 32-byte public key rather than a 20-byte EVM-style address. The pallet explicitly special-cases and *accepts* 20-byte inputs (rather than rejecting them), actively encouraging this failure mode instead of guarding against it. Given HFT is designed as a generic bridge between arbitrary EVM and Substrate chains, and EVM-side senders naturally think in 20-byte addresses, this misuse is a highly plausible, unprivileged, no-special-conditions occurrence.

### Recommendation
Reject 20-byte `to` values when the destination is a Substrate `AccountId32`-based chain (mirroring `HyperFungibleToken.sol`'s strict `_toAddr` which reverts unless the length is exactly 20 [6](#0-5) ). If EVM-derived accounts must be supported on the Substrate side, use the chain's actual, verified `H160`→`AccountId` derivation (e.g., a `HashedAddressMapping`/keccak-based scheme registered in the runtime) rather than an unverified zero-pad, and document/enforce that senders must supply full 32-byte account IDs for non-EVM-account substrate destinations.

### Proof of Concept
1. Deploy `HyperFungibleToken` on an EVM chain and register a Substrate chain (running `pallet-hyper-fungible-token`) as a peer via `addChain`.
2. Call `send()` with `to: abi.encodePacked(someEvmAddress)` (20 bytes), targeting the Substrate `dest`.
3. Relay the resulting POST request; `on_accept` in `module.rs` takes the 20-byte `to`, zero-pads it into `beneficiary_bytes`, and mints/transfers the bridged amount to `beneficiary: T::AccountId = beneficiary_bytes.into()`.
4. Because `0x000000000000000000000000<addr>` is not a real substrate keypair (absent a special runtime-level H160 mapping matching this exact convention), no one can sign transactions from this account — the bridged tokens are permanently stranded, exactly as in the referenced M-14 report.
