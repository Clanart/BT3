### Title
Blame proof revealing the ECDH key is emitted before the message's PoP is verified, leaking honest parties' encrypted secret shares - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` returns a publishable `EncryptionKeyProof` (which contains the raw ECDH shared point for the encrypted share) when the decrypted bytes fail scalar deserialization, before the batched Schnorr proof-of-possession on `msg.key` has been verified. This reintroduces the exact attack the per-message PoP exists to prevent: an attacker copies an honest sender's per-message encryption key `X` into a garbage message, the victim's blame proof reveals `b·X`, and publishing it decrypts the honest party's real secret share.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs:476-499`, `calculate_share` iterates over received `EncryptedMessage`s. For each message it calls `Encryption::decrypt`, which only *queues* the PoP signature into the `BatchVerifier` under `BatchId::Decryption(l)` — it does not verify it — and immediately computes `key = ecdh(self.enc_key, msg.key)` and returns an `EncryptionKeyProof { key, dleq }` attesting that this key decrypts the message [1](#0-0) .

Immediately after, `calculate_share` attempts `C::F::from_repr` on the decrypted bytes and, on failure, returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` — returning early, before `batch.verify_with_vartime_blame()` at line 493 ever checks the PoP [2](#0-1) . Only when the failure surfaces through the batch verifier is blame downgraded to `None` for PoP failures (the `BatchId::Decryption` arm at lines 494-497).

The `EncryptionKeyProof` revealed in this error is exactly `b·msg.key` where `b` is the victim's DKG encryption private key, with a DLEq proof binding it to the victim's registered encryption key (`crypto/dkg/pedpop/src/encryption.rs:381-390`). Whoever holds it can decrypt *any* ciphertext whose `key` field equals `msg.key`. The code itself documents the danger: without PoP on `key`, Eve could reuse Alice's key `X`, trigger a blame, and the revealed `bX` would decrypt Alice's message to Bob — "a massive side effect which could break some protocols" [3](#0-2) . The PoP is the mitigation, but the early `?` on `from_repr` failure leaks the blame proof before the PoP is verified, so the mitigation is bypassed.

### Impact Explanation
A malicious DKG participant Eve observes the honest sender Alice's encrypted share to Bob (key `X = k·G`, ciphertext `c`). Eve sends Bob a forged `EncryptedMessage { key: X, pop: <garbage>, msg: <bytes that are not a canonical scalar> }`. Bob's `calculate_share` computes `proof.key = b·X` — the exact shared key encrypting Alice's real share — and returns it in `PedPoPError::InvalidShare { blame: Some(proof) }` before ever discovering the PoP is invalid. Per protocol, Bob publishes this blame proof (`ProcessorMessage::InvalidShare` carries `blame.serialize()`), after which `AdditionalBlameMachine::blame`/`decrypt_with_proof` verifies the DLEq and uses `proof.key` to decrypt. Everyone can now decrypt Alice's secret share `f_A(Bob)`, a secret value that was only ever intended for Bob. This is secret material (a DKG share contributing to a threshold signing key) exposed through an ostensibly public diagnostic channel — the same bug class as secret content leaking into metrics labels.

### Likelihood Explanation
Requires a malicious participant in a DKG session who can observe a honest party's encrypted share message (the messages are broadcastable/commitment-bound in the coordinator flow) and get the victim to process the forged message — both within the normal protocol surface, since `calculate_share` accepts arbitrary `EncryptedMessage`s keyed by sender index. The leaked proof is then published as part of the standard blame flow. The impact is bounded (one honest share value per forgery rather than the full key), consistent with Medium severity.

### Recommendation
Verify the PoP on `msg.key` before emitting any `EncryptionKeyProof`, or suppress the proof when the PoP cannot yet be trusted. Concretely, in `calculate_share`, do not attach `blame` on the `from_repr` early-return path; instead defer share-validity checks until after `batch.verify_with_vartime_blame()` confirms all PoPs, or mark the share as suspect and produce `blame: None` unless the PoP is known-good. Alternatively, have `Encryption::decrypt` perform a synchronous `msg.pop.verify` (in addition to or instead of batching) before returning the `EncryptionKeyProof`.

### Proof of Concept
1. Participants run PedPoP; Alice (participant 1) sends Bob (participant 2) `EncryptedMessage { key: X, pop: σ_A, msg: Enc(share_{1→2}) }`. Eve observes `X`.
2. Eve (participant 3) sends Bob `EncryptedMessage { key: X, pop: <invalid signature>, msg: <non-canonical F::Repr, e.g. all-0xFF> }`.
3. Bob calls `KeyMachine::calculate_share`. `Encryption::decrypt` queues the (invalid) PoP into the batch verifier and returns `proof.key = ecdh(enc_key_bob, X) = b·X` plus a valid DLEq. `from_repr` on the garbage plaintext fails → early return `InvalidShare { participant: 3, blame: Some(proof) }`.
4. Bob broadcasts `blame`. Any party runs `BlameMachine::blame`/`decrypt_with_proof` with the proof, then applies `cipher(context, proof.key)` to Alice's original ciphertext `Enc(share_{1→2})`, recovering Alice's secret share to Bob — despite Eve never possessing the per-message private key `k`.
