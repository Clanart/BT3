Found key evidence: the Bank precompile's `decimals()` hardcodes `0` for **all** native denoms (`precompiles/bank/legacy/v600/bank.go:303-310` and later versions), on the stated rationale that "all native tokens are integer-based." However, the ERC20 native-token *pointer* contract (deployed via the `pointer` precompile's `AddNative`) derives `decimals` from the denom's bank `Metadata.DenomUnits[].Exponent` — a value that is fully attacker-controlled for any tokenfactory denom via `MsgSetDenomMetadata`, with no requirement that it be `0` or that it reflect any real sub-unit precision of the token's actual balance representation.

### Title
Tokenfactory admin can mint an ERC20 native-token pointer with an attacker-chosen `decimals()` while `balanceOf`/`totalSupply` remain unscaled raw integers - ([File: precompiles/pointer/legacy/v65/pointer.go])

### Summary
`AddNative` in the pointer precompile builds an EVM ERC20 pointer contract for any bank denom by reading `bankKeeper.GetDenomMetaData` and picking the largest `DenomUnit.Exponent` as the pointer's `decimals` constructor argument. For tokenfactory denoms, the underlying metadata is set entirely by the denom's admin via `MsgSetDenomMetadata`, which only validates internal consistency of the metadata (sorted units, base exponent 0, display unit present) — it does not constrain the exponent to match any real precision of the token, nor is `decimals` derived from `balanceOf`/`totalSupply`, which always return the raw integer bank amount unscaled (`contracts/src/NativeSeiTokensERC20.sol:33-43`).

### Finding Description
Any unprivileged account can call `tokenfactory.CreateDenom` to become the admin of a new denom, then call `MsgSetDenomMetadata` to set an arbitrary `DenomUnit.Exponent` (e.g. 18) for their own denom [1](#0-0) . `Metadata.Validate()` only checks structural well-formedness (sorted, unique, base exponent 0, display unit present) and never checks the exponent against how the token's raw integer balance is actually intended to be interpreted [2](#0-1) .

The admin (or anyone, since `AddNative` has no privilege gate beyond providing a valid `token` denom with metadata) then calls the pointer precompile's `AddNative`, which reads that metadata and sets the pointer's `decimals` to the largest exponent found: `for _, denomUnit := range metadata.DenomUnits { if denomUnit.Exponent > uint32(decimals) ... decimals = uint8(denomUnit.Exponent) }` [3](#0-2) . This decimals value is passed straight into the deployed `NativeSeiTokensERC20` contract's constructor [4](#0-3)  and returned verbatim from `decimals()` [5](#0-4) .

Critically, `balanceOf` and `totalSupply` on that same pointer contract are **not** scaled by `decimals` at all — they return the raw integer bank amount straight from the `BankPrecompile` [6](#0-5) . This mirrors the Blueberry root cause precisely: the "decimals" reported by the token interface does not match the actual precision used to represent quantities, and any downstream consumer that follows the standard ERC20 convention `humanValue = balanceOf(x) / 10**decimals()` will compute a value that is off by up to `10^18` (whatever exponent the tokenfactory admin picked), rather than the real usei-integer amount. Note also that the chain's own Bank precompile explicitly hardcodes `decimals() == 0` for all native denoms and comments that "all native tokens are integer-based" [7](#0-6) , confirming that `0` is the semantically correct value and that the pointer's metadata-derived `decimals` is inconsistent with the chain's own model — an internal misconfiguration of exactly the kind that caused the Blueberry incident (decimals reported by one code path disagreeing with the actual scale used by another).

### Impact Explanation
Any EVM contract (lending market, AMM, oracle-adapter, DEX router) that integrates a tokenfactory-denom's native ERC20 pointer and relies on the standard `decimals()`/`balanceOf()` contract to price or scale the asset will misvalue collateral or swap amounts by orders of magnitude, exactly as happened to Blueberry Protocol with WBTC's decimal mismatch. This can lead to under-collateralized borrowing, incorrect liquidation thresholds, or mispriced swaps — i.e., fund loss via unauthorized value extraction through the pointer contract, which is an explicitly in-scope impact category (unauthorized transfer/value abuse via a pointer).

### Likelihood Explanation
High reachability: creating a tokenfactory denom, setting its metadata, and registering a native pointer are all permissionless operations reachable from a single unprivileged sender's transactions (`MsgCreateDenom`, `MsgSetDenomMetadata`, and the `pointer` precompile's `AddNative` call) [8](#0-7) [9](#0-8) . No governance or validator involvement is required. The only remaining requirement is that a third-party integrator naively trusts `decimals()` from the pointer without independently confirming it matches `0`/integer-based semantics — a very common integration pattern.

### Recommendation
Make the native ERC20 pointer's `decimals()` a fixed constant of `0` (matching the Bank precompile's own semantics and `balanceOf`'s unscaled integer return), instead of deriving it from admin-controlled `DenomUnit.Exponent` metadata; or, if a non-zero decimals value must be exposed for display purposes, scale `balanceOf`/`totalSupply` consistently by the same factor so the ERC20 interface remains internally self-consistent.

### Proof of Concept
1. As any account, call `MsgCreateDenom` to create `factory/<addr>/evil`, becoming its admin.
2. Call `MsgSetDenomMetadata` with `DenomUnits: [{Denom: "factory/<addr>/evil", Exponent: 0}, {Denom: "EVIL", Exponent: 18}]`, `Base: "factory/<addr>/evil"`, `Display: "EVIL"` — this passes `Metadata.Validate()` since it is structurally well-formed.
3. Mint `1000` raw units of the denom to yourself via `MsgMint`.
4. Call the `pointer` precompile's `addNativePointer("factory/<addr>/evil")`; the deployed `NativeSeiTokensERC20` pointer will report `decimals() == 18`.
5. Query `balanceOf(you)` on the pointer — it returns `1000` (raw integer), not `1000 * 10**18`.
6. Any external contract computing `humanValue = balanceOf(you) / 10**decimals()` will compute `1000 / 10**18 ≈ 0`, or conversely if it assumes `balanceOf` is already scaled to `decimals`, it will treat `1000` raw units as `1000 * 10**-18` tokens — an 18-order-of-magnitude mismatch analogous to Blueberry's WBTC decimal mishandling, exploitable against any integrator that trusts the pointer's `decimals()`.

func (m Metadata) Validate() error {
	if strings.TrimSpace(m.Name) == "" {
		return errors.New("name field cannot be blank")
	}

	if strings.TrimSpace(m.Symbol) == "" {
		return errors.New("symbol field cannot be blank")
	}

	if err := sdk.ValidateDenom(m.Base); err != nil {
		return fmt.Errorf("invalid metadata base denom: %w", err)
	}

	if err := sdk.ValidateDenom(m.Display); err != nil {
		return fmt.Errorf("invalid metadata display denom: %w", err)
	}

	var (
		hasDisplay      bool
		currentExponent uint32 // check that the exponents are increasing
	)

	seenUnits := make(map[string]bool)

	for i, denomUnit := range m.DenomUnits {
		// The first denomination unit MUST be the base
		if i == 0 {
			// validate denomination and exponent
			if denomUnit.Denom != m.Base {
				return fmt.Errorf("metadata's first denomination unit must be the one with base denom '%s'", m.Base)
			}
			if denomUnit.Exponent != 0 {
				return fmt.Errorf("the exponent for base denomination unit %s must be 0", m.Base)
			}
		} else if currentExponent >= denomUnit.Exponent {
			return errors.New("denom units should be sorted asc by exponent")
		}

		currentExponent = denomUnit.Exponent

		if seenUnits[denomUnit.Denom] {
			return fmt.Errorf("duplicate denomination unit %s", denomUnit.Denom)
		}

		if denomUnit.Denom == m.Display {
			hasDisplay = true
		}

		if err := denomUnit.Validate(); err != nil {
			return err
		}

		seenUnits[denomUnit.Denom] = true
	}

	if !hasDisplay {
		return fmt.Errorf("metadata must contain a denomination unit with display denom '%s'", m.Display)
	}

	return nil

func (p PrecompileExecutor) AddNative(ctx sdk.Context, method *ethabi.Method, caller common.Address, args []interface{}, value *big.Int, evm *vm.EVM, hooks *tracing.Hooks) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	token := args[0].(string)
	metadata, metadataExists := p.bankKeeper.GetDenomMetaData(ctx, token)
	if !metadataExists {
		return nil, 0, fmt.Errorf("denom %s does not have metadata stored and thus can only have its pointer set through gov proposal", token)
	}
	name := metadata.Name
	symbol := metadata.Symbol
	var decimals uint8
	for _, denomUnit := range metadata.DenomUnits {
		if denomUnit.Exponent > uint32(decimals) && denomUnit.Exponent <= math.MaxUint8 {
			decimals = uint8(denomUnit.Exponent)
			name = denomUnit.Denom
			symbol = denomUnit.Denom
			if len(denomUnit.Aliases) > 0 {
				name = denomUnit.Aliases[0]
			}
		}
	}
	contractAddr, err := p.evmKeeper.UpsertERCNativePointer(ctx, evm, token, utils.ERCMetadata{Name: name, Symbol: symbol, Decimals: decimals})
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(contractAddr)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
