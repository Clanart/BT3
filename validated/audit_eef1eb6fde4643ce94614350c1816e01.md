### Title
Coinbase outputs reported as spendable `ReceivedOutput`s cannot actually be spent (immature coinbase), silently poisoning any transaction plan that selects them - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The original bug class is a "silent success": `safeTransfer` returns success while no transfer occurred, so funds are treated as moved when they were not. In `bitcoin-serai`, `Scanner::scan_block` exhibits the same shape: it scans every transaction in a block, including the coinbase transaction (`block.txdata[0]`), and returns matching outputs as `ReceivedOutput`s indistinguishable from spendable ones. A coinbase output is consensus-immature for 100 blocks, so any transaction spending it is invalid. The `ReceivedOutput` type carries no maturity/height metadata, so a downstream consumer (scheduler/planner) has no way to detect that the output it was told it "received" cannot actually be spent yet — the same "no indication of failure" hole, at the wallet-layer rather than the contract layer.

### Finding Description
`scan_block` iterates `block.txdata` unconditionally, which includes the coinbase transaction at index 0, and forwards it to `scan_transaction` [1](#0-0) . `scan_transaction` matches purely on `output.script_pubkey` membership in `self.scripts` and emits a `ReceivedOutput` with only `offset`, `output`, and `outpoint` [2](#0-1) . The `ReceivedOutput` struct exposes only `offset()`, `output()`, `outpoint()`, and `value()` — there is no field marking coinbase/immature status [3](#0-2) .

Bitcoin consensus rules reject any transaction spending a coinbase output before it is 100 blocks deep. The code acknowledges this only in a doc comment — "This will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed" [4](#0-3)  — but the API provides no data (coinbase flag, block height, or maturity depth) with which a caller could perform that post-processing. A `Transaction` does not even expose whether it is a coinbase through `ReceivedOutput`; the caller would have to re-scan the block itself.

### Impact Explanation
An output that Serai believes it controls is selected as an input to a spend plan, the multisig signs a transaction spending it, and the transaction is rejected by the Bitcoin network as consensus-invalid — yet nothing in the `ReceivedOutput` pipeline ever indicated the output was immature. The signed plan is unbroadcastable; the funds are "received" on Serai's books but the spend silently fails. This mirrors the original report exactly: an operation (here, scanning/registration of a received output) gives a success indication while the actual effect (spendability) does not exist, producing a silent-failure/loss-of-funds window. The failure is self-healing after 100 confirmations, which caps severity at Medium rather than High — funds are delayed and plans stall, not permanently lost.

### Likelihood Explanation
Reachability: a miner can pay a coinbase output directly to a Serai P2TR address (or to any registered offset script). The scanner accepts it unconditionally. Whether downstream planners select it depends on out-of-scope scheduler code, but the wallet library itself produces the poisoned `ReceivedOutput` from purely public on-chain data. Exploitation requires mining a block paying the multisig — costly but not privileged; any miner is an unprivileged party relative to Serai. Alternatively, any pool/service that legitimately pays out to a Serai address via coinbase triggers this accidentally.

### Recommendation
Do not return coinbase outputs from `scan_block`/`scan_transaction` as plain `ReceivedOutput`s. Either:
- Skip `block.txdata[0]` inside `scan_block` (or check `tx.is_coinbase()`), or
- Extend `ReceivedOutput` with a `matures_at: Option<u32>`/`is_coinbase: bool` field populated during scanning so consumers can enforce maturity before scheduling.

Also persist the marker through `ReceivedOutput::read`/`write` so deserialized outputs retain the distinction [5](#0-4) .

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs context
// A miner crafts a block whose coinbase pays to the Serai P2TR script.
let scanner = Scanner::new(group_key).unwrap();
let block: Block = /* block where txdata[0] (coinbase) pays p2tr_script_buf(group_key) */;

let received = scanner.scan_block(&block);
// `received` contains a ReceivedOutput for the coinbase output.
// Nothing on it distinguishes it from a mature, spendable output:
assert_eq!(received[0].value(), coinbase_amount);
// A spend plan built on this outpoint produces a transaction that is
// consensus-invalid for 100 blocks (BIP coinbase maturity), and every
// signing attempt silently produces an unbroadcastable transaction.
```

The root cause is that `scan_block` treats `block.txdata[0]` identically to all other transactions and `ReceivedOutput` has no maturity field to carry the distinction forward [6](#0-5) .

#[derive(Clone, PartialEq, Eq, Debug)]
pub struct ReceivedOutput {
  // The scalar offset to obtain the key usable to spend this output.
  offset: Scalar,
  // The output to spend.
  output: TxOut,
  // The TX ID and vout of the output to spend.
  outpoint: OutPoint,
}

impl ReceivedOutput {
  /// The offset for this output.
  pub fn offset(&self) -> Scalar {
    self.offset
  }

  /// The Bitcoin output for this output.
  pub fn output(&self) -> &TxOut {
    &self.output
  }

  /// The outpoint for this output.
  pub fn outpoint(&self) -> &OutPoint {
    &self.outpoint
  }

  /// The value of this output.
  pub fn value(&self) -> u64 {
    self.output.value.to_sat()
  }

  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  /// Scan a block.
  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
  }
