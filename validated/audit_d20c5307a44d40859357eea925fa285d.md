### Title
Unbounded length-prefix read in `is_atom_canonical` causes an uncaught `IndexError` on submitted spend-bundle CLVM data - (File: `chia/full_node/mempool_manager.py`)

### Summary
CVE-2016-2857 is an out-of-bounds heap read in QEMU's `net_checksum_calculate`, caused by trusting an attacker-controlled payload-length field to index into a buffer without validating it against the buffer's actual size. The direct analog in this codebase is `is_atom_canonical()` in `chia/full_node/mempool_manager.py`, which decodes a CLVM atom's variable-length size prefix (1–6 bytes) and walks that many bytes forward in the buffer without ever checking that the buffer actually contains that many remaining bytes.

### Finding Description
`is_atom_canonical` inspects the leading byte at `offset` to determine how many extra prefix bytes (`prefix_len`, up to 5) encode the atom length, then reads them in a loop: [1](#0-0) 

The loop `for i in range(prefix_len): offset += 1; atom_len |= clvm_buffer[offset]` increments `offset` and indexes `clvm_buffer` purely based on the bit pattern of the first byte, with no check that `offset < len(clvm_buffer)`. This function is called from `is_clvm_canonical`, which itself is invoked directly on attacker-supplied, unparsed byte buffers — the raw `puzzle_reveal` and `solution` bytes of every coin spend in a submitted `SpendBundle` — during mempool admission: [2](#0-1) 

`is_clvm_canonical` itself also indexes `clvm_buffer[offset]` in its main loop without a length check before dispatching into `is_atom_canonical`: [3](#0-2) 

If a submitter crafts a `puzzle_reveal` or `solution` whose *last* byte is a multi-byte length-prefix marker (e.g. `0xFC`, indicating 5 more prefix bytes should follow) but the buffer ends immediately after that byte, `clvm_buffer[offset]` reads past the end of the `bytes` object. In CPython this raises `IndexError` rather than causing memory corruption (Python `bytes` are bounds-checked at the interpreter level), but the exception is unhandled at this call site inside `validate_spend_bundle`, which runs under the mempool/blockchain lock during spend-bundle admission.

### Impact Explanation
An unhandled `IndexError` raised while holding the mempool/blockchain lock during `validate_spend_bundle` would propagate out of `add_spend_bundle` and out of the enclosing transaction-processing task instead of being converted into a controlled `MempoolInclusionStatus.FAILED` / `Err` result like every other validation failure in this pipeline. This breaks the invariant that malformed submitter input is turned into a normal rejection (`Err.INVALID_COIN_SOLUTION`, etc.) and instead surfaces as an unexpected exception in the transaction-processing path, which is a spend-triggered halt/denial-of-service condition for that processing flow — a single crafted spend bundle, submittable by any unprivileged peer or wallet user via the normal transaction submission path, can trigger it deterministically.

### Likelihood Explanation
High reachability: `is_clvm_canonical` is called unconditionally for every coin spend in every submitted `SpendBundle` during `validate_spend_bundle`, requiring no special privileges, no valid signature success first, and no coin ownership — only a syntactically crafted `puzzle_reveal`/`solution` byte string ending mid length-prefix. This is trivial to construct and does not require the CLVM to actually be a valid, executable program.

### Recommendation
Add explicit bounds checks in `is_atom_canonical` (and in the dispatching loop of `is_clvm_canonical`) before indexing `clvm_buffer[offset]`, mirroring the defensive pattern already used elsewhere in the codebase (e.g. `chia/full_node/full_block_utils.py`'s `skip_bytes`/`skip_list`, which explicitly check `n > len(buf)` and raise a descriptive `ValueError`). Any out-of-range condition encountered while decoding the prefix should be treated as "not canonical" (or raise a caught/expected exception) rather than allowed to surface as a raw `IndexError` from within the locked admission path.

### Proof of Concept
```python
from chia.full_node.mempool_manager import is_clvm_canonical

# Last byte 0xFC signals a 6-byte length prefix (5 more bytes expected),
# but the buffer ends right there.
malicious_buf = b"\xfc"
is_clvm_canonical(malicious_buf)  # raises IndexError: index out of range
```
Embedding such a byte string as the trailing bytes of a coin spend's `puzzle_reveal` or `solution` inside a `SpendBundle` submitted through the normal wallet/RPC transaction-submission path reaches `validate_spend_bundle`'s call to `is_clvm_canonical(bytes(coin_spend.puzzle_reveal))` / `is_clvm_canonical(bytes(coin_spend.solution))` and raises the same unhandled exception there.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```
