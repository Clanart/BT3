Based on my investigation, this codebase has a good analog in the AI-conflict-resolution write path — there is `resolveWithin` path-containment protection at write time, and `validateResolutionPaths` restricts written paths to the exact set of pre-existing conflicted files. However, there is no analogous "staleness/freshness" check I found on the actual data that matters most: **there is no verification that the resolved file content Copilot returns for hunk N still corresponds to the same conflict hunk that was present when the prompt was built**, other than a hunk-count match.

### Title
Silent commit corruption via unvalidated Copilot-generated conflict resolutions written verbatim to tracked files - (File: app/src/lib/stores/app-store.ts, app/src/lib/copilot-conflict-resolution.ts)

### Summary
The Copilot AI-assisted conflict-resolution feature treats the model's JSON response as authoritative merged code and splices it into the user's working tree with only structural checks (JSON shape, path allow-listing, hunk count, and "no leftover conflict markers" regexes). There is no semantic/content validation that the returned `resolvedContent` for a given hunk is a plausible, safe combination of the `ours`/`theirs` content actually present in that hunk. A model response that is stale (e.g., produced against different in-flight hunk content, batching/ordering bug, or a poisoned/compromised BYOK provider response) is accepted and written directly to disk and staged with `git add`, exactly analogous to the oracle report's "stale/incorrect data used without freshness checks."

### Finding Description
`parseCopilotConflictResolution` in `app/src/lib/copilot-conflict-resolution.ts` (lines 281-466) validates only structural shape: JSON well-formedness, that `path`/`hunks`/`reasoning` are the right types, and a regex check that a hunk's `resolvedContent` doesn't still contain a `<<<<<<<`/`=======` pair. [1](#0-0) 

`validateResolutionPaths` (lines 473-521) enforces only that the returned file paths exactly match the expected conflicted-file set and that the hunk *count* per file matches — it never checks that hunk *content* corresponds to what was actually sent for that file/hunk. [2](#0-1) 

`reassembleResolvedFile` (lines 549-599) then splices `hunkResolutions[hunkIndex].resolvedContent` into the original on-disk file **purely by ordinal position** ("matched by order, not by line number"), with no check that the resolution text is derived from (or even related to) the `ours`/`theirs` content of that specific hunk. [3](#0-2) 

Finally, `_applyCopilotConflictResolutions` in `app/src/lib/stores/app-store.ts` writes the reassembled content straight to the resolved path (after only a directory-traversal check via `resolveWithin`) and immediately runs `git add` to stage it — with no diff review, checksum, or "does this look like a merge of ours/theirs" gate before staging. [4](#0-3) 

The one freshness-style guard present is unrelated to hunk content: it only detects when the *user* has externally resolved the file since the prompt was sent (comparing git status), not whether the Copilot response itself is stale relative to the conflict data it was asked to resolve. [5](#0-4) 

### Impact Explanation
Because ordinal hunk-index splicing is trusted without content verification, any mechanism that causes the model's structural output to be well-formed but semantically wrong for the file it targets (BYOK/custom provider response injection, a compromised model backend, or a bug in chunk/hunk ordering across `createDependencyAwareChunks` batches) results in **silent corruption of code the user is about to commit and push** — the exact class of harm called out as in-scope ("silent corruption of what the user commits or pushes"). Since the flow auto-stages (`git add`) the written file, the corrupted content can be committed without the user ever diffing it against the true `ours`/`theirs` sides, if they rely on the dialog's "Continue Merge" action without inspecting the generated diff.

### Likelihood Explanation
This requires a BYOK/custom Copilot provider (attacker-controlled or MITM'd endpoint) returning a structurally valid but content-mismatched JSON resolution, or a chunking/ordering bug when files are split via `createDependencyAwareChunks`/`MaxConcurrentChunks`. This is a real, reachable path through user-facing functionality (Copilot conflict resolution with BYOK providers is a documented supported configuration — see `CopilotProviderConfig`), but it is gated behind the user opting into AI conflict resolution and, for the highest-likelihood variant, configuring a non-default (BYOK) provider. It does not require local/physical access or leaked credentials, satisfying the "Valid Impact" criteria (attacker controls a remote/API-like response consumed by the app).

### Recommendation
Add semantic validation before splicing/staging Copilot-provided hunk resolutions:
- Verify each hunk's `resolvedContent` is derived from the corresponding hunk's actual `oursContent`/`theirsContent`/`baseContent` (e.g., via a similarity/diff check, or requiring the model to echo hunk identifiers/checksums that are verified against the original context sent).
- Bind each returned hunk resolution to an opaque per-hunk token/hash computed from the original conflict text, and reject/refuel resolutions whose token doesn't match, rather than trusting ordinal position alone.
- Surface a mandatory diff review step before `_applyCopilotConflictResolutions` stages files, rather than allowing "Continue Merge" to silently `git add` unreviewed content.

### Proof of Concept
1. Configure a BYOK Copilot provider under attacker control (or intercept its HTTPS responses).
2. Trigger a merge/rebase/cherry-pick with real conflicts and invoke "Resolve with Copilot" (`_startCopilotConflictResolution` → `_resolveConflictsWithCopilot`).
3. Have the malicious provider return a structurally valid JSON payload matching `path` and hunk *count* for the true conflicted file, but with `resolvedContent` unrelated to the actual `ours`/`theirs` diff (e.g., inserting a backdoored line while looking superficially plausible).
4. `parseCopilotConflictResolution` and `validateResolutionPaths` both pass (correct path, correct hunk count, no literal conflict markers). [6](#0-5) 
5. `reassembleResolvedFile` splices the attacker content into the file at the exact conflict location by ordinal index.
6. The user clicks "Continue Merge" in `copilot-conflicts-dialog.tsx`, triggering `_applyCopilotConflictResolutions`, which writes the file and immediately `git add`s it — staging the corrupted content for commit without any content-fidelity check. [7](#0-6)
