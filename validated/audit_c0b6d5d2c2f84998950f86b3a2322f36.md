## Analysis

I found a valid analog in the codebase. It is a Go-level division-by-zero (panic, not just a Solidity-style revert) triggered by an under-validated governance parameter (`Kip71GasTarget`) used as a divisor in the KIP-71 base fee calculation — directly analogous to the external report's pattern of an unguarded, potentially-zero value being used as a divisor/log input in a critical, protocol-relied-upon fee/pricing computation, causing complete denial of service to the affected computation path.

### Title
Unvalidated `Kip71GasTarget` governance parameter can be set to `0`, causing a division-by-zero panic in `NextMagmaBlockBaseFee` that halts base-fee computation for every node - (File: `params/kip71_config.go`)

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by the governance-configurable `GasTarget` parameter without checking it is non-zero. While the sibling parameter `Kip71BaseFeeDenominator` has an explicit `FormatChecker` requiring `v != 0`, `Kip71GasTarget` is registered with `noopFormatChecker`, meaning governance can set it to `0` with no validation. Once `GasTarget == 0` and any block uses gas (`parentGasUsed > 0`), all Kaia nodes computing the next block's base fee for header verification will hit a native Go `big.Int` division-by-zero, which is a runtime panic rather than a graceful revert.

### Finding Description
`NextMagmaBlockBaseFee` computes the next base fee using `gasTarget` as a divisor in both the "gas used above target" and "gas used below target" branches: [1](#0-0) 

Specifically:
```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget))   // panics if gasTarget == 0
```
and the symmetric branch for `parentGasUsed < gasTarget`.

The early-exit shortcut `if parentGasUsed == gasTarget { return ... }` only protects the case where both values are `0` simultaneously. As soon as any block uses any gas at all (`parentGasUsed > 0`) while `gasTarget == 0`, execution falls into the `parentGasUsed > gasTarget` branch and divides by zero.

The governance parameter registry validates `Kip71BaseFeeDenominator` against zero explicitly: [2](#0-1) 

But `Kip71GasTarget` uses `noopFormatChecker`, i.e., no validation at all: [3](#0-2) 

This is a governance-parameter attack surface explicitly in scope: a governance vote (or a misconfigured/malicious governing node under single-governance mode) can push `Kip71GasTarget = 0` through the normal governance parameter update flow, since no `FormatChecker` rejects it.

### Impact Explanation
`NextMagmaBlockBaseFee` is called from `VerifyMagmaHeader`, which is part of consensus-critical header verification executed by every full node (validators and non-validators alike) processing every new block after the Magma hardfork: [4](#0-3) 

If the divisor panics, this is not a contained EVM `revert` — it's a Go runtime panic in the core block-processing path. Depending on panic recovery elsewhere in the call stack, this can crash node processes or otherwise halt block production/verification network-wide, since all nodes independently recompute and verify the expected base fee for every block. This is a total denial of service of the chain's core state-transition/pricing logic, far more severe than the referenced report's contained `Claimer` contract revert, since it can't be worked around by any alternate (e.g., "self-claim") path — the entire chain's block verification depends on this function.

### Likelihood Explanation
This requires a governance parameter change (`Kip71GasTarget = 0`) to be approved and activated, which is a privileged but explicitly in-scope surface ("governance parameters", "KIP-71 pricing" per the rules). Unlike the arithmetic edge case in the Sherlock report (which required an improbable confluence of liquidity/utilization conditions), triggering this bug requires only a single governance parameter update to `0` — no other preconditions, race, or probability-dependent liquidity state is needed. Once set, the very next block with nonzero gas usage (i.e., almost immediately) triggers the panic.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (mirroring the one already used for `Kip71BaseFeeDenominator`) that rejects `0`:
```go
FormatChecker: func(cv any) bool {
    v, ok := cv.(uint64)
    return ok && v != 0
},
```
Additionally, as defense-in-depth, `NextMagmaBlockBaseFee` itself should guard against `gasTarget == 0` (e.g., treat it the same way `BaseFeeDenominator == 0` is already defensively handled elsewhere) rather than relying solely on governance-side validation.

### Proof of Concept
1. Via governance (single or contract-based mode), submit a parameter update setting `governance.kip71.gastarget = 0`. `kaiax/gov/param.go`'s `Kip71GasTarget` entry has no `FormatChecker` rejecting `0`, so the update is accepted.
2. Once the parameter activates at the target block, any subsequent block that consumes any gas (`parentGasUsed > 0`, which is normal for any non-empty block) causes `NextMagmaBlockBaseFee` to hit the `parentGasUsed > gasTarget` branch: [5](#0-4) 
3. `new(big.Int).SetUint64(gasTarget)` is `0`; `x.Div(x, 0)` in Go's `math/big` panics with `division by zero`.
4. Because this function is invoked during header verification (`VerifyMagmaHeader`) by every node processing the new block, the panic propagates through consensus-critical code, halting block verification/production network-wide.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
