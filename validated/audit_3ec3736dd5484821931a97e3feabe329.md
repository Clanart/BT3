### Title
Missing zero-check on governance-settable `Kip71GasTarget` causes a division-by-zero panic in Magma base-fee calculation - ([File: params/kip71_config.go])

### Summary
The `Kip71GasTarget` governance parameter is registered with `FormatChecker: noopFormatChecker` (no validation at all), unlike its sibling `Kip71BaseFeeDenominator`, which explicitly rejects `0` (`return ok && v != 0`). `GasTarget` is subsequently used as a divisor in `KIP71Config.NextMagmaBlockBaseFee`, so a governance vote setting `gastarget=0` produces a chain-wide panic in every node's block-header validation/preparation path, exactly analogous to the otphp `digits` report: an externally-influenced numeric parameter is bounded only in some cases and unbounded in the code path that performs division/modulo.

### Finding Description
`Kip71GasTarget`'s parameter definition has no format check: [1](#0-0) 

Compare with `Kip71BaseFeeDenominator`, which is explicitly guarded against zero: [2](#0-1) 

The accepted value flows unchanged into `ParamSet.GasTarget` and then into `KIP71Config.GasTarget` via `ToKip71Config`: [3](#0-2) [4](#0-3) 

`NextMagmaBlockBaseFee` reads `gasTarget := kc.GasTarget` and — unlike `BaseFeeDenominator`, which has an explicit `if kc.BaseFeeDenominator == 0 { ... fallback ... }` guard — never checks whether `gasTarget` is zero before dividing by it: [5](#0-4) [6](#0-5) [7](#0-6) 

If `parentGasUsed != gasTarget` (true for virtually every real block once `gasTarget = 0`, since any nonzero gas usage exceeds the target), the code executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`. Go's `math/big.Int.Div` panics with `"division by zero"` when the divisor is zero, which is an unrecoverable runtime panic unless the calling goroutine has a deferred recover — precisely the uncatchable-`Error`-class failure mode described in the report (`DivisionByZeroError` extends `Error`, not `Exception`, and is not caught by ordinary exception handlers).

### Impact Explanation
`NextMagmaBlockBaseFee`/`VerifyMagmaHeader` are called from the core block-processing path (block validator, header preparation, chain makers, worker, gas price oracle) used by every full node and validator: [8](#0-7) 
Once `gastarget=0` becomes an active governance parameter (via a normal governance-vote header/transaction, which is the only mechanism through which `Kip71GasTarget` reaches this code, and is explicitly named in the reachable "governance parameters" category), every node computing or verifying the next block's base fee panics. This halts block production/validation network-wide — a consensus-breaking denial of service, not merely a local error, because the divide-by-zero is deterministic and identical on every honest node once the parameter takes effect.

### Likelihood Explanation
The value is only reachable through the governance-vote mechanism (a governing-council parameter change), so it's not exploitable by an arbitrary unprivileged transaction sender in the way the PHP `digits` bug is reachable via any URI. However, unlike most other KIP-71 parameters, there is no validation anywhere in the pipeline (`param.go` FormatChecker, `paramset.go` Set, or `kip71_config.go` runtime) that prevents `0` from being accepted and propagated — a single inconsistent/missing bound check is enough. Given that `BaseFeeDenominator` was deliberately special-cased against the same class of bug, `GasTarget`'s omission looks like an unintentional oversight rather than a deliberately trusted invariant.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` rejecting `v == 0` (mirroring `Kip71BaseFeeDenominator`), and/or add a defensive zero-check with fallback logic inside `NextMagmaBlockBaseFee` in `params/kip71_config.go` (as already done for `BaseFeeDenominator`) before dividing by `gasTarget`.

### Proof of Concept
1. Submit/approve a governance vote setting `kip71.gastarget = 0` (via the standard `kaiax/gov` header-vote mechanism, which accepts the value because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`).
2. Once active, on the next block where `parentGasUsed != 0` (i.e., almost any block with transactions), `KIP71Config.NextMagmaBlockBaseFee` executes:
   ```go
   gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget) // gasTarget=0
   x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
   y := x.Div(x, new(big.Int).SetUint64(gasTarget)) // panic: division by zero
   ```
   at [9](#0-8)  (and symmetric code at lines 118-121 for the gas-below-target branch).
3. This function is invoked from block header preparation/validation on every node, causing a chain-wide panic/halt.
