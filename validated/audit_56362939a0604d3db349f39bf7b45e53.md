## Finding: Missing HTML/script-context escaping (`<`, `>`) in upb's JSON encoder used by Ruby, PHP, and Python protobuf bindings

### Title
Inconsistent ProtoJSON escaping of `<`/`>` in upb-based encoder (Ruby/PHP/Python) breaks the XSS-hardening invariant enforced by the C++/Java/C# JSON encoders — (File: `upb/json/encode.c`)

### Summary
Protobuf's C++, Java, and C# ProtoJSON encoders deliberately escape `<` and `>` (and several other JS/HTML-sensitive code points) beyond what the JSON spec requires, explicitly to prevent script-context injection when JSON output is embedded in HTML (e.g., inside a `<script>` block). The shared `upb` C JSON encoder — which backs the Ruby, PHP, and Python protobuf bindings — does not implement this same escaping, silently breaking that cross-language security invariant.

### Finding Description
The Froxlor report's failed invariant was: attacker-controlled string content must be escaped before being placed into an HTML-rendering context; the fix chosen upstream was to stop treating attacker strings as raw/pre-escaped ("`|raw`" in the template).

Protobuf's own JSON serializers face an analogous but narrower risk: string field values are attacker/customer-controlled data (from a bounded ProtoJSON/binary parse), and once serialized back to JSON, that JSON is a very common thing for consuming applications to embed inside `<script>` tags or inline JS in HTML pages. Recognizing this, three of protobuf's independent JSON encoders proactively escape `<` and `>` (and a set of Unicode line/format separators) even though the JSON spec does not require it:

- C++: `MustEscape()` explicitly lists `case '<': case '>':` with the comment "not required by the JSON spec, but help to prevent security bugs in JavaScript." [1](#0-0) 

- Java: `replacementChars` maps `<>&='` to `\uXXXX` "to prevent XSS risks." [2](#0-1) 

- C#: `CommonRepresentations` maps `<`/`>` to `\u003c`/`\u003e`, with the comment "Escaping of < and > are required for HTML security." [3](#0-2) 

The upb JSON encoder (`jsonenc_put_escaped_char`/`jsonenc_stringbody`), which is the single shared native encoder for Ruby, PHP, and Python's C-extension bindings, only escapes the JSON-mandated characters (`\n \r \t \" \f \b \\` and control bytes `< 0x20`) — it passes `<` and `>` straight through, unescaped: [4](#0-3) 

The identical function is embedded verbatim in the generated amalgamated sources used by the PHP and Ruby extensions: [5](#0-4) [6](#0-5) 

Ruby's `Message.encode_json` and PHP's JSON serialization path call directly into `upb_JsonEncode`, so any consumer of these bindings gets the unhardened output: [7](#0-6) 

The PHP pure-PHP fallback path (`GPBJsonWire::escapedJson`) has the same gap — it only treats control chars, `"`, and `\` as escapable, and the STRING-field code path even delegates to plain `json_encode($value, JSON_UNESCAPED_UNICODE)`, which by default does not escape `<`/`>`/`&` either: [8](#0-7) 

The check that "should" transfer from the C++/Java/C# encoders — treat `<`/`>` as unsafe-for-embedding and rewrite them as `\u003c`/`\u003e` — is simply absent from the upb encoder's character table, so the bypass is total: any string field content containing `<` or `>` (fully attacker-controlled data from a bounded parse) passes through unmodified into the JSON output of Ruby, PHP, and Python bindings.

### Impact Explanation
If a consuming application (the only realistic exposure point, since protobuf itself has no HTTP endpoint) takes attacker-controlled string field values, round-trips them through protobuf (e.g., parses a request, stores it, and later re-serializes to ProtoJSON for embedding into a server-rendered HTML page inside a `<script>` block, a pattern the C++/Java/C# encoders explicitly defend against), the Ruby/PHP/Python-based services lose that defense-in-depth layer. A payload such as `</script><script>alert(document.domain)</script>` in a string field would break out of the script context and execute, mirroring the stored-XSS mechanics of the Froxlor report, but arising from an inconsistency between protobuf's own JSON encoder implementations rather than a template `|raw` bug. Impact is limited to consumers who rely on this specific (documented-by-comment, not by public API contract) escaping behavior; it does not affect binary wire parsing, memory safety, or JSON round-trip correctness (unescaped `<`/`>` are still valid, semantically-equivalent JSON).

### Likelihood Explanation
Likelihood is moderate-to-low: the escaping asymmetry is only exploitable if the consuming application embeds ProtoJSON output directly into an HTML/script context without its own output encoding — a pattern the C++/Java/C# comments imply is anticipated but is not a guaranteed or documented cross-language contract of ProtoJSON. Any Ruby, PHP, or Python protobuf-based service that follows this embedding pattern (common in server-side-rendered dashboards/logs that dump proto messages as JSON into inline scripts) is affected without any special privileges — a bounded, valid ProtoJSON/binary payload from an ordinary client is sufficient to reach the sink.

### Recommendation
Add `<` and `>` (and ideally the same additional code points the C++/Java/C# encoders escape: `\u2028/\u2029`, BOM, etc.) to `jsonenc_put_escaped_char` in `upb/json/encode.c`, and regenerate/resync the embedded copies in `php-upb.c` and `ruby-upb.c`. Also align the PHP pure-PHP fallback (`GPBJsonWire::escapedJson` and the `json_encode(...)` call for `GPBType::STRING`) to escape the same character set, so all supported language bindings provide a consistent JSON-embedding-safety guarantee.

### Proof of Concept
Using the upb JSON encoder test harness pattern already present in the repo (`upb/json/encode_test.cc`), encoding a string field containing `<script>` reproduces the gap:

```c
// Using upb_test_Box (or any message with a string field) as in
// upb/json/encode_test.cc's JsonEncodeGeneric() helper.
upb_test_Box* box = upb_test_Box_new(arena.ptr());
upb_test_Box_set_str(box, upb_StringView_FromString("</script><script>alert(1)</script>"));
std::string json = JsonEncodeGeneric(box, ..., /*options=*/0);
// json == {"str":"</script><script>alert(1)</script>"}
// C++'s google::protobuf::json::MessageToJsonString on an equivalent proto2 message instead
// produces {"str":"\u003c/script\u003e\u003cscript\u003ealert(1)\u003c/script\u003e"}
```

Compare with the existing Java regression test that encodes the same style of payload and asserts it *is* escaped by the reflection-based Java encoder — no equivalent assertion or escaping exists for the upb path: [9](#0-8) 

This confirms the C++/Java/C# encoders enforce the "no raw `<`/`>` in ProtoJSON string output" invariant while the upb encoder (Ruby/PHP/Python) does not, reproducing the exact escaping gap that enabled the Froxlor stored-XSS analog.

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}

static void jsonenc_stringbody(jsonenc* e, upb_StringView str) {
  const char* ptr = str.data;
  const char* end = UPB_PTRADD(ptr, str.size);

  while (ptr < end) {
    jsonenc_put_escaped_char(e, *ptr);
    ptr++;
  }
}

static void jsonenc_string(jsonenc* e, upb_StringView str) {
  jsonenc_putstr(e, "\"");
  jsonenc_stringbody(e, str);
  jsonenc_putstr(e, "\"");
}
