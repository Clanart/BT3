### Title
Attacker-controlled Bitcoin transaction overwrites `data`/`presumed_origin` of every earlier scanned output in the same block - (File: processor/src/networks/bitcoin.rs)

### Summary
Analogous to CVE-2021-40889 (where attacker-supplied input is written into a file later trusted/executed), `Bitcoin::get_outputs` accumulates matched `Output`s in a vector scoped outside the per-transaction loop, then stamps the *current* transaction's `extract_serai_data` result and presumed origin onto every accumulated `Output` — not just the ones from that transaction. An unprivileged party who gets any second transaction into the same block injects arbitrary `data` and a spoofed `presumed_origin` into honest users' deposit outputs.

### Finding Description
In `get_outputs`, `outputs` is declared once before iterating `block.txdata[1 ..]`:

- `let mut outputs = vec![];` is outside the `for tx in &block.txdata[1 ..]` loop, so it retains outputs from all prior transactions in the block.
- After scanning each tx, `if outputs.is_empty() { continue; }` skips only when *no* output has ever been collected — a tx matching zero scripts still proceeds if any earlier tx matched.
- Then `let presumed_origin = ...` is derived from `tx.input[0]` (the attacker's input's prevout script) and `let data = Self::extract_serai_data(tx)` (the attacker's OP_RETURN/InInstruction payload), and the loop `for output in &mut outputs` writes `output.data = data` (for `OutputType::External`) and `output.presumed_origin = presumed_origin` into *all* accumulated outputs, including ones from unrelated earlier transactions. [1](#0-0) 

The result is that attacker-controlled bytes are written into `Output.data`, a field which is persisted and later consumed as the deposit's Serai instruction (e.g. destination address for minted funds) via `Output::data()`/`Output::read`. [2](#0-1) 

### Impact Explanation
`data` on an `External` output is the instruction payload telling Serai what to do with the deposit (per the literal test, it encodes e.g. a `Shorthand::transfer` to a Serai address). By including a transaction paying any dust… actually paying anything at all (even a transaction with *no* matching outputs suffices, since the guard only checks the accumulated vector) in the same block as a victim's deposit, the attacker replaces the victim's `data` with their own instruction — redirecting the credited deposit to an attacker-controlled Serai address — and forges `presumed_origin` used for refund/origin attribution. This is injection of untrusted content into a record later treated as authoritative, mirroring the CMSUno write-then-execute flow.

### Likelihood Explanation
Fully reachable by any unprivileged Bitcoin user: broadcast a transaction in the same block as a victim deposit (trivially achievable by observing the mempool, or simply by chance on busy blocks). No validator status, collusion, or malformed curve inputs required — just ordinary public transactions.

### Recommendation
Scope the stamping to outputs collected from the *current* transaction: either move `outputs` inside the per-tx loop (collecting into a fresh per-tx vector then extending the outer one), or record each output's source tx and only mutate `outputs[start_of_this_tx ..]`. Additionally, the `tx.input[0]` origin derivation should only run for txs that actually produced matched outputs.

### Proof of Concept
1. Victim broadcasts a deposit TX paying to the Serai external address with OP_RETURN data encoding "mint to victim".
2. Attacker, seeing it in the mempool, broadcasts any transaction in the same block (e.g. a self-transfer carrying an OP_RETURN with "mint to attacker", or even a tx with no Serai outputs at all).
3. `get_outputs` scans the block: victim's tx pushes an `Output` into `outputs`; attacker's tx is then processed, `outputs.is_empty()` is false, so `extract_serai_data(attacker_tx)` and the attacker's input origin are written into the victim's `Output.data`/`presumed_origin`.
4. The processor persists the corrupted `Output` (via `Output::write`) and later executes the attacker's instruction for the victim's funds.
