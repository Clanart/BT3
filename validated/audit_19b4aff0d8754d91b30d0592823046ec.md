### Title
`SignableTransaction::new` omits the OP_RETURN output from fee/weight accounting, producing under-priced or unrelayed transactions — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the LiquidityPool bug where `hedgingFees` were added to `usedFunds` by `_hedge()` but never deducted from the trader-facing accounting, `SignableTransaction::new` pushes an `OP_RETURN` output into the real transaction's output list while every subsequent accounting step — vsize/fee computation, minimum-relay-fee check, `NotEnoughFunds` check, change deduction, and the `MAX_STANDARD_TX_WEIGHT` check — is computed on a model transaction that does not contain that output. The result is a systematic under-accounting of the transaction's true weight by up to ~90 vbytes (an 8-byte value + script with up to 80 bytes of data), so the wallet commits to an incorrect fee formula.

### Finding Description
The OP_RETURN output is appended to `tx_outs`, the vector that becomes the real signed transaction's outputs (`networks/bitcoin/src/wallet/send.rs:194-202`). However, the weight/vbytes used for all fee and limit math is obtained from `calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204) and `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (line 226), and `calculate_weight_vbytes` builds its template transaction *only* from `payments` and an optional change output (`send.rs:85-99`). The `data`/`OP_RETURN` output is never part of the template.

Consequences of the missing deduction of the OP_RETURN weight:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) and `fee_with_change = fee_per_vbyte * vbytes_with_change` (line 227) are both computed on too-small vbytes. When change is created, the change amount is `input_sat - payment_sat - fee_with_change` (lines 228-232), so the *actual* fee paid equals the underestimated `needed_fee` while the real transaction is larger — the effective fee rate is strictly below the caller-requested `fee_per_vbyte`.
2. The `TooLowFee` check compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` (line 211) using the same underestimated `vbytes`. A caller can pass `fee_per_vbyte` at the relay minimum, pass the check, yet produce a transaction whose real fee rate falls below the minimum relay fee — a transaction nodes will not relay.
3. The `NotEnoughFunds` check (line 215) and change-creation branch (lines 224-235) also use the understated fee, so a change output can be created where the residual `input_sat - payment_sat - true_fee` is actually below `DUST`.
4. The `MAX_STANDARD_TX_WEIGHT` check (line 241) uses `weight` that excludes the OP_RETURN output; a transaction near the 400,000 WU limit can pass the check while the signed transaction exceeds the standardness weight limit and is unrelayed.

`fee()` (lines 138-141) honestly reports `sum(prevouts) - sum(outputs)`, so `needed_fee()` — the value the scheduler uses to amortize fees and decide plan viability — disagrees with reality whenever `data` is present.

### Impact Explanation
An unprivileged party who can cause a `data` payload to be attached to a spend (the `data`/`OP_RETURN` field is populated from externally supplied instruction data) induces the wallet to produce transactions paying a lower effective fee rate than the network layer requested. At minimum this wastes the difference between intended and actual confirmation priority; at boundary fee rates the signed transaction fails minimum-relay-fee or standardness checks entirely and cannot be broadcast, freezing the inputs' value in an unusable transaction plan. When change is included, the accounting error can also leave a sub-dust change output commitment inconsistent with the dust logic. This mirrors the reported bug's shape: a cost added to the real artifact (margin/`usedFunds` there; the OP_RETURN output's weight here) that the shared accounting ledger never deducts, corrupting every downstream balance/limit decision.

### Likelihood Explanation
Any invocation of `SignableTransaction::new` with `data: Some(..)` triggers the discrepancy — it is deterministic, not probabilistic. Exploitation requires only that an external party can influence the `data` field of a spend (as with instruction-carrying deposits/withdrawals) and that the fee rate or transaction size is near a boundary for the strongest effects. The under-payment direction is guaranteed on every data-bearing transaction; the unrelayed-transaction outcome requires boundary conditions, making the reliable impact a Medium-severity accounting error rather than a guaranteed loss.

### Recommendation
Include the OP_RETURN output in the weight model. Either pass the already-built `tx_outs` (including the OP_RETURN output) into `calculate_weight_vbytes`, or add an explicit `data_len` parameter so the template transaction contains the real `ScriptBuf::new_op_return` output in both the no-change and with-change calculations at lines 204 and 226. Also recompute `weight`/`vbytes` after the change decision so the `TooLowFee` and `MAX_STANDARD_TX_WEIGHT` checks operate on the true transaction shape.

let inputs = vec![output];
let data = vec![0u8; 80]; // max allowed OP_RETURN payload
let change = p2tr_script_buf(key).unwrap();

let tx = SignableTransaction::new(
  inputs.clone(),
  &[(p2tr_script_buf(key).unwrap(), 1_000)],
  Some(change),
  Some(data),
  fee_per_vbyte, // e.g. exactly the minimum relay rate
).unwrap();

// needed_fee was computed without the OP_RETURN output
let real_vbytes = /* vsize of a tx built identically but including the
                   OP_RETURN output in the template */;
