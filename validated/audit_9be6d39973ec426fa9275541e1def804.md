## Analysis

`_fillSameChain` computes the escrow to release for output index `i` differently depending on whether that specific output has now reached full completion: [1](#0-0) 

On the full-fill branch it reads `_orders[commitment][token]` directly — the **entire current escrow balance stored under that token address** — rather than a value scoped to input index `i`. Compare that to the partial-fill branch, which computes a proportional amount from `order.inputs[i].amount`: [2](#0-1) 

The escrow storage itself is keyed **only by `(commitment, token address)`**, not by input index: [3](#0-2) 

and `_withdraw` simply decrements that single bucket by whatever amount it's told to release, with no check that the amount corresponds to a specific input record's rightful share: [4](#0-3) 

### The exploit path

If an order has two (or more) output assets whose corresponding `order.inputs[i].token` / `order.inputs[j].token` (i ≠ j) resolve to the **same token address**, the escrow for both inputs is pooled into a single `_orders[commitment][token]` bucket at order placement (aggregation happens because the mapping has no per-index dimension). When output `i` reaches `amountFilled == totalRequired` first (the full-fill branch), line 118 reads and releases the **entire remaining pooled balance** for that token — including the portion that was escrowed on behalf of input `j`, which is still logically owed to whoever fills output `j`. The solver who completes output `i` receives more input-escrow than `order.inputs[i].amount` warrants, and when the second solver later attempts to complete output `j`, `_withdraw` finds `_orders[commitment][token] == 0` (or reduced) and reverts with `UnknownOrder`, or – if any bucket balance is left – receives a wrong (short) amount. This breaks the escrow allocation invariant: one solver can capture funds intended for a different output/input pairing, and the rightful solver is denied their allocation or bridging revenue.

This matches the "broken timeout/refund/reward accounting" and "wrong beneficiary or amount"/"stealing or loss of funds" impact categories in scope, since escrow that belongs to one part of the order (input `j`) is misappropriated by the filler of a different, unrelated output (`i`) purely because the token addresses collide in the flat `_orders` mapping.

**Caveat / unverified assumption:** I was not able to inspect `placeOrder` (in `IntentGatewayV2.sol`) within the available iterations to confirm whether it explicitly forbids duplicate token addresses across different `order.inputs[]` entries. The vulnerability as described depends on such duplication being possible (unprivileged, since the order creator fully controls the `inputs` array). If `placeOrder` enforces uniqueness of input token addresses across indices, this specific multi-output collision path would not be reachable, though the underlying design smell (full-fill branch trusting the aggregate bucket balance rather than a per-index value) would remain.

### Title
Escrow bucket collision in `_fillSameChain` full-fill branch lets one solver drain input escrow reserved for other outputs - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_fillSameChain`'s full-fill branch releases `_orders[commitment][token]` in its entirety instead of a value scoped to the specific input index being settled, while the underlying `_orders` mapping pools escrow purely by token address across all input entries of an order.

### Finding Description
For an order with multiple `output.assets`/`inputs` entries that share the same input token address, escrow for all such inputs accumulates in one `_orders[commitment][token]` slot. When any single output index first reaches `amountFilled == totalRequired`, line 118 releases the *whole* remaining balance of that slot to the filler of that output, rather than the proportional amount tied to `order.inputs[i].amount`. This lets the first-completing solver capture escrow that belongs to a different, still-open output.

### Impact Explanation
A solver can obtain more input-token escrow than their output contribution entitles them to, at the expense of the rightful beneficiary of another output in the same order (who will subsequently hit `UnknownOrder` in `_withdraw` or receive a reduced amount). This is a direct escrow/fund-misallocation issue.

### Likelihood Explanation
Requires an order with two output legs whose paired input token addresses collide — fully controllable by the (unprivileged) order creator at `placeOrder` time, assuming no dedup validation exists there (unverified in this review).

### Recommendation
Track escrow per input index (or per `(commitment, inputIndex)`), not solely per `(commitment, token)`, or reject orders whose `inputs[]` contain duplicate token addresses across distinct indices at `placeOrder` time. On full-fill, cap the released amount to the input's originally escrowed amount minus already-released proportional amounts for that specific index.

### Proof of Concept
1. Place an order with two outputs (index 0 and 2) both paired to input token `DAI`: `inputs[0].amount = 100 DAI`, `inputs[2].amount = 50 DAI`; total pooled `_orders[commitment][DAI] = 150`.
2. Solver A fully fills output 0 in one call (`solverAmount == totalRequired` for output 0), triggering the full-fill branch at line 118, which reads/releases the full `150 DAI` bucket to Solver A instead of `100 DAI`.
3. Solver B later attempts to fill output 2; `_withdraw` finds `_orders[commitment][DAI] == 0`, reverting `UnknownOrder`, denying Solver B their rightful `50 DAI` escrow. [1](#0-0) [4](#0-3)
