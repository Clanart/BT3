### Title
External Bitcoin deposits to a retiring multisig are silently dropped during `ClosingExisting` - (File: `processor/src/multisigs/mod.rs`)

### Summary
Bitcoin outputs sent to the old multisig’s external address while rotation is in `ClosingExisting` are detected as spendable multisig outputs, but are discarded before their attached instruction is decoded or any forwarding/refund plan is created. [1](#0-0) [2](#0-1) 

### Finding Description
`Bitcoin::get_outputs` scans every non-coinbase transaction and returns any output whose `script_pubkey` matches the multisig’s external, branch, change, or forward offsets. [1](#0-0)  The resulting `Output::key` is recovered from the Taproot key minus the recorded offset, so an external output using offset zero resolves to the old multisig key. [3](#0-2) 

`scanner_event_to_multisig_event` retains only `External` outputs for instruction processing. [4](#0-3)  The special forwarding logic that converts an old-key deposit into `PlanFromScanning::Forward` is executed only when the current step is `ForwardFromExisting`. [5](#0-4)  When the step has advanced to `ClosingExisting`, that loop is skipped and the later unconditional filter drops every external output belonging to the existing key before `instruction_from_output` is called. [2](#0-1) 

The same separation happens again when the acknowledged outputs are scheduled: `filter_outputs_due_to_closing` removes `External` and `Forwarded` outputs from the existing-key set, allowing only a matching `Branch` output or an authenticated `Change` output to proceed. [6](#0-5)  Although the UTXO scheduler already has a forwarding plan that spends an old-key output to the new multisig’s forward address, no such plan is invoked for these deposits. [7](#0-6) 

### Impact Explanation
A valid Bitcoin deposit to the still-scanned old external address can be permanently stranded: it is neither reported as an inbound instruction, refunded to the presumed origin, forwarded to the new multisig, nor retained as a scheduler UTXO. [8](#0-7)  After the old key is retired, no active signing set remains for the output’s threshold key, making the deposited funds unspendable even though they were publicly received at a Serai-controlled address. [9](#0-8) [10](#0-9) 

### Likelihood Explanation
The trigger is an ordinary external Bitcoin transaction sent during the key-rotation window after the processor enters `ClosingExisting` but while the old key is still being scanned. No validator compromise, malformed encoding, malicious RPC response, or protocol violation is required; the sender only needs to use the previously advertised external multisig address. The narrow timing requirement limits the exploitability, so this is most appropriately rated Medium rather than Critical or High. [1](#0-0) [2](#0-1) 

### Recommendation
While the old key remains scanned, always preserve external outputs sent to it: create a forwarding plan through `Scheduler::forward_plan`/`shim_forward_plan`, or emit a refund plan when a valid refund destination is available. [7](#0-6)  For deposits carrying instructions, store the instruction in `ForwardedOutputDb` before forwarding so it is emitted when the forwarded output is observed under the new key. [11](#0-10)  Do not silently discard old-key `External` outputs in `ClosingExisting`; reject them only if the old key is no longer scanned.

### Proof of Concept
1. Rotate a Bitcoin multisig so `current_rotation_step(block_number)` returns `RotationStep::ClosingExisting` while the old key is still active in the scanner. [12](#0-11) 
2. Broadcast a non-coinbase transaction containing a normal P2TR output to the old external script and an OP_RETURN payload encoding a valid `InInstruction`.
3. `Bitcoin::get_outputs` returns `Output { kind: OutputType::External, output, ... }`, and `output.key()` equals the old group key. [1](#0-0) [3](#0-2) 
4. `scanner_event_to_multisig_event` retains it as external, skips the `ForwardFromExisting` forwarding block, then reaches this condition and drops it:

```rust
RotationStep::ForwardFromExisting | RotationStep::ClosingExisting => true,
```

from `processor/src/multisigs/mod.rs`. [2](#0-1) 
5. The instruction is never pushed, no refund is created, no `PlanFromScanning::Forward` is saved, and the later closing filter also refuses to return the output to the scheduler. [13](#0-12) [14](#0-13)
