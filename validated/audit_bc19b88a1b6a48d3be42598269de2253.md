### Title
Out-of-range participant index in PedPoP blame evaluation panics the verifier (invalid read → crash) - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP blame APIs (`BlameMachine::blame`, `AdditionalBlameMachine::blame`, and the shared `blame_internal`) index their internal `enc_keys` / `commitments` maps with the caller-supplied `sender`/`recipient` `Participant` values without checking that they are within the registered range `1..=n`. `Participant` only guarantees non-zero (`Participant::new`, crypto/dkg/src/lib.rs:29-35); any `u16` up to 65535 is accepted. Indexing a `HashMap` with `map[&key]` panics on a missing key, so an accusation naming a participant index `> n` crashes the party evaluating blame — an invalid read driven by attacker-controlled inputs, the same bug class as CVE-2017-9147 (invalid read → denial of service on crafted input).

### Finding Description
`AdditionalBlameMachine::new` registers encryption keys and commitments only for participants `1..=n` (crypto/dkg/pedpop/src/lib.rs:649-661). The blame path then performs unchecked indexing:

1. `Decryption::decrypt_with_proof` dereferences `self.enc_keys[&decryptor]` (crypto/dkg/pedpop/src/encryption.rs:388) as soon as a `proof` is `Some`, before any DLEq verification. If `recipient` (the accuser) is a valid `Participant` but `> n`, this panics.
2. `BlameMachine::blame_internal` dereferences `self.commitments[&sender]` (crypto/dkg/pedpop/src/lib.rs:599) when evaluating whether an accused share is consistent with the accused sender's commitments. If `sender` (the accused) is `> n`, this panics — reachable after the message parses, its PoP verifies, and it decrypts.

Both `EncryptionKeyProof::read` (crypto/dkg/pedpop/src/encryption.rs:267-269) and `EncryptedMessage::read` (crypto/dkg/pedpop/src/encryption.rs:171-177) are pure length-bounded parses of public bytes; neither validates the participant arguments of `blame`. Nothing in `blame`/`blame_internal`/`decrypt_with_proof` enforces `sender, recipient ∈ 1..=n`, and `AdditionalBlameMachine`'s own docs acknowledge this: "Usage of invalid commitments … may cause everything from inaccurate blame to panics" (crypto/dkg/pedpop/src/lib.rs:647-648) — but the panic is triggered by the participant indexes, not the commitments.

The concrete downstream path exists in `processor/src/key_gen.rs` `VerifyBlame` handling (lines 504-549), which forwards wire-supplied `accuser`/`accused` values — parsed from a tributary transaction with only non-zero validation (coordinator/src/tributary/transaction.rs:346-353) — into `AdditionalBlameMachine::blame`.

### Impact Explanation
Any party able to submit a blame/accusation message (an unprivileged protocol participant, or anyone who can get a `VerifyBlame`-shaped request evaluated) can crash the node processing it by naming a `Participant` index outside `1..=n`. This halts key-generation / blame adjudication for that validator and, since blame evaluation is how faults are resolved, lets a faulty DKG participant stall the protocol instead of being slashed. Per-node crash, no secret leakage — consistent with Medium severity, matching the source advisory's DoS class.

### Likelihood Explanation
The trigger requires only: (a) a `Participant::new(k)` with `n < k <= 65535` (passes the non-zero check), and (b) a parseable `EncryptedMessage` plus a parseable `EncryptionKeyProof` — both obtainable by replaying/serializing any well-formed values, since the panic occurs on index lookup before cryptographic validity matters (`enc_keys[&decryptor]` is evaluated prior to `dleq.verify`). No valid shares or signatures are needed. The only mitigating factor is that the accusation message must reach the blame API, which assumes an authenticated channel — but authenticity does not constrain the `Participant` value itself.

### Recommendation
In `BlameMachine::blame`, `AdditionalBlameMachine::blame`, and/or `blame_internal`/`decrypt_with_proof`, reject `sender`/`recipient` values not present in the registered `enc_keys`/`commitments` maps (e.g., return the accuser/sender as faulty or a `PedPoPError::InvalidParticipant`) instead of using `map[&key]` indexing. Range-check `u16::from(p) <= n` at the boundary where wire `Participant` values are converted.

### Proof of Concept
```rust
// crypto/dkg/pedpop: n = 4 DKG; attacker submits blame with accuser = 5.
let params_n = 4u16;
// AdditionalBlameMachine::new registers enc_keys only for 1..=4.
let machine = AdditionalBlameMachine::<Ristretto>::new(context, params_n, commitment_msgs).unwrap();

// Participant::new(5) succeeds — only zero is rejected.
let bad_accuser = Participant::new(5).unwrap();
let accused = Participant::new(1).unwrap();

// Any parseable EncryptedMessage + any parseable EncryptionKeyProof.
let msg = EncryptedMessage::<Ristretto, SecretShare<_>>::read(&mut bytes, params).unwrap();
let proof = Some(EncryptionKeyProof::read(&mut proof_bytes).unwrap());

// Decryption::decrypt_with_proof evaluates self.enc_keys[&bad_accuser]
// (encryption.rs:388) -> HashMap index panic -> crash.
machine.blame(accused, bad_accuser, msg, proof);
```
