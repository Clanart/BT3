### Title
Malicious repository can escape the repository sandbox via symlinked directories when revealing/opening/copying file paths from Changes, History, PR, and conflict-resolution views - ([File: app/src/lib/app-shell.ts](), [File: app/src/ui/history/selected-commits.tsx](), [File: app/src/ui/changes/sidebar.tsx](), [File: app/src/ui/changes/filter-changes-list.tsx](), [File: app/src/ui/lib/conflicts/unmerged-file.tsx](), [File: app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx](), [File: app/src/ui/open-pull-request/pull-request-files-changed.tsx](), [File: app/src/ui/diff/binary-file.tsx]())

### Summary
GitHub Desktop has a dedicated, symlink-aware sandboxing primitive, `resolveWithin()`, that resolves a repo-relative path and refuses to return it if it escapes the repository root — even via a directory symlink (this exact escape scenario is unit-tested). [1](#0-0)  This strict check is only applied in two call sites: the "Open Repository from URL" deep-link handler and the Copilot conflict-context file reader. [2](#0-1) [3](#0-2)  Every other UI surface that turns a repository-relative `file.path` (sourced from git status/diff/commit output, i.e. from data the repository author fully controls) into an absolute path for "Reveal in File Manager", "Open with Default Program", "Open in External Editor", and "Copy File Path" uses a bare `Path.join(repository.path, path)` with no traversal/symlink check at all. [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) 

This is structurally identical to the reported bug class: the same conceptual operation ("resolve a path that is supposed to stay inside a trusted boundary") has two implementations — one strict, one lenient — and the lenient one is reachable by an attacker-controlled input, defeating the purpose of the strict check that exists elsewhere in the same codebase.

### Finding Description
`resolveWithin(rootPath, ...segments)` resolves symlinks via `fs.realpath` on both the root and the candidate path and rejects the result unless the real, symlink-resolved path stays under the real root. [10](#0-9)  The test suite explicitly documents the threat model this defends against: a directory symlink inside the sandboxed root that points outside of it. [11](#0-10) 

A cloned/fetched repository is attacker-controlled: it can contain a tracked symlink (e.g. a directory-like entry `evil -> ../../../../`) checked out onto the user's disk when they clone or pull. Git will happily commit and check out symlink blobs; nothing in Desktop's checkout/status pipeline validates symlink targets before or after checkout (no `core.symlinks`/target validation found in `app/src/lib/git/*.ts` aside from an unrelated match in `refs.ts`). Once such a symlink exists inside the working directory, any relative "file path" that Desktop later reports underneath it (via `git status`/`git diff --name-status`/commit tree listings, surfaced as `WorkingDirectoryFileChange.path` or `CommittedFileChange.path`) is still just a repository-relative string like `evil/whatever`. All of the UI call sites below turn that string into an absolute path with plain `Path.join`, which does **not** dereference symlinks and therefore does not detect that `repository.path/evil` actually points outside the repo:

- `revealInFileManager()` — used everywhere as the "Reveal in File Manager" menu action. [12](#0-11) 
- `onOpenItem` in the commit/history file list ("Open with Default Program"). [13](#0-12) 
- `onOpenItem` in the Changes sidebar. [14](#0-13) 
- The merge/rebase conflict-resolution dropdown, which builds an absolute path and immediately calls `openFile()` on it. [15](#0-14) 
- The Copilot conflict-resolution dialog's overflow menu, same pattern. [16](#0-15) 
- Pull-request file-changed view "Open with Default Program" / binary-file open. [9](#0-8) [17](#0-16) 
- "Copy File Path" clipboard action, which writes the joined absolute path (pointing outside the repo) to the clipboard. [18](#0-17) 

By contrast, `dispatcher.ts`'s `openRepositoryFromUrl` (triggered by an `x-github-client://` deep link, also attacker-influenceable) explicitly guards the exact same "open/reveal a repo-relative path" operation with `resolveWithin`, refusing and logging when the path escapes the repo. [2](#0-1)  `copilot-conflict-context.ts` does the same for reading conflicted file contents. [3](#0-2)  The existence of these two hardened call sites shows the maintainers recognize this exact attacker primitive is a real threat — the inconsistency is that the fix was applied only to the deep-link and Copilot-conflict paths, not to the (far more directly reachable) "open a file from the working directory / a commit / a PR" flows that every user exercises on every malicious repository they open.

### Impact Explanation
Clicking "Open with Default Program", "Reveal in File Manager", or "Open in External Editor" on a file whose reported path traverses a malicious symlink causes Desktop to open/reveal a file *outside* the cloned repository, using a path fully chosen by the repository author. Depending on where the symlink points (e.g., SSH keys, shell profile, another repo's working tree), this can lead to disclosure of local file locations/content (opened in an editor the attacker can also influence the association of via the crafted extension) or, at minimum, silent user confusion about what is actually being opened/committed, satisfying the "file read outside the repo" impact category from an unprivileged, attacker-controlled repository. It is medium rather than critical because it requires the user to interact with the compromised entry (click Open/Reveal) and depends on the OS's handling of the target file type — there is no fully unattended code-execution primitive demonstrated here from local evidence alone.

### Likelihood Explanation
Likelihood is medium: the attacker only needs the victim to clone or fetch a hostile repository (a completely ordinary, expected Desktop action) and then interact with a normal context-menu action ("Open", "Reveal in File Manager") on a file that looks unremarkable in the Changes/History/PR file list. No admin rights, local access, or prior compromise is needed — the entire attack surface is git content the remote repository owner controls, matching the required threat model.

### Recommendation
Route every repo-relative-path-to-absolute-path conversion that is subsequently used for filesystem interaction (open, reveal, copy) through `resolveWithin()` (or `resolveWithinPosix`/`resolveWithinWin32` as appropriate), exactly as already done in `dispatcher.ts` and `copilot-conflict-context.ts`, and refuse the action (with a user-visible error, mirroring the `log.error('Prevented attempt to open path outside of the repository root...')` pattern) when resolution fails. At minimum, harden `revealInFileManager()` in `app-shell.ts` since it is the single shared helper used by nearly every call site listed above — fixing it centrally would close most of the gap in one place.

### Proof of Concept
1. Attacker creates a public repository with two commits:
   - Commit 1: adds a real file `evil/marker.txt`.
   - Commit 2: deletes the `evil/` directory and replaces path `evil` with a symlink pointing to `../../../../` (or another sensitive absolute-reachable location via relative traversal), then re-adds a file so that git status/diff will report a path such as `evil/passwords.txt` referencing content that, after checkout, resolves through the symlink to a location outside the repository.
2. Victim clones the repository in Desktop; the symlink `evil` is created on disk pointing outside the repo root, per normal `git checkout` symlink handling (no symlink-target validation exists in `app/src/lib/git/*.ts`).
3. Victim opens the commit/PR containing the change and right-clicks the file entry `evil/passwords.txt` in `selected-commits.tsx` / `pull-request-files-changed.tsx`, then chooses "Reveal in File Manager" or "Open with Default Program".
4. `Path.join(repository.path, file.path)` (`app/src/ui/history/selected-commits.tsx:384`, `app/src/lib/app-shell.ts:62`) produces `<repoPath>/evil/passwords.txt`, which the OS resolves through the symlink to a path outside the repository — no `resolveWithin` check ever runs, unlike the equivalent, already-hardened deep-link code path in `dispatcher.ts:1963`.
5. The file manager/editor opens the out-of-repo target, confirming the sandbox escape that `resolveWithin` was designed to prevent (as demonstrated by the passing/failing cases in `app/test/unit/path-test.ts:65-100`).

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
