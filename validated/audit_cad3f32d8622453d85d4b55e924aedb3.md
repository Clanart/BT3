## Analysis Summary

The Nouns fork report's core invariant is: **a permissioned list of tokens, iterated over in a batch, where one bad entry can block payout of the whole batch to a rightful party.** The closest Hyperbridge analog is in the IntentGatewayV2 cross-chain intents system, where `order.inputs` (a token list chosen freely by the *unprivileged order creator*, not governance) is later replayed through an all-or-nothing transfer loop that has no timeout-based recovery path.

### Title
Unprivileged order creator can permanently lock a solver's earned escrow (and any bundled legitimate tokens) by including one reverting ERC-20 in `order.inputs` — ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` releases every token in a `WithdrawalRequest.tokens` array in a single loop, reverting the entire call if any single transfer fails. [1](#0-0) 
The `RedeemEscrow`/`RefundEscrow` messages that carry this token list are dispatched with `timeout: 0` from `_fillCrossChain`, `_cancelFromDest`, and `_cancelFromSource`, i.e. they never expire and have no `onPostRequestTimeout` fallback. [2](#0-1) [3](#0-2) 

### Finding Description
Any user can create a cross-chain order with an arbitrary `order.inputs` list — there is no allowlist check on input token addresses in the escrow/order-creation path visible in `IntentGatewayV2.sol`. An attacker crafts an order whose `order.inputs` bundles a legitimate, attractive token (e.g. USDC) alongside a malicious ERC-20 that reverts unconditionally on `transfer`/`safeTransfer` once called from the gateway (e.g. a custom contract, or a token that self-destructs/pauses after listing).

A solver, seeing an attractive fill opportunity, calls `_fillCrossChain` on the destination chain: they pay the beneficiary the output assets and the gateway dispatches a `RedeemEscrow` POST request back to the source chain to release `order.inputs` (all of them, malicious token included) to the solver. [4](#0-3) 

On the source chain, `onAccept` for `RedeemEscrow` calls `_withdraw`, which loops through every token in the request and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each; a revert on the malicious token entry reverts the whole transaction. [1](#0-0) 
Because the dispatch used `timeout: 0`, there is no expiry and thus no alternate code path (like `onPostRequestTimeout`) that could ever unlock the escrow for the solver — the message can never be successfully delivered, no matter how many times a relayer retries.

### Impact Explanation
The solver has already irrevocably paid the beneficiary on the destination chain in good faith, but can never redeem any of their escrowed input tokens on the source chain — including the legitimate, valuable token bundled with the malicious one — because the transfer loop is all-or-nothing and the request has no timeout/recovery mechanism. This is a direct, permanent loss of funds for an honest, unprivileged actor (the solver), caused entirely by another unprivileged actor (the order creator) with no governance, admin, or relayer collusion required — matching the required impact category "stealing or loss of funds" and the pivot that escrowed/bridged assets "must move exactly once and only to the rightful beneficiary."

### Likelihood Explanation
Likelihood is meaningful because order creation and token-list composition are fully permissionless client actions; no proposal review or governance gate exists (unlike the original Nouns report, where a DAO vote at least provides some scrutiny). A solver only needs to be enticed by favorable pricing on one attractive token within a multi-token order to be exposed, without visibility into the other bundled token's transfer behavior ahead of time.

### Recommendation
- Do not make escrow release all-or-nothing across an entire token list. Release each token independently (e.g. loop with per-token try/catch or per-token dispatch) so a single malicious/reverting token cannot block release of the other tokens.
- Give `RedeemEscrow`/`RefundEscrow` requests a real, non-zero timeout with an `onPostRequestTimeout` handler that refunds/unlocks whatever is redeemable, instead of `timeout: 0`.
- Consider allowing solvers to select/verify (or a per-token allowlist for) which input tokens they are willing to accept as escrow release, so a bundled malicious token doesn't need to block the entire order's redemption.

### Proof of Concept
1. Attacker deploys `EvilToken`, a normal-looking ERC-20 whose `transfer()` reverts whenever called by the `IntentGateway` contract address specifically (or simply reverts unconditionally after the order is escrowed).
2. Attacker creates a cross-chain order with `order.inputs = [ {token: USDC, amount: 10_000e6}, {token: EvilToken, amount: 1} ]`, escrowing both tokens on the source chain.
3. An honest solver observes the order, calls `_fillCrossChain` on the destination chain, and pays the beneficiary the required output assets, triggering dispatch of a `RedeemEscrow` request (`timeout: 0`) back to the source chain naming the solver as beneficiary for `order.inputs`. [4](#0-3) 
4. When the relayer delivers this request, `onAccept` → `_withdraw` iterates `[USDC, EvilToken]`; the `EvilToken.transfer` call reverts, reverting the whole `_withdraw` call and the entire `onAccept` transaction. [1](#0-0) 
5. Because the request was dispatched with `timeout: 0`, it never expires; every future delivery attempt hits the same revert. The solver's 10,000 USDC (and their already-paid destination-side output) is permanently locked/lost, with no possible recovery path in the current code.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });
