### Title
ProtoJSON parser skips duplicate-key / oneof-exclusivity validation for `null`-valued fields, silently deviating from the MUST-reject invariant - (File: `src/google/protobuf/json/internal/parser.cc`)

### Summary
In `ParseField()`, when a JSON field's value is the literal `null` (and the field is not `google.protobuf.Value`/`NullValue`), the function returns via `lex.Expect("null")` at line 1252 *before* calling `Traits::RecordAsSeen(*field, msg)` at line 1256. This early return, gated on an attacker-controlled JSON token (`null`), bypasses the bookkeeping step that the parser relies on to detect duplicate keys and conflicting `oneof` members, exactly analogous to the ERC1155Fuse `_transfer` short-circuit that returns before the balance/ownership invariant is enforced. [1](#0-0) 

### Finding Description
`ParseField` looks up the target field, then checks whether the next JSON token is `null`:

```
if (lex.Peek(JsonLexer::kNull)) {
    MessageType type = ClassifyMessage(Traits::FieldTypeName(*field));
    if (type != MessageType::kValue && type != MessageType::kNull) {
      return lex.Expect("null");
    }
}
SeenState seen = Traits::RecordAsSeen(*field, msg);
``` [2](#0-1) 

The comment immediately above this code explicitly documents the gap: *"Note that spec behavior is that we should do duplicate key checking in the case of a null value, but this implementation currently does not (b/519557203)."* [3](#0-2) 

`RecordAsSeen` is the mechanism that later enforces the "MUST reject" rule for duplicate keys on the same field and for conflicting members of the same `oneof`:

```
SeenState seen = Traits::RecordAsSeen(*field, msg);
if (seen == SeenState::kOneofAlreadySeen ||
    (seen == SeenState::kFieldAlreadySeen &&
     !lex.options().allow_legacy_nonconformant_behavior)) {
  return lex.Invalid(...); // "'%s' has already been set..."
}
``` [4](#0-3) 

Because a `null`-valued key returns before `RecordAsSeen` runs, the parser never records that field/oneof-case as "seen." Consequently:
- An attacker-controlled ordinary ProtoJSON payload with `{"foo": null, "foo": "x"}` will not be rejected as a duplicate key, even though non-null duplicates (`{"foo": "y", "foo": "x"}`) are correctly rejected by the same code path.
- For a `oneof`, `{"oneof_a": null, "oneof_b": "x"}` will not trigger the "already set" error that non-null conflicting oneof members trigger, because the null-valued branch never calls `RecordAsSeen` to mark the oneof case as taken.

This is the direct analog of the ERC1155Fuse bug: both bugs are an *early return, gated on an attacker-supplied value equal to a "no-op-looking" condition* (`to == oldOwner` for ERC1155Fuse; `value == null` here), which short-circuits before a required invariant-enforcing step (balance/ownership check vs. `RecordAsSeen` duplicate/oneof bookkeeping) — silently deviating from the spec's MUST-reject/MUST-revert requirement instead of failing loudly.

### Impact Explanation
JSON/ProtoJSON parsing is a supported public parse API that ordinary clients use to submit untrusted, bounded payloads to trusted schemas. Downstream application code (e.g., request validators, gateways, systems that treat "parse succeeded" as proof the JSON was unambiguous and spec-conformant) may rely on the parser to reject duplicate/conflicting keys as an integrity guarantee — the same class of reliance the external report warns about ("problems for other contracts using this token, since they assume the token was transferred if `safeTransferFrom` does not revert"). Here, a consuming application that assumes strict duplicate-key/oneof-exclusivity enforcement (a documented, intentional MUST-reject behavior in the non-legacy mode) can silently accept ambiguous/conflicting JSON that should have been rejected, when one of the conflicting occurrences is `null`. This is a correctness/integrity gap rather than memory corruption or RCE; impact is bounded to parse-result correctness for a known, narrow input shape.

### Likelihood Explanation
High trigger likelihood: the payload shape (`null` followed by a non-null duplicate, or `null` in one oneof member followed by a value in a different member of the same oneof) is trivial for any external client to construct with a bounded, valid JSON payload against a trusted schema — no special permissions, schema tricks, or huge inputs required. The gap is also explicitly acknowledged by an open, unresolved bug reference (`b/519557203`) in the code comment itself, confirming it is a known, currently-unfixed condition rather than a hypothetical.

### Recommendation
Call `Traits::RecordAsSeen(*field, msg)` (and perform the duplicate/oneof-conflict check) before or independent of the `null`-value short-circuit, so that a `null` value is treated as "seen" for duplicate-key and oneof-exclusivity purposes just like any other value, matching the documented JSON-parsing spec requirement referenced in the existing code comment.

### Proof of Concept
Given a proto schema with a `oneof` group containing `string oneof_a` and `string oneof_b`, or simply a message with a single field `foo`, and a strict (non-`allow_legacy_nonconformant_behavior`) parse call through the public ProtoJSON parsing API (`Message::ParseFrom`-style entry into `json::internal::parser.cc`):

- Non-null duplicate: `{"foo": "a", "foo": "b"}` → correctly rejected via `SeenState::kFieldAlreadySeen` path at line 1261-1267.
- Null-then-duplicate: `{"foo": null, "foo": "b"}` → the first occurrence hits the `lex.Peek(JsonLexer::kNull)` branch and returns via `lex.Expect("null")` at line 1252 without calling `RecordAsSeen`; the second occurrence is then processed as if it were the *first* sighting of `foo`, so the "already been set" error at line 1264-1266 is never raised.

I was not able to run this payload through an actual build/conformance test in this environment (no execution access), so this is a static-code-path trace, not an executed reproduction; the acknowledged bug ID `b/519557203` in the source comment corroborates that this is a real, currently open gap rather than a misreading of the code.
