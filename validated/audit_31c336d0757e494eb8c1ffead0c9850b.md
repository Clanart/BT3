### Title
Webhook HMAC verification does not cover the shop-identifying header, allowing cross-shop webhook forgery - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

### Summary
`ShopifyApp::WebhookVerification#verify_request` only authenticates the raw POST body via HMAC, while the shop identity used by application code (`shop_domain`) is read from a separate, unsigned request header. Because the header is not part of the signed data, an attacker who possesses one legitimately-signed webhook body (e.g., from their own shop, which they fully control) can replay it to the app with a forged `X-Shopify-Shop-Domain` header, causing the app to process the request as if it belongs to a different (victim) shop.

### Finding Description
`verify_request` computes and checks the HMAC over `request.raw_post` only: [1](#0-0) 

`hmac_valid?` in `PayloadVerification` likewise only ever hashes the `data` argument (the body), never any header: [2](#0-1) 

The `shop_domain` value that downstream application code is documented to trust for tenant/job attribution is pulled straight from the unauthenticated header `HTTP_X_SHOPIFY_SHOP_DOMAIN`: [3](#0-2) 

The gem's own documentation instructs custom webhook controllers to enqueue background jobs keyed by this unverified `shop_domain` value alongside the webhook body: [4](#0-3) 

This is the same class of bug as the reported issue: one value (`body`/`makerAsk.price`) is what's cryptographically verified, while a *different*, attacker-controllable value (`X-Shopify-Shop-Domain` header/`takerBid.price`) is what's actually trusted and acted upon downstream. Because the app's webhook secret is a single, app-wide `ShopifyApp.configuration.secret` shared across every shop that installs the app (not a per-shop signing key bound to shop identity), any merchant/attacker who installs the app on their own shop obtains a genuinely-signed `(body, HMAC)` pair for events they control. They can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `X-Shopify-Shop-Domain` header. `verify_request` still passes since it never checks the header, and the job is enqueued attributing attacker-supplied webhook content to the victim shop.

### Impact Explanation
Depending on how a given app's webhook jobs use `shop_domain` (e.g., looking up/updating a `Shop` record, mandatory privacy webhooks like `customers/redact`/`shop/redact`, triggering side effects scoped to "the shop"), this allows an unprivileged attacker to inject forged, cross-shop webhook events. This can result in state corruption, spurious privacy/redaction actions, or business-logic abuse attributed to a shop the attacker does not own or control — a cross-shop/cross-tenant integrity violation reachable from an unrelated (attacker-controlled) merchant account.

### Likelihood Explanation
Any developer/merchant who has installed the target app on their own store can generate one authentic signed webhook (body+HMAC) trivially, then replay it against the public webhook endpoint with a spoofed shop-domain header — no secret leakage or privileged access is required beyond normal app installation. The `WebhookVerification` concern and its documented usage pattern (`shop_domain` used directly, unchecked against the signed payload) is present as shipped in the gem.

### Recommendation
Do not trust `X-Shopify-Shop-Domain` (or any other unsigned header) as the shop identity for a verified webhook. Either:
- Bind the shop domain into the HMAC verification itself (e.g., include the header value in the data being hashed, or otherwise cryptographically tie body+shop together), or
- Cross-check the header-derived shop against an independently trusted source (e.g., the shop associated with the webhook subscription/session on Shopify's side via the newer `ShopifyAPI::Webhooks::Request`/`Registry.process` flow, which resolves `shop` from Shopify's verified webhook envelope rather than a raw header), and reject mismatches before allowing any job to run business logic scoped to that shop.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, granting the app the configured webhook topics (e.g. `orders/create`).
2. Attacker performs an action on their own store that triggers a real webhook; Shopify sends `POST /webhook_path` with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` — a fully valid `(B, HMAC)` pair.
3. Attacker replays `POST /webhook_path` to the app with the same body `B` and same valid `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `verify_request` calls `hmac_valid?(request.raw_post)`, which passes because the body/HMAC pair is genuinely valid — the header is never checked.
5. Controller/job code (per the gem's documented pattern) calls `shop_domain`, which returns the attacker-supplied `victim-shop.myshopify.com`, and processes the attacker's webhook payload as if it originated from the victim shop.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
