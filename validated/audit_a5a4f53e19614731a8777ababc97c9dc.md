### Title
Legacy bank precompile `send` methods bypass `BlockedAddr` recipient check, allowing transfers to blocked/blacklisted addresses - (File: precompiles/bank/legacy/v555/bank.go, precompiles/bank/legacy/v580/bank.go)

### Summary
The bank precompile's `send` method (callable only by a registered ERC20 native pointer contract) is supposed to move native/bank-module coins between Sei addresses on behalf of an EVM caller. In the current/latest implementation this call is routed through `p.bankMsgServer.Send(...)`, which enforces the bank module's recipient blocklist check. However, several still-registered legacy versions of the precompile (versions active for historical/pre-upgrade EVM bytecode, selected via `GetVersioned` in `precompiles/bank/setup.go`) implement `send` by calling `p.bankKeeper.SendCoins(...)` directly, which never checks `BlockedAddr`.

### Finding Description
The bank module's blocklist ("full restriction" analog) is enforced only at specific choke points: `msgServer.Send`/`MultiSend`, and `BaseKeeper.SendCoinsFromModuleToAccount`, all of which explicitly call `k.BlockedAddr(to)` before transferring: [1](#0-0) [2](#0-1) 

The lower-level `BaseSendKeeper.SendCoins` (and `SendCoinsWithoutAccCreation`) itself performs **no** blocklist check at all — it only debits the sender and credits the receiver: [3](#0-2) 

The current bank precompile correctly avoids this gap by using the msg-server path, which does enforce `BlockedAddr`: [4](#0-3) 

But several legacy precompile versions still registered and reachable through `GetVersioned` — e.g. `v555` and `v580` — implement `send` by calling `p.bankKeeper.SendCoins` directly, completely skipping the blocklist check: [5](#0-4) [6](#0-5) 

These legacy implementations remain wired into the live precompile dispatch table: [7](#0-6) 

This mirrors the reported bug class: the "soft restriction"-equivalent enforcement (blocklist) exists at one call path (`msgServer.Send`) but is missing at an alternate reachable path (`SendCoins` invoked directly from the legacy precompile), letting a caller route funds to a blocklisted/blocked address by using a different entry point than the intended one — exactly the "point to a different receiver/path to bypass the restriction" pattern from the report.

### Impact Explanation
An EVM caller that is a registered ERC20 native pointer contract (or anyone able to trigger a call into the legacy precompile version, if the historical bytecode path is still reachable at runtime) can send native/bank coins to addresses that the bank module blocklist is designed to protect (e.g., module accounts, the EVM coinbase address range, or other addresses intentionally blocked from receiving funds). Funds landing in a blocked module account outside expected accounting flows can corrupt module invariants (as explicitly warned in the bank module's own documentation) and could lead to fund loss, broken invariants, or a halted network. [8](#0-7) 

### Likelihood Explanation
Likelihood depends on whether the legacy precompile code paths (`v555`, `v580`) are actually still dispatched for current-height transactions or are retained purely for replaying/verifying historical blocks pre-upgrade. Since they are compiled into the versioned dispatch table returned by `GetVersioned` and keyed by upgrade version strings, whether they are reachable by a live transaction depends on the EVM precompile version-selection logic (not fully inspected here) — this could not be conclusively verified within available context. If reachable for current transactions (e.g., via replay of the same contract bytecode compiled against an older EVM precompile ABI/version, or if version selection is based on contract deployment height rather than current chain height), the bug is directly and trivially triggerable by any pointer contract caller.

### Recommendation
Audit the versioned precompile dispatch logic to confirm whether legacy bank precompile versions (`v552` through `v580`, before the fix presumably occurred) can still be invoked for current-block transactions. If so, either patch those legacy `send` implementations to call the blocklist-checking path (`bankMsgServer.Send` or explicit `BlockedAddr` checks before `SendCoins`), or ensure the version-selection mechanism can never route new transactions to those legacy contracts. More generally, `BaseSendKeeper.SendCoins`/`SendCoinsWithoutAccCreation` should not be treated as safe against blocked recipients by any caller — every caller of `SendCoins` outside of `msgServer.Send` (including all precompiles, wasm bridge transferrers, etc.) should be audited to ensure `BlockedAddr` is checked before invoking it.

### Proof of Concept
Not independently executable within this analysis (would require deploying/registering an ERC20 native pointer and confirming the current on-chain upgrade version routes calls to the `v555`/`v580` precompile implementation). Conceptually: a pointer contract calls `send(sender, blockedRecipient, denom, amount)` on the bank precompile at `0x0000000000000000000000000000000000001001`; if the runtime resolves to the `v555`/`v580` implementation, `p.bankKeeper.SendCoins` is invoked directly with no `BlockedAddr(blockedRecipient)` check, succeeding where the `MsgSend`-based path would fail with "not allowed to receive funds".

func (p Precompile) send(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, value *big.Int, readOnly bool) ([]byte, error) {
	if readOnly {
		return nil, errors.New("cannot call send from staticcall")
	}
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, err
	}
	denom := args[2].(string)
	if denom == "" {
		return nil, errors.New("invalid denom")
	}
	pointer, _, exists := p.evmKeeper.GetERC20NativePointer(ctx, denom)
	if !exists || pointer.Cmp(caller) != 0 {
		return nil, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())
	}
	amount := args[3].(*big.Int)
	if amount.Cmp(utils.Big0) == 0 {
		// short circuit
		return method.Outputs.Pack(true)
	}
	senderSeiAddr, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		return nil, err
	}
	receiverSeiAddr, err := p.accAddressFromArg(ctx, args[1])
	if err != nil {
		return nil, err
	}

	if err := p.bankKeeper.SendCoins(ctx, senderSeiAddr, receiverSeiAddr, sdk.NewCoins(sdk.NewCoin(denom, sdk.NewIntFromBigInt(amount)))); err != nil {
		return nil, err
	}

	return method.Outputs.Pack(true)
}

## Blocklisting Addresses

The `x/bank` module accepts a map of addresses that are considered blocklisted
from directly and explicitly receiving funds through means such as `MsgSend` and
`MsgMultiSend` and direct API calls like `SendCoinsFromModuleToAccount`.

Typically, these addresses are module accounts. If these addresses receive funds
outside the expected rules of the state machine, invariants are likely to be
broken and could result in a halted network.
