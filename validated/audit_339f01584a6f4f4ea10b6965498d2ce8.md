### Title
`SignableTransaction::new` balance check bypassed by u64 overflow, letting payments/change exceed real input value - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The bug-class analog: code accepts a reported sum of value without verifying it actually fits/exists. `SignableTransaction::new` verifies funds with `input_sat < (payment_sat + needed_fee)` and computes change with `input_sat.checked_sub(payment_sat + fee_with_change)`, but `payment_sat` is an unchecked `u64` sum of attacker-influenceable payment amounts. A crafted set of payments whose total exceeds `u64::MAX` wraps the addition to a small value, bypassing the `NotEnoughFunds` check and producing a signed transaction whose outputs are far larger than its inputs.

### Finding Description
`payment_sat` is accumulated with a plain `sum::<u64>()` and then used in an unchecked addition:

- `networks/bitcoin/src/wallet/send.rs:187` — `let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();`
- `networks/bitcoin/src/wallet/send.rs:215` — `if input_sat < (payment_sat + needed_fee)` (overflow wraps in release builds)
- `networks/bitcoin/src/wallet/send.rs:228` — `input_sat.checked_sub(payment_sat + fee_with_change)` — the inner `payment_sat + fee_with_change` also wraps before `checked_sub` sees it

The only per-payment validation is `*amount < DUST` (line 166); there is no upper bound on a payment amount or on the running total. Individual `TxOut` amounts are also unchecked — `Amount::from_sat` accepts any `u64`, and consensus serialization of `TxOut` does not enforce the 21M BTC limit, so each overflowed payment still serializes into the final transaction.

Reachability: `ReceivedOutput`s come from `Scanner::scan_transaction`/`scan_block` (networks/bitcoin/src/wallet/mod.rs:199-227) and the payments list is built from transaction data; an unprivileged party controlling the payment amount field (e.g., a burn/withdrawal amount) can supply an amount near `u64::MAX`. The multisig then signs this transaction via `TransactionSignMachine::sign` (send.rs:355-398) which commits to `Prevouts::All` of the real inputs — the signature itself is valid, but the transaction is consensus-invalid (outputs > inputs) and can never be relayed or confirmed.

### Impact Explanation
The threshold group produces a fully signed Bitcoin transaction that the network will permanently reject. Any inputs/outputs accounted against this plan are effectively burned from the protocol's perspective: the batch cannot be broadcast, the scheduler's UTXOs remain committed to an unspendable plan, and the intended payment/change bookkeeping diverges from real on-chain value — the direct analog of "reported reward/balance increasing without a check that the funds exist." Additionally `fee()` (send.rs:138-141) subtracts `sum(outputs)` from `sum(inputs)` without checking, so an overflowing transaction causes `fee()` to underflow/panic.

### Likelihood Explanation
Medium. Exploitation requires the ability to influence a payment amount to a value near `u64::MAX` sats; real input totals are bounded by the BTC supply so at least ~4e19 sats of declared payments are needed, meaning the payment amount itself is unrealistic on the Bitcoin network — but the code never validates that, and the overflow path is deterministic once reached. No panic occurs at construction in release builds (wrapping arithmetic), so the invalid transaction propagates all the way to signing.

### Recommendation
- Accumulate `payment_sat` with `checked_add`/`saturating` semantics and reject on overflow.
- Validate each payment amount against a sane bound (e.g., `<= MAX_MONEY` / 21e6 BTC in sats) in addition to the `DUST` floor.
- Compute the funds check as `input_sat.checked_sub(payment_sat).and_then(|r| r.checked_sub(needed_fee))` so overflow cannot bypass `NotEnoughFunds`.
- Guard `fee()` with `checked_sub` and return an error rather than panicking.

### Proof of Concept
```rust
// In SignableTransaction::new (release build, wrapping arithmetic):
let inputs = vec![received_output_with_value(100_000)]; // 0.001 BTC real input
let payments = &[(some_script, u64::MAX), (other_script, u64::MAX - 1000)];
// payment_sat wraps: u64::MAX + (u64::MAX - 1000) -> wraps to u64::MAX - 1001 mod 2^64
// then payment_sat + needed_fee wraps again to a small value < input_sat
// -> NotEnoughFunds check passes, tx_outs contain ~4e19 sats of outputs
// -> multisig signs a transaction the network will never accept
```
The two `TxOut`s with `Amount::from_sat(u64::MAX)` serialize fine, `SighashCache`/`Prevouts::All` commit to the real 100k-sat prevout, the Schnorr signature verifies against the sighash — yet the transaction is consensus-invalid and unbroadcastable, stranding the inputs in the plan.
