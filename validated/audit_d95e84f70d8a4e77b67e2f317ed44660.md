### Title
Withdrawal payout matching keyed only by `(withdrawal_utxo_txid, withdrawal_utxo_vout)`, not by `(idx, utxo)`, lets one Bitcoin spend satisfy two Citrea withdrawal indices - ([File: core/src/database/verifier.rs])

### Summary
`Database::get_payout_txs_for_withdrawal_utxos` matches a spent UTXO to a withdrawal solely via `bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout`, with no constraint tying the match to a unique `idx`. Because an attacker fully controls the withdrawal-UTXO bytes registered per Citrea withdrawal index, they can register the same outpoint for two distinct indices `idx1` and `idx2`, causing a single Bitcoin spend of that outpoint to be recorded as the payout for both.

### Finding Description
The binding that must hold is: **for withdrawal index `i`, exactly one Bitcoin spend of the UTXO registered at `withdrawals.idx = i` is treated as the payout for `i`, and that spend is unique to `i`**. This equality is broken because the matching query has no `idx`-scoping on the reused UTXO: [1](#0-0) 

`update_withdrawal_utxo_from_citrea_withdrawal` writes `withdrawal_utxo_txid`/`withdrawal_utxo_vout` per `idx` with no uniqueness check across other `idx` rows: [2](#0-1) 

An attacker calls Citrea's `withdraw()` twice, choosing identical withdrawal-UTXO bytes for both calls, producing two independent Citrea withdrawal indices `idx1`/`idx2` that both point at the same Bitcoin outpoint. When that outpoint is later spent once on Bitcoin, `bitcoin_syncer_spent_utxos` records a single `spending_txid` for that `(txid, vout)`. `get_payout_txs_for_withdrawal_utxos` joins on the outpoint alone, so it returns **both** `(idx1, spending_txid)` and `(idx2, spending_txid)` for the same block. Whatever caller in `Verifier::update_finalized_payouts` (per the 15 matches in `core/src/verifier.rs`, not fully retrievable in this session) forwards this result set unchanged into `update_payout_txs_and_payer_operator_xonly_pk`, which sets `payout_txid`/`payout_payer_operator_xonly_pk`/`payout_tx_blockhash` independently for each `idx` row: [3](#0-2) 

The downstream reimbursement query `get_first_unhandled_payout_by_operator_xonly_pk` selects the earliest unhandled `idx` with `payout_txid IS NOT NULL` for a given operator key and has no mechanism to detect that its `payout_txid` is shared with another already/subsequently handled `idx`: [4](#0-3) 

Since each `idx` is tied to its own `move_to_vault_txid` (deposit) via `upsert_move_to_vault_txid_from_citrea_deposit`, and reimbursement is looked up per `move_to_vault_txid`/`idx` via `get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id`, the same operator xonly pk extracted from the single spend can be used to justify reimbursement for both `idx1`'s and `idx2`'s vault UTXOs, even though only one payout was ever fronted.

None of the listed guards intercept this: `is_deposit_valid`, `is_profitable`, `SECP.verify_schnorr`, storage-proof verification, and SPV checks validate the *deposit* and *withdrawal registration* individually, but nothing in this repo enforces that a `(withdrawal_utxo_txid, withdrawal_utxo_vout)` pair is unique across `withdrawals.idx`, and the payout-matching join itself is UTXO-keyed, not `(idx, UTXO)`-keyed.

### Impact Explanation
If exploited, an operator can be credited with a payout it only fronted once but which satisfies two withdrawal indices, letting it draw reimbursement from a second move-to-vault UTXO with no matching fronted withdrawal - directly matching the Critical categories "an operator reimbursed for a payout it never funded" and "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal." The attack is repeatable across any pair (or more) of withdrawal registrations sharing a UTXO and across any operator/deposit, since the flaw is structural in the matching query, not tied to a specific deposit or operator.

### Likelihood Explanation
The attacker only needs the capabilities explicitly granted: ability to call `withdraw()` on the Citrea bridge contract and choose the withdrawal-UTXO bytes twice with the same value, then wait for/trigger a normal single spend of that outpoint (which happens as part of ordinary bridge operation). No verifier, operator, or aggregator collusion is required, and the cost is limited to the two withdrawal registrations' Citrea gas and any incidental Bitcoin fees. I was not able to fully retrieve `core/src/verifier.rs::update_finalized_payouts` in this session to check whether an additional idx-scoped safeguard exists there before the DB write, but the DB-layer query and reimbursement-selection query - which are the direct implementers of the binding under question - do not, by construction, exclude this collision.

### Recommendation
Enforce uniqueness of `(withdrawal_utxo_txid, withdrawal_utxo_vout)` across `withdrawals` rows (reject/ignore a second registration reusing an already-registered outpoint), and change `get_payout_txs_for_withdrawal_utxos`/`update_payout_txs_and_payer_operator_xonly_pk` and the reimbursement selection path to bind on `(idx, utxo, spending_txid)` so a given spend can only ever satisfy the single `idx` it was originally registered for.

        tx: Option<DatabaseTransaction<'_>>,

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
                    txid.0,
                ))
            })
            .collect()
    }

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
