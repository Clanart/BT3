### Title
Silent ERC20 `transfer`/`transferFrom` failures are treated as success by the CW20↔ERC20 wrapper contract, allowing crediting of un-transferred funds - (File: example/cosmwasm/cw20/src/contract.rs)

### Summary
The CW20-wraps-ERC20 CosmWasm contract (`example/cosmwasm/cw20/src/contract.rs`) forwards `transfer`/`transfer_from` requests to an arbitrary underlying ERC20 token (`ERC20_ADDRESS`, settable at instantiation) via an `EvmMsg::DelegateCallEvm` custom Cosmos message. Neither the contract nor the chain-level handler that executes this delegatecall inspects the ABI-encoded `bool` return value of the wrapped ERC20's `transfer`/`transferFrom` — only whether the EVM call reverted is checked. Non-standard ERC20 tokens that return `false` on failure instead of reverting therefore let `transfer_from`/`send_from` succeed at the CosmWasm layer even though no tokens moved, exactly the bug class described in the report (non-compliant `transfer`/`transferFrom` semantics not checked, enabling "success" without effect).

### Finding Description
`execute_transfer_from` → `transfer_from` in `example/cosmwasm/cw20/src/contract.rs` builds the ABI payload for `transferFrom` and wraps it in a `EvmMsg::DelegateCallEvm { to: erc_addr, data }`, then unconditionally returns a successful `Response` with `from`/`to`/`amount` attributes: [1](#0-0) . The analogous `transfer` function behaves the same way: [2](#0-1) . `execute_send_from` additionally forwards a `Cw20ReceiveMsg` to the recipient contract immediately after building this transfer message, without waiting to confirm the transfer's on-chain boolean result: [3](#0-2) .

At the chain level, the `DelegateCallEvm` custom message is routed to `MsgInternalEVMDelegateCall`, handled by `HandleInternalEVMDelegateCall`, which calls `k.CallEVM` and only propagates an error if the EVM execution itself reverted (`res.Err != nil`); the raw `res.ReturnData` (which encodes the ERC20's `bool` return value) is passed back unchecked: [4](#0-3) [5](#0-4) . Nothing in this pipeline or in the CW20 contract logic decodes and checks that returned boolean, so a non-standard ERC20 (or a deliberately malicious one) that returns `false` on `transferFrom` failure instead of reverting will cause the wrapper's CosmWasm message to be treated as a fully successful transfer.

This mirrors the reported Cooler.sol issue: the vulnerable code assumes `transfer`/`transferFrom` either succeeds or reverts, but non-compliant ERC20 tokens can return `false` silently, letting a caller obtain the effects of a successful transfer (crediting downstream receivers via `send_from`'s `Cw20ReceiveMsg`, or reporting a successful `transfer_from` in transaction attributes/events) without any real balance movement.

### Impact Explanation
Since `ERC20_ADDRESS` in this contract is attacker-controllable at instantiation time (any user can instantiate this wrapper pointing at any ERC20 contract they deploy), an attacker can deploy a non-standard ERC20 that returns `false` on `transferFrom` when the caller has insufficient balance/allowance, then call `send_from`/`transfer_from` on the wrapper. The wrapper will emit a successful response and forward a `Cw20ReceiveMsg` to a receiving contract (e.g., a DEX, lending market, or escrow) that trusts the CW20 "send" semantics, causing that receiver to credit the attacker for funds that were never actually transferred — a direct unauthorized-transfer / fund-loss vector reachable purely from a submitted CosmWasm execute message, satisfying the "unauthorized transfer via pointer" impact category.

### Likelihood Explanation
This requires an attacker to deploy their own non-standard ERC20 (something fully within their control, no privileged access needed) and instantiate the example CW20 wrapper contract pointing at it, then interact with any downstream contract that accepts CW20 `Send`/`SendFrom` hooks. This is straightforward for any unprivileged user to set up and does not require any validator or governance action, making it a realistic, self-contained attack surface reachable via ordinary wasm execute messages.

### Recommendation
After issuing the `DelegateCallEvm` for `transfer`/`transferFrom`, decode the ABI-encoded return value and treat a `false` (or empty-but-expected-bool) result as a failure, aborting the CosmWasm message (returning a `ContractError`) instead of unconditionally emitting success attributes/messages. Alternatively, have the underlying EVM call layer (`HandleInternalEVMDelegateCall`/`CallEVM`) or a shared ERC20 helper enforce standard-compliant checks (equivalent to OpenZeppelin's `SafeERC20`) so that any boolean-returning ERC20 method with a `false` result is converted into a hard failure before it reaches CosmWasm message construction.

### Proof of Concept
1. Attacker deploys a custom ERC20 contract whose `transferFrom` returns `false` (does not revert) when `amount > balanceOf(from)` or `allowance < amount`.
2. Attacker instantiates `example/cosmwasm/cw20` wrapper with `erc20_address` = the malicious ERC20.
3. Attacker (with zero balance/allowance) calls `ExecuteMsg::SendFrom { owner: victim, contract: receiver, amount: X, msg }` on the wrapper.
4. `transfer_from` (`example/cosmwasm/cw20/src/contract.rs:250-274`) builds and dispatches the `DelegateCallEvm` message; the underlying ERC20's `transferFrom` returns `false` without reverting.
5. `HandleInternalEVMDelegateCall`/`CallEVM` (`x/evm/keeper/evm.go:47-153`) sees `res.Err == nil` and returns success.
6. The wrapper's `Response` (marked successful, with `add_message(cw20receive_into_cosmos_msg(...))`) is processed; the `receiver` contract's `Receive` hook is invoked believing funds arrived, crediting the attacker despite no real ERC20 balance change.

    deps: DepsMut<EvmQueryWrapper>,
    env: Env,

    owner: String,
    contract: String,

    msg: Binary,

        .add_attribute("action", "send_from");
    Ok(res)
}

    info: MessageInfo,
    owner: String,

    deps.api.addr_validate(&recipient)?;

    let querier = EvmQuerier::new(&deps.querier);

    let res = Response::new()
        .add_attribute("from", owner)
        .add_attribute("to", recipient)
        .add_attribute("by", info.sender)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

func (k *Keeper) HandleInternalEVMDelegateCall(ctx sdk.Context, req *types.MsgInternalEVMDelegateCall) (*sdk.Result, error) {
	var to *common.Address
	if req.To != "" {
		addr := common.HexToAddress(req.To)
		to = &addr
	} else {
		return nil, errors.New("cannot use a CosmWasm contract to delegate-create an EVM contract")
	}
	addr, _, exists := k.GetAnyPointerInfo(ctx, types.PointerReverseRegistryKey(common.BytesToAddress([]byte(req.FromContract))))
	if !exists || common.BytesToAddress(addr).Cmp(*to) != 0 {
		return nil, errors.New("only pointer contract can make delegatecalls")
	}
	zeroInt := sdk.ZeroInt()
	senderAddr, err := sdk.AccAddressFromBech32(req.Sender)
	if err != nil {
		return nil, err
	}
	// delegatecall caller must be associated; otherwise any state change on EVM contract will be lost
	// after they asssociate.
	senderEvmAddr, found := k.GetEVMAddress(ctx, senderAddr)
	if !found {
		err := types.NewAssociationMissingErr(req.Sender)
		evmKeeperMetrics.associationError.Add(ctx.Context(), 1, otelmetric.WithAttributes(attribute.String("scenario", "evm_handle_internal_evm_delegate_call"), attribute.String("type", err.AddressType())))
		return nil, err
	}
	ret, err := k.CallEVM(ctx, senderEvmAddr, to, &zeroInt, req.Data)
	if err != nil {
		return nil, err
	}
	return &sdk.Result{Data: ret}, nil
}
