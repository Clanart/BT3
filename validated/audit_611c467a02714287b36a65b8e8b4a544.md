This is the key finding. `Pallet::withdraw` in `modules/pallets/relayer/src/withdrawal.rs` is the exact analog of `AccountFacet.executeWithdraw` from the seed report: it zeroes out `Fees::<T>` immediately and dispatches an ISMP `PostRequest` that must be delivered before the relayer actually receives the payout, and it does so with zero relayer incentive.

### Title
Relayer fee withdrawal request dispatched with zero relayer incentive can leave already-debited fees permanently unclaimed - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`Pallet::withdraw` (`modules/pallets/relayer/src/withdrawal.rs:81-187`) zeroes the relayer's `Fees::<T>` balance on Hyperbridge and dispatches a POST request instructing the destination chain to disburse the funds — but the request is dispatched with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` [1](#0-0) . This is confirmed by the project's own internal design note as an unresolved, live gap: "hyperbridge itself originates requests too: ... the relayer pallet's withdrawal request. Today these all dispatch with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` ... Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism." [2](#0-1) 

### Finding Description
The withdrawal flow is: `Fees::<T>::insert(dest_chain, address, U256::zero())` runs unconditionally right after the dispatch call succeeds, i.e. the balance is debited on Hyperbridge before delivery to the destination is guaranteed [3](#0-2) . The corresponding `DispatchPost` carries `fee: Default::default()` and `payer: [0u8;32]`, meaning no relayer (including any relayer other than the withdrawing party) is economically compensated for delivering the message that actually pays out the funds. Unlike ordinary user requests, which flow through `RequestPayments` and get picked up by the existing `accumulate_fees`/reward pipeline, this system-originated request has no attached fee and (per the design doc) is only reachable through the newly-added, governance-gated `OutboundRequestDeliveryReward` allowlist keyed by `module_id` — and a module is only incentivized if governance has explicitly set a non-zero reward for it [4](#0-3) . If `MODULE_ID` for `pallet-relayer`'s withdrawal path is not (yet) registered with a non-zero reward, or the reward is later zeroed, this withdrawal POST reverts to being purely altruism-dependent, exactly the scenario the seed report describes for `AccountFacet.executeWithdraw`/`cancelWithdraw`: state is already mutated (fee cleared / withdraw request pending) but the actual settlement leg has no guaranteed executor.

Because `pallet_ismp`'s `RequestCommitments` entry for this request never receives a refund path — it's not a normal user-funded request with `payer` set to a real account, so it can never time out into a refund the way `DispatchPost.fee`-bearing requests do (this dispatch also sets `timeout: 0`, i.e. it never times out at all) [5](#0-4)  — a relayer whose withdrawal message never gets delivered has no way to reclaim the debited `Fees` balance and no timeout-triggered reversion exists.

### Impact Explanation
If this outbound message is never delivered (no relayer picks it up, or the module isn't in the reward allowlist), the requesting relayer's already-earned and already-debited fee balance becomes permanently stuck: `Fees::<T>` is zero, and the pending `WithdrawalRequest`/`WithdrawalParams` POST has `timeout: 0`, so it can never time out to allow re-issuing the withdrawal. This is a direct fund-lock matching the bounty's "stealing or loss of funds" / stuck-funds category, mirroring the seed report's core invariant (execution-fee-less keeper actions block user funds).

### Likelihood Explanation
This requires no malicious actor, relayer collusion, or governance compromise — it is a straightforward consequence of the protocol's own default configuration (`OutboundRequestDeliveryReward` defaulting to zero unless a governance extrinsic explicitly registers a nonzero reward for the withdrawal path's `module_id`) combined with the fact that `withdraw()` unconditionally clears the balance before delivery is guaranteed. The project's own design document, written to describe and fix precisely this defect, confirms the vulnerable state is real and currently live in the affected system dispatch sites [2](#0-1) .

### Recommendation
- Do not zero `Fees::<T>` until the withdrawal POST is confirmed delivered (or move to a "pending withdrawal" state that is reverted if delivery never completes).
- Give the withdrawal-request dispatch a non-zero, non-optional relayer incentive at the protocol level (not solely dependent on a governance-configured allowlist entry that could be zero/unset), or add a timeout/refund path so an undelivered withdrawal automatically restores the `Fees` balance.
- Ensure `pallet-relayer`'s own `MODULE_ID` is unconditionally registered in `OutboundRequestDeliveryReward` with a non-zero value at genesis/runtime-upgrade, not left to a follow-up governance call.

### Proof of Concept
1. A relayer accumulates fees via `accumulate_fees`, building up `Fees::<T>::get(dest_chain, relayer)` > `MinWithdrawal`.
2. Relayer calls `withdraw_fees` → `Pallet::withdraw` (`modules/pallets/relayer/src/withdrawal.rs:81`). The call succeeds, dispatches the `WithdrawalRequest`/`WithdrawalParams` POST with `fee: 0`, `payer: 0x00..00`, `timeout: 0`, and immediately sets `Fees::<T>::insert(dest_chain, relayer, 0)`.
3. Because `module_id = MODULE_ID` for this dispatch site is not present (or reward = 0) in `OutboundRequestDeliveryReward`, off-chain relayers running `retain_incentivized_requests` drop this event before delivery (per the pre-delivery filter logic in `docs/outbound-request-incentivization.md`), and no self-interested party other than the requester itself is compensated to relay it.
4. Since `timeout: 0` means the request never expires, and `Fees` is already zero, the relayer has no recourse: the withdrawn amount is permanently unrecoverable unless some altruistic relayer eventually delivers it.
