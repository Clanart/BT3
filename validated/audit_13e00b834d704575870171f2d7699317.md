### Title
Reward-sniping via permissionless `WombatStaking.harvest()` dilutes long-term LP stakers' yield in `BaseRewardPool` - (File: `wombat/WombatStaking.sol`, `rewards/BaseRewardPool.sol`)

### Summary
`WombatStaking.harvest()` is callable by anyone with no cooldown or time-weighting, and `BaseRewardPool._provisionReward` distributes newly harvested WOM/bonus rewards strictly in proportion to the **current, instantaneous** `totalStaked()` snapshot. An attacker can deposit a large amount of LP into a Wombat pool via `WombatPoolHelper`/`WombatStaking.deposit`, immediately call the permissionless `harvest()` to force distribution of rewards that accrued in the underlying Wombat `MasterWombat` pool over time (before the attacker ever staked), and then withdraw, capturing a disproportionate share of yield that rightfully belongs to long-term stakers.

### Finding Description
`WombatStaking.harvest(address _lpToken)` is guarded only by `_onlyActivePool`, which checks `poolInfo.isActive` — it does **not** restrict `msg.sender`: [1](#0-0) 

This calls `_toMasterWomAndSendReward(_lpToken, 0, true)`, which measures the WOM balance delta from `MasterWombat.deposit/withdraw` (i.e. the real yield accrued in the underlying Wombat protocol since the last checkpoint) and forwards it to the pool's `BaseRewardPool` via `queueNewRewards`: [2](#0-1) 

`BaseRewardPool._provisionReward` (invoked from `queueNewRewards`) then updates `rewardPerTokenStored` using the pool's **current** `totalStaked()` — not a time-weighted average: [3](#0-2) 

`totalStaked()` and `balanceOf()` read live balances from `MasterMagpie`: [4](#0-3) 

Because reward accrual per user is `userShare * (rewardPerToken - userRewardPerTokenPaid)`, a user who stakes immediately before a `harvest()` call receives full credit for `rewardPerTokenStored` growth even though their capital was not staked while the underlying yield was accruing: [5](#0-4) 

An unprivileged wallet can therefore:
1. Deposit a large LP amount through `WombatPoolHelper.deposit()`/`depositLP()`, which stakes into `MasterMagpie` via `_stake` → `MasterMagpie.depositFor`: [6](#0-5) 
2. Immediately call the permissionless `WombatPoolHelper.harvest()` → `WombatStaking.harvest(lpToken)`: [7](#0-6) 
3. This flushes all WOM/bonus rewards that accrued in `MasterWombat` since the last harvest into `BaseRewardPool.rewardPerTokenStored`, computed against the now-inflated `totalStaked()` that includes the attacker's freshly staked amount.
4. Withdraw immediately via `WombatPoolHelper.withdraw()`, which itself triggers another harvest before unstaking: [8](#0-7) 

This is the direct structural analog of the reported `SurplusGuildMinter` bug class: reward distribution keyed off an instantaneous stake snapshot rather than time-weighted stake, permissionless triggering of the distribution event, and no minimum staking duration or same-block stake/unstake guard.

### Impact Explanation
The attacker captures a share of already-accrued WOM/bonus rewards proportional to their large, momentarily-staked balance, directly diluting the rewards owed to genuine long-term LPs of that pool — this is a direct theft of unclaimed yield from other depositors. Because `harvest()` can be repeated at will and requires no special privilege, the attack is repeatable across every active Wombat pool in `WombatStaking`, and the only real cost to the attacker is the capital needed to dominate `totalStaked()` for the duration of one transaction (or a few blocks, since `MasterWombat`'s underlying accrual and the harvest-based `queueNewRewards` calls are not time-locked or vested).

### Likelihood Explanation
`harvest()` has no access control on the caller, and `deposit()`/`withdraw()` are freely callable by any wallet holding the underlying LP token or deposit token. No cooldown, minimum stake duration, or same-block stake/unstake protection exists in `MasterMagpie`, `BaseRewardPool`, or `WombatStaking`. The only requirement is capital to temporarily dominate the pool's `totalStaked()`, which is economically feasible for many pools, especially right after a period of pending, un-harvested WOM emissions accumulates in `MasterWombat`.

### Recommendation
- Time-weight reward accrual (e.g., track `rewardPerTokenStored` growth against a duration-weighted stake, or accrue rewards continuously per-second like a standard `Synthetix StakingRewards` rather than lump-summing on harvest against instantaneous `totalStaked()`).
- Disallow deposit and withdraw (or deposit and harvest-claim) within the same block/transaction for the same account.
- Introduce a minimum warm-up period before newly staked balances become eligible for freshly queued rewards, similar to mitigations discussed in the original Ethereum Credit Guild report.
- Alternatively, restrict who may trigger `harvest()` (e.g., only pool helpers or authorized keepers) and rate-limit/queue harvested rewards to vest over time rather than being instantly reflected in `rewardPerTokenStored`.

### Proof of Concept
1. Let pool `P` have long-standing stakers A, B, C with WOM rewards accruing in `MasterWombat` since the last `harvest()` call (e.g. several days of emissions pending, unflushed into `BaseRewardPool`).
2. Attacker calls `WombatPoolHelper.deposit(largeAmount, minLiquidity)` for pool `P`, which stakes `largeAmount` into `MasterMagpie` via `depositFor` (`wombat/WombatPoolHelper.sol:148-165`).
3. Attacker immediately calls `WombatPoolHelper.harvest()` (`wombat/WombatPoolHelper.sol:142-144`), which invokes `WombatStaking.harvest(lpToken)` (`wombat/WombatStaking.sol:329-335`) with no caller restriction, forcing `_toMasterWomAndSendReward` to withdraw the multi-day pending WOM balance delta from `MasterWombat` and call `queueNewRewards` on `BaseRewardPool`.
4. `BaseRewardPool._provisionReward` computes `rewardPerTokenStored += (harvestedAmount * scale) / totalStaked()`, where `totalStaked()` now includes the attacker's large freshly staked balance (`rewards/BaseRewardPool.sol:297-318`).
5. Attacker's `earned()` for the reward token is now large despite having staked for zero elapsed time, while A/B/C's owed share (which should have been undiluted, based on their true long-term proportional stake) is reduced.
6. Attacker withdraws via `WombatPoolHelper.withdraw()` (triggering another harvest and unstake) and later calls `MasterMagpie`/`BaseRewardPool.getReward` to realize the sniped rewards.

        Pool storage poolInfo = pools[_lpToken];

        address[] memory bonusTokens = assetToBonusRewards[_lpToken];
        uint256 bonusTokensLength = bonusTokens.length;

        uint256 womBeforeBalance = IERC20(wom).balanceOf(address(this));
        uint256[] memory beforeBalances = _rewardBeforeBalances(_lpToken);

        if(_isStake)
            _stakeToWombatMaster(_lpToken, lpAmount); // triggers harvest from wombat exchange

            IMasterWombat(masterWombat).withdraw(poolInfo.pid, lpAmount); // triggers harvest from wombat exchange
        uint256 womRewards = IERC20(wom).balanceOf(address(this)) - womBeforeBalance;
        _sendRewards(_lpToken, wom, poolInfo.rewarder, womRewards);

        for (uint256 i; i < bonusTokensLength; i++) {

                _sendRewards(_lpToken, bonusTokens[i], poolInfo.rewarder, bonusBalanceDiff);
            }
        }

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
