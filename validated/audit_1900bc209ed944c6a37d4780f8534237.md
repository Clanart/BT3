### Title
`ConvertERC20`/`ConvertCoin` silently delete a native-ERC20 `TokenPair` on code-hash loss without verifying escrowed exposure is zero, permanently freezing backed coin/token balances - (File: `x/erc20/keeper/msg_server.go`)

### Summary
The reported Alchemix bug is a case of an admin/automatic function switching the "backing" contract for user positions (`setAlchemist`) without first verifying that outstanding exposure to the old backing contract is zero, freezing user funds. The same invariant-break exists in `x/erc20`'s `ConvertERC20` and `ConvertCoin` handlers: when the native ERC20 contract behind a `TokenPair` loses its code hash, the keeper immediately calls `k.DeleteTokenPair` and returns success, with zero check that minted native coins are still backed by escrowed ERC20 tokens (or vice versa).

### Finding Description
For a native-ERC20-owned `TokenPair` (`types.OWNER_EXTERNAL`), the accounting model is:
- `ConvertERC20` (ERC20→Coin): escrows the user's ERC20 tokens on the module address and mints native coin 1:1 [1](#0-0) .
- `ConvertCoin` (Coin→ERC20): burns the escrowed native coin and releases the previously escrowed ERC20 tokens from the module address back to the receiver [2](#0-1) .

Both entrypoints, before doing any conversion work, check whether the underlying ERC20 contract still has code:

```go
acc := k.evmKeeper.GetAccountWithoutBalance(ctx, pair.GetERC20Contract())
if acc == nil || !acc.HasCodeHash() {
    k.DeleteTokenPair(ctx, pair)
    ...
    return nil, nil
}
``` [3](#0-2) [4](#0-3) 

If the code hash is empty (contract removed/self-destructed), the keeper calls `DeleteTokenPair`, which unconditionally wipes the pair, denom map, ERC20 map, and allowances: [5](#0-4) 

No check is performed on:
- whether native coin supply for `pair.Denom` is still non-zero (i.e., other users still hold minted coins backed by ERC20 tokens escrowed in the module account), or
- whether ERC20 tokens are still escrowed at the module address (i.e., users hold native coins that are supposed to be redeemable for tokens).

This is exactly the class of bug in the referenced report: switching/removing a backing representation ("Alchemist") for one caller's transaction without checking whether *other* exposure (other users' escrowed positions) to the removed backing still exists, before the mapping is destroyed.

Once the pair is deleted:
- Holders of the native coin denom that was minted via prior `ConvertERC20` calls can no longer call `ConvertCoin` to redeem it for the ERC20 token, because `MintingEnabled` (used by `ConvertCoin`) resolves the pair via `GetTokenPairID`/`GetDenomMap`, which now returns nothing — the pair is gone.
- The ERC20 tokens that were escrowed at the module account inside the (now codeless) contract are unreachable, since no code exists to call `transfer` on.
- The result is a permanent mismatch: native coin balances exist in `x/bank` with no way to redeem the value they represent, i.e., a frozen/orphaned balance.

### Impact Explanation
This causes permanent freezing of user-spendable value: native coin balances backed by escrowed ERC20 tokens become permanently non-redeemable once the pair is auto-deleted, and the escrowed ERC20 tokens become permanently unreachable. This matches the "Critical permanent freezing... of user funds... or token-pair-backed balances" allowed impact for this program, since it breaks the 1:1 accounting invariant between native coin, ERC20 view, and escrow that `x/erc20` is required to preserve.

### Likelihood Explanation
Any single unprivileged transaction (a call to `ConvertERC20` or `ConvertCoin` against a pair whose underlying contract has lost its code hash) triggers the silent deletion path — there's no privilege check, and no requirement that the caller be the one who caused the code loss. Any external ERC20 contract registered via the permissionless `RegisterERC20` flow can reach a codeless state (e.g., legitimate self-destruct semantics or other code-removal paths supported by the EVM module), after which the very next conversion call by *any* user against that pair destroys the mapping for everyone who still holds exposure, without any exposure check.

### Recommendation
Before calling `k.DeleteTokenPair` in the code-hash-loss branches of `ConvertERC20` and `ConvertCoin`, require that all outstanding exposure is zero, mirroring the audit's suggested Alchemist fix:
- verify `bankKeeper.GetSupply(ctx, pair.Denom)` (or an equivalent tracked "outstanding minted amount") is zero, and
- verify the ERC20 balance escrowed at `types.ModuleAddress` for `pair.GetERC20Contract()` is zero (or accept the call may not be able to check due to the contract already lacking code, in which case pair deletion should require a separate governance-gated cleanup path rather than an automatic, permissionless call).

If exposure is non-zero, the handler should return an error (e.g., `types.ErrBalanceInvariance`) rather than silently deleting the pair, so that stuck balances are flagged for a proper (e.g., governance-driven) remediation instead of being permanently orphaned.

### Proof of Concept
1. Attacker deploys and registers (permissionlessly via `MsgRegisterERC20`) a malicious ERC20 contract that supports self-destruct, creating a `TokenPair` with `OWNER_EXTERNAL` [6](#0-5) .
2. Victim user calls `ConvertERC20` to convert some of the ERC20 token into the paired native coin: tokens are escrowed at `types.ModuleAddress`, native coin is minted to the victim [7](#0-6) .
3. Attacker self-destructs the ERC20 contract (removing its code hash) after the escrow has been established.
4. Any user (attacker or otherwise) calls `ConvertERC20` or `ConvertCoin` again for that pair; the keeper detects `!acc.HasCodeHash()` and calls `DeleteTokenPair`, wiping the mapping [3](#0-2) .
5. The victim's minted native coin balance from step 2 can no longer be converted back (`MintingEnabled` fails to resolve the deleted pair), and the ERC20 tokens escrowed in step 2 remain permanently locked in the codeless contract at `types.ModuleAddress` — user value is permanently frozen with no recovery path in the module's code.

func (k Keeper) convertERC20IntoCoinsForNativeToken(
	ctx sdk.Context,
	pair types.TokenPair,
	msg *types.MsgConvertERC20,
	receiver sdk.AccAddress,
	sender common.Address,
) (*types.MsgConvertERC20Response, error) {
	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()
	balanceCoin := k.bankKeeper.GetBalance(ctx, receiver, pair.Denom)
	balanceToken := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)
	if balanceToken == nil {
		return nil, sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow tokens on module account
	transferData, err := erc20.Pack("transfer", types.ModuleAddress, msg.Amount.BigInt())
	if err != nil {
		return nil, err
	}

	res, err := k.evmKeeper.CallEVMWithData(ctx, sender, &contract, transferData, true, nil)
	if err != nil {
		return nil, err
	}

	// Check evm call response
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return nil, err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return nil, err
		}
		if !unpackedRet.Value {
			return nil, sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute transfer")
		}
	}

	// Check expected escrow balance after transfer execution
	// NOTE: coin fields already validated in the ValidateBasic() of the message
	coins := sdk.Coins{sdk.Coin{Denom: pair.Denom, Amount: msg.Amount}}
	tokens := coins[0].Amount.BigInt()
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)
	if balanceTokenAfter == nil {
		return nil, sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	expToken := big.NewInt(0).Add(balanceToken, tokens)

	if r := balanceTokenAfter.Cmp(expToken); r != 0 {
		return nil, sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v",
			expToken, balanceTokenAfter,
		)
	}

	// Mint coins
	if err := k.bankKeeper.MintCoins(ctx, types.ModuleName, coins); err != nil {
		return nil, err
	}

	// Send minted coins to the receiver
	if err := k.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, receiver, coins); err != nil {
		return nil, err
	}

// DeleteTokenPair removes a token pair.
func (k Keeper) DeleteTokenPair(ctx sdk.Context, tokenPair types.TokenPair) {
	id := tokenPair.GetID()
	k.deleteTokenPair(ctx, id)
	k.deleteERC20Map(ctx, tokenPair.GetERC20Contract())
	k.deleteDenomMap(ctx, tokenPair.Denom)
	k.deleteAllowances(ctx, tokenPair.GetERC20Contract())
}

// RegisterERC20 creates a Cosmos coin and registers the token pair between the
// coin and the ERC20
func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
