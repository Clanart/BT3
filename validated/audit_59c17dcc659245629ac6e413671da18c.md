### Title
SignableTransaction fee/weight calculation omits the OP_RETURN data output, causing transactions with data to systematically underpay fees and fail relay - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes `needed_fee` and `weight` using `calculate_weight_vbytes`, which builds the template transaction's output vector only from `payments` (plus optional change). The OP_RETURN output carrying `data` is pushed onto `tx_outs` *before* the weight calculation but is never passed into it. The result is analogous to the L1ECOBridge "zero gas" bug: a code path (any transaction carrying data) is constructed with an insufficient resource parameter, so the produced transaction systematically underpays its fee and can fall below the node's minimum relay fee, leaving funds stuck.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:194-202` the OP_RETURN output is appended to `tx_outs`:

```rust
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}
```

But at `send.rs:204` the size estimate uses `payments` only:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

Inside `calculate_weight_vbytes` (`send.rs:85-93`), `tx.output` is built exclusively from `payments`, so the OP_RETURN output — up to ~90 vbytes (8-byte value + `OP_RETURN` + push of up to 80 bytes) — is excluded. The same omission occurs in the change branch at `send.rs:225-226`. Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) is underestimated by `fee_per_vbyte * ~90`.
2. The change amount computed at line 228 uses `fee_with_change` derived from the same undersized estimate, so change is slightly overpaid — but the *actual* fee (`sum(inputs) - sum(outputs)`, line 138-141) is still exactly `needed_fee`, which no longer corresponds to the requested fee rate once the real (larger) transaction is broadcast.
3. The `TooLowFee` guard at line 211 and the `TooLargeTransaction` guard at line 241 are both evaluated against the underestimated `vbytes`/`weight`, so a transaction with data can pass the minimum-relay-fee check while its true fee rate is below the relay minimum, or exceed `MAX_STANDARD_TX_WEIGHT` undetected.

### Impact Explanation
Any Bitcoin transaction constructed via `SignableTransaction::new` with `data: Some(_)` (the mechanism used for in-instructions/OP_RETURN metadata) pays a fee rate strictly lower than `fee_per_vbyte` requested — potentially below `DEFAULT_MIN_RELAY_TX_FEE`. Like the audit issue where `sendCrossDomainMessage(l2TokenBridge, 0, message)` guarantees the refund path reverts, this guarantees data-bearing transactions are produced with an insufficient parameter. Such a transaction will be rejected or stuck in mempools, and since the UTXOs are consumed by this exact sighash-committed transaction shape, the spend must be reconstructed — the intended operation silently fails. The weight undercount additionally means a maximally-sized transaction can exceed `MAX_STANDARD_TX_WEIGHT` without triggering `TooLargeTransaction`.

### Likelihood Explanation
Deterministic whenever `data` is specified: the underestimation is a fixed ~10–90+ vbytes. Whether the resulting transaction actually falls below relay minimum depends on how close `fee_per_vbyte` is to the floor; at minimum acceptable fee rates it always does. Reaching the path requires only that a caller supplies OP_RETURN data, a supported public input of the API.

### Recommendation
Include the data output in the size estimate. Either pass the already-built `tx_outs` (or an output count/size including the OP_RETURN script) into `calculate_weight_vbytes`, or add the data output's serialized size to `weight`/`vbytes` after the call:

```diff
- let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
+ // account for the OP_RETURN output already pushed to tx_outs
+ let (mut weight, vbytes) =
+   Self::calculate_weight_vbytes(tx_ins.len(), payments, data_script.as_ref(), None);
```

i.e., extend `calculate_weight_vbytes` to accept the optional OP_RETURN `ScriptBuf` (and include it in the change-variant call at line 225-226) so `needed_fee`, the `TooLowFee` check, and the `TooLargeTransaction` check all reflect the true transaction size.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs logic trace:
let payments = vec![(some_addr, 1000)];
let data = Some(vec![0u8; 80]); // max allowed
// calculate_weight_vbytes is called with `payments` only -> vbytes excludes
// the ~91-byte OP_RETURN output (8 value + 1+1 push opcode + 80 payload + script len)
let tx = SignableTransaction::new(inputs, &payments, None, data, fee_per_vbyte).unwrap();
// tx.fee() == fee_per_vbyte * vbytes_without_opreturn
// actual vsize is ~91 bytes larger, so effective rate < fee_per_vbyte,
// and potentially < DEFAULT_MIN_RELAY_TX_FEE -> non-relayable transaction
```
