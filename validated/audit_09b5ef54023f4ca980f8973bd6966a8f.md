### Title
Disabled overfill clamp lets the Simplex filler execute unbounded-loss fills despite a computed safety ceiling - (File: `sdk/packages/simplex/src/strategies/fx.ts`)

### Summary
This is the local analog of the jDola `maxDeposit()` bug: a limit is *computed* correctly but never *enforced*, so callers (here, the fill-execution path) rely on a safety bound that silently does nothing. In `HyperFXStrategy.calculateProfitability`, the code computes an `overfillCeiling = (output.amount * (10000n + maxOverfillBps)) / 10000n` and compares `rawPolicyMaxOutput` against it, but instead of clamping the output to the ceiling it assigns `policyMaxOutput = rawPolicyMaxOutput` unconditionally and only logs a warning [1](#0-0) .

### Finding Description
The documented safety mechanism for the intent-fill flow states: "the filler clamps its computed output to at most `(1 + maxOverfillBps) × user-requested amount`" and that after `maxConsecutiveClamps` consecutive clamp activations the HyperFX strategy halts itself as a signal of a systemic pricing error [2](#0-1) .

The implementation, however, computes the ceiling and detects breaches but never applies the clamp — the comment explicitly documents the removal: "Overfill detection is warn-only: the clamp is DISABLED, so the filler fills the full computed amount even when it exceeds (1 + maxOverfillBps) × user-requested ... This removes the per-leg loss bound that previously protected against a bug / stale cache / manipulated venue price. Output is no longer capped; we only emit a warning." [1](#0-0) 

`policyMaxOutput` (unclamped) then flows directly into `finalOutputAmount`, which becomes the amount transferred to the counterparty/solver payout on `fillOrder` execution [3](#0-2) . Since the clamp never fires, the `maxConsecutiveClamps` self-halt circuit breaker described in the docs also can never trigger (it is keyed on clamp activation), so the one remaining automated defense against a stale-price or manipulated-venue bug is dead as well.

### Impact Explanation
Any error in `resolveLegRates`/venue pricing (stale cache, manipulated Uniswap V4 pool quote, misconfigured curve) now translates directly into unbounded overpayment on every fill that uses that leg — there is no per-order ceiling and no automatic halt to stop repeated bad fills. This is a direct "loss of funds" / "logic attack" path against the filler's treasury during legitimate order settlement, exactly analogous to how jDola's `maxDeposit()` failing to reflect real limits breaks the guarantee integrators depend on — here the guarantee that "output is capped at 105% of user request" is broken at the exact point that should enforce it.

### Likelihood Explanation
This triggers on the normal `calculateProfitability` → `fillOrder` execution path for every order priced via `HyperFXStrategy`, with no privileged actor, malicious relayer, or governance action required — any latent pricing bug or a manipulated Uniswap V4 quote used by `resolveLegRates` is sufficient to realize it, and the code path is unconditionally reached (the `if (rawPolicyMaxOutput > overfillCeiling)` branch only logs, it never returns or reduces the value) [4](#0-3) .

### Recommendation
Restore enforcement: when `rawPolicyMaxOutput > overfillCeiling`, set `policyMaxOutput = overfillCeiling` (or reject the leg) instead of only logging, and re-wire the `maxConsecutiveClamps` halt counter to increment on actual clamp activation so the systemic-error circuit breaker functions as documented.

### Proof of Concept
1. Configure a pair priced from a venue (e.g. Uniswap V4) and let its on-chain quote/cache become stale or manipulated so `resolveLegRates` returns a rate far better than fair value.
2. Submit an order; `computeLegPolicyOutput` yields a `rawPolicyMaxOutput` far above `output.amount * (1+maxOverfillBps)`.
3. Observe: the code logs `"Overfill ceiling exceeded — clamp disabled, filling unclamped amount"` but proceeds to set `finalOutputAmount` to the full unclamped value and fills the order, transferring far more value than the configured 5% ceiling permits, with no halt triggered regardless of how many times this repeats [5](#0-4) .

### Overfill Protection

Bounds per-leg loss if the filler's internal pricing is wrong (bug, stale cache, manipulated venue). For every order, the filler clamps its computed output to at most `(1 + maxOverfillBps) × user-requested amount` — this ceiling applies to every strategy. After `maxConsecutiveClamps` consecutive orders where the clamp activated, the **HyperFX** strategy halts itself — a pattern that strongly suggests a systemic pricing error — and requires an operator restart. HyperFX additionally rejects any order where the total output USD value ≥ total input USD value.

Defaults are sensible (`maxOverfillBps = 500` ≈ 5% ceiling, `maxConsecutiveClamps = 3`). Override under `[simplex.overfillProtection]`:

```toml lineNumbers
[simplex.overfillProtection]
maxOverfillBps       = 500   # 5% ceiling above user-requested output
maxConsecutiveClamps = 3     # halt threshold (HyperFX)
```
