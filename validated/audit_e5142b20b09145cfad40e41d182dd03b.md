## Title
Governance-controllable zero `GasTarget` causes divide-by-zero panic in KIP-71 base-fee calculation - (File: `params/kip71_config.go`)

### Summary
The FastNetMon CVE is a classic "attacker-controlled zero divisor causes crash" bug class. The analogous reachable path in this codebase is the KIP-71 (Magma) base-fee formula, `KIP71Config.NextMagmaBlockBaseFee`, which divides by the `GasTarget` governance parameter without checking it for zero. Unlike the sibling parameter `Kip71BaseFeeDenominator`, which has an explicit `FormatChecker` rejecting zero, `Kip71GasTarget` uses `noopFormatChecker`, i.e., no validation at all. [1](#0-0) 

### Finding Description
`NextMagmaBlockBaseFee` computes the next block's base fee using `gasTarget := kc.GasTarget` as a divisor in both the "gas used above target" and "gas used below target" branches: [2](#0-1) 

If `gasTarget == 0`, and the parent block used any gas at all (`parentGasUsed != 0`), the code takes the `parentGasUsed > gasTarget` branch (since any positive value is greater than 0) and executes:
```go
y := x.Div(x, new(big.Int).SetUint64(gasTarget))  // division by 0
```
`big.Int.Div` with a zero divisor panics ("division by zero"), crashing the node process — the same denial-of-service bug class as the CVE (zero-length/zero-value input leading to a divide-by-zero crash), just triggered via a governance-set numeric parameter instead of a network packet field.

Critically, while `Kip71BaseFeeDenominator`'s `FormatChecker` explicitly rejects `0`:
```go
FormatChecker: func(cv any) bool {
    v, ok := cv.(uint64)
    return ok && v != 0
},
```
the `Kip71GasTarget` entry uses `noopFormatChecker`, meaning any `uint64` value, including `0`, passes format validation and can be voted into the chain config. [3](#0-2) 

Note that `BaseFeeDenominator == 0` is defensively handled in `NextMagmaBlockBaseFee` (falls back to 64), but there is no equivalent guard for `GasTarget == 0`. [4](#0-3) 

### Impact Explanation
Once a `Kip71GasTarget = 0` governance parameter is active on-chain (via a governance vote reflected in `ParamSet`), every node — including full/public-RPC nodes — computing the next base fee will panic and crash. This function is invoked:
- During header validation of every new block (`VerifyMagmaHeader` → `NextMagmaBlockBaseFee`), i.e., in the hot consensus/block-processing path reached by any submitted or relayed block/transaction.
- In the public JSON-RPC `eth_feeHistory`/gas price oracle path (`node/cn/gasprice/feehistory.go`), which any public RPC caller can invoke to compute `nextBaseFee`. [5](#0-4) 

This results in a chain-wide denial of service: all honest nodes evaluating the affected block or serving the affected RPC call crash simultaneously, which is a supply/availability-impacting, network-wide failure — consistent with the "state divergence / invalid state acceptance / DoS" impact classes in scope.

### Likelihood Explanation
Reaching this bug requires `GasTarget` to be set to `0` via the governance parameter update mechanism. This is not a bug reachable by an arbitrary unprivileged transaction sender directly, but it is reachable through the in-scope "governance parameters" surface named in the validation rules, and the root cause is a straightforward missing-validation defect (no divisor guard, and format checker doesn't reject zero) rather than a hypothetical. Given the explicit contrast with `Kip71BaseFeeDenominator`'s zero-check, this looks like an overlooked validation gap rather than an intentional design choice.

I was unable to fully verify, within the available tool budget, whether there is an additional layer of validation performed elsewhere in the governance vote-acceptance pipeline (e.g., in `kaiax/gov/headergov` vote application, or in a smart-contract-based governance path) that might reject a zero `GasTarget` before it reaches `ParamSet`/`ChainConfig`. My searches for vote-validity/format-checking call sites in `kaiax/gov/headergov` did not surface such a check, but a full audit of the vote-application code path could not be completed in the remaining iterations.

### Recommendation
- Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0`, mirroring `Kip71BaseFeeDenominator`.
- Defensively guard `params/kip71_config.go`'s `NextMagmaBlockBaseFee` against `kc.GasTarget == 0` (e.g., fallback to `DefaultGasTarget` or return early), similar to the existing `BaseFeeDenominator == 0` fallback.

### Proof of Concept
1. Via governance, set `governance.kip71.gastarget = 0` (currently accepted because `Kip71GasTarget`'s format checker is a no-op).
2. Once this parameter takes effect for a subsequent block, produce/observe a block where `parentHeaderGasUsed > 0`.
3. `NextMagmaBlockBaseFee` takes the `parentGasUsed > gasTarget` branch and executes `x.Div(x, new(big.Int).SetUint64(0))`, causing a Go panic ("division by zero") in every node validating that header or serving `eth_feeHistory` for that block, crashing affected nodes network-wide.
