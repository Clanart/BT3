### Title
Missing `chain_id` in EIP-712 Domain Enables Cross-Chain Replay of Aggregator Verification Signatures - (`File: core/src/rpc/ecdsa_verification_sig.rs`)

### Summary

The `CLEMENTINE_EIP712_DOMAIN` used to authenticate `OptimisticPayoutMessage` and `OperatorWithdrawalMessage` ECDSA verification signatures is constructed without a `chain_id` or `verifying_contract` field. This is a direct analog to the external report's missing `block.chainid` / `address(this)` in the oracle schema. A valid aggregator signature produced for a testnet deployment can be replayed verbatim on a mainnet deployment (or any other network) when the same aggregator key is used across networks, bypassing the authorization gate that is supposed to restrict who can trigger optimistic payouts and operator withdrawals.

---

### Finding Description

`CLEMENTINE_EIP712_DOMAIN` is defined as:

```rust
// core/src/rpc/ecdsa_verification_sig.rs L42-45
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
```

EIP-712 explicitly provides `chainId` and `verifyingContract` fields in the domain separator precisely to prevent cross-chain and cross-contract replay. Both are absent here. The domain separator hash is therefore identical on every EVM-compatible network, so any signature over an `OptimisticPayoutMessage` or `OperatorWithdrawalMessage` is valid on all networks simultaneously.

The message structs themselves also contain no nonce or expiry:

```rust
// core/src/rpc/ecdsa_verification_sig.rs L22-39
struct OptimisticPayoutMessage {
    uint32 withdrawal_id;
    bytes  input_signature;
    bytes32 input_outpoint_txid;
    uint32 input_outpoint_vout;
    bytes  output_script_pubkey;
    uint64 output_amount;
}
```

The signature is verified in `Verifier::sign_optimistic_payout` and `operator::withdraw`:

```rust
// core/src/verifier.rs L1602-1622
if let Some(address_in_config) = self.config.aggregator_verification_address {
    if let Some(verification_signature) = verification_signature {
        let address_from_sig =
            recover_address_from_ecdsa_signature::<OptimisticPayoutMessage>(
                deposit_id, input_signature, input_outpoint,
                output_script_pubkey.clone(), output_amount,
                verification_signature,
            )?;
        if address_from_sig != address_in_config {
            return Err(BridgeError::InvalidECDSAVerificationSignature);
        }
    } else {
        return Err(BridgeError::ECDSAVerificationSignatureMissing);
    }
}
```

The check is also **entirely optional**: if `aggregator_verification_address` is `None` in config, the block is skipped and no signature is required at all.

---

### Impact Explanation

If the same aggregator key is used on testnet and mainnet (a common operational pattern during staged rollouts), an attacker who observes a valid `OptimisticPayoutMessage` signature on testnet can replay it on mainnet. The verifier's only additional guards are:

1. `is_utxo_spent(&input_outpoint)` — the mainnet UTXO must not yet be spent.
2. `withdrawal_utxo != input_outpoint` — the mainnet DB must store the same `input_outpoint` for the same `deposit_id`.

Condition 2 is satisfiable when the same Bitcoin UTXO is confirmed on both testnet4 and mainnet (Bitcoin testnet4 and mainnet share the same transaction format; a transaction valid on one is structurally valid on the other). If both conditions are met, every verifier will produce a valid MuSig2 partial signature over the mainnet optimistic payout transaction, and the aggregator will broadcast a payout of the full bridge amount (~10 BTC) to the attacker-controlled `output_script_pubkey` that was in the replayed message.

The same replay path applies to `OperatorWithdrawalMessage` via `operator::withdraw`, which would cause the operator to sign and broadcast a payout transaction it never independently authorized for mainnet.

---

### Likelihood Explanation

- The aggregator key is a single off-chain ECDSA key managed by the Citrea team; reuse across testnet and mainnet is a realistic operational assumption.
- Testnet4 Bitcoin UTXOs can be replicated on mainnet by broadcasting the same raw transaction.
- The attacker only needs to monitor the testnet gRPC traffic (or the signed messages) to capture a valid signature, then submit it to the mainnet aggregator RPC.
- The `aggregator_verification_address` field defaults to `Some(...)` in `BridgeConfig::default()`, so the check is active in default deployments, making the signature the sole authorization gate for optimistic payouts.

---

### Recommendation

Add `chain_id` (and optionally `verifying_contract`) to the EIP-712 domain:

```rust
pub fn clementine_eip712_domain(chain_id: u64) -> Eip712Domain {
    alloy_sol_types::eip712_domain! {
        name: "ClementineVerification",
        version: "1",
        chain_id: chain_id,
    }
}
```

Pass `citrea_chain_id` from `BridgeConfig` when constructing the domain at signature creation and verification time. This ensures a signature produced for chain ID 5655 (Citrea testnet) cannot be accepted by a verifier running on a different chain ID.

Optionally, add a per-withdrawal nonce or expiry timestamp to the message struct to prevent any future same-chain replay if the UTXO-spent guard is ever relaxed.

---

### Proof of Concept

1. Deploy the bridge on testnet (chain ID T) and mainnet (chain ID M) with the same aggregator key `K`.
2. On testnet, initiate a legitimate optimistic payout for `deposit_id=D`, `input_outpoint=O`, `output_script_pubkey=ATTACKER_ADDR`, `output_amount=A`. The aggregator signs `OptimisticPayoutMessage` with key `K`, producing signature `σ`.
3. Broadcast the same Bitcoin transaction that created UTXO `O` on mainnet so that `O` is confirmed on mainnet and deposit `D` on mainnet also references `O` as its withdrawal UTXO.
4. Call the mainnet aggregator's `optimistic_payout` RPC with the same parameters and `verification_signature = σ`.
5. Each mainnet verifier calls `recover_address_from_ecdsa_signature::<OptimisticPayoutMessage>(...)` using `CLEMENTINE_EIP712_DOMAIN` (identical on both chains), recovers address `K`, matches `aggregator_verification_address`, and issues a partial MuSig2 signature.
6. The aggregator aggregates the partial signatures and broadcasts the mainnet optimistic payout transaction, sending `A` satoshis to `ATTACKER_ADDR`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
