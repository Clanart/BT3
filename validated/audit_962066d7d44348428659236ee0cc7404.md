### Title
Missing Timestamp Freshness Check in App Proxy Signature Verification Allows Indefinite Replay of Signed Requests - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` only validates that the HMAC signature over the query parameters matches the app secret; it never checks that the `timestamp` parameter included in those same parameters is recent. This mirrors the reported bug class: a time-bounded artifact (the commitment / here, the signed proxy request) is meant to be usable only within a limited window, but the verification code applies no restriction based on elapsed time, so the artifact remains fully accepted indefinitely.

### Finding Description
`query_string_valid?` extracts the `signature` parameter and recomputes the HMAC over the remaining sorted parameters (which include `shop`, `path_prefix`, and `timestamp`), then does a constant-time comparison: [1](#0-0) 

The signature calculation itself: [2](#0-1) 

Nowhere in `verify_proxy_request` or `query_string_valid?` is the `timestamp` value compared to the current time: [3](#0-2) 

Because the signature is a deterministic function of the query parameters (including `timestamp`) and the shared secret, any request URL that was once validly signed (e.g., a proxied storefront link, a link shared/cached/logged, or a URL captured via browser history, referer headers, or a proxy/CDN log) remains permanently "valid" from the module's perspective — there is no restriction analogous to `commitmentHalfLife` that would cause the verification to reject a stale, otherwise-correctly-signed request.

### Impact Explanation
Any controller that relies solely on `ShopifyApp::AppProxyVerification` for authorization of app-proxy actions (as documented and scaffolded by the gem's own generator) will accept a previously issued proxy request at any point in the future, since the concern's only job is deciding whether to allow the request through: [4](#0-3) 

If an old app-proxy URL is disclosed (via logs, browser history, shared links, or referer leakage) and the target action is not idempotent (e.g., triggers a purchase-adjacent action, redemption, or state change scoped to a shop/customer), the request can be replayed by an unrelated party indefinitely, since expiry is never enforced by this concern.

### Likelihood Explanation
Exploitation requires only that an attacker obtain one previously-issued, validly signed app-proxy URL — the same low bar as a URL leak via browser history/referrer/logs. No secret, private key, or privileged access is required; the vulnerability is purely a missing time-window check in unprivileged signature verification code, and the gem does not fill this gap in the documented/generated usage. The library's own test suite reinforces that only signature correctness is exercised, not recency: [5](#0-4) 

### Recommendation
Add an explicit timestamp freshness check in `query_string_valid?` (or `verify_proxy_request`), rejecting requests whose `timestamp` parameter is older than a configurable tolerance (e.g., a few minutes), in addition to the existing signature check, and document this requirement for apps relying on `ShopifyApp::AppProxyVerification` for non-idempotent actions.

### Proof of Concept
1. A merchant's storefront generates (or a user is sent) a Shopify app-proxy request such as:
   `GET /apps/my-app/action?shop=some-store.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=<valid_hmac>`
2. This URL is captured (browser history, shared link, proxy/CDN access log, referer header leakage, etc.).
3. Days/weeks later, an unrelated party replays the exact same URL against the app.
4. `verify_proxy_request` calls `query_string_valid?`, which recomputes the HMAC over the same parameters (including the stale `timestamp`) and finds it matches — the request is accepted with no check that `timestamp` is far in the past: [6](#0-5) 
5. If the underlying action performs a state change (e.g., applying a discount, submitting a review, redeeming a one-time action) without its own idempotency/expiry guard, it executes again on replay.

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
