### Title
OP_RETURN `data` output omitted from fee/weight calculation, causing underpaid fees and oversized change — (`networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` appends an OP_RETURN output carrying up to 80 bytes of caller-controlled `data` to `tx_outs`, but computes the transaction weight, vbytes, `needed_fee`, and change amount using `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which only sees the `payments` list — never the data output. The analog of the "excess ether locked" bug is inverted but shares the same root: the accounting of funds-in vs. funds-out is wrong because one output isn't counted. Here the excess is *over*-returned to change and the actual fee paid is lower than `needed_fee()` reports, potentially below the network's minimum relay fee for the transaction's true vsize.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed to `tx_outs` first:

`send.rs` lines 194–202:
```rust
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...)
  })
}
```

But the fee is derived from a weight estimate built only from `payments`:

`send.rs` line 204:
```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` (lines 62–127) builds its template `Transaction` with `output:` populated solely from `payments` — the OP_RETURN output (~11–92 bytes of real transaction weight, ~90–100 weight units) is never included. The same omission occurs in the change path at lines 225–227, where `fee_with_change` is computed from `payments` plus `change`, still excluding the data output. The change amount is then `input_sat.checked_sub(payment_sat + fee_with_change)` (line 228), so every sat that should have paid for the data output's weight is instead redirected into the change output.

Consequences:
1. `needed_fee()` and `fee()` return a fee computed for a smaller vsize than the actual transaction. The effective feerate is `needed_fee / actual_vsize < fee_per_vbyte`.
2. The `TooLowFee` check at lines 211–213 validates `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the understated `vbytes`, so a transaction can pass the check while its real feerate is below the relay minimum — making the transaction unbroadcastable, and all its outputs (including change) never materialize.
3. The `MAX_STANDARD_TX_WEIGHT` check at line 241 also uses the understated `weight`, so a transaction legitimately over the standardness limit once the data output is counted can be constructed and signed.

`data` is unprivileged input: `SignableTransaction::new` is a public constructor and the OP_RETURN payload is exactly the channel used for deposit `InInstruction`s (see `tests/processor/src/networks.rs` attaching `RefundableInInstruction` via OP_RETURN).

### Impact Explanation
The transaction commits `needed_fee` sats to miners, but the true vsize is larger by the size of the OP_RETURN output (up to ~92 weight units ≈ 23 vbytes, more depending on script overhead). The difference is silently absorbed by the change output — change receives funds that were supposed to cover the fee for the data output. When `fee_per_vbyte` is chosen near the minimum (as is the intent of the `TooLowFee` guard), the resulting transaction's actual feerate can fall below `DEFAULT_MIN_RELAY_TX_FEE`, causing relay rejection after signing. All inputs remain spendable only via re-signing; the payments and change in the signed transaction are permanently void. Additionally, near the standardness weight limit, a signed transaction can exceed `MAX_STANDARD_TX_WEIGHT` once the uncounted output is included, again making it unbroadcastable. This is a funds-accounting error reachable entirely through public inputs (chosen `data`, `payments`, `fee_per_vbyte`).

### Likelihood Explanation
Triggered whenever `data` is `Some` and non-empty — a normal, documented use of the API (OP_RETURN instructions are the intended data channel). The severity scales with the data length and how close `fee_per_vbyte` is to the relay minimum. The miscounting is unconditional; only the relay-failure outcome is conditional on the feerate margin (~23 vbytes of slack suffices to bridge the gap only if feerate isn't at the floor). Medium likelihood of underpayment; lower likelihood of outright relay failure.

### Recommendation
Include the OP_RETURN output in the weight estimate. Change `calculate_weight_vbytes` calls to pass `&tx_outs` (or a slice reflecting all outputs) instead of `payments`, e.g. compute the data-bearing output list before line 204 and pass it in:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), &tx_outs, None);
```

and correspondingly pass `&tx_outs` in the change branch so `fee_with_change` covers payments + data + change. This ensures `needed_fee`, the `TooLowFee` check, the change amount, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction actually signed.

### Proof of Concept
```rust
// inputs: one ReceivedOutput of 100_000 sats
// payments: [(addr, 50_000)], change: Some(change_addr), fee_per_vbyte: 1
// data: Some(vec![0u8; 80])
let tx = SignableTransaction::new(inputs, &payments, Some(change), Some(data), 1).unwrap();

// Actual signed transaction includes a ~92-weight-unit OP_RETURN output.
let actual_vsize = /* tx.txid-size once completed */;
// tx.fee() == tx.needed_fee() == fee_per_vbyte * vbytes_without_data
// => effective feerate = needed_fee / (vbytes_without_data + ~23) < 1 sat/vbyte
// => below DEFAULT_MIN_RELAY_TX_FEE for the true size => relay rejection.
// Meanwhile change = 100_000 - 50_000 - needed_fee, i.e., ~23 sats too large.
```

The assertion `input_value - output_value == needed_fee` in `networks/bitcoin/tests/wallet.rs:272` passes only because `needed_fee` is itself computed on the understated size — the test never exercises the `data` path.
