## Analysis

The DODO finding is a classic **"unchecked monotonic-array invariant"** bug: code assumes an externally-supplied index array is sorted ascending and starts at zero, uses each element as a loop bound (`splitNumber[i-1]` to `splitNumber[i]`), and never validates the assumption — so an out-of-order array silently skips iterations and corrupts downstream state.

Searching Desktop's diff-processing pipeline turns up the same invariant-without-validation pattern in the unified-diff parser and its consumers.

### Title
DiffParser and patch reconstruction trust hunk header line numbers without validating monotonic ordering, allowing a malformed diff to silently corrupt partial-commit patches - (File: app/src/lib/diff-parser.ts)

### Summary
`DiffParser.parseHunk` extracts `oldStartLine`/`newStartLine` for each hunk purely via regex from the raw diff text and never checks that consecutive hunks are ascending and non-overlapping. [1](#0-0) 
Every downstream consumer — hunk-expansion math, absolute-line indexing, and most importantly patch reconstruction for partial commits — implicitly assumes hunks are produced in file order (as a well-behaved `git diff` always does), exactly like DODO's loop assumed `splitNumber` was sorted ascending starting at 0.

### Finding Description
`parseHunk` computes `header.oldStartLine`/`header.newStartLine` from the `@@ -l,s +l,s @@` line and stores each hunk's absolute range as `linesConsumed` .. `linesConsumed + lines.length - 1`, purely sequentially, with no cross-check against the numeric line numbers claimed by the header itself. [2](#0-1) [3](#0-2) 

`getHunkHeaderExpansionType` then computes `distanceToPrevious = hunkHeader.oldStartLine - previousHunk.header.oldStartLine - previousHunk.header.oldLineCount`, which silently produces a nonsensical (e.g. negative) value if a later hunk's `oldStartLine` is not strictly greater than the previous hunk's end — analogous to DODO's `splitNumber[i-1] >= splitNumber[i]` case being silently accepted instead of rejected. [4](#0-3) 

The most impactful consumer is `formatPatch` in `patch-formatter.ts`, which is used to build the actual `git apply --cached` payload for **partial staging/committing** (checking/unchecking individual lines in the UI). It writes out `hunk.header.oldStartLine`/`newStartLine` verbatim as the new patch's hunk header and decides which lines to keep based on `absoluteIndex = hunk.unifiedDiffStart + lineIndex` and the UI's `file.selection.isSelected(absoluteIndex)` state. [5](#0-4) 
That reconstructed patch is piped straight into `git apply --cached` without any re-validation of hunk ordering/consistency. [6](#0-5) 

If a diff ever contains hunk headers that are not properly ascending/non-overlapping (e.g., through a crafted `.gitattributes` external diff/textconv driver, or any git plumbing path that produces non-standard unified-diff text feeding `DiffParser.parse`), the parser accepts it without complaint, `unifiedDiffStart/End` bookkeeping and the checkbox-based `DiffSelection` bit-indices computed by the UI no longer correspond to the real file positions implied by the (bogus) headers written into the hand-rolled patch, and `git apply --cached` will apply the resulting hunk at the position dictated by the (unvalidated) header numbers — not at the position the user visually selected in the diff viewer.

### Impact Explanation
Because `formatPatch`'s output header numbers are taken as-is from a diff whose ordering is never validated, a corrupted/malformed diff can cause `git apply --cached` to stage content at different line positions than what was shown/selected in the UI. This is a silent corruption of what the user commits — the user believes they are staging exactly the checked lines, but the applied patch can diverge from that selection, matching the "silent corruption of what the user commits" impact criterion.

### Likelihood Explanation
This requires an attacker to make the unified diff text fed into `DiffParser.parse` violate the ascending/non-overlapping hunk-header invariant that ordinary `git diff` output always satisfies. I was not able to fully confirm, from the indexed code alone, a currently-reachable path (e.g. a custom diff/textconv driver configured via a cloned repo's `.gitattributes`) that lets an attacker author diff text consumed by this parser; verifying that requires inspecting how `getWorkingDirectoryDiff`/`convertDiff` invoke git and whether any user-controllable driver output can reach `DiffParser.parse` unmodified. What is concretely established from local code is that the invariant is never checked anywhere in `diff-parser.ts`, `text-diff-expansion.ts`, or `patch-formatter.ts`.

### Recommendation
In `DiffParser.parseHunk`/`parse`, validate that each hunk's `oldStartLine`/`newStartLine` is strictly greater than the previous hunk's corresponding end line, and throw (treat as malformed diff) otherwise — mirroring the DODO fix of validating `splitNumber` is sorted ascending and starts at 0 before trusting it as loop bounds.

### Proof of Concept
Conceptual (not confirmed against a live attacker-controlled input path):
1. Construct raw diff text with two hunks where the second hunk's header (`@@ -5,2 +5,2 @@`) has a lower/overlapping start line than the first hunk's already-consumed range (`@@ -10,2 +10,2 @@` followed by `@@ -5,2 +5,2 @@`).
2. Feed this text to `DiffParser.parse` — it parses successfully with no ordering error, at `app/src/lib/diff-parser.ts:399-460`.
3. Select lines via `DiffSelection` using UI-visible absolute indices, then call `formatPatch`, at `app/src/lib/patch-formatter.ts:129-232`, which reuses the (unordered) `hunk.header.oldStartLine/newStartLine` verbatim in the emitted patch.
4. Apply via `applyPatchToIndex`, at `app/src/lib/git/apply.ts:52-81` — `git apply --cached` positions the hunk per the (unvalidated) header, potentially staging different file lines than the ones visually checked in the UI.

export function getHunkHeaderExpansionType(
  hunkIndex: number,
  hunkHeader: DiffHunkHeader,
  previousHunk: DiffHunk | null
): DiffHunkExpansionType {
  const distanceToPrevious =
    previousHunk === null
      ? Infinity
      : hunkHeader.oldStartLine -
        previousHunk.header.oldStartLine -
        previousHunk.header.oldLineCount

  // In order to simplify the whole logic around expansion, only the hunk at the
  // top can be expanded up exclusively, and only the hunk at the bottom (the
  // dummy one, see getTextDiffWithBottomDummyHunk) can be expanded down
  // exclusively.
  // The rest of the hunks can be expanded both ways, except those which are too
  // short and therefore the direction of expansion doesn't matter.
  if (hunkIndex === 0) {
    // The top hunk can only be expanded if there is content above it
    if (hunkHeader.oldStartLine > 1 && hunkHeader.newStartLine > 1) {
      return DiffHunkExpansionType.Up
    } else {
      return DiffHunkExpansionType.None
    }
  } else if (distanceToPrevious <= DefaultDiffExpansionStep) {
    return DiffHunkExpansionType.Short
  } else {
    return DiffHunkExpansionType.Both
  }
}

```typescript
export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })
```
