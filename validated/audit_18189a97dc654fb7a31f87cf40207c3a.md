### Title
Fee and weight calculation ignores the OP_RETURN data output, undercharging fees and undercounting transaction weight - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` builds the transaction's weight/vbyte estimate solely from the inputs and `payments`, plus optionally `change`. The caller-supplied `data` payload — which becomes a real `TxOut` (OP_RETURN) on the signed transaction — is never fed into `calculate_weight_vbytes`. This is the Serai analog of assuming a fixed `1e18` denominator: a fixed shape assumption (only payment/change outputs affect size) makes the fee and size math wrong whenever a data output is present.

### Finding Description
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150-256`):

- The OP_RETURN output is appended to `tx_outs` at lines 194-202 when `data` is `Some`.
- But the weight/vbyte estimate at line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — `payments` only, `data` excluded. `needed_fee = fee_per_vbyte * vbytes` (line 206) therefore prices a transaction smaller than the one actually signed.
- The change-path estimate at lines 225-227 also omits the data output, so both `needed_fee` values are too low, and the leftover-change test at line 228 (`input_sat - payment_sat - fee_with_change`) overestimates the available change.
- The standardness check at line 241 uses `weight` that never includes the OP_RETURN output's bytes, so a transaction up to ~90 weight units (marker/flag + value + scriptPubKey + ~80-byte pushdata) over `MAX_STANDARD_TX_WEIGHT` can pass.

The caller controls `data` (up to 80 bytes per the check at line 171), i.e., untrusted transaction data fed into a sign API — the reachable public input path per scope rules.

### Impact Explanation
The transaction actually signed commits (via `Prevouts::All` SIGHASH_DEFAULT) to a larger, more expensive transaction than `needed_fee` reflects. Effective fee rate is below the caller-requested `fee_per_vbyte`, potentially below relay minimums — burns/payments stall and may need re-signing with new preprocesses. If the operator/payer intends a guaranteed fee rate, the multisig signs a transaction paying less than intended, and the change output receives the difference that was intended as fee headroom — or vice versa, change is overestimated relative to true cost. This parallels the report's "feeAmount too large or too small" consequence.

### Likelihood Explanation
Triggered whenever `SignableTransaction::new` is called with `data.is_some()` — a single public input, no collusion or privileged position needed. Effect scales with data length (~10-90 extra bytes → proportional underpayment).

### Recommendation
Include the OP_RETURN output in the `payments`-equivalent list passed to `calculate_weight_vbytes` (or construct the full `tx_outs` before measuring), so both the no-change and with-change estimates, the `needed_fee` computation, and the `MAX_STANDARD_TX_WEIGHT` check account for the data output.

### Proof of Concept
Call `SignableTransaction::new(inputs, payments, None, Some(vec![0u8; 80]), fee_per_vbyte)` where `inputs` cover `payment_sat + needed_fee` exactly. It returns `Ok` with a signed transaction containing an extra OP_RETURN `TxOut` (~90 weight units ≈ 22 vbytes) not priced into `needed_fee`; `fee()` (line 138) equals `needed_fee` computed for a transaction ~22 vbytes smaller, so the effective sat/vbyte rate is below `fee_per_vbyte` and may drop under `DEFAULT_MIN_RELAY_TX_FEE` despite passing the check at line 211.
