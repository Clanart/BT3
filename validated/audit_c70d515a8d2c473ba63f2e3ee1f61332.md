### Title
Clawback coins can become permanently stuck (unclaimable without manual `force` override) due to premature `sent` marking before spend bundle push - ([File: chia/wallet/clawback_manager.py])

### Summary
`ClawbackManager.spend_clawback_coins` marks a clawback coin's underlying incoming transaction as "sent"/pending before the aggregate spend bundle that actually claims the coin is fully assembled and handed off for broadcast. If assembly fails after that marking (e.g. the fee tandem-transaction step or the aggregate-bundle post-processing throws), the coin is left in a state that both the automatic claimer and any un-forced manual retry will skip forever.

### Finding Description
In `spend_clawback_coins`, for each clawback coin being processed the code builds the coin's individual spend and then immediately marks its `incoming_tx` as sent/pending: [1](#0-0) 

This call happens **inside the per-coin loop**, well before the aggregated `spend_bundle` is built, before the optional fee tandem transaction is created, and before the final `TransactionRecord` is appended to the action scope for broadcast: [2](#0-1) 

That trailing block (lines 264-321) is not wrapped in a `try/except`, unlike the per-coin loop body. If it raises — for instance `create_tandem_xch_tx` failing due to insufficient fee-paying coins, or the `assert derivation_record is not None` at line 299 failing — the exception propagates out of `spend_clawback_coins` and the aggregated bundle is never appended to `action_scope.side_effects.transactions`, so nothing is ever pushed to the mempool for that batch.

However, `incoming_tx.sent` was already incremented for every coin successfully processed earlier in the loop. On any subsequent call (automatic, via the periodic `auto_claim_coins`, or manual), the guard: [3](#0-2) 
skips these coins because `incoming_tx.sent > 0`, unless the caller explicitly passes `force=True`. This is structurally the same root cause as the reported issue: state is mutated to reflect "in-flight/done" before the actual external action (the on-chain broadcast) is confirmed to have started, and a failure in between leaves no automatic path back to a retryable state.

### Impact Explanation
Affected clawback coins are neither spent nor lost on-chain — the underlying funds are still safely locked in the clawback puzzle — but the wallet's own claim-recovery logic silently treats them as already handled. The scheduled `auto_claim_coins` job will perpetually skip these coins on every future run, since it never sets `force=True`: [4](#0-3) 
Recovering the coin therefore requires knowledge of, and explicit use of, the internal `force` parameter, which is not exercised by the normal auto-claim path. This is a fund-availability/liveness impact (temporary loss of automated access to owned coins), not an outright asset theft, so I assess it as Medium rather than High/Critical.

### Likelihood Explanation
Triggering requires only a normal wallet operation (receiving a clawback-eligible coin and letting/forcing the auto-claim/claim RPC run) plus one of the downstream failure conditions (e.g., insufficient available XCH to pay the claim fee at the moment `create_tandem_xch_tx` runs, coin selection race, or any other exception in the trailing aggregate-and-append block). Fee-related coin-selection failures are a realistic, unprivileged condition a normal wallet user can encounter (e.g., low available balance, coins locked in other pending transactions), making this reachable without any privileged or malicious actor.

### Recommendation
Move the `increment_sent` call (or an equivalent "in-flight" marker) to occur only after the aggregate spend bundle has been successfully constructed and appended to `action_scope.side_effects.transactions` (i.e., after line 321), or wrap the whole post-loop aggregation/fee logic in a `try/except` that reverts the `sent` marking (or calls `increment_sent` with `MempoolInclusionStatus.FAILED`) for every coin already marked in this batch if any later step fails. This ensures a failure during bundle assembly leaves affected coins in a retryable state without needing `force=True`.

### Proof of Concept
1. A wallet has multiple clawback-eligible coins ready to auto-claim and `auto_claim_tx_fee > 0`.
2. `auto_claim_coins` batches several coins and calls `spend_clawback_coins`; the per-coin loop succeeds for all coins and calls `increment_sent(...)` for each, marking their `incoming_tx.sent > 0`.
3. Immediately afterward, `create_tandem_xch_tx` (invoked because `fee > 0`) fails because the wallet has no additional spendable coin available for the fee at that moment (e.g., concurrently reserved by another pending transaction) — this raises an exception that is not caught anywhere in `spend_clawback_coins`.
4. No `TransactionRecord`/spend bundle is ever appended to the action scope, so nothing is broadcast; the clawback coins remain unspent on-chain.
5. On the next `auto_claim_coins` cycle, all of these coins are skipped via `if incoming_tx.sent > 0 and not force: continue`, and remain stuck indefinitely unless a caller manually invokes the claim path with `force=True`.
