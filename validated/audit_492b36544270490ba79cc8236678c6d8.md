### Title
Non-unique withdrawal_utxo join lets a single payout transaction be attributed to multiple withdrawal indices, crediting operator reimbursement for deposits it never fronted - (File: core/src/database/verifier.rs, core/src/verifier.rs)

### Summary
`Database::get_payout_txs_for_withdrawal_utxos` joins `withdrawals` to `bitcoin_syncer_spent_utxos` solely on `withdrawal_utxo_txid`/`withdrawal_utxo_vout`, with no requirement that this pair be unique per `idx`. `Verifier::update_finalized_payouts` feeds every `(idx, payout_txid)` row this join produces into `update_payout_txs_and_payer_operator_xonly_pk`, so if two withdrawal indices (backing two different deposits) are ever registered with the same underlying Bitcoin outpoint, one on-chain payout transaction gets recorded as having paid both.

### Finding Description
The binding that must hold is: **for a given payout Bitcoin transaction `T` spending outpoint `U`, there is exactly one `idx` in `withdrawals` such that `withdrawals.withdrawal_utxo_txid:vout = U`** (i.e., one fronted payout ⇔ one settled withdrawal claim). Nothing in this repository enforces that binding.

- `withdrawals` (`core/src/database/schema.sql:269-281`) has only `idx` as primary key; there is no `UNIQUE(withdrawal_utxo_txid, withdrawal_utxo_vout)` constraint. [1](#0-0) 
- `update_withdrawal_utxo_from_citrea_withdrawal` blindly writes the attacker/L2-user supplied outpoint bytes into the row keyed by `idx`, with no check that this outpoint is not already used by another `idx`: [2](#0-1) 
- `get_payout_txs_for_withdrawal_utxos` joins purely on `(txid, vout)`: [3](#0-2) 
- `Verifier::update_finalized_payouts` iterates every row returned by that join and unconditionally calls `update_payout_txs_and_payer_operator_xonly_pk`, which does a bulk `UPDATE ... WHERE w.idx = c.idx`, so *every* `idx` sharing the outpoint gets the same `payout_txid`, `payout_payer_operator_xonly_pk`, and `payout_tx_blockhash`: [4](#0-3) [5](#0-4) 
- Downstream, `PayoutCheckerTask::run_once` (running automatically on the operator's own node) picks up *any* unhandled row that has `payout_payer_operator_xonly_pk = self` and `payout_txid IS NOT NULL`, resolves it to a *different* deposit via `move_to_vault_txid`, and calls `Operator::handle_finalized_payout` to kick off the reimbursement flow for that deposit, using the shared `payout_tx_blockhash`: [6](#0-5) [7](#0-6) 

Exploit flow: an attacker who has made two separate deposits (`deposit_id`=D1, D2) calls Citrea's bridge `withdraw()` twice, once for each deposit, but supplies the **same Bitcoin outpoint bytes** `U` as the intended `withdrawal_utxo` for both L2 withdrawal indices `idx1` and `idx2` (nothing in `core/src/citrea.rs`'s `collect_withdrawal_utxos`/`get_storage_proof` path checks cross-index uniqueness of the registered outpoint before Clementine ingests it). The operator's automated `Operator::withdraw` for `idx1` fronts a real BTC payout transaction `T` spending `U`; when `idx2`'s withdraw is subsequently attempted, `rpc.get_txout_from_outpoint(U)` fails because `U` is already spent, so the operator never funds a second payout — only `T` ever exists on-chain (`core/src/operator.rs:560-627`). However, because both `withdrawals` rows reference the same `(txid, vout)`, `get_payout_txs_for_withdrawal_utxos` returns `(idx1, T)` **and** `(idx2, T)`, and both get written with `payout_payer_operator_xonly_pk = operator`. `PayoutCheckerTask` then independently processes `idx2` (whose `move_to_vault_txid` points at deposit D2, never actually fronted), drives a kickoff, and eventually the reimbursement connector for D2 is claimed — the operator is paid back for a payout it never sent for D2.

None of the existing guards catch this: `Verifier::is_deposit_valid` and `Operator::is_profitable` only gate the initial `withdraw()` call, not the later join in `update_finalized_payouts`; there is no check that `payout_txid` (and the outpoint it spent) is used by only one `idx`; the bridge circuit's `verify_storage_proofs` only proves that `idx2`'s registered outpoint genuinely equals `U` in Citrea state and that `T` spends `U` — it says nothing about `T` also having satisfied `idx1`, so the on-chain kickoff/challenge/disprove machinery for D2 will pass even though D2's payout was never separately funded.

### Impact Explanation
An operator ends up being reimbursed (collateral released via the `ReimburseInKickoff` connector) for a deposit (D2) whose withdrawal was never actually fronted with BTC — one on-chain payout transaction is double-counted across two withdrawal indices/deposits. This lets more BTC leave the move-to-vault UTXOs than was ever fronted to users, matching the Critical category "an operator reimbursed for a payout it never funded" / "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal." The blast radius scales with however many deposits the attacker controls and can register under colliding withdrawal outpoints; it is repeatable per attacker-controlled deposit pair and is not limited to a single operator (any operator that happens to process the colliding indices is affected).

### Likelihood Explanation
The attacker only needs to be a normal, unprivileged Citrea/bridge user: make two deposits, then call the public `withdraw()` entrypoint on the Citrea bridge contract twice, supplying identical outpoint bytes for both calls' `withdrawal_utxo`. This requires no signature forgery, no verifier/operator/aggregator privilege, and no majority hashrate — only the ability to submit L2 transactions and to construct a Bitcoin dust output whose outpoint they reuse as the declared `withdrawal_utxo` for two withdrawal registrations. Cost is limited to normal deposit/withdrawal fees. Whether the Citrea bridge contract itself permits registering a duplicate outpoint across indices could not be verified from this repository (the contract is out of this repo's scope), but nothing in Clementine's ingestion path (`collect_withdrawal_utxos`, `update_withdrawal_utxo_from_citrea_withdrawal`, `get_payout_txs_for_withdrawal_utxos`) rejects or even detects such a duplicate, so if the L2 side allows it, Clementine will silently mis-attribute the payout.

### Recommendation
Enforce a uniqueness invariant on the join key: add a uniqueness check to `get_payout_txs_for_withdrawal_utxos` (or the `withdrawals` table) so a given `(withdrawal_utxo_txid, withdrawal_utxo_vout, payout_txid)` can settle at most one `idx`, e.g. by adding a `UNIQUE(withdrawal_utxo_txid, withdrawal_utxo_vout)` constraint on the `withdrawals` table (rejecting/erroring the second registration at ingestion in `update_withdrawal_utxo_from_citrea_withdrawal`), and/or by making `update_payout_txs_and_payer_operator_xonly_pk` fail loudly (rather than silently update all matching idxs) whenever `get_payout_txs_for_withdrawal_utxos` returns more than one `idx` for the same `payout_txid`.

### Proof of Concept
In `core/src/database/verifier.rs` tests (or a new integration test under `core/src/test`):
1. Insert two `withdrawals` rows for `idx1`/`idx2` with distinct `move_to_vault_txid` (D1, D2) but identical `withdrawal_utxo_txid`/`withdrawal_utxo_vout = U`, via `upsert_move_to_vault_txid_from_citrea_deposit` + `update_withdrawal_utxo_from_citrea_withdrawal`.
2. Record one spent-UTXO entry (`insert_spent_utxo`) showing `U` spent by a single payout txid `T` in `block_id`.
3. Call `get_payout_txs_for_withdrawal_utxos(Some(&mut dbtx), block_id)` and assert the binding: `results.len() == 1` (one payout ⇒ one settled `idx`). The current implementation will return `len() == 2` (`[(idx1, T), (idx2, T)]`), demonstrating the bug.
4. Follow with `update_payout_txs_and_payer_operator_xonly_pk` and `get_first_unhandled_payout_by_operator_xonly_pk` to show both `idx1` and `idx2` become "payable" (`is_payout_handled = false`, `payout_txid = T`, same operator) despite only one payout ever having existed on-chain.

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }

    async fn run_once(&mut self) -> Result<Self::Output, BridgeError> {
        let mut dbtx = self.db.begin_transaction().await?;
        let unhandled_payout = self
            .db
            .get_first_unhandled_payout_by_operator_xonly_pk(
                Some(&mut dbtx),
                self.operator.signer.xonly_public_key,
            )
            .await?;

        if unhandled_payout.is_none() {
            return Ok(false);
        }

        let (citrea_idx, move_to_vault_txid, payout_tx_blockhash) =
            unhandled_payout.expect("Must be Some");

        tracing::info!(
            "Unhandled payout found for withdrawal {}, move_txid: {}",
            citrea_idx,
            move_to_vault_txid
        );

        let deposit_data = self
            .db
            .get_deposit_data_with_move_tx(Some(&mut dbtx), move_to_vault_txid)
            .await?;
        if deposit_data.is_none() {
            return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());
        }

        let deposit_data = deposit_data.expect("Must be Some");

        let kickoff_txid = self
            .operator
            .handle_finalized_payout(
                &mut dbtx,
                deposit_data.get_deposit_outpoint(),
                payout_tx_blockhash,
            )
            .await?;

        // fetch and save the LCP for if we get challenged and need to provide proof of payout later
        let (_, payout_block_height) = self
            .operator
            .db
            .get_block_info_from_hash(Some(&mut dbtx), payout_tx_blockhash)
            .await?
            .ok_or_eyre("Couldn't find payout blockhash in bitcoin sync")?;

        let _ = self
            .operator
            .citrea_client
            .fetch_validate_and_store_lcp(
                payout_block_height as u64,
                citrea_idx,
                &self.operator.db,
                Some(&mut dbtx),
                self.operator.config.protocol_paramset(),
            )
            .await?;

        #[cfg(feature = "automation")]
        self.operator.end_round(&mut dbtx).await?;

        self.db
            .mark_payout_handled(Some(&mut dbtx), citrea_idx, kickoff_txid)
            .await?;
