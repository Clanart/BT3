### Title
Unchecked user-supplied reward-token addresses let any caller sweep the entire token balance of `ManualCompound` - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` is a fully permissionless, unprivileged-callable function that accepts attacker-controlled `_rewards[i][j]` token addresses and uses them to decide which ERC20 balances to move out of the contract. For any address that is not in the admin-controlled `compoundableRewards` whitelist, the function unconditionally transfers the contract's **entire current balance** of that token to `msg.sender`, with no verification that the balance corresponds to something the caller actually earned in that transaction. This mirrors the CoverRouter bug class: an externally reachable function trusts caller-supplied addresses to drive fund movement without validating them or enforcing a zero-residual-balance invariant.

### Finding Description
`compound()` is declared `external` with no access-control modifier [1](#0-0) , so it can be called by any unprivileged wallet with arbitrary `_lps` and `_rewards` calldata arrays.

After claiming through `IMasterMagpie.multiclaimOnBehalf`, the function performs a "sweep" pass over the attacker-supplied `_rewards[i][j]` addresses:

```solidity
if (!compoundableRewards[_rewards[i][j]]) {
    uint256 rewardBalance = IERC20(_rewards[i][j]).balanceOf(address(this));
    if (rewardBalance > 0)
        IERC20(_rewards[i][j]).safeTransfer(msg.sender, rewardBalance);
}
``` [2](#0-1) 

There is no check that `rewardBalance` was produced by this specific call for `msg.sender` — the code simply reads whatever the contract currently holds for that token and pays it all out. The same pattern repeats for the admin-configured "compoundable" reward list a few lines later, which also converts/locks the contract's **full current balance** (`IERC20(_tokenAddress).balanceOf(address(this))`) rather than the delta produced by this specific claim [3](#0-2) .

Compounding this, MGP itself is always routed to the `_receiver` (i.e., the `ManualCompound` contract) independently of the `_rewardTokens` argument passed to `_multiClaim`, via `_sendMGP` / `_sendVlMGPFor` / `_sendMGPForVlMGPPool` [4](#0-3) . So MGP (and any bonus reward tokens) can land in the `ManualCompound` balance whenever any user calls compound, and the withdrawal logic that sweeps it out is keyed only on the attacker-chosen token address, not on who legitimately earned it.

This differs from the report's core problem in the same way: `CoverRouter.addCoverAndCreatePools` let a caller supply arbitrary `_protocol`/`_collateral` addresses that drove unconditional token movement, and failed to enforce that the contract ends the transaction holding zero balance beyond what the caller is entitled to. `ManualCompound.compound()` similarly lets a caller supply arbitrary reward-token addresses that drive an unconditional full-balance sweep, with no balance-delta accounting to tie the payout to the caller's own claim.

### Impact Explanation
If the `ManualCompound` contract ever holds a residual ERC20 balance that is not attributable to the current caller — e.g., dust left over from imperfect conversion/locking of a previously "compoundable" token, a token that was later de-registered via `removeReward` (which just flips `compoundableRewards[_tokenAddress] = false` without sweeping the existing balance) [5](#0-4) , or reward tokens accidentally sent to the contract — any unprivileged wallet can drain that balance completely by simply calling `compound()` with the target token address in `_rewards`. This is a direct theft of funds that do not belong to the caller and, depending on what accumulates, can also represent permanent loss of legitimately earned but not-yet-distributed rewards belonging to other users.

### Likelihood Explanation
The function is `external` and callable by any wallet with no special privileges, matching the "unprivileged-wallet analog" scope. Exploitability is contingent on the contract actually holding a non-zero balance of a non-compoundable (or de-registered) token at the time of the call — a state that is realistically reachable through admin token removal, rounding in `IConverter`/`ILocker`/`ISimpleHelper` interactions, or accidental transfers, all of which are plausible in normal, long-running operation of a "sweep the whole current balance" design.

### Recommendation
Do not use `IERC20.balanceOf(address(this))` as the amount to distribute in `compound()`. Instead, record balances immediately before and after the `multiclaimOnBehalf` call (or after each specific reward token's claim) and only forward the balance **delta** attributable to the current caller for both the non-compoundable "return to sender" branch and the compoundable convert/lock branch. Additionally, provide an owner-only sweep function to recover genuinely stuck/misconfigured token balances instead of allowing any caller to claim them via unchecked address input.

### Proof of Concept
1. Admin calls `addReward(tokenX, ...)` then later `removeReward(index, tokenX)`, setting `compoundableRewards[tokenX] = false`, while `ManualCompound` still holds a leftover balance of `tokenX` (e.g., dust from prior conversions that were not fully swept). [5](#0-4) 
2. Any unprivileged wallet calls `compound(_lps, _rewards, 0, 0, false)` where `_lps` contains any valid pool token (even one the caller has zero stake in) and `_rewards[0] = [tokenX]`.
3. Inside `compound()`, since `compoundableRewards[tokenX] == false`, the code executes `IERC20(tokenX).safeTransfer(msg.sender, IERC20(tokenX).balanceOf(address(this)))`, sending the entire leftover `tokenX` balance to the caller regardless of whether they claimed or earned anything. [6](#0-5)
