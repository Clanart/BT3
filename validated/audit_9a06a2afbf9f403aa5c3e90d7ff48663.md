### Title
Identity ("zero") verification shares are accepted by `ThresholdKeys::new`/`ThresholdKeys::read`, yielding an identity group key for which anyone can forge signatures - (File: crypto/dkg/src/lib.rs)

### Summary
The external report's bug class — failing to reject a zero-value where a nonzero value is required — maps onto Serai's threshold-key deserialization: `ThresholdKeys::read` parses `verification_shares` via `Ciphersuite::read_G`, which enforces canonicality/torsion-freedom but *not* non-identity, and `ThresholdKeys::new` never checks that verification shares, or the resulting `group_key`, are non-identity. An unprivileged party who supplies crafted serialized `ThresholdKeys` bytes (a listed untrusted-bytes sink) can therefore instantiate a key set whose group key is the identity point — the curve-level equivalent of the zero address. Schnorr signatures under an identity public key verify trivially for any `R = s·G`, so signatures for this "zero" key are forgeable by anyone.

### Finding Description
`ThresholdKeys::read` reads `n` verification shares with `<C as Ciphersuite>::read_G(reader)` and passes them to `ThresholdKeys::new` (crypto/dkg/src/lib.rs:620-631). `Ciphersuite::read_G` only rejects invalid/non-canonical encodings (crypto/ciphersuite/src/lib.rs:91-101); the identity point is a canonical, torsion-free point and is accepted. `ThresholdKeys::new` then computes `group_key` as a weighted sum of `verification_shares[1..=t]` (crypto/dkg/src/lib.rs:376-378) with no identity check on either the inputs or the result. Only `Curve::read_G` in the FROST crate rejects identity (crypto/frost/src/curve/mod.rs:124-131), and it is not used here. If an attacker supplies shares where the first `t` verification shares are identity (or otherwise interpolate to identity), the resulting `group_key` is the identity point. `SchnorrSignature::verify` checks `R + c·A − s·G == 0` (crypto/schnorr/src/lib.rs:88-110); with `A` = identity, any `(R = s·G, s)` pair satisfies this for every challenge — a universal forgery for the "zero" key. `SchnorrSignature::read` likewise does not reject identity `R` (crypto/schnorr/src/lib.rs:51-53).

### Impact Explanation
Any funds or authorizations bound to the identity group key are spendable/forgeable by anyone: with `A = 0`, `s·G == R` verifies regardless of the challenge or message. Downstream (e.g., `tweak_keys` in networks/bitcoin/src/wallet/mod.rs:46 derives a Taproot address from `group_key`), outputs scanned as received to such a key are effectively unowned — anyone can produce a valid-looking spend authorization for them. This is the exact analog of "account opened for the zero address": a zero-valued cryptographic identity accepted as a legitimate account/key.

### Likelihood Explanation
Exploitation requires feeding crafted bytes to `ThresholdKeys::read` (or equivalent construction), which is a reachable path for untrusted input per the accepted threat surface. No secret, collusion, or privileged position is needed — only the ability to supply the serialized key material, e.g., a malicious peer providing key blobs that a node deserializes and uses to derive deposit addresses or verify signatures.

### Recommendation
In `ThresholdKeys::new` (and/or `ThresholdKeys::read`), reject identity verification shares and abort if the computed `group_key` is the identity point; additionally consider rejecting identity `R`/zero `s` in `SchnorrSignature::read` and identity `public_key` in `SchnorrSignature::verify` as defense-in-depth, mirroring the existing identity rejection in `Curve::read_G`.

### Proof of Concept
1. Serialize a `ThresholdKeys<C>` blob with `t = n` (e.g., 2), interpolation = `Constant`, any `secret_share`, and set `verification_shares[1]` and `verification_shares[2]` to the canonical encoding of the identity point.
2. `ThresholdKeys::read` accepts it; `keys.group_key() == C::G::identity()`.
3. For any message, compute `challenge` per the protocol's HRAM against this group key, pick random `s`, set `R = C::generator() * s`; `SchnorrSignature { R, s }.verify(identity, challenge)` returns `true` — a signature forged by a party holding no key material, and conversely any honestly produced FROST signature for this key is indistinguishable from forgeries.
