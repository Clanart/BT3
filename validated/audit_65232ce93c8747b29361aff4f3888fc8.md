Based on my investigation, I found a real gap in `getGitHubCredential` / `findGitHubTrampolineAccount`, which is checked **before** any host-kind validation and returns real GitHub account tokens for any credential request whose URL origin matches a signed-in account's endpoint origin.

### Title
Overly-permissive origin match in the Git credential-helper trampoline can leak a stored GitHub token to a same-origin, attacker-influenced credential request - (File: `app/src/lib/trampoline/find-account.ts`)

### Summary
`createCredentialHelperTrampolineHandler` (`app/src/lib/trampoline/trampoline-credential-helper.ts:220-259`) is invoked by git itself, via `git-credential-desktop`, whenever any git operation (clone/fetch/push, including recursive **submodule** operations, `insteadOf` rewrites, and LFS) needs credentials for some URL. The very first thing `getCredential` does is call `getGitHubCredential`, which resolves the account purely by comparing origins: [1](#0-0) 

There is no check that the credential request corresponds to the repository/remote the user actually intended to operate on, nor to the specific path/organization the account is scoped to — only scheme+host+port ("origin") of the account's HTML URL is compared to the origin of the URL git is asking credentials for.

### Finding Description
GitHub Desktop resolves any git credential request whose origin equals a signed-in account's endpoint origin by handing back that account's real OAuth/PAT token, without regard to the specific repository, submodule path, or `insteadOf`-derived remote that triggered the request: [2](#0-1) 

This function is called unconditionally, prior to the endpoint-kind classification (`getEndpointKind`) that later governs whether generic/external credential handling applies: [3](#0-2) 

The broken invariant: Desktop treats "same origin as a signed-in account's endpoint" as sufficient proof that a credential request is legitimate for that account, for *any* git subcommand that can trigger a fetch/clone with that origin — including operations initiated implicitly during recursive submodule handling of an attacker-authored repository (`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts:29-56`, invoked from `checkoutBranch`/`checkoutCommit`). A malicious repository can declare a submodule (or use `url.<base>.insteadOf` rewriting inside `.gitmodules`/config that Desktop trusts once the repo is added and safe-directory checked) that points at `https://github.com/<attacker-controlled-path>`. Because the origin (`https://github.com`) matches the signed-in account's endpoint origin, `findGitHubTrampolineAccount` returns the user's account and Desktop's credential helper hands the real token straight to git for that request — with no per-repository or per-path scoping, and no user confirmation.

Existing guards do not stop this path:
- `resolveWithin`/`resolveWithinPosix` protect *file path* traversal, not credential scoping — irrelevant here.
- `isTrustedIPCSender` protects the Electron IPC boundary, not the trampoline TCP protocol — the trampoline is a separate, git-facing channel authenticated only by a per-operation `trampolineToken` (`isValidTrampolineToken` in `trampoline-tokens.ts`), which proves the request came from a git process Desktop spawned, but does nothing to scope *which* origin that token is allowed to request credentials for.
- `getEndpointKind` classification (github.com / ghe.com / enterprise / generic) is computed and used to decide storage/retrieval semantics for *non*-GitHub-account (generic) credentials, but `getGitHubCredential` bypasses this entirely and runs first.

### Impact Explanation
This results in the user's real GitHub token/credential being sent by Desktop's own trampoline to whatever git subprocess (including one processing an untrusted, attacker-authored repository's submodules) is talking to `github.com`/the configured GHE host, without the user knowingly authorizing a request in that specific context. This is a genuine token-exfiltration-adjacent primitive: any git operation that can be steered (via submodule refs, URL rewriting, or a crafted remote in a cloned repository) into requesting credentials for an origin that happens to match a signed-in account is silently authenticated with the real user token — the "authorization" check is only an origin string comparison, not a scoped, per-repository confirmation.

### Likelihood Explanation
Likelihood is moderate: the attacker needs the victim to add/open/clone a malicious repository (this satisfies the "attacker controls a cloned/fetched repository" condition in Valid Impact) and for that repository (via submodules, or a remote) to reference a URL under the same origin as an already-signed-in account. Given GitHub Desktop's core function is browsing/cloning arbitrary repositories and adding submodules automatically on checkout (`updateSubmodulesAfterOperation`), this scenario is reachable without unusual user steps beyond normal repository use.

### Recommendation
Scope credential resolution beyond origin equality: verify that the credential request corresponds to a remote URL the user has explicitly configured for the *currently open* repository (or an explicit, user-approved submodule/LFS/`insteadOf` target), and require the same repository/path-prefix context that was used when the account was associated, rather than trusting any request that merely shares the account's endpoint origin. At minimum, avoid auto-approving `github.com`-origin credential requests triggered by submodule/hook/insteadOf-derived operations without explicit UI confirmation tying the request back to the specific repository action the user initiated.

### Proof of Concept
1. Sign in to GitHub Desktop with a github.com account (Account A, token T).
2. Attacker publishes a public repository `evil/repo` containing a `.gitmodules` entry (or `url.insteadOf` config) pointing a submodule to `https://github.com/private-org/secret-repo` that Account A does not have local credentials cached for via a *different* path, but the origin is `https://github.com`.
3. Victim clones/opens `evil/repo` in Desktop and checks out a branch, triggering `checkoutBranch` → `updateSubmodulesAfterOperation` → `git submodule update --init --recursive`.
4. Git spawns the credential helper (`git-credential-desktop`) for the submodule URL; `createCredentialHelperTrampolineHandler` → `getCredential` → `getGitHubCredential` matches origin `https://github.com` against Account A's endpoint and returns Account A's real token to satisfy the submodule fetch, without any dialog confirming this specific repository/target to the user.

Note: I was not able to execute this end-to-end in a live environment (no filesystem/terminal access here) — this analysis is based on static reading of `app/src/lib/trampoline/find-account.ts`, `app/src/lib/trampoline/trampoline-credential-helper.ts`, and `app/src/lib/git/submodule.ts`. A background Devin session with repo/terminal access would be needed to build and run the concrete PoC (clone a crafted repo with a submodule under `github.com` and observe the credential helper handing out the real account token) to confirm exploitability end-to-end.

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
