### Title
`SignableTransaction` fee/weight calculation ignores the `OP_RETURN` data output, letting a caller reduce the effective fee rate below the declared/minimum rate - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` appends a caller-supplied `data` payload as an `OP_RETURN` output to `tx_outs`, but the weight/vbyte computation in `calculate_weight_vbytes` is performed only over `payments` and `change`. The `data` output is never passed into the sizing function, so `needed_fee` (and the minimum-fee and max-weight checks) is computed against a transaction that is smaller than the one actually signed and broadcast. This is the same bug class as the Footium report: the fee is derived from a caller-influenced parameter set that does not reflect the real cost basis.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

- Lines 194-202: if `data` is `Some`, an `OP_RETURN` `TxOut` is pushed onto `tx_outs`. `data` can be up to 80 bytes (checked at line 171).
- Line 204: `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` — only `payments` is passed; the already-appended `tx_outs` (including the `OP_RETURN` output) are ignored.
- Line 206: `needed_fee = fee_per_vbyte * vbytes` — undercharges by `fee_per_vbyte * (data_len + output_overhead)`.
- Lines 225-233: the with-change recalculation (`calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`) again omits the `data` output, so `fee_with_change` is likewise undercharged and the change output is credited with more satoshis than it should be.
- Line 241: `weight > MAX_STANDARD_TX_WEIGHT` is checked against a `weight` that excludes the `OP_RETURN` output, so a transaction that is actually non-standard can pass validation.

`calculate_weight_vbytes` (lines 62-127) builds a synthetic `Transaction` whose `output` vector is derived solely from its `payments` and `change` arguments; there is no parameter for `data` at all, confirming the omission is structural rather than a call-site typo.

### Impact Explanation
The signed transaction's real fee (`sum(inputs) - sum(outputs)`) equals the undercomputed `needed_fee`, while its real vsize is larger by the `OP_RETURN` output (~9-90+ weight units). Effects:

- The effective fee rate is strictly lower than the `fee_per_vbyte` the constructor promised and lower than `needed_fee()` reports. For transactions constructed near the relay minimum, the actual fee can fall below `DEFAULT_MIN_RELAY_TX_FEE` for the *real* vsize — the check at line 211 compares `needed_fee` against a minimum computed on the undersized `vbytes`, not the real size. Such a transaction will not relay/confirm, leaving the inputs effectively frozen (they cannot be double-spent into a new plan while the stale TX is pending).
- The weight bound check can pass a transaction that is actually over `MAX_STANDARD_TX_WEIGHT`, producing a non-standard transaction the network rejects outright, burning the fee-intended funds' availability.

In Serai, `data` is a public caller input to `SignableTransaction::new`; whoever supplies (or influences) the message embedded in the transaction reduces the fee everyone else (the change output / operating-cost accounting) effectively bears — the direct analog of a club owner minting under a favorable `divisionTier`.

### Likelihood Explanation
Any construction path that supplies `Some(data)` triggers the undercount automatically — no race or special state is needed, only a non-empty `data` argument up to the 80-byte cap. The underestimate grows linearly with `data.len()`, so maximal impact (dropping below relay minimum or pushing weight over the standardness cap) is achieved with a full 80-byte payload. Whether a specific integrator exposes `data` to untrusted parties determines exploitability, but within the in-scope `bitcoin-serai` wallet API the parameter is attacker-controlled by design.

### Recommendation
Include the `data` output in the weight/vbyte accounting. Either add a `data: Option<&[u8]>` parameter to `calculate_weight_vbytes` and push the corresponding `TxOut` into the synthetic transaction, or — more robustly — compute `weight`/`vbytes` directly from the final `tx_outs`/`tx_ins` (after the change decision) instead of rebuilding a separate output list. Re-derive `weight` for the `MAX_STANDARD_TX_WEIGHT` check from the actual `tx` being returned so the check cannot diverge again.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs logic, conceptually:
// Construct a SignableTransaction with an 80-byte OP_RETURN payload.
let data = Some(vec![0u8; 80]);
let st = SignableTransaction::new(inputs, &payments, Some(change), data, fee_per_vbyte).unwrap();

// Reported fee basis:
let needed = st.needed_fee(); // == fee_per_vbyte * vbytes(payments + change)  <-- no OP_RETURN

// Actual transaction size once broadcast:
let actual_vsize = st.transaction().vsize() as u64; // includes the OP_RETURN output
assert!(actual_vsize > needed / fee_per_vbyte);      // undercharged by ~data_len+overhead vbytes

// Effective fee rate actually paid:
let effective_rate = st.fee() as f64 / actual_vsize as f64;
assert!(effective_rate < fee_per_vbyte as f64);      // strictly below the requested rate
```

For `fee_per_vbyte` near the minimum relay rate, `st.fee() < DEFAULT_MIN_RELAY_TX_FEE * actual_vsize / 1000`, so the transaction would be rejected by relay policy despite `new` having passed the `TooLowFee` check on line 211.
