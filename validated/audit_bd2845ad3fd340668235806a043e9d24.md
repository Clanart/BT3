The `associateAddresses`/`AssociateAddresses` path checks only that the *new* Sei address (`seiAddr`) is not already associated, but never checks whether the *EVM address* being bound (`evmAddr`) is already associated with a *different* Sei address before `SetAddressMapping` overwrites the reverse mapping — the same "missing existence check on the other side of the migration" defect class as the `migrateUser`/`prevUser` report.

### Title
Missing check that the target EVM address is not already associated with a different Sei address allows silent re-association / fund and identity hijack - ([File: precompiles/addr/addr.go])

### Summary
`associateAddresses` (and its EVM-ante-pipeline counterpart in `Preprocess`/`AnteHandle`) only guards against the *Sei* address side already being associated: `_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr); if found { revert }`. It never checks the reverse direction — whether `evmAddr` is already mapped to some other, already-associated Sei address via `GetSeiAddress(ctx, evmAddr)`. `SetAddressMapping` unconditionally overwrites both the forward and reverse KV entries.

### Finding Description
`AssociationHelper.AssociateAddresses` in [1](#0-0)  calls `p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)` unconditionally, and `SetAddressMapping` itself performs no existence check at all — it blindly overwrites both `EVMAddressToSeiAddressKey(evmAddress)` and `SeiAddressToEVMAddressKey(seiAddress)`: [2](#0-1) .

All callers of this helper (the `addr` precompile's `associateAddresses`, the legacy precompile versions, and the EVM preprocess ante decorator) only verify the forward direction before calling it: [3](#0-2) [4](#0-3) 

None of these callers ever call `GetSeiAddress(ctx, evmAddr)` to verify that the `evmAddr` argument being bound is not already the associated EVM address of a *different* Sei account. Since `SetCode`/EIP-7702 authority association and normal EVM tx signer association go through the same `AssociateAddresses` helper without a prevUser-style existence check, an attacker who can produce a valid signature/pubkey recovery for an arbitrary `evmAddr` (or exploit the EIP-7702 authority pre-association path noted in the code's own comment about "orphaning any staking/distribution state") can overwrite the reverse mapping for an EVM address that another Sei account already legitimately owns.

### Impact Explanation
Overwriting the reverse `EVMAddressToSeiAddressKey(evmAddress)` entry silently detaches a previously-associated Sei account's EVM identity and rebinds the EVM address to a new Sei account. Given `MigrateBalance` moves all spendable coins and wei balance from the direct-cast address to the newly bound `seiAddr` ( [5](#0-4) ), and given the EVM StateDB/JSON-RPC surface, precompiles, and pointer/pointee lookups key off this association to route funds and identity, a hijacked reverse mapping can result in unauthorized transfer of funds associated with that EVM address and permanent loss of EVM identity/state for the original owner — meeting the "unauthorized transfer" / "fund loss" bar.

### Likelihood Explanation
Reachable directly by any transaction sender: `associateAddresses` is invoked by the public `addr` precompile (`Associate`/`AssociatePubKey` methods, callable by any EVM caller) and by every plain EVM transaction through `EVMPreprocessDecorator.AnteHandle` / `HandleAssociateTx`. No privileged role is required — only a valid ECDSA signature recovering to the target `evmAddr`/`seiAddr` pair, which is inherent to the association mechanism's design (self-service association via signed message).

### Recommendation
Before calling `SetAddressMapping`, check `p.evmKeeper.GetSeiAddress(ctx, evmAddr)`; if it is already associated with a Sei address different from `seiAddr`, reject the association (mirroring the existing forward-direction check `GetEVMAddress(ctx, seiAddr)`). Apply this symmetric check in `AssociationHelper.AssociateAddresses` itself (so all callers—precompile, ante decorator, EIP-7702 authority pre-association—are covered) rather than duplicating it in each call site.

### Proof of Concept
1. Account A signs a normal Sei/EVM transaction, causing `SetAddressMapping(ctx, seiA, evmA)` to be recorded and `seiA`'s balance/state to live under `evmA`.
2. A second party constructs an `AssociateTx` (or calls the `addr` precompile's `associate`) with a signature that recovers to `evmA` but a different `seiB` derived from the same signature components (or via the EIP‑7702 authority path noted in `preprocess.go`), where `seiB` itself is not yet associated (so the only existing guard `GetEVMAddress(ctx, seiB)` passes).
3. `HandleAssociateTx`/`associateAddresses` proceeds to call `AssociateAddresses(ctx, seiB, evmA, pubkey, false)`, which calls `SetAddressMapping(ctx, seiB, evmA)`, overwriting `EVMAddressToSeiAddressKey(evmA)` from `seiA` to `seiB` with no check that `evmA` was already claimed by `seiA`.
4. `MigrateBalance` then moves the cast-address (`evmA`-as-AccAddress) balance to `seiB`, and any subsequent EVM/precompile lookup of `evmA` resolves to `seiB`, hijacking `evmA`'s on-chain identity and funds away from `seiA`.

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}

func (k *Keeper) SetAddressMapping(ctx sdk.Context, seiAddress sdk.AccAddress, evmAddress common.Address) {
	store := ctx.KVStore(k.storeKey)
	store.Set(types.EVMAddressToSeiAddressKey(evmAddress), seiAddress)
	store.Set(types.SeiAddressToEVMAddressKey(seiAddress), evmAddress[:])
	if !k.accountKeeper.HasAccount(ctx, seiAddress) {
		k.accountKeeper.SetAccount(ctx, k.accountKeeper.NewAccountWithAddress(ctx, seiAddress))
	}
	ctx.EventManager().EmitEvent(sdk.NewEvent(
		types.EventTypeAddressAssociated,
		sdk.NewAttribute(types.AttributeKeySeiAddress, seiAddress.String()),
		sdk.NewAttribute(types.AttributeKeyEvmAddress, evmAddress.Hex()),
	))
}
