### Title
Copilot merge-conflict resolution writes model-supplied `path`/content without verifying it belongs to the actual conflicted file set - ([File: app/src/lib/stores/app-store.ts])

### Summary
`AppStore._applyCopilotConflictResolutions` writes each `IFileResolution` returned by the Copilot conflict-resolution model directly to disk and `git add`s it, checking only that the resolved path stays inside the repository (`resolveWithin`) and, if the path happens to match a file already present in `workingDirectory.files`, that it isn't a conflict the user already resolved externally. It never validates that `resolution.path` corresponds to one of the files that were actually part of the merge/rebase/cherry-pick conflict set the user reviewed. This mirrors the reported bug class: a validation step compares against the wrong reference value (any working-directory file rather than the specific "conflicted files" set), so the check can silently pass on values it should reject.

### Finding Description
The write path is: [1](#0-0) 

For each `resolution` in `copilotResolutions` (the array returned by the Copilot model, reassembled by `reassembleResolutions` in `app/src/lib/copilot-conflict-resolution.ts`), the code:
1. Resolves `resolution.path` under `repository.path` via `resolveWithin`, which only prevents path traversal outside the repo root [2](#0-1) .
2. Looks up `onDiskFile` in `state.changesState.workingDirectory.files` by `f.path === resolution.path`, and skips the write **only if** that file exists **and** is a conflicted status that has since become externally resolved [3](#0-2) .
3. If `onDiskFile` is `undefined` (i.e., `resolution.path` doesn't match any file currently reported by `git status`), the code falls straight through to `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and stages it with `git add` [4](#0-3) .

There is no check anywhere in this function, or upstream in `reassembleResolutions` [5](#0-4) , that `resolution.path` is a member of the actual conflicted-file set the user was shown in the `ShowCopilotConflicts` dialog. `reassembleResolutions` only requires that `raw.path` match a key in `fileContexts` (the context sent *to* the model) — it does not cross-check against the set of files git reports as unmerged/conflicted at apply time. Because `path` is part of the model's raw JSON output (`IRawFileResolution.path`) [6](#0-5) , it is effectively attacker-influenceable: a merge/rebase/cherry-pick against a hostile branch or PR can include content (commit messages, file contents, or conflict-marker text) designed to manipulate the model (prompt injection) into emitting a resolution for a file path that was never actually conflicted, e.g. `.github/workflows/*.yml`, `package.json`, or any other tracked file the attacker wants altered.

### Impact Explanation
If the model can be steered into returning a resolution for a non-conflicted, non-status-reported path, `_applyCopilotConflictResolutions` will silently overwrite that file's contents on disk and stage it (`git add`) as part of the merge commit — with no diff review specific to that file having been shown to the user in the Copilot conflicts dialog (which only lists the conflicted files, per `CopilotConflictsChanges`/`copilotResolutions` filtering by `conflictedFiles` in `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-changes.tsx`). This is a silent corruption of what the user commits, matching the "silent corruption of what the user commits or pushes" impact bucket: the user believes they are accepting AI-resolved *conflict* content, but an unrelated tracked file could be modified and included in the commit without their awareness, potentially injecting malicious CI config, dependency manifests, or build scripts that later execute with the user's or CI's privileges.

### Likelihood Explanation
Exploitation requires: (1) the victim uses the "Resolve with Copilot" feature on a merge/rebase/cherry-pick against attacker-influenced content (a malicious branch, PR, or upstream commit the user merges), and (2) the LLM can be steered via prompt injection embedded in commit content to emit an out-of-scope `path`. Both preconditions are plausible in the threat model (attacker controls a fetched/merged repository or PR), but reliability depends on LLM susceptibility to injection, which introduces some uncertainty — this is a probabilistic rather than deterministic exploit path, similar in spirit to the original report's slippage-check flaw where the wrong value being compared can cause an incorrect accept/reject outcome depending on runtime state.

### Recommendation
In `_applyCopilotConflictResolutions`, build an explicit allow-list of conflicted file paths (e.g., from `state.changesState.conflictState` / the `conflictedFiles` originally passed into the Copilot resolution flow) and reject/skip any `resolution.path` not present in that set, instead of only consulting `workingDirectory.files` opportunistically. Additionally, `reassembleResolutions` should validate `raw.path` against the same conflicted-file allow-list at reassembly time so an out-of-scope path never reaches the write path at all.

### Proof of Concept
Conceptual PoC (cannot be executed without the Copilot backend, but the logic gap is directly demonstrable from the code):
1. Attacker crafts a branch/PR with a genuine conflicting file (e.g. `README.md`) but embeds instructions or content designed to make the model additionally emit a second `IRawFileResolution` entry with `path: "package.json"` and attacker-chosen `resolvedContent`, even though `package.json` has no conflict.
2. Victim merges the branch and clicks "Resolve with Copilot".
3. `reassembleResolutions` reassembles both entries because it only checks `fileContexts` keyed by path (which the attacker can also seed) — no cross-check against `git`'s actual unmerged-file list.
4. `_applyCopilotConflictResolutions` iterates `copilotResolutions`; for the `package.json` entry, `onDiskFile` lookup in `workingDirectory.files` may not classify it as an unresolved conflict, so the `continue` guard at [7](#0-6)  is never hit, and `writeFile` + `git add` execute unconditionally at [8](#0-7) .
5. The victim's next commit silently includes the attacker's `package.json` changes.

Note: I was unable to fully trace the exact contents/validation performed inside `copilot-store.ts` or the system prompt sent to the model (only partial context was retrievable), so I cannot confirm with certainty how strongly the model is constrained to the conflicted-file set before this point — this should be verified directly in a live session for a complete assessment.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
