### Title
`ThresholdKeys::read` deserializes semantically invalid threshold keys — no `secret_share`/verification-share consistency check and identity shares admitted — (File: crypto/dkg/src/lib.rs)

### Summary
The external report describes unsafe deserialization: untrusted structured input accepted without validation of the security-relevant invariants it is supposed to satisfy. Serai's analog is `ThresholdKeys::read` in `crypto/dkg/src/lib.rs`, which reconstructs `ThresholdKeys` — the root of trust for all FROST signing — purely from attacker-shapable bytes. The reader validates only that scalars are canonical (`C::read_F`) and points are canonical encodings (`Ciphersuite::read_G`, which explicitly does *not* reject the identity point, unlike `Curve::read_G`), plus parameter sanity in `ThresholdParams::new`. It never checks that `secret_share * G == verification_shares[i]`, never rejects a zero `secret_share`, and never rejects identity verification shares. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`ThresholdKeys::read` accepts:
1. `t, n, i` validated only by `ThresholdParams::new` (nonzero, `t <= n`, `i <= n`),
2. an interpolation tag (Constant vector of `n` scalars, or Lagrange),
3. an arbitrary `secret_share` scalar — including zero — and
4. `n` verification-share points read via `Ciphersuite::read_G`, which admits the identity point.

`ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) checks only the count/index range of `verification_shares` and derives `group_key = Σ_{i=1..=t} verification_shares[i] * λ_i`. There is no proof, anywhere in the deserialization path, that `secret_share` is consistent with `verification_shares[i]` (`G * secret_share == verification_shares[i]` is never evaluated). The code itself acknowledges the resulting state is possible: `complete()` in `crypto/frost/src/sign.rs:491-494` ends with an `InternalError` reachable only by "deserializ[ing] a semantically invalid FrostKeys".

Concrete attack shape: an attacker supplies a serialized `ThresholdKeys` where
- `secret_share = s_a` and `verification_shares[i] = G * s_a` are attacker-chosen, and
- the remaining verification shares are points `X_j = G * x_j` whose discrete logs the attacker also knows (or sets to identity).

The derived `group_key` is then `Σ λ_i * (attacker-known scalars) * G` — a key whose discrete logarithm is fully known to the attacker. Because every subsequent step (`view()`, `group_key()`, `secret_share()`) trusts the deserialized structure, the victim participant proceeds to run FROST `sign_share` (`crypto/frost/src/algorithm.rs:201-211`) and `complete` under this group key, and the produced signatures verify correctly — against a group key the attacker could have signed for alone. ### Impact Explanation
Threshold security is silently voided: the victim believes they hold one share of a t-of-n multisig, but the group key's discrete log is known to the attacker (or is identity for an all-identity verification-share vector). Consequences:

- Any funds/outputs locked to `group_key()` (e.g., the Taproot key produced by `tweak_keys`/`p2tr_script_buf` in `networks/bitcoin/src/wallet/mod.rs:46-86`) are spendable by the attacker unilaterally — the victim's signature adds no security.
- The victim will sign arbitrary messages during the FROST protocol whose resulting signatures are valid under a key it does not control — i.e., the participant attests on behalf of an attacker-owned "multisig".
- A milder variant (`secret_share` inconsistent with `verification_shares[i]` only) makes the victim emit invalid shares, letting the attacker selectively trigger blame/`InternalError` paths.

This matches the accepted impact classes: an incorrect verifier outcome (signatures valid under a key with no real threshold backing) and funds received that are not spendable by the group (they are spendable solely by the attacker). [7](#0-6) 

### Likelihood Explanation
`ThresholdKeys::read` is explicitly among the untrusted-input surfaces for this codebase (serialized keys crossing trust boundaries: key export/import, backup restoration, recovery/reshare flows, coordinator-supplied key material). The only code cost is crafting canonical scalars and points — trivially satisfiable. The attack requires no cryptographic break, no collusion among honest participants, and no privileged position: whoever controls the serialized bytes fully controls the resulting "threshold" key. Severity is gated only by whether the deployment treats serialized `ThresholdKeys` as trusted local state; any path where these bytes originate outside the node's own key-generation output is exploitable.

### Recommendation
In `ThresholdKeys::read` (or `ThresholdKeys::new`, so all constructors benefit):
- Reject `secret_share == 0` and reject identity `verification_shares` (use `Curve::read_G` semantics, or an explicit `is_identity` check).
- Verify `C::generator() * secret_share == verification_shares[&params.i()]` and return an error otherwise.
- Optionally verify the interpolation/Constant coefficients are non-trivially consistent (e.g., reject all-zero coefficient vectors that force `group_key` to identity, and reject `group_key.is_identity()`).

### Proof of Concept
```rust
// Construct a semantically valid-by-parsing but attacker-controlled ThresholdKeys.
// n = t = 2; victim is participant 1.
let s_a = Scalar::from(7u64);          // attacker-chosen "secret share" for victim
let x_2 = Scalar::from(9u64);          // attacker-known discrete log for share 2
let x_1 = s_a;                         // vs[1] = G * s_a (consistent-looking)
let vs1 = ProjectivePoint::GENERATOR * x_1;
let vs2 = ProjectivePoint::GENERATOR * x_2;
// group_key = λ1*vs1 + λ2*vs2 = G*(λ1*x_1 + λ2*x_2) -> discrete log known to attacker.

// Serialize per ThresholdKeys::write layout: ID, t=2, n=2, i=1, Lagrange tag=1,
// secret_share=s_a, then vs1, vs2 -> ThresholdKeys::read accepts it with no error.
```
The accepted `ThresholdKeys` yields `group_key()` with attacker-known discrete log; `view([1,2]).secret_share()` and the FROST machines then sign normally. Caveat: I verified the parsing/validation gap and the downstream trust of the deserialized fields, but did not trace every Serai deployment path that feeds external bytes into `ThresholdKeys::read` — exploitability depends on such a path existing (e.g., key recovery or coordinator-distributed key material).

        Err(different())?;
      }

      let mut id = vec![0; C::ID.len()];
      reader.read_exact(&mut id)?;
      if id != C::ID {
        Err(different())?;
      }
    }

    let (t, n, i) = {
      let mut read_u16 = || -> io::Result<u16> {
        let mut value = [0; 2];
        reader.read_exact(&mut value)?;
        Ok(u16::from_le_bytes(value))
      };
      (
        read_u16()?,
        read_u16()?,
        Participant::new(read_u16()?).ok_or(io::Error::other("invalid participant index"))?,
      )
    };

    let mut interpolation = [0];
    reader.read_exact(&mut interpolation)?;
    let interpolation = match interpolation[0] {
      0 => Interpolation::Constant({
        let mut res = Vec::with_capacity(usize::from(n));
        for _ in 0 .. n {
          res.push(C::read_F(reader)?);
        }
        res

      1 => Interpolation::Lagrange,
      _ => Err(io::Error::other("invalid interpolation method"))?,
    };

      verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
    }

    ThresholdKeys::new(
      ThresholdParams::new(t, n, i).map_err(io::Error::other)?,
      interpolation,
      secret_share,
      verification_shares,
    )

  }

  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
    reader.read_exact(encoding.as_mut())?;

    let point = Option::<Self::G>::from(Self::G::from_bytes(&encoding))
      .ok_or_else(|| io::Error::other("invalid point"))?;
    if point.to_bytes().as_ref() != encoding.as_ref() {
      Err(io::Error::other("non-canonical point"))?;
    }
    Ok(point)
  }
