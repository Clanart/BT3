**Reasoning:** The stored `record.head.sha` (from `storePullRequests` at `app/src/lib/stores/pull-request-store.ts:312`) flowing into `PullRequestRef` construction in `getAll` (`app/src/lib/stores/pull-request-store.ts:194`) is never used to select which commit gets fetched or checked out.

The actual checkout path, `_checkoutPullRequest` → `_findPullRequestBranch` in `app/src/lib/stores/app-store.ts:8613-8721`, works entirely off the PR's `headRefName` and `headCloneUrl`/`headRepoOwner`, not the SHA: [1](#0-0) 

It adds/finds a remote, looks for a local/remote branch by name, and if not found performs a live `git fetch` (`_fetchRemote`) against that remote, then checks out whatever the remote branch tip is at fetch time. The tip commit checked out is therefore always the actual current tip of the fork's branch as observed via `git fetch`, never the cached `pr.head.sha` value from the database.

The stored `head.sha` is only consumed for auxiliary/display purposes such as building `refs/pull/<n>/head`-style commit refs for CI-check lookups and notification text (`getPullRequestCommitRef` in `app/src/models/pull-request.ts:4-6`, and its use in `app/src/lib/stores/notifications-debug-store.ts:206-225`), not for any checkout/diff/fetch decision: [2](#0-1) [3](#0-2) 

So even if the GitHub API returned a `pr.head.sha` that didn't match the fork branch's real tip, the persisted mismatch would at worst cause a stale/incorrect SHA to be displayed or used for a CI-status lookup — it does not corrupt what is actually fetched or checked out, since that always comes from a fresh `git fetch` of the named branch. No code execution, unintended file read/write outside the repo, credential exfiltration, or silent corruption of committed/pushed content results from this. This does not meet the bounty's valid-impact criteria.
