### Title
`Verifier::sign_optimistic_payout` never binds `output_amount` to the Citrea-recorded withdrawal amount, allowing payout up to `bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT` regardless of the amount actually withdrawn - ([File: core/src/verifier.rs])

### Summary
`Verifier::sign_optimistic_payout` enforces only two constraints on the requested payout: a static protocol-wide ceiling (`output_amount <= bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT`) and equality of the input outpoint (`withdrawal_utxo == input_outpoint`). Neither check ties `output_amount` to the amount that was actually recorded/authorized for that specific withdrawal, so the co-signed move-to-vault spend can pay out far more than the registered withdrawal amount.

### Finding Description
The binding that should hold is: `output_amount == withdrawal_amount_recorded_by_citrea_for(deposit_id)`.

In `Verifier::sign_optimistic_payout`: [1](#0-0) 
only checks `output_amount` against the fixed protocol parameter `bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT`, not against any Citrea-recorded amount for `deposit_id`. [2](#0-1) 
then only checks that the *outpoint* `withdrawal_utxo` fetched via `get_withdrawal_utxo_from_citrea_withdrawal(None, deposit_id)` equals `input_outpoint` — an identity check on which UTXO is being spent as the authorization input, not a check on the destination amount or script.

The verifier then builds the payout output directly from the caller-supplied `output_amount`/`output_script_pubkey` and computes the sighash the co-signing verifiers will sign over: [3](#0-2) 

The only place `output_amount` and `output_script_pubkey` are cross-checked against anything external is the optional ECDSA "verification signature" path, gated behind `self.config.aggregator_verification_address` being configured: [4](#0-3) 
This is an operator/deployment-configurable, optional guard — not a protocol invariant enforced unconditionally by the code, and it checks an aggregator-controlled ECDSA key's approval, not the amount Citrea's Bridge contract recorded for the withdrawal.

No code in this function (nor anywhere reachable from it that I could locate) fetches the amount that Citrea's Bridge contract associated with the specific withdrawal (`deposit_id`/withdrawal index) and compares it to `output_amount`. The withdrawal-UTXO-outpoint check only proves that whoever supplied `input_signature` controls the private key of the UTXO that was registered as the withdrawal's authorization input; it does not prove, nor does the code check, that the payout amount matches what was actually committed/burned on Citrea for that withdrawal.

### Impact Explanation
If `aggregator_verification_address` is not configured (which is the deployment-optional case), the party who registered a withdrawal for a small amount `X` and controls the withdrawal UTXO's private key can request `output_amount` up to `bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT` and have the verifiers co-sign a move-to-vault spend for that inflated amount. This is BTC leaving a move-to-vault UTXO without a matching fronted/recorded withdrawal amount — the Critical impact category defined in scope. This is repeatable per-deposit for every withdrawal whose registered amount is smaller than the protocol ceiling.

### Likelihood Explanation
Preconditions: the attacker must be able to register a withdrawal on Citrea (an unprivileged, standard user action) for a small amount and must control the corresponding withdrawal UTXO's signing key (which they naturally do, as it's their own withdrawal). The check that would prevent the attack — comparing `output_amount` to the Citrea-recorded withdrawal amount — is absent unconditionally, and the only mitigating check (`aggregator_verification_address`) is optional configuration, not a code-level invariant. This makes the attack feasible with normal transaction fees whenever that optional verification address is unset.

### Recommendation
Fetch the withdrawal amount recorded by Citrea's Bridge contract for `deposit_id`/withdrawal index (in addition to the outpoint) and require `output_amount == recorded_withdrawal_amount` (accounting for fixed anchor/fee deductions), instead of only bounding `output_amount` by the protocol-wide `bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT` ceiling.
