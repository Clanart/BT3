## Title
Untrusted repository content can hijack the Git credential trampoline to exfiltrate stored GitHub tokens - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The reported bug class is a privileged operation (minting loot) reachable by any caller because the function performing it never checks who/what is invoking it. The same broken invariant exists in GitHub Desktop's Git credential trampoline: any process spawned as part of a Git operation — including a filter/clean/smudge/hook process defined by an **attacker-controlled cloned or fetched repository** — inherits the environment needed to talk to Desktop's local trampoline socket, and the trampoline's credential handler grants GitHub credentials to whoever asks for `https://github.com` without verifying that the request actually originates from the Git operation on the intended remote.

### Finding Description
When Desktop runs any Git command that might need authentication, it wraps the call in `withTrampolineEnv`, which sets `GIT_CONFIG_PARAMETERS` to globally enable `credential.helper=desktop` and provides `DESKTOP_PORT` / `DESKTOP_TRAMPOLINE_TOKEN` in the environment [1](#0-0) . The comment in the code explicitly notes this is done via environment variables (not command-line args) specifically **so that subprocesses invoked by Git filters (e.g. Git LFS) also inherit the credential helper configuration**, since "arguments passed to git commands are not passed down to filters" [2](#0-1) .

This means any custom `.gitattributes` filter/clean/smudge driver, or any hook (`post-checkout`, `post-merge`, etc.) defined inside a repository that Desktop clones or fetches, runs with `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN` in its environment, and with `credential.helper=desktop` globally configured for that process tree.

The trampoline server accepts a connection on `127.0.0.1` and dispatches the command to a registered handler as long as the token is a currently-valid (recently issued) trampoline token — it performs no check on which process, executable, or repository is making the request [3](#0-2) .

The `CredentialHelper` handler, on a `get` command, resolves credentials purely by matching the requested URL's origin against a stored account's endpoint:

```
async function getGitHubCredential(cred: Credential, store: AccountsStore) {
  const endpoint = `${getCredentialUrl(cred)}`
  const account = await findGitHubTrampolineAccount(store, endpoint)
  ...
``` [4](#0-3) 

`findGitHubTrampolineAccount` simply compares the origin of the *caller-supplied* URL to the account's endpoint host, with no binding to the repository/remote that the outer Git operation is actually working with [5](#0-4) . There is no cross-check that the `get` request came from the actual `git fetch/clone/push` subprocess that Desktop itself spawned toward that same remote, versus a filter/hook process spawned as a side effect of processing repository content.

The broken invariant: **"only the Git process performing the operation on the repository's declared remote should receive credentials for that remote."** Nothing enforces this — any code path that can read the trampoline environment (any subprocess of the git invocation, which includes attacker-supplied filter/hook scripts) can independently open a TCP connection to `127.0.0.1:$DESKTOP_PORT`, send a `CREDENTIALHELPER get` command for `protocol=https\nhost=github.com`, and receive the user's real GitHub username/token pair, exactly as if it were the legitimate Git subprocess.

### Impact Explanation
A successful exploitation silently exfiltrates the victim's GitHub account credentials (their stored OAuth/PAT token) to arbitrary code embedded in a cloned/fetched repository, without any user interaction beyond the normal clone/fetch/checkout that Desktop already performs automatically. This is a severe, unprivileged, remote-triggerable credential theft — comparable in severity to the original report's unrestricted minting, since the attacker (a malicious repo owner) can repeatedly and silently obtain valid credentials belonging to any Desktop user who opens their repository.

### Likelihood Explanation
Any Git operation Desktop performs automatically on a newly added/cloned repository (fetch, checkout, background fetch) can trigger filter/hook execution if the repository defines a `.gitattributes` filter or is configured with hooks that are honored (note: Desktop does still invoke `clean`/`smudge` filters and LFS filters as part of normal checkouts, which is the exact scenario the `GIT_CONFIG_PARAMETERS` comment calls out). Because the token is short-lived but valid for the whole duration of the outer Git operation and the whole environment is inherited, no race condition or brute-forcing is required — the filter process reads `DESKTOP_TRAMPOLINE_TOKEN` directly from its environment.

### Recommendation
Bind trampoline credential/askpass responses to the specific Git invocation context (e.g., pass and validate an expected remote/host and repository path alongside the token, and reject `get` requests whose host does not match the operation-specific expected remote passed to `withTrampolineEnv`). Additionally, consider not exposing `credential.helper=desktop` to filter/hook subprocesses at all, or issuing distinct, purpose-scoped tokens for the primary Git process vs. filters, so a filter/hook cannot request credentials for hosts unrelated to the current operation.

### Proof of Concept
1. Attacker publishes a public repository containing a `.gitattributes` entry, e.g.:
   ```
   * filter=exfil
   ```
   and repo-local `.git/config` (or a `pre-commit`/`post-checkout` hook) defining:
   ```
   [filter "exfil"]
       clean = /bin/sh -c 'exfil.sh'
   ```
   where `exfil.sh` reads `DESKTOP_PORT` / `DESKTOP_TRAMPOLINE_TOKEN` from its environment, connects to `127.0.0.1:$DESKTOP_PORT`, and sends a trampoline `CREDENTIALHELPER get` command with `protocol=https\nhost=github.com\n\0`.
2. Victim clones or fetches this repository in GitHub Desktop, which triggers `withTrampolineEnv` around the Git invocation, exporting `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` and setting `credential.helper=desktop` globally [1](#0-0) .
3. Git invokes the `clean` filter as part of checking out files, running `exfil.sh` with the inherited environment.
4. `exfil.sh` connects to the trampoline server; `processCommand` validates only that the token is currently valid, not who is asking [6](#0-5) .
5. `createCredentialHelperTrampolineHandler`'s `get` path calls `getCredential` → `getGitHubCredential` → `findGitHubTrampolineAccount`, matching the attacker-supplied `host=github.com` to the victim's real GitHub account and returning the account's login/token via `formatCredential` [7](#0-6) .
6. `exfil.sh` receives the plaintext credential and exfiltrates it over the network.

  private async processCommand(socket: Socket, command: ITrampolineCommand) {
    if (!isValidTrampolineToken(command.trampolineToken)) {
      throw new Error('Tried to use invalid trampoline token')
    }

    const handler = this.commandHandlers.get(command.identifier)

    if (handler === undefined) {
      socket.end()
      return
    }

    const result = await handler(command).catch(e =>
      log.error('Error processing trampoline command', e)
    )

    if (result !== undefined) {
      socket.end(result)
    } else {
      socket.end()
    }
  }

  const firstParameter = command.parameters.at(0)
  if (!firstParameter) {
    return undefined
  }

  const { trampolineToken: token } = command

  if (__DEV__) {

        .replaceAll(/^(.*)$/gm, '  $1')
        .trimEnd()}`
    )

        setHasRejectedCredentialsForEndpoint(token, endpoint)

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
