### Title
Cross-shop session hijack via unauthenticated `shop` param in legacy `EnsureInstalled` flow - ([File: app/controllers/concerns/shopify_app/ensure_installed.rb])

### Summary
The reported bug class is: a piece of claimed identity/correlation data (the `BeaconBlockHeader`, containing `ProposerIndex`) is trusted and used to drive protocol logic without being cross-checked against an authenticated/signed source of truth for that identity. The closest reachable analog in `shopify_app--017`'s legacy (non–token-exchange) authentication path is `ShopifyApp::EnsureInstalled#current_shopify_domain`, which derives the shop identity purely from the unauthenticated `params[:shop]` query parameter and uses it to look up and activate that shop's stored offline session — without requiring any signed proof (JWT, HMAC, or session cookie) that the requester is actually that shop.

### Finding Description
`current_shopify_domain` is computed directly from the request parameter, with no signature or session-token verification: [1](#0-0) 

This value is then used to fetch the shop's persisted session (containing its offline access token) from the session store: [2](#0-1) 

`check_shop_known` assigns `@shop` from that lookup with no correlation to any authenticated identity of the caller: [3](#0-2) 

The only subsequent check, `validate_non_embedded_session`, merely confirms the *retrieved* session's stored access token still works against Shopify's API — it does not verify that the *current request* is authorized to act as that shop: [4](#0-3) 

This mirrors the reported bug class exactly: an unsigned identity claim (`params[:shop]`, analogous to the unvalidated `BeaconBlockHeader`/`ProposerIndex`) is accepted and used to drive privileged behavior (loading and using another shop's access token) without correlating it against a verified/signed counterpart (a session cookie, JWT `dest` claim, or HMAC-signed Shopify Admin load parameters).

By contrast, the newer token-exchange path (`ShopifyApp::TokenExchange`) does perform this correlation correctly via `reject_mismatched_requested_shopify_domain`, comparing the requested shop against the shop authenticated by the verified JWT: [5](#0-4) 
No equivalent check exists in the `EnsureInstalled`/legacy branch.

### Impact Explanation
Any anonymous requester who knows or guesses a victim shop's `.myshopify.com` domain (these are often guessable/enumerable, e.g., via storefront) can hit an app route protected by `EnsureInstalled` (non–token-exchange configuration) with `?shop=<victim>.myshopify.com`. If that shop has previously installed the app (session already stored), the controller loads and uses the victim's persisted offline access token for subsequent Admin API calls performed on behalf of "the current request" (e.g., rendering shop data, product listings, or any authenticated action in the app), effectively achieving cross-shop access/session theft without ever presenting a valid session cookie or JWT.

### Likelihood Explanation
This is only reachable when an app is configured to use the legacy (non `use_new_embedded_auth_strategy?`) flow, which remains a fully supported and still-default-in-many-apps configuration path in this gem. It requires no secret knowledge, no valid session token, and no CSRF bypass — just an anonymous HTTP GET with a `shop` query parameter, making it directly reachable from an anonymous or unrelated-merchant request as required by the validation rules.

### Recommendation
In the legacy `EnsureInstalled` flow, do not derive the acting shop identity solely from `params[:shop]`. Require it to be corroborated by a signed source (e.g., the Shopify-signed `host`/`hmac`/`session` parameters from an Admin embed, or an existing session cookie bound to that shop) before loading and using the shop's stored offline access token. At minimum, reject any request where an unauthenticated `shop` param is used to activate a session without first establishing (via signed embed parameters or an existing authenticated session) that the request actually originates from that shop's Admin context.

### Proof of Concept
1. Attacker learns that `victim-shop.myshopify.com` has installed a `shopify_app`-based app that uses the legacy (non-token-exchange) `EnsureInstalled` flow.
2. Attacker sends `GET /<app_route>?shop=victim-shop.myshopify.com` directly (not embedded in Shopify Admin, no valid session cookie, no JWT).
3. `check_shop_domain` passes because `current_shopify_domain` resolves from `params[:shop]` alone.
4. `check_shop_known` sets `@shop = installed_shop_session`, loading `victim-shop`'s persisted offline session/access token from `SessionRepository`.
5. `validate_non_embedded_session` confirms the token is valid by calling the Shopify Admin API with it, then allows the request through — the attacker's action now executes using the victim shop's access token/session context.
