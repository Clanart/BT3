## Reduced invariant from the source report

The Sherlock finding trusted a live, externally-mutable value (`balanceOf(account)`) instead of an internally-tracked, validated value (`stakingAccount.stakeTokenBalances[...].stakeAmount`) to make an accounting decision. Because the external value could be freely moved between accounts the attacker controls, the protocol could be made to silently apply the wrong (attacker-favorable) value at the moment of use.

The GitHub Desktop analog of this class is: **trusting a live, externally-supplied value from an untrusted source (a GitHub API response) instead of validated/pinned repository configuration, and silently applying it to security-relevant local state** — here, the git remote URL used for all future pushes/fetches/credential handling.

### Title
Silent remote URL takeover via spoofed GitHub API `clone_url` in `updateRemoteUrl` - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`repositoryWithRefreshedGitHubRepository` in `app-store.ts` fetches repository metadata from the GitHub API and feeds the API's `clone_url` field directly into `updateRemoteUrl`, which will silently rewrite the user's `origin` remote to that URL with no confirmation dialog, as long as a same-protocol heuristic passes. If the API response (or the account's GHES endpoint) is attacker-influenced, this becomes a silent redirection of all future `git push`/`git fetch` traffic — and the credentials sent with them — to an attacker-controlled host.

### Finding Description
`repositoryWithRefreshedGitHubRepository` fetches the repository from the API and unconditionally passes the returned object into `updateRemoteUrl`: [1](#0-0) 

`updateRemoteUrl` then compares the *current* remote against the *previously cached* `gitHubRepository.cloneURL` — not against a cryptographic or otherwise non-spoofable identity — and, if they still match ("remoteUrlUnchanged") and the protocol scheme superficially matches, calls `gitStore.setRemoteURL` with the brand-new `apiRepo.clone_url` value with **no user prompt**: [2](#0-1) 

The safety checks are weak by construction:
- `protocolsMatch` only compares the URL scheme string (`https` vs `https`, or both null for `git@`-style SSH), not host or owner/name.
- `remoteUrlUnchanged` only confirms the user hasn't manually edited the remote since the *last* time Desktop wrote it — it does nothing to validate that the *new* value came from a trustworthy source.
- There is no confirmation dialog, diff view, or any user-visible signal that the remote is about to change.

This function is reachable any time Desktop refreshes GitHub metadata for a repo — after fetch/pull, account refresh, or periodic background refresh — via `repositoryWithRefreshedGitHubRepository`, which is called from `refreshSelectedRepositoryAfterAccountChange` and from `withRefreshedGitHubRepository` used by fetch/pull flows. The unit tests confirm the intended behavior is exactly "update remote URL whenever GitHub reports a new `clone_url`": [3](#0-2) 

The `IAPIRepository.clone_url` field itself is nothing more than a string returned from the endpoint response — the report's "GitHub API object" attacker-controlled input: [4](#0-3) 

**Why existing guards don't stop this:** GitHub Desktop pins repositories to accounts/endpoints but does not pin or verify that a `clone_url` change corresponds to a legitimate rename/transfer versus a spoofed/hostile response (e.g., a compromised or on-path GitHub Enterprise Server the account is configured against, a compromised proxy performing TLS termination that the user has been socially engineered into trusting, or a GHES admin-level compromise). None of that requires local machine access, malware, or leaked user credentials — only that the attacker can influence what the configured API endpoint returns for this one field, which is exactly the "attacker controls a GitHub API object" scenario named as in-scope.

### Impact Explanation
Silently repointing `origin` means:
- All subsequent `git push` operations (and the credentials sent for authentication over HTTPS, or the SSH host key negotiation) go to the attacker's endpoint instead of the real one — this is the direct analog of "silent corruption of what the user commits or pushes."
- Because Desktop also uses this remote for `fetch`, an attacker-controlled remote can subsequently serve poisoned refs/objects to the victim on the next fetch, without ever showing a prompt.
- No commit content is altered on disk, so there's no diff for the user to notice; the compromise is entirely in the network destination, discoverable only by manually inspecting `git remote -v`.

### Likelihood Explanation
The change is only gated by matching URL scheme and "did the user manually edit the remote since we last touched it," both of which are trivially satisfiable by a spoofed API response carrying the same scheme (e.g., `https://`) with a different host/owner. The refresh path runs automatically in the background on ordinary Desktop usage (account refresh, fetch/pull), so no unusual user action is required beyond normal use of the app while pointed at a compromised/malicious endpoint.

### Recommendation
- Never silently rewrite an existing, user-visible remote URL. At minimum, surface a confirmation dialog showing old vs. new URL before calling `setRemoteURL`.
- Strengthen the match criteria beyond protocol-scheme string equality — validate host/owner/name identity against the previously known-good, persisted `GitHubRepository` record, and require an explicit user action (or a strongly authenticated signal such as a documented repository transfer event) before switching hosts.
- Treat `clone_url` from the API as sensitive input requiring the same scrutiny as any other externally-supplied trust-affecting value, per the same principle the ELF Protocol fix applied (rely on already-verified/tracked state rather than a live, spoofable external read at time-of-use).

### Proof of Concept
1. Victim has an account configured against a GitHub Enterprise Server endpoint (or any environment where the attacker can influence responses from the account's API endpoint, e.g., a malicious/compromised proxy sitting in front of that endpoint).
2. Victim opens a repository in Desktop whose `origin` currently matches the endpoint's real `clone_url` for `owner/repo`.
3. Attacker arranges for a subsequent `GET repos/{owner}/{name}` response (triggered by Desktop's periodic/automatic refresh, e.g. `repositoryWithRefreshedGitHubRepository` called after a fetch/pull or account refresh) to return the same scheme but a different host/path in `clone_url`, e.g. `https://attacker.example/owner/repo.git`.
4. `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true` (user hasn't touched the remote), `urlsMatch === false`, and calls `gitStore.setRemoteURL('origin', 'https://attacker.example/owner/repo.git')` with no prompt: [5](#0-4) 
5. The victim's next `git push`/`git fetch` from Desktop silently targets `attacker.example`, sending credentials and/or receiving attacker-controlled history without any warning shown in the UI.

Note: exploitability depends on the attacker's ability to influence the specific API endpoint's response for this field (e.g., a compromised/malicious GHES instance or an on-path proxy for that endpoint) — I could not find any signature/allow-list verification of `clone_url` elsewhere in the reachable code paths that would prevent this once such response manipulation is achievable.

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
