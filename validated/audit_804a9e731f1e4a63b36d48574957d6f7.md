Confirmed: `EvmHost.withdraw` at [1](#0-0)  performs no zero-address (or any address sanity) check on `params.beneficiary` before transferring native token or ERC20 — this is the exact analog of the `_updateFeeWallet` bug class.

### Title
No validation of the withdrawal beneficiary address allows protocol fees to be irrecoverably burned - (File: evm/src/core/EvmHost.sol)

### Summary
The cross-chain fee-withdrawal path (`pallet-ismp-host-executive::withdraw` → `HostManager.onAccept` → `EvmHost.withdraw`) never validates that the beneficiary address is non-zero or otherwise capable of receiving funds. A malformed or mistaken beneficiary value silently burns the withdrawn protocol revenue with no recovery path, exactly mirroring the reported `_updateFeeWallet` bug class (missing address validation causing "funds to become irretrievable").

### Finding Description
On the Substrate side, `pallet_ismp_host_executive::Pallet::withdraw` takes a caller-supplied `WithdrawalParams { beneficiary_address: Vec<u8>, amount, ... }` and only requires `T::HostExecutiveOrigin` authorization — it performs no check that `beneficiary_address` is non-zero: [2](#0-1) 

The SCALE→ABI conversion in `WithdrawalParams::abi_encode` (via `TryFrom<&WithdrawalParams> for WithdrawParamsAbi`) only validates that the byte slice is exactly 20 bytes long — it explicitly does not reject the all-zero address: [3](#0-2)  A 20-byte all-zero `beneficiary_address` passes this check cleanly, as confirmed by the accompanying unit tests which only assert on length, never on the zero value: [4](#0-3) 

The message is then dispatched to the EVM `HostManager`, which forwards it unchecked to `IHostManager(_params.host).withdraw(withdrawParams)`: [5](#0-4) 

Finally, `EvmHost.withdraw` executes the transfer with zero validation on `params.beneficiary`: for the native-asset case it does `params.beneficiary.call{value: params.amount}("")`, which succeeds trivially when sent to `address(0)` (a call with no code always "succeeds"), and for ERC20 it calls `safeTransfer(params.beneficiary, params.amount)`, which also succeeds when the recipient is the zero address (most ERC20s, including OpenZeppelin's, don't block transfers to `address(0)` from a `transfer` call initiated by the token holder): [1](#0-0) 

Unlike `updateHostParamsInternal`, which does validate `hostManager`, `handler`, and `consensusClient` against `address(0)` and code-existence before writing them: [6](#0-5)  — no equivalent guard exists anywhere in the withdrawal path for the beneficiary address.

### Impact Explanation
Any withdrawal dispatched with a zero (or otherwise unrecoverable) beneficiary permanently burns the withdrawn amount of protocol/bridge revenue — direct, irreversible loss of funds, matching the "stealing or loss of funds" impact category. Because `EvmHost.withdraw`'s only guard is `restrict(_hostParams.hostManager)` (i.e., it trusts whatever the cross-chain governance message carries), and neither the pallet, the ABI-conversion layer, nor the EVM contract sanity-checks the beneficiary, a single malformed extrinsic argument (e.g., an uninitialized/zeroed input in tooling, a scripting bug, or a copy-paste error) is enough to destroy funds with no on-chain recovery mechanism.

### Likelihood Explanation
The path requires `HostExecutiveOrigin` (governance/admin) to submit the withdrawal, so this cannot be triggered by an arbitrary unprivileged attacker — it is analogous in trust level to the original `_updateFeeWallet` finding, which was also admin-triggered and rated Low severity for the same reason. The likelihood of an admin-supplied zero/invalid beneficiary is non-trivial precisely because nothing in the stack (pallet, ABI encoder, or contract) stops it, unlike the adjacent `hostManager`/`handler`/`consensusClient` fields which are defensively checked.

### Recommendation
Add explicit non-zero (and, on EVM, code-existence-appropriate) validation of the beneficiary address at the earliest point in the flow — ideally in `pallet_ismp_host_executive::withdraw` before dispatch, and defensively again in `EvmHost.withdraw` (mirroring the `address(0)` / code-length checks already used for `hostManager`, `handler`, and `consensusClient` in `updateHostParamsInternal`).

### Proof of Concept
1. `HostExecutiveOrigin` calls `pallet_ismp_host_executive::Pallet::withdraw(origin, StateMachine::Evm(chain), WithdrawalParams { beneficiary_address: vec![0u8; 20], amount: X, token: H160::zero() })`.
2. `WithdrawalParams::abi_encode` succeeds (`beneficiary_address.len() == 20`), producing an ABI-encoded `WithdrawParams { beneficiary: address(0), amount: X, token: address(0) }`.
3. The ISMP POST is delivered to `HostManager.onAccept`, which decodes the `Withdraw` action and calls `EvmHost.withdraw(withdrawParams)` — passing the `restrict(_hostParams.hostManager)` check since the call originates from the authorized `hostManager`.
4. `EvmHost.withdraw` executes `address(0).call{value: X}("")`, which returns `sent = true` (a call to an address with no code always succeeds), silently burning `X` native tokens with `HostWithdrawal` emitted showing `beneficiary = address(0)` and no error raised anywhere in the flow.

        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});

impl TryFrom<&WithdrawalParams> for WithdrawParamsAbi {
	type Error = WithdrawalParamsError;

	fn try_from(value: &WithdrawalParams) -> Result<Self, Self::Error> {
		// Reject anything that isn't exactly a 20-byte EVM address.
		if value.beneficiary_address.len() != 20 {
			Err(WithdrawalParamsError::InvalidBeneficiaryAddressLength(
				value.beneficiary_address.len(),
			))?;
		}
		let beneficiary = H160::from_slice(&value.beneficiary_address[..]);

		Ok(WithdrawParamsAbi {
			beneficiary: beneficiary.0.into(),
			amount: alloy_primitives::U256::from_be_bytes(value.amount.to_big_endian()),
			token: value.token.0.into(),
		})
	}
}
