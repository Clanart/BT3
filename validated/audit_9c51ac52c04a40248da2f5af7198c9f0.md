The `EvmHost.dispatch(DispatchGet)` path swaps native tokens for the exact fee-token amount via `swapETHForExactTokens` with **no caller-controllable minimum output / no way to bound the input amount actually spent** in a way that protects the payer against price manipulation — this mirrors the "missing minimum output amount" bug class from the SEuroOffering report, just inverted (missing max-input / min-output protection on a Hyperbridge fee-swap path).

### Title
Unbounded native-token spend in `EvmHost.dispatch(DispatchGet)` due to missing slippage/output protection on the Uniswap swap - (`evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchGet)` swaps the caller's entire `msg.value` for an exact `get.fee` amount of the fee token using `swapETHForExactTokens`, exactly the same "trust the router with no minimum-output/maximum-input guard chosen by the caller" pattern flagged in the external report for `SEuroOffering.swap()`/`swapETH()`.

### Finding Description
In `dispatch(DispatchGet)`, when `msg.value > 0`, the host builds a WETH→feeToken path and calls the Uniswap V2 router directly: [1](#0-0) 
There is no caller-supplied minimum-output or maximum-input bound on this swap beyond the amount of ETH sent as `msg.value`. The router uses `swapETHForExactTokens`, so the exact fee-token output is guaranteed, but the amount of native ETH actually consumed to obtain that output is entirely determined by pool price at execution time — the function silently refunds nothing, and does not let the caller specify a maximum ETH they are willing to spend for `get.fee` beyond the raw `msg.value` supplied. This is essentially the same class of missing-slippage-protection code path as `SEuroOffering.swap()`: the function derives amounts to move/mint purely from an oracle-like source (here, on-chain AMM price) at the time of execution, with no explicit user-set bound checked by a `require`.

By contrast, other swap paths in this same codebase (`SimplexPaymaster.swapAndDeposit`, the intent gateway's Uniswap-integrated predispatch/postdispatch tests) explicitly compute an oracle-derived `amountOutMin` and enforce it on-chain: [2](#0-1) 
This shows the project is aware of the slippage-protection pattern and applies it elsewhere, but `EvmHost.dispatch(DispatchGet)` (and its POST-dispatch counterpart) does not apply the same pattern — the caller cannot bound how much ETH is consumed relative to fee-token output beyond what they send as `msg.value`, and the documentation itself only warns that `quote()` should not be called on-chain due to sandwich-attack exposure, without describing any mitigation in `dispatch()` itself: [3](#0-2) 

### Impact Explanation
A caller (or a contract relying on `quote()`/`HyperApp.quote()` off-chain estimates) that submits `msg.value` computed from a stale or sandwich-manipulated pool price can have their entire `msg.value` consumed by `swapETHForExactTokens` at a worse effective rate than expected, since there is no upper bound the transaction itself enforces beyond "however much ETH the router pulls to hit `get.fee`." Because `swapETHForExactTokens` in the standard Uniswap V2 router refunds unused ETH, the practical loss is bounded by price movement between quote and execution, but there is no explicit revert path protecting the payer if the router's price has moved unfavorably — the transaction executes and spends the manipulated amount silently. This falls into the "loss of funds" impact category for users relying on `dispatch(DispatchGet)`/`dispatch(DispatchPost)`'s native-payment path.

### Likelihood Explanation
Likelihood is limited by two factors: (1) the underlying router call is `swapETHForExactTokens`, which does refund unspent ETH, constraining the damage to price-manipulation-magnitude losses rather than unbounded fund loss; and (2) the docs explicitly caution developers off-chain to be aware `quote()` (which uses `getAmountsIn`) is sandwich-attackable, indicating this is a known, partially-accepted design tradeoff rather than an undiscovered bug. This weakens confidence that it represents a *new*, previously-unknown, exploitable vulnerability distinct from the documented sandwich-attack caveat.

### Recommendation
Add an explicit maximum-native-spend parameter (or a minimum-fee-token-per-wei bound) to `DispatchGet`/`DispatchPost` that the payer sets at dispatch time, and `require` that the swap's implied price does not exceed it — mirroring the `amountOutMin` check pattern already used in `SimplexPaymaster.swapAndDeposit`. This closes the same class of "unauthenticated on-chain price with no user-set bound" gap called out in the external report.

### Proof of Concept
Not constructed — this finding is based on static code review of the swap call sites; a full PoC would need to simulate pool-price movement between a client's `quote()` call and the `dispatch()` transaction's inclusion, which requires live pool state not present in this repository's fork tests. The existing fork test `EvmHostForkTest.testCanDispatchFundRequestWithNative` exercises the happy path but does not test adversarial price movement between quote and execution. [4](#0-3) 

**Caveat on confidence**: Given the docs already flag the sandwich-attack risk on the `quote()` side, and `swapETHForExactTokens` inherently refunds excess ETH (bounding the blast radius), this is a weaker/lower-confidence analog than the original report's direct "no min-output check at all" pattern. I could not find a Hyperbridge code path where funds are transferred/minted based on an oracle price with **zero** enforced bound (unlike `SimplexPaymaster`, which does enforce one) — the `EvmHost.dispatch` swap paths are the closest structural analog but carry inherent partial protection via the router's own refund mechanics and documented developer awareness.
