### Title
`compound()` pays out the contract's entire token balance instead of the caller's claimed delta - (File: rewards/ManualCompound.sol)

### Summary
In `ManualCompound.compound()`, after calling `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)`, the function computes `receivedBalance = IERC20(_tokenAddress).balanceOf(address(this))` for every configured reward and forwards that entire balance to `msg.sender` via `convertFor`, `lockFor`, `depositFor`, or a direct transfer. There is no snapshot of the pre-claim balance and no delta computation, so any tokens already resting on the contract (dust from rounding, a prior failed/partial transfer, or tokens sent by another party) are swept and awarded entirely to whichever address happens to call `compound()` next.

### Finding Description
The vulnerable code is:
```solidity
// rewards/ManualCompound.sol
for (uint256 i; i< rewardTokensLength; i++) {
    address _tokenAddress = rewards[i].tokenAddress;
    ...
    uint256 receivedBalance = IERC20(_tokenAddress).balanceOf(address(this));
    if (receivedBalance > 0) {
        ...
        IConverter(_convertor).convertFor(receivedBalance, _convertRatio, _minRec, msg.sender, 2);
        ...
    }
}
``` [1](#0-0) 

The function is `external` with no access control - any unprivileged EOA or contract can call it. The caller supplies `_lps` and `_rewards` (attacker-controlled arrays passed to `multiclaimOnBehalf`), plus `_convertRatio`, `_minRec`, and `_lockMgp`. Because `receivedBalance` is read as the raw `balanceOf(address(this))` after the claim rather than `balanceAfter - balanceBefore` captured immediately prior to the claim, any token balance that was already sitting on the `ManualCompound` contract before this call — e.g., dust left from a previous caller whose downstream leg (`convertFor`/`lockFor`/`depositFor`) didn't fully consume the approved amount, or leftover reward tokens from a partial claim — gets attributed entirely to the current caller and paid out to them.

The caller can trivially reach this by passing empty inner arrays in `_rewards` (triggering the "claim-all" path in `multiclaimOnBehalf`) so that the claim touches all pools/rewards, then benefits from whatever balance is on the contract, including residuals unrelated to their own claim. Since `_minRec` is fully attacker-supplied and passed straight into `IConverter.convertFor`, the caller controls the slippage/minimum-received check on the conversion leg, meaning there is no invariant reconciling the caller's actual claimed delta with what they walk away with — they simply receive whatever balance is present at settlement time. No modifier, `nonReentrant` guard, or balance snapshot exists to prevent this.

### Impact Explanation
This breaks the core invariant that a compounding caller should only receive value produced by their own claim. Any resting balance in `ManualCompound` (rounding dust, leftover approvals not consumed by `convertFor`/`lockFor`/`depositFor`, or tokens routed there by a partially-failed prior transaction) is transferred out to the next caller for free. This matches "Theft of unclaimed yield / direct theft of user funds" since value that should belong to other users' claims (or to the protocol) is captured by an arbitrary caller. The severity scales with however much reward-token balance accumulates on the contract between compound calls — under specific claim-ordering or partial-consumption scenarios, this could be non-trivial.

### Likelihood Explanation
Reaching the vulnerable path requires no privileged role — anyone can call `compound()` with arbitrary `_lps`/`_rewards`/`_convertRatio`/`_minRec`/`_lockMgp`. The precondition is that some non-zero balance of a configured reward token exists on `ManualCompound` before the call not resulting from the caller's own claim; this can occur naturally from dust/rounding in the convert/lock/deposit legs across many prior calls, or could be induced by a caller who intentionally leaves dust behind (e.g., by manipulating `_convertRatio`/`_minRec` on a prior call to cause `convertFor` to consume less than the full approved amount, leaving residual balance for their own subsequent call). Exploitability is repeatable across every reward token registered in `rewards`.

### Recommendation
Snapshot the balance of each reward token immediately before calling `multiclaimOnBehalf`, and use `receivedBalance = balanceOf(address(this)) - balanceBefore` when settling each reward, so only the delta produced by the current caller's claim is forwarded. Also ensure any unspent `approve` allowance from `convertFor`/`lockFor`/`depositFor` is reset to zero after use to avoid stale-approval leakage.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `ManualCompound` with a mock `masterMagpie`, mock `IConverter`, mock reward token, and register the reward token via `addReward`.
2. Simulate residual balance: directly transfer (mint) `100e18` of the reward token to the `ManualCompound` contract address, bypassing any claim (simulating dust/leftover from a prior partially-consumed conversion).
3. Have a mock `multiclaimOnBehalf` mint `10e18` of the same reward token to `ManualCompound` when called by `attacker` with empty `_rewards[i]` arrays (claim-all path).
4. Call `compound(emptyLps or dummyLps, emptyRewardsArrays, _convertRatio, _minRec, false)` as `attacker`.
5. Assert that `IConverter.convertFor` (or the final transfer) is invoked with `receivedBalance == 110e18` (100 dust + 10 claimed) instead of the expected `10e18` that corresponds solely to the attacker's own claim.
6. Assert `attacker` receives value corresponding to the full `110e18`, confirming that `_minRec` and `obtainedmWomAmount` in `SmartWomConvert` are reconciled against the inflated `receivedBalance`, not the caller's actual claimed delta — demonstrating the theft of the pre-existing 100e18 balance.
