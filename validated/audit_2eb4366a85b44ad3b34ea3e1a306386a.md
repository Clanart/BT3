### Title
MessageSet extension parsing spawns a fresh `GPBCodedInputStream` that resets `recursionDepth` to 0, bypassing the recursion limit - (File: `objectivec/GPBMessage.m`)

### Summary
`-[GPBMessage parseMessageSet:extensionRegistry:forcedExtension:]` extracts the raw bytes of a MessageSet item's message payload and parses them with a brand-new `GPBCodedInputStream` rather than continuing to use the parent stream. The comment at [1](#0-0)  claims the new stream is constructed via `initWithData:parentRecursionDepth:` in order to "carry the parent stream's recursion depth across to the child stream," but no such initializer exists in `GPBCodedInputStream`/`GPBCodedInputStream_PackagePrivate.h`; the real recursion counter (`state->recursionDepth`) is only ever checked by `CheckRecursionLimit` against `kDefaultRecursionLimit` [2](#0-1) , and every fresh `GPBCodedInputStream` starts that counter at 0. This mirrors the Sherlock report's root cause: a value meant to accumulate/persist across repeated operations (`totalERC20Claimed` per "round" vs. recursion depth per "nesting hop") is silently reset/reinitialized instead of being carried forward, defeating the invariant the mechanism exists to enforce.

### Finding Description
`CheckRecursionLimit` enforces `kDefaultRecursionLimit = 100` [3](#0-2)  purely off `state->recursionDepth`, which is incremented while parsing nested embedded messages/groups. In `parseMessageSet:extensionRegistry:forcedExtension:`, each `MessageSet` item's message-typed payload is decoded into a standalone `NSData` via `GPBCodedInputStreamReadRetainedBytesNoCopy` and then handed to a *new* `GPBCodedInputStream` object [4](#0-3) . Because a new stream object has its own freshly-initialized `state_`, its `recursionDepth` field starts at 0 regardless of how deep the enclosing parse already is — the comment describing depth "inheritance" does not correspond to any actual code path that copies the parent's depth into the child. `mergeFromCodedInputStream:extensionRegistry:endingTag:` is then invoked on this child stream, and if the extension's message type itself contains another `MessageSet`-typed field (or itself uses the extendable-message-set mechanism recursively), each hop through `parseMessageSet:` resets the attacker-controlled recursion counter back to 0, allowing unbounded nesting depth while each individual "layer" only ever appears to be `kDefaultRecursionLimit` deep to the check.

### Impact Explanation
An attacker sending a bounded, well-formed serialized `MessageSet`-style extendable message can nest MessageSet items to a depth far beyond the intended 100-level cap, because each `parseMessageSet:` call effectively resets recursion accounting. This can drive the Objective-C runtime into deep native call-stack recursion (stack exhaustion) that the recursion-limit mechanism was specifically designed to prevent, defeating a documented hardening control on the binary Protobuf parsing path in the Objective-C runtime. This corresponds to a Medium/High severity availability-impacting parser-hardening bypass rather than memory corruption, since no bounds/type checks are otherwise skipped and the payload itself is bounded.

### Likelihood Explanation
Likelihood is high in an application that parses attacker-supplied binary Protobuf into an extendable message type using the `MessageSet` wire format, since `parseMessageSet:` is invoked automatically by `-[GPBMessage mergeFromCodedInputStream:extensionRegistry:endingTag:]` whenever a message-set item is present and the corresponding extension exists in the registry (or is unrecognized, in which case bytes are just stored, so the bypass matters specifically for registered message-typed extensions that themselves recursively contain further nested message/group/MessageSet fields). Because the schema, generated code, and registry are trusted per the report's threat model, this is purely a matter of a bounded, ordinary client payload structured with recursive `MessageSet` extension chains.

### Recommendation
Do not spawn an independent `GPBCodedInputStream` with a reset recursion counter for MessageSet item payloads. Either continue parsing with the parent stream's `PushLimit`/`PopLimit` machinery (as the equivalent C++/Java/C# implementations do via `IncrementRecursionDepthAndPushLimit`/`DecrementRecursionDepthAndPopLimit`, see [5](#0-4) ), or explicitly propagate `input->state_.recursionDepth` into the newly constructed stream's `state_.recursionDepth` before merging, and add/verify a genuine initializer (e.g., an actual `parentRecursionDepth:` parameter) that performs this propagation, since none currently exists in `GPBCodedInputStream`/`GPBCodedInputStream_PackagePrivate.h`.

### Proof of Concept
Construct a message whose extendable range is populated with `MessageSet` items (`GPBWireFormatMessageSetTypeIdTag`/`GPBWireFormatMessageSetMessageTag` per [6](#0-5) ) where the extension's message type recursively contains further `MessageSet`-format extension fields, nested 100+ layers deep via valid, bounded length-delimited payloads. On the parent stream, `CheckRecursionLimit` would normally reject depth ≥ 100 [2](#0-1) ; because each `parseMessageSet:` hop parses its extension payload on a brand-new `GPBCodedInputStream` (verified: no `initWithData:parentRecursionDepth:` initializer exists in the codebase to carry depth forward), each hop resets the counter to 0, allowing the encoded nesting to exceed the intended limit and drive native recursion depth in `mergeFromCodedInputStream:` well past 100 real stack frames. I was not able to execute this against a live build within this session (no compiler/runtime access here); this should be validated by a Devin session with build tooling to construct the exact nested `MessageSet` byte stream and observe actual stack depth versus the documented 100-frame cap.
