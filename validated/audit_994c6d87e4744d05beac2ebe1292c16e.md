### Title
Copilot merge-conflict reassembly silently corrupts committed content when a file contains embedded conflict-marker-like text - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
The Penumbra hotfix (#4996/#4993) was a "broken invariant" bug: an internal state-machine assumption in the DEX (about ordering/well-formedness of routed data) didn't hold for an attacker/user-reachable input, causing the chain to halt on an unhandled inconsistency. The closest reachable analog in this codebase is the merge-conflict-marker scanner used by the Copilot AI conflict-resolution feature: `extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts`) and `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts`) both assume that the first `=======`/`>>>>>>>`-looking line encountered after a `<<<<<<<` line is the *real* end of that conflict block. That invariant breaks when the "theirs" (incoming, attacker-controlled) side of the merge itself contains text that looks like conflict markers — a scenario that is entirely plausible for documentation, README/tutorial files about Git, or test fixtures (this very repo's own test files contain literal `<<<<<<< HEAD` / `=======` / `>>>>>>> feature` strings as fixture data, per [1](#0-0) ).

### Finding Description
`extractConflictHunks` collects "ours" content by scanning forward until it sees a line matching `separatorMarker` (`/^={7}$/`) or `baseMarker`, without checking whether a *nested* `<<<<<<<` line appears first: [2](#0-1) 
It then collects "theirs" content until the first line matching `theirsMarker` (`/^>{7}(?:\s|$)/`): [3](#0-2) 

`reassembleResolvedFile` — the function that later splices the model's per-hunk resolution back into the on-disk file before it is committed — performs the *same* first-match scan independently: [4](#0-3) 

If a real Git conflict's "theirs" region (content coming from a branch/PR the attacker controls) happens to contain embedded lines that match `^={7}$` and `^>{7}(?:\s|$)` — e.g. literal example markers in a doc/tutorial file, or a crafted string an attacker deliberately puts in a PR to be merged — both functions truncate the hunk at that *first* embedded pseudo-marker instead of the real closing `>>>>>>>` further down. The genuine trailing content (the real `=======`, the rest of "theirs", and the real `>>>>>>>`) is left in the file as ordinary text, outside of any hunk that `extractConflictHunks` reports to the model and outside of the region that `reassembleResolvedFile` treats as "conflict block to replace."

Because both functions use the identical "first occurrence wins" logic, the *hunk count* they agree on, so `validateResolutionPaths`'s hunk-count check does not catch anything: [5](#0-4) 
Nothing downstream re-scans the final `resolvedContent` for stray marker-like text; the only marker check that exists is on the model's own `resolvedContent` string per hunk, checking for `<{7}` and `={7}` together, which does not apply to left-over raw file bytes: [6](#0-5) 

### Impact Explanation
The result is silent corruption of what the user commits: the AI-resolved file that is written to disk and staged for commit contains stray, real `=======` / `>>>>>>> <branch>` lines that are not conflict markers being flagged to the user (since the tool reports the conflict as fully resolved) but are leftover raw content spliced in the wrong place. This can (a) break the file syntactically (e.g. `=======` inside source code), (b) silently drop the tail of the "theirs" branch content that the attacker/collaborator intended to merge, and (c) leave text that looks like an unresolved conflict marker permanently committed into the user's repository history — exactly the "silent corruption of what the user commits" class targeted by the reported bug class. No code execution occurs, but the invariant break is directly analogous: an assumption about well-formed nested structure fails under adversarial/attacker-influenced input and the tool proceeds to produce a corrupted authoritative result instead of failing safe.

### Likelihood Explanation
Likelihood is moderate: it requires (1) the user to opt into the Copilot-powered "resolve conflicts with AI" feature, and (2) a real merge conflict whose "theirs" side contains marker-like text. This is not contrived — repositories that contain Git tutorials, conflict-resolution documentation, or test fixtures with literal marker strings (as this very codebase does) are common, and an attacker who controls a PR/branch that will be merged can trivially embed such lines to force this path deliberately. No local access, malware, or credentials are required — only that the victim performs an AI-assisted merge against attacker-supplied branch content.

### Recommendation
Make `extractConflictHunks` and `reassembleResolvedFile` conflict-block detection non-greedy and marker-aware: when scanning for the separator/closing marker inside an already-open `<<<<<<<` block, treat any nested `<<<<<<<` line encountered before a matching close as invalidating that block (skip/copy-through) rather than silently accepting the first `=======`/`>>>>>>>` found. Additionally, add a final integrity check on the fully reassembled file (or each spliced region) confirming no lines matching the marker regexes remain outside intentionally-preserved literal content, and surface a hard validation error rather than committing silently if ambiguity is detected. Keep `extractConflictHunks`'s and `reassembleResolvedFile`'s marker-matching logic in a single shared implementation to eliminate the possibility of the two functions drifting out of sync in the future.

### Proof of Concept
1. Create a repo with a file `README-git.md` containing a paragraph of example conflict-marker text, e.g.:
```
Example of a Git conflict:
<<<<<<< HEAD
example ours
=======
example theirs
>>>>>>> feature
```
2. On branch `main`, modify a nearby line to create a real conflicting edit.
3. On branch `attack`, modify the same line differently and add real content after the embedded example block.
4. Merge `attack` into `main`, producing a real conflict whose "theirs" region (as seen by Git) spans across the embedded example block.
5. Run the Copilot "Resolve with AI" flow (`extractConflictHunks` → model → `reassembleResolutions`/`reassembleResolvedFile`).
6. Observe that the resulting committed file contains stray `=======`/`>>>>>>> attack` text and is missing the real trailing "theirs" content, while the tool reports the file as fully resolved with no errors — this can be verified purely by unit-testing `extractConflictHunks` and `reassembleResolvedFile` directly with the crafted content shown above, without needing the live model.
