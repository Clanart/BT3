### Title
Race condition in `Transaction.ValidateSender`/`ValidateFeePayer` caching can silently corrupt the resolved fee payer for fee-delegated transactions - ([File: blockchain/types/transaction.go])

### Summary
`types.Transaction` memoizes the resolved sender and fee-payer addresses (`validatedSender`, `validatedFeePayer`) directly on the shared, pointer-based `Transaction` object so that expensive `AccountKey` signature/recovery work is only performed once. The two setter paths, `ValidateSender` and `ValidateFeePayer`, are each individually protected by `tx.mu`, but the *combined* invariant they rely on ("whoever runs first initializes both fields, whoever runs second only overwrites the fee-payer field") is not atomic across the two functions. This is the classic TOCTOU bug class described by the external report (a race between the "check" and the "use/commit" step of a privilege-relevant decision), reachable here through ordinary concurrent processing of the same `*Transaction` object (e.g. block state prefetching racing with the main executor, or concurrent RPC/tracer calls that build messages from the same pooled transaction, as already reproduced in `tests/race_test.go`'s `TestRaceAsMessageWithAccountPickerForFeePayer`).

### Finding Description
`ValidateSender` sets both `validatedSender` and `validatedFeePayer` to the resolved sender address, but only when `validatedFeePayer` has never been set: [1](#0-0) 

`ValidateFeePayer` separately resolves the real fee payer and only assigns it when it observes `validatedFeePayer == validatedSender` (i.e. still holding the sender's placeholder value): [2](#0-1) 

Both critical sections individually hold `tx.mu`, so each read-modify-write is atomic, but the two functions are called independently and their relative order is not synchronized:

- If `ValidateSender` runs first, it sets `validatedFeePayer = sender` as a placeholder, then `ValidateFeePayer` correctly detects the placeholder and overwrites it with the real fee payer. Correct outcome.
- If `ValidateFeePayer` runs first (both fields still zero-valued, so the equality check trivially holds), it correctly sets `validatedFeePayer` to the real fee payer. But when `ValidateSender` subsequently runs, its own guard only checks `validatedSender == common.Address{}` — it has no way to know `validatedFeePayer` was already correctly resolved — and it unconditionally re-stamps `validatedFeePayer = sender`, clobbering the already-correct value.

Because a single `*types.Transaction` object is reused and referenced from multiple call sites that can run concurrently on the same underlying object (transaction pool validation, block state prefetching in `blockchain/state_prefetcher.go`, tracer/RPC message construction in `node/cn/tracers/api.go` and `node/cn/state_accessor.go`, all of which call `AsMessageWithAccountKeyPicker` → `ValidateSender`/`ValidateFeePayer`), the ordering between these two setters is not guaranteed, and the corrupted `validatedFeePayer` value is then permanently cached on the object (the "only-if-unset" guards prevent it from ever being corrected).

The project's own test `TestRaceAsMessageWithAccountPickerForFeePayer` demonstrates exactly this scenario — two goroutines concurrently call `tx.AsMessageWithAccountKeyPicker` on the same fee-delegated `Transaction` instance and assert the resolved fee payer is always correct: [3](#0-2) 

### Impact Explanation
`ValidatedFeePayer()`/`ValidatedSender()` are later consumed directly by `StateTransition.buyGas()` to decide which account's balance is debited for gas (and, in ratio-fee-delegation, how the cost is split): [4](#0-3) 

If the memoized `validatedFeePayer` is corrupted back to the sender address due to the race above, gas/fee accounting for a fee-delegated transaction can silently collapse to "sender pays," defeating the fee-delegation guarantee that the designated fee payer (not the sender) is charged. Because the corruption depends on non-deterministic goroutine scheduling, different honest nodes processing the same block (some with prefetch races, some without) can derive different balances/state roots for the same transaction, which is a state-divergence / consensus-safety issue, and also constitutes fee-delegation abuse (the sender's assumption that a third-party fee payer bears the cost, or vice versa, is not consistently enforced).

### Likelihood Explanation
The race requires two code paths to build a `Message` from the same `*types.Transaction` pointer concurrently before the memoized fields settle. This is plausible in kaia's architecture because: (1) the tx pool retains and revalidates pooled transactions across resets, (2) block processing uses a state prefetcher that runs multiple goroutines over the transactions of an incoming block, and (3) RPC/tracing paths (`AsMessageWithAccountKeyPicker` call sites in `node/cn/tracers/api.go`, `node/cn/state_accessor.go`) can execute concurrently with the main processor on the same decoded transaction objects. The existence of a dedicated stress/race regression test for this exact scenario in the codebase (`tests/race_test.go`) indicates the developers were aware this is a realistic race window, not a purely theoretical one.

### Recommendation
Make the sender/fee-payer resolution atomic as a unit rather than two independently-locked, order-dependent mutations: hold a single lock for the entire "resolve sender + resolve fee payer" sequence (or use a `sync.Once` per field with an explicit "fee payer resolved" flag that `ValidateSender` must never clobber once set). Concretely, `ValidateSender` should never unconditionally overwrite `validatedFeePayer`; it should only initialize `validatedFeePayer` if it is still the zero value, not merely because `validatedSender` was zero, and `ValidateFeePayer`'s completion should be tracked independently (e.g., a boolean `feePayerResolved`) so a later `ValidateSender` call can't regress it.

### Proof of Concept
1. Construct a fee-delegated transaction (`TxTypeFeeDelegatedValueTransfer` or similar) signed by both `sender` and `feePayer`.
2. From two goroutines, concurrently call `tx.AsMessageWithAccountKeyPicker(signer, stateDB, blockNumber)` on the same `*types.Transaction` instance (mirroring `TestRaceAsMessageWithAccountPickerForFeePayer` at `tests/race_test.go:103-157`), arranging (e.g. via `runtime.Gosched()`/repeated iterations) for `ValidateFeePayer`'s critical section to execute before `ValidateSender`'s critical section on at least one interleaving.
3. Observe that `msg.ValidatedFeePayer()` returns the sender's address instead of the actual fee payer's address in the losing interleavings, and that this corrupted value persists on the transaction object for all subsequent consumers (`buyGas`, receipt generation, etc.), because both setters guard on "unset" rather than "correct."

**Note on confidence:** I was not able to fully trace every call site that might create two concurrent `AsMessageWithAccountKeyPicker` invocations on the exact same `*Transaction` pointer in production block processing (e.g., whether `state_prefetcher.go` and `blockchain.go`'s main processor definitely share the same pointer rather than a deep copy) due to tool-call limits; this should be verified in a Devin session to confirm the concrete reachable trigger path before treating this as fully proven in the live block-processing pipeline as opposed to the RPC/tracer paths, where shared-pointer concurrent access is clearly demonstrated by the existing test.

func TestRaceAsMessageWithAccountPickerForFeePayer(t *testing.T) {
	log.EnableLogForTest(log.LvlCrit, log.LvlTrace)

	// Configure and generate a sample block chain
	var (
		gendb = database.NewMemoryDBManager()

		// create a sender and a feepayer
		from, _     = createAnonymousAccount("a5c9a50938a089618167c9d67dbebc0deaffc3c76ddc6b40c2777ae594389999")
		feePayer, _ = createAnonymousAccount("ed580f5bd71a2ee4dae5cb43e331b7d0318596e561e6add7844271ed94156b20")

		funds = new(big.Int).Mul(big.NewInt(1e16), big.NewInt(params.KAIA))
		gspec = &blockchain.Genesis{
			Config: params.TestChainConfig,
			Alloc: blockchain.GenesisAlloc{
				from.GetAddr():     {Balance: funds},
				feePayer.GetAddr(): {Balance: funds},
			},
		}
		genesis = gspec.MustCommit(gendb)
		signer  = types.LatestSignerForChainID(gspec.Config.ChainID)
	)

	iterNum := 10000
	errCh := make(chan error, 2*iterNum)

	for i := 0; i < iterNum; i++ {
		tx, _ := genFeeDelegatedChainDataAnchoring(t, signer, from, nil, feePayer, big.NewInt(1234))
		for i := 0; i < 2; i++ {
			go func() {
					stateDB, err := state.New(genesis.Root(), state.NewDatabase(gendb), nil, nil)
				if err != nil {
					panic(err)
				}

				msg, err := tx.AsMessageWithAccountKeyPicker(signer, stateDB, 0)
				if err != nil {
					panic(err)
				}

				if msg.ValidatedFeePayer() != feePayer.GetAddr() {
					errCh <- fmt.Errorf("expected: %v, actual: %v", feePayer.GetAddr().String(), msg.ValidatedFeePayer().String())
				} else {
					errCh <- nil
				}
			}()
		}
	}

	for i := 0; i < 2*iterNum; i++ {
		if err := <-errCh; err != nil {
			t.Fatal(err)
		}
	}
}
