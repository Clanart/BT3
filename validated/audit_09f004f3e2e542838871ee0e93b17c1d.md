## Analysis Summary

I found a concrete analog to CVE-2019-3860's bug class (parsing a length-prefixed wire format without validating that enough bytes remain before reading them, causing an out-of-bounds read on attacker-supplied data) inside the mempool's CLVM-canonical-form checker.

### Title
Out-of-bounds read via truncated multi-byte atom length prefix in CLVM canonical-form check - (File: chia/full_node/mempool_manager.py)

### Summary
`is_atom_canonical()` and `is_clvm_canonical()` in `chia/full_node/mempool_manager.py` parse raw CLVM-serialized bytes (puzzle reveal/solution bytes taken from a submitted spend bundle) to decide whether a coin spend is eligible for mempool fast-forward/dedup handling. The multi-byte atom length-prefix decoding loop indexes into the buffer without first checking that enough bytes remain, exactly mirroring the libssh2 SFTP empty/short-payload parsing flaw in CVE-2019-3860.

### Finding Description
`is_atom_canonical()` reads the first byte at `offset` to determine how many additional length-prefix bytes follow (0–5, depending on which high bits are set), then loops reading those bytes one at a time: [1](#0-0) 

Crucially, the loop that reads the additional prefix bytes does not check that `offset` stays within the bounds of `clvm_buffer` before indexing:
```
for i in range(prefix_len):
    atom_len <<= 8
    offset += 1
    atom_len |= clvm_buffer[offset]
```
If the CLVM buffer is truncated right after the atom's introductory byte (e.g., the byte pattern signals "5 more length bytes follow" per the `0b11111100` mask branch, but the buffer ends there), `clvm_buffer[offset]` runs past the end of the buffer.

`is_clvm_canonical()`, the caller, only guards against a fully empty buffer (`assert clvm_buffer != b""`) — it never validates that each atom's declared length-prefix or payload actually fits in the remaining buffer before advancing `offset`: [2](#0-1) 

This is structurally identical to the libssh2 flaw: a field claims a certain number of trailing bytes, the parser trusts that claim, and reads past the end of the actually-received buffer when the claim is wrong (analogous to "empty/short SFTP payload" causing an OOB read while parsing).

### Impact Explanation
This code path processes puzzle reveal/solution bytes that originate from an untrusted, attacker/wallet-controlled spend bundle submitted to the mempool (used for singleton fast-forward and dedup eligibility checks in mempool item processing). A malformed but otherwise validly-hashed CLVM solution can be crafted so that its raw serialization ends immediately after a multi-byte atom-length introducer byte. When `is_clvm_canonical()`/`is_atom_canonical()` is invoked on that buffer during mempool admission, the buffer read past its end raises an uncaught `IndexError` inside per-spend-bundle processing, rather than returning `False` in a controlled way. This falls into the "spend-triggered transaction-processing halt" category the scan targets — a single submitted spend bundle can cause mempool processing logic tied to fast-forward/dedup eligibility to throw an unexpected exception instead of gracefully rejecting the spend.

### Likelihood Explanation
Any unprivileged spend-bundle submitter can trigger the code path: the eligibility-check functions operate directly on solution bytes taken from spend bundles fed into the mempool manager (e.g., via `push_tx`/RPC or protocol `new_transaction`/`respond_transaction`). Crafting a puzzle/solution `Program` whose canonical CLVM serialization ends right after an atom's length-prefix introducer byte is straightforward and requires no privileged access, no colluding peer, and no proof-of-space/VDF manipulation.

Note: I was unable to fully verify, within the available context, the exact call site(s) invoking `is_clvm_canonical()`/`is_atom_canonical()` from the mempool-item admission pipeline (e.g., whether it's wrapped in a broad `try/except` at a higher layer that would downgrade this to a caught, non-fatal error). This should be confirmed by inspecting all call sites of `is_clvm_canonical` in `chia/full_node/mempool_manager.py` and `chia/full_node/eligible_coin_spends.py` before treating this as a confirmed unhandled-crash DoS.

### Recommendation
In `is_atom_canonical()`, validate `offset + prefix_len < len(clvm_buffer)` before entering the multi-byte read loop, and return a controlled non-canonical result (or raise a well-defined, caught exception) instead of allowing `IndexError` to propagate. Add equivalent bounds checks in `is_clvm_canonical()` for the atom-length and pair-traversal bounds so that any truncated/malformed buffer is rejected safely rather than causing an out-of-bounds index during parsing.

### Proof of Concept
Conceptual (bytes, not full harness — construct a CLVM buffer ending right after a length-prefix introducer byte):
```python
from chia.full_node.mempool_manager import is_clvm_canonical

# 0b11111100 pattern => 5 additional length bytes expected, but buffer ends here
malformed = bytes([0b11111101])  # first byte demands prefix_len=5 more bytes
is_clvm_canonical(malformed)  # raises IndexError instead of returning False
```
A spend bundle whose solution/puzzle-reveal, once serialized to CLVM bytes, embeds this pattern at any atom boundary would trigger the same unhandled `IndexError` when the mempool manager evaluates fast-forward/dedup eligibility for that spend.

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
