### Title
`auction_submitBid` RPC endpoint lacks per-caller rate limiting present in the P2P bid path, enabling unauthenticated resource exhaustion of the bid pool and signature-verification CPU - ([File: kaiax/auction/impl/api.go])

### Summary
The `auction_submitBid` JSON-RPC method (`kaiax/auction/impl/api.go`, `AuctionAPI.SubmitBid`) is the intended, unauthenticated public entry point for searchers to submit auction bids per KIP-249. Unlike the P2P ingestion path `BidPool.HandleBid`, which enforces a 300 bids/sec per-peer token-bucket rate limit before adding a bid, the RPC path calls `BidPool.AddBid` directly with no rate limiting at all.

### Finding Description
`AuctionModule.APIs()` registers the `auction` namespace with `Public: false` [1](#0-0) , meaning it is only exposed on nodes that opt it into `--rpc.api`/`ws-rpc.api`. The module's own README documents `auction_submitBid` as a `curl`-able, unauthenticated public HTTP-RPC endpoint intended for external searchers [2](#0-1) , so once enabled it is the designed reachable path for any external caller, analogous to Twilio's designed-to-be-reachable `/media-stream` endpoint in the original report.

`SubmitBid` immediately: (1) decodes and forwards the target transaction to the node's transaction pool via `Backend.SendTx`, and (2) calls `bidPool.AddBid(bid)` directly — with no call to any rate limiter: [3](#0-2) 

Compare this to the P2P ingestion path, `BidPool.HandleBid`, which is gated by a per-peerID `rate.Limiter` (300 bids/sec, LRU cache of 1024 limiters) before a bid is even queued: [4](#0-3) 

`BidPool.AddBid` itself performs meaningful CPU work per call — full bid validation including two ECDSA signature verifications (`validateBidSigs` → `ValidateSearcherSig`/`ValidateAuctioneerSig`) — before any pool-size or duplicate check trips: [5](#0-4) [6](#0-5) 

Because the RPC path bypasses `checkRateLimit` entirely, the only throttle protecting the node from a flood of `auction_submitBid` calls is the generic RPC layer's global `ConcurrencyLimit` (default 3000 concurrent requests, node-wide, shared across all RPC methods) [7](#0-6)  — there is no per-caller/per-IP limit analogous to the peer-based limiter used for the gossip path. An attacker with no stake, no signing key relationship to the auctioneer, and no special privileges can send an unbounded volume of `auction_submitBid` requests (using intentionally-invalid signatures, since signature validation happens *after* the expensive crypto work and cheap parameter checks), consuming CPU on every call and — while `insertBid` does enforce `maxBidPoolSize` and the internal `bidMsgCh`/`newBidCh` channels are bounded (`bidChSize = 2048`) — every RPC call still executes `Backend.SendTx` against the transaction pool and full bid validation logic before any of those pool-size limits can reject it.

### Impact Explanation
This matches the report's bug class (CWE-770, uncontrolled resource consumption from an unauthenticated network-facing endpoint) mapped onto Kaia's auction module, which is explicitly reachable by any public-RPC caller/searcher — one of the permitted actor types (auction bidder). The impact is a CPU/goroutine resource-exhaustion vector on CN nodes running the auction module that can degrade legitimate bid processing and general RPC responsiveness, without requiring the attacker to hold any stake, valid signature, or special relationship to the auctioneer. This is a Medium-severity availability concern (not a value-movement, fee-theft, or consensus-divergence bug); the maxBidPoolSize and bounded channels prevent unbounded memory growth, limiting worst-case impact to CPU/goroutine pressure and RPC-concurrency-slot exhaustion.

### Likelihood Explanation
Likelihood is high for nodes that expose the `auction` RPC namespace (which is the module's intended deployment mode per its own README example), since no authentication, signature pre-check, or rate limit gates the RPC call before expensive validation work runs.

### Recommendation
Apply the same per-caller rate limiting used in `BidPool.HandleBid` to the RPC-facing `SubmitBid` path — e.g., have `AuctionAPI.SubmitBid` extract a caller identifier (remote IP/peer context from `ctx`) and call `bidPool.checkRateLimit` (or an equivalent limiter) before performing signature validation or forwarding the target transaction, mirroring the protection already applied to the P2P `HandleBid` ingestion path.

### Proof of Concept
Not independently verified with a live node in this session (no code-execution/network access available); the analysis is based on static code inspection of `kaiax/auction/impl/api.go` and `kaiax/auction/impl/bid_pool.go` showing that `SubmitBid` invokes `AddBid` without any call to `checkRateLimit`, in contrast to `HandleBid`, which explicitly rate-limits by peer ID before enqueueing a bid. A concrete PoC would be: repeatedly call `auction_submitBid` via HTTP-RPC with syntactically valid but cryptographically invalid bids at a rate far exceeding 300/sec from a single source, and observe CPU usage from repeated `crypto.Sign`/signature-recovery work in `validateBidSigs`, absent in the equivalent P2P flow which would have dropped such a flood at the peer rate limiter.

func (api *AuctionAPI) SubmitBid(ctx context.Context, bidInput BidInput) RPCOutput {
	numBidRequestCounter.Inc(1)
	if api.a.IsDisabled() {
		return makeRPCOutput(EMPTY_HASH, auction.ErrAuctionDisabled)
	}

	//  1. directly send target transaction
	targetTx, errTxDecode := toTx(bidInput.TargetTxRaw)
	if errTxDecode != nil {
		return makeRPCOutput(EMPTY_HASH, errTxDecode)
	}
	if targetTx.Hash() != bidInput.TargetTxHash {
		return makeRPCOutput(EMPTY_HASH, auction.ErrInvalidTargetTxHash)
	}
	errTargetTxSend := api.a.Backend.SendTx(ctx, targetTx)
	// ignore known transaction related errors against target tx validation
	if errTargetTxSend != nil && !(strings.HasPrefix(errTargetTxSend.Error(), "known transaction:") || errors.Is(errTargetTxSend, gasless_impl.ErrUnableToAddKnownBundleTx)) {
		return makeRPCOutput(EMPTY_HASH, errTargetTxSend)
	}

	// 2. add bid
	bid := ToBid(bidInput)
	bidHash, errValidateBid := api.a.bidPool.AddBid(bid)
	return makeRPCOutput(bidHash, errValidateBid)
}

// AddBid adds a bid to the bid pool.
// Required mutex is locked in each function.
func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)

	bp.newBidCh <- bid

	return bid.Hash(), nil
}

func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}

func (bp *BidPool) HandleBid(peerID string, bid *auction.Bid) {
	if atomic.LoadUint32(&bp.running) == 0 || bid == nil {
		return
	}

	// Check rate limit for this peer
	if !bp.checkRateLimit(peerID) {
		logger.Trace("Rate limit exceeded for peer", "peerID", peerID)
		return
	}

	select {
	case bp.bidMsgCh <- bid:
	default:
		logger.Trace("Bid queue is full, dropping bid", "peerID", peerID)
	}
}

// checkRateLimit checks if the peer is within rate limit
func (bp *BidPool) checkRateLimit(peerID string) bool {
	bp.peerRateLimiterMu.Lock()
	defer bp.peerRateLimiterMu.Unlock()

	limiter, exists := bp.peerRateLimiter.Get(peerID)
	if !exists {
		// Create new rate limiter for this peer
		// Use burst equal to the rate limit (we only use rate limit, not the burst)
		limiter = rate.NewLimiter(rate.Limit(bidsPerSecondPerPeer), bidsPerSecondPerPeer)
		bp.peerRateLimiter.Add(peerID, limiter)
	}

	// It'll simply discard the bid if the rate limit is exceeded
	// We don't need to reserve for a bid here because the original bid will be sent from auctioneer through different channel (see #api.SubmitBid)
	return limiter.(*rate.Limiter).Allow()
}
