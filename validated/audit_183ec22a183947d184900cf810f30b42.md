### Title
Live-fetched asset decimals let `convert_to_erc20` skip scaling and inflate cross-chain mint amounts - (File: `modules/pallets/hyper-fungible-token/src/module.rs`, `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The `hyper-fungible-token` pallet only validates `erc_decimals >= local_decimals` at `register_token`/`update_token` time, but the actual `decimals` value used in every `send()` call is re-fetched live from `fungibles::metadata::Inspect::decimals()` rather than cached from registration. If the local asset's decimals metadata is later changed by anyone with `pallet-assets` metadata permissions on that asset (a permission entirely separate from the `hft` pallet's `T::CreateOrigin`), the registration-time invariant silently breaks. `convert_to_erc20` then divides by `10^(erc_decimals.saturating_sub(local_decimals))`, and `saturating_sub` clamps negative results to zero, so no scaling is applied where scaling down is required — producing a wildly inflated ERC-20 `amount` in the outgoing cross-chain `Message` relative to what was actually escrowed/burned locally.

### Finding Description
`send()` in [1](#0-0)  fetches `erc_decimals` from the `Precisions` map (set once at registration) and `decimals` live from the asset's current metadata, then computes:

```
let erc20_amount = convert_to_erc20(amount, erc_decimals, decimals);
```

`convert_to_erc20` is defined as: [2](#0-1) 

It multiplies by `10^(erc_decimals.saturating_sub(local_decimals))`. This formula is only correct when `erc_decimals >= local_decimals`. The `register_token`/`update_token` extrinsics enforce this invariant only at configuration time: [3](#0-2) 

But nothing re-validates the invariant when `send()` actually converts amounts, and `decimals` for non-native assets is read live from `T::Assets` metadata: [4](#0-3) 

If the asset's metadata decimals are later raised above the registered `erc_decimals` (e.g., via `pallet_assets::set_metadata`, callable by the asset's owner/admin — a role independent of the `hft` pallet's `T::CreateOrigin` governance), `local_decimals > erc_decimals` becomes true. `saturating_sub` then returns `0`, so `convert_to_erc20` multiplies by `10^0 = 1` instead of dividing the value down by `10^(local_decimals - erc_decimals)` as correct conversion requires. The result: the ERC-20 `amount` field in the dispatched `Message` is `10^(local_decimals - erc_decimals)` times larger than the correctly-scaled value, even though only `params.amount` (in the now-larger local-decimal units) was actually escrowed/burned from the sender.

This message is sent via ISMP to the destination EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract, which will mint/release tokens according to the (inflated) `amount` encoded in the message — a direct amplification of value crossing the bridge unbacked by real escrow.

The same asymmetric bug exists in the inbound direction, `convert_to_balance`: [5](#0-4)  used in `on_accept`/`on_timeout` [6](#0-5) , though in that direction a broken invariant would under-mint rather than over-mint.

### Impact Explanation
This is exactly the H-07 bug class (contract assumes a fixed/validated decimal precision but the actual decimal source can drift out of sync at runtime), applied to Hyperbridge's own fungible-token bridging pallet. The consequence is unauthorized/incorrect cross-chain minting: the destination EVM contract mints or releases more tokens than were locked or burned on the source chain, directly matching the bounty's "stealing or loss of funds" / "transaction manipulation" impact categories. Because the escrow/burn on the source chain is for the real (small) `params.amount`, but the message dispatched instructs the destination to mint the erroneously unscaled (much larger) amount, the bridge's custody invariant ("moves exactly once and only the rightful amount") is violated.

### Likelihood Explanation
Exploitation requires only that:
1. A non-native asset is registered in `hft` with `erc_decimals == local_decimals` (or any margin), and
2. The asset's decimals metadata is later increased past `erc_decimals` by whoever controls that pallet-assets asset's metadata-setting permission.

Since asset creation/decimals metadata control in `pallet-assets` is a distinct authorization path from the `hft` pallet's `T::CreateOrigin`, and the `hft` pallet performs no re-check of the invariant at `send()` time (a live lookup with no revalidation against `Precisions`), this is reachable by any account holding metadata-owner rights over a registered asset — not necessarily bridge governance or a relayer/prover. No malicious peer, prover, or relayer is required; the exploit is entirely local, using only Substrate-side pallet calls that are then bridged, and does not require front-running.

### Recommendation
- Re-validate `erc_decimals >= local_decimals` inside `send()` (and in `on_accept`/`on_timeout`) immediately before calling `convert_to_erc20`/`convert_to_balance`, returning an error (e.g., reusing `Error::<T>::ErcDecimalsBelowLocal`) if the live decimals no longer satisfy the invariant instead of silently clamping via `saturating_sub`.
- Alternatively, cache the local asset's decimals at registration time in the `Precisions`/a companion storage item and use the cached value consistently, so asset-metadata mutations post-registration cannot silently desynchronize the conversion factor.
- Make `convert_to_erc20`/`convert_to_balance` explicitly handle both directions (`local > erc` and `erc > local`) rather than relying on `saturating_sub` to implicitly encode "erc >= local"; a genuine mismatch should hard-error, not silently default to a no-op scale factor.

### Proof of Concept
1. Register asset `X` (pallet-assets, decimals = 6) via `hft::register_token` with `erc_decimals = 6` for destination chain `EVM-C`. Invariant `erc_decimals (6) >= local_decimals (6)` holds.
2. Asset `X`'s pallet-assets owner/admin (any account with `set_metadata` rights on `X`, independent of `hft`'s `CreateOrigin`) calls `pallet_assets::set_metadata` to change `X`'s decimals to `18`.
3. A holder of `X` calls `hft::send(asset_id = X, amount = 1_000_000 (i.e., 1.0 token at new 18-decimal display, but really just 1e6 raw units), destination = EVM-C, ...)`. `Assets::burn_from`/`transfer` escrows/burns `1_000_000` raw units of `X`.
4. In `send()`, `decimals` is fetched live as `18` while `erc_decimals` remains `6` from `Precisions`. `convert_to_erc20(1_000_000, 6, 18)` computes `10^(6.saturating_sub(18)) = 10^0 = 1`, so `erc20_amount = 1_000_000` is dispatched unscaled, instead of the correctly-scaled-down value that reflects that only `1_000_000 / 10^12` of a "full" 18-decimal-equivalent unit was actually escrowed.
5. The destination `HyperFungibleToken` contract on `EVM-C` mints/releases `1_000_000` raw ERC-20 units to the recipient, which (given the contract's own decimal assumptions matching the registered `erc_decimals = 6`) is far more value than the true economic amount escrowed once the true precision drift is accounted for, resulting in value inflation extractable by the sender.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
