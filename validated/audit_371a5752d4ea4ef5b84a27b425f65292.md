### Title
Malicious or compromised authorized DID provider can permanently trap CR-CAT holder funds by revoking/withholding Verified Credential proofs - ([File: chia/wallet/vc_wallet/cr_cat_drivers.py])

### Summary
Credential-Restricted CATs (CR-CATs) require a currently valid Verified Credential (VC), issued and maintained by a designated "authorized provider" DID, to be spent at all. The provider DID fully controls whether a holder's VC contains proofs that satisfy the CR-CAT's `proofs_checker`, and can unilaterally revoke that VC at any time via the backdoor mechanism. A malicious or compromised provider can therefore permanently prevent an honest, unprivileged CR-CAT holder from ever spending their own coins — the same "admin-controlled blacklist traps funds" impact described in the referenced USDC/ProtectionPool report, but implemented here via the VC/CR-CAT protocol instead of a token-level blacklist.

### Finding Description
Every CR-CAT is curried with a `CREDENTIAL_RESTRICTION` puzzle layer that hard-codes a fixed list of `authorized_providers` and a `proofs_checker` [1](#0-0) . Any spend of the CR-CAT must supply a `proof_of_inclusions` derived from a VC that is (a) issued by one of the `authorized_providers`, and (b) currently holds proofs matching every flag required by `proofs_checker` [2](#0-1) .

On the wallet side, both normal spends and claiming approved balances look up a VC via `get_vc_with_provider_in_and_proofs`, which raises if no VC with the correct provider and proof flags exists: [3](#0-2) 

`CRCATWallet._generate_unsigned_spendbundle` and `claim_pending_approval_balance` both hard-depend on this lookup succeeding, and there is no fallback spend path if it fails: [4](#0-3) [5](#0-4) 

The provider DID (or anyone who compromises the provider's DID key) fully controls whether a proof-matching VC continues to exist for a given holder:
- Proofs are only updated by a spend authorized by the provider DID's announcement (`magic_condition_for_new_proofs`), meaning the provider can simply refuse to ever renew/extend a holder's proof set, letting a needed flag lapse or never granting it in the first place: [6](#0-5) 
- The provider can outright revoke the VC via the "backdoor," bricking the VC singleton (an operation the code itself documents as intentionally leaving the holder with a permanently useless/backdoored VC, "Sync attempts by this class on spends generated by this method are expected to fail"): [7](#0-6) 
- `VCWallet.revoke_vc` is the RPC-exposed entry point a provider uses to invoke this backdoor against a specific holder's VC coin: [8](#0-7) 

Once the holder has no valid VC with matching proofs from an authorized provider, the `CREDENTIAL_RESTRICTION` layer will never validate a spend of their CR-CAT coin, and there is no alternative unlock/escape path coded into the CR-CAT puzzle or wallet logic (`_generate_unsigned_spendbundle`/`claim_pending_approval_balance` simply raise `RuntimeError`/`ValueError`). The coin becomes permanently unspendable by its rightful owner — an unprivileged wallet user who never did anything wrong.

### Impact Explanation
This is a direct analog of the reported bug class: a privileged, potentially malicious or compromised third party (the token owner in the USDC case, the authorized DID provider here) can trap an honest, unprivileged user's coins indefinitely, with no recourse for the holder. Because a single provider can be shared by an entire CR-CAT asset class, one compromised or malicious provider key can freeze funds for every CR-CAT holder relying on that provider, not just one victim. This satisfies the "spend-triggered transaction-processing halt" / permanent loss-of-funds criteria for Medium severity.

### Likelihood Explanation
Exploitation requires control of the authorized provider's DID key (or provider complicity), which is the trust model CR-CATs are designed around — analogous to a stablecoin issuer's blacklist admin key. Given that DID keys can be compromised (phishing, key leakage, insider action) just as centralized-issuer blacklist keys can, and the protocol grants no timeout, appeal, or escape-hatch spend path for CR-CAT holders, likelihood is comparable to the original USDC blacklist scenario referenced in the report.

### Recommendation
Add a holder-side escape/timeout mechanism to CR-CAT/VC design — e.g., a way for holders to migrate or reclaim funds if a provider becomes unresponsive or malicious for an extended period, or allow inclusion of multiple independent authorized providers with an OR-based proof requirement so no single provider can unilaterally freeze a holder's funds. At minimum, document this centralization/freeze risk clearly for any consumer of the CR-CAT primitive so pools/products relying on it can price in this risk or restrict which providers are trusted.

### Proof of Concept
1. Provider DID mints/authorizes a VC for Alice and lets her acquire CR-CATs restricted to `authorized_providers=[provider_did]` with a `proofs_checker` requiring flag `"kyc"`.
2. Provider DID either (a) never issues/renews the `"kyc"` proof for Alice via `magic_condition_for_new_proofs`, or (b) calls `revoke_vc` to invoke `activate_backdoor` on Alice's VC coin (`chia/wallet/vc_wallet/vc_wallet.py:376-436`, `chia/wallet/vc_wallet/vc_drivers.py:757-798`).
3. Alice attempts to spend her CR-CAT via `CRCATWallet._generate_unsigned_spendbundle`; `get_vc_with_provider_in_and_proofs` finds no valid VC and raises `ValueError`/`RuntimeError` (`chia/wallet/vc_wallet/vc_wallet.py:610-625`, `chia/wallet/vc_wallet/cr_cat_wallet.py:569-576`).
4. Alice's CR-CAT coin remains permanently locked with no alternative spend path, mirroring the "malicious token owner blacklists and traps funds" scenario from the report.

    async def get_vc_with_provider_in_and_proofs(
        self, authorized_providers: list[bytes32], proofs: list[str]
    ) -> VerifiedCredential:
        vc_records: list[VCRecord] = await self.store.get_vc_records_by_providers(authorized_providers)
        if len(vc_records) == 0:  # pragma: no cover
            raise ValueError(f"VCWallet has no VCs with providers in the following list: {authorized_providers}")
        else:
            for rec in vc_records:
                if rec.vc.proof_hash is None:
                    continue  # pragma: no cover
                vc_proofs: VCProofs | None = await self.store.get_proofs_for_root(rec.vc.proof_hash)
                if vc_proofs is None:
                    continue  # pragma: no cover
                if all(proof in vc_proofs.key_value_pairs for proof in proofs):
                    return rec.vc
        raise ValueError(f"No authorized VC has the correct proofs: {proofs}")  # pragma: no cover

    def magic_condition_for_new_proofs(
        self,
        new_proof_hash: bytes32 | None,
        provider_innerpuzhash: bytes32,
        new_proof_provider: bytes32 | None = None,
    ) -> Program:
        """
        Returns the 'magic' condition that can update the metadata with a new proof hash. Returning this condition from
        the inner puzzle will require a corresponding announcement from the provider DID authorizing that proof hash
        change.
        """
        magic_condition: Program = Program.to(
            [
                -10,
                self.eml_lineage_proof.to_program(),
                [
                    Program.to(self.eml_lineage_proof.parent_proof_hash),
                    self.launcher_id,
                ],
                [
                    provider_innerpuzhash,
                    self.coin.name(),
                    Program.to(new_proof_hash),
                    None,  # TP update is not allowed because then the singleton will leave the VC protocol
                ],
            ]
        )
        return magic_condition

    def activate_backdoor(
        self, provider_innerpuzhash: bytes32, announcement_nonce: bytes32 | None = None
    ) -> tuple[CreatePuzzleAnnouncement, CoinSpend]:
        """
        Activates the backdoor in the VC to revoke the credentials and remove the provider's DID.

        Returns the announcement we expect from the provider's DID authorizing this, and the spend of the VC.
        Sync attempts by this class on spends generated by this method are expected to fail. This could be improved in
        the future with a separate type/state of VC that is revoked, but perfectly useful as a singleton.
        """
        vc_solution: Program = solution_for_singleton(
            self.singleton_lineage_proof,
            uint64(self.coin.amount),
            Program.to(
                [  # solve EML
                    solve_revocation_layer(
                        self.hidden_puzzle(),
                        solve_std_vc_backdoor(
                            self.launcher_id,
                            Program.to((self.proof_provider, self.proof_hash)).get_tree_hash(),
                            self.construct_transfer_program().get_tree_hash(),
                            self.inner_puzzle_hash,
                            uint64(self.coin.amount),
                            self.eml_lineage_proof,
                            provider_innerpuzhash,
                            self.coin.name(),
                            announcement_nonce,
                        ),
                        hidden=True,
                    ),
                ]
            ),
        )

        expected_announcement: CreatePuzzleAnnouncement = CreatePuzzleAnnouncement(
            std_hash(self.coin.name() + Program.NIL.get_tree_hash() + ACS_TRANSFER_PROGRAM.get_tree_hash())
        )

        return (
            expected_announcement,
            make_spend(self.coin, self.construct_puzzle(), vc_solution),
        )
