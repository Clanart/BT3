## Finding: Confirmed Vulnerability

The trace is real and unmitigated end-to-end.

### Title
Unvalidated GitHub API `html_url`/`clone_url` persisted and later passed to `shell.openExternal` without a scheme allowlist - (File: `app/src/lib/stores/repositories-store.ts`)

### Summary
`RepositoriesStore._upsertGitHubRepository` writes `gitHubRepository.html_url` (and `clone_url`) directly into the local Dexie database as `htmlURL`/`cloneURL`, with no validation of scheme or format. [1](#0-0) 

### Finding Description
`_upsertGitHubRepository` copies `gitHubRepository.html_url` verbatim into `updatedGitHubRepo.htmlURL`, and that value is used unchanged to construct the persisted `GitHubRepository` model: [2](#0-1) 

That `htmlURL` is later retrieved via `getGitHubHtmlUrl`/`getNonForkGitHubRepository`: [3](#0-2) 

and consumed by `App.viewOnGitHub` (and several other call sites such as `openBranchOnGitHub`, `openIssueCreationPage`, PR/check-run "View on GitHub" handlers) which pass it straight to `dispatcher.openInBrowser`: [4](#0-3) 

`Dispatcher.openInBrowser` calls `AppStore._openInBrowser`, which calls `shell.openExternal(url)` with no scheme check: [5](#0-4) 

`shell.openExternal` in the renderer proxies via IPC to the main process's `open-external` handler: [6](#0-5) 

And critically, the main-process handler does **not** reject non-http(s) schemes — it only logs when the URL happens to start with `http://`/`https://`, then unconditionally calls `shell.openExternal(path)` regardless of the actual scheme: [7](#0-6) 

So a malicious or MITM'd GitHub Enterprise API response returning e.g. `html_url: "file:///etc/passwd"` (or a custom OS URI handler scheme) would be persisted verbatim in the local repo database, and later reach Electron's `shell.openExternal` unfiltered when the user clicks "View on GitHub" or similar actions.

### Impact Explanation
`shell.openExternal` with a `file://` URL opens the file in the OS default handler (potentially executing/rendering attacker content locally), and with a custom-registered URI scheme it can invoke arbitrary installed OS handlers (a well-known Electron `shell.openExternal` RCE/abuse vector on Windows and other platforms). Because there is no scheme allowlist anywhere along the persist → retrieve → open path, this is a full path from an untrusted API response (repository/API object under attacker/GHE-server control) to OS-level action.

### Likelihood Explanation
Requires the attacker to control or MITM a GitHub Enterprise API endpoint the user has already added as an account (matches the described scope: "a GitHub API object" is attacker-controlled), and requires the user to click a "View on GitHub"-style action for the affected repository/branch/PR/check. This is a normal, expected user action, not an unnatural step, so likelihood is meaningful for GHE users pointed at a malicious/compromised endpoint.

### Recommendation
- Enforce a strict `http:`/`https:` scheme allowlist for `htmlURL`/`cloneURL` at ingestion time in `_upsertGitHubRepository` (reject or null out non-http(s) values before persisting).
- Additionally/defensively, enforce the same allowlist check in the main-process `open-external` IPC handler in `app/src/main-process/main.ts` before calling `shell.openExternal`, rather than only logging on http(s) prefixes.

### Proof of Concept
1. Configure a GitHub Enterprise account against a malicious/mocked API server.
2. Have the mocked `/user/repos` or repository-fetch endpoint return an `IAPIFullRepository` with `html_url: "file:///etc/passwd"`.
3. Add/refresh that repository in Desktop; `_upsertGitHubRepository` persists `htmlURL: "file:///etc/passwd"` into the repositories DB (confirmed by existing test pattern in `app/test/unit/repositories-store-test.ts`, which asserts `htmlURL` is stored exactly as returned).
4. Right-click the repository → "View on GitHub" → `viewOnGitHub` → `getGitHubHtmlUrl` → `dispatcher.openInBrowser("file:///etc/passwd")` → `shell.openExternal` → main process `open-external` handler → `shell.openExternal("file:///etc/passwd")`, opening the local file with the OS default handler.
