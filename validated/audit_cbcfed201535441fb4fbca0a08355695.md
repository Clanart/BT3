## Title
Unvalidated `number` field from GitHub API issue objects can corrupt commit message text via `#${item.number}` interpolation - (File: `app/src/ui/autocompletion/issues-autocompletion-provider.tsx`)

### Summary
`IssuesAutocompletionProvider.getCompletionText` blindly interpolates `item.number` into the completion string `#${item.number}` without validating that it is actually a safe integer. The `number` field originates from a remote GitHub API response (`fetchIssues` in `app/src/lib/api.ts`), is passed through `IssuesStore.storeIssues`/`getIssuesMatching` unchanged, and is only compile-time typed as `number` via `IAPIIssue`/`IIssueHit` — there is no runtime check (e.g. `Number.isInteger`) anywhere in this path.

### Finding Description
The relevant flow is:
1. `IssuesStore.refreshIssues` calls `api.fetchIssues(...)`, deserializing whatever JSON body the GitHub host (or a malicious/compromised proxy in an enterprise setup) returns, into `IAPIIssue[]`. [1](#0-0) 
2. `storeIssues` copies `i.number` straight into the local Dexie-backed `IIssue` record without validation. [2](#0-1) 
3. `getIssuesMatching`/`getAllIssueHitsFor` returns these records unchanged as `IIssueHit`, whose `number` field is only statically (TypeScript, not runtime) typed as `number`. [3](#0-2) [4](#0-3) 
4. `IssuesAutocompletionProvider.getCompletionText` interpolates that value directly into the text that gets inserted into the commit-summary/description editor when the user accepts the autocomplete suggestion. [5](#0-4) 

Because JSON parsing does not enforce TypeScript interfaces at runtime, a malicious or compromised GitHub Enterprise server / MITM response for the issues endpoint could supply a `number` field that is not a plain integer (e.g. a string containing arbitrary characters, or an object). This value would flow unchanged into the text inserted into the commit message when the user picks that autocomplete suggestion, breaking the invariant that `getCompletionText` produces a safe `#<int>` token.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes" — a listed valid impact category. If an attacker can control the `number` field of an issue returned by the API (e.g., via a compromised/spoofed GitHub Enterprise endpoint or a MITM on an insecure connection), they could cause arbitrary text to be silently inserted into a user's commit message when the user selects the autocomplete suggestion, without the user realizing that inserted text is not a normal `#123` issue reference. This does not achieve code execution or file/credential access — the impact is limited to text-content corruption in the commit message.

### Likelihood Explanation
Likelihood is low. Exploitation requires the attacker to control or manipulate the response of the trusted GitHub API/GHE host contacted over HTTPS with the user's authenticated account (i.e., either a compromised GitHub server, a GHE instance the attacker administers, or a successful MITM/TLS-bypass), none of which are within normal unprivileged attacker capabilities against github.com. There is also no evidence in the reviewed code that ordinary repository content or unauthenticated deep links can influence this `number` field — it's populated solely from the authenticated Issues API response. I was unable to fully inspect `app/src/lib/api.ts`'s `IAPIIssue` interface and `fetchIssues` implementation (file appeared largely empty aside from the import line in my read), so I could not verify whether any parsing/validation exists there that might reject non-numeric `number` fields before they reach the store.

### Recommendation
Add a runtime guard when mapping API issues into `IIssue`/`IIssueHit` (e.g., `Number.isInteger(i.number)` check, skipping/rejecting malformed entries), and defensively coerce/validate in `getCompletionText` (e.g., `Number.isInteger(item.number) ? `#${item.number}` : ''`) before interpolating into user-facing/committed text.

### Proof of Concept
Not independently confirmed end-to-end due to inability to inspect `app/src/lib/api.ts`'s `fetchIssues`/`IAPIIssue` definitions in this session (file content returned empty). Conceptually: mock `IssuesStore.getIssuesMatching` (or the underlying `fetchIssues` API call) to resolve an issue hit `{ number: "1\nmalicious text", title: "x" }`, trigger autocompletion in the commit summary field, select the suggestion, and inspect the resulting text — `getCompletionText` would produce `` `#1 malicious text` `` verbatim since no runtime validation of `number` occurs in the traced path.
