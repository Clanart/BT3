## Title
Partial-commit line selections are re-applied against a freshly re-fetched diff, letting a stale selection silently stage the wrong lines - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop lets a user stage a subset of the lines in a modified file (a "partial commit"). The UI records the user's choice as a bitmap of absolute line indices (`DiffSelection`) against the `IDiff`/hunks that were rendered on screen. When the user actually commits, Desktop does **not** reuse that diff. Instead `applyPatchToIndex` independently re-runs `git diff` to obtain a brand-new `IDiff`, and then reuses the *old* selection bitmap positionally against the *new* hunk/line layout to build the patch that is fed to `git apply --cached`. [1](#0-0) 

### Finding Description
The verification/selection step (what the user reviewed and checked/unchecked in the Changes view) and the enforcement step (what actually gets staged and committed) operate on two different snapshots of the same file:

1. The renderer computes an `ITextDiff` via `getWorkingDirectoryDiff` and the user builds a `DiffSelection` where `isSelected(absoluteIndex)` is keyed to line positions in *that* diff.
2. At commit time, `_commitIncludedChanges` passes the (already staged) `WorkingDirectoryFileChange`, carrying the old `selection`, into `createCommit` → `stageFiles` → `applyPatchToIndex`. [2](#0-1) [3](#0-2) 
3. `applyPatchToIndex` calls `getWorkingDirectoryDiff(repository, file)` **again**, generating a second, independent diff from the current on-disk state. [4](#0-3) 
4. `formatPatch` then walks the *new* diff's hunks and decides whether each line is included using `file.selection.isSelected(absoluteIndex)` — an index computed from the *old* diff. [5](#0-4) 

If the working-tree contents of the file being partially committed change between the moment the user reviews/selects lines and the moment `applyPatchToIndex` re-diffs the file, the hunk boundaries and line offsets shift. The stale positional bitmap then lands on different, unrelated lines in the new diff — lines the user never looked at, let alone selected. Git happily applies whatever hunk `formatPatch` constructs (`git apply --cached -`), so there is no re-verification that the committed content matches what was shown in the UI.

Nothing in `createCommit`, `stageFiles`, or `applyPatchToIndex` re-validates that the diff used to build the patch is the same diff the selection was made against — there is no diff/version stamp, hash, or generation check comparable to a "balances snapshot," so the mismatch is silent. [6](#0-5) 

### Impact Explanation
This breaks the core guarantee of the partial-commit feature: "only the lines I explicitly selected end up in the commit." A shifted patch can cause Desktop to:
- Silently include working-tree content the user never reviewed or intended to commit (e.g. secrets, debug code, or content an external/attacker-influenced process wrote into the file), or
- Silently drop lines the user explicitly selected, producing a commit that differs from what the user believes they pushed.

Either outcome is a "silent corruption of what the user commits" — the class of impact explicitly called out as in-scope.

### Likelihood Explanation
The window is real but narrow: it requires the tracked file's on-disk bytes to change (line-count/offset-affecting change) between the user finishing their hunk/line selection and the click on "Commit," while the stale `WorkingDirectoryFileChange`/`DiffSelection` object is still what's passed to `_commitIncludedChanges`. This can happen without any unusual user action whenever something else touches the file in that window (auto-formatters/build tools/editors, a background `git` operation Desktop itself triggers, or line-ending/`.gitattributes` normalization differences introduced by content fetched into the working tree). No admin rights, local malware, or social engineering is required; it only needs an ordinary, timing-dependent write between two `git diff` invocations Desktop performs against the same path.

### Recommendation
Do not re-derive the diff at patch-apply time. Persist (or hash/fingerprint) the exact `IDiff`/hunks the user's `DiffSelection` was computed against, pass that same diff object through `stageFiles` → `applyPatchToIndex` → `formatPatch`, and fail the commit (forcing a refresh of the Changes view) if the file's current content/hash no longer matches what was used to build the selection, rather than silently reusing stale line indices against a newly fetched diff.

### Proof of Concept
1. In a repo, modify `foo.txt` and open the Changes view; Desktop computes `ITextDiff` D1 with hunks H1.
2. Select only specific lines in H1 (e.g., lines 10-12) via the diff view, producing `DiffSelection` S1 keyed to D1's absolute line indices.
3. Before clicking Commit, let something else (e.g., an editor autosave, a build/format step, or line-ending normalization) insert/remove lines earlier in `foo.txt`, shifting subsequent line offsets, and re-save the file — Desktop's UI still shows the stale S1/D1 pairing since the user hasn't manually refreshed.
4. Click Commit. `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) calls `getWorkingDirectoryDiff` again, producing D2 with shifted hunks H2; `formatPatch` (`app/src/lib/patch-formatter.ts:143-157`) applies S1's absolute indices against H2.
5. Inspect the resulting commit: the staged hunk corresponds to different source lines than the ones the user selected in step 2, demonstrating the selection/enforcement mismatch.
