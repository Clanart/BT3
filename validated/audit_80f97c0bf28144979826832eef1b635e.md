### Title
`load_and_reward_commission_accounts` silently drops commission lamports from burn/incinerator accounting when the pre-SIMD-0232 commission account is missing - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
`Bank::load_and_reward_commission_accounts` computes, per commission recipient, how many lamports are actually distributed vs. burned vs. sent to the incinerator, and returns those three totals in `RewardCommissionLamportAmounts` for the caller to reconcile against capitalization/total rewards. When `custom_commission_collector` is inactive and the (pre-SIMD-0232) commission account cannot be found, the closure takes an early `return None` without adding `*commission_lamports` to `total_non_incinerator_burned_lamports` (or any other counter), unlike every other failure branch in the same function, which explicitly does `fetch_add` before returning `None`.

### Finding Description
The closure inside `load_and_reward_commission_accounts` handles several failure modes for a commission account, and in every other case it accounts for the lamports that failed to land: [1](#0-0) 

- If `checked_add_lamports` overflows, the code does `total_non_incinerator_burned_lamports.fetch_add(*commission_lamports, Relaxed)` before returning `None`. [2](#0-1) 
- If `collector_type_checked` fails (invalid owner/rent state/reserved key), the same accounting is performed before returning `None`. [3](#0-2) 

But the "account missing" branch — reached specifically when `custom_commission_collector` is *not* active and `self.get_account_with_fixed_root_no_cache(commission_pubkey)` returns `None` — just logs a `debug!` and returns `None` with **no** call to `fetch_add` on `total_non_incinerator_burned_lamports` or `total_incinerator_lamports`: [4](#0-3) 

The corrupted value is `RewardCommissionLamportAmounts::burned_lamports` (and, transitively, `distributed_lamports`), assembled at the end of the function: [5](#0-4) 

`burned_lamports` is supposed to be the complement of `distributed_lamports`/`distributed_to_incinerator_lamports` relative to the total commission lamports that were computed to be owed to that vote account for the epoch. In the "missing account" branch, the `commission_lamports` amount is neither added to any account (the account never existed to be credited) nor accounted for as burned — it disappears from the totals entirely. This is the same bug class as the referenced NFTX finding: a code path that is supposed to signal "this transfer did not happen" (so the caller can correctly account for/re-route the funds) instead silently returns without recording that outcome, corrupting downstream bookkeeping that assumes the return value/counter faithfully reflects what happened to the funds.

The comment directly above the `let Some(...) = ... else { ... }` block says this path is believed unreachable in practice ("commission accounts were always vote accounts, which cannot be closed unless the account hasn't voted for at least a full epoch"), which is exactly analogous to NFTX's own defense ("We aren't using any EOAs as receivers in production... this has not been caught") — the guard that's supposed to make the branch impossible is a soft assumption, not an enforced invariant, and the accounting bug exists regardless of whether the branch is hit in the tested configurations.

### Impact Explanation
If this branch is ever taken (i.e., a stake-linked vote account closes/disappears while `custom_commission_collector` is disabled, which can legitimately happen if a validator stops voting for a full epoch before this distribution step is reached — per the code's own comment), the commission lamports for that validator are dropped from both the "distributed" and "burned" totals returned by this function. Any downstream capitalization/reward invariant that relies on `RewardCommissionLamportAmounts` to reconcile total rewards issued vs. burned against `Bank::capitalization` would then be off by the dropped amount, producing an inconsistency in the ledger's fund-accounting invariants for that epoch's reward distribution (false accounting for real fund flows).

### Likelihood Explanation
Low-to-moderate: the code comment states the missing-account condition should not normally occur under the pre-SIMD-0232 (non-custom-commission-collector) path, since vote accounts backing commission collection can't be closed while actively staked/voted within the epoch. However, the condition is reachable by a validator that stops voting for an entire epoch and closes its vote account before reward distribution executes for that historical epoch, which is not an admin/trusted-party-only action — it's within reach of any staked validator operator, i.e., an unprivileged path relative to the network. This mirrors the NFTX report's own risk profile (a rare configuration is what exposes the bug), and was similarly judged real despite the low-probability trigger.

### Recommendation
Account for `*commission_lamports` (and, if appropriate, `*burned_lamports`) in `total_non_incinerator_burned_lamports` (or a distinct "missing account" counter) before returning `None` in the "account missing" branch, mirroring the accounting done in the overflow and `collector_type_checked` failure branches, so that `RewardCommissionLamportAmounts` always fully reconciles against the total commission lamports computed for the epoch.

### Proof of Concept
1. Disable the `custom_commission_collector` feature (pre-SIMD-0232 mode).
2. Arrange for a validator's vote account tied to `reward_commissions` to be closed/absent by the time `load_and_reward_commission_accounts` runs for the epoch (per the code's own comment, achievable if the validator stops voting for a full epoch).
3. Observe that `self.get_account_with_fixed_root_no_cache(commission_pubkey)` returns `None`, hitting: [6](#0-5) 
4. The closure returns `None` without incrementing `total_non_incinerator_burned_lamports`, so the final `RewardCommissionLamportAmounts` (line 1210-1217) undercounts total lamports accounted for by exactly `commission_lamports`, unlike the structurally identical overflow/`collector_type_checked` failure branches which correctly perform the `fetch_add` before returning `None`.
