Confirmed: the Tron-deployment variant of the IntentGateway contract still contains the exact bug class described in the report, while the canonical EVM contract has already been patched for it.

### Title
Fee-on-transfer/deflationary token deposits cause escrow over-crediting and fund insolvency in Tron `IntentGatewayV2.placeOrder` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder` in the Tron variant of `IntentGatewayV2.sol` credits escrow (`_orders[commitment][token]`) using the amount computed from the user-supplied `order.inputs[i].amount` minus the protocol fee, but never verifies how many tokens the contract actually received from `safeTransferFrom`. For any ERC20 input token that does not transfer the full nominal amount (fee-on-transfer, deflationary/rebasing tokens), the contract credits more escrow than it actually holds.

### Finding Description
In `placeOrder`, the reduced escrow amount is computed purely from the caller-declared amount: [1](#0-0) 
and this `reducedInputs[i].amount` is credited directly to escrow after the transfer, without ever measuring the contract's actual balance delta: [2](#0-1) 
This is the exact bug class from the RenovaQuest report: `TokenDeposit`-style accounting is increased by the declared amount, not the amount that `transferFrom` actually moved.

By contrast, the primary EVM contract (`evm/src/apps/IntentGatewayV2.sol`) was explicitly hardened against this: it snapshots balances before/after the transfer and mutates `order.inputs[i].amount` to the measured delta before computing the commitment and crediting escrow: [3](#0-2) 
with an explicit code comment acknowledging the fee-on-transfer risk: [4](#0-3) 
This fix (and dedicated fee-on-transfer regression tests) exists only for the main EVM path: [5](#0-4) 
The Tron contract's `placeOrder`/predispatch-sweep path and its `_withdraw`/`withdraw` release logic still use unverified nominal amounts: [6](#0-5) 

### Impact Explanation
Because `_orders[commitment][token]` is per-order bookkeeping but the underlying ERC20 balance held by the gateway is fungible across *all* orders in that token, over-crediting escrow for one order effectively creates a claim against tokens that were never actually deposited by that order — those tokens can only come from balances belonging to other orders/users in the same token. Any solver filling an order, or user cancelling/refunding, that relies on `_orders[...][token]` will either: (a) succeed in withdrawing more than their order actually contributed, depleting the shared pool at the expense of other legitimate order holders, or (b) revert/be permanently unable to withdraw their rightful amount once the pool is drained by earlier claims — i.e., loss or lock of funds for later beneficiaries. This directly matches the bounty's "stealing or loss of funds" and "false state acceptance" impact categories.

### Likelihood Explanation
No privileged actor, relayer, or prover is required — any unprivileged user can place an order using a deflationary/fee-on-transfer ERC20 as the input token via the public `placeOrder` entrypoint. There is no token whitelist or balance-diff check gating which ERC20s can be used as order inputs in this contract, so exploitation only requires selecting or deploying such a token as the order's input asset.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure the gateway's actual token balance before and after each `safeTransferFrom` (and after the predispatch sweep), use the measured delta — not the caller-declared amount — to compute `reducedInputs`, the commitment hash, and the escrow credit in `_orders[commitment][token]`. Alternatively, restrict input tokens to a vetted whitelist that excludes fee-on-transfer/rebasing tokens.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee, as in `FeeOnTransferToken` from the existing EVM test suite: `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` lines 2501-2547).
2. User approves and calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: FOT, amount: 1000e18}`.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` actually delivers only 990e18 to the contract (1% burned/fee), but `_orders[commitment][FOT] += reducedInputs[0].amount`, where `reducedInputs[0].amount` is derived from the full `1000e18` (minus protocol fee only), i.e. credited as ~1000e18 (or `1000e18 * (1-protocolFeeBps)`), not `990e18`.
4. Repeat with additional orders using the same FOT token; the sum of all `_orders[*][FOT]` now exceeds `IERC20(FOT).balanceOf(address(gateway))`.
5. When solvers/users call `withdraw`/`onGetResponse` to release escrow for these orders, the last claimants attempting `token.call(transfer.selector, beneficiary, amount)` in `_withdraw`-equivalent logic will fail or drain balance meant for others, depending on withdrawal order — demonstrating fund loss/lock caused purely by the escrow-accounting mismatch.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount");

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
