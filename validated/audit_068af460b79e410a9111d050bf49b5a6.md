### Title
Unauthenticated payments to deterministic internal offsets are admitted and misclassified as Branch/Change/Forwarded outputs - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`Scanner::scan_transaction` admits any transaction output solely by matching `script_pubkey` against registered scripts (`networks/bitcoin/src/wallet/mod.rs:199-214`). The internal offsets (`Branch`, `Change`, `Forwarded`) are deterministically derived from public data via `Secp256k1::hash_to_F(KEY_DST, ...)` (`processor/src/networks/bitcoin.rs:308-346`), so any external party can compute these internal-only addresses and pay to them. Like the OpenQ whitelist bypass — where an admission check existed but could be circumvented so an attacker injects an asset the protocol later mishandles — the scanner's script-match is an admission check that cannot distinguish protocol-generated internal outputs from attacker-injected ones, so attacker outputs are admitted under privileged classifications.

### Finding Description
`Scanner::register_offset` inserts `script -> offset` mappings and `scan_transaction` returns a `ReceivedOutput` for any output whose `script_pubkey` is in `scripts`, with no check on provenance, value (beyond the dust filter applied later in `processor/src/multisigs/scanner.rs:564`), or whether the protocol itself created the output. `Bitcoin::get_outputs` then maps each scanned output's offset back to an `OutputType` (`External`, `Branch`, `Change`, `Forwarded`) purely from the offset table (`processor/src/networks/bitcoin.rs:686-700`). Because `BRANCH_OFFSET`, `CHANGE_OFFSET`, and `FORWARD_OFFSET` are `hash_to_F` of fixed public strings under the public group key, an attacker can derive `key + G*offset`, build the identical P2TR script via `p2tr_script_buf` (the offset loop in `register_offset` only enforces evenness, which anyone can replicate), and broadcast a transaction paying to it. The scanner and processor will accept it as an authentic `Branch`/`Change`/`Forwarded` output.

### Impact Explanation
Internal output kinds are intended to exist only when the multisig itself produces them (branch creation for new multisigs, change from its own spends, forwarded funds). Attacker-injected outputs under these kinds pollute the output set the scheduler consumes: the scheduler can be induced to treat adversarial deposits as protocol-internal flows, mis-attribute them (e.g., count them as change or forwardable funds), and build `Plan`s spending inputs the protocol never intended to exist. This matches the report's shape: admission of an asset the whitelist was meant to exclude leads to state corruption — here, corrupted output classification that poisons downstream scheduling and accounting, and can strand or misroute accounting for those inputs since `presumed_origin`/`data` handling assumes genuine internal provenance (`processor/src/networks/bitcoin.rs:707-736`).

### Likelihood Explanation
The attack requires only broadcasting an ordinary Bitcoin transaction — no key material, no collusion, no validator misbehavior. The offset scalars and resulting scripts are fully deterministic and publicly computable by anyone who knows the group key (which is public on the Serai chain) and the fixed `KEY_DST`/`"branch"`/`"change"`/`"forward"` constants. Cost is a single transaction fee plus a ≥546-sat output.

### Recommendation
Bind internal-kind outputs to protocol intent rather than script alone: e.g., only classify an output as `Branch`/`Change`/`Forwarded` if it was produced by a transaction the multisig itself signed (tracked via known plan/tx IDs or eventuality registration), and treat any unmatched payment to internal scripts as `External` (or ignore it). Alternatively, commit per-multisig secret or session-bound data into internal offsets so their scripts are not derivable by third parties.

### Proof of Concept
1. Compute `group_key` (public), `branch_offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch")`, then `branch_key = group_key + GENERATOR*branch_offset` (increment as `register_offset` does until `p2tr_script_buf` returns `Some`).
2. Broadcast a transaction with an output `script_pubkey = p2tr_script_buf(branch_key)`, value ≥ `N::DUST`.
3. `get_outputs` scans the block, `scan_transaction` matches the script, `kinds[offset]` yields `OutputType::Branch`, and the processor emits it as a genuine branch output despite no branch operation occurring.
