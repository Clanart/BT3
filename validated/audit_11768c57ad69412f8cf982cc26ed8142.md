### Title
Insufficient aggregate balance check allows a fee payer to sponsor more fee-delegated transactions than its balance can cover, enabling txpool DoS - (File: `blockchain/tx_pool.go`)

### Summary
Kaia's `validateTx` and `txList.Filter` validate a fee-delegated transaction's fee-payer balance against the fee payer's current state balance on a per-transaction basis. Because the txpool's `pending`/`queue` maps and the `costcap`-based `Filter` logic are keyed by **sender**, not by fee payer, nothing tracks or limits the *sum* of fees a single fee payer has already committed to across multiple sponsored transactions from different senders. This mirrors the reported op-geth `validateMetaTxList` bug class: individually-valid sponsored transactions can collectively exceed the sponsor's real balance.

### Finding Description
In `blockchain/tx_pool.go`, `validateTx` performs the fee-payer balance check like this: [1](#0-0) 

`feePayerBalance` is fetched via `pool.getBalance(feePayer)`, which reads the fee payer's balance from `pool.currentState` (the last mined block's state) — it is not decremented by fees already reserved for other pending/queued fee-delegated transactions sponsored by the same fee payer for different senders.

Because Kaia's txpool organizes transactions in `pool.pending[addr]` / `pool.queue[addr]` per **sender** address (`blockchain/tx_pool.go`), and the cost-based re-validation (`txList.Filter`) is likewise done independently for each sender's list: [2](#0-1) 

there is no cross-sender aggregation for a shared `feePayer`. If attacker-controlled sender addresses `A1, A2, …, An` each submit a fee-delegated transaction naming the same victim/sponsor `feePayer`, with each individual `tx.Fee()` (or `feeByFeePayer` for ratio txs) within the payer's current balance, every transaction passes `validateTx` and is accepted into `pool.pending`. All of them remain in the pool (surviving `promoteExecutables`/`demoteUnexecutables`, which re-run the same per-sender `Filter` check) even though the fee payer cannot actually pay for more than one of them once its balance is exhausted at block-building time.

### Impact Explanation
This is the same DoS bug class as the reported op-geth `validateMetaTxList` issue: the pool accumulates many transactions that the node believes are valid (each satisfies the fee-payer balance check independently), but only the first ones consuming the sponsor's balance can succeed. Since Kaia allows an arbitrary account to act as a fee payer for transactions submitted by *any* sender (see fee-delegated tx types validated via `ValidateFeePayer` in `blockchain/tx_pool.go:938`), an attacker who controls (or colludes with) any senders that reference a target fee payer can occupy substantial pending pool slots and per-account nonce ordering with transactions that will ultimately fail at block-processing time (`buyGas` in `blockchain/state_transition.go:294-376` will reject them once `checkFeePayerBalance` fails against the real depleted balance). This wastes pending-slot capacity, and colliding/failing sponsored transactions can crowd out or delay honest transactions relying on the same sponsor, degrading transaction processing for that fee-delegation relationship.

### Likelihood Explanation
This requires only submitting ordinary, individually well-formed fee-delegated transactions (`TxTypeFeeDelegated*` / `...WithRatio`) from multiple sender-controlled accounts, all naming the same fee payer and using a valid fee-payer signature (fee-delegation requires the fee payer to co-sign the transaction via `SignFeePayerWithKeys`/`ValidateFeePayer`). This means the attack requires cooperation of, or key access to, the fee-payer address (e.g., a sponsor service that automatically countersigns transactions for many users, such as a KIP-247 gasless-style relayer or a general sponsor DApp) — an unprivileged fee-delegation counterparty. No validator/consensus/peer privileges are required.

### Recommendation
Track and enforce an aggregate reserved-cost limit per fee payer across all pending/queued transactions in the pool (not just per-sender), e.g., maintain a `feePayerReservedFee` map updated on tx admission/removal in `addTx`/`removeTx`, and check `feePayerBalance - feePayerReservedFee >= newTxFee` in `validateTx` (`blockchain/tx_pool.go`) and in `txList.Filter` (`blockchain/tx_list.go`) before accepting/keeping a fee-delegated transaction.

### Proof of Concept
1. Fund `feePayer` with balance `B`.
2. Have `N` independent sender keys each submit a `TxTypeFeeDelegatedValueTransfer` transaction with `tx.Fee() ≈ B` (e.g., `gasLimit * gasPrice ≈ B`), each signed by `feePayer` as fee payer (analogous to `feeDelegatedTx` helper used in `blockchain/tx_pool_test.go:290-304`, `TestFeeDelegatedTransaction`).
3. Submit all `N` transactions via `pool.AddRemote`/`AddRemotes`. Each call to `validateTx` independently checks `feePayerBalance.Cmp(tx.Fee()) < 0` against the same unchanged `pool.getBalance(feePayer)` and passes, since none of the checks subtract already-admitted sponsored fees.
4. All `N` transactions are accepted into `pool.pending`, even though the fee payer's actual balance `B` can cover at most one of them — confirming that the pool's admission and demotion logic (`validateTx`, `txList.Filter`) never aggregate fee-payer exposure across senders.
