## Title
Dangling ERC20 `approve` granted to attacker-controlled callback contracts permanently compromises the reusable IBC-callback isolated address - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
The IBC callback keeper's `IBCReceivePacketCallback` grants an ERC20 `approve` allowance from the deterministic, un-signable "isolated address" to the sender-supplied callback contract before invoking that contract, and only verifies that the isolated address ends up with a zero token balance — not that the allowance itself was consumed. Because the isolated address is derived deterministically from `(destChannel, sender)` and is reused for every future packet from that same sender/channel, a callback contract that satisfies the balance check without consuming the granted allowance (e.g. by having the isolated address call `transfer()` directly instead of relying on the contract's `transferFrom()`) leaves a live, unrevoked approval on an address nobody can ever sign for. Any future IBC receive to that same isolated address can then be drained by the previously-designated contract.

### Finding Description
In `x/ibc/callbacks/keeper/keeper.go`, `IBCReceivePacketCallback`: [1](#0-0) 
computes `isolatedAddr := types.GenerateIsolatedAddress(packet.GetDestChannel(), data.Sender)`, whose generation is purely deterministic: [2](#0-1) 
This same address is reused for **every** subsequent ICS-20 packet sent by the same `sender` over the same `channelID` — no one holds a private key for it (per the module's own README, "no user has the ability to sign messages on behalf of this account"). [3](#0-2) 

Before invoking the sender-supplied callback contract, the keeper grants that contract a full ERC20 `approve` from the isolated address for the packet's token amount: [4](#0-3) 
It then invokes the calldata with `msg.sender = receiverHex` (the isolated address): [5](#0-4) 
and — after committing all of this via `writeFn()` — only validates that the isolated address's final balance is zero: [6](#0-5) 

The comment states the intended design: "contracts must implement an `IERC20(token).transferFrom(msg.sender, address(this), amount)` for the total amount, or the callback will fail." However, nothing enforces that the funds actually leave via the granted allowance. The isolated address itself is `msg.sender` for the callback call, so its calldata could just as easily call `token.transfer(dst, amount)` directly (satisfying the zero-balance check) while leaving the `approve(contractAddr, amountInt)` granted moments earlier completely unconsumed and therefore still valid.

Since the isolated address is permanently reused for the same `(channelID, sender)` pair and has no owner who can call `approve(contractAddr, 0)` to revoke it, this dangling allowance persists indefinitely. Any later IBC transfer from the same sender/channel to this address (with or without a callback memo) will mint/unescrow tokens into an account against which an attacker-designated contract already holds a live, unlimited-for-that-amount allowance, enabling that contract to call `transferFrom` completely independently of the IBC pipeline and steal the newly arrived funds.

### Impact Explanation
This allows unauthorized, permanent extraction of user funds from an address that legitimate users cannot ever control or protect (no signing key exists for the isolated address). Because the isolated address is deterministically reused across all future packets from the same sender/channel, a single malicious or compromised callback contract designated once can continuously drain future unrelated transfers routed through the same channel/sender pairing — a critical unauthorized theft of spendable user value via a token-pair-backed/precompile-mediated balance, matching the "theft/unauthorized extraction of user funds ... via precompile-mediated assets" allowed-impact category.

### Likelihood Explanation
Any unprivileged IBC packet sender chooses their own `dest_callback.address` and `calldata` in the packet memo — this is fully within an ordinary user's/attacker's control, requiring no privileged access. The only requirement to trigger the vulnerable state is that the "victim" (attacker's own designated callback contract logic) call `transfer()` instead of `transferFrom()` while still zeroing the isolated balance, which is straightforward for an attacker to construct deliberately.

### Recommendation
Do not leave any residual allowance on the isolated address. After the callback executes, explicitly reset the allowance to zero (`approve(contractAddr, 0)`) regardless of the balance-check outcome, or better, avoid using persistent `approve`/`transferFrom` semantics entirely by having the keeper perform the token transfer to the contract directly (e.g., via `transfer`/`send` initiated by the keeper) rather than delegating that responsibility to attacker-controlled calldata combined with a standing allowance.

### Proof of Concept
1. Attacker sends themself (or colludes with) an ICS-20 transfer with `dest_callback.address = AttackerContract` and appropriate calldata, using `sender = S` on `channel-X`.
2. `IBCReceivePacketCallback` computes `isolatedAddr = GenerateIsolatedAddress("channel-X", S)`, and calls `approve(AttackerContract, amount)` from `isolatedAddr`.
3. The calldata invoked (as `isolatedAddr`) calls `token.transfer(AttackerContract, amount)` directly instead of relying on `AttackerContract` pulling via `transferFrom`. Balance of `isolatedAddr` becomes zero, satisfying the check at [7](#0-6) , so the packet succeeds and all state (including the now-unused `approve`) is committed.
4. Later, any other party sends an unrelated ICS-20 transfer with the same `sender = S` over `channel-X` (with or without a callback), causing new tokens to be minted/unescrowed to the same deterministic `isolatedAddr`.
5. `AttackerContract` calls `token.transferFrom(isolatedAddr, AttackerContract, newAmount)` using the still-valid allowance from step 2, stealing the newly received funds. No signature from `isolatedAddr` is required since it's a pre-approved allowance.

```markdown
## Limitations

The receiver side callback **must** receive funds to an ephemeral address generated from the channelId and packet
sender address. Note that since this is a generated address, no user has the ability to sign messages on behalf of
this account even though it is a cross-chain representation of the packet sender.

Thus, a contract that receives the funds and calldata from the isolated receiver address **must** send the tokens
onwards to a desired address that is specified in the calldata. If tokens are deposited back into the isolated address,
they are unreachabe. If you wish to interact with a contract that does not implement functionality for sending the
tokens to a different address then you must interact with that contract through some wrapper contract interface that
can receive the funds, call the contract which deposits funds back to `msg.sender` and then the wrapper contract
can move the funds to a final desired address.
```
