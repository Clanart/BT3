### Title
Sudden increase of `reward.minimumstake` immediately demotes previously-qualified validators and redirects their staking rewards with no grace period - ([File: kaiax/valset/impl/getter_demote.go])

### Summary
The bug class in the Union Finance report is a threshold (`overdueBlocks`/`maxOverdueBlocks`) that is read live against `block.number` at the moment of an action, with no snapshot taken when the position was created. If the threshold suddenly shrinks, positions that were previously safe are instantly and irreversibly penalized. Kaia's validator-demotion logic in `kaiax/valset` exhibits the same pattern with the governance-controlled `reward.minimumstake` parameter (`MinimumStake`).

### Finding Description
`getDemotedValidatorsIstanbul` computes the set of demoted (non-qualified) validators purely by comparing each council member's **current** staking amount against the **current** governance parameter `pset.MinimumStake`, with no per-validator snapshot of the requirement that applied when they staked: [1](#0-0) 

This parameter is a mutable, votable governance parameter (`reward.minimumstake`, aka "reward.minstake") that any governing node can change via a header-governance vote: [2](#0-1) 

Per the header-governance rules, a parameter ratified at epoch `k` takes effect starting at epoch `k+1` — i.e., practically the very next epoch boundary, with no additional grace/notice period for validators that are already staking below the new threshold: [3](#0-2) 

The exact same live `MinimumStake` threshold is also used by the reward module to decide who receives staking rewards for a block, via `assignStakingRewards`: [4](#0-3) 

Consequently, if `reward.minimumstake` is suddenly raised, at the very next epoch:
1. Validators who staked according to the old (lower) requirement are immediately added to `DemotedValidators`, losing committee/proposer eligibility (`kaiax/valset/impl/getter_demote.go`).
2. The same validators simultaneously stop being counted in `assignStakingRewards`, losing staking rewards starting from the very next block, with the reallocated reward going to the remaining (still-qualified) validators.

There is no mechanism analogous to "caching the parameter value at the time the validator entered the qualified set" (the very mitigation recommended in the referenced report) — the check is always performed against the live parameter value.

### Impact Explanation
A sudden governance-driven increase of `reward.minimumstake` causes an abrupt, un-telegraphed redistribution of consensus power and staking rewards: validators that were fully compliant under the previous rule are demoted and lose reward eligibility starting the very next epoch, with their share redirected to the remaining qualified validators (`kaiax/reward/impl/getter.go` `assignStakingRewards`). This is reward redirection triggered purely by a parameter update, without any snapshot/grace-period protection for validators already staked, and can also abruptly shrink the committee/qualified set used for BFT quorum calculation (`consensus/istanbul/core/core.go` `getRoundCommitteeState`), affecting the live validator/committee composition without prior notice to affected node operators.

### Likelihood Explanation
Changing `reward.minimumstake` is a normal, expected governance action (no special exploit needed) that takes effect automatically at the next epoch boundary per the documented header-governance rules. Any governance vote that meaningfully raises the parameter will deterministically trigger this effect on all validators currently staked below the new threshold, making the scenario straightforward to trigger, even if unintentionally, by ordinary governance operation.

### Recommendation
Consider snapshotting/staggering the effective minimum-stake requirement per validator (e.g., grandfathering existing council members for a transition window, or requiring a minimum number of epochs' notice before a raised `reward.minimumstake` becomes enforceable), similar to the "cache the parameter at the time debt/validator state was established" mitigation recommended in the referenced report, so that governance parameter changes cannot instantaneously strip consensus/reward eligibility from already-compliant validators.

### Proof of Concept
1. Council has validators A, B, C, D with staking amounts of 5,000,001 / 5,000,000 / 5,000,000 / 5,000,000 KAIA, and `reward.minimumstake` = 5,000,000 — all four are qualified, as shown in the existing test data (`Test_BasedOnStaking`, `getter_demote_test.go` lines 402-428).
2. Governing node casts a vote raising `reward.minimumstake` to 5,500,000 KAIA.
3. At the very next epoch, `getDemotedValidatorsIstanbul` (kaiax/valset/impl/getter_demote.go:78-104) re-evaluates the same staking amounts against the new threshold; B, C, D (all below 5,500,000) are now placed in `DemotedValidators`, immediately losing proposer/committee eligibility.
4. In the same block range, `assignStakingRewards` (kaiax/reward/impl/getter.go:486-507) uses the same updated `MinimumStake`, so B, C, D also stop receiving staking rewards, with their share going to A — all without any prior notice or transition window, purely as a side effect of the parameter update taking effect at the epoch boundary.

func getDemotedValidatorsIstanbul(council *valset.AddressSet, si *staking.StakingInfo, pset gov.ParamSet) *valset.AddressSet {
	var (
		demoted        = valset.NewAddressSet(nil)
		singleMode     = pset.GovernanceMode == "single"
		governingNode  = pset.GoverningNode
		minStake       = pset.MinimumStake.Uint64() // in KAIA
		stakingAmounts = collectStakingAmounts(council.List(), si)
	)

	// First filter by staking amounts.
	for _, node := range council.List() {
		if uint64(stakingAmounts[node]) < minStake {
			demoted.Add(node)
		}
	}

	// If all validators are demoted, then no one is demoted.
	if demoted.Len() == len(council.List()) {
		demoted = valset.NewAddressSet(nil)
	}

	// Under single governance mode, governing node cannot be demoted.
	if singleMode && demoted.Contains(governingNode) {
		demoted.Remove(governingNode)
	}
	return demoted
}

The ratification condition is determined by the `governance.governancemode` parameter. Mainnet and Kairos both operate in `single` mode. There are two governance modes:

- `none` mode: all members of the GC can vote. For each governance parameter, the last vote in the epoch will be ratified.
- `single` mode: only one member of the GC, stipulated in the parameter `governance.governingnode`, can vote. All valid votes from the governing node in the epoch are ratified in block order. For each governance parameter, the last vote in the epoch will be ratified.

Parameter change ratified at `k*epoch` block takes effect starting from `(k+1)*epoch` block.
It is worth noting that the effective time of the ratification is `(k+1)*epoch + 1` before Kore.

func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}
