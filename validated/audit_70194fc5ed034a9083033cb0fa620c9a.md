### Title
Unimplemented `TcParser::LazyMessage` fast-path handler causes `LOG(FATAL)` abort when parsing an eagerly-verified lazy message field - ([File: src/google/protobuf/generated_message_tctable_lite.cc])

### Summary
The external report describes a Substrate pallet where a dispatchable call (`force_unreserve`) is reachable through a public interface, but its weight-computation implementation is a stub (`todo!()`), so an attacker-controlled call into that reachable interface triggers a runtime `panic!`/abort instead of a graceful error. The invariant that fails is: *"every code path reachable from an externally-triggerable, schema/attacker-influenced dispatch must be fully implemented, not a stub that aborts the process."*

The nearest genuine analog in this Protobuf checkout is `TcParser::LazyMessage`, a fast-table tail-call parse function that is a literal stub:

```cpp
// src/google/protobuf/generated_message_tctable_lite.cc:706-710
template <typename TagType>
const char* TcParser::LazyMessage(PROTOBUF_TC_PARAM_DECL) {
  ABSL_LOG(FATAL) << "Unimplemented";
  return nullptr;
}
```

This function is wired into the fast dispatch table as `FastMlS1`/`FastMlS2` and is selected by the tail-call table generator (`generated_message_tctable_gen.cc`) whenever a singular `TYPE_MESSAGE` field `HasLazyRep()` — i.e., is a trusted-schema field marked with the lazy field option and is eligible for the fast path. ### Finding Description
Fast-path dispatch entry selection for message-typed fields is done in `MakeFastFieldEntry`:

```cpp
case FieldDescriptor::TYPE_MESSAGE:
  picked = HasLazyRep(field, options)
               ? PROTOBUF_PICK_SINGLE_FUNCTION(kFastMl)
               : PROTOBUF_PICK_REPEATABLE_FUNCTION(kFastMc);
``` [2](#0-1) 

Eligibility for the fast path is gated in `IsFieldEligibleForFastParsing`, which explicitly *excludes* the "fully lazy, not-yet-verified" mode (`kTvLazy`) from the fast path, but leaves the "eagerly verified lazy representation" mode (`kTvEager`) eligible:

```cpp
if (HasLazyRep(field, options) && options.lazy_opt == field_layout::kTvLazy) {
  // We only support eagerly verified lazy fields in the fast path.
  return false;
}
``` [3](#0-2) 

So for a message field whose lazy representation is `kTvEager`, the generated `TcParseTable` fast slot points at `TcParseFunction::kFastMlS1`/`kFastMlS2`, which resolve (via `PROTOBUF_TC_PARSE_FUNCTION_X`) to the real function bodies `TcParser::FastMlS1`/`FastMlS2`:

```cpp
PROTOBUF_NOINLINE const char* TcParser::FastMlS1(PROTOBUF_TC_PARAM_DECL) {
  PROTOBUF_MUSTTAIL return LazyMessage<uint8_t>(PROTOBUF_TC_PARAM_PASS);
}
``` [4](#0-3) 

`LazyMessage<TagType>` is *not implemented* — it unconditionally calls `ABSL_LOG(FATAL) << "Unimplemented";`, which aborts the process (`ABSL_LOG(FATAL)` behaves like `abort()`/`std::terminate`, analogous to the Rust `todo!()` panic in the original report).

**Consuming-application exposure assumption**: A generated `.proto` message that declares a singular message field with the lazy option (`[lazy = true]`, driving `HasLazyRep()`/`kTvEager`) is a *trusted schema decision*, but the *bytes triggering parsing of that specific field* on the wire come from an ordinary, untrusted client calling the message's standard public `ParseFromString`/`MergeFromString`/`ParseFromArray` API — exactly the "attacker sends bounded binary protobuf through a supported public parse API" threat model specified in the rules. The attacker does not need to control the schema, only supply bytes for a tag that the trusted schema has already marked lazy+eager.

### Impact Explanation
Any process that links a generated message type containing an eagerly-verified lazy message field, and calls the standard public parse API (`ParseFromString`/`MergeFrom`/`ParseFromArray`) on attacker-supplied bytes containing that field's tag, will have the fast-path parser dispatch to `TcParser::LazyMessage`, which immediately aborts the process via `ABSL_LOG(FATAL)`. This is a remotely triggerable denial-of-service: a single crafted message causes an unconditional process abort rather than a `false` return / `ParseError`, which is the correctly-implemented behavior for every other field-kind fast-path handler (they all either succeed or `MUSTTAIL return Error(...)` on malformed input). Unlike normal parse failures, this is not catchable/recoverable by the caller: `ABSL_LOG(FATAL)` is a hard process abort, matching the "runtime panic that crashes the process" impact class from the source report.

### Likelihood Explanation
Likelihood depends entirely on whether any linked message type actually has such a field. The lazy field option (`[lazy = true]` with eager verification, `kTvEager`) is a supported, documented C++-only proto2 feature (see the many `lazy_field`/`InternalLazyField`/`LazyMessageLiteTest` references in the tree), and the fast-path table generator (`generated_message_tctable_gen.cc`) deliberately keeps `kTvEager` fields on the fast path while excluding only `kTvLazy`. That deliberate carve-out for "eagerly verified lazy fields" strongly implies the fast path for eager-lazy fields is meant to be supported, yet its handler is an unimplemented stub — this looks like an incomplete C++ tail-call-table feature (the `FastMl` fast-path implementation was apparently never finished) rather than genuinely dead/unreachable code. However, I could not fully verify from the available index whether any currently-shipping, publicly-exposed default `.proto` compilation path actually emits `kTvEager` for real-world message types today (this requires checking `helpers.cc`'s decision of when `lazy_opt` is set to `kTvEager` versus `kTvLazy`/none, which the index did not let me fully trace within the remaining budget). This is the main open uncertainty; if `kTvEager` can currently only be produced for message types that also disable fast-path eligibility for other reasons (e.g. lack of codegen), the bug would be present but effectively unreachable in default builds.

### Recommendation
- **Short term**: Either implement `TcParser::LazyMessage` to correctly parse into the lazy representation, or make `IsFieldEligibleForFastParsing` also exclude `kTvEager` lazy fields from the fast path (falling back to the mini-parse/reflection path, which does have real support for lazy fields), so that `kFastMl`/`LazyMessage` can never be selected by generated code.
- **Long term**: Add a build-time or `ABSL_CHECK`-based assertion in the tail-call-table generator that no `TcParseFunction` value pointing to an unimplemented function body can ever be emitted into a real `TcParseTable`, and add parser fuzz/unit-test coverage specifically for messages with `[lazy=true]` fields to catch this class of "wired-up but unimplemented dispatch target" bug before release.

### Proof of Concept
Conceptual reproduction (schema trusted, payload attacker-controlled):
1. Define a proto2 message `Outer` with a singular message field `inner` carrying the internal lazy option that results in `HasLazyRep(field)==true` and `lazy_opt == field_layout::kTvEager` (this is the internal-only "verify eagerly, store lazily" mode used by some Google-internal/lite lazy-field configurations).
2. Compile with protoc/C++ codegen so that the tail-call table for `Outer` places `kFastMlS1`/`kFastMlS2` in the fast dispatch slot for `inner`'s tag, per `MakeFastFieldEntry` at `generated_message_tctable_gen.cc:225-229`.
3. An ordinary client calls `Outer().ParseFromArray(payload, size)` with `payload` containing a valid tag/length prefix for field `inner` (any length-delimited bytes for that field number).
4. Parsing reaches the fast-table entry, tail-calls into `TcParser::FastMlS1`/`FastMlS2`, which tail-calls `TcParser::LazyMessage<TagType>`, which executes `ABSL_LOG(FATAL) << "Unimplemented";` and aborts the process — regardless of whether the length-delimited payload itself is well-formed.
