### Title
Missing HashMap lookup in PedPoP decryption path panics on unregistered participant, enabling remote crash via crafted blame flow - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The w3m CVE-2016-9443 bug class is "crafted input causes a crash (denial of service)". In Serai, the closest reachable analog is a panic in the PedPoP decryption/blame path: `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` directly, panicking if the named decryptor never registered an encryption key. A DKG participant can reach this with attacker-influenced data by triggering the blame/decryption flow for a participant whose `EncryptionKeyMessage` was absent or never registered.

### Finding Description
`Decryption::register` only inserts into `enc_keys` when a participant's `EncryptionKeyMessage` is processed:

```rust
// crypto/dkg/pedpop/src/encryption.rs
assert!(
  !self.enc_keys.contains_key(&participant),
  "Re-registering encryption key for a participant"
);
self.enc_keys.insert(participant, msg.enc_key);
```

Later, `decrypt_with_proof` verifies the accuser's `EncryptionKeyProof` and then indexes the map with the `decryptor` index passed by the caller:

```rust
// crypto/dkg/pedpop/src/encryption.rs ~line 388
&[self.enc_keys[&decryptor], *proof.key],
```

`HashMap`'s `Index` impl panics on a missing key. `decryptor` is a participant index carried through the blame/decryption call path (`EncryptedMessage::read` / `EncryptionKeyProof::read` are attacker-readable deserialization entry points, and the blame flow is driven by inter-participant messages), so a participant absent from `enc_keys` — e.g., one who never delivered a valid `EncryptionKeyMessage` in the commitments round — causes a panic rather than a `DecryptionError`. The function already has a proper error type (`DecryptionError::InvalidProof`) but returns early on a `None` proof without ever checking membership.

The same pattern exists at `encrypt` (`self.decryption.enc_keys[&participant]` at line 466), which panics if encryption to an unregistered participant is requested.

### Impact Explanation
A panic in library code unwinds into the caller; in the processor's DKG handling this aborts the key-generation attempt and can crash the task/thread processing participant messages. This is a remote, unprivileged denial of service against a validator node reachable through the DKG message flow — the same impact class as CVE-2016-9443 (crafted input → crash). Impact is limited to availability; no secret material is leaked.

### Likelihood Explanation
Triggering requires a DKG session where the named `decryptor` has no entry in `enc_keys`. Registration only occurs per successfully processed `EncryptionKeyMessage`, so a missing, dropped, or rejected registration (malformed `enc_key` fails `C::read_G` in `EncryptionKeyMessage::read`) leaves the map incomplete. The blame path is driven by messages any DKG participant can send, so a malicious participant — or merely a failed/missing commitment from one — combined with an accusation referencing them reaches the panic. Moderate likelihood: it requires a specific protocol state but no special privileges.

### Recommendation
Replace the panicking index with a checked lookup:

```rust
let enc_key = self
  .enc_keys
  .get(&decryptor)
  .ok_or(DecryptionError::InvalidProof)?;
```

and use it in the DLEq `verify` call at `crypto/dkg/pedpop/src/encryption.rs:388`. Apply the same treatment to `self.decryption.enc_keys[&participant]` in `encrypt` (line 466). More broadly, audit all `HashMap` indexing on participant-derived keys in `crypto/dkg` for unchecked `[]` access.

// registered an EncryptionKeyMessage (so enc_keys lacks P).

// An EncryptedMessage<Share> and EncryptionKeyProof read from

// decryptor = Participant(3), never registered -> panic on

Note: I verified the panic site and the registration invariant directly in `encryption.rs`, but could not fully trace the upstream caller that selects `decryptor` in the PedPoP blame flow within my remaining tool budget; the reachability argument assumes the blame API accepts an arbitrary participant index for the accused decryptor, which is consistent with how `from`/`decryptor` are threaded as parameters rather than validated against `enc_keys`.
