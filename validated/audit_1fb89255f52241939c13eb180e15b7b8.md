### Title
Unbounded loops over zeroeds/allocateds in TreasuryRebalance(V2) can cause block finalization to exceed the block gas limit - ([File: blockchain/system/rebalance.go])

### Summary
`RebalanceTreasury` in `blockchain/system/rebalance.go` iterates over all `zeroeds` and `allocateds` entries stored in the on-chain `TreasuryRebalance`/`TreasuryRebalanceV2` contract, and additionally invokes `checkZeroedsApproved()` on the contract, which itself loops over every zeroed entry and, for contract-type zeroeds, every approver, calling an external `getState()` for each. This mirrors the BondAggregator pattern (unbounded loop doing per-item external/state calls) but here the caller is not a `view` RPC call — it runs unconditionally as part of block state-transition at the KIP-103/KIP-160 hard-fork block, making the cost hit consensus-critical code instead of merely reverting a read-only query.

### Finding Description
`RebalanceTreasury` is called during block processing at the KIP-103/KIP-160 fork block [1](#0-0) . It calls `result.fillZeroed` and `result.fillAllocated`, each of which loops `numRetired`/`numNewbie` times, doing one EVM call per iteration to fetch each zeroed/allocated entry [2](#0-1) . It then calls `caller.CheckZeroedsApproved(nil)`, which for `TreasuryRebalanceV2` executes `checkZeroedsApproved()` — a Solidity function that loops over all `zeroeds`, and for each contract-type zeroed, calls the external `getState()` and loops over all approvers validating each admin [3](#0-2) . The contract's own comment already flags the risk: "make sure its adminList is not too long because otherwise the for-loops around adminList or approvers may run out of gas" [4](#0-3) .

Unlike the BondAggregator case (a mere `view` RPC getter), here the equivalent cost is paid unconditionally by every node during the state transition of the fork block via `RebalanceTreasury`, gated only by a fixed `gasLimit := uint64(1e8)` per `CallContract` invocation in `Kip103ContractCaller.CallContract` [5](#0-4)  (for KIP-103) — but the V2/KIP-160 path uses `backends.NewBlockchainContractBackend`, and `checkZeroedsApproved` is a single call that must complete within whatever gas budget that backend allows.

### Impact Explanation
If the owner of the (permissioned, admin-controlled) `TreasuryRebalance`/`TreasuryRebalanceV2` contract registers a large number of `zeroeds` (each potentially a multisig-style contract with a large admin list) prior to the target rebalance block, the O(numZeroeds × numApprovers) work inside `checkZeroedsApproved()` and the O(numZeroeds + numAllocateds) external calls inside `fillZeroed`/`fillAllocated` could exceed the gas budget allotted to the internal contract call, causing `RebalanceTreasury` to fail or behave inconsistently across nodes at the hard-fork block — a block that all nodes must process identically. Because this executes inside block finalization rather than as an optional RPC read, a failure or excessive cost here risks state divergence or block-processing failure at a hard-fork boundary, which is a higher-severity class of issue than a reverting view call.

### Likelihood Explanation
Likelihood is low-to-moderate: `registerZeroed`, `registerAllocated`, and admin-list sizing of the "zeroed" multisig contracts are controlled by the contract `Owner` (a privileged/governance role), not by an arbitrary unprivileged transaction sender. The contract's own inline documentation acknowledges the risk but argues it is unlikely "as it takes a few million gas" and normal use cases stay well under 1000 admins [4](#0-3) . This is therefore reachable only via privileged/administrative action rather than a fully permissionless path, which weakens (but does not eliminate) the applicability of the M-12 analog since the rules require reachability "from a single submitted transaction, bundle, bid, or RPC call" by an unprivileged actor — registration here requires `onlyOwner`.

### Recommendation
Add a pagination mechanism (start/stop indices, or a maximum enforced count) to `registerZeroed`/`registerAllocated` and to `checkZeroedsApproved`/`_validateAdmin` loops in `contracts/testing/system_contracts/TreasuryRebalanceV2.sol` (and the KIP-103 equivalent), and correspondingly update `blockchain/system/rebalance.go`'s `fillZeroed`/`fillAllocated` to page through entries rather than assuming a single call can enumerate everything within the available gas. Additionally, enforce a hard cap on the number of zeroeds/allocateds and on admin-list length at registration time so the fork-block state transition cannot be pushed out of the deterministic gas budget.

### Proof of Concept
Not applicable as unprivileged PoC: triggering the unbounded loop requires the `TreasuryRebalance(V2)` contract `Owner` to register many `zeroeds` (optionally pointing at contracts with very large `adminList`s returned from `getState()`) before the configured `rebalanceBlockNumber`; at that block, all nodes will execute `RebalanceTreasury` → `fillZeroed`/`fillAllocated`/`CheckZeroedsApproved`, which iterate over every entry and, for contract zeroeds, every admin, per [2](#0-1)  and [3](#0-2) . Because registration is owner-gated, this is a governance/administrative-scope issue rather than a fully permissionless-transaction analog to the original BondAggregator report.

func (result *rebalanceResult) fillZeroed(contract RebalanceCaller, state *state.StateDB) error {
	numRetiredBigInt, err := contract.GetZeroedCount(nil)
	if err != nil {
		logger.Error("Failed to get ZeroedCount from TreasuryRebalance contract", "err", err)
		return err
	}

	for i := 0; i < int(numRetiredBigInt.Int64()); i++ {
		ret, err := contract.Zeroeds(nil, big.NewInt(int64(i)))
		if err != nil {
			logger.Error("Failed to get Zeroeds from TreasuryRebalance contract", "err", err)
			return err
		}
		result.Before.Zeroed[ret] = state.GetBalance(ret)
		result.After.Zeroed[ret] = state.GetBalance(ret) // will be set as zero if rebalance succeeds
	}
	return nil
}

func (result *rebalanceResult) fillAllocated(contract RebalanceCaller, state *state.StateDB) error {
	numNewbieBigInt, err := contract.GetAllocatedCount(nil)
	if err != nil {
		logger.Error("Failed to get AllocatedCount from TreasuryRebalance contract", "err", err)
		return nil
	}

	for i := 0; i < int(numNewbieBigInt.Int64()); i++ {
		ret, err := contract.Allocateds(nil, big.NewInt(int64(i)))
		if err != nil {
			logger.Error("Failed to get Allocateds from TreasuryRebalance contract", "err", err)
			return err
		}

		result.Before.Allocated[ret.Addr] = state.GetBalance(ret.Addr)
		result.After.Allocated[ret.Addr] = ret.Amount
	}
	return nil
}

    function checkZeroedsApproved() public view {
        uint256 numZeroeds = zeroeds.length;
        for (uint256 i = 0; i < numZeroeds; i++) {
            Zeroed memory zeroed = zeroeds[i];
            bool isContract = isContractAddr(zeroed.addr);
            if (isContract) {
                (address[] memory adminList, uint256 req) = _getState(zeroed.addr);
                require(zeroed.approvers.length >= req, "min required admins should approve");
                //if min quorom reached, make sure all approvers are still valid
                address[] memory approvers = zeroed.approvers;
                uint256 numApprovers = approvers.length;
                uint256 validApprovals = 0;
                for (uint256 j = 0; j < numApprovers; j++) {
                    if (_validateAdmin(approvers[j], adminList)) {
                        validApprovals++;
                    }
                }
                require(validApprovals >= req, "min required admins should approve");
            } else {
                require(zeroed.approvers.length == 1, "EOA should approve");
            }
        }
    }
