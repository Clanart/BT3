### Title
Tron port of `IntentGatewayV2` lacks any reentrancy protection on fund-moving entrypoints - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The mainline EVM `IntentGatewayV2` contract had the exact bug class described in the external report — a fund-moving settlement function calling out to an attacker-controlled beneficiary via native ETH `.call` before all invariants were locked in — and it was fixed by (1) reordering state writes before external calls (CEI) and (2) adding `nonReentrant` to `fillOrder` and `cancelOrder` as defense-in-depth. The Tron-targeted duplicate of this same intent-settlement contract does not carry either protection.

### Finding Description
The audited/fixed mainline contract explicitly marks its fund-moving entrypoints `nonReentrant`: [1](#0-0) [2](#0-1) 

That protection exists because a beneficiary contract can re-enter during the native-token `.call` made mid-fill, before order-completion state (`_filled[commitment]`) is durably finalized — precisely the "artificially increased share/order value" primitive from the external `TransactionManager.removeLiquidity` report. The project's own regression tests document this exact historical vulnerability and its fix: [3](#0-2) 

A search of the entire `evm/tron/` tree — the Tron-targeted deployment of the same `IntentGatewayV2` contract — for `nonReentrant` or `ReentrancyGuard` returns zero matches, meaning none of its external fund-moving entrypoints (`fillOrder`, `cancelOrder`, the inline same-chain/cross-chain fill paths, `withdraw`) carry any reentrancy guard. Its internal `withdraw` function does perform the state write before external transfers: [4](#0-3) 
but this CEI ordering alone was demonstrably insufficient in the mainline contract to fully close the same-chain fee/escrow theft window (the beneficiary's `receive()` fires mid-loop across the output token array, before `isFullyFilled`/dust/surplus bookkeeping and the calldata `_execute` step complete), which is why the mainline fix additionally required `nonReentrant` on `fillOrder` itself. I was not able to fully inspect the Tron file's `fillOrder`/`_fillSameChain`-equivalent entry logic (outside the 571–735 range retrieved) within the available tool budget, so I cannot confirm with certainty whether the same per-output-token CEI ordering used in `IntrinsicIntents._fillSameChain` was also ported; what is confirmed is the complete absence of the `nonReentrant` modifier that the mainline contract relies on as its primary/hardening guard.

### Impact Explanation
If the Tron contract's fill loop mirrors the pre-fix mainline structure (state finalized only after all outputs are processed, or only inside `withdraw`), a malicious beneficiary can re-enter `fillOrder`/`cancelOrder` during the native-asset `.call{value: ...}("")` and manipulate escrow release, tx-fee release, or surplus/dust accounting — resulting in a solver/attacker receiving more escrowed input tokens or fee-token payouts than they are entitled to, i.e. direct loss of bridged/escrowed user funds. This falls squarely within the bounty's "stealing or loss of funds" / "logic attacks" / "double-settlement" categories for intent settlement.

### Likelihood Explanation
Exploitability requires only that the beneficiary of an order be a contract with a `receive()`/fallback that re-enters — an ordinary, unprivileged intent-gateway user action, not a malicious relayer/prover/admin. No special node or governance conditions are needed; it's directly reachable through the public `fillOrder`/`cancelOrder` entrypoints on Tron. The main uncertainty is whether the CEI-ordering fix that partially mitigates this on the mainline EVM chain was also applied inline in this file's fill logic — since the missing `nonReentrant` guard is confirmed but the full fill-function body was not retrievable in this session.

### Recommendation
Port the same fixes applied to `evm/src/apps/IntentGatewayV2.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`: import a reentrancy guard and add `nonReentrant` to `fillOrder`, `cancelOrder`, and any other external fund-moving entrypoint, and verify (or apply) the same CEI reordering used in `IntrinsicIntents._fillSameChain`/`ExtrinsicIntents._fillCrossChain` so that `_filled[commitment]` is set before any external `.call`/token transfer in the fill path, not only inside `withdraw`.

### Proof of Concept
Mirror the existing `ReentrantBeneficiary` harness used against the mainline contract: [5](#0-4) 
against the Tron contract's `fillOrder`, but without the `nonReentrant` modifier (and without confirmed CEI ordering) present, the reentrant call is not guaranteed to hit an early `Filled()` revert — it can reach the beneficiary's `receive()` mid-fill and re-enter `fillOrder`/`cancelOrder` to double-claim escrow/fees, analogous to the `removeLiquidity` reentrancy in the external report where the reentering call sees stale-but-not-yet-transferred state.

Given the incomplete visibility into the Tron file's fill-loop internals, this should be treated as a confirmed missing-guard finding (verified via exhaustive grep) with an unconfirmed-but-likely full reentrancy path pending direct review of the fill function body by the development team.
