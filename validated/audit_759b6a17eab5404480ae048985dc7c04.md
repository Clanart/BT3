Given the depth of investigation possible within budget, the strongest locally-provable analog to the M‑4 pattern (economically-earned value destroyed by an unrelated "cleanup" path that never checks whether it is still owed) is in `pallet-beefy-consensus-proofs`'s uncle-proof bookkeeping, not in the reward-manager-style pallets (bandwidth, relayer fees, consensus-incentives), whose lazy-materialization paths are all additive (`+=`) and therefore immune to the "close wipes accrued value" shape.

### Title
FIFO proof-height eviction deletes uncle-prover reward bookkeeping before `settle_uncle_proof` can pay out already-earned rewards - (File: `modules/pallets/beefy-consensus-proofs/src/lib.rs`)

### Summary
`pallet-beefy-consensus-proofs` rewards the first prover to submit a valid consensus proof for a finality target immediately, but rewards additional independent ("uncle") provers for the same target through a separate, later call, gated by per-height bookkeeping (`ProofContext`, `ProverCount`, `AcceptedProvers`). That bookkeeping is stored in a bounded FIFO (`MessagingProofs` / `RotationProofs`, capped at `T::MaxStoredProofs`) and is deleted the instant the FIFO overflows — with no check for whether an uncle reward against that height is still outstanding. An uncle prover who has already done the real work (produced a valid SP1 proof for that finality target) can have their entitlement permanently destroyed by ordinary chain progress before they submit it, exactly mirroring the M‑4 pattern: economic entitlement accrues globally/implicitly before the per-actor claim is materialized, and a housekeeping path that only checks a counter (here, FIFO capacity) — not outstanding claims — destroys the entitlement.

### Finding Description
When `submit_proof` accepts a new height, it records uncle-eligibility metadata for SP1 proofs: [1](#0-0) 

The FIFO lists that back this bookkeeping are capped, and pushing past the cap evicts the oldest tracked height and immediately tears down all of its uncle-tracking state: [2](#0-1) 

Note the eviction key is purely FIFO order over accepted heights (`vec.remove(0)` / oldest `set_id`), with no reference to whether any prover has already generated a valid, unsubmitted uncle proof for that evicted height. The pallet's own comment on the mainline reward-skip path confirms `settle_uncle_proof` is a distinct, later call gated on this same per-height state: [3](#0-2) 

This is structurally identical to the M‑4 root cause:
- Global/implicit accrual happens first (a valid SP1 proof for a finality target is real, verifiable, economically-earned work — analogous to the borrower's share-based accrual against `total_shares`).
- Per-actor materialization is lazy and happens on a separate call (`settle_uncle_proof`, analogous to `claim_rewards`).
- A housekeeping/cleanup path (FIFO eviction here, `close_pool_reward` there) destroys the underlying entitlement state using a proxy condition (FIFO slot count / `num_obligation_reward_managers == 0`) that has no relationship to whether an entitlement is still outstanding.

### Impact Explanation
On a network processing consensus proofs faster than `MaxStoredProofs` distinct heights can be retained (busy periods, or an adversary flooding `submit_proof` with valid no-op-avoiding but low-value proofs at many distinct heights to churn the FIFO), an honest uncle prover who already produced a valid, correctly-bound SP1 proof for a given finality target loses the ability to ever be paid for it — `settle_uncle_proof` will reject once `ProverCount`/`AcceptedProvers`/`ProofContext` for that height are gone. This is a direct, permanent loss of a prover's economically-earned `$BRIDGE` reward, falling under the accepted "loss of funds" impact category. It requires no malicious peer, relayer, prover, or admin — only ordinary throughput on the chain (or a low-cost stream of valid proofs at increasing heights from any permissionless account, since proof submission is explicitly permissionless and unsigned/self-attributed).

### Likelihood Explanation
`MaxStoredProofs` is a fixed, governance-set bound, while proof submission is unsigned and permissionless — any account can submit valid proofs to advance `latest_height`/rotate authority sets at a rate independent of how quickly a specific uncle chooses to submit its own already-generated proof. The race is between the eviction FIFO depth and normal prover latency, which is exactly the kind of "no special conditions" scenario Sherlock-style logic bugs are scored on: it doesn't need a malicious actor, only two honest independent provers plus enough intervening accepted heights.

### Recommendation
Do not evict per-height uncle bookkeeping purely by FIFO position. Either:
1. Only evict a height's `ProofContext`/`ProverCount`/`AcceptedProvers` once uncle settlement is closed for it (e.g., after a bounded settlement window has elapsed, or once `AcceptedProvers` shows all curve positions have been paid or explicitly forfeited), or
2. Persist a lightweight "uncle window closed" watermark separate from proof-offchain-storage FIFO pruning, so offchain proof bytes can be pruned for storage-cost reasons independently of the on-chain reward eligibility bookkeeping.

### Proof of Concept
Conceptual reproduction (not runnable without the pallet's test harness, which was not available for direct execution in this session):
1. Prover A submits a valid SP1 proof for height H, advancing `latest_height`; `record_uncle_metadata` records `ProofContext[H]`, `ProverCount[H]`, `AcceptedProvers[H]`.
2. Prover B independently produces a second valid SP1 proof for the same finality target H (a legitimate uncle) but has not yet submitted it (e.g., queued for the next block).
3. `T::MaxStoredProofs` further valid proofs at new, higher heights are accepted before B submits (ordinary network activity, not an attack), each going through `MessagingProofs::mutate`/`RotationProofs::mutate`.
4. Once the FIFO for H's proof type reaches its cap, the next accepted height evicts H: `ProofContext::<T>::remove(H)`, `ProverCount::<T>::remove(H)`, `AcceptedProvers::<T>::remove(H)` all execute (`modules/pallets/beefy-consensus-proofs/src/lib.rs:616-621`).
5. Prover B then submits its valid uncle proof for H via `settle_uncle_proof`; per the pallet's own documented invariant, once `ProverCount` position/`AcceptedProvers` state for H is gone, B cannot be rewarded — the reward B already earned by doing the proving work is permanently lost.

I was unable to inspect `settle_uncle_proof`'s exact implementation body in this session (only its behavior as described in a neighboring code comment and the developer docs), so the exact rejection error path is not independently verified from source in this answer — this should be confirmed directly against `settle_uncle_proof` before treating this as final.
