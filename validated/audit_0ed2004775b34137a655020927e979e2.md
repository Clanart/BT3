### Title
Consensus Liquidity reward split uses an unlocked, spot CL-pool balance, allowing reward-share manipulation via flash deposits - (File: kaiax/staking/staking_info.go, kaiax/reward/impl/getter.go)

### Summary
The reward module splits a validator's staking reward between the validator's own reward address (CN) and its associated Consensus Liquidity pool (CL) address in proportion to `StakingAmount` vs. `CLStakingAmount`. `CLStakingAmount` is derived from a spot balance/registry read of the CL pool at a single, predictable snapshot block, with no lock-up or time-weighting analogous to the Sherlock `ProtectionPool` finding where a spot `totalSTokenUnderlying`/`totalSupply` ratio is used to compute an exchange rate. Anyone who can deposit into a CL pool (an unprivileged staker) can inflate `CLStakingAmount` immediately before the snapshot block is captured and withdraw shortly after, skewing the CN/CL reward split in their favor for that snapshot period.

### Finding Description
`consolidatedNode.Split()` divides a reward amount between the CN reward address and its `CLStakingInfo.CLPoolAddr` strictly by the ratio of `StakingAmount` to `CLStakingInfo.CLStakingAmount`: [1](#0-0) 

This ratio is consumed to allocate real minted KAIA reward funds between recipients in both the Kore and Flex reward paths: [2](#0-1) [3](#0-2) 
and again when finalizing the proposer's own share: [4](#0-3) 

`CLStakingAmount` itself is populated straight from a live read of the CL registry / CL pool's balance at a single "source" block, with no accumulation, vesting, or time-weighting: [5](#0-4) 

The staking module documents that this per-validator staking snapshot is captured from a single, well-known and predictable block:
- Before the Kaia hardfork: two staking intervals in the past.
- After the Kaia hardfork: **the immediately preceding block** (`num - 1`): [6](#0-5) 

The test fixtures confirm the CL pool amount is taken directly as the pool contract's native balance (no share accounting is modeled in-repo): [7](#0-6) 

This is structurally the same bug class as the referenced `ProtectionPool._getExchangeRate()` issue: a value-distribution ratio (there, an SToken exchange rate; here, the CN/CL reward split) is computed from a spot balance/supply figure that any unprivileged depositor can inflate immediately before the snapshot is taken, then withdraw immediately after, since there is no mechanism in this client-side accounting to prevent transient balance inflation from being captured as the "official" stake for reward-splitting purposes.

### Impact Explanation
If deposits/withdrawals to a validator's CL pool are permissionless and not subject to a lock-up enforced at the point the client reads the balance (the client only reads a balance/registry value — it enforces no lock itself), an attacker (any staker/CL depositor) can:
1. Submit a deposit transaction into a target validator's CL pool at (or just before) the source block (`num-1` after Kaia HF, i.e., every block).
2. Have this inflate `CLStakingAmount` used in the very next block's reward computation via `consolidatedNode.Split`.
3. Redirect a larger fraction of that validator's minted block reward from the CN reward address to the CL pool (of which the attacker holds a temporarily inflated share).
4. Withdraw the deposited principal immediately afterward, retaining a disproportionate share of the captured reward relative to their genuine, sustained stake.

This is a concrete reward-redirection/value-misappropriation vector reachable from a single submitted transaction by an unprivileged staker, directly impacting block reward distribution correctness (kaiax/reward module) which underpins the token economy and total-supply accounting (kaiax/supply).

### Likelihood Explanation
Likelihood depends on parameters not fully verifiable from this repository: the on-chain lock-up/cooldown behavior of the actual CL pool / PublicDelegation contract (its Solidity source was not found in this repo; only mocks such as `WrappedKaiaMock.balanceOf` returning `account.balance` are present, and `contracts/bindings/publicdelegation/PublicDelegation.go` bindings expose ERC4626-style `convertToAssets/convertToShares/previewDeposit/previewRedeem` functions, suggesting share-based accounting that may include a withdrawal delay not visible in this codebase). If the real CL pool enforces even a one-block deposit lock, the attack narrows to sustained pre-positioning rather than atomic flash manipulation, which would reduce (but not eliminate) the severity. Because `sourceNum = num - 1` after the Kaia hardfork, the snapshot is refreshed every block, making the window of opportunity per-block rather than per-epoch, which increases exploitability compared to the pre-Kaia interval-based snapshot.

### Recommendation
- Do not use an instantaneous CL pool balance as the basis for reward splitting. Use a time-weighted or block-delayed stake snapshot (e.g., require deposits to be effective only after N blocks/epochs, mirroring how CN `StakingAmounts` are already snapshotted at a stable interval before Kaia HF).
- Enforce a minimum holding period for CL pool deposits/shares at the contract level, and have the client additionally cross-check that the CL balance used for a given source block has been stable for a minimum duration before treating it as authoritative for reward splitting.
- Consider using accumulated/average balance over the staking interval rather than the single-block balance in `parseCallResult`/`parsePermissionlessCallResult`.

### Proof of Concept
Conceptual sequence (client-side, based on this repo's logic):
1. Attacker holds a CL-pool share in validator V's `CLPoolAddr`.
2. At block `N-1` (source block for reward computation of block `N` per `sourceBlockNum`, `kaiax/staking/impl/getter.go:330-347`), attacker deposits a large amount into V's CL pool, inflating its balance/`CLStakingAmount` as read by `parseCallResult`/`parsePermissionlessCallResult` (`kaiax/staking/impl/getter.go:211-221`).
3. Block `N`'s reward is computed; `assignStakingRewards`/`assignStakingRewardsFlex` and `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` call `consolidatedNode.Split()` (`kaiax/staking/staking_info.go:169-187`), which now assigns a larger fraction of V's reward to `CLPoolAddr` because `CLStakingAmount` is inflated relative to `StakingAmount`.
4. Attacker withdraws the deposited principal from the CL pool once the reward has been credited, retaining a disproportionate share of the extra reward relative to genuine, non-transient CL depositors and the validator's own CN reward address.

Note: Full exploitability confirmation requires inspecting the actual on-chain CL pool/PublicDelegation contract's deposit/withdrawal timing rules, which are not present in this repository (only client-side read logic and ERC4626-style bindings were found); this should be verified against the deployed CL pool contract before treating this as conclusively exploitable.

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}

// Returns the allocation and the remainder.
func assignStakingRewardsFlex(config *reward.RewardConfig, budget *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		minStake  = config.MinimumStake.Uint64()
		threshold = config.StakingRewardThreshold.Uint64()
		isPrague  = config.Rules.IsPrague

		cns            = si.ConsolidatedNodes()
		excessInt      = make(map[common.Address]uint64)
		totalExcessInt = uint64(0)
	)

	// Calculate the excess stakes (the amount over the threshold) for each CN.
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it. Even if (CNStaking + CLStaking) could be more than minStake,
		// the CNStaking alone must be at least minStake to be eligible.
		if cn.StakingAmount < minStake {
			continue
		}

		amount := cn.StakingAmount
		if isPrague && cn.CLStakingInfo != nil {
			amount += cn.CLStakingInfo.CLStakingAmount
		}

		// Excess is the amount over the threshold (not over minStake).
		if amount > threshold {
			excessInt[cn.RewardAddr] = amount - threshold
			totalExcessInt += excessInt[cn.RewardAddr]
		}
	}

	// Distribute the budget to the CNs based on the excess stakes.
	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(budget)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		if excessInt[cn.RewardAddr] <= 0 {
			continue
		}
		excess := new(big.Int).SetUint64(excessInt[cn.RewardAddr])

		// The KAIA unit will cancel out:
		// reward (kei) = excess (KAIA) * budget (kei) / totalExcess (KAIA)
		reward := new(big.Int).Div(new(big.Int).Mul(excess, budget), totalExcess)
		if reward.Sign() <= 0 {
			continue
		}

		// If Prague and CL is configured for this CN, split the reward between CN and CL.
		if isPrague && cn.CLStakingInfo != nil {
			cnAmount, clAmount := cn.Split(reward)
			alloc[cn.RewardAddr] = cnAmount
			alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
		} else {
			alloc[cn.RewardAddr] = reward
		}
		remaining.Sub(remaining, reward)
	}
	return alloc, remaining
}

// assignStakingRewards assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining
}

func sourceBlockNum(num uint64, isKaia bool, interval uint64) uint64 {
	if isKaia {
		if num == 0 {
			return 0
		} else {
			return num - 1
		}
	} else {
		if num <= 2*interval {
			return 0
		} else {
			// Simplified from the previous implementation:
			// if (num % interval) == 0, return num - 2*interval
			// else return num - interval - (num % interval)
			return roundDown(num-1, interval) - interval
		}
	}
}
