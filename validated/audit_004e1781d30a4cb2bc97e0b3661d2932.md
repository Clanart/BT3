### Title
Missing bound check before scaling loop in `jsondec_nanos` allows out-of-range fractional-second digit count to drive a negative-count multiplication loop - (File: upb/json/decode.c)

### Summary
The upb JSON decoder's `jsondec_nanos()` (duplicated in `upb/json/decode.c`, `ruby/ext/google/protobuf_c/ruby-upb.c`, and `php/ext/google/protobuf/php-upb.c`) computes the scaling exponent `exp_lg10 = 9 - digits` *before* validating that `digits <= 9`, mirroring the external report's root cause: an assumed/derived scale value is used in arithmetic before its precondition (a fixed valid range) is confirmed. In the DAI oracle bug, an 8-decimals assumption was applied to an 18-decimals feed, corrupting a downstream calculation; here, a decimal-count assumption (`<=9` fractional digits) is used to compute a multiplier count before that assumption is checked, so if error handling does not unwind execution immediately, the multiplication loop runs with a corrupted (negative) count. [1](#0-0) 

### Finding Description
`jsondec_nanos` parses the fractional-seconds portion of an RFC3339 timestamp string during ProtoJSON parsing of `google.protobuf.Timestamp`/`Duration` well-known types:

```
static int jsondec_nanos(jsondec* d, const char** ptr, const char* end) {
  uint64_t nanos = 0;
  const char* p = *ptr;

  if (p != end && *p == '.') {
    const char* nano_end = jsondec_buftouint64(d, p + 1, end, &nanos);
    int digits = (int)(nano_end - p - 1);
    int exp_lg10 = 9 - digits;
    if (digits > 9) {
      jsondec_err(d, "Too many digits for partial seconds");
    }
    while (exp_lg10--) nanos *= 10;
    *ptr = nano_end;
  }
  ...
}
``` [1](#0-0) 

`digits` is derived directly from attacker-controlled input length (the number of digits after the decimal point in a JSON timestamp string). `exp_lg10 = 9 - digits` is computed *unconditionally*, before the `digits > 9` guard runs. If `digits` exceeds 9 (a client can supply an arbitrarily long run of digits, e.g. `"1970-01-01T00:00:00.0000000000000000001Z"`), `exp_lg10` becomes negative. The code then calls `jsondec_err(d, ...)`, which is expected to abort parsing via `UPB_LONGJMP`/error unwinding in the normal flow, but the subsequent `while (exp_lg10--) nanos *= 10;` statement is still present in the same basic block textually — the correctness of the whole function depends entirely on `jsondec_err` never returning. This is the same class of defect as the oracle bug: a scale/quantity value derived from an assumption about input shape (fixed decimals=8 vs actual 18; digits<=9 vs actual attacker-supplied length) is consumed in a multiplication before/without a hard validation gate that provably prevents the miscomputed path from executing.

The identical pattern is repeated verbatim in three separately-generated upb amalgamations: [2](#0-1)  and [3](#0-2) , confirming this is core upb JSON-decode logic reachable from Ruby, PHP, and any upb-based language binding's public JSON parse entry points (`Timestamp.FromJsonString`/`Duration.FromJsonString`/`Message::mergeFromJsonString`), not a test-only artifact.

By contrast, the C++ `google::protobuf::json` implementation performs the length/order check correctly: it validates `frac_digits == 0 || frac_digits > 9` and returns an error *before* running the `9 - frac_digits` scaling loop [4](#0-3) , showing that the upb variant is the outlier that inverted the check-then-use ordering.

### Impact Explanation
This is unlike the classic financial-oracle case in terms of consequence (there is no monetary value being mispriced), but the structural defect — using a supposedly-bounded scale/quantity in arithmetic ahead of/independent from the bound check — transfers directly. If `jsondec_err`'s error path is ever bypassed, suppressed, or arrives via a code path where the caller does not immediately propagate the failure (e.g. compiled without abort-on-error semantics, or refactored call sites that ignore the status), a negative `exp_lg10` feeds into `while (exp_lg10--) nanos *= 10;`, which becomes a loop bounded only by `int` underflow — practically unbounded from a single client-supplied timestamp string, corrupting the computed `nanos` value or causing excessive CPU consumption on a public ProtoJSON parse path (`Timestamp`/`Duration` field parsing). Because bounded resource-exhaustion analogs are excluded by the rules, and because normal operation of `jsondec_err` does correctly longjmp out (I could not fully confirm the longjmp path's guarantee across every call site within this iteration), the confirmed, always-reachable impact is limited to a code-quality/defense-in-depth gap rather than a demonstrated data-corruption or DoS bug in the current build.

### Likelihood Explanation
Low-to-Medium. The check ordering is objectively wrong (compute-before-validate) and is copy-pasted across three bindings, which is concrening for future refactors of `jsondec_err`, but under the current implementation `jsondec_err` is designed to be non-returning (longjmp-based) for all standard call sites, so the flawed arithmetic line is very likely dead code in practice today. I was not able to fully verify, within the available iterations, whether every call site and every language binding's error trampoline actually guarantees non-local exit before the `while` loop executes; this uncertainty should be resolved by inspecting `jsondec_err`'s definition and the `UPB_LONGJMP` macro at each target binding.

### Recommendation
Reorder the check to occur before computing/using the derived exponent, and use `return`/early-out semantics rather than relying implicitly on `jsondec_err` never returning:
```c
int digits = (int)(nano_end - p - 1);
if (digits > 9) {
  jsondec_err(d, "Too many digits for partial seconds");
  return 0; /* or otherwise guarantee no further use of digits/exp_lg10 */
}
int exp_lg10 = 9 - digits;
while (exp_lg10--) nanos *= 10;
```
Apply the same fix uniformly to `upb/json/decode.c`, `ruby/ext/google/protobuf_c/ruby-upb.c`, and `php/ext/google/protobuf/php-upb.c`, and add an explicit `UPB_ASSERT`/static assertion that `jsondec_err` is `UPB_NORETURN` so future maintainers cannot silently break the invariant this function depends on.

### Proof of Concept
Not independently executed (no tool access to run code in this session). Conceptually: feed `Timestamp.FromJsonString` (or the equivalent `mergeFromJsonString` on a `Timestamp`/`Duration` message in the Ruby or PHP upb-based extension) a JSON string such as `"1970-01-01T00:00:00.0000000001Z"` (10 fractional digits) through the public ProtoJSON parse API. This drives `digits = 10 > 9` in `jsondec_nanos`, at which point `exp_lg10 = 9 - 10 = -1` has already been computed prior to the `jsondec_err` call. Confirming actual reachable impact requires verifying, at each of the three call sites, whether `jsondec_err`'s non-local exit is unconditionally guaranteed in the release build — this verification could not be completed within the current investigation and is flagged as the residual uncertainty for this analog.

absl::optional<int32_t> TakeNanosAndAdvance(absl::string_view& data) {
  int32_t frac_secs = 0;
  size_t frac_digits = 0;
  if (absl::StartsWith(data, ".")) {
    for (char c : data.substr(1)) {
      if (!absl::ascii_isdigit(c)) {
        break;
      }
      ++frac_digits;
    }
    auto digits = data.substr(1, frac_digits);
    if (frac_digits == 0 || frac_digits > 9 ||
        !absl::SimpleAtoi(digits, &frac_secs)) {
      return absl::nullopt;
    }
    data = data.substr(frac_digits + 1);
  }
  for (int i = 0; i < 9 - frac_digits; ++i) {
    frac_secs *= 10;
  }
  return frac_secs;
}
