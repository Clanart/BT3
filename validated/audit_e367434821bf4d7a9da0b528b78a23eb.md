## Title
Unauthenticated operator attribution in payout OP_RETURN allows crediting/framing an operator that never funded the withdrawal - (File: `core/src/builder/transaction/operator_reimburse.rs`, `core/src/verifier.rs`)

### Summary
The `payout_tx`'s OP_RETURN output — the sole piece of on-chain data that identifies *which operator fronted a withdrawal* — is never cryptographically bound to the party that actually supplies the withdrawal funds. The user's presigned input only uses `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY`, which commits solely to the withdrawal input and the same-index user payout output. It leaves the OP_RETURN output (and any additional funding inputs used to cover the withdrawal amount and fee) completely unsigned and mutable. Any unprivileged party who can assemble/broadcast (or RBF-replace) the final transaction can therefore stamp an *arbitrary* operator's x-only pubkey into the OP_RETURN field, hijacking or forging the "who paid this withdrawal" attribution that the rest of the protocol treats as ground truth.

### Finding Description
The payout transaction is built in `create_payout_txhandler`: [1](#0-0) 

Only the input at index 0 is signed by the user with `SinglePlusAnyoneCanPay` (see the test helper that generates this signature): [2](#0-1) 

`SIGHASH_SINGLE|ANYONECANPAY` commits only to input[0] and the output sharing its index (the user payout output). It places **no constraint** on the OP_RETURN output (`operator_xonly_pk.serialize()`) or on any additional funding inputs a broadcaster adds to cover the payout amount/fees. Consequently, the OP_RETURN value is pure self-declared metadata.

Downstream, the verifier's chain-sync trusts this unauthenticated field as the authoritative "payer" record: [3](#0-2) 

That value is persisted as `payout_payer_operator_xonly_pk` and later used to:
1. Decide whether a kickoff is malicious, purely by comparing the OP_RETURN pubkey to the kickoff operator: [4](#0-3) 

2. Let an operator's own automation look up "its" unhandled payout to reimburse, by simply filtering on this same untrusted column: [5](#0-4) 

3. Gate the operator's reimbursement-eligibility check, which only compares the stored `payer_xonly_pk` to its own signer key — never verifying that the operator actually supplied the funds in the payout tx: [6](#0-5) 

Because operator registration itself is permissionless (`set_operator`/`Operator::new` only require funding a collateral UTXO — no privileged role check): [7](#0-6) 

an unprivileged attacker can (a) register cheaply as an "operator," and (b) construct or RBF-replace a payout transaction that reuses the withdrawing user's presigned input/output untouched, adds their own funding input(s) to cover the withdrawal value, and writes an arbitrary target operator's x-only pubkey into the OP_RETURN. Nothing in the protocol verifies that the pubkey in OP_RETURN corresponds to the entity whose funds actually moved the withdrawal.

This breaks the equality that must hold for the reimbursement flow to be sound:
`payer_xonly_pk recorded on-chain == operator whose own funds paid the withdrawal`

### Impact Explanation
This is a "the operator credited versus the party that paid" binding failure. Concretely:
- A targeted, uninvolved operator can be framed as the payer of a withdrawal it never authorized. Its own automation (`get_first_unhandled_payout_by_operator_xonly_pk`, `validate_payer_is_operator`) will pick this up as its own obligation and drive it into the kickoff/BitVM disprove flow for a payout it never funded, exposing its collateral/round slot to unplanned risk.
- Conversely, if the forced kickoff succeeds (nothing in `is_kickoff_malicious`/reimbursement logic checks that the credited operator's own wallet funded the payout — only that the OP_RETURN pubkey matches the kickoff operator), the credited operator ends up reimbursed the full bridge amount from the vault for a withdrawal it never funded. This matches the listed Critical impact: "an operator reimbursed for a payout it never funded."

### Likelihood Explanation
Exploitation requires no special role beyond being able to broadcast a Bitcoin transaction (and optionally cheaply registering as an "operator," which is permissionless). The attack surface is the standard `SIGHASH_SINGLE|ANYONECANPAY` malleability inherent to how the withdrawal input/output pair is signed; nothing additional binds the OP_RETURN or the funding side of the transaction. This makes it directly reachable on mainnet by any actor monitoring withdrawal fulfillment activity, without needing verifier, watchtower, or aggregator privileges.

### Recommendation
Bind the OP_RETURN operator attribution cryptographically to the actual funder of the payout, e.g. by:
- Requiring the funding input(s) added to the payout tx to be spent from (or signed by) the same key as the OP_RETURN-declared operator, and verifying this on the verifier side during `update_finalized_payouts`, or
- Extending the user's presigned commitment to cover the OP_RETURN output (e.g. using `SIGHASH_ALL`-style commitments for a second, operator-specific pre-agreed output) so the operator identity cannot be swapped after the fact, or
- Cross-checking in `is_kickoff_malicious`/`validate_payer_is_operator` that the operator claiming reimbursement is provably the source of the funding UTXO(s) used to satisfy the withdrawal output, not merely the OP_RETURN string.

### Proof of Concept
1. Watch for a withdrawal whose presigned user input/output (`SinglePlusAnyoneCanPay`) is public/known (e.g., in mempool as broadcast by the honest operator, or obtainable off-chain per protocol design).
2. Construct a payout transaction reusing that exact input/output pair, add attacker-controlled funding input(s) sufficient to cover the withdrawal amount + fee (per `create_payout_txhandler`, `core/src/builder/transaction/operator_reimburse.rs:407-436`), and set the OP_RETURN output to an arbitrary target operator's x-only pubkey instead of the attacker's own.
3. Broadcast (or RBF-replace an in-flight competing tx) so this version confirms.
4. Verifier's `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) records `payout_payer_operator_xonly_pk` = the arbitrary target pubkey with no validation against actual fund source.
5. The targeted operator's own node, running `validate_payer_is_operator`/payout automation, treats this as its own payout and proceeds to kickoff, potentially completing reimbursement for a withdrawal it never funded.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
