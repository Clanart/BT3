### Title
Fee-Sentinel Address Collision in `IntentsBase._withdraw` Allows Draining Real Escrowed Fee Tokens - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase` uses a single mapping, `_orders[commitment][tokenAddress]`, to track both per-order token escrow **and** accumulated Hyperbridge relayer/protocol fees, distinguishing the fee "row" only by a hardcoded sentinel address, `TRANSACTION_FEES = address(uint160(uint256(keccak256("txFees"))))`. [1](#0-0) [2](#0-1) 

Because an `Order`'s `inputs[i].token` / `output.assets[i].token` fields are plain `bytes32`-encoded addresses supplied by the order creator with no validation against this reserved sentinel, an attacker can craft an order whose input "token" equals the `TRANSACTION_FEES` address. This overshadows the same storage slot that legitimately holds real, collected relayer fees for that commitment, letting the attacker inflate `_orders[commitment][TRANSACTION_FEES]` without depositing any real value, and then redeem it as if it were genuine fee-token balance in `_withdraw`.

### Finding Description
`_withdraw` (called from both same-chain fill/cancel paths and the cross-chain `onAccept` redeem/refund paths) does two things with the same mapping key space:

1. It transfers out whatever `body.tokens[i].token` says, decrementing `_orders[commitment][token]` generically for any address, with no check that `token != TRANSACTION_FEES`. [3](#0-2) 
2. On `finalize`, it separately reads `_orders[commitment][TRANSACTION_FEES]` and pays it out from the *real* protocol fee token (`IDispatcher(host()).feeToken()`), trusting that this slot only ever holds genuine accumulated relayer fees. [4](#0-3) 

Nowhere in `IntentsBase` (including `_validateParams`, `_fillSameChain`, or `_cancelSameChain`) is there a guard rejecting an order/input/output token address equal to `TRANSACTION_FEES`. [5](#0-4) [6](#0-5) 

Since `TRANSACTION_FEES` is a deterministic, computable non-contract address, an attacker can place an order declaring an input token equal to it. During escrow deposit, `SafeERC20`-style calls against an address with no deployed code succeed silently (an EVM `CALL` to a non-contract address always returns `success = true` with empty return data, which passes OpenZeppelin's `SafeERC20` checks). This lets the attacker "escrow" an arbitrary amount at `_orders[commitment][TRANSACTION_FEES]` without transferring any real value into the contract — directly overshadowing the slot that also accumulates the order's legitimate relayer fees (funded in the real fee token by the protocol dispatch logic, e.g. via `IDispatcher`/host fee accounting). When the order is later filled or cancelled, `_withdraw`'s finalize branch reads this poisoned `_orders[commitment][TRANSACTION_FEES]` value and pays it out of the contract's real fee-token balance to the attacker-controlled beneficiary. [7](#0-6) 

This mirrors the external report's core defect exactly: a single address/state variable is reused for two distinct purposes (a caller-suppliable "which token to move" parameter and an internally-trusted accounting key), and the lack of a temporary/segregated variable or explicit collision check lets attacker-controlled input overshadow and corrupt protocol-held funds accounting.

### Impact Explanation
This is a direct, unprivileged fund-loss vector: an attacker can fabricate a "fee" balance under the reserved sentinel key for any order commitment they control (or that they cause to be created), then redeem real fee-token funds belonging to the protocol/relayers via the normal `_withdraw` finalize path, all without depositing genuine value. This satisfies the bounty's "stealing or loss of funds" / "wrong beneficiary or amount" impact class for the IntentGatewayV2 escrow/settlement flow.

### Likelihood Explanation
The precondition is only that (a) order/input token addresses are not validated against the `TRANSACTION_FEES` sentinel anywhere in the reviewed `IntentsBase`/`IntrinsicIntents` validation code, and (b) `SafeERC20` calls to a non-contract address silently succeed (standard EVM/OZ behavior). Both conditions are satisfied by the code as reviewed; I was not able to inspect `ExtrinsicIntents.sol` (the cross-chain `placeOrder` implementation) in this pass to confirm there is no separate token-allowlist check applied there before escrow, so this should be verified before treating it as confirmed-exploitable end-to-end. No relayer, prover, governance, or malicious-peer assumption is required — only a same-chain order placed and filled/cancelled by the attacker themselves.

### Recommendation
- Reject any `Order` whose `inputs[i].token` or `output.assets[i].token` equals `TRANSACTION_FEES` at order-placement/validation time (in both `ExtrinsicIntents` cross-chain placement and any same-chain equivalent).
- Store fee accounting in a dedicated mapping keyed only by `commitment` (not reusing the general `_orders[commitment][token]` address-keyed map), eliminating the possibility of key collision with caller-supplied token addresses altogether.

### Proof of Concept
1. Attacker computes `T = address(uint160(uint256(keccak256("txFees"))))` (a public constant, `TRANSACTION_FEES`). [1](#0-0) 
2. Attacker places (or triggers placement of) an order whose `inputs[0].token == T` with an attacker-chosen nonzero `amount`. Because `T` has no contract code, the `safeTransferFrom`-style escrow call during order placement succeeds without moving real value, yet `_orders[commitment][T]` is credited with `amount`.
3. Separately, the order's real relayer/protocol fee — funded by the actual fee token — also accumulates at the same key, `_orders[commitment][TRANSACTION_FEES]`, per the intended design shown in `_withdraw`. [4](#0-3) 
4. Attacker fills/cancels the order (`_fillSameChain` / `_cancelSameChain`), invoking `_withdraw(body, isRefund, finalize=true)` with `beneficiary` set to an attacker-controlled address. [8](#0-7) 
5. `_withdraw`'s finalize branch reads the inflated `_orders[commitment][TRANSACTION_FEES]` and transfers that amount of the *real* fee token (`IDispatcher(host()).feeToken()`) from the contract's balance to the attacker's beneficiary — funds the attacker never deposited. [4](#0-3)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
