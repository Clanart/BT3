### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The CKB advisory concerns a node treating data that exists in memory (mempool) as if it were committed chain state, producing inconsistent behavior. The analog in Serai's Bitcoin wallet is `Scanner::scan_block`, which scans every transaction in a block — including the coinbase — and returns coinbase outputs as `ReceivedOutput`s indistinguishable from normal, immediately-spendable outputs.

### Finding Description
`scan_block` iterates over `block.txdata` with no filtering and delegates to `scan_transaction`, which pushes a `ReceivedOutput` for any output whose `script_pubkey` matches a registered script. [1](#0-0)  A coinbase output matched this way is returned with a valid `offset`, `output`, and `outpoint`, and nothing in `ReceivedOutput` marks it as immature. [2](#0-1)  The only mitigation is a doc comment stating "a post-processing pass is needed" — the API itself provides no field to perform that filtering other than the caller re-checking which tx was the coinbase. [3](#0-2) 

The downstream spend path treats every `ReceivedOutput` as spendable: `SignableTransaction::new` accepts them as inputs and the sighash commits to them via `Prevouts::All` with `TapSighashType::Default`. [4](#0-3)  A threshold-signed transaction spending an immature coinbase output is consensus-invalid and will be rejected by the network — yet the funds were reported received and signed for. Serai's own processor had to special-case this by skipping `block.txdata[0]` in `get_outputs`, proving the hazard is real rather than theoretical. [5](#0-4) 

### Impact Explanation
An unprivileged party can reach this path indirectly: a miner (or any integration path feeding a `Block` to `scan_block`) produces a coinbase paying to the scanner's P2TR script. The scanner reports the output as received and spendable, a `SignableTransaction` is built over it, and the FROST signing round produces a valid signature over a transaction Bitcoin consensus rejects until maturity. The result is a wasted signing ceremony, a stuck output in the scheduler's plan set (the outpoint is real, so it occupies plan state), and depending on the integration, funds reported received that are not actually spendable — exactly the class of "uncommitted state treated as committed" inconsistency in the reference advisory.

### Likelihood Explanation
Medium. Coinbases paying to arbitrary P2TR scripts are possible for any miner and common in regtest/test environments (the test suite itself mines coinbases directly to the scanner key in `send_and_get_output`). [6](#0-5)  Severity is bounded because the coinbase output does become spendable after 100 confirmations, and Serai's own processor skips `txdata[0]` — so the exposure is for any consumer of the public `scan_block` API that trusts the doc comment less than the return type. Since `ReceivedOutput` carries no maturity flag, the "post-processing pass" required by the docs is impossible without re-scanning the block externally, making misuse the path of least resistance.

### Recommendation
Either skip `block.txdata[0]` inside `scan_block` (matching the processor's `get_outputs` behavior), or add an `is_coinbase`/maturity field to `ReceivedOutput` so callers can mechanically enforce the documented requirement instead of relying on a comment.

### Proof of Concept
```rust
// networks/bitcoin regtest context (as in tests/wallet.rs::send_and_get_output)
// 1. Mine one block whose coinbase pays p2tr_script_buf(key).
// 2. scanner.scan_block(&block) returns a ReceivedOutput for the coinbase
//    output — identical in shape to a normal spendable output.
// 3. Build SignableTransaction::new(vec![received], &payments, change, None, fee)
//    and run the FROST signing round (TransactionSignMachine::sign).
// 4. rpc.send_raw_transaction(&tx) is rejected by the node:
//    "bad-txns-premature-spend-of-coinbase" — the signed TX is consensus-invalid
//    despite the scanner having reported the funds as received.
```

      res.extend(self.scan_transaction(tx));
    }
