### Title
Wildcard FT allowance in `restrict-assets?`/`as-contract?` is checked per distinct fungible-token type instead of cumulatively, letting an asset move past its post-condition allowance - (File: `clarity/src/vm/functions/post_conditions.rs`)

### Summary
`check_allowances` in `clarity/src/vm/functions/post_conditions.rs` enforces a `with-ft <contract> "*" <amount>` wildcard allowance independently for every distinct fungible-token asset name defined in that contract, rather than bounding the *total* value moved across all of them. Any contract body protected by `restrict-assets?`/`as-contract?` that moves several different token types from the same contract can extract up to `amount` of *each* token type, multiplying the effective allowance by the number of token types instead of capping the aggregate outflow, which is the documented intent ("the allowance applies to **all** FTs defined in `contract-id`").

### Finding Description
`check_allowances` ( [1](#0-0) ) iterates `assets.get_all_fungible_tokens(owner)` and, for each distinct asset (`AssetIdentifier`) moved, builds a `merged` list from (a) exact-match allowances for that asset and (b) wildcard (`"*"`) allowances registered for the same contract. It then checks `*amount_moved > allowance` per merged entry and moves on to the next asset with a **fresh** `amount_moved`/allowance comparison — the wildcard allowance amount is never decremented or summed across the different assets that consume it.

This is inconsistent with how the same file treats STX: STX movement and STX burn are explicitly summed into `total_stx_change` and checked once against the STX allowance ( [2](#0-1) ), specifically to prevent an attacker from using two different "channels" (transfer + burn) to each independently consume the full allowance. No equivalent aggregation exists for FT wildcard allowances across multiple token names, even though the Clarity docs describe `with-ft ... "*" amount` as a single allowance that "applies to all FTs defined in contract-id" ( [3](#0-2) ) — i.e. one intended aggregate cap over a set of different underlying assets, exactly the "several different assets share one quota" pattern described in the external report.

Existing tests only exercise a single token name against a wildcard allowance (`stackaroo` against `with-ft current-contract "*" u100`, e.g. [4](#0-3) ) and never test two distinct token names sharing one wildcard allowance, so this gap is not caught by the test suite.

### Impact Explanation
`restrict-assets?`/`as-contract?` are Clarity's mechanism for bounding how much value a nested/contract-call can move — the equivalent of a transaction post-condition enforced at the language level. A contract author who writes `(with-ft .vault "*" u100)` intending "at most 100 units of value may leave the vault across any of its fungible tokens" actually grants "at most 100 units of *each* fungible token the vault defines." If the vault (analogous to Rio's multi-asset reETH) defines multiple FTs, the protected body can move `numTokenTypes × 100` instead of `100`, i.e. an asset moves past the post-condition/allowance that was meant to bound it. This matches the "asset moving past its post-conditions" Critical-impact category.

### Likelihood Explanation
This is trivially and deterministically reachable by anyone who can supply or influence the body executed inside `restrict-assets?`/`as-contract?` with more than one fungible-token type defined in the wildcarded contract — no privileged role, miner, signer, or admin key is required, and no flash-loan-scale capital is needed. It reproduces on every call, not just under specific market conditions.

### Recommendation
Change the FT wildcard handling in `check_allowances` to track cumulative consumption per wildcard allowance entry (mirroring the combined STX check at lines 678-700): sum `amount_moved` across all asset identifiers that fall under a given wildcard allowance and compare the total against that allowance's amount, rather than re-checking each asset independently against the same untouched allowance value.

### Proof of Concept
```clarity
(define-fungible-token token-a)
(define-fungible-token token-b)
(ft-mint? token-a u1000 current-contract)
(ft-mint? token-b u1000 current-contract)

(as-contract?
  ((with-ft current-contract "*" u100))
  (begin
    (try! (ft-transfer? token-a u100 tx-sender 'SP000000000000000000002Q6VF78))
    (try! (ft-transfer? token-b u100 tx-sender 'SP000000000000000000002Q6VF78))
    (ok true)))
;; Returns (ok true): 200 total FT units moved out of the protected scope
;; despite a single "with-ft ... *" allowance of u100.
```
This can be verified by extending the existing wildcard test pattern in [4](#0-3)  with a second `define-fungible-token` and a second `ft-transfer?` under the same wildcard allowance.

        for (asset, amount_moved) in ft_moved {
            // Build merged allowance list: exact-match entries + wildcard entries for the same contract
            let mut merged: Vec<(usize, u128)> = Vec::new();

            if let Some(allowance_vec) = ft_allowances.get(asset) {
                merged.extend(allowance_vec.iter().cloned());

            if let Some(wildcard_vec) = ft_allowances.get(&AssetIdentifier {
                contract_identifier: asset.contract_identifier.clone(),
                asset_name: ClarityName::from_literal("*"),
            }) {
                merged.extend(wildcard_vec.iter().cloned());
            }

            if merged.is_empty() {
                // No allowance for this asset, any movement is a violation
                record_violation(&mut earliest_violation, MAX_ALLOWANCES as u128);
                continue;
            }

            for (index, allowance) in merged {
                if *amount_moved > allowance {
                    record_violation(&mut earliest_violation, index as u128);
                }
            }
        }
