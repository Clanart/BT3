## Title
Escrowed coins are not restored when `ConvertCoinNativeERC20` fails mid-flight during IBC receive/timeout auto-conversion, permanently trapping user funds - (File: `x/erc20/keeper/msg_server.go`, `x/erc20/keeper/ibc_callbacks.go`)

### Summary
This is the same bug class as the reported `nft_resolve_transfer` issue: a function that is supposed to fully roll back state when a downstream call fails or "must revert" instead only reverts part of the state, leaving other fields/balances mutated. In Cosmos EVM, `Keeper.ConvertCoinNativeERC20` [1](#0-0)  escrows the user's native coins into the module account **before** attempting the ERC20 unescrow transfer, and if the later EVM transfer step fails, the function simply returns the error without restoring the coins it already moved.

### Finding Description
`ConvertCoinNativeERC20` performs, in order:
1. `SendCoinsFromAccountToModule` — moves `amount` of native coin from `sender` into the `erc20` module account. [2](#0-1) 
2. `CallEVM(... "transfer" ...)` — unescrows the ERC20 tokens from the module address to `receiver`. If this EVM call errors, or the `unpackedRet.Value` transfer bool is false, or the post-transfer balance invariance check fails, the function returns an error **without undoing step 1**. [3](#0-2) 

There is no compensating `SendCoinsFromModuleToAccount` (refund) on any of these failure branches, unlike the reported NFT bug where `split_owners`/`approvals` needed to be restored on failure.

This function is invoked from two IBC auto-conversion paths that do **not** wrap the call in a `CacheContext`/rollback boundary:

- `Keeper.OnRecvPacket`, Case 2 (native ERC20 IBC receive): calls `ConvertCoinNativeERC20` directly on the live `ctx`; on error it just returns `channeltypes.NewErrorAcknowledgement(err)`. [4](#0-3) 
- `ConvertCoinToERC20FromPacket` (used for both `OnTimeoutPacket` and `OnAcknowledgementPacket` error-ack refund conversion), Case 2: same call, and on error it swallows the error entirely (emits an event, `return nil`). [5](#0-4) 

Because `Acknowledgement`-based failures in ibc-go's `OnRecvPacket` do not automatically revert `sdk.Context` state changes made by the callback (only a genuine Go `error` return from the ICS4Wrapper stack does that), the coins already pulled into the `x/erc20` module account by step 1 remain stuck there permanently — the user gets neither their original native coin balance nor the ERC20 representation, and there is no code path that returns the escrowed coins from the module account back to the user.

### Impact Explanation
This is a Critical, unprivileged, permanent freezing/loss-of-funds bug: any IBC transfer of a registered native-ERC20-backed denom whose destination-chain ERC20 `transfer` call can be made to fail (e.g., a paused/blacklisting ERC20 implementation, a malicious/non-standard token contract returning `false` instead of reverting, an out-of-gas EVM call, or an unexpected balance due to fee-on-transfer/rebasing token semantics triggering `ErrBalanceInvariance`) results in the user's coins being escrowed into the `erc20` module account with no path to recover them. This matches the "permanent freezing, locking, theft, or unauthorized extraction of user funds ... or token-pair-backed balances" allowed impact category.

### Likelihood Explanation
Triggering this only requires an ordinary IBC transfer of a token registered as a native ERC20 pair where the underlying ERC20 contract's `transfer` can fail or return `false` for the specific recipient/amount (a fairly common pattern for tokens with pausability, blocklists, or non-standard boolean-return semantics), or where `res.Ret`/`Logs`/balance verification doesn't line up (e.g., non-standard token behavior). No privileged access is needed — any relayer delivering such a packet, or any recipient owning a token pair with these properties, can trigger the stuck-fund state.

### Recommendation
In `ConvertCoinNativeERC20`, wrap the escrow + EVM unescrow steps so that any failure after the `SendCoinsFromAccountToModule` call is compensated by sending the coins back to `sender` (or by using `ctx.CacheContext()` for the whole conversion and only calling `writeFn()` on full success), mirroring the fix pattern from the reported bug (restore original state on failure rather than partially applying it). Additionally, review `OnRecvPacket`/`ConvertCoinToERC20FromPacket` call sites to ensure that when `ConvertCoinNativeERC20` fails, the packet processing path either (a) leaves the recipient's original bank balance intact (no conversion attempted state change persists), or (b) explicitly refunds the escrowed amount before returning the error acknowledgement.

### Proof of Concept
1. Register a native ERC20 token pair for denom `X` whose ERC20 contract can be configured (by its owner) to make `transfer` return `false` or revert for a specific address/amount (e.g., a pausable/blacklist ERC20).
2. Have a user hold IBC-transferable `X` and receive an IBC packet crediting them with `X`, triggering `x/erc20`'s `OnRecvPacket` auto-conversion to ERC20.
3. Before/during packet processing, ensure the ERC20 `transfer` call in `ConvertCoinNativeERC20` fails (e.g., contract owner blacklists the recipient, or the token is paused) — this can also be forced via timing with `OnTimeoutPacket`/error-ack refund flow through `ConvertCoinToERC20FromPacket`.
4. Observe: `SendCoinsFromAccountToModule` already moved `X` from the recipient to the `erc20` module account (step 1 succeeded), then the EVM `transfer` fails, and the function returns an error / silently returns nil (depending on path) without refunding.
5. Verify: recipient's `X` balance is now debited into the module account, the ERC20 balance was never minted/transferred, and no subsequent code path exists to return the escrowed native coins to the recipient — funds are permanently stuck.
