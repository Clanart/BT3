### Title
Attacker-spammed dust outputs to the vault script_pubkey are unconditionally reported as received spendable inputs, enabling unspendable-funds inflation and input-set DoS - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`Scanner::scan_transaction` matches only `output.script_pubkey` and reports every output paying to a watched script as a `ReceivedOutput`, with no minimum value, no per-block/tx bound, and no confirmation of economic spendability. `SignableTransaction::new` then blindly consumes whatever inputs it is given — the only sanity checks are non-emptiness, a `NotEnoughFunds` sum check, and the `MAX_STANDARD_TX_WEIGHT` limit which simply errors out. An unprivileged party can send arbitrarily many dust/minimal-value Bitcoin transactions to the Serai P2TR vault address; each one is permanently reported as a received input that is either economically unspendable (worth less than the ~57 vbytes it costs to spend) or actively crowds the input set until transaction construction fails.

### Finding Description
`Scanner` keeps a `HashMap<ScriptBuf, Scalar>` of watched scripts and `scan_transaction` pushes a `ReceivedOutput` for every output whose `script_pubkey` matches — no value threshold, no cap:

```rust
// networks/bitcoin/src/wallet/mod.rs:199-214
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput {
    offset: *offset,
    output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout),
  });
}
```

On the spend side, `SignableTransaction::new` checks `DUST` (546 sat) only on *payments Serai creates*, never on the inputs it is handed (send.rs:165-169). Every input becomes a `TxIn` and a separate FROST `AlgorithmMachine` / `Schnorr` signature (send.rs:275-284), and the sighash commits to all prevouts (`Prevouts::All`, send.rs:375). If the accumulated inputs make the transaction exceed `MAX_STANDARD_TX_WEIGHT`, `new` returns `TooLargeTransaction` (send.rs:241-243) — there is no input-selection or dust-filtering logic anywhere in the crate.

This mirrors the reference bug: an attacker populates a shared, effectively bounded structure (the spendable input set, bounded by tx weight) with cheap spam entries; the victim must bear the cost of distinguishing/removing them, and there is no mechanism in the wallet to do so.

### Impact Explanation
- Each Taproot input costs ~57 vbytes to spend. An output below `57 * fee_rate` sats is net-negative: spending it burns more in fees than it contributes. At modest fee rates (~10 sat/vB), anything under ~570 sat — i.e. near-dust — is unspendable, yet `get_outputs`/`scan_transaction` reports it as a real received `Output` counted toward the vault balance: funds reported received that are not spendable.
- The attacker can cheaply create hundreds of such outputs (cost ~546 sat each, recoverable to nobody but already-paid). Once enough accumulate, any `SignableTransaction` that must include them (e.g., to reach a payment amount) either pays fees on attacker-chosen inputs (fee drain / griefing — the 1:1 cost asymmetry of the original bug) or, past the weight limit, fails construction entirely: a DoS on the vault's ability to transact until inputs are manually segregated — logic that does not exist in this code.

### Likelihood Explanation
Reachable entirely with public inputs: sending ordinary Bitcoin transactions to a public vault address requires no privilege, no validator status, and no cooperation. The vault `script_pubkey` is derivable from the published group key via `p2tr_script_buf`, so the attack surface is open to anyone who can send Bitcoin transactions. Cost to the attacker is bounded only by the dust relay minimum per output, while the cost to the protocol is a permanently polluted input set and failed/fee-draining transaction construction.

### Recommendation
- Enforce a minimum economic value on `ReceivedOutput`s before treating them as spendable inputs — e.g., filter in `get_outputs`/`scan_transaction` or in `SignableTransaction::new` on `input.value() < DUST_THRESHOLD * fee_rate`, where the threshold reflects the ~57-vbyte marginal spend cost.
- Implement input selection in `SignableTransaction::new`: prefer largest inputs, stop adding inputs once `input_sat` covers `payment_sat + needed_fee`, and hard-cap input count so `TooLargeTransaction` is unreachable by accumulation.
- Consider tracking and quarantining attacker-sent dust outpoints so the scheduler never selects them.

### Proof of Concept
1. Derive the vault address: `Address::new(p2tr_script_buf(group_key).unwrap())`.
2. Attacker broadcasts N transactions, each paying 546 sat (or any amount below the marginal spend cost) to that script_pubkey — standard P2TR outputs relay fine.
3. `get_outputs`/`scan_transaction` returns all N outputs as `ReceivedOutput`s with `OutputType::External`; they are indistinguishable from legitimate deposits except by value and presumed origin.
4. `SignableTransaction::new(inputs, &payments, change, None, fee)`:
   - With ~600+ spam inputs plus real inputs, weight exceeds `MAX_STANDARD_TX_WEIGHT` → `TooLargeTransaction`, blocking any spend.
   - With fewer, every forced signature pays ~57 vbytes for a sub-546-sat input — net fee drain orchestrated by the attacker, with one FROST signing round required per spam input (send.rs:275-284).
