### Title
SignableTransaction underestimates weight/fee when an OP_RETURN `data` output is present — underpaying fees and bypassing the standardness weight check - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` adds an OP_RETURN output carrying up to 80 bytes of attacker-influenced `data` to `tx_outs`, but computes the transaction weight, virtual size, `needed_fee`, and the `MAX_STANDARD_TX_WEIGHT` standardness check using only `payments` (and optionally `change`). The data output is never included in the size accounting, so the transaction underpays its declared fee rate and can be produced despite being non-standard/under-minimum-relay-fee.

### Finding Description
The OP_RETURN output is pushed at `send.rs:194-202` before the weight calculation, yet the weight/vbytes used for fee purposes come from `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at `send.rs:204`, which expands a dummy transaction containing only `payments` and `change` — no OP_RETURN output. The same omission propagates to the change path (`send.rs:225-226`) and to the standardness check `weight > MAX_STANDARD_TX_WEIGHT` at `send.rs:241`. Consequences:

- `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) underestimates the true vsize by roughly `(8 + 1 + ~1 + 1 + data.len())` bytes (~25 vbytes for 80 bytes of data), so the effective fee rate is below both the requested rate and the value reported by `needed_fee()`.
- The minimum-fee check at `send.rs:211` uses the underestimated `vbytes`, so a transaction can pass `TooLowFee` while its real fee rate is below `DEFAULT_MIN_RELAY_TX_FEE`, making it unrelayable.
- A transaction near `MAX_STANDARD_TX_WEIGHT` can pass the `TooLargeTransaction` check while the actual (data-bearing) transaction exceeds the limit and is rejected by the mempool.

Since `fee()` is `sum(prevouts) - sum(outputs)` (`send.rs:138-141`), the "missing" value is still paid as fee (the change is computed from the underestimated `fee_with_change`), so coins are over-spent on fees while the tx may still be unbroadcastable.

### Impact Explanation
The data field originates from externally supplied instructions that the protocol embeds in Bitcoin transactions it signs. An unprivileged party who can cause a transaction to carry a `data` payload (e.g., via an out-instruction with arbitrary data) can cause the multisig to sign a transaction whose effective fee rate is materially lower than requested — potentially below the node's minimum relay fee or above the standardness weight cap once the OP_RETURN output is counted. The signed transaction is then rejected/stuck, freezing the inputs (which are committed to that specific signed transaction's sighash via `Prevouts::All`) until a new signing round produces a corrected transaction. This is unauthorized degradation of availability of the pool's funds (partial DoS) plus incorrect fee accounting — matching the CVE-2019-2975 class of untrusted data causing unauthorized partial integrity/availability impact.

### Likelihood Explanation
Requires a flow where externally influenced `data` reaches `SignableTransaction::new`, which the Serai protocol does support (arbitrary instruction data is embedded via OP_RETURN). The fee shortfall is deterministic whenever `data.is_some()`; whether it causes an actual broadcast failure depends on the margin between the requested fee rate and the relay minimum, and on proximity to the weight cap. Exploitation is not guaranteed per attempt, consistent with a "difficult to exploit / partial impact" medium-severity analog.

### Recommendation
Include the OP_RETURN output (and any other outputs actually emitted) in `calculate_weight_vbytes` — e.g., pass the constructed `tx_outs`/`Vec<TxOut>` rather than `payments` — so `needed_fee`, the `TooLowFee` check, the change computation, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the true transaction size. Alternatively, compute weight from the final assembled `Transaction` directly.

### Proof of Concept
```rust
// networks/bitcoin context; conceptual PoC
let inputs = vec![received_output];           // ReceivedOutput from Scanner
let payments: &[(ScriptBuf, u64)] = &[];      // no payments
let data = Some(vec![0u8; 80]);               // externally influenced OP_RETURN data

let tx = SignableTransaction::new(inputs, payments, None, data, fee_per_vbyte)?;
// tx.needed_fee() == fee_per_vbyte * vbytes_of(inputs + zero outputs)
// Actual tx includes an OP_RETURN output of ~92 bytes, so the real
// fee rate is lower than `fee_per_vbyte` and lower than implied by needed_fee().
// With fee_per_vbyte near the relay minimum, the real rate falls below
// DEFAULT_MIN_RELAY_TX_FEE and the signed transaction is unrelayable,
// while the check at send.rs:211 still passed.
```
Root cause: `calculate_weight_vbytes(tx_ins.len(), payments, None)` at `networks/bitcoin/src/wallet/send.rs:204` never sees the OP_RETURN output pushed at `send.rs:194-202`, and the `MAX_STANDARD_TX_WEIGHT` check at `send.rs:241` uses the same incomplete `weight`.
