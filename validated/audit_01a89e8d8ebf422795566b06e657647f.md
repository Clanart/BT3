### Title
Partial line-selection state is preserved by line index (not content) across diff reloads, silently corrupting staged/committed hunks - (File: `app/src/lib/stores/app-store.ts`, `app/src/models/diff/diff-selection.ts`)

### Summary
This is a structural analog of the Stakehouse H-04 bug: a per-entity "claim" value (`sETHUserClaimForKnot`) was left stale after a partial state change (`unstake`) instead of being recomputed from the *current* authoritative quantity (`sETHStakedBalanceForKnot`), so a later read used a mismatched basis. GitHub Desktop has the same class of defect in its partial-diff-selection tracking: when the working-directory diff for the currently open file is reloaded, the previously "selected" line indices are carried over and re-validated purely by numeric line index, not by verifying the line's content is still the one the user actually reviewed and selected.

### Finding Description
`DiffSelection` tracks partial selections as a `Set<number>` of "diverging" line indices, with no notion of what content lives at that index [1](#0-0) . When the diff for the selected file is reloaded, `withSelectableLines` recomputes which indices are *selectable* in the new diff and intersects it with the old `divergingLines` set purely by index membership: `this.divergingLines].filter(x => selectableLines.has(x))` [2](#0-1) .

This is invoked from `updateChangesWorkingDirectoryDiff` in the app store, whose own comment acknowledges the gap: *"Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines..."* [3](#0-2) . The new selectable set is built purely from `h.unifiedDiffStart + index` positions in the freshly loaded diff [4](#0-3)  and then applied to the existing selection object with `withSelectableLines`/`withSelection` [5](#0-4) .

If the on-disk content of the currently open file changes between the time the user picks specific lines to stage and the time the diff is silently reloaded (e.g. triggered by the file-watcher-driven status refresh, a checkout, stash pop, or any git operation that mutates the working tree — all of which can be driven by content/hooks/behavior in a cloned or fetched repository the attacker controls), the same numeric line index in the new diff can now correspond to entirely different, attacker-controlled content. Because the "still selected" check is index-based rather than content-based, that new content silently inherits the "selected" (staged-for-commit) status the user never actually reviewed. This is exactly the same broken invariant as the report: a derived/cached value keyed to a quantity (staked balance / selected line) is not recomputed against the new authoritative baseline (remaining stake / new diff content) when that baseline changes.

### Impact Explanation
This falls squarely in "silent corruption of what the user commits or pushes." A user reviewing and partially staging a diff could end up committing/pushing lines they never explicitly selected, because those lines happen to land at the same index as previously-selected lines after the file changes underneath them. In a supply-chain-adjacent scenario, an attacker who can influence what appears in the user's working tree at just the right moment (via a repo they got the victim to fetch/checkout, a hook-driven rewrite, or a race with an editor/tool that resaves the file) can get unreviewed content silently marked "included" in the next commit.

### Likelihood Explanation
The refresh path is not attacker-invoked directly, it's an ordinary Desktop behavior (file watcher → status refresh → `updateChangesWorkingDirectoryDiff`) that runs constantly while a file is open with a partial selection. Any legitimate git/filesystem event that changes the selected file's content (checkout, merge, stash pop, external editor autosave, or a modification introduced by a git hook from a fetched repository) is sufficient to trigger the stale-index reuse; no privileged access or local compromise is required, only that the file be modified while a partial selection is active.

### Recommendation
When recomputing selectable lines after a diff reload, validate divergence by line *content* (e.g., comparing the actual line text/hash at each index) rather than by index alone, or simply drop the previous partial selection entirely whenever the file's diff changes in a way that isn't a pure line-number shift of unchanged content. At minimum, force the UI to clear/highlight discarded selections instead of implicitly carrying line-index-based selection state across diff reloads, mirroring the report's fix of recomputing the state (`sETHUserClaimForKnot`) from the current authoritative balance whenever the underlying quantity changes.

### Proof of Concept
1. Open Desktop on a repository, select a file with a multi-line diff, and select for staging only lines 10–12 (`DiffSelection.divergingLines = {10,11,12}`).
2. While the diff view is open (not yet committed), have the working tree file rewritten so the content at lines 10–12 changes but the total selectable line-index range still includes 10–12 (e.g., another process, an autosave from an editor, a `git checkout -- <file>` from a script, or a git hook the attacker's repo triggers on fetch/merge).
3. Desktop's file watcher fires a status refresh, calling `updateChangesWorkingDirectoryDiff`, which reloads the diff and calls `currentlySelectedFile.selection.withSelectableLines(selectableLines)` [5](#0-4) .
4. Because indices 10–12 are still within the new `selectableLines` set, they remain in `divergingLines` per `withSelectableLines` [2](#0-1) , even though their content is now entirely different from what the user reviewed.
5. The user commits, and `_commitIncludedChanges` includes the file based on this stale per-line selection [6](#0-5) , silently committing content the user never actually selected or reviewed.

    const divergingLines = this.divergingLines
      ? new Set([...this.divergingLines].filter(x => selectableLines.has(x)))
      : null

    return new DiffSelection(
      this.defaultSelectionType,
      divergingLines,
      selectableLines
    )
  }

    const selectableLines = new Set<number>()
    if (diff.kind === DiffType.Text || diff.kind === DiffType.LargeText) {
      // The diff might have changed dramatically since last we loaded it.
      // Ideally we would be more clever about validating that any partial
      // selection state is still valid by ensuring that selected lines still
      // exist but for now we'll settle on just updating the selectable lines
      // such that any previously selected line which now no longer exists or
      // has been turned into a context line isn't still selected.

        h.lines.forEach((line, index) => {
          if (line.isIncludeableLine()) {
            selectableLines.add(h.unifiedDiffStart + index)
          }
        })
      })
    }
