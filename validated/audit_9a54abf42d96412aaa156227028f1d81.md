### Title
Discarding changes inside a symlinked path in a cloned repository can move/delete files outside the repository - (File: app/src/lib/stores/git-store.ts)

### Summary
`GitStore.discardChanges()` resolves the on-disk path for a file the user chooses to discard with plain `Path.resolve()` / `Path.join()` against the repository root, instead of the codebase's own symlink-safe helper `resolveWithin()` (defined in `app/src/lib/path.ts`). `resolveWithin()` exists specifically to defeat symlink/traversal escapes by calling `realpath()` on both the root and the resolved target and verifying containment, and it is already used for this purpose in newer code paths (`app/src/lib/copilot-conflict-context.ts`, `app/src/ui/dispatcher/dispatcher.ts`, `app/src/lib/stores/app-store.ts`). `discardChanges` was never migrated to it. ### Finding Description
The bug-class from the report is "a return value / guard is silently skipped, so an unsafe operation proceeds on attacker-influenced data, corrupting user state." The Desktop analog here is a missing containment guard: `file.path` (and `file.status.oldPath` for renames/copies) is a repository-relative path reported by `git status`, which is data derived from the contents of a cloned/fetched repository. An attacker who controls that repository can create a directory entry that is a symlink pointing outside the working directory (e.g. `evil -> ../../..` or to `$HOME/.ssh`), and then an untracked/modified file appears to Desktop as `evil/some-file` inside the repo.

When the user chooses "Discard Changes" for that file, `discardChanges()` builds the on-disk path with:
```
Path.resolve(this.repository.path, file.path)
```
and, for the "always discard permanently" fallback:
```
Path.join(this.repository.path, file.path)
```
Neither of these calls resolves symlinks or validates that the final path stays under the repository root — that is exactly what `resolveWithin()` was built for, and its own unit tests explicitly document that symlinks are used to escape a root and that `resolveWithin` rejects those cases. Because `discardChanges` bypasses that helper, `shell.moveItemToTrash(...)` or `rm(...)` operate on whatever the OS-level symlink resolution actually points to, which can be outside the cloned repository entirely. ### Impact Explanation
This allows a malicious repository (opened after clone, or added as a local repository the user is induced to browse in Desktop) to cause Desktop, at the user's single "Discard Changes" click, to move an arbitrary file/directory reachable via a symlink into the OS trash, or — in the "always discard permanently" flow — to `rm` it outright. This is a file write/delete outside the intended repository boundary, driven entirely by content the remote/cloned repository controls, matching the "file write or read outside the repo" impact category from the task's Valid Impact list.

### Likelihood Explanation
Exploitation requires only that the victim clone or open an attacker-controlled repository containing a symlinked path and then use the normal "Discard Changes" UI action on a file shown under that symlinked directory — no admin rights, no pre-existing malware, and no unnatural steps beyond the ordinary git workflow of cloning a repo and discarding changes. The project's own `resolveWithin` and its tests demonstrate this exact symlink-escape scenario is a known, previously-mitigated class of issue elsewhere in the codebase, but `discardChanges` was not updated to use it, making the path realistic and reachable through ordinary UI flows (`filter-changes-list.tsx` discard menu action calls into `dispatcher`/`GitStore.discardChanges`). [6](#0-5) 

### Recommendation
In `app/src/lib/stores/git-store.ts`, replace the raw `Path.resolve`/`Path.join` calls in `discardChanges()` with `resolveWithin(this.repository.path, file.path)` (and `file.status.oldPath` where used), rejecting/skipping any file whose resolved path is `null` (i.e., escapes the repository root via traversal or symlink), mirroring the guard already implemented in `copilot-conflict-context.ts` and `dispatcher.ts`.

### Proof of Concept
1. Attacker publishes/serves a git repository containing a symlink `link` at the repo root pointing to `../../../..` (or any external directory), plus a file `link/pwn.txt` that appears untracked in that external location.
2. Victim clones the repository with GitHub Desktop; `git status` reports `link/pwn.txt` as an untracked change (`AppFileStatusKind.Untracked`) because the working tree contains the symlink.
3. Victim selects "Discard Changes" on `link/pwn.txt` from the Changes list (`filter-changes-list.tsx`'s discard menu item).
4. `GitStore.discardChanges()` computes `Path.resolve(repository.path, 'link/pwn.txt')`, which — when passed to `shell.moveItemToTrash` — follows the symlink at the OS level and moves/deletes the real target file, located outside the cloned repository, instead of anything actually inside the sandboxed repo directory. async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
