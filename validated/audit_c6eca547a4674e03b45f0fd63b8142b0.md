### Title
Missing-key panic in PedPoP blame decryption lets a DKG participant crash the node - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2021-28971 is a crash caused by mishandling a status field in a PEBS record: attacker-controlled input reaches a code path that assumes a condition holds and faults when it does not. The Serai analog is `Decryption::decrypt_with_proof` in the PedPoP DKG encryption layer, which indexes `self.enc_keys[&decryptor]` after verifying attacker-supplied proof material, panicking whenever the `decryptor` participant index has no registered encryption key. A participant who submits a crafted encrypted-share/blame message causes an index-out-of-map panic instead of an `Err`, halting the validator's DKG processing.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `decrypt_with_proof` verifies the Schnorr PoP over an `EncryptedMessage` (`msg.pop.verify(...)`), then verifies a supplied `EncryptionKeyProof` DLEq and dereferences `self.enc_keys[&decryptor]`:

```rust
proof
  .dleq
  .verify(
    &mut encryption_key_transcript(self.context),
    &[C::generator(), msg.key],
    &[self.enc_keys[&decryptor], *proof.key],
  )
  .map_err(|_| DecryptionError::InvalidProof)?;
``` [1](#0-0) 

`enc_keys` is populated only via `Decryption::register`, which itself asserts on re-registration:

```rust
assert!(
  !self.enc_keys.contains_key(&participant),
  "Re-registering encryption key for a participant"
);
``` [2](#0-1) 

`decryptor` is a `Participant` value flowing in from the PedPoP share-verification/blame path in `crypto/dkg/pedpop/src/lib.rs`, i.e. derived from untrusted message data (`EncryptedMessage::read` / share vectors read over the wire). Nothing in `decrypt_with_proof` checks membership before indexing the `HashMap`, so a `decryptor` index for which no `EncryptionKeyMessage` was registered — or an index skipped by a malicious dealer — reaches `HashMap::index` and panics rather than returning `DecryptionError::InvalidProof`. The same unchecked indexing pattern exists at `Encryption::encrypt` (`self.decryption.enc_keys[&participant]`). This mirrors the CVE shape exactly: a record field (here, the accused participant's registered-key status) is consumed with an assumed invariant, and malformed attacker-controlled input triggers a fault instead of a handled error.

### Impact Explanation
A single malicious DKG participant can panic the PedPoP verification thread of every honest node evaluating its messages (or a blame built against a crafted `EncryptedMessage`), aborting the key-generation attempt and denying availability of the threshold-signing service. Matching the CVE's CVSS 5.5 (A:H only): no secret material is leaked, but the node process is crashable on demand with public, well-formed-protocol inputs.

### Likelihood Explanation
Reachability requires only that the PedPoP caller passes a `decryptor`/`participant` derived from untrusted share or blame messages without first confirming registration in `enc_keys`. The panic is deterministic (not probabilistic), requires no race or special privileges, and triggers on an ordinary malformed-protocol path rather than an edge-case encoding. The residual uncertainty is whether every higher-level caller filters unregistered participants before invoking `decrypt_with_proof`; the library itself imposes no such check, and `register`'s assert shows the design assumes callers uphold invariants it cannot enforce.

### Recommendation
Replace `self.enc_keys[&decryptor]` with `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?`, and likewise use `.get()` in `Encryption::encrypt`. Downgrade `Decryption::register`'s `assert!` to a returned error so untrusted re-registration cannot panic the process. Every map lookup keyed by a network-supplied `Participant` should return `Err`, never panic.

### Proof of Concept
1. Honest node runs PedPoP with params `(t, n)` and registers `EncryptionKeyMessage`s only for participants `{1..=n}` that actually sent one.
2. Malicious participant sends a validly-formed `EncryptionKeyProof`/`EncryptedMessage` (or triggers a blame) naming a `decryptor` whose enc key was never registered — e.g. by omitting their registration or referencing an index outside the registered set but within `1..=n`.
3. `decrypt_with_proof` passes the `msg.pop` Schnorr check (attacker knows the ephemeral key), reaches `self.enc_keys[&decryptor]`, and `HashMap::index` panics: `called 'HashMap::index' on a missing key`, crashing the node's DKG task.
