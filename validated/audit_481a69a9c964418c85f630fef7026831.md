### Title
OP_RETURN data output excluded from fee estimation causes systematic underpayment and stuck transactions - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/bsaldua/serai--023/blob/main/networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` appends an OP_RETURN output to the transaction when `data` is provided, but computes the transaction weight/vbytes — and therefore `needed_fee` — using only `payments`, omitting the OP_RETURN output entirely. The signed transaction is larger than estimated, so its effective fee rate is lower than `fee_per_vbyte` requested, potentially falling below the mempool minimum and leaving funds locked in an unbroadcastable transaction — the same "funds locked due to unaccounted resource usage" bug class as the reference report.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed into `tx_outs` before the weight calculation:

- `networks/bitcoin/src/wallet/send.rs:194-202` pushes the OP_RETURN `TxOut` (up to 80 bytes of data plus script overhead, ~90+ bytes / ~90+ vbytes).
- `networks/bitcoin/src/wallet/send.rs:204` calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, where `payments` does not include the OP_RETURN output.
- `calculate_weight_vbytes` (`send.rs:62-127`) reconstructs a transaction containing only the inputs, the `payments` outputs, and optionally `change`. The OP_RETURN output is never represented in the estimated weight, at either the no-change call (`send.rs:204`) or the with-change call (`send.rs:225-226`).

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206, 227, 232`) is computed against a vsize that is too small by roughly `8 + 1 + pushdata_len` vbytes (an OP_RETURN output with 80 bytes of data is ~90 vbytes, i.e., up to ~35% error on a minimal transaction).
- The minimum-relay-fee check at `send.rs:211` is also evaluated against the understated `vbytes`, so a transaction can pass `TooLowFee` while its true feerate is below `DEFAULT_MIN_RELAY_TX_FEE`.
- The change computation (`send.rs:228-234`) subtracts only the underestimated `fee_with_change`, so the final transaction's actual fee (`inputs − outputs`, per `fee()` at `send.rs:138-141`) equals the underpriced `needed_fee`.

Note that the test in `networks/bitcoin/tests/wallet.rs:235-272` passes `None` for `data`, so this path is untested.

### Impact Explanation
Any caller that constructs a `SignableTransaction` with `data: Some(_)` produces a transaction whose real fee rate is strictly lower than the requested `fee_per_vbyte`. For transactions near the relay minimum, the transaction is silently below the mempool minimum feerate: `send_raw_transaction` rejects it, yet `needed_fee()`/`fee()` report a self-consistent-but-wrong value, so callers cannot detect the shortfall. Since `Prevouts::All` commits all inputs (`send.rs:373-375`), the consumed UTXOs are tied up in a transaction that cannot propagate — funds are locked until a replacement is constructed, directly analogous to the report's "all funds locked in the pool" outcome. This is an incorrect fee/weight formula reachable purely through public inputs (payment scripts and OP_RETURN data), not dependent on privileged state.

### Likelihood Explanation
Triggering requires only calling `SignableTransaction::new` with a non-`None` `data` argument — a documented, public API path. The miscalculation is deterministic on every such call; whether the transaction stalls depends on how close `fee_per_vbyte` is to the relay minimum and how large `data` is. With maximal `data` (80 bytes), the underestimation approaches a third of a small transaction's vsize, making the shortfall material even at moderate fee rates.

### Recommendation
Include the OP_RETURN output in the weight estimation: either pass the fully-built `tx_outs` (including OP_RETURN) into `calculate_weight_vbytes`, or add the OP_RETURN output to the estimated transaction before computing `weight`/`vbytes` at both call sites (`send.rs:204` and `send.rs:225-226`). The min-relay-fee check at `send.rs:211` must likewise run against the vbytes including the data output.

### Proof of Concept
```rust
// networks/bitcoin conceptual PoC
let data = vec![0u8; 80];
let tx = SignableTransaction::new(
    vec![input],                       // one ReceivedOutput
    &[(payment_script, 10_000)],
    None,
    Some(data.clone()),
    fee_per_vbyte,                     // e.g. 1 sat/vbyte
).unwrap();

// Actual signed transaction contains an OP_RETURN output (~90 vbytes)
// that was never included in `calculate_weight_vbytes`.
let real_vsize = tx.transaction().vsize() as u64;
let paid_fee = tx.fee();               // == needed_fee, estimated WITHOUT the OP_RETURN
assert!(paid_fee < real_vsize * fee_per_vbyte);
// Effective feerate < requested; if paid_fee < DEFAULT_MIN_RELAY_TX_FEE * real_vsize / 1000,
// the transaction is unrelayable and the inputs are locked.
```
Root cause is visible at `send.rs:194-206`: `tx_outs.push(OP_RETURN)` precedes `calculate_weight_vbytes(tx_ins.len(), payments, None)`, which only serializes `payments` into the estimated transaction.
