### Title
`shell.openExternal` is called with attacker-controlled URLs from legacy commit-status `target_url` / check-run `html_url` with no scheme allow-list - (File: `app/src/lib/ci-checks/ci-checks.ts`)

### Summary
The Sherlock finding is about performing a privileged, fund-moving action (`_aggregator.call`, `wallet.transfer`) using an address that is never validated to be non-zero, so the "success" path silently executes with an attacker/no-op target and money is lost. The GitHub Desktop analog is structurally the same "unchecked external target" pattern: `IRefCheck.htmlUrl` is populated directly from GitHub API objects that are not fully within the repository owner's control — specifically the legacy commit-status `target_url` field [1](#0-0)  and the check-run `html_url` field [2](#0-1) . This value is passed straight to `shell.openExternal` with no scheme/host validation.

### Finding Description
`apiStatusToRefCheck` maps a raw GitHub Commit Status API object's `target_url` into `IRefCheck.htmlUrl` with zero validation of its scheme: [3](#0-2) . Commit statuses can be created by any actor holding a token with `repo:status` scope for the repository (this includes third-party CI integrations and, in many org configurations, any contributor/bot with write access) — the value is fully attacker-influenced free text, not a GitHub-controlled link.

`getCheckRunStepURL` similarly builds a navigable URL directly from `checkRun.htmlUrl` with no validation: [4](#0-3) .

That URL is passed to `dispatcher.openInBrowser` on click: [5](#0-4)  and [6](#0-5) , which ultimately reaches `shell.openExternal(url)` — either directly in the renderer (`app-store.ts` `_openInBrowser`) [7](#0-6) , or via the `open-external` IPC handler in the main process: [8](#0-7) .

Crucially, the `open-external` handler only *logs* when the URL starts with `http://`/`https://`; for any other scheme it takes no special action and unconditionally calls `shell.openExternal(path)` regardless of protocol: [8](#0-7) . There is no allow-list rejecting `file:`, custom OS URI schemes, or otherwise dangerous protocol handlers before the call reaches Electron's `shell.openExternal`.

This mirrors the zero-address bug class exactly: a value from an external/attacker-influenced source (`target_url`/`html_url`, analogous to `wallet`/`_aggregator`) is used in a "low level" operation (`shell.openExternal`, analogous to `.call()`) without validating that it is a well-formed, safe target before the operation is dispatched.

### Impact Explanation
If a commit status or check run's URL is set to a non-`http(s)` scheme (e.g. a `file://` URI pointing at a local resource, or an OS-registered custom URI handler), a user viewing PR checks in the CI-checks popover or a notification and clicking "View Check Details" / a job step will have Desktop invoke `shell.openExternal` on that value with no validation. Depending on what's registered on the OS as a handler for that scheme, this can result in opening a local file outside the intended context, invoking another installed application with attacker-chosen arguments, or (on platforms/Electron versions with known `shell.openExternal` argument-injection issues) unintended command execution — all without the user typing or vetting a URL themselves, only clicking a "check details" link they'd reasonably assume is scoped to `https://github.com/...` or the CI provider.

### Likelihood Explanation
Commit status `target_url` (legacy Statuses API) is attacker-settable by anyone/anything with `repo:status` write access to the repository (frequently third-party CI apps, bots, or any collaborator), and is rendered as a clickable "View Check Details" link with no scheme filtering. This requires no special privilege beyond ordinary status-posting capability, and the victim only needs to open a PR in Desktop and click the check-details link — a normal workflow action, not an "unnatural user step."

### Recommendation
Before calling `shell.openExternal`/`openInBrowser` with any URL sourced from GitHub API objects (`target_url`, `html_url`, check-run/job URLs), validate that the URL parses successfully and its protocol is restricted to an allow-list (`https:`, and `http:` only if necessary), rejecting the navigation otherwise — mirroring the existing scheme check already used for GitHub Enterprise endpoint validation in `app/src/ui/lib/enterprise-validate-url.ts` [9](#0-8) . Additionally, tighten the `open-external` IPC handler in `main.ts` to actively reject (not just log) non-`http(s)` schemes rather than passing through to `shell.openExternal` unconditionally: [8](#0-7) .

### Proof of Concept
1. As a contributor/CI integration with `repo:status` write access to a repository, post a commit status via the GitHub API with `target_url` set to a non-HTTP scheme (e.g. `file:///some/local/path` or a registered custom protocol handler URI) instead of a normal `https://` link.
2. Open the pull request containing that commit in GitHub Desktop; the check appears in the CI-checks popover with `IRefCheck.htmlUrl` set to the malicious value via `apiStatusToRefCheck` (`ci-checks.ts:70-79`).
3. The victim clicks "View check details" (`ci-check-run-popover.tsx:152-169`), triggering `dispatcher.openInBrowser(url)` → `shell.openExternal(url)` with the unvalidated scheme.
4. Because `main.ts`'s `open-external` handler (`main.ts:581-597`) only logs for `http(s)` prefixes and otherwise proceeds unconditionally, the non-HTTP URL is passed straight to Electron's `shell.openExternal`, executing whatever OS-level behavior is bound to that scheme/path.

Note: I could not locate an `app-shell.ts` wrapper in this checkout (the file path `app/src/ui/lib/app-shell.ts` was not found by the read tool), so I cannot fully confirm whether an additional renderer-side sanitizer wraps `shell.openExternal` elsewhere in the codebase; the citations above reflect the concrete call sites I was able to verify directly.

export function apiStatusToRefCheck(apiStatus: IAPIRefStatusItem): IRefCheck {
  let state: APICheckStatus
  let conclusion: APICheckConclusion | null = null

  if (apiStatus.state === 'success') {
    state = APICheckStatus.Completed
    conclusion = APICheckConclusion.Success
  } else if (apiStatus.state === 'pending') {
    state = APICheckStatus.InProgress
  } else {
    state = APICheckStatus.Completed
    conclusion = APICheckConclusion.Failure
  }

  return {
    id: apiStatus.id,
    name: apiStatus.context,
    description: getCheckRunShortDescription(state, conclusion),
    status: state,
    conclusion,
    appName: '',
    checkSuiteId: null,
    htmlUrl: apiStatus.target_url,
  }
}

export function getCheckRunStepURL(
  checkRun: IRefCheck,
  step: IAPIWorkflowJobStep,
  repository: GitHubRepository,
  pullRequestNumber: number
): string | null {
  if (checkRun.htmlUrl === null && repository.htmlURL === null) {
    // A check run may not have a url depending on how it is setup.
    // However, the repository should have one; Thus, we shouldn't hit this
    return null
  }

  const url =
    checkRun.htmlUrl !== null
      ? `${checkRun.htmlUrl}/#step:${step.number}:1`
      : `${repository.htmlURL}/pull/${pullRequestNumber}`

  return url
}

export function validateURL(address: string): string {
  // ensure user has specified text and not just whitespace
  // we will interact with this server so we can be fairly
  // relaxed here about what we accept for the server name
  const trimmed = address.trim()
  if (trimmed.length === 0) {
    const error = new Error('Unknown address')
    error.name = InvalidURLErrorName
    throw error
  }

  let url = URL.parse(trimmed)
  if (!url.host) {
    // E.g., if they user entered 'ghe.io', let's assume they're using https.
    address = `https://${trimmed}`
    url = URL.parse(address)
  }

  if (!url.protocol) {
    const error = new Error('Invalid URL')
    error.name = InvalidURLErrorName
    throw error
  }

  if (url.protocol !== 'https:') {
    const error = new Error('Invalid protocol')
    error.name = InvalidProtocolErrorName
    throw error
  }

  return address
}
