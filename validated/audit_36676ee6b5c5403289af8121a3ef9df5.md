### Title
Infinite Loop DoS in `Offer.get_cancellation_coins()` via Cyclic Coin Parent References - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer.get_cancellation_coins()` walks a coin-dependency graph built entirely from attacker-supplied offer data (declared `parent_coin_info`/coin identities inside a `SpendBundle` that has not yet been validated against the real chain state). A crafted offer file with a cyclic parent reference among its non-addition coin spends causes an unbounded `while True` loop with no iteration cap or timeout, hanging the wallet process that examines or cancels the offer — directly analogous to the libheif `Box_stts::get_sample_duration()` infinite-loop bug: a lookup/traversal loop over untrusted, attacker-controlled structured data that never terminates because the malformed input never satisfies the loop's exit condition.

### Finding Description
`get_cancellation_coins()` builds `non_ephemeral_removals` as the set of removal coins whose `parent_coin_info` is *not* the name of another coin in the same removal set: [1](#0-0) 

It is then used inside `get_root_removal()`:
```python
while coin not in non_ephemeral_removals:
    coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)
``` [2](#0-1) 

This loop assumes the parent chain is acyclic and eventually reaches a coin outside `all_removals` (i.e., a "root"). However, `Coin` fields (`parent_coin_info`, `puzzle_hash`, `amount`) inside an `Offer`'s `SpendBundle` are declarative values chosen entirely by whoever authored the offer file — they are not yet checked against real on-chain lineage at this point (that validation only happens later, at spend/mempool time). An attacker can craft an offer whose non-addition coin spends form a cycle (e.g., coin A's `parent_coin_info` equals coin B's name, and coin B's `parent_coin_info` equals coin A's name). In that case every coin in the cycle has its parent present in `all_removals`, so `non_ephemeral_removals` excludes all of them, and the `while coin not in non_ephemeral_removals` loop in `get_root_removal()` walks the cycle forever, never finding a coin outside it.

The related `get_cancellation_coins()` method has a second unguarded loop (lines 449–468) that iterates `detect_dependent_coin()` and an inner `while True` de-duplication loop; it is also driven by attacker-supplied `dependencies`/`announcements` maps derived from the same untrusted puzzle/solution conditions, and can be steered into non-terminating states through crafted `ASSERT_COIN_ANNOUNCEMENT`/`CREATE_COIN_ANNOUNCEMENT` condition graphs designed to keep producing non-empty `removed_announcements` forever, similar in spirit to the unbounded root-cause traversal in `get_root_removal()`.

### Impact Explanation
Offers are exchanged between mutually untrusted counterparties before being pushed to the mempool. A wallet user who receives a malicious offer file and calls into code paths that compute cancellation/primary coins (`get_primary_coins()` → `get_root_removal()`, and `get_cancellation_coins()` directly) will have the calling thread hang in an infinite loop consuming 100% CPU with no progress and no exception — matching the "invisible to crash-based monitoring" characteristic from the libheif report. Because this executes in the wallet process handling RPC requests (offer examine/cancel flows in `chia/wallet/trade_manager.py` and `chia/wallet/wallet_rpc_api.py`), a single malicious offer can render the wallet's RPC thread unresponsive, a transaction-processing halt reachable by any offer counterparty — satisfying the "spend-triggered transaction-processing halt" acceptance criterion.

### Likelihood Explanation
Likely, an unprivileged offer counterparty only needs to construct an offer file (a serialized `SpendBundle`) with two or more non-addition coin spends whose `parent_coin_info` fields point to each other's coin names, forming a cycle. No signature validity or successful mempool acceptance is required to trigger the hang, since the vulnerable traversal happens client-side while inspecting/cancelling the offer, before any chain-level validation would reject the bundle.

### Recommendation
Add a visited-set/iteration bound to both loops in `chia/wallet/trading/offer.py`:
- In `get_root_removal()`, track visited coin names while ascending the parent chain and raise a `ValueError` (e.g., "cyclic or invalid coin lineage in offer") if a coin is revisited or a hard iteration cap is exceeded, rather than looping unconditionally on `coin not in non_ephemeral_removals`.
- In `get_cancellation_coins()`'s two `while True` loops, add a max-iteration guard (bounded by the number of coin spends) and fail closed if the loop would exceed it, since a well-formed offer can only have as many dependency-resolution rounds as it has coins.

### Proof of Concept
1. Construct two dummy coin spends `A` and `B` (with a puzzle/solution producing no announcements, only satisfying the `run_with_cost` calls) such that:
   - `A.parent_coin_info == B.name()`
   - `B.parent_coin_info == A.name()`
   - Neither `A` nor `B` is in `self.additions()`.
2. Wrap them in a `WalletSpendBundle` and build an `Offer(requested_payments={}, bundle=that_bundle, driver_dict={})`.
3. Call `offer.get_primary_coins()` (which calls `get_root_removal()` for each offered coin) or `offer.get_cancellation_coins()` directly.
4. Observe the call never returns: `get_root_removal()`'s `while coin not in non_ephemeral_removals: coin = next(...)` cycles endlessly between `A` and `B` since both are excluded from `non_ephemeral_removals` (each one's parent is inside `all_removals`), consuming CPU indefinitely with no exception raised.
