### Title
Cached FROST preprocess is never invalidated, causing deterministic nonce reuse across `share`/`complete` calls with attacker-controlled messages - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

The external report's bug class is *stale state not updated on use*: a withdrawal reduces real balances but the counters (`ethWithdrawn`, `nETHMinted`) are never decremented, so subsequent calculations act on a value that no longer exists. The direct analog in Serai is `SigningProtocol::preprocess_internal`, which caches a FROST preprocess seed keyed by `context` and **never deletes or rotates it**. Every call to `share_internal` (invoked by both `DkgConfirmer::share` and `DkgConfirmer::complete`) rebuilds an `AlgorithmSignMachine` via `AlgorithmSignMachine::from_cache` from the same 32-byte seed, deterministically regenerating the *same* nonces, and then calls `machine.sign(preprocesses, msg)` where `preprocesses` and `msg` (via `key_pair`) come from external, validator-supplied tributary data. Two `sign` executions under the same context with different preprocess sets or `key_pair`s produce two signature shares under one nonce over different binding factors / challenges — classic Schnorr nonce reuse enabling recovery of the coordinator's MuSig secret key (`x = (s1 − s2)/(e1 − e2)`).

### Finding Description

`preprocess_internal` writes `CachedPreprocesses` once per `context = (b"DkgConfirmer", attempt)` and reads it back on every invocation, decrypting it with a key derived from `context || self.key` (lines 107–145). There is no delete/invalidate step after `sign` is called.

`share_internal` calls `preprocess_internal` and then `machine.sign(preprocesses, msg)` (lines 150–181). `DkgConfirmer::complete` calls `share_internal` *again* with `preprocesses` and `key_pair` taken from the current tributary event (lines 312–327). The signed message is `set_keys_message(set, removed, key_pair)` (line 296), so `msg` varies with `key_pair`, and the binding-factor transcript in `crypto/frost/src/sign.rs` varies with the received preprocesses. The file's own header acknowledges nonce reuse is unsafe and that safety rests solely on context-binding plus BFT ordering — with an explicit `TODO` noting the check that on-chain commitments match the presumed preprocess is not implemented (lines 25–54).

### Impact Explanation

A second `sign` under the same `attempt` with a different `key_pair` or a different preprocess set yields two shares `s_i = d + b_i·e_i + λ_i·x` under the same `d`/`b` pair (same seed → same `Commitments::new` output, `crypto/frost/src/sign.rs` lines 127–132). If the receiving set is identical but `key_pair` differs, `b` and `λ` are identical while the Schnorrkel challenge `e` differs, giving `x = (s1 − s2)/(e1 − e2)` — full recovery of the coordinator's validator MuSig secret share, i.e. compromise of the DKG-confirmation root of trust.

### Likelihood Explanation

`complete` unconditionally re-executes `share_internal`, so any attempt where `share` and `complete` are invoked with differing `key_pair`/preprocess inputs triggers reuse; those inputs originate from validator-published tributary messages, reachable by any validator. Reuse additionally triggers on partial rebuilds/re-execution, which the code comments admit are possible. This requires the coordinator-side flow, so likelihood is medium rather than guaranteed.

### Recommendation

Treat the cached preprocess as single-use: delete or mark `CachedPreprocesses[context]` consumed after `sign`, and before publishing a share verify the on-chain/finalized preprocess commitments match the ones regenerated from the cache (the existing TODO at line 51). If they differ, abort rather than sign.

### Proof of Concept

1. Attempt `a` begins; validator publishes preprocesses `P` and confirmation for `key_pair` K1. Coordinator calls `DkgConfirmer::share(P, K1)` → seed cached under `(b"DkgConfirmer", a)`, share `s1` emitted over `msg1 = set_keys_message(.., K1)`.
2. Validator publishes confirmation for a different `key_pair` K2 in the same attempt; `DkgConfirmer::complete(P, K2, shares)` internally calls `share_internal` → same cached seed → same nonces → share `s2` over `msg2`.
3. Attacker collects `s1`, `s2` (broadcast), recomputes both Schnorrkel challenges, recovers the coordinator's secret share via `(s1 − s2)·(e1 − e2)⁻¹`.
