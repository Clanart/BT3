### Title
Legacy `pattern`-based file-event rules silently fail to block `Write` tool operations due to field-inference mismatch - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`Rule.from_dict` in `plugins/hookify/core/config_loader.py` infers the condition `field` for legacy `pattern:` rules based solely on `event`, mapping `event: file` to `field: new_text`. However, `RuleEngine._extract_field` in `plugins/hookify/core/rule_engine.py` only populates `new_text` from `tool_input['new_string']`, which exists for `Edit`/`MultiEdit` but not for the `Write` tool (whose payload key is `content`). As a result, any hookify rule authored in the simple/legacy `pattern:` style with `event: file` and `action: block` never matches `Write` tool calls, silently allowing attacker-controlled file writes that were meant to be blocked.

### Finding Description
In `Rule.from_dict` [1](#0-0) , when a rule uses the legacy `pattern` field instead of explicit `conditions`, the field name is inferred purely from `event`:
```
if event == 'bash': field = 'command'
elif event == 'file': field = 'new_text'
else: field = 'content'
```
This produces a `Condition(field='new_text', operator='regex_match', pattern=simple_pattern)`.

At evaluation time, `RuleEngine._extract_field` [2](#0-1)  handles the `Write`/`Edit` tools:
```
elif tool_name in ['Write', 'Edit']:
    if field == 'content':
        return tool_input.get('content') or tool_input.get('new_string', '')
    elif field == 'new_text' or field == 'new_string':
        return tool_input.get('new_string', '')
```
Only `field == 'content'` checks the `Write` tool's actual payload key (`content`). `field == 'new_text'` looks exclusively at `new_string`, which the `Write` tool never populates. Because `tool_input` lacks a top-level `new_text` key, the direct-lookup branch at the top of `_extract_field` [3](#0-2)  also does not fire, so this falls through to the `Write`/`Edit` branch and returns `''` (empty string, not `None`).

Since `_check_condition` [4](#0-3)  only short-circuits on `None`, an empty string is passed to `regex_match`, which will not match any realistic dangerous-content pattern. Consequently `_rule_matches` returns `False` for the `Write` tool for any block rule written in the documented simple/legacy format, even though the same rule expressed via explicit `conditions` with `field: content` (as documented in `plugins/hookify/README.md` and `plugins/hookify/skills/writing-rules/SKILL.md`) would correctly match `Write` operations.

The `/hookify` slash command's rule-generation flow documents and defaults to generating this exact legacy `pattern:` format for simple rules [5](#0-4) , meaning any auto-generated or repo-shipped `event: file`, `action: block` rule using the simple format is silently non-functional against the `Write` tool — the most common tool for creating new files with attacker/Claude-authored content.

### Impact Explanation
An operator (or Claude, via `/hookify` generation) believes they have deployed a `block` rule preventing dangerous content (e.g., secrets, malicious scripts, backdoors) from being written to files, but because of the field-inference mismatch, `Write` tool calls bypass the block entirely — only `Edit`/`MultiEdit` calls are actually checked. This breaks the invariant that default field inference must not weaken enforcement relative to the explicit style, and results in unauthorized file writes proceeding without the intended block/deny enforcement, undermining a security control users rely on to constrain Claude Code's local file actions.

### Likelihood Explanation
This is highly likely to occur in practice: it requires no adversarial crafting beyond using the plugin's own documented and auto-generated simple-rule format (`pattern:` + `event: file`) for a `block` action, which is the primary format shown in the README, SKILL doc, and the `/hookify` command's own generation template. Any user or agent creating a file-content block rule via the standard/simple format is silently affected whenever content is introduced via the `Write` tool rather than `Edit`.

### Recommendation
In `Rule.from_dict`, infer `field = 'content'` (not `'new_text'`) for `event == 'file'` legacy pattern rules, matching the broader extraction logic already used for explicit conditions; alternatively, update `_extract_field` so the `new_text` alias also falls back to `tool_input.get('content')` for the `Write` tool, keeping legacy and explicit condition semantics equivalent.

### Proof of Concept
Unit test in `plugins/hookify/core/` test suite:
```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

frontmatter = {
    "name": "block-secret-write",
    "enabled": True,
    "event": "file",
    "pattern": "API_KEY",
    "action": "block",
}
rule = Rule.from_dict(frontmatter, "Blocked: secret detected")
engine = RuleEngine()

# Write tool call containing the blocked pattern
write_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Write",
    "tool_input": {"file_path": "config.py", "content": "API_KEY = 'xxxx'"},
}
result = engine.evaluate_rules([rule], write_input)
assert result == {}, "Expected block, but Write bypassed the rule due to field-inference mismatch"

# Equivalent Edit tool call is correctly blocked
edit_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Edit",
    "tool_input": {"file_path": "config.py", "new_string": "API_KEY = 'xxxx'"},
}
result2 = engine.evaluate_rules([rule], edit_input)
assert result2.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
```
Expected/observed: the `Write` case returns `{}` (no block) while the semantically identical `Edit` case correctly denies, demonstrating the legacy vs. explicit differential and confirmed enforcement bypass for the `Write` tool.

    def _check_condition(self, condition: Condition, tool_name: str,
                        tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> bool:
        """Check if a single condition matches.

        Args:
            condition: Condition to check
            tool_name: Tool being used
            tool_input: Tool input dict
            input_data: Full hook input data (for Stop events, etc.)

        Returns:
            True if condition matches
        """
        # Extract the field value to check
        field_value = self._extract_field(condition.field, tool_name, tool_input, input_data)
        if field_value is None:
            return False

        # Apply operator
        operator = condition.operator
        pattern = condition.pattern

        if operator == 'regex_match':
            return self._regex_match(pattern, field_value)
