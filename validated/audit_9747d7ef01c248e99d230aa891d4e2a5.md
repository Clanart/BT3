### Title
Bridge ERC20 value-transfer accounting ignores fee-on-transfer/deflationary tokens, causing cross-chain supply/liquidity mismatch - ([File: contracts/service_chain/bridge/BridgeTransferERC20.sol])

### Summary
`BridgeTransferERC20`'s `requestERC20Transfer`/`onERC20Received` flow pulls tokens via `safeTransferFrom`/`safeTransfer` and then uses the caller-supplied nominal `_value`/`_feeLimit` for all downstream accounting (fee payment, refund, burn, and the `RequestValueTransfer` event that the counterpart bridge uses to mint/pay out funds), without ever checking the token balance actually received by the contract. For a fee-on-transfer/deflationary ERC20, the bridge will hold or burn less than the nominal amount it advertises, while the counterpart chain still mints/transfers the full nominal `_value` to the recipient.

### Finding Description
`requestERC20Transfer` transfers the full nominal amount from the user: [1](#0-0) 

It never re-checks `IERC20(_tokenAddress).balanceOf(address(this))` after the transfer to determine what was actually received. It then immediately calls `_requestERC20Transfer`, which: [2](#0-1) 

- Calls `_payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit)`, which pays `fee` to `feeReceiver` and refunds `_feeLimit - fee` to the sender, both based purely on the nominal `_feeLimit`/stored `feeOfERC20[_token]`, not the tokens actually held by the bridge: [3](#0-2) 

- In `modeMintBurn` mode, it burns the nominal `_value` via `ERC20Burnable(_tokenAddress).burn(_value)`, again independent of the actual balance received.
- It emits `RequestValueTransfer` with the nominal `_value`, which is the exact amount the counterpart chain's `handleERC20Transfer` will later mint or transfer out to the recipient: [4](#0-3) 

If `_tokenAddress` charges a transfer fee (deflationary/fee-on-transfer token), `safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit))` delivers strictly less than `_value + _feeLimit` to the bridge contract. The bridge nonetheless:
1. Pays fee/refund amounts computed from the nominal `_feeLimit`, which can exceed what it actually received (in non-mint-burn liquidity mode, this drains the bridge's token reserve faster than deposits replenish it), and
2. Emits/burns the full nominal `_value`, which the destination bridge will mint or pay out in full via `handleERC20Transfer`: [4](#0-3) 

This produces a systematic discrepancy between tokens actually escrowed/burned on the source chain and tokens minted/paid out on the destination chain — the exact fee-on-transfer accounting bug class from the external report, applied to Bridge's cross-chain value-transfer bookkeeping instead of a single-chain gauge deposit.

### Impact Explanation
- In `modeMintBurn=true` (wrapped/bridged token) configurations, each fee-on-transfer token bridged from parent→child (or vice versa) causes the destination chain to mint tokens (`ERC20Mintable(_tokenAddress).mint(_to, _value)`) in an amount greater than what was actually burned/escrowed on the source chain, i.e., unbacked token supply inflation on the counterpart chain.
- In `modeMintBurn=false` (liquidity-pool) configurations, the bridge contract pays out fee/refund and later `handleERC20Transfer` liquidity based on nominal values while its actual balance is lower than expected due to per-transfer fee leakage, gradually depleting the bridge's real token reserves relative to its accounted liabilities — a form of value extraction/insolvency for anyone using such a token with the bridge.
- Any unprivileged user can trigger this simply by calling `requestERC20Transfer`/`onERC20Received` (or the token's own `requestValueTransfer` per the test files) with a fee-on-transfer ERC20 registered on the bridge; no special privilege is required.

### Likelihood Explanation
Likelihood is Medium: the bug only manifests when a fee-on-transfer/deflationary ERC20 is registered with the bridge (via `RegisterToken`, an operator action), but once such a token is registered, every ordinary user-initiated bridge transfer (a single transaction from any sender) triggers the miscounting deterministically — there is no need for coordination, timing, or privileged access, only the existence of one non-standard registered token.

### Recommendation
After pulling funds into the bridge (`safeTransferFrom`/`onERC20Received`), measure the actual balance delta (`balanceOf(address(this))` before/after) and use that measured amount — not the caller-supplied nominal `_value`/`_feeLimit` — for:
- fee/refund computation in `_payERC20FeeAndRefundChange`,
- the burn amount in mint-burn mode, and
- the `valueOrTokenId` emitted in `RequestValueTransfer` that the counterpart bridge relies on for minting/payout.
Alternatively, explicitly reject registration of tokens whose `transfer`/`transferFrom` do not preserve the requested amount (e.g., verify `balanceOf` delta equals requested amount immediately after transfer, and revert otherwise) to keep bridge accounting exact.

### Proof of Concept
1. Operator registers a fee-on-transfer ERC20 `T` (e.g., 1% fee on every `transfer`/`transferFrom`) via `RegisterToken` on a non-mint-burn bridge, and configures `feeOfERC20[T] = 0` for simplicity.
2. User Alice holds 100 `T`, approves the bridge for 100 `T`, and calls `requestERC20Transfer(T, Bob, 100, 0, "")`.
3. `safeTransferFrom(Alice, bridge, 100)` actually delivers only 99 `T` to the bridge (1% fee burned/redirected by token `T`).
4. `_payERC20FeeAndRefundChange` computes `feeRefund = _feeLimit - fee = 0`, so no refund attempt reverts here, but `RequestValueTransfer` is emitted with `valueOrTokenId = 100`.
5. On the counterpart chain, an operator/relayer submits `handleERC20Transfer(..., _value = 100, ...)`, which executes `IERC20(T).safeTransfer(Bob, 100)` (non-mint-burn) — requiring the bridge to have at least 100 `T` even though it only ever received 99 `T` for this request. Repeated over many such transfers, the bridge's real `T` balance falls behind its recorded/obligated liabilities, eventually causing failed handles (denial of service) or, if bridge liquidity was topped up separately, a systematic value leak/insolvency; in mint-burn mode the same nominal-`_value` accounting instead inflates `T`'s supply on the counterpart chain beyond what was actually burned on the source chain.

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
