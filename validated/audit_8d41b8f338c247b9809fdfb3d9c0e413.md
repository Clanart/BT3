### Title
`unvote()` check is inverted, permanently trapping vote allocations and blocking `VLMGP.startUnlock()` once a pool is deactivated - ([File: wombat/WombatBribeManager.sol])

### Summary
The `unvote()` function in `WombatBribeManager.sol` reverts with `PoolNotActive` when `pool.isActive` is `false`, which is the exact opposite of its intended purpose (its own docstring states it should let users "unvote from an inactive pool" so deactivation doesn't block withdrawals). Once the owner deactivates a pool a user has voted for, that user can never reduce `userVotedForPoolInVlmgp`/`userTotalVotedInVlmgp` for that pool via either `vote()` or `unvote()`, both of which share the same `if (!pool.isActive) revert PoolNotActive();` guard, permanently blocking `VLMGP.startUnlock()` for the corresponding locked MGP.

Note: the question labels the file as `Mgp.sol`, but `Mgp.sol` [1](#0-0)  is only the plain ERC20 `MGP` token contract and contains no `unvote`/`vote` logic at all. The function under discussion actually lives in `wombat/WombatBribeManager.sol`, which is where this analysis applies.

### Finding Description
`vote()` guards every pool in the loop with an active-pool check: [2](#0-1) 

`unvote()` uses the identical check, but the doc comment above it explicitly says the function exists so users *can* exit inactive pools: [3](#0-2) 

Since `unvote()` reverts precisely when `pool.isActive` is `false`, the moment the owner deactivates a pool the user voted for, that user's `userVotedForPoolInVlmgp[msg.sender][pool.poolAddress]` and the aggregated `userTotalVotedInVlmgp[msg.sender]` can never be reduced again: `vote()` also reverts for the same inactive pool, and `unvote()` reverts too. There is no unprivileged path left for the user to shrink their outstanding vote allocation on that pool.

`VLMGP.startUnlock()` then enforces: [4](#0-3) 

If the user's `userTotalVotedInVlmgp` equals (or is close to) their full locked balance, any `_amountToCoolDown > 0` produces `totalLockAfterStartUnlock < userTotalVotedInVlmgp`, causing `NotEnoughLockedMPG` to revert indefinitely — with no way for the affected user to fix the accounting.

### Impact Explanation
This is a permanent freezing-of-funds bug (Immunefi "permanent freezing of funds ≥24h" class). A normal, unprivileged user who voted heavily/fully for a pool that is later deactivated through ordinary protocol lifecycle management (deprecating a delisted/retired Wombat pool) loses the ability to ever call `startUnlock()` for the portion of MGP tied to that vote, since the on-chain accounting (`userTotalVotedInVlmgp`) can never be decremented back down. The affected MGP remains locked in `VLMGP` with no owner/admin recovery path visible in the reviewed code.

### Likelihood Explanation
Preconditions are simple and require no special privilege from the attacker/victim: (1) lock MGP in `VLMGP`, (2) call `vote()` allocating some/all voting power to a pool, (3) wait for the pool to be deactivated by the protocol owner as part of normal pool-list maintenance (this is a routine, expected admin action, not a malicious act targeting the user), (4) attempt `unvote()` or `startUnlock()`. No capital beyond normal locking is needed, and the bug is deterministically reproducible for any user who voted for a pool that becomes inactive.

### Recommendation
Invert the condition in `unvote()` so it does NOT require the pool to be active — the check should be removed entirely (or replaced with an explicit "pool must be inactive OR msg.sender authorized" style logic) so users can always exit their vote on a deactivated pool, matching the function's own documented intent. Alternatively, provide an admin/owner-only emergency function to zero out `userVotedForPoolInVlmgp` for deactivated pools, but the primary fix is correcting the inverted `if (!pool.isActive)` guard in `unvote()`.

### Proof of Concept
Foundry test outline:
1. Deploy `VLMGP`, `WombatBribeManager`, and a mock rewarder/pool; register pool `lp` as active via the pool-add function.
2. User locks `X` MGP in `VLMGP`, then calls `vote([lp], [int256(X)])` — succeeds, `userVotedForPoolInVlmgp[user][lp] == X`, `userTotalVotedInVlmgp[user] == X`.
3. Protocol owner (routine lifecycle action, not attacking the user) calls the pool-deactivation admin function to set `poolInfos[lp].isActive = false`.
4. User calls `unvote(lp)` → assert it reverts with `PoolNotActive`.
5. User calls `vote([lp], [-int256(X)])` to attempt correction → assert it also reverts with `PoolNotActive`.
6. User calls `VLMGP.startUnlock(X)` → assert it reverts with `NotEnoughLockedMPG` because `totalLockAfterStartUnlock (0) < userTotalVotedInVlmgp (X)`.
7. Confirm no other unprivileged function exists to reduce `userTotalVotedInVlmgp[user]`, proving the lock is permanent.

    /// @notice Unvote from an inactive pool. This makes it so that deleting a pool, or changing a rewarder doesn't block users from withdrawing
    function unvote(address _lp) public {
        Pool storage pool = poolInfos[_lp];
        uint256 currentVote = userVotedForPoolInVlmgp[msg.sender][pool.poolAddress];
        if(!pool.isActive)
            revert PoolNotActive();
        
        pool.totalVoteInVlmgp -= uint256(currentVote);
        userTotalVotedInVlmgp[msg.sender] -= uint256(currentVote);
        userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] = 0;
