### Title
Missing path-separator boundary check in `resolveWithin()` allows sibling-directory escape - (File: `app/src/lib/path.ts`)

### Summary
The `_resolveWithin()` helper in `app/src/lib/path.ts` is the sole guard used to keep repository-relative paths from a cloned/fetched repo confined to the repo's working directory before those files are read and sent to the Copilot conflict-resolution SDK. Like the `_convert()` function in the reported DAOfi bug — which mishandled a boundary condition (`decimals == resolution`) and silently produced a wrong result instead of the intended value — `_resolveWithin()` mishandles a boundary condition in its containment check: it uses a raw string `startsWith()` comparison without verifying a path-separator boundary, so a sibling directory whose name happens to share the root directory's name as a prefix (e.g. `repo-secrets` vs `repo`) is incorrectly treated as "inside" the repository.

### Finding Description
`resolveWithin()` is meant to guarantee that a resolved path stays "at, or underneath" `rootPath`: [1](#0-0) 

The final containment check is:
```
return realResolved.startsWith(realRoot) ? resolved : null
```
This is a plain string prefix check with no trailing separator enforcement. If `realRoot` is `/Users/victim/Documents/GitHub/repo` and an attacker-influenced relative path (via `../`) resolves to `/Users/victim/Documents/GitHub/repo-secrets/token.txt`, the string `repo-secrets/...` still starts with the literal string `repo`, so the function incorrectly returns the escaped path as "safe" instead of `null`. This mirrors the DAOfi `_convert()` bug class: a branch/edge condition (here, "is this actually a subdirectory boundary, or just a string-prefix coincidence?") is not fully handled, causing the function to silently produce an incorrect (in this case, dangerously permissive) result rather than failing safe.

The one real consumer of this guard that processes attacker-influenced, repo-relative paths is `buildConflictContext()`, which resolves each conflicted file's path against the repository's working directory before reading its contents and forwarding them to the Copilot SDK prompt: [2](#0-1) [3](#0-2) 

If `file.path` (sourced from the merge/rebase conflict file list of a cloned/fetched, attacker-influenced repository) contains a `../` sequence that lands in a sibling directory sharing a name prefix with the repo directory, `resolveWithin()`'s flawed `startsWith` check would incorrectly treat the escaped path as contained, allowing `readFile()` to read a file outside the repository and have its content included in the prompt sent to the Copilot service — i.e., a read primitive outside the intended repo boundary, with potential exfiltration to a remote LLM endpoint.

### Impact Explanation
If reachable, the primitive is a file read outside the intended repository root, whose content is subsequently transmitted off-device as part of an AI prompt — this matches the accepted impact class of "file read outside the repo" and potential "credential/token exfiltration" (e.g. reading a sibling checkout containing secrets, or a directory like `repo-secrets`, `repo.bak`, etc.). The other two `resolveWithin` call sites (`app/src/ui/dispatcher/dispatcher.ts`, `app/src/lib/stores/app-store.ts`) were not fully inspected in this pass, and other consumers could have the same weakness.

### Likelihood Explanation
Exploitability depends entirely on whether `file.path` values reaching `buildConflictContext()` can actually contain `../` traversal segments and whether a suitably-named sibling directory exists on the victim's disk at a predictable location. Git normally rejects `..` path components from tracked index entries, so I could not confirm from static code alone that a crafted repository can inject a traversal path into this specific call site — this would need runtime verification (e.g., via a crafted rename/conflict scenario, case-insensitive filesystem tricks, or a malformed git status parse) to confirm reachability. The `_resolveWithin` code itself already defends against `..` normalization and null bytes, so the *only* remaining gap is the missing separator check in the final `startsWith` comparison, which is unambiguously present in the code.

### Recommendation
Change the final check in `_resolveWithin()` (`app/src/lib/path.ts`) to enforce a proper path-boundary comparison instead of a raw string prefix, e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This avoids the false-positive containment result for sibling directories that merely share a name prefix, closing the same class of "boundary condition silently mishandled" bug identified in the original report.

### Proof of Concept
Conceptual (not confirmed against a live reachable input, since git path validation may already block literal `..` conflict-file paths — see Likelihood):
```ts
import { resolveWithin } from './path'

// Directory layout:
//   /Users/victim/Documents/GitHub/repo            (the actual repo)
//   /Users/victim/Documents/GitHub/repo-secrets/token.txt

const result = await resolveWithin(
  '/Users/victim/Documents/GitHub/repo',
  '../repo-secrets/token.txt'
)
// Expected: null (outside the repo)
// Actual (due to prefix-only startsWith check): resolves and returns the
// path to token.txt, because
// "/Users/victim/Documents/GitHub/repo-secrets/token.txt".startsWith(
//   "/Users/victim/Documents/GitHub/repo"
// ) === true
