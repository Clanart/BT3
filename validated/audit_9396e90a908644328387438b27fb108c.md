### Title
GitHub repository identity keyed on mutable `[owner+name]` instead of GitHub's immutable repo ID lets a name takeover silently redirect PR/fork checkout to an attacker's remote - (File: app/src/lib/stores/repositories-store.ts)

### Summary
Analogous to the Mochi bug where `engine.nft` (a mutable, governance-controlled address) is used as the sole key for CDP state and can overwrite existing debt positions when changed, GitHub Desktop's `RepositoriesStore._upsertGitHubRepository` (and `upsertGitHubRepositoryFromMatch`) identifies a *local* `GitHubRepository` DB record purely by the composite key `[ownerID+name]` — i.e. owner login + repository name — rather than GitHub's immutable numeric repository `id`. The model explicitly documents this: `GitHubRepository.dbID` is "no relation to the API ID" [1](#0-0) . Any time the API returns repository data for that same owner/name pair (rename-back, delete-and-recreate, or hostile repo creation after the old one is renamed/deleted), Desktop's upsert logic finds the "existing" row and overwrites its `cloneURL`, `htmlURL`, `parentID`, and `permissions` in place, and every local `Repository` that referenced that DB row (via `gitHubRepositoryID`) is silently repointed to the new underlying GitHub repository.

### Finding Description
`_upsertGitHubRepository` looks up the "existing" DB record via `[ownerID+name]`, not via GitHub's immutable repo id: [2](#0-1) 

It then persists the new API data into that same row (`id: existingRepo.id`) unconditionally, replacing `cloneURL`, `htmlURL`, `parentID`, and `permissions`: [3](#0-2) 

`upsertGitHubRepositoryFromMatch` (used for matching a local git remote to a GitHub repo) performs the identical name-based lookup, again with no reference to the immutable GitHub id: [4](#0-3) 

`Repository` objects only store a foreign key (`gitHubRepositoryID`) into this table, resolved lazily via `findGitHubRepositoryByID`, so once the underlying row is overwritten every consumer transparently sees "the same" GitHub repository with new field values: [5](#0-4) 

This value flows directly into security-relevant operations. `cloneURL` is used to add remotes / fetch fork branches when checking out pull requests without any further validation that it belongs to the repo the user originally added: [6](#0-5) 
and to add the `upstream` remote for forks: [7](#0-6) 

The report's broken invariant ("changeable identity field used as a persistent primary key for state that should track an immutable entity") is exactly reproduced here: `owner+name` is mutable (repos can be renamed, deleted, and recreated by anyone with control of that owner/org), yet it's treated as if it uniquely and permanently identifies "the GitHub repository the user is tracking."

### Impact Explanation
If an org repository (or a personal repo whose owner login can be reused/taken over, e.g. via GitHub's username-change/repository-rename mechanics) that a victim already has in Desktop is deleted/renamed and a different, attacker-controlled repository is created under the same `owner/name`, the very next background refresh, PR fetch, or repo-info sync will silently rewrite the local DB record: `cloneURL`/`htmlURL` are replaced with the attacker's repository URLs and `permissions`/`parentID` are recomputed from the attacker's repo. Because `_findPullRequestBranch`/`addUpstreamRemoteIfNeeded` use these fields to add remotes and fetch without prompting the user, this can result in Desktop silently fetching from and adding a remote pointing at an attacker-controlled repository under the guise of the user's original project, and can corrupt the "upstream"/fork relationship used for future pushes and PR checkouts. This satisfies the impact bar of "silent corruption of what the user commits/pushes" via a git-remote/API-object-controlled path.

### Likelihood Explanation
Requires the specific precondition of an owner+name being freed and reclaimed with a different underlying repository (rename/delete + recreate, or org repo lifecycle), so it is not exploitable against an arbitrary, unmodified repository at will. It is fully unprivileged from the victim's perspective (no local access, no admin rights, no leaked credentials) — it only requires normal Desktop usage (periodic repo refresh / opening a repository / fetching) after the attacker has repositioned the owner/name pair. Likelihood is moderate: it depends on an owner login or org handle becoming available and reused, which does happen in practice (squatting on renamed/deleted repos and orgs is a known GitHub attack pattern).

### Recommendation
Key `IDatabaseGitHubRepository` records (and the `[ownerID+name]` lookup used in `_upsertGitHubRepository` / `upsertGitHubRepositoryFromMatch`) by the immutable GitHub API repository `id` in addition to (or instead of) `[ownerID+name]`. When the API-reported `id` for a given `owner/name` differs from the previously stored one, treat it as a *new* repository record rather than merging into the old one, and require re-establishing the `origin`/`upstream` relationship (or at minimum warn the user) rather than silently rewriting `cloneURL`/`permissions` on the existing row.

### Proof of Concept
1. Victim adds a Desktop-tracked repository backed by `github.com/org/project` (GitHub API id `111`). Desktop calls `upsertGitHubRepository`, creating DB row `{id: 5, ownerID: 1, name: "project", cloneURL: "https://github.com/org/project.git", ...}` [3](#0-2) .
2. `org/project` is deleted or renamed away, freeing the `org/project` slot. An attacker with control of `org` (or a similarly-named org/user) creates a new, unrelated repository at `github.com/org/project` (GitHub API id `999`).
3. On the next PR list refresh / repository refresh, Desktop calls `_upsertGitHubRepository` again for `owner=org, name=project`. The lookup `.where('[ownerID+name]').equals([1, "project"])` matches the *old* row (`id: 5`) since it is keyed on owner+name, not on the API `id` [2](#0-1) .
4. The old row is overwritten in place with the attacker's `cloneURL`/`htmlURL`/`permissions` via `db.gitHubRepositories.put(updatedGitHubRepo)` [8](#0-7) , while the victim's local `Repository.gitHubRepositoryID` (still `5`) now resolves to attacker-controlled data.
5. When the victim opens a pull request or triggers "fetch"/"upstream" logic, Desktop uses the now-corrupted `cloneURL` to `addRemote`/fetch, causing it to add and fetch from the attacker's repository under the trusted local repository entry [6](#0-5) .
