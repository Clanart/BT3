## PlotNFT/Wallet Coin-Sync Path

Confirmed usages of `PuzzleWithRestrictions.from_memo()` in `chia/wallet/plotnft_wallet/plotnft_wallet.py` and `chia/pools/plotnft_drivers.py` (`PlotNFT.get_next_from_coin_spend()`), which is invoked during wallet sync when the wallet processes coin-spend/coin-creation data pulled from the chain (attacker-controlled `memo_blob` on a coin an attacker creates), and in `chia/wallet/wallet_state_manager.py`. This confirms the reachability path from an on-chain coin (which any spend-bundle submitter can create) into the recursive parser.

### Title
Unbounded Python recursion in `PuzzleWithRestrictions.from_memo()` allows an attacker-crafted coin memo to crash a wallet/plotNFT sync via stack exhaustion - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively reconstructs nested `MofN` custody structures from an untrusted `Program` memo with no depth limit, directly analogous to the infinite/unbounded recursion in GNU libiberty's `d_name()`/`d_encoding()`/`d_local_name()` (CVE-2018-18700), where attacker-controlled nested structure drives unbounded native/interpreter stack growth.

### Finding Description
`MofN.from_memo`/`PuzzleWithRestrictions.from_memo` reconstruct a custody tree from a `Program` memo attached to a coin: [1](#0-0) 

For every nested `MofN` node, `from_memo` calls itself once per member with no recursion-depth or nesting-depth check: [2](#0-1) 

An attacker who controls a `CREATE_COIN` condition can set an arbitrary `memo_blob` (the CLVM hint/memo list attached to the created coin) to an arbitrarily deep, nested `MofN` memo structure (`("CHIP-0043" (nonce restriction_hints 1 (m [(memo…) (memo…) …])))`, itself containing another such tuple, etc.). This memo is stored on-chain as part of the coin's hint/memo and is later parsed by wallet/plotNFT sync code without any CLVM execution or Rust-side sandboxing — the parsing happens entirely in pure Python via `Program.at()`/`as_iter()` recursive calls.

This memo is consumed during PlotNFT sync reconstruction: [3](#0-2) 

`PlotNFT.get_next_from_coin_spend()` is called from wallet code that walks the chain of singleton coin spends for a PlotNFT/pool wallet, meaning any attacker who spends a plotNFT-shaped singleton (or otherwise creates a coin whose memo an observing wallet later parses in this code path) can supply the deeply-nested `MofN` memo. Because CPython's default recursion limit (~1000 frames) is far smaller than what an attacker can encode in a CLVM list (bounded only by mempool cost/serialized-program size limits, which allow thousands of nested atoms cheaply), the recursive Python call chain in `from_memo` will exhaust the interpreter's call stack and raise `RecursionError`, unhandled by any `try/except` around this specific call path other than a narrow `except ValueError` in `get_next_from_coin_spend` (which does not catch `RecursionError`).

### Impact Explanation
Triggering `RecursionError` inside wallet code that processes on-chain coin data (PlotNFT/pool sync, wallet state manager parsing of hinted/memoized coins) halts the processing of that transaction/coin, and — because `RecursionError` is an uncaught `Exception`-family error at this call site — can crash or destabilize the sync loop that is walking the singleton chain, preventing legitimate PlotNFT/pool-wallet state updates from completing. This is a spend-triggered transaction-processing halt reachable purely by any actor able to publish a coin/spend containing a maliciously deep memo, satisfying the "spend-triggered transaction-processing halt" impact category.

### Likelihood Explanation
Likelihood is Medium: constructing the malicious memo requires only building a nested list/CLVM structure and attaching it as a coin memo — something any wallet-capable actor can construct without needing signatures on the exploited data (the memo is a hint, not separately signed) or any special privileges. The main cost to the attacker is the mempool/block-inclusion cost of the coin spend that creates the memo-bearing coin, which is bounded by normal CLVM cost limits but still allows thousands of small nested atoms well beyond CPython's default stack recursion limit.

### Recommendation
Convert `PuzzleWithRestrictions.from_memo`/`MofN.from_memo` parsing to an iterative (stack-based) algorithm, or add an explicit maximum nesting-depth check (raising a normal `ValueError`) before recursing, mirroring the non-recursive design used elsewhere in the codebase for untrusted tree-shaped data (e.g. `sha256_treehash` in `chia/types/blockchain_format/tree_hash.py`, and the `RecursionDepthExceededError` guard used for Data Layer merkle blobs). Additionally, ensure calling code (`PlotNFT.get_next_from_coin_spend` and any other consumer of `from_memo`) catches `RecursionError` alongside `ValueError` so a malformed/malicious memo degrades to a handled parse failure rather than crashing the sync process.

### Proof of Concept
1. Construct a `CREATE_COIN` condition whose memo (`memo_blob`) encodes a `PuzzleWithRestrictions` memo of the form `("CHIP-0043" (0 () 1 (1 [(deeply nested MofN memo) ...])))`, where the nested `MofN` structure is repeated recursively N times (N in the low thousands is sufficient to exceed CPython's default recursion limit).
2. Include this `CREATE_COIN` condition in a normal spend bundle submitted to the mempool; it is accepted like any other coin creation since memos are opaque hints not subject to structural validation.
3. Once the coin is confirmed on-chain, trigger any wallet/plotNFT sync path that calls `PlotNFT.get_next_from_coin_spend()` (or any other consumer of `PuzzleWithRestrictions.from_memo`) against that coin's spend.
4. Observe `RecursionError` raised from the recursive calls in `PuzzleWithRestrictions.from_memo` (`chia/wallet/puzzles/custody/custody_architecture.py:283-286`), which is not caught by the `except ValueError` in `PlotNFT.get_next_from_coin_spend`, halting/crashing the sync path processing that coin.

Note: I could not fully trace every calling context of `from_memo` in `wallet_state_manager.py` and `vc_drivers.py`/`cr_cat_drivers.py` (whether each has broader exception handling around the whole sync loop that would catch and recover from a `RecursionError`, versus letting it propagate and abort/crash the service). This affects exact severity (unhandled process crash vs. per-coin skip) and should be verified by reading those call sites directly with full file access.
