### Title
Secret-dependent table indexing in `straus`/`pippenger` leaks scalar bits via cache-bank timing (CacheBleed analog) - (File: crypto/multiexp/src/straus.rs)

### Summary
CVE-2016-0702 (CacheBleed) is a cache-bank timing attack where secret-dependent memory accesses during modular exponentiation leak the secret exponent. The direct analog exists in Serai's `multiexp` crate: the nominally constant-time `straus` and `pippenger` functions index precomputed tables and buckets using values derived directly from the secret scalar bits, creating secret-dependent memory access patterns observable by a co-located attacker.

### Finding Description
`multiexp::multiexp` is the constant-time entry point, distinguished from `multiexp_vartime`, and dispatches to `straus` or `pippenger` for multi-scalar multiplication (crypto/multiexp/src/lib.rs:180-189). However, neither implementation is actually constant-time with respect to memory access:

- In `straus` (crypto/multiexp/src/straus.rs:42-44), the accumulator line `res += tables[s][usize::from(groupings[s][b])]` performs a lookup into `tables[s]` at an index equal to the secret scalar's `window`-bit grouping. The address accessed is a direct function of secret bits.
- In `pippenger` (crypto/multiexp/src/pippenger.rs:24-27), `buckets[usize::from(bits[p][n])] += pairs[p].1` writes to a bucket index determined by secret scalar bit-groupings — a secret-dependent store, the exact primitive exploited by CacheBleed.

`prep_bits` (crypto/multiexp/src/lib.rs:54-74) carefully extracts scalar bits via `u8_from_bool`/`black_box` to avoid timing leaks during bit extraction, but the extracted groupings are then used as raw array indices, negating that protection. By contrast, `Ed448Point::mul` (crypto/ed448/src/point.rs:258-266) and `Scalar::pow` (crypto/dalek-ff-group/src/lib.rs:223-231) correctly use `conditional_select` over the whole table, showing the intended pattern.

The non-vartime `multiexp` is reachable from `musig`/`musig_key` (crypto/dkg/musig/src/lib.rs:107,151) and `BatchVerifier::verify` (crypto/multiexp/src/batch.rs:94), and is the API any in-scope caller must use whenever a scalar is secret (binding factors, interpolation coefficients, weights). Nothing prevents or warns against passing secret scalars, and on architectures with cache-bank conflicts (Intel Sandy Bridge and similar), the index `groupings[s][b]` / `bits[p][n]` is recoverable by an unprivileged process sharing the CPU core.

### Impact Explanation
Any secret scalar passed to `multiexp` (e.g., interpolation coefficients or per-participant scalars in threshold operations) has its bit-groupings recoverable nibble-by-nibble through cache-bank/cache-set timing, enabling partial-to-full scalar recovery by a co-located unprivileged attacker — the same secret-leakage consequence as CVE-2016-0702. This undermines the constant-time guarantee the non-`vartime` API name implies.

### Likelihood Explanation
Exploitation requires a co-resident process on the same physical core, matching the CVSS 5.1 local/high-complexity profile of the original CVE. The leak is deterministic in structure: every window position produces an observable index for every scalar in the multiexp, so repeated signing/DKG operations give the attacker many samples of the same indexing channel.

### Recommendation
In `straus`, replace the indexed lookup `tables[s][groupings[s][b]]` with a constant-time `conditional_select` pass over `tables[s]` (as done in `Scalar::pow`/`Ed448Point::mul`). In `pippenger`, replace the secret-indexed bucket write with either a constant-time conditional-assignment pass over all buckets, or bucket accumulation via a radix/sort structure whose memory pattern is scalar-independent. Alternatively, document `multiexp` as variable-time and rename it to make the leak explicit — but since `multiexp` is the safe counterpart advertised to callers, fixing the indexing is preferred.

### Proof of Concept
```rust
// Conceptual: victim performs a multiexp over a secret scalar while an
// attacker process on the same Sandy Bridge-class core measures cache-bank
// conflicts on the `tables`/`buckets` arrays.
use multiexp::multiexp; // not multiexp_vartime — advertised as safe
let secret = Scalar::random(&mut OsRng);   // e.g., binding factor / share
let pair = [(secret, G::generator())];
let _ = multiexp(&pair); // straus: tables[0][groupings[0][b]] — index = secret nibble
```
Each `groupings[s][b]` in `straus.rs:43` (and `bits[p][n]` in `pippenger.rs:26`) is a 4–8 bit slice of the secret scalar used verbatim as an array index; a cache-bank-conflict measurement per iteration recovers the slices, reassembling the scalar — precisely the CacheBleed mechanism of CVE-2016-0702.
