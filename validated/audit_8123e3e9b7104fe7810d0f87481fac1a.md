### Title
Missing boundary checks in `ArrayDecoders` varint/list decoding rely entirely on implicit JVM bounds-check-as-exception, with no proven catch at the Lite parsing boundary - ([File: java/core/src/main/java/com/google/protobuf/ArrayDecoders.java])

### Summary
The DCT decoder CVE (`DCTStream::readHuffSym`) crashes because a variable-length code table walk advances an index/position based on attacker-controlled bitstream content without validating that the walk stays inside the backing buffer, causing an out-of-bounds read that crashes the process. The Java Lite runtime's `ArrayDecoders` class contains a structurally analogous pattern: `decodeVarint32`, `decodeVarint64`, and every packed/unpacked list decoder (`decodeVarint32List`, `decodeVarint64List`, `decodeFixed32List`, `decodeDoubleList`, `decodeBoolList`, `decodeSInt32List`, `decodeSInt64List`, `decodeStringList`, etc.) advance a `position` index through the `byte[] data` buffer purely based on attacker-controlled varint continuation bits and field lengths, with **no explicit bounds check** — the file's own header comment states this is deliberate: "these functions don't do boundary check on the byte array but instead rely on Java VM to check it... parsing routines... must catch IndexOutOfBoundsException... when crossing protobuf public API boundaries" [1](#0-0) .

### Finding Description
`decodeVarint32`/`decodeVarint64` read successive bytes (`data[position++]`) following the continuation bit of each byte, with no check that `position < data.length` before each read [2](#0-1) . Packed-list decoders similarly compute a `fieldLimit = position + packedDataByteSize` from an attacker-supplied length prefix and loop `while (position < fieldLimit)` calling these same unchecked varint readers [3](#0-2) . Unpacked list decoders (fixed32/fixed64/float/double/varint/sint) advance `position` by fixed strides or via `decodeVarint32` calls driven by tag matching, again with no guard against reading past `data.length` [4](#0-3) .

This mirrors the xpdf flaw's failed invariant: **a decode loop's forward progress is entirely governed by attacker-controlled data (continuation bits / length prefixes) instead of an explicit remaining-bytes check**, and the design intentionally offloads bounds enforcement to a downstream mechanism (JVM array-bounds checking here; presumably table bounds in xpdf, which failed to enforce it). The attacker-controlled values are the varint continuation bits and the packed-field byte-length prefix, both fully controlled by an ordinary client sending a bounded binary Protobuf payload through `parseFrom`/`mergeFrom` on a Lite-runtime generated message.

### Impact Explanation
By itself, an `IndexOutOfBoundsException` thrown by the JVM is a *safe*, catchable Java exception — not a memory-corruption bug like the C-based xpdf overread. The documented contract requires callers "crossing protobuf public API boundaries" to catch `IndexOutOfBoundsException` and rethrow it as `InvalidProtocolBufferException`. I was not able to conclusively locate and verify that catch in this checkout: `grep` for `IndexOutOfBoundsException` in `CodedInputStream.java` returned **no matches**, and I could not complete verification of the exact call sites in `MessageSchema.mergeFrom`/`GeneratedMessageLite.parseFrom` that wrap Lite array-based parsing before the session ended. If such a catch is indeed missing or incomplete on some call path (e.g., an extension or map-field path that invokes `ArrayDecoders` directly), a crafted truncated varint or packed field would surface an uncaught `RuntimeException` to the caller instead of the documented `InvalidProtocolBufferException`, which is a denial-of-service (unhandled exception/crash) analog to the CVE's "application crash" impact — but only a DoS, not memory corruption, consistent with the rules excluding RCE claims from a crash alone.

### Likelihood Explanation
Moderate-to-low confidence given incomplete verification. The mechanism (unchecked, attacker-driven forward index advancement based on continuation bits/lengths) is real and matches the CVE's root-cause pattern precisely, and the pattern is reachable from any public `parseFrom` call using the Lite runtime and its generated `MessageSchema`-based parsing of packed/repeated fields. However, protobuf-java's documented design explicitly anticipates and mitigates this via a required catch-and-convert at the API boundary; whether that catch is complete for every call path (all field types/extensions) in this exact revision could not be confirmed with the tools available here.

### Recommendation
Verify that every public entry point that can invoke `ArrayDecoders` (via `MessageSchema.mergeFrom`, extension parsing, map-field parsing) wraps calls in `try { ... } catch (IndexOutOfBoundsException e) { throw InvalidProtocolBufferException.truncatedMessage(); }`, with unit tests using intentionally truncated packed/unpacked varint, fixed32/64, and string fields (including truncated UTF-8 length prefixes) for every field kind handled in `parseRepeatedField`. Add defensive `position < limit`/`data.length` assertions at the top of each `ArrayDecoders` helper as a second line of defense, consistent with how `decodeLengthPrefixVarint` already validates `length > limit - position` [5](#0-4) .

### Proof of Concept

A minimal reproduction would construct a Lite-generated message byte array where a packed varint field's length prefix is set larger than remaining buffer bytes, or where a repeated fixed64 field's declared count implies reading past `data.length` (analogous to the Java packed-field unit tests already present in the repo, e.g. `WireFormatLiteTest.testParsePackedFieldsWithIncorrectLength`, which tests the *lite* packed-length-mismatch case but does not by itself prove whether truncation past the actual array bounds is uniformly caught) [6](#0-5) .   /** Like decodeVarint32 except that the first byte is already read. */
  static int decodeVarint32(int firstByte, byte[] data, int position, Registers registers) {
    int value = firstByte & 0x7F;
    final byte b2 = data[position++];
    if (b2 >= 0) {
      registers.int1 = value | ((int) b2 << 7);
      return position;
    }
    value |= (b2 & 0x7F) << 7;

    if (b3 >= 0) {

      throws InvalidProtocolBufferException {
    position = decodeVarint32(data, position, registers);
    final int length = registers.int1;
    if (length < 0) {
      throw InvalidProtocolBufferException.negativeSize();
    } else if (length > limit - position) {
      throw InvalidProtocolBufferException.truncatedMessage();
    }

  static int decodeVarint64List(
      int tag, byte[] data, int position, int limit, ProtobufList<?> list, Registers registers) {
    final LongArrayList output = (LongArrayList) list;
    position = decodeVarint64(data, position, registers);
    output.addLong(registers.long1);
    while (position < limit) {
      int nextPosition = decodeVarint32(data, position, registers);
      if (tag != registers.int1) {
        break;
      }
      position = decodeVarint64(data, nextPosition, registers);
      output.addLong(registers.long1);
    }
    return position;
  }

  /** Decodes a packed 32-bit varint field. Returns the position after all read values. */
  static int decodePackedVarint32List(
      byte[] data, int position, ProtobufList<?> list, Registers registers) throws IOException {
    final IntArrayList output = (IntArrayList) list;
    position = decodeLengthPrefixVarint(data, position, data.length, registers);
    final int packedDataByteSize = registers.int1;
    final int fieldLimit = position + packedDataByteSize;
    while (position < fieldLimit) {
      position = decodeVarint32(data, position, registers);
      output.addInt(registers.int1);
    }
    if (position != fieldLimit) {
      throw InvalidProtocolBufferException.truncatedMessage();
    }
    return position;
  }
