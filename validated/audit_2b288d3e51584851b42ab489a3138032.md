### Title
Ambiguous/non-terminated ident regex in `CommitIdentity.parseIdentity` allows an attacker-crafted commit author field to spoof the parsed name/email/date shown in the UI - (File: `app/src/models/commit-identity.ts`)

### Summary
`CommitIdentity.parseIdentity` uses a lazy, **not end-anchored** regex to split a raw `GIT_AUTHOR_IDENT`/`GIT_COMMITTER_IDENT`-style string into `name`, `email`, `date`, and `tzOffset`. Because both capture groups are non-greedy and the pattern has no `$` anchor, the regex matches the **first** substring in the string that looks like `<...> <digits> <sign><HH><MM>`, not necessarily the one that git intended to be the actual email/date pair for that identity. [1](#0-0) 

### Finding Description
`getCommits` builds the raw identity string it hands to `parseIdentity` by simple string concatenation of `%an <%ae> %ad` (and `%cn <%ce> %cd` for committer): [2](#0-1) 

`%an`/`%cn` are the raw author/committer **name** fields taken directly from the commit object. Git's porcelain commit path (`ident.c`) strips `<`/`>` from a name entered via `git commit`, but that sanitization only happens when a commit is *created* through git's normal ident-formatting code path — it is not re-validated when git objects are merely read back with `%an`. A commit object can be constructed with arbitrary bytes in the name field via plumbing (e.g. `git hash-object -t commit`, `git commit-tree`, or by writing a loose object directly), and Desktop performs no validation of commit-object contents on clone/fetch (`transfer.fsckObjects` is not on by default and Desktop doesn't set it).

If an attacker crafts a commit whose author name field itself contains a `"<...> <digits> +/-HHMM"`-shaped substring, e.g.:
```
author Real Name <spoof@trusted.example> 1200000000 +0000 junk <realauthor@evil.example> 1699999999 +0000
```
the string handed to `parseIdentity` becomes:
```
Real Name <spoof@trusted.example> 1200000000 +0000 junk <realauthor@evil.example> 1699999999 +0000
```
Because `parseIdentity`'s regex is lazy and unanchored at the end, it stops at the **first** valid match:
- `name` = `"Real Name"`
- `email` = `"spoof@trusted.example"`
- `date`/`tzOffset` from `1200000000 +0000`

The genuine trailing `<realauthor@evil.example> 1699999999 +0000` segment is silently discarded and never parsed — the app has no way to detect that the identity string it received was actually a longer, different value.

### Impact Explanation
`CommitIdentity` values produced by this path feed directly into UI-facing trust signals:
- `getAvatarUserFromAuthor` uses `author.email`/`author.name` verbatim to build the avatar/gravatar lookup and to key deduplication of shown avatars [3](#0-2) 
- `commit-message.tsx`'s `renderAvatar` uses `commitAuthor.email` to decide whether to show a "misattribution"/"disallowed email" warning and which avatar to render [4](#0-3) 

By choosing a spoofed email that happens to match a trusted account's address (or one that passes `isAttributableEmailFor`), an attacker-authored commit can make Desktop's UI display a different avatar/identity than the one actually recorded, or avoid displaying misattribution warnings that would otherwise flag a suspicious commit. This is a UI-trust/spoofing issue, not remote code execution or credential exfiltration — the underlying git object and its real author metadata are unaffected; only what GitHub Desktop *displays* to the user is corrupted.

### Likelihood Explanation
Requires the attacker to control the content of a repository the victim clones/fetches (in scope) and to craft a commit object at the plumbing level with an engineered author-name field. This is straightforward to do (`git commit-tree`/direct object write) and does not require any privileged access, but it does depend on the app rendering author identity for the crafted commit (which happens automatically for any commit shown in history/changes views), so likelihood of exposure is high once such a repo is opened, though the practical value of the spoof (choosing an email that maps to an interesting avatar/trust indicator) is attacker-effort-dependent.

### Recommendation
- Anchor the regex to the end of the string (or otherwise require the full remainder of the string to be consumed) so that the identity is only accepted if the entire string parses as `NAME <EMAIL> TIMESTAMP TZ` with no matching-ambiguity, e.g. `^(.*) <(.*)> (\d+) ([+-])(\d{2})(\d{2})$` (greedy name match plus end anchor forces the *last* `<...>` block near the end to be used, matching git's own right-to-left `ident.c` parsing behavior) rather than the current leftmost/lazy match.
- Alternatively, reject/normalize any name or email component that itself contains `<`, `>`, or embedded digit-timestamp-looking sequences before display.
- Add a regression test with a crafted identity string containing an embedded fake `<email> timestamp +tz` sequence in the name portion to ensure the parser doesn't silently swallow the real trailing identity segment.

### Proof of Concept
```ts
import { CommitIdentity } from '../../src/models/commit-identity'

const crafted =
  'Real Name <spoof@trusted.example> 1200000000 +0000 junk <realauthor@evil.example> 1699999999 +0000'

const identity = CommitIdentity.parseIdentity(crafted)

console.log(identity.name)   // "Real Name"           (as intended)
console.log(identity.email)  // "spoof@trusted.example"  <-- attacker-chosen, not the trailing "real" email
console.log(identity.date)   // 2008-01-11T... (from 1200000000) instead of the later trailing timestamp
```
This can be reproduced end-to-end by cloning a repository containing a commit created via `git commit-tree` (or a hand-written loose object) whose author line is:
```
author Real Name <spoof@trusted.example> 1200000000 +0000 junk <realauthor@evil.example> 1699999999 +0000
```
then opening that repository's history in GitHub Desktop and observing that the author avatar/email shown is `spoof@trusted.example` rather than any faithful representation of the crafted raw field.
