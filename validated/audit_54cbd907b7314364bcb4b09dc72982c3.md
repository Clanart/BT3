### Title
Unbound encrypted-share recipient enables cross-recipient replay and false blame - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
PedPoP’s per-message proof of possession authenticates the sender and ciphertext but omits the intended recipient. Consequently, an encrypted share created for one participant remains a valid `EncryptedMessage` when presented under the same sender to another participant, who derives the wrong ECDH key, obtains an invalid share, and produces blame against an honest sender. [1](#0-0) 

### Finding Description
`encrypt` uses the recipient’s registered public encryption key to derive the ChaCha20 key, but the accompanying Schnorr PoP only commits to `context`, `nonce`, `key`, `sender`, and ciphertext. [2](#0-1) [1](#0-0) 

`Encryption::decrypt` verifies this sender-bound PoP and then derives the ECDH secret using the local participant’s private encryption key, without proving that the message was encrypted for that participant. [3](#0-2) 

`KeyMachine::calculate_share` attributes each supplied message to the participant used as the map key, decrypts it, and treats either a non-canonical scalar or failed polynomial verification as that sender’s invalid share. [4](#0-3) 

The resulting `EncryptionKeyProof` is subsequently accepted by `blame_internal`, which returns the supplied `sender` when the decrypted bytes are non-canonical or fail share verification. [5](#0-4) 

### Impact Explanation
A transport-level attacker who can replay a ciphertext onto another sender-authenticated delivery path can turn a valid share for participant `r1` into an invalid share for participant `r2`, aborting key generation and causing the honest sender to be blamed. [6](#0-5)  This can translate into an incorrect fatal fault attribution where PedPoP blame is acted upon as evidence of equivocation or malformed-share submission.

### Likelihood Explanation
The attack does not require knowledge of the sender’s secret share or either party’s encryption private key; it only requires replaying an existing ciphertext under the same sender identity to a different recipient. [7](#0-6)  With overwhelming probability, the wrong-recipient ECDH produces either a non-canonical scalar or a scalar that fails polynomial verification, yielding a blame artifact against the sender. [8](#0-7) 

### Recommendation
Bind the intended recipient into the per-message PoP. Specifically, extend `pop_challenge` with the recipient `Participant` and preferably the recipient’s registered public encryption key; `encrypt` should pass the recipient/key used for ECDH, while `decrypt` and `decrypt_with_proof` should require the local/supplied decryptor identity and key. A ciphertext replayed to another participant will then fail `msg.pop.verify` before any blame proof can attribute the malformed share to the sender. [9](#0-8) 

### Proof of Concept

```rust
// Alice generated per-recipient shares during PedPoP.
let alice_to_bob: EncryptedMessage<C, SecretShare<C::F>> =
    shares_for_bob[&alice].clone();

// A transport attacker presents Alice's Bob-directed ciphertext as
// Alice's message on the Alice -> Carol path.
let mut carol_inputs = HashMap::new();
carol_inputs.insert(alice, alice_to_bob);

// The PoP verifies because `from == alice` and the ciphertext is unchanged.
// Carol nevertheless decrypts using c * msg.key rather than b * msg.key.
let err = carol_machine.calculate_share(rng, carol_inputs).unwrap_err();
let PedPoPError::InvalidShare { participant, blame } = err else {
    panic!("expected invalid share");
};
assert_eq!(participant, alice);

// The proof demonstrates the ECDH key for Carol and the supplied message.
let blamed = AdditionalBlameMachine::new(context, n, commitment_msgs)
    .unwrap()
    .blame(alice, carol, alice_to_bob, blame);
assert_eq!(blamed, alice);
```

```rust
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],

  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop

  // This, as written above, doesn't hurt

  // an unknown to anyone discrete log, breaking the system
```

```rust
  pub fn calculate_share<R: RngCore + CryptoRng>(
    mut self,
    rng: &mut R,
    mut shares: HashMap<Participant, EncryptedMessage<C, SecretShare<C::F>>>,
  ) -> Result<BlameMachine<C>, PedPoPError<C>> {
    validate_map(
      &shares,
      &self.params.all_participant_indexes().collect::<Vec<_>>(),
      self.params.i(),
    )?;

    let mut batch = BatchVerifier::new(shares.len());
    let mut blames = HashMap::new();
    for (l, share_bytes) in shares.drain() {
      let (mut share_bytes, blame) =
        self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
      let share =
        Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
          PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
        })?);
      share_bytes.zeroize();
      *self.secret += share.deref();

      blames.insert(l, blame);
      batch.queue(
        rng,
        BatchId::Share(l),
        share_verification_statements::<C>(self.params.i(), &self.commitments[&l], share),
      );
    }
    batch.verify_with_vartime_blame().map_err(|id| {
      let (l, blame) = match id {
        BatchId::Decryption(l) => (l, None),
        BatchId::Share(l) => (l, Some(blames.remove(&l).unwrap())),
      };
      PedPoPError::InvalidShare { participant: l, blame }
    })?;
```
