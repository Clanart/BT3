### Title
Unauthenticated `ReceivedOutput` deserialization permits fictitious Bitcoin funds to be credited and signed - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` accepts an arbitrary scalar offset, `TxOut`, and `OutPoint` without proving that the outpoint exists, contains the claimed value, or pays to the claimed key. [1](#0-0)  A forged serialized object can therefore be treated as spendable Bitcoin collateral even though no corresponding UTXO exists.

### Finding Description
`ReceivedOutput` is defined as “a spendable output,” but its `read` implementation performs only syntactic scalar and consensus decoding. [2](#0-1)  It does not check blockchain provenance, whether the outpoint is unspent, whether the real output has the claimed amount, or whether the output script corresponds to the supplied offset. [3](#0-2) 

`SignableTransaction::new` then treats `input.output.value` as available input value and `input.outpoint` as a real previous output. [4](#0-3)  The same claimed `TxOut` is committed as a Taproot prevout, so the inflated amount directly affects fee, payment, and change calculations. [5](#0-4) 

`SignableTransaction::multisig` verifies only that the serialized prevout script equals the script derived from the threshold key plus the supplied offset; it does not verify that `previous_output` actually references such a UTXO. [6](#0-5)  Signing then commits the fabricated prevout set through `Prevouts::All`, allowing the threshold group to produce a transaction that Bitcoin consensus will reject because the input does not exist or does not match the actual prevout data. [7](#0-6) 

This mirrors the reported bug class: an attacker-controlled value is accepted as authoritative collateral state instead of being derived from a trusted, consensus-validated source. [1](#0-0) 

### Impact Explanation
An unprivileged party who can supply serialized `ReceivedOutput` bytes can cause an application to report or account for funds that are not spendable. [3](#0-2)  If the forged object uses a script matching the expected offset key, the object can pass the wallet’s only ownership check and cause construction and threshold signing of a transaction spending a nonexistent or mismatched outpoint. [6](#0-5) 

The resulting transaction cannot be validly broadcast, but downstream systems may already have credited deposits, released counterparties, or selected the fictitious input for a signing session. [4](#0-3)  This is a concrete “funds reported received that are not spendable” impact and can also cause unnecessary threshold-signing work and invalid transaction generation. [8](#0-7) 

### Likelihood Explanation
The attack requires only control of bytes passed to `ReceivedOutput::read`; no private key, validator compromise, malformed curve point, or invalid Bitcoin encoding is needed. [1](#0-0)  The crafted data is cheap to construct because all three fields are attacker-controlled and no on-chain evidence is requested. [3](#0-2) 

The impact is bounded because consensus nodes will reject the resulting transaction, so this is best rated **Medium** rather than Critical or High. [8](#0-7) 

### Recommendation
Do not treat deserialized `ReceivedOutput` values as authenticated scanner results. [1](#0-0)  Require `ReceivedOutput` objects consumed by accounting or transaction construction to originate from `Scanner::scan_transaction` or another consensus-validated source, and re-fetch/compare the referenced outpoint’s full `TxOut` before crediting or spending it. [9](#0-8) 

If untrusted serialization must remain supported, expose it as an unverified wire representation and add a contextual validation API that binds the base key, offset, script, outpoint, and amount to confirmed blockchain data before conversion into `ReceivedOutput`. [6](#0-5) 

### Proof of Concept
The following constructs a syntactically valid `ReceivedOutput` claiming an arbitrary value at a nonexistent outpoint. [3](#0-2) 

```rust
// networks/bitcoin/src/wallet/mod.rs
use bitcoin::{
  consensus::serialize,
  hashes::Hash,
  Amount, OutPoint, ScriptBuf, TxOut, Txid,
};
use bitcoin_serai::wallet::ReceivedOutput;

fn forged_received_output(attacker_script: ScriptBuf) -> ReceivedOutput {
  // Offset scalar: zero is canonical and makes the script correspond to the base key.
  let mut bytes = vec![0; 32];

  // Claimed prevout contents and value.
  let fake_txout = TxOut {
    value: Amount::from_sat(1_000_000_000),
    script_pubkey: attacker_script,
  };
  bytes.extend(serialize(&fake_txout));

  // No UTXO needs to exist at this outpoint.
  let fake_outpoint = OutPoint {
    txid: Txid::from_byte_array([0x41; 32]),
    vout: 0,
  };
  bytes.extend(serialize(&fake_outpoint));

  ReceivedOutput::read(&mut bytes.as_slice()).unwrap()
}
```

For a target threshold key, setting `attacker_script` to the output of `p2tr_script_buf(key)` makes `SignableTransaction::multisig` accept the object under offset zero. [6](#0-5)  `SignableTransaction::new` then counts the claimed satoshis as inputs and uses the fake outpoint in the transaction despite the absence of a real UTXO. [4](#0-3)
