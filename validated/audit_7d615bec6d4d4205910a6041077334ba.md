### Title
Unsynchronized `reason`/`err` field write (Stop) vs. read (CaptureState/CaptureExit/GetResult) causes data race in `InternalTxTracer` and JS `Tracer` used by public `debug_trace*` RPCs - ([File: blockchain/vm/internaltx_tracer.go], [File: node/cn/tracers/tracer.go])

### Summary
The upstream go-ethereum fix (#34827) addressed a data race where a tracer's interruption `reason error` field was written by `Stop()` (invoked from a timeout watchdog goroutine) and read by `GetResult()`/step callbacks (invoked from the main tracing goroutine) without synchronization. The Kaia codebase contains the identical unsynchronized pattern in two tracer implementations that are reachable via public RPC tracing endpoints: `blockchain/vm/internaltx_tracer.go` (`InternalTxTracer`) and `node/cn/tracers/tracer.go` (JS `Tracer`). Notably, two sibling tracers in the same package, `CallTracer` (`blockchain/vm/call_tracer.go`) and `PrestateTracer` (`blockchain/vm/prestate_tracer.go`), have already been hardened with atomic reason storage and explicit happens-before comments, while `InternalTxTracer` and `Tracer` were left with a plain `error` field guarded only by a separate atomic flag.

### Finding Description
Both vulnerable tracers use the same broken pattern:

`InternalTxTracer`: [1](#0-0) 
holds `interrupt atomic.Uint32` and a plain `reason error` field. `Stop()` writes `t.reason` then stores the atomic flag: [2](#0-1) 
`CaptureState()` reads `t.interrupt.Load()` and then reads `t.reason` into `t.err`: [3](#0-2) 

JS `Tracer` has the identical layout: [4](#0-3) 
`Stop()`: [5](#0-4) 
and `CaptureExit()` reading `jst.reason` after observing the flag: [6](#0-5) 

Although the flag itself (`atomic.Uint32`/`atomic.Store`/`Load`) is accessed atomically, the plain `error` field write in `Stop()` and read in `CaptureState`/`CaptureExit`/`GetResult` is a separate, non-atomic memory access. On platforms/compilers without a strict store-then-store / load-then-load ordering guarantee for adjacent non-atomic and atomic operations, this is a classic Go data race (flagged by `-race`), because Go's memory model does not guarantee that a plain write becomes visible before a subsequent unrelated atomic operation unless it is part of the same atomic value or protected by a lock. This is exactly the bug class fixed upstream by converting the raw `error` field to an atomic-guarded value (as already done for `CallTracer.interruptReason` and `PrestateTracer.reason` in this same repo, showing the maintainers recognized and partially fixed this issue but missed `InternalTxTracer` and the JS `Tracer`).

The tracers are invoked from `node/cn/tracers/api.go`, in `traceTx`, where the trace-timeout mechanism runs `Stop()` from a watchdog goroutine concurrently with the main EVM execution goroutine calling the tracer's `Capture*` hooks and ultimately `GetResult()`: [7](#0-6) 

### Impact Explanation
This is a data race, not a straightforward "value movement" bug — the direct impact is memory-safety-adjacent (race detector failures, potential torn reads of the `error` interface causing panics or corrupted error values, e.g., mismatched dynamic-type/pointer pairs of the `error` interface value read concurrently with its write). A torn `error` interface read could cause a panic (nil dereference or type assertion failure inside RPC handling) or return an incorrect/garbage trace result to the RPC caller. Any public caller who can invoke `debug_traceTransaction`, `debug_traceCall`, or `debug_traceBlock*` with a long-running/looping transaction can trigger the timeout path that races with the interrupt reason field. This does not directly enable fund theft or consensus divergence, but it can cause node crashes/RPC service disruption (panic in the RPC goroutine) or corrupted trace output, which is a reliability/availability issue for public-RPC infrastructure.

### Likelihood Explanation
Likelihood is moderate: it requires a public RPC consumer to submit a `debug_trace*` call for a transaction/call that runs long enough to hit the tracer timeout (`Context.Timeout` in tracer config), which any external RPC caller can trigger by crafting a computation-heavy call (e.g., a loop) and requesting tracing with a short timeout. The race window is small but is a genuine unsynchronized memory access reachable without any special privileges.

### Recommendation
Apply the same fix used for `CallTracer` and `PrestateTracer` in this repo to `InternalTxTracer` and the JS `Tracer`:
- Replace the plain `reason error` field with an atomically-guarded value (e.g., `atomic.Pointer[error]` as done in `PrestateTracer.Stop`/`GetResult`, or store-once-then-load-only-after-flag-observed as done in `CallTracer`), ensuring a proper happens-before relationship between `Stop()`'s write and any read in `CaptureState`, `CaptureExit`, and `GetResult`.
- Update `blockchain/vm/internaltx_tracer.go` (`InternalTxTracer.reason`) and `node/cn/tracers/tracer.go` (`Tracer.reason`) accordingly.
- Run the existing tracer tests (e.g., `TestHaltBetweenSteps` in `node/cn/tracers/tracer_test.go`) under `go test -race` to confirm the fix.

### Proof of Concept
1. Submit `debug_traceCall`/`debug_traceTransaction` for a transaction that executes an unbounded loop (or a contract deliberately consuming near the full block gas limit in a tight loop), with the tracer configured to use the internal-call or JS tracer and a short `timeout` in `TraceConfig`.
2. The trace-timeout watchdog goroutine in `node/cn/tracers/api.go` calls `tracer.Stop(errExecutionTimeout)` concurrently with the main goroutine's ongoing `CaptureState`/`CaptureExit` calls inside `blockchain.ApplyMessage(vmenv, message)` (see `traceTx`), [8](#0-7) .
3. Running the node binary/tests built with `-race` against repeated concurrent trace-timeout scenarios exercises the unsynchronized `reason`/`err` field access in `InternalTxTracer.CaptureState` [9](#0-8)  and `Tracer.CaptureExit` [6](#0-5) , and the Go race detector reports the race.
