### Title
Attacker-controlled participant index in PedPoP blame evaluation panics the process via unchecked HashMap indexing - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2024-21194 is an availability bug: a remote input path lets an attacker trigger a repeatable crash/hang of the server. The Serai analog lives in the PedPoP DKG blame machinery. `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` with a participant index that is fully attacker-controlled, and `BlameMachine::blame_internal` / `AdditionalBlameMachine::blame` pass the `recipient` argument straight through with no bounds check against the DKG's `1..=n` registration set. Any party able to submit a blame accusation (a normal, unprivileged protocol input — `AdditionalBlameMachine` is explicitly designed so non-members can evaluate blame) can crash the evaluating node.

### Finding Description
`Decryption::register` only inserts entries for participants actually registered (in `AdditionalBlameMachine::new`, exactly `1..=n` at `crypto/dkg/pedpop/src/lib.rs:656-660`). In `decrypt_with_proof`, the decryptor's registered encryption key is fetched by direct indexing at `crypto/dkg/pedpop/src/encryption.rs:388`:

```rust
&[self.enc_keys[&decryptor], *proof.key],
```

`HashMap`'s `Index` impl panics on a missing key. `decryptor` here is the `recipient` parameter of `blame`/`blame_internal` (`crypto/dkg/pedpop/src/lib.rs:575-588`), which is supplied by the accusation being evaluated — i.e., attacker input. No check enforces `recipient ∈ 1..=n` or `enc_keys.contains_key(&recipient)` before the index.

The only gate before the panic is `msg.pop.verify(...)` at `encryption.rs:374-379`, which the attacker trivially satisfies: they generate any scalar `k`, set `msg.key = k*G`, and produce a valid Schnorr signature over `pop_challenge`, since the challenge binds only public values (`context`, `nonce`, `key`, `sender`, `msg`). A `proof: Some(EncryptionKeyProof { key: anything_valid, dleq: anything_parseable })` then reaches line 388 and panics while evaluating the argument slice — before `dleq.verify` even runs.

A second reachable panic of the same class exists at `crypto/dkg/pedpop/src/lib.rs:599`, where `blame_internal` indexes `self.commitments[&sender]` — an attacker-supplied `sender` outside `1..=n` panics once `decrypt_with_proof` succeeds.

### Impact Explanation
An attacker can repeatedly crash any node running `BlameMachine::blame` or `AdditionalBlameMachine::blame` — the exact "hang or frequently repeatable crash (complete DOS)" impact of the CVE. In a validator/coordinator deployment, panic-per-accusation means a single malicious participant (or even a non-participant submitting accusations to `AdditionalBlameMachine`, which exists precisely for third-party evaluation) can abort the process every time blame is evaluated, denying DKG completion and dispute resolution. If panics unwind rather than abort, the crash still tears down the in-progress key-generation state machine.

### Likelihood Explanation
Triggering requires only: (a) the ability to submit a blame accusation naming an out-of-range `sender`/`recipient` `Participant` — `Participant::new` accepts any non-zero `u16`, so e.g. `Participant(0xFFFF)` when `n < 0xFFFF` — and (b) a well-formed `EncryptedMessage` with a valid Schnorr PoP, which the attacker constructs freely from public values. No threshold collusion, key knowledge, or privileged position is needed; blame evaluation is a public-input path.

### Recommendation
Replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with fallible lookups (`get` + explicit `DecryptionError`/blame outcome), and validate `sender`/`recipient` against the registered participant set at the top of `blame_internal` before any indexing. More broadly, audit all `map[&key]` index expressions on attacker-derived `Participant`/`BatchId` values in `crypto/dkg` and `crypto/frost` (e.g., `responses[l]`, `self.0[&l]`) to confirm the validating `validate_map` calls fully constrain them.

### Proof of Concept
```rust
// Setup: a 2-of-3 DKG context; AdditionalBlameMachine built over participants 1..=3
let params = ThresholdParams::new(2, 3, Participant::new(1).unwrap()).unwrap();
let context = [0u8; 32];
// ... run KeyGenMachine for each participant, collect EncryptionKeyMessage<Commitments> ...
let machine = AdditionalBlameMachine::<Ristretto>::new(context, 3, commitment_msgs).unwrap();

// Attacker: a validly-signed EncryptedMessage, but accusation names Participant(0xFFFF)
let key = Zeroizing::new(<Ristretto as Ciphersuite>::random_nonzero_F(&mut rng));
let pub_key = Ristretto::generator() * *key;
let nonce = Zeroizing::new(<Ristretto as Ciphersuite>::random_nonzero_F(&mut rng));
let pub_nonce = Ristretto::generator() * *nonce;
let msg_bytes = SecretShare::<<Ristretto as Ciphersuite>::F>(Scalar::ONE.to_repr());
let pop = SchnorrSignature::sign(
    &key, nonce,
    pop_challenge::<Ristretto>(context, pub_nonce, pub_key,
        Participant::new(1).unwrap(), msg_bytes.as_ref()),
);
let evil_msg = EncryptedMessage { key: pub_key, pop, msg: Zeroizing::new(msg_bytes) };
let any_proof = Some(EncryptionKeyProof { /* any parseable key + dleq */ });

// Panics at crypto/dkg/pedpop/src/encryption.rs:388 on `self.enc_keys[&decryptor]`
machine.blame(
    Participant::new(1).unwrap(),        // sender
    Participant::new(0xFFFF).unwrap(),   // recipient: valid Participant, not in 1..=3
    evil_msg,
    any_proof,
);
```
