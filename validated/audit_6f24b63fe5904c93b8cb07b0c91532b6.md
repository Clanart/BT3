### Title
DataLayer Mirror URLs Are Never Validated Before Server-Side HTTP Requests, Enabling SSRF Against Internal Hosts - (File: chia/data_layer/download_data.py)

### Summary
Any wallet holder can publish a DataLayer "mirror" coin on-chain with arbitrary attacker-controlled URLs via `dl_new_mirror`/`create_new_mirror`, which are stored as free-form strings in the mirror coin's memos with no host/scheme allow-listing. Any DataLayer node subscribed to that store id (a normal Data Layer client role) later reads those URLs from the wallet (`update_subscriptions_from_wallet`) and, via its own background sync loop, has its server automatically issue outbound HTTP requests to them (`http_download`, `get_downloader`, `get_uploaders`, `get_plugin_info`). This is the same bug class as the Ghost SSRF advisory (CWE-918): untrusted user-controlled input directly drives a server-side outbound HTTP request with no validation against internal/private network destinations.

### Finding Description
`DataLayerWallet.create_new_mirror()` writes attacker-supplied URLs directly into the memos of a mirror coin with no validation of scheme or host: [1](#0-0) 

The wallet RPC (`dl_new_mirror`) exposes this to any wallet owner without restriction: [2](#0-1) 

Any node that subscribes to (or owns) that store id reads these mirror URLs straight from the chain/wallet and inserts them as subscription server info, again with no validation: [3](#0-2) 

The background sync loop (`periodically_manage_data` → `update_subscription` → `fetch_and_validate`) then iterates over these server URLs and calls `insert_from_delta_file`/`download_file`, which performs a raw `aiohttp` GET to `server_info.url + "/" + filename` with no host restriction: [4](#0-3) [5](#0-4) 

Similarly, plugin/downloader/uploader URLs configured via `get_downloader`, `get_uploaders`, and `get_plugin_info` also perform POST requests to fully attacker-influenced URLs (in the downloader case, `server_info.url`, which is the same untrusted mirror URL, is embedded in the outgoing JSON body/request target): [6](#0-5) [7](#0-6) 

None of these code paths perform DNS/IP-range validation (no `ipaddress`, no private-range denylist, no scheme restriction) before making the outbound request — confirmed by the absence of any such validation logic in `chia/data_layer/*` (`is_filename_valid()` only validates local file naming, not remote URLs).

### Impact Explanation
An unprivileged chain participant (any wallet owner, reachable exactly like the "Data Layer client" persona in scope) can create a mirror coin whose URLs point at internal-network endpoints (e.g. `http://127.0.0.1:<port>/...`, `http://169.254.169.254/...` cloud metadata, or other RFC1918 addresses reachable from the DataLayer host). Any other node that subscribes to that store — including via the normal `dl track_new`/subscribe flow that any Data Layer client is expected to use — will have its own DataLayer service (server-side process) automatically issue outbound HTTP GET/POST requests to that address once per sync cycle (default every 60s per `manage_data_interval`), without the operator explicitly choosing to contact that host. This matches CVSS AC:H/PR:N/UI:N/S:C/C:L profile of the reference advisory: the requesting node's process makes limited HTTP requests into its internal network on behalf of an unauthenticated/low-privileged third party, though the HTTP response body/status is not returned to the attacker directly (some information, such as request timing/ban behavior differences for reachable vs. unreachable hosts, can be inferred by the mirror publisher via subsequent `get_mirrors`/timing side channels).

### Likelihood Explanation
Likelihood is high given reachability: publishing a mirror requires only a normal wallet spend (`dl_new_mirror`) with no special permission, and subscribing to a store id (`subscribe`) is a routine, expected Data Layer client action. There is no code path that filters or rejects private/loopback/link-local addresses before the sync loop issues requests, so any store subscriber is automatically exposed.

### Recommendation
- Validate all mirror/downloader/uploader URLs before use for outbound requests: enforce `http`/`https` scheme, resolve the hostname, and reject connections to private, loopback, link-local, and multicast IP ranges (RFC1918, RFC5735, `169.254.0.0/16`, etc.), consistent with standard SSRF mitigations.
- Apply this validation both at mirror creation time (`create_new_mirror`) as a courtesy check and — more importantly — at the point of use in `http_download`, `get_downloader`, `get_uploaders`, and `get_plugin_info` in `chia/data_layer/data_layer.py` and `chia/data_layer/download_data.py`, since the wallet-side check can be bypassed by external chain data.
- Optionally add an allow-list/deny-list configuration option (similar to `proxy_url`) so operators can explicitly opt in to internal mirror URLs when needed (e.g., in trusted private DataLayer deployments).

### Proof of Concept
1. Attacker wallet: call `dl_new_mirror` (or `chia data add_mirror`) for their own owned store, with `urls=["http://169.254.169.254/latest/meta-data/"]` (or any internal address reachable from the victim node) — [8](#0-7) .
2. Victim operator runs a DataLayer client and subscribes to the attacker's store id via `subscribe()` (a normal Data Layer client action) — [9](#0-8) .
3. On the next `periodically_manage_data` cycle, `update_subscriptions_from_wallet` pulls the attacker's URL from the mirror coin memo into the victim's subscription table, and `fetch_and_validate`/`http_download` causes the victim's DataLayer server process to issue an HTTP GET to the attacker-chosen internal URL — [3](#0-2) [4](#0-3) .

    async def get_downloader(self, store_id: bytes32, url: str) -> PluginRemote | None:
        request_json = {"store_id": store_id.hex(), "url": url}
        for d in self.downloaders:
            async with aiohttp.ClientSession() as session:
                try:
                    async with session.post(
                        d.url + "/handle_download",
                        json=request_json,
                        headers=d.headers,
                        timeout=self.client_timeout,
                    ) as response:
                        res_json = await response.json()
                        if res_json["handle_download"]:
                            return d
                except Exception as e:
                    self.log.error(f"get_downloader could not get response: {type(e).__name__}: {e}")
        return None

    async def subscribe(self, store_id: bytes32, urls: list[str]) -> Subscription:
        parsed_urls = [url.rstrip("/") for url in urls]
        subscription = Subscription(store_id, [ServerInfo(url, 0, 0) for url in parsed_urls])
        await self.wallet_rpc.dl_track_new(DLTrackNew(launcher_id=subscription.store_id))
        async with self.subscription_lock:
            await self.data_store.subscribe(subscription)
        self.log.info(f"Done adding subscription: {subscription.store_id}")
        return subscription

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
