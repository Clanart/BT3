### Title
Zero-slippage WOM→mWom buyback swap in `SmartWomConvert` is sandwichable, allowing theft of protocol WOM reward fees - (File: `wombat/SmartWomConvert.sol`)

### Summary
`SmartWomConvert._convertFor` performs an on-chain AMM swap of protocol-owned WOM into mWom with a hard-coded `amountOutMinimum` of `0`, i.e. no slippage protection at the swap-call level. This function is reachable from `WombatStaking._sendRewards`, which is triggered on every ordinary user deposit/withdraw through the Wombat staking flow, and swaps a portion of the collected WOM reward fee (funds belonging to all stakers, not the caller) through this unprotected swap.

### Finding Description
`_convertFor` builds a `tokenPath`/`poolPath` for `wom -> mWom` and calls: [1](#0-0) 
Note the `0` passed as `amountOutMin` to `IWombatRouter(router).swapExactTokensForTokens`. The only downstream protection is the aggregate check: [2](#0-1) 

This function is invoked by `smartConvert`, whose doc comment states it is meant to be driven by `WombatStaking`: [3](#0-2) 

`smartConvert` is called from `WombatStaking._sendRewards` on the WOM fee amount collected from the shared reward stream (not the caller's personal funds) whenever a fee is configured as mWOM-denominated: [4](#0-3) 

`_sendRewards` is called from `_toMasterWomAndSendReward`, which fires on ordinary deposit/withdraw actions that trigger a harvest from Wombat's MasterWombat: [5](#0-4) 

Because any ordinary wallet's deposit/withdraw transaction (via the pool helpers that call into `WombatStaking`) can trigger this harvest-and-fee-convert path at a predictable point, and the swap itself carries `amountOutMin = 0`, an attacker can front-run the transaction to move the `womMWomPool` price unfavorably, let the protocol's WOM fee swap execute at the manipulated (bad) price, and back-run to restore the pool — extracting the value lost by the protocol as arbitrage profit. Unlike a user's own `convert()`/`convertFor()` call (where the caller sets their own `_minRec` to protect their own funds), the WOM being swapped here belongs to the collective reward stream (`poolInfo.rewarder`/stakers), so the attacker profits at the expense of other users' claimable yield, and the only backstop is the crude `convertAmount + amountRec < _minRec` check where `_minRec == _amountIn` — an approximate 1:1 floor that still allows significant slippage/skim within that band before reverting.

### Impact Explanation
The vulnerability lets any actor extract value from the WOM reward fees destined for the reward pool/stakers, effectively stealing a portion of unclaimed yield that would otherwise accrue to legitimate stakers via `poolInfo.rewarder`. This matches "theft of unclaimed yield" impact criteria.

### Likelihood Explanation
Any ordinary wallet performing a normal deposit or withdraw that routes through `WombatStaking` can trigger the harvest/fee-convert path; an attacker only needs to observe the mempool for such transactions (or trigger their own) and sandwich the resulting WOM→mWom swap in `womMWomPool`, which requires no special privilege — a plain unprivileged-wallet MEV/sandwich strategy, similar in mechanism to the referenced AutoPxGmx report.

### Recommendation
Compute an on-chain-oracle- or TWAP-derived minimum output for the `buybackAmount` swap in `_convertFor` instead of hard-coding `0`, and tighten the aggregate `_minRec` check so it reflects true expected output (including expected router fees/slippage) rather than a loose `_amountIn` floor.

### Proof of Concept
1. Any user calls a deposit/withdraw path (e.g. via a Wombat pool helper) that ultimately invokes `WombatStaking._toMasterWomAndSendReward` → `_sendRewards`.
2. Because the WOM fee is configured `isMWOM = true`, `_sendRewards` calls `SmartWomConvert.smartConvert(feeAmount, 0)` [4](#0-3) .
3. `smartConvert` → `_convertFor` swaps the `buybackAmount` portion of the fee via `IWombatRouter.swapExactTokensForTokens(..., 0, ...)` [6](#0-5) .
4. An attacker front-runs step 3 by trading in `womMWomPool` to worsen the WOM→mWom rate, lets the protocol's swap execute at the bad rate (as long as `amountRec + convertAmount` stays ≥ `_amountIn`, the transaction won't revert), then back-runs to restore the pool, pocketing the difference extracted from the stakers' reward fee.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
