### Title
Relayer/fill fee escrowed at order placement is paid entirely to the last partial-fill solver instead of being distributed across all contributing solvers - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
The core invariant broken in the original ALCX report is: *value that accrues to a position/order incrementally is only ever released through one privileged completion path, and any code path that finalizes/burns the position without routing through that path forfeits or misdirects the accrued value.* The local Hyperbridge analog is in the same-chain intents fill logic: `order.fees` (the `TRANSACTION_FEES` escrow set once at `placeOrder`) is only released by `_withdraw` when `finalize == true`, and `_fillSameChain` sets `finalize = isFullyFilled`. Because `isFullyFilled` is a property of the *order*, not of the *solver making the current call*, the entire escrowed fee is transferred to whichever solver happens to submit the fill that pushes the order over 100%, even though multiple, unrelated solvers may have supplied all of the preceding partial fills.

### Finding Description
`_fillSameChain` in `evm/src/apps/intentsv2/IntrinsicIntents.sol` (lines 54-149) tracks cumulative progress per output token in `_partialFills[commitment][outputToken]` and computes `isFullyFilled` across the whole order: [1](#0-0) 

When `isFullyFilled` becomes true, the function builds a `WithdrawalRequest` whose `beneficiary` is `msg.sender` (the solver executing *this* fill call) and calls `_withdraw(body, false, isFullyFilled)`.

`_withdraw`, in `evm/src/apps/intentsv2/IntentsBase.sol`, only releases the escrowed `TRANSACTION_FEES` when `finalize` is true, and pays the entire balance to `beneficiary` — the caller of the completing fill: [2](#0-1) 

`order.fees` is escrowed once, in full, at `placeOrder` time as a single lump sum keyed only by `commitment`, with no per-solver or per-fill accounting: [3](#0-2) 

Because the fee escrow has no notion of "who contributed how much," any solver who submits the fill that flips `isFullyFilled` from `false` to `true` receives 100% of `order.fees`, regardless of whether they supplied 1% or 100% of the total output. Solvers who filled the first 99% of the order under `finalize == false` receive nothing from the fee pool — the funds aren't refunded to them, nor pro-rated; they are unconditionally routed to whichever address happens to close out the order last.

This mirrors the reported bug's root cause exactly: a single, order-scoped reward pool (ALCX rewards / `order.fees`) is claimed via one specific state transition (withdraw / final-fill), and any other legitimate contributor to the position's lifecycle (merge target / earlier partial filler) is excluded from that payout path, permanently losing their entitled share.

### Impact Explanation
This is a wrong-beneficiary / wrong-amount fault in reward settlement for a public, permissionless entry point (`fillOrder`). An unprivileged solver can capture value (the full `order.fees` payout) that should economically be shared with, or attributable to, earlier solvers who did the bulk of the fill work — value that those earlier solvers can never subsequently claim, since the `TRANSACTION_FEES` slot is `delete`d as soon as the first (and only) `finalize == true` withdrawal executes. This falls under the required impact category "wrong beneficiary or amount" for order escrow / relayer-style rewards; it doesn't require a malicious relayer, prover, or admin — any ordinary solver interacting with `fillOrder` can trigger and profit from it.

### Likelihood Explanation
High for any order that supports partial fills (the norm for same-chain orders) and carries `order.fees > 0`. No special timing, race condition with a privileged actor, or governance action is required — a rational solver simply needs to observe an order that is already mostly filled and undercut/complete the remaining sliver to sweep the entire fee pool. Because solver competition on such systems is expected and encouraged, this is a routinely reachable condition, not an edge case.

### Recommendation
Track the fee escrow proportionally to each partial fill's contribution (e.g., `feeShare = order.fees * fillAmount / totalOutputAmount`, transferred at the time each partial fill executes) instead of settling the entire lump sum only on the fill that satisfies `isFullyFilled`. Alternatively, refactor `_withdraw`'s fee-release condition so it triggers per-fill proportionally rather than being gated solely on the order-level `finalize` flag.

### Proof of Concept
1. User calls `placeOrder` with `order.fees = 100` fee-token units and an output requiring 100 units of token X.
2. Solver A calls `fillOrder` supplying 99 units of X. `_partialFills` becomes 99/100, `isFullyFilled = false`, so `_withdraw(..., false, false)` runs — Solver A receives their proportional input escrow but **no share of the 100 fee-token units** (fees untouched because `finalize == false`).
3. Solver B (unrelated, uninvolved in the first 99%) calls `fillOrder` supplying the last 1 unit of X. `isFullyFilled` becomes `true`; `_withdraw(..., false, true)` runs with `beneficiary = Solver B`, transferring the **entire 100 fee-token units** to Solver B alone.
4. Solver A, who supplied 99% of the fill, receives 0 of the fee pool and has no code path to reclaim any portion of it — the funds have already been irrevocably transferred to Solver B and the `TRANSACTION_FEES` storage slot deleted.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();

                IERC20(token).safeTransfer(beneficiary, amount);
