### Title
Stale line-selection indices reused against a freshly re-fetched diff can silently corrupt partial commits - (File: app/src/lib/git/apply.ts)

### Summary
`applyPatchToIndex` re-reads the working directory diff from disk immediately before building a patch, but applies the user's previously computed `DiffSelection` (a set of positional line indices) against that new diff without verifying the line positions still correspond to the same content. If the file changes between the time the user made a partial selection in the UI and the time the commit executes, the resulting patch can stage the wrong lines.

### Finding Description
`DiffSelection` tracks selected/unselected lines purely by numeric position (`absoluteIndex = hunk.unifiedDiffStart + lineIndex`), not by content hash or stable line identity. [4](#0-3)  When a user commits, `createCommit` → `stageFiles` → `applyPatchToIndex` is invoked. `applyPatchToIndex` calls `getWorkingDirectoryDiff(repository, file)` to fetch the diff at commit-time [5](#0-4) , then passes this fresh diff plus the (older) `file.selection` into `formatPatch`, which selects lines purely by `absoluteIndex` matching against `file.selection.isSelected(absoluteIndex)` [2](#0-1) .

The app is aware that diffs can change "dramatically" between load and use — this exact comment and a partial mitigation exists in `updateChangesWorkingDirectoryDiff`, but it only fires when the UI proactively reloads the diff for display, updating `selectableLines` to drop indices that no longer exist [3](#0-2) . This reconciliation is not present on the actual commit path (`apply.ts` / `update-index.ts` / `commit.ts`), which simply reuses whatever `DiffSelection` was last stored on the `WorkingDirectoryFileChange` object dispatched from the renderer.

### Impact Explanation
If the working tree file is modified between the user's selection action and the commit action (e.g., a slow autosave from an editor, a filesystem watcher-triggered externally-run formatter/hook, a git LFS smudge/clean filter, or any external process writing to a file the user is mid-review on — all plausible in normal desktop workflow without "local malware" or admin access), the line-position-based selection can map onto unrelated lines in the new diff. This causes the user to commit and push content they never intended and never saw — a silent corruption of what is committed, matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Requires a timing window between selection and commit plus an external write to the same file — plausible in normal usage (editors autosaving, formatters, git hooks, LFS filters) without any attacker having local/admin access to the user's machine. No existing guard revalidates `DiffSelection` positions against the diff fetched in `applyPatchToIndex` at commit time, unlike the UI display path which does perform such reconciliation.

### Recommendation
Before applying the patch in `applyPatchToIndex`, compare the diff last shown to the user (the one from which `selection` was derived) against the diff fetched fresh at commit time; if they differ, either abort with a "file changed since selection, please review" error, or re-run the same `selectableLines` reconciliation used in `updateChangesWorkingDirectoryDiff` and re-derive the user's intended selection against the new diff before building the patch.

### Proof of Concept
1. Modify a tracked file, open Desktop, partially select some added/removed lines via line-level checkboxes in the diff view (sets a `DiffSelection` keyed by `absoluteIndex`).
2. Before clicking "Commit", have an external process append/insert/remove lines earlier in the same file (simulating an autosave, formatter, or hook), shifting all subsequent line numbers without the Changes view reloading the diff.
3. Click "Commit" — `createCommit` → `stageFiles` → `applyPatchToIndex` fetches the new diff via `getWorkingDirectoryDiff` but reuses the old `DiffSelection`.
4. Inspect the resulting commit: it stages lines at the old numeric offsets, which now correspond to different (unintended) content in the file, silently committing unreviewed changes.

 *

export class DiffSelection {
  /**
   * Initialize a new selection instance where either all lines are selected by default
   * or not lines are selected by default.

    if (

      initialSelection !== DiffSelectionType.None

      return assertNever(
