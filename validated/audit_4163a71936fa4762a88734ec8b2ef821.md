## Title
Unhandled uint32/uint64 overflow in `compute_assert_height()` from attacker-controlled relative timelock values can crash mempool transaction processing - (File: `chia/full_node/mempool_manager.py`)

### Summary
`compute_assert_height()` adds an attacker-controlled relative height/seconds value taken directly from a submitted spend bundle's conditions to a coin's confirmed height/timestamp, then casts the sum back into a `uint32`/`uint64`. This is structurally the same bug class as the reported libp2p-gossipsub PRUNE `backoff` issue: an attacker-supplied numeric field is added to a base value (there: `Instant::now() + Duration::from_secs(backoff)`; here: `coin.confirmed_block_index + spend.height_relative` / `coin.timestamp + spend.seconds_relative`) without a guaranteed-safe bound check before the arithmetic/cast, creating a crash surface reachable by an unprivileged spend-bundle submitter.

### Finding Description
`compute_assert_height()` in [1](#0-0)  computes:

```
h = uint32(removal_coin_records[bytes32(spend.coin_id)].confirmed_block_index + spend.height_relative)
...
s = uint64(removal_coin_records[bytes32(spend.coin_id)].timestamp + spend.seconds_relative)
```

`spend.height_relative` and `spend.seconds_relative` originate from `ASSERT_HEIGHT_RELATIVE`/`ASSERT_SECONDS_RELATIVE` conditions inside the CLVM-executed spend, i.e. fully attacker-controlled up to the maximum encodable `uint32`/`uint64` values (test cases confirm values up to `0x100000000` and `0x10000000000000000` are exercised as boundary conditions in [2](#0-1) ). Because Python integers are arbitrary precision, the addition itself never overflows — but wrapping the result back into `uint32(...)`/`uint64(...)` will raise an exception if the sum exceeds the type's max value (e.g. `confirmed_block_index` close to `uint32` max plus a large `height_relative`, or `timestamp` close to `uint64` max plus a large `seconds_relative`).

Note that the Rust `check_time_locks()` function (imported from `chia_rs`) already recognizes this exact hazard: it takes an explicit `nowrap` parameter, only set `True` post-`HARD_FORK2_HEIGHT` [3](#0-2)  and in body validation [4](#0-3) , indicating the Rust side was hardened against wraparound/overflow for this scenario. However, `compute_assert_height()` is separate, pure-Python logic that performs the same relative-timelock arithmetic without any such overflow guard, and is not gated by `nowrap`.

### Impact Explanation
If `compute_assert_height()` is invoked on a spend bundle whose relative-timelock condition value, added to the coin's actual confirmed height/timestamp, exceeds the `uint32`/`uint64` range, the `uint32(...)`/`uint64(...)` cast raises an unhandled exception. If this exception is not caught by the caller in the mempool/pending-transaction-cache code path, it can abort processing of an otherwise-well-formed spend bundle admission, resulting in a spend-triggered transaction-processing halt in the affected code path — matching the "spend-triggered transaction-processing halt" acceptance criterion. This is remotely reachable by any unprivileged spend-bundle submitter without requiring node compromise, key leakage, or special privileges, consistent with the severity class of the reported PRUNE backoff bug (remote, unauthenticated DoS via crafted attacker-controlled numeric input causing arithmetic/cast failure).

### Likelihood Explanation
Medium-High: constructing a spend bundle with an `ASSERT_HEIGHT_RELATIVE`/`ASSERT_SECONDS_RELATIVE` (or `ASSERT_BEFORE_*_RELATIVE`) condition with a maximal relative value is straightforward and requires no special access — only a valid coin to spend and a crafted condition. The existing test suite already demonstrates that such extreme values (`0x100000000`, `0x10000000000000000`) are accepted as inputs into the relevant data structures [5](#0-4) , showing the boundary is exercised by design, but the specific downstream cast failure path in `compute_assert_height()` was not directly confirmed to be exception-handled by its caller within the scope of this review — this is the main remaining uncertainty.

### Recommendation
Harden `compute_assert_height()` to mirror the `nowrap`-safe semantics already used by `check_time_locks()`: perform the relative-value addition with explicit bounds checking (e.g. saturate at `uint32`/`uint64` max, or reject the spend with a defined `Err` code) instead of relying on an unguarded cast that can raise. Ensure any caller of `compute_assert_height()` wraps the call in exception handling that maps overflow to a graceful mempool-rejection error rather than letting the exception propagate and interrupt bundle processing.

### Proof of Concept
Not independently executed in this review (no runtime access). Conceptually:
1. Submit a spend bundle spending a coin whose `confirmed_block_index` is close to `uint32` max (or simulate one via mempool testing harness).
2. Include condition `(ASSERT_HEIGHT_RELATIVE <value>)` where `<value>` is chosen so that `confirmed_block_index + value > uint32::MAX` (or analogous `ASSERT_SECONDS_RELATIVE` with `timestamp + value > uint64::MAX`).
3. Trigger the code path that calls `compute_assert_height()` on this bundle's `SpendBundleConditions`.
4. Observe whether the `uint32(...)`/`uint64(...)` cast in [6](#0-5)  raises an unhandled exception that is not caught by the caller, verifying whether it disrupts mempool bundle admission processing.

**Uncertainty note**: I was unable to fully trace, within the given tool budget, whether the specific caller(s) of `compute_assert_height()` wrap this function in try/except that converts overflow exceptions into a normal `Err` rejection (which would neutralize the DoS) or let them propagate. This should be verified directly against `chia/full_node/mempool_manager.py` (the caller context around the two `compute_assert_height` references) before treating this as a confirmed, unmitigated vulnerability.

def compute_assert_height(
    removal_coin_records: dict[bytes32, CoinRecord],
    conds: SpendBundleConditions,
) -> TimelockConditions:
    """
    Computes the most restrictive height- and seconds assertion in the spend bundle.
    Relative heights and times are resolved using the confirmed heights and
    timestamps from the coin records.
    """

    ret = TimelockConditions()
    ret.assert_height = uint32(conds.height_absolute)
    ret.assert_seconds = uint64(conds.seconds_absolute)
    ret.assert_before_height = (
        uint32(conds.before_height_absolute) if conds.before_height_absolute is not None else None
    )
    ret.assert_before_seconds = (
        uint64(conds.before_seconds_absolute) if conds.before_seconds_absolute is not None else None
    )

    for spend in conds.spends:
        if spend.height_relative is not None:
            h = uint32(removal_coin_records[bytes32(spend.coin_id)].confirmed_block_index + spend.height_relative)
            ret.assert_height = max(ret.assert_height, h)

        if spend.seconds_relative is not None:
            s = uint64(removal_coin_records[bytes32(spend.coin_id)].timestamp + spend.seconds_relative)
            ret.assert_seconds = max(ret.assert_seconds, s)

        if spend.before_height_relative is not None:
            h = uint32(
                removal_coin_records[bytes32(spend.coin_id)].confirmed_block_index + spend.before_height_relative
            )
            if ret.assert_before_height is not None:
                ret.assert_before_height = min(ret.assert_before_height, h)
            else:
                ret.assert_before_height = h

        if spend.before_seconds_relative is not None:
            s = uint64(removal_coin_records[bytes32(spend.coin_id)].timestamp + spend.before_seconds_relative)
            if ret.assert_before_seconds is not None:
                ret.assert_before_seconds = min(ret.assert_before_seconds, s)
            else:
                ret.assert_before_seconds = s

    return ret
