### Title
Submodule `file://` protocol re-enablement bypasses Git's built-in local-file-disclosure hardening during checkout - (File: `app/src/lib/git/submodule.ts`)

### Summary
Upstream Git hardened `protocol.file.allow` to default to `user` (rather than `always`) specifically to stop a known class of attacks where a malicious repository's `.gitmodules` file points a submodule URL at a local `file://` path (e.g. a relative path that escapes into the user's home directory), causing `git submodule update --recursive` to silently copy sensitive local files into the tracked working tree. GitHub Desktop's `updateSubmodulesAfterOperation` helper contains a caller-controlled `allowFileProtocol` boolean that, when `true`, explicitly re-enables this disabled transport via `-c protocol.file.allow=always` for the `git submodule update --init --recursive` invocation run after every branch/commit checkout [1](#0-0) .

### Finding Description
`checkoutBranch` and `checkoutCommit` both accept an `allowFileProtocol` parameter (default `false`) and forward it unchanged into `updateSubmodulesAfterOperation` [2](#0-1) [3](#0-2) . Inside that helper, when the flag is `true`, the arguments passed to `git submodule update --init --recursive` are prefixed with `-c protocol.file.allow=always` [4](#0-3) . This unconditionally overrides Git's own safer default (`protocol.file.allow=user`) for the *entire* recursive submodule tree, meaning a submodule (or a nested submodule-of-a-submodule, since it's `--recursive`) whose URL in `.gitmodules` is `file://../../.ssh` or similar can have its contents copied straight into the repository's working directory the moment the flag is set to `true` for any checkout operation on an attacker-authored repository.

This exactly mirrors the reported bug class: Git upstream shipped a "mitigation" (defaulting `protocol.file.allow` away from `always`) to close a submodule-based local file disclosure primitive, and Desktop has a code path (`allowFileProtocol: true`) that deliberately re-opens that closed door for the recursive submodule-update step that runs after checkout — the same "one path fixed, an adjacent path reintroduces it" pattern as the RocketSwapRouter case in the seed report.

### Impact Explanation
If a checkout is triggered with `allowFileProtocol = true` against an attacker-controlled repository (cloned or opened by the victim), the attacker's `.gitmodules` can point at arbitrary local paths using `file://` URLs with relative traversal segments, and `git submodule update --init --recursive` will copy the referenced local directory's contents into a submodule path inside the tracked working tree. Once those files land inside the repository, ordinary Desktop workflows (stage → commit → push) will silently commit and push local secrets (SSH keys, cloud credentials, config files) to whatever remote the attacker's repository points at — this is a credential/token exfiltration primitive and "silent corruption of what the user commits/pushes," both explicitly in-scope impact categories.

### Likelihood Explanation
I confirmed the vulnerable mechanism exists exactly as designed (default-safe unless the flag is flipped) but I was not able to fully verify, within the available search budget, every caller in `app-store.ts`/`dispatcher.ts` that decides when `allowFileProtocol` is set to `true` versus left at its safe default of `false` [5](#0-4) . If that flag is only ever flipped to `true` behind an explicit, informed user "trust this repository's local submodules" prompt, the finding would not meet the unprivileged bar. If it is instead flipped automatically for common flows (e.g. any checkout of a branch that already has file:// submodules configured, without a distinct trust gate separate from the general "open repository" action), then this is directly and remotely triggerable by an attacker-authored public repository. This ambiguity should be resolved by tracing every call site of `checkoutBranch(..., allowFileProtocol)` / `checkoutCommit(..., allowFileProtocol)` in `app-store.ts` and the UI dialogs found in the earlier search (`stash-and-switch-branch-dialog.tsx`, `confirm-checkout-commit.tsx`, `overwrite-stashed-changes-dialog.tsx`, `branches-container.tsx`, `compare.tsx`).

### Recommendation
- Trace and document every call site that can set `allowFileProtocol = true` and confirm each is gated behind an explicit, per-repository, informed consent step equivalent in strength to Git's own dubious-ownership "Trust Repository" flow already implemented for `core.safe.directory` in `app/src/ui/missing-repository.tsx`.
- Prefer scoping `protocol.file.allow=always` to only the top-level submodule (non-recursive) rather than applying it globally to `--recursive`, so nested submodules-of-submodules from third-party sources can't inherit the relaxed policy.
- Consider never silently permitting `file://` submodules for repositories that were cloned from a remote (as opposed to genuinely local development scenarios), since this specific attack requires the submodule URL to reference paths on the victim's own machine.

### Proof of Concept
1. Attacker publishes a public repository containing a `.gitmodules` entry: `url = file://../../../../../.ssh` (relative traversal computed from the eventual clone location) and commits a submodule reference for that path.
2. Victim clones/opens the repository in GitHub Desktop and performs a checkout action that internally invokes `checkoutBranch`/`checkoutCommit` with `allowFileProtocol` resolved to `true` (exact trigger UI unconfirmed — see Likelihood).
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, which clones the victim's local `~/.ssh` directory into the submodule path inside the working tree [6](#0-5) .
4. Victim stages and commits changes (e.g. via `createCommit` in `app/src/lib/git/commit.ts`) without noticing the extra submodule content, and pushes to the attacker-controlled remote, exfiltrating the private keys.
