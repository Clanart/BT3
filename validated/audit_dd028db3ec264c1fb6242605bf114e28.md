Based on the code I was able to examine, the core claim is technically accurate, but the resulting impact needs a more precise characterization than the prompt implies.

### Title
Unauthenticated `InternalSendTx` on aggregator broadcasts attacker-chosen transactions - (`core/src/servers.rs`)

### Summary
When `config.client_verification == false` (the deployment mode documented for the aggregator), `create_grpc_server` wraps all aggregator services in `InterceptedService::new(service, Noop)`, and `Interceptors::Noop::call` unconditionally returns `Ok(req)` for every request, including `ClementineAggregator/InternalSendTx`. Any network peer that can reach the aggregator's TCP port can call `internal_send_tx` with an arbitrary `bitcoin::Transaction`, which is queued via `TxSender::insert_try_to_send` and processed by `TxSenderTaskInternal::run_once` for confirmation/fee-bumping.

### Finding Description
Broken binding: `CALLER_AUTHORITY(request) == HOLDER(aggregator_client_cert)`. In `create_grpc_server` (`core/src/servers.rs:106-139`), the interceptor is chosen purely from `config.client_verification`: `true` → `OnlyAggregatorAndSelf{...}`, `false` → `Noop`. `Interceptors::Noop::call` (`core/src/rpc/interceptors.rs:22-32`) returns `Ok(req)` for every request with no certificate check at all, so the binding collapses to true for the empty set of certificates — i.e., any caller. `create_aggregator_grpc_server` (`core/src/servers.rs:293-317`) only emits a `tracing::warn!` when `client_verification` is `true`; it applies no independent enforcement, and per `docs/usage.md:203`, "The aggregator does not enforce client certificates." [1](#0-0) [2](#0-1) [3](#0-2) 

`internal_send_tx` (`core/src/rpc/aggregator.rs:1269-1312`) takes the caller-supplied `bitcoin::Transaction` and `fee_type`, and forwards it directly to `self.tx_sender.insert_try_to_send(...)` with no signature/whitelist check of any kind. [4](#0-3) 

However, what happens after `insert_try_to_send` depends on `FeePayingType`:
- For `FeePayingType::CPFP` and `FeePayingType::RBF`, the underlying `send_cpfp_tx`/`send_rbf_tx` logic in `crates/clementine-tx-sender/src/cpfp.rs` and `rbf.rs` adds fee-payer UTXOs / uses `psbt_bump_fee`/wallet funding to bump the fee of the **original attacker-supplied transaction** — the original transaction's inputs/outputs are preserved (see `reorder_psbt_outputs`, which explicitly re-inserts the original tx's outputs unchanged, and `verify_new_inputs`, which only allows the wallet to add new inputs, not replace existing ones). [5](#0-4) 
- Critically, Bitcoin consensus rules still require the attacker's supplied transaction to carry valid signatures/witnesses for whatever inputs it spends. The aggregator's tx-sender wallet only signs/funds the *additional* fee-payer inputs it adds — it does not sign inputs the attacker did not already control/sign. I was not able to fully trace whether any code path (e.g. `send_no_funding_tx`, `FeePayingType::NoFunding`) would let the wallet fund and sign a completely attacker-authored transaction whose primary inputs belong to the wallet itself (which would allow wallet drain), because I ran out of budget to inspect `crates/clementine-tx-sender/src/lib.rs`'s `send_no_funding_tx` and the full `fund_raw_transaction`/`wallet_create_funded_psbt` flow used on first-send RBF (only partially reviewed at `rbf.rs:532-711`).

### Impact Explanation
What is definitely established: any unauthenticated party can insert an arbitrary transaction into the aggregator's tx-sender queue and have the aggregator's Bitcoin node **broadcast it and pay to bump its fee using node-controlled UTXOs**. This matches the rules' High-severity bucket "an unauthenticated state-changing or broadcasting call" for certain. It lets an attacker: (a) force the aggregator's automation node to spend real BTC (fee-payer/anchor UTXOs) fee-bumping garbage transactions, and (b) potentially interfere with the tx-sender's queue/DB state for legitimate transactions (e.g. by submitting conflicting/duplicate entries). Whether this reaches Critical ("BTC leaving a move-to-vault UTXO without a matching fronted withdrawal") depends on whether the transaction the attacker submits still needs a valid N-of-N/operator signature to actually move bridge funds — which it does, since Bitcoin script/consensus validation of the taproot spend still applies on-chain regardless of what the aggregator's RPC accepts. The attacker cannot forge that signature through this endpoint; they can only get the aggregator to *try* to broadcast/fee-bump transactions they hand it.

### Likelihood Explanation
Preconditions are exactly as stated: default/documented aggregator deployment with `client_verification=false`, aggregator's gRPC port reachable, and the `automation` feature compiled in (`internal_send_tx` returns `unimplemented` otherwise). This is trivially reachable by any network client with a plain TLS connection (no client cert needed since `ServerTlsConfig` has no `.client_ca_root()` in the `else` branch). [1](#0-0) 

### Recommendation
Do not rely on `Noop` for the aggregator's internal/state-changing RPCs. At minimum, `InternalSendTx` (and other `Internal*` methods) should require the entity's own client certificate check (reuse `is_internal`/`OnlyAggregatorAndSelf`-style logic) regardless of `client_verification`, or the aggregator's gRPC server should bind only to a private/loopback network interface, never a public one, and enforce mTLS unconditionally for automation endpoints.

### Proof of Concept
A `cargo test` demonstrating the unauthenticated broadcast would: spin up `create_aggregator_grpc_server` with `client_verification=false`, connect with a bare `tonic::transport::Channel` carrying no client identity, call `internal_send_tx` with a `FeePayingType::CPFP` transaction that has a valid presigned witness for a real UTXO (e.g. reuse a round tx as in `core/src/test/deposit_and_withdraw_e2e.rs:1797-1806`), and assert the call succeeds and the tx enters the mempool via `getrawmempool`. This proves the unauthenticated-broadcast (High) finding conclusively. I could not construct or confirm a PoC that reaches Critical impact (actual theft of a move-to-vault UTXO without a valid N-of-N signature) within the code paths reviewed — that would require a code path where the aggregator's own wallet signs a completely attacker-authored spend of a real bridge UTXO, which I did not find evidence of in `insert_try_to_send`/`internal_send_tx`.

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}

    /// PSBT.
    ///
    /// This is required for a transaction to be added to the wallet.
    pub fn verify_new_inputs(&self, psbt: &str, original_tx: &Transaction) -> bool {
        let Ok(psbt) = Psbt::from_str(psbt) else {
            tracing::error!("Failed to parse PSBT");
            return false;
        };

        psbt.inputs.len() > original_tx.input.len()
    }

    /// Reorders PSBT outputs so that the original transaction outputs appear first
    /// in the same order, followed by any newly added outputs (e.g., change outputs).
    ///
    /// This is important for watchtower challenge transactions where the OP_RETURN
    /// output is expected to remain at a specific index.
    pub fn reorder_psbt_outputs(&self, psbt: &mut Psbt, original_tx: &Transaction) -> Result<()> {
        if psbt.unsigned_tx.output.len() != psbt.outputs.len() {
            return Err(SendTxError::Other(eyre!(
                "PSBT outputs length mismatch: unsigned_tx outputs={} psbt outputs={}",
                psbt.unsigned_tx.output.len(),
                psbt.outputs.len()
            )));
        }

        let mut used = vec![false; psbt.unsigned_tx.output.len()];
        let mut new_outputs = Vec::with_capacity(psbt.unsigned_tx.output.len());
        let mut new_psbt_outputs = Vec::with_capacity(psbt.outputs.len());

        for original_out in &original_tx.output {
            let mut found_idx = None;
            for (idx, out) in psbt.unsigned_tx.output.iter().enumerate() {
                if !used[idx]
                    && out.value == original_out.value
                    && out.script_pubkey == original_out.script_pubkey
                {
                    found_idx = Some(idx);
                    break;
                }
            }

            let Some(idx) = found_idx else {
                return Err(SendTxError::Other(eyre!(
                    "Failed to find original output in PSBT"
                )));
            };

            used[idx] = true;
            new_outputs.push(psbt.unsigned_tx.output[idx].clone());
            new_psbt_outputs.push(psbt.outputs[idx].clone());
        }

        for (idx, out) in psbt.unsigned_tx.output.iter().enumerate() {
            if !used[idx] {
                new_outputs.push(out.clone());
                new_psbt_outputs.push(psbt.outputs[idx].clone());
            }
        }

        psbt.unsigned_tx.output = new_outputs;
        psbt.outputs = new_psbt_outputs;

        Ok(())
    }
