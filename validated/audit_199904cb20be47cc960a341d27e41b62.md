Confirmed: the "withdrawal_utxo" is a small dust UTXO owned and controlled entirely by the withdrawing party's own key (`generate_withdrawal_utxo`/`sign_withdrawal_output` in `core/src/test/common/setup_utils.rs:480-543`), and the signature the withdrawer supplies is `TapSighashType::SinglePlusAnyoneCanPay`, enforced in `core/src/rpc/parser/operator.rs:161-203` (`parse_withdrawal_sig_params`). SIGHASH_SINGLE|ANYONECANPAY only commits the single spent input plus the output at the *same index* — it does **not** commit to any other input or output, including the OP_RETURN output that carries the operator's `xonly_pk` in `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`, OP_RETURN is output index 2, unrelated to the committed index 0).

### Title
Payout OP_RETURN operator attribution is unauthenticated, allowing false "fronted-payout" credit via SIGHASH_SINGLE|ANYONECANPAY malleability - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The `Payout` transaction's OP_RETURN (which asserts "operator O fronted this withdrawal") is never covered by any signature or on-chain authorization; the only signed part of the transaction is the withdrawal input and its corresponding output (index 0), signed with `SinglePlusAnyoneCanPay`. Anyone possessing a valid withdrawal signature (the withdrawing user themself, who is by definition allowed to be the "attacker" per the threat model) can build their own payout transaction that satisfies the committed input/output, but freely append additional inputs (self-funded) and an OP_RETURN naming an arbitrary victim operator `O`, then broadcast it directly to Bitcoin — bypassing every operator's RPC entirely.

### Finding Description
The broken binding: `deposit_constant.operator_xonlypk == O` (and DB column `withdrawals.operator_xonly_pk == O`, set by `update_finalized_payouts`) is supposed to imply "O funded/broadcast this payout." In reality, the equality can be forced true by anyone who owns a valid `SinglePlusAnyoneCanPay` signature for the specific withdrawal UTXO, without O's participation.

Path:
1. `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds output[0] = user payout, output[1] = anchor, output[2] = OP_RETURN(move_txid or operator_xonly_pk). The only Schnorr signature check happens in `Operator::withdraw` (`core/src/operator.rs:614-637`) against `sighash = payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)`.
2. `parse_withdrawal_sig_params` (`core/src/rpc/parser/operator.rs:161-203`) enforces the sighash type must be `SinglePlusAnyoneCanPay`. Per BIP341/`taproot_key_spend_signature_hash` (implemented at `circuits-lib/src/bridge_circuit/mod.rs:731-844`, mirrored by bitcoin crate), `AnyoneCanPay` excludes `sha_prevouts`/`sha_amounts`/`sha_scriptpubkeys`/`sha_sequences` for other inputs, and `Single` excludes `sha_outputs` for any output except the one at the signed input's index. Consequently outputs[1] and outputs[2] (anchor, OP_RETURN) and any additional inputs are **not covered** by the signature.
3. `update_finalized_payouts` (`core/src/verifier.rs:2283-2352`) — run by every verifier/operator's Bitcoin syncer — scans any transaction that spends a registered `withdrawal_utxo` (tracked via `bitcoin_syncer_spent_utxos`, keyed purely by outpoint, `core/src/database/verifier.rs:170-196`), reads whichever OP_RETURN happens to be present, and stores that key as `operator_xonly_pk` for the withdrawal with **no signature or on-chain proof** that the named operator authored the tx.
4. `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) on operator `O`'s own node queries `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` — i.e., it trusts the DB column populated in step 3 — and if a payout is found bearing `O`'s key, it automatically calls `handle_finalized_payout` (`core/src/operator.rs:839+`), which allocates a kickoff connector and drives `O`'s automation to send a `Kickoff` transaction claiming reimbursement, even though `O` never built, signed, or broadcast that payout.
5. Downstream, `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) only checks that `operator_xonly_pk` (again, read from the forgeable OP_RETURN) matches `kickoff_data.operator_xonly_pk` and that the committed payout blockhash matches — both of which trivially hold for the attacker-crafted transaction, so the false kickoff is accepted as non-malicious.

None of the listed guards (`is_deposit_valid`, `is_profitable`, `SECP.verify_schnorr`, `is_kickoff_malicious`, `verify_storage_proofs`, `SPV::verify`) authenticate *who broadcast* the payout tx or *who is entitled to* the OP_RETURN credit — they only authenticate that the correct dust UTXO was spent to the correct user output, which SIGHASH_SINGLE|ANYONECANPAY still allows an attacker to satisfy while forging the rest of the transaction.

### Impact Explanation
An attacker (the withdrawer themself, or anyone who obtains this signature, e.g. from the aggregator's public `Withdraw`/`OptimisticPayout` broadcast) can name **any** currently-active operator `O` in the OP_RETURN of their own withdrawal's payout transaction, self-funding the extra input(s)/fee via ANYONECANPAY. This causes `O`'s own `PayoutCheckerTask` automation to believe `O` fronted the withdrawal and to automatically kick off the reimbursement flow for a payment `O` never made. If this results in `O` receiving `bridge_amount` in reimbursement from the round/collateral machinery, this is a direct value leak — BTC (the reimbursement) is credited to an operator that funded nothing, i.e., "an operator reimbursed for a payout it never funded" (Critical). Because the attack requires only broadcasting a transaction that spends a UTXO the attacker/withdrawer legitimately controls, it is repeatable across every withdrawal and every operator xonly_pk currently registered, with no operator collusion, no key compromise, and no privileged access.

### Likelihood Explanation
Preconditions: attacker needs (a) to be (or obtain the signature of) a legitimate withdrawer with a `SinglePlusAnyoneCanPay` signature over a registered `withdrawal_utxo`/output, and (b) to know a target operator's public `xonly_pk` (public information, advertised by every operator). No verifier/security-council/collateral access is needed. Cost is just Bitcoin fees for the forged payout transaction. This is straightforwardly reproducible in a regtest/test harness by constructing a payout tx that reuses an existing `SinglePlusAnyoneCanPay` signature but swaps the OP_RETURN xonly_pk for a different operator's key, and observing that `update_finalized_payouts`/`payout_checker` attribute it to that operator.

### Recommendation
Bind the OP_RETURN operator commitment to the signature. Concretely, either:
- Require the withdrawal signature to use `AllPlusAnyoneCanPay` (or plain `All`) instead of `SinglePlusAnyoneCanPay`, so all outputs (including the OP_RETURN) are covered by the sighash and cannot be altered post-signing while still allowing additional-input funding; or
- Have each operator co-sign (or otherwise cryptographically bind, e.g. via a covenant/second signature) their own OP_RETURN attribution, and have `update_finalized_payouts`/`is_kickoff_malicious` verify that binding instead of trusting raw OP_RETURN bytes; or
- At minimum, require `PayoutCheckerTask`/`handle_finalized_payout` to additionally verify that the payout transaction's funding inputs (beyond the withdrawal UTXO) are actually controlled/spent by `O`'s own wallet before auto-kicking off reimbursement.
