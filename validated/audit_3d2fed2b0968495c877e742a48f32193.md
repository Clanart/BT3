## Title
Unprivileged FIFO eviction of prepaid bandwidth subscriptions via cross-chain sponsorship — permanent loss of paid-for allowance - (File: `modules/pallets/bandwidth/src/lib.rs`, `evm/src/apps/BandwidthManager.sol`)

### Summary
`pallet-bandwidth`'s subscription ledger for `(app_chain, app)` is a FIFO list capped at 1024 entries; pushing past the cap silently evicts the oldest entry regardless of its remaining value [1](#0-0) . Because `purchase()` on `BandwidthManager.sol` is fully permissionless and lets any caller specify an arbitrary `chain`/`app` pair independent of `msg.sender` or the calling chain (the "sponsorship" feature), any attacker can cheaply spam the smallest tier against a victim's `(app_chain, app)` bucket to force-evict the victim's legitimately purchased, high-value subscriptions before they are consumed.

### Finding Description
`purchase()` takes `app` and `chain` as free-form calldata parameters with no relationship to `msg.sender`: [2](#0-1)  This is by design, documented as "Sponsorship" — a payer on one chain can credit an app on any other chain [3](#0-2) .

On the receiving side, `pallet-bandwidth` keys the subscription ledger `Allowance<T>` purely by `(app_chain, app)` taken from the purchase body, not by payer identity [4](#0-3) . `push_subscription` unconditionally evicts the oldest entry in the list once it reaches `MAX_SUBSCRIPTIONS = 1024`, with no minimum-remaining-bytes or minimum-remaining-duration protection: [5](#0-4) [6](#0-5) 

Since any account, on any chain that has a registered `BandwidthManager`, can call `purchase()` targeting the smallest configured tier and any `chain`/`app` combination, an attacker can drive 1024 cheap purchases against a specific victim `(app_chain, app)` pair. Each cheap purchase appends to the FIFO tail; once the list is full, the victim's own (potentially large, expensive, long-duration) subscriptions sitting at the head get evicted one by one, with `SubscriptionEvicted` only emitted as an audit trail — no economic guard prevents it [7](#0-6) .

This mirrors the LOAN_TERM bug class: a value calculated/enforced using shared mutable state (the FIFO list/cap) can be invalidated by activity unrelated to the original committer, causing loss of a position (here, prepaid bandwidth) the victim believed was safely purchased and locked in.

### Impact Explanation
This directly causes loss of funds: the victim paid fee-token for a bandwidth tier expecting `bytes`/`duration_secs` to be available to drain (documented as "immutable across its lifetime" [8](#0-7) ), but an unrelated unprivileged attacker can force early eviction, destroying that paid-for allowance before it is consumed. This falls under "stealing or loss of funds" and "logic attacks" in the bounty's impact gate, and requires no admin, governance, relayer, or prover — only a registered `BandwidthManager` contract and enough fee-token to buy the cheapest tier repeatedly.

### Likelihood Explanation
The attack is economically bounded by `cheapest_tier_price × number_of_evictions_needed`, which is attacker-controlled and can be made arbitrarily cheap if the pallet or manager ever configures a low-priced smallest tier, or if the victim's bucket is already near capacity from legitimate high-frequency top-ups. It does not require any privileged role, malicious relayer, or front-running — any address with a live `BandwidthManager` deployment and fee tokens can execute it end-to-end through the documented public `purchase()` flow.

### Recommendation
Do not let untrusted purchase traffic evict subscriptions purely by FIFO position. Options:
- Key eviction priority by remaining value (e.g., evict the entry with the least `remaining_bytes * time_left` rather than strictly oldest), or
- Segregate the FIFO cap per payer/source rather than a single shared 1024-slot list per `(app_chain, app)`, or
- Require a minimum idle/expired state before an entry becomes evictable, so unconsumed, unexpired, high-value subscriptions cannot be evicted by cheap spam.

### Proof of Concept
1. Attacker identifies victim `(app_chain = "EVM-8453", app = 0xVictimApp)` that has just purchased a large, long-duration Tier Four subscription via `BandwidthManager.purchase()` (documented flow, step 6 in the overview) [9](#0-8) .
2. Attacker (from any registered source chain, possibly a cheap L2) calls `purchase(app = 0xVictimApp, tier = TierOne, months = 1, chain = "EVM-8453")` 1024 times, paying only `TierOne` price each time (as low as $50 or whatever the cheapest configured tier is) [2](#0-1) .
3. Each relayed purchase triggers `push_subscription`, appending to the `(EVM-8453, 0xVictimApp)` FIFO list; once at cap, the oldest entries — including the victim's freshly purchased Tier Four subscription — are evicted and emit `SubscriptionEvicted` [10](#0-9) .
4. Victim's paid-for, unconsumed bandwidth allowance is permanently destroyed while the attacker's cheap junk subscriptions occupy the list, at a fraction of the cost of what was destroyed.

		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.

/// One purchase, immutable across its lifetime: `remaining_bytes`
/// drains via the gate, `expires_at` is fixed at purchase time and
/// never extends. Repurchases append a new row instead of stacking.
#[derive(
	Encode, Decode, DecodeWithMemTracking, TypeInfo, MaxEncodedLen, Clone, PartialEq, Eq, Debug,
)]
pub struct Subscription {
	/// SKU this subscription was bought against; for analytics/events
	/// only — the gate doesn't look at it during drain.
	pub tier: TierIndex,
	/// Bytes left to spend. Decrements as the gate drains; the entry
	/// is popped once this hits zero.
	pub remaining_bytes: BandwidthBytes,
	/// Unix seconds. Gate sweeps entries where `expires_at <= now`.
	pub expires_at: u64,
	/// Unix seconds at insertion — fixes FIFO order under same-block buys.
	pub purchased_at: u64,
}
