Based on my investigation, I confirmed the journal system (`journalEntry.revert`) in `x/evm/state/journal.go` has no entry type for reversing `DeleteAddressMapping` — there is no `addressMappingChange` journal entry, only `accountStatusChange`, `codeCacheChange`, balance/storage/transient-state journal entries, etc. `SelfDestruct` calls `s.k.DeleteAddressMapping` directly against the underlying KV store, outside the journal, while the balance debit and `AccountDeleted` marker are journaled and thus revertible.

### Title
EVM `SelfDestruct` deletes the Sei↔EVM address association outside the revert journal, permanently orphaning the association on a reverted call - ([File: x/evm/state/state.go])

### Summary
`DBImpl.SelfDestruct` (and the Giga equivalent in `giga/deps/xevm/state/state.go`) unconditionally calls `k.DeleteAddressMapping` to remove the bidirectional Sei↔EVM address mapping the instant `SELFDESTRUCT` executes, before the rest of destruction (balance debit, `AccountDeleted` marking, and eventual `Finalize()` cleanup) completes. Every other side effect of `SelfDestruct` is journaled and can be undone by `RevertToSnapshot`, but the address-mapping deletion is not, so it survives a revert of the enclosing call frame or transaction.

### Finding Description
`SelfDestruct` in `x/evm/state/state.go`:
```go
func (s *DBImpl) SelfDestruct(acc common.Address) uint256.Int {
	s.k.PrepareReplayedAddr(s.ctx, acc)
	if seiAddr, ok := s.k.GetSeiAddress(s.ctx, acc); ok {
		// remove the association
		s.k.DeleteAddressMapping(s.ctx, seiAddr, acc)
	}
	b := s.GetBalance(acc)
	s.SubBalance(acc, b, tracing.BalanceDecreaseSelfdestruct)
	s.MarkAccount(acc, AccountDeleted)
	return *b
}

`DeleteAddressMapping` writes directly to the module KV store: [2](#0-1) 

The journal (`journal.go`) defines revert handlers only for `accountStatusChange`, `codeCacheChange`, balance/storage/transient-state/access-list/refund/surplus changes — there is no entry type that restores a deleted address mapping. `accountStatusChange.revert` only restores the transient in-memory `AccountDeleted` marker, not the persisted KV-store mapping: [3](#0-2) 

This matches the bug class in the report exactly: a teardown step (clearing the address-flag/mapping) is performed and becomes externally visible before — and independent of — the rest of the teardown/commit completing or being rolled back. In the kernel bug, `IFF_OVS_DATAPATH` is cleared before unregistration finishes, letting `netdev_destroy` free the device early; here, the address association is deleted before the rest of `SelfDestruct`'s effects are confirmed (i.e., before the enclosing call is known not to revert), and unlike the balance/status changes it is never rolled back.

Reachability: `SelfDestruct` is driven by the `SELFDESTRUCT` opcode, reachable by any EVM contract call from a submitted `MsgEVMTransaction`. Since EIP-7702 (`SetCode`, Type 4) is supported per `x/evm/AGENTS.md`, an EOA that has an active Sei↔EVM association (from an `Associate` transaction) can delegate code to a contract that self-destructs, letting an ordinary transaction sender trigger `SelfDestruct` against their own associated address.

### Impact Explanation
If the outer call that triggered `SELFDESTRUCT` (or an ancestor call/transaction) subsequently reverts — e.g., due to a nested revert, an out-of-gas condition in a later sub-call, or an explicit `revert()` after the `SELFDESTRUCT` in the same call graph — the EVM/Cosmos state model is expected to fully roll back to the pre-call snapshot: balance, self-destruct marker, storage, and any other tracked effects are undone via the journal. But the address-mapping deletion, being unjournaled, remains committed. Consequences:
- The account permanently loses its Sei↔EVM association even though, from the perspective of all other observable EVM/Cosmos state, the self-destruct "never happened."
- Per `x/evm/AGENTS.md`, unassociated ("cast") addresses have restricted ability to receive funds and produce two separate balance views of the same logical account (`CanAddressReceive` in `x/evm/keeper/address.go` lines 81-86 depends on this mapping). Losing the association can freeze the account's ability to receive funds through its EVM identity or fork its balance into an unreachable cast-address view — a permanent, uncompensated loss/freezing of funds condition for the affected user, triggered entirely by their own reachable transaction.
- Because this is a state-consistency violation (partial revert), it can also desynchronize any downstream logic that assumes reverted calls have zero persistent side effects, which is a foundational invariant of EVM semantics that Sei's bridge is expected to preserve.

### Likelihood Explanation
Reasonably likely: `SELFDESTRUCT` remains a supported opcode, and reverting after invoking it is trivial to arrange in Solidity (calling a helper contract from within a try/catch-like sub-call pattern, or letting a subsequent operation in the same transaction/call run out of gas). Achieving this specifically against an *associated* account requires the self-destructing address to have a Sei↔EVM mapping, which is realistically achievable via EIP-7702 delegation from an already-associated EOA, or via a contract address that was set up with an explicit mapping.

### Recommendation
Journal the address-mapping deletion in `SelfDestruct` (both `x/evm/state/state.go` and `giga/deps/xevm/state/state.go`) the same way `MarkAccount`/`SubBalance` are journaled, e.g. add an `addressMappingChange` journal entry capturing the prior `(seiAddr, evmAddr)` pair and re-inserting it via `SetAddressMapping` on revert. Alternatively, defer the actual `DeleteAddressMapping` call to `Finalize()` (mirroring `clearAccountStateIfDestructed`/`handleResidualFundsInDestructedAccounts`, which already correctly wait until finalization to act on `AccountDeleted` status), so it only takes effect once the enclosing execution is confirmed non-reverted.

### Proof of Concept
1. Associate an EOA: sign an `Associate` transaction (or any transaction) so `seiAddr` and `evmAddr` are bound via `SetAddressMapping`.
2. Send a Type-4 (EIP-7702) transaction that delegates code to a helper contract for that EOA's address.
3. In the same top-level transaction, have the delegated code:
   a. Execute `SELFDESTRUCT` (invoking `DBImpl.SelfDestruct`, which immediately calls `DeleteAddressMapping`).
   b. Immediately after, perform an operation guaranteed to revert the *current call frame* at a level that does not roll back this call's *own* selfdestruct scope but does trigger a higher-level `RevertToSnapshot` covering balance/status changes made in this call — e.g., structure the call so the self-destructing call is itself wrapped by an outer contract that catches the sub-call's revert via a low-level `call` and swallows it (standard Solidity try/catch pattern), while ensuring the outer transaction still commits.
3. After the transaction settles, verify: `k.GetSeiAddress(ctx, evmAddr)` returns not-found (mapping is gone), balance is unchanged (self-destruct effects reverted), and `HasSelfDestructed`/`AccountDeleted` status is cleared (confirming the enclosing scope rolled back) — demonstrating the mapping deletion escaped the revert.
