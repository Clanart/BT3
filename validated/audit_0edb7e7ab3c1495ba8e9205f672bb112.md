## Finding

### Title
SimplexPaymaster prices ERC-20 gas payments from a single staleness-only-checked Chainlink feed, letting any UserOp sender underpay for gas and drain the paymaster's EntryPoint deposit - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` charges ERC-20 stablecoins for ERC-4337 gas by converting the real, up-to-the-block native gas cost into token units using two Chainlink price feeds (`nativeOracle` and each token's `tokenOracle`). The only validation on those feeds is a positivity check and a staleness bound (`maxOracleAge`, governance-configurable up to 7 days). There is no deviation check against a second source and no reconciliation with the actual native asset price at execution time. This mirrors the BLVaultLido bug class from the seed report: an on-chain oracle price, trusted at face value, is used to fix an exchange rate for a value transfer that is otherwise paid at the real market rate — any discrepancy is a free arbitrage against the protocol's funds.

### Finding Description
`_fetchDetails` (called by the inherited `PaymasterERC20._validatePaymasterUserOp`/prefund logic) returns `tokenPrice = _tokenPrice(cfg)`: [1](#0-0) 

`_tokenPrice` computes `(nativeUsd * 10^tokenDecimals * (10000+markupBps)) / (tokenUsd * 10000)`, where both `nativeUsd` and `tokenUsd` come straight from `_getOraclePrice`: [2](#0-1) 

The only guard is `answer <= 0` (reverts) and `block.timestamp - updatedAt > maxOracleAge` (reverts). There is no bound on how far the reported price can have drifted from the true market price within that staleness window, no secondary oracle cross-check, and no minimum-margin/circuit-breaker logic. `maxOracleAge` is governance-settable up to `MAX_ORACLE_AGE = 7 days`, and the code's own comment acknowledges heartbeats "up to 24h" are expected for some chains' stablecoin feeds: [3](#0-2) [4](#0-3) 

`PaymasterERC20` (the OZ base contract this inherits) then computes `erc20Cost = weiCost * tokenPrice / 1e18` and pulls exactly that amount from the UserOp sender, while the paymaster's EntryPoint deposit pays the real `weiCost` in native gas for execution. Submitting a UserOp through this paymaster is fully permissionless — no relayer, prover, or admin is involved; any account with a valid signature and (a permit or pre-approval) can call it via a bundler.

If the native asset's real market price rises (or the token's stablecoin peg dips) after the last Chainlink round but before the feed updates — a routine, non-malicious occurrence within any staleness window — `nativeUsd`/`tokenUsd` used by `_tokenPrice` is stale-low relative to the true cost of gas. An attacker can time UserOp submission into that window and pay `erc20Cost` computed off the stale price while consuming real, more-expensive native gas from the paymaster's EntryPoint deposit. Because the paymaster is permissionless and stateless per-tx (no per-block/price-move circuit breaker, no cap on volume per staleness window), this can be repeated with many UserOps to maximize extraction before the oracle round updates.

This is the same broken invariant as the seed report: an economically-meaningful exchange rate (mint amount / gas price) is derived from a single on-chain oracle that is allowed, by design, to diverge from the true asset price for a bounded window, and nothing in the settlement path re-checks or bounds that divergence before moving real value.

### Impact Explanation
Each exploited window results in `SimplexPaymaster`/its EntryPoint deposit paying full native-token gas cost while receiving under-priced ERC-20 stablecoins — a direct, repeatable loss of funds from the protocol's paymaster balance to an ordinary, unprivileged UserOp sender. This matches the bounty's "stealing or loss of funds" and "logic attacks" categories: no malicious relayer, prover, or governance actor is required, only a normal user timing transactions around routine oracle staleness/deviation, exactly as in the seed report.

### Likelihood Explanation
Likelihood is high in relative terms because:
- The attack requires no privileged access, no compromised infrastructure, and no front-running of another party's transaction — only observing a public price feed and a public gas market.
- `maxOracleAge` is explicitly designed to tolerate staleness windows as long as 24 hours (per the code's own comment) and up to 7 days at the governance ceiling, giving a wide and recurring attack surface across normal market volatility.
- The paymaster is intentionally permissionless (any UserOp with a valid signature/permit is accepted), so there is no gating mechanism that would otherwise prevent repeated exploitation within a single staleness window.

### Recommendation
- Add a maximum allowed deviation check between the oracle price and a secondary source (e.g., a second Chainlink feed, a Uniswap TWAP already available via `IDispatcher(host()).uniswapV2Router()`, or an off-chain-attested bound), rejecting `_fetchDetails`/pricing when the two disagree beyond a safe threshold.
- Tighten `maxOracleAge` per token/chain to the feed's actual heartbeat rather than allowing a governance ceiling of 7 days, and consider scaling the applied `markupBps` with elapsed staleness to price in the tail risk.
- Introduce a volume/exposure cap per staleness window (or per oracle round) so that even a favorable, briefly-stale price cannot be exploited across an unbounded number of UserOps before the feed updates.

### Proof of Concept
1. Governance registers a token with `maxOracleAge` at or near the practical heartbeat (e.g., 24h for a Base/Ethereum stablecoin feed, as anticipated by the contract's own comments) — this is normal, intended configuration, not a misconfiguration.
2. The native asset's true market price rises meaningfully (a routine market move) shortly after the last Chainlink round update for `nativeOracle`, but before the next round is published; `nativeOracle.latestRoundData()` still returns the older, lower price, and `block.timestamp - updatedAt <= maxOracleAge`, so `_getOraclePrice` accepts it without reverting (`evm/src/utils/SimplexPaymaster.sol#L428-L442`).
3. An unprivileged actor constructs a `PackedUserOperation` with `paymasterData` referencing the registered token (mode `0x01`, pre-approved) and submits it via any bundler to the `EntryPoint`.
4. `_fetchDetails` → `_tokenPrice` (`evm/src/utils/SimplexPaymaster.sol#L419-L424`) computes `tokenPrice` from the stale-low `nativeUsd`, so `PaymasterERC20` charges the sender `erc20Cost = weiCost * tokenPrice / 1e18` at the stale (discounted) rate.
5. The EntryPoint executes the UserOp; the paymaster's deposit is debited the real, higher-value native gas, while the sender only paid the stale-priced ERC-20 amount. Repeating step 3 for many UserOps within the remaining staleness window compounds the loss to the paymaster's EntryPoint deposit and ERC-20 balance, all funded from `swapAndDeposit`/treasury top-ups (`evm/src/utils/SimplexPaymaster.sol#L299-L330`).

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
