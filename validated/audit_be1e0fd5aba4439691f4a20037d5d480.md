### Title
Shared per-token `_partialFills` counter lets a solver underpay and permanently lock a leg's escrow in a multi-leg same-chain order - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` tracks fill progress per `(commitment, outputToken)` in `_partialFills`, but a single order can contain multiple legs (array indices) that request the *same* output token with different `totalRequired` amounts and different escrowed inputs. Because the "already filled" counter is keyed only by token (not by leg index), completing an earlier leg can make a later leg's `remaining` computation read as `0` even though the solver never paid anything for that specific leg. The result: the order gets marked fully filled, the solver pays less than the sum of the legs' requirements, and the victim's escrow for the underpaid leg becomes permanently stuck (the order can no longer be filled or cancelled once `_filled[commitment]` is set).

### Finding Description
In `_fillSameChain` [1](#0-0) , for each output index `i`:

```solidity
uint256 alreadyFilled = _partialFills[commitment][outputToken];
uint256 remaining = totalRequired - alreadyFilled;
if (remaining == 0 || solverAmount == 0) {
    if (solverAmount == 0 && remaining > 0) isFullyFilled = false;
    continue;
}
```

`alreadyFilled` is read from `_partialFills[commitment][outputToken]`, a mapping keyed purely by `outputToken` (a `bytes32`), while `totalRequired = order.output.assets[i].amount` is the per-index requirement. Nothing in `placeOrder` or `_fillSameChain` enforces that `outputToken` is unique across the `output.assets[]` array [2](#0-1) . If two legs in the same order specify the same output token, the counter accumulated from filling leg A "bleeds into" leg B's completion check.

When `remaining == 0`, the code silently `continue`s and treats the leg as satisfied — it never sets `isFullyFilled = false`, never requires `solverAmount` to cover leg B's `totalRequired`, and never writes an entry to `escrowedInputs[i]` (which stays the zero-valued default `TokenInfo`). The order is then marked fully filled via `_filled[commitment] = beneficiary` inside `_withdraw` [3](#0-2) , permanently finalizing it. Because leg B's escrow entry was never included with a nonzero amount in `escrowedInputs`, its balance in `_orders[commitment][token]` is never decremented or transferred out — it is silently orphaned. Since `_filled[commitment]` is now non-zero, no further `fillOrder` or `cancelOrder` call can retrieve it: `_cancelSameChain` requires the caller be `order.user` and, more importantly, downstream fill/cancel checks in `IntentGatewayV2` gate on `_filled[commitment] == 0`, which is no longer true.

### Impact Explanation
This is a direct loss-of-funds / logic-attack bug: a solver can construct a fill where they fully pay for one leg (obtaining that leg's escrow legitimately) while a second leg that happens to share the same output token address is treated as satisfied for free. The victim's escrowed input for the underpaid leg is neither transferred to the solver nor returned to the user — it is permanently locked in the contract, since the order is already marked as finalized (`_filled[commitment]` set), closing off both the fill and cancellation paths. The solver effectively captures the intended trade at less than the agreed total price while the user's remaining collateral is lost.

### Likelihood Explanation
Exploitation requires only:
1. An order with ≥2 legs (indices in `output.assets[]`/`inputs[]`) that reference the same output token address but different required amounts and different escrowed input tokens — a plausible pattern for "basket" orders (e.g., swap both USDC and DAI for ETH in one order).
2. A solver that sequences `options.outputs[]` so the first leg's payment exactly (or more) satisfies the shared counter relative to the second leg's `totalRequired`.

No relayer, prover, admin, or leaked-key assumptions are needed; any unprivileged solver calling the public `fillOrder` entrypoint can trigger this against any order with the described structure, and nothing in `placeOrder` rejects duplicate output tokens across legs to prevent the order from being constructed in the first place.

### Recommendation
- Key `_partialFills` (and the completion/remaining computation) by `(commitment, outputIndex)` instead of `(commitment, outputToken)`, or explicitly reject orders whose `output.assets[]` contains duplicate token entries at `placeOrder` time (mirroring the existing duplicate-input-token check in `IntentGatewayV2.placeOrder`).
- In `_fillSameChain`, ensure that when a leg is skipped because `remaining == 0`, this can only happen if that specific leg's own prior fills (not another leg's) fully satisfied `totalRequired`, and that `escrowedInputs[i]` is always populated whenever `isFullyFilled` is derived to include that leg — never leave escrow un-attributed on a path that also finalizes the order.

### Proof of Concept
1. User places an order with two legs sharing output token `ETH`:
   - Leg0: escrow 1000 USDC, `output.assets[0] = {token: ETH, amount: 1 ether}`.
   - Leg1: escrow 1000 DAI, `output.assets[1] = {token: ETH, amount: 1 ether}`.
2. Solver calls `fillOrder` with `outputs = [{ETH, 1 ether}, {ETH, 0}]`.
   - Index 0: `alreadyFilled = 0`, `remaining = 1 ether`, `fillAmount = 1 ether` → `_partialFills[commitment][ETH] = 1 ether`; `amountFilled == totalRequired` releases the full 1000 USDC escrow to the solver.
   - Index 1: `alreadyFilled = _partialFills[commitment][ETH] = 1 ether` (inherited from leg0), `totalRequired = 1 ether`, `remaining = 0` → the `if (remaining == 0 ...)` branch fires, the leg is skipped, `isFullyFilled` stays `true`, and `escrowedInputs[1]` stays the zero-value default.
3. `isFullyFilled == true` → `_withdraw` sets `_filled[commitment] = solver`, finalizing the order. The 1000 DAI escrow for leg1 is never transferred and its `_orders[commitment][DAI]` balance is never decremented.
4. The solver paid only 1 ether total for goods worth 2 ether (1000 USDC + 1000 DAI); the 1000 DAI is now permanently stuck since the order is finalized and neither `fillOrder` nor `cancelOrder` can act on it again.

Note: I was not able to execute this scenario in a live test environment (no filesystem/terminal access here); the trace above is derived directly from reading `_fillSameChain`, `_withdraw`, and the `_partialFills`/`_orders` mapping declarations in the cited files. A Devin session with repo access should write a Foundry test analogous to the existing `testPartialFill_RoundingDustReleasedToFinalSolver` tests in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` to confirm the DAI lock and short-payment on-chain.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
