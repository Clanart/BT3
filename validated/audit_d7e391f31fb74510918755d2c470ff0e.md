## Title
`CertsBuilder::handle_input` uses `return` instead of `continue` in the External-aggregate loop, discarding all remaining reward aggregates in the batch when one slot lookup fails - (File: core/src/block_creation_loop/rewards/certs_builder.rs)

### Summary
In `CertsBuilder::handle_input`, the `RewardInput::External(aggregates)` branch iterates over a `Vec<VoteAggregate>` and, for each aggregate, looks up `root_bank.get_rank_map(slot)` and each rank's stake entry via `rank_map.get_pubkey_stake_entry(rank)`. On failure of either lookup, the code executes a bare `return` rather than `continue`, which exits the entire `handle_input` call — abandoning processing of every subsequent aggregate in the same `Vec<VoteAggregate>` batch, not just the offending one. [1](#0-0) 

### Finding Description
The loop body is:
```rust
for aggregate in aggregates {
    let slot = aggregate.vote().slot();
    let Some(rank_map) = root_bank.get_rank_map(slot) else {
        warn!(...);
        return;
    };
    ...
    for rank in aggregate.ranks().iter_ones() {
        let Some(stake_entry) = rank_map.get_pubkey_stake_entry(rank) else {
            return;
        };
        ...
    }
    ...
}
``` [2](#0-1) 

Both `else` branches return from the whole `handle_input` function instead of skipping only the current `aggregate` and continuing the `for` loop. Since `RewardInput::External` carries a `Vec<VoteAggregate>` (a batch that can contain aggregates for multiple distinct slots), any single aggregate whose slot fails `get_rank_map` (e.g., slot too old/too new relative to `root_bank`'s available epoch stakes) or whose rank is out of range in the rank map causes every later aggregate in that same batch to be silently dropped without being added to `self.aggregates`.

I confirmed the aggregates that populate `RewardInput::External` are filtered by `rewards_wants_vote`/`vote_is_relevant_for_rewards` at sig-verification time using the `root_bank` slot known to the sig-verifier thread at that moment [3](#0-2) , and are forwarded via `send_votes_to_rewards` to a channel consumed later by `RewardCertsService`'s `Context::run`, which fetches its own possibly-different `root_bank` snapshot via `self.sharable_banks.root()` before calling `handle_input` [4](#0-3) . Because the root bank used for the `rewards_wants_vote` filter (at sig-verify time) and the root bank used inside `handle_input` (at consumption time) can differ due to normal root advancement and channel latency, it is plausible for a slot's rank-map lookup to fail at consumption time even though the aggregate passed the earlier relevance filter, without any single peer needing to send malformed input.

However, I was not able to fully verify within the available tool budget whether `Bank::get_rank_map` / `epoch_stakes_from_slot` can plausibly return `None` for a slot that legitimately passed `vote_is_relevant_for_rewards` — I could not retrieve the body of `Bank::get_rank_map`/`epoch_stakes_from_slot` in `runtime/src/bank.rs` before running out of search iterations. This is the key fact needed to determine whether an *unprivileged* external actor (as opposed to a colluding/malicious validator sending a batch containing a slot outside the reward window) can realistically trigger the `None` branch on a legitimate batch. The question's proof idea (unit test with a synthetic bad-slot aggregate followed by a good one) demonstrates the mechanical bug in isolation, but does not by itself establish that an unprivileged network peer can cause this condition in a real batch, since `Vec<VoteAggregate>` batches sent into this channel are constructed internally by the sig-verifier from its own filtering logic, not directly assembled by an attacker.

### Impact Explanation
If triggerable, the impact is a logic/completeness bug: aggregates for valid, distinct slots that arrive later in the same `RewardInput::External` batch are dropped from `self.aggregates`, meaning the leader may fail to build reward certificates for those slots on its window, potentially never producing a reward certificate for a legitimately voted slot. This does not halt consensus or cause fund loss/false execution — it only affects the reward-certificate side channel used by `CertsBuilder::build_certs` [5](#0-4) , and does not directly correspond to consensus halt, transaction/fund loss, false rooting/acceptance, or an RPC/QUIC/gossip/shred DoS as required by the bounty's "Valid Impact" criteria.

### Likelihood Explanation
Low/uncertain. The `for rank in aggregate.ranks().iter_ones()` inner loop operates on ranks that were already validated during BLS sig verification against a specific `rank_map` snapshot [6](#0-5) , so `get_pubkey_stake_entry(rank)` failing on the same-slot `rank_map` at consumption time would require the rank map itself to have changed, which is not established. The outer `get_rank_map(slot)` failure is more plausible given root advancement, but requires natural timing/race conditions rather than a single unprivileged, crafted external input — this pushes the finding toward the "reject if existing checks already stop it" / relies on internal timing rather than a directly attacker-controlled value.

### Recommendation
Replace both bare `return` statements at lines 96 and 102 with `continue` so that a lookup failure for one aggregate only skips that aggregate, preserving processing of the remainder of the batch, consistent with the invariant that every valid `External` aggregate in a batch should be processed.

### Proof of Concept
A unit test constructing a `Vec<VoteAggregate>` with a first entry whose slot returns `None` from `root_bank.get_rank_map` and a second, valid entry for a different slot, then calling `CertsBuilder::handle_input(&root_bank, RewardInput::External(vec![bad, good]))` and asserting `self.aggregates` does not contain an entry for the good slot, would demonstrate the mechanical `return`-vs-`continue` bug as described in the question. I was unable to construct and run this test myself given the tool constraints, and I was unable to confirm from the available code whether such a bad-slot condition can arise for an aggregate that legitimately passed the earlier `rewards_wants_vote` filter without attacker/validator collusion.     pub(super) fn handle_input(&mut self, root_bank: &Bank, input: RewardInput) {
        let root_slot = root_bank.slot();
        // drop state that is too old based on how the root slot has progressed
        // TODO: if this actually purges state, that probably indicates that the leader missed its
        // window.  We should have a metric for this.
        self.aggregates = self
            .aggregates
            .split_off(&root_slot.saturating_sub(NUM_SLOTS_FOR_REWARD));

        match input {
            RewardInput::External(aggregates) => {
                for aggregate in aggregates {
                    let slot = aggregate.vote().slot();
                    let Some(rank_map) = root_bank.get_rank_map(slot) else {
                        warn!(
                            "failed to look up rank_map for slot {slot} using bank for slot {}",
                            root_bank.slot()
                        );
                        return;
                    };
                    let max_validators = rank_map.len();
                    let mut vote_account_pubkeys = vec![];
                    for rank in aggregate.ranks().iter_ones() {
                        let Some(stake_entry) = rank_map.get_pubkey_stake_entry(rank) else {
                            return;
                        };
                        vote_account_pubkeys.push(stake_entry.vote_account_pubkey);
                    }

                    let vote = *aggregate.vote();
                    match self
                        .aggregates
                        .entry(aggregate.vote().slot())
                        .or_insert_with(|| Entry::new(max_validators))
                        .add_aggregate(aggregate, vote_account_pubkeys)
                    {
                        Ok(()) => (),
                        Err(e) => {
                            warn!("Adding aggregate with vote {vote:?} failed with {e}");
                        }
                    }
                }
            }

/// Returns true if a reward vote at the `vote_slot` is needed by this node for rewards.
pub fn vote_is_relevant_for_rewards(
    vote_slot: Slot,
    root_slot: Slot,
    cluster_info: &ClusterInfo,
    leader_schedule: &LeaderScheduleCache,
) -> bool {
    if vote_slot.saturating_add(NUM_SLOTS_FOR_REWARD) <= root_slot {
        return false;
    }
    let my_pubkey = cluster_info.id();
    let Some(leader) =
        leader_schedule.slot_leader_at(vote_slot.saturating_add(NUM_SLOTS_FOR_REWARD), None)
    else {
        return false;
    };
    if leader.id != my_pubkey {
        return false;
    }
    true
}
