### Title
Unvalidated `Participant` indices in PedPoP blame path panic on `HashMap` indexing, crashing the node on unauthenticated blame claims - (File: crypto/dkg/pedpop/src/lib.rs, crypto/dkg/pedpop/src/encryption.rs)

### Summary
The XXE advisory describes a parser accepting attacker-controlled structures without validation, enabling remote file reads and denial of service via malformed input. The closest analog in Serai's in-scope crates is PedPoP's blame protocol: `BlameMachine::blame` / `AdditionalBlameMachine::blame` accept `sender` and `recipient` `Participant` values supplied by an accusing party and feed them directly into `HashMap` indexing (`self.commitments[&sender]`, `self.enc_keys[&decryptor]`) with no range check. A `Participant` outside `1..=n` causes a panic, aborting the calling process — a remotely triggerable crash from public input, matching the "improperly formatted input crashes the server" impact of the XXE report.

### Finding Description
`blame_internal` in `crypto/dkg/pedpop/src/lib.rs` resolves the accused sender's commitments via `self.commitments[&sender]` (line 599) and, inside `Decryption::decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs`, line 388), resolves `self.enc_keys[&decryptor]`. Both `commitments` and `enc_keys` are populated only for `Participant` values `1..=n` (via `all_participant_indexes()` in `verify_r1`/`calculate_share`, or `1 ..= n` in `AdditionalBlameMachine::new` at line 656). Neither `blame` entry point validates that `sender`/`recipient` lie within that range:

```rust
// crypto/dkg/pedpop/src/lib.rs
pub fn blame(
  &self,
  sender: Participant,
  recipient: Participant,
  msg: EncryptedMessage<C, SecretShare<C::F>>,
  proof: Option<EncryptionKeyProof<C>>,
) -> Participant {
  self.0.blame_internal(sender, recipient, msg, proof)
}
```

`blame_internal` then does `&self.commitments[&sender]` — an out-of-range sender panics immediately. Even for a valid sender, `decrypt_with_proof` does `self.enc_keys[&decryptor]` — an out-of-range recipient panics after the PoP check.

### Impact Explanation
`Participant` is a `u16` newtype constructible via `Participant::new(i)` for any `i != 0`, so an accuser can supply e.g. `Participant(n + 1)` or `u16::MAX`. The blame API is explicitly designed to evaluate accusations about *other* parties' messages, so these indices are attacker-influenced inputs in any deployment that relays blame claims (e.g., a coordinator or validator collecting blame evidence). An `index` panic on the `HashMap` lookups crashes the host process — in Rust, an unwinding panic in a signing/blame-handling thread takes down the caller unless explicitly caught, denying service to the DKG/key-management node. This mirrors the XXE report's availability impact (server crash via malformed input) more than its file-read impact; no direct secret leakage results, though a crash mid-signing can abort threshold operations at attacker-chosen times.

### Likelihood Explanation
High reachability where blame processing is exposed: `AdditionalBlameMachine::new` exists precisely so that *non-participants* can evaluate blame, and its docs state commitment messages must be authenticated but impose no constraint on the `sender`/`recipient` arguments to `blame`. Any integrator that forwards user-submitted accusations without first checking `sender <= n && recipient <= n` (nothing in the API forces this, and the function returns `Participant` rather than `Result`) is one crafted accusation away from a panic. The fix requires no cryptographic exploit — only an out-of-range index.

### Recommendation
Validate `sender` and `recipient` against the registered key sets at the top of `blame_internal` (e.g., `if !self.commitments.contains_key(&sender) || !self.encryption.enc_keys.contains_key(&recipient) { return <accuser-or-error> }`), or change the API to take `Result`. Since `blame` currently returns `Participant` unconditionally, the minimal change is an early return identifying the accuser as faulty, or adding a `Result<Participant, PedPoPError>` signature.
