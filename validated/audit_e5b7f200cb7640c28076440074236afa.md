## Title
Division-by-zero panic in migration-epoch stake reward calculation - (File: `runtime/src/inflation_rewards/mod.rs`)

## Summary
`calculate_stake_rewards` in the Alpenglow `MigrationEpoch` branch uses `checked_div(point_value.points).unwrap()` on the tower-points term. The zero-guard that precedes it only rejects the case where **both** `tower_points == 0 && ag_points == 0`. It does not reject the case where `tower_points == 0`, `ag_points != 0`, and `point_value.points == 0`, which lets a `None` result from `checked_div` reach `.unwrap()` and panic.

## Finding Description
In `calculate_stake_rewards` (`runtime/src/inflation_rewards/mod.rs`), the `MigrationEpoch` arm is: [1](#0-0) 

```
AlpenglowEpochType::MigrationEpoch { num_tower_slots, num_ag_slots, .. } => {
    if tower_points == 0 && ag_points == 0 {
        return skip_reward(SkippedReason::ZeroPoints);
    }
    if ag_points == 0 && point_value.points == 0 {
        return skip_reward(SkippedReason::ZeroPointValue);
    }
    let total_slots = (num_tower_slots + num_ag_slots) as u128;
    let tower_points = tower_points
        .checked_mul(u128::from(point_value.rewards))
        .expect("Rewards intermediate calculation should fit within u128")
        .checked_div(point_value.points)
        .unwrap()
        ...
```

`checked_div` on `u128` returns `None` whenever the divisor is `0`, independent of the value of the numerator (i.e. `0u128.checked_div(0)` is also `None`). The two preceding guards only cover:
1. `tower_points == 0 && ag_points == 0` (both zero — this branch returns early).
2. `ag_points == 0 && point_value.points == 0` (returns early only when `ag_points` is also zero).

Neither guard covers the combination `tower_points == 0`, `ag_points != 0`, `point_value.points == 0`. In that combination execution falls through to `tower_points.checked_mul(...).checked_div(point_value.points).unwrap()`, where `point_value.points == 0` causes `checked_div` to return `None`, and `.unwrap()` panics.

`point_value.points` is the aggregate tower-point total for the epoch, computed in `calculate_reward_points_partitioned` [2](#0-1)  by summing `calculate_points_for_tower` across all stake delegations, and it is entirely plausible for the tower-points sum for a given migrating stake account to be `0` (e.g., activated too recently, never observed the tower vote credits) while its `ag_points` for the same epoch are non-zero (earned purely through the Alpenglow credit-based path). This is directly analogous to the reported StakingPool.sol bug: a per-period/per-account denominator (`total_points`/`periodTotalSupply`) becomes zero for a subset of accounts due to their specific stake/credit history, and the code fails to check the denominator before dividing.

## Impact Explanation
This code runs inside `Bank` reward-distribution logic during the Alpenglow migration epoch, which is part of core consensus/bank execution rather than an isolated RPC path. A panic here (an `unwrap()` on `None`) would abort the validator process/thread computing/redeeming rewards for that bank, which can cause validators to crash or diverge depending on how the panic is handled at the call site, undermining consensus liveness for any validator processing the migration epoch's rewards for the affected stake accounts.

## Likelihood Explanation
This path is only exercised once, during the one-time Alpenglow migration epoch, and only for stake accounts whose tower points are exactly `0` while `ag_points` is non-zero and the aggregate `point_value.points` for the epoch is `0`. This is a narrow, specific window of the migration transition and I could not fully verify from local code alone whether `point_value.points == 0` while some stake account's `ag_points != 0` is actually reachable in practice, since `calculate_reward_points_partitioned` only returns a `Some(PointValue)` when the aggregate tower points sum is `> 0` for the Tower/MigrationEpoch types [3](#0-2) . I was unable to trace, within the remaining budget, whether callers ever construct a `MigrationEpoch` `point_value.points == 0` (e.g., via `recalculate_stake_rewards`, which reads `point_value` directly from the on-chain `EpochRewards` sysvar rather than recomputing it) [4](#0-3) , which would make this reachable without the `>0` guard applying at all.

## Recommendation
Guard the `checked_div` explicitly for `point_value.points == 0` regardless of `ag_points`, e.g. treat the tower contribution as `0` when `point_value.points == 0` (matching the semantics already used for the `Tower` branch, which checks `point_value.points == 0` unconditionally before dividing) [5](#0-4) , instead of only checking it in conjunction with `ag_points == 0`.

## Proof of Concept
Not independently confirmed end-to-end due to inability to trace all callers of `calculate_stake_rewards` for the `MigrationEpoch` arm with a recalculated/sysvar-sourced `point_value` within the remaining tool budget. The concrete unguarded code path is: [1](#0-0) 

Calling `calculate_stake_rewards` with `ag_epoch_type = AlpenglowEpochType::MigrationEpoch{..}`, `tower_points = 0`, `ag_points != 0`, and `point_value.points = 0` reaches `checked_div(0).unwrap()` and panics — this can be verified directly with a unit test constructing those inputs.

Given the residual uncertainty about reachability of `point_value.points == 0` alongside non-zero `ag_points` for the affected account (I could not fully confirm this end-to-end from local code within the remaining exploration budget), I flag this as a plausible but not fully confirmed analog rather than a certain vulnerability.

    /// Returns reward lamports and points for the epoch or none if points == 0.
    fn calculate_reward_points_partitioned<'a>(
        &self,
        stake_history: &StakeHistory,
        stake_delegations: &Vec<(&'a Pubkey, &'a StakeAccount<Delegation>)>,
        cached_vote_accounts: &CachedVoteAccounts<'_>,
        epoch_inflation_rewards: u64,
        ag_epoch_type: &AlpenglowEpochType,
        thread_pool: &ThreadPool,
        metrics: &RewardsMetrics,
    ) -> Option<PointValue> {
        let CachedVoteAccounts {
            distribution_epoch_vote_accounts,
            ..
        } = cached_vote_accounts;

        let solana_vote_program: Pubkey = solana_vote_program::id();
        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        match ag_epoch_type {
            AlpenglowEpochType::Alpenglow { .. } => {
                // In alpenglow, we do not need to compute `PointValue::points` as the final
                // rewards are simply the total credits stored in the vote account.  We just need
                // to return a `Some` value with valid rewards.
                return Some(PointValue {
                    rewards: epoch_inflation_rewards,
                    points: 0,
                });
            }
            AlpenglowEpochType::Tower => {
                // For tower we need to compute the valid `PointValue::points`.
            }
            AlpenglowEpochType::MigrationEpoch { .. } => {
                // For the migrating epoch, we need to compute the tower portion of `PointValue::points`.
            }
        }

        let use_fixed_point_stake_math = self.use_fixed_point_stake_math();
        let (points, measure_us) = measure_us!(thread_pool.install(|| {
            stake_delegations
                .par_iter()
                .map(|(_stake_pubkey, stake_account)| {
                    let vote_pubkey = stake_account.delegation().voter_pubkey;

                    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey)
                    else {
                        return 0;
                    };
                    if vote_account.owner() != &solana_vote_program {
                        return 0;
                    }

                    calculate_points_for_tower(
                        stake_account.stake_state(),
                        DelegatedVoteState::from(vote_account.vote_state_view()),
                        stake_history,
                        new_warmup_cooldown_rate_epoch,
                        use_fixed_point_stake_math,
                    )
                    .unwrap_or(0)
                })
                .sum::<u128>()
        }));
        metrics.calculate_points_us.fetch_add(measure_us, Relaxed);

        (points > 0).then_some(PointValue {
            rewards: epoch_inflation_rewards,
            points,
        })
    }
