### Title
Missing format/bounds validation on the `kip71.gastarget` governance parameter allows a governance vote of `GasTarget = 0` to cause a division-by-zero panic in `NextMagmaBlockBaseFee`, halting all nodes - (File: `kaiax/gov/param.go`, `kaiax/gov/headergov/impl/header.go`, `params/kip71_config.go`)

### Summary
This is a direct analog of the reported bug class: privileged "admin-like" setter functions (`_updatePercentFee`, `_updateBaseFee`) that accept attacker/operator-controlled numeric inputs without range validation, leading to unintended contract state. In Kaia, the equivalent privileged setters are the governance-vote handlers for KIP-71 dynamic base-fee parameters. The `Kip71GasTarget` parameter uses a `noopFormatChecker` that accepts *any* `uint64` value, including `0`, and no additional consistency check is performed for it in `checkConsistency`. A `GasTarget` of `0` is then propagated into `KIP71Config.NextMagmaBlockBaseFee`, which performs `big.Int` division using `gasTarget` as the divisor without a zero-guard (unlike `BaseFeeDenominator`, which does have such a fallback).

### Finding Description
`Params[Kip71GasTarget]` is defined with `FormatChecker: noopFormatChecker`, which always returns `true`, i.e. it performs no validation at all: [1](#0-0) 

Contrast this with `RewardKip82Ratio`, which does implement a real format checker that validates the value sums to 100 — showing that meaningful validation is expected and possible for governance parameters, but was omitted for `Kip71GasTarget`.

The header-governance consistency checker (`checkConsistency`) explicitly special-cases `Kip71LowerBoundBaseFee` and `Kip71UpperBoundBaseFee` (cross-checking them against each other), but `Kip71GasTarget` falls into the default "no more checks here" bucket that simply returns `nil`: [2](#0-1) 

Once a vote sets `kip71.gastarget = 0` and it becomes part of `ParamSet` for a subsequent epoch (via `ParamSet.Set`/`SetFromMap`, which only performs type assertions, no range checks) it is converted into `KIP71Config` via `ToKip71Config()`: [3](#0-2) 

`NextMagmaBlockBaseFee` then uses `gasTarget` directly as a division operand with no zero-guard, unlike `BaseFeeDenominator` which is explicitly protected against zero: [4](#0-3) 

If `gasTarget == 0` and the parent block used any gas (`parentGasUsed > 0`, which is true for virtually every real block), execution takes the `parentGasUsed > gasTarget` branch and calls `x.Div(x, new(big.Int).SetUint64(gasTarget))` with a zero divisor. Go's `math/big` `Int.Div` panics on division by zero. This function is invoked from block validation (`VerifyMagmaHeader` in `blockchain/block_validator.go`), the tx pool, the worker, and the gas price oracle — i.e., by every full node processing every block once the parameter takes effect, not just the block proposer.

### Impact Explanation
A single governing-node vote (in the standard "single" governance mode used on Kaia mainnet) setting `kip71.gastarget` to `0` becomes canonical governance data for the following epoch with no rejection. From that epoch onward, essentially every block with nonzero gas usage will cause `NextMagmaBlockBaseFee` to panic wherever it's called: block validation, transaction pool base-fee logic, block assembly (`work/worker.go`), and the gas price oracle. This affects all nodes uniformly (not an isolated node crash), effectively halting block production/validation network-wide — a chain-halt / total availability failure, which is a severe, concrete impact analogous to (and arguably worse than) the "unintended behavior" flagged in the original report.

### Likelihood Explanation
This requires control of the governing node's voting key (or, post-Kore, contract governance access to `kip71.gastarget`), which is a privileged actor — structurally identical to the privilege level of the original report's contract owner/admin calling `_updatePercentFee`/`_updateBaseFee`/`_fundPool`. Given that the same class of validation exists for the sibling parameters `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` (cross-checked) but was evidently forgotten for `Kip71GasTarget`, this looks like an oversight rather than a deliberate design decision, making it a realistic gap.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally `Kip71MaxBlockGasUsedForBaseFee`) in `kaiax/gov/param.go` that rejects `0`, mirroring the safety fallback already present for `BaseFeeDenominator`. Additionally, add a defensive zero-check inside `KIP71Config.NextMagmaBlockBaseFee` in `params/kip71_config.go` (e.g., fallback to a safe default gasTarget, similar to the existing `BaseFeeDenominator == 0` fallback) so that a bad governance value cannot cause a network-wide panic even if the format-checker layer is bypassed.

### Proof of Concept
1. Governing node submits a header-governance vote: `NewVoteData(governingNode, "kip71.gastarget", uint64(0))`.
2. `VerifyVote`/`checkConsistency` accept it because `Kip71GasTarget` uses `noopFormatChecker` and has no dedicated consistency case (falls into the "no more checks" default branch) — see `kaiax/gov/headergov/impl/header.go` lines 214-220.
3. At the next epoch boundary, `GetParamSet` merges this into the active `ParamSet`, so `ParamSet.GasTarget == 0`.
4. Any subsequent block with `GasUsed > 0` triggers, via `ParamSet.ToKip71Config().NextMagmaBlockBaseFee(...)`, the branch `parentGasUsed > gasTarget` (since `0 > 0` is false but any positive `parentGasUsed` is `> 0`), executing `x.Div(x, new(big.Int).SetUint64(0))`, which panics in Go's `math/big` package.
5. Because `NextMagmaBlockBaseFee`/`VerifyMagmaHeader` is invoked by block validators, the tx pool, and block builders on every node, the panic occurs network-wide, halting the chain.
