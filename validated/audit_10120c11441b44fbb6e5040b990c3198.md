Reducing the external report to its core primitive: a single authorization credential (there, the `GOVERNANCE` role; here, a relayer's off-chain signature) is accepted by more than one privileged code path without being scoped to the specific action it was meant to authorize, letting the credential be *replayed* into a context its issuer never approved. I found a concrete local analog of that broken invariant in `pallet-ismp-relayer`'s two independent signed-authorization flows, which share both a nonce namespace and an identical message-hashing scheme.

### Title
Relayer withdrawal and fee-redirect signatures share an identical message hash, allowing cross-context replay that forces an unauthorized full-balance withdrawal - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`pallet-ismp-relayer` exposes two unsigned, publicly-callable extrinsics that each accept a relayer-produced signature over a `(nonce, state_machine, beneficiary)` tuple: `withdraw_fees` (in `withdrawal.rs`) and the beneficiary-redirect path inside `accumulate_fees` (in `accumulate.rs`). Both signed messages are built with the exact same encoding and share the exact same `Nonce` storage map keyed by `(address, state_machine)`. A signature a relayer creates for one purpose is therefore byte-for-byte valid for the other, letting anyone who observes it on-chain replay it into the sibling extrinsic to trigger an unintended, unauthorized full-balance withdrawal.

Consequence: a relayer who signs a small beneficiary-redirect authorization for use inside `accumulate_fees` (visible on-chain once submitted, since `accumulate_fees` is `ensure_none` and its `WithdrawalProof.beneficiary_details` carries the raw signature) exposes a signature that is also valid input for `withdraw_fees`: [6](#0-5) [7](#0-6) 

Unlike the beneficiary-redirect path — which only pays out the batch's `total_fee` — `withdraw_fees` pays out the relayer's *entire* accumulated balance for that `(address, chain)`: [8](#0-7) 

An unprivileged third party (not the relayer, not requiring any admin/governance/prover compromise) can extract a valid `(nonce, chain, beneficiary)` signature from a submitted `accumulate_fees` transaction and immediately front-run/resubmit it as `withdraw_fees` with the same `beneficiary`, forcing an unauthorized, premature drain of the relayer's full unwithdrawn fee balance and burning the nonce the relayer intended to use for their own next signed action (denial of that pending authorization).

### Impact Explanation
This breaks the "one-time receipt handling" and "bind... commitment uniqueness" invariant required for request/response/fee flows: a signature scoped by its issuer to authorize redirecting a *specific batch's* fee is silently usable to trigger an unrelated extrinsic that moves the *entire* balance. This is an unauthorized-execution / transaction-manipulation bug reachable by any on-chain observer without needing to compromise a relayer, prover, or governance account — it only requires reading a public extrinsic and resubmitting a different one.

### Likelihood Explanation
Medium: it requires a relayer to actually use the beneficiary-redirect feature (`beneficiary_details` in `WithdrawalProof`) while it still has an outstanding accumulated balance greater than the batch amount, and for an attacker to be watching the chain/mempool for such signed payloads (a passive, permissionless monitoring task, well within an unprivileged attacker's capability).

### Recommendation
Add call-specific domain separation to both signed payloads, e.g. prefix each hash with a distinct static tag (`b"ismp-relayer:withdraw"` vs `b"ismp-relayer:redirect"`) before hashing `(nonce, chain, beneficiary)`, or otherwise ensure the two message constructors can never collide. Additionally consider using disjoint nonce namespaces per action type so a signature consumed in one flow cannot be replayed against the other even if the hash collision is fixed incompletely.

### Proof of Concept
1. Relayer A has `Fees::<T>::get(ChainC, A) = 10_000` DAI-equivalent accumulated from prior deliveries, not yet withdrawn.
2. Relayer A delivers a new small request worth `5` and wants to redirect just that fee to beneficiary `X`. It signs `beneficiary_message(nonce=N, ChainC, X)` and submits `accumulate_fees` with `beneficiary_details = Some((X, sig))`; this transaction, and thus `sig`, is now publicly visible in the block/mempool.
3. Attacker (no privileges) extracts `sig` and `N` from the submitted transaction and immediately calls `withdraw_fees` with `WithdrawalInputData { signature: Signature::Sr25519 { public_key: A, signature: sig }, dest_chain: ChainC, beneficiary: Some(X) }` before Relayer A's own `accumulate_fees` is finalized.
4. Because `message(N, ChainC, Some(X))` hashes identically to `beneficiary_message(N, ChainC, X)`, `signature.verify(&msg, None)` in `withdrawal.rs` succeeds against public key `A`.
5. `withdraw_fees` pays out `Fees::<T>::get(ChainC, A) = 10_000` (the full balance, not the intended `5`) to `X`, zeroes the balance, and increments the nonce — consuming Relayer A's intended nonce/signature before their own `accumulate_fees` call lands, forcing an unplanned full withdrawal and invalidating the in-flight accumulate transaction's expected post-state. 	pub fn verify(
		&self,
		msg: &[u8; 32],
		public_key_op: Option<Vec<u8>>,
	) -> Result<Vec<u8>, anyhow::Error> {
		match self {
			Signature::Evm { signature, .. } => {
				if signature.len() != 65 {
					Err(anyhow!("Invalid Signature"))?
				}

				let mut sig = [0u8; 65];
				sig.copy_from_slice(&signature);
				let pub_key = sp_io::crypto::secp256k1_ecdsa_recover(&sig, msg)
					.map_err(|_| anyhow!("Signature Verification failed"))?;
				let signer = sp_io::hashing::keccak_256(&pub_key[..])[12..].to_vec();
				Ok(signer)
			},
			Signature::Sr25519 { signature, public_key } => {
				Self::verify_sr25519(signature, public_key, msg, &public_key_op)?;
				Ok(public_key_op.unwrap_or(public_key.clone()))
			},
			Signature::Ed25519 { signature, public_key, .. } => {
				let signature =
					signature.as_slice().try_into().map_err(|_| anyhow!("Invalid Signature"))?;
				let pub_key = public_key_op
					.clone()
					.unwrap_or(public_key.clone())
					.as_slice()
					.try_into()
					.map_err(|_| anyhow!("Invalid Public Key"))?;
				if !sp_io::crypto::ed25519_verify(&signature, msg, &pub_key) {
					Err(anyhow!("Signature Verification failed"))?
				}
				Ok(public_key_op.unwrap_or(public_key.clone()))
			},
		}
	}
