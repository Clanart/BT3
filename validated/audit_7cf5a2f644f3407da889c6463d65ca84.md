### Title
`Any.type_url` written unescaped into JSON output enables JSON/script injection - (File: `php/src/Google/Protobuf/Internal/Message.php`)

### Summary
The pure-PHP JSON serializer's handling of `google.protobuf.Any` writes the `type_url` field's raw bytes directly into the JSON string without any escaping, unlike every other string-valued field in the same codebase, which is passed through `json_encode()`. Since `type_url` is a normal protobuf `string` field populated by parsing untrusted binary input, an attacker-controlled value containing `"`, `\`, or control characters breaks out of the JSON string context, producing invalid or attacker-influenced JSON — a direct structural analog to the KaTeX `\htmlData` flaw, where an attacker-controlled token was emitted into generated output without validating/escaping characters that are syntactically significant in the output format.

### Finding Description
In `Message::serializeToJsonStream()`, the `Any` branch does: [1](#0-0) 

```
$output->writeRaw("\"@type\":", 8);
$output->writeRaw("\"", 1);
$output->writeRaw($this->getTypeUrl(), strlen($this->getTypeUrl()));
$output->writeRaw("\"", 1);
```

`getTypeUrl()` returns the raw `type_url` string field value as parsed from binary input (a `Message::string` scalar), with no escaping applied before it is wrapped in JSON quotes.

Compare this to the general STRING field serialization path used for every other string field, which correctly escapes via `json_encode`: [2](#0-1) 

The other language/runtime implementations of the same `Any`→JSON encoder consistently escape the type URL:
- upb (used by PHP/Ruby/Python C extensions) calls `jsonenc_string()`, which invokes `jsonenc_put_escaped_char` on every byte: [3](#0-2) 
- C++'s internal JSON writer wraps the type URL with `MakeQuoted`, which performs the same escaping as any other JSON string: [4](#0-3) 
- C#'s formatter uses `WriteString`, the same escaping helper used for all JSON string values: [5](#0-4) 

Only the pure-PHP path (`php/src/Google/Protobuf/Internal/Message.php`) bypasses escaping for this one field, breaking the invariant enforced everywhere else in the codebase: *all string-typed content emitted into JSON output must be escaped for JSON string-context safety* (this same invariant is explicitly called out as a defense against XSS in the C++ writer's comments: "these characters ... are escaped to prevent XSS risks"): [6](#0-5) 

There is no length, character-set, or format validation on `type_url` at parse time, and `AnyBase::unpack()` only checks the `type.googleapis.com/` prefix when *unpacking*, not when serializing to JSON — so an attacker can supply an arbitrary byte string for `type_url` (e.g., containing `"`, `\`, or newline) and it will be emitted verbatim between quotes in the JSON output.

### Impact Explanation
An attacker who controls the bytes of a binary-encoded `google.protobuf.Any` message (a normal, bounded, valid-schema payload delivered through the public `mergeFromString`/`parseFromStream`-style APIs) can set `type_url` to a value like `evil","injected":true,"x":"` or containing raw control characters/backslashes. When the receiving application calls the public `serializeToJsonString()` API on that message, the resulting JSON is corrupted: additional keys can be injected, the JSON becomes structurally invalid, or (if the consuming application embeds this JSON into HTML/JS without further encoding — the exact "consuming-application exposure" class flagged by the KaTeX advisory) client-side script execution becomes possible. This is a confidentiality/integrity-impacting output-generation bug (CWE-116: Improper Encoding/Escaping of Output), matching the CWE class of the KaTeX report. It is scoped to the pure-PHP runtime's JSON serialization of `Any` messages specifically.

### Likelihood Explanation
High likelihood of triggering: `Any` is a widely used well-known type, `type_url` is an ordinary attacker-controlled string field with no validation enforced on the encode-to-JSON path, and the vulnerable code executes on every `Any`→JSON serialization in the pure-PHP runtime, with no gating flag or opt-in required. The only precondition is that the application (1) accepts untrusted binary protobuf containing an `Any` field and (2) re-serializes it to JSON via the public API — a common pattern for proto/JSON gateways.

### Recommendation
Escape `type_url` identically to how every other string field is escaped in the same file, e.g. replace the raw write with the same `json_encode($value, JSON_UNESCAPED_UNICODE)` treatment used in `GPBJsonWire::serializeFieldValueToStream()`'s `STRING` case, or route it through the existing `escapedJson()`/`jsonNiceEscape()` helpers already present in `GPBJsonWire.php` before writing it to the output stream. Add a regression test (parity with `JsonFormatTest.testHtmlEscape` in Java) that serializes an `Any` with a maliciously-crafted `type_url` and asserts proper escaping.

### Proof of Concept
1. Construct binary protobuf bytes for a wrapper message containing an `Any` field where `type_url` is set to a string containing a double quote, e.g. `type.googleapis.com/pkg.Msg","x":"1` (this is a valid protobuf `string` field value — no schema/wire-format constraint rejects arbitrary bytes in a string field).
2. In PHP: `$msg = new WrapperMessage(); $msg->mergeFromString($bytes); echo $msg->serializeToJsonString();`
3. Observe the output JSON contains an injected key/value pair or malformed JSON, e.g.:
   `{"any_field":{"@type":"type.googleapis.com/pkg.Msg","x":"1", ...}}` — demonstrating the raw `type_url` bytes were spliced into the JSON string context unescaped, matching the code path shown at [1](#0-0) .

(Note: I was unable to fully inspect `php/src/Google/Protobuf/Any.php`'s generated `getTypeUrl`/`setTypeUrl` accessors within the available tool budget to confirm there is no additional validation layer added there beyond the base `Message` string-field setter; based on standard protobuf PHP code generation patterns and the `AnyBase::unpack()` code shown, `type_url` is a plain string field with only a prefix check applied during `unpack()`, not during JSON serialization.)
