### Title
`SignableTransaction::new` omits the OP_RETURN output from weight/vbytes, so the minimum-fee check can pass while the real transaction is below the minimum relay fee - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` appends the `data` OP_RETURN output to `tx_outs` before computing the transaction's weight and vbytes, but `calculate_weight_vbytes` is only called with `payments` (and optionally `change`), never including the OP_RETURN output. Analogous to the reported bug class — a minimum-amount boundary check that fails to account for an edge case — the `TooLowFee` minimum-relay-fee check and the `needed_fee` computation are evaluated against a smaller transaction than the one actually produced, letting an undersized fee slip through.

### Finding Description
At `send.rs:194-202` the OP_RETURN output is pushed onto `tx_outs`. Then at `send.rs:204` the weight/vbytes are computed via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — `payments` is the caller-supplied slice only; the data output just added is absent from the reconstructed transaction inside `calculate_weight_vbytes` (lines 85-99 build `tx.output` solely from `payments` plus optional `change`).

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) is underestimated by `fee_per_vbyte * vbytes(OP_RETURN)`. The actual fee paid is `sum(inputs) - sum(outputs)`; since the OP_RETURN carries zero value, the *absolute* fee is unchanged, but the *effective fee rate* of the final transaction is lower than `fee_per_vbyte` — the exact thing the caller asked for is silently violated.
2. The minimum relay check at lines 211-213 (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) uses the underestimated `vbytes`. A caller supplying a low-but-valid `fee_per_vbyte` and a `data` payload of up to 80 bytes (per the `TooMuchData` bound at line 171) produces a transaction whose actual fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE`, yet the check passes. The signed transaction is then rejected by Bitcoin Core's mempool (`min relay fee not met`) and cannot be broadcast.
3. The `MAX_STANDARD_TX_WEIGHT` check at line 241 also uses the underestimated `weight`, though this is marginal given the 80-byte data cap.

An unprivileged party who can cause a transaction to be built with a `data` payload (the `data` argument of `new` is untrusted caller input to this public API) controls up to ~90 extra vbytes excluded from the fee calculation.

### Impact Explanation
A produced `SignableTransaction` can pay an effective fee rate below both the requested `fee_per_vbyte` and the network minimum relay fee. The transaction the threshold group signs will be non-standard/unrelayable, so the spend cannot complete — the consumed inputs remain locked in the wallet's view until a replacement is constructed, a liveness/funds-availability failure rather than a recoverable error (`new` returned `Ok`). Additionally, `needed_fee()` returns a value that does not reflect the true minimum fee of the emitted transaction, so any caller accounting (fee amortization) is off.

### Likelihood Explanation
Exploitation requires the `data` parameter to be non-`None` combined with a low `fee_per_vbyte` (near or below `DEFAULT_MIN_RELAY_TX_FEE` prorated). Callers not using `data` are unaffected, and at high fee rates the discrepancy merely overpays relative to intent... rather, underpays relative to the requested rate. The window is narrow (the missing output is bounded to ~90 vbytes), so it primarily bites when the requested rate is already near the relay minimum — precisely the case the `TooLowFee` guard exists to catch, which is why the omission matters. Medium likelihood in deployments that attach `data`; low otherwise.

### Recommendation
Include the OP_RETURN output in the transaction built inside `calculate_weight_vbytes`, e.g., pass `data` (or push the zero-value OP_RETURN `TxOut`) so `weight`/`vbytes` reflect the final transaction. Perform the `TooMuchData` bound and construct the OP_RETURN `TxOut` *before* calling `calculate_weight_vbytes`, and use the data-inclusive vbytes for `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check.
