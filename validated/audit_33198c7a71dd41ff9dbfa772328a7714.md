## Analog Found: Shared `BalanceHandler` State Causes Balance Desync on Recursive/Nested Precompile Calls

### Title
Recursive precompile calls corrupt EVM StateDB balances via shared `BalanceHandler.prevEventsLen` bookkeeping - (File: `precompiles/common/balance_handler.go`)

### Summary
The Velodrome `earned()` bug is a class of "stale/overwritten bookkeeping cursor causes incorrect delta replay" — a checkpoint pointer used to compute an incremental reward delta is not properly re-derived on repeated/nested invocation, letting the same value be counted more than once (or dropped). The Cosmos EVM analog is the `BalanceHandler` used by every precompile to translate `x/bank` events into `StateDB` balance deltas: it uses a single mutable cursor, `prevEventsLen`, to slice "new" events since the call started. When precompile calls recurse or nest (a precompile call that internally triggers another precompile call, e.g. via a contract's callback/hook), this cursor is overwritten by the inner call, and the outer call's `AfterBalanceChange` then replays/misses event ranges — corrupting which of `StateDB.AddBalance`/`SubBalance` are (re-)applied.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records the current event count as `prevEventsLen`, and `AfterBalanceChange` later slices `events[bh.prevEventsLen:]` to translate bank Coin-spent/received events into `StateDB` balance mutations: [1](#0-0) [2](#0-1) [3](#0-2) 

Exactly like Velodrome's `earned()`, which uses a single `checkpoints[tokenId][_endIndex]` pointer that is expected to only be consumed once per call but is fully re-derivable on every invocation (so repeated calls double count the same interval), the `BalanceHandler` cursor `prevEventsLen` is set once per call and consumed on `AfterBalanceChange` — but the codebase itself documents that this cursor is **shared across recursive precompile invocations**, which overwrites the outer call's starting point: [4](#0-3) 

This is exercised by a dedicated regression test that deploys a contract performing recursive precompile calls, explicitly built to reproduce "the balance handler bug where recursive precompile calls share the same `BalanceHandler` instance, causing `prevEventsLen` to be overwritten... leads to balance desync between native bank keeper and EVM stateDB": [5](#0-4) 

There is a second, related regression suite testing the same class of bug specifically through the ICS20 precompile combined with the Distribution precompile invoked recursively from an ERC20 `_beforeTokenTransfer` hook, again explicitly annotated as testing "the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated": [6](#0-5) [7](#0-6) 

The recursive-call primitive is trivially reachable by any unprivileged ERC20 token holder: a malicious or buggy ERC20 contract overriding `_beforeTokenTransfer` to call the Distribution precompile (`claimRewards`) recursively, as shown in the test fixtures: [8](#0-7) 

### Impact Explanation
If the shared cursor causes the outer call's `AfterBalanceChange` to re-slice an event range that was already consumed (or partially consumed) by the inner call, `StateDB.AddBalance`/`SubBalance` can be invoked with the wrong deltas relative to the actual `x/bank` state change: either double-crediting an address's EVM-visible balance for a bank movement that happened once (duplication of spendable value on the EVM side that later persists via `StateDB` commit into the KV store), or dropping a balance-changing event entirely (permanent desync between the native bank balance and the EVM balance view, which precompiles, ERC20 representations, and JSON-RPC balance queries rely on). Either direction is a critical accounting-corruption invariant violation as defined in the allowed-impact gate ("irreversible accounting corruption of spendable user value across native balances, EVM balances... or precompile-mediated assets").

### Likelihood Explanation
The trigger requires only deploying an ordinary ERC20 contract (or any contract) with a hook that calls a precompile from within another precompile-triggered execution context — no privileged role, validator, or relayer involvement is needed. The project's own test suite already demonstrates the recursive-call condition is reachable through standard user flows (ERC20 transfer hooks calling Distribution, and ICS20 transfers of ERC20-wrapped tokens triggering the same hook chain), which strongly suggests the root cause is exercised by ordinary transaction/contract paths and not merely a hypothetical.

### Recommendation
Do not store `prevEventsLen` as mutable state on a `BalanceHandler` instance that can be shared/reused across nested precompile invocations. Instead, capture start/end event index pairs per call frame (e.g., return the recorded length from `BeforeBalanceChange` and require callers to pass it explicitly into `AfterBalanceChange`, or use a stack of markers), so that nested calls cannot clobber an outer call's bookkeeping — analogous to the Velodrome fix of looping deterministically over fully-specified epoch boundaries instead of relying on a single mutable pointer that assumes non-reentrant, single-shot consumption.

### Proof of Concept
The existing regression tests already constitute a proof of concept for the root-cause mechanism (shared cursor overwritten by recursion): [9](#0-8) [7](#0-6) 

Note: I could not fully verify from the indexed code whether `BalanceHandler` instances are actually shared (singleton per `Precompile` struct) versus freshly constructed per `Run` call in production `precompiles/common/precompile.go` — the grep found references there but the file content wasn't retrievable within the index. This distinction determines whether the bug is already latent/reachable in current `main` or only demonstrated as a targeted regression test for a since-mitigated pattern. I recommend a Devin session with full repository access to confirm whether `precompile.go`'s call-setup path constructs a new `BalanceHandler` per `Run` invocation (which would neutralize this exact bug) or reuses one across nested/recursive calls (which would confirm the vulnerability is live).
