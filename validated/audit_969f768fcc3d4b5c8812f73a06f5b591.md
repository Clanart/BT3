## Analysis

The external report is about an `unimplemented!()` panic in `LogicCallExecutedEvent::from_log` that crashes the oracle when parsing untrusted/unexpected on-chain events — the underlying bug class is: **event-driven state-update logic that assumes clean, self-consistent event sequences, but breaks (crash, or here, silent corruption) when that assumption is violated by nested/unexpected execution paths.**

The closest reachable analog in this repository is in the precompile `BalanceHandler`, which mirrors bank/precisebank events emitted during a precompile call into the EVM `StateDB` balances. Unlike the Gravity Bridge case, the CosmosEVM code doesn't panic — it can silently double-apply or drop a balance delta when a precompile call is executed recursively/nested, corrupting the invariant that `StateDB` balances mirror the underlying bank ledger 1:1.

### Title
Recursive/Nested Precompile Calls Corrupt EVM StateDB Balances via Shared `BalanceHandler` — (File: precompiles/common/balance_handler.go)

### Summary
`BalanceHandler.BeforeBalanceChange`/`AfterBalanceChange` uses a single mutable `prevEventsLen` cursor to determine which `sdk.Context` events (bank `CoinSpent`/`CoinReceived`/precisebank `FractionalBalanceChange`) to mirror into `StateDB.AddBalance`/`SubBalance` [1](#0-0) . Several precompiles (bank, erc20, distribution, gov, ics20, slashing, staking) obtain this handler via a shared accessor (`GetBalanceHandler()`) rather than instantiating a fresh handler per call, as `RunNativeAction` does [2](#0-1) . When a precompile call is nested (a contract calling a precompile which internally triggers another precompile/bank-event-emitting path before returning), the inner call's `BeforeBalanceChange` overwrites `prevEventsLen`, and the inner `AfterBalanceChange` consumes/resets the event window. The outer call's subsequent `AfterBalanceChange` then computes its balance delta over the wrong event slice, causing balance changes to be double-applied or skipped.

The repository's own integration test suite explicitly documents this as a known defect: `TestRecursivePrecompileCallsWithDebugPrecompile` states it "demonstrates the balance handler bug by triggering recursive calls that share the same BalanceHandler instance" [3](#0-2) .

### Finding Description
`AfterBalanceChange` iterates `events[bh.prevEventsLen:]` and, for each `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` event, calls `stateDB.SubBalance`/`AddBalance` with the parsed amount [4](#0-3) . This design implicitly assumes a single, non-reentrant call frame per handler instance: `prevEventsLen` is set once at call entry and consumed once at call exit.

When the same `BalanceHandler` instance is shared across nested precompile invocations (as occurs for precompiles that fetch it via `p.GetBalanceHandler()` instead of creating one per call through `BalanceHandlerFactory.NewBalanceHandler()` [5](#0-4) ), a nested call:
1. Overwrites `prevEventsLen` to the (larger) event count observed inside the outer call.
2. Consumes and applies (via `AddBalance`/`SubBalance`) events emitted for the inner action.
3. Returns control to the outer call, whose own `AfterBalanceChange` now computes its delta starting from the inner call's (already advanced) `prevEventsLen` — meaning outer-call bank events that were emitted *before* the nested call are silently skipped, or events already applied by the inner pass could be re-applied depending on ordering, breaking the 1:1 mapping between `x/bank`/`x/precisebank` coin movements and EVM `StateDB` balances.

This directly violates the "Asset-representation path" invariant call out in the audit brief: precompile-mediated flows must preserve exact 1:1 accounting between native coins and EVM-visible balances across nested-call execution.

### Impact Explanation
If a `CoinSpent`/`CoinReceived` event is dropped from the `StateDB` view, the caller's on-chain EVM balance can end up higher than what was actually debited from the bank ledger — the caller could spend that inflated EVM balance in the same or later transaction, extracting value that was never actually escrowed/backed, i.e., unauthorized duplication of spendable value. Conversely, an event applied twice would inflate a receiver's `StateDB` balance beyond the actual bank credit, again producing spendable EVM value not backed by real coins. Both cases match the Critical "unauthorized minting/duplication ... accounting corruption of spendable user value across ... EVM balances" scope.

### Likelihood Explanation
This requires an unprivileged attacker to structure a transaction that nests two balance-affecting precompile calls sharing the same `BalanceHandler` instance (e.g. a contract calling a precompile like `bank`/`distribution`/`staking` whose execution path re-enters a precompile that also touches the shared handler, or a self-reentrant call through `call`/`delegatecall` back into the same precompile before the outer call's `AfterBalanceChange` runs). The repository's own test explicitly confirms recursive precompile calls reach and exercise this shared-handler code path, though the demonstration test uses a non-money-moving debug precompile and does not itself assert a balance divergence, so full confirmation that a real money-moving precompile (bank/erc20/staking/distribution) is reachable via the same shared-handler pattern needs to be verified by re-inspecting `GetBalanceHandler()`'s implementation and each precompile's `Run` entrypoint (I was unable to complete this last verification step due to tool-call exhaustion).

### Recommendation
Ensure every precompile call path (not just `RunNativeAction`) obtains a **fresh** `BalanceHandler` per top-level call via `BalanceHandlerFactory.NewBalanceHandler()`, or make `BeforeBalanceChange`/`AfterBalanceChange` reentrancy-safe (e.g., push/pop a stack of `prevEventsLen` cursors instead of a single mutable field) so nested calls cannot clobber an in-flight outer call's event window.

### Proof of Concept
The repository's own regression test frames the reproduction scaffold: it registers a debug precompile, deploys a caller contract that recursively invokes the precompile (`callback(0)`), and observes the shared `BalanceHandler` being exercised across nested precompile invocations [6](#0-5) . To turn this into a concrete fund-extraction PoC, the debug precompile would need to be replaced with two real balance-moving precompiles (e.g., `bank` and `distribution`) invoked in a nested call chain from a single Solidity contract, then asserting that `stateDB.GetBalance` diverges from the actual `x/bank` balance after the call completes — this concrete money-moving PoC was not present in the indexed test files and would need to be constructed to fully confirm exploitability.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case precisebanktypes.EventTypeFractionalBalanceChange:
			addr, err := ParseAddress(event, precisebanktypes.AttributeKeyAddress)
			if err != nil {
				return fmt.Errorf("failed to parse address from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}
			if bh.bankKeeper.BlockedAddr(addr) {
				// Bypass blocked addresses
				continue
			}

			delta, err := ParseFractionalAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}

			deltaAbs, err := utils.Uint256FromBigInt(new(big.Int).Abs(delta))
			if err != nil {
				return fmt.Errorf("failed to convert delta to Uint256: %w", err)
			}

			if delta.Sign() == 1 {
				stateDB.AddBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			} else if delta.Sign() == -1 {
				stateDB.SubBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			}

func (p Precompile) Run(evm *vm.EVM, contract *vm.Contract, readonly bool) ([]byte, error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.Wrap(errors2.ErrUnauthorized, "could not create statedb in debug precompile")
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	err = stateDB.AddPrecompileFn(p.Address(), snapshot, events)
	if err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	// Start the balance change handler before executing the precompile.
	p.GetBalanceHandler().BeforeBalanceChange(ctx)

	initialGas := ctx.GasMeter().GasConsumed()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)
	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	// This handles any out of gas errors that may occur during the execution of a precompile tx or query.
	// It avoids panics and returns the out of gas error so the EVM can continue gracefully.
	defer cmn.HandleGasError(ctx, contract, initialGas, &err)()

	res, err := p.Execute(ctx, stateDB, contract, readonly)
	if err != nil {
		return nil, err
	}

	if err != nil {
		return nil, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	// Process the native balance changes after the method execution.
	if err := p.GetBalanceHandler().AfterBalanceChange(ctx, stateDB); err != nil {
		return nil, err
	}

	return res, nil
}
