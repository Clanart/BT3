Confirmed: there's no bound check anywhere preventing `Kip71GasTarget` from being set to `0`. This mirrors the reported bug class exactly — an inconsistent/missing boundary check on a governance-tunable parameter that is later used as a divisor.

### Title
KIP-71 `GasTarget` governance parameter can be voted to 0, causing a division-by-zero panic in base fee calculation - (File: `params/kip71_config.go`)

### Summary
The KIP-71 governance parameter `Kip71GasTarget` has no format/bound validation preventing it from being set to `0`, unlike its sibling divisor parameter `Kip71BaseFeeDenominator`, which is explicitly checked and defensively handled at zero. Once `GasTarget` is set to `0` via a governance vote, the next call to `NextMagmaBlockBaseFee` divides by `gasTarget` and panics whenever a block uses any gas, crashing every node that validates or builds the next block.

### Finding Description
`Kip71GasTarget`'s parameter definition uses `noopFormatChecker`, imposing no validation at all on the voted value: [1](#0-0) 

Contrast this with `Kip71BaseFeeDenominator`, which is explicitly required to be non-zero: [2](#0-1) 

The `checkConsistency` function in headergov, which is meant to validate votes against chain state (e.g. it validates `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` against each other), explicitly treats `gov.Kip71GasTarget` as needing no additional checks beyond format checking: [3](#0-2) 

Because the format checker is a no-op, and consistency checking is also a no-op for this parameter, a governance vote for `Kip71GasTarget = 0` is accepted and stored, updating `ParamSet.GasTarget` via `(*ParamSet).Set`: [4](#0-3) 

The resulting `ParamSet` is converted into a `KIP71Config` and used directly in `NextMagmaBlockBaseFee`, where `gasTarget` is used as a divisor in both the "gas used above target" and "gas used below target" branches: [5](#0-4) 

Unlike `BaseFeeDenominator`, which has an explicit zero-guard that substitutes a safe default of `64` before it's used, `gasTarget` has no equivalent guard: [6](#0-5) 

If `parentGasUsed == gasTarget` (i.e., both zero, an empty block), the function returns early without dividing. But as soon as `parentGasUsed > 0` and `gasTarget == 0`, the "used more than target" branch executes `x.Div(x, new(big.Int).SetUint64(gasTarget))`, which is a division by zero. Go's `big.Int.Div` panics on division by zero, so every node computing/verifying the next block's base fee — both the block proposer and every validating full node — will crash deterministically at the same block.

### Impact Explanation
This is a network-wide, deterministic denial of service: after a single successful governance vote sets `GasTarget` to `0`, the very next non-empty block causes a panic in `NextMagmaBlockBaseFee`, which is called both during block header verification (`VerifyMagmaHeader`) and block assembly. Because the panic is deterministic and triggered by consensus-agreed governance state, it halts the entire chain rather than causing a localized failure, which is a critical availability impact for the network.

### Likelihood Explanation
Setting `Kip71GasTarget` requires a successful governance vote (in single mode, cast by the governing node; in ballot mode, by the council), so the direct trigger is not a fully unprivileged transaction. However, per the accepted analog domains ("governance parameters" is explicitly in scope), and given there is no code path anywhere — canonicalizer, format checker, or consistency checker — that rejects `0` for this specific value despite it being used as a divisor exactly like `BaseFeeDenominator` (which *is* protected), the likelihood of this being exploitable by any single governance participant able to cast a vote is high, and the impact (total chain halt) is severe enough to warrant fixing regardless of the voting privilege level required.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0` (i.e., `v > 0`), mirroring the existing check on `Kip71BaseFeeDenominator`. As defense in depth, also add a zero-guard in `NextMagmaBlockBaseFee` in `params/kip71_config.go` for `gasTarget`, similar to the existing guard for `baseFeeDenominator`, so that even a governance misconfiguration cannot crash the node.

### Proof of Concept
1. Governance vote (or council ballot) sets `kip71.gastarget` to `0`. This vote passes `NewVoteData`'s format checks (`noopFormatChecker`, `kaiax/gov/param.go:324-334`) and `checkConsistency`'s no-op handling for `gov.Kip71GasTarget` (`kaiax/gov/headergov/impl/header.go:213-220`), so it is accepted into `ParamSet.GasTarget`.
2. At the next epoch, `GetParamSet` returns `GasTarget = 0`, and `ToKip71Config()` propagates it into a `KIP71Config` with `GasTarget: 0`.
3. When the next non-empty block (`parentHeaderGasUsed > 0`) is assembled or verified, `NextMagmaBlockBaseFee` is invoked; since `parentGasUsed != gasTarget (0)`, it enters the `parentGasUsed > gasTarget` branch and executes `x.Div(x, new(big.Int).SetUint64(0))`, which panics with a division-by-zero runtime error (`params/kip71_config.go:100-103`).
4. Every node (proposer and validators) hits this same panic when processing the block, halting the chain network-wide.
