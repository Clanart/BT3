### Title
Read-before-write reward accounting in `ArbWomUp3.incentiveDeposit` credits MGP based on nominal deposit amount while the actual mWomSV lock can be materially smaller due to unprotected internal swap - ([File: wombat/ArbWomUp3.sol])

### Summary
`incentiveDeposit()` computes the MGP reward via `getRewardAmount()` using the raw `_amount` the user *intends* to deposit **before** `_deposit()` actually executes, assuming the full amount will end up 1:1 backed in `mWomSV`. When `_mode == 2`, half of the amount is routed through `SmartWomConvert.convert()` with a hardcoded `_minRec = 0`, so the mWom actually obtained (and thus actually locked into `mWomSV`) can be significantly less than the nominal half, letting an attacker collect MGP for tier/backing that was never actually locked.

### Finding Description
In `incentiveDeposit`, the reward is computed first, then the deposit is performed: [1](#0-0) 

`getRewardAmount` (and `calDoubledCounted`) determine tier/reward using `accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account)`, i.e., it assumes the *entire* `_amountToConvert` (the full nominal `_amount` being deposited) will become new locked mWomSV balance: [2](#0-1) 

However, in `_deposit`, only half of `_amount` (`toDeposit`) is wrapped 1:1 via `IMWom.deposit`. The other half (`toSwap`) is routed through `smartWomConvert.convert(toSwap, _convertRatio, 0, 0)` — note the hardcoded `_minRec = 0`, meaning **no slippage protection** on this internal swap: [3](#0-2) 

Inside `SmartWomConvert._convertFor`, when `_convertRatio` is low, most of `toSwap` is routed through the AMM router (`buybackAmount`) rather than 1:1 wrapped, and the actual `amountRec` returned depends entirely on AMM pricing/slippage at execution time — there is no floor enforced since `_minRec` was passed as `0`: [4](#0-3) 

The total mWom actually locked for the account, `mWomBal = toDeposit + amountRec`, can therefore be materially less than the nominal `_amount` that was used to compute the reward tier in step 1. Because `getRewardAmount` is evaluated *before* the swap executes and uses the nominal `_amount` rather than the post-swap locked delta, the attacker is credited `rewardMultiplier[tier]`-based MGP for backing that never materializes 1:1 in `mWomSV`. An attacker can choose a low `_convertRatio` (routing most funds through the unprotected swap) and manipulate/time the `womMWomPool` swap (e.g., via a preceding large swap or flash-loan-funded trade against the same pool in the same transaction, which is within the allowed unprivileged attacker capabilities) to depress `amountRec` far below `toSwap`, while still receiving MGP reward computed as if the full nominal `_amount` were locked.

No existing modifier or check mitigates this: `_checkAmount`, `whenNotPaused`, and `nonReentrant` only guard against zero-amount/pausing/reentrancy, not against the reward/locking amount mismatch, and the internal `convert()` call's `_minRec` is hardcoded to `0`, removing the one place a floor could have prevented the discrepancy.

### Impact Explanation
This allows direct theft of protocol MGP tokens: attacker-controlled `vlMGP.lockFor(rewardToSend, msg.sender)` mints/locks MGP rewards tied to a `mWomSV` tier that is not actually backed by the equivalent locked mWom, degrading the reward pool's solvency (`mgpleft` balance depleted disproportionately to real backing) and effectively stealing unclaimed yield meant for legitimately-backed depositors. This matches the "theft of unclaimed yield / protocol insolvency" impact class.

### Likelihood Explanation
The attacker needs only: (1) call the public `incentiveDeposit` with `_mode == 2` and a low `_convertRatio`, and (2) influence the `womMWomPool` swap rate at execution time (via a same-transaction flash-loan-funded swap or simply sizing the deposit large enough that price impact alone produces a bad rate), both of which are actions available to any unprivileged EOA/contract. The lack of `_minRec` enforcement in the internal call makes this fully repeatable and requires no privileged role.

### Recommendation
Compute (or re-verify) the reward based on the actual post-deposit delta in `mWomSV.getUserTotalLocked(_account)` rather than the pre-deposit nominal `_amount`, i.e., call `_deposit` first, capture the locked-balance delta, and then compute/mint the reward off that real delta. Additionally, pass a proper non-zero `_minRec` (e.g., derived from `estimateTotalConversion`) into the internal `smartWomConvert.convert(...)` call inside `_deposit` to bound acceptable slippage.

### Proof of Concept
Foundry test plan:
1. Deploy `ArbWomUp3`, `SmartWomConvert`, `mWomSV`, `vlMGP`, and a mock/real Wombat WOM/mWom pool with configurable liquidity.
2. Fund attacker with WOM and approve `ArbWomUp3`.
3. Snapshot `mWomSV.getUserTotalLocked(attacker)` (0) and compute `expected = ArbWomUp3.getRewardAmount(amount, attacker, true)` before any call.
4. Have attacker (or a helper contract in the same tx) execute a large swap against the WOM/mWom pool to skew price unfavorably for subsequent WOM->mWom swaps.
5. Call `incentiveDeposit(amount, convertRatio=0, false, mode=2)`.
6. Assert `mWomSV.getUserTotalLocked(attacker)` after the call is significantly less than `amount` (post-deposit locked delta < nominal amount).
7. Assert the MGP amount locked into `vlMGP` for attacker (via `VLMGPRewarded` event or `vlMGP` balance) matches `expected` (computed off the nominal, unbacked amount), quantifying the free/unbacked MGP minted relative to the real `mWomSV` backing shortfall.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }

        IERC20(wom).safeTransferFrom(_account, address(this), _amount);

        if (_mode == 1) {
            IERC20(wom).safeApprove(mWom, _amount);
            IMWom(mWom).deposit(_amount);            
            IERC20(mWom).safeApprove(smartWomConvert, _amount);
            IConverter(smartWomConvert).depositFor(_amount, _account);

        } else if (_mode == 2) {
            uint256 toDeposit = _amount / 2;
            uint256 toSwap = _amount - toDeposit;

            // 50% goes to deposit
            IERC20(wom).safeApprove(mWom, toDeposit);
            IMWom(mWom).deposit(toDeposit); 

            // 50% smart smart convert
            IERC20(wom).safeApprove(smartWomConvert, toSwap);
            IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0);

            uint256 mWomBal = IERC20(mWom).balanceOf(address(this));
            IERC20(mWom).safeApprove(address(mWomSV), mWomBal);
            ILocker(mWomSV).lockFor(mWomBal, _account);

        } else {
            IERC20(wom).safeApprove(mWom, _amount);
            IMWom(mWom).deposit(_amount);               
            IERC20(mWom).safeTransfer(_account, _amount);
        }
        
        emit WomDeposited(_account, _amount, _mode);
    }
