### Title
Missing `--` end-of-options guard in `addWorktree` allows ref/branch argument injection into `git worktree add` - (File: `app/src/lib/git/worktree.ts`)

### Summary
`addWorktree` constructs `['worktree', 'add', ...(createBranch ? ['-b', createBranch] : []), path, ...(commitish ? [commitish] : [])]` and passes it straight to `git()` with no `--` separator between options and operands. [1](#0-0) 

### Finding Description
`git`'s option parser (`parse-options`) does not stop scanning for flags at the first non-option token unless `--` is given; any subsequent argument starting with `-` can still be interpreted as an option, even when it appears in a position intended to be a plain ref/path. `addWorktree` never inserts `--` before `path` or `commitish`, so both operands are parsed permissively.

`commitish` is populated from `branch.ref`/`branch.name`, which for a `BranchType.Remote` branch is derived from an existing remote-tracking ref, and `createBranch` can be `branch.nameWithoutRemote` or arbitrary dialog input seeded from `initialBranchName`. Critically, `AddWorktreeDialog` seeds `branchName` directly from attacker-influenced text without going through `sanitizedRefName`: `onCheckoutPRInNewWorktree` in `app/src/ui/toolbar/branch-dropdown.tsx:424-431` sets `initialBranchName: pullRequest.head.ref` — the head ref name of a pull request, which is controlled by whoever opened the PR (an unprivileged attacker on a public repo). That value flows into `AddWorktreeDialog`'s state as `branchName: props.initialBranchName ?? ''` and, if it does not match an existing branch, is used verbatim as `createBranch: effectiveBranchName` in `onSubmit`. [2](#0-1) [3](#0-2) [4](#0-3) 

By contrast, `checkoutBranch`'s equivalent code path (`getBranchCheckoutArgs`) always appends a trailing `'--'` before the ref, explicitly to end option parsing, showing the codebase is aware of and normally guards against this exact class of issue elsewhere. [5](#0-4) 

I was not able to fully verify, without a live git binary, which specific `git worktree add` flags (e.g. `--lock`, `--orphan`, `-f`) could be leveraged into a meaningfully dangerous effect (arbitrary file write/exec) versus a benign parse error, so the concrete blast radius (beyond confirmed argv confusion / DoS via a bad-usage error) is unconfirmed.

### Impact Explanation
If a value beginning with `-`/`--` reaches `addWorktree` as `createBranch`, `path`, or `commitish`, it can be parsed as a `git worktree add` option instead of an inert value. At minimum this breaks the intended operation (unexpected flags such as `--force`, `--lock`, `--orphan`, `--detach` could be silently triggered), and in the worst case (depending on which flags accept further arguments) could redirect subsequent positional arguments, corrupting what worktree/branch gets created. This matches the "argv/flag injection" invariant described in the question: attacker text should only ever reach git as an inert operand.

### Likelihood Explanation
Exploitability requires a PR head-ref name (or similarly attacker-influenced branch name) to both start with `-`/`--` and pass git's ref-name validation for the value used as `-b <name>` (git's `check-ref-format` does permit some `-`-prefixed components), and requires the local user to open the "Checkout in new worktree" flow for that specific PR/branch without editing the pre-filled branch name field. This requires some, but not extensive, user interaction, and does not require the attacker to control the `path`/local install and is realistically triggerable from a public-repo PR.

### Recommendation
Insert `'--'` before positional ref/commit-ish operands in `addWorktree`, mirroring `getBranchCheckoutArgs` in `checkout.ts`, e.g.:
```ts
args.push(path)
if (options.commitish) {
  args.push('--', options.commitish)
} 
```
and additionally validate/sanitize `createBranch` (e.g., via `sanitizedRefName`) before it is used as `-b`'s value, since `AddWorktreeDialog` currently allows an unsanitized `initialBranchName` (sourced from `pullRequest.head.ref`) to flow straight into `createBranch`.

### Proof of Concept
1. Open a public repository in GitHub Desktop that has a pull request from an external contributor whose branch name begins with `-`, e.g. `--orphan` or `-b--evil` (subject to git ref-name constraints).
2. In the Branches dropdown, use "Checkout PR in new worktree" for that PR — `onCheckoutPRInNewWorktree` seeds `initialBranchName: pullRequest.head.ref` unsanitized.
3. Accept the dialog defaults (worktree name auto-filled, branch name pre-filled with the malicious ref) and submit.
4. `addWorktree` is invoked with `createBranch` set to the raw attacker-supplied ref text, producing `git worktree add -b <attacker-text> <path>` with no `--` guard, allowing `<attacker-text>` to be reinterpreted by git's option parser instead of used as a literal branch name. [6](#0-5)
