### Title
Panic on `unwrap()` of `ThresholdView` construction with participant index 0 crashes the FROST signer — (File: crypto/frost/src/sign.rs)

### Summary
CVE-2019-0982 is a denial-of-service class bug: improperly handled input causes the service to crash. The reachable analog in Serai's FROST signing path is in `AlgorithmSignMachine::sign`, which validates the signing set for duplicates and an out-of-bounds maximum index, but never rejects `Participant(0)`. It then calls `self.params.keys.view(included.clone()).unwrap()`, so any condition under which `ThresholdView::view` returns `Err` for the otherwise-validated `included` set becomes a panic, aborting the signer.

### Finding Description
In `crypto/frost/src/sign.rs`, `sign` builds `included` from the local index plus every key in the attacker-influenced `preprocesses: HashMap<Participant, Preprocess>`, sorts it, and enforces only:

- `included.len() >= t` (line 298)
- `included.last() <= n` (line 302)
- no adjacent duplicates after sorting (lines 306–310)

It then does `let view = self.params.keys.view(included.clone()).unwrap();` (line 312). Because the set-level validation is done here while semantic validity of each `Participant` is deferred to `view`, a preprocess keyed to a `Participant` value that `ThresholdKeys::view` rejects — most notably `Participant(0)`, which passes the `<= n` and no-duplicate checks — turns the `Err` into a panic via `unwrap`. `Participant` values arrive over the wire as keys of the preprocess map (fed through `read_preprocess` → `Commitments::read` at lines 276–281), so this is reachable by any counterparty able to submit a preprocess message, i.e., any participant in a signing session.

### Impact Explanation
An unprivileged cosigner submits a preprocess under participant index `0`. Validation passes, `view(...)` returns `Err`, and `.unwrap()` panics, crashing the signer's signing task/process. In a threshold network this repeatedly kills honest signers mid-session, preventing the multisig from reaching `t` completions — a persistent denial of service of the signing service, matching the report's availability-impact class (C:N/I:N/A:H). This is a reachable-panic DoS rather than a correctness bug, so severity is Medium.

### Likelihood Explanation
Any party who can deliver a preprocess message to a signer controls the `Participant` keys in `preprocesses`. No key material, collusion, or privileged position is needed — just participation in (or injection into) one signing round. The panic is deterministic and repeatable across sessions.

### Recommendation
Replace the `unwrap()` at `crypto/frost/src/sign.rs:312` with error propagation (`map_err` into `FrostError::InvalidParticipant`), and explicitly reject `Participant(0)` and indexes `> n` during the `included` validation loop alongside the existing duplicate check, mirroring the validation `ThresholdKeys::view` performs.

### Proof of Concept
Conceptual: construct `HashMap<Participant, Preprocess>` for a `ThresholdParams` with `t=2, n=3`, `i=1`; insert a valid `Preprocess` under key `Participant(0)` and one under `Participant(2)`, then call `AlgorithmSignMachine::sign(map, msg)`. `included` becomes `[0, 1, 2]`: passes `t`, `max <= n`, and duplicate checks, then `view(included)` fails on the zero index and `.unwrap()` panics, aborting the signer.

Note: the claim that `ThresholdKeys::view` returns `Err` for `Participant(0)` is inferred from the defense-in-depth split between `sign`'s set checks and `view`'s semantic checks; I could not open `ThresholdView::view`/`ThresholdKeys::view` within the iteration budget to confirm the exact rejection. If `view` instead silently accepts index 0, this finding degrades to a Lagrange-interpolation correctness issue rather than a panic, and the finding should be re-scored accordingly.
