### Title
Cross-transaction contamination of output `data`/`presumed_origin` lets any sender overwrite other deposits' InInstructions in the same block - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::get_outputs` accumulates scanned `Output`s into a single `outputs` vector shared across every transaction in a block, then applies the *current* transaction's `presumed_origin` and `extract_serai_data(tx)` to **all** accumulated outputs — not just the ones found in that transaction. Any user who gets a transaction paying to a Serai address mined in the same block as a victim deposit can overwrite the victim's `data` (the serialized Serai InInstruction) and `presumed_origin`, redirecting how the deposit is interpreted/credited.

### Finding Description
In `get_outputs`, the `outputs` vector is declared once before the per-transaction loop [1](#0-0) . After scanning each `tx`, the code computes `presumed_origin` from `tx.input[0]`'s spent output and `data` via `Self::extract_serai_data(tx)`, then iterates `for output in &mut outputs` and assigns `output.data = data` (for `OutputType::External`) and `output.presumed_origin` to every element [2](#0-1) . Outputs pushed by earlier transactions in the same block are mutated again by later transactions. There is no per-transaction scoping — the intent (per the comments about identifying the InInstruction origin) is clearly to decorate only the outputs of the transaction currently being processed.

`scan_transaction` only matches registered script pubkeys, so an attacker can produce a matching "output" trivially by sending dust to Serai's external/branch/forward address [3](#0-2) . The `data` field is consumed downstream as the Serai `InInstruction` attached to an `External` output (see `extract_serai_data` usage and the literal test embedding a `Shorthand::transfer` instruction via OP_SHA256/OP_EQUALVERIFY witness data) [4](#0-3) .

### Impact Explanation
This is the analog of the reference bug's "tokens stranded in the contract / handled under attacker-controlled terms": funds arrive at the correct key (so they are *reported received*), but the instruction metadata that determines how the protocol credits/moves them is attacker-controlled. An attacker who lands a transaction later in the same block as a victim's deposit can replace the victim's `data` with an arbitrary serialized instruction (e.g., a `transfer` to the attacker's Serai address, or an invalid instruction causing the deposit to be dropped/mishandled) and falsify `presumed_origin` for refund/attribution logic. This requires only sending a standard Bitcoin transaction — fully reachable by an unprivileged party — with likelihood gated only on same-block ordering, which the attacker can engineer by broadcasting after observing the victim's transaction in the mempool.

### Likelihood Explanation
Any Bitcoin user can send to a Serai address and control their transaction's witness/OP_RETURN data and input ordering. Same-block inclusion is common and manipulable (higher fee, or reacting to mempool transactions). The overwrite is deterministic: every output collected earlier in the loop is rewritten by the last matching transaction's data. Severity is High: attacker-controlled redirection of deposit instructions.

### Recommendation
Scope decoration to the current transaction's outputs. Collect per-transaction results (e.g., `let tx_outputs = scanner.scan_transaction(tx)`), apply `presumed_origin`/`data` only to `tx_outputs`, then extend the block-level `outputs` vector — so each `ReceivedOutput` is only ever annotated by the transaction that actually created it.

### Proof of Concept
1. Victim broadcasts `tx_v` paying X BTC to the Serai external address with witness data encoding `InInstruction` crediting the victim.
2. Attacker sees `tx_v` in the mempool and broadcasts `tx_a` paying dust (≥ `DUST`) to the same Serai external address, with `data` = `Shorthand::transfer(None, attacker_serai_address)` and a higher fee / position later in the block.
3. In `get_outputs`, `tx_v` pushes the victim's `Output` with correct `data`; then `tx_a` pushes its dust output and the `for output in &mut outputs` loop overwrites the victim's `output.data` with the attacker's instruction and `presumed_origin` with the attacker's input.
4. The processor emits the victim's deposit carrying the attacker's instruction — the funds are received by the multisig key but attributed/handled per attacker-supplied data.
