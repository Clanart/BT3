### Title
Symlink-following in `showFolderContents` allows a malicious repo to reveal directories outside the repo boundary - (File: `app/src/ui/main-process-proxy.ts`)

### Summary
`showFolderContents` (declared in the `IAppShell` interface in `app/src/lib/app-shell.ts` and implemented in `app/src/ui/main-process-proxy.ts`) opens whatever path is passed to it in the OS file manager without verifying that the resolved (real) path stays inside the repository root. Because a git repository can contain a tracked symlink, an attacker can commit a symlink such as `evil -> /Users/victim/.ssh` and get the victim's file manager to open that target directory when the victim selects the symlink in Changes/History and clicks "Show Folder Contents."

### Finding Description
`revealInFileManager` in `app/src/lib/app-shell.ts` builds the path to reveal via simple string concatenation with no resolution or containment check: [1](#0-0) 

That path is handed to `showFolderContents`, implemented in `app/src/ui/main-process-proxy.ts`. This function calls `fs.stat` (which follows symlinks by default) to decide whether the target is a directory, and then — on Windows/Linux — passes the *original, unresolved* path straight to `UNSAFE_openDirectory`, or on macOS decides between `_showItemInFolder` and `UNSAFE_openDirectory` based on `isApplicationBundle`, again on the unresolved path: [2](#0-1) 

Nowhere in this flow is the resolved/real path checked against the repository root (`repository.path`). If `path` in the repo (e.g. `Changes` or `History` list item) is a symlink to a directory outside the repository, `fs.stat` will report it as a directory (following the link), and the underlying Electron/OS API (`shell.openPath`/explorer "open folder") will follow the symlink and show the contents of the linked target directory — which can be anywhere on the victim's filesystem, including sensitive folders like `~/.ssh`.

The callers that reach this code path from attacker-controlled repository content are the Changes and History file lists, e.g. `revealInFileManager` used from `app/src/ui/changes/filter-changes-list.tsx` and `app/src/ui/history/selected-commits.tsx`, both of which construct the file-manager path directly from the user-selected changed/committed file path without any symlink-target validation: [3](#0-2) 

### Impact Explanation
A malicious repository can trick a victim, after cloning/fetching it and browsing Changes or History, into opening a native file-manager window rooted at an arbitrary host directory chosen by the attacker (any directory the OS user account can read, e.g. `~/.ssh`, `~/.aws`, browser profile directories, etc.). This discloses directory listings (filenames, metadata) of sensitive locations outside the repository boundary, and gives the victim a one-click path to further open individual files from that folder in Finder/Explorer. This matches the "file read outside the repo" impact class in the bounty scope, though the direct effect is a directory listing exposure rather than a raw file read.

### Likelihood Explanation
Requires the victim to explicitly select the symlinked path in the Changes or History view and click the "Show Folder Contents" context-menu action; it is not automatically triggered on clone/fetch. This is a normal, expected user interaction (context menu action available on any working-directory or history file) rather than an "unprompted unnatural user step," so it is a plausible, low-friction interaction pattern once a user is exploring an attacker-supplied repository.

### Recommendation
In `showFolderContents` (and `revealInFileManager`), resolve the real path with `fs.realpath`/`fs.promises.realpath` and verify that the resolved path is contained within `repository.path` (or the intended base directory) before invoking `UNSAFE_openDirectory`/`_showItemInFolder`. Reject or warn when the resolved path escapes the repository root, similar to existing symlink-containment protections that should be applied consistently across all file-manager-reveal code paths.

### Proof of Concept
1. Create a repository containing a tracked symlink: `evil -> /Users/victim/.ssh` (or any sensitive absolute path) and commit it.
2. Have the victim clone/fetch this repository and open it in GitHub Desktop.
3. In the Changes or History view, select the `evil` entry and choose "Show Folder Contents" from the context menu, which calls `revealInFileManager` → `showFolderContents`.
4. `fs.stat` follows the symlink and reports it as a directory; `UNSAFE_openDirectory` opens the path, and the OS file manager follows the symlink, displaying the contents of `/Users/victim/.ssh` to the attacker's chosen directory instead of anything inside the repository.

```typescript
export async function showFolderContents(path: string) {
  const stats = await stat(path).catch(err => {
    log.error(`Unable to retrieve file information for ${path}`, err)
    return null
  })

  if (!stats) {
    return
  }

  if (!stats.isDirectory()) {
    log.error(`Trying to get the folder contents of a non-folder at '${path}'`)
    await _showItemInFolder(path)
    return
  }

  // On Windows and Linux we can count on a directory being just a
  // directory.
  if (!__DARWIN__) {
    UNSAFE_openDirectory(path)
    return
  }

  // On macOS a directory might also be an app bundle and if it is
  // and we attempt to open it we're gonna execute that app which
  // it far from ideal so we'll look up the metadata for the path
  // and attempt to determine whether it's an app bundle or not.
  //
  // If we fail loading the metadata we'll assume it's an app bundle
  // out of an abundance of caution.
  const isBundle = await isApplicationBundle(path).catch(err => {
    log.error(`Failed to load metadata for path '${path}'`, err)
    return true
  })

  if (isBundle) {
    log.info(
      `Preventing direct open of path '${path}' as it appears to be an application bundle`
    )

    await _showItemInFolder(path)
  } else {
    UNSAFE_openDirectory(path)
  }
}
```
