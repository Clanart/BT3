Based on the investigation, I found a plausible analog but want to be upfront: I could not fully trace an end-to-end call graph from network/RPC input all the way into `PuzzleInfo` construction within the tool budget, so treat the "Likelihood" section as based on structural evidence, not a confirmed live exploit trace.

### Title
Unbounded recursion when parsing untrusted `PuzzleInfo`/offer driver data can crash the wallet (DoS) - (File: `chia/wallet/puzzle_drivers.py`)

### Summary
`chia/wallet/puzzle_drivers.py` implements `PuzzleInfo` (asset "driver" metadata attached to offers, CATs, NFTs, CR-CATs, etc.) using plain Python recursion with no depth bound, unlike other CLVM-adjacent parsers in this codebase which were deliberately hardened against deep-recursion DoS.

### Finding Description
`PuzzleInfo.also()` / `check_type()` and the free function `decode_info_value()` recurse into nested dictionaries/lists without any depth limit: [1](#0-0) [2](#0-1) 

`PuzzleInfo` objects are constructed directly from externally-supplied data: RPC callers can pass a `driver_dict: dict[bytes32, PuzzleInfo]` via `CreateOfferForIDs`, and offer *takers* parse a `PuzzleInfo`-bearing `driver_dict` out of an offer file supplied by the offer-making counterparty: [3](#0-2) [4](#0-3) 

Elsewhere in the same codebase, comparable untrusted-input recursion has been explicitly eliminated for exactly this reason — `sha256_treehash()` is deliberately implemented iteratively "so we don't have to worry about blowing out the python stack", and `Program.from_bytes()` is routed through the Rust parser instead of a recursive Python one: [5](#0-4) [6](#0-5) 

`PuzzleInfo`/`decode_info_value`, by contrast, has no such protection: a deeply nested `"also"` chain (the documented mechanism for chaining multiple asset drivers) or deeply nested list/dict values will recurse once per level in pure Python.

### Impact Explanation
If reachable with sufficient nesting depth, this hits Python's default recursion limit and raises `RecursionError`, which is not caught anywhere in this call path, crashing the wallet RPC request (and potentially the wallet process/thread) processing the offer or driver_dict — a spend-triggered/offer-triggered transaction-processing halt, analogous to the WBXML dissector crash in the reference CVE. This is a Medium-severity denial-of-service (crash), not fund loss.

### Likelihood Explanation
Medium-to-low confidence: `PuzzleInfo` is populated from data controlled by an offer counterparty or local RPC caller (`CreateOfferForIDs.driver_dict`, `Offer.driver_dict` parsed from a taken offer file), both of which are in-scope untrusted-input paths per the rules. I was not able to fully verify, within the available time, whether a JSON/CLVM-based nesting depth sufficient to trigger Python's default recursion limit (~1000) can be constructed and survive earlier size/format validation on the offer/streamable path before reaching `PuzzleInfo`/`decode_info_value`. This should be validated further (e.g., write a test constructing a `PuzzleInfo` with 2000+ nested `"also"` levels and confirm `RecursionError` propagates uncaught through `create_offer_for_ids`/`respond_to_offer`).

### Recommendation
Add an explicit recursion/nesting depth limit (or convert to an iterative implementation, following the pattern already used in `sha256_treehash()`) in `PuzzleInfo.also()`, `PuzzleInfo.check_type()`, and `decode_info_value()` in `chia/wallet/puzzle_drivers.py`, and reject with a clean `ValueError` instead of allowing an uncaught `RecursionError` to propagate out of offer/RPC handling.

### Proof of Concept
Conceptual (not verified end-to-end):
```python
from chia.wallet.puzzle_drivers import PuzzleInfo

info = {"type": "CAT", "tail": "0x00"}
for _ in range(5000):
    info = {"type": "CAT", "tail": "0x00", "also": info}

PuzzleInfo(info)  # constructing/`also()`-walking this should raise RecursionError
```
This structure could originate from an offer's `driver_dict` (`chia/wallet/trading/offer.py`) supplied by an offer-making counterparty and processed by `TradeManager`/`WalletRpcApi.create_offer_for_ids` / `respond_to_offer` on the taker's wallet.
