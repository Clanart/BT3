### Title
Attacker-flooded dust outputs force Serai to pay network fees exceeding their value, draining multisig funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class is a griefing loop where an unprivileged party triggers a resource-consuming operation whose cost to the attacker rounds to ~zero while the protocol pays the real cost. In Serai's Bitcoin network code, `Scanner::scan_transaction` registers every output paying to a known `script_pubkey` as a spendable `ReceivedOutput` with no minimum-value check. An attacker can send arbitrarily small outputs to Serai's Taproot address. Each such output becomes a distinct input that Serai must spend, and `SignableTransaction::new` prices the fee per input weight (`fee_per_vbyte * vbytes`), so every dust input costs more in fees than it contributes. Repeating the deposits forces Serai to burn its own balance spending attacker-owned dust, at only dust-level cost to the attacker.

### Finding Description
`Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs` matches outputs solely on `output.script_pubkey` and pushes a `ReceivedOutput` regardless of `output.value` [1](#0-0) . There is no `value >= DUST` or economic-viability filter anywhere in the receive path; `ReceivedOutput::read` similarly accepts any `TxOut` [2](#0-1) .

On the spend side, `SignableTransaction::new` computes the needed fee from transaction weight, which grows linearly with `inputs` [3](#0-2) . A single-input taproot input contributes ~58 vbytes, so at 1 sat/vbyte a dust input of <546 sats can cost more to include than it is worth, and `input_sat < payment_sat + needed_fee` causes `NotEnoughFunds` or fee consumption against Serai's balance [4](#0-3) .

The UTXO scheduler treats un-spendable-worth inputs as operating costs: when `needed_fee` returns unfulfillable or fees exceed output value, the difference is accumulated into `operating_costs` borne by the protocol [5](#0-4) . The spec confirms input-accumulation and rotation fees are charged to Serai rather than to the depositor [6](#0-5) .

### Impact Explanation
High. Every dust output an attacker sends to a registered Serai `script_pubkey` creates a UTXO Serai must eventually consolidate or spend; the fee to spend it can exceed the recovered value, so each repeat of the attack transfers a net loss to Serai's multisig balance — directly analogous to draining the VRF subscription, except the drained asset is the Bitcoin multisig itself. The attacker's cost per iteration is only dust + their own tx fee.

### Likelihood Explanation
Medium. It requires only standard, permissionless Bitcoin payments to a publicly known address — no validator collusion, no leaked keys. It does depend on attacker deposits being indexed by the scanner and the scheduler attempting to spend the resulting inputs, which is the designed flow.

### Recommendation
Enforce a minimum output value in `Scanner::scan_transaction`/`ReceivedOutput` handling (e.g., reject `output.value < DUST` or a fee-viability threshold), mirroring the report's "add a minimum cost" fix. Additionally, track economically-irrational inputs in the scheduler so that spending them is deferred or skipped when `input.value < marginal fee`, rather than paying the fee out of protocol funds.

### Proof of Concept
1. Attacker obtains Serai's P2TR `script_pubkey` (publicly visible on-chain).
2. Attacker broadcasts many transactions each creating an output of value `v < fee_to_spend(v)` to that script; `scan_transaction` yields a `ReceivedOutput` for each [7](#0-6) .
3. Scheduler eventually includes these inputs; `SignableTransaction::new` prices `needed_fee = fee_per_vbyte * vbytes` over all inputs, and the per-input weight (~58 vbytes) exceeds the dust value [8](#0-7) .
4. The deficit becomes `operating_costs` charged to Serai [9](#0-8) ; repeating indefinitely drains the multisig balance at near-zero marginal cost to the attacker.

Uncertainty: the scheduler merge/consolidation path was not fully read to confirm automatic spending of dust inputs; the finding holds as long as received outputs enter the spendable-input set, which `ReceivedOutput` and the spec's input-accumulation design indicate.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res

## Fees Incurred During Operations

While fees incurred when satisfying burn were covered above, with documentation
on how solvency is maintained, two other operating costs exists.

1) Input accumulation
2) Multisig rotations

Input accumulation refers to transactions which exist to merge inputs. Just as
there is a `max_outputs_per_tx`, there is a `max_inputs_per_tx`. When the amount
of inputs belonging to Serai exceeds `max_inputs_per_tx`, a TX merging them is
created. This TX incurs fees yet has no outputs mapping to burns to amortize
them over, accumulating operating costs.

Please note that this merging occurs in parallel to create a logarithmic
execution, similar to how outputs are also processed in parallel.

As for multisig rotation, multisig rotation occurs when a new multisig for an
external network is created and the old multisig must transfer its inputs in
order for Serai to continue its operations. This operation also incurs fees
without having outputs immediately available to amortize over.

Serai could charge fees on received outputs, deducting from the amount of
`sriXYZ` minted in order to cover these operating fees. An overt amount would be
deducted to practically ensure solvency, forming a buffer. Once the buffer is
filled, fees would be reduced. As the buffer drains, fees would go back up.
