All other view/query methods in the distribution precompile (`params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`) route through `p.validateInput(value, args, N)` which calls `pcommon.ValidateNonPayable(value)` and reverts if `value != 0`. ### Title
Distribution precompile `rewards()` view accepts value and permanently strands native token sent with the call - (File: precompiles/distribution/distribution.go)

### Summary
The `rewards(address delegator)` view method of the distribution precompile (address `0x...1007`) is callable with a non-zero `msg.value`, unlike every other view method in the same precompile, which all reject payable calls via `ValidateNonPayable`. Any wei sent along with a `rewards()` call is debited from the caller's EVM balance by the EVM value-transfer semantics but never forwarded, refunded, or otherwise accounted for by the precompile logic, permanently stranding the funds at the precompile's associated address.

### Finding Description
`Execute` dispatches `RewardsMethod` directly to `p.rewards(ctx, method, args)` without any `readOnly` staticcall check or `pcommon.ValidateNonPayable(value)` guard, and `value` isn't even passed into the function signature [1](#0-0) . Compare this to `withdrawValidatorCommission`, which explicitly guards with `ValidateNonPayable` even though it is a transaction method [6](#0-5) , and to every other view method (`params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`), all of which call `p.validateInput(value, args, N)` which internally invokes `pcommon.ValidateNonPayable(value)` [4](#0-3) [5](#0-4) . The `rewards` implementation itself only reads `args[0]` to query `DelegationTotalRewards` and packs the result; it never touches `value` [2](#0-1) .

Since Sei's EVM precompile calls treat `value` like a normal EVM call (the sei/wei is transferred to the precompile's associated account as part of the CALL semantics before `Run`/`Execute` is invoked), any `msg.value` attached to a `rewards()` call is moved into the distribution precompile's balance, and because the precompile logic does no refund (as `HandlePaymentUsei`/`HandlePaymentUseiWei` do in every payable path such as `bank.sendNative` [7](#0-6) ), that value has no way to be returned to the caller. This bug has already been identified by the codebase's own maintainers/testers, who left an explicit note about it in the integration test file rather than fixing it [3](#0-2) . Note this exact same gap (missing `ValidateNonPayable` on `rewards()`, dispatched without any guard) is present identically across essentially every legacy version of the distribution precompile (v580–v640, v65–v67).

### Impact Explanation
Any unprivileged EVM caller (an externally-owned account or a contract) can send native token (usei/wei) along with a call to `rewards(address)` on the distribution precompile. That value is irrecoverably lost/stranded at the precompile address, since the precompile does not forward, refund, or expose any mechanism to reclaim it. This is a direct, concrete loss-of-funds bug reachable by any public-RPC/EVM transaction sender, requiring no special privilege, satisfying "concrete fund loss or permanent freezing."

### Likelihood Explanation
Likelihood is high in the sense that it requires zero special conditions: any address can call `rewards()` on the well-known precompile address with a non-zero `value`, e.g. through `ethers`/web3 tooling that fails to set `value: 0` explicitly, or through a malicious frontend/contract that tricks a user into sending value with what looks like a harmless view call. There is no economic barrier beyond the value itself and no error is returned on submission (the call succeeds), so the loss is silent to the caller.

### Recommendation
Add a `pcommon.ValidateNonPayable(value)` check (consistent with every other view method in this precompile) before dispatching to `rewards()` in `Execute`, e.g.:
```go
case RewardsMethod:
    if err = pcommon.ValidateNonPayable(value); err != nil {
        return nil, 0, err
    }
    return p.rewards(ctx, method, args)
```
This should be applied to the current `precompiles/distribution/distribution.go` as well as to all legacy versions that share the same gap, to reject value-bearing calls to `rewards()` instead of silently accepting and stranding funds.

### Proof of Concept
1. Associate an EVM account with a Sei address and fund it with native token.
2. Call the distribution precompile at its EVM address (`0x...1007`) via the `rewards(address)` ABI method, e.g. using ethers.js: `distribution.rewards(delegatorSeiOrEvmAddress, { value: ethers.parseEther("1") })`.
3. Observe the transaction succeeds (status 1) and returns the expected `Rewards` struct — the call behaves exactly like a value-free call.
4. Check the caller's EVM/usei balance: it has decreased by 1 native token (plus gas), while the precompile's associated account balance has increased by 1 native token with no way for the caller (or anyone) to reclaim it via any exposed precompile method, since `rewards()` performs no bank transfer and no other method exposes a withdrawal path for value sent to this specific precompile call.
