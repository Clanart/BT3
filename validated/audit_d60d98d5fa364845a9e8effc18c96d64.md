## Finding: Certificate‑error suppression is never invalidated when the underlying certificate changes

### Summary
`suppressCertificateErrorFor(url)` adds the URL string to a `Set` that lives for the lifetime of the renderer/main process, and the corresponding `clearCertificateErrorSuppressionFor(url)` function is defined but never called anywhere in the app. Once a user clicks through the "Untrusted Server" dialog once for a given URL, GitHub Desktop will silently accept **any** certificate presented for that same URL for the rest of the session — including a completely different certificate later swapped in by a man‑in‑the‑middle.

### Finding Description
The suppression store is a plain module-level `Set<string>` keyed only by URL, with no binding to the certificate's fingerprint/public key: [1](#0-0) 

`clearCertificateErrorSuppressionFor` exists in this module but a codebase-wide search shows it is never invoked from any other file — only `suppressCertificateErrorFor` and `isCertificateErrorSuppressedFor` are used, from `app/src/lib/api.ts` and `app/src/ui/app.tsx`. There is no call site tied to account switching, repository removal/re-add, sign-out, or any other lifecycle event that would invalidate a previously trusted certificate for a URL.

Consequently, the trust decision made by the `UntrustedCertificate` dialog (`app/src/ui/untrusted-certificate/untrusted-certificate.tsx`) is remembered per-URL for the life of the process, not per-certificate. The dialog itself has no memory of which certificate (by fingerprint) the user actually approved — it only reports the certificate object at the time of the click; the suppression logic downstream discards that identity and stores just the URL string.

### Impact Explanation
If an attacker can perform a machine-in-the-middle/DNS-based interception against a GitHub Enterprise host the user has previously connected to (and accepted a self-signed/untrusted cert warning for), they can present an entirely different, attacker-controlled certificate for the exact same URL and GitHub Desktop will not show any warning — the request proceeds as if the certificate were trusted. Since these requests carry API/OAuth tokens (`app/src/lib/api.ts` is one of the suppression call sites), this can lead to credential/token exfiltration or a full MITM of the user's GitHub Enterprise traffic, silently and with zero further prompts, for the remainder of the process lifetime. Switching accounts or removing/re-adding a repository pointed at the same host does not clear the suppression, so the exposure window persists across normal user actions within the same app session.

### Likelihood Explanation
This requires the attacker to already be positioned to intercept/MITM traffic to the specific GitHub Enterprise host (e.g., via a compromised network, ARP/DNS spoofing, or a malicious proxy) — this is a real-world condition for enterprise/self-signed-cert users who are already accustomed to seeing this warning once. It doesn't require local machine access, malware, or leaked credentials; it only requires network-position control at the time of the initial "accept" and again later. It is a plausible, if non-trivial, threat model, most acute for GHE trial/internal deployments (explicitly the intended use case for this dialog, per the code's own comments).

### Recommendation
Bind suppression to the certificate's identity, not just the URL string — e.g., key the `Set` (or a `Map`) by a combination of URL and the certificate's fingerprint/public key hash (`certificate.fingerprint`), so a cert rotation on the same URL triggers a fresh prompt. Additionally, wire up `clearCertificateErrorSuppressionFor` to relevant lifecycle events (account sign-out/switch, repository removal) so stale trust decisions don't outlive the context in which they were made.

### Proof of Concept
1. Connect to a GHE instance at `https://ghe.example.com` presenting a self-signed certificate A; accept the "Untrusted Server" dialog (calls `suppressCertificateErrorFor('https://ghe.example.com')`).
2. As a MITM positioned on the network path, swap the presented certificate to a different, attacker-controlled certificate B for the same URL.
3. Trigger another request to `https://ghe.example.com` (e.g., background fetch/API call).
4. Because `isCertificateErrorSuppressedFor('https://ghe.example.com')` still returns `true` (nothing ever called `clearCertificateErrorSuppressionFor`), the `certificate-error` handling skips the dialog and the connection under certificate B proceeds without any warning to the user. [1](#0-0)

### Citations

**File:** app/src/lib/suppress-certificate-error.ts (L1-13)
```typescript
const suppressedUrls = new Set<string>()

export function suppressCertificateErrorFor(url: string) {
  suppressedUrls.add(url)
}

export function clearCertificateErrorSuppressionFor(url: string) {
  suppressedUrls.delete(url)
}

export function isCertificateErrorSuppressedFor(url: string) {
  return suppressedUrls.has(url)
}
```
