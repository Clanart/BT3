Based on my research, I did not find a Protobuf analog with confirmed memory-safety or crash impact, but I did trace one concrete instance where the exact invariant described in the report — negating a signed integer that can equal the type's minimum value without a `neg()`-style bounds check — reproduces in Protobuf's Well-Known-Type JSON encoder for `Duration`.

### Title
Unchecked negation of `INT32_MIN` `nanos` field in `Duration` JSON encoder produces incorrect/malformed output - (File: `upb/json/encode.c`, duplicated in `ruby/ext/google/protobuf_c/ruby-upb.c` and `php/ext/google/protobuf/php-upb.c`)

### Summary
`jsonenc_duration()` bounds-checks the `seconds` field of a `Duration` message but does not independently bound-check the `nanos` field before negating it. If an attacker-controlled binary payload sets `Duration.seconds == 0` and `Duration.nanos == INT32_MIN (-2147483648)` — both legal on the wire since Protobuf performs no range validation of `int32`/`int64` scalar fields at parse time — the subsequent `nanos = -nanos;` reproduces exactly the invariant failure described in the external report: negating the minimum representable signed value does not produce the intended positive magnitude.

### Finding Description [1](#0-0) 

```
static void jsonenc_duration(jsonenc* e, const upb_Message* msg, ...) {
  int64_t seconds = ...;
  int32_t nanos = ...;
  bool negative = false;

  if (seconds > 315576000000 || seconds < -315576000000 ||
      (seconds != 0 && nanos != 0 && (seconds < 0) != (nanos < 0))) {
    jsonenc_err(e, "bad duration");
  }

  if (seconds < 0) { negative = true; seconds = -seconds; }
  if (nanos < 0)   { negative = true; nanos = -nanos; }
  ...
}
```

The sign-consistency check `(seconds != 0 && nanos != 0 && (seconds < 0) != (nanos < 0))` only fires when `seconds != 0`. There is no independent range check on `nanos` (e.g., `nanos < -999999999 || nanos > 999999999`). Since the `.proto` schema comment stating `nanos` must be within `[-999999999, 999999999]` is documentation only and not wire-enforced [2](#0-1) , an attacker who controls the binary bytes for an embedded `Duration` message (a common WKT used inside application schemas) can set `seconds = 0` and `nanos = INT32_MIN`. This bypasses the sign-consistency check entirely (since `seconds == 0`), and `nanos = -nanos` on `INT32_MIN` is signed-integer-overflow UB in C and, under typical two's-complement wraparound, leaves `nanos` unchanged (still `INT32_MIN`, still negative), exactly mirroring `wfrac`'s failure where `t.neg()` on `_INT256_MIN` returns the same (wrong-signed) value instead of reverting.

This is the same class of missing invariant as the external report: an implicit unary negation (`-x`) is used instead of a checked negation, and the one input value for which negation is a no-op (the type minimum) is not special-cased or rejected.

### Impact Explanation
The immediately provable consequence is an integrity failure of the JSON-encoded output: the resulting `nanos` value fed into the fractional-seconds formatting routine is still negative and far outside the documented `[0, 999999999)` post-negation range, so the emitted duration string will not correctly represent `-2147483648` nanoseconds; downstream consumers parsing this JSON will observe a corrupted/incorrect `Duration` value. I was not able to fully verify, within the scope of this investigation, whether the downstream formatting function that consumes this out-of-range `nanos` value performs any unchecked buffer-size arithmetic based on an assumed non-negative/bounded input (which would elevate this from an output-correctness bug to a memory-safety bug) — I did not get to read the body of the nanos-formatting routine before running out of investigation budget. Absent that additional confirmation, the concretely provable impact is a data-integrity failure (silently wrong serialized value), which parallels the original report's classification (a function returning an unintended value rather than a crash).

### Likelihood Explanation
Reachability requires only that an attacker control the wire bytes of a message containing an embedded `google.protobuf.Duration` field (or a top-level `Duration`) that a victim service later serializes to JSON via the public `upb_JsonEncode` (or the equivalent PHP/Ruby native binding wrapping the same C source, per the duplicated code in `php-upb.c`/`ruby-upb.c`). Setting `seconds=0, nanos=-2147483648` is a single 6-byte varint field write and requires no schema tricks — this is well within "ordinary client sending bounded binary Protobuf."

### Recommendation
- In `jsonenc_duration`, validate `nanos` independently of `seconds`: reject (or clamp) if `nanos < -999999999 || nanos > 999999999`, mirroring the existing `IsDurationValid`/`IsTimestampValid` checks already present in `src/google/protobuf/util/time_util.cc`.
- Replace the bare `nanos = -nanos;` / `seconds = -seconds;` idiom with a checked negation that explicitly rejects (or asserts against) `INT32_MIN`/`INT64_MIN` inputs, analogous to the `neg()` fix recommended in the original report.
- Apply the same fix uniformly across `upb/json/encode.c`, `ruby/ext/google/protobuf_c/ruby-upb.c`, and `php/ext/google/protobuf/php-upb.c`, since all three contain byte-identical vulnerable logic.

### Proof of Concept
Construct a binary-encoded `Duration` message with field 1 (`seconds`, varint) absent/zero and field 2 (`nanos`, varint zigzag-free `int32`) set to `-2147483648`:
```
tag=0x10 (field 2, varint), value = zigzag-free int32 encoding of -2147483648
```
Parse this into a `Duration` via the standard binary parse API (no range validation occurs at parse time for plain `int32` fields), then call `upb_JsonEncode` (or the equivalent `Google\Protobuf\Duration::serializeToJsonString()` / Ruby `JSON.dump`) on the resulting message. I was not able to execute this PoC in this environment to confirm the exact malformed output string or to rule out a buffer-safety consequence in the nanos-formatting helper; this should be validated with an actual build/run before treating the impact as more than a data-integrity bug.               seconds <= TimeUtil::kDurationMaxSeconds)
      << "Duration seconds are outside of the valid range";

  // Make sure nanos is in the range.
  if (nanos <= -kNanosPerSecond || nanos >= kNanosPerSecond) {

    nanos = nanos % kNanosPerSecond;
  }
  // nanos should have the same sign as seconds.
  if (seconds < 0 && nanos > 0) {
    seconds += 1;
    nanos -= kNanosPerSecond;
  } else if (seconds > 0 && nanos < 0) {
    seconds -= 1;
    nanos += kNanosPerSecond;
  }

              nanos <= TimeUtil::kDurationMaxNanoseconds)
