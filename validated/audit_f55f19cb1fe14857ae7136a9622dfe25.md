### Title
Reentrancy via native-token output transfer in `_fillSameChain` lets a malicious order creator steal the solver's fill payment while also reclaiming escrowed input tokens - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` sends the native-ETH fill payment to `order.output.beneficiary` via a raw `.call` **before** the corresponding input-token escrow is decremented (escrow release happens later, inside `_withdraw`). Because `beneficiary` is attacker-controlled data on a same-chain order and can equal `order.user`, the beneficiary contract can reenter `cancelOrder` → `_cancelSameChain` during that transfer and drain the still-untouched escrow for itself, before the outer fill call gets a chance to release that same escrow to the solver.

### Finding Description
`_fillSameChain` ( [1](#0-0) ) iterates over output assets and, for native-token outputs, performs an external call to `beneficiary` at: [2](#0-1) 
immediately followed by a **storage read** of `_orders[commitment][token]` on the next lines to compute `escrowedInputs[i]` for the *input* side of the trade: [3](#0-2) 

The actual escrow **decrement** for that input token only happens afterwards, outside the loop, inside `_withdraw`: [4](#0-3) 

Meanwhile, `_cancelSameChain` is a public-reachable path gated only by `order.user == msg.sender` and a plain "is there escrow left" check — it does **not** consult `_filled[commitment]` and has no reentrancy lock: [5](#0-4) 

Attack sequence:
1. Attacker places a same-chain order where `order.user == order.output.beneficiary == <attacker contract>` and the output asset is the native token.
2. A solver calls the fill entrypoint, invoking `_fillSameChain`. The native-token transfer to the attacker's beneficiary contract at line 104 triggers the attacker's `receive()`/fallback, which reenters and calls `cancelOrder` → `_cancelSameChain`.
3. At reentry time, `_orders[commitment][inputToken]` is still fully escrowed (the fill's own `_withdraw` for the input side hasn't executed yet), so `_cancelSameChain` succeeds, refunds the full input escrow to the attacker, and zeroes `_orders[commitment][inputToken]`.
4. Execution returns to the outer `_fillSameChain`; the next line reads `_orders[commitment][inputToken]` (now zero) into `escrowedAmount`, so `escrowedInputs[i].amount == 0`.
5. `_withdraw(body, false, isFullyFilled)` is then called with `amount == 0` for that token, which is explicitly skipped (`if (amount == 0) continue;`), so no revert occurs.
6. The fill completes normally — `OrderFilled` is emitted and any attached calldata runs — even though the solver's counterpart escrow was already stolen via the reentrant cancel in step 3.

Net effect: the solver pushed the agreed native-token output to the beneficiary and received **nothing** in return (the input escrow went to the attacker twice over — once implicitly by fill completing "successfully" with zero release, and explicitly via the reentrant refund). This is a public-entrypoint, unprivileged-attacker path (no relayer, prover, or admin required) that results in loss of funds for the solver and a wrong-beneficiary transfer of the escrowed input tokens.

### Impact Explanation
This directly matches the bounty's accepted impact classes: stealing/loss of funds (solver loses its fill payment for nothing) and unauthorized/duplicate settlement of an order's escrow (the same escrow is both "released" by the fill accounting and paid out again via cancellation). The victim is any legitimate, unprivileged solver interacting with the public `IntentGatewayV2` fill entrypoint — no compromised relayer, prover, or admin is needed, satisfying the "unprivileged attacker" and "public entrypoint" requirements.

### Likelihood Explanation
The order creator fully controls `order.output.beneficiary` and `order.user` for a same-chain order, and native-token outputs are a normal, expected order shape, so constructing the malicious order is trivial. The only requirement is that the beneficiary be a contract with a payable fallback that reenters — a one-time deployment cost. The bug is purely a checks-effects-interactions violation in `_fillSameChain`/`_withdraw`, not dependent on races, external actors, or governance actions, making it reliably and cheaply exploitable by anyone willing to author a malicious order and wait for a solver to fill it.

Note: I was not able to inspect the top-level `fillOrder`/`cancelOrder` public entrypoints in `IntentGatewayV2.sol` (only the internal `_fillSameChain`/`_cancelSameChain` logic was available in the indexed context) to confirm whether a `nonReentrant` modifier is applied at that layer. Neither `IntentsBase.sol` nor `IntrinsicIntents.sol` import OpenZeppelin's `ReentrancyGuard`, which is the primary evidence for this being unguarded, but this should be verified directly against the public function definitions before treating this as fully confirmed.

### Recommendation
- Move all state updates (including the input-escrow decrement performed inside `_withdraw`) strictly before any external call (native transfer or ERC20 transfer) in `_fillSameChain`, per checks-effects-interactions.
- Add a `nonReentrant` guard (or a transient-storage reentrancy lock) to the public `fillOrder`/`cancelOrder`/`select` entrypoints that funnel into `_fillSameChain`, `_cancelSameChain`, and `_withdraw`.
- Have `_cancelSameChain` also treat an order with an in-progress/finalized `_filled[commitment]` state as terminal, rather than relying solely on the `_orders` escrow balance, to remove the dependency on ordering between escrow decrement and external calls.

### Proof of Concept
Conceptual PoC (Foundry-style), based on the cited functions:
1. Deploy `MaliciousBeneficiary` implementing `receive()` that calls `intentGateway.cancelOrder(order)` for the same `commitment` when it receives ETH.
2. Place a same-chain `Order` with `order.user = order.output.beneficiary = address(MaliciousBeneficiary)`, `output.assets[0].token = address(0)` (native), escrowing some ERC20/native `inputs[0]`.
3. A separate solver EOA calls the public fill function with `options.outputs[0].amount == totalRequired`.
4. Trace: `_fillSameChain` → native `.call` to `MaliciousBeneficiary` ( [6](#0-5) ) → reentrant `_cancelSameChain` ( [5](#0-4) ) drains `_orders[commitment][inputToken]` → outer call resumes, reads zeroed escrow ( [3](#0-2) ) → `_withdraw` skips the zero-amount release ( [7](#0-6) ) → `OrderFilled` emitted, solver receives no input tokens, attacker holds both the solver's output payment and the refunded input escrow.

    function _fillSameChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        bool isFullyFilled = true;

        TokenInfo[] memory escrowedInputs = new TokenInfo[](outputsLen);
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            uint256 alreadyFilled = _partialFills[commitment][outputToken];
            uint256 remaining = totalRequired - alreadyFilled;
            if (remaining == 0 || solverAmount == 0) {
                if (solverAmount == 0 && remaining > 0) isFullyFilled = false;
                continue;
            }
            uint256 fillAmount;

            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;
            if (alreadyFilled == 0 && solverAmount > totalRequired) {
                fillAmount = totalRequired;
                uint256 dust = solverAmount - totalRequired;
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            } else {
                fillAmount = solverAmount > remaining ? remaining : solverAmount;
            }

            uint256 amountFilled = alreadyFilled + fillAmount;
            _partialFills[commitment][outputToken] = amountFilled;
            uint256 beneficiaryTotal = fillAmount + beneficiaryShare;

            if (token == address(0)) {
                if (msgValue < beneficiaryTotal + protocolShare) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }

            if (totalRequired > amountFilled) isFullyFilled = false;
            if (protocolShare > 0) emit DustCollected(token, protocolShare);

            uint256 escrowedAmount;
            if (amountFilled == totalRequired) {
                escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
            } else {
                escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
            }
            escrowedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: escrowedAmount});
            outputFills[i] = TokenInfo({token: outputToken, amount: fillAmount});
        }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        if (orderSource != currentChain) revert WrongChain();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
