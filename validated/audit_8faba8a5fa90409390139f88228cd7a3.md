### Title
Uncontrolled recursion in wallet outer-puzzle driver matching allows a malicious offer/spend bundle to crash the wallet (`chia/wallet/outer_puzzles.py`)

### Summary
`chia.wallet.outer_puzzles.match_puzzle()` and the individual outer-puzzle drivers (`CATOuterPuzzle`, `CROuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, `SingletonOuterPuzzle`) recursively call each other once per curried "layer" found in an attacker-supplied puzzle reveal, with no depth limit. A malicious offer file or spend bundle containing a puzzle reveal with many nested layers of the same recognizable puzzle type (e.g. CAT-inside-CAT-inside-CAT…) drives unbounded Python recursion, which can exhaust the interpreter stack and crash/hang the process parsing it (wallet accepting an offer, or any code path inspecting an untrusted `CoinSpend.puzzle_reveal`). This mirrors the CVE-2018-20822 bug class: uncontrolled recursion on attacker-controlled nested structure causing denial of service.

### Finding Description
`match_puzzle()` iterates known driver types and calls `driver.match(puzzle)`: [1](#0-0) 

Each driver's `match()` method, upon recognizing its own puzzle mod, recurses back into the very same `match_puzzle` dispatcher (stored as `self._match`) to inspect the puzzle's inner layer, with no bound on recursion depth: [2](#0-1) 

Identical recursive patterns exist in the CR, ownership, metadata, and singleton outer-puzzle drivers (`self._match(UnknownPuzzle(known_program=inner_puzzle))`): [3](#0-2) [4](#0-3) 

Because a puzzle can be curried into a layered structure of arbitrary depth (e.g., `construct_cat_puzzle(CAT_MOD, tail, construct_cat_puzzle(CAT_MOD, tail, construct_cat_puzzle(...)))`, as already demonstrated in the test suite for two levels), an attacker fully controls how many recursive matching layers a wallet must traverse when it parses a supplied puzzle reveal: [5](#0-4) 

This matcher is reached from untrusted, attacker-controlled data during offer parsing. `Offer.from_spend_bundle()` runs `match_puzzle` over every `coin_spend.puzzle_reveal` in a bundle that can come from an offer file supplied by a counterparty: [6](#0-5) 

Similarly, `Offer._get_offered_coins()` calls `match_puzzle(parent_puzzle)` directly on the parent spend's `puzzle_reveal` taken from the offer's bundle when computing offered coins during trade validation: [7](#0-6) 

No recursion depth check, cost accounting, or `RecursionError` handling exists anywhere around these call chains (confirmed by repository-wide search), unlike `sha256_treehash()`, which was deliberately implemented iteratively specifically "so we don't have to worry about blowing out the python stack": [8](#0-7) 

### Impact Explanation
A counterparty can craft an offer file (or a spend bundle containing a CAT/CR-CAT/NFT-style puzzle reveal) with enough nested curry layers of a recognized outer-puzzle type to exceed Python's default recursion limit. When the victim's wallet calls `TradeManager` methods (e.g. accepting or examining the offer) or any code invoking `Offer.from_spend_bundle()` / `Offer._get_offered_coins()` / `match_puzzle()` on the untrusted puzzle reveal, this raises an uncaught `RecursionError`, halting that offer/spend-bundle-processing operation and potentially destabilizing the wallet process. This is a spend/offer-triggered processing halt, consistent with a Medium-severity DoS analog of the reported LibSass recursion bug.

### Likelihood Explanation
Constructing deeply nested curried puzzles is straightforward CLVM curry-composition (as already exercised for two levels in the test suite) and requires no special privileges — only that the victim's wallet parse an offer or spend bundle supplied by an untrusted counterparty, which is a normal, expected wallet operation (reviewing/accepting an offer).

### Recommendation
Add an explicit recursion/iteration depth bound (or convert `match_puzzle`/driver `.match()`/`.get_inner_puzzle()`/`.get_inner_solution()` chains to an iterative loop, similar to `sha256_treehash`) before traversing attacker-supplied puzzle layers, and reject or safely error out on puzzles exceeding the bound instead of letting Python's stack recursion raise uncaught exceptions.

### Proof of Concept
1. Build a puzzle reveal `P_0 = ACS` (any puzzle).
2. Recursively wrap it N times using `construct_cat_puzzle(CAT_MOD, tail, P_i)` to produce `P_N`, where N is large enough to exceed Python's recursion limit (e.g., a few thousand layers), analogous to `double_cat_puzzle` in `chia/_tests/wallet/cat_wallet/test_cat_outer_puzzle.py` but with many more layers.
3. Place `P_N` as the `puzzle_reveal` of a `CoinSpend` inside a `WalletSpendBundle`/`Offer`.
4. Call `Offer.from_spend_bundle(bundle)` or trigger `TradeManager` offer acceptance flow on the crafted offer.
5. Observe `match_puzzle()` recursing once per layer via `chia/wallet/outer_puzzles.py` / `chia/wallet/cat_wallet/cat_outer_puzzle.py`, eventually raising an uncaught `RecursionError` and aborting/crashing the offer-processing call.
