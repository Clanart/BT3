Confirmed: `CallDispatcher` at `evm/src/utils/CallDispatcher.sol` is a **single, generic, stateless-by-design contract, shared across every order** — it is stored once in `_params.dispatcher` and referenced by every call to `placeOrder`, `fillOrder`, and `_execute` across every user, in `IntentGatewayV2.sol` and `IntentsBase.sol`. It has a `receive()` that accepts ETH from anyone, and `dispatch()` will forward arbitrary calls to any contract with code, with no access control on who may call `dispatch` on it directly. This is the exact structural precondition the LiFi report describes: a persistent "vault-like" intermediate contract with no per-call balance isolation.

### Title
Predispatch/postdispatch sweeps in IntentGatewayV2 credit escrow from the full current balance of the shared `CallDispatcher`, not the delta produced by the call — (File: `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
Both `placeOrder`'s predispatch sweep and `IntentsBase._execute`'s postdispatch sweep measure the amount to credit/sweep by reading the **current total balance** of the shared `CallDispatcher` (`address(dispatcher).balance` / `IERC20(token).balanceOf(dispatcher)`), exactly the anti-pattern the LiFi report flags: no `startingBalance` is captured for the dispatcher itself before its call executes, only for the gateway's own balance after the sweep. Because `CallDispatcher` is a single shared, publicly payable, permissionless-`dispatch()` contract used by all users, any resting balance on it (attacker-sent ETH/tokens, or dust genuinely belonging to another order) is indistinguishable from output produced by the current predispatch/postdispatch call and gets folded into the current order's escrow input / dust accounting.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol:229-256`, before running the predispatch calldata, `balancesBefore[i]` is snapshotted on `address(this)` (the gateway), but the check that decides how much is "available" reads `dispatcher`'s **live balance**, not a before/after delta on the dispatcher:
```solidity
uint256 balance = address(dispatcher).balance;   // no dispatcher-side startingBalance
if (balance < requiredAmount) revert InsufficientNativeToken();
transferCalls[i] = Call({to: address(this), value: balance, data: ""});
``` [1](#0-0) 
Same pattern for ERC20: [2](#0-1) 

The equivalent postdispatch sweep in `IntentsBase._execute` unconditionally sweeps whatever balance sits on `dispatcher` after the output call, again with no pre-call snapshot on the dispatcher itself: [3](#0-2) 

`CallDispatcher` (`evm/src/utils/CallDispatcher.sol:39,44`) is a single, `receive()`-payable, permissionlessly-callable-`dispatch()` contract reused across every order via `_params.dispatcher`: [4](#0-3) 

Since `dispatch()` has no caller restriction and `receive()` accepts any ETH, anyone can pre-fund the shared dispatcher, and any inexact/partial predispatch or postdispatch swap that leaves a residual balance of a token also used as an `order.inputs[i].token`/`order.output.assets[i].token` for a *later* order will be silently absorbed into that later order's "received" sweep as escrow input, or counted as that order's dust — because the code checks only `balance >= requiredAmount` on the dispatcher's current total, never a call-scoped delta.

### Impact Explanation
This directly maps to the "startingBalance not tracked / everything present gets swept" bug class from the external report. Concretely: whatever ETH/tokens are resting on the shared dispatcher at the moment a given order's sweep executes get attributed to that order — inflating `order.inputs[i].amount` (more escrow credited than the user actually paid via `predispatch.call`) or being emitted as `DustCollected` for the wrong order/token. Because escrow crediting and dust accounting both key off the dispatcher's live balance rather than a per-call delta, value that belongs to no one in particular (attacker-donated) or to a different order's leftover gets folded into whichever order's sweep runs next, corrupting the escrow accounting that downstream cross-chain settlement (`RedeemEscrow`/`RefundEscrow`, `_withdraw` in `IntentsBase.sol:390-410`) treats as authoritative.

### Likelihood Explanation
Medium — it requires either (a) an attacker directly sending ETH/tokens to the well-known, permissionlessly-payable `CallDispatcher` address before calling `placeOrder`/triggering `fillOrder`, or (b) natural residual dust from an imprecise swap sitting on the dispatcher when the next order's predispatch/postdispatch sweep runs. No relayer, prover, or admin compromise is needed; the dispatcher address is discoverable via `IntentGatewayV2.params().dispatcher`, and `dispatch()`/`receive()` are unauthenticated. This mirrors the "in practice there is some dust" caveat in the original LiFi report — the risk is bounded by how much value typically transits or rests on the shared dispatcher, same as the original finding's medium-risk rating.

### Recommendation
Snapshot the dispatcher's own balance for each token **before** invoking the predispatch/postdispatch call (`ICallDispatcher(dispatcher).dispatch(...)`), and only sweep/credit the delta produced by that specific call, mirroring the fix pattern already used for the gateway's own balance (`balancesBefore[i] = address(this).balance` at line 241/250). Apply the same startingBalance-before/after-delta pattern in `IntentsBase._execute`'s sweep loop so unrelated resting balances on the shared `CallDispatcher` cannot be attributed to the wrong order.

### Proof of Concept
1. Read `dispatcher = IntentGatewayV2(gateway).params().dispatcher` (public getter).
2. Attacker sends `1 ETH` directly to `dispatcher` (accepted by its unrestricted `receive()`).
3. Attacker (or any user) calls `placeOrder` with `order.inputs[0] = {token: address(0), amount: 1 ether}` and a trivial `predispatch.call` that dispatches a no-op call to some contract with code (satisfying `NotContract` check) without itself producing the 1 ETH.
4. In the sweep loop, `balance = address(dispatcher).balance` reads the attacker-donated `1 ETH` (not the output of the predispatch call), passes `balance >= requiredAmount`, and the full amount is swept and credited to `order.inputs[0].amount`, letting the order's escrow be funded/inflated by value that did not originate from this order's own predispatch execution — demonstrating the missing before/after-delta check on the dispatcher side. Reproducing the equivalent flow via `fillOrder`'s `_execute` postdispatch path (`IntentsBase.sol:438-468`) with a resting balance on `dispatcher` shows the same unguarded full-balance sweep on the output side.

    function _execute(Order calldata order, uint256 outputsLen) internal {
        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
