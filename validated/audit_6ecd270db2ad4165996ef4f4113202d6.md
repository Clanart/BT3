### Title
Division by zero in `KIP71Config.NextMagmaBlockBaseFee` via ungoverned `GasTarget=0` vote - (File: `params/kip71_config.go`)

### Summary
The Magma/KIP-71 base-fee calculation `NextMagmaBlockBaseFee` divides by the governance parameter `GasTarget` without checking for zero, unlike the adjacent `BaseFeeDenominator` parameter, which has an explicit zero-fallback. Because the governance parameter registry (`kaiax/gov/param.go`) assigns `Kip71GasTarget` a `noopFormatChecker` and the header-vote consistency checker (`kaiax/gov/headergov/impl/header.go`) explicitly allows this vote with no additional bound checks, a validator/governing node can vote `GasTarget=0` into governance, and once it activates, every node's block-base-fee computation panics.

### Finding Description
`NextMagmaBlockBaseFee` in [1](#0-0)  explicitly guards against `BaseFeeDenominator == 0` by falling back to `64`, but performs no equivalent guard for `GasTarget`: [2](#0-1) 
When `parentGasUsed > gasTarget` (trivially true for any nonzero gas usage if `gasTarget == 0`), the code computes: [3](#0-2) 
`y := x.Div(x, new(big.Int).SetUint64(gasTarget))` divides by zero when `gasTarget == 0`. Go's `math/big.Int.Div` panics on division by zero (unlike the described TensorFlow CVE which is a runtime crash from unchecked op constraints — same bug class: an unchecked divisor reachable from user/validator-controlled input). The same unguarded division exists in the "gas used below target" branch as well: [4](#0-3) 

Governance-side, the parameter `Kip71GasTarget` is registered with no format validation: [5](#0-4) 
compare to `Kip71BaseFeeDenominator`, which explicitly requires `v != 0`: [6](#0-5) 
And the header-vote consistency checker explicitly whitelists `gov.Kip71GasTarget` for no-op checking beyond generic format validation: [7](#0-6) 

### Impact Explanation
Once a `GasTarget=0` vote is cast by an authorized voter (the governing node in single mode, or any council member in other governance modes per `VerifyVote`), and takes effect at the next epoch's `ParamSet`, `NextMagmaBlockBaseFee` is invoked during header preparation/validation for every subsequent block with `parentGasUsed > 0`. This causes an unrecovered panic in the block-processing path shared by all nodes, resulting in a chain-wide denial of service / consensus halt — nodes crash simultaneously rather than diverging, since the vulnerable code runs deterministically on every node during header verification (`BlockValidator.ValidateHeader` calls `VerifyMagmaHeader`, which calls `NextMagmaBlockBaseFee`).

### Likelihood Explanation
Reaching this requires a validator/governing-node-level vote, not an arbitrary transaction sender. In "single" governance mode this requires control of the governing node; in more permissionless configurations any council member could vote it. This is a higher bar than a plain unprivileged transaction, but the flaw itself — an admitted governance parameter change causing a network-wide panic — is a real gap: there is no format or consistency check preventing `GasTarget=0`, whereas the adjacent, semantically identical `BaseFeeDenominator` parameter is properly protected. This asymmetry indicates a genuine oversight rather than intentional design.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` requiring `v != 0` (mirroring `Kip71BaseFeeDenominator`), and/or add a defensive zero-check with fallback inside `NextMagmaBlockBaseFee` before dividing by `gasTarget`, analogous to the existing `baseFeeDenominator` zero-fallback.

### Proof of Concept
1. Governing node (or authorized voter) casts a vote setting `kip71.gastarget = 0`.
2. The vote passes `VerifyVote`/`checkConsistency` in [7](#0-6)  unchecked, and is committed into governance at the next epoch boundary.
3. Once active, any block with `parentGasUsed > 0` (virtually every block) triggers [3](#0-2) , calling `big.Int.Div(x, 0)`, which panics in every node computing/verifying the header's `BaseFee`, halting the chain.
