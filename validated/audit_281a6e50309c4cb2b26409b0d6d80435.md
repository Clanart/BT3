### Title
PedPoP accepts identity encryption keys, making all secret shares sent to a malicious participant publicly decryptable - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to CVE-2023-30456 (nVMX accepting guest-controlled register state without consistency checks), PedPoP accepts a participant-controlled elliptic-curve value — the per-participant encryption key in `EncryptionKeyMessage` — without checking it against a required invariant (non-identity). `EncryptionKeyMessage::read` uses `Ciphersuite::read_G`, which only enforces canonical encoding, and `Decryption::register` stores the key with no validation. The FROST `Curve::read_G` wrapper explicitly rejects identity points, proving the codebase knows this check is needed, yet the DKG encryption path omits it.

### Finding Description
Each PedPoP participant broadcasts an `EncryptionKeyMessage` carrying `enc_key`, which `Decryption::register` inserts into `enc_keys` with no validation (crypto/dkg/pedpop/src/encryption.rs:351-362). The key is read via `C::read_G` — `Ciphersuite::read_G` (crypto/ciphersuite/src/lib.rs:91-101) checks only that the encoding is canonical; it does not reject the identity point. Contrast with `Curve::read_G` in crypto/frost/src/curve/mod.rs:125-131, which adds an explicit `is_identity` rejection — a consistency check that exists for FROST but is absent here.

When a participant registers `enc_key = identity`, every honest sender encrypting a share to them computes `ecdh(ephemeral, identity) = ephemeral * identity = identity` (encryption.rs:95-97, 466). The ChaCha20 cipher key is then derived solely from `transcript(context || identity.to_bytes())` with a static IV `"DKG IV v0.2\0"` (encryption.rs:101-133). Both inputs are public constants/values, so the keystream is publicly computable by any observer, and it is identical for every sender to that participant.

The `pop` proof-of-possession on `EncryptedMessage` covers only the per-message ephemeral `key`, not the registered `enc_key`, so it does not stop this.

### Impact Explanation
Every `SecretShare` addressed to the malicious participant is encrypted under a publicly known key. Anyone who observes the ciphertexts (in Serai these are relayed/published as DKG share messages) recovers the plaintext scalar shares `share_j(l)` for all `j`, and hence the participant's full aggregated secret share. This silently reduces the effective threshold: a passive observer obtains one complete key share for free, and because the ciphertexts persist, an attacker who later compromises fewer than `t` participants reaches the threshold. It also produces keystream reuse across all senders' messages to `l`. This is a concrete key-share confidentiality break reachable purely by a participant's public DKG message.

### Likelihood Explanation
Any DKG participant can serialize an `EncryptionKeyMessage` with the identity point encoding in place of `enc_key`; deserialization and registration succeed, and no PoP or blame path detects it. The only requirement is that the attacker control one participant slot — no collusion or privileged access needed.

### Recommendation
In `EncryptionKeyMessage::read` and/or `Decryption::register`, reject identity `enc_key` values (and ideally require a proof of possession of the registered encryption key), matching the `is_identity` check already performed by `Curve::read_G`. Rejecting identity also prevents the degenerate fixed shared secret from collapsing the ChaCha20 keystream to a public constant.
