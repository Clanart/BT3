### Title
Webhook HMAC Signature Does Not Bind to Shop Domain, Enabling Cross-Shop Replay of Signed Webhook Payloads - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

### Summary
`ShopifyApp::WebhookVerification#verify_request` validates only that the HMAC over the raw request body matches a value computed from the app secret. It never includes the `X-Shopify-Shop-Domain` header (or any other domain identifier) in the HMAC computation, and `shop_domain` is read directly and unauthenticated from that header. This mirrors the H-06 root cause: a signature is computed over a payload that omits the destination/tenant-binding field, so the same valid signed payload can be replayed with a different domain identifier attached, letting an attacker route a legitimately-signed webhook body to a different shop's processing pipeline.

### Finding Description
`verify_request` computes `hmac_valid?(request.raw_post)` and, on success, allows processing to continue: [1](#0-0) 

`hmac_valid?` in `PayloadVerification` computes the HMAC purely over the raw body bytes (`data`), using the app's client secret: [2](#0-1) 

Critically, `shop_domain` is derived from a separate, unsigned header and is never included in the HMAC input: [3](#0-2) 

Downstream, `ShopifyApp::WebhooksController#receive` builds a `ShopifyAPI::Webhooks::Request` from `request.raw_post` and `request.headers.to_h` and dispatches to app-registered jobs, which trust the `shop_domain`/`shop` value taken from the (unsigned) header to select which shop's data/session to operate on: [4](#0-3) [5](#0-4) 

Because the domain/tenant identifier is excluded from the signed material, an entity capable of intercepting/replaying one previously delivered, validly-signed webhook body (analogous to a "malicious relayer" replaying signed calldata across chains) can resend that exact body while substituting a different `X-Shopify-Shop-Domain` header value. The HMAC check still passes (the body is byte-identical to what Shopify actually signed), but the downstream job now attributes the payload to an attacker-chosen shop rather than the shop the data originated from — precisely the same class of flaw as `ExecuteArgs.local`/destination domain not being covered by the signature check in the reported bug (`BridgeFacet._getTransferId` / missing `s.domain` vs `CallParams.destinationDomain` validation).

### Impact Explanation
If an attacker can capture one legitimately-signed webhook (e.g., by triggering an event on a shop they control, such as `customers/data_request`, `products/update`, or any subscribed topic, and observing/logging the raw POST body and its valid HMAC), they can replay that exact body against the app's public webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a different, victim shop. Because the signature check is domain-agnostic, the request passes verification and the job runs `Shop.find_by(shopify_domain: attacker_supplied_domain)`/equivalent business logic under the wrong shop's identity — potentially triggering privacy-webhook data actions, cache invalidation, or app-specific side effects (e.g. cache busting, uninstall/redact flows, session/webhook-triggered API calls) attributed to a shop that never actually experienced that event. This is a cross-shop confused-deputy condition triggered entirely by an unauthenticated/replay-capable actor hitting a public HTTP endpoint.

### Likelihood Explanation
The webhook endpoint is unauthenticated by design (it only relies on HMAC) and is reachable by anyone who can send an HTTP POST with the right headers/body — the only prerequisite is possession of one previously-issued, validly-signed payload for the app (obtainable by the attacker triggering a webhook on their own installed shop, or via interception in transit/logging). No secret material needs to be forged; only the unsigned header needs to be altered. This makes the likelihood moderate: it depends on the app's job/business logic actually branching meaningfully on `shop_domain`, but the underlying verification gap itself is unconditionally present in every app using `ShopifyApp::WebhookVerification`.

### Recommendation
Bind the tenant/destination identifier into the signed verification step rather than trusting it from an unsigned header:
- Verify that the `shop_domain` extracted from the header corresponds to a shop that is expected to have triggered this specific webhook body (e.g., cross-check against `webhook_id`/topic-specific data embedded in the JSON body when available), or
- Require verification via Shopify's official webhook processing (`ShopifyAPI::Webhooks::Registry.process`) end-to-end without also independently trusting `request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]` for authorization decisions in generated job templates, and
- At minimum, document/enforce that consumers must treat `shop_domain` as verified only insofar as it matches shop-identifying fields inside the (HMAC-covered) JSON body itself, never solely the header, mirroring the fix pattern from the referenced report (bind destination context into what is actually verified/signed).

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com` and trigger a webhook topic the app subscribes to (e.g. `products/update`). Capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent — this HMAC is valid per `PayloadVerification#hmac_valid?` since it's exactly what Shopify signed.
2. Replay this exact same body and HMAC header to `POST /webhooks/:type` (the app's webhook endpoint), but change the `X-Shopify-Shop-Domain` header to `victim.myshopify.com`.
3. `WebhookVerification#verify_request` ( [6](#0-5) ) validates the HMAC solely against `request.raw_post`, which passes because the body is unchanged.
4. `WebhooksController#receive` ( [7](#0-6) ) forwards the request headers (including the forged shop domain) to the registered job, which processes/attributes the event to `victim.myshopify.com` instead of `attacker.myshopify.com`.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
