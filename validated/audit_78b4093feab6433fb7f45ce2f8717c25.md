### Title
Aggregate Schnorr signature forgery via aggregation weight not bound to nonces/keys - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` derives the per-signature aggregation weights `z_i` from a transcript that commits only to the challenges (`keys_and_challenges`), never to the aggregate's `Rs` or the public keys. Because the weights are fully computable before choosing `R`, an attacker can produce a valid `SchnorrAggregate` for a victim's public key and any challenge — i.e., forge an aggregate signature "for free". This is the Serai analog of the "no lower bound on output" bug class: the verifier places no binding constraint on the critical adversary-chosen value (`R`), so an attacker can push it to an algebraically degenerate choice (`R = r·G − c·K`).

### Finding Description
In `crypto/schnorr/src/aggregate.rs`, the aggregation weight function is:

```rust
digest.domain_separate(b"signatures");
for (_, challenge) in keys_and_challenges {
  digest.append_message(b"challenge", challenge.to_repr());
}
// z_i = weight(&mut digest) drawn sequentially from this digest
```

`verify` then checks `Σ z_i·(R_i + c_i·K_i) − s·G = 0` via `multiexp_vartime` (lines 127–145).

The half-aggregation scheme of eprint 2021/350 (cited on line 67) requires the weight `z_i` to be unpredictable *and* bound to the full statement — including `R_i` and the key — precisely so the adversary cannot choose `R_i` adaptively after knowing `z_i`. Here the digest commits only to the challenges. `keys_and_challenges` is supplied by the verifier caller and `Rs` come from the attacker-controlled `SchnorrAggregate` itself (`SchnorrAggregate::read`, lines 77–88, reads arbitrary `Rs` and `s` via `C::read_G`/`C::read_F` from untrusted bytes). An unprivileged party who reaches `verify` can therefore compute every `z_i` in advance, then solve for `R_i` and `s`.

### Impact Explanation
Any consumer that verifies a `SchnorrAggregate` built over `(key, challenge)` pairs where challenges bind meaningful messages will accept a forged aggregate for a victim public key `K` it does not control: set `R = r·G − c·K` and `s = z·r`. Since `z(R + cK) = z·r·G = s·G`, verification returns true. This yields a forged Schnorr signature under an arbitrary victim key — a complete break of unforgeability for any protocol using this aggregate verifier (e.g., batched/coordinator-level signature checks). Severity: High/Critical.

### Likelihood Explanation
- `SchnorrAggregate::read` (lines 77–88) is an untrusted-bytes entry point in scope; any peer can submit arbitrary `Rs`/`s`.
- The forgery requires no secret material and no interaction: the attacker only needs the victim's public key `K` and the challenge `c` under which the victim was supposed to sign. Forging costs one scalar multiply and one point subtraction per statement.
- The only mitigating factor is whether callers feed challenges that bind the `R` independently (the doc comment on lines 119–125 shifts challenge-crafting responsibility to the caller). But even a well-formed per-signature challenge `c = H(K, R, m)` does not save this: the attacker can't pick `c` freely for the victim's `R`, yet for a single aggregate member the attacker controls the reported `R`, and `c` is supplied externally — for any `(K, c)` pair where `c` is fixed by the protocol (e.g., batch of distinct messages/keys), the attack works whenever the challenge is not itself a function of the aggregate's reported `R`. In the intended batch use (many `(K_i, c_i)` with `c_i` binding distinct pre-set messages), the attack is unconditional.

### Recommendation
Bind the nonces and public keys into the weight transcript before deriving any `z_i`. In `SchnorrAggregate::verify` and symmetrically in `SchnorrAggregator`/`complete`:

```rust
let mut digest = DigestTranscript::<C::H>::new(dst);
digest.domain_separate(b"signatures");
for ((key, challenge), R) in keys_and_challenges.iter().zip(&self.Rs) {
  digest.append_message(b"key", key.to_bytes());
  digest.append_message(b"nonce", R.to_bytes());
  digest.append_message(b"challenge", challenge.to_repr());
}
```

so `z_i` cannot be known until all `R_i` are fixed. `SchnorrAggregator::aggregate` must accumulate `(challenge, key, R)` into the digest in the same order, which requires storing keys alongside signatures (or taking `(key, challenge, sig)` at aggregation time). This restores the binding required by the referenced 2021/350 construction.

### Proof of Concept
```
Given: victim public key K, challenge c (as supplied to verify), dst.
1. Attacker computes z:
     digest = DigestTranscript::<C::H>::new(dst);
     digest.domain_separate(b"signatures");
     digest.append_message(b"challenge", c.to_repr());
     z = weight::<_, C::F>(&mut digest);   // fully public computation
2. Attacker picks random r, sets R = r·G − c·K, s = z·r.
3. Attacker submits SchnorrAggregate { Rs: [R], s } (serialized via ::read path).
4. verify computes pairs [(z, R), (z·c, K), (−s, G)]:
     multiexp = z·R + z·c·K − s·G
              = z·(r·G − c·K) + z·c·K − z·r·G
              = 0  → returns true.
```
The forged aggregate verifies for a key the attacker does not control, because `z` was derivable before `R` was fixed. [1](#0-0) [2](#0-1) [3](#0-2)

  pub fn aggregate(&mut self, challenge: C::F, sig: SchnorrSignature<C>) {
    self.digest.append_message(b"challenge", challenge.to_repr());
    self.sigs.push(sig);
  }

  /// Complete aggregation, returning None if none were aggregated.
  pub fn complete(mut self) -> Option<SchnorrAggregate<C>> {
    if self.sigs.is_empty() {
      return None;
    }

    let mut aggregate = SchnorrAggregate { Rs: Vec::with_capacity(self.sigs.len()), s: C::F::ZERO };
    for i in 0 .. self.sigs.len() {
      aggregate.Rs.push(self.sigs[i].R);
      aggregate.s += self.sigs[i].s * weight::<_, C::F>(&mut self.digest);
    }
    Some(aggregate)
  }
