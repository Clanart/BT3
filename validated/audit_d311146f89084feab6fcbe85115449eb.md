## Finding: Inconsistent IPC sender validation — `app-window.ts` / `crash-window.ts` register raw `ipcMain` listeners that bypass the app's own `isTrustedIPCSender` guard

### Title
IPC sender-validation hook is inconsistently applied across main-process modules, allowing untrusted `WebContents` to reach privileged handlers - (File: `app/src/main-process/app-window.ts`, `app/src/main-process/crash-window.ts`)

### Summary
The report's underlying bug class is: **a security invariant (a hook/interface contract) is enforced correctly in one implementation but a sibling implementation that is supposed to cooperate with it uses a different, incompatible mechanism, silently breaking the guarantee.** In Desktop, the analogous invariant is *"every IPC message must be validated against `isTrustedIPCSender` before being handled,"* which is implemented once, centrally, in `app/src/main-process/ipc-main.ts`, but is not applied uniformly across the codebase.

### Finding Description
Desktop's own module `app/src/main-process/ipc-main.ts` wraps `ipcMain.on`/`once`/`handle` in a `safeListener` that checks `isTrustedIPCSender(event.sender)` before invoking any handler: [1](#0-0) [2](#0-1) 

`main.ts` correctly imports this wrapper (`import * as ipcMain from './ipc-main'`) so every handler registered there is validated: [3](#0-2) 

However, `app-window.ts` (and `crash-window.ts`) register IPC listeners directly against Electron's raw `ipcMain`, not through the safe wrapper, for channels such as `renderer-ready` and `update-window-background-color`: [4](#0-3) [5](#0-4) 

These raw `ipcMain.on`/`once` calls never call `isTrustedIPCSender`, so they process the message from **any** `WebContents` in the process, not just the one that was explicitly added via `addTrustedIPCSender`: [6](#0-5) 

This is structurally identical to the report's bug: two "hook consumers" (`ipc-main.ts`'s safe wrapper and `app-window.ts`/`crash-window.ts`'s raw registrations) are meant to share the same trust contract, but one was implemented differently (forked/refactored without carrying over the validation), so the protection silently does not apply to some code paths — exactly like `ZLRewardsController.handleActionAfter` not being invoked by tokens that call `handleAction`.

### Impact Explanation
`ipcMain.on`/`once` is process-global — it is not scoped to a particular `BrowserWindow`. Any additional `WebContents` created in the same renderer process space (e.g., a secondary window used for sign-in/OAuth flows that loads an external/attacker-influenced page, a popup, or a compromised extension/devtools context) that is not on the `trustedSenders` allow-list can still successfully deliver `renderer-ready` or `update-window-background-color` messages to these raw listeners, because they never call `isTrustedIPCSender`. This defeats the sender-validation defense that Electron's security guidelines (referenced directly in `trusted-ipc-sender.ts`) recommend, and that the rest of the app enforces. While the currently wired channels (`renderer-ready`, `update-window-background-color`) have limited direct impact by themselves, the structural gap means any future/side window content that is not fully trusted can influence main-process state through these unguarded IPC channels — undermining the process-isolation boundary that the trusted-sender allow-list is supposed to guarantee.

### Likelihood Explanation
This does not require local/physical access, admin rights, or pre-existing malware — it only requires a secondary `WebContents` (any window loading non-fully-trusted content, e.g., an OAuth/sign-in popup) to reach these already-registered, unguarded main-process listeners, which is consistent with the valid-impact scope (attacker-controlled content reaching a privileged process boundary). The likelihood is moderate: it depends on whether any non-trusted `WebContents` in the running app can actually execute `ipcRenderer.send`/`sendSync` (e.g., via a preload script or a window not fully sandboxed), which I could not fully confirm within the available tool budget — the exact preload/contextIsolation configuration of secondary windows (e.g., sign-in dialogs) was not verified.

### Recommendation
Route all `ipcMain` registrations in `app-window.ts` and `crash-window.ts` (and any other main-process module) through the shared `app/src/main-process/ipc-main.ts` wrapper instead of importing Electron's `ipcMain` directly, so `isTrustedIPCSender` is enforced uniformly for every IPC channel, matching the report's recommendation to "update the hook" so all callers use the same, correct interface/contract.

### Proof of Concept
Not independently reproduced end-to-end; this is a code-level structural finding. Conceptually:
1. Any `BrowserWindow`/`WebContents` is created in the app that is not passed to `addTrustedIPCSender` (e.g., a secondary/auxiliary window).
2. That window's renderer calls `ipcRenderer.send('update-window-background-color', color)` or `ipcRenderer.once('renderer-ready', ...)`-triggering events.
3. Because `app-window.ts` registers these listeners via raw `ipcMain.on`/`once` (not the `isTrustedIPCSender`-checked wrapper), the handler executes regardless of sender trust, unlike every channel registered in `main.ts`.

**Caveat:** I could not verify within the available exploration budget whether any currently-shipped secondary window exposes `ipcRenderer` to non-trusted/attacker-influenced content (this would require inspecting each `BrowserWindow` creation site's `webPreferences`/preload scripts, e.g. for the OAuth sign-in flow), so the full exploit chain from "attacker-controlled content" to concrete impact is not fully confirmed from the code I was able to read.

function safeListener<E extends IpcMainEvent | IpcMainInvokeEvent, R>(
  listener: (event: E, ...a: any) => R
) {
  return (event: E, ...args: any) => {
    if (!isTrustedIPCSender(event.sender)) {
      log.error(
        `IPC message received from invalid sender: ${event.senderFrame?.url}`
      )
      return
    }

    return listener(event, ...args)
  }
}

```typescript
import { WebContents } from 'electron'

// WebContents id of trusted senders of IPC messages. This is used to verify
// that only IPC messages sent from trusted senders are handled, as recommended
// by the Electron security documentation:
// https://github.com/electron/electron/blob/main/docs/tutorial/security.md#17-validate-the-sender-of-all-ipc-messages
const trustedSenders = new Set<number>()

/** Adds a WebContents instance to the set of trusted IPC senders. */
export const addTrustedIPCSender = (wc: WebContents) => {
  trustedSenders.add(wc.id)
  wc.on('destroyed', () => trustedSenders.delete(wc.id))
}

/** Returns true if the given WebContents is a trusted sender of IPC messages. */
export const isTrustedIPCSender = (wc: WebContents) => trustedSenders.has(wc.id)
```
