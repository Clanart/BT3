Based on my investigation, the core technical claim is confirmed but the actual exploitable impact differs from how the question frames it — the missing binding does not let an unprivileged attacker capture the vault's BTC for themselves (Reimburse always pays a specific pre-registered operator's `operator_reimbursement_address`, which an unprivileged attacker never controls), but it does allow an unprivileged withdrawer to falsely attribute an unfunded payout to an arbitrary, non-colluding operator.

### Title
Bridge circuit and payout attribution never bind the payout output value to the registered withdrawal amount, letting an unprivileged withdrawer trigger reimbursement for an operator that never paid - ([File: circuits-lib/src/bridge_circuit/mod.rs])

### Summary
`bridge_circuit`'s `verify_storage_proofs` step only checks that the payout transaction's referenced input matches the withdrawal outpoint's `txid`/`vout`; it never compares any output value in `payout_spv.transaction` to the withdrawal's registered `bridge_amount`. Combined with the fact that operator attribution for a payout is taken verbatim, unauthenticated, from the payout's OP_RETURN data, an unprivileged withdrawer can self-author and self-fund a payout transaction that spends their own registered withdrawal outpoint, pays a negligible amount to their own output, and embeds an arbitrary operator's `xonly_pk`, causing that operator's own automation to claim a full `bridge_amount` reimbursement for a payment it never made.

### Finding Description
The broken binding: `sum(payout output value paid to withdrawer script) == bridge_amount for that withdrawal` is never asserted anywhere in the reachable path.

In `circuits_lib::bridge_circuit::bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs`), the only checks tying the payout transaction to the withdrawal are: [1](#0-0) 
which validate `txid`/`vout` equality only — no output value or script check exists anywhere in the function, and `get_first_op_return_output` (used to derive `operator_xonlypk` for `deposit_constant`) merely reads OP_RETURN bytes with no signature or authentication: [2](#0-1) 

The same unauthenticated OP_RETURN-derived attribution is used off-circuit, in `Verifier::update_finalized_payouts`, to assign `payout_payer_operator_xonly_pk` to whichever payout transaction spends a tracked withdrawal outpoint: [3](#0-2) 

That DB column then drives `PayoutCheckerTask::run_once`, which runs autonomously on each operator's own node and, upon finding an "unhandled payout" tagged with its own `xonly_pk`, immediately proceeds to kickoff/reimbursement without ever checking that the operator itself broadcast or funded the transaction: [4](#0-3) 

An unprivileged attacker who is also a legitimate withdrawer controls the private key of their own registered withdrawal outpoint (a dust UTXO, e.g. 550 sats in the test harness) and can freely choose the sighash flag on a brand-new self-authored signature for that outpoint — Clementine's own `SinglePlusAnyoneCanPay` enforcement in `parse_withdrawal_sig_params` only constrains signatures submitted *through Clementine's gRPC*, not transactions the attacker broadcasts directly to Bitcoin: [5](#0-4) 

Exploit flow: the attacker (1) registers a withdrawal on Citrea for `bridge_amount`, (2) crafts and broadcasts their own transaction spending the registered withdrawal outpoint, paying a trivial amount (e.g. 1000 sats) to their own withdrawer script, and embeds an arbitrary operator's `xonly_pk` in an OP_RETURN output, (3) once mined and SPV-included, `update_finalized_payouts` attributes this as "operator X paid this withdrawal," (4) operator X's own `PayoutCheckerTask` autonomously proceeds through kickoff and eventually `Reimburse`, paying operator X the full `move_txhandler` deposit value (`bridge_amount`) from the vault: [6](#0-5) 
— despite operator X never having sent any BTC to the withdrawer.

Existing guards fail because: `verify_storage_proofs`/SPV verification only proves *chain inclusion* of the txid/vout reference, not amount; `SECP.verify_schnorr` checks in `operator.rs::withdraw` and `aggregator.rs::optimistic_payout` are only exercised when the *operator itself* constructs a payout through Clementine's RPCs, not when an attacker self-authors and independently broadcasts a transaction; and no code path re-derives or asserts that the operator named in the payout OP_RETURN actually supplied any of the transaction's value.

### Impact Explanation
This matches the Critical category "an operator reimbursed for a payout it never funded." The vault UTXO (`move_txhandler` output, value = `bridge_amount`) is spent to the named operator's `operator_reimbursement_address` with no economic input from that operator. Note this does **not** let the attacker capture bridge funds for themselves (Reimburse pays a pre-registered operator address the attacker does not control), and it does not directly increase attacker's own balance — the attacker's own withdrawal remains underpaid (self-inflicted). The blast radius is per-withdrawal and repeatable across deposits/withdrawals and against any operator whose `xonly_pk` is publicly known (all operator keys are published via `GetXOnlyPublicKey`/`GetParams`).

### Likelihood Explanation
Preconditions: attacker needs only to be a legitimate withdrawer with a registered withdrawal (any user can call Citrea's withdraw), a Bitcoin wallet able to sign an arbitrary S+AP-or-other-sighash transaction over their own dust UTXO, and enough sats to fund fees for their own transaction (cheap, no bridge-amount capital required). No verifier, operator or aggregator collusion required. It is trivially repeatable for every withdrawal the attacker creates and for every operator whose xonly public key is known (which is all operators, by protocol design).

### Recommendation
In `bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs`), after locating `first_op_return_output`, assert that the payout's paid output(s) to the withdrawer's registered `output_script_pubkey` sum to the withdrawal's registered `output_amount`/`bridge_amount` (both obtained via the same storage-proof path already used for `user_wd_outpoint`/`vout`), and commit this checked amount (or its equality) into the journal so downstream disprove/reimburse logic cannot diverge from the value actually delivered to the withdrawer.

pub fn parse_withdrawal_sig_params(
    params: WithdrawParams,
) -> Result<(u32, taproot::Signature, OutPoint, ScriptBuf, Amount), Status> {
    let mut input_signature =
        taproot::Signature::from_slice(&params.input_signature).map_err(|e| {
            Status::invalid_argument(format!("Can't convert input to taproot Signature - {e}"))
        })?;

    // If the Taproot sighash type is Default (no explicit type attached; i.e. a 64-byte
    // signature without a sighash flag), normalize it to SinglePlusAnyoneCanPay.
    // Prior to v0.5 this was Clementine's implicit behavior; we retain it here for
    // backwards compatibility when a 64-byte signature is provided.
    if input_signature.sighash_type == TapSighashType::Default {
        tracing::warn!(
            "Input signature for withdrawal {} has sighash type default, setting to SinglePlusAnyoneCanPay", params.withdrawal_id,
        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }
