### Title
Out-of-gas-free DoS via unbounded `TxSignatures` array processed before signature-count limit is enforced - ([File: blockchain/types/transaction.go], [File: blockchain/types/tx_signatures.go], [File: blockchain/tx_pool.go])

### Summary
`tx.ValidateSender()`, invoked from `TxPool.validateTx` for every incoming transaction (reachable by any unprivileged public-RPC caller via `eth_sendRawTransaction`), recovers a public key for **every** signature in the transaction's `TxSignatures` slice via `SenderPubkey` → `RecoverTxPubkeys` → `TxSignatures.RecoverPubkey`, before the account-key's `MaxNumKeysForMultiSig` (10) bound is checked.

### Finding Description
`TxPool.validateTx` calls: [1](#0-0) 

which dispatches to `Transaction.ValidateSender`: [2](#0-1) 

Here, `SenderPubkey(signer, tx)` is called **before** `accKey.SigValidationGas(...)` is checked. `SenderPubkey` calls `RecoverTxPubkeys`, which calls `TxSignatures.RecoverPubkey`: [3](#0-2) 

This loop performs one `ecrecover`-class elliptic-curve signature-recovery operation for **every element** of the `TxSignatures` slice with no upper bound check on `len(t)`. The `MaxNumKeysForMultiSig = 10` bound is only enforced later, inside `AccountKeyWeightedMultiSig.SigValidationGas`, and only if `numKeys > MaxNumKeysForMultiSig` on the *account's registered key* — it does not bound the number of *signatures the attacker attaches to the transaction itself*: [4](#0-3) 

Crucially, nothing in the RLP decode path or in `TxPool.validateTx` bounds `len(tx.RawSignatureValues())` before the expensive `RecoverPubkey` loop runs. The only size-based rejection prior to this call is `MaxTxDataSize`, which limits payload size but not signature-array cardinality specifically — since signatures are cheap to encode (a signature is only ~3 small integers), an attacker can pack thousands of bogus (V,R,S) tuples into the signatures field while staying under `MaxTxDataSize`: [5](#0-4) 

Because `validateTx` runs for every transaction submitted to the pool (including those that will ultimately be rejected for other reasons, e.g. insufficient balance or an invalid account key), an attacker never needs a valid signature or sufficient balance to trigger the expensive recovery loop — the transaction is never included in a block and no gas is ever paid for the wasted computation.

### Impact Explanation
A single unprivileged RPC caller can submit a transaction whose `TxSignatures` array contains an arbitrarily large number of forged (V,R,S) tuples. Each is fed to elliptic-curve public-key recovery inside `TxSignatures.RecoverPubkey`/`RecoverTxPubkeys`/`SenderPubkey`, causing the node's mempool-validation path (`TxPool.validateTx`) to perform thousands of expensive cryptographic operations per submitted transaction, with **zero gas cost** to the attacker since the transaction is rejected in the pool before any fee is charged. Submitted repeatedly (or via `eth_sendRawTransaction`/gossip), this degrades CPU capacity of nodes performing tx-pool admission, which underlies gas/computation-cost metering guarantees for the pool-admission path (every transaction admitted to the pool is supposed to cost bounded validation effort proportional to a bounded/gas-metered signature count).

### Likelihood Explanation
High reachability: any public RPC caller (no special role, no balance, no valid account key required) can construct and submit such a transaction. Constructing it requires only appending extra signature tuples to the RLP-encoded signatures list of any transaction type; no cryptographic validity of the extra signatures is required since `RecoverPubkey` will just return an arbitrary recovered key (or fail cleanly after doing the recovery work) — the computational cost is paid regardless of correctness. Since `MaxTxDataSize` bounds bytes and each signature is small, a large number of forged signatures fits comfortably within existing size limits.

### Recommendation
Enforce a strict upper bound (e.g. `accountkey.MaxNumKeysForMultiSig`, matching the maximum number of keys any account can ever have) on the length of `TxSignatures`/`FeePayerSignatures` immediately after RLP decoding or as the very first check in `TxPool.validateTx`/`Transaction.ValidateSender`, before any call to `SenderPubkey`/`RecoverTxPubkeys`. This mirrors the referenced Sherlock finding's "add a limit on the array length and revert early" recommendation, but here applied to bound expensive per-signature EC-recovery work rather than gas accounting in a Solidity loop.

### Proof of Concept
1. Craft any valid transaction type (e.g. `TxTypeValueTransfer`).
2. Instead of signing normally, construct `TxSignatures` as a slice of, e.g., 5,000 arbitrary `(V, R, S)` triples (can reuse a single valid signature repeated, or random values — validity doesn't matter, only length).
3. RLP-encode and submit via `eth_sendRawTransaction` (or directly to `TxPool.AddRemote`).
4. `TxPool.validateTx` → `tx.ValidateSender` → `SenderPubkey` → `RecoverTxPubkeys` → `TxSignatures.RecoverPubkey` iterates over all 5,000 entries performing `ecrecover`-equivalent work per entry before any signature-count/account-key check rejects the transaction.
5. Repeat rapidly from a single sender/multiple senders with no balance requirement to consume node CPU across many mempool-admission calls at zero cost, since the tx is ultimately rejected without ever being charged gas. [3](#0-2) [6](#0-5) [7](#0-6)

// ValidateSender finds a sender from both legacy and new types of transactions.
// It returns the senders address and gas used for the tx validation.
func (tx *Transaction) ValidateSender(signer Signer, p AccountKeyPicker, currentBlockNumber uint64) (uint64, error) {
	if tx.IsEthereumTransaction() {
		addr, err := Sender(signer, tx)
		// Legacy transaction cannot be executed unless the account has a legacy key.
		if p.GetKey(addr).Type().IsLegacyAccountKey() == false {
			return 0, kerrors.ErrLegacyTransactionMustBeWithLegacyKey
		}
		tx.mu.Lock()
		if tx.validatedSender == (common.Address{}) {
			tx.validatedSender = addr
			tx.validatedFeePayer = addr
		}
		tx.mu.Unlock()
		return 0, err
	}

	pubkey, err := SenderPubkey(signer, tx)
	if err != nil {
		return 0, err
	}
	txfrom, ok := tx.data.(TxInternalDataFrom)
	if !ok {
		return 0, errNotTxInternalDataFrom
	}
	from := txfrom.GetFrom()
	accKey := p.GetKey(from)

	gasKey, err := accKey.SigValidationGas(currentBlockNumber, GetRoleTypeForValidation(tx.Type()), len(pubkey))
	if err != nil {
		return 0, err
	}

func (t TxSignatures) RecoverPubkey(txhash common.Hash, homestead bool, vfunc func(*big.Int) *big.Int) ([]*ecdsa.PublicKey, error) {
	var err error

	pubkeys := make([]*ecdsa.PublicKey, len(t))
	for i, s := range t {
		pubkeys[i], err = s.RecoverPubkey(txhash, homestead, vfunc)
		if err != nil {
			return nil, err
		}
	}

	return pubkeys, nil
}

func (a *AccountKeyWeightedMultiSig) SigValidationGas(currentBlockNumber uint64, r RoleType, numSigs int) (uint64, error) {
	numKeys := uint64(len(a.Keys))
	if numKeys > MaxNumKeysForMultiSig {
		logger.Warn("validation failed due to the number of keys in the account is larger than the limit.",
			"account", a.String())
		return 0, kerrors.ErrMaxKeysExceedInValidation
	}
	if numKeys == 0 {
		logger.Error("should not happen! numKeys is equal to zero!")
		return 0, kerrors.ErrZeroLength
	}

	isIstanbul := fork.Rules(new(big.Int).SetUint64(currentBlockNumber)).IsIstanbul
	if isIstanbul {
		return uint64(numSigs-1) * params.TxValidationGasPerKey, nil
	}
	return (numKeys - 1) * params.TxValidationGasPerKey, nil
}
