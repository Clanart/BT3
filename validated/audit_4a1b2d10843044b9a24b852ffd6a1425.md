### Title
Trampoline credential-helper access (`DESKTOP_TRAMPOLINE_TOKEN`/`GIT_CONFIG_PARAMETERS`) is not revoked/scoped away from untrusted subprocesses spawned while processing a cloned/fetched repository, unlike hooks - (File: `app/src/lib/trampoline/trampoline-environment.ts`, `app/src/lib/git/spawn.ts`, `app/src/lib/hooks/hooks-proxy.ts`)

### Summary
The Sherlock finding is about an approval (`safeApprove`) that is granted to an untrusted `target` to let it pull funds, and is never reset to zero afterwards, so the untrusted party can reuse the still-live authorization outside the intended single-use flow. The structural analog in GitHub Desktop is the "trampoline" credential-helper channel: for every git operation Desktop grants the *entire process tree* of that git invocation a live credential/askpass channel back into Desktop (via `DESKTOP_PORT`, `DESKTOP_TRAMPOLINE_TOKEN`, and `GIT_CONFIG_PARAMETERS='credential.helper=desktop'`), and this authorization is intentionally *not* scoped to the specific remote endpoint the user is authenticating against — any process in that tree can request a credential for an arbitrary `host`, and the trampoline hands back the real signed-in GitHub account token if the host matches a known account. Desktop only "resets"/strips this authorization for one specific class of untrusted-repo-spawned process — hooks — via an explicit allowlist. It does not do so for other git-spawned subprocesses (filters, LFS smudge/clean, etc.) that also execute while operating on an attacker-controlled repository.

### Finding Description
`withTrampolineEnv` (app/src/lib/trampoline/trampoline-environment.ts:93-147) builds the environment for every remote git operation and always injects: [1](#0-0) 

`spawnGit`/`git()` merge this env into the *whole* environment of the spawned git process (app/src/lib/git/spawn.ts:27-37, app/src/lib/git/core.ts:277-295): [2](#0-1) 

Git subprocesses that git itself spawns during that operation (filter drivers, credential helpers invoked by extensions such as Git LFS, submodule commands, etc.) inherit this full environment by default, including `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` and the `credential.helper=desktop` configuration — the code comment even states this is deliberate "because we want commands invoked by filters (i.e. Git LFS) to be able to pick up our configuration": [3](#0-2) 

The credential handler that answers requests coming through that channel decides which stored account/token to hand back purely from the `host`/`url` fields supplied in the request (`getCredentialUrl`, `getGitHubCredential`, `findGitHubTrampolineAccount`) — it does not verify that the requesting host matches the remote URL of the operation actually being performed: [4](#0-3) [5](#0-4) 

Contrast this with hooks: Desktop is fully aware this channel must not reach code driven by *tracked, attacker-controlled repository content*, so `hooks-proxy.ts` explicitly filters the environment passed to hooks down to a `GIT_`/`GITHEAD_` allowlist and additionally excludes `GIT_CONFIG_PARAMETERS`, `GIT_ASKPASS`, `GIT_SSH_COMMAND`, `GIT_USER_AGENT` before running the hook: [6](#0-5) [7](#0-6) 

No equivalent stripping exists for other git-spawned subprocesses that run while Desktop is cloning/fetching/checking out a repository whose content (e.g. `.gitattributes`/`.lfsconfig` defined filters) is fully attacker-controlled. In other words, the "approval" (access to the trampoline's `credential.helper=desktop`) that Desktop grants for the duration of a git operation is reset/removed for the one path Desktop recognized as untrusted (hooks) but is left live and un-scoped for the rest of the process tree spawned during the same operation.

### Impact Explanation
If an attacker-controlled repository can cause git to spawn a subprocess during clone/fetch/checkout that inherits the full environment (a filter/clean-smudge driver, an LFS extension, etc.), that subprocess can speak the git credential-helper protocol against the still-live trampoline connection and request credentials for an arbitrary host string. If the host matches a signed-in account (e.g. `github.com`/GHE), the trampoline will hand back the user's real OAuth token via `credWithAccount`, giving the untrusted content a copy of the user's GitHub credentials — a credential-exfiltration outcome squarely in scope (attacker controls a cloned/fetched repository → token exfiltration).

### Likelihood Explanation
Medium/low-confidence: the environment-inheritance and unscoped credential lookup are directly confirmed in this codebase, and the explicit design comment confirms filters (LFS) are meant to receive this configuration. However, fully weaponizing this requires an attacker-controlled repository to get git/LFS to actually issue a `git credential fill` request for `host=github.com` while exfiltrating the returned value to an attacker server — that final step depends on external Git/Git-LFS behavior (e.g. `.lfsconfig` / filter driver configuration semantics) that is not implemented in this repository and could not be verified here. The core, verifiable defect is the asymmetry: this channel is explicitly sanitized for hooks but not for any other git-spawned subprocess.

### Recommendation
Apply the same allowlist/exclusion approach used in `hooks-proxy.ts` to any environment inherited by non-Desktop-initiated git subprocesses more broadly, or bind the trampoline credential responses to the endpoint of the remote actually being operated on (validate the requested host/URL against the operation's `remoteUrl` passed into `envForRemoteOperation`) rather than trusting the `host`/`url` fields supplied by the requesting process. At minimum, avoid propagating `GIT_CONFIG_PARAMETERS` (which enables `credential.helper=desktop`) and `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` into subprocesses spawned to process untrusted repository content that isn't explicitly required to authenticate (filters, LFS extensions), mirroring the exclusion list already applied to hooks.

### Proof of Concept
Not independently reproducible from this codebase alone: reproducing the end-to-end exfiltration requires driving real Git/Git-LFS filter invocation behavior (external binaries not present in this repo) to trigger a `git credential fill` call for an arbitrary host from within a smudge/clean subprocess spawned during `clone`/`fetch`. The verifiable code-level evidence is the contrast between the unfiltered environment passed to all git subprocesses in `trampoline-environment.ts`/`spawn.ts` and the explicit allowlist/exclusion applied only to hooks in `hooks-proxy.ts`, cited above.

export const getCredentialUrl = (cred: Map<string, string>) => {
  const u = cred.get('url')
  if (u) {
    return new URL(u)
  }

  const protocol = cred.get('protocol') ?? ''
  const username = cred.get('username')
  const user = username ? `${encodeURIComponent(username)}@` : ''
  const host = cred.get('host') ?? ''
  const path = cred.get('path') ?? ''

  return new URL(`${protocol}://${user}${host}/${path}`)
}
