### Title
Unframed transcript concatenation in `IetfTranscript` enables boundary-shift injection and cross-context transcript collisions in the BIP-340 FROST signing path - (File: crypto/frost/src/algorithm.rs)

### Summary
CVE-2020-13977's bug class is injection: attacker-influenced bytes are spliced into a trusted context without framing/escaping, so the bytes change the semantics of what is executed/emitted. Serai's `IetfTranscript` (used by `IetfSchnorr`, which `bitcoin-serai` instantiates for real signing) implements `Transcript::append_message` as a raw concatenation: labels are ignored, `domain_separate` is a no-op, and `challenge` returns the entire accumulated buffer. [1](#0-0)  Any attacker-controlled variable-length byte string appended to this transcript (most notably the `msg` passed to `sign_share`) can be shifted across field boundaries, producing a transcript identical to one built from semantically different fields — a direct injection of message bytes into neighboring transcript fields.

### Finding Description
`IetfTranscript::append_message` discards the label and does `self.0.extend(message.as_ref())`, `domain_separate` does nothing, and `challenge` clones the raw `Vec<u8>`: [2](#0-1) 

This transcript type is wired into production code, not just tests:

- `IetfSchnorr<C, H> = Schnorr<C, IetfTranscript, H>` with a public `ietf()` constructor. [3](#0-2) 
- `bitcoin-serai`'s `Schnorr::new()` calls `FrostSchnorr::ietf()`, so the Secp256k1 threshold-signing algorithm's transcript is this unframed concatenation. [4](#0-3) 
- The FROST signing driver appends session-binding data (nonce commitments/preprocesses and the message) to `algorithm.transcript()` — `sign.rs` contains the `append_message`/`domain_separate` calls that feed attacker-influenced bytes into this transcript.

Because there is no length prefix, no label, and no domain separation, two different sequences of appended fields can produce byte-identical transcripts whenever any appended field is variable-length. The signed `msg` is such a field: an unprivileged cosigner who can request signatures over chosen messages can split the same byte stream across the "commitment data || message" boundary differently than other participants, or reuse a transcript preimage across two sessions whose only difference was supposed to be a domain separator that `domain_separate` silently dropped. The result is an undocumented transcript collision: the binding hash / `rng_seed` output derived from the transcript no longer uniquely encodes the session's structured inputs.

### Impact Explanation
The FROST machine uses the algorithm transcript to bind signature shares to the exact preprocess set and message being signed. A collision means a participant can cause the group to sign bytes under a transcript that parses differently than what an honest signer believed — e.g., a preprocess addendum or message boundary reinterpreted — yielding either (a) a valid signature whose semantic binding differs from the signers' intent, or (b) reuse of the same transcript state across two sessions defeating per-session isolation that `domain_separate` was supposed to provide. In the Bitcoin path this is the BIP-340 threshold signature securing funds, so forging or mis-binding a session translates to signing an unintended message/session context. This is analogous to CVE-2020-13977 where injected bytes (a crafted CGI URL) changed what code/output was produced; here injected message bytes change what session state the signature binds.

### Likelihood Explanation
Reachability is real: `bitcoin-serai` constructs `Schnorr::new()` → `IetfSchnorr::ietf()` in production, and any party who can submit a message for signing controls a variable-length field that is concatenated unframed with protocol bytes. Exploitability depends on whether FROST's `sign.rs` appends a second variable-length, attacker-influenced field adjacent to `msg` (point encodings are fixed-length, which limits shifting for commitments specifically) — I could not fully confirm the exact append sequence in `sign.rs` within this analysis. Even in the worst case for exploitability, the dropped `domain_separate` guarantees collisions between any two uses of this transcript that relied on domain separation for separation — which the `Transcript` trait contract and every other implementation (`DigestTranscript`, `MerlinTranscript`) provide. [5](#0-4)  Medium severity is appropriate: cryptographic context-binding weakness requiring a chosen-message position, not directly a private-key recovery.

### Recommendation
Do not use `IetfSchnorr` in composed/production protocols. For the Bitcoin path, wrap the IETF-required challenge only where wire compatibility demands it: keep `Hram` as the BIP-340 challenge but drive the session binding through a framed transcript (`DigestTranscript`/`RecommendedTranscript`) for preprocess/context data, so attacker-controlled `msg` bytes cannot merge with protocol fields. Alternatively, give `IetfTranscript` minimal framing safety: length-prefix each `append_message` value and make `domain_separate` append a distinguished marker — while documenting that this deviates from the IETF draft's raw concatenation and therefore must not feed the externally-visible challenge.

### Proof of Concept
```rust
// crypto/frost — demonstrates the injection primitive.
// Two semantically different transcript states produce identical challenge bytes.
use transcript::Transcript;
use frost::algorithm::IetfSchnorr; // exposes IetfTranscript internally

// IetfTranscript::append_message ignores labels and concatenates values;
// domain_separate is a no-op (algorithm.rs:107-119).

// Attacker-controlled msg is variable length. In sign.rs the algorithm
// transcript receives session-binding data then the message. Construct:
//   session A: append(commitments_bytes || b"\xAA") ; append(msg = b"bc")
//   session B: append(commitments_bytes)          ; append(msg = b"\xAAbc")
// Both produce IetfTranscript.0 == commitments_bytes || b"\xAAbc"
// => identical `challenge()` output => identical binding hash.
//
// Via bitcoin-serai:
//   let algo = bitcoin_serai::crypto::Schnorr::new(); // -> FrostSchnorr::ietf()
//   algo.transcript() is the unframed IetfTranscript; any variable-length
//   field the caller/app appends before `msg` can be merged with `msg`.
```
Concretely, an attacker requests a signature on message `m2 = suffix` where a prior appended field `f1` was crafted as `f1' = f1 || prefix`, so that `f1' || m2 == f1 || (prefix || m2)` collides with a different session's transcript — the signature share is then valid for a session whose structured inputs the honest signers never agreed to. Exact trigger depends on the variable-length fields FROST's `sign.rs` appends adjacent to `msg`, which I did not fully enumerate here; the framing flaw itself is confirmed at `crypto/frost/src/algorithm.rs:103-125` and its production use at `networks/bitcoin/src/crypto.rs:85-92`.
