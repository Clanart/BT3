### Title
Symlink-Following Write in `.gitignore` Handling Leads to Arbitrary File Corruption Outside Repository - (File: `app/src/lib/git/gitignore.ts`)

### Summary
`readGitIgnoreAtRoot`, `saveGitIgnore`, and `appendIgnoreRule` operate on `Path.join(repository.path, '.gitignore')` using plain `fs` calls (`FS.readFile`, `writeFile`) that transparently follow symbolic links. If the tracked `.gitignore` path in a cloned repository is a symlink pointing to a file outside the repository's working tree, Desktop's "Ignore file" flow will read, reformat, and overwrite the external target instead of failing or refusing to touch a path outside the repo.

### Finding Description
`readGitIgnoreAtRoot` resolves the ignore file path with `Path.join(repository.path, '.gitignore')` and reads it via `FS.readFile` [1](#0-0) . Node's `fs.readFile`/`fs.promises.writeFile` follow symlinks by default (no `lstat`/`O_NOFOLLOW` check), so if `.gitignore` in the working tree is a symlink, the OS transparently resolves it to whatever file it points to, even outside the repository directory.

`saveGitIgnore` computes the same `ignorePath` and calls `writeFile(ignorePath, fileContents)` unconditionally, again following any symlink at that path [2](#0-1) .

`appendIgnoreRule` chains these two: it reads the current (possibly external, symlink-resolved) contents, appends the new pattern text, reformats, and writes it back via `saveGitIgnore` [3](#0-2) . `appendIgnoreFile`, invoked from the "Ignore file" context-menu action, escapes special gitignore characters in the target file path and forwards it to `appendIgnoreRule` [4](#0-3) .

Notably, the codebase already has a helper, `resolveWithin` (and its POSIX/Win32 variants), specifically designed to resolve a path against a root and reject it if the real, symlink-resolved path escapes that root [5](#0-4) . None of the functions in `gitignore.ts` use `resolveWithin`, `lstat`, or any other symlink-escape check before reading or writing the ignore file — I found no such calls anywhere in `gitignore.ts`, and grepping the repo for `lstat`/`realpath`/`isSymbolicLink`/`O_NOFOLLOW` turned up no usage tied to gitignore handling.

Because a `.gitignore` symlink is ordinary repository content, an attacker who controls a repository (e.g., a malicious clone/fetch target) can commit a `.gitignore` symlink pointing to a sensitive out-of-tree file (e.g., a shell profile, another project's config file, or any file writable by the victim's OS user). When the victim right-clicks a file in Desktop's Changes list and chooses "Ignore file", `appendIgnoreFile` → `appendIgnoreRule` → `readGitIgnoreAtRoot`/`saveGitIgnore` will follow the symlink and append the (attacker-influenced, escaped) pattern text into the external target file, silently corrupting/modifying a file the user never intended to touch and did not select.

### Impact Explanation
This matches the in-scope impact category "silent corruption of what the user commits or pushes" and "file write ... outside the repo": an unprivileged, attacker-controlled repository can cause Desktop to write into a file outside the cloned repository's directory tree without any prompt or warning, using only ordinary git content (a symlink) and a normal, expected user action (ignoring a file from the context menu). Depending on which file the symlink targets, this could corrupt configuration files, injection into files later executed/sourced by the user (e.g., shell rc files) is possible if attacker can predict what such a file will contain, though the appended content itself is limited to git-ignore-pattern-escaped path text.

### Likelihood Explanation
Requires the victim to clone/open the attacker's repository and to perform the ordinary, common action of "Ignore file" from the Changes context menu on any file — a very plausible interaction. No admin rights, no local access, and no unusual user steps beyond normal repository browsing are required, satisfying scope.

### Recommendation
Before reading or writing the repository's `.gitignore` file, verify the resolved path stays within the repository root and is not a symlink — e.g., use the existing `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` helper from `app/src/lib/path.ts`, or `lstat` the path and refuse to proceed (or refuse to follow) if it is a symlink pointing outside `repository.path`, in both `readGitIgnoreAtRoot` and `saveGitIgnore`.

### Proof of Concept
1. Attacker creates a repository containing a symlink named `.gitignore` at the repo root pointing to an out-of-tree file, e.g. `ln -s /home/victim/.bashrc .gitignore`, and commits/pushes it (symlinks are valid git blobs of mode `120000`).
2. Victim clones this repository with GitHub Desktop and opens it.
3. Victim modifies/creates any file, opens the Changes list, right-clicks a file, and selects "Ignore file".
4. This invokes `appendIgnoreFile` → `appendIgnoreRule` → `readGitIgnoreAtRoot` (follows the symlink and reads `/home/victim/.bashrc`) → `saveGitIgnore` (follows the symlink and overwrites/appends to `/home/victim/.bashrc`) [3](#0-2) .
5. Diffing `/home/victim/.bashrc` before and after shows the attacker-influenced ignore pattern text appended, confirming the external file was modified via the followed symlink.

export async function readGitIgnoreAtRoot(
  repository: Repository
): Promise<string | null> {
  const ignorePath = Path.join(repository.path, '.gitignore')

  return new Promise<string | null>((resolve, reject) => {
    FS.readFile(ignorePath, 'utf8', (err, data) => {
      if (err) {
        if (err.code === 'ENOENT') {
          resolve(null)
        } else {
          reject(err)
        }
      } else {
        resolve(data)
      }
    })
  })
}

export async function saveGitIgnore(
  repository: Repository,
  text: string
): Promise<void> {
  const ignorePath = Path.join(repository.path, '.gitignore')

  if (text === '') {
    return new Promise<void>((resolve, reject) => {
      FS.unlink(ignorePath, err => {
        if (err) {
          reject(err)
        } else {
          resolve()
        }
      })
    })
  }

  const fileContents = await formatGitIgnoreContents(text, repository)
  await writeFile(ignorePath, fileContents)
}

export async function appendIgnoreRule(
  repository: Repository,
  patterns: string | string[]
): Promise<void> {
  const text = (await readGitIgnoreAtRoot(repository)) || ''

  const currentContents = await formatGitIgnoreContents(text, repository)

  const newPatternText =
    patterns instanceof Array ? patterns.join('\n') : patterns
  const newText = await formatGitIgnoreContents(
    `${currentContents}${newPatternText}`,
    repository
  )

  await saveGitIgnore(repository, newText)
}

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
