## Analysis

`getEndpointKind` classifies a git remote as `'enterprise'` purely based on an attacker-controllable `WWW-Authenticate` header, before any protocol/authenticity check is performed: [1](#0-0) 

This header (`wwwauth[...]`) is forwarded by git verbatim from whatever the remote HTTP(S) server sends, so it is fully attacker-controlled for any remote the user adds — including a plain generic remote that was never registered as a GitHub account. If `getEndpointKind` returns `'enterprise'`, `getCredential` treats the endpoint as a GitHub host and, finding no matching stored account, invokes the native GitHub sign-in flow instead of the generic-credential prompt: [2](#0-1) 

`promptForGitHubSignIn` then wires the sign-in flow's target endpoint directly to the attacker's own server origin: [3](#0-2) 

- If the remote is plain HTTP, this path is blocked: `SignInStore.setEndpoint` rejects non-HTTPS URLs with "Unsupported protocol" and stays on `EndpointEntry`, as shown by `sign-in-store.ts`'s protocol validation and the corresponding test (`sets error for non-HTTPS URL`). [4](#0-3) [5](#0-4) 

- If the remote is a **self-hosted HTTPS** server (any domain, no relation to GitHub), the HTTPS check passes and `SignInStore` advances straight to the `Authentication` step for that attacker-controlled `endpoint`: [6](#0-5) 

From there, both the browser-based OAuth path and (if present) any direct credential submission target the attacker's own server: [7](#0-6) [8](#0-7) 

So the spoofing works for a self-hosted HTTPS remote (not plain HTTP, which is blocked by the endpoint-entry protocol check), and it causes GitHub Desktop to surface an unwarranted "Sign in to GitHub Enterprise" popup pointed at the attacker's server, with `requestOAuthToken`/`fetchUser` (or basic-auth submission, if that UI path exists) sending requests to that attacker-controlled `endpoint`.

## Caveat on validity

This requires the user to actively complete the resulting sign-in dialog (enter credentials or complete browser OAuth) pointed at what they might reasonably believe is a legitimate GitHub Enterprise prompt, since the trigger itself is fully automatic and attacker-driven (not something the user consciously initiated). Whether reviewers consider this "unprompted unnatural user steps"/"social engineering" (explicitly excluded per the stated scope) or a legitimate spoofing/trust-boundary bug (the app itself misrepresents an arbitrary attacker server as GitHub Enterprise) is a judgment call. I could not verify from the available files whether the `Authentication` step's UI (`sign-in.tsx`) also supports direct username/password submission to `endpoint` (vs. browser-OAuth only) — that file's contents were not available in the index, and this detail affects whether raw credentials (not just OAuth authorization codes) could be exfiltrated. I recommend a Devin session with full repo access to confirm the `sign-in.tsx` / `SignIn` component behavior for the `Authentication` step if this needs to be resolved definitively.

### Title
Spoofed `WWW-Authenticate: realm="GitHub"` from an untrusted self-hosted HTTPS git remote causes GitHub Desktop to launch its native GitHub-Enterprise sign-in flow against the attacker's server - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`getEndpointKind` classifies any remote sending `WWW-Authenticate: Basic realm="GitHub"` as `'enterprise'` without verifying the host is actually a GitHub endpoint, ahead of the existing `isGitHubHost` reachability check that would normally validate this.

### Finding Description [1](#0-0) 
The `wwwauth[...]` credential fields are populated by git from the actual HTTP response of the remote server the user configured, so any self-hosted HTTPS git server the attacker controls can emit this header. This causes `getEndpointKind` to short-circuit and return `'enterprise'` instead of falling through to the legitimate `isGitHubHost(endpoint)` network check at [9](#0-8) , which would otherwise correctly classify a non-GitHub host as `'generic'`.

Because the endpoint is now misclassified as `'enterprise'`, `getCredential` skips the generic-credential/prompt path and instead calls `ui.promptForGitHubSignIn(endpoint)` with `endpoint` pointing at the attacker's server [10](#0-9) . `promptForGitHubSignIn` then calls `dispatcher.setSignInEndpoint(origin)` with `origin` derived from the attacker's URL [11](#0-10) , which flows into `SignInStore.setEndpoint`, and (since the attacker's HTTPS URL passes protocol validation) advances the sign-in flow to the `Authentication` step targeting the attacker's own origin [6](#0-5) .

### Impact Explanation
If the user proceeds with the resulting sign-in prompt (browser-based OAuth or any credential entry UI bound to this step), subsequent network calls — `shell.openExternal(getOAuthAuthorizationURL(endpoint, csrfToken))`, `requestOAuthToken(endpoint, action.code)`, `fetchUser(endpoint, token)` — are all directed at the attacker's server rather than a real GitHub host [7](#0-6) [8](#0-7) . This could result in credential or token exchange occurring against an attacker-controlled endpoint.

### Likelihood Explanation
Requires the attacker to control an HTTPS-served git remote the victim has added (as a generic, non-GitHub remote) and requires the victim to interact with the resulting sign-in popup; plain-HTTP remotes are blocked by the protocol check in `setEndpoint`.

### Recommendation
Move the `wwwauth[...]` realm heuristic after (or gate it behind) the existing `isGitHubHost` verification, or otherwise require a positive network confirmation that the host is actually a GitHub instance before trusting a client-supplied `realm="GitHub"` header to classify an endpoint as `'enterprise'`.

### Proof of Concept
1. Host a self-signed/valid-HTTPS git-over-HTTP server that, on any authentication challenge, responds with `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, add this server as a plain remote (never sign in to it as a GitHub account) and trigger a fetch/push requiring auth.
3. Observe `getEndpointKind` returns `'enterprise'`, and GitHub Desktop shows the native "Sign in to GitHub Enterprise" popup with `credentialHelperUrl`/sign-in endpoint set to the attacker's server.
4. Any browser OAuth flow or credential submission this popup performs targets the attacker's server.

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }
