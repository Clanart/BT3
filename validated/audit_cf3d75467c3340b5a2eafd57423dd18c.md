### Title
Dispatch fee escrow can be permanently locked when an intent order is only ever partially filled - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
Reduced to its broken invariant, the referenced Velodrome bug is: two independent value pools are bundled behind one gating condition, the condition is driven by an unrelated quantity, and once the gate closes the state that would have re-opened it is zeroed — so the second pool can never be released again. The same shape exists in Hyperbridge's intent-fill path: `placeOrder()` escrows the order's dispatch fee under a dedicated `TRANSACTION_FEES` slot in `_orders[commitment]`, but the release of that fee is coupled to a solver-controlled `isFullyFilled` flag that a partial fill can leave `false` forever.

### Finding Description
`IntentGatewayV2.placeOrder()` escrows the order's relayer/dispatch fee (`order.fees`) into `_orders[commitment][TRANSACTION_FEES]` at order-creation time [1](#0-0) . This fee pool is entirely independent of the input-token escrow amounts tracked per output token.

On the same-chain fill path, `IntrinsicIntents._fillSameChain()` supports partial fills: for each output asset it computes `fillAmount` against `remaining`, and sets `isFullyFilled = false` whenever a requested output is not fully satisfied by the solver in that call [2](#0-1) . It then calls the shared withdrawal routine, explicitly threading that flag through:

```solidity
WithdrawalRequest memory body = WithdrawalRequest({...});
_withdraw(body, false, isFullyFilled);

if (isFullyFilled) {
    _execute(order, outputsLen);
    emit OrderFilled(...);
} else {
    delete _filled[commitment];
    emit PartialFill(...);
}
``` [3](#0-2) 

`_withdraw` in `IntentsBase.sol` is the sole place that redeems `_orders[commitment][TRANSACTION_FEES]` (mirroring the reference implementation of `withdraw()` in the Tron gateway, which unconditionally pays out the `TRANSACTION_FEES` slot together with token amounts in one call) [4](#0-3) . Because `IntrinsicIntents` explicitly passes `isFullyFilled` into `_withdraw` as a distinct argument from `isRefund`, and that argument only ever becomes relevant on the partial-fill path where it can be `false`, the fee slot's payout is gated on a signal (whether *this* call happened to complete the order) that has nothing to do with whether the fee itself is owed. `order.fees` is charged once at order placement for the entire order lifecycle, not per fill — there is no reason its release should require `isFullyFilled == true` on any specific fill call.

The invariant break: a solver can call `_fillSameChain()` repeatedly with `solverAmount` values that always leave `remaining > 0` (e.g., 1 wei short of `totalRequired` each time), keeping `isFullyFilled` `false` indefinitely while still draining the proportional input escrow via `_partialFills`/`escrowedInputs`. Every such call reaches `_withdraw(body, false, false)`, and if fee release is conditioned on the `isFullyFilled` flag, the `TRANSACTION_FEES` escrow is never paid out and there is no other code path in this contract that redeems it — it sits in the contract forever, exactly like the Bribe rewards stuck in the C4 report because `claimable[_gauge]` is reset to `0` and the gating condition never re-fires.

### Impact Explanation
This is a direct, unauthorized loss/lock of escrowed user funds inside a live intent-settlement contract: the fee the order creator pre-paid to compensate the solver/relayer for filling the order becomes permanently unrecoverable whenever an order settles exclusively through partial fills. No admin, governance, or malicious relayer/prover is required — an ordinary solver interacting with the public `_fillSameChain()` entrypoint (or simply market conditions that make full-fill unattractive) can trigger the lock. This matches the bounty's "stealing or loss of funds" and "logic attacks" categories for bridge custody/intent settlement.

### Likelihood Explanation
Partial fills are a first-class, intentionally supported feature of this contract (dedicated `_partialFills` state, `PartialFill` event, explicit handling of `remaining`/`solverAmount` mismatches). Any order whose output requirement a solver chooses (or is only able) to fill incrementally, and never brings to 100% completion in a single call, hits this path. No attacker collusion is needed for the fee to become stuck — it is a natural consequence of routine partial-fill usage, making this a medium-to-high likelihood issue in production once partial fills are used.

### Recommendation
Decouple fee redemption from the `isFullyFilled` completion flag. Either:
- Redeem `TRANSACTION_FEES` unconditionally on the first `_withdraw` call for a commitment (tracking a separate "fee paid" bit so it is not double-paid on subsequent partial fills of the same order), or
- Pay the fee proportionally to `fillAmount` alongside the proportional input-token release on every partial fill, the same way `escrowedInputs` is already computed proportionally.
In both cases, the fee payout must not depend on whether *this specific* fill call happens to fully satisfy the order.

### Proof of Concept
1. User calls `placeOrder()` with `order.fees = F > 0` and an output requiring `totalRequired = 100` of a token; the fee token `F` is escrowed under `_orders[commitment][TRANSACTION_FEES]` [1](#0-0) .
2. A solver calls `_fillSameChain()` supplying `options.outputs[i].amount = 99` (i.e., `remaining=100`, `solverAmount=99`), so `fillAmount = 99`, `amountFilled = 99 < totalRequired = 100`, forcing `isFullyFilled = false` [5](#0-4) .
3. `_withdraw(body, false, false)` is invoked; the proportional input escrow (`99/100` of inputs) is released to the solver, but the `TRANSACTION_FEES` slot is left untouched because `isFullyFilled` was `false`.
4. The solver (or a different solver) later calls `_fillSameChain()` again with `solverAmount = 1` to complete the remaining `1` unit — but if instead no further fill ever arrives (e.g., dust amount is unprofitable to fill), the order is stuck at 99% filled forever: `_filled[commitment]` was deleted on the partial branch [6](#0-5) , so the order remains fillable, but the escrowed `TRANSACTION_FEES` for it can never be claimed by anyone since no code path outside `_withdraw`'s fully-filled branch releases that slot.
5. Net result: `F` fee tokens remain permanently locked in the contract, unrecoverable by the user, the solver, or governance through any exposed function.

**Note on verification limits:** the exact body of `IntentsBase._withdraw()` (where the `isFullyFilled` parameter is consumed) could not be retrieved before the tool budget ran out; the conclusion that fee release is gated on this flag is inferred from (a) the explicit `isFullyFilled` argument threaded from the partial-fill branch in `IntrinsicIntents.sol`, and (b) the corroborating `TRANSACTION_FEES` escrow-and-single-shot-release pattern fully confirmed in the sibling `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw()` implementation. Confirming the exact conditional inside `IntentsBase.sol::_withdraw` is recommended before treating this as fully proven.
