## Title
Unbounded recursion in wallet outer-puzzle driver matching can crash wallet transaction processing via deeply-layered puzzle reveal - ([File: chia/wallet/outer_puzzles.py])

### Summary
The external CVE describes a stack-overflow / out-of-bounds read in a Lua debug interpreter (`ldebug.c`) triggered by unbounded recursive traversal of attacker-influenced structures. The closest reachable analog in this repository is the recursive `match()` / `get_inner_puzzle()` / `get_inner_solution()` chain used by wallet outer-puzzle drivers (`SingletonOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, etc., wired through `match_puzzle()` in `chia/wallet/outer_puzzles.py`). These functions recurse once per curried "outer layer" of a puzzle reveal with **no depth limit**, and the puzzle reveal/solution originates from CLVM data that is only bounded by the (very large) CLVM cost budget, not by nesting depth. I was not able to fully confirm, within the remaining time, whether an untrusted, attacker-crafted coin (e.g., an NFT/CAT/singleton-shaped puzzle with thousands of nested curry layers) is actually processed through this exact call chain during normal wallet sync before the process budget/cost limit would reject it first — this needs further verification via a background agent with full repository/test access.

### Finding Description
`chia/wallet/outer_puzzles.py:match_puzzle()` iterates over `driver_lookup` and calls `driver.match(puzzle)` [1](#0-0) . Drivers such as `SingletonOuterPuzzle.match()`, `OwnershipOuterPuzzle.match()`, and `MetadataOuterPuzzle.match()` each recursively call `self._match(...)` on the puzzle's inner layer when an "also" nested constructor is present [2](#0-1) [3](#0-2) [4](#0-3) . Similarly, `get_inner_puzzle()` and `get_inner_solution()` in these drivers recurse per layer [5](#0-4) . None of these recursive paths enforce a maximum nesting depth — the only limiter is Python's default recursion limit, which would raise `RecursionError` rather than gracefully rejecting malformed/oversized input.

A related, more clearly recursive and depth-unbounded parser exists in the custody architecture memo decoder, `PuzzleWithRestrictions.from_memo()`, which recursively parses `MofN` member memos with no depth bound [6](#0-5) , and its `unknown_puzzles` property also recurses per `MofN` member [7](#0-6) .

By contrast, the codebase explicitly hardens the hot consensus/tree-hash path against this exact bug class: `sha256_treehash()` is deliberately implemented as an iterative, stack-based algorithm specifically "so we don't have to worry about blowing out the python stack" [8](#0-7) , and `Program.get_tree_hash()` uses the Rust `tree_hash()` implementation entirely [9](#0-8) . This shows the project is aware of and mitigates Python-recursion-limit DoS for the consensus-critical hashing path, but the wallet-side outer-puzzle/memo recursive parsers were not given the same treatment.

### Impact Explanation
If reachable with attacker-controlled, deeply-layered puzzle/memo data (e.g., via a coin sent to a victim wallet with an unusually deep curry/"also" chain, or a maliciously crafted custody memo), this could raise an unhandled `RecursionError` inside wallet coin-processing code, crashing or halting transaction/coin-state processing for the affected wallet — matching the accepted "spend-triggered transaction-processing halt" impact category. This is a local/light DoS against a wallet process, not a consensus-breaking or fund-theft bug.

### Likelihood Explanation
Uncertain/Medium. Reaching `match_puzzle()`/`get_inner_puzzle()` with sufficiently deep nesting from a single externally-supplied coin depends on (a) whether CLVM cost limits would reject an equivalently large program before the driver even attempts recursion, and (b) whether the recursion depth required to exceed Python's default limit (~1000) can be encoded cheaply enough in CLVM cost terms to slip through mempool/cost checks. I could not conclusively verify the exact call sites that would automatically invoke `match_puzzle()` on arbitrary untrusted coins received during standard wallet sync within the available time; this needs confirmation.

### Recommendation
Add explicit recursion-depth limits (or convert to iterative traversal, following the pattern already used in `sha256_treehash`) to `match_puzzle()`/`get_inner_puzzle()`/`get_inner_solution()` driver chains in `chia/wallet/outer_puzzles.py` and its outer-puzzle drivers, and to `PuzzleWithRestrictions.from_memo()`/`unknown_puzzles` in `chia/wallet/puzzles/custody/custody_architecture.py`, so that malformed or adversarially deep puzzle reveals/memos are rejected with a normal exception rather than risking a Python stack `RecursionError`.

### Proof of Concept
Not fully constructed — would require crafting a puzzle reveal or custody memo with a curry/"also"-chain or `MofN` nesting depth exceeding Python's recursion limit and confirming it reaches `match_puzzle()` / `PuzzleWithRestrictions.from_memo()` from an untrusted coin/spend path (e.g., during wallet `coin_added` processing or offer/puzzle-info reconstruction) before any CLVM cost-based rejection occurs. This verification step should be completed by a follow-up investigation with full test-execution access.

    def get_inner_puzzle(
        self, constructor: PuzzleInfo, puzzle_reveal: UnknownPuzzle, solution: Program | None = None
    ) -> Program | None:
        matched, curried_args = match_singleton_puzzle(puzzle_reveal)
        if matched:
            _, inner_puzzle = curried_args
            also = constructor.also()
            if also is not None:
                deep_inner_puzzle: Program | None = self._get_inner_puzzle(
                    also, UnknownPuzzle(known_program=inner_puzzle), None
                )
                return deep_inner_puzzle
            else:
                return inner_puzzle
        else:
            raise ValueError("This driver is not for the specified puzzle reveal")

    def get_inner_solution(self, constructor: PuzzleInfo, solution: Program) -> Program | None:
        my_inner_solution: Program = solution.at("rrf")
        also = constructor.also()
        if also:
            deep_inner_solution: Program | None = self._get_inner_solution(also, my_inner_solution)
            return deep_inner_solution
        else:
            return my_inner_solution

        restriction_hints = [RestrictionHint.from_program(hint) for hint in restriction_hints_prog.as_iter()]

    @property
    def unknown_puzzles(self) -> Mapping[bytes32, UnknownMember | UnknownRestriction]:
        unknown_restrictions = {
            ur.restriction_hint.puzhash: ur for ur in self.restrictions if isinstance(ur, UnknownRestriction)
        }

        unknown_puzzles: Mapping[bytes32, UnknownMember | UnknownRestriction]
        if isinstance(self.puzzle, UnknownMember):
            unknown_puzzles = {self.puzzle.puzzle_hint.puzhash: self.puzzle}
        elif isinstance(self.puzzle, MofN):
            unknown_puzzles = {
                uph: up
                for puz_w_restriction in self.puzzle.members
                for uph, up in puz_w_restriction.unknown_puzzles.items()
            }
        else:
            unknown_puzzles = {}
        return {
            **unknown_puzzles,
            **unknown_restrictions,
        }
