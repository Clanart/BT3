### Title
Escrow withdrawal on Tron `IntentGatewayV2` accepts a non-reverting `false` return from `IERC20.transfer` as success, permanently marking escrow as released without delivering funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` settles escrowed order tokens and transaction fees via a raw low-level `.call()` to `IERC20.transfer`, checking only that the call did not revert (`success`) and never inspecting the ABI-encoded boolean return value. Non-reverting ERC20 implementations that return `false` on a failed transfer will pass this check, causing the contract to mark the order as `_filled`/withdrawn and decrement the escrow accounting even though the beneficiary received nothing.

### Finding Description
In `withdraw()`, redemption/refund of escrowed order tokens and transaction fees is done as: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

`success` here only reflects whether the external call reverted — it does not decode/verify the `bool` returned by a compliant `transfer()` implementation. This is functionally identical to the `GenericToken.executeLowLevelCall` pattern in the referenced report: the code assumes any token that "fails" will revert, when in reality many ERC20 tokens (including some already deployed on Tron, e.g. non-standard/legacy tokens) return `false` instead of reverting on failure. The same unchecked pattern is repeated for the transaction-fee payout right below it, and again in the `SweepDust` branch of `onAccept`: [2](#0-1) 

Note this contract explicitly imports and enables `SafeERC20` (`using SafeERC20 for IERC20;`), and the sibling EVM contracts in this same repo (`evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`) consistently use `safeTransfer`/`safeTransferFrom` for exactly this reason: [3](#0-2) 

The Tron file declares the same `using SafeERC20 for IERC20` import but bypasses it for the withdrawal/sweep/fee paths, reintroducing the exact "return data not verified" flaw the report describes.

`withdraw()` is reachable from two unprivileged/permissionless paths that any user can trigger once an order commitment exists:
- `onAccept` with `RequestKind.RedeemEscrow`/`RefundEscrow`, driven by a cross-chain message.
- `onGetResponse`, which calls `withdraw(body, true)` directly after a GET response proving the order was never filled: [4](#0-3) 

In both cases, once `withdraw()` runs, `_filled[body.commitment]` is set and `_orders[body.commitment][token]` is decremented unconditionally, regardless of whether the token transfer actually succeeded.

### Impact Explanation
If the escrowed token is a non-reverting ERC20 (returns `false` on failed transfer rather than reverting — a documented and known category of ERC20 behavior that Notional's own audit explicitly warns about), the contract will:
1. Decrement `_orders[commitment][token]`, deleting the escrow record.
2. Set `_filled[commitment] = beneficiary`, marking the order as settled.
3. Emit `EscrowReleased`/`EscrowRefunded` as if funds were delivered.

The beneficiary receives zero tokens, and because the escrow bookkeeping is already zeroed and the order is marked filled, there is no retry or recovery path — the escrowed tokens remain stuck in the contract while the intended beneficiary permanently loses their fill/refund. This is a direct, permanent loss-of-funds condition for a real production settlement path (cross-chain intent escrow release), matching the bounty's "stealing or loss of funds" and "false proof/state acceptance"-adjacent category (false success acceptance leading to wrong economic outcome).

### Likelihood Explanation
Likelihood depends on the token used for `order.inputs`/fee token being a non-standard ERC20 that returns `false` instead of reverting. Since the IntentGateway is designed to be generic across arbitrary tokens supplied by users constructing orders (the escrow key is keyed by arbitrary `token` addresses from `order.inputs`), an attacker or unaware user filling/creating an order with such a token — or a token that later becomes non-reverting via a pausable/blacklist mechanism (e.g., returns `false` for blacklisted addresses instead of reverting) — will trigger this silently. No malicious relayer, prover, or admin is required; the flaw is purely in how the contract itself interprets the call's success flag.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer`, matching the pattern already used elsewhere in this file (`safeTransferFrom` calls) and in the sibling EVM `IntentGatewayV2`/`IntentsBase` contracts, which correctly decode and require the boolean return value (or handle no-return-value tokens per EIP-20 ambiguity) before treating the transfer as successful.

### Proof of Concept
1. Deploy (or use) an ERC20 token whose `transfer()` implementation returns `false` on failure instead of reverting (e.g., an already-blacklisted/paused legacy-style token, or a token with an internal cap check that returns `false`).
2. Create and escrow an order on the Tron `IntentGatewayV2` using this token as `order.inputs[i].token`.
3. Cause the token transfer to fail post-escrow (e.g., beneficiary becomes blacklisted, or contract balance manipulated to trigger the token's internal `false`-return failure path) while ensuring the call itself does not revert.
4. Trigger `withdraw()` via `onAccept(RedeemEscrow)` or `onGetResponse` (order-cancellation GET response).
5. Observe: `(bool success,) = token.call(...)` returns `success == true` (call didn't revert) even though the token's internal `transfer` logic returned `false` and moved no funds.
6. `_orders[commitment][token]` is decremented to zero, `_filled[commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — while the beneficiary's token balance is unchanged and the escrowed tokens remain trapped in the contract with no accounting path to reclaim them.
