### Title
Missing proof-of-possession on PedPoP encryption keys lets a participant co-opt another's `enc_key`, causing public/blame disclosure and cross-party leakage of secret shares - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2021-37968 is an information-disclosure bug: a crafted input caused Chrome to leak data belonging to a different origin. The Serai analog lives in PedPoP's encryption-layer registration. `EncryptionKeyMessage` carries a raw `enc_key: C::G` with no proof of possession, and `Decryption::register` only asserts a participant doesn't *re*-register — it never checks that two participants didn't register the *same* key [1](#0-0) [2](#0-1) . A malicious participant who copies victim Alice's `enc_key` causes every dealer to encrypt the share for the attacker's index under Alice's key: Alice can decrypt a message never addressed to her, and any blame resolution publishes an `EncryptionKeyProof` (the ECDH shared point + DLEq) that lets *anyone* — including non-participants via `AdditionalBlameMachine::new` — decrypt that share ciphertext [3](#0-2) [4](#0-3) .

### Finding Description
`EncryptionKeyMessage::read` deserializes `enc_key` with only `C::read_G` (canonical point check); no Schnorr/DLEq proof binds the key to the sender [5](#0-4) . `SecretShareMachine::verify_r1` batch-verifies the coefficient-zero PoK via `msg.sig.batch_verify`, but calls `self.encryption.register(l, msg)` first and performs no uniqueness or ownership check on `msg.enc_key` [6](#0-5) . The per-message PoP in `EncryptedMessage` only protects the *ephemeral* message key (`msg.key`), not the long-term `enc_key` [7](#0-6) .

Attack: participant Eve submits her `EncryptionKeyMessage` with `enc_key = Alice.enc_pub_key` (publicly visible on the authenticated channel). Dealers then call `self.encryption.encrypt(rng, l=Eve, share)` which ECDHs the fresh message key against `enc_keys[Eve]` = Alice's public key [8](#0-7) . Two leaks result:

1. Alice's `Encryption::decrypt` computes `ecdh(self.enc_key, msg.key)`, the identical shared point, so Alice decrypts the share polynomial-evaluated at Eve's index — a secret share she was never meant to hold [9](#0-8) .
2. Eve cannot decrypt, claims an invalid share, and submits `blame` (`EncryptionKeyProof` = ECDH point + DLEq). `BlameMachine::blame`/`AdditionalBlameMachine::blame` verifies the DLEq against `enc_keys[Eve]` (Alice's key) and `msg.key`, then applies the cipher and recovers the plaintext share — making the share for index Eve *public* to all observers of the blame process [10](#0-9) [11](#0-10) .

### Impact Explanation
The group secret is `sum of f_l(0)`; each delivered share `f_l(j)` is a confidential input to participant `j`'s key share. Publishing index-Eve's share (via blame) or leaking it to Alice reduces the effective threshold of the resulting `ThresholdKeys`: anyone who learns that share needs one fewer honest share to reconstruct the group private key or to forge FROST signatures. This is cross-party secret disclosure (another participant's confidential material) triggered purely by bytes the attacker places in her commitment message — matching the CVE's leak-across-a-boundary class. The code's own comments acknowledge this exact class ("revealing Alice's message to Bob") but only mitigate it for *per-message* keys, leaving `enc_key` unbound [12](#0-11) [13](#0-12) . Severity Medium: requires a malicious DKG participant and a blame/observation path, but yields concrete disclosure of another party's secret share.

### Likelihood Explanation
A DKG participant controls their `EncryptionKeyMessage` bytes and copying a published `enc_key` is trivial; nothing in `verify_r1`, `Decryption::register`, or `EncryptedMessage`'s PoP detects it. However, realizing the leak requires the attacker to trigger blame (or collude-adjacent observation by the key's real owner), and each incident exposes only the attacked index's share rather than the full group key, so exploitation is meaningful but bounded — consistent with Medium.

### Recommendation
Bind each `enc_key` to its registrant: require a Schnorr proof-of-possession over `enc_key` in `EncryptionKeyMessage` (challenged over `context` and `sender`, like `pop_challenge`), verified in `verify_r1` before `encryption.register`; additionally reject duplicate `enc_key` values across participants in `Decryption::register`.

### Proof of Concept
1. Run a 3-party PedPoP DKG (participants 1=Alice, 2=Eve, 3=Carol). Observe Alice's `EncryptionKeyMessage` on the authenticated channel and copy `msg.enc_key`.
2. Eve builds her own `EncryptionKeyMessage<Commitments>` with a valid PoK for her coefficients but `enc_key = alice_enc_key`; `EncryptionKeyMessage::read`/`verify_r1` accept it.
3. Each dealer's `generate_secret_shares` encrypts `polynomial(coeffs, Participant(2))` under `enc_keys[2] = alice_enc_key` via `Encryption::encrypt` → `ecdh(key, to)`.
4. Eve's `calculate_share` fails to decrypt meaningfully → she publishes `PedPoPError::InvalidShare { blame: Some(EncryptionKeyProof) }`.
5. Any observer runs `AdditionalBlameMachine::new(context, n, commitment_msgs).blame(sender=Eve_accused..., msg, Some(proof))`; `decrypt_with_proof` verifies the DLEq against `enc_keys[2]` and applies `cipher(context, proof.key)`, publicly recovering the plaintext `SecretShare` for index 2 — and Alice independently decrypts the same ciphertext with her private `enc_key`.

```rust
/// Wraps a message with a key to use for encryption in the future.
#[derive(Clone, PartialEq, Eq, Debug, Zeroize)]
pub struct EncryptionKeyMessage<C: Ciphersuite, M: Message> {
  msg: M,
  enc_key: C::G,
}

// Doesn't impl ReadWrite so that doesn't need to be imported
impl<C: Ciphersuite, M: Message> EncryptionKeyMessage<C, M> {
  pub fn read<R: io::Read>(reader: &mut R, params: ThresholdParams) -> io::Result<Self> {
    Ok(Self { msg: M::read(reader, params)?, enc_key: C::read_G(reader)? })
  }

  pub fn write<W: io::Write>(&self, writer: &mut W) -> io::Result<()> {
    self.msg.write(writer)?;
    writer.write_all(self.enc_key.to_bytes().as_ref())
  }

  pub fn serialize(&self) -> Vec<u8> {
    let mut buf = vec![];
    self.write(&mut buf).unwrap();
    buf
  }

  #[cfg(test)]
  pub(crate) fn enc_key(&self) -> C::G {
    self.enc_key
  }
}
```

```rust
  pub(crate) fn decrypt_with_proof<E: Encryptable>(
    &self,
    from: Participant,
    decryptor: Participant,
    mut msg: EncryptedMessage<C, E>,
    // There's no encryption key proof if the accusation is of an invalid signature
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Result<Zeroizing<E>, DecryptionError> {
    if !msg.pop.verify(
      msg.key,
      pop_challenge::<C>(self.context, msg.pop.R, msg.key, from, msg.msg.deref().as_ref()),
    ) {
      Err(DecryptionError::InvalidSignature)?;
    }

    if let Some(proof) = proof {
      // Verify this is the decryption key for this message
      proof
        .dleq
        .verify(
          &mut encryption_key_transcript(self.context),
          &[C::generator(), msg.key],
          &[self.enc_keys[&decryptor], *proof.key],
        )
        .map_err(|_| DecryptionError::InvalidProof)?;

      cipher::<C>(self.context, &proof.key).apply_keystream(msg.msg.as_mut().as_mut());
      Ok(msg.msg)
    } else {
      Err(DecryptionError::InvalidProof)
    }
  }
```

```rust
  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }
```

**File:** spec/cryptography/Distributed Key Generation.md (L28-35)
```markdown
While key reuse by a participant is considered as them revealing the messages
themselves, and therefore out of scope, there is an attack where a malicious
adversary claims another participant's encryption key. They'll fail to encrypt
their message, and the recipient will issue a blame statement. This blame
statement, intended to reveal the malicious adversary, also reveals the message
by the participant whose keys were co-opted. To resolve this, a
proof-of-possession is also included with encrypted messages, ensuring only
those actually with per-message keys can claim to use them.
```
