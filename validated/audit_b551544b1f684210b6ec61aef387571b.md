### Title
Missing reentrancy guard on `emergencyWithdraw` violates checks-effects-interactions in MasterMagpie emission accounting - (File: rewards/MasterMagpie.sol)

### Summary
`MasterMagpie.emergencyWithdraw()` is the only user-facing state-changing entry point in `MasterMagpie.sol` that performs an external token transfer before finishing its internal accounting update, and it is not protected by `nonReentrant`, unlike every other deposit/withdraw path in the same contract.

### Finding Description
All the normal staking entry points in `MasterMagpie.sol` — `deposit`, `withdraw`, `depositFor`, `withdrawFor` — are guarded with `nonReentrant` [1](#0-0) . However `emergencyWithdraw()` has no such guard and violates checks-effects-interactions: it zeroes `user.available` and performs the `safeTransfer` external call to the staking token before decrementing `user.amount` and recomputing `user.rewardDebt`: [2](#0-1) 

At the moment the external `safeTransfer` executes, `user.amount` and `user.rewardDebt` for that pool still hold their pre-withdrawal values (only `user.available` has been zeroed). Since `emergencyWithdraw` has no reentrancy lock, and no other function it calls acquires a global lock either (`updatePool` is a plain `public` function with no guard, see `whenNotPaused` at [3](#0-2) ), a staking token that executes a callback on transfer (e.g. ERC777-style, or any token with transfer hooks that MasterMagpie does not explicitly forbid) can re-enter MasterMagpie mid-call. During that re-entrant call, MasterMagpie's other pool-mutating functions (`deposit`, `multiclaim*`, or another `emergencyWithdraw` for a different pool sharing accounting through `_calLpSupply`) will read the stale, not-yet-decremented `user.amount`/`rewardDebt` for the pool under withdrawal, allowing rewards to be computed/harvested against principal that is already in the process of being withdrawn.

### Impact Explanation
This is a genuine violation of the reentrancy guard pattern the rest of the contract otherwise strictly follows for state-changing external calls, and it sits directly in MasterMagpie emission accounting, which is in-scope. The pending reward math (`_harvestMGP`, `_calNewMGP`, `_multiClaim`) is entirely driven by `user.amount` and `user.rewardDebt`, so an out-of-order update creates a window where unclaimed yield can be double-accounted for the same principal, resulting in theft/duplication of unclaimed MGP yield rather than a benign accounting quirk.

### Likelihood Explanation
Exploitability depends on the staking token registered for a pool having transfer/callback semantics (the contract does not restrict registered staking tokens to plain, hook-free ERC20s), and `emergencyWithdraw` only being reachable while the contract is `whenPaused` — a state an ordinary user can act within once triggered, not requiring any privileged action from the attacker themselves. This narrows likelihood compared to a globally reachable bug, but the missing guard is a concrete, provable code defect inconsistent with the rest of the contract's own security model.

### Recommendation
Add the `nonReentrant` modifier to `emergencyWithdraw()`, and reorder the function to update `user.amount` and `user.rewardDebt` before performing the `safeTransfer` call, consistent with checks-effects-interactions and with how `_withdraw`/`_harvestAndUnstake` are structured elsewhere in the same contract.

### Proof of Concept
1. Owner pauses `MasterMagpie` (emergency scenario).
2. Attacker holds a staked position in a pool whose staking token implements a transfer hook (e.g., ERC777 `tokensToSend`/`tokensReceived`, or any hook-enabled token registered as a pool's staking token).
3. Attacker calls `emergencyWithdraw(stakingToken)`.
4. Inside `safeTransfer`, the token's hook calls back into MasterMagpie (e.g., `deposit`/`multiclaim`) before `user.amount`/`rewardDebt` for that pool have been updated by the outer call, allowing reward accounting to be computed against the stale, still-full `user.amount`. [2](#0-1)

    /// @param _stakingToken Staking token of the pool
    function updatePool(address _stakingToken) public whenNotPaused {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        if (block.timestamp <= pool.lastRewardTimestamp || totalAllocPoint == 0) {
            return;
        }
        uint256 lpSupply = _calLpSupply(_stakingToken);
        if (lpSupply == 0) {
            pool.lastRewardTimestamp = block.timestamp;
            return;
        }        
        uint256 multiplier = block.timestamp - pool.lastRewardTimestamp;
        uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) / totalAllocPoint;
        
        pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
        pool.lastRewardTimestamp = block.timestamp;

        emit UpdatePool(
            _stakingToken,
            pool.lastRewardTimestamp,
            lpSupply,
            pool.accMGPPerShare
        );
    }
