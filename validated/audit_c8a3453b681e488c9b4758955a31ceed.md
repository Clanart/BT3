### Title
Attacker-controlled "theirs" content in a merge conflict can desynchronize Copilot conflict-hunk boundary detection between `extractConflictHunks` and `reassembleResolvedFile`, silently corrupting the file Desktop commits - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The upstream report describes a loop that walks a list until it finds the "next" element matching a condition, and shows that an attacker who controls what gets inserted into that list can shape it so the walk terminates at the wrong place, breaking an invariant the rest of the system depends on. GitHub Desktop's AI merge-conflict resolution feature has a structurally identical pattern: two independent forward-scanning loops walk the *same* conflicted file text looking for the first line that matches a conflict-marker regex, and both loops trust that the first match they find is the "real" one. The content being scanned (the `theirs` side of a merge/rebase/cherry-pick) is fully attacker-controlled when the incoming branch/commit comes from an untrusted remote, PR, or cherry-picked commit.

### Finding Description
Two parsers independently determine where a conflict hunk ends by regex-matching the closing `>>>>>>>` line:

- `extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` walks the file and, for each hunk, collects `theirsLines` until it hits the first line matching `theirsMarker` (`^>{7}(?:\s|$)`), then stops (`hunkEnd = i`). [1](#0-0) 

- `reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` independently re-walks the raw file later (after the model responds) and locates the same block boundary by scanning forward for the first line matching `reassemblySeparatorMarker`/`reassemblyTheirsMarker`, splicing the model's `resolvedContent` in place of everything between the opening `<<<<<<<` and the detected closing marker. [2](#0-1) 

Both loops use a naive "first match wins" strategy with no validation that the matched line is the marker git actually inserted (which always carries a branch/commit suffix, e.g. `>>>>>>> feature-branch`) versus attacker-supplied text that merely matches the regex shape (any line of 7+ `>` characters followed by whitespace or EOL). Because the `theirs` side of the conflict is verbatim content from the incoming branch, an attacker who controls that branch (a malicious PR, a crafted remote ref, or a cherry-picked/rebased commit) can embed a line such as `>>>>>>> ` inside their own contributed lines, upstream of the real git-inserted closing marker.

When this happens, both `extractConflictHunks` (which builds the hunk sent to the model, and the `expectedHunkCounts` used by `validateResolutionPaths`) and `reassembleResolvedFile` (which splices the model's answer back into the file) terminate the hunk at the *same* attacker-chosen fake marker line — so hunk-count validation in `validateResolutionPaths` passes (it only compares counts between these two functions' outputs, not against the true git-authored markers). [3](#0-2) 

The consequence: the text between the attacker's fake marker and the real, git-inserted `>>>>>>> <branch>` line is never seen by the model as conflict content, is never resolved, and is not stripped by `reassembleResolvedFile` (which only removes lines from the real `<<<<<<<` up to the marker it detected). That leftover attacker text — plus the genuine trailing `>>>>>>> <branch>` line — is copied through verbatim as ordinary file content into the final "resolved" file that Desktop writes and that the user then stages/commits. [4](#0-3) 

### Impact Explanation
This lets an unprivileged attacker who controls the *incoming* side of a merge/rebase/cherry-pick (a malicious PR branch, remote, or commit fetched into Desktop) cause the AI conflict-resolution pipeline to silently produce a "fully resolved" file that actually still contains attacker-authored raw text and a residual literal `>>>>>>>`-shaped line that was never reviewed by the model or flagged to the user as unresolved. The system prompt and validation logic both believe the conflict was completely and correctly handled (`validateResolutionPaths` passes, `CopilotValidationError` is never raised), so nothing surfaces to the user indicating a problem — this matches the "silent corruption of what the user commits or pushes" impact class, since the committed file diverges from what both the model's reasoning and the UI's resolution summary claim was produced.

### Likelihood Explanation
Exploitation requires only that the attacker control content on the incoming/`theirs` side of a conflict that the victim resolves with Copilot (e.g., merging or rebasing onto a malicious branch, or cherry-picking an attacker's commit) and that the resulting merge actually conflicts with the victim's local changes on at least one hunk. Crafting a single line of seven-plus `>` characters followed by whitespace inside otherwise normal-looking source (e.g., inside a comment, string, or ASCII-art banner) is trivial and does not require any unusual or suspicious-looking payload. The main mitigating factor is that Desktop still shows the reassembled file/diff before the user finalizes the commit, so an attentive user could notice the stray marker-like line and the unresolved remainder — this is a likelihood-reducing factor but does not prevent the underlying parser divergence.

### Recommendation
- Require the closing/separator/base markers used by both `extractConflictHunks` and `reassembleResolvedFile` to match git's actual marker format including the trailing label (e.g., validate `^>{7}\s+\S` matches the real branch/commit label that git wrote, not just seven `>` characters), or track marker boundaries once (in `extractConflictHunks`) and pass the exact line indices through to `reassembleResolvedFile` instead of independently re-detecting them by regex.
- After reassembly, re-scan the final resolved content for any line still matching the conflict-marker regexes (`<{7}`, `|{7}`, `={7}`, `>{7}`) and treat this as a validation failure (already partially done for hunk content returned by the model in `parseCopilotConflictResolution`, but not applied to the final reassembled file).
- Fail closed (raise `CopilotValidationError`) rather than silently accepting the file when the two marker-detection passes could plausibly disagree, e.g., when more than one candidate closing-marker line is found within a single hunk region.

### Proof of Concept
1. Attacker publishes a branch/PR whose file content, within a region that will conflict with the victim's local change, contains (verbatim, as ordinary code/comment content):
   ```
   some legitimate-looking attacker code
   >>>>>>> 
   more attacker code that should have been part of the conflict
   ```
   followed further down by nothing else unusual — git itself will still insert its own real closing marker (`>>>>>>> attacker-branch`) at the true end of the conflict region during the merge.
2. Victim, using GitHub Desktop, merges/rebases/cherry-picks this branch, producing a conflict whose on-disk `theirs` section contains the attacker's fake `>>>>>>> ` line before git's real one.
3. Victim invokes Copilot conflict resolution. `extractConflictHunks` builds the hunk sent to the model using content truncated at the attacker's fake marker (`app/src/lib/copilot-conflict-context.ts:228-242`).
4. The model resolves only the truncated hunk; `validateResolutionPaths` compares hunk counts against the same truncated count and passes (`app/src/lib/copilot-conflict-resolution.ts:509-520`).
5. `reassembleResolvedFile` splices the model's answer in at the same attacker-chosen fake marker boundary (`app/src/lib/copilot-conflict-resolution.ts:559-591`), leaving the remaining attacker text and git's real `>>>>>>> attacker-branch` line embedded verbatim in the "resolved" file.
6. The dialog reports the conflict as fully resolved; the victim commits/pushes a file containing unreviewed attacker content and a stray conflict-marker-shaped line.

*Note: this analysis is based on static code review of the referenced files; it was not validated by executing the actual Copilot resolution pipeline end-to-end, so real-world behavior (e.g., any additional sanitization elsewhere in the write/commit path) should be confirmed by running the described scenario against the app.*
