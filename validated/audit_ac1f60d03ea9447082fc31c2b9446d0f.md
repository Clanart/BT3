## Title
IntentGatewayV2 (Tron) escrows the nominal transfer amount instead of the actual received balance, permanently locking funds for fee-on-transfer/rebasing tokens - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits escrow with the requested (nominal) token amount immediately after calling `safeTransferFrom`, without verifying the gateway's actual received balance. The mainline EVM contract (`evm/src/apps/IntentGatewayV2.sol`) was hardened against exactly this class of bug by measuring `balanceOf` before/after the transfer, but the Tron fork was never updated to match, reintroducing the stETH-style "transferFrom delivers less than requested" issue from the external report.

### Finding Description
In the mainline EVM `placeOrder`, the non-predispatch escrow path explicitly reconciles the escrowed amount with the actual balance delta to defend against fee-on-transfer/rebasing tokens: [1](#0-0) 

```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
```

The Tron port of the same function omits this reconciliation. It calls `safeTransferFrom` for the nominal amount and then immediately credits the escrow ledger with `reducedInputs[i].amount`, which was derived from the *nominal* `order.inputs[i].amount` computed earlier in the function — never from an observed balance delta: [2](#0-1) 

```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            // native token
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
            msgValue -= order.inputs[i].amount;
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }

        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;

        unchecked {
            ++i;
        }
    }
}
```

`reducedInputs` is computed from `order.inputs[i].amount` (the amount the user *intended* to send) earlier in the function, before this transfer even executes: [3](#0-2) 

If `token` under-delivers relative to the requested amount (fee-on-transfer tokens, or share-based rebasing tokens like Lido's stETH where `transferFrom(amount)` can move `amount - 1/2 wei`), the contract's `_orders[commitment][token]` ledger records more value than the contract physically holds. The commitment hash is also computed from the nominal (not actual-received) `reducedInputs`, so this mismatch is baked into the cross-chain commitment that gets verified/redeemed on other chains.

Later, `withdraw()` transfers exactly `body.tokens[i].amount` (taken from the committed order data) to the beneficiary, gated only by `_orders[body.commitment][token] == 0` (a non-zero check, not a sufficiency check): [4](#0-3) 

Since the ledger overstates the true balance, this `token.call(transfer...)` can revert for lack of contract balance — a direct analog of the reported `wrap()`/downstream revert in the Lido report, except here it hits the escrow-redemption path in a cross-chain intent settlement flow.

### Impact Explanation
When escrow is overstated relative to actual token balance:
- The `withdraw()` transfer for that order (and potentially subsequent orders sharing the same token pool) reverts due to insufficient contract balance, permanently denying settlement of the fill/refund for that commitment — a fund-lock DoS on intent settlement, matching the "Contract functionality DoS" impact in the source report.
- Because escrow crediting is decoupled from actual received balance, the aggregate `_orders[...][token]` ledger across multiple orders can exceed the contract's real token holdings, so a later order's legitimate withdrawal can fail even though that specific order's tokens were transferred correctly — cross-order griefing/insolvency within the shared token pool.
- This impacts the intent settlement/escrow custody path, a directly bounty-relevant surface for stealing, locking, or misallocating bridged funds.

### Likelihood Explanation
Any unprivileged user placing an order with a fee-on-transfer or rebasing/shares-accounted ERC-20 (stETH-like tokens are explicitly called out in the seed report) as an input token triggers this on the Tron deployment. No malicious relayer, prover, or governance actor is needed — the caller of `placeOrder` is the ordinary order-placing user, and the discrepancy is purely a consequence of token semantics vs. the contract's unchecked accounting.

### Recommendation
Port the balance-before/after reconciliation from the mainline EVM `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol` lines 288-292) into the Tron variant's non-predispatch escrow loop, so `_orders[commitment][token]` and the commitment-hashed `order.inputs`/`reducedInputs` reflect the actually-received balance rather than the nominal requested amount.

### Proof of Concept
1. Deploy `evm/tron/contracts/apps/IntentGatewayV2.sol` with a token that implements a small transfer shortfall (e.g., a mock ERC20 whose `transferFrom` delivers `amount - 2` due to internal share rounding, mirroring stETH).
2. Call `placeOrder` with `order.inputs[0].amount = X` for that token, taking the non-predispatch branch (lines 444-463).
3. Observe: `IERC20(token).safeTransferFrom(msg.sender, address(this), X)` actually moves `X - 2` tokens, but `_orders[commitment][token]` is credited with `reducedInputs[0].amount` derived from the full `X` (minus protocol fee only).
4. On fill/redemption, `withdraw()` attempts `token.call(transfer(beneficiary, amount))` for the full committed amount; with insufficient real balance in the contract (short by 2 wei plus any prior orders' shortfalls), the transfer call fails and `withdraw()` reverts, permanently blocking escrow release for that commitment.
