### Title
Coarse `(filePath, category)` dedup key lets a new dangerous finding in an already-flagged file/category go unreported - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
`handle_commit_review_posttooluse` and `handle_push_sweep_posttooluse` record previously-shown vulnerability findings into shared session state keyed only on `(filePath, category)`, not on the actual vulnerable code or line. Because `_dedup_against_state` suppresses new LLM findings that match anything already in `previous_findings`, any subsequent, genuinely different dangerous change in the same file that the LLM classifies under the same category is silently dropped and never surfaces a warning or asyncRewake.

### Finding Description
Both the commit-review and push-sweep handlers persist findings for dedup purposes using a coarse key: [1](#0-0) 

and identically in push-sweep: [2](#0-1) 

The comment explicitly documents the tradeoff: `vulnerableCode` bytes drift between fires, so the key intentionally ignores the actual vulnerable snippet and matches only on `(filePath, category)`. This same `previous_findings` set is fed as the `prompted` set into `_dedup_against_state(session_id, vulns, prompted=_finding_keys(previous_findings))` for both `handle_commit_review_posttooluse` (`start=1322,end=1324`) and `handle_push_sweep_posttooluse` (`start=1625,end=1627`): [3](#0-2) [4](#0-3) 

`previous_findings` is shared across the Stop hook, commit-review, and push-sweep surfaces and lives for `PREVIOUS_FINDINGS_TTL_SEC` (default 3600s): [5](#0-4) 

Exploit flow: an attacker-controlled session first introduces (or the LLM flags) any vulnerability of category `"Command Injection"` (or any category) in file `X`. That finding is recorded as `{filePath: X, category: "Command Injection"}` in `previous_findings`. Within the TTL window, the attacker (via ordinary edits/commits/amends/pushes) introduces a completely different, more severe command-injection vulnerability elsewhere in the same file `X`. Because the LLM re-classifies it under the same category string, `_finding_keys`/`_dedup_against_state` treats it as already-known and drops it from `new_vulns`, so no warning is emitted and no `exit(2)` rewake occurs — even though the actual dangerous code differs entirely. This defeats the design invariant stated in the module docstring that dangerous edits must "stay reviewable and blockable ... across retries, amends, and pushes," since retries/amends/pushes all consult the same coarse-keyed `previous_findings` state.

None of the existing safeguards (rate limiting, `_reviewed_shas` SHA-exact tracking, amend-delta scoping, cross-repo guards) protect against this because they operate on a different axis (which commits/SHAs were reviewed, not which specific vulnerabilities were shown). The `(filePath, category)` key is a content-insensitive session-level cache that outlives individual commits/pushes.

### Impact Explanation
A genuinely new and potentially more severe vulnerability (e.g., a second, unrelated command-injection or hardcoded-secret introduction in a file that previously had an unrelated/lower-severity finding of the same category) is silently suppressed from the Stop hook, commit review, and push sweep. This breaks the reviewability/blockability guarantee the plugin exists to enforce, allowing dangerous code to reach a commit/push without triggering the intended asyncRewake review-and-block cycle — a security-control bypass with real downstream impact (unreviewed dangerous code reaching `main`/pushed branches).

### Likelihood Explanation
No special privileges are required — only normal editing/commit/push activity within one Claude Code session (or any session sharing the state file) inside the `PREVIOUS_FINDINGS_TTL_SEC` window (1 hour by default). Any file that accumulates two distinct findings of the same LLM-assigned category during that window will hit this suppression. This is a systemic per-file/per-category collision, not a rare edge case, given the plugin's own comment acknowledges the dedup key is intentionally coarse.

### Recommendation
Tighten the dedup key so it distinguishes distinct vulnerabilities in the same file/category, e.g., by keying on `(filePath, category, line_hint)` or a normalized/fuzzy hash of `vulnerableCode` that tolerates line-shift/context drift (rather than dropping content matching entirely), or by capping how many findings of the same category can be silently suppressed per file. At minimum, cap the TTL-based suppression to identical or near-identical vulnerable code, not just the same category label.

### Proof of Concept
Integration test plan:
1. Seed session state with `previous_findings = [{"filePath": "app.py", "category": "Command Injection", "vulnerableCode": "os.system(user_input)"}]` and a fresh `previous_findings_ts`.
2. Simulate a commit whose diff introduces a different, unrelated command-injection sink in `app.py`, e.g. `subprocess.call(shell_cmd, shell=True)` at a different line, and mock `analyze_code_security`/`agentic_review` to return this as a new finding with `category: "Command Injection"`.
3. Invoke `handle_commit_review_posttooluse` (or `handle_push_sweep_posttooluse`) with a valid commit/push output so `commit_succeeded`/push detection passes.
4. Assert: expected behavior is `exit(2)` with the new vulnerability surfaced via `_format_vulns_guidance`; actual (buggy) behavior is `sys.exit(0)` with `vulns_found: 0` in metrics because `_dedup_against_state` treats `(app.py, Command Injection)` as already prompted, confirming the new distinct dangerous change is never reported.
