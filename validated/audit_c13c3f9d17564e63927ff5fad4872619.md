### Title
GitHub Repository Identity Is Keyed by Mutable `owner login + name` Instead of GitHub's Immutable Repository ID, Enabling Repo-Jacking Impersonation - ([File: app/src/lib/stores/repositories-store.ts])

### Summary
The external report's broken invariant is: a destroyable/reusable *name* is treated as a permanent identity, so an attacker can re-register that name and inherit trust built around the old identity. The same class of bug exists in GitHub Desktop's local repository cache: GitHub repositories are looked up and upserted in the local Dexie database by the mutable pair `[ownerID, name]` (owner login + repo name) rather than GitHub's immutable numeric repository ID, and `Owner` records are keyed by `endpoint + login` rather than the immutable GitHub user/org ID.

### Finding Description
`RepositoriesStore._upsertGitHubRepository` resolves the "existing" GitHub repository record purely by owner and name: [1](#0-0) 

and if a match is found, it treats it as the same logical repository, carrying forward stored fields such as `permissions` and `parentID`: [2](#0-1) 

The `Owner` lookup that feeds into this key is itself keyed by `endpoint + login` (a mutable GitHub username/org slug), and `putOwner` will happily reuse/update the same `Owner` row when it sees a login match, rather than pinning to a GitHub account ID: [3](#0-2) 

GitHub allows account/org renames and deletions, after which the vacated login string becomes available for anyone to register (a well-known "repo-jacking"/"namesquatting" primitive on GitHub itself). Once an attacker claims the old owner login and creates a repository with the same name that a victim previously had tracked in Desktop, any code path that re-resolves the GitHub association for a locally tracked repository — e.g. `repositoryWithRefreshedGitHubRepository`, which calls `matchGitHubRepository` and then `api.fetchRepository(owner, name)` and finally `upsertGitHubRepository` — will match the attacker's new repository against the *same* local `GitHubRepository`/`Repository` record used for the previously trusted project: [4](#0-3) 

The remote URL is also updated to the attacker's new remote (`updateRemoteUrl`) as part of this same flow, meaning Desktop will silently repoint the user's local clone's `origin` at the attacker-controlled remote while preserving the same visible repository identity/history in the Desktop UI. Higher-level matching functions used for "Open in Desktop" deep links and PR-checkout flows (`doesRepositoryMatchUrl`, `repositoryMatchesRemote`, `matchGitHubRepository`) are all built on the same owner/name-derived URL equality rather than an immutable GitHub repository ID: [5](#0-4) [6](#0-5) 

No guard exists anywhere in this path that checks GitHub's numeric `id` field to detect that the "matched" repository is in fact a brand-new object with a reused name/owner rather than the original.

### Impact Explanation
This lets an attacker who reclaims a deleted/renamed GitHub owner login and repo name hijack the identity that a victim's Desktop client already trusts. Consequences include:
- The victim's `origin` remote is silently updated to point at the attacker's repository (`updateRemoteUrl`), so subsequent fetches/pulls/pushes and "Open in Desktop"/PR-checkout flows operate against attacker-controlled content without any renaming/ownership-change warning surfaced to the user.
- Stale `permissions`/`parentID` metadata can be carried over from the old repository into the new, attacker-controlled one, potentially affecting UI trust indicators (e.g., write-access assumptions).
- Because matching for deep-link "Open in Desktop" (`openOrCloneRepository`, `doesRepositoryMatchUrl`) and PR checkout (`getRepositoryFromPullRequest`) also rely on owner/name-derived URLs rather than immutable IDs, a crafted `x-github-client://` / `github-mac://openRepo/` link or a malicious PR pointing at the reclaimed owner/name can cause Desktop to associate/checkout against the impersonating repository.

This does not achieve arbitrary code execution or credential exfiltration by itself, but it corrupts what remote the user's local repository is bound to and what identity is displayed for it — a silent-corruption/impersonation impact in the same class as the vault-name-reuse report (identity confusion enabling users to unknowingly interact with an attacker-controlled entity that has assumed a reputable name).

### Likelihood Explanation
Exploitation requires the attacker to successfully claim a previously-used GitHub owner login (or repo name under the same owner) after the original is renamed or deleted — a scenario GitHub itself permits and is a documented real-world technique ("repo-jacking"). It requires no local/physical access, no admin rights, and no prior malware; the victim simply needs to have previously added the original repository in Desktop and to trigger a routine refresh/PR-checkout/deep-link flow afterward. Likelihood is moderate: it depends on external GitHub-side conditions (owner rename/deletion + attacker re-registration) rather than a flaw purely within Desktop, similar to how the original report's exploit also depended on a vault being closed/removed first.

### Recommendation
Key local `Owner` and `GitHubRepository` records by GitHub's immutable numeric IDs (`owner.id`, `repository.id`) rather than by `login`/`name` strings. When refreshing a tracked repository's GitHub association (`repositoryWithRefreshedGitHubRepository`, `_upsertGitHubRepository`), verify that the fetched repository's immutable ID matches the previously stored ID before reusing/overwriting the local record or updating the `origin` remote; if the ID differs, treat it as a new/unrelated repository and surface a warning to the user (e.g., "This repository's owner or name matches one you have open, but it is a different repository") rather than silently merging identities or rewriting the remote URL.

### Proof of Concept
1. Victim clones `github.com/acme/tool` in Desktop; Desktop stores an `Owner` row keyed by `(endpoint, "acme")` and a `GitHubRepository` row keyed by `(ownerID, "tool")`, associated with the victim's local `Repository`.
2. The `acme` account/org is later renamed or deleted on GitHub.
3. Attacker registers the now-available login `acme` and creates a new repository named `tool`.
4. Victim performs any action that triggers `repositoryWithRefreshedGitHubRepository` (e.g. app refresh) — see [4](#0-3) . `matchGitHubRepository`/`api.fetchRepository('acme', 'tool')` returns the attacker's new repository, and `_upsertGitHubRepository`'s `[ownerID+name]` lookup at [1](#0-0)  matches and overwrites the existing local `GitHubRepository` record, and `updateRemoteUrl` repoints the victim's `origin` remote to the attacker's clone URL — with no ID-based check to detect that this is a different underlying repository.

  private async putOwner(
    endpoint: string,
    login: string,
    ownerType?: GitHubAccountType
  ): Promise<Owner> {
    const key = getOwnerKey(endpoint, login)
    const existingOwner = await this.db.owners.get({ key })
    let id

    // Since we look up the owner based on a key which is the product of the
    // lowercased endpoint and login we know that we've found our match but it's
    // possible that the case differs (i.e we found `usera` but the actual login
    // is `userA`). In that case we want to update our database to persist the
    // login with the proper case.
    if (
      existingOwner === undefined ||
      existingOwner.login !== login ||
      // This is added so that we update existing owners with an undefined type.
      (ownerType !== undefined && existingOwner.type !== ownerType)
    ) {
      id = existingOwner?.id
      const existingId = id !== undefined ? { id } : {}
      id = await this.db.owners.put({
        ...existingId,
        key,
        endpoint,
        login,
        type: ownerType,
      })
    } else {
      id = forceUnwrap('Missing owner id', existingOwner.id)
    }

    return new Owner(login, endpoint, id, ownerType ?? existingOwner?.type)

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

/**
 * Check whether or not a GitHub repository matches a given remote.
 *
 * @param gitHubRepository the repository containing information from the GitHub API
 * @param remote the remote details found in the Git repository
 */
export function repositoryMatchesRemote(
  gitHubRepository: GitHubRepository,
  remote: IRemote
): boolean {
  return (
    urlMatchesRemote(gitHubRepository.htmlURL, remote) ||
    urlMatchesRemote(gitHubRepository.cloneURL, remote)
  )
}

  private doesRepositoryMatchUrl(
    repo: Repository | CloningRepository,
    url: string
  ): repo is RepositoryWithGitHubRepository {
    if (repo instanceof Repository && isRepositoryWithGitHubRepository(repo)) {
      const originRepoUrl = repo.gitHubRepository.htmlURL
      const upstreamRepoUrl = repo.gitHubRepository.parent?.htmlURL ?? null

      if (originRepoUrl !== null && urlsMatch(originRepoUrl, url)) {
        return true
      }

      if (upstreamRepoUrl !== null && urlsMatch(upstreamRepoUrl, url)) {
        return true
      }
    }

    return false
  }
