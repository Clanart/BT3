### Title
OP_RETURN `data` output is excluded from the transaction fee and weight calculation, so added bytes are never paid for - (networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends a caller-supplied OP_RETURN output to `tx_outs`, but computes `needed_fee` and the standard-weight check on a transaction that only contains `payments` (and optionally `change`). The fee is therefore charged for a smaller transaction than the one actually signed, exactly the bug class of the reference issue where the caller performs an operation without paying its full fee.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` at `networks/bitcoin/src/wallet/send.rs:194-202`, before the fee is calculated. However, the weight/vbytes are computed at line 204 via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, which only models `payments` and never the data output (`send.rs:85-93` builds outputs exclusively from `payments`). The recomputation for change at lines 224-235 likewise omits the OP_RETURN output. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` underprices the real transaction by `fee_per_vbyte` × ~91 vbytes (a zero-value `TxOut` plus up to 80 push bytes, all non-witness).
- The `MAX_STANDARD_TX_WEIGHT` check at line 241 uses `weight`/`weight_with_change`, which also never includes the data output, so a transaction can pass the check while its true weight exceeds the standardness limit.
- The `NotEnoughFunds` check at line 215 is evaluated against this understated fee.

The actual fee paid is `sum(inputs) - sum(outputs)` (see `fee()` at `send.rs:138-141`), which equals the underpriced `needed_fee`; the deficit for the data bytes is silently absorbed by the fixed fee budget rather than charged to the caller who supplied `data`.

### Impact Explanation
A signed transaction can pay a fee rate materially below the requested `fee_per_vbyte` — potentially below relay/mining minimums despite passing the `TooLowFee` guard — or exceed `MAX_STANDARD_TX_WEIGHT` while passing the `TooLargeTransaction` check. In both cases the transaction may be unrelayable after the threshold signature has already been produced, stalling or effectively burning the spend. Callers are never charged for the marginal vbytes their `data` adds, so the multisig's inputs subsidize arbitrary up-to-80-byte payload inclusion.

### Likelihood Explanation
Any caller of `SignableTransaction::new` with a non-`None` `data` argument triggers the underpricing; the missing bytes scale with `fee_per_vbyte`, and the standard-weight bypass is deterministic whenever the transaction is already near the limit. It requires no special blockchain state.

### Recommendation
Include the OP_RETURN output when sizing the transaction: pass a payment-style `(script_pubkey, 0)` entry for the data output (or extend `calculate_weight_vbytes` to accept `tx_outs`) in both the initial calculation at line 204 and the `fee_with_change` recomputation at lines 225-227, and compute the `MAX_STANDARD_TX_WEIGHT` check on the fully-formed transaction rather than on the payment-only skeleton.
