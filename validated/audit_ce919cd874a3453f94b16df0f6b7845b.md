## Finding [1](#0-0) 

### Title
Unbalanced `global_context` rollback stack when `get_readonly_asset_map` errors inside `restrict-assets?`/`as-contract?` - (File: `clarity/src/vm/functions/post_conditions.rs`)

### Summary
`evaluate_body_with_allowance_check` (shared by the `restrict-assets?` and `as-contract?` special forms) opens a nested rollback context with `exec_state.global_context.begin()` and then correctly scopes the body evaluation's `?` usage inside a closure so that a body error is turned into a value the function can act on. However, immediately after that closure, the function calls `exec_state.global_context.get_readonly_asset_map()?` directly with the `?` operator — outside of any closure and without the matching `roll_back()`/`commit()` that every other exit path performs. [2](#0-1) 

This is the same bug class as the reported SputnikVM issue: `begin_inter_transaction` (there) / `global_context.begin()` (here) pushes a new layer onto a transaction/rollback stack, and a later fallible call is allowed to short-circuit with `?` before the corresponding "pop" (`end_inter_transaction` / `roll_back()`/`commit()`) runs.

### Finding Description
Every other exit from `evaluate_body_with_allowance_check` explicitly balances the `begin()` call:
- Rejectable body error → `roll_back()` then return the error.
- Allowance violation → `roll_back()` then return `Ok(err ...)`.
- `check_allowances` error → `roll_back()` then return the error.
- Success → `commit()` then return `Ok(...)`. [3](#0-2) 

But the call `exec_state.global_context.get_readonly_asset_map()?` at line 405 is not inside a closure and is not followed by any cleanup on the error path — if it returns `Err`, the function returns immediately with the `begin()` context still open on `GlobalContext`'s internal rollback-context stack, exactly mirroring the "pushed a new execution stack ... enters ... with Rust's `?` syntax ... returns directly without any further clean-up" pattern described in the external report.

### Impact Explanation
`GlobalContext` (and its underlying MARF/datastore rollback-wrapper) is reused across the whole block of transactions being processed, not just within a single Clarity call. If a nested context is left open because of this early return, the block-level bookkeping of nested contexts becomes inconsistent for the remainder of block processing: a `commit()`/`roll_back()` performed by an enclosing caller (e.g., `run_contract_call`, or the transaction-level rollback that `db/transactions.rs` performs on error) would then be operating against the wrong depth, which can cause writes that should have been rolled back to be committed (or vice versa) for this or subsequent transactions in the same block — i.e., assets moving past what the post-conditions/allowances were supposed to enforce, or a divergence between what one node computes versus another depending on whether/when `get_readonly_asset_map` fails in their execution environment.

### Likelihood Explanation
`get_readonly_asset_map` is documented/used elsewhere as fallible (`.expect("failed to get asset map")` in tests), so it is not a function whose error path is unreachable in principle. The report's own reasoning applies directly here as well: this path is more likely to be hit in unusual states (e.g., after a database/MARF migration or in edge cases of the asset-map accounting) than in ordinary correct execution, but because `restrict-assets?`/`as-contract?` are ordinary Clarity special forms reachable by any contract, an attacker/contract author does not need any privileged role to reach this code path — they just need a contract that uses `restrict-assets?` or `as-contract?` and can trigger the rare error condition in `get_readonly_asset_map`.

I was not able to inspect the full implementation of `GlobalContext::begin`/`roll_back`/`commit`/`get_readonly_asset_map` in `clarity/src/vm/contexts.rs` within the available search budget, so I cannot fully confirm the exact conditions under which `get_readonly_asset_map` returns `Err`, nor precisely characterize the downstream effect of an unbalanced context on block commit semantics. This should be verified against `clarity/src/vm/contexts.rs` before treating the severity as final.

### Recommendation
Wrap the `get_readonly_asset_map()?` call (and any other fallible call between `begin()` and the final `roll_back()`/`commit()`) inside the same closure pattern already used for the body evaluation, or otherwise ensure that any early return from `evaluate_body_with_allowance_check` after `global_context.begin()` performs `roll_back()` first — mirroring the fix Tezos applied for `execute_fa_withdrawal`.

### Proof of Concept
Not concretely constructible from the available context: reproducing the bug requires an input that makes `GlobalContext::get_readonly_asset_map()` return `Err` while inside a `restrict-assets?`/`as-contract?` body, and I could not confirm from the indexed code what conditions trigger that error. fn evaluate_body_with_allowance_check(
    asset_owner: &PrincipalData,
    allowances: Vec<Allowance>,
    body_exprs: &[SymbolicExpression],
    invoke_ctx: &InvocationContext,
    exec_state: &mut ExecutionState,
    context: &LocalContext,
) -> Result<Value, VmExecutionError> {
    let epoch = *exec_state.epoch();
    exec_state.global_context.begin();

    // Evaluate the body expressions inside a closure so `?` only exits the closure
    let eval_result: Result<Option<Value>, VmExecutionError> =
        (|| -> Result<Option<Value>, VmExecutionError> {
            let mut last_result = None;
            for expr in body_exprs {
                let result =
                    eval(expr, exec_state, invoke_ctx, context)?.clone_with_cost(exec_state)?;
                last_result.replace(result);
            }
            Ok(last_result)
        })();

    // A block-rejecting error raised inside the body must abort the transaction.
    if matches!(&eval_result, Err(err) if err.rejectable()) {
        exec_state.global_context.roll_back()?;
        return Err(eval_result.unwrap_err());
    }

    let asset_maps = exec_state.global_context.get_readonly_asset_map()?;

    // If the allowances are violated:
    // - Rollback the context
    // - Return an error with the index of the violated allowance
    match check_allowances(asset_owner, allowances, asset_maps, epoch) {
        Ok(None) => {}
        Ok(Some(violation_index)) => {
            exec_state.global_context.roll_back()?;
            return Ok(Value::error(Value::UInt(violation_index))?);
        }
        Err(e) => {
            exec_state.global_context.roll_back()?;
            return Err(e);
        }
    }

    exec_state.global_context.commit()?;
