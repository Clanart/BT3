### Title
Value sent with `distribution` precompile's `rewards()` call is permanently stranded — ([File: precompiles/distribution/distribution.go])

### Summary
The `distribution` precompile at `0x0000000000000000000000000000000000001007` dispatches the `RewardsMethod` to `p.rewards(ctx, method, args)` without ever inspecting or validating the `value` sent with the EVM call, and `rewards()` never refunds or otherwise consumes that value. Any usei/wei attached to a `rewards(address)` call is transferred into the precompile module account with no code path to reclaim it — the direct analog of the reported "stuck ETH in a contract with a `receive()` but no withdrawal" bug class.

### Finding Description
In `Execute()`, most other read-only distribution methods (`ValidatorOutstandingRewardsMethod`, `ValidatorCommissionMethod`, `DelegationRewardsMethod`, etc.) still pass `value` through to their handlers, but `WithdrawValidatorCommissionMethod` explicitly calls `pcommon.ValidateNonPayable(value)` before proceeding: [1](#0-0) 

`RewardsMethod`, however, is dispatched to `p.rewards(ctx, method, args)` — note the `value` argument is dropped entirely from the call site: [2](#0-1) 

And the `rewards()` implementation itself never checks or refunds `value`: [3](#0-2) 

Other payable precompile transaction handlers (e.g. `bank`'s `sendNative`) explicitly route the attached value through `pcommon.HandlePaymentUseiWei`/`HandlePaymentUsei` to either spend it meaningfully or refund the caller: [4](#0-3) 

The `distribution` precompile address is also not registered in `payablePrecompiles`, so no special event suppression/handling exists for value sent to it outside the explicit refund calls each handler is expected to make: [5](#0-4) 

This exact quirk is independently documented in the integration test suite, which deliberately skips a "view rejects value" assertion for `rewards()` because a value-bearing call succeeds and strands the funds: [6](#0-5) 

This pattern (present in the current `precompiles/distribution/distribution.go` and mirrored in most legacy versions such as `v67`, `v640`, `v630`, etc.) means any EOA or contract that mistakenly (or is tricked into) attaching `msg.value` to a `rewards(address)` call on `0x...1007` loses that value permanently, with no `receive()`-style analog withdraw function anywhere in the distribution precompile to recover it.

### Impact Explanation
Any unprivileged transaction sender who calls `rewards(address)` on the distribution precompile with a non-zero `value` field has that usei/wei permanently and irrecoverably transferred into the precompile's underlying module account, since the query handler neither rejects the payment nor refunds it, and there is no other precompile method to withdraw arbitrary balance from that account. This constitutes a permanent freezing/loss of user funds reachable directly from a single submitted EVM transaction — no privileged role or multi-step exploit required.

### Likelihood Explanation
Likelihood is moderate: this requires a caller to attach native value to what is semantically a read-only/view call, which is unusual but entirely possible for contracts or SDKs that unconditionally forward `msg.value` in generic call-forwarding patterns (e.g., multicall/router contracts, or wallets that don't distinguish payable vs. view ABI entries), or through user/tooling error. Because Solidity `view`/non-payable ABI declarations for the interface would normally prevent this at the caller's compile time, the bulk of exposure comes from raw low-level calls or misconfigured integrations, but the on-chain enforcement gap fully mirrors the reported bug class and is directly demonstrable via a raw `eth_sendTransaction`/`eth_call`-style transaction with calldata for `rewards(address)` and non-zero value.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` to the `RewardsMethod` case in `Execute()` (matching the pattern already used for `WithdrawValidatorCommissionMethod` and other non-payable handlers), so that any value-bearing call to `rewards()` reverts instead of silently stranding funds. Audit all other view/query methods in the distribution precompile (and its legacy versions) to confirm they either reject non-zero `value` or explicitly refund it, consistent with the pattern already applied elsewhere in the codebase.

### Proof of Concept
1. An EOA sends an EVM transaction to `0x0000000000000000000000000000000000001007` with calldata encoding `rewards(address delegator)` and `value = 1 SEI`.
2. `x/evm` routes the call into `PrecompileExecutor.Execute`, which matches `RewardsMethod` and calls `p.rewards(ctx, method, args)` — `value` is discarded at the call site: [2](#0-1) .
3. `rewards()` proceeds to query and pack the rewards output without ever touching `value`: [3](#0-2) .
4. The transaction succeeds and returns the rewards data, but the 1 SEI attached to the call is now held by the precompile's account with no method in the distribution precompile ABI capable of withdrawing it back to the sender.

```go
func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
```
