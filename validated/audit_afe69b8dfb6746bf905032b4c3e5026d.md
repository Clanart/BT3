### Title
GitHub credential-helper trusts an attacker-controlled `WWW-Authenticate` header/hostname substring match to classify a remote as "GitHub Enterprise," triggering the native GitHub sign-in flow against an attacker's server - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
The Sherlock bug is a broken invariant: a security-relevant decision (slippage protection) is computed from the wrong reference price (OP/USD, OP/ETH) instead of the actual traded asset (alUSD/alETH), so the check doesn't validate what it claims to validate and an attacker can exploit the mismatch. The GitHub Desktop analog is `getEndpointKind()` in `trampoline-credential-helper.ts`, which decides whether a git remote is a trustworthy "GitHub"/"enterprise" endpoint. Instead of authoritatively verifying the host belongs to GitHub, it substitutes weaker/attacker-controlled signals — a substring match on the git server's own HTTP response header, and a loose hostname regex — as proxies for "this is GitHub."

### Finding Description
`getEndpointKind()` is invoked from the credential-helper trampoline whenever git needs credentials for a remote (`get`/`store`/`erase`), i.e. on every `fetch`/`clone`/`push`. It walks through several checks to decide if the target host is `'github.com'`, `'ghe.com'`, `'enterprise'`, or `'generic'`: [1](#0-0) 

The `wwwauth[...]` loop trusts a value that comes straight from the remote git server's HTTP response (the `WWW-Authenticate` header, forwarded by git to the credential helper) and classifies the endpoint as `'enterprise'` if that header merely `.includes('realm="GitHub"')` — with no verification that the host is actually a GitHub instance. Any malicious/compromised git server or on-path proxy fully controls this header for arbitrary hostnames.

If that heuristic doesn't fire, the fallback `isGitHubHost()` in `app/src/lib/api.ts` uses a similarly loose invariant substitution — a regex substring match on the hostname instead of an authoritative check: [2](#0-1) 

This is the same pattern as the Sherlock bug: a value that superficially resembles "the real thing" (a header claiming `realm="GitHub"`, or a hostname containing the substring `github.`) is used in place of the actual authoritative signal (verified TLS-trusted origin match / meta-endpoint check), and the substitute value is entirely attacker-controlled.

The consequence of misclassification as `'enterprise'` is that `getCredential()` calls `ui.promptForGitHubSignIn(endpoint)`: [3](#0-2) 

`promptForGitHubSignIn()` then begins the app's native GitHub Enterprise sign-in flow bound to the attacker's origin: [4](#0-3) 

The endpoint is passed to `setEndpoint()` in `sign-in-store.ts`, which only validates URL syntax/protocol (`https`), not that the host is actually GitHub: [5](#0-4) 

### Impact Explanation
An attacker who controls a git remote (self-hosted server, compromised mirror, or MITM proxy on an HTTP(S) git transport) can, purely by controlling their own server's response headers, make GitHub Desktop believe an arbitrary host is a "GitHub Enterprise" instance. This causes Desktop to spontaneously pop the native "Sign in to GitHub Enterprise" dialog and drive the OAuth/enterprise-authentication flow against the attacker's chosen origin the moment the victim clones/fetches from the attacker's repository — without the user ever intending to add that host as a GitHub account. This is an unprompted, attacker-triggered unauthorized OAuth/account-binding flow (the category explicitly called out as valid impact: "unauthorized OAuth or account binding"), and it originates purely from cloning/fetching a malicious repository / interacting with a malicious remote's HTTP responses — no local access, no pre-existing malware, no leaked credentials, and no unnatural user steps are required beyond the normal act of fetching from a remote the user added.

### Likelihood Explanation
Triggering the `wwwauth[]` path requires only that the attacker's git HTTP server answer an authentication challenge with a `WWW-Authenticate` header containing the substring `realm="GitHub"` — something entirely within the attacker's control and requiring no cooperation from GitHub or the real github.com domain. The hostname-regex fallback in `isGitHubHost()` is similarly triggerable with cheap domain choices (e.g., `github.attacker.com`). Both paths run automatically as part of ordinary git operations (`fetch`, `clone`, `push`) via the trampoline credential helper, so likelihood of the classification firing is high whenever a user interacts with an attacker-controlled remote.

### Recommendation
Replace the substring/regex-based "looks like GitHub" heuristics with authoritative checks: verify the host against a known/trusted endpoint list or an already-configured, matching account origin, and require the discovery request (`/meta` with `x-github-request-id`) confirmation, rather than trusting attacker-supplied `WWW-Authenticate` header content or the mere presence of the substring "github." anywhere in the hostname, before allowing the sign-in flow to bind a new endpoint. At minimum, do not auto-launch `promptForGitHubSignIn` for hosts classified only via the `wwwauth[]`/regex heuristics without additional confirmation from the user that they intend to add this specific host as a GitHub Enterprise account.

### Proof of Concept
1. Attacker stands up an HTTP(S) git server at `https://attacker.example.com/evil.git` (or performs a MITM on an insecure git transport).
2. Attacker configures the server so that any unauthenticated git request receives a `401` response with header:
   `WWW-Authenticate: Basic realm="GitHub"`
3. Victim adds/clones this remote in GitHub Desktop and performs a `fetch`.
4. Git's credential-helper protocol invokes GitHub Desktop's trampoline `get` command; `parseCredential` captures the `wwwauth[...]` header value and passes it into `getEndpointKind()`.
5. Because `v.includes('realm="GitHub"')` matches, `getEndpointKind` returns `'enterprise'` for `attacker.example.com` — a host that is not GitHub at all.
6. `getCredential()` finds no matching stored account for this apiEndpoint and calls `ui.promptForGitHubSignIn('https://attacker.example.com/...')`.
7. `promptForGitHubSignIn` calls `dispatcher.beginEnterpriseSignIn` and `setSignInEndpoint(origin)` with the attacker's origin, and shows the native GitHub sign-in popup — the victim is now driven through Desktop's trusted sign-in UI pointed at the attacker's server, without ever manually choosing to add that account.

  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.

    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })

  public async setEndpoint(url: string): Promise<void> {
    const currentState = this.state

    if (
      currentState?.kind !== SignInStep.EndpointEntry &&
      currentState?.kind !== SignInStep.ExistingAccountWarning
    ) {
      const stepText = currentState ? currentState.kind : 'null'
      return fatalError(
        `Sign in step '${stepText}' not compatible with endpoint entry`
      )
    }

    /**
     * If the user enters a github.com url in the GitHub Enterprise sign-in
     * flow we'll redirect them to the GitHub.com sign-in flow.
     */
    if (/^(?:https:\/\/)?(?:api\.)?github\.com($|\/)/.test(url)) {
      this.beginDotComSignIn(currentState.resultCallback)
      return
    }

    this.setState({ ...currentState, loading: true })

    let validUrl: string
    try {
      validUrl = validateURL(url)
    } catch (e) {
      let error = e
      if (e.name === InvalidURLErrorName) {
        error = new Error(
          `The GitHub Enterprise instance address doesn't appear to be a valid URL. We're expecting something like https://example.ghe.com.`
        )
      } else if (e.name === InvalidProtocolErrorName) {
        error = new Error(
          'Unsupported protocol. Only https is supported when authenticating with GitHub Enterprise instances.'
        )
      }

      this.setState({ ...currentState, loading: false, error })
      return
    }
