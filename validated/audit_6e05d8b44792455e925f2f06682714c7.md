### Title
Webhook HMAC signature validates payload origin but not shop attribution, enabling cross-shop webhook spoofing - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
The reported Biconomy bug is a class of "signature is structurally valid but not bound to the correct principal" — `checkSignature` accepted any `_signer` whose `isValidSignature` returned the magic value, without checking that the signer was actually the wallet owner. The `shopify_app` webhook verification path has the same structural flaw: `hmac_valid?` proves the request body was signed with the app's secret, but the shop identity attached to that request (`X-Shopify-Shop-Domain` header) is never bound to, or validated against, that signature.

### Finding Description
`ShopifyApp::WebhookVerification#verify_request` only checks that the raw POST body's HMAC matches the app's shared secret: [1](#0-0) 

The underlying comparison in `PayloadVerification#hmac_valid?` recomputes the HMAC only over `data` (the raw body) and compares it to the `HTTP_X_SHOPIFY_HMAC_SHA256` header: [2](#0-1) 

Notice `shop_domain` is read directly from the `X-Shopify-Shop-Domain` header and is not part of the HMAC-covered data at all: [3](#0-2) 

The generated webhook controller (and the built-in `WebhooksController`) then dispatches jobs using that unauthenticated header value as the shop identity, alongside the (correctly-signed) body: [4](#0-3) [5](#0-4) 

Because the app's webhook secret (`ShopifyApp.configuration.secret`) is a single shared secret for the whole app (not per-shop), any shop that has the app installed can receive a genuinely Shopify-signed webhook body+HMAC for its own store. That attacker-controlled shop can then re-POST the exact same body and `X-Shopify-Hmac-Sha256` value directly to the app's public webhook endpoint, but with the `X-Shopify-Shop-Domain` header swapped to a victim shop's domain. `hmac_valid?` still returns true (it never looked at the header), so `verify_request` passes, and the downstream job is enqueued with `shop_domain` = the spoofed victim domain and `webhook` = attacker-supplied body content.

### Impact Explanation
This lets any unrelated merchant who has installed the app forge webhook events "as" another shop, from the app's perspective: fabricated `orders/create`, `customers/create`, `app/uninstalled`, GDPR (`shop/redact`, `customers/redact`) or any other subscribed topic can be injected and attributed to a shop the attacker does not control. Depending on what the app's job classes do with `shop_domain` (e.g., write records, trigger redaction/deletion of a shop's data, mark a shop as uninstalled, or trigger fulfillment/refund logic keyed off webhook content), this is a cross-shop data-integrity/business-logic bypass driven purely by an anonymous-relative-to-victim, unprivileged HTTP request with a forged header — the direct analog of accepting an "always-valid" signer without checking whose signature it actually is.

### Likelihood Explanation
Reachable by any actor who can install the app on a store they control (a standard, unprivileged action for any Shopify merchant) and can issue direct HTTP POSTs to the app's public webhook route. No secret leakage or host access is required — only reuse of a webhook the attacker's own store legitimately received.

### Recommendation
Bind the shop identity to the signed payload rather than trusting an unsigned header: verify the `shop`/`X-Shopify-Shop-Domain` value against the shop encoded in the webhook body itself where possible, and additionally confirm the shop referenced by the webhook has an active, matching session/installation in `SessionRepository` before processing job side effects. Consider incorporating the shop domain into the HMAC-covered data if using custom verification, or explicitly cross-check header vs. payload shop fields in `WebhookVerification#verify_request` before allowing the request to proceed.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining a legitimately Shopify-signed webhook (e.g., `orders/create`) delivered to the app's public webhook endpoint, capturing the raw body `B` and its valid `X-Shopify-Hmac-Sha256: H` header (computed by Shopify using the app's shared secret).
2. Attacker crafts a new HTTP POST to the same app webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since it only covers `B`), but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyApp::WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which recomputes the HMAC of `B` against the shared secret and matches `H` — request passes verification.
4. The controller (per `webhook_controller.rb.tt` / `WebhooksController#receive`) enqueues the corresponding job with `shop_domain: "victim-shop.myshopify.com"` and the attacker's `webhook` body, causing the victim shop's records/state to be mutated based on attacker-supplied webhook content.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
