### Title
OP_RETURN Data Output Excluded From Fee/Weight Calculation, Yielding Underpriced Transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the reference bug (where a "minimum" formula lets a user pay for one side while the amount minted reflects only the other), `SignableTransaction::new` charges the caller for a fee computed on a transaction shape that omits the OP_RETURN data output, yet ships a transaction that includes it. The transaction's actual size — and thus the fee rate it really pays — diverges from what was calculated and enforced.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` **before** the weight/vbytes computation:

```rust
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data).expect("data didn't fit into PushBytes depsite being checked"),
    ),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` reconstructs a template transaction whose `output` vector is built **only** from `payments` (and optionally `change`) — the data output is never included:

```rust
output: payments
  .iter()
  .map(|payment| TxOut { value: Amount::from_sat(payment.1), script_pubkey: payment.0.clone() })
  .collect(),
```

Consequences:

1. `vbytes` underestimates the real size by the serialized size of the OP_RETURN output (roughly `9 + script_len`, up to ~90 vbytes for the allowed 80-byte payload).
2. `needed_fee = fee_per_vbyte * vbytes` is therefore undercharged.
3. The minimum-relay-fee check (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) is evaluated against the same underestimated `vbytes`, so a transaction can pass `TooLowFee` validation while its *actual* fee rate is below the relay minimum.
4. When `change` is present, `change_value = input_sat - payment_sat - fee_with_change` leaves `fee_with_change` as the real fee — meaning the change output absorbs the entire underestimation: the change is *larger* than it should be by the uncharged amount, while the effective fee rate drops below `fee_per_vbyte`.

### Impact Explanation
Any caller passing `data` produces a transaction paying a strictly lower fee rate than requested — potentially below the mempool minimum relay fee, making the signed transaction non-relayable and the funds temporarily unmovable (the UTXOs are committed as inputs to a tx the network rejects). Because the `TooLowFee` guard uses the same wrong `vbytes`, the safety check gives false assurance. This is a concrete incorrect-fee formula over caller-supplied bytes (`data`, up to 80 bytes), reachable by anyone constructing a `SignableTransaction`.

### Likelihood Explanation
The `data` parameter is a public input to `SignableTransaction::new`; no privileged position is needed. The bug triggers deterministically whenever `data.is_some()`. The underestimation is proportional to `data.len()`, maximized at the 80-byte cap.

### Recommendation
Include the data output in the weight/vbytes estimation — e.g., extend `calculate_weight_vbytes` to accept the full output list (or an extra `Option<&ScriptBuf>` for the OP_RETURN script, whose length affects both the script and its pushdata encoding), and use that same accounting when computing `fee_with_change` and the minimum-relay check.

### Proof of Concept
```rust
// Conceptual: payments + 80-byte data, fee_per_vbyte = 1
let data = vec![0u8; 80];
let tx = SignableTransaction::new(inputs, &payments, Some(change), Some(data), 1).unwrap();
// tx.fee() == vbytes(computed without the ~91-byte OP_RETURN output)
// Actual published size is ~91 vbytes larger, so the real fee rate is ~
// (vbytes_no_data / (vbytes_no_data + 91)) of the requested rate — below relay min for
// fee_per_vbyte near the minimum, and the change output retains the uncharged sats.
