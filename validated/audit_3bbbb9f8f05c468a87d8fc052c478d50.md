### Title
Data Layer `verify_proof`/offer-taking accepts stale historical roots as valid without treating `current_root=False` as untrusted — analog of the notation rollback-attack advisory - ([File: chia/data_layer/data_layer_util.py])

### Summary
The GHSA-57wx-m636-g3g8 issue is that "permissive" consumers accept validly-signed but outdated/rolled-back artifacts from a compromised registry because verification doesn't enforce freshness. Chia's DataLayer proof-verification path has the same shape: `dl_verify_proof_internal()`/`dl_verify_proof()` cryptographically prove Merkle inclusion against a *puzzle hash* built from an arbitrary root supplied inside the proof, and only separately report whether that coin is *currently* unspent via a `current_root` boolean — it never rejects or fails the proof outright when the referenced state is stale/superseded.

### Finding Description
`dl_verify_proof_internal()` in [1](#0-0)  reconstructs the expected singleton puzzle hash from the caller-supplied `reference_proof.root()` and checks the Merkle inclusion proof math, but performs no check of whether the root is the *current* (latest unspent) singleton state.

`dl_verify_proof()` in [2](#0-1)  looks up the coin state for the referenced coin id and merely sets `current_root=coin_states[0].spent_height is None` — i.e., freshness is reported as a *hint field* in the response, not enforced as a hard verification failure. As the module context notes, [3](#0-2)  "Historical proofs can verify successfully while not being current." This is confirmed by the test `test_dl_proof_changed_root`, which shows the exact same proof continuing to "verify" successfully after the maker updates the store, with only the `current_root` flag flipping to `False`: [4](#0-3) .

This is structurally identical to the notation issue: a validly-signed (here, validly-Merkle-proven) artifact whose freshness/validity window has expired is still treated as "verified," and it is left to the caller/consumer to apply a "strict" policy (checking `current_root`) versus a "permissive" one (ignoring it). Any caller that only checks `success`/`verified_clvm_hashes` and does not gate on `current_root` — e.g., automated DataLayer proof consumers, plugins, or offer/CR-CAT approval flows that reuse the same proof machinery — can be tricked into trusting outdated key/value data from a rolled-back or superseded DataLayer store, exactly analogous to an artifact consumer using outdated signed images from a rolled-back registry.

### Impact Explanation
An unprivileged DataLayer client (verifier) that consumes proofs produced by `get_proof`/`verify_proof` RPCs, or any downstream code (offers, external integrations) that treats a syntactically-valid inclusion proof as authoritative without checking `current_root`, can be shown stale key/value state as if it were current. In a trading/offer context this can lead to acting on outdated data (e.g., accepting a trade or price predicated on a superseded DataLayer root), which maps to the "coin-set divergence" / "offer settlement theft"-adjacent class of impact the scan is looking for, since it's a state-integrity issue reachable by any wallet/DataLayer user submitting or verifying proofs, not an operator-only or network-layer bug.

### Likelihood Explanation
Likelihood is Medium: exploitation requires (1) a store owner to advance/roll back their store after generating a proof, and (2) a verifier that does not check the `current_root` field of `VerifyProofResponse`. The verification API itself provides the freshness signal but does not enforce it, so the vulnerability's realization depends entirely on caller discipline — consistent with the "permissive vs strict policy" framing of the underlying advisory, and consistent with Medium severity (CVSS AC:H / UI:R) in the original report.

### Recommendation
Treat `current_root=False` as a hard verification failure (or provide a separate strict-mode API that raises) rather than a soft informational flag, so that DataLayer proof consumers cannot silently accept historical/rolled-back roots unless they explicitly opt into audit/permissive semantics — mirroring the Notary Project's guidance to default to `strict` trust policies and make `permissive`/`audit` an explicit, documented opt-in.

### Proof of Concept
1. Maker creates a DataLayer store, inserts key `k1`, and generates an inclusion proof for `k1` via `get_proof` (root R1).
2. Taker verifies the proof via `verify_proof` — succeeds with `current_root: True`.
3. Maker performs `batch_update` inserting new data, advancing the store to root R2 (superseding R1); the original singleton coin at R1 is now spent.
4. Taker (or any third party) re-submits the same original proof to `verify_proof`. As shown in [5](#0-4) , the proof still returns `success: True` with the same `verified_clvm_hashes`, only `current_root` changes to `False`.
5. Any consumer that checks only `success`/`verified_clvm_hashes` (ignoring `current_root`) accepts the stale, superseded data as valid — the rollback-style acceptance of outdated but "verified" state.

```python
def dl_verify_proof_internal(dl_proof: DLProof, puzzle_hash: bytes32) -> list[KeyValueHashes]:
    """Verify a proof of inclusion for a DL singleton"""

    verified_keys: list[KeyValueHashes] = []

    for reference_proof in dl_proof.store_proofs.proofs:
        inner_puz_hash = dl_proof.inner_puzzle_hash
        host_fullpuz_program = create_host_fullpuz(
            inner_puz_hash, reference_proof.root(), dl_proof.store_proofs.store_id
        )
        expected_puzzle_hash = host_fullpuz_program.get_tree_hash_precalc(inner_puz_hash)

        if puzzle_hash != expected_puzzle_hash:
            raise ProofIntegrityError(
                "Invalid Proof: incorrect puzzle hash: expected:"
                f"{expected_puzzle_hash.hex()} received: {puzzle_hash.hex()}"
            )

        proof = ProofOfInclusion(
            node_hash=reference_proof.node_hash,
            layers=[
                ProofOfInclusionLayer(
                    other_hash_side=Side(layer.other_hash_side),
                    other_hash=layer.other_hash,
                    combined_hash=layer.combined_hash,
                )
                for layer in reference_proof.layers
            ],
        )

        leaf_hash = internal_hash(left_hash=reference_proof.key_clvm_hash, right_hash=reference_proof.value_clvm_hash)
        if leaf_hash != proof.node_hash:
            raise ProofIntegrityError("Invalid Proof: node hash does not match key and value")

        if not proof.valid():
            raise ProofIntegrityError("Invalid Proof: invalid proof of inclusion found")

        verified_keys.append(
            KeyValueHashes(key_clvm_hash=reference_proof.key_clvm_hash, value_clvm_hash=reference_proof.value_clvm_hash)
        )

    return verified_keys
```

```python
async def dl_verify_proof(
    dlproof: DLProof,
    wallet_node: WalletNode,
    peer: WSChiaConnection,
) -> VerifyProofResponse:
    """Verify a proof of inclusion for a DL singleton"""

    coin_id = dlproof.coin_id
    coin_states = await wallet_node.get_coin_state([coin_id], peer=peer)
    if len(coin_states) == 0:
        raise ProofIntegrityError(f"Invalid Proof: No DL singleton found at coin id: {coin_id.hex()}")

    verified_keys = dl_verify_proof_internal(dlproof, coin_states[0].coin.puzzle_hash)

    response = VerifyProofResponse(
        verified_clvm_hashes=ProofResultInclusions(dlproof.store_proofs.store_id, verified_keys),
        success=True,
        current_root=coin_states[0].spent_height is None,
    )
    return response
```
