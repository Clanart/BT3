## Analog Found: Panic in `replenish_program_cache()` on a missing program account

### Title
Validator panic via `.expect("called load_program_with_pubkey() with nonexistent account")` in `replenish_program_cache()` - (File: `svm/src/transaction_processor.rs`)

### Summary
The external report's bug class is: a shared/aggregate operation (`withdrawExcessRewards()`) is permanently blocked because a per-item step (`transfer()` to one user) can fail, and the code has no fallback for that failure. The closest reachable analog in agave is in the SVM's cooperative program-loading path, where the code assumes an account that was previously classified as "missing and loadable" will still exist by the time it is actually loaded, and `.expect()`s on that assumption instead of handling failure gracefully.

### Finding Description
`TransactionBatchProcessor::replenish_program_cache()` computes a list of `missing_programs` via `filter_executable_program_accounts()` and the global `ProgramCache::extract()` call, then loads each one with `load_program_with_pubkey()`: [1](#0-0) 

`load_program_with_pubkey()` calls `load_program_accounts()`, which does `callbacks.get_account_shared_data(pubkey)?` — returning `None` if the account no longer exists — and the whole function returns `None` in that case: [2](#0-1) [3](#0-2) 

Back in `replenish_program_cache()`, that `None` is force-unwrapped:

```rust
let (program, last_modification_slot) = load_program_with_pubkey(...)
    .expect("called load_program_with_pubkey() with nonexistent account");
```

This is not merely theoretical — the codebase's own regression test proves the panic is reachable and exactly named: [4](#0-3) 

The comment inside the caller of this pattern even acknowledges the difficulty of reasoning about all cases: "This branch is taken when there is an error in assigning a program to a cache slot. It is not possible to mock this error for SVM unit tests purposes," showing the surrounding error-handling was already known to be incomplete/fragile: [5](#0-4) 

The mechanism is directly parallel to the FactoryDAO bug: a per-entity failure condition (one account becoming unavailable) that the aggregate/looping logic never anticipated turns into total denial of service — except here it's amplified because this is validator-global shared state (`global_program_cache` and its `loading_task_waiter`), guarded under a lock and a cooperative-loading coordination mechanism: [6](#0-5) 

If the thread performing the cooperative load panics mid-way (via this `.expect()`), it never calls `finish_cooperative_loading_task()`, so the `loading_entries` map entry for that program pubkey is never cleared and `loading_task_waiter.notify()` is never called for that key: [7](#0-6) [8](#0-7) 

Any other concurrently-executing transaction batch on any other TransactionBatchProcessor thread that also needs that same program will be stuck retrying `extract()`/`wait()` in a loop forever (the entry is permanently "loading" but nobody will ever finish it), since `extract()` treats an occupied `loading_entries` slot as still in-progress: [9](#0-8) 

But in practice the panic itself unwinds the whole validator thread (a full process/thread crash), which is a much stronger and immediate DoS than the FactoryDAO analog — instead of "funds locked forever," it is "validator process/thread crash."

### Impact Explanation
A `.expect()` panic on a validator-critical shared cache path is a crash-class bug (VM/validator-triggered node crash), not merely fund-lock: it can bring down banking/replay threads that touch the global program cache, and (per the loading-task analysis above) even absent an immediate panic, permanently stall any other concurrent batch that needs the same program, similar in spirit to the FactoryDAO DoS where one stuck entity blocks all others sharing the aggregate state.

### Likelihood Explanation
Reaching this specific `.expect()` requires a genuine TOCTOU: the account must be classified in `filter_executable_program_accounts`/`extract()` as an executable program owned by a BPF loader and "missing" from the cache, but then be truly absent (`get_account_shared_data` returns `None`) by the time `load_program_with_pubkey` runs. I was not able to fully trace, within the remaining budget, the exact code path in `AccountLoader`/`TransactionProcessingCallback::get_account_shared_data` that would let an account observed as present during `filter_executable_program_accounts` become entirely absent moments later within the same batch-processing call — this is the part of the root cause I could not fully verify with certainty in this pass. The reachable proof I do have is the maintainers' own reproduction, encoded as `test_replenish_program_cache_with_nonexistent_accounts`, confirming the panic is directly reachable through the public `replenish_program_cache` API surface with a `ProgramToLoad` whose account does not exist in the callback's account store.

### Recommendation
Replace the `.expect("called load_program_with_pubkey() with nonexistent account")` unwraps in `replenish_program_cache()` and `prepare_one_program_for_upcoming_feature_set()` with graceful handling (e.g., synthesize a `Closed`/`FailedVerification` tombstone entry, or simply drop the transaction with a recoverable `TransactionError`) instead of panicking, and ensure `finish_cooperative_loading_task`/`loading_task_waiter.notify()` (or an explicit release of the `loading_entries` slot) is always invoked on the error path so that other threads waiting on the same program pubkey are not left blocked indefinitely.

### Proof of Concept
Existing repository test already demonstrates the panic deterministically: [4](#0-3) 

This test calls `replenish_program_cache` with a `ProgramToLoad` referencing a `Pubkey::new_unique()` that was never inserted into `MockBankCallback`'s account store, causing `load_program_accounts` → `load_program_with_pubkey` to return `None`, and the `.expect(...)` to panic with the message `"called load_program_with_pubkey() with nonexistent account"`, confirming that any code path which allows the "missing program" list to include an account absent from the callback's account store at load time will crash the calling thread.

    /// Called by Bank::replenish_program_cache() for each program that is done loading.
    pub fn finish_cooperative_loading_task(
        &mut self,
        program_runtime_environment: &ProgramRuntimeEnvironment,
        current_slot: Slot,
        key: Pubkey,
        last_modification_slot: Slot,
        loaded_program: Arc<ProgramCacheEntry>,
    ) -> bool {
        match &mut self.index {
            IndexImplementation::V1 {
                loading_entries, ..
            } => {
                let loading_thread = loading_entries.get_mut().unwrap().remove(&key);
                debug_assert_eq!(loading_thread, Some((current_slot, thread::current().id())));
                // Check that it will be visible to our own fork once inserted
                if loaded_program.deployment_slot > self.latest_root_slot
                    && !matches!(
                        self.fork_graph
                            .as_ref()
                            .unwrap()
                            .upgrade()
                            .unwrap()
                            .read()
                            .unwrap()
                            .relationship(loaded_program.deployment_slot, current_slot),
                        BlockRelation::Equal | BlockRelation::Ancestor
                    )
                {
                    self.stats.lost_insertions.fetch_add(1, Ordering::Relaxed);
                }
                let was_occupied = self.assign_program(
                    program_runtime_environment,
                    key,
                    last_modification_slot,
                    loaded_program,
                );
                self.loading_task_waiter.notify();
                was_occupied
            }
        }
    }

/// Suspends the thread in case no cooprative loading task was assigned
#[derive(Debug, Default)]
pub struct LoadingTaskWaiter {
    cookie: Mutex<LoadingTaskCookie>,
    cond: Condvar,
}

impl LoadingTaskWaiter {
    pub fn new() -> Self {
        Self {
            cookie: Mutex::new(LoadingTaskCookie::new()),
            cond: Condvar::new(),
        }
    }

    pub fn cookie(&self) -> LoadingTaskCookie {
        *self.cookie.lock().unwrap()
    }

    pub fn notify(&self) {
        let mut cookie = self.cookie.lock().unwrap();
        cookie.update();
        self.cond.notify_all();
    }

    pub fn wait(&self, cookie: LoadingTaskCookie) -> LoadingTaskCookie {
        let cookie_guard = self.cookie.lock().unwrap();
        *self
            .cond
            .wait_while(cookie_guard, |current_cookie| *current_cookie == cookie)
            .unwrap()
    }
}
