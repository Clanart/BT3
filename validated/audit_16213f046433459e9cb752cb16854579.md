### Title
Data race in Python C-extension lazy sub-message unpacking on a shared parsed message allows concurrent-thread state corruption - ([File: python/google/protobuf/internal/thread_safe_test.py])

### Summary
The HackerOne report describes a TOCTOU-style race in Starport's faucet: a Go `map` tracking issued-token totals is read and updated without synchronization, so concurrent requests bypass the `coins_max` invariant (check-then-act on shared mutable state without a lock). The transferable invariant for Protobuf is: *"read-only/const operations on a message must be safe to call concurrently from multiple threads without corrupting shared internal state,"* as documented in [1](#0-0)  (read access is safe from multiple threads; only non-const/write access requires external synchronization). Protobuf's own regression tests demonstrate that this invariant is violated for lazily-materialized fields: a single shared, already-parsed message object, when accessed by two threads where one thread performs an apparently read-only access that triggers lazy unpacking of an embedded field (`shared_msg.lazy_field.value`) while another thread concurrently calls purportedly read-only APIs (`HasField`, `str()`), races on the internal lazy-unpack/mutation state, as captured in `testConcurrentLazyUnpackAndRead` [2](#0-1) .

### Finding Description
Protobuf messages containing "lazy" fields defer full parsing of a nested/cord-encoded submessage until first accessed. That first access is a mutation of internal state (unpacking bytes into a submessage, caching the resulting object) even though from the calling application's perspective it looks like a plain field read — exactly the kind of "const method that secretly mutates" case package_info.h calls out as needing internal mutex protection: *"The implementation does contain some 'const' methods which actually modify the object behind the scenes ... but in these cases mutex locking is used to make the access thread-safe."* [3](#0-2) 

The regression test `testConcurrentLazyUnpackAndRead` builds exactly this scenario: a message with a `lazy_field` is parsed once via `FromString` (an ordinary public parse API call on attacker-supplied, bounded, valid bytes) and the resulting message object is then shared across two threads — one thread performs `shared_msg.lazy_field.value` (triggering the CPython/native unpack of the lazy submessage) while the other thread concurrently calls `shared_msg.HasField('lazy_field')` and `str(shared_msg)` [2](#0-1) . Both accesses are attacker-influenced only insofar as the attacker controls the *content* of the message that a multi-threaded consuming application will then read concurrently from separate handler threads (a common server pattern: parse once, fan out to worker threads for logging/formatting/field checks). If the lazy-unpack write path and the `HasField`/serialize read path are not mutually excluded, the reading thread can observe a partially-unpacked or torn field state.

The same file documents multiple related, previously-fixed data races reachable purely through concurrent "read-only" API usage on a shared parsed message or its descriptor/type metadata — none requiring privileged access, hostile schemas, or unbounded input: `testFieldDecodersDataRace` (lazy `_decoders` cache init on `FieldDescriptor` during concurrent `ParseFromString`) [4](#0-3) , `testGetType` (a `Dealloc()/Dealloc()` race) [5](#0-4) , `testConcurrentGetFieldValueRace` (lazy init of the `composite_fields` map in `CMessage`) [6](#0-5) , and dealloc/interning races for descriptors and submessage wrappers [7](#0-6) . These confirm the class of bug — unsynchronized lazy-initialization/caching mutating shared native state behind an apparently-const Python API — is a recognized, real issue in this codebase, of which the lazy-field unpack race is the most directly analogous to the faucet's "check-then-mutate shared counter without a lock" pattern, because it involves an actual value-bearing field (not just cache/refcount bookkeeping) whose torn/incorrect state can be silently observed and propagated (e.g., re-serialized) by the reading thread.

### Impact Explanation
If the unpack-vs-read race is not fully closed, a concurrent reader thread can observe a message in a transiently inconsistent state (e.g., `HasField` returning a stale answer, or `str()`/re-serialization capturing a partially-unpacked lazy submessage), leading to data integrity issues in the consuming application (incorrect business logic decisions, corrupted re-serialized output) or, in the C-extension backend, memory-safety issues in native reference counting/state if the write path is not properly guarded — the same class of risk flagged by the sibling dealloc-race tests in this file. This mirrors the faucet bug's impact class: an invariant that is supposed to hold for all readers/writers of shared state is violated purely due to insufficient synchronization, not because of malicious input content.

### Likelihood Explanation
Likelihood is High in genuinely multi-threaded consuming applications (e.g., Python servers using thread pools where a single parsed message is fanned out to multiple handler threads for read-only field access) since the attacker-controlled payload need only contain a lazy field for the trigger path to exist; the race is a timing property of the caller's concurrency, not requiring any conformance-breaking encoding. It is Low/None for single-threaded consumers, and the existence of a dedicated regression test (`testConcurrentLazyUnpackAndRead`) confirms upstream engineers considered it real enough to add loop-based (500 iterations) reproduction to catch flaky timing windows.

### Recommendation
Ensure the lazy-unpack path for lazy message/cord fields synchronizes with all other "read-only" accessors (`HasField`, string conversion, serialization) using the same mutex/atomic-state pattern already used elsewhere in the codebase for const-methods-that-mutate (e.g., the `absl::MutexLock` + double-checked state pattern used in `MapFieldBase::SyncMapWithRepeatedField`/`SyncRepeatedFieldWithMap` for map/repeated-field synchronization [8](#0-7)  and [9](#0-8) ). Verify that the Python C-extension's lazy-field unpack and the underlying C++/upb lazy field implementation apply an equivalent lock or memory-order-safe first-unpack guard, and keep/extend `testConcurrentLazyUnpackAndRead` (and the related descriptor/dealloc race tests) as permanent CI regression coverage, run under ThreadSanitizer where applicable.

### Proof of Concept
The existing upstream regression test is the concrete, already-present reproduction: [2](#0-1) 
It: (1) serializes a message containing a populated `lazy_field` via the public `SerializeToString`/`FromString` parse API, (2) shares the single parsed instance across two threads synchronized with a `threading.Barrier`, (3) has one thread trigger first-access unpacking (`shared_msg.lazy_field.value`) while the other concurrently calls `HasField` and `str()`, and (4) repeats 500 times to reliably hit the race window — mirroring the external report's pattern of concurrent requests racing on a shared, unsynchronized data structure to defeat an invariant that is supposed to hold under concurrency.

// Thread-safety in the Protocol Buffer library follows a simple rule:
// unless explicitly noted otherwise, it is always safe to use an object
// from multiple threads simultaneously as long as the object is declared
// const in all threads (or, it is only used in ways that would be allowed
// if it were declared const).  However, if an object is accessed in one
// thread in a way that would not be allowed if it were const, then it is
// not safe to access that object in any other thread simultaneously.
//
// Put simply, read-only access to an object can happen in multiple threads
// simultaneously, but write access can only happen in a single thread at
// a time.

  def testConcurrentGetFieldValueRace(self):
    """Reproduces a data race in GetFieldValue due to lazy initialization."""

    def AccessFields(msg, barrier) -> None:
      barrier.wait()
      # This access triggers GetFieldValue and lazy initialization
      # of the composite_fields map in CMessage.
      _ = msg.optional_nested_message

    for _ in range(100):
      threads = []
      msg = unittest_proto3_pb2.TestAllTypes()

      # Use a barrier to ensure all threads hit the GetFieldValue call
      # at nearly the same time, maximizing the race window.
      barrier = threading.Barrier(10)

      for _ in range(10):
        thread = threading.Thread(target=AccessFields, args=(msg, barrier))
        threads.append(thread)
        thread.start()

    """Tests descriptor cache interning under concurrent deallocation."""
    pool = descriptor_pool.DescriptorPool()
    file_proto = descriptor_pb2.FileDescriptorProto(name='race.proto')
    file_proto.message_type.add(name='RaceMessage')
    pool.Add(file_proto)

    barrier = threading.Barrier(10)
    errors = []

    def Worker():
      barrier.wait()
      for _ in range(500):
        try:
          d1 = pool.FindMessageTypeByName('RaceMessage')
          d2 = pool.FindMessageTypeByName('RaceMessage')
          if d1 is not d2:
            errors.append('Descriptor interning broken')
            break
          # Explicitly delete local references to trigger concurrent tp_dealloc
          del d1
          del d2

          errors.append(str(e))

    for t in threads:
      t.start()
    for t in threads:
      t.join()
    self.assertEqual([], errors)

  def testConcurrentLazyUnpackAndRead(self):
    # 1. Create a template proto containing a lazy sub-message
    template = test_proto2_pb2.ReproMessageForLazy()
    template.lazy_field.value = 'repro_value'
    serialized_bytes = template.SerializeToString()

    # 2. Helper to run concurrent read/write loops on shared unparsed instances
    def RunRace():
      # Parse a fresh unparsed message instance
      shared_msg = test_proto2_pb2.ReproMessageForLazy.FromString(
          serialized_bytes
      )

      barrier = threading.Barrier(2)

      def ThreadWriter():
        barrier.wait()
        # Access the lazy field for the first time.
        # This forces the C++ protobuf library to unpack the lazy field,
        _ = shared_msg.lazy_field.value

      def ThreadReader():
        barrier.wait()
        # Concurrently read field presence or format to string.
        _ = shared_msg.HasField('lazy_field')
        _ = str(shared_msg)

      t1 = threading.Thread(target=ThreadWriter)
      t2 = threading.Thread(target=ThreadReader)

      t1.start()
      t2.start()
      t1.join()
      t2.join()

    # 3. Run in a loop to reliably trigger
    for _ in range(500):
      RunRace()

const RepeatedPtrFieldBase& MapFieldBase::SyncRepeatedFieldWithMap(
    bool for_mutation) const {
  ConstAccess();
  if (state() == STATE_MODIFIED_MAP) {
    auto* p = maybe_payload();
    if (p == nullptr) {
      // If we have no payload, and we do not want to mutate the object, and the
      // map is empty, then do nothing.
      // This prevents modifying global default instances which might be in ro
      // memory.
      if (!for_mutation && GetMapRaw().empty()) {
        return *RawPtr<const RepeatedPtrFieldBase>();
      }
      p = &payload();
    }

    {
      absl::MutexLock lock(&p->mutex());
      // Double check state, because another thread may have seen the same
      // state and done the synchronization before the current thread.
      if (p->load_state_relaxed() == STATE_MODIFIED_MAP) {
        const_cast<MapFieldBase*>(this)->SyncRepeatedFieldWithMapNoLock();
        p->set_state_release(CLEAN);
      }
    }
    ConstAccess();
    return static_cast<const RepeatedPtrFieldBase&>(p->repeated_field());
  }
  return static_cast<const RepeatedPtrFieldBase&>(payload().repeated_field());
}

void MapFieldBase::SyncMapWithRepeatedField() const {
  ConstAccess();
  // acquire here matches with release below to ensure that we can only see a
  // value of CLEAN after all previous changes have been synced.
  if (state() == STATE_MODIFIED_REPEATED) {
    auto& p = payload();
    {
      absl::MutexLock lock(&p.mutex());
      // Double check state, because another thread may have seen the same state
      // and done the synchronization before the current thread.
      if (p.load_state_relaxed() == STATE_MODIFIED_REPEATED) {
        const_cast<MapFieldBase*>(this)->SyncMapWithRepeatedFieldNoLock();
        p.set_state_release(CLEAN);
      }
    }
    ConstAccess();
  }
}
