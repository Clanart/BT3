### Title
Same-chain `fillOrder`/`cancelOrder` paths in `IntentGatewayV2` bypass the `EvmHost` emergency-freeze guard, allowing escrow withdrawal while cross-chain operations are frozen - (File: `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`EvmHost` implements an emergency pause mechanism (`FrozenStatus` / `_frozen`) enforced via the `notFrozen` modifier on `dispatch()` (outgoing) [1](#0-0)  and on `HandlerV2.handlePostRequests`/`handleGetResponses` (incoming) [2](#0-1) . Cross-chain intent flows in `IntentGatewayV2` (fills, cancels) route through `IDispatcher(host).dispatch(...)` or `dispatchIncoming`/`onAccept`, so they are properly blocked by `FrozenStatus.Outgoing/Incoming/All`. However, the **same-chain** fill and cancel paths (`_fillSameChain`, `_cancelSameChain` in `IntrinsicIntents.sol`) never touch the host's dispatch or incoming pipeline at all — they call the internal `_withdraw()` directly to release escrowed tokens. This is the exact analog of the reported bug: one custody-moving code path is gated by the pause/freeze mechanism, the other is not.

### Finding Description
`EvmHost.setFrozenState` is meant to halt bridge operations during incidents: `FrozenStatus.All` should stop all fund movement associated with the bridge [3](#0-2) . The `notFrozen` modifier is applied only to `dispatch()` (outgoing requests) and, in `HandlerV2`, to the message-handling entrypoints (`handlePostRequests`, `handleGetResponses`) that process incoming proofs [4](#0-3) .

`IntentGatewayV2.fillOrder()` and `cancelOrder()` branch on whether the order is same-chain or cross-chain [5](#0-4) [6](#0-5) . For cross-chain orders, `_fillCrossChain`/`_cancelFromSource`/`_cancelFromDest` eventually call `IDispatcher(hostAddr).dispatch(...)` (outgoing, frozen-gated) or are processed via `onAccept`/`onGetResponse` invoked from `dispatchIncoming` (incoming, frozen-gated). For same-chain orders, `_fillSameChain` and `_cancelSameChain` release escrow by calling `_withdraw(body, ...)` directly, with no reference to `host()`'s frozen status anywhere in the call path [7](#0-6) [8](#0-7) . The underlying token transfer logic in `withdraw()`/`_withdraw()` performs the actual escrow transfer with no frozen check either [9](#0-8) . A full grep of `IntentGatewayV2.sol` confirms there is no `frozen`, `notFrozen`, `onlyHost`, or `restrict` reference anywhere in the contract governing fill/cancel entrypoints — only an `_owner` immutable is stored for "future upgrade-gated actions (e.g. pausing)" that is not wired to any check.

### Impact Explanation
If the admin freezes `EvmHost` (e.g., `FrozenStatus.All`) in response to a detected exploit, compromised consensus client, or other incident affecting the `IntentGateway`, an attacker (or ordinary solver) can still call `fillOrder`/`cancelOrder` for same-chain orders and have escrowed tokens released, exactly the "withdrawals continue while the system should be completely paused" scenario from the seed report. This is a fund-custody control gap on an unprivileged, public entrypoint reachable by any user — matching the bounty's "stealing or loss of funds"/"unauthorized transaction or execution" categories, since the emergency stop invariant ("no escrow should move while frozen") is silently violated for one of the two custody-moving paths.

### Likelihood Explanation
High under an active-incident scenario: the freeze mechanism exists specifically to be invoked during emergencies, and same-chain intents are a normal, frequently-used path (the docs confirm same-chain fills/cancels are fully supported, atomic, and don't require cross-chain messaging [10](#0-9) ). No special privileges, malicious relayer, or governance compromise are required — any user placing/filling/cancelling a same-chain order during a freeze window triggers the gap.

### Recommendation
Add an explicit `notFrozen`/pause check (reading `IHost(host()).frozen()`) at the top of `fillOrder()` and `cancelOrder()` in `IntentGatewayV2.sol` (or inside `_fillSameChain`/`_cancelSameChain`/`_withdraw` in `IntrinsicIntents.sol`) so that same-chain escrow movement is halted consistently with the cross-chain path whenever the host is frozen (at minimum for `FrozenStatus.All`).

### Proof of Concept
1. Admin calls `EvmHost.setFrozenState(FrozenStatus.All)` in response to an incident.
2. Cross-chain fills/cancels now revert (`FrozenHost()`) because they call `IDispatcher.dispatch` [11](#0-10) .
3. A user still calls `IntentGatewayV2.placeOrder(...)` for a same-chain order (source == destination), which only escrows tokens locally and does not dispatch through the host.
4. A solver calls `fillOrder(order, options)`; since `isSameChain` is true, execution goes to `_fillSameChain` → `_withdraw`, releasing escrowed input tokens to the solver with no frozen-state check anywhere in the call chain — the withdrawal succeeds despite `FrozenStatus.All`.
5. Similarly, `cancelOrder` on a same-chain order routes to `_cancelSameChain` → `_withdraw`, refunding escrow to the user unaffected by the freeze.

Note: I could not fully trace whether `placeOrder` (the escrow-creation entrypoint) itself performs any host-frozen check, since that function's implementation was not returned in the available search results; if placement is also unguarded, the bypass extends to new escrow creation as well as withdrawal during a freeze. A Devin session with full repo access could confirm this and locate `placeOrder`'s exact definition to determine the complete scope of the fix.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        if (orderSource != currentChain) revert WrongChain();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();

                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();

                ++i;

## Same-Chain Swaps

Intent Gateway supports same-chain swaps where source and destination are the same chain. Settlement is atomic — no cross-chain messaging required. Supports **partial fills** where multiple solvers can each fill a portion of an order, with escrow released proportionally. Cancellation is immediate and any remaining escrowed assets are returned to the user.

![Same-Chain Swap](/intent-gateway-same-chain.svg)

### Partial Fills

For same-chain orders, solvers can fill any portion of the output. The proportional share of escrowed inputs is released immediately (`inputs[i].amount × fillAmount / totalRequired`). The order is fully filled once all output pairs reach their target amounts.
