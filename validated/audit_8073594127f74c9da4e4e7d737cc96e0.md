### Title
Two different fresh Pyth prices can be written and consumed within a single atomic Stacks transaction, bypassing the monotonic-timestamp safeguard - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
Zest's oracle path in `market.clar`/`v0-4-market.clar` guards against stale or replayed price data with a *monotonic per-feed timestamp* check (`oracle-timestamp-fresh`) backed by `pyth-storage-v4.clar`'s `is-price-update-more-recent`. Both checks only compare an incoming `publish-time` against the *last stored* value for that feed — they do not prevent two **different, both-valid, both-newer** Pyth updates from being written and consumed sequentially inside the same atomic transaction. Because Pythnet republishes signed price attestations roughly every 400ms, an attacker-controlled caller contract can bundle two market calls, each carrying its own optional Pyth update payload, in one Stacks transaction: the first call writes/consumes price `P1`, the second call writes/consumes a strictly newer, but different, price `P2`. Each call passes the monotonic check independently, yet the two operations that make up a single logical trade/liquidation flow end up priced inconsistently, exactly as in the Sherlock M-8 Pyth/Flatmoney finding.

### Finding Description
The relevant checks are: [1](#0-0) 

`oracle-timestamp-fresh` enforces `(<= delta max-staleness)` and `(>= ts prev)` — i.e., "not too old" and "not older than the last price used for this feed." It never asserts that the timestamp/price used has not *already been superseded within this same transaction* by a different valid update, nor does it lock the feed for the duration of the transaction.

The same pattern exists at the storage layer: [2](#0-1) [3](#0-2) 

`write-batch-entry` only asserts `is-price-update-more-recent`, i.e. `publish-time > last stored publish-time`, and `write` can be called multiple times per Stacks transaction (each `market` action optionally supplies up to 3 fresh feed buffers via `write-feeds`/`write-feed`): [4](#0-3) 

Because Pyth (Hermes) issues a new signed VAA for the same feed roughly every 400ms, it is trivial to obtain two distinct, both-fresh, both-monotonically-increasing VAAs (`P1` at `T1`, `P2` at `T2 > T1`) off-chain and submit them through two sequential `contract-call?`s to `market` from a single wrapper/caller contract in one atomic Stacks transaction. Each call independently satisfies `oracle-timestamp-fresh`/`is-price-update-more-recent`, so both updates are accepted and each market action is priced using the specific update it was fed — allowing the attacker to pick which of the two legs of a single logical operation (e.g., borrow vs. withdraw, or open vs. liquidate on the same/related position) sees the more favorable of the two prices, exactly as in the referenced Flatmoney/Pyth M-8 report where `updatePriceFeeds` could be called twice in one transaction with two different valid prices.

### Impact Explanation
An attacker who can atomically chain two market operations against price updates that arrive within the same block/transaction can obtain a wrong health/LTV verdict for one leg of the trade (e.g., borrowing valued favorably at `P1`, then withdrawing/closing valued favorably at `P2`), realizing a risk-limited arbitrage profit funded by the pool's other depositors/borrowers — analogous to the "temporary freezing of funds" / "theft of unclaimed yield" impact class recognized as Medium/High in the source report. Because Zest's checks bind only to "is this feed's timestamp newer than what I last stored," they provide no defense against intra-transaction price-switching once an attacker controls sequencing of two calls with two distinct valid VAAs.

### Likelihood Explanation
Likelihood is bounded by the same real-world constraints discussed in the Sherlock report (needing a favorable price delta within the current staleness/execution window, and being first to construct/relay the transaction), and is limited to callers who can compose multiple `market` contract-calls atomically (any Clarity contract can trivially do this — Clarity has no restriction on a wrapper contract issuing several sequential `contract-call?`s to `market` in one transaction). Requires monitoring Hermes for successive published attestations differing enough to cover fees/slippage of the two legs, which is feasible during moderate volatility, mirroring the conditions accepted as valid-Medium in the source finding.

### Recommendation
Add a per-transaction (not just per-feed) freshness gate, e.g., cache the current transaction's/block's already-consumed publish-time(s) per feed identifier and reject a second, different update for the same feed used later in the same transaction; alternatively, restrict all price consumption within one transaction to prices that were valid as of the start of the transaction (single price-read per feed per tx), or require `stacks-block-time`-bucketed price snapshot semantics so that all calls within the same transaction/block resolve to one canonical stored price per feed regardless of how many valid updates are submitted.

### Proof of Concept
1. Off-chain, poll Hermes for the target feed twice, roughly 1 second apart, to obtain two valid VAAs: `vaa1` (price `P1`, publish-time `T1`) and `vaa2` (price `P2` > `P1`, publish-time `T2 > T1`), both within `max-staleness`.
2. Deploy (or use) a wrapper contract that performs, in one Stacks transaction:
   - `contract-call?` to `market`'s borrow/increase-position action, passing `vaa1` as the optional feed update — `oracle-timestamp-fresh`/`is-price-update-more-recent` pass because `T1` is newer than the previously stored timestamp; position/loan valued at `P1`.
   - `contract-call?` to `market`'s withdraw/close/liquidate action, passing `vaa2` — checks pass because `T2 > T1`; this leg valued at `P2`.
3. Because both legs of what should be one economically-consistent operation are priced using two different, attacker-chosen valid prices within the same atomic transaction, the attacker captures the price delta `(P2 - P1)` net of protocol fees, with no risk of an intervening keeper/liquidator transaction landing between the two legs since they are atomic.

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
