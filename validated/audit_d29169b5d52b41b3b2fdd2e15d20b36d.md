### Title
Stack exhaustion via uncontrolled recursion in `AccountKeyRoleBased.DecodeRLP` when decoding a nested `AccountKeyTypeRoleBased` AccountKey - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`TxTypeAccountUpdate` transactions carry an `accountkey.AccountKey` that is RLP-decoded via `AccountKeySerializer.DecodeRLP`, which for a `AccountKeyTypeRoleBased` key delegates to `AccountKeyRoleBased.DecodeRLP`. That function decodes each role entry by calling `rlp.DecodeBytes` on a nested `AccountKeySerializer`, which in turn calls `AccountKeyRoleBased.DecodeRLP` again if the nested entry is itself typed `AccountKeyTypeRoleBased`. The "no nested RoleBased key" rule is enforced only *after* decoding, in `CheckInstallable`/`CheckUpdatable`, so an attacker can submit a single `AccountUpdate` transaction whose `Key` field contains a deeply, linearly nested `AccountKeyRoleBased` structure, causing unbounded recursive decoding before any validation occurs.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` is defined as: [1](#0-0) 

For each byte-string element `b` in the outer list, it calls `rlp.DecodeBytes(b, &serializer)`, and `AccountKeySerializer.DecodeRLP` does: [2](#0-1) 

If `serializer.keyType` is `AccountKeyTypeRoleBased`, `s.Decode(serializer.key)` invokes `AccountKeyRoleBased.DecodeRLP` again — a fresh, unbounded recursive call chain, each level requiring its own Go-level stack frame plus a nested `rlp.DecodeBytes` call. No depth counter or nesting-depth limit exists at decode time.

The "nested RoleBased key not allowed" rule is only checked afterwards, in `CheckInstallable`/`CheckUpdatable`, e.g. as exercised in the negative test `TestAccountUpdateRoleBasedKeyNested`, which asserts `kerrors.ErrNestedCompositeType` is returned — but only *after* the (potentially deeply nested) key has already been fully RLP-decoded: [3](#0-2) 

This decode path is reached from `TxInternalDataAccountUpdate.DecodeRLP` → `fromSerializable`, which is invoked whenever an `AccountUpdate` transaction is RLP-decoded (from the wire, from the tx pool, or from a block), before any semantic/tx-pool validation is applied: [4](#0-3) [5](#0-4) 

This is analogous to the reported Go bug class (`CVE-2022-30630`): uncontrolled recursion driven directly by attacker-supplied structure/length, causing a panic via stack exhaustion, before any bound/limit check is applied.

### Impact Explanation
A single unprivileged transaction sender can submit (or simply gossip) an `AccountUpdate` transaction containing a deeply nested `AccountKeyRoleBased` value. Every node that decodes this transaction — during p2p tx propagation, tx pool admission, or block processing — will recurse through `AccountKeyRoleBased.DecodeRLP`/`AccountKeySerializer.DecodeRLP` before the nesting is ever rejected by `CheckInstallable`/`CheckUpdatable`. Sufficient nesting depth can exhaust the goroutine stack and crash the node (panic), and since this triggers identically on every honest node processing the same transaction/block, it is a network-wide, remotely triggerable denial-of-service affecting transaction relay, tx pool admission, and block execution paths.

### Likelihood Explanation
Likelihood is high for any code path that RLP-decodes an untrusted `AccountUpdate` transaction (or block containing one) before validating the key structure: p2p transaction ingestion, `TxPool` add/validate, and block import all decode the transaction body (and thus the account key) via `DecodeRLP` prior to running `CheckInstallable`/`CheckUpdatable`. Crafting the payload only requires nested single-element `AccountKeyRoleBased` lists, each adding a small constant number of RLP overhead bytes, so a transaction near the max tx-size limit can encode a large nesting depth.

### Recommendation
Enforce a maximum recursion/nesting depth check inside `AccountKeyRoleBased.DecodeRLP` (and/or in `AccountKeySerializer.DecodeRLP`) before recursing further, rejecting any `AccountKeyTypeRoleBased`-within-`AccountKeyTypeRoleBased` structure at decode time rather than deferring the check to `CheckInstallable`/`CheckUpdatable`. Alternatively, track decode depth via `rlp.Stream` (or an explicit depth parameter threaded through the decode calls) and return an error once a small fixed limit (e.g. 1, since nesting is never valid) is exceeded.

### Proof of Concept
1. Construct an `AccountKeyRoleBased` value whose entries recursively contain another `AccountKeyRoleBased` (as already modeled by `TestAccountUpdateRoleBasedKeyNested`'s `nestedAccKey := accountkey.NewAccountKeyRoleBasedWithValues(accountkey.AccountKeyRoleBased{roleKey.AccKey})`), but repeat the nesting many (e.g. tens of thousands of) levels deep instead of one level, keeping within the maximum tx payload size.
2. RLP-encode this key via `accountkey.NewAccountKeySerializerWithAccountKey(nestedKey)` and embed it as the `Key` field of a `TxTypeAccountUpdate` transaction (`TxInternalDataAccountUpdate.EncodeRLP` → `toSerializable`).
3. Submit/broadcast the transaction; any node that decodes it — via `TxInternalDataAccountUpdate.DecodeRLP` → `fromSerializable` → `rlp.DecodeBytes(serialized.Key, serializer)` — recurses through `AccountKeyRoleBased.DecodeRLP` for each nesting level before `CheckInstallable`/`CheckUpdatable` ever run, exhausting the stack and panicking the node process.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil

func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}
