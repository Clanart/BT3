### Title
Attacker-controlled post-commit hook output can hijack `_COMMIT_SHA_RE`'s "last match" selection to make the commit reviewer inspect the wrong SHA or skip review entirely - ([File: plugins/security-guidance/hooks/security_reminder_hook.py])

### Summary
`handle_commit_review_posttooluse` pins security review to the SHA parsed from Bash stdout via `_COMMIT_SHA_RE.findall(bash_output)[-1]`, explicitly choosing the *last* line-anchored `[...hex]` match on the theory that git's real `[branch sha]` line always comes last. This assumption breaks when repo-tracked tooling (e.g. a `post-commit` git hook such as a committed `.husky/post-commit` script, invoked via `core.hooksPath` configured in the repository) prints additional line-anchored bracketed text *after* git's own commit line, letting attacker-controlled repository content override which commit gets reviewed.

### Finding Description
The relevant logic: [1](#0-0) [2](#0-1) 

`bash_output` is `stdout + "\n" + stderr` of the exact `git commit` Bash invocation [3](#0-2) . Git hooks (`pre-commit`, `post-commit`, `commit-msg`, etc.) run as children of `git commit` and their stdout is interleaved into this same captured output. Tools like husky install these hooks as *tracked* repository files (e.g. `.husky/post-commit`) and configure `core.hooksPath` — meaning their content is ordinary, attacker-controllable repository content (e.g., delivered via a malicious PR), not a privileged capability. The code's own comment at lines 574-583 acknowledges that pre-commit/husky hooks can emit bracketed labels resembling `[branch sha]`, but the mitigation (require a diffstat pattern anywhere in the buffer, plus "take the last match") only defends against decoys that appear *before* the real commit line — not decoys appearing *after* it via a `post-commit` hook or any wrapper/echo that runs after `git commit` completes.

If an attacker adds/modifies a tracked `post-commit` hook (or any script Claude runs immediately after `git commit` in the same Bash invocation) that echoes a line matching `^\[[^\]]*?\b([0-9a-f]{7,40})\]` at line start, `_COMMIT_SHA_RE.findall(bash_output)[-1]` picks that forged token instead of git's real SHA. The `commit_succeeded` gate is unaffected because it only checks that *some* diffstat pattern exists anywhere in the buffer [4](#0-3) , which is already satisfied by git's own real diffstat output before the forged line appears.

Downstream, the forged SHA is passed to `git show -p <sha>` [5](#0-4) . Two outcomes are possible:
1. The forged token happens to resolve to a real, unrelated (attacker-chosen or coincidental) commit — the reviewer analyzes and "clears" that commit instead of the actual one Claude just made.
2. The forged token does not resolve to any object — `git show` returns non-zero, `resolved` stays 0, and the handler skips entirely with `skip_reason=28` [6](#0-5) , silently dropping all review of the actual commit that was just made.

Either way, the invariant "commit review is pinned to the commit the Bash command actually produced" is violated, and no existing allowlist/approval/workspace guard catches this since the whole design already trusts the shape of Bash stdout as an oracle for what happened.

### Impact Explanation
This is a security-control bypass: it allows a real, malicious commit made during a Claude Code session to escape the automated commit security review (`analyze_code_security` / `agentic_review`), either because the review is silently skipped (`skip_reason=28`) or because it validates an unrelated benign commit instead. This maps to a trust-boundary bypass of a security-relevant automation (the plugin's own commit-review safety net), scoped to sessions where the repository contains attacker-influenced hook/wrapper scripts that run as part of the `git commit` invocation.

### Likelihood Explanation
Preconditions: the repository (or a PR merged into it) must contain a script that executes as part of the same Bash `git commit` invocation and prints a line-start bracketed hex token after git's own `[branch sha]` line — most naturally a committed `post-commit` git hook (e.g., husky-style `.husky/post-commit` with `core.hooksPath` set in the repo), or any project build/lint wrapper invoked in the same compound command that echoes such a token. This is realistic in supply-chain scenarios (malicious PR adding/modifying hook scripts) and requires no special privilege beyond ordinary repo-content contribution — it does not require admin/maintainer access to the victim's machine. It is fully repeatable: any commit made in a repo with such a hook present will trigger the misparse deterministically.

### Recommendation
Do not rely solely on regex position ("last match") to identify git's own commit line. Instead:
- Prefer resolving the commit deterministically via `git rev-parse HEAD` (or comparing pre/post `HEAD` via `git rev-list`/reflog) immediately after the Bash command, rather than trusting parsed stdout text that can include hook output.
- If stdout parsing must be kept as a fallback, restrict the search window to the prefix of `bash_output` up to and including the first diffstat-pattern match (git's own commit summary is emitted atomically right after the `[branch sha]` line and before any hooks run), so post-commit hook output textually after it is excluded from consideration.
- Alternatively, validate the candidate SHA is actually a parent-of/equal-to the current `HEAD` in `repo_root` (via `git merge-base --is-ancestor`/`git rev-parse`) before trusting it for `git show`, rejecting any SHA that isn't reachable/recent relative to HEAD-before/after the Bash call.

### Proof of Concept
Unit test on `handle_commit_review_posttooluse` (or directly on the SHA-extraction logic at lines 1040-1051):
1. Set up `tool_input.command = "git commit -m 'fix'"`.
2. Construct `tool_response.stdout` as:
```
[main abc1234] fix
 1 file changed, 1 insertion(+)
[decoy deadbee1]
```
   (the second line simulates a tracked `post-commit` hook's stdout, satisfying `_COMMIT_SHA_RE` at line-start and appearing after the real diffstat line, so `commit_succeeded` is still `True`).
3. Mock `_git_toplevel` to point at a real temp git repo whose `HEAD` is `abc1234`, and where `deadbee1` does not resolve to any object.
4. Run the handler and assert:
   - Expected (correct) behavior: `git show -p abc1234` is invoked and review proceeds.
   - Actual (buggy) behavior: `_COMMIT_SHA_RE.findall(bash_output)[-1]` returns `"deadbee1"`, `git show -p deadbee1` fails (`returncode != 0`), `resolved == 0`, and `emit_metrics` is called with `skip_reason=28` — i.e. the real commit `abc1234` is never reviewed.
5. A second variant where `deadbee1` is replaced with a real but unrelated benign commit SHA in the repo demonstrates the "reviews the wrong commit" variant: assert that `git show -p` is called with the decoy SHA, not `abc1234`.
