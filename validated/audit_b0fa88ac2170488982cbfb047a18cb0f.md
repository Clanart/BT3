### Title
Unchecked `u64` overflow in `SignableTransaction::new` balance/fee arithmetic lets an oversized payment bypass the funds check and produce a transaction that overdraws inputs - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` sums payment amounts and fees with plain `u64` addition/multiplication (`payment_sat + needed_fee`, `payment_sat + fee_with_change`, `fee_per_vbyte * vbytes`). A payment amount near `u64::MAX` wraps the sum, the `NotEnoughFunds` check passes, and an oversized change output is emitted — the same "add header/length to attacker-controlled size before the bounds check" overflow class as CVE-2022-49727.

### Finding Description
The kernel bug overflowed `ulen = len + transhdrlen` because `len` wasn't bounded against `INT_MAX - transhdrlen`. Here, the analog is `input_sat < (payment_sat + needed_fee)` at `networks/bitcoin/src/wallet/send.rs:215` and `input_sat.checked_sub(payment_sat + fee_with_change)` at line 228:

- `payment_sat = payments.iter().map(|p| p.1).sum::<u64>()` (line 187) is attacker-controlled: each `(ScriptBuf, u64)` payment is derived from a withdrawal/transaction request an unprivileged user can cause to be planned. Only `< DUST` (546 sats) is rejected (line 165); there is no upper bound and no per-output `MAX_MONEY` check.
- `payment_sat + needed_fee` and `payment_sat + fee_with_change` are non-checked `u64` additions. In release builds they wrap; a `payment_sat` of e.g. `u64::MAX - needed_fee + 1` yields a wrapped sum smaller than `input_sat`.
- `fee_per_vbyte * vbytes` (lines 206, 227) is likewise unchecked multiplication over a partially caller-controlled fee rate.
- `fee()` at lines 139–140 computes `sum(inputs) - sum(outputs)` with plain subtraction; once the wrapped check passes, this underflows/panics on any later call.

Concretely, with `payment_sat + needed_fee` wrapping to a small value `x < input_sat`, the `NotEnoughFunds` error is skipped. Then `input_sat.checked_sub(payment_sat + fee_with_change)` returns `input_sat - x'`, a value far exceeding the real inputs, which is pushed as the change output (line 230). The resulting transaction is then handed to `multisig()`/`TransactionSignMachine::sign`, which produces valid Schnorr signature shares committing to this transaction.

### Impact Explanation
The threshold multisig signs a transaction whose declared outputs (`payment` of ~`u64::MAX` sats plus inflated change) massively exceed its inputs and exceed Bitcoin's `MAX_MONEY`. Such a transaction is consensus-invalid: it can never be mined, yet the processor treats the plan as completed and signed (the signature itself is valid). The burn/withdrawal that triggered it is marked processed while the outputs are unspendable and the inputs are never moved — a "funds reported received that are not spendable" outcome, plus a DoS on the signing pipeline (any downstream `fee()` call panics on underflow). Severity: Medium.

### Likelihood Explanation
Reachable by any user who can cause a payment to be planned (e.g., a Substrate burn requesting a Bitcoin withdrawal with an attacker-chosen amount/script). The only guard on amount is the dust floor; values approaching `u64::MAX` wrap the balance check deterministically. Requires a release build (debug panics on overflow, still a DoS).

### Recommendation
Bound each payment to `Amount::MAX_MONEY` (`21_000_000 * 100_000_000` sats) and use `checked_add`/`checked_mul`/`checked_sub` for `payment_sat`, `needed_fee`, `fee_with_change`, and `fee()`, returning a `TransactionError` on overflow. Also cap the total payment sum rather than relying on the wrapped comparison.

### Proof of Concept
Conceptual: construct `SignableTransaction::new` with one input of `input_sat = 1_000_000`, `payments = [(script, u64::MAX - 1_000)]`, `fee_per_vbyte` such that `needed_fee ≈ 10_000`. Then `payment_sat + needed_fee` wraps to ≈ 9_000 < `input_sat`, so `NotEnoughFunds` is not raised; `input_sat.checked_sub(payment_sat + fee_with_change)` yields ≈ 990_000 (not an underflow), producing a change output while the payment output alone requests ~18.4 billion BTC. `multisig(keys)` + `sign()` produce valid signature shares for a consensus-invalid transaction. A debug-build caller hits a panic on `payment_sat + needed_fee`; `fee()` panics in all builds via subtraction underflow.

Relevant code: `input_sat`/`payment_sat` sums and `NotEnoughFunds` check at `networks/bitcoin/src/wallet/send.rs:175-221`, change math at lines 224-234, underflowing `fee()` at lines 138-141.
