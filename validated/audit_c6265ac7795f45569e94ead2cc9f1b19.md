### Title
`ReceivedOutput::read` trusts a caller-supplied scalar offset and never verifies the decoded output actually pays to the key derived from that offset — ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The bug class in the external report is an insecure direct object reference: an identifier supplied in the request is used to locate an object without checking that the object belongs to the scope the caller was authorized for. The structural analog in Serai's Bitcoin wallet is `ReceivedOutput::read`. A `ReceivedOutput` asserts "this `TxOut`/`OutPoint` belongs to us and is spendable with `keys.offset(self.offset)`". `Scanner::scan_transaction` establishes that invariant honestly — it only emits a `ReceivedOutput` when `output.script_pubkey` is found in `self.scripts`, a map keyed by script and built exclusively through `register_offset`/`Scanner::new`, so the stored `offset` is provably the one that derives the matched script. The deserializer performs no such check: it reads `offset` via `Secp256k1::read_F` and then decodes an arbitrary `TxOut` and `OutPoint` from the byte stream, returning the triple with no verification that `p2tr_script_buf(key + offset*G) == output.script_pubkey`. The script↔offset binding that the scan path enforces is exactly the "ownership check" the deserializer drops.

### Finding Description
`ReceivedOutput` couples three attacker-controlled fields — `offset` (a scalar read at `networks/bitcoin/src/wallet/mod.rs:123`), `output` (`:128-129`), and `outpoint` (`:130-131`) — and returns them as a bundle asserting joint validity. The constructor that preserves the invariant is `scan_transaction` (`:199-214`): `self.scripts.get(&output.script_pubkey)` returns `None` for any script not registered against this `Scanner`'s `key`, so an emitted `ReceivedOutput` is guaranteed spendable under `key` tweaked by `offset` (subject to the unspendable-script-path tweak rules of `tweak_keys`/`p2tr_script_buf`). `read` bypasses the `Scanner` entirely. There is no `Scanner`, no `key`, and no `p2tr_script_buf` re-derivation anywhere in the read path, so the parser accepts `(offset, output, outpoint)` tuples where `output.script_pubkey` is a P2TR script for a *different* tweaked key — e.g., an offset tweaked to a script-path-bearing key the multisig cannot sign for, or an honest output of a foreign wallet. This is the same shape as the IDOR: the "ID" (`offset`) is accepted from untrusted input while the object it claims to authorize (`output`) is never resolved against the authorized scope (the scanner's key).

Reachability: `ReceivedOutput::read` is in the enumerated list of untrusted-byte sinks for this engagement, and `ReceivedOutput` is the currency of outputs feeding `sign`/`send` (`send.rs` builds spends from `ReceivedOutput`s, using `offset()` to derive the signing keys). Any channel that feeds serialized `ReceivedOutput`s to a processor — network event payloads, DB rows populated from peer data — reaches this code with public input.

### Impact Explanation
An unprivileged party can cause the multisig to record funds as received that are not spendable: a `ReceivedOutput` whose `output.script_pubkey` does not match `key + offset*G` will be treated as ours (it carries a plausible `offset`), yet any attempt to spend it either derives the wrong tweaked key (producing a BIP-340 signature for a key that doesn't control the output) or tweaks to a key with an attacker-chosen script path (`register_offset`'s own docs warn arbitrary offsets "may introduce a script path into the output, allowing the output to be spent by satisfaction of an arbitrary script (not by the signature of the key)", `:177-179` — a warning enforced only against *registered* offsets, not deserialized ones). Consequences: phantom balance credited to the multisig, spend transactions built over outpoints the threshold key cannot authorize, and — where outputs are later spent via the matching script path — value claimable by a script that never required the multisig's signature. This maps to the report's integrity claim (objects linked to a scope they don't belong to) and hits the acceptance criterion "funds reported received that are not spendable".

### Likelihood Explanation
The check is structurally absent, not probabilistic: every byte string of the form `scalar || TxOut || OutPoint` that parses is accepted. Exploitation requires a channel where an unprivileged party supplies serialized `ReceivedOutput`s (or controls fields later re-serialized into one); within a wallet that mixes scan-derived and deserialized outputs, that is the same posture as the report's "member of one workspace supplying foreign IDs". No collusion, no key material, and no malformed encodings are needed — `read_F` can return a perfectly canonical scalar that simply doesn't correspond to the output. Severity is bounded (Medium-High) by the impact being mis-accounting/unspendable reporting rather than direct theft of the group key.

### Recommendation
Bind `offset` to `output` at deserialization or consumption. Options:

- Make `ReceivedOutput::read` crate-private and require construction through `Scanner::scan_transaction`/`scan_block`, which already enforces the script↔offset binding.
- If deserialization must remain public, add a verification step: `ReceivedOutput::verify(&self, key: ProjectivePoint) -> bool` (or a `read` variant taking the scanner's key) that recomputes `p2tr_script_buf(key + GENERATOR * offset)` and compares it to `output.script_pubkey`, rejecting mismatches — the exact analogue of resolving the ID against the authorized workspace before use.
- Apply the same check in `send` before signing: derive the tweaked key from `offset()` and confirm it matches `output.script_pubkey`, failing closed if not.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs behavior, conceptual PoC
use bitcoin::{TxOut, OutPoint, ScriptBuf, Amount, Txid, hashes::Hash};
use k256::Scalar;
use frost::curve::Secp256k1;
use ciphersuite::Ciphersuite;

// Attacker picks any scalar and any output that pays to a DIFFERENT script —
// e.g., a P2TR output to their own key, or to a script-path they control.
let bogus_offset = Scalar::from(42u64);
let foreign_output = TxOut {
    value: Amount::from_sat(1_000_000),
    script_pubkey: ScriptBuf::new_p2tr_tweaked(/* attacker key — NOT key + 42*G */),
};
let foreign_outpoint = OutPoint { txid: Txid::all_zeros(), vout: 0 };

// Serialize exactly as ReceivedOutput::write would.
let mut bytes = bogus_offset.to_bytes().to_vec();
bytes.extend(bitcoin::consensus::encode::serialize(&foreign_output));
bytes.extend(bitcoin::consensus::encode::serialize(&foreign_outpoint));

// ReceivedOutput::read accepts it with zero binding checks.
let received = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(received.value(), 1_000_000);          // phantom 1M sat "received"
// keys.offset(received.offset()) does NOT control foreign_output.script_pubkey,
// so any spend built over this ReceivedOutput is unspendable by the multisig —
// while a Scanner-derived ReceivedOutput can never have this property.
```
