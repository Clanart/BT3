### Title
First-staker capture of pre-existing queued rewards accrued while `totalStaked()==0` - (File: rewards/vlMGPBaseRewarder.sol)

### Summary
When `totalStaked() == 0`, `queueNewRewards` and `_queueNewRewardsWithoutTransfer` park incoming rewards in `rewardInfo.queuedRewards` instead of updating `rewardPerTokenStored`. The very next time either function is called while `totalStaked() > 0`, the entire accumulated `queuedRewards` balance is flushed into `rewardPerTokenStored` based on the *current* `totalStaked()`, meaning whoever holds stake at that instant receives 100% of the rewards that accrued during the zero-stake period, even if they held no stake during that period.

### Finding Description
`queueNewRewards` (lines 294-327) and `_queueNewRewardsWithoutTransfer` (lines 331-347) both branch on `totalStaked() == 0`: [1](#0-0) 

If `totalStaked()==0` at call time, the reward is only added to `queuedRewards` and `rewardPerTokenStored` is left untouched. On the next call where `totalStaked() > 0`, the full accumulated `queuedRewards` is added to the new `_amountReward` and distributed via `rewardPerTokenStored += (_amountReward * 1e18) / totalStaked()` — using whatever `totalStaked()` is *at that moment*, not a time-weighted value over the period the rewards accrued.

Exploit flow:
1. All existing lockers fully unlock, driving `totalStaked()` (i.e., `vlMGP.totalSupply()`, [2](#0-1) ) to 0. This is normal, permissionless user behavior, not an admin action.
2. The reward manager performs its normal, expected periodic call to `queueNewRewards(largeAmount, token)` while `totalStaked()==0`. This is routine protocol operation, not a privileged/malicious act — the manager has no way to know or control whether users are staked.
3. An attacker (unprivileged EOA) locks a minimal amount of vlMGP (e.g., 1 wei-equivalent) right after step 2, becoming the sole staker in the pool (`totalStaked() == attacker's tiny amount`).
4. The reward manager's *next* `queueNewRewards` call (even funding a small new amount, or triggered by any forfeit routed through `_queueNewRewardsWithoutTransfer`) executes the `else` branch, computing `rewardPerTokenStored += (_amountReward + queuedRewards) * 1e18 / totalStaked()`. Because `totalStaked()` is now tiny (attacker's dust stake) and `queuedRewards` contains the entire historical amount accrued while no one was staked, the attacker's `rewardPerTokenStored` share balloons.
5. Attacker calls `getReward`, whose `updateReward` modifier computes `_earned` using the now-inflated `rewardPerTokenStored`, and receives virtually the entire queued reward pool despite holding stake for only a brief instant.

No existing check prevents this: `updateReward`/`updateRewards` modifiers only snapshot `rewardPerTokenStored` at the time of interaction (lines 100-118, 349-361) and have no time-weighting or vesting; `nonReentrant` and `onlyMasterMagpie` do not address this because the exploit doesn't require reentrancy or unauthorized calls — it uses the normal `getReward` entry point through `MasterMagpie`.

### Impact Explanation
This is a theft of unclaimed yield: rewards that should conceptually belong to no one (accrued while `totalStaked()==0`) or should be fairly distributed pro-rata to future stakers over time end up being captured almost entirely by the first minimal staker after the queued-reward flush. This matches the "theft of unclaimed yield" impact category. Legitimate future stakers who lock larger, more meaningful amounts after the attacker are also diluted/harmed, but the immediate and concrete loss is the queued reward balance funded by the reward manager (funds sourced from protocol/manager, transferred out via `_sendReward`/`safeTransfer`, line 371).

### Likelihood Explanation
- Precondition: `totalStaked()==0` occurring is plausible in low-activity or new pools, or off-hour periods when all lockers have voluntarily unlocked — this is not a contrived edge case for less-used reward tokens/pools.
- The reward manager routinely calls `queueNewRewards`; this is a normal operational flow, not manager misconduct.
- Capital required by the attacker is minimal — the whole point of the exploit is staking the smallest possible unit to maximize `_amountReward/totalStaked()` skew.
- The attack is fully permissionless, repeatable each time `totalStaked()` cycles back to zero and refills, and requires only front-running (or simply timing) a lock transaction, which is a normal capability of any user (not privileged).
- The main uncertainty is how often `totalStaked()` realistically reaches exactly zero in production given the platform's typical usage; this reduces frequency but does not eliminate the vulnerability. I was unable to fully inspect `VLMGP.sol`'s lock function within the available iterations to determine if there's any minimum lock time or if `balanceOf` reflects lock amount instantaneously, but based on `balanceOf` in the rewarder calling `IMasterMagpie(masterMagpie).stakingInfo(...)` directly and the modifiers not applying delay, locking effects appear immediate.

### Recommendation
When flushing `queuedRewards`, do not let a single instantaneous `totalStaked()` snapshot absorb a full historical backlog. Options:
1. Track a timestamp when a pool goes to `totalStaked()==0`, and only allow queued rewards to flush once `totalStaked()` has been non-zero for a minimum duration, or distribute queued rewards linearly over time rather than in one lump `rewardPerTokenStored` jump.
2. Alternatively, freeze/return queued rewards to the reward manager if `totalStaked()` was zero for an extended period, instead of auto-flushing to the next staker.
3. At minimum, add a cooldown/vesting requirement so that reward entitlement is proportional to time-weighted stake rather than instantaneous balance at the flush moment (mirroring how many reward-streaming systems already vest deposits e.g., via `rewardRate` release over a `duration`).

### Proof of Concept
Foundry test plan (`vlMGPBaseRewarder.t.sol`):
1. Deploy `VLMGP`, `MasterMagpie`, `vlMGPBaseRewarder` with a mock ERC20 reward token; register reward token via constructor or `queueNewRewards`.
2. Have `userA` lock MGP into `vlMGP` so `totalStaked() > 0`, then fully unlock/withdraw so `totalStaked() == 0`.
3. As `rewardManager`, call `queueNewRewards(1000e18, rewardToken)` while `totalStaked()==0`; assert `rewards[rewardToken].queuedRewards == 1000e18` and `rewardPerTokenStored` unchanged.
4. As `attacker`, lock the minimal unit of MGP (e.g., `1`) via `vlMGP`/`MasterMagpie`, making `totalStaked() == 1`.
5. As `rewardManager`, call `queueNewRewards(0 or small dust, rewardToken)` (or trigger `_queueNewRewardsWithoutTransfer` via any forfeit path) to force the flush branch; assert `rewardPerTokenStored` jumps by `~1000e18 * 1e18 / 1`.
6. Call `getReward(attacker, attacker)` through `MasterMagpie`; assert attacker receives (near) the full `1000e18` reward token balance despite having staked only 1 wei for a single block, and other legitimate future stakers receive none of that batch.
7. Assert conservation invariant is violated: attacker's claimed yield vastly exceeds their pro-rata time-weighted share of the pool.
