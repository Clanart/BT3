## Title
Hardcoded 7-character conflict-marker assumption in `reassembleResolvedFile` silently leaves live git conflict markers in AI-"resolved" committed content - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
Just as the Fuel bridge hardcoded a fixed `DECIMALS` value instead of reading the token's real decimal precision from metadata — causing a silent amount mismatch — GitHub Desktop's Copilot conflict-resolution reassembly logic hardcodes an *exact* 7-character conflict-marker length instead of respecting the actual marker length Git used for a given conflict. Git conflict markers are not always exactly 7 characters: Git widens them via the tracked, attacker-controllable `.gitattributes` `conflict-marker-size` attribute, or automatically when a conflicting file's own content already contains `<<<<<<<`-like sequences. When the real marker length differs from 7, Desktop's reassembly scanner fails to recognize the conflict block at all and copies it through as "regular content" — silently leaving raw, unresolved git conflict-marker text inside the file that the UI presents as fully resolved and ready to commit.

### Finding Description
`reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` uses these regexes to locate conflict blocks on disk: [1](#0-0) 

```
const reassemblyOursMarker = /^<{7}(?:\s|$)/
const reassemblySeparatorMarker = /^={7}$/
const reassemblyTheirsMarker = /^>{7}(?:\s|$)/
```

`{7}` requires *exactly* seven `<`/`>` characters immediately followed by whitespace or end-of-line. If Git actually emitted a marker longer than 7 characters (e.g. `<<<<<<<<<`), the character right after the 7th `<` is still `<`, which fails `(?:\s|$)`, so the regex does not match at all.

The scanning loop treats any line that doesn't match `reassemblyOursMarker` (or a well-formed marker trio) as ordinary file content and copies it through verbatim: [2](#0-1) 

The function's own documentation confirms the invariant it relies on and how deviations are handled ("treated as regular file content ... copied through unchanged"): [3](#0-2) 

Git does not guarantee a fixed 7-character marker length:
- The `conflict-marker-size` gitattribute (a normal, tracked `.gitattributes` setting) lets any repository — including a malicious fork or branch the user merges/rebases — force a different marker width for specific files.
- Git's recursive/xdiff merge machinery independently widens markers when the conflicting content already contains marker-like runs, to avoid ambiguity — something an attacker can trivially engineer by embedding lines like `<<<<<<< example` inside a file on one side of the merge.

Both paths are fully attacker-controlled through ordinary, unprivileged repository content (tracked files merged/fetched from a remote), matching the valid-impact category of "attacker controls a cloned/fetched repository ... or a git remote/proxy response."

### Impact Explanation
When the real marker width ≠ 7, `reassembleResolvedFile` never recognizes the conflict block, so:
- `hunkIndex` is not consumed for it (it's copied through as-is), leaving raw `<<<<<<<…`, `=======`, `>>>>>>>…` text embedded verbatim inside what Desktop reports as the *fully resolved* file.
- The reassembled content is handed straight to the write path and to the commit UI as `resolvedContent`, with no further check that the output is free of conflict markers (the "no markers" check in `parseCopilotConflictResolution` only validates the *model's per-hunk* text, not the final spliced file — see the `/^<{7}\s/m` check at line 444, which has the identical 7-character blind spot).
- The user is presented with an apparently clean, AI-resolved file and is expected to commit it; committing then bakes literal unresolved git-conflict syntax into the repository's history — a silent corruption of what the user commits/pushes, exactly analogous to the bridge silently minting the wrong token amount.

This can also desynchronize subsequent, real 7-character conflict hunks in the same file relative to the hunk-resolution array the model returned, since `hunkIndex` bookkeeping assumes every actual conflict in the file is detected in order.

### Likelihood Explanation
No local access, admin rights, or leaked credentials are required. An attacker only needs to get the victim to merge, rebase, or cherry-pick a branch/fork/PR that either (a) sets `conflict-marker-size` in a tracked `.gitattributes` file for a target path, or (b) contains a crafted line resembling a 7-character conflict marker inside real file content so that Git's own ambiguity-avoidance widens the true marker — both are ordinary, natural outcomes of accepting external contributions, which is core GitHub Desktop workflow. The user must then use the Copilot "Resolve with Copilot" feature and commit, which is the intended, expected usage path, not an unnatural user step.

### Recommendation
Do not hardcode the marker width. Detect the marker length dynamically per conflict block (e.g. via a `<(<{7,})(?:\s|$)`-style pattern capturing the run length, then require the separator/closing markers to match that same captured length), or read `conflict-marker-size` from `.gitattributes`/git config before scanning. Additionally, after reassembly, scan the final spliced content for *any* run of 7+ `<`/`=`/`>` characters at line start and fail closed (mark the file as unresolved/skipped) rather than allowing it to be presented as commit-ready.

### Proof of Concept
1. Attacker adds `.gitattributes` to a branch/fork: `conflicted-file.ts conflict-marker-size=9`.
2. Attacker's branch and the victim's branch both modify the same line in `conflicted-file.ts`.
3. Victim (unprivileged, normal workflow) merges/rebases the attacker's branch in GitHub Desktop, producing a real conflict where Git emits `<<<<<<<<<`, `=========`(9-wide, not matched by `={7}$` either since it's exactly-7 anchored... actually `=======` 9 chars also fails `={7}$` since `$` requires end-of-line after exactly 7 `=`), and `>>>>>>>>>` markers.
4. Victim invokes "Resolve with Copilot." `reassembleResolvedFile` never matches the 9-character marker lines, so the conflicted block is passed through unchanged into `resolvedContent`.
5. Desktop's UI shows the file as resolved with no conflicts remaining; the user commits, and the repository now contains a committed file with literal, unresolved git conflict-marker text — silently corrupting the commit content the user intended to ship, mirroring the Fuel bridge's silent value-corruption pattern from a hardcoded fixed constant.
