### Title
`_calExpireForfeit` never queries `mWomSV.getRewardablePercentWAD`, permanently disabling the cooldown reward-forfeiture mechanism, letting users claim full undiminished mWOMSV rewards while simultaneously exiting with full mWOM principal - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` (lines 385-398) is dead code: it sets `rewardableAmount = _amount` unconditionally and never calls `mWOMSV.getRewardablePercentWAD(_account)`, so `forfeitAmount` is always `0` regardless of a user's cooldown state. This confirms the premise of the question - the WAD-based decay logic implemented in `mWomSV.sol` (`getRewardablePercentWAD`, lines 181-206) is entirely unreferenced/unused by the rewarder that is supposed to consume it, and any user in `startUnlock` cooldown can `getReward()` at full value with no penalty before finally calling `unlock()` for full principal.

### Finding Description
`mWomSV.sol` implements a full WAD-percentage decay calculation intended to reduce a user's "rewardable" share while tokens are mid-cooldown: [1](#0-0) 

However, `mWOMSVBaseRewarder._calExpireForfeit` — the only function meant to consume that percentage to compute forfeiture on reward payout — never calls it: [2](#0-1) 

`rewardableAmount` is hardcoded to `_amount`, so `forfeitAmount = _amount - rewardableAmount` is always `0`, and the `if (rewardableAmount > _amount) revert` guard is unreachable dead code. This is called from `_sendReward`, which is invoked by `getReward`/`getRewards` on every claim: [3](#0-2) 

A grep across the repo confirms `getRewardablePercentWAD` is referenced only in `VLMGP.sol`, `vlMGPBaseRewarder.sol`, and `mWomSV.sol` itself — never in `mWOMSVBaseRewarder.sol` — proving the mWOMSV reward path is structurally disconnected from the cooldown decay mechanism that `mWomSV.sol` was built to support (unlike the analogous, correctly-wired `vlMGP`/`vlMGPBaseRewarder` pair).

Exploit flow: a user locks mWOM into mWomSV, calls `startUnlock(amount)` (which itself triggers `multiclaimFor` and stops that amount from continuing to “fully lock” but leaves `balanceOf` unaffected for reward purposes since the rewarder's `balanceOf` used in `earned`/`_updateFor` doesn't discriminate cooldown vs. fully-locked stake), continues to accrue and claim 100% of rewards during the entire cooldown window via `getReward`, then calls `unlock(slotIndex)` once cooldown ends to reclaim the full mWOM principal: [4](#0-3) 

No existing modifier (`onlyMasterMagpie`, `updateReward`, `nonReentrant`) prevents this, because none of them check cooldown status or apply any forfeiture — the forfeiture logic is simply never wired up.

### Impact Explanation
Because `forfeitAmount` is always `0`, the pooled-redistribution path (`_queueNewRewardsWithoutTransfer`, adding forfeited rewards back to `rewardPerTokenStored` for remaining stakers) never fires. This means the yield that permanent lockers are economically entitled to receive from cooldown/exiting users' forfeitures is permanently never generated — a real, quantifiable loss of expected/unclaimed yield to honest permanent lockers, matching the Immunefi "theft or permanent freezing of unclaimed yield" impact class. Any mWOMSV holder can withdraw full mWOM principal via `unlock()` while having already harvested full, non-decayed rewards throughout the cooldown period, at no cost — a benefit that should have been partially forfeited and redistributed to users who kept their stake locked for the entire duration.

### Likelihood Explanation
This requires no special capital, timing, or privileged role — only holding locked mWomSV and following the ordinary staking lifecycle (`lock` → `startUnlock` → `getReward` via `masterMagpie.multiclaimFor` → wait → `unlock`). It is 100% reproducible by any unprivileged EOA and is repeatable indefinitely across every cooldown cycle, since the bug is a static code defect, not a race condition.

### Recommendation
Fix `_calExpireForfeit` in `rewards/mWOMSVBaseRewarder.sol` to actually query `mWOMSV.getRewardablePercentWAD(_account)` and scale `rewardableAmount = _amount * percent / 1e18` before computing `forfeitAmount`, mirroring the working reference implementation pattern used in `vlMGPBaseRewarder.sol`.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `mWOMSVBaseRewarder`, `MasterMagpie` with two users: `attacker` and `permanentLocker`, each locking an equal amount of mWOM at `t0`.
2. Queue identical reward amounts into `mWOMSVBaseRewarder` at `t0 + X`.
3. At `t0 + X`, `attacker` calls `mWomSV.startUnlock(amount)` then immediately `masterMagpie.multiclaimFor([mWOMSVBaseRewarder], ..., attacker)` (or `getReward`), recording `rewardsClaimed`.
4. Advance time past `coolDownInSecs`; `attacker` calls `mWomSV.unlock(slotIndex)`, recording `principalReturned`.
5. Assert `mWOMSVBaseRewarder.calExpireForfeit(attacker, rewardToken) == 0` throughout cooldown (proving forfeiture never applies) despite `mWomSV.getRewardablePercentWAD(attacker) < 1e18` during cooldown.
6. Assert `attacker`'s total realized value (`rewardsClaimed + principalReturned`) equals what `permanentLocker` would only get if they also unwound their position early, demonstrating `attacker` obtained full liquidity optionality with zero yield penalty, unlike the design intent embedded in `mWomSV.getRewardablePercentWAD`.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
