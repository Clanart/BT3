## Analysis

I reduced the external report's core broken invariant to: **a monotonic accrual/ledger structure is mutated by an unprivileged, fee-paying action, but the eviction/overwrite rule ignores the economic value or remaining validity of the entry being displaced — allowing a small payment to destroy a larger, still-valid, already-paid-for balance.**

I evaluated the following Hyperbridge candidates:

1. `EvmHost.updateHostParams` retroactively changing `challengePeriod`/rates — requires a `hostManager`/governance actor to trigger, which the task explicitly excludes.
2. `pallet-bandwidth::set_tier` and `IntentGatewayV2.UpdateParams` — both bake the paying rate into the record at creation/purchase time (`Subscription.tier`/`ParamsUpdate` is captured in the commitment or subscription at write time), so later governance rate changes do **not** retroactively reprice already-escrowed/purchased state. No exploitable analog.
3. `pallet-bandwidth`'s `push_subscription` FIFO eviction on the shared `(app_chain, app)` `Allowance` list — this is reachable by **any unprivileged caller** who can dispatch a purchase (`BandwidthManager.purchase()` on any source chain, crediting an **arbitrary** `app`/`chain` pair per the documented "Sponsorship" feature), and the eviction logic drops the *oldest* entry purely by insertion order, with no regard to its remaining value.

Only candidate 3 survives the exclusion filters (no admin/governance/relayer/prover assumption needed) and constitutes a genuine loss-of-funds primitive, so I selected it as the strongest analog.

### Title
Unprivileged FIFO-eviction of paid bandwidth subscriptions permits cheap destruction of a victim's high-value allowance - (File: modules/pallets/bandwidth/src/lib.rs)

### Summary
`pallet-bandwidth` credits a `(app_chain, app)` bucket with a new `Subscription` on every accepted purchase message, regardless of which chain paid for it (cross-chain "sponsorship" is a documented, intended feature). When the bucket's `SubscriptionList` reaches the hard cap of `MAX_SUBSCRIPTIONS` (1024), `push_subscription` unconditionally evicts index `0` — the *oldest* entry by insertion order — with no check on its `remaining_bytes`, `expires_at`, or economic value. [1](#0-0) [2](#0-1) 

### Finding Description
`purchase()` on `BandwidthManager.sol` is permissionless: any caller can pay for a tier and specify an arbitrary `(chain, app)` pair as the beneficiary of the credit — this is the pallet's advertised "Sponsorship" mechanism (a treasury on one chain can top up bandwidth for an app deployed on another). [3](#0-2) 

On `on_accept`, the pallet validates only that the sender is the registered `BandwidthManager` for `request.source` — it performs **no check tying the caller to the `app` being credited**: [4](#0-3) 

Each accepted purchase calls `push_subscription`, which appends unconditionally and, once the list is full, evicts `list.remove(0)` — the FIFO head — irrespective of how many bytes remain on it or how long until it expires:
```rust
let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
    let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
        Some(list.remove(0))
    } else {
        None
    };
    let _ = list.try_push(new_sub);
    evicted
});
``` [5](#0-4) 

The cheapest tier (`TierOne`) is priced independently of the value being displaced — a victim app can legitimately purchase a large, long-duration tier (e.g. the $1000/8MB plan) that sits at the head of an otherwise near-empty or newly-created list. An attacker who is not the app owner, not a relayer, and not privileged in any way can simply call `purchase()` 1024 times with the cheapest tier, targeting the victim's exact `(chain, app)` key, to force the victim's still-mostly-unconsumed, unexpired, expensive subscription off the front of the FIFO list via `list.remove(0)`. The lost value is only logged, not compensated: [6](#0-5) 

Because subscription order is fixed by `purchased_at` at insertion and the gate always drains/evicts from the head regardless of tier size, there is no mechanism protecting a large purchase from being pushed out by a flood of minimal ones from an unrelated payer.

### Impact Explanation
This directly causes loss of funds: the victim (app owner or their sponsor) paid real fee-token value for bandwidth that the gate would have otherwise metered out over its full byte allowance and duration; the eviction destroys that unspent, unexpired value with no refund path, replaced instead by minimal-tier junk purchased by the attacker. This matches the bounty's "stealing or loss of funds" and "bandwidth balances must move exactly once and only to the rightful beneficiary and amount" pivot — the beneficiary here is denied the balance they paid for, while an unprivileged third party accomplishes this purely by paying (and thus in the attacker's own economic interest, e.g. to grief a competing dApp or hold a target's bandwidth hostage).

### Likelihood Explanation
No malicious peer, relayer, prover, admin, or governance actor is required — the attacker is simply another user of the permissionless, publicly documented `purchase()`/sponsorship interface, driving 1024 cheap purchases against a known target `(chain, app)` key. The cost is bounded by `1024 × price(TierOne)`, which for well-funded or motivated attackers (e.g. a competitor of the target app) is a straightforward, deterministic, repeatable griefing/fund-destruction vector with no admin dependency.

### Recommendation
Change the eviction policy in `push_subscription` so it does not blindly evict the FIFO head once at capacity: e.g. evict the subscription with the least remaining value (lowest `remaining_bytes` scaled by time-to-expiry) rather than strict insertion order, or reject new pushes into a full bucket instead of silently evicting existing paid value, or bind purchases to a caller-verified relationship with `app` (so third-party sponsorship still works but cannot be abused purely to spam-evict), or increase/parametrize `MAX_SUBSCRIPTIONS` per app with economic cost scaling so eviction of legitimate high-value entries is not cheaply forced.

### Proof of Concept
1. Victim (or its sponsor) calls `BandwidthManager.purchase()` on any registered source chain for `app = X`, `chain = target_chain`, tier = TierFour (largest, e.g. 8MB/`$1000`). This lands as the sole/oldest `Subscription` in `Allowance::<T>::get(target_chain, X)`.
2. Attacker, with no relationship to `X`, repeatedly calls `BandwidthManager.purchase()` (on any registered manager chain) 1024 times using the cheapest tier (TierOne), each time targeting `app = X`, `chain = target_chain`, paying the minimal tier price each call.
3. Each accepted purchase message hits `pallet-bandwidth::on_accept` → `push_subscription`; once the list reaches `MAX_SUBSCRIPTIONS = 1024`, subsequent pushes evict index `0` in FIFO order.
4. After the queue fills past the victim's original position, the victim's largely-unconsumed, unexpired 8MB subscription is evicted via `list.remove(0)`, emitting `SubscriptionEvicted { lost_bytes }` — permanently destroying the value the victim/sponsor paid for, with the victim's app now dependent solely on the attacker's cheap, small, short-lived subscriptions (or none at all once those drain/expire too).

		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

	impl<T: Config> IsmpModule for Pallet<T> {
		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}
