## Finding [1](#0-0) 

`createLogParser` builds a `git log --format=...` invocation where every requested field is concatenated using a **NUL byte** (`%x00`) as the field separator, and then the raw stdout is naively split back into records on `'\0'`:

```
const format = Object.values(fields).join('%x00')
...
for (let i = 0; i < records.length - keys.length; i += keys.length) {
  const entry = {}
  keys.forEach((key, ix) => (entry[key] = records[i + ix]))
  ...
}
```

`getCommits` uses this parser with the field order `sha, shortSha, summary, body, author, committer, parents, trailers, refs`, where `body` is `%b` — the raw, attacker-controlled commit message body of a cloned/fetched commit: [2](#0-1) 

This is precisely the bug pattern in the 1inch report: **a dynamic, attacker-controlled field (`body`) is packed in front of subsequent "static-position" fields (`author`, `committer`, `parents`, `trailers`, `refs`)**, and the parser assumes each record occupies a fixed slot based on `keys.length`. The delimiter chosen to separate fields (`\0`) is not guarded against appearing *inside* the dynamic field. If a maliciously crafted commit object (constructed directly as a raw git object rather than through the normal `git commit` UI, e.g. via `git hash-object -t commit --stdin` and pushed to a repo, or shipped in a repository the user clones/fetches) embeds a literal NUL byte inside its message body, `git log`'s pretty-printer writes that NUL byte to stdout verbatim (strbuf-based, binary-safe). Node's `child_process` captures this as a `Buffer` (`encoding: 'buffer'`) and `splitBuffer(value, '\0')` will treat the embedded NUL as an extra record boundary — shifting every subsequent field of that commit (and potentially adjacent commits) out of alignment.

Unlike a filesystem path (which cannot contain a NUL byte, making the analogous `status-parser.ts`/`diff-index.ts` NUL-delimited parsers safe), a git commit message body has no such OS-level restriction, so this is a reachable primitive.

## Impact

The `author`, `committer`, `parents`, `trailers`, and `refs` fields for that commit (and the alignment of subsequent commits in the same `git log` batch) get silently mis-decoded. `commit.trailers` in particular feeds into `Commit.coAuthors`/`bodyNoCoAuthors` [3](#0-2)  and into the "restore commit and co-authors after undo" flow, which re-parses trailers to auto-populate co-authors for a *new* commit the user is about to create: [4](#0-3) . A maker of a hostile repository could engineer the shift so a forged `Co-Authored-By:` trailer (or forged author identity) ends up silently attached to history the user views or to a commit the user subsequently creates — corrupting attribution without any unusual user action beyond viewing history/using the standard undo→recommit flow in a repo they cloned.

## Recommendation

Do not rely on a fixed-position record scheme when any field can be attacker-controlled arbitrary bytes. Either:
- Reject/sanitize records where an embedded NUL is detected inside a field's raw byte stream before grouping, or
- Use a self-describing framing (length-prefixed records) instead of a bare delimiter that the same byte value could appear inside dynamic content, or
- Order fields so at minimum an out-of-place delimiter can't reassign values across records (though the safest fix is (1) or (2)). [5](#0-4) 

## Proof of Concept (conceptual)

1. Craft a raw commit object whose body contains a literal `\0` byte, e.g. via `printf` and `git hash-object -w -t commit --stdin`, then make it reachable (branch/tag) in a repository.
2. Have the victim clone/fetch this repository in GitHub Desktop and open History.
3. `getCommits` runs `git log ... --format=%H%x00%h%x00%s%x00%b%x00%an <%ae> %ad%x00...` and the embedded NUL in `%b` produces one extra token in `records`.
4. `createLogParser`'s fixed-offset grouping (`records[i+ix]`) now misassigns `author`/`committer`/`trailers`/`refs` for that commit (and shifts alignment for following commits parsed from the same buffer), silently corrupting the authorship/trailers metadata Desktop displays and reuses (e.g., in `loadCommitAndCoAuthors`).

Note: I could not find a config/fsck check in the codebase index that rejects such crafted commit bodies before they're parsed by `getCommits`; confirming this precisely would benefit from testing against a live `git log` binary, which a Devin session with actual git tooling could verify empirically.

export function createLogParser<T extends Record<string, string>>(fields: T) {
  const keys: Array<keyof T> = Object.keys(fields)
  const format = Object.values(fields).join('%x00')
  const formatArgs = ['-z', `--format=${format}`]

  const parse = <V extends string | Buffer>(value: V) => {
    const records = (
      Buffer.isBuffer(value) ? splitBuffer(value, '\0') : value.split('\0')
    ) as V[]
    const entries = []

    for (let i = 0; i < records.length - keys.length; i += keys.length) {
      const entry = {} as { [K in keyof T]: V }
      keys.forEach((key, ix) => (entry[key] = records[i + ix]))
      entries.push(entry)
    }

    return entries
  }

  return { formatArgs, parse }
}
