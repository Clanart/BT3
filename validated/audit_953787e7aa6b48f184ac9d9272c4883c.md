Confirmed: `EVMPreprocessDecorator.AnteHandle` calls `associateHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)` on every non-associated EVM sender [1](#0-0) , and inside `AssociateAddresses` the mapping `p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)` is written **before** `MigrateBalance` is called and can fail [2](#0-1) . `MigrateBalance` moves *all* `SpendableCoins` of the cast address in one unconditional `SendCoins` call covering every denom, and any single denom in that batch failing (e.g. `SendEnabledCoins`/denom allow-list restriction, blocked/frozen tokenfactory denom, or any other bank-level rejection) causes the whole call, and thus the whole migration, to return an error [3](#0-2) .

### Title
Address association can permanently strand all cast-address funds if `SendCoins` migration fails after `SetAddressMapping` is persisted - (File: `utils/helpers/associate.go`, `x/evm/ante/preprocess.go`)

### Summary
On the sender's first unassociated EVM transaction (or explicit Associate tx), the ante-handler's `EVMPreprocessDecorator` calls `AssociateAddresses`, which unconditionally sets the EVM↔Sei address mapping via `SetAddressMapping` *before* attempting to migrate all of the cast address's spendable balances via a single atomic `SendCoins` call spanning every held denom [4](#0-3) . If that batched `SendCoins` (or the subsequent `SendCoinsAndWei`) fails for any reason tied to one of the denoms the cast address holds, the whole migration aborts with an error that is returned by the ante handler, rejecting the transaction [5](#0-4) . Because the address mapping was already committed to state, any retry of the association path is blocked by the "already associated" guard used both in the ante handler (`isAssociated` check) and in the explicit associate precompile (`if found { return nil, fmt.Errorf("address ... is already associated") }`) [6](#0-5) . This is structurally the same class of bug as the MultiStrategyVault report: an unconditional, non-excludable, all-or-nothing batched operation across multiple "assets/denoms" that, once one item is un-transferable, permanently blocks recovery of everything else because there is no mechanism to exclude the problematic denom and no ability to retry after partial mapping-state has already been written.

### Finding Description
`AssociateAddresses` is invoked from the EVM ante pipeline for every unassociated sender (unprivileged, attacker/user reachable simply by sending a normal EVM transaction) [5](#0-4) . Its logic:
1. `p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)` — commits the association unconditionally.
2. `p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)` — reads *all* `SpendableCoins` at the cast address in one call and attempts to move them in a single `SendCoins`, then separately migrates `wei` balance [7](#0-6) .

`SendCoins`/`SendCoinsAndWei` in `x/bank` enforce invariants like `IsSendEnabledCoins`, denom allow-lists, and blocked-address checks atomically across the whole coin set being sent (see the analogous atomic `MultiSend`/`InputOutputCoins` semantics documented in bank's spec, where "any of the coins do not have sending enabled" or "any of the coins are locked" fails the entire operation) [8](#0-7) . If the cast address holds even one denom that trips such a restriction (a paused/frozen tokenfactory denom, a denom removed from an allow-list, or any bank-level state that legitimately blocks that specific coin), `MigrateBalance` returns an error and the ante handler rejects the transaction — but the mapping written in step 1 is not rolled back because the ante handler's `ctx` is not a scoped cache-context for this path (unlike the SetCode authority pre-association, which explicitly uses `ctx.CacheContext()`/`write()` to make itself atomic) [9](#0-8) . The main sender-association call path at lines 93-97 has no such cache-context protection.

Once the mapping exists, subsequent calls to `AssociateAddresses` for the same address are refused (both the ante-handler `isAssociated` branch and the explicit `associate()` precompile check for "already associated"), so `MigrateBalance` can never be retried, and the user's entire cast-address balance — including the native `usei` needed to pay gas or interact further — remains permanently stuck at the un-migrated cast address.

### Impact Explanation
This can result in permanent freezing of funds: any tokens (including the native gas denom) sitting at a user's cast address become irrecoverable once one blocked/restricted denom in that same address poisons the batched migration, since (a) the association is one-shot and non-retryable, and (b) the migration of all denoms is atomic with no per-denom exclusion mechanism, mirroring the reported MultiStrategyVault flaw of an all-or-nothing withdrawal path with no way to exclude a single problematic asset.

### Likelihood Explanation
Likelihood is moderate: it requires that the cast address end up holding at least one denom that is restricted from being sent (e.g., a tokenfactory denom that gets frozen/paused, delisted from a send-enable list, or otherwise blocked) at the moment the owner's first EVM transaction triggers auto-association. Because deposits to cast addresses can come from arbitrary senders/airdrops before the owner ever signs anything, an attacker (or even organic token administration action) could plant such a denom at a victim's cast address to trigger this on the victim's next transaction.

### Recommendation
Wrap the entire `AssociateAddresses`/`MigrateBalance` sequence in a `ctx.CacheContext()`/`write()` pattern (as already done for the EIP-7702 authority pre-association path) so that a migration failure rolls back the address-mapping write, allowing retries; additionally, consider migrating denoms individually/independently (skipping and logging failures per-denom) rather than atomically as a single `SendCoins` call, so a single restricted denom cannot block migration of all others.

### Proof of Concept
Exact reproduction would require constructing a bank-level restriction (e.g., a tokenfactory denom flagged as not-send-enabled or removed from a denom allow-list) and funding a not-yet-associated EVM cast address with both that restricted denom and `usei`, then submitting any signed EVM transaction from that address so the ante handler's auto-association path (`x/evm/ante/preprocess.go` lines 93-97) triggers `MigrateBalance`; the existing repo test `TestMigrateBalance` in `x/evm/ante/preprocess_test.go` (lines 423-441) demonstrates the same code path succeeding with a vesting-locked coin excluded from `SpendableCoins`, confirming that any coin `SendCoins` rejects (rather than simply excludes, as vesting-locked coins are) surfaces as a hard error from `MigrateBalance` [10](#0-9) . I was not able to fully verify within the available index whether any Cosmos-SDK-level denom restriction (e.g. tokenfactory pause) is reachable purely by an unprivileged sender without governance/admin action; this would need to be confirmed with a live repro in a Devin session.

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
