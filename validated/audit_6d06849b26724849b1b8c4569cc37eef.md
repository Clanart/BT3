### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` causes stack-overflow DoS on account (creation/update) transactions - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each role slot by calling `rlp.DecodeBytes` on an `AccountKeySerializer`, which itself can decode another `AccountKeyRoleBased`, with no depth limit enforced at decode time. A single crafted `TxTypeAccountUpdate`/`TxTypeAccountCreation` (or fee-delegated variants) transaction submitted through the public RPC can nest `RoleBased` account keys arbitrarily deep, driving unbounded recursion purely through RLP parsing — the same bug class as CVE-2020-36366 (stack overflow in a recursive `parse_value`-style decoder via crafted input).

### Finding Description
Account-key data for account-creation/account-update transactions is RLP-encoded separately and decoded via `AccountKeySerializer.DecodeRLP`, which dispatches on `keyType` and calls `s.Decode(serializer.key)`: [1](#0-0) 

When the key type is `AccountKeyTypeRoleBased`, `AccountKeyRoleBased.DecodeRLP` treats the payload as a list of byte-strings, and for **each** element independently invokes `rlp.DecodeBytes(b, &serializer)` on a fresh `AccountKeySerializer` — which can itself be another `AccountKeyRoleBased`: [2](#0-1) 

This recursive decode path is reached from `TxInternalDataAccountUpdate.fromSerializable` (and the analogous account-creation / fee-delegated variants), which is invoked directly from `DecodeRLP` when an incoming transaction is parsed off the wire / from a raw-tx RPC call: [3](#0-2) 

The only place in the codebase that rejects a "RoleBased key nested inside a RoleBased key" is `checkAccountKeyZeroValues` in the JSON-RPC `EncodeAccountKey` helper, which is not used on the transaction-decode/consensus path: [4](#0-3) 

Because the RLP `Stream` only bounds total input size (via `willRead`/`listLimit`), not recursion depth: [5](#0-4) 

an attacker can encode many nested `RoleBased→RoleBased→RoleBased…` levels within the size limits accepted by the mempool/RPC, each level costing only a few bytes of RLP overhead, so a bounded-size transaction can still produce very deep recursion. Each nesting level triggers another `rlp.DecodeBytes` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` cycle, growing the goroutine stack until Go's runtime hard stack limit is hit, which is a fatal, unrecoverable process crash (not a normal panic that can be caught).

### Impact Explanation
Submitting the crafted transaction via a public RPC endpoint (e.g., `eth_sendRawTransaction`) reaches this decode path in every full node/validator that receives and parses the transaction (mempool admission, block re-execution by other nodes). Exceeding Go's maximum goroutine stack size produces a fatal runtime error that terminates the entire node process, not just the handling goroutine. This is a concrete denial-of-service against Kaia's transaction/account-key handling reachable by any unprivileged transaction sender.

### Likelihood Explanation
Reaching the vulnerable code requires only crafting and submitting a single `TxTypeAccountUpdate`/`TxTypeAccountCreation` (or fee-delegated equivalent) transaction with a deeply nested `AccountKeyRoleBased` key payload — no special privileges, prior account state, or consensus role are required. The bug triggers purely during RLP decoding, before any semantic validation (including the existing but unused "no nested RoleBased" check) can reject the malformed key.

### Recommendation
Enforce a recursion/nesting depth limit (e.g., reject any `AccountKeyRoleBased` whose elements are themselves `AccountKeyTypeRoleBased`, matching the intent already expressed in `checkAccountKeyZeroValues`) directly inside `AccountKeyRoleBased.DecodeRLP`, before recursively decoding nested serializers, and/or track and cap decode depth in the shared `rlp.Stream`/`AccountKeySerializer.DecodeRLP` path so that malformed nested account keys are rejected immediately with a decode error instead of unbounded recursion.

### Proof of Concept
Conceptually:
1. Build `AccountKeyRoleBased` value `K0 = RoleBased([AccountKeyNil, AccountKeyNil, AccountKeyNil])`.
2. Recursively wrap: `K1 = RoleBased([K0, AccountKeyNil, AccountKeyNil])`, `K2 = RoleBased([K1, AccountKeyNil, AccountKeyNil])`, … up to `Kn` for large `n` (each level costs only a few RLP bytes).
3. RLP-encode `Kn` via `AccountKeySerializer` (as done by `EncodeAccountKey`/`toSerializable`) to get `KeyData`.
4. Construct a `TxTypeAccountUpdate` transaction whose `Key` field is this `KeyData`, sign it, and submit via `eth_sendRawTransaction`.
5. When any node calls `rlp.DecodeBytes` on the transaction (mempool ingestion or block processing), `TxInternalDataAccountUpdate.fromSerializable` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` recurses `n` times, eventually exhausting the goroutine stack and crashing the node with `runtime: goroutine stack exceeds ... fatal error`.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

// checkAccountKeyZeroValues returns errors if the input account key contains zero values of threshold or weight.
func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}
	return nil

// willRead is called before any read from the underlying stream. It checks
// n against size limits, and updates the limits if n doesn't overflow them.
func (s *Stream) willRead(n uint64) error {
	s.kind = -1 // rearm Kind

	if inList, limit := s.listLimit(); inList {
		if n > limit {
			return ErrElemTooLarge
		}
		s.stack[len(s.stack)-1] = limit - n
	}
	if s.limited {
		if n > s.remaining {
			return ErrValueTooLarge
		}
		s.remaining -= n
	}
	return nil
}
