### Title
Cached FROST preprocess seed is never deleted, enabling nonce reuse and secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

The kernel bug class is a missing cleanup: when a later step fails (or a one-time resource is consumed), the previously allocated resource is not released. The direct analog lives in `SigningProtocol::preprocess_internal`, which persists a one-time FROST preprocess seed in `CachedPreprocesses` and never deletes it after use — even though the FROST spec and the `from_cache` documentation explicitly require deletion to prevent reuse.

### Finding Description

`preprocess_internal` generates a `CachedPreprocess` (a 32-byte ChaCha20Rng seed that deterministically derives the FROST nonces `d` and `e`), XOR-encrypts it under a key derived from `self.key`, and stores it in the DB keyed by `self.context`. On every subsequent call with the same `context`, the stored seed is decrypted and loaded via `AlgorithmSignMachine::from_cache`, reproducing the *identical* nonces and commitments — `seeded_preprocess` derives `nonces` and `commitments` purely from `ChaCha20Rng::from_seed(*seed.0)` (crypto/frost/src/sign.rs:127-135).

There is no `CachedPreprocesses::remove` call anywhere; the seed survives for the lifetime of the context. This directly violates the contract in `SignMachine::from_cache` (crypto/frost/src/sign.rs:216-224): "After this, the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share." The spec/cryptography/FROST.md caching section states the same requirement.

The consumer `DkgConfirmer` binds the context to `(b"DkgConfirmer", self.attempt)` (signing_protocol.rs:275) while the signed message is `set_keys_message(set, removed, key_pair)` where `key_pair` is a caller-supplied parameter to `share()`/`complete()` (signing_protocol.rs:296-301). Any code path that calls `share()` a second time for the same `attempt` with a different `key_pair` — e.g., a retried DKG confirmation signing a different generated key pair — reuses the same nonces over a different message. `complete()` also re-invokes `share_internal`, again loading the identical seed.

### Impact Explanation

FROST shares are `z = d + b·e + c·λ·share`. Two shares `z1`, `z2` produced with the same `(d, e)` over different messages (different challenges `c1`, `c2`, same binding factor `b` and Lagrange coefficient `λ` for the same participant set) yield `share = (z1 - z2) / ((c1 - c2)·λ)`. Any participant who supplies preprocesses and observes both emitted signature shares recovers this validator's MuSig secret key, which under `musig(...)` reconstructs to the validator's threshold signing key. This is key share recovery from publicly exchanged protocol messages — the exact consequence the caching documentation warns about.

### Likelihood Explanation

The reuse is deterministic: the same `context` always reproduces the same seed. Exploitation requires the signer to emit two shares under the same `attempt` for differing `set_keys_message` payloads. Since `key_pair` is a parameter to `share()` rather than bound into the context, any retry path, double-invocation, or reboot-and-resign flow where a distinct `KeyPair` is proposed for the same attempt triggers the reuse. The risk was clearly anticipated — the code encrypts the cache and the spec mandates deletion — yet the delete step was never implemented, mirroring the kernel fix where `pci_release_regions()`/`pci_disable_device()` were missing.

### Recommendation

After loading the cached preprocess in `preprocess_internal` (signing_protocol.rs:137-145), remove it from `CachedPreprocesses` so each context yields the seed exactly once. Additionally, bind the intended message (or a hash of `key_pair`) into `context` so a retry with different signed data cannot reuse the same nonce, and add a regression test asserting a second `share()` under the same context produces different commitments.

### Proof of Concept

1. Validator runs `DkgConfirmer` for attempt `N`; `share(preprocesses, key_pair_A)` emits share `z1` over `msg_A = set_keys_message(set, removed, key_pair_A)` using seed `S` from `CachedPreprocesses[(b"DkgConfirmer", N)]`.
2. The confirmation is retried (or `share` is invoked again) with `key_pair_B`; `preprocess_internal` reloads the same undeleted seed `S`, regenerating identical `d`, `e`, and identical broadcast commitments.
3. The attacker collects `z1` and `z2`. With the same signing set, they compute `b` and `λ` from the public preprocesses and solve `share = (z1 - z2)·((c1 - c2)·λ)⁻¹`, recovering the validator's private key share.

A variant I could not fully verify within scope: whether `processor/src/signer.rs` retry/reboot paths can re-drive `share()` for the same attempt with differing key pairs — the missing-delete defect stands regardless, since the API contract requiring deletion is unambiguously violated.
