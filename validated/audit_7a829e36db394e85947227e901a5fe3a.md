## Title
ProtoJSON String Encoders Fail to Escape Unicode BiDi Override/Isolate Characters, Enabling Visual Spoofing of Serialized Text — (File: `src/google/protobuf/json/internal/writer.cc`, `upb/json/encode.c`, `php/ext/google/protobuf/php-upb.c`, `ruby/ext/google/protobuf_c/ruby-upb.c`)

## Summary
The Symfony advisory's failed invariant is: a value containing Unicode explicit-direction BiDi formatting characters (U+202A–U+202E, U+2066–U+2069) is serialized into an output format (HTML `href`) without escaping/rejecting those code points, letting an attacker control the *visual* rendering of trusted-looking text independent of its actual bytes. Protobuf has a directly analogous surface: `string` fields are validated only for UTF-8 *well-formedness* (`utf8_range::IsStructurallyValid`), never for dangerous code points, and the ProtoJSON string encoders are the place where downstream consumers (browsers, log viewers, terminals) actually render the decoded text. The C++ ProtoJSON writer (`src/google/protobuf/json/internal/writer.cc`) has a security-escaping table for exactly this class of characters, but it contains a code-point gap that leaves U+2066–U+2069 (LRI/RLI/FSI/PDI) unescaped, and the upb-based JSON encoders shared by C++, PHP, Ruby, and Python/upb do no Unicode security escaping at all, so both BiDi override (U+202A–U+202E) and isolate (U+2066–U+2069) characters flow straight into the emitted JSON string.

## Finding Description
`WireFormat`/`TcParser`/upb wire decoders accept any string field whose bytes are structurally valid UTF-8 [1](#0-0) [2](#0-1) . BiDi override characters (U+202A–U+202E) and isolate characters (U+2066–U+2069) are perfectly valid, structurally-correct UTF-8 code points, so no parser rejects them — the same missing check the Symfony advisory describes for `UrlSanitizer::parse()`.

When such a string is serialized to ProtoJSON, the C++ encoder explicitly maintains a table of "security escaped" ranges to defend against exactly this class of rendering attack: [3](#0-2) 
The table escapes `{0x2028, 0x202e}` (covering LRE/RLE/PDF/LRO/RLO) and `{0x2060, 0x2064}` plus `{0x206a, 0x206f}`, but leaves the range `0x2065`–`0x2069` completely uncovered. That gap exactly contains U+2066 (LRI), U+2067 (RLI), U+2068 (FSI) and U+2069 (PDI) — the very isolate characters the Symfony advisory calls out. These are passed to `Write(scalar.utf8)` unescaped: [4](#0-3) 

The upb JSON encoder — shared verbatim across core upb, PHP (`php-upb.c`), and Ruby (`ruby-upb.c`) — does not implement this security-escaping table at all; it only escapes ASCII control characters below `0x20` and the JSON-mandatory quote/backslash, passing every other byte (including full BiDi override/isolate sequences) straight through as raw bytes: [5](#0-4) . The identical logic recurs in [6](#0-5)  and [7](#0-6) .

By contrast, Java's `JsonFormat` only escapes control chars, quotes, `<>&='`, and `\u2028`/`\u2029` — it never escapes any of the BiDi override/isolate ranges either: [8](#0-7) . C#'s `JsonFormatter.WriteString` has the same code-point gap as the C++ implementation: escapes `0x2028-0x202e` and `0x2060-0x2064`/`0x206a-0x206f`, but not `0x2065-0x2069`: [9](#0-8) .

## Impact Explanation
An attacker who controls a bounded, well-formed Protobuf binary payload (an ordinary client of any consuming application/service that accepts and re-serializes protobuf messages to JSON for logs, UIs, or downstream systems) can embed U+2066–U+2069 (or, for the upb/Java backends, also U+202A–U+202E) in a `string` field. When that message is re-serialized via `MessageToJson`/`upb_JsonEncode`/PHP or Ruby's JSON serializer, the override/isolate characters pass through unescaped into the JSON string value. Any downstream viewer that renders that JSON string in a UI, terminal, or log console (the same class of consumer targeted by the original href-spoofing bug) can have its display visually reordered or spoofed — e.g., making a malicious filename, display name, or embedded URL-like string appear to be something else. This is CWE-1007/CWE-451-class visual spoofing, transferred from HTML `href` rendering to any UI that trusts ProtoJSON-escaped strings as "safe for display."

## Likelihood Explanation
High likelihood of reachability: any attacker who can supply a valid Protobuf message with a `string` field (a completely ordinary, schema-conformant capability) can trigger this, since there is no additional validation blocking these code points anywhere in the parse or JSON-encode path. However, actual security impact depends on the consuming application choosing to trust protobuf's JSON escaping as an XSS/spoofing defense and rendering the value in a security-sensitive UI context — which is a real but non-default assumption (protobuf itself makes no promises about this and the escaping tables that do exist are clearly intended precisely for this purpose, e.g., the `<`/`>`, ZWSP, and Arabic-sign entries are annotated "to prevent security bugs in JavaScript").

## Recommendation
- Extend the escaped-range table in `MustEscape()` (`src/google/protobuf/json/internal/writer.cc`) to close the `0x2065`–`0x2069` gap, covering U+2066–U+2069 (LRI/RLI/FSI/PDI) alongside the existing U+202A–U+202E coverage.
- Add equivalent Unicode security-escaping (not just ASCII control-char escaping) to the shared upb JSON encoder (`upb/json/encode.c`) so PHP, Ruby, and any upb-backed Python/C++ JSON serialization inherit the same protection.
- Add the same set of BiDi override/isolate ranges to Java's `JsonFormat.getReplacementOrNull` and complete C#'s `JsonFormatter` table.
- Consider documenting that ProtoJSON escaping is a best-effort mitigation for display-safety and is not a substitute for output-context-specific sanitization by consuming applications.

## Proof of Concept
1. Define a trusted schema with `string name = 1;`.
2. Build a binary payload where field 1 is the UTF-8 bytes for `"\xE2\x81\xA6malicious\xE2\x81\xA9safe.txt"` (U+2066 LRI ... U+2069 PDI wrapping "malicious"), which is structurally valid UTF-8 and parses successfully through `TcParser::MpString`/`upb_Decode` with no UTF-8 validation error.
3. Serialize the parsed message to ProtoJSON via the C++ `json/internal/writer.cc` path (or `upb_JsonEncode`, PHP/Ruby's JSON encoder).
4. Observe the emitted JSON string contains the raw U+2066/U+2069 bytes unescaped (verify against the `kEscapedRanges` table at lines 253–263, which has no entry covering `0x2065`–`0x2069`; for upb/PHP/Ruby, verify via `jsonenc_put_escaped_char`, lines 268–301/6807–6839/5560–5592, which never checks scalar value beyond `< 0x20`).
5. Rendering that JSON string value in a directionality-aware terminal or browser context will visually reorder the text, matching the spoofing effect described in GHSA-h5vq-qfcg-4m6p.

    private static final String[] replacementChars;

    static {
      replacementChars = new String[128];
      for (int i = 0; i <= 0x1f; i++) {
        replacementChars[i] = String.format("\\u%04x", i);
      }
      replacementChars['"'] = "\\\"";
      replacementChars['\\'] = "\\\\";
      replacementChars['\t'] = "\\t";
      replacementChars['\b'] = "\\b";
      replacementChars['\n'] = "\\n";
      replacementChars['\r'] = "\\r";
      replacementChars['\f'] = "\\f";

      // These characters are fully legal in JSON, but are escaped to prevent XSS risks. Notably
      // this topic is not like 'html escaping' where these would be replaced with something like
      // `&lt;`. The escaped or not ways of writing it are verbatim 2 exactly equivalent
      // ways to represent the same exact value in JSON: consumers should never do any manual
      // unescape to round trip the intended value. This replacement is only be semantically
      // observable if someone tries to handle it raw textually and not as JSON.
      for (int i : "<>&='".toCharArray()) {
        replacementChars[i] = String.format("\\u%04x", i);
      }
    }

    /**
     * If a character needs to be escaped, returns the replacement string. Otherwise, returns null.
     */
    private static String getReplacementOrNull(char c) {
      if (c < 128) {
        return replacementChars[c];
      }

      // \u2028 and \u2029 are paragraph whitespace characters that had mismatch between the
      // JSON spec and the browser JavaScript object literal spec. It is extremely unlikely
      // this topic matters now, but for parity with GSON we escape them.
      if (c == '\u2028') {
        return "\\u2028";
      }
      if (c == '\u2029') {
        return "\\u2029";
      }

      return null;
    }
