### Title
Deterministic `CachedPreprocess` reused across `share`/`complete` invocations for the same DKG attempt — FROST nonce reuse leaks the private key share - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The Tapioca bug class is: a message is produced under state snapshot S, but processed later against mutated state S′ — the count check then fails and the message (and the funds it carries) is stuck forever. Serai's analogous shape is `SigningProtocol::preprocess_internal` / `DkgConfirmer`: the FROST preprocess is not generated fresh per signing action — it is deterministically regenerated from a cached 32-byte seed keyed only by `(context = "DkgConfirmer", attempt)`, while the message being signed (`set_keys_message`) depends on mutable state (the `KeyPair` stored in `DkgKeyPair`). Where Tapioca reverts and strands the message, Serai silently produces a second signature share over the *same* nonces — the strictly worse outcome.

### Finding Description
`preprocess_internal` stores a ChaCha20-seeded `CachedPreprocess` in `CachedPreprocesses`, keyed only by `context` (`(b"DkgConfirmer", attempt)`), and regenerates the identical `AlgorithmSignMachine` — identical nonces and identical commitments — on every call for that attempt [1](#0-0) . The machine is rebuilt in `share_internal`, which is invoked by both `share()` and `complete()` [2](#0-1) . The signed message is `set_keys_message(&spec.set(), &removed, key_pair)` — it varies with the `key_pair` argument [3](#0-2) . The caller `generated_key_pair` unconditionally overwrites `DkgKeyPair`/`KeyToDkgAttempt` and then calls `share(preprocesses, key_pair)` with no guard against a second invocation for the same `attempt` [4](#0-3) . Inside `sign`, the effective nonce is `base + rho * actual` where `actual` comes from the deterministic seed and `rho` is bound only to the preprocesses transcript — not to `key_pair` [5](#0-4) .

So if `generated_key_pair` (or `share`/`complete` more generally) executes twice for the same attempt with a different `key_pair` — e.g., a re-driven DKG confirmation producing a distinct key pair, or a retry after a DB state change — two Schnorrkel signature shares are emitted (or one emitted plus one used to assemble the confirmation signature in `complete`) over identical nonces but different challenge hashes. Given shares `s1 = k + c1·x` and `s2 = k + c2·x` with the same effective nonce `k`, the secret share is recovered as `x = (s1 − s2)/(c1 − c2)`. The code's own comments acknowledge reuse "will enable third-party recovery of your private key share" [6](#0-5) .

### Impact Explanation
Recovery of a validator's FROST secret share for the set-keys confirmation session reduces the security of the just-confirmed threshold key; combined with shares recovered from other sessions or a threshold of compromised validators, it can enable unauthorized signing. This is a concrete key-share-recovery primitive, not a DoS — mirroring the report's "permanent loss" impact but with secret leakage instead of stuck funds.

### Likelihood Explanation
The vulnerability requires `share`-producing paths to execute more than once for the same `(attempt)` context with differing signed content. `generated_key_pair` has no idempotence guard (it blindly `set`s `DkgKeyPair`/`KeyToDkgAttempt` and calls `share`), and `complete` re-derives the share machine internally, so any path where the stored `key_pair` or the preprocess set seen by `share` vs. `complete` diverges (late-arriving `ConfirmationNonces`, DB rewrite, processor re-drive) produces a second share over reused nonces. I was unable to trace every upstream caller of `generated_key_pair`/`DkgConfirmer::share` to confirm how easily a second invocation with a distinct `key_pair` is triggered, so the trigger frequency is uncertain — but the reuse is unconditional in the code: the cached seed is never cleared or rotated after `share` completes.

### Recommendation
- Delete (or rotate) the `CachedPreprocesses` entry the first time a share is produced for a context, so `share_internal` cannot deterministically regenerate the same nonces.
- Bind the context to the full message being signed (e.g., include `key_pair` bytes and the preprocess set hash in `context`) rather than just `attempt`, so any change in signed content forces fresh nonce material.
- Add an idempotence guard in `generated_key_pair` (e.g., refuse if `DkgKeyPair` is already set for the attempt).

### Proof of Concept
1. Attempt `a` of the DKG confirmation completes its preprocess phase; `ConfirmationNonces` is populated and `dkg_confirmation_nonces(a)` returns the deterministic commitments derived from the cached seed.
2. `generated_key_pair(txn, key, spec, kp1, a)` stores `kp1` and calls `DkgConfirmer::share` → emits share `s1` over `set_keys_message(set, removed, kp1)` with nonce `k = base + rho·actual` derived from the cached seed.
3. A second call `generated_key_pair(txn, key, spec, kp2, a)` with `kp2 ≠ kp1` (the unconditional `DkgKeyPair::set` at handle.rs:54 permits this) calls `share` again → `preprocess_internal` returns the identical seed → identical `k`, but challenge `c2 ≠ c1` since the message differs.
4. `x = (s1 − s2)·(c1 − c2)⁻¹` recovers the validator's MuSig'd secret share for the confirmation session.

Caveat: I did not fully enumerate the processor-side call graph that drives `generated_key_pair`, so step 3's trigger depends on whether the coordinator can be driven to confirm two distinct key pairs within one attempt (e.g., via a DKG retry/blame path). The nonce reuse itself is unconditional and needs only that second `share` invocation.

    msg: &[u8],

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();

      preprocesses.insert(

        machine

          .map_err(|_| participant)?,
      );

      FrostError::InvalidSigningSet(_) |

      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;
