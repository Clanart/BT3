### Title
Silent, unconfirmed rewrite of the default git remote URL from an untrusted GitHub API `clone_url` field - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts` automatically executes `git remote set-url` on the repository's default remote whenever the GitHub API's `clone_url` for the associated repository differs from what Desktop has cached, with no user prompt or confirmation. This is structurally the same broken-invariant class as the GammaVault report: a value that materially changes a critical action (there: liquidation collateral; here: the destination of every future `push`/`fetch`) is derived directly from a single, spoofable/attacker-influenced external data source and applied without a manipulation-resistant check or explicit user consent.

### Finding Description
`updateRemoteUrl` is invoked from `repositoryWithRefreshedGitHubRepository` in `app-store.ts`, which is Desktop's periodic/background repository-refresh path that calls `api.fetchRepository(owner, name)` and feeds the raw API response straight into `updateRemoteUrl`: [1](#0-0) 

Inside `updateRemoteUrl`, the only guards are protocol matching and a check that the *previously cached* `cloneURL` still matches the current remote — there is no verification that the new `clone_url` value returned by the API is legitimate, nor any user confirmation step, before Desktop rewrites the remote: [2](#0-1) 

The actual mutation goes straight to disk via `git remote set-url`: [3](#0-2) [4](#0-3) 

Notably, Desktop *does* have a confirmation-dialog pattern for a very similar remote-URL change — the `upstream` remote is only updated after the user clicks "Update" in the `UpstreamAlreadyExists` dialog: [5](#0-4) 

But the `origin`/default remote path in `updateRemoteUrl` bypasses that pattern entirely and writes silently. This satisfies the "attacker controls a GitHub API object" precondition explicitly listed as valid: any entity able to influence the `clone_url` field returned for a repository the user has added to Desktop (e.g., a compromised/malicious GitHub Enterprise Server the user has connected an account to, a MITM'd API response, or a repository owner who transfers/renames a repo the victim tracks) can cause Desktop to silently retarget the user's local git remote to an arbitrary host.

### Impact Explanation
Because the remote rewrite happens transparently in the background, all subsequent `git push`/`git fetch` operations — and the credentials/tokens supplied by the credential helper for that host — go to whatever host is now configured, without the user ever seeing a prompt. This can result in: silent redirection of code pushes to an attacker-controlled endpoint (source exfiltration), or credential/token exfiltration if the new host differs from github.com and the credential helper offers stored credentials for that context. This matches the explicitly valid impact category "silent corruption of what the user commits or pushes" / "credential exfiltration."

### Likelihood Explanation
Medium: exploitation requires the attacker to control (or manipulate) an `IAPIRepository.clone_url` value returned to the victim's Desktop instance for a repository already tracked locally — realistic for GitHub Enterprise Server setups where the attacker has admin/API-response control, or for repository transfer/rename scenarios engineered by a malicious repo owner that a victim has cloned. It does not require local access, admin rights, or prior malware, matching the "GitHub API object" attacker model called out as valid.

### Recommendation
Do not silently `git remote set-url` the default remote from background API refresh. At minimum:
- Require explicit user confirmation (reusing the existing `UpstreamAlreadyExists`-style dialog pattern) before changing the default/origin remote URL based on API data.
- Cross-validate the new `clone_url`'s owner/repo identity against the repository's known `id` (GitHub repository IDs are stable across renames) rather than trusting the string value alone, and flag/reject changes where the resolved host or owner differs unexpectedly.
- Log/surface the change prominently so users can detect unexpected remote retargeting.

### Proof of Concept
1. User adds a repository in Desktop backed by an account/endpoint under attacker influence (e.g., a GHES instance the attacker can manipulate, or a github.com repo later transferred to an attacker-controlled account while keeping the same name).
2. Desktop's background refresh calls `api.fetchRepository(owner, name)` → `apiRepo.clone_url` now points to the attacker's target repository/host. [1](#0-0) 
3. `updateRemoteUrl` finds `protocolsMatch === true`, `remoteUrlUnchanged === true` (user never manually touched the remote), and `urlsMatch === false` (new URL differs) → calls `gitStore.setRemoteURL(...)` unconditionally. [6](#0-5) 
4. `git remote set-url origin <attacker-url>` executes with no dialog shown to the user. [3](#0-2) 
5. The user's next push/fetch silently targets the attacker's URL.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
