## Title
Consensus-relayer reward misattribution lets an attacker steal other relayers' rewards by batching an unrelated `ConsensusMessage` alongside honest updates - (`modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::on_executed` identifies exactly one relayer to pay per batch — the signer of the *first* message, only if that message is a `Message::Consensus` — but then pays that single relayer for **every** `StateMachineUpdated` event present in the whole batch, regardless of which message/relayer actually produced each state-machine advance.

### Finding Description
`on_executed` derives `maybe_relayer_account` solely from `messages.get(0)`: [1](#0-0) 

It then collapses **all** `IsmpEvent::StateMachineUpdated` events in the batch (for every state machine, not just the one touched by message 0) into `highest_per_state_machine`, and pays the single identified relayer for every entry: [2](#0-1) 

A single `pallet-ismp` extrinsic call can carry a `Vec<Message>` containing multiple `Message::Consensus` entries for different state machines, each independently signed and independently verified/committed by the ISMP consensus handler. `on_executed` receives the whole batch's events but only ever looks at `messages[0]`'s signature to decide who gets paid. If an attacker crafts (or simply reorders/front-loads within their own extrinsic submission) a batch where their own trivial/minimal `ConsensusMessage` for chain A is `messages[0]`, and includes an honestly-relayed `ConsensusMessage` for chain B (obtained by copying a legitimate, still-valid consensus proof — no signing key needed, since ISMP consensus messages are proofs, not authenticated relayer actions tied to payment), both state machine advances land in `highest_per_state_machine`, and **the attacker's address collects the reward for chain B's advance too**, even though the real reward calculated in `calculate_reward` is based on genuine height deltas the attacker did not cause with their own message. The `LastRewardedHeight` watermark correctly prevents double-payment of the *same* height range on separate calls, but it does not prevent the *wrong* payee from being credited within a single batch.

This is a real logic/beneficiary-binding bug: the code binds "who gets paid" to `messages[0]` while binding "how much to pay" to the union of `StateMachineUpdated` events across the whole batch, breaking the intended one-to-one relayer↔proof reward relationship enforced everywhere else in the pallet (e.g., the watermark logic explicitly designed to prevent double-claiming, per the `reward_covers_only_unpaid_heights_after_rollback` test). [3](#0-2) 

### Impact Explanation
This is a direct fund-diversion bug in a live reward-distribution pallet: treasury funds intended for the relayer who actually submitted/verified a given state machine's consensus proof are instead transferred to whichever relayer happens to occupy `messages[0]` of the batch. An attacker who can influence batch composition (e.g. by submitting their own message alongside — or racing to include — other pending consensus messages in the mempool/block) can systematically redirect `RelayerRewarded` payouts to themselves, at the expense of the legitimate relayers who performed the actual consensus verification work. This is unauthorized transfer of treasury funds to the wrong beneficiary — squarely within the bounty's "stealing or loss of funds" / "logic attacks" category.

### Likelihood Explanation
Exploitability depends on the ability to compose a multi-message batch where the attacker's own message is first while other genuine `ConsensusMessage`s for other state machines are included in the same call. Whether normal block/extrinsic construction allows an unprivileged relayer to arbitrarily interleave multiple independent relayers' pending messages into a single `pallet-ismp` call (vs. one message per call) determines real-world frequency; this could not be fully confirmed from the indexed code (the exact `handle`/dispatch entrypoint of `pallet-ismp` that assembles `messages: Vec<MessageWithWeight>` before calling `on_executed` was not retrievable within the available search budget). If batches are normally single-message per submitter, likelihood is lower but the flaw remains latent and triggers as soon as any legitimate multi-message batch (e.g. a relayer bundling several chains' updates in one call, or several relayers' messages combined by a sequencer/aggregator) occurs — at that point mis-payment happens automatically, with no attacker action needed beyond ordinary batch construction.

### Recommendation
Attribute each `StateMachineUpdated` event's reward to the relayer who actually signed the specific `Message::Consensus` that produced it, not to `messages[0]`'s signer applied to the whole batch. Concretely: iterate `messages`, and for each `Message::Consensus`, recover its own relayer key, and only reward the `StateMachineUpdated` event(s) that resulted from processing *that* message (e.g. by correlating message index/state-machine-id, or by having the consensus handler emit an event that includes the relayer/message identity directly) — never fan out a single message's signer credit across unrelated events elsewhere in the batch.

### Proof of Concept
Conceptual sequence:
1. Relayer B submits a valid, currently-includable `ConsensusMessage` update for state machine `Y` (e.g. advancing height 100→110), which is pending inclusion.
2. Attacker A crafts their own extrinsic/batch call to `pallet-ismp` containing `[ConsensusMessage_for_X_signed_by_A, ConsensusMessage_for_Y_taken_from_B's_proof]` (the second message is a valid, unmodified consensus proof — no signature forgery needed since its validity is proof-based, not payment-authorization-based).
3. `pallet-ismp`'s message handler processes both, successfully advancing state machine `X` and `Y`, emitting two `IsmpEvent::StateMachineUpdated` events.
4. `on_executed` is invoked with `messages = [msg_X(signed A), msg_Y]` and both `StateMachineUpdated` events.
5. `maybe_relayer_account` resolves to `A` (from `messages[0]`) per [4](#0-3) .
6. Both `highest_per_state_machine` entries (`X` and `Y`) are processed and rewarded to `A` per [5](#0-4) , so `A` is paid for `Y`'s 10-block advance that `B` actually delivered — `B` receives nothing for that update.

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}

#[test]
fn reward_covers_only_unpaid_heights_after_rollback() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		const BLOCK_COST: u128 = 100;
		let host = Ismp::default();
		let state_machine_id = setup_state_machine();
		let treasury_account: AccountId32 = PalletId(*b"treasury").into_account_truncating();

		pallet_consensus_incentives::Pallet::<Test>::update_cost_per_block(
			RuntimeOrigin::root(),
			state_machine_id,
			BLOCK_COST,
		)
		.unwrap();

		let (consensus_message, relayer_account) = setup_host_and_message(&host);
		let message = MessageWithWeight { message: consensus_message, weight: Weight::zero() };
		let updated = |height: u64| {
			vec![IsmpEvent::StateMachineUpdated(StateMachineUpdated {
				state_machine_id,
				latest_height: height,
			})]
		};

		// The chain has already advanced to 1025 and every block up to it has been rewarded once.
		host.store_state_machine_commitment(
			StateMachineHeight { id: state_machine_id, height: 1024 },
			commitment(),
		)
		.unwrap();
		host.store_latest_commitment_height(StateMachineHeight {
			id: state_machine_id,
			height: 1024,
		})
		.unwrap();
		host.store_state_machine_commitment(
			StateMachineHeight { id: state_machine_id, height: 1025 },
			commitment(),
		)
		.unwrap();
		host.store_latest_commitment_height(StateMachineHeight {
			id: state_machine_id,
			height: 1025,
		})
		.unwrap();

		let treasury_before_first = Balances::balance(&treasury_account);
		<pallet_consensus_incentives::Pallet<Test> as FeeHandler>::on_executed(
			vec![message.clone()],
			updated(1025),
		)
		.unwrap();

		assert_eq!(Balances::balance(&treasury_account), treasury_before_first - BLOCK_COST);
		assert_eq!(
			pallet_consensus_incentives::LastRewardedHeight::<Test>::get(state_machine_id),
			Some(1025)
		);

		// The previous-height pointer references an older height whose commitment is no longer
		// retained in the bounded map.
		pallet_ismp::PreviousStateMachineHeight::<Test>::insert(state_machine_id, 1);

		// Deleting the latest commitment rolls the latest height back to that previous pointer.
		host.delete_state_commitment(StateMachineHeight { id: state_machine_id, height: 1025 })
			.unwrap();
		assert_eq!(host.latest_commitment_height(state_machine_id).unwrap(), 1);

		// The next honest consensus update advances to 1030, carrying the stale pointer forward as
		// the new previous height.
		host.store_state_machine_commitment(
			StateMachineHeight { id: state_machine_id, height: 1030 },
			commitment(),
		)
		.unwrap();
		host.store_latest_commitment_height(StateMachineHeight {
			id: state_machine_id,
			height: 1030,
		})
		.unwrap();
		assert_eq!(host.previous_commitment_height(state_machine_id), Some(1));

		let treasury_before_second = Balances::balance(&treasury_account);
		<pallet_consensus_incentives::Pallet<Test> as FeeHandler>::on_executed(
			vec![message],
			updated(1030),
		)
		.unwrap();

		// The real advance is 1025 -> 1030, so only the 5 new blocks are paid rather than the full
		// span back to the previous pointer.
		assert_eq!(Balances::balance(&treasury_account), treasury_before_second - 5 * BLOCK_COST);
		assert_eq!(
			pallet_consensus_incentives::LastRewardedHeight::<Test>::get(state_machine_id),
			Some(1030)
		);
	})
}
