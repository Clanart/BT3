## Title
NUL-Byte Field-Boundary Injection in `git log -z` Delimiter Parsing Can Silently Reassign Commit SHAs/Authors to the Wrong Commit — (`File: app/src/lib/git/git-delimiter-parser.ts`)

### Summary
The BLS report's core defect is that a single logical object (a signature) has two distinct valid byte encodings, and code that treats byte-equality/positional-parsing as a proxy for object identity gets fooled, corrupting a uniqueness/attribution invariant. The closest verifiable analog in this codebase is in Desktop's own git-output parser: `createLogParser` (used by `getCommits`) assumes the NUL byte (`\0`) can never appear inside a commit field (message, body, trailers, refs) and uses it purely as a positional field separator. Git does not prevent a commit's message/body from containing raw NUL bytes, so a malicious/compromised repository the user clones or fetches can supply a commit whose body contains an embedded `\0`. This desynchronizes the fixed-width record splitting in `createLogParser`, causing every subsequent commit's SHA, author, parents, and message to be reassigned to the wrong entry — a silent metadata/identity corruption analogous to the malleable-encoding problem in the source report.

### Finding Description
`getCommits` in [1](#0-0)  builds a `git log -z --format=...` invocation whose fields are separated with `%x00` (a literal NUL byte), and reads the result as a `Buffer`.

The parser that consumes this output, `createLogParser`, is defined in [2](#0-1) :

```
const parse = <V extends string | Buffer>(value: V) => {
  const records = (
    Buffer.isBuffer(value) ? splitBuffer(value, '\0') : value.split('\0')
  ) as V[]
  const entries = []
  for (let i = 0; i < records.length - keys.length; i += keys.length) {
    const entry = {} as { [K in keyof T]: V }
    keys.forEach((key, ix) => (entry[key] = records[i + ix]))
    entries.push(entry)
  }
  return entries
}
```

This logic performs **pure positional slicing**: it splits the entire buffer on every `\0` byte, then walks the flat list in fixed-size chunks of `keys.length` (here 8: sha, shortSha, summary, body, author, committer, parents, trailers, refs — actually 9 fields), assuming that exactly one `\0` separates each formatted field and that no `\0` ever appears *inside* a field's content (e.g. inside `%b` — the raw commit body — or `%(trailers:unfold,only)`).

Git does not sanitize or reject NUL bytes embedded in a commit message/body; such objects can be created (e.g., via `git hash-object`/`git commit-tree` writing a tree+message blob with a raw `\0` in it, or a crafted pack) and successfully fetched/cloned by an unprivileged remote/repository the user adds. `splitBuffer` (`app/src/lib/split-buffer.ts`) faithfully splits on every literal `\0`, so an attacker-controlled body containing even one extra `\0` inserts one extra "record" into the flat array. Because the parser has no per-record delimiter or field-count guard — it only knows the intended field count `keys.length` and blindly re-slices from wherever it currently is — one injected `\0` in a single malicious commit shifts every subsequent commit's field alignment by one, permanently misattributing SHA↔author↔message↔parents pairs for the remainder of the log output.

`getCommits` then trusts this misaligned data to construct `Commit` objects directly [3](#0-2) , with no sanity check (e.g., verifying `commit.sha` looks like a 40-hex-character string, or that `parents` values are valid SHAs) before they're surfaced throughout the UI (history list, commit details, diff view, blame, revert/cherry-pick/reset target selection).

### Impact Explanation
This breaks the same class of invariant as the source report: an attacker-controlled object (here, a commit body/trailer inside a repository the victim clones or adds as a remote) has a byte-level property (an embedded `\0`) that defeats a supposedly reliable identity/association check (positional field mapping), causing the wrong metadata to be silently bound to the wrong commit. Concretely, a user could:
- See an innocuous author/message/SHA displayed for what is actually a different, malicious commit (attribution spoofing).
- Select an item in the History list to revert, cherry-pick, or reset to, believing it corresponds to the SHA/message shown, while the app internally records or acts on a different SHA than displayed — "silent corruption of what the user commits/pushes" as specified in the Valid Impact criteria.
- Have downstream automation (rebase todo generation, amend flows, changelog generation) act on mismatched SHA/author/parent data derived from this corrupted parse.

This does not directly grant code execution or file-system escape, but it is a genuine, unprompted, attacker-reachable data-integrity break sourced entirely from cloning/fetching a hostile repository — no unusual user action beyond normal repo browsing is required.

### Likelihood Explanation
Requires only that the victim open/clone/fetch a repository controlled (or made malicious via compromise) by the attacker and view its history in Desktop (which happens automatically when a repository is opened — `getCommits` backs the default History view). Crafting a commit object containing a raw NUL in its message is straightforward using low-level plumbing commands (`git hash-object -w --stdin`, `git commit-tree`) and does not require the victim to run anything unusual — Desktop calls `getCommits` as part of normal repository browsing.

### Recommendation
- Do not rely on a single fixed separator byte for machine-parseable `git log`/`git for-each-ref` output when the payload includes arbitrary user-controlled content (commit body, trailers). Use a self-describing format (e.g., length-prefixed fields, or a per-record delimiter distinguishable from within-field content, or invoke `git log` once per field with `%x00%x00` record boundaries and reject/escape embedded NULs).
- Alternatively, validate/reject records whose `sha` field does not match `^[0-9a-f]{40}$` (or the configured hash length) before constructing a `Commit`, so a desynchronized parse fails safely (drops/flags the bad entries) instead of silently misattributing metadata.
- Apply the same review to other delimiter-based parsers in this file (`createForEachRefParser`) and any other `-z`/NUL-delimited `git` invocations for the same failure mode.

### Proof of Concept
1. In a scratch repository, craft a commit object whose message contains a literal NUL byte, e.g. using `git hash-object` / `git commit-tree` to write a commit whose message bytes are `"innocuous message" + "\x00" + "extra"` (bypassing the shell's normal inability to pass NUL via `-m`).
2. Push/host this repository and have the victim clone/fetch it in GitHub Desktop.
3. Call `getCommits` (as Desktop does automatically to populate the History pane) — the injected `\0` adds one extra element to the flat `records` array produced by `splitBuffer`/`split('\0')` in [4](#0-3) , shifting the chunked field mapping for that commit and every commit parsed afterward in the same invocation.
4. Observe that the SHA, author, and message shown for subsequent commits in the History list no longer correspond to their actual git values — confirming the malleability-style corruption of the SHA↔metadata association that downstream UI/actions (revert, cherry-pick, reset, PR review) rely on being trustworthy.

**Note on verification limits:** I was unable to execute git or the app in this environment to empirically confirm that git will actually store/transmit a commit message containing a raw `\0` byte without `fsck`/transfer rejecting it (git has an `fsck.nulInCommitMessage` check that some configurations treat as an error, and the default strictness during `receive-pack`/`fetch` for arbitrary NUL bytes was not verifiable via static code search alone). This assumption is the crux of exploitability and should be validated experimentally (e.g., with a local test repo and `dugite`) before treating this as a confirmed, exploitable finding rather than a plausible analog derived from the parser's code structure.

export function createLogParser<T extends Record<string, string>>(fields: T) {
  const keys: Array<keyof T> = Object.keys(fields)
  const format = Object.values(fields).join('%x00')
  const formatArgs = ['-z', `--format=${format}`]

  const parse = <V extends string | Buffer>(value: V) => {
    const records = (
      Buffer.isBuffer(value) ? splitBuffer(value, '\0') : value.split('\0')
    ) as V[]
    const entries = []

    for (let i = 0; i < records.length - keys.length; i += keys.length) {
      const entry = {} as { [K in keyof T]: V }
      keys.forEach((key, ix) => (entry[key] = records[i + ix]))
      entries.push(entry)
    }

    return entries
  }

  return { formatArgs, parse }
}
