### Title
Missing zero-check on governance-controlled `GasTarget` causes division-by-zero panic in KIP-71 base fee calculation - (File: `params/kip71_config.go`)

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by the governance-controlled parameter `GasTarget` without checking that it is non-zero, unlike the sibling parameter `BaseFeeDenominator`, which is explicitly protected against a zero value in both the calculation function and its governance format checker.

### Finding Description
In `NextMagmaBlockBaseFee`, when the parent block's gas usage differs from `gasTarget`, the code computes the base-fee delta by dividing by `gasTarget` directly, with no zero-check: [1](#0-0) [2](#0-1) 

Compare this to `BaseFeeDenominator`, which does have an explicit zero-guard right above: [3](#0-2) 

The governance parameter registry confirms the asymmetry: `Kip71BaseFeeDenominator` enforces `v != 0` in its `FormatChecker`, while `Kip71GasTarget` uses `noopFormatChecker`, which performs no validation at all: [4](#0-3) 

Because `GasTarget` can be set to `0` through the governance parameter update mechanism (single governance mode governing-node vote, or KIP governance contract vote, both of which are in-scope "governance parameters" paths) without any client-side rejection, the very next block whose `parentGasUsed != 0` (i.e., almost any block containing at least one transaction) will trigger `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0`. `big.Int.Div` panics on division by zero, exactly analogous to the TFLite `Div` kernel's unchecked division-by-zero (CVE-2021-37683/GHSA-rhrq-64mq-hf9h): both lack a guard on a caller/governance-supplied divisor before performing integer division.

`NextMagmaBlockBaseFee` is used across the block-production and validation pipeline (header base-fee verification in `blockchain/block_validator.go`, block assembly in `work/worker.go`, test block makers in `blockchain/chain_makers.go`, and RPC-facing gas price/fee-history estimation in `node/cn/gasprice/gasprice.go` and `node/cn/gasprice/feehistory.go`), so a governance-set `GasTarget = 0` propagates the panic to every node computing or verifying the next base fee.

### Impact Explanation
Once `GasTarget` is set to `0` via a governance vote, every full node that attempts to verify the next block header's `BaseFee` (via `VerifyMagmaHeader`) or to assemble the next block (via the worker/miner) hits an unrecovered `big.Int` division-by-zero panic. This uniformly crashes the base-fee computation path across all nodes on the network for essentially every subsequent block (any block with `GasUsed != 0`), which is a consensus-critical chain-halting condition. Because RPC gas-price/fee-history endpoints also call the same routine, public-RPC-facing services are affected as well.

### Likelihood Explanation
The bug is triggered purely by a governance parameter value with no defensive validation (`noopFormatChecker`), unlike the adjacent `BaseFeeDenominator` parameter which is explicitly protected. Any governance participant (governing node in single mode, or a party controlling votes in KIP governance mode) reaching consensus on `Kip71GasTarget = 0` — a value that passes all existing format checks — will deterministically and immediately crash base-fee computation for the following block(s), which occur naturally as soon as any transaction consumes gas.

### Recommendation
Add a non-zero `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go`, mirroring the one already used for `Kip71BaseFeeDenominator` (`v != 0`). Additionally, add a defensive guard in `NextMagmaBlockBaseFee` (`params/kip71_config.go`) that falls back to a safe default (as is already done for `BaseFeeDenominator == 0`) when `GasTarget == 0`, so that a malformed or historically-set configuration cannot crash header verification or block assembly.

### Proof of Concept
1. Through the governance mechanism, submit/approve a governance vote setting `kip71.gastarget` (or the equivalent `GovParam`) to `0`. This passes validation because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`. [5](#0-4) 
2. Once the parameter becomes active at the next epoch/apply block, any subsequent block with `GasUsed > 0` causes `KIP71Config.NextMagmaBlockBaseFee` to execute the `parentGasUsed > gasTarget` branch, computing `gasUsedDelta := parentGasUsed - 0` and then `x.Div(x, new(big.Int).SetUint64(0))`. [6](#0-5) 
3. `big.Int.Div` panics with "division by zero" inside header verification (`blockchain/block_validator.go`) and block assembly (`work/worker.go`), crashing/halting node processes network-wide.
