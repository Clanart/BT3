### Title
Unbounded recursive RLP deserialization of nested `AccountKeyRoleBased` allows CPU/memory DoS before nesting is rejected - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively RLP-decodes each element of an `AccountKeyRoleBased` key as an arbitrary nested `AccountKey`, with no depth limit, size budget, or nesting check applied during decoding. The check that forbids nested composite keys (`ErrNestedCompositeType`) only runs afterwards, in `CheckInstallable`/`CheckUpdatable`. This mirrors the AshCloak bug class: attacker-supplied bytes are fully deserialized into memory/CPU-consuming structures before any safety validation gate is reached.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of opaque byte strings, and for each one instantiates a fresh `AccountKeySerializer` and recursively RLP-decodes it as an `AccountKey`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads a key type byte and then dispatches decoding to the corresponding `AccountKey` implementation — which, if that type is again `AccountKeyTypeRoleBased`, re-enters `AccountKeyRoleBased.DecodeRLP`: [2](#0-1) 

Nothing in this decode path bounds the number of elements per `RoleBased` list or the recursion depth. The only guard against this structure — rejecting nested composite keys and enforcing `len(*a) <= RoleLast` — is `CheckInstallable`, which is invoked only *after* the full RLP structure has already been decoded into memory: [3](#0-2) 

This decode path is reached directly by `AccountUpdate`/`FeeDelegatedAccountUpdate`/`AccountCreation` transactions and their fee-delegated variants, all of which carry an `accountkey.AccountKey` field decoded from attacker-controlled RLP as part of ordinary transaction decoding (`tx.DecodeRLP` → `TxInternalDataSerializer.DecodeRLP` → type-specific `DecodeRLP`), i.e. before any pool-level or block-level semantic validation runs: [4](#0-3) [5](#0-4) 

The existing test suite explicitly documents that nested `RoleBased` keys are supposed to be forbidden, but the enforcement happens at the semantic-validation stage (tx pool `AddRemote` / block application), not at decode time — confirming that decoding proceeds unconditionally on attacker-chosen nesting before rejection: [6](#0-5) 

Unlike the AshCloak case (unbounded atom interning / decompression bomb from a single decrypted binary), here the amplification vector is combinatorial: each `RoleBased` node can contain up to a large number of byte-string children (no size cap enforced during decode), and each child can itself be a `RoleBased` node containing more children, recursively, all reconstructed into live Go objects and recursively RLP re-decoded (`rlp.DecodeBytes` called once per node) before the top-level `CheckInstallable`/`CheckUpdatable` call ever runs.

### Impact Explanation
A single crafted `AccountUpdate`/`AccountCreation` (or fee-delegated variant) transaction with a deeply/broadly nested `AccountKeyRoleBased` payload forces every node that decodes the transaction (mempool ingestion via `AddRemote`, and later block-application by all nodes) to perform unbounded recursive allocation and RLP decoding work proportional to the crafted structure's node count, before the nesting is ever rejected. This can consume excessive CPU and memory, or trigger a Go runtime stack-overflow panic in the recursive decode, causing the processing node to crash or stall — a node-level Denial of Service reachable by any unprivileged transaction sender, matching the medium-severity DoS-via-untrusted-deserialization class of CVE-2026-81319.

### Likelihood Explanation
Any account holder can submit an `AccountUpdate`, `FeeDelegatedAccountUpdate`, or `AccountCreation` transaction containing a hand-crafted RLP-encoded `AccountKeyRoleBased` value; no special privileges, prior state, or cooperation from other parties is required. The transaction only needs to pass basic RLP well-formedness and signature checks to reach the vulnerable decode path in the mempool of every peer that receives/gossips it, and again during block execution.

### Recommendation
Enforce structural limits (maximum element count and maximum nesting depth, e.g. reject any `AccountKeyRoleBased`/composite key type nested inside another) directly inside `AccountKeyRoleBased.DecodeRLP` before recursing, rather than only in the post-decode `CheckInstallable`/`CheckUpdatable` validators. Additionally, bound the total decoded size/element count for `AccountKeySerializer`-driven recursive decoding to prevent CPU/memory amplification from a single RLP-encoded transaction field.

### Proof of Concept
1. Construct a chain of `AccountKeyRoleBased` values where each level's single element is itself an `AccountKeyRoleBased` with N further such elements (only bounded by overall transaction RLP encoding size, which is not depth-checked during decode).
2. Encode this nested structure with `accountkey.NewAccountKeySerializerWithAccountKey` / `rlp.EncodeToBytes`, and place it as the `Key` field of an `AccountUpdate` transaction, sign it validly.
3. Submit the transaction via public RPC (`eth_sendRawTransaction`) to an endpoint node; on ingestion the node calls `tx.UnmarshalBinary`/`DecodeRLP`, which recursively invokes `AccountKeyRoleBased.DecodeRLP` for every nested level, fully materializing the structure in memory before `CheckInstallable` is reached and the transaction is finally rejected with `ErrNestedCompositeType`, as shown by the existing test at [7](#0-6) , confirming decode completes prior to rejection.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (serializer *TxInternalDataSerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.txType); err != nil {
		// fallback to the original transaction decoding.
		txd := newEmptyTxInternalDataLegacy()
		if err := s.Decode(txd); err != nil {
			return err
		}
		serializer.txType = TxTypeLegacyTransaction
		serializer.tx = txd
		return nil
	}

	if serializer.txType == EthereumTxTypeEnvelope {
		var ethType TxType
		if err := s.Decode(&ethType); err != nil {
			return err
		}
		serializer.txType = serializer.txType<<8 | ethType
	}

	var err error
	serializer.tx, err = NewTxInternalData(serializer.txType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.tx)
}
