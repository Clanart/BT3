## Title
Partial-selection commits apply stale line-based `DiffSelection` against a freshly re-fetched diff, allowing silent corruption of committed content - (File: `app/src/lib/git/apply.ts`)

### Summary
The Malt report shows a state-invalidation race: an admin-trusted operation (`populateFromPreviousThrottle`) writes derived state that is silently invalidated because a second function (`_fillInEpochGaps`) can run in between and mutate the same underlying counter (`activeEpoch`) using stale assumptions. The Desktop analog is the "partial file staging" flow: the UI computes a `DiffSelection` (line/range offsets) against one diff snapshot, but at commit time GitHub Desktop re-fetches a **new** diff from disk and applies the **old** offset-based selection to it in `applyPatchToIndex`. If the tracked file's on-disk content changes between the moment the user reviews/selects lines and the moment `createCommit` actually executes (which is unavoidable given the async gap in `_commitIncludedChanges`), the offsets no longer correspond to the lines the user approved, and the wrong hunks get staged and committed — without any re-validation against the diff the user actually saw.

### Finding Description
`_commitIncludedChanges` snapshots the current `workingDirectory.files` (including each file's `DiffSelection`, which is a set of selected line-offsets computed against the diff rendered earlier in the Changes view) and only afterwards performs asynchronous work (`formatCommitMessage`, hook execution) before finally invoking `createCommit`: [1](#0-0) 

`createCommit` calls `stageFiles`, which for files with a `Partial` selection calls `applyPatchToIndex`: [2](#0-1) [3](#0-2) 

`applyPatchToIndex` re-fetches the diff from disk **at apply time** — not the diff the user actually looked at — and then formats a patch from that fresh diff using the (now potentially stale) `file.selection` offsets: [4](#0-3) 

The broken invariant: the `DiffSelection` object is a set of line/hunk offsets meaningful only relative to the exact diff it was computed against (`updateChangesWorkingDirectoryDiff` explicitly acknowledges this fragility — "The diff might have changed dramatically since last we loaded it… we'll settle on just updating the selectable lines"): [5](#0-4) 

That code path only reconciles selection when the user is still browsing the diff in the UI; it does **not** run again right before `applyPatchToIndex` regenerates the diff during `stageFiles`/`createCommit`. So there is no guard preventing `applyPatchToIndex` from applying offsets that were valid for diff-version-A onto diff-version-B fetched fresh from disk.

An attacker who controls content inside a cloned/fetched repository (e.g. a build tool, `.gitattributes` smudge/clean filter, or another process the repo's tooling spawns) can modify a tracked file on disk in the small window between when the user makes a partial line selection in Desktop's diff viewer and when they click "Commit". Because `getWorkingDirectoryDiff` is called fresh inside `applyPatchToIndex` with no re-validation against the previously-displayed diff, the stale line offsets from the old selection get mapped onto different, attacker-shifted lines in the new diff, and `git apply --cached` stages whatever ends up at those offsets.

### Impact Explanation
This causes silent corruption of what the user commits: the Changes view still shows the diff/selection the user approved, but the actual staged/committed content can differ — potentially including attacker-injected lines the user never selected, or omitting lines the user intended to commit. Since this flows straight into `git commit` and can be pushed afterward, it can result in unreviewed/attacker-influenced code entering the user's commit history without any error or warning surfaced by Desktop.

### Likelihood Explanation
Exploitability depends on winning a race between the user's UI interaction (select lines → click Commit) and an attacker-controlled process modifying a tracked file on disk, which requires some means of running code in the context of the cloned repo (e.g., a build step, watch script, or filter driver bundled with the repository). This narrows the attack surface compared to a purely remote/passive vector, but it is squarely in-scope as "attacker controls a cloned/fetched repository" causing "silent corruption of what the user commits," and the timing window (typing a commit message, reviewing, clicking Commit) is often long enough in practice for a background process to win the race.

### Recommendation
Before calling `applyPatchToIndex`/`formatPatch`, re-fetch the diff for each partially-selected file and validate it is unchanged (e.g., compare diff/patch content hash or the underlying blob hash) versus what was originally shown when the selection was made; if it differs, fail the commit for that file (or re-derive selection safely) rather than silently applying stale offsets to new content. Alternatively, capture the exact diff content at selection time and reuse it (instead of re-fetching) when constructing the patch, so the same diff that produced the user's selection is the one that gets staged.

### Proof of Concept
1. In a tracked file with multiple hunks, open the Changes view and select only certain lines/hunks for commit (Partial `DiffSelection`).
2. Before clicking "Commit", have a concurrently-running process in the repository (e.g., a build/watch script, a `clean`/`smudge` filter triggered by another git operation, or any tool with write access to the working directory) modify the same file so that hunk boundaries shift (lines added/removed above the originally selected hunk).
3. Click "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff via `getWorkingDirectoryDiff` (now reflecting the modified file) and builds a patch using the stale line-offset `DiffSelection` from step 1. [6](#0-5) 
4. Inspect the resulting commit: it contains content at the previously-selected offsets, which now correspond to different lines than the ones the user reviewed and approved in the UI — despite Desktop never re-showing or re-confirming the changed diff.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
