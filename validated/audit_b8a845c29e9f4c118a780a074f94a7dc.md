Based on my investigation, I found a solid analog in the CR-CAT / Verified Credential (VC) system's `claim_pending_approval_balance` flow, which mirrors the OpenQ bug class: a party who controls an eligibility gate (KYC/proof requirement) can front-run a user's pending claim and revoke that eligibility, permanently blocking the claim and locking the user's already-owned funds.

### Title
DID provider can front-run and revoke a recipient's VC to permanently block `crcat_approve_pending`/`claim_pending_approval_balance`, locking already-owned CR-CAT funds - ([File: chia/wallet/vc_wallet/cr_cat_wallet.py])

### Summary
CR-CATs (Credential-Restricted CATs) sent to a wallet that does not already hold a valid VC (Verified Credential) land in a "pending approval" state [1](#0-0) . To move them into the spendable balance, the recipient must call `claim_pending_approval_balance` (exposed via the `crcat_approve_pending` RPC), which requires locating a currently valid VC issued by one of the CR-CAT's `authorized_providers` and using it (and its proofs) to authorize the spend [2](#0-1) . `get_vc_with_provider_in_and_proofs` only returns a VC if it currently has a matching, unrevoked proof root [3](#0-2) .

The DID that acts as the "authorized provider" retains a backdoor ("hidden puzzle") on every VC it issues, letting it revoke the VC at any time via `activate_backdoor`/`revoke_vc`, independent of the recipient's consent [4](#0-3) [5](#0-4) . This is structurally identical to the OpenQ bug: a privileged party (`BountyCore.setKycRequired`/issuer) can flip an eligibility condition to block a specific pending claim from a specific claimant.

### Finding Description
When a recipient submits their `claim_pending_approval_balance` spend bundle to the mempool to move CR-CATs out of the "pending approval" puzzle hash into their spendable balance, the transaction is public in the mempool before confirmation. The DID provider (who is watching for this exact spend, analogous to the issuer watching for a claim call in OpenQ) can construct and broadcast a higher-priority `revoke_vc` spend of the same VC coin, using `activate_backdoor` [6](#0-5) . Since the VC coin is a prerequisite input announced/asserted in the recipient's claim bundle, revoking it invalidates the claim, causing the claim spend to fail on-chain (its expected `AssertCoinAnnouncement`/spend of the now-different VC coin will not match) or simply removing the VC the recipient needed. The wallet code that selects a VC for the claim has no re-check for a race between "at select time" and "at confirmation time" [7](#0-6) .

Because the CR-CAT can only leave "pending approval" state with a valid, provider-issued VC proof, and the provider can revoke that VC at will, the provider has an on-chain lever to selectively block a specific recipient's claim right when they attempt it — exactly the "front-run and block claim" pattern from the OpenQ report, where `setKycRequired`/`setInvoiceRequired` block `_eligibleToClaimAtomicBounty`.

### Impact Explanation
If the CR-CAT's `authorized_providers` list is small (often just the issuer's own DID, as used throughout the test/mint helpers such as `mint_cr_cat`) [8](#0-7) , revocation of the recipient's only usable VC leaves them with CR-CAT funds permanently stuck in the "pending approval" puzzle hash — they own the coin but cannot produce a satisfying proof of inclusion, and cannot ever spend it out of the pending state (`construct_pending_approval_state`) without a valid VC from an authorized provider. This is a direct, wallet-user-reachable, high-impact loss-of-funds primitive: a trusted-but-adversarial credential issuer can weaponize the revocation backdoor specifically against a user who is actively trying to claim already-received CR-CAT payments.

### Likelihood Explanation
The recipient must broadcast their claim transaction (via `crcat_approve_pending`) before it confirms, making the provider's front-running window realistic (same as OpenQ's issuer front-running a claim call). No special privilege beyond DID ownership (the credential-issuing entity, which is by design semi-trusted but adversarial-capable per this class of bug) is required to execute the block.

### Recommendation
Consider decoupling "ability to revoke credentials going forward" from "ability to invalidate a specific already-in-flight claim spend." Options include: giving recipients a way to retry with an alternate authorized-provider VC atomically, adding a grace/finality window during which revocation cannot invalidate an already-broadcast pending-approval claim, or requiring revocation to be committed with a delay (similar to a timelock) so recipients have a fair opportunity to complete pending claims before revocation takes effect.

### Proof of Concept
1. Provider DID mints/authorizes a VC to recipient R; issuer's CR-CAT is sent to R while R has no existing valid VC, landing R's coin in `construct_pending_approval_state` [9](#0-8) .
2. R calls `crcat_approve_pending`/`claim_pending_approval_balance`, which selects R's VC and builds a claim bundle using `vc.wrap_inner_with_backdoor()` and the VC's current proof root, then broadcasts it [10](#0-9) .
3. Before R's bundle confirms, the provider observes it in the mempool and submits `revoke_vc`, spending R's VC coin via `activate_backdoor` with higher priority/fee [11](#0-10) [4](#0-3) .
4. R's claim bundle now references a spent/invalid VC coin and fails; R's CR-CAT remains in "pending approval" state. If the provider was the only authorized provider (or refuses to issue a fresh VC), R can never claim the funds — a permanent loss of already-owned assets, mirroring the OpenQ `setKycRequired` block-then-refund pattern (here, block-then-refuse-to-reissue).

    async def get_vc_with_provider_in_and_proofs(
        self, authorized_providers: list[bytes32], proofs: list[str]
    ) -> VerifiedCredential:
        vc_records: list[VCRecord] = await self.store.get_vc_records_by_providers(authorized_providers)
        if len(vc_records) == 0:  # pragma: no cover
            raise ValueError(f"VCWallet has no VCs with providers in the following list: {authorized_providers}")
        else:
            for rec in vc_records:
                if rec.vc.proof_hash is None:
                    continue  # pragma: no cover
                vc_proofs: VCProofs | None = await self.store.get_proofs_for_root(rec.vc.proof_hash)
                if vc_proofs is None:
                    continue  # pragma: no cover
                if all(proof in vc_proofs.key_value_pairs for proof in proofs):
                    return rec.vc
        raise ValueError(f"No authorized VC has the correct proofs: {proofs}")  # pragma: no cover

    def activate_backdoor(
        self, provider_innerpuzhash: bytes32, announcement_nonce: bytes32 | None = None
    ) -> tuple[CreatePuzzleAnnouncement, CoinSpend]:
        """
        Activates the backdoor in the VC to revoke the credentials and remove the provider's DID.

        Returns the announcement we expect from the provider's DID authorizing this, and the spend of the VC.
        Sync attempts by this class on spends generated by this method are expected to fail. This could be improved in
        the future with a separate type/state of VC that is revoked, but perfectly useful as a singleton.
        """
        vc_solution: Program = solution_for_singleton(
            self.singleton_lineage_proof,
            uint64(self.coin.amount),
            Program.to(
                [  # solve EML
                    solve_revocation_layer(
                        self.hidden_puzzle(),
                        solve_std_vc_backdoor(
                            self.launcher_id,
                            Program.to((self.proof_provider, self.proof_hash)).get_tree_hash(),
                            self.construct_transfer_program().get_tree_hash(),
                            self.inner_puzzle_hash,
                            uint64(self.coin.amount),
                            self.eml_lineage_proof,
                            provider_innerpuzhash,
                            self.coin.name(),
                            announcement_nonce,
                        ),
                        hidden=True,
                    ),
                ]
            ),
        )

        expected_announcement: CreatePuzzleAnnouncement = CreatePuzzleAnnouncement(
            std_hash(self.coin.name() + Program.NIL.get_tree_hash() + ACS_TRANSFER_PROGRAM.get_tree_hash())
        )

        return (
            expected_announcement,
            make_spend(self.coin, self.construct_puzzle(), vc_solution),
        )
