### Title
Governance-settable `kip71.gastarget` parameter can be set to zero, causing a division-by-zero panic in `KIP71Config.NextMagmaBlockBaseFee` and halting block validation/production - ([File: params/kip71_config.go])

### Summary
This is the same bug class as the reported AvailBridge issue: an admin/governance-controlled numeric parameter that feeds into a fee-calculation function is never validated against zero, and a zero value causes the dependent function to fail unconditionally (revert in AvailBridge's case, a runtime panic in Kaia's case). In Kaia, the `kip71.gastarget` governance parameter is used as a divisor inside `KIP71Config.NextMagmaBlockBaseFee`, and there is no format check preventing it from being set to `0`.

### Finding Description
`kip71.gastarget` is a mutable governance parameter (`Kip71GasTarget`) defined in [1](#0-0) , and it is registered in the `Params` map with `Canonicalizer: uint64Canonicalizer` — unlike `IstanbulCommitteeSize`, which explicitly enforces `v > 0`, the KIP-71 fields use `noopFormatChecker`, meaning any `uint64` value including `0` is accepted as valid: [2](#0-1) .

The parameter is consumed in `KIP71Config.NextMagmaBlockBaseFee`, which computes the next block's base fee using `gasTarget` as a divisor: [3](#0-2) 

When `parentGasUsed > gasTarget` (true for virtually any nonzero gas usage if `gasTarget == 0`), the code performs `x.Div(x, new(big.Int).SetUint64(gasTarget))`, i.e., division by zero on a `*big.Int`, which panics in Go's `math/big` package. Note that the code explicitly guards against `BaseFeeDenominator == 0` with a fallback (`baseFeeDenominator = 64`) at [4](#0-3) , but no equivalent guard exists for `gasTarget == 0`, confirming the omission is a gap rather than an intentional design choice.

This function is invoked from core, non-optional consensus and mempool paths reachable by ordinary block/transaction processing:
- Header validation: `blockchain/block_validator.go` (calls `VerifyMagmaHeader`/`NextMagmaBlockBaseFee`, confirmed by the mock test setup at [5](#0-4) ).
- Transaction pool gas price floor calculation: `blockchain/tx_pool.go`.
- Block production: `work/worker.go`.
- Gas price oracle / fee history RPC: `node/cn/gasprice/gasprice.go`, `node/cn/gasprice/feehistory.go`.

### Impact Explanation
If `kip71.gastarget` is ratified as `0` via governance voting (header governance `governance_vote`/ratification, or contract governance via KIP-81 GovParam contract), every node that processes a block with `gasUsed > 0` after the change takes effect will panic inside `NextMagmaBlockBaseFee` when validating the header, building the next block, or answering `eth_gasPrice`/`eth_feeHistory` RPC calls. Because this logic sits in the block validation and block-building path used by all consensus nodes, this is not merely "one transaction reverts" (as in the AvailBridge case) but a chain-wide denial of service: block production and/or block validation crashes for the entire network, and any wallet/dApp calling gas-price RPCs would also error out. This satisfies the requirement of "state divergence between honest nodes" / "acceptance of invalid transaction or block" risk, since some nodes may crash while in-flight while others may not yet have processed the update, and it is a Critical/High-severity DOS.

### Likelihood Explanation
Setting `kip71.gastarget` requires a governance vote to be ratified (via `governance_governancemode: single`, controlled by the `governingnode`, or via the permissionless GovParam contract post-Kore hard fork per KIP-81). This is the same privilege boundary as the original `updateFeePerByte` (an "admin" role), but is explicitly one of the allowed analog domains ("governance parameters") because governance actions are a first-class transaction path in Kaia (header votes are transactions/votes cast via `governance_vote` RPC, and contract governance uses standard on-chain transactions/voting by GC members) — i.e., it is reachable via a normal transaction-based mechanism rather than an out-of-band, off-chain administrative fix. No additional protocol-level validation currently prevents the mistake or malicious governance proposal from being ratified.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally also `Kip71MaxBlockGasUsedForBaseFee`) in `kaiax/gov/param.go` that rejects `0`, e.g.:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v > 0
    },
    ...
},
```
Additionally, add a defensive zero-check fallback inside `NextMagmaBlockBaseFee` in `params/kip71_config.go` (mirroring the existing `baseFeeDenominator == 0` fallback) so that even a value that slips past validation (e.g., pre-existing chain configs, or genesis misconfiguration) cannot cause a panic.

### Proof of Concept
1. Governing node (in `single` governance mode) casts `governance_vote("kip71.gastarget", 0)`.
2. At the next epoch boundary, this vote is ratified and takes effect starting the following epoch (per `kaiax/gov/headergov` semantics: [6](#0-5) ).
3. Once effective, on any block where `parentGasUsed > 0`, `NextMagmaBlockBaseFee` at [7](#0-6)  executes `x.Div(x, new(big.Int).SetUint64(0))`, which panics.
4. This function is called during header validation in `blockchain/block_validator.go`, block assembly in `work/worker.go`, and gas price suggestions in `node/cn/gasprice/gasprice.go`, causing block processing/production to crash across the network — a chain-wide denial of service, analogous to `AvailBridge::sendMessage` reverting unconditionally once `feePerByte` is set to `0`.
