### Title
Untrusted serialized outputs can duplicate UTXOs and induce an unspendable signed transaction - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`ReceivedOutput::read` accepts an offset, claimed `TxOut`, and claimed `OutPoint` without authenticating that the outpoint exists or is unspent. `SignableTransaction::new` then counts every supplied output and creates an input for each, without rejecting duplicate `previous_output` values. Because `multisig` only checks that each stored prevout script matches the corresponding offset key, duplicated serialized outputs pass validation and produce a consensus-invalid transaction referencing the same UTXO multiple times. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`ReceivedOutput::read` deserializes `offset`, `output`, and `outpoint` directly, but does not validate the claimed UTXO against the chain. `SignableTransaction::new` sums `input.output.value`, converts each `input.outpoint` into a `TxIn`, and stores each claimed `TxOut` as a prevout, with no uniqueness or authenticity check for the outpoints. [1](#0-0) [4](#0-3) [5](#0-4) 

`SignableTransaction::multisig` checks only that the script produced by `keys.offset(offset)` equals `prevouts[i].script_pubkey`; it does not check whether the referenced outpoint is real, unspent, or unique. [3](#0-2) 

### Impact Explanation
An attacker who can provide untrusted `ReceivedOutput` bytes can make a wallet treat the same spendable output as multiple inputs, inflating its apparent input total and causing the threshold signer to sign a transaction that Bitcoin nodes will reject as invalid. This is a medium-severity availability analog: funds are treated as spendable inputs, but the resulting signed transaction cannot spend them. [2](#0-1) [6](#0-5) 

### Likelihood Explanation
The attack is reachable whenever an unprivileged party can submit or corrupt serialized `ReceivedOutput` values consumed through the explicitly supported `ReceivedOutput::read` path. No malformed curve point, invalid signature, privileged validator, leaked key, or unsafe code is required; duplicating a valid serialized output is sufficient. [1](#0-0) 

### Recommendation
Reject duplicate `ReceivedOutput::outpoint` values in `SignableTransaction::new` and ensure callers only construct `ReceivedOutput` values from authenticated scanner or chain data. If serialized outputs cross an untrusted boundary, authenticate the serialized record and validate that every referenced outpoint exists, is unspent, has the claimed value, and has the expected script before signing. [2](#0-1) 

### Proof of Concept
```rust
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction};

let real: ReceivedOutput = scanner.scan_transaction(&tx).remove(0);
let bytes = real.serialize();

// Feed the same untrusted serialized output twice.
let first = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
let second = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();

let signable = SignableTransaction::new(
  vec![first, second],
  &[(payment_script, payment_amount)],
  None,
  None,
  fee_per_vbyte,
).unwrap();

// Both entries pass the script check because they contain the same TxOut.
let machine = signable.clone().multisig(&keys).unwrap();
```

`signable.transaction().input[0].previous_output` equals `input[1].previous_output`, while `prevouts` and the calculated input total contain the claimed value twice. The resulting signed transaction is therefore consensus-invalid and cannot spend the duplicated output. [2](#0-1) [5](#0-4)
