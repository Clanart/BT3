### Title
Uncontrolled recursion in `PuzzleWithRestrictions.from_memo()` allows a crafted coin memo to crash a syncing wallet - ([File: chia/wallet/puzzles/custody/custody_architecture.py])

### Summary
`PuzzleWithRestrictions.from_memo()` is a pure Python recursive-descent parser for the CHIP-0043 custody memo format. Like the SurrealDB kind/type parser, it recurses into nested `MofN` structures with no depth limit and no cost/size metering, unlike CLVM execution itself which is always bounded by `MAX_BLOCK_COST_CLVM`/`max_tx_clvm_cost`. This parser is reached from `PlotNFT.get_next_from_coin_spend()` when reconstructing a plotnft/custody puzzle from an on-chain coin's memo.

### Finding Description
`PuzzleWithRestrictions.from_memo()` reconstructs a `PuzzleWithRestrictions` tree from a `Program` memo. When the memo indicates "further branching" (an `MofN` node), it recurses once per member, and each member's memo can itself encode another `MofN`, with no bound on nesting depth: [1](#0-0) 

This is a direct Python `def from_memo(cls, memo): ... [PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]` recursive call with no depth counter, no `enter_object_recursion!`-style guard, and no size/cost accounting - the exact bug class described in the SurrealDB advisory (CWE-674, missing recursion-depth enforcement for a nested type/structure parser), just implemented in Python instead of Rust. A repo-wide search confirms there is no `sys.setrecursionlimit`, `RecursionError` handling, or explicit max-recursion guard anywhere in this parsing path.

The only production call site found is in `PlotNFT.get_next_from_coin_spend()`, which parses `singleton_create_coin.memo_blob.rest()` — the memo of a `CREATE_COIN` condition emitted by a spend — directly with `PuzzleWithRestrictions.from_memo()`: [2](#0-1) 

Memos on `CREATE_COIN` conditions are attacker-controlled arbitrary CLVM data chosen by whoever creates the spend; there is no consensus-level bound on memo nesting depth beyond overall CLVM cost limits (which bound total execution/atoms, not Python-side post-processing recursion depth). Because Python has a fixed C-stack-backed recursion limit, a sufficiently deep nested `MofN` memo (e.g., thousands of levels of `(m [member_memo...])` structures) will exhaust the Python call stack and raise `RecursionError`, or in CPython builds without stack-overflow protection, crash the process outright.

### Impact Explanation
If a full-node/wallet component syncing plotnft or custody state calls `PuzzleWithRestrictions.from_memo()` on a memo obtained from chain data without a depth/size cap, an attacker who can get a matching coin spend recorded (or otherwise get such a memo delivered to the parsing code) can trigger unbounded Python recursion, causing a crash or unhandled exception in the wallet process that halts its normal processing loop until restarted. This matches the general bug class in the report: an uncontrolled recursion depth in structural/type parsing leading to resource exhaustion / crash (CWE-674).

### Likelihood Explanation
Reachability is narrower here than in SurrealDB's RPC/HTTP surface. Based on the code paths found, `get_next_from_coin_spend()` is invoked while tracking a specific singleton lineage (a plotnft the wallet already owns/watches), and singleton spends normally require the owner's signature to advance the lineage. I could not fully verify, within the available context, whether any code path allows an attacker without control of the singleton's inner puzzle to inject an arbitrary memo that reaches `from_memo()` for a wallet it does not own (e.g., via a malicious spend of someone else's tracked singleton, or via another entry point that parses attacker-supplied memos independent of signature checks). This uncertainty could not be resolved with the tools available, so the exact blast radius (self-DoS of one's own client vs. cross-user DoS against arbitrary syncing wallets) is unconfirmed.

### Recommendation
- Add an explicit recursion-depth (or memo-size) limit inside `PuzzleWithRestrictions.from_memo()` and reject memos exceeding it, similar to the SurrealDB fix that wraps the recursive kind/type parsing functions with an `enter_object_recursion!`-style guard bound to a configured limit.
- Alternatively/additionally, convert `from_memo()` to an iterative parser (as already done for `sha256_treehash()` in `chia/types/blockchain_format/tree_hash.py`, which was deliberately made non-recursive to avoid exactly this class of Python stack-exhaustion issue) to avoid relying on Python's recursion limit as the only backstop.
- Audit all other call sites that parse untrusted `Program`/memo data recursively in Python (e.g., `PuzzleInfo.also()`/`check_type()` chains, driver `match_puzzle`/`get_inner_puzzle`/`get_inner_solution` recursive traversal in `chia/wallet/outer_puzzles.py` and related outer-puzzle drivers) for the same missing depth bound, since these follow the identical "recurse into nested driver/puzzle structure with no depth cap" pattern.

### Proof of Concept
Conceptual PoC (structure only, not fully verified end-to-end due to tool limitations):
1. Construct a `Program` memo of the form `("CHIP-0043", [nonce, [], 1, [1, [member_memo_1]]])` where `member_memo_1` is itself another such `MofN` memo, nested N times (N ≈ Python recursion limit, e.g. 2000-5000).
2. Deliver this memo as the memo of a `CREATE_COIN` condition on a coin spend that a target wallet's `PlotNFT.get_next_from_coin_spend()` will process (e.g., as part of the wallet's own plotnft lineage sync, or any other reachable call site parsing attacker-controlled memos with `PuzzleWithRestrictions.from_memo()`).
3. When the wallet calls `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())`, the recursive list comprehension `[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]` recurses N times, exhausting the Python call stack and raising `RecursionError` (or crashing the interpreter), halting the wallet's sync/processing loop.

Because I was unable to conclusively confirm an attacker-reachable path that lets an unprivileged party control the memo of a *victim's* tracked singleton (as opposed to only their own), I present this as a probable but not fully confirmed cross-user DoS; further verification against `chia/wallet/plotnft_wallet/plotnft_wallet.py` and `chia/wallet/wallet_state_manager.py` call sites would be needed to establish whether the memo reaching `from_memo()` can originate from a party other than the singleton's legitimate owner.

    def from_memo(cls, memo: Program) -> PuzzleWithRestrictions:
        if memo.atom is not None or memo.first() != Program.to(cls.spec_namespace):
            raise ValueError("Attempting to parse a memo that does not belong to this spec")
        nonce = memo.at("rf")
        restriction_hints_prog = memo.at("rrf")
        further_branching_prog = memo.at("rrrf")
        puzzle_hint_prog = memo.at("rrrrf")
        additional_memos = memo.at("rrrrrf") if memo.at("rrrrr").atom is None else None
        restriction_hints = [RestrictionHint.from_program(hint) for hint in restriction_hints_prog.as_iter()]
        further_branching = further_branching_prog != Program.to(None)
        if further_branching:
            m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
            puzzle: MIPSComponent = MofN(
                m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
            )
        else:
            puzzle_hint = MemberHint.from_program(puzzle_hint_prog)
            puzzle = UnknownMember(puzzle_hint)
