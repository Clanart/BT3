### Title
FROST signature shares are accepted without enforcing participant attribution - (File: crypto/frost/src/sign.rs)

### Summary

`AlgorithmSignatureMachine::complete` trusts the caller-supplied `HashMap<Participant, SignatureShare>` keys, sums the scalar shares, and returns a signature if the aggregate Schnorr verification succeeds. It only verifies each share against the claimed participant’s verification share after aggregate verification fails. Consequently, an observer can relabel valid shares among included participants—and potentially redistribute their difference—and still obtain a valid final signature, bypassing per-participant share authentication. Severity: Medium.

### Finding Description

`SignatureShare` is only a scalar and carries no cryptographic participant identity or authentication tag. [1](#0-0) 

`complete` first uses `validate_map` to check that the map contains every expected participant other than the local signer, but this validates only which keys are present, not whether a supplied scalar was produced by that participant. [2](#0-1) [3](#0-2) 

The implementation then inserts the local share, adds all supplied scalars into `sum`, and immediately returns if `algorithm.verify(group_key, &Rs, sum)` accepts the aggregate signature. [4](#0-3) 

The participant-specific check—calling `verify_share` with `view.verification_share(l)` and that participant’s bound nonce commitments—is reached only after aggregate verification fails. [5](#0-4) 

For the Schnorr algorithm, the aggregate verifier checks `sum` against the group key and combined nonce commitment. [6](#0-5)  The skipped per-share check instead verifies `s_i G = R_i + cY_i`, where `Y_i` is the claimed participant’s interpolated verification share. [7](#0-6) 

### Impact Explanation

An unprivileged party that observes two or more valid signature-share messages can submit them under different `Participant` keys. Because scalar addition is commutative, the aggregate response remains unchanged and the final signature verifies, even though the attributed shares no longer satisfy their claimed participants’ individual verification equations.

This does not let an attacker reduce the threshold or create a valid signature without enough valid shares. It does let them forge participation attribution, cause an implementation to accept a share under an identity that did not produce it, and evade the share-validation path responsible for assigning `InvalidShare(participant)` blame.

### Likelihood Explanation

The attack is deterministic whenever at least two remote signature shares are observable or relayable by the attacker. `read_share` accepts a bare canonical scalar, so no additional proof accompanies the network bytes. [8](#0-7)  The bypass is reachable through the public `complete` API using only attacker-controlled map labels and publicly observed share bytes. [9](#0-8) 

### Recommendation

Do not return the aggregate signature before checking participant attribution. Either:

- Always run `verify_share` for every `Participant` before accepting `sum`, even when aggregate verification succeeds; or
- Include authenticated participant-bound share messages, while still retaining per-share verification as the authoritative attribution check.

The fast-path aggregate check can remain as an additional integrity check, but it cannot replace per-participant verification because it intentionally validates only the sum.

### Proof of Concept

Consider a signing session with local participant `P0` and remote participants `P1` and `P2`. Let their valid shares be:

```text
s1 = r1 + c * λ1 * x1
s2 = r2 + c * λ2 * x2
```

The coordinator receives:

```text
{ P1: s1, P2: s2 }
```

An attacker who observes those scalar messages submits instead:

```text
{ P1: s2, P2: s1 }
```

`validate_map` succeeds because both expected participant keys are present. [2](#0-1)  The sum remains:

```text
s0 + s1 + s2
```

so aggregate Schnorr verification still succeeds and `complete` returns the final signature immediately. [4](#0-3)  However, `P1` is now credited with `s2`, which does not satisfy `s2 G = R1 + cY1`, and `P2` is credited with `s1`, which does not satisfy `s1 G = R2 + cY2`; those failures are never evaluated because the per-share fallback is skipped. [5](#0-4)

/// Validate a map of values to have the expected participants.
pub fn validate_map<T>(
  map: &HashMap<Participant, T>,
  included: &[Participant],
  ours: Participant,
) -> Result<(), FrostError> {
  if (map.len() + 1) != included.len() {
    Err(FrostError::InvalidParticipantQuantity(included.len(), map.len() + 1))?;
  }

  for included in included {
    if *included == ours {
      if map.contains_key(included) {
        Err(FrostError::DuplicatedParticipant(*included))?;
      }
      continue;
    }

    if !map.contains_key(included) {
      Err(FrostError::MissingParticipant(*included))?;
    }
  }

  Ok(())
