### Title
`ThresholdKeys::read` accepts identity/mismatched verification shares and never binds `secret_share` to `verification_shares[i]`, yielding a deserialized group key with attacker-known discrete log - (File: crypto/dkg/src/lib.rs)

### Summary
CVE-2026-2785 is an invalid-pointer/type-confusion bug: untrusted input materializes an object in a state the engine never intended. The direct analog in Serai is a deserialization routine that materializes a *cryptographic object* in an invalid state which downstream code fully trusts. `ThresholdKeys::read` reconstructs a threshold key from raw bytes and delegates validation to `ThresholdKeys::new`, which validates only structural parameters (`t <= n`, indexes in range, interpolation applicability). It never verifies that `secret_share * G == verification_shares[i]`, and it accepts the identity point for verification shares because it uses `Ciphersuite::read_G`, not the identity-rejecting `Curve::read_G`.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i`, the interpolation mode, `secret_share` (via `C::read_F`), and `n` verification shares via `<C as Ciphersuite>::read_G` at crypto/dkg/src/lib.rs:620-623, then calls `ThresholdKeys::new` at lines 625-631. `ThresholdKeys::new` (lines 349-391) checks `verification_shares.len() == n`, participant indexes `<= n`, and interpolation applicability — nothing else. Critically, at lines 376-378 it computes the group key as:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

The group key is wholly derived from the untrusted verification shares. `Ciphersuite::read_G` (crypto/ciphersuite/src/lib.rs:91-101) only enforces a canonical encoding — it does not reject the identity. Only `Curve::read_G` (crypto/frost/src/curve/mod.rs:125-131) rejects identity, and it is not used here. Nor is there any check that the deserialized `secret_share` is consistent with `verification_shares[i]` (`generator() * secret_share == verification_shares[i]`), the invariant every honest DKG output maintains and every downstream consumer assumes.

### Impact Explanation
An attacker who feeds crafted bytes to `ThresholdKeys::read` obtains a fully "valid" `ThresholdKeys` whose group key the attacker controls:

- Set all verification shares to `x_j * G` for attacker-chosen scalars `x_j`. The interpolated `group_key` then has discrete log `sum(x_j * lambda_j)`, known to the attacker. Equivalently, set shares to identity (DL = 0), producing `group_key == identity` — a "key" whose secret is trivially 0.
- Choose `secret_share` arbitrarily (or consistently with the fake `verification_shares[i]`). Since nothing binds share to share-commitment, the object passes every internal invariant.

Any subsequent signature "verification" or signing under this `ThresholdKeys` happens under a group key whose discrete logarithm is public knowledge. The attacker can forge `s = r + c * dlog(group_key)` Schnorr signatures indistinguishable from threshold output, and any funds/outputs associated with `group_key()` are spendable by the attacker alone. This is concrete key-share/group-key compromise and signature forgery — not a panic or DoS — reachable purely through untrusted bytes to a whitelisted `read` API.

### Likelihood Explanation
Exploitation requires getting crafted `ThresholdKeys` bytes into a `read` call — e.g., key-material import, backup/seed restore, DB contents an attacker can influence, or any protocol path deserializing keys from peer-supplied data (the scan rules themselves whitelist `ThresholdKeys::read` as an untrusted-input sink). There is no integrity/MAC check on the serialization (`write`/`read` are a plain byte format), so a single flipped or wholly crafted blob silently produces attacker-controlled keys rather than being rejected. Once loaded, all downstream validation (`view()`, `group_key()`, FROST signing) treats the object as authoritative, so exploitation needs no further interaction.

### Recommendation
- In `ThresholdKeys::new` (and therefore `read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise.
- Deserialize verification shares with the identity-rejecting `Curve::read_G` (or explicitly check `is_identity()` on each share), and reject an identity/otherwise-invalid derived `group_key`.
- Optionally verify the shares' internal consistency (e.g., that they lie on a `t-1` degree polynomial, or at minimum recompute and sanity-check the interpolated group key against any independently authenticated key).

### Proof of Concept
```rust
use ciphersuite::Ciphersuite;
use frost::{curve::Secp256k1, ThresholdKeys};

// Crafted blob for t = n = 1, i = 1, Lagrange interpolation.
let mut bytes = vec![];
bytes.extend((Secp256k1::ID.len() as u32).to_le_bytes());
bytes.extend(Secp256k1::ID);
bytes.extend(1u16.to_le_bytes()); // t
bytes.extend(1u16.to_le_bytes()); // n
bytes.extend(1u16.to_le_bytes()); // i
bytes.push(1);                    // Lagrange
// secret_share: attacker-chosen scalar s
bytes.extend(attacker_scalar.to_repr().as_ref());
// verification_shares[1]: attacker-chosen point x*G (or identity encoding)
bytes.extend(attacker_point.to_bytes().as_ref());

let keys = ThresholdKeys::<Secp256k1>::read(&mut bytes.as_slice()).unwrap();
// keys.group_key() == attacker_point; its discrete log (x) is known to the
// attacker, who can now forge signatures accepted under this "threshold" key.
// No check ever confirmed generator() * secret_share == verification_shares[1].
```

Note on reachability: this finding is conditional on `ThresholdKeys::read` actually consuming attacker-influenced bytes in deployment; the routine itself performs no integrity or consistency validation, so that question reduces to how the key blob is stored/transported, which is outside the in-scope crates' guarantees.
