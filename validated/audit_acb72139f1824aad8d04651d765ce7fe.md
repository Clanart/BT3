### Title
`SignableTransaction` fee calculation omits the OP_RETURN data output, producing transactions below the requested (and possibly minimum-relay) fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the Biconomy report's divergence between `providedLiquidity` (accounted value) and `currentLiquidity` (actual value), `SignableTransaction::new` computes the transaction weight and `needed_fee` from `payments` alone, while the actual transaction may additionally carry a caller-controlled OP_RETURN output (up to 80 bytes of data). The recorded fee budget therefore diverges from the real serialized weight, so the signed transaction pays an effective fee rate lower than `fee_per_vbyte` — and can even fall below the relay minimum that was checked against the underestimated vsize. The result is a transaction that is never relayed/confirmed while its inputs are consumed from the wallet's perspective, leaving funds stuck.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` before the weight is computed, but `calculate_weight_vbytes` is invoked with `payments` — the OP_RETURN output is never represented in the weight:

```rust
// send.rs:194-204 — OP_RETURN pushed to tx_outs, then weight computed from `payments` only
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
``` [1](#0-0) 

`calculate_weight_vbytes` builds the measurement transaction solely from `payments` plus an optional change output; there is no parameter for the data output, so it is structurally impossible for the OP_RETURN bytes to be counted: [2](#0-1) 

The change branch has the same defect — `fee_with_change` is also derived from a weight that excludes the data output: [3](#0-2) 

Consequences:
- `needed_fee` and the `TooLowFee` minimum-relay check (line 211) are evaluated against a vsize that omits up to ~90+ bytes (8-byte amount + script length + OP_RETURN push of up to 80 bytes). The actual fee rate is `needed_fee / real_vsize < fee_per_vbyte`.
- With `fee_per_vbyte` at/near the minimum relay rate, adding the unaccounted OP_RETURN pushes the real rate below `DEFAULT_MIN_RELAY_TX_FEE`, so nodes reject the transaction — mirroring the report's "redeem reverts / funds unavailable" deficit: the wallet constructed a spend it cannot actually execute.

### Impact Explanation
An unprivileged party who can influence the `data` payload of a transaction built by this wallet (e.g., a protocol embedding attacker-influenced memo/instruction bytes via the `data` parameter) can force construction of transactions whose effective fee rate is arbitrarily below the intended rate — up to ~90 uncharged vbytes per transaction. At low fee rates this produces transactions that fail relay or languish unconfirmed indefinitely, while the inputs are committed to that exact txid/sighash (`Prevouts::All` commits every input, line 375), i.e., the spent outputs are locked to a non-propagating transaction. This is a denial-of-service on withdrawals, the direct analog of LPs being unable to redeem shares in the deficit state.

### Likelihood Explanation
The divergence triggers whenever `data.is_some()` — a deterministic code path, not an edge case. Severity is bounded because (a) `data` is capped at 80 bytes, bounding the undercharge to roughly 90 vbytes, and (b) at high `fee_per_vbyte` values the transaction still confirms, just at a lower effective rate. The critical case — falling under `DEFAULT_MIN_RELAY_TX_FEE` — requires a low requested fee rate and a sizable data payload. Like the judged Medium report, the deficit is real and reachable via public inputs, but requires specific conditions to fully strand funds.

### Recommendation
Include the OP_RETURN output in the weight calculation: pass the fully-built `tx_outs` (or an explicit `data: Option<&[u8]>` parameter) into `calculate_weight_vbytes` for both the no-change and with-change computations so that `needed_fee`, the `TooLowFee` check, and the change-vs-dust decision all reflect the true serialized size. Alternatively, compute the fee after `tx_outs` is finalized by measuring `tx.weight()` on the actual transaction.

### Proof of Concept
Conceptual trace in `networks/bitcoin/src/wallet/send.rs`:

1. Call `SignableTransaction::new(inputs, &payments, Some(change), Some(vec![0u8; 80]), fee_per_vbyte)` where `fee_per_vbyte` equals the minimum relay rate (1 sat/vbyte equivalent).
2. Line 195 pushes a `TxOut` with `script_pubkey = OP_RETURN <80 bytes>` (~91 serialized bytes, ~91 vbytes) onto `tx_outs`.
3. Line 204 computes `vbytes` from a measurement transaction built only from `payments` — the OP_RETURN output contributes 0.
4. Line 211 passes the `TooLowFee` check because `needed_fee >= min_fee * underestimated_vbytes`.
5. Line 228 computes `fee_with_change` against `vbytes_with_change` which likewise excludes the data output; change may be created as `input_sat - payment_sat - fee_with_change`, which is *larger* than the economically-correct change, further underpaying the true required fee.
6. The returned `SignableTransaction` has `fee() == needed_fee` spread over a real vsize ~91 bytes larger: actual rate ≈ `needed_fee / (vbytes + 91) < 1 sat/vbyte` → rejected by `sendrawtransaction` (`mempool min fee not met`), leaving the wallet's inputs bound to a tx that cannot propagate — the spend-side equivalent of LP redemption reverting in the deficit state.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
