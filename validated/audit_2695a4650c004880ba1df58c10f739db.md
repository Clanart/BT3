### Title
Missing `pool.mu` lock in `TxPool.reset()` causes concurrent map/pointer corruption of the pending transaction pool - ([File: blockchain/tx_pool.go])

### Summary
`TxPool.reset()` is invoked on every new chain head (from the pool's internal event loop) to reconcile `pool.pending` / `pool.queue` / `pool.all` with the new state and to reinject reorged transactions. The lock that is supposed to serialize this mutation against concurrently-running public entry points (`AddLocal`, `AddRemotes`, `Pending`, `Get`, RPC-triggered tx submission, etc.) has been commented out: [1](#0-0) 

```go
// pool.mu.Lock()
// defer pool.mu.Unlock()

pool.addTxsLocked(reinject, false)

// validate the pool of pending transactions, this will remove
// any transactions that have been included in the block or
// have been invalidated because of another transaction (e.g.
// higher gas price)
pool.demoteUnexecutables()
```

`addTxsLocked` and `demoteUnexecutables` mutate the shared `pool.pending`/`pool.queue`/`pool.all` maps and per-account `txList`/`txSortedMap` structures under the explicit assumption that `pool.mu` is held (the same pattern documented for `enqueueTx`: "Note, this method assumes the pool lock is held!"). [2](#0-1) 

With the lock removed, `reset()` runs concurrently with any other public path that also takes `pool.mu` (e.g. `Pending()`, `CachedPendingTxsByCount()`, `AddLocal`, `AddRemotes`) or, worse, concurrently with code that assumes exclusive ownership while it isn't held at all.

### Finding Description
This is the same bug class as the Linux kernel CVE: a data structure (there, the VLAN list under RCU/spinlock; here, the tx-pool's per-account nonce-sorted maps/lists and lookup index) is walked and mutated from one context assuming a lock is held, while the lock has been dropped, and another context can concurrently mutate/free the same structure. In `tx_pool.go`, `reset()` is called from the pool's background loop on every `ChainHeadEvent`, i.e. once per block, without holding `pool.mu`. During that time window, an unprivileged transaction sender calling `AddLocal`/`AddRemotes` (reachable via public RPC `eth_sendRawTransaction`/`eth_sendTransaction`) can concurrently execute `pool.add()` → `enqueueTx()` → mutate `pool.queue[from]`, `pool.all`, `pool.priced` — the exact same maps that `addTxsLocked`/`demoteUnexecutables` are mutating inside `reset()` without a lock.

Concurrent, unsynchronized writes to Go maps (`pool.pending`, `pool.queue`, `pool.all.txs`) and to the linked heap/slice-backed `txSortedMap`/`nonceHeap` structures (e.g. `Forward`, `Put`, `Flatten` cache field) produce undefined behavior: stale/aliased slice backing arrays, cache pointers reused after being logically invalidated, or corrupted map internals. This mirrors the kernel bug where a VLAN entry could be freed by one path while still referenced (via a stale pointer) by another concurrently-running path holding no proper lock. [3](#0-2) 

### Impact Explanation
Because `reset()` runs on every block and normal user traffic (transaction submission via RPC) is completely unprivileged and unthrottled with respect to this race, an attacker only needs to submit ordinary transactions at the moment blocks are produced to trigger the race window. Corruption of the pending-pool bookkeeping can:
- Cause a transaction that should have been rejected (e.g., duplicate nonce, insufficient price bump) to be admitted into `pending`/`priced`/`all` due to a torn/corrupted map state, i.e. acceptance of a transaction that should be invalid under the pool's own admission rules.
- Cause divergent pool states between honest nodes that observe the race differently (timing-dependent), leading to different sets of transactions being proposed/broadcast/mined by different nodes and inconsistent block-building behavior.
- Corrupt the nonce-tracking (`pendingNonce`, `txSortedMap.cache`) used to determine which txs are "next executable," which can be leveraged to get a replacement/duplicate transaction processed out of the intended price-bump/nonce ordering, i.e., fee/ordering-priority abuse.

This satisfies the "state divergence between honest nodes" / "acceptance of an invalid transaction" bar required by the validation rules.

### Likelihood Explanation
High reachability, requires no privilege: any account submitting transactions through the standard public transaction submission path (`TxPool.AddLocal`/`AddRemotes`, reachable from RPC) races against the pool's own head-processing loop that calls `reset()` on every new block — a naturally frequent, attacker-uninfluenced trigger. The missing lock is unconditional (not behind a feature flag or rare code path), so the race window exists on every block for the lifetime of the node.

### Recommendation
Restore the `pool.mu.Lock()`/`defer pool.mu.Unlock()` around the section of `reset()` that calls `addTxsLocked` and `demoteUnexecutables` (and any other mutation of `pool.pending`/`pool.queue`/`pool.all` inside `reset`), consistent with the locking contract documented on `enqueueTx`/`addTxsLocked`. Audit all callers of `reset()` (direct and via `lockedReset`) to make sure the lock is acquired exactly once per call path (no double-locking, no missing locking), and add a `-race` test that concurrently drives `AddLocal`/`AddRemotes` against block-triggered `reset()` calls to catch regressions (similar in spirit to the existing `tests/race_test.go` and `tests/resend_nil_test.go`). [4](#0-3) 

### Proof of Concept
1. Start a node with the tx pool running its normal event loop (block processing triggers `pool.reset(oldHead, newHead)` on each `ChainHeadEvent`).
2. From an external, unprivileged client, continuously submit transactions via the public RPC (`eth_sendRawTransaction`) at high rate for several accounts, targeting the moments right after new blocks are produced (to overlap with `reset()`'s unlocked mutation window).
3. Run the node under `go test -race` (or instrument `tx_pool.go` with `-race` in production-like load, analogous to `tests/race_test.go`'s `TestRaceBetweenTxpoolAddAndCommitNewWork`) to observe concurrent map read/write or map write/write races on `pool.pending`, `pool.queue`, and `pool.all.txs` between `reset()`'s `addTxsLocked`/`demoteUnexecutables` call and `AddLocal`/`AddRemotes`'s `pool.add()`/`enqueueTx()`.
4. Observe either a Go runtime `fatal error: concurrent map writes` crash, or (without `-race`, under sustained load) inconsistent pending-pool state — e.g., a transaction admitted despite violating the price-bump/duplicate-nonce rule enforced by `list.Add`/`enqueueTx` — demonstrating divergent/incorrect pool state directly caused by the missing lock in `reset()`. [5](#0-4)
