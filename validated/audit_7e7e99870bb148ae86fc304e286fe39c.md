## Analysis Summary

The external report describes RCE caused by URL/argument-injection flaws in Git/SVN/Mercurial transport handling (`ssh://` and similar URLs being passed unsafely to helper processes). Desktop's own `parseRemote`/`sanitizeCloneName` in [1](#0-0)  and the `isClonePathSensitive` path guard in [2](#0-1)  show the app has already been hardened against the "malicious URL/name" class of attack. However, while investigating `clone.ts` I found a more direct, Desktop-specific analog: the clone path explicitly disables a Git-native anti-RCE mitigation.

### Title
Disabled Git clone-recursion protection re-opens hook-injection RCE during recursive clone (`GIT_CLONE_PROTECTION_ACTIVE=false`) - (File: app/src/lib/git/clone.ts)

### Summary
Desktop's `clone()` function unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment used to invoke `git -c init.defaultBranch=... clone --recursive -- <url> <path>`. [3](#0-2) 

### Finding Description
`GIT_CLONE_PROTECTION_ACTIVE` is Git's own internal recursion guard, introduced as part of the fix line for the class of `git clone --recursive` hook-execution vulnerabilities (the same "attacker controls a cloned repository → arbitrary code execution during clone/checkout" bug class that the reported ssh/hg/svn URL RCEs belong to). Git sets this variable itself to `true` when a top-level `clone --recursive` recurses into submodule clones, and uses its presence/value to detect and reject dangerous situations such as case-confusable or symlinked `.git`/`.gitmodules` paths that would let a malicious submodule plant executable hooks (e.g. `post-checkout`) that Git then invokes as part of the same recursive clone. This is precisely the mechanism that stops a hostile repository from executing code the moment a user clones it with submodules.

By explicitly setting this variable to `'false'` before invoking `git clone --recursive`, Desktop disables that internal protection for every single clone operation, regardless of whether the URL is trusted. This is not a case of an attacker crafting a URL to smuggle arguments (the invariant the ssh:// CVEs broke) — it's Desktop actively turning off Git's own hardening for the equivalent hook-execution primitive during recursive submodule cloning. None of the other local mitigations checked (`isClonePathSensitive`, `sanitizeCloneName`, `parseRemote`) address this: they guard against destination-path traversal and malformed remote names, not against malicious submodule content triggering hook execution during `--recursive` clone. [4](#0-3) 

I could not find any comment, test, or surrounding code in this repository explaining a legitimate reason for disabling this specific protection (no reference to `GIT_CLONE_PROTECTION_ACTIVE` elsewhere in the codebase), and no compensating control (e.g., `protocol.file.allow`, hook-path override, or symlink checks) covers the same window. [5](#0-4)  additionally shows Desktop always runs `submodule update --init --recursive` after checkout/pull with no protocol allowlist beyond the optional `protocol.file.allow=always`, reinforcing that submodule content is trusted more than it should be. `GIT_CLONE_PROTECTION_ACTIVE` was found only in `clone.ts`; I was not able to verify against the bundled `dugite`/git binary version whether the underlying Git release still honors or requires this variable, since that is outside the indexed source.

### Impact Explanation
If Git's recursion guard is meaningful for the bundled Git version, disabling it means: an attacker who gets a victim to clone their repository (a normal, low-friction, and fully expected Desktop action — "Clone repository" from a URL, GitHub search result, or deep link) with the default `--recursive` flag could plant a malicious submodule (crafted `.gitmodules`, symlinked or case-confusable `.git` directory) whose hook is executed by Git during the clone itself, before the user has any chance to review the repository. That is an unprivileged, remote-triggered RCE — squarely inside the report's valid-impact class ("attacker controls a cloned/fetched repository ... result is code execution").

### Likelihood Explanation
Cloning is one of the most common actions in Desktop, and `clone()` always passes `--recursive` — the environment variable is set unconditionally for every clone, not behind any advanced/opt-in setting. [6](#0-5)  No user interaction beyond "clone this URL" is required, which matches valid-impact criteria (no local access, no admin, no pre-existing malware).

### Recommendation
Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override from the `clone()` environment (or set it to `'true'`/leave it unset so Git's own default/internal logic governs it), and audit whether it was added to work around a benign warning/error — if so, address that root cause instead of disabling the safety check for all clones.

### Proof of Concept
1. Attacker publishes a repository containing a `.gitmodules` referencing a submodule whose on-disk path collides case-insensitively (or via symlink) with `.git`, paired with a hook script (e.g. `post-checkout`) that runs a payload — the same construction used in the Git recursive-clone hook-execution vulnerability class.
2. Victim opens Desktop → "Clone Repository" → pastes the attacker's URL.
3. Desktop calls `clone(url, path, options)`, which runs `git ... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` in the environment. [7](#0-6) 
4. Because Desktop has disabled Git's internal recursion-safety check, Git proceeds to check out and execute the planted hook during the recursive submodule clone, achieving code execution on the victim's machine without further user interaction.

Note: I could not execute this PoC against the actual bundled Git binary to confirm exploitability end-to-end (that requires a live environment/terminal, which is outside my current read-only capability) — the finding is based on static analysis of the explicit, unexplained disabling of a named Git anti-RCE environment variable in the clone path.

/** Parse the remote information from URL. */
export function parseRemote(url: string): IGitRemoteURL | null {
  for (const { protocol, regex } of remoteRegexes) {
    const match = regex.exec(url)
    if (match !== null && match.length >= 4) {
      return { protocol, hostname: match[1], owner: match[2], name: match[3] }
    }
  }

  return null
}

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
