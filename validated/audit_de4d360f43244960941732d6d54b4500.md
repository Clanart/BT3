## Finding [1](#0-0) 

The `pallet-hyper-fungible-token` has the same bug class as the external report: a legitimate administrative action ("manager" in the report, `CreateOrigin` here) removes a token's chain mapping while user funds dispatched under the old mapping are still in-flight, permanently blocking their refund path. There is no check that all outstanding cross-chain sends for the removed `(chain, asset_id)` pair have already been delivered or timed out.

### Title
Removing/re-mapping a token's chain configuration via `update_token` permanently locks escrowed/burned funds of in-flight sends - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
`update_token` lets `CreateOrigin` remove (`remove_chains`) or re-point (`add_chains`) a `(StateMachine, AssetId)` mapping by deleting `TokenContracts`, `ContractToAsset`, and `Precisions` entries. Any `send()` that was dispatched to that chain *before* the update, and later times out, cannot be refunded: `on_timeout` looks up `ContractToAsset::<T>::get(dest, &to)` and `Precisions::<T>::get(...)`, both of which now return `None`, causing the timeout handler to error out instead of releasing escrowed native tokens or re-minting burned assets to the original sender.

### Finding Description
`send()` escrows (native asset) or burns (non-native asset) a user's funds and dispatches a `PostRequest` whose `to` field is the token contract address recorded in `TokenContracts` at dispatch time [2](#0-1) . If this request later times out, `on_timeout` is invoked to refund the sender, but it must first resolve `local_asset_id` via `ContractToAsset::<T>::get(dest, &to)` [3](#0-2)  and the decimal precision via `Precisions::<T>::get(local_asset_id.clone(), dest)` [4](#0-3) .

`update_token`'s `remove_chains` branch deletes exactly these two storage entries (plus `TokenContracts`) for the given chain/asset with no check for outstanding requests: [1](#0-0) . The `add_chains` branch has the same effect on the old contract mapping, since it removes the previous `ContractToAsset` entry before inserting the new one: [5](#0-4) .

Once these entries are gone, `on_timeout` unconditionally fails with `HftError::UnknownContractOnTimeout` / `HftError::DecimalsNotConfigured` for every pending send that was dispatched under the old mapping, so the ISMP timeout dispatch never completes successfully and the escrowed/burned funds are never returned to the sender. This mirrors the reported bug pattern exactly: a privileged party changes an address/contract binding before all funds tied to the old binding have finished settling, and there is no invariant check preventing it — the report recommended checking that funds are "distributed or closed" before allowing the address change; this pallet has no analogous check before mutating `TokenContracts`/`ContractToAsset`/`Precisions`.

### Impact Explanation
Ordinary users who called `send()` in good faith have their tokens escrowed/burned. If the chain/asset mapping is updated or removed for any operational reason (deprecating a chain, migrating a contract, fixing a misconfiguration) while their request is still outstanding, the refund path for that specific pending request is permanently broken. This is a direct loss of user funds (locked with no recovery mechanism), a fund-loss class explicitly in scope of the bounty (loss/lock of funds via a broken settlement/refund invariant).

### Likelihood Explanation
This requires only an ordinary operational `update_token` call (a routine, non-malicious governance action expected to happen over the pallet's lifetime, e.g. rotating a compromised EVM contract or deprecating chain support) occurring while any user send to that chain is still in flight — a common and easily-hit timing window given real-world timeouts are minutes-to-hours. No proof forgery, malicious relayer, or compromised key is needed for the funds to become unrecoverable; the affected party is simply any unprivileged user whose in-flight transfer happens to straddle the update.

### Recommendation
Before removing/re-pointing a `(chain, asset_id)` mapping in `update_token`, keep the old `ContractToAsset`/`Precisions` entries alive (e.g. in a secondary "retired mapping" store) until all outstanding requests dispatched under the old contract address have either been delivered or timed out, or make `on_timeout` resolve the asset from the historical mapping recorded on the request/commitment itself rather than from the live, mutable `ContractToAsset`/`Precisions` maps.

### Proof of Concept
1. `register_token`/`update_token` sets `TokenContracts[Evm(1)][AssetX] = ContractA`, `ContractToAsset[Evm(1)][ContractA] = AssetX`, `Precisions[AssetX][Evm(1)] = 18`.
2. User calls `send()` with `destination = Evm(1)`, `asset_id = AssetX`, escrowing/burning `amount`; a `PostRequest` is dispatched with `to = ContractA`, `timeout = T`.
3. Before the request is delivered or times out, `CreateOrigin` calls `update_token` with `remove_chains = [Evm(1)]` (e.g. deprecating that chain) — this deletes `TokenContracts`, `ContractToAsset[Evm(1)][ContractA]`, and `Precisions[AssetX][Evm(1)]`.
4. The dispatched request never gets delivered and eventually times out; `pallet-ismp` invokes `on_timeout` on the pallet with the original `PostRequest` (`to = ContractA`, `dest = Evm(1)`).
5. `on_timeout` executes `ContractToAsset::<T>::get(Evm(1), ContractA)` which now returns `None`, so it returns `Err(HftError::UnknownContractOnTimeout)`. The refund never happens and the user's escrowed/burned funds remain stuck in the pallet account permanently.
