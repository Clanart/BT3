### Title
Divide-by-zero on attacker-crafted mempool item during legacy block generation - (File: chia/full_node/mempool.py)

### Summary
`Mempool.create_bundle_from_mempool_items()` (the legacy block-building path used by `create_block_generator()` when `full_node.config["block_creation"] = 0`) computes `item_cost = cost - cost_saving` for every mempool item it considers, then unconditionally divides `fee / item_cost` inside a logging call, with no guard against `item_cost` being zero. This mirrors the CVE-2023-46849 bug class: an unvalidated integer used as a divisor in a reachable code path causes an unhandled `ZeroDivisionError`, crashing transaction/block processing.

### Finding Description
In the legacy bundle-creation path: [1](#0-0) 

`cost = item.conds.cost` is the total CLVM cost recorded for the whole mempool item at admission time, and `cost_saving` is the sum of `DedupCoinSpend.cost` values accumulated by `IdenticalSpendDedup.get_deduplication_info()` for every coin spend in the item that is `eligible_for_dedup` and matches a solution already committed by a previously processed, higher-fee-rate item: [2](#0-1) 

`item_cost = cost - cost_saving` is not checked against zero anywhere before being used as a divisor at `fee / item_cost` inside the `log.info(...)` call. Because `log.info("%0.4f", ..., fee / item_cost, ...)` evaluates the division eagerly as a Python expression (it is not lazy `%`-formatting deferred to the logging module — the division itself happens in the caller before `log.info` is invoked), if `item_cost` equals `0` this raises an unhandled `ZeroDivisionError` in the full node's block-building code path.

`item_cost` can reach `0` when a mempool item is admitted with a positive `cost` (`cost == 0` is already rejected at admission per `MempoolManager.validate_spend_bundle` — [3](#0-2) ), but every one of its coin spends is `eligible_for_dedup` and coincides in solution with a spend already deduplicated against by an earlier, higher-fee item, so that the accumulated `cost_saving` equals the item's full recorded `cost`. An unprivileged submitter can construct such a scenario by submitting one spend bundle with a normal, unique fee, and a second spend bundle that spends the exact same dedup-eligible coin(s) with the identical solution but a lower fee (or is otherwise ordered after it by `fee_per_cost`), so that when the block builder walks mempool items in fee order, the later item’s entire cost is “saved” via dedup, producing `item_cost == 0`.

The identical `item_cost` value is also propagated to `new_cost_sum = cost_sum + item_cost` and further block-building logic, so even if the immediate `ZeroDivisionError` were avoided by disabling logging, the zero-cost item still corrupts block cost accounting downstream.

### Impact Explanation
This is a spend-triggered denial-of-service against full node block production: any full node farming with the legacy (`block_creation = 0`) generator path that attempts to build a block containing such crafted mempool items hits an unhandled `ZeroDivisionError`, halting the block-assembly call. Depending on how the caller handles exceptions from `create_block_generator`, this can prevent block templates/blocks from being produced, denying farming for affected nodes — a transaction-processing halt caused by a single submitted spend bundle, matching the required impact class (spend-triggered halt).

### Likelihood Explanation
The trigger requires only two ordinary, mempool-admissible spend bundles from an unprivileged submitter: no privileged access, no malicious peer/node behavior, and no protocol-level exploit is needed — only crafting coin spends that are `eligible_for_dedup` (canonical CLVM serialization, identical solution) and controlling relative fees so the block builder walks the higher-fee item first and captures its full cost as `cost_saving` for the second. However, exploitability is scoped to the legacy `create_bundle_from_mempool_items`/`create_block_generator` path (`block_creation = 0`); the current default farming path is `create_block_generator2`, whose analogous cost computation was not confirmed to contain the same eager division (the equivalent block in `create_block_generator2` at `chia/full_node/mempool.py:809-898` did not show the same log-based division in the reviewed excerpt). This uncertainty about default-path reachability lowers confidence and should be verified directly against `create_block_generator2` and any nodes/operators still configured for the legacy path.

### Recommendation
- Guard against `item_cost <= 0` in `create_bundle_from_mempool_items()` before performing `fee / item_cost`, either by skipping/logging such items without division or by asserting invariants at dedup-savings computation time (`cost_saving < cost`).
- Cap `cost_saving` in `IdenticalSpendDedup.get_deduplication_info()` so it can never reach or exceed the item's own recorded `cost`.
- Audit `create_block_generator2` (the default path) for equivalent unguarded divisions using cost/fee values derived from dedup or fast-forward savings.
- Add a regression test with two admissible spend bundles sharing an identical dedup-eligible coin spend, ordered so the second item's `cost_saving` equals its `cost`, to confirm the fix prevents the `ZeroDivisionError`.

### Proof of Concept
1. Submit spend bundle A with a dedup-eligible coin spend (canonical serialization) and a high fee.
2. Submit spend bundle B that spends a coin with the exact same puzzle/solution pair as in A (dedup match) plus no other cost-bearing content, with a lower fee-per-cost than A, such that B is processed after A by `create_bundle_from_mempool_items`'s `ORDER BY priority DESC, seq ASC` cursor.
3. Trigger legacy block building (`full_node.config["block_creation"] = 0`) via `Mempool.create_block_generator()`.
4. When processing item B, `dedup_coin_spends.get_deduplication_info()` returns `cost_saving == B.conds.cost` (since B's only cost-bearing spend was already fully credited to A), making `item_cost = cost - cost_saving == 0`.
5. `log.info("Cumulative cost: %d, fee per cost: %0.4f, item cost: %d", cost_sum, fee / item_cost, item_cost)` raises `ZeroDivisionError`, propagating out of `create_bundle_from_mempool_items` and `create_block_generator`.
