### Title
`ReceivedOutput::read` accepts an attacker-supplied scalar offset unbound to the output's `script_pubkey`, letting untrusted bytes redefine the key that controls a reported deposit - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
The Camel advisory's class is "externally-supplied parameters mapped into an internal control namespace without any filtering, so a client can redirect internal operations / resolve internal values." Serai's analog is `ReceivedOutput`, whose wire format carries two independently attacker-controlled fields: a scalar `offset` and a `TxOut`/`script_pubkey`. `ReceivedOutput::read` copies both verbatim into the structure with no consistency check, exactly as the vulnerable Camel consumer copied query parameters into Camel-internal headers. The offset is later consumed as a *key-derivation control parameter*: `Output::key()` computes `script_key - offset·G` (`processor/src/networks/bitcoin.rs:112-122`) and `SignableTransaction::multisig` applies `keys.offset(offset)` (`networks/bitcoin/src/wallet/send.rs:273-285`). The only places the offset is ever bound to the script are the honest `Scanner` (`scan_transaction` inserts offsets it registered itself) and a late check inside `multisig`; nothing in the deserialization path, the scanner-facing data path, or `Output::key()` verifies the pair.

### Finding Description
`ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) performs `Secp256k1::read_F(r)` for the offset and `consensus_decode` for the `TxOut`/`OutPoint`, then stores them together. There is no proof or check that `script_pubkey == p2tr_script_buf(key + offset·G)` for any particular `key` — the function doesn't even take the scanner key. Downstream:

- `Output::key()` (`processor/src/networks/bitcoin.rs:112-122`) reconstructs the owning key as `read_G(script_key) - GENERATOR * offset`. Because both halves are attacker-chosen, `key()` returns an entirely attacker-defined point: for any target group key `K` and any chosen `δ`, setting `script_pubkey = p2tr(K + δ·G)` and `offset = δ` makes the output attribute to `K`. Conversely pairing an arbitrary `script_pubkey` with an arbitrary `δ` attributes it to a key nobody controls.
- `SignableTransaction::new` stores `input.offset` verbatim (`send.rs:176`) and `multisig` re-derives `keys.offset(offsets[i])` and only then compares `p2tr_script_buf` to the prevout script (`send.rs:276-279`). A mismatch returns `None`, which `attempt_sign` turns into `.expect("used the wrong keys")` — a panic (`processor/src/networks/bitcoin.rs:841`).
- `Output::key()` itself asserts `script.is_p2tr()` and unwraps the x-only parse, so a non-P2TR or malformed script in the same unfiltered input panics earlier (`processor/src/networks/bitcoin.rs:114-119`).

### Impact Explanation
Two concrete impacts, both reachable purely by feeding crafted bytes to `ReceivedOutput::read`/`Output::read` (the output object serialized into processor DBs/messages):

1. **Funds reported received that are not spendable / wrong attribution.** A crafted `{offset: δ, script_pubkey: p2tr(K + δG)}` reports an output owned by group key `K` even though the deposit never touched any scanner-registered address; or a mismatched pair reports an output whose claimed key (`key()`) doesn't correspond to the script, so the value is credited to a set that cannot actually authorize its spend — signing fails the `multisig` script check or produces a signature for the wrong tweaked key.
2. **Validator crash (availability).** Any inconsistent `(offset, script_pubkey)` makes `multisig` return `None` → `expect("used the wrong keys")` panics at `attempt_sign`; a non-P2TR script panics inside `key()`. An unprivileged party who can get a malformed serialized `Output` into the pipeline (e.g., via DB/eventually-handled output data) kills the signing attempt.

### Likelihood Explanation
The attacker needs only to supply the 32-byte offset plus a consensus-encoded `TxOut`/`OutPoint` — all public, self-chosen values; no discrete logs, no collusion. Reachability depends on the deployment accepting deserialized `ReceivedOutput`/`Output` from an untrusted writer (the type exists precisely to be serialized over the wire / to disk, and `#[cfg(feature = "std")] read` is a public API). The `Scanner`-produced path is safe because offsets come from the registered map; the bug is the deserialization path skipping that binding — directly paralleling Camel skipping its `HeaderFilterStrategy`.

### Recommendation
Bind the offset to the output at the trust boundary, mirroring the upstream fix (apply the filter at the point external data enters the internal namespace):

- Give `ReceivedOutput` a checked constructor / make `read` take the expected base key (or a `&Scanner`) and reject inputs where `p2tr_script_buf(base + offset·G) != output.script_pubkey`, or
- Store the offset implicitly: re-derive it from `script_pubkey` via the scanner's registered-offset table instead of trusting the serialized scalar, and
- Replace the `assert!(script.is_p2tr())`/`expect`/`unwrap` chain in `Output::key()` and `attempt_sign` with error propagation so malformed inputs fail cleanly rather than panicking.

### Proof of Concept
```
// Attacker crafts bytes fed to ReceivedOutput::read / Output::read:
let target = serai_group_key;                    // K
let delta  = Scalar::random(rng);                // arbitrary offset
let script = p2tr_script_buf(target + GENERATOR*delta).unwrap();
// serialize: offset=delta, output=TxOut{value, script_pubkey=script}, outpoint=any
let ro = ReceivedOutput::read(&mut crafted).unwrap();
let out  = Output { kind: External, presumed_origin: None, output: ro, data: vec![] };
assert_eq!(out.key(), target);   // attributed to K without any scanner registration

// Unspendable/crash variant: keep an honest scanned output's TxOut+outpoint,
// flip one byte of the serialized offset to delta'.
// -> SignableTransaction::multisig returns None (script mismatch)
// -> attempt_sign hits .expect("used the wrong keys") -> panic
```
