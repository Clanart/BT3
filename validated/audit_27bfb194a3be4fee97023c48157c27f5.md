## Analysis

The core broken invariant in the Particle report: **an unprivileged caller can pass attacker-controlled data to a call that moves value out of a shared-custody context, and the receiving contract only validates a coarse post-condition (`amountReceived`) rather than authenticating the caller or the destination of value**, letting the attacker skim off the difference.

The direct structural analog in this repo is `CallDispatcher`, the shared execution helper used by `IntentGatewayV2` (predispatch/postdispatch calldata) and the `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-execution feature.

### Title
Permissionless `CallDispatcher.dispatch()` lets anyone drain any token/ETH balance left on the shared dispatcher contract - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` has no caller restriction whatsoever [1](#0-0) . It is a single shared contract used by `IntentGatewayV2` for predispatch/postdispatch calldata execution [2](#0-1) [3](#0-2) , and by `HyperFungibleToken`/`WrappedHyperFungibleToken` for cross-chain calldata execution. Every legitimate flow only sweeps back the specific token set it cares about (`order.inputs` for predispatch, `order.output.assets` for postdispatch) — any other token or ETH balance the attached arbitrary calldata produces or leaves behind on the dispatcher is not swept and remains sitting on a contract with a `dispatch()` entrypoint open to anyone.

### Finding Description
`IntentGatewayV2.placeOrder()`'s predispatch flow transfers `order.predispatch.assets` to the dispatcher, then executes user-supplied arbitrary calls (`order.predispatch.call`), then sweeps back **only the tokens listed in `order.inputs`** [4](#0-3) . If the predispatch calldata (a swap, an unwrap, a claim, etc.) produces a byproduct token that is not one of `order.inputs` — e.g., a reward token, an extra leg of a multi-hop swap, or dust from an LP unwind — that token balance is never swept and remains on the `CallDispatcher`.

Symmetrically, `IntentsBase._execute()` (postdispatch, run after a fill) sweeps back only the tokens in `order.output.assets` [3](#0-2) ; any other token produced by the attached calldata is left stranded on the dispatcher.

Because `CallDispatcher.dispatch()` is `external` with zero access control — it only checks that `call.to` has code, not who `msg.sender` is [5](#0-4)  — **any address** can, in a separate transaction, call `dispatch()` directly with a `Call{to: strandedToken, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)}` and pull out whatever balance is sitting on the dispatcher. `IntentGatewayV2`'s `nonReentrant` guard on `placeOrder`/`fillOrder` [6](#0-5)  does not help here because the theft happens via a direct external call to `CallDispatcher`, not via re-entering `IntentGatewayV2`.

This mirrors the H-03 pattern: a shared contract temporarily custodies value while running attacker/user-chosen calldata, and the "settlement" logic (the sweep) only checks a narrow, pre-declared set of outcomes rather than authenticating who is allowed to move balance out of the shared contract.

### Impact Explanation
Any token balance transiently or accidentally present on `CallDispatcher` — including legitimate byproducts of predispatch/postdispatch calldata that fall outside the declared `order.inputs`/`order.output.assets` sets — is permanently and permissionlessly stealable by an unrelated third party who simply calls `dispatch()`. This is direct fund loss from a shared bridge-app utility contract, reachable by any unprivileged EOA, with no reliance on a malicious relayer, prover, or peer.

### Likelihood Explanation
Likelihood is realistic: predispatch/postdispatch calldata explicitly exists to support "swap-then-escrow" and "fill-then-act" DeFi composition (per the docs) [7](#0-6) , which commonly produces byproduct tokens (referral rewards, multi-hop swap remainders, LP-unwind second legs) not enumerated in `order.inputs`/`order.output.assets`. Any watcher monitoring `CallDispatcher`'s balance can front-run the legitimate sweep or simply claim balances that were never going to be swept at all.

### Recommendation
Restrict `CallDispatcher.dispatch()` to an allow-listed set of callers (e.g., only registered gateway/HFT contracts via an `onlyAuthorized` modifier), and/or make the dispatcher sweep its **entire** balance of every token touched by the dispatched calls back to the calling contract at the end of `dispatch()`, rather than relying on each app to enumerate which tokens to sweep.

### Proof of Concept
1. User calls `IntentGatewayV2.placeOrder()` with `predispatch.call` that swaps ETH into token A (the sole `order.inputs` token) via a multi-hop path that also yields a small amount of token B as a fee-rebate/dust byproduct.
2. `placeOrder()` sweeps only token A back to the gateway per the loop bounded by `inputsLen` [8](#0-7) ; token B balance remains on the `CallDispatcher`.
3. Attacker, in a later transaction, calls:
```solidity
Call[] memory calls = new Call[](1);
calls[0] = Call({
    to: address(tokenB),
    value: 0,
    data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, tokenB.balanceOf(dispatcherAddr))
});
CallDispatcher(dispatcherAddr).dispatch(abi.encode(calls));
```
4. The call succeeds because `dispatch()` performs no `msg.sender` check, transferring token B's stranded balance to the attacker.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```

```text
### Predispatch

The `predispatch` field in `Order` contains calldata to execute *before* escrowing inputs. The predispatch assets specified in `DispatchInfo.assets` are transferred to the `CallDispatcher`, the encoded calls are executed, and the resulting tokens are transferred back to the gateway for escrow. This enables swap-then-escrow patterns — for example, a user sends ETH which the `CallDispatcher` swaps to DAI on Uniswap, and the resulting DAI is escrowed as the order input.

### Postdispatch

The `call` field in `PaymentInfo` contains calldata to execute *after* the order is filled. This enables fill-then-act patterns — for example, output tokens received from the solver are routed through a DeFi protocol before reaching the beneficiary.

Execution timing differs by mode:

- **Same-chain**: Calldata executes only after the order is **fully filled**. Partial fills do not trigger calldata — only the final fill that completes the order executes it. This ensures all output tokens are available when the calls run.
- **Cross-chain**: Calldata executes **immediately** after the solver delivers output tokens to the beneficiary, before the settlement message is dispatched back to the source chain.

After execution, any tokens remaining in the `CallDispatcher` are swept back to the gateway and collected as dust (emitting `DustCollected` for each token). When postdispatch calldata is present, 100% of any surplus (solver overpayment) goes to the protocol rather than being split with the beneficiary — this prevents manipulation of surplus distribution through calldata side effects.
```
