## Analysis Summary

The GMX report's core failure pattern is: a broad catch-block classifies errors generically and takes an unintended, silent recovery action (cancellation) instead of properly propagating/signaling a specific error condition, because a check for that specific error type is missing.

The closest verified Protobuf analog is in `LazyFieldLite`, the internal helper used to lazily parse embedded/extension message fields. In `ensureInitialized`, a caught `InvalidProtocolBufferException` sets an internal `corrupted` flag before substituting the default instance [1](#0-0) . But the two other call sites that catch the exact same exception type — `mergeFrom(CodedInputStream, ExtensionRegistryLite)` and the private `mergeValueAndBytes` helper — swallow it **without** setting `corrupted`, silently keeping the pre-merge value and returning normally as if the merge succeeded [2](#0-1) .

### Title
Silent swallowing of `InvalidProtocolBufferException` in `LazyFieldLite.mergeFrom`/`mergeValueAndBytes` omits corruption flag set elsewhere in the same class - (File: `java/core/src/main/java/com/google/protobuf/LazyFieldLite.java`)

### Summary
`LazyFieldLite` has three code paths that catch `InvalidProtocolBufferException` while lazily materializing an embedded/extension message from attacker-supplied bytes. One path (`ensureInitialized`) records the failure via the internal `corrupted` boolean before falling back to a default instance. The other two paths (`mergeFrom(CodedInputStream, ExtensionRegistryLite)` at lines 360-365, and `mergeValueAndBytes` at lines 370-377) catch the identical exception but omit setting `corrupted`, silently discarding the merge attempt and returning as if nothing happened.

### Finding Description
`LazyFieldLite` stores a message either as raw `delayedBytes` or as a parsed `value`, materializing lazily [3](#0-2) . When a `LazyFieldLite` already holds a parsed `value` and a caller merges in additional bytes (e.g. via `mergeFrom(CodedInputStream, ExtensionRegistryLite)`, reached from generated `mergeFrom` methods when a field is duplicated on the wire) the merge is attempted against the existing value:
```java
try {
  setValue(value.toBuilder().mergeFrom(input, extensionRegistry).build());
} catch (InvalidProtocolBufferException e) {
  // Nothing is logged and no exceptions are thrown. Clients will be unaware that a proto
  // was invalid.
}
``` [4](#0-3) 

The comment explicitly documents that no exception is thrown and nothing is logged, in contrast to the class's own `ensureInitialized`, which — for the analogous "first parse" case — records the failure via `this.corrupted = true` [5](#0-4) . `mergeValueAndBytes`, used by `merge(LazyFieldLite other)` when combining a parsed value with another field's bytes, has the same asymmetry [6](#0-5) .

The missing check here is structurally identical to the GMX report: a broad catch that should classify a specific failure condition and propagate/flag it instead silently takes the "do nothing, keep prior state" branch because the flag-setting logic present in one sibling code path was not applied in the other two. The externally observable behavior mirrors GMX's outcome: a caller-issued operation (deposit execution / here, a message merge from bytes) that should fail loudly is instead treated as a no-op success.

### Impact Explanation
A caller invoking `Message.mergeFrom`/`Builder.mergeFrom` on a message containing a lazily-parsed extension or embedded field, where malformed bytes are supplied for that sub-field during a merge (not the initial parse), will get no `InvalidProtocolBufferException` and no indication via `isCorrupted()` (since that flag is only set by `ensureInitialized`, not by these two merge paths). The final built message silently retains its pre-merge value for that field, i.e., the merge is dropped without any signal — an integrity failure where the application believes the merge succeeded when attacker-controlled bytes were in fact rejected and discarded. This differs from ordinary "catch-and-convert" exception handling (excluded by the ruleset) in that the exception is fully swallowed *inside the library*, before any application-level `catch` block could ever observe it, and the class's own internal corruption-tracking mechanism is inconsistently applied.

### Likelihood Explanation
Triggering this requires an attacker to control bytes fed into a `mergeFrom(CodedInputStream, ExtensionRegistryLite)` or `merge(LazyFieldLite)` call on a `LazyFieldLite`-backed field after it has already been parsed — e.g., a duplicated field occurrence on the wire for an extension/embedded field that uses lazy parsing, or an explicit application-level merge of two parsed messages. This is reachable through the standard public `parseFrom`/`mergeFrom` binary parsing API and requires no privileged access, matching the exposure assumption (ordinary client sending bounded binary Protobuf through a supported parse API).

### Recommendation
Set `this.corrupted = true` (or otherwise surface the failure, e.g. rethrow) in the `catch (InvalidProtocolBufferException e)` blocks of `LazyFieldLite.mergeFrom(CodedInputStream, ExtensionRegistryLite)` and `mergeValueAndBytes`, consistent with `ensureInitialized`, so that `isCorrupted()` reliably reflects any merge failure and callers relying on that signal are not misled.

### Proof of Concept
1. Construct a `LazyFieldLite` for an embedded message type, initialize it so `value` is already parsed (e.g. via `getValue()` after construction from valid bytes, or via `fromValue`).
2. Call `mergeFrom(codedInputStreamWithTruncatedOrCorruptBytes, extensionRegistry)`.
3. Observe: no exception propagates, `getValue()` still returns the prior valid value, and `isCorrupted()` returns `false` even though the supplied merge bytes were invalid protobuf — contrasted with performing the equivalent corruption on the *initial* parse path (via `ensureInitialized`), where `isCorrupted()` would return `true`. This demonstrates the inconsistent, missing-check handling of the identical exception type across the class's three catch sites, at [4](#0-3)  and [7](#0-6)  versus [1](#0-0) .
