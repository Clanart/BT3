### Title
Partial-commit patch is built from a diff re-fetched at commit time while the line-selection bitmap is indexed against the diff shown in the UI, allowing a race to silently commit different lines than the user selected - (File: `app/src/lib/patch-formatter.ts`, `app/src/lib/git/apply.ts`)

### Summary
The HyperdriveLP report's broken invariant is: a value used to *validate* an operation (`_minOutput`) is checked against stale/partial state (`baseProceeds`) while a second, causally-linked output (`withdrawalShares`) is computed later from state that can be moved by an attacker in between, with no check tying the two together. The Desktop analog is the "partial commit" / line-selection flow: the set of lines a user has selected to stage is a bitmap of **absolute line indices** computed against one snapshot of a file's diff, but the patch that is actually applied to the index is built from a **freshly re-fetched diff** at commit time, with no verification that the two diffs still describe the same hunks/line layout.

### Finding Description
When a user does a partial stage/commit, the UI computes a `DiffSelection` bitmap keyed by `hunk.unifiedDiffStart + lineIndex` against the diff object held in `changesState.selection.diff` (loaded via `updateChangesWorkingDirectoryDiff`) [1](#0-0) . That comment block explicitly acknowledges: "The diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines" — i.e. the app does **not** re-validate that selected line indices still refer to the same content, it only prunes indices that are no longer "includeable" [2](#0-1) .

When staging actually happens, `stageFiles` iterates the files and, for any file with a partial selection, calls `applyPatchToIndex(repository, file)` [3](#0-2) . Critically, `applyPatchToIndex` does **not** use the diff that produced the selection UI — it independently re-fetches the working directory diff at commit time via `getWorkingDirectoryDiff(repository, file)` [4](#0-3) , then calls `formatPatch(file, diff)` [5](#0-4) .

`formatPatch` walks the hunks of this **newly fetched** diff and decides which lines to keep purely by testing `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex = hunk.unifiedDiffStart + lineIndex` [6](#0-5) . There is no check that the new diff's hunk layout/line content matches the diff the selection bitmap was originally built from. If the working tree content changes between the moment the user made their line selection and the moment `applyPatchToIndex` runs (e.g. the file is rewritten by an external process, another tool, a slow background operation, or content synced from a fetched/checked-out ref while the commit dialog is open), the hunk boundaries and `unifiedDiffStart` offsets shift. The stale bitmap indices then map onto **different lines in the new diff**, so `formatPatch` silently includes/excludes the wrong content — corrupting exactly what the user believes they are committing, without any error, confirmation, or slippage-style safety check.

### Impact Explanation
This directly matches the "silent corruption of what the user commits" impact category: a user can partially stage/commit content different from what they explicitly selected in the diff viewer, with no warning. Depending on the race window, this can cause committing unintended additions/deletions (e.g. reintroducing content the user thought they excluded, or omitting content they thought they included), which then gets pushed. There's no cryptographic or content-hash tie between the diff snapshot used for the UI selection and the diff snapshot used to materialize the patch — precisely analogous to HyperdriveLP computing `withdrawalShares` from state that moved after the `_minOutput` check was satisfied.

### Likelihood Explanation
The window is real but narrow: it requires the working directory file to change between diff-load-for-selection and the staging/commit action. Desktop's own review comment at `app-store.ts:3480-3485` documents that this scenario ("diff might have changed dramatically since last we loaded it") is known and only partially mitigated (pruning removed lines from the selectable set, not fully re-validating the bitmap against new hunk offsets). Sources of such change while a user is in the middle of reviewing/staging include another running process (editor autosave, linter/formatter with fix-on-save, background build tool), or a file-watcher-driven update in Desktop itself while the Changes view is open — none of which require local/admin access beyond normal use of the tool, and none of which are "prior malware." This is a real, if intermittent, correctness gap rather than a purely theoretical one, but it is not deterministically triggerable by a remote attacker without some local write access to the working tree during the race window, so likelihood should be considered Medium/Low rather than High.

### Recommendation
Tie the diff used to build the selection bitmap to the diff used to build the patch: either (a) pass the exact `IDiff` object used for the UI selection through to `applyPatchToIndex`/`formatPatch` instead of re-fetching a new diff at apply time, or (b) if a fresh diff must be fetched for correctness/staleness reasons, compute a content fingerprint (e.g. hash) of the diff used for selection and compare it against the fresh diff before applying; if they differ, abort the partial stage and force the user to re-review/re-select before committing, rather than silently reinterpreting old indices against new hunk data.

### Proof of Concept
1. Modify a tracked file and open it in Desktop's Changes view; the diff is loaded and a `DiffSelection` bitmap is created keyed by absolute line index against this diff (`updateChangesWorkingDirectoryDiff`).
2. Select only specific lines/hunks for partial staging (e.g. select the addition on line 10 but not line 20).
3. Before triggering the commit, use an external process (editor autosave, `sed`, a build tool, etc.) to modify the file such that hunk boundaries shift (e.g. insert lines earlier in the file), without the Changes view re-rendering/re-syncing selection state in time.
4. Trigger "Commit" — `stageFiles` → `applyPatchToIndex` re-fetches the diff via `getWorkingDirectoryDiff` and calls `formatPatch`, which reuses the old bitmap's absolute indices against the new hunk layout.
5. Inspect the resulting commit via `git show`: the staged content does not match the lines the user visually selected in the diff viewer — content the user did not select is committed, or content the user did select is dropped, silently.
