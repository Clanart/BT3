### Title
Race between `branch.upstreamRemoteName` and cached `remote.name` can cause `git push` to target the wrong (attacker-configured) remote - ([File: app/src/lib/stores/app-store.ts])

### Summary
`performPush` in `app-store.ts` builds the destination for `git push` from two independently-refreshed pieces of state: the repository's cached `remote` object (`state.remote`) and the current tip's `branch.upstreamRemoteName`. The developers themselves documented that these two values have "no guarantee that they'll be refreshed at the exact same time," creating a theoretical window in which `remoteName` (derived from `branch.upstreamRemoteName`) diverges from `remote.name`. When that happens, the resulting `safeRemote` object is pushed to using the *stale/racy name* while only the URL used for proxy resolution comes from the trusted `remote` object — but the actual git destination is resolved by `git` itself from local `.git/config` using that name, not the URL Desktop computed. [1](#0-0) 

### Finding Description
`getBranchToPush`/`performPush` compute:
```
const remoteName = branch.upstreamRemoteName || remote.name
...
const safeRemote: IRemote = { name: remoteName, url: remote.url }
``` [2](#0-1) 

`safeRemote` is passed into `pushRepo`, which ultimately calls `git push <remote.name> <localBranch>:<remoteBranch>`, i.e., the *name* argument, not the URL, is what git resolves against the repository's local remote configuration: [3](#0-2) 

The comment in `app-store.ts` explicitly acknowledges the underlying invariant is not actually enforced — it is only detected after the fact via a non-fatal telemetry event (`sendNonFatalException('remoteNameMismatch', ...)`), and the mismatch is *not blocked*; the push proceeds anyway using the possibly-stale `remoteName`: [4](#0-3) 

Because `git push <name>` resolves the destination URL from whatever is configured under that name in `.git/config` — content that can be attacker-influenced (e.g., a cloned/forked repository, a repository whose `.git/config` was written by a prior clone/fetch flow, or a "fork remote" added by Desktop's fork-remote handling in `find-forked-remotes-to-prune.ts`) — a name/state desync means Desktop can silently push the user's commits to a different, unintended remote than the one shown to the user in the UI. This is exactly the class of bug the nano-node report describes: an assertion/guard (`safeRemote.name !== remote.name`) exists to *detect* the race but does not prevent the racy value from being used before the guard fires, mirroring how genesis could still cast a vote before the drain fully took effect.

### Impact Explanation
If exploitable, this results in a user's commits/branch content being pushed to a remote the user did not intend, which the report's rules classify as "silent corruption of what the user commits or pushes." Since git push also transmits credentials via the credential/askpass trampoline for whichever remote URL is resolved, this could also route authentication material to an unintended endpoint if that remote name maps to attacker infrastructure in local config.

### Likelihood Explanation
This is explicitly called out by Desktop's own developers as a "theoretical possibility" that they added a safeguard and telemetry for rather than a hard fix, and a near-identical bug class ("Race condition with remote lookup could cause push to go to incorrect remote — #6986") was previously fixed in 1.7.0-beta1, per the changelog: [5](#0-4) 
I was not able to fully trace, within the remaining tool budget, the exact async call sequence that updates `state.remote` versus the one that updates `branch.upstreamRemoteName` (i.e., which refresh paths in `git-store.ts` / `app-store.ts` populate each, and how far apart in time they can be triggered by attacker-controlled repository state such as remote-tracking branch changes from a fetch). This code path predates the safeguard being generalized to a preventive check (it only reports, doesn't abort), which suggests the maintainers considered the race unlikely but did not close it. Given this uncertainty, I cannot claim a confirmed, reproducible trigger — only a design gap with an explicit code comment acknowledging the residual risk.

### Recommendation
- Make the `safeRemote.name !== remote.name` check fail closed: abort the push (surfacing an error to the user) instead of merely emitting a non-fatal telemetry event and continuing with the racy name.
- Prefer resolving the push destination by URL rather than by locally-configured remote name where possible, or re-validate that the name still maps to the expected URL in `.git/config` immediately before invoking `git push`.
- Ensure `state.remote` and `branch.upstreamRemoteName` are refreshed atomically (from the same repository state snapshot) rather than from independently-timed refresh cycles.

### Proof of Concept
I could not construct a concrete, verified reproduction within the available investigation — doing so would require exercising the exact refresh-timing race between the branch-state refresh and the remote-state refresh in `git-store.ts`, which was not fully traced. The finding is a documented, acknowledged design gap (self-flagged by the `sendNonFatalException('remoteNameMismatch', ...)` instrumentation) rather than a demonstrated exploit; I'm reporting it with that caveat rather than asserting exploitability with certainty.
