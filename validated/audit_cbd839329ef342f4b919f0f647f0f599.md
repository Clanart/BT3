### Title
Webhook shop-domain and topic headers are excluded from the HMAC signature, allowing a captured signed payload to be replayed against an arbitrary shop - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` authenticates a webhook only by HMAC-signing the raw request body, but the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers — the data that determines *which shop* and *which handler* the payload is applied to — are never included in the signed material. This is the same class of bug as the Diamond upgrade issue: the "id" used to decide what gets executed (facet cuts in the C4 report; shop/topic here) is not part of the hashed/verified data, so an attacker can keep a validly-signed body while swapping the unsigned routing metadata to redirect its effect.

### Finding Description
`hmac_valid?` in `lib/shopify_app/controller_concerns/payload_verification.rb` computes the digest solely over `request.raw_post`: [1](#0-0) 

`WebhookVerification#verify_request` calls this with only the body, and `shop_domain` is read straight from an unsigned header: [2](#0-1) 

`WebhooksController#receive` builds the `ShopifyAPI::Webhooks::Request` from `request.headers.to_h` (which supplies shop/topic used for routing) independent of the HMAC check that only covers the raw body: [3](#0-2) 

Downstream job handlers trust this header-derived `shop_domain` for destructive, shop-scoped operations, e.g. the generated uninstall job deletes the local `Shop` record by that value with no other verification: [4](#0-3) 

Because the shared secret (`ShopifyApp.configuration.secret`) is per-app, not per-shop, a merchant who installs the app on their own store (any unrelated merchant, unprivileged relative to other shops) legitimately receives HMAC-valid webhook deliveries signed with that same app secret. They can capture one such `(body, HMAC)` pair and replay it to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a victim shop/topic. `verify_request` still passes because the signature never covered those headers, and the job then executes against the attacker-chosen shop.

### Impact Explanation
An unrelated/anonymous-relative-to-victim merchant can force actions to be attributed to a different shop than the one that actually produced the signed payload — a cross-shop access/state-change primitive. Depending on the app's webhook handlers this can cause the victim shop's locally stored session/model to be destroyed (as in the generated `AppUninstalledJob`, causing a forced disconnect/DoS), or improperly trigger privacy/redact or business-logic jobs against a victim shop with attacker-controlled body content, all while passing the app's webhook authenticity check.

### Likelihood Explanation
The webhook endpoint is unauthenticated by design (protected only by HMAC), and any developer/merchant can install the app on their own store to obtain a batch of legitimately signed request bodies. Forging the replay only requires changing an HTTP header, which is trivial once a valid `(body, hmac)` pair is obtained — no cryptographic secret needs to be recovered. Reachability from an anonymous/unrelated-merchant HTTP request is direct.

### Recommendation
Bind the shop domain (and topic, if used for routing/authorization decisions) into the HMAC-verified material — e.g., verify the header values against the payload's own shop/topic fields when present, or require that the signature be computed over a canonical string that includes the shop domain and topic headers, not just the raw body. At minimum, cross-check that the shop present in the parsed webhook body matches the `X-Shopify-Shop-Domain` header before trusting it in `verify_request`.

### Proof of Concept
1. Install the app on an attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `app/uninstalled`) and capture the raw POST body plus the `X-Shopify-Hmac-Sha256` header Shopify sent — this HMAC is computed with the app's single shared secret, valid for any shop.
2. Replay that exact body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and matching topic header) instead of the attacker's own domain.
3. `ShopifyApp::WebhookVerification#verify_request` → `hmac_valid?(request.raw_post)` succeeds because only the body is checked.
4. The generated `AppUninstalledJob#perform` looks up `Shop.find_by(shopify_domain: "victim.myshopify.com")` and calls `shop.destroy`, deleting the victim's local session/shop record despite the request never originating from the victim shop.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

class AppUninstalledJob < ActiveJob::Base
  extend ShopifyAPI::Webhooks::WebhookHandler

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end
end
