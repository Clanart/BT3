## Analog Found: Out-of-bounds read while parsing a submitted spend bundle's CLVM buffer

### Title
Unbounded atom length-prefix parsing causes out-of-bounds buffer read in `is_atom_canonical`/`is_clvm_canonical` - (File: `chia/full_node/mempool_manager.py`)

### Summary
The CVE describes jhead's `ReadJpegSections`/`process_SOFn` reading past the end of an input buffer because a length field taken from attacker-controlled input is trusted without checking it against the remaining buffer size. The same bug class — trusting an embedded length/marker byte to drive sequential indexed reads without validating against the buffer's actual length — exists in `is_atom_canonical()` and its caller `is_clvm_canonical()` in [1](#0-0)  which is reachable from an unprivileged spend-bundle submitter's transaction data.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` inspects the leading byte of a purported CLVM atom to determine how many additional length-prefix bytes follow (0–5 bytes depending on the high bits), then loops that many times reading `clvm_buffer[offset]` and shifting it into `atom_len`: [2](#0-1) 

There is no check that `offset` remains within `len(clvm_buffer)` before each indexed read. If the CLVM buffer is truncated immediately after a multi-byte length-prefix marker (e.g. a byte matching `0b11111100` pattern, which signals a 5-byte trailing length prefix) with insufficient trailing bytes, the loop indexes past the end of the buffer.

The caller, `is_clvm_canonical()`, walks a full serialized CLVM program byte-by-byte using the same unchecked-offset pattern for the pair/atom dispatch and for computing `atom_len` used to advance `offset`, again without bounds checks against `len(clvm_buffer)`: [3](#0-2) 

This function is used by the mempool manager to determine DEDUP eligibility for a spend's solution bytes — data that originates directly from a submitted `SpendBundle`'s `CoinSpend.solution`, i.e., attacker/wallet-controlled bytes that have not yet been validated by the Rust CLVM deserializer at the point this canonical-form check runs (this check is a Python-side auxiliary check layered on top of the raw bytes, per the module's documented role, `.cursor/context/clvm-execution.md` lines 96–118).

### Impact Explanation
In Python, out-of-bounds indexing into a `bytes` object raises `IndexError` rather than causing memory corruption, so this is not a memory-safety vulnerability as in the C-based jhead case. However, the analog bug class (trusting an internal length marker to drive further reads without validating remaining buffer size) still produces a crash/DoS condition: a crafted spend bundle whose solution bytes are engineered to look like a canonical-encoding candidate but are truncated right after a multi-byte length-prefix marker can trigger an unhandled `IndexError` while the mempool manager evaluates DEDUP eligibility for that spend. If this exception is not caught by the calling code path, it can abort spend-bundle admission processing, a spend-triggered transaction-processing halt.

### Likelihood Explanation
An unprivileged spend-bundle submitter fully controls the `solution` bytes of a `CoinSpend`, and no upstream validation step canonicalizes or length-checks solution bytes before this DEDUP-eligibility check runs, per the CLVM execution context notes describing `is_clvm_canonical()`'s role and location (`chia/full_node/mempool_manager.py:185` in the referenced context doc). Crafting a truncated multi-byte atom length prefix is a simple, low-cost byte-level manipulation, requiring no special privileges, keys, or network position.

### Recommendation
Add explicit bounds checks in both `is_atom_canonical()` and `is_clvm_canonical()` before every indexed access to `clvm_buffer`, raising a well-defined, caught exception/return value (e.g., treat as "not canonical") instead of letting Python's `IndexError` propagate. Specifically:
- In `is_atom_canonical()`, verify `offset < len(clvm_buffer)` before each `clvm_buffer[offset]` read inside the `for i in range(prefix_len)` loop, and validate `1 + prefix_len + atom_len <= len(clvm_buffer) - start_offset` before returning.
- In `is_clvm_canonical()`, verify `offset < len(clvm_buffer)` before each `clvm_buffer[offset]` read in the main `while True` loop.
- Ensure any caller of `is_clvm_canonical()` treats parsing failures as "not canonical" rather than allowing an uncaught exception to escape spend-bundle processing.

### Proof of Concept
Construct a `SpendBundle` whose `CoinSpend.solution` (or another part exercised by `is_clvm_canonical`) contains a CLVM buffer ending immediately with a byte matching the `0b11111100` (5-byte length prefix) pattern and no further bytes, e.g. a solution bytes tail of `b"\xfc"` with nothing after it. Submitting this bundle for mempool admission drives `is_clvm_canonical()` → `is_atom_canonical()` to read `clvm_buffer[offset]` with `offset == len(clvm_buffer)`, raising `IndexError`. I was not able to fully confirm, within available tool calls, whether the specific call site wrapping `is_clvm_canonical()` in the DEDUP-eligibility path catches this exception or lets it propagate to abort spend-bundle processing — this should be verified directly against `chia/full_node/mempool_manager.py` and its test suite (`chia/_tests/core/mempool/test_mempool_manager.py`) in a full Devin session before treating this as confirmed-exploitable DoS.

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value


def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
