### Title
Unbounded Lagrange interpolation causes quadratic CPU exhaustion during `ThresholdKeys` deserialization - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` trusts the serialized participant count `n`, which can be as large as `u16::MAX`, and `ThresholdKeys::new` then derives the group key by calculating a Lagrange interpolation factor for each of the first `t` participants. [1](#0-0) 

When `t = n = 65535`, each interpolation factor iterates over the other 65,534 participants, producing more than 4.2 billion field operations from a serialized payload of only a few megabytes. [2](#0-1) [3](#0-2) 

### Finding Description
The deserializer reads attacker-controlled `t`, `n`, and `i` directly from the input and permits any `t <= n <= 65535`. [4](#0-3) [5](#0-4) 

For `Interpolation::Lagrange`, it reads one secret scalar and `n` verification shares, then invokes `ThresholdKeys::new`. [6](#0-5) 

`ThresholdKeys::new` constructs `t` participant identifiers and sums `verification_share * interpolation_factor(i, participants)` for each one. [3](#0-2) 

`interpolation_factor` performs an inner loop over every participant in `included`, making group-key reconstruction quadratic in the attacker-selected participant count. [7](#0-6) 

### Impact Explanation
An unprivileged party who can submit bytes to `ThresholdKeys::read` can make deserialization consume CPU resources disproportionate to the input size. [8](#0-7) 

With `n = t = 65535`, the caller performs approximately `65535 * 65534` inner-loop field operations plus 65,535 field inversions before `read` returns. [7](#0-6) [3](#0-2) 

This can stall or effectively deny service to a signing component that deserializes threshold keys from untrusted input, preventing subsequent signing or verification work from proceeding. [3](#0-2) 

### Likelihood Explanation
The malicious payload is validly encoded and does not require malformed scalars, malformed points, duplicate participants, private keys, consensus control, or a malicious validator. [1](#0-0) 

All verification shares can simply encode the same valid generator point, and the threshold parameters only need to satisfy the documented `1 <= t <= n` and `i <= n` checks. [5](#0-4) [9](#0-8) 

### Recommendation
Enforce a protocol-appropriate maximum for `n` and `t` before allocating vectors or entering `ThresholdKeys::new`, and reject serialized parameter sets whose required interpolation work exceeds that bound. [1](#0-0) 

Prefer a bounded signing-set representation or an interpolation algorithm whose group-key reconstruction does not perform a separate linear pass over every signer for every participant. [7](#0-6) 

### Proof of Concept

use dkg::{Participant, ThresholdKeys};
use ciphersuite::Ciphersuite;
use ciphersuite::group::{ff::PrimeField, Group, GroupEncoding};

fn malicious_keys<C: Ciphersuite>() -> Vec<u8> {
  let mut bytes = Vec::new();

  bytes.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
  bytes.extend(C::ID);
  bytes.extend(u16::MAX.to_le_bytes()); // t
  bytes.extend(u16::MAX.to_le_bytes()); // n
  bytes.extend(1u16.to_le_bytes());     // i
  bytes.push(1);                        // Interpolation::Lagrange
  bytes.extend(C::F::ONE.to_repr().as_ref());

  let share = C::generator().to_bytes();
  for _ in 0 .. u16::MAX {
    bytes.extend(share.as_ref());
  }

  bytes
}

// For a 32-byte point encoding, this is roughly 2 MiB of input and induces
// 65,535 * 65,534 Lagrange inner-loop iterations.
let payload = malicious_keys::<C>();
let _ = ThresholdKeys::<C>::read(&mut payload.as_slice());
