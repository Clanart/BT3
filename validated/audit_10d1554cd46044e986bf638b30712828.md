### Title
`Scanner::scan_block` returns immature coinbase outputs as spendable `ReceivedOutput`s, enabling deposits that cannot actually be spent - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
The InventoryGui bug class is "a component unconditionally exposes stored items for withdrawal without gating whether withdrawal is permitted". The Serai analog is `Scanner::scan_block` in `networks/bitcoin/src/wallet/mod.rs`, which iterates over `block.txdata` including `txdata[0]` — the coinbase transaction — and returns any matching outputs as ordinary `ReceivedOutput`s. Coinbase outputs are consensus-immature for 100 blocks, yet the scanner hands them out with no maturity flag, no gating, and no distinction from normally spendable outputs.

### Finding Description
`scan_block` calls `scan_transaction` on every transaction in the block, including the coinbase:

```rust
// networks/bitcoin/src/wallet/mod.rs:221-227
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

`scan_transaction` matches purely on `script_pubkey` and builds a `ReceivedOutput` carrying only `offset`, `output`, and `outpoint` — there is no field indicating coinbase origin or maturity (`networks/bitcoin/src/wallet/mod.rs:199-214`, `ReceivedOutput` struct at lines 90-97). The only mitigation is a doc comment stating "a post-processing pass is needed" or that callers may use `txdata[1 ..]` — but nothing in the API enforces this, and the returned `ReceivedOutput` type provides no way to distinguish an immature output after the fact without re-fetching the block.

Notably, Serai's own processor had to work around this: `Bitcoin::get_outputs` manually slices `&block.txdata[1 ..]` with the comment "Skip the coinbase transaction which is burdened by maturity" (`processor/src/networks/bitcoin.rs:690-691`). Any consumer of the library that calls `scan_block` directly (the documented entry point, exercised in `networks/bitcoin/tests/wallet.rs:65` where `scan_block` output is asserted equal to scanning `txdata[0]`) receives coinbase outputs it believes are spendable.

### Impact Explanation
An unprivileged party can reach this: anyone can mine (or have a pool mine) a block whose coinbase pays Serai's P2TR script — the script is derived from a public group key and can also be reached via a registered offset. Serai then reports the coinbase output as received funds. If Serai treats such an output as backing a deposit (e.g., credits a bridge deposit), it cannot actually spend it for 100 blocks; worse, if that coinbase is orphaned by a reorg, the "received" output vanishes entirely while the credit may already have been issued. This matches the accepted impact "funds reported received that are not spendable", and is a direct analog of a GUI allowing items to be withdrawn from storage that should not be withdrawable.

### Likelihood Explanation
Mining a block paying an arbitrary address requires mining capability, but is not collusion, not a malicious-RPC assumption, and uses only public data (the group's address). The likelihood is bounded by block-production cost, hence Medium rather than High.

### Recommendation
Have `scan_block` skip `block.txdata[0]` or tag `ReceivedOutput` with a coinbase/maturity flag so callers can enforce maturity, rather than relying on a doc comment. Add a consensus-height check or expose `is_coinbase` on `ReceivedOutput`.

### Proof of Concept
`networks/bitcoin/tests/wallet.rs:40-77` demonstrates it: `send_and_get_output` mines one block to Serai's P2TR address, calls `scanner.scan_block(&block)`, and the returned single output is `txdata[0]` (the coinbase). A `ReceivedOutput` for a consensus-unspendable coinbase is produced with no indication of its immaturity — the test even asserts `outputs[0].outpoint() == OutPoint::new(block.txdata[0].compute_txid(), 0)` and only avoids failure by mining 100 additional blocks before any spend attempt.
