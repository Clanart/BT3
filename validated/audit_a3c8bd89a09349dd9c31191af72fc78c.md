### Title
Aggregate Schnorr verification omits nonces and keys, allowing forged aggregate signatures - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` derives each half-aggregation weight solely from the per-signature challenges, not from the aggregate’s `Rs` or the verified public keys. A remote prover can therefore compute the weights in advance and choose a nonce commitment that makes an invalid residual cancel another invalid residual.

### Finding Description
The verification transcript commits only to `challenge` values at `crypto/schnorr/src/aggregate.rs:132-136`. It then computes `z = weight(&mut digest)` and verifies `sum(z_i * (R_i + c_i * A_i)) - sG = identity` at `crypto/schnorr/src/aggregate.rs:138-145`. Because neither `R_i` nor `A_i` is appended to the weight transcript, `z_i` is predictable independently of the forged nonce commitments. For two entries, an attacker can set `R_2 = -(z_1 / z_2) * E_1 - c_2 * A_2 + s_2 * G`, where `E_1 = R_1 + c_1 * A_1 - s_1 * G` is the first invalid signature’s nonzero residual. The weighted residuals then sum to zero even though neither component signature verifies.

### Impact Explanation
Any caller relying on `SchnorrAggregate::verify` can accept an aggregate signature for which no valid constituent Schnorr signatures exist. The aggregator also derives weights using the same challenge-only transcript at `crypto/schnorr/src/aggregate.rs:164-183`, so honest aggregation and attacker verification use the same predictable weights. This satisfies the forged-proof/signature impact class.

### Likelihood Explanation
The attacker needs only the public keys/challenges and can freely choose the aggregate’s `Rs` and `s` bytes supplied through `SchnorrAggregate::read` or constructed programmatically. No private key, validator privilege, malformed encoding, or collision in the underlying hash is required.

### Recommendation
Bind every aggregation input to the weight transcript: each public key, nonce commitment `R`, challenge, and positional index. Prefer deriving each weight after appending the complete `(A_i, R_i, c_i)` tuple, and ensure verification and aggregation serialize identical data.

### Proof of Concept
```text
For signatures i = 1, 2:
  E_i = R_i + c_i*A_i - s_i*G
  individual validity requires E_i = identity

Current aggregate check:
  z_1*E_1 + z_2*E_2 = identity

Because z_1 and z_2 depend only on c_1 and c_2:
  1. Choose arbitrary A_1, c_1, s_1, R_1 producing nonzero E_1.
  2. Choose arbitrary A_2, c_2, s_2.
  3. Compute:
       R_2 = -(z_1 / z_2)*E_1 - c_2*A_2 + s_2*G
  4. Then E_2 = -(z_1 / z_2)*E_1.
  5. SchnorrAggregate { Rs: [R_1, R_2],
                        s: z_1*s_1 + z_2*s_2 }
     verifies while both individual signatures are invalid.
