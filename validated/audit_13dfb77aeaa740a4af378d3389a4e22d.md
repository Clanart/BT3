### Title
Swapped accuser/accused in `VerifyBlame` inverts DKG blame attribution — honest reporters fatally slashed, malicious share-senders never blamed - ([File: processor/src/key_gen.rs])

### Summary
`AdditionalBlameMachine::blame(sender, recipient, msg, proof)` expects the first argument to be the party that *sent* the allegedly-invalid encrypted share and the second to be the party that *received* it. In `Transaction::InvalidDkgShare` handling, `accuser` is the share recipient and `accused` (`faulty`) is the share sender, per `DkgShare::get(txn, genesis, accuser, faulty)` where shares are stored as `DkgShare::set(txn, genesis, from, to, share)` (`from` = sender, `to` = recipient). The processor then calls `.blame(accuser, accused, ...)` — the arguments are reversed.

### Finding Description
In `coordinator/src/tributary/handle.rs:486-503`, `accuser` is the participant who claims they received a bad share, and `faulty` (mapped to `accused` in `CoordinatorMessage::VerifyBlame`) is the alleged sender.

In `processor/src/key_gen.rs:543-556`:

```rust
.blame(accuser, accused, substrate_share, substrate_blame);
.blame(accuser, accused, network_share, network_blame);
```

But `BlameMachine::blame`/`blame_internal` in `crypto/dkg/pedpop/src/lib.rs:575-632` take `(sender, recipient, ...)` — confirmed by `pedpop/src/tests.rs:156` where `machine.blame(ONE, TWO, ...)` correctly blames `ONE`, the sender of the mutated share to `TWO`.

Inside `blame_internal`, `decrypt_with_proof(from = sender, ...)` verifies the message's Schnorr PoP against `pop_challenge(context, R, key, from, msg)`, which binds `from` to the actual sender (`crypto/dkg/pedpop/src/encryption.rs:302-324`, `374-379`). With the swapped arguments, `from` is set to the accuser, so the PoP verification fails for every legitimately-formed message, `blame_internal` returns `sender` (the accuser), and `key_gen.rs:559-563` emits `ProcessorMessage::Blame { participant: accuser }`.

### Impact Explanation
Any `InvalidDkgShare` report causes the *accuser* — an honest validator correctly reporting a malicious/faulty share — to be identified as faulty and fatally slashed. The actually-malicious share sender is never attributable: even a genuinely invalid share cannot produce blame on the sender because the PoP check fails before share-verification statements are evaluated. This inverts the entire DKG accountability mechanism: it punishes honesty, shields the faulty party, and (since DKG confirmation requires all non-removed participants) lets a malicious participant abort key generation while honest reporters are slashed — degrading cluster liveness and draining honest validators' stake. This is an analog of "takeover/compromise via the communication segment": a participant's on-wire messages cause the protocol to fatally misattribute faults.

### Likelihood Explanation
Deterministic. The argument order is wrong unconditionally, so every blame report — a normal, reachable protocol action by any validator holding an allegedly-invalid share — triggers the inversion. No collusion, threshold corruption, or privileged access is needed; the accuser only needs to publish `InvalidDkgShare` referencing an existing `DkgShare` entry, which any participant in a DKG session can do.

### Recommendation
Swap the arguments: call `.blame(accused, accuser, share, blame)` (i.e., `sender = accused`, `recipient = accuser`) in both the substrate and network `AdditionalBlameMachine::blame` calls at `processor/src/key_gen.rs:549` and `processor/src/key_gen.rs:556`. Add a regression test that feeds a genuinely invalid share and a genuine `EncryptionKeyProof` through the `VerifyBlame` path and asserts the accused party is blamed, plus a valid-share case asserting the accuser is blamed.

### Proof of Concept
```rust
// crypto/dkg/pedpop/src/tests.rs:156-159 demonstrates correct orientation:
let (additional, blamed) = machine.blame(ONE, TWO, msg.clone(), blame.clone());
assert_eq!(blamed, ONE); // ONE = sender of the bad share to TWO
```

In `processor/src/key_gen.rs`, the call is `.blame(accuser, accused, ...)` where `accuser` occupies the `sender` position. In `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:582`):

```rust
let share_bytes = self.encryption.decrypt_with_proof(sender, recipient, msg, proof)?;
// decrypt_with_proof verifies msg.pop against pop_challenge(context, ..., from = accuser, msg)
```

`pop_challenge` appends `sender.to_bytes()` into the transcript (`encryption.rs:317`), so a share whose PoP was generated by the real sender (`accused`) fails verification when `from = accuser` → `DecryptionError::InvalidSignature` → `blame_internal` returns `sender` = `accuser` (`lib.rs:585`). Then `key_gen.rs:559-563` returns `ProcessorMessage::Blame { participant: accuser }`, fatally slashing the honest reporter while the malicious sender goes unpunished.
