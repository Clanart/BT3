## Title
Path-containment check in `resolveWithin()` uses a bare string-prefix comparison, allowing an attacker-controlled repo file/symlink to be treated as "inside" the repository when it actually resolves to a sibling directory — (File: `app/src/lib/path.ts`)

### Summary
`_resolveWithin()` is Desktop's shared guard used to make sure a repository-relative path never escapes the repository root before the app reads its contents. The final check, `realResolved.startsWith(realRoot)`, is a raw string-prefix test with no path-separator boundary. Any directory on disk whose name has the repository root as a *string prefix* (e.g. `…/GitHub/myrepo-secret` vs. root `…/GitHub/myrepo`) is incorrectly accepted as "within" the root. Combined with a symlink committed by an attacker-controlled/cloned repository, this lets Desktop read and exfiltrate file contents from outside the repository.

### Finding Description
`resolveWithin()` (used cross-platform) delegates to `_resolveWithin()`: [1](#0-0) 

```
  const resolved = resolve(normalizedRoot, normalizedRelative)
  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)
  return realResolved.startsWith(realRoot) ? resolved : null
```

This is the same class of bug as the report's boundary defect: a guard that is supposed to enforce "must be equal to or nested under X" is implemented with a comparison that has no boundary discipline (there `<` vs `<=` on an exact-percentage total; here `startsWith` with no separator check). `"/Users/victim/Documents/GitHub/myrepo-evil".startsWith("/Users/victim/Documents/GitHub/myrepo")` is `true` even though `myrepo-evil` is a sibling directory, not a subdirectory, of `myrepo`.

This helper is the sole containment guard used by `buildConflictContext()` when GitHub Desktop's Copilot merge-conflict-resolution feature reads conflicted files off disk before sending their contents to the Copilot backend: [2](#0-1) 

`workingDirectory` is the repository root (attacker can fully control the repo's name and layout when the user clones or opens it), and `file.path` is a repository-relative path taken from git's conflicted-file list, which an attacker can make a symlink (committed as a normal blob with symlink mode). The same primitive is reused for opening files from GitHub Desktop URL handlers: [3](#0-2) 

### Impact Explanation
If a victim has two adjacent directories where one repository's root path is a string-prefix of a sibling path (a very common layout — e.g. `~/Documents/GitHub/project` and `~/Documents/GitHub/project-private`, or any two repos cloned into the same base folder where one name prefixes another), an attacker who controls the *first* repository (e.g. via a symlinked file committed in a cloned/fetched repo) can:
1. Commit a symlink such as `leak -> ../project-private/secrets.env` inside `project`.
2. Trigger a merge/rebase/cherry-pick conflict that includes `leak` as a "conflicted" path (or otherwise get it read via any caller of `resolveWithin`).
3. `resolveWithin()` calls `realpath()` on the symlink, producing `.../project-private/secrets.env`, and the `startsWith(realRoot)` check on `.../project` incorrectly returns `true`.
4. `buildConflictContext()` then `stat()`s and `readFile()`s that path and includes its content in the payload sent to the Copilot conflict-resolution API — reading and exfiltrating a file outside the intended repository boundary over the network.

This satisfies the "file read outside the repo" / "credential exfiltration" impact class from an attacker-controlled cloned/fetched repository, without any local/admin access or prior malware.

### Likelihood Explanation
Exploitability depends on there being a sibling path on disk whose name is a superstring of the victim repository's path (not merely a subdirectory). This is a real-world layout pattern (organizations frequently clone `repo` and `repo-private`/`repo-secrets`/`repo2` side by side), but it is not guaranteed for every victim, so likelihood is data-dependent rather than universal — still realistic enough that the guard should not silently rely on unbounded prefix matching, and the existing test suite in `app/test/unit/path-test.ts` does not cover this specific sibling-prefix scenario, so the gap is unnoticed.

### Recommendation
Fix the boundary check in `_resolveWithin()` to require an exact match or a match followed by the platform path separator, e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + sep)
  ? resolved
  : null
```
using the appropriate `sep` from the `options` argument (`Path.sep`, `Path.posix.sep`, or `Path.win32.sep`) so POSIX and Windows variants are both corrected.

### Proof of Concept
1. Create `~/Documents/GitHub/project` and `~/Documents/GitHub/project-secret/secrets.txt`.
2. Inside `project`, add a symlink `leak -> ../project-secret/secrets.txt` and commit it.
3. Create a merge/rebase conflict in `project` that lists `leak` among the conflicted files (or any code path invoking `resolveWithin(workingDirectory, 'leak')` with `workingDirectory = '.../project'`).
4. Observe that `resolveWithin` returns a non-null path (because `realpath('.../project-secret/secrets.txt').startsWith(realpath('.../project'))` is `true`), and `buildConflictContext()` reads `secrets.txt` and includes it in the Copilot request payload — content from outside the repository is exfiltrated to the network.
