### Title
Hookify PreToolUse/Stop hooks fail open (silently bypass block rules) on any unhandled exception - (File: plugins/hookify/hooks/pretooluse.py)

### Summary
The external report describes a class of bug where a security-relevant operation (`transfer()`) can silently fail without reverting or signaling failure, causing the caller to believe the operation succeeded/failed correctly when it didn't — resulting in unintended, unchecked outcomes. The closest reachable analog in this codebase is not a token transfer but a **security control**: the `hookify` plugin's `PreToolUse`/`Stop` hook executors are the mechanism used to block dangerous operations (e.g., `rm -rf`, credential edits), but they are explicitly coded to swallow *any* exception and always exit `0` (allow), meaning a block/deny decision can be silently dropped instead of surfaced, letting the guarded operation proceed unchecked.

### Finding Description
`plugins/hookify/hooks/pretooluse.py` wraps the entire rule-evaluation path (`load_rules()` → `RuleEngine().evaluate_rules()`) in a `try/except Exception` that on any failure just emits a `systemMessage` and, in a `finally` block, unconditionally calls `sys.exit(0)`: [1](#0-0) 

The same fail-open pattern exists in `plugins/hookify/hooks/stop.py` (Stop hook, used to enforce completion checks) and `plugins/hookify/hooks/posttooluse.py`: [2](#0-1) [3](#0-2) 

The evaluation path itself is attacker/user-influenced: rules are loaded from `.claude/hookify.*.local.md` files and matched against `tool_input` fields (e.g., `command`, `file_path`, `new_text`) via regex, in `RuleEngine._check_condition` / `_regex_match`: [4](#0-3) [5](#0-4) 

Per `plugins/hookify/README.md`, this is the documented mechanism for **blocking destructive operations** (e.g. `action: block` on `rm -rf`, credential file edits): [6](#0-5) 

If rule evaluation throws for any reason not covered by the narrow exception handling inside `_extract_field`/`_regex_match` (e.g., a malformed `hookify.*.local.md` rule file causing a `KeyError`/`AttributeError` in `Condition.from_dict`, an unusual `tool_input` shape, or any other unexpected exception in `config_loader.load_rules`), the hook does not deny/block — it swallows the exception and exits `0`, which is the "allow" exit code. This mirrors the reported bug class: a function meant to enforce a guarantee (deny/block a dangerous action, analogous to `transfer()` returning a success indicator) instead fails silently, and the silent failure resolves to the permissive/unsafe outcome (operation proceeds) rather than the safe outcome (operation blocked), with the caller (Claude Code's tool-execution pipeline) having no way to detect that the intended block rule never fired.

### Impact Explanation
This is a hook-bypass condition on a project's own configured guardrails: an unprivileged user (or malicious/incorrectly-formed rule content, or malformed data reaching the rule matching code) can cause the hookify block/deny logic to silently fail open, allowing destructive Bash commands (`rm -rf`, `dd`, etc.) or sensitive-file edits that the user explicitly configured to be blocked, to execute anyway. Because the failure is swallowed and reported only via a generic `systemMessage`, there is no hard failure signal that would alert an operator that their safety rule stopped functioning — this is directly analogous to the "unusable/loses guarantee silently" impact called out in the report, except here the asset at risk is command-execution/file-write safety guarantees rather than token transfers.

### Likelihood Explanation
Moderate. The exception handling inside `RuleEngine` is narrow (only `re.error`, specific I/O errors for transcript reading), so most attacker/user-triggerable failure modes (malformed frontmatter, unusual `tool_input` shapes, encoding issues in rule files, etc.) are not caught at the point of failure and will propagate up to the hook's outer `except Exception` → fail-open path. This is easily triggerable by anyone who can place or edit a `.claude/hookify.*.local.md` rule file (a normal, documented, unprivileged user workflow via `/hookify`), and is also explicitly, deliberately coded ("ALWAYS exit 0 — never block operations due to hook errors"), so it is a design decision not merely a slip — but it still constitutes a fail-open trust-boundary weakness for a component whose entire purpose is enforcing "block" decisions.

### Recommendation
For `action: block` rules specifically, do not fail open on unexpected exceptions. Distinguish between "no rules matched" (allow) and "rule evaluation errored" (should default to a safe/blocking decision, or at minimum surface a hard, visible error rather than a silently-swallowed `systemMessage` with an allow exit code). Widen and make explicit the exception handling in `RuleEngine`/`config_loader` so that malformed rule files fail loudly at load time (e.g., reject the malformed rule but continue evaluating well-formed ones) instead of causing the entire hook invocation to fall through to "allow everything."

### Proof of Concept
1. Create `.claude/hookify.block-rm.local.md` with a valid `block` rule for `rm -rf` as documented in `plugins/hookify/README.md` (lines 152-169).
2. Craft a second rule file `.claude/hookify.broken.local.md` with a frontmatter `conditions` entry missing a required field or of malformed type (e.g., `conditions: "not-a-list"` or a condition dict missing `field`), causing `Condition.from_dict` / `Rule.from_dict` (in `plugins/hookify/core/config_loader.py`, lines 44-84) to raise on load.
3. Trigger a `Bash` tool call with command `rm -rf /tmp/test`.
4. Because `load_rules()` raises while parsing the broken rule file, `pretooluse.py`'s outer `except Exception` catches it, emits a `systemMessage`, and unconditionally `sys.exit(0)`s (allow) — meaning the `rm -rf` block rule that was correctly configured never gets evaluated, and the destructive command is permitted to run despite the user's explicit block configuration.

*Note: I was not able to directly execute this PoC (no filesystem/terminal access in this mode) or fully audit every exception path in `config_loader.py`'s YAML/frontmatter parsing for confirmation that a malformed file raises an uncaught exception rather than being caught internally; this should be validated by a background agent with repo/tool access before treating this as fully confirmed.*

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```

```python
    def _check_condition(self, condition: Condition, tool_name: str,
                        tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> bool:
        """Check if a single condition matches.

        Args:
            condition: Condition to check
            tool_name: Tool being used
            tool_input: Tool input dict
            input_data: Full hook input data (for Stop events, etc.)

        Returns:
            True if condition matches
        """
        # Extract the field value to check
        field_value = self._extract_field(condition.field, tool_name, tool_input, input_data)
        if field_value is None:
            return False

        # Apply operator
        operator = condition.operator
        pattern = condition.pattern

        if operator == 'regex_match':
            return self._regex_match(pattern, field_value)
        elif operator == 'contains':
            return pattern in field_value
        elif operator == 'equals':
            return pattern == field_value
        elif operator == 'not_contains':
            return pattern not in field_value
        elif operator == 'starts_with':
            return field_value.startswith(pattern)
        elif operator == 'ends_with':
            return field_value.endswith(pattern)
        else:
            # Unknown operator
            return False
```

```python
    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
```
