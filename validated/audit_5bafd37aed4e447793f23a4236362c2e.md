### Title
Stale line-selection indices are silently reapplied to a freshly re-fetched diff during staging, corrupting partial commits - (File: `app/src/lib/git/apply.ts`)

### Summary
`TreasuryAction._executeRebalance()`'s bug is a "before" value computed one way and an "after" value computed a different (fresher) way, with no re-validation that the two are comparable. The same broken invariant — comparing/consuming a value against a *different, later snapshot* of the same object without revalidating that the snapshot still matches — exists in Desktop's partial-commit staging path: `applyPatchToIndex` re-fetches the diff from disk right before building the patch, but reuses `file.selection`, a `DiffSelection` built earlier from a *different* diff, indexing purely by line offset. [1](#0-0) 

### Finding Description
When a user partially stages/commits a file, the `WorkingDirectoryFileChange.selection` (a `DiffSelection` bitmap keyed by absolute line index) is computed against the diff that was rendered in the UI at selection time. Later, during `stageFiles()` → `applyPatchToIndex()`, Desktop does **not** reuse that diff. Instead it calls `getWorkingDirectoryDiff(repository, file)` again, fetching a brand-new diff straight from `git diff`: [2](#0-1) 

It then calls `formatPatch(file, diff)`, which walks the **new** diff's hunks/lines and asks `file.selection.isSelected(absoluteIndex)` — an index computed from the **new** diff — using a selection bitmap that was built from the **old** diff: [3](#0-2) 

There is no check that the new diff's hunk layout, line count, or content still matches what the user actually selected. Desktop is aware this "diff might have changed dramatically since last we loaded it" — that exact comment exists in the UI-refresh path (`updateChangesWorkingDirectoryDiff`) — but that safeguard only clamps *selectable* lines for re-rendering; it is never invoked before `stageFiles`/`applyPatchToIndex` builds the actual commit patch: [4](#0-3) 

So exactly like the Notional bug — where `totalUnderlyingValueBefore` and `totalUnderlyingValueAfter` are computed via two different code paths of `getExchangeRateView()` and compared without accounting for the discrepancy — Desktop compares/consumes an index computed against diff-snapshot-A using a selection bitmap built against diff-snapshot-B, with no guard ensuring A and B are structurally identical.

### Impact Explanation
If the working tree file changes between the moment the user makes their line/hunk selection in the Changes view and the moment `_commitIncludedChanges`/`stageFiles` actually runs `applyPatchToIndex` (e.g. a smudge/clean filter, `.gitattributes` text-normalization, a file-system watcher, a build tool, or an editor autosave rewrites the file in that window), the hunk boundaries and absolute line indices shift. `isSelected(absoluteIndex)` will then pick the wrong lines from the *new* diff — silently including lines the user intended to exclude, or excluding lines the user intended to include — and `git apply --cached` will apply that mismatched patch to the index without error (the line offsets are still internally consistent, just semantically wrong). This is a silent corruption of the content of what the user commits, one of the explicitly in-scope impacts.

### Likelihood Explanation
This requires no privileged access — only that the working copy changes between diff-render time and stage time, which can happen from ordinary background activity (autosave, formatter-on-save, git attributes causing line-ending rewrite, external process). Desktop's own architecture already anticipates this race (see the "diff might have changed dramatically" comment) but only handles it for the read/redisplay path, not for the write/patch-generation path in `apply.ts`, making this analogous to the "viable but not certain" medium-severity characterization of the original finding — the window is real but narrow, and the corruption is silent rather than a crash.

### Recommendation
Use the same diff object (or re-derive/validate the selection against a freshly-diffed structure) for both display and staging: either pass the diff used for selection into `applyPatchToIndex`, or re-validate `file.selection` against the newly-fetched diff's hunks (reusing the existing "remap selectable lines" logic from `app-store.ts`) before calling `formatPatch`, and abort/re-prompt the user if the diff has structurally changed since selection.

### Proof of Concept
1. Open a large modified file in Desktop's Changes view and partially select a subset of lines for commit (leave others unselected).
2. Before clicking "Commit", trigger a change to the file that shifts line numbers without altering the file's on-disk mtime check that Desktop relies on for its own diff cache invalidation — e.g. a background formatter, an editor auto-save, or a `.gitattributes`/smudge filter reprocessing the file.
3. Click "Commit". `applyPatchToIndex` calls `getWorkingDirectoryDiff` again (`app/src/lib/git/apply.ts:60`), producing hunks with shifted `unifiedDiffStart` offsets.
4. `formatPatch` (`app/src/lib/patch-formatter.ts:143-157`) applies the stale `file.selection.isSelected(absoluteIndex)` bitmap against the new hunk layout — the resulting patch stages/omits different lines than what the user visually selected, and `git apply --cached` commits this silently without any warning to the user.
