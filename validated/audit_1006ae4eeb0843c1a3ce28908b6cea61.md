### Title
Unbounded CW721 pagination loop in the `solo` precompile's `ClaimSpecific` lets a large NFT balance permanently DoS a legacy-account fund claim - ([File: precompiles/solo/solo.go])

### Summary
The `solo` precompile's `ClaimSpecific` handler migrates funds from a pre-association ("legacy") Cosmos account to a newly-associated EVM account. When the claimed asset is a CW721 collection with no specific token ID given, the executor paginates through *every* NFT the legacy account owns via repeated `QuerySmartSafe` calls, accumulates all token IDs in memory, and then executes a `transfer_nft` message for each one — all inside a single EVM call. There is no cap on the number of tokens processed.

### Finding Description
In `ClaimSpecific`, for a CW721 asset with an empty `Denom` (i.e., "claim all my NFTs from this collection"), the code runs an unbounded pagination loop: [1](#0-0) 

This loop has no iteration cap, no gas pre-check, and no limit on `allTokens` length. It queries the CW721 contract page-by-page (`start_after`) until it sees an empty page, then executes a `transfer_nft` wasm message for *every* token found. All of this happens synchronously within one precompile call and one EVM transaction, which is subject to the block gas limit — exactly the same bug class as TRST-H-5's `_calculateMaxVotePossible()`/`getTotalVotingPower()`, which looped over every veSatin NFT and could exceed the max gas permitted in a block.

The `sender` account whose NFTs are enumerated is derived from a signed legacy `MsgClaim`/`MsgClaimSpecific` transaction that the claimer controls and must have signed themselves: [2](#0-1) 

Since this is a pre-association (never touched EVM) account, an attacker (or even a normal power user) could have accumulated a very large number of CW721 tokens in that account (e.g. via cheap mints, airdrops, or simply operating a bot that holds many NFTs) prior to migrating to EVM. Once the number of tokens exceeds what fits in a single block's gas budget for the wasm queries + wasm executes + associated precompile overhead, `ClaimSpecific` for that CW721 asset will *always* revert, with no way to specify a smaller/partial claim (the empty-`Denom`/"claim all" code path provides no pagination or batching parameter to the caller — `asset.GetDenom()` either names one specific token or triggers "claim everything").

This differs from `withdrawMultipleDelegationRewards`-style loops elsewhere in the precompiles (distribution precompile), where the loop bound (`validators := args[0].([]string)`) is directly caller-supplied and caller-choosable, so the caller can always split the call into smaller batches. Here, the loop bound (number of owned NFTs) is *not* controllable by the caller at call time — it is a fixed property of on-chain state (their legacy account's holdings), and the "claim all" code path offers no smaller granularity than "all tokens in the collection."

### Impact Explanation
If a legacy account holds more CW721 tokens than fit within a block's gas limit for this loop's wasm query+execute overhead, that account's `ClaimSpecific(..., CW721, denom="")` call becomes permanently un-executable — the NFTs (and hence any transfer of ownership to the new EVM-associated account) are frozen forever via this precompile. This matches the "permanent freezing" impact criterion. It does not achieve a global protocol-wide DoS (like TRST-H-5 did for governance/voting), so the blast radius is scoped to affected legacy accounts with large NFT holdings using this specific migration path, but the freezing for those accounts is permanent and reachable purely through a single transaction/precompile call.

### Likelihood Explanation
Reaching this path requires: (1) a pre-existing legacy (non-EVM-associated) Cosmos account, (2) that account holding a sufficiently large number of CW721 tokens in a single collection, and (3) the account owner (or anyone who can produce the required signature over the legacy account) invoking `solo.claimSpecific` with the CW721 asset's `Denom` left empty. Because tests and integration specs (`SeiSoloTest.js`) show `ClaimSpecific` is an intended, user-reachable end-to-end migration flow, and nothing in the code enforces an upper bound on `allTokens`, this is straightforward to trigger deliberately (self-DoS as a griefing/documentation-issue) or accidentally for legitimate large NFT holders. It requires no validator collusion, no governance, and no privileged access — only ordinary EVM transaction submission.

### Recommendation
Bound the CW721 enumeration and transfer loop, e.g.:
- Add a `startAfter`/pagination parameter to the `ClaimSpecific` ABI so a caller can claim NFTs in bounded batches across multiple transactions, rather than requiring "claim all in one call."
- Alternatively, cap the number of tokens processed per call (e.g., process up to N tokens per invocation and return/emit which tokens remain), mirroring the mitigation applied to TRST-H-5 where system-wide totals were replaced with an O(1) cached lookup — here the fix is analogous but different in kind: replace "all-at-once" with paginated/batched claims, since the number of owned NFTs is inherently unbounded caller-side state.
- Add an explicit gas or count pre-check that fails fast/returns a clear error before attempting a huge pagination + execute loop, rather than letting the whole call run out of gas deep into execution.

### Proof of Concept
1. Prior to associating a Cosmos account with an EVM address, mint or acquire a very large number of CW721 tokens (e.g., 5,000+) in one collection to that account (feasible since CW721 minting itself is a normal wasm message, unbounded by anything at the account level).
2. Associate an EVM address for a *different* signer that will act as the claimer, per the `solo` precompile's claim flow.
3. Construct and sign a legacy `MsgClaimSpecific` (from the CW721-holding legacy account) naming the CW721 contract with an empty `Denom` (i.e., "claim all tokens").
4. Call `solo.claimSpecific(txBytes)` on the EVM precompile at `0x100C` (see `precompiles/solo/solo.go` `SoloAddress`).
5. Observe that the call attempts a `for {}` pagination loop over `QuerySmartSafe` plus one `wasmKeeper.Execute` (`transfer_nft`) per token — with enough tokens, the transaction exceeds the block gas limit and reverts every time it's retried, regardless of the gas limit provided (bounded by the block's total gas limit), permanently blocking the claim for that CW721 collection. [1](#0-0) 

**Note on confidence**: I was not able to fully verify the exact wasm-execute gas cost per NFT transfer, nor the exact configured block gas limit, from the indexed code, so the precise NFT-count threshold at which this becomes exploitable is not confirmed — this would need empirical benchmarking (e.g., via a Devin session with terminal access) to establish the concrete number of tokens required to trigger an unrecoverable out-of-gas revert in a live network configuration.

func (p PrecompileExecutor) validate(ctx sdk.Context, caller common.Address, args []interface{}, readOnly bool) (claimMsg, sdk.AccAddress, error) {
	if readOnly {
		return nil, nil, errors.New("cannot call send from staticcall")
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, nil, err
	}
	tx, err := p.txConfig.TxDecoder()(args[0].([]byte))
	if err != nil {
		return nil, nil, fmt.Errorf("failed to decode claim tx due to %w", err)
	}
	if len(tx.GetMsgs()) != 1 {
		return nil, nil, fmt.Errorf("claim tx must contain exactly 1 message but %d were found", len(tx.GetMsgs()))
	}
	claimMsg, ok := tx.GetMsgs()[0].(claimMsg)
	if !ok {
		return nil, nil, errors.New("claim tx can only contain MsgClaim or MsgClaimSpecific type")
	}
	if common.HexToAddress(claimMsg.GetClaimer()).Cmp(caller) != 0 {
		return nil, nil, fmt.Errorf("claim tx is meant for %s but was sent by %s", claimMsg.GetClaimer(), caller.Hex())
	}
	sender, err := sdk.AccAddressFromBech32(claimMsg.GetSender())
	if err != nil {
		return nil, nil, fmt.Errorf("failed to parse claim tx sender due to %s", err)
	}
	if err := p.sigverify(ctx, tx, claimMsg, sender); err != nil {
		return nil, nil, err
	}
	return claimMsg, sender, nil
