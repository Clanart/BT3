### Title
Unbounded Filter Creation via Public RPC Leads to Goroutine/Memory Exhaustion - ([File: node/cn/filters/api_kaia_filter.go])

### Summary
`eth_newFilter`, `kaia_newFilter`, `eth_newBlockFilter`/`kaia_newBlockFilter`, and `eth_newPendingTransactionFilter`/`kaia_newPendingTransactionFilter` are publicly reachable, unauthenticated RPC methods that create an entry in `FilterAPI.filters` plus a dedicated backing goroutine and event-system subscription, with **no per-connection or global cap** on the number of filters that can be created — unlike the WebSocket subscription path, which explicitly enforces `MaxSubscriptionPerWSConn` [1](#0-0) . This mirrors the CVE-2025-48041 bug class: an unauthenticated/low-privilege remote caller can repeatedly invoke a "create handle" RPC operation to exhaust server-side resources (goroutines, memory, subscriptions) because no throttling or limit exists on that specific allocation path.

### Finding Description
`NewFilterAPI` initializes an unbounded map with a mutex and no capacity check: [2](#0-1) 

Each of `NewFilter`, `NewBlockFilter`, and `NewPendingTransactionFilter` unconditionally inserts a new `filter` entry into `api.filters` and spawns a dedicated goroutine plus event-system subscription on every call, with no check against `len(api.filters)` or any maximum: [3](#0-2) [4](#0-3) 

Filters are only reaped by a background `timeoutLoop` that runs every 5 minutes and deletes filters that have not been polled via `GetFilterChanges` within `defaultFilterDeadline` (5 minutes): [5](#0-4) [6](#0-5) 

Contrast this with the WebSocket subscribe path (`eth_subscribe`/`kaia_subscribe`), which explicitly caps subscriptions per connection via `MaxSubscriptionPerWSConn` before installing a new subscription: [7](#0-6) 

No equivalent cap exists for the filter-creation methods (`NewFilter`/`NewBlockFilter`/`NewPendingTransactionFilter`), which are exposed on the public `eth`/`kaia`/`klay` RPC namespaces and reachable over HTTP RPC (not just WebSocket), so the 5-minute retention window and per-connection subscription limit do not apply. Because HTTP RPC calls are typically not persistent per-connection state (unlike a WS connection), an attacker can fire an unbounded number of `eth_newFilter`/`eth_newBlockFilter`/`eth_newPendingTransactionFilter` calls from a single IP (or many) in rapid succession; each call keeps a live goroutine, an event-system subscription (channel + registration in `EventSystem`), and a map entry alive for up to 5 minutes regardless of caller identity or connection count.

### Impact Explanation
Every unauthenticated RPC caller can trigger allocation of goroutines, channels and `EventSystem` subscriptions without any built-in ceiling, unlike the WS subscribe path. Sustained abuse drives up goroutine count and memory, and increases mutex contention on `filtersMu`/the event system's internal lock, degrading or denying RPC service availability for the node (public RPC / gasless / auction bidder / tx sender endpoints depend on the same node process). This maps to the CVE-2025-48041 class ("Allocation of Resources Without Limits" leading to Excessive Allocation/Flooding) — the impact is node-level service degradation rather than direct value theft, but it is reachable by any public, unprivileged RPC caller and has no throttling, matching the "public RPC caller" reachable surface allowed by the rules.

### Likelihood Explanation
High likelihood: no authentication, no rate limiting, and no per-caller/per-connection cap exist on this specific set of RPC methods; a single script issuing many `eth_newFilter` (or `eth_newBlockFilter`/`eth_newPendingTransactionFilter`) calls in a loop is sufficient to trigger continuous resource growth, capped only by the 5-minute idle-timeout reaper.

### Recommendation
Enforce a maximum number of concurrently live filters per API instance (and ideally per caller/IP or per connection), mirroring the existing `MaxSubscriptionPerWSConn` pattern used for WebSocket subscriptions, before inserting a new entry into `api.filters` in `NewFilter`, `NewBlockFilter`, and `NewPendingTransactionFilter`. Reject filter creation with an RPC error once the limit is reached, and/or reduce `defaultFilterDeadline` for filters that have never been polled, and/or apply RPC-level rate limiting to these methods.

### Proof of Concept
1. Start a Kaia node with the RPC HTTP API enabled and the `eth`/`kaia` namespace exposed (default configuration for public RPC nodes).
2. From an unauthenticated client, repeatedly call `eth_newFilter` (or `eth_newBlockFilter`, `eth_newPendingTransactionFilter`) in a tight loop, e.g.:
```
for i in $(seq 1 100000); do
  curl -s -X POST --data '{"jsonrpc":"2.0","method":"eth_newBlockFilter","params":[],"id":1}' http://NODE:8551
done
```
3. Each call inserts an entry into `api.filters` and starts a new goroutine/subscription with no cap check [8](#0-7) , unlike the WS `eth_subscribe` path which would reject once `MaxSubscriptionPerWSConn` is hit [1](#0-0) .
4. Observe growing goroutine count / memory usage on the node process until the 5-minute `defaultFilterDeadline` reaper runs, and repeat faster than the reaper can clean up to sustain resource growth indefinitely.

```go
// timeoutLoop runs every 5 minutes and deletes filters that have not been recently used.
// It is started when the api is created.
func (api *FilterAPI) timeoutLoop() {
	var toUninstall []*Subscription
	ticker := time.NewTicker(api.timeout)
	defer ticker.Stop()
	for {
		<-ticker.C
		api.filtersMu.Lock()
		for id, f := range api.filters {
			select {
			case <-f.deadline.C:
				toUninstall = append(toUninstall, f.s)
				delete(api.filters, id)
			default:
				continue
			}
		}
		api.filtersMu.Unlock()

		// Unsubscribes are processed outside the lock to avoid the following scenario:
		// event loop attempts broadcasting events to still active filters while
		// Unsubscribe is waiting for it to process the uninstall request.
		for _, s := range toUninstall {
			s.Unsubscribe()
		}
		toUninstall = nil
	}
```

```go
func (api *KaiaFilterAPI) NewPendingTransactionFilter() rpc.ID {
	var (
		pendingTxs   = make(chan []*types.Transaction)
		pendingTxSub = api.events.SubscribePendingTxs(pendingTxs)
	)

	api.filtersMu.Lock()
	api.filters[pendingTxSub.ID] = &filter{typ: PendingTransactionsSubscription, deadline: time.NewTimer(api.timeout), txs: make([]*types.Transaction, 0), s: pendingTxSub}
	api.filtersMu.Unlock()

	go func() {
		defer pendingTxSub.Unsubscribe()
		for {
			select {
			case pTx := <-pendingTxs:
				api.filtersMu.Lock()
				if f, found := api.filters[pendingTxSub.ID]; found {
					f.txs = append(f.txs, pTx...)
				}
				api.filtersMu.Unlock()
			case <-pendingTxSub.Err():
				api.filtersMu.Lock()
				delete(api.filters, pendingTxSub.ID)
				api.filtersMu.Unlock()
				return
			}
		}
	}()

	return pendingTxSub.ID
}

func (api *KaiaFilterAPI) NewBlockFilter() rpc.ID {

		headers   = make(chan *types.Header)
		headerSub = api.events.SubscribeNewHeads(headers)
	)

	api.filtersMu.Lock()
	api.filters[headerSub.ID] = &filter{typ: BlocksSubscription, deadline: time.NewTimer(api.timeout), hashes: make([]common.Hash, 0), s: headerSub}
```
