## Title
Webhook shop identity (`X-Shopify-Shop-Domain`) is not covered by HMAC verification, allowing cross-shop tenant confusion in `ShopifyApp::WebhookVerification` - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
The reported Frax bug class is about trusting an attacker-manipulable input (Uniswap spot price) to compute a security-relevant value (reward boost) without binding that input to the actor performing the action. The reachable analog in `shopify_app` is `ShopifyApp::WebhookVerification`, whose `shop_domain` helper returns the value of the `X-Shopify-Shop-Domain` request header without that header ever being covered by the webhook HMAC signature. The HMAC only authenticates the raw request body, so the shop-identity value returned to app code is attacker-controllable while still passing signature verification, enabling cross-shop tenant confusion for any app that follows the documented usage pattern.

### Finding Description
`ShopifyApp::PayloadVerification#hmac_valid?` computes the HMAC exclusively over `request.raw_post`: [1](#0-0) 

`ShopifyApp::WebhookVerification#verify_request` calls `hmac_valid?(data)` with `data = request.raw_post`, and separately exposes a `shop_domain` method that reads the unauthenticated `HTTP_X_SHOPIFY_SHOP_DOMAIN` header: [2](#0-1) 

Because the header is never part of the signed payload, any actor who can produce one valid `(body, HMAC)` pair signed with the app's secret (e.g., by triggering a genuine webhook event from their own installed shop) can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value pointing at a different (victim) shop. `verify_request` will still accept the request because it only checks the body's HMAC, not the header.

The `shop_domain` value returned by this concern is the officially documented mechanism for identifying the tenant in custom webhook controllers: [3](#0-2) 

This is directly analogous to the audited bug: a value that appears authoritative (it "came with" a validly-HMAC'd Shopify webhook) is actually attacker-influenced and used downstream for a security-relevant decision (which tenant/shop the webhook body applies to) without being cryptographically bound to that decision.

### Impact Explanation
Any application that follows the documented `shop_domain` pattern for custom webhook controllers/jobs is exposed to cross-shop tenant confusion: a malicious but otherwise unprivileged merchant (one who has installed the app on their own store, and is therefore able to trigger real webhook deliveries) can craft a forged request that is processed by the victim's tenant context (e.g., `Shop.find_by(shopify_domain: shop_domain)` followed by `shop.with_shopify_session`, as shown in the generator job templates using the same `shop_domain:` argument convention): [4](#0-3) 

This can lead to attacker-controlled webhook body content being processed under a victim shop's session/context (e.g. GDPR/redaction jobs, cart/order/product update jobs), i.e., cross-shop data or action injection triggered by an unrelated merchant's forged HTTP request.

### Likelihood Explanation
Medium: exploitation requires the attacker to obtain at least one valid `(body, HMAC)` pair, which is straightforward since the attacker can install the app on their own store and trigger genuine webhook events to capture a validly-signed body/HMAC, then replay it directly to the app's public endpoint with a substituted shop-domain header. No secrets need to be leaked; the app's shared webhook secret is not per-shop, so this works against any tenant using shared secret-based HMAC webhooks.

### Recommendation
- **Short term:** Do not treat `X-Shopify-Shop-Domain` (or any other unsigned header) as an authoritative source of tenant identity. Derive the shop from data that is inside the HMAC-signed payload, or cross-check the header against a shop identity retrieved through an authenticated channel (e.g., the resource IDs in the signed body combined with a lookup that doesn't blindly trust the header).
- **Long term:** Update `ShopifyApp::WebhookVerification`/documentation to warn against using `shop_domain` for authorization/tenant-scoping decisions, and consider extending HMAC verification (or requiring `ShopifyAPI::Webhooks::Request`'s own topic/shop resolution, which should be audited for the same header-trust issue) to bind the shop identity into what is verified.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`.
2. Trigger a real webhook (e.g. `carts/update`) to capture the exact `raw_post` body and its valid `X-Shopify-Hmac-Sha256` value signed with the app's secret.
3. Replay this captured request directly to the app's custom webhook endpoint (built following `docs/shopify_app/webhooks.md`'s pattern using `ShopifyApp::WebhookVerification`), replacing only the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
4. `verify_request` passes (HMAC only checks body), `shop_domain` returns `"victim-shop.myshopify.com"`, and the app's job/controller processes the attacker-supplied body under the victim shop's tenant context.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),

class CustomWebhooksController < ApplicationController

    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
