### Title
`addr` precompile `associate()` accepts an unbound signature over arbitrary attacker-supplied text, allowing replay of a victim's unrelated off-chain signature to force address association - (File: precompiles/addr/addr.go)

### Summary
The `associate` method of the `addr` precompile (address `0x...1004`) recovers an EVM/Sei address pair and pubkey from a raw `(v, r, s)` signature over a caller-supplied `customMessage` string, with no domain separation binding the signature to the association action, the target chain, or the precompile itself. [1](#0-0) 

### Finding Description
`associate()` takes `v`, `r`, `s`, and `customMessage` directly from the caller, hashes `customMessage` with `crypto.Keccak256Hash`, and recovers `evmAddr`/`seiAddr`/`pubkey` from that hash and the signature via `helpers.GetAddresses`. [2](#0-1) 
Unlike the ID-token flow in the analog Jenkins OIDC bug — where the `aud` claim should scope a signed credential to the specific relying party/action it was issued for — nothing here ties the signature to the "association" purpose: the precompile does not enforce a fixed message template, a chain ID, the precompile address, or any other domain separator inside `customMessage` before hashing and recovering the key. `associate` merely checks that the derived Sei address is not already associated before calling `AssociateAddresses`. [3](#0-2) 

Because any third party (not the key holder) can call this method with `customMessage` and `(v,r,s)` values, **any signature the victim has produced over any known plaintext** — e.g., an off-chain order signature, a different dApp's `personal_sign` login message, or any other publicly disclosed message the victim ever signed with the same key — can be repurposed here as an "association" signature, as long as the attacker knows the exact plaintext. There is no mechanism analogous to an audience/purpose claim requiring the signed payload to have been intended specifically for Sei-EVM address association.

This is the same bug class the codebase's own EIP-7702 pre-association logic explicitly guards against: `AuthorityToPreAssociate` and `associateAuthorizationAuthorities` were hardened specifically because "a publicly-visible authorization a user signed for another chain... could be replayed in a sponsored Sei SetCode tx to force-associate the victim — migrating their direct-cast balance and orphaning staking/distribution state." [4](#0-3) 
That fix added chain-ID and cross-checking constraints for the SetCode authorization path, but the `addr` precompile's `associate()` entry point (and its many legacy versions) still lacks any equivalent domain/purpose binding on `customMessage`.


### Impact Explanation
Forced association permanently and irreversibly links a victim's EVM address to their Sei address without their consent, triggering the same balance-migration/state-relocation behavior the codebase's own comments describe as dangerous for the SetCode authority case (migrating a direct-cast balance and orphaning staking/distribution state). An attacker who can obtain any signed message from a victim (many of which are routinely broadcast publicly, e.g., signed orders, off-chain approvals, or messages from other dApps) can force this association at a time and in a manner the victim never intended, potentially causing loss of access to funds tied to the previous unassociated state or unauthorized migration of value between address spaces.

### Likelihood Explanation
This is reachable by any unprivileged EVM caller with no special permissions: a plain `associate(v, r, s, customMessage)` call to the public precompile address `0x1004` is enough, given knowledge of a signature/plaintext pair from the victim. Users routinely sign many messages off-chain (wallet logins, meta-tx approvals, exchange orders), so a supply of eligible signatures is plausible in practice. Note: I was unable to fully verify within the available context whether `AssociateAddresses` (in `utils/helpers/associate.go`) performs the same balance-migration behavior called out in the SetCode comment, or whether some other check elsewhere (e.g., a fixed prefix enforced client-side only) mitigates this — that would need direct inspection of `utils/helpers/associate.go` to confirm the exact consequences of a forced association.

### Recommendation
Bind the association signature to its intended purpose the same way the SetCode authorization path now does: require `customMessage` to match a canonical, precompile-enforced template that embeds the chain ID and a fixed association-specific magic string/prefix, and reject the call if the supplied message does not match that exact template, rather than trusting whatever plaintext the caller provides.

### Proof of Concept
Conceptually (not verified against a live deployment, since only static analysis was available):
1. Victim signs any message `M` off-chain for an unrelated purpose (e.g., a login challenge for a third-party site) with their EVM key.
2. Attacker observes `(v, r, s)` and `M` (often public, e.g., leaked via a compromised or malicious dApp, or a public order book).
3. Attacker calls `associate(v, r, s, M)` on the `addr` precompile at `0x0000000000000000000000000000000000001004`. [5](#0-4) 
4. `helpers.GetAddresses` recovers the victim's `evmAddr`/`seiAddr`/`pubkey` from `keccak256(M)` and the signature, and `associateAddresses` permanently links them, with no verification that `M` was ever intended for this action. [6](#0-5)

func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)

func (p PrecompileExecutor) associateAddresses(ctx sdk.Context, method *abi.Method, evmAddr common.Address, seiAddr sdk.AccAddress, pubkey cryptotypes.PubKey) (ret []byte, remainingGas uint64, err error) {
	// Check that address is not already associated
	_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if found {
		return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
	}

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)
	err = associationHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
