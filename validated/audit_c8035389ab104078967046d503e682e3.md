## Analysis

The Tron build of the IntentGateway reimplements ERC-20 transfers with a raw low-level `.call()` instead of OpenZeppelin's `SafeERC20`, and only checks that the *call itself* did not revert — it never decodes or validates the ERC-20 `bool` return value. This is the exact bug class from the seed report, reintroduced in escrow-redemption/refund logic that moves bridged funds. [1](#0-0) 

Compare this to the canonical (non-Tron) implementation, which correctly uses `SafeERC20.safeTransfer`, which decodes and asserts the returned boolean (or absence of return data per EIP-20 ambiguity): [2](#0-1) 

### Title
Unchecked ERC-20 `transfer()` return value in Tron IntentGateway escrow withdrawal/refund/dust-sweep - (`evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` and `onAccept`'s `SweepDust` handler on the Tron build move escrowed tokens using a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` and only check that the low-level `call` did not revert (`success`). They never inspect the ABI-decoded boolean return value that ERC-20's `transfer()` is specified to return. Any token whose `transfer()` returns `false` on failure instead of reverting (a well-known class of real, non-malicious tokens, e.g. legacy tokens that follow the letter of ERC-20 but not the "revert on failure" convention) will cause this code to treat a failed transfer as successful.

### Finding Description
In `withdraw()`: [3](#0-2) 

the escrow accounting `_orders[body.commitment][token] -= amount;` and the terminal state `_filled[body.commitment] = beneficiary;` are updated unconditionally once `success` (the low-level call outcome) is true — regardless of whether `token.transfer()` actually returned `true`. The same unchecked pattern appears in the `SweepDust` handler: [4](#0-3) 

and again in the predispatch/fee-recovery path used during order placement/filling: [5](#0-4) 

Because `order.inputs[i].token` / `order.output.assets[i].token` are attacker-supplied addresses (any user can create an order denominated in an arbitrary ERC-20), an order creator can pick a token whose `transfer()` returns `false` on failure without reverting. When `withdraw()` is invoked from `onAccept`/`onGetResponse` (reachable via a normal `RedeemEscrow`/`RefundEscrow` cross-chain message — no privileged actor required), if the transfer legitimately fails (e.g. token quirks, insufficient balance drift from rounding/dust accounting elsewhere in the same contract, or a token that returns `false` under specific edge conditions), the function still:
- decrements the escrow ledger as if funds were paid out,
- sets `_filled[commitment] = beneficiary`, permanently closing the order (no retry path),
- emits `EscrowReleased`/`EscrowRefunded` as if funds moved.

The beneficiary never receives the tokens, yet the protocol's bookkeeping says the obligation is settled and the commitment can never be redeemed again. This is functionally identical to the reported bug: "the return value of `transfer()` is not being processed, which can lead to incorrect operation of the smart contract."

### Impact Explanation
This breaks the required invariant that "escrowed assets ... must move exactly once and only to the rightful beneficiary and amount." A failed-but-unchecked transfer results in silent, permanent loss of the escrowed tokens (they remain locked in the contract, unclaimable, since `_filled`/`_orders` are already mutated to reflect a completed payout) with no way to recover or re-trigger the transfer. This is a fund-loss condition reachable through the ordinary settlement path, not through a malicious relayer/prover/admin — it only requires an ERC-20 whose `transfer()` can return `false` instead of reverting, a real-world token behavior, not a fabricated adversarial dependency.

### Likelihood Explanation
Likelihood is moderate: it requires a token used in the intent system to exhibit the "return false, don't revert" behavior on a failure path. Several real, widely used tokens historically implement `transfer` this way (e.g., ZRX and other pre-OpenZeppelin-era ERC-20s), and the intent system is generically token-agnostic (any ERC-20 can be specified as `order.inputs`/`order.output.assets`). The bug is also purely a code defect — the rest of the codebase (`IntentsBase.sol`, `EvmHost.sol`, `WrappedHyperFungibleToken.sol`) uses `SafeERC20.safeTransfer` correctly, confirming this Tron-specific reimplementation is the outlier and not an intentional divergence with equivalent safety.

### Recommendation
Replace all `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw`, `SweepDust` handling, and the predispatch dispatcher-transfer path) with `SafeERC20.safeTransfer`/`safeTransferFrom`, consistent with the rest of the codebase, so that both call failure and a decoded `false` return value revert the transaction rather than being silently accepted.

### Proof of Concept
1. Order creator deploys a custom ERC-20 `EvilToken` where `transfer()` returns `false` (without reverting) whenever some condition holds (e.g. `to == specificAddress`, or simply always for a subset of calls) but otherwise behaves like a normal ERC-20 for `transferFrom`/`balanceOf` so it passes the earlier `safeTransferFrom` deposit step.
2. Creator places an order using `EvilToken` as an input asset via `placeOrder`, funding escrow normally.
3. A solver fills the order; a cross-chain `RedeemEscrow` request eventually calls `onAccept` → `withdraw()` on the source chain to release the escrowed `EvilToken` to the solver's beneficiary address, and the token's `transfer()` returns `false` for that specific beneficiary.
4. `withdraw()`'s `token.call(...)` reports `success = true` (the call didn't revert) even though the ERC-20-level transfer failed; `_orders[commitment][token] -= amount` executes, `_filled[commitment]` is set, `EscrowReleased` is emitted.
5. The beneficiary's `EvilToken` balance is unchanged — the escrowed tokens are now stuck in the `IntentGatewayV2` contract with no state left that would allow a retry, since the commitment is marked filled and its escrow value is already zeroed.
