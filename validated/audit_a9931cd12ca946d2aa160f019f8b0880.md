### Title
Recursive precompile calls cause double-processing of bank events, desyncing EVM StateDB balances from the Bank keeper - (File: `precompiles/common/precompile.go`)

### Summary
The Tezos report flags that `handler.execute_call` tracks call-stack depth but fails to create an isolated "transaction data" layer per call, so nested calls can corrupt shared state. The Cosmos EVM analog is in `Precompile.runNativeAction`, which uses a `BeforeBalanceChange`/`AfterBalanceChange` pair keyed on the length of the *shared* `ctx.EventManager()` event slice (`prevEventsLen`) to translate bank module events into StateDB balance updates for a single precompile call [1](#0-0) . When a precompile call recursively/re-entrantly triggers another precompile call (contract calls back into a precompile, as demonstrated by `DebugPrecompileCaller.callback`), the inner call's `AfterBalanceChange` consumes and applies the event slice from `prevEventsLen(inner)` to the end. Execution then returns to the outer call, which applies its own `AfterBalanceChange` using `prevEventsLen(outer)` — a smaller index recorded *before* the inner call ran — over the *same shared* event manager, causing it to re-process the inner call's already-applied bank events a second time.

### Finding Description
`runNativeAction` records `prevEventsLen` from the shared `ctx.EventManager().Events()` before invoking the native action, and afterwards replays events `[prevEventsLen:]` into `stateDB.AddBalance`/`SubBalance` calls [2](#0-1) [3](#0-2) . Although a fresh `BalanceHandler` instance is created per call via the factory [4](#0-3) , the underlying event manager (`ctx.EventManager()`) is not scoped per call — it is the same shared event log across the whole transaction, including nested/recursive precompile invocations.

Call ordering for a recursive case:
1. Outer precompile call sets `prevEventsLenOuter = N`.
2. Outer's native action triggers a nested precompile call (re-entrant call, e.g. contract calling back into the precompile or another precompile emitting bank events on its behalf, as shown by the `debug` test precompile calling back via `CallEVMWithData` and by `StakingReverter`/ERC20-hook style recursive precompile call test contracts) [5](#0-4) .
3. The inner call sets `prevEventsLenInner = N + k` (k events emitted so far by outer before the recursive call), runs, emits its own bank events, and its `AfterBalanceChange` processes `events[N+k:]`, applying balance deltas to `stateDB` and returning.
4. Control returns to the outer native action, which finishes and calls `AfterBalanceChange` with `prevEventsLenOuter = N`. This reprocesses `events[N:]`, which includes the inner call's bank events that were **already applied to the StateDB by the inner call**.

This results in the same `CoinSpent`/`CoinReceived` (or precisebank fractional-balance) event being applied twice to the EVM `StateDB` via `AddBalance`/`SubBalance`, while the Bank keeper's ledger (the source of truth) only reflects the transfer once. This is exactly analogous to the Tezos issue: the "call stack" (nested precompile calls) is tracked only implicitly via a shared, unbounded event index rather than via an isolated, properly-scoped data layer per call frame, so state from an inner call leaks into and is duplicated by an outer call's post-processing.

The existing repository test `BalanceHandlerTestSuite.TestRecursivePrecompileCallsWithDebugPrecompile` explicitly documents this exact defect: "recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten... leads to balance desync between native bank keeper and EVM stateDB" [6](#0-5) .

### Impact Explanation
This breaks the 1:1 accounting invariant that must hold between native bank balances and the EVM `StateDB` view of balances mediated by precompiles (staking, distribution, ERC20, ICS20, gov, werc20, bank, slashing precompiles all use this same `BalanceHandlerFactory`/`RunNativeAction` path) [7](#0-6) . Double-applying `AddBalance` on a receiver inflates that account's EVM-visible balance beyond what the bank module actually holds/transferred, which is a form of unauthorized duplication of spendable value in the EVM balance view (Critical accounting corruption per the impact gate), reachable by any unprivileged user able to deploy/call a contract that triggers a nested precompile call.

### Likelihood Explanation
Triggering the corruption only requires an ordinary, unprivileged EVM transaction: deploy a contract that calls a bank-affecting precompile (staking delegate, distribution claimRewards, ICS20 transfer, ERC20 transfer, bank precompile) from within a call that itself was invoked from another precompile call or from a re-entrant/hook path (e.g., an ERC20 `_beforeTokenTransfer` hook that calls back into a precompile, as demonstrated by the existing `ERC20RecursiveReverting`/`ERC20RecursiveNonReverting` and `StakingReverter` test contracts, and the `DebugPrecompileCaller` recursive test) [8](#0-7) [9](#0-8) . No privileged role is needed.

I was unable to fully confirm, from the indexed code alone, whether `stateDB.GetCacheContext()`/`CommitWithCacheCtx()` fully isolates the event manager per nested call (which would negate the double-counting) or whether it is shared across the recursion depth as the existing repository test suite's naming and comments strongly suggest. The presence of a dedicated, purpose-built regression test (`balance_handler_test.go`) asserting this exact bug class, without an accompanying fix commit visible in the indexed snapshot, indicates this is a known, currently-tracked issue rather than a fully verified end-to-end exploit in this pass.

### Recommendation
Scope the event-index tracking (or better, the entire event manager) to each individual precompile call frame rather than to the shared transaction-wide `ctx.EventManager()`. Concretely: use `ctx.WithEventManager(sdk.NewEventManager())` before invoking the native action in `runNativeAction` so each precompile call (including nested/recursive ones) only sees and processes events it itself emitted, then propagate those events back up to the parent's event manager after processing (via `EmitEvents`) without letting the parent re-scan the child's already-applied event range. This mirrors the Tezos fix's recommendation of creating an isolated "transaction data" layer per call rather than relying on a single shared counter/depth marker.

### Proof of Concept
Conceptual PoC (mirrors the existing `TestRecursivePrecompileCallsWithDebugPrecompile`):
1. Deploy a contract that, within one EVM call, invokes a bank-state-changing precompile (e.g., `staking.delegate` or `bank` send) and, from inside that precompile call's native action, causes another nested precompile call that also emits bank events (e.g., via `CallEVMWithData` re-entering the EVM, as `debug.Call0` does) [5](#0-4) .
2. After the transaction, compare `BankKeeper.GetBalance` for the affected account against `StateDB`/`evmKeeper` reported balance for the same denom.
3. Observe the StateDB balance reflects the transferred amount applied more than once (or an account balance that diverges from the bank ledger), matching the discrepancy documented by the existing `balance_handler_test.go` comment describing "balance desync between native bank keeper and EVM stateDB" [10](#0-9) .

```go
func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
```

```text
pragma solidity ^0.8.4;

contract DebugPrecompileCaller {
    address constant debugPrecompile = 0x0000000000000000000000000000000000000799;
    error CallFailed(bytes data);
    function callback(uint256 counter) public {
        bool result;
        bytes memory data;

        // emit events
        for (uint i = 0; i < counter; i++) {
            (result, data) = debugPrecompile.call(abi.encodePacked(uint8(1)));
            if (!result) {
                revert CallFailed(data);
            }
        }

        if (counter > 3) {
            // stop the recursion
            return;
        }

        // recursive call
        (result, data) = debugPrecompile.call(abi.encodePacked(uint8(0), counter));
        if (!result) {
            revert CallFailed(data);
        }
    }
}
```
