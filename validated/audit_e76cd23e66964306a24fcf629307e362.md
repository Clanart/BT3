### Title
Directory-containment check in `resolveWithin()` uses unanchored string prefix match, allowing sibling-directory escape - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` is the sole containment guard used before Desktop reads or writes files derived from repository-relative paths (e.g. the Copilot conflict-resolution write path in `app-store.ts`). Its containment check compares the resolved real path to the real root path with a plain `String.prototype.startsWith()`, without verifying a path-separator boundary. This is the same class of bug as the reported StakeWise issue: a safety invariant ("stay within the vault"/"stay within the repo") that is *believed* to hold in the normal case but silently fails at an edge-boundary condition the guard never accounts for.

### Finding Description
`resolveWithin()` is documented as guaranteeing the resolved path "resides at, or underneath" `rootPath`: [1](#0-0) 

The check is:
```ts
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```
`String.startsWith` is a raw character comparison. If the repository lives at `/Users/x/Projects/myrepo` and a sibling directory `/Users/x/Projects/myrepo-secrets` exists on disk, then `'/Users/x/Projects/myrepo-secrets/config.json'.startsWith('/Users/x/Projects/myrepo')` evaluates to `true`, even though `myrepo-secrets` is a completely different directory. A resolved path such as `resolve(root, '../myrepo-secrets/config.json')` therefore passes the containment check and is returned as a "safe", in-repo path.

This guard protects the write path used to persist AI-generated ("Copilot") conflict resolutions to disk: [2](#0-1) 

That flow resolves each `resolution.path` (a path returned by the Copilot conflict-resolution response) through `resolveWithin(repository.path, resolution.path)` and, if non-null, writes `resolution.resolvedContent` to the resulting `absolutePath` with `writeFile(...)` before staging it with `git add`.

The same containment primitive is invoked earlier when building the LLM prompt context from the working directory, again relying on the boundary check to reject any conflicted path outside the repository: [3](#0-2) 

Because both the "gather context" and "write result" halves of the feature rely exclusively on this single, boundary-unsafe primitive, any caller that supplies (or is tricked into supplying) a relative path that traverses into a sibling directory sharing the repository directory name as a prefix defeats the guard entirely, at every use site that trusts `resolveWithin`.

### Impact Explanation
If the containment check can be bypassed, the effect is a write of attacker- or model-influenced content to a file outside the intended repository — matching the "file write outside the repo" / "silent corruption of what the user commits or pushes" impact category. In the Copilot conflict-resolution flow specifically, this means content is written to disk and then staged (`git add`) based on a path that was never actually validated to be inside the repository, silently corrupting whatever file happens to live at the colliding path in a sibling directory.

### Likelihood Explanation
Exploitability is bounded by the fact that today's primary caller (`buildConflictContext` / `_applyCopilotConflictResolutions`) sources the "expected" path set from `git status` conflicted-file paths, and Git itself blocks `..`-containing path components in tracked tree entries, and `validateResolutionPaths` further restricts the model's returned `path` to that same expected set. This significantly narrows exploitation through *this specific* call chain today. However:
- `resolveWithin` is a general-purpose, exported security primitive with no built-in boundary safety; its contract ("resides at, or underneath root") is violated by design for any caller whose relative-path input is not independently sanitized against `..` traversal (e.g. future callers, submodule path handling, or any code that resolves paths derived from `.gitmodules`, archive extraction, or other less-constrained sources).
- The bug requires a specific pre-condition (a sibling directory whose name is prefixed by the repository directory's own name) to exist on the victim's filesystem, which is a real but not universal condition, and I could not fully enumerate all current callers of `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` within the remaining investigation budget to confirm whether another, less-constrained call site exists that is directly reachable from attacker-controlled repository content.

Given these caveats, I am reporting this as a confirmed code-level guard defect with a clear, concrete PoC against the primitive itself, but with **medium-to-low confirmed likelihood** of end-to-end exploitation through the currently known Copilot call site, pending further audit of all `resolveWithin` callers.

### Recommendation
Fix the boundary check to require a path-separator (or exact equality) after the prefix match, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Apply this fix once in `_resolveWithin` in `app/src/lib/path.ts` so all current and future callers (including the Copilot conflict-resolution read/write path) inherit the corrected containment guarantee. Add a regression test covering a sibling directory whose name is prefixed by the root directory's basename.

### Proof of Concept
```ts
import { resolveWithin } from '../src/lib/path'

// Setup on disk:
//   /tmp/demo/myrepo/            (root, a real Desktop-managed repository)
//   /tmp/demo/myrepo-secrets/config.json   (sibling directory, attacker's target)

const result = await resolveWithin(
  '/tmp/demo/myrepo',
  '../myrepo-secrets/config.json'
)

// Expected (per the documented contract): null, because the target is
// NOT underneath the root.
//
// Actual: resolves to '/tmp/demo/myrepo-secrets/config.json' because
// realResolved.startsWith(realRoot) is true (string-prefix match,
// no separator boundary check).
console.log(result) // '/tmp/demo/myrepo-secrets/config.json'
```
If this path is ever reachable through a caller of `resolveWithin` that accepts an attacker-influenced relative path containing `..` segments (e.g. a future or less-constrained integration point), `_applyCopilotConflictResolutions`'s `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` at `app/src/lib/stores/app-store.ts:7258` would write content outside the intended repository directory while Desktop believes the write was safely contained.
