### Title
Distribution precompile `rewards()` accepts `msg.value` with no non-payable check or payment handling, permanently stranding sent SEI - (File: precompiles/distribution/distribution.go)

### Summary
The distribution precompile's `rewards(address)` view method is dispatched in `Execute` without calling `pcommon.ValidateNonPayable(value)` and without any `HandlePaymentUsei`/`HandlePaymentUseiWei` logic to consume or refund `value`. Every other payable-looking distribution method either rejects value or explicitly processes it; `rewards` does neither, so any usei/wei sent alongside the call is debited from the caller via the standard EVM value-transfer mechanics of a `CALL` but is never refunded or used, leaving it permanently stuck at the precompile's associated account — the exact bug class described in the referenced Allo.sol report (excess/attached value accepted by a contract call path with no recovery mechanism).

### Finding Description
In `precompiles/distribution/distribution.go`, `Execute` dispatches methods based on `method.Name`: [1](#0-0) 
Every state-mutating method (`SetWithdrawAddressMethod`, `WithdrawDelegationRewardsMethod`, etc.) or the payable `WithdrawValidatorCommissionMethod` either calls `pcommon.ValidateNonPayable(value)` or is genuinely value-consuming. `RewardsMethod`, however, is dispatched straight into `p.rewards(ctx, method, args)` with `value` dropped entirely: [2](#0-1) 

The `rewards` implementation itself takes only `ctx, method, args` — it never receives or checks `value` at all: [3](#0-2) 

Because `distribution` is registered as a "payable precompile" (transfer events to/from the precompile address are suppressed), the standard EVM value-transfer semantics apply: when a caller invokes `rewards(address)` with non-zero `msg.value`, the EVM's `Call` opcode handling deducts `value` from the caller's balance and credits it to the precompile's associated account before `Run`/`Execute` is invoked, exactly as with any other precompile call: [4](#0-3) 

Since `rewards()` performs no `SendCoins`/`SendCoinsAndWei` refund and no debit-based state change tied to that value, the usei/wei credited to the precompile's account is never moved anywhere — it sits at that address indefinitely, with no `recoverFunds`-style mechanism anywhere in the distribution module to reclaim it. This mirrors the reported Allo.sol pattern of a payable function whose excess value is silently retained by the contract with no built-in refund path.

This is not merely theoretical: the integration test suite for this precompile explicitly documents the gap as a known "quirk", confirming the code path is reachable and intentional (or at least accepted) with no protective check: [5](#0-4) [6](#0-5) 

### Impact Explanation
Any unprivileged EVM caller — either directly via an EOA transaction or through an intermediate contract like `PrecompileCaller.callTarget` forwarding `msg.value` — who calls `rewards(address)` on the distribution precompile (`0x...1007`) with non-zero value permanently loses that value. There is no withdrawal, sweep, or refund function reachable by users or validators that would recover funds sent to the precompile's underlying account via this path. Repeated calls accumulate ever-increasing amounts of permanently frozen SEI/wei, meeting the "permanent freezing of funds" impact bar.

### Likelihood Explanation
Likelihood is Medium: this requires the caller to actively attach `msg.value` to a call that is documented/expected to be a free view function (most tooling/wallets would not do this by default, and the ABI likely doesn't mark `rewards` as `payable`, so this would typically only be triggered by an intentional low-level call or a custom crafted contract). However, it requires no special privilege, no association bypass, and no unusual chain state — just a single transaction — making it trivially reachable by any user who discovers or is told about the missing guard.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` at the top of the `RewardsMethod` case in `Execute` (and equivalently in all legacy versions of the distribution precompile that expose `rewards`), consistent with every other view/query method in the same switch statement (`ParamsMethod`, `ValidatorOutstandingRewardsMethod`, etc., which already implicitly disallow payment via their handlers not consuming `value`, but explicit validation is the safer/consistent fix). Alternatively, if a value-bearing view call is ever intentionally needed, wire it through `HandlePaymentUseiWei` to refund the caller immediately, as done in `precompiles/common/precompiles.go`'s `HandlePaymentUsei`/`HandlePaymentUseiWei` helpers used elsewhere in the same package.

### Proof of Concept
1. Deploy or use the existing `PrecompileCaller` contract (or call directly from an EOA tx with data set to `rewards(address)`'s selector).
2. Call `distribution.rewards(delegatorAddress)` at address `0x...1007` with `msg.value = 1 ether` (or any non-zero wei/usei amount) and sufficient gas.
3. Observe: the call succeeds (per the documented test-suite note, "a value-bearing call would succeed and strand the funds") and returns the expected reward data.
4. Query the caller's EVM balance — it has decreased by exactly `value`.
5. There is no function in the distribution precompile, bank precompile, or any governance/admin path that returns this value to the caller; it is permanently stuck at the precompile's associated Sei account. [2](#0-1) [7](#0-6) [8](#0-7)

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
