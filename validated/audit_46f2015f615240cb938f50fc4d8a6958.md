### Title
Attacker-controlled length prefix causes up-front heap allocation DoS in `ReceivedOutput::read` - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
CVE-2021-22173 is a memory-exhaustion bug: a dissector allocates/copies attacker-sized buffers from crafted bytes, turning a few input bytes into large memory consumption and a denial of service. The reachable analog in Serai's in-scope code is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs`, which deserializes a `TxOut` via `TxOut::consensus_decode`. A `TxOut`'s `script_pubkey` is decoded as a `CompactSize` length followed by a `vec![0; len]` allocation performed before the bytes are validated/read, so a handful of attacker bytes triggers a heap allocation far larger than the input actually provided.

### Finding Description
`ReceivedOutput::read` reads a 32-byte offset scalar, then hands the stream to rust-bitcoin consensus decoding for `TxOut` and `OutPoint` [1](#0-0) . Inside `TxOut::consensus_decode`, the `script_pubkey: ScriptBuf` field is length-prefixed with a Bitcoin `CompactSize` (u64 range). The consensus decoder allocates a `Vec<u8>`/`ScriptBuf` of the *claimed* size before populating it — the allocation happens regardless of whether the bytes are actually present (note the deliberate `BufReader::with_capacity(0, r)` wrapper, which prevents buffered over-read but does nothing to bound the allocation [2](#0-1) ).

So a serialized `ReceivedOutput` consisting of `32-byte scalar || 0xfd/0xfe/0xff CompactSize claiming ~0xffffffff bytes` causes an immediate multi-gigabyte (or, where rust-bitcoin's `MAX_VEC_SIZE` cap applies, multi-megabyte) allocation from ~40 input bytes. This is reachable precisely along the path the audit scope allows: untrusted bytes fed to `ReceivedOutput::read`. The same allocation-then-verify pattern exists in-scope-adjacent readers (`Plan::read` in `processor/src/plan.rs:180` reads a u32 count then loops `N::Output::read`, and `Payment::read` at `processor/src/plan.rs:53-70` does `vec![0; u32]`), but those files are outside the allowed scope; `ReceivedOutput::read` is the in-scope entry point.

Unlike the other length-driven readers in scope — `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632, bounded by a u16 `n` and requiring the bytes to actually be supplied) and `Commitments::read`/`read_preprocess`/`read_share` (crypto/frost/src/nonce.rs:133-139, sign.rs:276-281, sizes fixed by the algorithm's nonce layout, not by attacker bytes) — `ReceivedOutput::read` trusts a fully attacker-controlled u64-range length and allocates before confirming the data exists.

### Impact Explanation
An unprivileged party who can submit bytes that reach `ReceivedOutput::read` (e.g., a serialized output/plan message, or any consumer that persists or exchanges `ReceivedOutput` blobs) forces the host to perform a heap allocation proportional to the claimed `CompactSize` length — up to ~4 GB per message, or ~4 MB per message if the pinned rust-bitcoin enforces `MAX_VEC_SIZE`. Repeated messages exhaust memory or abort the process (Rust aborts on allocation failure for `vec![0; n]`), denying service to the signing/scanning pipeline. This is the same impact class as CVE-2021-22173 (A:H in the advisory): a memory-exhaustion DoS from crafted input, not a memory-safety corruption. A caveat I could not fully verify from the index: the exact `MAX_VEC_SIZE` behavior depends on the pinned rust-bitcoin version; even in the capped case, ~5 input bytes per ~4 MB allocation remains a severe amplification factor.

### Likelihood Explanation
Likelihood depends on whether any in-scope consumer exposes `ReceivedOutput::read` to untrusted bytes (it is listed among the permitted attacker-controlled entry points, and `ReceivedOutput` values are produced by `Scanner::scan_transaction`/`scan_block` and serialized via `write`/`serialize` for transport/storage [3](#0-2) ). Any peer, chain-reorg re-delivery, or stored blob that is re-read through `read` without an outer size bound is exploitable with trivial crafted input — no signing capability, valid key, or malformed curve encodings are required.

### Recommendation
Do not length-prefix-trust consensus data. In `ReceivedOutput::read`, bound the reader before decoding — e.g., wrap `r` in `io::Read::take`/`BufReader` limited to the maximum legitimate `TxOut + OutPoint` size (well under Bitcoin's ~1 MWU transaction bound), or decode `TxOut` from a pre-bounded buffer and reject claimed `script_pubkey` lengths exceeding a sane cap (e.g., 10 KB) before allocation. Apply the same chunked-read/limit-check pattern already used elsewhere in the codebase (e.g., the `MAX_LIBP2P_REQRES_MESSAGE_SIZE` check in `coordinator/src/p2p.rs` and the 1 KB chunked read in `networks/ethereum/src/machine.rs`).

### Proof of Concept
```rust
use std::io;
use bitcoin_serai::wallet::ReceivedOutput;

// 32 bytes: any scalar < group order
let mut msg = vec![1u8; 32];
msg[0] = 1; // valid non-zero scalar encoding

// TxOut::consensus_encode layout: u64 value (8 bytes) + CompactSize(script len) + script
msg.extend_from_slice(&0u64.to_le_bytes());           // value = 0
// CompactSize for a huge claimed script_pubkey length
msg.extend_from_slice(&[0xff]);                       // u64 CompactSize marker
msg.extend_from_slice(&0xffff_ffff_ffff_ffffu64.to_le_bytes()); // claimed len
// Provide NO script bytes.

let mut cursor = std::io::Cursor::new(&msg);
// Decoder allocates a Vec sized by the claimed CompactSize before reading fails.
let _ = ReceivedOutput::read(&mut cursor); // OOM / abort, or ~4MB wasted alloc under MAX_VEC_SIZE
```
For a capped rust-bitcoin build, loop the call: each ~41-byte message forces the maximum-allowed allocation, exhausting memory over repeated reads.

  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }
