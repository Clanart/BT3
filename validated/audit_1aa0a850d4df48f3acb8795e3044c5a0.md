## Analog Identified: Balance Handler `prevEventsLen` Marker Not Scoped to a Single Precompile Invocation

### Title
Shared/reentrant `BalanceHandler` allows `prevEventsLen` to be overwritten mid-execution, causing StateDB/bank balance desync - (File: `precompiles/common/balance_handler.go`)

### Summary
The Poseidon2 bug is a class of "single-shot marker corrupted by re-entry": a flag meant to be set exactly once at the start of a top-level process (`start_top_level`) is instead settable mid-process, letting an attacker substitute the wrong preimage into an accumulated value. The Cosmos EVM analog is `BalanceHandler.prevEventsLen`, which is meant to mark the start of the event window for exactly one (outer/top-level) precompile invocation, but can be overwritten by a nested/recursive invocation of the same precompile before the outer invocation finishes reading it back.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records the current SDK event count as a marker (`prevEventsLen`), and `AfterBalanceChange` later replays only the events emitted after that marker to update the EVM `StateDB` balances: [1](#0-0) 

This works correctly only if `BeforeBalanceChange`/`AfterBalanceChange` execute as a strictly nested (LIFO) pair per precompile call, with the marker reset only once per top-level entry — analogous to `start_top_level` being true only at the very first row. The repository's own test suite documents that this invariant is violated: a `BalanceHandler` instance can be shared across recursive precompile invocations, so a nested call's `BeforeBalanceChange` overwrites `prevEventsLen` before the outer call reaches its `AfterBalanceChange`: [2](#0-1) [3](#0-2) 

A companion test explicitly frames this as "the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated": [4](#0-3) 

In `precompiles/common/precompile.go`'s generic `runNativeAction` path, a fresh `BalanceHandler` is created per call via the factory, which is the correct pattern: [5](#0-4) 

However, other precompiles (`distribution`, `erc20`, `gov`, `ics20`, `slashing`, `staking`) reference `GetBalanceHandler()` rather than instantiating a fresh handler scoped strictly to the current call frame — matching the pattern the test suite calls out as buggy when calls recurse into the same precompile (e.g., via reentrant contract logic, ICS20 transfer triggering distribution/staking calls, or IBC callback flows).

### Impact Explanation
When `prevEventsLen` is clobbered mid-processing by a nested call, the outer call's `AfterBalanceChange` will only replay bank events emitted after the nested call started — silently dropping the `coin_spent`/`coin_received`/fractional-balance events attributable to the outer call. This produces a **StateDB balance that diverges from the actual bank-module ledger**: EVM-visible balances (`BALANCE` opcode, `stateDB.GetBalance`) become permanently desynchronized from the true bank balance for the accounts involved. Because contract logic, subsequent `AddBalance`/`SubBalance` deltas, and value-transfer decisions within the same or later transactions build on top of this corrupted base, this constitutes irreversible accounting corruption of spendable user value between native bank balances and EVM-visible balances — matching the "Critical unauthorized... duplication... irreversible accounting corruption of spendable user value across native balances, EVM balances" impact category.

### Likelihood Explanation
The trigger requires only an unprivileged user to deploy/call a contract that causes recursive/nested invocation of a balance-affecting precompile (staking, distribution, gov, slashing, erc20, or ics20) — for example, a contract with a fallback/callback hook that re-enters the same precompile, or an ICS-20 transfer/IBC-callback flow that triggers further precompile calls within the same EVM message. The repository's own tests demonstrate this scenario is reachable in normal transaction flow without any privileged setup.

### Recommendation
Scope the `BalanceHandler`'s `prevEventsLen` marker strictly to a single call frame instead of sharing mutable handler state across nested/recursive invocations of the same precompile — e.g., always construct a new `BalanceHandler` per `Run`/native-action invocation (as already done in `precompile.go`'s `runNativeAction`), or use a call-stack of markers so that an inner call's `Before/After` pair cannot clobber an outer call's marker. Additionally add a regression test asserting that after a nested precompile call completes, the outer call's `AfterBalanceChange` still processes the full set of events emitted since the true start of the outer call.

### Proof of Concept
The repository already contains a reproducing test: `BalanceHandlerTestSuite.TestRecursivePrecompileCallsWithDebugPrecompile` deploys `DebugPrecompileCaller.sol`, which recursively calls a balance-handler-enabled debug precompile, and documents the resulting event/balance discrepancy. [6](#0-5) [7](#0-6) 

**Caveat / uncertainty**: I was not able to inspect the exact field layout of `GetBalanceHandler()` in `distribution.go`, `staking.go`, `erc20.go`, `gov.go`, `ics20.go`, and `slashing.go` (only that they reference this method, per `grep_search`) before running out of tool iterations, so I cannot cite the precise line where the handler is stored as a shared/singleton field in those production precompiles. The root-cause mechanism and its reachability are established via the checked-in test suite and the confirmed `BeforeBalanceChange`/`AfterBalanceChange` window-slicing logic, but full confirmation of which specific precompiles share a non-scoped instance vs. always allocate fresh instances would benefit from a follow-up Devin session with full repository access.

// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.4;

contract DebugPrecompileCaller {
    address constant debugPrecompile = 0x0000000000000000000000000000000000000799;
    error CallFailed(bytes data);
    function callback(uint256 counter) public {
        bool result;
        bytes memory data;

        // emit events
        for (uint i = 0; i < counter; i++) {
            (result, data) = debugPrecompile.call(abi.encodePacked(uint8(1)));
            if (!result) {
                revert CallFailed(data);
            }
        }

        if (counter > 3) {
            // stop the recursion
            return;
        }

        // recursive call
        (result, data) = debugPrecompile.call(abi.encodePacked(uint8(0), counter));
        if (!result) {
            revert CallFailed(data);
        }
    }
}
