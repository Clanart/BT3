### Title
Stale cached diff reused for commit when file content changes but path/status stay the same - ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
GitHub Desktop's `updateChangedFiles` decides whether to keep the previously loaded `diff` object across a `git status` refresh purely by comparing the file's `id` (path + status kind), not any content-derived value. [2](#0-1)  Because `FileChange.id` never encodes file content, a file whose on-disk contents mutate between two status refreshes (same path, same status kind, e.g. "Modified") will keep displaying the old diff on the "Changes" screen even though it will actually be re-diffed against the new content at commit time.

### Finding Description
`updateChangedFiles` is invoked from `_loadStatus` every time the working directory status is refreshed (background polling, focus events, post fetch/pull/merge, or automatically). [3](#0-2)  When merging the new `status.workingDirectory.files` with the previous state, the reused-diff decision is:
```
const diff =
  selectedFileIDs.length === 1 &&
  state.selection.selectedFileIDs.length === 1 &&
  state.selection.selectedFileIDs[0] === selectedFileIDs[0]
    ? state.selection.diff
    : null
``` [2](#0-1) 

The comparison uses only `selectedFileIDs`, and the ID itself is `${status.kind}+${path}` (or with `oldPath` for renames). [4](#0-3)  Nothing about the blob hash, mtime, or file size is part of this identity. So if a file keeps the same path and the same status kind ("Modified") across two consecutive status refreshes — which is common when a script, build tool, editor auto-save, git hook, or (in the attacker-repo scenario) a malicious `post-checkout`/`post-merge`/file-watcher process modifies the file shortly after Desktop finishes one diff render but before/while the next status poll occurs — the old, now-stale `diff` object is kept and displayed to the user in the Changes view.

`updateChangesWorkingDirectoryDiff`, the function responsible for actually re-fetching the diff via `getWorkingDirectoryDiff`, is only invoked opportunistically after selection changes or explicit refresh triggers; it is not always re-triggered synchronously on every `_loadStatus` call for files whose ID didn't change. [5](#0-4)  The staleness guard added there only checks whether the *selection* (file IDs) changed while an async diff load was in flight — it does nothing to detect that the underlying file bytes changed between two status polls when no diff reload was even triggered.

This is structurally the same invariant violation as the USDs bug: a derived/displayed value (USDs balance vs. Desktop's rendered diff) is computed from a cached intermediate (`_creditsPerToken` vs. cached `diff`) that is not invalidated when the true underlying state (`totalSupply`/rebasing vs. file content) changes, because the invalidation key (`totalSupply` snapshot vs. `FileChange.id`) does not fully capture the state that changed.

### Impact Explanation
The Changes pane is the primary trust surface the user relies on to decide what to stage and commit. If the diff shown is stale relative to actual working-directory content but the user commits with "select all" (default `includeAll` behavior at `WorkingDirectoryStatus`/`getIncludeAllState`), git will commit the *current* file bytes regardless of the stale preview — meaning the user can be shown a benign diff while an entirely different (attacker-modified) set of bytes gets silently committed and potentially pushed. This matches the explicitly valid impact category "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Requires no local/physical access or credentials from the attacker beyond the standard Desktop threat model of "attacker controls a cloned/fetched repository": a malicious repo can ship a `post-checkout`, `post-merge`, or `pre-commit` hook (Desktop does invoke git hooks during checkout/merge/commit flows) or a file-watch/build script referenced by repo tooling that rewrites a tracked file shortly after Desktop's UI has rendered its diff and before the next background status refresh completes. Because status polling in Desktop is asynchronous and not always followed by a forced diff re-fetch for files with unchanged IDs, the race window is real, though it does require the attacker's mutation to land in that specific window, which is a timing-dependent condition rather than a guaranteed trigger. I am not able to fully confirm from static reading whether some other code path (e.g. `_loadChangedFilesForCurrentSelection` or a full remount) unconditionally forces a diff reload on every status change for the currently selected file outside of the `updateChangesWorkingDirectoryDiff` guard shown above — that would need dynamic verification.

### Recommendation
Include a content-derived invalidation signal (e.g. git blob OID from `git status`/`ls-files -s`, or file mtime+size) in the diff-reuse decision inside `updateChangedFiles`, instead of relying solely on `FileChange.id`. Alternatively, force `updateChangesWorkingDirectoryDiff` to unconditionally re-fetch the diff for the currently selected file whenever `_loadStatus` runs, rather than only on selection changes.

### Proof of Concept
Conceptual reproduction (not independently executed):
1. Open a repository in Desktop, select a modified tracked file `foo.txt` in the Changes pane; Desktop calls `getWorkingDirectoryDiff` and caches the resulting diff under `id = "Modified+foo.txt"`.
2. While Desktop is between background status polls (or via a repo-shipped hook triggered by a checkout/merge), overwrite `foo.txt` with different content while keeping it "Modified" in git status.
3. The next `_loadStatus` call runs `updateChangedFiles`; because `selectedFileIDs` before/after are both `["Modified+foo.txt"]`, the previous (stale) `diff` is retained per [2](#0-1) .
4. The user, trusting the displayed stale diff, clicks "Commit" with all changes included; the actual new file bytes (not shown in the diff) get committed and can be pushed.

    ) {
      this.id = `${status.kind}+${path}+${status.oldPath}`
    } else {
      this.id = `${status.kind}+${path}`
    }
  }

    }

  private async updateChangesWorkingDirectoryDiff(
    repository: Repository
  ): Promise<void> {
    const stateBeforeLoad = this.repositoryStateCache.get(repository)
    const changesStateBeforeLoad = stateBeforeLoad.changesState

    if (
      changesStateBeforeLoad.selection.kind !==
      ChangesSelectionKind.WorkingDirectory
    ) {
      return
    }

    const selectionBeforeLoad = changesStateBeforeLoad.selection
    const selectedFileIDsBeforeLoad = selectionBeforeLoad.selectedFileIDs

    // We only render diffs when a single file is selected.
    if (selectedFileIDsBeforeLoad.length !== 1) {
      if (selectionBeforeLoad.diff !== null) {
        this.repositoryStateCache.updateChangesState(repository, () => ({
          selection: {
            ...selectionBeforeLoad,
            diff: null,
          },
        }))
        this.emitUpdate()
      }
      return
    }

    const selectedFileIdBeforeLoad = selectedFileIDsBeforeLoad[0]
    const selectedFileBeforeLoad =
      changesStateBeforeLoad.workingDirectory.findFileWithID(
        selectedFileIdBeforeLoad
      )

    if (selectedFileBeforeLoad === null) {
      return
    }

    const diff = await getWorkingDirectoryDiff(
      repository,
      selectedFileBeforeLoad,
      this.hideWhitespaceInChangesDiff
    )

    const stateAfterLoad = this.repositoryStateCache.get(repository)
    const changesState = stateAfterLoad.changesState

    // A different file (or files) could have been selected while we were
    // loading the diff in which case we no longer care about the diff we
    // just loaded.
    if (
      changesState.selection.kind !== ChangesSelectionKind.WorkingDirectory ||
      !arrayEquals(
        changesState.selection.selectedFileIDs,
        selectedFileIDsBeforeLoad
      )
    ) {
      return
    }
