The actual staging path, `applyPatchToIndex`, independently re-fetches a fresh diff via `getWorkingDirectoryDiff` and blindly applies the caller-supplied `file.selection` (a set of absolute line indices) against it with `formatPatch`, with no re-validation step: [2](#0-1)  and [3](#0-2) .

### Title
Selective-line commit staging trusts stale line-index selections against a freshly re-fetched diff, allowing silent corruption of what is committed - (File: `app/src/lib/git/apply.ts`)

### Summary
Desktop's partial/interactive staging feature lets a user select individual added/removed lines in a diff to include in a commit. That selection is stored as an abstract set of absolute line indices (`DiffSelection`), not tied to any content hash or diff snapshot [4](#0-3) . When the user actually commits, `stageFiles` → `applyPatchToIndex` re-runs `git diff` on disk and reformats a patch using those same indices against whatever hunks come back [5](#0-4) , [6](#0-5) . If the working tree content changes between the moment the diff was rendered/selected in the UI and the moment `_commitIncludedChanges` triggers staging, the indices no longer refer to the same logical lines, and `git apply --cached` will stage whatever lines now occupy those positions — not what the user reviewed.

### Finding Description
`DiffSelection` is a pure index-based bitset with no binding to the diff content it was derived from [7](#0-6) . Desktop only reconciles selectable/selected line indices against a fresh diff in one place: `updateChangesWorkingDirectoryDiff`, which is triggered on a repository refresh while updating the Changes tab UI, and even there the code explicitly settles for a partial fix rather than true content validation [8](#0-7) .

The commit path does not go through this reconciliation at all. `_commitIncludedChanges` takes whatever `file.selection` is currently attached to the in-memory `WorkingDirectoryFileChange` objects in `repositoryStateCache` and passes the selected files straight to `createCommit` → `stageFiles` [9](#0-8) , [10](#0-9) . For partially-selected files, `applyPatchToIndex` performs its own independent `getWorkingDirectoryDiff` call and formats a patch from the current on-disk hunks using the stale selection indices, with no check that the diff hunk boundaries/oids match what was originally shown to the user [2](#0-1) .

`formatPatch` walks the new diff's hunks and, for each line, calls `file.selection.isSelected(absoluteIndex)` purely by numeric position [3](#0-2) . If the file was modified between diff-render time and commit time (e.g., by a background process, an editor autosave, a build tool, an `.gitattributes`-driven clean/smudge filter, or content rewritten by a post-checkout/post-merge hook after a `fetch`/`pull`/`checkout` performed by Desktop on an attacker-supplied remote), the hunk structure and line ordering can shift. The stale indices then bind to unrelated lines in the new diff — potentially staging attacker-introduced or otherwise unreviewed content while the user believes they are committing only the lines they explicitly checked in the diff viewer, or conversely omitting lines the user intended to include.

### Impact Explanation
This breaks the core invariant users rely on for interactive/partial staging: *"the lines I checked in the diff are the lines that get committed."* A mismatch here is a silent corruption of what the user commits (and, if they push immediately after, of what gets pushed to a shared/public remote) — squarely within the requested impact category. It's the closest structural analog to the CToken bug: a value (`DiffSelection`, analogous to the cached "exchange rate") is computed against one snapshot of state and later reused against a different, live-refetched snapshot without a consistency/staleness check, producing an outcome the caller did not intend.

### Likelihood Explanation
Exploitability depends on being able to reliably change tracked file content in the narrow window between diff render and commit-click while a partial line selection is active. This is a realistic but narrow race — it is more plausibly triggered via automated file mutation (build tools, filters, or hooks executed as a side effect of git operations Desktop performs on attacker-supplied repository content) than through direct attacker timing control, so likelihood is moderate rather than high. I could not find any additional guard elsewhere in the codebase (e.g., a diff hash/oid check before `git apply`) that would prevent this; the only mitigation present (`app-store.ts:3478-3497`) explicitly operates on the UI-selection-state path, not the staging path.

### Recommendation
Before calling `applyPatchToIndex`/`formatPatch`, verify that the hunks of the freshly fetched diff are structurally equivalent (e.g., via a content hash or by comparing hunk headers/oids) to the diff the selection was originally computed against; if they differ, force a re-diff/re-selection (or abort/warn) rather than silently applying stale indices to new content — mirroring the recommendation in the source report to validate a derived value against current state before using it, rather than reusing a snapshot computed earlier.

### Proof of Concept
1. Open a repository in Desktop and modify a tracked file, producing a multi-hunk diff in the Changes view.
2. In the diff viewer, select only specific individual lines/hunks for inclusion (partial `DiffSelection`), leaving the commit dialog open.
3. Before clicking "Commit," have an external process (build tool, `.gitattributes` filter, or a hook fired by a Desktop-initiated `fetch`/`checkout` against a crafted remote) rewrite the file so hunk boundaries shift (e.g., insert/remove lines above the previously selected hunk).
4. Click "Commit selected changes." `applyPatchToIndex` re-diffs the file and applies the original line-index selection to the new hunk layout via `formatPatch`.
5. Inspect the resulting commit: it contains different content than what was visually selected/reviewed by the user (either omitting reviewed lines or including unreviewed ones), demonstrating the silent corruption of the committed diff.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
