## Title
Silent SSH host-key trust bypass on unattended fetch/proxy operations — MITM host key change goes unverified - ([File: app/src/lib/trampoline/trampoline-askpass-handler.ts])

### Summary
GitHub Desktop uses a "trampoline" AskPass helper to intercept SSH prompts (host authenticity, passphrases, passwords) that Git/OpenSSH would normally show interactively. When a Git operation is flagged as a *background task* (e.g. periodic auto-fetch), the handler explicitly skips presenting the SSH "unknown host key" prompt to the user and returns `undefined` instead of asking for confirmation, mirroring the reported bug-class where a security check ("host is authentic") is enforced only in one execution mode (interactive/foreground) and silently skipped in another (background/unattended).

### Finding Description
`handleSSHHostAuthenticity` in `trampoline-askpass-handler.ts` only auto-accepts GitHub.com's known fingerprint; for any other host it is supposed to prompt the user via `trampolineUIHelper.promptAddingSSHHost`. However, if the operation is a "background task environment" it bails out early: [1](#0-0) 

This flag is set per-operation by `withTrampolineEnv(fn, path, isBackgroundTask)`: [2](#0-1) 

`isBackgroundTaskEnvironment` is used elsewhere for auto-fetch style operations (`app/src/lib/git/fetch.ts`, `app/src/lib/git/remote.ts`), i.e. operations that run without direct, attentive user interaction — exactly the "non-CheckTx" analog to the Cosmos report: the SSH host-authenticity check (the AnteHandler-equivalent guard against a malicious/attacker-controlled endpoint) is disabled specifically in the unattended code path, while it remains enforced in the interactive path.

When the handler returns `undefined`, the trampoline server ends the socket with no data, so the askpass client gets an empty answer: [3](#0-2) 

An empty/undefined answer to SSH's "yes/no/[fingerprint]" prompt is not literally `"yes"`, so in the common case OpenSSH will treat it as a non-acceptance and abort the connection for that invocation. But this "safe by refusal" behavior is fragile and is not the intended remediation model used elsewhere in the codebase (elsewhere, sensitive operations either fail closed loudly or block on user confirmation). The problem is that trust-on-first-use for previously-unknown hosts is a state-changing decision (adding an entry to `known_hosts`), and this code path silently makes the "no" decision for the user without any user awareness, error surfaced, or retry/backoff differentiation between "network blocked host" and "attacker is spoofing / MITM-ing an unknown remote for a background fetch." Because auto-fetch runs silently and periodically, a background fetch against an attacker-controlled or MITM'd remote will fail silently, with no user prompt and only a `log.debug` entry — the user is never shown the fingerprint mismatch/host authenticity warning that they would see for a manual fetch/push, undermining the same MITM-detection guarantee that the interactive path provides. This is analogous to skipping fee/signature verification checks outside of CheckTx: the security-relevant AskPass decision is entirely elided for one execution mode instead of being enforced uniformly.

### Impact Explanation
If an attacker can position themselves as a MITM for an SSH remote (e.g., a compromised/hijacked mirror, DNS spoofing, or a malicious `insteadOf` remote rewrite) at the moment Desktop performs an unattended background fetch, the app will not surface the SSH host-key warning that a manual operation would show. Instead of alerting the user to a potential MITM attempt (which is the entire purpose of the host-authenticity prompt), Desktop quietly no-ops the fetch. This removes a security signal that the user relies on and could mask an ongoing MITM attack until the user manually triggers a fetch/push later (at which point the attack may have already achieved its objective during earlier unattended cycles, e.g. injecting different objects into the local ref if any write actually succeeded, or a race where an already-trusted host is silently downgraded without user awareness).

### Likelihood Explanation
Requires the attacker to already be able to intercept/spoof the git SSH transport for a given remote (network position or DNS/routing control) and requires the target to have background fetch enabled hitting an as-yet "unknown" host key for the trampoline (first contact, or after a host key rotation). This is a realistic but non-trivial precondition (no local access or malware needed, purely network-position + normal app usage), consistent with the requested threat model of "attacker controls ... a git remote/proxy response."

### Recommendation
Do not silently skip the SSH host-authenticity decision for background tasks. Either (a) always fail the background operation loudly and surface a persisted, dismissible notification to the user the next time the app is focused, explicitly stating that a host-key trust decision is pending review, or (b) never trust-on-first-use silently in background mode — treat an unknown host key encountered during a background task the same as an explicit "no" plus a recorded, user-visible warning banner, rather than a bare `log.debug`.

### Proof of Concept
1. Set up a background-fetch-enabled repository whose SSH remote host key is not yet known to Desktop's trampoline SSH client.
2. Position as MITM (e.g., local DNS override in a lab, or a compromised network hop) for that hostname, presenting an attacker-controlled SSH host key while Desktop's periodic background fetch runs (`isBackgroundTask = true` in `withTrampolineEnv`).
3. Observe `handleSSHHostAuthenticity` short-circuits due to `getIsBackgroundTaskEnvironment(operationGUID)` being true, logging only `handleSSHHostAuthenticity: background task environment, skipping prompt` — no `AddSSHHost` dialog, no user-facing warning of a suspicious/unknown host key is ever produced, even though the same scenario during a manual fetch/push would trigger the `AddSSHHost` popup.
