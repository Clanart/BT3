### Title
`SmartWomConvert._convertFor` can become permanently stuck due to non-zero-to-non-zero `safeApprove` calls on WOM/mWOM - (File: `wombat/SmartWomConvert.sol`)

### Summary
`SmartWomConvert._convertFor` (called from the unprivileged, user-reachable `convert`/`convertFor`/`smartConvert` entry points) repeatedly calls `IERC20(wom).safeApprove(router, buybackAmount)` and `IERC20(wom).safeApprove(mWom, convertAmount)`, and `IERC20(mWom).safeApprove(masterMagpie/mWomSV, obtainedmWomAmount)`, without ever resetting the allowance to zero first, exactly the pattern flagged in the referenced SuperVault finding.

### Finding Description
OpenZeppelin's `SafeERC20.safeApprove` (used everywhere here via `using SafeERC20 for IERC20`) contains a hard `require` that reverts if the current allowance is non-zero and the new value is also non-zero ("SafeERC20: approve from non-zero to non-zero allowance"). In `_convertFor`, `wom` is approved to `router` and to `mWom`, and `mWom` is approved to `masterMagpie` or `mWomSV`, every single call, with no zero-allowance reset beforehand: [1](#0-0) 
If any prior call to these external contracts (`IWombatRouter.swapExactTokensForTokens`, `IMWom.deposit`, `IMasterMagpie.depositFor`, `mWomSV.lockFor`) does not consume the entire approved amount — leaving any dust allowance — the very next `safeApprove` call from a non-zero to a non-zero value will unconditionally revert, independent of whether `wom`/`mWom` themselves are "weird" tokens; this is baked into OZ's `SafeERC20` wrapper itself. Notably, this same codebase demonstrates that the maintainers are aware of and fix this exact hazard elsewhere: `WombatStaking._sendRewards` explicitly zeroes the allowance before re-approving (`safeApprove(feeInfo.to, 0)` then `safeApprove(feeInfo.to, feeTosend)`, and similarly for `_rewarder`): [2](#0-1) [3](#0-2) 
but this zero-first pattern is inconsistently omitted in `SmartWomConvert._convertFor`, `mWOM.incentiveDeposit`, and `WombatStaking.deposit`/`withdraw`/`_stakeToWombatMaster`/`convertWOM`.

### Impact Explanation
`SmartWomConvert` is the smart-conversion path used by `WombatStaking._sendRewards` to convert `WOM` reward fees to `mWOM` for every harvest, as well as directly by any user calling `convert`/`convertFor`/`smartConvert`. If a residual non-zero allowance is ever left on `wom` (to `router` or `mWom`) or on `mWom` (to `masterMagpie`/`mWomSV`) after any external call — e.g. `IWombatRouter.swapExactTokensForTokens` returning less than the exact swap-in amount consumed, or `IMWom.deposit`/`IMasterMagpie.depositFor`/`ILocker.lockFor` not draining the full approved amount — every subsequent call into `_convertFor` reverts permanently. Since `WombatStaking._sendRewards` funnels `WOM` fees through `smartConvert` on every pool harvest when `smartWomConverter` is set, this would also permanently break harvest-triggered fee routing for all pools, freezing that unclaimed-yield conversion path indefinitely (>24h, unrecoverable without a contract upgrade), matching the accepted "permanent freezing of unclaimed yield" criterion.

### Likelihood Explanation
Reachable purely through ordinary user transactions (`convert`, `convertFor`, `smartConvert`, or indirectly via any pool `harvest()`/`deposit()`/`withdraw()` that triggers `_sendRewards` → `smartConvert`) with no privileged role required. The trigger condition (external call not consuming full approved allowance) is plausible under normal AMM swap slippage/rounding in `IWombatRouter.swapExactTokensForTokens`, since the function approves `buybackAmount` exactly but a swap does not guarantee the router pulls the full approved amount in a single atomic operation in all router implementations.

### Recommendation
Force allowance to zero before each `safeApprove` call in `_convertFor` (and `mWOM.incentiveDeposit`, `WombatStaking.deposit`/`withdraw`/`_stakeToWombatMaster`/`convertWOM`), mirroring the pattern already used in `WombatStaking._sendRewards`, or migrate to `forceApprove`/`safeIncreaseAllowance` semantics that tolerate non-zero starting allowances.

### Proof of Concept
1. A user calls `SmartWomConvert.convert(amountIn, ratio, minRec, mode)`, which routes through `_convertFor`, approving `router` for `buybackAmount` at line 193 and swapping via `IWombatRouter.swapExactTokensForTokens`.
2. If the router's swap does not fully consume the approved `wom` allowance (e.g., due to internal accounting/rounding on the router's `swapExactTokensForTokens` path), a small non-zero allowance from `SmartWomConvert` to `router` remains.
3. On the next call to `convert`/`convertFor`/`smartConvert`, line 193 (`IERC20(wom).safeApprove(router, buybackAmount)`) attempts a non-zero-to-non-zero approval and reverts unconditionally per OZ's `SafeERC20.safeApprove` guard.
4. `_convertFor` becomes permanently unusable, and since `WombatStaking._sendRewards` calls `IConverter(smartWomConverter).smartConvert(...)` on every harvest when a `smartWomConverter` is configured, harvest-triggered `WOM`→`mWOM` fee conversion for all pools is frozen indefinitely.
