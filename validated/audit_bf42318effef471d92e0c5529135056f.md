### Title
`SignableTransaction` fee and weight accounting omit the OP_RETURN output, so the reported `needed_fee` understates the transaction's real size and the signed transaction can be rejected for broadcast - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The external report describes a credited amount (`increasePoolAmount(amountAfterFee)`) that exceeds the tokens actually received, creating an accounting mismatch that later prevents distribution. The analog in Serai's Bitcoin wallet is an accounting mismatch between the fee the transaction *claims* to pay (`needed_fee`, computed from an underestimated vsize) and the fee the transaction *actually* needs to be standard/relayable: `SignableTransaction::new` appends an `OP_RETURN` data output to `tx_outs`, but `calculate_weight_vbytes` is only ever called with `payments` — the data output is never included in the weight/vbytes calculation. The resulting `needed_fee` (and the minimum-relay-fee check) are computed against a transaction that is up to ~93 vbytes smaller than the real one. Like the Allo bug — where the recorded pool balance didn't match the delivered tokens — the recorded/declared fee does not match the real cost of the produced transaction.

### Finding Description
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`):

- The `OP_RETURN` output is pushed into `tx_outs` at lines 194-202 when `data` is `Some`.
- The size estimate at line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — it passes `payments`, never `tx_outs`, so the `OP_RETURN` output (up to 80 bytes of data + overhead) is excluded from `weight` and `vbytes`.
- `needed_fee = fee_per_vbyte * vbytes` (line 206) and the minimum relay fee check (lines 211-213) therefore assume a smaller transaction than what is actually built.
- The change-output branch (lines 224-235) repeats the same underestimation via `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`.
- The `MAX_STANDARD_TX_WEIGHT` check at line 241 also uses the understated `weight`.

The actual fee paid is `sum(inputs) - sum(outputs)` (see `fee()`, lines 138-141), which still equals `fee_per_vbyte * underestimated_vbytes` because the `OP_RETURN` output carries zero value. So the signed transaction pays a fee computed for a smaller transaction — its effective feerate is strictly lower than the caller-requested `fee_per_vbyte`.

### Impact Explanation
Funds reported spendable that are not spendable in practice:

- When `fee_per_vbyte` is at or near the minimum relay rate (1 sat/vbyte), a transaction carrying a large data payload (up to 80 bytes, i.e. ~90+ additional vbytes since it's non-witness data) has an effective feerate below `DEFAULT_MIN_RELAY_TX_FEE`. Bitcoin nodes reject it with "min relay fee not met" on `sendrawtransaction`.
- The transaction is already fully formed and the FROST signing session commits to `Prevouts::All` and the exact outputs (`taproot_key_spend_signature_hash`, send.rs lines 373-390). Once signatures are produced, the fee cannot be raised — the change output was already fixed using the underestimated fee. The inputs (including Serai-owned change) are bound to a transaction that cannot be broadcast; the spend must be re-constructed and re-signed from scratch.
- Additionally, a transaction near `MAX_STANDARD_TX_WEIGHT` with data can exceed the standardness limit while the check at line 241 passes, again yielding an unbroadcastable transaction.

This mirrors the report's impact: the accounting says one thing (fee covers `fee_per_vbyte`; change value X), while the deliverable object (the signed transaction) doesn't satisfy it — outputs are locked until an out-of-band rebuild.

### Likelihood Explanation
Medium. The bug triggers deterministically whenever `data.is_some()` — the fee is *always* understated for data-carrying transactions. The damage (broadcast rejection) materializes only when the chosen `fee_per_vbyte` is close to the minimum relay rate and the data payload is large, or when the transaction is near the standard weight cap. Callers paying a comfortable feerate merely overpay... rather, merely pay a slightly lower effective rate than requested (the tx still confirms). The reachable trigger — untrusted instruction data of up to 80 bytes flowing into outbound transactions combined with a minimal fee policy — is plausible for an automated processor that reacts to on-chain instructions, but it requires the integrator to select a near-minimum fee rate.

### Recommendation
Include the data output in the size estimate, mirroring the external report's recommendation to measure the real result rather than the nominal one. Concretely, build the full output list (payments + `OP_RETURN` + change) before calling `calculate_weight_vbytes`, e.g. change its signature to take the actual `tx_outs: &[TxOut]` (or pass `data.len()`) so `weight`, `vbytes`, `needed_fee`, the min-relay check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction that is actually produced. At minimum:

```rust
// include the OP_RETURN output in both estimate calls
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, None, data.as_deref());
```

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs semantics demo
// A caller requests the minimum viable fee rate and attaches 80 bytes of data.

let fee_per_vbyte = 1; // sat/vb, the minimum relay rate
let data = vec![0u8; 80]; // max allowed by the TooMuchData check

// SignableTransaction::new computes:
//   vbytes           = size(inputs + payments + change)            // NO OP_RETURN
//   needed_fee       = 1 * vbytes
//   min-relay check  = needed_fee >= DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000  // passes
//
// but the produced tx also contains:
//   TxOut { value: 0, script_pubkey: OP_RETURN <80 bytes> }        // ~93 more vbytes
//
// actual_vsize  ≈ vbytes + 93
// actual feerate = needed_fee / actual_vsize < 1 sat/vb
//
// => SighashCache commits to this exact tx (Prevouts::All), signatures are
//    produced, and bitcoind rejects sendrawtransaction:
//    "min relay fee not met". The inputs cannot be spent by this signed tx;
//    the entire FROST signing round must be discarded and redone.
```

The structural defect is directly visible in the code: `data` is pushed to `tx_outs` (send.rs:194-202) but every `calculate_weight_vbytes` call site (send.rs:204, 226) receives only `payments`, so the declared fee/weight never accounts for the real output set — the same "credited amount doesn't match delivered amount" mismatch as `_strategy.increasePoolAmount(amountAfterFee)` in the source report.
