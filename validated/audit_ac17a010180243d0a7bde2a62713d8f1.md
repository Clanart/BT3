### Title
Division-by-zero panic in `consolidatedNode.Split` when a proposer's CL staking pool has zero stake - ([File: kaiax/staking/staking_info.go])

### Summary
`consolidatedNode.Split` divides a reward amount by `totalAmount = StakingAmount + CLStakingAmount` without checking that this sum is non-zero, analogous to the reported `Reward.sol` issue where a zero `exchangeRate` denominator was never validated before being used to compute a user's redeemable amount.

### Finding Description
`consolidatedNode.Split` computes the CL/CN reward split as:
```
totalAmount = cnAmountBig + clAmountBig
clAmount = clAmountBig * amount / totalAmount
``` [1](#0-0) 

There is no guard ensuring `totalAmount > 0` before the `Div` call. In Go, `big.Int.Div` with a zero divisor panics.

This function is invoked unconditionally for the block proposer in `specWithProposerAndFundsFlex` and `specWithProposerAndFunds` whenever the proposer's consolidated node has a non-nil `CLStakingInfo`, with no check on the magnitude of `StakingAmount` or `CLStakingAmount`: [2](#0-1) [3](#0-2) 

By contrast, the staking-reward distribution helpers (`assignStakingRewards`, `assignStakingRewardsFlex`) only call `cn.Split` after already confirming the CN's total stake exceeds `minStake`/threshold, so `totalAmount` is guaranteed non-zero there (`cnTotalStakingAmount > minStake` / `excessInt[...] > 0`) [4](#0-3) [5](#0-4) . The proposer path has no equivalent check.

Under the `IsSimple == false` policy (`istanbul.policy == WeightedRandom`, i.e., non-Simple, which is required to reach `getDeferredRewardFull`) [6](#0-5) , if `CLStakingInfo` exists for the elected proposer's node (registered via `CLRegistry`/consensus-liquidity registration, reachable by an unprivileged staker who registers a CL pool) but that pool's `CLStakingAmount` becomes `0` (e.g., all delegated stake withdrawn) while the CN's own `StakingAmount` is also `0` or otherwise makes the sum `0`, `cn.Split(proposer)` divides by zero and panics.

### Impact Explanation
A panic inside `FinalizeState`/block-reward computation is triggered deterministically for every node processing that block, since it's pure Go arithmetic executed identically on every node computing rewards (this includes the `kaia_getReward`/`kaia_getRewardsAccumulated` RPC handlers and the reward module used during block finalization). This halts block finalization / reward RPCs — a liveness-impacting bug in the reward-distribution and block-assembly path, matching the "acceptance/processing of a block leading to a crash across validators" bucket in scope. It does not require any privileged action — an ordinary staker/CL-pool participant fully withdrawing consensus liquidity from a validator's pool while that validator remains eligible to be a round/weighted proposer is sufficient to arm the crash.

### Likelihood Explanation
Likelihood is Medium: it requires (1) Prague hardfork active with consensus liquidity (`CLStakingInfo` populated) [7](#0-6) , and (2) a validator whose CN's own `StakingAmount` combined with its CL pool's `CLStakingAmount` reaches zero while it's still selected as block proposer. Whether a CN with zero stake can still be selected as proposer depends on validator/committee selection logic not fully reviewed here (uncertain — I could not verify the exact CN-eligibility/committee-selection rules that gate proposer selection), so this should be validated against the proposer-selection code before treating it as fully confirmed exploitable, but the missing zero-check itself is a clear code-level defect independent of that gate.

### Recommendation
Add an explicit zero-check in `consolidatedNode.Split` before dividing:
```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}
	cnAmountBig := big.NewInt(int64(c.StakingAmount))
	clAmountBig := big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
	totalAmount := new(big.Int).Add(cnAmountBig, clAmountBig)
	if totalAmount.Sign() == 0 {
		return amount, big.NewInt(0) // or handle explicitly
	}
	...
}
```

### Proof of Concept
1. Enable Prague/consensus-liquidity and non-Simple istanbul policy so `getDeferredRewardFull` → `specWithProposerAndFundsFlex`/`specWithProposerAndFunds` path is used [8](#0-7) .
2. Register a CL pool for validator V (`CLStakingInfo` populated with `CLStakingAmount > 0` initially).
3. As an unprivileged staker, withdraw all delegated stake from V's CL pool so `CLStakingAmount` becomes `0`; ensure V's own `StakingAmount` in `AddressBook`/CNStaking is also `0` (or otherwise causes the consolidated total to be zero).
4. When V is elected/rotated as the block proposer, `specWithProposerAndFundsFlex`/`specWithProposerAndFunds` calls `cn.Split(proposer)` unconditionally [9](#0-8) , which panics inside `consolidatedNode.Split` due to division by `totalAmount == 0` [10](#0-9) .

Note: I was not able to fully trace the proposer-selection/eligibility code within the indexed context to conclusively confirm a zero-stake CN can be chosen as proposer under all configurations; this is the main remaining uncertainty for exploitability and should be verified directly against the istanbul consensus/proposer-selection implementation.

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
```
