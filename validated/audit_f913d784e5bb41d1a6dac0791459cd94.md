### Title
Same-chain partial fill releases the entire pooled token escrow bucket instead of the per-output-index share when two output assets share an input token - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
The external report's core broken invariant is: a value that must be shared across N recipients is tracked as a single pooled/aggregated quantity, but is consumed by "give the full remaining pool to whoever finishes their sub-claim" logic instead of a per-recipient allotment. In Party DAO this was voting power rounding; in Hyperbridge's `IntrinsicIntents.sol` same-chain intent-fill path, the analogous broken invariant is: escrow is tracked per `(commitment, token address)` in `IntentsBase._orders`, not per output-asset index, while the "final fill gets the whole remaining balance" dust-fix released at `evm/src/apps/intentsv2/IntrinsicIntents.sol:116-121` assumes the entire remaining bucket for that token belongs exclusively to the output index currently being completed.

### Finding Description
`_orders` is keyed only by `(commitment, token)`: [1](#0-0) 

`_fillSameChain` computes, per output index `i`, the escrow to release using the **same index** `i` into `order.inputs`: [2](#0-1) 

When an output index reaches `amountFilled == totalRequired`, the code does not compute a proportional/allotted share — it reads `_orders[commitment][inputToken]`, i.e. the *entire* remaining escrow balance currently stored for that token, and hands it all to whichever solver completes that index: [3](#0-2) 

This "final solver gets remaining balance" pattern was deliberately added to fix integer-division dust loss (see the explicit regression tests `testPartialFill_RoundingDustReleasedToFinalSolver*`), which correctly assumes a *single* input token backs a *single* output asset for the life of the order: [4](#0-3) 

The flaw: nothing in `placeOrder`/`_fillSameChain` prevents an order from declaring two (or more) output assets at indices `i` and `j` that are both funded from the **same** `inputs[token]` address (e.g. a user paying USDC-in-multiple-tranches order, or a duplicate token entry). Because `_orders` pools escrow by token address across all indices sharing that token, completing output index `i` first triggers `escrowedAmount = _orders[commitment][token]` — draining the *whole* pooled bucket, including the portion that was escrowed to satisfy the still-unfilled output index `j`. `_withdraw` then zeroes/decrements the shared bucket: [5](#0-4) 

Any subsequent attempt to complete index `j` reads `escrowed == 0` and reverts with `UnknownOrder`, permanently locking output index `j` (and the corresponding user funds already paid out to the wrong solver) — or, if a small remainder happens to still exist, releases an incorrect (too-small or too-large) amount to the second solver. Either way, the pooled bucket-vs-per-index accounting mismatch produces an unauthorized/incorrect amount transfer or a fund lock, exactly analogous to the Party DAO bug where a shared pooled quantity (voting power denominator) didn't correctly sum/allocate to each individual claimant.

### Impact Explanation
This falls squarely within the accepted impact categories: wrong beneficiary/amount and loss/lock of escrowed user funds in the Intent Gateway's bridge-custody path. A solver that completes the first of two same-token output legs receives escrow intended for the second leg's future filler, and the second leg's rightful solver either receives nothing (order un-fillable, user funds stuck) or an incorrect amount. No relayer, prover, or admin is involved — this is a pure smart-contract accounting bug reachable by any two competing solvers (or even a single solver deliberately splitting their own fills) calling the public `fillOrder` entrypoint.

### Likelihood Explanation
Likelihood is moderate: it requires an order to be crafted (by the user or session key) with more than one output asset entry that resolves to the same input token address — not explicitly forbidden by any validation seen in `IntentsBase`/`IntrinsicIntents`. Because `placeOrder` accepts arbitrary `TokenInfo[]` arrays for `inputs`/`outputs`, a malicious or careless order author (or a solver colluding with the order's session key) can construct such an order intentionally to grief a second solver or to extract more than their entitled share by racing to complete the "first" index of a shared-token pair.

### Recommendation
Track escrow per output index (or per unique input-array index) rather than pooling by bare token address, or explicitly reject orders whose `inputs` array contains duplicate token addresses across indices that map to distinct output assets. When releasing escrow on final-fill-of-an-index, cap the release at the amount originally allocated to that specific index (`order.inputs[i].amount` minus what's already been released for index `i`), never at the raw shared `_orders[commitment][token]` balance, unless it's verified that index `i` is the *only* remaining consumer of that token bucket.

### Proof of Concept
1. User places a same-chain order with `output.assets = [{token: DAI, amount: 100}, {token: DAI, amount: 50}]` and correspondingly `inputs = [{token: USDC, amount: 100e6}, {token: USDC, amount: 50e6}]` (both input entries reference the same USDC token address). `_orders[commitment][USDC]` accumulates to `150e6`.
2. Solver A fully fills output index 0 (provides 100 DAI). In `_fillSameChain`, `amountFilled == totalRequired` for index 0, so `escrowedAmount = _orders[commitment][USDC] = 150e6` (the full pooled balance, not just the 100e6 allocated to index 0). Solver A receives all 150e6 USDC; `_orders[commitment][USDC]` is set to 0.
3. Solver B attempts to fill output index 1 (provide 50 DAI, expecting 50e6 USDC). `_withdraw` reads `escrowed = _orders[commitment][USDC] == 0` and reverts `UnknownOrder`, permanently blocking index 1 and leaving Solver B unable to claim USDC despite having (or being ready to provide) the DAI — while Solver A walked away with 50e6 USDC beyond their entitlement.
