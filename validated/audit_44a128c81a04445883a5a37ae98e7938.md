## Title
Unbounded, cheaply-grown vote-account set is fully iterated (no pagination/cap) on every `getVoteAccounts` RPC call - ([File: rpc/src/rpc.rs])

## Summary
`RpcSol::get_vote_accounts` in `rpc/src/rpc.rs` retrieves `bank.vote_accounts()` and does a full, unpaginated `.iter().filter_map(...)` scan of every entry on each call, performing per-account vote-state deserialization, epoch-credits slicing, and string formatting. Since vote accounts can be created permissionlessly and cheaply (rent-exempt `VoteStateV4::size_of()` bytes, no stake requirement), and are only removed via explicit `Withdraw`, an unprivileged actor can grow this set indefinitely, making every future `getVoteAccounts` call cost strictly more CPU/latency with no upper bound.

## Finding Description
`get_vote_accounts` fetches `bank.vote_accounts()` and iterates it entirely: [1](#0-0) 

The only bound present is on epoch-credits history *per account* (`MAX_RPC_VOTE_ACCOUNT_INFO_EPOCH_CREDITS_HISTORY`), not on the number of accounts iterated: [2](#0-1) 

`RpcGetVoteAccountsConfig` has no `limit`/`offset`/cursor field, confirming the absence of pagination at the protocol level: [3](#0-2) 

The underlying `Stakes` admission logic accepts any correctly-sized, initialized, vote-program-owned account with no stake requirement (`vote_accounts.insert(*pubkey, (0, vote_account))` — activated stake `0` is accepted): [4](#0-3) 

Creating such an account requires only a permissionless `InitializeAccount`/`InitializeAccountV2` instruction after `CreateAccount`, with no admin permission or stake delegation: [5](#0-4) 

By contrast, the consensus/epoch-reward path explicitly filters the vote-account set to `MAX_ALPENGLOW_VOTE_ACCOUNTS` before iterating for reward distribution, showing engineers recognized and mitigated this exact class of risk elsewhere but did not apply the same guard to the RPC-facing `get_vote_accounts` path: [6](#0-5) 

## Impact Explanation
This matches the explicitly allowed "single-client low-rate RPC crash/degradation" impact class: an unprivileged actor who cheaply inflates `bank.vote_accounts()` can cause any single caller invoking `getVoteAccounts` to experience unbounded latency growth, excessive CPU/memory usage per request, and potential RPC-thread degradation, without needing validator/admin privilege.

## Likelihood Explanation
The attack path is straightforward and requires only ordinary, unprivileged transactions (rent-exemption payment plus `CreateAccount`/`InitializeAccount`), repeatable at will with no protocol-enforced cap on vote-account count. The `getVoteAccounts` RPC method is a standard, widely used JSON-RPC call reachable without any special permission, making the degradation trivially triggerable once the set has been inflated.

## Recommendation
Add pagination (`limit`/`offset`/cursor) to `RpcGetVoteAccountsConfig` and enforce a hard cap on the number of vote accounts scanned per `get_vote_accounts` call, or apply the existing VAT-style minimum-stake/minimum-balance eligibility filter used in the epoch-reward path to the RPC-visible vote-account set so cheaply created, unstaked accounts cannot inflate the fully-scanned structure.

## Proof of Concept
1. Fund a keypair and repeatedly submit `system_instruction::create_account` + `vote_instruction::create_account_with_config`/`initialize_account`, paying only rent-exemption for `VoteStateV4::size_of()` bytes, to create N unstaked vote accounts (see `cli/src/vote.rs::process_create_vote_account` for the exact instruction sequence): [7](#0-6) 
2. Repeat until N is large; each persists in `bank.vote_accounts()` since admission requires only correct size/initialization, not stake, as shown in `Stakes::new_from_accounts_for_genesis`/the equivalent runtime insertion path.
3. Call `getVoteAccounts` against the target RPC node and observe response latency/CPU scaling linearly with N due to the full, unpaginated iteration in `get_vote_accounts`.
