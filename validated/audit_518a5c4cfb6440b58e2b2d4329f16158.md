### Title
Unvalidated `kip71.gastarget = 0` governance vote causes division-by-zero panic in `NextMagmaBlockBaseFee` — ([File: params/kip71_config.go])

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by `kc.GasTarget` in both the "gas used above target" and "gas used below target" branches. `GasTarget` is a mutable governance parameter (`kip71.gastarget`) whose `FormatChecker` is `noopFormatChecker` — it accepts any `uint64`, including `0`. This exactly mirrors the reported bug class: acceptance of `0` for a value later used as an unguarded divisor/threshold. Notably, the sibling parameter `BaseFeeDenominator` in the very same function *does* have an explicit zero-guard ("To avoid panic, set the fluctuation range small"), but `GasTarget` does not.

### Finding Description
`GetDefaultKIP71Config`/`KIP71Config.NextMagmaBlockBaseFee` computes the next block's base fee (Magma/KIP-71) using `GasTarget` as a divisor: [1](#0-0) [2](#0-1) [3](#0-2) 

Unlike `BaseFeeDenominator`, which has an explicit guard against `0` right above (`if kc.BaseFeeDenominator == 0 { baseFeeDenominator = 64 }`), `gasTarget := kc.GasTarget` has no such guard. If `parentGasUsed != gasTarget` (true almost always when `gasTarget == 0` and any gas is used in a block), the code executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with a zero divisor, which panics in Go's `math/big` package.

`GasTarget` is exposed as the governance parameter `kip71.gastarget`: [4](#0-3) 
Its `FormatChecker` is `noopFormatChecker`, which unconditionally returns `true`: [5](#0-4) 

The vote-value validation pipeline (`NewVoteData` -> canonicalize -> `FormatChecker`) accepts `0` for `Kip71GasTarget`, and the additional consistency check `checkConsistency` in header governance explicitly lists `gov.Kip71GasTarget` among parameters that get "no more checks" beyond the format check: [6](#0-5) [7](#0-6) 

The test suite even documents `uint64(0)` as a "bad vote" only for `Kip71MaxBlockGasUsedForBaseFee`, not for `Kip71GasTarget` — confirming `GasTarget = 0` is a currently *accepted* format: [8](#0-7) 

### Impact Explanation
Once a council/governing-node vote sets `kip71.gastarget = 0` and it becomes effective (after being aggregated into the `ParamSet` and propagated into `ChainConfig.Governance.KIP71.GasTarget`), every node computing or verifying the Magma/KIP-71 base fee for any block with nonzero gas usage (essentially every subsequent block) will panic inside `NextMagmaBlockBaseFee` during header verification/block building. This is not a bounded local error — it is a runtime panic in a function invoked as part of core header validation and block assembly, meaning honest nodes could crash or halt block processing network-wide, i.e., a chain-halting consensus-critical bug, not just localized DoS to one caller. This matches the "state transition / gas accounting" and "governance parameters" reachable-path categories permitted by the rules.

### Likelihood Explanation
Setting a governance parameter requires the governing node / council voting privilege (same level of privilege as the original Chainlink report's "oracle owner sets pricingTimeout=0" — an authorized-but-unvalidated misconfiguration, not a fully anonymous public call). Given `FormatChecker` and `checkConsistency` place **no restriction** on `GasTarget` being `0` (unlike `BaseFeeDenominator`, `LowerBoundBaseFee`/`UpperBoundBaseFee`, or `IstanbulCommitteeSize`, all of which have nonzero/consistency checks), a single malformed or malicious vote (or governance UI/tooling bug that fails to reject 0) is sufficient to trigger the condition on the very next processed block with nonzero gas usage.

### Recommendation
Add an explicit zero-guard for `GasTarget` in `NextMagmaBlockBaseFee` analogous to the existing `BaseFeeDenominator` guard (e.g., fall back to `DefaultGasTarget` or treat `gasTarget == 0` as `parentGasUsed == gasTarget` to skip the division), and/or reject `0` in `Kip71GasTarget`'s `FormatChecker` in `kaiax/gov/param.go`, mirroring the `Kip71BaseFeeDenominator` checker (`v != 0`).

### Proof of Concept
1. A governance vote sets `kip71.gastarget` to `uint64(0)` via `NewVoteData(voter, "kip71.gastarget", uint64(0))`; because `FormatChecker` is `noopFormatChecker`, `NewVoteData` succeeds and the vote is accepted, and `checkConsistency` performs no further validation for this parameter.
2. Once finalized in a `ParamSet`/`ChainConfig.Governance.KIP71.GasTarget = 0`, on the next block whose `parentHeaderGasUsed != 0` (i.e., essentially any normal block), `NextMagmaBlockBaseFee` executes:
   - `parentGasUsed := min(parentHeaderGasUsed, upperGasLimit)` — nonzero.
   - Since `parentGasUsed != gasTarget (0)`, it enters the `>` branch, computing `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`, which panics with "division by zero" in `math/big`.
3. This function is invoked from block header validation via `VerifyMagmaHeader`, so this panics deterministically across every node validating the resulting header.

Note: I was unable to fully trace every call site (e.g. `blockchain/block_validator.go` invocation context) due to remaining tool-call budget, but the direct call chain `VerifyMagmaHeader -> NextMagmaBlockBaseFee` and the unguarded governance-parameter path are confirmed directly in the cited source.

func NewVoteData(voter common.Address, name string, value any) VoteData {
	param, ok := gov.Params[gov.ParamName(name)]
	if !ok {
		param, ok = gov.ValidatorParams[gov.ParamName(name)]
		if !ok {
			logger.Error("Invalid vote name", "name", name)
			return nil
		}
	}

	cv, err := param.Canonicalizer(value)
	if err != nil {
		logger.Error("Canonicalize error", "name", name, "value", value, "err", err)
		return nil
	}

	if !param.FormatChecker(cv) {
		logger.Error("Format check error", "name", name, "value", value)
		return nil
	}

	return &voteData{
		voter: voter,
		name:  gov.ParamName(name),
		value: cv,
	}
}
