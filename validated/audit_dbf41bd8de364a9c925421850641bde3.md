## Analog Found

### Title
Front-running of VC revocation (`revoke_vc`) allows a malicious credential holder to claim/move Credential-Restricted CAT funds before the restricting DID authority's revocation lands - ([File: chia/wallet/vc_wallet/vc_wallet.py])

### Summary
The Dinari `TransferRestrictor.restrict()` bug is a classic "blacklist front-running" pattern: a privileged actor submits a transaction that will cut off a malicious user's ability to move funds, but the malicious user can watch the mempool and front-run it. Chia's Verifiable Credential (VC) / Credential-Restricted CAT (CR-CAT) system implements the same conceptual "restrict/blacklist" pattern on-chain: a DID authority revokes a user's VC to cut off that user's ability to spend CR-CATs gated on that VC's authorized-provider proofs. Because the revocation and the user's own spend are two independently-signed transactions that both consume the *same* VC coin, whichever spend is mined first wins — giving the malicious VC holder an opportunity to front-run the revocation.

### Finding Description
A CR-CAT's spendability is gated by presenting a valid, unspent `VerifiedCredential` (VC) issued by an `authorized_provider` (a DID), with `proofs_checker`-approved flags [1](#0-0) . The DID authority "restricts" a user by revoking their VC through `VCWallet.revoke_vc`, which spends the DID coin together with the VC coin, using the VC's built-in backdoor (`activate_backdoor` / `REVOCATION_LAYER`) to invalidate it going forward [2](#0-1) [3](#0-2) .

However, the same VC coin can also be spent by its legitimate holder for ordinary purposes — e.g., updating proofs, transferring the VC, self-revoking, or (most importantly) authorizing a `claim_pending_approval_balance` spend that releases CR-CAT funds sitting in the "pending approval" state into the holder's own wallet [4](#0-3) . Both the provider's revocation spend and the holder's self-initiated spend consume the identical VC coin, so they are mutually exclusive in the mempool: only one can be included in a block.

Because a `restrict`-equivalent revocation transaction (`vc_revoke`/`RevokeVCCMD`) is broadcast the same way as any other transaction, a malicious VC holder monitoring the mempool can detect the provider's incoming revocation spend and immediately submit a competing higher-fee spend of the same VC coin — for example a `claim_pending_approval_balance` transaction — to pull already-pending, provider-approved CR-CAT funds into their own spendable balance before the revocation lands. Once the CR-CAT is out of the "pending approval" puzzle and into the holder's ordinary inner puzzle hash, the provider's revocation of the VC no longer has any effect on those coins, since they're no longer gated by the credential-restriction layer.

This mirrors the report's bug class precisely: an authority intends to restrict/blacklist an address's ability to move/claim funds, but the restricted party can win a mempool race and complete the restricted action first.

### Impact Explanation
A user who is about to be revoked (e.g., for compliance/fraud reasons — the entire purpose of the VC/CR-CAT credential-restriction system) can preempt the revocation and permanently move CR-CAT funds that were meant to be frozen/restricted out of the credential-gated state. This defeats the security guarantee that CR-CATs provide (only credentialed, provider-approved holders can move restricted assets), directly undermining the asset issuer's compliance control — the core purpose of the `CREDENTIAL_RESTRICTION` puzzle layer [5](#0-4) .

### Likelihood Explanation
Any mempool observer can detect a pending `vc_revoke` spend bundle (it spends a specific, known VC coin and DID coin) and submit a competing higher-fee transaction spending the same VC coin. No special privileges are required beyond already holding the VC and having pending approvable CR-CAT balance, which is the normal state of an actively-restricted user right before revocation.

### Recommendation
- Avoid relying purely on mempool-race semantics for a security-critical action like credential revocation; consider a design where revocation can supersede/void pending-approval claims even if a competing spend is mined first (e.g., revocation checks a freshness window, or approvals require a time-lock/challenge period during which revocation always wins).
- Alternatively, submit revocation transactions via a private mempool / direct-to-block-producer channel to avoid mempool visibility, and/or require a minimum on-chain relative time-lock on `claim_pending_approval_balance` spends so that a pending compliance revocation has time to be observed and prioritized.

### Proof of Concept
1. DID authority `P` issues a VC to user `U` and later determines `U` should be revoked (analogous to `restrict()` blacklisting) because `U` holds CR-CATs pending approval that should not be released.
2. `P` calls `vc_revoke` and broadcasts a spend bundle that spends `U`'s VC coin via `activate_backdoor` [6](#0-5) .
3. `U` monitors the mempool, sees the pending revocation spend targeting their VC coin, and immediately submits a `claim_pending_approval_balance` transaction (also spending the same VC coin) with a higher fee, moving the CR-CAT funds out of the pending-approval puzzle hash into `U`'s ordinary spendable balance [4](#0-3) .
4. If `U`'s transaction is included first, the VC coin is consumed by `U`'s spend, `P`'s revocation spend bundle becomes invalid (double-spend of same coin) and is dropped from the mempool, and `U` has successfully claimed the funds that were meant to be frozen by the revocation.

# Basic drivers
def construct_cr_layer(
    authorized_providers: list[bytes32],
    proofs_checker: Program,
    inner_puzzle: Program,
) -> Program:
    first_curry: Program = CREDENTIAL_RESTRICTION.curry(
        CREDENTIAL_STRUCT,
        authorized_providers,
        proofs_checker,
    )
    return first_curry.curry(first_curry.get_tree_hash(), inner_puzzle)
