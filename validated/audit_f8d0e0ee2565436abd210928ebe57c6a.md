### Title
Markdown link-click handler enforces `http:` in addition to documented `https`-only policy, enabling clear-text link dispatch from untrusted content - (File: `app/src/ui/lib/sandboxed-markdown.tsx`)

### Summary
`SandboxedMarkdown` documents that its `onMarkdownLinkClicked` callback only fires for links that have been "verif[ied] to be https", but the actual guard in `setupLinkInterceptor` checks a broader regex that also accepts `http:`. This is the same class of bug as the reported `validateOrderParam` issue: the enforced check does not match the constant/invariant the code claims to enforce, silently weakening the intended security boundary.

### Finding Description
The prop doc comment states the enforcement invariant explicitly: [1](#0-0) 

But the actual implementation of the click interceptor uses a regex that matches both `http:` and `https:`: [2](#0-1) 

`/^https?:/.test(a.protocol)` is true for `http:` as well as `https:`, so any `<a href="http://...">` link embedded in rendered markdown (which is untrusted content — PR bodies, issue/comment bodies, release notes, commit messages, Copilot conflict summaries, all of which are rendered through this same `SandboxedMarkdown` component per the multiple callers found: `pull-request-quick-view.tsx`, `pull-request-comment-like.tsx`, `release-notes-dialog.tsx`, `copilot-conflicts-dialog.tsx`, `copilot-conflicts-resolution-summary.tsx`) will successfully invoke `onMarkdownLinkClicked` and be dispatched to the OS/browser exactly as if it were an `https:` link. This exactly mirrors the reported bug pattern: the code's documented/intended constraint ("must be https") is not what is actually checked at runtime — the hardcoded regex is broader than the invariant it is meant to enforce.

### Impact Explanation
An attacker who controls a PR description, PR/issue comment, commit message, or other GitHub-hosted markdown rendered by Desktop can embed a plain `http://` link. Instead of the app enforcing HTTPS-only outbound navigation (the explicit security property called out in the code comment), it will silently downgrade to allowing clear-text HTTP dispatch. This exposes users to on-path tampering/redirection and defeats the intended defense-in-depth against link-based attacks in untrusted content, without requiring any unusual user action beyond the normal expected click on a rendered link.

### Likelihood Explanation
High reachability: the vulnerable check is a single regex in a component rendered for many untrusted, remotely-sourced markdown sources (PRs, comments, release notes) as confirmed by the multiple call sites found. No special user privilege or local access is required — only that the user click a link in attacker-supplied markdown, which is the exact interaction this feature exists to support.

### Recommendation
Change the check in `setupLinkInterceptor` to strictly match the documented invariant, e.g. `a.protocol === 'https:'`, rather than the broader `/^https?:/` regex, so behavior matches the documented "must be https" contract.

### Proof of Concept
1. Render a PR/issue comment or PR body containing `[click me](http://attacker.example/track)` through any consumer of `SandboxedMarkdown` (e.g. `pull-request-comment-like.tsx`).
2. Click the rendered link inside the sandboxed iframe.
3. `setupLinkInterceptor`'s check `/^https?:/.test(a.protocol)` evaluates true for `http:`, so `onMarkdownLinkClicked('http://attacker.example/track')` fires and the link is opened externally, contrary to the documented https-only guarantee. [2](#0-1)

```typescript
  private setupLinkInterceptor(doc: Document): void {
    doc.addEventListener('click', ev => {
      if (doc.defaultView && ev.target instanceof doc.defaultView.Element) {
        const a = ev.target.closest('a')
        if (a !== null) {
          ev.preventDefault()

          if (/^https?:/.test(a.protocol)) {
            this.props.onMarkdownLinkClicked?.(a.href)
          }
        }
      }
    })
  }
```
