Found the analog: `RegisterPointer` in the EVM module is a fully permissionless message — any transaction sender can call it, and unlike the CosmWasm precompile equivalents (`AddCW20`/`AddCW721`/`AddNative`), it drives a `wasmKeeper.Migrate` on an already-live pointer contract holding user funds, gated only by a version check, with no check on whether the pointer contract currently has balances/state that could be broken by a migration to a different stored code ID.

### Title
Permissionless `RegisterPointer` message allows any user to trigger migration of a live, fund-holding CW pointer contract - (File: x/evm/keeper/msg_server.go)

### Summary
`MsgRegisterPointer` is dispatched to `msgServer.RegisterPointer` with no admin/authority check on `msg.Sender` at all — it is a fully public, permissionless transaction that any account can submit for any `ErcAddress`/`PointerType`. [1](#0-0)  When a pointer for that ERC address already exists but its stored version is lower than `currentVersion`, the handler does not create a new contract but instead calls `wasmKeeper.Migrate` directly on the *existing* pointer address, using whatever CW code ID is currently stored via `GetStoredPointerCodeID` (which is set by chain upgrades/governance, not validated against the caller). [2](#0-1) 

### Finding Description
This mirrors the `updateFounders` bug class: a state-mutating "administrative" action (registering/upgrading the token's pointer implementation) that is meant to be an infrastructure-level bootstrap/upgrade action, but has no guard tying it to the lifecycle state of the pointee. In the referenced Nouns Builder bug, `updateFounders` lacked the `mintCount > 0` / `totalSupply > 0` guards that its sibling `setReservedUntilTokenId` enforces, letting founder allocations be rewritten after tokens were already minted and control handed to the DAO. Here, `RegisterPointer` similarly lacks any check on whether the *existing* pointer contract already has live balances/holders (i.e., has already been used in production, analogous to "tokens already minted") before letting a random caller trigger a `Migrate` call that swaps in a new CW code implementation at the currently-configured `codeID`.

Unlike the sibling precompile functions `AddCW20`/`AddCW721`/`AddNative` in `precompiles/pointer/...`, which only ever *create* a brand-new pointer via `evm.Create` when no pointer exists (and reject with an error if one already exists at a version `>= 1`) [3](#0-2) , `RegisterPointer`'s migrate branch is reachable by anyone as soon as a chain upgrade bumps `erc20.CurrentVersion`/`erc721.CurrentVersion`/`erc1155.CurrentVersion` and stores a new code ID — at that point *any* unprivileged account can force-migrate the live pointer contract that already holds/represents user token balances, with the only gate being the version comparison, not any authorization or fund-safety check.

### Impact Explanation
If the newly stored pointer CW code (set for an unrelated future ERC version bump) is not state-layout/interface compatible with the currently deployed pointer instance's stored state, forcing this migration via an unprivileged, front-runnable transaction could corrupt the pointer's internal token-accounting state (balances/allowances/owners it wraps), potentially freezing user funds represented by the pointer or causing accounting mismatches between the CW-side token and its ERC pointer. This falls under "unauthorized transfer via precompile or pointer" / "permanent freezing" impact categories, since the pointer contract mediates real token balances between the CW and EVM sides and any account (not just the chain/governance) can trigger this state transition on a pointer that already has funds locked behind it.

### Likelihood Explanation
Likelihood is tied to the chain performing a pointer version bump (which does happen — the version constants and `GetStoredPointerCodeID` infrastructure exist specifically for periodic upgrades, as shown by the extensive `pointer_upgrade.go` and migration files). Once any such bump occurs, every existing pointer instance becomes eligible for a permissionless `Migrate` call from any sender, with no waiting period, allowlist, or authority check — this is a systemic gap rather than a one-off misconfiguration.

### Recommendation
Add the same category of protective checks used elsewhere in the codebase for pointer creation (e.g., restrict `RegisterPointer`'s migrate path to only be callable by module governance/authority, or require it go through the same "does not already have version >= 1 / live balances" style guard as `AddCW20`/`AddCW721`/`AddNative`), and/or require the new CW code to declare itself compatible with the old state schema before allowing an unprivileged, permissionless `Migrate` call on a pointer that already holds funds.

### Proof of Concept
1. Chain state has a live `CW20->ERC20` pointer contract at address `P` for CW20 token `T`, created via `RegisterPointer` (or the precompile), currently holding accounting state for real token balances routed through it.
2. A chain upgrade bumps `erc20.CurrentVersion` and calls `StoreCWPointerCode`, storing a new code ID under `PointerCW20ERC20Prefix` for the new version. [4](#0-3) 
3. Any unprivileged account submits `MsgRegisterPointer{PointerType: ERC20, ErcAddress: T}`.
4. `RegisterPointer` sees `existingVersion < currentVersion`, and executes `server.wasmKeeper.Migrate(ctx, existingPointer, moduleAcct, codeID, bz)` on the live pointer `P` — with no check that the sender is authorized or that the migration is safe relative to `P`'s existing token-holder state. func (server msgServer) RegisterPointer(goCtx context.Context, msg *types.MsgRegisterPointer) (*types.MsgRegisterPointerResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)
	if server.GetRegisterPointerDisabled(ctx) {
		return nil, fmt.Errorf("registering CW->ERC pointers has been disabled")
	}
	var existingPointer sdk.AccAddress
	var existingVersion uint16
	var currentVersion uint16
	var exists bool
	switch msg.PointerType {
	case types.PointerType_ERC20:
		currentVersion = erc20.CurrentVersion
		existingPointer, existingVersion, exists = server.GetCW20ERC20Pointer(ctx, common.HexToAddress(msg.ErcAddress))
	case types.PointerType_ERC721:
		currentVersion = erc721.CurrentVersion
		existingPointer, existingVersion, exists = server.GetCW721ERC721Pointer(ctx, common.HexToAddress(msg.ErcAddress))
	case types.PointerType_ERC1155:
		currentVersion = erc1155.CurrentVersion
		existingPointer, existingVersion, exists = server.GetCW1155ERC1155Pointer(ctx, common.HexToAddress(msg.ErcAddress))
	default:
		panic("unknown pointer type")
	}
	if exists && existingVersion >= currentVersion {
		return nil, fmt.Errorf("pointer %s already registered at version %d", existingPointer.String(), existingVersion)
	}
