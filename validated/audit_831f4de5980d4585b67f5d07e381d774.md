## Analysis: Single-block-old staking snapshot enables reward-share manipulation

The reported Sherlock bug is a class of "use of instantaneous (non-averaged, non-delayed) state to compute a rate/weight that a party can manipulate within its own transaction/block to redirect value." The closest reachable analog in the `blackvul/kaia--014` codebase is in the `kaiax/staking` module: since the Kaia hardfork, the `StakingInfo` used to compute a validator's proportional share of block staking rewards is sourced from the **immediately preceding block** (`num-1`) rather than from a staking-interval-delayed snapshot as before the hardfork. [1](#0-0) [2](#0-1) 

This value is fed directly into `assignStakingRewards`/`assignStakingRewardsFlex`, which split the staking-reward budget proportionally to each consolidated node's current staking amount: [3](#0-2) 

Because CnStaking deposits (`receive()`/staking functions) take effect immediately with no deposit-side lockup — only withdrawals are subject to `STAKE_LOCKUP` — a staking-contract operator can deposit a large amount of KAIA into their `CnStakingV4` contract in block `N-1`, causing the `StakingInfo` sourced for block `N`'s reward computation (`sourceBlockNum = N-1`) to reflect the inflated stake, and thereby capture an outsized share of the `stakersAlloc` reward budget for that single block, at the expense of the other consolidated nodes: [4](#0-3) [5](#0-4) 

Below is the finding written up per the requested output format.

### Title
Reward-weight computed from a single-previous-block staking snapshot (no averaging/lockup) allows self-funded stake injection to redirect staking rewards - (File: kaiax/staking/impl/getter.go)

### Summary
Since the Kaia hardfork, `StakingModule.GetStakingInfo(num)` sources the staking amounts used for staking-reward distribution from block `num-1` only (`sourceBlockNum(num, isKaia, interval) = num-1`), instead of the interval-delayed snapshot used pre-Kaia. Because CnStaking deposits take effect immediately with no lockup on deposits (only on withdrawal requests), a validator operator can inflate their staking-contract balance by one block prior to a reward-bearing block to receive a disproportionately large share of that block's staking-reward allocation, then withdraw the injected capital afterward, redirecting rewards away from honestly, continuously staked validators.

### Finding Description
`sourceBlockNum` resolves the `StakingInfo` used for a block `num` to `num-1` after the Kaia hardfork: [1](#0-0) 

`GetStakingInfo` fetches this snapshot from `s.Chain.StateAt(header.Root)` for that single historical block, with no time-weighting or averaging of the staking balance over an interval: [6](#0-5) 

This `StakingInfo` (specifically `StakingAmounts`) directly determines each validator's proportional cut of the staking-reward budget in `assignStakingRewards` (Kore rule) and `assignStakingRewardsFlex` (Flex rule): [3](#0-2) [7](#0-6) 

`CnStakingV4` staking deposits are not subject to any lockup — `STAKE_LOCKUP` only gates the time before an *approved withdrawal* becomes executable (`approveStakingWithdrawal` → `withdrawApprovedStaking` after `withdrawableFrom`): [4](#0-3) [8](#0-7) 

Because there is no averaging window and no deposit-side delay (unlike the pre-Kaia rule, which drew the snapshot from the *start of the previous staking interval*, e.g. 86,400 blocks earlier per `RewardStakingUpdateInterval`'s default), a staker can inject capital into their `CnStakingV4` contract at block `N-1` and have it fully counted in the reward split computed for block `N`, one block later. This mirrors the root cause of the referenced Sherlock finding: an instantaneous (non-averaged) state read is used to compute a proportional value (utilization rate there, staking-reward share here), which a party can manipulate with a single self-funded transaction within one block of the value being consumed. [9](#0-8) 

### Impact Explanation
Every block's staking-reward budget (`stakers` in `RewardSpec`) is a fixed pool distributed proportionally to `(stakingAmount - minStake)` across consolidated nodes. By temporarily inflating their own `CnStakingV4` balance one block ahead of a reward-bearing block, an attacker captures a larger fraction of that pool than their genuinely, continuously committed capital would earn — this is reward redirection away from other honest validators, achieved with a single ordinary staking-deposit transaction reachable by any staking-contract owner, no special privilege required beyond already operating a registered CN staking contract.

### Likelihood Explanation
The precondition (being a registered CN with a `CnStakingV4`/`PublicDelegation` contract) is a normal operator capability, not a privileged role. The deposit action is a single, ordinary transaction (`receive()`/stake) with no lockup, and the reward computation is deterministic and public, so the exact block to time the deposit for (to land in `N-1` relative to a reward-bearing block `N`) is fully predictable from chain state. The main friction is that capital must sit in the staking contract for a comparatively short window (versus the full `StakingUpdateInterval` required pre-Kaia) rather than being truly free/flash-loanable within a single block, which lowers — but does not eliminate — the practicality relative to the referenced flash-style attack.

### Recommendation
Consider computing the staking-reward allocation weights from a time-averaged or interval-anchored staking snapshot (as was done pre-Kaia via `StakingUpdateInterval`), or require a minimum bonding duration before newly deposited stake counts toward reward-weight calculations, so that a single-block deposit cannot materially influence the very next block's reward split.

### Proof of Concept
1. Attacker operates a registered CN with an under-minimum or modestly staked `CnStakingV4` contract at block `N-2`.
2. At block `N-1`, attacker sends a large KAIA deposit transaction to their `CnStakingV4` contract (`receive()`), immediately increasing `StakingAmounts[attacker]` as read by `AddressBook`/`MultiCall`.
3. At block `N`, `kaiax/reward` calls `GetDeferredRewardFull` → `assignStakingRewards`/`assignStakingRewardsFlex`, which calls `StakingModule.GetStakingInfo(N)`; per `sourceBlockNum(N, isKaia=true, interval) = N-1`, this returns the inflated balance from block `N-1`. [10](#0-9) 
4. The attacker's `excess = stakingAmount - minStake` is now larger relative to other validators for this one block's `stakersReward` distribution, so `assignStakingRewards` allocates them a disproportionately large `reward` share: [11](#0-10) 
5. After the reward-bearing block(s) of interest have passed, the attacker files `approveStakingWithdrawal`/`withdrawApprovedStaking` to recover the injected capital once `STAKE_LOCKUP` elapses, having already captured the inflated reward share regardless of the eventual withdrawal outcome.

```go
func (s *StakingModule) GetStakingInfo(num uint64) (*staking.StakingInfo, error) {
	isKaia := s.ChainConfig.IsKaiaForkEnabled(new(big.Int).SetUint64(num))
	sourceNum := sourceBlockNum(num, isKaia, s.stakingInterval)

	// Try cache first
	if si, ok := s.stakingInfoCache.Get(sourceNum); ok {
		return si.(*staking.StakingInfo), nil
	}

	// Only before Kaia, try the database
	if !isKaia {
		if si := ReadStakingInfo(s.ChainKv, sourceNum); si != nil {
			s.stakingInfoCache.Add(sourceNum, si)
			return si, nil
		}
	}

	// Read from the state
	si, err := s.getFromStateByNumber(sourceNum)
	if err != nil {
		return nil, err
	}

	// Only before Kaia, write to database
	if !isKaia {
		WriteStakingInfo(s.ChainKv, sourceNum, si)
	}

	// Cache it
	s.stakingInfoCache.Add(sourceNum, si)
	return si, nil
}
```

```go
func sourceBlockNum(num uint64, isKaia bool, interval uint64) uint64 {
	if isKaia {
		if num == 0 {
			return 0
		} else {
			return num - 1
		}
	} else {
		if num <= 2*interval {
			return 0
		} else {
			// Simplified from the previous implementation:
			// if (num % interval) == 0, return num - 2*interval
			// else return num - interval - (num % interval)
			return roundDown(num-1, interval) - interval
		}
	}
}
```

```go
// assignStakingRewardsFlex assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewardsFlex(config *reward.RewardConfig, budget *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		minStake  = config.MinimumStake.Uint64()
		threshold = config.StakingRewardThreshold.Uint64()
		isPrague  = config.Rules.IsPrague

		cns            = si.ConsolidatedNodes()
		excessInt      = make(map[common.Address]uint64)
		totalExcessInt = uint64(0)
	)

	// Calculate the excess stakes (the amount over the threshold) for each CN.
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it. Even if (CNStaking + CLStaking) could be more than minStake,
		// the CNStaking alone must be at least minStake to be eligible.
		if cn.StakingAmount < minStake {
			continue
		}

		amount := cn.StakingAmount
		if isPrague && cn.CLStakingInfo != nil {
			amount += cn.CLStakingInfo.CLStakingAmount
		}

		// Excess is the amount over the threshold (not over minStake).
		if amount > threshold {
			excessInt[cn.RewardAddr] = amount - threshold
			totalExcessInt += excessInt[cn.RewardAddr]
		}
	}

	// Distribute the budget to the CNs based on the excess stakes.
	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(budget)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		if excessInt[cn.RewardAddr] <= 0 {
			continue
		}
		excess := new(big.Int).SetUint64(excessInt[cn.RewardAddr])

		// The KAIA unit will cancel out:
		// reward (kei) = excess (KAIA) * budget (kei) / totalExcess (KAIA)
		reward := new(big.Int).Div(new(big.Int).Mul(excess, budget), totalExcess)
		if reward.Sign() <= 0 {
			continue
		}

		// If Prague and CL is configured for this CN, split the reward between CN and CL.
		if isPrague && cn.CLStakingInfo != nil {
			cnAmount, clAmount := cn.Split(reward)
			alloc[cn.RewardAddr] = cnAmount
			alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
		} else {
			alloc[cn.RewardAddr] = reward
		}
		remaining.Sub(remaining, reward)
	}
	return alloc, remaining
```

```go
// assignStakingRewards assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining
}
```
