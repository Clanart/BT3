### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s — ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to a contract that accepts ETH it cannot move, `Scanner::scan_block` (and `scan_transaction` on a coinbase transaction) returns outputs from a block's coinbase transaction as `ReceivedOutput` — defined as "a spendable output" — even though coinbase outputs are consensus-unspendable for 100 blocks. Downstream, `SignableTransaction::new` treats every `ReceivedOutput` as immediately spendable, so the wallet builds a transaction that the network will reject, and the immature funds are counted toward `inputs`/`NotEnoughFunds` math as if they were usable balance.

### Finding Description
`scan_block` iterates `block.txdata` including `txdata[0]`, the coinbase, and pushes any matching outputs into the result without a maturity or coinbase check:

```rust
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
``` [1](#0-0) 

`scan_transaction` only matches on `output.script_pubkey`, with no coinbase discrimination:

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput { offset: *offset, output: output.clone(), ... });
}
``` [2](#0-1) 

`ReceivedOutput` is documented as "A spendable output" and carries no coinbase/maturity metadata, so the caller cannot distinguish it from a normal output. `SignableTransaction::new` then sums `input.output.value` into `input_sat` and builds `TxIn`s referencing these outpoints; `TransactionSignMachine::sign` produces real FROST signatures over `Prevouts::All`, yielding a fully-signed transaction that is consensus-invalid (`bad-txns-premature-spend-of-coinbase`). [3](#0-2) [4](#0-3) [5](#0-4) 

An unprivileged party (a miner) can reach this purely with public on-chain data: by mining a block whose coinbase pays to a scanned P2TR script, they cause the wallet to report funds as received that are not spendable.

### Impact Explanation
Funds reported received that are not spendable — exactly the "cannot receive/use funds" class of the reference report. The wallet's balance view is inflated by immature outputs, `needed_fee`/`NotEnoughFunds` accounting is wrong, and any spend that includes such an output produces a transaction the network rejects, wasting a full threshold-signing round (preprocesses, shares) across all participants for an output that can never confirm.

### Likelihood Explanation
Requires a miner to pay the scanner's script in a coinbase — an unusual but permissionless action any miner can take at trivial cost (they'd just be donating). More realistically it is triggered accidentally or by an adversary seeking to waste threshold-signing rounds or corrupt accounting. The doc comment notes coinbase outputs are scanned and advises post-processing, but nothing in the type system enforces it and `ReceivedOutput` is explicitly labeled "spendable," so callers handling `scan_block` results generically will trip it.

### Recommendation
Track coinbase provenance: either add an `immature: bool` / confirmation-height field to `ReceivedOutput`, or have `scan_block` skip `block.txdata[0]` by default with a separate explicit `scan_coinbase` API. `SignableTransaction::new` should reject or defer immature inputs.

### Proof of Concept
1. Construct `Scanner::new(key)` for a TweakedKey `key`.
2. Miner crafts a coinbase transaction whose output pays to `p2tr_script_buf(key)` and includes it in a block at height `h`.
3. `scanner.scan_block(&block)` returns a `ReceivedOutput` for that coinbase output.
4. Caller passes it to `SignableTransaction::new(vec![received], payments, ...)`; it is counted in `input_sat` and a `TxIn` is created.
5. `multisig(keys)` → `preprocess` → `sign` → `complete` produces a fully signed transaction spending an outpoint that is consensus-unspendable until height `h+100`; broadcast fails with premature-coinbase-spend.
