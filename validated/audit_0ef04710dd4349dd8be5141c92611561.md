## Analog Found

The core bug class in the report—an unprivileged actor depositing a large amount immediately before a value-distributing event to capture a disproportionate share, diluting/stealing from existing depositors—has a direct, stronger analog in this repo's Wombat staking reward-distribution pipeline (`WombatStaking.sol`, `WombatPoolHelper.sol`, `BaseRewardPool.sol`/`BaseRewardPoolV2.sol`).

### Title
Reward theft via front-running the permissionless `harvest()`/`queueNewRewards` reward injection with a large deposit - (File: wombat/WombatStaking.sol, wombat/WombatPoolHelper.sol, rewards/BaseRewardPool.sol)

### Summary
`BaseRewardPool`/`BaseRewardPoolV2._provisionReward` distributes an incoming lump-sum reward to stakers strictly according to `totalStaked()` measured at the instant `queueNewRewards` executes, rather than time-weighting by how long each staker actually held their stake during the accrual period. `WombatPoolHelper.harvest()` (and `AnkrBNBPoolHelper`/`WombatPoolHelperV2` equivalents) is a fully permissionless, unauthenticated entry point that triggers this reward injection at will. Since deposits in `MasterMagpie`/`WombatStaking` have no lock, vesting, or cooldown period, an attacker can deposit a large stake, immediately call `harvest()`, claim a share of the freshly harvested WOM/bonus rewards proportional to their new (undiluted-by-time) stake, and withdraw—all atomically or within a couple of blocks.

### Finding Description
`WombatStaking.deposit`/`depositLP` and `WombatPoolHelper._stake` register a user's receipt-token stake in `MasterMagpie` with no delay: [1](#0-0) 

`MasterMagpie.withdraw`/`_withdraw` allow immediate exit once `user.available` is non-zero, with no lock: [2](#0-1) 

`WombatPoolHelper.harvest()` is callable by anyone, with no access control beyond pausing: [3](#0-2) 

When `harvest()`/`deposit()`/`withdraw()` trigger `_toMasterWomAndSendReward`, the harvested WOM (and bonus tokens) are pushed into the rewarder via `queueNewRewards`: [4](#0-3) 

`_provisionReward` then splits this lump sum across `totalStaked()` **at the moment of the call**, with no time-weighting for individual receipt-token holders: [5](#0-4) 

Because a staker's `rewardDebt`/`userRewardPerTokenPaid` is only set at deposit time (to the pre-reward `rewardPerTokenStored`), any stake registered before a `queueNewRewards` call—no matter how briefly held—receives a full pro-rata share of that entire reward tranche, which was actually accrued (in `MasterWombat`) based on other users' long-held stakes.

### Impact Explanation
An attacker can:
1. Deposit a very large amount via `WombatPoolHelper.deposit()`/`depositLP()`, instantly registering a large receipt-token stake in `MasterMagpie`'s rewarder.
2. Immediately call the permissionless `harvest()` to force `queueNewRewards`, which distributes the WOM/bonus-token rewards according to the now-inflated `totalStaked()`, granting the attacker a large chunk of yield that was actually earned by long-term stakers.
3. Claim rewards and withdraw the stake immediately, since there is no lock/cooldown.

This constitutes direct theft of unclaimed yield from legitimate long-term stakers, permanently diluting their expected rewards, satisfying the "theft ... of unclaimed yield" impact bar.

### Likelihood Explanation
`harvest()` is unauthenticated and can be called by anyone at any time (e.g., right after a large deposit, or by watching the mempool for another actor's pending harvest and front-running it with a deposit). No capital lock-up, vesting, or minimum staking duration exists to prevent this, and the attack can be executed by any ordinary wallet with sufficient capital and gas, making it highly likely to be attempted whenever `MasterWombat` has significant unharvested rewards pending.

### Recommendation
Introduce a time-weighted reward distribution (e.g., a `lastDepositTimestamp` cooldown before a stake counts toward `queueNewRewards` splits, or an explicit minimum staking duration/deposit-lock before rewards are claimable/withdrawable), or restrict `harvest()`/`queueNewRewards` triggering to prevent same-block/near-instant deposit-then-harvest-then-withdraw sequences. Add regression tests simulating: deposit → harvest → getReward → withdraw within the same or adjacent block to confirm the attacker cannot capture disproportionate rewards.

### Proof of Concept
1. Attacker calls `WombatPoolHelper.deposit(largeAmount, minLiquidity)` → receipt tokens minted and staked into `MasterMagpie` via `depositFor` (`WombatPoolHelper.sol:148-155`, `MasterMagpie.sol:482-505`).
2. Attacker (or anyone) calls `WombatPoolHelper.harvest()` → `WombatStaking.harvest` → `_toMasterWomAndSendReward` → `queueNewRewards` on the rewarder, splitting the harvested WOM according to current `totalStaked()` which now includes the attacker's large stake (`WombatStaking.sol:329-335`, `671-686`; `BaseRewardPool.sol:297-320`).
3. Attacker calls `MasterMagpie` claim path to invoke `BaseRewardPool.getReward`, receiving a disproportionate reward share.
4. Attacker calls `WombatPoolHelper.withdraw()` → `MasterMagpie.withdrawFor` → immediate exit since `user.available` was set at deposit time with no lock (`MasterMagpie.sol:507-534`, `WombatPoolHelper.sol:123-140`).

        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
