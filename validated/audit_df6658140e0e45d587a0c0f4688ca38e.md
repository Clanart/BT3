### Title
Unauthenticated `SendMoveToVaultTx` broadcast call when `Interceptors::Noop` is active - ([File: core/src/servers.rs])

### Summary
When `client_verification=false`, `create_grpc_server` builds the aggregator's TLS config without `client_ca_root` and wraps the service with `Interceptors::Noop`, which passes every request through with no certificate check at all. This means `ClementineAggregator::send_move_to_vault_tx` — which triggers a real state-changing DB write and a broadcast attempt via `tx_sender` — is reachable by any party with network access to the gRPC port, not only the aggregator-cert holder.

### Finding Description
Binding: `CALLER_AUTHORITY` should hold `caller(send_move_to_vault_tx) == holder(OnlyAggregatorAndSelf.aggregator_cert)`.

In `core/src/servers.rs:106-138`, the TLS/interceptor setup branches strictly on `config.client_verification`:
```
let tls_config = if config.client_verification { ...client_ca_root(client_ca)... } else { ServerTlsConfig::new().identity(server_identity) };
let service = InterceptedService::new(service, if config.client_verification { OnlyAggregatorAndSelf {...} } else { Noop });
``` [1](#0-0) 

`Interceptors::Noop::call` unconditionally returns `Ok(req)` with no inspection of peer certs at all: [2](#0-1) . Only the `OnlyAggregatorAndSelf` variant performs the leaf-certificate comparison against `aggregator_cert`/`our_cert`: [3](#0-2) .

Given the question's stated precondition (`Noop` active), the binding is broken by construction: any caller reaching the gRPC port — with no TLS client certificate presented — can invoke `send_move_to_vault_tx`. The handler [4](#0-3)  only validates the *shape* of the supplied transaction (1 input, 2 outputs, output amounts equal to `bridge_amount`/0, and output scriptPubKeys equal to the publicly-computable vault script and anchor script) [5](#0-4) , then unconditionally performs a DB write and asks `tx_sender` to broadcast it: [6](#0-5) . No caller-identity check exists inside the handler itself; authorization is delegated entirely to the interceptor layer, which is bypassed under `Noop`.

Note that the shape checks constrain the *outputs* (they must pay the real, publicly-known vault/anchor scripts) but not the *input* — the attacker still needs to supply a transaction whose single input carries a valid Bitcoin-consensus-valid signature/witness for whatever UTXO it spends (the aggregator does not fabricate signatures). This prevents literal fund theft from the deposit UTXO (an attacker cannot forge the N-of-N signature required to spend a real deposit output), so the Critical-tier "value leaving a move-to-vault UTXO" outcome is not reachable this way. What remains reachable is exactly the unauthenticated invocation of a state-changing/broadcasting RPC (DB insert into the tx-sender's queue plus a broadcast attempt funded via the aggregator's own CPFP fee-payer UTXOs) by a party holding no certificate whatsoever.

### Impact Explanation
This matches the High-severity category "an unauthenticated state-changing or broadcasting call": with `client_verification=false`, `SendMoveToVaultTx` performs a database write (`insert_try_to_send`) and initiates broadcast logic without verifying the caller is the aggregator-cert holder. It is repeatable per attacker-chosen `deposit_outpoint`/well-formed-shape transaction. It does not by itself move bridge value or create a false reimbursement, because the output constraints tie the transaction to the real vault script (self-funded deposits into the vault are not a value-transfer exploit) and the input still requires a Bitcoin-valid signature the attacker cannot forge for someone else's UTXO. The downstream cost to the aggregator's own fee-payer wallet from repeated calls is a resource-exhaustion/DoS-style effect, which is explicitly out of scope per the rules.

### Likelihood Explanation
This requires the deployment to run with `client_verification=false` (i.e., `CLIENT_VERIFICATION` env var unset/false), which the question stipulates as the precondition (`Interceptors::Noop` active). Under that configuration, exploitation is trivial: any network-reachable client can call the RPC over plain TLS with no client certificate. Repo defaults for test/regtest configs (`core/src/test/data/bridge_config.toml`) set `client_verification = true`, so this depends on operational/deployment configuration rather than the code's default test behavior.

### Recommendation
Do not allow `Interceptors::Noop` to be selected for any externally-reachable aggregator/verifier/operator gRPC service in non-test builds; require `client_verification=true` (or an equivalent bearer/mTLS check) to be enforced for state-changing/broadcasting RPCs like `SendMoveToVaultTx` regardless of the `client_verification` flag — e.g., add an in-handler authorization check independent of the interceptor, or fail server startup unless `OnlyAggregatorAndSelf` is configured for production profiles.

fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
