### Title
Reputation minted per-byte for self-relayed messages lets an attacker manufacture collator-selection "share" without providing real relay service - ([File: modules/pallets/messaging-incentives/src/lib.rs])

### Summary
`pallet-messaging-incentives` mints a non-transferable `ReputationAsset` to whichever account's sr25519 signature appears in the `signer` field of a delivered ISMP `Request`/`Response` message, scaled by `max(body_len, 32)` bytes per request. This reputation balance is the *sole* ranking input `pallet-collator-manager::new_session` uses to select the next Collator set, and it is burned (reset to zero) only at the session boundary at which it is consumed [1](#0-0) . This is structurally the same broken invariant as the RocketPool report: a reward/selection share is computed from a balance that can be inflated arbitrarily right before the "claim" (session) snapshot, with no requirement that the balance-holder actually rendered a proportional amount of real service to the network.

### Finding Description
`on_executed` mints reputation for every `Request`/`Response` message with no check that the message represents genuine cross-chain value transfer to a third party, nor any check that the relayer who is credited is distinct from the request's dispatcher/beneficiary: [2](#0-1) 

The mint amount is `bytes(request) × MintPerByte`, with a `max(body, 32)` per-request floor applied to *each* individual request in the batch, explicitly to prevent gaming via splitting: [3](#0-2) 

However, nothing in `on_executed`/`relayer_for` restricts *who* can be the source, destination, or "app" of the request — only that the message carry a valid sr25519 signature for `signer`. Since dispatching an ISMP request (even a trivial-payload one, to any registered destination the attacker also controls) and then delivering it themselves is a fully permissionless, unprivileged action (this is exactly what `pallet-messaging-incentives`'s own README says the pallet is for — rewarding "the relayer that delivered each ISMP message" with no session accounting or DoS guard), an attacker can:

1. Dispatch a stream of minimal-cost, self-serving ISMP requests (arbitrary source/dest app addresses under their control) with body length ≥ 32 bytes.
2. Deliver/relay these to Hyperbridge under their own signer key, at `Pays::No` weight-class for the fee handler itself.
3. Rapidly accumulate `ReputationAsset` immediately before a session boundary.
4. Get selected into the Collator set by `pallet-collator-manager::new_session`, which ranks purely by `ReputationAsset::balance` at that instant [4](#0-3) .
5. Once selected, earn real, transferable `$BRIDGE` collator block-production rewards from the treasury (documented as `0.7 $BRIDGE` per authored block, ~4,000,000 $BRIDGE/year total pool) — a real economic payout disbursed by the protocol based on a manufactured, non-representative reputation snapshot.
6. Reputation is burned only at session end, so the attacker can repeat this cycle every session with a fresh burst of cheap self-relayed traffic, never needing to sustain genuine service between selections — the direct analog of RocketPool's "stake right before `claim()`, withdraw/rotate immediately after."

The `ReputationCallFilter` only prevents transferring reputation between accounts; it does nothing to prevent unlimited self-minting via spam messages [5](#0-4) .

### Impact Explanation
This lets an unprivileged attacker unfairly capture Collator slots — and thus the associated `$BRIDGE` treasury payouts — without providing commensurate real relaying service to the network, diverting protocol rewards away from operators doing genuine work. Because Collators also author blocks and run the network's fisherman fraud-detection task, a reputation-farmed Collator seat additionally hands block-production and fraud-detection responsibility to an operator selected purely by cheap self-dealt traffic rather than proven reliability, which is a direct logic/incentive-integrity attack on a production reward path (matches "logic attacks" / unfair reward capture in the bounty scope).

### Likelihood Explanation
High feasibility: dispatching and delivering trivial ISMP messages to a registered destination the attacker controls is a normal, permissionless, unprivileged operation requiring no relayer/prover/admin trust assumption and no malicious peer behavior — it is exactly the surface `pallet-messaging-incentives` is designed to reward. The `MintPerByte` rate and message volume are the only throttles, and an attacker can batch many minimal requests (32-byte floor each) cheaply just before a session rotation.

### Recommendation
Do not let raw per-byte-minted reputation alone gate a real economic reward (Collator selection/treasury payout) without accounting for the durability/genuineness of the underlying service, mirroring the RocketPool fix direction: (1) require reputation to be accrued over a sustained window rather than an instantaneous pre-session snapshot (e.g., time-weighted or moving-average reputation rather than raw balance at `new_session`), (2) exclude or heavily discount messages where source and destination are both controlled by the same relayer/signer (self-dealt traffic), and/or (3) rate-limit or diminish mint-per-byte returns for bursts of low-value/low-uniqueness traffic from a single relayer immediately preceding a session boundary.

### Proof of Concept
1. Attacker deploys/controls both the source-chain dispatcher app and the destination handler for an ISMP `Post` request (or reuses `pallet-ismp-demo`-style pings).
2. Attacker dispatches N minimal `PostRequest`s (body length ≥ 32 bytes each) from a chain to Hyperbridge, timed just before the next session rotation.
3. Attacker relays/delivers these messages to Hyperbridge under their own sr25519 signer key; `pallet_ismp` invokes `FeeHandler::on_executed`, and `pallet-messaging-incentives::on_executed` mints `N × 32 × MintPerByte` reputation to the attacker's Controller account [6](#0-5) .
4. At the session boundary, `pallet-collator-manager::new_session` reads `ReputationAsset::balance` for all controllers, ranks them, and selects the top N (attacker included) — despite the attacker never delivering messages of any real economic/cross-chain value to a third party [4](#0-3) .
5. Attacker is now a Collator, earning `$BRIDGE` block rewards from the treasury; reputation is burned, and the attacker repeats the spam burst before the next session to remain selected indefinitely at minimal genuine cost.

	/// Same minimum-byte rule as the bandwidth gate (`max(body, 32)`),
	/// applied **per request** so packing requests into one envelope
	/// vs. splitting them across many produces identical mints.
	/// Applying the floor once per envelope would let a relayer inflate
	/// the mint by splitting (each split picks up its own 32-byte floor).
	fn message_bytes(message: &Message) -> u32 {
		match message {
			Message::Request(req) => req
				.requests
				.iter()
				.map(|p| core::cmp::max(p.body.len() as u32, 32))
				.sum::<u32>(),
			_ => 0,
		}
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}

/// Reputation tokens are soulbound — credited via the incentive pallets
/// and consumed only by `pallet-collator-manager`'s per-session reset.
/// The holder must not be able to send them anywhere, so this filter
/// rejects every dispatched `Assets` call that could move balance out
/// of a holder's account when the target asset is the reputation asset.
/// Programmatic `fungible::Mutate` (mint / burn from runtime pallets)
/// bypasses dispatch and is therefore unaffected.
pub struct ReputationCallFilter;
impl frame_support::traits::Contains<RuntimeCall> for ReputationCallFilter {
	fn contains(call: &RuntimeCall) -> bool {
		let rep = ReputationAssetId::get();
		match call {
			RuntimeCall::Assets(
				pallet_assets::Call::transfer { id, .. } |
				pallet_assets::Call::transfer_keep_alive { id, .. } |
				pallet_assets::Call::transfer_all { id, .. } |
				pallet_assets::Call::approve_transfer { id, .. } |
				pallet_assets::Call::transfer_approved { id, .. },
			) => *id != rep,
			_ => true,
		}
	}
}
