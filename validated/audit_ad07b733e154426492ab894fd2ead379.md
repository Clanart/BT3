## Analysis

The Sherlock report's core bug pattern is: **an index-based collection (`balances`) is mutated in a way that shortens/shifts it, while another data structure (NFT `tokenId`s) still references the *old* index positions** — so subsequent operations silently operate on the wrong slot with no identity check tying the two together.

The closest structural analog in Desktop is how **partial-commit line selection** is tracked and later applied to a **freshly re-fetched diff**.

- `DiffSelection` tracks selected/deselected lines purely by **absolute numeric line index** (`divergingLines: Set<number>`), with no notion of the line's actual content/identity: [1](#0-0) 
- When the working-directory diff is reloaded (e.g. after a file-watcher event fires because the file on disk changed), Desktop only prunes selection indices that are **no longer selectable at all** — it does not verify that the content at a given index is still the same line the user selected: [2](#0-1) 
- At actual commit time, `applyPatchToIndex` **re-fetches the diff from disk** (a fresh `getWorkingDirectoryDiff` call) and then applies the file's (possibly stale) `DiffSelection` indices against that brand-new diff via `formatPatch`: [3](#0-2) 
- `formatPatch`/`formatPatchToDiscardChanges` blindly trust `hunk.unifiedDiffStart + lineIndex` as the key into `file.selection.isSelected(...)`, with no check that the line at that absolute index is the same line the user actually reviewed and checked: [4](#0-3) 

This is the same invariant break as `CouncilMember.burn`: the "index" (`tokenId` / diff-line index) and the "backing array" (`balances` / current hunk contents) are allowed to drift apart, and the code trusts index membership instead of identity, with only a partial, non-authoritative guard (`balances.pop()` vs `withSelectableLines`).

### Title
Stale line-index-based `DiffSelection` can cause commit of unreviewed content when the working tree changes between selection and commit - (File: app/src/lib/patch-formatter.ts)

### Summary
Desktop tracks which diff lines a user has checked for a partial commit using purely numeric absolute line indices (`DiffSelection`), decoupled from the actual line content. If the tracked file on disk changes (e.g. as a result of a malicious `post-checkout`/`post-merge` hook shipped in a cloned/fetched repository, another tool, or any concurrent write) between the time the diff was rendered/selected and the time the commit patch is generated, the index-to-content mapping shifts, but the stale selection indices remain "selected." Because `applyPatchToIndex` re-fetches the diff fresh at commit time and reuses the old `DiffSelection` against it, the wrong lines can be silently included in (or excluded from) the commit.

### Finding Description
`DiffSelection.isSelected(lineIndex)` only knows about line numbers, never line content: [5](#0-4) 

When the working directory diff is reloaded, the app updates `selectableLines` to drop indices that are no longer "includeable" lines at all, but this is explicitly an incomplete guard, as the code comment states: "the diff might have changed dramatically… we would be more clever about validating that any partial selection state is still valid… but for now we'll settle on just updating the selectable lines": [6](#0-5) 

If the diff shifts such that a previously "add"/"delete" line at index N is replaced by a *different* add/delete line at that same index N (same line count, different content — e.g., a hook rewrites a file line in place), that index is still in `selectableLines`, so the stale "selected" flag silently carries over to the new content.

At commit time, `applyPatchToIndex` calls `getWorkingDirectoryDiff` again (a fresh read of the file), then builds the patch from `file.selection` against that fresh diff: [3](#0-2) 

`formatPatch` then trusts `hunk.unifiedDiffStart + lineIndex` purely as a numeric key into the (possibly stale) selection: [7](#0-6) 

There is no re-validation that the line's text/hash at that index matches what the user actually clicked to select — the exact same class of bug as `CouncilMember.burn`, where the array shrank/shifted but the `tokenId` mapping wasn't re-validated against the new array state.

### Impact Explanation
This can cause **silent corruption of what the user commits or pushes**: content the user never saw or explicitly checked can be staged and committed (or, in the discard-changes path, the wrong lines can be discarded from the working tree), because the same numeric index now refers to unrelated content. This directly matches the "silent corruption of what the user commits or pushes" criterion in the valid-impact list, and the trigger vector (a cloned/fetched repository shipping a hook or tooling that mutates tracked files between diff render and commit) matches "attacker controls a cloned/fetched repository."

### Likelihood Explanation
The window is real but narrow: it requires the working tree to change between the time Desktop last rendered/recorded the selection and the moment `_finishCommit`/`applyPatchToIndex` executes. This is plausible via repo-shipped git hooks (`post-checkout`, `post-merge`, `pre-commit` that rewrites tracked files) or any external process/tool triggered by opening a hostile repository, combined with normal user latency in reviewing a diff and clicking "Commit." Desktop's own code comments acknowledge the underlying assumption is known to be incomplete ("for now we'll settle on..."), indicating the maintainers are aware the guard is not authoritative.

### Recommendation
Do not trust numeric line indices alone across diff reloads. Either (a) invalidate/reset the entire selection whenever the file's diff changes at all (not just remove indices that became unselectable), or (b) key selection state by line content hash/identity (e.g., normalized line text + relative position within its hunk) rather than raw absolute index, so a content change at the same index can't silently inherit a stale "selected" state. Additionally, `applyPatchToIndex`/`formatPatch` should re-derive/verify the diff immediately before generating the patch and reject (or re-prompt) if the diff used for the patch differs from the diff the selection was computed against, rather than silently applying possibly-mismatched indices.

### Proof of Concept
Conceptual reproduction (cannot be executed here, but follows directly from the cited code):
1. Modify a tracked file with two adjacent lines, e.g. line A (`+fooA`) and line B (`+fooB`), both additions in the same hunk.
2. In Desktop's Changes view, uncheck line B only (deselect index `N+1`), leaving line A selected.
3. Before committing, have an external process (e.g., a hook run by `git pull`/`checkout`, or any script triggered when opening the repo) rewrite line B's content in place with different but semantically important content (e.g., a secret, a backdoor line, or reverted security fix), keeping it as a single addition line so the diff still has one addition at the same index `N+1`.
4. Desktop's file watcher triggers `updateChangesWorkingDirectoryDiff`, which calls `withSelectableLines` — index `N+1` remains selectable, and the previous deselect state at that index is preserved even though it now refers to *different content*: [8](#0-7) 
5. User commits. `applyPatchToIndex` re-fetches the diff and calls `formatPatch(file, diff)` using the same `file.selection`, and the still-deselected index `N+1` line is dropped from the patch, or, in an analogous scenario where the hook toggles line ordering/content so a previously-*selected* index now maps to unreviewed content, that unreviewed content is silently included in the commit: [9](#0-8) 

Note: I was not able to fully trace the exact timing/ordering guarantees between the file-watcher-triggered diff refresh and the commit trigger in the dispatcher within the indexed code (some orchestration code in `dispatcher.ts`/`git-store.ts` was only partially covered by search results), so the precise race window size is not fully confirmed from the index alone. A Devin session with full repo access would be needed to trace the exact commit dispatch sequence and build a concrete executable PoC.

/**
 * An immutable, efficient, storage object for tracking selections of indexable
 * lines. While general purpose by design this is currently used exclusively for
 * tracking selected lines in modified files in the working directory.
 *
 * This class starts out with an initial (or default) selection state, ie
 * either all lines are selected by default or no lines are selected by default.
 *
 * The selection can then be transformed by marking a line or a range of lines
 * as selected or not selected. Internally the class maintains a list of lines
 * whose selection state has diverged from the default selection state.
 */
export class DiffSelection {
  /**
   * Initialize a new selection instance where either all lines are selected by default
   * or not lines are selected by default.
   */
  public static fromInitialSelection(
    initialSelection: DiffSelectionType.All | DiffSelectionType.None
  ): DiffSelection {
    if (
      initialSelection !== DiffSelectionType.All &&
      initialSelection !== DiffSelectionType.None
    ) {
      return assertNever(
        initialSelection,
        'Can only instantiate a DiffSelection with All or None as the initial selection'
      )
    }

    return new DiffSelection(initialSelection, null, null)
  }

  /**
   * @param divergingLines Any line numbers where the selection differs from the default state.
   * @param selectableLines Optional set of line numbers which can be selected.
   */
  private constructor(
    private readonly defaultSelectionType:
      | DiffSelectionType.All
      | DiffSelectionType.None,
    private readonly divergingLines: Set<number> | null = null,
    private readonly selectableLines: Set<number> | null = null
  ) {}
