### Title
Insecure ("local-only") offer cancellation does not invalidate the offer, allowing a counterparty to later take it as if never cancelled - ([File: chia/wallet/trade_manager.py])

### Summary
`TradeManager.cancel_pending_offers` supports a non-`secure` cancellation path that only updates the maker's local trade database status to `CANCELLED` and never spends or otherwise invalidates the offer's underlying coins on-chain. [1](#0-0) 
Meanwhile, `respond_to_offer`/`check_offer_validity` — the only gate a taker goes through before accepting an offer — validates solely against on-chain coin-spent state, never against the maker's local trade status. [2](#0-1) [3](#0-2) 

This mirrors the reported bug class: a "cancel" operation that removes the item from the canceller's own bookkeeping but does not consume/burn the deterministic on-chain identity of the order, letting anyone still holding the original request replay/complete it. Here, the "salt-derived orderId" analog is the offer's coin set (`Offer.get_offered_coins()` / arbitrage coins), which remains live and unspent after an insecure cancel.

### Finding Description
When `secure=False`, `cancel_pending_offers` simply calls `self.trade_store.set_status(trade.trade_id, TradeStatus.CANCELLED)` and returns — it never selects the offered coins, never spends them, and never broadcasts a cancellation spend bundle: [4](#0-3) 

This is exposed directly through the RPC surface (`cancel_offer`/`cancel_offers` with `secure=False`), reachable by any wallet-holder/local RPC caller: [5](#0-4) 

A counterparty (taker) who already possesses a copy of the offer file — e.g., received it via the normal offer-sharing flow before the maker "cancelled" it — can call `take_offer`/`respond_to_offer` at any later time. That path only checks `check_offer_validity`, which fetches the coin states for the offer's non-ephemeral removals and succeeds as long as those coins are still unspent on-chain: [2](#0-1) [6](#0-5) 

Nothing in this validation logic queries the maker's `trade_store` status, so an offer the maker believes is "CANCELLED" (via the insecure path) remains fully acceptable and will be completed on-chain by the taker's spend bundle, moving the maker's coins without their current consent — directly analogous to `requestOrder` reviving a cancelled order using the stale `salt`/state.

By contrast, the `secure=True` path actually spends the offer's cancellation coins on-chain, which correctly invalidates the offer (confirmed by tests asserting `respond_to_offer` raises `"This offer is no longer valid"` after a secure cancel): [7](#0-6) 
But the insecure path provides no such protection while still marking the trade as `CANCELLED` in the UI/RPC, giving the maker a false sense that the offer can no longer be executed.

### Impact Explanation
A maker who cancels an offer via the insecure (`secure=False`, i.e. `cancel_offer --insecure`) path — the faster, fee-free default many wallet users/integrators reach for — retains no actual on-chain protection. If the offer bytes were shared with a counterparty (e.g., listed publicly, sent to multiple parties, or shared then "cancelled" because terms changed), that counterparty can still submit `respond_to_offer`/take the offer and settle it on-chain at any time before the maker performs an actual (secure) coin-consuming cancel or otherwise spends those coins. This results in unauthorized/unintended coin movement — the exact outcome the maker's cancel action was meant to prevent — despite the wallet reporting `TradeStatus.CANCELLED`.

### Likelihood Explanation
High reachability: this only requires two unprivileged wallet actions — the maker creating and then insecurely cancelling an offer, and a taker who already has (or later obtains) a copy of the offer file calling the standard `take_offer` RPC/CLI. No special privileges, timing races with the node, or malicious infrastructure are needed; it only depends on the offer coins remaining unspent, which is the default state after an insecure cancel.

### Recommendation
Have `respond_to_offer`/`check_offer_validity` (or an earlier gate in `take_offer`) also consult the local `trade_store` (and ideally cross-check against any other node/peer view) to reject offers whose trade record is marked `CANCELLED`/`PENDING_CANCEL`, and/or make the insecure cancel path also broadcast an announcement-based invalidation. At minimum, clearly disallow/deprecate an "insecure" cancel that produces a `CANCELLED` status without any on-chain guarantee, since it misleads users into believing the offer can no longer be completed.

### Proof of Concept
1. Maker creates an offer via `create_offer_for_ids` and shares the resulting offer bytes/bech32 string with a taker.
2. Maker cancels it with `cancel_offer`/`cancel_pending_offers(secure=False)` — local status becomes `CANCELLED`, no coins are spent: `chia/wallet/trade_manager.py:298-301`.
3. Taker, who still holds the original offer bytes, calls `take_offer`/`respond_to_offer` with that offer.
4. `check_offer_validity` (`chia/wallet/trade_manager.py:680-690`) finds the offer's coins still unspent and returns `True`; `respond_to_offer` proceeds to build and broadcast a completing spend bundle (`chia/wallet/trade_manager.py:852-915`), settling the "cancelled" trade on-chain against the maker's wishes.

    async def check_offer_validity(self, offer: Offer, peer: WSChiaConnection) -> bool:
        all_removals: list[Coin] = offer.removals()
        all_removal_names: list[bytes32] = [c.name() for c in all_removals]
        non_ephemeral_removals: list[Coin] = list(
            filter(lambda c: c.parent_coin_info not in all_removal_names, all_removals)
        )
        coin_states = await self.wallet_state_manager.wallet_node.get_coin_state(
            [c.name() for c in non_ephemeral_removals], peer=peer
        )

        return len(coin_states) == len(non_ephemeral_removals) and all([cs.spent_height is None for cs in coin_states])
```

    async def respond_to_offer(
        self,
        offer: Offer,
        peer: WSChiaConnection,
        action_scope: WalletActionScope,
        solver: Solver | None = None,
        fee: uint64 = uint64(0),
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> TradeRecord:
        if solver is None:
            solver = Solver({})
        take_offer_dict: dict[bytes32 | int, int] = {}
        arbitrage: dict[bytes32 | None, int] = offer.arbitrage()

        for asset_id, amount in arbitrage.items():
            if asset_id is None:
                wallet: WalletProtocol | None = self.wallet_state_manager.main_wallet
                assert wallet is not None
                key: bytes32 | int = int(wallet.id())
            else:
                # ATTENTION: new wallets
                wallet = await self.wallet_state_manager.get_wallet_for_asset_id(asset_id)
                if wallet is None and amount < 0:
                    raise ValueError(f"Do not have a wallet for asset ID: {asset_id} to fulfill offer")
                elif wallet is None or wallet.type() in {WalletType.NFT, WalletType.DATA_LAYER}:
                    key = asset_id
                else:
                    key = int(wallet.id())
            take_offer_dict[key] = amount

        # First we validate that all of the coins in this offer exist
        valid: bool = await self.check_offer_validity(offer, peer)
        if not valid:
            raise ValueError("This offer is no longer valid")
```
