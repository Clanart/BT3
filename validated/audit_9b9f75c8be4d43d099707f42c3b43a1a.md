### Title
App Proxy signature verification accepts indefinitely-replayable requests due to missing timestamp expiration check - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` verifies only that the HMAC `signature` query parameter matches the other query parameters (including `timestamp`), but never validates that the `timestamp` value itself is recent. This is the same bug class as the Derby M-8 report: a value that is meant to bound the validity window of a signed/authorized action (there, Uniswap's `deadline`; here, Shopify's `timestamp`) is present in the signed payload but never checked, so an old, otherwise-valid signed artifact can be reused far outside its intended validity window.

### Finding Description
`AppProxyVerification` is the concern apps are told to include in custom app-proxy controllers (and is used by the generator template) to authenticate storefront-proxied requests forwarded by Shopify: [1](#0-0) 

The verification logic is:
```
def query_string_valid?(query_string)
  query_hash = Rack::Utils.parse_query(query_string)
  signature = query_hash.delete("signature")
  return false if signature.nil?
  ActiveSupport::SecurityUtils.secure_compare(calculated_signature(query_hash), signature)
end
``` [2](#0-1) 

`calculated_signature` recomputes the HMAC over all remaining query parameters, `timestamp` included, and compares it to the supplied `signature`: [3](#0-2) 

Shopify includes a `timestamp` parameter specifically so that receivers can bound how long a signed proxy request is considered valid — this is directly analogous to Uniswap's `deadline` parameter used to bound the validity of a signed/authorized swap. In both cases the value is transmitted and even included in what's being authenticated (the swap's `amountOutMinimum`/`deadline` pairing here, the HMAC signature there), but `shopify_app` never inspects `timestamp` against `Time.now` to reject stale requests. The test suite confirms this: a query string with a fixed, ancient `timestamp=1466106083` (year 2016) still validates successfully today with no freshness check: [4](#0-3) [5](#0-4) 

No other part of the concern (`verify_proxy_request` before_action) adds an expiration check: [6](#0-5) 

Grepping the library code confirms there is no timestamp-freshness/expiry logic anywhere in `lib/shopify_app` related to app proxy or webhook verification — the only `timestamp` references in `lib/` are unrelated to request verification (model generators). Webhook and extension HMAC verification (`PayloadVerification#hmac_valid?`) likewise never checks a timestamp, but Shopify's webhook HMAC scheme doesn't include a timestamp in the signed payload at all, so that path is not a case of a present-but-unchecked expiration value — the App Proxy path is the concrete analog because `timestamp` is present in the signed data and simply ignored for freshness purposes.

### Impact Explanation
Because no freshness check exists, any app-proxy request URL (with its valid `signature`) that is captured by an attacker — e.g., leaked via browser history, referrer headers, shared/forwarded links, proxy/CDN logs, or an XSS on the storefront that reads `location.href` — remains a permanently valid, forgeable-looking authenticated request to the merchant's app proxy endpoint. This lets an unrelated party replay that exact signed request indefinitely, at any time in the future, and have the app treat it as a fresh, Shopify-originated request. If the app-proxy endpoint performs any state-changing or shop-context-sensitive action based on those query parameters (common in generated app-proxy controllers, which developers build using this concern per the generator template), this becomes a durable request-replay/forgery primitive rather than a one-time signed action.

### Likelihood Explanation
Exploitability depends on an attacker obtaining one previously-issued valid app-proxy URL for a target shop (via logs, referrer leakage, or shared links) — this is a realistic and commonly-cited class of leakage for GET-based signed URLs. Once obtained, replay requires no interaction with the merchant, no valid session, and no knowledge of the app's secret; the attacker simply resends the exact query string. Likelihood is moderate: it requires the attacker to first capture a genuine signed URL, but shopify_app provides zero mitigation (no timestamp window, no nonce/single-use tracking) once that occurs, which is a materially weaker posture than typical signed-URL schemes that bound validity to minutes.

### Recommendation
In `ShopifyApp::AppProxyVerification#query_string_valid?`, after verifying the HMAC, additionally parse and validate the `timestamp` parameter against `Time.now.to_i` and reject requests outside a reasonable window (e.g., a few minutes), mirroring how OAuth callback state/HMAC values are time-bounded elsewhere in the gem. Consider making the window configurable via `ShopifyApp.configuration` so app developers can tune it for their latency/CDN characteristics.

### Proof of Concept
1. A developer generates an app-proxy controller using `ShopifyApp::AppProxyVerification` (per `lib/generators/shopify_app/app_proxy_controller/templates/app_proxy_controller.rb`).
2. A legitimate storefront visitor triggers an app-proxy request; Shopify signs and forwards `GET /apps/my-app?shop=...&path_prefix=...&timestamp=1466106083&signature=...`.
3. This exact URL (with its `signature`) leaks (browser history/referrer/log access) to an unrelated third party.
4. Years later, the third party replays the identical URL. `query_string_valid?` recomputes the same HMAC over the same parameters (including the stale `timestamp`) and it matches, so `verify_proxy_request` allows the request through — as demonstrated by the test asserting `query_string_valid?` returns `true` for `timestamp=1466106083` with no time-based rejection: [5](#0-4)

```ruby
# frozen_string_literal: true

module ShopifyApp
  module AppProxyVerification
    extend ActiveSupport::Concern
    included do
      skip_before_action :verify_authenticity_token, raise: false
      before_action :verify_proxy_request
    end

    def verify_proxy_request
      head(:forbidden) unless query_string_valid?(request.query_string)
    end

    private

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
  end
```
