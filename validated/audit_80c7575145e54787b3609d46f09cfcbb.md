### Title
Dust-output spam inflates `SignableTransaction` past standard weight, blocking threshold spends - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
An unprivileged party can send arbitrarily many dust outputs to a Serai Bitcoin multisig address. `Scanner::scan_transaction` reports every matching output with no minimum-value or sanity filter, and `SignableTransaction::new` consumes all supplied `ReceivedOutput`s as inputs without checking whether they are dust or whether the resulting transaction stays under `MAX_STANDARD_TX_WEIGHT`. Once enough dust accumulates, every spend attempt fails with `TransactionError::TooLargeTransaction`, freezing the multisig's funds until operators manually curate the input set — a direct analog of the reported "attacker forces a privileged removal/operation to revert by injecting dust" bug class.

### Finding Description
`Scanner::scan_transaction` pushes a `ReceivedOutput` for *every* transaction output whose `script_pubkey` matches a registered script, with no value check: [1](#0-0) 

Those outputs are later passed wholesale into `SignableTransaction::new`, which builds one `TxIn` per `ReceivedOutput` and only enforces dust limits on *payments*, never on inputs: [2](#0-1) 

The transaction is rejected after construction when its weight exceeds the standardness limit: [3](#0-2) 

Each Taproot input contributes ~57.5 vbytes, so roughly ~1,700 attacker-funded dust outputs suffice to make any spend fail. There is also no per-input economic check: a dust input worth less than its weight × `fee_per_vbyte` is a net negative, silently burned into the fee via `input_sat - payment_sat - fee` change math. [4](#0-3) [5](#0-4) 

### Impact Explanation
All spending of the multisig's Bitcoin (withdrawals, rotations, forwards) goes through `SignableTransaction::new`. An attacker who dusts the scanned address forces `TooLargeTransaction` on every spend built from the full UTXO set, halting fund movement until operators manually exclude dust inputs — the same "block the privileged operation until manual intervention" impact as the source report. No FROST failure or key compromise is required; this is pure on-chain input inflation reachable by anyone who can send a Bitcoin transaction.

### Likelihood Explanation
Sending dust to a known Taproot address is permissionless and cheap (~546 sats/output, or less if non-standard-but-consensus-valid outputs are relayed). The multisig address is publicly observable on-chain, so the attacker needs no internal access. The only precondition is that downstream callers feed `scan_transaction`'s full output list into `SignableTransaction::new`, which is the intended usage.

### Recommendation
- Filter inputs in `SignableTransaction::new` (or in `Scanner`): drop `ReceivedOutput`s whose value is below `DUST` or below `fee_per_vbyte * input_vbytes` so dust can never be a net-negative input.
- Cap total input count/weight and select inputs greedily (largest-first) rather than consuming the full set, so spam cannot push the transaction over `MAX_STANDARD_TX_WEIGHT`.

### Proof of Concept
1. Attacker broadcasts a transaction (or several) creating ~2,000 outputs paying `p2tr_script_buf(group_key)` (the `Scalar::ZERO`-offset script registered by `Scanner::new`).
2. `Scanner::scan_transaction` returns all of them as `ReceivedOutput`s.
3. The processor passes `Vec<ReceivedOutput>` (all received UTXOs) to `SignableTransaction::new` with a legitimate payment.
4. `calculate_weight_vbytes` produces weight > `MAX_STANDARD_TX_WEIGHT` (400,000 WU); `Err(TransactionError::TooLargeTransaction)` is returned at `send.rs:241-243`, and no spend can be constructed until inputs are manually filtered.

    let mut res = Vec::new();

      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
