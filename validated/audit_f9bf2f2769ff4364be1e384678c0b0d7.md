## Analog identified: `evm/tron/contracts/apps/IntentGatewayV2.sol` — `placeOrder()` escrow accounting lacks duplicate-input-token rejection, unlike its EVM sibling

### Title
Duplicate input-token entries in an `Order` let a single order over-attribute escrow into a shared `_orders[commitment][token]` slot on the Tron `IntentGatewayV2` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The `ConcentratedLiquidityPosition` bug's core defect is a pooled-value bucket keyed too coarsely (by tick range, not by depositor) that gets flushed in full to whichever caller reaches `burn()`. The closest verified local analog is the escrow bucket `_orders[commitment][token]` in the Tron variant of `IntentGatewayV2.placeOrder()`, which accumulates with `+=` and — unlike the canonical `evm/src/apps/IntentGatewayV2.sol` — has no guard against the same token appearing multiple times in `order.inputs`.

### Finding Description
In the canonical contract, `placeOrder()` explicitly rejects a duplicate input token before crediting escrow: [1](#0-0) 
which uses a strict assignment (`_orders[commitment][token] = reducedInputs[i].amount`) and reverts with `InvalidInput()` if the slot is already non-zero — enforcing a 1:1 mapping between an input-array index and the escrow bucket for that token within one order.

The Tron variant, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements the equivalent step differently: [2](#0-1) 
Here the escrow credit is `_orders[commitment][token] += reducedInputs[i].amount;` inside the per-input loop, with **no check that `token` hasn't already been seen** earlier in `order.inputs`. Nothing in `placeOrder` (Tron) rejects a duplicate `order.inputs[i].token`/`order.inputs[j].token` pair the way the canonical version's `if (_orders[commitment][token] != 0) revert InvalidInput();` does.

This matters because `withdraw()` in the Tron contract iterates `body.tokens` (which mirrors `order.inputs` as constructed by the caller of `fillOrder`/`cancelOrder`) and, for **each** entry, checks `_orders[commitment][token] == 0` and subtracts `amount` from the shared per-token bucket: [3](#0-2) 
Because the escrow bucket is keyed only by `(commitment, token)` and not by input-array index, a `WithdrawalRequest.tokens` array with the same token repeated `N` times can drain up to `N` times the amount actually escrowed for that token, as long as the cumulative `_orders[commitment][token]` balance built up by (potentially duplicated) `placeOrder` credits is large enough to satisfy each sequential subtraction without underflowing. Since a solver constructs the `WithdrawalRequest.tokens` array that ultimately reaches `withdraw()` (via the cross-chain `RedeemEscrow`/`RefundEscrow` message body encoded by the filling/cancelling contract, itself built from `order.inputs`), and `order.inputs` is attacker-supplied at `placeOrder` time with no duplicate-token rejection, an attacker who places an order with duplicate input tokens can inflate the bucket beyond what any single logical input represents and structure the fill/cancel path to walk the same token multiple times, each time transferring `amount` out and decrementing the shared bucket — repeating "double-spend of a single escrowed value" until the shared bucket is exhausted, exactly mirroring the Trident bug's "shared bucket paid out per caller/entry instead of per rightful share."

### Impact Explanation
This lets the order's own creator (or the solver acting on `order.inputs` they control the shape of) manipulate a single escrow deposit into a repeated-withdrawal primitive, resulting in the gateway paying out more ERC-20/native value than was actually escrowed for that commitment — direct loss of gateway-held funds, a false-state/over-withdrawal condition equivalent to double-settlement of a single deposit. This falls squarely under "stealing or loss of funds" and "replay/double-claim/double-settlement" in the bounty's impact gate.

### Likelihood Explanation
The attacker is an unprivileged, ordinary order-placer — no relayer, prover, or admin compromise is required. The only local guard rail (`_orders[commitment][token] != 0` duplicate check) that the canonical `evm/src/apps/IntentGatewayV2.sol` contains is simply absent from the Tron variant's `placeOrder`, so the divergence between the two contract implementations is the concrete local evidence of the missing invariant.

### Recommendation
Port the duplicate-input-token rejection from `evm/src/apps/IntentGatewayV2.sol#L336-343` into `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder`, replacing the unconditional `+=` accumulation with an assign-once check (`if (_orders[commitment][token] != 0) revert InvalidInput(); _orders[commitment][token] = reducedInputs[i].amount;`), and additionally validate that `withdraw()`'s `body.tokens` array contains no duplicate token entries before iterating, so no per-token escrow bucket can be decremented more than once per settlement.

### Proof of Concept
1. Attacker calls `placeOrder` on the Tron gateway with `order.inputs = [ {token: USDC, amount: X}, {token: USDC, amount: X} ]` (same token twice, no protocol fee for simplicity).
2. `_orders[commitment][USDC]` accumulates to `2X` via two `+=` credits inside the loop at [4](#0-3)  even though the gateway only actually needed/expected `X` worth of unique economic input per logical asset — the bucket now silently represents twice the "intended" single-asset escrow.
3. On settlement (fill or cancel), the `WithdrawalRequest.tokens` array constructed from `order.inputs` also contains USDC twice; `withdraw()` processes each entry independently, transferring `X` to the beneficiary and decrementing `_orders[commitment][USDC]` by `X` on the first entry, then repeating the same transfer and decrement on the second entry at [5](#0-4) , releasing the full `2X` — double the token value that a single "one-asset-per-order" escrow guard was meant to bound, without any additional deposit having occurred beyond what a bug-free duplicate check would have rejected at placement time.

**Note on completeness:** I was not able to fully trace, within the remaining tool budget, the exact downstream code path in the Tron contract's `fillOrder`/cross-chain settlement functions that constructs `WithdrawalRequest.tokens` from `order.inputs` (I confirmed the vulnerable `placeOrder` accumulation and the vulnerable `withdraw()` loop, but did not view the full `fillOrder` body in the Tron file). This should be verified against the live Tron deployment before treating it as fully proven end-to-end.
