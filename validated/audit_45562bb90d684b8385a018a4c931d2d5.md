## Analysis

The external report's core invariant: **a raw ERC20 return-value check that doesn't correctly distinguish real success from failure**, causing state to update as if a transfer succeeded when it did not (or vice versa).

The Tron variant of `IntentGatewayV2` diverges from the standard EVM variant by using raw low-level `.call()` and inspecting only the call's `success` bit — **never decoding the boolean return value** — instead of OpenZeppelin's `SafeERC20.safeTransfer`, which the mainline EVM `IntentGatewayV2.sol`/`IntentsBase.sol` correctly use via `using SafeERC20 for IERC20;`.

### Title
Escrow/dust withdrawal on Tron IntentGatewayV2 treats non-reverting `transfer()` failures as success, permanently losing escrowed user funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` and the `SweepDust` handler in the Tron `IntentGatewayV2` release escrowed tokens using a raw low-level call that checks only whether the call reverted, not whether the token's `transfer` actually returned `true`: [1](#0-0) 

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```

The mainline EVM version instead uses `SafeERC20.safeTransfer`, which correctly requires `success && (returndata.length == 0 || abi.decode(returndata,(bool)))`: [2](#0-1) 

### Finding Description
The report's bug class is "assuming `transfer()` returning nothing or `false` means failure/success incorrectly." Here the Tron gateway has the inverse but equally dangerous defect: any ERC20 (or TRC20) whose `transfer` function does not revert but returns `false` on failure (a common non-standard pattern, and effectively guaranteed on some Tron TRC20 tokens whose ABI/behavior diverges from strict ERC20) will make `success == true` from the low-level `.call`, even though no tokens moved.

This occurs in two places:
1. `withdraw(WithdrawalRequest, bool)` — the internal function invoked from `onAccept`'s `RedeemEscrow`/`RefundEscrow` handling and from `onGetResponse`, which decrements `_orders[commitment][token]` and marks `_filled[commitment] = beneficiary` regardless of whether the token transfer truly succeeded: [3](#0-2) 
2. The `SweepDust` admin/governance request handler, which sweeps accumulated dust the same unsafe way: [4](#0-3) 

Since the escrow accounting (`_orders[commitment][token] -= amount`) and the `_filled` receipt marker are updated unconditionally once `success` is true, a token that returns `false` (without reverting) causes:
- the beneficiary to receive **nothing**,
- the escrow record to be permanently zeroed out,
- the order marked filled/redeemed (one-time receipt) so it can never be retried,
- an `EscrowReleased`/`EscrowRefunded`/`DustSwept` event to fire as if funds moved.

This is a genuine, non-relayer, non-admin, protocol-logic defect: it fires on the ordinary "successful proof, correct beneficiary" happy path whenever the token used is one of the many that signal failure via a `false` return instead of reverting.

### Impact Explanation
This is a direct loss-of-funds / stuck-escrow bug in bridge custody release logic. Escrowed principal or transaction fees credited to a legitimate beneficiary can become permanently unrecoverable: the on-chain escrow bookkeeping is deleted/decremented and the order is marked as filled, but the tokens never leave the contract to the intended beneficiary, and there is no remaining code path to retry or reclaim them (compare with the retry-safe pattern used in `EvmHost.dispatchTimeOut`, which explicitly restores commitment state on failure: [5](#0-4) ). Funds become effectively locked in the `IntentGatewayV2` contract with no accounting trail pointing to them, matching the bounty's "stealing or loss of funds" impact category.

### Likelihood Explanation
The path is triggered purely by legitimate protocol flow (a proven `RedeemEscrow`/`RefundEscrow` request from the host, or a governance `SweepDust` request) combined with an escrowed token that follows the widespread "return false instead of revert" ERC20/TRC20 convention — no malicious relayer, prover, or admin is required, and no privileged role needs to be compromised. Given Tron's TRC20 ecosystem includes tokens with non-standard transfer semantics, and the gateway is explicitly designed to escrow "any" configured token, the likelihood that some supported token exhibits this behavior (transiently, e.g., due to a blacklist/pause condition on the token itself) is realistic.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw` and the `SweepDust` handler) with OpenZeppelin's `SafeERC20.safeTransfer`, exactly as already done in the canonical EVM `IntentsBase.sol`/`IntentGatewayV2.sol`. `SafeERC20` correctly requires `success && (returndata.length == 0 || abi.decode(returndata, (bool)))`, so a `false` return value reverts the whole call, leaving escrow state and the `_filled` marker untouched and allowing the request to be retried/re-delivered instead of silently burning the record.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with an ERC20/TRC20 token whose `transfer(address,uint256)` returns `false` on failure instead of reverting (e.g., insufficient allowance-independent internal condition such as a paused/blacklisted recipient check that the token author implemented to return `false`).
2. A user places an order and escrows this token via `placeOrder`, crediting `_orders[commitment][token]`.
3. The order is legitimately filled/cancelled cross-chain, and the host delivers a valid `RedeemEscrow`/`RefundEscrow` `onAccept` request (or `onGetResponse` for a cancellation) targeting a beneficiary for whom the token's `transfer` returns `false` (no revert).
4. Inside `withdraw()`, `token.call(...)` returns `success = true` (the call itself didn't revert) even though the token internally returned `false` and moved no balance: [6](#0-5) 
5. `_orders[body.commitment][token] -= amount;` executes, zeroing the escrow record, and `_filled[body.commitment] = beneficiary;` is set, alongside an `EscrowReleased`/`EscrowRefunded` event.
6. The beneficiary's on-chain token balance is unchanged — the funds remain stuck in the `IntentGatewayV2` contract with no remaining reference to them, and the one-time `_filled` marker blocks any retry.

        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
