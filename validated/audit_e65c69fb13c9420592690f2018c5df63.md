Based on the code read from `parse-app-url.ts`, the `filepath` query parameter is indeed parsed without any validation, unlike `branch` and `pr`, which both have explicit checks.

### Title
Missing validation of `filepath` parameter in `openrepo` deep link enables path traversal - (File: `app/src/lib/parse-app-url.ts`)

### Summary
The `openrepo://` deep-link handler in `parseAppURL` extracts `pr`, `branch`, and `filepath` from the query string. `pr` is validated against `/^\d+$/` [1](#0-0) , and `branch` is validated against a PR-ref regex and `testForInvalidChars` [2](#0-1) . However, `filepath` receives **no validation whatsoever** before being returned as part of the `IOpenRepositoryFromURLAction` object [3](#0-2) .

### Finding Description
The `IOpenRepositoryFromURLAction.filepath` field is documented as "the file to open after cloning the repository" [4](#0-3) , which strongly implies it is later combined (e.g. via `path.join`) with the cloned repository's local directory path in the consuming code (`app/src/ui/dispatcher/dispatcher.ts`, which imports `IOpenRepositoryFromURLAction` and references `filepath`/`filePath` in multiple places) [5](#0-4) . Because `parseAppURL` never sanitizes or restricts the characters allowed in `filepath` (no rejection of `..`, no path normalization/containment check as is done for `branch`), an attacker-crafted deep link such as `x-github-client://openrepo/OWNER/REPO?filepath=../../../etc/hosts` would pass through `parseAppURL` unmodified.

**Caveat:** I was able to fully confirm the *lack of validation at the parse boundary* (`parse-app-url.ts`), which is the exact symbol/lines named in the question. I was not able to fully retrieve and confirm the exact downstream sink line(s) in `dispatcher.ts` (e.g., a `path.join(repository.path, filepath)` followed by `shell.openItem`/`shell.showItemInFolder`/similar) within the available tool budget — only that `filepath` is imported and referenced there. This means the "does it actually escape the repo directory when opened" step is based on the documented intent of the field rather than a directly cited sink line. This should be verified against the full `dispatcher.ts` source (or by using a Devin session with full file access) before treating this as fully proven end-to-end.

### Impact Explanation
If the downstream consumer joins `repository.path` with the unsanitized `filepath` and then opens the resulting path (e.g. with the OS's default file handler), a malicious `openrepo` link could cause GitHub Desktop to open/read a file entirely outside the cloned repository (e.g., `/etc/hosts`, SSH keys, `.netrc`, credential files), which matches the "file... read outside the repo" impact criterion for valid findings.

### Likelihood Explanation
Deep links are clickable by an unprivileged attacker (e.g., embedded in a webpage or GitHub-hosted content) and require only that the victim click a crafted `x-github-client://openrepo/...` link — no local access or malware needed. The asymmetry in validation (branch/pr are checked, filepath is not) suggests this was simply overlooked rather than intentionally allowed.

### Recommendation
- Validate `filepath` in `parseAppURL` the same way `branch` is validated: reject values containing `..` path segments, absolute path indicators, or invalid characters (reuse/extend `testForInvalidChars` or add a dedicated check).
- At the consumption site in `dispatcher.ts`, when joining `filepath` to `repository.path`, resolve the final path and verify it remains within the repository directory (e.g., using `path.resolve` + a prefix check against the repository root) before opening it.

### Proof of Concept
1. Register/trigger the custom protocol handler for GitHub Desktop.
2. Send/click a link: `x-github-client://openrepo/octocat/Hello-World?filepath=../../../../etc/hosts`
3. `parseAppURL` returns `{ name: 'open-repository-from-url', url: 'octocat/Hello-World', branch: null, pr: null, filepath: '../../../../etc/hosts' }` unchanged [6](#0-5) .
4. If the downstream handler in `dispatcher.ts` joins this with the cloned repo path and opens it, the traversal sequence causes a file outside the repository to be opened. (This final step requires confirmation against the full `dispatcher.ts` implementation, which could not be completely retrieved in this session.)
