Based on the investigation, I found a real, verifiable inconsistency in how Desktop guards against Git argument/option injection via attacker-controlled remote URLs and names — a class of bug the codebase clearly recognizes and defends against in one place (`clone.ts`) but not in others (`remote.ts`, `push.ts`, `fetch.ts`).

### Title
Git argument injection via unsanitized remote URL/name passed to `git remote add` / `fetch` / `push` without `--` separator - (File: app/src/lib/git/remote.ts, app/src/lib/git/fetch.ts, app/src/lib/git/push.ts)

### Summary
`clone.ts` explicitly appends a `--` separator before the attacker-influenced `url` argument to prevent Git from parsing a crafted remote URL/name as a command-line option (`args.push('--', url, path)`), and additionally hardens against path-traversal clone destinations. That same defensive pattern is not applied to `addRemote`, `setRemoteURL`, `fetch`, `fetchRefspec`, or `push`, where a remote name or URL is passed as a bare positional argument to `git`.

### Finding Description
`clone.ts` treats the remote URL as attacker-controlled input and defends it accordingly: [1](#0-0) 

By contrast, `addRemote` and `setRemoteURL` in `remote.ts` pass the caller-supplied `url`/`name` directly to `git` with no `--` terminator: [2](#0-1) [3](#0-2) 

`push` similarly builds its argument array with `remote.name` as a bare positional value, never separated with `--`: [4](#0-3) 

`fetch`/`fetchRefspec` do the same: [5](#0-4) [6](#0-5) 

`remote.name` itself is derived by parsing the raw output of `git remote -v` with a permissive regex that does not reject names beginning with `-`: [7](#0-6) 

Because `.git/config` is a plain text file inside the repository that a user clones/fetches, an attacker who controls the repository contents (e.g., via a submodule, a forked repo, or a repo shared with the victim) can craft a `[remote "..."]` section whose name or url begins with `-` (e.g., something resembling `--upload-pack=<cmd>`). If Desktop later performs a `fetch`/`push`/`addRemote`/`setRemoteURL` operation against that entry without a `--` separator, Git's option parser can interpret the value as a flag rather than a literal name/URL — the exact class of bug that `clone.ts`'s own comments describe defending against ("a crafted URL tricks the UI into deriving a clone path outside the intended base directory" / general Git argument-injection concerns).

### Impact Explanation
If exploitable, this could let a malicious repository (something the victim clones, forks, or adds as a remote) coerce the locally-installed `git` binary to invoke an alternate transport helper or upload-pack/receive-pack executable path when Desktop performs a routine fetch/push, resulting in local code execution outside of Desktop's own sandboxing — matching the "attacker controls a cloned/fetched repository" impact category.

### Likelihood Explanation
Moderate-to-low confidence. I verified the *structural* gap (no `--` separator, no rejection of `-`-prefixed remote names) exists in `remote.ts`/`fetch.ts`/`push.ts` while an equivalent guard exists in `clone.ts`. I was **not able to fully verify** whether modern Git's `parse-options` handling for `fetch`/`push`/`remote add` subcommands actually treats a positionally-placed value beginning with `-` as an option in the exact call shapes used here (this depends on Git's internal `PARSE_OPT_STOP_AT_NON_OPTION` behavior per subcommand, which I could not test in this environment). This uncertainty means the finding should be treated as a code-pattern/hardening gap requiring confirmation with a live Git binary before being treated as a proven RCE.

### Recommendation
- Add `--` separators before all attacker-influenced remote names/URLs passed to `git` (`remote add`, `remote set-url`, `fetch`, `fetchRefspec`, `push`), mirroring the pattern already used in `clone.ts`.
- Reject/normalize remote names that begin with `-` when parsed from `git remote -v` output in `getRemotes` (`app/src/lib/git/remote.ts:12-26`), similar to how `sanitizeCloneName` in `app/src/lib/remote-parsing.ts` already sanitizes clone-derived path names.

### Proof of Concept
Not independently confirmed end-to-end due to inability to execute Git in this environment; the PoC sketch is:
1. Attacker crafts a repository whose `.git/config` contains a `[remote "..."]` section with a name/URL starting with `-` (e.g., mimicking `--upload-pack=<payload>`).
2. Victim clones or is given this repository and adds/fetches/pushes using Desktop's `addRemote`/`fetch`/`push` (`app/src/lib/git/remote.ts:29-37`, `app/src/lib/git/fetch.ts:39-89`, `app/src/lib/git/push.ts:48-118`).
3. Because no `--` separator precedes the name/URL argument, Git may interpret it as an option rather than data.

Given I could not fully verify step 3 against a live Git binary, I'm flagging this as a **plausible but unconfirmed** finding rather than a proven exploit chain.

```typescript
export async function getRemotes(
  repository: Repository
): Promise<ReadonlyArray<IRemote>> {
  const result = await git(['remote', '-v'], repository.path, 'getRemotes', {
    expectedErrors: new Set([GitError.NotAGitRepository]),
  })

  if (result.gitError === GitError.NotAGitRepository) {
    return []
  }

  return [...result.stdout.matchAll(/^(.+)\t(.+)\s\(fetch\)/gm)].map(
    ([, name, url]) => ({ name, url })
  )
}
```
