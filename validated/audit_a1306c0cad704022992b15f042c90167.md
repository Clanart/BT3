This confirms the vulnerability class: the codebase itself explicitly acknowledges (in `sei-cosmos/x/distribution/keeper/hooks.go` comments and its test) that an EVM address's Sei mapping can be **"re-associated ... away from the direct-cast Sei address it was created under"** via `associatePubKey`, making the direct-cast address permanently unable to receive funds via `CanAddressReceive`/`BlockedAddr` checks. This is caused by the `associatePublicKey` precompile method never verifying that the caller actually controls the private key for the supplied public key.

### Title
Unauthenticated forced Sei⇄EVM address (re-)association via public-key-only `associatePubKey` precompile permanently freezes funds sent to the direct-cast address - (File: precompiles/addr/addr.go)

### Summary
The `addr` precompile exposes two ways to link an EVM address to a Sei address: `associate` (requires an ECDSA signature proving key ownership) and `associatePubKey`/`associatePublicKey`, which accepts only a raw public key with **no proof of possession**. Any caller can invoke `associatePubKey(pubKeyHex)` with a victim's known public key (public keys are not secret — they are recoverable from any prior signed EVM or Cosmos transaction) to force-create the EVM↔Sei mapping for the victim's account at a time of the attacker's choosing.

### Finding Description
`PrecompileExecutor.associatePublicKey` in [1](#0-0)  only requires the raw public key bytes as an argument and never checks a signature over any challenge message. It derives `evmAddr`/`seiAddr` from that pubkey via `helpers.GetAddressesFromPubkeyBytes` and immediately calls `associateAddresses` [2](#0-1) , which permanently writes the mapping via `AssociationHelper.AssociateAddresses` and migrates balances from the "cast" address to the derived address [3](#0-2) .

By contrast, the sibling `associate` method requires a valid ECDSA signature (v, r, s) over a message before deriving/associating addresses [4](#0-3) , proving the caller controls the private key. `associatePubKey` bypasses this proof-of-possession requirement entirely.

Once an address mapping exists, `CanAddressReceive`/`BlockedAddr` logic in the bank keeper starts rejecting sends to the now-obsolete direct-cast address unless it equals the newly associated address [5](#0-4) . The codebase's own tests and comments confirm this consequence is real and previously observed: `hooks.go` explicitly documents that a delegator/validator's cast address can become "unable to receive — e.g. accAddr is an EVM address whose Sei mapping was re-associated to a different address ... via associatePubKey" [6](#0-5) , and a regression test reproduces exactly this scenario by calling `SetAddressMapping` to simulate `associatePubKey` re-associating away from the direct-cast/operator address, causing sends to that address to fail [7](#0-6) .

### Impact Explanation
Any address that has not yet self-associated is vulnerable: an attacker can extract a target's Ethereum secp256k1 public key from any previously broadcast transaction (public by definition) and call `associatePubKey` on Sei to unilaterally establish the mapping. This:
- Forces `MigrateBalance`, moving all funds at the target's direct-cast Sei address to the pubkey-derived Sei address without the owner's consent or timing choice.
- Permanently blocks the direct-cast address from receiving further funds (`CanAddressReceive` returns false once a different associated address exists), so counterparties, module hooks (e.g., distribution commission withdrawal, IBC transfers, staking rewards) or third parties who still target the old cast address after this forced association can have their transfers rejected/reverted or, in EndBlock contexts, at minimum have funds diverted to the community pool instead of the intended recipient — a permanent misdirection/freezing of funds relative to the sender's intent.
- Because association is one-way and irreversible (`already associated` guard prevents undoing it), this is a permanent state change forced by an unauthorized third party, matching the CVE's root cause: an identity-linking control that should require the account owner's affirmative proof of control skips that verification, causing the "unintended" identity to be established for the victim without consent.

### Likelihood Explanation
Trivial to exploit: `associatePubKey` is a public precompile method reachable by any EVM transaction sender at `0x0000...1004`. The only precondition is knowing the target's public key, which is inherent to how ECDSA/secp256k1 signatures work and is exposed the first time the target signs any transaction (Cosmos or EVM). No special privileges, timing races with validators, or governance access are needed.

### Recommendation
Require the same proof-of-key-possession for `associatePubKey` as for `associate` — e.g., require a signature over a fixed/nonce-based challenge message signed by the corresponding private key, or restrict `associatePubKey` so it can only be invoked by the address's own tx sender/authority (e.g., verify `msg.sender`/tx signer corresponds to the derived `evmAddr`) before performing `AssociateAddresses`.

### Proof of Concept
1. Observe any transaction signed by a victim (EVM tx or Cosmos tx using secp256k1), and extract the uncompressed/compressed public key via standard ECDSA recovery (public keys are not secret).
2. As any account, call `associatePubKey(victimPubKeyHex)` on the addr precompile (`0x0000000000000000000000000000000000001004`) before the victim ever calls `associate` themselves.
3. Observe: `GetSeiAddress(victimEvmAddr)` / `GetEVMAddress(victimTrueSeiAddr)` now return the forced association; any funds previously sitting at `sdk.AccAddress(victimEvmAddr[:])` are moved to the derived Sei address; subsequent sends to `sdk.AccAddress(victimEvmAddr[:])` from other actors (e.g., a counterparty who cached the old cast address, or the distribution module during validator removal, per `keeper_test.go`'s `TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator`) are now rejected/redirected rather than reaching the victim as originally intended.

func (p PrecompileExecutor) associatePublicKey(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {

		return nil, 0, err

		return nil, 0, err
	}

	// Takes a single argument, a compressed pubkey in hex format, excluding the '0x'
	pubKeyHex := args[0].(string)

	pubKeyBytes, err := hex.DecodeString(pubKeyHex)
	if err != nil {
		return nil, 0, err
	}

	pubKey, err := btcec.ParsePubKey(pubKeyBytes)

	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)
}

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)

	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err

		}
