### Title
Missing bounds check in `is_atom_canonical`/`is_clvm_canonical` CLVM-serialization scanner can throw an unhandled out-of-range access on attacker-supplied spend data - (File: chia/full_node/mempool_manager.py)

### Summary
The Linux CVE is a classic "attacker-controlled length field used to index a buffer without validating it stays within bounds" bug. The closest reachable analog in this codebase is `is_atom_canonical`/`is_clvm_canonical` in `chia/full_node/mempool_manager.py`, which walks a CLVM-serialized buffer byte-by-byte using length-prefix bits taken directly from attacker-supplied bytes, without checking that the derived `offset` stays inside `clvm_buffer` before dereferencing it.

### Finding Description
`is_atom_canonical` decodes the high bits of `clvm_buffer[offset]` to determine how many additional prefix bytes (`prefix_len`) encode the atom length, then loops `prefix_len` times doing: [1](#0-0) 

At no point does the function verify `offset < len(clvm_buffer)` before indexing `clvm_buffer[offset]`, even though `prefix_len` (up to 5) is derived from the untrusted byte the attacker controls. `is_clvm_canonical` then drives this walk across the whole buffer with a similar unchecked `clvm_buffer[offset]` access pattern: [2](#0-1) 

This is directly analogous to CVE-2021-31916: a bound check failure on a length field supplied by the caller leads to a read past the allocated buffer. In this Python implementation the access is bounds-checked by the interpreter, so it manifests as an `IndexError` instead of raw memory corruption, but the root cause — deriving an offset from an attacker-controlled length prefix and dereferencing it without validating remaining buffer size — is the same bug class.

### Impact Explanation
`clvm_buffer` here corresponds to serialized CLVM data taken from a submitted spend bundle's coin-spend solution/puzzle-reveal, which is fully attacker-controlled content reachable by any unprivileged spend-bundle submitter through the mempool admission path. A malformed buffer (e.g., an atom byte at/near the end of the buffer whose top bits declare a 5-byte length prefix that the remaining buffer cannot satisfy) drives `offset` past `len(clvm_buffer)`, raising an unhandled `IndexError` inside the canonical-serialization check performed during spend-bundle validation. If that exception is not caught somewhere in the calling chain, it can abort the async validation task for that spend bundle, which is a spend-triggered transaction-processing halt — one of the accepted impact categories.

### Likelihood Explanation
Any user able to submit a spend bundle can construct a CLVM buffer with a crafted length-prefix byte sequence; no privileged access, other peers, or farming is required. The trigger only depends on the last few bytes of the serialized CLVM payload subjected to this canonical check.

### Recommendation
Add explicit bounds checks in `is_atom_canonical` before each `clvm_buffer[offset]` access (mirroring the pattern already used elsewhere in the codebase, e.g. `skip_bytes`/`skip_list` in `chia/full_node/full_block_utils.py`, which validate `n > len(buf)` before slicing), and ensure `is_clvm_canonical`'s call sites in `mempool_manager.py` wrap this check in exception handling (or return a definitive `False`/error) rather than allowing an `IndexError` to propagate out of spend-bundle validation.

### Proof of Concept
I was unable to fully trace every call site and exception-handling wrapper around `is_clvm_canonical` within the available index (the tool budget was exhausted before I could confirm whether an outer `try/except` already guards every caller). A concrete PoC would need to:
1. Build a coin-spend whose serialized CLVM solution/puzzle ends in a byte matching the `0b11111100` (5-prefix-byte) pattern with fewer than 5 bytes remaining in the buffer.
2. Submit it as part of a spend bundle to `MempoolManager` and observe whether `is_clvm_canonical`'s unguarded `clvm_buffer[offset]` access raises an uncaught `IndexError` during admission, and whether that exception escapes far enough to disrupt transaction processing for other bundles.

Given I could not verify the exception-handling boundary with certainty from the available index, this should be validated against the full source (e.g., via a Devin session with complete repository access) before treating it as a confirmed DoS.
