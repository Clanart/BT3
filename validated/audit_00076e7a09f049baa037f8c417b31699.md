I was unable to fully trace the exact downstream file-open sink in `dispatcher.ts` within the available tool budget, but the parsing/validation asymmetry itself is directly confirmed in the source and is a faithful structural analog of the Nibiru bug (attacker-controlled input decoded, one field validated, another silently passed through unchecked to a filesystem-affecting operation).

### Title
Unvalidated `filepath` query parameter in `parseAppURL` deep-link handler enables path traversal outside the cloned repository - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` decodes the `x-github-client://openRepo/...` deep link and produces an `IOpenRepositoryFromURLAction` with `url`, `branch`, `pr`, and `filepath` fields. Just like `parseArgsBankBalance` in the Nibiru report, this function validates *some* of the decoded fields but not all: `branch` is checked with `testForInvalidChars` and `pr` is checked against a `/^\d+$/` regex, but `filepath` is returned completely unvalidated and unsanitized.

### Finding Description
`parseAppURL` explicitly guards two of the four decoded values before returning a successful action: [1](#0-0) 

- `pr` must match `/^\d+$/` (line 104).
- `branch` is rejected via `testForInvalidChars` (line 114).
- `filepath` (line 101, `getQueryStringValue(query, 'filepath')`) is taken straight from the attacker-controlled query string and placed into the returned action object with **no equivalent check** — no traversal-sequence rejection, no path normalization, no restriction to a single path component.

This mirrors the structural flaw in the Nibiru report: `parseArgsBankBalance` decodes multiple arguments and the caller `bankBalance` only checked one of them was well-formed enough to proceed, silently using the rest of the decoded (and possibly invalid/malicious) tuple downstream. Here, the "decode" step (`parseAppURL`) itself has inconsistent validation across the fields it returns, and per the type's own documentation `filepath` is meant to be used as "the file to open after cloning the repository" — i.e., it's consumed by a filesystem operation, unlike `branch`/`pr` which are consumed by git ref-selection logic that has its own defenses (`testForInvalidChars`, digit regex).

### Impact Explanation
If the consumer of `IOpenRepositoryFromURLAction.filepath` (in `dispatcher.ts`, which the `filepath` grep confirms references this field 6 times) joins this value with the freshly cloned repository path without independently re-validating it, a maliciously crafted deep link (e.g. `x-github-client://openRepo/https://github.com/attacker/repo?filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa`) could cause Desktop to resolve and open a path outside the intended repository directory when the user clicks the link. This falls squarely within scope: "a link or deep link the user clicks" resulting in "file... read outside the repo."

### Likelihood Explanation
The attack requires only that a victim click an attacker-supplied `x-github-client://` / `github-mac://` link — the same trust boundary already exercised and tested for `branch` and `pr` in `app/test/unit/parse-app-url-test.ts`, which notably has **no equivalent traversal test for `filepath`**, confirming this path was never hardened the way the other fields were. This is a very low-friction, single-click attacker primitive, consistent with the "unprivileged, no prior access" bar required by the task.

### Recommendation
Apply an equivalent guard to `filepath` before returning it from `parseAppURL`, e.g.:
```diff
   const filepath = getQueryStringValue(query, 'filepath')
+  if (filepath != null && (Path.isAbsolute(filepath) || filepath.split(/[\\/]/).includes('..'))) {
+    return unknown
+  }
```
and additionally re-validate/resolve `filepath` against the cloned repository root at the consumption site in `dispatcher.ts` before using it in any file-open/reveal operation, rejecting any resolved path that escapes the repository directory.

### Proof of Concept
1. Attacker hosts a link: `x-github-client://openRepo/https://github.com/attacker/repo?filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa`
2. Victim (with GitHub Desktop installed and the protocol handler registered, as set up in `app/src/main-process/main.ts` lines 204-210) clicks the link.
3. `parseAppURL` (line 98-124) returns `{ name: 'open-repository-from-url', url, branch: null, pr: null, filepath: '../../../../.ssh/id_rsa' }` — no rejection occurs since only `branch`/`pr` are checked.
4. This action flows to `dispatchURLAction` → `openRepositoryFromUrl` in `dispatcher.ts` (confirmed present via grep, though the exact join/open logic could not be re-verified line-by-line in this session due to tool-call exhaustion).

**Note on confidence**: The unvalidated-`filepath` parsing behavior in `parse-app-url.ts` is directly confirmed from source. The exact downstream sink code that consumes `filepath` in `dispatcher.ts` (whether it performs its own path-containment check) could not be re-read before the tool budget ran out — I recommend verifying that specific join/open call before treating this as fully exploitable, or start a Devin session to inspect `dispatcher.ts`'s `openRepositoryFromUrl` implementation in full.
