### Title
Colliding Display Names in `make_offer` Cause Hidden/Unreviewed Asset Transfers in Offer Confirmation Summary - (File: `chia/cmds/wallet_funcs.py`)

### Summary
`make_offer` in `chia/cmds/wallet_funcs.py` builds a confirmation summary (`printable_dict`) keyed by the human-readable asset **name** rather than by the unique asset **id**. When two distinct, unrecognized CAT asset ids are included in the same offer, they both resolve to the literal name `"Unknown CAT"`, causing the second entry to silently overwrite the first in the dictionary used to render the "OFFERING"/"REQUESTING" summary the user reviews before confirming (`cli_confirm("Confirm (y/n): ", ...)`). The actual offer that gets built and signed (`offer_dict`, keyed by the real asset id) still contains both distinct assets/amounts. This is the same rendering-collision bug class as the reported Cosmos SDK `SIGN_MODE_TEXTUAL` issue: two semantically different transaction contents ("denominations") are collapsed into an identical rendered confirmation screen, defeating rendering injectivity and the user's ability to give informed consent.

### Finding Description
In `chia/cmds/wallet_funcs.py`, `make_offer` iterates over all `offers`/`requests` items and, for each, computes a display `name` and a unique `id`: [1](#0-0) 

For any hex asset id that is a valid `bytes32` but not a CAT the wallet already knows about, `name` is hard-coded to `"Unknown CAT"`: [2](#0-1) 

The confirmation-display structure `printable_dict` is keyed by this `name`, not by `id`: [3](#0-2) [4](#0-3) 

Meanwhile, the actual offer sent to `create_offer_for_ids` (`offer_dict`) is keyed by `id`, which correctly stays unique per asset: [5](#0-4) 

The uniqueness check at line 591 only rejects duplicate `id`s (the same asset offered/requested twice); it does nothing to prevent multiple *distinct* ids from mapping to the same display `name`. When the user later reviews the printed summary and confirms: [6](#0-5) 

only the *last* `printable_dict[name]` entry for each colliding name is shown — earlier entries for a different, distinct asset id are silently dropped from the screen, even though that asset's amount remains fully present in `offer_dict` and is included in the offer that is created, written to the offer file, and (when taken/pushed) results in real coin spends: [7](#0-6) 

This mirrors the reported bug class exactly: the rendering function is not injective with respect to the underlying transaction content (asset id + amount), so two different offers/requests can render identically (or one can silently mask another), allowing a user to "confirm" an offer whose real content differs from what was displayed.

### Impact Explanation
A user (or a user following instructions/tooling suggested by a counterparty) who runs `make_offer` with two or more unrecognized CAT asset ids on the same side (both "offers" or mixed) will see a confirmation screen that omits one of the offered/requested assets entirely. If they confirm, the resulting `Offer` — which does get signed and can be pushed/broadcast or shared as a `.offer` file for a counterparty to take — actually commits to spending/requesting an asset amount the user never saw and did not knowingly approve. This is a concrete instance of unintended/unauthorized-from-the-user's-perspective coin movement caused purely by a rendering defect, not by any on-chain validation gap. The same collision applies more broadly any time two distinct asset identifiers happen to resolve to the same display `name` (e.g., two unrecognized CATs, or CAT wallets a user has manually renamed to the same string via `add_token`/`set_cat_name`).

### Likelihood Explanation
Reaching this requires only invoking the existing `chia wallet make_offer` CLI/RPC path with two or more foreign/unregistered CAT asset ids in the offer/request list — no privileged access, no protocol-level exploit, and no cooperation from a malicious peer or farmer is needed. An attacker who wants a victim to unknowingly co-offer an extra unwanted CAT amount only needs to supply/suggest asset ids that the victim's wallet does not already recognize (trivial, since any newly created/unregistered CAT tail hash qualifies), making this readily reachable in normal wallet-usage/offer-creation workflows.

### Recommendation
Key `printable_dict` (and any equivalent structure used purely for confirmation display) by the unique asset `id`, not by the resolved display `name`, and render the (possibly duplicated) `name` as a label alongside each unique `id` line. Alternatively, detect when two distinct ids map to the same display name and disambiguate the presented labels (e.g., append a shortened asset id) before printing the confirmation summary, ensuring the rendering is injective with respect to the actual offer content the user is about to sign.

### Proof of Concept
1. Identify (or mint) two distinct CAT asset ids, `CAT_A` and `CAT_B`, neither of which is registered/named in the victim wallet (so both resolve to `"Unknown CAT"` per lines 522-526 of `chia/cmds/wallet_funcs.py`).
2. Run:
   ```
   chia wallet make_offer -o <CAT_A_hex>:1 -o <CAT_B_hex>:0.000001 -r 1:5
   ```
3. Observe the "Creating Offer" / "OFFERING:" summary printed at lines 600-604: only a single `- <amount> Unknown CAT (<mojos> mojos)` line appears (the entry for whichever asset id was processed last in `printable_dict`), because both `CAT_A` and `CAT_B` wrote to the same `printable_dict["Unknown CAT"]` key.
4. Confirm the offer (`y`). The resulting offer file created via `create_offer_for_ids` (lines 650-664) contains offer entries for **both** `CAT_A` and `CAT_B` in `offer_dict` (each keyed by its distinct `id`), even though the confirmation screen the user approved only displayed one of them — an exact analog of the reported "collision of formatted coins" rendering-invariability violation.
