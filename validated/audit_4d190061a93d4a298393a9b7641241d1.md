### Title
Unbounded memory allocation from attacker-controlled git blob/diff output due to `maxBuffer: Infinity` for buffer-encoded git commands - (File: `app/src/lib/git/core.ts`)

### Summary
The CL-2020-21 report describes a broken invariant: a length/size field taken from attacker-controlled data is used to allocate memory *before* the size is validated, allowing a single malicious message to force a multi-gigabyte allocation. GitHub Desktop has a structurally identical pattern in its git process execution layer: whenever a git command is run with `encoding: 'buffer'`, the `git()` helper in `app/src/lib/git/core.ts` sets `maxBuffer` to `Infinity`, meaning Node.js will buffer the *entire* stdout of the git subprocess into memory with no upper bound, regardless of how large that output is. The actual size checks (`isValidBuffer`, `MaxDiffBufferSize`) that exist in `app/src/lib/git/diff.ts` are only applied *after* the buffer has already been fully allocated and read into the renderer/main process memory.

### Finding Description
`git()` builds its default execution options as: [1](#0-0) 

```
maxBuffer: options?.encoding === 'buffer' ? Infinity : kStringMaxLength,
```

Several code paths that read data derived directly from a cloned/fetched repository's content invoke `git()` with `encoding: 'buffer'` and do not override `maxBuffer`, so they inherit `Infinity`:

- `getBlobContents` in `app/src/lib/git/show.ts`, used to read arbitrary blob content by commitish/path: [2](#0-1) 
- `getCommitDiff` in `app/src/lib/git/diff.ts`, which runs `git log ... --patch-with-raw` over a commit path and reads the whole diff into a `Buffer`: [3](#0-2) 
- `getWorkingDirectoryDiff`, same pattern for working-directory diffs: [4](#0-3) 

The only mitigations that exist are a *post-hoc* size check performed after the buffer has already been materialized: [5](#0-4) [6](#0-5) 

`isValidBuffer` and `isBufferTooLarge`/`isDiffTooLarge` only run inside `buildDiff`, i.e. *after* `git()` has already resolved with a fully-buffered `Buffer` in memory — the allocation (and the cost of it) has already happened by the time the guard fires. This is the exact same "unchecked-header-then-alloc" shape as the Snappy bug: the attacker (via crafted repository content — a huge blob, a huge generated diff, or a pathological binary-to-text diff) fully controls the size of data git will emit on stdout, and Desktop places no bound on how much of that output it will buffer before it looks at the size.

By contrast, `getPartialBlobContentsCatchPathNotInRef` correctly sets an explicit, caller-supplied `maxBuffer: length` [7](#0-6)  — showing that the codebase is aware bounded reads are needed for untrusted blob content, but this bound is not applied to `getBlobContents` or to the diff-producing functions.

### Impact Explanation
A crafted/malicious repository (something the user clones, fetches, or opens — squarely within the report's threat model of "attacker controls a cloned/fetched repository") can contain a commit or working-tree file that, when diffed or shown, produces an extremely large stdout stream from git (e.g., a large blob, or content engineered to explode when diffed, such as many changed lines in a huge text file). Because `maxBuffer` is `Infinity` for these calls, Node/dugite will buffer the entire output with no cap, causing excessive memory consumption in Desktop's main process. This can degrade to an out-of-memory crash of the Electron main process (denial of service for the whole application, not just a background operation), and in constrained environments can be used to reliably force the app to abort while handling a single crafted repository, without any local access, admin rights, or social engineering beyond opening/viewing a repository the user already added.

### Likelihood Explanation
Likelihood is realistic: simply viewing a commit, browsing history, or opening the Changes view for a file that triggers `getCommitDiff`/`getWorkingDirectoryDiff`/`getBlobContents` on attacker-crafted content is a normal user action that requires no special interaction. No warning or confirmation is shown before the buffer is fully read, since the size check happens only after `git()` already returned.

### Recommendation
Set an explicit, bounded `maxBuffer` for all buffer-encoded git invocations that read potentially attacker-sized content (`getBlobContents`, `getCommitDiff`, `getWorkingDirectoryDiff`, and any other caller relying on the `encoding: 'buffer'` default), matching the existing `MaxDiffBufferSize`/reasonable size constants already defined in `diff.ts`, so that the same `ERR_CHILD_PROCESS_STDIO_MAXBUFFER` handling used by `getPartialBlobContentsCatchPathNotInRef` is exercised, and the size check happens *before* unbounded memory is committed, not after.

### Proof of Concept
1. Create or obtain a repository containing a single file with an extremely large blob (or content that generates a pathologically large unified diff) — fully within attacker control since they craft the repository being cloned/opened.
2. Have the victim open this repository in GitHub Desktop and view the commit/file diff, triggering `getCommitDiff` or `getWorkingDirectoryDiff` (or view the blob via a path that calls `getBlobContents`).
3. Observe that `git()` is invoked with `encoding: 'buffer'` and no `maxBuffer` override, so `core.ts`'s default of `maxBuffer: Infinity` is used [8](#0-7) , letting Node buffer the entire git stdout output unbounded before `isValidBuffer`/`isDiffTooLarge` in `diff.ts` ever run [6](#0-5) , resulting in excessive memory usage/crash from a single crafted repository.
