### Title
Attacker can pre-occupy Serai's deterministic internal Bitcoin addresses (Change/Forwarded/Branch) with crafted outputs, which the Scanner unconditionally reports as protocol-owned funds - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary

Analogous to [H-12], where an adversary pre-computes a deterministic CREATE2 address and occupies it before the protocol acts on it, Serai's Bitcoin scanner derives a fixed set of internal script addresses from public parameters and then attributes **any** on-chain payment to those scripts to the protocol itself, with no provenance check. An unprivileged attacker can precompute all four internal addresses (External, Branch, Change, Forwarded) from the public group key and public `hash_to_F` offsets, and send arbitrary Bitcoin transactions to them. These outputs are classified as `OutputType::Change`/`OutputType::Forwarded`/`OutputType::Branch` — i.e., treated as outputs the protocol itself created — and are inserted into the multisig UTXO pool regardless of value, including sub-economical dust.

### Finding Description

`Scanner::register_offset` and `scan_transaction` in `networks/bitcoin/src/wallet/mod.rs` work purely on `script_pubkey` matching:

- `Scanner::new` registers the base P2TR script (`offset = Scalar::ZERO`) [1](#0-0) 
- `register_offset` deterministically maps an offset scalar to a script, incrementing until the point is even [2](#0-1) 
- `scan_transaction` emits a `ReceivedOutput` for **any** transaction output whose `script_pubkey` is in the map — no origin, value floor, or transaction-shape check [3](#0-2) 

The processor then deterministically reconstructs the same scanner in `scanner()` using public constants (`KEY_DST`, `hash_to_F(KEY_DST, "branch"|"change"|"forward")`) [4](#0-3) , and `get_outputs` labels every match by kind (`kinds[offset_repr_ref]`) and pushes it into the output set [5](#0-4) . `OutputType::Change` is documented as "added to the available UTXO pool with no further action" and `Forwarded` as "forwarded output from the prior multisig" [6](#0-5) .

Nothing prevents an attacker — who needs only the public group key and the public hash constants — from pre-computing these scripts exactly as the Safe attacker precomputed the proxy address, and sending transactions to them. The code even acknowledges the forged-output possibility for `Branch` ("Eve, a malicious actor, has sent us a forged TX which is... equally as usable?") [7](#0-6) , but that reasoning does not extend to `Change`/`Forwarded` outputs of attacker-chosen, uneconomical values.

### Impact Explanation

1. **Unspendable-but-reported funds:** `scan_transaction` applies no minimum-value filter, while spending each input costs a fee (`calculate_weight_vbytes` adds ~230 WU per input) [8](#0-7) . An attacker can flood the Change/Forwarded scripts with dust-valued outputs. These are reported as received protocol outputs yet cost more to spend than they are worth — funds reported received that are not economically spendable.
2. **Griefing/DoS of withdrawals:** polluted inputs inflate the UTXO pool, increasing `needed_fee`, forcing `NotEnoughFunds`/`TooLargeTransaction` failures in `SignableTransaction::new` [9](#0-8) , mirroring H-12's "counterpart creation can never complete" denial.
3. **Kind spoofing:** an output to the `Forwarded` script is indistinguishable from a real forwarded output from a retired multisig, corrupting provenance/`presumed_origin` accounting [10](#0-9) .

### Likelihood Explanation

High likelihood as a griefing vector: the addresses are fully deterministic and publicly derivable (public group key, fixed `KEY_DST`, fixed labels), the attacker needs only an ordinary Bitcoin transaction of their own construction, and no authentication or provenance check exists in `scan_transaction`. The cost is the value the attacker chooses to lock (can be minimal dust) plus fees.

### Recommendation

- Enforce `N::DUST` (or a stricter internal-floor) on scanned outputs before admitting non-`External` kinds to the UTXO pool.
- Bind `Change`/`Forwarded`/`Branch` outputs to a protocol-originated transaction where feasible (e.g., match against registered eventualities / expected plan outputs, as `EventualitiesTracker` already does), rather than accepting any payment to the script.
- Track attacker-sent dust to internal addresses as `operating_costs` and prefer dropping them instead of forcing them into spends.

### Proof of Concept

1. Observe the multisig's public `group_key` `K` (published on-chain / derivable from prior deposits).
2. Compute `branch = hash_to_F(b"Serai Bitcoin Output Offset", b"branch")` etc., resolve each through `register_offset`'s even-point loop, and derive the P2TR scripts — identical to `processor/src/networks/bitcoin.rs:313-347`.
3. Broadcast a Bitcoin transaction with dozens of outputs of value < `Bitcoin::DUST` (10,000 sat; even 546 sat suffices since the scanner has no floor) paying the Change and Forwarded scripts.
4. `Bitcoin::get_outputs` returns each as `Output { kind: Change|Forwarded, .. }`; the scheduler admits them to the spendable pool. Subsequent `prepare_send`/`SignableTransaction::new` calls must spend these inputs (paying more in fees than their value) or hit `TooLargeTransaction`/`NotEnoughFunds`, degrading or blocking withdrawals — the same griefing impact class as blocking the Safe counterpart deployment.

Caveat: the precise downstream loss depends on the scheduler's UTXO selection policy (`processor/src/multisigs/scheduler/utxo.rs`), which I did not fully trace; if the scheduler can simply ignore poisoned inputs indefinitely, the impact reduces to misreported unspendable funds rather than hard DoS.

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

// Always construct the full scanner in order to ensure there's no collisions
fn scanner(
  key: ProjectivePoint,
) -> (Scanner, HashMap<OutputType, Scalar>, HashMap<Vec<u8>, OutputType>) {
  let mut scanner = Scanner::new(key).unwrap();
  let mut offsets = HashMap::from([(OutputType::External, Scalar::ZERO)]);

  let zero = Scalar::ZERO.to_repr();
  let zero_ref: &[u8] = zero.as_ref();
  let mut kinds = HashMap::from([(zero_ref.to_vec(), OutputType::External)]);

  let mut register = |kind, offset| {
    let offset = scanner.register_offset(offset).expect("offset collision");
    offsets.insert(kind, offset);

    let offset = offset.to_repr();
    let offset_ref: &[u8] = offset.as_ref();
    kinds.insert(offset_ref.to_vec(), kind);
  };

  register(
    OutputType::Branch,
    *BRANCH_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"branch")),
  );
  register(
    OutputType::Change,
    *CHANGE_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"change")),
  );
  register(
    OutputType::Forwarded,
    *FORWARD_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"forward")),
  );

  (scanner, offsets, kinds)
}

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
