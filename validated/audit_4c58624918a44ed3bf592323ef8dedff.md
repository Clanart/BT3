### Title
Unsanitized PR `head.repo.clone_url` passed to `git remote add`/`git fetch` enables remote-helper command execution - ([File: app/src/lib/stores/app-store.ts])

### Summary
This mirrors the report's "check happens on one value, but a subsequent privileged operation trusts a different, attacker-supplied value" pattern. In the smart-contract report, the taker's callback is trusted to have moved tokens correctly and the balance check is fooled by reusing the same credit against a second order. In Desktop, `_findPullRequestBranch` trusts an attacker-controlled string (`headCloneUrl`, sourced from a pull request's `head.repo.clone_url`) as a legitimate git remote URL and feeds it unvalidated into `git remote add` and later `git fetch`, without ever checking it against an allow-list of URL schemes/hosts.

### Finding Description
`_findPullRequestBranch` receives `headCloneUrl` straight from GitHub API pull-request data and, when no existing remote matches it, calls: [1](#0-0) 

`addRemote` then executes `git remote add <name> <url>` with that raw string as a positional argument, with no format validation (no scheme allow-list, no rejection of values that don't look like `https://`/`ssh://`/`git@` URLs): [2](#0-1) 

Git supports "remote helper" URLs of the form `<scheme>::<command>` (e.g. `ext::`, or any registered helper) as well as `file://` targets. Because this value is never checked against `parseRemote`'s known GitHub URL shapes (that validation only exists in `app/src/lib/remote-parsing.ts` and is not applied here) or against an allow-listed set of protocols, an attacker who opens a pull request against a repository the victim has cloned in Desktop can set `head.repo.clone_url` (or, since PR head repos can be arbitrary, could point `clone_url` at a URL Git will treat as a "remote helper" invocation) so that when the victim opens/checks out that PR — either from the in-app PR list (`app/src/ui/branches/pull-request-list.tsx:291-307` → `dispatcher.checkoutPullRequest` → `_checkoutPullRequest`) or via the `x-github-desktop://` deep link handler (`openPullRequestFromUrl` in `app/src/ui/dispatcher/dispatcher.ts:1998-2049`) — Desktop calls `addRemote(repository, forkRemoteName, headCloneUrl)` and later fetches from it: [3](#0-2) [4](#0-3) 

No search in the codebase turned up any `GIT_ALLOW_PROTOCOL` setting or equivalent restriction being passed into the `git`/`fetch` execution path used here, so the default (unrestricted) set of git transports, including remote helpers, is available when this fetch runs.

### Impact Explanation
If the attacker-controlled `clone_url` can be crafted as (or resolves through git config expansion to) a remote-helper invocation, `git fetch` against that remote executes an attacker-chosen command in the context of the Desktop process/user, i.e. code execution outside any sandbox, triggered purely by the victim opening/checking out a pull request or clicking a "x-github-desktop://openPullRequest" deep link — squarely within the accepted impact categories (attacker controls a GitHub API object / a link the user clicks, resulting in code execution). Even short of full command execution, an unchecked URL also allows redirecting the fetch to an attacker-controlled server, which combined with Desktop's credential-helper trampoline (`app/src/lib/trampoline/trampoline-credential-helper.ts`) risks leaking stored GitHub credentials/tokens to that server during authentication.

### Likelihood Explanation
Likelihood is moderate to high in terms of reachability — no user action beyond viewing/opening a PR (or clicking a link) is required, and the code path is exercised by ordinary, documented Desktop features (fork PR checkout). What is **unverified** with the available tooling is whether the dugite/git version bundled with Desktop still honors the historical `ext::`/remote-helper schemes when passed this way, and whether any upstream `dugite`/git config in Desktop's spawn environment (not visible in the indexed subset of the repo) already sets `GIT_ALLOW_PROTOCOL` or `protocol.*.allow`. I could not find such a restriction in this codebase, but the relevant environment setup for `git fetch` (`envForRemoteOperation`, `withTrampolineEnv`) does not appear to set it either based on what was inspected.

### Recommendation
- Validate `headCloneUrl` (and any other externally-sourced clone/remote URL, e.g. `apiRepo.clone_url` in `update-remote-url.ts`) against `parseRemote`/an explicit allow-list of `https://`, `ssh://`/`git@` schemes before calling `addRemote` or `setRemoteURL`.
- Explicitly set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` (excluding `ext`, `file`, and other helper protocols) in the environment used for any fetch/remote-add triggered by externally sourced data (PR objects, deep links).
- Reject `clone_url` values that don't match the expected GitHub repository URL shape before ever reaching `git remote add`.

### Proof of Concept
1. Attacker forks the victim's public/organization repository and opens a pull request from a "head repository" whose `clone_url` field is set/resolves to a value that Git's transport layer will treat as a remote-helper invocation rather than a plain URL.
2. Victim, using GitHub Desktop, opens that pull request from the in-app PR list or via a `x-github-desktop://openPullRequest` link (e.g. shared in the PR description/comment).
3. `openPullRequestFromUrl` / `checkoutPullRequest` → `_checkoutPullRequest` → `_findPullRequestBranch` executes `addRemote(repository, forkRemoteName, headCloneUrl)` followed by `_fetchRemote`, both operating on the unvalidated `clone_url`.
4. If the URL resolves to a remote-helper transport, the fetch step causes Git to invoke that helper, executing attacker-controlled logic in the victim's environment.

Note: I was not able to fully confirm the exact remote-helper string format that a GitHub API `clone_url` field can be coerced into within the bounds of the indexed code (this would require testing against the live `dugite`/git binary Desktop bundles), so this should be verified experimentally before treating it as fully confirmed remote code execution rather than a URL-validation gap with SSRF/credential-leak impact at minimum.
