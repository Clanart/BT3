### Title
Stale GitHub repository association is never cleared, letting a re-pointed remote silently reuse a different repository's identity/permissions - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`AppStore.repositoryWithRefreshedGitHubRepository` contains an explicit, acknowledged gap: it never clears a local `Repository`'s `gitHubRepository` association once one has been established, and only re-derives it opportunistically from the current `origin` remote. [1](#0-0) 
This mirrors the reported bug class exactly: an old mapping entry (delegatee/association) is never removed when a new relationship is (or should be) established, so stale trust/identity data keeps being used alongside or instead of the correct one.

### Finding Description
`matchGitHubRepository` derives `owner`/`name` purely from the string contents of the current default remote URL, with no cryptographic or server-side verification tying it back to the previously associated `GitHubRepository` row. [2](#0-1) 

`repositoryWithRefreshedGitHubRepository` uses that match to refresh the association, but the code comment states the invariant is intentionally broken: associations are *never cleared*, only updated when a fresh match/API call succeeds:
```
// TODO: We currently never clear GitHub repository associations (see
// https://github.com/desktop/desktop/issues/1144). So we can bail early at
// this point.
if (!match) {
  return repository
}
``` [3](#0-2) 

`upsertGitHubRepositoryFromMatch` compounds this: it looks up an *existing* `GitHubRepository` row purely by the `[ownerID+name]` composite key parsed out of the (attacker-influenced) remote URL, and if found, reuses that existing row's identity/permissions/parent chain rather than creating a fresh, unambiguous record: [4](#0-3) 

Because `owner`/`name` come from parsing a string the remote controls (a cloned repo's `origin`, or a URL the user is asked to add), and because a match is only attempted opportunistically (`if (!gitStore.defaultRemote) await gitStore.loadRemotes()`), a repository whose remote is changed to spoof an existing `owner/name` pair already known to Desktop's local database can end up carrying over the previously-established `GitHubRepository` identity (`endpoint`, `permissions`, `parentID`) for that owner/name, without any explicit invalidation step comparable to `removeDelegation` in the Solidity report. [5](#0-4) 

This is the same broken invariant as [H-04]: reassigning an association to a "new tokenId" (here, a new local `Repository`/remote) without clearing the corresponding old mapping entry lets two different local repositories end up sharing/inheriting one GitHub identity's cached permission and pull-request state (`branchProtectionSettingsFoundCache`, `protectionEnabledForBranchCache`, pull request store data keyed by `GitHubRepository.id`). [6](#0-5) 

### Impact Explanation
If an attacker controls a cloned/fetched repository's remote (e.g., a repository the user is asked to add/clone whose `origin` is later changed, or a fork whose owner/name string coincides with a private repo the victim already has open in Desktop), Desktop can silently carry forward a stale `GitHubRepository` association's cached `permissions` (e.g., `write`), branch-protection cache entries, and pull-request data into the attacker-influenced local repository context. This can cause Desktop to make incorrect trust decisions (e.g., suppressing branch-protection warnings, showing/using another repository's PR metadata) tied to the wrong remote — a silent corruption of the metadata Desktop uses to decide what's safe to push/commit, without any explicit re-authorization step, analogous to the voting-power inflation in the original report.

### Likelihood Explanation
Medium-to-low: it requires (1) the victim to have previously opened/associated a legitimate repository with a given `owner/name`, and (2) a different local repository's remote to be changed (by the attacker, or by the user following attacker instructions) so that `matchGitHubRepository`/`upsertGitHubRepositoryFromMatch` resolves to the same `owner/name` key on the same endpoint. The code path is reached automatically during routine repository refresh (`repositoryWithRefreshedGitHubRepository`), and the lack-of-clearing behavior is explicitly acknowledged as unresolved via the linked upstream issue, but no code in the codebase currently invalidates a stale association when a remote changes to something else, which is a distinguishing, already-known gap rather than a purely theoretical one.

### Recommendation
When re-matching a repository's GitHub association (`repositoryWithRefreshedGitHubRepository`/`matchGitHubRepository`), explicitly clear or nullify the existing `gitHubRepository` link on the local `Repository` record whenever the newly matched `owner/name/endpoint` differs from the currently stored association, instead of only overwriting it on successful match and leaving it untouched otherwise. Additionally, `upsertGitHubRepositoryFromMatch`'s reuse-by-`[ownerID+name]` lookup should be paired with verification (e.g., against `cloneURL`) before reusing a pre-existing `GitHubRepository` row's cached permissions/parent for a different local repository.

### Proof of Concept
1. Victim clones/opens repository A with remote `https://github.com/org/private-repo` and Desktop stores a `GitHubRepository` row for `org/private-repo` with `permissions: 'write'` and cached branch-protection state.
2. Victim clones a second, attacker-controlled repository B and is later induced to point its `origin` remote to a URL that parses (via `parseRemote`) to the same `owner`/`name` (`org/private-repo`) on the same GitHub endpoint (e.g., through a crafted remote alias/URL format edge case, or simply reusing the string during a "fix remote" flow).
3. On the next background refresh, `repositoryWithRefreshedGitHubRepository` → `matchGitHubRepository` matches repository B to `org/private-repo`, and `upsertGitHubRepositoryFromMatch`/`upsertGitHubRepository` reuse the existing DB row for `org/private-repo`, transferring its permissions/branch-protection cache/PR data onto repository B's context — with no step in the code that ever cleared or re-verified the prior association.   private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo
  }

  private async matchGitHubRepository(
    repository: Repository
  ): Promise<IMatchedGitHubRepository | null> {
    const gitStore = this.gitStoreCache.get(repository)

    if (!gitStore.defaultRemote) {
      await gitStore.loadRemotes()
    }

    const remote = gitStore.defaultRemote
    return remote !== null
      ? matchGitHubRepository(this.accounts, remote.url)
      : null
  }

/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

  public async upsertGitHubRepositoryFromMatch(
    match: IMatchedGitHubRepository
  ) {
    return await this.db.transaction(
      'rw',
      this.db.gitHubRepositories,
      this.db.owners,
      async () => {
        const { account } = match
        const owner = await this.putOwner(account.endpoint, match.owner)
        const existingRepo = await this.db.gitHubRepositories
          .where('[ownerID+name]')
          .equals([owner.id, match.name])
          .first()

        if (existingRepo) {
          return this.toGitHubRepository(existingRepo, owner)
        }

        const skeletonRepo: IDatabaseGitHubRepository = {
          cloneURL: null,
          htmlURL: null,
          lastPruneDate: null,
          name: match.name,
          ownerID: owner.id,
          parentID: null,
          private: null,
        }

        const id = await this.db.gitHubRepositories.put(skeletonRepo)
        return this.toGitHubRepository({ ...skeletonRepo, id }, owner, null)
      }
    )
