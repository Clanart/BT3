### Title
`_deleteBranch` deletes the local branch even when the pre-checkout to `branchToCheckout` silently fails - ([File: app/src/lib/stores/app-store.ts])

### Summary
`AppStore._deleteBranch` first checks out a fallback branch (if the branch being deleted is currently checked out) and then unconditionally deletes the local branch, regardless of whether that checkout actually succeeded.

### Finding Description
In `_deleteBranch`, when the branch to delete is the currently checked-out one, Desktop computes a `branchToCheckout` and performs the checkout wrapped in `gitStore.performFailableOperation`: [2](#0-1) 

`performFailableOperation` catches any thrown error, emits it via `this.emitError(e)`, and resolves to `undefined` instead of rejecting: [1](#0-0) 

Because the checkout call's failure is absorbed and not propagated, execution falls straight through to the very next line, which unconditionally deletes the local branch (and possibly its upstream) via a second, independent `performFailableOperation` call: [3](#0-2) 

This mirrors the Besu pattern precisely: a value/marker computed for one purpose (here, "we need to move off this branch before deleting it") is applied (the branch delete) without verifying that the precondition step it depended on (the checkout away from the branch) actually completed. If `checkoutBranch` fails (e.g., due to a hook failure, a locked index file, an assume-unchanged/skip-worktree working-tree conflict, or any other git error), Desktop still proceeds to run `git branch -D` on the branch whose HEAD you may still be sitting on, and — if `includeUpstream` is set — also deletes the corresponding remote branch, all guarded by nothing but an already-swallowed exception.

### Impact Explanation
The user only sees an error banner from the failed checkout, but the subsequent, logically-dependent branch deletion is not stopped by that failure. This can permanently delete the local branch ref (`git branch -D`, no safety check for unmerged commits since `-D` forces it) and, if the checkbox for "delete on remote" is selected, push a deletion of the upstream branch as well — all while the working directory may still reference the just-deleted branch as its current HEAD, or while local commits that only exist on that branch are still not reachable from anywhere else the user is aware of. This is a silent-corruption-of-repository-state class of bug: it removes refs the user still needs, without their subsequent action failing loudly to explain why, similar in spirit to the Besu bug leaving state inconsistent with the actual (failed) outcome of the preceding operation.

### Likelihood Explanation
The checkout-before-delete path only triggers when the branch being deleted is currently checked out, which is a common workflow (deleting your current feature branch). The checkout can plausibly fail for reasons outside the user's direct control (a `post-checkout` hook rejecting the switch, a stale lock file, concurrent git operations, or a submodule/worktree conflict), and none of those failure modes are rare edge cases requiring local/admin access — they can occur during normal use of a cloned repository with a checked-in hook or a busy `.git` directory.

### Recommendation
Make the local/upstream branch deletion in `_deleteBranch` conditional on the checkout call actually succeeding — check the return value of the `performFailableOperation(() => checkoutBranch(...))` call (or otherwise detect/rethrow failure) and abort (returning early, refreshing the repository, and surfacing the error) rather than falling through to `deleteLocalBranchAndUpstreamBranch` unconditionally.

### Proof of Concept
1. Check out branch `feature/x` which has unpushed commits.
2. Install (or have present via a cloned repository) a `post-checkout` hook that exits non-zero for a specific target branch (simulating a lock/hook failure), or otherwise arrange for `checkoutBranch` to fail (e.g., simulate a git index lock).
3. In Desktop, delete `feature/x` with "delete on remote" checked, triggering `_deleteBranch`.
4. Observe: the checkout to the fallback branch fails and is reported via `emitError`, but `deleteLocalBranchAndUpstreamBranch` still runs immediately after, permanently deleting `feature/x` locally and on the remote — even though Desktop never actually moved off of it.

**Caveat / uncertainty:** I could not fully trace whether `checkoutBranch` (the git-level function used here, not the `AppStore._checkoutBranch` workflow) throws on all realistic failure modes versus resolving successfully in some partial-failure cases, since its full implementation was not returned by search. The core structural flaw — that the delete step is not gated on the checkout step's success because `performFailableOperation` swallows failures — is confirmed directly from the code shown above.

  public async performFailableOperation<T>(
    fn: () => Promise<T>,
    errorMetadata?: IErrorMetadata
  ): Promise<T | undefined> {
    try {
      const result = await fn()
      return result
    } catch (e) {
      e = new ErrorWithMetadata(e, {
        repository: this.repository,
        ...errorMetadata,
      })

      this.emitError(e)
      return undefined
    }
  }
