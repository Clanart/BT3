### Title
`safe.directory` trust exception is never revoked when a repository is removed, allowing a later attacker-controlled directory at the same path to be silently treated as trusted - ([File: app/src/lib/git/config.ts])

### Summary
GitHub Desktop lets a user "trust" a Git working directory that Git considers unsafe (owned by a different user) by calling `addSafeDirectory`, which permanently appends the path to the global `safe.directory` Git config (`~/.gitconfig`) via `addGlobalConfigValueIfMissing`. [1](#0-0)  This trust decision is bound only to a filesystem path, not to the repository's identity/contents. When the repository is later removed from GitHub Desktop (`_removeRepository`), only the app's internal repository record is deleted — the corresponding `safe.directory` entry is never cleaned up. [2](#0-1) [3](#0-2) 

### Finding Description
This is a direct structural analog of the reported bug: an action that conceptually "revokes" a privileged state (removing/destructing a repository) fails to reset the associated trust/permission flag (the pool's `Packed3`/`claimed` fields in the report; here, the `safe.directory` git-config entry), leaving a stale privileged state reachable through a different, unprivileged path.

Concretely:
- `addSafeDirectory(path)` writes the path into `~/.gitconfig`'s `safe.directory` multi-value list. [4](#0-3) 
- The UI surfaces this trust action from `MissingRepository.onTrustDirectory` and `AddExistingRepository.onTrustDirectory` whenever `getRepositoryType` reports `kind: 'unsafe'`. [5](#0-4) [6](#0-5) 
- `getRepositoryType` classifies a directory as `unsafe` purely from Git's dubious-ownership detection for that filesystem path. [7](#0-6) 
- There is no code path anywhere in the codebase that removes/unsets a `safe.directory` entry — a repo-wide search for `removeSafeDirectory`/`unset ... safe` finds nothing. Repository removal (`_removeRepository` → `repositoriesStore.removeRepository`) only deletes the DB row and clears push-tag bookkeeping; it never touches Git's global config. [2](#0-1) [3](#0-2) 

Because `safe.directory` entries are keyed by path (not by repo identity, owner, or content hash), once a path has been trusted it stays trusted forever — even after the user removes that repository from Desktop, deletes the directory, and a completely different, attacker-controlled repository later ends up at the identical path (e.g., re-cloning a different/malicious remote to the same local path, restoring from a backup, or an attacker planting a directory at a well-known path used by shared/mounted storage). Git will no longer warn about dubious ownership for that path, and Desktop's "unsafe" gate (`getRepositoryType` returning `unsafe`) is silently bypassed for the new, untrusted content — exactly like the smart-contract analog where destroying the pool without resetting `Packed3`/`claimed` leaves `claim()` reachable against a state that should be considered closed.

### Impact Explanation
Git's own unsafe-directory protection exists specifically to prevent automatic execution of repository-controlled configuration (e.g. `core.fsmonitor`, hooks configured via local `.git/config`) when a directory is owned by another user — i.e., it is a code-execution guard. A stale `safe.directory` allow-list entry silently disables that guard for any future content placed at the previously-trusted path, without any indication to the user that trust was ever granted or that it is still in effect. This can lead to automatic execution of attacker-supplied Git hooks/config the moment Desktop (or the user's shell operating through the same environment) interacts with the new repository at that path, satisfying the "unprivileged attacker controls a repository object" and "code execution outside expected trust boundary" impact criteria.

### Likelihood Explanation
Exploitation requires: (1) the user previously trusted a directory that Git considered unsafe, and (2) that same path later hosts different, attacker-influenced content (shared drives, network paths, restored VM/container images, or reused temp/mount points are realistic scenarios where path reuse with different ownership happens). Desktop explicitly supports and calls out trusting "network shares" (see changelog entries referencing UNC path support for `safe.directory`), which increases the realism of path reuse across different content/owners. [8](#0-7)  The bug is entirely silent — there is no revocation UI, no reminder, and no automatic invalidation on repository removal — so likelihood of an unaware, long-lived stale trust entry is high once the initial trust decision has ever been made.

### Recommendation
When a repository is removed via `_removeRepository` (and/or when its path changes via `_relocateRepository`/`updateRepositoryPath`), remove the corresponding `safe.directory` entry from the global Git config if Desktop was the one that added it, or at minimum warn the user that the trust exception for that path will persist. Consider tracking which `safe.directory` entries were added by Desktop (vs. pre-existing user config) so cleanup doesn't remove entries the user configured independently, and re-validate directory ownership/identity before reusing a previously-trusted path.

### Proof of Concept
1. Clone/add a repository at path `P` that Git reports as `unsafe` (different-owner directory, e.g. a network share or restored backup).
2. In Desktop, click "Trust Repository" — this calls `addSafeDirectory(P)`, which persists `P` into `~/.gitconfig`'s `safe.directory` list. [4](#0-3) 
3. Remove the repository from Desktop (`Remove` in the repository list) — `_removeRepository` deletes only the app-level record; `safe.directory=P` remains in `~/.gitconfig`. [2](#0-1) 
4. Delete directory `P` and have a different/attacker-controlled repository (with malicious local `.git/config` or hook-triggering content, owned by another user) placed at the same path `P`.
5. Add/open this new repository in Desktop. `getRepositoryType(P)` no longer reports `unsafe` because Git consults the now-stale `safe.directory=P` entry, so Desktop's unsafe-directory warning and trust gate never trigger for the new, attacker-controlled content. [7](#0-6)

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}

/** Set the global config value by name. */
export async function addGlobalConfigValueIfMissing(
  name: string,
  value: string
): Promise<void> {
  const { stdout, exitCode } = await git(
    ['config', '--global', '-z', '--get-all', name, value],
    __dirname,
    'addGlobalConfigValue',
    { successExitCodes: new Set([0, 1]) }
  )

  if (exitCode === 1 || !stdout.split('\0').includes(value)) {
    await addGlobalConfigValue(name, value)
  }
}
