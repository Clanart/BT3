### Title
`withdraw()` in IntentGatewayV2 trusts the message-supplied token amount instead of validating it against the recorded escrow balance - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The internal `withdraw()` function that pays out escrowed order funds on `RedeemEscrow`/`RefundEscrow` only checks that an escrow entry is *non-zero*, never that the amount being paid out actually equals (or is bounded by) the amount recorded in `_orders[commitment][token]`. This is the same class of bug as the external report: a withdrawal path decrements/uses one accounting value without reconciling it against the authoritative recorded balance for that entry, breaking the invariant that "amount transferred == amount tracked as escrowed."

### Finding Description
`withdraw()` is the internal handler invoked from `onAccept()` for `RequestKind.RedeemEscrow` / `RequestKind.RefundEscrow`, and from `cancelOrder()`'s same-chain path: [1](#0-0) 

The only guard against paying out an amount that doesn't match what was actually escrowed is:
```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
```
This is purely an existence check. It never verifies `amount == _orders[body.commitment][token]` (or `amount <= _orders[...]`) before transferring `amount` to `beneficiary` and only *afterwards* does:
```solidity
_orders[body.commitment][token] -= amount;
```
For the trusted, same-chain `cancelOrder()` path the `amount` is always `order.inputs[i].amount`, which is bound to the escrow because the commitment is `keccak256(abi.encode(order))`. But for the cross-chain `RedeemEscrow`/`RefundEscrow` path, `body` (including `tokens[].amount`) is decoded directly from an inbound ISMP `PostRequest.body` originating from the counterpart `IntentGatewayV2` instance on another chain: [2](#0-1) 

`authenticate()` only checks that `request.from` matches the registered instance address for `request.source`; it never checks that the `WithdrawalRequest.tokens[].amount` values match the original `Order.inputs` recorded for that `commitment`: [3](#0-2) 

This is structurally the same broken-invariant pattern from the Aries report: the function mutates the accounting field (`_orders[...] -= amount`) using a value (`amount`) that is not independently reconciled against the field it is supposed to be consistent with, instead of asserting equality/consistency the way `check_stats_integrity` demanded in the original bug.

### Impact Explanation
If the amount encoded in the inbound `WithdrawalRequest` for a `RedeemEscrow`/`RefundEscrow` request can ever diverge from the escrow actually recorded under that commitment — whether through a bug/compromise in the destination-side fill/cancel dispatch logic, or any code path that constructs this body independent of the original `Order.inputs` — `withdraw()` will pay out that unchecked amount and silently desynchronize `_orders[commitment][token]` from the physical token balance actually owed, rather than reverting on a mismatch. This falls squarely under "wrong beneficiary or amount" / "unauthorized transaction manipulation" in the impact gate: escrowed bridge funds could be paid out in an amount that does not match what was actually escrowed for that order.

### Likelihood Explanation
I was not able to fully trace, within this session's tool budget, whether the destination-chain fill logic that constructs the `RedeemEscrow` `WithdrawalRequest.tokens[].amount` is unconditionally bound to `order.inputs` at dispatch time (i.e., whether the amount field is attacker-influenceable anywhere along that path). The code fact that is verified is that `withdraw()` itself performs no defense-in-depth check tying `amount` to the recorded `_orders` value — it relies entirely on upstream code elsewhere in the system (destination-chain solve/fill logic) getting the amount right, with no on-chain assertion here. This absence of a local invariant check is what makes this analogous to the reserve report: correctness depends on an implicit, unenforced assumption rather than an explicit check.

### Recommendation
In `withdraw()`, before transferring funds, assert that the message-supplied amount matches (or is capped by) the recorded escrow:
```solidity
uint256 owed = _orders[body.commitment][token];
if (owed == 0) revert UnknownOrder();
if (amount > owed) revert InvalidInput(); // or require amount == owed for exact-settlement semantics
_orders[body.commitment][token] = owed - amount;
```
placed before the token transfer, so the accounting state can never diverge from the physical payout, matching the same fix pattern the Aries report used (reconcile the aggregate/tracked value with the actual transferred amount at the point of withdrawal, not after the fact).

### Proof of Concept
Not independently reproducible from the code inspected in this session — full confirmation requires tracing the destination-chain `fill()`/`solve()` dispatch logic that produces the `RedeemEscrow` `WithdrawalRequest` body to determine whether its `tokens[].amount` can ever be set independently of the original `Order.inputs`. This is flagged as an unverified assumption; the concrete, verifiable defect is the missing amount-equality assertion in `withdraw()` itself, shown in the cited lines above.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
