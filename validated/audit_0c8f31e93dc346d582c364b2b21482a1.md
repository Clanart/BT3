Based on the evidence gathered, the strongest analog is in the "Open in Desktop" deep-link handler, which performs a network fetch and a branch checkout on an attacker-chosen branch name entirely automatically once a user clicks a crafted `x-github-client://openRepo/...` link — with no confirmation dialog gating the repository-selection/fetch/checkout sequence itself.

### Title
Deep-link `openRepo` action silently fetches and checks out an attacker-chosen branch without user confirmation - (File: `app/src/ui/dispatcher/dispatcher.ts`)

### Summary
The custom protocol handler for `x-github-client://openRepo/...` (and legacy `github-mac`/`github-windows` aliases) parses an attacker-supplied `url` and optional `branch` query parameter [1](#0-0) , and when the app processes it, `openBranchNameFromUrl` will select the matching existing local repository, run `git fetch` against its remote, and immediately check out the attacker-specified branch name — all without ever asking the user whether they want to leave their current branch or that a fetch/checkout is about to happen [2](#0-1) .

### Finding Description
`parseAppURL` validates only that the branch value doesn't contain "invalid ref characters" [3](#0-2)  — it does not require any user confirmation semantics, it's purely a syntactic check. The resulting `IOpenRepositoryFromURLAction` is dispatched straight to `dispatchURLAction`, which routes it to `openRepositoryFromUrl` with no confirmation step before acting [4](#0-3) .

If the repository referenced by `url` already matches one of the user's existing repositories (matched only by comparing remote URLs, see `doesRepositoryMatchUrl`), `openOrCloneRepository` calls `selectRepository` directly — bypassing the "Clone Repository" popup path that is shown only for repos that aren't already present locally [5](#0-4) . Immediately afterward, `openBranchNameFromUrl` runs `_refreshRepository`, then `_fetch` against the remote, then `checkoutLocalBranch` for the attacker-supplied branch name [2](#0-1) . `checkoutLocalBranch` calls `checkoutBranch` with no explicit strategy [6](#0-5) , meaning `_checkoutBranch` falls back to the user's configured `uncommittedChangesStrategy` [7](#0-6) .

The default preference is `AskForConfirmation`, which does gate on `hasChanges` before proceeding [8](#0-7) [9](#0-8) , so for a user with a dirty working directory on the default setting, an explicit dialog does appear before the checkout proceeds. However, for any user who has changed this preference to "Always stash and leave changes" or "Always bring changes to new branch" (both are supported, documented options in Preferences → Prompts [10](#0-9) ), the checkout proceeds immediately and silently, stashing/moving whatever the user was working on, switching HEAD to an attacker-named branch, and pulling data from the network — purely as a result of the user clicking a link on a web page. Even when there are no local changes on the current branch, the fetch + branch switch itself still happens with zero UI confirmation regardless of the preference, since the `hasChanges` gate is the only check that produces a popup.

### Impact Explanation
An attacker who controls a web page (or any clickable surface capable of emitting an `x-github-client://openRepo/...` URI) can force GitHub Desktop to silently: (1) select a specific already-cloned repository the victim has open, (2) initiate a `git fetch` against its configured remote, and (3) switch the working tree to a branch name of the attacker's choosing, without the victim ever intending to switch branches inside the app. Depending on the victim's uncommitted-changes preference, this can silently stash or carry forward in-progress work onto an unintended branch, and it always changes what's checked out in the working directory without a distinct "an external link wants to open/switch this repository" confirmation prompt. If the target repository has any automation that reacts to branch checkouts (editor auto-run tasks, watch/build scripts, git hooks tied to checkout), this provides a path from "user clicks a link" to code execution in the context of the repository.

### Likelihood Explanation
Exploitation requires only that the victim already has the targeted repository cloned/added in Desktop and clicks a link with a `openRepo` scheme pointing at a branch name — a scenario squarely within the "link/deep link the user clicks" and "git remote response" attacker model. It does not require local/physical access, admin rights, or pre-existing malware. The severity is reduced by the fact that the checkout still requires an existing local branch of the given name (`checkoutLocalBranch` only proceeds if `branches.find(b => b.nameWithoutRemote === branch)` matches) [11](#0-10) , and full silent data loss depends on the victim having opted out of the default `AskForConfirmation` setting.

### Recommendation
Require an explicit, dedicated confirmation dialog before acting on any `open-repository-from-url` action that results in a fetch and/or branch checkout for an *existing* repository, independent of the user's uncommitted-changes-strategy preference, so that URL-triggered navigation is always distinguishable from an intentional in-app branch switch. Consider also validating that the branch parameter corresponds to a branch that is verifiably associated with the specified `url`/remote before checking it out.

### Proof of Concept
1. Victim has previously added/cloned a GitHub repository, e.g. `https://github.com/acme/webapp`, and has a local branch named `hotfix` from prior work, with Desktop's uncommitted-changes preference set to "Always bring my changes to my new branch" or "Always stash…" (a supported, documented setting).
2. Attacker hosts a page (or sends a chat/email link) containing:
   `<a href="x-github-client://openRepo/https://github.com/acme/webapp?branch=hotfix">Open in Desktop</a>`
3. Victim clicks the link. The OS invokes the registered protocol handler, which calls `handleAppURL` → `parseAppURL` → dispatched as `open-repository-from-url` [12](#0-11) .
4. `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl` matches the existing repository, runs `_fetch`, and calls `checkoutLocalBranch('hotfix')` [2](#0-1) .
5. Because the strategy is not `AskForConfirmation`, `_checkoutBranch` proceeds directly to `checkoutImplementation`, stashing or moving the victim's current uncommitted work and switching HEAD to `hotfix` [13](#0-12)  — with no dialog ever shown indicating this was triggered by an external link.

(Note: I was unable to fully verify, in the time available, whether the sibling `openPullRequestFromUrl`/`_checkoutPullRequest` path — which creates a new branch from a PR ref rather than switching to an existing local branch — has additional or fewer safeguards; that path may represent an even stronger variant of this issue and would benefit from separate review.)

function handleAppURL(url: string) {
  log.info('Processing protocol url')

  })
