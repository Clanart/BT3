### Title
Dividend/reward sniping via `queueNewRewards` frontrunning in `BaseRewardPool` (and its variants) - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool` (and the analogous `BaseRewardPoolV2`, `vlMGPBaseRewarder`, `mWOMSVBaseRewarder`) globally updates `rewardPerTokenStored` the instant new rewards are queued, based only on the `totalStaked()` snapshot at that block, with no warmup, vesting, or minimum holding period. Any unprivileged wallet can watch the public mempool for a pending `queueNewRewards` call (triggered permissionlessly by `WombatBribeManager.castVotes`/`harvestSinglePool` → `WombatStaking.vote`/`_sendRewards` → `IBaseRewardPool.queueNewRewards`), front-run it with a large `MasterMagpie.deposit`, let the reward-injection transaction execute, and immediately back-run it with `MasterMagpie.withdraw` to capture a disproportionate share of the newly queued rewards without ever meaningfully holding the staking position.

### Finding Description
`_provisionReward` in `BaseRewardPool` increases `rewardPerTokenStored` proportionally to `totalStaked()` measured at the exact moment the reward is provisioned: [1](#0-0) 

`earned()`/`rewardPerToken()` then computes a user's share purely from `balanceOf(_account)` at the time `_updateFor` is invoked (on deposit/withdraw/getReward), with no time-weighting, snapshotting, or lock: [2](#0-1) 

Reward injections into these pools are triggered by economically-unprivileged, publicly callable paths. `WombatBribeManager.castVotes` is `public` (any wallet can call it, and callers even receive a fee for doing so) and pushes bribes to `wombatStaking.vote`, which calls `IBaseRewardPool(_rewarders[i]).queueNewRewards(...)`: [3](#0-2) [4](#0-3) 

`WombatStaking._sendRewards` (used for WOM emission harvesting) also calls `queueNewRewards` on the target rewarder: [5](#0-4) 

Because these reward-injecting transactions are visible in the mempool before execution, and `MasterMagpie.deposit`/`withdraw` are unprivileged, un-cooldowned, fee-free operations available to any wallet: [6](#0-5) [7](#0-6) 

an attacker can sandwich the reward-injection call: deposit right before it lands, then withdraw right after `_harvestBaseRewarder`/`getReward` credits the pro-rata share, extracting reward tokens that should have accrued to genuine long-term stakers. This is the direct analog of the reported `distributeDividends` sniping bug class, mapped onto Magpie's `BaseRewardPool` reward-per-share accounting instead of a token's dividend distributor.

### Impact Explanation
This constitutes theft of unclaimed yield from legitimate long-term stakers: an attacker with sufficient capital can capture a share of a reward distribution proportional to a deposit held for only the duration of one or two blocks, diluting the rewards that should accrue to users who were staked for the entire period. Because the reward pools distribute real value (WOM, MGP, bribe tokens, mWOM), this is a direct value transfer from honest stakers to the attacker with no counterparty compensation, satisfying the "theft or permanent freezing of unclaimed yield" impact category. The Bridges Team's original resolution (this requires costly swaps/LP actions and is thus unlikely) does not apply here: the analog attack path requires no DEX swaps or LP provisioning at all — it is a plain `deposit` → (reward auto-injected by any wallet calling `castVotes`) → `withdraw` sequence directly against `MasterMagpie`/`BaseRewardPool`, making it materially cheaper (gas-only) than the case the team dismissed.

### Likelihood Explanation
Reward injections (`castVotes`, WOM harvests forwarded via `_sendRewards`) are permissionless and routinely called by third parties/keepers for the caller fee, so pending reward-injection transactions are frequently visible in the mempool. `deposit`/`withdraw` on `MasterMagpie` carry no cooldown, lock, or fee that would deter same-block or adjacent-block sandwiching, and MEV searchers can automate front-run/back-run bundles around any observed `castVotes`/harvest transaction. This is a low-cost, high-frequency-opportunity attack for any capital-holding wallet, and is more practical than the token-swap-based scenario the team previously evaluated.

### Recommendation
Introduce a minimum holding/warmup period before a deposit becomes eligible for a given reward-per-share checkpoint (e.g., snapshot-based accrual, or requiring stake to be held across the block in which `queueNewRewards` executes), or apply a time-weighted average balance for reward accrual instead of instantaneous `balanceOf`. Alternatively, add a short withdrawal cooldown/lock in `MasterMagpie` so that deposit-then-immediate-withdraw sandwiching cannot capture freshly queued rewards.

### Proof of Concept
1. Attacker monitors the mempool for a `WombatBribeManager.castVotes(...)` (or any transaction that ultimately calls `WombatStaking._sendRewards`/`vote`, which calls `IBaseRewardPool.queueNewRewards`) targeting pool `P` with rewarder `R`.
2. Attacker front-runs with `MasterMagpie.deposit(stakingTokenOfP, largeAmount)`, becoming a large fraction of `totalStaked()` for `R` an instant before the reward injection.
3. The victim's `castVotes`/harvest transaction executes, calling `R.queueNewRewards(amountReward, rewardToken)`, which raises `rewards[rewardToken].rewardPerTokenStored` based on the now-inflated `totalStaked()` that includes the attacker's fresh deposit — [1](#0-0) .
4. Attacker immediately back-runs with `MasterMagpie.withdraw(stakingTokenOfP, largeAmount)`, which internally calls `_harvestBaseRewarder`/`getReward`, crediting the attacker `balanceOf(_account) * (rewardPerToken - userRewardPerTokenPaid) / 10**stakingDecimals` — [2](#0-1)  — capturing a disproportionate share of the just-queued reward, then exits the position entirely.
5. Net effect: attacker earns reward tokens for holding stake across essentially zero economic time, diluting the share that accrues to genuine long-term stakers of pool `P`.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
