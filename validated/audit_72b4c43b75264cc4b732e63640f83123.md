### Title
Unauthenticated `ReceivedOutput` deserialization fabricates spendable Bitcoin inputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

`ReceivedOutput::read` allows arbitrary bytes to instantiate a private-field `ReceivedOutput` containing a caller-selected scalar offset, `TxOut`, and `OutPoint`. Unlike `Scanner::scan_transaction`, it performs no proof that the referenced Bitcoin output exists, belongs to the scanner, or is spendable.

This is analogous to unrestricted minting: an untrusted input can create a supposedly spendable balance entry without passing through the authorized discovery path.

### Finding Description

`ReceivedOutput` represents “a spendable output” and stores:

- `offset`: the scalar needed to derive the spending key
- `output`: the claimed Bitcoin output
- `outpoint`: the claimed transaction output location

Its constructor fields are private. The legitimate producer is `Scanner::scan_transaction`, which only creates an object after matching `output.script_pubkey` against a registered scanner script.

However, `ReceivedOutput::read` accepts serialized scalar, `TxOut`, and `OutPoint` fields directly and returns the object without authenticating the claimed outpoint against the Bitcoin chain:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)?;
outpoint = OutPoint::consensus_decode(&mut buf_r)?;
Ok(ReceivedOutput { offset, output, outpoint })
```

`SignableTransaction::new` then sums `input.output.value` as available funds and stores each `input.output` as a prevout. `SignableTransaction::multisig` verifies only that applying the serialized offset to the threshold keys produces the serialized output’s `script_pubkey`.

An attacker who knows the wallet’s public group key can derive its base P2TR script, choose `offset = 0`, and serialize a fake high-value `TxOut` with an arbitrary nonexistent `OutPoint`. The resulting object is indistinguishable to downstream transaction-building code from one produced by `Scanner`.

### Impact Explanation

The application can report or consume funds that were never received and cannot be spent.

A forged serialized `ReceivedOutput` can:

1. Inflate the wallet’s perceived received balance.
2. Cause `SignableTransaction::new` to accept payments based on nonexistent value.
3. Pass `SignableTransaction::multisig` because the fake output uses the wallet’s real script.
4. Cause threshold signers to sign a transaction spending a nonexistent UTXO.

The signed transaction will be rejected by Bitcoin consensus, but the wallet has already classified attacker-controlled bytes as spendable funds. This maps to the report’s unauthorized supply mutation because bytes outside the authorized scanner path create an asset-like input object that changes the value available to downstream logic.

### Likelihood Explanation

An unprivileged party only needs the victim’s public P2TR script or group key and the ability to supply serialized `ReceivedOutput` data to code that persists, synchronizes, imports, or otherwise accepts untrusted `ReceivedOutput` encodings.

No private key, validator privilege, malformed curve point, or hash collision is required. The attacker does not need to make the referenced Bitcoin transaction exist.

Likelihood is bounded by deployments treating `ReceivedOutput` serialization as an authenticated internal database format rather than untrusted input. When that assumption is absent, this path is directly reachable.

### Recommendation

Prevent unauthenticated bytes from constructing claimed spendable outputs.

Possible mitigations:

- Restrict `ReceivedOutput::read` to trusted internal storage and expose a separate untrusted-input parser that revalidates the outpoint against the chain.
- Add an authenticated representation binding the `offset`, full `TxOut`, and `OutPoint` to trusted wallet state.
- Before accepting a deserialized output, verify through Bitcoin RPC or an authenticated UTXO index that:
  - the `OutPoint` exists,
  - it is unspent,
  - its `TxOut` exactly matches the serialized output,
  - it has sufficient confirmations/maturity.
- Prefer retaining enough scanner context to prove the output came from `Scanner::scan_transaction` or `Scanner::scan_block`.

### Proof of Concept

The following demonstrates the root cause without requiring the fake outpoint to exist on-chain:

```rust
use std::io;

use bitcoin::{
  consensus::encode::serialize,
  Amount, OutPoint, TxOut, Txid,
};
use bitcoin::hashes::Hash;

use k256::Scalar;
use bitcoin_serai::wallet::{p2tr_script_buf, ReceivedOutput};

fn forged_received_output(
  group_key: k256::ProjectivePoint,
) -> io::Result<ReceivedOutput> {
  let mut bytes = Vec::new();

  // Base-key outputs use offset zero.
  bytes.extend_from_slice(&Scalar::ZERO.to_bytes());

  // Claim a large output controlled by the victim wallet.
  let fake_output = TxOut {
    value: Amount::from_sat(100_000_000),
    script_pubkey: p2tr_script_buf(group_key).unwrap(),
  };
  bytes.extend_from_slice(&serialize(&fake_output));

  // Reference a transaction output which was never created.
  let fake_outpoint = OutPoint {
    txid: Txid::from_byte_array([0x41; 32]),
    vout: 0,
  };
  bytes.extend_from_slice(&serialize(&fake_outpoint));

  ReceivedOutput::read(&mut bytes.as_slice())
}
```

For the victim’s base P2TR output, this passes the later key-binding check in `SignableTransaction::multisig` because:

```rust
keys.clone().offset(Scalar::ZERO).group_key()
```

maps to the same `script_pubkey` selected by the attacker. `SignableTransaction::new` consequently treats the fake `TxOut` value as available input value, despite the referenced `OutPoint` not existing.
