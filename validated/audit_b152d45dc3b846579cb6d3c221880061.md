### Title
Unauthenticated OP_RETURN operator identity in `payout_tx` allows anyone to hijack/frame the "who fronted the withdrawal" attribution - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` builds the `payout_tx` with the user's withdrawal signature covering only input 0 / output 0 via key-path spend (SIGHASH `SinglePlusAnyoneCanPay`), but the third output — the `OP_RETURN` that records `operator_xonly_pk`, i.e. *who is credited with fronting the withdrawal* — is completely unsigned and unauthenticated. Because the signature type is `SIGHASH_SINGLE | ANYONECANPAY`, any party can take the publicly-broadcast/mempool-visible partially-spending transaction (or reconstruct it from the same user signature), add their own funding inputs, and replace the `OP_RETURN` payload with an arbitrary `operator_xonly_pk` before it confirms. This is the same bug class as the reported `replayMessage`/`dropMessage` front-running: an unprivileged party can front-run the intended actor's transaction and substitute themselves (or a third party) into a binding that should only be settable by whoever actually paid.

### Finding Description
`create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) constructs the payout transaction as:
- Input 0: the withdrawal UTXO, spent with the user's Schnorr signature using key-path spend.
- Output 0: user payout.
- Output 1: anchor.
- Output 2: `op_return_txout(operator_xonly_pk)` — records which operator "fronts" the peg-out.

The user's `taproot::Signature` is applied with `set_p2tr_key_spend_witness(&user_sig, 0)` [1](#0-0)  and verified against `SinglePlusAnyoneCanPay`, explicitly documented and enforced in `Operator::withdraw`: `"Ensure the signature uses SinglePlusAnyoneCanPay sighash type."` [2](#0-1) . By definition of `SIGHASH_SINGLE | ANYONECANPAY`, this signature only commits to input 0 and output 0 — it places **no constraint** on any other input or output, including the `OP_RETURN` (output 2) that names the operator. The transaction is subsequently funded with `fund_raw_transaction(..., add_inputs: Some(true), ...)` [3](#0-2) , meaning whoever supplies the additional funding input can also freely control that unsigned `OP_RETURN` output.

Downstream, the recorded `operator_xonly_pk` from this unauthenticated `OP_RETURN` field is the *sole* source of truth for which operator is deemed to have "fronted" the withdrawal:
- `update_finalized_payouts` parses the `OP_RETURN` from the confirmed payout tx and writes it straight into `payout_payer_operator_xonly_pk` in the DB with no cross-check against who actually funded the transaction: [4](#0-3) .
- `PayoutCheckerTask` looks up "unhandled payouts" strictly by `payout_payer_operator_xonly_pk == self.operator.signer.xonly_public_key` [5](#0-4)  and immediately drives that operator into `handle_finalized_payout`, allocating a kickoff connector to reimburse this specific operator: [6](#0-5) .
- `validate_payer_is_operator` / `get_reimbursement_txs` similarly trust the DB-recorded payer pubkey unconditionally: [7](#0-6) .
- `is_kickoff_malicious` in the verifier treats a mismatch between the recorded payer and the kickoff's `operator_xonly_pk` as evidence of malice, and treats a *matching* payer field as legitimate proof of payout with no further verification of actual funding: [8](#0-7) .

Because the `OP_RETURN` binding "operator credited" ↔ "party that paid" is not cryptographically enforced by the withdrawal signature, an unprivileged attacker who observes the legitimate operator's unconfirmed `payout_tx` in the mempool (it is broadcast via `send_raw_transaction`/RBF machinery, e.g. `crates/clementine-tx-sender/src/rbf.rs`) can construct a conflicting transaction that:
1. Reuses the same user-signed input 0 and output 0 (still valid, since the signature only commits to those).
2. Substitutes its own funding input(s) to cover the payout amount.
3. Rewrites output 2's `OP_RETURN` to name a **different** `operator_xonly_pk` — e.g. an honest operator who never authorized or intended to front this withdrawal.

If this front-running transaction confirms first (a normal mempool race/RBF outbid, not requiring any privileged role), the honest, framed operator is now marked in the DB as the payer for a withdrawal they never funded. This directly breaks the "operator credited" == "party that paid" invariant.

### Impact Explanation
Once a framed operator's `xonly_pk` is written to `payout_payer_operator_xonly_pk`, the protocol's automated `PayoutCheckerTask` and kickoff/reimbursement machinery treat that operator as obligated to go through the kickoff/challenge/reimbursement cycle for a withdrawal it never paid:
- If reimbursement is completed, the framed operator is "reimbursed for a payout it never funded" (an explicit listed Critical impact) — the vault UTXO's bridge-amount output goes to that operator via `create_reimburse_txhandler`'s `operator_reimbursement_address` [9](#0-8) , essentially a duplicated/misattributed reimbursement not paid for by that operator's own funds.
- Alternatively, if the framed operator is unaware of this spurious assignment (their automation only watches for their own `xonly_pk`) and fails to act within the protocol's kickoff deadlines, the round state machine's `KickoffNotFinalized`/unused-kickoff-burn logic can burn that operator's collateral, matching the Critical impact "an honest operator's collateral burned" [10](#0-9) .

Either outcome is a genuine custody/attribution binding violation: "the operator credited" no longer equals "the party that paid," and it is entirely achievable by an unprivileged attacker with mempool visibility and enough funds to cover one withdrawal's fee/funding, mirroring the front-running class described in the external report.

### Likelihood Explanation
The attack requires only: (1) visibility into the unconfirmed `payout_tx` (a normal, publicly broadcast Bitcoin transaction, not a privileged gRPC call — the SIGHASH type is explicitly designed to be completed by third parties), and (2) sufficient capital to front the withdrawal amount plus fees, and (3) winning a standard mempool fee race/RBF, which is routine on Bitcoin. No verifier, aggregator, or operator credentials, and no misconfiguration, are required — this is inherent to how `SinglePlusAnyoneCanPay` and the unsigned `OP_RETURN` output are combined.

### Recommendation
Bind the `operator_xonly_pk` `OP_RETURN` output to the same signature that authorizes the withdrawal, or otherwise authenticate it: e.g., require the funding operator to also provide a signature (or use `SIGHASH_ALL`/`SIGHASH_SINGLE` without `ANYONECANPAY` for a dedicated "attribution" input) that commits to the `OP_RETURN` payload, so the credited `operator_xonly_pk` cannot be rewritten independently of who actually supplies the funding inputs. Alternatively, cross-check on-chain, at `update_finalized_payouts` time, that the wallet/UTXO(s) funding the extra payout inputs are provably controlled by the named `operator_xonly_pk` before recording `payout_payer_operator_xonly_pk`.

### Proof of Concept
1. Operator O broadcasts (via RBF, non-final) a `payout_tx` spending the user's withdrawal UTXO with a valid `SinglePlusAnyoneCanPay` signature, output 0 = user payout, output 2 = `OP_RETURN(O.xonly_pk)`.
2. Attacker A observes this transaction in the mempool.
3. A constructs a new transaction reusing input 0 (with O's/user's unchanged witness for that input, still valid because the sighash only committed to input 0/output 0) and output 0 unchanged, but substitutes A's own additional funding input(s) and rewrites output 2 to `OP_RETURN(V.xonly_pk)` where V is a victim honest operator.
4. A broadcasts this with a higher fee (RBF) so it replaces O's transaction and confirms first.
5. `update_finalized_payouts` parses `OP_RETURN` from the now-confirmed tx and records `payout_payer_operator_xonly_pk = V.xonly_pk` in the `withdrawals` table.
6. V's `PayoutCheckerTask` (unaware it never paid) is triggered to allocate a kickoff for a payout it did not make, exposing V to either being wrongly reimbursed (misattributed credit) or missing the kickoff deadline and having its collateral burned via the unspent-kickoff-connector burn path.

/// 1. KickoffTx: KickoffFinalizer utxo
/// 2. ReadyToReimburseTx: BurnConnector utxo
///
/// # Outputs
/// 1. Anchor output for CPFP
///
/// # Arguments
/// * `kickoff_txhandler` - The kickoff transaction handler providing the input.
/// * `ready_to_reimburse_txhandler` - The ready-to-reimburse transaction handler providing the input.

/// # Returns

    paramset: &'static ProtocolParamset,

    Ok(TxHandlerBuilder::new(TransactionType::KickoffNotFinalized)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::KickoffNotFinalized1,
            kickoff_txhandler.get_spendable_output(UtxoVout::KickoffFinalizer)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,

            builder::script::SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(UnspentTxOut::from_partial(
            builder::transaction::anchor_output(paramset.anchor_amount()),
        ))
        .finalize())
}

pub fn create_reimburse_txhandler(
    move_txhandler: &TxHandler,
    round_txhandler: &TxHandler,
    kickoff_txhandler: &TxHandler,
    kickoff_idx: usize,
    paramset: &'static ProtocolParamset,
    operator_reimbursement_address: &bitcoin::Address,
) -> Result<TxHandler, BridgeError> {
    let builder = TxHandlerBuilder::new(TransactionType::Reimburse)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::Reimburse1,
            move_txhandler.get_spendable_output(UtxoVout::DepositInMove)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::Reimburse2,
            kickoff_txhandler.get_spendable_output(UtxoVout::ReimburseInKickoff)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::OperatorSighashDefault,
            round_txhandler.get_spendable_output(UtxoVout::ReimburseInRound(
                kickoff_idx,
                paramset.num_kickoffs_per_round,
            ))?,
            builder::script::SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        );

    Ok(builder
        .add_output(UnspentTxOut::from_partial(TxOut {
            value: move_txhandler
                .get_spendable_output(UtxoVout::DepositInMove)?
                .get_prevout()
                .value,
            script_pubkey: operator_reimbursement_address.script_pubkey(),
        }))
        .add_output(UnspentTxOut::from_partial(
            builder::transaction::anchor_output(paramset.anchor_amount()),
        ))
        .finalize())
