### Title
`ThresholdKeys::read`/`ThresholdKeys::new` accept attacker-inconsistent `secret_share`/`verification_shares`, causing valid shares to be blamed as invalid - (File: crypto/dkg/src/lib.rs)

### Summary

`ThresholdKeys::read` deserializes `secret_share` and a `verification_shares` map entirely from untrusted bytes and `ThresholdKeys::new` performs structural checks only — count matches `n`, indices ≤ `n`, interpolation form — but never verifies the fundamental consistency invariant `C::generator() * secret_share == verification_shares[params.i()]`, nor that the map forms any consistent polynomial. The group key is derived only from shares `1..=t`. Like pg_basebackup letting an origin write attacker-chosen content into files later trusted by the server, this lets untrusted bytes silently overwrite unrelated verification shares that downstream signing code trusts for blame.

### Finding Description

In `ThresholdKeys::read`, `t`, `n`, `i`, the interpolation blob, `secret_share`, and all `n` `verification_shares` come straight from the reader; `ThresholdKeys::new` then validates only cardinality and bounds [1](#0-0) . It never checks the secret share against its own verification share, nor checks shares `t+1..=n` against anything.

During `complete()`, honest peers' shares are verified against `self.view.verification_share(l)`, which is built from this map [2](#0-1) . `ThresholdView::verification_share` indexes the deserialized map directly [3](#0-2) . The code itself acknowledges this hole: the fallback error in `complete()` says "The only known way to cause this ... is to deserialize a semantically invalid FrostKeys" [4](#0-3) .

### Impact Explanation

If attacker-crafted bytes reach `ThresholdKeys::read` (key blob restored from an untrusted store/backup or supplied in place of genuine key material — the stated reachable surface), the victim can be made to report `FrostError::InvalidShare(l)` for an *honest* signer `l`, because `l`'s correct share is checked against a corrupted `verification_shares[l]` and fails `verify_share`/batch verification. In the processor this error path maps to blaming/slashing the accused validator, corrupting an honest party's standing — an integrity violation produced purely by deserialization, with no opportunity for the honest party to defend itself.

### Likelihood Explanation

Requires attacker influence over the serialized `ThresholdKeys` consumed by a validator (e.g., untrusted key material/backup or any path feeding external bytes to `read`), plus participation in a signing round with the targeted honest signer. No cryptographic break or collusion is needed; the missing consistency check does all the work. Medium likelihood, Medium-High impact (erroneous blame of honest validators).

### Recommendation

In `ThresholdKeys::new`, verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise. For Lagrange interpolation, additionally verify the map's internal consistency where feasible (e.g., reconstructed verification share for `i` equals `generator * secret_share`, and all shares lie on a degree-`t-1` polynomial via a randomized check), so no share can be silently corrupted relative to the rest.

### Proof of Concept

```rust
// For any Curve C and params (t=2, n=3, i=1):
// 1) Take a valid serialized ThresholdKeys blob produced by dkg::key_gen.
// 2) Corrupt the encoded verification_share for Participant(2)
//    (e.g., replace with C::generator() * random scalar) — read() accepts it:
let keys = ThresholdKeys::<C>::read(&mut crafted.as_ref()).unwrap();
// group_key is derived only from shares 1..=t, so a corruption of share 3
// is invisible even to group_key(); a corruption of share 2 changes nothing
// structurally either since no consistency check exists.
// 3) Run FROST signing with honest participants {1,2,3}.
//    Participant 2 sends a VALID share. In complete():
//      verify_share(view.verification_share(2), B.bound(2), share)
//    fails because verification_shares[2] was overwritten, yielding
//      Err(FrostError::InvalidShare(Participant(2)))
//    -> honest participant 2 is blamed/slashed despite a correct share.
```

The root cause is that `ThresholdKeys::new` performs only shape checks (lines 355–374) and derives `group_key` from just `1..=t` (line 376–378), leaving every other deserialized field unauthenticated against the secret share [5](#0-4) .

    if verification_shares.len() != usize::from(params.n()) {
      Err(DkgError::IncorrectAmountOfVerificationShares {
        n: params.n(),
        shares: verification_shares.len(),
      })?;
    }
    for participant in verification_shares.keys().copied() {
      if u16::from(participant) > params.n() {
        Err(DkgError::InvalidParticipant { n: params.n(), participant })?;
      }
    }

    match &interpolation {
      Interpolation::Constant(_) => {
        if params.t() != params.n() {
          Err(DkgError::InapplicableInterpolation("constant interpolation for keys where t != n"))?;
        }
      }
      Interpolation::Lagrange => {}
    }

    let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
    let group_key =
      t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();

    Ok(ThresholdKeys {
      core: Arc::new(Zeroizing::new(ThresholdCore {
        params,
        interpolation,
        secret_share,
        group_key,
        verification_shares,
      })),
      scalar: C::F::ONE,
      offset: C::F::ZERO,
    })
  }
