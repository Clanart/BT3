### Title
Front-runnable reward distribution in `BaseRewardPool`/`BaseRewardPoolV2` allows theft of unclaimed WOM/bonus yield via last-block deposits before permissionless `harvest()` - (File: rewards/BaseRewardPoolV2.sol, wombat/WombatStaking.sol)

### Summary
`WombatStaking.harvest()` is a permissionless, unprivileged-callable function that pulls accrued WOM (and bonus) rewards from Wombat and immediately queues them into the corresponding `BaseRewardPool`/`BaseRewardPoolV2` via `queueNewRewards`/`_provisionReward`. That function distributes the entire incoming reward amount instantly and pro-rata over the pool's *current* `totalStaked()`, with no vesting, cooldown, or deposit/withdrawal fee in the deposit/withdraw path (`MasterMagpie._deposit`/`_withdraw`, `WombatPoolHelper.deposit`/`withdraw`). This mirrors the reported `UniV3Vault` bug class: value earned over time by long-term stakers (unharvested LP/protocol yield) is not protected from a large, instantaneous deposit made immediately before the yield is realized/distributed, letting an attacker with an ordinary wallet capture a share of yield they never contributed to earn, then withdraw immediately.

### Finding Description
`WombatStaking.harvest(address _lpToken)` has only a `whenNotPaused` and `_onlyActivePool` modifier — any wallet may call it to trigger `_toMasterWomAndSendReward(_lpToken, 0, true)`, which claims pending WOM (and bonus rewards) from Wombat and forwards them into the pool's `BaseRewardPool`/`BaseRewardPoolV2` via `queueNewRewards`: [1](#0-0) 

`queueNewRewards` calls `_provisionReward`, which — when `totalStaked() > 0` — immediately spreads the entire newly-added reward across the pool's current total stake by bumping `rewardPerTokenStored`: [2](#0-1) 

Because `rewardPerTokenStored` is a single global accumulator shared by all depositors regardless of how long they have staked, any address that deposits stake into the pool (via `WombatPoolHelper.deposit`/`WombatPoolHelperV2.deposit`, ultimately calling `MasterMagpie.depositFor` → `_deposit`) immediately prior to a `harvest()` call becomes eligible for a full pro-rata slice of the yet-to-be-distributed reward: [3](#0-2) [4](#0-3) 

There is no lockup, cooldown, or entry/exit fee on this deposit/withdraw path (unlike `mWomSV`, which enforces cooldowns for unlocking), so the attacker can withdraw again in the very same block/transaction sequence after the reward has been credited: [5](#0-4) [6](#0-5) 

This is directly analogous to the reported `UniV3Vault.collectEarnings()`/`tvl()` bug: pending/unharvested yield accrued for existing depositors is not protected from a large last-second deposit that dilutes their claim to it once the yield is realized.

### Impact Explanation
An attacker can permanently steal a portion of unclaimed WOM/bonus-token yield rightfully owed to long-term stakers of a given Wombat pool, by depositing right before calling (or front-running someone else calling) `harvest()`, then withdrawing immediately after. Every legitimate staker's share of that harvested reward is diluted by the attacker's inflated temporary stake, resulting in a genuine, direct theft of user-owned unclaimed yield — the exact impact class ("theft of unclaimed yield") accepted for this bug class.

### Likelihood Explanation
`harvest()` is unauthenticated/permissionless and callable by any wallet, and can be combined by the attacker in the same transaction/atomic bundle with a deposit and a withdrawal (deposit → harvest → withdraw), requiring no front-running of another user at all — the attacker can trigger the entire sequence themselves in one transaction, making this trivially and repeatedly exploitable.

### Recommendation
Introduce a delay between deposit and reward eligibility (e.g., snapshot-based reward accrual, or only crediting new rewards to stakers who were present before the reward-triggering block), and/or add a withdrawal cooldown or entry/exit fee to `MasterMagpie`/`WombatPoolHelper` deposit-withdraw flows so that a single-block deposit cannot claim a share of rewards accrued prior to that deposit. Alternatively, restrict who may call `harvest()` to reduce the attacker's ability to time the reward injection precisely, though the core fix must be in the reward-per-token accounting to exclude same-block/flash deposits from freshly queued rewards.

### Proof of Concept
1. Pool `P` has been accumulating WOM rewards on Wombat for its stakers over time; `harvest()` has not yet been called, so the accrued external yield is not yet reflected in `BaseRewardPool`'s `rewardPerTokenStored`.
2. Attacker calls `WombatPoolHelper.deposit()` with a very large amount of `depositToken`, receiving newly minted receipt tokens and staking them into `MasterMagpie`/`BaseRewardPoolV2`, sharply inflating `totalStaked()`. [3](#0-2) 
3. Attacker (or anyone) calls `WombatStaking.harvest(lpAddress)`, which claims the accrued WOM and calls `queueNewRewards` → `_provisionReward`, which distributes the entire reward pro-rata over the now-inflated `totalStaked()`. [7](#0-6) 
4. Attacker immediately calls `WombatPoolHelper.withdraw()` to unstake, retaining the accrued `rewardPerTokenStored` credit for the block(s) they were staked and can claim it via `MasterMagpie`/`BaseRewardPoolV2.getReward()`. [6](#0-5) 
5. As a result, the attacker captures a share of yield that was earned entirely by prior long-term stakers, diluting their rightful rewards — with no lockup or fee preventing the instantaneous deposit-harvest-withdraw sequence.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }

    /// @notice internal function to deal with withdraw staking token
    function _withdraw(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        _harvestAndUnstake(_stakingToken, _account, _amount, _isVlMgp);

        if (!_isVlMgp)
            IERC20(tokenToPoolInfo[_stakingToken].stakingToken).safeTransfer(address(msg.sender), _amount);
        emit Withdraw(_account, _stakingToken, _amount);
    }

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
