### Title
Attacker-controlled participant count causes amplified memory allocation in `ThresholdKeys::read` - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` trusts a serialized `u16` participant count `n` and immediately reserves `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficients before any of the corresponding bytes are present, then iterates `n` times reading scalars and group elements. An unprivileged party feeding crafted bytes to `ThresholdKeys::read` (one of the listed untrusted-input deserialization APIs) obtains a ~100× memory-amplification primitive — roughly 2 MB of heap allocation is committed in exchange for ~20 bytes of input — enabling resource-exhaustion denial of service (CWE-770, the same class as CVE-2023-44271).

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` parses `t`, `n`, `i` directly from the reader with no prior validation. When the interpolation tag is `0` (`Interpolation::Constant`), it performs `Vec::with_capacity(usize::from(n))` where `n` is fully attacker-controlled (up to 65535), reserving `n * size_of::<C::F>()` bytes — about 2 MiB for 256-bit fields — before reading a single scalar. [1](#0-0) 

The subsequent loops (`for _ in 0 .. n` reading `C::read_F`, and `for l in 1 ..= n` reading `C::read_G` into `verification_shares`) abort on the first missing byte, so the attacker only needs to supply the small header (~20 bytes: curve ID length + ID + 6 bytes params + 1 byte tag) to trigger the multi-megabyte reservation. [2](#0-1) 

Each invocation allocates up to ~2 MiB plus `HashMap` growth while the `ThresholdParams::new`/`ThresholdKeys::new` validation happens only *after* all allocation and parsing, so the oversized `n` is never rejected pre-allocation. [3](#0-2) 

This contrasts with `Call::read` in `networks/ethereum/src/machine.rs`, which explicitly defends against the identical pattern ("A valid DoS would be to claim a 4 GB data is present for only 4 bytes") by chunking reads; and with `RrCodec::read_request` in `coordinator/src/p2p.rs`, which bounds `len` by `MAX_LIBP2P_REQRES_MESSAGE_SIZE` before allocating. The `dkg` deserialization path has no such guard. [4](#0-3) [5](#0-4) 

### Impact Explanation
A remote party that can cause a coordinator/processor node to deserialize `ThresholdKeys` bytes it controls (e.g., via tributary transactions or key-gen message handling that calls `ThresholdKeys::read`) can force repeated ~2 MiB allocations with ~20-byte inputs each — an amplification factor of roughly 100,000:1 in input-to-committed-capacity terms for the `with_capacity` reservation, and ~100:1 in practice once the transient Vec is dropped and re-allocated per message. Sustained submissions cause progressive memory exhaustion and node crash/OOM, denying service to the DKG/signing pipeline. Because the allocation precedes all semantic validation, invalid-but-cheap payloads fully trigger it.

### Likelihood Explanation
`ThresholdKeys::read` is a public deserialization entry point on an untrusted-bytes path expressly in scope. The attacker needs no keys, no valid signatures, and no threshold participation — only the ability to have their bytes parsed. The primitive is deterministic and repeatable at message rate.

### Recommendation
Validate `t`, `n`, `i` via `ThresholdParams::new` *before* any allocation, cap `n` at a sane protocol maximum (e.g., the real validator-set size), and replace `Vec::with_capacity(n)` plus the `1 ..= n` read loops with incremental `Vec::push` bounded by actually-present bytes — mirroring the chunked-read defense already used in `networks/ethereum/src/machine.rs:51-60`.

### Proof of Concept
```rust
use std::io::Cursor;
use ciphersuite::Ciphersuite;
use dkg::ThresholdKeys;
// C = any Ciphersuite with a ~32-byte F, e.g. Ristretto

// Craft: ID_len(4) || C::ID || t=1(2) || n=65535(2) || i=1(2) || tag=0(1)
let mut buf = vec![];
buf.extend(&(C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(&1u16.to_le_bytes());       // t
buf.extend(&u16::MAX.to_le_bytes());   // n = 65535 -> Vec::with_capacity(65535)
buf.extend(&1u16.to_le_bytes());       // i
buf.push(0u8);                         // Interpolation::Constant

// ~20 bytes of input commits ~2 MiB of heap capacity before failing on read_F
let _ = ThresholdKeys::<C>::read(&mut Cursor::new(&buf));
```
Spamming this message forces repeated multi-megabyte allocations, exhausting memory at a tiny bandwidth cost.
