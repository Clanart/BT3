## Title
Malicious git remote/submodule can spoof a `WWW-Authenticate` header to trigger Desktop's native "Sign in to GitHub" dialog against an attacker-controlled endpoint - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The Magnetar report's root cause is: the contract lets an unprivileged, attacker-influenced input (a user-supplied address) decide which external party receives a trusted, sensitive action (an approval/transfer), with no whitelist. In GitHub Desktop, the analogous trust boundary is the Git credential-helper trampoline, which decides whether to treat a remote host as "GitHub-like" (and therefore worth prompting the user to sign in to) based on data that originates from the remote server itself, including data forwarded from an HTTP response. That classification then drives Desktop to open its native, trusted-looking GitHub/Enterprise sign-in UI against whatever host git happened to contact - which can be a completely attacker-controlled server reached via a malicious remote, submodule, or a proxying MITM host.

### Finding Description
When git needs credentials it invokes Desktop's credential helper (`credential.helper=desktop`), passing key/value pairs it collected for the request, including any `wwwauth[]` entries copied from the server's `WWW-Authenticate` response header. `getEndpointKind` classifies the endpoint using this attacker-influenced data: [1](#0-0) 

If the (attacker-controlled) server's `WWW-Authenticate` header contains `realm="GitHub"`, the endpoint is classified `enterprise`, even if it isn't `github.com` and isn't a previously known enterprise account. `getCredential` then checks `!accounts.some(a => a.endpoint === apiEndpoint)` and, finding no match, calls `ui.promptForGitHubSignIn(endpoint)`: [2](#0-1) 

`promptForGitHubSignIn` opens Desktop's native sign-in popup, using the attacker's own endpoint as the sign-in target and displaying it as `credentialHelperUrl` with copy stating "Git requesting credentials to access `<url>`": [3](#0-2) [4](#0-3) 

The sign-in store then advances directly to the `Authentication` step for that attacker-controlled URL without verifying it is a legitimate/expected GitHub Enterprise host — it merely syntax-validates the URL: [5](#0-4) 

The remote host that triggers all of this is exactly the kind of untrusted input Desktop's own documentation acknowledges can point "to another host entirely" — e.g., via a submodule inside a cloned repository: [6](#0-5) 

None of `getEndpointKind`, `getCredential`, or `promptForGitHubSignIn` verify that the host is actually a whitelisted/previously-configured GitHub or GHE endpoint before surfacing Desktop's trusted sign-in chrome — exactly the missing-whitelist pattern flagged in the Magnetar report (there `cluster.isWhitelisted` was bypassable because the checked address itself was attacker-supplied; here the `realm="GitHub"` signal used to decide "is this a GitHub host" is itself attacker-supplied).

### Impact Explanation
An attacker who controls a git remote, a submodule URL embedded in a repository the user clones/fetches, or a network-level proxy/MITM position for a git operation can force Desktop to display its native "Sign in to GitHub"/"Sign in to GitHub Enterprise" dialog pointed at an arbitrary attacker-controlled origin. Because this UI is produced entirely by Desktop (not the browser address bar for a webpage), users have a strong trust signal that this is a legitimate internal GitHub Desktop action, increasing the odds they proceed with authentication (browser-based OAuth or PAT-based flow depending on build) against the attacker's server — leading to unauthorized OAuth/account binding to a spoofed endpoint and potential capture of GitHub credentials/tokens.

### Likelihood Explanation
Requires only that the user perform a normal, unprivileged operation — cloning/fetching a repository that contains a submodule pointing at an attacker's git server, or fetching over a network path an attacker can intercept/respond on — no local access, no prior malware, and no elevated privileges. The header/value used for classification (`wwwauth[*]`) is fully attacker-controlled server response data, not authenticated by Desktop.

### Recommendation
Do not derive the "is this a GitHub host" decision from unauthenticated data supplied by the remote server (`WWW-Authenticate` realm string) or from an unverified user-entered/derived URL. Only trigger the GitHub/Enterprise sign-in UI for hosts that are already recognized (e.g., matched against `isDotCom`/`isGHE`/an existing whitelist of endpoints, or a verified `/meta`-style API probe as already used elsewhere), analogous to applying the existing `cluster.isWhitelisted` pattern recommended for Magnetar. At minimum, require explicit user confirmation that clearly shows the raw untrusted host before any sign-in flow is initiated, and never auto-advance past `EndpointEntry` for hosts sourced from git's `wwwauth` data.

### Proof of Concept
1. Attacker publishes a repository with a submodule (or serves as the origin remote) whose git server responds to HTTPS requests with `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim clones/fetches the repository in GitHub Desktop, which invokes `git` with `credential.helper=desktop`, per `withTrampolineEnv` (`app/src/lib/trampoline/trampoline-environment.ts:143`).
3. Git forwards the captured `WWW-Authenticate` header as `wwwauth[]=Basic realm="GitHub"` to the trampoline's `get` command.
4. `getEndpointKind` (`trampoline-credential-helper.ts:153-165`) classifies the attacker host as `enterprise`.
5. `getCredential` (`trampoline-credential-helper.ts:107-125`) finds no existing account for that endpoint and calls `ui.promptForGitHubSignIn(endpoint)`.
6. Desktop shows its native GitHub sign-in dialog directed at the attacker's endpoint (`trampoline-ui-helper.ts:80-104`, `sign-in.tsx:183-198`), and `SignInStore.setEndpoint` advances straight to the `Authentication` step (`sign-in-store.ts:394-458`) without any host-legitimacy check.

I was not able to fully confirm within available tool calls whether the current `AuthenticationForm` build path exposes a direct PAT/basic-auth entry field (which would send credentials straight to the attacker endpoint) versus only browser-based OAuth (`onBrowserSignInRequested`) — this affects whether the exfiltration is direct-credential or phishing-via-trusted-UI. This should be verified by reading `app/src/ui/lib/authentication-form.tsx` in full and `app/src/lib/api.ts` (`requestOAuthToken`, `getOAuthAuthorizationURL`) in a follow-up session, since the index did not return their full contents in this session.

  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }

    if (

      currentState?.kind !== SignInStep.ExistingAccountWarning
    ) {
      const stepText = currentState ? currentState.kind : 'null'
      return fatalError(
        `Sign in step '${stepText}' not compatible with endpoint entry`
      )
    }

    /**
     * If the user enters a github.com url in the GitHub Enterprise sign-in
     * flow we'll redirect them to the GitHub.com sign-in flow.
     */
    if (/^(?:https:\/\/)?(?:api\.)?github\.com($|\/)/.test(url)) {
      this.beginDotComSignIn(currentState.resultCallback)
      return
    }

    this.setState({ ...currentState, loading: true })

    let validUrl: string
    try {
      validUrl = validateURL(url)
    } catch (e) {
      let error = e
      if (e.name === InvalidURLErrorName) {
        error = new Error(
          `The GitHub Enterprise instance address doesn't appear to be a valid URL. We're expecting something like https://example.ghe.com.`
        )
      } else if (e.name === InvalidProtocolErrorName) {
        error = new Error(
          'Unsupported protocol. Only https is supported when authenticating with GitHub Enterprise instances.'
        )
      }

      this.setState({ ...currentState, loading: false, error })
      return
    }

    const endpoint = getEnterpriseAPIURL(validUrl)

    const existingAccount = this.accounts.find(x => x.endpoint === endpoint)

    if (existingAccount) {
      this.setState({
        kind: SignInStep.ExistingAccountWarning,
        endpoint,
        existingAccount,
        error: null,
        loading: false,
        resultCallback: currentState.resultCallback,
      })
    } else {
      this.setState({
        kind: SignInStep.Authentication,
        endpoint,
        error: null,
        loading: false,
