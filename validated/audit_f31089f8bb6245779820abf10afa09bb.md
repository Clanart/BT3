### Title
Balance-handler event-range desync between EVM StateDB (cached) balance and x/bank (actual) balance during nested/recursive precompile calls - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
The Tokemak bug is a class of vulnerability where a "cached" accounting value (`totalAssets_cached`) can diverge from the "actual" on-chain value (`totalAssets_actual`), and different code paths inconsistently read one or the other, letting an attacker arbitrage the gap. In Cosmos EVM the structurally equivalent invariant is that the EVM `StateDB` balance for an address (the value the EVM/precompiles/contracts "see" and act on) must always equal the real `x/bank` (and `x/precisebank`) balance (the "actual" settled value). This equivalence is maintained by `precompiles/common.BalanceHandler`, which snapshots the event-manager length before a precompile executes (`BeforeBalanceChange`) and replays only the bank `coin_spent`/`coin_received` events emitted after that point into `StateDB.AddBalance/SubBalance` (`AfterBalanceChange`) [1](#0-0) .

### Finding Description
`BeforeBalanceChange` records `prevEventsLen = len(ctx.EventManager().Events())`, and `AfterBalanceChange` only processes `events[bh.prevEventsLen:]` [2](#0-1) . This design implicitly assumes each precompile invocation owns a single, non-overlapping window of the shared `ctx.EventManager()` event log between its `Before`/`After` calls. When precompile calls are nested or recursive within the same EVM transaction (a Solidity contract calling a precompile, which internally calls back into an EVM contract, which calls the same or another precompile again — as reproduced in `evmd/tests/integration/balance_handler/balance_handler_test.go` and `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go`), the inner call's `BeforeBalanceChange` overwrites `prevEventsLen`, and the inner call's `AfterBalanceChange` consumes events that the outer call would otherwise need to reconcile. The repository's own test comments describe this precisely: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten... leading to balance desync between native bank keeper and EVM stateDB"* [3](#0-2) , and a companion test explicitly targets *"reverted distribution calls [that] leave persistent bank events that are incorrectly aggregated"* during nested ICS20/distribution precompile interaction [4](#0-3) .

Production stateful precompiles (distribution, staking, gov, slashing, ics20, erc20) all wire a `BalanceHandlerFactory` into `cmn.Precompile` [5](#0-4) , and `RunNativeAction`/`runNativeAction` constructs a `BalanceHandler` per call and brackets `action(ctx)` with `BeforeBalanceChange`/`AfterBalanceChange` [6](#0-5) . Any keeper action inside `action(ctx)` that itself triggers another EVM call (e.g. `evmKeeper.CallEVM`/`CallEVMWithData` back into an attacker contract, which then invokes another stateful precompile before the outer one returns) re-enters this same event-window bookkeeping, since `ctx.EventManager()` is a single shared, non-reentrant-aware log for the whole transaction.

### Impact Explanation
If the event window that `AfterBalanceChange` processes is desynced from the actual bank-event range produced by that specific call (either skipping events that should apply, or double/mis-attributing events from a different nested call, or including events from a reverted nested call that were never rolled back from the outer event manager), the EVM-visible balance (`StateDB`, which subsequent EVM instructions, `balanceOf` precompile calls, and value transfers all rely on within the same transaction) diverges from the real, settled `x/bank`/`x/precisebank` balance. This is a direct analog of `totalAssets_cached` vs `totalAssets_actual`: an attacker who can craft a contract that nests precompile calls (staking/distribution/ics20/erc20 precompiles are all reachable from arbitrary user contracts) could cause the StateDB to over-credit an address relative to its true bank balance — enabling spend/duplication of value that isn't actually backed by escrowed/native funds — or under-credit another account, permanently losing accounted value. Either direction breaks the "Asset-representation path" 1:1 invariant between native coins and EVM-visible balances called out in scope, and unauthorized duplication/loss of spendable value is a Critical-severity impact.

### Likelihood Explanation
Reachability requires an unprivileged attacker to deploy an EVM contract that nests calls into two or more stateful precompiles (or recursively calls the same precompile) within a single transaction, which is easily achievable with an ordinary EVM tx (no privileged keys needed) — the repository's own tests demonstrate the mechanism using the debug precompile and using real ICS20-triggered nested distribution calls with reverts. However, I was only able to fully trace and reproduce the desync mechanism against the test-only `debug` precompile (`testutil/testdata/debug/debug.go`), which manages its `BalanceHandler` as a shared field via `GetBalanceHandler()`, distinct from the per-call `NewBalanceHandler()` construction path used by production precompiles in `precompiles/common/precompile.go`. I could not conclusively confirm, within the available tool budget, whether production precompiles' per-call handler instantiation fully eliminates the desync when call reentrancy/nesting occurs through `evmKeeper.CallEVM`-style callbacks (as opposed to a literally shared struct field) — the `ics20_recursive_precompile_calls_test.go` file name and comments suggest this is exercised and asserted against in the production code path as well, but I did not read that full test/its assertions to confirm whether it currently passes (i.e., is a regression guard for a fixed bug) or is a known-failing reproduction.

### Recommendation
- Make the event-window tracking reentrancy-safe: instead of a single mutable `prevEventsLen` int compared against the tail of a global event slice, use a stack (or the existing `journal`/snapshot machinery) to push/pop per-call event boundaries, or capture events by reference/copy at `Before` time and diff by set/index rather than length, so nested/recursive precompile invocations cannot clobber each other's bookkeeping.
- Ensure that events emitted by any nested call that ultimately reverts are excluded from being processed by an enclosing call's `AfterBalanceChange` (i.e., align event manager rollback with `StateDB` snapshot revert semantics), verified via a strict invariant check that `StateDB` balance equals `x/bank`(+`x/precisebank`) balance after every precompile call and at end-of-transaction, not just in unit tests.
- Add/extend integration tests that exercise nesting across *distinct* production stateful precompiles (not only the debug precompile) with an interleaved revert, and assert `GetBalance` (bank) == `StateDB.GetBalance` (EVM) for every touched address after the transaction, to close any residual gap between cached (StateDB) and actual (bank) balances.

### Proof of Concept
The repository already contains a reproducible harness for the core mechanism:
1. `evmd/tests/integration/balance_handler/balance_handler_test.go` deploys `DebugPrecompileCaller.sol`, which recursively calls the debug precompile [7](#0-6) , and shows the resulting event/balance accounting is affected by the shared `BalanceHandler` instance and `prevEventsLen` overwrite [8](#0-7) .
2. `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go` reproduces the same class of bug using a real production flow: an ICS20 transfer of a native ERC20 token whose contract overrides `_beforeTokenTransfer` to recursively re-enter, interacting with distribution reward claims, and asserts on the resulting bank-denominated balance and event counts [9](#0-8) .

I was not able to independently execute these tests or trace all downstream assertions in the time available; the finding here documents a genuine, codebase-acknowledged desync-of-cached-vs-actual-balance bug class matching the seed report, with confirmed reachability from an unprivileged EVM contract, but confidence on the exact exploitable delta (which account gains vs. loses value, and by how much) is Medium-High pending full execution/trace of the cited test suites against current `main`.

// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.4;

contract DebugPrecompileCaller {
    address constant debugPrecompile = 0x0000000000000000000000000000000000000799;
    error CallFailed(bytes data);
    function callback(uint256 counter) public {
        bool result;
        bytes memory data;

        // emit events
        for (uint i = 0; i < counter; i++) {
            (result, data) = debugPrecompile.call(abi.encodePacked(uint8(1)));
            if (!result) {
                revert CallFailed(data);
            }
        }

        if (counter > 3) {
            // stop the recursion
            return;
        }

        // recursive call
        (result, data) = debugPrecompile.call(abi.encodePacked(uint8(0), counter));
        if (!result) {
            revert CallFailed(data);
        }
    }
}
