## Analog Found

### Title
Automatic, unconfirmed remote-URL rewrite from untrusted GitHub API `clone_url` field allows silent push/fetch redirection - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The upstream finding calls for a timelock/notification before a privileged, trust-sensitive value (`platformFee`) is changed, so users aren't surprised by a critical config mutation. In GitHub Desktop, the analogous trust-sensitive value is the local repository's `origin` remote URL — the destination for every future `git push`/`git fetch`. Desktop automatically rewrites this URL based on data returned by the GitHub/GHE API, with **no user prompt, confirmation, or notification of any kind**, whenever the repository is (re)selected.

### Finding Description
`updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts` compares the current git remote to the `clone_url` field of an `IAPIRepository`/`IAPIFullRepository` fetched from the API, and silently calls `gitStore.setRemoteURL(...)` (which runs `git remote set-url origin <url>`, see `app/src/lib/git/remote.ts:56-64`) when three conditions hold: [1](#0-0) 

- `protocolsMatch` — only the URL **scheme** (`https:` vs `git+ssh:` etc.) is checked to be equal; the **hostname is never validated against the endpoint the account is authenticated to**.
- `remoteUrlUnchanged` — the *previously cached* `gitHubRepository.cloneURL` still matches the current remote (via `urlMatchesRemote`, which only compares hostname/owner/name derived from `parseRemote`) [2](#0-1) 
- `!urlsMatch` — the new API-provided URL differs from the current remote.

This function is invoked automatically, without any user action, every time a GitHub-backed repository is refreshed — which happens on every repository selection: [3](#0-2) [4](#0-3) 

The broken invariant: nothing in this path verifies that the new `clone_url` actually belongs to the same host/account endpoint the user is connected to — it only checks that the *scheme* matches. The `clone_url` value is sourced entirely from `api.fetchRepository(owner, name)`, i.e., from the API server's response body, which is exactly the "GitHub API object" / "git remote... response" class of attacker input called out as valid in this scan's scope. A malicious or compromised GitHub Enterprise Server (or a MITM/proxy sitting in front of the configured API endpoint) can therefore return an arbitrary `clone_url` and Desktop will rewrite the user's `origin` remote to point at it — silently.

### Impact Explanation
Once the remote is rewritten, every subsequent `Push`/`Fetch`/`Pull` performed through Desktop's UI silently targets the attacker-controlled destination instead of the user's real repository. This is a direct case of "silent corruption of what the user commits or pushes": the user believes they are pushing to their known repository, but the destination has been swapped without any dialog, warning, or diff shown (contrast with the deliberate, user-facing confirmation dialog that exists for the *unrelated* upstream-remote case in `app/src/ui/upstream-already-exists/upstream-already-exists.tsx`, which explicitly asks the user before updating a remote). No equivalent confirmation exists for `updateRemoteUrl`.

### Likelihood Explanation
This requires an attacker who controls the API endpoint's response for `fetchRepository` (e.g., a compromised/malicious GitHub Enterprise Server the user has added an account for, or a network position that can tamper with that specific API response) — an "attacker-controlled ... GitHub API object" scenario, not local access, not a leaked credential, and not requiring any unnatural user action. The trigger condition (protocol match + no manual remote edit since last successful sync) is the common, default case for the vast majority of users who never hand-edit their remote URL.

### Recommendation
Before silently rewriting the remote URL, validate that the new `clone_url`'s hostname matches the hostname of the account's authenticated API endpoint (not merely that the scheme string matches), and/or surface a confirmation dialog to the user (as already done for the upstream-remote-mismatch case) before mutating `origin`. This gives users the same kind of "time to react to a critical change" that the original report asked for with `setPlatformFee()`.

### Proof of Concept
1. Add an account in Desktop pointing to a GitHub Enterprise Server endpoint controlled by (or later compromised/MITM'd by) an attacker.
2. Clone a repository from that server; `origin` is set to `https://ghe.example.com/org/repo.git`.
3. Attacker's server, when Desktop calls `GET /repos/:owner/:name` during a routine repository refresh (`_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository`), returns a JSON body with `clone_url: "https://ghe.example.com/attacker/decoy.git"` (same scheme, different repo/host path).
4. `updateRemoteUrl` sees `protocolsMatch === true` and `remoteUrlUnchanged === true` (user hasn't manually edited the remote) and `urlsMatch === false`, so it calls `gitStore.setRemoteURL('origin', 'https://ghe.example.com/attacker/decoy.git')` with zero user interaction.
5. The next time the user clicks "Push" in Desktop, their commits are silently sent to the attacker's repository instead of their own, with no warning ever shown.

  // want to change what they've done just to be safe

  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
