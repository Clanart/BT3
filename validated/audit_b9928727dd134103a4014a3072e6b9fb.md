### Title
Single global `challengePeriod` applied uniformly to all whitelisted state machines on `EvmHost`, ignoring per-chain finality requirements - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost` stores exactly one `challengePeriod` value in `HostParams` and applies it identically to every whitelisted counterparty `stateMachine`, even though `EvmHost.stateMachines` can list multiple heterogeneous state machines with different consensus finality characteristics. This is the same bug class as the reported `ChainlinkPriceOracle` issue: a single hardcoded interval used for entities (here, counterparty chains instead of price feeds) that individually require different freshness/safety windows.

### Finding Description
`HostParams` defines a single scalar field: [1](#0-0) [2](#0-1) 

```
// Minimum challenge period for state commitments in seconds;
uint256 challengePeriod;
...
// State machines whose state commitments are accepted
uint256[] stateMachines;
```

This one value is exposed by `challengePeriod()` with no state-machine argument and is used verbatim in every handler that gates message processing on elapsed delay: [3](#0-2) 

`HandlerV2` calls `host.challengePeriod()` (no `stateMachineId` parameter) in `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts`: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

By contrast, the Rust/Substrate side of the same protocol explicitly models challenge period as a per-`StateMachine` value, acknowledging that different chains require different safety windows: [8](#0-7) [9](#0-8) 

and `CreateConsensusState`/`UpdateConsensusState` on Substrate carry a `BTreeMap<StateMachine, u64>` of challenge periods, not a single scalar: [10](#0-9) 

`updateHostParams` on `EvmHost` sets `_hostParams.challengePeriod` as one number while adding an arbitrary-length `params.stateMachines` array, with no validation that the single value is adequate for every listed chain: [11](#0-10) 

### Impact Explanation
When an `EvmHost` deployment (e.g., on Ethereum) whitelists more than one counterparty state machine (which is expected — `stateMachines` is an array), the operator must pick a single `challengePeriod` that is safe for the least-safe/longest-finality chain in the set. If it is instead tuned (or left) at a value safe only for the fastest-finalizing chain, every `handlePostRequests`/`handleGetResponses`/timeout handler will allow processing of state commitments from the slower-finality chain as soon as the same short delay elapses — i.e., before that chain's state commitment is actually irreversible. This directly produces false state acceptance: `dispatchIncoming` is invoked on a `PostRequest`/`GetResponse` proven only against a commitment that could still be reverted/finality-violated for that specific state machine, which can be leveraged for double-processing, forged message delivery, or unauthorized execution against apps and any escrowed value (relayer fees, order settlement, paymaster balances) that trust the dispatch.

### Likelihood Explanation
This requires no malicious relayer, prover, or admin — it is a structural gap in the public entrypoints `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts`, callable by any address once the (uniformly too-short-for-some-chain) challenge period has elapsed for a given `StateMachineHeight`. Any host configured with multiple whitelisted state machines of differing finality profiles exposes this gap by design of the current `HostParams` schema, not through misuse.

### Recommendation
Change `challengePeriod` from a single `uint256` in `HostParams` to a `mapping(uint256 stateMachineId => uint256 challengePeriod)` (mirroring the Substrate/pallet `BTreeMap<StateMachine, u64>` model), require `updateHostParams`/whitelisting flows to set a period per state machine, and update `HandlerV2` to call `host.challengePeriod(stateMachineId)` for the specific `StateMachineId` embedded in the proof height, instead of a chain-agnostic `host.challengePeriod()`.

### Proof of Concept
1. Deploy `EvmHost` with `HostParams.challengePeriod = X` and `stateMachines = [chainA, chainB]`, where `chainB`'s consensus client has a materially longer effective finality/safety window than `X`.
2. Wait `X` seconds after a state commitment for `chainB` is stored via `storeStateMachineCommitment` (called by the handler after consensus verification).
3. Call `HandlerV2.handlePostRequests` (or `handleGetResponses`) with a valid MMR proof against that `chainB` commitment — the check `challengePeriod > delay` at [12](#0-11)  passes even though `chainB`'s commitment is not yet safely final, allowing `dispatchIncoming` to execute against unsafe state.
