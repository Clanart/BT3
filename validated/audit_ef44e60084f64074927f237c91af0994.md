## Analysis

The OgvStaking bug's core invariant: **a value-holding operation lets the caller redirect proceeds to an arbitrary receiver, with no check that the receiver is actually capable of later claiming/operating on those funds** — causing permanent loss.

The local analog is in Hyperbridge's relayer-fee pipeline: `pallet-ismp-relayer`'s fee accumulation lets the delivering relayer redirect their earned fees to an arbitrary `beneficiary_address` of unchecked length/format, and the later `withdraw` path can only ever release funds to whoever can produce a signature whose derived address/pubkey bytes exactly equal what was stored. There is no format validation tying the two together.### Title
Unvalidated `beneficiary_address` in relayer fee redirection can permanently lock accumulated fees - ([File: modules/pallets/relayer/src/accumulate.rs])

### Summary
`pallet-ismp-relayer`'s `accumulate` extrinsic lets the delivering relayer redirect their earned fee to an arbitrary `beneficiary_address` supplied as raw, unvalidated `Vec<u8>`, authorized only by a signature proving the *delivery* relayer authorized the redirect — not that the beneficiary bytes are a well-formed, key-derivable address. `Fees` are then credited to whatever `beneficiary_address` bytes were given. Withdrawal (`Pallet::withdraw` in `modules/pallets/relayer/src/withdrawal.rs`) can only ever release a `Fees` entry to the account whose signature-derived `address`/`public_key` bytes exactly match the stored key. If the redirected `beneficiary_address` is malformed or does not correspond to any address a private key can produce a matching signature for, the credited fee becomes permanently unclaimable — the same "receiver cannot interact with the deposited value" failure mode as the OgvStaking report.

### Finding Description
In `modules/pallets/relayer/src/accumulate.rs`, the `beneficiary_details` branch: [1](#0-0) 

verifies only that the **delivery_address** (proven from the destination receipt) produced a valid signature over `beneficiary_message(nonce, state_machine, &beneficiary_address)`. The `beneficiary_address: Vec<u8>` payload itself is never checked for:
- correct length for the destination's signature scheme (20 bytes for EVM secp256k1 addresses, 32 bytes for sr25519/ed25519 public keys), or
- correspondence to an actual key any private key holder controls.

It is stored as-is via `Fees::<T>::try_mutate(state_machine, beneficiary_address.clone(), |inner| *inner += total_fee)`.

Later, `Pallet::withdraw` (`modules/pallets/relayer/src/withdrawal.rs:81-116`) derives the lookup key strictly from a fresh signature: [2](#0-1) 
and reads `Fees::<T>::get(dest_chain, address.clone())` using that derived key. The only way to claim a `Fees` balance is to produce a signature whose derived `address`/`public_key` bytes are byte-identical to whatever was stored as `beneficiary_address`.

There is no guard preventing the delivery relayer from redirecting to:
- a byte string of the wrong length/format for the destination chain,
- a syntactically valid address/pubkey nobody holds the private key for (e.g. a mistyped or truncated address, or a smart-contract-style address on a chain where the withdrawal path requires an ECDSA/sr25519/ed25519 signature and has no EIP-1271 or equivalent contract-signature fallback).

This is structurally identical to OgvStaking's `stake(amount, duration, to)`: the protocol accepts an arbitrary receiver for value with no verification that the receiver can subsequently exercise control over it.

### Impact Explanation
Fees accumulated for a relayer's honest delivery work can become permanently stuck and unrecoverable in the `Fees` storage map, satisfying "loss of funds" under the bounty's impact gate. Because the redirect is authenticated only by the original delivery relayer's signature (not by round-tripping through a matching withdrawal-side signature check at the time of redirect), a relayer can lock their own accrued rewards through a formatting mistake, or the flow could be scripted/automated (as in `tesseract/messaging/relayer/src/fees.rs`) in a way that silently produces malformed beneficiary bytes, locking real BRIDGE-denominated relayer revenue with no recovery path (no admin/governance rescue call is visible in this pallet).

### Likelihood Explanation
Reachable by any unprivileged relayer through the public, unsigned `accumulate_fees` extrinsic — no relayer/prover/admin trust assumption beyond the relayer's own key, which they legitimately possess to deliver ISMP messages. The only precondition is supplying a `beneficiary_details` tuple with an incorrectly formatted or unowned `beneficiary_address`; there is no on-chain check rejecting this before the fee is committed to that key.

### Recommendation
Validate `beneficiary_address` length/format against the target `state_machine`'s expected key encoding (20 bytes for EVM, 32 bytes for sr25519/ed25519) before accepting the redirect in `accumulate`, and/or require the beneficiary to co-sign (prove key possession) at redirect time the same way `withdraw` requires a matching signature to claim, rather than trusting only the delivery relayer's authorization.

### Proof of Concept
1. Relayer `R` (holding key for `delivery_address`) delivers a request and is entitled to `total_fee` on `state_machine`.
2. `R` calls `accumulate` with a `WithdrawalProof` whose `beneficiary_details = Some((malformed_or_unowned_bytes, signature_from_delivery_address))`. The signature check in `accumulate.rs:112-126` only validates that `delivery_address` authorized this redirect — `malformed_or_unowned_bytes` is accepted with no format check.
3. `Fees::<T>::try_mutate(state_machine, malformed_or_unowned_bytes, |inner| *inner += total_fee)` credits the fee under that key (`accumulate.rs:134-137`).
4. No key ever produces a `Signature::{Evm,Sr25519,Ed25519}` whose derived `address`/`public_key` (`withdrawal.rs:82-86`) equals `malformed_or_unowned_bytes` exactly, so `Fees::<T>::get(state_machine, address)` in `withdraw` (`withdrawal.rs:116`) never matches for any caller.
5. `total_fee` is permanently stranded in that `Fees` entry with no extrinsic path to reclaim it.

**Uncertainty note:** I could not find, within the indexed portion of this repo, any rescue/sweep extrinsic on `pallet-ismp-relayer` that would let governance recover stranded `Fees` entries, nor could I confirm whether off-chain tooling (`tesseract`) enforces length validation before submitting `beneficiary_details` that the on-chain pallet itself does not enforce. Given index size limits, some file contents (e.g. additional pallet call surfaces or migrations) may not be fully covered by my search; a full-repo Devin session would be needed to definitively rule out an existing mitigation elsewhere.
