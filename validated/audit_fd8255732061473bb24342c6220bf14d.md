## Title
Missing `--` end-of-options guard in `getCommits`/`getCommit` allows attacker-controlled ref/SHA to be interpreted as a `git log` option - (File: `app/src/lib/git/log.ts`)

## Summary

`getCommit(repository, ref)` forwards `ref` unchanged into `getCommits(repository, ref, 1)`. [2](#0-1) 

In `getCommits`, the `revisionRange` argument (here, `ref`) is pushed onto the `git log` argv immediately after `'log'`, **before** the `--` end-of-options separator that is only appended much later, after `formatArgs`/`additionalArgs`: [3](#0-2) 

Because the terminating `--` appears far after the revision argument in the argv list, and git parses `--`-preceded terms only as ceasing to interpret *later* tokens as pathspecs — not retroactively de-flagging tokens that precede it — any `ref`/`revisionRange` value that begins with `-` (e.g. `--upload-pack=...`, `-O<file>`, `--output=<path>`) is parsed by `git log` as an option/flag rather than as an inert revision operand.

## Finding Description

The invariant that "attacker-controlled text reaches a child process only as an inert operand, never as an option/flag" is violated: `revisionRange` sits at argv position 2 (right after `log`), with no guard preventing git's option parser from treating a `-`-prefixed value as a flag. The `--` added at the end of the argument list only protects `additionalArgs` and anything meant as a pathspec — it does not retroactively make the earlier `revisionRange` argument safe.

Reaching `getCommit` with attacker-influenced text: `notifications-store.ts`'s `handleChecksFailedEvent` calls `getCommit(repository, commitSHA)` where `commitSHA` comes from `event.commit_sha`, a field of an Alive/server-pushed `IDesktopChecksFailedAliveEvent`. [4](#0-3) 

## Impact Explanation

If an attacker can deliver a crafted "checks failed" Alive event (or otherwise control the value passed as `ref`/`commitSHA`) beginning with `-`, they could inject arbitrary `git log` flags such as `--output=<file>` (arbitrary file write), `-O`, or other options accepted by `git log`, potentially leading to file write outside the repo or other unintended git behavior in the context of the user's Desktop client.

## Likelihood Explanation

Likelihood is **low-to-uncertain** because it depends on whether:
1. The `commit_sha`/Alive-event pipeline sanitizes or validates the SHA format before use (I was not able to fully trace validation logic for the Alive event delivery/parsing path within the available tool budget).
2. Other call sites of `getCommit`/`getCommits` (e.g. `git-store.ts`, `app-store.ts`, `cherry-pick.ts`) pass fully attacker-controlled, unvalidated strings — I was only able to confirm the `notifications-store.ts` path clearly in the time available; the others need further tracing to confirm whether their `ref` values are locally-derived (e.g., from already-validated branch/commit objects) versus externally supplied.

## Recommendation

In `getCommits` (`app/src/lib/git/log.ts`), insert `'--'` immediately after `args.push(revisionRange)` (or before the `revisionRange` push, following git's `<rev> -- <path>` disambiguation convention), so a `-`-prefixed value cannot be interpreted as an option. Alternatively, validate that `ref`/`revisionRange` does not begin with `-` before use, rejecting such values outright.

/** Get the commit for the given ref. */
export async function getCommit(
  repository: Repository,
  ref: string
): Promise<Commit | null> {
  const commits = await getCommits(repository, ref, 1)
  if (commits.length < 1) {
    return null
  }

  return commits[0]
}
