### Title
BIP-340 signer ignores group-key parity: signatures produced for odd-Y aggregate keys fail consensus verification - (File: networks/bitcoin/src/crypto.rs)

### Summary
`Hram::hram` binds the challenge to the x-coordinate of the group key `A` only (`x(A)`), discarding its Y parity — the analog of treating a changed port as the same origin. Under BIP-340, verifiers lift the x-only public key to the *even*-Y point, so a signer whose aggregate key `A` is odd-Y must sign with `-d` (equivalently, negate `s`). `bitcoin::crypto::Schnorr::verify` corrects `s` only for the parity of `R` (`needs_negation(&sig.R)`), never for the parity of `A`. For every key generation or TapTweak offset that yields an odd-Y output key (~50% probability), every threshold signature the protocol produces is invalid under BIP-340 consensus rules.

### Finding Description
In `crypto/frost/src/algorithm.rs`, `Schnorr::sign_share` computes `s = r + c·x` where `x` is the literal secret share corresponding to `params.group_key()` — the full point, whatever its parity. In `networks/bitcoin/src/crypto.rs`:

- `Hram::hram` hashes `x(R) || x(A) || m` and applies `conditional_select(&c, &-c, needs_negation(R))`, correcting only for `R`'s parity.
- `Schnorr::verify` finalizes with `sig.s = conditional_select(&sum, &-sum, needs_negation(&sig.R))` and emits `sig.serialize()[1..]` as the BIP-340 signature. There is no `needs_negation(&group_key)` correction anywhere: the secret share is never negated when `A` is odd, and `s` is never negated for `A`'s parity.

BIP-340/341 verification computes `s·G =? R + c·lift_x(A)`, where `lift_x(A)` is the even-Y point with x-coordinate `x(A)`. If the actual group key is `A_odd = -lift_x(A)`, the produced `s = r + c·a` satisfies `s·G = R + c·A_odd = R - c·lift_x(A)`, so every external verifier rejects the signature. The internal `verify` in `complete()` still passes because `SchnorrSignature::verify` is checked against the true (odd) `group_key` and the same `c` — so the protocol believes it produced a valid signature while consensus does not.

`needs_negation` exists (`crypto.rs:26-28`) and is applied to `R` twice but never to the key. The FROST layer cannot compensate: `ThresholdKeys::group_key()` returns `(core.group_key * scalar) + G·offset` with arbitrary parity once a TapTweak offset is applied.

### Impact Explanation
Any Bitcoin output controlled by an odd-Y aggregate/output key is unspendable: the threshold network will complete FROST successfully, emit a 64-byte signature, and every Bitcoin node will reject any transaction using it. Since output-key parity after tweaking is uniformly distributed, roughly half of all generated wallet keys/outputs are affected. This is funds-reachable-but-unspendable, matching the "funds reported received that are not spendable" acceptance criterion, and requires no malicious behavior — honest participants with public inputs hit it.

### Likelihood Explanation
Certain on every odd-parity group key; parity is effectively a coin flip per key generation and per TapTweak offset. Triggering requires no adversary action beyond the network attempting to spend from such a key.

### Recommendation
When the group key is odd-Y, sign with the negated effective secret. Concretely, either negate `s` in `Schnorr::verify` when `needs_negation(&group_key_from_share)` is true (equivalently fold key parity into the `s` correction alongside the `R` parity correction), or have the FROST `Algorithm::sign_share` path negate the interpolated secret share when `group_key` is odd, keeping `x(A)` in the challenge unchanged.

### Proof of Concept
1. Construct `ThresholdKeys<Secp256k1>` such that `group_key()` has odd Y (e.g., apply `.offset(t)` with `t` chosen so the sum is odd, or any key pair whose aggregate key is odd).
2. Run the two-round FROST protocol with `bitcoin::crypto::Schnorr::new()` over any sighash `m` to completion: `complete()` returns `Ok([u8; 64])` because internal verification uses the true odd point.
3. Verify the emitted signature with any BIP-340 verifier (`bitcoin::key::XOnlyPublicKey::verify` / `secp256k1::schnorr::verify`) against `x_only(group_key)`. Verification fails because the verifier uses `lift_x(A) = -A` while `s` was computed for `+A`.

Approximate assertion: `needs_negation(&group_key)` is `Choice(1)`, `Hram::hram(R, A, m)` hashes `x(A)` without parity correction, and `verify` emits `s` adjusted only by `needs_negation(&sig.R)` — hence `s·G ≠ R_even + c·lift_x(A)` whenever `A` is odd. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    fn hram(R: &ProjectivePoint, A: &ProjectivePoint, m: &[u8]) -> Scalar {
      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());
      data.input(&x(R));
      data.input(&x(A));
      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));
      // If the nonce was odd, sign `r - cx` instead of `r + cx`, allowing us to negate `s` at the
      // end to sign as `-r + cx`
      <_>::conditional_select(&c, &-c, needs_negation(R))
    }
