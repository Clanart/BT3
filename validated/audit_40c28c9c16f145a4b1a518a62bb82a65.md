### Title
Ed448 `Point::from_bytes` torsion check is a no-op, accepting low-order points from untrusted bytes - (File: crypto/ed448/src/point.rs)

### Summary
The bug class in the report is a parser accepting attacker-controlled external input it was supposed to reject (XXE entities in XML). In Serai, the analogous surface is point deserialization of untrusted bytes via `GroupEncoding::from_bytes` (reached through `C::read_G`, `Commitments::read`, `DLEqProof`/`SchnorrSignature`/`ThresholdKeys` readers). The Ed448 implementation intends to reject torsion points but its `is_torsion_free` test is mathematically vacuous, so any curve point — including small-order points — is accepted as a valid canonical encoding.

### Finding Description
`Point::from_bytes` gates acceptance on `not_negative_zero & point.is_torsion_free()` at `crypto/ed448/src/point.rs:316`. However `is_torsion_free` is defined as: [1](#0-0) 

`Scalar::ZERO - Scalar::ONE` is `-1`, so the expression `(*self * -1) + self` is `(-self) + self`, which is the identity for *every* point. The function therefore always returns `Choice(1)` and rejects nothing — it never multiplies by the cofactor or subgroup order, which a real torsion check requires. The accompanying test at `crypto/ed448/src/point.rs:352-368` even asserts a known-torsion point returns `false`, which cannot hold under this implementation.

The consequences propagate through the in-scope decoders: `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-100`) validates only canonicality of the encoding and relies on `from_bytes` for subgroup membership; every Ed448 consumer of `read_G` (FROST `Commitments::read`, `ThresholdKeys::read` verification shares, `DLEqProof`/Schnorr PoK `read_point` paths in `crypto/dleq`) will therefore admit 4-torsion points supplied by an unprivileged peer.

### Impact Explanation
An attacker can submit points outside the prime-order subgroup wherever Ed448 points are deserialized from untrusted bytes:

- **FROST**: a torsion `group_key`, verification share, or nonce commitment in a `Preprocess`/`ThresholdKeys` read shifts the effective signature relation by a small-order component. Lagrange interpolation of verification shares from a malformed `ThresholdKeys` is no longer bound to the prime-order group, enabling incorrect verifier behavior and share/key confinement attacks analogous to classic small-subgroup confinement on cofactored curves.
- **DLEq / Schnorr PoK**: proofs verified against torsion generators or points satisfy the batch verification equation for a different-order relation than intended — a verifier-formula correctness failure reachable purely through `read_point` bytes.

This yields the accepted impact class "incorrect verifier formula" (statements verified over the wrong group law/order), with a deserialization path reachable from a peer's public preprocess/share bytes.

### Likelihood Explanation
Any protocol participant able to send bytes consumed by `read_G`/`Commitments::read`/`ThresholdKeys::read` against the Ed448 ciphersuite can craft a torsion or mixed-torsion point encoding (e.g., the known-torsion y-coordinate used in the crate's own test) and have it accepted. No key material, collusion, or node compromise is needed — just serialization of a non-prime-order point, which the standard Ed448 encoding supports.

### Recommendation
Fix `is_torsion_free` to perform a real subgroup check: either compute `self.double().double()` (multiply by cofactor 4) and verify the result is in the prime-order subgroup by multiplying by the group order `q` and checking identity, or equivalently check `(*self * q).is_identity()` where `q` is `Scalar`'s modulus... more precisely, check `(*self * (Scalar::ZERO - Scalar::ONE))` should instead be `*self * q` where `q = Scalar` modulus minus... concretely: return `(*self * <subgroup order>).is_identity()` — i.e., multiply by the order of the prime-order subgroup (`Scalar::CHARACTERISTIC`/`q` obtained via `-Scalar::ONE + Scalar::ONE`... the correct implementation is `(*self * q)` where `q` is derived from `Scalar::MODULUS` parsed to a `Scalar`, or simpler: `(self.double().double() * q)`) and additionally reject `self.is_identity()` if identity points are not acceptable. Ensure the existing `torsion` test passes.

//   (*self * (Scalar::ZERO - Scalar::ONE)) + self  ==  -self + self  ==  identity

let old_y = FieldElement::from_repr(hex!("12796c15...c16fa5100")).unwrap();
let torsion_point = Point { x: -recover_x(old_y).unwrap(), y: old_y, z: FieldElement::ONE };

// encode it and feed through the public decoder path used by read_G:
let bytes = torsion_point.to_bytes(); // canonical 57-byte encoding, sign bit set
let decoded = <Point as GroupEncoding>::from_bytes(&bytes);
// BUG: decoded.is_some() == true; a subgroup check would reject it.
// This same byte string passes Ciphersuite::<Ed448>::read_G, hence
// Commitments::read / ThresholdKeys::read accept torsion group keys and shares.
