### Title
Missing length validation on signer-supplied preprocess/share vectors causes out-of-bounds indexing panic in Bitcoin transaction signing - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
CVE-2020-12659 is a missing-length-validation bug: `xdp_umem_reg` trusted a user-supplied headroom value without bounds-checking it, yielding an out-of-bounds write. The analog in Serai is `TransactionSignMachine::sign` / `TransactionSignatureMachine::complete`, which index into counterparty-supplied `Vec<Preprocess>` / `Vec<SignatureShare>` values without first verifying their length equals the number of transaction inputs (`self.sigs.len()`), producing out-of-bounds indexing panics reachable with untrusted input.

### Finding Description
For Bitcoin signing, the `Preprocess` and `SignatureShare` associated types are `Vec<Preprocess<Secp256k1, ()>>` and `Vec<SignatureShare<Secp256k1>>` — one element per transaction input [1](#0-0) .

In `sign`, each per-input sign machine pulls `commitments[c]` out of each participant's vector, indexing directly by input index with no check that the vector has `self.sigs.len()` elements: [2](#0-1) . In `complete`, each input calls `shares.remove(0)` on every participant's share vector, again with no length check: [3](#0-2) .

Although `read_preprocess`/`read_share` populate these vectors with exactly `sigs.len()` elements when the bytes are well-formed [4](#0-3) , the `HashMap<Participant, Vec<…>>` arguments to `sign`/`complete` are public API surface — any coordinator or peer that assembles these maps from per-participant messages can supply a short or empty vector for a given `Participant`. `validate_map` (called inside `AlgorithmSignMachine::sign`, not before the indexing in `TransactionSignMachine::sign`) only validates the *outer* map keys, not inner vector lengths: the `commitments[c]` index occurs before any inner validation runs [5](#0-4) .

This mirrors the CVE's structure exactly: an attacker-controlled length is trusted, and a downstream index/write is performed against a buffer sized for the honest case.

### Impact Explanation
A malicious signing participant (or a coordinator relaying malformed preprocesses) who supplies fewer than `tx.input.len()` preprocess/share elements for their `Participant` entry triggers a panic in every honest signer processing that session (`index out of bounds` at `commitments[c]` or `removal index … out of bounds` at `shares.remove(0)`). In Rust this is a memory-safe panic rather than the CVE's OOB write, but it aborts the signing thread — a remotely triggerable denial of service against threshold signing of Bitcoin transactions, permanently stalling spends of the multisig's UTXOs for that session. This is reachable purely with untrusted protocol input (the preprocess/share vectors a participant is expected to broadcast).

### Likelihood Explanation
Requires a participant (or whoever deserializes preprocesses into the `HashMap`) to submit a malformed-length vector — trivially done by crafting a short `Vec`, since neither `read_preprocess` nor `sign` enforces per-participant vector length before indexing. Any multi-input transaction signing session is exposed; single-input sessions panic on any empty vector. No key material or collusion needed.

### Recommendation
In `TransactionSignMachine::sign` and `TransactionSignatureMachine::complete`, validate `commitments.len() == self.sigs.len()` (and each share vector's length) for every participant before indexing, returning `FrostError::InvalidParticipant`/a new malformed-message error instead of panicking — the same "validate the headroom before use" fix as upstream commit `99e3a23`.

### Proof of Concept
```rust
// Honest signer has a TransactionSignMachine for a 2-input tx (sigs.len() == 2).
// Malicious participant l submits a HashMap entry whose Vec<Preprocess> has len 1.
let mut commitments: HashMap<Participant, Vec<Preprocess<Secp256k1, ()>>> = ...;
commitments.insert(malicious_l, vec![honest_looking_preprocess]); // len 1 < sigs.len() 2
// sign() iterates c in 0..2; commitments[l][1] indexes out of bounds -> panic.
let _ = machine.sign(commitments, &[]); // thread panics, session aborted
```

Note: I could not fully verify whether higher-level callers (e.g., coordinator/processor crates) pre-validate these vectors before reaching `sign`/`complete`; the library-level API itself performs no such check.
