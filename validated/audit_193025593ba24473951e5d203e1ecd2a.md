### Title
Malicious repo content can make partial-stage/discard patches apply to the wrong hunk location via `git apply --unidiff-zero`, silently corrupting staged/committed content - (File: `app/src/lib/git/apply.ts`)

### Summary
The bug-class seed is: a downstream operation that trusts a derived, attacker-influenceable computation without validating that the computation still matches the caller's intent, so the operation either blocks or (worse) silently does the wrong thing. In GitHub Desktop, the analogous invariant is: "the patch built from the diff the user *saw and selected* must be applied to the exact lines the user selected." That invariant is only as strong as the context git uses to locate the hunk, and Desktop deliberately weakens that context by invoking `git apply` with `--unidiff-zero` when staging (`applyPatchToIndex`) and discarding (`discardChangesFromSelection`) partial selections.

### Finding Description
`applyPatchToIndex` and `discardChangesFromSelection` both build a hand-rolled unified diff via `formatPatch`/`formatPatchToDiscardChanges` in `app/src/lib/patch-formatter.ts` and feed it to `git apply --cached --unidiff-zero --whitespace=nowarn -` (`app/src/lib/git/apply.ts:52-58`, `115`). `formatPatch` reconstructs hunk headers with recomputed line counts (`formatHunkHeader`, `app/src/lib/patch-formatter.ts:86-111`) based on the *original* diff's line numbers (`hunk.header.oldStartLine` / `newStartLine`), not on a re-verified position in the current working-tree file.

Because the working directory content is git-tracked and can come from a cloned/fetched attacker-controlled repository (e.g. a file with intentionally duplicated blocks, templated boilerplate, or repeated lines), and because `git apply` resolves hunk placement using surrounding context, a patch generated with truncated/zero context (partial-selection patches routinely emit hunks whose context is very small, and `--unidiff-zero` explicitly tells `git apply` to tolerate hunks without the normal 3-line context) can match more than one location in the file. `git apply` does not fail in that case — it applies at the first/best fuzzy match it finds, which is not necessarily the line range the user visually selected in the diff viewer.

No guard in `applyPatchToIndex` or `discardChangesFromSelection` re-reads the resulting index/working file to confirm the intended lines were the ones modified; the functions simply resolve their promise on git's exit code [1](#0-0) , exactly mirroring the report's pattern of trusting an external call's success/failure without checking that the *value* it produced (here, "which lines got staged") matches the caller's assumption.

### Impact Explanation
If the patch is misapplied, the user unknowingly stages or discards different lines than what they selected in the UI. This is "silent corruption of what the user commits or pushes" — the exact impact class called out as valid: the working tree or index ends up containing changes the user never reviewed/approved, which can then be committed and pushed, propagating unintended or attacker-shaped content into the user's history without any error being surfaced.

### Likelihood Explanation
This requires a git-tracked file with repeating/duplicate line content (common in generated code, config files with repeated blocks, or a file crafted by a hostile repository author) combined with the user doing partial line-level staging/discarding (a core, everyday GitHub Desktop feature) on that file. No admin rights, local access, or prior malware are needed — only that the user opens/clones a repository containing such a file and interacts with the normal changes/diff UI. I could not fully verify from static reading alone how frequently `git apply`'s fuzzy matching actually diverges in this codebase's exact hunk-construction (that would require dynamic testing with crafted duplicate-content fixtures), so likelihood is asserted based on `git apply`'s documented fuzzy-context behavior combined with `--unidiff-zero` relaxing context requirements, not a confirmed reproduction in this session.

### Recommendation
- Avoid `--unidiff-zero` for hunks that do include context lines; only pass it when the hunk genuinely has zero context, or preserve full context in generated patches.
- After `git apply --cached`/`git apply`, verify the resulting index/working tree diff matches the intended selection (e.g., diff the new index state against the expected outcome) before treating the operation as successful, rather than trusting exit code alone.
- Consider using `git apply --recount --unidiff-zero=false` style safeguards, or fall back to `git apply --index --3way` semantics that fail loudly on ambiguous context instead of silently fuzzy-matching.

### Proof of Concept
1. Clone/open a repository containing a text file with a duplicated block, e.g. two identical `console.log("noop")` lines separated by unrelated content.
2. Modify only the second occurrence's surrounding lines so a diff hunk for that occurrence has minimal/no distinguishing context (small edit near line-count boundaries).
3. In the Changes view, select only the intended (second) line for partial staging via `applyPatchToIndex` → `formatPatch` → `git apply --cached --unidiff-zero`.
4. Inspect `git diff --cached` afterward: because the constructed hunk lacks enough unique context and `--unidiff-zero` relaxes context checking, `git apply` may resolve the hunk against the duplicate (first) occurrence instead of the one the user selected, staging/discarding the wrong line silently (no error is thrown by `applyPatchToIndex`, which only checks the git exit code) [2](#0-1) . export async function discardChangesFromSelection(
```typescript
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}
```

```typescript
function formatHunkHeader(
  oldStartLine: number,
  oldLineCount: number,
  newStartLine: number,
  newLineCount: number,
  sectionHeading?: string | null
) {
  // > @@ -l,s +l,s @@ optional section heading
  // >
  // > The hunk range information contains two hunk ranges. The range for the hunk of the original
  // > file is preceded by a minus symbol, and the range for the new file is preceded by a plus
  // > symbol. Each hunk range is of the format l,s where l is the starting line number and s is
  // > the number of lines the change hunk applies to for each respective file.
  // >
  // > In many versions of GNU diff, each range can omit the comma and trailing value s,
  // > in which case s defaults to 1
  const lineInfoBefore =
    oldLineCount === 1 ? `${oldStartLine}` : `${oldStartLine},${oldLineCount}`

  const lineInfoAfter =
    newLineCount === 1 ? `${newStartLine}` : `${newStartLine},${newLineCount}`

  sectionHeading = sectionHeading ? ` ${sectionHeading}` : ''

  return `@@ -${lineInfoBefore} +${lineInfoAfter} @@${sectionHeading}\n`
}
```

```typescript
export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })

  // If we get into this state we should never have been called in the first
  // place. Someone gave us a faulty diff and/or faulty selection state.
  if (!patch.length) {
    log.debug(`formatPatch: empty path for ${file.path}`)
    throw new Error(`Could not generate a patch, no changes`)
  }

  patch = formatPatchHeaderForFile(file) + patch

  return patch
}
```
