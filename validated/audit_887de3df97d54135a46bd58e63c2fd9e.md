## Title
Uncaught exception on malformed `git log --raw --numstat` output from a malicious repository crashes/corrupts commit history rendering - ([File: app/src/lib/git/log.ts])

## Summary
The tonlib advisory hardens parsers against malformed/attacker-supplied blockchain data so that untrusted input cannot crash the wallet daemon. The closest reachable analog in GitHub Desktop is `parseRawLogWithNumstat` in `app/src/lib/git/log.ts`, which parses `git log --raw --numstat -z` output using unguarded array indexing and a helper (`forceUnwrap`) that throws on any unexpected shape. Since this parser processes output derived directly from a cloned/fetched repository's commit and tree data, a maliciously crafted repository can produce raw/numstat lines that don't match the expected pattern, causing the parser to throw.

## Finding Description
`getChangedFiles` runs `git log -C -M -m -1 --no-show-signature --first-parent --raw --format=format: --numstat -z --` and hands the resulting stdout to `parseRawLogWithNumstat`: [1](#0-0) 

That function assumes strict alternation between `:`-prefixed raw lines and numeric numstat lines, and unwraps required fields with `forceUnwrap`, which throws `Error` on `undefined`: [2](#0-1) 

In particular:
- `lineComponents.at(-1)` is forced to be the status code without validating the raw line has the expected number of space-separated fields.
- The numstat branch uses `files[numStatCount]` and calls `isCopyOrRename(files[numStatCount].status)` without checking that `numStatCount` is in bounds relative to `files.length` — if the raw and numstat sections ever get out of sync (e.g., due to an unusual mode, a null/binary-file numstat line `-\t-\t` combined with unexpected extra `\0`-separated fields, or a crafted commit that manipulates rename/copy detection edge cases), this can index past the end of `files` and throw a `TypeError: Cannot read properties of undefined`.
- The regex `/^(\d+|-)\t(\d+|-)\t/` on numstat lines is matched with `forceUnwrap`, so any numstat line that git emits in a shape Desktop doesn't anticipate (e.g., paths containing tab characters if the OS/locale/emoji edge cases cause quoting differences, or a numstat line for a submodule/symlink change with an unexpected marker) throws immediately.

This mirrors the tonlib bug class: parsing of attacker/remote-controlled structured data without defensive bounds checks, where a crafted input can throw synchronously inside a parser that was assumed to only ever see well-formed data from a "friendly" git process.

## Impact Explanation
`getChangedFiles` is invoked from the history/commit-details UI (`app-store.ts`) whenever a user views a commit's changed files — this happens automatically when browsing history in a cloned repository, including a repository the user did not create. If the attacker can craft a commit (in a repo the victim clones, or a branch/PR they check out) whose raw diff/numstat output desynchronizes this parser, viewing that commit's file list throws an uncaught exception in the parsing path. Because this runs in Desktop's main/renderer git-invocation code (not inside a try/catch at this call site as verified), the failure surfaces as an unexpected error to the user, and in the worst case destabilizes the commit-history and diff-rendering flow (denial of a specific feature / instability), rather than a silent corruption of what the user commits. This is bounded by the fact that `parseRawLogWithNumstat` operates on read-only display data (it doesn't write to disk or execute code), so this does not on its own achieve code execution or credential exfiltration — the severity is a hardening/robustness gap, not a memory-safety or RCE bug, similar in spirit (but not in impact ceiling) to what tonlib fixed for its own untrusted-input parsers.

## Likelihood Explanation
Likelihood is limited because it requires an attacker to control a specific, unusual git raw/numstat line shape that git itself may not normally emit, and the exact bypass of the `files[numStatCount]` bookkeeping (rename/copy detection heuristics, submodule and mode-change interactions) needs further empirical validation against `dugite`/git's actual raw output grammar — I could not confirm from static reading alone that a real crafted commit can desynchronize the counter in the current codebase (this needs test/fuzz confirmation with actual git-produced edge cases, which requires runtime experimentation I don't have tool access for in this session). The finding is included because the code path itself lacks any bounds checking or try/catch around a parser consuming untrusted repository content, which is the exact invariant class described in the report; verifying an exploitable input concretely would require running git against a crafted tree/commit and observing the exact raw/numstat output.

## Recommendation
- Add bounds checks before indexing `files[numStatCount]` in `parseRawLogWithNumstat`, returning/skipping gracefully (or throwing a clearly scoped, caught `GitError`-style exception) instead of allowing `TypeError` from `undefined` access.
- Replace `forceUnwrap` usage in this hot parsing path with defensive parsing that treats any unexpected line shape as "skip and log", consistent with how `status-parser.ts`'s `parseUnmergedEntry` already logs and throws a scoped error rather than crashing on an internal `undefined` dereference.
- Wrap `getChangedFiles`/`parseRawLogWithNumstat` calls at the UI-facing call sites (`app-store.ts`) in `performFailableOperation`-style handling (already used elsewhere in the store) so a malformed commit cannot escape as an unhandled exception up through the renderer.

## Proof of Concept
Concrete PoC not established — this requires crafting a repository whose commits produce raw/numstat lines that desynchronize the `numStatCount` bookkeeping (e.g., via unusual submodule, symlink-to-file, or mode-only changes interacting with rename/copy detection), which needs to be validated empirically by running `git log -C -M -m -1 --raw --numstat -z` against a hand-built repo and confirming the parser throws. I was unable to execute git or run the parser in this session to confirm a working malformed input; a background engineering session with terminal access would be needed to construct and verify the exact commit tree that triggers the out-of-bounds access.

/** Get the files that were changed in the given commit. */
export async function getChangedFiles(
  repository: Repository,
  sha: string
): Promise<IChangesetData> {
  // opt-in for rename detection (-M) and copies detection (-C)
  // this is equivalent to the user configuring 'diff.renames' to 'copies'
  // NOTE: order here matters - doing -M before -C means copies aren't detected
  const args = [
    'log',
    sha,
    '-C',
    '-M',
    '-m',
    '-1',
    '--no-show-signature',
    '--first-parent',
    '--raw',
    '--format=format:',
    '--numstat',
    '-z',
    '--',
  ]

  const { stdout } = await git(args, repository.path, 'getChangesFiles')
  return parseRawLogWithNumstat(stdout, sha, `${sha}^`)
}

export function parseRawLogWithNumstat(
  stdout: string,
  sha: string,
  parentCommitish: string
) {
  const files = new Array<CommittedFileChange>()
  let linesAdded = 0
  let linesDeleted = 0
  let numStatCount = 0
  const lines = stdout.split('\0')

  for (let i = 0; i < lines.length - 1; i++) {
    const line = lines[i]
    if (line.startsWith(':')) {
      const lineComponents = line.split(' ')
      const srcMode = forceUnwrap(
        'Invalid log output (srcMode)',
        lineComponents[0]?.replace(':', '')
      )
      const dstMode = forceUnwrap(
        'Invalid log output (dstMode)',
        lineComponents[1]
      )
      const status = forceUnwrap(
        'Invalid log output (status)',
        lineComponents.at(-1)
      )
      const oldPath = /^R|C/.test(status)
        ? forceUnwrap('Missing old path', lines.at(++i))
        : undefined

      const path = forceUnwrap('Missing path', lines.at(++i))

      files.push(
        new CommittedFileChange(
          path,
          mapStatus(status, oldPath, srcMode, dstMode),
          sha,
          parentCommitish
        )
      )
    } else {
      const match = /^(\d+|-)\t(\d+|-)\t/.exec(line)
      const [, added, deleted] = forceUnwrap('Invalid numstat line', match)
      linesAdded += added === '-' ? 0 : parseInt(added, 10)
      linesDeleted += deleted === '-' ? 0 : parseInt(deleted, 10)

      // If this entry denotes a rename or copy the old and new paths are on
      // two separate fields (separated by \0). Otherwise they're on the same
      // line as the added and deleted lines.
      if (isCopyOrRename(files[numStatCount].status)) {
        i += 2
      }
      numStatCount++
    }
  }

  return { files, linesAdded, linesDeleted }
}
