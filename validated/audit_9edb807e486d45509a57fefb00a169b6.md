### Title
Unauthenticated `Option::unwrap` panic in `GeneratorPromotion::complete` enables remote DoS via a proof map keyed to the victim's own index - (File: crypto/dkg/promote/src/lib.rs)

### Summary
`GeneratorPromotion::complete` takes a `HashMap<Participant, GeneratorProof<C1>>` supplied by other participants. It validates only (a) `proofs.len() == n - 1` and (b) every key `<= n`. It never checks that the map contains every expected participant, nor that it excludes the victim's own index `params.i()`. A malicious participant can therefore include their proof keyed to the victim's index `i` while omitting some other participant `j`. The length check still passes (n-1 entries), all keys pass `<= n`, and then `proofs.get(&i).unwrap()` at the `for i in 1..=n` loop hits `None` for the missing `j` and panics — analog of CVE-2015-8767's attacker-triggerable denial of service, but expressed as a crash reachable from untrusted peer input.

### Finding Description
In `crypto/dkg/promote/src/lib.rs`, `complete` iterates `1 ..= params.n()` and unconditionally unwraps:

```rust
// crypto/dkg/promote/src/lib.rs:125-146
if proofs.len() != (usize::from(params.n()) - 1) { ... }   // count check only
for i in proofs.keys().copied() {
  if u16::from(i) > params.n() { ... }                    // range check only
}
...
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() { continue; }
  let proof = proofs.get(&i).unwrap();                    // panics on missing key
```

Two issues combine:

1. **Missing-key panic**: the map's key set is never compared against `all_participant_indexes() \ {i}` (contrast with `validate_map` used in PedPoP's `calculate_share` and FROST's `sign`/`complete`, which enforce exact-set membership). Any map of `n-1` distinct keys all `<= n` that does not equal the expected set — e.g., containing the victim's own `i` or duplicated-logically entries — reaches the `unwrap()` with `None`.
2. **Self-key acceptance**: a proof keyed to `params.i()` is never rejected; it is simply never queried, silently displacing a required proof and guaranteeing the panic.

### Impact Explanation
Generator promotion is executed after a DKG when rotating the validator set's keys to a new generator. Each participant broadcasts a `GeneratorProof` (a `DLEqProof` + share point). A single malicious or faulty participant submits a correctly-sized proof map containing a proof under the victim's `Participant` index instead of their own (or omits another participant's entry). Every honest node that calls `complete` on that map panics on an `unwrap` — aborting the key-rotation flow and crashing the task. Since `complete` runs on the honest side with attacker-controlled map contents, this is a remotely triggerable denial of service by an unprivileged protocol participant, matching the CVE's "crafted call → DoS" class.

### Likelihood Explanation
Any participant in the promotion ceremony controls the key under which their `GeneratorProof` is inserted (the map is constructed by the caller from received messages). Supplying a proof keyed to a valid-but-wrong `Participant` requires no special privileges and passes all existing validation. Only one faulty participant is needed to crash every completing node.

### Recommendation
Before iterating `1 ..= params.n()`, validate the key set exactly: reject if `proofs` contains `params.i()`, or use the existing `validate_map` helper (`crypto/dkg`) with `all_participant_indexes()` minus self, mirroring how `calculate_share` in `crypto/dkg/pedpop/src/lib.rs` validates the shares map. Alternatively, replace `proofs.get(&i).unwrap()` with `.ok_or(PromotionError::MissingProof(i))`.

### Proof of Concept
