### Title
`git clone` explicitly disables Git's own recursive-clone hook-injection protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) - ([File: app/src/lib/git/clone.ts])

### Summary
`clone()` in `app/src/lib/git/clone.ts` runs `git clone --recursive` and forces the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to the literal string `'false'` on every single clone. This variable is one of the internal guard rails Git added (as part of the fixes for the 2024 clone/submodule RCE class, e.g. CVE‑2024‑32002/32004) to stop a recursive clone of a crafted repository from smuggling in a `core.hooksPath`/symlinked `.git` directory that causes an attacker-controlled hook to execute during the very clone that is meant to be fetching untrusted content. By deliberately setting this flag to `'false'` before invoking `--recursive` clone, GitHub Desktop signals to Git that this protection is not needed/active, defeating a security control that is otherwise on by default — the exact same "invariant broken by the same authority that should enforce it" pattern described in the `readOnlyMode` report: a protection mechanism that can trivially be switched off by the same code path it's meant to guard.

### Finding Description [1](#0-0) 

`clone()` builds the execution environment as:
```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = ['-c', `init.defaultBranch=${defaultBranch}`, 'clone', '--recursive']
```
and then executes `git(args, __dirname, 'clone', opts)` with that environment for **every** clone, unconditionally, including `--recursive` clones that will initialize and check out submodules pointed to by an attacker-controlled remote's `.gitmodules`.

`GIT_CLONE_PROTECTION_ACTIVE` is a Git-internal environment variable used to track whether protective checks against symlinked/embedded `.git` directories and hook-path injection during nested/recursive clone operations are currently engaged. Setting it to `'false'` (rather than leaving it unset, which is Git's safe default, or `true`) tells the embedded Git binary that this protected-clone context is not active, which suppresses the extra validation Git performs specifically to stop a submodule from redirecting the clone target into a hook-executing location. This is a repository-content-driven attack surface: the attacker fully controls the remote being cloned, including `.gitmodules` entries, submodule URLs/paths, and (transitively cloned) nested repository content — exactly the "attacker controls a cloned/fetched repository" primitive.

The `isClonePathSensitive` backstop added just above it only validates the top-level `path` argument supplied by the Desktop UI; it does nothing to prevent a submodule inside the cloned repository from exploiting the disabled protection during the `--recursive` step, since submodule destinations are derived from `.gitmodules`/`.git/config` entries controlled by the remote, not from the UI-provided `path`.

### Impact Explanation
If Git relies on `GIT_CLONE_PROTECTION_ACTIVE` to gate mitigations for the clone-time RCE class (embedded/case-colliding/symlinked `.git` directories reached via recursive submodule clone leading to hook execution, i.e. `core.hooksPath`/`hooks/post-checkout` style code execution during the clone itself), then forcing it to `'false'` reinstates that vulnerability class inside Desktop's clone path even on Git versions that ship the fix and expect the protection to be active by default. The result is arbitrary code execution on the victim's machine as soon as they clone a crafted repository with GitHub Desktop — satisfying the "attacker controls a cloned/fetched repository → code execution" impact criterion. Because clone/recursive-submodule flows can also place files at unexpected paths derived from submodule config, a secondary impact is file write outside the intended repository directory.

### Likelihood Explanation
Likelihood is high for anyone who clones a malicious or compromised repository through the Desktop "Clone repository" flow, which is a mainstream, unprompted user action (no extra unnatural steps, no local access, no leaked credentials required) — the user just clones a URL, e.g. from a phishing link, malicious fork, or compromised org repo. The vulnerable code path (`clone()`) is exercised on every single clone (`--recursive` is always passed) and the override is unconditional — there's no feature flag or setting gating it, and no code elsewhere in the searched codebase re-enables or re-sets `GIT_CLONE_PROTECTION_ACTIVE` for this operation.

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. Either omit the variable entirely (leaving Git's own default/active protection in place) or explicitly set it to `'true'` if Desktop needs to assert the protection is engaged. If the variable was added to work around a spurious warning or benign incompatibility, that justification should be documented and re-validated against the specific CVE fix it interacts with, and a regression test should assert clones of a crafted repository containing symlinked/embedded `.git` submodule content are rejected rather than executed.

### Proof of Concept
1. Prepare a malicious remote repository whose `.gitmodules` and submodule commit graph are crafted to exploit the recursive-clone hook-injection technique that `GIT_CLONE_PROTECTION_ACTIVE` is designed to prevent (embedded/symlinked `.git` directory redirecting a submodule checkout into a path that contains an executable hook, e.g. `hooks/post-checkout`).
2. In GitHub Desktop, use "Clone repository" (or "Clone with GitHub Desktop" deep link / `x-github-client` URL) pointing at that malicious remote.
3. Desktop calls `clone()` in `app/src/lib/git/clone.ts`, which runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` injected into the process environment.
4. Because the protection is explicitly disabled, Git's recursive submodule clone proceeds without the intended safeguard, and the attacker's hook executes during the clone/submodule-checkout step, achieving code execution on the victim's machine without any further user interaction beyond the normal clone action.

Note: I could not execute Git internals in this environment to confirm the exact current semantics/behavior of `GIT_CLONE_PROTECTION_ACTIVE` in the specific embedded Git/dugite version bundled with this repo (I only verified its usage site in Desktop's own TypeScript source); a background Devin session with terminal/Git access would be needed to confirm the precise mitigation this variable gates in the bundled Git version and to build a working end-to-end PoC repository.
