The bug class is a degenerate lower-bound check (`> 0` instead of `>= minimum`). Let me look at the in-scope validation paths — bitcoin wallet scanner/output handling and FROST parameter checks.### Title
Scanner reports economically unspendable dust outputs as received funds - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to the report's `rd > 0` check (which accepts any non-expired lock rather than enforcing the required minimum duration), `Scanner::scan_transaction` accepts any output paying to a registered `script_pubkey` with no minimum value check. Outputs below the dust threshold — including outputs whose value cannot cover the cost of the signature needed to spend them — are returned as `ReceivedOutput`, a type documented as "A spendable output", and flow into the processor's balance accounting as if they were spendable funds.

### Finding Description
`Scanner::scan_transaction` matches outputs purely on `output.script_pubkey` membership in `self.scripts` and pushes a `ReceivedOutput` for every match without inspecting `output.value` [1](#0-0) . The struct is declared as "A spendable output" [2](#0-1) , yet no spendability bound is enforced.

The codebase does define the relevant minimum elsewhere: `DUST = 546` in `send.rs` [3](#0-2) , enforced for payments (`*amount < DUST` → `DustPayment`) [4](#0-3)  and for change (`value >= DUST`) [5](#0-4) . The receive path never applies an equivalent bound. Further, the processor bills each aggregated output `COST_TO_AGGREGATE = 800` sat [6](#0-5) , so any output below that cost is net-negative: reporting it as received value is incorrect.

### Impact Explanation
An unprivileged attacker can send dust (1–545 sat, or even near-dust amounts below `COST_TO_AGGREGATE`) to the multisig's external/branch/change P2TR addresses. `get_outputs` feeds these through `scan_transaction` into `Output` objects credited by the batch logic [7](#0-6) . The result is funds reported as received that are not spendable at a profit: each such output either cannot be relayed when re-created or costs more in signature fees than its face value, inflating accounted balances and forcing the multisig to subsidize spending worthless inputs. This mirrors the original bug's impact — the acceptance predicate validates existence/non-expiry rather than the protocol-required minimum.

### Likelihood Explanation
Anyone can craft a transaction paying an arbitrary amount to a known multisig script; sub-dust outputs are consensus-valid (non-standard only for relay, easily mined or sent to the internal branch/change addresses which the multisig itself creates). No collusion, validator status, or key material is required — only a Bitcoin transaction the attacker causes to be created, which is squarely within the permitted attack surface.

### Recommendation
Apply the required minimum on the receive path, matching how the send path enforces it: in `Scanner::scan_transaction` (or in `Bitcoin::get_outputs`), skip outputs whose `value.to_sat() < DUST` — or, to reflect actual economics, below the per-input spend cost (`COST_TO_AGGREGATE`). At minimum, `ReceivedOutput` should not be constructed for outputs that can never satisfy `SignableTransaction`'s own constraints without other funds subsidizing them.

### Proof of Concept
```rust
// Attacker tx: one output paying 1 sat (or 0 sat) to the multisig's P2TR script
let tx = Transaction {
  version: Version(2),
  lock_time: LockTime::ZERO,
  input: vec![/* any spendable input of the attacker */],
  output: vec![TxOut {
    value: Amount::from_sat(1), // below DUST, far below COST_TO_AGGREGATE
    script_pubkey: p2tr_script_buf(multisig_key).unwrap(),
  }],
};

// scan_transaction returns a ReceivedOutput despite the output being
// unspendable at a profit
let outputs = scanner.scan_transaction(&tx);
assert_eq!(outputs.len(), 1);
assert_eq!(outputs[0].value(), 1); // reported as received funds
```
The `ReceivedOutput` is then consumed by `Bitcoin::get_outputs` → `Output { kind, output, .. }` and credited in the batch, even though spending it requires ~800 sat of fee for 1 sat of value.

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```
