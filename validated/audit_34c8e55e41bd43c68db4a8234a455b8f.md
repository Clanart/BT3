Unauthenticated encryption-key registration lets a DKG participant redirect other participants' secret shares to a key they don't own — shares are delivered decryptable by an unintended actor - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`EncryptionKeyMessage` carries a participant's long-term encryption public key `enc_key` with **no proof of possession**. `Decryption::register` / `Encryption::register` store whatever `enc_key` a participant broadcasts, and `SecretShareMachine::generate_secret_shares` encrypts each secret share to `enc_keys[recipient]` via ECDH. A malicious participant Eve can register a public key whose private key is held by a different party Alice (e.g. copy Alice's `enc_key` from Alice's broadcast commitments message). Every honest dealer then encrypts Eve's share `f_i(Eve)` to *Alice's* key — exactly the reported bug class: secret material is forwarded to an endpoint other than the one the sender intended, because the credential (here the decryption key standing in for the Authorization-bearing identity) is not bound to its claimed origin. ### Finding Description
- `Encryption::registration` wraps the commitments message with `self.enc_pub_key` and no signature/PoK over it: `EncryptionKeyMessage { msg, enc_key: self.enc_pub_key }` [3](#0-2) .
- `Decryption::register` blindly inserts `msg.enc_key` keyed by participant index; the only integrity check is `assert!(!contains_key)` [2](#0-1) .
- `verify_r1` validates only the Schnorr PoK on `commitments[0]` (`msg.sig.batch_verify(..., msg.commitments[0], challenge(..., &msg.cached_msg))`); `cached_msg` contains only the commitment points, so the challenge never commits to `enc_key` [4](#0-3) .
- `encrypt` computes `ecdh(key, to)` where `to = self.decryption.enc_keys[&participant]`, i.e. the attacker-supplied key [5](#0-4) [6](#0-5) .
- The per-message PoP added to fix the *transposed* variant of this attack only authenticates the per-message ephemeral key `msg.key`, not the registered `enc_key` [7](#0-6) . The spec's own threat discussion acknowledges key-co-option leaks via blame yet only mitigates it at the per-message layer [8](#0-7) .

### Impact Explanation
Because shares for Eve are encrypted to Alice's private key, anyone holding that key (Alice — who need not behave maliciously at all) can decrypt every `EncryptedMessage` addressed to Eve as soon as it is published/relayed (the blame design requires these ciphertexts be reproducible to third parties via `AdditionalBlameMachine`/`VerifyBlame`, so they are not private to Eve) [9](#0-8) . Alice thereby learns `f_i(Eve)` for every participant `i`, in addition to her own `f_i(Alice)`. For a `t=2` threshold (e.g. 2-of-3 multisigs), two points per degree-1 polynomial let Alice reconstruct every dealer's polynomial and sum the constant terms — recovering the **entire group secret key** with only a single malicious participant (Eve), strictly below the `t`-of-`n` threshold security bound. For larger `t`, each honest party's share confidentiality is still violated, eroding the threshold margin. This is secret-key/share recovery — the maximal-impact class.

### Likelihood Explanation
Reachable by an unprivileged DKG participant using only public inputs: Eve broadcasts a syntactically valid `EncryptionKeyMessage` (parsed by `EncryptionKeyMessage::read`) whose `enc_key` field is copied verbatim from Alice's broadcast message. No cryptographic break is needed — the copied point is a valid non-identity group element and passes `C::read_G`. Detection is plausible only after the fact (Eve cannot produce a blame proof and will be faulted on complaint), but by then Alice has already passively decrypted Eve's shares; the leak is irreversible.

### Recommendation
Bind `enc_key` to its registrant at registration time: extend `EncryptionKeyMessage`/`Commitments` with a Schnorr proof of possession over the encryption key (challenge transcripting `context`, participant index, `enc_key`, and `cached_msg`), verified in `verify_r1` alongside the existing coefficient PoK. Alternatively, derive `enc_key` deterministically from `commitments[0]` or fold `enc_key` into the existing PoK `challenge` so substitution is impossible.

### Proof of Concept
1. Participants `Alice=1`, `Eve=2`, `Bob=3` run `KeyGenMachine::generate_coefficients` with `ThresholdParams::new(2, 3, i)` (t=2).
2. Eve observes Alice's broadcast `EncryptionKeyMessage` and broadcasts her own commitments message with `enc_key` replaced by Alice's `enc_pub_key`. `verify_r1` accepts it — the PoK covers only the polynomial commitments.
3. Alice and Bob each call `generate_secret_shares`, producing `EncryptedMessage` ciphertexts for Eve encrypted under `ecdh(ephemeral_key, Alice_enc_pub_key)`.
4. Alice reads the public ciphertext addressed to Eve, computes `ecdh(alice_enc_key, msg.key)`, applies `cipher(context, key)`, and recovers `f_Alice(Eve)` and `f_Bob(Eve)`. She already holds `f_Alice(Alice)` and `f_Bob(Alice)`.
5. With two points on each degree-1 polynomial, Alice Lagrange-interpolates both polynomials, evaluates at x=0, and sums the constant terms to obtain the full group private key — without Eve's cooperation and below the threshold adversary bound.

While key reuse by a participant is considered as them revealing the messages
themselves, and therefore out of scope, there is an attack where a malicious
adversary claims another participant's encryption key. They'll fail to encrypt
their message, and the recipient will issue a blame statement. This blame
statement, intended to reveal the malicious adversary, also reveals the message
by the participant whose keys were co-opted. To resolve this, a
proof-of-possession is also included with encrypted messages, ensuring only
those actually with per-message keys can claim to use them.
