### Title
Float-based NFT royalty calculation in CLI can under/overstate requested royalty amounts vs. consensus-safe integer calculation - ([File: chia/cmds/wallet_funcs.py])

### Summary
`chia/cmds/wallet_funcs.py`'s `calculate_nft_royalty_amount()` computes the royalty amount using Python floating-point division (`amount * percentage / 10000`) instead of the integer arithmetic used everywhere else in the wallet's royalty logic (`compute_royalty_amount()` in `chia/wallet/nft_wallet/nft_wallet.py`, which explicitly uses `//` and is annotated "Compute royalty using integer arithmetic, validating against overflow"). This mirrors the reported REEF bug class: a division that can lose precision for large integer amounts, producing a royalty value that differs from the value the trade-manager/offer-settlement path will actually enforce. [1](#0-0) [2](#0-1) 

### Finding Description
`calculate_nft_royalty_amount()` is used by the `make_offer` CLI flow to display/plan the royalty amount and total requested amount for an NFT trade before the actual offer is created via `create_offer_for_ids` / `wallet_client.nft_calculate_royalties`:

```
royalty_amount: uint64 = uint64(amounts[0][1] * nft_royalty_percentage / 10000)
``` [3](#0-2) 

This performs true (floating point) division rather than integer floor division. Python `float` has only 53 bits of mantissa; once `amount * percentage` exceeds `2**53` (easily reached for XCH/CAT amounts denominated in mojos, e.g. any offer above roughly 9 million mojos at max royalty), the multiplication/division result silently rounds to the nearest representable float, which can differ from the exact integer result that the consensus-safe `compute_royalty_amount()` computes and that the NFT trade manager (`chia/wallet/nft_wallet/nft_wallet.py:840-934`, `992-1032`) actually uses when constructing the real offer's `CreateCoin` royalty payments and trade prices.

The actual on-chain/offer-construction path already fixed this exact class of bug by using strict integer math with explicit overflow/percentage validation:

```
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
royalty = uint64(amount)
``` [4](#0-3) 

but the CLI-side `calculate_nft_royalty_amount()` was not updated to match, so it can mispresent (understate or overstate) the true royalty/total amount to a user constructing or reviewing an offer via the CLI, in the same way the Sqwid contract's division caused a mismatch between what a user sent and what the contract actually processed.

### Impact Explanation
Because the CLI's `calculate_nft_royalty_amount()` is only used for local pre-flight summarization in `wallet_funcs.py` (I could not find it feeding into `offer_dict`/`driver_dict` sent to `create_offer_for_ids`, only into the printed/computed `total_amount_requested` return value used in caller logic), the immediate blast radius is limited to a wallet user being shown or acting on an incorrect royalty total when constructing an offer from the CLI. This is a Medium-severity issue: it can cause a maker to under-fund the CAT/XCH side of a royalty-bearing NFT offer (leading to an offer that fails to complete or completes with a different royalty payout than displayed), rather than a direct on-chain fund theft, since the authoritative integer computation still happens in the trade manager (`compute_royalty_amount`) before the real spend bundle is built.

### Likelihood Explanation
Triggering the float precision loss requires an NFT offer/request whose `amount * royalty_percentage` product exceeds `2**53` (~9.007×10^15), which is realistically reachable for XCH-denominated offers in mojo units (1 XCH = 10^12 mojos) combined with a nontrivial royalty percentage (e.g., an offer of a few thousand XCH at a modest royalty bps). Any user/CLI caller constructing or reviewing such an offer would hit this discrepancy without any special privileges — a normal wallet CLI user is enough to reach this path.

### Recommendation
Change `calculate_nft_royalty_amount()` in `chia/cmds/wallet_funcs.py` to use integer arithmetic consistent with `compute_royalty_amount()`:
```
royalty_amount: uint64 = uint64(amounts[0][1] * nft_royalty_percentage // 10000)
```
and ideally have it delegate to (or duplicate exactly) `compute_royalty_amount()`'s overflow/percentage-bound checks so the CLI-reported figures always match what the trade manager will actually enforce on-chain.

### Proof of Concept
Not independently reproduced in this session (no execution environment available); the precision-loss mechanism is demonstrable purely from Python semantics: for `amounts[0][1] = 10_000_000_000_000_000` (10 quadrillion mojos) and `nft_royalty_percentage = 500` (5%), `10_000_000_000_000_000 * 500 / 10000` in float arithmetic can lose the low-order bits relative to the exact integer result `10_000_000_000_000_000 * 500 // 10000 == 500_000_000_000_000`, whereas `compute_royalty_amount(offered_amount=-10_000_000_000_000_000, royalty_split=1, percentage=500)` (integer path) is exact per the existing tests in `chia/_tests/wallet/nft_wallet/test_nft_royalty.py:35-39` (`test_large_amount_no_overflow`), confirming the two code paths can diverge for large amounts. I was unable to verify the exact numeric divergence magnitude or trace every downstream consumer of `calculate_nft_royalty_amount()`'s return value without running code; a background engineer should confirm the divergence with a concrete script and audit all call sites of this function to fully bound the impact.

def calculate_nft_royalty_amount(
    offered: dict[str, Any], requested: dict[str, Any], nft_coin_id: bytes32, nft_royalty_percentage: int
) -> tuple[str, int, int]:
    nft_asset_id = nft_coin_id.hex()
    amount_dict: dict[str, Any] = requested if nft_asset_id in offered else offered
    amounts: list[tuple[str, int]] = list(amount_dict.items())

    if len(amounts) != 1 or not isinstance(amounts[0][1], int):
        raise ValueError("Royalty enabled NFTs only support offering/requesting one NFT for one currency")

    royalty_amount: uint64 = uint64(amounts[0][1] * nft_royalty_percentage / 10000)
    royalty_asset_id = amounts[0][0]
    total_amount_requested = (requested[royalty_asset_id] if amount_dict == requested else 0) + royalty_amount
    return royalty_asset_id, royalty_amount, total_amount_requested
```

def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
