### Title
PedPoP `AdditionalBlameMachine::new` accepts commitment messages without the validation performed by `verify_r1`, enabling wrong blame attribution - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The PedPoP DKG has two entry points that consume the same untrusted `EncryptionKeyMessage<C, Commitments<C>>` round-1 messages. The primary path, `SecretShareMachine::verify_r1`, validates each message: it checks `msg.commitments.len() == t` and batch-verifies the Schnorr proof of knowledge before using the commitments. The parallel path, `AdditionalBlameMachine::new` — used by any third party adjudicating blame after the fact — performs neither check. It silently registers the messages and stores whatever commitments were provided, then `blame_internal` evaluates secret shares against them. A wrong-length or unauthenticated commitment vector flips the verdict of `share_verification_statements`, blaming an honest sender for a valid share or an honest recipient for correctly rejecting an invalid one.

### Finding Description
`verify_r1` (the participant path) enforces two checks on each round-1 commitment message before trusting it: [1](#0-0) 

`AdditionalBlameMachine::new` — the standalone auditor path reachable purely from public data (context, n, and the broadcast commitment messages) — registers the same message type with neither check: [2](#0-1) 

The resulting `commitments` map is then consumed by `blame_internal`, which judges a disputed share via `share_verification_statements::<C>(recipient, &self.commitments[&sender], share)`: [3](#0-2) 

`share_verification_statements` builds `exponential(target, commitments)` — a sum of `commitments[j] * target^j` over however many commitments exist — plus `-share*G`: [4](#0-3) 

If a malicious participant broadcast a commitment vector of length `t' != t` (fewer or more terms), `verify_r1` rejects it outright, but `AdditionalBlameMachine::new` accepts it. The auditor's `exponential` then reconstructs the wrong polynomial, so the zero-sum multiexp in `blame_internal` evaluates a statement that does not correspond to the share polynomial the rest of the network agreed on. Similarly, a commitment whose PoK signature is invalid (identity first-commitment trivially satisfies `batch_statements`, since `sG == R` when `A` is identity — see `schnorr/src/lib.rs` `batch_statements`/`verify`) is never screened on this path, so commitments that no honest participant would have accepted govern the verdict.

### Impact Explanation
Blame adjudication produces an incorrect verdict: `blame_internal` returns `sender` when the share was actually consistent with the honest commitments (share fails against the attacker's malformed/short commitment vector), or returns `recipient` — declaring the share "canonical and valid" — when it was not (attacker-supplied commitments that make a garbage share's statement sum to zero). In Serai's coordinator this misattributes a slashable fault to an honest party or exonerates the faulty one, an incorrect-verifier outcome caused entirely by attacker-controlled round-1 bytes fed to a public audit API.

### Likelihood Explanation
The audit path is intended to be callable by any observer with the transcript of the DKG, so the attacker only needs to have submitted a malformed `EncryptionKeyMessage` during round 1 (e.g., with the wrong commitment count or a forged PoK) and later force a blame evaluation. The check asymmetry is unconditional — `AdditionalBlameMachine::new` iterates `1 ..= n` and inserts commitments with no length or signature validation — so any dispute involving that participant's messages yields a verdict computed against unauthenticated data. It is partially mitigated only by the doc comment requiring callers to pre-verify messages, but the library provides no verified constructor, and the participant path demonstrates the checks are cheap and available.

### Recommendation
In `AdditionalBlameMachine::new`, replicate the `verify_r1` validation: check `msg.commitments.len() == t` for every participant (requires taking `ThresholdParams` or `t` rather than bare `n`) and batch-verify each `msg.sig` against `challenge::<C>(context, l, msg.sig.R.to_bytes().as_ref(), &msg.cached_msg)` with `msg.commitments[0]` as the public key, failing the constructor on any invalid PoK. Alternatively, refactor so both paths share a single `register_and_verify` routine.

fn exponential<C: Ciphersuite>(i: Participant, values: &[C::G]) -> Vec<(C::F, C::G)> {
  let i = C::F::from(u16::from(i).into());
  let mut res = Vec::with_capacity(values.len());
  (0 .. values.len()).fold(C::F::ONE, |exp, l| {
    res.push((exp, values[l]));
    exp * i
  });
  res
}

fn share_verification_statements<C: Ciphersuite>(
  target: Participant,
  commitments: &[C::G],
  mut share: Zeroizing<C::F>,
) -> Vec<(C::F, C::G)> {
  // This can be insecurely linearized from n * t to just n using the below sums for a given
  // stripe. Doing so uses naive addition which is subject to malleability. The only way to
  // ensure that malleability isn't present is to use this n * t algorithm, which runs
  // per sender and not as an aggregate of all senders, which also enables blame
  let mut values = exponential::<C>(target, commitments);

  // Perform the share multiplication outside of the multiexp to minimize stack copying
  // While the multiexp BatchVerifier does zeroize its flattened multiexp, and itself, it still
  // converts whatever we give to an iterator and then builds a Vec internally, welcoming copies
  let neg_share_pub = C::generator() * -*share;
  share.zeroize();
  values.push((C::F::ONE, neg_share_pub));

  values
