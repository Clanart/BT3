## Title
Webhook HMAC verification does not bind the signature to the shop domain, enabling cross-shop webhook replay/forgery - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
This is the same class of bug as the `LPTokenFactory.deployLPToken` replay finding: a signed payload is accepted without binding it to the "context" that distinguishes one principal from another. In the Solidity report, the missing `chain.id` let a signature/action be replayed on a different chain. In `shopify_app`, `ShopifyApp::WebhookVerification` computes and checks an HMAC over the **raw request body only**, and reads the `shop_domain` used to route/attribute the webhook from an **unauthenticated header** that is not part of the signed data. This missing binding lets an HMAC that is valid for shop A's webhook body be replayed with a forged `X-Shopify-Shop-Domain` header claiming to be shop B, exactly analogous to replaying a chain-agnostic signed payload across a different context.

### Finding Description
`ShopifyApp::PayloadVerification#hmac_valid?` computes the HMAC solely from `request.raw_post`: [1](#0-0) 

`ShopifyApp::WebhookVerification` uses this same `hmac_valid?(data)` (where `data = request.raw_post`) as the sole check before allowing the request to proceed, and separately exposes `shop_domain` read directly from the `HTTP_X_SHOPIFY_SHOP_DOMAIN` header, which plays no part in the HMAC computation: [2](#0-1) 

The generated/default webhook controllers then use this unauthenticated `shop_domain`/header value to route and attribute the webhook to a specific shop for job processing: [3](#0-2) [4](#0-3) 

Because the app's webhook secret (`ShopifyApp.configuration.secret`) is shared across every shop that installs the app (it's the app's client secret, not a per-shop secret), the HMAC only proves "this body was signed by someone who knows the app secret" — it proves nothing about which shop the event pertains to. The shop attribution comes entirely from the `X-Shopify-Shop-Domain` header, which is not covered by the signature. The test suite confirms this design: the header is set independently of the HMAC computation over `"{}"` in test fixtures: [5](#0-4) 

This mirrors the root cause in the reported analog: a signed action (`deployLPToken`) lacked a binding to the differentiating context (`chain.id`), so a valid signature/action for one chain could be replayed for another. Here, a valid HMAC for one shop's webhook body can be replayed with a forged shop-domain header to be attributed to a different shop.

### Impact Explanation
Any entity that can capture (or is legitimately sent) one genuine, correctly-signed webhook body for their own shop — which any unrelated merchant that installs the app can obtain simply by triggering a real webhook event on their own store — can replay that exact body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `hmac_valid?` will still pass because it only checks the body, and the downstream job/controller will process the (attacker-controlled, but originally Shopify-signed) payload under the victim shop's identity. Depending on the app's webhook handlers (e.g., `orders/create`, `app/uninstalled`, `shop/update`, mandatory privacy webhooks), this can lead to cross-shop data confusion, forged events being attributed to a shop that never sent them, or state changes (e.g., billing/plan updates, data deletion flows triggered by mandatory privacy webhooks) executed against the wrong shop.

### Likelihood Explanation
Moderate. It requires a merchant (unrelated to the victim) who has installed the app and can trigger/capture one legitimate webhook for their own store, then replay it directly via HTTP with a modified shop-domain header — no secret knowledge or privileged access is needed since HMAC verification is bypassed by design (the header isn't covered by the signature). This is fully reachable from an unrelated-merchant HTTP request as required by the validation rules.

### Recommendation
Include the shop domain (and topic/webhook id, to also prevent same-shop replay) as part of the data that is HMAC-verified, or otherwise cryptographically bind the `X-Shopify-Shop-Domain` header value to the signature before trusting it for job attribution — analogous to including `chain.id` in the signed payload in the original report. At minimum, `WebhookVerification#verify_request` should validate that the shop domain associated with a webhook's origin matches an expected/known installed shop before dispatching downstream jobs, rather than trusting an unauthenticated header value for attribution.

### Proof of Concept
1. Attacker (Shop A, a legitimate app install) receives a real Shopify webhook, e.g. `POST /webhooks` with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid, since Shopify signed it with the shared app secret) and `X-Shopify-Shop-Domain: shopA.myshopify.com`.
2. Attacker replays the same request to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: shopB.myshopify.com` (victim shop).
3. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which only checks `B` against `H` and the shared secret — it passes regardless of the shop-domain header, per `lib/shopify_app/controller_concerns/payload_verification.rb` lines 13-23 and `lib/shopify_app/controller_concerns/webhook_verification.rb` lines 15-21.
4. The controller dispatches the job using the (forged) shop attribution, e.g. `CartsUpdateJob.perform_later(shop_domain: webhook_request.shop, webhook: webhook_request.parsed_body)`, per `lib/generators/shopify_app/add_declarative_webhook/templates/webhook_controller.rb.tt` lines 7-10, processing shop A's captured webhook data as if it belonged to shop B.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

```ruby
# frozen_string_literal: true

module ShopifyApp
  module WebhookVerification
    extend ActiveSupport::Concern
    include ShopifyApp::PayloadVerification

    included do
      skip_before_action :verify_authenticity_token, raise: false
      before_action :verify_request
    end

    private

    def verify_request
      data = request.raw_post
      unless hmac_valid?(data)
        ShopifyApp::Logger.debug("Webhook verification failed - HMAC invalid")
        head(:unauthorized)
      end
    end

    def shop_domain
      request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]
    end
  end
end
```

```text
module Webhooks
  class <%= @controller_class_name %> < ApplicationController
    include ShopifyApp::WebhookVerification

    def receive
      webhook_request = ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
      <%= @job_class_name %>.perform_later(shop_domain: webhook_request.shop, webhook: webhook_request.parsed_body)
      head(:no_content)
    end
  end
```

class CustomWebhooksController < ApplicationController

  def carts_update

    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)

  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
