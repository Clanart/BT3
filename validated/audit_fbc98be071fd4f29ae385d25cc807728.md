### Title
Unvalidated attacker-controlled NFT metadata key causes unhandled `KeyError` crash in wallet NFT metadata-update processing - ([File: chia/wallet/nft_wallet/nft_puzzle_utils.py])

### Summary
`get_metadata_and_phs` processes conditions emitted by a spent NFT coin's inner puzzle to detect a metadata-update magic condition (`-24`) and applies it via `update_metadata` → `prepend_value`. `prepend_value` indexes the metadata dict directly with an attacker-supplied key without checking membership, causing an unhandled `KeyError` if the key is not one of the metadata dict's pre-existing keys.

### Finding Description
`update_metadata` decodes the on-chain condition and calls `prepend_value(uri.first().as_python(), uri.rest(), new_metadata)`: [1](#0-0) 

`prepend_value` then does `metadata[key] == b""` / `metadata[key].insert(...)` without ever checking `if key not in metadata`: [2](#0-1) 

The `key` originates from `uri.first().as_python()` inside a `-24` (metadata-update) condition that is entirely attacker-controlled — it comes from whatever inner puzzle solution the coin's holder or a maliciously-crafted spend supplies at line 244-247 of `get_metadata_and_phs`: [3](#0-2) 

`new_metadata` is built from `nft_program_to_metadata(metadata)`, whose keys are only whatever key/value pairs happen to exist in the previous NFT's curried metadata program (`nft_program_to_metadata`, line 140-149) — commonly a fixed, small set such as `b"u"`, `b"h"`, `b"mu"`, `b"lu"`, etc. Any `-24` condition presenting a key not already present in that dict (e.g., an entirely new/unknown key, or a coin whose metadata was minted without that key) triggers `KeyError` inside `prepend_value` when `metadata[key]` is evaluated on a missing key, since Python dictionary access does not silently fail like a `.get()` — it raises.

This is directly analogous to the freeradius CVE: an EAP-SIM peer sends an "unknown option" that is looked up in an internal dictionary; the lookup fails but the failure is never checked, and the code dereferences the invalid/absent entry, crashing the server. Here, an NFT-owning/spending party crafts an on-chain spend containing a `-24` condition with an unrecognized metadata key; the wallet processing this spend (via `get_metadata_and_phs`, called from `puzzle_solution_received` in `chia/wallet/nft_wallet/nft_wallet.py` and from `manual_nft_search` in `chia/wallet/wallet_state_manager.py`) looks the key up in the metadata dict without existence-checking, and the missing-key case is not handled — the exact same "unchecked-lookup-then-dereference" bug shape.

### Impact Explanation
This is reachable by any wallet that is *tracking* an NFT once a spend containing a malformed `-24` condition with an unrecognized metadata key is confirmed on-chain (or seen via sync) for that NFT coin. Processing that update causes an unhandled exception in the wallet sync/coin-processing path (`puzzle_solution_received`), which can abort NFT wallet sync and, depending on how the exception propagates through the wallet's coin-state processing loop, halt further processing of coin state updates for the wallet — a spend-triggered denial-of-service against a wallet client tracking that NFT. It does not, however, touch consensus-critical mempool/full-node code (both matched call sites are wallet-side, not full-node validation), so it is a wallet DoS rather than a network-wide halt.

### Likelihood Explanation
Likelihood is High: any party who can spend/update an NFT (the NFT owner, or in DID-transfer/owner-change flows a counterparty) can trivially construct an inner-puzzle solution producing a `-24` condition with an arbitrary metadata key, since the NFT state-layer puzzle imposes no on-chain validation restricting update keys to the pre-existing metadata key set. No special privileges beyond normal NFT-spending ability are required.

### Recommendation
In `prepend_value` (and correspondingly in `update_metadata`/`nft_program_to_metadata`), check for key membership before indexing, e.g. `if key not in metadata: metadata[key] = [value.as_python()]` else append/prepend as today, or use `metadata.setdefault(key, b"")` before the comparison. Wrap the metadata-update condition handling in `get_metadata_and_phs` with exception handling so a malformed/unknown update key is logged and ignored rather than propagating an unhandled exception into the wallet's coin-processing pipeline.

### Proof of Concept
1. Mint or acquire an NFT whose on-chain metadata program contains only the standard keys (e.g. `b"u"`, `b"h"`).
2. As the NFT's current owner (or via any spend path that reaches the NFT's p2/ownership inner puzzle), construct a solution that causes the inner puzzle to emit a condition `(-24 . (<unknown_key> . <uri>))`, e.g. key `b"zz"` which was never present in the original metadata.
3. Submit/confirm this spend on-chain.
4. Any wallet tracking this NFT coin will call `puzzle_solution_received` → `get_metadata_and_phs` → `update_metadata` → `prepend_value(b"zz", ..., new_metadata)`, which executes `metadata[b"zz"] == b""` on a dict lacking that key, raising an unhandled `KeyError` and aborting NFT coin-state processing for that wallet.

def prepend_value(key: bytes, value: Program, metadata: dict[bytes, Any]) -> None:
    """
    Prepend a value to a list in the metadata
    :param key: Key of the field
    :param value: Value want to add
    :param metadata: Metadata
    :return:
    """
    if value != Program.to(0):
        if metadata[key] == b"":
            metadata[key] = [value.as_python()]
        else:
            metadata[key].insert(0, value.as_python())

def get_metadata_and_phs(unft: UncurriedNFT, solution: SerializedProgram) -> tuple[Program, bytes32]:
    conditions = unft.p2_puzzle.run(unft.get_innermost_solution(Program.from_serialized(solution)))
    metadata = unft.metadata
    puzhash_for_derivation: bytes32 | None = None
    for condition in conditions.as_iter():
        if condition.list_len() < 2:
            # invalid condition
            continue
        condition_code = condition.first().as_int()
        log.debug("Checking condition code: %r", condition_code)
        if condition_code == -24:
            # metadata update
            metadata = update_metadata(metadata, condition)
            metadata = Program.to(metadata)
