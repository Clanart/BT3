## Analysis Summary

The reported bug class (fee-on-transfer / transfer-tax ERC20 tokens breaking 1:1 accounting between "amount specified" and "amount actually received") has a concrete analog in the Kaia service-chain bridge contracts, which are reachable by any unprivileged EOA calling a public transaction.

### Title
Fee-on-transfer ERC20 tokens cause accounting deficit and loss of user funds in the service-chain bridge - ([File: contracts/service_chain/bridge/BridgeTransferERC20.sol])

### Summary
`BridgeTransferERC20.requestERC20Transfer` and `onERC20Received` accept an ERC20 `_value` and `_feeLimit` from any caller and pull tokens via `safeTransferFrom`, but all downstream accounting (bridge fee payment, refund, burn, and the cross-chain `RequestValueTransfer` event that drives minting/unlocking on the counterpart chain) is computed from the nominal `_value`/`_feeLimit` parameters rather than the amount actually received by the contract. If the registered token charges a transfer fee (fee-on-transfer / transfer-tax token), the bridge will under-collect tokens relative to what it commits to release on the other chain, creating a persistent shortfall paid for by other bridge users.

### Finding Description
`requestERC20Transfer` transfers `_value.add(_feeLimit)` from the caller: [1](#0-0) 

It then calls `_requestERC20Transfer`, which pays the bridge fee and refunds any leftover fee limit, optionally burns tokens (mint/burn mode), and emits `RequestValueTransfer` carrying the nominal `_value`: [2](#0-1) 

The fee/refund logic in `BridgeFee._payERC20FeeAndRefundChange` transfers `fee` to the fee receiver and refunds `_feeLimit.sub(fee)` back to the sender purely based on the nominal `_feeLimit` value, with no check of the contract's actual token balance before/after the initial `safeTransferFrom`: [3](#0-2) 

On the counterpart chain, an operator calls `handleERC20Transfer` with the same nominal `_value`, which either mints new tokens or unlocks/transfers `_value` from that side's pool — regardless of how much was actually deposited on the source side: [4](#0-3) 

If the registered ERC20 token deducts a transfer fee on `transferFrom` (a common pattern for tokens such as fee-enabled stablecoins or deflationary/tax tokens), the bridge contract actually receives less than `_value.add(_feeLimit)`. Since the fee payment/refund and the cross-chain settlement amount are computed from the nominal, uncorrected `_value`, the bridge progressively accumulates a deficit between what it holds and what it has promised to release for pending/future withdrawals — directly mirroring the referenced Y2K `VaultV2` issue where minted shares/burn amounts don't reflect the real transferred balance.

### Impact Explanation
Because settlement on the counterpart chain (mint or unlock of the full nominal `_value`) is decoupled from the actual balance change in the source bridge contract, a token with even a small transfer fee will cause the bridge's real token balance to fall behind its committed liabilities. Over repeated deposits, this shortfall grows and eventually prevents legitimate users from withdrawing their full entitled balance — a direct loss of user funds, matching the "unauthorized value movement" / accounting-mismatch category.

### Likelihood Explanation
`requestERC20Transfer` and `onERC20Received` are `public`/reachable by any unprivileged transaction sender who holds and approves the registered token — no special privilege is required to trigger the deficit once such a token is registered (`registerToken` is `onlyOwner`, but many bridges list widely used tokens such as stablecoins that have historically activated transfer fees, e.g. USDT's fee-switch capability). Any ordinary depositor using such a token, even unintentionally, degrades the shared pool for all bridge users, and no on-chain check currently catches this.

### Recommendation
Measure the bridge contract's token balance before and after `safeTransferFrom` in `requestERC20Transfer`/`onERC20Received`, use the actual received delta for burn/lock accounting and for the `_value` propagated in `RequestValueTransfer`, and revert (or adjust) if the received amount differs from the expected `_value.add(_feeLimit)`.

### Proof of Concept
1. Owner registers a fee-on-transfer ERC20 token `T` (e.g., 1% transfer fee) via `registerToken`, with `modeMintBurn = false` (lock/unlock mode).
2. Alice calls `requestERC20Transfer(T, bob, 100, 0, "")`. `safeTransferFrom` attempts to pull 100 `T`, but the bridge contract actually receives only 99 `T` due to the token's fee.
3. `RequestValueTransfer` is emitted with `valueOrTokenId = 100` (nominal), not the 99 actually held.
4. An operator relays this to the counterpart chain, where `handleERC20Transfer` mints/unlocks 100 `T` to Bob.
5. Repeating this across many deposits accumulates a growing deficit between the source bridge's real token balance and its committed release amounts, so later withdrawers cannot be paid in full — funds effectively lost for other bridge users. [1](#0-0) [3](#0-2)

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
