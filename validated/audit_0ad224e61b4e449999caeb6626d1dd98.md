### Title
Wallet hang via circular coin-lineage in an untrusted Offer - (File: chia/wallet/trading/offer.py)

### Summary
`Offer.get_root_removal()` walks the `parent_coin_info` chain of coins contained in a `SpendBundle` that is embedded in an attacker-supplied offer file, using an unbounded `while` loop that assumes the chain always terminates at a "non-ephemeral" removal. Similar to CVE-2016-1981 (QEMU e1000 infinite loop caused by an unvalidated descriptor pointer that never reaches a terminating condition), a wallet user who opens a maliciously crafted offer can make this loop run forever because the coin lineage inside the offer is fully attacker-controlled and is never checked for cycles.

### Finding Description
`get_root_removal()` searches backward through a coin's `parent_coin_info` chain until it finds a coin that is a member of `non_ephemeral_removals` (removals whose parent is *not* itself a removal in the bundle): [1](#0-0) 

`non_ephemeral_removals` is computed purely from the `Coin` objects declared in the offer's own `SpendBundle` (`self.removals()`), which is attacker-controlled data taken directly from an offer file/RPC payload — the `parent_coin_info` field of a `Coin` is not validated against actual on-chain lineage before this walk happens, since these are candidate/unconfirmed coins from an offer, not confirmed coin records. If the attacker crafts two (or more) coin spends A and B in the bundle such that `A.parent_coin_info == B.name()` and `B.parent_coin_info == A.name()`, both A and B have their parent inside `all_removal_ids`, so **neither is ever added to `non_ephemeral_removals`**. The `while coin not in non_ephemeral_removals: coin = next(...)` loop then cycles between A and B forever with no termination condition and no cost/step limit.

This function is reached by `get_primary_coins()` and `get_pending_amounts()`: [2](#0-1) [3](#0-2) 

which are invoked by `trade_manager.py`/`trade_record.py` when a wallet displays, previews, or otherwise processes an incoming offer (e.g., before or during `take_offer`), i.e. from data supplied entirely by the offer's counterparty, without the wallet ever needing to broadcast or sign anything first.

### Impact Explanation
Because the coroutine/thread evaluating the offer spins forever in a pure-Python loop, it will hang the wallet process (or the async event loop it runs on) indefinitely, denying service to the wallet — the same infinite-loop-hang DoS class as the QEMU e1000 CVE, just reachable via an application-level state machine instead of a hardware descriptor ring. This does not, by itself, allow theft or forgery, but it satisfies the "spend-triggered transaction-processing halt" impact category since a crafted (never-broadcast) coin lineage inside an offer can hang the local wallet indefinitely.

### Likelihood Explanation
Any wallet user who opens/imports an offer file from an untrusted counterparty (a normal, expected wallet workflow) can trigger this: the attacker only needs to hand-craft a `SpendBundle` with two or more coin spends whose `parent_coin_info` fields point at each other. No signature validity or on-chain confirmation is required to reach `get_root_removal()`, since these coin lineage checks run on the raw offer content before/independent of chain validation.

### Recommendation
In `get_root_removal()` (and the `while True` loops in `get_cancellation_coins()`), track visited coin names and abort with a `ValueError`/`ValidationError` if a cycle is detected (i.e., if the loop would revisit a coin already seen), or bound the number of iterations to `len(all_removals)`.

### Proof of Concept
1. Craft an `Offer` whose `_bundle.coin_spends` contains two `CoinSpend`s, A and B, where `A.coin.parent_coin_info == B.coin.name()` and `B.coin.parent_coin_info == A.coin.name()` (both amounts/puzzle hashes otherwise arbitrary/valid CLVM so `run_with_cost` succeeds).
2. Ensure one of A/B (or a coin whose lineage traces to A/B) is returned by `get_offered_coins()`.
3. Call `offer.get_pending_amounts()` (or trigger the equivalent UI/RPC path that previews an incoming offer) — `get_root_removal()` enters `while coin not in non_ephemeral_removals: ...` and never terminates, hanging the calling thread/process.

```python
    def get_pending_amounts(self) -> dict[str, int]:
        all_additions: list[Coin] = self.additions()
        all_removals: list[Coin] = self.removals()
        non_ephemeral_removals: list[Coin] = list(filter(lambda c: c not in all_additions, all_removals))

        pending_dict: dict[str, int] = {}
        # First we add up the amounts of all coins that share an ancestor with the offered coins (i.e. a primary coin)
        for asset_id, coins in self.get_offered_coins().items():
            name = "xch" if asset_id is None else asset_id.hex()
            pending_dict[name] = 0
            for coin in coins:
                root_removal: Coin = self.get_root_removal(coin)

                for addition in filter(lambda c: c.parent_coin_info == root_removal.name(), all_additions):
                    pending_dict[name] += addition.amount

        # Then we gather anything else as unknown
        sum_of_additions_so_far: int = sum(pending_dict.values())
        unknown: int = sum(c.amount for c in non_ephemeral_removals) - sum_of_additions_so_far
        if unknown > 0:
            pending_dict["unknown"] = unknown

        return pending_dict
```

```python
    def get_root_removal(self, coin: Coin) -> Coin:
        all_removals: set[Coin] = set(self.removals())
        all_removal_ids: set[bytes32] = {c.name() for c in all_removals}
        non_ephemeral_removals: set[Coin] = {
            c for c in all_removals if c.parent_coin_info not in {r.name() for r in all_removals}
        }
        if coin.name() not in all_removal_ids and coin.parent_coin_info not in all_removal_ids:
            raise ValueError("The specified coin is not a coin in this bundle")

        while coin not in non_ephemeral_removals:
            coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)

        return coin
```
