### Title
Silent remote URL rewrite from an untrusted GitHub API `clone_url` field allows push-target hijacking - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` automatically rewrites a repository's `origin` remote URL based on the `clone_url` field returned by the GitHub API, without ever asking the user for confirmation. The decision to trust and apply this value is guarded only by string-based heuristics (`urlMatchesRemote`/`parseRemote`), not by any identity check tied to the immutable repository ID. This mirrors the paymaster bug's core flaw: an externally supplied, attacker-influenceable value (`clone_url` from the API) is trusted to silently trigger a consequential state change (rewriting where the user's `git push`/`fetch` goes) with only heuristic guardrails.

### Finding Description
`repositoryWithRefreshedGitHubRepository` re-fetches the repository object from the GitHub API on every refresh/fetch/push/pull cycle and unconditionally passes it into `updateRemoteUrl`: [1](#0-0) 

`updateRemoteUrl` then decides, purely from the API response, whether to rewrite the local `origin` remote: [2](#0-1) 

The only checks performed are:
- `protocolsMatch` — same URL scheme (`https`/`ssh`) as before,
- `remoteUrlUnchanged` — the current remote still matches the last known `cloneURL` cached from a *previous* API response,
- `!urlsMatch` — the new `clone_url` differs from the current remote.

None of these validate that the new `clone_url` still points to the *same* repository identity (e.g. by numeric repo ID); the match is purely regex-based hostname/owner/name parsing (`parseRemote` in `app/src/lib/remote-parsing.ts`). If `updateRemoteUrl`'s conditions are satisfied, it calls `gitStore.setRemoteURL`, which directly runs `git remote set-url` with no user prompt: [3](#0-2) 

This function is invoked as part of ordinary background/foreground operations — every fetch, pull, push, and repository refresh calls `withRefreshedGitHubRepository`, which triggers `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`: [4](#0-3) 

The corrupted value is the local git remote (`origin`) URL: it is silently replaced with whatever `clone_url` the API server chooses to return, as long as the scheme matches and the local remote hasn't been manually edited since the last cached value. On a compromised or malicious self-hosted GitHub Enterprise Server (a realistic "GitHub API object" attacker in Desktop's threat model, since Desktop trusts whatever the configured API endpoint returns), or any scenario where the attacker can influence the API's `clone_url` response for a repository the user already has cloned, Desktop will rewrite the user's push/fetch destination without any dialog, confirmation, or visible diff of the change.

### Impact Explanation
This is silent corruption of what the user pushes/fetches: subsequent `git push` operations from Desktop (`_performPush`, etc., which use `gitStore.defaultRemote`) will silently transmit the user's commits — potentially including secrets, proprietary code, or credentials embedded in the repo — to an attacker-controlled remote instead of the intended one. Because the rewrite happens transparently during routine background fetches, there's no clear signal to the user that their remote has changed. This satisfies the "silent corruption of what the user commits or pushes" impact category without requiring local access, admin rights, or social engineering — only that the attacker control an API response the user's Desktop instance already trusts (e.g., a rogue or compromised GHES deployment, matching the "GitHub API object" attacker class in scope).

### Likelihood Explanation
The exploit path requires no unusual user action: it fires automatically on any fetch/pull/push/refresh as long as (a) the local remote hasn't been manually edited since caching, and (b) the URL scheme is unchanged. For users of GitHub Enterprise Server (a supported, in-scope endpoint type in Desktop), a malicious or compromised server operator directly controls the `clone_url` returned by its API for any repository, making this trivially reachable. For GitHub.com, exploitation would require compromising the API response in transit, which is out of scope, but the GHES admin-controlled path is a legitimate and directly reachable analog matching the report's "no extra user action" attacker model.

### Recommendation
Do not silently rewrite the remote URL based on API data. At minimum:
- Tie repository identity checks to the immutable numeric repository `id` (already available from `IAPIRepository`) rather than string URL parsing, to avoid conflating a differently-hosted-but-similarly-named repository with the tracked one.
- Require explicit user confirmation (a dialog showing old vs. new URL) before calling `gitStore.setRemoteURL` in `updateRemoteUrl`.
- Log/notify the user prominently whenever an automatic remote URL change occurs.

### Proof of Concept
1. User clones a repository from a GitHub Enterprise Server and has it tracked in Desktop with `origin` pointing at `https://ghes.example.com/org/repo.git`.
2. The GHES instance (malicious or compromised) is later queried by Desktop's background refresh (`_fetch`/`_refreshRepository` → `repositoryWithRefreshedGitHubRepository`, `app/src/lib/stores/app-store.ts:4890`), returning an `IAPIRepository` object whose `clone_url` is set to `https://ghes.example.com/attacker/repo.git` (same host, same scheme, different owner/name).
3. `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts:42-44`) finds `protocolsMatch === true`, `remoteUrlUnchanged === true` (user never manually touched the remote), and `urlsMatch === false` (owner/name differ) — all conditions satisfied — and calls `gitStore.setRemoteURL('origin', 'https://ghes.example.com/attacker/repo.git')`.
4. The next time the user runs "Push" from Desktop, their commits are sent to `attacker/repo` instead of the intended repository, with no dialog or warning shown at any point in the flow. The existing unit tests confirm this exact automatic-rewrite behavior is by design and unguarded by user confirmation: [5](#0-4)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
