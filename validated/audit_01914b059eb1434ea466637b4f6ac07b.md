### Title
Retry-time baseline restore leaves a raced, advanced `baseline_sha` in place, letting a committed vulnerable change fall outside the next Stop review diff - (File: `plugins/security-guidance/hooks/diffstate.py`)

### Summary
`restore_unreviewed_stop_state` is called by `handle_stop_hook` when a Stop pass exits early after a transient failure (unreachable API, or a failed LLM call after `analyze_code_security` already ran) so the next Stop still reviews the unreviewed edits. It re-merges `touched_paths` but only restores `baseline_sha` when the in-state value is currently falsy, not when it has since been advanced by a racing `UserPromptSubmit` (UPS). Because the next Stop's review window is computed purely from `baseline_sha`/`head_at_capture` via `compute_v2_review_set` (not from `touched_paths`), a raced baseline advance causes the dangerous diff to be silently excluded from the next review.

### Finding Description
`handle_stop_hook` snapshots session state via `consume_stop_state`, which clears `touched_paths` on disk but leaves `baseline_sha`/`head_at_capture` untouched [1](#0-0) . The Stop hook is documented as `asyncRewake` — it runs in the background after Claude's turn ends, and the user can submit the next prompt (triggering UPS) while the current Stop pass is still running its LLM calls, e.g. inside `analyze_code_security` [2](#0-1) .

`handle_user_prompt_submit` decides whether to preserve the old baseline based solely on whether `touched_paths` is currently non-empty *and* `baseline_sha` is set: [3](#0-2) 
Since `consume_stop_state` already cleared `touched_paths` for the in-flight Stop pass, a UPS that fires before that Stop pass finishes sees `touched_paths == []`, so the preservation guard does **not** trigger — UPS overwrites `baseline_sha`/`head_at_capture` with a fresh baseline reflecting the current (already-advanced) HEAD/worktree, which now includes the dangerous, not-yet-reviewed change.

When the delayed Stop pass finally hits its failure path (`ensure_anthropic_reachable()` failing, or `llm._last_call_claude_http_error` after the LLM call), it calls `restore_unreviewed_stop_state(session_id, touched_paths, snap_baseline)` [4](#0-3) . That function merges `touched_paths` back in, but only writes back `baseline_sha` if the state's current value is falsy: [5](#0-4) 
Because UPS already wrote a non-null (advanced) `baseline_sha`, this condition is false, so the stale/older `snap_baseline` is **not** restored — the advanced baseline silently remains in state.

The next Stop hook then calls `compute_v2_review_set(cwd, baseline_sha, head_at_capture, untracked_at_baseline)`, which computes the review set as `dirty_now & changed_since` where `changed_since = git diff --name-only baseline_sha` [6](#0-5) . Crucially, `compute_v2_review_set` never consumes `touched_paths` at all — it derives the review set purely from git state relative to `baseline_sha`/`head_at_capture`. Since the advanced `baseline_sha` already postdates the commit containing the dangerous change, that file is no longer "changed since baseline" and is excluded from `changed_since`, so it drops out of the review set even though `touched_paths` (restored) still lists it. The dangerous commit is thus never diffed or reviewed by any subsequent Stop firing, defeating the security-guidance LLM review entirely for that change.

### Impact Explanation
This breaks the core invariant that a change made during a turn must remain inside the computed git diff review window until an LLM (Haiku) pass actually reviews it. A change that slips outside the window is never sent to `analyze_code_security`, so a dangerous/malicious edit (e.g., one that removes an approval gate, adds unrestricted command execution, or otherwise weakens Claude Code's guardrails) is permanently unreviewed and unflagged — enabling unauthorized local command execution/bypass of Claude Code approval or deny controls, matching the stated Immunefi impact category.

### Likelihood Explanation
The precondition is a normal, single-user session: the Stop hook must be mid-flight (its LLM calls, e.g. `analyze_code_security`, are network round trips that can take multiple seconds) while the user submits their next prompt before that Stop pass fails/exits. This is exactly the race the code's own comments in `restore_unreviewed_stop_state`'s docstring acknowledge ("if Stop then exits early for a transient reason... the next UPS would see an empty list, fall through the preservation guard, and re-baseline past the unreviewed edits") [7](#0-6) , but the fix only restores `touched_paths`, not `baseline_sha` in the already-overwritten case. No special privilege is needed — an attacker able to influence turn timing (e.g., a fast follow-up prompt, or a slow/failing network condition that widens the race window such as `ensure_anthropic_reachable` timeouts) in an ordinary cloned repo can reliably trigger the shift.

### Recommendation
Make `restore_unreviewed_stop_state` restore `baseline_sha`/`head_at_capture` unconditionally to the pre-Stop snapshot values (or take the min/oldest of the two, preferring whichever is an ancestor), rather than only when the field is empty. Alternatively, track an explicit "oldest unconsumed baseline" watermark independent of `touched_paths` emptiness, and have `compute_v2_review_set` union the diff against that watermark even when a later UPS has advanced the working baseline, ensuring a raced UPS can never permanently exclude an unreviewed diff.

### Proof of Concept
Unit/integration test plan (pytest style, targeting `diffstate.py`/`security_reminder_hook.py`):
1. Initialize a git repo; commit an initial file; call `handle_user_prompt_submit` to set `baseline_sha=A`.
2. Simulate a turn that edits `dangerous.py` and commits it (`HEAD=B`), with `touched_paths=["dangerous.py"]`.
3. Call `consume_stop_state(session_id)` (as `handle_stop_hook` does) → `touched_paths` cleared on disk, snapshot returns `baseline_sha=A`.
4. Before calling `restore_unreviewed_stop_state`, simulate the race: call `handle_user_prompt_submit` again (representing the next turn's UPS) after making another benign commit (`HEAD=C`) — assert this overwrites `state["baseline_sha"]` to `C` because `touched_paths` was empty at that point.
5. Now call `restore_unreviewed_stop_state(session_id, ["dangerous.py"], "A")` (simulating the delayed Stop's transient-failure retry).
6. Assert `load_baseline_sha(session_id) == "C"` (bug: should have been restored to `"A"` or something ≤ B so the diff still covers `dangerous.py`).
7. Call `compute_v2_review_set(cwd, "C", ...)` and assert `dangerous.py` is **absent** from the returned `review_paths` — demonstrating the dangerous change is silently dropped from review, confirming the vulnerability. A fixed implementation should assert `dangerous.py` **is present** in `review_paths` after the same sequence.
