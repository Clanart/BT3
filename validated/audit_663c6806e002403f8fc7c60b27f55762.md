### Title
`ThresholdKeys::read` accepts identity and inconsistent verification shares, permitting an attacker-chosen group key - (File: crypto/dkg/src/lib.rs)

### Summary
The external report describes an incomplete blocklist: a filter enumerating "sensitive" inputs yet omitting cases that reach the same protected operation. The Serai analog is `ThresholdKeys::read` in `crypto/dkg/src/lib.rs`, which deserializes `n` verification shares with `<C as Ciphersuite>::read_G` — the generic reader that checks only canonicality — instead of the FROST-level `Curve::read_G`, which additionally rejects the identity point. `ThresholdKeys::new` then performs no validation of the share values at all (only count and participant-index bounds), so attacker-controlled bytes produce `ThresholdKeys` whose `group_key` has a discrete logarithm known to the attacker — including the identity/zero key.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i`, an interpolation method, a `secret_share`, and then `n` verification shares via `<C as Ciphersuite>::read_G(reader)` at `crypto/dkg/src/lib.rs:620-623`. `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) rejects only invalid/non-canonical encodings. The FROST-aware `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`) wraps it and rejects identity — but `ThresholdKeys::read` never uses it, and `dkg` is generic over `Ciphersuite`, not `Curve`, so the identity ban is silently dropped for these shares.

`ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349-391`) then checks only:
- `verification_shares.len() == n` (always true, since `read` inserts keys `1..=n` into a `HashMap`),
- participant indexes `<= n` (guaranteed by construction),
- `t == n` for `Interpolation::Constant`.

It never checks that a verification share is non-identity, nor that `secret_share * G == verification_shares[i]`, nor that the shares correspond to a consistent polynomial. The group key is computed as `sum(verification_shares[i] * interpolation_factor(i))` over participants `1..=t` (`crypto/dkg/src/lib.rs:376-378`).

An attacker supplying bytes to `ThresholdKeys::read` can therefore:
1. Set every verification share in `1..=t` to `a_i * G` for known scalars `a_i`, making `group_key` a point with known discrete log.
2. Set them all to the identity point (accepted by `Ciphersuite::read_G` since identity is canonical), making `original_group_key() == identity`. With `Interpolation::Constant` and arbitrary coefficients, `interpolation_factor` for participant `i` is just coefficient `c_i`, so the sum is fully attacker-controlled regardless.

Any later `view()`/`sign` usage then produces signatures under a group key the attacker fully controls, or under the identity key — a signature that "verifies" against `group_key` proves nothing about any real threshold.

### Impact Explanation
`ThresholdKeys` is the output of Serai's DKG and the input to FROST signing (`ThresholdKeys::view` feeds `ThresholdView` used by `crypto/frost/src/sign.rs`). If untrusted serialized `ThresholdKeys` reach `ThresholdKeys::read` (listed in scope), the resulting `group_key()` can be the identity or any known-logarithm point. Consequences:

- Signatures produced verify against a key whose discrete log the attacker knows — equivalent to a forged-key registration; any protocol treating `group_key` as the authoritative threshold identity (e.g., deriving a Bitcoin receive address from it) attributes funds/actions to a "threshold" that is actually a single attacker key.
- `original_verification_share(i)` values need have no relation to `secret_share`, so `view()` yields a secret share inconsistent with every advertised verification share, corrupting the FROST binding assumption (share signature verification `s_i*G == R_i + c_i*Y_i` will fail or, worse, be made to pass for attacker-chosen `Y_i`).

This matches the acceptance criteria: signing under an unintended/attacker-controlled key and an incorrect verification relationship.

### Likelihood Explanation
Reachability requires attacker-supplied bytes to `ThresholdKeys::read`. That is plausible wherever keys cross a trust boundary (processor/coordinator messages, recovery flows), but no in-repo production call site feeding network input into `ThresholdKeys::read` was identified in this scan; the vulnerability exists at the deserialization boundary itself. Identity acceptance is deterministic (identity is a canonical encoding); known-log group keys require only choosing `a_i`. The missing consistency check (`secret_share*G == verification_shares[i]`) is the primary gap — the identity gap is a secondary instance of the same incomplete-restriction class.

### Recommendation
In `ThresholdKeys::new` (so it applies to `read` and all constructors), reject any verification share `is_identity()`, and verify `C::generator() * secret_share == verification_shares[i]` (modulo the documented scalar/offset being ephemeral and thus excluded). Where the `Curve` trait is in scope, deserialize shares with `Curve::read_G` instead of `Ciphersuite::read_G`. Also consider checking `ThresholdParams` consistency (nonzero `t`, `t <= n`, `i <= n`) — `ThresholdParams::new` likely covers this but was not fully verified here.

### Proof of Concept
```rust
// crypto/dkg — conceptual PoC over any Ciphersuite C (e.g. Secp256k1)
// n = t = 1, i = 1, Interpolation::Constant([1])
let mut buf = vec![];
buf.extend((C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(1u16.to_le_bytes()); // t
buf.extend(1u16.to_le_bytes()); // n
buf.extend(1u16.to_le_bytes()); // i
buf.push(0);                    // Interpolation::Constant
buf.extend(C::F::ONE.to_repr());// c_1 = 1 → interpolation_factor = 1
buf.extend(C::F::ZERO.to_repr()); // secret_share = 0 (read_F allows zero)
// verification share = IDENTITY — canonical encoding, accepted by
// Ciphersuite::read_G, would be rejected by Curve::read_G
buf.extend(C::G::identity().to_bytes());
let keys = ThresholdKeys::<C>::read(&mut buf.as_slice()).unwrap();
// group_key = identity * 1 = identity: a "threshold key" with discrete log 0
assert!(bool::from(keys.group_key().is_identity()));
```
Variant: set each share `1..=t` to `a_i * G` with known `a_i`; `group_key` then equals `sum(c_i * a_i) * G`, a key the attacker can sign for directly — yet `ThresholdKeys::read`/`new` accept it without error.
