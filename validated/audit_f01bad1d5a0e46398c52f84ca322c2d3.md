### Title
`ReceivedOutput::read` trusts deserialized offset→outpoint→TxOut mapping without consistency verification - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
The Minder advisory (GHSA-q6h8-4j2v-pjg4 / CVE-2024-27093) is a "trusted client-provided mapping" bug: `RegisterRepository` accepted a caller-supplied `repo_id` alongside `owner`/`name` and never checked that the ID actually corresponded to the named repository, so a mismatched entry was stored and downstream operations (webhooks, remediations) silently failed. The Serai analog lives in `networks/bitcoin/src/wallet/mod.rs`: `ReceivedOutput` is a triple of `(offset: Scalar, output: TxOut, outpoint: OutPoint)` where `offset` is the claimed HDKD offset mapping `outpoint`'s script to the wallet key. `ReceivedOutput::read` deserializes all three fields from untrusted bytes with no cross-check that `p2tr_script_buf(key + G*offset) == output.script_pubkey` or that `outpoint` actually resolves to `output`, and `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` then consumes these claims — crediting `input.output.value` into `input_sat` and building `TxIn`s from `input.outpoint` — before any consistency check runs.

### Finding Description
`ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) reads an arbitrary scalar via `Secp256k1::read_F`, then consensus-decodes a `TxOut` and an `OutPoint`, returning the struct with no validation that the three fields are mutually consistent. `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150-256`) trusts the mapping: it sums `input.output.value.to_sat()` into `input_sat` (line 175), copies `input.offset` into `self.offsets` (line 176), and builds inputs from `input.outpoint` (line 180). The only consistency check is deferred to `SignableTransaction::multisig` (`send.rs:273-285`), which verifies `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` and returns `None` on mismatch.

Two mismatches are therefore reachable from attacker-controlled bytes:

1. **offset↔script mismatch**: a crafted `ReceivedOutput` pairs a real wallet `outpoint`/`TxOut` with a wrong `offset`. `SignableTransaction::new` accepts it and counts its value as spendable; `multisig()` then silently returns `None` (`send.rs:277-279`), mirroring Minder's "registered but remediations never apply" failure — the output is reported spendable yet produces no signature.
2. **outpoint↔TxOut mismatch**: the `multisig` check only binds `offset` to `script_pubkey`; it never verifies that `outpoint` actually references a UTXO carrying `output`'s value and script. An attacker supplies an `outpoint` pointing at someone else's (or a nonexistent) UTXO plus a fabricated `TxOut` whose `script_pubkey` satisfies the offset check and whose `value` is inflated. `input_sat` is inflated accordingly, so `new()` succeeds, payment/change/fee math (`send.rs:204-235`) is computed against phantom balance, and the signers produce a `SighashType::Default` signature over `Prevouts::All(&self.prevouts)` (`send.rs:373-390`) committing the fraudulent prevout data. The resulting transaction is either unbroadcastable (bad prevout commitment under BIP-341) or, if the outpoint is a real wallet UTXO with a mismatched claimed value, provably invalid — the spend never confirms even though the wallet counted the funds.

There is no deduplication either: two `ReceivedOutput`s claiming the same `outpoint` both become `TxIn`s, producing a double-spend transaction that is invalid on its face.

### Impact Explanation
An unprivileged party who can feed serialized `ReceivedOutput` bytes into a wallet/consumer path (the documented `read`/`serialize` round-trip exists precisely so outputs can be transported) can cause the wallet to (a) report phantom spendable balance via inflated `TxOut.value`, (b) construct transactions that the FROST signers will fully sign but which can never confirm, and (c) silently abort signing via the `multisig() -> None` path. This is a denial of service against spend construction and a "funds reported received that are not spendable" accounting error — the same impact class as the Minder advisory (registered but inoperative), rated Medium there and here. No key material is leaked and no valid signature on attacker-beneficial data results, because the offset↔script check in `multisig` plus BIP-341 prevout commitment prevent forging a *valid* theft transaction.

### Likelihood Explanation
Reachability requires the attacker to control bytes passed to `ReceivedOutput::read` or to inject `ReceivedOutput`s into `SignableTransaction::new`. Within the in-scope crate this is a public deserialization API; whether a production consumer exposes it to untrusted input depends on integrator plumbing outside the audited scope. The offset-collision surface is narrower: `register_offset` (`mod.rs:180-196`) is documented as surjective and order-dependent, but in-tree callers (`processor/src/networks/bitcoin.rs:324-344`) register only fixed `hash_to_F`-derived offsets, so attackers cannot steer it. Exploitation needs no threshold compromise, no malicious peer, and no leaked keys — only malformed input bytes — matching the report's low-privilege bar, but the confinement of impact to DoS/phantom-accounting rather than fund theft keeps likelihood-adjusted severity at Medium.

### Recommendation
- Verify consistency at the boundary: after `ReceivedOutput::read`, or inside `SignableTransaction::new`, assert `p2tr_script_buf(group_key + G*offset) == output.script_pubkey` for each input rather than deferring it to `multisig()`, so malformed inputs fail during construction instead of silently at signing time.
- Reject duplicate `outpoint`s in `SignableTransaction::new` (`send.rs:175-185`).
- Where chain access is available, resolve `outpoint` against the node and confirm the referenced UTXO's `script_pubkey` and `value` equal the claimed `TxOut` before crediting `input_sat`.
- Document on `ReceivedOutput::read` that the deserialized triple is unvalidated claim data, not a verified spendable output.
