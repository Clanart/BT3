## Finding Confirmed

### Title
Unverified `signer` field in `RequestMessage`/`ResponseMessage` lets any submitter forge the `relayer` beneficiary recorded in `RequestReceipts` and emitted in `PostRequestHandled` - (File: `modules/pallets/ismp/src/host.rs`)

### Summary
The relayer identity written into `RequestReceipts`/`ResponseReceipts` and emitted in the `PostRequestHandled`/`GetRequestHandled` events is derived from `extract_signer()`, which decodes the attacker-supplied `signer` bytes as a `Signature` enum and returns the embedded `public_key`/`address` field via `Signature::signer()` — **without ever calling `Signature::verify()`**. This means the "relayer" credited for message delivery is whatever public key/address the caller chooses to embed, not the account that actually produced/submitted the proof.

### Finding Description
`pallet_ismp` handles incoming `RequestMessage`/`ResponseMessage` via `handle_unsigned` (callable with `ensure_none(origin)`, i.e. unprivileged), which eventually calls `IsmpHost::store_request_receipt(&req, &msg.signer)`: [1](#0-0) 

`store_request_receipt` calls `extract_signer`, which for any `signer` bytes longer than 32 bytes decodes them as a `Signature` and returns `.signer()`: [2](#0-1) 

Critically, `Signature::signer()` just extracts the embedded `public_key`/`address` field with **no cryptographic check**: [3](#0-2) 

The actual verification method, `Signature::verify()`, exists in the same file and does check `sr25519_verify`/`secp256k1_ecdsa_recover`/`ed25519_verify` against a signed message hash, but it is **not invoked anywhere along the `handle` → `store_request_receipt` path**: [4](#0-3) 

The returned `signer` bytes are then used directly as the `relayer` field of the `RequestResponseHandled` event/`PostRequestHandled`: [5](#0-4) [6](#0-5) 

Compare this to the messaging-incentives pallet, which *does* perform a proper `verify_and_get_sr25519_pubkey` check before attributing a message to a relayer for minting reputation tokens — showing that a correctly-verified pattern exists elsewhere in the codebase but was not applied to the core `store_request_receipt`/`PostRequestHandled` path: [7](#0-6) 

Because `RequestMessage`/`ResponseMessage` handling only verifies the **state/membership proof of the request contents** (via `state_machine.verify_membership`), not any signature binding `msg.signer` to the submitter, an attacker (account A, or even an unsigned submission since `handle_unsigned` uses `ensure_none`) can craft `msg.signer = Signature::Sr25519 { public_key: B, signature: <arbitrary bytes> }.encode()`. `Signature::decode` succeeds (it is just SCALE decoding of the enum), `extract_signer` returns `B` unconditionally, and the on-chain `RequestReceipts[commitment]` is set to `B` and the emitted `PostRequestHandled` event's `relayer` field is `B`, regardless of who actually delivered the proof.

### Impact Explanation
`RequestReceipts` is the canonical on-chain record of "who delivered this request," consumed both by relayer-reward accounting (per `docs/outbound-request-incentivization.md`, described as the receipt slot state proofs read for `accumulate_fees`/`claim_outbound_request_delivery_reward`) and by off-chain indexers/analytics (`sdk/packages/indexer/.../handlePostRequestHandledEvent.handler.ts`) attributing bandwidth/relayer statistics. Forging this field lets an attacker redirect relayer fee/reward accounting to an address of their choosing — an arbitrary "wrong beneficiary," which is explicitly in the accepted impact set (wrong beneficiary / broken reward accounting).

### Likelihood Explanation
High. No privileged role is required — `handle_unsigned` accepts `ensure_none(origin)`, and forging the `signer` bytes only requires SCALE-encoding a `Signature` enum with an arbitrary embedded public key and garbage signature bytes; the decode step never checks the signature validity in this code path.

### Recommendation
Call `Signature::verify()` (not just `.signer()`) against a deterministic message derived from the request/response batch (as `messaging-incentives::relayer_for` already does) inside `extract_signer`/`store_request_receipt`/`store_response_receipt`, rejecting the message if verification fails, before using the recovered identity as the `relayer` value stored in receipts and emitted in events.

### Proof of Concept
1. Attacker A crafts a valid `PostRequest` batch with a legitimate membership proof (obtained honestly or copied from a real relayer's submission).
2. Attacker sets `RequestMessage.signer = Signature::Sr25519 { public_key: B_bytes, signature: [0u8; 64] }.encode()` (arbitrary/garbage signature — no valid signing key for B is needed).
3. Attacker submits `pallet_ismp::handle_unsigned(RuntimeOrigin::none(), vec![Message::Request(request_message)])`.
4. `handle()` → `store_request_receipt(&req, &msg.signer)` → `extract_signer` decodes the `Signature` and returns `B_bytes` without verifying the (invalid) signature.
5. `RequestReceipts[commitment] = B` is stored and `Event::PostRequestHandled(RequestResponseHandled { commitment, relayer: B })` is emitted, crediting the reward/bandwidth beneficiary `B` even though `B` never produced any valid signature or proof — confirmable by tracing `modules/ismp/core/src/handlers/request.rs:112` and `modules/pallets/ismp/src/host.rs:351-359` where `.verify()` is never called. fn extract_signer(signer: &[u8]) -> Result<Vec<u8>, Error> {
	if signer.len() > 32 {
		Signature::decode(&mut signer.as_ref())
			.map(|sig| sig.signer())
			.map_err(|_| Error::SignatureDecodingFailed)
	} else {
		Ok(signer.to_vec())
	}
}
