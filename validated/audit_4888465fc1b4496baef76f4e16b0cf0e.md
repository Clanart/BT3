### Title
Missing HTML-context (`<`/`>`) escaping in upb-based JSON string encoder allows JSON/JS-context injection - (File: `upb/json/encode.c`)

### Summary
The Svelte advisory (GHSA-6738-r8g5-qwp3) is a case where an attacker-influenced string value is written into a `<script>`-embedded JSON/JS context without escaping the characters (`<`, `>`) that let a value break out of that context, producing script injection. Protobuf's canonical JSON writer for C++ (`src/google/protobuf/json/internal/writer.cc`) and Java (`java/util/src/main/java/com/google/protobuf/util/JsonFormat.java`) both implement this exact defense-in-depth invariant: they escape `<`/`>` (and Java additionally `&`, `=`, `'`) specifically "to prevent security bugs in javascript" when the produced JSON is later inlined into an HTML `<script>` block. The upb-based encoder used by Ruby, PHP and any C/C++ embedder calling `upb_JsonEncode` directly (`upb/json/encode.c`, mirrored verbatim in `ruby/ext/google/protobuf_c/ruby-upb.c` and `php/ext/google/protobuf/php-upb.c`) does **not** implement this invariant: its `jsonenc_put_escaped_char` only escapes the JSON-mandated control characters and quote/backslash, leaving `<` and `>` (and the other Unicode bidi/invisible characters that the C++/Java writers also escape) untouched.

### Finding Description
`jsonenc_put_escaped_char` in `upb/json/encode.c` (identical copies in `ruby-upb.c` and `php-upb.c`) is the single low-level routine used to escape every byte of every string field, map string key, and (through `jsonenc_string`) the `Any` `@type` URL when producing ProtoJSON output: [1](#0-0) 

It handles `\n \r \t \" \f \b \\` and generic control bytes `< 0x20`, but has no case for `<`/`>` and passes all other bytes through verbatim via `jsonenc_putbytes`.

Compare this to the C++ writer's `MustEscape`, which explicitly documents and implements escaping of `<`, `>`, and a set of invisible/bidi Unicode characters "to prevent security bugs in JavaScript", beyond what the JSON spec requires: [2](#0-1) 

Java's `JsonFormat` implements the analogous invariant, additionally escaping `&`, `=`, and `'`, with a comment stating this exists "to prevent XSS risks": [3](#0-2) 

Because `jsonenc_stringbody`/`jsonenc_string` are the sole functions used for every string surface in the upb encoder — including scalar string fields (`jsonenc_scalar`, `upb/json/encode.c:633`), map string keys (`jsonenc_mapkey`, `upb/json/encode.c:648-676`), and the `Any` `@type` value (`jsonenc_any`, `upb/json/encode.c:390-423`) — any of those attacker-controlled strings parsed from an incoming Protobuf binary/JSON message will be emitted into the resulting JSON byte stream with `<`/`>` left unescaped: [4](#0-3) [5](#0-4) 

This upb JSON encoder is the actual implementation backing Ruby's `Message#to_json` and PHP's `serializeToJsonString`/`__toString`-style JSON APIs, since `ruby/ext/google/protobuf_c/message.c` and `php/ext/google/protobuf/message.c` invoke the identical `jsonenc_*` machinery (verified present as `ruby-upb.c`/`php-upb.c` copies of `jsonenc_mapkey`, `jsonenc_any`, `jsonenc_stringbody`).

The failed invariant transferred from the Svelte report: a string value that will predictably be embedded into an HTML/`<script>` document context must have HTML-breakout characters (`<`, `>`) escaped even though they are not required by the underlying data format (JSON) spec — exactly the same class of gap the Svelte advisory describes for the `hydratable` key embedded in a `<script>` block. Protobuf's own C++/Java writers already codify this exact defense; the upb C encoder simply omits it.

### Impact Explanation
Consuming applications commonly render server-produced ProtoJSON directly into a `<script>` tag (e.g., `<script>var data = {{ message.to_json }};</script>`) to bootstrap client-side state, which is precisely the scenario the C++/Java escaping comments were written to defend against. When the underlying data path is upb (Ruby, PHP, or any C/C++ code calling `upb_JsonEncode` directly), a string field, map key, or `Any` type URL containing `</script><script>...` breaks out of the intended script context and results in stored/reflected XSS in the consuming application — the same "Impact" bullets as the Svelte advisory (session/token theft, DOM defacement, CSRF bypass, account takeover). This is Medium severity, consistent with the source advisory's rating, since it depends on a specific (but common and protobuf's own docs implicitly anticipate) unescaped-embedding usage pattern by the consuming application, not a memory-safety or RCE bug in protobuf itself.

### Likelihood Explanation
High likelihood of reachability: any client can send arbitrary UTF‑8 string field content (including `<`, `>` sequences) through the normal, public binary Protobuf parse → ProtoJSON serialize path in Ruby or PHP bindings, with no attacker privilege beyond sending a bounded, schema-valid message. No malicious schema, plugin, or internal API misuse is required — this is triggered purely by ordinary field values.

### Recommendation
Align `jsonenc_put_escaped_char` in `upb/json/encode.c` (and the generated copies in `ruby-upb.c` / `php-upb.c`) with the C++ (`writer.cc`'s `MustEscape`) and Java (`JsonFormat`'s `replacementChars`) behavior: escape `<` and `>` (and ideally the same invisible/bidi Unicode ranges) as `\uXXXX` sequences in all string output paths (`jsonenc_string`, `jsonenc_stringbody`, `jsonenc_mapkey`), so ProtoJSON output is safe to embed directly in an HTML `<script>` context across all language bindings.

### Proof of Concept
Given a trusted `.proto` schema `message M { string s = 1; }`, an attacker sends a bounded, well-formed binary Protobuf payload for `M` with `s = "</script><script>alert(1)</script>"`. Using the Ruby or PHP protobuf extension:
1. Parse the bytes into `M` via the normal public parse API.
2. Call the message's JSON serialization API (`Message#to_json` in Ruby / `serializeToJsonString` in PHP), which internally reaches `jsonenc_string`/`jsonenc_stringbody` in `ruby-upb.c`/`php-upb.c`.
3. The resulting JSON is `{"s":"</script><script>alert(1)</script>"}` — the `<`/`>` bytes are emitted verbatim because `jsonenc_put_escaped_char` (upb/json/encode.c:268-301) has no case for them, unlike C++'s `MustEscape` (writer.cc:239-241) or Java's `replacementChars['<'|'>']` (JsonFormat.java:1589-1591).
4. If this JSON string is subsequently interpolated into a `<script>` block by the consuming application (a documented, anticipated usage pattern that motivated the C++/Java escaping), the injected `<script>alert(1)</script>` executes in the victim's browser.

I was not able to execute this PoC in a live runtime (no code-execution access in this session); the finding is based on direct code comparison across `writer.cc`, `JsonFormat.java`, and the three verified-identical `jsonenc_put_escaped_char`/`jsonenc_mapkey`/`jsonenc_any` implementations in `upb/json/encode.c`, `ruby-upb.c`, and `php-upb.c`.

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}

static void jsonenc_any(jsonenc* e, const upb_Message* msg,
                        const upb_MessageDef* m) {
  const upb_FieldDef* type_url_f = upb_MessageDef_FindFieldByNumber(m, 1);
  const upb_FieldDef* value_f = upb_MessageDef_FindFieldByNumber(m, 2);
  upb_StringView type_url = upb_Message_GetFieldByDef(msg, type_url_f).str_val;
  upb_StringView value = upb_Message_GetFieldByDef(msg, value_f).str_val;
  const upb_MessageDef* any_m = jsonenc_getanymsg(e, type_url);
  const upb_MiniTable* any_layout = upb_MessageDef_MiniTable(any_m);
  upb_Arena* arena = jsonenc_arena(e);
  upb_Message* any = upb_Message_New(any_layout, arena);
  if (!any) {
    jsonenc_err(e, "Out of memory");
    return;
  }

  if (upb_Decode(value.data, value.size, any, any_layout, NULL, 0, arena) !=
      kUpb_DecodeStatus_Ok) {
    jsonenc_err(e, "Error decoding message in Any");
  }

  jsonenc_putstr(e, "{\"@type\":");
  jsonenc_string(e, type_url);

  if (upb_MessageDef_WellKnownType(any_m) == kUpb_WellKnown_Unspecified) {
    /* Regular messages: {"@type": "...","foo": 1, "bar": 2} */
    jsonenc_msgfields(e, any, any_m, false);
  } else {
    /* Well-known type: {"@type": "...","value": <well-known encoding>} */
    jsonenc_putstr(e, ",\"value\":");
    jsonenc_msgfield(e, any, any_m);
  }

  jsonenc_putstr(e, "}");
}

static void jsonenc_scalar(jsonenc* e, upb_MessageValue val,
                           const upb_FieldDef* f) {
  switch (upb_FieldDef_CType(f)) {
    case kUpb_CType_Bool:
      jsonenc_putstr(e, val.bool_val ? "true" : "false");
      break;
    case kUpb_CType_Float:
      upb_JsonEncode_Float(e, val.float_val);
      break;
    case kUpb_CType_Double:
      upb_JsonEncode_Double(e, val.double_val);
      break;
    case kUpb_CType_Int32:
      jsonenc_printf(e, "%" PRId32, val.int32_val);
      break;
    case kUpb_CType_UInt32:
      jsonenc_printf(e, "%" PRIu32, val.uint32_val);
      break;
    case kUpb_CType_Int64:
      jsonenc_printf(e, "\"%" PRId64 "\"", val.int64_val);
      break;
    case kUpb_CType_UInt64:
      jsonenc_printf(e, "\"%" PRIu64 "\"", val.uint64_val);
      break;
    case kUpb_CType_String:
      jsonenc_string(e, val.str_val);
      break;
    case kUpb_CType_Bytes:
      jsonenc_bytes(e, val.str_val);
      break;

      break;

    // to prevent security bugs in JavaScript.
    //
    // These were originally present in the ESF parser, so they are kept for
    // legacy compatibility (and because escaping most of these is in good
    // taste, regardless).
    case '<':
    case '>':
    case 0xfeff:      // Zero width no-break space.
    case 0xfff9:      // Interlinear annotation anchor.
    case 0xfffa:      // Interlinear annotation separator.
    case 0xfffb:      // Interlinear annotation terminator.
    case 0x00ad:      // Soft-hyphen.
    case 0x06dd:      // Arabic end of ayah.
    case 0x070f:      // Syriac abbreviation mark.
    case 0x17b4:      // Khmer vowel inherent Aq.
    case 0x17b5:      // Khmer vowel inherent Aa.
    case 0x000e0001:  // Language tag.
      return true;
    default:
      static constexpr std::pair<uint32_t, uint32_t> kEscapedRanges[] = {
          {0x0000, 0x001f},          // ASCII control.
          {0x007f, 0x009f},          // High ASCII bytes.
          {0x0600, 0x0603},          // Arabic signs.
          {0x200b, 0x200f},          // Zero width etc.
          {0x2028, 0x202e},          // Separators etc.
          {0x2060, 0x2064},          // Invisible etc.
          {0x206a, 0x206f},          // Shaping etc.
          {0x0001d173, 0x0001d17a},  // Music formatting.
          {0x000e0020, 0x000e007f},  // TAG symbols.
      };
