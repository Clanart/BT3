### Title
CATWallet.identify auto-creates a CR-CAT wallet using unvalidated `authorized_providers`/`proofs_checker` from an untrusted incoming coin spend - (File: chia/wallet/cat_wallet/cat_wallet.py)

### Summary
`CATWallet.identify()` is the code path that automatically creates (or converts) a wallet when a node/wallet observes a new CAT-shaped coin sent to one of its own puzzle hashes. For coins that turn out to be CR-CATs, the `authorized_providers` and `proofs_checker` values are taken directly from the attacker-controlled coin spend (`crcat.authorized_providers`, `crcat.proofs_checker`) and used to permanently configure the wallet's `CRCATInfo`, with no verification that these values correspond to a legitimate, reachable proof provider (DID) or a sane proofs checker. [1](#0-0) 

### Finding Description
When a coin identified as a CR-CAT is received, `identify()` either looks up an existing `CRCATWallet` for the asset id, or (if none exists) creates one via `CRCATWallet.get_or_create_wallet_for_cat(..., authorized_providers=crcat.authorized_providers, proofs_checker=...)`, sourcing these fields straight from the untrusted `coin_spend`. [2](#0-1) 

`CRCATWallet.get_or_create_wallet_for_cat` stores whatever `authorized_providers`/`proofs_checker` it is given into `self.info = CRCATInfo(limitations_program_hash, None, authorized_providers, proofs_checker)` and persists the wallet, with wallet reuse for a given asset id keyed only on `limitations_program_hash` (the TAIL/asset id), not on the providers/checker. [3](#0-2) 

There is no check anywhere in this path that `authorized_providers` actually contains a DID the recipient (or anyone) controls, or that `proofs_checker` encodes sane/verifiable proof flags. This mirrors the reported bug class exactly: an externally supplied "contract-like" configuration value (here, the CR-CAT's list of authorized proof providers and its proofs checker) is accepted and locked into a wallet object with no interface/sanity validation, and the resulting object cannot later be reconfigured because subsequent identical-asset-id coins reuse the very first wallet's configuration.

### Impact Explanation
Because a wallet's CR-CAT configuration is derived from data controlled by whoever crafts the coin spend that first "teaches" a wallet about a given CR-CAT asset id, an unprivileged spend-bundle submitter can send a CR-CAT-shaped coin (hinted to a victim's puzzle hash) whose `authorized_providers` list references providers the victim cannot obtain proofs from (e.g., nonexistent or attacker-only DIDs), or whose `proofs_checker` requires flags the victim can never satisfy. The victim's wallet auto-creates (or, in the CAT->CR-CAT conversion path, permanently converts) a `CRCATWallet` using these bogus parameters. Any legitimate CR-CATs of that asset id received later are matched to the same wallet id/config (lookup is by `limitations_program_hash` only), so the victim can end up holding coins that are permanently unspendable through the wallet because it never has a valid VC from any of the configured providers — a spend-triggered transaction-processing halt for that asset, without any way for the victim to reset it since wallet creation happens automatically and only once per asset id.

### Likelihood Explanation
This requires only pushing a spend bundle that creates a coin whose puzzle reveal decodes into a CR-CAT layer and that hints to the victim's own puzzle hash — something any mempool submitter can construct without special privileges, matching the "unprivileged spend-bundle submitter" reachability bar. The main mitigating factor is that this is a griefing/self-lockout of a specific asset id rather than direct theft of unrelated funds, but it still satisfies the "spend-triggered transaction-processing halt" impact category.

### Recommendation
Do not trust `authorized_providers` / `proofs_checker` taken from an arbitrary incoming coin spend to silently create or convert a wallet. At minimum:
- Validate that `authorized_providers` is non-empty and, where possible, corresponds to DIDs/puzzle hashes that are independently known/registered (e.g., via a user-approved list of trusted providers) before auto-creating a `CRCATWallet`.
- Surface a user confirmation step (similar to the "stray CAT" flow used for plain CATs) before silently binding an asset id to attacker-supplied provider/proof-checker configuration.
- Treat mismatched `authorized_providers`/`proofs_checker` for an already-known asset id as a distinct, clearly-surfaced case rather than silently reusing the first-seen wallet's configuration.

### Proof of Concept
1. Attacker crafts a spend bundle that creates a CR-CAT coin (constructed via `construct_cr_layer`/CRCAT drivers) whose inner puzzle hint points at a puzzle hash controlled by the victim's wallet, and whose `authorized_providers` list contains only DIDs the attacker controls (or none reachable by the victim), with an arbitrary `proofs_checker`.
2. Attacker submits the spend bundle to the mempool; it is accepted and confirmed like any normal CAT-shaped coin.
3. Victim's `WalletStateManager` sync processes the new coin; `CATWallet.identify()` detects it as a CR-CAT (via `CRCAT.get_next_from_coin_spend`) and, finding no existing wallet for that asset id, calls `CRCATWallet.get_or_create_wallet_for_cat(...)` using the attacker-chosen `authorized_providers`/`proofs_checker`. [2](#0-1) 
4. `CRCATWallet` is now permanently configured with the attacker's provider list/proof checker for that asset id; any subsequent legitimate CR-CATs of the same asset id sent to the victim are associated with this same wallet, which the victim cannot spend through because no VC exists from the configured authorized providers. [3](#0-2)

    @classmethod
    async def get_or_create_wallet_for_cat(
        cls,
        wallet_state_manager: WalletStateManager,
        wallet: Wallet,
        limitations_program_hash: bytes32,
        name: str | None = None,
        authorized_providers: list[bytes32] | None = None,
        proofs_checker: ProofsChecker | None = None,
    ) -> Self:
        if authorized_providers is None or proofs_checker is None:  # pragma: no cover
            raise ValueError("get_or_create_wallet_for_cat was call on CRCATWallet without proper arguments")
        self = cls()
        self.standard_wallet = wallet
        if name is None:
            name = self.default_wallet_name_for_unknown_cat(limitations_program_hash)
        self.log = logging.getLogger(name)

        for id, w in wallet_state_manager.wallets.items():
            if w.type() == cls.type():
                assert isinstance(w, cls)
                if w.get_asset_id() == limitations_program_hash:
                    self.log.warning("Not creating wallet for already existing CR-CAT wallet")
                    return w

        self.wallet_state_manager = wallet_state_manager

        self.info = CRCATInfo(limitations_program_hash, None, authorized_providers, proofs_checker)
        info_as_string = bytes(self.info).hex()
        self.wallet_info = await wallet_state_manager.user_store.create_wallet(name, WalletType.CRCAT, info_as_string)

        await self.wallet_state_manager.add_new_wallet(self)
        self.tail_hash = self.info.limitations_program_hash
        return self
