### Title
Unbounded participant indexes in blame adjudication cause out-of-map indexing panic - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The DKG blame path (`BlameMachine::blame`, `AdditionalBlameMachine::blame`) accepts attacker-influenced `sender` / `recipient` `Participant` values and directly indexes `self.commitments[&sender]` and `self.enc_keys[&decryptor]` without checking they are `<= n`. A malformed accusation crashes the adjudicating node — an analog of CVE-2021-3612's unprivileged attacker-controlled index causing an out-of-bounds memory access.

### Finding Description
`Participant` only enforces "non-zero" (`Participant::new`), so any value `1..=u16::MAX` is a validly typed index, including values `> n`. `blame_internal` performs `self.commitments[&sender]` when verifying the accused share, and `decrypt_with_proof` performs `self.enc_keys[&decryptor]` when validating the accuser's `EncryptionKeyProof`. Neither `blame` entry point bounds `sender` or `recipient` against `params.n()` or membership in the maps. In every other protocol path, participant indexes are validated (`ThresholdParams::new` rejects `i > n`; `view`/`sign` check `included.last() <= n`; `validate_map` requires exact coverage of `1..=n`), so this unchecked indexing is reachable only through blame — precisely the path fed by an adversarial accusation containing an out-of-range participant index.

Relevant code:
- `blame_internal` indexes commitments: `&self.commitments[&sender]` at crypto/dkg/pedpop/src/lib.rs:599
- `decrypt_with_proof` indexes registered keys: `self.enc_keys[&decryptor]` at crypto/dkg/pedpop/src/encryption.rs:388
- Public entry points pass the indexes through unchecked: crypto/dkg/pedpop/src/lib.rs:623-632 (`BlameMachine::blame`), 674-682 (`AdditionalBlameMachine::blame`)
- `Participant::new` admits any non-zero `u16` (no `<= n` bound): crypto/dkg/src/lib.rs (Participant construction via `Participant::new(read_u16()?)` at line 600; validation against `n` only occurs inside `ThresholdParams::new` at lines 166-179, which `blame` never calls)

### Impact Explanation
An accusation naming `sender` or `recipient` as a participant index `> n` (or any index absent from the maps) causes a `HashMap` index panic inside `blame_internal`, aborting the blame/adjudication flow and crashing the calling task/node. This is a remotely triggerable denial of service reachable with untrusted bytes fed to a `blame` API — a direct availability impact matching the bug class (attacker-controlled index → memory-safety violation; safe-Rust manifestation is an unhandled panic instead of a silent OOB write).

### Likelihood Explanation
Blame adjudication is explicitly designed to process accusations about arbitrary (potentially faulty) parties, and the accusation's `sender`/`recipient` fields come from the accuser. An accuser — or any party relaying a malformed accusation, including a non-participant invoking `AdditionalBlameMachine::new` + `blame` — can pick an index like `u16::MAX` which parses as a valid non-zero `Participant` but is not in `commitments`/`enc_keys`. No cryptographic validity is required to reach the panicking line for the `InvalidSignature`/`InvalidProof` ordering: `self.commitments[&sender]` is reached after signature/decryption checks on the message, and `self.enc_keys[&decryptor]` is reached whenever a proof is supplied. Because `Commitments::read` fixes lengths from `params.t()` and indexes are never range-checked, the panic is deterministic.

### Recommendation
Bounds-check `sender` and `recipient` in `blame_internal`/`blame` before any map indexing: reject or return a defined result when either index is `> n` or not present in `self.commitments`/`self.enc_keys` (e.g., use `.get()` and treat absent indexes as a malformed accusation). Also apply the same check in `AdditionalBlameMachine::blame`.

### Proof of Concept
```rust
// Participant index far beyond n parses fine (non-zero), then panics in blame.
let attacker_sender = Participant::new(u16::MAX).unwrap();
let recipient = Participant::new(1).unwrap();

// `msg`/`proof` are attacker-controlled bytes read via
// EncryptedMessage::read / EncryptionKeyProof::read.
let (additional, faulty) = blame_machine.blame(attacker_sender, recipient, msg, proof);
//                                    ^^^^^^^^^^^^^^^
// blame_internal -> self.commitments[&sender] where sender = 65535
// HashMap index on absent key -> panic (process crash)

// Alternative path: valid sender, bogus recipient with a proof ->
// decrypt_with_proof -> self.enc_keys[&decryptor] -> panic.
```
