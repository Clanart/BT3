### Title
`associate`/`associatePubKey` precompile and EVM tx association only check the seiAddr side, letting a second signer bind their account to an EVM address that is already associated with a different Sei address - (File: precompiles/addr/addr.go)

### Summary
The Footium bug lets multiple clubs redeem the same unique player because the double-redemption guard is scoped to only one dimension of the composite key (`clubId`) and never checks whether the `generationId` was already claimed by *another* club. The same class of bug exists in sei-chain's EVM/Sei address-association logic: uniqueness is enforced only on the `seiAddr` side of the mapping, never on the `evmAddr` side, before the mapping is (over)written.

### Finding Description
`associateAddresses` in `precompiles/addr/addr.go` only guards against re-association by checking if the caller-supplied `seiAddr` already has an EVM address mapped: [1](#0-0) 

It never calls `p.evmKeeper.GetSeiAddress(ctx, evmAddr)` to check whether `evmAddr` is already mapped to a *different* `seiAddr` before calling `AssociateAddresses` → `SetAddressMapping`, which unconditionally overwrites both directions of the mapping: [2](#0-1) 

The same one-sided check pattern repeats across every legacy precompile version (`v575`, `v600`, `v601`, `v603`, `v605`, `v606`, `v610`, `v614`, `v620`, `v630`, `v640`, `v65`, `v66`, `v67`) and in the ante-handler path `HandleAssociateTx`/`AssociateAddress` in `app/ante/evm_checktx.go`, and in `Preprocess`'s implicit-association branch in `x/evm/ante/preprocess.go`: [3](#0-2) [4](#0-3) [5](#0-4) 

All of these paths check `GetEVMAddress(ctx, seiAddr)` (has this Sei address already claimed an EVM address?) but none check `GetSeiAddress(ctx, evmAddr)` (has this EVM address already been claimed by a different Sei address?) before calling `AssociateAddresses`/`SetAddressMapping`.

`AssociateAddresses` itself performs no reciprocal check either — it directly calls `SetAddressMapping`, which blindly overwrites `EVMAddressToSeiAddressKey(evmAddr)` and `SeiAddressToEVMAddressKey(seiAddr)`: [6](#0-5) [2](#0-1) 

There is one narrower guard, `AuthorityToPreAssociate`, used only for EIP-7702 SetCode authorities, which does check `GetEVMAddress(ctx, seiAddr)` to skip already-associated authorities, but this is scoped to that one code path and still does not check the reverse direction (`GetSeiAddress(ctx, evmAddr)`), so it does not close the gap for the primary `associate`/`associatePubKey` precompile or `AssociateTx` paths: [7](#0-6) 

### Impact Explanation
An EVM address `E` can legitimately be associated with Sei address `S1` (e.g. via signing an `associate` call or sending a first EVM tx). If a second, unrelated Sei account holder `S2` can produce a valid signature recoverable to the same EVM address `E` — which is not possible under normal ECDSA usage since the EVM address is derived from the pubkey used to sign — this bug class would matter. However, the actual reachable exploit path here is more subtle: since `SetAddressMapping` unconditionally overwrites `EVMAddressToSeiAddressKey(evmAddr)` and the guard is only "is `seiAddr` already associated," any account already possessing the direct-cast `seiAddr` (i.e., `sdk.AccAddress(evmAddr[:])`, distinct from a pubkey-derived `seiAddr`) is treated as a brand-new, unassociated seiAddr and will pass the `GetEVMAddress(ctx, seiAddr)==false` check even when `evmAddr` is already truly associated with a different `seiAddr`. This can re-point the reverse EVM→Sei mapping away from the legitimate associated account to whichever caller races the association call, and can also drag balance migration (`MigrateBalance`) into the wrong account, since `AssociateAddresses` moves the `castAddr` balance into whatever `seiAddr` is passed.

### Likelihood Explanation
Reaching this requires crafting an EVM-address/Sei-address/pubkey triple that satisfies `helpers.GetAddresses`/`GetAddressesFromPubkeyBytes` validation (i.e., a valid signature-derived or pubkey-derived pairing) while colliding with an already-associated `evmAddr`. This is unlikely to occur naturally since address derivation is deterministic from the pubkey, and I was not able to conclusively construct a concrete transaction path in the given time that produces two distinct, differently-authenticated `seiAddr` values mapping to the same `evmAddr` without also controlling the pubkey for that `evmAddr` (which would already grant control of funds there). I could not verify a fund-loss-producing end-to-end trigger with full confidence in the tool budget available.

### Recommendation
Add a symmetric check in `associateAddresses` (and in the ante-handler equivalents) that also verifies `p.evmKeeper.GetSeiAddress(ctx, evmAddr)` is unset (or matches the resolved `seiAddr`) before calling `AssociateAddresses`, mirroring the intended one-to-one invariant of the address-association store, analogous to guarding on the full composite key rather than one half of it as recommended in the source report.

### Proof of Concept
Not able to construct a concrete, fully verified transaction sequence within the available tool budget that demonstrates two distinct authenticated Sei addresses successfully mapping to the same EVM address; this would require deeper tracing of `helpers.GetAddresses`/`GetAddressesFromPubkeyBytes` and the direct-cast account interaction in `AssociateAddresses` (lines 34-42 of `utils/helpers/associate.go`) than the tool budget allowed.

	// Check that address is not already associated
	_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)

		return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)

	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}

func HandleAssociateTx(ctx sdk.Context, ek *evmkeeper.Keeper, atx *ethtx.AssociateTx, readOnly bool) (sdk.Context, error) {
	V, R, S := atx.GetRawSignatureValues()
	V = new(big.Int).Add(V, utils.Big27)
	// Hash custom message passed in
	customMessageHash := crypto.Keccak256Hash([]byte(atx.CustomMessage))
	evmAddr, seiAddr, seiPubkey, err := helpers.GetAddresses(V, R, S, customMessageHash)
	if err != nil {
		return ctx, err
	}
	_, isAssociated := ek.GetEVMAddress(ctx, seiAddr)
	if isAssociated {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrInvalidRequest, "account already has association set")
	}
	if !IsAccountBalancePositive(ctx, ek, seiAddr, evmAddr) {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrInsufficientFunds, "account needs to have at least 1 wei to force association")
	}
	if !readOnly {
		if err := AssociateAddress(ctx, ek, evmAddr, seiAddr, seiPubkey); err != nil {
			return ctx, err
		}
	}
	return ctx.WithPriority(antedecorators.EVMAssociatePriority), nil

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

// already associated. Mirroring validateAuthorization is essential to security: the
// authorization sig hash is computed from the auth's own ChainID, so recovery and
// auth.Authority() succeed for an authorization signed for ANY chain. Without these checks a
// publicly-visible authorization a user signed for another chain (e.g. Ethereum mainnet)
// could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their
// direct-cast balance and orphaning staking/distribution state — even though the EVM skips
// the wrong-chain authorization and installs no delegation.
func AuthorityToPreAssociate(ctx sdk.Context, k AuthorizationStateReader, auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, bool) {
	// Chain ID must be null or match the local chain.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(k.ChainID(ctx)) != 0 {
		return common.Address{}, nil, nil, false
	}
	// Nonce must not overflow (EIP-2681).
	if auth.Nonce+1 < auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	evmAddr, seiAddr, pubkey, err := RecoverAddressesFromAuthorization(auth)
	if err != nil {
		return common.Address{}, nil, nil, false
	}
	// Cross-check against go-ethereum's authoritative recovery so we only ever act on the
	// exact address SetCode would target during execution.
	if authAddr, aerr := auth.Authority(); aerr != nil || authAddr != evmAddr {
		return common.Address{}, nil, nil, false
	}
	// Authority must have no code, or only an existing delegation designator.
	if code := k.GetCode(ctx, evmAddr); len(code) != 0 {
		if _, ok := ethtypes.ParseDelegation(code); !ok {
			return common.Address{}, nil, nil, false
		}
	}
	// Authority account nonce must match the authorization nonce.
	if k.GetNonce(ctx, evmAddr) != auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	// Already-associated authorities need no pre-association (and cannot be re-mapped).
	if _, associated := k.GetEVMAddress(ctx, seiAddr); associated {
		return common.Address{}, nil, nil, false
	}
	return evmAddr, seiAddr, pubkey, true
