### Title
`BaseRewardPool.totalStaked()` reads raw `stakingToken.balanceOf(operator)` instead of tracked stake, allowing a direct-transfer donation attack that permanently dilutes `rewardPerTokenStored` and freezes legitimate stakers' yield - (File: wombat/ArbWomUp3.sol → rewards/BaseRewardPool.sol)

### Summary
`BaseRewardPool.totalStaked()` returns `IERC20(stakingToken).balanceOf(operator)` [1](#0-0)  rather than a value derived from `MasterMagpie`'s internal accounting of staked amounts. Any unprivileged holder of `stakingToken` can inflate this denominator with a plain `IERC20.transfer` to the `operator` address before a reward manager calls `queueNewRewards`, causing `_provisionReward` to compute a permanently reduced `rewardPerTokenStored` increment for that distribution event.

### Finding Description
`_provisionReward` computes the per-token reward increment as:
```
rewardInfo.rewardPerTokenStored += (_amountReward * 10**stakingDecimals()) / this.totalStaked();
``` [2](#0-1) 

`totalStaked()` is defined as the raw ERC20 balance of the pool operator (MasterMagpie), not a sum of internally tracked `user.amount` values [1](#0-0) . Meanwhile, a user's `balanceOf(_account)` used in `earned()` comes from `IMasterMagpie(operator).stakingInfo(stakingToken, _account)`, i.e. MasterMagpie's separate, correctly-tracked ledger [3](#0-2) .

Because these two values are sourced independently (one from raw balance, one from internal accounting), an attacker can call `stakingToken.transfer(operator, X)` directly — bypassing `deposit`/`depositFor` entirely — to inflate `totalStaked()` without incrementing anyone's `user.amount`. If this transfer happens before a manager's `queueNewRewards(amountReward, rewardToken)` call, the `rewardPerTokenStored` increment for that call is diluted by the artificially inflated denominator. Since `rewardPerTokenStored` is a monotonically accumulating value used for all future `earned()` calculations [4](#0-3) [5](#0-4) , this dilution is permanent for that reward tranche — legitimate stakers' `earned()` for that reward event is fixed lower than fair share forever, while the full `_amountReward` of the reward token has already been pulled into the contract via `safeTransferFrom` [6](#0-5) . The undistributed remainder becomes stuck in the reward pool with no reconciliation mechanism, since there is no function that credits the discrepancy back to `rewardPerTokenStored` or lets anyone reclaim it based on the true internal total.

No modifier or accounting check in `queueNewRewards`/`_provisionReward`/`totalStaked` guards against the raw-balance vs. tracked-total mismatch; `onlyManager` only gates who can *queue* the reward, not the state of `totalStaked()` at that time [7](#0-6) .

Note: I could not fully confirm within available context whether `MasterMagpie` exposes any function that would let the attacker later recover raw-transferred `stakingToken` balance not backed by `user.amount` (its `withdraw` logic appears to transfer based on tracked `user.amount`, not raw balance, based on partial inspection of `rewards/MasterMagpie.sol`, but I did not get to fully read its withdraw implementation before running out of tool calls). If no recovery path exists, the attacker's transferred tokens become permanently stuck as idle balance, meaning the attack is a self-funded griefing attack against other stakers with no path to profit — it still constitutes a fund-freezing/dilution vulnerability for other stakers' unclaimed yield.

### Impact Explanation
This constitutes **permanent freezing/theft of unclaimed yield** for legitimate stakers: the `rewardPerTokenStored` growth from a `queueNewRewards` call is permanently reduced below the fair-share level that would result from computing `totalStaked()` against actual staked principal. Since reward tokens are already pulled into the contract at the full `_amountReward`, the shortfall is neither distributed to stakers nor recoverable by any party, resulting in reward tokens becoming permanently unclaimable — satisfying the "permanent freezing of unclaimed yield" impact class for at least 24 hours (indefinitely, in fact, since there's no self-correcting mechanism).

### Likelihood Explanation
The attack requires only capital to acquire `stakingToken` and a plain `IERC20.transfer` call to `operator` timed before/around a `queueNewRewards` transaction — fully within an unprivileged attacker's capability (front-running is explicitly permitted per rules). It is repeatable for every `queueNewRewards`/`donateRewards` call and does not require any admin, oracle, or governance compromise. The main deterrent is that (pending confirmation of `MasterMagpie`'s withdraw semantics) the attacker's transferred tokens may become permanently stuck, making the attack capital-costly and primarily useful as a pure griefing vector rather than a profit vector — this reduces but does not eliminate likelihood, since griefing attacks by disgruntled/malicious actors or competitors remain a valid threat model, and the impact on other users is real and quantifiable.

### Recommendation
Replace `totalStaked()`'s raw `balanceOf(operator)` read with an actual sum of tracked stake amounts (e.g., have `MasterMagpie` expose and `BaseRewardPool` consume a `totalSupply`-style value maintained solely through `deposit`/`withdraw` accounting, never derived from raw ERC20 balance). This decouples the reward-per-token calculation from any balance that can be manipulated by direct transfers to the operator contract.

### Proof of Concept
1. Deploy `MasterMagpie`, `BaseRewardPool`, and a mock `stakingToken`/`rewardToken`.
2. Control run: Stake `100` `stakingToken` from `userA` via `deposit`. As a manager, call `queueNewRewards(1000, rewardToken)`. Record `rewardPerTokenStored` and `userA.earned()`.
3. Attack run (fresh deployment): Stake `100` `stakingToken` from `userA` via `deposit`. Attacker (no stake, or a small stake) calls `stakingToken.transfer(address(masterMagpie), 900)` directly (bypassing `deposit`). As the same manager, call `queueNewRewards(1000, rewardToken)` with `totalStaked()` now returning `1000` instead of `100`.
4. Assert `rewardPerTokenStored` in the attack run is `10x` smaller than in the control run, and `userA.earned(rewardToken)` in the attack run is `10x` smaller than in the control run, despite `userA`'s tracked stake and the queued reward amount being identical in both runs.
5. Attempt to have the attacker withdraw the `900` raw-transferred tokens via `MasterMagpie.withdraw`; confirm (or refute) whether this reverts/fails due to lack of tracked `user.amount`, establishing whether the tokens are permanently stuck (pure griefing) or recoverable (profitable attack).

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
