## Title
Ethereum-typed transaction sender validation bypasses error checking, using zero-address before validating recovery error - (File: blockchain/types/transaction.go)

### Summary
`Transaction.ValidateSender` for Ethereum-typed transactions calls `Sender(signer, tx)` and uses the returned `addr` in `p.GetKey(addr)` before checking the accompanying `err`, matching the report's bug class of "using variables created alongside an error."

### Finding Description
In `ValidateSender`, the Ethereum-transaction branch is: [1](#0-0) 

`addr, err := Sender(signer, tx)` is immediately followed by `p.GetKey(addr)` — the account-key lookup executes using `addr` regardless of whether `err` is non-nil. When `Sender()` fails (e.g., malformed or invalid signature `V/R/S` from an unauthenticated caller), `addr` is the zero value `common.Address{}`. `Sender()` itself, for an Ethereum transaction, only wraps `SenderFrom`, which returns `common.Address{}, err` on failure: [2](#0-1) 

The code checks `p.GetKey(addr).Type().IsLegacyAccountKey()` before ever inspecting `err`, and only returns `err` afterward at line 911 — after already committing to `tx.validatedSender = addr` (the zero address) when `tx.validatedSender == (common.Address{})`, i.e. on a fresh transaction object: [3](#0-2) 

This differs from the correctly-guarded non-Ethereum branch a few lines below, which checks `err` immediately after `SenderPubkey`: [4](#0-3) 

### Impact Explanation
An attacker submits an Ethereum-typed transaction (`LegacyTx`/`DynamicFeeTx`/etc.) with a syntactically-valid-but-cryptographically-invalid signature via public RPC. `Sender()` fails, but the code still calls `p.GetKey(common.Address{})`. In `kaia`, an address with no on-chain account state resolves to a default `AccountKeyLegacy` (this is the standard default account key type for unset EOAs), so `IsLegacyAccountKey()` returns true and the "malformed legacy tx" check is silently satisfied on a zero address rather than the real sender. The function still returns the non-nil `err` to the caller at line 911, so the transaction is ultimately rejected upstream by callers that check the error — but the zero-address's `validatedSender`/`validatedFeePayer` fields on the `*Transaction` object get mutated as a side effect before the error is returned, and this happens even though the tx pool / EVM caller is expected to treat `err != nil` as fatal. Because a non-nil error is still returned, no direct fund movement or state divergence has been proven; the primary demonstrable defect is the reachable violation of the "check error before using its co-returned value" invariant that the reported advisory flags, with a concrete corrupted-state side effect (writing a zero address into `tx.validatedSender`) executed prior to the error being surfaced.

### Likelihood Explanation
Trivially reachable by any unprivileged transaction sender or public JSON-RPC caller submitting a single malformed Ethereum-typed transaction — no special privileges, precompiled contracts, or additional protocol conditions are required to reach the vulnerable code path.

### Recommendation
Check `err` returned by `Sender(signer, tx)` immediately, before calling `p.GetKey(addr)` or mutating `tx.validatedSender`/`tx.validatedFeePayer`, mirroring the pattern already used in the non-Ethereum branch (`SenderPubkey` checked immediately after the call).

### Proof of Concept
1. Craft an Ethereum-typed (`LegacyTx`) transaction with a syntactically valid but non-recoverable signature (e.g., `s` value that fails `crypto.ValidateSignatureValues`, or values causing `Ecrecover` to fail) and submit it via the public RPC `eth_sendRawTransaction`/`kaia_sendRawTransaction`.
2. This transaction reaches `Transaction.ValidateSender` in `blockchain/types/transaction.go`.
3. `Sender(signer, tx)` returns `(common.Address{}, err)`.
4. `p.GetKey(common.Address{})` is called and evaluated before `err` is checked, and if `tx.validatedSender == (common.Address{})`, `tx.validatedSender`/`tx.validatedFeePayer` are set to the zero address as a side effect prior to returning the error.

Note: I was unable to fully trace every downstream caller of `ValidateSender` to confirm whether any caller relies on `tx.validatedSender` being set as a cache without re-checking the returned `err`, which would elevate this from an unchecked-error-code-quality issue to a stronger authorization bypass; this bounds the confidence of the Impact section.

func (tx *Transaction) ValidateSender(signer Signer, p AccountKeyPicker, currentBlockNumber uint64) (uint64, error) {
	if tx.IsEthereumTransaction() {
		addr, err := Sender(signer, tx)
		// Legacy transaction cannot be executed unless the account has a legacy key.
		if p.GetKey(addr).Type().IsLegacyAccountKey() == false {
			return 0, kerrors.ErrLegacyTransactionMustBeWithLegacyKey
		}
		tx.mu.Lock()
		if tx.validatedSender == (common.Address{}) {
			tx.validatedSender = addr
			tx.validatedFeePayer = addr
		}
		tx.mu.Unlock()
		return 0, err

func SenderFrom(signer Signer, tx *Transaction) (common.Address, error) {
	if sc := tx.from.Load(); sc != nil {
		sigCache := sc.(sigCache)
		if signer.IsCompatibleWith(sigCache.signer, tx) {
			return sigCache.from, nil
		}
	}

	addr, err := signer.Sender(tx)
	if err != nil {
		return common.Address{}, err
	}
	tx.from.Store(sigCache{signer: signer, from: addr})
	return addr, nil
}
