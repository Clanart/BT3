### Title
Deserialized `ReceivedOutput` credits an output to a scalar offset without verifying the script_pubkey/key binding, allowing unspendable or foreign outputs to be reported as received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The JOJO report describes split accounting: collateral is credited to a `to` address while the borrow liability is recorded on `msg.sender`, so the attacker withdraws the collateral from the credited account while the debt check runs against a different identity. The analogous flaw in Serai's in-scope code is in `ReceivedOutput::read`, which decouples the two halves of a received output's identity — the `offset` (which determines which key can spend it) and the `output.script_pubkey` (which determines who actually controls it on-chain) — and never re-verifies their binding on deserialization.

### Finding Description
`Scanner` maintains the binding between a scalar offset and an on-chain script: `register_offset` inserts `script -> offset` into `self.scripts` after computing `p2tr_script_buf(self.key + GENERATOR * offset)` [1](#0-0) , and `scan_transaction` only produces a `ReceivedOutput` when `output.script_pubkey` matches a registered script [2](#0-1) . The `offset` stored on the `ReceivedOutput` is therefore guaranteed, at scan time, to be the scalar that turns the scanner's key into the key controlling that exact script.

`ReceivedOutput::read` destroys that guarantee. It reads `offset` via `Secp256k1::read_F`, then consensus-decodes an arbitrary `TxOut` and `OutPoint`, and returns the struct with no check that `output.script_pubkey == p2tr_script_buf(key + offset·G)` [3](#0-2) . Like the JOJO `deposit`/`borrow`/`withdraw` triad that lets a caller split `from` and `to` across two accounts, this splits the "who is credited" field (`offset`, which spend logic uses to derive the signing key, e.g. via `output.offset()`) from the "who is liable/actually controls the funds" field (`script_pubkey`), with no code path tying them back together. `ReceivedOutput` exposes `offset()`, `output()`, `outpoint()`, and `value()` as independent accessors [4](#0-3) , so downstream consumers see a self-consistent-looking struct while the two fields can describe entirely unrelated outputs and keys.

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` can construct `offset || TxOut || OutPoint` where the `TxOut` pays an arbitrary script (one they control, or a script belonging to a different registered offset/key) while claiming any scalar offset. Two concrete consequences:

- **Funds reported received that are not spendable**: a `ReceivedOutput` carrying a valid-looking `offset` and an `OutPoint`, but whose `TxOut.value` is large and whose `script_pubkey` was never derivable from the scanner's key. Any balance/UTXO accounting that trusts the deserialized struct credits value the signer set cannot actually spend — the produced signature would be for `key + offset·G`, which does not match the output's script, so the input is unspendable at Bitcoin consensus.
- **Output misattribution**: an output paying a *different* offset's script can be serialized with a chosen offset, causing the spending path to derive the wrong signing key for a genuinely-held UTXO — analogous to JOJO's collateral being withdrawn under the wrong account identity.

This is exactly the reported class: value is credited to one identity (the claimed offset) while the spending-control check lives on a different identity (the actual script_pubkey), and nothing reconciles them.

### Likelihood Explanation
Reachability requires an integrator to accept serialized `ReceivedOutput`s from an untrusted source rather than only from its own `Scanner`. The type is explicitly designed for serialization (`serialize()`, `write()`, `read()` at mod.rs:120-148) and `ReceivedOutput::read` is listed among the in-scope untrusted-byte sinks. Within Serai's architecture, outputs scanned by one component are relayed to others (processor/coordinator), so a malicious peer feeding forged `ReceivedOutput` bytes is a plausible path — but this is contingent on integrator usage rather than guaranteed, which bounds the severity.

### Recommendation
Make `ReceivedOutput::read` (or a dedicated `verify`/`new` constructor) re-establish the scan-time invariant: given the scanner key, require `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey` before accepting the struct. Alternatively, store the offset implicitly and derive it from a script→offset map on deserialization, mirroring how `scan_transaction` never trusts a claimed offset — it always looks it up from the verified `script_pubkey` [2](#0-1) .

### Proof of Concept
```rust
// Attacker crafts bytes consumed by ReceivedOutput::read:
//   offset  = arbitrary canonical scalar (passes Secp256k1::read_F)
//   TxOut   = { value: 1_000_000, script_pubkey: <attacker's own P2TR script> }
//   OutPoint= any plausible txid:vout
//
// ReceivedOutput::read (mod.rs:122) returns Ok(ReceivedOutput { offset, output, outpoint })
// with no check that script_pubkey == p2tr_script_buf(scanner_key + G*offset).
//
// Integrator calls .value() -> 1_000_000 credited as received;
// .offset() -> offset used to derive the spend key, which does NOT correspond
// to the attacker's script_pubkey => reported funds are unspendable.
```
Scanner-produced outputs are always internally consistent (`scan_transaction` only emits outputs whose script was registered under the returned offset), so the flaw is only observable through the deserialization path — precisely the gap the JOJO bug exploits: the crediting path and the controlling path are checked under different identities.

Caveat: I was unable to fully trace every downstream consumer of `ReceivedOutput` in `processor/src/networks/bitcoin.rs` and `coordinator` within the available iterations, so whether a specific Serai component currently feeds attacker-controlled bytes into `ReceivedOutput::read` is not confirmed; the vulnerability exists in the in-scope API regardless.
