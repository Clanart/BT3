### Title
Auto-update of a repository's Git remote URL trusts the GitHub API `clone_url` without validating the hostname, allowing a malicious/compromised API endpoint to silently redirect where the user pushes and fetches - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` rewrites a repository's default remote (`origin`) URL whenever the app refreshes GitHub repository metadata, based solely on the `clone_url` field returned by the GitHub API. The only integrity check it performs is that the URL *scheme* (http vs https) stays the same; it never checks that the hostname of the new URL matches the hostname of the existing remote or the account's endpoint. A GitHub API response (attacker-controlled per the task's valid-impact list) can therefore point `git remote set-url origin` at an attacker-controlled host, silently, with no user confirmation.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app-store.ts` derives `owner`/`name` purely by parsing the current git remote URL string (`matchGitHubRepository`), then calls `api.fetchRepository(owner, name)` and immediately hands the resulting `IAPIFullRepository` object to `updateRemoteUrl`: [1](#0-0) 

`updateRemoteUrl` then decides whether to rewrite the remote: [2](#0-1) 

The critical guard is `protocolsMatch`, which only compares `URL.parse(...).protocol` (i.e. `"https:"` vs `"https:"`), never the hostname: [3](#0-2) 

`urlMatchesRemote`/`urlsMatch`, used elsewhere in the codebase (e.g. `repository-matching.ts`), do compare hostname, owner, and name, but `updateRemoteUrl` deliberately only uses `urlMatchesRemote` to detect whether an update is *needed* (`!urlsMatch`) — it does not use it to validate that the *new* URL is reasonable relative to the account/endpoint the repository is associated with: [4](#0-3) 

Because `apiRepo.clone_url` (attacker-controlled if the API endpoint/server is compromised, e.g. a malicious or MITM'd GitHub Enterprise Server the user has added as an account) is trusted directly, and only the scheme is checked, an attacker who can influence the `fetchRepository` response can set `clone_url` to any `https://` (or `http://`) URL on any host they control. The function then calls `gitStore.setRemoteURL(...)` to overwrite the local `origin` remote with that value: [5](#0-4) 

This is invoked from a background refresh path (`repositoryWithRefreshedGitHubRepository`, called e.g. from `refreshSelectedRepositoryAfterAccountChange`), so it can happen without the user initiating any git operation, and the remote change is silent — there is no diff/confirmation UI shown before the remote URL is swapped.

### Impact Explanation
If the remote is silently repointed to an attacker-controlled host, subsequent operations initiated by the user (fetch, pull, push) will transparently talk to the attacker's server instead of the legitimate GitHub/GHES endpoint. This satisfies "silent corruption of what the user commits or pushes": the user believes they are pushing to their known repository, but the commits go to (and could be served from) an attacker-controlled remote. Depending on how git credential resolution behaves for the new host, this could also expose credentials (e.g. an HTTPS Git credential helper invocation for the new hostname) to the attacker. Because the check that is bypassed (`protocolsMatch`) was clearly *intended* to be a safety guard against unwanted remote changes ("we don't want to alter the protocol in case they are relying on a specific one"), but was implemented incompletely (scheme-only, no host/owner check), the existing guard gives a false sense of safety while not actually preventing host takeover.

### Likelihood Explanation
Exploitation requires the attacker to control the API response object returned for `repos/{owner}/{name}` (or the git/proxy layer serving it) — this matches the task's valid-impact category of "a GitHub API object" or "a git remote/proxy response" being attacker-controlled, most realistically via a compromised or malicious GitHub Enterprise Server account the victim has added to Desktop, or a MITM position that can tamper with API responses. This is a background, non-interactive path (repository info refresh), requiring no unusual user action beyond normal use of Desktop with that account.

### Recommendation
In `updateRemoteUrl`, validate that the new `clone_url`'s hostname matches the existing remote's hostname (and ideally the account's expected endpoint) before calling `setRemoteURL`, not just the scheme. Reuse the existing hostname comparison already implemented in `urlMatchesRemote`/`parseRemote` for this purpose, and consider prompting the user (or at minimum logging/telemetry) before rewriting `origin` to a different host.

### Proof of Concept
1. Add a GitHub Enterprise Server (or a MITM-capable) account to Desktop and clone a repository from it as `origin` (e.g. `https://ghe.example.com/acme/widget.git`).
2. Have the (compromised/malicious) server respond to `GET repos/acme/widget` with `clone_url: "https://evil.attacker.com/acme/widget.git"` (same scheme, different host).
3. Trigger a repository info refresh (e.g. switching accounts, or any flow that calls `repositoryWithRefreshedGitHubRepository`).
4. Observe that `updateRemoteUrl` silently calls `gitStore.setRemoteURL('origin', 'https://evil.attacker.com/acme/widget.git')` because `protocolsMatch` only compared `https:` === `https:`, with no host check, and `urlsMatch` was false (different host), satisfying the update condition — the user's next `push`/`fetch` transparently targets the attacker's host.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
