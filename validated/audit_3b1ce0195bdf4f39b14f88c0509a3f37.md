### Title
Unbounded recursive puzzle-driver matching in `Offer` parsing enables stack-overflow DoS via nested outer-puzzle layers - ([File: chia/wallet/outer_puzzles.py], [File: chia/wallet/cat_wallet/cat_outer_puzzle.py], [File: chia/wallet/trading/offer.py])

### Summary
The wallet's outer-puzzle driver dispatch (`match_puzzle`, `get_inner_puzzle`, `construct_puzzle`, `solve_puzzle`) recursively descends through nested "layers" of a curried puzzle (CAT → ownership → metadata → singleton → CR, etc.) via the `also()` chain, with no bound on nesting depth. This recursion is Python-level (not CLVM cost-metered), so an attacker who crafts a coin spend / offer with a deeply nested puzzle structure can trigger Python's `RecursionError`, crashing whatever wallet process attempts to parse or evaluate it (e.g. accepting/viewing an offer). This mirrors the reported bug class in Hats Protocol: unbounded recursive traversal of nested/linked structures leading to stack exhaustion.

### Finding Description
`match_puzzle` in [1](#0-0)  dispatches to each `DriverProtocol.match()` implementation. Each outer-puzzle driver (`CATOuterPuzzle.match`, `SingletonOuterPuzzle.match`, `OwnershipOuterPuzzle.match`, `MetadataOuterPuzzle.match`, `CROuterPuzzle.match`) recursively calls `self._match(...)` on the puzzle's inner puzzle to build a nested `PuzzleInfo` via the `"also"` key, e.g. [2](#0-1) . This mirrors `PuzzleInfo.also()` in [3](#0-2) , which is explicitly documented as "the supported way to do recursion of PuzzleInfos" — there is no depth limit anywhere in this chain.

The same unbounded recursion pattern repeats for `get_inner_puzzle`, `construct`, and `solve` in every outer-puzzle driver (CAT, singleton, ownership, metadata, CR), each calling back into `self._get_inner_puzzle` / `self._construct` / `self._solve` for the next nested layer, as seen consistently across [4](#0-3) , [5](#0-4) , and [6](#0-5) .

This matching logic is invoked by `Offer` processing on untrusted, attacker-supplied coin spends. `Offer.__post_init__` and `Offer.additions()`/`_get_offered_coins()` operate on `self._bundle.coin_spends`, whose `puzzle_reveal` fields come directly from the offer file/spend bundle a counterparty sends — a wallet user receiving an offer (via `chia wallet take_offer`, GUI offer viewer, or DL/NFT/CAT wallet syncing) will have `match_puzzle(parent_puzzle)` called on the attacker-controlled `parent_spend.puzzle_reveal`, per [7](#0-6) . A `puzzle_reveal` can be constructed as an arbitrary, deeply-curried CLVM program whose structural layers (CAT-in-CAT-in-CAT, etc.) match the driver patterns thousands of levels deep. Because `curry`/`uncurry`/`match` operations don't execute the CLVM program (so they aren't cost-metered against `MAX_BLOCK_COST_CLVM`), an attacker can cheaply construct such nesting.

Note: elsewhere in the codebase the project has explicitly hardened analogous tree-walk code against this exact class of bug — `sha256_treehash` is deliberately implemented as an iterative/stack-based algorithm "so we don't have to worry about blowing out the python stack" per [8](#0-7) , and Data Layer merkle-tree insertion explicitly raises `RecursionDepthExceededError` to bound recursion depth (see `test_insert_into_data_store_from_file_line_graph_depth` in [9](#0-8) ). The outer-puzzle driver dispatch chain in `chia/wallet/outer_puzzles.py` and its associated driver classes have no equivalent protection.

### Impact Explanation
This is a spend/offer-triggered process crash (unhandled `RecursionError`) in the wallet process handling an untrusted offer or coin spend. It does not directly cause fund loss, but it is a transaction-processing halt reachable by an unprivileged offer counterparty or spend-bundle submitter targeting a wallet client — matching the accepted "spend-triggered transaction-processing halt" impact category. Repeated malicious offers could be used to reliably crash/DoS a wallet's offer-viewing or take-offer workflow.

### Likelihood Explanation
Medium. Constructing a deeply nested but structurally valid puzzle (satisfying `match_cat_puzzle`/`match_ownership_layer_puzzle`/etc. mod-hash checks at each layer) purely for matching purposes is inexpensive (no CLVM execution/cost accounting is required to pass through `match`), so an attacker can create an offer file with thousands of nested layers without needing to actually spend real value or produce a valid signature until the point recursion is triggered during offer inspection (`get_offered_coins`/`additions()`), which happens before signature validation.

### Recommendation
Convert the `also()`-chain traversal in `chia/wallet/outer_puzzles.py` and each `DriverProtocol` implementation (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, `CROuterPuzzle`, `RevocationOuterPuzzle`) from recursive dispatch to an iterative loop with an explicit maximum nesting depth (analogous to the `RecursionDepthExceededError` guard already used in the Data Layer merkle code and the iterative `sha256_treehash` implementation). Reject/short-circuit `Offer` parsing when puzzle-layer nesting exceeds a sane bound before calling `match_puzzle`/`get_inner_puzzle`/`construct_puzzle`/`solve_puzzle`.

### Proof of Concept
Conceptual PoC (not run, since tool access is unavailable in this session):
1. Programmatically build a puzzle `P_0 = ACS` (accept-condition puzzle), then repeatedly wrap: `P_{i+1} = construct_cat_puzzle(CAT_MOD, tail, P_i)` for `i` in `range(N)` with `N` large (e.g. 5,000–10,000), matching the pattern already exercised in `test_cat_outer_puzzle` (`double_cat_puzzle = construct_cat_puzzle(CAT_MOD, tail, cat_puzzle)`) per [10](#0-9) , but iterated many more times than the existing test's single nesting.
2. Wrap `P_N` as the `puzzle_reveal` of a `CoinSpend` in a `WalletSpendBundle`, and build an `Offer` object from it (or send it as an offer file to a victim wallet).
3. When the victim wallet inspects the offer (e.g. via `Offer._get_offered_coins()` calling `match_puzzle(parent_puzzle)`, per [11](#0-10) ), the recursive `CATOuterPuzzle.match` → `self._match` chain recurses `N` times, exceeding Python's default recursion limit (1000) and raising an unhandled `RecursionError`, crashing the offer-viewing/take-offer code path.

@pytest.mark.anyio
@pytest.mark.parametrize("depth", [1000, 100_000])
async def test_insert_into_data_store_from_file_line_graph_depth(
    data_store: DataStore,
    store_id: bytes32,
    tmp_path: Path,
    depth: int,
) -> None:
    # Binary "line graph":
    #   1 -> leaf_1, 2
    #   2 -> leaf_2, 3
    #   ...
    #   depth -> leaf_depth, leaf_end
    #
    # This stresses depth/stack handling while staying strictly binary.
    #
    # Node IDs:
    # - internal nodes: 1..depth
    # - per-level leaf nodes: (depth+1)..(2*depth)
    # - final leaf: (2*depth+1)
    internal_first = 1
    internal_last = depth
    leaf_base = internal_last + 1
    leaf_end = (2 * depth) + 1

    edges: list[tuple[int, int]] = []
    for i in range(internal_first, internal_last):
        # Order matters: first edge is left child, second edge is right child.
        edges.append((i, leaf_base + (i - internal_first)))  # unique leaf for this internal node
        edges.append((i, i + 1))  # next internal node

    # last internal points to its leaf and a final leaf
    edges.append((internal_last, leaf_base + (internal_last - internal_first)))
    edges.append((internal_last, leaf_end))

    filename = tmp_path / f"line_graph_depth_{depth}.dat"
    root_hash = create_graph_util(filename, edges)

    with pytest.raises(chia_rs.datalayer.RecursionDepthExceededError):
        await data_store.insert_into_data_store_from_file(store_id, root_hash, filename)

def test_cat_outer_puzzle() -> None:
