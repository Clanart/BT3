### Title
Unhandled arithmetic underflow in mempool fee computation causes uncaught exception on minting-style spend bundles - (File: chia/full_node/mempool_manager.py)

### Summary
`MempoolManager.validate_spend_bundle()` computes the transaction fee as `fees = uint64(removal_amount - addition_amount)` without first checking that `removal_amount >= addition_amount`. This mirrors the reported Solidity bug class: a value that is expected to only shrink (or stay non‑negative) is subtracted unconditionally into an unsigned type, and once the subtrahend exceeds the minuend the conversion underflows and raises instead of being handled gracefully.

### Finding Description
In `chia/full_node/mempool_manager.py`, inside `validate_spend_bundle()`: [1](#0-0) 

`removal_amount` is the sum of the amounts of coins being spent, and `addition_amount` is the sum of the amounts of the `CREATE_COIN` outputs declared in the spend bundle's conditions (accumulated earlier at [2](#0-1) ). Nothing in `validate_spend_bundle()` verifies `removal_amount >= addition_amount` before the subtraction at line 814. A spend bundle is fully attacker/user controlled: any wallet-signed spend of an owned coin can include a `CREATE_COIN` condition requesting an output amount larger than the coin being spent (CLVM does not itself enforce the total-value-conserved rule; that check only exists later, at block-body/consensus validation in `chia/consensus/block_body_validation.py`, where the equivalent computation is explicitly guarded): [3](#0-2) 

Note that this consensus-layer code explicitly performs the `removed < added` check and returns `Err.MINTING_COIN` *before* subtracting, and even leaves an `assert fees >= 0`. The mempool-layer code, which runs earlier in the pipeline (when a single spend bundle is submitted to the mempool, not yet included in a block), has no equivalent pre-check before calling `uint64(removal_amount - addition_amount)`. Because `uint64(...)` (from `chia_rs.sized_ints`) raises on negative input, a spend bundle whose total `CREATE_COIN` amounts exceed its total input amounts (an otherwise-syntactically-valid, correctly-signed "minting" attempt that is *supposed* to be rejected with a controlled `Err.MINTING_COIN`/similar) instead raises an unhandled `ValueError` inside `validate_spend_bundle()`.

This exception is not caught anywhere between `validate_spend_bundle()` and its caller `add_spend_bundle()`: [4](#0-3) 

so it propagates out of the normal `(Err, item, conflicts)` / `SpendBundleAddInfo` control-flow contract that the rest of the mempool admission pipeline (and its callers such as `respond_transaction`) expect.

### Impact Explanation
Any unprivileged spend-bundle submitter can construct a spend bundle from coins they control (or even a bundle with a valid signature over their own coin) that requests creation of an output whose amount exceeds the input amount. Submitting such a bundle to `MempoolManager.add_spend_bundle()`/`validate_spend_bundle()` triggers an unhandled `ValueError` instead of the intended, well-formed `Err.MINTING_COIN`-style rejection. This is a spend-triggered halt of the mempool's transaction-processing/admission logic for that call path: the exception bypasses the structured error-handling contract the rest of the codebase relies on (`(err, item, conflicts)` tuples, `SpendBundleAddInfo`), and depending on how the exception surfaces to the calling protocol handler (e.g. `respond_transaction`), it can crash or abort the coroutine handling that peer's transaction submission rather than cleanly rejecting the malformed bundle.

### Likelihood Explanation
High likelihood of reachability: constructing an addition sum greater than the removal sum requires nothing more than crafting `CREATE_COIN` conditions with an inflated amount in an otherwise normally-signed spend — no special privileges, no malicious peer/node behavior, and no cryptographic breaks are needed. It is a single, cheaply repeatable spend bundle submission from any wallet user or RPC caller.

### Recommendation
Add an explicit guard before the subtraction, mirroring the consensus-layer check in `block_body_validation.py`:
```python
if addition_amount > removal_amount:
    return Err.MINTING_COIN, None, []
fees = uint64(removal_amount - addition_amount)
```
This converts the underflow into a controlled, documented rejection path consistent with the rest of the mempool/consensus code, instead of an unhandled exception.

### Proof of Concept
1. Build a spend bundle spending a single owned coin of amount `N`.
2. Include a `CREATE_COIN` condition with amount `N + 1` (any puzzle the sender controls can emit this condition; CLVM execution itself does not restrict output amount relative to input amount).
3. Sign the spend normally (valid `AGG_SIG` over the actual coin owned).
4. Submit via `respond_transaction` / RPC push_tx so it reaches `MempoolManager.add_spend_bundle()` → `validate_spend_bundle()`.
5. `addition_amount` (`N+1`) exceeds `removal_amount` (`N`); `uint64(removal_amount - addition_amount)` at line 814 raises `ValueError` uncaught by any surrounding handler in the mempool admission pipeline, instead of returning the expected `Err.MINTING_COIN` (or similar) rejection.

Note: I was unable to fully trace, within the available indexed context, whether the outer full-node protocol handler that calls into `add_spend_bundle` (e.g. `respond_transaction`) wraps this specific call in a broad try/except that would fully absorb the exception without any denial-of-service effect; this residual uncertainty should be verified directly in a full checkout of `chia/full_node/full_node.py`'s `add_transaction`/`respond_transaction` handling before treating the DoS impact as fully confirmed.
