### Title
Author's disagreement reaction can be silently dropped by unpaginated reactions fetch, bypassing the auto-close override guard - (File: `scripts/auto-close-duplicates.ts`)

### Summary
The `authorThumbsDown` guard in `autoCloseDuplicates()` only inspects the first page of the GitHub reactions API response, which defaults to 30 items per page and is not explicitly paginated in the script. An unprivileged GitHub user can pad the bot's duplicate-detection comment with enough reactions to push the true issue author's `-1` reaction outside the fetched window, causing the guard to evaluate `authorThumbsDown` as `false` even though the author expressed disagreement, allowing `closeIssueAsDuplicate` to run against the author's intent.

### Finding Description
The guard is implemented as: [1](#0-0) 

The reactions are fetched with a single, unpaginated call: [2](#0-1) 

`githubRequest` passes the endpoint straight through with no `per_page`/`page` parameters and no loop to follow pagination (unlike the issue-listing logic earlier in the same file, which explicitly paginates with a `while (true)` loop and `page` increments): [3](#0-2) 

GitHub's `/reactions` list endpoints default to 30 items per page (up to 100 if `per_page` is passed, which it is not here). Any unprivileged GitHub user can react to the bot's publicly visible "Found ... possible duplicate" comment. A single account can add up to 8 distinct reaction types (`+1`, `-1`, `laugh`, `hooray`, `confused`, `heart`, `rocket`, `eyes`) per comment, so a handful of throwaway accounts (well within reach of an unprivileged actor with no special privilege on the target repo) is sufficient to accumulate 30+ reactions on the comment before or interleaved with the real author's `-1` reaction. If the true author's `-1` reaction is not among the first page returned, `reactions.some(...)` never sees it, `authorThumbsDown` evaluates to `false`, and the script proceeds to call `closeIssueAsDuplicate`, closing the issue despite the author's explicit disagreement.

This is distinct from the "near-miss content string" or "spoofed user.id" variants raised in the question — GitHub's reaction `content` field is a fixed, server-validated enum (a client cannot submit `"confused"` and have GitHub store it as `-1 "` with trailing whitespace, and `user.id` is an immutable, non-spoofable identity value), so those specific vectors are not reachable. The actually reachable bypass is the missing pagination handling on the reactions fetch, which the question's phrase "paginated/stale reaction data" correctly gestures at.

### Impact Explanation
This breaks the "deny means deny" invariant of the auto-close automation: an issue author who explicitly signals disagreement with an auto-generated duplicate determination can still have their issue automatically closed and mislabeled `duplicate`, with an automated comment posted on their behalf, purely because unrelated third-party reactions pushed their signal out of the unpaginated response window. The impact is limited to this specific triage automation (closing/mislabeling an issue and posting a bot comment); it does not grant code execution, secret disclosure, or workspace/tool access.

### Likelihood Explanation
Exploitation requires only unauthenticated-adjacent GitHub interaction (reacting to a public comment) via a small number of accounts — no repo write access, no maintainer/admin privilege, and no exploitation of Claude Code hooks/tools is needed. The precondition (comment reaching 30+ reactions before the fetch, with the author's `-1` outside the returned page) is a matter of reaction ordering/volume, which is plausible on any issue that attracts community pile-on reactions, and is trivially achievable by a determined attacker using a handful of accounts.

### Recommendation
Paginate the reactions fetch the same way issues are paginated earlier in the file (loop over `page`/`per_page` until an empty page is returned, or use the `Link` header) before evaluating `authorThumbsDown`, so the full reaction set is considered rather than only the first page.

### Proof of Concept
Unit/integration test plan for `scripts/auto-close-duplicates.ts`:

Mock `githubRequest` such that the reactions endpoint for `lastDupeComment.id` returns exactly 30 reactions from distinct non-author users on "page 1" (i.e., simulate the un-paginated call returning only the first page), and returns the real author's `{ user: { id: issue.user.id }, content: "-1" }` reaction only on a hypothetical "page 2" that the current implementation never requests.
2. Run `autoCloseDuplicates()` (or a refactored, exported unit under test) against a fixture issue/comment matching all other auto-close preconditions (old dupe comment, no activity after it).
3. Assert that `closeIssueAsDuplicate` is called even though the author's `-1` reaction exists in the full (paginated) reaction set — demonstrating the guard's false negative.
4. After applying the pagination fix, re-run the same test and assert `closeIssueAsDuplicate` is never invoked, confirming the author's `-1` reaction (now retrieved from the additional page) correctly blocks auto-close.
