### Title
Malicious FROST preprocess can force the aggregate Bitcoin nonce to infinity and crash signing - (File: networks/bitcoin/src/crypto.rs)

### Summary
An unprivileged signing participant can submit a syntactically valid FROST preprocess whose nonce commitments algebraically cancel the other participants’ commitments. The resulting aggregate nonce `R` becomes the secp256k1 point at infinity. Bitcoin’s BIP-340 `Hram` then calls `x(R)`, which unconditionally expects an x-coordinate and panics, aborting the signing process.

### Finding Description
Each FROST preprocess contributes nonce commitments `(D_i, E_i)` that are parsed from untrusted bytes by `read_preprocess` and are individually required only to be canonical, non-identity points. During signing, the aggregate nonce is calculated as `Σ D_i + ρ_i Σ E_i` without checking whether the resulting point is infinity. A malicious signer who sees the honest commitments can choose `D_m = -Σ_honest D_i` and `E_m = -Σ_honest E_i`, causing the aggregate `R` to be infinity for any binding factor. `AlgorithmSignMachine::sign` passes that value to `Schnorr::sign_share`, which invokes the Bitcoin `Hram`. `Hram` calls `x(R)`, and `x` panics on the point at infinity because its compressed encoding has no x-coordinate. ### Impact Explanation
This produces a remote denial of service against threshold Bitcoin signing. The panic occurs inside the local signer while processing a protocol message, before a signature share or transaction signature is produced. In a service where this panic is not isolated, one malicious signing-set member can terminate the signer process; even if the panic is caught, the signing attempt is reliably aborted.

### Likelihood Explanation
The attack is deterministic and requires only participation in the signing set and the ability to choose the adversary’s own preprocess after observing the other preprocesses. `Curve::read_G` rejects an encoded identity point, but it does not prevent two nonzero adversarial commitments from canceling the honest aggregate. This is therefore not dependent on a negligible random event.

### Recommendation
Check every aggregate nonce returned by `BindingFactor::nonces` for `is_identity()` and return a `FrostError` identifying the signing session as invalid rather than passing infinity into algorithm-specific `Hram` implementations. The Bitcoin `Hram` should also be made non-panicking where possible, but the aggregate-nonce invariant should be enforced in `crypto/frost` so all algorithms are protected.

### Proof of Concept
For a two-party Bitcoin signing session, let the honest participant submit commitments `(D_h, E_h)`. The attacker submits:

```text
D_a = -D_h
E_a = -E_h
```

Both points are valid non-identity secp256k1 encodings and pass `GeneratorCommitments::read`. The aggregate nonce becomes:

```text
R = (D_h + D_a) + ρ * (E_h + E_a)
  = identity + ρ * identity
  = identity
```

`AlgorithmSignMachine::sign` then calls `Hram::hram(&R, ...)` through `Schnorr::sign_share`, and `Hram` calls `x(R)`, which panics at `encoded.x().expect("point at infinity")`.
