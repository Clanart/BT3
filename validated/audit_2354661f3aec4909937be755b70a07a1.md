### Title
Ed448 accepts small-order public keys, enabling Schnorr signature forgery - (File: crypto/ed448/src/point.rs)

### Summary
`crypto/ed448/src/point.rs` implements the subgroup check as `((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()`. Because `Scalar::ZERO - Scalar::ONE` is `-1`, this computes `(-P) + P`, which is identity for every point. As a result, `Point::from_bytes` accepts canonical non-identity points outside Ed448's prime-order subgroup.

These points can enter through `Ciphersuite::read_G`, which validates canonical encoding but relies on `GroupEncoding::from_bytes` for subgroup membership. `SchnorrSignature::read` then accepts signatures using such points as `R`, and `SchnorrSignature::verify` applies the uncofactored equation `R + cA - sG = 0`.

### Finding Description
The defective check is here: [1](#0-0) 

`Scalar::ZERO - Scalar::ONE` is the scalar `-1`, not the prime subgroup order. Therefore `is_torsion_free` returns true for every point. `GroupEncoding::from_bytes` calls this check and consequently accepts invalid small-order points.

The generic deserializer only checks canonicality after `from_bytes`: [2](#0-1) 

`SchnorrSignature::read` exposes this to untrusted signature bytes: [3](#0-2) 

Verification uses the ordinary prime-subgroup equation without clearing the cofactor: [4](#0-3) 

### Impact Explanation
An attacker can submit an Ed448 public key consisting of a canonical small-order point `A`. For such a key there is no discrete logarithm relative to the standard generator, but the verifier can still accept a Schnorr signature.

For an order-4 point `A`, choose `s = 0` and a torsion nonce `R`. The verification equation becomes:

```text
R + cA = 0
```

This only requires `c ≡ -r mod 4`, where `R = rA`. Because there are only four residue classes modulo the cofactor, an attacker can vary the message, nonce encoding choice, or other challenge-bound data until the challenge satisfies this congruence. The result is a validly parsed `(R, s)` accepted by `SchnorrSignature::verify` despite the attacker not possessing a private key for `A`.

This is a concrete forged signature/proof path reachable entirely from public bytes supplied to `Ed448::read_G` and `SchnorrSignature::read`.

### Likelihood Explanation
The torsion subgroup is small enough that satisfying the required challenge congruence is practical. Any protocol that accepts attacker-selected Ed448 public keys or verifies Schnorr signatures for externally supplied Ed448 identities is exposed. The vulnerability is in the deserialization path itself and does not require leaked keys, malicious local state, collusion, or misuse of a documented private invariant.

### Recommendation
Implement a real subgroup membership check in `Point::is_torsion_free`. For Ed448, multiply the candidate by the prime subgroup order (or equivalently multiply by the cofactor and verify the result lies in the intended prime-order identity relationship, according to the implementation's representation) before accepting it in `GroupEncoding::from_bytes`.

At minimum, replace the current `-P + P` check with multiplication by the prime subgroup order and require identity. Add tests for canonical Ed448 points of order 2 and 4 and verify `Ciphersuite::read_G` rejects them.

### Proof of Concept
The defect is directly visible in the subgroup test:

```rust
// crypto/ed448/src/point.rs
fn is_torsion_free(&self) -> Choice {
  ((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
}
```

For every point `P`:

```text
P * (-1) + P = -P + P = 0
```

Thus the check is vacuous. A canonical order-4 Ed448 point passes `Point::from_bytes`, then `Ed448::read_G`, even though `Point` claims `PrimeGroup`.

For a signature forgery against such a public key:

1. Choose an order-4 public key `A`.
2. Use `s = 0`.
3. Select `R` from `{0, A, 2A, 3A}` such that `R + cA = 0`, where `c` is the protocol's Schnorr challenge over `R`, `A`, and the message.
4. If the current challenge residue is wrong, change the message or repeat with another torsion nonce candidate until `c mod 4` has the required value.
5. Encode the resulting `R` and `s` and submit them to `SchnorrSignature::read`.
6. `SchnorrSignature::verify(A, c)` accepts the forged signature because its multiexponentiation evaluates `R + cA - 0G = identity`.
