### Title
Quadratic Lagrange interpolation in `ThresholdKeys::read` enables remote denial of service - (`crypto/dkg/src/lib.rs`)

### Summary
`ThresholdKeys::<C>::read` accepts attacker-controlled `t`/`n` values and `n` verification shares, then calls `ThresholdKeys::new`. For `Interpolation::Lagrange`, `ThresholdKeys::new` computes an interpolation factor for each of `t` participants, while each factor iterates over all `t` included participants. The result is Θ(t²) scalar operations from a linear-size public encoding.

### Finding Description
`ThresholdKeys::read` deserializes attacker-controlled `t`, `n`, participant index, interpolation mode, secret share, and `n` verification shares [1](#0-0) . Setting the interpolation byte to `1` selects `Interpolation::Lagrange` [2](#0-1) . `ThresholdKeys::new` then computes the group key by evaluating `interpolation_factor` for every participant `1..=t` [3](#0-2) . Each Lagrange `interpolation_factor` call iterates over the complete included set, multiplying once per other participant [4](#0-3) .

Therefore, deserialization is Θ(n²) field work when `t = n`, despite the serialized input being only Θ(n).

### Impact Explanation
An unprivileged party that can submit untrusted bytes to `ThresholdKeys::read` can cause disproportionate CPU consumption. With the maximum representable `t = n = 65,535`, the parser performs more than 4.2 billion field multiply/subtract operations after reading roughly `n` encoded group elements. This can stall or exhaust the processing thread handling threshold-key material.

### Likelihood Explanation
The path requires only attacker-controlled bytes passed to `ThresholdKeys::read`; no valid DKG transcript, signature, threshold cooperation, or secret knowledge is required. The encoded parameters are accepted up to `u16` bounds by `ThresholdParams::new` as long as `t <= n` and `i <= n` [5](#0-4) . Invalid or arbitrary verification-share encodings still require the attacker to provide syntactically valid points, but those points do not need to correspond to a meaningful threshold secret.

### Recommendation
Avoid recomputing each Lagrange coefficient independently. Compute the `t` group-key interpolation coefficients in aggregate, cache repeated products, or use an O(t log² t) / O(t) product-tree formulation. Alternatively, impose a bounded participant limit or precompute/cache the group key so untrusted deserialization cannot trigger unbounded quadratic work.

### Proof of Concept
1. Construct a `ThresholdKeys<C>` byte stream with:
   - the expected `C::ID`,
   - `t = 65,535`,
   - `n = 65,535`,
   - `i = 1`,
   - interpolation byte `1` (`Lagrange`),
   - one canonical scalar for `secret_share`,
   - `65,535` canonical encoded points for verification shares.
2. Pass it to `ThresholdKeys::<C>::read`.
3. `ThresholdKeys::new` invokes `interpolation_factor` `65,535` times.
4. Each invocation scans all `65,535` included participants, producing approximately `65,535 × 65,534` field multiply/subtract operations.

The input remains only a few megabytes, while CPU work grows quadratically with `n`.

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
