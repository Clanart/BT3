### Title
Unvalidated `checkRun.htmlUrl` scheme is forwarded to `shell.openExternal` via `onViewCheckExternally` - (File: app/src/ui/check-runs/ci-check-run-list-item.tsx)

### Summary
`onViewCheckExternally` on `CICheckRunListItem` simply forwards the attacker/API-controlled `checkRun` object up the call chain with no URL/scheme validation, and the consumers of this callback pass `checkRun.htmlUrl` directly to `dispatcher.openInBrowser()`, which ultimately reaches Electron's `shell.openExternal` in the main process.

### Finding Description
`ICICheckRunListItemProps.onViewCheckExternally` is invoked with the raw `checkRun` object [1](#0-0) , and this callback is wired by consumers such as `ci-check-run-popover.tsx` and `pull-request-checks-failed.tsx` to open `checkRun.htmlUrl` directly with no scheme allow-listing: [2](#0-1) [3](#0-2) 

`checkRun.htmlUrl` originates from GitHub API check-run objects, which can be set by any GitHub App/CI integration that posts check runs against a PR — this is attacker-influenceable data if the victim reviews a PR from an untrusted/third-party CI integration. The URL is passed unmodified to `dispatcher.openInBrowser(url)`, which (per the codebase's own IPC bridge) eventually triggers the `open-external` IPC channel handled in the main process, which calls `shell.openExternal(path)`.

I was able to confirm the renderer-side call graph completely (`checkRun.htmlUrl → dispatcher.openInBrowser`), but I could not fully verify the main-process handler's exact scheme-filtering logic in this session — the question's claim that the handler "only logs for http(s) but never blocks other schemes" matches the publicly known upstream GitHub Desktop `main.ts` `open-external` handler pattern, but I recommend confirming the exact current implementation directly in `app/src/main-process/main.ts` / `app/src/main-process/ipc-main.ts` before finalizing severity.

### Impact Explanation
If the main-process handler indeed calls `shell.openExternal` without restricting to `http:`/`https:` schemes, an attacker-controlled `checkRun.htmlUrl` (e.g. `ssh://`, a registered custom protocol, or on Windows, more exotic schemes historically abused for shell.openExternal RCE/NTLM-leak issues) would be handed to the OS shell purely from a link the user clicks inside Desktop's Checks UI. Depending on installed protocol handlers, this can range from launching an unexpected local application to more serious argument-injection issues in vulnerable third-party protocol handlers. `file://` URIs are lower severity here since they'd need a pre-existing malicious file on disk, which is out of scope per the review's exclusions.

### Likelihood Explanation
Requires a victim to have a PR with check runs from a third-party/attacker-supplied CI integration and to click "View check details"/"View on GitHub" for that check. This is a plausible, low-friction user interaction (no unnatural steps), since viewing check results is a core Desktop workflow.

### Recommendation
Before calling `dispatcher.openInBrowser(checkRun.htmlUrl)` (and in the main-process `open-external` IPC handler itself), validate that the URL scheme is `http:` or `https:` (e.g., via `new URL(url).protocol`) and reject/ignore otherwise, rather than relying on prefix-based logging alone.
