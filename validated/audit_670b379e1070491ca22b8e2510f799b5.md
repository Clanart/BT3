### Title
EVM ante pipeline trusts an externally-suppliable `Derived` sender identity without re-verifying it against the transaction signature - ([File: x/evm/ante/preprocess.go])

### Summary
`PreprocessUnpacked` (and the legacy-ABCI equivalent `EvmDeliverHandleSignatures`/`EvmCheckTxAnte`) treats a `MsgEVMTransaction` whose `Derived` field is already non-nil as "already preprocessed" and skips ECDSA signature recovery entirely, trusting the `SenderEVMAddr`/`SenderSeiAddr`/`PubKey` values baked into that field. The only validation performed is that `PubKey != nil` — there is no check that this claimed identity actually corresponds to a valid signature over the enclosed `txData`. This mirrors the Soft Serve bug class: an identity claim ("offer") is captured into a context object and is trusted downstream without being cleared or re-validated against real authentication.

### Finding Description
In `x/evm/ante/preprocess.go`: [1](#0-0) 
`PreprocessUnpacked` short-circuits with `return nil` whenever `msgEVMTransaction.Derived != nil` and `Derived.PubKey != nil`, without ever calling `helpers.GetAddresses`/ECDSA-recovering the sender from `V, R, S` over the actual tx hash. The comment even acknowledges this is meant to reject a message "with `Derived` set from the outside," but the guard only rejects the case where `PubKey == nil`; a fully-populated forged `Derived` (with an attacker-chosen `SenderEVMAddr`, `SenderSeiAddr`, and any non-nil `PubKey` bytes) passes straight through as if signature verification had already succeeded.

`x/evm/types/message_evm_transaction.go`'s `ValidateBasic` has the identical, insufficient guard: [2](#0-1) 

The same pattern recurs in the legacy ABCI delivery path, where `msg.Derived.SenderEVMAddr`/`SenderSeiAddr` are consumed directly and only associated (not re-verified) if `msg.Derived != nil`: [3](#0-2) 

Downstream, `EVMPreprocessDecorator.AnteHandle` and `EVMSigVerifyDecorator.AnteHandle` both consume `derived.SenderSeiAddr`/`derived.SenderEVMAddr` as the authenticated identity for the rest of the ante pipeline (association, fee charging, nonce checking, gas metering) and for setting `ctx.WithEVMSenderAddress`/`ctx.WithSeiSenderAddress`, which is what `x/evm`'s state transition ultimately uses as `msg.From`/`tx.origin`: [4](#0-3) [5](#0-4) 

At no point after this is the claimed sender re-derived from the transaction's actual ECDSA signature — exactly like Soft Serve's session-context identity being trusted post-"offer" without re-checking it against the authentication result.

### Impact Explanation
If a `MsgEVMTransaction` with a pre-populated, forged `Derived` field can be submitted (i.e., the field is part of the wire-serializable message, which the code's own defensive comments imply), an attacker can impersonate any already-associated Sei/EVM address pair — including any user's real address — and have the EVM state transition execute with that address as the effective sender. Since `AssociateAddress` is a no-op when the address is already associated, the attacker's crafted transaction is accepted with the victim's identity, letting the attacker spend the victim's usei/wei balance, invoke precompiles or CW/EVM pointer transfers as the victim, and increment/consume the victim's nonce — a direct unauthorized-transfer / fund-loss vulnerability reachable from a single submitted EVM transaction, matching the High severity of the analog.

### Likelihood Explanation
This requires only that a submitter can construct raw transaction bytes for a `MsgEVMTransaction` with the `Derived` sub-message populated and get it accepted by `ValidateBasic`/`PreprocessUnpacked`/`CheckTx`; no privileged access, validator collusion, or network position is required — it is reachable by any unprivileged transaction sender through the standard public ingestion path (mempool `CheckTx` and `DeliverTx`), making likelihood high if the field is indeed attacker-settable on the wire (which the source code's own comments explicitly anticipate as an attack the code intends, but fails, to reject).

### Recommendation
Never trust a `Derived` value that arrives already populated on an inbound `MsgEVMTransaction`; unconditionally reject any message where `Derived != nil` prior to server-side derivation (not just when `PubKey == nil`), and only allow `Derived` to be set by the node's own preprocessing logic. Alternatively, if caching serialized-in `Derived` is required for internal message construction, always re-run `helpers.GetAddresses`/ECDSA recovery against the enclosed `txData`'s signature and compare it byte-for-byte to the claimed `SenderEVMAddr`/`SenderSeiAddr`/`PubKey` before trusting it anywhere in the ante pipeline.

### Proof of Concept
1. Craft an EVM transaction body (`ethtx.LegacyTx`/`DynamicFeeTx`) with arbitrary/garbage signature fields (`V, R, S`) — signature validity of the inner tx data is irrelevant to this bypass.
2. Wrap it in a `MsgEVMTransaction` and manually set `Derived = &derived.Derived{SenderEVMAddr: <victim EVM addr>, SenderSeiAddr: <victim Sei addr>, PubKey: <any non-nil pubkey bytes>, Version: derived.Cancun, IsAssociate: false}` before marshaling to the wire bytes submitted to the node.
3. Submit via `CheckTx`/`DeliverTx`. `PreprocessUnpacked` (or `EvmCheckTxAnte`/`EvmDeliverHandleSignatures`) sees `Derived != nil && Derived.PubKey != nil`, skips signature recovery, and the ante pipeline proceeds treating the victim's address as sender/signer for fee charging, nonce checks, and EVM execution.
4. Verify (in a Devin session with full source/build access) whether `x/evm/types/tx.pb.go`'s generated `(*MsgEVMTransaction).Unmarshal` deserializes the `Derived` field from untrusted wire bytes, confirming end-to-end reachability of this crafted message from a public RPC submission.
