### Title
IntentsBase settles escrowed transaction fees in the *current* `feeToken()` instead of the token escrowed at order placement, risking wrong-token payout or fund lock after a governance fee-token change - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
This mirrors the `bribeVault`/RewardDistributor bug class: a mutable address that a claim/settlement path re-reads at payout time, rather than the value that was true when the funds were escrowed, so a later config change strands or misroutes user funds. Here, `IntentGatewayV2`/`IntentsBase` accrues order fees under a `TRANSACTION_FEES` bucket denominated in whatever the fee token was at placement time, but pays it out using `IDispatcher(host()).feeToken()` evaluated at redemption/refund time.

### Finding Description
When an order fee is collected at placement, it is escrowed under the `_orders[commitment][TRANSACTION_FEES]` accounting slot, implicitly denominated in the fee token that was active on the host at that time. When the order later settles (fill or refund), `_withdraw()` pays this bucket out by re-querying the host's *current* fee token: [1](#0-0) 

```solidity
if (finalize) {
    uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
    if (fees > 0) {
        delete _orders[body.commitment][TRANSACTION_FEES];
        IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
    }
    ...
```

The same pattern exists in the Tron fork of the gateway: [2](#0-1) 

The `feeToken` address is a governance-mutable `HostParams` field, changed via `updateHostParams`/`updateHostParamsInternal` in `EvmHost.sol`: [3](#0-2) 

That function only guards the **host's own** balance of the old fee token before allowing the swap (`CannotChangeFeeToken` if `IERC20(oldFeeToken).balanceOf(address(this)) != 0`): [4](#0-3) 

This guard has no visibility into balances held by *other* ISMP apps such as `IntentGatewayV2`, which independently escrows fee-token amounts for pending, not-yet-settled orders. So a legitimate host `feeToken` update can pass the host's own zero-balance check while the gateway still holds a nonzero balance of the old fee token committed to open orders' `TRANSACTION_FEES` buckets. Any order that settles after that point pays out `fees` (an amount denominated in old-token units) using `IERC20(newFeeToken).safeTransfer(...)`, i.e., transfers the wrong ERC20 entirely: either the wrong asset and amount if the gateway happens to hold some of the new token, or a revert (permanently locking the escrowed fee, since delete happens before/at the same time as the failing transfer attempt — actually delete happens before the call, but `safeTransfer` reverting would revert the whole `_withdraw`, and thus revert the entire settlement, i.e. block the main escrow release/refund from completing at all).

### Impact Explanation
This directly matches the required impact categories: unauthorized/incorrect transaction execution, wrong-beneficiary/wrong-amount fund movement, and possible fund loss or fund lock. Because the fee payout call is bundled in the same `_withdraw()` that releases/refunds the principal escrow, a revert on the fee leg blocks legitimate users/solvers from ever receiving their principal input tokens or output settlement — a denial of the entire order's fund release, not just the fee. If instead the new fee token happens to be held by the gateway (e.g., from other in-flight orders), the fee is paid in the wrong asset/amount, which is a fund-loss/mismatch bug.

### Likelihood Explanation
No malicious peer, relayer, or leaked key is required. The trigger is a normal, authorized `feeToken` governance update on the host (a routine operational action, not exploitation of a compromised admin) landing while any Intent Gateway order with an outstanding `TRANSACTION_FEES` balance is still unsettled — a state that is very common given orders can remain open for their full `deadline` window and cross-chain settlement round-trip time. `EvmHost` does not check for these external dependents, so nothing stops the update from proceeding while gateway state is fee-token-dependent.

### Recommendation
Snapshot the fee token address (or the fee amount already converted/settled) into the order/commitment state at placement time instead of re-reading `IDispatcher(host()).feeToken()` at settlement time. Alternatively, extend `EvmHost.updateHostParamsInternal`'s `CannotChangeFeeToken` check to also require that all registered dependent apps (or at least a documented sweep/drain step) confirm zero outstanding fee-token liabilities before a fee token change is accepted, mirroring the original report's recommended mitigation of "ensure all funds have been withdrawn before changing."

### Proof of Concept
1. User places a cross-chain order via `IntentGatewayV2`/`IntrinsicIntents`, paying `order.fees` in fee token `A`; the amount is stored in `_orders[commitment][TRANSACTION_FEES]`, and the gateway now holds token `A` for this fee.
2. Before the order settles, Hyperbridge governance calls `updateHostParams` on `EvmHost` to switch `feeToken` from `A` to `B`. The host-side check only inspects `IERC20(A).balanceOf(address(EvmHost))`, which can legitimately be zero even though the Intent Gateway (a separate contract) still holds `A` fee-token funds for this order — so the update succeeds.
3. Later, the order fills or is cancelled/refunded, invoking `_withdraw()` → `IERC20(IDispatcher(host()).feeToken())` now resolves to `B`, and `safeTransfer(beneficiary, fees)` either reverts (because the gateway holds no/insufficient `B`), blocking the entire settlement including principal escrow release, or transfers `fees` units of `B` instead of `A`, misdelivering value.

Note: I could not fully trace the exact placement-time code in `IntentsBase.sol` (the file read for lines confirming `TRANSACTION_FEES` accrual and `order.fees` handling truncated before completion in this session), so the precise accrual line numbers are not cited; the settlement-side re-read of `feeToken()` and the `EvmHost` guard scope are directly confirmed. A Devin session with full file access would be needed to pin down the exact placement-time line and confirm there is no additional per-order fee-token snapshot elsewhere in the contract.
