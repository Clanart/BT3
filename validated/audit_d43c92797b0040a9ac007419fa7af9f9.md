## Analysis

Looking for a Desktop analog to the Switchboard "wrong identifier passed to a state-mutating call" bug class, I found a strong structural match in `app/src/ui/diff/side-by-side-diff.tsx`.

### Title
Diff line-selection uses the same column for both sides, causing mismatched before/after selection state in partial commits - (File: `app/src/ui/diff/side-by-side-diff.tsx`)

### Summary
`onLineNumberCheckedChanged` is supposed to update the selection state of *both* underlying diff lines that make up a side-by-side "modified" row (the deleted line on the left/`Before` column and the added line on the right/`After` column), the same way `oracleHeartbeat` was supposed to garbage-collect `gcOracleId` while acting only on the object that triggered the call. Instead it calls the same lookup twice with the identical, single `column` argument that was actually clicked, rather than explicitly resolving one line for `DiffColumn.Before` and one for `DiffColumn.After`.

### Finding Description [1](#0-0) 

```ts
private onLineNumberCheckedChanged = (
  row: number,
  column: DiffColumn,
  isSelected: boolean
) => {
  ...
  const lineBefore = this.getDiffLineNumber(row, column)
  const lineAfter = this.getDiffLineNumber(row, column)

  if (lineBefore !== null) {
    selection = selection.withLineSelection(lineBefore, isSelected)
  }
  if (lineAfter !== null) {
    selection = selection.withLineSelection(lineAfter, isSelected)
  }

  this.props.onIncludeChanged(selection)
}
```

The naming (`lineBefore`/`lineAfter`) and the fact that both resulting values are applied unconditionally strongly implies the intended call shape was `getDiffLineNumber(row, DiffColumn.Before)` and `getDiffLineNumber(row, DiffColumn.After)`, so that toggling either checkbox on a paired modified row keeps the deletion half and addition half of that row selection-synchronized. Instead, both calls use whatever `column` the click handler actually reports, so both computed "line" values collapse onto the *same* diff line index (the one the user clicked), and the *other* side of the row is never touched.

This is structurally identical to the oracle bug: `setNumRows(oracleId, 0)` used the wrong identifier (the caller's own id) instead of the one that should have been reset (`gcOracleId`), leaving stale state for the entity that should have been cleaned up. Here, `getDiffLineNumber(row, column)` is called with the wrong identifier (the clicked column) in the place that should reference the *paired* line, leaving the paired line's `DiffSelection` state unmodified/stale.

### Impact Explanation
`DiffSelection` computed here directly drives `formatPatch` in `app/src/lib/patch-formatter.ts` via `file.selection.isSelected(absoluteIndex)` [2](#0-1) , which in turn is what `applyPatchToIndex`/`stageFiles` write into the git index for a partial commit [3](#0-2) . If the "before" and "after" halves of a modified row become desynchronized because only the clicked column's line is ever updated, a user who unchecks (or checks) a row in the side-by-side diff can end up committing/excluding content different from what the UI visually indicated — a form of silent corruption of what the user commits. Since diff content originates from files in a cloned/fetched repository (including attacker-crafted merge/rebase conflict content or attacker-authored file contents), an attacker who controls repository content can shape a "modified line" row specifically to exploit this desynchronization and get unreviewed lines silently included in — or reviewed lines silently excluded from — the user's next commit.

### Likelihood Explanation
This code path executes on every checkbox interaction in the side-by-side diff view for "modified" rows (paired delete+add), which is a common and unprivileged user action (reviewing/partially staging changes from an untrusted diff). No special permissions or unusual steps are required beyond normal use of the "select individual lines" commit feature. However, I was not able to inspect the body of `getDiffLineNumber` in this session (ran out of tool budget) to conclusively confirm it returns different diff-line indices per `DiffColumn` for a modified row rather than being a no-op for one column — this is inferred from the `lineBefore`/`lineAfter` naming and the symmetric `withLineSelection` calls, and should be verified against the function's implementation before treating this as confirmed exploitable.

### Recommendation
Change the two calls to resolve each side explicitly, e.g.:
```ts
const lineBefore = this.getDiffLineNumber(row, DiffColumn.Before)
const lineAfter = this.getDiffLineNumber(row, DiffColumn.After)
```
so that both the deletion and addition halves of a modified row are kept in sync regardless of which column's checkbox was clicked, matching the evident intent of the surrounding `if (lineBefore !== null) / if (lineAfter !== null)` logic.

### Proof of Concept
Not independently verified end-to-end due to tool-budget exhaustion before reading `getDiffLineNumber`'s implementation. Suggested verification/reproduction for a background engineer:
1. Open a repository with a text file, make a single-line modification (delete old line + add new line) so it renders as one paired "modified" row in side-by-side view.
2. In the Changes pane, use the per-line selection checkboxes to check the "before" (left) checkbox only, then inspect the resulting `DiffSelection` (or the generated patch via `formatPatch`) to see whether the "after" (right) line's selection state changed as intended.
3. Compare against clicking the "after" (right) checkbox only, and confirm whether `lineBefore`/`lineAfter` in `onLineNumberCheckedChanged` actually resolve to two different diff-line indices as the variable names imply, or resolve to the same index in both cases (confirming the bug). [4](#0-3)
