### Title
`get_payout_txs_for_withdrawal_utxos` attributes a single payout tx to multiple `withdrawals` rows sharing a `withdrawal_utxo` outpoint - ([File: core/src/database/verifier.rs])

### Summary
`Database::get_payout_txs_for_withdrawal_utxos` joins `withdrawals` to `bitcoin_syncer_spent_utxos` solely on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` scoped by `block_id`, with no constraint that this pair be unique across withdrawal indices. If two `withdrawals` rows (different Citrea indices) end up with the same `withdrawal_utxo_txid/vout` — because that field is populated verbatim from `CitreaClient::collect_withdrawal_utxos`, i.e. from user-supplied bytes passed to the Citrea Bridge contract's `withdraw()` — a single real Bitcoin payout transaction that spends that one UTXO gets matched to both rows in one query result, and `update_payout_txs_and_payer_operator_xonly_pk` commits `payout_txid`/`payout_payer_operator_xonly_pk` for both indices atomically.

### Finding Description
The binding this code must preserve is: `withdrawals.payout_txid` for index `idx` == the txid of the payout transaction that actually funded index `idx`'s specific withdrawal output. This binding is broken because attribution is keyed only on the shared `(withdrawal_utxo_txid, withdrawal_utxo_vout)` pair rather than on a per-index unique reference.

- `withdrawal_utxo_txid/vout` is written per-index by `update_withdrawal_utxo_from_citrea_withdrawal` with no cross-row uniqueness check: [1](#0-0) .
- This value originates from `CitreaClient::collect_withdrawal_utxos`, which reads whatever `(txId, outputId)` bytes were supplied to `withdraw()` on the Citrea Bridge contract for each index, with no uniqueness enforcement visible in this repo's client code: [2](#0-1)  and is written per-index in `update_citrea_deposit_and_withdrawals`: [3](#0-2) .
- Per the attacker capability list, the attacker can "choose the bytes of a withdrawal UTXO" when calling `withdraw` on the Citrea Bridge contract, so nothing in this repo stops the same physical outpoint being registered as the `withdrawal_utxo` for two different withdrawal indices `idx1`/`idx2`.
- `get_payout_txs_for_withdrawal_utxos` then joins purely on `bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout`, scoped only by `block_id`: [4](#0-3) . Because a Bitcoin outpoint can only be spent once, only one payout tx will ever exist for the shared UTXO, but the join returns `(idx1, payout_txid)` and `(idx2, payout_txid)` — the same `payout_txid` for both indices.
- `update_payout_txs_and_payer_operator_xonly_pk` then performs a bulk `UPDATE ... FROM (VALUES ...)` writing `payout_txid`, `payout_payer_operator_xonly_pk`, `payout_tx_blockhash` for every `(idx, txid, ...)` tuple it is given, with no check that the tuple's `txid` actually corresponds to a payout output matching `idx`'s registered withdrawal parameters: [5](#0-4) . Both `idx1` and `idx2` rows are committed in the same `dbtx` in one call.
- Existing guards do not catch this: `Operator::withdraw` only checks that the *specific* `withdrawal_index` it was asked to service matches its own registered `withdrawal_utxo` via `get_withdrawal_utxo_from_citrea_withdrawal` and verifies the user's Schnorr signature for that one payout tx [6](#0-5) ; it has no visibility into, and does not prevent, a second index sharing the same outpoint. `SECP.verify_schnorr` and `is_profitable` validate the payout that is actually built, not whether the DB will later misattribute it to another index. `get_payout_info_from_move_txid`, used downstream for reimbursement lookups, blindly trusts the `payout_txid`/`payout_payer_operator_xonly_pk` columns once set: [7](#0-6) .
- Once committed, there is no corrective re-scan path: the query is keyed by `block_id`, and the erroneous rows for `idx2` are truth after `dbtx.commit()`, matching the question's premise that this is permanent app state rather than a transient race.

### Impact Explanation
The false attribution lets a second, distinct withdrawal index (`idx2`) be marked `payout_txid`/`payout_payer_operator_xonly_pk` as fulfilled by a payout transaction that only paid out `idx1`'s recipient/output. Any downstream logic that uses these columns to authorize reimbursement (kickoff / collateral release tied to `idx2`'s deposit) would treat `idx2` as funded when no distinct BTC was ever sent to `idx2`'s intended output — this is the Critical category "an operator reimbursed for a payout it never funded" and correspondingly a move-to-vault UTXO for `idx2`'s deposit can be drained without a matching fronted withdrawal for that specific index. It is also permanent and irreversible for the affected index (no re-scan), so an honest operator who later actually funds `idx2`'s real payout could find `idx2` already marked handled by someone else's transaction, i.e. "an honest operator permanently unable to be reimbursed." The attack is repeatable per pair of withdrawal indices the attacker controls (each requires the attacker to own/control one Bitcoin UTXO and register it via two separate Citrea `withdraw()` calls), so blast radius scales with the number of duplicate registrations the attacker can create.

### Likelihood Explanation
This requires: (1) the Citrea Bridge contract's `withdraw()` allowing the same `(txId, outputId)` bytes to be registered for two different withdrawal indices — a precondition granted explicitly by the audit's attacker-capability list ("choose the bytes of a withdrawal UTXO") but whose actual on-chain enforcement lives in the Citrea contract, not in this repo, and could not be independently confirmed from this codebase; (2) an operator (not colluding, just doing its normal `withdraw` flow) actually fronting a payout for one of the two indices, spending the shared UTXO; and (3) that payout confirming and being finalized. Cost is limited to normal deposit/withdrawal fees and one dust UTXO the attacker controls; no key compromise or majority hashrate needed. The DB-level mis-join itself is deterministic and directly reproducible without any Citrea dependency, using the same fixtures as the existing test `update_get_payout_txs_from_citrea_withdrawal` in `core/src/database/verifier.rs`.

### Recommendation
Enforce a unique constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` in the `withdrawals` table (or reject `update_withdrawal_utxo_from_citrea_withdrawal` if the pair is already used by another `idx`), and/or change `get_payout_txs_for_withdrawal_utxos`/`update_payout_txs_and_payer_operator_xonly_pk` to additionally verify that the spending transaction's output actually matches the specific withdrawal index's registered output script/amount before crediting `payout_txid` for that index.

### Proof of Concept
Extend the existing `core/src/database/verifier.rs` test module (`update_get_payout_txs_from_citrea_withdrawal`) with a `cargo test` that:
1. Inserts one block and one spent-UTXO record for `utxo` spent by `txid` (as in the existing test).
2. Calls `upsert_move_to_vault_txid_from_citrea_deposit` and `update_withdrawal_utxo_from_citrea_withdrawal` twice, for `index1` and `index2`, both pointing at the same `utxo`.
3. Calls `db.get_payout_txs_for_withdrawal_utxos(Some(&mut dbtx), block_id)` and asserts the result contains **both** `(index1, txid)` and `(index2, txid)`.
4. Calls `db.update_payout_txs_and_payer_operator_xonly_pk` with both tuples in a single call and commits the `dbtx`.
5. Asserts, via `get_payout_info_from_move_txid` or a direct `SELECT payout_txid FROM withdrawals WHERE idx IN (index1, index2)`, that both rows now carry the same non-null `payout_txid`, proving the binding "payout for `idx2` == a payout that actually funded `idx2`" is broken — `idx2` is marked paid though no transaction was ever built for it.

                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,

    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }

    async fn collect_withdrawal_utxos(
        &self,
        last_withdrawal_idx: Option<u32>,
        to_height: u64,
    ) -> Result<Vec<(u64, OutPoint)>, BridgeError> {
        let mut utxos = vec![];

        let mut start_idx = match last_withdrawal_idx {
            Some(idx) => idx + 1,
            None => 0,
        };

        loop {
            let withdrawal_utxo = self
                .contract
                .withdrawalUTXOs(U256::from(start_idx))
                .block(BlockId::Number(BlockNumberOrTag::Number(to_height)))
                .call()
                .await;
            match withdrawal_utxo {
                Err(e) if e.to_string().contains("execution reverted") => {
                    tracing::trace!("Withdrawal utxo not found for index, error: {:?}", e);
                    break;
                }
                Err(e) => return Err(e.into()),
                Ok(_) => {}
            }
            let withdrawal_utxo = withdrawal_utxo.expect("Failed to get withdrawal UTXO");
            let txid = withdrawal_utxo.txId.0;
            let txid =
                Txid::from_slice(txid.as_ref()).wrap_err("Failed to convert txid to Txid")?;
            let vout = withdrawal_utxo.outputId.0;
            let vout = u32::from_le_bytes(vout);
            let utxo = OutPoint { txid, vout };
            utxos.push((start_idx as u64, utxo));
            start_idx += 1;
        }
        Ok(utxos)
    }
