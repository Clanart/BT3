### Title
PedPoP accepts the identity point as a participant's ECDH encryption key, making encrypted secret shares publicly decryptable - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to the free5GC invalid-curve bug (CVE-2023-46324), where an unvalidated public key was fed into an ECDH shared-secret computation, PedPoP's `Encryption::encrypt` computes a ChaCha20 key from `attacker_supplied_enc_key * ephemeral_key` without checking that the recipient's registered encryption key is a valid, non-identity group element. `EdwardsPoint::from_bytes` (and `C::read_G` generally) rejects non-torsion-free points but does not reject the identity point, so a malicious DKG participant can register `enc_key = identity`, forcing every ECDH shared secret computed against them to be the publicly known identity point — turning their "encrypted" secret shares into ciphertext any observer can decrypt.

### Finding Description
- Each participant registers an encryption public key via `EncryptionKeyMessage`, whose `enc_key` field is deserialized with `C::read_G` and stored verbatim in `Decryption::enc_keys` with no validation (`encryption.rs`, `Decryption::register`, lines 351-362).
- For Ed25519, `EdwardsPoint::from_bytes` checks decompression validity and `is_torsion_free()`, but never checks `is_identity()` (`crypto/dalek-ff-group/src/lib.rs`, lines 429-437). The identity is torsion-free, so a 32-byte encoding of the identity point is accepted.
- `encrypt` then computes `ecdh::<C>(&key, to)` = `to * key` (line 95-97, 154). With `to = identity`, the shared secret is `identity` regardless of the ephemeral key.
- `cipher` derives the ChaCha20 key by hashing the shared secret's encoding plus the public `context` and a fixed IV (`DKG IV v0.2\0`) (lines 101-132). An identity shared secret produces a fully public, reproducible keystream.
- The same issue exists in the incoming direction: `EncryptedMessage::read` accepts `key = identity` (line 173) and `decrypt` computes `ecdh(&self.enc_key, msg.key)` (line 487); the Schnorr PoP is trivially satisfiable for `key = identity` (`s*G = R + c*I = R`), so no check catches it — though this direction leaks nothing since the resulting blame proof only reveals the constant identity.

### Impact Explanation
All `EncryptedMessage`s produced by every honest participant addressed to the malicious participant are encrypted under a keystream derived from `identity || context`, which any third party can recompute. Anyone who observes the (authenticated but not necessarily confidential) channel carrying the DKG secret-share messages recovers the plaintext `SecretShare` values intended for the malicious participant. This is secret key-share material leaking to parties outside the protocol — key share recovery reachable purely from attacker-supplied bytes (`enc_key` in `EncryptionKeyMessage`). In a t-of-n FROST multisig, leaked shares reduce the effective security threshold for any observer who combines them with shares they otherwise obtain.

### Likelihood Explanation
Requires a malicious DKG participant registering an identity encryption key — a single crafted 32-byte value in the round-1 `EncryptionKeyMessage`. No collusion or special privileges needed; the identity encoding deserializes successfully and no code path validates it. The attack is passive afterward: exploitation is deterministic since `identity * x = identity` always.

### Recommendation
Reject the identity point wherever untrusted group elements are deserialized for ECDH use. Options:
- In `Decryption::register`, return an error if `msg.enc_key.is_identity()` (and consider enforcing it in `EncryptedMessage::read`/`decrypt` for `msg.key`).
- Alternatively, tighten `EdwardsPoint::from_bytes` / `C::read_G` to reject identity for all in-scope ciphersuites (`dalek-ff-group`, `ed448`, `kp256`), matching the `Group::random` behavior that already bans identity.
- Optionally, also reject identity results in `ecdh` (`if ecdh.is_identity() { abort }`) as defense-in-depth, mirroring the "contributory behavior" checks recommended for ECDH protocols.

### Proof of Concept
```rust
// Malicious participant P_mal registers an identity encryption key.
// Ed25519 identity encodes as CompressedEdwardsY([1, 0, 0, ..., 0]).
let mut id_bytes = [0u8; 32];
id_bytes[0] = 1;
let id_point = <Ed25519 as Ciphersuite>::read_G(&mut &id_bytes[..]).unwrap();
// id_point == EdwardsPoint::identity() — accepted, no error.

// P_mal broadcasts EncryptionKeyMessage { enc_key: id_point, msg: commitments }.
// Honest participant P_i calls Decryption::register(P_mal, msg) — stored unchecked.
// P_i then calls Encryption::encrypt(rng, P_mal, share_bytes), which computes:
//   ecdh = id_point * ephemeral_key = identity   (encryption.rs:96)
//   ChaCha20 key = H("DKG Encryption v0.2" || context || identity.to_bytes())
//   IV = "DKG IV v0.2\0"                          (encryption.rs:124-126)
// An eavesdropper recomputes the identical key/IV from public data and
// XORs the keystream against msg to recover the SecretShare plaintext.
```
