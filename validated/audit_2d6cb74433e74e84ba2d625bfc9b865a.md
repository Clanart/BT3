### Title
`InternalWithdraw` gRPC Endpoint Bypasses `aggregator_verification_address` Authorization Check Present in `Withdraw` — (`File: core/src/rpc/operator.rs`)

---

### Summary

The `ClementineOperator` gRPC service exposes two withdrawal endpoints: `Withdraw` and `InternalWithdraw`. When `aggregator_verification_address` is configured, `Withdraw` strictly enforces an ECDSA authorization signature from the aggregator before processing a payout. `InternalWithdraw` accepts the same `WithdrawParams` and calls the identical `operator.withdraw()` logic, but **completely omits the authorization check**. Any party with network access to the operator's gRPC port can call `InternalWithdraw` directly, bypassing the aggregator's approval gate and forcing the operator to front BTC for withdrawals the aggregator has not authorized.

---

### Finding Description

In `core/src/rpc/operator.rs`, the two RPC handlers diverge in their authorization logic:

**`withdraw` — STRICT path** (lines 192–258):
```rust
// if verification address is set in config, check if verification signature is valid
if let Some(address_in_config) = self.operator.config.aggregator_verification_address {
    let verification_signature = params.verification_signature ...;
    if let Some(verification_signature) = verification_signature {
        let address_from_sig = recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>(...)?;
        if address_from_sig != address_in_config {
            return Err(BridgeError::InvalidECDSAVerificationSignature).map_to_status();
        }
    } else {
        return Err(BridgeError::ECDSAVerificationSignatureMissing).map_to_status();
    }
}
// ... then calls self.operator.withdraw(...)
```

**`internal_withdraw` — LENIENT path** (lines 168–190):
```rust
async fn internal_withdraw(&self, request: Request<WithdrawParams>) -> Result<Response<RawSignedTx>, Status> {
    let (withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount) =
        parser::operator::parse_withdrawal_sig_params(request.into_inner())?;
    // ❌ No aggregator_verification_address check at all
    let payout_tx = self.operator.withdraw(withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount).await?;
    Ok(Response::new(RawSignedTx::from(&payout_tx)))
}
```

Both handlers ultimately call the same `operator.withdraw()` function, which:
1. Verifies the UTXO exists on-chain and matches the Citrea-registered withdrawal UTXO
2. Checks profitability
3. Constructs and queues the payout transaction via TxSender

The `aggregator_verification_address` guard in `withdraw` is the only mechanism preventing unauthorized parties from forcing the operator to front BTC. `InternalWithdraw` is documented as "intended for operator's own use" in the proto file, but it is registered on the same `ClementineOperator` gRPC service that aggregators and other actors connect to, with no code-level enforcement of that intent.

The proto definition confirms both endpoints are on the same public service:
```protobuf
rpc InternalWithdraw(WithdrawParams) returns (RawSignedTx) {}  // no sig required
rpc Withdraw(WithdrawParamsWithSig) returns (RawSignedTx) {}   // sig enforced
```

---

### Impact Explanation

When `aggregator_verification_address` is configured (the intended production security posture), an attacker with network access to the operator's gRPC port can:

1. Observe a withdrawal UTXO registered in Citrea (public on-chain data).
2. Construct a valid `WithdrawParams` (withdrawal index, user's SIGHASH_SINGLE|ANYONECANPAY signature, UTXO outpoint, output script, amount).
3. Call `InternalWithdraw` directly, bypassing the aggregator's ECDSA authorization gate.
4. The operator's `withdraw()` logic passes all remaining checks (UTXO match, profitability) and queues a payout transaction via TxSender.
5. The operator fronts `bridge_amount` BTC (e.g., 10 BTC) for a withdrawal the aggregator never approved.

The operator's BTC liquidity is drained for each such call. Since the kickoff/reimbursement flow depends on the aggregator's coordination, an operator forced into unauthorized payouts may not recover the fronted BTC through the normal reimbursement path, resulting in direct loss of operator collateral-equivalent funds.

---

### Likelihood Explanation

- The operator's gRPC port must be reachable by the aggregator and verifiers for normal bridge operation; it is not a purely internal service.
- The CLI tool (`core/src/bin/cli.rs`) calls `internal_withdraw` directly, confirming the endpoint is reachable without the aggregator's signature.
- No mTLS enforcement is visible at the handler level for `InternalWithdraw`; the check is purely opt-in via `aggregator_verification_address` config, which is absent from `internal_withdraw`.
- A Citrea withdrawal UTXO is public on-chain data, so constructing valid `WithdrawParams` requires only the user's cooperation or observation of the mempool.

---

### Recommendation

Apply the same `aggregator_verification_address` guard to `internal_withdraw`, or remove the endpoint from the public gRPC surface and restrict it to localhost/Unix socket only. The minimal fix:

```rust
async fn internal_withdraw(&self, request: Request<WithdrawParams>) -> Result<Response<RawSignedTx>, Status> {
    // Reject if aggregator_verification_address is configured — use Withdraw instead
    if self.operator.config.aggregator_verification_address.is_some() {
        return Err(Status::permission_denied(
            "aggregator_verification_address is set; use the Withdraw RPC with a verification signature"
        ));
    }
    // ... existing logic
}
```

Alternatively, enforce the same ECDSA check in `internal_withdraw` when `aggregator_verification_address` is set, making both paths consistent.

        &self,
        withdrawal_index: u32,
        in_signature: taproot::Signature,
        in_outpoint: OutPoint,
        out_script_pubkey: ScriptBuf,
        out_amount: Amount,
    ) -> Result<Transaction, BridgeError> {
        tracing::info!(
            "Withdrawing with index: {}, in_signature: {:?}, in_outpoint: {:?}, out_script_pubkey: {}, out_amount: {}",
            withdrawal_index,
            in_signature,
            in_outpoint,
            out_script_pubkey,
            out_amount
        );

        // Prepare input and output of the payout transaction.
        let input_prevout = self.rpc.get_txout_from_outpoint(&in_outpoint).await?;
        let input_utxo = UTXO {
            outpoint: in_outpoint,
            txout: input_prevout,
        };
        let output_txout = TxOut {
            value: out_amount,
            script_pubkey: out_script_pubkey,
        };

        // Check Citrea for the withdrawal state.
        let withdrawal_utxo = self
            .db
            .get_withdrawal_utxo_from_citrea_withdrawal(None, withdrawal_index)
            .await?;

        if withdrawal_utxo != input_utxo.outpoint {
            return Err(eyre::eyre!("Input UTXO does not match withdrawal UTXO from Citrea: Input Outpoint: {0}, Withdrawal Outpoint (from Citrea): {1}", input_utxo.outpoint, withdrawal_utxo).into());
        }

        let operator_withdrawal_fee_sats =
            self.config
                .operator_withdrawal_fee_sats
                .ok_or(BridgeError::ConfigError(
                    "Operator withdrawal fee sats is not specified in configuration file"
                        .to_string(),
                ))?;
        if !Self::is_profitable(
            input_utxo.txout.value,
            output_txout.value,
            self.config.protocol_paramset().bridge_amount,
            operator_withdrawal_fee_sats,
        ) {
            return Err(eyre::eyre!("Not enough fee for operator").into());
        }
