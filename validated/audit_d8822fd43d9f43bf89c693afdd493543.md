### Title
Stale `this.state` re-read after `await` in `resolveOAuthRequest`/`authenticateWithBrowser` can bind a resolved OAuth account to a different, concurrently-started sign-in flow - (File: `app/src/lib/stores/sign-in-store.ts`)

### Summary
`resolveOAuthRequest` validates the CSRF `state` value against the *currently active* sign-in state before doing the network round-trip, but then completes the flow by re-reading `this.state` (a live, mutable field) **after** the `await`s instead of using a value captured at validation time. If the store transitions to a new `Authentication` state (e.g. a second, unrelated sign-in flow, possibly reached via the `ExistingAccountWarning` → `Authentication` transition) while the first OAuth token exchange is still pending, the account resolved from the *first* flow gets delivered to the *second* flow's `onAuthCompleted`/`resultCallback`, corrupting which account/endpoint the resolved identity is bound to.

### Finding Description
`resolveOAuthRequest` performs its CSRF check synchronously against `this.state.oauthState.state`, but the actual completion call reads `this.state` fresh, after two `await`s: [1](#0-0) 

Specifically:
- Line 341 validates `this.state.oauthState.state !== action.state` using the state object **at call time**.
- Line 348 destructures only `endpoint` from `this.state` before the awaits.
- Line 349 `await requestOAuthToken(...)` and line 352 `await fetchUser(...)` yield control back to the event loop.
- Line 353 calls `this.state.oauthState.onAuthCompleted(account)` — but `this.state` here is re-evaluated live, **not** the object that was validated at line 341.

If, during the two `await`s, the store transitions to a brand-new `Authentication` state (e.g. the user/dispatcher starts a second sign-in flow — including the `ExistingAccountWarning` → `Authentication` path taken in `authenticateWithBrowser`, lines 260-330), `this.state.oauthState` now refers to the **second** flow's `oauthState`, with its own `onAuthCompleted`/`onAuthError` closures tied to a *different* `resultCallback` and potentially a different `endpoint`/account context. The account object fetched from the *first* flow's `code`/token exchange gets passed into the second flow's `onAuthCompleted`, which resolves the second flow's promise in `authenticateWithBrowser`'s `.then` handler: [2](#0-1) 

That handler itself also re-reads `this.state` (rather than a captured reference) to decide whether to proceed and which `resultCallback` to attach to the `Success` state, so the check `this.state.kind !== SignInStep.Authentication` will still pass (because the *second* flow legitimately is in `Authentication`), masking the mismatch. The result: `emitAuthenticate(account)` fires with an account that was never validated against the CSRF token of the currently-active flow, and the wrong `resultCallback`/context receives it.

This breaks the intended invariant described in the question: `onAuthCompleted` is supposed to resolve only the account for the sign-in flow whose CSRF `state` matched at validation time; instead, due to reading `this.state` after `await` instead of capturing it beforehand, the completion can be delivered to whatever flow happens to be active by the time the network calls resolve.

### Impact Explanation
A successful race causes GitHub Desktop to attach an authenticated account to the wrong in-flight sign-in session/`resultCallback`, i.e., silent corruption of account identity binding. Depending on caller context (dotcom vs. Enterprise sign-in, or a flow triggered from `ExistingAccountWarning` for a specific existing account), this could result in the wrong account being stored/associated with an endpoint the user did not intend, or an unrelated UI flow's promise resolving with an account it never asked for.

### Likelihood Explanation
This requires a genuine race: a second `Authentication` state transition must occur (typically requiring the user or app to start a new sign-in flow) while a prior `resolveOAuthRequest` call is still awaiting `requestOAuthToken`/`fetchUser` for an earlier flow. `resolveOAuthRequest` is only invoked when a deep link with a `state` matching the currently active `oauthState.state` is delivered, so an attacker cannot arbitrarily trigger it without either the legitimate GitHub redirect or knowledge of the random `crypto.randomUUID()` CSRF token — this is not something derivable purely from "an attacker-controlled link" without also controlling or racing the legitimate OAuth callback and the app's own concurrent state transitions. I could not find any locking/serialization in `app/src/lib/stores/app-store.ts` or `app/src/ui/dispatcher/dispatcher.ts` (only 1-2 references found, not enough to confirm request queuing) that would prevent a second sign-in flow from starting while the first is still in-flight, so I cannot rule the race out, but I also could not construct a concrete, purely-attacker-driven (no cooperating legitimate user action) exploitation path within the available code.

### Recommendation
Capture the relevant `oauthState` (and `resultCallback`) into a local variable at the point the CSRF check succeeds, and use that captured reference — not `this.state` — when calling `onAuthCompleted`/`onAuthError` after the `await`s. Similarly, `authenticateWithBrowser`'s `.then`/`.catch` handlers should compare against the captured `csrfToken`/state object rather than re-reading the live `this.state`, consistent with what the `.catch` handler already does (line 320-322) but the `.then` handler (line 304-317) does not.

### Proof of Concept
Not independently verifiable in this environment (no test harness executed). Conceptually:
1. Start Enterprise sign-in for endpoint A with an existing account, reach `ExistingAccountWarning`, click continue → `authenticateWithBrowser` sets `Authentication` state with `oauthState1` (`csrf1`).
2. GitHub redirects to `x-github-client://oauth?code=C1&state=csrf1` → `resolveOAuthRequest` begins; CSRF check passes; `await requestOAuthToken` is in flight.
3. Before that resolves, start a second, unrelated sign-in flow (e.g. dotcom sign-in) → store transitions to a new `Authentication` state with `oauthState2` (`csrf2`), different `resultCallback`.
4. First `requestOAuthToken`/`fetchUser` completes; `resolveOAuthRequest` calls `this.state.oauthState.onAuthCompleted(account1)`, which is now `oauthState2.onAuthCompleted` — resolving the second flow's promise with `account1` instead of the account the second flow's own OAuth exchange would have produced.

```typescript
  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }
```
