### Title
Automatic, unconfirmed rewiring of git remotes from GitHub API data allows silent redirection of fetch/push targets - (File: `app/src/lib/stores/updates/update-remote-url.ts`, `app/src/lib/stores/git-store.ts`)

### Summary
The external report's broken invariant is: a trusted-but-untrusted-enough actor (`admin`) can overwrite a security-relevant address mapping (`l2WBaseTokenAddress`) an unlimited number of times, with no confirmation step and no limit, letting it silently redirect where funds/trust flow. The GitHub Desktop analog is the pair of background routines that rewrite a repository's git remote configuration purely from a GitHub API response, with no user confirmation and no bound on how often this can happen: `updateRemoteUrl` (which calls `gitStore.setRemoteURL`) and `addUpstreamRemoteIfNeeded` (which calls `addRemote`) in `app/src/lib/stores/git-store.ts`.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` runs during routine repository refresh. It re-derives `owner`/`name` from the *current* default remote URL via `matchGitHubRepository`, fetches the corresponding repository object from the GitHub/GHES API (`api.fetchRepository`), and then unconditionally feeds that API object into `updateRemoteUrl`: [1](#0-0) 

`updateRemoteUrl` itself will silently call `gitStore.setRemoteURL(...)` — i.e. rewrite `.git/config`'s remote URL — whenever the API's `clone_url` differs from the current remote but the *previously cached* clone URL matched it and the URL "protocol" (as parsed by the deprecated, permissive `url.parse`) is unchanged: [2](#0-1) 

Separately, `GitStore.addUpstreamRemoteIfNeeded` will add a brand-new `upstream` remote pointing at `parent.cloneURL` — taken directly from the GitHub API's fork `parent` object — with **no user confirmation at all**, as long as no remote named `upstream` already exists: [3](#0-2) 

The only guard rail Desktop has (`UpstreamAlreadyExistsError` / the `UpstreamAlreadyExists` dialog) fires solely when a remote literally named `upstream` already exists and points somewhere else — it does not gate the *first* creation of that remote, and it does not gate `updateRemoteUrl`'s rewrite of `origin` at all: [4](#0-3) 

Both `clone_url` and fork `parent.cloneURL` are values reported by the GitHub API for whatever `owner/name` currently resolves on that host — i.e., they are attacker-influenceable "GitHub API objects" in exactly the sense called out as valid impact: if the account/org that a repo's remote or fork-parent points to is renamed, deleted, and reclaimed by an attacker (classic "repo-jacking"/dangling-reference takeover, a purely remote, unprivileged action requiring no local access), the very next background refresh in Desktop will, without asking, either (a) rewrite the tracked repository's remote URL to keep pointing at the same owner/name path — now attacker-controlled — via `setRemoteURL`, or (b) auto-create an `upstream` remote aimed at the attacker's resurrected "parent" repository via `addRemote`.

### Impact Explanation
Once Desktop has silently pointed `origin` or newly created `upstream` at an attacker-controlled repository, ordinary one-click actions in Desktop (Fetch, "Update from upstream", Pull) will pull attacker-supplied refs/objects into the user's working repository's remote-tracking branches. If the user then merges or bases new work on those refs (a normal fork-contribution workflow Desktop actively encourages), attacker-authored commits are woven into what the user subsequently commits/pushes — silent corruption of the user's own history and, if pushed, of the shared project. This matches the report's core harm ("malicious/unauthorized changes... difficult to detect without constant monitoring") mapped onto git remotes instead of a token-address mapping.

### Likelihood Explanation
Exploitation requires only that an attacker control the GitHub-side identity/repo that a victim's fork or clone currently resolves to (e.g. by reclaiming a renamed/deleted owner or repo name) — no local access, no credential theft, no social engineering beyond having previously forked or cloned a repository that later becomes danglable. The rewrite is fully automatic and happens on Desktop's normal background repository-refresh cadence, without any dialog, confirmation, or rate limiting, which is precisely the "unlimited, unrestricted overwrite" pattern in the source report.

### Recommendation
- Require explicit user confirmation before `updateRemoteUrl`/`GitStore.setRemoteURL` silently changes an existing remote URL as a side effect of a background refresh, not just when a name collision occurs (as `UpstreamAlreadyExists` already does for the `upstream` case).
- Apply the same confirmation gate to `addUpstreamRemoteIfNeeded`'s first-time creation of the `upstream` remote, rather than only warning when a conflicting remote already exists.
- When comparing old vs. new clone URLs, resolve and pin the underlying repository/owner numeric ID (as reported by the GitHub API) rather than trusting owner/name strings, so a renamed/reclaimed identity cannot silently satisfy `urlMatchesRemote`/`remoteUrlUnchanged`.

### Proof of Concept
1. Victim clones/forks `github.com/OrgA/example` in GitHub Desktop; Desktop stores the `GitHubRepository` (owner `OrgA`, cloneURL `https://github.com/OrgA/example`) and, if a fork, records `parent.cloneURL` pointing to the same host/owner/name pattern.
2. `OrgA` is later renamed or deleted, and an attacker registers `OrgA` and creates a repository named `example` (or `OrgA/example` becomes reachable at the same path through GitHub's own redirect/dangling-reference behavior).
3. On the victim's next app launch/background refresh, `repositoryWithRefreshedGitHubRepository` (`app/src/lib/stores/app-store.ts:4874-4914`) calls `api.fetchRepository('OrgA', 'example')`, which now returns the attacker's repository object.
4. `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts:7-45`) sees the cached clone URL still "matches" and silently calls `gitStore.setRemoteURL('origin', clone_url)`; if the repository is a fork, `GitStore.addUpstreamRemoteIfNeeded` (`app/src/lib/stores/git-store.ts:1321-1356`) additionally adds an `upstream` remote pointing at the attacker's declared `parent.cloneURL` — with no dialog shown to the victim in either case.
5. Victim clicks "Fetch"/"Update from upstream" in the normal UI; attacker-controlled commits are pulled into local tracking refs and can be merged into the victim's branches without any warning that the remote target changed.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
