### Title

Forged `ReceivedOutput` bytes over-report Bitcoin funds as spendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary

`ReceivedOutput::read` deserializes an arbitrary scalar offset, `TxOut`, and `OutPoint` without authenticating that the `TxOut` is the actual output identified by the `OutPoint` or that it was produced by `Scanner`. [1](#0-0)  An attacker-controlled byte stream can therefore claim that a real outpoint pays more satoshis than it does on chain, analogous to crediting the requested transfer amount rather than the amount actually received. [2](#0-1) 

### Finding Description

`ReceivedOutput` stores three independently supplied fields: `offset`, `output`, and `outpoint`. [3](#0-2)  Its reader accepts all three fields directly from serialized bytes and returns the object without checking the outpoint against a confirmed transaction or binding the output script to a registered scanner offset. [1](#0-0) 

This differs from `Scanner::scan_transaction`, which derives `ReceivedOutput` from a transaction whose `compute_txid()` matches the assigned outpoint and copies the exact on-chain `TxOut`. [4](#0-3)  The deserializer has no equivalent provenance check, so `value()` returns the forged `TxOut` amount rather than the value committed to by the real UTXO. [2](#0-1) 

### Impact Explanation

A forged `ReceivedOutput` can represent funds as received and spendable when the referenced outpoint contains less value or does not exist. [1](#0-0)  `SignableTransaction::new` then trusts the serialized `TxOut` amount when calculating available input funds and stores that forged output as the signature prevout. [5](#0-4) [6](#0-5) 

If the forged script is copied from a genuine Serai output, `SignableTransaction::multisig` accepts it because it checks only that the script corresponds to the offset-derived group key. [7](#0-6)  Signing commits the forged prevout through `Prevouts::All`, producing a transaction whose reported balance cannot actually be spent at the claimed amount. [8](#0-7) 

### Likelihood Explanation

The trigger is an attacker supplying bytes to `ReceivedOutput::read`; no validator compromise, malformed curve implementation, or invalid Bitcoin transaction is required. [1](#0-0)  The attacker needs only know or choose a plausible outpoint and a script that satisfies the later offset check, both of which can be copied from public chain data. [9](#0-8) 

### Recommendation

Do not treat standalone deserialized `ReceivedOutput` values as authenticated UTXOs. Either:

- restrict construction to `Scanner::scan_transaction` / `Scanner::scan_block`, which derive the `TxOut` and outpoint from the same transaction; or
- authenticate deserialized outputs with the full previous transaction or a merkle/UTXO proof and verify that `compute_txid()` and `vout` resolve to the embedded `TxOut`.

The reader should also bind the embedded P2TR script to the supplied offset and expected base key rather than allowing an arbitrary script until `SignableTransaction::multisig`. [4](#0-3) [9](#0-8) 

### Proof of Concept

```rust
use bitcoin::{
  Amount, OutPoint, TxOut,
  consensus::Encodable,
};
use bitcoin_serai::wallet::{ReceivedOutput, Scanner};

// `real` is a genuine output found by scanning a public funding transaction.
let real: ReceivedOutput = scanner.scan_transaction(&funding_tx).remove(0);

// Keep the genuine outpoint, offset, and script, but inflate the amount.
let forged_output = TxOut {
  value: Amount::from_sat(real.value() + 1_000_000),
  script_pubkey: real.output().script_pubkey.clone(),
};

let mut forged = Vec::new();
forged.extend_from_slice(&real.offset().to_bytes());
forged_output.consensus_encode(&mut forged).unwrap();
real.outpoint().consensus_encode(&mut forged).unwrap();

// Accepted despite the TxOut not matching the value at the referenced outpoint.
let forged = ReceivedOutput::read(&mut forged.as_slice()).unwrap();
assert_eq!(forged.value(), real.value() + 1_000_000);
```

The forged object preserves the real output's script and outpoint, so the later key/offset check can still pass while `input_sat` is calculated from the inflated amount. [5](#0-4) [9](#0-8)
