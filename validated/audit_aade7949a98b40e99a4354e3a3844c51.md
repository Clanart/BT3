### Title
Cached FROST preprocess reused across signing calls, enabling nonce reuse and private key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The mod_auth_mellon CVE-2019-3878 bug class is "an alternate, specially-crafted input path that bypasses a security invariant the normal path enforces." In Serai, the analog is the cached-preprocess path in `SigningProtocol::preprocess_internal`: instead of generating a fresh random preprocess per signing session (the invariant FROST requires), it deterministically reconstructs the *same* nonces from a seed cached in the database. If that cached seed is consumed more than once — which the API permits — the signer emits signature shares that reuse the same nonce, the exact failure mode FROST documents as fatal.

### Finding Description
`preprocess_internal` derives an encryption key from `b"Cached Preprocess Encryption Key" || context || key`, then either generates-and-caches a `CachedPreprocess` seed or reuses the stored one, and finally calls `AlgorithmSignMachine::from_cache` [1](#0-0) . `from_cache` routes to `seeded_preprocess`, which deterministically expands the 32-byte seed through `ChaCha20Rng` to produce the FROST nonces and commitments [2](#0-1) . FROST itself states the requirement being violated: "This cached preprocess MUST only be used once. Reuse of it enables recovery of your private key share" [3](#0-2) .

Nothing in `preprocess_internal` deletes or rotates `CachedPreprocesses::get(self.txn, &self.context)` after use. Every subsequent call with the same `context` — for `DkgConfirmer`, `context = (b"DkgConfirmer", self.attempt)` [4](#0-3)  — reconstructs a machine with byte-identical `nonces` and an identical published `preprocess` (commitments). `share_internal` calls `preprocess_internal` then `machine.sign(preprocesses, msg)` [5](#0-4) , and `DkgConfirmer::complete` calls `share_internal` again after `share` has already run [6](#0-5) . Within `sign`, the effective nonce is `base + rho_i * actual` where `rho_i` is the binding factor computed over the *caller-supplied* preprocess set [7](#0-6)  — so identical seed nonces are combined with attacker-influenced binding factors each time the function is invoked.

### Impact Explanation
FROST signature shares have the form `s_i = λ_i·x_i·c + Σ_j (base_j + ρ_{i,j}·d_j)`. If `share`/`complete` are invoked twice under the same `context` with different signing sets or preprocess contents (producing different binding factors ρ and/or different challenge c), the two emitted shares are two linear equations over the same nonce scalars and the secret share `x_i`. An observer can solve for the nonce terms and then recover the signer's Ristretto private key — the key used for all MuSig-style tributary/substrate signing, including the DKG confirmation signature that authorizes setting threshold keys on-chain [8](#0-7) . Recovery of this key lets an attacker forge the validator's confirmation shares and signing-protocol shares, crossing the authentication boundary the DKG relies on.

### Likelihood Explanation
The seed is keyed only by `context`, so reuse requires `share_internal` (or `preprocess_internal` followed by `share`) to run more than once per context. `DkgConfirmer::share` then `DkgConfirmer::complete` both run it unconditionally [9](#0-8) ; any retry of `share` after a failed accumulation, or a `complete` invoked with a preprocess set differing from the one `share` used, produces a second share over the same nonces. Because the preprocess inputs are accumulated from on-chain tributary data and the binding factors depend on which participants' preprocesses are supplied, the ρ values are not fixed — defeating the protection that deterministic-but-bound nonces might otherwise provide. I could not fully trace every coordinator call site of `share`/`complete` to confirm a second invocation with a differing set always occurs; the vulnerability is that the design permits it at all, with no single-use guard on the cached seed.

### Recommendation
- After `seeded_preprocess` consumes the cached seed in `preprocess_internal`, delete or overwrite `CachedPreprocesses` for that context, and refuse to sign if a share was already produced for that context.
- Alternatively, mix a per-invocation nonce (e.g., hash of the sorted preprocess map plus a monotonic counter) into `ChaCha20Rng::from_seed` so identical seeds cannot yield identical nonces under different binding factors.
- Document and enforce at the `SigningProtocol` level the invariant FROST requires [10](#0-9) .

### Proof of Concept
1. A DKG attempt reaches the confirmation phase; the coordinator calls `DkgConfirmer::share(preprocesses_A, key_pair)` for attempt `a`. `preprocess_internal` caches seed `S` under context `(b"DkgConfirmer", a)` and a share `s₁` is emitted using nonces derived from `S`.
2. The confirmation is retried or `complete` is invoked with a different accumulated preprocess map `preprocesses_B` (e.g., a late-arriving or re-accumulated set on the tributary). `share_internal` again loads `S` from `CachedPreprocesses` (it was never cleared) and produces a second share `s₂` with the same `nonces` but binding factors `ρ'` and challenge `c'` differing from `ρ`, `c`.
3. From `s₁` and `s₂` (both observable in emitted signing data), solve the linear system: `s₁ − s₂ = λ·x·(c − c') + Σ_j (ρ_j − ρ'_j)·d_j`. With the nonce commitments known from the published preprocess, the unknowns reduce to `x` (the private key) and the nonce scalars; recover the validator's Ristretto secret key.
4. Use the recovered key to forge further `DkgConfirmer`/signing-protocol shares or the validator's tributary signatures, bypassing the authentication the MuSig-based confirmation was meant to provide — the direct analog of the ECP-header authentication bypass.

Note: step 2's trigger depends on coordinator retry/re-accumulation behavior I could not fully verify within the indexed code; the cryptographic flaw (unbounded reuse of a deterministic nonce seed) is confirmed at `signing_protocol.rs:123-147` and `sign.rs:121-144`.

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
