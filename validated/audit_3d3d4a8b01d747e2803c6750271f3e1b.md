### Title
Unbounded growth of `rewardTokens[]` in `BaseRewardPool` can permanently DoS `withdraw()`/`harvest()` via out-of-gas - (File: rewards/BaseRewardPool.sol)

### Summary
`BaseRewardPool` (and its sibling reward pools) store all reward tokens ever registered in an append-only array `rewardTokens`, which is iterated in full on every `_updateFor`/`getReward` call that `MasterMagpie` triggers on deposit, withdraw and harvest. There is no upper bound on `rewardTokens.length` and no mechanism to remove stale entries, so the loop cost grows monotonically over the life of the pool.

### Finding Description
`rewardTokens` only grows, via `queueNewRewards`, which pushes a new token whenever it isn't already tracked: [1](#0-0) 

Every user-triggered accounting path — `_updateFor` (invoked by the `updateReward` modifier) and `getReward` — iterates over the *entire* `rewardTokens` array, regardless of whether the caller cares about those tokens: [2](#0-1) [3](#0-2) 

This loop is unavoidable in the ordinary user withdraw flow: `MasterMagpie._withdraw` → `_harvestAndUnstake` → `_harvestBaseRewarder`/`_harvestMGP`, which update pool state and rewards before releasing the staked tokens: [4](#0-3) 

`BaseRewardPoolV2` and `mWOMSVBaseRewarder` implement the identical unbounded pattern: [5](#0-4) [6](#0-5) 

As with the `PuttyV2` finding, there is no cap on the number of iterated elements and no way for a normal user to opt out of the full scan or pay for a partial one — the same class of bug (unbounded loop over an ever-growing array embedded in a fund-releasing code path).

### Impact Explanation
As reward tokens accumulate over the pool's operating lifetime (a normal, expected occurrence — new incentive tokens are added periodically, exactly as Putty accumulates orders over long durations), the gas cost of `_updateFor`/`getReward` increases without bound. Once the cumulative gas cost of iterating `rewardTokens` exceeds the block gas limit, every `deposit`, `withdraw`, and `harvest` call through `MasterMagpie` for that staking token becomes unexecutable, since all of them route through `updatePool`/`_harvestBaseRewarder`, which call into the reward pool's full-array loops. Users would be permanently unable to withdraw their staked principal or claim any already-accrued rewards from that pool — a permanent freeze of user funds and unclaimed yield.

### Likelihood Explanation
Likelihood is low-to-moderate and organic rather than adversarial: it requires the reward-token list for a single pool to grow large enough over time (through normal `queueNewRewards` additions) that the per-call loop overhead pushes total gas above the block limit. No attacker action or privileged misbehavior is needed — it is a direct consequence of the append-only, never-pruned design, mirroring the exact conditions (long-lived positions, growing per-call array cost) described in the referenced Putty finding.

### Recommendation
Cap the number of reward tokens a single pool can register, or support removing tokens with drained/negligible balances from `rewardTokens`. Alternatively, provide paginated/selective reward-claim and pool-update paths (already partially present via `getRewards(address[] _rewardTokens)`) and make `withdraw` not require a full-array `_updateFor` scan, so a user can always retrieve staked principal independent of the size of `rewardTokens`.

### Proof of Concept
1. Over time, a manager legitimately calls `queueNewRewards` many times for a given staking token's `BaseRewardPool`, each time with a new `_rewardToken`, growing `rewardTokens.length` (see `queueNewRewards` at `rewards/BaseRewardPool.sol:261-274`).
2. A user who staked into that pool calls `MasterMagpie.withdraw`/`_withdraw`, which calls `_harvestAndUnstake` → `_harvestBaseRewarder` → the pool's `getReward`, and `updatePool`/`_updateFor`, both of which loop `for (uint256 index = 0; index < rewardTokens.length; ...)`.
3. As `rewardTokens.length` grows, the gas required for this loop grows linearly; once it exceeds the block gas limit, the withdraw transaction can never be mined, permanently locking the user's staked principal and any unclaimed rewards in that pool.

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;

            user.available = user.available - _amount;
