### Title
Unbounded attacker-controlled allocation in `ThresholdKeys::read` enables memory-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary

CVE-2017-16913 is a bug class where an attacker-controlled length field in a wire message drives a large memory allocation before the corresponding data is received or validated. The same shape exists in Serai's `ThresholdKeys::read` in `crypto/dkg/src/lib.rs`: the participant count `n` is read directly from untrusted bytes and immediately used as a `Vec::with_capacity` size, allocating up to `u16::MAX` field elements (~2 MB+) while the attacker has supplied only a handful of bytes.

### Finding Description

`ThresholdKeys::<C>::read` parses serialized threshold keys from an arbitrary `io::Read`. After the curve ID check, it reads `t`, `n`, and `i` as `u16`s from the stream, then reads a one-byte interpolation discriminant. When the discriminant is `0` (`Interpolation::Constant`), it executes:

```rust
// crypto/dkg/src/lib.rs:604-613
let mut interpolation = [0];
reader.read_exact(&mut interpolation)?;
let interpolation = match interpolation[0] {
  0 => Interpolation::Constant({
    let mut res = Vec::with_capacity(usize::from(n));
    for _ in 0 .. n {
      res.push(C::read_F(reader)?);
    }
    res
  }),
``` [1](#0-0) 

The `n` value (read at `crypto/dkg/src/lib.rs:598` via `read_u16`) is fully attacker-controlled and never bounds-checked before `Vec::with_capacity(usize::from(n))` executes. `ThresholdParams::new`, which would validate `n`, is only invoked afterward at `crypto/dkg/src/lib.rs:626`. A malicious byte string of roughly `4 + C::ID.len() + 6 + 1` bytes — valid curve ID, `t = 1`, `n = 0xFFFF`, `i = 1`, interpolation `0` — forces a `Vec::with_capacity(65535)` of `C::F` elements (≥ ~2 MB for 32-byte scalars, more for wider fields) before any payload bytes are consumed.

This is reachable on untrusted bytes: `ThresholdKeys::read` is one of the explicitly listed deserialization sinks for untrusted input, and unlike the defensive chunked read used in `networks/ethereum/src/machine.rs:51-60` (which exists precisely because "a valid DoS would be to claim a 4 GB data is present"), there is no incremental or capped allocation here. Note that `SchnorrAggregate::read` (`crypto/schnorr/src/aggregate.rs:77-87`), despite reading a `u32` count, grows its `Vec` one parsed element at a time and is therefore bandwidth-proportional, not an instance of this class.

### Impact Explanation

Each malformed input of ~15–50 bytes triggers a ~2 MB heap allocation, an amplification ratio on the order of 10⁴–10⁵×. Because the allocation happens before a single element is read, an attacker needs to send almost no actual data. Repeated/concurrent calls (e.g., many parallel deserializations of attacker-supplied key blobs) create sustained allocator pressure and can exhaust memory or degrade the allocator badly enough to deny service to legitimate key-loading and signing operations. This mirrors the CVE's impact: memory consumption driven by a length field, not by actual transmitted data.

### Likelihood Explanation

Likelihood depends on `ThresholdKeys::read` being invoked on peer/network-controlled input rather than only on trusted local storage. If it is only ever read from the local DB, the attack surface disappears and severity drops. Even when reachable, the allocation is transient — the subsequent `read_F` loop fails quickly on a short stream and the `Vec` is freed — so sustained DoS requires many concurrent invocations rather than a single message. The `u16` bound also caps each allocation (~2 MB), unlike the near-unbounded allocation in the original CVE. These factors make it a real but moderate amplification vector, consistent with Medium severity at most.

### Recommendation

Do not pre-allocate based on the untrusted count. Replace `Vec::with_capacity(usize::from(n))` with `Vec::new()` and push elements as `read_F` succeeds, so memory grows only in proportion to data actually received. Alternatively, validate `(t, n, i)` via `ThresholdParams` (or a sanity bound such as `n <= MAX_PARTICIPANTS`) *before* allocating. A comparable guard already exists in `coordinator/src/p2p.rs:264` where the length is rejected if it exceeds a maximum before `vec![0; len]` is allocated — the same pattern should be applied here.

### Proof of Concept

```rust
use std::io;
use ciphersuite::Ciphersuite;
use dkg::ThresholdKeys;
use dalek_ff_group::Ed25519; // any Ciphersuite impl

fn main() {
  let mut msg = Vec::new();
  // Curve ID length + ID
  msg.extend((<Ed25519 as Ciphersuite>::ID.len() as u32).to_le_bytes());
  msg.extend(<Ed25519 as Ciphersuite>::ID);
  // t = 1, n = u16::MAX, i = 1
  msg.extend(1u16.to_le_bytes());
  msg.extend(u16::MAX.to_le_bytes());
  msg.extend(1u16.to_le_bytes());
  // interpolation = 0 => Interpolation::Constant
  msg.push(0u8);
  // No further bytes needed: Vec::with_capacity(65535) of C::F executes,
  // allocating ~2 MB before read_F fails on the truncated stream.
  let _ = ThresholdKeys::<Ed25519>::read(&mut msg.as_slice());
}
```

Expected behavior: a ~2 MB heap allocation is performed and then dropped when `C::read_F` errors out; repeating this across concurrent reads multiplies allocator pressure with near-zero attacker bandwidth.

Caveat: I could not fully verify every in-scope deserialization path (e.g., frost `read_map`/`read_share` internals, bitcoin `ReceivedOutput::read`) within the available iterations; if another path allocates proportional to a `u32`/`u64` field rather than a `u16`, it would be the stronger analog.
