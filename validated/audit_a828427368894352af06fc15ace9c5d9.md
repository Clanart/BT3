## Title
Protocol fee rounds down to zero for small-amount orders, allowing systematic fee bypass via order splitting - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` computes the protocol fee taken on each placed order with a truncating integer division: `protocolFee = (originalAmount * protocolFeeBps) / 10_000`. Because Solidity integer division floors toward zero, any `originalAmount` small enough relative to `protocolFeeBps` produces `protocolFee == 0`, and the order is escrowed with the *full* input amount and zero fee collected, exactly mirroring the RizLeverager "loop with small amount" fee-bypass pattern from the external report.

### Finding Description
In `_placeOrder` (`evm/src/apps/IntentGatewayV2.sol`, lines 300–331), the protocol fee is derived per input token: [1](#0-0) 

`protocolFeeBps` is read from `_destinationProtocolFees[destinationHash]` or falls back to `_params.protocolFeeBps`, and the only check on the input amount is `originalAmount == 0` reverting — there is no minimum-order-size floor. For any `protocolFeeBps` value that is not a divisor of `10_000` cleanly relative to the amount, an attacker can pick `originalAmount` such that `(originalAmount * protocolFeeBps) / 10_000` truncates to `0` (e.g., with `protocolFeeBps = 5` — 0.05% — any `originalAmount < 2000` in the token's smallest unit yields `protocolFee = 0`). The order is then placed with `reducedAmount = originalAmount` (no reduction), `DustCollected` is never emitted (`if (protocolFee > 0) emit ...`), and the full amount is escrowed under `_orders[commitment][token]` for the solver to fill — with zero fee paid to the protocol.

This is directly analogous to the reported bug: a user with control over the "amount" parameter can drive the fee-calculation numerator below the rounding threshold and repeat the operation ("looping") to place many orders that each pay zero protocol fee, instead of one large order that would pay a non-zero fee. There is no floor/minimum-fee enforcement and no `divCeil`-style rounding — confirmed by the SDK's own mirror of this exact logic: [2](#0-1) 
which is explicitly commented "Mirrors the gateway's floored fee deduction," confirming the on-chain behavior is intentional flooring with no minimum-amount guard.

### Impact Explanation
Every order placed under the rounding threshold escapes the protocol fee entirely while still consuming full escrow, settlement, and solver-fill capacity. Repeated at scale (splitting a large intended transfer into many sub-threshold orders), an attacker can move arbitrary total value through `IntentGatewayV2` while paying zero cumulative protocol fee — a direct, repeatable loss of protocol revenue that governance configured `protocolFeeBps` to collect. Because the fee logic and escrowed/commitment amount are attacker-observable and attacker-controlled (`order.inputs[i].amount`), this is a public-entrypoint, unprivileged-attacker path with no reliance on a malicious relayer, prover, or admin.

### Likelihood Explanation
Likelihood is high: `placeOrder`/`_placeOrder` is a fully public entry point, the exploit requires only choosing small per-order amounts (no special timing, no governance/relayer collusion), and low-bps fee configurations (which the docs/tests explicitly support, e.g. `protocolFeeBps: 0` and other low values in `IntentGatewayV2Test.sol`) make the rounding-to-zero window wide for common token decimals (e.g., 6-decimal stablecoins like USDC). Gas cost is the only friction, and on low-fee chains (a scenario the original report itself calls out) this remains net-favorable for high-volume users seeking to avoid protocol fees.

### Recommendation
Round the protocol fee calculation up (ceiling division) instead of down, e.g. `protocolFee = (originalAmount * protocolFeeBps + 9999) / 10_000`, or enforce a minimum order/input amount per destination such that `protocolFeeBps > 0` implies `protocolFee >= 1` for any accepted order. Optionally, revert (rather than silently accept) when `protocolFeeBps > 0` but the computed fee would be zero, forcing users to place orders above the minimum fee-bearing threshold.

### Proof of Concept
1. Governance sets `_params.protocolFeeBps = 5` (0.05%) or a per-destination fee via `_destinationProtocolFees`.
2. Attacker calls `placeOrder` with `order.inputs[0].amount = 1999` (in the input token's smallest unit, e.g., USDC's 6-decimal base units).
3. In `_placeOrder`: `protocolFee = (1999 * 5) / 10_000 = 9995 / 10_000 = 0` (Solidity integer truncation).
4. `reducedAmount = 1999 - 0 = 1999`; `DustCollected` is not emitted; `_orders[commitment][token] = 1999` — the full amount is escrowed with zero fee collected.
5. Attacker repeats step 2 in a loop across many orders instead of placing one order of amount ≥ 2000, extracting arbitrary aggregate volume through the gateway while the protocol collects `0` fee on every one of them. [1](#0-0)

export function deductProtocolFee(amount: bigint, protocolFeeBps: bigint): bigint {
	if (protocolFeeBps <= 0n) return amount
	const fee = (amount * protocolFeeBps) / BPS_DENOMINATOR
	return amount - fee
