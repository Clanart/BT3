### Title
Signed integer overflow in `Timestamp`/`Duration` arithmetic helpers from unchecked attacker-controlled `seconds` fields - (File: `src/google/protobuf/util/time_util.cc`)

### Summary
`google::protobuf::Timestamp` and `Duration` are ordinary messages whose `seconds` (`int64`) fields accept any value when parsed from untrusted binary Protobuf via the standard `ParseFromString`/`MergeFrom` API — there is no wire-level range validation for these well-known types. The C++ `TimeUtil`/operator helpers (`operator+=`, `operator-=`, `CreateNormalizedTimestamp`, `CreateNormalizedDuration`) then perform signed 64-bit addition/subtraction on these attacker-controlled values with only a debug-only `ABSL_DCHECK` guarding the valid range, not a runtime-enforced check. This mirrors the Sherlock report's root cause: an attacker-controlled value accepted without an upper/lower bound during "deposit" (here, message parsing) is later combined arithmetically with another value during a "settlement" operation (here, `Timestamp + Duration` in consuming application code), causing an overflow that the original bounds check was supposed to prevent.

### Finding Description
`Timestamp.seconds` and `Duration.seconds` are plain `int64` protobuf fields [1](#0-0) . Binary parsing of these fields places no constraint on the numeric value — any `int64_t`, including `INT64_MAX`/`INT64_MIN`, is accepted through the standard, trusted `ParseFrom*` API.

Once such a message is parsed, application code that manipulates timestamps via the C++ `TimeUtil` operators performs raw signed addition of `seconds()`: [2](#0-1) 

These operators funnel into `CreateNormalizedTimestamp`/`CreateNormalizedDuration`, whose only defense against out-of-range results is `ABSL_DCHECK`, which is a debug-only assertion compiled out of `NDEBUG`/release builds: [3](#0-2) 

The same missing-hard-check pattern exists for `Duration`: [4](#0-3) 

Because `seconds` is a `int64_t` and the addition `t.seconds() + d.seconds()` (or `lhs.Seconds - rhs.Seconds` in the C# `checked` variants) can overflow when an attacker supplies a boundary value such as `INT64_MAX`/`INT64_MIN` for `seconds` in a parsed message, the C++ path exhibits undefined behavior (signed integer overflow) in release builds where `ABSL_DCHECK` is a no-op, exactly analogous to the Solidity `depositTime[i] + expiration[i]` overflow: an attacker-supplied unbounded value is combined with a second, otherwise-trusted value in unchecked arithmetic that was implicitly assumed to be "safe" by the surrounding range-validation logic, which in this codebase only fires as an assertion rather than a hard runtime guard.

Other language runtimes handle this more defensively — Java's `Timestamps`/`Durations` utilities use `addExact`/`subtractExact`, which throw `ArithmeticException` on overflow [5](#0-4) [6](#0-5) , and C# wraps the same arithmetic in a `checked` block that throws `OverflowException` [7](#0-6) . The C++ implementation is the outlier: it relies solely on `ABSL_DCHECK`, which provides no protection in production (`NDEBUG`) builds.

### Impact Explanation
In a release build (the default for production deployments, where `NDEBUG` is defined and `ABSL_DCHECK` compiles to nothing), an attacker who controls one parsed `Timestamp`/`Duration` message (e.g., relayed through a service that deserializes untrusted Protobuf and later performs date arithmetic with `TimeUtil` operators) can trigger signed 64-bit integer overflow — undefined behavior in C++ that can manifest as silently wrapped/incorrect timestamp values (integrity impact on any downstream logic gated by time comparisons, such as expiration checks) or as a crash under UBSan-instrumented builds. This is a genuine "missing runtime bound enforcement" defect analogous to the reported Solidity issue, though its blast radius is narrower: it requires application code to invoke the `TimeUtil` C++ arithmetic helpers on attacker-influenced `Timestamp`/`Duration` values, so severity should be scoped to Medium rather than High, since the direct Protobuf parse/serialize path itself is not corrupted — only the well-known-type utility helper's arithmetic is unsound.

### Likelihood Explanation
Likelihood is moderate: it requires (1) an attacker being able to set the `seconds` field of a parsed `Timestamp`/`Duration` to a boundary value (trivial via the public binary parse API, since there is no wire-level range check), and (2) consuming application code invoking one of the vulnerable C++ operators (`operator+=`, `operator-=`, or equivalently `TimeUtil::TimeUtil` add/subtract helpers) on that value combined with another duration/timestamp. This is a common pattern for services that compute expirations, deadlines, or durations from externally supplied timestamps.

### Recommendation
Replace the debug-only `ABSL_DCHECK` range/overflow guards in `CreateNormalizedTimestamp`/`CreateNormalizedDuration` and the `operator+=`/`operator-=` implementations in `src/google/protobuf/util/time_util.cc` with runtime-enforced checks (e.g., using an overflow-checked addition helper similar to `upb_AddOverflow_size_t_size_t` already present in `upb/port/overflow.h`, or `absl::CheckedAdd`) that reject or saturate out-of-range results instead of relying on assertions compiled out of production binaries. This would bring the C++ implementation in line with the Java (`addExact`/`subtractExact`, throwing `ArithmeticException`) and C# (`checked` block, throwing `OverflowException`) implementations, which already enforce these bounds at runtime.

### Proof of Concept
Conceptual reproduction (requires a local Devin session with build tooling to confirm precisely, as I could not execute code from this read-only investigation):
1. Build a release configuration where `NDEBUG` is defined (default for typical production CMake/Bazel release builds), so `ABSL_DCHECK` compiles to a no-op.
2. Parse (via the standard, trusted `ParseFromString` binary API) a `Timestamp` message with `seconds = INT64_MAX` and a `Duration` message with `seconds = 1` — both are accepted without error since there is no field-level range validation on the wire.
3. Execute `Timestamp& operator+=(Timestamp& t, const Duration& d)` [8](#0-7)  with these two values: `t.seconds() + d.seconds()` computes `INT64_MAX + 1`, a signed integer overflow (undefined behavior), that in a release build reaches `CreateNormalizedTimestamp` where the `ABSL_DCHECK` guard is compiled out [9](#0-8) , silently producing an invalid/wrapped `Timestamp` (e.g., `INT64_MIN`) instead of raising an error, unlike the Java equivalent which throws `ArithmeticException` via `addExact` [5](#0-4) .

Timestamp CreateNormalizedTimestamp(int64_t seconds, int32_t nanos) {
  ABSL_DCHECK(seconds >= TimeUtil::kTimestampMinSeconds &&
              seconds <= TimeUtil::kTimestampMaxSeconds)
      << "Timestamp seconds are outside of the valid range";

  // Make sure nanos is in the range.
  if (nanos <= -kNanosPerSecond || nanos >= kNanosPerSecond) {
    seconds += nanos / kNanosPerSecond;
    nanos = nanos % kNanosPerSecond;
  }
  // For Timestamp nanos should be in the range [0, 999999999]
  if (nanos < 0) {
    seconds -= 1;
    nanos += kNanosPerSecond;
  }

  ABSL_DCHECK(seconds >= TimeUtil::kTimestampMinSeconds &&
              seconds <= TimeUtil::kTimestampMaxSeconds &&
              nanos >= TimeUtil::kTimestampMinNanoseconds &&
              nanos <= TimeUtil::kTimestampMaxNanoseconds)
      << "Timestamp is outside of the valid range";
  Timestamp result;
  result.set_seconds(seconds);
  result.set_nanos(nanos);
  return result;
}

Duration CreateNormalizedDuration(int64_t seconds, int32_t nanos) {
  ABSL_DCHECK(seconds >= TimeUtil::kDurationMinSeconds &&
              seconds <= TimeUtil::kDurationMaxSeconds)
      << "Duration seconds are outside of the valid range";

  // Make sure nanos is in the range.
  if (nanos <= -kNanosPerSecond || nanos >= kNanosPerSecond) {
    seconds += nanos / kNanosPerSecond;
    nanos = nanos % kNanosPerSecond;
  }
  // nanos should have the same sign as seconds.
  if (seconds < 0 && nanos > 0) {
    seconds += 1;
    nanos -= kNanosPerSecond;
  } else if (seconds > 0 && nanos < 0) {
    seconds -= 1;
    nanos += kNanosPerSecond;
  }

  ABSL_DCHECK(seconds >= TimeUtil::kDurationMinSeconds &&
              seconds <= TimeUtil::kDurationMaxSeconds &&
              nanos >= TimeUtil::kDurationMinNanoseconds &&
              nanos <= TimeUtil::kDurationMaxNanoseconds)
      << "Duration is outside of the valid range";
  Duration result;
  result.set_seconds(seconds);
  result.set_nanos(nanos);
  return result;
}
