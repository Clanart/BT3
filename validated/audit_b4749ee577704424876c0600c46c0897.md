### Title
distribution precompile `rewards()` view is missing the non-payable guard, permanently stranding any usei/wei sent with the call - (File: precompiles/distribution/distribution.go)

### Summary
The `rewards(address)` view function on the distribution precompile (`0x0000000000000000000000000000000000001007`) is the only query method in the precompile that does not call `pcommon.ValidateNonPayable(value)` before executing. Every other query on the same precompile (`params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`) routes through `p.validateInput(value, args, N)`, which explicitly rejects non-zero `value`. `rewards()` instead only calls `pcommon.ValidateArgsLength(args, 1)`, so a call to `rewards()` carrying non-zero `msg.value` is accepted.

### Finding Description
`Execute` dispatches `rewards` straight to `p.rewards(ctx, method, args)` with no non-payable check: [1](#0-0) 

Contrast with the other view handlers, which all call `p.validateInput`, and `validateInput` itself enforces `pcommon.ValidateNonPayable(value)`: [2](#0-1) [3](#0-2) 

Distribution is registered as one of the "payable precompiles" in the EVM keeper, meaning value transfers to/from this address are treated specially (transfer events are suppressed) rather than rejected outright at the EVM call layer: [4](#0-3) 

Because distribution is payable at the EVM/StateDB level, the EVM `CALL` opcode's normal value-transfer semantics move the `usei`/`wei` from the caller's balance to the precompile's associated Sei address (the distribution module account) before/along with `Execute` running. State-changing precompile functions on this contract that legitimately accept value (e.g. `withdrawDelegationRewards`, `setWithdrawAddress` when non-payable is enforced) either reject non-zero value or handle it via `pcommon.HandlePaymentUsei`, which refunds the payer out of the precompile balance. `rewards()` does neither: it doesn't reject the value, and it performs no refund/forwarding logic — it merely queries `distrKeeper.DelegationTotalRewards` and returns the result. The integration test suite explicitly documents this as a known quirk: [5](#0-4) 

There is no method on the distribution precompile (or elsewhere) that lets a caller reclaim usei/wei that lands on the precompile's associated account via this path — the module account is not a normal EOA/contract with a sweep/claim function, so the value becomes permanently unspendable by the sender, structurally analogous to the Prisma `PrismaConnector` finding where funds sent to a contract/module have no corresponding claim path.

### Impact Explanation
Any unprivileged EVM caller (contract or EOA) invoking `rewards(address)` on the distribution precompile with non-zero `value` permanently loses that value: the funds move into the distribution module's account with no bookkeeping tying them back to the sender and no exposed function to claim/refund them. This is a direct, unrecoverable loss of user funds triggered by a single ordinary transaction — no special privileges required, satisfying "concrete fund loss or permanent freezing."

### Likelihood Explanation
High likelihood of accidental triggering: `rewards` is a commonly called read-only helper, and naive integrators (bots, dashboards, wallets) that blanket-attach `value` or reuse a payable call pattern across all precompile calls could trigger this without realizing the funds are non-refundable. It requires no special setup beyond a plain EVM transaction/call with `value > 0` to the distribution precompile address, calling `rewards(address)`.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` to `rewards()` (mirroring `validateInput` used by every other query in this file) so the call reverts if `value != 0`, consistent with the rest of the precompile's read-only methods, preventing funds from ever landing on the module account in the first place.

### Proof of Concept
1. Deploy/obtain an ethers.js contract bound to `DISTR_PRECOMPILE_ADDRESS` (`0x...1007`) using the distribution ABI.
2. Call `distribution.rewards(delegatorAddress, { value: ethers.parseEther("1") })` from any associated EVM account.
3. Observe the transaction succeeds (status 1) and returns valid reward data — unlike calling any other view method (e.g. `communityPool({value: ...})`), which reverts with "sending funds to a non-payable function".
4. Check the caller's usei/wei balance: the sent value has been debited and transferred to the distribution module account, with no corresponding precompile method (`claim`, `refund`, etc.) to retrieve it — the funds are permanently stuck.

Note: I could not directly inspect `precompiles/common/precompiles.go`'s `RunAndCalculateGas`/value-transfer glue code (ran out of tool iterations) to show the exact line where `value` is moved into the precompile's Sei address for payable precompiles; this part of the mechanism is inferred from the `payablePrecompiles` map and the `HandlePaymentUsei` refund pattern used elsewhere, plus the explicit test-file comment confirming `rewards()` lacks the non-payable guard and would "strand the funds." func (p PrecompileExecutor) validateInput(value *big.Int, args []interface{}, expectedArgsLength int) error {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return err
	}

	if err := pcommon.ValidateArgsLength(args, expectedArgsLength); err != nil {
		return err
	}

	return nil
}
