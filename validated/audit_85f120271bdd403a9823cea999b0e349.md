## Title
Native ERC20 IBC receive middleware can double-credit value via ack-overwrite when post-transfer ERC20 conversion fails — (File: `x/erc20/ibc_middleware.go`, `x/erc20/keeper/ibc_callbacks.go`)

### Summary
The external report's core bug class is: an integrator performs a critical state-changing action (transfer/mint) that is treated as final, and then a *secondary* compliance/behavior check on an external token can fail unpredictably, without the integrator accounting for the fact that the primary action already succeeded. In Cosmos EVM's ERC20 IBC middleware, the analogous flaw is architectural rather than a compliance-list check: `IBCMiddleware.OnRecvPacket` first executes the standard ICS20 transfer (which mints/unescrows real spendable bank coins to the recipient, committed directly against `ctx`), and only afterward attempts an "extra" native-ERC20 conversion step. If that second step fails — which can happen for many benign, permissionless reasons (a native ERC20 contract that reverts on transfer to certain addresses, is paused, self-destructed mid-flight, or implements any of the compliance-style restrictions described in the report) — the middleware overwrites the already-successful acknowledgement with an `ErrorAcknowledgement`, without rolling back the first step's already-committed bank credit.

### Finding Description
`IBCMiddleware.OnRecvPacket` [1](#0-0)  executes in two sequential phases against the *same, non-cached* `sdk.Context`:

1. `im.Module.OnRecvPacket(ctx, ...)` — the standard ICS20 transfer logic. This mints or unescrows the transferred coin directly into the recipient's bank balance and returns a success acknowledgement.
2. `im.keeper.OnRecvPacket(ctx, packet, ack)` — the erc20 module's additional logic that, for a token pair backed by a **native ERC20** (`pair.IsNativeERC20()`), tries to automatically convert the just-credited bank coin into its ERC20 representation by calling `ConvertCoinNativeERC20` [2](#0-1) .

If `k.MintingEnabled` or `ConvertCoinNativeERC20` returns an error (e.g., the native ERC20 contract reverts the `transfer` call for any reason — paused, blacklisted recipient, self-destructed, out-of-gas from a complex hook, or any compliance-like restriction analogous to `minUSTokens`), the function returns `channeltypes.NewErrorAcknowledgement(err)` [3](#0-2) .

Critically, step 1's bank-level credit to the recipient was already applied to `ctx` and is **not wrapped in `ctx.CacheContext()`/write-only-on-success**, so it is not reverted when step 2 fails and downgrades the ack to an error. The doc-comment on `IBCMiddleware.OnRecvPacket` explicitly acknowledges the intended behavior should be "the user receives the bank token instead" of an error [4](#0-3) , but the actual code path for `case found && pair.IsNativeERC20()` returns a hard `ErrorAcknowledgement` on conversion failure instead of preserving the success ack (`return ack`) as done elsewhere in the same function for disabled pairs (`return ack`) [5](#0-4) .

An `ErrorAcknowledgement` written back to the counterparty chain causes that chain's standard ICS20 `OnAcknowledgementPacket` handling to refund/re-credit the original sender (unescrow or re-mint the voucher there), because from the source chain's perspective the packet failed. Meanwhile, on the destination (this) chain, the recipient already holds the real, spendable bank coin credited in step 1. The net effect is duplicated spendable value across two chains from a single IBC transfer.

### Impact Explanation
This produces unauthorized duplication of spendable user value across native balances and IBC escrows: the destination chain recipient retains bank coins that were already unescrowed/minted, while the source chain independently refunds the sender as if the transfer failed. This directly matches the Critical impact gate for "unauthorized minting, burning, duplication ... of spendable user value across native balances ... IBC escrows." The trigger requires no privileged access — any account can be the recipient of an IBC transfer for a native-ERC20-backed token pair, and the ERC20-side revert can be triggered by ordinary conditions of the registered ERC20 contract (which itself may be permissionlessly registered under `PermissionlessRegistration`, per `RegisterERC20` [6](#0-5) ) or by conditions outside the caller's control (paused/blacklisted contract, gas griefing in the ERC20's fallback logic, or a self-destructed contract check racing with the intended conversion).

### Likelihood Explanation
The pattern is reachable through the standard IBC packet-relay path, requires no validator or relayer misbehavior, and is triggered whenever a registered native-ERC20 token pair's `transfer` call reverts during the automatic post-receive conversion — a condition entirely plausible for tokens with owner-controlled compliance/pausable logic (the exact scenario the external BUIDL report describes) or simply a token whose contract self-destructs or runs out of gas mid-conversion. Given `PermissionlessRegistration` allows arbitrary contracts to become native-ERC20 token pairs, an attacker can deploy a malicious ERC20 that succeeds for most transfers but selectively reverts (e.g., after first receiving funds) to reliably trigger this ack-overwrite double-credit at will.

### Recommendation
Isolate the erc20-conversion side effects with `ctx.CacheContext()` and only call the write-function on success; if the conversion fails, discard the cached ERC20-side state changes (none should exist beyond what was already committed by the base transfer) and return the original **success** acknowledgement (as the code comment for `IBCMiddleware.OnRecvPacket` already promises) rather than `channeltypes.NewErrorAcknowledgement`. This preserves the invariant that acknowledgement outcome and actually-committed state remain consistent, matching the pattern already used correctly for the disabled-pair case (`return ack`).

### Proof of Concept
1. Deploy and register (permissionlessly, if enabled, or via governance) a native ERC20 contract whose `transfer` function reverts when called by the erc20 module for a specific recipient address (or after a state flag is flipped, mirroring BUIDL's `minUSTokens`-style restriction).
2. Convert some of the ERC20 to its native bank-coin representation (`MsgConvertERC20`) and send it out via IBC to a counterparty chain, as in `TestOnRecvPacketNativeErc20` [7](#0-6) .
3. Send the token back over IBC to this chain, targeting the crafted recipient/condition that makes `ConvertCoinNativeERC20`'s internal `transfer` call revert.
4. Observe: `im.Module.OnRecvPacket` succeeds and credits the recipient's bank balance for the returned coin; then `k.OnRecvPacket`'s `ConvertCoinNativeERC20` fails and the function returns `channeltypes.NewErrorAcknowledgement` [8](#0-7) .
5. This error acknowledgement is relayed back to the source chain, causing it to refund/re-credit the original sender — while the recipient on the destination chain still holds the bank coins credited in step 4, resulting in duplicated value on both chains.

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}

func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}
