Found: `internal_send_tx` on the aggregator's gRPC server (`core/src/rpc/aggregator.rs:1270-1312`) is a raw, arbitrary Bitcoin-transaction broadcast endpoint whose name (`Internal...`) signals it's meant to be restricted, yet the aggregator's own server explicitly does not enforce any client certificate check.

### Title
Unauthenticated `InternalSendTx` RPC on the aggregator lets anyone broadcast arbitrary transactions and spam the tx-sender queue - (File: core/src/rpc/aggregator.rs)

### Summary
Per the documented mTLS scheme, "internal" methods are supposed to be callable only by the entity's own certificate, while "aggregator" methods are callable by the aggregator only. This authorization model is enforced by `Interceptors::OnlyAggregatorAndSelf` on verifier/operator servers [1](#0-0) , but the docs explicitly state the aggregator server itself never enforces client certificates at all: "The aggregator does not enforce client certificates but does use TLS for encryption" [2](#0-1) . Consequently every RPC exposed on `ClementineAggregator`, including `InternalSendTx`, is reachable by any network peer that can complete a TLS handshake.

### Finding Description
`internal_send_tx` accepts an arbitrary, already-signed raw Bitcoin transaction and inserts it directly into the `TxSender` queue for broadcast, without checking who supplied it or validating that the transaction is tied to any legitimate protocol flow (deposit, round, kickoff, etc.): [3](#0-2) 

This mirrors the report's bug class: a mechanism named/intended for a narrowly scoped, privileged caller ("Internal...") ends up reachable with a broader scope than intended because the enforcing check (client-cert / gas-meter restriction) is missing at the point where the call actually executes — just as the Cosmos precompile's dispatched `MsgCall` inherited the parent's unrestricted gas meter instead of a scoped one. Here, any unauthenticated caller inherits the aggregator's authority to feed transactions into the bridge's own fee-bumping/broadcast pipeline (`TxSender::insert_try_to_send`), which is otherwise meant to be restricted to the aggregator's own vetted transaction-construction logic.

Other aggregator RPCs such as `NewDeposit`, `Withdraw`, `OptimisticPayout`, and `SendMoveToVaultTx` are individually protected by downstream signature checks (user Schnorr signatures, withdrawal-state checks against Citrea, movetx output-shape validation), so they don't directly cross a custody boundary. `InternalSendTx`, however, has no such downstream check — the raw transaction is queued for broadcast as-is.

### Impact Explanation
An unauthenticated caller can inject arbitrary transactions into the `TxSender` fee-management pipeline (RBF/CPFP bumping, database bookkeeping via `insert_try_to_send`) for any `FeeType`. Depending on what the tx-sender subsequently does with untrusted transactions (fee-rate bumping, anchor spending, wallet UTXO consumption for CPFP), this can be used to: broadcast unintended transactions, pollute/exhaust tx-sender database state, or interfere with the timing of legitimate round/kickoff/challenge transactions that share the same fee-bumping infrastructure — potentially causing deadline-bound protocol transactions (kickoff, challenge, disprove) to be delayed or to conflict in the mempool. This matches the "unauthenticated state-changing or broadcasting call" High-severity class.

### Likelihood Explanation
Likelihood is high in any deployment following the documented architecture, since the aggregator server is *designed* to skip client-certificate verification (it relies on TLS only for encryption, not authentication), and the endpoint is a standard unary gRPC call requiring no special privilege, secret, or race condition — only network reachability to the aggregator's port.

### Recommendation
Require some form of caller authentication or authorization for `InternalSendTx` (and any other "Internal*" aggregator RPC) even on the aggregator server — e.g., a lightweight shared secret/token, restricting the RPC to a loopback/unix-socket interface only, or validating that the submitted transaction actually corresponds to a transaction previously constructed and tracked by the aggregator's own state (e.g., matching a known `TransactionType`/deposit/kickoff record) before queuing it for broadcast.

### Proof of Concept
1. Start an aggregator per the standard deployment (aggregator gRPC server without client-certificate enforcement, as is the documented default).
2. From any machine with network access to the aggregator's port, open a TLS connection (no client cert required) and call `ClementineAggregator/InternalSendTx` with an arbitrary signed Bitcoin transaction and a chosen `fee_type`.
3. Observe that `internal_send_tx` accepts the request and calls `self.tx_sender.insert_try_to_send(...)` and commits it to the DB without any authorization check, exactly as exercised in the test helper that calls it directly with only an aggregator client handle [4](#0-3) .

#[allow(clippy::result_large_err)]
fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }

Clementine uses mutual TLS (mTLS) to secure gRPC communications between entities

    async fn internal_send_tx(
        &self,
        request: Request<clementine::SendTxRequest>,
    ) -> Result<Response<Empty>, Status> {
        #[cfg(not(feature = "automation"))]
        {
            Err(Status::unimplemented("Automation is not enabled"))
        }
        #[cfg(feature = "automation")]
        {
            let send_tx_req = request.into_inner();
            let fee_type = send_tx_req.fee_type();
            let signed_tx: bitcoin::Transaction = send_tx_req
                .raw_tx
                .ok_or(Status::invalid_argument("Missing raw_tx"))?
                .try_into()?;
            tracing::warn!(
                "Internal send tx rpc called with feetype: {:?}, tx hex: {}",
                fee_type,
                bitcoin::consensus::encode::serialize_hex(&signed_tx)
            );

            let mut dbtx = self.db.begin_transaction().await?;
            self.tx_sender
                .insert_try_to_send(
                    &mut dbtx,
                    None,
                    &signed_tx,
                    fee_type.try_into()?,
                    None,
                    &[],
                    &[],
                    &[],
                    &[],
                )
                .await
                .map_to_status()?;
            dbtx.commit()
                .await
                .map_err(|e| Status::internal(format!("Failed to commit db transaction: {e}")))?;
            Ok(Response::new(Empty {}))
        }
    }
