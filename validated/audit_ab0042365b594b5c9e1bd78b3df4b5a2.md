### Title
`ReceivedOutput::read` accepts an arbitrary `TxOut`/`offset` pair without verifying the output pays to the offset key, allowing unspendable outputs to be registered as received funds — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The `TokenBridge` bug class is "interface-compatible input accepted where a different type was intended, enabling a one-way operation whose reverse always fails." In Serai, `ReceivedOutput::read` deserializes an `offset` scalar, an arbitrary `TxOut`, and an `OutPoint` — and returns a `ReceivedOutput` that the rest of the system treats as a spendable output owned by the scanner's key. Yet `read` never checks that `output.script_pubkey == p2tr(key + offset·G)`. An attacker-controlled byte stream can therefore register an output the wallet cannot actually spend, the direct analog of an ERC721 being "bridged" as if it were an ERC20.

### Finding Description
`Scanner::scan_transaction` correctly constructs `ReceivedOutput`s: it only pushes one when `self.scripts.get(&output.script_pubkey)` matches a registered `offset` (networks/bitcoin/src/wallet/mod.rs:199-214). That guarantees `ReceivedOutput` implies "this output pays to `p2tr(key + offset·G)`".

`ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) breaks that invariant. It reads:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)?;
outpoint = OutPoint::consensus_decode(&mut buf_r)?;
Ok(ReceivedOutput { offset, output, outpoint })
```

There is no binding between `offset` and `output.script_pubkey`, and no check that `outpoint` references a real on-chain output paying to the derived script. The deserializer is like `bridgeToken` accepting an ERC721: the wire format is satisfiable by any `TxOut` (any script, any value, dust), and the result is accepted as a genuine received output.

Concretely, untrusted bytes fed to `ReceivedOutput::read` can claim:
- an `offset` of `0` with a `script_pubkey` paying to an attacker key (funds "received" that were never the multisig's, or worse),
- a valid `script_pubkey` belonging to the scanner but paired with the *wrong* `offset` — when the processor later tries to spend it via `send.rs`/`sign`, it produces a signature for `key + offset·G` which does not match the output's actual key, so the spend always fails — the same "bridged over fine, cannot bridge back" one-way failure,
- an `outpoint` that doesn't exist, producing phantom received funds.

### Impact Explanation
A deserialized `ReceivedOutput` is treated downstream as spendable wallet funds (it feeds `Plan` inputs in processor/src/plan.rs, which are transcripted and signed). Consequences:
- **Unspendable-input plans**: a `ReceivedOutput` with a mismatched offset yields a spending transaction whose Schnorr key (`key + offset·G` after tweak/negation in `tweak_keys`, networks/bitcoin/src/wallet/mod.rs:46-75) does not equal the output's key; the signature will not verify under BIP-341, so the plan can never complete — the analog of permanently stuck NFTs.
- **Phantom deposits**: attacker bytes can report funds as received that are not spendable by the threshold key, satisfying the "funds reported received that are not spendable" acceptance criterion.

### Likelihood Explanation
Reachability is exactly the permitted surface: untrusted bytes fed to `ReceivedOutput::read`. Outputs cross component boundaries in serialized form (the processor obtains received outputs from scanners/queues), and `read` is the trust boundary that should re-establish the scanner's invariant but doesn't. No malicious validator or leaked key is required — only control of the serialized bytes. The caveat: I could not fully trace every caller of `ReceivedOutput::read` within the index (callers in `processor/src/networks/bitcoin.rs` and the message queue were identified as deserializing network outputs but not fully verifiable), so concrete exploitation depends on whether a peer/untrusted party can influence those bytes; if the bytes only ever come from the node's own trusted scanner, impact reduces to defense-in-depth.

### Recommendation
Bind the deserialized fields cryptographically, mirroring the fix of "revert if `decimals()` fails":
- Pass the scanner's `key` (or a `Scanner`/`ProjectivePoint` reference) into `ReceivedOutput::read`, recompute `p2tr_script_buf(key + GENERATOR * offset)`, and reject the input unless it equals `output.script_pubkey`. Also reject `offset` values that don't correspond to a registered script.
- Alternatively, store `Scanner::scripts` lookup results inside `ReceivedOutput` and make deserialization a `Scanner` method (`Scanner::read_output`) so construction without validation is impossible (make fields private and `read` the only constructor path that verifies).

### Proof of Concept
```rust
use bitcoin::{TxOut, OutPoint, ScriptBuf, Amount, Txid, hashes::Hash};
use bitcoin_serai::wallet::ReceivedOutput;
use k256::Scalar;
use frost::curve::{Ciphersuite, Secp256k1};

// Attacker supplies bytes: offset = 0, TxOut paying to an attacker P2TR script, fake outpoint
let mut bytes = vec![];
bytes.extend(Scalar::ZERO.to_bytes()); // offset claim: "pays to base key"

let attacker_output = TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: ScriptBuf::new_p2tr_tweaked(
    bitcoin::key::TweakedPublicKey::dangerous_assume_tweaked(
      bitcoin::key::XOnlyPublicKey::from_slice(&[0x02; 32]).unwrap() // not the wallet's key
    ),
  ),
};
bytes.extend(bitcoin::consensus::encode::serialize(&attacker_output));
bytes.extend(bitcoin::consensus::encode::serialize(&OutPoint::new(Txid::all_zeros(), 0)));

let received = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
// Accepted with no error despite the output being unspendable by the scanner's key.
assert_eq!(received.value(), 100_000);
// Any downstream spend attempt produces a signature for key + 0·G, which will not
// satisfy attacker_output.script_pubkey -> permanently unspendable "received" funds.
```
