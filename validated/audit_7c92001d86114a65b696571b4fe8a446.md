### Title
Path traversal via crafted PR file path when opening a file in an external editor / default program - (File: `app/src/ui/open-pull-request/pull-request-files-changed.tsx`)

### Summary
When a user double-clicks a file in the "Files Changed" list of the pull-request review UI, or uses the "Open with default program" context-menu action, Desktop builds the on-disk path by joining the repository root with the attacker-influenced `file.path` string coming from the GitHub API pull-request diff, using plain `Path.join()`, with no `resolveWithin`-style containment check. This is the same broken-invariant class as the `Policy.removeSelf` report: a security-relevant check ("stay inside the repo") is expected but silently skipped instead of failing loudly.

### Finding Description
`onOpenFile` and `onFileContextMenu` in `PullRequestFilesChanged` compute the file path like this: [1](#0-0) [2](#0-1) 

`fullPath` is then passed straight to `dispatcher.openInExternalEditor(fullPath)` or `this.onOpenFile(file.path)` → `openFile(fullPath, ...)`. `file.path` originates from `CommittedFileChange` entries built from the PR diff data returned by the GitHub API for the pull request's head repository — a repository that, for a PR from a fork, is fully controlled by the PR author, not the local repo owner.

Compare this to the sibling code path in `app/src/ui/dispatcher/dispatcher.ts`'s `openRepositoryFromUrl`, which handles a conceptually identical "open a path relative to a repo" operation but explicitly guards it: [3](#0-2) 

That function rejects absolute paths and calls `resolveWithin(repository.path, filepath)` (defined in `app/src/lib/path.ts`, lines 36-72) which normalizes, rejects null bytes, and — critically — resolves symlinks via `realpath` before verifying the result is still inside the root. `Path.join` alone provides none of these guarantees; a `file.path` value that is an absolute path (e.g. `/etc/passwd` style) or that traverses via `..` segments, or that traverses through a symlink already present in the working tree, would not be constrained the way `resolveWithin` constrains it.

### Impact Explanation
If the PR head repo (attacker-controlled fork) can produce a diff entry whose path is not confined to the checkout, or if the local working tree contains a symlink (itself potentially introduced by content from the same fork/branch), the "open in external editor" / "open with default program" actions could open, and — depending on the external program associated with the file extension — potentially execute or expose a file outside the repository (e.g., an SSH key, `.netrc`, or another sensitive file), fulfilling the "file write or read outside the repo" impact criterion. The context-menu path additionally exposes `fullPath` via `Copy File Path`, which can leak absolute filesystem structure to whatever the user pastes it into, but the more serious primitive is unconfined open of an out-of-repo path.

### Likelihood Explanation
Requires the victim to open a pull request from a hostile fork (an ordinary, expected Desktop workflow: reviewing external contributions) and to double-click or use "open with" on a file in the files-changed list — no unusual steps beyond normal PR review. The `nonLocalCommitSHA` / “files changed” list is populated straight from the GitHub API pull-request diff, so the attacker only needs to control commit content of their own fork/branch. This is meaningfully weaker likelihood than the `resolveWithin`-protected `open-repository-from-url` path, indicating the omission here is inconsistent hardening rather than a deliberate, documented design decision (unlike the `Policy.removeSelf` case, where Eco explicitly justified the silent behavior).

### Recommendation
Route `file.path` through `resolveWithin(repository.path, file.path)` (as already done in `dispatcher.ts`'s `openRepositoryFromUrl`) before constructing `fullPath` in `onOpenFile` and `onFileContextMenu`, and refuse (fail loudly, e.g. disable the menu item / log and no-op with user-visible feedback) when the resolved path is `null` or falls outside the repository root, rather than silently trusting `Path.join`.

### Proof of Concept
Conceptual PoC (cannot be executed without live Desktop + GitHub API/fork setup, so this is a code-path trace, not an exploited run):
1. Attacker opens a PR from a fork against a repository the victim has open in Desktop.
2. The PR diff (as returned by the GitHub API) includes a file entry whose path, when normalized, is crafted to resolve outside the repository root once joined (e.g., via traversal segments or via a symlink pre-existing at a shallow path inside the checkout that a prior commit in the same PR added).
3. Victim opens the PR in Desktop's "Files changed" view (`PullRequestFilesChanged`) and double-clicks the file, or right-clicks → "Open with default program".
4. `onRowDoubleClick` / `onOpenFile` builds `fullPath = Path.join(repository.path, file.path)` with no containment check and hands it to `openInExternalEditor` / `openFile`, opening whatever `fullPath` resolves to.

Note: I was not able to fully verify, within the available tool budget, whether `git`/GitHub API diff parsing elsewhere in this codebase already normalizes/rejects such `file.path` values before they reach `CommittedFileChange` (e.g., in the diff-parsing or status-parsing layers) — that would be the key mitigating factor to check next in a full engagement, since if upstream parsing already strips `..`/absolute paths, this specific PR-review path may already be defended in depth even without `resolveWithin` here.
