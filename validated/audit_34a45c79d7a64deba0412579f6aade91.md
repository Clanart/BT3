## Analog Found

### Title
Receipt token over-minting in `WombatStaking.depositLP` due to lack of balance-diff accounting for non-standard LP tokens - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking` mints receipt tokens 1:1 based on the caller-supplied `_lpAmount` in `depositLP`, instead of measuring the actual tokens received via `balanceOf` diff (the pattern used elsewhere in the same contract for the `depositToken`). If the staked `lpAddress` token has any balance-affecting mechanism outside of a plain 1:1 transfer (fee-on-transfer, deflationary, or rebasing-style behavior), the receipt token supply issued will not match the underlying balance actually custodied, breaking the accounting invariant that the reported bug class (Zerem's cached-vs-actual-balance mismatch) is built on.

### Finding Description
In `WombatStaking.deposit`, the protocol correctly guards against non-standard token transfer semantics by measuring the LP tokens actually received: [1](#0-0) 

However, `depositLP` skips this pattern entirely and mints the receipt token for the full user-specified `_lpAmount`, trusting that the `safeTransferFrom` delivered exactly that amount: [2](#0-1) 

This is the same root cause class as the external report: the protocol caches/assumes an amount (`_lpAmount`) as the true custodied balance and mints accounting tokens (`receiptToken`) against it, without verifying it against the actual balance received via `IERC20(poolInfo.lpAddress).balanceOf(address(this))` diff, `IERC20(poolInfo.lpAddress).safeTransferFrom(_for, address(this), _lpAmount);` followed directly by `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount);` with no reconciliation step. If `lpAddress` is a non-standard ERC20 (fee-on-transfer or later subject to a rebase reducing the WombatStaking contract's LP balance), the receipt token supply outstanding will exceed the LP tokens actually backing it in the system (staked into `masterWombat` via `_stakeToWombatMaster`, which itself pulls `_lpAmount` — not the actual received amount — from the contract): [3](#0-2) 

### Impact Explanation
Once receipt tokens are over-issued relative to actual LP backing, later `withdraw()` calls by unrelated depositors of the same pool can revert or leave insufficient balance to redeem all receipt tokens, causing a permanent freeze of the pool's legitimately deposited funds for some users — mirroring the "funds getting stuck" impact described in the source report.

### Likelihood Explanation
This path is reachable by an ordinary wallet through the pool helper contracts calling `depositLP`, requires no privileged role, and depends only on the `lpAddress` token exhibiting non-standard transfer/balance behavior (a token-class precondition), consistent with the Medium-severity classification in the original report.

### Recommendation
Mirror the `deposit()` pattern in `depositLP`: measure `balanceOf(address(this))` before and after the `safeTransferFrom`, mint `receiptToken` and stake only the actually-received delta, and document that `lpAddress` tokens with fee-on-transfer or rebasing mechanics are unsupported.

### Proof of Concept
1. Configure or migrate a pool where `lpAddress` is (or becomes) a token with fee-on-transfer or rebasing behavior.
2. A user calls `depositLP(_lpAddress, _lpAmount, _for)`; `safeTransferFrom` delivers less than `_lpAmount` to `WombatStaking`, but `mint(msg.sender, _lpAmount)` issues the full amount of receipt tokens.
3. Over time (or immediately), the receipt token supply for that pool exceeds the LP balance actually staked/held, so a subsequent legitimate withdrawer's `withdraw()` call fails or drains the pool's remaining LP balance, permanently freezing funds for the remaining receipt-token holders.
