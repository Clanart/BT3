### Title
DoS eviction of a paid bandwidth subscription via unauthenticated `app` key on shared FIFO cap - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth` stores prepaid allowances in a FIFO list keyed only by `(app_chain, app)`, capped at `MAX_SUBSCRIPTIONS` (1024), where pushing past the cap silently evicts the oldest entry [1](#0-0) . The `app` key comes directly from the caller-supplied `PurchaseMessage.app` field on `BandwidthManager.purchase()` and is never bound to the purchaser's identity [2](#0-1) . Any account can therefore purchase cheap tier subscriptions under the exact same `(app_chain, app)` pair as a victim application and, after 1024 purchases, force-evict the victim's legitimately paid, unconsumed allowance — mirroring the vePeg `MAX_DELEGATES` bug where an unbounded, uncontrolled counter check enables a griefer to force an unwanted removal of another party's position.

### Finding Description
Each `(app_chain, app)` entry is a `BoundedVec<Subscription, MaxSubscriptions>` of size 1024 [3](#0-2) . `push_subscription`, used by both real purchases (`on_accept`) and admin `force_credit`, evicts index `0` (the oldest, FIFO-head) whenever the list is already full, unconditionally of the evicted entry's remaining value [4](#0-3) .

The `app` key is decoded straight out of the wire message with no ownership check tying it to `msg.sender` on the EVM side or to `request.from` on the pallet side — only the *manager contract address* (`request.from`) is authenticated, not the `app` value inside the payload [5](#0-4) . Per the documentation, "any purchase" (from any caller) can name an arbitrary `app` and `chain`, since sponsorship of a foreign app is an intended feature [6](#0-5) .

This means an attacker who observes a large legitimate `BandwidthCredited` event for `(app_chain, app)` (containing a big `remaining_bytes` allowance meant to last it a long time) can immediately submit 1024 cheap tier-1 purchases against that same `(app_chain, app)` pair. Because eviction is strictly FIFO-by-age and not size-aware, the attacker's minimal-tier entries queue up and, once the cap is hit, begin evicting the front of the list — including the victim's large, still-unconsumed subscription — well before it naturally expires or is drained by the gate.

This directly parallels the reported vePeg issue: a hard cap (`MAX_DELEGATES` there, `MAX_SUBSCRIPTIONS`/1024 here) combined with a cheap, permissionless way to add entries under someone else's tracked key (1-wei lock there, minimal-tier purchase here) lets an attacker force the removal/loss of a victim's larger position that the victim did not consent to relinquish.

### Impact Explanation
The victim application loses bandwidth it already paid for — `SubscriptionEvicted` fires with `lost_bytes` equal to whatever remained on the evicted entry [7](#0-6) . Depending on how much was left on the evicted (oldest) entry versus how cheap the smallest tier is, an attacker can destroy an amount of prepaid bandwidth value disproportionate to what they spent, and can repeat the attack on renewal. Because `BandwidthGate::try_consume` rejects (`GateError::NoAllowance`/`Insufficient`) any non-purchase POST request once the allowance is exhausted [8](#0-7) , this is a denial-of-service on the victim's ability to relay cross-chain messages through Hyperbridge until it repurchases — a direct loss/lock of prepaid funds tied to bridge message throughput.

### Likelihood Explanation
High: `app`/`chain` values are visible on-chain in `BandwidthCredited` events, purchase itself is a public, permissionless call to `BandwidthManager.purchase()`, and the only requirement is paying for the cheapest configured tier 1024 times (a bounded, attacker-controlled cost, not requiring any privileged role, malicious relayer, or governance actor).

### Recommendation
Do not let unrelated purchasers dilute/evict another party's allowance under the same `(app_chain, app)` key by unauthenticated third-party purchases. Options: (1) require the purchase caller (or a governance-approved sponsor list) to match the `app` being credited, similar to how `request.from` is checked against `BandwidthManager`; (2) make eviction size/value-aware (e.g., refuse to evict an entry with more remaining bytes than the new one being pushed, or extend the cap rather than silently drop value); (3) increase `MAX_SUBSCRIPTIONS` cost asymmetry by requiring a minimum `bytes`/purchase or rate-limiting purchases per `(app_chain, app)` within a time window.

### Proof of Concept
1. Observe a `BandwidthCredited { app_chain, app, tier, bytes, expires_at }` event for a victim app with a large multi-month purchase (few entries, high `remaining_bytes`).
2. Call `BandwidthManager.purchase(app = <victim's app bytes>, tier = TIER1, months = 1, chain = <victim's app_chain>)` 1024 times from an unrelated account (paying the tier-1 price each time), each dispatching a `BandwidthPurchaseMsg` decoded by `on_accept` into `push_subscription` under the identical `(app_chain, app)` key [2](#0-1) .
3. On the 1025th push (or once the victim's original entries reach index 0), `push_subscription` evicts the victim's still-unconsumed subscription and emits `SubscriptionEvicted { lost_bytes }` [9](#0-8) , per the pallet's own documented eviction test behavior `subscription_cap_evicts_oldest` [10](#0-9) .
4. The victim's app now has its prepaid allowance destroyed and, if no other live subscription remains, subsequent dispatch requests fail the gate with `GateError::NoAllowance`, halting the app's cross-chain messaging until it repurchases.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

/// The 1024-sub cap evicts the oldest entry. force_credit reuses the
/// same push path as purchase, so this also covers the purchase cap.
#[test]
fn subscription_cap_evicts_oldest() {
	new_test_ext().execute_with(|| {
		jump_to(T0);
		let cap = MAX_SUBSCRIPTIONS as u128;

		// Fill the list to exactly the cap. `bytes` encodes the index
		// so we can prove which one got evicted.
		for i in 0..cap {
			Bandwidth::force_credit(
				RuntimeOrigin::root(),
				ForceCreditParams {
					app_chain: APP_CHAIN,
					app: app_key(),
					tier: TIER1,
					bytes: i + 1,
					duration_secs: MONTH_SECS,
				},
			)
			.unwrap();
		}
		assert_eq!(sub_count(APP_CHAIN), cap as usize);
		assert_eq!(sub_at(APP_CHAIN, 0).unwrap().remaining_bytes, 1, "oldest is index 1");

		// One more push: evicts the oldest, appends the new one.
		Bandwidth::force_credit(
			RuntimeOrigin::root(),
			ForceCreditParams {
				app_chain: APP_CHAIN,
				app: app_key(),
				tier: TIER1,
				bytes: cap + 1,
				duration_secs: MONTH_SECS,
			},
		)
		.unwrap();

		assert_eq!(sub_count(APP_CHAIN), cap as usize, "still capped");
		assert_eq!(
			sub_at(APP_CHAIN, 0).unwrap().remaining_bytes,
			2,
			"former second-oldest is now front",
		);
		assert_eq!(
			sub_at(APP_CHAIN, (cap - 1) as usize).unwrap().remaining_bytes,
			cap + 1,
			"new sub is at the back",
		);
	});
}
