## Analysis

The C4 finding centers on a broken invariant: a trusted config value (`token_contract`) can be silently updated to attacker/administrator-influenced data, and that new value is then used downstream (undelegation amount calculation) without re-validating consistency with previously recorded state (`requested_with_fee`), leading to silent miscalculation.

The closest Desktop analog is the automatic remote-URL rewrite performed by `updateRemoteUrl`, which trusts a `clone_url` value returned by the GitHub/GHES API and silently rewrites the local git remote used for all future `push`/`fetch` operations — with no user confirmation, unlike the explicit, user-reviewed remote-URL change flow in Repository Settings.

### Title
Automatic remote-URL rewrite trusts unverified API `clone_url`, allowing silent push/fetch redirection - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
When Desktop refreshes the GitHub metadata for a repository, it calls `updateRemoteUrl`, which automatically overwrites the repository's `origin` remote URL with whatever `clone_url` the API (`api.fetchRepository`) returns for the matched repository, as long as a same-protocol, "unchanged since last sync" heuristic passes. [1](#0-0) [2](#0-1) 

### Finding Description
`repositoryWithRefreshedGitHubRepository` runs on repository refresh and matches the local remote to a GitHub account/host purely from the git remote URL string, then fetches the repository from the API and hands the result to `updateRemoteUrl`. [3](#0-2) 

`updateRemoteUrl` compares the current remote URL to `gitHubRepository.cloneURL` (the value cached from a *previous* API sync) and, if they match and the protocol is the same, silently calls `gitStore.setRemoteURL(...)` with the *new* `apiRepo.clone_url` — with no user prompt: [4](#0-3) 

This mirrors the C4 bug's core pattern: a config value (`token_contract` / here, the cached `cloneURL`) is trusted as the basis for auto-propagating a new value (the new `clone_url`) into a security-relevant field (the `origin` remote used for all subsequent git network operations), without validating that the *source* of the new value (the API response) is trustworthy. If the API endpoint is a GitHub Enterprise Server under attacker control, or the request/response path is intercepted (e.g. via a corporate/malicious proxy that MITMs the configured GHES endpoint — a scenario explicitly in-scope as "git remote/proxy response"), the attacker can return an arbitrary `clone_url`. Because `protocolsMatch` only checks the URL scheme (e.g. `https:`) and not host/owner, an attacker-controlled `https://` host passes this guard, and `setRemoteURL` rewrites `origin` to point at the attacker's git server: [5](#0-4) 

Compare this to the deliberate, user-facing flow for changing a remote URL, which requires the user to explicitly review and submit the new URL in Repository Settings: [6](#0-5) 
and to the explicit consent dialog Desktop shows when an *upstream* remote mismatches expectations (`UpstreamAlreadyExists`), which the automatic origin-URL rewrite has no equivalent of: [7](#0-6) 

### Impact Explanation
If `origin` is silently repointed to an attacker-controlled server, subsequent `git fetch`/`git pull` operations will silently ingest attacker-controlled repository content (supply-chain injection into the local working copy/history), and subsequent `git push` operations will silently send the user's commits to the attacker's server instead of the intended one — a form of "silent corruption of what the user commits or pushes." Depending on how Desktop's credential helper resolves credentials for the new host, this could also risk credential exposure if the rewritten URL embeds a matching hostname the credential helper trusts.

### Likelihood Explanation
This requires the attacker to control the API endpoint's response for the *already-associated* repository (i.e., a compromised/malicious GitHub Enterprise Server or a MITM on that connection) — it does not require local access, admin rights, or pre-existing malware, matching the in-scope "attacker controls...a git remote/proxy response" category. Existing guards (`protocolsMatch`, `remoteUrlUnchanged`, `urlsMatch`) reduce but do not eliminate the risk, since none of them verify the *host* of the new URL against anything the attacker doesn't already control (the API response itself).

### Recommendation
Do not auto-rewrite `origin`'s remote URL without explicit user confirmation (mirroring the `UpstreamAlreadyExists` pattern), and/or restrict automatic rewrites to cases where the new `clone_url`'s hostname matches the account's configured endpoint hostname exactly, rather than relying solely on protocol-scheme equality.

### Proof of Concept
1. User has a repository associated with a GitHub Enterprise account whose API endpoint is later compromised (or is behind a malicious/MITM proxy).
2. Desktop calls `repositoryWithRefreshedGitHubRepository`, which calls `api.fetchRepository(owner, name)`. [8](#0-7) 
3. The attacker-controlled response sets `clone_url` to `https://attacker.example.com/owner/repo.git` (same `https:` scheme as the original, so `protocolsMatch` passes; `remoteUrlUnchanged` passes because the local remote still matches the last legitimately cached `cloneURL`).
4. `updateRemoteUrl` calls `gitStore.setRemoteURL('origin', 'https://attacker.example.com/owner/repo.git')` with no user prompt. [9](#0-8) 
5. The next fetch/push silently targets the attacker's server.

**Uncertainty note:** I could not fully trace how Desktop's credential-attachment logic (trampoline credential helper) behaves when `origin`'s host diverges from the account's configured endpoint host after this rewrite — this affects whether credentials would also be exposed to the attacker's server, or whether the operation would simply fail/prompt for new credentials, and would benefit from a hands-on session to verify end-to-end via a running app.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
```
