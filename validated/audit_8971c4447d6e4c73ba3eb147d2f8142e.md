### Title
`SignableTransaction::new` omits the OP_RETURN data output from the fee/weight calculation, inflating the change output and underpaying the fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes an OP_RETURN output carrying the caller-supplied `data` into `tx_outs`, but both calls to `calculate_weight_vbytes` (with and without change) only pass `payments`, never the data output. The vbyte estimate — and therefore `needed_fee` and the change amount — is computed as if the OP_RETURN output did not exist. This is the direct analog of the Perennial `incrementFees` bug: a leftover amount (donation there, change here) is computed without deducting a real cost component (keeper fee there, the data output's fee contribution here).

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

```rust
// Add the OP_RETURN output
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
``` [1](#0-0) 

`calculate_weight_vbytes` builds its weight-estimation transaction solely from `payments` plus an optional change output; the OP_RETURN output already pushed onto `tx_outs` is never included: [2](#0-1) 

The same omission occurs for the change path, so `fee_with_change` is also underestimated and the change output's value is computed as `input_sat - payment_sat - fee_with_change` with a too-small fee: [3](#0-2) 

An 80-byte OP_RETURN output adds ~90+ non-witness bytes (~90 vbytes) that are never priced. The final signed transaction is strictly larger than estimated, so its effective fee rate is `needed_fee / actual_vbytes < fee_per_vbyte`, while the change output retains the sats that should have covered those bytes.

### Impact Explanation
Two concrete consequences, both reachable purely through the public `data` input:

1. **Change over-credit / fee under-charge.** Every sat the data output should have cost is instead credited to the change output, exactly mirroring the over-credited donation in the Perennial report. The transaction pays less than the requested `fee_per_vbyte`.
2. **Transaction produced at below-relay fee rate.** The `TooLowFee` guard checks `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes` using the *underestimated* `vbytes`. A caller requesting the minimum relay rate with up to 80 bytes of data produces a signed transaction whose true fee rate falls below the network minimum — it will be rejected by relays while Serai's eventuality is already committed to `txid`, stalling the associated payments/funds.

### Likelihood Explanation
`data` is a caller-controlled parameter to `SignableTransaction::new` (bounded at 80 bytes by the `TooMuchData` check at line 171). Any invocation passing `Some(data)` deterministically produces a mispriced transaction — no race, no adversarial timing. The effect scales linearly with `data.len()` and `fee_per_vbyte`. Severity is Medium: the miscalculation is unconditional on the data path, but the practical damage is a modest over-credit to change plus a possible below-minimum-fee transaction, not direct theft of principal.

### Recommendation
Include the OP_RETURN output in the weight estimation. Either pass the fully-built `tx_outs` (or `payments` plus an explicit data-length parameter) into `calculate_weight_vbytes`, e.g.:

```rust
fn calculate_weight_vbytes(
  inputs: usize,
  payments: &[(ScriptBuf, u64)],
  data_len: Option<usize>,
  change: Option<&ScriptBuf>,
) -> (u64, u64) {
  ...
  if let Some(len) = data_len {
    tx.output.push(TxOut {
      value: Amount::ZERO,
      script_pubkey: ScriptBuf::new_op_return(PushBytesBuf::try_from(vec![0; len]).unwrap()),
    });
  }
  ...
}
```

and call it with `data.as_ref().map(Vec::len)` at both call sites (lines 204 and 225-226), so `needed_fee`, `fee_with_change`, and the change value all reflect the real transaction size.

### Proof of Concept
```rust
// FEE = some sat/vbyte rate
let data = vec![0u8; 80];
let tx = SignableTransaction::new(
  vec![output],                 // one input of V sats
  &[(payment_script, 1000)],
  Some(change_script.clone()),
  Some(data),
  FEE,
).unwrap();

// needed_fee is computed over a tx WITHOUT the ~90-vbyte OP_RETURN output.
// Actual signed tx includes it, so:
//   actual_fee_rate = tx.fee() / signed_tx.vsize()  <  FEE
// and change = V - 1000 - needed_fee is ~90*FEE sats larger than correct.
let signed = sign(&keys, &tx);
assert!(signed.vsize() as u64 * FEE > tx.needed_fee()); // underpaid fee
assert_eq!(
  tx.fee(), tx.needed_fee(),
  // yet change keeps the difference: donation-analogous over-credit
);
```
Concretely: `calculate_weight_vbytes` at line 204 estimates the weight of a transaction whose outputs are only `payments`; the constructed `SignableTransaction.tx` additionally contains the OP_RETURN `TxOut` pushed at line 195, so every vbyte it occupies is unpriced in `needed_fee` and in `fee_with_change` used for the change value at line 228.
