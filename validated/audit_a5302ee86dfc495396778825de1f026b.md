### Title
`SignableTransaction` computes `needed_fee` from a template transaction that omits the `OP_RETURN` data output, so the signed transaction pays a lower feerate than requested — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The bug class in the external report is a fee computed on a declared parameter (`matchAmount`) rather than the actual value being transferred. The same shape exists in `bitcoin-serai`: `SignableTransaction::new` pushes an `OP_RETURN` output carrying up to 80 bytes of caller-supplied `data` onto `tx_outs`, but `calculate_weight_vbytes` — which determines `needed_fee = fee_per_vbyte * vbytes` — builds its template transaction only from `payments` and `change`, never including the data output. The transaction that is actually signed and broadcast is larger than the one the fee was priced for, so the transaction systematically underpays relative to the intended feerate, exactly like a fee assessed on a declared `matchAmount` that can be made smaller than the real payout.

### Finding Description [1](#0-0) 

The `OP_RETURN` output is appended to `tx_outs` at lines 194-202, but the weight/vbyte estimate at line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, passing only `payments` — the `data` output is never included in the template `tx.output`. The same omission occurs in the change branch at lines 225-227. `calculate_weight_vbytes` (lines 62-127) only constructs `TxOut`s from `payments` and the optional `change`, so `vbytes` — and therefore `needed_fee` — are computed for a transaction missing up to ~90 bytes (80-byte push + `OP_RETURN` + output overhead).

Two consequences follow:

1. `needed_fee = fee_per_vbyte * vbytes` underprices the real transaction. The docstring at lines 129-132 promises "the fee necessary for this transaction to achieve the fee rate specified at construction," but the achieved feerate is `needed_fee / actual_vsize < fee_per_vbyte`.
2. The `TooLowFee` guard at lines 211-213 checks `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the same underestimated `vbytes`. A caller specifying a borderline feerate produces a transaction whose *actual* feerate falls below the minimum relay feerate, so it will be rejected/expelled from mempools even though the constructor returned `Ok`.

The change path has an additional wrinkle: `fee_with_change` is also computed without the data output, and the leftover `input_sat - payment_sat - fee_with_change` can be pushed below `DUST` by the unpriced data output, silently converting value that would have been change into extra fee (or vice versa — a change output is created that absorbs fee budget priced for a smaller tx).

### Impact Explanation
The multisig signs a transaction whose effective feerate is strictly lower than the `fee_per_vbyte` it agreed to, and which can fall below `DEFAULT_MIN_RELAY_TX_FEE` despite the constructor's own guard passing. In a threshold-signing context this is a "concrete signing of an unintended message" in economic terms: the signed artifact does not satisfy the fee-rate contract the signers were shown via `needed_fee()`. Practically, outputs can become temporarily unspendable (stuck in mempool / dropped), and on regtest-tested flows the discrepancy is up to ~90 vbytes × `fee_per_vbyte` sats of missing fee. Severity is Medium rather than High because the underpayment is bounded by the 80-byte data cap and overpayment — not theft — is the worst steady-state outcome.

### Likelihood Explanation
`data` is an attacker-/caller-controlled parameter of the public `SignableTransaction::new` API. Any integration that attaches `OP_RETURN` metadata to spends (the Serai protocol itself uses `Shorthand`-encoded `OP_RETURN` data on Bitcoin transactions, e.g. `tests/full-stack/src/tests/mint_and_burn.rs` lines 316-319) hits this path. The only reason it is not triggered inside `processor/src/networks/bitcoin.rs` today is that `make_signable_transaction` currently passes `None` for `data` (line 450); the moment outflow transactions carry data, every such transaction underpays its intended feerate by up to ~90 vbytes worth.

### Recommendation
Include the `data` output in `calculate_weight_vbytes` (e.g., pass `tx_outs` or an `Option<&ScriptBuf>` for the `OP_RETURN` script) so `needed_fee` and the `TooLowFee` check are priced against the transaction actually produced. Alternatively, build the real `Transaction` first and derive `needed_fee` from `tx.weight()`/`tx.vsize()` directly, eliminating the declared-vs-actual split entirely — mirroring the report's recommendation to base the fee on the actual amount rather than a parameter.

### Proof of Concept
```rust
// networks/bitcoin/tests/wallet.rs — conceptual extension of test_data
let output = send_and_get_output(&rpc, &scanner, key).await;
let data = vec![0u8; 80]; // max allowed, +80 bytes of OP_RETURN payload

let stx = SignableTransaction::new(
  vec![output],
  &[],
  Some(p2tr_script_buf(key).unwrap()),
  Some(data),
  FEE,
).unwrap();

let tx = sign(&keys, &stx);
let actual_vsize = u64::try_from(tx.vsize()).unwrap();

// needed_fee was priced on a template WITHOUT the OP_RETURN output
let needed_fee = stx.needed_fee();
let implied_vsize = needed_fee / FEE; // vsize the fee was calculated for

// The actual transaction is larger than what was priced:
assert!(actual_vsize > implied_vsize);
// Effective feerate is below the requested FEE:
assert!(needed_fee / actual_vsize < FEE);
// With FEE chosen at the relay minimum boundary, the check at
// send.rs:211 passes while the real tx falls under DEFAULT_MIN_RELAY_TX_FEE.
```
