### Title
Recursive clone disables Git's CVE-2024-32004 protection via `GIT_CLONE_PROTECTION_ACTIVE=false`, enabling arbitrary code execution from a malicious repository - (File: app/src/lib/git/clone.ts)

### Summary
GitHub Desktop's `clone()` function always performs `git clone --recursive` while explicitly forcing the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` for every clone operation. This variable corresponds to the runtime safety check Git added upstream to defend against malicious repositories (with crafted submodules/symlinked `.git` directories or case-confusable hook paths) that can smuggle in hooks that execute during a recursive clone. Explicitly disabling this checked path removes an upstream-hardened guard for every user-initiated or automatic clone.

### Finding Description
`clone()` builds the git invocation with `--recursive` and always merges an env object that sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` regardless of the source of the URL: [1](#0-0) 

The `env` used here flows straight into the `git()` execution wrapper with no further gating, and the same disabling flag is applied uniformly whether the clone target is a trusted first-party remote or an arbitrary attacker-supplied URL entered by the user (e.g. via "Clone repository" dialog, a deep link, or `cloneAgain` for GitHub-derived `cloneURL`): [2](#0-1) 

Because the clone path itself is attacker-influenced content — a malicious repository can ship submodules whose superproject `.gitmodules`/`.git` structure is crafted to exploit the exact class of clone-time hook execution bug this protection variable exists to stop — turning the check off during `--recursive` clone reopens that attack surface inside an application whose core feature is cloning arbitrary user- and internet-supplied repositories.

The existing guards in this codebase (`isClonePathSensitive`, the "unsafe repository"/`safe.directory` ownership check in `AddExistingRepository`/`MissingRepository`) only address (a) destination-path traversal and (b) locally pre-existing repositories owned by another OS user. Neither guard inspects or restricts what a freshly *cloned* repository's submodule/hook content can do during the clone itself, so they do not compensate for disabling `GIT_CLONE_PROTECTION_ACTIVE`. [3](#0-2) 

### Impact Explanation
If disabling this variable indeed suppresses Git's built-in defense against the clone-time hook/submodule execution class of bug, then any user who clones a malicious repository URL through GitHub Desktop (a normal, expected action — the whole point of the app) could have arbitrary code executed on first clone, before the user ever opens or interacts with the resulting repository. This maps directly to the report's "attacker controls a cloned/fetched repository" primitive and to the code-execution impact tier defined as valid.

### Likelihood Explanation
Cloning is the primary, unavoidable workflow of GitHub Desktop and is triggered from multiple attacker-reachable entry points (manual URL entry, GitHub repository picker, "Clone Again" from a `gitHubRepository.cloneURL`), and `--recursive` + the protection-disabling env var are applied unconditionally on every call to `clone()` with no opt-out or extra confirmation shown to the user: [4](#0-3) 
This makes the path both easy to trigger (just clone a crafted repo) and universal (affects every clone, not just an edge case).

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. If it was disabled to work around a compatibility/UX issue, gate the recursive submodule clone behind Git's protection remaining active, and instead handle any resulting errors/prompts explicitly (e.g., surface a warning dialog and require explicit user confirmation before proceeding with an unprotected recursive clone), rather than silently defeating the check for all clones.

### Proof of Concept
I could not execute this in the sandbox (no filesystem/terminal access), and I was unable to fully confirm the exact upstream semantics of `GIT_CLONE_PROTECTION_ACTIVE` from local files alone since it originates in the `git`/`dugite` binary rather than this repo's source — this should be independently verified against the Git changelog for CVE-2024-32004/CVE-2024-32002 before treating this as fully confirmed. Conceptually:
1. Attacker publishes a public repository containing a submodule structured to exploit the clone-time hook execution class of bug that `GIT_CLONE_PROTECTION_ACTIVE` was introduced to block.
2. Victim opens GitHub Desktop and clones the attacker's repository URL (via "Clone repository" or a shared link).
3. `clone()` runs `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false` set, per [1](#0-0) , bypassing the check that would otherwise abort or warn.
4. If the underlying Git protection would have blocked the malicious submodule/hook combination, code execution occurs during the clone, before the user does anything else with the repository.

Given I could not verify the precise runtime behavior of this flag against the bundled `dugite`/Git version, I recommend a background agent confirm via the Git changelog and by testing against a crafted proof-of-concept submodule repository whether disabling this flag actually removes protection in the bundled Git version, and if so, treat this as the confirmed finding; otherwise, re-scope the report accordingly.
