### Title
`Scanner::scan_block` omits the coinbase-maturity predicate, reporting immature (unspendable) outputs as received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates `block.txdata` unconditionally — including `txdata[0]`, the coinbase transaction — and feeds every transaction through `scan_transaction`, which matches outputs purely by `script_pubkey`. Coinbase outputs are consensus-immature for 100 blocks, yet they are returned in the same `Vec<ReceivedOutput>` as immediately spendable outputs, with no flag distinguishing them. This mirrors the Cloudreve bug class: a function whose contract implies a filtered result set (`SearchActive` / "received spendable outputs") omits the eligibility predicate (status / maturity), silently including entries the caller expects suppressed.

### Finding Description
`scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214) matches each `output.script_pubkey` against registered scripts and emits a `ReceivedOutput` with the outpoint and offset. `scan_block` (lines 221-227) loops `for tx in &block.txdata` starting at index 0 — the coinbase — with no `tx.is_coinbase()` check, no maturity tracking, and no depth/height context. The only mitigation is a doc comment (lines 216-220) telling integrators to post-process or scan `block.txdata[1 ..]` themselves. `ReceivedOutput` (lines 90-97) carries no maturity or coinbase marker, so downstream code cannot distinguish an immature output without re-fetching the transaction.

Reachability: a Bitcoin miner (an unprivileged party) can craft a coinbase paying the Serai multisig's P2TR script. Any caller using `scan_block` — the natural API for block-level scanning — receives a `ReceivedOutput` that cannot be spent for 100 blocks. The same gap applies to any future coinbase-like immature crediting path.

### Impact Explanation
Funds are reported received that are not spendable — an explicitly accepted impact class. A downstream processor crediting deposits from `scan_block` would mark balance as available while the UTXO is consensus-unspendable; attempts to spend it fail (or, worse, a batch built including it is rejected by the network), and reorgs of immature coinbases additionally invalidate the credit entirely.

### Likelihood Explanation
Low-to-moderate. Requires a miner to deliberately place the scanned script in a coinbase (costless for the miner beyond normal block production), and requires the integrator to use `scan_block` rather than `scan_transaction` on `txdata[1 ..]`. The doc comment mitigates this — the caveat is documented, which weakens the finding toward documented-misuse territory — but the API itself provides no enforcement or marker, so the failure mode is silent.

### Recommendation
- Skip `block.txdata[0]` (or filter on `tx.is_coinbase()`) inside `scan_block`, matching the "Active" predicate siblings apply in the reference bug.
- Alternatively, add a `coinbase: bool` / maturity field to `ReceivedOutput` so callers can enforce policy without re-fetching.

### Proof of Concept
```rust
// Any miner mines a block whose coinbase (txdata[0]) has an output paying
// scanner-registered script_pubkey. Then:
let outputs = scanner.scan_block(&block);
// outputs contains a ReceivedOutput for the coinbase UTXO, indistinguishable
// from a normal deposit, despite being unspendable for 100 blocks.
// send/sign flows consuming it produce a transaction the network rejects
// (bad-txns-coinbase / non-BIP68-final style maturity failure).
```

Relevant code: `scan_block` at `networks/bitcoin/src/wallet/mod.rs:221-227`, `scan_transaction` at lines 199-214, `ReceivedOutput` at lines 90-97.

Caveat: the maturity hazard is disclosed in the `scan_block` doc comment, so strict reviewers may classify this as documented-misuse rather than a vulnerability; it is reported because the API commingles immature outputs without an enforceable predicate, which is the direct analog of the omitted status filter.
