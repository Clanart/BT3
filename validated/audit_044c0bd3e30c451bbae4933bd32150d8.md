### Title
Unchecked payment and fee arithmetic permits crash or creation of an unintended Bitcoin transaction - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` adds attacker-influenced payment and fee values using unchecked `u64` arithmetic. A payment amount near `u64::MAX` overflows `payment_sat + needed_fee`, causing a panic in checked builds or wrapping in unchecked-release builds. [1](#0-0) 

### Finding Description
The constructor sums caller-provided payment amounts into `payment_sat` and computes `needed_fee` by multiplying caller-provided `fee_per_vbyte` with transaction vbytes. [2](#0-1) 

The subsequent funds check evaluates `input_sat < (payment_sat + needed_fee)` without checked arithmetic. [3](#0-2) 

For example, a single payment of `u64::MAX` passes the dust check, while adding any nonzero `needed_fee` overflows. [4](#0-3) 

If the arithmetic wraps, the insufficient-funds check can pass even though the transaction output value is far larger than the collected inputs, producing a `SignableTransaction` for an economically impossible Bitcoin transaction. [5](#0-4) [6](#0-5) 

### Impact Explanation
An unprivileged party that can influence transaction-payment data may either crash the signing process or cause it to construct and sign a transaction containing outputs that cannot be funded by the specified inputs. [7](#0-6) [8](#0-7) 

The wrapped result also undermines later fee accounting because `fee()` subtracts the sum of outputs from the sum of prevouts. [9](#0-8) 

### Likelihood Explanation
The affected values are direct parameters to `SignableTransaction::new`: every payment amount and `fee_per_vbyte` are caller-controlled, while the collected input total is derived from the provided received outputs. [7](#0-6) [10](#0-9) 

Only values approaching `u64::MAX` trigger the addition overflow, so ordinary payments are unaffected; however, triggering the condition requires no secret, valid UTXO ownership, or cryptographic break. [4](#0-3) [3](#0-2) 

### Recommendation
Replace unchecked accumulation, multiplication, and addition with `checked_add`, `checked_mul`, and checked summation, returning `TransactionError` on overflow. Payment totals should also be bounded by Bitcoin's maximum money supply before constructing `TxOut` values, and the same checked formula should be used consistently for `needed_fee`, change, and `fee()`. [11](#0-10) 

### Proof of Concept
The following minimal call demonstrates the vulnerable expression. `payment` must be `u64::MAX`, while `needed_fee` only needs to be nonzero:

```rust
let input_sat: u64 = 200;
let payment_sat: u64 = u64::MAX;
let needed_fee: u64 = 1;

// Panics with overflow checks enabled; wraps to 0 otherwise.
let required = payment_sat + needed_fee;

// In an unchecked-release build this comparison is false,
// despite the payment being u64::MAX.
assert!(!(input_sat < required));
```

The vulnerable production path calculates `payment_sat` from `payments`, multiplies `fee_per_vbyte` by `vbytes`, and then performs the overflowing addition inside the `NotEnoughFunds` check. [1](#0-0) 

A transaction-level trigger is to call `SignableTransaction::new` with one spendable output worth at least the wrapped requirement, one payment of `u64::MAX`, and a nonzero fee rate. In a checked build, evaluation panics; in an unchecked-release build, the wrapped comparison can allow construction of the `SignableTransaction`. [7](#0-6) [6](#0-5)
