### Title
Bridge Value-Transfer Mint Relies on External `MinterRole`, Letting Any Minter-Holder on a Mint-Burn Chain Drain Locked/Bridged Liquidity on the Counterpart Chain - (File: `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary
`BridgeTransferERC20.handleERC20Transfer` mints tokens to the recipient whenever the local `Bridge` is configured with `modeMintBurn = true`, by directly invoking `ERC20Mintable(_tokenAddress).mint(_to, _value)`. The security of the whole cross-chain 1:1 accounting model implicitly assumes that **only the Bridge contract** can ever call `mint()` on the token. However, `mint()` authorization is governed entirely by the token's own `MinterRole`, a role that is independent of the Bridge and, by default, is granted to the token **deployer** at construction time and can be freely re-granted to further accounts by any existing minter. Any account that legitimately holds (or was granted) `MinterRole` on the schain-side (or mint-burn side) token can mint tokens out of thin air and move them across the bridge to redeem/drain real value on the counterpart chain — the same bug class as SKALE C4 finding M-07 (`ERC20OnChain`/`DepositBoxERC20` `transferredAmount` drain).

### Finding Description
`ERC20Mintable` mint permission comes from `MinterRole`: [1](#0-0) 

The constructor grants the *deployer* the `MinterRole`, and `addMinter` is gated only by `onlyMinter` — i.e. any existing minter (not just the token owner) can add new minters, and a minter never automatically loses the role when it grants it to someone else (only `renounceMinter()` removes it): [2](#0-1) 

The Bridge's mint-side handling path calls this externally-controlled `mint()` with no additional check that the caller of the *original* mint grant is restricted to the bridge: [3](#0-2) 

The burn-side of the same bridge only requires holding a token balance, with no proof that the tokens being burned originated from a legitimate bridge deposit: [4](#0-3) 

The production test fixture demonstrates the exact setup pattern operators are expected to use — granting `MinterRole` to the bridge via `addMinter` without ever revoking the deployer/owner's own pre-existing minter role: [5](#0-4) 

Because `mode MintBurn` is set independently per `Bridge` instance (one chain can run in lock mode holding real assets, the counterpart chain in mint-burn mode holding a synthetic 1:1 representation) — this is the standard "child chain mints synthetic token, parent chain locks real token" service-chain bridging pattern: [6](#0-5) 

— any account that still holds `MinterRole` on the mint-burn-side token (the original deployer, or anyone that deployer/any minter subsequently added) can:
1. Call `mint(attacker, amount)` directly on the schain token (bypassing the Bridge entirely — no `onlyOperators`/Bridge check exists on the token itself).
2. Call `requestValueTransfer`/`requestERC20Transfer` on the Bridge to burn the freely-minted tokens and emit `RequestValueTransfer`.
3. Have the Bridge operators on the counterpart (lock-mode) chain relay/vote and call `handleERC20Transfer`, which executes `IERC20(_tokenAddress).safeTransfer(_to, _value)` out of the Bridge's real, escrowed token balance: [7](#0-6) 

This drains real locked liquidity on the counterpart chain while other legitimate bridge users' claims on the mint-burn chain become unbacked/worthless — the identical failure mode described in the SKALE report ("mint on the schain side, exit to drain `transferredAmount`/locked balance on mainnet").

### Impact Explanation
An account retaining `MinterRole` on a mint-burn-mode bridged token (which by default includes the token deployer, and any account subsequently granted the role) can mint unlimited synthetic tokens and redeem them for real, escrowed assets on the counterpart chain via the standard bridge `requestERC20Transfer` → `handleERC20Transfer` flow. This is a concrete unauthorized value movement / supply-inflation-to-drain attack across the bridge, matching the "Accept only concrete unauthorized value movement" validation bar. Severity is Medium-to-High depending on locked liquidity value, consistent with the original C4 judge's Medium rating for the analogous root cause (role mismanagement enabling drains contingent on setup).

### Likelihood Explanation
Likelihood is contingent on operational setup: it requires that the deployer/owner of a mint-burn side token either (a) never renounces its own `MinterRole` after granting the role to the Bridge (the exact pattern shown in the repo's own test fixtures), or (b) that role is further delegated to an operator/service account that is later compromised or acts maliciously. Because `MinterRole.addMinter` is `onlyMinter`-gated rather than `onlyOwner`/Bridge-only, there is no protocol-level guarantee preventing this, matching the "contract deployer" reachable-analog category permitted by the rules.

### Recommendation
- Restrict mintable service-chain tokens so that only the Bridge contract address can ever hold `MinterRole`, and have the deployer call `renounceMinter()` immediately after granting the Bridge the role (and disallow further `addMinter` calls, e.g. by overriding `addMinter` to be a one-time/immutable assignment to the bridge address).
- Alternatively, replace the generic `MinterRole` used by `ERC20Mintable`/`BridgeTransferERC20.handleERC20Transfer` with an immutable, bridge-only minter address set at token construction, removing the ability for any other account to ever be granted mint rights.
- Add supply-invariant checks/monitoring so that mismatches between minted supply on the mint-burn chain and escrowed balance on the lock-mode chain can be detected and the bridge frozen (`setRunningStatus`) before large-scale drains occur.

### Proof of Concept
1. Parent chain: Bridge deployed with `modeMintBurn = false`; `ServiceChainToken` registered and real ERC20 liquidity held in the Bridge contract (`contracts/service_chain/bridge/BridgeTransferERC20.sol:70-72`).
2. Child (schain) chain: Bridge deployed with `modeMintBurn = true`; the same token contract is deployed there, and its owner calls `token.addMinter(bridge.address)` per the standard setup shown in `contracts/test/Bridge/bridge.test.ts:84` — but the deployer's own `MinterRole`, granted automatically in the `MinterRole` constructor (`contracts/libs/openzeppelin-contracts-v2/contracts/access/roles/MinterRole.sol:13-15`), is never renounced.
3. Attacker (the deployer, or any account it later added via `addMinter`) calls `token.mint(attacker, LARGE_AMOUNT)` directly — no Bridge/operator check exists on this call (`contracts/libs/openzeppelin-contracts-v2/contracts/token/ERC20/ERC20Mintable.sol:20-23`).
4. Attacker calls `token.requestValueTransfer(LARGE_AMOUNT, attacker, feeLimit, "0x")` (or `bridge.requestERC20Transfer(...)`), burning the freely-minted tokens on the schain and emitting `RequestValueTransfer` (`contracts/service_chain/bridge/BridgeTransferERC20.sol:88-107`).
5. Parent-chain bridge operators observe the event and call `handleERC20Transfer`, which executes `IERC20(_tokenAddress).safeTransfer(attacker, LARGE_AMOUNT)` out of the Bridge's real escrowed balance (`contracts/service_chain/bridge/BridgeTransferERC20.sol:68-72`), draining real locked liquidity that legitimately belongs to other bridge users.

    function _requestERC20Transfer(
        address _tokenAddress,
        address _from,
        address _to,
        uint256 _value,
        uint256 _feeLimit,
        bytes memory _extraData
    )
        internal
        onlyRegisteredToken(_tokenAddress)
        onlyUnlockedToken(_tokenAddress)
    {
        require(isRunning, "stopped bridge");
        require(_value > 0, "zero ERC20 token amount");

        uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);

        if (modeMintBurn) {
            ERC20Burnable(_tokenAddress).burn(_value);
        }

        emit RequestValueTransfer(
            TokenType.ERC20,
            _from,
            _to,
            _tokenAddress,
            _value,
            requestNonce,
            fee,
            _extraData
        );
        requestNonce++;
    }
