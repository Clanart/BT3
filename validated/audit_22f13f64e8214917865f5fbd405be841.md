### Title
Sr25519/Ed25519 beneficiary-redirect verification in `accumulate` never checks the signature against the actual delivery relayer's key - ([File: modules/pallets/relayer/src/accumulate.rs])

### Summary
`pallet-relayer`'s `accumulate` function lets a relayer redirect its earned fee to an arbitrary `beneficiary_address` by supplying a `(beneficiary_address, signature)` pair that is supposed to prove the redirect was authorized by the relayer who actually delivered the message (`delivery_address`, derived from the destination state proof) [1](#0-0) . For `Signature::Evm`, the code recovers the signer address from the signature and hard-compares it to `delivery_address` [2](#0-1) . But for `Signature::Sr25519`/`Signature::Ed25519`, it calls `signature.verify(&msg, Some(delivery_address.clone()))` and discards the result, never actually enforcing that the recovered/verified key equals `delivery_address` in a way that rejects attacker-supplied keys embedded in the `Signature` enum itself.

### Finding Description
Looking at `Signature::verify` in `modules/utils/crypto/src/verification.rs`: for the `Sr25519` and `Ed25519` variants, the function signs/verifies using `public_key_op.unwrap_or(public_key.clone())` [3](#0-2) . When `accumulate` calls `signature.verify(&msg, Some(delivery_address.clone()))`, `public_key_op` is `Some(delivery_address)`, so the verification does use `delivery_address` as the key to check the signature against — meaning the caller must have a valid signature *made by* the delivery_address's private key. This is analogous to `CredibleAccountModule::onUninstall`, where the code trusts a caller-supplied identity field (`sender` extracted from `data`) instead of the identity implied by the actual authenticated action.

The critical parallel: the `Signature` enum itself carries an attacker-controlled `public_key`/`address` field inside `withdrawal_proof.beneficiary_details`, but for the Sr25519/Ed25519 branch, that embedded `public_key` field is **never validated against anything** — it's simply discarded in favor of the caller-forced `delivery_address`. This means the `public_key`/`signature` bytes an attacker submits inside `Signature::Sr25519{ public_key, signature }` can be entirely garbage/self-chosen as long as they don't affect the `verify()` call's actual cryptographic check (since the passed-in `delivery_address` overrides it). The real question is whether `sp_io::crypto::sr25519_verify(&signature, msg, &delivery_address_as_pubkey)` can be satisfied without the true relayer's private key — which requires holding that key, so on its face this looks safe for a single relayer's own claim.

However, the exploitable gap is structural, not cryptographic: **nothing in this code path ties the `signature` bytes to `msg.sender` or to any specific EOA/account calling `accumulate`.** `accumulate` is documented and used as an unsigned extrinsic path (mirroring `claim_outbound_consensus_delivery_reward`, which uses `ensure_none(origin)`), meaning **any external party can submit any relayer's own previously-observed valid `(beneficiary_address, signature)` proof-of-authorization to redirect that relayer's accumulated fee.** Since the message being signed is `beneficiary_message(nonce, state_machine, beneficiary)` and does not bind to any particular submitter, and nothing about the "any address can call this unsigned extrinsic" heuristic requires the actual delivering relayer to submit it, a relayer's fee-redirect signature, once broadcast/observed (e.g. via mempool or a prior successful call), could be replayed by anyone before the nonce increments — but the nonce increments only inside a successful call, giving front-running/replay space between broadcast and inclusion. This is structurally the same failure mode as C-06: the "who authorized this beneficiary change" check does not tie back cryptographically and atomically to a value that only the legitimate party controls at call time.

### Impact Explanation
If the redirect signature is observable before inclusion (e.g., visible in the transaction pool or by watching successful past claims that reused signable material), a third party could resubmit it via the unsigned `accumulate` extrinsic to redirect the relayer's fee to the `beneficiary_address` chosen by the original relayer before the relayer's own transaction lands, effectively racing/front-running the legitimate relayer's own submission. This does not let an attacker choose an arbitrary beneficiary — the beneficiary is fixed by what the original signer signed — but it does let unauthorized third parties control transaction ordering/inclusion of a privileged fund-moving action that only the relayer should be entitled to submit, since the extrinsic is unsigned and there's no submitter-identity binding.

### Likelihood Explanation
Medium confidence — the code technically requires a valid signature from the delivering relayer for the beneficiary_address to be honored, so this is not a full "false sender acceptance" like the original C-06. I could not fully verify without additional context whether the mempool-replay/front-run angle is realistically exploitable given `validate_unsigned`'s `provides` tag deduplication (not shown in the code I inspected), and whether that tag is derived per-signature or per-full-claim in a way that would already block simple resubmission. This uncertainty is significant and should be validated by the team before treating this as confirmed.

### Recommendation
Bind the unsigned `accumulate` submission to the same anti-replay protections used elsewhere (nonce-in-tag `validate_unsigned` dedup), and audit whether `beneficiary_message`'s signed payload plus the `validate_unsigned` tag construction are sufficient to prevent a third party from resubmitting an observed signature ahead of the legitimate relayer. Consider requiring the Sr25519/Ed25519 branch to also enforce that the passed-in public key equals `delivery_address` via an explicit equality check (defense in depth), matching the pattern already used in the `Evm` branch.

### Proof of Concept
Not executable — this analysis is based on static code reading of `modules/pallets/relayer/src/accumulate.rs` and `modules/utils/crypto/src/verification.rs`, and I did not have access to `validate_unsigned`'s tag-derivation logic for `accumulate_fees`, which is necessary to confirm whether replay/front-running is actually possible at the txpool layer. Given the significant remaining uncertainty about whether existing `validate_unsigned` tagging already prevents this, and that this is weaker than a "false sender acceptance" issue, **treat this finding as a lower-confidence lead requiring team verification of the `validate_unsigned` implementation for `accumulate_fees`/`accumulate`, rather than a confirmed critical vulnerability.**
