### Title
Certificate-trust suppression is keyed by URL only, not by certificate fingerprint — allows silent MITM cert-swap acceptance - ([File: app/src/lib/suppress-certificate-error.ts])

### Summary
The bug report is a generic "trust state machine that doesn't re-validate the underlying signal before reusing a prior trust decision" class of bug (OracleAdapterV4 trusting Redstone/Pyth again after a prior failure without cross-checking that the *current* value is actually consistent with what was trusted before). The GitHub Desktop analog lives in the certificate-trust-suppression cache: once a user dismisses/continues past an untrusted TLS certificate warning for a given URL, the suppression is recorded against the bare URL string, with no binding to the specific certificate (fingerprint/serial) that was actually approved.

### Finding Description
`suppressCertificateErrorFor`, `clearCertificateErrorSuppressionFor`, and `isCertificateErrorSuppressedFor` operate on a `Set<string>` keyed purely by `url`: [1](#0-0) 

The renderer checks this cache when Electron reports a `certificate-error` for a given URL, and if suppressed, skips showing the `UntrustedCertificate` dialog entirely: [2](#0-1) 

The dialog itself (`UntrustedCertificate`) only ever receives the certificate and URL to display, and its "Continue" action forwards to `onContinueWithUntrustedCertificate`, which calls `showCertificateTrustDialog` in the main process — an OS-level "always trust this cert" action — but the suppression state that gates whether the in-app warning reappears is tracked independently, by URL string: [3](#0-2) [4](#0-3) 

Because the suppression key is the URL and not `certificate.fingerprint`/`serialNumber`, the invariant "the user approved *this specific* certificate" is broken: any subsequent certificate presented for the same URL — including one substituted by an active network attacker (MITM) after the user's initial approval — will be silently accepted without a new prompt, exactly the same "state 3 → 1 trusts the primary again without cross-checking that it's the *same* trusted signal" flaw described in the OracleAdapterV4 report.

### Impact Explanation
If exploited, a network-position attacker (rogue proxy/Wi-Fi MITM/DNS-spoofed GHE endpoint) who is able to trigger one certificate-error acceptance for a host (e.g. during a GitHub Enterprise sign-in against a self-signed/test cert the user is told is expected) gains a durable window to swap in an arbitrary certificate for that same URL — including one it fully controls — and Desktop will not re-prompt the user. This can lead to interception/modification of HTTPS API traffic (credential/token exfiltration, tampered API responses) for that endpoint, which affects account binding/OAuth flows and can corrupt what the user believes they are pushing/fetching from that host.

### Likelihood Explanation
This requires an active network attacker capable of presenting a different TLS certificate for the same URL after an initial legitimate-looking cert warning was accepted once (e.g., during GHE onboarding, self-signed trial instances, as the `UntrustedCertificate` dialog copy itself acknowledges is expected in some cases) — a scenario within the accepted threat model (attacker controls a git remote/proxy response), not requiring local access or leaked credentials. Likelihood is Medium: it depends on the user having previously accepted a cert warning for that specific URL, which the app's own UI explicitly encourages for GHE trial/unusual-TLD cases.

### Recommendation
Key the suppression cache by a tuple of URL and certificate identity (e.g., SHA-256 fingerprint), not URL alone, so that trust granted for one certificate never silently extends to a different certificate later presented for the same host — mirroring the recommendation to require cross-validation before re-trusting a previously-untrusted signal.

### Proof of Concept
1. Attacker MITMs a GHE-like host and presents a self-signed cert A; user is shown the `UntrustedCertificate` dialog and clicks "Continue"/trust (this path is plausible since the dialog explicitly tells users this can be expected for GHE trials).
2. `suppressCertificateErrorFor(url)` (or equivalent code path feeding `isCertificateErrorSuppressedFor`) records the bare `url` in `suppressedUrls`.
3. Attacker later swaps to a different, fully attacker-controlled certificate B for the same `url` (e.g., new MITM session).
4. `certificate-error` fires again for the same `url`; `isCertificateErrorSuppressedFor(url)` returns `true` (it does not check which certificate triggered the error), so `app.tsx` returns early and never shows the warning dialog: [2](#0-1) 
5. All subsequent HTTPS traffic to that host is silently sent over the attacker's connection with no further user warning.

Note: I was unable to fully trace, within the available iterations, every call site that invokes `suppressCertificateErrorFor` (i.e., confirm the exact UI action that populates the cache versus just displaying the dialog), so the precise trigger step of the PoC should be verified against the full call graph before treating this as fully confirmed exploitable end-to-end.

```typescript
const suppressedUrls = new Set<string>()

export function suppressCertificateErrorFor(url: string) {
  suppressedUrls.add(url)
}

export function clearCertificateErrorSuppressionFor(url: string) {
  suppressedUrls.delete(url)
}

export function isCertificateErrorSuppressedFor(url: string) {
  return suppressedUrls.has(url)
}
```
