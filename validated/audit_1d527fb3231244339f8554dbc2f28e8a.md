### Title
Reentrancy via unguarded external receiver callback after state-changing CW module transfer in `CW1155ERC1155Pointer.safeTransferFrom`/`safeBatchTransferFrom` (and inherited `CW721ERC721Pointer.safeTransferFrom`) - (File: `contracts/src/CW1155ERC1155Pointer.sol`)

### Summary
`CW1155ERC1155Pointer.safeTransferFrom` and `safeBatchTransferFrom` perform the token-moving CosmWasm `send`/`send_batch` state change via `_execute` (a `delegatecall` into the wasmd precompile) **before** calling the attacker-controlled recipient's `onERC1155Received`/`onERC1155BatchReceived` hook, and no reentrancy guard is applied anywhere in the contract. This is the exact checks-effects-interactions violation described in the referenced report (external, user-controlled contract call reached before the calling context's logic has fully unwound), reachable by any EVM transaction sender who deploys a malicious ERC1155 receiver and calls the pointer.

### Finding Description
In `contracts/src/CW1155ERC1155Pointer.sol`: [1](#0-0) 

`safeTransferFrom` first executes the CW1155 `send` message via `_execute` (which `delegatecall`s the wasmd precompile at `0x...1002`, actually moving the token balance in the underlying CosmWasm contract), and only afterwards calls `IERC1155Receiver(to).onERC1155Received(...)` if `to` is a contract. The same pattern is repeated in `safeBatchTransferFrom`: [2](#0-1) 

Neither function (nor `burn`, `burnBatch`, or `setApprovalForAll`) has any reentrancy protection — there is no `nonReentrant` modifier or reentrancy-guard state variable anywhere in the contract, unlike the fixture/test contracts elsewhere in the repo that explicitly use `FixtureReentrancyGuard`/OpenZeppelin `ReentrancyGuard` for exactly this class of external-call risk: [3](#0-2) 

Because `to` is fully attacker-controlled bytecode, the callback executes with the transfer already settled at the CW module layer, but the outer EVM call stack (this pointer contract, and any calling contract such as a marketplace/lending integration on the same pointer) has not yet returned. The attacker's receiver can reenter the pointer contract — e.g. call `safeTransferFrom` again on other token ids it (or an approved operator) holds, call `setApprovalForAll`, or call back into whatever contract initiated the original transfer — while that outer contract's own invariants (balance snapshots, "in progress" flags, etc.) are still mid-execution. This mirrors the `Trader.executeTrade` bug class: an external, user-controlled call (`makeOrder.market` there, `IERC1155Receiver(to).onERC1155Received` here) is reached from inside a state-mutating function with no reentrancy guard.

`CW721ERC721Pointer.sol` shares the same underlying pattern: it overrides `transferFrom` to call the CW module via `_execute` but does not override `safeTransferFrom`, so the inherited OpenZeppelin `safeTransferFrom` calls the overridden `transferFrom` (which moves the CW-side NFT) and then invokes `_checkOnERC721Received`, again reaching an attacker-controlled external call after the token has already moved, with no guard: [4](#0-3) 

### Impact Explanation
Any contract that composes with these pointer contracts (marketplaces, lending/staking integrations, DEX routers taking CW20/CW721/CW1155-backed pointer tokens as collateral or trade legs) can have its own accounting corrupted by reentrant calls that land mid-transaction, since the pointer offers no reentrancy protection and reaches attacker bytecode after committing the transfer. This can enable unauthorized transfer/approval sequencing, double-use of a single approval across nested reentrant calls, or state desynchronization between a caller's pre/post balance checks — i.e., fund-loss-class impact for integrators of the CW⇄EVM pointer bridge, a core, actively used interoperability primitive on Sei.

### Likelihood Explanation
Any unprivileged EVM transaction sender can deploy a malicious contract implementing `IERC1155Receiver`/`IERC721Receiver` and call `safeTransferFrom`/`safeBatchTransferFrom` on a CW1155/CW721 pointer with `to` set to that contract — no special privileges, whitelisting, or governance action is required, since pointer deployment and use is a standard, permissionless flow described in `x/evm/AGENTS.md`. [5](#0-4) 

### Recommendation
Add a reentrancy guard (e.g., OpenZeppelin's `ReentrancyGuard`) to `CW1155ERC1155Pointer` and `CW721ERC721Pointer` state-changing external entry points (`safeTransferFrom`, `safeBatchTransferFrom`, `transferFrom`, `burn`, `burnBatch`, `setApprovalForAll`, `approve`), and/or reorder logic so the CW module state mutation is the last effect (or is otherwise made atomic with the receiver-hook check) rather than preceding an attacker-controlled external call.

### Proof of Concept
1. Deploy a malicious contract `Attacker` implementing `onERC1155Received` that, on being called, immediately calls back into the same `CW1155ERC1155Pointer` (e.g., `safeTransferFrom` on a different token id it controls, or `setApprovalForAll`) before returning the correct selector.
2. From an EOA, call `pointer.safeTransferFrom(attackerOwnedFrom, address(Attacker), id, amount, data)`.
3. Observe that `_execute` (lines 60-63 of `CW1155ERC1155Pointer.sol`) has already committed the CW-side `send` before `Attacker.onERC1155Received` (lines 64-75) runs, and that the reentrant call executes successfully mid-transaction with no guard blocking it — demonstrating the unguarded reentrancy window.

    }

        string memory spender = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(approved)));
        string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(tokenId)));
        string memory req = _curlyBrace(_formatPayload("approve", _curlyBrace(_join(spender, tId, ","))));
        _execute(bytes(req));
    }

    function setApprovalForAll(address operator, bool approved) public override {
        string memory op = _curlyBrace(_formatPayload("operator", _doubleQuotes(AddrPrecompile.getSeiAddr(operator))));
        if (approved) {
            _execute(bytes(_curlyBrace(_formatPayload("approve_all", op))));
        } else {
            _execute(bytes(_curlyBrace(_formatPayload("revoke_all", op))));
        }
    }

    function _execute(bytes memory req) internal returns (bytes memory) {
        (bool success, bytes memory ret) = WASMD_PRECOMPILE_ADDRESS.delegatecall(
            abi.encodeWithSignature(
                "execute(string,bytes,bytes)",
                Cw721Address,
                bytes(req),
                bytes("[]")
            )
        );
        require(success, "CosmWasm execute failed");
        return ret;
    }

```markdown
## Pointer Contracts (CW ↔ ERC Interoperability)

Pointer contracts enable tokens on one VM to be accessed from the other VM. This is the primary interoperability mechanism between CosmWasm and EVM.

**EVM pointers for CW/native tokens:**
- Native Cosmos denoms get an ERC20 representation.
- CW20 tokens get an ERC20 pointer.
- CW721 NFTs get an ERC721 pointer.
- CW1155 multi-tokens get an ERC1155 pointer.

**CW wrappers for ERC tokens:**
- ERC20 tokens get a CW20 wrapper.
- ERC721 NFTs get a CW721 wrapper.
- ERC1155 multi-tokens get a CW1155 wrapper.

Pointers are versioned and can be upgraded. A reverse registry allows looking up the original token from its pointer address.

Pre-compiled bytecode for all pointer contracts is embedded in the binary under `artifacts/`.
```
