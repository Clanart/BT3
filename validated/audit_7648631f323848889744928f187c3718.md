### Title
Unbounded `order.inputs` array in IntentGatewayV2 lets a malicious order-placer permanently lock a solver's escrow redemption - ([File: evm/src/apps/IntentGatewayV2.sol], [File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`placeOrder()` only checks that `order.inputs.length != 0` — there is no upper bound on the number of input tokens (or output assets) a user can pack into an order. [1](#0-0) 
Every escrow-release path (`RedeemEscrow`/`RefundEscrow` delivered via `onAccept`, same-chain cancel, `onGetResponse`) later loops over that same attacker-controlled `tokens`/`inputs` array once, with no length cap and no per-token/batched-claim fallback: [2](#0-1) [3](#0-2) 
This is the same bug-class as the `PeriodicPrizeStrategy` report: an unbounded list that must be fully iterated in a single call in order to release funds, with no way to claim a subset. The difference here is that the "attacker" doesn't need to be an admin — it's the ordinary intent-order placer, and the victim is not themselves but the solver who fills the order.

### Finding Description
A solver fills a cross-chain order on the destination chain (`fillOrder`), which dispatches a `RedeemEscrow` `WithdrawalRequest` back to the source chain containing `order.inputs` verbatim. On the source chain, `onAccept` authenticates the request and calls `_withdraw`/`withdraw`, which iterates `body.tokens` (== `order.inputs`) once per token to decrement escrow and transfer funds to the solver as beneficiary: [4](#0-3) 

Because `order.inputs.length` is unbounded at order-placement time, a malicious user can place an order whose `output` side is small/attractive enough for a solver to profitably fill (the solver only needs to inspect and pay the `output` assets), but whose `inputs` array contains thousands of distinct dummy ERC-20 token entries. The solver has no way to know in advance, from the order alone, that the resulting `RedeemEscrow` message will be economically/technically undeliverable — `dispatchIncoming` → `onAccept` → `withdraw`/`_withdraw` must process the *entire* token list in one call, so once the list is large enough to exceed the destination/source chain's block gas limit (or make the transaction prohibitively expensive), the redemption message can never succeed.

Per the ISMP request-handling invariant documented for the framework, if `on_accept` does not return `Ok`, no receipt is persisted and the message can be endlessly resubmitted — but if it *always* runs out of gas, it can never succeed and never times out either (the request is still "in flight" from the relayer's perspective and there is no automatic timeout-triggered refund path for a request that keeps reverting rather than being delivered before its timeout): [5](#0-4) 

The net effect: the solver has already paid out the order's `output` assets to the beneficiary (the malicious order's `user`), but the solver's own compensation — the escrowed `order.inputs` on the source chain — is permanently unredeemable, because no code path exists to claim the escrowed tokens in batches or one-by-one. There is no length cap in `placeOrder` to prevent this: [6](#0-5) 

The same unbounded-array loop exists in the `withdraw()` used for `RefundEscrow` (order cancellation) and in the Tron fork's `IntentGatewayV2.withdraw`: [3](#0-2) 

### Impact Explanation
This results in genuine loss of funds for an unrelated, honest third party (the solver), triggered purely by an unprivileged user action (crafting and placing a pathological order) — no malicious relayer, prover, admin, or governance actor is required. This matches the bounty's "stealing or loss of funds" / fund-lock category, not a generic gas DoS, because the loss is asymmetric and permanent for the victim (solver), while the attacker (order placer) pays only for a set of dummy-token escrow deposits (or none if the input tokens can be worthless/zero-value tokens, since `_withdraw`/`withdraw` don't require nonzero value per token beyond skip-on-zero logic in `IntentsBase._withdraw`, and duplicate-token rejection only forbids repeats, not array-length).

### Likelihood Explanation
Likelihood is moderate: a solver would typically simulate/estimate gas before filling, but nothing in `fillOrder`/`_fillCrossChain` inspects or bounds `order.inputs.length` before commitment, and solver tooling that only checks profitability of the `output` leg (the common design for intent-fill bots) may not proactively gas-simulate the eventual `RedeemEscrow` delivery on the source chain. The cost to the attacker is bounded by however many dummy `TokenInfo` entries they must supply and deposit (which can be minimal-value/dust or duplicate-free zero-amount entries skipped in one variant), making the attack cheap relative to the value a solver stands to lose.

### Recommendation
- Impose a hard cap (`MAX_INPUTS`) on `order.inputs.length` and `order.output.assets.length` in `placeOrder`, enforced on-chain, sized to a value the destination/source `withdraw`/`_withdraw` loop is guaranteed to process within a safe gas budget.
- Alternatively/additionally, support partial or per-token escrow release so a `WithdrawalRequest` covering many tokens can be redeemed incrementally rather than atomically in one call, mirroring the batching recommendation from the referenced report.
- Consider requiring solvers'/relayers' gas-estimation tooling to reject orders whose "release-cost footprint" exceeds a safe threshold, but this should not be relied upon as the primary defense — the on-chain cap is required.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.output.assets` containing a single attractive asset (e.g., a small amount of USDC) but `order.inputs` containing e.g. 5,000 distinct low/zero-cost `TokenInfo` entries (dummy ERC-20s deployed cheaply, or duplicate-free wrapped variants), escrowing them on the source chain.
2. A solver, seeing a profitable `output` leg, calls `fillOrder` on the destination chain, paying the `output.assets` to the order's beneficiary.
3. `fillOrder`'s cross-chain path dispatches a `RedeemEscrow` `WithdrawalRequest` with `tokens = order.inputs` (5,000 entries) back to the source chain: [7](#0-6) 
4. On the source chain, relayers attempt to deliver this via `handlePostRequests` → `host.dispatchIncoming` → `onAccept` → `withdraw`/`_withdraw`, which must loop over all 5,000 tokens in a single call: [8](#0-7) 
5. The call reverts for out-of-gas on every delivery attempt (block gas limit exceeded), so the request is never marked delivered, `onAccept` is never observed to succeed, and the solver's escrowed compensation is permanently stuck while the solver has already paid the order's output.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
