### Title
Malicious git remote can spoof `WWW-Authenticate: realm="GitHub"` to redirect the Enterprise sign-in prompt and harvest credentials/OAuth tokens - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`SablierV2MerkleLockupFactory` trusts an attacker-suppliable address as if it were a whitelisted, trusted contract, and lets that untrusted value drive a privileged action (fund transfer) without independent verification. The same broken-invariant pattern exists in GitHub Desktop's Git credential trampoline: the credential helper decides whether a remote is "GitHub Enterprise" based purely on a header value that the remote server itself controls (`wwwauth[...]` containing `realm="GitHub"`), and then uses that unverified classification to launch a GitHub sign-in flow bound to the attacker's origin.

### Finding Description
When Git needs credentials for a host, it forwards any `WWW-Authenticate` response headers it received to Desktop's credential helper trampoline. `getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts` uses this attacker-controlled header as a "happy path" to decide whether the remote is treated as `enterprise` without making any independent verification request: [1](#0-0) 

If the remote (a git server the user cloned from, or fetched/pushed to, e.g. `http://malicious.example/repo.git`) answers HTTP auth challenges with a header like `WWW-Authenticate: Basic realm="GitHub"`, `getEndpointKind` returns `'enterprise'` purely on the attacker's say-so - there is no whitelist of known GHE endpoints and no call to `isGitHubHost`, which performs an actual network check, in this branch: [2](#0-1) 

That classification then feeds `getCredential`, which - finding no existing account for the fabricated "enterprise" endpoint - calls `ui.promptForGitHubSignIn(endpoint)` with the attacker-controlled `endpoint` string: [3](#0-2) 

`promptForGitHubSignIn` in `trampoline-ui-helper.ts` then configures and opens the real Sablier-analog "trusted contract" here: it calls `dispatcher.beginEnterpriseSignIn(cb)` and `dispatcher.setSignInEndpoint(origin)` using the attacker's `origin`, and shows a `SignIn` popup carrying `credentialHelperUrl: endpoint`: [4](#0-3) 

This is functionally identical to the report's broken invariant: an externally-supplied, unwhitelisted value (there: a "Lockup" contract address; here: a claimed GitHub "realm") is trusted to drive a sensitive operation (there: fund transfer via approved allowance; here: initiating a GitHub Enterprise authentication/OAuth flow) with no separate whitelist or validation step, and the flow's UI presentation ("looks like a normal GitHub sign-in") does not "attract suspicion", exactly as called out in the original report ("as long as it supports the required functions, not to attract any suspicion in the front-end").

### Impact Explanation
If a user clones or adds a remote to a repository hosted by an attacker-controlled Git server (fully in the "attacker controls a git remote/proxy response" category from the valid-impact list), and Desktop attempts to authenticate against it, the attacker's HTTP response can force Desktop to present a "GitHub Enterprise sign-in" popup bound to the attacker's origin. Depending on which sign-in path is used, the user could either enter Basic-Auth-style credentials that are sent to the attacker's server, or be redirected into an OAuth flow (`getOAuthAuthorizationURL`/`requestOAuthToken` in `sign-in-store.ts`) against an endpoint the attacker names, which can result in exfiltration of session/OAuth material to an untrusted host. This matches the "unauthorized OAuth or account binding" / "credential/token exfiltration" impact categories.

### Likelihood Explanation
The attacker only needs to control the HTTP responses of a git server the victim already interacts with (a cloned repo's remote, or a repo added by URL) - no local access, no prior malware, no leaked credentials, and no unnatural extra steps beyond normal git operations (fetch/push/pull) that Desktop performs automatically when the user opens/syncs a repository. The trigger condition (`wwwauth[...]` header containing `realm="GitHub"`) is entirely attacker-defined server config, which is a low-effort action.

### Recommendation
Do not use the self-reported `WWW-Authenticate` realm as sufficient proof that a host is GitHub Enterprise. At minimum, corroborate the header-based classification with the same independent check already implemented for other code paths (`isGitHubHost`, which performs an actual network request) before elevating an unknown endpoint to `'enterprise'`, and/or maintain a per-account whitelist/allow-list of endpoints the user has explicitly registered as GitHub Enterprise, mirroring the report's own recommendation of using a whitelist of trusted addresses rather than trusting attacker-suppliable data.

### Proof of Concept
1. Stand up a malicious Git-over-HTTP server that, on an authenticated request, replies with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, clone or add this server's repository as a remote and perform a fetch/push/pull that requires auth.
3. Git forwards the `wwwauth[...]` header to the trampoline credential helper; `getEndpointKind` (`app/src/lib/trampoline/trampoline-credential-helper.ts:157-165`) classifies the endpoint as `'enterprise'`.
4. Since no account exists for that endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)` (`trampoline-credential-helper.ts:118`), which opens a GitHub Enterprise sign-in dialog bound to the attacker's origin (`trampoline-ui-helper.ts:80-104`).
5. If the user completes sign-in (basic auth or OAuth), their credentials/token are sent to the attacker-controlled origin instead of a legitimate GitHub Enterprise instance.

Note: I was not able to fully trace the downstream OAuth/basic-auth submission code path in `sign-in-store.ts` within the available iterations (file was only partially read), so the exact mechanics of what is transmitted to the attacker's origin (raw password vs. OAuth code/token) are not fully confirmed from local code and would benefit from further review of `app/src/lib/stores/sign-in-store.ts` and `app/src/ui/sign-in/sign-in.tsx`.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }
