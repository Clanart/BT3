### Title
Address re-association can orphan staking/distribution state, risking the same chain-halt the code explicitly patched for EIP-7702 authorities - (File: utils/helpers/associate.go)

### Summary
`AssociationHelper.AssociateAddresses`/`MigrateBalance` in [1](#0-0)  migrates bank balances from the "direct-cast" address (`sdk.AccAddress(evmAddr[:])`) to the newly associated Sei address, and then deletes the direct-cast account outright when `LockedCoins` is zero. `LockedCoins` only reflects vesting locks, not bonded/delegated stake, so an account that has active staking delegations under its direct-cast identity can still be wiped by `RemoveAccount`. This is the exact bug class flagged in the original report (state tied to an old identity becomes unreachable/orphaned when the identity mapping changes), and sei-chain's own code comments show the team is aware of this failure mode and has patched it only for one narrow trigger path (EIP-7702 `SetCode` authorization authorities), not for the general association flow.

### Finding Description
The Sei chain lets an EVM address transact against a "direct-cast" Sei account (`sdk.AccAddress(evmAddr[:])`) before an explicit Sei<->EVM association exists. Once an `AssociateTx`, an implicit association (regular EVM tx from an unassociated address), or an EIP-7702 authorization causes `AssociateAddresses` to run, `MigrateBalance` moves spendable coins and wei balance from the direct-cast address to the real Sei address, and then calls `accountKeeper.RemoveAccount` on the direct-cast address if its `LockedCoins` are zero [2](#0-1) .

`LockedCoins` on the bank keeper reflects only vesting-account locking, not funds delegated to validators via staking, which are held in the bonded/unbonding pool rather than the account's spendable balance. Consequently, a direct-cast account that has delegated stake (or has other module state keyed to its address, e.g. distribution reward info) can pass the "LockedCoins is zero" check and have its base account entry removed, while the staking/distribution modules still hold delegation and reward state referencing that address as the delegator.

The code base already documents this exact failure mode for one specific trigger: the ante handler comment in [3](#0-2)  explicitly states that a mutable direct-cast EVM->Sei mapping that gets remapped by a later `associatePubKey` call can "orphan any staking/distribution state created under the direct-cast identity," which "can then halt the chain via the distribution validator-removal hook." The fix implemented, `associateAuthorizationAuthorities` [4](#0-3) , only pre-associates EIP-7702 `SetCode` authorization authorities before their delegation code is installed — it does not address the general case where any direct-cast identity accumulates staking/distribution state (e.g., by delegating stake using the direct-cast Sei address before ever sending a transaction through the EVM, or before ever calling `Associate`) and is later associated (or re-associated) through the normal `AssociateAddresses`/`MigrateBalance` path.

### Impact Explanation
If a direct-cast identity's account object is removed by `RemoveAccount` while staking/distribution keepers still reference it as a delegator (or otherwise expect an existing account), any subsequent hook that reads that account (for example the distribution module's validator-removal hook mentioned in the code comment) can encounter a missing account and panic, which on a consensus-critical path halts block production chain-wide — matching the "validator halt" / "chain split" impact criteria. This mirrors precisely the impact class of the referenced report (permanent loss/inaccessibility of state tied to an identity after a remapping event), but here the state loss can propagate into a liveness-critical panic rather than just cosmetic metadata loss.

### Likelihood Explanation
Reaching this requires: (1) an attacker or ordinary user funds/uses a direct-cast Sei address (`bytes(evmAddr)`) and delegates stake or otherwise creates staking/distribution state under it before that EVM address is associated, and (2) a subsequent transaction (a normal EVM tx from that address, or an `AssociateTx`) triggers `AssociateAddresses`/`MigrateBalance`, which removes the now-"clean" account. Both actions are fully reachable by any public transaction sender — no privileged access is required. The team's own comment confirms this scenario has previously been identified as capable of halting the chain, which raises confidence that the underlying condition is real; however, I could not verify from the available index whether staking's `Delegate` message actually accepts a direct-cast (unassociated) address as delegator, or whether some other guard elsewhere prevents delegation from an unassociated direct-cast identity. That verification would require deeper tracing through `x/staking` message handling that is not covered by the current index.

### Recommendation
In `MigrateBalance` (or an equivalent pre-removal check within `AssociateAddresses`), before calling `accountKeeper.RemoveAccount(ctx, ...)` on the direct-cast address, verify not just `LockedCoins` but also the absence of staking delegations, unbonding delegations, and any distribution withdrawal-address/reward state tied to that address. If such state exists, either migrate it to the newly associated Sei address atomically, or refuse to remove the account (leave it in place) so that later hooks referencing the delegator address do not observe a missing account. Apply the same protection uniformly across every code path that calls `AssociateAddresses` (`AssociateTx` handling, implicit association in `EVMPreprocessDecorator.AnteHandle`, and the `associateAuthorizationAuthorities`/`associate` precompile paths), not just the EIP-7702 authorization path that was already patched.

### Proof of Concept
Conceptual reproduction (not independently executed against a live node, since this requires cross-module interaction with `x/staking`):
1. Compute the direct-cast Sei address for an EVM address that has not yet been associated: `castAddr = sdk.AccAddress(evmAddr[:])`.
2. Fund `castAddr` with `usei` and submit a `MsgDelegate` from `castAddr` to a validator (if the staking module accepts a signed message from this account without requiring prior EVM association — this step needs confirmation against `x/staking` message validation, which was not fully traced here).
3. From the corresponding EVM private key, submit any ordinary EVM transaction (or an `AssociateTx`) so that `EVMPreprocessDecorator.AnteHandle` executes the "not associated" branch and calls `associateHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)` [5](#0-4) .
4. Inside `MigrateBalance`, `LockedCoins(ctx, castAddr)` returns zero (delegated stake is not counted as "locked" bank balance), so `RemoveAccount(ctx, castAddr)` executes despite `castAddr` still being the delegator of record for an active delegation [6](#0-5) .
5. At the next point the staking/distribution modules process a hook against that delegator (e.g., validator removal, reward withdrawal, or slashing), the missing account can trigger a panic in the ABCI path, halting block production — the exact scenario the code's own comment warns about for the EIP-7702 case.

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}

// associateAuthorizationAuthorities associates every EIP-7702 authorization authority in
// the transaction with its true (pubkey-derived) Sei address, so that a subsequent
// SetCode for the authority does not create a mutable direct-cast mapping. It is
// best-effort: authorities with invalid signatures (which EVM execution would also skip)
// or that are already associated are left untouched, and an association failure skips
// only that authority rather than rejecting the transaction, which go-ethereum would
// still accept.
func (p *EVMPreprocessDecorator) associateAuthorizationAuthorities(ctx sdk.Context, msg *evmtypes.MsgEVMTransaction, associateHelper *helpers.AssociationHelper) {
	txData, err := evmtypes.UnpackTxData(msg.Data)
	if err != nil {
		return
	}
	setCodeTx, ok := txData.(*ethtx.SetCodeTx)
	if !ok {
		// Only SetCode (EIP-7702) transactions carry authorizations.
		return
	}
	ethTx := ethtypes.NewTx(setCodeTx.AsEthereumData())
	for _, auth := range ethTx.SetCodeAuthorizations() {
		// Only pre-associate authorities whose authorization the EVM will actually apply
		// (matching chain id, nonce, and account state). This prevents replaying a
		// publicly-visible authorization a user signed for another chain to force-associate
		// them, which the EVM would skip but which still recovers a valid authority.
		evmAddr, seiAddr, pubkey, ok := helpers.AuthorityToPreAssociate(ctx, p.evmKeeper, auth)
		if !ok {
			continue
		}
		cacheCtx, write := ctx.CacheContext()
		if err := associateHelper.AssociateAddresses(cacheCtx, seiAddr, evmAddr, pubkey, false); err == nil {
			write()
		}
	}
}
