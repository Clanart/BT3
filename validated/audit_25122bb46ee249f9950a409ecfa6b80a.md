### Title
Disassemble/assemble round-trip of an attacker-controlled `transfer_program`/`proofs_checker` in outer-puzzle drivers can smuggle divergent CLVM into a wallet's reconstructed puzzle - (`chia/wallet/nft_wallet/ownership_outer_puzzle.py`)

### Summary
The CVE describes a "deparse → later re-parse and execute" bug: PostgreSQL's `EXTRACT()` deparser can emit text that, when subsequently parsed and executed by another consumer (`pg_dump`, `\sf`), does not faithfully reproduce the original object and lets a hostile object owner inject SQL that runs with elevated privilege. Chia's `PuzzleInfo`/outer-puzzle driver framework has the same architecture: an untrusted CLVM sub-program (`transfer_program` for NFT ownership layers, `proofs_checker` for CR-CAT/VC layers) is *deparsed* with `disassemble()` into a plain string, stored in a `PuzzleInfo` dict that is serialized/transmitted as part of an `Offer`'s `driver_dict`, and later *re-parsed* with `assemble()` when the counterparty's wallet reconstructs the puzzle to build/verify a spend.

### Finding Description
`OwnershipOuterPuzzle.match()` extracts a `transfer_program` directly from an untrusted puzzle reveal (the NFT/DID owner controls its content) and, if it doesn't match a known driver, stores its textual deparse: [1](#0-0) 

This same pattern occurs for `proofs_checker` in the CR/VC outer puzzle driver: [2](#0-1) 

The resulting `PuzzleInfo` object is a thin wrapper whose values are plain strings; when a consumer later reads `constructor["transfer_program"]`, `decode_info_value()` re-parses the string with `clvm_tools.binutils.assemble()` back into a CLVM `Program`: [3](#0-2) 

`OwnershipOuterPuzzle.construct()` then uses that re-assembled `Program` verbatim to build the puzzle reveal that gets curried into the coin actually spent: [4](#0-3) 

This `PuzzleInfo`/`driver_dict` is exactly what a spend-bundle submitter controls end-to-end through the offer flow: `Offer.from_spend_bundle()` calls `match_puzzle()` on the untrusted `coin_spend.puzzle_reveal` supplied by the offer maker/taker, populating `driver_dict` with the disassembled `transfer_program` text: [5](#0-4) 

and that same `driver_dict` is fed back through `create_offer_for_ids` (including directly from the RPC request body) and used to reconstruct puzzles (`construct_puzzle`) when building the final spend bundle or announcements: [6](#0-5) [7](#0-6) 

The overall shape mirrors the CVE precisely: an "object owner" (NFT/DID/offer creator) supplies a hostile object definition (a crafted `transfer_program`/`proofs_checker` CLVM tree). It is deparsed to text by one trust domain and later re-parsed and *executed* by another trust domain (the counterparty's wallet, acting with its own signing/spend authority) without re-validating that the reconstructed CLVM is semantically identical to what was originally reviewed/matched. Any place where `disassemble()`'s text form and `assemble()`'s grammar do not agree on how to represent a given byte sequence (e.g., atoms colliding with `KEYWORD_TO_ATOM` operator names, numeric vs. quoted-string vs. hex-atom ambiguities in `type_for_atom`) becomes an injection point that lets the malicious party's structure execute as different CLVM than what was inspected/matched, all while riding on a signature/spend authorized by the innocent party's wallet.

### Impact Explanation
If the deparse/re-parse round trip is not byte-for-byte faithful for some crafted input, an NFT/DID/VC "object owner" acting as an offer counterparty could get a victim wallet to curry and execute a `transfer_program`/`proofs_checker` that differs from the one actually matched/displayed. Because this puzzle directly gates NFT/DID ownership transfer conditions and CR-CAT proof checking, a divergence could let the attacker bypass ownership/royalty checks or forge asset trust conditions inside a spend the victim's wallet signs — i.e., unauthorized coin/ownership movement or forged asset semantics, satisfying the "concrete unsigned or unauthorized coin movement" bar.

### Likelihood Explanation
The path is reachable purely through the offer protocol (`Offer.from_spend_bundle`/`create_offer_for_ids`), which any wallet user or RPC caller exercises when accepting or building an offer with a counterparty-controlled driver dict — no special privilege, node compromise, or network position is required.

### Recommendation
Do not trust the `disassemble()`/`assemble()` string round trip as a semantics-preserving transport for untrusted CLVM inside `PuzzleInfo`. Instead: (1) keep the original `Program` object (not its disassembled text) in `PuzzleInfo` for any sub-puzzle sourced from an untrusted puzzle reveal, only using text for known-safe cases; (2) after reconstructing a puzzle via `construct()`, re-verify its tree hash against the tree hash of the originally matched puzzle reveal before using it in a spend; (3) audit `clvm_tools.binutils.assemble`/`disassemble` and `type_for_atom` for lossless round-tripping of arbitrary atoms, especially ones colliding with keyword/operator names.

### Proof of Concept
1. Craft an NFT ownership-layer inner puzzle whose `transfer_program` is a CLVM tree containing an atom chosen so that `disassemble()` renders it ambiguously (e.g., an atom that collides with an entry in `KEYWORD_TO_ATOM`/`type_for_atom`'s int/quote/keyword classification).
2. Offer this NFT via `trade_manager.create_offer_for_ids` / the `create_offer_for_ids` RPC; `Offer.from_spend_bundle` (`chia/wallet/trading/offer.py:641`) calls `match_puzzle` → `OwnershipOuterPuzzle.match` → `disassemble(transfer_program)` (`chia/wallet/nft_wallet/ownership_outer_puzzle.py:48`), storing the text in `driver_dict`.
3. When the counterparty's wallet accepts the offer, it calls `construct_puzzle`/`OwnershipOuterPuzzle.construct` (`chia/wallet/nft_wallet/ownership_outer_puzzle.py:64-68`), which triggers `PuzzleInfo.__getitem__` → `decode_info_value` → `assemble(value)` (`chia/wallet/puzzle_drivers.py:138`) to rebuild the `Program`.
4. Compare the tree hash of the rebuilt `transfer_program` to the original; a mismatch demonstrates the injection point that lets the attacker's crafted definition execute as different CLVM than what was matched/reviewed by the victim's wallet.

def decode_info_value(cls: Any, value: dict[str, Any] | list[Any] | Program | str) -> Any:
    if isinstance(value, dict):
        return cls(value)
    elif isinstance(value, list):
        return [decode_info_value(cls, v) for v in value]
    elif isinstance(value, Program) and value.atom is None:
        return value
    else:
        if isinstance(value, str):
            if value in {"()", ""}:  # special case
                return Program.to([])
            if value.startswith("0x"):
                return hexstr_to_bytes(value)
            expression: SExp = assemble(value)
        else:
            expression = value
        if expression.atom is None:
            return Program(expression)

    @classmethod
    def from_spend_bundle(cls, bundle: WalletSpendBundle) -> Offer:
        # Because of the `to_spend_bundle` method, we need to parse the dummy CoinSpends as `requested_payments`
        requested_payments: dict[bytes32 | None, list[NotarizedPayment]] = {}
        driver_dict: dict[bytes32, PuzzleInfo] = {}
        leftover_coin_spends: list[CoinSpend] = []
        for coin_spend in bundle.coin_spends:
            driver = match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))
            if driver is not None:
                asset_id = create_asset_id(driver)
                assert asset_id is not None
                driver_dict[asset_id] = driver
            else:
                asset_id = None
            if coin_spend.coin.parent_coin_info == bytes32.zeros:
                notarized_payments: list[NotarizedPayment] = []
                for payment_group in Program.from_serialized(coin_spend.solution).as_iter():
                    nonce = bytes32(payment_group.first().as_atom())
                    payment_args_list = payment_group.rest().as_iter()
                    notarized_payments.extend(
                        [NotarizedPayment.from_condition_and_nonce(condition, nonce) for condition in payment_args_list]
                    )

                requested_payments[asset_id] = notarized_payments
            else:
                leftover_coin_spends.append(coin_spend)

        return cls(
            requested_payments, WalletSpendBundle(leftover_coin_spends, bundle.aggregated_signature), driver_dict
        )
