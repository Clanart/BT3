### Title
Payout-to-withdrawal join in `get_payout_txs_for_withdrawal_utxos` binds by UTXO bytes only, letting a duplicated `withdrawal_utxo` credit an unrelated deposit's payout - ([File: core/src/database/verifier.rs])

### Summary
`Database::get_payout_txs_for_withdrawal_utxos` joins the `withdrawals` table to `bitcoin_syncer_spent_utxos` purely on `withdrawal_utxo_txid`/`withdrawal_utxo_vout`, with no scoping by `move_to_vault_txid` or deposit identity. If two distinct withdrawal indices (backing two distinct deposits) end up with the same registered `withdrawal_utxo` bytes, a single real payout spending that UTXO is fanned out to both rows, and `update_payout_txs_and_payer_operator_xonly_pk` writes the same `payout_txid`/operator/blockhash onto both - crediting an operator for a deposit whose vault UTXO was never actually paid out.

### Finding Description
The binding that must hold is: for each `withdrawals.idx`, `payout_txid` set on that row must correspond to a Bitcoin transaction that actually pays out the withdrawal tied to that row's `move_to_vault_txid`. Concretely: `withdrawals[idx2].payout_txid` should be set only if the transaction spending `withdrawals[idx2].withdrawal_utxo` genuinely fronts the withdrawal for `withdrawals[idx2].move_to_vault_txid`.

The query that determines this binding is: [1](#0-0) 
which selects `w.idx, bsu.spending_txid` joined solely `ON bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout`, with no reference to `move_to_vault_txid` or any deposit identifier. The `withdrawals` table stores `withdrawal_utxo_txid`/`withdrawal_utxo_vout` with no uniqueness constraint across rows (only `idx` is primary key): [2](#0-1) 
and these columns are populated straight from Citrea sync data with no cross-index duplicate check: [3](#0-2) 

`Verifier::update_finalized_payouts` calls this join per finalized block, and for every `(idx, payout_txid)` pair returned it derives the operator xonly pk from the payout tx's OP_RETURN and unconditionally writes it via `update_payout_txs_and_payer_operator_xonly_pk`: [4](#0-3) 

If withdrawal idx2 (backing deposit B) is registered with `withdrawal_utxo_txid/vout` bytes identical to idx1's (backing deposit A) - achievable because Citrea's `withdraw()` call lets the caller supply arbitrary UTXO bytes with no on-chain existence/uniqueness check, and this repo performs no dedup either - then once the operator legitimately fronts A's withdrawal by spending that UTXO, `bitcoin_syncer_spent_utxos` records a single `(txid,vout)->spending_txid` entry that matches BOTH withdrawal rows in the join. Both idx1 and idx2 get the same `payout_txid`, `payout_payer_operator_xonly_pk`, and `payout_tx_blockhash` written to their rows.

Downstream, `get_payout_info_from_move_txid` and `is_kickoff_malicious` both key exclusively off `move_to_vault_txid`, not off any independent verification that the payout transaction's spent input actually belongs to that deposit's withdrawal request: [5](#0-4) [6](#0-5) 
So when `PayoutCheckerTask` later finds deposit B's `idx2` as "unhandled" via `get_first_unhandled_payout_by_operator_xonly_pk` and calls `handle_finalized_payout` for deposit B, and a kickoff is created and checked with `is_kickoff_malicious`, the malicious check re-reads the same corrupted `get_payout_info_from_move_txid(move_txid_B)` entry and finds it "consistent," failing to flag the kickoff as malicious. The bridge circuit's storage-proof check (`verify_storage_proofs` / `bridge_circuit`) compares only the withdrawal-UTXO bytes to the spent input of the payout transaction, which also passes because the attacker deliberately made those bytes identical to idx1's: [7](#0-6) 
None of the existing guards check that a distinct deposit's vault UTXO/move_to_vault_txid is uniquely and exclusively bound to the withdrawal_utxo that was actually spent.

### Impact Explanation
An operator can be credited with (and later claim reimbursement from) deposit B's move-to-vault UTXO despite never sending a payout transaction that fronts B's withdrawal - directly matching the Critical category "an operator reimbursed for a payout it never funded" / "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal." The blast radius is one attacker-controlled pair of withdrawal registrations per exploitation, but the underlying join defect is structural and would recur for any pair of withdrawal indices sharing duplicate UTXO bytes, across any deposits/operators.

### Likelihood Explanation
The attacker only needs the capabilities explicitly granted in this audit's threat model: ability to deposit and call `withdraw()` on the Citrea bridge contract with fully attacker-chosen UTXO bytes, twice, using identical bytes for two different withdrawal indices. No verifier/operator/aggregator privilege, key compromise, or majority hashrate is needed. The cost is limited to normal deposit/withdrawal fees; the DB-level join flaw fires automatically as part of normal `update_finalized_payouts` processing once the shared UTXO is spent by a legitimate payout.

### Recommendation
Scope `get_payout_txs_for_withdrawal_utxos` (and the update it feeds) per-deposit, not purely by UTXO bytes: add a uniqueness constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` in the `withdrawals` table (rejecting/erroring on duplicate registration for a different `idx`/`move_to_vault_txid`), and/or have the join carry through and verify `move_to_vault_txid` association so a single spent UTXO cannot satisfy two different deposits' payout bindings.

### Proof of Concept
Extend `core/src/database/verifier.rs`'s `update_get_payout_txs_from_citrea_withdrawal` test:
1. Insert deposit A (`idx=1`, `move_to_vault_txid = txid_A`) via `upsert_move_to_vault_txid_from_citrea_deposit`, and register its `withdrawal_utxo` = `UTXO_X` via `update_withdrawal_utxo_from_citrea_withdrawal`.
2. Insert deposit B (`idx=2`, `move_to_vault_txid = txid_B`, distinct from `txid_A`), and register its `withdrawal_utxo` = the SAME `UTXO_X` bytes.
3. Insert one `bitcoin_syncer_spent_utxos` row for `UTXO_X` spent by `spending_txid = payout_txid_real` (simulating a single real payout).
4. Call `get_payout_txs_for_withdrawal_utxos(block_id)` and assert it returns rows for BOTH `idx=1` and `idx=2` with the same `spending_txid`.
5. Call `update_payout_txs_and_payer_operator_xonly_pk` with both results and assert `get_payout_info_from_move_txid(txid_B)` now returns `Some` payout info equal to that of `txid_A`, proving deposit B is falsely marked as paid out - `assert_eq!(payout_info(txid_A).2, payout_info(txid_B).2)` (same `payout_txid`) despite `txid_A != txid_B` and no transaction ever having spent deposit B's actual withdrawal path independently.

        tx: Option<DatabaseTransaction<'_>>,

            execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

                Ok((
                    operator_xonly_pk.map(|pk| pk.0),
                    block_hash.0,
                    txid.0,
                    deposit_idx,
                ))
            })
            .transpose()
    }

                    "Payout tx not found in block cache: {:?} and in block: {:?}",

                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());
            let op_return_output = get_first_op_return_output(&circuit_payout_tx);

            // If OP_RETURN doesn't exist in any outputs, or the data in OP_RETURN is not a valid xonly_pubkey,
            // operator_xonly_pk will be set to None, and the corresponding column in DB set to NULL.
            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.
            let operator_xonly_pk = op_return_output
                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,
            ));

            .update_payout_txs_and_payer_operator_xonly_pk(

                payout_txs_and_payer_operator_idx,
