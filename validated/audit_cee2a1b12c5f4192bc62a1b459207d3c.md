Confirmed: `immediate_dependencies()`/`immediate_dependencies_iter()` walk `module_handles()` (excluding self), which is a distinct set from `friend_decls()` used by `immediate_friends()`/`immediate_friends_iter()`. These are two disjoint categories of external module references in the Move bytecode format.

### Title
Allowed-dependency check in `validate_publish_request` omits friend module declarations, allowing packages to reference unregistered/policy-violating dependencies via `friend` - ([File: aptos-move/aptos-vm/src/aptos_vm.rs])

### Summary
The Aptos publish-path invariant equivalent to "all excess/extra value must be accounted for" is: every external module reference declared in a to-be-published package's bytecode must be covered by the `allowed_deps` set computed from the package's declared `PackageMetadata.deps` in `code::check_dependencies` (Move) and enforced natively in `validate_publish_request` (Rust). Only `immediate_dependencies()` (regular `module_handles`) are checked against `allowed_deps`; `immediate_friends()` (bytecode `friend_decls`) are never checked, leaving that category of dependency unaccounted for — mirroring the original bug class where only part of the value/relationship is validated while the rest bypasses the invariant. [1](#0-0) [2](#0-1) 

### Finding Description
`code::publish_package` (Move) computes `allowed_deps` from the package's declared `PackageDep` list via `check_dependencies`, which walks each declared dependency's `upgrade_policy` and pushes `AllowedDep{account, module_name}` entries for every module in that dependency package. This vector is passed to the native `request_publish_with_allowed_deps`, and ultimately consumed by `validate_publish_request` in `aptos_vm.rs`, whose stated purpose is to "verify that bytecode dependencies are actually what is pretended here" (per the comment on `check_dependencies`). [3](#0-2) 

However, `validate_publish_request` only enumerates `m.immediate_dependencies()` when checking against `allowed_deps`:
```
if let Some(allowed) = &allowed_deps {
    for dep in m.immediate_dependencies() {
        ...
    }
}
``` [1](#0-0) 

`immediate_dependencies()` only iterates `module_handles()` (excluding self), a structurally separate pool from `friend_decls()`, which is what `immediate_friends()` reads:
```
fn immediate_dependencies(&self) -> Vec<ModuleId> {
    ... self.module_handles() ...
}
fn immediate_friends(&self) -> Vec<ModuleId> {
    self.friend_decls().iter()...
}
``` [2](#0-1) 

Interestingly, elsewhere in the VM (`charge_package_dependencies`), the code explicitly treats friends as a first-class dependency category requiring its own validation ("friends, when published, are limited to the same package"), confirming that friend declarations are recognized internally as a distinct, security-relevant reference class that must be constrained — yet this constraint is enforced only for gas-charging/self-package containment, not for the allowed-dependency (declared-metadata) check. [4](#0-3) 

Note: the `friend` compatibility check in `check_upgradability`/bytecode compatibility only concerns backward compatibility for existing published friend visibility, not the declared-dependency/policy-conformance check performed by `check_dependencies`.

I could not fully verify within the available context whether the Move bytecode verifier or an earlier deserialization stage independently rejects modules whose `friend_decls` point to modules not present in on-chain storage at all (which would make this an availability-only bypass rather than a false-metadata bypass) — this would require tracing the friend-linking checks in `move-bytecode-verifier/src/friends.rs`, which I was not able to read due to the iteration limit.

### Impact Explanation
If real, this would let a published module declare a `friend` relationship to a module belonging to a package with a stronger upgrade policy (e.g., `immutable`) or that was never listed in the publishing package's `PackageMetadata.deps`, without the native side detecting the mismatch. Since `PackageMetadata.deps` is what `code::check_dependencies` uses to enforce "a dependency cannot have a weaker upgrade policy" (`EDEP_WEAKER_POLICY`) and same-address restrictions for `arbitrary`-policy dependencies (`EDEP_ARBITRARY_NOT_SAME_ADDRESS`), an omitted friend-dependency check could let a package metadata under-declare its true dependency graph while still bytecode-referencing modules through `friend`, undermining the "committed module bytes must match declared metadata/dependencies" invariant that this Publish Impact Gate targets.

### Likelihood Explanation
Friend declarations in Move require the friended module to already exist and link at verification/loading time (module linking checks apply to both dependencies and friends in `move-bytecode-verifier`), so the practical exploitability hinges on whether friend-linking enforces the same allowed-dependency/policy semantics elsewhere. I was unable to confirm this within the current investigation, so likelihood is uncertain without confirming whether `move-bytecode-verifier::friends` or module loading independently re-derives and checks the policy relationship for friends the way `check_dependencies` does for the metadata-declared deps.

### Recommendation
Extend the `allowed_deps` check in `validate_publish_request` to also iterate `m.immediate_friends()` (or `immediate_friends_iter()`), just as `charge_package_dependencies` already treats friends and dependencies as parallel categories, so that friend module references are validated against the same `allowed_deps` set derived from `PackageMetadata.deps`.

### Proof of Concept
Could not be independently constructed/verified within the available tool budget. A full PoC would require: (1) building a package `P` whose `PackageMetadata.deps` omits a dependency package `D` with a weaker upgrade policy, (2) making one of `P`'s modules declare `D`'s module as a `public(friend)` reference rather than a regular `use`, and (3) confirming whether `code_dependency_check_enabled` publish path accepts this without the `EDEP_WEAKER_POLICY`/`unregistered dependency` error that would occur for a regular dependency. This last step is exactly what I was unable to verify given the remaining iteration budget, so this finding should be treated as an unconfirmed candidate requiring a live/e2e-test check before being reported as a confirmed vulnerability.

    /// compute the list of module dependencies which are allowed by the package metadata. The later
    /// is passed on to the native layer to verify that bytecode dependencies are actually what is pretended here.
    fun check_dependencies(publish_address: address, pack: &PackageMetadata): vector<AllowedDep>
    acquires PackageRegistry {
        let allowed_module_deps = vector::empty();
        let deps = &pack.deps;
        deps.for_each_ref(|dep| {
            let dep: &PackageDep = dep;
            assert!(exists<PackageRegistry>(dep.account), error::not_found(EPACKAGE_DEP_MISSING));
            if (is_policy_exempted_address(dep.account)) {
                // Allow all modules from this address, by using "" as a wildcard in the AllowedDep
                let account: address = dep.account;
                let module_name = string::utf8(b"");
                vector::push_back(&mut allowed_module_deps, AllowedDep { account, module_name });
            } else {
                let registry = borrow_global<PackageRegistry>(dep.account);
                let found = vector::any(&registry.packages, |dep_pack| {
                    let dep_pack: &PackageMetadata = dep_pack;
                    if (dep_pack.name == dep.package_name) {
                        // Check policy
                        assert!(
                            dep_pack.upgrade_policy.policy >= pack.upgrade_policy.policy,
                            error::invalid_argument(EDEP_WEAKER_POLICY)
                        );
                        if (dep_pack.upgrade_policy == upgrade_policy_arbitrary()) {
                            assert!(
                                dep.account == publish_address,
                                error::invalid_argument(EDEP_ARBITRARY_NOT_SAME_ADDRESS)
                            )
                        };
                        // Add allowed deps
                        let account = dep.account;
                        let k = 0;
                        let r = vector::length(&dep_pack.modules);
                        while (k < r) {
                            let module_name = vector::borrow(&dep_pack.modules, k).name;
                            vector::push_back(&mut allowed_module_deps, AllowedDep { account, module_name });
                            k += 1;
                        };
                        true
                    } else {
                        false
                    }
                });
                assert!(found, error::not_found(EPACKAGE_DEP_MISSING));
            };
        });
        allowed_module_deps
    }
