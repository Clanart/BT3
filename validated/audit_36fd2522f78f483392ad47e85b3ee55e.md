### Title
Sandwichable zero-slippage AMM swap in `SmartWomConvert` conversion path - ([File: wombat/SmartWomConvert.sol])

### Summary
`SmartWomConvert` exposes permissionless conversion entry points (`convert`, `convertFor`, `smartConvert`) that internally route a portion of the deposited WOM through the `womMWomPool` AMM via `IWombatRouter.swapExactTokensForTokens` with a hardcoded minimum-output of `0`, relying only on a coarse aggregate check afterward. This mirrors the reported `BuyAndBurn.swap()` pattern where a permissionlessly-triggerable AMM swap with no real slippage protection can be sandwiched to extract value from the shared pool.

### Finding Description
`SmartWomConvert._convertFor()` computes a `buybackAmount` of WOM to be swapped for mWOM through the `womMWomPool`, and executes the swap with an explicit `0` minimum-received parameter: [1](#0-0) 

The only downstream protection is an aggregate check comparing the *total* obtained amount (`convertAmount + amountRec`, where `convertAmount` is minted 1:1 via `IMWom(mWom).deposit`) against `_minRec`: [2](#0-1) 

For the permissionless `smartConvert()` entry point — documented as the path meant to be used "upon sending wom" and callable by any account, including `WombatStaking` on behalf of the protocol — `_minRec` is hardcoded to the full `_amountIn`, and the split between "swap via pool" vs. "mint 1:1" is itself derived from a spot-price read (`currentRatio()`) taken from the same `womMWomPool`: [3](#0-2) [4](#0-3) 

Because both the *decision* (`currentRatio`, `maxSwapAmount`) and the *execution* (`swapExactTokensForTokens` with `minAmountOut = 0`) read/act on the same manipulable pool reserves within a single transaction, an attacker can:
1. Trade against `womMWomPool` beforehand (in the same transaction) to temporarily skew the mWOM/WOM price.
2. Call `smartConvert()`/`convert()` so the buyback swap executes at the manipulated price with no per-swap slippage floor.
3. Reverse the initial trade in the same transaction, extracting value from `womMWomPool` liquidity while the aggregate `_minRec` check (bounded loosely by the input amount, or fully attacker-controlled via `convert()`'s `_minRec` parameter) does not prevent the manipulation from being profitable.

This is structurally the same bug class as the reported `BuyAndBurn.swap()` issue: a swap against an AMM pool, triggerable within an attacker-controlled transaction, guarded only by an aggregate/absent slippage check rather than a true per-swap minimum-output tied to trusted pricing.

### Impact Explanation
Exploiting this allows extraction of value from the `womMWomPool` liquidity that backs the mWOM peg/minting mechanism, at the expense of other mWOM holders and the protocol's reserve backing. Repeated sandwiching degrades the WOM/mWOM peg and drains pool liquidity that other users rely on for fair conversion pricing, constituting a value-extraction / fund-drain vector against protocol/user reserves rather than a purely self-inflicted slippage loss.

### Likelihood Explanation
The functions (`convert`, `convertFor`, `smartConvert`) are `external` with no access control, so any unprivileged wallet can construct the sandwich in a single atomic transaction. The `0`-value minimum-output parameter on the internal `swapExactTokensForTokens` call means there is no protocol-level circuit breaker against an unfavorable/manipulated execution price for that leg of the trade, only reliance on an aggregate check that is either attacker-supplied (`convert`/`convertFor`) or loosely bounded (`smartConvert`).

### Recommendation
Pass a properly computed, TWAP- or oracle-anchored minimum output (not `0`) directly into the `IWombatRouter.swapExactTokensForTokens` call in `_convertFor`, rather than deferring all slippage protection to the post-hoc aggregate `_minRec` comparison. Additionally, avoid deriving both the swap-size decision and the execution price from the same single-block spot read of `womMWomPool` (`currentRatio`/`maxSwapAmount`), e.g. by requiring a minimum time-weighted price or capping the deviation permitted within one transaction.

### Proof of Concept
1. Attacker flash-manipulates `womMWomPool` reserves by swapping a large amount of mWOM for WOM (or vice versa), pushing `currentRatio()` favorably.
2. In the same transaction, attacker calls `SmartWomConvert.convert(_amountIn, _convertRatio, _minRec, _mode)` (or `smartConvert`), causing `_convertFor` to execute `IWombatRouter.swapExactTokensForTokens(..., 0, ...)` against the now-skewed pool, yielding more mWOM than a fair price would allow.
3. Attacker reverses the initial pool manipulation trade, restoring reserves and pocketing the mWOM/WOM price difference extracted from the pool's liquidity, all within one atomic transaction.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
