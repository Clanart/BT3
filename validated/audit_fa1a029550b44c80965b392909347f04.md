### Title
Tokenfactory denom `AllowList` membership restriction is enforced only in `bank.MsgSend`/`MsgMultiSend`, not in the underlying `SendCoins`/mint paths, allowing bypass via precompiles and module actions - ([File: sei-cosmos/x/bank/keeper/send.go])

### Summary
The tokenfactory module lets a denom admin restrict token membership to only an explicit list of addresses via `MsgUpdateDenom`'s `AllowList` (analogous to Liferay's "limit membership to members of parent site" option). This restriction is checked with `IsInDenomAllowList` [1](#0-0)  but that check is wired in **only** at the Cosmos `MsgSend`/`MsgMultiSend` handlers [2](#0-1) [3](#0-2) , and is absent from the `BaseSendKeeper.SendCoins`/`InputOutputCoins`/mint-and-transfer primitives that other modules and EVM precompiles call directly. This is the same bug class as CVE-2024-25149: an access-control "membership" restriction set on a resource (child site / restricted denom) is not propagated to every code path that can add a member (grant site access / receive the restricted token).

### Finding Description
`IsInDenomAllowList` explicitly documents that it is the sole gate for tokenfactory `factory/...` denom transfers [4](#0-3) , and it is invoked from `msgServer.Send`/`msgServer.MultiSend` before calling `SendCoins`/`InputOutputCoins` [2](#0-1) . Nothing inside `SendKeeper.SendCoins`, `InputOutputCoins`, or `SendCoinsFromModuleToAccount` itself enforces the allow list — the interface only exposes `IsInDenomAllowList` as a helper for callers to opt into [5](#0-4) .

Multiple reachable code paths call the bank keeper's lower-level primitives directly, bypassing this check entirely:

1. **Solo/Claim precompile** — `Claim`/`ClaimSpecific` call `p.bankKeeper.SendCoins(...)` directly to move an arbitrary caller-controlled `sender`'s entire balance (including any restricted tokenfactory denom) to `caller`, with no `IsInDenomAllowList` check [6](#0-5) [7](#0-6) . If a denom admin sets an `AllowList` intending only certain addresses to ever hold/receive the token, an address that signs a valid claim tx targeting an EVM address outside the allow list can still receive the denom through this precompile path.
2. **Tokenfactory Mint/Burn** — `msgServer.Mint`/`Burn` route through `mintTo`/`burnFrom` in `x/tokenfactory/keeper/bankactions.go`, which use `MintCoins`/`SendCoinsFromModuleToAccount`/`BurnCoins`, none of which consult `IsInDenomAllowList`. An admin (or anyone with an authz grant for `MsgMint`, as shown in the module's own integration test [8](#0-7) ) can mint the restricted denom straight into any account's balance, defeating the purpose of the `AllowList` before any `MsgSend`/`MsgMultiSend` check is ever reached.
3. Legacy EVM bank-precompile versions (`v600`, `v601`, `v67`) called `p.bankKeeper.SendCoins` directly for ERC20-native-pointer transfers [9](#0-8) , bypassing the allow list the same way, before being fixed in newer legacy revisions to route through `p.bankMsgServer.Send` [10](#0-9) . The current head-of-branch `precompiles/bank/bank.go` correctly proxies through `bankMsgServer.Send`, so that specific vector is already fixed in the current head, but the underlying root cause (the check living only in the message-server layer instead of the keeper layer) remains.

### Impact Explanation
The tokenfactory `AllowList` is documented as the mechanism enforcing "membership" restrictions on holding/transferring a permissioned denom [11](#0-10) . Because the restriction check lives in the message-server layer rather than in the shared keeper primitives, any caller that reaches `SendCoins`/mint paths without going through `bank.MsgSend`/`MsgMultiSend` can move or create the restricted denom into or out of accounts that were never granted "membership," directly undermining an authorization decision the denom admin made. This matches the CWE-863 (Incorrect Authorization) bug class of the referenced advisory: a permission/membership restriction on a "parent" resource (the denom's `AllowList`) is not enforced by "child" operations (mint, precompile-driven transfers) that can still add or move membership.

### Likelihood Explanation
Reaching the `solo` precompile's `Claim`/`ClaimSpecific` requires only a valid signed Cosmos claim transaction from any account holding balance of the restricted denom, callable by any EVM user — a low-privilege, publicly reachable path. Reaching the mint bypass requires tokenfactory admin privileges (or an authz grant of `MsgMint`), which is a normal, permissionless capability of any denom creator over their own denom.

### Recommendation
Move the `IsInDenomAllowList` enforcement out of the `bank` message-server handlers and into the shared `SendKeeper.SendCoins`/`InputOutputCoins`/`SendCoinsFromModuleToAccount`/`MintCoins` primitives (or add an explicit hook invoked by all of them), so that every code path that can change token custody for an allow-listed tokenfactory denom — including EVM precompiles, tokenfactory mint/burn, and any future module code — is subject to the same membership check, rather than relying on each caller to remember to invoke `IsInDenomAllowList` itself.

### Proof of Concept
1. Denom admin creates `factory/{admin}/restricted` and sets `AllowList{Addresses: [admin, allowedUser]}` via `MsgUpdateDenom` [11](#0-10) .
2. Admin mints the restricted denom directly to `notAllowedUser` via `MsgMint`; this succeeds because `mintTo` never calls `IsInDenomAllowList` [12](#0-11) , even though a direct `MsgSend` to `notAllowedUser` would be rejected with "not allowed to receive funds" per the module's own test [13](#0-12) .
3. Separately, `notAllowedUser` (or any account) can call the `solo` precompile's `claim`/`claimSpecific` methods with a valid claim tx to pull the restricted-denom balance of a claimer account into an EVM-associated address of their choosing, again with no allow-list check performed by `bankKeeper.SendCoins` [6](#0-5) .

**Uncertainty note:** I was not able to fully trace every module (e.g., IBC transfer keeper, distribution/rewards) that might call `SendCoins`/`InputOutputCoins` directly on tokenfactory denoms to confirm whether additional bypasses exist beyond mint/burn and the solo precompile; the `giga/` FlatKV implementation of the same allow-list logic in `giga/deps/xbank/keeper/send.go` was excluded from analysis per scope rules.

func (k BaseSendKeeper) GetDenomAllowList(ctx sdk.Context, denom string) types.AllowList {
	store := ctx.KVStore(k.storeKey)
	store = prefix.NewStore(store, types.DenomAllowListKey(denom))

	bz := store.Get([]byte(denom))
	if bz == nil {
		return types.AllowList{}
	}

	var allowList types.AllowList
	k.cdc.MustUnmarshal(bz, &allowList)

	return allowList
}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

func (p PrecompileExecutor) send(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, value *big.Int, readOnly bool) ([]byte, error) {
	if readOnly {
		return nil, errors.New("cannot call send from staticcall")
	}
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, err
	}
	denom := args[2].(string)
	if denom == "" {
		return nil, errors.New("invalid denom")
	}
	pointer, _, exists := p.evmKeeper.GetERC20NativePointer(ctx, denom)
	if !exists || pointer.Cmp(caller) != 0 {
		return nil, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())
	}
	amount := args[3].(*big.Int)
	if amount.Cmp(utils.Big0) == 0 {
		// short circuit
		return method.Outputs.Pack(true)
	}
	senderSeiAddr, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		return nil, err
	}
	receiverSeiAddr, err := p.accAddressFromArg(ctx, args[1])
	if err != nil {
		return nil, err
	}

	if err := p.bankKeeper.SendCoins(ctx, senderSeiAddr, receiverSeiAddr, sdk.NewCoins(sdk.NewCoin(denom, sdk.NewIntFromBigInt(amount)))); err != nil {
		return nil, err
	}

	return method.Outputs.Pack(true)
}

		return nil, 0, err

		// short circuit

	if err != nil {
		return nil, 0, err

	if err != nil {
		return nil, 0, err

		ToAddress:   receiverSeiAddr.String(),

func (server msgServer) Mint(goCtx context.Context, msg *types.MsgMint) (*types.MsgMintResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	// pay some extra gas cost to give a better error here.
	_, denomExists := server.bankKeeper.GetDenomMetaData(ctx, msg.Amount.Denom)
	if !denomExists {
		return nil, types.ErrDenomDoesNotExist.Wrapf("denom: %s", msg.Amount.Denom)
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Amount.GetDenom())
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	err = server.mintTo(ctx, msg.Amount, msg.Sender)
	if err != nil {
		return nil, err
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgMint,
			sdk.NewAttribute(types.AttributeMintToAddress, msg.Sender),
			sdk.NewAttribute(types.AttributeAmount, msg.Amount.String()),
		),
	})

	return &types.MsgMintResponse{}, nil
}
