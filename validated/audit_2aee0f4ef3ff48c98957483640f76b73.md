### Title
Path traversal via unsanitized `CommittedFileChange.path`/`WorkingDirectoryFileChange.path` used in file-menu actions (Reveal in Finder / Open with Default Program / Copy Path) - (File: `app/src/lib/git/log.ts`, `app/src/lib/app-shell.ts`, `app/src/ui/history/selected-commits.tsx`, `app/src/ui/changes/filter-changes-list.tsx`, `app/src/ui/open-pull-request/pull-request-files-changed.tsx`)

### Summary
`parseRawLogWithNumstat` takes the raw path string emitted by `git log --raw --numstat -z` and stores it verbatim into `CommittedFileChange.path` with no normalization or containment check. [1](#0-0) 
Several UI actions then build a filesystem path by naively joining this untrusted value with `repository.path` using `Path.join`, e.g. `revealInFileManager` in `app-shell.ts`, `onOpenItem` in `selected-commits.tsx`, and the context menus in `filter-changes-list.tsx` / `pull-request-files-changed.tsx`. [2](#0-1) [3](#0-2) [4](#0-3) 

None of these call sites use the app's own containment helper, `resolveWithin`, which is defined precisely to reject/neutralize `..` traversal and is already used elsewhere in the codebase (e.g. the deep-link file handler in `dispatcher.ts` calls `resolveWithin(repository.path, filepath)` and rejects the result if it escapes the repo root). [5](#0-4) [6](#0-5) 

### Finding Description
`git log --raw --numstat -z` prints each changed tree entry's name as returned by git's tree-diff machinery. `parseRawLogWithNumstat` reads that string directly off the line following the `:mode mode sha sha status` marker and puts it into `new CommittedFileChange(path, ...)` with no `Path.normalize`, no rejection of `..` segments, and no check that the result stays inside the repository. [7](#0-6) 
That `path` value then flows, unaltered, into UI components (`SelectedCommits`, `FilterChangesList`, `PullRequestFilesChanged`) that call `Path.join(repository.path, file.path)` for "Reveal in Finder/Explorer", "Open with Default Program", "Open in External Editor", and "Copy File Path" actions. [8](#0-7) [9](#0-8) 

Note the important caveat, which I was not able to fully verify from within this codebase because it depends on Git core (not GitHub Desktop) behavior: whether a crafted tree object containing a component literally named `..` (built via `git hash-object`/`git mktree` without `--strict`) actually survives an ordinary `git fetch`/`git clone` performed by the victim, and whether `git log --raw` (a tree-diff, not a checkout operation) will print that name unchanged. This is a property of Git's `diff-tree`/`unpack-trees`/`fsck` internals (e.g. `verify_path()` in Git's `read-cache.c`, and the fact that `fetch.fsckObjects`/`transfer.fsckObjects` default to `false` on the client), none of which live in this repository, so I cannot confirm from the GitHub Desktop source alone that such a tree object would successfully reach `parseRawLogWithNumstat` in a real clone from a malicious remote. What I *can* confirm from the Desktop source is that `parseRawLogWithNumstat` performs no sanitization of whatever string `git log` hands it, and downstream consumers perform no containment check either — GitHub Desktop provides zero defense-in-depth here, in contrast to the deep-link handler, which explicitly guards against exactly this class of traversal with `resolveWithin`.

### Impact Explanation
If a malicious path did reach `CommittedFileChange.path` (or the working-directory equivalent, `WorkingDirectoryFileChange.path`, which flows through the same `Path.join(repository.path, file.path)` pattern), the consequence would be limited to what the affected context-menu actions do: reveal an arbitrary host file/folder in Explorer/Finder, open an arbitrary file with the OS default handler (subject only to a Windows-only extension blocklist, `RestrictedFileExtensions`), or copy an arbitrary absolute path to the clipboard. [10](#0-9) 
This is a read/reveal/open primitive, not a direct arbitrary-write primitive — I found no evidence that this same unsanitized `file.path` is used as a target for `checkout -- <path>` / `git apply` / `git reset` writes (those flows were not fully traced in this session), so the "diff-apply" write-corruption scenario in the question is speculative rather than confirmed. On its own, "reveal/open a host file whose path is fully attacker-chosen" is a meaningful but bounded impact (information disclosure / user-confused-into-opening-a-file-outside-repo), contingent entirely on the unverified precondition that Git will actually deliver a `..`-containing path through `git log --raw` on the victim's machine.

### Likelihood Explanation
Low-to-uncertain. The precondition — Git accepting and faithfully round-tripping a tree entry component literally named `..` through an ordinary fetch/clone and then printing it via `git log --raw --numstat` without any normalization — is a Git-core behavior that I could not verify from this repository's code, and Git has historically hardened several related path-confusion classes (`.git` case-folding, `.gitmodules` handling, etc.) at the checkout/fsck layer. Whether the same protections apply to a pure `log --raw` tree-diff (which never touches the working tree or the index) is exactly the open question above.

### Recommendation
Regardless of whether the Git-level precondition holds, GitHub Desktop should not rely on Git to guarantee well-formed relative paths for values it turns into filesystem operations. Route every `Path.join(repository.path, file.path)` call site (`app-shell.ts:revealInFileManager`, `selected-commits.tsx:onOpenItem`/`onContextMenu`, `filter-changes-list.tsx`, `pull-request-files-changed.tsx`, `sidebar.tsx:onOpenItem`, `unmerged-file.tsx`, `copilot-conflicts-dialog.tsx`) through the existing `resolveWithin` helper (as already done in `dispatcher.ts`'s deep-link handler) and reject/abort the action if the resolved path escapes `repository.path`. Additionally, consider having `parseRawLogWithNumstat` reject or flag any path containing `..` path segments defensively, since that is the cheapest and most central place to close off this entire class regardless of Git's own guarantees.

### Proof of Concept
Not independently verified end-to-end in this session. The proof idea from the question (craft a tree via `git hash-object`/`git mktree` with an entry name containing `../`, commit it, run `getChangedFiles`) would need to be executed with an actual Git binary to determine (a) whether `git mktree`/`git commit-tree` accept the entry, (b) whether a subsequent `git fetch`/`clone` from that repository preserves the entry, and (c) whether `git log --raw --numstat` on the clone prints the unsanitized name — none of which can be confirmed by static code inspection of the GitHub Desktop TypeScript source alone. What is confirmed by inspection is that `parseRawLogWithNumstat` performs no validation of the returned string, and no downstream consumer of `CommittedFileChange.path`/`WorkingDirectoryFileChange.path` applies `resolveWithin` before using it in filesystem operations.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
