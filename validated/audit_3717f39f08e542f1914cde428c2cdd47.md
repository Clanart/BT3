### Title
Attacker-controlled threshold parameters cause quadratic Lagrange interpolation during `ThresholdKeys::read` - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` accepts serialized `t`, `n`, and participant index values, then reads `n` verification shares before calling `ThresholdKeys::new`. [1](#0-0) [2](#0-1)  When Lagrange interpolation is selected, `ThresholdKeys::new` calculates one interpolation factor for each of the first `t` participants. [3](#0-2)  Each factor iterates over the complete `t`-participant list, making key deserialization quadratic in `t`. [4](#0-3) [5](#0-4) 

### Finding Description
The serialized format permits `t = n = i = 65,535`: `Participant` only rejects zero, while `ThresholdParams::new` only enforces nonzero parameters, `t <= n`, and `i <= n`. [6](#0-5) [7](#0-6)  After reading the Lagrange selector, the secret share, and all `n` group elements, `ThresholdKeys::read` invokes `ThresholdKeys::new`. [8](#0-7) [9](#0-8) 

`ThresholdKeys::new` then performs `t` separate Lagrange-factor calculations, each scanning `t - 1` participants. [3](#0-2) [10](#0-9)  At the maximum encoded parameters, this requires approximately 4.29 billion field multiplications, 65,535 field inversions, and 65,535 scalar-point multiplications from an input of roughly 2 MiB. [11](#0-10) [3](#0-2) 

### Impact Explanation
An attacker who can supply serialized threshold-key bytes to `ThresholdKeys::read` can consume disproportionate CPU resources with a small canonical input. In a service that deserializes these objects from messages, uploaded state, peer data, or recovered configuration supplied by an untrusted party, this can stall the executing thread and create a denial-of-service condition.

### Likelihood Explanation
No malformed points, duplicate participants, signatures, or secret knowledge are required. The attacker only needs to provide enough canonical scalar and group encodings to satisfy the declared `n`; arbitrary valid points, including repeated generator encodings, are sufficient to reach the quadratic computation. [12](#0-11) [2](#0-1) 

### Recommendation
Enforce a protocol-appropriate maximum `n`/`t` before allocating vectors or invoking `ThresholdKeys::new`. Additionally, replace the per-participant recomputation of Lagrange factors with an algorithm that shares work across evaluations, or compute the group key through a bounded multiexponentiation/precomputation strategy. The limit should be enforced in `ThresholdKeys::read`, not left solely to callers.

### Proof of Concept
The following constructs canonical serialized keys which reach the worst-case interpolation path:

```rust
use std::io::Read;

use ciphersuite::{
  group::{ff::PrimeField, GroupEncoding},
  Ciphersuite,
};
use dkg::ThresholdKeys;

fn quadratic_threshold_keys<C: Ciphersuite>() -> Vec<u8> {
  let max = u16::MAX;
  let mut bytes = Vec::new();

  // Curve identifier.
  bytes.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
  bytes.extend(C::ID);

  // t = n = i = 65,535.
  bytes.extend(max.to_le_bytes());
  bytes.extend(max.to_le_bytes());
  bytes.extend(max.to_le_bytes());

  // Interpolation::Lagrange.
  bytes.push(1);

  // Arbitrary canonical secret share.
  bytes.extend(C::F::ONE.to_repr().as_ref());

  // n canonical verification shares. Repeated generator encodings are sufficient.
  let generator = C::generator().to_bytes();
  for _ in 0 .. max {
    bytes.extend(generator.as_ref());
  }

  bytes
}

fn trigger<C: Ciphersuite>() {
  let bytes = quadratic_threshold_keys::<C>();
  let _ = ThresholdKeys::<C>::read(&mut bytes.as_slice());
}
```

The encoded `u16` parameters select `t = n = 65,535`, after which the read path consumes `n` points and enters the quadratic group-key calculation. [13](#0-12) [2](#0-1)
