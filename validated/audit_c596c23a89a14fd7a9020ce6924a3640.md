### Title
Attacker-controlled `WWW-Authenticate` header spoofs a GitHub Enterprise host and triggers OAuth sign-in / token exfiltration to the attacker's server - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
When Git needs credentials for an HTTPS remote, GitHub Desktop's credential-helper trampoline decides whether the remote is a GitHub host by inspecting the `WWW-Authenticate` header Git captured from the server's `401` response. If the header contains the literal string `realm="GitHub"`, the endpoint is unconditionally classified as `'enterprise'` — with no verification that the host is actually a GitHub Enterprise instance. This classification then drives an Enterprise sign-in popup bound to the attacker's origin, and any resulting account/token gets persisted in `AccountsStore`, keyed by that attacker-controlled origin. On subsequent requests to the same origin, Desktop's credential lookup matches purely on origin and will hand the stored token back to Git for that host automatically.

### Finding Description
In `getEndpointKind()`: [1](#0-0) 

the code trusts a header value entirely controlled by the remote server (or a MITM/malicious proxy in the git transport path) to decide the endpoint "kind" as `'enterprise'`, bypassing the `isGitHubHost()` network check that is otherwise used as the fallback: [2](#0-1) 

Because `endpointKind !== 'generic'` and no existing account matches this new `apiEndpoint`, `getCredential()` calls `ui.promptForGitHubSignIn(endpoint)`: [3](#0-2) 

`promptForGitHubSignIn` derives `hostname`/`origin` directly from the attacker-supplied `endpoint` string and, for any non-`github.com` hostname, starts the Enterprise sign-in flow bound to that attacker origin: [4](#0-3) 

Once the user completes sign-in (e.g. supplying a Personal Access Token, believing they are authenticating to what looks like a legitimate corporate/GHE host), the resulting `Account` is persisted via `AccountsStore.addAccount()`, keyed by `getKeyForAccount(account)`/`account.endpoint`: [5](#0-4) 

On any subsequent credential request for the same origin, `findGitHubTrampolineAccount()` matches purely by URL origin and unconditionally returns the stored token: [6](#0-5) [7](#0-6) 

The broken invariant is: the credential helper equates "server claims realm=GitHub in an HTTP header" with "server is a trustworthy GitHub/GHE host," and then persists and auto-releases credentials to that host based solely on that unauthenticated claim.

### Impact Explanation
This matches the report's core primitive — an unprivileged, attacker-controlled input (here, an HTTP response header from a git remote/proxy the victim is fetching from or pushing to) is trusted without validation, and that trust is later used to leak/misdirect a resource that should have gone elsewhere (in the original report, reward tokens; here, the user's GitHub token/credentials). Concretely:
- The user's PAT or OAuth-derived token, entered believing they're authenticating to a legitimate GHE server, is stored keyed to the attacker's origin.
- Any future automated credential fill for that origin (background fetches, `git push`, CI-like automation via Desktop) will silently hand the token to the attacker's server (`credWithAccount` sets `password` = `a.token`), i.e. token exfiltration.
- This also constitutes unauthorized "account binding" of a real GitHub account to an attacker-designated endpoint, which downstream code (avatar authenticated-image-filter, credential helper, API calls) may treat as trusted.

### Likelihood Explanation
The trigger requires only that the victim clone or add a remote pointing at, or be redirected/proxied through, a server the attacker controls (or a MITM position on an HTTP-only/plain remote), and that the server return a `401` with a crafted `WWW-Authenticate: realm="GitHub"` header — a single, low-effort HTTP response the attacker fully controls. No admin rights, local access, or prior compromise of the victim's machine is needed; the only "unnatural" user step is confirming a sign-in dialog, which is the same normal flow used for legitimate GHE first-time sign-in, making it plausible for a user to complete unknowingly.

### Recommendation
Do not classify a host as `'enterprise'` (i.e., a trusted GitHub host warranting the sign-in flow) based solely on a client-supplied `WWW-Authenticate` header string. Require an authenticated/verified check (e.g., the existing `isGitHubHost()` API probe against a known GitHub API path/response, or certificate/well-known endpoint pinning) before triggering `promptForGitHubSignIn`, and additionally warn the user with the actual origin they are about to authenticate against, mirroring the validation already performed by `setEndpoint()` for manual Enterprise sign-in.

### Proof of Concept
1. Attacker stands up an HTTPS git server (or a MITM/plain-HTTP proxy) at `https://evil.example.com/some/repo.git`.
2. Victim adds this as a remote (or clones it) in GitHub Desktop and performs a fetch/push.
3. Git requests credentials; the server responds `401` with header `WWW-Authenticate: Basic realm="GitHub"`.
4. `getEndpointKind()` sees `wwwauth[...]` containing `realm="GitHub"` and returns `'enterprise'` without any real verification: [8](#0-7) 
5. `getCredential()` finds no existing account for `evil.example.com` and calls `ui.promptForGitHubSignIn('https://evil.example.com')`, which opens the Enterprise sign-in dialog bound to that origin: [9](#0-8) 
6. The victim enters a PAT (or completes OAuth), the account is stored keyed by `evil.example.com`.
7. On the next fetch/push to the same origin, `findGitHubTrampolineAccount` matches by origin and Desktop automatically sends the stored token to `evil.example.com`, exfiltrating it to the attacker.

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })

          new Error(
            `GitHub Desktop was unable to store the account token in the keychain. Please check you have unlocked access to the 'login' keychain.`
          )
        )
      } else {
        this.emitError(e)
      }
      return null
    }

    const accountsByEndpoint = this.accounts.reduce(
      (map, x) => map.set(x.endpoint, x),
      new Map<string, Account>()
    )
    accountsByEndpoint.set(account.endpoint, account)

    this.accounts = sortAccounts([...accountsByEndpoint.values()])

    this.save()
    return account
  }

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
