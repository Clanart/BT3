### Title
GitHub Desktop silently rewrites a repository's git remote URL based on an untrusted GitHub API `clone_url` value - (`File: app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` treats the GitHub API repository object (`IAPIRepository.clone_url`) as an implicit "oracle" for what the local git remote URL should be, and will automatically rewrite the user's `origin` (or default) remote to whatever the API reports, without any user confirmation, as long as a loose heuristic (protocol match + remote "hasn't been manually changed") is satisfied. [1](#0-0) 

### Finding Description
`updateRemoteUrl(gitStore, gitHubRepository, apiRepo)` compares the currently configured remote URL to `apiRepo.clone_url` (a value returned by a GitHub host — github.com, GitHub Enterprise, or any endpoint the user has signed into) and, if the protocols match and the current remote still matches the previously cached `gitHubRepository.cloneURL`, it silently calls `gitStore.setRemoteURL(...)` to overwrite the remote with the new API-provided URL: [2](#0-1) 

This mirrors the Oracle bug pattern exactly: a single external, mutable data source (`Oracle.setExternalOracle` there, the GitHub API repository object here) is trusted to define a security-relevant target (settlement price there, the git remote destination here) with **no locking mechanism** once the "battle" (repository) already exists. The check only guards against the *local* remote having been manually edited — it does **not** validate that the new `clone_url` still points to the same repository identity (owner/name/host) that the user originally added. `urlMatchesRemote` is only used to detect whether an update is *needed*, not to bound what the new URL is allowed to be: [3](#0-2) 

The actual remote-URL write path (`git remote set-url`) executes unconditionally on this signal: [4](#0-3) [5](#0-4) 

Because a GitHub Enterprise endpoint (attacker-operated or compromised GHE instance, or a MITM'd/compromised API response for a repository the user tracks) is a fully attacker-controlled "GitHub API object" per the valid-impact criteria, this lets that party redirect the trusted remote to an attacker-controlled git host during Desktop's normal background repository refresh, with no explicit re-confirmation UI shown to the user (contrast with the manual "Remote path can be edited" flow in Repository Settings, which does prompt/save explicitly): [6](#0-5) 

### Impact Explanation
Once the remote is silently repointed, subsequent user-initiated `git push`/`git fetch`/`git pull` operations transparently go to the attacker's git host instead of the real one. Combined with the credential trampoline, which resolves credentials by matching endpoint hostnames, a redirected remote can also cause Desktop to hand credentials to (or fetch/authenticate against) a different, attacker-chosen host, and can silently corrupt what gets pushed/fetched without the user noticing, since the UI reflects the rewritten remote as "current."

### Likelihood Explanation
The rewrite only fires under specific preconditions (protocol match, and the remote still equal to the last known-good `cloneURL`), which limits — but does not eliminate — the attack surface: it requires the local remote not to have been manually edited away from the API-reported clone URL, a common baseline state for most repositories. Given the check is entirely based on trusting the API-returned `clone_url` string, and this refresh runs automatically as part of the background repository refresh cycle (not gated by any explicit user prompt), the likelihood is meaningful for anyone using GitHub Enterprise or any environment where the API response can be manipulated.

### Recommendation
Do not silently rewrite a remote URL from a background API refresh. At minimum:
- Validate that the new `clone_url`'s host/owner/name identity is unchanged from what the repository was originally added with (or require it to at least resolve to the exact same `GitHubRepository.dbID`/API `id`, not just string URL matching).
- Require explicit user confirmation before changing an existing remote URL (mirroring the manual flow in `repository-settings.tsx`), especially when the change affects the hostname component of the URL.
- Treat GitHub Enterprise / non-dotcom API responses with the same "lock after creation" principle recommended in the original report: once a repository's remote has been established, changing the trusted remote host should require an explicit, user-visible action, not an implicit background sync.

### Proof of Concept
1. User adds/clones a repository from `https://ghe.example.com/org/repo.git` and signs into that GHE endpoint in Desktop; `gitHubRepository.cloneURL` is cached as this URL.
2. The GHE instance is compromised, or the API response is otherwise manipulated so that a subsequent `GET` for the repository returns `clone_url: "https://ghe.attacker.example.com/org/repo.git"` (same protocol, so `protocolsMatch` is true) — this can occur via a compromised/malicious enterprise server, or any path where the API repository object served to Desktop is attacker-influenced.
3. On the next background repository refresh, `updateRemoteUrl` sees `remoteUrlUnchanged === true` (local remote still equals cached `cloneURL`) and `urlsMatch === false` (new URL differs), satisfying `protocolsMatch && remoteUrlUnchanged && !urlsMatch`.
4. `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)` executes `git remote set-url origin https://ghe.attacker.example.com/org/repo.git` with no user prompt. [7](#0-6) 
5. The user's next `git push`/`fetch` transparently targets the attacker's host, and Desktop's credential trampoline resolves credentials for the new hostname per its endpoint-hostname matching logic. [8](#0-7) 

This is corroborated by the existing unit test suite for `updateRemoteUrl`, which explicitly exercises the "silently update when clone_url changes" behavior with no confirmation step involved: [9](#0-8)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
