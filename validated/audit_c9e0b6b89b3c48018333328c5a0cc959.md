## Title
IBC Callback `approve()` return-value assumption permanently freezes user funds for non-standard ERC20 token pairs - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
`IBCReceivePacketCallback` calls `approve()` on an arbitrary, permissionlessly-registered native ERC20 contract and unconditionally unpacks the return data as a `bool`, exactly mirroring the reported USDT-style `approve()` bug class: non-standard tokens (e.g., USDT) do not return a `bool` from `approve()`, causing the ABI unpack to fail and the callback to revert. Unlike the sibling `transfer()` handling in the same module (which explicitly falls back to checking `Transfer` event logs when `len(res.Ret) == 0`), the `approve()` call path has no such fallback.

### Finding Description
In `x/ibc/callbacks/keeper/keeper.go`, `IBCReceivePacketCallback` handles ICS-20 receive packets carrying a destination callback (per ADR-8 / IBC-Go callbacks middleware). At this point in the flow, the transferred coins have already been credited to a deterministic, non-EOA "isolated address" (`types.GenerateIsolatedAddress(packet.GetDestChannel(), data.Sender)`), which has no known private key and is only usable by pre-approving the target callback contract to pull funds via `transferFrom`. [1](#0-0) 

The code calls `approve` on `tokenPair.GetERC20Contract()` — for a `IsNativeERC20()` token pair this is an **arbitrary, externally-deployed ERC20 contract** registered via `RegisterERC20`, which supports permissionless registration (`PermissionlessRegistration = true` is a valid, non-privileged configuration, confirmed by the "ok - non-governance, permissionless true" test case in `x/erc20/keeper/msg_server.go`). The ABI used to pack/unpack the call is the module's fixed `ERC20MinterBurnerDecimalsContract` ABI, which declares `approve` as returning `bool`.

If the registered native ERC20 contract is a USDT-style implementation whose `approve()` does not return any data (`res.Ret` has length 0), `erc20.ABI.UnpackIntoInterface(&approveSuccess, "approve", res.Ret)` fails to decode, and `IBCReceivePacketCallback` returns `ErrAllowanceFailed`.

Compare this to the sibling `transfer()` handling in `x/erc20/keeper/msg_server.go`, which explicitly guards against exactly this case: [2](#0-1) 

No equivalent `len(res.Ret) == 0` fallback exists for the `approve` call in the IBC callback path.

### Impact Explanation
Because the receive-packet processing (crediting the isolated address with the ERC20-registered coin) has already completed by the time the callback runs, a failure in the callback does not roll back the transfer — the funds remain in the isolated address. That isolated address is derived deterministically from the destination channel and sender and is not a standard EOA with a recoverable private key; it is designed to be spent only via the contract-approval flow that this same code implements.

If `approve()` reverts (empty return data) every time this token pair is used with a callback, the tokens credited to the isolated address can never be approved to the target contract and therefore can never be pulled out, since the failure is deterministic and will recur on every retry with the same non-compliant token. This satisfies the Critical "permanent freezing/locking of user funds" impact criteria: an unprivileged user (the packet sender / relayer) can trigger this simply by sending an ordinary ICS-20 transfer with a destination callback memo for a token pair backed by a non-standard ERC20 (which anyone can permissionlessly register).

### Likelihood Explanation
Requires: (1) a native ERC20 token pair registered for a token whose `approve()` does not return a `bool` (permissionless, so any user can register such a pair for an existing non-standard token like USDT or a USDT-clone), and (2) an ordinary IBC transfer with a destination callback memo targeting that denom. No privileged role, relayer misbehavior, or governance action is required — it can be triggered purely through standard user-facing transaction flows (registering a token pair + sending an IBC transfer with callback memo).

### Recommendation
Mirror the existing safe-approve/no-return-data handling already used for `transfer()` in `x/erc20/keeper/msg_server.go`: check `len(res.Ret) == 0` before attempting to unpack the `approve` return value, and treat a missing return value as success (optionally combined with an `Approval` event-log check), consistent with the `IERC20-approve` non-standard-token handling pattern (e.g. OpenZeppelin's `safeApprove`/`forceApprove`). Additionally, consider verifying `allowance(isolatedAddr, contractAddr)` after the call instead of relying solely on decoding the return data.

### Proof of Concept
1. Deploy (or use) an ERC20 contract whose `approve(address,uint256)` function has no return value (e.g. a USDT-style implementation), on the counterparty/EVM chain acting as the token's native chain, and register it as a native ERC20 token pair via `MsgRegisterERC20` (permissionless registration enabled).
2. From another chain, send an ICS-20 transfer of this token to the isolated address with a destination-callback memo pointing at any valid contract on the EVM chain.
3. `OnRecvPacket` credits the isolated address with the coin representation of the token pair, then invokes `IBCReceivePacketCallback`.
4. `k.evmKeeper.CallEVM(..., "approve", contractAddr, amountInt.BigInt())` succeeds at the EVM level (no revert) but returns empty `res.Ret` because the token's `approve()` doesn't return data.
5. `erc20.ABI.UnpackIntoInterface(&approveSuccess, "approve", res.Ret)` fails, `IBCReceivePacketCallback` returns `ErrAllowanceFailed`.
6. The coins remain permanently at the isolated address (per the code's own comment: "funds getting stuck in the isolated address ... since they would become irretrievable"), with no available path to recover them because the underlying token's `approve()` will always fail to decode on every retry.
