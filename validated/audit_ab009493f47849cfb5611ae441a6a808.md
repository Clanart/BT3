### Title
mWOMSVBaseRewarder never applies the expiry-forfeit reduction, permanently misallocating unclaimed yield between early exiters and remaining stakers - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit()` is supposed to compute a `forfeitAmount` of a user's pending rewards proportional to how much of their `mWOMSV` lock has actually vested (the "rewardable percent"), redistributing the forfeited portion back to the pool for other stakers, exactly like the sibling contract `vlMGPBaseRewarder` does. Instead, the function hard-codes `rewardableAmount = _amount`, which always yields `forfeitAmount = 0`, so no forfeiture is ever applied and no value is ever redistributed to remaining stakers.

### Finding Description
`vlMGPBaseRewarder._calExpireForfeit()` correctly computes the rewardable share using the locker's real vesting percentage: [1](#0-0) 

By contrast, `mWOMSVBaseRewarder._calExpireForfeit()` never queries `mWOMSV.getRewardablePercentWAD(_account)` (which exists on the locker, as referenced in `wombat/mWomSV.sol` and `interfaces/ILocker.sol`) and instead sets `rewardableAmount = _amount` directly, making the subsequent subtraction always compute to zero: [2](#0-1) 

This is invoked from `_sendReward()`, reachable by any ordinary staker through the normal `getReward`/`getRewards` claim path (routed via `MasterMagpie`): [3](#0-2) 

Because `forfeitAmount` is always `0`, the `toSend` amount transferred to the claiming user always equals their full computed `userRewards`, and the `_queueNewRewardsWithoutTransfer` branch that redistributes forfeited rewards back into `rewardPerTokenStored` for the benefit of remaining stakers is never triggered.

This is the same bug class as the referenced report: a value that is supposed to be split between two parties via a correct subtraction/percentage calculation is instead computed incorrectly (in this case, hard-coded to the full amount instead of a reduced share), causing an incorrect allocation of funds between users.

### Impact Explanation
Any staker who exits or claims before their `mWOMSV` lock is fully vested is unconditionally paid their entire pending reward instead of only the vested (rewardable) portion. The portion that should have been forfeited and redistributed to remaining, fully-vested `mWOMSV` stakers is instead permanently paid out to the early-exiting user and never re-enters `rewardPerTokenStored`. This is a permanent, protocol-wide misallocation of yield: honest long-term stakers who continue to hold their lock never receive the redistributed forfeited rewards they are entitled to under the intended design, constituting a permanent loss of unclaimed yield for those users.

### Likelihood Explanation
This triggers on every single reward claim, since `_calExpireForfeit` is called unconditionally from `_sendReward` in the normal claim flow used by any unprivileged `mWOMSV` staker (via `getReward`/`getRewards`, callable by `MasterMagpie` on behalf of the user). No special conditions, admin actions, or edge cases are needed — it happens deterministically every time.

### Recommendation
Update `mWOMSVBaseRewarder._calExpireForfeit()` to mirror `vlMGPBaseRewarder._calExpireForfeit()` by computing the rewardable share from the locker's actual vesting percentage:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();

    uint256 forfeitAmount = _amount - rewardableAmount;
    if (forfeitAmount < (_amount / 1000)) {
        forfeitAmount = 0;
        rewardableAmount = _amount;
    }
    return forfeitAmount;
}
```

### Proof of Concept
1. A user locks `mWOMSV` and accrues pending rewards while only partially vested (i.e., `mWOMSV.getRewardablePercentWAD(user) < 1e18`).
2. The user calls the claim path, which routes to `mWOMSVBaseRewarder.getReward`/`getRewards`, calling `_sendReward` → `_calExpireForfeit`. [3](#0-2) 
3. `_calExpireForfeit` sets `rewardableAmount = _amount` unconditionally, so `forfeitAmount` computes to `0` regardless of the user's actual vesting percentage. [2](#0-1) 
4. `toSend = userRewards[...] - 0` transfers the user's full pending reward, and `_queueNewRewardsWithoutTransfer` (which would redistribute the forfeited share to `rewardPerTokenStored` for other stakers) is never invoked, permanently withholding that yield from the remaining `mWOMSV` stakers.
