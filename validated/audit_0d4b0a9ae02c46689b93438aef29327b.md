### Title
EIP-7702 SetCode authorization bypasses `AccountKeyFail` protection, allowing signature-based control of accounts explicitly disabled from key-based transactions - (File: `blockchain/types/accountkey/account_key_fail.go`, `blockchain/tx_pool.go`)

### Summary
`AccountKeyFail` is a Kaia account-key type whose explicit purpose is to make an account's transaction validation "always fail" for any ecrecover-derived signature, specifically to guarantee that a smart-contract-like account can never be drained via a raw private-key signature — only via the contract's own `transfer()` logic. [1](#0-0)  This invariant is enforced in `Transaction.Validate()`, which checks the sender's/fee-payer's `AccountKey` via `accountkey.ValidateAccountKey`, and `AccountKeyFail.Validate()` unconditionally returns `false`. [2](#0-1) [3](#0-2) 

However, EIP-7702 `TxTypeEthereumSetCode` authorizations recover an "authority" address directly via raw ECDSA signature recovery over the authorization tuple, completely independent of the `AccountKey` system. The tx-pool's authorization handling (`validateAuth`/`checkDelegationLimit`) only limits the number of in-flight transactions per authority; it never calls `accountkey.ValidateAccountKey` on the recovered authority address. [4](#0-3) [5](#0-4)  This is the same class of bug as the reported finding: a resource that is explicitly marked "disabled"/"disallowed" via one control-plane check (`isAllowed` in `_addCollateralToVault` / `AccountKeyFail.Validate()` for signature-based sender/fee-payer checks) is not re-validated in a second, newer code path that can still exercise the same underlying capability (`_increaseDebt` / EIP-7702 delegation authorization).

### Finding Description
Kaia's `AccountKey` abstraction is meant to be the single authority controlling which signatures are valid for a given address's transactions. `AccountKeyFail` is a special case precisely engineered to permanently and irrevocably strip key-based control from an address — the doc comment states it exists "to prevent smart contract accounts from withdrawing tokens from themselves with a public key recovery mechanism," and both `Validate()` and `CheckUpdatable()` unconditionally fail, meaning the key can never again be replaced or used to authorize transactions through the normal signer/fee-payer validation path. [6](#0-5) 

The EIP-7702 (`TxTypeEthereumSetCode`) mechanism introduces a second, independent authorization channel: each `SetCodeAuthorization` in a transaction's authorization list is verified purely by ECDSA signature recovery to obtain an "authority" address, entirely bypassing `db.GetKey(...)`/`accountkey.ValidateAccountKey`. In `TxPool.validateAuth`, the only checks performed against `SetCodeAuthorities()` are in-flight transaction count limits — there is no lookup of the authority's `AccountKey` type, and specifically no check that the authority does not hold an `AccountKeyFail` key. [5](#0-4)  The general `Transaction.Validate()` account-key check is only applied to `tx.ValidatedSender()` (the transaction's submitter) and, for fee-delegated types, `tx.ValidatedFeePayer()` — never to the authorities embedded in the authorization list. [7](#0-6) 

Consequently, if an address's original ECDSA key holder still exists (i.e., the private key is known) but Kaia's account-level policy has been set to `AccountKeyFail` specifically to revoke that key's ability to sign transactions for that account (e.g. because the account is meant to act purely as a smart-contract account), that same private key can still be used to sign a valid EIP-7702 authorization tuple. Any unprivileged transaction sender can submit a `TxTypeEthereumSetCode` transaction embedding that authorization, causing delegated code to be installed at the `AccountKeyFail`-protected address, wholly bypassing the "irrevocable, signature-proof" guarantee the `AccountKeyFail` type is documented to provide.

### Impact Explanation
This breaks a documented security invariant of Kaia's account model: `AccountKeyFail` accounts are supposed to be permanently unusable via any ecrecover-based signature, so that value stored at that address can only move through the smart contract's own logic. If the underlying secp256k1 private key is still known to an adversary (or was known prior to being fail-flagged for this exact reason), the EIP-7702 path re-opens signature-based control of the account, letting that party install arbitrary delegated code at the address and, from within that code's execution context, move any KAIA/token balance held by the account. This is a state divergence from the intended security model and unauthorized value movement, reachable purely from a single, unprivileged submitted transaction — matching the required severity bar (unauthorized value movement via a reachable single-transaction path).

### Likelihood Explanation
The precondition — an attacker holding the private key of an address whose account key has separately been demoted to `AccountKeyFail` — is a realistic scenario, since `AccountKeyFail` is explicitly designed for exactly this threat model (guarding against private-key-based takeover of what is meant to be a pure smart-contract account). Exploitation requires no special privileges: any account can submit a `TxTypeEthereumSetCode` transaction carrying the authorization signed by the target's original key, and the transaction pool's `validateAuth`/`checkDelegationLimit` logic performs no `AccountKey`-type check to block it. [5](#0-4) 

### Recommendation
When processing `SetCodeAuthorization` entries (in `TxPool.validateAuth`, and in the corresponding state-transition/consensus-path authorization application), look up each recovered authority's current `AccountKey` via the state DB and reject (or ignore) authorizations from addresses whose `AccountKey.Type()` is `AccountKeyTypeFail` (or more generally, addresses for which `AccountKeyFail.Validate()` would return false), mirroring the same signature-validity guarantee already enforced for `tx.ValidatedSender()`/`tx.ValidatedFeePayer()` in `Transaction.Validate()`.

### Proof of Concept
1. Attacker Alice controls address `A` and its ECDSA private key `k`.
2. `A`'s on-chain `AccountKey` is updated (by Alice or a prior owner) to `AccountKeyFail`, with the intent of permanently disabling any future key-based signing for `A` (per the documented purpose in `account_key_fail.go`). [1](#0-0) 
3. Later, `A` accumulates KAIA/token balance (e.g., is used purely as a contract-controlled vault).
4. Alice, still possessing `k`, signs an EIP-7702 `SetCodeAuthorization{Address: maliciousImpl, Nonce: n}` using `k`.
5. Alice (or anyone) submits a `TxTypeEthereumSetCode` transaction whose `AuthorizationList` includes this authorization.
6. `TxPool.validateAuth` / `checkDelegationLimit` only checks in-flight tx counts for authority `A`, never `A`'s `AccountKey` type, so the transaction is accepted and processed. [8](#0-7) 
7. Code is delegated to `A`; Alice can now invoke functions in `maliciousImpl`'s context at address `A`, transferring out the balance held at `A` — despite `A`'s `AccountKeyFail` setting being specifically intended to make this impossible via any ecrecover-based signature path.

func (pool *TxPool) checkDelegationLimit(tx *types.Transaction) error {
	from, _ := types.Sender(pool.signer, tx) // validated

	// Short circuit if the sender has neither delegation nor pending delegation.
	if pool.currentState.GetCodeHash(from) == types.EmptyCodeHash && !pool.all.hasAuth(from) {
		return nil
	}
	pending := pool.pending[from]
	if pending == nil {
		// Transaction with gapped nonce is not supported for delegated accounts
		if pool.getPendingNonce(from) != tx.Nonce() {
			return ErrOutOfOrderTxFromDelegated
		}
		return nil
	}
	// Transaction replacement is supported
	if pending.Contains(tx.Nonce()) {
		return nil
	}
	return ErrInflightTxLimitReached
}

// validateBlobTx validates the blob transaction fields.
func (pool *TxPool) validateBlobTx(tx *types.Transaction) error {
	sidecar := tx.BlobTxSidecar()
	if sidecar == nil {
		return errors.New("missing sidecar in blob transaction")
	}
	// Ensure the blob fee cap satisfies the minimum blob gas price
	if tx.BlobGasFeeCapIntCmp(pool.blobBaseFee) < 0 {
		return fmt.Errorf("%w: blob fee cap %v, minimum needed %v", ErrTxGasPriceTooLow, tx.BlobGasFeeCap(), pool.blobBaseFee)
	}
	// Ensure the number of items in the blob transaction and various side
	// data match up before doing any expensive validations
	hashes := tx.BlobHashes()
	if len(hashes) == 0 {
		return errors.New("blobless blob transaction")
	}
	if len(hashes) > params.BlobTxMaxBlobs {
		return fmt.Errorf("too many blobs in transaction: have %d, permitted %d", len(hashes), params.BlobTxMaxBlobs)
	}
	if err := sidecar.ValidateWithBlobHashes(hashes); err != nil {
		return err
	}
	return nil
}

// validateAuth verifies that the transaction complies with code authorization
// restrictions brought by SetCode transaction type.
func (pool *TxPool) validateAuth(tx *types.Transaction) error {
	// Allow at most one in-flight tx for delegated accounts or those with a
	// pending authorization.
	if err := pool.checkDelegationLimit(tx); err != nil {
		return err
	}

	// For symmetry, allow at most one in-flight tx for any authority with a
	// pending transaction.
	for _, auth := range tx.SetCodeAuthorities() {
		var count int
		if pending := pool.pending[auth]; pending != nil {
			count += pending.Len()
		}
		if queue := pool.queue[auth]; queue != nil {
			count += queue.Len()
		}
		// Replace the existing in-flight transaction for delegated accounts
		// are still supported
		if count > 1 {
			return ErrAuthorityReserved
		}
	}
	return nil
}
