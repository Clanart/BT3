### Title
Attacker-controlled allocation of `n * size_of::<C::F>()` in `ThresholdKeys::read` before any input validation - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to CVE-2025-51846 (unbounded per-message resource consumption by an unauthenticated remote party), `ThresholdKeys::<C>::read` trusts a 16-bit `n` field from the byte stream and immediately performs `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient vector — before validating `t <= n`, before validating `i`, and before reading a single scalar. A remote, unprivileged party feeding crafted bytes to `ThresholdKeys::read` gets ~2 MiB of heap allocation per ~10 bytes of input, and the same pattern repeats in the `verification_shares` loop which issues `n` point-deserializations. There is no bound check against `n` beyond the implicit u16 maximum of 65535.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` parses `(t, n, i)` straight from the reader, then reads a one-byte interpolation selector. For selector `0` (`Interpolation::Constant`) it executes `Vec::with_capacity(usize::from(n))` — allocating `n * size_of::<C::F>()` bytes — and only afterwards enters the `read_F` loop. `ThresholdParams::new(t, n, i)` (the only validation of `n`) is not invoked until the very end at line 626, after all allocation and reads have occurred. The relevant code:

```rust
// crypto/dkg/src/lib.rs:597-616
(
  read_u16()?,   // t — unvalidated
  read_u16()?,   // n — unvalidated, fully attacker-controlled
  Participant::new(read_u16()?)...
)
...
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));  // allocates n * size_of::<F>()
  for _ in 0 .. n {
    res.push(C::read_F(reader)?);
  }
  res
}),

Additionally, the `verification_shares` loop at lines 620–623 iterates `1 ..= n` performing a full `read_G` (point decompression + canonicality re-encoding check) per iteration — expensive group operations driven by the same unvalidated `n`. While the loop body requires bytes to be present, each iteration still costs a decompression, so a buffer padded with valid-but-meaningless point encodings forces `n` decompression operations with no `n <= participants` sanity check up front.

This mirrors the CryptPad flaw: a length/count field in attacker-supplied input directly controls memory/CPU expenditure with no pre-validation bound.

### Impact Explanation
Per request, an attacker supplying `n = 0xFFFF` and interpolation byte `0` forces a single allocation of `65535 * size_of::<C::F>()` — ~2 MiB for 256-bit fields, ~3.7 MiB for ed448-sized scalars — from an input prefix under a dozen bytes (the `C::ID` prefix is a public constant and trivially satisfied). Repeated calls create sustained allocator churn and memory-pressure amplification (~200,000:1 transient amplification per call), degrading or denying service for the calling process — e.g., any node deserializing `ThresholdKeys`/`ThresholdCore` from network, database, or message-queue bytes. The verification-shares loop additionally allows `n`-scaled CPU burn (decompression per declared share) whenever the input is padded accordingly. This matches the CVE's VA:H denial-of-service profile; it does not leak secrets.

### Likelihood Explanation
`ThresholdKeys::read` is the canonical deserialization entry point for all DKG-produced keys (PedPoP, MuSig, promote/recovery/dealer all funnel into `ThresholdKeys::new`), and it is explicitly in the reachable-read surface for untrusted bytes. Any deployment that persists or transports serialized keys and reads them in a path influenced by external data hits this code. The only mitigating factor is that the oversized allocation is transient (dropped on the first failed `read_F`), so sustained DoS requires a request loop rather than a single message — consistent with a Medium rating like the source CVE rather than High.

### Recommendation
Validate parameters before allocating or iterating:

```rust
let (t, n, i) = ...;
// Immediately:
let params = ThresholdParams::new(t, n, i).map_err(io::Error::other)?;
```

then use `params.n()`/`params.t()` for all `with_capacity` calls and loop bounds. This still permits `n = 65535` by design of `ThresholdParams`, so additionally consider bounding `n` by an application-meaningful maximum (e.g., `MAX_KEY_SHARES_PER_SET`) or reading scalars incrementally with `Vec::new()` and an explicit cap, so allocation tracks bytes actually consumed rather than the declared count.

### Proof of Concept
Feed `ThresholdKeys::<C>::read` a byte stream consisting of:

1. `u32::to_le_bytes(C::ID.len())` followed by `C::ID` (public constant),
2. `t = 0x0001u16`, `n = 0xFFFFu16`, `i = 0x0001u16`,
3. interpolation selector byte `0x00`,
4. EOF.

Observed behavior: `Vec::with_capacity(65535)` allocates `65535 * size_of::<C::F>()` (~2 MiB for Ristretto/Secp256k1 scalars) at line 608 before `read_F` fails at line 610. Looping this request yields continuous multi-MiB alloc/free cycles per ~15 bytes received — unbounded memory-bandwidth and allocator pressure proportional to request rate, no authentication or valid key material required. Setting interpolation to `0x01` (Lagrange) and padding with `n` valid point encodings instead forces 65535 `read_G` decompressions per message at lines 621–623.

Caveat I could not fully verify within scope: whether production coordinator/processor call sites pass genuinely remote-controlled bytes into `ThresholdKeys::read` unauthenticated (the coordinator transaction layer caps `DkgCommitments` sizes via `TRANSACTION_SIZE_LIMIT`, but `ThresholdKeys::read` itself performs no equivalent guard). The flaw exists in the deserialization routine regardless of the transport's own limits.
