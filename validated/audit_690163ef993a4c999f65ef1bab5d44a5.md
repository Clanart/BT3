## Title
Forfeiture bypass via same-block `cancelUnlock()` before `getReward()` due to spot-state (non time-weighted) `getRewardablePercentWAD` check - (File: `rewards/vlMGPBaseRewarder.sol`)

## Summary
`_calExpireForfeit` computes the forfeiture on accrued bonus rewards using the account's *current* `vlMGP.getRewardablePercentWAD(_account)` value at the moment `getReward()`/`getRewards()` is called, rather than a time-weighted percentage reflecting the account's cooldown history over the accrual period. Because a user can freely call `cancelUnlock()` on `VLMGP` to move `amountInCoolDown` back into `fullyInLock` immediately before calling `getReward()`, they can force `getRewardablePercentWAD` to report 100% and reduce `forfeitAmount` to zero for rewards that accrued while they were actually in cooldown.

## Finding Description
`getReward`/`getRewards` in `rewards/vlMGPBaseRewarder.sol` call `_sendReward`, which computes the forfeit strictly from the account's live lock state: [1](#0-0) 

`_calExpireForfeit` derives `rewardableAmount`/`forfeitAmount` purely from a single spot read of `vlMGP.getRewardablePercentWAD(_account)`: [2](#0-1) 

There is no historical/time-weighted accounting tying the forfeit calculation to the state the account was actually in while the reward accrued (i.e., between the last `userRewardPerTokenPaid` update and now). Because `balanceOf`/weighting is itself derived from the account's live lock/cooldown composition (as documented in the comment "amount of MGP still in lock + amount of MGP in cool down / 2"): [3](#0-2) 

an account that entered cooldown, accrued bonus reward while its `rewardablePercentWAD` should reflect partial cooldown, and then calls `VLMGP.cancelUnlock()` to restore `fullyInLock` status atomically before calling `getReward()`, will have `_calExpireForfeit` read the post-cancel (fully-locked) state and return `forfeitAmount == 0`, when a value computed from the true historical cooldown exposure would have been non-zero.

Existing guards (`onlyMasterMagpie`, `updateReward`, `nonReentrant` on `getRewards`) only protect against unauthorized callers/reentrancy — they do not validate that the state used for forfeiture calculation matches the state during which the reward was earned, so they do not stop this manipulation.

Note: I was unable to fully retrieve the implementation of `cancelUnlock()` and `getRewardablePercentWAD()` inside `VLMGP.sol` in this session (only match counts were returned, not the code body), so the exact mechanics of how `amountInCoolDown` is moved back to `fullyInLock` and whether any cooldown-timestamp memory is retained could not be directly confirmed here. This is a limitation of the available context, not a claim that the code was verified line-by-line.

## Impact Explanation
If confirmed, this allows an unprivileged staker to systematically avoid the forfeiture penalty designed to redistribute a cooldown-exiting user's unclaimed bonus rewards to the remaining honest lockers via `_queueNewRewardsWithoutTransfer`. This is a theft of unclaimed yield that should have accrued to other stakers, matching the Immunefi "theft of unclaimed yield" impact class, and is repeatable on every harvest cycle for any account willing to toggle its lock state around claims.

## Likelihood Explanation
No special privileges are required — `cancelUnlock()` and `getReward()`/`getRewards()` (via MasterMagpie) are both reachable by any account holding vlMGP. The exploit only requires ordering two of the attacker's own transactions in the same block (or back-to-back), which is trivial and requires no flash loan or front-running of another party's transaction — the attacker manipulates their own state before claiming their own reward. This significantly increases feasibility/repeatability, though full confirmation depends on the exact cooldown/lock semantics in `VLMGP.sol`, which could not be fully verified here.

## Recommendation
Compute the forfeit based on a time-weighted or snapshot record of the account's lock/cooldown composition captured at reward-accrual time (e.g., snapshot `rewardablePercentWAD` alongside each `userRewardPerTokenPaid` checkpoint update, or accumulate forfeit incrementally each time `_updateFor` runs) rather than reading live state only at claim time. Alternatively, disallow `cancelUnlock()` from affecting the reward-eligible weighting for the amount/duration already spent in cooldown.

## Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, and `vlMGPBaseRewarder` (or a fork/mock replicating current mainnet state) with `_rewardManager` queuing MGP as bonus.
2. Attacker locks MGP, then calls the unlock function to start cooldown (`amountInCoolDown > 0`, `fullyInLock` reduced).
3. While in cooldown, have `queueMGP`/`queueNewRewards` push bonus rewards that accrue to the attacker (`userRewards` updated via `_earned`).
4. In the same block/transaction sequence, call `vlMGP.cancelUnlock()` to restore `fullyInLock`, then immediately call `getReward(attacker, attacker)` on `vlMGPBaseRewarder`.
5. Assert `calExpireForfeit(attacker, rewardToken)` (or the emitted `forfeitAmount` in `MGPHarvested`/via `_sendReward`) equals `0`.
6. Compare against a control run where the attacker does NOT call `cancelUnlock()` and instead lets cooldown proceed naturally to expiry before harvesting — assert `forfeitAmount > 0` in that path, computed from `getRewardablePercentWAD` while genuinely in cooldown.
7. Show the discrepancy demonstrates the attacker captured bonus reward that should have been partially routed to `_queueNewRewardsWithoutTransfer` for other stakers.

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```
