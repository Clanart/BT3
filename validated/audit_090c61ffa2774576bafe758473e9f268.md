### Title
Silent precision loss when decoding unquoted large int64/uint64 ProtoJSON numbers in upb's JSON decoder - (File: `upb/json/decode.c`, `php/ext/google/protobuf/php-upb.c`, `ruby/ext/google/protobuf_c/ruby-upb.c`)

### Summary
The Lodestar advisory's failed invariant is: a 64-bit integer value is parsed by converting attacker-supplied input into an IEEE-754 double, and that double is treated as an exact representation, causing values above 2^53 to silently round to a different (but still "valid-looking") integer. Protobuf's `upb`-based ProtoJSON decoder — shared by the PHP and Ruby native extensions (and any other upb-JSON consumer) — contains the same failed invariant when a 64-bit integral field (`int64`/`sint64`/`sfixed64`/`uint64`/`fixed64`) is supplied as an *unquoted JSON number* rather than the canonical quoted-string form.

### Finding Description
`jsondec_int`/`jsondec_uint` in `upb/json/decode.c:698-771` (identically duplicated in `php/ext/google/protobuf/php-upb.c:5629-5702` and `ruby/ext/google/protobuf_c/ruby-upb.c:4383-4455`) handle the `JD_NUMBER` case by calling `jsondec_number(d)`, which parses the numeric literal text into a `double`, then casts that `double` back to `int64_t`/`uint64_t`: [1](#0-0) [2](#0-1) 

The only integrity check performed is a round-trip check (`val.int64_val != dbl`) and a magnitude bound against the nearest representable double below `INT64_MAX`/`UINT64_MAX` (`9223372036854774784.0` / `18446744073709549568.0`). This check only detects *non-integral* doubles (fractional remainders); it cannot detect that the decimal text itself was already rounded to a different integer during text→double conversion, because doubles only have 53 bits of mantissa precision. For any integer whose magnitude is between 2^53 (~9.007×10^15) and the ~2^63/2^64 bound, several distinct decimal integers map to the same nearest double, and that double is always "integral," so the round-trip check passes silently — decoding a different value than what was encoded, without error.

This is only reachable through the *unquoted* number path (`JD_NUMBER`). When the same field is quoted as a string, the code instead uses `upb_BufToInt64`/`upb_BufToUint64`, which perform exact digit-by-digit accumulation and correctly reject overflow: [3](#0-2) 

By contrast, the newer/independent C++ core ProtoJSON parser (`src/google/protobuf/json/internal/parser.cc`) mitigates exactly this class of bug: it first attempts an exact `absl::SimpleAtoi` parse, and only falls back to the lossy double path (`ParseFloatStringAsInt`) when that fails, additionally clamping the double fallback to the JS-safe-integer range (±2^53 for `int64`, up to 2^54 for `uint64`) rather than the full 63/64-bit range: [4](#0-3) [5](#0-4) 

So there is a real, provable differential: two supported, actively-shipped ProtoJSON decoders in the same repository (C++ core vs. upb, the latter powering PHP/Ruby and other upb-based language bindings) disagree on both (a) whether an out-of-double-precision unquoted integer is valid, and (b) what value it decodes to. The upb path can silently accept and misdecode a value instead of erroring.

### Impact Explanation
Any consuming application that treats protobuf's ProtoJSON decode as authoritative for 64-bit IDs, balances, slot/epoch-like counters, timestamps in nanoseconds, or similar large integers — and that accepts unquoted JSON numbers for such fields (permitted by the ProtoJSON spec for robustness) — can be made to silently store/act on a different integer value than what was actually sent, when decoded via the upb backend (PHP, Ruby, and other upb-JSON consumers). This mirrors the Lodestar impact category: silent misinterpretation of a large integer value due to double-precision rounding, which can produce integrity failures in downstream logic (e.g., a validity check keyed on the exact value passes/fails incorrectly). It does not, by itself, cause memory corruption or RCE; the impact is data-integrity/consensus-similar misdecoding, which is why classification depends heavily on how a downstream schema/application uses such fields — Protobuf itself has no "consensus" concept, so severity is bounded by integrity impact on the consuming application, consistent with the scope constraint that Protobuf itself doesn't expose an RPC endpoint.

### Likelihood Explanation
High: the attacker only needs to submit a bounded, well-formed ProtoJSON document with an unquoted numeric literal in the (2^53, ~2^63) range for an int64/uint64/fixed64 field — this is a normal, spec-permitted, bounded input via any public `JsonDecode`/`parseJson`-equivalent entry point using the upb backend. No malicious schema, no huge payload, and no privileged access are required. The round-trip self-check gives a false sense of safety while not actually validating fidelity of the original decimal value.

### Recommendation
In `upb/json/decode.c` (and its generated copies in PHP/Ruby), for `JD_NUMBER` on 64-bit integral fields, parse the raw numeric text with an exact integer parser (`upb_BufToInt64`/`upb_BufToUint64`) first, falling back to the double path only for genuinely non-integer-literal forms (e.g., exponent notation), and reject values outside the double-safe-integer range (±2^53) when only a double parse is possible — mirroring the approach already used in `src/google/protobuf/json/internal/parser.cc`. This closes the precision-loss window and makes upb-based JSON decoding behavior consistent with the C++ core decoder.

### Proof of Concept
Given a `.proto` message `message M { uint64 id = 1; }` (trusted schema), submit ProtoJSON `{"id": 9007199254740993}` (2^53 + 1, unquoted) to a upb-backed decoder (PHP/Ruby `JsonDecode`):
1. `jsondec_uint` reaches `JD_NUMBER`, calls `jsondec_number` producing `dbl = 9007199254740992.0` (round-to-even of the literal, since 9007199254740993 is not exactly representable).
2. `val.uint64_val = (uint64_t)dbl = 9007199254740992`.
3. Round-trip check `val.uint64_val != dbl` is `9007199254740992 != 9007199254740992.0` → false → no error raised.
4. Decoded `M.id` is `9007199254740992`, not the `9007199254740993` sent by the client — a silent 1-off (in general, arbitrary-magnitude) misdecoding.

By contrast, the same literal submitted to the C++ core's `ParseUInt` (`src/google/protobuf/json/internal/parser.cc:255-268`) would be rejected as "integer out of range" because its double-fallback bound is capped at `18014398509481984.0` (2^54) and it first attempts an exact `SimpleAtoi`, demonstrating both the fix pattern and the current cross-backend inconsistency. const char* upb_BufToUint64(const char* ptr, const char* end, uint64_t* val) {
  uint64_t u64 = 0;
  while (ptr < end) {
    unsigned ch = *ptr - '0';
    if (ch >= 10) break;
    if (u64 > UINT64_MAX / 10 || u64 * 10 > UINT64_MAX - ch) {
      return NULL;  // integer overflow
    }
    u64 *= 10;
    u64 += ch;
    ptr++;
  }

  *val = u64;
  return ptr;
}

template <typename T>
absl::StatusOr<LocationWith<T>> ParseIntInner(JsonLexer& lex, double lo,
                                              double hi) {
  absl::StatusOr<JsonLexer::Kind> kind = lex.PeekKind();
  RETURN_IF_ERROR(kind.status());

  LocationWith<T> n;
  switch (*kind) {
    case JsonLexer::kNum: {
      absl::StatusOr<LocationWith<MaybeOwnedString>> x = lex.ParseRawNumber();
      RETURN_IF_ERROR(x.status());
      n.loc = x->loc;
      if (absl::SimpleAtoi(x->value.AsView(), &n.value)) {
        break;
      }

      RETURN_IF_ERROR(ParseFloatStringAsInt<T>(*x, &n.value, lo, hi));
      break;
    }
    case JsonLexer::kStr: {
      absl::StatusOr<LocationWith<MaybeOwnedString>> str = lex.ParseUtf8();
      RETURN_IF_ERROR(str.status());

      n.loc = str->loc;

      // SimpleAtoi will ignore leading and trailing whitespace, so we need
      // to check for it ourselves.
      for (char c : str->value.AsView()) {
        if (absl::ascii_isspace(c)) {
          return lex.Invalid("non-number characters in quoted number");
        }
      }
      if (absl::SimpleAtoi(str->value.AsView(), &n.value)) {
        break;
      }

      RETURN_IF_ERROR(ParseFloatStringAsInt<T>(*str, &n.value, lo, hi));
      break;
    }
    default:
      return lex.Invalid("expected number or string");
  }

  return n;
}

template <typename Traits>
absl::StatusOr<int64_t> ParseInt(JsonLexer& lex, Field<Traits> field) {
  absl::StatusOr<LocationWith<int64_t>> n =
      ParseIntInner<int64_t>(lex, -9007199254740992.0, 9007199254740992.0);
  RETURN_IF_ERROR(n.status());

  if (Traits::Is32Bit(field)) {
    if (std::numeric_limits<int32_t>::min() > n->value ||
        n->value > std::numeric_limits<int32_t>::max()) {
      return n->loc.Invalid("integer out of range");
    }
  }

  return n->value;
}
