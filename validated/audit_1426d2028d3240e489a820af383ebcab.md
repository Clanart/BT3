### Title
DID transfer preserves stale recovery/backup DID authority, allowing a removed backup ID holder to recover control of a DID after ownership transfer - (File: chia/wallet/did_wallet/did_wallet.py)

### Summary
GitLab's SAML SSO bug (CVE-2022-4331) allowed a previously removed maintainer/owner of a group to retain access after the group was transferred to a new namespace, because stale authorization state was not revoked at transfer time. The closest reachable analog in this codebase is `DIDWallet.transfer_did()` in [1](#0-0) , which transfers ownership of a DID singleton to a new p2 puzzle hash but by default carries forward the existing `backup_ids` (the DID's "recovery"/co-owner list) unless the caller explicitly opts to reset it.

### Finding Description
`transfer_did()` builds the new DID inner puzzle using `self.did_info.backup_ids` and `self.did_info.num_of_backup_ids_needed`, only clearing them via `self.reset_recovery_list()` [2](#0-1) . `reset_recovery_list()` only nils out the recovery list hash if `backup_ids` is already empty [3](#0-2) ; it does not proactively strip a non-empty backup list. The CLI/RPC surface exposes this as an explicit, opt-in choice: `DidTransferDidCMD` has a `reset_recovery` flag defaulting to `False` [4](#0-3) , and `transfer_did()` in `wallet_funcs.py` passes `with_recovery_info=not reset_recovery` straight through to the RPC call [5](#0-4) .

The DID puzzle itself embeds this recovery list as a hash of DIDs that are each individually able to co-sign an "attestment" recovery message (`create_recovery_message_puzzle` / `create_spend_for_message`) to help a new owner take over the singleton [6](#0-5) . If a DID owner sells or transfers a DID (e.g., in a marketplace/offer context) without recognizing that `reset_recovery` defaults to `False`, any address previously listed as a backup/recovery ID — which could be a former business partner, employee, or otherwise untrusted party who was supposed to lose all authority over the DID at transfer time — retains the cryptographic capability to participate in recovering/taking over the DID's current inner puzzle after the transfer, exactly mirroring the GitLab bug class: prior authority (backup DID) is not revoked when custody/ownership moves to a new party.

### Impact Explanation
A DID is a singleton identity that anchors NFT ownership (minter/owner DID), VC (Verifiable Credential) proof-provider authority (`vc.proof_provider` in [7](#0-6) ), and other trust relationships. If a seller transfers a DID to a buyer via `transfer_did` with the default `reset_recovery=False` (or a buyer fails to independently reset it post-transfer), the seller's previously configured backup/recovery DIDs remain embedded in the puzzle and can be used to initiate a recovery flow against the singleton the buyer now believes they solely control. This is an unauthorized-control/coin-movement risk on a purchased/transferred asset — a former stakeholder retaining a path to reclaim or interfere with ownership after the transfer was believed complete.

### Likelihood Explanation
This requires no privileged access or malicious peer/network behavior — any wallet user who transfers a DID via the standard CLI/RPC path (`chia wallet did transfer` or `did_transfer_did`) without passing `--reset_recovery` is affected, since that is not the default. The behavior is also silent: nothing in the CLI output or RPC response warns that recovery authority is being carried over. Because DID transfers are a common flow in NFT/offer/marketplace scenarios, and the flag defaults to preserving the stale list, this is a realistic misconfiguration rather than a deliberately exploited attack in and of itself.

### Recommendation
Default `transfer_did` (and the `reset_recovery` CLI/RPC flag) to clearing the recovery/backup ID list on transfer unless the new owner explicitly opts to keep it, and surface a clear warning in `DidTransferDidCMD`/`transfer_did` output when a non-empty backup list is being carried over to a new owner puzzle hash.

### Proof of Concept
1. Alice creates a DID with `num_of_backup_ids_needed > 0` and a `backup_ids` list containing Mallory's DID (e.g., a former co-signer).
2. Alice sells/transfers the DID to Bob using the default flow: `chia wallet did transfer -i <id> -ta <bob_address>` without `--reset_recovery`, exercising [4](#0-3)  and [1](#0-0) .
3. The resulting DID inner puzzle still curries in Mallory's DID as part of the recovery-list hash, since `backup_ids` was passed through unchanged.
4. Bob believes he now solely controls the DID, but Mallory (holding sufficient co-signers per `num_of_backup_ids_needed`) can still construct recovery attestment spends (`create_spend_for_message`) against the singleton, per the puzzle logic in [6](#0-5) , demonstrating retained stale authority after the ownership transfer.

    def reset_recovery_list(self) -> Program | None:
        if self.did_info.current_inner is None:
            return None

        uncurried_args = uncurry_innerpuz(self.did_info.current_inner)
        if uncurried_args is None:
            return None

        _, og_recovery_list_hash, _, _, _ = uncurried_args
        if self.did_info.num_of_backup_ids_needed == 0 and not did_recovery_is_nil(og_recovery_list_hash):
            return None

        if len(self.did_info.backup_ids) > 0:
            return None

        return og_recovery_list_hash

async def transfer_did(
    wallet_info: WalletClientInfo,
    did_wallet_id: int,
    fee: uint64,
    target_cli_address: CliAddress,
    with_recovery: bool,
    push: bool,
    condition_valid_times: ConditionValidTimes,
    tx_config: TXConfig,
) -> list[TransactionRecord]:
    try:
        target_address = target_cli_address.original_address
        response = await wallet_info.client.did_transfer_did(
            DIDTransferDID(
                wallet_id=uint32(did_wallet_id),
                inner_address=target_address,
                fee=fee,
                with_recovery_info=with_recovery,
                push=push,
            ),
            tx_config=tx_config,
            timelock_info=condition_valid_times,
        )
        if push:
            print(f"Successfully transferred DID to {target_address}")
        print(f"Transaction ID: {response.transaction_id.hex()}")
        print(f"Transaction: {response.transaction.to_json_dict()}")
        return response.transactions
    except Exception as e:
        print(f"Failed to transfer DID: {e}")
        return []

def create_recovery_message_puzzle(recovering_coin_id: bytes32, newpuz: bytes32, pubkey: G1Element) -> Program:
    """
    Create attestment message puzzle
    :param recovering_coin_id: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: Message puzzle
    """
    puzzle = Program.to(
        (
            1,
            [
                [ConditionOpcode.CREATE_COIN_ANNOUNCEMENT, recovering_coin_id],
                [ConditionOpcode.AGG_SIG_UNSAFE, bytes(pubkey), newpuz],
            ],
        )
    )
    return puzzle


def create_spend_for_message(
    parent_of_message: bytes32, recovering_coin: bytes32, newpuz: bytes32, pubkey: G1Element
) -> CoinSpend:
    """
    Create a CoinSpend for a atestment
    :param parent_of_message: Parent coin ID
    :param recovering_coin: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: CoinSpend
    """
    puzzle = create_recovery_message_puzzle(recovering_coin, newpuz, pubkey)
    coin = Coin(parent_of_message, puzzle.get_tree_hash(), uint64(0))
    solution = Program.to([])
    return make_spend(coin, puzzle, solution)
