## Analysis

The seed report's underlying bug pattern is a **gating check that fails to actually restrict a dangerous operation to the intended safe set of inputs** (in Nexus, module types; the fix removes an over-restriction, but the general class of bug — a validation check that looks like it enforces a safety boundary but doesn't — has a direct inverse analog in Desktop, which is *far more security-relevant*: a check that pretends to gate a scheme/type but never actually blocks anything).

I found this exact pattern in Desktop's `open-external` IPC handler. [1](#0-0) 

The code checks whether `path` starts with `http://` or `https://` — but that check is used **only to decide whether to log a message**. It performs no `return`/`reject` for any other scheme; `shell.openExternal(path)` is invoked unconditionally with whatever string the renderer passed. Meanwhile `shell.openExternal` is invoked throughout the renderer with URLs sourced directly from GitHub API content the user does not control, e.g. markdown links inside PR/review comments rendered by `SandboxedMarkdown` and dispatched via `onMarkdownLinkClicked`: [2](#0-1) [3](#0-2) [4](#0-3) 

I was not able to inspect the full contents of `app/src/ui/lib/sandboxed-markdown.tsx` (only grep hits, not full file body) to confirm whether it applies its own scheme allowlist before invoking `onMarkdownLinkClicked` — this is a real gap in what I could verify from the index, and it materially affects whether this is exploitable end-to-end from a PR comment. If you need certainty here, a Devin session with full file access should read that file in full.

### Title
`open-external` IPC handler passes attacker-influenced URLs to `shell.openExternal` without scheme allowlisting - (File: `app/src/main-process/main.ts`)

### Summary
The `open-external` IPC handler in the main process contains a scheme check (`http://`/`https://`) that is used only for logging, not for gating. Any string reaching this handler — including one derived from GitHub-hosted content such as PR/review comment markdown — is forwarded verbatim to Electron's `shell.openExternal`, which can invoke OS-level protocol handlers or UNC paths.

### Finding Description
`ipcMain.handle('open-external', ...)` inspects `pathLowerCase` only to decide whether to `log.info`; there is no `else`/early-return path that rejects non-http(s) schemes: [1](#0-0) . This mirrors the seed's broken-invariant class: a validation-looking check exists in the code but doesn't actually enforce the boundary it appears to assert (there, it wrongly blocked types; here it wrongly fails to block types). Callers throughout the renderer (`LinkButton`, `release-notes-dialog`, `pull-request-comment-like` via `dispatcher.openInBrowser`) pass URLs originating from rendered markdown of GitHub objects (PR bodies, review comments) straight through to this IPC channel.

### Impact Explanation
`shell.openExternal` with an unvalidated scheme can be abused to launch arbitrary local executables via `file://` paths pointing at binaries already on disk, invoke unusual registered URI handlers (a known Windows abuse class for RCE via IE/Edge/Office protocol handlers), or leak NTLM credentials by resolving a UNC path (`\\attacker-host\share`) supplied as the "URL," all without the user leaving Desktop or taking any unnatural action beyond clicking a link inside a comment they're reading. This satisfies the valid-impact bar: attacker controls a GitHub API object (PR/review comment body) and the result can be code execution or credential exfiltration.

### Likelihood Explanation
Medium: this requires an attacker to place a malicious link inside content that GitHub Desktop renders as clickable markdown (PR comment, review, notification), and for the user to click it. Desktop already trusts markdown-derived links enough to forward them to `openExternal`; the missing gate is entirely server-content-driven, not requiring local access, admin rights, or prior compromise — consistent with the report's "click a link" primitive, but likelihood ultimately hinges on whatever scheme filtering (if any) exists in `sandboxed-markdown.tsx`, which I could not fully verify from the available index.

### Recommendation
Make the existing check load-bearing: reject (return `false`, do not call `shell.openExternal`) for any `path` whose parsed protocol is not `http:` or `https:` inside the `open-external` IPC handler in `app/src/main-process/main.ts`, rather than only using the check for logging. This centralizes protection regardless of what the renderer-side markdown sanitizer does or doesn't enforce.

### Proof of Concept
1. As an attacker, post a PR/review comment on a repository the victim has open in Desktop, containing a markdown link such as `[click me](file:///C:/some/attacker-planted-or-preexisting.exe)` or `[click me](\\attacker-server\share)`.
2. Victim receives/views the notification or comment inside Desktop, which renders it via `SandboxedMarkdown` and wires link clicks to `onMarkdownLinkClicked` → `shell.openExternal`/`dispatcher.openInBrowser` [2](#0-1) .
3. The click reaches the `open-external` IPC handler, whose scheme check only affects logging, not execution [1](#0-0) .
4. `shell.openExternal(path)` executes with the attacker-chosen scheme/path.

  ipcMain.handle('open-external', async (_, path: string) => {
    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
