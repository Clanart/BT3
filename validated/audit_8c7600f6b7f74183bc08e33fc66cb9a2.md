### Title
Webhook shop-domain header is not covered by HMAC signature, allowing cross-shop webhook spoofing - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification` only validates the raw POST body against the app's shared client secret. It never binds the `X-Shopify-Shop-Domain` (or `X-Shopify-Topic`) header to that signature, so any request with a previously-valid `(body, HMAC)` pair is accepted as authentic regardless of which shop domain header accompanies it. This is directly analogous to the Sentiment bug: an "operation" (here, HMAC verification) returns/accepts a value (the shop domain) that is trusted downstream for tenant identification without checking it against anything that ties it to the signed payload or an allow-list of shops the app actually has installed.

### Finding Description
`hmac_valid?` computes the digest over `request.raw_post` only, comparing it against a signature produced with `ShopifyApp.configuration.secret`/`old_secret`: [1](#0-0) 

`WebhookVerification#verify_request` calls `hmac_valid?(data)` where `data = request.raw_post`, and exposes `shop_domain` purely by reading the header, with no cross-check against the signed body: [2](#0-1) 

The built-in `WebhooksController#receive` forwards the untrusted headers (including shop domain) straight into `ShopifyAPI::Webhooks::Registry.process`, which dispatches to app-defined job handlers keyed off that header value: [3](#0-2) 

The generator-provided controller/job templates (which represent the officially recommended integration pattern) take this even further — they extract `webhook_request.shop` (the same unsigned header) and use it directly to look up and mutate a shop record, e.g. `Shop.find_by(shopify_domain: shop_domain)` followed by `shop.destroy` for the `app/uninstalled` topic: [4](#0-3) [5](#0-4) 

Because the HMAC secret (`config.secret`) is the app's single client secret shared across every shop that installs the app — not a per-shop secret — any merchant who installs the app on their own store can capture a legitimate `(raw_body, HMAC)` pair delivered to their own webhook endpoint (e.g. by triggering a webhook on their own store) and then replay that exact body/signature to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `verify_request` will still succeed because the header is not part of the signed data.

### Impact Explanation
An attacker (a legitimate but malicious merchant of the app) can cause the app to process a forged webhook "as if" it came from an arbitrary victim shop domain, without needing that victim's cooperation or credentials. Depending on which topic/body is replayed and how the app's job consumes `shop_domain`, this enables cross-shop data confusion or corruption — for example, using the `app/uninstalled` template pattern, an attacker could get `Shop.find_by(shopify_domain: <victim_domain>)` deleted (`shop.destroy`), or other shop-scoped webhook jobs (orders, customers, GDPR jobs) executed under a victim shop's identity. This is a cross-shop trust boundary violation reachable by any anonymous/unrelated merchant with no special privilege beyond installing the app once.

### Likelihood Explanation
Moderate-to-high: exploitation requires the attacker to first capture one valid `(body, HMAC)` pair, which any merchant can obtain by installing the app and triggering any webhook topic on their own store (trivial, self-service). No secret leakage or insider access is needed — the shared app secret only needs to sign *some* body, and the attacker controls which unsigned header (shop domain/topic in some non-standard use) accompanies the replay.

### Recommendation
Bind the shop domain (and topic) into the authenticity check rather than trusting them as unauthenticated headers: verify that the resolved `shop_domain` corresponds to a shop with an active session/installation before enqueuing any job, and/or require that consuming jobs re-validate the shop's installation state before performing destructive or shop-scoped actions based on webhook-provided identifiers.

### Proof of Concept
1. Install the target app on an attacker-controlled dev store `attacker.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g. `app/uninstalled` or any topic with a registered job) on the attacker's store; capture the exact `raw_post` body and the `X-Shopify-Hmac-Sha256` header Shopify sends.
3. Replay that same body and HMAC header to the app's `/webhooks/:topic` endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `WebhookVerification#verify_request` (`hmac_valid?`) succeeds because it only checks the body/secret, not the shop header.
5. The job handler (per the generator templates) executes using `shop_domain: "victim.myshopify.com"`, e.g. looking up and destroying the victim's `Shop` record via `Shop.find_by(shopify_domain: shop_domain)` / `shop.destroy`.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

```text
class AppUninstalledJob < ActiveJob::Base
  extend ShopifyAPI::Webhooks::WebhookHandler

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end
end
```
