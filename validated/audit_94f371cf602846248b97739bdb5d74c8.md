### Title
Uncontrolled Recursion in `AccountKeyRoleBased.DecodeRLP` via Self-Nested Role-Based Account Keys Causes Unrecoverable Node Crash - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each element of a role-based key list by dispatching to `AccountKeySerializer.DecodeRLP`, which in turn instantiates a new `AccountKey` based on an attacker-controlled type tag and recurses back into `AccountKeyRoleBased.DecodeRLP` if that tag is again `AccountKeyTypeRoleBased`. There is no recursion-depth check, no composite-type check, and no `EnsureSufficientExecutionStack`-style guard anywhere in this decode path, so a crafted `TxTypeAccountUpdate` (or fee-delegated variant) transaction containing deeply self-nested role-based keys will overflow the goroutine stack during RLP decoding — before any semantic/pool validation such as `CheckInstallable` ever runs.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` at [1](#0-0)  reads a list of RLP byte-blobs and, for each one, calls `rlp.DecodeBytes(b, &serializer)` where `serializer` is an `AccountKeySerializer`. `AccountKeySerializer.DecodeRLP` at [2](#0-1)  reads an attacker-controlled `AccountKeyType` byte and calls `NewAccountKey(serializer.keyType)` to instantiate the concrete key, then decodes into it. `NewAccountKey` at [3](#0-2)  maps `AccountKeyTypeRoleBased` back to a fresh `*AccountKeyRoleBased`, re-entering `AccountKeyRoleBased.DecodeRLP`.

Nothing in this call chain enforces the "composite key must not be nested" rule — that rule (`IsCompositeType()` check, `kerrors.ErrNestedCompositeType`) only exists in `CheckInstallable`/`CheckUpdatable` at [4](#0-3) , which runs *after* the key has already been fully decoded. There is also no depth counter or `runtime.debug`/`EnsureSufficientExecutionStack`-equivalent guard comparable to the safety nets described in the external Scriban report. An attacker can therefore craft a `TxTypeAccountUpdate` (or `TxTypeFeeDelegatedAccountUpdate*`) transaction whose new-key field is a chain of nested `AccountKeyRoleBased([AccountKeyRoleBased([AccountKeyRoleBased([...])])])` blobs. Because RLP list nesting is very size-efficient, a modestly sized transaction payload (well within normal transaction-size limits) can encode thousands of nesting levels, which is enough to exhaust the default Go goroutine stack during `Transaction.DecodeRLP`/`UnmarshalBinary`, which is invoked the moment any node (including via public RPC `eth_sendRawTransaction`/`sendRawTransaction`, or during p2p tx-pool propagation) attempts to decode the raw transaction bytes — i.e., prior to signature verification, `CheckInstallable`, or pool admission.

Because Go stack overflows from unbounded recursion crash the entire process (unlike Go's growable-stack recover for goroutine panics, an actual stack-overflow due to exceeding the maximum stack size is fatal and unrecoverable, printing `runtime: goroutine stack exceeds ... - fatal error: stack overflow` and terminating the process), this is a genuine process-crash analog to the Scriban `WriteValue()` finding: unbounded, attacker-controlled recursion with no depth limit anywhere in the call graph, reachable by a single crafted input from an unprivileged actor.

### Impact Explanation
Any Kaia node (RPC node, full node, or consensus node) that decodes a submitted raw transaction — via public RPC transaction submission or transaction propagation from peers — will attempt to fully RLP-decode the `AccountKeyRoleBased` structure before any semantic validation, gas checks, or pool admission occurs. A crafted single transaction can crash the receiving node process outright (unrecoverable `StackOverflow`-equivalent fatal error in Go), producing denial of service. If this transaction propagates through the p2p tx-pool broadcast mechanism (which relays syntactically well-formed but not yet fully-validated transactions), it could potentially crash multiple nodes across the network simultaneously — a severe availability impact for the chain.

### Likelihood Explanation
Exploitation requires no privileges beyond the ability to submit a transaction through any Kaia node's public transaction-submission RPC endpoint (`eth_sendRawTransaction`, `klay_sendRawTransaction`) — something any unprivileged sender can do. Constructing the nested-RLP payload is a mechanical exercise (encode `AccountKeyRoleBased` nested inside itself N times) and does not require a valid signature to reach the vulnerable decode path, since RLP decoding of the transaction body happens before signature verification. The only constraint is the maximum transaction size accepted by the node/RPC layer, but RLP list nesting achieves exponential-effort-to-attacker-cost ratio, so a payload comfortably under typical size limits (tens of KB) can encode a recursion depth sufficient to overflow a default goroutine stack.

### Recommendation
Add an explicit recursion-depth parameter/limit to `AccountKeyRoleBased.DecodeRLP` and `AccountKeySerializer.DecodeRLP` (e.g., reject decoding if depth exceeds 1, since role-based keys are documented as non-nestable — matching the existing `IsCompositeType`/`ErrNestedCompositeType` invariant that `CheckInstallable` enforces post-hoc). Alternatively, thread a `TemplateContext`-like depth counter through the RLP `Stream` for this call path and return an explicit decode error such as `kerrors.ErrNestedCompositeType` immediately upon encountering `AccountKeyTypeRoleBased` while already decoding within an `AccountKeyRoleBased`, instead of silently recursing. This enforces the "no composite type nesting" rule at decode time rather than only at installation/update-check time, closing the gap between the intended invariant and its actual enforcement point.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}

func NewAccountKey(t AccountKeyType) (AccountKey, error) {
	switch t {
	case AccountKeyTypeNil:
		return NewAccountKeyNil(), nil
	case AccountKeyTypeLegacy:
		return NewAccountKeyLegacy(), nil
	case AccountKeyTypePublic:
		return NewAccountKeyPublic(), nil
	case AccountKeyTypeFail:
		return NewAccountKeyFail(), nil
	case AccountKeyTypeWeightedMultiSig:
		return NewAccountKeyWeightedMultiSig(), nil
	case AccountKeyTypeRoleBased:
		return NewAccountKeyRoleBased(), nil
	}

	return nil, errUndefinedAccountKeyType
}
