### Title
`SignableTransaction::new` calculates the fee from the payment list while ignoring the OP_RETURN data output, underpaying the fee on every data-bearing transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The analog to "use `pricePerShare` instead of `balance` when computing withdrawal worth" is `SignableTransaction::new` computing a transaction's cost basis (the vbytes the fee is charged against) from `payments` alone, even though the constructed transaction also contains an OP_RETURN output carrying up to 80 bytes of caller-supplied data. The fee is therefore assessed against a stale/incomplete measure of the transaction — exactly the class of using a raw balance where the obligation-adjusted value (`pricePerShare`) is required — and every data-bearing transaction is signed paying a fee lower than the requested rate.

### Finding Description
`SignableTransaction::new` builds `tx_outs` in two steps: the payment outputs, then an OP_RETURN output if `data` is present (lines 188–202). It then computes the fee via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204), which reconstructs a template transaction containing **only** the payment outputs:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` (lines 62–127) builds its template `Transaction` purely from `payments` plus an optional change output; the `data`/`tx_outs` OP_RETURN output is never included. The same omission occurs in the change path at lines 225–227. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` is charged on a vsize that excludes the OP_RETURN output (~90+ weight units / ~23+ vbytes for 80 bytes of data plus output overhead).
- The minimum-relay-fee floor check (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`, line 211) is evaluated against the same understated `vbytes`, so a transaction can pass the `TooLowFee` check while its *actual* feerate is below the relay minimum.
- `needed_fee()` (line 133) misreports the fee the transaction will actually pay (`fee()` at line 138 correctly returns `sum(prevouts) - sum(outputs)`), so any caller accounting change as `inputs - payments - needed_fee` over-credits the change by `fee_per_vbyte * (vbytes_real - vbytes)`.

The user-supplied `data` (up to 80 bytes, checked at line 171) is a public input that directly controls the size of the understatement — analogous to a depositor influencing the obligation that `pricePerShare` should account for.

### Impact Explanation
Any `SignableTransaction` carrying an OP_RETURN output is signed with a fee rate strictly below `fee_per_vbyte`. In the worst case — `fee_per_vbyte` near the minimum relay boundary — the signed transaction falls below `DEFAULT_MIN_RELAY_TX_FEE` on its true vsize and is rejected by relay/mempool, leaving the multisig's funds locked in the signed-but-unbroadcastable transaction until a new plan is constructed and re-signed. Even when relayed, the transaction confirms slower than specified and `needed_fee()` returns a value that does not reflect the fee actually paid, corrupting downstream change/operating-cost accounting that trusts `needed_fee`. The discrepancy scales with caller-controlled `data` length.

### Likelihood Explanation
The bug triggers on every call that passes `Some(data)` — no adversarial timing or collusion required; the data field is attacker-influenced transaction content. Impact is capped at fee underpayment/relay failure rather than direct theft, so it is Medium: it produces transactions that fail to meet the caller-specified fee rate and can be unbroadcastable at low fee rates, a "funds reported/committed at an incorrect value" condition rather than a loss-of-funds primitive.

### Recommendation
Compute weight/vbytes from the actual output set, not just `payments`. Either pass `data` into `calculate_weight_vbytes` (pushing the OP_RETURN `TxOut` into the template), or construct the full `tx_outs` vector first and run `tx.weight()`/`get_virtual_tx_size` on the real transaction before finalizing output values. Apply the same fix in both fee computations (lines 204 and 225–227), and evaluate the `TooLowFee` floor against the data-inclusive vbytes.

### Proof of Concept
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` with any inputs, no payments, `change = None`, `data = Some(vec![0; 80])`, and `fee_per_vbyte` chosen so `fee_per_vbyte * vbytes` exactly equals the `DEFAULT_MIN_RELAY_TX_FEE` floor for the payment-only template:

1. `tx_outs` gains a ~91-weight-unit OP_RETURN output (line 195).
2. `vbytes` (line 204) is computed from an empty `payments` template — excluding the OP_RETURN — so `needed_fee` passes the line-211 floor check.
3. The returned `SignableTransaction.tx` is ~23 vbytes larger than measured; its real feerate is `needed_fee / real_vbytes < DEFAULT_MIN_RELAY_TX_FEE`, below relay minimum, and `needed_fee()` under-reports `fee()` by `fee_per_vbyte * 23+`.

The test at `networks/bitcoin/tests/wallet.rs:185-187` exercises `Some(vec![0; 80])` but only asserts `is_ok()`, never comparing `needed_fee()`/`fee()` against the real `tx.vsize()`, so the understatement is undetected. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
