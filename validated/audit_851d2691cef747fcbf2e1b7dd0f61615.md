### Title
Multi-token bribes beyond `rewardTokens()[0]` are transferred into `DelegateVoteRewardPool` but never queued, permanently freezing them - (File: `wombat/WombatBribeManager.sol`, `rewards/DelegateVoteRewardPool.sol`)

### Summary
`WombatBribeManager.claimAllBribes` only reports the first bribe reward token per pool (`rewardTokens[i] = ... rewardTokens()[0]`), yet the subsequent call `IBribeRewardPool(pool.rewarder).getReward(_for, _for)` executes `BaseRewardPool.getReward`, which loops over **all** registered `rewardTokens` of that pool's rewarder and transfers every one of them to `_for`. When `_for` is the `delegatedPool` (i.e. `DelegateVoteRewardPool`, reached through `WombatBribeManager.castVotes` → `IDelegateVoteRewardPool(delegatedPool).harvestAll()`), all bribe tokens beyond index 0 land physically in `DelegateVoteRewardPool`'s balance, but `harvestAll`/`_manageRewards` only queues the single (first) token that `claimAllBribes` reported, so the extra tokens are never added to `rewardTokens`/`rewards[token].rewardPerTokenStored` and can never be distributed via `getReward`.

### Finding Description
The path is:
1. Anyone (unprivileged EOA) calls `WombatBribeManager.castVotes(...)`, a public function with no access control [1](#0-0) .
2. At the end, if a `delegatedPool` is configured, it unconditionally calls `IDelegateVoteRewardPool(delegatedPool).harvestAll()` [2](#0-1) .
3. `DelegateVoteRewardPool.harvestAll()` calls back into `claimAllBribes(address(this))` and then feeds the returned arrays into `_manageRewards` [3](#0-2) .
4. Inside `claimAllBribes`, for every active pool the reported reward token is hard-coded to the bribe contract's **first** token only: `rewardTokens[i] = address(IWombatBribe(bribesContract).rewardTokens()[0])`, and `earnedRewards[i]` is computed only for that token [4](#0-3) .
5. However, the actual payout call `IBribeRewardPool(pool.rewarder).getReward(_for, _for)` executes `BaseRewardPool.getReward`, which iterates over **all** entries in that rewarder's `rewardTokens` array and transfers every earned token to `_for` [5](#0-4) .
6. Because `_for == address(this) == delegatedPool` in this flow, every bribe token beyond index 0 is physically transferred into `DelegateVoteRewardPool`'s balance, but `claimAllBribes` never reported them, so `_manageRewards` (which only processes the tokens/amounts it receives) never calls `_queueNewRewardsWithoutTransfer` for them [6](#0-5) [7](#0-6) .
7. Since these tokens were never pushed into `rewardTokens`/`rewards[token]` for `DelegateVoteRewardPool`, `getReward(address _for)`/`_getDelegateReward` (which only iterates `DelegateVoteRewardPool`'s own `rewardTokens` array) can never distribute them [8](#0-7) . The tokens sit in the contract forever with no rescue mechanism visible in this contract.

No modifier, reentrancy guard, or reward-index update prevents this — it's a pure array/reporting mismatch between what `claimAllBribes` returns and what `BaseRewardPool.getReward` actually moves.

Note: the framing in the question that ties this to `votingWeights[pool]`/`totalWeight` consistency with `_updateVote` deltas does not correspond to any real code path — `votingWeights`/`totalWeight` are only mutated by the owner-only `updateWeight` and are unrelated to token accounting. The genuine, verifiable defect is the token-count mismatch between `claimAllBribes` and the underlying `BaseRewardPool.getReward` transfer loop described above.

### Impact Explanation
Any pool whose Wombat bribe contract registers more than one reward token will have all non-first bribe tokens accrued by the delegated pool permanently stranded in `DelegateVoteRewardPool`'s balance once `castVotes` triggers `harvestAll`. These tokens are never added to the reward index and there is no admin/rescue function shown in `DelegateVoteRewardPool` to recover them, so they are permanently unclaimable by the pool's voters/stakers — matching "Permanent freezing of unclaimed yield" (High).

### Likelihood Explanation
- No privileged role is required: `castVotes` is `public` and callable by any EOA (it even pays the caller a fee for gas costs) [9](#0-8) .
- The only precondition is that a `delegatedPool` is configured and at least one pool it voted for has a bribe contract with more than one registered reward token — a realistic configuration on Wombat, not a misconfiguration of this protocol.
- The bug reproduces every time `castVotes`/`harvestAll` runs against such a pool, so it is fully repeatable and requires no capital from the attacker.

### Recommendation
Make `claimAllBribes` (and `harvestAll`'s handling of it) enumerate and report **all** reward tokens returned by each bribe contract, not just index 0, e.g. loop over `IWombatBribe(bribesContract).rewardTokens()` fully and collect earned amounts for each into the returned arrays; alternatively, have `DelegateVoteRewardPool._manageRewards`/`harvestAll` read the destination pool rewarder's full `rewardTokens()` list directly (via `rewardTokenInfos()`) instead of relying on `claimAllBribes`'s truncated report, ensuring every token physically transferred is also queued into the reward index.

### Proof of Concept
Hardhat plan:
1. Deploy `WombatBribeManager`, a mock Wombat `voter`/bribe contract that registers 2 reward tokens (`tokenA`, `tokenB`) for a pool `lpX`, and `DelegateVoteRewardPool` as `delegatedPool`.
2. Configure `delegatedPool.updateWeight(lpX, weight)` (owner-only setup step, not part of the attack) so the delegate pool votes for `lpX`.
3. Have a staker call `DelegateVoteRewardPool.stakeFor` (via the operator) to generate a non-zero `userVotedForPoolInVlmgp[delegatedPool][lpX]`.
4. Seed the bribe contract so that both `tokenA` and `tokenB` accrue non-zero `earned` amounts for `delegatedPool`.
5. From an unprivileged EOA, call `WombatBribeManager.castVotes(false)`.
6. Assert: `tokenB.balanceOf(delegatedPool) > 0` (physically received) while `DelegateVoteRewardPool.isRewardToken(tokenB) == false` and `DelegateVoteRewardPool.rewards(tokenB).rewardPerTokenStored == 0` — proving `tokenB` is stuck and unqueued.
7. Call `DelegateVoteRewardPool.getReward(staker)` and confirm the staker never receives any `tokenB`, only `tokenA`, even though `tokenB.balanceOf(delegatedPool)` remains unchanged and positive — demonstrating permanent freezing of the yield.

    function _queueNewRewardsWithoutTransfer(
        uint256 _amountReward,
        address _rewardToken
    ) internal {
        if (!isRewardToken[_rewardToken]) {
            rewardTokens.push(_rewardToken);
            isRewardToken[_rewardToken] = true;
        }
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (totalSupply == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10 ** this.stakingDecimals()) /
                totalSupply;
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
