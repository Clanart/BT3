### Title
Untrusted `ReceivedOutput` bytes can claim unspendable Bitcoin outputs are spendable - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput::read` deserializes a scalar offset, `TxOut`, and `OutPoint`, but never checks that the offset derives the scanned script or that the outpoint identifies an output carrying that script. Because `ReceivedOutput` represents a spendable output, crafted bytes can inject a false spendability claim into any caller trusting this decoder. [1](#0-0) 

### Finding Description
`Scanner` maintains the only binding between spendable `script_pubkey`s and their private scalar offsets. [2](#0-1)  Legitimate outputs are produced by matching a transaction output’s `script_pubkey` against that map. [3](#0-2) 

The decoder bypasses that invariant. It accepts any canonical scalar followed by any consensus-decodable `TxOut` and `OutPoint`, then constructs `ReceivedOutput` without calling `p2tr_script_buf`, checking `self.key + offset * G`, or looking up the script in a `Scanner`. [4](#0-3)  A remote party therefore can encode a known/registered offset with an unrelated script, unrelated value, or nonexistent outpoint and have the result represented as a spendable wallet output.

### Impact Explanation
A caller that stores, relays, synchronizes, or otherwise accepts serialized `ReceivedOutput` values can be induced to report attacker-selected Bitcoin outputs as owned and spendable. The recorded offset will not authorize spending an unrelated `script_pubkey`, producing the accepted “funds reported received that are not spendable” impact and potentially causing wallet/accounting state to select inputs that can never be signed successfully.

### Likelihood Explanation
The attack requires a path where an unprivileged party controls bytes passed to `ReceivedOutput::read`. In that threat model, exploitation is deterministic: no malformed primitive encoding is needed, only a validly encoded scalar, `TxOut`, and `OutPoint` whose semantic relationship was never established by `Scanner::scan_transaction`. Callers that only deserialize locally generated scanner results are not exposed through this path.

### Recommendation
Do not expose `ReceivedOutput::read` as an unauthenticated constructor for supposedly spendable outputs. Either:

- require a `Scanner`/public key context during deserialization and verify `output.script_pubkey` equals the script registered for `offset`, or
- rename/split the API so untrusted bytes deserialize to an unverified candidate and become a `ReceivedOutput` only through `Scanner::scan_transaction` or an equivalent validation routine.

The validation should recompute or look up `p2tr_script_buf(key + offset * G)` and compare it to `output.script_pubkey`. Outpoint existence and transaction confirmation still need to be established from trusted chain data.

### Proof of Concept
```rust
// Constructed for any registered offset and an unrelated output.
let mut encoded = Vec::new();
encoded.extend(registered_offset.to_bytes());

let forged_output = TxOut {
    value: Amount::from_sat(100_000),
    script_pubkey: attacker_controlled_script, // not Scanner::scripts[registered_offset]
};
encoded.extend(bitcoin::consensus::encode::serialize(&forged_output));

let forged_outpoint = OutPoint::new(attacker_selected_txid, 0);
encoded.extend(bitcoin::consensus::encode::serialize(&forged_outpoint));

let received = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();
assert_eq!(received.offset(), registered_offset);
assert_eq!(received.output().script_pubkey, attacker_controlled_script);
```

`ReceivedOutput::read` accepts this object because it only checks encoding validity; it does not establish the offset-to-script ownership invariant used by `Scanner`.

    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
