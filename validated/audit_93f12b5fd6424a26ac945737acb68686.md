### Title
`Interceptors::Noop` completely skips the `is_internal` self-only gate, letting anyone call `InternalSendTx` - ([File: core/src/rpc/interceptors.rs])

### Summary
`only_aggregator_and_self` enforces that RPC methods whose gRPC method name starts with `Internal` (checked via `is_internal`) may only be called by a peer presenting `our_cert` (self), but this check is only reached through the `OnlyAggregatorAndSelf` interceptor variant. `core/src/servers.rs` installs `Interceptors::Noop` instead whenever `config.client_verification` is `false`, and `Noop::call` returns `Ok(req)` unconditionally without ever invoking `is_internal` or checking any certificate, so the self-only restriction on `Internal*` methods such as `ClementineAggregator::internal_send_tx` is bypassed entirely.

### Finding Description
The intended binding is: `caller_of(internal_send_tx) == our_cert` (self), enforced in `only_aggregator_and_self` at [1](#0-0) .

That check is only reached from the `OnlyAggregatorAndSelf` match arm of `Interceptor::call`: [2](#0-1) 

`core/src/servers.rs` selects which interceptor variant to install based purely on `config.client_verification`: [3](#0-2) 

When `config.client_verification == false`, `Noop` is installed for the aggregator's gRPC server, and `Interceptors::Noop => Ok(req)` never calls `is_internal` or inspects `peer_certs()` at all [4](#0-3) . This means the `Internal*` naming convention that `is_internal` relies on (`path.as_bytes().starts_with(b"Internal")`, [5](#0-4) ) provides zero protection under `Noop`; any caller reaching the aggregator's public gRPC port can invoke `internal_send_tx` (confirmed present on `ClementineAggregator` per `core/src/rpc/aggregator.rs`) exactly as if they were `our_cert`.

The code itself acknowledges the aggregator is normally reachable without client verification — `create_aggregator_grpc_server` logs a warning only when verification is *enabled* (`"Client verification is enabled on aggregator gRPC server"`, [6](#0-5) ), implying the aggregator's typical/expected deployment posture is public-facing with `client_verification=false` for its ordinary (non-internal) RPCs. In that common configuration, the `Internal*` prefix carries no actual authorization weight, since there is no separate authentication layer independent of the interceptor's certificate check.

### Impact Explanation
Any unauthenticated caller who can reach the aggregator's gRPC port can invoke `internal_send_tx`, which forwards a transaction to the aggregator's tx-sender queue for broadcast/fee-bumping — this is an unauthenticated state-changing/broadcasting call on the aggregator's own infrastructure. This matches the High severity category "an unauthenticated state-changing or broadcasting call" explicitly listed in scope. The exact downstream consequences of what `internal_send_tx` allows to be queued (arbitrary attacker-supplied transactions consuming the aggregator's fee-bumping wallet, or interfering with legitimate queued sends) could not be fully confirmed here because the implementation body of `internal_send_tx` was not visible within the retrieved portion of `core/src/rpc/aggregator.rs` (file is 2691 lines; the tool output was truncated at line 1000 before reaching this handler). This is repeatable per request with no rate limit tied to authentication (rate limiting itself is out of scope per the rules).

### Likelihood Explanation
This requires the aggregator to be deployed with `config.client_verification = false`. Based on the code's own warning message structure (warning fires only when verification is *enabled*), this is presented as the normal/expected aggregator configuration rather than a rare misconfiguration, since the aggregator is meant to accept public, non-mTLS client calls for ordinary bridge operations. Under that deployment, the attack costs nothing beyond network access to the gRPC port — no BTC, no fees, no credentials.

### Recommendation
Do not rely solely on the interceptor/certificate layer to gate `Internal*` methods. Either (a) always run the `is_internal` name-prefix check regardless of which `Interceptors` variant is active (i.e., check it unconditionally in `Interceptor::call` before dispatching to `Noop` or `OnlyAggregatorAndSelf`, and reject any `Internal*` call under `Noop`), or (b) enforce a separate, independent authentication mechanism for `Internal*` methods (e.g., a shared secret or loopback-only binding) that does not depend on `config.client_verification`.
