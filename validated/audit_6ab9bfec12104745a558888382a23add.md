### Title
`resolveWithin` uses a bare `startsWith` prefix check, allowing escape into sibling directories that share a name prefix - (File: `app/src/lib/path.ts`)

### Summary
`_resolveWithin` in `app/src/lib/path.ts` is the shared guard used across GitHub Desktop to make sure a path derived from untrusted input (a deep-link `filepath` parameter, a repository-relative path, etc.) never resolves outside of a given root directory. The final check is a plain string `startsWith` comparison with no path-separator boundary, so a resolved path in a *sibling* directory that merely shares the root directory's name as a prefix (e.g. `…/myrepo-secret` vs root `…/myrepo`) is incorrectly treated as "inside" the root.

### Finding Description
`_resolveWithin` computes `realRoot` and `realResolved` via `realpath()` and then allows the path through if: [1](#0-0) 

This is a classic prefix-boundary bug: `String.prototype.startsWith` has no concept of path segments. If `realRoot` is `/Users/victim/Documents/GitHub/repo` and an attacker-influenced path resolves (after `realpath`) to `/Users/victim/Documents/GitHub/repo-secrets/token.txt`, the check `realResolved.startsWith(realRoot)` is `true` even though `repo-secrets` is a completely different, sibling directory. The function was clearly designed to prevent exactly this kind of containment bypass (it already handles `..` traversal and symlinks, see the null-byte and symlink checks around it), but it omits the one guard that matters most: requiring `realResolved === realRoot` or `realResolved.startsWith(realRoot + Path.sep)`.

Notably, the codebase already recognizes this exact class of bug and fixes it correctly in a sibling function, `isClonePathSensitive` in `app/src/lib/git/clone.ts`, which explicitly checks `clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)` — i.e., the fix pattern exists in the code but was not applied to `resolveWithin`, which is used more broadly: [2](#0-1) 

`resolveWithin` is used to sanitize attacker-influenceable paths in multiple security-sensitive call sites, including opening a file from a GitHub Desktop deep link (`x-github-client://openRepo/...&filepath=...`), where the `filepath` comes directly from a URL that the user is enticed to click: [3](#0-2) 

It is also used in `app/src/lib/copilot-conflict-context.ts` and `app/src/lib/stores/app-store.ts` to bound paths derived from repository content.

The existing regression tests for `resolveWithin` cover `..` traversal, null bytes, and symlink traversal, but do not cover the sibling-directory-prefix case, so this gap is not caught: [4](#0-3) 

### Impact Explanation
An attacker who controls a GitHub Desktop deep link (`x-github-client://openRepo/...`) that a user clicks can supply a `filepath` value that, once joined to an opened repository's root and resolved, lands in a sibling directory whose name is prefixed by the repository directory's name (e.g., a repository cloned to `.../GitHub/desktop` alongside a directory `.../GitHub/desktop-secrets` or `.../GitHub/desktop.bak`). `resolveWithin` would incorrectly treat this as "inside" the repository and `dispatcher.ts` would call `shell.showItemInFolder(resolved)` on the out-of-bounds path — revealing/opening files the user did not intend to expose via a link click. Because `resolveWithin` is the general containment primitive used elsewhere for repository-relative path handling, any other caller relying on it for security containment is subject to the same sibling-directory bypass. This matches the "Valid Impact" criteria: the attacker controls a link the user clicks, and the result is a file read/open outside the intended repository root, without needing local/physical access, admin rights, or prior malware.

### Likelihood Explanation
Exploitability requires the victim to have (or an attacker to be able to induce) a directory structure where a sibling of the target repository shares its name as a literal prefix — this is a real but not universal condition (e.g., users who clone forks/backups side-by-side, such as `repo` and `repo-old`, `repo` and `repo.bak`, or an attacker who can first get the user to clone a maliciously-named repo like `victimrepo-attacker-controlled` next to `victimrepo`). Given GitHub Desktop's default behavior of cloning repos by name into a common parent folder (e.g., `~/Documents/GitHub/<repo-name>`), such prefix collisions are plausible in practice (case in point: repos named `x` vs `x-archive`, or an attacker-authored repo intentionally cloned with a name that is a prefix of a legitimate repo the user already has).

### Recommendation
Change the final containment check in `_resolveWithin` (`app/src/lib/path.ts`, line 71) from:
```ts
return realResolved.startsWith(realRoot) ? resolved : null
```
to a boundary-aware comparison, mirroring the fix already applied in `isClonePathSensitive`:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the appropriate `sep` for the `options` variant — `Path.sep`, `Path.posix.sep`, or `Path.win32.sep`). Add a regression test asserting that a sibling directory sharing the root's name as a prefix (e.g., root `/tmp/foo`, target realpath `/tmp/foobar`) is rejected.

### Proof of Concept
1. Set up two directories: `/Users/victim/Documents/GitHub/repo` (the trusted repository root) and `/Users/victim/Documents/GitHub/repo-secrets/token.txt` (attacker's target, sibling dir sharing the `repo` prefix).
2. Craft a deep link: `x-github-client://openRepo/https://github.com/owner/repo?filepath=../repo-secrets/token.txt` (or any relative path construction that, after `Path.resolve`/`realpath`, lands in `repo-secrets`).
3. When the victim clicks the link, `openRepositoryFromUrl` in `dispatcher.ts` calls `resolveWithin(repository.path, filepath)` with `repository.path = /Users/victim/Documents/GitHub/repo`.
4. Inside `_resolveWithin`, `realResolved` becomes `/Users/victim/Documents/GitHub/repo-secrets/token.txt`, and `realRoot` is `/Users/victim/Documents/GitHub/repo`. The check `realResolved.startsWith(realRoot)` evaluates to `true` (string prefix match) even though `repo-secrets` is a different directory.
5. `resolveWithin` returns the out-of-repo path instead of `null`, and `dispatcher.ts` calls `shell.showItemInFolder(resolved)`, revealing the file to the user via the OS file manager — a containment bypass triggered purely by clicking a link. [5](#0-4) [6](#0-5)

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```

```typescript
  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }
```

```typescript
  describe('resolveWithin', () => {
    const root = process.cwd()

    it('fails for paths outside of the root', async () => {
      assert((await resolveWithin(root, join('..'))) === null)
      assert((await resolveWithin(root, join('..', '..'))) === null)
    })

    it('succeeds for paths that traverse out, and then back into, the root', async () => {
      assert.equal(await resolveWithin(root, join('..', basename(root))), root)
    })

    it('fails for paths containing null bytes', async () => {

    })
```
