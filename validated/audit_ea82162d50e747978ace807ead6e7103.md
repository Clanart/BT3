### Title
Instant vote-then-harvest allows attackers to steal a share of already-accrued bribe yield from long-term voters - ([File: wombat/WombatBribeManager.sol])

### Summary
`vote()` immediately calls `IBribeRewardPool(pool.rewarder).stakeFor()`, which increases the attacker's `balanceOf()` in `BribeRewardPool` before any bribe is harvested. Because `BribeRewardPool`/`BaseRewardPoolV2` use a Synthetix-style `rewardPerTokenStored` accounting model with no checkpoint delay or minimum holding period, calling `harvestSinglePool()` right after voting causes the freshly harvested bribe (which accrued to the pool's real Wombat vote weight over the *entire prior period*) to be distributed pro-rata based on the *current* `totalStaked()`/`balanceOf()`, rewarding the attacker for a balance they only held for one block.

### Finding Description
1. `vote(_lps, _deltas)` in `wombat/WombatBribeManager.sol` (lines 182-220) updates `userVotedForPoolInVlmgp` and calls `IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, uint256(delta))` [1](#0-0) . Note this function never touches the real Wombat voter contract - it only updates internal MGP-side bookkeeping and the reward-pool share balance.
2. `BribeRewardPool.stakeFor` (via `updateRewards` modifier in `rewards/BaseRewardPoolV2.sol` lines 107-120) snapshots the caller's pre-stake reward-per-token checkpoint, then increases `_balances[_for]` and `totalSupply` immediately [2](#0-1) .
3. `harvestSinglePool(_lps)` casts a zero-delta vote on-chain via `wombatStaking.vote(_lps, votes, rewarders, address(0))` with all `votes[i] = 0` [3](#0-2) . This still triggers `voter.vote()` inside `WombatStaking.vote`, which harvests all bribes that accrued to the pool's actual on-chain vote weight since the last cast, and forwards them via `IBaseRewardPool(_rewarders[i]).queueNewRewards(rewardAmount, token)` [4](#0-3) .
4. `queueNewRewards` → `_provisionReward` increases `rewardPerTokenStored` by `(_amountReward * 10**decimals) / totalStaked()`, where `totalStaked()` is the pool's *current* `totalSupply`, which already includes the attacker's just-added stake `X` [5](#0-4) .
5. Since the attacker's `userRewardPerTokenPaid` checkpoint was taken *before* this increment (step 2), calling `claimBribe([lp])` computes `earned = userShare * (rewardPerTokenStored_new - userRewardPerTokenPaid_old) / 1e18`, crediting the attacker with a full pro-rata share of the newly harvested bribe pool, proportional only to the size of their stake at the moment of harvest, not to how long they held it [6](#0-5) .
6. `unvote(_lp)` then lets the attacker withdraw `X` immediately with no cooldown or lockup, restoring their vlMGP capacity [7](#0-6) .

There is no time-weighted accrual, minimum staking duration, or reward-vesting mechanism to prevent this: `updateRewards`/`_updateFor` only checkpoint balances at stake/withdraw/claim time and rewards are distributed strictly by instantaneous share of `totalStaked()` at the time `queueNewRewards` is called. `harvestSinglePool` is explicitly documented as callable by anyone ("this function has a lesser importance... hence no rewards will be given to the caller") with no access control beyond that, and does not require the caller to have any existing vote on the pool.

### Impact Explanation
This directly dilutes and steals a portion of already-accrued but unclaimed bribe yield that rightfully belongs to voters who held their vote for the full accrual period. The attacker with `X` vlMGP (already locked, just reallocated) can capture `X / totalStakedAtHarvest` share of the whole bribe drop instantly, at the expense of long-term voters' pro-rata share, matching Immunefi's "theft of unclaimed yield" impact class.

### Likelihood Explanation
- Preconditions: attacker only needs spare (already-locked) vlMGP capacity — no flash loan or special privilege is required, since `vote()` checks `userTotalVotedInVlmgp[msg.sender] <= getUserVotable(msg.sender)` against total locked MGP, not newly acquired capital.
- `harvestSinglePool` is a public, unprivileged function by design.
- The whole sequence (`vote` → `harvestSinglePool` → `claimBribe` → `unvote`) can be executed in a single transaction/bundle or across consecutive blocks with front-running, making it highly repeatable and low-cost (only gas).
- The larger the pending unharvested bribe and the smaller the existing `totalStaked()` on that pool's `BribeRewardPool`, the more profitable the attack, so it is more severe for smaller/less-active pools.

### Recommendation
Implement time-weighted reward accrual (e.g., checkpoint-based streaming of rewards over a minimum vesting window, or a minimum staking duration before a balance counts toward `queueNewRewards` distributions) so newly staked balances cannot immediately claim a share of rewards that accrued before the stake was placed. Alternatively, only allow reward accrual proportional to `balanceOf` at the time of the *previous* harvest snapshot, or add a cooldown between `vote()`/`unvote()` and `harvestSinglePool`/`claimBribe` for the same address to prevent same-window flash-vote extraction.

### Proof of Concept
Foundry test plan:
1. Deploy `WombatBribeManager`, `WombatStaking`, `BribeRewardPool`, and mocks for `IWombatVoter`/`IVeWom` that simulate pending bribe accrual proportional to elapsed blocks since last `vote()` call on a given lp.
2. Setup: Control voter `Alice` locks MGP, calls `vote(lp, +X)` and holds for `N` blocks (simulating long-term voting) while bribes accrue in the mock voter.
3. Attacker `Bob` (holding spare locked vlMGP) calls, in the block right before harvest: `vote(lp, +X)` (same `X` as Alice) via `WombatBribeManager`.
4. Bob calls `harvestSinglePool([lp])`, triggering `wombatStaking.vote` → mock bribe harvest → `queueNewRewards` on `BribeRewardPool`.
5. Bob calls `claimBribe([lp])` and records `bobReward`.
6. Alice calls `claimBribe([lp])` and records `aliceReward`.
7. Bob calls `unvote(lp)` to fully exit.
8. Assert `bobReward` is non-trivial (roughly `X / (X_alice + X_bob) * totalHarvested`), despite Bob holding the position for only one block versus Alice's `N` blocks — demonstrating that reward split is based purely on stake-at-harvest-time, not accrual-weighted-by-duration, confirming the yield theft from Alice's rightful share.

    function harvestSinglePool(address[] calldata _lps) public {
        uint256 length = _lps.length;
        int256[] memory votes = new int256[](length);
        address[] memory rewarders = new address[](length);
        for (uint256 i; i < length; i++) {

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
