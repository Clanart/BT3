### Title
PedPoP encrypted secret shares are not bound to their intended recipient, allowing a relaying party to frame an honest participant as faulty - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2023-2002 is a missing authorization check enabling an unprivileged party to issue privileged operations. The analog in Serai is a missing *recipient* check in the PedPoP DKG's encrypted share messages: the proof-of-possession challenge `pop_challenge` binds the `sender` index and the ciphertext, but never binds the intended `decryptor`, and decryption only verifies knowledge of the ephemeral key — not that the ciphertext was actually addressed to the local party's encryption key.

### Finding Description
`encrypt` signs a Schnorr PoP over `pop_challenge(context, pub_nonce, pub_key, from, msg)` — the transcript commits to `sender` and `message` only (crypto/dkg/pedpop/src/encryption.rs:302-324, 159-167). Neither `Encryption::decrypt` (encryption.rs:469-501) nor `Decryption::decrypt_with_proof` (encryption.rs:366-397) verifies that the ECDH was formed with *this* decryptor's registered `enc_key`; any `EncryptedMessage` with a valid PoP is accepted for any `from`.

Concretely, in `KeyMachine::calculate_share` (crypto/dkg/pedpop/src/lib.rs:476-492), whatever `EncryptedMessage` is present in the `shares` map under sender `l` is decrypted using the local `enc_key`. The share-verification statements then fail and the local machine emits a blame proof (`EncryptionKeyProof` revealing the ECDH shared key). In `blame_internal` (lib.rs:581-609), a message that PoP-verifies but decrypts to an invalid scalar/share is adjudicated as `sender` faulty.

A routing party (the coordinator/tributary layer that distributes the `HashMap<Participant, EncryptedMessage>` maps) can therefore take the ciphertext Alice honestly produced *for Bob* and deliver it to Carol's machine as Alice's share for Carol. Carol's PoP check passes (sender and ciphertext are unmodified), decryption under Carol's `enc_key` yields garbage, share verification fails, and every `BlameMachine`/`AdditionalBlameMachine` evaluating the accusation will return `sender` (Alice) — an honest participant is conclusively blamed for sending an invalid share, while the actual fault (misdelivery by the relayer) is undetectable. No code checks that `msg.key * enc_key_i` corresponds to the intended recipient because the intended recipient is never committed to.

### Impact Explanation
In Serai's deployment, PedPoP blame maps to fatal slashing of validators (`ProcessorMessage::InvalidShare`/`Blame` in key_gen). A single relayer can frame an arbitrary honest participant as faulty for a share that participant correctly generated and correctly encrypted — the participant has no recourse because the blame proof cryptographically "proves" decryption of *their* message under a different recipient's key fails. This enables unauthorized, indisputable misattribution of fault (integrity/availability impact), mirroring the CVE's "unauthorized execution of management commands" class: a missing binding check lets a party trigger a privileged adjudication outcome it should not be able to cause.

### Likelihood Explanation
Any party able to control or reorder the delivered `shares` map (coordinator, or a participant that also relays) can perform this with only public ciphertexts — no secret keys, collusion, or threshold corruption needed. The attack works deterministically whenever an honest dealer sends distinct encrypted shares to multiple recipients.

### Recommendation
Bind the intended recipient into the message: add the decryptor's `Participant` index (or registered `enc_key`) to `pop_challenge` in `encrypt`/`decrypt`/`decrypt_with_proof`, and include it in the DLEq transcript context in `encryption_key_transcript`. Then `decrypt_with_proof` can reject messages not addressed to `decryptor`, and `blame_internal` can attribute misdelivery to the submitter rather than the sender.

### Proof of Concept
1. Run `KeyGenMachine::generate_coefficients` for participants 1 (Alice), 2 (Bob), 3 (Carol), n=3, t=2.
2. Alice calls `generate_secret_shares`; take `res[Bob]` — the `EncryptedMessage` Alice produced for Bob's `enc_key`.
3. Deliver to Carol's `KeyMachine::calculate_share` a `shares` map where Alice's entry is the Alice→Bob ciphertext.
4. Carol's `encryption.decrypt` queues the PoP (valid — sender and ciphertext unmodified), decrypts to garbage; the `BatchId::Share` statement fails and `PedPoPError::InvalidShare { participant: Alice, blame: Some(..) }` is returned with a valid `EncryptionKeyProof`.
5. Any `BlameMachine::blame(Alice, Carol, msg, proof)` or third-party `AdditionalBlameMachine::new(...).blame(...)` returns `Alice`, confirming honest Alice is cryptographically blamed for a correctly formed share.
