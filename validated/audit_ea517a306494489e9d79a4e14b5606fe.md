### Title
`WombatStaking.depositLP()` mints receipt tokens 1:1 based on input amount instead of actual LP received, breaking accounting for fee-on-transfer / deflationary LP tokens - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking.depositLP()` transfers the wombat pool LP token from the caller and then mints the same amount of receipt token, without measuring how much LP was actually received by the contract. This is inconsistent with the sibling `deposit()` function in the very same contract, which correctly computes the received amount via a before/after balance diff before minting/forwarding it. If the underlying LP token does not transfer exactly the requested amount (fee-on-transfer, deflationary, or any non-standard ERC20 behavior), the receipt token supply becomes over-minted relative to the LP actually custodied by `WombatStaking`.

### Finding Description
`deposit()` correctly guards against amount mismatches: [1](#0-0) 

But `depositLP()`, called right after it, uses the raw input `_lpAmount` for both the reward-triggering stake and the receipt token mint, with no balance verification: [2](#0-1) 

This function is reachable by any ordinary wallet through the pool helpers, e.g. `WombatPoolHelper.depositLP()` / `AnkrBNBPoolHelper.depositLP()`, which simply forward the user-supplied `_lpAmount` and then stake whatever the *receipt token* balance changed by: [3](#0-2) 

Note that the helper-level balance-diff check only measures the `receiptToken` (`stakingToken`) balance, which is minted deterministically as exactly `_lpAmount` inside `WombatStaking.depositLP()` — it does not detect any shortfall that occurred in the underlying LP `safeTransferFrom` call. The actual amount of underlying LP received by `WombatStaking` is never checked against `_lpAmount` before minting the receipt token, so the helper-level check cannot compensate for it.

### Impact Explanation
If any registered wombat pool's LP/Asset token behaves in a non-standard way and delivers less than `_lpAmount` on `transferFrom` (fee-on-transfer, rebasing, deflationary), `WombatStaking` mints receipt tokens for the shortfall amount that is not backed by actual LP holdings. Since receipt tokens back `MasterMagpie` staking positions and are burned 1:1 on withdrawal to redeem underlying LP tokens (`withdraw()` / `burnReceiptToken()`), an unbacked receipt-token supply results in later withdrawers being unable to redeem their full share — i.e., protocol insolvency for that pool, since the contract no longer holds enough LP to honor all outstanding receipt tokens.

### Likelihood Explanation
Likelihood depends on whether an LP token registered for a Wombat pool ever exhibits a fee/deflationary transfer, which is not the case for the standard Wombat `Asset.sol` LP token today. However, the deposit path is fully permissionless and reachable by any wallet with no other precondition, and the code contains a demonstrable inconsistency versus the correctly-guarded `deposit()` function in the same contract, making this a code-level correctness/robustness defect matching the reported bug class exactly.

### Recommendation
Mirror the pattern already used in `deposit()`: capture `IERC20(poolInfo.lpAddress).balanceOf(address(this))` before and after `safeTransferFrom` in `depositLP()`, and use the resulting diff (not the raw `_lpAmount` parameter) for both `_toMasterWomAndSendReward` and the `IMintableERC20(...).mint(...)` call.

### Proof of Concept
1. Governance registers a pool whose `lpAddress` token charges a transfer fee (e.g. 1%).
2. User calls `WombatPoolHelper.depositLP(1000)`, which calls `WombatStaking.depositLP(lpToken, 1000, user)`.
3. `IERC20(lpAddress).safeTransferFrom(user, address(this), 1000)` only delivers 990 LP tokens to `WombatStaking` due to the fee.
4. `WombatStaking` still mints `1000` receipt tokens to the caller (`msg.sender` = pool helper), which the helper stakes 1000 (as measured by receipt-token balance diff, since minting is exact) on behalf of the user into `MasterMagpie`.
5. Repeating deposits increases receipt-token/staked balance beyond the actual LP the contract holds; when users withdraw pro-rata to their receipt token holdings, the pool runs out of real LP before all receipt tokens can be redeemed. [2](#0-1) [4](#0-3)
