### Title
Excess `msg.value` is never refunded in `MultiSender.batchTransferEqualAmount`/`batchTransfer` - (File: contracts/src/MultiSender.sol)

### Summary
`MultiSender.sol` exposes two `payable` batch-transfer entry points, `batchTransferEqualAmount` and `batchTransfer`, that only check `msg.value >= totalAmount` before distributing funds to recipients. Neither function returns, tracks, or refunds any amount the caller sent above the computed `totalAmount`.

### Finding Description
In `batchTransferEqualAmount`, `totalAmount = amount * recipients.length` is computed and checked with `require(msg.value >= totalAmount, ...)`, then exactly `totalAmount` (via per-recipient `amount`) is disbursed to recipients — any `msg.value` above `totalAmount` remains permanently in the `MultiSender` contract's balance with no withdrawal or refund mechanism. [3](#0-2) 
The same pattern repeats in `batchTransfer`, where `totalAmount` is the sum of the `amounts` array; the `>=` check permits overpayment, and again only `totalAmount` is distributed while the excess is stranded in the contract. [4](#0-3) 
This mirrors exactly the Footium `mintPlayers` bug class cited in the report: a `payable` function that checks `msg.value` is *at least* the required amount but never returns the difference to the caller. Because `MultiSender` has no `withdraw`, `sweep`, or fallback-refund logic anywhere in the contract, any excess ETH sent to it is unrecoverable by the sender (it is only reachable by whoever can call the contract's other functions — none exist here).

### Impact Explanation
Any external account or contract that calls either batch function with `msg.value` greater than the exact required total permanently loses the difference — the funds sit in the `MultiSender` contract with no code path to retrieve them. This is a direct, permanent loss of user funds reachable by any unprivileged EVM transaction sender who miscalculates or over-supplies `msg.value` (e.g., due to rounding, UI estimation, or intentionally batching a buffer for gas/slippage margin as is common practice in many multisender UIs).

### Likelihood Explanation
Likelihood is meaningful because `>=` (not `==`) is used deliberately as the guard, which invites callers to send a buffer above the exact total (a common pattern to avoid "insufficient funds" reverts from off-by-one calculation), directly triggering the loss on the very first use. No malicious actor or special conditions are required — a single normal transaction from a legitimate but slightly overpaying user triggers permanent fund loss.

### Recommendation
Change the `require` checks to `msg.value == totalAmount` to reject overpayment outright, or, if `>=` is intentionally retained for UX buffering, add a refund step after the distribution loop that returns `msg.value - totalAmount` to `msg.sender` (mirroring the Footium `mintPlayers` fix), e.g.:
```solidity
uint256 refund = msg.value - totalAmount;
if (refund > 0) {
    (bool refunded, ) = msg.sender.call{value: refund}("");
    require(refunded, "Failed to refund excess ETH");
}
```

### Proof of Concept
1. Caller invokes `MultiSender.batchTransfer(recipients, amounts)` with `msg.value = totalAmount + 1 wei` (or any positive excess). [5](#0-4) 
2. The `require(msg.value >= totalAmount, ...)` check passes since `msg.value > totalAmount`.
3. The loop sends exactly `amounts[i]` to each recipient, totaling `totalAmount`. [6](#0-5) 
4. The transaction completes successfully; the leftover `msg.value - totalAmount` remains in the `MultiSender` contract's balance.
5. No function in the contract allows the caller (or anyone) to retrieve that leftover balance — the funds are permanently lost to the sender.

  function batchTransferEqualAmount(
    address[] calldata recipients,
    uint256 amount
  ) external payable {
    uint256 totalAmount = amount * recipients.length;
    require(msg.value >= totalAmount, "Insufficient amount sent");

    for (uint256 i = 0; i < recipients.length; i++) {
      bool success = payable(recipients[i]).send(amount);
      require(success, "Failed to send Ether");
      emit SendSuccessful(msg.sender, recipients[i], amount);
    }
  }

  function batchTransfer(
    address[] calldata recipients,
    uint256[] calldata amounts
  ) external payable {
    require(
      recipients.length == amounts.length,
      "Recipients and amounts do not match"
    );
    uint256 totalAmount = 0;
    for (uint256 i = 0; i < amounts.length; i++) {
      totalAmount += amounts[i];
    }

    require(msg.value >= totalAmount, "Insufficient amount sent");

    for (uint256 i = 0; i < recipients.length; i++) {
      bool success = payable(recipients[i]).send(amounts[i]);
      require(success, "Failed to send Ether");
      emit SendSuccessful(msg.sender, recipients[i], amounts[i]);
    }
  }
