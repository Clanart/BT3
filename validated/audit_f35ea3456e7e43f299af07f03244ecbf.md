### Title
Nil-pointer dereference DoS via crafted EIP-7702 `SetCodeTx` with empty `to` field - (File: x/evm/types/ethtx/set_code_tx.go)

### Summary
`SetCodeTx.Validate()` never requires the `To` field to be non-empty, but `SetCodeTx.AsEthereumData()` unconditionally dereferences the pointer returned by `GetTo()`, which is `nil` whenever `To == ""`. A transaction sender can submit a `MsgEVMTransaction` whose packed `Any` payload is a `SetCodeTx` with an empty `To` string and otherwise-valid signature fields; every node that decodes and preprocesses this message (mempool admission and block execution) will panic on a nil pointer dereference instead of rejecting the malformed transaction with a normal error.

### Finding Description
`SetCodeTx.GetTo()` explicitly returns `nil` for an empty `To` string: [1](#0-0) 

`AsEthereumData()` then dereferences that pointer unconditionally to populate the underlying go-ethereum `SetCodeTx.To` (a non-pointer `common.Address` field, since EIP-7702 transactions cannot be contract-creation transactions): [2](#0-1) 

`Validate()` only checks the *format* of `To` when it is non-empty; it never rejects an empty `To`: [3](#0-2) 

This is unlike `LegacyTx`/`AccessListTx`/`DynamicFeeTx`, whose `AsEthereumData()` implementations pass the (possibly nil) `*common.Address` through directly (contract creation is legal for those types), e.g. `AccessListTx.AsEthereumData()`: [4](#0-3) 

Because `NewSetCodeTx` (used when *encoding* a genuine go-ethereum transaction) always copies a real `To` address, this defect is unreachable via the normal encode path. However, an attacker does not need to go through `NewSetCodeTx`: they can construct the `codectypes.Any`-wrapped `SetCodeTx` protobuf message directly (e.g. via a raw Cosmos-SDK tx containing `MsgEVMTransaction{Data: Any{TypeUrl: ".../SetCodeTx", Value: <crafted bytes with To="">}}`) and submit it through the normal broadcast/RPC path. `UnpackTxData` in `x/evm/types/codec.go` will happily unmarshal it, and `Validate()` never rejects the missing `To`.

The crafted message is then processed by every node reaching:
- `EvmStatelessChecks` → `msg.AsTransaction()` → `UnpackTxData` + `AsEthereumData()` (CheckTx / mempool admission path): [5](#0-4) 
- `PreprocessUnpacked` → `ethtypes.NewTx(txData.AsEthereumData())` (DeliverTx / block execution ante path): [6](#0-5) 

Both call sites dereference the nil `*common.Address` deep inside `AsEthereumData()`, causing an unrecovered Go panic at that call frame.

### Impact Explanation
This is the direct analog of CVE-2015-8734: a dissector/decoder mishandles a particular "packet type" field (here, the EIP-7702 `SetCodeTx` `to` field) and crashes on a crafted, attacker-controlled input, rather than returning a decode error. In sei-chain the same class of defect exists at the EVM tx-decoding layer that every full node, validator, and public RPC node executes on every submitted transaction (`CheckTx` and `DeliverTx`/`FinalizeBlock`). The codebase's own comments show the team is actively aware of and defends against exactly this bug class elsewhere (e.g. `app/prioritizer.go`'s explicit recover "to avoid DoS vectors where a malicious actor crafts a transaction that panics", and the recover-wrapped `DecodeTransactionsConcurrently`/`GetEVMMsg` in `app/app.go`), but `EvmStatelessChecks` and `PreprocessUnpacked` are not similarly wrapped and rely only on any implicit recover further up the call stack (e.g. cosmos-sdk `BaseApp.runTx`).

If the surrounding execution context (a goroutine without a panic-recover, e.g. concurrent mempool checking or an RPC handler that calls into this decode path outside the standard ante-handler recover) is not protected, this results in a crash of that node process — a denial-of-service against validators and/or public RPC nodes from a single, cheaply-crafted transaction, matching the "crash of default-configuration RPC nodes" acceptance criterion. Where a higher-level recover (e.g. `BaseApp.runTx`) does catch the panic, the practical impact is reduced to a rejected transaction rather than a crash; I could not fully verify from the available code whether every reachable call path (including mempool concurrency and gas-estimation/tracing RPC paths that may call `AsTransaction()`/`AsEthereumData()` outside the ante-handler recover boundary) is covered by such a recover.

### Likelihood Explanation
Likelihood is high for triggering the underlying nil-pointer panic: constructing the malformed `SetCodeTx` requires no special privilege, only knowledge of the protobuf schema and the ability to submit a broadcast transaction or raw tx bytes to any node's RPC/mempool endpoint. No valid signature over a coherent transaction is even strictly required to reach the panic, since the panic occurs during decoding/preprocessing, before or during signature-based address recovery. The main uncertainty is how many of the several call paths that reach `AsEthereumData()` for a `SetCodeTx` are covered by an outer panic recovery boundary versus which (if any) are not.

### Recommendation
Add an explicit non-empty check for `To` in `SetCodeTx.Validate()` (EIP-7702 requires a `to` address; reject with a normal decode/validation error if absent), and/or make `AsEthereumData()` defensively construct the ethereum `SetCodeTx.To` only when `GetTo()` is non-nil, returning an error instead of panicking. Additionally, audit all call sites of `UnpackTxData`/`AsTransaction`/`AsEthereumData` (mempool CheckTx, DeliverTx ante, RPC `eth_call`/`eth_estimateGas`/tracing helpers) to guarantee each is wrapped in a panic-recovery boundary equivalent to those already added in `app/app.go` and `app/prioritizer.go`.

### Proof of Concept
1. Build a Cosmos SDK `Tx` containing a single `evm.MsgEVMTransaction` whose `Data` is a `codectypes.Any` with `TypeUrl` set to the `SetCodeTx` type URL and `Value` a protobuf-marshaled `SetCodeTx` with `To: ""`, `GasTipCap`/`GasFeeCap` set to valid non-negative `sdk.Int`s, and a syntactically-valid (not necessarily cryptographically correct) `V`/`R`/`S` of at most 32 bytes each so `Validate()` passes.
2. Broadcast the tx to any node's RPC endpoint (or gossip it into the mempool).
3. On decode, `EvmStatelessChecks`/`PreprocessUnpacked` call `UnpackTxData` (succeeds) then `AsEthereumData()`, which executes `To: *tx.GetTo()` with `GetTo()==nil`, causing a Go nil-pointer-dereference panic in the goroutine handling the request/tx. [7](#0-6) [5](#0-4) [6](#0-5)

	if tx.To == "" {
		return nil
	}
	to := common.HexToAddress(tx.To)
