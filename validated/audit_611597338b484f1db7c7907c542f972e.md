### Title
`Scanner::scan_block` credits immature coinbase outputs as received funds that are not spendable - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
The bug class in the external report is a protection bound (minimum output / acceptable result) derived inside the same operation from state that can differ from what the caller assumed, so the reported "successful" outcome does not match what was actually obtained. The Serai analog is `Scanner::scan_block` in `bitcoin_serai::wallet`, which reports "received" outputs by matching `script_pubkey` alone and includes `block.txdata[0]` — the coinbase transaction — whose outputs are encumbered by the 100-block maturity rule and can additionally be invalidated entirely by a reorg before maturity. The scanner reports these as ordinary `ReceivedOutput`s: funds reported received that are not spendable.

### Finding Description
`Scanner::scan_transaction` iterates all outputs of a transaction and returns a `ReceivedOutput` for any output whose `script_pubkey` is in the registered `scripts` map, with no further checks:

```rust
// networks/bitcoin/src/wallet/mod.rs
199:  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
...
205:      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
206:        res.push(ReceivedOutput {
207:          offset: *offset,
208:          output: output.clone(),
209:          outpoint: OutPoint::new(tx.compute_txid(), vout),
210:        });
```

`scan_block` then applies this to every transaction in the block, including the coinbase:

```rust

218:  /// outputs must be immediately spendable, a post-processing pass is needed ...
221:  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
222:    let mut res = Vec::new();
223:    for tx in &block.txdata {
224:      res.extend(self.scan_transaction(tx));
```

Just as the Fenix function computed `amountOutQuote` from pool state manipulable within the same transaction — so the "minimum" was not a real bound on what the user received — `scan_block` derives the "received funds" result purely from script matching within the scanned block, without accounting for the spendability state of those outputs. A coinbase output paying to a registered script (the plain key `Scalar::ZERO`, or any registered offset — all computable publicly via `p2tr_script_buf` / `register_offset`-derived keys) is indistinguishable to the scanner from a normal confirmed deposit, yet:

- it cannot be spent for 100 blocks (consensus-enforced maturity),
- if the block is orphaned before maturity, the output ceases to exist at all — the "received" funds evaporate rather than merely becoming unavailable.

The real-world impact of this discrepancy is demonstrated by the sole in-tree consumer, which had to special-case the defect rather than rely on the API: `processor/src/networks/bitcoin.rs` skips the coinbase explicitly (`for tx in &block.txdata[1 ..]`, with the comment "Skip the coinbase transaction which is burdened by maturity"). Any other caller of `scan_block` — the natural API for "what did this block pay us" — receives coinbase outputs conflated with spendable deposits.

Additionally, `scan_transaction` performs no value check: outputs matching a registered script with dust-level values are reported as received, though they are economically unspendable (the fee to spend them exceeds their value). The downstream processor again compensates externally (`output.balance().amount.0 >= N::DUST` in `processor/src/multisigs/scanner.rs:564`), confirming the API alone reports non-spendable outputs as funds.

### Impact Explanation
An unprivileged party can cause Serai's view of received funds to include outputs that cannot be spent. On Bitcoin, any miner (or on a competing/short-lived fork, an attacker deliberately mining an orphan) can place a coinbase output paying to the multisig's registered script. If a caller of `scan_block` credits that output as a deposit or counts it toward the multisig's balance:

- Funds are recorded as received that are consensus-unspendable for 100 blocks, and permanently non-existent if the block is reorganized out before maturity. This is the direct analog of the sandwich attack's "received far less than expected": the reported result is not the effective result.
- A malicious miner can mine a block on a non-final fork paying a large coinbase output to a registered Serai offset script, let it be credited, then let the block be orphaned — the credited balance never existed.

This matches the accepted impact class "funds reported received that are not spendable."

### Likelihood Explanation
Reachable with public inputs only: the attacker sends a Bitcoin transaction (the coinbase of a block they mine) paying to a publicly derivable script — no key material, validator status, or RPC access is required. The receiving scripts are deterministic: the base key's `p2tr_script_buf(key)` and every offset script (`key + offset*G` for offsets derived from `Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", ...)` per `processor/src/networks/bitcoin.rs:308-345`) are computable by anyone. The only mitigating factor is that producing a coinbase requires mining a block; however the vulnerability also triggers with no attacker at all — any miner whose pool's coinbase happens to target a registered script (e.g., a legitimate deposit of mining proceeds to a Serai deposit address) produces a falsely-credited output. Likelihood is therefore moderate: it requires either block-mining capability or coincidence, but no privileged position.

### Recommendation
- In `Scanner::scan_block` (`networks/bitcoin/src/wallet/mod.rs`), skip `block.txdata[0]` rather than requiring every caller to post-process, or return coinbase-derived outputs through a separately-typed result so immature outputs can never be conflated with spendable ones.
- Track coinbase outputs until maturity and only then expose them as `ReceivedOutput`, so a reorg before maturity removes them from the reported set instead of leaving them credited.
- Have `scan_transaction` (or a documented wrapper) filter outputs below the dust threshold so reported outputs are economically spendable, mirroring the `N::DUST` check the processor currently performs ad hoc.
- Document on `ReceivedOutput` that existence in the scan result does not imply current spendability, and provide a helper (`is_spendable_at(height)`) so callers cannot silently mis-handle maturity-encumbered outputs.

The existing test `send_and_get_output` in `networks/bitcoin/tests/wallet.rs:40-78` is itself the witness: it scans a coinbase block and must mine 100 additional blocks before the resulting `ReceivedOutput` is usable — confirming `scan_block` returns maturity-encumbered coinbase outputs as if they were normal receipts.

Note on scope confidence: the in-crate root cause (`scan_transaction` matching on `script_pubkey` alone and `scan_block` including `txdata[0]`) is fully verified from the file contents shown. The downstream consequence depends on how callers consume `scan_block`; the one observed caller (`processor`) works around the coinbase case and dust externally, which both confirms reachability and shows the API contract is unsafe as written. The inline comment acknowledging maturity borders on documented behavior, but it documents the defect rather than enforcing safe handling — no API-level guard exists — so this is reported rather than rejected as documented misuse.
