### Title
OP_RETURN data output excluded from weight/fee calculation, causing underpaid fee and over-credited change - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Sherlock finding describes a leftover-value accounting error: when a partially filled order spawns a new PENDING quote, the leftover locked values are subtracted from the wrong counterparty's `partyBPendingLockedBalances`, permanently locking funds. The Serai analog is in `SignableTransaction::new`: the OP_RETURN `data` output is appended to `tx_outs` but is not passed to `calculate_weight_vbytes`, so the transaction's weight/vbytes (and therefore `needed_fee` and the change amount) are computed for a smaller transaction than the one actually signed. The leftover value is misattributed — change is over-credited and the effective fee rate falls below the caller-specified `fee_per_vbyte`, potentially below `DEFAULT_MIN_RELAY_TX_FEE`, leaving the signed transaction unbroadcastable and the plan's inputs locked.

### Finding Description
`SignableTransaction::new` builds `tx_outs` from `payments`, then pushes an OP_RETURN output carrying up to 80 bytes of caller-supplied `data` (`send.rs:194-202`). It then computes the weight and needed fee via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (`send.rs:204`), which reconstructs a transaction containing only `payments` — the OP_RETURN output is omitted (`send.rs:85-93`). The same omission occurs when sizing the change output (`send.rs:225-226`).

Consequences:
- `needed_fee` and the `TooLowFee` minimum-relay check (`send.rs:206-213`) are computed against a vsize that is up to ~95 weight units (~24 vbytes) too small.
- The change value `input_sat - payment_sat - fee_with_change` (`send.rs:228-230`) credits change with funds that should have paid for the OP_RETURN output's marginal weight — exactly the "leftover values accounted to the wrong bucket" class of the original bug.
- The realized fee rate is `needed_fee / actual_vsize < fee_per_vbyte`. If `fee_per_vbyte` was chosen at or near the relay minimum, the real transaction is below `DEFAULT_MIN_RELAY_TX_FEE` despite passing the `TooLowFee` check.

The `data` bytes are attacker-reachable: in `processor/src/networks/bitcoin.rs`, `make_signable_transaction` feeds payment `data` (derived from user-submitted `InInstruction`/`Shorthand` data on burns) into `SignableTransaction::new`, so an unprivileged user triggering a withdrawal can force the OP_RETURN output to exist and be large.

### Impact Explanation
When the effective fee rate lands below the node's minimum relay fee, `send_raw_transaction` is rejected. The scheduler treats the plan as unconfirmed and can only retry via the same `make_signable_transaction` path, which reproduces the identical under-fee'd transaction — so the inputs (multisig-controlled BTC) remain unspendable for that plan indefinitely, a permanent-in-practice lock of funds mirroring the original report's stuck `partyBPendingLockedBalances`. Even when the transaction does relay, the accounting is wrong: change outputs are systematically over-valued and fees under-valued relative to the negotiated rate, breaking the assumption (asserted in `test_send`, `networks/bitcoin/tests/wallet.rs:269`) that `needed_fee == vsize * fee_per_vbyte` for any transaction carrying `data`.

### Likelihood Explanation
Any withdrawal with attached `data` (an InInstruction up to 80 bytes) triggers the miscalculation on every attempt — deterministic, not probabilistic. The lock-up materializes whenever the selected `fee_per_vbyte` is within the OP_RETURN delta of the relay floor (a realistic condition when fee markets are at minimums or when integrators deliberately request the minimum fee). No malicious validator, collusion, or privileged access is required; only public burn/payment inputs.

### Recommendation
Include the OP_RETURN output in the weight calculation. Pass the fully-built `tx_outs` (or an output descriptor including `data`) into `calculate_weight_vbytes` at both call sites (`send.rs:204` and `send.rs:225-226`), e.g.:

```rust
// build a unified Vec<(ScriptBuf, u64)> including the OP_RETURN entry, or
// change calculate_weight_vbytes to accept &mut tx_outs-style slice
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), &all_outputs, None);
```

and compute `fee_with_change`/`vbytes_with_change` with the change output appended to the same full output list. Alternatively, push the OP_RETURN into `payments` as a zero-valued entry before sizing. Add a regression test asserting `needed_fee == tx.vsize() * fee_per_vbyte` for a transaction constructed with `data: Some(...)`.

### Proof of Concept
```rust
// networks/bitcoin — regtest or unit context
let data = vec![0u8; 80]; // max allowed, worst case
let tx = SignableTransaction::new(
  vec![input.clone()],
  &payments,
  Some(change_addr.clone()),
  Some(data),
  fee_per_vbyte, // e.g. exactly the minimum relay rate
).unwrap();

// The signed transaction is ~24 vbytes larger than what needed_fee priced.
assert!(tx.fee() < fee_per_vbyte * u64::try_from(tx_vsize_with_op_return).unwrap());

// With fee_per_vbyte at the relay floor, the real fee rate is below
// DEFAULT_MIN_RELAY_TX_FEE even though TooLowFee was not raised —
// send_raw_transaction rejects it and the inputs stay locked.
```
