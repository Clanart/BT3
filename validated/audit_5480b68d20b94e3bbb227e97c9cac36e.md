### Title
Malformed serialized threshold key packages can install an unspendable group key - (File: `crypto/dkg/src/lib.rs`)

### Summary
`ThresholdKeys::read` accepts untrusted `t`, `n`, participant, secret-share, interpolation, and verification-share fields, but `ThresholdKeys::new` performs only structural validation. It never checks that the supplied secret share corresponds to the participant’s verification share, nor that the `n` verification shares represent one consistent threshold sharing. The group key is then derived solely from verification shares `1..=t`, allowing a malformed key package to advertise a `t`-of-`n` key that cannot actually be signed for by an arbitrary quorum.

### Finding Description
`ThresholdKeys::read` deserializes attacker-controlled `t`, `n`, `i`, a secret share, and `n` verification shares before calling `ThresholdKeys::new`. [1](#0-0)  The constructor only checks the number and upper bound of participant indexes and rejects constant interpolation when `t != n`. [2](#0-1)  It then computes `group_key` using only the first `t` verification shares. [3](#0-2) 

No check verifies `C::generator() * secret_share == verification_shares[i]` for the local participant, and no check verifies that all `n` verification shares interpolate to the same group key for every size-`t` quorum. Later, `ThresholdKeys::view` enforces only that enough distinct in-range participants were selected. [4](#0-3)  FROST similarly checks the cardinality and uniqueness of preprocess submitters, not whether the serialized shares form a consistent threshold sharing. [5](#0-4) 

This is analogous to accepting a replacement validator set without proving the new set has sufficient effective signing power: the serialized object claims a threshold policy, while its actual usable quorum may be restricted to the first `t` shares—or be unusable by the recipient if the local secret does not match its public verification share.

### Impact Explanation
A party that accepts an attacker-supplied `ThresholdKeys` encoding can publish or scan for the resulting `group_key` while being unable to produce a valid signature. FROST completion first rejects the aggregate signature, then identifies the malformed share during per-share verification. [6](#0-5) 

If this key is used as a Bitcoin receive key, `Scanner::new` and `register_offset` accept the public key and report matching outputs without any way to detect that the associated threshold shares cannot spend them. [7](#0-6) [8](#0-7)  The concrete impact is therefore funds reported as received under a malformed threshold key that are not spendable by the intended quorum.

### Likelihood Explanation
An unprivileged party only needs to cause a victim to load crafted bytes through `ThresholdKeys::read`; no valid DKG transcript or secret knowledge is required. The format explicitly accepts all fields needed to make the verification shares inconsistent with the local secret or with each other. [1](#0-0)  Because deserialization succeeds and exposes the derived `group_key` as valid, downstream wallet code can naturally begin accepting payments to it before the first attempted spend fails. [9](#0-8) [10](#0-9) 

### Recommendation
During `ThresholdKeys::new` or at least during `ThresholdKeys::read`, reject semantically inconsistent packages:

- Verify `C::generator() * secret_share == verification_shares[params.i()]`.
- Verify all `n` verification shares belong to the claimed threshold sharing, rather than deriving the group key only from participants `1..=t`.
- For Lagrange interpolation, compare the group key interpolated by each size-`t` subset, or otherwise validate the commitments/PoK provenance that established those shares.
- Document that raw serialized `ThresholdKeys` require authentication/integrity until semantic validation is added.

### Proof of Concept
Conceptually, for `t = 2`, `n = 3`, `i = 1`, construct a serialized `ThresholdKeys` object containing:

1. A valid curve ID.
2. `t = 2`, `n = 3`, `i = 1`.
3. Lagrange interpolation.
4. A victim secret share `s1`.
5. Verification shares `[G*s1, G*s2, G*s3]`, where `s1`, `s2`, and `s3` are not points on one degree-1 polynomial.

`ThresholdKeys::read` accepts the object because all indexes are in range and the map has `n` entries. [11](#0-10)  The resulting group key is computed only from shares `1` and `2`. [3](#0-2)  A signing set `{1,3}` or `{2,3}` is accepted by participant-count validation but interpolates a different secret/public key, so its aggregate signature fails and the shares are blamed or the operation ends in the documented internal-error path. [12](#0-11)  The wallet nevertheless scans outputs to the advertised public key. [8](#0-7)
