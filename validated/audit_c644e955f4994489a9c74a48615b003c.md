## Title
Malicious `src_callback` contract can permanently block IBC acknowledgement/timeout processing, freezing escrowed funds on ordered channels — (File: `x/ibc/callbacks/keeper/keeper.go`)

## Summary
This is a native analog of the Curves `HoneyPot` bug: in Curves, an attacker-controlled `referralFeeDestination` is unconditionally `.call{value: ...}`'d during `_transferFees`, and any revert from that address reverts the *entire* transaction — so the subject creator can brick `sell` while `buy` keeps working, trapping victims' funds. In Cosmos EVM's IBC callbacks module, the IBC packet **sender** similarly gets to designate an arbitrary EVM contract (`src_callback.address` in the transfer memo) that is unconditionally invoked during `OnAcknowledgementPacket`/`OnTimeoutPacket` processing, and any revert from that contract is propagated as a hard error out of the packet lifecycle callback, exactly like the honeypot's unconditional external call.

## Finding Description
`IBCOnAcknowledgementPacketCallback` and `IBCOnTimeoutPacketCallback` in `x/ibc/callbacks/keeper/keeper.go` call an attacker-chosen contract address (taken from the packet's own `memo.src_callback.address`, which — per the module's own README — **"only the IBC packet sender can set"**) via `k.evmKeeper.CallEVM(...)`, and if that EVM call returns an error, the function returns `errorsmod.Wrapf(types.ErrCallbackFailed, "EVM returned error: %s", err.Error())`: [1](#0-0) [2](#0-1) 

This is wired into the transfer stack as the **outermost** middleware, wrapping the ERC-20 middleware and the core `transfer` module: [3](#0-2) 

Because `ibccallbacks.NewIBCMiddleware` sits at the top of the stack, its `OnAcknowledgementPacket`/`OnTimeoutPacket` implementation calls the inner `IBCModule` first (which performs the refund/erc20 conversion logic in `x/erc20/keeper/ibc_callbacks.go`, see `OnAcknowledgementPacket`/`OnTimeoutPacket`), and then invokes the sender-controlled callback contract afterward: [4](#0-3) 

If the callback processing returns an error (as it will whenever the attacker's contract reverts), that error propagates up through the message handler for `MsgAcknowledgement`/`MsgTimeout`. Cosmos SDK message execution is atomic — an error returned from the port's `IBCModule` causes the entire `sdk.Msg` execution (including all already-applied refund/conversion state changes made deeper in the stack) to be rolled back, and the packet commitment/ack-processing state is **not** advanced. The README's own security note implicitly acknowledges this risk ("failures in callback execution may affect the IBC packet lifecycle") but the implementation does not swallow or isolate callback errors the way ADR-8 normally recommends (only panics/out-of-gas are recovered elsewhere; a plain `revert()`/require-false in the callback contract results in a returned Go `error`, not a panic, and is not caught).

Just like the Curves referral-fee call, the sender fully controls the target address and can trivially make it always revert (e.g. a contract whose fallback always executes `revert()`), while the packet was legitimately sent through the normal, unprivileged `MsgTransfer`/ICS-20 flow.

## Impact Explanation
On an **ordered** IBC channel, acknowledgement/timeout processing must occur strictly in packet sequence order. If the sender-designated callback contract for packet N deterministically reverts, the ack/timeout for packet N can never be committed successfully. Because ordered channels enforce sequential ack/timeout processing, this permanently blocks the ack/timeout of packet N **and every subsequent packet on that channel**, freezing the escrowed funds not only of the attacker but of every other user who has sent (or is sending) tokens over the same ordered channel — a critical, irreversible freezing of user funds triggered by an ordinary, unprivileged transaction (`MsgTransfer` with a malicious `src_callback` memo). This matches the "Critical permanent freezing/locking of escrowed assets... triggerable through ordinary transaction flow" impact class.

## Likelihood Explanation
The `src_callback` address is entirely attacker-supplied via a JSON memo on a completely permissionless `MsgTransfer`; no privileged access, relayer collusion, or validator cooperation is required. Deploying a small "always revert" contract and referencing it in the memo is a one-transaction setup. The only prerequisite for the maximal (multi-victim) impact is that the channel used is `ORDERED`; on `UNORDERED` channels the impact is limited to the attacker's own funds, which is a lower-severity self-harm case, but the mechanism (unconditional external call whose failure reverts the entire ack/timeout state transition, including funds refund logic) is a broken invariant regardless of channel ordering.

## Recommendation
- Isolate the sender-provided callback execution from the mandatory refund/state-transition logic: run `IBCOnAcknowledgementPacketCallback` / `IBCOnTimeoutPacketCallback` in a way whose failure is only logged/emitted as an event and never returned as a hard error that aborts the surrounding `OnAcknowledgementPacket`/`OnTimeoutPacket` message execution (per ADR-8 guidance that "ack"/"timeout" callback errors must not affect the underlying packet lifecycle, since the core refund logic has already run).
- Ensure the refund/conversion logic committed by the inner `transfer`/`erc20` modules is durably applied (e.g., via its own `CacheContext`+`writeFn` commit) *before* invoking the sender's callback contract, so a reverting callback cannot roll back the refund.
- Add channel-ordering-aware safeguards or gas/error containment so a single malicious callback cannot stall subsequent packets' ack/timeout processing on ordered channels.

## Proof of Concept
1. Attacker deploys `AlwaysRevertCallback`, whose `onPacketAcknowledgement`/`onPacketTimeout` implementations immediately `revert()`.
2. Attacker sends `MsgTransfer` over an `ORDERED` ICS-20 channel with memo:
   ```json
   { "src_callback": { "address": "<AlwaysRevertCallback>", "gas_limit": "200000" } }
   ```
3. When the relayer submits `MsgAcknowledgement` (or `MsgTimeout`) for this packet, `IBCOnAcknowledgementPacketCallback`/`IBCOnTimeoutPacketCallback` calls the attacker's contract, which reverts; `CallEVM` returns an error, which is wrapped and returned as `ErrCallbackFailed`.
4. The `MsgAcknowledgement`/`MsgTimeout` transaction fails atomically; the packet's commitment remains, and ack/timeout processing for this sequence number can never succeed.
5. On the ordered channel, all packets sent by other users after this sequence number become permanently stuck as well, since their acknowledgements/timeouts cannot be processed out of order — freezing their escrowed funds indefinitely.

func (k ContractKeeper) IBCOnAcknowledgementPacketCallback(
	ctx sdk.Context,
	packet channeltypes.Packet,
	acknowledgement []byte,
	relayer sdk.AccAddress,
	contractAddress,
	packetSenderAddress string,
	version string,
) error {
	data, err := transfertypes.UnmarshalPacketData(packet.GetData(), version, "")
	if err != nil {
		return err
	}

	cbData, isCbPacket, err := callbacktypes.GetCallbackData(data, version, packet.GetDestPort(), ctx.GasMeter().GasRemaining(), ctx.GasMeter().GasRemaining(), callbacktypes.SourceCallbackKey)
	if err != nil {
		return err
	}
	if !isCbPacket {
		return nil
	}

	// `ProcessCallback` in IBC-Go overrides the infinite gas meter with a basic gas meter,
	// so we need to generate a new infinite gas meter to run the EVM executions on.
	// Skipping this causes the EVM gas estimation function to deplete all Cosmos gas.
	// We re-add the actual EVM call gas used to the original context after the call is complete
	// with the gas retrieved from the EVM message result.
	cachedCtx, writeFn := ctx.CacheContext()
	cachedCtx = evmante.BuildEvmExecutionCtx(cachedCtx).
		WithGasMeter(evmtypes.NewInfiniteGasMeterWithLimit(cbData.CommitGasLimit))

	if len(cbData.Calldata) != 0 {
		return errorsmod.Wrap(types.ErrInvalidCalldata, "acknowledgement callback data should not contain calldata")
	}

	sender, err := utils.HexAddressFromBech32String(packetSenderAddress)
	if err != nil {
		return errorsmod.Wrapf(err, "unable to parse packet sender address %s", packetSenderAddress)
	}

	contractAddr := common.HexToAddress(contractAddress)

	// Check if the contract address contains code.
	// This check is required because if there is no code, the call will still pass on the EVM side,
	// but it will ignore the calldata and funds may get stuck.
	if !k.evmKeeper.IsContract(ctx, contractAddr) {
		return errorsmod.Wrapf(types.ErrCallbackFailed, "provided contract address is not a contract: %s", contractAddr)
	}

	abi, err := callbacksabi.LoadABI()
	if err != nil {
		return err
	}

	// Call the onPacketAcknowledgement function in the contract
	// NOTE: use the cached ctx for the EVM calls.
	res, err := k.evmKeeper.CallEVM(cachedCtx, *abi, sender, contractAddr, true, math.NewIntFromUint64(cachedCtx.GasMeter().GasRemaining()).BigInt(), "onPacketAcknowledgement",
		packet.GetSourceChannel(), packet.GetSourcePort(), packet.GetSequence(), packet.GetData(), acknowledgement)
	if err != nil {
		return errorsmod.Wrapf(types.ErrCallbackFailed, "EVM returned error: %s", err.Error())
	}

	// Consume the actual gas used on the original callback context.
	ctx.GasMeter().ConsumeGas(res.GasUsed, "callback onPacketAcknowledgement")
	if ctx.GasMeter().IsOutOfGas() {
		return errorsmod.Wrapf(types.ErrCallbackFailed, "out of gas")
	}

	writeFn()

	return nil
}

// OnAcknowledgementPacket responds to the success or failure of a packet
// acknowledgement written on the receiving chain. If the acknowledgement was a
// success then nothing occurs. If the acknowledgement failed, then the sender
// is refunded and then the IBC Coins are converted to ERC20.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnAcknowledgementPacket
// still succeeds, but the user receives the corresponding bank token from the
// TokenPair instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnAcknowledgementPacket(
	ctx sdk.Context, _ channeltypes.Packet,
	data transfertypes.FungibleTokenPacketData,
	ack channeltypes.Acknowledgement,
) error {
	switch ack.Response.(type) {
	case *channeltypes.Acknowledgement_Error:
		// convert the token from Cosmos Coin to its ERC20 representation
		return k.ConvertCoinToERC20FromPacket(ctx, data)
	default:
		// the acknowledgement succeeded on the receiving chain so nothing needs to
		// be executed and no error needs to be returned
		return nil
	}
}

// OnTimeoutPacket converts the IBC coin to ERC20 after refunding the sender
// since the original packet sent was never received and has been timed out.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnTimeoutPacket still
// succeeds, but the user receives the corresponding bank token from the TokenPair
// instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnTimeoutPacket(ctx sdk.Context, _ channeltypes.Packet, data transfertypes.FungibleTokenPacketData) error {
	return k.ConvertCoinToERC20FromPacket(ctx, data)
}
