### Title
CW20 pointer registration panics on token_info responses missing/wrong-typed `name`/`symbol` fields - ([File: precompiles/pointer/pointer.go])

### Summary
The `pointer` precompile's `AddCW20` handler assumes every CW20 contract's `token_info` query response contains string-typed `name` and `symbol` fields, exactly the assumption the referenced report flags as unsafe for ERC20 `symbol()`/`name()`. Sei's implementation is stricter/worse: it does an un-checked Go type assertion (`formattedRes["name"].(string)`) instead of a graceful revert, so a non-conforming or malicious CW20 contract can turn a normal user transaction into a runtime panic inside consensus-critical code.

### Finding Description
`AddCW20` (in every version of `precompiles/pointer/pointer.go` / `precompiles/pointer/legacy/vNNN/pointer.go`) queries an arbitrary, caller-supplied CW20 contract address via `wasmdKeeper.QuerySmart(ctx, cwAddress, []byte("{\"token_info\":{}}"))`, unmarshals the JSON result into a `map[string]interface{}`, and then does:
```go
name := formattedRes["name"].(string)
symbol := formattedRes["symbol"].(string)
``` [1](#0-0) 

Any of the following make this panic with `interface conversion: interface {} is nil, not string` (or "... is X, not string"):
- The `token_info` handler in the target CW20 contract omits the `name` or `symbol` key from its JSON response (fields are absent → the map lookup returns `nil`).
- The value is present but not a JSON string (e.g. a `null`, number, or object) — legal in raw JSON even though it violates the CW20 spec.

Because the caller supplies `cwAddr` directly (`cwAddr := args[0].(string)` then `sdk.AccAddressFromBech32(cwAddr)`) with no validation that the target actually implements the full, well-typed CW20 interface, any CosmWasm contract deployer can create such a contract and any unprivileged EVM caller can then invoke `addCW20Pointer(contractAddr)` against it, triggering the panic deterministically. This is the same root-cause class as the reported issue — code assumes conformance to an optional/non-enforced metadata interface — but manifests as a raw Go panic rather than a Solidity `revert`. [2](#0-1) 

### Impact Explanation
The panic occurs inside `PrecompileExecutor.AddCW20`, which is invoked from `DynamicGasPrecompile.RunAndCalculateGas` via `d.executor.Execute(...)`. The `RunAndCalculateGas` wrapper only recovers/normalizes a returned `err` value (`defer func(){ HandlePrecompileError(err, ...) }`) — it does not `recover()` an actual Go panic, so an unrecovered type-assertion panic unwinds past this defer. [3](#0-2) 

Whether this becomes only a failed transaction (caught by an outer `recover()` in baseapp's tx-processing pipeline) or a validator-crashing panic depends on whether such a recover exists on the EVM message-execution path above the precompile call; I was not able to fully confirm the exact recovery boundary for EVM `Call`-driven precompile panics within the remaining investigation budget. In the conforming case (recovered by baseapp), the practical effect matches the referenced report: pointer creation permanently fails for any CW20 token whose `token_info` doesn't return well-typed `name`/`symbol` — breaking the "core protocol requirement" that arbitrary CW20 tokens must be pointer-able into the EVM, and repeatable/griefable by any wasm contract deployer. In the worse case (no recover on this path), it would crash node processing of that transaction/block, i.e. a validator/RPC-node halt.

### Likelihood Explanation
High: no privileged access is required. Any account can deploy a CosmWasm contract that answers `{"token_info":{}}` with a `name`/`symbol` field missing or of the wrong JSON type (or simply omit those keys), then call `addCW20Pointer`/`addNativePointer`-equivalent CW20 registration through the `pointer` precompile from a normal EVM transaction.

### Recommendation
Replace the unchecked type assertions with the checked (`, ok`) form and return a proper `error` (causing a normal EVM revert) instead of panicking when `name`/`symbol` are missing or not strings:
```go
nameVal, ok := formattedRes["name"].(string)
if !ok {
    return nil, 0, fmt.Errorf("cw20 token_info response missing/invalid name field")
}
symbolVal, ok := formattedRes["symbol"].(string)
if !ok {
    return nil, 0, fmt.Errorf("cw20 token_info response missing/invalid symbol field")
}
```
Apply the same fix consistently across all `AddCW20` implementations, including the legacy versioned copies (`precompiles/pointer/legacy/v552`...`v640`), and audit other `formattedRes[...].(...)` type assertions on wasm query results in this codebase for the same pattern (e.g. `HandleERC20TokenInfo` and related handlers that unpack ABI results assuming specific types) for consistency. [4](#0-3) 

### Proof of Concept
1. Deploy a CW20-ABI-compatible wasm contract whose `token_info` query handler returns JSON such as `{"decimals":6,"total_supply":"0"}` (omitting `name`/`symbol`), or `{"name":null,"symbol":123,...}`.
2. From any EVM account, call the `pointer` precompile's `addCW20Pointer(contractAddr)` method (address `0x100b`, exposed via `precompiles/pointer/pointer.go`).
3. Execution reaches:
```go
res, err := p.wasmdKeeper.QuerySmart(ctx, cwAddress, []byte("{\"token_info\":{}}"))
...
name := formattedRes["name"].(string)   // panics: nil/non-string is not string
symbol := formattedRes["symbol"].(string)
``` [5](#0-4) 
4. The transaction execution panics; depending on whether an outer recover boundary exists on this specific call path, this either fails the transaction (denial-of-pointer-creation, mirroring the referenced report) or halts the processing node — this final determination was not conclusively verified in this pass and should be validated with a live-node/simulation test before treating it as a validator-crash-level finding.
