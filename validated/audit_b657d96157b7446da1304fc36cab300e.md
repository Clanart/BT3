### Title
Quadratic CPU exhaustion via attacker-controlled `t`/`n` in `ThresholdKeys::read` - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` deserializes the threshold parameters `t`, `n`, and `i` directly from untrusted bytes, then `ThresholdKeys::new` computes the group key by calling `Interpolation::interpolation_factor` once for each of the `t` participants `1..=t`. For `Interpolation::Lagrange`, each `interpolation_factor` call iterates over all `t` included participants, making group-key derivation `O(t²)` in field operations plus `t` scalar inversions and `t` point multiplications. With `t = n = 65535` (both attacker-controlled `u16`s), a ~2 MB crafted input triggers roughly 4.3 billion field multiplications and 65535 field inversions — a large-loops denial of service analogous to CVE-2022-0585.

### Finding Description
`ThresholdKeys::read` at crypto/dkg/src/lib.rs:591-623 reads `t`, `n`, `i` from the stream and then loops `n` times reading verification-share points before any parameter validation. `ThresholdParams::new` (lib.rs:166-179) only enforces `0 < t <= n` and `i <= n` — there is no upper bound on `n`/`t`, so `t = n = 0xffff` is accepted as valid.

The cost lives in `ThresholdKeys::new` (lib.rs:376-378):

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

For `Interpolation::Lagrange`, `interpolation_factor` (lib.rs:229-247) multiplies over all `t` entries of `included` and performs a field inversion per call:

```rust
for l in included {
  if i == *l { continue; }
  let share = F::from(u64::from(u16::from(*l)));
  num *= share;
  denom *= share - i_f;
}
num * denom.invert().unwrap()
```

So a single `read` performs `t` calls each costing `O(t)` field multiplications plus one inversion, i.e. `O(t²)` total scalar work and `t` scalar→point multiplications. The attacker only needs to supply `n` encoded points (`n` × ~32 bytes for Ristretto/ed25519-class curves) and one scalar — a ~2 MB input for `n = 65535` — yielding an amplification factor of millions of CPU operations per input byte.

The same quadratic structure exists in `ThresholdKeys::view` (lib.rs:500-507), where `interpolation_factor` is called for every `i` in `included` over the same `included` slice, though there `included` is bounded by the caller's signing set. The `read`/`new` path is the one driven purely by untrusted bytes.

### Impact Explanation
Any caller that feeds untrusted or peer-supplied bytes into `ThresholdKeys::read` (listed in scope as a reachable untrusted-bytes API) can be stalled for an effectively unbounded amount of CPU time. A node parsing a crafted `ThresholdKeys` blob performs ~4.3e9 field multiplications, ~65k inversions, and ~65k point multiplications for a 2 MB input, blocking the executing thread far beyond any proportional work bound. This matches the CVE-2022-0585 class: a length/count field in crafted input drives loops whose cost is disproportionate (here quadratic) to the input size, enabling remote denial of service against a single unprivileged message.

### Likelihood Explanation
- Reachability: `ThresholdKeys::read` is an explicitly in-scope sink for untrusted bytes; `n` and `t` are read straight from the stream before `ThresholdParams::new` checks anything beyond `t <= n`.
- No bound: neither `read` nor `ThresholdParams::new` caps `n`/`t`, unlike e.g. `Transaction::read` in coordinator/src/tributary/transaction.rs which enforces `TRANSACTION_SIZE_LIMIT` on nested counts.
- Cost realism: `u16` bounds the worst case to `n = t = 65535`, but that is still ~4.3 billion scalar multiplications plus 65k inversions — many orders of magnitude beyond a healthy per-message budget. Even a modest `n` of a few thousand produces a clear quadratic stall.
- Attacker effort is trivial: the payload is one scalar, `n` copies of a valid point encoding, and a valid interpolation tag; all points can be the generator.

### Recommendation
- Enforce a protocol-level maximum on `n` (and hence `t`) inside `ThresholdParams::new`/`ThresholdKeys::read` (e.g. the `MAX_KEY_SHARES_PER_SET`-style bound used elsewhere in Serai), rejecting oversized parameters before any allocation or group-key computation.
- Alternatively, compute the Lagrange group key with an `O(t)` product-of-differences scheme (compute the full numerator once, then per-participant factors via a single inversion each) and/or batch-invert the denominators, removing the `O(t²)` term even for permitted sizes.

### Proof of Concept
```rust
// crypto/dkg/src/lib.rs — ThresholdKeys::<C>::read on crafted bytes
// For C = Ristretto (32-byte points, 32-byte scalars):

let n: u16 = u16::MAX; // 65535
let mut buf = vec![];
buf.extend(u32::try_from(Ristretto::ID.len()).unwrap().to_le_bytes());
buf.extend(Ristretto::ID);
buf.extend(n.to_le_bytes());                 // t = 65535
buf.extend(n.to_le_bytes());                 // n = 65535
buf.extend(1u16.to_le_bytes());              // i = 1
buf.push(1);                                 // Interpolation::Lagrange
buf.extend(<Ristretto as Ciphersuite>::F::ONE.to_repr()); // secret_share
for _ in 0 .. n {
  buf.extend(<Ristretto as Ciphersuite>::generator().to_bytes()); // verification shares
}
// ~2.1 MB input
let _ = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice());
// ThresholdKeys::new -> interpolation_factor called 65535 times,
// each iterating 65535 elements + one field inversion:
// ~4.3e9 field muls + 65535 inversions + 65535 point muls.
```
