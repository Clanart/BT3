## Analysis

The Halborn report's core broken invariant: **code assumes a token transfer moves exactly the requested amount, then commits that unverified amount into protocol accounting** — for OUSD (and other rebasing/fee-on-transfer tokens) this assumption is false, and the mismatch causes either a revert (Coordinator.sol) or, more dangerously, a silent accounting corruption if no check exists at all.

I found the local analog in `WrappedHyperFungibleTokenUpgradeable.sol::send()` (and its non-upgradeable twin `WrappedHyperFungibleToken.sol::send()`). Compare it against `IntentGatewayV2.sol::placeOrder`, which explicitly guards against this exact bug class by measuring the balance delta: [1](#0-0)

### Title
Wrapped-token bridge lock accepts unverified transfer amount, enabling under-collateralized cross-chain minting/unlocking - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol)

### Summary
`WrappedHyperFungibleTokenUpgradeable.send()` (and the non-upgradeable `WrappedHyperFungibleToken.send()`) locks the underlying ERC-20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and then encodes `params.amount` — the value the caller *requested*, not the value the contract *actually received* — into the cross-chain `Message`. For any underlying token whose `transferFrom` does not deliver exactly `params.amount` to the recipient (fee-on-transfer tokens, deflationary/burn-on-transfer tokens, or rebasing tokens like OUSD where a `balanceOf` read immediately after a transfer can differ from the naive arithmetic sum), the contract commits and bridges a value that exceeds what it actually escrowed.

### Finding Description
`send()` never re-derives the received amount from a balance-delta check, unlike the sibling app `IntentGatewayV2`, which explicitly does this for exactly this reason (see `IntentGatewayV2.sol:289-291`, with `FeeOnTransferToken` tests covering the case). In `WrappedHyperFungibleTokenUpgradeable.send()`:

```solidity
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
...
bytes memory body = abi.encode(HyperFungibleTokenUpgradeable.Message({
    from: abi.encodePacked(msg.sender),
    to: params.to,
    amount: params.amount,   // <-- requested amount, not measured delta
    data: params.data
}));
```

If the escrow contract's actual token balance increases by less than `params.amount` (e.g., a 1% fee-on-transfer token, or an OUSD-style token whose exact-equality/rounding behavior differs from naive addition), the dispatched message still commits to the full `params.amount`. The destination-side `onAccept` then unconditionally transfers `message.amount` of the underlying out of its own escrow to the beneficiary:

```solidity
IERC20(_underlying).safeTransfer(beneficiary, message.amount);
```

There is no guard anywhere in this path (source lock or destination release) validating that the escrowed balance matches the committed/bridged amount. Each such send under-collateralizes the destination-side escrow pool by the shortfall. Repeated sends compound the deficit until the pool cannot honor legitimate `onAccept` releases for other users — the classic bridge insolvency pattern, and the same root cause as the OUSD "positions cannot be unwound" bug, except here nothing reverts to protect users; the corruption is silent and cumulative.

### Impact Explanation
This corrupts the fundamental 1:1 backing invariant between locked collateral on the source chain and unlockable claims on the destination chain — an unauthorized state acceptance/fund-loss class explicitly in scope. Because the deficit accumulates across every affected transfer, later legitimate beneficiaries on the destination chain can find their `onAccept` release fail (funds stuck) or, if a malicious/aware token owner configures such an underlying, an attacker can systematically drain the pool: deposit a token that yields less than requested on `transferFrom`, obtain a fully-valued unlock claim on the destination chain, and repeat until the destination escrow is exhausted at the expense of other bridge users.

### Likelihood Explanation
The wrapper is explicitly designed as a generic tool to wrap "existing ERC20 tokens" (per `configure()` and its purpose), so any deployment wrapping a fee-on-transfer, deflationary, or rebasing token hits this immediately and deterministically on every `send()` — no malicious relayer, prover, or governance actor required. The bug is triggered purely by normal user interaction with an already-deployed, legitimately configured wrapper instance.

### Recommendation
Mirror `IntentGatewayV2`'s pattern in `send()`: snapshot `IERC20(_underlying).balanceOf(address(this))` before `safeTransferFrom`, take the balance delta afterward as the amount to embed in `Message.amount`, and use that measured value for dispatch/commitment instead of the caller-supplied `params.amount`. Apply the same fix to the non-upgradeable `WrappedHyperFungibleToken.sol`.

### Proof of Concept
1. Owner deploys `WrappedHyperFungibleTokenUpgradeable` and calls `configure()` with `underlying` set to a fee-on-transfer ERC20 (e.g., 1% fee burned on transfer, as modeled by the `FeeOnTransferToken` test contract already present in the repo's test suite).
2. User calls `send({ amount: 1000e18, ... })`. `safeTransferFrom` moves `1000e18` requested but the contract's balance only increases by `990e18` (1% fee burned in transit).
3. The dispatched `Message.amount` is still `1000e18`.
4. On the destination chain, `onAccept` releases `1000e18` of the (mirrored) underlying to the beneficiary, i.e., `10e18` more than was ever actually escrowed on the source chain for this transfer.
5. Repeating this deposit pattern accumulates a growing shortfall in the destination-side escrow pool, eventually causing `onAccept` reverts (locked funds) for other legitimate users, or, an attacker can specifically target a token they know underpays on transfer to systematically extract more value than they deposited.     function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleTokenUpgradeable.Message memory message =
            abi.decode(request.body, (HyperFungibleTokenUpgradeable.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }
