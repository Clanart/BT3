### Title
Missing decimal-direction guard in `convert_to_erc20` causes silent no-op scaling and cross-chain token over-minting - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token` scales balances between a Substrate asset's local decimals and the paired EVM ERC20's decimals whenever a `send()` transfers value cross-chain. The scaling helper `convert_to_erc20` (and its inverse `convert_to_balance`) computes the scaling exponent with `erc_decimals.saturating_sub(local_decimals)`. `saturating_sub` silently clamps to `0` instead of erroring when `local_decimals > erc_decimals`, so in that configuration the function returns the *unscaled* raw value. This exactly mirrors the reported bug class: a decimal-scaling routine that behaves correctly only when moving in one directional case (source dp ≤ target dp) and silently degenerates to no-op/linear behavior in the other direction (source dp > target dp), producing a value off by `10^(local_decimals - erc_decimals)`.

### Finding Description [1](#0-0) 

```rust
/// Converts an ERC20 U256 amount to a local balance type
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256, erc_decimals: u8, local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value / U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))).to_string();
    dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both helpers assume `erc_decimals >= local_decimals` (the documented typical case, e.g. 10-decimal DOT locally vs 18-decimal wrapped DOT on EVM — see `modules/pallets/hyper-fungible-token/README.md:31`). When that assumption is violated — i.e. the locally registered asset has *more* decimals than the EVM contract it's paired with (`local_decimals > erc_decimals`) — `erc_decimals.saturating_sub(local_decimals)` clamps to `0`, so the exponent is `0` and **no scaling is applied at all**, instead of correctly dividing/multiplying by `10^(local_decimals - erc_decimals)`.

This is invoked from the outbound path in `send()`: [2](#0-1) 

```rust
let token_contract = TokenContracts::<T>::get(params.destination, params.asset_id.clone())...
let erc_decimals = Precisions::<T>::get(params.asset_id.clone(), params.destination)...
...
let erc20_amount = convert_to_erc20(amount, erc_decimals, decimals);
...
let token_message = Message { ..., amount: alloy_primitives::U256::from_be_bytes(erc20_amount.to_big_endian()), ... };
```

`Precisions` is a registerable, per-`(asset_id, StateMachine)` value set via `register_token`/`update_token`, with no on-chain check that it be `>= decimals` of the local asset. If a token is registered where the local asset uses more decimals than the destination EVM contract (`erc_decimals < decimals`), a normal user calling `send()` triggers `convert_to_erc20(amount, erc_decimals, decimals)` with `erc_decimals < decimals`, so the returned `erc20_amount == amount` unscaled — i.e., the *raw local-decimal integer* is sent as the ERC20 `amount` field, without dividing it down by `10^(decimals - erc_decimals)`.

On the receiving EVM side the amount is minted directly: [3](#0-2) 
```solidity
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
    ...
    Message memory message = abi.decode(request.body, (Message));
    address beneficiary = _toAddr(message.to);
    _mint(beneficiary, message.amount);
    ...
}
```

Because `message.amount` was never scaled down, `_mint` credits `10^(local_decimals - erc_decimals)` times more tokens than the user actually escrowed/burned on the Substrate side.

### Impact Explanation
This is a fund-inflation/unauthorized-minting bug reachable through the ordinary, unprivileged `send()` extrinsic: any account holding even a tiny amount of an affected asset can burn/lock a small quantity locally and receive a vastly larger (`10^n`) amount of the corresponding wrapped ERC20 token on the destination EVM chain. This directly matches the bounty's accepted impact categories ("stealing or loss of funds", "unauthorized transaction or execution", "logic attacks"). The severity scales with how large `decimals - erc_decimals` is (e.g., an 18 vs 6 decimal mismatch inflates value 10^12x), and it requires no relayer/prover/admin misbehavior — only a legitimately-set (or accidentally misconfigured) `Precisions` entry where the local asset's decimals exceed the destination's registered ERC20 decimals.

### Likelihood Explanation
The trigger condition (`local_decimals > erc_decimals` for a registered asset/chain pair) is not prevented anywhere in `register_token`/`update_token`/`update_asset_precision` — there is no validation enforcing `erc_decimals >= local_decimals`. Since `Precisions` values are set per-asset-per-chain by governance (`CreateOrigin`) independently for each destination chain, it is plausible for an asset with high local precision (e.g., 18-decimal Substrate asset) to be paired with a chain-specific ERC20 whose configured decimals are lower (e.g., 6, matching a stablecoin-like design) — this is a normal, foreseeable configuration, not a contrived edge case, and the existing test suite (`pallet_hyper_fungible_token.rs`) only exercises the safe direction (`convert_to_erc20(SEND_AMOUNT, 18, 10)`, i.e., `erc_decimals > local_decimals`), leaving the inverse direction completely uncovered and unguarded.

### Recommendation
Replace `saturating_sub` with an explicit direction check that scales correctly both ways (analogous to `adjustDecimals` used elsewhere in the SDK, `sdk/packages/sdk/src/utils.ts:985-994`):

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
Apply the same bidirectional fix to `convert_to_balance`, and add validation in `register_token`/`update_token`/asset-precision updates plus explicit unit tests covering `local_decimals > erc_decimals`.

### Proof of Concept
1. Governance registers asset `X` with local `decimals = 18` (via `pallet-assets`) and, for destination `StateMachine::Evm(C)`, sets `Precisions::<T>::insert(X, Evm(C), 6)` (a 6-decimal ERC20 contract) via `register_token`.
2. Attacker holds `1_000_000_000` raw units of `X` locally (i.e., `0.000000001` real tokens at 18 decimals).
3. Attacker calls `send(SendParams { asset_id: X, destination: Evm(C), amount: 1_000_000_000, ... })`.
4. In `send()`, `erc_decimals = 6`, `decimals = 18`. `convert_to_erc20(1_000_000_000, 6, 18)` computes `erc_decimals.saturating_sub(local_decimals) = 6u8.saturating_sub(18) = 0`, so `erc20_amount = 1_000_000_000 * 10^0 = 1_000_000_000`, unchanged.
5. `onAccept` on the EVM `HyperFungibleToken` contract mints `1_000_000_000` raw units, interpreted at the contract's actual `6` decimals — i.e., `1000` real tokens — to the beneficiary.
6. Result: attacker escrowed only `10^-9` real tokens locally but received `1000` real tokens on the EVM side, a `10^12`x inflation, confirming unauthorized token creation from the missing decimal-direction guard.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
