### Title
Improper input validation in `oracle-timestamp-fresh` bypasses staleness gating and can poison the monotonic per-feed timestamp, permanently freezing price resolution for an asset - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
The oracle freshness/monotonicity gate used before every collateral/debt price is accepted zeroes out the staleness delta whenever the incoming price timestamp is greater than the recorded Stacks block time, instead of rejecting or correctly signing the skew. This mis-handled edge case both defeats the staleness check and — because the accepted timestamp is then persisted as the new "last known good" value — can permanently lock the per-feed monotonicity check into a state that every subsequent, genuinely-fresh price update fails, reverting `price-resolve` and freezing all market operations that depend on that asset's price.

### Finding Description
`oracle-timestamp-fresh` computes the staleness delta like this: [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

Instead of treating `ts > stacks-block-time` as an invalid/anomalous input (or clamping it safely while still enforcing monotonic freshness against the network clock), the code silently sets `delta` to `u0`. This makes the first conjunct `(<= delta max-staleness)` trivially true for *any* future-dated `ts`, no matter how large the skew.

This function gates `price-resolve`, which also persists the accepted timestamp as the new floor for future comparisons: [2](#0-1) 

```clarity
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        ...
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
    (ok final-price)))
```

Once any price update whose `publish-time` exceeds `stacks-block-time` is accepted (which happens whenever Pyth's real-world publish clock is ahead of the recorded Stacks block time — a routine clock-skew condition rather than malicious oracle data), `last-update` for that feed key is overwritten with this inflated future value. Every subsequent price update — even one carrying a fully correct, non-stale, real-world timestamp — must satisfy `(>= ts prev)` where `prev` is now this artificially inflated value. If the new genuine `ts` is smaller than the poisoned `prev`, `oracle-timestamp-fresh` returns `false`, `price-resolve` returns `ERR-ORACLE-INVARIANT`, and every function that resolves this asset's price (`get-assets`, `get-notional-evaluation`, deposit/borrow/withdraw/liquidation checks) reverts until `stacks-block-time` naturally catches up to the poisoned value.

This is a bug purely in Zest's own comparison logic (the `if (> ts stacks-block-time) u0 ...` shortcut), independent of whether the underlying Pyth/DIA data itself was correct — it is an improper-input-validation flaw in the monotonic per-feed timestamp gate, analogous in class to the Shardeum `fromBlock`/`toBlock` parsing bug where an unvalidated edge-case value defeats the intended bound check.

### Impact Explanation
Successful triggering of the future-timestamp edge case (which does not require any malicious oracle publisher, only ordinary clock skew between Pyth's wall-clock `publish-time` and Stacks' `stacks-block-time`) causes the staleness gate to be bypassed and can then poison `last-update` so that all later legitimate updates for that feed are rejected. This reverts price resolution for the affected asset, which in turn reverts `get-assets`/`get-notional-evaluation` used by deposits, borrows, withdrawals, and liquidations that reference that asset — a **temporary freezing of funds** for all positions holding or borrowing that asset until block time overtakes the poisoned timestamp.

### Likelihood Explanation
The condition `ts > stacks-block-time` is not an exotic adversarial input — it can arise from ordinary latency/clock differences between Pyth's publish clock and the Stacks chain's block timestamp, especially under block-production delays. No privileged access, DAO action, or malicious oracle data is required; the flaw lives entirely in `oracle-timestamp-fresh`'s handling of this normal edge case.

### Recommendation
Do not special-case `ts > stacks-block-time` to `delta = u0`. Compute the true (possibly negative) skew, and either reject a future-dated timestamp beyond a reasonable clock-drift tolerance, or use unsigned-safe comparisons that don't silently disable the staleness bound while also not silently ratcheting `last-update` to an inflated value. In addition, guard the `map-set last-update` update path so a single unusually large `timestamp` cannot become a permanent floor that blocks otherwise-valid subsequent updates.

### Proof of Concept
1. Pyth publishes a price update whose `publish-time` (real UTC seconds) is, due to routine Stacks block-production lag, greater than the current `stacks-block-time` recorded on-chain.
2. `resolve-pyth`/`price-resolve` calls `oracle-timestamp-fresh timestamp last-update-time max-staleness`; because `ts > stacks-block-time`, `delta` is forced to `u0`, so `(<= delta max-staleness)` passes regardless of the actual skew magnitude. [1](#0-0) 
3. `price-resolve` accepts this price and persists the inflated `timestamp` into `last-update` via `map-set`. [3](#0-2) 
4. On the next legitimate price submission with a correct, smaller real-world `ts`, `(>= ts prev)` fails because `prev` is the previously-poisoned future value, causing `price-resolve` to return `ERR-ORACLE-INVARIANT`.
5. Any market call that depends on this asset's price (deposit, borrow, withdraw, liquidate via `get-assets`/`get-notional-evaluation`) reverts, freezing user funds in that asset until `stacks-block-time` exceeds the poisoned timestamp.
