### Title
Unvalidated participant index causes index-out-of-bounds panic in PedPoP blame resolution - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame` / `AdditionalBlameMachine::blame` take attacker-controlled `sender` and `recipient` `Participant` values and index `self.commitments` (a `HashMap` keyed only by `1..=n`) via `self.commitments[&sender]` in `blame_internal`. A `Participant` is any non-zero `u16`, so a caller-supplied index `> n` is accepted by the type but absent from the map, causing a panic — the same bug class as the referenced Erigon "index out of range" fix.

### Finding Description
In `blame_internal` the sender index is used as a map key without a membership check:

```rust
// crypto/dkg/pedpop/src/lib.rs
if !bool::from(
  multiexp_vartime(&share_verification_statements::<C>(
    recipient,
    &self.commitments[&sender],   // panics if sender not in 1..=n
    Zeroizing::new(share),
  ))
  ...
```

The commitments map is populated strictly for `1 ..= n` (`AdditionalBlameMachine::new` inserts `Participant::new(i)` for `i in 1 ..= n`; `verify_r1`/`calculate_share` similarly key by `all_participant_indexes`). `Participant::new` only rejects zero, so `Participant::new(n+1)` is a valid, constructible value.

Reachability: `blame()` is the public API for adjudicating accusations of faulty DKG behavior. The `sender`, `recipient`, `msg` (an `EncryptedMessage` read from bytes) and `proof` arguments are all supplied by the party raising the accusation — unauthenticated, attacker-choosable inputs. Any accusation naming a sender index outside `1..=n` that survives `decrypt_with_proof` (or a path where decryption succeeds on a message crafted for a valid recipient) reaches the unchecked `HashMap` index and panics. The same unguarded lookup pattern exists wherever `self.commitments[&l]`/`[&sender]` is indexed by caller-provided participants in this file.

### Impact Explanation
A panic in blame resolution crashes the host process (or kills the task handling the DKG/blame transaction) whenever a party submits an accusation referencing an out-of-range participant index. In a validator/coordinator deployment this is a remotely triggerable denial of service on the key-management path — any participant (or anyone able to submit a blame claim) can abort the process evaluating blame rather than receiving an `Err`. Per the standard model this is a Medium-severity availability issue: attacker-controlled input → panic, no key or secret leakage required.

### Likelihood Explanation
Triggering only requires calling `blame`/`AdditionalBlameMachine::blame` with `sender` (or `recipient`, where used as a map key downstream) set to any `Participant` in `(n, u16::MAX]`. Such an index is trivially constructible (`Participant::new(n + 1).unwrap()`), requires no collusion, no valid key share, and no protocol participation beyond the ability to have a blame claim evaluated. The only uncertainty is whether `decrypt_with_proof` short-circuits before the lookup for every out-of-range `sender`; even if it does for `sender`, the code contains no defensive check guaranteeing this ordering, and `recipient`/other indexed paths share the same assumption.

### Recommendation
Replace the indexing `self.commitments[&sender]` with `self.commitments.get(&sender)` and return the accusing party (or a dedicated `PedPoPError`) when the key is absent. More robustly, validate at the top of `blame`/`blame_internal` that `u16::from(sender) <= n` and `u16::from(recipient) <= n` and both differ from zero-participant semantics, returning an error instead of panicking. Apply the same treatment to every `HashMap` index on caller-supplied `Participant` values in the crate (`calculate_share` is safe only because `validate_map` bounds it — keep that invariant explicit).

### Proof of Concept
```rust
// Setup: n participants complete PedPoP, producing a BlameMachine, or an
// observer builds AdditionalBlameMachine:
let machine = AdditionalBlameMachine::<Ristretto>::new(context, n, commitment_msgs).unwrap();

// Attacker submits a blame claim naming a non-existent sender.
// Participant::new only rejects 0, so n + 1 is accepted by the type system.
let sender = Participant::new(n + 1).unwrap();
let recipient = Participant::new(1).unwrap();

// msg / proof are attacker-controlled bytes (EncryptedMessage::read / signature bytes).
machine.blame(sender, recipient, msg, proof);
// -> panic: `self.commitments[&sender]` indexes a HashMap that only holds
//    keys 1..=n (crypto/dkg/pedpop/src/lib.rs, blame_internal)
```

Equivalent trigger exists for `BlameMachine::blame`, whose `commitments` map is likewise keyed `1..=n`.
