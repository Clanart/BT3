### Title
Sybil self-referral in `ReferralStorage.trigger()` allows one actor to capture both referer and referee reward shares - ([File: rewards/ReferralStorage.sol])

### Summary
`ReferralStorage.useCode()` only blocks a wallet from using its own code (`codeOwners[_code] == msg.sender`), but nothing in `useCode()`, `registerCode()`, or `trigger()` prevents an attacker from registering a code with wallet A and using it from a Sybil wallet B they also control. When B's stake is claimed through `MasterMagpie`, `trigger()` computes and credits `refererAmount` to A and `refereeAmount` to B — both amounts flow to the same economic actor for capital they alone staked, i.e., a self-directed referral rebate that was intended for independent third parties.

### Finding Description
The relevant checks are in [1](#0-0) :
```
function useCode(bytes32 _code) external {
    if (_code == bytes32(0)) revert InvalidCode();
    if (codeOwners[_code] == address(0)) revert InvalidCode();
    if (codeOwners[_code] == msg.sender) revert Circled();
    if (myReferer[msg.sender] != address(0)) revert HasReferral();
    ...
    myReferer[msg.sender] = codeOwners[_code];
    myReferees[codeOwners[_code]].push(msg.sender);
}
```
`Circled()` only compares `msg.sender` (the referee address) to `codeOwners[_code]` (the referer address), a purely address-level identity check. It has no way to detect that both addresses are controlled by the same beneficial owner — an attacker simply uses two independently funded EOAs.

`registerCode()` has the same limitation — it does not restrict who can register codes, so any attacker can trivially register a code from wallet A [2](#0-1) .

When B's staking rewards are claimed through `MasterMagpie._multiClaim`, the total claimed reward is passed to `trigger()` unconditionally as long as `myReferer[_user] != address(0)`, with no ownership/anti-Sybil check: [3](#0-2) .

`trigger()` then splits the reward-linked rebate (`basic + boosted` tier percentage) between referer and referee purely based on the `myReferer` mapping, with the only guard being `_referer == address(0)`: [4](#0-3) . Since `_referer` (wallet A) and `_referee` (wallet B) are both attacker-controlled, both `refererInfo.rewardAmount` and `refereeInfo.rewardAmount` accrue to the same actor, who later collects both via `claimReward()` [5](#0-4) .

None of `nonReentrant`, `whenNotPaused`, or existing modifiers address this because the exploit doesn't require reentrancy or bypassing pause state — it's a pure identity/Sybil gap in the referral-eligibility logic.

### Impact Explanation
This lets any user extract an extra `refererPercentage + refereePercentage` fraction of the tier rebate (`basic + boosted`) on top of the base yield they would otherwise earn on their own stake, for capital that never involved an independent referral relationship. This is a theft of unclaimed yield: value intended to reward genuine third-party referral growth is instead siphoned by self-dealing, diluting whatever pool funds `ReferralStorage`'s `MGP` balance for legitimate referrers/referees (since `claimReward()` pays from the same `MGP` balance for everyone).

### Likelihood Explanation
Fully permissionless and repeatable: an attacker only needs two wallets, no privileged role, no flash loan even required. `registerCode()` is open to anyone, `useCode()` is open to anyone with any address other than the code owner itself, and `trigger()` fires automatically whenever the referee wallet claims through `MasterMagpie`. The attacker can repeat this with unlimited Sybil wallets, or boost the referer's tier via vlMGP locking to further inflate `boostesd` via `_calBoosted()` [6](#0-5) , scaling the extracted rebate.

### Recommendation
Add an anti-Sybil/anti-self-referral safeguard beyond the literal address check, e.g.:
- Require a minimum unrelated deposit history, KYC-independent staking checkpoint, or a bonding/cooldown period between code registration and use to raise the cost of Sybil attacks (does not fully solve it but raises cost), or
- More fundamentally, redesign the rebate so it is funded from protocol emission dilution proportional to referred *new* TVL rather than being retroactively applied to the referee's own yield, removing the incentive to self-refer since there is no net gain if referer and referee are the same beneficial owner (e.g., cap total `referer+referee` distribution so that self-referral cannot exceed the non-referral baseline).
- At minimum, document/accept this as an inherent limitation of purely address-based Sybil resistance, since no on-chain check can distinguish "wallet A and B are both mine" without off-chain attestation.

### Proof of Concept
Foundry test plan:
1. Deploy `ReferralStorage`, `MasterMagpie` (or mock with `_onlyMasterMagpie` set to test contract), `vlMGP`, and `MGP` token; fund `ReferralStorage` with `MGP` balance for reward payouts.
2. Set a tier via `setTier(1, X)` with `X > 0` as owner (test setup only, not attacker-privileged).
3. From wallet A (attacker-controlled): call `registerCode(codeA)`.
4. From wallet B (attacker-controlled, different address): call `useCode(codeA)` — assert it succeeds (no `Circled()` revert since `msg.sender != codeOwners[codeA]`).
5. Simulate B staking and claiming through `MasterMagpie`, causing `_multiClaim` to invoke `IReferralStorage(referral).trigger(B, totalReward)`.
6. Assert `userInfos[A].rewardAmount == refererAmount` and `userInfos[B].rewardAmount == refereeAmount`, both nonzero.
7. Have wallet A call `claimReward()` and wallet B call `claimReward()`; assert total `MGP` received by A + B for the single stake claim by B exceeds `totalReward` alone — i.e., `(refererAmount + refereeAmount) / totalReward` matches the tier's `(basic + boosted)` rebate rate, all captured by a single beneficial owner.
8. Compare against a baseline where B has no referer (`myReferer[B] == 0`): B receives only `totalReward` with no extra rebate — demonstrating the delta is pure Sybil-farmed extra yield.

    function trigger(address _referee, uint256 _amount) external _onlyMasterMagpie {
        UserInfo storage refereeInfo = userInfos[_referee];
        address _referer = myReferer[_referee];

        if (_referer == address(0))
            return;

        UserInfo storage refererInfo = userInfos[_referer];
        uint256 tierId = userInfos[_referer].tier;
        uint256 basic = tiers[tierId].rewardPercentage;
        uint256 boostesd = _calBoosted(_referer);

        uint256 refererPercentage = (basic + boostesd) * (DENOMINATOR - sharePercent)  / DENOMINATOR;
        uint256 refereePercentage = (basic + boostesd) *  sharePercent / DENOMINATOR;
        uint256 refererAmount = _amount * refererPercentage / DENOMINATOR;
        uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;

        refererInfo.rewardAmount += refererAmount;
        refereeInfo.rewardAmount += refereeAmount;

        emit RefererRewardHarvested(_referer, refererAmount);
        emit RefereeRewardHarvested(_referee, refereeAmount);
    }
