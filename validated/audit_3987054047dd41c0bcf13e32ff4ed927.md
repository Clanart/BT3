### Title
Independent, inconsistent conflict-marker parsers in Copilot conflict resolution can silently drop legitimate code from a merged file - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`Solidity's MetadataRenderer` bug reduces to: a state value derived from user/attacker-controlled input (an empty `items` array) is consumed by two code paths that disagree on how to treat it, and the mismatch is only discovered when a core operation (`mint`) blows up. The Desktop analog is the AI merge-conflict-resolution pipeline, where **two independently implemented conflict-marker parsers** — `extractConflictHunks` (used to build the hunk list sent to the model and to validate the model's response) and the marker-scanner inside `reassembleResolvedFile` (used to actually splice content back into the file) — can disagree on how many/which conflict blocks exist in a file with a malformed marker. The count-only validation (`validateResolutionPaths`) does not catch this disagreement, and the mismatch causes a legitimate conflict block's content to be silently deleted when the resolved file is written to disk.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) scans a conflicted file and, for a well-formed block, extracts `oursContent`/`theirsContent`. Its "ours" collection loop only stops on a `baseMarker` or `separatorMarker`: [1](#0-0) 

If a conflict block never has a `=======` separator before EOF (or before a later, unrelated `=======`), the loop keeps swallowing subsequent lines — including any following, otherwise well-formed `<<<<<<<...=======...>>>>>>>` block — as if they were part of the first block's "ours" content. When no closing marker is ever found, the whole malformed hunk (and everything it swallowed) is dropped silently: [2](#0-1) 

This hunk list (`file.hunks`) is what determines both what is sent to Copilot and the expected hunk count used later for validation.

Separately, `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) re-scans the **same raw file content** with its own, differently-behaved well-formedness check: for a malformed opening marker it only advances one line and re-enters the scan loop, so it *will* independently discover and treat a subsequent, well-formed conflict block as a legitimate hunk: [3](#0-2) 

`validateResolutionPaths` (`app/src/lib/copilot-conflict-resolution.ts:473-521`) only checks that the *count* of hunks returned by the model matches `expectedFiles`'s hunk count computed from `extractConflictHunks` — it never verifies that the reassembly parser agrees on hunk boundaries: [4](#0-3) 

Because `extractConflictHunks` under-counts hunks in the crafted-malformed-marker scenario while `reassembleResolvedFile` finds an "extra" one, `reassembleResolvedFile`'s `hunkIndex < hunkResolutions.length` guard fails for that extra block: [5](#0-4) 

...yet the code still consumes/removes the block from the output (`i = closingIndex + 1` unconditionally skips the original lines) without splicing in any replacement content. The net effect is that a full, legitimately-conflicting code block is deleted from the reassembled file with no error, no validation failure, and no visual difference in the resulting diff other than the missing code.

### Impact Explanation
This breaks the invariant that "resolved content == original non-conflicted lines + model's per-hunk resolutions, one-to-one". Instead, an attacker who controls one side of a merge (a branch, PR, or fetched ref the victim merges/rebases against) can craft a file with a malformed conflict marker sequence such that a second, real conflicting hunk (e.g., a security check, a dependency pin, an important business-logic branch) is silently stripped from the file that Desktop writes to disk and that the user then stages and commits/pushes. This is a silent corruption of what the user commits, matching the class of impact the report seeks (not a crash/DoS — the operation "succeeds" and produces a plausible-looking but corrupted result), triggered purely by attacker-controlled repository/branch content with no local access or credentials needed.

### Likelihood Explanation
Requires the victim to use the "Resolve with Copilot" conflict-resolution feature (Copilot conflict resolution system prompt at `app/src/lib/copilot-conflict-resolution.ts:190-254`) on a merge/rebase/cherry-pick that includes attacker-influenced content, and requires the attacker to specifically craft a malformed-then-legitimate marker sequence in one file. This is a realistic but non-trivial setup — it needs a fairly deliberate PoC file, but no privileged access, no social engineering beyond a normal collaborative merge, and no separate malware. I was not able to trace the full call-site wiring (where `validateResolutionPaths` and `reassembleResolutions` are invoked relative to each other in the UI orchestration layer) due to index truncation, so I can't fully confirm there isn't an additional guard elsewhere in the pipeline; this should be verified by an engineer with full repository access.

### Recommendation
Short term: in `reassembleResolvedFile`, when the malformed-marker fallback path (`!hasSeparator || closingIndex === -1`) is taken, do not keep scanning forward for new conflict blocks; treat this as a fatal state (throw `CopilotValidationError`) rather than silently continuing, and make `extractConflictHunks` and the reassembly scanner share a single implementation so they can never disagree on hunk boundaries/count. Long term: change reassembly to match hunks against the original file's `<<<<<<< / ======= / >>>>>>>` byte offsets computed once (during `extractConflictHunks`) rather than re-parsing the raw file a second time, and fail the whole resolution (rather than silently dropping content) if the number of consumed hunks does not exactly equal the number of resolutions supplied by the model.

### Proof of Concept
Conceptual file with an attacker-controlled malformed marker directly preceding a legitimate conflict block (both `extractConflictHunks` and `reassembleResolvedFile` are pure functions that can be unit-tested with this input to observe the divergence):
```
line before
<<<<<<< HEAD
some ours content that never gets a "=======" before EOF-ish
<<<<<<< HEAD
real ours
=======
real theirs
>>>>>>> feature
```
- `extractConflictHunks` on this content: the first `<<<<<<<` never finds a `=======`/base marker, so its "ours" loop keeps consuming lines, including the second `<<<<<<<`, `real ours`, `=======`, `real theirs`, treating `=======` as *its own* separator and the trailing `>>>>>>> feature` as its own closing marker → it emits exactly **one** hunk whose `theirsContent` is `real theirs` and never records a second hunk.
- `reassembleResolvedFile`, given a `hunkResolutions` array of length 1 (matching `validateResolutionPaths`'s expectation), independently re-scans the same raw content: the outer `<<<<<<<` fails its look-ahead (no `=======` found before hitting the *second* `<<<<<<<`'s `=======`... — depending on exact scan order this either mis-splices content from the wrong logical hunk or silently drops the `real ours`/`real theirs` block once `hunkIndex` exceeds `hunkResolutions.length`), producing a written file that differs from what the single validated resolution accounts for.

This demonstrates the same fundamental bug class as the Solidity finding: an attacker-influenced, edge-case input (empty/malformed structure) is treated inconsistently by two code paths that are supposed to agree, and the mismatch surfaces only downstream — in Desktop's case as silently corrupted committed content rather than a revert.
