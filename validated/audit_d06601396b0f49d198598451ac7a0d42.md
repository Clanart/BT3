## Analysis

The M-14 report's core invariant is: *"a token-transfer call that returns `success=true` without reverting must not be trusted as proof that value actually moved — the return data / balance delta must be checked, because a non-standard/malicious ERC20 can return `false` (or nothing) while doing nothing."*

Hyperbridge's `IntentGatewayV2` places/fills orders and locks/escrows/sweeps arbitrary ERC-20 tokens through a shared `CallDispatcher` contract. I compared how token movement is verified in two places that route through `CallDispatcher`:

1. **`placeOrder`'s predispatch sweep** (`evm/src/apps/IntentGatewayV2.sol`) builds low-level `transfer()` calls, routes them through `CallDispatcher.dispatch`, and then *independently re-verifies* actual funds received via a `balanceOf` delta (`balancesBefore[i]` vs. post-dispatch balance) before crediting `order.inputs[i].amount`. [1](#0-0) 

2. **`_execute`'s postdispatch sweep** (`evm/src/apps/intentsv2/IntentsBase.sol`), used after an order is filled to collect leftover output-token dust from the dispatcher, does the opposite: it reads the dispatcher's balance *before* the call, builds a `transfer()` call to that recorded balance, dispatches it through `CallDispatcher`, and then unconditionally emits `DustCollected(token, balance)` — with no post-call balance check that the tokens actually arrived at `address(this)`. [2](#0-1) 

`CallDispatcher.dispatch` itself only checks `extcodesize(to) > 0` (guards against EOA/no-code targets, the literal Solmate check) and that the raw `.call` did not revert (`success`) — it never decodes or validates the ERC-20 boolean return value: [3](#0-2) 

So the exact Solmate gap (trusting a non-reverting call as proof of transfer) is closed for the "target has no code" case, but **not** for the "target is a contract whose `transfer()` returns `false` (or returns nothing meaningfully checked) without reverting" case — this is precisely the well-known non-standard-ERC20 pattern (e.g., tokens that signal failure via a `false` return rather than reverting). `_execute`'s sweep path has no analog to the balance-delta re-check that `placeOrder`'s predispatch path has.

### Impact
An order whose `output.assets` includes such a non-standard/adversarial ERC-20 (the order/output token set is attacker-controlled input to `fillOrder`/`_execute`) can cause the protocol to believe dust tokens were swept back into the gateway (`DustCollected` emitted, accounting updated) when no value actually moved. The tokens remain stuck in the shared `CallDispatcher` — a single contract instance reused across all orders — corrupting the dust/fee accounting and potentially stranding or misattributing funds intended for one beneficiary's fill in the shared dispatcher balance.

### Caveat
I was not able to fully trace whether a downstream consumer of this stranded dispatcher balance (e.g., a subsequent `placeOrder` predispatch call, which measures balance deltas on the same shared dispatcher) could be manipulated to misattribute those stranded funds to an unrelated order, which would elevate this from an accounting/dust-loss bug to a direct fund-redirection exploit. That composability path would need deeper tracing across concurrent order flows than the available context allowed to confirm with certainty.

### Title
Unverified ERC-20 return value in `_execute` postdispatch sweep allows dust/fund loss via non-standard tokens - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`_execute()`'s sweep of leftover output-asset balances from the shared `CallDispatcher` relies solely on the low-level call's `success` flag (checked inside `CallDispatcher.dispatch`) and never confirms via a balance delta that the swept tokens actually landed on the gateway, unlike the equivalent predispatch-sweep logic in `IntentGatewayV2.placeOrder`.

### Finding Description
`_execute` snapshots the dispatcher's token balance, builds a `transfer(address(this), balance)` call, dispatches it via `ICallDispatcher(dispatcher).dispatch(...)`, and unconditionally emits `DustCollected(token, balance)`. [4](#0-3) 
`CallDispatcher.dispatch` checks `extcodesize(to) != 0` and that the call itself does not revert, but it never inspects the ABI-encoded boolean return value of `transfer()`. [3](#0-2) 
A token contract that returns `false` on a failed transfer instead of reverting (a well-documented non-standard ERC-20 pattern, the same class the Solmate/M-14 report warns about) will cause `success=true` even though no tokens moved. In contrast, `placeOrder`'s predispatch sweep performs an explicit `balanceOf` before/after comparison to determine the *actual* received amount rather than trusting the call outcome. [5](#0-4) 

### Impact Explanation
Because `_execute` never re-derives actual received balance, the gateway's dust accounting and events (`DustCollected`) can diverge from reality: value is presumed collected when it is not, and the tokens remain stranded on the shared, reusable `CallDispatcher` contract instance used by every order.

### Likelihood Explanation
The order's `output.assets` token list is attacker-supplied via `fillOrder`, so any user constructing/filling an order that references a self-controlled non-standard ERC-20 as an output asset can trigger this path deterministically — no privileged role, relayer, or governance action is required.

### Recommendation
Mirror the predispatch-sweep pattern in `_execute`: snapshot `balanceOf(address(this))` before dispatching the sweep call and compare after, only emitting `DustCollected`/crediting for the actually-observed delta, or switch the sweep calls to use `SafeERC20.safeTransfer` semantics executed directly rather than raw `abi.encodeWithSelector` calls routed through a dispatcher that only checks call success.

### Proof of Concept
1. Deploy a malicious ERC-20 `EvilToken` whose `transfer()` always returns `false` without reverting and never moves balances.
2. Create and fill an order whose `order.output.assets` includes `EvilToken`, with `order.output.call` non-empty so `_execute` is invoked with the dispatcher holding some `EvilToken` balance.
3. Observe `_execute` computes `balance = IERC20(EvilToken).balanceOf(dispatcher) > 0`, builds a sweep `Call`, and `CallDispatcher.dispatch` succeeds (transfer returns `false` but doesn't revert, `extcodesize>0`).
4. `DustCollected(EvilToken, balance)` is emitted and internal accounting treats the amount as collected, while `EvilToken.balanceOf(dispatcher)` remains unchanged — the tokens never reach `address(this)`.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
