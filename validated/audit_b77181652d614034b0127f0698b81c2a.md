### Title
Governance-settable `kip71.gastarget = 0` causes division-by-zero panic in `NextMagmaBlockBaseFee`, crashing all nodes on every subsequent block - ([File: params/kip71_config.go])

### Summary
`KIP71Config.NextMagmaBlockBaseFee` computes the base fee for the next block by dividing intermediate values by `GasTarget`. Unlike `BaseFeeDenominator`, which has an explicit zero-guard, `GasTarget` has no such protection. The governance parameter `kip71.gastarget` that feeds this field has a `noopFormatChecker` that accepts any `uint64` value, including `0`. Once such a value is voted in and activated, every node computing the next block's base fee will hit an integer division by zero and panic, crashing the node process. Since `NextMagmaBlockBaseFee`/`VerifyMagmaHeader` runs during ordinary block header processing for every block after Magma is active, this results in a chain-wide denial of service.

### Finding Description
`GasTarget` is read directly from governance state with no zero check: [1](#0-0) 

When `GasTarget == 0` and `parentGasUsed != 0` (which is essentially guaranteed as any usage above the zero target), the code takes the "usage above target" branch and divides by `gasTarget` (which is `0`): [2](#0-1) 

The same unguarded division exists in the "usage below target" branch: [3](#0-2) 

`big.Int.Div` in Go panics with "division by zero" when the divisor is zero, so this is a direct Go-runtime analog of the FPE/CWE-369 condition described in the PaddlePaddle advisory (integer division by zero causing a runtime crash).

Crucially, the governance parameter registry defines a `noopFormatChecker` (always returns `true`) for `Kip71GasTarget`, in contrast to `Kip71BaseFeeDenominator` which explicitly rejects `0`: [4](#0-3) 

The `checkConsistency` function in header governance vote validation also does not perform any additional bound/nonzero check for `Kip71GasTarget` — it simply allows the vote to pass: [5](#0-4) 

Thus a governance vote setting `kip71.gastarget = 0` is accepted by the node software's validation logic. Once the vote is finalized and this value takes effect at the next governance epoch, `VerifyMagmaHeader`/`NextMagmaBlockBaseFee` is invoked on every subsequent block by every node (validators and full nodes alike) as part of ordinary block header validation, and any block with nonzero gas usage will trigger the panic: [6](#0-5) 

### Impact Explanation
This causes an unrecoverable panic/crash in the base-fee computation path that runs on every block for every node in the network after the malicious/misconfigured parameter takes effect. This is a chain-wide denial-of-service: all full nodes and validators panic identically, halting the network (or repeatedly crash-looping if restarted, since the parameter persists in governance state and the same block will be reprocessed). This matches "acceptance of an invalid state / state divergence" and denial-of-service class impacts and is a direct, severe consensus-critical failure, going beyond mere resource exhaustion.

### Likelihood Explanation
The governance parameter format checker performs no bounds/nonzero validation for `Kip71GasTarget`, and header governance vote consistency-checking also imposes no restriction on this parameter (unlike `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`, which cross-validate against each other). Under a `single` governance mode, only the governing node can vote such a parameter change, but no code path anywhere in the vote/format validation stack rejects `GasTarget = 0`, meaning this can be introduced through the standard supported governance workflow rather than requiring any exploit of a separate bug. The absence of the same zero-guard that exists for `BaseFeeDenominator` on the very next parameter strongly suggests this is an overlooked edge case rather than an intentionally-permitted value.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally `Kip71MaxBlockGasUsedForBaseFee`) rejecting `0`, mirroring the existing check for `Kip71BaseFeeDenominator`:
```go
FormatChecker: func(cv any) bool {
    v, ok := cv.(uint64)
    return ok && v != 0
},
```
Additionally, apply a defensive zero-guard directly inside `NextMagmaBlockBaseFee` (as already done for `BaseFeeDenominator`) so that a corrupted or legacy-persisted `GasTarget = 0` value cannot crash the node regardless of upstream validation.

### Proof of Concept
1. Deploy/point a test network with Magma (KIP-71) enabled and `governance.governancemode = "single"`.
2. As the governing node, submit a governance vote `kip71.gastarget = 0` (this passes `Kip71GasTarget`'s `noopFormatChecker` and `checkConsistency`, since no other check rejects it) — see the accepted-vote test data showing arbitrary `uint64` values pass: [7](#0-6) 
3. Wait for the governance change to take effect at the next epoch/governance-effective block.
4. Produce (or process) any block whose gas usage differs from `0` (essentially any normal block with `MaxBlockGasUsedForBaseFee`-bounded usage above `GasTarget=0`).
5. All nodes calling `NextMagmaBlockBaseFee`/`VerifyMagmaHeader` for that block panic on `x.Div(x, new(big.Int).SetUint64(gasTarget))` with divisor `0`, crashing the node process network-wide.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {

	}
	// Verify the baseFee is correct based on the parent header.

		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
