### Title
Panic on out-of-range `recipient` in `BlameMachine::blame` / `AdditionalBlameMachine::blame` crashes the node evaluating a blame accusation - (File: crypto/dkg/pedpop/src/encryption.rs, crypto/dkg/pedpop/src/lib.rs)

### Summary
The IoTeX bug class is a panic triggered while processing untrusted input, taking the validating process down instead of surfacing an error. The same class exists in Serai's PedPoP DKG blame handling: `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]`, and `blame_internal` indexes `self.commitments[&sender]`, with no validation that `sender`/`recipient` are registered participants. A blame accusation is attacker-controlled protocol input; an accusation naming a `Participant` index outside the registered set (e.g. `n + 1`) causes a HashMap index panic, crashing the evaluating node rather than returning a fault verdict.

### Finding Description
- `BlameMachine::blame` and `AdditionalBlameMachine::blame` accept attacker-supplied `(sender, recipient, msg, proof)` and forward them verbatim to `blame_internal` (crypto/dkg/pedpop/src/lib.rs:623-631, 674-682). There is no check that `sender` or `recipient` is in `1 ..= n`.
- `blame_internal` calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)` (crypto/dkg/pedpop/src/lib.rs:582).
- `decrypt_with_proof` first verifies `msg.pop` (a Schnorr PoP over `context`, `msg.key`, `sender`, and the ciphertext bytes), then evaluates `self.enc_keys[&decryptor]` (crypto/dkg/pedpop/src/encryption.rs:388). `enc_keys` only contains keys for participants `1 ..= n` registered via `Decryption::register` (crypto/dkg/pedpop/src/encryption.rs:351-362). For `recipient` not in the map, indexing panics.
- If `recipient` is valid but `sender` is out of range and the DLEq proof path is passed, `self.commitments[&sender]` at crypto/dkg/pedpop/src/lib.rs:599 also panics.
- Reaching the panic requires a valid `pop` signature; the attacker generates `key`/`pop` themselves with `SchnorrSignature::sign`, so this is fully attacker-constructible from public inputs (crypto/dkg/pedpop/src/encryption.rs:374-379).
- Other panic sites in the same crate were checked and are not reachable from untrusted input: `Decryption::register`'s duplicate-participant `assert!` is guarded by `validate_map` and HashMap key uniqueness (crypto/dkg/pedpop/src/lib.rs:57-83, 305-316); `self.commitments[&l]` in `calculate_share` is safe because `validate_map` constrains `l` to the participant set whose commitments were all registered (crypto/dkg/pedpop/src/lib.rs:490). The blame path lacks an equivalent guard.

### Impact Explanation
An unprivileged DKG participant (or any party able to submit a blame accusation to an honest node, per the protocol's blame-propagation design) can crash every node that evaluates the accusation by naming a `recipient` (or `sender`) index outside `1 ..= n`. This is a remote denial of service of threshold-key infrastructure: instead of blame resolution identifying a faulty party, the evaluating process aborts on a HashMap panic, halting DKG completion and any dependent signing. Equivalent in effect to the IoTeX fix — untrusted input causes a fatal panic rather than a rejectable error.

### Likelihood Explanation
Triggering requires only a well-formed `EncryptedMessage`/`EncryptionKeyProof` (the attacker controls `key`, `pop`, and `proof`) plus an out-of-range `Participant` index — no key compromise, collusion, or racing needed. The only mitigating factor is that the panic occurs during blame evaluation (a post-fault path), not the happy path, and `Participant` is a typed index rather than raw bytes; whether accusations are auto-evaluated is deployment-dependent. Rated Medium: reliable crash, but only on the blame/accusation handling path.

### Recommendation
In `blame_internal` (crypto/dkg/pedpop/src/lib.rs:575-609), validate `sender` and `recipient` against `self.commitments`/`self.encryption.enc_keys` membership before use, returning a defined result (e.g. blame the accuser/sender, or an error variant) instead of indexing. Replace `self.enc_keys[&decryptor]` in `Decryption::decrypt_with_proof` and `self.commitments[&sender]` in `blame_internal` with `.get()` + error propagation so malformed accusations are rejected rather than fatal.

### Proof of Concept
```rust
// After a PedPoP DKG completes and each honest party holds a BlameMachine<C>,
// an attacker constructs an accusation naming a non-participant recipient.
let n = params.n();

// Attacker builds a self-consistent EncryptedMessage with a valid PoP.
let key = Zeroizing::new(C::random_nonzero_F(rng));
let pub_key = C::generator() * key.deref();
let nonce = Zeroizing::new(C::random_nonzero_F(rng));
let pub_nonce = C::generator() * nonce.deref();
let msg_bytes = Zeroizing::new(SecretShare::<C::F>(C::F::ZERO.to_repr()));
let pop = SchnorrSignature::<C>::sign(
    &key, nonce,
    pop_challenge::<C>(context, pub_nonce, pub_key, Participant::new(1).unwrap(), msg_bytes.as_ref()),
);
let msg = EncryptedMessage { key: pub_key, pop, msg: msg_bytes };

// recipient = n + 1 was never registered in Decryption::enc_keys.
let bogus_recipient = Participant::new(n + 1).unwrap();

// Honest node evaluates the accusation:
//   blame -> blame_internal -> decrypt_with_proof ->
//   self.enc_keys[&bogus_recipient]  =>  HashMap panic: "no entry found for key"
blame_machine.blame(Participant::new(1).unwrap(), bogus_recipient, msg, None);
// Process aborts instead of identifying a faulty party.
```

Uncertainties: whether `blame` accusations are auto-evaluated by a given deployment is caller-defined (the library leaves networking to the integrator), and `AdditionalBlameMachine::new` documents panics for invalid *commitments* — however, no documentation covers out-of-range `sender`/`recipient` indexes to `blame`, so this is an undocumented panic on protocol input rather than documented-misuse behavior.
