### Title
Legacy `pattern` field silently fails to match `Write` tool content, allowing block/warn rules to be bypassed - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`Rule.from_dict` converts a legacy `pattern:` frontmatter field into an implicit `Condition` by inferring `field` solely from `event`, hardcoding `field='new_text'` for all `event: file` rules regardless of which tool (`Write`, `Edit`, `MultiEdit`) actually triggers the hook. In `rule_engine.py`, `_extract_field` only resolves `new_text`/`new_string` from `tool_input.get('new_string', '')`, which is empty for `Write` operations (whose payload key is `content`), so a legacy-style `pattern` rule intended to block/warn on file writes never actually matches `Write` tool_input, while the equivalent explicit `conditions:` form (using `field: content`) does match correctly.

### Finding Description
`Rule.from_dict` in [1](#0-0)  infers the condition field from `event` only: for `event == 'file'` it always sets `field = 'new_text'`, with no distinction between `Write`, `Edit`, and `MultiEdit` tools. The evaluation engine's `_extract_field` in [2](#0-1)  resolves `field == 'new_text'` strictly via `tool_input.get('new_string', '')`, but `Write` tool_input carries its payload under the `content` key, not `new_string` — that mapping is only handled for `field == 'content'` at [3](#0-2) . Consequently, a legacy `pattern:`-based rule with `event: file` produces an empty string for `Write` operations, and the regex/contains/etc. check in `_check_condition` at [4](#0-3)  fails to match against empty text, so the rule never triggers for `Write`. The exact same policy intent expressed via the explicit `conditions:` list (e.g. `field: content`, as shown in the plugin's own documentation and `/hookify` generation templates [5](#0-4) ) does correctly detect and block the content. This breaks the stated invariant that legacy and explicit rule forms are equivalent.

The reachable attacker path is: a repository ships (or `/hookify:create`/generation writes) a `.claude/hookify.*.local.md` file using the legacy simple-pattern format with `event: file` and `action: block` intended to prevent sensitive content from being written to disk (e.g., blocking secrets from being written into a synced/exported file). Because `load_rules`/`load_rule_file` in [6](#0-5)  and `pretooluse.py`'s dispatch [7](#0-6)  route all of `Edit`, `Write`, `MultiEdit` under the single `event: 'file'` bucket, the operator/maintainer believes the block rule covers all file-writing tools, but it silently never fires for `Write`, letting a `Write` call carrying the same sensitive payload proceed unblocked — exfiltrating/persisting sensitive code, secrets, or diffs to disk or another local/remote sink without warning or blocking.

No existing validation catches this: `load_rule_file` only checks for malformed YAML/IO errors, not semantic equivalence between legacy and explicit forms, and there is no test enforcing that both forms produce the same effective condition set.

### Impact Explanation
This maps to the "Sensitive code, prompt, token, diff, or local file disclosure to an unintended local or remote sink" impact category. A rule author (human or `/hookify` LLM-driven generation) who intends to block sensitive writes using the simpler legacy syntax gets a false sense of security: the block silently doesn't apply to `Write` tool invocations, so an LLM session (potentially influenced by a prompt injection from repo content) can write secrets/credentials/diffs to a file (e.g., a file later synced, committed, or exfiltrated) without the intended guardrail activating.

### Likelihood Explanation
High feasibility and fully repeatable: it requires no special privilege beyond being able to place a `.claude/hookify.*.local.md` file in the repository (which is exactly what `/hookify` generation does, and what a malicious or careless repo-shipped rule file would contain) using the documented legacy `pattern:` + `event: file` format. The bug is deterministic — every `Write` invocation triggers the divergence, not just an edge case.

### Recommendation
In `Rule.from_dict`, when converting the legacy `pattern` field for `event == 'file'`, do not hardcode a single field name. Instead, either: (1) generate multiple OR'd conditions/checks covering `content`, `new_text`/`new_string`, and `old_text` so the legacy form covers the same tool_input shapes as the explicit form, or (2) make `_extract_field`'s `new_text` handling also fall back to `tool_input.get('content')` the same way `content` does. Add a unit/invariant test asserting that for every event/tool combination, a legacy-pattern rule and an equivalent explicit-conditions rule produce identical `_rule_matches` results.

### Proof of Concept
```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

engine = RuleEngine()

# Legacy-style rule: intended to block API_KEY from ever being written to a file
legacy_rule = Rule.from_dict(
    {"name": "block-api-key", "enabled": True, "event": "file",
     "pattern": "API_KEY", "action": "block"},
    "Blocked: API key detected in file write"
)

# Explicit-style rule with equivalent intent
explicit_rule = Rule.from_dict(
    {"name": "block-api-key-explicit", "enabled": True, "event": "file",
     "conditions": [{"field": "content", "operator": "contains", "pattern": "API_KEY"}],
     "action": "block"},
    "Blocked: API key detected in file write"
)

write_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Write",
    "tool_input": {"file_path": "/tmp/leak.txt", "content": "API_KEY=sk-12345"}
}

legacy_result = engine.evaluate_rules([legacy_rule], write_input)
explicit_result = engine.evaluate_rules([explicit_rule], write_input)

assert legacy_result == {}, "BUG: legacy rule failed to block Write despite matching content"
assert explicit_result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
```
Expected (buggy) behavior: `legacy_result` is `{}` (operation allowed) while `explicit_result` correctly denies — demonstrating the legacy/explicit semantic divergence and the resulting block-evasion for `Write` tool operations.

def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)

        except (IOError, OSError, PermissionError) as e:
            # File I/O errors - log and continue
            print(f"Warning: Failed to read {file_path}: {e}", file=sys.stderr)
            continue
        except (ValueError, KeyError, AttributeError, TypeError) as e:
            # Parsing errors - log and continue
            print(f"Warning: Failed to parse {file_path}: {e}", file=sys.stderr)
            continue
        except Exception as e:
            # Unexpected errors - log with type details
            print(f"Warning: Unexpected error loading {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
            continue

    return rules


def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule
