### Title
`Verifier::update_finalized_payouts` binds a withdrawal's payer to `NULL` if an attacker RBF-replaces the honest operator's payout tx with an OP_RETURN whose push isn't exactly 32 bytes - ([File: core/src/verifier.rs])

### Summary
The payout transaction created by `create_payout_txhandler` signs only input0/output0 with the user's `SinglePlusAnyoneCanPay` signature and uses the RBF-enabled `DEFAULT_SEQUENCE = Sequence(0xFFFFFFFD)`; the anchor and OP_RETURN outputs are unsigned by that signature. Because the tx opts into replacement, any unprivileged party can submit a fee-bumping full replacement that reuses the same signed input0/output0 but corrupts the OP_RETURN push length, making `XOnlyPublicKey::from_slice` fail in `Verifier::update_finalized_payouts`, permanently recording `payout_payer_operator_xonly_pk = NULL` for that withdrawal.

### Finding Description
Binding claimed: `payout_payer_operator_xonly_pk` for withdrawal `i` == the xonly pubkey of the operator `O` whose broadcast tx funded that payout's `input0`/`output0`.

Trace:
- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds the payout tx with input0 signed by the user (`SinglePlusAnyoneCanPay`), and appends output1 (anchor) and output2 (OP_RETURN with `O`'s xonly pk) unsigned by that user signature, using `DEFAULT_SEQUENCE` from `core/src/builder/transaction/txhandler.rs:27` = `Sequence::ENABLE_RBF_NO_LOCKTIME` (`0xFFFFFFFD`), which is BIP125-replaceable.
- `Operator::withdraw` (`core/src/operator.rs:560-691`) verifies only the user's `SinglePlusAnyoneCanPay` signature over input0/output0 (`calculate_sighash_txin(0, ...)`), then calls `fund_raw_transaction` with `add_inputs: Some(true)` and broadcasts via `sign_raw_transaction_with_wallet`/`send_raw_transaction`.
- Because `SinglePlusAnyoneCanPay` on input0 commits only to input0's outpoint/script/amount and output0, outputs at index 1 (anchor) and index 2 (OP_RETURN with `O`'s pubkey) are **not** covered by any signature that the network enforces beyond the operator's own choice at broadcast time.
- Since the tx signals RBF, an unprivileged attacker who observes it in the mempool can construct and broadcast a standard BIP125 replacement: keep input0's outpoint/witness (the signature stays valid because it doesn't commit to the mutated fields), keep output0 unchanged, add the attacker's own input/fee to satisfy the higher-fee RBF rule, and replace output2's OP_RETURN push with 31 or 33 bytes. This requires no operator or verifier key material — the attacker only needs to pay fees, matching the stated attacker capability set.
- `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) finds the txid that actually spent the withdrawal UTXO via `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`), which is fed by `bitcoin_syncer` recording whichever transaction is mined spending that outpoint (`core/src/bitcoin_syncer.rs:143-164`) — there is no cross-check against the txid the operator itself submitted via its own tx_sender.
- `update_finalized_payouts` computes `operator_xonly_pk = get_first_op_return_output(...).and_then(parse_op_return_data).and_then(|b| XOnlyPublicKey::from_slice(b).ok())`. A 31/33-byte push parses fine as OP_RETURN data but fails `XOnlyPublicKey::from_slice`, yielding `None`.
- `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`) writes this `None` as SQL `NULL` into `payout_payer_operator_xonly_pk`. This write happens exactly once, driven by the immutable on-chain spend of the withdrawal outpoint, with no later correction mechanism.
- `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-51`) and `get_first_unhandled_payout_by_operator_xonly_pk` filter with SQL `=` on the operator's own xonly pk, which never matches `NULL`, so `O` never finds this withdrawal as unhandled and is never reimbursed. Separately, `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) explicitly treats a `None` payer pubkey as "assume malicious" (`core/src/verifier.rs:1882-1885`), so if `O` later tries to kick off for this deposit anyway, the kickoff is flagged malicious.

Existing guards that don't prevent this: `SECP.verify_schnorr` in `Operator::withdraw` only authenticates input0/output0 against the user, not the OP_RETURN; `fund_raw_transaction`/`sign_raw_transaction_with_wallet` don't pin the tx as non-replaceable; nothing in `update_finalized_payouts` reconciles against the operator's own broadcast txid.

### Impact Explanation
An honest operator `O` who genuinely fronted a withdrawal's BTC becomes permanently unable to claim reimbursement for that withdrawal, because the on-chain record used by `get_first_unhandled_payout_by_operator_xonly_pk` is `NULL` and can never equal `O`'s pubkey. Worse, because `is_kickoff_malicious` treats `NULL` as "assume malicious," any subsequent kickoff `O` sends for that deposit is treated as malicious, which can lead to a challenge and loss of `O`'s posted collateral. This is repeatable per-withdrawal and is not specific to one operator or deposit — any payout transaction is subject to this class of manipulation. This matches the Critical category "an honest operator permanently unable to be reimbursed" (and potentially "an honest operator's collateral burned").

### Likelihood Explanation
Preconditions: a withdrawal is in flight and the operator has broadcast (but not yet deeply confirmed) the RBF-enabled payout tx. The attacker needs only: (1) the ability to observe the mempool/relay network, (2) any UTXO(s) to fund a fee-bumped replacement, and (3) awareness that the tx signals BIP125 replacement (`nSequence = 0xFFFFFFFD`, a public consensus-visible field). No verifier/operator/aggregator privilege, key share, or majority hashrate is required — this is a standard RBF replacement using a signature (`SinglePlusAnyoneCanPay`) that intentionally does not commit to the anchor/OP_RETURN outputs. The only friction is a modest fee premium to satisfy RBF rules and the timing window before the operator's original tx confirms, both of which are realistic and repeatable for every withdrawal cycle.

### Recommendation
Do not rely solely on OP_RETURN parsing of whatever transaction happens to spend the withdrawal UTXO. Either (a) have the operator's own signature (or an additional covenant/commitment enforced by the withdrawal's taproot script, not just a `SinglePlusAnyoneCanPay` key-spend) cover the OP_RETURN output so it cannot be mutated by a fee-bumping replacement, (b) disable RBF (`nSequence = 0xFFFFFFFE/FFFFFFFF`) on the payout tx's input0 so it cannot be replaced by anyone but the original broadcaster, and/or (c) have verifiers reconcile the payer's identity against the txid the operator explicitly recorded/submitted via its own outbound channel (e.g., tx_sender records) rather than trusting whichever transaction ultimately spends the outpoint on-chain.
