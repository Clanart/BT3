### Title
Out-of-bounds read in CLVM canonical-atom length-prefix parsing during mempool dedup checks - (File: chia/full_node/mempool_manager.py)

### Summary
`is_atom_canonical()` in `chia/full_node/mempool_manager.py` parses the CLVM atom length-prefix directly from attacker-controlled spend-bundle solution bytes without validating that the declared prefix length actually fits inside the remaining buffer, mirroring the root cause of CVE-2017-17840 (`process_iscsid_broadcast` trusting a length field before a write, causing an out-of-bounds access). [1](#0-0) 

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads the leading byte at `offset`, determines a `prefix_len` (0–5 extra bytes) from its high bits, and then unconditionally loops `prefix_len` times, incrementing `offset` and indexing `clvm_buffer[offset]` to build `atom_len`, with no check that `offset + prefix_len < len(clvm_buffer)`: [2](#0-1) 

This is invoked by `is_clvm_canonical()`, which walks an entire CLVM-serialized buffer (a spend's solution bytes) atom-by-atom, calling `is_atom_canonical` at each atom boundary and advancing `offset` by the returned `atom_len` (which itself is derived purely from attacker-supplied length bytes, unchecked against the buffer size): [3](#0-2) 

Per `.cursor/context/clvm-execution.md`, `is_clvm_canonical()` is used to determine DEDUP-eligibility for spends processed by the mempool manager during spend-bundle admission — i.e., it runs on solution bytes taken from an untrusted, externally submitted `SpendBundle` before/alongside CLVM cost validation. [4](#0-3) 

A submitter can craft a solution whose final atom's length-prefix byte claims a multi-byte prefix (e.g. `0xF8`, needing 4 additional length bytes) but truncate the buffer right after that byte. `is_atom_canonical` will then index past the end of `clvm_buffer`, raising an unhandled `IndexError` in Python (the memory-safe analog of the C buffer overflow described in the CVE, since Python bounds-checks byte indexing but the code performs no domain-level length validation before trusting the attacker's length field).

### Impact Explanation
An `IndexError` raised out of `is_clvm_canonical`/`is_atom_canonical` during spend-bundle admission is not wrapped in a try/except at the call site material to this parsing routine (based on the surrounding code inspected, `check_removals` and neighboring dedup-eligibility logic in `mempool_manager.py` do not appear to guard this specific function). An uncaught exception during processing of a single submitted spend bundle can abort that bundle's mempool-admission task; if this occurs in a shared executor/thread-pool context used for spend validation across the mempool manager, this fits the "spend-triggered transaction-processing halt" impact category — an unprivileged submitter can trigger it with one crafted `SpendBundle`.

### Likelihood Explanation
Reachability is straightforward: any wallet user or spend-bundle submitter fully controls the solution bytes for the coin spends inside a `SpendBundle`, and dedup-eligibility checks (which call `is_clvm_canonical`) run as a normal part of admitting a spend bundle to the mempool. Crafting a truncated multi-byte atom length-prefix at the tail of a solution requires no special privileges, keys, or coordination.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before indexing `clvm_buffer[offset]` in the prefix-parsing loop (and in `is_clvm_canonical()`'s outer loop before dereferencing `clvm_buffer[offset]`), raising an ordinary/caught error (e.g., returning "not canonical" or raising a specific, caught exception) instead of letting a raw `IndexError` propagate out of mempool admission logic. Verify (or add) a caller-side try/except around `is_clvm_canonical` calls so malformed input can never abort spend-bundle processing.

### Proof of Concept
1. Construct a `SpendBundle` whose coin-spend solution, when CLVM-serialized, ends with a truncated atom: the last byte is `0xF8` (5-byte length prefix indicator per `is_atom_canonical`'s `0b11111000` branch) with zero or fewer than 4 trailing bytes actually present in the buffer.
2. Submit the spend bundle to a full node for mempool inclusion so that dedup-eligibility evaluation invokes `is_clvm_canonical(solution_bytes)` → `is_atom_canonical(clvm_buffer, offset)`.
3. `is_atom_canonical`'s loop attempts `clvm_buffer[offset]` beyond the buffer end, raising `IndexError`, which — if unguarded at the call site — surfaces as an exception during spend-bundle processing for that submission.

*Note: I was unable to fully trace, within the remaining tool budget, the exact call site of `is_clvm_canonical` inside the spend-bundle admission pipeline (`pre_validate_spendbundle`/`add_spend_bundle` area) to confirm whether an outer try/except already catches all exceptions from this path. This should be verified directly in `chia/full_node/mempool_manager.py` to confirm exploitability of the DoS impact versus a merely logged/caught error.*

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

```python
def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```

```markdown
## Canonical serialization

**Location**: `mempool_manager.py:185`

### `is_clvm_canonical(clvm_buffer)`

Checks that a CLVM program uses shortest-form atom encoding:

- No unnecessary length prefix bytes
- No back-references (`0xFE` byte)
- No trailing garbage

### When enforced

Required for DEDUP-eligible spends. Without canonical form, identical
solutions could have different serializations, breaking dedup.

### `is_atom_canonical(clvm_buffer, offset)`

Validates a single atom's length prefix encoding. The CLVM format uses
variable-length prefixes (1-6 bytes) based on atom size. Each prefix
length has a minimum atom size threshold.
```
