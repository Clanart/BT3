Based on the investigation, the strongest local analog is in the deep-link URL parser, not the OAuth flow (which correctly validates a CSRF `state` token before exchanging any `code` for a token — see [1](#0-0) ).

### Title
Unvalidated `url` parameter in `openRepo` deep-link action enables git argument/option injection during clone - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` validates the `branch` and `pr` query parameters of an `openRepo` deep link with strict allow-list regexes/character filters, but the `url` value — the actual remote repository location that will be passed to `git clone` — is taken from the URL path completely unvalidated and forwarded as-is.

### Finding Description
In `parseAppURL`, when `actionName === 'openrepo'`, `branch` is checked with `testForInvalidChars` (which rejects git-unsafe/control characters) and `pr` is checked against `/^\d+$/`, but `url` (`parsedPath`, derived directly from `pathName.substring(1)`) has no equivalent validation before being returned as part of `IOpenRepositoryFromURLAction`: [2](#0-1) 

This action is dispatched via `dispatchURLAction` in `dispatcher.ts`, which routes `open-repository-from-url` actions to `openRepositoryFromUrl`, and the CLI clone path (`dispatchCLIAction`) takes the same unvalidated `url` string into `openOrCloneRepository`/`openBranchNameFromUrl` for an eventual `git clone` invocation: [3](#0-2) [4](#0-3) 

Because `branch` and `pr` are explicitly hardened against unsafe characters but `url` is not, an attacker who controls a link (e.g., `x-github-client://openrepo/-<injected-option>...` or a URL containing a leading dash) can supply a value that, depending on how it is ultimately interpreted by the git invocation layer, is treated as a command-line flag rather than a repository location — the classic "argument injection via untrusted URL passed to `git clone`" class of bug. This is structurally the same broken-invariant pattern as the reported Ethereum issue: an entry point reachable by an untrusted actor accepts a parameter that "may be valid in some settings" (a bare numeric epoch of 0 / a bare `url` string) and is never subjected to the same validation applied to sibling parameters, so downstream logic has no way to reject the dangerous case.

### Impact Explanation
If the `url` field reaches the `git clone` argument list without a validation step equivalent to `testForInvalidChars`, an attacker-crafted deep link clicked by a victim could smuggle git CLI options (e.g., `--upload-pack`, `-c`, `--config`) into the clone invocation. Depending on the underlying git wrapper's argument construction, this is a known vector for local code execution or arbitrary file write outside of any repository boundary — squarely within the requested impact bar (code execution / file write outside the repo via a link the user clicks).

### Likelihood Explanation
Requires only that a user click an attacker-supplied `x-github-client://openrepo/...` deep link, no local access, no credentials, and no unnatural steps beyond a single click, consistent with Desktop's documented deep-link handling in `main.ts` (`handleAppURL`) and `possibleProtocols`: [5](#0-4) 

### Recommendation
Apply the same character/format validation used for `branch` (`testForInvalidChars`) — or a stricter allow-list validation of remote URL schemes (`https://`, `git@`) — to the `url` field in `parseAppURL` before constructing an `IOpenRepositoryFromURLAction`, and re-validate/escape the value again immediately before it is interpolated into any git command argument list downstream.

### Proof of Concept
1. Host or send a link of the form `x-github-client://openrepo/-<git-option-payload>?branch=main`.
2. Victim clicks the link; `parseAppURL` accepts it because only `branch`/`pr` are validated, returning `{ name: 'open-repository-from-url', url: '-<git-option-payload>', ... }` (`app/src/lib/parse-app-url.ts:118-124`).
3. `dispatchURLAction` → `openRepositoryFromUrl` (or the CLI `clone-url` path) forwards this string toward the clone routine without further sanitization (`app/src/ui/dispatcher/dispatcher.ts:2050-2120`).

Note: I was not able to reach and confirm the exact `git clone` argument-construction sink (e.g., inside `openOrCloneRepository`/`git/clone.ts`) within the available tool budget, so whether the underlying git wrapper fully neutralizes a leading-dash `url` (e.g., via `--` separators) is unverified — this should be confirmed by inspecting that function directly. export function parseAppURL(url: string): URLActionType {
  const parsedURL = URL.parse(url, true)
  const hostname = parsedURL.hostname
  const unknown: IUnknownAction = { name: 'unknown', url }
  if (!hostname) {
    return unknown
  }

  const query = parsedURL.query

  const actionName = hostname.toLowerCase()
  if (actionName === 'oauth') {
    const code = getQueryStringValue(query, 'code')
    const state = getQueryStringValue(query, 'state')
    if (code != null && state != null) {
      return { name: 'oauth', code, state }
    } else {
      return unknown
    }
  }

  // we require something resembling a URL first
  // - bail out if it's not defined
  // - bail out if you only have `/`
  const pathName = parsedURL.pathname
  if (!pathName || pathName.length <= 1) {
    return unknown
  }

  // Trim the trailing / from the URL
  const parsedPath = pathName.substring(1)

  if (actionName === 'openrepo') {
    const pr = getQueryStringValue(query, 'pr')
    const branch = getQueryStringValue(query, 'branch')
    const filepath = getQueryStringValue(query, 'filepath')

    if (pr != null) {
      if (!/^\d+$/.test(pr)) {
        return unknown
      }

      // we also expect the branch for a forked PR to be a given ref format
      if (branch != null && !/^pr\/\d+$/.test(branch)) {
        return unknown
      }
    }

    if (branch != null && testForInvalidChars(branch)) {
      return unknown
    }

    return {
      name: 'open-repository-from-url',
      url: parsedPath,
      branch,
      pr,
      filepath,
    }
  }

  return unknown
}
