### Title
Quadratic denial of service in FROST `sign`/`view` over attacker-supplied participant set - (File: crypto/frost/src/sign.rs)

### Summary
The Shescape advisory (GHSA-gm3r-q2wp-hw87, CWE-400/CWE-407) is a quadratic-time DoS: work proportional to the input is repeated for each element of the input. The same shape exists in Serai's FROST implementation: `AlgorithmSignMachine::sign` builds the `included` signing set from attacker-controlled `HashMap<Participant, Preprocess>` keys and then performs per-signer work that is itself linear in the size of the set — Lagrange coefficient computation in `ThresholdKeys::view`/`ThresholdView` and binding-factor generation over the serialized commitment list — yielding O(|included|²) scalar operations on untrusted input.

### Finding Description
In `crypto/frost/src/sign.rs`, `sign` derives `included` directly from the keys of the `preprocesses` map, where each `Preprocess` is produced by `read_preprocess` → `Commitments::read` over bytes supplied by a remote (unprivileged) participant:

- `included` is populated from `preprocesses.keys()` and only validated for `≥ t`, `≤ n`, and no duplicates (`crypto/frost/src/sign.rs:290-313`). `n` is a `u16`, so `included` can contain up to 65,535 entries while the actual number of honest signers is small — a single malicious participant can present preprocesses for thousands of participant indexes it doesn't control (nothing binds a `Preprocess` message to a participant's signature share at this stage; the share check only happens later in `complete`).
- `self.params.keys.view(included.clone())` (`sign.rs:312`) computes per-signer Lagrange coefficients in `crypto/dkg/src/lib.rs` (`Interpolation::Lagrange` / `Interpolation::Constant` path), where each signer's coefficient is a product over all other included participants — O(|included|) field operations per signer, O(|included|²) total.
- `B.calculate_binding_factors(&rho_transcript)` (`sign.rs:371`) computes each signer's `rho` over a transcript that binds to all participants' commitments (`crypto/frost/src/nonce.rs`, `BindingFactor`), again linear in the set per signer.
- `B.nonces(&nonces)` and the per-signer `bound` in `complete` (`sign.rs:478`) compound the cost.

With `n` bounded only by `u16` (`ThresholdParams::new` in `crypto/dkg/src/lib.rs`), an attacker can force ~65,535² ≈ 4.3·10⁹ field multiplications per `sign` call from a message whose size is only ~65,535 × (point + addendum) bytes — quadratic blowup from a modest input, matching the CVE's class exactly (attacker-controlled input size drives runtime quadratic in it).

### Impact Explanation
An unprivileged party who can send preprocess messages to a signer/coordinator triggers the quadratic path with a single crafted input. The victim's node burns CPU proportional to the square of the declared participant set before any cryptographic validity is established (the failure only surfaces at `InvalidSigningSet`/share verification, after the expensive work). Repeated messages cause sustained CPU exhaustion of a validator/signing node — availability impact analogous to the reported CVE.

### Likelihood Explanation
High for reachability: `read_preprocess` explicitly exists to parse remote participants' bytes (`sign.rs:276-281`), and `sign` accepts a map keyed by arbitrary `Participant` values within `1..=n`. The attacker needs no valid key share to inflate `included` — deduplication only requires distinct indexes, which are free to claim. The cost is borne by any node that runs `sign` over the received preprocess set.

### Recommendation
- Bound `included.len()`/`preprocesses.len()` to the protocol's actual participant set `n` known a priori (reject indexes not in the established participant roster before any per-signer work).
- Authenticate preprocesses to participant indexes before `sign` (the coordinator/tributary layer should only pass preprocesses from the declared validator set).
- If a large `n` is legitimate, compute Lagrange coefficients in O(n log n) or incremental form rather than per-signer O(n) products, and memoize the serialized-commitment hash used by `calculate_binding_factors`.

### Proof of Concept
```rust
// Attacker crafts preprocesses for participant indexes 1..=MAX (up to u16::MAX)
let mut preprocesses: HashMap<Participant, Preprocess<C, A::Addendum>> = HashMap::new();
for i in 1u16 ..= u16::MAX {
    // Each preprocess is just serialized Commitments + addendum bytes;
    // produced via read_preprocess from bytes the attacker sends.
    preprocesses.insert(Participant(i), attacker_preprocess.clone());
}
// Victim call:
sign_machine.sign(preprocesses, msg)?;
// sign() builds `included` of size ~65535, then:
//   - ThresholdKeys::view(included) does O(65535^2) scalar muls for Lagrange
//   - BindingFactor::calculate_binding_factors does O(65535^2) hashing/scalar work
// Runtime grows quadratically in attacker-controlled input before failing.
```
