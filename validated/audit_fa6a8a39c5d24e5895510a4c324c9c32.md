### Title
Sandwichable zero-slippage buyback swap in `SmartWomConvert._convertFor` lets attacker extract the WOM/mWOM peg-recovery arbitrage margin during permissionless `harvest()` fee routing - ([File: wombat/SmartWomConvert.sol])

### Summary
`AnkrBNBPoolHelper.harvest()` is unprivileged and forwards to `WombatStaking.harvest()` → `_toMasterWomAndSendReward` → `_sendRewards`, which calls `IConverter(smartWomConverter).smartConvert(feeAmount, 0)` whenever a fee is marked `isMWOM`. Inside `smartConvert`/`_convertFor`, the "buyback" portion of the fee is swapped WOM→mWOM through `IWombatRouter.swapExactTokensForTokens(..., 0, ...)` with **zero slippage protection**, so an attacker can sandwich this call to capture most of the peg-recovery arbitrage margin that the buyback mechanism is designed to earn for the protocol.

### Finding Description
`_sendRewards` in [1](#0-0)  routes the WOM fee into `smartWomConverter.smartConvert(feeAmount, 0)` whenever the fee is flagged `isMWOM`. `smartConvert` in [2](#0-1)  computes `currentRatio()` (spot price of mWOM in WOM read live from the `womMWomPool` via `router.getAmountOut`, [3](#0-2) ). If mWOM is trading below `buybackThreshold` (90%), part of the fee (`amountToSwap`, bounded by `maxSwapAmount()`) is routed through an actual AMM swap instead of being 1:1 minted.

That swap happens in `_convertFor`: [4](#0-3)  — `swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp)` passes `0` as `amountOutMin`, i.e., **no per-swap slippage protection**. The only guard is the aggregate check `if (convertAmount + amountRec < _minRec) revert MinRecNotMatch();` at [5](#0-4) , and since `smartConvert` calls `_convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode)` (`_minRec = _amountIn`), this only guarantees `obtainedmWomAmount >= feeAmount` — it does **not** enforce fair pricing on the swap leg.

Because `harvest()` on `AnkrBNBPoolHelper` (and `WombatPoolHelper`/`WombatPoolHelperV2`) is permissionless ( [6](#0-5) ) and triggers this swap with a predictable size (`feeAmount` derived from harvested WOM rewards and a fixed `feeInfo.value`), an attacker can front-run the harvest transaction by buying mWOM in the same pool (pushing its price up before the buyback swap executes), let the victim's fee-swap execute at the worse price, then back-run by selling mWOM back to WOM, extracting the price impact as classic sandwich MEV. Because the aggregate `_minRec` check only requires `obtainedmWomAmount >= feeAmount` (a 1:1 floor), the attacker can tune the sandwich to shrink the buyback bonus down toward that floor without triggering a revert, capturing the arbitrage margin the buyback was intended to earn for the protocol/fee pool.

### Impact Explanation
This does **not** allow mWOM backing to fall below the WOM fee amount consumed — the `MinRecNotMatch` check in `_convertFor` strictly enforces `obtainedmWomAmount >= feeAmount`, so the specific outcome hypothesized in the question (mWOM minted less than WOM consumed, i.e., under-backing) cannot occur. What is real and exploitable is a **partial loss of the intended peg-recovery arbitrage yield**: when `currentRatio() < buybackThreshold`, the protocol is meant to buy discounted mWOM with the fee WOM and capture the discount as extra backing/yield for `WombatStaking`'s fee pool. A sandwich attacker can capture most of that discount instead, degrading (but not eliminating) the expected upside from the buyback mechanism — best characterized as "theft of unclaimed yield" rather than insolvency or fund freezing.

### Likelihood Explanation
Feasible for any unprivileged actor: `harvest()` is permissionless and callable by anyone, fee parameters (`feeInfo.value`, `isMWOM`) and `buybackThreshold`/`maxSwapAmount` are public state, and `currentRatio()`/pool reserves are readable on-chain, so the swap size and direction are fully predictable before submission. The attack requires no special privileges, only capital to front-run/back-run on the `womMWomPool`, and is repeatable every time a fee-triggering harvest occurs while mWOM trades below the buyback threshold.

### Recommendation
Add real slippage protection on the buyback swap leg in `SmartWomConvert._convertFor` (pass a computed `amountOutMin` based on `currentRatio()`/oracle-observed price with reasonable tolerance, not `0`), and/or use a TWAP-based `currentRatio()` instead of the spot `getAmountOut` reading to reduce single-block manipulability of the buyback decision and swap execution price.

### Proof of Concept
Foundry test plan:
1. Fork BSC at a block where `smartWomConverter` (`SmartWomConvert`) is deployed and `currentRatio() < buybackThreshold`.
2. Simulate a pending WOM reward large enough that `_sendRewards` triggers `smartConvert` with a nontrivial `feeAmount` requiring a buyback swap (`amountToSwap > 0`).
3. Baseline: call `AnkrBNBPoolHelper.harvest()` directly and record `mWom` minted to the WombatStaking fee recipient (`feeTosend`) vs `feeAmount`.
4. Sandwich: from an attacker EOA, before the harvest tx, swap WOM→mWOM on `womMWomPool` via the router to push `currentRatio()` up; execute the harvest tx; then swap mWOM→WOM back.
5. Assert: `feeTosend_sandwiched < feeTosend_baseline` (attacker captures the buyback discount) while confirming `feeTosend_sandwiched >= feeAmount` (i.e., the `MinRecNotMatch` floor holds, refuting under-backing but confirming yield extraction).
6. Assert attacker's net WOM balance after the round-trip sandwich is positive, quantifying the extracted arbitrage margin.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
