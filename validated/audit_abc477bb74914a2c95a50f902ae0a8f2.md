### Title
Unchecked type assertion on attacker-controlled CosmWasm query response causes panic in pointer precompiles - (File: precompiles/pointer/pointer.go)

### Summary
The `AddCW20`, `AddCW721`, and `AddCW1155` handlers in the pointer precompile query an arbitrary, caller-supplied CosmWasm contract address and blindly type-assert the `name`/`symbol` fields of the JSON response to `string` without checking the type or presence of those fields.

### Finding Description
`AddCW20` accepts a bech32 contract address supplied by the caller, queries it via `QuerySmartSafe(ctx, cwAddress, []byte("{\"token_info\":{}}"))`, unmarshals the JSON response into a `map[string]interface{}`, and then does: [1](#0-0) 

Because the queried contract is any CosmWasm contract the caller chooses to deploy (an unprivileged, attacker-controlled contract), the attacker fully controls the JSON body returned from `token_info`/`contract_info`. If the `name` or `symbol` field is omitted (yielding `nil`) or is of a non-string JSON type (number, bool, array, object), the type assertion `formattedRes["name"].(string)` panics with an unrecovered "interface conversion" runtime panic, since no comma-ok form (`, ok := ...`) or a `!ok` check is used. The identical unguarded pattern exists in `AddCW721` and `AddCW1155`: [2](#0-1) [3](#0-2) 

Unlike other precompiles (e.g. `addr` and `oracle`), which wrap their `Execute` dispatch with a `defer recover()` to convert panics into reverted errors: [4](#0-3) 
the pointer precompile's `Execute` has no such recovery: [5](#0-4) 
And the outer `Precompile.Run` wrapper only calls `HandlePrecompileError` on an `err` return value in its `defer`; it does not itself `recover()` from a panic bubbling up from `p.executor.Execute`: [6](#0-5) 

This maps to the same bug-class root cause as CVE-2017-14146: attacker-supplied content (here, the JSON query response from a contract the caller deploys) is trusted and used by privileged/downstream logic without validating its type/structure, leading to unsafe processing of unvalidated input.

### Impact Explanation
A crash-inducing panic here would only be a genuine chain-halt / RPC-node-crash issue if it propagates past any transaction-level panic recovery in the EVM message/ante-handler dispatch path. I was not able to confirm from the code I retrieved whether such a top-level `recover()` exists in the sei-EVM `ApplyMessage`/precompile-call dispatch (e.g. in `x/evm/keeper` or the go-ethereum EVM interpreter fork) that would convert this into a normal reverted transaction rather than an uncaught panic that halts block processing or crashes the node process. If no such top-level recovery exists, an attacker could deploy a trivial CW20-look-alike contract whose `token_info` query returns `{"name": 123}` (or omits `name`), then call `addCW20Pointer` (precompile address `0x...100b`) with that contract's address, panicking on every node that processes the transaction — a `nil`/wrong-type crash across the network (potential validator halt / RPC crash, satisfying the Medium/High criteria). If a higher-level recover does exist and this only surfaces as `execution reverted`, the practical impact is limited to a poor error message rather than a crash, and would not meet this program's bar.

### Likelihood Explanation
Trivially reachable: any unprivileged account can deploy a CosmWasm contract (a CW20/CW721-shaped contract that satisfies `wasmdKeeper.QuerySmartSafe` but returns malformed `token_info`/`contract_info` JSON) and then call the public `addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer` methods on the pointer precompile from an EVM transaction, with no special permissions or preconditions beyond gas.

### Recommendation
Replace the unchecked type assertions with the comma-ok form and return a proper error (not a panic) when `name`/`symbol` are missing or not strings, e.g.:
```go
name, ok := formattedRes["name"].(string)
if !ok {
    return nil, 0, fmt.Errorf("token_info response missing or invalid 'name' field")
}
symbol, ok := formattedRes["symbol"].(string)
if !ok {
    return nil, 0, fmt.Errorf("token_info response missing or invalid 'symbol' field")
}
```
Apply the same fix to `AddCW721` and `AddCW1155`. Additionally, wrap `PrecompileExecutor.Execute` in the pointer precompile with a `defer recover()` (as is already done in the `addr` and `oracle` precompiles) as defense-in-depth against similar unvalidated-external-data panics in this and future precompile code.

### Proof of Concept
1. Deploy a CosmWasm contract whose `token_info` query handler returns `{"name": 12345, "symbol": "TEST", "decimals": 6, "total_supply": "0"}` (i.e., `name` is a JSON number, not a string), or a contract that omits `name` entirely.
2. From an EVM account, call `addCW20Pointer(<contract_bech32_address>)` on the pointer precompile at `0x000000000000000000000000000000000000100b`.
3. Inside `AddCW20`, `formattedRes["name"].(string)` panics because the value is not a string (or is `nil`), since the code performs a bare type assertion instead of using the comma-ok pattern. [1](#0-0) 

**Note on verification limits**: I could not fully trace whether the sei-chain EVM transaction/message dispatch path (outside `precompiles/`) recovers arbitrary panics before they reach block processing; confirming whether this results in a full node crash/halt versus a merely-reverted transaction would require further investigation of `x/evm/keeper` message handling and the go-ethereum-fork EVM `Call` opcode dispatch, which the available index did not surface clearly.
