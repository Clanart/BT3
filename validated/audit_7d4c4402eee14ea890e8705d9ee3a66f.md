## Finding [1](#0-0) 

### Title
Desktop explicitly disables Git's `GIT_CLONE_PROTECTION_ACTIVE` safeguard during recursive clones, re-enabling embedded/symlinked `.git` submodule attacks - (File: `app/src/lib/git/clone.ts`)

### Summary
Git's `clone` function sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` unconditionally on every clone performed by Desktop, while also always passing `--recursive` (recursive submodule clone) to the underlying `git clone` invocation. [2](#0-1)  `GIT_CLONE_PROTECTION_ACTIVE` is the internal flag upstream Git introduced (as part of the fixes for the CVE-2024-32004/32020/32021/32465 family of clone-time symlink/embedded-repository vulnerabilities) to prevent a maliciously crafted repository — typically via a submodule containing a symlinked or embedded `.git` directory — from tricking the recursive-clone/checkout machinery into writing files (or running hooks) outside the intended working tree. By forcing this protection flag to `false`, Desktop deliberately opts every single clone (including "Open in Desktop" / "Clone URL" flows driven by attacker-supplied remote URLs) out of that safety net.

### Finding Description
The broken invariant is: "the destination of any file written during clone/checkout of a submodule must stay within the clone's working directory." Upstream Git enforces this invariant via the protection Governor by `GIT_CLONE_PROTECTION_ACTIVE`, refusing to follow/replace symlinked `.git` entries and refusing to treat embedded git directories as ordinary content during a recursive submodule clone. Desktop's `clone()` function overrides this by hard-setting the variable to `'false'` in the environment passed to every `git clone --recursive` invocation. [1](#0-0) 

The `isClonePathSensitive` check right above it only guards against the *top-level* clone destination being a sensitive directory (home dir, `.ssh`, `.gnupg`, etc.) — it does nothing to constrain what a *submodule inside the cloned repository* can do once `--recursive` triggers submodule cloning/checkout. [3](#0-2)  That check is therefore not a substitute for the protection being disabled.

The attacker primitive matches the report's pattern precisely: a modular "step" (Git's own clone-time protection layer) is skipped/turned off, and the subsequent step (recursive submodule checkout) then trusts state (paths under the clone directory) that is no longer guaranteed by the disabled step — exactly analogous to `_participateOnTOLP` trusting that `_lockOnTOB`'s custody transfer happened when `lock` was skipped.

### Impact Explanation
An attacker who controls a Git remote/repository (the exact threat model called out for this task: "the attacker controls a cloned/fetched repository") can craft a submodule containing a symlinked or embedded `.git` directory. When a Desktop user clones that repository — via the normal Clone dialog, the CLI (`github clone`), or the `x-github-client://openRepo/...` deep link handled in `parseAppURL`/`dispatcher.openOrCloneRepository` [4](#0-3) [5](#0-4)  — the recursive submodule clone proceeds with Git's built-in symlink/embedded-repo protections explicitly disabled. This can lead to writes outside the intended repository directory (e.g., overwriting hook files or other files on disk), matching the "file write... outside the repo" and potential "code execution" impact classes defined as valid for this assessment.

### Likelihood Explanation
Every clone performed by Desktop is affected because the override is unconditional and applies to all clone call sites (manual clone, CLI clone, "Open in Desktop" deep links, "Clone Again" for missing repos). No local access, admin rights, or social engineering beyond "the user clones an attacker-supplied URL/repo" — a core, expected Desktop workflow — is required, satisfying the required attacker model.

### Recommendation
Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override from the environment built in `clone()` so that Git's default (protection-enabled) behavior is preserved for recursive submodule clones, restoring the upstream safeguard against embedded/symlinked `.git` directories in untrusted repositories.

### Proof of Concept
1. Attacker publishes a repository with a submodule reference whose checked-out content is engineered to include a symlink where a `.git` directory or hook path is expected (the class of payloads addressed by the Git 2.45.1 clone-protection fixes).
2. Victim uses GitHub Desktop to clone the attacker's repository URL (via Clone dialog, `github clone <url>` CLI, or an `x-github-client://openRepo/...` link).
3. `clone()` in `app/src/lib/git/clone.ts` runs `git clone --recursive ...` with `GIT_CLONE_PROTECTION_ACTIVE=false` in the environment. [6](#0-5) 
4. Because the protection is disabled, Git's clone-time defenses against the embedded/symlinked `.git` submodule attack do not apply, allowing the crafted submodule to write/overwrite files outside the intended working directory during checkout.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
