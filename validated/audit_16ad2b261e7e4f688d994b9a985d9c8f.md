### Title
Reward-per-token sniping via same-block deposit before `queueNewRewards` allows an unprivileged staker to steal yield from long-term stakers - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool._provisionReward()` (invoked by `queueNewRewards`) applies the entire newly-queued reward amount to `rewardPerTokenStored` instantaneously, based on `totalStaked()` at the exact moment the manager's transaction executes, with no time-weighted streaming (`rewardRate`/`periodFinish`) and no minimum holding period. An attacker can front-run the manager's `queueNewRewards` call by depositing a large amount into `MasterMagpie` in the same block, causing the reward-per-token increment to be computed while their inflated stake is counted, then immediately withdraw and claim, capturing reward proportional to their instantaneous share of `totalStaked` despite holding the position for zero effective blocks of prior accrual.

### Finding Description
`_provisionReward` computes the reward index update purely as a function of the current live balance: [1](#0-0) 

`totalStaked()` reads the live `stakingToken` balance held by the `operator` (MasterMagpie) at call time [2](#0-1) , and `balanceOf(_account)` reads the account's live stake from `MasterMagpie.stakingInfo` [3](#0-2) . `earned()` computes reward strictly from `balanceOf(_account) * (rewardPerToken - userRewardPerTokenPaid)` with no time-duration term at all [4](#0-3) .

Exploit flow:
1. Attacker observes (mempool or same-block ordering) the manager's pending `queueNewRewards(_amountReward, _rewardToken)` transaction.
2. Attacker calls `MasterMagpie.deposit(largeAmount)` in the same block just before it. This increases `totalStaked()` and, via the `updateReward` checkpointing pattern (`userRewardPerTokenPaid` set to current `rewardPerToken` at deposit time), the attacker's baseline is captured *before* the reward bump.
3. `queueNewRewards` executes: `rewardInfo.rewardPerTokenStored += (_amountReward * 1e_dec) / totalStaked()`, where `totalStaked()` now includes the attacker's flash-deposited stake, diluting the per-token increment relative to what it would have been for the pre-existing stakers, but crediting the attacker with a full share of that increment.
4. Attacker immediately calls `MasterMagpie.withdraw(amount, true)`, which routes to `getReward`, protected only by the `updateReward` modifier (`_updateFor`), not by any cooldown or vesting check [5](#0-4) . The attacker's `earned()` is computed and paid out based on the full `delta * balanceOf`, with zero effective holding duration.

No existing guard mitigates this: there is no `nonReentrant`-style time lock, no minimum staking duration, no `periodFinish`/linear vesting of rewards over time (unlike Synthetix-style `rewardRate` pools), and `onlyManager`/`onlyMasterMagpie` modifiers only gate *who* can call `queueNewRewards`/`getReward`, not *when* relative to deposits. The `updateReward` modifier only checkpoints state; it does not prevent JIT (just-in-time) stake capture.

### Impact Explanation
This is a direct theft-of-yield vulnerability: the attacker extracts reward tokens that were intended to compensate long-term stakers for the risk/duration of holding `stakingToken`, permanently diluting/stealing that yield from legitimate depositors. This matches the Immunefi impact class "theft of unclaimed yield" — real economic loss transferred from long-term stakers to a JIT attacker with no capital lockup risk (flash-loanable if `stakingToken` is an LP/receipt token).

### Likelihood Explanation
High feasibility: requires only the ability to front-run a public/known manager transaction within the same block (trivial via mempool monitoring or MEV bundling), and capital sufficient to acquire/flash-loan a large amount of `stakingToken`. No privileged role is needed — `deposit`/`withdraw` on `MasterMagpie` are presumably open to any staker. The attack is fully repeatable every time `queueNewRewards`/`donateRewards` is called, and profitability scales with `_amountReward` and the attacker's ability to dominate `totalStaked` momentarily.

### Recommendation
Stream rewards over time instead of applying them instantaneously to `rewardPerTokenStored`: adopt a Synthetix-style `rewardRate` + `periodFinish` + `lastUpdateTime` model so `rewardPerToken` accrues linearly per second based on `totalStaked` sampled continuously, rather than being bumped in full at the instant of `queueNewRewards`. Additionally/alternatively, enforce a minimum staking duration or withdrawal cooldown in `MasterMagpie`/`BaseRewardPool` so a deposit cannot be immediately withdrawn in the same block it was made, closing the JIT window.

### Proof of Concept
Hardhat test plan:
1. Deploy `MasterMagpie`, `BaseRewardPool` (or `BaseRewardPoolV2`), a mock `stakingToken` (ERC20/LP mock), and a mock reward token.
2. Have `staker1` deposit `100e18` stakingToken into `MasterMagpie` and let several blocks pass with no reward activity (simulating a long-term staker).
3. In one transaction/block: `attacker` calls `MasterMagpie.deposit(10000e18)` (large relative to `staker1`), then in the same block `manager` calls `rewardPool.queueNewRewards(1000e18, rewardToken)`, then `attacker` calls `MasterMagpie.withdraw(10000e18, true)`.
4. Assert `rewardPool.earned(attacker, rewardToken) > 0` and specifically `earned(attacker, rewardToken)` is close to `1000e18 * 10000/(10000+100)` (attacker's instantaneous share), despite the attacker holding stake for 1 block/0 duration.
5. Assert `staker1`'s remaining claimable reward is diluted below what it would have been absent the attacker's flash stake (compare against a control run without the attacker's deposit), demonstrating value transfer from `staker1` to `attacker`.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
