### Title
Attacker-controlled transaction overwrites the InInstruction data and presumed origin of unrelated Serai outputs in the same block - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::get_outputs` accumulates discovered outputs in a single `outputs` vector that lives across the entire `for tx in &block.txdata[1 ..]` loop. For each transaction, the processor resolves `presumed_origin` from `tx.input[0].previous_output` (an attacker-selectable outpoint fetched via `self.rpc.get_transaction`) and extracts Serai instruction data via `Self::extract_serai_data(tx)`. It then applies that origin/data to `for output in &mut outputs` — every output found so far in the block, not just those produced by the current transaction. An unprivileged Bitcoin user who gets any transaction into a block *after* a victim's deposit transaction therefore dictates which remote transaction's data the processor fetches and assigns to the victim's output.

### Finding Description
In `get_outputs`, `outputs` is declared once before the transaction loop and pushed to inside it ( [1](#0-0) ). The `if outputs.is_empty() { continue }` guard only skips enrichment when *no* output has been found yet ( [2](#0-1) ). Then `tx.input[0].previous_output` — fully attacker-chosen, since the attacker constructs the spending transaction — is used to fetch a spent output via RPC to derive `presumed_origin` ( [3](#0-2) ), and `Self::extract_serai_data(tx)` is applied to **all** accumulated `outputs`, overwriting `data` for `OutputType::External` outputs and `presumed_origin` for every kind ( [4](#0-3) ).

The `data` field carries the InInstruction (e.g. `Shorthand::transfer` destination — a Serai address), which determines who gets credited for a deposit. Because the write loop is not scoped to the outputs of `tx`, the last transaction in the block that triggers the enrichment path wins and clobbers `data`/`presumed_origin` on every earlier output. This is the Serai analog of the SSRF class: the attacker supplies an arbitrary reference (`previous_output` txid/vout) and arbitrary payload (embedded InInstruction), causing the node to fetch and trust attacker-directed remote data for resources it did not originate.

### Impact Explanation
A victim sends BTC to Serai's external address embedding `Shorthand::transfer(victim_serai_address)`. An attacker places any transaction *after* it in the same block whose input[0] and embedded Serai data encode `Shorthand::transfer(attacker_serai_address)`. When `get_outputs` runs, the victim's `External` output has its `data` overwritten with the attacker's instruction, so the deposit is credited to the attacker. `presumed_origin` on all outputs is likewise forged. `data` is only written for `External` outputs, but that is exactly the user-deposit path.

### Likelihood Explanation
Fully reachable by an unprivileged party: the attacker only needs a confirmed transaction in the same block, which they can mine themselves or arrange via normal broadcast. No validator collusion, key material, or malformed encodings are required. The only requirement is ordering — attacker's tx later in `block.txdata` than the victim's — which is trivially achievable by miners and routinely achievable by fee/relay timing. Note the loop also retries `get_transaction` forever on a nonexistent outpoint, but the primary, Medium+ impact is the cross-transaction data overwrite.

### Recommendation
Scope enrichment to the current transaction's outputs: track `let start = outputs.len()` before scanning `tx`, and iterate `for output in &mut outputs[start ..]` when assigning `presumed_origin` and `data`. Outputs whose own transaction carries no Serai data should retain `data: vec![]` and `presumed_origin: None`, not inherit a later transaction's values.

### Proof of Concept
1. Victim broadcasts tx_A paying `external_address(group_key)` with a P2WSH InInstruction encoding `transfer(alice)`.
2. Attacker broadcasts tx_B (any tx, e.g. spending their own UTXO) with an InInstruction encoding `transfer(mallory)`, mined after tx_A in block B.
3. `get_outputs(B, group_key)`: `scan_transaction(tx_A)` pushes the victim output; `scan_transaction(tx_B)` finds nothing; `outputs` is non-empty, so the enrichment block runs for tx_B: `data = extract_serai_data(tx_B)` → `transfer(mallory)`; `for output in &mut outputs` assigns it to the victim's `External` output.
4. Result: `output.data()` on the victim's deposit returns the attacker's instruction, crediting the deposit to `mallory`.

Uncertainty: `extract_serai_data` was not fully read this session, but the code comments and surrounding logic confirm it extracts the InInstruction-embedding output from the tx, and the overwrite loop applies to already-collected outputs regardless of which tx produced them — the structural flaw is confirmed at lines 689–736.
