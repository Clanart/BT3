Based on my research, I found a concrete, locally-provable module-identity binding gap in the `HostManager` contract that mirrors the "documented protection not actually enforced in code" pattern from the seed report.

### Title
`HostManager.onAccept` only authenticates the source chain, not the sending module, unlike other IApp modules in the same codebase - (File: `evm/src/core/HostManager.sol`)

### Summary
`HostManager` is the sole channel through which cross-chain governance can update `EvmHost` protocol parameters (`updateHostParams`) or drain bridge revenue (`withdraw`). Its `onAccept` handler authenticates only the ISMP `request.source` (the origin *chain*), and never checks `request.from` (the origin *module/pallet* on that chain). [1](#0-0) 

By contrast, the sibling `BandwidthManager` design in the same repository explicitly enforces both chain identity and module identity: "The pallet rejects any purchase whose `request.from` doesn't equal the address stored under `BandwidthManager<T>::get(request.source)`. An attacker who deploys their own contract on a source chain cannot mint subscriptions." No equivalent `from` binding exists for `HostManager`.

### Finding Description
`HostManager.onAccept` decodes an action byte and dispatches directly to `IHostManager(_params.host).withdraw(...)` or `updateHostParams(...)` based solely on:
```solidity
if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();
``` [2](#0-1) 

This checks that the message originated from *the Hyperbridge state machine as a whole*, but does not verify that the specific sender (`request.from`) is the intended governance pallet (e.g. `host-executive`, whose calls are gated by `HostExecutiveOrigin` on the Substrate side). [3](#0-2) 

On the EVM side, both privileged actions are gated only by `restrict(_hostParams.hostManager)`, i.e. "caller must be the HostManager contract" — but `HostManager` itself never re-validates *which* logical actor on Hyperbridge issued the underlying cross-chain request: [4](#0-3) [5](#0-4) 

Additionally, `updateHostParamsInternal` enforces a floor only on `unStakingPeriod` (`if (1 days > params.unStakingPeriod) revert InvalidUnstakingPeriod();`) but applies **no minimum-value check at all to `challengePeriod`**, even though `challengePeriod` is the exact "delay"/timelock value that the fraud-proof/fisherman veto window depends on to prevent false remote state from being trusted (`verify_delay_passed` treats `delay_period.as_secs() == 0` as an automatic pass). [6](#0-5) [7](#0-6) 

So any message that reaches `HostManager.onAccept` from *some* account on the Hyperbridge chain (not necessarily the intended `host-executive` pallet) can push a `HostParams` update that zeroes `challengePeriod`, instantly collapsing the challenge window meant to let fishermen veto malicious state commitments before they are trusted — or it can trigger an unauthorized `withdraw` draining the host's fee-token/native balance.

### Impact Explanation
If exploitable, this allows: (1) unauthorized withdrawal of the host's held revenue to an attacker-chosen beneficiary (direct fund loss), and (2) collapsing `challengePeriod` to `0`, which removes the fraud-proof delay and lets a subsequently-submitted malicious/attacker state commitment be treated as immediately finalized — i.e., false remote state acceptance, matching the "false proof/state acceptance" impact category.

### Likelihood Explanation
This requires establishing that some entity other than the intended `host-executive` pallet on the Hyperbridge chain can dispatch a PostRequest whose `to` is the `HostManager` address with attacker-chosen `body`. I was not able to fully verify, within available tool calls, whether Hyperbridge exposes any generic/unrestricted dispatch path (e.g. a raw ISMP-dispatch precompile or pallet) that lets a caller other than `host-executive` set an arbitrary `from`/`body` while `source` still correctly resolves to the Hyperbridge state machine. The missing `request.from` check is a genuine, confirmed code gap and a clear deviation from the pattern used elsewhere in the codebase (`BandwidthManager`), but I cannot confirm a fully unprivileged trigger path without further investigation of Hyperbridge's dispatch surface (all runtime pallets/precompiles that can call `pallet_ismp`'s dispatch API with a `to` matching arbitrary EVM addresses). This should be verified by a Devin session with full repo access before treating it as a confirmed exploitable path.

### Recommendation
Add explicit `request.from` verification in `HostManager.onAccept`, restricting inbound governance messages to a configured, single expected sender identity (e.g. the `host-executive` pallet's `PALLET_ID`) in addition to the existing `request.source` chain check — mirroring the `from`-binding pattern already used by `BandwidthManager`. Separately, add a minimum-value guard for `challengePeriod` in `updateHostParamsInternal` (analogous to the existing `1 days` floor on `unStakingPeriod`) so governance cannot silently zero out the fraud-proof delay.

### Proof of Concept
Conceptual (pending confirmation of an unprivileged dispatch path on the Hyperbridge side):
1. Identify or construct a Hyperbridge-side call that dispatches a `PostRequest` with `dest = Evm(<target>)`, `to = <HostManager address>`, and attacker-controlled `body = [ACTION_WITHDRAW or SET_HOST_PARAM] + abi.encode(...)`, where `from` is not enforced to equal `host-executive`'s `PALLET_ID`.
2. Once relayed and processed by the EVM handler, `EvmHost` calls `HostManager.onAccept`, which only checks `request.source == hyperbridge()` [8](#0-7) .
3. The decoded action executes `withdraw` (draining the host balance to an attacker beneficiary) or `updateHostParams` (e.g. setting `challengePeriod = 0`), exactly as demonstrated by the legitimate test flow in [9](#0-8)  and [10](#0-9) , but without requiring the caller to actually be `host-executive`.

    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }

/// for the state machine has elasped.
pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}

#[test]
fn test_host_manager_withdraw() {
	let mut env = TestEnv::new();
	let manager = host_manager_of(&mut env);

	// Mint 1000e18 fee tokens to the host
	let amount_to_mint = U256::from(1000u128) * U256::from(10u128.pow(18));
	env.call(env.fee_token, mintCall { to: env.host, amount: amount_to_mint }.abi_encode());
	assert_eq!(host_balance(&mut env), amount_to_mint);

	// Build a withdraw request (body = [0] + abi.encode(WithdrawParams)).
	// Withdraw the fee token (non-zero `token`) — the zero address would be
	// the native-ETH path which this test isn't exercising.
	let params = WithdrawalParams {
		beneficiary_address: H160::random().as_bytes().to_vec(),
		amount: SubstrateU256::from(500_000_000_000_000_000_000u128),
		token: H160::from_slice(env.fee_token.as_slice()),
	};

	let post = router::PostRequest {
		source: StateMachine::Kusama(2000),
		dest: StateMachine::Evm(1),
		nonce: 0,
		from: env.sender.as_slice().to_vec(),
		to: vec![],
		timeout_timestamp: 100,
		body: params.abi_encode().expect("20-byte beneficiary"),
	};
	let evm_request: EvmPostRequest = post.into();

	// HostManager.onAccept is `restrict(_params.host)` — must call AS the host
	let host_addr = env.host;
	let calldata = onaccept_calldata(evm_request, env.sender);
	env.call_as(host_addr, manager, calldata);

	let withdraw_amount = U256::from(500u128) * U256::from(10u128.pow(18));
	assert_eq!(host_balance(&mut env), amount_to_mint - withdraw_amount);
}
