### Title
Partial-commit line selection is applied against a diff re-fetched at commit time, letting a changed working file corrupt what is actually committed - (File: `app/src/lib/git/apply.ts`)

### Summary
`applyPatchToIndex()` re-computes the diff from disk at commit time (`getWorkingDirectoryDiff`) and blindly re-applies the `DiffSelection` line indices that the user chose while looking at an earlier rendering of that diff in the UI. There is no check that the freshly fetched diff still matches the diff the selection was computed against, so if the file's on-disk content shifts between "user reviews/selects lines" and "commit runs," the selection indices are silently reinterpreted against different hunks/lines, producing a commit whose content does not match what the user saw and approved.

### Finding Description
`stageFiles()` in `app/src/lib/git/update-index.ts` calls `applyPatchToIndex(repository, file)` for every file with a partial (line-level) selection. [1](#0-0) 

Inside `applyPatchToIndex`, the diff used to build the patch is fetched fresh, at the moment of staging, not the diff instance the UI rendered when the user picked which lines to include: [2](#0-1) 

The patch itself is produced by `formatPatch()`, which walks the (freshly fetched) diff's hunks and decides per line whether to include it purely via `file.selection.isSelected(absoluteIndex)` — an index into the *old* diff's line layout: [3](#0-2) 

`DiffSelection` (the `file.selection` object) is a set of absolute line indices computed when the diff was last rendered in the Changes list / diff viewer; it carries no reference to a diff hash, size, or content fingerprint that could be used to validate it against a newer diff. Nowhere in `applyPatchToIndex`, `formatPatch`, or `stageFiles` is there a comparison confirming that the diff used to build the selection is the same diff being patched now. If the working tree changes between the two points — e.g. a `post-checkout`/`smudge` filter from a cloned/fetched repository rewrites the file, a background process touches the file, or the file is refreshed by a large fetch/checkout while the Changes view is still showing a stale diff — the hunk boundaries and line offsets shift, but the selection's absolute indices are re-applied to the new hunk structure regardless. This is structurally the same class of bug as the Sablier finding: a value (the fee rate / here, the line-selection indices) that was fixed at one point in time (debt accrual / diff render) is retroactively re-applied against a different, later state (withdrawal time / commit time) without re-validating that the two states still match, silently changing what the user actually gets charged / commits.

### Impact Explanation
If exploited, the concrete corrupted value is the set of lines included in a commit: a user could believe they are committing only the lines they selected in the diff viewer, but `git apply --cached` ends up staging different lines (because the hunk offsets in the fresh diff no longer line up with the indices from the stale selection), silently corrupting what the user commits and later pushes. This matches the report's "silent corruption of what the user commits or pushes" impact category, since the committed tree can end up containing content the user never reviewed or intended to include (potentially attacker-influenced content originating from a fetched/checked-out repository state that changed the working file after the diff was rendered).

### Likelihood Explanation
This requires the working directory file to change between the time the diff/selection was rendered and the time `stageFiles`/`applyPatchToIndex` runs — a narrow timing window that in the normal UI is usually closed by re-diffing before commit, but I was not able to confirm from the indexed code whether the caller in `app-store.ts` always re-fetches and re-validates the diff/selection pairing immediately before calling `createCommit`/`stageFiles`, or whether a stale in-memory `WorkingDirectoryFileChange` (with its `selection`) captured earlier in the session could be passed through unchanged. Given the index size limits, I could not fully trace the exact call chain from the "Commit" button through `app-store.ts` into `stageFiles` to determine how much time (and therefore how much opportunity for external file mutation) can elapse between diff-render and staging. This uncertainty should be resolved with a full-repository session before treating this as confirmed-exploitable end-to-end, though the missing validation in `apply.ts`/`patch-formatter.ts` itself is verifiable from the indexed code.

### Recommendation
Before applying a partial-selection patch, re-validate that the diff used to build `file.selection` still matches the diff fetched at staging time (e.g. compare hunk headers/line counts, or store a content hash/mtime alongside the `DiffSelection` and abort/re-prompt the user if the working file changed). If a mismatch is detected, `applyPatchToIndex` should fail loudly (forcing the UI to re-diff and ask the user to re-select) rather than silently reapplying indices computed against a stale diff.

### Proof of Concept
Conceptual PoC (would need to be validated in a full checkout, since only partial call-chain visibility was available from the index):
1. Modify a tracked file and open it in Desktop's diff viewer; select only lines 1–5 for the next commit (sets `DiffSelection` indices 1–5 against the current hunk layout).
2. Before clicking "Commit", have an external process (e.g., a git hook triggered by a background fetch/checkout, or another tool) insert/remove lines earlier in the same file, shifting all hunk offsets.
3. Click "Commit". `stageFiles` → `applyPatchToIndex` calls `getWorkingDirectoryDiff` fresh, producing a diff with shifted hunks, but `formatPatch` still uses the original absolute indices 1–5 from the stale selection.
4. Observe (via `git show` on the resulting commit) that the staged/committed lines do not correspond to the 5 lines the user actually selected in the UI, demonstrating silent corruption of committed content — analogous to the Sablier fee being retroactively applied to already-accrued debt without re-checking the debt's context.
