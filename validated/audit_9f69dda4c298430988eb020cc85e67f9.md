### Title
Recursive/nested precompile calls share a single `BalanceHandler` instance, causing balance-changing bank events to be silently dropped and creating a balance desync between `x/bank` and the EVM `StateDB` - (File: `precompiles/common/balance_handler.go`)

### Summary
This is the Cosmos EVM analog of the reported bug class: a value that must be re-captured "fresh" at each logical scope (the liquidation threshold, recomputed per-update) is instead reused/overwritten from a stale earlier computation. In `BalanceHandler`, the "fresh per-call cursor" is `prevEventsLen`, which records the event-manager cursor at the *start* of a precompile call so that only events emitted *during that call* get applied to the EVM `StateDB`. Because the same `BalanceHandler` instance is shared across nested/recursive precompile invocations, an inner call's `BeforeBalanceChange` overwrites this cursor, corrupting the outer call's view of "its own" events, exactly like the reported bug where a shared/global config value overwrote a value that should have been evaluated per-context.

### Finding Description
`BalanceHandler.BeforeBalanceChange` stores the current length of `ctx.EventManager().Events()` into the instance field `prevEventsLen`: [1](#0-0) 

`AfterBalanceChange` then only processes events with index `>= bh.prevEventsLen`, translating `EventTypeCoinSpent`/`EventTypeCoinReceived`/`EventTypeFractionalBalanceChange` bank events into `StateDB.AddBalance`/`SubBalance` calls: [2](#0-1) 

The precompile `Run` flow calls `BeforeBalanceChange` right before executing the precompile method and `AfterBalanceChange` right after, using `p.GetBalanceHandler()`: [3](#0-2) 

If the same precompile (or an EVM contract that calls back into the precompile, or a precompile call that itself triggers another nested precompile call within the same EVM execution) is invoked recursively, the *inner* call's `BeforeBalanceChange` resets `prevEventsLen` to a higher index. When the *outer* call's `AfterBalanceChange` subsequently executes, it uses this now-advanced cursor and therefore skips the bank events that were emitted by the outer call's own balance-changing operations (before the nested/inner call happened), because those events now sit before the (incorrectly advanced) cursor. This causes those bank-side balance changes to never be mirrored into the EVM `StateDB`, producing a divergence between the native `x/bank`/`x/precisebank` balance and the balance visible to the EVM.

This exact defect is reproduced and documented in the repository's own test suite: [4](#0-3) [5](#0-4) 

The test deploys a caller contract that recursively invokes a precompile 10 times within a single transaction and asserts the resulting event count/precompile-call count, confirming that recursive precompile calls sharing one `BalanceHandler` is a real, reachable code path — not a hypothetical.

### Impact Explanation
A StateDB/bank balance desync is a critical accounting-integrity violation under the "Asset-representation path" invariant: `x/vm` StateDB balances must always be reconcilable 1:1 with `x/bank`/`x/precisebank` balances. If bank-side debits are applied (funds actually leave an account in `x/bank`) but the corresponding `StateDB.SubBalance` is skipped due to the clobbered cursor, an attacker's EVM-visible balance would remain inflated relative to their real spendable bank balance — enabling them to spend/transfer funds via EVM operations that should not be available (double-spend), or conversely, if a credit event is dropped, a user could lose funds that were correctly bank-credited without ever appearing as spendable in EVM. Either direction is an unauthorized balance corruption of spendable user value reachable by any unprivileged user who can deploy a contract that makes nested precompile calls (e.g., staking, distribution, bank, or ERC20 precompiles that support such recursion) — matching the required "Critical unauthorized minting/duplication/irreversible accounting corruption" impact class.

### Likelihood Explanation
The trigger requires only an unprivileged user to deploy and call a smart contract that performs precompile calls in a nested/recursive pattern (a `try/catch` self-call pattern, similar to `StakingReverter.sol`'s `nestedTryCatchDelegations`, is already present in the test suite for other purposes), and does not require any privileged role, relayer, or validator collusion. The repository's own dedicated regression test for this exact scenario indicates the maintainers are aware of and actively tracking the bug class, which raises confidence this is a genuine, reachable defect rather than a theoretical one; however, whether it is already fully patched (i.e., whether `BalanceHandler` instances are now created fresh per call rather than shared) could not be confirmed from the available source excerpts — the factory pattern (`BalanceHandlerFactory.NewBalanceHandler()`) suggests fresh instances are *intended* to be created per call, so the actual severity depends on whether any precompile path still reuses a single handler across a recursive call chain (as the test's own comment states occurs).

### Recommendation
Ensure every precompile invocation obtains balance-change tracking that is scoped strictly to its own execution frame, not to an instance shared across nested/recursive calls:
- Use `BalanceHandlerFactory.NewBalanceHandler()` to construct a brand-new `BalanceHandler` for every `Run` invocation (including nested/recursive ones) instead of reusing a `BalanceHandler` field stored on the precompile struct.
- Alternatively, make the event-cursor tracking re-entrant/stack-based (push/pop cursors per call depth) rather than storing a single scalar `prevEventsLen` on a shared struct, so that an inner call's bookkeeping cannot clobber the outer call's bookkeeping.
- Extend the existing `evmd/tests/integration/balance_handler` test to explicitly assert bank-vs-StateDB balance equality after nested calls (not just event counts) to catch silent balance drift.

### Proof of Concept
The repository already contains a reproduction harness at `evmd/tests/integration/balance_handler/balance_handler_test.go`, which:
1. Registers a `debug` static precompile whose `Run` method invokes `BeforeBalanceChange`/`AfterBalanceChange` via a shared `BalanceHandler`.
2. Deploys a `DebugPrecompileCaller` contract and calls `callback(0)`, which recursively re-enters the precompile.
3. Asserts on the resulting event counts (`debug_precompile` events == 10) to demonstrate the recursive-call/shared-handler pattern is reachable in a single transaction. [6](#0-5) 

To fully weaponize this into a fund-extraction PoC, the test would need to be extended to include a real balance-changing precompile (e.g., bank/staking/ERC20 precompile) in the recursive call chain and assert `x/bank` balance vs. EVM `StateDB` balance equality after execution — this final verification step could not be completed here due to tool/session limits, so the Critical balance-corruption impact is inferred from the documented mechanism and existing test comment rather than an end-to-end fund-theft trace.

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))

	res, _, _, err := s.chain.SendEvmTx(
