### Title
`ThresholdKeys::read` allocates attacker-controlled `n`-sized vector before any bounds/limit check, enabling memory-amplification DoS - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to the OpenClaw advisory (GHSA-w2cg-vxx6-5xjg: decode → allocate → check budget), `ThresholdKeys::read` in `crypto/dkg` trusts the serialized `n` field (`u16`, attacker-controlled) and immediately performs `Vec::with_capacity(usize::from(n))` for `Interpolation::Constant`, before validating `ThresholdParams` and before confirming that `n` scalars/points are actually present in the stream.

### Finding Description
The vulnerable code is in `ThresholdKeys::read`: [1](#0-0) 

- `id_len`, `id`, `t`, `n`, `i`, and the interpolation tag are all read directly from the untrusted reader (lines 578-616).
- If `interpolation[0] == 0`, the code executes `Vec::with_capacity(usize::from(n))` (line 608) — a heap allocation sized by the attacker-supplied `n` (up to 65535 elements, ~2 MB for a 32-byte `C::F`) — **before** `ThresholdParams::new(t, n, i)` is invoked at line 626, which is the only place `t <= n`, `i <= n`, and non-zero parameters are enforced.
- Consequently a ~15-byte malicious prefix (`id_len` + `C::ID` + `t` + `n = 0xFFFF` + `i` + `0x00` interpolation tag) forces a ~2 MB allocation; the subsequent `C::read_F` then fails on the truncated stream, but the oversized allocation was already committed and touched.
- The same pattern repeats for the `verification_shares` `HashMap` loop at lines 620-623 (`1 ..= n` `read_G` calls), and `AllParticipantIndexes`/interpolation machinery is only reached after the unchecked sizing work.

Contrast with the defended pattern the codebase itself uses elsewhere (`ethereum/src/machine.rs:51-60` explicitly comments on the 4 GB claim DoS and chunk-reads; `coordinator/src/tributary/transaction.rs:286` checks `commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT` **before** allocating). `ThresholdKeys::read` performs no equivalent pre-allocation budget check.

### Impact Explanation
An unprivileged party that can feed bytes to `ThresholdKeys::read` (an explicitly in-scope sink per the engagement rules — e.g., a peer supplying serialized key material during onboarding, recovery, or key-handoff flows) obtains a memory amplification of roughly four orders of magnitude: ~15 bytes of input → ~2 MB allocation per call. Issued repeatedly, this produces heap pressure / OOM-based denial of service against the host process (CWE-400, CWE-770), matching the reported bug class of "allocation sized by untrusted input before limit enforcement."

### Likelihood Explanation
- Reachability: `ThresholdKeys::read` is a public deserialization entry point on the in-scope `dkg` crate and is listed as an acceptable untrusted-input sink.
- Cost asymmetry: amplification is per-call and repeatable; `n` is a `u16` so the max single allocation is bounded (~2 MB for scalars, plus the follow-on `read_G`/`HashMap` work scaled to `n`), making this a Medium rather than High severity — a sustained stream is required for real memory exhaustion, consistent with the source advisory's Medium rating.
- No authentication or valid signature is needed to reach the allocation; the `ThresholdParams::new` validity check that would reject nonsense `t/n/i` happens strictly *after* the allocation.

### Recommendation
- Validate `t`, `n`, `i` via `ThresholdParams::new` **before** performing any `n`-dependent allocation, and reject `Interpolation::Constant` inputs where the claimed `n` cannot correspond to remaining input length (e.g., require the reader to prove `n * size_of::<C::F::Repr>()` bytes are present, or chunk reads like `ethereum/src/machine.rs` does).
- Replace `Vec::with_capacity(n)` with `Vec::new()` + incremental `push` so capacity is paid only for bytes actually consumed, or impose a hard `MAX_DKG_PARTICIPANTS` bound enforced prior to allocation.
- Audit sibling readers for the same pattern: `SchnorrAggregate::read` (`crypto/schnorr/src/aggregate.rs:77-88`) loops `u32`-controlled `read_G` pushes (no pre-allocation, so proportional — lower risk), and `Commitments::read` (`crypto/dkg/pedpop/src/lib.rs:111`) uses `params.t()` (caller-controlled, not wire-controlled — safe).

### Proof of Concept
```rust
// crypto/dkg/src/lib.rs ThresholdKeys::read amplification
// Input bytes (for a ciphersuite C with a short C::ID, e.g. b"ristretto"):
//   [id_len u32 LE][C::ID][t u16][n u16][i u16][interpolation u8 = 0]
// Set n = 0xFFFF. Only ~10 + C::ID.len() bytes are required.
let mut bytes = vec![];
bytes.extend(&(C::ID.len() as u32).to_le_bytes());
bytes.extend(C::ID);
bytes.extend(&1u16.to_le_bytes());      // t (never validated before alloc)
bytes.extend(&u16::MAX.to_le_bytes());  // n = 65535
bytes.extend(&1u16.to_le_bytes());      // i
bytes.push(0u8);                        // Interpolation::Constant
// Triggers Vec::with_capacity(65535) (~2 MB for 32-byte F) then fails on read_F
let _ = ThresholdKeys::<C>::read(&mut bytes.as_slice());
```

Each invocation commits a ~2 MB allocation from ~15 input bytes; looping it yields the described memory-pressure DoS.
