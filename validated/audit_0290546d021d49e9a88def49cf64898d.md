### Title
Bandwidth metering is bypassed when GetResponses are delivered via the core ISMP `handle` response path - (File: `modules/ismp/core/src/handlers/response.rs`)

### Summary
`pallet-bandwidth`'s `BandwidthGate::try_consume` is the sole mechanism metering inbound message bytes for a `(source chain, app)` pair [1](#0-0) . It is wired into the ISMP router's `on_accept` for POST requests [2](#0-1) , and into `pallet-state-coprocessor`'s custom `Get`-response-with-proof extrinsic, which calls `try_consume` for each `GetResponse` it constructs before dispatch [3](#0-2) . However, the ISMP protocol also exposes a second, generic entry point for delivering `GetResponse`s — `modules/ismp/core/src/handlers/response::handle` — documented as the canonical way relayers submit `ResponseMessage`s with state proofs [4](#0-3) . This handler independently verifies the state proof and dispatches straight to `cb.on_response(...)` with **no call to `BandwidthGate::try_consume` anywhere in the function** [5](#0-4) .

### Finding Description
The core invariant the bandwidth model depends on is: *"Every non-purchase POST/response message from a registered source chain runs through the gate"* [6](#0-5) . This is enforced for POST requests uniformly in `ProxyModule::on_accept` [7](#0-6) , but for Get responses, enforcement was only ever added to the app-specific `pallet-state-coprocessor` code path, not to the generic protocol-level `response::handle` function that the base ISMP message handler dispatches to when a relayer submits `Message::Response(ResponseMessage)` directly. `ProxyModule::on_response` in the runtime even carries a comment claiming it "mirrors the request path in `on_accept`" for bandwidth enforcement, but the function body contains no such check [8](#0-7) , showing the gate is not actually present on this path and was never called there.

This is the direct structural analog of the report's bug class: a resource-consuming operation is validated/charged in one code path (state-coprocessor's custom handler) but the equivalent operation reachable through another legitimate entry point (`ismp::handlers::response::handle`, invoked via the standard `Message::Response` message type) skips that charge entirely — exactly like EIP-7623 floor-gas being checked in execution but not in the consensus path that gates what gets admitted.

### Impact Explanation
Any unprivileged relayer/app can submit a standard `ResponseMessage` (with a genuine state/membership proof for a real `GetRequest`) through the generic ISMP `handle` entrypoint instead of going through `pallet-state-coprocessor`'s metered path, and have `GetResponse`s delivered to destination modules with the byte cost never deducted from the app's `pallet-bandwidth` subscription. This lets bandwidth-metered inbound traffic occupy the router/module dispatch machinery for free, silently draining the value the bandwidth model is supposed to sell (apps stop needing to purchase tiers for GET-response traffic at all), undermining the fee/allowance guarantee `pallet-bandwidth` exists to enforce for any app relying on it for revenue or DoS protection.

### Likelihood Explanation
High — the bypass requires no privileged role, malicious relayer collusion, or front-running; any account capable of constructing a normal `ResponseMessage` with a legitimate proof (the same data structure documented as the standard way to submit responses) can use this path instead of the metered one and get identical execution results without paying bandwidth.

### Recommendation
Add the same `BandwidthGate::try_consume(source, app, bytes)` check to `modules/ismp/core/src/handlers/response.rs::handle` (mirroring the byte computation and gating already done in `state-coprocessor::impls.rs`), or otherwise make the gate check a mandatory precondition inside the router's `on_response` dispatch (`ProxyModule::on_response`) so it applies uniformly regardless of which entrypoint produced the `GetResponse`.

### Proof of Concept
1. Attacker (any account) observes an app `(chain, app)` that has exhausted or never purchased bandwidth.
2. Attacker constructs a valid `ResponseMessage { requests: vec![get_request], proof, signer }` for a legitimate, already-dispatched `GetRequest` targeting that app, with a correct state proof for the destination chain.
3. Attacker submits it via the standard ISMP message-handling extrinsic that routes to `ismp::handlers::response::handle` (rather than through `pallet-state-coprocessor::handle_unsigned`).
4. `handle()` verifies the proof, builds the `GetResponse`, stores the receipt, and calls `cb.on_response(...)` directly — never touching `pallet_bandwidth::BandwidthGate::try_consume` [9](#0-8) .
5. The message is delivered and executed even though `Allowance::<T>::get(app_chain, app)` shows zero remaining bytes, bypassing the gate entirely.

```text
## The Gate

Every non-purchase POST request from a registered source chain runs through `BandwidthGate::try_consume(source, app, bytes)`:

1. If the app is on the **allowlist** for that source, return `Ok` without touching the ledger.
2. Sweep expired subscriptions in place.
3. If no live subscriptions remain → `GateError::NoAllowance`.
4. Sum `remaining_bytes` across live entries. If the sum is short → `GateError::Insufficient { remaining, required }`. **No mutation happens in this case** — the caller can retry after a top-up.
5. Otherwise drain from the head until the requested bytes are satisfied. Pop entries that hit zero. Emit `BandwidthConsumed` with the post-deduct remaining.

The "no mutation on insufficient" property is load-bearing: it means a top-up race is safe — if a message arrives between when an app notices it's short and when the top-up lands, the message stays rejectable rather than half-consuming the subscription.
```
