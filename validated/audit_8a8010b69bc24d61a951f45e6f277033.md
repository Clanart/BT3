## Finding

### Title
Flash-manipulation of AMM spot price via `getAmountIn` lets a gasless-swap user underpay `amountRepay` for `swapForGas` - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The Kaia gasless module gates and prices `SwapForGas` transactions using a spot-price read (`getAmountIn`) from a Uniswap-V2-style AMM pool's instantaneous reserves. Because this price is derived from mutable on-chain reserves rather than a manipulation-resistant oracle, and because Kaia's auction/bundle mechanism allows a searcher to guarantee atomic execution of an arbitrary transaction sequence around a target transaction, a user can transiently skew the pool reserves immediately before (and restore them immediately after) their `SwapForGas` transaction to reduce the `amountIn` required to satisfy `amountRepay`/`minAmountOut`, analogous to the flash-mint/burn price manipulation described in the report.

### Finding Description
`GaslessModule.checkBalanceForSwap` enforces `tx.amountIn >= gsr.getAmountIn(token, minAmountOut)` by calling the on-chain `GaslessSwapRouter.getAmountIn` view function, which is backed by the AMM pool's `getReserves()`/constant-product formula (`UniswapV2Router02.GetAmountIn(amountOut, reserveIn, reserveOut)`): [1](#0-0) [2](#0-1) [3](#0-2) 

This is structurally the same bug class as the FairSide report: a fee/required-payment amount is derived from a pool's live reserve ratio (a spot price) rather than a manipulation-resistant reference, so anyone who can shift the reserves within the same atomic execution window can move the effective exchange rate used for the fee/payment computation.

Kaia's auction module (KIP-249) provides exactly this atomic execution primitive: a searcher's bid guarantees that an arbitrary bundle transaction is executed immediately after a chosen target transaction in the same block, with the bid pool enforcing only bid/sender/size/signature constraints, not any restriction on what the bundled transaction does to shared state such as AMM reserves: [4](#0-3) 

Using this, an attacker (as an `Auctioneer`/searcher, i.e., a normal transaction-bundle submitter) can:
1. Submit a large swap into the same DEX pool used by `GaslessSwapRouter` to skew its reserves and depress the effective price of the gasless-fee token relative to the native gas token.
2. Have their `SwapForGas` transaction execute immediately after, where `checkBalanceForSwap`'s `getAmountIn` (and the router's internal execution, which relies on the same pool state) is evaluated against the manipulated reserves, letting the attacker satisfy `amountRepay`/`minAmountOut` while supplying an artificially reduced `amountIn`.
3. Reverse the initial swap in a following bundled transaction to restore the pool and recover most of the capital used to skew the price, similar to how the FSD attacker burns the minted tokens back after gaining a favorable price.

### Impact Explanation
If exploited, this allows a gasless-swap user to systematically underpay the token amount required to cover their gas repayment (`amountRepay`) relative to its true market value, effectively subsidizing their transaction fees at the expense of the DEX liquidity providers / the gas-repayment mechanism's economic assumptions. This is a fee-abuse / value-extraction vulnerability directly reachable from a public transaction/bundle submitter, matching the "fee delegation abuse" / "gasless settlement theft" categories in scope.

### Likelihood Explanation
Exploitability depends on: (a) the specific token's DEX pool having low enough liquidity/depth relative to the attacker's capital to move the price meaningfully within slippage tolerances (`minAmountOut`), and (b) the attacker being able to reliably sequence transactions atomically, which the auction/bundle mechanism explicitly provides. Both `checkBalanceForSwap`'s gating logic and the underlying `getAmountIn` pricing function read live, unprotected reserve state, so the likelihood is directly tied to available liquidity depth for supported gasless tokens rather than any additional protocol defense (e.g., there is no TWAP, no minimum block delay, and no reserve-manipulation resistance visible in the reviewed code).

### Recommendation
- Avoid using a single-block spot price (`getReserves`-derived `getAmountIn`) for fee/payment validation in `checkBalanceForSwap` and in the router's execution path; use a time-weighted or otherwise manipulation-resistant price reference, or require the `SwapForGas` price check to be re-validated using a price captured over a minimum number of preceding blocks.
- Consider constraining or disallowing DEX-state-mutating bundle transactions from being ordered immediately adjacent to `SwapForGas`/other gasless transactions that rely on that same pool's reserves within a single auction bundle, or add a maximum permissible price-impact bound between the state used for admission and the state used for execution.

### Proof of Concept
1. Attacker deploys/uses an existing low-liquidity Uniswap-V2-style pool registered via `GaslessSwapRouter.dexAddress`.
2. Attacker becomes/colludes with the `Auctioneer`/searcher and submits a bid whose bundle contains: `[large swap skewing reserves] -> [SwapForGas tx with amountIn computed against skewed reserves] -> [reverse swap restoring reserves]`.
3. Because `checkBalanceForSwap` accepts the `SwapForGas` tx as long as `amountIn >= gsr.getAmountIn(token, minAmountOut)` evaluated against current (attacker-controlled) reserves ( [1](#0-0) ), and the bid pool guarantees the bundle's ordering ( [4](#0-3) ), the attacker's `SwapForGas` transaction is admitted and executed with an artificially reduced `amountIn`, netting a profit equal to the price-impact difference minus the swap-back trading fees.

func (bp *BidPool) validateBid(bid *auction.Bid) error {
	blockNumber := bid.BlockNumber

	bp.bidMu.RLock()

	// Check if the auction tx is already in the pool.
	if _, ok := bp.bidMap[bid.Hash()]; ok {
		bp.bidMu.RUnlock()
		return auction.ErrBidAlreadyExists
	}

	// 1. The `bid.Sender` must not be in the winner list of the same block number if the new bid isn't equal to the previous bid.
	if bp.senderHasDifferentWinner(bid) {
		bp.bidMu.RUnlock()
		return auction.ErrBidSenderExists
	}
	bp.bidMu.RUnlock()

	curBlock := bp.Chain.CurrentBlock()
	if curBlock == nil {
		return auction.ErrBlockNotFound
	}

	// 2. The `bid.BlockNumber` must be in range of `[currentBlockNumber + 1, currentBlockNumber + allowFutureBlock]`.
	curNum := curBlock.NumberU64()
	if blockNumber <= curNum || blockNumber > curNum+allowFutureBlock {
		return auction.ErrInvalidBlockNumber
	}

	// 3. The `bid.Bid` must be greater than 0.
	if bid.Bid.Sign() <= 0 {
		return auction.ErrZeroBid
	}

	// 4. The data size must be less than the maximum limit.
	if uint64(len(bid.Data)) > BidTxMaxDataSize {
		return auction.ErrExceedMaxDataSize
	}

	// 5. The gas limit must be less than the maximum limit.
	if bid.CallGasLimit > BidTxMaxCallGasLimit {
		return auction.ErrExceedMaxCallGasLimit
	}

	// 6. The `bid.SearcherSig` and `bid.AuctioneerSig` must be valid.
	if err := bp.validateBidSigs(bid); err != nil {
		return err
	}

	return nil
}
