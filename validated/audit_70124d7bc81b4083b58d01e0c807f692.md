## Finding

### Title
Submodule `file://` protocol re-enabled during checkout can be used by a malicious repository to bypass Git's built-in submodule sandboxing - (File: `app/src/lib/git/submodule.ts`)

### Summary
The lending-contract bug is a case where a per-resource safety configuration (`maxLoanRatio`) is enforced on the "normal" path (`borrow()`) but a second, less-obvious path (`buyLoan()`) performs the same state transition without re-checking the invariant, letting an attacker route around the control that the victim thought was protecting them. The structural analog in Desktop is `updateSubmodulesAfterOperation()` in `app/src/lib/git/submodule.ts`, which accepts an `allowFileProtocol` flag that, when `true`, adds `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation: [1](#0-0) 

### Finding Description
Git added `protocol.file.allow` (default `user`, effectively disabling local `file://` submodule clones for untrusted repos) specifically to close a class of vulnerabilities where a malicious repository's `.gitmodules` points a submodule at a `file://` URL, causing `git submodule update` to silently "clone" arbitrary local paths into the working tree (CVE-2022-39253 and related). Desktop's `updateSubmodulesAfterOperation` reintroduces the old, unsafe behavior whenever it is invoked with `allowFileProtocol: true`: [2](#0-1) 

This function is called from `checkoutBranch()` and `checkoutCommit()` in `app/src/lib/git/checkout.ts`, both of which expose the same flag and pass it straight through to the submodule update step after every checkout: [3](#0-2) [4](#0-3) 

The attacker-controlled surface is a cloned/fetched repository: a repository's `.gitmodules` file is fully attacker-controlled content. If any call site in Desktop's checkout flow (e.g. via `checkoutLocalBranch`, which is itself reachable from the `x-github-client://openRepo` deep link handled in `openBranchNameFromUrl` in `app/src/ui/dispatcher/dispatcher.ts`) invokes `checkoutBranch`/`checkoutCommit` with `allowFileProtocol: true` for a repository the user did not already trust, the attacker's `.gitmodules` can point a submodule at a local `file://` path (e.g. another of the victim's local repos or a path an attacker previously dropped on disk), and `git submodule update --init` will happily "clone" that local content into the victim's working tree — bypassing Git's own protocol-allow guard exactly the way `buyLoan()` bypassed `maxLoanRatio`: the guard exists and is enforced by default in the underlying engine (git), but a specific call path deliberately flips it off without re-validating whether the flag is safe to use for the current, potentially-untrusted repository: [5](#0-4) [6](#0-5) 

Unlike `clone()`, which has an explicit backstop (`isClonePathSensitive`) against path-traversal/sensitive-location writes for the top-level clone destination: [7](#0-6) 

there is no equivalent backstop applied to the *destination* of a submodule update performed with `protocol.file.allow=always` — the sensitive-location and traversal checks are scoped to `clone()`'s own path argument, not to submodule paths resolved from an attacker-supplied `.gitmodules`.

### Impact Explanation
If confirmed to be reachable with `allowFileProtocol: true` for a repository the user is opening/checking out for the first time (e.g. via a crafted `x-github-client://openRepo` link, a malicious fork, or a PR checkout), this allows a remote/attacker-controlled repository to cause Desktop to read/copy local filesystem content into the working tree via a local "clone" of another path on disk, and that content could then be silently committed and pushed by the victim (matching the "silent corruption of what the user commits or pushes" impact class) or used to probe/exfiltrate local paths.

### Likelihood Explanation
Confidence is moderate, not high: I confirmed the flag exists, defaults to `false` in `checkoutBranch`/`checkoutCommit`, and that git's own default (`protocol.file.allow=user`) is designed specifically to block this. I was not able to fully trace, within the available tool budget, every call site in `app-store.ts`/`git-store.ts` that invokes `checkoutBranch`/`checkoutCommit` to determine whether any of them pass `allowFileProtocol: true` unconditionally for repositories that have not been established as locally-trusted (e.g., for the app's own local-fork/test-fixture workflows vs. for arbitrary cloned repositories). This is the key fact that would need to be verified to turn this from "structural bypass exists" into "confirmed exploitable path."

### Recommendation
1. Audit every caller of `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` and confirm `allowFileProtocol` is only ever `true` for repositories/submodule URLs the user has explicitly trusted (e.g., local test fixtures the app itself created), never for arbitrary remote-origin repositories reached via clone, deep link, or PR checkout.
2. If `allowFileProtocol` is needed for legitimate local-submodule workflows, scope it per-submodule-URL (e.g., only allow `file://` if the referenced path is already a known, previously-added local repository) rather than as a blanket flag for the whole checkout.
3. Add a resolved-path safety check for submodule destinations analogous to `isClonePathSensitive()`, so that even with `protocol.file.allow=always`, submodule content cannot be pulled from or written to sensitive host locations.

### Proof of Concept
Conceptual (not executed, since exact reachability of `allowFileProtocol: true` from an untrusted checkout was not fully confirmed):
1. Attacker publishes a repository whose `.gitmodules` defines a submodule with URL `file:///C:/Users/victim/Documents/GitHub/other-private-repo` (or a POSIX equivalent).
2. Victim opens the repository in Desktop via a link that triggers `openBranchNameFromUrl`/`checkoutLocalBranch`, or checks out a PR branch from it.
3. If the checkout path passes `allowFileProtocol: true` into `updateSubmodulesAfterOperation`, `git -c protocol.file.allow=always submodule update --init --recursive` clones the local path into the victim's working tree, bypassing git's built-in protection meant to stop exactly this scenario.
4. The victim, unaware, commits and pushes the resulting working tree, disclosing the local file's contents. [8](#0-7) [3](#0-2)

  private async checkoutLocalBranch(repository: Repository, branch: string) {
    let shouldCheckoutBranch = true

    const state = this.repositoryStateManager.get(repository)
    const branches = state.branchesState.allBranches

    const { tip } = state.branchesState

    if (tip.kind === TipState.Valid) {

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
