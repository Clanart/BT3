### Title
Gasless swap admission check uses a stale on-chain price quote that can diverge from the price at actual execution - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The gasless-transaction sponsorship flow validates a `GaslessSwapTx` by querying the DEX's current exchange rate once, at tx-pool admission/promotion time, and then relies on that single snapshot for the remainder of the transaction's lifetime in the pool (which can span multiple blocks while queued/pending). Just like the Tokemak `LMPVault` issue where `totalAssets()` is read once and used for share pricing without being refreshed before the price-sensitive operation actually executes, `checkBalanceForSwap` computes `requiredAmountIn` from `GetAmountIn` against the current state and never re-validates it against the state at actual inclusion.

### Finding Description
`checkBalanceForSwap` in [1](#0-0)  performs the KIP-247 "swap amount" check by calling the `GaslessSwapRouter.GetAmountIn` view function against the *current* chain state:

```go
requiredAmountIn, err := routerContract.GetAmountIn(nil, token, minAmountOut)
...
if swapArgs.AmountIn.Cmp(requiredAmountIn) < 0 {
    return fmt.Errorf("insufficient amountIn...")
}
```

This function is used both as the tx-pool balance/validity check on submission (`pool.validateTx` → `module.GetCheckBalance()`, [2](#0-1) ) and again during pending-list maintenance (`txList.Filter`, [3](#0-2) ). Both call sites evaluate the AMM's reserves/price *at the moment of the check*, i.e., a live "spot" quote derived from mutable DEX reserve state. Since a `GaslessSwapTx` can sit in the pool (or be re-broadcast) for an unbounded number of blocks before the block-builder actually assembles the `[LendTxGenerator, ApproveTx, SwapTx]` bundle described in [4](#0-3) , ordinary market activity (unrelated swaps against the same DEX pair) can move the pool's reserves between the time this check passes and the time the bundle is actually executed on-chain.

This mirrors exactly the reported bug class: a financial invariant (`requiredAmountIn`/exchange rate here, `totalAssets`/share price there) is computed from state that is read once and used later without being refreshed immediately before the price-sensitive action executes.

### Impact Explanation
Because the gasless flow fronts real KAIA via `LendTxGenerator` (the proposer pays gas on the user's behalf, expecting `amountRepay` back from the swap output, per `repayAmount`/`lendAmount` in [5](#0-4) ), a stale `requiredAmountIn` check means the pool can admit and later promote a swap whose declared `AmountIn` was sufficient at admission time but is no longer sufficient at the block-inclusion reserves. If the on-chain `swapForGas` execution does not independently and atomically re-verify `minAmountOut`/`amountRepay` against the true, current reserves at execution (the only protection visible from the tx-pool side is this stale off-chain quote), the proposer's lent gas may not be fully repaid, or the sender may receive fewer output tokens than assumed when `amountRepay` was fixed — a fee-delegation/gasless settlement value-transfer risk directly reachable by any unprivileged party who can submit a `GaslessApproveTx`/`GaslessSwapTx` pair through the public RPC.

### Likelihood Explanation
Any public-RPC caller can submit gasless approve/swap transaction pairs (KIP-247), and DEX reserves for gasless-whitelisted tokens are moved by ordinary, permissionless swap activity. No privileged access, validator collusion, or p2p manipulation is required — the price staleness window is a normal consequence of tx-pool queuing latency (`MaxBundleTxsInPending`/`MaxBundleTxsInQueue` in [6](#0-5) ) plus block-proposal timing, both of which are attacker-observable and can be amplified by simply timing a counter-swap.

### Recommendation
Re-validate `GetAmountIn`/the effective exchange rate against the state immediately preceding actual swap execution (e.g., inside `swapForGas` itself, atomically, rather than relying solely on the off-chain `checkBalanceForSwap` pre-check), and/or shrink the staleness window by re-checking `checkBalanceForSwap` right before bundle inclusion in block building, not only at admission/`Filter` time.

### Proof of Concept
1. Attacker observes a pending `GaslessSwapTx` for `token`, with `AmountIn` computed to satisfy `GetAmountIn(token, minAmountOut)` at submission time (checked in [7](#0-6) ).
2. While the tx remains queued (subject to `MaxBundleTxsInPending`/pool congestion), attacker submits ordinary swaps on the same DEX pair, shifting reserves so the true `amountOut` for the victim's fixed `AmountIn` would now be lower.
3. When the proposer eventually builds the bundle (`LendTxGenerator + ApproveTx + SwapTx`), the swap executes at the new, worse rate; if the on-chain contract does not itself atomically reject execution when actual output falls below `amountRepay`, the proposer's lent gas is not fully recovered from the swap proceeds — a direct value loss to the fee-delegation counterparty (the block proposer) that was masked by the stale admission-time check.

func (g *GaslessModule) checkBalanceForSwap(swapArgs *SwapArgs, swapNonce uint64) error {
	token := swapArgs.Token
	bc := backends.NewBlockchainContractBackend(g.Chain, nil, nil)

	g.gaslessInfoMu.RLock()
	swapRouter := g.swapRouter
	g.gaslessInfoMu.RUnlock()

	// tx.minAmountOut >= tx.amountRepay
	minAmountOut := swapArgs.MinAmountOut
	amountRepay := swapArgs.AmountRepay
	if minAmountOut.Cmp(amountRepay) < 0 {
		return fmt.Errorf("insufficient minAmountOut: minAmountOut=%s, amountRepay=%s", minAmountOut.String(), amountRepay.String())
	}

	if g.GaslessConfig.ShouldCheckSenderCode() {
		if g.getCurrentHasCode(swapArgs.Sender) {
			return errors.New("sender with code is not allowed")
		}
	}

	if g.GaslessConfig.ShouldCheckSwapAmount() {
		// tx.amountIn >= gsr.getAmountIn(minAmountOut)
		routerContract, err := kip247.NewGaslessSwapRouterCaller(swapRouter, bc)
		if err != nil {
			return err
		}
		// Required token amountIn, given the current exchange rate and the declared minAmountOut.
		requiredAmountIn, err := routerContract.GetAmountIn(nil, token, minAmountOut)
		if err != nil {
			return err
		}
		if swapArgs.AmountIn.Cmp(requiredAmountIn) < 0 {
			return fmt.Errorf("insufficient amountIn: have=%s, want=%s", swapArgs.AmountIn.String(), requiredAmountIn.String())
		}
	}

### Block building rules

Upon detection of GaslessTxs, the following logics are executed:

- Per sender, if exists, GaslessApproveTx is relocated before GaslessSwapTx.
- LendTxGenerator is prepended before GaslessApproveTx.
- A new bundle is generated which contain either `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]` or `[LendTxGenerator, GaslessSwapTx]`
- If the bundle has conflict with any previous bundles, it is excluded from the returned bundle list.

func lendAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	r := new(big.Int)

	// R2 = ApproveTx.Fee() if exists
	if approveTxOrNil != nil {
		r.Add(r, approveTxOrNil.Fee())
	}

	// R3 = SwapTx.Fee()
	r.Add(r, swapTx.Fee())

	// LendAmount = R2 + R3
	return r
}

func repayAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	// R1 = LendTx.Fee() = SwapTx.GasPrice() * TxGas
	r1 := new(big.Int).Mul(swapTx.GasPrice(), new(big.Int).SetUint64(params.TxGas))

	// RepayAmount = R1 + R2 + R3
	return new(big.Int).Add(r1, lendAmount(approveTxOrNil, swapTx))
}
