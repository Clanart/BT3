## Finding [1](#0-0) 

### Title
Escrow accounting is finalized even when ERC20 `transfer` silently fails in `withdraw()` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()` moves escrowed tokens using a raw low-level `.call()` encoded with `IERC20.transfer.selector` and only checks that the *call itself* did not revert (`success`), never decoding/checking the returned `bool` payload. For ERC20 tokens that signal a failed transfer by returning `false` rather than reverting, `success` is still `true`, so the function proceeds to permanently zero out the escrow accounting (`_orders[commitment][token] -= amount`), mark `_filled[commitment]`, and emit `EscrowReleased`/`EscrowRefunded` — even though the beneficiary never received the tokens. This is the direct analog of the external report's ERC20-return-value class bug, but manifests as silent fund loss/permanent lock rather than a DoS-by-revert.

### Finding Description
In `withdraw()`: [2](#0-1) 
```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```
`success` here only reflects whether the low-level call reverted — not whether the ERC20 `transfer` actually moved value. Standard-compliant tokens that return `false` on failed transfer (rather than reverting) will make `success == true` while zero tokens move. The same pattern repeats for the transaction-fee payout a few lines later, and again in `onAccept`'s `SweepDust` handling: [3](#0-2) [4](#0-3) 

Notably, the contract *does* use OpenZeppelin's `SafeERC20` (`using SafeERC20 for IERC20;`) elsewhere, e.g. `safeTransferFrom` on deposit (`evm/tron/contracts/apps/IntentGatewayV2.sol:399,478`), showing the codebase is aware of non-standard ERC20 return semantics but did not apply the same safety to the payout/withdraw path. This is the same broken invariant as the external report (naive ERC20 transfer handling breaking custody/settlement bookkeeping), just inverted: instead of reverting on a token with no return value, it silently accepts a token that explicitly signals failure via a `false` return.

Once `withdraw()` completes its loop, `_orders[commitment][token]` is decremented to zero regardless of whether the transfer moved funds. Any subsequent retry (`cancelOrder` cross-chain refund path, or a repeated `onAccept` `RedeemEscrow`/`RefundEscrow` delivery) is blocked by the `UnknownOrder()` check: [5](#0-4) 
so the escrowed tokens remain stuck in the `IntentGatewayV2` contract with no code path left to release them to the rightful beneficiary.

### Impact Explanation
This directly breaks the required invariant that "bridged assets, order escrow, refunds... must move exactly once and only to the rightful beneficiary and amount." Here funds move zero times to the beneficiary, yet the contract's internal state (`_orders`, `_filled`, emitted events) asserts settlement occurred, causing silent, permanent loss/lock of user-escrowed funds with no retry path. This qualifies as fund loss under the bounty's accepted impact categories.

### Likelihood Explanation
Likelihood is Medium: it requires an escrowed input/output token whose ERC20 implementation returns `false` on failure instead of reverting (a known, non-trivial-but-real subset of deployed ERC20 tokens), or a corner case where the contract's tracked balance and actual token balance diverge (e.g. fee-on-transfer tokens) causing a legitimate `transfer` call to return `false`. No malicious relayer, prover, or admin is required — this can be triggered by ordinary users choosing (or being forced by order construction) to use such a token as an input/output asset.

### Recommendation
Use `SafeERC20.safeTransfer` (already imported and used elsewhere in the contract, e.g. `safeTransferFrom`) for all outbound token movements in `withdraw()` and the `SweepDust` handler, instead of manually crafting low-level `.call()` + `abi.encodeWithSelector(IERC20.transfer.selector, ...)` and checking only call-level success. This ensures both revert-on-no-bool and false-return failures are treated consistently as failures, and the escrow state is only finalized after a genuinely successful transfer.

### Proof of Concept
1. Create/fill an order where one of `order.inputs`/`order.output.assets` tokens is an ERC20 implementation that returns `false` (instead of reverting) on a failed `transfer` (e.g., due to a paused/blacklist state on the token that resolves to `false`, or a fee-on-transfer token where the contract's tracked escrow amount exceeds the actual transferable balance).
2. Have the destination or source path invoke `withdraw()` via `onAccept` (`RedeemEscrow`/`RefundEscrow`) or same-chain `cancelOrder`.
3. `token.call(...)` returns `(true, data)` where `data` decodes to `false`; since only `success` (call-level) is checked, execution proceeds.
4. `_orders[body.commitment][token] -= amount` zeroes the escrow slot, `_filled[commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — while the beneficiary's token balance is unchanged.
5. Any retry attempt hits `UnknownOrder()` at [6](#0-5) , permanently trapping the tokens in the `IntentGatewayV2` contract.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
