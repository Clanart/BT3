### Title
Rotation proofs bypass the parachain-height staleness check, enabling duplicate first-proof (position-0) treasury rewards for the same finality advance - (File: modules/pallets/beefy-consensus-proofs/src/lib.rs)

### Summary
`pallet-beefy-consensus-proofs` pays the full base reward to whichever prover's `submit_proof` call is treated as the "first proof" for a given parachain height, and treats a proof as "first" whenever `verify_and_apply` returns `Ok` rather than `Err(StaleProof)`. The pallet's own documentation states that the staleness check based on "parachain height ≤ latest_state_machine_height" is **exempted for rotation (mandatory) proofs** [1](#0-0) . Because `settle_first_proof` unconditionally pays `pay_position_reward(&submitter, 0)` (full reward) whenever the dispatch reaches that path [2](#0-1) , and `record_uncle_metadata`/`ProverCount`/`AcceptedProvers`/`ProofContext` are all keyed only by `outcome.latest_height` regardless of whether the settling proof is a messaging proof or a rotation proof [3](#0-2) , a rotation proof that targets a height already advanced past by an earlier messaging proof can still land on the "first proof" path and mint a second full reward for the same finality/height, rather than being demoted to the decreasing-curve uncle path.

### Finding Description
The reward-settlement dispatch in `do_submit_proof` routes as follows:
- `verify_and_apply(&proof)` → `Ok(outcome)` ⇒ `settle_first_proof` (full base reward, position 0) [4](#0-3) 
- `verify_and_apply(&proof)` → `Err(StaleProof)` for an SP1 proof ⇒ `settle_uncle_proof` (decreasing-curve reward, position ≥ 1) [5](#0-4) 

The documented semantics of `StaleProof` are: "the BEEFY verifier rejected its commitment as at or below `latest_beefy_height`, **or** it is a messaging proof whose parachain height is `≤ latest_state_machine_height`. **Rotation proofs are exempt from the latter**" [1](#0-0) . In other words, the "have we already advanced past this parachain height" guard that normally forces a second submission for an already-settled height into the uncle path does not apply to rotation proofs.

`settle_first_proof` treats every successful `verify_and_apply` outcome identically: it records uncle bookkeeping keyed by `outcome.latest_height` and unconditionally pays position-0 reward via `Self::pay_position_reward(&submitter, 0)` [6](#0-5) . There is no check here for "was a first proof already settled at this same `outcome.latest_height`" — that information (`ProverCount`, `AcceptedProvers`, `ProofContext`) is only consulted by the uncle path (`settle_uncle_proof`), which is never reached because the rotation proof did not return `StaleProof` in the first place.

This is the direct structural analog of the FlywheelV2 bug: a value meant to gate "have we already accounted for this cycle/height" (`storedCycle` vs `gaugeCycle` in FlywheelV2; `latest_state_machine_height` vs the rotation proof's own target height here) is bypassed for one code path (reactivated gauges / rotation proofs), producing an incorrect reward-accounting outcome (lost rewards in FlywheelV2; duplicated full reward here) instead of the intended fallback (correctly computed prior-cycle reward in FlywheelV2; decreasing-curve uncle reward here).

### Impact Explanation
If a rotation (mandatory authority-set) BEEFY proof can validly target a parachain height that a prior messaging proof has already advanced state past, the treasury pays out a second full base reward (`ProofReward`) for what should be, at most, an uncle-curve reward — a duplicate settlement of the same finality-advance work. This is fund loss from the treasury attributable to a logic flaw in reward routing, matching the bounty's "duplicate settlement / double-claim" and "loss of funds" categories. The reward is paid from `TreasuryPalletId`'s account via `T::Currency::transfer` [7](#0-6) , so each mis-routed "first proof" settlement directly drains protocol funds.

### Likelihood Explanation
Running a BEEFY prover is explicitly permissionless — "no staking or whitelisting is required to participate. Any operator can run a prover and begin competing to submit proofs and earn rewards" [8](#0-7) . This satisfies the "unprivileged attacker, no malicious relayer/prover/admin assumption needed" requirement, since prover participation itself is an open, permissionless role rather than a privileged/trusted one. The likelihood that a legitimate mandatory-rotation commitment happens to target a height already covered by a prior messaging proof (or lower) depends on the underlying BEEFY/ISMP commitment structure, which I could not fully verify because the body of `verify_and_apply` was not available in the index — this is the main open uncertainty in this finding.

### Recommendation
Have `settle_first_proof` check whether `ProverCount::<T>::get(outcome.latest_height)` (or an equivalent "already settled" marker) is nonzero before paying a position-0 reward, regardless of proof type; if a first-proof reward for that exact height has already been paid, route the rotation proof through the same position/curve logic as `settle_uncle_proof` instead of unconditionally paying full reward. This closes the gap the same way the FlywheelV2 fix did — by keeping the "already accounted for" state (`ProverCount`/`AcceptedProvers`) authoritative across every code path that can reach a reward payout for the same height, rather than only being consulted on the `StaleProof` branch.

### Proof of Concept
Not independently reproducible from the available index because the exact conditions under which a rotation proof's `outcome.latest_height` can coincide with (or fall behind) an already-processed messaging proof's height depend on `verify_and_apply`'s internal logic, which was not retrievable via search/read tools in this session. The vulnerability claim rests on the documented exemption in the `Error::StaleProof` comment [1](#0-0)  combined with the unconditional position-0 payout in `settle_first_proof` [2](#0-1) . Confirming exploitability requires reading the full `verify_and_apply` implementation (not included in the search results) to establish precisely which height/staleness conditions a rotation proof can satisfy while a messaging proof cannot.
