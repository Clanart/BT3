### Title
Unpriced O(account_size) zero-fill/copy work in `update_caller_account`/`update_callee_account` via shrink/grow CPI oscillation - (File: program-runtime/src/cpi.rs)

### Summary
When `syscall_parameter_address_restrictions` is enabled and `!account_data_direct_mapping`, every CPI whose target account's data length differs from the previous length triggers a full zero-fill of the discarded tail and/or a full `copy_from_slice` proportional to the account's data size in `update_callee_account` and `update_caller_account`, but the CPI is charged only the flat `invoke_units` cost via `cpi_common`. An attacker can toggle an account's length (shrink then grow) on every CPI, at `MAX_PERMITTED_DATA_INCREASE` granularity, to repeatedly force O(account_size) memory work per CPI call for the price of a single flat charge.

### Finding Description
`cpi_common` charges a fixed `invoke_units` compute cost per CPI regardless of any account data-size work performed: [1](#0-0) 

Unlike instruction data and account metas, which are explicitly billed per byte via `cpi_bytes_per_unit` in `translate_instruction_c`: [2](#0-1) 

...the account *data buffer* copy/zero-fill performed in `update_callee_account` (CPI entry) and `update_caller_account` (CPI exit) has no equivalent per-byte charge. On CPI entry, if the caller previously shrunk the account, `update_callee_account` zero-fills the old tail via `get_serialized_data`: [3](#0-2) 

On CPI exit, `update_caller_account` re-derives `serialized_data` (which re-slices/zero-fills on shrink) and then unconditionally copies the entire callee's data buffer back into the caller's serialized region: [4](#0-3) 

`CallerAccount::get_serialized_data` is only bounded by `address_space_reserved_for_account = original_data_len + MAX_PERMITTED_DATA_INCREASE`, not by any compute charge: [5](#0-4) 

An attacker program can, in a loop, directly write the `AccountInfo` data-length field (no syscall required — this is a plain host-memory write the program does before invoking) to shrink the account to 0 and then grow it back to `original_data_len` before each successive no-op CPI. Because `original_data_len` is fixed for the whole top-level instruction (it is the account's size at instruction start, which can be pre-grown to up to `MAX_PERMITTED_DATA_LENGTH` in a prior transaction), each CPI call in the loop causes:
- a full-length zero-fill of the tail on shrink,
- a full-length `copy_from_slice` of size `post_len` to propagate data back to the caller on grow,

while the CPI is charged only `invoke_units` (a small flat constant), independent of `original_data_len`. This work-for-cost ratio is unbounded by the account size, since `original_data_len` (and hence the per-CPI work) can be made arbitrarily large (up to `MAX_PERMITTED_DATA_LENGTH`) while `invoke_units` stays fixed.

The existing safeguards (`InvalidRealloc` size checks, `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION`/`MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION`) only limit *net growth* of account data across a transaction; they do not limit the number of shrink/grow CPI *oscillations*, since the resulting size after each oscillation returns to the same `original_data_len` and never triggers the growth-limit accounting (which only tracks deltas relative to on-chain size, not intra-instruction toggling).

This code path is only reachable when `!account_data_direct_mapping` — this is explicit in the guard `!(virtual_address_space_adjustments && account_data_direct_mapping)` at lines 1275 and 1313. If `account_data_direct_mapping` is cluster-activated, both the zero-fill and the copy are skipped (`get_serialized_data` returns `Ok(&mut [])` at lines 239-240), neutralizing this specific vector.

### Impact Explanation
This falls under "materially underpriced compute": an attacker can force real CPU work (memset + memcpy) that scales with account size (up to 10 MB per operation) on every CPI call, while the CU meter only deducts a small, size-independent `invoke_units` charge. Repeated across many CPIs within one instruction's compute budget, this multiplies the ratio of real work to billed compute units far beyond what legitimate memory operations cost (e.g., `mem_op_base_cost`/`cpi_bytes_per_unit` pricing used elsewhere for memcpy/memmove syscalls), degrading validator throughput without proportional fee/CU cost, matching the described scope: "syscall/CPI/deserialization work whose real CPU/memory cost far exceeds the compute units charged."

### Likelihood Explanation
Preconditions: `syscall_parameter_address_restrictions == true` and `!account_data_direct_mapping`. This is fully attacker-controllable in the sense that the attacker just deploys/writes their own program using ordinary CPI/realloc patterns; it does not require any validator, leader, or config compromise. The main caveat for real-world exploitability is that `account_data_direct_mapping` has been progressively activated on live Solana clusters; where it is active, the vulnerable branch is skipped. On any cluster/config where this feature is not yet active (or in future forks/testnets), the described shrink/grow oscillation is directly reachable using standard `AccountInfo::realloc`/CPI mechanics, and is repeatable indefinitely within a single transaction's compute budget.

### Recommendation
Charge a per-CPI compute cost proportional to the account data size touched in `update_callee_account`/`update_caller_account` (e.g., using `cpi_bytes_per_unit`, consistent with how `translate_instruction_c` prices instruction data and account metas), for both the zero-fill and the `copy_from_slice`/`set_data_from_slice` operations, whenever `prev_len != post_len` or data is propagated. Alternatively, bound the number of length-oscillations per instruction, or track cumulative bytes zero-filled/copied via CPI account-length changes against a compute-metered budget in `cpi_common`.

### Proof of Concept
```rust
// program-runtime/src/cpi.rs (integration-style unit test, extending existing test harness)
// Simulates repeated shrink(0)/grow(original_len) toggling across N CPI calls and
// measures cumulative bytes touched by update_caller_account/update_callee_account
// vs. cumulative CU charged (invoke_units * N).

#[test]
fn test_shrink_grow_oscillation_underpriced() {
    const ORIGINAL_LEN: usize = 9 * 1024 * 1024; // pre-grown account, within MAX_PERMITTED_DATA_LENGTH
    const ITERATIONS: usize = 100;

    // Setup: account pre-grown to ORIGINAL_LEN (simulating a prior transaction's growth).
    // For each iteration:
    //   1. caller_account.ref_to_len_in_vm = 0  (shrink)
    //   2. call update_callee_account -> expect full ORIGINAL_LEN zero-fill
    //   3. callee resizes back up to ORIGINAL_LEN (grow, within address_space_reserved_for_account)
    //   4. call update_caller_account -> expect full ORIGINAL_LEN copy_from_slice
    //
    // Assertions:
    //   - cumulative_bytes_touched == ITERATIONS * 2 * ORIGINAL_LEN (approx)
    //   - cumulative_cu_charged == ITERATIONS * invoke_units (flat, independent of ORIGINAL_LEN)
    //   - assert cumulative_bytes_touched / cumulative_cu_charged >> cpi_bytes_per_unit
    //     (i.e., real bytes-per-CU ratio far exceeds the priced memcpy rate),
    //     demonstrating underpricing.
}
```
Expected result: the ratio of bytes actually zero-filled/copied to CUs charged for CPI (`invoke_units`) is orders of magnitude higher than the priced `cpi_bytes_per_unit` rate used for equivalent memcpy/memset syscalls elsewhere in the codebase (e.g. `mem_ops.rs::mem_op_consume`), confirming the underpricing when `!account_data_direct_mapping`.
