## Analysis

The Solidity bug's core defect is a **stale cached value that is only conditionally refreshed** (only when `accPnlPerToken < 0`) instead of being unconditionally recomputed against the new state, so the cached value silently drifts from truth as external state changes.

GitHub Desktop has a structurally identical pattern in how it preserves a user's **partial line-selection state** for committing when the underlying diff is refreshed. The selection is tracked purely by **numeric line index**, and when the diff is reloaded, the code re-maps the old selection onto the new diff by index only — never validating that the line at that index still contains the same content.

### Title
Partial commit line-selection is preserved by numeric index (not content) across diff refresh, allowing silent corruption of what the user commits/pushes - (`app/src/lib/stores/app-store.ts`, `app/src/models/diff/diff-selection.ts`)

### Summary
`WorkingDirectoryFileChange.selection` (a `DiffSelection`) records which lines are checked/unchecked for the next commit using integer line indices (`divergingLines: Set<number>`). When the working-directory diff for the selected file is reloaded (e.g. after a file-system change caused by `pull`, `checkout`, a stash pop, or any external process that rewrites the file while the Changes view is open), `updateChangesWorkingDirectoryDiff` recomputes the new diff and calls `DiffSelection.withSelectableLines()` to reconcile the old selection with it [1](#0-0) . `withSelectableLines` only filters `divergingLines` to indices that are still "selectable" in the new diff — it does not check whether the text at that index is the same as before [2](#0-1) .

### Finding Description
The code comment in `app-store.ts` explicitly acknowledges the gap:

> "The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines such that any previously selected line which now no longer exists or has been turned into a context line isn't still selected." [3](#0-2) 

This mirrors the `scaleVariables()` flaw exactly: instead of always recomputing the invariant (which lines are truly intended to be committed) against the new authoritative state (new diff content), the code only performs a partial/conditional reconciliation (index-existence check) and keeps the stale `divergingLines` set otherwise. If a hunk shifts or content is replaced but the **same line indices remain selectable** in the new diff (a very common occurrence — e.g., a 3-line block replaced by another 3-line block at the same position, or `unifiedDiffStart` recomputing to the same offsets), the old "checked" state is silently reapplied to entirely different content, with `isSelected(lineIndex)` returning true/false based on stale bookkeeping rather than the actual new line [4](#0-3) .

### Impact Explanation
This is "silent corruption of what the user commits or pushes": the partial-commit patch (built via `formatPatch`, which walks `file.selection.isSelected(...)` per diff line) will stage/commit content the user never reviewed at that index, or omit content the user intended to include, with no error, warning, or diff re-render forcing a fresh look before commit. Given the low `getSelectableLines`-based bar and no content hash comparison, this can happen in ordinary flows (fetch/pull/checkout while the Changes pane has a partial selection), and can be amplified by a malicious remote/hook that intentionally shapes commits so that a victim's stale selection maps onto attacker-chosen lines. There is no confirmation dialog before commit, so this corrupts the commit/push output without the user's awareness.

### Likelihood Explanation
Likelihood is High for accidental corruption (any workflow where the working tree changes underneath an open partial selection — a very common Desktop usage pattern), and plausible for adversarial amplification (an attacker-controlled remote/hook engineering diffs so index alignment reliably lands on attacker content) whenever the victim has staged a partial selection and then updates the working copy from that remote before committing.

### Recommendation
Never reconcile `DiffSelection` state by line index alone across a diff refresh. Instead, `withSelectableLines`/`updateChangesWorkingDirectoryDiff` should invalidate (clear to unselected, or force full re-selection) the diverging-line set whenever the file's diff content actually changes at previously-selected indices, or track selection against a content-derived key (e.g., hash of line content plus hunk anchor) rather than raw numeric offsets, so a refreshed diff can never silently inherit stale include/exclude decisions.

### Proof of Concept
1. Open GitHub Desktop, modify a tracked file so that it has several added lines in one hunk; in the Changes view, select only some of those lines for the next commit (partial selection), leaving the file uncommitted.
2. While the partial selection is active, cause the working directory diff to be recomputed for that same file — e.g. run `git checkout -- <file>`/`git pull`/`git stash pop` from another terminal, or have a background tool (formatter, build step, or malicious post-checkout hook from a fetched remote) rewrite the same line range with different content but the same number of lines/hunk shape.
3. Desktop's file watcher triggers `updateChangesWorkingDirectoryDiff`, which calls `getWorkingDirectoryDiff` and then `currentlySelectedFile.selection.withSelectableLines(selectableLines)` [5](#0-4) .
4. Because the previously selected indices remain "selectable" in the new diff, they remain marked as selected/deselected exactly as before, even though the underlying text is now different content.
5. Commit: the resulting patch (from `formatPatch`) silently includes/excludes lines the user never actually reviewed at commit time, corrupting the committed/pushed content without any warning.

  /** Returns a value indicating wether the given line number is selected or not */
  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }

  public withSelectableLines(selectableLines: Set<number>) {
    const divergingLines = this.divergingLines
      ? new Set([...this.divergingLines].filter(x => selectableLines.has(x)))

    return new DiffSelection(
      this.defaultSelectionType,
      divergingLines,
