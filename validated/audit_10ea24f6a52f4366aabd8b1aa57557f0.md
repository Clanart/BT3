### Title
Outputs below `N::DUST` sent to a multisig address are silently dropped by the scanner, permanently locking spendable funds — ([File: processor/src/multisigs/scanner.rs])

### Summary
When the processor's scanner finds outputs paying to a tracked multisig key, it discards any output whose value is below `N::DUST` before recording it. For Bitcoin, `DUST` is hard-coded to `10_000` satoshis — far above the actual economic spendability threshold (~285 sats at 5 sat/vbyte per the code's own analysis). Any external party can send e.g. 9,999 sats to the multisig's external address; the output is confirmed on-chain, is cryptographically spendable by the threshold key, yet is never reported, tracked, or recoverable. Like the `SpiceAuction` finding, value becomes permanently locked with no recovery mechanism because accounting drops it instead of tracking it.

### Finding Description
In `processor/src/multisigs/scanner.rs`, the scan loop filters outputs before pushing them into `outputs`:

```rust
// processor/src/multisigs/scanner.rs
for output in network.get_outputs(&block, key).await {
  assert_eq!(output.key(), key);
  if output.balance().amount.0 >= N::DUST {
    outputs.push(output);
  }
}
```

Sub-dust outputs are dropped here and never reach `save_scanned_block`, the RAM output set, or the DB — no output ID is ever recorded, so rescanning cannot resurrect them (they are filtered on every pass, not merely deferred). For Bitcoin, `Bitcoin::DUST` in `processor/src/networks/bitcoin.rs` is `10_000` sats, justified in comments by needing outputs "worth our time" — yet the same comment computes a real spendability floor of ~285–1,000 sats. A 9,999-sat output to `external_address(key)` is therefore economically spendable but permanently invisible to the scheduler, and `SignableTransaction::new` can only consume `ReceivedOutput`s it is handed — there is no API to recover an untracked UTXO.

### Impact Explanation
Funds confirmed on-chain to the multisig become permanently unspendable by the protocol. This is reachable entirely with public inputs: any unprivileged user sends a normal Bitcoin transaction paying <10,000 sats to the externally published deposit address. Repeated small deposits, a fee-skimming pattern, or a user dusting the address can accumulate a meaningful locked balance with no remediation path — a direct analog of "auction tokens locked, `recoverToken` bounded by `balance - totalAllocation`": the contract holds the tokens, but no mechanism exists to move them.

### Likelihood Explanation
Medium. It requires only a below-threshold deposit, which happens naturally with small payments or attacker-initiated griefing; no privileged position, collusion, or malformed inputs are needed. Impact is bounded per-deposit (each lock is <10k sats) but can be repeated arbitrarily, and protocol-level recovery would require an out-of-band key ceremony — effectively the "rare but irrecoverable" profile of the source report.

### Recommendation
Track all confirmed outputs regardless of value (record them in the scanned-outputs DB), and let the scheduler — not the scanner — decide whether including an input is economical given the current fee rate. Lower `Bitcoin::DUST` to the actual spendability bound, or add a sweep/recovery plan that can consolidate sub-threshold UTXOs when fee conditions make it worthwhile.

### Proof of Concept
1. Retrieve the multisig's external address via `Bitcoin::external_address`.
2. From any wallet, publish a transaction paying 5,000 sats to that address and wait `CONFIRMATIONS` blocks.
3. `Bitcoin::get_outputs` returns the `Output` with `balance.amount.0 = 5000`; the filter at `processor/src/multisigs/scanner.rs` `output.balance().amount.0 >= N::DUST` (5000 < 10_000) drops it, so no `ScannerEvent::Block` reports it and it is never written via `save_scanned_block`.
4. The UTXO sits at `key`'s P2TR script — spendable in principle — but no plan, scheduler entry, or DB record references its `OutPoint`, and `SignableTransaction::new` has no way to obtain it. The 5,000 sats are locked indefinitely with no recovery mechanism.
