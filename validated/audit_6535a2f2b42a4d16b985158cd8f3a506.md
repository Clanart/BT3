### Title
Division-by-zero crash in `Mempool.create_bundle_from_mempool_items()` when a mempool item's dedup cost-saving fully offsets its cost - (File: `chia/full_node/mempool.py`)

### Summary
`Mempool.create_bundle_from_mempool_items()` computes `item_cost = cost - cost_saving` for every mempool item it considers for inclusion in a new block, and then eagerly evaluates `fee / item_cost` as a positional argument to `log.info(...)`. [2](#0-1) . Because Python evaluates call arguments before invoking the function, this division is executed unconditionally on every iteration of block building, independent of the configured log level. If `item_cost` reaches `0`, this raises an uncaught `ZeroDivisionError`, aborting block-generator construction. This is analogous to the referenced GStreamer CVE-2017-5844, where crafted/attacker-influenced input drove an unguarded arithmetic operation (division) to a value that produced a floating-point exception and crashed processing.

### Finding Description
`cost` is the mempool item's total CLVM execution cost (`item.conds.cost`), and `cost_saving` is the sum of per-coin costs of any coin spends in the item that are eligible for DEDUP and whose identical solution was already committed to `dedup_coin_spends` by a higher-fee-rate item earlier in the same block-building pass: [3](#0-2) 

`get_deduplication_info()` sums `dedup_coin_spend.cost` for every DEDUP-eligible coin ID whose solution matches a previously-cached spend, without any bound relative to the item's overall cost: [4](#0-3) 

Back in `create_bundle_from_mempool_items()`, this `cost_saving` is subtracted from `cost` to form `item_cost`, which is then used unguarded as a divisor in the eagerly-evaluated logging call: [5](#0-4) 

Unlike the admission-time check in `MempoolManager.validate_spend_bundle()`, which rejects a spend bundle whose *own* `cost == 0` at submission time [6](#0-5) , there is no equivalent check on `item_cost` (the *post-dedup* cost) inside `create_bundle_from_mempool_items()`. Nothing in `IdenticalSpendDedup.get_deduplication_info()` prevents `cost_saving` from equaling `cost` if every coin spend in the item is DEDUP-eligible and all of them were already recorded by earlier-processed items in the same block-building pass.

Since DEDUP eligibility is checked purely on canonical CLVM serialization matching, an unprivileged wallet user or spend-bundle submitter can construct multiple otherwise-independent spend bundles that spend the exact same DEDUP-eligible coin(s) with byte-identical solutions (a normal, permitted pattern for ring/announcement-style aggregation coins) and stagger their fees such that a lower-fee-rate item's *entire* set of coin spends becomes fully "shadowed" by a higher-fee-rate item processed earlier in the same block-building pass.

### Impact Explanation
If `item_cost` reaches `0`, the unguarded division raises `ZeroDivisionError` inside `create_bundle_from_mempool_items()`, which is invoked by `create_block_generator()` on the full node's block-farming path [7](#0-6) . An uncaught exception here halts block-generator creation for that farming attempt, a spend-triggered denial-of-service against transaction processing/block production reachable purely from mempool contents assembled by unprivileged spend-bundle submitters.

### Likelihood Explanation
Reaching this requires that an item's coin spends are *entirely* composed of DEDUP-eligible spends and that *all* of them, with matching costs, were already cached by earlier, higher-fee-rate items processed in the same pass — a specific but not inherently forbidden configuration, since there is no rule (analogous to the FF-only rejection at admission) preventing an all-DEDUP item from being admitted or from having its full cost dedup-shadowed during block building. I was not able to fully verify from the available context whether `conds.cost` (used as `cost`) always includes non-zero fixed overhead (e.g., quote/generator overhead) beyond the sum of per-coin spend costs, which would determine whether `item_cost` can reach exactly `0` in practice versus only a very small positive residual. This uncertainty means the crash-triggering condition is plausible but not conclusively proven from the code alone.

### Recommendation
Guard the divisor before use: compute `fee / item_cost` only when `item_cost > 0`, or move the division inside a lazy log format (`%s`-style with the ratio precomputed under an `if item_cost > 0` branch, or skip/represent as `"n/a"` when `item_cost == 0`). More robustly, cap `cost_saving` in `IdenticalSpendDedup.get_deduplication_info()` so it can never reach the item's own total `cost`, and add an explicit `item_cost == 0` defensive check in `create_bundle_from_mempool_items()` (skip the item or treat it as free/zero-fee-rate) before any arithmetic uses it as a divisor.

### Proof of Concept
Conceptual reproduction (given the identified gap could not be fully confirmed to reach exact zero from static review alone):
1. Submit spend bundle A spending coin X (DEDUP-eligible, e.g., a CAT ring/announcement coin) plus a normal fee-paying coin, with a high fee rate.
2. Submit spend bundle B spending the *same* coin X with an identical solution, and no other coins, at a lower fee rate, such that B's `conds.cost` is entirely attributable to spending X.
3. During block building, A is processed first (higher fee rate) and caches X's dedup cost. When B is processed, `get_deduplication_info()` returns `cost_saving == B.cost`, making `item_cost = B.cost - cost_saving == 0`.
4. `log.info("Cumulative cost: %d, fee per cost: %0.4f, item cost: %d", cost_sum, fee / item_cost, item_cost)` raises `ZeroDivisionError`, aborting `create_bundle_from_mempool_items()` / `create_block_generator()` for that farming attempt.
