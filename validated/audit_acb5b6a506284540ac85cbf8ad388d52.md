### Title
Missing `Approval`-event validation in ERC20↔Coin conversion lets a permissionlessly-registered malicious ERC20 drain the entire pooled escrow held by the `x/erc20` module account - (File: `x/erc20/keeper/msg_server.go`)

### Summary
This is a direct analog of the PoolTogether finding: a factory-style trust boundary (`LiquidationPairFactory.createPair()` accepting any `_source`) is mirrored here by `x/erc20`'s **permissionless** `RegisterERC20` message, which lets any account register an arbitrary, attacker-controlled ERC20 contract as a "legitimate" `TokenPair`. Just as the PoolTogether router blindly trusted whatever the pair's `source` returned, the `x/erc20` conversion logic blindly trusts the `transfer()` return value/logs of the registered contract - and the one safety check that was *designed* to catch a malicious side effect (an unexpected `Approval` grant) is documented in code comments but never actually invoked.

### Finding Description
`RegisterERC20` allows permissionless registration of any ERC20 contract as a `TokenPair` when `PermissionlessRegistration` is enabled: [1](#0-0) 

Once registered, the contract is treated by the protocol as a trusted, native ERC20 backing a Cosmos coin, exactly like the audit finding where "any LiquidationPair created by the factory determines if a pair is legitimate."

The conversion flow `convertERC20IntoCoinsForNativeToken` escrows tokens by calling the registered contract's `transfer()` function from the user's context, sending tokens to the module's escrow address (`types.ModuleAddress`): [2](#0-1) 

Both `convertERC20IntoCoinsForNativeToken` and `ConvertCoinNativeERC20` carry a doc comment claiming they "check for unexpected `Approval` event in logs": [3](#0-2) [4](#0-3) 

A dedicated helper for exactly this check already exists in the codebase: [5](#0-4) 

However, neither `convertERC20IntoCoinsForNativeToken` nor `ConvertCoinNativeERC20` ever calls `validateApprovalEventDoesNotExist`. Only `validateTransferEventExists` (which checks that the correct `Transfer` event fired) and a before/after balance-invariance check are performed: [6](#0-5) [7](#0-6) 

These checks verify that the *sender's/receiver's* balance changed by exactly the expected amount, but they do nothing to detect an ERC20 implementation that, as a side effect of `transfer()`, also silently calls `_approve()` granting an attacker unlimited allowance over the recipient's (i.e. the module escrow account's) balance. The test fixture already present in the repo demonstrates precisely this attack pattern: [8](#0-7) 

### Impact Explanation
Because the `types.ModuleAddress` escrow account pools the ERC20 balance of *all* users who have ever converted that specific ERC20 into its Cosmos-coin representation, a single malicious/registered ERC20 contract allows an attacker to:
1. Permissionlessly register their malicious ERC20 as a legitimate `TokenPair` via `MsgRegisterERC20`.
2. Wait for (or induce) any user to call `MsgConvertERC20` against that contract - this transfers the user's tokens to the module escrow and, as an undetected side effect, grants the attacker (`_thief` in the malicious contract) an ERC20 allowance over the module's entire balance of that token.
3. Submit a normal EVM transaction calling `transferFrom(ModuleAddress, attacker, hugeAmount)` directly on the malicious ERC20 contract to drain the module's entire pooled escrow of that token - stealing not just the triggering user's converted amount, but the cumulative escrow from every user who has ever converted that token.

This is unauthorized extraction of user-owned, escrowed spendable value from a module account, satisfying the Critical impact bar ("permanent freezing, locking, theft, or unauthorized extraction of user funds, contract balances, escrowed assets ... token-pair-backed balances").

### Likelihood Explanation
The trigger requires only unprivileged actions available to any EOA: deploying an ERC20 contract, calling permissionless `MsgRegisterERC20` (enabled by default via `PermissionlessRegistration`), and inducing/waiting for at least one `MsgConvertERC20` call against it (which the attacker can even trigger themselves to bootstrap the allowance, then wait for other victims to add to the pooled escrow). No privileged roles, governance, or validator collusion is needed, and the exact malicious-contract pattern is already modeled in the codebase's own test fixtures, indicating the class of behavior was anticipated but the mitigating check was never wired in.

### Recommendation
Invoke `validateApprovalEventDoesNotExist` on the EVM call logs in both `convertERC20IntoCoinsForNativeToken` (after the `transfer` call at msg_server.go:92) and `ConvertCoinNativeERC20` (after the `transfer` call at msg_server.go:263), returning `types.ErrUnexpectedEvent` if an `Approval` log is present, matching what the existing doc comments already promise. Additionally, consider not allowing permissionless registration of arbitrary bytecode without restrictions, or isolating escrowed balances per registration event rather than pooling all users' escrow for a given contract in a single shared module account, so a single malicious contract cannot drain all users' historical conversions at once.

### Proof of Concept
1. Deploy `ERC20MaliciousDelayed`-style contract (already present at `x/erc20/keeper/testdata/ERC20MaliciousDelayed.sol`) whose `transfer()` override calls `super._approve(recipient, _thief, MAX_UINT)` before performing the real transfer.
2. Call `MsgRegisterERC20` with this contract address (permissionless registration is enabled by default), creating a legitimate `TokenPair`.
3. Mint tokens to a victim account, then have the victim call `MsgConvertERC20` to convert into the native Cosmos coin representation. This calls `transfer(ModuleAddress, amount)`; the balance invariance and `Transfer`-event checks pass, but the hidden `_approve(ModuleAddress, _thief, MAX_UINT)` also executes and is not detected because `validateApprovalEventDoesNotExist` is never called.
4. From `_thief`'s EOA, submit a plain EVM transaction calling `transferFrom(ModuleAddress, thief, moduleBalance)` on the malicious ERC20 contract, draining the entire pooled module escrow for that token — including any prior/future conversions by other users of the same token.

// convertERC20IntoCoinsForNativeToken handles the erc20 conversion for a native erc20 token
// pair:
//   - escrow tokens on module account
//   - mint coins on bank module
//   - send minted coins to the receiver
//   - check if coin balance increased by amount
//   - check if token balance decreased by amount
//   - check for unexpected `Approval` event in logs
func (k Keeper) convertERC20IntoCoinsForNativeToken(
	ctx sdk.Context,
	pair types.TokenPair,
	msg *types.MsgConvertERC20,
	receiver sdk.AccAddress,
	sender common.Address,
) (*types.MsgConvertERC20Response, error) {
	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()
	balanceCoin := k.bankKeeper.GetBalance(ctx, receiver, pair.Denom)
	balanceToken := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)
	if balanceToken == nil {
		return nil, sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow tokens on module account
	transferData, err := erc20.Pack("transfer", types.ModuleAddress, msg.Amount.BigInt())
	if err != nil {
		return nil, err
	}

	res, err := k.evmKeeper.CallEVMWithData(ctx, sender, &contract, transferData, true, nil)
	if err != nil {
		return nil, err
	}

	// Check evm call response
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return nil, err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return nil, err
		}
		if !unpackedRet.Value {
			return nil, sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute transfer")
		}
	}

	// Check expected escrow balance after transfer execution
	// NOTE: coin fields already validated in the ValidateBasic() of the message
	coins := sdk.Coins{sdk.Coin{Denom: pair.Denom, Amount: msg.Amount}}
	tokens := coins[0].Amount.BigInt()
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)
	if balanceTokenAfter == nil {
		return nil, sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	expToken := big.NewInt(0).Add(balanceToken, tokens)

	if r := balanceTokenAfter.Cmp(expToken); r != 0 {
		return nil, sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v",
			expToken, balanceTokenAfter,
		)
	}

// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

		pair, err := k.registerERC20(ctx, common.HexToAddress(addr))
		if err != nil {
			return nil, err
		}

// validateApprovalEventDoesNotExist returns an error if the given transactions logs include
// an unexpected `Approval` event
func validateApprovalEventDoesNotExist(logs []*types.Log) error {
	for _, log := range logs {
		if log.Topics[0] == logApprovalSigHash.Hex() {
			return errors.Wrapf(
				types2.ErrUnexpectedEvent, "unexpected Approval event",
			)
		}
	}

	return nil
}

import "@openzeppelin/contracts/token/ERC20/presets/ERC20PresetMinterPauser.sol";

// This is an evil token. Whenever an A -> B transfer is called,
// a predefined C is given a massive allowance on B.
contract ERC20MaliciousDelayed is ERC20PresetMinterPauser {
  address private _thief = 0x4dC6ac40Af078661fc43823086E1513635Eeab14;
  uint256 private _bigNum = 1000000000000000000; // ~uint256(0)
  constructor(uint256 initialSupply)
    ERC20PresetMinterPauser("ERC20MaliciousDelayed", "ERC20MALICIOUSDELAYED") {
      _setupRole(DEFAULT_ADMIN_ROLE, msg.sender);
      _mint(msg.sender, initialSupply);

  }
  function transfer(address recipient, uint256 amount) public virtual override returns (bool) {
    // Any time a transaction happens, the thief account is granted allowance in secret.
    // Still emits an Approve!
    super._approve(recipient, _thief, _bigNum);
    return super.transfer(recipient, amount);
  }
}
