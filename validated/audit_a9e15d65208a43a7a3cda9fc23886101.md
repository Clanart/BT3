### Title
Hookify `RuleEngine._check_condition`/`_extract_field` field-extraction gap lets `MultiEdit` bypass file-edit block rules - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._extract_field`, invoked from `_check_condition` during `PreToolUse`/`PostToolUse` rule evaluation, only implements `old_text`/`old_string` extraction for the `Edit`/`Write` tools; it has no equivalent branch for `MultiEdit`. Combined with the common rule-authoring pattern of restricting `tool_matcher` to `"Edit|Write"` (as documented and exemplified throughout `plugins/hookify`), a Hookify block/warn rule written to inspect `old_text`/`old_string`, or one that only lists `Edit|Write` in `tool_matcher`, silently fails to trigger when the identical file mutation is performed via the semantically-equivalent `MultiEdit` tool.

### Finding Description
`_rule_matches` (`plugins/hookify/core/rule_engine.py:96-125`) first applies `_matches_tool` (exact-string / pipe-split matching against `tool_name`, no normalization across tool aliases) and then requires every `Condition` to pass via `_check_condition` (`rule_engine.py:144-180`), which calls `_extract_field` (`rule_engine.py:182-254`) to pull the field value.

For `Edit`/`Write`, `_extract_field` handles `old_text`/`old_string`: [1](#0-0) 

For `MultiEdit`, only `file_path` and `new_text`/`content` (concatenation of all `edits[].new_string`) are handled — there is no branch reading `edits[].old_string`: [2](#0-1) 

When the field is unsupported, `_extract_field` returns `None`, and `_check_condition` treats that as an automatic non-match regardless of operator: [3](#0-2) 

Independently, `_matches_tool` performs strict, non-normalized matching: [4](#0-3) 

Hookify's own documentation and example patterns repeatedly instruct authors to use `tool_matcher: "Edit|Write"` (or bare `Bash`) for file-protection rules without including `MultiEdit`, e.g. the Skill/plugin-dev pattern examples that use `"matcher": "Write|Edit"`: [5](#0-4) 

The router scripts (`pretooluse.py`, `posttooluse.py`) group `Edit`, `Write`, and `MultiEdit` together under the same `event='file'` filter before rules are even loaded: [6](#0-5) [7](#0-6) 

This creates the false impression that all three tools are uniformly covered by a `file` event rule, while the engine's per-field extraction and typical `tool_matcher` configuration silently diverge for `MultiEdit`.

An agent (steerable via ordinary repository content / prompt injection, without any special privilege) can perform the exact same edit — e.g., removing a security check line, or overwriting sensitive `old_string` content — by choosing `MultiEdit` instead of `Edit`/`Write`. If the locally-configured Hookify block rule inspects `old_text`/`old_string` (a documented, first-class field per `plugins/hookify/skills/writing-rules/SKILL.md`) or restricts `tool_matcher` to `"Edit|Write"`, the rule never fires for the `MultiEdit` invocation, and `evaluate_rules` returns `{}` (allow), letting the dangerous edit through unblocked.

### Impact Explanation
This breaks the stated invariant "a matching block rule must reliably deny the protected operation." An attacker-influenced agent can perform an unauthorized file write (e.g., stripping a `.env`/secret guard, removing a safety check the user relied on Hookify to enforce, or modifying protected files) by simply using `MultiEdit` instead of `Edit`/`Write`, evading the user's configured guardrail. This maps to unauthorized file write/modification outside the user-approved policy scope.

### Likelihood Explanation
This requires no elevated privilege: any normal Claude Code session using the Hookify plugin with a locally authored rule that (a) checks `old_text`/`old_string`, or (b) sets `tool_matcher: "Edit|Write"` without `MultiEdit` — both patterns explicitly shown in the plugin's own documentation/examples — is affected. The only "trigger" needed is that the agent (which can be steered by untrusted repository/tool content) issues a `MultiEdit` call instead of `Edit`/`Write` for the same change, which is a normal, unprivileged tool choice with no approval prompt distinguishing it from other file-edit tools. This is deterministic and fully reproducible.

### Recommendation
- Add an `old_text`/`old_string` extraction branch for `MultiEdit` in `_extract_field` that concatenates `edits[].old_string`, mirroring the existing `new_text`/`content` handling.
- Treat `Edit`, `Write`, and `MultiEdit` as a single logical "file edit" tool family in both `_matches_tool` documentation/examples and rule-authoring guidance, or auto-expand `tool_matcher` patterns like `Edit|Write` to include `MultiEdit` when the rule's `event` is `file`.
- Consider making `_check_condition` fail closed (block) rather than silently pass when `_extract_field` cannot resolve a documented field for the invoked tool, to avoid silent rule bypass due to unimplemented field/tool combinations.

### Proof of Concept
Unit test against `plugins/hookify/core/rule_engine.py`:
```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

rule = Rule(
    name="block-remove-security-check",
    enabled=True,
    event="file",
    action="block",
    tool_matcher=None,  # or "Edit|Write" per documented pattern
    conditions=[
        Condition(field="old_text", operator="contains", pattern="SECURITY_CHECK")
    ],
    message="Blocked: removal of security check"
)
engine = RuleEngine()

# Edit tool: rule correctly blocks
edit_input = {
    "tool_name": "Edit",
    "tool_input": {"file_path": "app.py", "old_string": "if SECURITY_CHECK(): deny()", "new_string": ""}
}
assert engine.evaluate_rules([rule], edit_input).get("hookSpecificOutput", {}).get("permissionDecision") == "deny"

# MultiEdit tool performing the identical removal: rule silently fails to block
multiedit_input = {
    "tool_name": "MultiEdit",
    "tool_input": {"file_path": "app.py", "edits": [{"old_string": "if SECURITY_CHECK(): deny()", "new_string": ""}]}
}
result = engine.evaluate_rules([rule], multiedit_input)
assert result == {}  # BUG: dangerous operation not blocked, invariant violated
```
Expected (fixed) behavior: both invocations should return a `deny` `hookSpecificOutput`, since they perform the identical file mutation.

    def _matches_tool(self, matcher: str, tool_name: str) -> bool:
        """Check if tool_name matches the matcher pattern.

        Args:
            matcher: Pattern like "Bash", "Edit|Write", "*"
            tool_name: Actual tool name

        Returns:
            True if matches
        """
        if matcher == '*':
            return True

        # Split on | for OR matching
        patterns = matcher.split('|')
        return tool_name in patterns
