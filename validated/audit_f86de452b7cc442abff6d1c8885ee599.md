### Title
Webhook HMAC verification does not bind the signature to the shop domain, allowing cross-shop webhook replay/redirection - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` only validates the HMAC over the raw POST body [1](#0-0)  using `PayloadVerification#hmac_valid?`, which computes the HMAC solely from `request.raw_post` [2](#0-1) . The `shop_domain` value that downstream handlers use to decide *which shop's record* to act on is read straight from the `X-Shopify-Shop-Domain` header, which is not covered by the signature at all [3](#0-2) . This is directly analogous to the Balancer report: the verification step only "accounts for" one final signed artifact (the body/HMAC), while a second piece of data that materially affects account state (the shop-identifying header) travels alongside unauthenticated and unaccounted for.

### Finding Description
`WebhooksController#receive` builds a `ShopifyAPI::Webhooks::Request` from `request.raw_post` and `request.headers` and hands it to the registry for processing [4](#0-3) . The only authentication gate is `verify_request`, which checks `hmac_valid?(request.raw_post)` — a pure function of the body and the app's shared secret [2](#0-1) . The shop the webhook is attributed to (`shop_domain`) is taken from the `HTTP_X_SHOPIFY_SHOP_DOMAIN` header [3](#0-2) , a value that is never mixed into the HMAC computation.

Because the app's client secret (`ShopifyApp.configuration.secret`) is the same for every shop that installs the app, a valid `(body, HMAC)` pair generated by Shopify for one merchant's real webhook remains a valid pair regardless of which shop domain header accompanies it. Generated job templates such as `AppUninstalledJob`, `ShopRedactJob`, and `CustomersRedactJob` look up the shop purely by this unauthenticated header value and then perform destructive, account-scoped actions (`shop.destroy`, redaction, etc.) [5](#0-4) [6](#0-5) .

An attacker who is a merchant installing the app on their own shop receives genuine Shopify webhooks (with a genuine HMAC computed by Shopify using the app's shared secret) for their own shop. They can capture the raw body + HMAC of any such webhook and replay it to the app's webhook endpoint while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header. `hmac_valid?` still passes because it only checks the (unchanged) body against the shared secret; the request is accepted, and the job handler mis-attributes the payload to the victim's shop record.

### Impact Explanation
This is a cross-shop/account-confusion vulnerability: a request that is cryptographically valid for one merchant can be redirected onto another merchant's stored account by changing an unauthenticated header. Depending on which webhook topic is replayed, this can lead to unauthorized destruction of a victim shop's persisted record (`app/uninstalled`), forced GDPR redaction actions against a victim (`shop/redact`, `customers/redact`), or otherwise-legitimate-looking webhook bodies being processed under the wrong shop's session/context — all triggered by an unrelated, low-privileged merchant.

### Likelihood Explanation
Any merchant who installs the app is capable of receiving legitimate webhooks for their own shop and capturing the raw body/HMAC header pair (e.g., via a debug proxy or by intercepting their own app's webhook endpoint traffic before it's rejected/logged). No secret material needs to be recovered — only the header needs to be swapped, since the header is not part of the signed content. The barrier to reproducing this is low for anyone who is (or becomes) a legitimate merchant of the target app.

### Recommendation
Bind the shop domain into the authenticated portion of the request before trusting it for record lookups: either include the `X-Shopify-Shop-Domain` header in the HMAC computation, or ignore the header entirely and rely only on the shop domain embedded in the (already-verified) webhook body/payload as `ShopifyAPI::Webhooks::Request#shop` does, cross-checking it against any header-derived value before use. Reject the request if the two disagree.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a real webhook (e.g. `app/uninstalled`) and capture `raw_post` body `B` and the `X-Shopify-Hmac-Sha256` header `H` that Shopify sent — both valid under the app's shared secret.
3. Replay a POST to the app's webhooks endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H`, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `WebhookVerification#verify_request` -> `hmac_valid?(B)` succeeds (body unchanged) [1](#0-0) ; the queued job (e.g. `AppUninstalledJob`) looks up `Shop.find_by(shopify_domain: "victim.myshopify.com")` and destroys the victim's shop record [7](#0-6) .

```ruby
    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
