### Title
Attacker-controlled `remote:` push output lets a malicious git remote inject an arbitrary bypass URL into the Secret-Scanning Push-Protection dialog - ([File: app/src/ui/dispatcher/error-handlers.ts])

### Summary
When a `git push` is rejected with `DugiteError.PushWithSecretDetected`, Desktop parses the raw `remote: ` lines coming back from the remote server with a regex and turns them directly into UI data — including a `bypassURL` that later becomes a clickable external link in the `PushProtectionErrorDialog`. Nothing in this pipeline verifies that the text actually originated from github.com/GHE, or that `bypassURL` points to a GitHub-owned domain. Any git server the user has configured as a remote (self-hosted, forwarded through a proxy, or a malicious/compromised host) can emit stderr that mimics GitHub's secret-scanning rejection format and fully control where the "Bypass" link takes the user.

### Finding Description
`secretScanningPushProtectionErrorHandler` only checks the Dugite error code, not the source/authenticity of the message: [1](#0-0) 

The stderr is reduced to raw `remote: `-prefixed lines with no origin/signature validation: [2](#0-1) 

That untrusted text is then regex-parsed to build `ISecretScanResult` objects, including a `bypassURL` captured as any string that merely starts with `https` and a `requiresApproval` flag derived from the presence of the substring `"request an exemption"` — both entirely attacker-controlled: [3](#0-2) 

The resulting model is rendered directly in the dialog, and when `requiresApproval` is true, the "Bypass" button is a plain external link that opens whatever URL the attacker placed into the message, with `onDelegatedBypassLinkClick` only incrementing a telemetry counter — no host allowlist check: [4](#0-3) [5](#0-4) 

The push itself goes through the normal `git push` flow without any host verification tied to this feature: [6](#0-5) 

There is no code anywhere in this chain that confirms the `X-GitHub-Request-Id` header, the endpoint identity (`isDotCom`/`isGHE`/`isGitHubHost`), or that the stderr text came from an authenticated GitHub connection before it is trusted and surfaced to the user as an actionable, GitHub-branded security dialog.

### Impact Explanation
An attacker who controls (or can MITM/proxy) a git remote the victim pushes to can craft a fake "push rejected due to secret scanning" response. Desktop will render a dialog styled exactly like GitHub's real push-protection UI, with a "Bypass" button whose destination URL is fully attacker-chosen. Because users are trained by this exact feature to click "Bypass" links to resolve a legitimate GitHub push-protection block, this is a strong vector for credential/OAuth phishing (tricking the user into entering their GitHub credentials or authorizing an OAuth app on a look-alike page) — matching the "unauthorized OAuth" / "credential exfiltration via attacker-controlled link the user clicks" impact category.

### Likelihood Explanation
Any repository configuration where the remote is not github.com/GHE — a corporate proxy, a compromised third-party host, a repo the user cloned that already points `origin` somewhere attacker-controlled — is enough to trigger this. It requires only a normal `git push` attempt by an unprivileged user; no admin rights, no local access, and no prior malware are needed, satisfying the report's "attacker controls a git remote/proxy response" criterion.

### Recommendation
Before parsing/rendering secret-scanning bypass data, verify that the push actually went to a known GitHub endpoint (`isDotCom`/`isGHE`/`isGitHubHost`) and validate that `bypassURL` resolves to that same trusted GitHub host (e.g., matching `getHTMLURL(endpoint)` origin) before treating it as a clickable link. Reject/ignore the parsed secret-scanning payload if the remote isn't a verified GitHub endpoint or if the bypass URL's origin doesn't match.

### Proof of Concept
1. Configure a repository's remote to point at an attacker-controlled HTTPS git server (or intercept the connection with a proxy).
2. On `git push`, have the malicious server return a non-zero exit and stderr containing lines formatted like:
   ```
   remote: —— Fake Secret ——————————————————
   remote:   locations:
   remote:     - commit: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
   remote:       path: some/file:1
   remote: (request an exemption) https://attacker.example.com/phish 
   ```
3. Dugite maps this to `DugiteError.PushWithSecretDetected` (mirroring GitHub's real format), Desktop's `secretScanningPushProtectionErrorHandler` fires, `extractSecretScanningResults` parses out `bypassURL = "https://attacker.example.com/phish"` and `requiresApproval = true`.
4. The `PushProtectionErrorDialog` shows a "Bypass" link; clicking it opens the attacker's phishing page, styled as a continuation of the trusted GitHub secret-scanning workflow.

Note: I was not able to execute the app to confirm the exact `LinkButton`/`uri` click-handling implementation (e.g., whether it calls `shell.openExternal` unconditionally) since I only have read access to the indexed codebase; this should be verified in a full session before treating the phishing chain as end-to-end confirmed, though the missing origin validation in `error-handlers.ts` and `push-protection-error-dialog.tsx` themselves are directly confirmed in the code shown above.

/**
 * Extracts secret scanning results from the provided `remoteMessage` string
 * from the git error provided when GitHub Secret Scanning detects a secret on
 * push..
 *
 * This function parses the output of a secret scanning tool to identify
 * secrets, their descriptions, locations in the codebase, and bypass URLs.
 */
function extractSecretScanningResults(
  remoteMessage: string
): ReadonlyArray<ISecretScanResult> {
  const secretsRegex =
    /—— (?<description>.*?) —+[\s\S]*?locations:(?<locationsGroup>(?:\s+- commit: [a-f0-9]{40}\s+path: [\s\S]*?)+).*?(?<bypassURL>https[\s\S]*?) /g

  const matches = [...remoteMessage.matchAll(secretsRegex)]

  const secrets: Array<ISecretScanResult> = []
  if (matches.length === 0) {
    return secrets
  }

  for (const match of matches) {
    if (match.groups === undefined || match.index === undefined) {
      continue
    }

    const { bypassURL, description, locationsGroup } = match.groups

    const locationsRegex =
      /- commit: (?<commitSha>[a-f0-9]{40})\s+path: (?<path>.*?):(?<lineNumber>\d+)/g
    const locationMatches = [...locationsGroup.matchAll(locationsRegex)]

    const locations: ISecretLocation[] = []

    locationMatches.forEach(locationMatch => {
      if (locationMatch.groups === undefined) {
        return
      }
      const { commitSha, path, lineNumber } = locationMatch.groups
      locations.push({
        commitSha,
        path,
        lineNumber: parseInt(lineNumber, 10),
      })
    })

    secrets.push({
      id: bypassURL.split('/').pop() || '',
      description,
      bypassURL,
      locations,
      requiresApproval: !!match.at(0)?.includes('request an exemption'),
    })
  }

  return secrets
}

export async function secretScanningPushProtectionErrorHandler(
  error: Error,
  dispatcher: Dispatcher
) {
  const e = asErrorWithMetadata(error)
  if (!e) {
    return error
  }

  const gitError = asGitError(e.underlyingError)
  if (gitError?.result.gitError !== DugiteError.PushWithSecretDetected) {
    return error
  }

  const remoteMessage = getRemoteMessage(coerceToString(gitError.result.stderr))
  const secrets = extractSecretScanningResults(remoteMessage)

  dispatcher.incrementMetric('pushBlockedBySecretScanningCount')
  dispatcher.incrementMetric('secretsDetectedOnPushCount', secrets.length)

  dispatcher.showPopup({
    type: PopupType.PushProtectionError,
    secrets,
  })

  return null
}

/**
 * Extract lines from Git's stderr output starting with the
 * prefix `remote: `. Useful to extract server-specific
 * error messages from network operations (fetch, push, pull,
 * etc).
 */
function getRemoteMessage(stderr: string) {
  const needle = 'remote: '

  return stderr
    .split(/\r?\n/)
    .filter(x => x.startsWith(needle))
    .map(x => x.substring(needle.length))
    .join('\n')
}

export async function push(
  repository: Repository,
  remote: IRemote,
  localBranch: string,
  remoteBranch: string | null,
  tagsToPush: ReadonlyArray<string> | null,
  options?: PushOptions,
  progressCallback?: (progress: IPushProgress) => void
): Promise<void> {
  const args = [
    'push',
    remote.name,
    remoteBranch ? `${localBranch}:${remoteBranch}` : localBranch,
  ]

  if (tagsToPush !== null) {
    args.push(...tagsToPush)
  }
  if (!remoteBranch) {
    args.push('--set-upstream')
  } else if (options?.forceWithLease) {
    args.push('--force-with-lease')
  }

  if (options?.noVerify) {
    args.push('--no-verify')
  }

  let opts: IGitStringExecutionOptions = {
    env: await envForRemoteOperation(remote.url),
    interceptHooks: ['pre-push'],
    onHookProgress: options?.onHookProgress,
    onHookFailure: options?.onHookFailure,
    onTerminalOutputAvailable: options?.onTerminalOutputAvailable,
  }

  if (progressCallback) {
    args.push('--progress')
    const title = `Pushing to ${remote.name}`
    const kind = 'push'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new PushProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({
          kind,
          title,
          description,
          value,
          remote: remote.name,
          branch: localBranch,
        })
      }
    )

    // Initial progress
    progressCallback({
      kind: 'push',
      title,
      value: 0,
      remote: remote.name,
      branch: localBranch,
    })
  }

  await git(args, repository.path, 'push', opts)
