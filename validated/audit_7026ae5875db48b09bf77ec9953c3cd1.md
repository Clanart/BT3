## Analysis

The report's core "broken invariant" is: an unprivileged/attacker-influenced input is processed under an unchecked structural assumption, and violating that assumption lets attacker-controlled bytes end up permanently and silently baked into a trust-critical output (the Wallet's balances). The closest structural analog in this GitHub Desktop codebase is the Copilot merge-conflict resolution pipeline, where the assumption "the first line matching `>{7}` after an `ours` marker is *the* real conflict terminator" is violated identically by two independent parsers, letting unreviewed, attacker-controlled branch content get spliced verbatim into the file that Desktop writes and the user commits.

### Title
Crafted incoming-branch content bypasses Copilot conflict-marker parsing, silently splicing unreviewed attacker content into the committed file - (File: app/src/lib/copilot-conflict-resolution.ts)

### Summary
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts`) and `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts`) both detect a conflict block's closing marker with the same naive regex, `/^>{7}(?:\s|$)/`, matching the *first* line beginning with seven `>` characters after an `ours` marker [1](#0-0) . If the "theirs" side of a real conflict (content the attacker controls, e.g. a merged PR/fork branch) contains a line that itself starts with `>{7}`, both parsers treat it as the true closing marker and stop reading there, even though the *actual* `>>>>>>> branch` marker appears later in the file.

### Finding Description
`extractConflictHunks` walks the file collecting `theirsLines` until it hits any line matching `theirsMarker`, then breaks [2](#0-1) . `reassembleResolvedFile` performs the identical lookahead independently against the raw on-disk content when deciding where a hunk ends and splicing in the model's resolution [3](#0-2) .

Because both scanners stop at the *first* `>{7}`-prefixed line, an attacker who controls the "theirs" branch (the branch or PR being merged in) can plant a decoy closing marker inside their own conflicting content, e.g.:

```
<<<<<<< HEAD
ours line
=======
theirs line 1
>>>>>>> decoy
theirs line 2
>>>>>>> feature
```

- `extractConflictHunks` builds `theirsContent = "theirs line 1"` and never surfaces `"theirs line 2"` or the trailing `>>>>>>> feature` line to the model at all — so the model's resolution is generated with incomplete/wrong information about the conflict, and `validateResolutionPaths` only checks hunk *counts* match (which they will, since both parsers are fooled identically) [4](#0-3) .
- `reassembleResolvedFile` splices the model's (already-incomplete) resolution in place of the truncated block, then falls through to its `else` branch for the remaining lines, appending `"theirs line 2"` and the literal `>>>>>>> feature` marker line verbatim into the reassembled file as ordinary content [5](#0-4) .

No downstream check (`parseCopilotConflictResolution`'s marker check only inspects the model's own `resolvedContent` string for markers, not the fully reassembled file) verifies that the final reassembled output is free of leftover conflict-marker syntax or unreviewed attacker content [6](#0-5) .

### Impact Explanation
The `IFileResolution.resolvedContent` produced here is written directly to disk and staged/committed as the user's merge resolution. This lets an attacker who controls the incoming ("theirs") side of a merge — a malicious PR/fork branch — smuggle content past Copilot's review entirely: the model never sees it, and the reassembly step writes it back into the file unresolved, without markers, as if it were normal, already-agreed-upon code. This is a silent corruption of what the user commits/pushes: the user believes Copilot fully resolved and reviewed the conflict, but part of the file was never inspected and is written verbatim from the attacker-controlled branch, potentially including malicious logic, backdoored code, or broken content disguised as ordinary lines.

### Likelihood Explanation
Exploitation only requires an attacker to author a branch/PR whose changes conflict with the victim's branch and includes an innocuous-looking line of seven-or-more `>` characters (e.g., in a comment, ASCII divider, quoted diff/patch text, or changelog snippet) inside their changed region — no unusual or unnatural user action is required beyond the normal act of using Desktop's "Resolve with Copilot" feature on a routine merge. This is plausible in real-world content (diffs quoted in docs, changelog fragments, ASCII banners).

### Recommendation
Make both parsers require the closing marker to be an *exact* boundary rather than the first matching prefix, e.g. by validating that a candidate `>>>>>>>` line's trailing label matches the expected branch/label used to open the hunk, or by only accepting a closing marker whose surrounding structure hasn't been altered relative to what `extractConflictHunks` and `reassembleResolvedFile` each independently determine (cross-validate hunk boundaries, not just counts). Additionally, after reassembly, scan the final resolved content for any remaining lines matching `^<{7}`, `^={7}`, or `^>{7}` and fail/flag the file for manual resolution instead of silently emitting them.

### Proof of Concept
1. Create branch `feature` that modifies a file so it conflicts with `main`, where the attacker's changed hunk includes:
   ```
   theirs line 1
   >>>>>>> decoy
   theirs line 2
   ```
2. Victim merges `feature` into `main` in Desktop, hits a conflict, and invokes "Resolve with Copilot."
3. `extractConflictHunks` sends only `"theirs line 1"` to the model as the conflict's "theirs" content — `"theirs line 2"` and the real `>>>>>>> feature` marker are invisible to the model.
4. `reassembleResolvedFile` splices the model's resolution in place of the truncated block, then copies `"theirs line 2"` and the literal `>>>>>>> feature` line into the final file untouched.
5. The committed file contains unreviewed attacker content plus a stray literal `>>>>>>> feature` marker line, with no warning to the user that part of the conflict was never actually resolved.

Note: I was not able to execute the Copilot resolution pipeline end-to-end (no test harness access in this read-only session) — the trace above is derived purely from static analysis of the two parsing functions and their shared regex; a Devin session with repo access could add a unit test exercising `reassembleResolvedFile`/`extractConflictHunks` together to confirm the exact spliced output.
