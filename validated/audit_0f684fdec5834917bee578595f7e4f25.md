### Title
Unchecked `IERC20.transfer` reward payout in `ArbWomUp.incentiveDeposit` permanently burns user's claimed-reward accounting on a non-standard token - ([File: wombat/ArbWomUp.sol])

### Summary
`ArbWomUp.sol` (and its near-identical sibling `ArbWomUp2.sol`) pay out incentive rewards to depositors using a raw `IERC20.transfer()` call whose boolean return value is never checked. Because `claimedReward[msg.sender]` is incremented *before* this unchecked transfer, a non-compliant ERC20 reward token that returns `false` on failure (instead of reverting) will leave the user's on-chain reward accounting permanently marked as "claimed" even though no tokens were ever received.

### Finding Description
In `_deposit`/`incentiveDeposit`, WOM deposits correctly use `safeTransferFrom` via `SafeERC20`, but the actual reward payout does not: [1](#0-0) 

```
function incentiveDeposit(uint256 _amount) external _checkAmount(_amount) whenNotPaused nonReentrant {
    uint256 rewardToSend = this.getRewardAmount(_amount, msg.sender);
    _deposit(_amount);
    claimedReward[msg.sender] += rewardToSend;

    IERC20(usdt).transfer(msg.sender, rewardToSend);
    emit USDTRewarded(msg.sender, rewardToSend);
}
```

The `claimedReward` mapping is updated *before* the transfer, and the transfer's return value is discarded, so:
1. If `usdt` (a configurable, owner-settable token address, not necessarily true USDT) is an ERC20 implementation that returns `false` instead of reverting on failure (e.g., due to a paused/blacklist state, insufficient contract balance edge case in some ERC20 forks, or any other weird-ERC20 behavior), execution continues normally.
2. `claimedReward[msg.sender]` has already been incremented by `rewardToSend`, so `getRewardAmount` — which subtracts `claimedReward[_account]` from the tier-based entitlement — will never again include this amount in a future reward calculation.
3. The user permanently loses the reward they were entitled to, with no path to reclaim it, since the accounting state (not the token balance) determines future eligibility.

The identical pattern exists in `ArbWomUp2.sol`: [2](#0-1) 

This is the same root-cause bug class as the reported issue (unchecked ERC20 return values from weird-ERC20-implementations causing silent failure while the contract's internal state assumes success), except manifesting on the payout side (`transfer`) rather than the deposit side (`transferFrom`). Everywhere else in the audited contracts (`MasterMagpie.sol`, `vlMGPBaseRewarder.sol`, `mWOM.sol`, `SmartWomConvert.sol`, `ArbWomUp3.sol`'s user-facing deposit path) consistently use `SafeERC20`'s `safeTransfer`/`safeTransferFrom`, confirming this is an inconsistency specific to the `ArbWomUp`/`ArbWomUp2` reward-payout leg.

### Impact Explanation
This causes permanent, unrecoverable loss of a user's earned/unclaimed incentive reward: the accounting (`claimedReward`) is updated as if the payout succeeded, so the user can never claim that portion of reward again even though they never received the tokens. This meets the "theft or permanent freezing of unclaimed yield" bar, triggered purely by an ordinary user calling `incentiveDeposit()` — no privileged role is required.

### Likelihood Explanation
Likelihood depends on the reward token (`usdt`/`busd`) actually deviating from strict ERC20 semantics (returning `false` rather than reverting on failure), which the owner can freely set via `__arbWomUp_init`/`setup`. Given these are airdrop/incentive contracts intended to hold and disburse third-party stablecoin-like tokens, and many real-world tokens (including USDT itself on some chains, and various BSC/Arbitrum BEP-20/ERC-20 forks) exhibit non-standard return-value or fee/blacklist behavior, this is a realistic risk rather than a purely theoretical one.

### Recommendation
Replace the raw `IERC20(usdt).transfer(...)` / `IERC20(busd).transfer(...)` calls in `ArbWomUp.sol` and `ArbWomUp2.sol` with `safeTransfer` from OpenZeppelin's `SafeERC20` (already imported and used elsewhere in the same files), and update `claimedReward` only after confirming the transfer succeeded (or perform the increment atomically with a call that reverts on failure).

### Proof of Concept
1. Owner deploys `ArbWomUp` and sets `usdt` to a token whose `transfer()` returns `false` on failure instead of reverting (e.g., contract paused, or transfer amount exceeds contract's dynamic transfer cap in some token implementations).
2. Contract's `usdt` balance is temporarily insufficient or the token enters a state where `transfer` returns `false` for this specific call.
3. User calls `incentiveDeposit(amount)`; `_deposit` succeeds (WOM pulled via `safeTransferFrom`), `claimedReward[msg.sender] += rewardToSend` executes, then `IERC20(usdt).transfer(msg.sender, rewardToSend)` returns `false` silently — the user receives 0 USDT.
4. `claimedReward[msg.sender]` is now permanently inflated by `rewardToSend`; all future `getRewardAmount` calls subtract this phantom claimed amount, permanently freezing that portion of the user's earned incentive.
