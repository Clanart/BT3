### Title
Unregistered blame recipient causes panic during encrypted-share adjudication - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`AdditionalBlameMachine::blame` accepts an arbitrary nonzero `Participant` as the alleged recipient without checking that it belongs to the DKG’s `1..=n` participant set. [1](#0-0) [2](#0-1) 

After the encrypted message’s Schnorr proof of possession verifies, `Decryption::decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` while preparing the DLEq verification statement. [3](#0-2) 

Because `HashMap` indexing panics for an absent key, a blame message naming recipient `n + 1` crashes the adjudication path instead of returning an error. [4](#0-3) [5](#0-4) 

### Finding Description
`AdditionalBlameMachine::new` populates `Decryption::enc_keys` only for participant identifiers `1..=n`. [6](#0-5) 

However, `Participant::new` validates only that the identifier is nonzero and permits values greater than `n`. [1](#0-0) 

Neither `AdditionalBlameMachine::blame` nor `BlameMachine::blame_internal` validates `recipient` against the constructed participant set before forwarding it to `decrypt_with_proof`. [7](#0-6) [2](#0-1) 

The PoP challenge binds the context, nonce, encryption public key, sender and ciphertext, but not the alleged recipient. [8](#0-7) 

Consequently, an encrypted share legitimately produced by `sender` passes the signature check even when the submitted `recipient` is out of range. [9](#0-8) 

If the supplied `proof` is `Some`, execution reaches `self.enc_keys[&decryptor]` before DLEq verification can reject the proof, and the missing-map-key indexing operation panics. [5](#0-4) 

### Impact Explanation
An unauthenticated or unprivileged participant who can submit a blame accusation with serialized `EncryptedMessage` and `EncryptionKeyProof` bytes can force a panic in the PedPoP blame-resolution path. [10](#0-9) [2](#0-1) 

The attacker does not need a valid decryption proof or knowledge of the victim’s secret because the panic occurs while constructing the DLEq statement, before `DLEqProof::verify` is called. [5](#0-4) 

If this code runs in an arbitrator, processor, validator or other host that does not isolate and recover from Rust panics, the host crashes or aborts the key-generation/blame workflow, producing a concrete availability failure. [11](#0-10) 

### Likelihood Explanation
The trigger requires only a syntactically valid encrypted share whose PoP verifies for `sender`, plus any parseable `EncryptionKeyProof` wrapped in `Some`, and an out-of-range but nonzero `recipient`. [12](#0-11) [13](#0-12) 

A valid encrypted share can be copied from ordinary DKG traffic because the PoP does not bind the recipient, or freshly generated by a participant able to run the normal encryption flow. [14](#0-13) [8](#0-7) 

The invalid recipient is trivially constructible as `Participant::new(n + 1)`, since only zero is rejected. [1](#0-0) 

### Recommendation
Validate both `sender` and `recipient` against the DKG participant set at the start of `BlameMachine::blame`, `AdditionalBlameMachine::blame`, or `blame_internal`, and return an explicit error for identifiers outside `1..=n`. [7](#0-6) [15](#0-14) 

Replace indexing expressions such as `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `get` followed by a typed error, so malformed accusations cannot convert missing state into a panic. [5](#0-4) [16](#0-15) 

Because `blame` currently returns only the accused participant, exposing this validation to callers requires adding an error result or otherwise defining an explicit invalid-accusation outcome. [10](#0-9) [2](#0-1) 

### Proof of Concept
1. Initialize an `AdditionalBlameMachine<C>` for `n` participants using valid commitment messages, causing `Decryption::enc_keys` to contain only `Participant(1)..=Participant(n)`. [6](#0-5) 
2. Obtain any valid `EncryptedMessage<C, SecretShare<C::F>>` produced by a legitimate `sender`, including its valid Schnorr PoP. [14](#0-13) 
3. Supply any syntactically valid `EncryptionKeyProof<C>` as `proof`; its mathematical validity is irrelevant because the panic occurs before DLEq verification. [13](#0-12) [5](#0-4) 
4. Invoke `blame(sender, Participant::new(n + 1).unwrap(), msg, Some(proof))`. [2](#0-1) 
5. The copied or generated message passes `msg.pop.verify`, after which `self.enc_keys[&decryptor]` indexes a nonexistent participant and panics. [3](#0-2)

  let key = Zeroizing::new(C::random_nonzero_F(rng));

      nonce,
      pop_challenge::<C>(context, pub_nonce, pub_key, from, msg.deref().as_ref()),

  }

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
