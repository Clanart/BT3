### Title
Repeated fork conversion silently discards the true origin URL, permanently corrupting the `upstream` remote - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`AppStore._convertRepositoryToFork` re-points the repository's `origin` remote to a caller-supplied fork URL and, in the same call, saves whatever `origin` *currently* points to into the `upstream` remote so the user doesn't lose track of the real original repository. Because the function reads the "previous" URL from live git state (`gitStore.defaultRemote?.url`) instead of from a persisted, checked record of the *original* repository, a second invocation of the same flow (or a second "fork" operation, or a stale/duplicated dispatch) captures the already-rewritten `origin` URL — not the genuine original — and overwrites `upstream` with it. This is structurally the same flaw as the referenced Yield `Witch.grab()` bug: an "original owner" value is only ever taken from mutable current state and gets clobbered on a repeat operation, with nothing to detect that the value has already been captured once.

- `remoteUrl` is read from `gitStore.defaultRemote.url`, i.e. whatever `origin` currently is — not a stored/verified "true original repository" value.
- `gitStore.setRemoteURL(...)` rewrites `origin` to `fork.clone_url`, an attacker-influenceable value coming from a GitHub API/proxy response (`api.forkRepository`, see `app/src/ui/forks/create-fork-dialog.tsx` lines 46-60): [2](#0-1) 
- Immediately after, `gitStore.ensureUpstreamRemoteURL(remoteUrl)` is called, which either creates `upstream` or, if it already exists, overwrites it via `setRemoteURL(this.repository, UpstreamRemoteName, remoteUrl)`: [3](#0-2) 

**First "grab"**: `origin = trueOriginURL` → sets `origin = fork1.clone_url`, sets `upstream = trueOriginURL` (correct, mirrors `Witch.grab` storing the original owner).

**Second "grab"**: if the same flow runs again (e.g. the user runs "Fork this repository" a second time, a retried/duplicated dispatch of `convertRepositoryToFork`, or the flow being invoked again after `origin` was already switched), `gitStore.defaultRemote.url` is now `fork1.clone_url` — the already-rewritten value, not the real original. `ensureUpstreamRemoteURL` then overwrites `upstream` with `fork1.clone_url`, permanently discarding `trueOriginURL`. There is no persisted record anywhere in `Repository`/`GitHubRepository`/`git-store.ts` of the pristine original remote to fall back on — exactly the missing "vaultOwners" record in the Yield bug.

Nothing in `GitStore.ensureUpstreamRemoteURL` (`app/src/lib/stores/git-store.ts:1364`) or `_convertRepositoryToFork` checks whether `upstream` has already been set by a previous conversion before overwriting it — the same missing-idempotency-guard pattern called out in the original report ("check if the witch is already the owner... and keep the previous owner if that is the case").

### Impact Explanation
Once `upstream` is corrupted, Desktop's UI features that rely on it (`updateExistingUpstreamRemote`, the "upstream already exists" reconciliation dialog, "Update from upstream default branch" used by `create-branch-dialog.tsx`, `_findPullRequestBranch`, etc.) silently operate against the wrong remote. Any subsequent "fetch upstream"/"merge upstream" or manual `git fetch upstream` the user performs pulls history from the intermediate (or attacker-controlled) repository instead of the genuine original, and this can flow directly into local branches and future commits/pushes — matching the "silent corruption of what the user commits or pushes" impact criterion. Because `origin` itself was already switched in the first call, and now the one remaining trace of the real repository (`upstream`) is gone too, the user has no in-app way to recover the original remote URL.

### Likelihood Explanation
This requires the fork-conversion flow (`_convertRepositoryToFork`) to execute a second time for the same repository while `origin` is already pointing away from the true original — plausible via UI retry, a queued/duplicate dispatcher call, or the user legitimately re-running "Create Fork"/reconciliation flows over time. The `fork.clone_url` and any GitHub API-served `clone_url`/`parent.cloneURL` values are exactly the class of attacker-influenceable input called out as in-scope ("attacker controls... a GitHub API object... or a git remote/proxy response" e.g. a malicious/compromised GHES endpoint or MITM proxy). No local access, admin rights, or leaked credentials are needed — only a crafted/duplicated API response and a naturally repeatable user action.

### Recommendation
Do not derive the value written into `upstream` from the live, mutable `origin` remote. Instead:
- Persist the original repository's clone URL once (e.g., alongside `GitHubRepository`/`Repository` metadata) at the time of the *first* conversion, and refuse to overwrite it on subsequent conversions unless explicitly requested by the user.
- In `ensureUpstreamRemoteURL`/`_convertRepositoryToFork`, check whether `upstream` already exists and was already set by a prior Desktop-driven conversion before blindly overwriting it (mirroring the Yield team's fix of checking whether the "owner" is already recorded before overwriting).
- Validate/pin `fork.clone_url` and `parent.cloneURL` against the expected host/owner before using them to mutate git remotes.

### Proof of Concept
1. Clone `origin = https://good.example/real/repo.git` (a GitHub Desktop `RepositoryWithGitHubRepository`).
2. Trigger "Create Fork" (`CreateForkDialog.onSubmit` → `dispatcher.convertRepositoryToFork`); a compromised/MITM API or proxy response for `api.forkRepository` returns `clone_url = https://good.example/fork1/repo.git`.
   - `app-store.ts:_convertRepositoryToFork` sets `origin → fork1`, `upstream → real/repo.git` (correct so far).
3. Re-trigger the same flow a second time (retry after a transient error, duplicate click race, or a second legitimate "fork" attempt) with a new/attacker-served `clone_url = https://evil.example/fork2/repo.git`.
   - `remoteUrl = gitStore.defaultRemote.url` is now `https://good.example/fork1/repo.git` (already-corrupted state, not the real original).
   - `setRemoteURL(origin, evil.example/fork2/repo.git)` and `ensureUpstreamRemoteURL(good.example/fork1/repo.git)` run, so `upstream` is now `fork1`, and the real `real/repo.git` URL is permanently lost from both remotes.
4. From this point, any "fetch upstream" / "update from upstream default branch" in Desktop pulls from `fork1` (or an attacker-controlled repo, depending on which step was compromised) with no path in the UI to recover the true original repository URL.

Note: I could not fully verify from the indexed code whether the UI currently allows two concurrent/duplicate invocations of `_convertRepositoryToFork` for the same repository (e.g., via double-submit protection in `CreateForkDialog`), since `create-fork-dialog.tsx` does disable the button while `loading` is true. The strongest, unambiguous reproduction path is therefore the "run the fork-conversion flow twice over time" scenario rather than a same-session double-click race; a Devin session with full repo/file access would be needed to confirm whether any additional call sites or retry logic can invoke `_convertRepositoryToFork`/`ensureUpstreamRemoteURL` more than once in immediate succession.

  public async ensureUpstreamRemoteURL(remoteUrl: string): Promise<void> {
    await this.performFailableOperation(async () => {
      try {
        await addRemote(this.repository, UpstreamRemoteName, remoteUrl)
      } catch (e) {
        if (
          e instanceof DugiteError &&
          e.result.gitError === GitError.RemoteAlreadyExists
        ) {
          // update upstream remote if it already exists
          await setRemoteURL(this.repository, UpstreamRemoteName, remoteUrl)
        } else {
          throw e
        }
      }
    })
  }
