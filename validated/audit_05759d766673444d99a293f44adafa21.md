Based on my investigation, I found a concrete analog: `_findPullRequestBranch` in `app/src/lib/stores/app-store.ts` uses `headCloneUrl` and `headRefName` — both fully attacker-controlled fields from a GitHub API pull-request object (an attacker opens a PR from their own fork against any public repo the victim has cloned) — to add a git remote and construct a ref, and neither value is checked for being empty/malformed before use, unlike the `url`/`branch` fields that flow through `parse-app-url.ts`, which does validate with `testForInvalidChars`.

### Title
Missing validation of PR `head.ref`/`head.repo.clone_url` from GitHub API before use in remote/ref operations - (File: app/src/lib/stores/app-store.ts)

### Summary
`_checkoutPullRequest` / `_findPullRequestBranch` [1](#0-0)  take `headRepoOwner`, `headCloneUrl`, and `headRefName` directly from the pull request object returned by the GitHub API and use them, unvalidated, to call `addRemote` and to build `remoteRef = \`${remote.name}/${headRefName}\`` which is subsequently used in branch lookup/creation (`_createBranch`) [2](#0-1) . Unlike the deep-link path (`x-github-client://openRepo/...`) which validates the `branch` query parameter with `testForInvalidChars` before use [3](#0-2) , or `setRemoteURL`/`addRemote` callers elsewhere in the code that route names through `sanitizedRefName`, the PR-checkout path performs no equivalent check on `head.ref` or `head.repo.clone_url` (empty string, control characters, or a value beginning with `-` are all accepted).

### Finding Description
`addRemote(repository, forkRemoteName, headCloneUrl)` [4](#0-3)  passes `headCloneUrl` straight to `git(['remote', 'add', name, url], ...)` [5](#0-4)  with no emptiness/format check comparable to the `isClonePathSensitive` or `sanitizeCloneName` guards used for the clone flow [6](#0-5) . Similarly `headRefName` is concatenated into `remoteRef` and eventually into a `git checkout`/`branch` argument via `_createBranch` without going through `sanitizedRefName`/`testForInvalidChars`, the sanitizers this codebase clearly relies on elsewhere for exactly this class of input (see `app/src/lib/sanitize-ref-name.ts` and its use in `parse-app-url.ts`). Since `dugite`/`git` is invoked via `execFile` with an argv array (not a shell), classic shell injection is not possible, but a ref/branch value can still be crafted to be empty, or to collide with reserved names, causing git to interpret it unexpectedly, or a `clone_url` value that is empty/malformed could still be handed to `git remote add`.

### Impact Explanation
An attacker only needs to open a pull request from their own fork against any public GitHub repository (no special permission needed) and get the victim to view/open that PR in Desktop — a normal action for reviewers. Desktop will then call `addRemote`/create a branch using values the attacker fully controls (`clone_url`, `head.ref`). This falls in the "attacker controls a GitHub API object" category. If exploited, the corrupted values are the local git remote configuration and the branch that gets checked out, i.e., silent corruption of repository state that could subsequently confuse the user's next commit/push. The reachable path is narrower/lower severity than the deep-link filepath or clone-name-traversal bugs already hardened in this codebase, since it relies on other guardrails (e.g., `sanitizedRefName` is applied at branch-name display/creation elsewhere, and `addRemote` failures are caught in a try/catch), so I could not confirm arbitrary command execution or path escape — only inconsistent input validation relative to the rest of the codebase's defenses.

### Likelihood Explanation
Moderate: the trigger (open/view a PR from a fork) is a routine, low-friction user action, but exploitation depends on how git/`_createBranch` reacts to unusual `head.ref` values, which I could not fully verify from the available code — I did not find the implementation details of `_createBranch`'s validation, if any.

### Recommendation
Validate `headRefName` with the existing `testForInvalidChars`/`sanitizedRefName` helpers, and validate/require a non-empty, well-formed `headCloneUrl` (e.g., via `parseRemote`) before calling `addRemote` in `_findPullRequestBranch`, mirroring the checks already applied in `parse-app-url.ts` for the `branch` deep-link parameter.

### Proof of Concept
1. Attacker forks `victim-org/public-repo` and creates a branch/PR with an unusual `head.ref` (e.g., empty after URL decoding, or containing characters not permitted by `sanitizedRefName`) — this is attacker-controlled data returned by the GitHub API.
2. Victim, using GitHub Desktop, opens this PR (via the pull request list or an "Open in Desktop" link), triggering `checkoutPullRequest` → `_checkoutPullRequest` → `_findPullRequestBranch` [7](#0-6) .
3. `addRemote(repository, forkRemoteName, headCloneUrl)` and the later branch creation run with the attacker's unvalidated `head.ref`/`clone_url`, with no equivalent of `testForInvalidChars` applied.

Note: I could not verify the internal implementation of `_createBranch` (branch-name validation) or confirm a full, exploitable consequence beyond "unvalidated attacker-controlled input reaches git remote/branch operations"; a Devin session with full repo access would be needed to trace `_createBranch` and any downstream effects to establish definitive impact/severity.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
