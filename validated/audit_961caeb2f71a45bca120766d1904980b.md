### Title
Scanner drops sub-dust outputs but still permanently marks the block as scanned, losing deposited funds - (File: processor/src/multisigs/scanner.rs)

### Summary
`LinearDistributor.declareReward` processed only `min(distributed, balance)` yet stored `previouslyVested = currentlyVested`, permanently discarding the undistributed remainder. The same shape exists in Serai's scanner pipeline: when scanning a block, outputs whose value is below `N::DUST` are silently dropped from the `outputs` list, yet the block's number is still recorded as fully scanned (`ram_scanned` / `ScannerDb::save_scanned_block`). The sub-dust output is never revisited — its funds are on-chain but permanently invisible to the multisig: never credited, never spendable.

### Finding Description
In `processor/src/multisigs/scanner.rs`, the scanning loop collects outputs only if they meet the dust threshold:

```rust
for output in network.get_outputs(&block, key).await {
  assert_eq!(output.key(), key);
  if output.balance().amount.0 >= N::DUST {
    outputs.push(output);
  }
}
``` [1](#0-0) 

Regardless of how many outputs were filtered out, the block is then unconditionally marked scanned:

```rust
scanner.ram_scanned = Some(block_being_scanned);
``` [2](#0-1) 

and durably via `ScannerDb::<N, D>::save_scanned_block(txn, number)` inside `ack_block` [3](#0-2) . If the dropped output was the only output in the block, no `ScannerEvent::Block` is even emitted (`sent_block` requires `!outputs.is_empty()`) [4](#0-3) , so nothing downstream ever learns the deposit exists. `get_outputs` in `processor/src/networks/bitcoin.rs` only filters by script_pubkey match inside `scan_transaction` [5](#0-4) ; the value filter lives solely in the scanner, and once `ram_scanned`/the DB cursor advance past the block, the output is permanently skipped — exactly the "checkpoint advanced past unprocessed remainder" pattern of M-15.

### Impact Explanation
Any unprivileged third party can send a Bitcoin transaction paying a Serai external/branch/change/forward address with an amount below `N::DUST` (e.g., a few hundred satoshis; consensus-valid even if non-standard to relay). The deposit lands on-chain under the multisig's key but is never emitted as an `Output`, never saved via `save_outputs`, and never enters a scheduler plan — it becomes funds received that are neither credited nor spendable, and there is no rescan path since the block is recorded as scanned. Depending on where `N::DUST` sits relative to the network's true economic dust/fee boundary, real user deposits marginally above relay dust but below `N::DUST` are also silently burned.

### Likelihood Explanation
Triggering requires only that an attacker (or a careless depositor) broadcast a transaction paying a monitored script_pubkey with `amount < N::DUST`. This needs no privileged position, no collusion, and no control over Serai infrastructure — just a public Bitcoin transaction, which the threat model explicitly permits. Cost to the attacker is the burned output value itself. There is one caveat I could not fully verify within this analysis: the exact constant value of `N::DUST` (defined in `processor/src/networks/mod.rs`/per-network impls) relative to what a wallet might legitimately deposit; the larger `N::DUST` is above Bitcoin's ~546-sat dust limit, the more realistic accidental triggering becomes.

### Recommendation
Do not advance the scanned-block cursor past outputs that were dropped. Either:
- Emit all scanned outputs (with their balance) regardless of the dust threshold and let the scheduler decide whether an output is economical to spend, or
- Track dropped outputs (e.g., a per-block `dropped` list persisted in `ScannerDb`) and re-evaluate them if `N::DUST` ever decreases or fee conditions change, rather than treating the block as fully processed.

### Proof of Concept
Conceptual, mirroring the M-15 structure:

1. Processor registers key `K`; scanner begins scanning blocks after `activation_number`.
2. Attacker crafts and broadcasts a tx `T` in block `B` whose output pays `p2tr_script_buf(K)` (offset `Scalar::ZERO`, the External address) with `value = N::DUST - 1`.
3. Scanner reaches `B`: `scan_transaction` returns the `ReceivedOutput` (the scanner library itself has no amount filter), but `output.balance().amount.0 >= N::DUST` fails, so `outputs` stays empty.
4. Since `has_activation`, `is_retirement_block`, and `!outputs.is_empty()` are all false, no `ScannerEvent::Block` is emitted and nothing is saved via `save_outputs`; `ram_scanned = Some(B)` still executes and `save_scanned_block` is committed.
5. The deposit is permanently orphaned: it is under the multisig's control cryptographically, but no code path will ever surface it again — the remainder was "distributed" to zero while the progress marker recorded full progress. [6](#0-5)
