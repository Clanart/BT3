### Title
Consensus Liquidity (CL) pool balance is read as an instantaneous, single-block snapshot for staking reward allocation, allowing deposit-then-withdraw arbitrage of KIP-226/Flex staking rewards - (File: kaiax/staking/impl/getter.go, kaiax/reward/impl/getter.go)

### Summary
The `liquidity_lockbox` bug class (deposit into a reward-bearing pool, immediately harvest a proportional reward, then withdraw, with no lock-up) has a structural analog in Kaia's Prague-era Consensus Liquidity (CL) reward mechanism. The staking module reads a validator's CL pool native-KAIA balance from state at a single historic block and uses it, unmodified and un-timelocked, to compute that validator's share of the per-block minting reward, which is paid directly to the CL pool address every block.

### Finding Description
`GetStakingInfo` sources `StakingInfo` (including `CLStakingInfo.CLStakingAmount`) from a single historic block state, and after the Kaia hardfork this source is simply the immediately preceding block (`num - 1`): [1](#0-0) 

The CL staking amount itself is read directly as the CL pool contract's native balance at that block via the CL registry multicall, with no minimum holding period, cooldown, or snapshot averaging: [2](#0-1) [3](#0-2) 

This raw, single-block balance is then used every block to compute the validator's total staking amount (CNStaking + CL) and to split staking rewards proportionally between the validator's own reward address and the CL pool address: [4](#0-3) [5](#0-4) 

Because `SourceNum(num) = num - 1`, a depositor into a CL pool only needs their deposit to be reflected in the state at block `N-1` to have it count toward the staking-reward calculation that pays out at block `N`. There is no mechanism analogous to `STAKE_LOCKUP` (used by `CnStakingV4`, see below) applied to CL pool deposits — the lockup constant exists for the CN staking contract's own stake withdrawal approval flow, not for the CL pool's balance eligibility for reward computation: [6](#0-5) 

This mirrors the Autonolas `liquidity_lockbox` root cause precisely: the reward-determining "position size" (there, LP NFT size; here, CL pool KAIA balance) is measured with no vesting/lock-up, and rewards are paid out to whoever holds that position at the measurement instant, with no penalty or delay for withdrawing right after.

### Impact Explanation
An attacker (a public depositor to a permissionless CL pool — no special privilege required) can:
1. Deposit a very large amount of KAIA into a CL pool associated with a validator (self-owned or complicit) in block `N-1`.
2. The staking module snapshot at block `N-1` captures this inflated CL balance.
3. At block `N`, `assignStakingRewards`/`assignStakingRewardsFlex` allocate a disproportionate share of the block's minting reward to that CL pool (and by extension its depositors/shares), proportional to the artificially inflated stake.
4. The attacker withdraws the deposited KAIA (and claims/redeems their proportional share of the harvested reward) immediately afterward, repeating the deposit/withdraw cycle every block or every few blocks.

This allows reward-farming that dilutes the honest, long-term-committed CL depositors and validators, since minting rewards are a fixed, protocol-wide finite resource distributed proportionally to (potentially manipulated) instantaneous stake — a concrete reward-redirection/theft impact matching the "Medium/High" bar (unauthorized value movement via reward redirection).

### Likelihood Explanation
Reachability requires only a public CL pool deposit/withdrawal transaction (no privileged access) timed around ordinary block boundaries, which is well within reach of a single unprivileged transaction sender bidding for block-boundary inclusion. The only prerequisites are: (a) a CL pool that allows permissionless deposit/withdrawal without a lock-up longer than 1-2 blocks, and (b) sufficient capital or a flash-loan-like mechanism to make the temporary deposit worthwhile relative to gas/opportunity cost. Because the actual CL pool contract's deposit/withdraw implementation was not found in the indexed codebase (only mocks such as `CLRegistryMock.sol` were available), I could not fully confirm whether the production CL pool contract enforces any lock-up on withdrawals; this is a material verification gap that should be checked in the CL pool contract source before finalizing severity.

### Recommendation
- Use a time-weighted or delayed CL staking amount (e.g., minimum balance over the past N blocks, or balance snapshotted several blocks in the past with an enforced minimum holding period) rather than the raw balance at `num-1`, mirroring the STAKE_LOCKUP protections already present for CNStaking withdrawals.
- Enforce a lock-up/cooldown period on CL pool deposits before they count toward `CLStakingAmount` used in `assignStakingRewards`/`assignStakingRewardsFlex`.
- Consider excluding the block-N reward from CL pool depositors whose funds were deposited within the same lockup window, similar to the "don't reward the withdrawing user" mitigation suggested in the original report.

### Proof of Concept
1. Deploy/identify a CL pool registered in `CLRegistry` for validator V, eligible for staking rewards (CNStaking(V) ≥ `reward.minstake`).
2. At block `N-1`, submit a transaction depositing a large amount of KAIA into the CL pool (increasing its native balance).
3. `kaiax/staking.GetStakingInfo(N)` computes `sourceBlockNum(N) = N-1` and reads the CL pool's inflated balance via `MultiCallDPStakingInfo`, populating `CLStakingInfo.CLStakingAmount`. [7](#0-6) 
4. At block `N`, `FinalizeState` calls `GetDeferredReward` → `assignStakingRewards`, which computes `reward = excess * stakersReward / totalExcess` using the inflated `CLStakingAmount`, then splits and credits `alloc[cn.CLStakingInfo.CLPoolAddr]` directly via `state.AddBalance`. [8](#0-7) [9](#0-8) 
5. Immediately after (block `N` or `N+1`), the attacker withdraws their deposited KAIA from the CL pool along with their proportional share of the harvested reward, and repeats.

Note: Step 5's exact mechanics depend on the (unindexed) production CL pool contract's withdrawal function and share-accounting logic, which I was unable to locate in this codebase snapshot — only test mocks were found. This should be verified directly against the CL pool contract source before treating this as confirmed rather than a strong structural analog.

// assignStakingRewards assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining
