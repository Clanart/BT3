### Title
Spoofed `WWW-Authenticate` realm from an attacker-controlled Git remote/proxy triggers a GitHub Enterprise sign-in prompt for the attacker's host - (`app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The bug-class in the report is a **trust-classification bug**: a value that should require strong verification (an SPL mint address) is instead classified by matching it against a hard-coded literal in a branch, and the wrong branch drives a security-relevant decision (which balance/API to call). The closest analog in GitHub Desktop is `getEndpointKind()` in the Git credential-helper trampoline, which classifies an unauthenticated remote host as `'enterprise'` (i.e., "this is a real GitHub Enterprise/GHE server, safe to prompt the user for a first-party GitHub sign-in") based solely on an attacker-suppliable HTTP header value, without any origin/hostname verification.

### Finding Description
`getEndpointKind()` determines how the trampoline credential helper should treat a host that Git is asking for credentials for: [1](#0-0) 

For hosts that aren't already known to be `github.com`/`ghe.com`/an existing account's endpoint, the code inspects the `wwwauth[...]` credential-helper fields — which are populated directly from the `WWW-Authenticate` HTTP response header sent by the remote Git server (or any proxy/MITM sitting on that connection) — and classifies the endpoint as `'enterprise'` purely if the header string contains `realm="GitHub"`. This value is **fully attacker-controlled**: it originates from the HTTP response of whatever host the user is fetching/cloning/pushing to, and Git forwards it to the credential helper verbatim as documented in the code's own comment ("we use them as a happy-path... without having to resort to making a request ourselves").

That classification then feeds directly into `getCredential()`'s trust decision: [2](#0-1) 

If `endpointKind !== 'generic'` and Desktop has no existing account for the derived `apiEndpoint`, it calls `ui.promptForGitHubSignIn(endpoint)` — presenting the user with a native "Sign in to GitHub Enterprise" flow **pointed at the attacker's endpoint**, rather than falling back to the generic username/password credential path used for arbitrary Git hosts. This mirrors the WSOL bug exactly: a single attacker-influenced signal (`realm="GitHub"` string vs. `WRAPPED_SOL_ADDRESS` string) causes the code to jump into a more privileged/trusted code path (native SOL balance call vs. first-party GitHub sign-in flow) instead of the generic path that would otherwise apply.

### Impact Explanation
Any Git server the user interacts with (clone, fetch, push, pull) can trigger this by simply returning `WWW-Authenticate: Basic realm="GitHub"` on a 401 response. Desktop will then invite the user into a GitHub Enterprise sign-in flow scoped to that attacker's host. Because Desktop treats this as legitimate "enterprise" classification (rather than "generic" third-party auth), the resulting account is stored via `AccountsStore`/`TokenStore`, and subsequent Git operations to that host will use `credWithAccount` to inject the account's login/token as Basic Auth credentials automatically — training users to complete GitHub-branded sign-in for a server that has nothing to do with GitHub, and normalizing entry of GitHub-style credentials/PATs into a UI flow the user is led to trust because Desktop itself labeled it "GitHub Enterprise". This satisfies the "unauthorized OAuth or account binding" / credential-handling impact category, since it is a git remote/proxy response (fully attacker-controlled) driving a security decision with no server-side verification (no call to `isGitHubHost()`, no origin check).

### Likelihood Explanation
Likelihood is limited by the ordering of checks: `isDotCom`, `isGHE`, and `findGitHubTrampolineAccount` are tried first, so this path only triggers for hosts unknown to Desktop, which is exactly the case for a first-time clone/fetch from a brand-new attacker-controlled server — a common, natural workflow (e.g., a user adding an "internal" remote, or opening a link that clones from an unfamiliar host). No unusual user behavior is required beyond the normal act of authenticating against a new remote, and `getIsBackgroundTaskEnvironment` only suppresses the prompt for non-interactive/background fetches, not user-initiated clone/push/pull actions.

### Recommendation
Do not classify a host as `'enterprise'` based solely on the `WWW-Authenticate` realm string. At minimum, corroborate the header-based heuristic with an actual `isGitHubHost()` network check (already implemented elsewhere in `api.ts`) before offering the first-party "Sign in to GitHub" flow, and clearly surface the actual hostname/URL being authenticated in the sign-in prompt so users can distinguish a spoofed GitHub-branded prompt from a real GHE sign-in.

### Proof of Concept
1. Attacker stands up a Git-over-HTTP server (or a transparent proxy) that, on receiving a credential request for any repository path, responds with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim adds this server as a remote in GitHub Desktop and performs `Fetch`/`Push`/`Clone`.
3. Git forwards the `wwwauth[...]` field to Desktop's credential helper trampoline; `getEndpointKind()` returns `'enterprise'` for this arbitrary host: [3](#0-2) 
4. Since no account exists for this endpoint, `getCredential()` calls `ui.promptForGitHubSignIn(endpoint)`, presenting a "Sign in to GitHub Enterprise" dialog scoped to the attacker's host: [4](#0-3) 
5. If the victim completes sign-in (PAT entry or OAuth against the attacker's fake "GitHub Enterprise" endpoint), the resulting credential is bound to and reused for that attacker host on all future operations.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }
