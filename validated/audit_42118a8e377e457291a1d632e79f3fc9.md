### Title
Deterministic CachedPreprocess reuse across repeated `share`/`complete` invocations leaks the signer's secret share via parallel-session (ROS-style) nonce reuse — (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` stores a deterministic nonce seed in `CachedPreprocesses` keyed only by `context`, and every call to `share_internal` (via `share()` and again inside `complete()`) rebuilds the FROST `AlgorithmSignMachine` from that same seed. The participant set and the attacker-supplied preprocess bytes (`read_preprocess`) are effectively "reconfigured" on each call — the direct analog of `setMintAgent`/`setReleaseAgent`/`setFinalizeAgent` being invocable post-initialization — while the nonce is frozen. Each extra call emits another signature share over the same nonce with different binding factors/signing sets, yielding linear equations that recover the signer's secret share.

### Finding Description
In `coordinator/src/tributary/signing_protocol.rs:123-145`, the preprocess is generated once and cached:

- `CachedPreprocesses::get(self.txn, &self.context)` is checked; if absent, a machine's `cache()` (the ChaCha20 seed) is XOR-encrypted and persisted with `CachedPreprocesses::set`.
- On every subsequent call, `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))` regenerates the *identical* nonce pair from the identical seed (`crypto/frost/src/sign.rs:127-133`, `Commitments::new(&mut rng, ...)` seeded by `ChaCha20Rng::from_seed(*seed.0)`).

`share_internal` (lines 150-180) is then invoked with a caller-supplied `serialized_preprocesses` map, each entry parsed by `machine.read_preprocess` (untrusted bytes), and `machine.sign(preprocesses, msg)` computes the share as `base + rho_i * actual` over those same nonces (`crypto/frost/src/sign.rs:386-398`).

Crucially, `DkgConfirmer::complete` (lines 312-327) calls `share_internal` a *second* time — "trying to complete a machine which failed to preprocess" — and `share()` itself can be invoked repeatedly as preprocess sets arrive. The FROST API documents the invariant this breaks: `CachedPreprocess` "MUST only be used once. Reuse will enable third-party recovery of your private key share" (`crypto/frost/src/sign.rs:85-87`, `:216-219`, "the preprocess must be deleted so it's never reused"). The coordinator never deletes or rotates the cache for a context, so the nonce is reused once per `share`/`complete` call.

### Impact Explanation
Each `sign` produces a share `s = Σ (d_j + rho_j * e_j) + λ_i * c * x_i` where `(d_j, e_j)` are the fixed nonces and `x_i` the secret share. The binding factors `rho` and the interpolated coefficient `λ_i`/`c` depend on the preprocess set and message (`crypto/frost/src/sign.rs:361-367`, rho over `group_key`, `hash_msg`, and the `preprocesses` challenge; participant list is appended per-signer at `:325-331`). An attacker feeding multiple distinct preprocess sets to `read_preprocess`/`share` for the same context obtains multiple equations in the same three unknowns `(d, e, λc x_i)`. With enough distinct challenges (Wagner/ROS-style parallel-session reuse), the system is solvable and the signer's FROST secret share — equivalent to its long-term MuSig/tributary private key — is recovered, enabling forgery of all future signatures under that key.

### Likelihood Explanation
The cache is never invalidated after a successful or failed `sign`, so any code path that calls `share()` more than once for the same `(context)` — retries, `share()` then `complete()`, or resubmission with a different participant set — triggers nonce reuse. The preprocess bytes themselves are untrusted `read_preprocess` input, so the per-call challenge variation needed for share recovery is externally controllable. Exploitation requires inducing multiple share emissions per context, which is plausible given `complete` unconditionally re-runs `share_internal` and retry attempts for the same attempt number share the context.

### Recommendation
Make the cached preprocess single-use: delete `CachedPreprocesses[context]` (or store a "consumed" flag) on the first `share_internal`, and refuse subsequent `share`/`complete` calls for that context rather than silently re-deriving the same nonces. Alternatively, mix the preprocess set/message into the seed so nonces cannot be replayed across differing signing sets — though true single-use deletion is the FROST-required fix. Keep `preprocess()` idempotent (it may safely regenerate the same commitments), but gate the signing side.

### Proof of Concept
1. Fix a context, e.g. `("DkgConfirmer", attempt)` for a given tributary `spec`/attempt.
2. Call `DkgConfirmer::preprocess()` → seed `k` is stored in `CachedPreprocesses`.
3. Submit preprocess set `P1` (participant subset A) via `share(P1, key_pair)` → share `s1 = d + rho_1·e + λ_1·c_1·x`.
4. Submit a different valid preprocess set `P2` (different participants/commitments → different `rho`, `λ`, `c`) → `share_internal` rebuilds the machine from the same cached `k`, emitting `s2 = d + rho_2·e + λ_2·c_2·x`.
5. Repeat with `P3`, `P4`, … Each new distinct challenge adds an independent equation in `(d, e, x)`; three or more distinct equations suffice to solve for `x`, the victim's Ristretto secret share underlying its `ThresholdKeys`, after which the attacker can compute valid shares/signatures for the tributary MuSig key unilaterally.
