## Title
Reputation-mint rewards in `pallet-messaging-incentives` can be minted to an arbitrary self-chosen account, scaled by an attacker-controlled byte count, with no requirement that real relaying work occurred - (File: `modules/pallets/messaging-incentives/src/lib.rs`)

### Summary
`pallet-messaging-incentives::on_executed` mints `ReputationAsset` (the metric that determines Collator/block-producer selection) proportional to `max(body.len(), 32)` for every delivered `Request`/`Response` message, and pays it to whatever account it recovers from the message's embedded `signer` signature. Because `handle_unsigned` is a free, permissionless, unsigned extrinsic that "permits anyone [to] execute ISMP messages for free, provided they have valid proofs" [1](#0-0) , and because the `signer` field is arbitrary application data chosen by whoever submits the message rather than something tied to a paying transaction origin, an attacker who also controls the source-chain module dispatching the request can (a) pick the body size that maximizes the mint and (b) attribute the mint to any account of their choosing, self-relaying their own oversized message for essentially zero marginal cost. This is structurally the same broken invariant as the Prisma "mint awards can be manipulated" bug: a reward is computed from a metric the beneficiary fully controls, decoupled from any real, externally-verifiable cost or service.

### Finding Description
`pallet-messaging-incentives::on_executed` is wired as `pallet_ismp`'s `FeeHandler`, firing after every successfully executed batch of ISMP messages: [2](#0-1) 

The byte count used for the mint is computed purely from the dispatched body, with only a 32-byte floor: [3](#0-2) 

The recipient of the mint is recovered from an sr25519 signature embedded in the `Message`'s `signer` field — a field the message author controls, not a field cryptographically bound to whoever pays gas/fees to submit the extrinsic: [4](#0-3) 

Delivery itself goes through `pallet_ismp::handle_unsigned`, which is explicitly documented as permissionless and free: [5](#0-4) [6](#0-5) 

Putting these together: an attacker who owns a module on any connected source chain can dispatch a `PostRequest` with `fee: 0` and an arbitrarily large `body` (e.g. padded with junk bytes) to any destination, wait for the request's commitment to be provable, then submit `handle_unsigned` themselves, embedding a signature from a keypair they control in the `signer` field. `on_executed` will mint `bytes × MintPerByte` `ReputationAsset` to that self-chosen account. There is no check that:
- the "relayer" delivering the message did any work distinct from the module that created it,
- the `signer` corresponds to the account that actually paid for or submitted the extrinsic,
- the byte count reflects genuine payload utility rather than padding chosen purely to inflate the mint.

This mirrors the Prisma report's core broken invariant: a reward metric (`accountLatestMint` there, `bytes`/`signer` here) that the attacker can freely manipulate within their own controlled sequence of actions, decoupled from the real economic value the reward is supposed to compensate.

### Impact Explanation
`ReputationAsset` is the sole ranking input for Collator (block-producer) selection on Hyperbridge — "It ranks the remaining candidates from highest to lowest based on their Controller's Reputation Asset balance" [7](#0-6) . Collators are paid directly from the treasury per authored block (`0.7 $BRIDGE`/block, ~4,000,000 $BRIDGE/year in aggregate) [8](#0-7) , and also run the network's fisherman fraud-detection task. An attacker able to mint unlimited Reputation cheaply can jump the Collator selection queue without performing genuine, costly relaying/consensus work, letting them capture block-production rewards and gain influence over the fisherman veto path — a direct "logic attack" on the incentive architecture that determines who gets privileged execution authority (collator status) on the chain.

### Likelihood Explanation
The path requires no privileged role, no relayer/prover collusion, and no malformed proof — only: (1) controlling a module on any already-connected source chain (any dApp/user can deploy one), (2) dispatching a self-serving request with a large, cheap-to-produce body, and (3) submitting the free, permissionless `handle_unsigned` extrinsic with a self-chosen `signer`. All of these are ordinary, unprivileged, already-documented capabilities of the protocol, making this a low-effort, repeatable, purely mechanical exploitation of the reward formula rather than a one-off edge case.

### Recommendation
Do not compute rewards purely from a value the reward's beneficiary fully controls (message body size) combined with a self-asserted `signer` field. Concretely:
- Tie the mint to real fee payment/escrow (similar to `pallet-consensus-incentives`, which rewards based on verified externally-sourced progress, not attacker-suppliable data), or cap/normalize the per-message byte contribution against the actual relayer fee paid for that message.
- Bind the reward recipient to the actual extrinsic submitter/payer rather than an arbitrary embedded signature the message author can set to anything.
- Rate-limit or diminishing-return the per-source-module or per-account mint within a time window so padding-driven inflation has bounded impact even if the metric itself isn't fully fixed.

### Proof of Concept
1. Deploy a module `M` on any connected source chain `S`.
2. From `M`, dispatch a `PostRequest` (`fee: 0`) to a destination `D` with `body` padded to the maximum practical size (repeat across many dispatches to accumulate more).
3. Once the request commitment is provable (ordinary ISMP flow, no special access needed), craft a `Message::Request(RequestMessage { requests, proof, signer })` where `signer` is an sr25519 signature over `keccak256(requests.encode())` produced with any keypair the attacker controls (e.g., their own Controller account).
4. Submit `Ismp::handle_unsigned(vec![message])` — free, unsigned, permissionless per `modules/pallets/ismp/src/lib.rs:360-382`.
5. `pallet-messaging-incentives::on_executed` runs, computes `bytes = max(body.len(), 32)` per request [3](#0-2) , recovers the attacker's chosen account from `signer` [9](#0-8) , and mints `bytes × MintPerByte` `ReputationAsset` to it.
6. Repeat across many self-dispatched, self-relayed, maximally-padded requests to accumulate Reputation far in excess of any genuine relaying contribution, then use it to win Collator selection at the next session boundary.

```rust
	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}
```

```rust
impl<T: Config> FeeHandler for Pallet<T>
where
	T::AccountId: From<[u8; 32]>,
{
	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}
}
```

```text
## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
```
