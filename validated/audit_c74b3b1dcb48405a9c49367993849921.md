## Analog Identification

Reducing the external report to its core broken invariant: **an unchecked externally-derived exchange value is used to move funds, with no bound and no reconciliation of what was actually consumed vs. what was paid in.** In Kelp, that was `getRate()` from an LST. In Hyperbridge, the local analog is the native-token→fee-token conversion done inline in `EvmHost.dispatch()`, which consumes a Uniswap V2 spot quote with no slippage bound and — unlike the equivalent code path in `IntentGatewayV2.sol` — never reconciles or refunds the unused portion of `msg.value`.

### Title
Unrefunded native-token overpayment silently locked in `EvmHost` on fee-token swap - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` accept `msg.value` and swap it for an exact amount of `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`, but never check or refund the leftover input. The sibling contract `IntentGatewayV2.sol` performs the identical swap and explicitly tracks `amounts[0]` (actual ETH consumed) to refund the difference to the caller. `EvmHost` omits this step entirely.

### Finding Description [1](#0-0) 

`dispatch(DispatchPost)` does:
```solidity
if (msg.value > 0) {
    ...
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
} ...
```
No `amountInMax` other than the full `msg.value` is enforced, and — critically — the router's return value (`amounts[0]`, the actual ETH spent) is discarded. The identical pattern repeats verbatim in `dispatch(DispatchGet)`. [2](#0-1) 

Uniswap V2's `swapETHForExactTokens` refunds unspent ETH to `msg.sender` **of the router call**, which here is `EvmHost` itself (since `EvmHost` is the direct caller of the router), not the original transaction sender or `post.payer`. Any ETH sent by a user beyond what the AMM's current spot price requires to produce `post.fee` units of `feeToken` is transferred back into `EvmHost`'s own balance and is never credited or returned to the user.

Contrast this with the correct pattern used in `IntentGatewayV2.sol`, which performs the same conversion but explicitly captures the swap's actual cost and refunds the remainder to the caller: [3](#0-2) 

```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
msgValue -= amounts[0];
...
if (msgValue > 0) {
    (bool sent,) = msg.sender.call{value: msgValue}("");
    if (!sent) revert InsufficientNativeToken();
}
```

`EvmHost.dispatch()` has no equivalent block. There is no local evidence of any subsequent sweep/withdraw entry point in `EvmHost.sol` that would return this specific trapped native balance to the original payer — it accumulates as an unattributed contract balance.

### Impact Explanation
Any application or end user who dispatches a POST/GET request paying with native token (the documented, first-class payment method per `docs/content/developers/evm/messaging/post-requests.mdx`) and supplies `msg.value` even slightly above the AMM's current required input (which is unavoidable in practice, since callers must estimate the swap input off-chain via `getAmountsIn`/`quoteNative`, and pool price moves between quote and execution) permanently loses the difference. This is a direct, unconditional loss of user funds on a public entry point (`dispatch`), with no adversarial relayer, prover, or governance actor required — it is triggered purely by normal usage variance between quoted and executed AMM price.

### Likelihood Explanation
High. `dispatch()` is the primary, unprivileged, permissionless entry point for every application built on Hyperbridge that chooses to pay fees in native token — a documented and expected usage pattern (`sdk/packages/sdk/src/chains/evm.ts` `quoteNative`/`getAmountsIn` exists specifically to compute this input, and any latency or price movement between quoting and the actual transaction guarantees over-supply of `msg.value`). Every such call leaks the residual ETH into `EvmHost`'s balance. The identical swap call already has the correct fix implemented next to it in `IntentGatewayV2.sol`/`evm/tron/contracts/apps/IntentGatewayV2.sol`, confirming the omission in `EvmHost.sol` is a real inconsistency rather than an intentional design choice.

### Recommendation
Capture the `amounts` return value from `swapETHForExactTokens` in both `dispatch(DispatchPost)` and `dispatch(DispatchGet)`, and refund `msg.value - amounts[0]` to `_msgSender()` (or the designated `payer`), mirroring the pattern already used in `IntentGatewayV2.sol`. Additionally consider adding a maximum-input bound (analogous to a price-oracle sanity check) so a manipulated or thin Uniswap V2 pool cannot force an unexpectedly large ETH consumption for a given `fee`.

### Proof of Concept
1. Caller estimates required ETH for a `post.fee` of `X` fee-token units using `getAmountsIn`/`quoteNative`, getting quote `Q`.
2. Caller calls `EvmHost.dispatch{value: Q + delta}(post)` where `delta` is any positive buffer (routine practice to avoid revert from price movement, and unavoidable if the pool price moves favorably between quote and inclusion).
3. `swapETHForExactTokens` consumes only `amounts[0] <= Q` ETH to acquire exactly `X` fee-token units; it refunds `msg.value - amounts[0]` — but to `EvmHost` itself, since `EvmHost` is the caller of the router.
4. `dispatch()` returns normally, having correctly recorded `post.fee` and the request commitment, but the excess `delta` (and up to `Q - amounts[0]`) ETH is now sitting in `EvmHost`'s balance, unattributed to the caller and not reachable through any code path back to them.
5. Repeating this over many dispatches accumulates unrecoverable-by-users native token inside `EvmHost`.

Note: I was unable to fully verify from the indexed content whether any privileged sweep/withdraw function in `EvmHost.sol` later returns this specific balance to affected users (49 grep matches for `withdraw`/`refund`/etc. existed in the file but were not individually inspected due to iteration limits) — if such a targeted per-payer reconciliation exists, the impact would be reduced to a temporary lock rather than permanent loss. Given the specific `dispatch()` code path shown has no local refund logic, and the direct sibling contract (`IntentGatewayV2.sol`) needed to add one explicitly, this is a credible, locally-provable fund-loss analog to the "no checks on returned value" bug class.
