### Title
Schnorr signature verification accepts forged signatures for identity public keys - (File: crypto/schnorr/src/lib.rs)

### Summary
`SchnorrSignature::verify` does not reject the identity public key. For `public_key = identity`, an attacker can choose any nonzero scalar `s`, set `R = s * G`, and produce a signature satisfying the verification equation for every challenge. Both the signature point and public key are accepted through canonical decoding, which permits the identity element. [1](#0-0) [2](#0-1) 

### Finding Description
`batch_statements` verifies `R + challenge * public_key - s * G == identity`. When `public_key` is the identity, the middle term is always identity, so the equation reduces to `R - sG == 0`. An attacker can satisfy it without knowing a private key by selecting `s` and calculating `R = sG`.

`SchnorrSignature::read` performs only canonical scalar/point decoding and imposes no restriction on `R`. [3](#0-2)  Similarly, `Ciphersuite::read_G` rejects malformed and non-canonical encodings but does not reject the canonical identity point. [2](#0-1) 

### Impact Explanation
Any reachable verification path that permits an untrusted party to select or cause use of an identity public key accepts a forged Schnorr signature for arbitrary messages/challenges. This is a signature forgery resulting from missing validation of a weak group element, analogous to the reported class of accepting improperly validated attacker-supplied input.

### Likelihood Explanation
The attack is deterministic once the identity public key reaches `verify`. The required signature consists only of `R = sG` and the attacker-chosen scalar `s`; no discrete logarithm or private key is needed. Exploitability therefore depends on whether the calling protocol permits an identity key, but the primitive accepts all inputs needed for the forgery.

### Recommendation
Reject identity public keys in `SchnorrSignature::verify` and `batch_verify`. Rejecting an identity `R` in `SchnorrSignature::read` or `verify` is also advisable as defense in depth, although identity `R` alone is not sufficient for this forgery. Callers constructing threshold or aggregate keys should additionally reject an identity resulting group key before verification.

### Proof of Concept
```rust
use ciphersuite::{
  group::{ff::Field, Group},
  Ciphersuite,
};
use schnorr::SchnorrSignature;

fn forge_for_identity_key<C: Ciphersuite>() {
  // Any nonzero scalar works.
  let s = C::F::ONE;

  // The attacker's public key is the identity point.
  let public_key = C::G::identity();

  // Choose R = sG so R - sG = identity.
  let signature = SchnorrSignature::<C> {
    R: C::generator() * s,
    s,
  };

  // Any challenge works because challenge * identity() == identity().
  let challenge = C::F::ONE;

  assert!(signature.verify(public_key, challenge));
}
```

The verification pairs are `R`, `challenge * public_key`, and `-s * G`. With `public_key = identity`, this becomes `sG + identity - sG = identity`, so verification succeeds despite the absence of a corresponding private key. [1](#0-0)
