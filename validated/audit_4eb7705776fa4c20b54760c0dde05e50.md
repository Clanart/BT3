## Analog Found: Stale `_requestCommitments` entry after GET response delivery enables a duplicate fee payout via a subsequent GET timeout

### Title
Un-consumed `_requestCommitments` entry after `dispatchIncoming(GetResponse)` allows a duplicate relayer-fee payout via `dispatchTimeOut(GetRequestTimeout)` - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(GetResponse memory response, address relayer)` pays out the request's fee to the relayer but never deletes the `_requestCommitments[commitment]` entry that stores that fee metadata. `dispatchTimeOut(GetRequestTimeout ...)` treats the mere *existence* of that same `_requestCommitments[commitment]` entry as its only "replay protection" and, if present, refunds `meta.fee` again to the original payer and invokes `onGetTimeout` on the app. Because the response path never clears the entry, a GET request that has already been successfully answered remains eligible for a later timeout once its `timeout_timestamp` elapses, producing a second fee payout and a second (conflicting) app-level callback for the same logical request — the same class of bug as H-22's un-deleted `_isLiquidation` flag causing a stale mapping to corrupt a later settlement.

### Finding Description
`dispatchIncoming(GetResponse)` sets `_responseReceipts[commitment]` and, on success, pays `_requestCommitments[commitment].fee` to the relayer, but it never deletes `_requestCommitments[commitment]`: [1](#0-0) 

Compare this with `dispatchTimeOut(GetRequestTimeout ...)`, which explicitly relies on deleting `_requestCommitments[commitment]` as its "replay protection", and pays `meta.fee` to `meta.sender` on success: [2](#0-1) 

Both of these entry points are restricted to `_hostParams.handler`, meaning the handler contract is expected to gate which messages reach them, but the underlying storage invariant they rely on — "a request that has already received a response must not also be timed-out" — is only enforced by the `_requestCommitments` mapping being deleted. Since the response path leaves the mapping intact, that invariant is silently broken: the mapping still looks like "an unresolved request awaiting timeout" even though the request was already fulfilled.

This mirrors the reported pattern exactly: in the source report, `_isLiquidation[_collection][_tokenId]` is left `true` after `reserve()`, so a later, legitimate state transition (`_fillListing`) incorrectly treats the position as still-in-liquidation and skips a refund it should have paid. Here, `_requestCommitments[commitment]` is left populated after `dispatchIncoming(GetResponse)`, so a later, legitimate state transition (`dispatchTimeOut`) incorrectly treats the request as still pending and pays a refund it should not pay — a mirror-image manifestation of the same "stale one-time-use mapping" bug class.

The Substrate/pallet-ismp implementation of the same protocol explicitly guards against this scenario for `GetRequest` timeouts by checking whether a response was already received before allowing the timeout to proceed: [3](#0-2) 

The EVM host has no equivalent check tying `dispatchTimeOut(GetRequestTimeout)` to `_responseReceipts[commitment]`; it only checks/consumes `_requestCommitments[commitment]`, which the response path failed to clear.

### Impact Explanation
For any GET request whose `timeout_timestamp` has elapsed by the time (or shortly after) its response is delivered — which is common, since responses can arrive close to or after the configured timeout under normal network delay — the protocol pays the fee twice out of the host's fee-token balance:
1. Once to the relayer via `dispatchIncoming(GetResponse)`.
2. A second time to the original fee payer via `dispatchTimeOut(GetRequestTimeout)`.

In addition, the destination application module receives two conflicting callbacks for the same logical request (`onGetResponse` then `onGetTimeout`), which can cause an app that unlocked or settled state on receiving the response to duplicate or reverse that settlement when the timeout callback later fires — a direct "loss of funds" / "duplicate settlement" outcome on the host contract and on any app built against `IApp`.

### Likelihood Explanation
No privileged actor, malicious relayer, or compromised prover is required — any relayer submitting a legitimately-proven, already-elapsed timeout for a GET request that was previously (and correctly) answered will trigger the duplicate payout, since the handler-side gating only depends on `_requestCommitments[commitment]` still existing, which it always does after a response. The GET response and GET timeout paths are both reachable through normal, unprivileged relayer submission flows. I could not fully inspect `evm/src/core/HandlerV2.sol` to confirm whether an additional response-existence check is layered in front of `dispatchTimeOut` at the handler-entrypoint level (the tool budget was exhausted before that file's content could be retrieved), so this should be validated against `HandlerV2.sol`'s `handleGetTimeouts`/timeout dispatch function before treating the likelihood as certain.

### Recommendation
Delete `_requestCommitments[commitment]` inside `dispatchIncoming(GetResponse)` immediately after (or as part of) paying out the relayer fee, mirroring the "replay protection" deletion pattern already used in `dispatchTimeOut`. Additionally, have `dispatchTimeOut(GetRequestTimeout ...)` (or its caller in `HandlerV2.sol`) explicitly reject the timeout if `_responseReceipts[commitment]` is already populated, to defend in depth against the same class of stale-mapping bug.

### Proof of Concept
1. A GET request is dispatched via `dispatch(DispatchGet)`, storing `_requestCommitments[commitment] = FeeMetadata{sender, fee}`.
2. Shortly before/at the request's `timeout_timestamp`, a relayer submits a valid membership proof for the response; the handler calls `dispatchIncoming(GetResponse, relayer)`. This pays `fee` to `relayer` but leaves `_requestCommitments[commitment]` intact. [4](#0-3) 
3. Once `host.timestamp()` has passed `timeout_timestamp` (true almost immediately, since delivery happened at/near the deadline), any relayer submits a `GetRequestTimeout` message for the same commitment. Because ISMP for `Get` timeouts requires no state-membership proof (only elapsed time), and the handler only checks `_requestCommitments[commitment]` existence (still present from step 2), `dispatchTimeOut` succeeds: it deletes the entry, calls `onGetTimeout` on the app, and refunds `fee` a second time to `meta.sender`. [5](#0-4) 
4. Net result: the host contract has paid out `fee` twice for a single GET request, and the destination app has received both `onGetResponse` and `onGetTimeout` for the same logical request.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
```

    /**
     * @dev Dispatch an incoming GET timeout to the source module.
     * @notice Does not refund any protocol fees.
     * @param timeout - timed-out get request bundled with the relayer that submitted the timeout proof
     * @param meta - fee metadata for the original request
     * @param commitment - request commitment
     */
    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
```
