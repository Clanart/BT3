### Title
Default oracle confidence-interval tolerance of 10% is too high, permitting manipulated Pyth prices to pass unrejected into liquidation/health pricing - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`v0-4-market.clar` gates every Pyth price used for collateral/debt valuation and liquidation health checks with `check-confidence`, which accepts any price whose reported confidence interval is within `max-confidence-ratio` of the price. This ratio defaults to `u1000` (10% of price) [1](#0-0) , and is only changeable by the DAO via `set-max-confidence-ratio` [2](#0-1) . This mirrors the Maple `maxSwapSlippage = 1000 // 10%` finding: a permissive default tolerance value baked into the protocol at deploy time that widens the window an attacker can exploit before any bespoke governance action is taken.

### Finding Description
`check-confidence` enforces `confidence <= (price * max-confidence-ratio) / BPS` [3](#0-2) , and is invoked directly inside `resolve-pyth`, which is the sole gate on every Pyth-sourced price before it flows into `price-resolve` and ultimately into collateral/debt USD valuation and liquidation LTV computation [4](#0-3) . Because the default tolerance is 10% of the reported price, a legitimate-looking Pyth update whose confidence interval spans up to ±10% of the mid-price is accepted as valid, even though such a wide interval indicates the oracle itself is highly uncertain about the true price at that moment (e.g., during high volatility or thin liquidity on the underlying price sources Pyth aggregates). The accepted price is then used unmodified as `final-price` in `price-resolve` for both collateral and debt-side USD notional calculations feeding the liquidation LTV check `(mul-div-down total-debt-usd BPS total-collateral-usd)` at `liquidate` [5](#0-4)  and the `calc-liquidation-params`/`process-collateral-asset`/`calc-final-liquidation-amounts` pipeline that determines how much collateral is seized per unit of debt repaid [6](#0-5) . A price within the tolerated 10% band, taken at the favorable extreme of its own confidence interval, is exactly the kind of stale/uncertain-but-technically-fresh input this gate is supposed to filter out, yet a 10% default lets it through untouched.

### Impact Explanation
An accepted price up to 10% off from the oracle's own best estimate directly skews both the health check (`current-ltv >= ltv-liq-partial`) and the seized-collateral computation in `liquidate`. If the accepted collateral price prints high, positions that are actually already deeply underwater are not yet flagged liquidatable, delaying liquidation and growing bad debt that is ultimately socialized onto other lenders/stakers via `bad-debt-socialization` logic — a temporary/permanent freezing-of-funds-adjacent loss for LPs. Conversely, if a borrower's debt-asset price prints artificially low (still within the 10% band) at the moment of liquidation, the debt-to-collateral seizure ratio computed in `calc-final-liquidation-amounts` extracts more collateral than truly owed, transferring value from the borrower to the liquidator beyond the intended liquidation penalty. Either direction routes value away from the party who should have kept it, purely due to the loose default acceptance band on oracle confidence.

### Likelihood Explanation
This does not require any bug in Pyth itself — the price and its stated confidence are genuinely reported by Pyth; the issue is that Zest's own default tolerance (`u1000`) accepts a 10%-wide band of inherently uncertain prices as gospel for use in liquidation math. Since this value is a straightforward deploy-time default (not accidental misconfiguration but the shipped code default, per the report's bug class), it is live on any market instance unless the DAO has proactively lowered it via `set-max-confidence-ratio`, which requires a deliberate, separate governance action.

### Recommendation
Lower the default `max-confidence-ratio` to a materially smaller value (e.g., 1-2%) so that only prices Pyth itself reports with tight confidence are used to compute liquidation health and seizure amounts, and consider scaling allowed liquidation slippage/tolerance inversely with confidence rather than using one static ratio.

### Proof of Concept
1. Pyth publishes a price update for the debt or collateral asset with `conf` equal to exactly 9.99% of `price` (still within tolerance).
2. `resolve-pyth` calls `check-confidence`, which passes since `conf <= price * 1000 / 10000` [3](#0-2) .
3. `price-resolve` returns this price as `final-price` without further adjustment for the confidence spread [7](#0-6) .
4. `liquidate` uses this price to compute `total-collateral-usd`/`total-debt-usd` and the final collateral seized, moving up to ~10% of value in the wrong direction relative to the oracle's true confidence-adjusted price [8](#0-7) .

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
