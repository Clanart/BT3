### Title
Untrusted `ReceivedOutput` bytes can report unspendable outputs as spendable - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`ReceivedOutput::read` accepts an offset, `TxOut`, and `OutPoint` from untrusted bytes but never verifies that the offset derives the output’s Taproot script. This allows a malformed serialized output to be reported as a spendable `ReceivedOutput` even though the wallet cannot sign for it.

### Finding Description
`ReceivedOutput` is documented as “A spendable output” and carries the scalar `offset` needed to derive the spending key. [1](#0-0) 

`ReceivedOutput::read` deserializes the offset, output, and outpoint independently and returns the object without checking that `p2tr_script_buf(key + generator * offset) == output.script_pubkey`. [2](#0-1) 

The inconsistency is only detected much later in `SignableTransaction::multisig`, which returns `None` when the offset-derived script does not equal the prevout script. [3](#0-2) 

This is analogous to the missing `deadline` finding: required semantic data needed for the operation to succeed is absent from validation. Here, deserialization omits the required binding between the offset and the received output’s script, so the object can represent a receipt that can never be spent.

### Impact Explanation
An attacker able to provide serialized `ReceivedOutput` data can cause the wallet to report arbitrary outputs as received and spendable. Those outputs may belong to unrelated Taproot keys, and signing setup will fail because the claimed offset does not derive their `script_pubkey`.

Depending on the caller’s handling, this can poison wallet state, cause unavailable/invalid transactions to be attempted, or misreport funds received when they are not spendable.

### Likelihood Explanation
The attack only requires supplying malformed bytes to the public `ReceivedOutput::read` API. No validator key, private key, peer privilege, or consensus failure is needed.

The impact is bounded because `SignableTransaction::multisig` later rejects the mismatched output instead of producing a signed invalid transaction. This makes the issue a wallet-integrity / availability issue rather than direct theft.

### Recommendation
Change `ReceivedOutput::read` to authenticate the offset against a known wallet key, for example by accepting the scanner’s base `ProjectivePoint` and checking that the derived P2TR script equals `output.script_pubkey`.

If the base key cannot be supplied during deserialization, do not expose untrusted deserialization as construction of a spendable `ReceivedOutput`; deserialize it into an unverified representation and only convert it after scanner/key validation.

### Proof of Concept
```rust
// Conceptual PoC: construct an unrelated P2TR output, pair it with any
// scalar offset, and deserialize it as a supposedly spendable output.

let offset = Scalar::ZERO;
let unrelated_output = TxOut {
    value: Amount::from_sat(100_000),
    script_pubkey: attacker_controlled_p2tr_script,
};
let outpoint = OutPoint::new(attacker_txid, 0);

let mut bytes = Vec::new();
bytes.extend(offset.to_bytes());
bytes.extend(serialize(&unrelated_output));
bytes.extend(serialize(&outpoint));

// Succeeds despite the offset not deriving unrelated_output.script_pubkey.
let output = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();

// Later, signing setup rejects it:
assert!(SignableTransaction::new(vec![output], &payments, None, None, fee)
    .unwrap()
    .multisig(&wallet_keys)
    .is_none());
```
