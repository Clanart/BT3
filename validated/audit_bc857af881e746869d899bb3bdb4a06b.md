### Title
Unfinalized `deposit_blockhash` Used as Kickoff-UTXO Seed Allows Bitcoin Reorg to Permanently Invalidate All Pre-Signed Bridge Transactions — (`File: core/src/verifier.rs`, `core/src/builder/transaction/sign.rs`)

---

### Summary

`is_deposit_valid()` accepts a deposit with a single confirmation (no finality-depth check). The `deposit_blockhash` of that single-confirmation block is then used as the entropy seed in `get_kickoff_utxos_to_sign()` to deterministically select which kickoff UTXOs all verifiers and operators sign. A Bitcoin reorg that re-mines the deposit transaction into a different block changes the blockhash, producing a completely different kickoff-UTXO index set. Every pre-signed kickoff, challenge, payout, and reimbursement transaction becomes invalid. BTC already moved to the vault is permanently locked.

---

### Finding Description

**Step 1 — Deposit accepted with 1 confirmation.**

`is_deposit_valid()` checks only that the transaction has a `blockhash` (i.e., is confirmed) and that its block height is ≥ `start_height`. There is no check against `finality_depth`. [1](#0-0) 

**Step 2 — `deposit_blockhash` is the sole entropy source for kickoff-UTXO selection.**

`get_kickoff_utxos_to_sign()` hashes `[op_xonly_pk ‖ deposit_blockhash ‖ deposit_txid ‖ vout]` to seed a ChaCha12 RNG that shuffles and selects the subset of kickoff UTXOs that every actor must sign. A one-bit change in `deposit_blockhash` produces a completely different index set. [2](#0-1) 

**Step 3 — Every actor fetches `deposit_blockhash` independently from its own Bitcoin node.**

The aggregator, each verifier (in both `deposit_sign` and `deposit_finalize`), and each operator all call `get_blockhash_of_tx()` independently at different points in time during the multi-step signing ceremony. [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

**Step 4 — `deposit_blockhash` propagates into every protocol sighash.**

Both `create_nofn_sighash_stream` and `create_operator_sighash_stream` receive `deposit_blockhash` and pass it to `get_kickoff_utxos_to_sign()` before generating the full sighash stream for all kickoff, challenge, payout, and reimbursement transactions. [7](#0-6) [8](#0-7) 

---

### Impact Explanation

**Scenario (concrete):**

1. User sends BTC to the deposit address; the transaction is mined in block B₁ (blockhash H₁, 1 confirmation).
2. Aggregator calls `new_deposit`. All verifiers pass `is_deposit_valid()` (1 confirmation is sufficient). The full MuSig2 signing ceremony completes; all kickoff/challenge/payout signatures are stored in the DB keyed to the kickoff-UTXO indices derived from H₁.
3. The aggregator broadcasts the move-to-vault transaction; it is mined. BTC is now in the bridge vault.
4. A Bitcoin reorg of depth ≥ 1 occurs. The deposit transaction is re-mined in block B₂ (blockhash H₂ ≠ H₁). The move-to-vault transaction is also re-mined (same txid, still valid — it spends the same UTXO).
5. `get_kickoff_utxos_to_sign(H₂, …)` now returns a different index set. Every pre-signed kickoff, challenge, payout, and reimbursement transaction is cryptographically invalid for the new index set.
6. The operator cannot initiate a valid kickoff (wrong UTXO indices). Verifiers cannot challenge. The BTC in the vault has no reachable withdrawal path. It is permanently locked.

**Why re-processing does not automatically fix it:** `insert_deposit_data_if_not_exists` stores deposit data keyed by outpoint (not blockhash). If the aggregator retries `new_deposit`, verifiers will fetch H₂ and sign a new index set — but the operator already holds signatures for H₁ and the DB state is inconsistent. There is no protocol-level mechanism to atomically invalidate and replace the old signatures.

**Severity:** Critical/High — permanent lock of bridged BTC with no user recovery path (the deposit UTXO is already spent by the move-tx; the timelock recovery path is gone).

---

### Likelihood Explanation

Bitcoin reorgs of 1–2 blocks occur on mainnet with non-negligible frequency (several times per year). The deposit validation deliberately accepts 1-confirmation deposits. Any reorg that touches the deposit block after the signing ceremony completes triggers the bug. No privileged access is required; the attacker is the Bitcoin network itself (or a miner).

---

### Recommendation

Add a finality-depth confirmation check inside `is_deposit_valid()`, mirroring the check already used by `BitcoinSyncer` and `ProtocolParamset::is_block_finalized()`:

```rust
// After retrieving block_height:
let chain_tip = self.rpc.get_current_chain_height().await?;
if !self.config.protocol_paramset().is_block_finalized(block_height as u32, chain_tip) {
    return Err(BridgeError::InvalidDeposit(format!(
        "Deposit not yet finalized: height {block_height}, tip {chain_tip}, \
         required depth {}",
        self.config.protocol_paramset().finality_depth
    )));
}
```

This ensures the `deposit_blockhash` is immutable (within the finality guarantee) before it is used as the kickoff-UTXO seed, eliminating the reorg window. [1](#0-0) [9](#0-8) 

---

### Proof of Concept

```
1. Mine deposit tx → block B1 (1 confirmation, blockhash H1).
2. Call aggregator.new_deposit(deposit_outpoint).
   → is_deposit_valid() passes (1 confirmation ≥ start_height).
   → get_kickoff_utxos_to_sign(H1, op_pk, outpoint) → indices [3, 7].
   → Signing ceremony completes; all sigs stored for indices [3, 7].
3. aggregator.send_move_to_vault_tx() → move-tx mined. BTC in vault.
4. Invalidate block B1 (regtest: bitcoin-cli invalidateblock <B1_hash>).
   → Bitcoin re-mines deposit tx in block B2 (blockhash H2 ≠ H1).
   → Move-tx also re-mined (same txid).
5. get_kickoff_utxos_to_sign(H2, op_pk, outpoint) → indices [1, 5].
6. Operator attempts kickoff using index 3 (signed) → script path fails.
   Operator attempts kickoff using index 1 (new correct) → no verifier sig exists.
7. No valid kickoff can be initiated. BTC permanently locked in vault.
```

```rust
pub fn get_kickoff_utxos_to_sign(
    paramset: &'static ProtocolParamset,
    op_xonly_pk: XOnlyPublicKey,
    deposit_blockhash: BlockHash,
    deposit_outpoint: bitcoin::OutPoint,
) -> Vec<usize> {
    let deposit_data = [
        op_xonly_pk.serialize().to_vec(),
        deposit_blockhash.to_byte_array().to_vec(),
        deposit_outpoint.txid.to_byte_array().to_vec(),
        deposit_outpoint.vout.to_le_bytes().to_vec(),
    ]
    .concat();

    let seed = bitcoin::hashes::sha256d::Hash::hash(&deposit_data).to_byte_array();
    let mut rng = ChaCha12Rng::from_seed(seed);

    let mut numbers: Vec<usize> = (0..paramset.num_kickoffs_per_round).collect();
    numbers.shuffle(&mut rng);

    numbers
        .into_iter()
        .take(paramset.num_signed_kickoffs)
        .collect()
}
```

```rust
    /// Checks if a block is finalized. In clementine and citrea, finality depth means the amount of confirmations needed for a block to be considered finalized.
    /// The chain tip has 1 confirmation.
    pub fn is_block_finalized(&self, block_height: u32, chain_tip_height: u32) -> bool {
        if block_height > chain_tip_height {
            return false;
        }

        chain_tip_height - block_height + 1 >= self.finality_depth
    }
```
