### Title
Silent commit corruption via stale line-selection replay against a freshly re-fetched diff in partial commits - (File: `app/src/lib/git/apply.ts`)

### Summary
`app/src/lib/stores/updates/changes-state.ts` shows that Desktop is *aware* that "the diff might have changed dramatically since last we loaded it" and updates the set of `selectableLines` accordingly when the working-directory diff is refreshed [1](#0-0) . However, this reconciliation only happens for the diff shown in the Changes UI. When a partial commit is actually built, `applyPatchToIndex` re-fetches a brand-new `getWorkingDirectoryDiff` from disk and feeds it straight into `formatPatch` together with the **old** `file.selection` object, with no re-validation step comparable to the one used for on-screen display [2](#0-1) .

### Finding Description
`DiffSelection` is a pure "set of absolute line indices" data structure; it has no knowledge of file content, only of `unifiedDiffStart`-relative line numbers computed against whatever diff/hunks existed at the moment the user clicked check-boxes [3](#0-2) . The UI computes and stores these indices via `_changeFileLineSelection` / `onLineNumberCheckedChanged`, which call `selection.withLineSelection(lineIndex, ...)` against the hunks currently rendered [4](#0-3) [5](#0-4) .

When the user commits, `stageFiles` → `applyPatchToIndex` is invoked. Inside `applyPatchToIndex`, the diff used to build the patch is **not** the diff object the user reviewed and checked boxes against — it's fetched fresh from disk right before staging: `const diff = await getWorkingDirectoryDiff(repository, file)` [6](#0-5) . `formatPatch` then walks this fresh diff's hunks and, for every changed line, calls `file.selection.isSelected(absoluteIndex)` using `hunk.unifiedDiffStart + lineIndex` from the *new* diff [7](#0-6) .

If the on-disk file content shifts between the moment the user made line selections and the moment the commit is executed (hunks add/remove lines, shifting `unifiedDiffStart` values for later hunks), the old `divergingLines` index set from `DiffSelection` will now silently map onto different, unrelated lines in the newly-fetched diff. Unlike the code path used to keep the *UI* diff consistent — which explicitly recomputes `selectableLines` and drops selections for lines that "no longer exist" whenever a fresh diff is loaded for display [8](#0-7)  — the commit-time code path in `apply.ts`/`patch-formatter.ts` has no equivalent reconciliation: it blindly trusts that the index numbering of the newly-fetched diff still matches the diff the user last saw.

This is structurally identical to the reported smart-contract bug class: a value (there, `wrapped1155.balanceOf(msg.sender)`; here, the diff/hunk structure) is re-read at execution time inside a loop and used together with state (there, an implicit "amount to transfer"; here, `DiffSelection`'s absolute indices) that was fixed at an earlier point in time, with the code failing to verify the two are still consistent.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A user who deliberately partially-stages a file (e.g., "include only these 3 lines in this commit, leave the rest for later") can end up committing lines they never selected/reviewed and/or omitting lines they did select — without any error, warning, or diff mismatch shown to them. Because the check happens purely on integer line indices with no content verification, the resulting patch can `git apply --cached` cleanly (the new diff is internally consistent) while committing the wrong hunks relative to user intent. This can leak unreviewed/sensitive lines into a commit that's about to be pushed, or drop intended lines silently.

### Likelihood Explanation
Reaching the vulnerable window requires the working-directory file to change between the time the user reviews/selects lines and the time `_finishCommitCreation`/`stageFiles` actually run `applyPatchToIndex`. Concretely, this can happen with: files under active editor autosave/format-on-save, files touched by build-watchers or linters running against the open repository, or filters/normalizations (e.g. line-ending conversion) triggered as part of routine git operations while the Commit dialog is open. Because Desktop already explicitly guards the *display* path against exactly this kind of concurrent modification (see the "diff might have changed dramatically" comment) but not the *staging* path, this is a genuine and reachable gap rather than a purely theoretical race. That said, I could not find a scenario in this codebase where a remote/attacker-controlled git object (as opposed to local file activity) can reliably and deterministically trigger the intervening file modification without some cooperating local tooling already running — so the practical exploitability specifically from "attacker controls the cloned/fetched repo alone" is not fully established from the code alone, and should be validated dynamically.

### Recommendation
Before generating/applying the partial-commit patch in `applyPatchToIndex`, re-validate the stored `DiffSelection` against the freshly-fetched diff the same way `app-store.ts` does for the display path (recompute `selectableLines`/hunk boundaries and drop or renumber diverging lines that no longer correspond to the same content), or better, capture and reuse the exact diff object the user last reviewed (failing/erroring out if the working tree has changed) instead of re-fetching a new diff purely for staging purposes.

### Proof of Concept
1. Open a tracked file with several separated hunks of changes in Desktop's Changes view.
2. Select (check) specific lines only in the second hunk for a partial commit, leaving the commit dialog open before pressing "Commit".
3. While the dialog is open, cause the file's earlier hunk(s) to change size (e.g., another process/editor with autosave/format-on-save adds or removes lines above the second hunk), shifting later hunks' `unifiedDiffStart`.
4. Click "Commit". `applyPatchToIndex` re-fetches the diff (now with shifted hunk offsets) and applies the old `DiffSelection` indices against it via `formatPatch`, producing a patch that includes/excludes different lines than what was originally checked in the UI, with no warning to the user (verifiable by inspecting `git show --stat`/`git diff HEAD~1` after the commit against what was visibly checked in the UI).
