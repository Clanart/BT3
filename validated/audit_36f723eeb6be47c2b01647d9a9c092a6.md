### Title
Silent regex-error swallowing in blocking-rule evaluation causes fail-open bypass of user-defined command blocks - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
The Canto finding is about a function that can fail, is caught, and the error is logged but the failure-path return value is then implicitly trusted as "safe/zero" by downstream logic, rather than being explicitly neutralized. The closest reachable analog in this codebase is `RuleEngine._regex_match` in the `hookify` plugin, which evaluates user-authored blocking rules against tool calls (e.g. `Bash` commands) before they execute.

### Finding Description
`RuleEngine._regex_match` compiles and evaluates a rule's regex pattern against a candidate field (e.g. a Bash `command` string): [1](#0-0) 

When `re.compile`/`re.search` raises `re.error`, the exception is caught, logged to stderr, and the function returns `False` — i.e., "condition did not match." This return value flows straight into `_check_condition`, which is invoked from `_rule_matches`: [2](#0-1) [3](#0-2) 

`evaluate_rules` treats a rule that fails to match as simply "not blocking," and if no other rule matches, the operation proceeds with an empty response (`{}`), i.e., the tool call is allowed: [4](#0-3) 

Just as in the Canto report — where an error from `TradeInputForExactOutput` is logged but the returned `swappedAmount` is still trusted as if the operation had cleanly failed with a zero value — here an error from the regex engine is logged but the boolean "no match" result is trusted as if the rule legitimately did not apply, rather than being flagged as "evaluation failed, block/warn defensively." A condition-evaluation failure is silently coerced into "rule passes / operation allowed," which is the opposite of fail-safe behavior for a **blocking** security rule.

This is compounded by the top-level `pretooluse.py` hook wrapper, which wraps the entire evaluation in a broad `try/except` that also fails open on any error and unconditionally `sys.exit(0)`s so the tool call is never blocked due to a hook error: [5](#0-4) 

### Impact Explanation
`hookify` is explicitly designed to let a user define `block` rules (e.g. to prevent dangerous `rm -rf`-style commands) via `.claude/hookify.*.local.md` files, which are then enforced as `PreToolUse` guards before Bash/Edit/Write/MultiEdit execute. If a blocking rule's regex pattern is malformed (invalid syntax) — whether due to an authoring mistake or a pattern built dynamically from user/template input — `_regex_match` silently swallows the `re.error` and returns "no match," causing the intended block to never fire, and the dangerous command/file edit is executed instead of denied. This is a genuine unprivileged-user-facing "hook bypass" / "command approval bypass" analog: the same trust-boundary category as the referenced report (an error path silently produces a value that downstream code treats as a legitimate "safe" outcome, defeating the protection the code was meant to provide).

### Likelihood Explanation
Likelihood is moderate-to-low: it requires a rule author (or a rule-generation flow) to supply an invalid regex pattern for a `block` rule. This is plausible in practice since hookify rules are hand-authored markdown/YAML-like configs and there is no validation step shown compiling patterns before they're used to gate tool execution; a single typo (e.g. unbalanced parenthesis) in a "protect against dangerous commands" rule silently disables that specific protection with no user-visible failure indication (only an stderr print, which is not surfaced as a warning to the operator through the hook's JSON output).

### Recommendation
- In `_regex_match`, do not return `False` on `re.error`. Instead, surface the failure distinctly (e.g., raise, or return a sentinel), and have `_check_condition`/`_rule_matches` treat a condition-evaluation failure as "cannot verify" — for `block` rules this should default to blocking (fail-closed) or at minimum emit a visible `systemMessage` warning that the rule failed to evaluate, rather than silently treating it as "rule did not match."
- Validate/compile all rule patterns at load time (`load_rules`) and reject or warn about invalid patterns before they are silently used at enforcement time.
- Reconsider the "always allow on any hook error" behavior in `plugins/hookify/hooks/pretooluse.py` for `block`-type rules specifically, since it converts any internal bug into a systemic bypass of user-configured protections.

### Proof of Concept
1. Author a hookify blocking rule targeting Bash commands with a deliberately malformed regex, e.g. pattern `rm\s+-rf(` (unbalanced parenthesis), action `block`.
2. Invoke a `Bash` tool call with a command matching the intended dangerous pattern, e.g. `rm -rf /important/data`.
3. `RuleEngine._rule_matches` → `_check_condition` → `_regex_match` calls `compile_regex("rm\\s+-rf(")`, which raises `re.error: missing ), unterminated subpattern`.
4. `_regex_match` catches the exception, prints a warning to stderr only, and returns `False`.
5. `_check_condition` returns `False`, so `_rule_matches` returns `False`; the rule is excluded from `blocking_rules`.
6. `evaluate_rules` returns `{}` (no block, no warning), and `pretooluse.py` prints `{}` and exits 0 — the dangerous `rm -rf` command executes unblocked, despite a `block` rule having been configured specifically to prevent it.

```python
    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
```
