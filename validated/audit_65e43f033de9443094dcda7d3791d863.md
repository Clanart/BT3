### Title
`stSTXbtc`/`zstSTXbtc` valued using the STX price feed instead of the BTC price feed - (`File: mainnet/contracts/utility/v0-1-data.clar`)

### Summary
The reported bug class (an asset that should track BTC's USD value being priced through the wrong feed) reproduces in this codebase, but not via a Chainlink BTC/USD fallback — it reproduces via a hardcoded asset-ID switch statement that resolves `stSTXbtc` and `zstSTXbtc` prices using the `PYTH-STX` (STX/USD) feed identifier instead of `PYTH-BTC` (BTC/USD), even though the surrounding comments explicitly label these assets as BTC-denominated.

### Finding Description
`get-asset-price` in `mainnet/contracts/utility/v0-1-data.clar` dispatches on asset ID to select the correct Pyth feed for each collateral/debt asset: [1](#0-0) 

For `stSTXbtc`, which the inline comment itself identifies as "BTC price (liquid staked STX with BTC yield)," the code calls `(get-pyth-price PYTH-STX)` instead of `(get-pyth-price PYTH-BTC)`: [2](#0-1) 

The same wrong-feed selection is repeated for the wrapped vault token `zstSTXbtc`, where a variable explicitly named `btc-price` is actually bound to the STX/USD Pyth result before being combined with the vault's liquidity index: [3](#0-2) 

`PYTH-STX` and `PYTH-BTC` are distinct, correctly defined constants elsewhere in the same file, so this is not a third-party oracle data problem or a registry misconfiguration — it is a code-level asset-to-feed binding error inside the pricing dispatcher itself: [4](#0-3) 

This is the same code pattern in the mirrored `local-testing` build (`get-asset-price` in `protocol-data.clar`), confirming the bug is systemic to the price-dispatch logic rather than an isolated typo in one deployment artifact: [5](#0-4) 

### Impact Explanation
Since BTC/USD trades orders of magnitude higher than STX/USD, substituting the STX feed for the BTC feed causes `stSTXbtc`/`zstSTXbtc` to be valued at a small fraction of their true USD worth wherever this dispatcher's output feeds into collateral or debt USD accounting (`sum-collateral-usd`/`sum-debt-usd` helpers in the same file, which call `get-asset-price` directly): [6](#0-5) 

If `stSTXbtc`/`zstSTXbtc` can be borrowed as a debt asset, a user's real BTC-denominated debt is reported to the system as a tiny STX-priced figure, letting them extract far more value in other assets than their true debt supports — an under-collateralization vector that manifests as accumulating bad debt/protocol insolvency, the same end-state as the reported WBTC depeg scenario. If instead it is only used as collateral, the direction of error is opposite (severe undervaluation, hurting the depositor rather than the protocol) — so the exploitable direction depends on which side of the ledger consumes this figure, which I could not fully confirm without deeper access to the debt/collateral asset registration tables.

### Likelihood Explanation
This triggers deterministically any time `get-asset-price` is invoked for `aid == stSTXbtc` or `aid == zstSTXbtc` — no external price manipulation or depeg event is required, unlike the original report; it is a straight code defect that always returns a mispriced value for these two asset IDs.

### Recommendation
Fix the feed selection for `stSTXbtc` and `zstSTXbtc` in `get-asset-price` (and its mirrored copy in `protocol-data.clar`) to use `PYTH-BTC` instead of `PYTH-STX`, matching the inline comments' stated intent, and add a regression test asserting `get-asset-price(stSTXbtc)` tracks the BTC feed rather than the STX feed.

### Proof of Concept
Not independently reproduced with a runnable test in this session; the defect is demonstrated statically by comparing the comment/intent ("BTC price") against the actual constant used (`PYTH-STX`) at [7](#0-6) . A concrete PoC would call `get-asset-price` (or its callers `sum-collateral-usd`/`sum-debt-usd`) for `aid = stSTXbtc`/`zstSTXbtc` with distinct mock STX and BTC Pyth prices and assert the returned value equals the STX price rather than the BTC price.
