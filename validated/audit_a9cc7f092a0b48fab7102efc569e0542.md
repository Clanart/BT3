### Title
Dust outputs received via `Scanner` are counted as spendable balance yet cost more in fees to spend than their value, blocking/erring withdrawal transaction construction - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` reports any transaction output paying to a registered Serai `script_pubkey` as a `ReceivedOutput`, with no check on the output's value. `SignableTransaction::new` then treats `sum(inputs)` as fully spendable toward `payment_sat + needed_fee`, even though each Taproot input adds ~57.5 vbytes of fee cost. An unprivileged attacker can send dust-value outputs (≥ 546 sat, standard-relayable) to the Serai key; these are reported as received funds, but spending them costs more in fees than they contribute, reducing the wallet's effective balance below its reported NAV and causing withdrawal transactions to fail `NotEnoughFunds` or silently burn the difference into fees.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs`, `scan_transaction` accepts any output whose `script_pubkey` matches a registered script, regardless of `output.value`: [1](#0-0) 

There is no minimum-value filter, so an output of 546 sat (the dust floor) is reported identically to one worth 1 BTC.

In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` sums all input values into `input_sat` and checks `input_sat < (payment_sat + needed_fee)`: [2](#0-1) [3](#0-2) 

`calculate_weight_vbytes` correctly accounts for each input's weight (~230 WU / ~57.5 vbytes for a key-path Taproot input with a 64-byte witness signature): [4](#0-3) 

But the accounting conflates "value held" with "net spendable value." At any fee rate above ~9.5 sat/vbyte, a 546-sat input contributes less than the fee it adds (546 / 57.5 ≈ 9.5). The transaction builder has no notion of input value vs. input cost, so:

- Reported/vaulted balance (`sum(ReceivedOutput.value)`) overstates spendable balance.
- A withdrawal sized to the full reported balance fails `NotEnoughFunds` even though the "NAV" claims sufficient funds — the direct analog of the LMPVault `noNavDecrease` revert: a check that doesn't account for real per-operation losses (here, per-input fee cost instead of swap slippage).
- If the withdrawal does succeed by shrinking payments, the dust inputs are consumed anyway, and the shortfall is silently absorbed into the transaction fee (`fee() = sum(inputs) - sum(outputs)` at `send.rs:138-141`), permanently burning vault value.

### Impact Explanation
An attacker can repeatedly dust the Serai Bitcoin address with cheap 546-sat outputs. The Scanner reports them as received funds; the wallet's only spend path (`SignableTransaction` + `TransactionMachine`) must include them as inputs to recover them, each input costing more in fee than it returns at moderate fee rates. This either (a) causes withdrawal transactions that appear fundable to fail `NotEnoughFunds`, blocking exits, or (b) drains treasury value into miner fees proportional to the number of dust inputs. This is a griefing/economic DoS reachable entirely with public on-chain data — the attacker only needs to send ordinary Bitcoin transactions to a publicly known address.

### Likelihood Explanation
Sending a standard dust output is trivially cheap (546 sat + fee) and requires no privileges, no validator collusion, and no malformed encodings. The Serai deposit address and its registered offsets are publicly derivable from the group key (`Scanner::new` / `register_offset`). Any observer of the chain can compute the P2TR script and fund it. The trigger condition — fee_per_vbyte × ~57.5 > dust value — holds at common fee rates, and coin-selection code has no mechanism to reject uneconomical inputs.

### Recommendation
- In `Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs`), filter out outputs whose value is below a configurable economical-spend threshold (e.g., value < `fee_per_vbyte * INPUT_VBYTES`, or at minimum `<= DUST`), or tag `ReceivedOutput` with its spend-cost so downstream selection can exclude uneconomical inputs.
- In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`), select/drop inputs whose marginal fee contribution exceeds their value rather than unconditionally including all provided inputs, so reported balance converges to net spendable balance — the analog of allowing NAV to decrease by the expected operational cost rather than reverting.

### Proof of Concept
1. Observe the Serai group key `K`; compute `script = p2tr_script_buf(tweaked K)` (as `Scanner::new` does at `mod.rs:164`).
2. Broadcast a Bitcoin transaction paying `script` with value 546 sat. It confirms (546 sat is standard).
3. `Scanner::scan_transaction` returns `ReceivedOutput { offset: ZERO, value: 546, ... }` — Serai books +546 sat.
4. Attempt a withdrawal spending this input at `fee_per_vbyte = 50`. The input adds ~57.5 vbytes → ~2875 sat of needed fee for a 546-sat contribution.
5. In `SignableTransaction::new`, `input_sat` includes the 546, but `needed_fee` grew by ~2875 because of the extra input: a payment equal to the previously reported balance now fails `NotEnoughFunds`, or succeeds only after shrinking the payment, with the dust input's cost absorbed as fee — the funds were reported received but are not spendable at face value.

Note: I was unable to fully verify the higher-level coin-selection/integration path (which entity chooses `inputs` passed to `SignableTransaction::new`) within the available iterations; the finding is strongest where callers pass all scanned outputs, which is the natural usage given `Scanner` returns them unconditionally.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
