## Finding

**Note on completeness:** I traced the call chain from `_openShell` (dispatcher) into the platform-specific `launch()` implementations. `darwin.ts` and `linux.ts` use `spawn()` with an argument array and no `shell: true`, which is safe against argument-injection style attacks. `win32.ts`, however, uses `spawn(..., { shell: true, ... })` for every terminal it supports, which on Windows means Node.js builds and hands the command line to `cmd.exe /d /s /c`. I was not able to fully trace every caller of `sanitizeCloneName()` (e.g. the exact wiring in `clone-generic-repository.tsx`) due to remaining tool budget, so the "attacker controls the local folder name via an arbitrary clone URL" step should be double-checked in a live session, but the sanitizer itself (`app/src/lib/remote-parsing.ts`) is confirmed to only strip path separators/traversal, not shell metacharacters.

### Title
Command injection via `cmd.exe`-unsafe quote nesting in the Cygwin "Open in shell" launcher - (File: app/src/lib/shells/win32.ts)

### Summary
`launch()` in `app/src/lib/shells/win32.ts` builds the Cygwin shell command as a single string argument that nests double quotes for the sake of the *bash* `cygpath` invocation, then passes it to Node's `spawn` with `shell: true`. On Windows, `shell: true` routes the whole command line through `cmd.exe`, which does its own independent double-quote parity tracking. The nested quotes cause `cmd.exe` to see the substituted repository `path` as sitting in an *unquoted* region of the command line, even though the string was written to look "quoted" for bash's benefit. Any `cmd.exe` metacharacter (`&`, `|`, `^`, `%`, `<`, `>`) present in that path is therefore interpreted by `cmd.exe` itself, not passed through literally — a classic Windows command-injection primitive, structurally the same broken invariant as the reported `pm2 install` tar filename issue (attacker-influenced string reaching a shell without metacharacter sanitisation).

### Finding Description
The vulnerable code: [1](#0-0) 

```ts
case Shell.Cygwin:
  const cygwinPath = `"${foundShell.path}"`
  return spawn(
    cygwinPath,
    [`/bin/sh -lc 'cd "$(cygpath "${path}")"; exec bash'`],
    { shell: true, cwd: path }
  )
```

Counting the literal `"` characters that precede the `${path}` interpolation inside the array element: `'cd "$(cygpath "` contains exactly two double quotes. Because `cmd.exe`'s command-line parser toggles "in-quotes" state on each `"` it encounters (regardless of nesting intent for the target program), an *even* number of preceding quotes means `path` lands in a region `cmd.exe` considers unquoted. All the sibling shells (`GitBash`, `Hyper`, `Alacritty`, `PowerShell`, `Warp`, etc.) wrap `path` in a single matching pair of quotes, e.g. `--cd="${path}"` [2](#0-1) , keeping `path` inside one quoted span — Cygwin's extra internal quote for the `cygpath` shell-substitution breaks that invariant.

The value substituted, `path`, is the full local repository path, whose leaf directory name is derived from the remote URL via `sanitizeCloneName()`: [3](#0-2) 

This function only strips path separators (`/`, `\`, `:`) and rejects `.`/`..`-only traversal segments; it performs **no filtering of shell metacharacters** such as `&`, `%`, `^`, `!`, `(`, `)`, backticks, or quotes. All of these are legal in Windows file/directory names (only `< > : " / \ | ? *` are actually forbidden by NTFS/Win32), so a crafted directory name containing `&calc.exe&` (for example) would survive both the filesystem and `sanitizeCloneName()` intact.

### Impact Explanation
If a user clones a repository from an arbitrary/generic URL (not restricted to GitHub.com's strict `[\w\-.]` repo-name rules, e.g. via the "URL" tab of the Clone dialog) whose last path segment contains `cmd.exe` metacharacters, the local clone directory name will contain those characters. When the user later selects "Open in Cygwin" from the repository context menu (`generateRepositoryListContextMenu` → `onOpenInShell` → `app.tsx: openInShell` → `dispatcher.openShell` → `AppStore._openShell` → `launchShell` → `win32.ts: launch`) [4](#0-3) [5](#0-4) , the crafted path is substituted into the unquoted region of the `cmd.exe` command line, resulting in arbitrary command execution in the context of the Desktop user (no sandboxing — `cmd.exe`/Cygwin run as the logged-in user).

### Likelihood Explanation
Moderate-to-low. It requires: (1) Cygwin to be installed and either the user's selected default shell or explicitly chosen from the context menu, and (2) the victim to clone from an attacker-supplied non-GitHub URL whose basename contains `cmd.exe` metacharacters and to subsequently use "Open in Shell" on that repository. This is a plausible but non-trivial social-engineering-light path (an attacker can advertise a "clone this URL" link) — it does not require local/physical access, admin rights, or pre-existing malware, satisfying the report's "remote/attacker-controlled repository or URL" bar.

### Recommendation
- Do not build shell-quoted strings by hand for `spawn(..., { shell: true })`. For the Cygwin case, avoid nesting an inner `"..."` substitution for `cygpath`; instead pass `path` as a separate argv element or perform the `cygpath` conversion out-of-band (e.g., resolve/convert in Node before constructing the string), so no interpolation occurs inside a quote-parity-sensitive fragment.
- More generally, apply `cmdEscape`/proper quoting (the same escaping already implemented in `app/src/lib/hooks/shell-escape.ts`) to every path interpolated into a `shell: true` spawn call on Windows, rather than manual `"${path}"` wrapping.
- Extend `sanitizeCloneName()` (or add a defense-in-depth check before using a folder name to open a shell) to reject/escape `cmd.exe`-significant characters (`& | ^ % < >` and quotes) even though they're legal NTFS filename characters.

### Proof of Concept
1. Host a git repository at a URL whose final path segment is: `repo&calc.exe&.git` (e.g. `https://example.com/repo&calc.exe&.git`), served by a generic (non-GitHub) git server or via `git daemon`.
2. In GitHub Desktop, use "Clone Repository" → "URL" tab and clone this URL; the resulting local folder is named `repo&calc.exe&` after `sanitizeCloneName()` processing (only `.git` suffix stripped, no metacharacter filtering).
3. With Cygwin installed and set as the shell (or selected via the repository context menu "Open in Cygwin"), right-click the repository in the repository list and choose "Open in Cygwin".
4. `win32.ts`'s `launch()` builds: `spawn('"<cygwin-path>"', ["/bin/sh -lc 'cd \"$(cygpath \"C:\\...\\repo&calc.exe&\")\"; exec bash'"], { shell: true })`. Because of the quote-parity break described above, `cmd.exe` treats `&calc.exe&` as a command separator and launches `calc.exe` (or any attacker-chosen command) before/alongside the intended Cygwin invocation.

```typescript
export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}
```
