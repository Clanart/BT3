### Title
Gasless swap validation relies on live, donation-manipulable DEX (Uniswap V2‑style) reserves as its "exchange rate" oracle - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The Umee report describes a class of bugs where an invariant ("the exchange rate can change only through a designated accrual mechanism") is silently violated because the value used to enforce that invariant (total token supply) can be altered out-of-band by a mechanism the module does not account for (IBC mint/burn via the bank keeper), letting an attacker manipulate the rate before it is read. The closest reachable analog in kaia is the gasless module's swap admission check, which enforces "fair exchange rate" for a subsidized gas swap using `GaslessSwapRouter.GetAmountIn`, a value derived from live AMM pool reserves that can be moved directly (donation/large swap) by any unprivileged sender in the same block, independent of the accrual/oracle mechanism the check assumes.

### Finding Description
`GaslessModule.checkBalanceForSwap` is the tx-pool-level validation used to admit a `GaslessSwapTx` into a bundle. It computes the "fair" `requiredAmountIn` for the declared `minAmountOut` by calling the router's price function: [1](#0-0) 

`routerContract.GetAmountIn(nil, token, minAmountOut)` is a stateful, on-chain view call into `GaslessSwapRouter`, which in turn is wired to a Uniswap‑V2‑style DEX (`dexAddress`, `factory`/`router` pair per token) as seen in the contract bindings: [2](#0-1) 

Uniswap‑V2‑style `getAmountsIn`/`getAmountsOut` derive price purely from the *instantaneous* reserve ratio of the token/WKAIA pair. That ratio is not an "accrual-only" invariant — it can be changed instantaneously by any account simply transferring (donating) tokens into the pair, or by executing a large swap immediately before the gasless swap is processed, exactly analogous to how Umee's `TotalUTokenSupply` assumed the bank supply could change only through interest accrual but could actually be altered by an out-of-band IBC mint/burn.

The check is only a point-in-time snapshot taken at tx-pool admission time (`GetCheckBalance`/`checkBalanceForSwap`): [3](#0-2) 

Because the block-building/bundle logic executes `LendTxGenerator → GaslessApproveTx → GaslessSwapTx` as an ordered bundle (per module docs) rather than atomically re-validating fair value at execution time against the same state used for admission, a sender who also controls (or times) a preceding transaction that shifts the pool reserves in the same block can cause the on-chain `swapForGas` execution to use a different (attacker-favorable) reserve state than what a naive observer expects, while still satisfying the router's own internal repayment checks (`minAmountOut >= amountRepay`) computed off the same manipulated reserves. [4](#0-3) 

### Impact Explanation
If an unprivileged sender can shift the DEX pool's reserves (via ordinary token transfer/donation to the pair or an adjacent swap) immediately before their own gasless swap executes in the same block, they can cause the gas-lending proposer to accept less real value (`amountIn` of `token`) than the fair market equivalent of the WKAIA that is disbursed and later reclaimed as `amountRepay`. This directly drains value from the block proposer/lender subsidizing gasless transactions — a concrete "unauthorized value movement" / fee-delegation abuse, matching the required impact bar (fee/gasless settlement theft).

### Likelihood Explanation
Medium. The attack requires the attacker to be able to move the specific token/WKAIA pool's reserves meaningfully within the same block as their gasless swap (feasible for low-liquidity or thinly traded gasless-eligible tokens, which the module explicitly supports via `AllowedTokens`/"all" configuration). It also depends on the `BalanceCheckLevel` configuration (`ShouldCheckSwapAmount`) being enabled but not being re-validated against a manipulation-resistant price source (e.g., TWAP) — the codebase shows no TWAP or slippage-protection beyond the instantaneous `GetAmountIn` read.

### Recommendation
- Use a manipulation-resistant price reference (TWAP, or a floor/ceiling derived from multiple blocks) instead of a single instantaneous `GetAmountIn` call in `checkBalanceForSwap`, or re-check the amount using reserves snapshotted before the bundle's transactions are allowed to alter them.
- Enforce that no non-bundle transaction from the same sender (or affecting the same pool) can execute between reserve read and swap execution within the same block/bundle.
- Consider bounding acceptable slippage/deviation between the pool price at tx admission and at execution, rejecting bundles where the deviation exceeds a safe threshold.

### Proof of Concept
Conceptual (not executed, no filesystem/terminal access here):
1. Attacker deploys/uses a low-liquidity token registered as gasless-eligible (`AllowedTokens` includes it or is set to "all").
2. In block N, attacker sends an ordinary ERC20 transfer of `token` directly into the Uniswap-V2 pair (or performs a swap) to skew the token/WKAIA reserve ratio in their favor.
3. In the same block, attacker's `GaslessApproveTx`+`GaslessSwapTx` bundle is processed; `checkBalanceForSwap` calls `GetAmountIn` against the now-skewed reserves, computing an artificially low `requiredAmountIn` for the declared `minAmountOut`.
4. `swapForGas` executes using the same skewed reserves, letting the attacker repay `amountRepay` in WKAIA to the proposer while surrendering less real economic value in `token` than fair-market price, effectively underpaying for lent gas. [1](#0-0) [5](#0-4)

func (g *GaslessModule) GetCheckBalance() func(tx *types.Transaction) error {
	return func(tx *types.Transaction) error {
		if approveArgs, ok := decodeApproveTx(tx, g.signer); ok {
			return g.checkBalanceForApprove(approveArgs)
		}
		if swapArgs, ok := decodeSwapTx(tx, g.signer); ok {
			return g.checkBalanceForSwap(swapArgs, tx.Nonce())
		}
		return errors.New("not a gasless transaction") // should not happen because IsModuleTx is called before GetCheckBalance
	}
}

### Block building rules

Upon detection of GaslessTxs, the following logics are executed:

- Per sender, if exists, GaslessApproveTx is relocated before GaslessSwapTx.
- LendTxGenerator is prepended before GaslessApproveTx.
- A new bundle is generated which contain either `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]` or `[LendTxGenerator, GaslessSwapTx]`
- If the bundle has conflict with any previous bundles, it is excluded from the returned bundle list.
