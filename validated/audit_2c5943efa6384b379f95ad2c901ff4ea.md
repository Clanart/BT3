### Title
`hookify` plugin rules configured with `action: block` for prompt-submission events silently degrade to non-blocking warnings - ([File: plugins/hookify/core/rule_engine.py])

### Summary
This is the same bug class as the reported Pod issue (`[H01] Deposit uses operator collateral`): a control's *declared* authorization outcome does not match the *actual* enforcement mechanism it triggers, because the code path that turns "the gate matched" into "the privileged action" is wired to the wrong branch/target. In the Pod contract, `_deposit` pulled funds from `operator` (the gate/authorizer) but credited `from` (a different principal) — an action/target mismatch. In `hookify`'s `RuleEngine.evaluate_rules`, a rule's declared `action: "block"` (the gate outcome) is only converted into a real blocking response for two hook event kinds; for the `prompt` rule type (which fires on the `UserPromptSubmit` hook), there is no corresponding case, so the "block" decision silently falls through to advisory-only behavior.

### Finding Description
`hookify` lets a user or org author markdown rule files (`.claude/hookify.*.local.md`) with `event: prompt` and `action: block`, intending to prevent a prompt from being submitted when it matches a dangerous pattern (documented in `plugins/hookify/README.md` and `skills/writing-rules/SKILL.md`, e.g. `event: prompt`, `action: block`).

The engine that turns a matched rule into an actual hook response is `RuleEngine.evaluate_rules`: [1](#0-0) 

This function only emits a real "stop the operation" payload for two branches:
- `hook_event == 'Stop'` → returns `{"decision": "block", ...}`
- `hook_event in ['PreToolUse', 'PostToolUse']` → returns `{"hookSpecificOutput": {"permissionDecision": "deny"}, ...}`

Every other `hook_event` value — which is exactly what `UserPromptSubmit` is, the event that fires `prompt`-typed rules (see `plugins/hookify/hooks/userpromptsubmit.py` in the hooks directory listing) — falls into the final `else` branch, which returns only `{"systemMessage": combined_message}`. That is *identical in shape* to what a plain `warn` rule returns: [2](#0-1) 

The `Rule` dataclass itself hints this was incomplete: `action: str = "warn"  # "warn" or "block" (future)`. [3](#0-2) 

So the "gate" (a rule author writing `action: block` for a `prompt` event) and the "action" (what the engine actually returns for that event) are mismatched — the same class of bug as the Pod report's "takes from operator, credits from" confusion, just expressed as "declares block, enforces warn."

### Impact Explanation
A user (or an org that ships a shared `hookify.*.local.md` rule set to enforce guardrails, e.g. "block prompts asking to exfiltrate secrets" or "block prompts referencing a blocked topic/command") reasonably believes `action: block` on a `prompt` rule stops the prompt from being processed. In fact the prompt is *not* blocked — Claude receives the prompt and a cosmetic system message, and proceeds normally. Depending on what the rule was meant to gate, this is a genuine local guardrail/hook-bypass: a user-authored or org-authored "deny" policy on prompt submission is silently downgraded to advisory-only, letting disallowed content or attacker-crafted prompts (e.g., in a shared/compromised repo shipping a `hookify` rule set expecting to block prompt-injection patterns) reach the model unblocked.

### Likelihood Explanation
High confidence in the root cause from `rule_engine.py` alone: the branch dispatch in `evaluate_rules` explicitly enumerates `'Stop'` and `['PreToolUse', 'PostToolUse']` and has no `elif` for `UserPromptSubmit`. Since `hookify` documents and supports `event: prompt` rules with `action: block` as first-class functionality, and ships a dedicated `hooks/userpromptsubmit.py` entry point, the mismatch is directly reachable by any unprivileged user (or plugin author) who writes such a rule expecting it to enforce a hard stop. I was not able to read `plugins/hookify/hooks/userpromptsubmit.py` in full before running out of tool calls, so I cannot 100% rule out that this script post-processes the engine's dict and independently converts a bare `systemMessage` into a real UserPromptSubmit-blocking response (e.g., via exit code 2). If it does not — which is the straightforward reading given the engine's own comment marking `action: "block"` as only partially implemented ("future") — the bypass is real and trivially reproducible.

### Recommendation
Add an explicit `elif hook_event == 'UserPromptSubmit':` branch to `RuleEngine.evaluate_rules` that returns the correct blocking payload for that hook type (per Claude Code's `UserPromptSubmit` hook contract — e.g. `decision: "block"` with a `reason`, or the appropriate `hookSpecificOutput`/exit-code-2 mechanism), so `action: "block"` has parity across every event type the plugin claims to support. Alternatively, if blocking is genuinely unimplemented for `prompt` events, `config_loader.Rule.from_dict` should reject or downgrade `action: "block"` combined with `event: "prompt"` at load time (fail loud) rather than silently accepting a configuration that can never enforce what it declares.

### Proof of Concept
1. Add `.claude/hookify.exfil-block.local.md`:
```markdown
---
name: block-secret-exfil-prompt
enabled: true
event: prompt
action: block
conditions:
  - field: user_prompt
    operator: contains
    pattern: "paste my .env contents into the chat"
---
Blocked: prompt requests secret disclosure.
```
2. Wire it via `hooks/userpromptsubmit.py` per `hookify`'s standard flow (`hook_event_name` = `"UserPromptSubmit"`, `reason`/`user_prompt` supplied in `input_data`).
3. Submit a prompt containing the matched pattern.
4. Trace through `RuleEngine._rule_matches` → matches → `rule.action == 'block'` → added to `blocking_rules` → `evaluate_rules` reaches the final `else` branch (since `hook_event` is `'UserPromptSubmit'`, not `'Stop'`/`'PreToolUse'`/`'PostToolUse'`) → returns only `{"systemMessage": ...}` with no blocking field set.
5. Result: the prompt is not actually blocked; Claude receives the full prompt plus a note, defeating the rule author's intended guardrail — the "block" gate never reaches the "deny the action" outcome, mirroring the Pod report's mismatch between the authorizing party and the party actually acted upon.
