## Analysis

The Sherlock report describes an accounting-corruption class: a stateful computation combines multiple sub-computations that mutate shared, order-dependent state (fractions summing to a total), and the shared budget/state can be corrupted when multiple operations interleave, causing over/under-crediting of value.

In this Cosmos EVM codebase, the direct analog is not in reward-fraction math but in the precompile `BalanceHandler`, which uses a **mutable, shared instance field (`prevEventsLen`)** to slice the Cosmos SDK event log and translate `x/bank` `CoinSpent`/`CoinReceived` events into `StateDB` balance mutations. This is a well-documented, already-detected defect in this very repository (see the dedicated regression test `evmd/tests/integration/balance_handler/balance_handler_test.go`), matching the required "own reachable root cause + unprivileged trigger + broken invariant" bar. [1](#0-0) [2](#0-1) 

### Title
Shared `BalanceHandler.prevEventsLen` in recursively-invoked stateful precompiles corrupts EVM `StateDB` vs `x/bank` balance accounting - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`, `testutil/testdata/debug/debug.go`)

### Summary
`BalanceHandler.BeforeBalanceChange`/`AfterBalanceChange` record and consume a single mutable field `prevEventsLen` to determine which `sdk.Context` bank events belong to the current precompile invocation. [3](#0-2) 
Some precompile call paths obtain a *shared/cached* `BalanceHandler` via `p.GetBalanceHandler()` rather than creating a fresh instance per call (as `RunNativeAction`/`runNativeAction` does via `p.BalanceHandlerFactory.NewBalanceHandler()`): [4](#0-3) [5](#0-4) [6](#0-5) 
When a stateful precompile is re-entered recursively during EVM execution (e.g., a malicious ERC20 or caller contract that triggers a nested precompile call before the outer call returns), the inner call's `BeforeBalanceChange` overwrites `prevEventsLen`, which was set by the outer call. When the outer call's `AfterBalanceChange` subsequently runs, it slices `ctx.EventManager().Events()[bh.prevEventsLen:]` using the value left behind by the inner call rather than its own original starting offset, causing it to process the wrong window of bank events.

### Finding Description
The event-window offset is a plain `int` field on `*BalanceHandler`, not a stack or per-call token: [1](#0-0) 

`AfterBalanceChange` walks `events[bh.prevEventsLen:]` and, for each `CoinSpent`/`CoinReceived`/precisebank fractional-balance event, calls `stateDB.SubBalance`/`stateDB.AddBalance`: [7](#0-6) 

The dedicated regression test `BalanceHandlerTestSuite` in this repository explicitly documents that "recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten," leading to "balance desync between native bank keeper and EVM stateDB": [2](#0-1) 

This is functionally identical to the Sherlock bug class: a value meant to represent "this call's share of a running total/log" is derived from shared mutable state that can be clobbered by a nested/concurrent operation, so the outer operation ends up crediting/debiting the wrong amount from the wrong window — either skipping real bank events (StateDB under-credits, effectively freezing/losing EVM-visible value) or re-consuming events that were already applied by the inner call (StateDB double-credits, effectively minting phantom EVM balance not backed by `x/bank`).

The related test `ICS20RecursivePrecompileCallsTestSuite`/`ics20_recursive_precompile_calls_test.go` independently documents the same class of bug for ICS20 + distribution recursive precompile interactions ("native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated"), reinforcing that recursive/nested precompile invocation is a real, reachable trigger path in this system, not a hypothetical. [8](#0-7) 

### Impact Explanation
If `stateDB.AddBalance`/`SubBalance` are invoked on the wrong event window:
- Under-consumption of the window means legitimate `CoinReceived`/`CoinSpent` events are never applied to `StateDB`, causing an EVM-visible account balance to diverge (understated) from the true `x/bank` ledger — funds become invisible/inaccessible through the EVM balance view, a form of fund freezing.
- Over-consumption (re-processing events already consumed by a nested call) causes `StateDB.AddBalance` to be called again for value already credited, inflating the EVM-visible balance beyond what is actually backed by `x/bank` reserves — an unauthorized, uncollateralized increase of spendable EVM balance, i.e., accounting corruption/duplication of value.

Both outcomes fall under "Critical unauthorized minting/duplication or irreversible accounting corruption of spendable user value across ... EVM balances" per the allowed impact gate, since the divergence between `StateDB` and `x/bank` state is not automatically reconciled and can be exploited by any user who can trigger recursive precompile calls (e.g., via a crafted ERC20 token or caller contract).

### Likelihood Explanation
This requires no privileged access — any unprivileged user can deploy a contract that triggers a nested/re-entrant call into a stateful precompile (distribution, staking, ICS20, gov, slashing, erc20 — all of which wire up `BalanceHandlerFactory`/`GetBalanceHandler`), as shown by the pre-existing test contracts (`ERC20RecursiveReverting`, `DebugPrecompileCaller`) already used in this repo's own regression tests to reproduce the bug. [9](#0-8) [10](#0-9) 

Given that the codebase already contains dedicated tests demonstrating the corrupted event/counter state, likelihood of a triggerable, reachable divergence is high; the main open question (which I could not fully verify given tool-call limits) is whether `GetBalanceHandler()` on the production precompiles (`distribution`, `staking`, `erc20`, `gov`, `ics20`, `slashing`) returns a cached singleton (vulnerable) versus always constructing a fresh handler like `runNativeAction` does — this determines exactly which call paths are exploitable in production versus only in the `debug` test precompile. This should be confirmed by inspecting the (not fully retrieved) `GetBalanceHandler()` method body in `precompiles/common/precompile.go`.

### Recommendation
- Make the event-window tracking non-shared per invocation: either always construct a fresh `BalanceHandler` per precompile call (as `runNativeAction` already does via `BalanceHandlerFactory.NewBalanceHandler()`), or replace the single `prevEventsLen int` field with a stack (e.g., `[]int`) that is pushed on `BeforeBalanceChange` and popped on `AfterBalanceChange`, so nested/recursive calls do not clobber the outer call's offset.
- Add an invariant check after `AfterBalanceChange` that reconciles cumulative `StateDB` balance deltas against actual `x/bank` balance changes for all touched addresses within the same EVM transaction, failing closed (reverting) on mismatch.
- Extend the existing `BalanceHandlerTestSuite` regression test to assert exact balance equality between `x/bank` and `StateDB` after multi-level (3+) recursive precompile calls, not just event counts.

### Proof of Concept
The repository already contains a working PoC in `evmd/tests/integration/balance_handler/balance_handler_test.go`, which deploys a caller contract that recursively invokes the `debug` precompile (`callback(0)`) and demonstrates that the shared `BalanceHandler` instance's event bookkeeping is corrupted across the recursive calls (verified via emitted event counts diverging from the expected non-recursive count). [11](#0-10) 
A second, independent PoC targeting production distribution/ICS20 precompiles is in `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go`, which deploys `ERC20RecursiveReverting`/`ERC20RecursiveNonReverting` contracts that recurse through precompile calls during an ICS20 transfer and asserts on the resulting (anomalous) event counts and reward/balance state. [12](#0-11) 

**Note on limitations:** Due to iteration limits I was unable to retrieve the full body of `GetBalanceHandler()` in `precompiles/common/precompile.go` to definitively confirm whether the singleton-sharing behavior is exercised by production precompiles (`distribution`, `staking`, `ics20`, `erc20`, `gov`, `slashing`) or is confined to the `debug`/test precompile. This should be verified directly before finalizing severity, since it determines whether the corruption is reachable via mainnet-facing precompiles or only via test-only code paths.

// BalanceHandler is a struct that handles balance changes in the Cosmos SDK context.
type BalanceHandler struct {
	bankKeeper    BankKeeper
	prevEventsLen int
}

// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

// AfterBalanceChange processes the recorded events and updates the stateDB accordingly.
// It handles the bank events for coin spent and coin received, updating the balances
// of the spender and receiver addresses respectively.
//
// NOTES: Balance change events involving BlockedAddresses are bypassed.
// Native balances are handled separately to prevent cases where a bank coin transfer
// initiated by a precompile is unintentionally overwritten by balance changes from within a contract.

// Typically, accounts registered as BlockedAddresses in app.go—such as module accounts—are not expected to receive coins.
