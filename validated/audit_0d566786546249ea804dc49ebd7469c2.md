## Analysis

The external report's core broken invariant is: **checking only a "success" signal without validating that funds actually moved**, causing the on-chain accounting state to diverge from real token custody. In Hyperbridge's own EVM-Tron `IntentGatewayV2`, the escrow-withdrawal path has the inverse but equally dangerous form of this bug: it checks the low-level call's `success` bit but never validates the returned boolean payload from the token's `transfer` function.

### Title
Escrow marked settled and accounting decremented even when ERC20 `transfer` returns `false` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In `withdraw()`, `onAccept()`'s `SweepDust` handling, and the transaction-fee redemption block, token payouts are performed with a raw low-level `.call()` to `IERC20.transfer.selector` and only the call's revert status (`success`) is checked — the ABI-decoded boolean return value of `transfer` is never inspected: [1](#0-0) [2](#0-1) 

### Finding Description
`token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` returns `success = true` whenever the callee does not revert — regardless of what value (if any) the callee returns. Many ERC20 implementations signal failure by returning `false` instead of reverting (e.g., legacy/some non-standard tokens, tokens with blacklist/pausable logic that swallow failed transfers and return `false`). Because the code never decodes/validates the returned boolean, a `transfer` call that returns `false` is treated identically to a successful transfer.

Immediately after this unchecked call, the contract unconditionally mutates protocol state as if funds moved:
- `_filled[body.commitment] = beneficiary;` marks the order permanently settled.
- `_orders[body.commitment][token] -= amount;` decrements escrow accounting.
- `EscrowReleased`/`EscrowRefunded` is emitted. [3](#0-2) 

This is the same class of defect flagged in the report (mishandling ERC20 return-value semantics), just inverted: instead of a *false negative* (safe transfer wrongly treated as failed), this is a *false positive* (failed transfer wrongly treated as succeeded). The consequence is worse for Hyperbridge because the withdrawal path is reached via cross-chain `RedeemEscrow`/`RefundEscrow` messages driven by user-supplied order data — the `token` address in `order.inputs` is attacker-controllable at order-creation time (`create`/`fillAndDispatch` flows), so a maker can escrow a token whose `transfer` returns `false` under specific conditions (e.g. paused, blacklisted beneficiary, custom non-reverting failure token) and have the contract still mark the order filled/refunded while funds remain stuck in the contract, never reaching the beneficiary.

### Impact Explanation
Escrowed funds can be permanently locked/lost from the rightful beneficiary's perspective: the accounting state (`_orders`, `_filled`) reflects settlement while the actual token balance never moved to `beneficiary`. This directly matches the bounty's "stealing or loss of funds" and "order escrow ... must move exactly once and only to the rightful beneficiary" impact categories, since the same commitment can never be withdrawn again (`_filled` is set) even though no value was delivered.

### Likelihood Explanation
Reachable through the ordinary, unprivileged `create` → cross-chain fill/redeem/refund flow without needing a malicious relayer, prover, or admin — only a maker who selects (or is tricked by protocol config into accepting) a non-reverting-failure ERC20 as an input token. Likelihood depends on such tokens being listed/whitelisted for use in `IntentGatewayV2`, but the code contains no defense (no `SafeERC20`, no return-data length/decoding check) against this class of token at all in the withdrawal path, unlike the deposit path elsewhere in the same file family which uses `SafeERC20.safeTransferFrom`.

### Recommendation
Replace the raw `.call()` + `success`-only check in `withdraw()`, the `SweepDust` branch, and the transaction-fee redemption with OpenZeppelin's `SafeERC20.safeTransfer`, which both handles tokens returning no data and correctly reverts when a token's `transfer` explicitly returns `false`. This closes both directions of the boolean-return-value bug class.

### Proof of Concept
1. Maker creates an order with `order.inputs[0].token` set to a token contract whose `transfer(address,uint256)` returns `false` (rather than reverting) when the recipient is blacklisted/paused, while still accepting deposits via `transferFrom` normally.
2. Order is filled cross-chain in the normal flow; escrow is recorded in `_orders[commitment][token]`.
3. Maker/beneficiary triggers `RedeemEscrow`/`RefundEscrow`, which calls `withdraw()`.
4. At the moment of withdrawal the beneficiary address is blacklisted (or the token is paused) so `transfer` returns `false` without reverting.
5. `token.call(...)` still reports `success = true` because the low-level call itself did not revert; `_filled[commitment]` is set and `_orders[commitment][token] -= amount` executes.
6. The order is now permanently marked settled/refunded with `EscrowReleased`/`EscrowRefunded` emitted, but the beneficiary never received the tokens — funds are stuck in the contract with no remaining code path to reclaim them for that commitment.
