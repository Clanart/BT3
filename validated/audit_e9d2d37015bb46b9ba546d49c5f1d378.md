### Title
Spoofed `WWW-Authenticate` realm header lets an attacker-controlled git remote impersonate a GitHub/Enterprise host and trigger a rogue OAuth sign-in flow - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The Coinbase report's broken invariant is: a one-time attestation grants trust to an identity (a smart-contract wallet) without verifying that the identity's underlying behavior stays the way it was when the check was performed. The Desktop analog is structurally identical: `getEndpointKind` in the git-credential trampoline decides whether a remote host is a genuine GitHub/GHE instance based on a **self-reported HTTP header returned by the very server being classified**, instead of relying on the actual network verification (`isGitHubHost`) that exists for exactly this purpose. A remote/proxy fully controlled by an attacker can therefore "attest" to being GitHub and short-circuit the real check.

### Finding Description
`getEndpointKind` first tries fast, unspoofable checks (`isGist`, `isDotCom`, `isGHE` — hostname allow-lists), and only falls back to a real network probe (`isGitHubHost`) at the very end of the function: [1](#0-0) 

In between, it trusts `wwwauth[]` entries that are forwarded verbatim from the HTTP response of the remote Git is talking to:
```
// When Git attempts to authenticate with a host it captures any
// WWW-Authenticate headers and forwards them to the credential helper. We
// use them as a happy-path to determine if the host is a GitHub host without
// having to resort to making a request ourselves.
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } ...
```
This header is attacker-supplied data: any git server (a malicious remote the user clones/fetches, or a MITM/proxy sitting in front of a real remote — both explicitly in-scope attacker positions) can respond to Git's unauthenticated HTTP request with `WWW-Authenticate: Basic realm="GitHub"` and immediately be classified as `'enterprise'`, bypassing the actual `isGitHubHost` verification entirely.

Once classified as `'enterprise'` with no matching stored account, the credential helper calls `ui.promptForGitHubSignIn(endpoint)`: [2](#0-1) 

which starts a full Enterprise OAuth sign-in flow *scoped to the attacker's own origin* (`setSignInEndpoint(origin)` / `beginEnterpriseSignIn`). The OAuth authorize URL is built against that same attacker-controlled origin: [3](#0-2) 

and when the (attacker-driven) OAuth callback completes, Desktop performs the code-exchange POST directly to the attacker's host, sending the app's embedded `client_id`/`client_secret`: [4](#0-3) 

So a server that never proved it was actually GitHub Enterprise ends up receiving Desktop's app-level OAuth secret and driving a real "GitHub sign-in" UI shown to the user, purely because it echoed a `realm="GitHub"` string in a header.

### Impact Explanation
- The verification step that exists specifically to stop this (`isGitHubHost`, an actual outbound check) is bypassed by attacker-supplied response metadata — same class of bug as the report: a check performed once (or replaced by a cheap self-declared signal) is trusted for a decision that has security consequences (initiating account/OAuth binding, or auto-filling credentials for what looks like a trusted enterprise account).
- Impact is "unauthorized OAuth/account binding": the app opens a legitimate-looking "Sign in with your browser" / "GitHub Enterprise sign-in" flow bound to an attacker's origin, and Desktop's shared OAuth `client_secret` is sent to that attacker origin during code exchange.
- It also creates a strong phishing primitive: victims cloning/fetching from a malicious remote will see Desktop's native "this looks like a GitHub host, please sign in" dialog for a server that is not actually GitHub, increasing the odds the user hands over real GitHub credentials believing Desktop already vetted the host.

### Likelihood Explanation
Low/Medium — it requires the victim to clone/fetch/push against an attacker-supplied or MITM'd remote (an in-scope "attacker controls a git remote/proxy response" scenario per the task's valid-impact list), and for the sign-in prompt to be accepted by the user. No local access, admin rights, or pre-existing malware is needed; the entire trigger is a crafted HTTP 401 response header from a git remote the user is already interacting with.

### Recommendation
Do not treat `WWW-Authenticate` realm strings as authoritative for classifying a host as GitHub/Enterprise/generic. Always require the real `isGitHubHost` network verification (or an existing account match) before classifying an endpoint as `'enterprise'`/`'github.com'`/`'ghe.com'`, and never use it to gate whether a "GitHub sign-in" UI/OAuth flow is initiated. At minimum, gate the OAuth code-exchange step so the `client_secret` is only ever sent to hostnames that passed the genuine `isGitHubHost` verification, not ones inferred from a header the remote controls.

### Proof of Concept
1. Stand up a plain HTTP(S) git server (e.g., `git http-backend`) that, for any unauthenticated request, replies `401` with header `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, clone/add this server as a remote and trigger a fetch.
3. Git invokes the trampoline credential helper; `getEndpointKind` sees the spoofed `wwwauth[]` header and returns `'enterprise'` without ever calling `isGitHubHost`.
4. Since no account matches this new endpoint, Desktop shows its native GitHub Enterprise "Sign in with your browser" dialog and opens `https://<attacker-host>/login/oauth/authorize?client_id=...` in the system browser.
5. The attacker's server drives the OAuth "callback" (via the `x-github-client://oauth?...` deep link Desktop registers) with an arbitrary code; Desktop's `resolveOAuthRequest`/`requestOAuthToken` POSTs `client_id`+`client_secret`+`code` to `https://<attacker-host>/login/oauth/access_token`, handing the attacker Desktop's embedded OAuth secret and completing an "account" bound to the attacker's fake response.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

export async function requestOAuthToken(
  endpoint: string,
  code: string
): Promise<string | null> {
  try {
    const urlBase = getHTMLURL(endpoint)
    const response = await request(
      urlBase,
      null,
      'POST',
      'login/oauth/access_token',
      {
        client_id: ClientID,
        client_secret: ClientSecret,
        code: code,
      }
    )
    tryUpdateEndpointVersionFromResponse(endpoint, response)

    const result = await parsedResponse<IAPIAccessToken>(response)
    return result.access_token
  } catch (e) {
    log.warn(`requestOAuthToken: failed with endpoint ${endpoint}`, e)
    return null
  }
}
