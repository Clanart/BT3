### Title
Attacker-controlled `n` in serialized `ThresholdKeys` triggers pre-allocation and a large read loop before any bounds check — uncontrolled resource consumption from untrusted bytes - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` in `crypto/dkg/src/lib.rs` trusts the serialized participant count `n` (a raw `u16`) to (a) eagerly pre-allocate a `Vec` of `n` field elements for `Interpolation::Constant` and (b) drive a loop performing `n` point deserializations and `HashMap` insertions, plus a polynomial/Lagrange parameter validation pass, all before any check that the declared sizes are consistent or that `n` corresponds to a real participant set. An unprivileged party that can feed untrusted bytes into `ThresholdKeys::read` (an explicitly in-scope untrusted-byte sink) can cause repeated allocation and deserialization work disproportionate to the bytes supplied, yielding a denial of service via uncontrolled resource consumption — the same bug class as CVE-2021-22217.

### Finding Description
In `crypto/dkg/src/lib.rs` (lines 574–632), `ThresholdKeys::read` performs:

1. Reads `t`, `n`, `i` as raw `u16`s from the stream (lines 591–602) — `n` is fully attacker-controlled up to 65535.
2. For `Interpolation::Constant` (tag byte `0`), immediately executes `Vec::with_capacity(usize::from(n))` (line 608) — an eager heap allocation sized purely by the attacker's `n`, before a single byte of coefficient data has been validated as present.
3. Then loops `for _ in 0 .. n` calling `C::read_F` (lines 609–611).
4. Then loops `for l in (1..=n)` calling `C::read_G` and inserting into a `HashMap` (lines 621–623).
5. Finally calls `ThresholdKeys::new` → `ThresholdParams::new(t, n, i)`, and computes `group_key` via `interpolation_factor` over `1..=t` (lines 376–378), which for `Interpolation::Constant` indexes `c[i-1]`.

Unlike the length-prefixed readers elsewhere in the codebase, there is no cap on `n` at all during the read — `Participant::new` only rejects `0`, and the `i <= n` check in `ThresholdParams::new` happens *after* the allocation and the full read loops have already run. The cost is driven entirely by the 2-byte `n` field; a ~15-byte crafted buffer requesting `n = 65535` forces a `with_capacity` allocation of `65535 * size_of::<F>()` (~2 MB for 32-byte fields, larger for wider fields) plus loop setup, before the first `read_F` hits EOF. Additionally, an attacker who *does* supply `n` scalars can force `n` group-element decodes (`read_G` performs full point decompression/validation) and `n` `HashMap` insertions, then make `ThresholdKeys::new` perform `t` Lagrange interpolation factor computations each `O(t)` — `O(t²)` field inversions/multiplications — driven entirely by attacker bytes.

### Impact Explanation
An attacker supplying crafted byte streams to any component deserializing `ThresholdKeys` (or `EncryptedMessage`/`Commitments` paths that embed parameter-driven reads) can cause:

- Memory amplification: ~2–4 MB of eager allocation plus `HashMap` bookkeeping for ~15 bytes of input (Constant interpolation path), per call.
- CPU amplification: supplying valid-length data with `n = 65535`, `t = 65535` forces `65535` `read_G` decompressions plus `t` Lagrange factors, each `O(t)` — `O(t²)` ≈ 4·10⁹ field operations, a pure-CPU stall from a few MB of input.

This is uncontrolled resource consumption reachable by an unprivileged party through public inputs, matching the bug class of the referenced advisory. Severity Medium: the work is bounded by `u16` fields (so it's exhaustion-by-repetition/amplification rather than a single unbounded allocation), but no limit, ratio check, or incremental-read strategy exists in this crate.

### Likelihood Explanation
`ThresholdKeys::read` is listed among the crate's untrusted-byte entry points (serialized key material exchanged/persisted during DKG and signing setup). Any protocol path that deserializes peer-supplied or disk-loaded `ThresholdKeys` without an outer size cap is exposed. The required input is trivially constructible — set `n = 0xFFFF`, pick interpolation tag `0`, and either truncate (allocation amplification) or supply filler scalars (CPU amplification). No valid key material, signatures, or privileged position is required. The main limitation is the `u16` width of `n`, capping per-call amplification and requiring repeated submissions for sustained impact — hence Medium, not High.

### Recommendation
- Validate `t <= n`, `n <= i`, and a protocol-level `MAX_PARTICIPANTS` (e.g., the real validator-set bound) **before** any allocation or read loop in `ThresholdKeys::read`.
- Replace `Vec::with_capacity(n)` with incremental `push` (allocation then tracks bytes actually present, as done deliberately in `networks/ethereum/src/machine.rs` `Call::read`, which reads in 1 KB chunks for exactly this reason — see `data_len` chunked read, `machine.rs` lines 51–60).
- Bound the `1..=n` `read_G` loop by the same validated `n`, and reject `n` values exceeding the expected multisig size for the context in which the keys are read.

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }
