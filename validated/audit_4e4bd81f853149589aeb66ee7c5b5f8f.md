Based on my investigation, the closest analog I could verify in the codebase is not a perfect match for the front-running/deterministic-initial-state pattern in the original report (that class of bug typically requires an attacker with local filesystem write access to pre-populate a path before Desktop creates/validates it, which is explicitly out of scope for this assessment). I was unable to confirm a remote/link/API-only path that lets an attacker poison a "fresh" state the same way `createPoolADD` is poisoned. However, I did find one concrete, security-relevant finding worth flagging with lower confidence, tied to the same underlying invariant ("assume a fresh, uncorrupted git operation, but attacker-controlled content is trusted before validation").

### Title
Recursive clone of an untrusted repository executes attacker-controlled Git hooks via crafted submodules, with a disabled/no-op clone protection flag - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` always passes `--recursive` and explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment for every clone operation, including clones of repositories chosen by URL/GitHub API listing (fully attacker-influenced content), without any check for malicious submodule configuration prior to recursively initializing submodules. [1](#0-0) 

### Finding Description
`clone()` is the single entry point used both for user-initiated clones and for the "Open in Desktop" deep-link flow (`open-repository-from-url` action, dispatched via `dispatchURLAction`), meaning the remote URL and its content are fully attacker-controlled. [2](#0-1) [3](#0-2) 

The invariant being broken mirrors the pool report: Desktop treats the outcome of a fresh `git clone --recursive` as trustworthy/inert before any of the app's own validation logic (status checks, repository-type detection, etc.) runs — but a malicious repository can define `.gitmodules` entries and submodule paths that are attacker-chosen, and `--recursive` will initialize/checkout those submodules as part of the same clone step, before Desktop has a chance to inspect anything. This is the same "trust-the-precondition, attacker-poisons-it-first" class of bug: instead of the pool's initial balance being poisoned before `createPoolADD` reads it, here the working tree/hooks state is poisoned by attacker-controlled submodule metadata before Desktop's own repository validation (`getRepositoryType`, `getStatus`, etc.) ever runs. [4](#0-3) 

The explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` is notable: its name strongly implies it is meant to toggle a hardening feature (the class of protections shipped upstream in Git after CVE-2024-32002/CVE-2017-1000117, which guard against case-insensitive-filesystem and symlinked `.git`/hook-path submodule tricks), and it is being force-disabled unconditionally for every clone. [5](#0-4) 

### Impact Explanation
If the underlying `dugite`/git binary bundled with Desktop does honor this flag (or an equivalent protection it controls) to gate submodule/hook-path safety checks, disabling it for every clone — including clones of arbitrary attacker-supplied URLs reached via the `x-github-client://openRepo/...` deep link — would let a malicious repository author execute code on the victim's machine, or write files outside the intended repository directory, the moment the user clones or opens the link. This matches the requested impact classes: code execution and file write outside the repo, triggered purely by cloning/fetching attacker-controlled content, with no local access or prior compromise needed.

### Likelihood Explanation
Moderate-to-low confidence. I could not verify from the available code whether `GIT_CLONE_PROTECTION_ACTIVE` corresponds to a real, functioning safeguard in the git version dugite ships (it does not match any standard upstream Git environment variable I'm aware of), so it's possible this line is inert (a no-op) rather than an active downgrade of a real protection. Because of index size limits I could not inspect the vendored git/dugite binary or its documentation to confirm behavior. If it is a no-op, the residual risk reduces to whatever protection level ships by default in the bundled Git version for recursive submodule clones of untrusted repositories.

### Recommendation
- Remove or justify `GIT_CLONE_PROTECTION_ACTIVE: 'false'`; if it maps to a real upstream safeguard, it should be left enabled (`true`) for all clones of non-trusted/remote sources.
- Verify against the actual bundled Git/dugite version which config values (e.g. equivalents of `protectNTFS`, `protectHFS`, or hook-path checks) are relevant, and ensure they are enabled by default rather than overridden.
- Consider not using `--recursive` blindly on first clone for repositories reached via deep links/URLs; instead parse `.gitmodules` first and warn/prompt if any submodule path/URL looks suspicious (path traversal, absolute paths, `file://`, unexpected protocol) before recursively initializing.

### Proof of Concept
Concrete exploitation could not be fully demonstrated without access to the bundled git binary's actual handling of `GIT_CLONE_PROTECTION_ACTIVE`, so this is reported as a configuration/hardening concern with supporting code evidence rather than a fully proven RCE chain:
1. Attacker publishes a public repository containing a `.gitmodules` file with a submodule path/URL crafted per the CVE-2024-32002-style technique (case-insensitive filesystem collision or crafted hook path). [4](#0-3) 
2. Attacker sends the victim a link such as `x-github-client://openRepo/https://github.com/attacker/evil-repo`. [6](#0-5) 
3. Desktop's `dispatchURLAction` routes this to `openRepositoryFromUrl`, which ultimately calls `clone()` with `--recursive` and `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. [3](#0-2) [1](#0-0) 
4. If the underlying git honors this variable to gate submodule-hook safety checks, the recursive clone step executes attacker-controlled hook code or writes outside the target directory before any Desktop-side validation occurs.

Given the uncertainty about whether `GIT_CLONE_PROTECTION_ACTIVE` is a real, enforced protection in the bundled git, I recommend this be verified in a live Desktop build (not achievable from the indexed code alone) before treating this as a confirmed, exploitable vulnerability rather than a hardening gap.
