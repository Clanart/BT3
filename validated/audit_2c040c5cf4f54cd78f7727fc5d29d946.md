### Title
Unbounded pre-allocation in `ThresholdKeys::read` enables memory exhaustion via attacker-controlled participant count - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` reads a fully attacker-controlled `u16` field `n` and immediately performs `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient vector before any of the `n` scalars have actually been supplied. A truncated input of ~15 bytes therefore forces an allocation of up to `65535 * size_of::<C::F>()` (≈2 MiB for 32-byte curves, ≈3.7 MiB for ed448) per call — an amplification of >100,000× relative to bytes delivered. This is the same bug class as GHSA-m2cx-gpqf-qf74 (unbounded response-body allocation), mapped onto a length-prefixed deserialization path reachable from untrusted bytes.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` parses `t`, `n`, and `i` from the reader (lines 591-602), then on the `Interpolation::Constant` branch (tag `0`) executes `Vec::with_capacity(usize::from(n))` (lines 607-613). `n` is never validated against `ThresholdParams` until `ThresholdParams::new` is called at line 626 — long after the allocation, and after the read loop which aborts on `read_exact` failure once the input ends, leaving the already-committed allocation on the heap until `res` is dropped.

`ThresholdKeys::read` is explicitly an untrusted-byte entry point (per the reachable-API list). Any component that deserializes `ThresholdKeys` from externally supplied data — e.g., key material passed to `view()`, `scale()`, or `offset()` after deserialization — exposes this allocation to an unprivileged party. Per call the attacker supplies only: 4-byte ID length + `C::ID` + 6 bytes of `t/n/i` + 1 interpolation tag byte ≈ 15–25 bytes, and triggers a multi-megabyte allocation that is never filled (the `C::read_F` loop fails immediately on `UnexpectedEof`). Repeated invocations — concurrent or sequential — accumulate allocations bounded only by request rate, since each allocating call completes in microseconds.

The analogous `verification_shares` loop (lines 620-623) does *not* amplify, since each `C::read_G` consumes real bytes; the vulnerability is specifically the speculative `with_capacity` which commits memory before the corresponding input exists — exactly the pattern the `ethereum` crate's `Call::read` deliberately avoids with chunked reads ("a valid DoS would be to claim a 4 GB data is present for only 4 bytes", `networks/ethereum/src/machine.rs:51-60`).

### Impact Explanation
**Denial of service via memory exhaustion.** An unprivileged party able to feed bytes to `ThresholdKeys::read` (key-recovery/promotion inputs, DKG artifacts, or any deserialization endpoint accepting serialized `ThresholdKeys`) can force multi-megabyte allocations at a cost of ~15 bytes per attempt. With `Interpolation::Constant` tag `0` and `n = 0xFFFF`, each call allocates ≈2–3.7 MiB (depending on ciphersuite field size, e.g. `dalek-ff-group` `Scalar` at 32 bytes or `ed448` at 57 bytes per element). Issuing allocations in a tight loop or across many concurrent requests drives the hosting process into OOM without any network-bandwidth symmetry: the attacker never has to transmit the bytes they claim exist. This satisfies the Medium bar of a remotely triggerable, unprivileged availability impact.

### Likelihood Explanation
Reachability requires a path where attacker-influenced bytes reach `ThresholdKeys::read` — which the accepted-input rules explicitly enumerate (`ThresholdKeys::read` is listed among untrusted-byte sinks). `Participant::new(i)` rejects `i == 0` but `n` itself is unconstrained until `ThresholdParams::new(t, n, i)` at line 626; setting `t = 1, n = 0xFFFF, i = 1` passes the `Participant::new` check at line 600 and reaches the `with_capacity` call. The interpolation byte must be `0` (Constant). No signatures, proofs, or valid group elements are needed — the input is trivially forgeable. The only mitigating factor is that the amplification per call is capped at ~`u16::MAX` elements rather than `u32::MAX`, hence Medium rather than High.

### Recommendation
Do not allocate before the bytes are proven present, mirroring the chunked-read approach already used in `networks/ethereum/src/machine.rs:53-60`:

```rust
// crypto/dkg/src/lib.rs, Interpolation::Constant branch of ThresholdKeys::read
0 => Interpolation::Constant({
    let mut res = Vec::new(); // no speculative with_capacity
    for _ in 0 .. n {
        res.push(C::read_F(reader)?); // fails on EOF before allocation grows
    }
    res
}),
```

Optionally also validate `n`/`t` via `ThresholdParams::new(t, n, i)` *before* entering the interpolation read, rejecting `t > n` and `t != n` for `Constant` up front (constant interpolation is already required to have `t == n` by `ThresholdKeys::new`, lines 367-374), and cap `n` at a protocol-sane maximum.

// Rust PoC sketch against crypto/dkg (e.g. C = ciphersuite::Ristretto)
use std::io::Cursor;
use dkg::ThresholdKeys;
use ciphersuite::Ciphersuite;
use ciphersuite::Ristretto;

fn main() {
    // Minimal input: id_len, ID, t=1, n=0xFFFF, i=1, interpolation tag 0 (Constant)
    // then EOF — no scalars actually provided.
    let mut input = Vec::new();
    input.extend(&(Ristretto::ID.len() as u32).to_le_bytes());
    input.extend(Ristretto::ID);
    input.extend(&1u16.to_le_bytes());      // t
    input.extend(&0xFFFFu16.to_le_bytes()); // n = 65535
    input.extend(&1u16.to_le_bytes());      // i
    input.push(0);                          // Interpolation::Constant

    // ~15 bytes of attacker input -> Vec::with_capacity(65535 * size_of::<Scalar>())
    // ≈ 2 MiB committed before the read loop hits EOF and errors.
    let _ = ThresholdKeys::<Ristretto>::read(&mut Cursor::new(&input));

    // Loop this call; each iteration allocates ~2 MiB which is freed on error,
    // but concurrent in-flight calls (or a caller that holds handles) accumulate
    // allocations at ~130,000x amplification relative to bytes sent, enabling
    // memory-exhaustion DoS of the deserializing process.
}
