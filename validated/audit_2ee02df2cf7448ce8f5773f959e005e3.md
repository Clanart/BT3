Confirmed: `PayoutCheckerTask::run_once` fully automates the exploit path — it runs on every operator without requiring any operator cooperation, pulling `get_first_unhandled_payout_by_operator_xonly_pk(operator.signer.xonly_public_key)` and, if a row exists, automatically calls `handle_finalized_payout` → `end_round` → drives the operator's own kickoff/Reimburse flow for that withdrawal, purely based on the DB attribution poisoned by `update_finalized_payouts`.

### Title
Attacker-controlled extra payout-tx output lets a withdrawer forge `payout_payer_operator_xonly_pk` and trigger an unearned Reimburse claim - (File: core/src/verifier.rs)

### Summary
`Verifier::update_finalized_payouts` determines which operator "fronted" a withdrawal purely from the first OP_RETURN output found in whatever transaction spends the withdrawal's committed UTXO, with no binding to which party actually funded the payout output. Because the user's authorizing signature uses `SIGHASH_SINGLE|ANYONECANPAY`, it only commits to the input and the single output at the same index, leaving every other output (including additional OP_RETURNs) completely unconstrained and forgeable by anyone holding that signature — including the withdrawer themselves.

### Finding Description
Binding claimed: `withdrawals.payout_payer_operator_xonly_pk[i] == xonly_pk_of(operator who funded the payout that satisfied withdrawal i)`.

Trace:
- `withdraw()`/`WithdrawParams` (`core/src/rpc/parser/operator.rs:161-203`, `core/src/rpc/clementine.proto:239-253`) requires `input_signature.sighash_type == SinglePlusAnyoneCanPay`, and the withdrawer supplies `in_outpoint`, `in_signature`, `output_script_pubkey`, `output_amount` themselves (they own the key for `in_outpoint`, per `core/src/test/common/setup_utils.rs:480-543` `generate_withdrawal_utxo`/`sign_withdrawal_output`, where the *withdrawer's* signer owns the dust input and signs it).
- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) is only what the *honest* operator uses; it is not enforced on-chain. `SIGHASH_SINGLE|ANYONECANPAY` (`core/src/builder/transaction/txhandler.rs:222-229`, `bitcoin::sighash::Prevouts::One`) only commits the digest to: the signed input's outpoint/amount/script, and the single output at the same index. It commits to **nothing else** — not the total output count, not any other output's content, not any other input.
- The verifier discovers "the payout tx" purely by scanning the chain for whatever transaction spends `withdrawal_utxo_txid:withdrawal_utxo_vout` (`get_payout_txs_for_withdrawal_utxos`, `core/src/database/verifier.rs:168-196`, joined against `bitcoin_syncer_spent_utxos` populated by the generic UTXO-spend scanner). There is no requirement that this spending transaction be the specific one the intended operator constructed.
- `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) then takes `get_first_op_return_output(&circuit_payout_tx)` — the *first* OP_RETURN output in that transaction, at any vout — and decodes it with `parse_op_return_data` + `XOnlyPublicKey::from_slice`, writing the result straight into `payout_payer_operator_xonly_pk` via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`).
- Attacker exploit: the withdrawer (who legitimately owns and signs the withdrawal input with `SinglePlusAnyoneCanPay`) constructs their *own* transaction — never touched by any operator — that spends `in_outpoint` with an output at the signed index matching the committed `output_script_pubkey`/`output_amount` (satisfying the signature), self-funds any additional inputs needed for the requested amount (which is paid right back to themselves, at effectively only the cost of miner fees), and appends an extra OP_RETURN output — placed before any other OP_RETURN, or as the only OP_RETURN — encoding an arbitrary, valid operator X xonly-pubkey of the attacker's choosing. They broadcast this themselves.
- `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) on operator X's own node then automatically finds this "unhandled payout" via `get_first_unhandled_payout_by_operator_xonly_pk(X's own key)` and drives `handle_finalized_payout` → kickoff → `end_round`, with `is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) comparing only `operator_xonly_pk` (the same poisoned DB field) against `kickoff_data.operator_xonly_pk`, so it will match and verifiers will not challenge.
- No existing guard fixes this: `is_deposit_valid`, `is_profitable`, `SPV::verify`, and the presigned-transaction graph all operate on inputs/state that remain internally consistent with the attacker's forged tx; none of them re-derive "who funded this payout" from actual value flow, only from the OP_RETURN the verifier trusts blindly, at whatever position it happens to appear first.

### Impact Explanation
Operator X — who never constructed, signed, or funded any payout — gets `payout_payer_operator_xonly_pk` set to their own key in the `withdrawals` table. `PayoutCheckerTask` on X's node autonomously drives the kickoff/Reimburse flow for that withdrawal, and since `is_kickoff_malicious` only checks the (poisoned) DB record against the kickoff data (both consistent with X), verifiers do not challenge X's presigned Reimburse transaction. X is thereby able to claim a Reimburse output — funded from the bridge deposit's `MoveToVault` UTXO — for a payout it never made. This is repeatable for any withdrawal and any target operator xonly-pk the attacker chooses (they control the entire attribution field), matching the Critical category "an operator reimbursed for a payout it never funded." Note X does not need to collude for this record to be planted, though X (or an operator impersonating X's public key as the attacker's chosen target) ultimately benefits — the write into the shared verifier-synced DB is unconditionally attacker-forged, independent of operator consent.

### Likelihood Explanation
Preconditions are all within the unprivileged attacker's stated capabilities: they call `withdraw` on the Citrea Bridge contract, choose the withdrawal UTXO bytes and its `SinglePlusAnyoneCanPay` signature (which they generate themselves since they own the input key), and broadcast Bitcoin transactions. No verifier, operator, or aggregator cooperation is needed to plant the forged attribution — only the attacker's own broadcast of a self-funded transaction that satisfies the exact single-output/ANYONECANPAY commitment. Cost to the attacker is essentially just their own withdrawal amount (returned to themselves) plus miner fees; the attack is fully repeatable per withdrawal/operator pair.

### Recommendation
Do not derive `payout_payer_operator_xonly_pk` from an unauthenticated OP_RETURN scan of "whatever spent the UTXO." Bind the attribution cryptographically to the actual funding party: e.g., require the operator to co-sign the payout transaction (so the operator's own key/signature over the transaction, not just an easily-forged OP_RETURN, proves they funded it), or require the specific OP_RETURN output to be at a fixed, protocol-defined vout that is itself covered by a signature/commitment tied to the party claiming credit, and reject transactions containing more than one candidate OP_RETURN rather than silently taking the first.
