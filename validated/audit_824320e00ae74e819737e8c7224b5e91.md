### Title
AssociateTx / `associate` signature verification lacks domain separation, enabling cross-context signature replay for forced address association - ([File: x/evm/ante/preprocess.go])

### Summary
The `jwcrypto` advisory describes a type-confusion bug where a verifier auto-detects the "type" of a signed token and reuses the same key material across two different validation domains without a strong domain separator, letting a token crafted for one purpose be substituted where a different type was expected. Sei-chain's EVM address-association path (`AssociateTx` and the `associate`/`associatePubKey` precompile) has an analogous pattern: it recovers a secp256k1 signer from an **arbitrary, attacker-supplied `CustomMessage` hash** with no chain-ID, nonce, or purpose binding, and the recovered identity is used to permanently bind an EVM address to a Sei address, migrating balances and account state.

### Finding Description
`PreprocessUnpacked` auto-detects the `AssociateTx` message type and, for that branch, recovers the signer purely from `keccak256(CustomMessage)`: [1](#0-0) 

Compare this to the normal EVM transaction branch just below it, which binds the signature to a chain-specific hash via `signer.Hash(ethTx)` and enforces `IsTxTypeAllowed`/chain-ID checks: [2](#0-1) 

The `associate` precompile entry points reproduce the same weakly-bound recovery, hashing whatever `customMessage` string is supplied by the caller with no required prefix, domain tag, or content check enforced on-chain: [3](#0-2) 

Unlike the EIP-7702 authorization path — which the codebase's own comments show was hardened specifically against this class of bug by requiring the authorization's `ChainID` to match the local chain (or be zero) before pre-associating an authority — the `AssociateTx`/`associate` custom-message path performs **no equivalent domain binding**: [4](#0-3) 

Grepping the Go sources confirms there is no server-side enforcement of a fixed/expected message format or constant for `CustomMessage` — the "personal_sign" EIP-191 envelope shown in the integration test is a purely client-side convention, not something the chain checks: [5](#0-4) 

Because verification only checks "does this signature recover to a valid secp256k1 pubkey," any ECDSA signature the victim has ever produced over data that happens to equal `keccak256(customMessage)` for some string reachable by an attacker (e.g., signatures leaked from other dApps/chains that use a non-EIP-191-enforced raw-hash signing scheme, or signatures over data an attacker can trick a wallet into signing as "just a message") can be replayed through `associate`/`AssociateTx` to force an association the user never intended for the Sei chain specifically — there is no chain ID, contract address, or nonce tying the signature to this action.

### Impact Explanation
`AssociateAddress`/pre-association permanently binds an EVM address to a derived Sei address and, per the codebase's own comments elsewhere, migrating association can move "direct-cast balance" and orphan staking/distribution state for the affected account. Forcing an unwanted association on a victim address can be used to disrupt their account state, front-run their intended association, or as a building block combined with other flows that assume `IsAssociate` addresses are user-consented, potentially leading to fund exposure/loss for the affected account. This falls under "unauthorized transfer/permanent freezing/fund loss via precompile" territory since it manipulates authoritative address-identity state through a public, unprivileged entry point.

### Likelihood Explanation
Any unprivileged EVM RPC client or contract deployer can submit an `AssociateTx` or call `addr.associate`/`associatePubKey`. Exploitation only requires possession of some (v, r, s) signature and message pair from the victim's key that the attacker can present as `CustomMessage` — no cooperation from validators or governance is needed, and this path is exercised on every transaction from a new address (association is part of normal onboarding), giving attackers many opportunities to observe or induce off-chain signatures. Likelihood is Medium: it requires the attacker to obtain a usable raw ECDSA signature from the victim over attacker-influenced or attacker-guessable byte content, which is a realistic but not universal condition (mirroring the "moderate" rating jwcrypto's advisory itself assigned to the analogous class of bug).

### Recommendation
Bind the `AssociateTx`/`associate` custom-message hash to a domain separator that is unique to this chain and this action, e.g., include the chain ID, the precompile/contract address, and a fixed protocol tag (similar to the `eip7702MagicPrefix` domain separation already used for EIP-7702 authorizations) inside the hashed payload, and reject any signature whose message does not match required constant/prefix. Additionally consider requiring the address association flow to consume a fresh nonce or expire so that a leaked signature cannot be replayed indefinitely.

### Proof of Concept
1. Attacker obtains any raw secp256k1 signature (r, s, v) produced by victim's key over some byte string `M` (e.g., from an off-chain signing flow, another chain's dApp, or a wallet "sign message" prompt not enforcing EIP-191 domain separation).
2. Attacker submits an `AssociateTx` (or calls `addr.associate(v, r, s, M)`) with `CustomMessage = M`.
3. `PreprocessUnpacked` computes `keccak256(M)` and recovers the victim's pubkey/EVM/Sei addresses purely from this hash, with no chain ID or purpose binding: [6](#0-5) 
4. `AssociateAddress` permanently links the victim's addresses on Sei without their consent for this specific action, even though `M` was never intended to authorize an on-chain association on Sei.

func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)
}

// AuthorityToPreAssociate returns the authority of an EIP-7702 authorization that should be
// associated with its true (pubkey-derived) Sei address before execution, or ok=false.
//
// It mirrors go-ethereum's StateTransition.validateAuthorization (chain id, nonce overflow,
// authority code, and account-nonce checks) so that pre-association happens only for
// authorizations the EVM will actually apply, and additionally skips authorities that are
// already associated. Mirroring validateAuthorization is essential to security: the
// authorization sig hash is computed from the auth's own ChainID, so recovery and
// auth.Authority() succeed for an authorization signed for ANY chain. Without these checks a
// publicly-visible authorization a user signed for another chain (e.g. Ethereum mainnet)
// could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their
// direct-cast balance and orphaning staking/distribution state — even though the EVM skips
// the wrong-chain authorization and installs no delegation.
func AuthorityToPreAssociate(ctx sdk.Context, k AuthorizationStateReader, auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, bool) {
	// Chain ID must be null or match the local chain.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(k.ChainID(ctx)) != 0 {
		return common.Address{}, nil, nil, false
	}
	// Nonce must not overflow (EIP-2681).
	if auth.Nonce+1 < auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	evmAddr, seiAddr, pubkey, err := RecoverAddressesFromAuthorization(auth)
	if err != nil {
		return common.Address{}, nil, nil, false
	}
	// Cross-check against go-ethereum's authoritative recovery so we only ever act on the
	// exact address SetCode would target during execution.
	if authAddr, aerr := auth.Authority(); aerr != nil || authAddr != evmAddr {
		return common.Address{}, nil, nil, false
	}
	// Authority must have no code, or only an existing delegation designator.
	if code := k.GetCode(ctx, evmAddr); len(code) != 0 {
		if _, ok := ethtypes.ParseDelegation(code); !ok {
			return common.Address{}, nil, nil, false
		}
	}
	// Authority account nonce must match the authorization nonce.
	if k.GetNonce(ctx, evmAddr) != auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	// Already-associated authorities need no pre-association (and cannot be re-mapped).
	if _, associated := k.GetEVMAddress(ctx, seiAddr); associated {
		return common.Address{}, nil, nil, false
	}
	return evmAddr, seiAddr, pubkey, true

const eip191Envelope = (message: string): string =>
    `\x19Ethereum Signed Message:\n${Buffer.from(message, 'utf8').length}${message}`;

/** v/r/s in the precompile's expected shape: v is the 0/1 recovery id as hex. */
const signatureParts = async (wallet: EvmAccount, message: string) => {
    const sig = ethers.Signature.from(await wallet.wallet.signMessage(message));
    return { v: `0x${sig.v - 27}`, r: sig.r, s: sig.s };
};

describe('addr precompile (0x1004)', function () {

    const addrIface = precompileInterface('addr');

    let admin: EvmAccount;
    let addr: ethers.Contract;
    let caller: ethers.Contract;

    before(() => {
        runtime = readRuntimeState();
        admin = EvmAccount.fromMnemonic(runtime.funded.adminMnemonic, provider);
        addr = precompileContract('addr', admin.wallet);
        caller = callerContract(runtime, admin.wallet);
    });

    describe('happy path & state parity', () => {
        it('getSeiAddr returns the admin’s pubkey-derived sei address', async () => {
            const seiAddr: string = await addr.getSeiAddr(admin.address);
            expect(seiAddr).to.match(SEI_ADDRESS);
