## Title
Partial-commit patch generation re-diffs the working tree but reuses a stale line-selection index, silently committing/staging unintended hunks - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop's partial-commit flow captures a user's line selection (`DiffSelection`) as a set of *absolute line indices* into a specific `ITextDiff` object rendered in the UI. When the commit is actually staged, `applyPatchToIndex` throws away that diff and calls `getWorkingDirectoryDiff` **again** to fetch a brand-new diff from disk, then blindly re-applies the old, index-based selection to the new diff's hunks via `formatPatch`. There is no check that the newly-fetched diff has the same shape/content as the one the selection indices were computed against. If the tracked file's on-disk content changes between the moment the diff was rendered/selected and the moment `applyPatchToIndex` runs, the numeric line indices silently point at different, unrelated lines in the new hunk layout - corrupting exactly what gets staged and committed, without any error or warning to the user. This is structurally the same class of bug as the `Basket.sol#auctionBurn` finding: a value (`ibRatio` / here, the line-selection index) is computed from one state snapshot (`startSupply` / the old diff) but is applied against a second, already-mutated state snapshot (post-`handleFees` supply / the freshly re-diffed file), silently corrupting the result for all downstream consumers.

### Finding Description
- The renderer computes `DiffSelection` line indices against a specific diff object loaded by `updateChangesWorkingDirectoryDiff`, which fetches the diff once and stores it in `changesState.selection.diff` [1](#0-0) .
- The UI translates the user's individual line checks into absolute indices with `hunk.unifiedDiffStart + lineIndex` and stores them via `DiffSelection.withLineSelection`/`withRangeSelection` [2](#0-1) .
- When the commit is finally staged, `stageFiles` calls `applyPatchToIndex` for every partially-selected file [3](#0-2) .
- `applyPatchToIndex` re-fetches the diff from disk at commit time rather than reusing the diff the selection was validated against, then hands that freshly computed diff plus the stale `file.selection` straight to `formatPatch`: [4](#0-3) .
- `formatPatch` maps selection state onto the new diff purely via `hunk.unifiedDiffStart + lineIndex` → `file.selection.isSelected(absoluteIndex)`, with no verification that the new diff's hunk boundaries/line ordering correspond to the diff that produced those absolute indices: [5](#0-4) .
- There is a partial staleness guard elsewhere in the code (`updateChangesWorkingDirectoryDiff` re-checks selection state after its own async diff load, and clears/prunes selectable lines when the diff visibly changes) but this guard only fires when the renderer happens to reload the diff for *display*; it is not consulted or enforced by `applyPatchToIndex`/`stageFiles`/`createCommit` at commit time [6](#0-5) . The commit path (`_commitIncludedChanges` → `createCommit` → `stageFiles`) never revalidates the diff shape before applying selection indices [7](#0-6) .

The corrupted value is the mapping from `DiffSelection` absolute line index → actual hunk/line content used to build the `git apply --cached` patch. Because `applyPatchToIndex` re-diffs independently of the diff the user actually reviewed, that mapping can point at the wrong content whenever the file was modified in between - and Desktop applies the resulting patch to the index unconditionally.

### Impact Explanation
If a tracked file's content in the working directory is rewritten between the time the user reviews/selects lines in the diff view and the time they click "Commit" (e.g., by a repository-provided git `smudge`/`clean` filter, a `post-checkout`/build hook triggered on file access from a hostile cloned repository, or any background process the repository can spawn that touches the file), the patch built for staging no longer corresponds to the hunks the user actually approved. This is a silent corruption of what the user commits and pushes: lines the user never reviewed can be staged/committed instead of (or in addition to) the ones they selected, and lines they explicitly excluded can end up committed. Because this happens with no error and no re-confirmation dialog, the user has no signal that the committed diff differs from what they saw and approved, satisfying the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Requires a maliciously crafted or compromised repository capable of mutating a tracked file's on-disk bytes during the (attacker-influenceable) window between diff-review and commit — e.g., via a repository-supplied git hook/filter, a build script the repo triggers, or another local tool watching the repo that the attacker's repository intentionally interacts with. It does not require local/physical access, admin rights, prior malware, or leaked credentials — only that the victim opens/works with a cloned repository containing such automation and commits a partial selection while it is active. This is a plausible, repo-controlled trigger rather than a purely theoretical race, but does require some timing coincidence, so likelihood is moderate.

### Recommendation
`applyPatchToIndex` (and `formatPatchToDiscardChanges`'s caller path) should not silently re-diff and reapply stale absolute-index selections. Instead:
- Pass the exact `ITextDiff` object the selection was validated against (the one already available in `changesState.selection.diff` / passed through the commit context) into `stageFiles`/`applyPatchToIndex`, rather than re-fetching a new diff at apply time.
- If a fresh diff must be fetched for correctness (e.g., to guard against a stale renderer diff), compare it against the diff the selection was derived from (e.g., hash of hunk headers/line counts) and abort/re-prompt the user if they differ, rather than silently applying mismatched indices.

### Proof of Concept
1. In a malicious repository, add a `pre-commit`-adjacent local automation (e.g., a file watcher script started by a `postCheckout`/npm lifecycle hook that Desktop or an IDE opened alongside the repo triggers) that rewrites `tracked-file.txt` shortly after it is opened for diffing.
2. Victim opens the repository in Desktop, views the diff for `tracked-file.txt`, and selects only lines 1–3 for a partial commit. The renderer computes and stores `DiffSelection` absolute indices based on the diff as rendered: [8](#0-7) .
3. Before the victim clicks "Commit," the hook rewrites `tracked-file.txt`, changing hunk boundaries/line counts.
4. Victim clicks "Commit." `stageFiles` → `applyPatchToIndex` re-fetches the diff from disk (now different) and calls `formatPatch(file, diff)` using the old selection indices: [4](#0-3) .
5. `formatPatch` interprets the stale absolute indices against the new hunk layout, producing a patch containing different content than what the user selected on screen, which is applied to the index and committed without any warning: [5](#0-4) .
