### Title
`resolveWithin()` prefix check allows path traversal outside repository root via deep-link `filepath` parameter - (File: `app/src/lib/path.ts`)

### Summary
The report's broken invariant is: *user-controlled input reaches a security-sensitive sink without a correctness check, so the intended safety guarantee silently fails.* In the Velodrome case that guarantee was "enough gas is attached"; in GitHub Desktop the analogous guarantee is "a file path derived from an attacker-controlled deep link stays inside the repository root." That guarantee is implemented by `resolveWithin()` in [1](#0-0) , and the check it uses (`realResolved.startsWith(realRoot)`) is a plain string-prefix comparison with no path-separator boundary, which is a well-known incomplete-containment-check bug.

### Finding Description
`app/src/main-process/main.ts` registers the `x-github-client` (and `github-mac`/`github-windows`) custom protocol and forwards any URL opened by the OS to `handleAppURL` [2](#0-1) . `parseAppURL()` parses `openrepo` deep links and extracts an attacker-controlled `filepath` query parameter with only light validation (branch/pr format checks; `filepath` itself is passed through unsanitized) [3](#0-2) .

That `filepath` is later consumed in `Dispatcher.openRepositoryFromUrl`: [4](#0-3) 
The only guard against traversal is `isAbsolute(filepath)` (blocking absolute paths) followed by `resolveWithin(repository.path, filepath)`.

`resolveWithin` resolves the segments and then validates containment with:
```
return realResolved.startsWith(realRoot) ? resolved : null
``` [5](#0-4) 

This is a classic prefix-check flaw: `startsWith` does not require a path separator (or exact match) after `realRoot`. If the repository lives at `/Users/victim/Documents/GitHub/repo` and a sibling directory exists that shares the same string prefix (e.g. `/Users/victim/Documents/GitHub/repo-backup`, `/Users/victim/Documents/GitHub/repository`, or any directory named `repo*`), a relative `filepath` such as `../repo-backup/secrets.txt` resolves to a path outside the intended repository but still passes the `startsWith(realRoot)` test, because the string `"…/repo-backup/secrets.txt"` starts with `"…/repo"`.

Unlike `sanitizeCloneName`/`isClonePathSensitive` used for clone destinations [6](#0-5) , there is no equivalent boundary-aware check applied to `resolveWithin`, so this specific containment guard is weaker than the guards used elsewhere in the same codebase for similar purposes.

### Impact Explanation
The exact corrupted value is the resolved absolute path handed to `shell.showItemInFolder(resolved)` [7](#0-6) . A crafted deep link that a user clicks (e.g. from a malicious webpage, README, or chat message) can cause Desktop to reveal/open a file located outside the intended repository directory, in any sibling directory whose name happens to share the repo directory's name as a prefix. This matches the allowed impact class "a link or deep link the user clicks… result is file… read outside the repo." The severity is bounded by needing a same-prefix sibling directory to exist, but many real-world workspace layouts (e.g., `repo`, `repo-old`, `repo.bak`, `repository`) make this plausible without any special local setup by the attacker.

### Likelihood Explanation
The attack requires only a single click on a `x-github-client://openrepo/...` deep link (or `github-mac://openRepo/...` on macOS) with a crafted `filepath` query parameter — no local access, no malware, no credential leak, and no unnatural additional steps beyond the normal "open in Desktop" flow that GitHub already advertises for these protocol links. The existing guard (`isAbsolute` check) does not block relative traversal sequences, and the `resolveWithin` containment check is the only remaining line of defense, which is bypassable by the prefix issue described above.

### Recommendation
Change the containment check in `_resolveWithin` (`app/src/lib/path.ts`) to require an exact match or a path-separator boundary after the root, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(with the appropriate separator for the `options` variant being used — `/` for POSIX, `\` for Win32). Add regression tests covering sibling directories that share a name prefix with the root (mirroring the existing traversal tests in `app/test/unit/path-test.ts`).

### Proof of Concept
1. Victim has a repository open at `/Users/victim/Documents/GitHub/repo`, and a sibling directory `/Users/victim/Documents/GitHub/repo-secrets` exists (e.g., a backup or unrelated folder).
2. Attacker sends the victim a link: `x-github-client://openrepo/https://github.com/victim/repo?branch=main&filepath=..%2Frepo-secrets%2Fcredentials.txt`
3. Victim clicks the link; Desktop is launched/foregrounded via `handleAppURL` → `parseAppURL` → `open-repository-from-url` action [3](#0-2) .
4. `Dispatcher.openRepositoryFromUrl` finds the existing repository, then processes `filepath = "../repo-secrets/credentials.txt"`. `isAbsolute()` returns `false`, so the check passes [8](#0-7) .
5. `resolveWithin('/Users/victim/Documents/GitHub/repo', '../repo-secrets/credentials.txt')` resolves to `/Users/victim/Documents/GitHub/repo-secrets/credentials.txt`, whose real path string starts with `/Users/victim/Documents/GitHub/repo` — passing the flawed check in [9](#0-8) .
6. `shell.showItemInFolder(resolved)` reveals/opens the file outside the intended repository boundary.

Note: I was not able to fully verify every other caller of `resolveWithin` (`copilot-conflict-context.ts`, `app-store.ts`) for exploitability within this session; the deep-link path above is the one with the clearest attacker-controlled, unprompted trigger (a clicked link) and file-read-outside-repo impact.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
