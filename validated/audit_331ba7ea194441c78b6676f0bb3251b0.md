## Title
Decimal-scaling underflow in `convert_to_erc20`/`convert_to_balance` lets cross-chain transfers mint amounts inflated by 10^(local_decimals − erc_decimals) - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token` scales amounts between a local Substrate asset's decimals and the registered EVM contract's decimals (`Precisions` storage) using `convert_to_erc20`/`convert_to_balance`. Both helpers compute the scaling exponent with `erc_decimals.saturating_sub(local_decimals)` (or the inverse), which silently clamps to `0` — i.e. "no scaling" — whenever the local asset's decimals exceed the destination chain's decimals. This is exactly the bug class in the external report: a single scaling assumption that fails once two sides disagree on decimals, corrupting the amount that is escrowed/minted/released.

### Finding Description
`convert_to_erc20` and `convert_to_balance` are the only place amounts are translated between the local asset's precision and the remote EVM contract's precision: [1](#0-0) 

Both functions use `saturating_sub` on the decimal difference and only ever act in one direction (multiply in `convert_to_erc20`, divide in `convert_to_balance`). They implicitly assume `erc_decimals >= local_decimals`. When a registered asset's local decimals are *greater* than the destination chain's registered `Precisions` decimals (a completely normal, governance-set configuration — e.g. a locally 18-decimal asset bridging to a 6-decimal stablecoin representation on EVM, or any native currency configured with more precision than the peer contract), `erc_decimals.saturating_sub(local_decimals)` evaluates to `0`, so the multiplier becomes `10^0 = 1` — the raw integer amount is passed through completely unscaled.

`send()` calls `convert_to_erc20(amount, erc_decimals, decimals)` right after escrowing/burning `amount` in local units, and puts the *unscaled* raw integer into the outbound `Message.amount` field that is ABI-encoded and dispatched to the peer EVM contract: [2](#0-1) 

Because the raw integer is not divided down to the destination's coarser precision, the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract interprets that raw integer using its own (lower) decimals, minting/releasing an amount inflated by `10^(local_decimals - erc_decimals)` relative to what was actually escrowed on the source chain.

The symmetric bug exists on `on_accept` via `convert_to_balance`, which under-credits the local beneficiary in the mirrored scenario (destination decimals lower than local decimals, receiving inbound): [3](#0-2) 

No check anywhere validates that `erc_decimals >= local_decimals` before this arithmetic runs, and `register_token`/`update_token` place no ordering constraint on the configured decimals: [4](#0-3) 

### Impact Explanation
Any unprivileged user who calls `send()` for an asset whose local decimals exceed the registered destination `Precisions` decimals can escrow a trivially small amount locally while causing the peer EVM contract to mint/release an amount inflated by orders of magnitude (`10^(local_decimals - erc_decimals)`). For non-native (mint/burn) assets, this results in unbacked token inflation on the destination chain; for native assets, it can drain far more from the destination's escrow custody than was ever locked on the source side. This is a direct "bridged assets must move exactly once and only to the rightful beneficiary and amount" violation and a fund-theft/fund-loss primitive reachable by any ordinary user, not a relayer/prover/admin.

### Likelihood Explanation
This does not require a malformed proof, malicious relayer, or governance misbehavior — it is triggered purely by normal, foreseeable configuration (any asset registered with higher local decimals than the peer chain's contract decimals, which is common since many EVM stablecoins use 6 decimals while Substrate assets frequently use 10, 12, or 18). Once such an asset is registered, exploitation is a single unauthenticated `send()` call from any signed account.

### Recommendation
Replace the one-directional `saturating_sub`-based scaling with symmetric logic that scales in the correct direction regardless of which side has more decimals: if `erc_decimals >= local_decimals`, multiply by `10^(erc_decimals - local_decimals)`; if `local_decimals > erc_decimals`, divide by `10^(local_decimals - erc_decimals)` (with explicit rejection or safe truncation-aware handling of the resulting precision loss). Apply the fix symmetrically to both `convert_to_erc20` and `convert_to_balance`, and add a unit test that registers an asset with local decimals greater than the configured `Precisions` value to lock in the corrected behavior.

### Proof of Concept
1. Governance registers an asset (e.g. via `register_token`) with local `decimals = 18` (or the native asset with `T::Decimals = 18`) and a `Precisions` entry for the destination chain of `erc_decimals = 6` (mirroring a common EVM stablecoin).
2. A user calls `send()` with `amount = 1` (1 raw local unit, effectively dust).
3. Inside `send()`, `erc_decimals.saturating_sub(decimals)` = `6u8.saturating_sub(18)` = `0`, so `convert_to_erc20` returns `amount * 10^0 = 1` unchanged instead of the mathematically correct (fractional/near-zero) scaled-down value.
4. Reversing the numbers to see the amplification: a user escrows `amount = 1_000_000_000_000_000_000` (1 whole token in 18-decimal local units). `convert_to_erc20` still returns `1_000_000_000_000_000_000` unscaled (multiplier stuck at `10^0`).
5. This raw value is placed in `Message.amount` and dispatched to the peer `HyperFungibleToken` contract on the 6-decimal destination chain, which mints/releases `1_000_000_000_000_000_000` raw units — interpreted at 6 decimals, this is `1,000,000,000,000` (one trillion) whole tokens, versus the `1` whole token actually escrowed on the source chain. /// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
