### Title
Aggregator's `Noop` interceptor when `client_verification=false` removes the "internal-only" access control on `SendMoveToVaultTx`/`InternalSendTx` - (File: core/src/servers.rs, core/src/rpc/interceptors.rs)

### Summary
`create_grpc_server` chooses the interceptor solely from `config.client_verification`, applying `Interceptors::Noop` to every entity's gRPC server, including the aggregator's own listener created by `create_aggregator_grpc_server`. When this flag is `false`, the `is_internal`/self-cert check in `only_aggregator_and_self` is never invoked, so any caller with a plain TLS (non-mTLS) connection can call methods normally gated as "internal-only," such as `SendMoveToVaultTx`.

### Finding Description
The claimed binding is: `caller reaches AggregatorServer::send_move_to_vault_tx` ⇒ `caller possesses aggregator_cert / our_cert` (i.e., is an authenticated self/aggregator peer).

In `core/src/servers.rs::create_grpc_server`, the interceptor wiring is: [1](#0-0) 
When `config.client_verification` is `false`, `Interceptors::Noop` is installed for **every** service passed into `create_grpc_server` — this includes the aggregator, since `create_aggregator_grpc_server` calls the same generic function with no special-casing: [2](#0-1) 

`Interceptors::Noop` simply returns the request unmodified with no certificate inspection at all: [3](#0-2) 

Contrast this with the `OnlyAggregatorAndSelf` path, which specifically distinguishes "internal" RPCs (prefixed `Internal`) from normal ones, and requires the caller's leaf certificate to equal `our_cert` for internal methods, or `aggregator_cert`/`our_cert` for regular ones: [4](#0-3) [5](#0-4) 

This `is_internal` gate is the only authorization mechanism in the codebase for methods like `InternalSendTx`/`SendMoveToVaultTx`; it exists entirely inside the interceptor, not inside the RPC handler itself. When `client_verification=false`, this gate is bypassed unconditionally — `Noop` performs zero identity checks, so a caller who opens a TLS connection to the aggregator's public port with no client certificate whatsoever reaches the handler exactly as if it were the aggregator or itself.

Additionally, `BridgeConfig::check_mainnet_requirements` only forbids `client_verification=false` for `cli::Actor::Verifier` and `cli::Actor::Operator`, but not for `cli::Actor::Aggregator`: [6](#0-5) 
So this misconfiguration is not blocked by the mainnet safety checks for the aggregator itself, and the deployment doc explicitly documents running the aggregator this way ("does not enforce client certificates but does use TLS for encryption").

I was not able to fetch the full body of `AggregatorServer::send_move_to_vault_tx` / `internal_send_tx` (grep confirms matches in `core/src/rpc/aggregator.rs` and `core/src/rpc/clementine.rs`, but the file is large and truncated in this session), so I cannot independently confirm from this session whether the handler itself performs additional cryptographic validation of the transaction bytes (e.g., that they contain a fully N-of-N-signed move-to-vault transaction) before submission to the tx-sender queue. That is a material gap in this verification.

### Impact Explanation
The finding as demonstrated is: the authorization boundary (`is_internal` + self-cert check) that is supposed to restrict internal-marked RPCs to the aggregator/self is completely disabled network-wide by a single boolean, with no compensating control in `create_grpc_server` or `Noop`. This matches the High category "an unauthenticated state-changing or broadcasting call" for the internal `SendMoveToVaultTx`/`InternalSendTx` path specifically, since that method is architecturally intended to be internal-only (per the `Internal` prefix convention checked in `is_internal`). Whether this reaches Critical (BTC actually pushed to broadcast without a valid N-of-N signature) depends on handler-level validation I could not confirm in this session.

### Likelihood Explanation
Preconditions: the aggregator must be deployed with `client_verification=false` (a real, documented, non-default configuration; `Default` sets `client_verification: true`) and its public gRPC port reachable by the attacker. Given `check_mainnet_requirements` does not enforce `client_verification=true` for the Aggregator actor, this misconfiguration would pass mainnet config validation. No BTC cost is required to reach the endpoint — only a plain TLS connection.

### Recommendation
Do not derive the interceptor purely from `client_verification`; always enforce the `is_internal` self-cert check for methods marked `Internal*` regardless of `client_verification`, or reject `client_verification=false` outright for the Aggregator actor in `check_mainnet_requirements` and in `create_aggregator_grpc_server`. Move the "internal-only" authorization out of the interceptor into an explicit, non-bypassable guard in the handler itself.

### Proof of Concept
Because full confirmation of `send_move_to_vault_tx`/`internal_send_tx` handler-level validation was not obtained in this session (file truncation, no more tool budget), and because `core/src/test/**` is explicitly out of scope for citation/reproduction per the rules, I cannot construct a fully-verified `cargo test` proof here. pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}

        return false;
