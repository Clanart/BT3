### Title
Cached DKG-confirmation nonces are reused across `share`/`complete` invocations whose effective message and signing set depend on the ordering of `RemoveParticipantDueToDkg` finalization - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The M-03 bug class is a state-changing operation whose outcome depends on whether a pending transition was applied first — two distinct, externally-orderable results. In Serai, `SigningProtocol::preprocess_internal` deterministically regenerates FROST nonces from a seed cached in `CachedPreprocesses` keyed only by `(b"DkgConfirmer", attempt)`. Both `DkgConfirmer::share` (via `generated_key_pair`, handle.rs:57-59) and `DkgConfirmer::complete` (via the `DkgConfirmed` accumulation path, handle.rs:535 → share_internal again, signing_protocol.rs:322) re-derive the *same* nonces, while the participant mapping and the signed message `set_keys_message(set, removed, key_pair)` are computed lazily from `removed_as_of_dkg_attempt` at each invocation. If a `RemoveParticipantDueToDkg` transaction finalizes between these two calls — ordering decided by whichever validator publishes it and when — the second signature share commits to a different `removed` list (different MuSig participant mapping in `threshold_i_map_to_keys_and_musig_i_map`, different message) under reused binomial nonces `(d, e)`.

### Finding Description
- `preprocess_internal` loads or creates a 32-byte seed in `CachedPreprocesses` under `context = (b"DkgConfirmer", attempt)` and rebuilds the sign machine via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` → `Commitments::new(ChaCha20Rng::from_seed(seed), ...)` (sign.rs:121-144). Nonces are therefore fixed per attempt, not per invocation.
- `share_internal` (signing_protocol.rs:288-301) builds `participants` and `msg` from `self.removed`, which is captured in `DkgConfirmer::new` from `removed_as_of_dkg_attempt(txn, genesis, attempt)` (line 271). `removed` is mutated whenever `fatal_slash`/`RemoveParticipantDueToDkg` reaches threshold (handle.rs:281-283).
- `generated_key_pair` signs once when our `DkgConfirmed` share is produced; `DkgConfirmed` handling calls `confirmer.complete(...)`, which internally calls `share_internal` a **second** time (signing_protocol.rs:322) and re-emits a signature share under the same nonces.
- The file's own safety argument (lines 25-54) states nonce reuse is impossible only because "received messages" are BFT-final — but `removed` and `key_pair` are *local DB state read at call time*, not part of the BFT-received message set. An ordering change of `RemoveParticipantDueToDkg` vs. `DkgConfirmed` finalization within the same attempt makes the second `sign()` operate on distinct inputs with identical nonces — exactly the front-run/back-run divergence of the source report. The TODO at line 50-54 admits the matching check ("commitments generated from the decided nonces are in fact its commitments on-chain") is unimplemented.

### Impact Explanation
Each signature share is `s = d + e·ρ_i + λ_i·scalar·share·c`, with `d, e` constant across invocations. Every additional `share`/`complete` execution under a mutated `removed` set (each removal finalization changes both the participant-index map and `msg`) publishes another linear equation over the same three unknowns `(d, e, λ·scalar·share)` on a public ledger (`DkgConfirmed` transactions). With ≥3 distinct sessions — reachable via repeated removal votes processed at different points in the attempt — the system becomes determined and the validator's MuSig secret share (the root-of-trust key) is recoverable by any observer. Even absent extraction, divergent `removed` between preprocess-time commitments and share-time `view(included)` yields an invalid aggregate confirmation, stalling `publish_set_keys` (key confirmation DoS). The two divergent end-states are selected purely by the ordering an external signer chooses for their `RemoveParticipantDueToDkg` transaction — the analog of front-running vs. back-running `transitionEpoch`.

### Likelihood Explanation
Triggering requires a `RemoveParticipantDueToDkg` vote crossing threshold between `DkgShares` accumulation (`ConfirmationNonces::set`, generated share) and `DkgConfirmed` accumulation (`complete` → second share). Any single validator can publish a removal vote; ordering relative to DkgConfirmed is not constrained by the protocol (attempt counters are equal, both are valid same-attempt transactions). Reaching three distinct share-publications for share extraction requires repeated removals — harder, keeping this at Medium; the inconsistent-signature/DoS outcome needs only one reordered finalization.

### Recommendation
Bind the cached preprocess context to the full signing inputs, not just `(label, attempt)`: include `removed` and the `key_pair` hash in `CachedPreprocesses`' context key (e.g., `context = (b"DkgConfirmer", attempt, removed.encode(), key_pair)`), or compute the message/participant map once at preprocess time and persist it alongside the seed, refusing to `sign` if the current `removed`/`key_pair` differ from the persisted values. This is the analog of applying `updateEpoch` before `setEpochDuration`: finalize (snapshot) the pending state before acting on it. Additionally implement the noted TODO of verifying on-chain commitments match the locally presumed preprocess before publishing shares.

### Proof of Concept
Conceptual trace (both orderings valid same-attempt transaction sequences):

Ordering A (removal first):
1. `DkgShares` accumulation completes → `ConfirmationNonces::set`.
2. `RemoveParticipantDueToDkg(v)` reaches `t` → `fatal_slash(v)`; `removed_as_of_dkg_attempt` now includes `v`.
3. `generated_key_pair` → `share()` uses `removed ∪ {v}`, signs `set_keys_message(.., removed∪{v}, kp)` with nonces from seed `(DkgConfirmer, attempt)`.
4. `DkgConfirmed` accumulation → `complete` → second `share_internal` with identical `removed` — consistent result (equivalent to `transitionEpoch` before the update).

Ordering B (confirmation first):
1. `DkgShares` completes → `generated_key_pair` → `share()` signs `set_keys_message(.., removed, kp)` with nonces `d, e`, ρ-vector over map M₁, share `s₁` implicitly committed.
2. `RemoveParticipantDueToDkg(v)` finalizes → `removed` gains `v`.
3. `DkgConfirmed` accumulation → `complete` → `share_internal` recomputes over `removed ∪ {v}`: `threshold_i_map_to_keys_and_musig_i_map` shifts all Musig indices after `v`, `msg` embeds the larger removed list, nonce sums/binding factors and challenge `c` all differ — yet `d, e` are regenerated identically from the same cached seed. Share `s₂` is published on-chain: a second equation over the same nonce secrets.
4. Repeatable with further removals → ≥3 published shares under fixed `(d, e)` → solve for the validator's secret share; at minimum the aggregate signature over divergent messages fails, halting set-keys confirmation.

The divergent end-state is decided solely by when an external validator's removal transaction finalizes relative to the confirmation transactions — the same externally-orderable inconsistency as M-03.

Note: severity depends on whether the processor-side signing paths (`processor/src/signer.rs`, in-memory machines) have an analogous lazy-state read; I could not fully verify those paths within the available iterations, but the coordinator `DkgConfirmer` path above is confirmed in the code.
