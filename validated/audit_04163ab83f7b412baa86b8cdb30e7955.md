### Title
Tron `IntentGatewayV2.instance()` silently trusts `address(this)` for any unregistered state machine, enabling forged cross-chain admin/escrow messages - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` diverges from the shared `IntentsBase.sol` trust model: instead of reverting when a remote peer has not been explicitly registered, `instance()` silently falls back to `address(this)` forever, which `authenticate()` then treats as an implicitly trusted peer for every unregistered chain.

### Finding Description
In the canonical implementation, `IntentsBase._instance()` reverts with `UnknownInstance` unless a deployment was explicitly registered via `_addDeployment` (either at `initialize()` or later via a `NewDeployment` governance message): [1](#0-0) 

The Tron fork instead defines: [2](#0-1) 

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}
```

and gates every incoming cross-chain module message on this value: [3](#0-2) 

```solidity
function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    if (instance(request.source) != module) revert Unauthorized();
}
```

Because `_instances[keccak256(stateMachineId)]` defaults to the zero value for *any* state machine that has never had an explicit `NewDeployment` entry recorded, `instance()` returns `address(this)` as the trusted peer for that chain **permanently**, not just during a bootstrap window. `RedeemEscrow`, `UpdateParams`, `SweepDust`, and `RefundEscrow` request kinds are routed through this same `authenticate()` gate.

### Impact Explanation
For any state machine that Hyperbridge's consensus layer supports but for which this specific `IntentGatewayV2` deployment has not yet been (or will never be) registered via `NewDeployment`, the contract implicitly authorizes any message whose `request.from` equals the local `address(this)`. If an attacker can get a contract deployed at that exact address on the source chain — plausible given the codebase's own deterministic CREATE2 deployment strategy across chains, where the address is derived from public bytecode/salt rather than a runtime secret — a message genuinely proven by that chain's consensus (real ISMP proof, no relayer/prover compromise needed) would still carry attacker-controlled semantics. `onAccept` would then execute `RedeemEscrow` (releasing escrowed funds to an attacker-chosen beneficiary), `UpdateParams` (rewriting fee/dispatcher/oracle parameters), or `SweepDust` (draining accumulated dust) against the real, deployed Tron gateway — i.e., unauthorized execution and fund loss without needing a malicious relayer, prover, or admin key.

### Likelihood Explanation
This requires only that (a) a state machine is enabled in Hyperbridge's consensus layer, and (b) this Tron gateway has not yet had a `NewDeployment` registered for that chain (a normal, expected operational gap during incremental rollout) — no privileged actor or protocol compromise is needed on the attacker's side, only the ability to land a contract at the expected CREATE2 address. Given I could not fully verify `onAccept`'s access modifier or the exact deployer/salt scheme used in production within the remaining iterations, treat the CREATE2-address-acquisition step as the open verification item; the authentication-fallback logic itself (default-trust-self instead of reverting) is confirmed directly in the source and is a clear deviation from the safe pattern used elsewhere in the same codebase.

### Recommendation
Make `instance()` on the Tron variant match `IntentsBase._instance()`: revert with `UnknownInstance` when `_instances[keccak256(stateMachineId)] == address(0)` instead of falling back to `address(this)`. If a bootstrap-trust-self period is intentional, scope it explicitly (e.g., a one-time `initializer`-gated set, as in the main `IntentGatewayV2.initialize()`) rather than as a permanent runtime default in the read path used for authentication.

### Proof of Concept
Conceptual (not executed, due to tool-call budget):
1. Governance enables consensus support for state machine `X` in Hyperbridge but has not yet dispatched a `NewDeployment` message to the Tron `IntentGatewayV2` for `X`.
2. Attacker deploys a contract to the same CREATE2 address as `address(this)` on chain `X` (using the same publicly known init code/salt scheme referenced in `IntentsBase.sol`'s deployment comments).
3. Attacker's contract dispatches a `PostRequest` (e.g., `RequestKind.RedeemEscrow` or `RequestKind.UpdateParams`) from chain `X` to the real Tron `IntentGatewayV2`.
4. `authenticate()` computes `instance(X) == address(this)` (default fallback) and matches `request.from == address(this)` (attacker's contract address), passing authentication.
5. `onAccept` executes the forged request, releasing escrow funds or rewriting protocol parameters. [4](#0-3)
