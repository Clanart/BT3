### Title
Malicious order beneficiary can permanently grief solvers on `fillOrder`, blocking native-token intents from ever being filled - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`IntentGatewayV2.placeOrder` lets any user set an arbitrary, unrestricted `order.output.beneficiary`. When a solver later calls the permissionless `fillOrder` entrypoint on a native-token-output order, `_fillSameChain` / `_fillCrossChain` push ETH to that attacker-controlled beneficiary with `beneficiary.call{value: ...}("")` and `revert` the entire transaction if the call fails. This is the same broken invariant as the Backd `TopUpAction` bug: an untrusted, protocol-external party (here the order creator, analogous to the "Staker") controls an address that a permissionless executor (the solver, analogous to the "Keeper") must pay during execution, and that address can be a contract that unconditionally reverts on `receive()`. Unlike the sibling `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` contracts — which explicitly guard against exactly this by falling back to a WETH ERC-20 transfer when the native push fails — `IntentsBase._withdraw`, `IntrinsicIntents._fillSameChain`, and `ExtrinsicIntents._fillCrossChain` have no such fallback and simply revert.

### Finding Description
`placeOrder` stamps `order.user` but does not validate or restrict `order.output.beneficiary` [1](#0-0) . An order creator can therefore set `beneficiary` to a purpose-built contract whose `receive()`/`fallback()` always reverts.

In the same-chain fill path, any solver calling `fillOrder` triggers `_fillSameChain`, which pushes the output amount directly to `beneficiary` via a raw call and reverts the whole transaction on failure: [2](#0-1) 

The identical pattern exists in the cross-chain fill path (`ExtrinsicIntents._fillCrossChain`) and in the generic escrow-release helper `_withdraw`, which is also reachable from the fill and cross-chain redemption flows: [3](#0-2) [4](#0-3) 

Because `fillOrder` is a public, permissionless entrypoint intended to be called by profit-seeking solvers (the "Keeper" equivalent in this protocol), any solver who attempts to fill such an order pays gas for the ERC-20 approval/transferFrom and dispatch logic that executes *before* the native push, then has the entire transaction — including state writes like `_filled[commitment]`, `_partialFills`, and escrow debits — rolled back the instant the malicious beneficiary's `receive()` reverts. The order becomes permanently unfillable by anyone (every solver hits the same revert), while the order creator retains the ability to cancel and reclaim their own escrowed input tokens at will via `_cancelSameChain`/`_cancelFromDest`, since those refund paths pay `order.user`, not an attacker-chosen beneficiary.

Notably, the developers were aware of this exact class of bug and mitigated it elsewhere: `WrappedHyperFungibleToken.onPostRequestTimeout`/receive-handling explicitly retries with a WETH ERC-20 transfer if the native push to an unpredictable recipient fails [5](#0-4) . No equivalent guard exists in `IntentsBase._withdraw`, `_fillSameChain`, or `_fillCrossChain`.

### Impact Explanation
This is a logic-level denial-of-service against the intent-fulfillment mechanism itself: an unprivileged, ordinary user (the order creator) can craft an order with a reverting beneficiary contract to guarantee that:
- Any solver that attempts to fill the order wastes gas and can never successfully execute it.
- The order remains permanently open/unfillable (its escrowed input tokens are inert liquidity that solvers can never earn against), directly undermining the intent-settlement guarantee that "orders move exactly once to the rightful beneficiary."
- Solvers have no way to detect this ahead of time short of simulating the fill and probing the beneficiary address, which still costs gas per attempt and can be repeated for many distinct orders, degrading solver economics network-wide.

This matches the accepted class of the source report (a designated, protocol-external party griefs the permissionless executor's gas/rewards via a `revert()`-only `receive()`), reframed onto Hyperbridge's intent-settlement path rather than a lending-position top-up.

### Likelihood Explanation
High: `placeOrder` performs no validation on `beneficiary` beyond decoding it as an address, and deploying a `receive() { revert(); }` contract is trivial and requires no privileged role, relayer, or governance access. Any user can place such an order at negligible cost.

### Recommendation
- In `IntentsBase._withdraw` (and the inline native-transfer sites in `IntrinsicIntents._fillSameChain` / `ExtrinsicIntents._fillCrossChain`), do not let a failed native push to `beneficiary` revert the whole fill.
- Mirror the pattern already used in `WrappedHyperFungibleToken`: on a failed native `.call`, fall back to wrapping the ETH (e.g., WETH) and delivering it as an ERC-20 transfer to `beneficiary`, or route unclaimed native funds to a per-beneficiary pull-payment/escrow mapping that the beneficiary can withdraw later, rather than blocking the solver's atomic fill.
- Alternatively, require `beneficiary` on native-output orders to pass a lightweight acceptance check at `placeOrder` time (e.g., a bounded-gas probe transfer) so unfillable orders are rejected up front instead of discovered by every subsequent solver.

### Proof of Concept
1. Deploy `MaliciousBeneficiary` with `receive() external payable { revert(); }`.
2. Call `IntentGatewayV2.placeOrder` with `order.output.beneficiary = address(MaliciousBeneficiary)`, `order.output.assets[0].token = address(0)` (native ETH), escrowing input tokens.
3. As a solver, call `fillOrder(order, options)` supplying sufficient `msg.value`.
4. Execution reaches `IntrinsicIntents._fillSameChain`'s `beneficiary.call{value: beneficiaryTotal}("")`, which reverts because `MaliciousBeneficiary.receive()` always reverts; the `if (!sent) revert InsufficientNativeToken();` check propagates this, reverting the entire `fillOrder` transaction and consuming the solver's gas.
5. Repeat with any other solver address — the outcome is identical every time, and the order can never be filled, only cancelled by `order.user` (the order creator/attacker) itself. [2](#0-1)
