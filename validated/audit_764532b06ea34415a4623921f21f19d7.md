### Title
Position-based (not content-based) diff line-selection identity lets a diff refresh silently remap a partial-commit selection to unintended lines - ([File: app/src/lib/stores/app-store.ts])

### Summary
GitHub Desktop's partial-commit feature tracks which lines a user has selected for staging using a purely numeric, position-based identifier (`unifiedDiffStart + lineIndex`), not a content- or line-content hash. When the working-directory diff for the currently selected file is refreshed (e.g. because the file on disk changed while the Changes view is still showing a prior selection), the app only prunes selection indices that fall outside the new diff's `selectableLines` set; it does not verify that a surviving index still refers to the same logical line. If the file changes in a way that shifts line positions but keeps the same index "shape" (same number of includeable lines at that position), a previously made line-level selection/deselection silently applies to different content than the user intended, and that different content is what gets built into the `git apply --cached` patch and committed — without any indication to the user that their selection now maps to something else.

### Finding Description
`DiffSelection` identifies lines purely by an absolute integer computed as `hunk.unifiedDiffStart + lineIndex`: [1](#0-0) 

This same identity scheme is used everywhere a line's "is it selected" state is queried, including inside the patch generator that turns a selection into the literal Git patch applied to the index: [2](#0-1) 

The `DiffSelection` class itself documents that it has "no notion of how many lines exist or what it is that is being selected" — it only knows integer indices: [3](#0-2) 

When the diff for the currently selected file is reloaded (this happens on file-watcher-driven working-directory refreshes while the Changes view is open, e.g. after an external process, background script, checkout hook, or IDE modifies the file), the app recomputes `selectableLines` from the *new* diff and calls `withSelectableLines`, which merely filters the existing `divergingLines` set to intersect with the new selectable set — it does not check whether index `N` in the old diff and index `N` in the new diff refer to the same source line: [4](#0-3) [5](#0-4) 

The code's own comment acknowledges this is a known limitation, framed only as a display-correctness workaround ("this could happen because we no longer know if the line still exists") rather than as an integrity issue: [6](#0-5) 

This is structurally the same broken invariant as the Seaport bug: a value (there, "amount spent"; here, "which content is selected for commit") is tracked through an index/position that is computed once, then reused after the underlying object has been transformed (there, `acurr → b → acurr`; here, diff v1's line layout → diff v2's line layout), without re-deriving it from the new state. In both cases the stale index silently produces a wrong answer that is then acted upon as if it were correct — in Seaport shared with an external `validateOrder`/`ratifyOrder` call, in Desktop fed directly into `git apply --cached` via `applyPatchToIndex`: [7](#0-6) 

### Impact Explanation
If a file's diff changes between the time a user makes a partial line selection and the time they click Commit — for example because a cloned/fetched repository ships a `post-checkout`/`post-merge`/`pre-commit` hook, a build tool, a linter/formatter-on-save, or any file watcher that rewrites the file, or because the user is editing the file in their IDE concurrently with Desktop's own file-watcher-driven diff refresh — Desktop can silently re-target the user's line selection onto different content without any visual re-confirmation. The result is that the git object created and committed (and potentially pushed) does not match what the user believes they selected: content the user explicitly deselected (e.g. a security check, a secret, or a malicious injected line from a hook) can end up included, or content the user meant to keep can be silently dropped. This is exactly the "silent corruption of what the user commits or pushes" impact category, driven by an attacker-influenced repository/hook rather than any local/physical access.

### Likelihood Explanation
This requires a specific but realistic sequence: the user must have an in-progress partial selection on a file, and the working copy of that same file must be modified (by something other than the Desktop UI itself) before the commit is finalized. Malicious repositories routinely ship Git hooks and tooling configs (pre-commit/post-checkout scripts, formatters, codegen) that can trigger exactly this kind of file rewrite as a side effect of normal operations the user performs (checking out a branch, pulling, running a configured lint-staged/husky hook). The bug does not require any unusual local access — it only requires the diff to legitimately change while a partial selection is still held, which the existing code path already anticipates (hence the comment), but does not fully account for. Likelihood is moderate: it depends on timing and on the target file being under a partial (not "select all") commit, but is realistically triggerable by content the attacker controls in the cloned repo.

### Recommendation
Replace position-based line identity with content- or hunk-relative-and-content-anchored identity for `DiffSelection`, or, at minimum, when a diff reload occurs for the currently selected file, invalidate (reset to none-selected, or reconcile via a text/patience diff between old and new hunk line texts at each surviving index) rather than merely intersecting index sets. Concretely, in `withSelectableLines`/the caller in `app-store.ts`, compare the actual line text (and type) at each `divergingLines` index between the previous and new diff before preserving its selection state; drop (or force-reset) any index whose underlying line content changed instead of assuming the same index still means the same thing.

### Proof of Concept
1. Modify a tracked file with several lines and open it in GitHub Desktop's Changes view so a partial-line diff is shown.
2. Deselect a specific "risky" added line (e.g. `+downloadAndRun(url)`), keeping the rest selected. This records that index into `divergingLines` per `withRangeSelection`/`withLineSelection`.
3. While the Commit button/dialog is still open (selection not yet turned into a patch), have an external process — simulating a malicious repo hook (`post-checkout`, file watcher, formatter-on-save) — rewrite the same file so that a hunk's line count changes in a way that keeps the total number of includeable lines the same but shifts which line falls at the previously-deselected index (e.g. insert a line above the previously "safe" content and remove one elsewhere in the same hunk).
4. Desktop's diff auto-refresh recomputes `selectableLines` and calls `withSelectableLines`, which keeps the stale index in `divergingLines` because it is still "selectable" in the new diff, per: [4](#0-3) 
5. Click Commit. `formatPatch` builds the patch using `file.selection.isSelected(absoluteIndex)` against the *new* hunk lines at that same index — which is now the "risky" line the user thought they had deselected, or vice versa: [8](#0-7) 
6. `applyPatchToIndex` stages that patch and the subsequent commit silently includes content the user never intended: [9](#0-8) 

Note: I was not able to fully trace every code path that triggers a mid-selection diff reload (e.g., the exact file-watcher wiring) within the indexed portion of this codebase; a Devin session with full repository access would be needed to confirm the exact trigger conditions and timing window end-to-end.

  public withSelectableLines(selectableLines: Set<number>) {
    const divergingLines = this.divergingLines
      ? new Set([...this.divergingLines].filter(x => selectableLines.has(x)))
      : null

    return new DiffSelection(
      this.defaultSelectionType,
      divergingLines,
      selectableLines
    )
  }
