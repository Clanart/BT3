### Title
Panic in `GeneratorPromotion::complete` via attacker-controlled participant key set causes denial of service - (File: crypto/dkg/promote/src/lib.rs)

### Summary
Analogous to CVE-2021-46048 (assertion abort on untrusted input in `WasmBinaryBuilder::readFunctions`), `GeneratorPromotion::complete` performs an unchecked `HashMap::get(...).unwrap()` on the attacker-influenced `proofs` map. A participant that supplies a `proofs` map containing the receiver's own participant index (while omitting a required index) triggers a panic instead of an error, aborting the calling process during a `complete` step driven by deserialized `GeneratorProof` bytes.

### Finding Description
`GeneratorPromotion::complete` validates only the count and upper bound of the `proofs` map: [1](#0-0) 

It checks `proofs.len() == n - 1` and that every key is `<= params.n()`, but never checks that the map's keys are exactly the set `1..=n` minus `params.i()`. It then iterates every `i` in `1..=params.n()` except `params.i()` and unconditionally unwraps: [2](#0-1) 

Because `HashMap` keys are unique, a map of `n - 1` entries where every key is `<= n` but which includes `params.i()` must omit some other required participant `j`. When the loop reaches `j`, `proofs.get(&j).unwrap()` panics. The proofs themselves are parsed from peer-supplied bytes via `GeneratorProof::read` (which internally uses `C::read_G` and `DLEqProof::read`), so a malformed-but-parseable set of messages reaches this code path. This mirrors the Binaryen bug class: an unchecked invariant (assertion/`unwrap`) reachable from inputs produced by an untrusted counterparty crashes the process rather than returning `Err`.

### Impact Explanation
A single message set in the generator-promotion flow aborts the node/process running `complete`, denying service. Since promotion is part of the DKG/key-management stack (`crypto/dkg`), the crash kills the in-progress key operation and, depending on how the host handles panics (no `catch_unwind`, `panic=abort`, or unwinding into non-panic-safe state), takes down the signer entirely — directly comparable to the availability impact (A:H) of the reference advisory.

### Likelihood Explanation
Triggering requires only sending a `proofs` map whose serialization parses (all `GeneratorProof::read` calls succeed) but whose key set includes the victim's own index. No valid proofs are needed — verification is never reached for the omitted participant because the panic occurs before/at `get(&i).unwrap()` for that index, and the `DLEqProof::verify` of other entries may not even run depending on iteration order. Any participant able to feed `complete` with crafted messages reaches it deterministically.

### Recommendation
Replace the indexing with checked lookups: iterate `1..=n` skipping `params.i()` and return `PromotionError::InvalidParticipant`/`IncorrectAmountOfParticipants` when `proofs.get(&i)` is `None`, or pre-validate that `proofs` keys equal exactly `all_participant_indexes() \ {params.i()}` (rejecting `params.i()` itself), similar to `validate_map` used in `crypto/frost/src/sign.rs`. The final `ThresholdKeys::new(...).unwrap()` at line 165 should likewise be mapped to an error.

### Proof of Concept
For `n = 3`, `params.i() = 1` (victim). Attacker-controlled `proofs` map: `{Participant(1): valid_proof, Participant(3): valid_proof}` — length `2 == n - 1`, all keys `<= n`, passes both checks. Loop over `1..=3` skips `1`, unwraps `proofs.get(&2)` → `None.unwrap()` → panic. Constructed by serializing two parseable `GeneratorProof`s (any `C::G` share + any `DLEqProof` bytes that deserialize; validity is irrelevant since verification of participant 2 is never reached) and inserting them under keys `1` and `3` before calling `promotion.complete(&proofs)` in `crypto/dkg/promote/src/lib.rs`.

Confidence note: reachability is contingent on the caller passing a `complete` map assembled from multiple distinct peers' messages without its own identity-checks; the panic itself is fully verified from the code paths cited.
