### Title
Unbounded length prefix in `SchnorrAggregate::read` enables remotely triggered CPU/IO exhaustion (hang) on untrusted bytes - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` trusts a 4-byte little-endian length prefix and loops `u32` times calling `C::read_G` — up to ~4.29 billion point-deserialization attempts — with no cap, no pre-check against remaining input, and no allocation limit. This is a direct analog of CVE-2020-14654's bug class (a hang / resource-exhaustion DoS reachable by an unprivileged remote party through crafted input bytes).

### Finding Description
In `crypto/schnorr/src/aggregate.rs:77-88`, deserialization reads a `u32` count and then loops that many times:

```rust
// crypto/schnorr/src/aggregate.rs:77-88
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
  let mut len = [0; 4];
  reader.read_exact(&mut len)?;

  let mut Rs = vec![];
  for _ in 0 .. u32::from_le_bytes(len) {
    Rs.push(C::read_G(reader)?);
  }

  Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```

Two compounding issues:

1. **No bound check**: `len` can be `u32::MAX`. Any `read_G` call feeds directly off the untrusted stream; if the reader is a network-backed `io::Read` (or any reader that blocks/buffers rather than hitting EOF immediately), the victim performs up to ~4.29 billion curve-point decode operations (~137 GB of reads for a 32-byte encoding), hanging the thread indefinitely. There is no `Vec::with_capacity` pre-allocation, but also no early sanity check such as comparing `len` against a protocol maximum.

2. **Contrast with the project's own convention**: the adjacent `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:591-616`) bounds its loops by `n: u16` and validates via `ThresholdParams::new`, and the coordinator's DKG transaction reader caps `commitments_len * each_commitments_len` against `TRANSACTION_SIZE_LIMIT`. `SchnorrAggregate::read` has no equivalent ceiling — the aggregate size is attacker-chosen rather than fixed by the protocol.

The verify path (`verify`, `crypto/schnorr/src/aggregate.rs:127-146`) additionally builds `pairs` of `2*len+1` elements and runs `multiexp_vartime` over all of them, so even a successfully-read large aggregate imposes a Pippenger/Straus pass proportional to the attacker's declared count — again with no cap enforced by the library itself.

### Impact Explanation
A remote unauthenticated party that can feed bytes into a `SchnorrAggregate::read` (or any composite `read` embedding it) forces the deserializing node into a CPU-bound / blocking-read loop of attacker-controlled length — a denial of service against the validator/processor thread analogous to the "hang or frequently repeatable crash" impact of the reference advisory. If the reader never returns `Err` (e.g., a stream kept open, or a reader over a large padded buffer), the loop runs to completion of the attacker's declared count, not the honest message size.

### Likelihood Explanation
Reachability depends on the integrator wiring `SchnorrAggregate::read` to a length-unbounded transport reader; the function itself is `pub` and takes generic `R: Read`, so any deployment that deserializes aggregate signatures from peer/network input hits this path directly. The primitive contains no defense: the loop bound is purely attacker-controlled. Likelihood is moderate because Serai's primary FROST signing flow uses `SignatureShare`/`Preprocess` reads (fixed-size), but the aggregate type is exposed publicly for half-aggregation use cases and carries no documented size precondition.

### Recommendation
Enforce a maximum aggregate size before looping, e.g. reject `len` exceeding a protocol bound (the expected number of cosigners/signatures per batch), or check remaining input length when `R` supports it. Failing that, cap iterations at a hard constant (e.g., `MAX_AGGREGATE_SIGNATURES`) and document that callers on untrusted streams must wrap the reader in `io::Read::take` with a byte limit so that a malicious `len` is bounded by actual available input.

### Proof of Concept
```rust
use std::io::Cursor;
use ciphersuite::Ristretto;
use schnorr::aggregate::SchnorrAggregate;

// A reader that never reports EOF (models a kept-open network stream /
// large padded buffer). The declared count is u32::MAX.
struct EndlessZeros;
impl std::io::Read for EndlessZeros {
  fn read(&mut self, buf: &mut [u8]) -> std::io::Result<usize> {
    buf.fill(0);
    Ok(buf.len())
  }
}

fn main() {
  let mut reader = EndlessZeros;
  // First 4 bytes: 0xFF 0xFF 0xFF 0xFF -> len = u32::MAX
  // SchnorrAggregate::<Ristretto>::read loops ~4.29 billion times,
  // each iteration performing a full point decode + push.
  // Thread hangs regardless of actual "message" size.
  let _ = SchnorrAggregate::<Ristretto>::read(&mut reader);
}
```

*Caveat*: I verified the read loop is unbounded at `crypto/schnorr/src/aggregate.rs:83-85` and confirmed no size cap exists in that file; I was unable to fully trace every in-scope call site that pipes untrusted streams into `SchnorrAggregate::read`, so the concrete remote trigger point is the public API itself rather than a named coordinator handler (which is outside the permitted scope).
