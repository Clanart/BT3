I found a strong analog. Let me verify the scan code's behavior regarding spent outputs.### Title
Scanner reports outputs spent within the same block as received funds, crediting deposits for non-existent UTXOs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates over every transaction in a block and reports any output whose `script_pubkey` matches a registered P2TR script as a `ReceivedOutput`, but it never inspects `tx.input`. An output created by transaction A and spent by transaction B within the same block is reported as spendable funds even though its outpoint never exists in the UTXO set. Any unprivileged party can produce this pattern — funds are reported received that are not spendable, and downstream the deposit is credited while the underlying Bitcoin can never be recovered, matching the "assets permanently locked / irrecoverable" bug class.

### Finding Description
`Scanner` matches outputs purely by `script_pubkey` (`self.scripts.get(&output.script_pubkey)`, `networks/bitcoin/src/wallet/mod.rs:205`) and constructs a `ReceivedOutput` keyed by `OutPoint::new(tx.compute_txid(), vout)` (`:209`). `scan_block` simply concatenates `scan_transaction` results across `block.txdata` (`:221-227`). Neither function checks whether a later transaction in the same block consumes that outpoint via its `tx.input[].previous_output`. 

Because `scan_transaction` only looks at `tx.output`, a same-block spend is indistinguishable from a live UTXO. The emitted `ReceivedOutput` is then treated as real funds by the multisig pipeline (`processor/src/multisigs/scanner.rs:562-567` pushes every `network.get_outputs` result into `outputs`, which become `ScannerEvent::Block` instructions / `PlanFromScanning` entries in `processor/src/multisigs/mod.rs`), causing the associated `InInstruction` (deposit credit) to be batched. When Serai later attempts to spend the outpoint, `SignableTransaction::multisig` verification of `p2tr_script_buf(offset.group_key()) == prevout.script_pubkey` (`networks/bitcoin/src/wallet/send.rs:277`) passes — the offset is correct — yet the signed transaction is invalid because the prevout was already spent. There is no path that detects or discards the phantom output.

### Impact Explanation
A `ReceivedOutput` for a non-existent UTXO causes Serai to credit a deposit (emit an `InInstruction` minting sriBTC) against Bitcoin it can never spend — an unbacked mint. The phantom output is also permanently stuck in the wallet view: it will be selected as an input for future `SignableTransaction`s, and every attempt to spend it produces a transaction Bitcoin consensus rejects (bad-txns-inputs-missingorspent). The "deposit" is effectively locked forever — unrecoverable by any unwind or refund path — exactly the class of the referenced finding (bonded assets rendered permanently inaccessible). Repeated in-block spends to a registered Serai script let an attacker inflate credited deposits arbitrarily, limited only by the fees of the same-block spend transaction.

### Likelihood Explanation
Fully reachable by any unprivileged Bitcoin user: they learn Serai's P2TR script_pubkey from any prior deposit transaction on-chain, craft tx A paying to it, and tx B spending A's output to an address they control — both mined in the same block (trivially arranged via any miner, accelerator, or self-mining; even ordinary CPFP/RBF chains can produce it opportunistically). No collusion, validator compromise, or leaked key is required. `scan_block`'s own documentation acknowledges it performs no maturity/spend filtering (the coinbase caveat at `:218-220` shows inputs are never examined — the recommended `txdata[1..]` filter only removes the coinbase transaction itself, not same-block spends).

### Recommendation
Track spent outpoints while scanning a block: collect every `tx.input[].previous_output` in `block.txdata`, then drop any `ReceivedOutput` whose `outpoint` appears in that set (or whose `txid` doesn't reference a UTXO confirmed unspent). Coinbase outputs should additionally be excluded until maturity. Ideally, verify each candidate outpoint against a UTXO view of the chain rather than relying solely on script_pubkey matching.

### Proof of Concept
1. Observe Serai's registered P2TR `script_pubkey` S on-chain (from any prior deposit).
2. Build tx A: output[0] = `{ value: >= DUST, script_pubkey: S }`.
3. Build tx B: `input[0].previous_output = OutPoint(txid(A), 0)`, spending to an attacker address.
4. Submit A and B so both confirm in block `blk` (A before B).
5. `Scanner::scan_block(blk)` calls `scan_transaction` on each tx (`mod.rs:223`). A's output matches `self.scripts` (`:205`), so a `ReceivedOutput` is pushed with `outpoint = (txid(A), 0)` (`:206-210`). B's input is never inspected.
6. Result: `Vec<ReceivedOutput>` contains a deposit credited by the processor (`scanner.rs:562-567` → `ScannerEvent::Block`), yet `OutPoint(txid(A), 0)` is not in the UTXO set — the credited funds are permanently unspendable and any `SignableTransaction` including it fails on broadcast.
