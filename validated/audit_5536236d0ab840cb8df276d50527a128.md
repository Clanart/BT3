### Title
Unbounded recursive layer matching in wallet offer/puzzle-driver parsing enables attacker-triggered stack overflow (transaction-processing halt) - ([File: chia/wallet/outer_puzzles.py])

### Summary
The QEMU `lsi53c895a` bug class is unbounded reentrant/recursive processing of attacker-influenced data leading to native stack exhaustion. Chia's wallet puzzle-driver registry has an analogous pattern: `match_puzzle()` in `chia/wallet/outer_puzzles.py` and every concrete outer-puzzle driver (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `MetadataOuterPuzzle`, `OwnershipOuterPuzzle`, `CROuterPuzzle`) recursively call back into `_match()`/`_get_inner_puzzle()`/`_get_inner_solution()`/`_construct()` once per curried puzzle layer, with no depth bound, driven entirely by the nesting depth of an attacker-supplied puzzle reveal. This is reachable by any wallet user who loads an offer file from an untrusted counterparty via `Offer.from_bytes()` → `Offer.from_spend_bundle()` / `Offer._get_offered_coins()`.

### Finding Description
`match_puzzle()` iterates the driver registry and calls `driver.match(puzzle)`: [1](#0-0) 

Each driver's `match()` recognizes one layer and, if a layer is present, recurses into the *same* dispatcher for the inner puzzle, e.g. `CATOuterPuzzle.match()`: [2](#0-1) 

and `CROuterPuzzle.match()` / `MetadataOuterPuzzle.match()` / `OwnershipOuterPuzzle.match()` / `SingletonOuterPuzzle.match()` follow the identical unbounded-recursion pattern: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

There is no maximum-layer-depth check anywhere in this call chain, unlike `sha256_treehash()` in `chia/types/blockchain_format/tree_hash.py`, which was deliberately made iterative specifically "so we don't have to worry about blowing out the python stack": [7](#0-6) 

An attacker (offer counterparty) can construct a `CoinSpend` whose `puzzle_reveal` is an arbitrarily deep, well-formed stack of recognized outer-puzzle layers (e.g., repeated CAT/metadata/ownership/CR wrapping around a trivial inner puzzle). Because `curry()` composition cost grows only linearly with layer count, thousands of layers can be encoded in a puzzle reveal of modest size, easily fitting within an offer file that a wallet client will parse.

This puzzle reveal reaches the vulnerable recursive matcher through the offer-parsing entry points:
- `Offer.from_spend_bundle()`, which calls `match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))` for every coin spend in an incoming offer bundle: [8](#0-7) 
- `Offer._get_offered_coins()`, which similarly calls `match_puzzle()`, then `get_inner_puzzle()`/`get_inner_solution()`/`construct_puzzle()` — all of which recurse through the same `also`-chained driver dispatch: [9](#0-8) 

Both are exercised whenever a wallet inspects or accepts an offer supplied by an untrusted counterparty (offer summary / take-offer flows go through `Offer.from_bytes()`/`from_bech32()` before any signature or full-node validation occurs), so the recursive matching happens purely on locally-parsed, attacker-controlled bytes before the spend is ever submitted to the mempool.

### Impact Explanation
Python's default recursion limit (~1000 frames) will be exceeded by a sufficiently deep layer stack, raising an uncaught `RecursionError` (or, in CPython, potentially a native stack overflow depending on frame size and platform stack limits) deep inside wallet offer-processing code. This can crash or hang the wallet RPC call handling the offer, denying legitimate wallet operations (offer summary, take-offer, trade processing) — a spend/data-triggered transaction-processing halt directly analogous to the QEMU DMA-MMIO reentrancy stack-overflow bug class. Because this is triggered purely by locally parsing an offer file (no signature or mempool validation gates it first), a malicious offer can be crafted and distributed to any wallet user without needing to be a valid, broadcastable spend bundle.

### Likelihood Explanation
Likelihood is moderate-to-high for wallet users who inspect offers from untrusted counterparties (a normal, expected P2P workflow for Chia offers/DeXie-style marketplaces). Constructing the malicious puzzle reveal requires only chaining `curry()` calls with existing, publicly known outer-puzzle mods (CAT, singleton, metadata, ownership, CR) — no cryptographic material or privileged access is needed, matching the "unprivileged... offer counterparty" reachability constraint.

### Recommendation
Add an explicit maximum recursion/layer-depth bound (e.g., a counter threaded through `match_puzzle`/`get_inner_puzzle`/`get_inner_solution`/`construct_puzzle` and each driver's recursive call, similar in spirit to `sha256_treehash`'s deliberate iterative design) and reject/raise a handled `ValueError` once the bound is exceeded, before Python's own recursion limit is hit. Apply the same bound uniformly across `CATOuterPuzzle`, `SingletonOuterPuzzle`, `MetadataOuterPuzzle`, `OwnershipOuterPuzzle`, and `CROuterPuzzle`, and ensure offer-parsing call sites (`Offer.from_spend_bundle`, `Offer._get_offered_coins`) catch/convert any residual `RecursionError` into a normal parsing failure rather than letting it propagate uncaught.

### Proof of Concept
Conceptually (not run, due to tool limitations):
1. Build an inner puzzle `P0 = 1` (accept-everything).
2. Repeatedly wrap it N times (N ~= 2000–5000) using one or more of `construct_cat_puzzle(CAT_MOD, tail, P_i)`, `NFT_STATE_LAYER_MOD.curry(...)`, `puzzle_for_ownership_layer(...)`, or `construct_cr_layer(...)` to produce `P_N`, mirroring the double-wrapping already exercised in existing tests: [10](#0-9) [11](#0-10) 
3. Place `P_N` as the `puzzle_reveal` of a `CoinSpend` inside an `Offer`/`WalletSpendBundle`, serialize it as a normal offer file.
4. Have a victim wallet call `Offer.from_bytes(offer_bytes)` (as in `Offer.from_spend_bundle`) or `offer.get_offered_coins()` (→ `_get_offered_coins`), which calls `match_puzzle()` recursively N times, exceeding Python's recursion limit and raising `RecursionError` inside wallet offer-handling code, halting that RPC call.
