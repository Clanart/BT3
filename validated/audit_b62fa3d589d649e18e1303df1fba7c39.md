### Title
Missing zero-address validation on `beneficiary` in intent escrow release/fill paths causes permanent, unrecoverable loss of funds - ([File: evm/src/apps/intentsv2/IntentsBase.sol], [File: evm/src/apps/intentsv2/IntrinsicIntents.sol], [File: evm/src/apps/intentsv2/ExtrinsicIntents.sol], [File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The external report's core invariant break is: a value-moving function accepts a zero-address recipient, moves value to it anyway (silently succeeding instead of reverting), and updates internal accounting as if the transfer succeeded, permanently destroying the funds. The same broken invariant exists in Hyperbridge's IntentGatewayV2 escrow logic: every path that pays out escrowed or solver-provided funds resolves `beneficiary` from user-supplied `bytes32` order fields (`order.output.beneficiary`, `order.user`, `body.beneficiary`) and sends native ETH via a raw `.call{value: amount}("")`, with no `beneficiary != address(0)` check anywhere in the payout code.

### Finding Description
`IntentsBase._withdraw` derives the payout address purely by truncation, with no zero check, then transfers native value with a low-level call that succeeds even to `address(0)`: [1](#0-0) 

The same pattern is duplicated in the Tron variant's `withdraw`: [2](#0-1) 

The fill paths derive `beneficiary` the same way and pay it directly from solver-supplied value/tokens, again with no zero-address guard, for both same-chain and cross-chain fills: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

Critically, unlike ERC20 `transfer()` (which OpenZeppelin implementations revert on a zero `to`), a raw `.call{value: amount}("")` to `address(0)` **succeeds** — the ETH is irrecoverably burned rather than the transaction reverting. This is functionally identical to the report's `LibERC20.mint` bug: the value-moving primitive is executed against a zero recipient, funds are lost, and the surrounding bookkeeping (`_orders[...] -= amount`, `_filled[commitment] = beneficiary`, `isFullyFilled`, event emission) proceeds exactly as if the transfer had reached a real beneficiary.

`order.output.beneficiary` and `order.user` are attacker/order-creator-controlled `bytes32` fields with no on-chain validation anywhere in order creation, fill, or cross-chain acceptance (`ExtrinsicIntents.onAccept` at lines 289-309 decodes `WithdrawalRequest.beneficiary` and calls `_withdraw`/`withdraw` unconditionally): [7](#0-6) 

An order creator can therefore craft an order with `output.beneficiary = bytes32(0)` for a native-ETH output. Any solver that fills it (same-chain via `IntrinsicIntents._fillSameChain` or cross-chain via `ExtrinsicIntents._fillCrossChain`) pays real ETH to the burn address, the transfer "succeeds" (no revert), and the protocol still marks the order filled and releases the creator's escrowed input tokens to that solver — i.e. the accounting treats the burned payment as delivered.

### Impact Explanation
This is a direct loss-of-funds bug reachable by any unprivileged party (order creator sets a malicious/careless `beneficiary`, or a user/relayer cancels/refunds an order where `order.user` was recorded as zero) with no need for a malicious relayer, prover, or admin — it only requires the ordinary public `fillOrder`/`cancelOrder`/`onAccept` entry points and a `bytes32` field that is never checked. Native-token payouts to the truncated zero address are permanently destroyed while the on-chain escrow/fill state is finalized as successful, exactly matching the "stealing or loss of funds" and "false state acceptance" categories in the bounty scope.

### Likelihood Explanation
The likelihood is moderate: it requires a beneficiary-controlling field (order creator's `output.beneficiary`, or `order.user`) to be `address(0)`, either through a malicious order construction, encoding mistake in an SDK/relayer, or default-zero-value bug. There is no on-chain guard preventing it in any of the four code paths reviewed (`IntentsBase._withdraw`, tron `withdraw`, `IntrinsicIntents._fillSameChain`, `ExtrinsicIntents._fillCrossChain`), so the class of bug is systemic across the intents module rather than a one-off.

### Recommendation
Add an explicit zero-address check on the resolved `beneficiary` at the earliest point it is derived in each of the four locations (`IntentsBase._withdraw`, `IntentGatewayV2.withdraw` (tron), `IntrinsicIntents._fillSameChain`, `ExtrinsicIntents._fillCrossChain`), e.g.:
```solidity
address beneficiary = address(uint160(uint256(body.beneficiary)));
require(beneficiary != address(0), "beneficiary is zero address");
```
Additionally, consider validating `order.output.beneficiary` and `order.user` at order-creation time so malformed orders cannot even be submitted.

### Proof of Concept
1. Order creator calls the order-creation entrypoint with `order.output.beneficiary = bytes32(0)` and a native-ETH output asset, escrowing input tokens for the solver.
2. A solver calls `fillOrder` → `_fillSameChain` (or cross-chain equivalent), sending the required ETH amount.
3. `beneficiary = address(uint160(uint256(order.output.beneficiary)))` resolves to `address(0)`.
4. `beneficiary.call{value: beneficiaryTotal}("")` at `evm/src/apps/intentsv2/IntrinsicIntents.sol:104` succeeds (raw calls to `address(0)` do not revert), burning the solver's ETH.
5. Execution continues normally: `isFullyFilled = true`, `_withdraw` releases the creator's escrowed input tokens to the solver, and `OrderFilled` is emitted — the protocol records a successful fill even though the intended payout was permanently destroyed. [8](#0-7)
