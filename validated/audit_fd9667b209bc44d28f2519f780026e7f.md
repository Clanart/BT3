### Title
Threshold secret share stored in plaintext in a DB the code explicitly distrusts as a secret store - (File: crypto/dkg/src/lib.rs, processor/src/key_gen.rs)

### Summary
The external bug class is CWE-201: secret-derived material embedded in a resource readable by parties who should not hold it (a hashed password embedded in public HTML). The Serai analog: `ThresholdKeys::write`/`serialize` embeds the raw `secret_share` scalar in the serialized key blob, and `GeneratedKeysDb::save_keys` persists that blob into the processor DB — a store the codebase itself declares "isn't a proper secret store and shouldn't be trusted as one." The same codebase encrypts the `CachedPreprocess` before writing it to this DB precisely because recovering it would compromise the private key, yet the actual long-lived secret share is written unencrypted.

### Finding Description
- `ThresholdCore` holds `secret_share: Zeroizing<C::F>`, and `ThresholdKeys::write` serializes it verbatim (`let mut share_bytes = self.core.secret_share.to_repr(); writer.write_all(...)`) with no encryption or access control. [1](#0-0) 
- The processor persists generated keys via `GeneratedKeysDb::save_keys::<N>(txn, &id, &substrate_keys, &network_keys)`, storing the serialized `ThresholdKeys` for both the substrate (Ristretto) and network curves. [2](#0-1) 
- By contrast, `SigningProtocol::preprocess_internal` XORs the `CachedPreprocess` with a key derived from `self.key` before writing to `CachedPreprocesses`, with the explicit comment that the DB "isn't a proper secret store and shouldn't be trusted as one." [3](#0-2) 
- This establishes the threat model internally: data in this DB is not treated as confidential, and exposure of key material from it is acknowledged to enable private-key recovery — yet the secret share itself is stored in plaintext while a less-sensitive ephemeral nonce seed is encrypted.

### Impact Explanation
Anyone who can read the processor DB (backups, misconfigured storage, an RPC/debug surface, or a lower-privileged process on the validator host — the same class of "unprivileged read" as an MITM reading HTML source) obtains the validator's complete `secret_share` for every generated key, for both substrate and network curves. Disclosure of a threshold share is direct key-share leakage: it reduces the threshold security by one and, combined with the publicly-known `verification_shares` and `interpolation` also serialized in the blob, hands an attacker everything except the other shares. This is strictly more sensitive than the `CachedPreprocess` the code bothers to encrypt — reuse/recovery of the preprocess only leaks the share under a second signature, while the stored share is the plaintext scalar itself. Severity: Medium (requires DB read access, which the code explicitly models as plausible but not guaranteed).

### Likelihood Explanation
The DB is documented in-code as not a proper secret store, i.e., the developers already assume it may be read by parties who should not see secrets. Any exposure of that storage layer — the exact assumption motivating the cached-preprocess encryption — trivially exposes the secret share, with no cryptographic work required.

### Recommendation
Encrypt the serialized `ThresholdKeys` (or at minimum the `secret_share` field) at rest using a key derived from validator-held material, applying the same pattern already used for `CachedPreprocesses` in `preprocess_internal`. Alternatively, store shares only in a dedicated secret store and keep the DB limited to public artifacts (`group_key`, `verification_shares`, `interpolation`).

### Proof of Concept
1. A validator completes key generation; `GeneratedKeysDb::save_keys` writes `substrate_keys.serialize()` and `network_keys.serialize()` into the DB.
2. `ThresholdKeys::write` emits `params || interpolation || secret_share.to_repr() || verification_shares` with `secret_share` in cleartext at a fixed offset.
3. An unprivileged reader of the DB reads the blob, calls `ThresholdKeys::read`, and obtains `core.secret_share` — the live threshold share — plus all verification shares needed to confirm validity (`C::generator() * secret_share == verification_shares[i]`).
4. The leaked share is usable directly in `view()`/signing by anyone able to combine it with threshold-many other compromised shares, and its exposure is a permanent compromise of that validator's key material, unlike a nonce whose misuse is bound to a single session.

Note: this assessment could not fully verify `GeneratedKeysDb::save_keys`'s internals (its definition wasn't returned in search results); the finding rests on the shown call site persisting `ThresholdKeys` and on `ThresholdKeys::serialize` unconditionally including `secret_share`, plus the codebase's own stated distrust of the DB.
