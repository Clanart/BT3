### Title
Underestimated fee/vbytes when an OP_RETURN data output is present causes transactions paying less than the requested fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the GMXReader `_maxTokenBLending` formula that omits a term from the denominator, `SignableTransaction::new` computes the transaction weight/vbytes — and hence `needed_fee` — from a transaction that omits the OP_RETURN data output it actually creates. The result is a systematically understated fee whenever `data` is specified, an incorrect bound reachable purely through caller-supplied bytes.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` when `data` is `Some`, before the fee is computed:

```rust
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}
```

However, the vbytes used for `needed_fee` come from:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
``` [1](#0-0) 

`calculate_weight_vbytes` builds its template transaction solely from `payments` and an optional `change` output — the OP_RETURN output (up to ~91 bytes: 8-byte amount + length + OP_RETURN + push of up to 80 bytes) is never included. The same omission occurs in the `fee_with_change` recomputation at lines 224–234, which again passes only `payments` and `change`.

The user-specified `data` (attacker/caller-controlled bytes to `SignableTransaction::new` / `make_signable_transaction`, which forwards `None` today but the API accepts arbitrary `Option<Vec<u8>>`) directly inflates the real transaction size while the fee is priced on the smaller template. The actual paid fee `sum(inputs) - sum(outputs)` equals `needed_fee`, so the *effective* feerate is strictly below `fee_per_vbyte`.

Additionally, the minimum-fee check `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` is evaluated against the understated `vbytes`, so a transaction can pass `TooLowFee` validation while actually being below the mempool's minimum relay feerate — producing a signed transaction that relays fail to propagate. This mirrors the reported bug's impact: an incorrectly computed bound ("depositable amount" there, "necessary fee" here) computed with a missing term, producing a TX that deviates from what the caller specified.

### Impact Explanation
- Transactions with `data` pay a lower effective sat/vbyte than requested, with the shortfall proportional to the data length (~80–90 vbytes uncharged).
- At low `fee_per_vbyte`, the constructed transaction can fall under the default minimum relay fee and be unbroadcastable/never confirming, despite passing `TooLowFee` — funds are locked in an unconfirmed state and must be re-planned, analogous to "deposits revert despite sufficient liquidity."
- `needed_fee()`/`fee()` report a fee inconsistent with the requested rate, corrupting the processor's operating-cost accounting in `prepare_send`/`amortize_fee` (processor/src/networks/mod.rs, processor/src/networks/bitcoin.rs) whenever a data-bearing path is used.

### Likelihood Explanation
Reachable by any unprivileged caller providing `data` bytes and a fee rate to `SignableTransaction::new`; no secret material or privileged position is required. The error magnitude scales with data size and is deterministic — it is not probabilistic. Exploitation requires no race or collusion; every data-bearing transaction is mispriced.

### Recommendation
Include the OP_RETURN output in the weight calculation. Either pass the already-built `tx_outs`/`payments`-plus-data into `calculate_weight_vbytes`, or extend its signature to accept `data` and append the OP_RETURN `TxOut` to the template transaction before calling `tx.weight()`. Apply the same fix to the `fee_with_change` computation so the change/dust decision and the `weight` used in the `TooLargeTransaction` check reflect the true transaction.

```diff
- let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
+ // incorporate the data output into the template tx (e.g., via a `data: Option<&Vec<u8>>` arg)
+ let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None, data.as_ref());
...
- Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
+ Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change), data.as_ref());
```

### Proof of Concept
```rust
// networks/bitcoin/tests/wallet.rs style
let data = vec![0xaa; 80];
let tx = SignableTransaction::new(
  vec![output], &[], Some(change_addr), Some(data), FEE /* sat/vbyte */
).unwrap();
// needed_fee was priced without the ~91-byte OP_RETURN output:
assert!(tx.needed_fee() < FEE * real_vsize_including_op_return);
// fee() == needed_fee, yet tx.vsize() exceeds the estimated vbytes,
// so effective feerate = needed_fee / tx.vsize() < FEE
// With FEE == DEFAULT_MIN_RELAY_TX_FEE/1000 the tx passes TooLowFee
// yet is below the relay minimum once the OP_RETURN is serialized.
```

Concretely: build `SignableTransaction::new(inputs, &[], Some(change), Some([0u8;80]), fee)`; compare `tx.vsize()` after signing against the internal `vbytes` estimate — the former exceeds the latter by the OP_RETURN output's size, and `tx.fee()/tx.vsize() < fee_per_vbyte`.
