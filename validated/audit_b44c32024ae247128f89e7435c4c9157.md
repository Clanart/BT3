### Title
`_fetchRefspec` deliberately bypasses the push/pull/fetch concurrency guard, allowing an attacker-controlled fork PR fetch to race with (and corrupt) an in-flight push/pull/checkout - (File: `app/src/lib/stores/app-store.ts`)

### Summary
GitHub Desktop centralizes all network git operations (`_pull`, `_fetch`, `_fetchRemote`) behind a single mutual-exclusion helper, `withPushPullFetch`, which checks/sets `state.isPushPullFetchInProgress` to guarantee only one push/pull/fetch runs against a repository's working tree at a time. [1](#0-0) 
`_fetchRefspec`, however, is explicitly documented and implemented to **not** use this guard: [2](#0-1) 

The comment states this is intentional because the action "is required to complete when viewing a Pull Request from a fork," i.e., it can be triggered by remote/PR data that is not fully under the local user's control (a PR opened by any GitHub user against/using a fork whose author controls ref names/content).

### Finding Description
Every other network mutation of the repository (fetch, pull, push, remote fetch) is serialized via `withPushPullFetch`, which sets/reads `isPushPullFetchInProgress` in `repositoryStateCache` before running `git fetch`/`git pull` and before the subsequent `fastForwardBranches` + `_refreshRepository` sequence: [3](#0-2) [4](#0-3) 

`_fetchRefspec` runs `git fetch <remote> <refspec>` directly against the same on-disk repository (same `.git` directory, same worktree) without checking or setting that flag, and then calls `_refreshRepository`, which re-reads branches/tip/status and updates in-memory state that other in-flight operations rely on: [5](#0-4) [6](#0-5) 

Because `git fetch` mutates shared repository state (`FETCH_HEAD`, remote-tracking refs, and potentially packed-refs/loose ref files) with no OS-level or app-level lock coordinating it against a concurrently-running `performPull`/`performFetch`/`_push` (which also run `git fetch`, `fastForwardBranches`, and `_refreshRepository`), the two operations can interleave: two `git` processes writing refs in the same repository simultaneously, followed by two independent `_refreshRepository` calls racing to update the shared `repositoryStateCache` (`tip`, `branchesState`, `remote`, `lastFetched`, etc.). The result is a state that doesn't correspond to what's actually on disk, or a corrupted intermediate `.git` ref file, since Desktop's own guard (`isPushPullFetchInProgress`) was specifically built to prevent exactly this concurrent-`git`-process scenario and `_fetchRefspec` was carved out as an exception.

This is conceptually the same broken invariant as the reentrancy bug in the report: a single mutual-exclusion mechanism (`ReentrancyGuardTransient` in the contract vs. `isPushPullFetchInProgress` in Desktop) is supposed to serialize a state-mutating operation, but one code path is allowed to re-enter/execute concurrently, corrupting shared state that other guarded callers assume is exclusively theirs.

### Impact Explanation
An attacker who controls a pull request (opening any PR, from any fork, against any public repository the victim has open in Desktop, or via the `x-github-client://openPR` deep link the victim clicks) can cause Desktop to invoke `_fetchRefspec` against the victim's local clone at an attacker-influenced time (e.g., when the victim happens to be pushing or pulling). Because `_fetchRefspec` is not gated by `isPushPullFetchInProgress`, this creates a window where two `git` processes concurrently write refs/`FETCH_HEAD` in the same repository, and two racing `_refreshRepository` calls overwrite each other's `repositoryStateCache` updates (tip/branch/remote state). This can lead to:
- The UI/tip state pointing at the wrong branch/commit relative to what's on disk after a push/pull finishes, silently corrupting what the user believes they are about to commit/push next.
- Ref corruption from concurrent `git fetch` writers in the same `.git` directory (loose ref races), a known git hazard the app's own `withPushPullFetch` design was meant to avoid.

This does not require local/physical access, malware, or leaked credentials — only that the victim has the target repository open in Desktop while an attacker-controlled PR/fetch is being resolved (satisfying the "attacker controls ... a git remote/proxy response" and "a link or deep link the user clicks" criteria).

### Likelihood Explanation
Moderate-to-low but plausible: it requires the victim's Desktop client to have a `_fetchRefspec` call in flight (e.g., viewing an attacker's PR from a fork) at the same time the victim (or a background task) initiates a push/pull/fetch. Desktop does run background fetches periodically, increasing the probability that the two paths overlap without any special timing effort from the attacker; the attacker doesn't need precise timing, just to keep the PR-view or diff-view open, which repeatedly triggers `_fetchRefspec`-style fetches, widening the race window. The code comment itself acknowledges the safety gap ("This might require some rework in the future to chain these actions"), confirming this is a known, unmitigated concurrency hole rather than a stretch inference.

### Recommendation
Route `_fetchRefspec` through the same `withPushPullFetch` mutual-exclusion wrapper (or a queue that defers it until any in-flight push/pull/fetch completes) instead of special-casing it as exempt from concurrency control. If immediate execution is required for the fork-PR-preview UX, at minimum serialize the underlying `git fetch` and the subsequent `_refreshRepository`/state-merge step per-repository (e.g., via a repository-scoped async mutex) so that no two `git` fetch/pull/push processes ever run concurrently against the same working directory, and so that `repositoryStateCache` updates from concurrent refreshes cannot race and silently overwrite each other.

### Proof of Concept
1. Open a repository in GitHub Desktop that has a public fork with open pull requests.
2. Trigger `_fetchRefspec` repeatedly/continuously — e.g., by opening a PR-from-fork view or by clicking an `x-github-client://openPR?...` deep link crafted by an attacker pointing at a PR whose branch changes frequently, causing Desktop to call `dispatcher.fetchRefspec` → `appStore._fetchRefspec` (`app/src/lib/stores/app-store.ts:5875-5885`), which does not set `isPushPullFetchInProgress`.
3. While step 2's fetch is in flight, have the victim (or a scheduled background fetch, see `performFetch`/`withPushPullFetch` at `app/src/lib/stores/app-store.ts:5924-5987`) perform a normal `Fetch`/`Pull`/`Push` on the same repository.
4. Observe that both `git` invocations execute concurrently against the same `.git` directory (no lock/flag prevents it, unlike `performFetch`/`performPull`, which check `state.isPushPullFetchInProgress` first), and that the two resulting `_refreshRepository` calls race to update `repositoryStateCache`, potentially leaving the app's `tip`/branch state inconsistent with the on-disk repository state.

  private async withPushPullFetch(
    repository: Repository,
    fn: () => Promise<void>
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    // Don't allow concurrent network operations.
    if (state.isPushPullFetchInProgress) {
      return
    }

    this.repositoryStateCache.update(repository, () => ({
      isPushPullFetchInProgress: true,
    }))
    this.emitUpdate()

    try {
      await fn()
    } finally {
      this.repositoryStateCache.update(repository, () => ({
        isPushPullFetchInProgress: false,
      }))
      this.emitUpdate()
    }
  }

  private async performFetch(
    repository: Repository,
    fetchType: FetchType,
    remotes?: IRemote[]
  ): Promise<void> {
    await this.withPushPullFetch(repository, async () => {
      const gitStore = this.gitStoreCache.get(repository)

      try {
        const fetchWeight = 0.9
        const refreshWeight = 0.1
        const isBackgroundTask = fetchType === FetchType.BackgroundTask

        const progressCallback = (progress: IFetchProgress) => {
          this.updatePushPullFetchProgress(repository, {
            ...progress,
            value: progress.value * fetchWeight,
          })
        }

        if (remotes === undefined) {
          await gitStore.fetch(isBackgroundTask, progressCallback)
        } else {
          await gitStore.fetchRemotes(
            remotes,
            isBackgroundTask,
            progressCallback
          )
        }

        const refreshTitle = __DARWIN__
          ? 'Refreshing Repository'
          : 'Refreshing repository'

        this.updatePushPullFetchProgress(repository, {
          kind: 'generic',
          title: refreshTitle,
          description: 'Fast-forwarding branches',
          value: fetchWeight,
        })

        await this.fastForwardBranches(repository)

        this.updatePushPullFetchProgress(repository, {
          kind: 'generic',
          title: refreshTitle,
          value: fetchWeight + refreshWeight * 0.5,
        })

        // manually refresh branch protections after the push, to ensure
        // any new branch will immediately report as protected
        await this.refreshBranchProtectionState(repository)

        await this._refreshRepository(repository)
      } finally {
        this.updatePushPullFetchProgress(repository, null)

        if (fetchType === FetchType.UserInitiatedTask) {
          if (repository.gitHubRepository != null) {
            this._refreshIssues(repository.gitHubRepository)
          }
        }
      }
    })

export async function fetchRefspec(
  repository: Repository,

  refspec: string
