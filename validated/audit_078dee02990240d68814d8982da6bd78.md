### Title
Quadratic CPU denial of service via attacker-sized participant list in MuSig key aggregation - (File: crypto/dkg/musig/src/lib.rs)

### Summary
The external report describes a DoS class where a fixed bound (`MAX_DELEGATES = 1024`) permits an attacker to force a victim to perform work proportional to an attacker-influenced count, exhausting a scarce resource (block gas). The direct analog in Serai lives in `crypto/dkg/musig`: the binding-factor transcript is built once as a `Vec<u8>` containing every participant's encoded key, and is then **cloned inside a loop over all participants**. With the maximum permitted key count (`u16::MAX = 65535`, enforced by `check_keys`), each clone copies ~2 MB, so aggregating the key set costs O(n²) memory traffic — roughly 137 GB of `memcpy` for a single `musig_key`/`musig` call — before any scalar multiplication even runs.

### Finding Description
`check_keys` bounds the participant list only at `u16::MAX`: [1](#0-0) 

`binding_factor_transcript` serializes `context || keys_len || keys[0] || ... || keys[n-1]` into a `Vec<u8>` of size ~`34 + 32n` bytes: [2](#0-1) 

Both `musig_key_multiexp` and `musig` then call `transcript.clone()` once per participant: [3](#0-2) [4](#0-3) 

So the work is `sum_{i=1..n} (34 + 32n)` bytes copied = O(n²). At `n = 65535` that is ~`2 × 10^5 × 2 × 10^6 ≈ 137 GB` of copying plus 65535 heap allocations of ~2 MB each, on top of a 65535-term `multiexp`. `musig_key`, `musig_key_vartime`, and `musig` all reach this path with fully attacker-influenced `keys`.

### Impact Explanation
A node or processor that runs `musig()`/`musig_key_vartime()` over a participant list influenced by an unprivileged party can be stalled for a very long time on a single call — functionally identical to the VotingEscrow issue, where the largest allowed delegation set exceeds what the environment can process. A ~2 MB transcript cloned 65535 times is also a large transient allocation series; on memory-constrained validators it can trigger OOM rather than just slowness. Since the clone is pure overhead (the transcript could be passed by reference and only the index appended), the amplification factor over honest work is ~n.

### Likelihood Explanation
Any code path that aggregates keys from a set an attacker can grow — e.g., a validator/joining set or a list deserialized from untrusted input — reaches this with no cryptographic assumptions to defeat. The cost requires no invalid data: `check_keys` accepts any distinct keys up to 65535, so an attacker only needs to supply many keys. Feasibility depends on the integrator allowing large key lists, but nothing in the crate prevents or warns about it.

### Recommendation
Avoid the O(n²) copy: pass the transcript by reference and append only the participant index inside `binding_factor`, e.g., have `binding_factor` take `&[u8]` plus `i` and hash `transcript || i.to_le_bytes()` without cloning:

```rust
fn binding_factor<C: Ciphersuite>(transcript: &[u8], i: u16) -> C::F {
  let mut t = Vec::with_capacity(transcript.len() + 2);
  t.extend_from_slice(transcript);
  t.extend(i.to_le_bytes());
  C::hash_to_F(b"dkg-musig", &t)
}
```

Additionally, enforce a sane `MAX_KEYS` (e.g., matching the protocol's real maximum validator count, analogous to reducing `MAX_DELEGATES` 1024 → 128) inside `check_keys` rather than permitting `u16::MAX`.

### Proof of Concept

let _ = musig_key_vartime::<C>([0u8; 32], &keys);

Each iteration of the `1 ..= keys_len` loop in `musig_key_multiexp` clones a `Vec` of ~2 MB; with `n = 65535` the loop performs ~65535 × 2 MB ≈ 137 GB of copying before the multiexp begins. Instrumenting `binding_factor_transcript`/`binding_factor` allocations or running with `n` in the low thousands already shows the quadratic scaling.

fn check_keys<C: Ciphersuite>(keys: &[C::G]) -> Result<u16, MusigError<C>> {
  if keys.is_empty() {
    Err(MusigError::NoKeysProvided)?;
  }

  let keys_len = u16::try_from(keys.len())
    .map_err(|_| MusigError::TooManyKeysProvided { max: u16::MAX, provided: keys.len() })?;

  let mut set = HashSet::with_capacity(keys.len());
  for key in keys {
    let bytes = key.to_bytes().as_ref().to_vec();
    if !set.insert(bytes) {
      Err(MusigError::DuplicatedParticipant(*key))?;
    }
  }

  Ok(keys_len)
}

fn binding_factor_transcript<C: Ciphersuite>(
  context: [u8; 32],
  keys_len: u16,
  keys: &[C::G],
) -> Vec<u8> {
  debug_assert_eq!(usize::from(keys_len), keys.len());

  let mut transcript = vec![];
  transcript.extend(&context);
  transcript.extend(keys_len.to_le_bytes());
  for key in keys {
    transcript.extend(key.to_bytes().as_ref());
  }
  transcript
}
