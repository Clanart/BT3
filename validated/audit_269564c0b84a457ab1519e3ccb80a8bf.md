### Title
Malformed CREATE_COIN condition from an offer counterparty crashes offer-processing (unvalidated CLVM structure) - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer._get_offered_coins()` in [1](#0-0)  parses CLVM conditions produced by running an *untrusted* offer counterparty's inner puzzle/solution without validating the shape of the resulting `CREATE_COIN` condition before indexing into it.

### Finding Description
When a wallet receives an offer file (`Offer.from_bech32`/`from_bytes`, reachable from an arbitrary offer counterparty via `respond_to_offer` / `TradeManager.respond_to_offer` [2](#0-1) ), `arbitrage()` → `get_offered_amounts()` → `get_offered_coins()` → `_get_offered_coins()` is executed automatically as part of taking or displaying the offer.

Inside `_get_offered_coins()`, for every coin spend whose puzzle matches a known asset driver, the inner puzzle is *run* with the attacker-supplied inner solution, and the resulting condition list is scanned:
```
for condition in conditions.as_iter():
    if condition.first() == 51 and condition.rest().first() == OFFER_MOD_HASH:
        expected_num_matches += 1
        offered_amounts.append(condition.rest().rest().first().as_int())
``` [3](#0-2) 

The code assumes any condition beginning with opcode `51` (`CREATE_COIN`) and a puzzle-hash argument equal to `OFFER_MOD_HASH` always has a third argument (the amount). Because the inner puzzle is entirely attacker-controlled CLVM (any puzzle that matches a recognized outer driver, e.g. CAT/NFT/DID puzzles, can still emit arbitrary conditions from its inner layer), it can output a truncated condition such as `(51 OFFER_MOD_HASH)` with no amount atom. `condition.rest().rest()` then evaluates to the CLVM nil atom, and calling `.first()` on nil is an invalid CLVM pair operation that raises an unhandled exception (an `EvalError`/atom-vs-pair error), analogous to the Wireshark MRDISC dissector dereferencing a pointer without first validating the presence of the expected field.

This mirrors the CVE's bug class: a parser assumes a fixed-size/fixed-shape field from untrusted input and dereferences/accesses it without a presence check first, causing a crash in the code path that processes attacker-supplied data.

### Impact Explanation
Because `_get_offered_coins()` is invoked with no surrounding `try/except` anywhere in `arbitrage()`, `respond_to_offer()`, `save_trade()`, or the RPC/CLI entry points that display or take offers, a malicious offer counterparty can craft an offer file that any recipient wallet will fail to process — the exception propagates out of the wallet RPC call (`take_offer`, `get_offer_summary`, etc.), halting that transaction-processing request. This is a spend-triggered (offer-triggered) processing halt reachable by any wallet user who is handed a malicious offer, satisfying the "offers and trades" and "spend-triggered transaction-processing halt" impact categories in scope.

### Likelihood Explanation
Likelihood is high for any wallet operator who opens/evaluates offer files from untrusted counterparties (a normal, expected workflow in Chia's offer protocol). Constructing a puzzle whose inner solution yields a truncated `CREATE_COIN` condition requires only writing arbitrary CLVM for the offered asset's inner puzzle — no signature or on-chain state is required to trigger the crash, since this code runs purely on the offer bundle before any broadcast or validation against the real coin set.

### Recommendation
Before indexing into the `CREATE_COIN` condition's rest/rest, validate that the condition has at least 3 atoms (opcode, puzzle-hash, amount) — e.g., check `condition.rest().rest().pair is not None` (or ensure the program is not nil) before calling `.first().as_int()`, and wrap the whole condition-scanning loop in a `try/except` that treats a malformed condition as "no match" rather than propagating an unhandled exception, consistent with how `conditions()` already guards similar CLVM execution with `except Exception: continue` at [4](#0-3) .

### Proof of Concept
1. Build an `Offer` whose `driver_dict` contains an asset (e.g., a CAT) with a `puzzle_driver` recognized by `match_puzzle`.
2. Craft the corresponding `CoinSpend`'s inner puzzle/solution so that running it yields a condition list containing `(51 OFFER_MOD_HASH)` — a `CREATE_COIN` with the offer settlement puzzle hash but missing the amount argument (valid CLVM, since conditions are not required to have exactly 3 args at the puzzle level).
3. Send this offer file to a victim wallet and have it call `respond_to_offer`, `get_offer_summary`, or any path that calls `offer.arbitrage()` / `offer.get_offered_coins()`.
4. Observe that `_get_offered_coins()` raises an unhandled exception when evaluating `condition.rest().rest().first()` on the nil tail, aborting offer processing.

Note: I was not able to execute this PoC or inspect the exact `chia_rs`-backed `Program.first()`/`.rest()` semantics on `nil` in this environment (the Rust-backed `Program` implementation is not indexed in this codebase snapshot), so the precise exception type raised on nil access is inferred from CLVM semantics rather than confirmed by direct execution — this should be verified with a live `SpendSim`/`Program` test before treating the severity as fully confirmed.

    def _get_offered_coins(self) -> dict[bytes32 | None, list[Coin]]:
        offered_coins: dict[bytes32 | None, list[Coin]] = {}

        cost_left = INFINITE_COST
        for parent_spend in self._bundle.coin_spends:
            coins_for_this_spend: list[Coin] = []

            parent_puzzle: UnknownPuzzle = UnknownPuzzle(known_program=parent_spend.puzzle_reveal)
            parent_solution = Program.from_serialized(parent_spend.solution)
            additions: list[Coin] = self._additions[parent_spend.coin]

            puzzle_driver = match_puzzle(parent_puzzle)
            if puzzle_driver is not None:
                asset_id = create_asset_id(puzzle_driver)
                inner_puzzle: Program | None = get_inner_puzzle(puzzle_driver, parent_puzzle, parent_solution)
                inner_solution: Program | None = get_inner_solution(puzzle_driver, parent_solution)
                assert inner_puzzle is not None and inner_solution is not None

                # We're going to look at the conditions created by the inner puzzle
                puzzle_cost, conditions = inner_puzzle.run_with_cost(cost_left, inner_solution)
                assert cost_left >= puzzle_cost
                cost_left -= puzzle_cost
                expected_num_matches: int = 0
                offered_amounts: list[int] = []
                for condition in conditions.as_iter():
                    if condition.first() == 51 and condition.rest().first() == OFFER_MOD_HASH:
                        expected_num_matches += 1
                        offered_amounts.append(condition.rest().rest().first().as_int())

                # Start by filtering additions that match the amount
                matching_spend_additions = [a for a in additions if a.amount in offered_amounts]

                if len(matching_spend_additions) == expected_num_matches:
                    coins_for_this_spend.extend(matching_spend_additions)
                # We didn't quite get there so now lets narrow it down by puzzle hash
                else:
                    # If we narrowed down too much, we can't trust the amounts so start over with all additions
                    if len(matching_spend_additions) < expected_num_matches:
                        matching_spend_additions = additions
                    matching_spend_additions = [
                        a
                        for a in matching_spend_additions
                        if a.puzzle_hash == construct_puzzle(puzzle_driver, OFFER_MOD).get_tree_hash()
                    ]
                    if len(matching_spend_additions) == expected_num_matches:
                        coins_for_this_spend.extend(matching_spend_additions)
                    else:
                        raise ValueError("Could not properly guess offered coins from parent spend")
            else:
                # It's much easier if the asset is bare XCH
                asset_id = None
                coins_for_this_spend.extend([a for a in additions if a.puzzle_hash == OFFER_MOD_HASH])

            # We only care about unspent coins
            coins_for_this_spend = [c for c in coins_for_this_spend if c not in self._bundle.removals()]

            if coins_for_this_spend != []:
                offered_coins.setdefault(asset_id, [])
                offered_coins[asset_id].extend(coins_for_this_spend)
        return offered_coins
