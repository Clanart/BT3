### Title
Payer attribution for operator reimbursement is derived from an unauthenticated OP_RETURN in the payout transaction, letting an unprivileged party misattribute (or hijack) which operator gets credited for a fronted withdrawal - (File: `core/src/verifier.rs`)

### Summary
The Splitter bug allowed anyone to fake being the trusted `RoyaltyVault` and call a state-mutating function that inflated a balance the contract believed it owed, later paid out via `claim`. The structural analog in Clementine is that **who gets credited as the "payer" (fronting operator) for a withdrawal is derived from data that is not bound to the actual funding input** by the user's signature, and this attribution directly drives automated reimbursement.

### Finding Description
`update_finalized_payouts` determines which operator is credited for fronting a given withdrawal purely by scanning the confirmed payout transaction's first OP_RETURN output and parsing an x-only pubkey out of it: [1](#0-0) 

This `operator_xonly_pk` is persisted as `payout_payer_operator_xonly_pk` and later used, with no further authentication, to decide which operator's automation treats the withdrawal as "its" unhandled payout to reimburse: [2](#0-1) 

and to gate the reimbursement path, where the only check performed is that the DB-recorded `payer_xonly_pk` equals the local operator's own key: [3](#0-2) 

The background `PayoutCheckerTask` automatically drives this: once a withdrawal is recorded with a `payout_payer_operator_xonly_pk`, the matching operator's node automatically calls `handle_finalized_payout` and proceeds to kickoff/reimburse, with no manual confirmation that this operator actually funded the payment: [4](#0-3) 

The root cause is that the withdrawal input is signed by the user with a `SinglePlusAnyoneCanPay` sighash, as documented on the wire type itself: [5](#0-4) 

`SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` only commits the user's signature to *their own* input/output pair (the withdrawal UTXO and the user payout output). It places no constraint on any other input or output of the transaction — including the OP_RETURN output that the protocol later trusts to identify "who paid." Consequently, whoever actually supplies the fee-paying input and constructs the final transaction is free to write an arbitrary x-only public key into the OP_RETURN, and the on-chain attribution logic in `update_finalized_payouts` will credit whichever operator's key appears there, whether or not that operator supplied any funds. Because the transaction is a normal Bitcoin transaction (not gated by any Clementine mTLS/gRPC authentication — that authentication only protects the gRPC control plane, not what gets written into a broadcast Bitcoin transaction), this is reachable by any party able to observe/replace the payout transaction before confirmation (the `ANYONECANPAY` input can be freely combined with different fee inputs and outputs by a third party), i.e., an unprivileged attacker with no protocol role.

This is the structural equivalent of the Splitter bug: a value that should only be set by the party who actually performed the underlying action (there, incrementing balance owed by the real vault; here, crediting a specific operator as payer) is instead attacker-controllable data that the contract/protocol trusts unconditionally.

### Impact Explanation
This breaks the binding "the operator credited" == "the party that paid": an operator can be credited (and their automation will proceed) for a withdrawal it never funded, matching the explicit Critical bullet "an operator reimbursed for a payout it never funded." Symmetrically, the operator that actually fronted the payment can be excluded from ever being recognized as payer (since the withdrawal UTXO can only be spent once and the DB records only the attacker-chosen key), matching "an honest operator permanently unable to be reimbursed" — because `validate_payer_is_operator` will reject that operator's own `get_reimbursement_txs`/`handle_finalized_payout` calls forever once a different key is recorded as payer for that withdrawal index.

### Likelihood Explanation
No verifier, operator, watchtower, aggregator, security-council, or sequencer credential is required to exploit this — it only requires the ability to observe a pending payout transaction (which uses `ANYONECANPAY`, explicitly designed to allow third parties to attach additional inputs/outputs) and rebroadcast a variant with a different OP_RETURN before confirmation, or independently construct and fund a valid payout using the (off-chain-distributed) withdrawal signature with an arbitrary embedded operator key. The attribution logic in `update_finalized_payouts` performs no cross-check against which key actually supplied the funding input.

### Recommendation
Do not derive payer attribution from an unauthenticated OP_RETURN. Instead, cryptographically bind the payer's identity to the transaction in a way that is enforced by consensus/signature, e.g.:
- Require the operator's own signature over the fee-input and the OP_RETURN output (so `SIGHASH_ALL`/`SIGHASH_SINGLE` on the operator's own input covers the OP_RETURN), or
- Derive payer identity from which xonly pubkey's UTXO/kickoff-connector was actually consumed as the fee input of the confirmed payout transaction, rather than from freely-writable OP_RETURN bytes.

### Proof of Concept
1. An honest operator `O1` broadcasts a payout transaction: input 0 = user's withdrawal UTXO (signed `SinglePlusAnyoneCanPay`), input 1 = `O1`'s fee UTXO, output 0 = user's payout (covered by user signature), output 1 = OP_RETURN(`O1_xonly_pk`), plus anchor.
2. Before confirmation, an unprivileged attacker observes this transaction in the mempool. Because input 0's signature only commits to input/output pair 0, the attacker constructs a replacement transaction: input 0 = same user withdrawal UTXO/signature, input 1 = attacker's own (higher-fee) UTXO, output 0 = identical user payout, output 1 = OP_RETURN(`O2_xonly_pk`) for an arbitrary victim operator `O2`, and broadcasts it with a higher fee to replace `O1`'s transaction (RBF) or simply gets mined first.
3. Once confirmed, `update_finalized_payouts` (`core/src/verifier.rs:2311-2335`) parses `O2_xonly_pk` from the OP_RETURN and records `O2` as `payout_payer_operator_xonly_pk` in the `withdrawals` table.
4. `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-79`) on `O2`'s node then automatically calls `handle_finalized_payout`, and `O2`'s automation proceeds through kickoff/reimburse to claim the vault's `bridge_amount` reimbursement despite never having funded the payout — while `O1`, who actually paid, is permanently unable to pass `validate_payer_is_operator` (`core/src/operator.rs:1703-1719`) for that withdrawal index.

Note: I was unable to retrieve the exact body of `create_payout_txhandler` (only the optimistic-payout variant and its caller `operator.rs::withdraw` were available in the index) to confirm the precise output ordering used for the standard (non-optimistic) payout path; this may limit certainty about exactly how the fee input/OP_RETURN are combined in that code path. The core issue — that `SinglePlusAnyoneCanPay` leaves the OP_RETURN operator-identity output unauthenticated and `update_finalized_payouts` trusts it unconditionally — is confirmed from the cited files.

    async fn run_once(&mut self) -> Result<Self::Output, BridgeError> {
        let mut dbtx = self.db.begin_transaction().await?;
        let unhandled_payout = self
            .db
            .get_first_unhandled_payout_by_operator_xonly_pk(
                Some(&mut dbtx),
                self.operator.signer.xonly_public_key,
            )
            .await?;

        if unhandled_payout.is_none() {
            return Ok(false);
        }

        let (citrea_idx, move_to_vault_txid, payout_tx_blockhash) =
            unhandled_payout.expect("Must be Some");

        tracing::info!(
            "Unhandled payout found for withdrawal {}, move_txid: {}",
            citrea_idx,
            move_to_vault_txid
        );

            .db
            .get_deposit_data_with_move_tx(Some(&mut dbtx), move_to_vault_txid)
            .await?;

            return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());

            .operator
            .handle_finalized_payout(
                &mut dbtx,
                deposit_data.get_deposit_outpoint(),
                payout_tx_blockhash,
