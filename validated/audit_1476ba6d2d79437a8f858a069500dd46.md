### Title
Panic on duplicate/missing encryption-key registration lets a single malicious DKG participant crash a node - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The external report describes a denial-of-service where a crafted input reaches an assertion (`avi_read_seek` assert fault). The same class exists in Serai's PedPoP DKG encryption layer: `Decryption::register` uses `assert!` on attacker-influenced state, and `decrypt_with_proof`/`encrypt` index `enc_keys` with `HashMap` indexing that panics on missing keys. All are reachable from deserialized peer messages (`EncryptionKeyMessage::read`, `EncryptedMessage::read`, `EncryptionKeyProof::read`).

### Finding Description
`Decryption::register` is called once per participant with their `EncryptionKeyMessage` (parsed from untrusted bytes via `EncryptionKeyMessage::read` → `M::read` + `C::read_G`). It asserts the participant was not already registered:

```rust
assert!(
  !self.enc_keys.contains_key(&participant),
  "Re-registering encryption key for a participant"
);
self.enc_keys.insert(participant, msg.enc_key);
``` [1](#0-0) 

Two additional panic sites exist on the same map:

- `self.enc_keys[&decryptor]` inside `decrypt_with_proof` — a blame/decryption request naming a `decryptor` Participant that was never registered panics on the `HashMap` index. [2](#0-1) 
- `self.decryption.enc_keys[&participant]` inside `encrypt` — indexing a participant whose registration was never processed panics. [3](#0-2) 

This mirrors the FFmpeg bug exactly: a library function reachable from attacker-controlled data converts an exceptional condition into a hard `assert`/panic instead of an error, aborting the process.

### Impact Explanation
An unprivileged participant in a PedPoP DKG session who sends a second `EncryptionKeyMessage` under the same `Participant` index (or triggers the blame/`decrypt_with_proof` path against an unregistered index) causes a panic in the victim's key-generation/signing process. Crashing a validator node mid-DKG aborts the session and denies service; repeated crashes can stall threshold-key generation or signing for the set. Availability impact only, matching the source advisory's `A:H` / Medium profile.

### Likelihood Explanation
The panic is deterministic and requires only that a DKG participant deliver a duplicate or out-of-set-keyed message. The library explicitly disclaims deduplication responsibility ("this library does not handle networking... That responsibility lies with the caller," `Commitments` docs), so whether an outer layer deduplicates before `register` determines exploitability — the crypto layer itself provides no defense and turns the condition into an abort. I was unable to fully trace every call site in `pedpop/src/lib.rs` within the iteration budget, so the precise caller-side deduplication is unverified; the library-level panic is confirmed.

### Recommendation
Return an error instead of panicking. Change `Decryption::register` to `io::Result`/`Result` and treat re-registration as `Err(...)` (or `insert` and return whether it replaced). Replace `self.enc_keys[&decryptor]` and `self.decryption.enc_keys[&participant]` with `.get(&participant).ok_or(...)` so unknown participants produce a blame/verification error rather than an abort. Any data derived from deserialized peer messages should never feed `assert!`/indexing on library-controlled invariants.

### Proof of Concept
In a PedPoP key-generation session with `ThresholdParams { t, n, i }`, participant `j` sends a valid `EncryptionKeyMessage` (serialized `M` + `enc_key` point) to victim `i`. The victim calls `Encryption::register(j, msg)`, populating `decryption.enc_keys[j]`. `j` then sends a second `EncryptionKeyMessage` under the same index `j`. On `register`, `self.enc_keys.contains_key(&j)` is true → `assert!` fires → process aborts. Alternatively, in the blame path, an accuser triggers `decrypt_with_proof` with a `decryptor` Participant value never registered (e.g., an index whose registration was rejected/missing); `self.enc_keys[&decryptor]` panics on `HashMap` indexing before the DLEq proof is even evaluated.
