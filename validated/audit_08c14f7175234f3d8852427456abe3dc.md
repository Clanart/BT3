### Title
Partial-commit line selections are applied against a freshly re-fetched diff, not the diff the user reviewed - ([File: app/src/lib/git/apply.ts])

### Summary
This is a structural analog of the Sherlock finding: a value (`totalTokenVotingPower`) is computed at one point in time (proposal creation) and a decision built on top of it (`proposalThreshold`, `quorumVotes`) is later applied without re-validating that the underlying state hasn't drifted. In GitHub Desktop, `applyPatchToIndex` re-derives the diff from disk at commit time and blindly applies the user's previously-computed line `selection` indices to that new diff, instead of using/validating against the diff the selection was actually computed from.

### Finding Description
When a user stages part of a file (line-by-line/hunk partial commit), the UI computes `file.selection` (a `DiffSelection` of line indices) against a diff that was fetched and rendered earlier in `app-store.ts`. That diff can go stale — the code itself acknowledges this staleness: [1](#0-0) 

At actual commit time, `applyPatchToIndex` does not reuse the diff the selection was computed against. Instead it fetches a brand-new diff via `getWorkingDirectoryDiff(repository, file)` and formats a patch by testing `file.selection.isSelected(absoluteIndex)` against line indices of this **new** diff: [2](#0-1) [3](#0-2) 

`stageFiles` calls `applyPatchToIndex` for every partially-selected file right before `git commit` runs: [4](#0-3) [5](#0-4) 

Between the moment the diff was rendered/selected in the UI and the moment `createCommit` runs `stageFiles`/`applyPatchToIndex`, the working-directory file content can change — e.g. because of an attacker-controlled `.gitattributes` smudge/clean filter, a background auto-fetch/checkout, an editor autosave, or any other process writing to the file (all of which can be triggered by opening/cloning an attacker-controlled repository, matching the "attacker controls a cloned/fetched repository" primitive). The recomputed diff's hunk boundaries and `unifiedDiffStart` offsets shift, so the same absolute line indices in `file.selection` now point at *different* lines than the ones the user actually reviewed and checked. `formatPatch`/`applyPatchToIndex` has no mechanism to detect that the diff changed since the selection was made — it only guards against total mismatch by throwing when `git apply` fails outright; it does not verify the *content* of the previously-selected lines still matches what the user saw.

### Impact Explanation
This can silently corrupt what the user commits: content the user never selected (or explicitly deselected) can be staged and committed if it happens to land at the same line index as a previously-selected line in the refreshed diff, and vice versa — content the user intended to include can be silently dropped. This maps to "silent corruption of what the user commits or pushes," one of the explicitly valid impact categories. Because commits are cryptographically part of history and often pushed/shared, this could result in unintended data (or attacker-planted content via a crafted repo state) being committed without the user's awareness.

### Likelihood Explanation
Medium-low but plausible without any local/physical access or admin rights: any mechanism that can modify a tracked file's on-disk content between the time the diff panel renders and the time the user clicks "Commit" (clean/smudge filters, hook-triggered writes, symlink retargeting mid-session, concurrent checkout/stash pop triggered by the app itself) can shift hunk line numbers. The window is a normal user-driven delay (reviewing a diff, typing a commit message) rather than a contrived race, and the app's own code comments acknowledge this staleness is expected ("The diff might have changed dramatically since last we loaded it").

### Recommendation
Before calling `applyPatchToIndex`/`formatPatch`, re-fetch the diff and compare it (or at least the touched hunks/line content) against the diff the `DiffSelection` was computed from; if the diff has changed, invalidate/re-map the selection (similar to the existing `selectableLines` reconciliation logic in `app-store.ts`) rather than applying stale line indices to new hunk offsets. Alternatively, thread the exact diff object used to build the selection through to `applyPatchToIndex` instead of re-fetching it, and fail/re-prompt the user if that diff no longer matches the current working tree state.

### Proof of Concept
Conceptual repro (not verified end-to-end due to lack of a live environment):
1. Open a repository in Desktop and modify a tracked file so it has multiple hunks.
2. In the Changes view, partially select specific lines within a hunk (this computes `DiffSelection` against the diff rendered at that time).
3. Before clicking "Commit", cause the file to be rewritten with different line offsets in the same region (e.g., via an external process, an editor autosave, or a `.gitattributes` clean/smudge filter triggered by a fetch/checkout) without the user re-opening/re-reviewing the diff panel.
4. Click "Commit". `stageFiles` → `applyPatchToIndex` re-fetches the diff (`app/src/lib/git/apply.ts:60`) and applies the old `file.selection` indices (`app/src/lib/patch-formatter.ts:157`) to the new hunk layout, staging/committing different content than what the user selected on screen.
