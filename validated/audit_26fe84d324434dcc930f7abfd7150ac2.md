### Title
Byte-budget truncation in `cap_diff_for_prompt` drops attacker-positioned dangerous diff content, letting a crafted commit evade the security review LLM entirely - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`cap_diff_for_prompt` (and its `llm.py` twin `_cap_files_for_prompt`) truncates diff content strictly by byte position — per-file head-truncation at `DIFF_PER_FILE_BYTES` (80,000) and a running total cutoff at `DIFF_TOTAL_BYTES` (400,000) — with no risk-aware reordering unless the file *count* exceeds `MAX_DIFF_FILES` (30). An attacker who authors the diff (e.g. a PR/commit reviewed by the Stop/commit-review hooks) can pad earlier content or a single file so that the truncation boundary falls exactly before the dangerous lines, causing those lines to never reach the review prompt at all.

### Finding Description
`cap_diff_for_prompt` in `plugins/security-guidance/hooks/review_api.py` (lines 31-64) iterates `files` in the order it is given and:
- truncates any single file's content past `DIFF_PER_FILE_BYTES` by keeping only the *first* 80,000 bytes and appending a truncation marker, dropping everything after that offset;
- once the running `total` exceeds `DIFF_TOTAL_BYTES` (400,000), subsequent files are entirely replaced with `"[omitted by security-guidance: total diff byte cap reached]"`.

Risk-based reordering only happens in `_prioritize_diff_files` (`plugins/security-guidance/hooks/gitutil.py:512-548`), and that function is only invoked when `len(diff_files) > MAX_DIFF_FILES` [1](#0-0) . For the common case of a commit with ≤30 touched files — which includes almost any realistic single PR/commit — `cap_diff_for_prompt`/`_cap_files_for_prompt` operates on the diff in its original (git-diff/path) order with zero risk awareness.

This gives an attacker who controls the diff content two deterministic ways to hide a dangerous change from the reviewing LLM:
1. **Per-file truncation**: pad the beginning of a modified file with >80,000 bytes of inert content (e.g. large comments, generated-looking data, a big benign refactor) before the actual malicious hunk. `cap_diff_for_prompt` keeps only the head and truncates the tail, so the dangerous `+` line is silently dropped and replaced with a generic truncation marker — the review model never sees it.
2. **Total-budget exhaustion**: place (or grow) an earlier, low-risk file so total content exceeds 400,000 bytes before the file containing the dangerous change is processed. That later file is entirely omitted from the prompt (`"[omitted by security-guidance: ...]"`), so the reviewer receives no diff text at all for it.

Both paths are exercised directly by `build_investigate_prompt` (`review_api.py:156-176`), which calls `cap_diff_for_prompt` unconditionally before building the prompt text, and by the internal `_cap_files_for_prompt`/`agentic_review` path in `llm.py:1059-1152` used by the Stop and commit-review hooks.

### Impact Explanation
This breaks the core invariant that the security reviewer must see the actual dangerous lines it is meant to check. An attacker able to shape diff content (padding size/order within a commit under the 30-file cap) can guarantee a malicious hunk is truncated out of the review prompt entirely, causing `analyze_code_security`/`agentic_review` to approve (or simply not flag) a commit/session that contains a real vulnerability. Because this runs inside Claude Code's Stop/PostToolUse security-guidance hooks that gate whether Claude continues, is warned, or pushes/commits code, silently defeating it lets attacker-crafted changes reach the repository/session without the intended safety net — a genuine bypass of the tool's protective control, matching "Cross-repo/cross-session mutation with real security impact" in that the reviewed commit's dangerous behavior is never surfaced to the user or blocked.

### Likelihood Explanation
Fully deterministic and requires no LLM cooperation to trigger — it's pure byte-offset arithmetic in `cap_diff_for_prompt`. The only precondition is that the attacker controls (or can influence, e.g. via an accepted PR/commit whose content the victim's Claude Code session later diffs and reviews) a diff whose size crosses `DIFF_PER_FILE_BYTES` or `DIFF_TOTAL_BYTES`, and that the number of touched files stays ≤ `MAX_DIFF_FILES` so `_prioritize_diff_files` never engages to reorder by risk. Both are easy to satisfy (a single padded file, or a modest handful of files) and repeatable every time the hook fires.

### Recommendation
Apply risk-aware ordering (the same scoring used in `_prioritize_diff_files`) to all diffs before applying `cap_diff_for_prompt`/`_cap_files_for_prompt`, not just those exceeding `MAX_DIFF_FILES`; and change per-file truncation to preserve high-signal regions (e.g. keep diff hunks/`+` lines preferentially, or truncate from the middle/least-risky spans) rather than unconditionally keeping only the byte-offset head of the file.

### Proof of Concept
Unit test against `cap_diff_for_prompt`:
```python
from review_api import cap_diff_for_prompt, DIFF_PER_FILE_BYTES, DIFF_TOTAL_BYTES

def test_per_file_truncation_drops_dangerous_tail():
    padding = "context line\n" * (DIFF_PER_FILE_BYTES // len("context line\n") + 10)
    dangerous = "+os.system(user_input)  # DANGEROUS"
    content = padding + dangerous
    capped, dropped = cap_diff_for_prompt([("app/handler.py", content)])
    fp, capped_content = capped[0]
    assert dropped > 0
    assert "DANGEROUS" not in capped_content  # dangerous line silently dropped

def test_total_budget_omits_later_dangerous_file():
    big_benign = ("x" * (DIFF_TOTAL_BYTES + 1000))
    dangerous_file_content = "+eval(request.GET['q'])  # DANGEROUS"
    capped, dropped = cap_diff_for_prompt([
        ("vendor/generated.js", big_benign),
        ("app/views.py", dangerous_file_content),
    ])
    fp, content = capped[1]
    assert "DANGEROUS" not in content
    assert "[omitted by security-guidance" in content
```
Expected: both assertions currently pass on the existing implementation, confirming the dangerous line/path is not present in the prompt text handed to the review model after truncation.
