### Title
`AdditionalBlameMachine::new` skips the commitments-length check, letting a DKG participant truncate their commitment vector so blame adjudication verifies shares against a different statement and faults an honest recipient - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`SecretShareMachine::verify_r1` enforces that every participant's commitment vector contains exactly `t` points before accepting it (`msg.commitments.len() != self.params.t()` → `InvalidCommitments`). The third-party adjudicator constructor `AdditionalBlameMachine::new` — which explicitly takes "all of the participant's commitment messages" so a non-participant can assign blame — performs no such check. When `blame_internal` later evaluates `share_verification_statements`, `exponential` iterates over `commitments.len()`, so a truncated vector silently produces a truncated verification equation. This mirrors the CVE-2024-3854 class: a bounds/arity check that exists on the primary path is absent on a secondary dispatch path, causing a statement to be evaluated against the wrong (short) operand list.

### Finding Description
In `verify_r1`, each sender's `Commitments` is validated to have exactly `t` commitments (the Pedersen vector commitment to a degree `t-1` polynomial) at crypto/dkg/pedpop/src/lib.rs:317 before being stored:

```rust
if msg.commitments.len() != self.params.t().into() {
  Err(PedPoPError::InvalidCommitments(l))?;
}
```

`AdditionalBlameMachine::new` (crypto/dkg/pedpop/src/lib.rs:649-662) accepts `commitment_msgs` and stores `encryption.register(i, msg).commitments` verbatim — no length check, no PoK verification (it documents assuming prior validity, but nothing enforces arity):

```rust
commitments.insert(i, encryption.register(i, msg).commitments);
```

`blame_internal` (crypto/dkg/pedpop/src/lib.rs:575-609) then verifies the disputed share via:

```rust
multiexp_vartime(&share_verification_statements::<C>(
  recipient,
  &self.commitments[&sender],
  Zeroizing::new(share),
)).is_identity()
```

`share_verification_statements`/`exponential` (crypto/dkg/pedpop/src/lib.rs:420-449) build the statement `sum_{j=0}^{len-1} i^j * commitments[j] - share*G` over *whatever length* the sender supplied. The correct statement must cover exactly `t` coefficients. A malicious dealer can therefore:

- Broadcast a commitment message with `len < t` (i.e., commit to a lower-degree polynomial than the agreed `t`).
- Send recipient `r` a share that is valid under that shorter polynomial.
- When `r` correctly rejects the share during `calculate_share` — because the honest-participant path `verify_r1` would have already rejected the malformed commitments, or because in a dispute the honest recipient reports the sender — an arbiter calling `AdditionalBlameMachine::new` + `blame(sender, recipient, msg, proof)` evaluates the share against the truncated commitment list, finds it valid, and returns `recipient` as the faulty party.

The honest recipient is blamed (and, per the documented protocol flow, the blame result is used to slash/exclude participants), while the actual faulty sender escapes attribution.

### Impact Explanation
Blame proofs in PedPoP are the mechanism by which honest parties remove malicious dealers and by which arbiters punish faults. Returning `recipient` for an incident the `sender` caused is an inverted-verdict forgery: an unprivileged DKG participant can cause arbiter nodes to mark an honest validator as faulty. In Serai's usage this maps to honest-validator removal from the key set and potential loss of staked funds attributable to the victim — comparable in effect to a forged proof of misbehavior. Severity: Medium (requires a DKG/blame-dispute context, but produces a definitively wrong adjudication outcome).

### Likelihood Explanation
The malicious sender only needs to craft a malformed `Commitments` message — truncated `Vec<C::G>` — plus a consistent share, both fully under their control. Any deployment that runs `AdditionalBlameMachine` arbitration over commitment messages that were collected without re-running the `t`-length validation (the constructor's own docs only require that messages were "authenticated", not arity-checked) reaches this path. The trigger conditions are realistic in any deployment where blame evidence is relayed to non-participant arbiters.

### Recommendation
In `AdditionalBlameMachine::new`, take `ThresholdParams` (or `t`) and reject any commitment message where `msg.commitments.len() != t`, mirroring `verify_r1`. Additionally, `blame_internal` should defensively require `self.commitments[&sender].len()` to equal the protocol `t` before evaluating `share_verification_statements`, so a malformed stored commitment set can never produce a `recipient` verdict.

//
// Under the real protocol s's share is *invalid* for a t=3 DKG (the committed
