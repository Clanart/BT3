## Analysis

The H1 report's core defect is: a security decision is made by diffing "old" vs "new" state, but the value used as "old" isn't actually the pre-change value, so the diff-based gate can be bypassed and the mutation happens without the intended check being effective.

The closest verifiable analog in this codebase is in `updateRemoteUrl`, which silently rewrites the user's `origin` remote URL based on a GitHub API response, gated by a comparison that never actually validates the security-relevant field (the host/trust boundary of the new URL). [1](#0-0) 

### Title
Silent, unauthenticated rewrite of a repository's git remote URL from an untrusted GitHub API `clone_url` field - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically overwrites the configured `origin` remote of a local repository with whatever `clone_url` the GitHub API returns for that repository, as long as (a) the URL scheme/protocol matches, and (b) the currently configured remote still matches the *previously cached* `clone_url`. Neither of those checks verifies that the new URL still points at the same host/owner/repo identity that the user originally trusted — only that the git protocol (https vs ssh) didn't change. This function is invoked automatically during routine repository refresh, with no user confirmation.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app-store.ts` fetches the repository object from the GitHub API and, before persisting the new data, calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`: [2](#0-1) 

Inside `updateRemoteUrl`, the only checks performed before calling `gitStore.setRemoteURL(...)` are:

1. `protocolsMatch` — only verifies the URL *scheme* (https vs ssh) is unchanged, not the hostname.
2. `remoteUrlUnchanged` — verifies that the *currently configured* remote still matches the previously known `gitHubRepository.cloneURL` (i.e., the user hasn't manually repointed `origin`). [3](#0-2) 

If both conditions hold and the new `apiRepo.clone_url` differs from the current remote, Desktop calls `git remote set-url origin <apiRepo.clone_url>` with **no user confirmation and no hostname/ownership pinning**. `urlMatchesRemote`/`parseRemote` are only used to compute equality, not to enforce that the new value stays on a trusted host: [4](#0-3) 

This is structurally the same defect class as the report: a mutation ("did the object change, and is it safe to accept the change") is gated by a comparison that omits the field that actually matters for the security decision (host/identity of the remote), so the "old vs new" check does not stop the class of change it is nominally there to prevent. Any code path that can influence what `IAPIRepository.clone_url` the app receives for a tracked repository (a compromised/MITM'd GitHub Enterprise Server, a malformed/spoofed API response, or a proxy able to tamper with API responses) can cause Desktop to silently repoint `origin` to an attacker-controlled host, on a completely different domain than the one originally cloned.

### Impact Explanation
`origin` is the destination of subsequent `git push`/`git fetch` operations. If Desktop can be made to silently rewrite it to an attacker-controlled host, all future pushes (source code, potentially private) go to that host, and fetches pull code/history from an attacker-controlled origin without any user awareness — a silent corruption of what the user thinks they are pushing to. This matches the "silent corruption of what the user commits or pushes" and "attacker controls...a GitHub API object...or a git remote/proxy response" impact classes explicitly listed as valid for this exercise.

### Likelihood Explanation
This requires the attacker to control (or tamper with) the response of an authenticated `GET repos/{owner}/{name}` API call that Desktop already trusts as coming from a GitHub/GHE endpoint (e.g. a compromised/malicious GHES instance, or a network position able to tamper with API traffic to a self-hosted GHE server). Note: Desktop's `isGitHubHost`/certificate-suppression logic and the same-origin/`same-origin-filter.ts` header-stripping protections exist for other request paths, but `updateRemoteUrl`'s guard logic itself does not perform any host allow-listing — it purely trusts the field value it's given. I could not fully verify from local code alone every upstream path that could inject an untrusted `clone_url` into this flow (e.g., whether TLS pinning/cert validation would realistically be defeated for a GitHub.com-backed account vs. a self-hosted GHE instance); this is the main uncertainty in assessing exploitability against github.com specifically versus GHE deployments.

### Recommendation
- In `updateRemoteUrl`, require that the new `clone_url`'s hostname matches the existing `gitHubRepository.endpoint`/known trusted host before silently updating the remote, not just that the protocol matches.
- Prompt the user for confirmation before rewriting `origin` when the hostname changes (similar to the existing `UpstreamAlreadyExists` / `RepositorySettings` confirmation flows), rather than performing the rewrite unconditionally in the background refresh path.
- Add a regression test to `update-remote-url-test.ts` asserting that a `clone_url` pointing at a different hostname than the previously known one is never auto-applied.

### Proof of Concept
1. Track a repository in Desktop associated with a GitHub Enterprise Server account (`repository.gitHubRepository.cloneURL = https://ghe.example.com/org/repo.git`), with `origin` set to that same URL.
2. Cause the API response for `GET repos/org/repo` to return `clone_url: "https://attacker.example.com/org/repo.git"` (e.g., via a compromised/MITM'd GHE instance, or a bug/response substitution on the API side) — same protocol (`https`), so `protocolsMatch` is true; `gitStore.defaultRemote` still equals the old cached `cloneURL`, so `remoteUrlUnchanged` is true; and `urlsMatch` is false since the host differs.
3. On the next background repository refresh (`repositoryWithRefreshedGitHubRepository`), Desktop runs `git remote set-url origin https://attacker.example.com/org/repo.git` with no prompt.
4. The next `git push`/`git fetch` performed by the user silently goes to `attacker.example.com`.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
