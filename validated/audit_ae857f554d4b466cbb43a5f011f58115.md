## Summary

`EvmHost.sol`'s outgoing-GET-request fee escrow (`_requestCommitments[commitment]`) is never cleared once a `GetResponse` is successfully delivered, while the completely separate GET-timeout path only checks that this same mapping entry is non-empty before paying out a refund. This lets the escrowed fee for a single GET request be paid out twice: once to the relayer who delivered the response, and once more to the original sender via a stale-height timeout proof — a double-payment of protocol funds, directly analogous to the `canExecute` boolean collapsing "not-yet-executed" and "already-executed" into one ambiguous state.

## Finding Description

`_requestCommitments` stores `FeeMetadata{sender, fee}` for every outgoing request (POST and GET share this single mapping) [1](#0-0) .

When a `GetResponse` is delivered, `dispatchIncoming(GetResponse ...)` pays the relayer directly from `_requestCommitments[commitment].fee` but **does not delete the entry**: [2](#0-1) 

Separately, `dispatchTimeOut(GetRequestTimeout ...)` refunds `meta.fee` to `meta.sender` whenever it is invoked, gated only on `_requestCommitments[commitment]` still existing: [3](#0-2) 

The permissionless entrypoint `handleGetRequestTimeouts` in `HandlerV2.sol` decides whether a timeout is valid by comparing `request.timeout()` against `state.timestamp`, where `state` is *any* previously stored state commitment for the destination chain at a caller-chosen `message.height`, and by proving non-membership of the response receipt **only at that chosen height**: [4](#0-3) 

The only "already handled" guard for this path is `meta.sender == address(0)` on `_requestCommitments`: [5](#0-4) 

Because `_requestCommitments[commitment]` is never cleared by the response-delivery path, this guard cannot distinguish "request still pending" from "request already fulfilled via `GetResponse`". Exactly like the reported `canExecute=false` ambiguity — where a single boolean is overloaded to mean both "not ready" and "already executed" — `meta.sender != address(0)` here is overloaded to mean both "GET request outstanding" and "GET request already answered." Since the destination chain's state commitments are updated by consensus proofs independently of, and not necessarily monotonically synchronized with, when a `GetResponse` MMR-leaf is relayed, an attacker can supply a *stale* (earlier) `message.height` whose committed `state.timestamp` already exceeds `request.timeout()` and whose response-receipt trie entry is genuinely absent at that earlier height — even though the response has *already been delivered and paid for* using a later height via `handleGetResponses`.

## Impact Explanation

This allows duplicate settlement of the escrowed relayer fee for a GET request: the fee is paid once to the honest relayer that delivered the `GetResponse`, and a second time to `meta.sender` (the original requester) via `dispatchTimeOut`, both funded from the same `_requestCommitments` entry. This is a direct double-claim of protocol/bridge funds reachable from a fully permissionless, unprivileged entrypoint (`handleGetRequestTimeouts` requires no special role), matching the bounty's "double-claim/double-settlement" and "stealing or loss of funds" categories.

## Likelihood Explanation

The precondition — an available, previously-finalized destination-chain state commitment whose `timestamp` already exceeds the request's `timeoutTimestamp` but which predates the block containing the response — is a normal, expected occurrence in cross-chain messaging where consensus updates and response relaying proceed on independent schedules/relayers. No malicious relayer, prover, or admin behavior is required; an unprivileged caller only needs to submit a standard, honestly-generated non-membership proof against an older already-stored height, which the contract accepts because it never re-validates that the response wasn't delivered at a *later*, more current height.

## Recommendation

- Clear `_requestCommitments[commitment]` in `dispatchIncoming(GetResponse ...)` once the fee has been paid to the relayer, mirroring the "replay protection" pattern already used for POST/GET timeout dispatch (`delete _requestCommitments[commitment];`), so that a subsequent timeout attempt sees the request as settled.
- Additionally/alternatively, in `handleGetRequestTimeouts`, require `message.height` to be at least as recent as the latest known/finalized height for the destination state machine (or check `_responseReceipts`/a dedicated "settled" flag directly) rather than trusting any arbitrary historical non-membership proof.
- As the original report recommends, replace the implicit two-state boolean-like semantics of `meta.sender != address(0)` with an explicit tri-state status (`Pending`, `Fulfilled`, `TimedOut`) for outgoing requests, and validate that status transition in both `dispatchIncoming(GetResponse)` and `dispatchTimeOut(GetRequestTimeout)`.

## Proof of Concept

1. User dispatches a `GetRequest` with `fee = F`, `timeoutTimestamp = T`; `_requestCommitments[commitment] = {sender, F}` is stored.
2. Destination chain executes the GET at some later time; a relayer submits `handleGetResponses` with an MMR proof against a *recent* destination-state root (height `H2`), successfully delivering the response. `dispatchIncoming(GetResponse)` pays fee `F` to that relayer and leaves `_requestCommitments[commitment]` untouched.
3. Separately, the source chain's consensus client had already stored an *older* destination-state commitment at height `H1 < H2`, whose `timestamp` is already `> T` (i.e., the request had already logically timed out as of `H1`, even though it was actually fulfilled by block `H2`).
4. Any unprivileged actor calls `handleGetRequestTimeouts` with `message.height = H1` and a valid non-membership proof (response receipt genuinely absent from the state trie at `H1`, since the response was only included at `H2`).
5. `handleGetRequestTimeouts` passes: `request.timeout() (T) > state.timestamp` is false, `meta.sender != address(0)` (never cleared) passes, non-membership proof at `H1` verifies. `dispatchTimeOut(GetRequestTimeout)` runs, refunding fee `F` a second time to `meta.sender`.
6. Net effect: fee `F` has been paid out twice from the same escrowed commitment — once to the relayer, once to the sender.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }

    function handleGetRequestTimeouts(IHost host, GetTimeoutMessage calldata message) external notFrozen(host) {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            GetRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            bytes32 commitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(commitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(RESPONSE_RECEIPTS_STORAGE_PREFIX, commitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(GetRequestTimeout(request, _msgSender()), meta, commitment);
        }
    }
