### Title
Superlinear (worst-case cubic) complexity in `Offer.get_cancellation_coins()` / `detect_dependent_coin()` enables wallet-side DoS via a crafted offer with many chained coin-announcement dependencies - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer.get_cancellation_coins()` and its helper `detect_dependent_coin()` resolve announcement dependencies between the coins in an offer's coin-spend set using nested loops whose cost scales super-linearly (worst case cubic) with the number of coin spends and the number of announcement/dependency edges among them. Because the number of coin spends and the announcement graph inside a spend bundle/offer are fully attacker-controlled data (analogous to the attacker-controlled buffer contents in the Suricata KRB5 case), a malicious offer counterparty can craft an offer that is cheap to create but extremely expensive for the receiving/holding wallet to process when it is cancelled, causing a long-running computation while holding the wallet-wide state manager lock.

### Finding Description
`detect_dependent_coin` performs a triple-nested scan: [1](#0-0) 

For every name in `names` (N coins), for every dependency of that coin (D), it iterates the entire `announcement_dict` (N coins again) and does a linear membership test (`dependency in announces`, O(A) per coin). A single call is therefore up to O(N² · D · A).

`get_cancellation_coins` calls `detect_dependent_coin` inside an outer `while True` loop that iterates once per removed coin (up to N times), and inside that loop it re-scans all remaining `dependencies.items()` and rebuilds `coin_names`/`dependencies`/`announcements` with list/set operations that are themselves O(N) per removal: [2](#0-1) 

Combining the O(N) outer removals with the O(N²) cost of `detect_dependent_coin` per removal yields worst-case cubic behavior in the number of coin spends/announcements in the offer — the same class of bug as the reported KRB5 issue: an attacker-controlled data structure (buffer size in KRB5, coin/announcement graph size here) is processed with nested nested-scan logic instead of an amortized/indexed algorithm.

This function is invoked from `TradeManager.cancel_pending_offers`, which runs under the global `wallet_state_manager.lock`: [3](#0-2) [4](#0-3) 

The offer bytes (`trade.offer`) originate from an offer file that can be produced by an untrusted counterparty (offer maker) and stored locally as a `TradeRecord` when the local wallet takes/creates the trade. The coin-spend count and their `CREATE_COIN_ANNOUNCEMENT` (opcode 60) / `ASSERT_COIN_ANNOUNCEMENT` (opcode 61) conditions are entirely controlled by whoever constructs the offer's spend bundle, since `Offer.from_bytes()` simply deserializes the bundle without bounding the number of coin spends or the announcement fan-out.

### Impact Explanation
When a user (maker or taker) later calls `cancel_offer`/`cancel_offers` (RPC or CLI) on a trade whose stored offer was crafted with a large number of coin spends and maximally chained announcement dependencies, `get_cancellation_coins()` can consume disproportionate CPU time while holding `wallet_state_manager.lock`. Since this lock guards general wallet state operations, this stalls the wallet's ability to process other pending transactions/RPCs — a spend/offer-triggered transaction-processing halt on the affected wallet node, matching the accepted impact class ("spend-triggered transaction-processing halt").

### Likelihood Explanation
Likelihood is moderate-to-high for a determined attacker: constructing an offer with many synthetic coin spends and announcement conditions requires no special privileges — it is standard CLVM condition data within a spend bundle that the attacker fully controls as offer maker, and getting a victim wallet to accept/store such an offer (e.g., via `chia offers take` or by sending an offer file) is a normal user workflow. The victim only needs to attempt to cancel the trade to trigger the expensive path.

### Recommendation
- Replace the O(N²)/O(N³) nested-scan dependency resolution in `detect_dependent_coin`/`get_cancellation_coins` with an indexed approach: build a reverse index from announcement message → coin name once, and use it for O(1) dependency lookups instead of re-scanning `announcement_dict.items()` for every dependency of every coin.
- Bound/validate the number of coin spends and the announcement fan-out considered when computing cancellation coins for externally-supplied offers, or move this computation off any lock that blocks unrelated wallet operations.
- Add a cost/time budget (similar to CLVM execution cost accounting) around cancellation-coin computation so a pathological offer cannot cause unbounded wallet-side computation.

### Proof of Concept
Conceptual construction (cannot be executed in this environment, described for a Devin session to implement and benchmark):
1. Build an `Offer` whose underlying `WalletSpendBundle` contains N (e.g., 5,000–50,000) non-ephemeral coin spends.
2. For each spend, include a `CREATE_COIN_ANNOUNCEMENT` (opcode 60) condition creating a unique announcement, and an `ASSERT_COIN_ANNOUNCEMENT` (opcode 61) condition that depends on another coin's announcement, forming a long dependency chain (e.g., coin i depends on coin i-1) so that `detect_dependent_coin` must repeatedly rescan the full `announcement_dict` for each of the N removals.
3. Call `offer.get_cancellation_coins()` (as done from `TradeManager.cancel_pending_offers`) and measure wall-clock time vs. N; verify the growth is super-linear (quadratic/cubic), demonstrating that runtime scales far worse than the number of coins, unlike a properly indexed O(N) implementation.

```python
def detect_dependent_coin(
    names: list[bytes32], deps: dict[bytes32, list[bytes32]], announcement_dict: dict[bytes32, list[bytes32]]
) -> tuple[bytes32, bytes32] | None:
    # First, we check for any dependencies on coins in the same bundle
    for name in names:
        for dependency in deps[name]:
            for coin, announces in announcement_dict.items():
                if dependency in announces and coin != name:
                    # We found one, now remove it and anything that depends on it (except the "provider")
                    return name, coin
    return None
```

```python
    def get_cancellation_coins(self) -> list[Coin]:
        # First, we're going to gather:
        dependencies: dict[bytes32, list[bytes32]] = {}  # all of the hashes that each coin depends on
        announcements: dict[bytes32, list[bytes32]] = {}  # all of the hashes of the announcement that each coin makes
        coin_names: list[bytes32] = []  # The names of all the coins
        additions = self.additions()
        for spend in [cs for cs in self._bundle.coin_spends if cs.coin not in additions]:
            name = bytes32(spend.coin.name())
            coin_names.append(name)
            dependencies[name] = []
            announcements[name] = []
            conditions: Program = run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)[1]
            for condition in conditions.as_iter():
                if condition.first() == 60:  # create coin announcement
                    announcements[name].append(
                        AssertCoinAnnouncement(asserted_id=name, asserted_msg=condition.at("rf").as_python()).msg_calc
                    )
                elif condition.first() == 61:  # assert coin announcement
                    dependencies[name].append(bytes32(condition.at("rf").as_python()))

        # We now enter a loop that is attempting to express the following logic:
        # "If I am depending on another coin in the same bundle, you may as well cancel that coin instead of me"
        # By the end of the loop, we should have filtered down the list of coin_names to include only those that will
        # cancel everything else
        while True:
            removed = detect_dependent_coin(coin_names, dependencies, announcements)
            if removed is None:
                break
            removed_coin, provider = removed
            removed_announcements: list[bytes32] = announcements[removed_coin]
            remove_these_keys: list[bytes32] = [removed_coin]
            while True:
                for coin, deps in dependencies.items():
                    if set(deps) & set(removed_announcements) and coin != provider:
                        remove_these_keys.append(coin)
                removed_announcements = []
                for coin in remove_these_keys:
                    dependencies.pop(coin)
                    removed_announcements.extend(announcements.pop(coin))
                coin_names = [n for n in coin_names if n not in remove_these_keys]
                if removed_announcements == []:
                    break
                else:
                    remove_these_keys = []

        return [cs.coin for cs in self._bundle.coin_spends if cs.coin.name() in coin_names]
```

```python
    async def cancel_pending_offers(
        self,
        trade_ids: list[bytes32],
        action_scope: WalletActionScope,
        fee: uint64 = uint64(0),
        secure: bool = True,  # Cancel with a transaction on chain
        trade_cache: dict[bytes32, TradeRecord] = {},  # Optional pre-fetched trade records for optimization
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> None:
        """This will create a transaction that includes coins that were offered"""

        # Need to do some pre-figuring of announcements that will be need to be made
        announcement_nonce: bytes32 = std_hash(b"".join(trade_ids))
        trade_records: list[TradeRecord] = []
        all_cancellation_coins: list[list[Coin]] = []
        announcement_creations: deque[CreateCoinAnnouncement] = deque()
        announcement_assertions: deque[AssertCoinAnnouncement] = deque()
        for trade_id in trade_ids:
            if trade_id in trade_cache:
                trade = trade_cache[trade_id]
            else:
                potential_trade = await self.trade_store.get_trade_record(trade_id)
                if potential_trade is None:
                    self.log.error(f"Cannot find offer {trade_id.hex()}, skip cancellation.")
                    continue
                else:
                    trade = potential_trade

            cancellation_coins = Offer.from_bytes(trade.offer).get_cancellation_coins()
            for coin in cancellation_coins:
                creation = CreateCoinAnnouncement(msg=announcement_nonce, coin_id=coin.name())
                announcement_creations.append(creation)
                announcement_assertions.append(creation.corresponding_assertion())

            trade_records.append(trade)
            all_cancellation_coins.append(cancellation_coins)
```
