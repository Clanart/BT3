Based on my investigation, I found a strong analog. The key finding: `validateResolutionPaths` in `copilot-conflict-resolution.ts` strictly validates that the model's returned paths match the `expectedFiles` set (rejecting unexpected/duplicate/missing paths) [1](#0-0) . However, this validation happens once, right after parsing the model response. The consuming write path in `AppStore._applyCopilotConflictResolutions` re-fetches `state.changesState.workingDirectory.files` at write time and only skips a resolution if the on-disk file is *found* and already externally resolved — it does **not** skip when the file is simply absent from the current working-directory list [2](#0-1) .

### Title
Stale-state file write in Copilot conflict resolution allows silent corruption of unrelated files - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_applyCopilotConflictResolutions` writes `resolution.resolvedContent` to disk whenever the current working-directory snapshot has no matching conflicted entry for `resolution.path`, rather than only writing to files that are confirmed to still be part of the active conflict set at write time.

### Finding Description
The write loop guards against clobbering a *user-resolved* file only when a matching entry is found in `state.changesState.workingDirectory.files` and that entry is no longer conflicted:
```
const onDiskFile = state.changesState.workingDirectory.files.find(f => f.path === resolution.path)
if (onDiskFile !== undefined && isConflictedFileStatus(onDiskFile.status) && !hasUnresolvedConflicts(onDiskFile.status)) {
  continue
}
await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
pathsToStage.push(resolution.path)
``` [3](#0-2) 

If `onDiskFile === undefined` — because the working-directory snapshot captured in `state` is stale relative to the actual repository at the moment the user clicks "Continue Merge" (e.g., the multi-commit operation completed, the conflict was resolved/staged out-of-band, or a git operation ran concurrently while the Copilot SDK request was in flight) — the function falls through and unconditionally writes attacker/model-controlled content to `resolution.path` and stages it with `git add`. `resolveWithin` only guards against path traversal outside the repository root [4](#0-3) ; it does not verify the target file was ever part of the conflict being resolved. This mirrors the report's core defect pattern: two different tracking mechanisms for the same logical state (the one-time `validateResolutionPaths` check at parse time vs. the live `workingDirectory.files` lookup at write time) that can fall out of sync, letting a stale/incomplete state check be bypassed to perform an unauthorized write — analogous to how `_events`/`_snapshots` tracking mismatch let a withdrawal bypass an intended guard.

### Impact Explanation
A successful exploitation silently corrupts what the user commits: file content the user never reviewed (LLM-influenced, and ultimately traceable back to attacker-crafted conflict content since Copilot's prompt is built from the repository's own conflicting hunks) gets written and staged into the commit, with `git add` executed on that path even though it was never displayed in the `copilot-conflicts-dialog.tsx` result-review UI. This satisfies "silent corruption of what the user commits or pushes" from an attacker-controlled repository/git-object without any privileged access or unnatural user steps beyond the normal "Resolve with Copilot" flow.

### Likelihood Explanation
This requires timing: the state read at the top of `_applyCopilotConflictResolutions` must be stale relative to the live working directory when the write loop iterates. I could not fully confirm from static analysis whether `state` is guaranteed fresh in all call paths (e.g., whether `_loadStatus` is always awaited immediately beforehand) or whether a race is practically reachable — this bounds my confidence and would need runtime/dynamic verification (e.g., stepping through `_startCopilotConflictResolution`/`_applyCopilotConflictResolutions` call sites) that a static-only Ask session cannot perform.

### Recommendation
Before writing, re-fetch current on-disk/working-directory status (or otherwise verify) and require an affirmative match confirming `resolution.path` is still an unresolved conflicted file, rather than defaulting to "write" when no matching entry is found. Fail closed (skip + surface to the user) on the not-found case symmetrically with the found-and-resolved case.

### Proof of Concept
Not independently reproduced at runtime; derived from static code review of the write-guard logic cited above. A concrete PoC would require instrumenting `_startCopilotConflictResolution` to inject a workflow where the working-directory state used at write time predates a change that removes/alters `resolution.path` from `workingDirectory.files`, then confirming the file is written and `git add`-staged despite not appearing in the confirmation dialog.

Given the uncertainty about reachability of the staleness window, treat this as a plausible but not fully confirmed analog — a Devin session with terminal/dynamic-testing access would be needed to conclusively demonstrate or rule out the race.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
