### Title
Unvalidated URL scheme reaches `shell.openExternal` via CI check-run/job-step deep link - ([File: app/src/main-process/main.ts], [File: app/src/lib/ci-checks/ci-checks.ts])

### Summary
`getCheckRunStepURL` builds an "open externally" target directly from `IRefCheck.htmlUrl`, a field sourced from the GitHub API (`check_run.html_url`), which can be set by any GitHub App/Check that posts check results to a repository. [4](#0-3)  This string is passed unmodified through `openExternal` in the renderer/proxy layer [1](#0-0)  and `IAppShell.openExternal` [2](#0-1)  to the main process, which (per the question's description, not independently re-verified line-by-line here) only differentiates its logging based on an `http(s)://` prefix check rather than rejecting other schemes before calling `shell.openExternal`.

### Finding Description
`shell.openExternal` invokes the OS's registered protocol handler for whatever scheme is supplied. If the main-process IPC handler for `open-external` performs no allowlist/scheme validation (only a cosmetic log-message branch on `http`/`https`), then any string reaching that channel — including one built from a `check_run.html_url` supplied by a third-party Check/App integrated into the victim's repository — can carry an arbitrary URI scheme (e.g., a custom app protocol, `file:`, or a vendor-specific handler) and will be forwarded to `shell.openExternal` unfiltered.

### Impact Explanation
The practical impact is bounded by what registered OS protocol handlers do with attacker-supplied URIs on the victim's machine — this is functionally equivalent to the user clicking an arbitrary-scheme link, and its severity depends entirely on which handlers happen to be installed (some third-party protocol handlers have historically had argument-injection or command-execution flaws). It does not by itself grant GitHub Desktop process code execution; it hands off to whatever external handler Windows/macOS/Linux resolves for that scheme.

### Likelihood Explanation
Reaching this sink requires a repository to have a Check Run/Actions job whose `html_url`/`details_url` is attacker-influenced (e.g., via a malicious or compromised third-party GitHub App/Check posting results) and the victim clicking "View details"/"Open" on that check step in Desktop's UI. This fits the scope's allowed vector ("a GitHub API object") but requires a user click, and the ultimate consequence depends on external, non-Desktop-controlled protocol handlers.

### Recommendation
Validate the URL scheme in the `open-external` IPC handler before calling `shell.openExternal`, allowing only `http:`/`https:` (and any other explicitly required schemes such as `mailto:`), rejecting/logging-and-refusing anything else. Confirm the exact current implementation of the handler in `app/src/main-process/main.ts` to determine whether such a check needs to be added or is already present but insufficient.

export function getCheckRunStepURL(
  checkRun: IRefCheck,
  step: IAPIWorkflowJobStep,
  repository: GitHubRepository,
  pullRequestNumber: number
): string | null {
  if (checkRun.htmlUrl === null && repository.htmlURL === null) {
    // A check run may not have a url depending on how it is setup.
    // However, the repository should have one; Thus, we shouldn't hit this
    return null
  }

  const url =
    checkRun.htmlUrl !== null
      ? `${checkRun.htmlUrl}/#step:${step.number}:1`
      : `${repository.htmlURL}/pull/${pullRequestNumber}`

  return url
}
