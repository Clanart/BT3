Based on the code traced, this is a real finding, but scoped more narrowly than the question implies: confirmation is present for **new** clones but absent for the branch-checkout step against **already-added** repositories.

### Title
Deep-link `open-repository-from-url` silently checks out attacker-chosen branch without confirmation when the target repository is already added to Desktop - (File: app/src/ui/dispatcher/dispatcher.ts)

### Summary
`Dispatcher.dispatchURLAction` routes an unauthenticated `open-repository-from-url` deep link straight into `openRepositoryFromUrl` with no gating dialog: [1](#0-0) 

`openRepositoryFromUrl` branches on the `branch`/`pr` fields parsed by `parseAppURL` from the untrusted URL and, for the plain-branch case, calls `openBranchNameFromUrl`: [2](#0-1) 

### Finding Description
`openBranchNameFromUrl` first resolves the repository via `openOrCloneRepository`, then unconditionally fetches and checks out `branchName`: [3](#0-2) 

`openOrCloneRepository` only shows a confirmation dialog (`PopupType.CloneRepository`, requiring an explicit "Clone" click gated by `_startOpenInDesktop`/`_completeOpenInDesktop`) when the repository is **not yet known** to Desktop: [4](#0-3) [5](#0-4) 

If a repository matching the URL (via `doesRepositoryMatchUrl`, comparing origin/upstream HTML URLs) is **already added**, `selectRepository` is called directly with no popup at all: [6](#0-5) 

In that path, the code proceeds straight to `_refreshRepository`, `_fetch`, and `checkoutLocalBranch(repository, branchName)` — a full fetch + checkout of an attacker-supplied branch name with zero user confirmation naming the branch that is about to be checked out.

`branch` itself only passes through `testForInvalidChars` in `parse-app-url.ts` (rejecting characters invalid in git ref names), which prevents ref-name injection but does not add any consent gate: [7](#0-6) 

I was unable to fully inspect the `checkoutLocalBranch` implementation body (only its call sites were indexed) to confirm whether it independently pops a "discard changes"/stash confirmation dialog when the working tree is dirty; that gap should be verified before finalizing severity, since GitHub Desktop generally does prompt for uncommitted-changes handling on branch switches through the normal checkout flow, which would blunt (but not eliminate) the "no confirmation at all" characterization for dirty working trees.

For a **new** repository (not previously added), the flow does require an explicit "Clone" click via the `PopupType.CloneRepository` dialog before any clone/checkout occurs, so the invariant described in the question ("only a deliberate click can initiate checkout") largely holds for first-time clones — the gap is specifically for repositories the user already has open in Desktop.

### Impact Explanation
An attacker who gets a user to click a `x-github-client://openRepo/<url>?branch=<attacker-branch>` (or equivalent protocol) link pointing at a repository the victim already has in Desktop can force Desktop to fetch and silently check out an attacker-chosen branch, with no dialog naming the branch, no click required, and no indication to the user other than the app switching context. This can be used to flip the user onto a branch containing malicious build scripts, hooks, or altered file content, setting up follow-on supply-chain-style attacks (e.g., a subsequent commit/push corrupting the wrong branch, or a build/IDE hook firing off the newly checked-out branch) if the user is not paying attention to which branch is active.

### Likelihood Explanation
Requires the victim to click an attacker-supplied deep link (the standard delivery vector for GitHub Desktop's protocol handler) and to already have the target repository present in their local repository list — a plausible but non-trivial precondition (most impactful against contributors who already track the targeted repo, e.g., popular OSS projects). `pr`-based branch checkouts (`openPullRequestFromUrl`) additionally validate against the GitHub API's PR object before checkout, making the plain `branch=` path the primary concern.

### Recommendation
Before calling `_fetch`/`checkoutLocalBranch` in `openBranchNameFromUrl` for an *already-added* repository, show an explicit confirmation dialog naming the repository and the exact branch to be checked out, mirroring the consent already required for first-time clones via `PopupType.CloneRepository`.

### Proof of Concept
1. Victim has `https://github.com/org/repo` already added in GitHub Desktop.
2. Attacker sends victim a link: `x-github-client://openRepo/https://github.com/org/repo?branch=malicious-branch`.
3. Victim clicks the link (single click, no in-app confirmation).
4. `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl` → `openOrCloneRepository` finds the existing repo via `doesRepositoryMatchUrl` and returns it with no popup → the dispatcher fetches and calls `checkoutLocalBranch(repository, 'malicious-branch')`, switching the victim's local checkout without any dialog naming the branch.

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }

  private async openOrCloneRepository(url: string): Promise<Repository | null> {
    const state = this.appStore.getState()
    const repositories = state.repositories
    const existingRepository = repositories.find(r =>
      this.doesRepositoryMatchUrl(r, url)
    )

    if (existingRepository) {
      return await this.selectRepository(existingRepository)
    }

    return this.appStore._startOpenInDesktop(() => {
      this.changeCloneRepositoriesTab(CloneRepositoryTab.Generic)
      this.showPopup({
        type: PopupType.CloneRepository,
        initialURL: url,
      })
    })
  }

  /**
   * Start an Open in Desktop flow. This will return a new promise which will
   * resolve when `_completeOpenInDesktop` is called.
   */
  public _startOpenInDesktop(fn: () => void): Promise<Repository | null> {
    const p = new Promise<Repository | null>(
      resolve => (this.resolveOpenInDesktop = resolve)
    )
    fn()
    return p
  }

  /**
   * Complete any active Open in Desktop flow with the repository returned by
   * the given function.
   */
  public async _completeOpenInDesktop(
    fn: () => Promise<Repository | null>
  ): Promise<Repository | null> {
    const resolve = this.resolveOpenInDesktop
    this.resolveOpenInDesktop = null

    const result = await fn()
    if (resolve) {
      resolve(result)
    }

    return result
  }
