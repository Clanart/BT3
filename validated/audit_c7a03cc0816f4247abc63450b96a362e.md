### Title
Cached FROST preprocess reused across validator sets due to context key omitting the set/genesis, enabling nonce reuse and validator secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` caches the FROST preprocess seed (`CachedPreprocess`, a ChaCha20 seed from which both nonce scalars `d, e` are deterministically derived) in the database keyed only by `context`. For `DkgConfirmer`, the context is `(b"DkgConfirmer", self.attempt)` — it does **not** include the tributary genesis, `ExternalValidatorSet`, or the `KeyPair` being confirmed. A cached seed is therefore reused whenever the same `(label, attempt)` pair recurs, and the same deterministic nonces are used to `sign` a *different* message (`set_keys_message` binds the set, removed list, and key pair). Two Schnorr signature shares produced with the same nonce over different challenges linearly reveal the signer's secret share.

### Finding Description
The external report's bug class is "resource used after it should have been invalidated" (use-after-free of the connection buffer). The Serai analog is a cryptographic use-after-free: a single-use preprocess (whose reuse leaks the secret share, per `crypto/frost/src/sign.rs` docs: "This cached preprocess MUST only be used once. Reuse of it enables recovery of your private key share") is kept in `CachedPreprocesses` and deterministically reloaded on every call.

The flow:

1. `preprocess_internal` computes `encryption_key = Blake2s256("Cached Preprocess Encryption Key" || context.encode() || key)` and checks `CachedPreprocesses::get(txn, &context)`; only if absent does it generate a fresh preprocess via `OsRng` (lines 123–135).
2. It then always reloads the cached seed and calls `AlgorithmSignMachine::from_cache`, which regenerates identical nonces via `ChaCha20Rng::from_seed(seed)` in `seeded_preprocess` (`crypto/frost/src/sign.rs:121-144`).
3. `DkgConfirmer::signing_protocol` sets `context = (b"DkgConfirmer", self.attempt)` (line 275). `attempt` is a per-tributary DKG attempt counter (`removed_as_of_dkg_attempt(txn, spec.genesis(), attempt)`), which restarts for each new validator set's DKG. Nothing in the key distinguishes `spec.genesis()` / `spec.set()`.
4. `share_internal` signs `msg = set_keys_message(&self.spec.set(), removed, key_pair)` — a message that differs across sets (different set ID, different `KeyPair`), while the nonce seed is identical.
5. `complete()` even calls `share_internal` a second time (line 322), and the produced shares are published on-chain inside the `set_keys` call for anyone to read.

Given two shares `s1 = d + e·ρ1 + λ·x·c1` and `s2 = d + e·ρ2 + λ·x·c2` from the same seed (same `d, e`, same secret share `x`), a third reuse or (when peer preprocess sets are identical, making ρ equal) the plain pair with distinct `c` reduces the unknowns; in the Schnorrkel/MuSig single-binding-factor case where `ρ` is the same (same participant set ordering) but `c` differs, `x = (s1 − s2) / (λ·(c1 − c2))` directly recovers the validator's MuSig secret share.

### Impact Explanation
Recovery of a validator's Ristretto secret share (`self.key`) — the validator's root-of-trust signing key used to confirm DKG results on Substrate. The leaked material is derivable passively from shares already published on-chain; no malformed input or privileged position is required. With threshold-many shares recovered this way across validators, an attacker forges `set_keys` confirmations, i.e., installs attacker-controlled threshold keys for the network's liquidity sets — full compromise of subsequently confirmed key sets.

### Likelihood Explanation
Reuse requires the same `(b"DkgConfirmer", attempt)` key to recur with a different message. `attempt` is scoped per-tributary DKG, so every new validator set rotation restarts the attempt counter while `spec.set()` and the confirmed `KeyPair` change — the cache key collides exactly when the message changes. A validator persisting its coordinator DB across a set rotation hits this deterministically on the next DKG confirmation, no adversarial action needed. Additionally, `complete()` re-invokes `share_internal` with caller-supplied preprocesses; if the preprocess set that reaches `complete` differs from the one used in `share` (e.g., a differing participant subset finalized for the same attempt), a second distinct share under the same nonces is emitted within a single set.

### Recommendation
Include the signing context's full identity in the cache key: change the context to include `spec.genesis()` (or `spec.set()`) and the `KeyPair`/message digest, e.g. `context = (b"DkgConfirmer", spec.genesis(), attempt, hash(set_keys_message))`, and key `CachedPreprocesses` on that. Additionally, delete the cached preprocess (`CachedPreprocesses::del`) once the confirmation for that context is finalized, and add the documented TODO check that the on-chain commitment equals the presumed preprocess before publishing shares.

### Proof of Concept
Conceptual (source-level):

1. Validator set N runs `DkgConfirmer` with `attempt = a`. `preprocess_internal` stores seed `S` under `CachedPreprocesses[("DkgConfirmer", a)]` and publishes share `s1` for `set_keys_message(set_N, removed_N, key_pair_N)` with nonce `R = d·G + e·ρ·H`.
2. Set rotates; set N+1's tributary runs `DkgConfirmer` again at `attempt = a`. `CachedPreprocesses::get` hits, `from_cache` regenerates identical `d, e`. `share_internal` signs `set_keys_message(set_{N+1}, …, key_pair_{N+1})` — a different challenge `c2` — producing `s2` with the same `R`.
3. Observer reads both published shares: `x = (s1 − s2) · (λ·(c1 − c2))⁻¹ mod l` recovers the validator's MuSig secret share (when ρ is unchanged — same participant ordering — or given a third reuse to solve the three-unknown system in the general case).
