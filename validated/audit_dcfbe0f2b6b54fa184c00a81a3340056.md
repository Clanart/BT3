### Title
Log Forging via Unsanitized Attacker-Controlled Field/Extension Names in ProtoJSON Parse Error Messages - (File: src/google/protobuf/json/internal/lexer.cc, src/google/protobuf/json/internal/parser.cc)

### Summary
The C++ ProtoJSON parser embeds raw, attacker-controlled JSON object keys (field names, extension names) verbatim into the `absl::Status` error message returned from public parse APIs (`JsonStringToMessage` / `JsonToBinaryStream` / `util::JsonStringToMessage`), with only a cosmetic whitespace-randomization "hardening" step (`HardenAgainstHyrumsLaw`) applied — not sanitization of control characters such as `\n`, `\r`, or ANSI escape sequences. If a consuming application logs `status.message()` on a parse failure (a very common pattern for diagnosing bad ProtoJSON input, exactly analogous to logging the invalid `mail` parameter in the JHipster advisory), an attacker can inject forged log entries or terminal escape sequences by including control characters as part of a JSON key.

### Finding Description
`JsonLocation::Invalid` builds the error string by directly formatting the caller-supplied `message` (which frequently contains the offending field/extension name taken straight from the JSON input) and the parser's path description: [1](#0-0) 

The comment inside this function makes the intent explicit: the "invalid JSON" prefix is deliberately *not* obfuscated "so that people have a hope of grepping for it in logs," and `HardenAgainstHyrumsLaw` only randomly inserts extra spaces after existing space characters — it does not strip, escape, or reject `\n`, `\r`, `\t`, or non-printable/ANSI control bytes: [2](#0-1) 

The unsanitized attacker-controlled value enters this pipeline from field/extension resolution failures during message parsing, where the JSON object key `name` (decoded from JSON, so `\n`/`\r`/control sequences supplied via `\u000a`, `\u000d`, `\u001b` escapes are already unescaped into literal control bytes by the JSON string lexer) is interpolated directly into the error message: [3](#0-2)  for unknown-field and mismatched-extension errors, and [4](#0-3)  for "already been set" duplicate-key errors.

This mirrors the failed invariant in the JHipster advisory exactly: user/attacker-supplied data (there, an email address; here, a JSON key/field name) is written into a message that is highly likely to be logged by the consuming application, without neutralizing characters (CR/LF, ANSI escapes) that let the attacker inject fabricated log records or terminal control sequences (CWE-117).

### Impact Explanation
Impact is Integrity-only (matching the original advisory's `C:N/I:L/A:N` profile): no data disclosure, no availability impact, no memory corruption. A remote, unauthenticated client sending a bounded, otherwise well-formed ProtoJSON payload through any public ProtoJSON parsing entry point (`JsonStringToMessage`, `JsonToBinaryStream`, and the language-specific ProtoJSON parsers that wrap this C++ core) can cause an application that logs parse-failure `Status` messages (a standard diagnostic practice) to write attacker-chosen bytes — including newlines that fabricate additional, fake log lines, or ANSI/terminal escape sequences that can corrupt terminal-based log viewers — into that log stream. This is exactly the log-forging/log-injection class described by CWE-117 and the referenced OWASP guidance, transposed from JHipster's email field to Protobuf's ProtoJSON field-name error path.

### Likelihood Explanation
High likelihood of reachability: any malformed/unexpected key in a ProtoJSON payload (unknown field, mismatched extension, duplicate key) triggers this path, and JSON string escaping (`\u000a`, `\u000d`, `\u001b`, etc.) is a standard, always-available mechanism for embedding literal control bytes in a JSON key — no special parser bypass is needed. The main precondition, consistent with the original advisory's scope note ("this problem affects only application[s] generated with jwt or session authentication ... using the value in a log statement"), is that the consuming application actually logs the returned error `Status`/message rather than only inspecting `ok()`. This is a common but not universal pattern, so the finding is a real but conditionally-exploitable Medium-severity issue, not a directly exploitable vulnerability in protobuf's own execution.

### Recommendation
- In `JsonLocation::Invalid` (and any other path/field-name interpolation site in `src/google/protobuf/json/internal/parser.cc`), sanitize or escape control characters (`\n`, `\r`, `\t`, and non-printable bytes) in attacker-controlled substrings (field names, extension names, path segments) before embedding them into the returned `absl::Status` message — e.g., using `absl::CEscape` or an equivalent escaping routine, rather than relying solely on `HardenAgainstHyrumsLaw`'s whitespace randomization, which is explicitly documented as anti-Hyrum's-Law obfuscation and not a security control.
- Document in the public ProtoJSON API surface that returned error messages may contain untrusted, attacker-influenced substrings, and that callers must not log them directly without their own escaping.

### Proof of Concept
Given a trusted proto schema with message `TestMessage` (no field literally named with embedded control characters), send the following ProtoJSON payload to any public entry point (e.g., `google::protobuf::json::JsonStringToMessage`):
```
{"unknown_field_name_with_injected\r\n2026-09-23 FAKE ERROR admin login succeeded from 10.0.0.1\r\n": 1}
```
After JSON unescaping, the object key `name` passed into `ParseField` at [5](#0-4) 
becomes `unknown_field_name_with_injected<CR><LF>2026-09-23 FAKE ERROR admin login succeeded from 10.0.0.1<CR><LF>`, which is embedded verbatim (only cosmetically padded with extra spaces by `HardenAgainstHyrumsLaw`) into the returned `absl::Status::message()` via [6](#0-5) . Any caller that does `ABSL_LOG(ERROR) << status;` or `logger.error(status.message())` on parse failure will write two additional, attacker-forged log lines into the log stream. // Randomly inserts bonus whitespace of a few different kinds into a string.
//
// This utility is intended to make error messages hostile to machine
// interpretation as a Hyrum's Law countermeasure, without potentially confusing
// human readers.
void HardenAgainstHyrumsLaw(absl::string_view to_obfuscate, std::string& out) {
  // Get some simple randomness from ASLR, which is enabled in most
  // environments. Our goal is to be annoying, not secure.
  static const void* const kAslrSeed = &kAslrSeed;
  // Per-call randomness from a relaxed atomic.
  static std::atomic<uintptr_t> kCounterSeed{0};

  constexpr uint64_t kA = 0x5851f42d4c957f2dull;
  constexpr uint64_t kB = 0x14057b7ef767814full;

  uint64_t state = absl::bit_cast<uintptr_t>(kAslrSeed) + kB +
                   kCounterSeed.fetch_add(1, std::memory_order_relaxed);
  auto rng = [&state, &kA, &kB] {
    state = state * kA + kB;
    return absl::rotr(static_cast<uint32_t>(((state >> 18) ^ state) >> 27),
                      state >> 59);
  };
  (void)rng();  // Advance state once.

  out.reserve(to_obfuscate.size() + absl::c_count(to_obfuscate, ' '));
  for (char c : to_obfuscate) {
    out.push_back(c);
    if (c != ' ' || rng() % 3 != 0) {
      continue;
    }

    size_t count = rng() % 2 + 1;
    for (size_t i = 0; i < count; ++i) {
      out.push_back(' ');
    }
  }
}

absl::Status JsonLocation::Invalid(absl::string_view message,
                                   SourceLocation sl) const {
  // NOTE: we intentionally do not harden the "invalid JSON" part, so that
  // people have a hope of grepping for it in logs. That part is easy to
  // commit to, as stability goes.
  //
  // This copies the error twice. Because this is the "unhappy" path, this
  // function is cold and can afford the waste.
  std::string status_message = "invalid JSON";
  std::string to_obfuscate;
  if (path != nullptr) {
    absl::StrAppend(&to_obfuscate, " in ");
    path->Describe(to_obfuscate);
    to_obfuscate.push_back(',');
  }
  absl::StrAppendFormat(&to_obfuscate, " near %zu:%zu (offset %zu): %s",
                        line + 1, col + 1, offset, message);
  HardenAgainstHyrumsLaw(to_obfuscate, status_message);

  return absl::InvalidArgumentError(std::move(status_message));
}

    absl::string_view extn_name = name.substr(1, name.size() - 2);
    field = Traits::ExtensionByName(desc, extn_name);

    if (field.has_value()) {
      // The check for whether this is an invalid field occurs below, since it
      // is combined for both extension and non-extension fields.
      auto correct_type_name = Traits::TypeName(desc);
      if (Traits::TypeName(Traits::ContainingType(*field)) !=
          correct_type_name) {

            "'%s' is a known extension name, but is not an extension "
            "of '%s' as expected",
            extn_name, correct_type_name));

    }

    field = Traits::FieldByName(desc, name);
  }

    if (!lex.options().ignore_unknown_fields) {
      return lex.Invalid(absl::StrFormat("no such field: '%s'", name));
    }
