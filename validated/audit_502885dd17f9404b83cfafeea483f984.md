## Title
Argument injection via unsanitized `clone_url`/remote URL in `git remote add` and `git remote set-url` - (File: `app/src/lib/git/remote.ts`)

### Summary
`addRemote` and `setRemoteURL` in `app/src/lib/git/remote.ts` build the git command line as `['remote', 'add', name, url]` / `['remote', 'set-url', name, url]` with no `--` end-of-options marker before the `url` positional argument. [1](#0-0) [2](#0-1) 
These functions are fed URLs that originate from attacker-influenceable data — most notably `pullRequest.head.repo.clone_url` from the GitHub API — without any validation that the value is a well-formed git URL rather than a git command-line option. [3](#0-2) [4](#0-3) 

### Finding Description
This is the same broken invariant as the flashloan report: Desktop trusts an attacker-influenced value (there, an AMM swap return value; here, a JSON field from a "GitHub API object") and threads it straight into a sensitive operation without validating its shape/bounds first. In this codebase, `IAPIPullRequest.head.repo.clone_url` and `.head.repo.owner.login` come from whatever GitHub/GHES/API-compatible endpoint the account is configured against, and are used to open a PR from a URL (`x-github-client://openrepo/...&pr=NNN`, a deep link an attacker can get a victim to click) or via "Open PR in Desktop":

`dispatcher.openPullRequestFromUrl` → `appStore._checkoutPullRequest` → `appStore._findPullRequestBranch` → `addRemote(repository, forkRemoteName, headCloneUrl)`. [5](#0-4) [6](#0-5) 

`addRemote` passes `headCloneUrl` as a raw, unguarded positional argument to `git remote add`:
```ts
await git(['remote', 'add', name, url], repository.path, 'addRemote')
``` [1](#0-0) 

Contrast this with `app/src/lib/git/clone.ts`, where the equivalent user/attacker-supplied `url` is explicitly separated with `--` before being passed to `git clone`:
```ts
args.push('--', url, path)
``` [7](#0-6) 

That `--` guard is exactly the "minimum output" check missing from `remote.ts` — a defensive pattern the codebase already knows how to apply elsewhere but did not apply consistently to `addRemote`/`setRemoteURL`. If `headCloneUrl` begins with `-`, it can be parsed by `git remote add`/`git remote set-url` as an option rather than a URL (e.g. `-f` to trigger an immediate fetch with attacker-influenced settings, `--mirror=fetch`, `-t`, `-m`, etc.), corrupting the remote configuration that the app relies on for subsequent fetch/push/pull operations — silently changing what a later `git fetch`/`push` on that remote will do. `setRemoteURL` has the same gap and is also reachable from user-editable repository settings and from `updateRemoteUrl`, which itself is driven by `apiRepo.clone_url` coming straight from an API response. [8](#0-7) 

### Impact Explanation
A malicious or compromised GitHub/GHES-compatible API endpoint (or a MITM'd API/proxy response, or an attacker who opens a pull request whose head repository JSON has been crafted/relayed through a non-standard endpoint) can supply a `clone_url` value that is interpreted as a git option instead of a repository URL. Depending on which option is smuggled in, this can: silently corrupt the remote's fetch/push configuration (e.g., mirror or refspec options), or trigger an immediate `-f` fetch under attacker-chosen network conditions at add-time. This falls squarely within scope: the attacker controls a GitHub API object / fork-repository metadata that Desktop consumes without validation, and the outcome is silent corruption of repository remote configuration that later fetch/push/pull operations rely on.

### Likelihood Explanation
The reachable path requires the victim to interact with a pull request whose head repository is attacker-supplied (own a fork, or the API/proxy is attacker-controlled/GHES-hosted), and to trigger "Open PR in Desktop" or click a `x-github-client://openrepo` deep link with `pr=` set — normal, low-friction PR/deep-link interactions. `owner.login` is namespaced with the `github-desktop-` prefix before being used as a remote name, so the name argument is not exploitable, but `clone_url` is passed unmodified as the `url` positional argument in both `addRemote` and `setRemoteURL`, with no format validation and no `--` separator anywhere in `remote.ts`.

### Recommendation
- Insert a `--` separator before the URL argument in both `addRemote` and `setRemoteURL` (mirroring `clone.ts`), e.g. `['remote', 'add', '--', name, url]` / `['remote', 'set-url', '--', name, url]`.
- Additionally validate that `clone_url`/remote URLs parsed from API responses match `parseRemote()`'s expected git URL shapes before using them in any git invocation, rejecting values that don't resemble a URL (e.g., start with `-`).

### Proof of Concept
1. Attacker forks a repository and opens a PR (or serves a crafted API/proxy response for `pull_request.head.repo`) where `clone_url` is set to a value beginning with `-`, e.g. `-f`, `--mirror=fetch`, or similar.
2. Victim uses "Open PR in Desktop" or a `x-github-client://openrepo/<url>?pr=<n>` deep link pointing at that PR.
3. `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch` calls `addRemote(repository, forkRemoteName, headCloneUrl)`, which executes `git remote add github-desktop-<owner> -f` (or similar), consuming the attacker string as an option rather than a URL. [4](#0-3) [1](#0-0) 

Note: I was not able to execute git locally to confirm the exact set of `git remote add`/`set-url` options that are practically exploitable for command execution (e.g., whether `ext::`/`-f` combinations are blocked by the installed git version's default protocol allow-list). The structural bug — missing `--` separator allowing option injection via an unvalidated API-sourced URL — is confirmed directly from the source; the precise severity ceiling (config corruption vs. RCE) depends on the git version bundled with dugite and its default `protocol.*.allow` settings, which I could not verify from the index.

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
```
