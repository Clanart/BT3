### Title
Silent, unvalidated remote-URL retargeting driven by GitHub API data - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The invariant broken in the original report is "state is mutated from attacker/caller-supplied data without validating that it is safe to carry forward the value." The Desktop analog is `updateRemoteUrl()`, which automatically rewrites a repository's `origin` remote URL to whatever `clone_url` the GitHub (or GitHub Enterprise) API returns for the repository, guarded only by a same-protocol check — not a same-host/same-owner check — and without any user confirmation.

### Finding Description
`repositoryWithRefreshedGitHubRepository()` fetches the repository object from the API (`api.fetchRepository(owner, name)`) during routine background refreshes (e.g. on account change, fetch, repository selection) and passes the result straight into `updateRemoteUrl()`: [1](#0-0) 

`updateRemoteUrl()` then decides whether to call `gitStore.setRemoteURL()`, which shells out to `git remote set-url origin <url>`: [2](#0-1) 

The only checks performed before silently overwriting the remote are:
- `protocolsMatch` — compares only the URL *scheme* (`https:` vs `https:`), not hostname/owner.
- `remoteUrlUnchanged` — confirms the *current* local remote still matches the *previously cached* `cloneURL`, which is true for the overwhelming majority of untouched repositories.
- `!urlsMatch` — the new URL differs from the current remote.

None of these checks constrain the new URL to the same host, owner, or even the same GitHub instance as before. `setRemoteURL` performs the update unconditionally once these preconditions hold: [3](#0-2) 

`urlMatchesRemote`, used only to compute the "did it change" boolean, checks hostname/owner/name equality, but that result is used to decide *whether* to update, not to *validate* the new value — so a mismatch (different host) is exactly the case that triggers the silent update rather than blocking it: [4](#0-3) 

This mirrors the `BobStaking::_setStakingCondition` bug class: a setter path exists that is supposed to safely carry forward/validate prior state, but the actual write path accepts the new externally-supplied value with an insufficient guard, silently corrupting the persisted value (here, the git remote instead of a staking condition).

### Impact Explanation
Any actor who can influence the `clone_url` field returned for a repository the user has cloned (e.g. an org owner or repo admin who transfers/renames the repo to point at a different host while keeping the association intact, or a compromised/malicious GitHub Enterprise Server the account is configured against) can cause GitHub Desktop to silently retarget the user's `origin` remote to an arbitrary host with the same scheme. Because this happens during unattended background refreshes (fetch, account refresh, repository selection) rather than via the explicit "Repository Settings → Remote" UI, the user is never shown a confirmation dialog, and subsequent `git push`/`git fetch` operations — and the credentials/tokens the trampoline askpass/credential-helper supplies for `origin` — go to the attacker-controlled destination. This can result in silent corruption of what the user pushes/fetches and possible credential exfiltration, which fits the requested impact classes (silent corruption of git operations, potential credential exfiltration).

### Likelihood Explanation
Likelihood is Medium: the attacker does not need local access, admin rights on the victim's machine, or leaked credentials — only the ability to influence the API-reported repository metadata (e.g., control over a repo/org that the victim already trusts and has associated in Desktop, or control of a GHES endpoint). The trigger path (`_refreshRepository` → `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`) runs automatically as part of normal Desktop usage without any special user action beyond routine fetch/refresh, which happens continuously in the background.

### Recommendation
Restrict the automatic remote-URL update to cases where the new URL is still on the same host/endpoint as the account, and require explicit user confirmation (similar to the manual Repository Settings flow) whenever the update would move `origin` to a different hostname or owner than previously recorded, rather than silently trusting API-returned `clone_url` values based only on scheme equality.

### Proof of Concept
1. Victim has a repository in Desktop tracked as a `RepositoryWithGitHubRepository`, with `origin` pointing at `https://github.com/victim-org/victim-repo`.
2. An attacker with control over the repository record as seen by the API (e.g. org owner performing a "transfer repository" to an attacker-controlled destination while name/owner path resolution in Desktop still matches the cached association, or a malicious/compromised GHES instance) causes `api.fetchRepository(owner, name)` to return `clone_url: "https://evil.example.com/attacker/pwned.git"`.
3. On the next background refresh (`_refreshRepository`, `_fetch`, or account refresh), `repositoryWithRefreshedGitHubRepository` calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` — see [5](#0-4) .
4. Because `remoteUrlUnchanged` is true (user never manually altered `origin`) and `protocolsMatch` is true (both `https:`), `updateRemoteUrl` calls `gitStore.setRemoteURL('origin', 'https://evil.example.com/attacker/pwned.git')` with no user prompt, confirmed by the existing test asserting exactly this update-on-clone_url-change behavior: [6](#0-5) .
5. The user's next push/fetch of `origin` — and any credential supplied via the askpass/credential-helper trampoline for that operation — targets the attacker's host instead of GitHub.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
