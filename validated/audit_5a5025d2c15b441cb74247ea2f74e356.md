Confirmed: governance votes require validator/council membership (block proposer must be in `council`, and in single mode only `GoverningNode` may vote after Permissionless fork), but the `Kip71GasTarget` parameter has **no format/range validation** enforcing `GasTarget != 0`.### Title
Missing zero-check on governance-controlled `Kip71GasTarget` causes division-by-zero panic in Magma base-fee calculation - ([File: params/kip71_config.go])

### Summary
The `Kip71GasTarget` governance parameter has no format/range validation preventing it from being set to `0`. When `GasTarget == 0` and a block's gas usage is non-zero, `NextMagmaBlockBaseFee()` performs `x.Div(x, new(big.Int).SetUint64(gasTarget))`, i.e. division by zero, which panics in Go's `math/big` package. This mirrors the reported bug class of "unchecked arithmetic without bounds guarantees on a governance-settable numerator/denominator" (the `protocolFeeNumerator` under/overflow example), except here the missing bound manifests as a division-by-zero panic instead of a silent underflow.

### Finding Description
`params/kip71_config.go` computes the next block's base fee in `NextMagmaBlockBaseFee`: [1](#0-0) 

Note the defensive fallback already present for `BaseFeeDenominator`: [2](#0-1) 

There is an explicit comment `// To avoid panic, set the fluctuation range small` guarding `BaseFeeDenominator == 0`, proving the developers were aware division-by-zero is a real risk for governance-settable divisors. However, no equivalent guard exists for `gasTarget`, which is used as a divisor twice (once in the `parentGasUsed > gasTarget` branch, once in the `parentGasUsed < gasTarget` branch): [3](#0-2) [4](#0-3) 

The governance parameter definition for `Kip71GasTarget` uses `noopFormatChecker`, which accepts any `uint64` value including `0`: [5](#0-4) 

Compare this to `Kip71BaseFeeDenominator`, which does have a non-zero check: [6](#0-5) 

The header-vote consistency checker (`checkConsistency`) also does not add any extra validation for `Kip71GasTarget` — it falls into the "no more checks beyond format checks" case: [7](#0-6) 

### Impact Explanation
`NextMagmaBlockBaseFee` is invoked during header verification and block header preparation (`VerifyMagmaHeader`) for every block once Magma/KIP-71 is active, on every full node. A panic here is a process-crashing bug that stops block processing entirely on all nodes computing the base fee (i.e., a chain-wide halt), not merely a computational error confined to one transaction. This is a consensus-availability issue: a single successful governance vote setting `GasTarget=0` would deterministically crash every node once a block with non-target gas usage is processed, since the panic occurs identically on all honest nodes (this is a shared crash rather than a state-divergence issue, but it is a critical availability failure of the network).

### Likelihood Explanation
Reaching this requires only a governance vote to set `kip71.gastarget` to `0`. This is reachable by:
- The `GoverningNode` in "single" governance mode (a normal governance operation, not requiring any exploit of a smart contract or cryptographic bug), or
- Any council member vote path (before/without single-mode restriction).

No smart-contract bug, malicious peer, or privileged infrastructure access is required — only a single validly-signed governance vote transaction/header field, which is an explicitly in-scope "governance parameters" path. The `FormatChecker` for this parameter performs no validation at all (`noopFormatChecker`), so this vote will be accepted without complaint by `NewVoteData`, `PartialParamSet.Add`, and `checkConsistency`.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` that rejects `0` (mirroring the existing `Kip71BaseFeeDenominator` check), e.g.:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
}
```
Additionally, as defense-in-depth, add the same "avoid panic" fallback used for `BaseFeeDenominator` directly inside `NextMagmaBlockBaseFee` for `gasTarget == 0`, so that even a pre-existing chain config (e.g., from genesis or an already-accepted historical vote) cannot crash node software.

### Proof of Concept
1. Governance council (or `GoverningNode` in single mode) casts a vote to set `kip71.gastarget = 0` via the standard header-vote mechanism (`headerGovModule.Vote`/`PrepareHeader`).
2. The vote passes `NewVoteData`'s `FormatChecker` (`noopFormatChecker` always returns `true`) and `checkConsistency` (no special-case check for `Kip71GasTarget`), so it is accepted and applied at the next epoch governance boundary via `ParamSet.GasTarget = 0` → `ToKip71Config()`. [8](#0-7) 
3. On the next block after activation where `header.GasUsed != 0`, `VerifyMagmaHeader`/`NextMagmaBlockBaseFee` is invoked with `parentHeaderGasUsed > 0` and `gasTarget = 0`:
   - `parentGasUsed := min(parentHeaderGasUsed, upperGasLimit)` will be `> 0` (assuming `upperGasLimit` unaffected),
   - since `parentGasUsed > gasTarget (0)`, execution enters the branch at line 92,
   - `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` divides by `big.NewInt(0)`, which panics with `division by zero` in Go's `math/big`.
4. This panic occurs identically on every node that processes/verifies this block header, crashing block processing network-wide.
