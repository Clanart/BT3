### Title
Attacker-controllable AssertionError crash in singleton fast-forward mempool processing during block building - ([File: chia/full_node/eligible_coin_spends.py])

### Summary
An unprivileged spend-bundle submitter can craft a spend bundle containing a coin spend that the mempool marks as eligible for fast-forward (FF), then wait for it to be admitted and cached in the mempool as a `MempoolItem`/`InternalMempoolItem`. When the full node later builds a block generator from mempool contents (`create_bundle_from_mempool_items` → `SingletonFastForward.process_fast_forward_spends`), the code hits `assert spend_data.latest_singleton_lineage is not None` [1](#0-0)  without a corresponding fallback path if this invariant is ever violated for a cached item. This mirrors the PowerDNS pattern: crafted records get cached first, and a later, differently-shaped operation (block assembly, analogous to the `ANY` query) triggers an assertion failure that can crash/halt transaction processing — a denial of service.

### Finding Description
The mempool's fast-forward (FF) mechanism lets a spend bundle targeting a singleton coin be "rebased" onto the latest unspent version of that singleton at block-building time, rather than being rejected as a double-spend [2](#0-1) . During admission (`validate_spend_bundle`), FF eligibility is determined and `get_unspent_lineage_info_for_puzzle_hash` is queried to populate `BundleCoinSpend.latest_singleton_lineage`, which is cached in the mempool as part of the `InternalMempoolItem` [3](#0-2) .

Later, at block-building time, `SingletonFastForward.process_fast_forward_spends()` iterates over the cached `bundle_coin_spends` and, for any entry with `supports_fast_forward=True`, unconditionally asserts that `latest_singleton_lineage` is populated: [4](#0-3) 

This is a hard Python `assert`, not a recoverable `ValueError`/`Err` return (unlike the neighboring `perform_the_fast_forward()`, which explicitly avoids asserting on "reachable input" and instead raises `ValueError` for a very similar amount-mismatch scenario, because the value can legitimately change between admission and block-building) [5](#0-4) . The comment in `perform_the_fast_forward` explicitly acknowledges that state between admission time and block-building time can diverge and that such divergence must be handled with a raised, catchable error rather than an assertion, because it is "reachable input." The `assert spend_data.latest_singleton_lineage is not None` check does not receive the same treatment: if `latest_singleton_lineage` is ever `None` for an item that is marked `supports_fast_forward=True` by the time block-building runs (for example, due to the two-step cache/consume timing gap between admission-time lineage-info lookup and eventual block-building re-use of the cached `InternalMempoolItem`, or due to an FF item whose lineage lookup legitimately returns `None` and is not otherwise excluded from the block-building set), the assertion fails.

Since Python `assert` statements raise `AssertionError`, and this occurs inside the synchronous block-building path called from the full node's peer-facing task, an uncaught `AssertionError` here would propagate up through `create_bundle_from_mempool_items` / `create_block_generator2` used during block farming/creation, which is a core, non-optional path for turning mempool contents into blocks. If it isn't wrapped in exception handling higher up the call stack, this can crash the full node process or otherwise halt block/transaction assembly — a spend-triggered transaction-processing halt, matching the reachable-DoS pattern described in the CVE (crafted data first cached, then a specific follow-on operation flips an internal invariant check into a crash).

### Impact Explanation
If reachable, this is a Medium-severity availability issue: a single attacker-controlled spend bundle, once cached in the mempool, can cause an `AssertionError` during block generator construction, which is executed by every full node building blocks from mempool contents. This does not permit fund theft, forged assets, or coin-set divergence between honest nodes on its own, but it does align with the CVE's "spend-triggered transaction-processing halt" impact category — repeated exploitation could degrade full node availability/mempool processing service.

### Likelihood Explanation
The likelihood of hitting this exact assertion depends on precisely how `supports_fast_forward` and `latest_singleton_lineage` are populated and kept in sync between admission and block-building, which I could not fully trace to a concrete reachable trigger within the available tool budget. Full node code that computes `latest_singleton_lineage` at admission for every FF-eligible coin was located, and the assumption embedded in the `process_fast_forward_spends` code (that this field is always non-`None` for `supports_fast_forward=True` items) is not defensively re-verified before block-building, unlike its sibling function `perform_the_fast_forward`, which explicitly documents and handles the same class of stale-cache-vs-current-state divergence via a raised (catchable) `ValueError` rather than an `assert`. This asymmetry in defensive coding between two adjacent functions in the same file is the strongest concrete signal supporting a real, though not fully proven, risk.

### Recommendation
Replace the bare `assert spend_data.latest_singleton_lineage is not None` in `SingletonFastForward.process_fast_forward_spends()` with an explicit, catchable check (e.g., raising `ValueError` and skipping/evicting the offending mempool item), consistent with the handling already used in `perform_the_fast_forward()` for the analogous "state advanced between admission and block-building" scenario. Additionally, audit all call sites that populate and later consume `BundleCoinSpend.latest_singleton_lineage` to guarantee the invariant truly always holds for cached mempool items, or add re-validation immediately before block-building consumes cached lineage data.

### Proof of Concept
I was not able to construct or confirm a concrete, end-to-end reproduction path (i.e., a specific sequence of admission-time and block-building-time states that leaves `latest_singleton_lineage` as `None` for a `supports_fast_forward=True` cached item) within the available investigation budget — this would require deeper tracing of `validate_spend_bundle`'s FF-eligibility/lineage-lookup logic and the `new_peak`/reorg re-validation paths that could re-populate mempool items. This is flagged as an uncertainty: further investigation (ideally with a running Devin session with full repo/test access) is needed to confirm whether the invariant can actually be violated by attacker-controlled input, or whether upstream admission logic always guarantees it cannot occur, in which case this would be a defense-in-depth/robustness recommendation rather than an exploitable vulnerability.
