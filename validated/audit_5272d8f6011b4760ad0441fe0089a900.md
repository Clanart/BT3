Based on the code I was able to examine, I found a strong Agave analog to the PoolTogether "missing check when transferring tokens out for a given promotion" bug class: a per-recipient reward amount is computed and clamped individually, but nothing checks that the sum of amounts paid out across all recipients stays within the shared pool total.

### Title
Per-Delegator Block Reward Calculation Lacks Aggregate Cap Against Vote Account's `pending_delegator_rewards` Pool - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
`calculate_block_reward` computes each stake delegator's share of a vote account's `pending_delegator_rewards` pool using `stake / total_active_stake`, and the code's own comment acknowledges that during recalculation `stake` can exceed `total_active_stake`, and that "individual rewards look greater than the pending rewards." The function clamps each *individual* reward to the vote account's total `pending_delegator_rewards`, but there is no check that the *sum* of rewards paid to all delegators of that vote account stays within the single shared `pending_delegator_rewards` amount, mirroring the PoolTogether flaw where per-claim calculations were not bounded by the total pool allocated by the promotion creator.

### Finding Description
`calculate_block_reward` in [1](#0-0)  computes, for each stake delegation to a vote account:

```
(pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
    .try_into()
    .unwrap_or(u64::MAX)
    .min(pending_delegator_rewards)
```

`pending_delegator_rewards` is read from the vote account's state (a single, shared pool value representing rewards to be distributed to all its delegators) via `vote_state.pending_delegator_rewards()`. The clamp `.min(pending_delegator_rewards)` only bounds a *single* delegator's computed reward to the full pool — it does nothing to bound the sum across the potentially many delegators of the same vote account. The comment directly above explicitly acknowledges the abnormal case: "if stake account has already received rewards, it's possible to have `stake > total_active_stake`" and "individual rewards look greater than the pending rewards," dismissing it as "harmless in practice." This function is invoked once per stake delegation inside a parallel iterator in `calculate_stake_rewards_and_commissions` [2](#0-1) , so each delegator's block reward is computed independently, with no running total tracked against `pending_delegator_rewards` for that vote account across delegators.

The only aggregate sanity check present is the `assert!` in `distribute_reward_commissions` [3](#0-2) , which checks `point_value.rewards >= distributed_lamports + distributed_to_incinerator_lamports + burned_lamports + total_stake_rewards_lamports`. This validates against the epoch's total inflation `point_value.rewards`, not against each individual vote account's `pending_delegator_rewards` pool. Nothing sums per-vote-account block rewards across delegators and compares that sum to the vote account's own `pending_delegator_rewards`, so an aggregate overpay condition specific to a single vote account's pool (analogous to a single "promotion" being over-claimed in the PoolTogether report) would not be caught by this global assertion.

### Impact Explanation
If aggregate block rewards paid to the delegators of one vote account exceed that vote account's `pending_delegator_rewards`, lamports are minted/distributed beyond what was actually allocated for that vote account's rewards pool, corrupting `distributed_lamports`/`stake_reward_lamports_minted` totals used to update bank `capitalization` [4](#0-3) . This would cause an incorrect capitalization increase (false acceptance of an inflated reward amount), a state divergence between validators that recompute rewards differently, and directly matches "false execution/rooting/acceptance" and "fund theft/loss" impact categories, since delegators would receive lamports never actually backed by the vote account's pool.

### Likelihood Explanation
Likelihood depends on whether `stake > total_active_stake` (the condition the code comment flags) can actually be reached across multiple delegators simultaneously during "recalculation," which the comment states is possible but claims is "harmless in practice." I was not able to fully verify, within the remaining tool budget, whether `total_active_stake` is guaranteed to always equal the true sum of all delegators' `stake` at calculation time, or whether some other invariant elsewhere in the reward-recalculation path (not found in the snippets reviewed) prevents the aggregate overpay. This is the key open question that would need further investigation (e.g., tracing `reward_epoch_delegated_stakes.delegated_stakes` population and the "recalculation" code path) to confirm exploitability versus the developers' "harmless in practice" claim.

### Recommendation
Track a running total of block rewards paid out per vote account across all its delegators during `calculate_stake_rewards_and_commissions`, and clamp/cap that aggregate to the vote account's `pending_delegator_rewards`, rather than only clamping each individual delegator's share. This mirrors the PoolTogether report's recommended mitigation of checking that cumulative claims against a shared pool never exceed the pool's total allocation.

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}

    /// Returns DistributionResults containing the sum of all the rewards
    /// stored, the sum of all rewards burned, and the updated StakeRewards.
    /// Because stake accounts are checked in calculation, and further state
    /// mutation prevents by stake-program restrictions, there should never be
    /// rewards burned.
    ///
    /// Note: even if staker's reward is 0, the stake account still needs to be
    /// stored because credits observed has changed
    fn store_stake_accounts_in_partition(
        &self,
        partition_rewards: &StartBlockHeightAndPartitionedRewards,
        partition_index: u64,
    ) -> DistributionResults {
        let feature_snapshot = self.feature_set.snapshot();
        // Name intentionally doesn't match -- "adjust delegations for rent" is
        // part of relaxing post-exec min balance checks.
        let adjust_delegations_for_rent = feature_snapshot.relax_post_exec_min_balance_check;
        let use_fixed_point_stake_math = feature_snapshot.upgrade_bpf_stake_program_to_v5_1;

        let mut stake_reward_lamports_minted = 0;
        let mut stake_reward_lamports_burned = 0;
        let mut block_reward_lamports_distributed = 0;
        let mut block_reward_lamports_burned = 0;
        let indices = partition_rewards
            .partition_indices
            .get(partition_index as usize)
            .unwrap_or_else(|| {
                panic!(
                    "partition index out of bound: {partition_index} >= {}",
                    partition_rewards.partition_indices.len()
                )
            });
        let mut updated_stake_rewards = Vec::with_capacity(indices.len());
        let stakes_cache = self.stakes_cache.stakes();
        let stakes_cache_accounts = stakes_cache.stake_delegations();
        let stake_history = stakes_cache.history();
        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        let rent = &self.rent_collector.rent;
        for index in indices {
            let partitioned_stake_reward = partition_rewards
                .all_stake_rewards
                .get(*index)
                .unwrap_or_else(|| {
                    panic!(
                        "partition reward out of bound: {index} >= {}",
                        partition_rewards.all_stake_rewards.total_len()
                    )
                })
                .as_ref()
                .unwrap_or_else(|| {
                    panic!("partition reward {index} is empty");
                });
            let stake_pubkey = partitioned_stake_reward.stake_pubkey;
            let stake_reward_amount = partitioned_stake_reward.inflation.stake_reward;
            let block_reward_amount = partitioned_stake_reward.block_reward;

            match Self::build_updated_stake_reward(
                self.epoch,
                stake_history,
                new_warmup_cooldown_rate_epoch,
                stakes_cache_accounts,
                partitioned_stake_reward,
                rent,
                adjust_delegations_for_rent,
                use_fixed_point_stake_math,
            ) {
                Ok(stake_reward) => {
                    stake_reward_lamports_minted += stake_reward_amount;
                    block_reward_lamports_distributed += block_reward_amount;
                    updated_stake_rewards.push(stake_reward);
                }
                Err(err) => {
                    error!(
                        "bank::distribution::store_stake_accounts_in_partition() failed for \
                         {stake_pubkey}, {stake_reward_amount} lamports burned: {err:?}"
                    );
                    stake_reward_lamports_burned += stake_reward_amount;
                    block_reward_lamports_burned += block_reward_amount;
                }
            }
        }
        drop(stakes_cache);
        self.store_accounts(
            (self.slot(), &updated_stake_rewards[..]),
            // Reuse the rewards calculation thread pool to parallelize
            // loading the previous versions of the stake accounts.
            Some(crate::bank::rewards_calculation_thread_pool()),
        );
        DistributionResults {
            stake_reward_lamports_minted,
            stake_reward_lamports_burned,
            block_reward_lamports_distributed,
            block_reward_lamports_burned,
            updated_stake_rewards,
        }
    }
}
