### Title
Partial-commit line selection is applied against a freshly re-fetched diff instead of the diff it was made against, allowing silent corruption of committed content - (File: `app/src/lib/git/apply.ts`)

### Summary
Github Desktop's partial-commit (line/hunk staging) feature stores the user's selection as a set of raw, positional line indices (`DiffSelection`), completely decoupled from the diff content it was originally computed against. When a partial commit is executed, `applyPatchToIndex` re-fetches a brand-new diff from disk and blindly re-applies the old positional selection to it. If the working-tree file content shifts between the time the user made the selection (in the UI) and the time the commit actually runs `git apply`, the selected line indices silently map onto different, unintended lines — producing a commit whose content does not match what the user visually selected, without any error being raised.

### Finding Description
`DiffSelection` (`app/src/models/diff/diff-selection.ts:41-136`) is a pure, generic "set of line indices" structure with no binding to a particular diff snapshot: [1](#0-0) 

`isSelected(lineIndex)` only looks at whether an absolute index is in `divergingLines` — it has no concept of which diff (or which file content/hash) produced that index: [2](#0-1) 

When the user actually commits, `stageFiles` routes any file with a partial selection to `applyPatchToIndex`: [3](#0-2) 

`applyPatchToIndex` does **not** reuse the diff that was rendered in the UI when the user made the selection. Instead it independently re-fetches the diff at commit time: [4](#0-3) 

`formatPatch` then walks the hunks/lines of this newly-fetched diff and calls `file.selection.isSelected(absoluteIndex)` on each line to decide what to include in the generated patch: [5](#0-4) 

There is a partial mitigation in `app-store.ts` (`updateChangesWorkingDirectoryDiff`), which recomputes `selectableLines` when the UI refreshes the diff after a status poll: [6](#0-5) 

but this reconciliation only prunes lines that no longer exist in the newer diff — it does not re-verify that the remaining selected indices still point at the *same logical content* the user intended, and more importantly it is not guaranteed to run synchronously right before `stageFiles`/`applyPatchToIndex` actually executes `git apply`. `applyPatchToIndex` performs its own independent, unconditional re-diff at staging time regardless of any reconciliation the UI store did.

The broken invariant is the same class as the 0x report: an operation (`fillOrder` / `applyPatchToIndex`) is executed against a precomputed selection/amount that is assumed to still be valid, but the underlying state (order book liquidity / working-tree file content) can have changed by the time the operation actually runs, and there is no atomic check binding the "intent" (selection) to the "state" (diff) it was computed from. In 0x this causes reverts with no clear cause; in Desktop it can instead cause the operation to *succeed* against the wrong lines, silently corrupting what gets committed.

### Impact Explanation
If the working-tree file for the file being partially committed changes between the point the user made the line selection and the point `applyPatchToIndex` re-diffs, the positional indices in `DiffSelection` will select different content than what the user saw and intended to include/exclude. This is a "silent corruption of what the user commits" scenario: the resulting commit can include content the user explicitly deselected, or omit content the user explicitly selected, with no error surfaced (the `git apply` call will simply succeed against the new, valid diff). This directly matches the report's core theme — the app has no reliable way to guarantee that the "fillable" operation (partial staging) still corresponds to the state it was validated against, and there is no user-facing signal when that assumption is violated.

### Likelihood Explanation
The window between selection and staging is not attacker-controllable via direct filesystem access, but content in a cloned/fetched repository can trigger asynchronous mutation of tracked files through repo-defined mechanisms such as `.gitattributes` clean/smudge filters, Git LFS pointer smudging, or checkout/merge hooks that a malicious repository can ship (hooks paths, LFS config, filter scripts are all repository content an attacker can control when a victim clones/fetches). Combined with normal UI latency (diff rendering, user interaction time before committing), this creates a realistic race window for a crafted repository to influence file content underneath an in-progress partial selection. This is a moderate-likelihood, state-desynchronization bug rather than a trivially reproducible one-shot exploit, since it depends on timing and on the working file actually changing during that window.

### Recommendation
- Bind `DiffSelection` (or the `WorkingDirectoryFileChange`) to the diff it was computed from (e.g., store a content hash/blob OID or the diff object itself), and have `applyPatchToIndex`/`formatPatch` refuse to apply a selection whose bound diff no longer matches the freshly-fetched diff, surfacing an explicit error/re-prompt instead of silently re-mapping indices.
- Alternatively, have `applyPatchToIndex` reuse the exact diff object the UI last displayed/validated for that selection rather than independently re-fetching a new diff at staging time, and only fall back to a fresh diff (with explicit invalidation of the selection) if none is available.
- Add integration tests that mutate the working tree between diff generation and `applyPatchToIndex` invocation to confirm the operation either fails loudly or re-validates the selection, rather than silently committing mismatched content.

### Proof of Concept
1. In a repository, create a file with a modification hunk and open it in Desktop's changes view; the app computes a diff (`getWorkingDirectoryDiff`) and the user selects a specific line for partial staging (`DiffSelection` records absolute index `N`).
2. Before the user clicks "Commit", trigger an asynchronous modification of that same file's content that shifts line numbers (e.g., simulate what a malicious repo's Git LFS `smudge` filter or a `post-checkout`/background formatter hook could do) — inserting/removing lines above index `N`.
3. Click "Commit". `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches the diff via `getWorkingDirectoryDiff`, producing new hunks/line layout.
4. `formatPatch` (`app/src/lib/patch-formatter.ts:143-161`) evaluates `file.selection.isSelected(absoluteIndex)` against the *new* hunk layout using the *old* index `N`, which now corresponds to a different line.
5. `git apply --cached` succeeds because the generated patch is internally consistent with the new diff, but the actually committed content differs from what the user saw and selected — no error is shown to the user.

  /** Returns a value indicating wether the given line number is selected or not */
  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
