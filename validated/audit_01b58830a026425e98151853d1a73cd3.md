### Title
Quadratic Lagrange interpolation in `ThresholdKeys::new`/`ThresholdView::view` allows CPU exhaustion from crafted `ThresholdKeys` bytes - (File: crypto/dkg/src/lib.rs)

### Summary
The Zulip CVE-2019-16215 class — a small attacker-controlled input causing disproportionate CPU consumption — maps onto Serai's threshold-key deserialization. `ThresholdKeys::read` lets the caller specify `t` and `n` up to `u16::MAX` (65535) and then calls `ThresholdKeys::new`, which computes the group key by evaluating `interpolation_factor` for each of the `t` participants. Under `Interpolation::Lagrange`, each `interpolation_factor` call iterates over the entire included set, making the computation `O(t²)` scalar multiplications plus `t` field inversions — triggered by a serialized object only ~2–4 MB in size. The same quadratic pattern exists in `ThresholdView::view`, which recomputes `interpolation_factor` for every included signer on every signing attempt.

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, the participant index, the interpolation mode, a secret share, and `n` verification shares, then invokes `ThresholdKeys::new` [1](#0-0) . `new` derives `group_key` as the sum over `i in 1..=t` of `verification_shares[i] * interpolation_factor(i, &t)` [2](#0-1) . For `Interpolation::Lagrange`, `interpolation_factor` loops over every element of `included`, performing two scalar multiplications per element and one inversion per call [3](#0-2) . The parameters are only sanity-checked against zero and `t <= n` — both `t` and `n` are free to be `u16::MAX` [4](#0-3) . The only bound on work is `n` encoded points in the input, which costs the attacker ~33–64 bytes each.

`ThresholdView::view` repeats the same pattern per signing set: it computes `interpolation_factor` once for the secret share and once per included signer [5](#0-4) , and `ThresholdView::interpolation_factor` is itself a public `O(|included|)` re-computation [6](#0-5) .

### Impact Explanation
With `t = n = 65535`, a single `ThresholdKeys::read` performs roughly `65535 × 65535 ≈ 4.3 × 10^9` scalar multiplications plus 65535 field inversions during `group_key` derivation. Each additional `view()` call over the full participant set costs another `O(n²)`. An unprivileged party who can get a node to deserialize attacker-chosen `ThresholdKeys` bytes (e.g., submitted keys, recovery payloads, or any protocol message carrying serialized `ThresholdKeys`/`ThresholdParams`) can stall the process for an effectively arbitrary amount of CPU time, mirroring the availability loss of CVE-2019-16215: a ~4 MB message yields billions of field operations, and repeated submissions multiply the stall linearly for the attacker at negligible cost.

### Likelihood Explanation
Exploitability requires a reachable path where `ThresholdKeys::read` (or a `ThresholdParams` with large `n` driving `view()`) processes bytes influenced by an untrusted party. The deserialization is unauthenticated and self-describing — `t`/`n` come straight from the byte stream [7](#0-6)  — so no special privileges or secret knowledge are needed to construct the input. Since there is no protocol-level bound on `n` enforced in `ThresholdParams::new` beyond `u16`, any integration that accepts serialized keys from less-trusted peers is exposed. This is a resource-exhaustion issue only; no key material or forgery results, consistent with a Medium rating.

### Recommendation
- Enforce a practical maximum on `n`/`t` in `ThresholdParams::new` (e.g., a few hundred participants), so deserialized parameters cannot request quadratic work beyond realistic multisig sizes.
- Compute all Lagrange interpolation factors in `O(t)` total using prefix/suffix products of `(x_j)` and `(x_j - x_i)` terms plus a single batched inversion (Montgomery's trick), instead of the current per-participant `O(t)` loop in `Interpolation::interpolation_factor` [8](#0-7) .
- Cache computed factors inside `ThresholdView` rather than recomputing them per call in `ThresholdView::interpolation_factor` [6](#0-5) .

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }
