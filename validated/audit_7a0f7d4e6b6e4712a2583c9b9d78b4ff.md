### Title
Output-token duplicate check compares raw `bytes32` identifiers while all downstream logic uses truncated addresses, allowing token aliasing to defeat the "one leg per token" invariant - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
The external report describes how `rageQuit()` in Party Protocol failed because it deduplicated a token withdrawal list by comparing token *addresses*, but a single logical token can have more than one valid address ("double-entry" tokens like the original TrueUSD), letting an attacker submit both addresses to withdraw the same underlying balance twice. Hyperbridge's `IntentGatewayV2` has the same class of bug, but the aliasing is internal to its own encoding rather than coming from an external token contract: the duplicate-output-token guard checks the raw `bytes32` value stored in `order.output.assets[i].token`, while every consumer of that field (escrow accounting, fee/dust sweeping, `_execute`) truncates it to an `address` before using it as the token identity.

### Finding Description
In `placeOrder`, the anti-duplicate guard for output legs operates on the untouched `bytes32`: [1](#0-0) 

```solidity
bytes32 token = order.output.assets[i].token;
assembly ("memory-safe") {
    if tload(token) { ... revert ... }
    tstore(token, 1)
}
```

This keys the transient-storage dedup slot on the full 32-byte value of `token`. However, everywhere the same field is subsequently consumed as a *token identity* — for escrow release, dust sweeping, and general execution — it is truncated to the lower 160 bits first: [2](#0-1) [3](#0-2) 

```solidity
address token = address(uint160(uint256(body.tokens[i].token)));
...
address token = address(uint160(uint256(order.output.assets[i].token)));
```

Because `bytes32(uint256(uint160(addr)))` only occupies the low 160 bits, an attacker can freely set the unused upper 96 bits of `token` to any nonzero value and still have it resolve to exactly the same ERC20 contract once truncated. Two output legs — `bytes32(uint256(uint160(dai)))` and `bytes32(uint256(uint160(dai)) | (uint256(1) << 200))` — are treated as *distinct* tokens by the `tload`/`tstore` guard (different raw values → no revert), yet both truncate to the identical `dai` address in every downstream function that actually moves or accounts for funds. This is the exact structural analog of the C4 report: the guard checks "identity" at one granularity (full 32-byte value / distinct on-chain address in the original bug) while the real balance-moving logic operates at a coarser granularity (the truncated 160-bit address / the shared underlying balance in the original bug), so a single physical balance can be represented as more than one "distinct" entry that passes the guard.

By contrast, the input-side dedup performed a few lines later in the same file correctly truncates *before* comparing: [4](#0-3) 

```solidity
address token = address(uint160(uint256(order.inputs[i].token)));
// Reject duplicate input tokens
if (_orders[commitment][token] != 0) revert InvalidInput();
```

This asymmetry — truncate-then-check on the input path, check-then-truncate on the output path — confirms the output guard is the defective one; it was clearly intended to enforce the same "one leg per real token" invariant that the tests explicitly document for outputs (`testRevert_PlaceOrder_DuplicateOutputTokens`, "shares one `_partialFills` bucket"), but the implementation does not achieve it once bit-level aliasing is introduced in the `bytes32` encoding.

### Impact Explanation
Per-token accounting throughout the intents flow (partial-fill bucketing, per-leg escrow release amounts, dust/fee sweeping in `_execute`) assumes that each output leg maps to a unique real token, which is exactly what the duplicate-output check is supposed to guarantee before the order commitment is even computed. An order crafted with two aliased-but-"distinct" output legs for the same real ERC20 bypasses that guarantee: both legs become part of the signed/committed order (the commitment is `keccak256(abi.encode(order))`, so the raw, un-normalized `bytes32` values are baked in), but any logic that resolves the real token address (release amounts, dust computation, `_execute`'s sweep) will collapse both legs onto one physical balance. This can manipulate expected output amounts, cause a single real token transfer to be miscredited across two logical legs, or let one leg's fulfillment requirement go unverified while still being marked filled — a direct transaction-manipulation / wrong-beneficiary-or-amount outcome on the intent settlement path, which is explicitly in-scope impact.

### Likelihood Explanation
This is fully reachable by an unprivileged order creator calling the public `placeOrder` entry point with a self-crafted `Order` struct — no relayer, prover, or admin involvement is required, matching the requirement that the path be attacker-controlled and public. The only requirement is basic knowledge of the `bytes32(uint256(uint160(address)))` encoding used throughout the contract, which is documented in the codebase itself.

### Recommendation
Normalize `order.output.assets[i].token` (and `order.inputs[i].token`, for defense in depth) to its truncated `address` form *before* using it as the dedup key in the `tload`/`tstore` guard in `placeOrder`, mirroring the truncate-then-compare pattern already used for input tokens at `IntentsBase.sol` around escrow crediting. Optionally, also enforce that the upper 96 bits of any `bytes32` token field are zero when decoding an `Order`, rejecting the aliasing vector at the input-validation layer entirely.

### Proof of Concept
1. Attacker builds `order.output.assets` with two entries:
   - `assets[0].token = bytes32(uint256(uint160(address(dai))))`
   - `assets[1].token = bytes32(uint256(uint160(address(dai))) | (uint256(1) << 200))`
2. Calls `intentGateway.placeOrder(order, graffiti)`.
3. The duplicate-output-token loop at `evm/src/apps/IntentGatewayV2.sol:165-179` computes `tload`/`tstore` on the two distinct raw `bytes32` values — no revert occurs, unlike `testRevert_PlaceOrder_DuplicateOutputTokens`, which only catches byte-for-byte identical entries.
4. The order commitment is computed and escrow/fulfillment proceeds with two "distinct" legs that any downstream `address(uint160(uint256(token)))` conversion (escrow release in `IntentsBase.sol:396`, sweep in `IntentsBase.sol:448`) resolves to the same `dai` contract, breaking the one-leg-per-token invariant the guard was meant to enforce.
