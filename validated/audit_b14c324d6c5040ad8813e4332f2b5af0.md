### Title
Aggregator gRPC server drops all client-certificate authentication when `client_verification = false`, allowing unauthenticated calls including `SendMoveToVaultTx` - ([File: core/src/servers.rs])

### Summary
`create_grpc_server` in `core/src/servers.rs` selects `Interceptors::Noop` instead of `OnlyAggregatorAndSelf` whenever `config.client_verification` is `false`, and simultaneously omits `.client_ca_root(...)` from the `ServerTlsConfig`, so the TLS layer never requests or verifies a client certificate at all. Because `create_aggregator_grpc_server` passes the aggregator's own `config` straight into `create_grpc_server`, an aggregator deployed with `client_verification = false` accepts gRPC calls, including `ClementineAggregator::send_move_to_vault_tx`, from any peer that can complete a plain (server-authenticated-only) TLS handshake, with no notion of `aggregator_cert` at all.

### Finding Description
The binding claimed by the caller ("caller reaching a bridge-UTXO-spending method == caller holding `aggregator_cert`") is enforced only by the `Interceptors::OnlyAggregatorAndSelf` variant, which compares the TLS leaf certificate against `aggregator_cert`/`our_cert`: [1](#0-0) [2](#0-1) 

`create_grpc_server` chooses between this interceptor and `Interceptors::Noop` purely based on `config.client_verification`: [3](#0-2) 

When `client_verification` is `false`:
- `ServerTlsConfig` is built with only `.identity(server_identity)` — no `.client_ca_root(...)` — so the TLS handshake never requires or validates a client certificate.
- The service is wrapped in `Interceptors::Noop`, whose `call` implementation returns `Ok(req)` unconditionally for every request: [4](#0-3) 

`create_aggregator_grpc_server` passes the aggregator's own `config` into this same `create_grpc_server` path used for verifier/operator servers, with no aggregator-specific override beyond a warning log when verification is *enabled*: [5](#0-4) 

So with `client_verification = false`, both the transport (TLS) and application (interceptor) layers impose zero identity requirement on any caller of the aggregator's gRPC surface, including `send_move_to_vault_tx`, which is exposed under `ClementineAggregatorServer`. This confirms the equality "caller reaching the method == caller holding `aggregator_cert`" is broken: the method is reachable by *any* caller with network access to the port, holding no certificate whatsoever.

Note: I was not able to retrieve, within the available tool budget, the body of `ClementineAggregator::send_move_to_vault_tx` in `core/src/rpc/aggregator.rs` nor `insert_try_to_send`/`TransactionType::MoveToVault` handling in the tx-sender crate, so I cannot confirm from source whether `insert_try_to_send` performs any additional on-chain signature/validity check on the supplied `raw_tx` before queuing it, or whether the queued transaction would actually be rejected by Bitcoin consensus at broadcast time due to missing a valid N-of-N witness for the deposit's Taproot script. That later-stage validation (or lack thereof) determines whether this unauthenticated reachability translates into an actual unauthorized bridge-UTXO spend (Critical) versus merely an unauthenticated state-changing/broadcasting call that queues a tx which would still fail against the real UTXO's script (High, since Bitcoin's own script validation would reject a witness the attacker cannot forge without the N-of-N keys).

### Impact Explanation
Confirmed: any unauthenticated network peer can invoke gRPC methods on an aggregator deployed with `client_verification = false`, including `send_move_to_vault_tx`, and have that request routed to the aggregator's tx-queuing logic without any certificate check. This unambiguously satisfies the accepted High category "an unauthenticated state-changing or broadcasting call." Whether it rises to Critical (actual BTC leaving a move-to-vault UTXO without a matching fronted withdrawal) depends on downstream signature validation of `raw_tx` that I could not verify in this pass — the move-to-vault UTXO is protected by an N-of-N Taproot script, and an attacker without verifier key shares cannot forge a valid witness for it, so a plainly attacker-crafted `raw_tx` would be rejected by Bitcoin's own consensus rules regardless of whether the aggregator queued it.

### Likelihood Explanation
This requires the aggregator operator to have deployed with `client_verification = false`, which the question states is a "documented" configuration option (the code explicitly supports and logs a warning only for the opposite case — enabling verification — implying `false` is a plausible/legitimate deployment mode, not merely a test artifact). Given that precondition, the attack costs nothing beyond opening a TCP/TLS connection to the aggregator's public port; no BTC, deposit, or withdrawal is strictly required to reach the endpoint, though a resulting `raw_tx` would still need a genuinely valid N-of-N witness to succeed on-chain.

### Recommendation
Do not allow `client_verification = false` to also disable the interceptor-level identity check for the aggregator's own inbound gRPC server; at minimum, methods that reach bridge-UTXO-spending logic (e.g., `SendMoveToVaultTx`) should enforce caller identity independent of the global TLS `client_verification` toggle, or `client_verification = false` should be restricted to non-production/test builds only (e.g., gated behind `#[cfg(test)]` as the certificate-bootstrapping code already is).

fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}
