### Title
Unbounded, unweighted-by-time VWAPOracle spread accumulator lets a single self-fill permanently dominate the cross-chain pricing signal - ([File: evm/src/utils/VWAPOracle.sol])

### Summary
`VWAPOracle` maintains a lifetime-cumulative volume-weighted spread per `(sourceChain, token)` pair with no decay, no cap, and no minimum sample-size gate. `IntentGatewayV2.fillOrder` calls `recordSpread` after every fill, unconditionally, for whoever calls `fillOrder` — including the order's own placer acting as solver. A single attacker-controlled self-fill with a large normalized volume permanently dominates `weightedSpreadSum / totalVolume` for that token/chain pair, exactly mirroring the external report's core primitive: one skewed/extreme data point overwhelming a weighted aggregate so that all subsequent genuine data points "contribute negligibly to the final result."

### Finding Description
`VWAPOracle` tracks, per `(sourceChainHash, inputToken)`, a `CumulativeSpreadData` struct: [1](#0-0) 

`recordSpread` is called automatically at the end of every `fillOrder`, for both same-chain and cross-chain fills, with no restriction preventing the order's placer from also being the solver that fills it: [2](#0-1) 

Inside `recordSpread`, the spread for the fill is computed from normalized input/output amounts and then folded into the running total with no bound, no decay window, and no minimum-fill-count gate before the value is trusted: [3](#0-2) [4](#0-3) 

The externally-readable `spread()` view simply divides the all-time running sums: [5](#0-4) 

`fillOrder` is a fully public entry point, callable by any address, with no requirement that the filler differ from the order's placer when `solverSelection` is disabled (the default in most tests/configs): [6](#0-5) 

Because the oracle is documented as tracking "same-token swaps" (`VWAPOracle` only supports input token == output token), an attacker can place an order for a large amount of a token and immediately fill it themselves, paying only gas/protocol-fee/relayer-fee overhead (no directional market loss since input and output are the same asset), while injecting an arbitrarily large `weightedSpread`/`volume` pair. The test suite itself demonstrates that a single large fill's spread permanently swamps the running average and cannot be diluted by many subsequent smaller genuine fills unless they collectively exceed the attacker's injected volume: [7](#0-6) [8](#0-7) 

This is the precise local analog of the external report: in the C4 finding, a flash-loan-skewed pool reserve made one pair's `currentLiquidityEvaluation` dominate a weighted oracle aggregate, drowning out all other pairs. Here, one attacker-controlled, self-funded fill dominates `totalVolume`/`weightedSpreadSum` for a `(sourceChain, token)` key, drowning out all future genuine solver fills for that pair — indefinitely, since there is no time decay, no volume cap, no per-epoch reset, and `recordSpread` never bounds `spreadBps` or `weightedSpread` magnitude (only `testMaxSpread`/`testMinSpread` clamp the per-fill *bps* to ±10000, but the *volume weight* itself is unbounded).

### Impact Explanation
`VWAPOracle.spread()` is the on-chain, canonical execution-quality/price-spread signal for a given source-chain token as observed through the Intent Gateway. Because the update path (`recordSpread`) has no floor on sample count, no decay, and no cap on the weight a single fill can carry, any unprivileged actor who can self-place-and-self-fill an order (a normal, permitted action — solver selection is optional and even when enabled the placer can select themselves) can permanently corrupt this on-chain pricing signal for a token/chain pair. This falls under "transaction/logic manipulation" of protocol state: the accumulator is production runtime state consumed as a price reference by the protocol's own contracts and downstream integrators, and it can be made to reflect one attacker's manufactured data point instead of genuine market activity, with no correction mechanism short of out-volume-ing the attacker's single deposit forever.

### Likelihood Explanation
High. `fillOrder` and `placeOrder` are unauthenticated, permissionless public entry points; `recordSpread` fires unconditionally on every fill whenever `_params.priceOracle != address(0)`; nothing prevents the placer and filler from being the same address; and the accumulator design (`weightedSpreadSum += weightedSpread; totalVolume += volume`) has no cap, decay, or minimum-liquidity/minimum-fill-count requirement before `spread()` is treated as reliable, matching the finding's requirement for a "public-entrypoint path" reachable by an "unprivileged attacker" with no relayer/prover/governance dependency.

### Recommendation
- Introduce a decay/windowing mechanism (e.g., exponential decay by `block.timestamp`, or a rolling window keyed by `lastUpdate`) so that stale, single-shot volume weight cannot persist indefinitely.
- Cap the per-fill contribution to the cumulative weight (e.g., clamp `volume` per update to some multiple of the pair's trailing average volume) so no single fill can dominate the aggregate.
- Require a minimum `fillCount` and/or minimum aggregate `totalVolume` before `spread()` is considered valid/non-zero, and expose that confidence signal to consumers.
- Consider excluding self-fills (`msg.sender == order.user`, or `order.user == solver` derived from beneficiary/committer) from `recordSpread`, or at minimum flag/segregate them from the trusted aggregate.

### Proof of Concept
1. Attacker (address `A`) calls `IntentGatewayV2.placeOrder` with `solverSelection` disabled, escrowing a very large amount `X` of token `T` (e.g., `1,000,000,000 * 1e18`) as both the required input and output token (same-token order), with a large `deadline`.
2. Attacker immediately calls `fillOrder` as the solver themselves, supplying `outputs` slightly below `inputs` (e.g., a self-chosen `-N` bps spread of their choosing) — this is legal because `fillOrder` has no self-fill restriction: [9](#0-8) 
3. `recordSpread` is invoked with `inputs`/`outputs` of volume `X`, producing `weightedSpread = spreadBps * X`, and this is added to `_tokenSpreads[sourceChainHash][T]`: [10](#0-9) 
4. Because `X` is arbitrarily large relative to any realistic future genuine fill volume, `spread(sourceChain, T)` now permanently reports (approximately) the attacker's chosen `spreadBps`, regardless of how many subsequent genuine fills occur, as demonstrated by the existing test showing a single large fill dominates ten times as many smaller genuine fills combined: [8](#0-7) 
5. The attacker's net cost is only gas, the protocol fee (if configured), and the relayer/dispatch fee for a same-token round trip — no directional loss — while achieving persistent corruption of the on-chain price/spread signal for that `(sourceChain, token)` pair.

    function spread(bytes memory sourceChain, address token) external view returns (int256) {
        bytes32 chainHash = keccak256(sourceChain);
        CumulativeSpreadData memory data = _tokenSpreads[chainHash][token];
        if (data.totalVolume == 0) return 0;

        return data.weightedSpreadSum / int256(data.totalVolume);
    }

    /**
     * @notice Updates cumulative spread data
     * @param data Storage reference to the cumulative spread data
     * @param weightedSpread The weighted spread (spread * volume)
     * @param volume The volume for this fill
     */
    function _updateCumulativeSpread(CumulativeSpreadData storage data, int256 weightedSpread, uint256 volume) private {
        data.weightedSpreadSum += weightedSpread;
        data.totalVolume += volume;
        data.fillCount += 1;
        data.lastUpdate = block.timestamp;
    }

    function fillOrder(Order calldata order, FillOptions calldata options) public payable nonReentrant {
        if (order.deadline < _blockNumber()) revert Expired();
        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain && orderSource != currentChain) revert WrongChain();
        if (!isSameChain && orderDest != currentChain) revert WrongChain();

        if (_filled[commitment] != address(0)) revert Filled();

        if (_params.solverSelection) {
            bytes32 storedSelectionHash;
            assembly {
                storedSelectionHash := tload(commitment)
            }

            bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
            if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
        }

        uint256 outputsLen = order.output.assets.length;
        if (options.outputs.length != outputsLen) revert InvalidInput();
        if (order.inputs.length != outputsLen) revert InvalidInput();

        if (isSameChain) {
            _fillSameChain(order, options, commitment);
        } else {
            _fillCrossChain(order, options, commitment);
        }

        if (_params.priceOracle != address(0)) {
            IIntentPriceOracle(_params.priceOracle)
                .recordSpread(commitment, order.source, order.inputs, options.outputs);
        }

    function testVWAPWithExtremeVolumeDifferences() public {
        _initOracle();

        // One tiny fill and one massive fill
        // Fill 1: 1 token, +1000 bps (10%)
        TokenInfo[] memory inputs1 = new TokenInfo[](1);
        TokenInfo[] memory outputs1 = new TokenInfo[](1);
        inputs1[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1 * 1e18});
        outputs1[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 11 * 1e17}); // 1.1 tokens
        oracle.recordSpread(keccak256("order1"), sourceChain, inputs1, outputs1);

        // Fill 2: 1 million tokens, -10 bps
        TokenInfo[] memory inputs2 = new TokenInfo[](1);
        TokenInfo[] memory outputs2 = new TokenInfo[](1);
        inputs2[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1_000_000 * 1e18});
        outputs2[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 999_000 * 1e18});
        oracle.recordSpread(keccak256("order2"), sourceChain, inputs2, outputs2);

        int256 vwap = oracle.spread(sourceChain, address(dai));

        // VWAP: (1000*1 + -10*1000000) / 1000001 = (1000 - 10000000) / 1000001 ≈ -9.99 bps
        // Tiny fill's huge spread (+1000 bps) is negligible compared to large volume at -10 bps
        assertTrue(vwap < 0, "VWAP should be dominated by large volume fill");
        assertEq(vwap, -9, "VWAP should be approximately -10 bps");
    }

    function testVWAPSingleLargeFillVsManySmallFills() public {
        _initOracle();

        // Compare: one 10000 token fill vs ten 1000 token fills, all same spread
        // Part 1: Single large fill
        TokenInfo[] memory inputs1 = new TokenInfo[](1);
        TokenInfo[] memory outputs1 = new TokenInfo[](1);
        inputs1[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 10000 * 1e18});
        outputs1[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 9950 * 1e18});
        oracle.recordSpread(keccak256("large"), sourceChain, inputs1, outputs1);

        int256 vwapSingle = oracle.spread(sourceChain, address(dai));

        // Part 2: Many small fills (use USDC to track separately)
        for (uint256 i = 0; i < 10; i++) {
            TokenInfo[] memory inputs = new TokenInfo[](1);
            TokenInfo[] memory outputs = new TokenInfo[](1);
            inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: 1000 * 1e6});
            outputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: 995 * 1e6});
            oracle.recordSpread(keccak256(abi.encodePacked("small", i)), sourceChain, inputs, outputs);
        }

        int256 vwapMany = oracle.spread(sourceChain, address(usdc));

        // Both should have same VWAP since spread and total volume are identical
        assertEq(vwapSingle, vwapMany, "VWAP should be identical regardless of fill count");
        assertEq(vwapSingle, -50, "Both should have -50 bps VWAP");
    }
