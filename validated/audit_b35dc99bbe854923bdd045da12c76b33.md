### Title
Unbounded CLVM execution (`INFINITE_COST`) in `Offer._get_offered_coins()` / `Offer.get_cancellation_coins()` allows a malicious offer file to hang a wallet's CPU when the offer is inspected or cancelled - (File: chia/wallet/trading/offer.py)

### Summary
Two `Offer` methods that a wallet must run on an *untrusted, counterparty-supplied* offer file execute the puzzle reveals of that offer's coin spends with `INFINITE_COST`, i.e. with no CLVM cost ceiling at all, unlike the rest of the offer-parsing code which passes `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM` and aborts on overrun.

### Finding Description
`Offer.__post_init__` (used for the additions cache) bounds CLVM execution correctly: [1](#0-0) 
uses `max_cost = int(DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM)`, decrements it per spend, and raises `ValidationError` if exceeded.

`Offer.conditions()` similarly bounds cost: [2](#0-1) 

However, `Offer._get_offered_coins()` runs each parent-spend's inner puzzle with an unbounded budget: [3](#0-2) 
`cost_left = INFINITE_COST` and `puzzle_cost, conditions = inner_puzzle.run_with_cost(cost_left, inner_solution)` — there is no cap and no exception path if the puzzle execution is extremely expensive.

`Offer.get_cancellation_coins()` has the same issue: [4](#0-3) 
`conditions: Program = run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)[1]` runs the puzzle reveal with no cost limit whatsoever.

Because CLVM execution cost is directly proportional to CPU work (that is the entire point of the cost-metering system used everywhere else in consensus/mempool code — see `pre_validate_spendbundle()`'s `max_tx_clvm_cost` enforcement and `compute_additions_with_cost()`'s `max_cost` enforcement), an attacker who crafts an offer file with a puzzle reveal containing a deliberately expensive computation (e.g., deep recursion or large loops that would normally be rejected by `BLOCK_COST_EXCEEDS_MAX`) can make `run_with_cost`/`inner_puzzle.run_with_cost` run for an unbounded amount of time when a victim wallet inspects or cancels that offer. `_get_offered_coins()` is invoked (via `get_offered_coins()`) whenever a wallet examines an offer's contents (offer summary / take-offer / trade-manager flows), and `get_cancellation_coins()` is invoked when a user cancels a pending offer — both are reachable from ordinary wallet/RPC actions on attacker-supplied offer bytes, well before any signature or on-chain validation takes place.

### Impact Explanation
This is directly analogous to the CVE's bug class: a crafted, otherwise well-formed input (SQL query / here, an offer file) triggers unbounded internal processing in a component that is supposed to be cost-metered, causing a hang (denial of service) of the processing component — here, the wallet's asyncio event loop, since `run_with_cost` is a synchronous call into Rust CLVM execution that will block the loop for as long as the puzzle takes to execute. A single malicious offer file sent to a wallet user (via any offer-sharing channel) can hang that user's wallet process/RPC for the duration of execution, which — with a puzzle designed to consume, e.g., cost near `2^64` — can be made arbitrarily long, i.e., a de facto crash/hang of transaction processing for that wallet.

### Likelihood Explanation
High likelihood of reachability: parsing/inspecting an offer (`get_offered_coins`) and cancelling an offer (`get_cancellation_coins`) are normal wallet operations performed on attacker-controlled offer bytes without prior cost-bounded validation of every code path (only `__post_init__`'s additions cache and `conditions()` are cost bounded; these two other paths are not). No signature or special privilege is required to construct or send an offer file.

### Recommendation
Bound CLVM execution in both `_get_offered_coins()` and `get_cancellation_coins()` the same way `__post_init__` and `conditions()` already do: pass a real, finite `max_cost` (e.g. `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM`, decremented across spends) into `run_with_cost`/`inner_puzzle.run_with_cost`, and treat cost-exceeded as a `ValidationError`/rejection of the offer rather than allowing `INFINITE_COST` execution.

### Proof of Concept
Not independently executed against a live wallet in this investigation (index/tool access is read-only); the argument is based on direct code inspection of `chia/wallet/trading/offer.py` showing `INFINITE_COST` used in `_get_offered_coins()` (line 247) and `get_cancellation_coins()` (line 436), contrasted with the properly cost-bounded sibling methods `__post_init__` (line 165) and `conditions()` (line 191). A concrete PoC would construct an `Offer` whose `_bundle` contains a `CoinSpend` with a puzzle reveal designed to consume CLVM cost far beyond `MAX_BLOCK_COST_CLVM` (e.g. a deep/wide recursive puzzle as used in the mempool's `deep_recursion`/`create_coins_loop` test fixtures) and call `offer.get_offered_coins()` or `offer.get_cancellation_coins()` to observe unbounded execution time. I could not fully verify runtime behavior without executing code, and I could not enumerate every RPC/CLI call path (e.g., `wallet_rpc_api.py`, `cmds/wallet_funcs.py`) invoking these two functions within the remaining iteration budget — this should be confirmed by a Devin session with code-execution access before treating this as fully validated.
