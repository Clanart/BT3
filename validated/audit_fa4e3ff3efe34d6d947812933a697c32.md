## Analysis

The requested bug class — an operation that updates internal "completed" state without verifying that the underlying asset transfer actually succeeded, causing assets to become permanently stuck — has a direct, provable analog in the Tron variant of the Intent Gateway.

### Title
Unchecked ERC20 `transfer()` return value in escrow withdrawal finalizes orders and burns escrow accounting even when the token transfer silently fails - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.sol` imports and uses `SafeERC20` for every token *inflow* (`safeTransferFrom` in `placeOrder`/`fillOrder`), which reverts on a falsy return value. However, every token *outflow* path — `withdraw()` (invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` and from `onGetResponse` for source-side cancellation) and the `SweepDust` branch of `onAccept` — uses a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the call did not revert, never inspecting the ABI-decoded boolean return value. [1](#0-0) 

### Finding Description
`withdraw()` marks the order as finalized (`_filled[body.commitment] = beneficiary`) and decrements the escrow accounting (`_orders[body.commitment][token] -= amount`) unconditionally, based only on whether the raw `.call()` succeeded — not on the semantic success of the `transfer()`:

```solidity
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
_orders[body.commitment][token] -= amount;
```

Any ERC20/TRC20 token that returns `false` instead of reverting on a failed transfer (a well-documented real-world token behavior, notably common among older/non-compliant tokens deployed on TRON) will make `success == true` while no tokens actually move to `beneficiary`. The same unchecked pattern is repeated in the `SweepDust` handling inside `onAccept`: [2](#0-1) 

Meanwhile, the escrow-funding paths (`placeOrder`, `fillOrder`) strictly use `SafeERC20.safeTransferFrom`, which does check the return value and reverts on failure: [3](#0-2) [4](#0-3) 

This asymmetry means tokens can enter escrow safely (guaranteed transfer) but can exit escrow *unsafely* (best-effort, silently ignorable failure), while the contract still treats the exit as having happened.

### Impact Explanation
Once `withdraw()` runs, `_filled[commitment]` is set and `_orders[commitment][token]` is decremented/zeroed — this is the *sole* record that funds are owed. If the actual `transfer()` call returns `false` without reverting, the beneficiary (user refund recipient or solver claiming redemption) receives nothing, yet the contract now believes the order is fully settled: `isOrderFilled`/`isOrderRefunded` report success, no retry path exists, and the token balance remains stranded in the gateway contract with no accounting entry pointing to it. This is a direct loss-of-funds / false-state-acceptance condition matching the bounty's accepted impact categories (stealing or loss of funds, false proof/state acceptance).

### Likelihood Explanation
No malicious actor, relayer, or governance action is required — only a legitimate order settlement/cancellation flow involving a non-standard ERC20/TRC20 token (or any token temporarily paused, blacklisting the recipient, or otherwise returning `false` on failure) exercising `onAccept`/`onGetResponse` → `withdraw()`. Given this contract targets the Tron EVM specifically (`evm/tron/contracts/apps/IntentGatewayV2.sol`), where TRC20 token implementations are known to deviate from strict revert-on-failure semantics, this is a realistic, unprivileged-path trigger rather than a contrived edge case.

### Recommendation
Replace every raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` in `withdraw()` and the `SweepDust` branch of `onAccept` with `SafeERC20.safeTransfer`, consistent with the deposit-side usage already present in the same file, so a falsy or missing return value reverts the state-changing accounting update instead of silently finalizing the order.

### Proof of Concept
1. Deploy (or use an existing) TRC20/ERC20 token whose `transfer()` returns `false` on failure instead of reverting (e.g., recipient blacklisted, insufficient allowance-independent internal check, or a paused-token implementation returning `false`).
2. User places a cross-chain order with this token as input via `placeOrder` (escrow succeeds via `safeTransferFrom`).
3. Solver fills the order on the destination chain; `RedeemEscrow` message is delivered back via `onAccept`, which calls `withdraw(body, false)`.
4. Inside `withdraw`, the token's `transfer(solver, amount)` call executes and returns `false`, but `success` (call-level) is `true`, so `if (!success) revert TransferFailed();` does not trigger.
5. `_orders[commitment][token] -= amount` and `_filled[commitment] = solver` are committed; `EscrowReleased` is emitted.
6. The solver's on-chain balance never increased, yet the order is permanently marked filled/settled with zero escrow remaining — the tokens are now stuck in the `IntentGatewayV2` contract with no accounting path to recover them.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
