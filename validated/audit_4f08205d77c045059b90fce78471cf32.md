### Summary
`Operator::withdraw` builds a payout transaction whose sole spending authorization is a user-supplied `SinglePlusAnyoneCanPay` Schnorr signature over `in_outpoint` (`core/src/operator.rs:630-637`, `core/src/builder/transaction/operator_reimburse.rs:407-436`). That sighash flag only commits input 0 and the output at the *same index* (the user payout output); it leaves the OP_RETURN output (which encodes "which operator fronted this withdrawal") and any additional funding inputs completely uncommitted. Anyone who obtains `(in_outpoint, output_txout, in_signature)` — e.g. by observing any operator's own broadcast attempt in the mempool, which is unavoidable public P2P data — can build and confirm a *different* transaction spending the same `in_outpoint`, paying the exact committed output, but with an OP_RETURN of their choosing (or none). Since attribution of "who fronted withdrawal idx i" is derived purely from parsing the OP_RETURN of whichever transaction actually confirms (`core/src/verifier.rs:2283-2352` → `core/src/database/verifier.rs:198-251`), and `PayoutCheckerTask` fully automates reimbursement based solely on that value (`core/src/task/payout_checker.rs:39-111`), the attacker fully controls who is credited/blocked from reimbursement, with no gRPC authorization required at any point in this chain.

### Finding Description
Binding claimed broken: `payout_payer_operator_xonly_pk` recorded for withdrawal idx `i` in the `withdrawals` table == the operator that the aggregator/operator-gated `withdraw` RPC (`core/src/rpc/operator.rs:192-258`, `core/src/rpc/aggregator.rs:1811-1887`) authorized to front that withdrawal.

Tracing the path:
1. `Operator::withdraw` (`core/src/operator.rs:560-637`) validates `withdrawal_utxo == input_utxo.outpoint` (line 594) and `is_profitable` (line 605-612) — both operate on caller-supplied data and gate whether *this* operator's own daemon decides to build+broadcast a tx. They do not, and cannot, gate what actually gets confirmed on Bitcoin.
2. `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) puts the user output at index 0, an anchor at index 1, and the fronting-operator's xonly pubkey OP_RETURN at index 2, then applies the pre-supplied `user_sig` via `set_p2tr_key_spend_witness`.
3. The signature is verified with `sighash_type` taken from the caller-supplied `in_signature.sighash_type` (`core/src/operator.rs:630-637`), documented and enforced elsewhere to be `SinglePlusAnyoneCanPay`. Under BIP341, `SIGHASH_SINGLE | ANYONECANPAY` commits only this one input and the output at the matching index (index 0) — nothing else. This is intentionally required so `fund_raw_transaction`/RBF (lines 639-689) can add extra funding inputs and reshuffle outputs after the fact without invalidating the signature.
4. Consequently the OP_RETURN (the only field that names the "fronting operator") and the entire set of additional inputs are unauthenticated with respect to the signature. Anyone possessing the `(in_outpoint, out_script_pubkey, out_amount, in_signature)` tuple — visible in cleartext the moment any operator submits it to bitcoind (mempool propagation is public, no TLS/gRPC involved) — can construct a competing transaction spending `in_outpoint`, reproducing output 0 exactly (satisfying the only committed constraint), funding it from their own UTXOs, and writing any OP_RETURN they want (a legitimate operator's pubkey, an invalid/garbage value, or nothing).
5. `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2352`) records `payout_payer_operator_xonly_pk` purely from `get_first_op_return_output` of whichever tx actually confirms in the block — it performs no check that this is the same tx/operator that any `withdraw`/`InternalFinalizedPayout` RPC call was made for.
6. `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) polls `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` and, upon a match, automatically calls `handle_finalized_payout` and proceeds through kickoff/reimbursement — with **no verification that this operator ever called `withdraw`, funded the output, or was contacted by the aggregator**.

None of the listed guards catch this: `Verifier::is_deposit_valid` and `SPV::verify`/`verify_storage_proofs` only check that *a* valid withdrawal-outpoint spend with correct amount exists at the committed Citrea index — they never check who funded/authored the extra inputs or the OP_RETURN. `Operator::is_profitable` and the `withdrawal_utxo != input_utxo.outpoint` check only run inside the honest operator's own aborted attempt and have zero effect on what miners actually confirm. `only_aggregator_and_self` and the operator-only gRPC gate only control who can *ask an operator daemon* to attempt a broadcast — they cannot control who broadcasts a *different, still-valid* transaction directly to bitcoind. `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) only checks that a kickoff's `operator_xonly_pk` matches the DB-recorded payer and that the committed blockhash matches — if the attacker frames a real registered operator, that operator's own kickoff for the payout will pass this check cleanly, since the operator genuinely is (falsely) the DB-recorded payer.

### Impact Explanation
- **An honest operator permanently unable to be reimbursed (Critical)**: if the attacker's competing spend confirms with a bogus/empty OP_RETURN before the true operator's own funded broadcast, the true operator's funding inputs are simply released (their tx never confirms — no loss of funds), but the withdrawal is now permanently recorded with `payout_payer_operator_xonly_pk = NULL` or a value that never matches them. `validate_payer_is_operator` (`core/src/operator.rs:1686-1740`) will forever reject reimbursement attempts for this deposit for every operator, since no operator's xonly pk matches the recorded payer — the withdrawal path for that deposit index is permanently orphaned from the reimbursement flow.
- **An operator reimbursed for a payout it never funded (Critical)**: if instead the attacker copies a targeted, currently-registered operator's xonly pubkey into the OP_RETURN while paying the withdrawal amount entirely from their own funds, `PayoutCheckerTask` on that operator's node will autonomously detect the "unhandled payout" and proceed through kickoff → reimbursement, crediting bridge collateral/reimbursement to an operator who spent nothing.
- Repeatable per withdrawal and per deposit; the only cost to the attacker is funding the exact committed output amount (potentially the full bridge amount) themselves, and racing/fee-bumping the transaction ahead of the legitimate operator's own funded broadcast — entirely feasible on a public mempool with no privileged access.

### Likelihood Explanation
Preconditions: (1) at least one operator (or the aggregator on behalf of operators) has broadcast, or is in the process of broadcasting, a payout tx for some withdrawal index — this happens for every legitimate withdrawal; (2) the attacker is watching the mempool/network (trivial, requires no privilege — any Bitcoin full node or Electrum server suffices); (3) the attacker has BTC to fund the committed output amount and pay a competitive fee to win the race (this is the main "cost", proportional to the withdrawal size, not free but far short of "must control majority hashrate" or similar exclusions). No key compromise, no TLS interception, no verifier/operator role is needed — this exactly matches the specified unprivileged attacker profile. The vulnerability is a direct, deterministic consequence of the chosen sighash type (`SIGHASH_SINGLE|ANYONECANPAY`) leaving the OP_RETURN and extra inputs unauthenticated, not a probabilistic race-condition bug; whenever the attacker successfully gets their competing spend mined first, the divergence is guaranteed.

### Recommendation
Commit the fronting operator's identity to the user's payout signature so it cannot be swapped by a third party. Options: (a) require the withdrawal's user signature to use `SIGHASH_ALL` (or at minimum a sighash mode that commits all outputs, e.g. `SIGHASH_DEFAULT` with a fixed transaction template) so the OP_RETURN output cannot be altered without invalidating the signature — this requires redesigning the fee-funding mechanism (e.g. moving to a separate CPFP anchor input rather than `fund_raw_transaction` add_inputs on the same tx); or (b) have the user's off-chain signature/authorization additionally commit to a specific operator xonly pubkey (verified before accepting the withdrawal request), and have `update_finalized_payouts` cross-check the confirmed OP_RETURN operator against that pre-committed value, rejecting (rather than crediting) confirmations whose OP_RETURN operator does not match the pre-agreed operator for that withdrawal index.

                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")

    async fn run_once(&mut self) -> Result<Self::Output, BridgeError> {
        let mut dbtx = self.db.begin_transaction().await?;
        let unhandled_payout = self
            .db
            .get_first_unhandled_payout_by_operator_xonly_pk(

                self.operator.signer.xonly_public_key,

            .await?;

        if unhandled_payout.is_none() {
            return Ok(false);
        }

        let (citrea_idx, move_to_vault_txid, payout_tx_blockhash) =
            unhandled_payout.expect("Must be Some");

        tracing::info!(
            "Unhandled payout found for withdrawal {}, move_txid: {}",
            citrea_idx,
            move_to_vault_txid
        );

        let deposit_data = self
            .db
            .get_deposit_data_with_move_tx(Some(&mut dbtx), move_to_vault_txid)
            .await?;
        if deposit_data.is_none() {
            return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());
        }

        let deposit_data = deposit_data.expect("Must be Some");

        let kickoff_txid = self
            .operator
            .handle_finalized_payout(
                &mut dbtx,
                deposit_data.get_deposit_outpoint(),
                payout_tx_blockhash,
            )
            .await?;

        // fetch and save the LCP for if we get challenged and need to provide proof of payout later
        let (_, payout_block_height) = self
            .operator
            .db
            .get_block_info_from_hash(Some(&mut dbtx), payout_tx_blockhash)
            .await?
            .ok_or_eyre("Couldn't find payout blockhash in bitcoin sync")?;

        let _ = self
            .operator
            .citrea_client
            .fetch_validate_and_store_lcp(
                payout_block_height as u64,
                citrea_idx,
                &self.operator.db,
                Some(&mut dbtx),
                self.operator.config.protocol_paramset(),
            )
            .await?;

        #[cfg(feature = "automation")]
        self.operator.end_round(&mut dbtx).await?;

        self.db
            .mark_payout_handled(Some(&mut dbtx), citrea_idx, kickoff_txid)
            .await?;
