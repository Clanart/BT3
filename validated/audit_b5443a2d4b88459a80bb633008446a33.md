## Title
Fee-on-transfer / deflationary input tokens over-credit escrow in the Tron `IntentGatewayV2.placeOrder` non-predispatch path — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder` in the Tron variant credits the internal escrow ledger `_orders[commitment][token]` with the user-*declared* `order.inputs[i].amount` (minus protocol fee) rather than the amount of tokens the contract actually received via `safeTransferFrom`. The mainline EVM contract (`evm/src/apps/IntentGatewayV2.sol`) fixes exactly this class of bug by snapshotting `balanceOf(address(this))` before and after the transfer and using the delta as the escrowed amount; that fix is missing from the Tron fork, reproducing the "minted/escrowed amount ≠ actually deposited amount" pattern from the reported Convex `Booster.deposit` bug.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 

```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
            msgValue -= order.inputs[i].amount;
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }
        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
```

`reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` (the user's declared value, reduced only by the protocol fee) — see the fee computation just above using `originalAmount = order.inputs[i].amount`. There is no check of the contract's actual token balance before/after the `safeTransferFrom`. For any ERC-20 input token that is fee-on-transfer, deflationary, or rebasing, `IntentGateway` will physically receive fewer tokens than `order.inputs[i].amount`, yet the escrow ledger `_orders[commitment][token]` is credited as if the full declared amount arrived.

This is precisely the "Booster" bug class from the external report: the contract accepts a declared `_amount`, but the amount actually deposited into the contract's internal accounting can diverge from what was actually transferred in, because the credited value is never reconciled against `balanceOf` deltas.

By contrast, the mainline EVM contract explicitly guards against this: [2](#0-1) 

```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
```

and a dedicated Foundry test proves this is a deliberately fixed invariant on the mainline path: [3](#0-2) 

The Tron fork's `placeOrder` (both the predispatch and non-predispatch branches were reviewed; the non-predispatch branch has no such reconciliation at all) never received this fix.

### Impact Explanation
`_orders[commitment][token]` is the accounting ledger that downstream logic (fill settlement, refund/cancel paths) relies on to know how many tokens are owed against a given order commitment and are assumed to be physically backed 1:1 by the contract's token balance. If the ledger is inflated relative to actual holdings (because a fee-on-transfer/deflationary token silently reduced what was received), the sum of all outstanding escrow liabilities across orders can exceed the contract's real token balance. The first orders to be filled/refunded/redeemed will drain the shortfall from tokens that actually belong to other, unrelated users' orders — a direct loss-of-funds / insolvency condition affecting other order owners, not just the attacker who used the deflationary token. This falls squarely under "stealing or loss of funds" and "logic attacks" in the bounty's impact gate, since it requires no privileged actor, relayer, or governance action — any unprivileged user placing an order with a fee-on-transfer/deflationary token triggers the mismatch.

### Likelihood Explanation
This requires only that: (1) the Tron `IntentGatewayV2` deployment allowlists or does not otherwise reject fee-on-transfer/deflationary/rebasing tokens as valid `order.inputs[].token`, and (2) a user places an order using such a token. No relayer, prover, or admin cooperation is needed, and no proof forgery is involved — the entire bug is local to `placeOrder`'s escrow bookkeeping. Likelihood is directly tied to whether such tokens are permitted as inputs on the deployed Tron gateway; since the mainline EVM contract explicitly hardens against this exact class of token (with tests), it strongly suggests fee-on-transfer tokens are an expected/supported input type for this product line, making the divergence in the Tron fork a real, reachable gap rather than a theoretical one.

### Recommendation
Apply the same fix used in `evm/src/apps/IntentGatewayV2.sol` to the Tron variant's `placeOrder`: snapshot `IERC20(token).balanceOf(address(this))` immediately before each `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` call, and after the transfer compute the actually-received amount as `balanceAfter - balanceBefore`. Use that reconciled, actually-received amount (after subtracting the protocol fee proportionally, as the mainline branch does) when incrementing `_orders[commitment][token]`, instead of crediting the escrow ledger from the caller-declared `order.inputs[i].amount`/`reducedInputs[i].amount` directly. The predispatch branch should be audited the same way to confirm it cannot be manipulated to under-deliver into the shared `CallDispatcher` while still crediting a fully-reduced amount to escrow.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a test ERC-20 that charges, e.g., a 5% transfer fee (standard fee-on-transfer mock, as already used in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`'s `FeeOnTransferToken`).
2. Register/allow this token as a valid `order.inputs[0].token`.
3. Call `placeOrder` with `order.inputs[0].amount = 1000e18` and no `predispatch` (empty `predispatch.call`/`predispatch.assets`), so the vulnerable branch at lines 444–463 executes.
4. Observe: `IERC20(token).balanceOf(address(intentGateway))` increases by only `950e18` (after the 5% fee), but `_orders[commitment][token]` is credited with the full `reducedInputs[0].amount` (≈`1000e18` minus protocol fee, i.e. ~`950e18` more than physically received, depending on protocol fee configuration — with 0% protocol fee, escrow reads `1000e18` against a real balance increase of only `950e18`).
5. This 50e18 shortfall is now unbacked; when this or a subsequent order's escrow is paid out, the contract will need to draw down real token balance belonging to other orders' un-related escrows, demonstrating the insolvency/loss-of-funds path.

Note: I was not able to directly inspect the fill/refund/redeem functions that consume `_orders[commitment][token]` in this session (ran out of tool iterations), so the exact downstream payout mechanics (e.g., whether fillers are paid directly from this mapping or via a separate settlement flow) should be confirmed by a follow-up review of `IntentsBase.sol`'s fill/refund logic before remediation, though the core over-crediting bug in `placeOrder` itself is fully confirmed from the code shown above.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount");

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
