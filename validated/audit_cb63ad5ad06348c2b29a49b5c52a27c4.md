### Title
Unauthenticated SSRF via attacker-controlled DataLayer mirror URLs fetched by a victim node's DataLayer sync loop - (File: `chia/data_layer/data_layer.py`)

### Summary
The DataLayer mirror mechanism lets **any** wallet on the network create a "mirror" coin that advertises an arbitrary URL for **any** existing DataLayer store (`launcher_id`), simply by spending a coin to the well-known `MIRROR_PUZZLE_HASH` with the target `launcher_id` and URL(s) placed in the coin memos. Any full node/wallet that is subscribed to (or owns) that store will, on its periodic DataLayer sync loop, treat that attacker-supplied URL as a legitimate mirror server and issue outbound `aiohttp` HTTP GET requests to it in order to download delta/full-tree files - with no host/IP allow-listing, scheme restriction, or SSRF protection. This mirrors the YesWiki `keyId` bug class: an unauthenticated/unprivileged actor supplies a URL that is embedded in protocol data (here: on-chain coin memos rather than an HTTP header), and a victim service later performs a server-initiated fetch to that URL before/independent of any trust validation of the URL's origin.

### Finding Description
Mirror coins are created via `DataLayerWallet.create_new_mirror()` [1](#0-0) , which spends XCH to `create_mirror_puzzle()` (`P2_PARENT.curry(Program.to(1))`, exposed as `MIRROR_PUZZLE_HASH`) and places `[launcher_id, *urls]` in the coin's memos [2](#0-1) . The `launcher_id` embedded in the memo is **not validated to be owned by, or related to, the spender** - it is simply free-form data chosen by whoever creates the `CREATE_COIN` condition. Any unprivileged wallet holding a small amount of XCH can construct a standard spend bundle with this puzzle hash/memo pair naming a victim's `launcher_id` and pointing the URL at any internal/attacker-chosen host.

The service side treats mirrors purely as a discovery mechanism for download servers: `DataLayer.update_subscription()` "sync[s] subscription URLs from wallet mirrors" and folds them into `DataStore.get_available_servers_for_store()` results, which `fetch_and_validate()` then iterates over and fetches from without validation [3](#0-2) . The download itself is performed over plain HTTP via `aiohttp` in `download_data.py`'s `http_download`/`download_file` path (referenced by `insert_from_delta_file`) with no destination-host restrictions - only the *downloaded content* is later verified against the wallet-advertised Merkle root, not the destination the request was sent to. This is explicitly called out as an accepted trust boundary in the module notes: "Plugin and mirror URLs are external trust inputs" and "mirror URLs... are never trust anchors" [4](#0-3) , but that boundary only protects data integrity - it says nothing about restricting the destination of the outbound network request itself, which is exactly the SSRF primitive.

Because store `launcher_id`s are public (they are on-chain singleton ids known to anyone who wants to interoperate with a DataLayer store, e.g. via offers), an attacker can target any actively-subscribed or self-owned store operated by a victim node, without needing any credentials, RPC access, or even being a counterparty to that node - just broadcasting a normal, validly-signed spend bundle to the mempool that anyone can submit.

### Impact Explanation
This is a genuine unauthenticated/unprivileged-triggered SSRF: a single spend-bundle submission from any wallet forces victim DataLayer-enabled nodes to make outbound HTTP requests to attacker-chosen URLs (e.g., cloud metadata endpoints, internal RPC/admin services, or ports intended to be firewalled off) on a recurring basis (`periodically_manage_data()`), without the victim operator taking any explicit action to "subscribe" to anything malicious - since any store they legitimately track can be paired with an attacker-injected mirror. Depending on network placement this can enable internal service/port discovery, cloud credential theft (metadata endpoints), or reaching intranet-only endpoints reachable from the node's host - the same class of impact as the YesWiki CVE.

### Likelihood Explanation
Likelihood is moderate-to-high for any Chia node operator running DataLayer with mirror/subscription features enabled and tracking third-party stores (a supported and documented use case for DataLayer offers/interop). Creating the malicious mirror coin requires only a standard signed transaction with a `CREATE_COIN` condition to a known puzzle hash and attacker-chosen memos - no special privileges, no cryptographic bypass, and no interaction with the victim beyond the victim independently deciding to track/subscribe to the targeted `launcher_id` (which is a normal, expected DataLayer workflow, e.g. taking a DataLayer offer).

### Recommendation
- Validate or restrict mirror URLs before using them as download targets: enforce scheme allow-listing (https only), reject private/loopback/link-local/metadata IP ranges (e.g. RFC1918, `169.254.169.254`) unless explicitly configured otherwise, and support an operator-controlled URL allow/deny list for DataLayer mirror/plugin fetches.
- Consider requiring some minimal proof-of-relationship (e.g., signed by the store's launcher-associated key, or amount/lock-based reputation) before a mirror entry for a `launcher_id` is trusted enough to be dialed automatically, rather than trusting arbitrary on-chain memo content.
- Add configurable network egress controls (e.g., resolve-then-filter DNS pinning to prevent DNS rebinding) around all outbound fetches originating from `download_data.py`/`fetch_and_validate()`.

### Proof of Concept
1. Attacker learns (or already knows, since it's public) the `launcher_id` of a DataLayer store that a victim node subscribes to (e.g., because the victim publicly offers DataLayer data via an offer / mirrors it).
2. Attacker constructs and broadcasts a normal signed spend bundle that creates a coin with puzzle hash `MIRROR_PUZZLE_HASH` (`create_mirror_puzzle()`), memo `[victim_launcher_id, "http://169.254.169.254/latest/meta-data/..."]`, mirroring the flow exercised in `test_mirrors`/`create_new_mirror` [5](#0-4) .
3. Once the spend confirms, any node tracking `victim_launcher_id`'s mirrors (via `dl_get_mirrors`/`get_mirrors_for_launcher`) will surface this URL as an available server for that store.
4. On its next `periodically_manage_data()` cycle, the victim's `DataLayer.fetch_and_validate()` iterates `get_available_servers_for_store()` and issues an HTTP GET to the attacker's URL [6](#0-5) , completing the SSRF.

Note: I was unable to fully trace the exact wallet-side coin-state scanning logic that populates `get_mirrors_for_launcher()` from arbitrary `MIRROR_PUZZLE_HASH` coin spends (i.e., confirming there is no additional filter restricting which `launcher_id` values are accepted into that mapping) within the available indexed content; a background agent with full repository access should verify `dl_wallet_store.py` and the coin-state handling for `MIRROR_PUZZLE_HASH` spends to confirm no additional authorization check exists before treating a mirror as valid for a given store.

def create_mirror_puzzle() -> Program:
    return P2_PARENT.curry(Program.to(1))


MIRROR_PUZZLE_HASH = create_mirror_puzzle().get_tree_hash()


def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]

Public DataLayer docs describe proving key/value inclusion without sharing the full dataset. Source-level correctness depends on two separate truths staying aligned: wallet singleton history publishes the root sequence, while local/mirrored files provide enough data to reconstruct those roots. Mirrors and plugins can improve availability, but they are never trust anchors; every downloaded file must rebuild the wallet-advertised root before becoming local committed state.

## Wrong Assumptions To Avoid

- Do not treat a local root as current chain truth until wallet confirmation status has been reconciled.
- Do not treat mirror URLs, plugins, or static file names as trusted data sources.
