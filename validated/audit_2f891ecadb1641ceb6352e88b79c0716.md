## Title
GitHub repository association is matched once and never re-verified against a changed remote URL, letting a hijacked/attacker-controlled remote inherit a trusted repo's branch protection, repo-rules, and CI status - (File: `app/src/lib/stores/app-store.ts`, `app/src/lib/stores/repositories-store.ts`)

### Summary
The report's broken invariant is: a security-relevant derived value (`totalQuestPeriodRewards`) is captured once from a mutable source (`questRewardsPerPeriod`) and then guarded by a "set only once" flag, so later legitimate changes to the source are silently ignored by every downstream consumer. The Desktop analog is the `gitHubRepository` association stored per local `Repository`: once Desktop matches a local repo's remote to a GitHub API repository and persists the association (`gitHubRepositoryID`), that binding is treated as permanent. The code explicitly acknowledges this is a "set once, never cleared" design: [1](#0-0) 

### Finding Description
When a repository is added, Desktop tries to match its remote to a GitHub repository via `matchGitHubRepository` and persists the found association through `repositoriesStore.upsertGitHubRepository` / `setGitHubRepository`: [2](#0-1) 

The comment at line 4880-4882 states the association is intentionally never cleared, bailing out early once a match exists. Subsequently, `updateRemoteUrl` only pushes the *API's* clone URL back onto the local git remote when the local remote is unchanged from the previously recorded `gitHubRepository.cloneURL` — it never reconciles the other direction (i.e., it does not detect/react to the local remote URL being switched to point at a completely different repository, git host content, or a repo the user does not actually control): [3](#0-2) 

Because the `GitHubRepository` object (dbID) is the value keyed against for downstream trust decisions — branch-protection enforcement cache (`branchProtectionSettingsFoundCache`, `protectionEnabledForBranchCache`), commit-status/CI subscriptions (`CommitStatusStore`), and repo-rules evaluation (`useRepoRulesLogic`, `parseRepoRules`) — all of these consumers rely on the *cached* `GitHubRepository` identity rather than re-validating that the repository's current remote still legitimately corresponds to that GitHub repository: [4](#0-3) [5](#0-4) 

This mirrors the Paladin bug precisely: `notifyDistributedQuestPeriod` sets `totalQuestPeriodRewards` once and ignores later, legitimate updates to `questRewardsPerPeriod`; here, the GitHub repository association is set once and Desktop's guard rails (repo rules warnings, branch-protection warnings, CI check display, PR association) never re-derive from the actual, current remote — they operate against the stale/cached `GitHubRepository` object tied to a dbID that was fixed at first-match time.

### Impact Explanation
If an attacker can influence a repository's remote (e.g., via a malicious `.git/config` shipped in a cloned/fetched repo, a crafted deep link that opens/adds a repository, or a compromised proxy/mirror that rewrites `origin`), the association between the local working copy and the "trusted" `GitHubRepository` record can become inconsistent with reality while still driving security-relevant UI/logic:
- Branch-protection and repo-rules warnings (`renderBranchProtectionsRepoRulesCommitWarning`, `useRepoRulesLogic`) reflect the stale/original GitHub repository's rules, not the rules of whatever repository the remote now actually points to.
- CI/commit status (`CommitStatusStore`) and PR-checks-based dialogs continue to reference the original `GitHubRepository`, so a user could be shown "this branch is protected" / "checks pass" information that no longer corresponds to where their commits are actually going.
- Since GitHub Desktop never clears this binding (per the code comment), there's no self-healing path; the stale trust decision persists for the life of the repository entry in Desktop's database.

This is a Medium-severity "silent corruption of what the user commits/pushes and reviews" class issue: users can be led to trust the wrong rule/branch-protection/CI context tied to a repository the remote no longer honestly represents.

### Likelihood Explanation
Likelihood is moderate: it requires an attacker to control a git remote configuration of a repository that Desktop already tracks (e.g., a crafted repo added via `x-github-client` deep link, or a compromised/malicious remote push that rewrites `origin` inside a repo the victim already has open in Desktop), plus enough time for the mismatch to persist because Desktop explicitly never re-validates the association (issue desktop/desktop#1144, referenced in the code). No admin rights, local malware, or credential leakage is needed — only the ability to alter the git remote of a tracked repository, which is squarely within the "attacker controls a cloned/fetched repository or a git remote" threat model.

### Recommendation
- Periodically re-verify that the repository's current `origin` (or default) remote still matches the persisted `GitHubRepository.cloneURL`/`htmlURL`, and re-run `matchGitHubRepository` when it doesn't, rather than bailing out early once any match exists.
- When the remote no longer matches, clear or re-scope the branch-protection cache (`branchProtectionSettingsFoundCache`, `protectionEnabledForBranchCache`), CI subscriptions, and repo-rules state for that repository so stale trust decisions are not surfaced.
- Surface a warning to the user when the tracked remote diverges from the recorded GitHub repository association instead of silently continuing to use the old one.

### Proof of Concept
1. Add/clone a repository in Desktop whose `origin` points to `github.com/org/real-repo`; Desktop matches and persists a `GitHubRepository` association (dbID X) with real-repo's branch protection/repo rules.
2. An attacker with push access to that repo (or via a crafted deep link workflow / malicious fetch that rewrites `.git/config`) changes the local `origin` remote URL to point to a different repository (`github.com/attacker/evil-repo`) that has no branch protection/repo rules configured.
3. Reload/refresh the repository in Desktop. Per `repositoryWithRefreshedGitHubRepository` (`app/src/lib/stores/app-store.ts:4874-4914`), since a match/association already exists it is not recomputed from the new remote; `updateRemoteUrl` only reconciles the URL to match `gitHubRepository.cloneURL` if unchanged, it does not detect the remote pointing elsewhere.
4. The commit UI, branch-protection warnings, and CI checks continue to reflect the original `real-repo`'s (now stale) rules/status while the user is actually pushing to `evil-repo`, or vice versa — a mismatch between displayed trust signals and actual push destination.

Note: I was not able to fully trace every downstream consumer of the `GitHubRepository` dbID (e.g., exact CI subscription lifecycle tied to repository switching) within the available index; a Devin session with full repository access would be needed to confirm all code paths that key off the stale association and to validate the exact severity of end-to-end exploitation.

   * refetches the associated GitHub remote repository, if possible
   *
   * if refetching fails, will return the given `repository` with
   * the same info it was passed in with
   *
   * @param repository
   * @returns repository model (hopefully with fresh `gitHubRepository` info)
   */
  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo
  }

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function useRepoRulesLogic(
  account: Account | null,
  repository: Repository
): boolean {
  if (
    !account ||
    !repository ||
    !isRepositoryWithGitHubRepository(repository)
  ) {
    return false
  }

  const { endpoint, owner, isPrivate } = repository.gitHubRepository

  if (!supportsRepoRules(endpoint)) {
    return false
  }

  // repo owner's plan can't be checked, only the current user's. purposely return true
  // if the repo owner is someone else, because if the current user is a collaborator on
  // the free plan but the owner is a pro member, then repo rules could still be enabled.
  // errors will be thrown by the API in this case, but there's no way to preemptively
  // check for that.
  if (
    account.login === owner.login &&
    (!account.plan || account.plan === 'free') &&
    isPrivate
  ) {
    return false
  }

  return true
}
