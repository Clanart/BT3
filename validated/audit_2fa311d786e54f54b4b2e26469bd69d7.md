### Title
Bridge circuit accepts operator total_work **equal to** watchtower max_total_work instead of requiring it to be strictly greater - (File: circuits-lib/src/bridge_circuit/mod.rs)

### Summary
The bridge circuit's specification (documented in the module itself and in `docs/bridge-circuit.md`) requires that the Operator's claimed cumulative proof-of-work (`total_work`) be strictly **greater than** the maximum verified work submitted by any challenging Watchtower (`max_total_work`). The implementation instead only rejects the case where `total_work` is strictly **less than** `max_total_work`, silently accepting the boundary case where the two are equal. This is the exact analog of the reported GovernorAlpha bug: a quorum/threshold check documented as strict `>` is implemented as `>=`.

### Finding Description
`bridge_circuit` computes the maximum verified watchtower work and only panics if the operator's work is strictly less than it: [1](#0-0) 

This means `total_work == max_total_work` passes silently. However, the module-level and function-level documentation explicitly state the intended (and stronger) requirement: [2](#0-1) [3](#0-2) 

and the human-readable spec (`docs/bridge-circuit.md`) reiterates the same strict requirement: [4](#0-3) 

The tie scenario is not merely theoretical: `calculate_work` in the header-chain circuit computes work purely as a function of the difficulty target/`bits`, independent of the actual block hash/content: [5](#0-4) 

Since Bitcoin's difficulty target only changes at 2016-block epoch boundaries, any two chains of equal length within the same difficulty epoch accumulate byte-for-byte identical `total_work`, regardless of which blocks/hashes they actually contain. This makes an exact `total_work == max_total_work` tie a realistic, easily reachable state (e.g. during an ordinary short-lived chain split/reorg, or by an operator deliberately assembling an HCP of the same length as a watchtower's competing branch within the same epoch), not something requiring astronomically improbable luck.

### Impact Explanation
The binding this check is supposed to enforce is: *the block hash the Operator commits to (used to justify the payout/fronting transaction) must belong to the canonical (strictly heaviest) chain > any chain a Watchtower can prove is heavier or equal*. By accepting equality, the circuit lets an Operator's HCP tie with (rather than strictly beat) a Watchtower-proven alternative chain and still be treated as canonical. This breaks the soundness guarantee described in the module doc ("ensures that an operator's claimed Bitcoin chain state ... has more cumulative proof-of-work than any challenging watchtower") and falls into the Critical bucket "a false circuit claim proved" — the circuit proves the Operator's payout-block claim valid in a case the documented rule says it should reject.

### Likelihood Explanation
No privileged role is required beyond the Operator's normal, permissionless ability to submit an HCP and payout claim through the existing bridge-circuit flow; watchtowers act adversarially/honestly as designed. Because `total_work` ties are a structural property of the header-chain's target-only work calculation (not a probabilistic hash-based coincidence), the boundary condition is reachable in ordinary reorg situations or through Operator-controlled chain construction within a difficulty epoch, without needing key compromise, majority hashrate, or a colluding verifier/operator/watchtower role beyond the Operator itself.

### Recommendation
Change the guard in `bridge_circuit` (circuits-lib/src/bridge_circuit/mod.rs) from `if total_work < max_total_work` to `if total_work <= max_total_work`, so the panic is triggered on equality as well, matching the documented "strictly greater than" requirement. Alternatively, if equality is intended to be accepted, update the docstrings (module doc, function panics section) and `docs/bridge-circuit.md` to explicitly state that ties are treated as sufficient, and add an inline comment justifying why equal work is acceptable given the target-only, hash-independent nature of `calculate_work`.

### Proof of Concept
1. Two chains fork at height `H` inside the same 2016-block difficulty epoch, chain A (Operator's claimed HCP chain) and chain B (a Watchtower's proven alternate chain), both reaching height `H+k` with `k` blocks each, all mined at the epoch's current `bits`.
2. Because `calculate_work` depends only on `bits`/target, not on block hash content (`circuits-lib/src/header_chain/mod.rs:706-726`), `total_work(A) == total_work(B)` exactly, both equal to `k * work_per_block` added to the pre-fork cumulative work.
3. Operator submits HCP for chain A; a Watchtower submits a valid Work-Only Proof for chain B with `max_total_work == total_work(A)`.
4. In `bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs:151-160`), `total_work < max_total_work` evaluates to `false` (they're equal), so no panic occurs, and the circuit proceeds to accept the Operator's payout claim on chain A — even though chain B is proven to be at least as heavy, violating the documented strict-inequality soundness rule.

/// Calculates the amount of work represented by a difficulty target.
///
/// Bitcoin measures cumulative proof-of-work as the sum of work done by all blocks.
/// The work for a single block is inversely proportional to its target:
/// work = 2 ** 256 / (target + 1)
/// The following implementation follows Rust-Bitcoin's approach:
/// https://github.com/rust-bitcoin/rust-bitcoin/blob/eb17995e49b68831114cbc8bda14cbe72811c4b7/bitcoin/src/pow.rs#L533
/// This calculation uses the mathematical identity:
/// 2**256 / (x + 1) == ~x / (x + 1) + 1
/// (Equation shamelessly stolen from bitcoind)
///
/// This allows comparing the total work between different chains to determine
/// which has the most accumulated proof-of-work.
///
/// ## Parameters
///
/// * `target` - The difficulty target as a 32-byte big-endian array
///
/// ## Returns
///
/// * `U256` - The amount of work represented by this target
fn calculate_work(target: &[u8; 32]) -> U256 {
    // We should never have a target/work of zero so this doesn't matter
    // that much but we define the inverse of 0 as max.
    let target = U256::from_be_slice(target);
    if target == U256::ZERO {
        return U256::MAX;
    }
    // We define the inverse of 1 as max.
    if target == U256::ONE {
        return U256::MAX;
    }
    // We define the inverse of max as 1.
    if target == U256::MAX {
        return U256::ONE;
    }

    let comp = !target;

    let ret = comp.wrapping_div(&target.wrapping_add(&U256::ONE));
    ret.wrapping_add(&U256::ONE)
}
