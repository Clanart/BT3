This confirms the mechanism: `get_payout_txs_for_withdrawal_utxos` joins purely on `bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout` [1](#0-0) , i.e. it records whichever transaction is found to have spent the withdrawal outpoint on-chain, with no check that this transaction is the exact one the honest operator broadcast. `update_finalized_payouts` then blindly parses that mined transaction's OP_RETURN and stores whatever `XOnlyPublicKey` it decodes to [2](#0-1) .

### Title
Payout tx OP_RETURN operator-pubkey binding is malleable under `SinglePlusAnyoneCanPay`, permanently orphaning honest operators' reimbursement - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The user's withdrawal signature is enforced to be `TapSighashType::SinglePlusAnyoneCanPay` [3](#0-2) , which per BIP-341 only commits to input 0's own outpoint/value/scriptPubkey and to output 0 — it does not commit to output 2 (the OP_RETURN carrying the fronting operator's x-only pubkey) [4](#0-3) . An attacker who observes an honest operator's broadcast payout tx can reuse input 0 (with its unchanged witness) and output 0 verbatim, replace the operator's own funding inputs with self-funded ones, and swap output 2's OP_RETURN for an arbitrary attacker-controlled but syntactically valid 32-byte x-only pubkey, then get this variant mined instead.

### Finding Description
The broken binding is: `payout_payer_operator_xonly_pk` stored for withdrawal `i` == the x-only pubkey of the operator who funded output 0 of the mined payout tx for withdrawal `i`. This binding is expected to be cryptographically enforced by the payout tx signature, but it is not, because of the following:

1. `get_payout_txs_for_withdrawal_utxos` selects, for a given withdrawal, whichever transaction is recorded in `bitcoin_syncer_spent_utxos` as spending `withdrawal_utxo_txid`/`withdrawal_utxo_vout` — it has no notion of "the" canonical payout tx the honest operator built [5](#0-4) .
2. `update_finalized_payouts` then trusts whatever OP_RETURN bytes are present in that mined tx and parses them into an `XOnlyPublicKey`, storing it unconditionally as the payer [6](#0-5) .
3. The user's signature over input 0 uses `SinglePlusAnyoneCanPay` [7](#0-6) , which per Taproot sighash rules (`calculate_pubkey_spend_sighash` selects `Prevouts::One` for `*PlusAnyoneCanPay` types) only commits to input 0's own prevout and output 0 [8](#0-7) . Output 1 (anchor) and, critically, output 2 (the OP_RETURN with the operator's pubkey) are entirely uncommitted by this signature.

Exploit flow: the attacker observes the honest operator's payout tx in the mempool (public data), extracts input 0's previous outpoint and witness (the user's valid signature, reusable verbatim) and output 0 (verbatim, required to keep the signature valid). The attacker discards the operator's added funding inputs (which are signed by the operator with standard `SIGHASH_ALL` and would be invalidated by any output change), substitutes their own funding input(s) to cover the payout amount/fee, and replaces output 2's OP_RETURN with an arbitrary, syntactically valid 32-byte x-only pubkey that decodes via `XOnlyPublicKey::from_slice` but belongs to no registered operator. The attacker broadcasts this competing transaction (e.g., with a higher fee) so it, rather than the honest operator's original, gets mined for that specific withdrawal UTXO.

Once mined, `update_finalized_payouts` stores the attacker's bogus pubkey as `payout_payer_operator_xonly_pk` for that withdrawal. Two failures cascade:
- `PayoutCheckerTask::run_once` calls `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)`, which filters `WHERE payout_payer_operator_xonly_pk = $1` [9](#0-8) . Since the stored pk is the attacker's, not the real funding operator's, this query never returns a row for the real operator, so `handle_finalized_payout`/kickoff automation is never triggered for them [10](#0-9) .
- If the real operator manually sends a kickoff for that deposit anyway, `is_kickoff_malicious` fetches `payout_info` by move txid, obtains the attacker's stored pubkey, and since `operator_xonly_pk != kickoff_data.operator_xonly_pk`, unconditionally returns `true` (malicious) [11](#0-10) , causing verifiers to challenge/eventually disprove the honest operator's legitimate reimbursement attempt.

No existing guard prevents this: `is_deposit_valid`, `is_profitable`, `SECP.verify_schnorr` (which only validates the *existing* signature over its committed data, not the uncommitted outputs), and the presigned transaction graph never re-validate that the OP_RETURN pubkey belongs to whoever actually funded output 0.

### Impact Explanation
The honest operator who genuinely fronted BTC to the withdrawing user (output 0) is permanently and irrecoverably blocked from any Reimburse path for that deposit, and any kickoff they later broadcast is flagged malicious and can be challenged/Disproved, burning their kickoff collateral path. This is repeatable per-withdrawal against any operator, for the cost of the attacker having to self-fund the payout output amount (plus fees) once per attack — expensive per instance but directly causable at will by any unprivileged party who can observe/replace mempool transactions, matching the Critical category "an honest operator permanently unable to be reimbursed."

### Likelihood Explanation
Preconditions: an honest operator must be racing to front a withdrawal (a routine, expected operation), and the attacker must be able to get a competing spend of the same withdrawal UTXO mined instead of/before the honest operator's original broadcast (e.g., relay a higher-fee version, standard mempool/RBF dynamics) — no majority hashrate, verifier/aggregator privilege, or key compromise is required. The attacker's cost is bounded by the withdrawal payout amount plus fees (since they must self-fund output 0 to keep it byte-identical), making this a costly-but-fully-unprivileged griefing primitive, reproducible against every withdrawal/operator pair.

### Recommendation
Do not treat "whichever tx spent the withdrawal UTXO" as authoritative for attributing the payout to an operator. Either (a) require the operator to commit to the specific full payout txid (not just the OP_RETURN pubkey) during withdrawal preparation and only accept the mined tx if its txid matches a value pre-registered by an authenticated operator RPC call, or (b) change the user's payout signature to `AllPlusAnyoneCanPay`/`All` (or otherwise cover output 2) so the OP_RETURN operator-pubkey binding is cryptographically fixed by the signature and cannot be swapped without invalidating the user's signature.

### Proof of Concept
`cargo test` plan:
1. In a bitcoind regtest env, run the standard e2e helper to generate a withdrawal UTXO and its `SinglePlusAnyoneCanPay` signature (`generate_withdrawal_transaction_and_signature` in `core/src/test/common/setup_utils.rs`).
2. Have the "honest operator" call `Operator::withdraw` to build and sign (but not yet mine) a payout tx `honest_tx` with its own funding inputs and its own xonly pubkey in the OP_RETURN.
3. Construct `attacker_tx` reusing `honest_tx.input[0]` (same previous outpoint + witness) and `honest_tx.output[0]` verbatim; add the attacker's own funding UTXO(s)/signature(s) to cover the fee/output amount; set output 2's OP_RETURN to a freshly generated random `XOnlyPublicKey` not belonging to any registered operator.
4. Broadcast and mine `attacker_tx` instead of `honest_tx`; run block-sync so `update_finalized_payouts` processes it.
5. Assert: `db.get_payout_info_from_move_txid(...)` returns the attacker's random pubkey (not the honest operator's) — binding broken.
6. Assert: `PayoutCheckerTask::run_once` for the honest operator returns `Ok(false)` (never finds the unhandled payout).
7. Assert: calling `Verifier::is_kickoff_malicious` for the honest operator's subsequently-sent kickoff on this deposit returns `true`.
