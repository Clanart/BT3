Confirmed: there is no `removeSafeDirectory` function anywhere in the codebase — once a path is added to `safe.directory`, GitHub Desktop never removes it, even if the user removes/deletes the repository from the app.

### Title
Trust decision for `safe.directory` is bound only to a filesystem path, never to repository identity/content, allowing stale trust to authorize automatic hook execution for attacker-controlled content later placed at that path - (File: app/src/lib/git/config.ts)

### Summary
GitHub Desktop treats a Git repository as "trusted" purely based on whether its literal path string has been added to the global `safe.directory` git config entry via `addSafeDirectory()`. This trust flag is never re-validated against repository ownership, content, or identity, and is never revoked. Consequently, if an attacker can later control the content written to a path that was previously trusted by the user, Desktop will silently treat that new, attacker-controlled repository as safe and allow Git to execute repository-defined hooks/config without ever re-prompting the user, even though the underlying "value" that justified the original trust decision (the specific directory owner/content) has since changed. This mirrors the LiquidityGauge bug pattern: a privileged decision derived from a piece of state (VotingEscrow balance / directory ownership) is cached and never invalidated when that underlying state changes, letting the attacker reuse the stale privilege.

### Finding Description
`getRepositoryType()` detects an "unsafe" repository purely from Git's dubious-ownership error, which itself is suppressed once the path is present in `safe.directory`: [1](#0-0) 

The only way to clear the "unsafe" state is `addSafeDirectory()`, which does a literal `git config --global --add safe.directory <path>`: [2](#0-1) 

Both `AddExistingRepository` and `MissingRepository` invoke this function when the user clicks "Trust Repository", and both explicitly acknowledge in their own UI copy that trusting a directory means Git "may automatically execute files in the repository": [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

The broken invariant: `safe.directory` (and therefore Desktop's decision to run Git commands/hooks without warning) is keyed **only by the path string**, not by any identity/content of the repository that existed at that path when trust was granted (no inode, no remote URL binding, no content hash, no timestamp). Once added, the entry is global and permanent — there is no `removeSafeDirectory` call anywhere in the codebase, so the trust is never revoked even when the repository is removed from Desktop via `_removeRepository`, relocated, or replaced. Any future content written to that same path (e.g., a shared/network path, a reused temp/build directory, a directory recreated after uninstall, or a path an attacker with earlier write access seeded and the victim later reuses for a different clone) will be silently treated as trusted, and Desktop will run ordinary Git operations (`status`, `checkout`, `commit`, LFS filters, etc.) against it — all of which can trigger Git hooks (`post-checkout`, `pre-commit`, `smudge`/`clean` filters) defined in that directory's own `.git/hooks` or `.git/config`.

This is directly analogous to the LiquidityGauge issue: the "bonus" (Desktop's trust of a directory) is computed once from a transient piece of state (the directory's owner/content at grant time) and never re-evaluated or invalidated when that underlying state is swapped out — enabling an attacker to reuse the stale privileged state for their own benefit.

### Impact Explanation
If an attacker can arrange for their own Git repository content (including hook scripts or `.gitattributes`-driven filter commands) to occupy a filesystem path the victim previously trusted (e.g., a shared drive, mapped network directory, container-mounted path, or reused local folder), GitHub Desktop will execute ordinary Git plumbing/porcelain operations against that path without any renewed warning, and Git will run the attacker's hooks/filters with the victim's OS user privileges — this is arbitrary code execution outside of what the user consciously reviewed, consistent with the "unsafe" warning text Desktop itself displays ("Adding untrusted repositories may automatically execute files in the repository").

### Likelihood Explanation
Requires a scenario where a shared/reusable path previously marked trusted by the victim is later repopulated with attacker-controlled content (e.g., shared network shares, CI/build directories, or a path recycled for a different clone) — a plausible but not universal condition, since it depends on path reuse rather than a fully remote, single-click compromise. It does not require local malware, admin rights, or leaked credentials — only the ability to write to a shared/reused path the victim previously trusted, and the victim performing a normal Desktop action (open/refresh the repository).

### Recommendation
Bind the trust decision to the specific repository's identity in addition to its path — e.g., require re-confirmation if the resolved `.git` directory's origin remote/commit graph root differs from what was recorded when trust was granted, or scope `addSafeDirectory` acceptance to a stored fingerprint (e.g., first-commit SHA or `.git` directory inode) rather than a bare path string. At minimum, add a `removeSafeDirectory` call when a repository is removed from Desktop or relocated, so stale trust does not persist indefinitely for paths no longer associated with the reviewed content.

### Proof of Concept
1. Victim adds/clones a Git repository at a shared or reusable path `P` (e.g., a mapped network share) and, prompted by Desktop's "unsafe" warning, clicks "Trust Repository" — Desktop runs `git config --global --add safe.directory P`.
2. Victim later removes the repository from GitHub Desktop (`_removeRepository`) or the directory contents are cleared; no code path removes the `safe.directory` entry for `P`.
3. Attacker (who also has write access to path `P`, e.g., another user on the shared drive) writes a new Git repository at `P` containing a malicious `post-checkout` (or `smudge`) hook.
4. Victim re-adds/opens the repository at `P` in Desktop. `getRepositoryType()` no longer reports `kind: 'unsafe'` because `P` is already listed in `safe.directory`, so Desktop performs normal operations (e.g., a checkout during branch switch) without any prompt, causing Git to execute the attacker's hook under the victim's account.

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
