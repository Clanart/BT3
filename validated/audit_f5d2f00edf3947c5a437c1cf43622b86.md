### Title
Webhook HMAC verification does not bind to the shop-domain identity used for downstream tenant scoping, enabling cross-shop webhook forgery - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` cryptographically validates only `request.raw_post` against the app's shared secret, while the tenant identity used to route/process the webhook (`shop_domain`) is read directly from the unauthenticated `HTTP_X_SHOPIFY_SHOP_DOMAIN` header, which is not covered by the HMAC. This is structurally the same root cause as the reported bug: the code that performs identity-sensitive verification (HMAC / withdrawal request creation) is decoupled from the code that later records/uses the identity for the sensitive action (shop domain used for tenant scoping / withdrawal owner). Because Shopify signs webhooks using a single app-level secret shared across every shop that installs the app (the same secret used by `ShopifyApp.configuration.secret`), any merchant that installs the app can obtain a validly-signed webhook body for their own shop, then replay that exact body with a *different* `X-Shopify-Shop-Domain` header value to the app's webhook endpoint.

### Finding Description
`hmac_valid?` computes/compares HMAC-SHA256 over `data = request.raw_post` only: [3](#0-2) 

`verify_request` calls this and only rejects the request if the HMAC fails; if it passes, `shop_domain` — sourced purely from the request header — is trusted for downstream tenant identification: [4](#0-3) 

The gem's own generator templates for custom webhook jobs demonstrate exactly this trust pattern: they take the (unverified) `shop_domain`, look up the tenant `Shop` record by it, and then execute app business logic within that shop's authenticated session: [5](#0-4) [6](#0-5) 

and the documentation explicitly instructs implementers to pass this same unverified value into job processing: [7](#0-6) 

Because the HMAC secret (`ShopifyApp.configuration.secret`) is the app's single API secret — identical for every shop that installs the app — any merchant/attacker who installs the app can generate a body+HMAC pair that is valid for the shared secret using their own shop's legitimate webhook delivery, then re-POST that same `(body, hmac)` pair to the webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to point at a victim shop. `verify_request` will still pass (it never inspects the header), and the downstream job resolves `shop = Shop.find_by(shopify_domain: attacker_supplied_header)`, executing attacker-controlled webhook body content within the victim shop's `with_shopify_session` context/access token — analogous to the C-02 pattern where the entity performing the verified action (creating the withdrawal / accepting the signed payload) is not bound to the entity later attributed as the actor (owner / tenant).

### Impact Explanation
An attacker who is or becomes a legitimate merchant of the app (a normal, unprivileged onboarding step, not requiring any secret leak) can forge webhook attribution to any other shop that has installed the app, causing app business logic to run against a victim shop's `Shop` record/session using attacker-controlled payload content. Depending on what webhook-driven logic app developers build (as instructed by the gem's own generator templates and docs), this can result in cross-shop data corruption, unauthorized actions performed with the victim's access token, or cross-tenant confusion — a direct instance of the "accepted forged signed request" / "cross-shop access" class.

### Likelihood Explanation
Likelihood is high: the only prerequisite is installing the app on any shop (a normal unprivileged action available to anyone), which yields legitimately HMAC-valid webhook bodies signed with the same shared secret used to validate all shops' webhooks. No secret leakage, no dependency bug, and no privileged access is required — only manipulation of an unauthenticated, unsigned header (`X-Shopify-Shop-Domain`) that the framework's own documented pattern trusts for tenant scoping.

### Recommendation
Do not use the unauthenticated `X-Shopify-Shop-Domain` header (or any header/field outside the HMAC-covered body) as the tenant identity for downstream processing. Either (a) include the shop domain in the HMAC-covered payload and verify it as part of `verify_request`, or (b) bind webhook shop attribution to data that is cryptographically covered by the signature (e.g., derive shop identity solely from fields inside `raw_post` that are HMAC-protected), and reject requests where the header-derived shop domain does not match the payload-derived one.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal, unprivileged flow).
2. Shopify delivers a legitimate webhook to the app's endpoint: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, HMAC(secret, B))` and re-sends a POST to the same webhook endpoint with identical body `B` and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `WebhookVerification#verify_request` → `hmac_valid?(B)` succeeds (secret is shared across all shops), so the request is accepted.
5. Custom/generated webhook job code executes `Shop.find_by(shopify_domain: "victim-shop.myshopify.com")` and runs attacker-controlled body `B` logic inside `shop.with_shopify_session`, i.e., under the victim shop's access token/session context.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
