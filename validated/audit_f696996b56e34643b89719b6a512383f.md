## Title
FieldMask JSON Serialization Path-Delimiter Smuggling via Unescaped Comma in `google.protobuf.FieldMask.paths` — (File: `src/google/protobuf/util/field_mask_util.cc`, `java/util/src/main/java/com/google/protobuf/util/FieldMaskUtil.java`, `python/google/protobuf/internal/field_mask.py`)

## Summary
`google.protobuf.FieldMask.paths` is an ordinary `repeated string` field with no character restrictions at the wire-format level. An ordinary client can send a bounded, valid binary Protobuf (or ProtoJSON, via the `[...]` path list) message containing a single path string that itself contains a literal comma (e.g. `"foo,admin_only_field"`). This message parses successfully with the public parse APIs (`ParseFromString`/`MergeFrom`). When that `FieldMask` is later serialized back to ProtoJSON/string form by `FieldMaskUtil::ToJsonString` (C++), `FieldMaskUtil.toJsonString` (Java), or `FieldMask.ToJsonString` (Python) — all of which join paths with `,` via string concatenation without checking that individual path elements are comma-free — the single attacker-controlled path is silently smuggled into what looks like **two independent paths**. Re-parsing that string (`FromJsonString`, used pervasively for `update_mask` handling in APIs) yields two separate mask entries instead of one, altering the field-mask's semantics without any error.

## Finding Description
The invariant that fails here mirrors OpenMeter's bug exactly: a stored/attacker-controlled string value is later assembled into a structured, delimiter-separated expression via naive string concatenation, and the code trusts that the value cannot contain the delimiter character used to build that expression.

- `FieldMaskUtil::SnakeCaseToCamelCase` (`src/google/protobuf/util/field_mask_util.cc:52-80`) only rejects uppercase letters and rejects non-lowercase characters immediately following an underscore. Any other character — including a literal `,` — falls into the `else` branch and is copied through unchanged: [1](#0-0) 
- `FieldMaskUtil::ToJsonString` then joins the per-path camelCase strings with `,` via simple concatenation, with no check that a path is free of `,`: [2](#0-1) 
- The same unguarded join pattern exists in Java (`String.join(FIELD_PATH_SEPARATOR, paths)`) and Python (`','.join(camelcase_paths)`): [3](#0-2) [4](#0-3) 
- On the reverse (parse) direction, `FieldMaskUtil::FromString`/`FromJsonString` and the equivalents in Java/Python/C++ ProtoJSON parser (`ParseFieldMask` in `src/google/protobuf/json/internal/parser.cc:991-1027`) split unconditionally on `,`, with no way to distinguish "one path containing a literal comma" from "two paths": [5](#0-4) [6](#0-5) 

This means the round trip binary-parse → (store/pass through app logic) → `ToJsonString`/JSON-serialize → `FromJsonString`/JSON-parse is lossy in a security-relevant way: a single path smuggles in an extra path. Because `FieldMask` is the standard mechanism many gRPC/REST APIs use to gate which fields a caller is permitted to read or update (`update_mask`), a consuming application that (a) validates a caller-supplied field-mask against an allow-list of writable fields as one array of strings, then (b) round-trips it through `ToJsonString`/`FromJsonString` (a very common pattern when re-serializing masks for logging, forwarding to another service, or storing/re-loading) can end up with a different, unvalidated path being introduced, or a validated single path effectively being split so an authorization check that matched the whole string no longer matches the split components (or vice versa: a benign string containing commas is unintentionally expanded into multiple field paths that get applied to `MergeMessage`/`Trim` operations).

## Impact Explanation
This is a data-integrity/authorization-adjacent issue, analogous in kind (not degree) to the OpenMeter CVE: an attacker-controlled string, valid and unremarkable under Protobuf's own wire format, is later assembled with plain string concatenation into a different textual encoding whose grammar uses the same character the attacker controls as a structural delimiter, and the split/parse code has no way to tell the difference. Concretely:
- `FieldMaskUtil::ToCanonicalForm`, `IsValidFieldMask`, and any application-side allow-list check that operates on the pre-serialization `repeated string paths` can pass, while the serialized/re-parsed representation silently contains additional or reinterpreted paths.
- Any code that uses `FieldMaskUtil::MergeMessageTo` / `TrimMessage` / `Union`/`Intersect` after a JSON round trip could apply the mask to unintended fields.
- Severity is capped at Medium/Low-High depending on the consuming application's exact usage; Protobuf itself does not enforce or document that `FieldMask.paths` elements must be comma-free, and there is no memory-safety or RCE impact — only semantic corruption of a value used for access control in typical consuming applications (comparable to OpenMeter's "insert into WITH map(...) via string concatenation" root cause, but for a field-mask expression instead of a SQL/ClickHouse expression).

## Likelihood Explanation
High likelihood of reachability: an ordinary client only needs to supply a `FieldMask.paths` repeated-string field containing a comma via a normal, bounded binary Protobuf parse or ProtoJSON array-of-strings parse (`["foo,bar"]` is a perfectly valid ProtoJSON path list entry, since JSON array parsing doesn't split on commas — only the *string-form* ProtoJSON `"foo,bar"` serialization/parsing does). No malformed input, no huge payloads, no privileged access is required. The only requirement for exploitation is that the consuming application performs the very common validate-then-serialize-then-later-reparse pattern, which is outside Protobuf's control but is the expected use of these public utility APIs (`FieldMaskUtil`, `JsonFormat`, `MessageToJson`).

## Recommendation
- In `FieldMaskUtil::SnakeCaseToCamelCase` / `CamelCaseToSnakeCase` (C++), `FieldMaskUtil.toJsonString`/`fromJsonString` (Java), and `FieldMask.ToJsonString`/`FromJsonString` (Python), explicitly reject (or escape) any path component that contains a literal `,` before joining, returning `false`/throwing an error rather than silently producing an ambiguous joined string.
- Add the same character-set validation used by `ParseFieldMask` (digits, lowercase letters, `.`) to the *serialization* direction as well, so `ToJsonString` fails loudly instead of allowing invalid characters through when `allow_legacy_nonconformant_behavior` is not set.
- Document in `field_mask.proto` / the well-known-type contract that `paths` entries must not contain the ProtoJSON path separator (`,`), and enforce it in `IsValidPath`/`GetFieldDescriptors`.

## Proof of Concept
1. Construct a `FieldMask` message with a single path containing a comma, using an ordinary binary `SerializeToString`/`ParseFromString` round trip (no special encoding needed — `repeated string` accepts any UTF-8 bytes):
   - `FieldMask{ paths: ["foo,secret_field"] }` — binary parse succeeds without error.
2. Call `FieldMaskUtil::ToJsonString(mask, &out)` (C++) — per `src/google/protobuf/util/field_mask_util.cc:100-114`, `SnakeCaseToCamelCase` passes the comma through unchanged, producing `out == "foo,secretField"`.
3. Call `FieldMaskUtil::FromJsonString("foo,secretField", &mask2)` — the string is split on `,` giving `mask2.paths() == ["foo", "secret_field"]`, i.e. two paths instead of the original single path `"foo,secret_field"`.
4. This demonstrates the smuggling: any application code that validated `mask.paths()[0] == "foo,secret_field"` against an allow-list before step 2, but re-derives the effective mask from the JSON string after step 3, ends up operating on the unintended, split path set `["foo", "secret_field"]`.

I was not able to execute this proof of concept in a live build within this session (no code-execution tool available); the trace above is derived directly from reading the cited source, and the character-set logic in `SnakeCaseToCamelCase`/`ParseFieldMask` confirms the asymmetry between serialization (no comma check) and parsing (unconditional split on comma).

bool FieldMaskUtil::SnakeCaseToCamelCase(absl::string_view input,
                                         std::string* output) {
  output->clear();
  bool after_underscore = false;
  for (char input_char : input) {
    if (input_char >= 'A' && input_char <= 'Z') {
      // The field name must not contain uppercase letters.
      return false;
    }
    if (after_underscore) {
      if (input_char >= 'a' && input_char <= 'z') {
        output->push_back(input_char + 'A' - 'a');
        after_underscore = false;
      } else {
        // The character after a "_" must be a lowercase letter.
        return false;
      }
    } else if (input_char == '_') {
      after_underscore = true;
    } else {
      output->push_back(input_char);
    }
  }
  if (after_underscore) {
    // Trailing "_".
    return false;
  }
  return true;
}

bool FieldMaskUtil::ToJsonString(const FieldMask& mask, std::string* out) {
  out->clear();
  for (int i = 0; i < mask.paths_size(); ++i) {
    absl::string_view path = mask.paths(i);
    std::string camelcase_path;
    if (!SnakeCaseToCamelCase(path, &camelcase_path)) {
      return false;
    }
    if (i > 0) {
      out->push_back(',');
    }
    out->append(camelcase_path);
  }
  return true;
}

absl::Status ParseFieldMask(JsonLexer& lex, const Desc<Traits>& desc,
                            Msg<Traits>& msg) {
  absl::StatusOr<LocationWith<MaybeOwnedString>> str = lex.ParseUtf8();
  RETURN_IF_ERROR(str.status());
  auto paths = str->value.AsView();

  // The special case of the empty string is not handled correctly below,
  // because StrSplit("", ',') is [""], not [].
  if (paths.empty()) {
    return absl::OkStatus();
  }

  // google.protobuf.FieldMask has a single field with number 1.
  auto paths_field = Traits::MustHaveField(desc, 1);
  for (absl::string_view path : absl::StrSplit(paths, ',')) {
    std::string snake_path;
    // Assume approximately six-letter words, so add one extra space for an
    // underscore for every six bytes.
    snake_path.reserve(path.size() * 7 / 6);
    for (char c : path) {
      if (absl::ascii_isdigit(c) || absl::ascii_islower(c) || c == '.') {
        snake_path.push_back(c);
      } else if (absl::ascii_isupper(c)) {
        snake_path.push_back('_');
        snake_path.push_back(absl::ascii_tolower(c));
      } else if (lex.options().allow_legacy_nonconformant_behavior) {
        snake_path.push_back(c);
      } else {
        return str->loc.Invalid("unexpected character in FieldMask");
      }
    }
    Traits::SetString(paths_field, msg, snake_path);
  }
