## Finding: Webhook `shop_domain` is not covered by HMAC verification, allowing shop-domain spoofing on webhook delivery

### Title
Unauthenticated `shop_domain` header trusted for webhook shop-scoping despite HMAC only covering the request body - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
This maps to the same root-cause pattern as the reported bug: a value that drives security/business-critical routing (`acceptedCurrency`/`offerCurrency` in the Solidity report; `shop_domain` here) is never cross-checked against the value that was actually authenticated by the signature/HMAC before being trusted downstream.

### Finding Description
`ShopifyApp::WebhookVerification#verify_request` computes HMAC validity only over `request.raw_post`: [1](#0-0) 

The module also exposes a `shop_domain` helper that simply reads the `X-Shopify-Shop-Domain` header, with no cross-check against anything that was actually signed: [2](#0-1) 

`hmac_valid?` itself, defined in `PayloadVerification`, only ever hashes `data` (the raw body) with the app's shared client secret; the shop domain header plays no part in the HMAC computation: [3](#0-2) 

The gem's own documentation instructs integrators to use this unauthenticated `shop_domain` value directly to key background job processing for the webhook payload: [4](#0-3) 

Because the HMAC secret (`ShopifyApp.configuration.secret`) is the app's single client secret, shared across every shop that installs the app, any merchant who installs the app receives their own legitimately-HMAC-signed webhook deliveries. That merchant can replay a captured `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value. `verify_request` still passes (it never inspected the header), and the resulting `shop_domain` handed to the job/controller is attacker-controlled and disconnected from the shop that actually owns the signed body — exactly analogous to `acceptOffer` trusting `offers[i].request.offerCurrency` instead of validating it against `acceptedCurrency`.

### Impact Explanation
An unrelated, low-privileged merchant who has merely installed the target app can cause webhook-triggered jobs to be attributed to/executed against a different shop's domain (e.g., triggering `shop/redact`, `app/uninstalled`, or custom topic jobs keyed by `shop_domain` for a victim shop), because the shop identity is never bound to the HMAC-verified payload. This can lead to cross-shop data confusion or unwanted state changes scoped to a shop the attacker does not control.

### Likelihood Explanation
Medium: it requires the attacker to have installed the app themselves (to receive at least one genuine signed webhook) and to know/guess a victim shop's `myshopify.com` domain, but no secret material is required — the header is fully unauthenticated and the pattern is explicitly documented as the recommended integration approach.

### Recommendation
Bind the trusted shop identity to data that is actually covered by the HMAC (e.g., derive `shop` strictly from the verified `raw_post` body via `ShopifyAPI::Webhooks::Request`/`parsed_body`, not from the `X-Shopify-Shop-Domain` header), or explicitly validate that the header's shop matches the shop embedded in the verified payload before using it for any job dispatch or state change — mirroring the fix recommended for `ListingRequest`/`OfferRequest`: validate the "currency"-equivalent field against the trusted/authenticated source before acting on it.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends the attacker a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
3. Attacker replays `POST /webhooks` with the same body `B` and same valid HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)` which succeeds (body/HMAC pair is genuinely valid) — see [5](#0-4) .
5. The app-level handler (as documented) calls `shop_domain`, getting `victim-shop.myshopify.com`, and dispatches a job scoped to that shop using attacker-supplied body content — see [6](#0-5) .

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
