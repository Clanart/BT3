## Analysis

The report's underlying broken invariant is: **a low-trust actor can unilaterally cause a high-trust action (granting/binding privileged credentials) with no independent verification step**, and the client's own mitigating claim ("only a governed, voting-based entity can invoke this") is exactly the kind of independent-check that's missing in the Desktop analog below.

In GitHub Desktop, the credential-helper trampoline decides whether an unknown host should be treated as a **GitHub Enterprise (GHE) host** — and therefore be offered an OAuth/enterprise sign-in flow that binds a new `Account` to that host — based on data the *remote server itself supplies* during authentication, with no independent corroboration.

`getEndpointKind()` classifies an endpoint as `'enterprise'` purely because the git server returned a `WWW-Authenticate` header containing `realm="GitHub"`: [1](#0-0) 

That classification then drives `getCredential()` to trigger a GitHub sign-in prompt for the attacker's own host when no account is stored for it yet: [2](#0-1) 

Finally, `promptForGitHubSignIn()` uses the *credential URL's own origin* (attacker-controlled) to kick off the enterprise sign-in flow and bind it as the sign-in endpoint: [3](#0-2) 

### Title
Attacker-Controlled `WWW-Authenticate` Header Triggers Unverified GitHub Enterprise Sign-In / Account Binding - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
Desktop's credential helper decides an unknown git remote is a "GitHub Enterprise" host solely from a `WWW-Authenticate: realm="GitHub"` HTTP header returned by that remote during a normal `fetch`/`clone`/`push`. This value is fully attacker-controlled (it comes from the server/proxy response), yet Desktop uses it, unchecked, to launch the GitHub Enterprise sign-in flow and bind the resulting account's endpoint to the attacker's own host — the equivalent of a low-trust "ward" self-certifying a new privileged binding without any independent verification.

### Finding Description
`getEndpointKind()` inspects credential-fill requests forwarded by git's credential protocol. If the endpoint is not already known to be `dotcom`/`ghe.com`/`gist`, it falls back to scanning the raw `wwwauth[...]` entries that were captured from the HTTP response of the remote/proxy Desktop just talked to: [4](#0-3)  A server realm string of `"GitHub"` is enough to make Desktop treat an arbitrary host as `'enterprise'`, before it even attempts the network-based `isGitHubHost()` check.

`getCredential()` then uses that classification directly: for any `endpointKind !== 'generic'` host with no existing stored account, it calls `ui.promptForGitHubSignIn(endpoint)`: [5](#0-4) 

`promptForGitHubSignIn()` takes the origin straight from the (attacker-supplied) credential URL and immediately begins the enterprise sign-in flow bound to it, with no comparison to any accounts already trusted by the user, no TLS/identity pinning, and no confirmation that the host is a real GHE instance beyond the header it sent about itself: [6](#0-5) 

This mirrors the report's broken invariant precisely: a value that should require independent, higher-trust arbitration (i.e., "is this really a GitHub host that deserves an OAuth binding?") is instead self-asserted by the untrusted party (the remote/proxy) and accepted at face value.

### Impact Explanation
A malicious git server or a MITM proxy for a "generic" remote can, purely by returning a crafted `WWW-Authenticate` header during a routine `git fetch`/`push`/`clone` performed by Desktop, cause Desktop to:
- Present an "enterprise sign-in" UI scoped to the attacker's arbitrary origin (`beginEnterpriseSignIn` + `setSignInEndpoint(origin)`), and
- On completion of that flow, persist a new `Account` bound to the attacker's host in `AccountsStore`.

Once bound, that endpoint is subsequently treated by Desktop's account-matching logic (`findGitHubTrampolineAccount`, `getAccountForRepository`) as a legitimate first-party GitHub endpoint for future operations, and Desktop will offer/attach that account's credentials to it (`credWithAccount`). This falls squarely under "unauthorized OAuth or account binding" from the valid-impact list, and is reachable purely from an attacker-controlled git remote/proxy response.

### Likelihood Explanation
The trigger requires only that the user perform an ordinary git operation (fetch/push/clone) against a remote or proxy the attacker controls (or a MITM position on an HTTP, non-pinned remote) — no unusual user action, no local access, and no prior credential compromise. The realm-string heuristic in `getEndpointKind` is a purposeful fast-path ("happy-path") to avoid a network round trip, and it runs before the safer `isGitHubHost()` check, making it the primary decision point for hosts that haven't been seen before.

### Recommendation
Do not classify an unknown endpoint as GitHub/GHE from a self-reported `WWW-Authenticate` realm alone. Require the authoritative `isGitHubHost()` check (or equivalent independently-verified signal, e.g., a successful `/meta` or well-known GitHub API probe over the endpoint) before offering the enterprise sign-in prompt, and never bind a new account/OAuth grant to a host based solely on data the host itself supplied during the credential exchange.

### Proof of Concept
1. Set up a small HTTP git-proxy/server for a remote used with Desktop (e.g., a "generic" HTTPS remote such as `https://malicious.example.com/foo.git`).
2. Configure it to answer authentication challenges with `WWW-Authenticate: Basic realm="GitHub"`.
3. In Desktop, add/clone this remote and trigger a fetch requiring authentication.
4. Observe `getEndpointKind()` returns `'enterprise'` for `malicious.example.com` purely from step 2's header (`app/src/lib/trampoline/trampoline-credential-helper.ts:157-165`), and that `getCredential()` calls `ui.promptForGitHubSignIn('https://malicious.example.com/...')` (same file, lines 109-125), launching an enterprise sign-in bound to the attacker's origin (`app/src/lib/trampoline/trampoline-ui-helper.ts:87-93`).

**Note on confidence:** I was not able to trace the full downstream `AccountsStore` persistence code path within the tool budget available, so the exact post-sign-in account-binding mechanics (and whether any later check invalidates such "enterprise" accounts) could not be fully verified here; a Devin session with full repository access would be needed to confirm end-to-end persistence and any existing mitigations in `AccountsStore`/`API.fromAccount`.

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }
