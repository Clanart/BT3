### Title
Fee/weight calculation omits the OP_RETURN data output, producing an underpaid fee and an underestimated weight check - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` builds the final output vector `tx_outs` including the attacker-influenced `OP_RETURN` data output, but then calls `calculate_weight_vbytes(tx_ins.len(), payments, ...)` passing `payments` — which does **not** contain the data output. The resulting `vbytes`, `needed_fee`, the `TooLowFee` relay-minimum check, and the `MAX_STANDARD_TX_WEIGHT` check are all computed on a transaction smaller than the one actually signed and broadcast, so the real fee rate is lower than `fee_per_vbyte` and can fall below the network minimum relay fee.

### Finding Description
In `SignableTransaction::new`, the data output is pushed onto `tx_outs` (networks/bitcoin/src/wallet/send.rs:194-202), yet the size estimation uses `payments`:

- `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` (send.rs:204)
- `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (send.rs:226)
- `needed_fee = fee_per_vbyte * vbytes` (send.rs:206)
- The minimum relay fee check uses the same underestimated `vbytes` (send.rs:211)
- The standardness check uses the underestimated `weight` (send.rs:241)

`calculate_weight_vbytes` only expands `payments` plus optional change into a dummy `Transaction` (send.rs:85-99), so an `OP_RETURN` output of up to ~89 bytes (80-byte push + script overhead) is entirely uncounted. This mirrors the VTVL bug class: a fee computed with one formula/units is then charged against a different real quantity, causing an incorrect amount of funds to be committed.

### Impact Explanation
The signed transaction commits a fee of `input_sat - payment_sat - change` equal to `needed_fee`, which was priced for a smaller transaction. The effective sat/vbyte rate is `needed_fee / actual_vsize < fee_per_vbyte`. When `fee_per_vbyte` is at or near the minimum relay rate, the `TooLowFee` guard passes on the underestimated vbytes while the actual transaction is below `DEFAULT_MIN_RELAY_TX_FEE` — it will be rejected/not relayed, leaving spent inputs' funds locked in an unconfirmable, unspendable transaction (nodes must re-sign or abandon the plan). Even when relayable, the processor/user pays a systematically lower fee rate than requested, and `needed_fee()` misreports the true cost. A sufficiently large `data` payload can also push the real weight past `MAX_STANDARD_TX_WEIGHT` despite the check passing.

### Likelihood Explanation
`data` is a public, caller-supplied input to `SignableTransaction::new` — Serai itself uses the OP_RETURN output to carry `Shorthand` protocol messages (e.g., `tests/full-stack/src/tests/mint_and_burn.rs` pushes `Shorthand::transfer(...)` via `ScriptBuf::new_op_return`). Any unprivileged user causing a transaction to be constructed with a data payload triggers the undercount; the miscalculation scales with payload size, no collusion or privileged access required.

### Recommendation
Pass the actual output set to `calculate_weight_vbytes` — i.e., build the dummy transaction from `tx_outs` (which already includes the OP_RETURN output) rather than `payments`, in both call sites (send.rs:204 and send.rs:226), or add the data output inside `calculate_weight_vbytes`. This ensures `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction that is actually signed and broadcast.

### Proof of Concept
```rust
// networks/bitcoin context
// One input worth `payment + fee`, one payment, 80-byte data payload
let data = vec![0u8; 80];
let tx = SignableTransaction::new(
    vec![input],                       // any ReceivedOutput
    &[(payment_script, 10_000)],
    None,
    Some(data),                        // OP_RETURN output added to tx_outs
    fee_per_vbyte,                     // e.g. 1 sat/vbyte
).unwrap();

// tx.tx contains the extra OP_RETURN output (~89 bytes) but
// needed_fee was priced on vbytes WITHOUT that output.
let actual_vsize = tx.transaction().vsize() as u64;
assert!(tx.needed_fee() < fee_per_vbyte * actual_vsize);
// Effective fee rate = needed_fee / actual_vsize < fee_per_vbyte;
// at fee_per_vbyte = 1 and ~89 unaccounted bytes, the real rate
// is ~0.5 sat/vbyte — below DEFAULT_MIN_RELAY_TX_FEE (1000 sat/kvB),
// so the TooLowFee check passed yet the TX is non-standard for relay.
```
Root cause is concrete: `calculate_weight_vbytes` reconstructs outputs solely from `payments` (send.rs:85-93) while the real transaction uses `tx_outs` which additionally contains the OP_RETURN output (send.rs:194-202, 246-250). [1](#0-0) [2](#0-1) [3](#0-2)
