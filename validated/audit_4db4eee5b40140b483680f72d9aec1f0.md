### Title
ReceivedOutput deserialization accepts an attacker-controlled spend offset unbound to the output, yielding unspendable "received" funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes three independent fields — a scalar `offset`, a `TxOut`, and an `OutPoint` — with no check that `key + offset*G` actually produces the `script_pubkey` contained in `output` [1](#0-0) . This is an object-reference-style flaw: the pairing between the spend authority (the offset) and the claimed output is asserted by the input bytes rather than verified, mirroring the CVE-2020-27662 class where an attacker-supplied reference grants access to an unrelated object.

### Finding Description
The `Scanner` maintains an authoritative `scripts: HashMap<ScriptBuf, Scalar>` map binding each watched `script_pubkey` to the offset that spends it [2](#0-1) . When outputs are discovered honestly via `scan_transaction`, the offset is looked up from that map and is therefore guaranteed correct [3](#0-2) . However, `ReceivedOutput` also exposes a public deserialization path that accepts arbitrary bytes: `offset` is read via `Secp256k1::read_F` and the `TxOut`/`OutPoint` are consensus-decoded, then returned as a valid `ReceivedOutput` with zero cross-validation. Any consumer that treats a deserialized `ReceivedOutput` as a spendable received output (using `offset()` to re-key the threshold keys and `value()` for accounting) will accept an output whose declared offset does not correspond to its `script_pubkey`.

### Impact Explanation
Spending requires the threshold signature to be produced under keys offset by `output.offset`. If an attacker supplies a `ReceivedOutput` naming a real on-chain output (or any `TxOut`) paired with an incorrect or attacker-chosen `offset`, downstream code reports the funds as received and attempts to spend with the wrong tweaked key — the resulting signature is invalid for the output's actual script path, or signs for an unrelated key entirely. This produces funds reported received that are not spendable, and can wedge fee/change accounting that trusts `value()`. Conversely, an offset chosen to collide with a different registered script can misattribute outputs across offsets (the code itself documents that offsets are surjective and order-dependent, and that arbitrary offsets "may introduce a script path into the output, allowing the output to be spent by satisfaction of an arbitrary script") [4](#0-3) .

### Likelihood Explanation
Reachability requires untrusted bytes to reach `ReceivedOutput::read` — i.e., any deployment that persists or transports `ReceivedOutput`s through storage or messages an unprivileged party can influence (the threat model already admits untrusted bytes fed to `read_*` APIs). No key material, collusion, or privileged position is needed; the attacker only crafts a serialization. The flaw is structural (missing validation), not probabilistic.

### Recommendation
Either remove the public `ReceivedOutput::read` path or bind the deserialized fields: after reading, recompute `p2tr_script_buf(key + G*offset)` (requiring the scanner's base key, or storing the expected `script_pubkey`) and reject inputs where it does not equal `output.script_pubkey`. At minimum, document that deserialized `ReceivedOutput`s must be re-validated against `Scanner::scripts` before being treated as spendable.

### Proof of Concept
1. Let the wallet's base key be `K`, with registered script `S = p2tr(K + o·G)` for honestly registered offset `o`.
2. Attacker constructs `ReceivedOutput` bytes as: `F::write(o') || serialize(TxOut{value: V, script_pubkey: S}) || serialize(outpoint)`, where `o' != o` (e.g., `o' = o + 1` or an offset introducing an arbitrary script path).
3. `ReceivedOutput::read` succeeds — no check links `o'` to `S` [1](#0-0) .
4. Wallet accounting credits `V` sats as received; spending re-keys threshold shares by `o'`, producing a signature invalid for `S`. Funds are reported received but are unspendable.
