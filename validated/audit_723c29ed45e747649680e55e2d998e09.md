Based on my investigation, I found a genuine analog to the reported pattern — not an unused parameter, but a structurally identical flaw: **a message handler validates only part of the cross-chain sender identity, omitting a check that should gate a privileged action**, in `HostManager.onAccept()`.

### Title
Governance/host-management callback authenticates only the source chain, not the sending module - ([File: evm/src/core/HostManager.sol])

### Summary
`HostManager.onAccept()` is the ISMP callback that executes privileged host-management actions (`Withdraw` bridge revenue, `SetHostParam` reconfiguration) on behalf of cross-chain governance. It checks only that the incoming request's `source` chain equals the configured Hyperbridge coprocessor chain, but never checks `request.from` — the address/module identifier of the specific sender on that source chain that dispatched the request. [1](#0-0) 

### Finding Description
`onAccept` is restricted to calls from the local `IHost` (`restrict(_params.host)`), which is correct and prevents direct spoofing. However, once inside, the only sender-authentication check performed is:

```solidity
if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();
``` [2](#0-1) 

This validates the **chain** the message came from, but not **which module/account on that chain** dispatched it. The body is then decoded and dispatched directly into privileged host functions:

```solidity
IHostManager(_params.host).withdraw(withdrawParams);
...
IHostManager(_params.host).updateHostParams(hostParams);
``` [3](#0-2) 

This mirrors the external report's core defect class: a parameter that carries identity/authorization information relevant to the interface contract (`evmCallScript`/`from`) is present in the message struct but is not consulted by the implementation, even though the function goes on to perform a state-changing/privileged action (unlike the Aragon `canForward()` which is a pure view). Here the consequence is worse than the original report, because `onAccept` **does** mutate protocol state (fee withdrawal destination, host parameters) yet skips authenticating the specific sender identity carried in the very struct it receives.

### Impact Explanation
If any account or pallet on the Hyperbridge coprocessor chain (not just the intended governance/treasury module) can cause an ISMP POST request to be dispatched with `to` set to this `HostManager` contract's address, the `source` check alone is satisfied, and the message will be decoded and forwarded into `withdraw()`/`updateHostParams()` on the `EvmHost`. This is exactly the "cross-chain admin or host-management effects reachable through... wrong module bindings" scenario called out in the impact gate — it can lead to unauthorized withdrawal of bridge/relayer fee revenue or unauthorized mutation of host parameters (fee token, uniswap router, challenge periods, etc.), i.e., fund loss and unauthorized execution.

### Likelihood Explanation
Exploitability depends on whether the Hyperbridge coprocessor chain restricts which of its own pallets/accounts are permitted to dispatch ISMP requests destined for this specific module id/address (a fact internal to the Substrate-side runtime that I could not fully verify within the available search budget). If dispatch to arbitrary destination `to` addresses is available to any account with an ISMP-dispatch-capable pallet on the coprocessor chain (not requiring a malicious relayer, prover, or leaked key — just an unprivileged account able to invoke a generic messaging/dispatch extrinsic), the missing `request.from` check makes this directly and permissionlessly exploitable. I was unable to confirm the coprocessor-side authorization scope for outbound dispatch before running out of tool iterations, so this should be verified against the pallet responsible for emitting governance/host-management requests.

### Recommendation
Add an explicit check on `request.from` in `HostManager.onAccept()`, comparing it against a configured, admin-set governance module identifier (analogous to how `EvmHost`/other apps validate module bindings), in addition to the existing `request.source` chain check, before decoding and forwarding to `withdraw()`/`updateHostParams()`.

### Proof of Concept
1. Identify (or, if unrestricted, use) any account/pallet on the Hyperbridge coprocessor chain capable of dispatching an ISMP POST request with `to = HostManager` address on the target EVM chain.
2. Craft `body = abi.encodePacked(uint8(OnAcceptActions.Withdraw), abi.encode(WithdrawParams{...attacker-controlled...}))`.
3. Have the request relayed and proven through the normal `IHandler`/`IHost` flow — this succeeds because proof verification only attests that the message was committed on the `source` chain, not which module on that chain authored it.
4. `HostManager.onAccept()` passes its `request.source.equals(hyperbridge())` check (true, since it genuinely came from the coprocessor chain) and forwards attacker-supplied `WithdrawParams` into `IHostManager(_params.host).withdraw(...)`, without ever checking `request.from`. [1](#0-0)

```text
    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
```
