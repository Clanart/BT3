### Title
Unbounded aggregate `Fees` values in `WombatStaking` cause underflow revert in `_sendRewards`, freezing WOM/bonus reward distribution - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking.addFee()` and `setFee()` each validate that a single fee's `_value` is below `DENOMINATOR`, but no function ever validates that the sum of all active fees (`totalFee`) stays below `DENOMINATOR`. `_sendRewards()` iterates over every active fee and repeatedly subtracts `feeAmount` from a running `_amount` (`_amount -= feeAmount`). If the cumulative fee value ever reaches or exceeds 100% (`DENOMINATOR`), this loop underflows and reverts, exactly mirroring the Basket.sol `handleFees()` bug where an unchecked accumulated percentage causes `BASE - feePct` to underflow.

### Finding Description
`addFee()` only checks the newly added value in isolation: [1](#0-0) 

`setFee()` similarly only bounds the single updated value, and freely lets `totalFee` grow via `totalFee = totalFee - fee.value + _value`: [2](#0-1) 

Neither function checks that `totalFee` (the sum of all active fee percentages) stays under `DENOMINATOR`. The dangerous consumption of this value happens in `_sendRewards()`, which loops over every active fee and subtracts each `feeAmount` from a running `_amount`: [3](#0-2) 

If, across multiple `addFee`/`setFee` calls (each individually valid, since each is `< DENOMINATOR`), the sum of all active `feeInfo[i].value` reaches or exceeds `DENOMINATOR`, then at some iteration `_amount -= feeAmount` underflows a `uint256` and reverts the whole transaction. `_sendRewards` is invoked internally from `_toMasterWomAndSendReward` on every stake/unstake-triggered harvest path, and from `vote()`: [4](#0-3) [5](#0-4) 

Both of these are reachable through ordinary, unprivileged user transactions (LP deposit/withdraw via the pool helper triggering `_toMasterWomAndSendReward`, and bribe voting/reward routing via `vote()`), i.e., the disruption manifests when a normal user tries to interact with the pool, not just when an admin calls the fee-setter.

### Impact Explanation
Once the aggregate fee configuration crosses 100%, every call path that routes newly harvested WOM/bonus rewards through `_sendRewards` (i.e., every stake, unstake, and Wombat harvest, as well as bribe-vote reward routing) reverts. This freezes distribution of already-harvested yield/rewards to `BaseRewardPool`s indefinitely (until the fee configuration is manually corrected), and also blocks ordinary users from staking/unstaking LP tokens through the affected pool since those actions themselves trigger the failing harvest-and-forward flow. This matches the accepted impact class of a freeze of unclaimed yield / prolonged (24h+) freeze of user-facing functionality.

### Likelihood Explanation
Likelihood is moderate: it requires the owner to configure multiple fees (each independently valid) that sum to ≥100%, which is plausible in a system with several fee recipients (protocol fee, bribe fee, mWOM conversion fee, etc.) added incrementally over time without a global invariant check—exactly the same class of oversight that caused the original Basket.sol bug (no cap on the aggregate percentage used in a subtraction). No malicious admin behavior is required, only a missing bounds check that a legitimate, non-adversarial admin action can trip.

### Recommendation
In `addFee()` and `setFee()`, validate that the resulting `totalFee` (including the new/updated value) remains strictly less than `DENOMINATOR` before applying the change, e.g. `require(totalFee + _value < DENOMINATOR)` (for `addFee`) and `require(totalFee - fee.value + _value < DENOMINATOR)` (for `setFee`), reverting the configuration change rather than allowing a state that will later break `_sendRewards`.

### Proof of Concept
1. Owner calls `addFee(value = DENOMINATOR/2, to = feeCollectorA, ...)` — succeeds since `value < DENOMINATOR`.
2. Owner calls `addFee(value = DENOMINATOR/2 + 1, to = feeCollectorB, ...)` — succeeds since this individual value is still `< DENOMINATOR`, but now `totalFee > DENOMINATOR`.
3. Any user stakes/unstakes LP tokens through the pool's helper, triggering `_toMasterWomAndSendReward` → `_sendRewards` with a nonzero harvested `wom` amount.
4. In `_sendRewards`'s loop, the first fee's `_amount -= feeAmount` succeeds but leaves `_amount` smaller than the second `feeAmount` computed off `originalRewardAmount`; the second `_amount -= feeAmount` underflows and reverts, blocking the harvest/stake/unstake transaction for all users in that pool until the owner fixes the fee list.

    function setFee(uint256 _index, uint256 _value, address _to,
        bool _isMWOM, bool _isAddress, bool _isActive) external onlyOwner {
        if (_value >= DENOMINATOR)
            revert InvalidFee();        

        Fees storage fee = feeInfos[_index];
        fee.to = _to;
        fee.isMWOM = _isMWOM;
        fee.isAddress = _isAddress;
        fee.isActive = _isActive;

        totalFee = totalFee - fee.value + _value;
        fee.value = _value;

        emit SetFee(fee.to, _value);
    }
