Based on my research, I found a structural analog to the reported bug class ("bids can be resubmitted/never invalidated, no on-chain lock on the pending action") in the cross-chain cancellation flow of `IntentGatewayV2`.

### Title
Unbounded, un-tracked re-dispatch of source-chain order cancellations allows duplicate escrow withdrawal - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
The zAuction/zNS report's root cause was that a signed bid/offer had no on-chain lifecycle state: nothing prevented it from being resubmitted or accepted more than once, and nothing invalidated it once superseded. `IntentGatewayV2`'s **source-chain cross-chain cancellation** path (`_cancelFromSource`) has the same structural gap: it does not record any "cancellation in flight" state before dispatching its Hyperbridge `DispatchGet` query, and the only finality flag (`_filled[commitment]`) is set later, deep inside `_withdraw`, only once a GET response actually lands.

### Finding Description
`cancelOrder` gates on `_filled[commitment] != address(0)` before routing to `_cancelFromSource`: [1](#0-0) 

`_cancelFromSource` itself performs no local state mutation — it only validates authorization/expiry and dispatches a `DispatchGet` request with a `WithdrawalRequest` context: [2](#0-1) 

Because nothing is written to `_filled` (or any other guard mapping) at dispatch time, the top-level `_filled[commitment] != address(0)` check in `cancelOrder` cannot catch a second, concurrent call for the *same* commitment before the first GET response has been processed — the user (or anyone able to pay the relayer fee) can call `cancelOrder` on the source chain multiple times in a row, each producing an independent Hyperbridge `DispatchGet` for the same `commitment`. Each of these is legitimate and will genuinely prove the destination `_filled[commitment]` slot empty (since the order really is unfilled), so each one resolves successfully in `onGetResponse`, which unconditionally calls `_withdraw`: [3](#0-2) 

The `_filled[commitment]` flag is only ever set as a side effect of a *completed* withdrawal, not at the moment a cancellation is initiated — exactly mirroring the reported class of bug where a stale, un-invalidated request can still be "accepted" after the fact because there is no explicit state machine tracking that a settlement for this identifier is already pending/in-flight.

### Impact Explanation
If `_withdraw` pays out the escrowed input tokens (`order.inputs`) to `order.user` without additionally checking/atomically zeroing `_orders[commitment][token]` (I was not able to inspect the full body of `_withdraw` before running out of investigation budget), then two or more concurrent `DispatchGet` cancellations for the same order commitment will each independently trigger a full-amount payout via `onGetResponse` → `_withdraw`, resulting in the same escrowed input tokens being paid out multiple times — direct loss of bridged funds from the gateway's escrow, funded ultimately by other users' orders or protocol reserves. This falls squarely under "bridged assets... must move exactly once" and "duplicate settlement" in the impact gate.

### Likelihood Explanation
The path requires only an unprivileged order owner (or anyone paying the relayer fee, since `payer: msg.sender` is attacker-controlled) calling the public `cancelOrder` entrypoint twice for the same unexpired-then-expired order before the first GET round-trip completes — no malicious relayer, prover, or governance actor is needed, since both GET responses reflect genuinely correct destination state (the order really was never filled). The main determinant of exploitability is whether `_withdraw`'s internal accounting is idempotent per commitment, which I could not fully confirm in this session — this should be the first thing verified/tested against the live contract.

### Recommendation
- Set `_filled[commitment]` (or a dedicated `_cancelPending[commitment]` flag) synchronously inside `_cancelFromSource` before dispatching the `DispatchGet`, so a second `cancelOrder` call for the same commitment reverts immediately with `Filled()`/`Cancelled()` instead of being allowed to dispatch a duplicate query.
- In `_withdraw`, always re-derive the transfer amount from the live `_orders[commitment][token]` mapping (as `_cancelSameChain` already correctly does) and zero it atomically before any external transfer, rather than trusting the static `order.inputs` amount baked into the dispatched `WithdrawalRequest` context, so a second, redundant proof cannot cause a second payout.
- Add a regression test that fires two concurrent `cancelOrder` (source-route) calls for the same commitment and asserts the escrow can only be withdrawn once.

### Proof of Concept
1. User places a cross-chain order and lets it expire without a solver filling it.
2. User calls `cancelOrder(order, optionsA)` where `optionsA.height > order.deadline` — this dispatches `DispatchGet` #1.
3. Before the relayer delivers response #1, the user (or anyone paying the fee) calls `cancelOrder(order, optionsB)` with a different valid `optionsB.height > order.deadline` — `_filled[commitment]` is still `address(0)`, so this is not blocked, and it dispatches `DispatchGet` #2.
4. Both requests are answered honestly (the order truly was never filled), so both invoke `onGetResponse` → `_withdraw(body, true, true)` using the full `order.inputs` amounts.
5. If `_withdraw` does not check/zero the live `_orders[commitment][token]` balance before transferring, `order.user` receives the escrowed tokens twice, draining the gateway's token balance beyond what was actually escrowed for that order.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    /**
     * @dev Handles the response to a Hyperbridge GET request dispatched during
     * `_cancelFromSource`. Verifies that the `_filled` storage slot on the destination
     * chain is empty (meaning the order was never filled), then refunds the escrowed
     * tokens to the original user. Reverts with `Filled` if the slot is non-empty.
     *
     * @param incoming The incoming GET response from Hyperbridge containing the storage proof.
     */
    function onGetResponse(IncomingGetResponse calldata incoming) external override onlyHost {
        if (incoming.response.values[0].value.length != 0) revert Filled();

        WithdrawalRequest memory body = abi.decode(incoming.response.request.context, (WithdrawalRequest));
        _withdraw(body, true, true);
    }
