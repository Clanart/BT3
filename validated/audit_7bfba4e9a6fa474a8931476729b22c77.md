### Title
Spot-price manipulation of `smartConvert` bypasses the intended anti-arbitrage safeguard for WOM→mWOM buyback conversion - (File: wombat/SmartWomConvert.sol)

### Summary
The original report concerns a mitigation meant to stop a single transaction/block from bypassing an arbitrage-prevention check by manipulating AMM state before the guarded action executes. `SmartWomConvert.smartConvert()` has the analogous flaw: it reads the mWOM/WOM spot exchange rate and pool imbalance from the very AMM pool it is about to trade against, in the same call, with no TWAP, no per-block cooldown, and no access restriction, so an attacker can move the price immediately before invoking it and capture the mispriced buyback.

### Finding Description
`smartConvert()` is `external` with no caller restriction, even though the code comment states it "should mainly be used by wombat staking" [1](#0-0) . It determines how much of the incoming WOM is bought back on the open market (`womMWomPool`) versus minted 1:1, based on:

- `currentRatio()`, the live spot price of mWOM in WOM taken from `router.getAmountOut` against `womMWomPool` [2](#0-1) 
- `maxSwapAmount()`, computed from the same pool's `cash()`/`liability()` of `womAsset` [3](#0-2) 

Both values are read and acted upon inside the same transaction that then performs the actual swap in `_convertFor`: [4](#0-3) 

Because `currentRatio()`/`maxSwapAmount()` and the subsequent `swapExactTokensForTokens` all reference the same pool without any block-delay, TWAP, or reentrancy/flash-swap protection, a caller can first push the mWOM price down (or shift `cash`/`liability`) via a swap on `womMWomPool`, then call `smartConvert` in the same transaction so that (a) `mWomToWom < buybackThreshold` triggers a larger-than-intended buyback amount via the inflated `maxSwapAmount()`, and (b) the buyback executes at the attacker-manipulated depressed price, yielding an inflated `obtainedmWomAmount` for the attacker's own conversion. This is the same class of defect as the report: a protection that only functions correctly if the market state is not adversarially set within the same block/transaction as the exploited action.

### Impact Explanation
`smartConvert` is the function `WombatStaking` uses to convert protocol-harvested WOM into mWOM as part of reward routing (referenced 6 times in `wombat/WombatStaking.sol`). Since the function is unauthenticated, any wallet can call it directly, or manipulate the pool immediately ahead of the protocol's own scheduled call, to force an unfavorable buyback ratio at the protocol's expense, or to self-serve an inflated mWOM output relative to WOM deposited. This directly harms the pool's WOM/mWOM liquidity providers and skews the economics of the mWOM peg mechanism that other stakers rely on, resulting in a real transfer of value away from the protocol/other users through manipulated pricing within a single transaction.

### Likelihood Explanation
The precondition is trivial to reach: `smartConvert` has no access control, and the only cost to the attacker is the WOM/mWOM swap fee plus gas for one flash-manipulation transaction against `womMWomPool`. No privileged role, governance action, or external dependency beyond composing two calls in one transaction is required.

### Recommendation
- Restrict `smartConvert` to only be callable by the trusted `WombatStaking` contract (add an `onlyWombatStaking`-style modifier), removing open, unauthenticated access.
- Replace spot `getAmountOut`/`cash()`/`liability()` reads with a TWAP or a price check that cannot be moved within the same transaction (e.g., comparing against a stored, delayed observation, or enforcing a minimum elapsed block/time since the last state-changing swap on `womMWomPool`).
- Add slippage/sanity bounds so `maxSwapAmount()` cannot spike due to a same-transaction manipulation of `womAsset.cash()`/`liability()`.

### Proof of Concept
1. Attacker takes a large WOM (or mWOM) position and, in transaction T, swaps against `womMWomPool` to depress `currentRatio()` below `buybackThreshold` and/or widen the `cash()`/`liability()` gap read by `maxSwapAmount()`.
2. In the same transaction T, attacker calls `smartConvert(_amountIn, _mode)` [5](#0-4) ; because `mWomToWom < buybackThreshold`, a larger `amountToSwap` is computed from the manipulated `maxSwapAmount()`, and `_convertFor` executes the buyback swap at the manipulated depressed price [6](#0-5) , producing an inflated `obtainedmWomAmount` for the attacker.
3. Attacker reverses the initial manipulation swap (or lets external arbitrageurs correct it), realizing the mWOM gained at the pool's/protocol's expense, all within a single transaction.

```text
    // should mainly used by wombat staking upon sending wom
    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
```
