## #Vulnerability found for this question

### Title
Attacker-controlled `pr.head.repo.clone_url` reaches `git remote add` / `git fetch` without a transport allowlist, enabling `ext::`/`file://` transport-helper code execution - (`app/src/lib/stores/app-store.ts`)

### Summary
`_checkoutPullRequest`/`_findPullRequestBranch` take `headCloneUrl` straight from the GitHub API's `pull_request.head.repo.clone_url` field (or from the deep-link handler `openPullRequestFromUrl`) and pass it unmodified to `addRemote`, and subsequently to `fetch`, with no validation that the URL uses an `http(s)`/`ssh`/`git` scheme.

### Finding Description
`_checkoutPullRequest` and `_findPullRequestBranch` receive `headCloneUrl` as a plain `string` parameter and forward it to `addRemote(repository, forkRemoteName, headCloneUrl)` when no existing remote matches it [1](#0-0) . `addRemote` performs no validation and shells out directly: `git(['remote', 'add', name, url], repository.path, 'addRemote')` [2](#0-1) .

The only place that could have blocked non-GitHub URLs — `urlMatchesRemote` — relies on `parseRemote`, whose regex table only recognizes `https?://`, `git@host:owner/name`, `git:host/owner/name`, and `ssh://git@host/owner/name` forms [3](#0-2) . A value such as `ext::sh -c $@|sh . echo pwned` or `file:///etc` does not match any of these patterns, so `parseRemote` returns `null` and `urlMatchesRemote` returns `false` [4](#0-3) . This function is used purely to decide whether to reuse an existing remote — it never rejects/blocks the untrusted value from being used with `addRemote`.

Once the malicious value is registered as a git remote, `_findPullRequestBranch` calls `this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)` [5](#0-4) , which ultimately invokes `fetch(repository, remote, ...)` in `app/src/lib/git/fetch.ts`, running `git fetch <remote>` with only `envForRemoteOperation` applied (auth headers + proxy resolution) — no `GIT_ALLOW_PROTOCOL`/`protocol.*.allow` restriction is ever set [6](#0-5) [7](#0-6) . A repo-wide search for `GIT_ALLOW_PROTOCOL`/`protocol.ext.allow` returns no matches anywhere in the codebase, confirming Desktop never restricts which git transport helpers are permitted.

The same untrusted field is also passed through `openPullRequestFromUrl` for the `x-github-client://openPullRequest` deep link (`pullRequest.head.repo.clone_url`) directly into `_checkoutPullRequest` [8](#0-7) , and via the ordinary "Checkout PR" dispatcher path (`pullRequest.head.gitHubRepository.cloneURL`) [9](#0-8) .

Git's `ext::` and `file://` transport helpers are gated by `protocol.<name>.allow`, which defaults to `user` (allowed unless `GIT_PROTOCOL_FROM_USER=0`, a variable git sets automatically only for recursively-triggered operations such as submodule fetches, not for a directly invoked `git remote add`/`git fetch`). Because Desktop invokes git directly as the "user" here and never sets `GIT_PROTOCOL_FROM_USER=0` or `GIT_ALLOW_PROTOCOL`, the `ext::` helper is permitted to run and will execute the attacker-supplied shell command; `file://` would allow local file reads.

### Impact Explanation
If confirmed against a real dugite/git invocation, this would allow an attacker who can get a PR (or a crafted API response / synthetic PR object opened via the `x-github-client://openPullRequest` deep link) processed by Desktop to achieve arbitrary command execution on the victim's machine merely by having them checkout the PR — no credentials, no local access. This maps to the "code execution... via attacker-controlled repository content, GitHub API objects" category explicitly listed as valid impact in the program scope.

### Likelihood Explanation
Requires the victim to actively checkout a PR (from the PR list or via the "Open PR from Desktop" deep link), which is a normal, expected user action rather than an "unnatural" step. The attacker fully controls `head.repo.clone_url` in their own fork's PR object / in the crafted deep-link payload, so no privileged position is needed.

### Recommendation
Before calling `addRemote`/`fetch` with any URL derived from an API object or deep link, validate that `parseRemote()` (or an equivalent explicit allowlist of `https:`, `http:`, `ssh:`, `git:` schemes) successfully parses the URL, and reject/refuse to add the remote otherwise. Additionally, consider always launching git for these operations with `GIT_ALLOW_PROTOCOL=http:https:ssh:git` (or the corresponding `protocol.*.allow=never` config for `ext`/`file`/`fd`/`ftp`) as defense in depth, matching mitigations adopted by other git-hosting desktop clients for this exact class of issue.

### Proof of Concept
1. Construct a synthetic `IAPIPullRequest`-like object (or intercept the pull-request API response) with `head.repo.clone_url = 'ext::sh -c $@|sh . echo pwned'` and `head.repo.owner.login`/`head.ref` set to arbitrary values.
2. Trigger `_findPullRequestBranch(repository, prNumber, headRepoOwner, 'ext::sh -c $@|sh . echo pwned', headRefName)` (e.g., via `_checkoutPullRequest`, reachable through the PR list UI or the `x-github-client://openPullRequest/...` deep link handled by `openPullRequestFromUrl`).
3. Observe that `urlMatchesRemote` returns `false` for all existing remotes (since `parseRemote` can't parse the `ext::` URL), causing `addRemote(repository, forkRemoteName, 'ext::sh -c $@|sh . echo pwned')` to run `git remote add <name> 'ext::sh -c $@|sh . echo pwned'` successfully.
4. Observe the subsequent `_fetchRemote` call invoke `git fetch <name>`, which — absent any `GIT_ALLOW_PROTOCOL`/`protocol.ext.allow` restriction in Desktop's git environment — should trigger execution of the injected shell command.

Note: I was not able to execute git/dugite directly in this environment to observe the runtime exit code/output of step 4; the conclusion that `ext::` executes is based on documented git default behavior (`protocol.ext.allow=user`, unset `GIT_PROTOCOL_FROM_USER`) combined with the confirmed absence of any allow/deny protocol configuration anywhere in this codebase. A background Devin session with a sandbox could confirm this empirically by running the exact `addRemote`/`fetch` calls from `app/src/lib/git/remote.ts` and `app/src/lib/git/fetch.ts` with a real git binary and observing whether the injected command executes.

/** Parse the remote information from URL. */
export function parseRemote(url: string): IGitRemoteURL | null {
  for (const { protocol, regex } of remoteRegexes) {
    const match = regex.exec(url)
    if (match !== null && match.length >= 4) {
      return { protocol, hostname: match[1], owner: match[2], name: match[3] }
    }
  }

  return null
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }
