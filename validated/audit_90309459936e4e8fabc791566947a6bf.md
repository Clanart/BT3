## Title
`reassembleResolvedFile` splices Copilot hunk resolutions by **position only, not by identity** — a malicious `<<<<<<< ======= >>>>>>>` block in a fetched repository can shift every subsequent hunk resolution into the wrong location, silently corrupting a merge commit - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The AI-assisted merge-conflict resolver validates the *set* of returned items (file paths and per-file hunk **counts**) but never validates the *identity/order* of hunks within a file. `reassembleResolvedFile` walks the original file and splices `hunkResolutions[i]` into the `i`‑th marker block it finds by scanning top-to-bottom [1](#0-0) . This is the same invariant break as the C4 report: a check that only verifies *aggregate quantity* ("hunk count matches") is used as a proxy for "each item matches the item it's supposed to," and an attacker who can influence what counts as a conflict-marker block can desynchronize the correspondence between resolutions and the locations they get spliced into.

### Finding Description
`validateResolutionPaths` only checks:
- returned paths ⊆ expected paths, no duplicate paths, no missing paths, and
- `resolution.hunks.length !== expectedCount` per file [2](#0-1) .

There is no per-hunk identity (no hash, no line-range, no content anchor). The comment in `reassembleResolvedFile` states this explicitly: *"matched by order, not by line number"* [3](#0-2) .

`extractConflictHunks` finds conflict marker blocks purely by regex over `<<<<<<<`, `|||||||`, `=======`, `>>>>>>>` lines [4](#0-3) [5](#0-4) . `reassembleResolvedFile` re-scans the same raw file for the same markers and does the same "well-formed block" check (`hasSeparator` + closing `>>>>>>>`) before consuming the next entry from `hunkResolutions` in sequence [6](#0-5) .

An attacker controls the fetched/merged branch content (this is exactly the trust boundary called out in the task: "attacker controls a cloned/fetched repository"). If the attacker's branch introduces a file whose *pre-existing, unrelated* content happens to contain a well-formed `<<<<<<<`/`=======`/`>>>>>>>` sequence that is **not actually part of the real git conflict** (e.g. it lives inside a string literal, a code comment, a markdown code block documenting git-conflict syntax, or a previously-committed "example conflict" fixture file) sitting adjacent to or before the real conflict region, then:
- `extractConflictHunks` will count and extract this extra "hunk" as hunk N, shifting every real hunk after it to N+1, N+2, ….
- The prompt sent to Copilot enumerates hunks as `Conflict 1 of N`, `Conflict 2 of N`, etc., using this same shifted numbering [7](#0-6) .
- `validateResolutionPaths` only checks that the returned hunk **count** for the file equals the expected count — it happily accepts N hunks in *any* order, since nothing ties resolution `i` back to the specific marker block it was generated for.
- `reassembleResolvedFile` then consumes `hunkResolutions` strictly in file-scan order, splicing resolution `i` into whichever marker block is the `i`-th one encountered on disk.

If the count still matches (attacker's spurious block simply adds one to both "expected" and, because it's still described faithfully to the model as a legitimate hunk, "returned"), the aggregate-count guard passes, exactly as in the audited Infinity Exchange bug where a duplicated/extra item satisfies the count check without satisfying identity. The net effect: real conflict-resolution content that the model generated for the user's actual (ours vs. theirs) conflict gets written into the wrong marker block, or the spurious/decoy block's "resolution" is spliced into a genuinely important hunk, while `resultLines` still assembles into what looks like a complete, marker-free file [8](#0-7) .

### Impact Explanation
This corrupts *what the user commits* without any further validation: the reassembled content is the final file content written to disk and committed as the merge/rebase/cherry-pick resolution — there is no line-level diff-vs-intent check before commit. A malicious upstream/fork branch that a victim merges (a normal, expected Desktop workflow — "Merge into Current Branch") can cause security-relevant code (e.g. an auth check, a dependency pin, a CI config) to silently receive the wrong resolved content, while the user believes Copilot correctly resolved the *real* conflict. This matches the required impact category: "silent corruption of what the user commits or pushes," triggered purely by content in a repository/branch the attacker controls, requiring no elevated privileges, malware, or unnatural user steps beyond a normal merge with AI-assisted resolution enabled.

### Likelihood Explanation
Requires: (1) the user has the Copilot conflict-resolution feature enabled and invokes it on a merge/rebase/cherry-pick, and (2) the attacker's branch/file contains, or can be made to contain, a well-formed decoy marker sequence outside the real conflict (via a prior commit on the attacker's branch, not necessarily as part of the conflict itself — e.g. a test fixture or documentation file demonstrating conflict-marker syntax, or lines produced by a rebase of nested conflicts). This is a plausible but non-trivial precondition (moderate likelihood) — it does not require the user to click anything unusual, just to run AI conflict resolution on an attacker-influenced merge, which is the intended use case of the feature.

### Recommendation
Anchor each hunk resolution to the specific marker block it was generated for instead of relying on positional/count-only matching:
- Assign a stable identifier to each extracted `IConflictHunk` (e.g. its starting line index in the original file, or a hash of `oursContent`/`theirsContent`/`baseContent`), include it in the prompt, and require the model to echo it back per hunk.
- In `validateResolutionPaths`/`reassembleResolvedFile`, verify that each returned hunk's identifier matches the corresponding hunk actually extracted from disk before splicing, rejecting the response (falling back to manual resolution) on any mismatch — mirroring the C4 report's own recommendation to validate identity, not just aggregate counts.
- Additionally, treat any conflict-marker-like sequence found outside a real unmerged/`MERGE_HEAD` context with suspicion (e.g., cross-check hunk locations against `git diff` conflict regions rather than a naive regex scan of the whole file) to reduce the chance of decoy blocks being counted at all.

### Proof of Concept
Conceptual PoC (exact reproduction requires the Copilot conflict-resolution session, which is not locally invokable from static analysis, so this is derived from code-path tracing rather than an executed test):
1. Attacker prepares a branch `evil` containing a file `notes.md` with these unrelated, pre-existing lines (not part of any real conflict):
   ```
   Example of a conflict marker:
   <<<<<<< decoy
   old
   =======
   new
   >>>>>>> decoy
   ```
2. The same file also has a *real* conflicting region further down, edited differently on `main` and `evil`.
3. Victim merges `evil` into `main` in Desktop; `notes.md` shows as conflicted (because of the real region) and the victim runs "Resolve with Copilot."
4. `extractConflictHunks` finds 2 hunks: hunk 0 = the decoy block, hunk 1 = the real conflict [5](#0-4) .
5. The prompt lists "Conflict 1 of 2" (decoy) and "Conflict 2 of 2" (real); Copilot returns two hunk resolutions in order, both accepted since `hunks.length === 2 === expectedCount` [9](#0-8) .
6. `reassembleResolvedFile` splices resolution[0] into the decoy block and resolution[1] into the real block — in this trivial case correct, but if the attacker inserts the decoy *between* two real hunks, or duplicates markers to desynchronize the scan order versus what the model believed it was resolving (e.g., attacker's file has hunks in an order that differs from what a line-based diff view would show the user, due to whitespace/marker games), resolution content ends up spliced into the wrong hunk, and the reassembled, marker-free file is committed as-is.

Because the matching mechanism is purely positional/count-based with no content or location anchor tying a resolution back to its source hunk, the exact attacker leverage — how easily marker-order confusion can be engineered — could not be fully verified without running the live Copilot session end-to-end; this PoC demonstrates the missing-identity-check code path rather than a confirmed exploit trace through the model's actual output.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}

const oursMarker = /^<{7}(?:\s|$)/
const baseMarker = /^\|{7}(?:\s|$)/
const separatorMarker = /^={7}$/
const theirsMarker = /^>{7}(?:\s|$)/

/**
 * Absolute upper bound (in bytes) on a conflicted file we'll read into memory.
 *
 * This is a memory-safety guard only, not a resolvability heuristic — we only
 * ever send the *conflict hunks* to the model, never the whole file, so a large
 * file with a small conflict is still perfectly resolvable. Files above this
 * size are skipped before reading to avoid loading pathological blobs (e.g. a
 * multi-megabyte generated lockfile) into a string.
 */
const MAX_CONFLICT_FILE_READ_SIZE = 10_485_760 // 10MB

/**
 * Maximum length (in characters) of any single line within a conflict hunk.
 *
 * Mirrors the diff renderer's `MaxCharactersPerLine`. Conflicts containing a
 * line longer than this are almost always minified/generated content where a
 * line-oriented resolution is meaningless, so we skip them rather than sending
 * an enormous single line to the model.
 */
const MAX_CONFLICT_LINE_LENGTH = 5000

/**
 * Maximum combined size (in characters) of the actual conflict content in a
 * single file — the sum of the ours/base/theirs text across every hunk.
 *
 * Unlike a whole-file cap, this measures what we actually send to the model, so
 * it protects prompt size and output quality (truncation/malformed JSON)
 * without penalising large files whose conflicts are small.
 */
const MAX_CONFLICT_CONTENT_SIZE = 262_144 // 256KB

function isConflictMarker(line: string): boolean {
  return (
    oursMarker.test(line) ||
    baseMarker.test(line) ||
    separatorMarker.test(line) ||
    theirsMarker.test(line)
  )
}

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }
