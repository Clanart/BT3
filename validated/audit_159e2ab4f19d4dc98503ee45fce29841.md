### Title
Arbitrary reward-token array in `ManualCompound.compound()` allows caller to sweep any non-registered token balance held by the shared contract - (File: `rewards/ManualCompound.sol`)

### Summary
The Bebop exploit stemmed from a contract trusting caller-supplied arrays inside an order struct (`sellTokens`/`buyTokens`/`sellAmounts`/`buyAmounts`) to drive fund movement without validating that those array entries actually matched the caller's legitimate entitlement. `ManualCompound.compound()` in the Magpie codebase has the same bug class: it accepts fully attacker-controlled `address[][] calldata _rewards` and uses each entry, unchecked against what was actually harvested for the caller, to decide which ERC20 balance currently held by the contract gets swept out to `msg.sender`.

### Finding Description
`compound()` is a public, unprivileged entry point: [1](#0-0) 

After calling `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)`, the function iterates over the **caller-supplied** `_rewards[i][j]` addresses. For any address that is not currently flagged `compoundableRewards[token] == true`, it reads `IERC20(_rewards[i][j]).balanceOf(address(this))` — i.e. the *entire current balance of that token held by the shared `ManualCompound` contract* — and transfers it to `msg.sender`: [2](#0-1) 

Nothing ties the `_rewards[i][j]` value to what was actually claimed on behalf of `msg.sender` for `_lps[i]`. The array is never cross-checked against `IMasterMagpie`'s registered reward tokens for that staking token, nor against the amount actually received during this call. Confirming this, `BaseRewardPool.getReward()` — the function actually invoked during `multiclaimOnBehalf` — ignores any externally-supplied reward-token list entirely and iterates its own internally registered `rewardTokens[]` storage array: [3](#0-2) 
(the corresponding `getRewards(address,address,address[])` override that would accept an explicit token list is an empty stub): [4](#0-3) 

So the `_rewards` array passed into `ManualCompound.compound()` has no verified relationship to the tokens genuinely paid out by the pool for that claim. It is used purely as an attacker-chosen key into `compoundableRewards`, letting any caller name an arbitrary ERC20 address and, if it isn't currently registered as "compoundable" by the owner, drain whatever balance of that token the shared contract happens to be holding at that moment (e.g., un-swept reward dust, freshly-added-but-not-yet-flagged reward tokens, or tokens left mid-processing from another leg of the same call) directly to themselves.

### Impact Explanation
`ManualCompound` is a shared, permissionless contract that transiently custodies reward tokens harvested on behalf of users before routing them to converters/lockers/helpers. Because the sweep condition (`!compoundableRewards[token]`) and the swept amount (full contract balance) are both derived from unverified, attacker-chosen input rather than the caller's actual claim, any token balance sitting in the contract that is not registered as compoundable can be redirected to an arbitrary caller. This is a direct theft-of-funds vector against value that does not belong to the caller (e.g., a newly harvested reward token before the owner has called `addReward` to mark it compoundable, or residual balances from other users' in-flight compounding), matching the accepted "direct theft of user funds" / "theft of unclaimed yield" impact class.

### Likelihood Explanation
Exploitation requires no privileged role — any wallet can call `compound()` with a crafted `_rewards` array. The condition for exploitation (a non-compoundable token balance being present in `ManualCompound`) is plausible during normal protocol operation, since new reward tokens are added by the owner via `addReward` only after they start being harvested by `MasterMagpie`/Wombat, creating a window where a real reward token sits in the contract without yet being flagged `compoundableRewards[token] = true`.

### Recommendation
Do not derive the sweep-eligibility or sweep-amount from caller-supplied `_rewards` entries. Instead, have `ManualCompound` independently query the actual reward tokens registered for each `_lps[i]` pool (e.g., via `IBaseRewardPool.rewardTokenInfos()`), and only ever sweep amounts that were provably received by this specific `compound()` invocation (e.g., using pre/post balance deltas per legitimate reward token, not the raw `balanceOf` of an arbitrary address). Reject or ignore any token address in `_rewards` that is not a genuine registered reward token for the corresponding pool.

### Proof of Concept
1. Owner has not yet called `addReward(tokenX, ...)`, but `MasterMagpie`/`WombatStaking` has already started routing `tokenX` rewards, so a `tokenX` balance is present in `ManualCompound` from a legitimate prior harvest step.
2. Attacker (unprivileged wallet) calls `compound(_lps, _rewards, 0, 0, false)` with `_rewards[i] = [tokenX]` for any valid `_lps[i]` (attacker's own stake can be zero — `multiclaimOnBehalf`/`getReward` simply produce zero additional reward, but this does not prevent the function from proceeding).
3. Since `compoundableRewards[tokenX] == false`, the loop at [5](#0-4)  transfers the entire `tokenX` balance held by `ManualCompound` to the attacker, regardless of whether the attacker actually earned it.
