### Title
Unvalidated GitHub API `clone_url` used to construct git remote arguments without `--` end-of-options guard, enabling argument/protocol injection - (File: `app/src/lib/git/remote.ts`)

### Summary
The Chainlink report's root cause is that external, attacker-influenceable data (oracle price) is consumed by `PriceCalculator` without validating its shape/freshness before being used in a financial calculation. The equivalent pattern in GitHub Desktop is that `headCloneUrl` — a string taken verbatim from a pull request's `head.repo.clone_url` field, which is data returned by (and thus can be shaped by) a GitHub API endpoint — is passed straight into `addRemote()`, which builds a `git remote add` command without any scheme/format validation and, unlike Desktop's own `clone()` implementation, without the `--` end-of-options separator that would neutralize argument injection.

### Finding Description
`_findPullRequestBranch` takes `headCloneUrl` straight from the pull request head repository object returned by the API and, when no existing remote matches, calls `addRemote(repository, forkRemoteName, headCloneUrl)`: [1](#0-0) 
This same unvalidated value originates from `pullRequest.head.repo.clone_url` in `openPullRequestFromUrl`: [2](#0-1) 

`addRemote()` itself performs no validation of the URL's scheme or shape and constructs the git argument vector without a `--` separator: [3](#0-2) 

This is inconsistent with the project's own hardening pattern: `clone()` explicitly documents and implements protection against exactly this class of issue by appending `--` before the untrusted `url`/`path` values: [4](#0-3) 

No equivalent guard exists for `addRemote`, `setRemoteURL`, or `removeRemote`: [5](#0-4) 

Because `clone_url` is only ever asserted to be a `string` in the API type layer and is not checked to start with `https://`/`git@`/`ssh://` anywhere before being handed to the git CLI (`urlMatchesRemote`/`parseRemote` are used for *matching* an existing remote, not for validating `headCloneUrl` before `addRemote` is called when no match is found), a value shaped like a CLI flag (e.g. beginning with `-`) or a git "ext"/"fd" transport string is accepted and forwarded unmodified. This mirrors the oracle report exactly: data crossing a trust boundary (external API / forked repository owner) is consumed without checking it conforms to the expected invariant (a well-formed `https`/`ssh` git URL) before being used in a sensitive operation (constructing a shell-adjacent git command).

### Impact Explanation
If the PR head repository's `clone_url` is attacker-influenced — e.g., the user is viewing a PR from a fork whose metadata is served by a malicious/compromised GitHub Enterprise Server, or a MITM/rogue proxy in the API request path (both explicitly in-scope per the task's "attacker controls...a GitHub API object...or a git remote/proxy response") — the value flows unchecked into `git remote add <name> <url>` without a `--` boundary. Because `url` is the last positional token and no separator forces it to be treated as a path, a value engineered to look like a git option, or a value using git's `ext::`/other unusual transport syntax, is passed through as-is. Subsequent fetch operations on that remote (`_fetchRemote` is called right after `addRemote` in `_findPullRequestBranch`) would execute against whatever transport/behavior the crafted string implies, which can range from unexpected git behavior to command execution depending on the user's/environment's git configuration (e.g., `protocol.ext.allow`). This is a silent, unprompted network write (a new remote persisted in `.git/config`) and a route to executing attacker-chosen git transport logic, without any user confirmation of the raw URL that was added.

### Likelihood Explanation
Likelihood is limited by the fact that `github.com` itself always returns well-formed `https://github.com/...` or SSH URLs for `clone_url`, so the primary trigger requires a non-github.com endpoint (GitHub Enterprise Server) that is attacker-controlled/compromised, or an on-path attacker tampering with the API response (per the task's accepted "git remote/proxy response" primitive). The user-facing trigger — viewing/opening a PR from a fork and checking it out via "Open PR from Desktop" or the browser deep-link flow — requires no unusual local steps beyond normal Desktop usage (clicking a PR/deep link), which is within the accepted attacker model.

### Recommendation
Before using any `clone_url`/remote URL obtained from the GitHub API (or any other externally supplied source) in `addRemote`, `setRemoteURL`, or similar functions, validate that the value parses as a well-formed `https`/`ssh`/`git` URL (e.g., via the existing `parseRemote` helper) and reject anything that does not match an expected scheme, mirroring the recommendation to explicitly validate untrusted feed data before use. Additionally, apply the same `--` end-of-options hardening used in `clone.ts` to `addRemote`/`setRemoteURL`/`removeRemote` in `app/src/lib/git/remote.ts` so that even a malformed value cannot be interpreted as a CLI flag.

3. In Desktop, open that PR (e.g., via "Open PR from Desktop" deep link, which calls `openPullRequestFromUrl` → `dispatcher.ts:2039-2045`).

export async function addRemote(
  repository: Repository,
  name: string,
  url: string
): Promise<IRemote> {

  return { url, name }
}
