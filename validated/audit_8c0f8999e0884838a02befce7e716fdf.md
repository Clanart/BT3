### Title
`reauth_on_access_scope_changes` silently no-ops when a stored session has an empty `scope`, letting under-scoped sessions bypass forced re-authentication - (File: `lib/shopify_app/access_scopes/user_strategy.rb`)

### Summary
The audited bug is a class of "silent policy downgrade": governance configures a protective threshold/flag, but a secondary check silently substitutes a weaker default without any signal, so the enforced behavior diverges from the configured intent. The analogous pattern in `shopify_app` is in the access-scope reauthentication guard used by `ShopifyApp::LoginProtection#activate_shopify_session`, which is gated by the `reauth_on_access_scope_changes` configuration flag and delegates the actual scope check to `ShopifyApp::AccessScopes::UserStrategy.covers_scopes?`.

### Finding Description
`activate_shopify_session` is meant to force re-login whenever the active session's granted scopes no longer satisfy the app's configured scopes, but only when the operator has explicitly opted into this protection: [1](#0-0) 

The actual check is delegated to `UserStrategy.covers_scopes?`: [2](#0-1) 

The `NOTE` comment shows this is intentional, but it produces the exact "governance sets a protective control, code silently discards it" pattern from the report: if `current_shopify_session.scope` is blank/empty (e.g. `nil` or `[]`), the method returns `true` ("covers scopes") unconditionally — regardless of what scopes the app actually requires via `ShopifyApp.configuration.scope` / `user_access_scopes`. No log message, no warning, and no error is raised; the operator who enabled `reauth_on_access_scope_changes = true` believes stale/insufficient sessions will be forced to re-authenticate, but any session whose `scope` attribute is empty sails through `activate_shopify_session` and is activated with `ShopifyAPI::Context.activate_session(current_shopify_session)`: [3](#0-2) 

This mirrors the C4 report precisely: a config toggle (`reauth_on_access_scope_changes`) is supposed to enforce a stricter policy, but a fallback condition inside the enforcement helper (`scope.to_a.empty?`) silently defeats it with no observable signal, so operators cannot tell that the protection isn't actually active for such sessions.

### Impact Explanation
Any stored/loaded session whose `scope` ends up empty — for example sessions created before scopes were persisted, sessions from a custom `SessionRepository` implementation that doesn't populate `scope`, or online sessions obtained through paths that don't set `scope` — will be treated as fully authorized for whatever the app currently requires, even though the app may have since added new, more sensitive scopes (e.g. `write_orders`, `read_customers`). The configured protective control (`reauth_on_access_scope_changes`) silently does nothing for these sessions, allowing continued use of an under-scoped access token without the intended re-consent/re-auth flow, exactly the kind of "governance thinks a stronger control is active, but it silently isn't" misconfiguration described in the report.

### Likelihood Explanation
This depends on session/scope population inputs (custom session storage, legacy sessions, or code paths that don't set `scope`) rather than a value directly forgeable by an anonymous attacker in a single request, so it is lower likelihood than a classic auth bypass, but it is reachable purely through normal authenticated app traffic (no privileged/host-operator access required) and requires no attacker crafting beyond causing/having a session record with empty scope.

### Recommendation
Change `covers_scopes?` to treat an empty/blank scope as *not* covering the configured scopes (fail closed) rather than treating it as automatically satisfying them, or explicitly log/warn when this fallback path is taken so the silent divergence from the configured `reauth_on_access_scope_changes` policy becomes visible to operators. Add a regression test asserting that a session with empty `scope` and `reauth_on_access_scope_changes = true` is redirected to login/re-auth rather than activated.

### Proof of Concept
1. Enable `config.reauth_on_access_scope_changes = true` and configure `config.scope = "read_products,write_orders"`.
2. Load/store a Shopify session (e.g. via a custom `SessionRepository` or a pre-existing legacy row) with `scope` set to `nil`/empty, while the shop has NOT actually granted the newly required scopes.
3. Hit any controller including `ShopifyApp::LoginProtection` with `around_action :activate_shopify_session`.
4. Observe that `ShopifyApp::AccessScopes::UserStrategy.covers_scopes?(current_shopify_session)` returns `true` because `current_shopify_session.scope.to_a.empty?` short-circuits, so `activate_shopify_session` proceeds to activate the session and `yield`s to the action instead of redirecting to `redirect_to_login`, silently bypassing the configured reauthorization policy.     def activate_shopify_session
      if current_shopify_session.blank?
        signal_access_token_required
        ShopifyApp::Logger.debug("No session found, redirecting to login")
        return redirect_to_login
      end

      if ShopifyApp.configuration.check_session_expiry_date && current_shopify_session.expired?
        ShopifyApp::Logger.debug("Session expired, redirecting to login")
        clear_shopify_session
        return redirect_to_login
      end

      if ShopifyApp.configuration.reauth_on_access_scope_changes &&
          !ShopifyApp.configuration.user_access_scopes_strategy.covers_scopes?(current_shopify_session)
        clear_shopify_session
        return redirect_to_login
      end
