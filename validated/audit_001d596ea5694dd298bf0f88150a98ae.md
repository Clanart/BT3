Based on my research, I found a solid analog for the "missing events after sensitive state change" bug class in Holdefi (Solidity) — the Desktop equivalent is a sensitive state mutation (a git remote URL rewrite) performed automatically and silently, with no notification/audit trail shown to the user, driven entirely by attacker-influenced GitHub API data.

### Title
Silent, unconfirmed remote-URL rewrite driven by GitHub API `clone_url` with no user notification - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The Holdefi report's core complaint is that sensitive state changes happen without any observable event, leaving no signal that a security-relevant value was altered. The Desktop analog is `updateRemoteUrl` in [1](#0-0) , which rewrites the local git `origin` remote URL automatically based on the `clone_url` field of a `GitHubRepository`/`IAPIRepository` object fetched from the GitHub API — with no dialog, banner, popup, or log visible to the user, and no way to review or reject the change.

### Finding Description
`updateRemoteUrl` compares the current default remote URL against `apiRepo.clone_url` (a value that originates from a GitHub API response) and, if the protocol matches and the remote wasn't manually changed away from the previously-cached `cloneURL`, calls `gitStore.setRemoteURL(...)` to silently rewrite the remote: [2](#0-1) 

`GitStore.setRemoteURL` performs the git operation and only emits an internal store update (`emitUpdate`) used for UI re-render of the settings panel — it does not raise any popup, banner, or toast telling the user "the origin remote was just changed": [3](#0-2) 

The trust boundary here is the GitHub API repository object (`clone_url`), which is exactly the "attacker controls...a GitHub API object" scenario named as valid in the Valid Impact section. This value is refreshed periodically as part of repository metadata refresh flows in `app-store.ts` (three call sites reference `updateRemoteUrl`, though I could not fully enumerate the exact trigger context due to index truncation of `app-store.ts`). If a repository is renamed/transferred, or if a compromised/malicious GitHub Enterprise Server, a MITM proxy, or a spoofed API response returns a different `clone_url` for the same logical repository (matching hostname/owner/name heuristics in `urlMatchesRemote`), the app will silently repoint `origin` to that URL.

The guard conditions (`protocolsMatch`, `remoteUrlUnchanged`) are heuristic string/hostname comparisons in `urlMatchesRemote`, [4](#0-3)  not cryptographic or user-confirmed checks — they only compare owner/name/hostname parsed out of the URL, so any API response claiming the "same" owner/repo but pointing to a different host under attacker control that still parses with matching components, or a scenario where the cached `cloneURL` itself was previously poisoned, would pass silently.

### Impact Explanation
If the remote URL is silently repointed to an attacker-controlled host, all subsequent `git push` operations from Desktop will send the user's future commits (and, depending on credential-helper behavior, their GitHub credentials via the git credential trampoline) to that attacker endpoint — a direct instance of "silent corruption of what the user commits or pushes" and potential "credential/token exfiltration," both explicitly listed as valid impacts. Because there is no `CollateralAssetWithdrawn`-style event/banner equivalent, the user has no way to notice the remote changed until they inspect repository settings manually.

### Likelihood Explanation
The API `clone_url` is periodically refreshed as part of normal repository metadata sync, so no unusual user action is required beyond having previously connected the repository to a GitHub/GHE account whose API is attacker-influenced (compromised or malicious GHE instance, a repository rename/redirect, or a MITM against the API). This does not require local/physical access, admin rights, or prior malware, satisfying the acceptance criteria; however, I was not able to fully trace all three `app-store.ts` call sites due to index truncation of that large file, so I cannot confirm every trigger path or whether additional confirmation exists elsewhere in the flow I couldn't inspect.

### Recommendation
Before silently calling `gitStore.setRemoteURL`, surface an explicit, dismissible notification/banner (or require user confirmation) whenever `updateRemoteUrl` detects and applies a remote URL change, showing both the old and new URL — mirroring the report's general recommendation to emit an event/observable signal (with the key changed values) whenever a sensitive state mutation like this occurs. This mirrors the existing `UpstreamAlreadyExists` dialog pattern already used elsewhere in the codebase for a related remote-URL decision: [5](#0-4) .

### Proof of Concept
1. Connect a repository in Desktop whose `origin` remote matches the GitHub API's `clone_url` for that repo.
2. Have the GitHub API endpoint (compromised GHE server, malicious proxy, or MITM) return an updated repository object where `clone_url` points to an attacker-controlled git host but still parses with an owner/name that satisfies `urlMatchesRemote`'s hostname/owner/name heuristic (e.g., same owner/name string, different or spoofed hostname resolution).
3. On the next repository metadata refresh, `updateRemoteUrl` finds `protocolsMatch && remoteUrlUnchanged && !urlsMatch` all true and calls `gitStore.setRemoteURL(...)`, silently rewriting `origin`.
4. The user, unaware of the change (no popup/banner/log surfaced to them), later runs "Push" in Desktop, sending commits (and via the credential trampoline, potentially credentials) to the attacker's remote. [1](#0-0)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
