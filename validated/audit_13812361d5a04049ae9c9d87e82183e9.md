Based on my investigation, I found a concrete Desktop analog. The external report's broken invariant is "an attacker-controlled input triggers a privileged, irreversible action with no validation gate." The closest verified local-code equivalent is that `shell.openExternal()` is invoked on attacker-influenced strings with no protocol allow-list anywhere in the call chain from renderer to the OS shell.

### Title
Unrestricted `shell.openExternal()` on attacker-controlled URLs from GitHub API content and IPC - ([File: app/src/main-process/main.ts])

### Summary
Desktop's `open-external` IPC handler and the `_openInBrowser` store method pass any string directly to Electron's `shell.openExternal()` without restricting the URL scheme to `http`/`https`. These paths are reachable from attacker-controlled data such as pull-request comment/review bodies (rendered Markdown) and other GitHub API-sourced content, so a malicious repository/PR author can cause Desktop to hand an arbitrary URI to the OS shell resolver when the user clicks a rendered link.

### Finding Description
The `open-external` IPC handler only logs when a URL starts with `http://`/`https://`; it does not reject other schemes before calling `shell.openExternal(path)`: [1](#0-0) 

Similarly, the renderer-side `_openInBrowser` on `AppStore` forwards its `url` argument straight to `shell.openExternal(url)` with no validation: [2](#0-1) 

That store method is invoked with strings originating from untrusted GitHub API content. For example, Markdown links in a rendered pull-request comment/review body call `dispatcher.openInBrowser(url)` for whatever `url` the Markdown renderer reports as clicked: [3](#0-2) 

The comment/review body itself is attacker-controlled GitHub API data rendered through `SandboxedMarkdown`: [4](#0-3) 

`LinkButton`, used throughout the UI (including for repository-derived URLs such as `repository.htmlURL`), also calls `shell.openExternal(uri)` unconditionally on click with no scheme check: [5](#0-4) 

No code path I found performs a protocol allow-list (e.g., restricting to `https:`) before calling `openExternal`. Electron's `shell.openExternal` ultimately resolves the string via the OS (e.g., `ShellExecute` on Windows, `LSOpenURL`/`open` handlers on macOS), which can invoke any registered custom URI-scheme handler or, for `file://`/UNC-style values, hand off to the OS file-open behavior — well outside the scope of "open this in a web browser."

### Impact Explanation
If an attacker can get an unusual/dangerous URI (a non-`http(s)` scheme, `file://` path, or a URI matching a locally-installed vulnerable protocol handler) into a place Desktop renders as a clickable link — e.g., a PR comment/review body, a repository field from the GitHub API — clicking it hands that value to the OS shell resolver with no gate. Depending on what's registered on the victim's machine, this can range from information disclosure/local file access to code execution via a chained, vulnerable OS-level protocol handler. This matches the "valid impact" criteria: attacker controls a GitHub API object/rendered link, the user performs a normal single click, and the app hands off to a privileged OS mechanism without a trust check.

### Likelihood Explanation
I could not fully verify within the available searches whether `SandboxedMarkdown` (`app/src/ui/lib/sandboxed-markdown.tsx`) already restricts which `href` values are surfaced to the `onMarkdownLinkClicked` callback (e.g., filtering to `http(s)` only) before calling back into the host renderer. This is an important open question that materially affects real-world exploitability of the Markdown-comment vector specifically. Independent of that, the `open-external` IPC handler in `main.ts` and `_openInBrowser`/`LinkButton` themselves perform no scheme validation, so any other caller that forwards unsanitized data (current or future) inherits the same gap.

### Recommendation
Add a single, centralized allow-list check (e.g., only `http:` and `https:`, and for GitHub Enterprise possibly restrict to configured endpoint hosts) at the lowest common point before invoking `shell.openExternal`, e.g., inside `_openInBrowser` in `app-store.ts` and inside the `open-external` IPC handler in `main.ts`, rejecting or warning on any other scheme (`file:`, `javascript:`, custom app-registered schemes, etc.). Ensure `SandboxedMarkdown`'s link-click handler also normalizes/validates `href` before invoking the callback, so this protection isn't solely reliant on call sites remembering to check.

### Proof of Concept
1. As a malicious actor, submit a pull request comment/review whose body contains a Markdown link with a non-`http(s)` URI, e.g. a locally-registered dangerous protocol handler or a `file://` path to an executable/script reachable via a mapped drive or UNC share.
2. Victim receives/opens the PR notification in Desktop; the comment is rendered via `SandboxedMarkdown` in `pull-request-comment-like.tsx`.
3. Victim clicks the link (a natural single click).
4. `onMarkdownLinkClicked` calls `dispatcher.openInBrowser(url)` → `_openInBrowser` → `shell.openExternal(url)` with the raw, unchecked URI.
5. The OS resolves and invokes whatever handler is registered for that scheme/path, outside the browser sandbox and outside the repo's directory.

**Caveat:** I was unable to confirm within the available search budget whether `sandboxed-markdown.tsx` already filters `href` values to `http(s)` before invoking `onMarkdownLinkClicked`; if it does, the Markdown-comment vector specifically may already be mitigated, though the underlying lack of validation in `_openInBrowser`/`main.ts`'s `open-external` handler/`LinkButton` remains as described.

    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
