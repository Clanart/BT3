### Title
Argument injection via attacker-controlled PR head ref name in `createBranch` startpoint - (File: `app/src/lib/git/branch.ts`)

### Summary
When a user checks out a pull request from a fork (including via the `x-github-client://openRepo/...?pr=NNN` deep link handled by `dispatchURLAction` → `openPullRequestFromUrl` → `_checkoutPullRequest`), GitHub Desktop derives a start-point string from the PR's `head.ref` field, which is returned by the GitHub API and is fully controlled by whoever opened the pull request (the "attacker"). This string flows unsanitized into `git branch <name> <startPoint>`.

### Finding Description
`createBranch()` builds its argument vector as:
```ts
const args = startPoint !== null ? ['branch', name, startPoint] : ['branch', name]
``` [1](#0-0) 
No `--` end-of-options separator is used before `startPoint`.

For fork PRs, `startPoint` is `remoteRef = \`${remote.name}/${headRefName}\`` where `headRefName` is `pullRequest.head.ref` — a value taken verbatim from the GitHub API PR object: [2](#0-1) 
This flows from the deep-link/PR-open path: [3](#0-2) 

Compare this to `checkoutBranch()` for local/remote branches, which explicitly appends `--` before the ref to guard against argument injection: [4](#0-3) 
No equivalent protection exists in `createBranch()`.

Other similarly attacker-influenced ref-name paths in the codebase (branch names from deep links) are explicitly validated with `testForInvalidChars`/`sanitizedRefName`, which reject/replace leading `-`/`+` characters: [5](#0-4) 
But `headRefName`/`remoteRef` used as the `startPoint` argument to `createBranch` never passes through this sanitizer — it's a raw GitHub-API string, not a locally-typed branch name, so none of the existing UI-level guards (`RefNameTextBox`, `parseAppURL`'s `testForInvalidChars`) apply to it.

Because `git branch` (unlike `git checkout`) is invoked without `--`, a `startPoint` value starting with `-` would be parsed by Git as an option rather than a revision. A remote head ref cannot literally contain `-` as its very first character in a way `git ls-remote` would report as a valid ref name only under some naming edge cases, but the more concrete risk is when `remote.name` itself is attacker-influenced via `forkPullRequestRemoteName(headRepoOwner)` — if `headRepoOwner` (also API-controlled) can begin with `-` after the `github-desktop-` prefix is applied, or if a future refactor drops the prefix, the resulting `startPoint` string could begin with a dash, letting an attacker smuggle Git CLI flags (e.g. `--track`) into the `git branch` invocation that runs on the victim's checkout of an untrusted PR.

### Impact Explanation
If exploitable, this allows an attacker (a PR author on GitHub) to influence the arguments passed to `git branch` on a victim's machine when the victim uses Desktop's "Open PR from Desktop" / checkout-PR feature, potentially altering tracking configuration or other `git branch` flag-controlled behavior without the user's knowledge — a silent corruption of the local repository state, which fits the "silent corruption of what the user commits/pushes" impact category.

### Likelihood Explanation
Likelihood is moderate-to-low: the primary attacker-controlled string (`headRefName`) is prefixed by a locally-derived, prefixed remote name (`github-desktop-<owner>/<ref>`), which in the common case does not start with `-`. Exploitation requires a scenario where the constructed `remoteRef` string can begin with a dash, which is not clearly reachable in the current code path — I could not confirm a concrete way to make `remote.name` (`forkPullRequestRemoteName(headRepoOwner)`) begin with `-` given the `github-desktop-` prefix, so this should be treated as a defense-in-depth gap rather than a confirmed exploitable primitive.

### Recommendation
Add a `--` separator before `startPoint` in `createBranch()` in `app/src/lib/git/branch.ts`, mirroring the pattern already used in `checkoutBranch()` (`app/src/lib/git/checkout.ts`), so that any future or edge-case attacker-influenced start-point value cannot be interpreted as a Git command-line option.

### Proof of Concept
1. Attacker opens a pull request against a repository the victim has cloned, from a fork whose owner login and branch name are crafted such that the resulting `remoteRef` (`<forkRemoteName>/<headRefName>`) begins with `-` (requires further verification of exact naming constraints imposed by `forkPullRequestRemoteName`).
2. Victim opens the PR via "Open in Desktop" (`x-github-client://openRepo/...?pr=<n>`) or the in-app "View on GitHub" → checkout-PR flow.
3. `_checkoutPullRequest` → `_findPullRequestBranch` computes `remoteRef` and calls `_createBranch(repository, "pr/<n>", remoteRef, false)` [6](#0-5) .
4. `createBranch()` executes `git branch pr/<n> <remoteRef>` with no `--` separator [7](#0-6) , allowing `<remoteRef>` to be parsed as Git flags if it begins with `-`.

Note: I was unable to fully verify (within the available index) whether `forkPullRequestRemoteName`/`headRepoOwner` sanitization elsewhere in the codebase prevents the leading-dash condition needed to fully weaponize this; a Devin session with full repo access would be needed to trace `forkPullRequestRemoteName` and any owner-login validation to confirm end-to-end exploitability.

export async function createBranch(
  repository: Repository,
  name: string,
  startPoint: string | null,
  noTrack?: boolean
): Promise<void> {
  const args =
    startPoint !== null ? ['branch', name, startPoint] : ['branch', name]

  // if we're branching directly from a remote branch, we don't want to track it
  // tracking it will make the rest of desktop think we want to push to that
  // remote branch's upstream (which would likely be the upstream of the fork)
  if (noTrack) {
    args.push('--no-track')
  }

  await git(args, repository.path, 'createBranch')
}

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}
