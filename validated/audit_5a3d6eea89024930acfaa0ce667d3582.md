### Title
Unvalidated Participant indexes in PedPoP blame handling panic on HashMap indexing, enabling remote DoS - (File: crypto/dkg/pedpop/src/encryption.rs, crypto/dkg/pedpop/src/lib.rs)

### Summary
The Mattermost Confluence report is a "malformed/unexpected input crashes a request handler" bug. The direct Serai analog lives in the PedPoP DKG blame path: `BlameMachine::blame`, `AdditionalBlameMachine::blame`, and `blame_internal` accept attacker-chosen `sender`/`recipient` `Participant` values plus an attacker-supplied `EncryptedMessage`/`EncryptionKeyProof`, and then index `HashMap`s with those values. `HashMap`'s `Index` impl panics on a missing key, so any accusation naming a `sender` or `recipient` outside the registered set crashes the process instead of returning a `PedPoPError`.

### Finding Description
`AdditionalBlameMachine::new` registers exactly `n` encryption keys and commitments, for `Participant(1) ..= Participant(n)`:

```rust
// crypto/dkg/pedpop/src/lib.rs:656-660
for i in 1 ..= n {
  let i = Participant::new(i).unwrap();
  let Some(msg) = commitment_msgs.remove(&i) else { Err(PedPoPError::MissingParticipant(i))? };
  commitments.insert(i, encryption.register(i, msg).commitments);
}
```

`blame` forwards the caller-supplied `sender`/`recipient` straight into `blame_internal` with no membership check:

```rust
// crypto/dkg/pedpop/src/lib.rs:680-682
pub fn blame(&self, sender: Participant, recipient: Participant, ...) -> Participant {
  self.0.blame_internal(sender, recipient, msg, proof)
}
```

`blame_internal` first calls `decrypt_with_proof`, which panics if `decryptor` was never registered:

```rust
// crypto/dkg/pedpop/src/encryption.rs:383-389
proof.dleq.verify(
  &mut encryption_key_transcript(self.context),
  &[C::generator(), msg.key],
  &[self.enc_keys[&decryptor], *proof.key],
)
```

If the proof check is skipped/short-circuited and execution reaches share verification, a second unchecked index panics on an out-of-set `sender`:

```rust
// crypto/dkg/pedpop/src/lib.rs:596-600
multiexp_vartime(&share_verification_statements::<C>(
  recipient,
  &self.commitments[&sender],
  Zeroizing::new(share),
))
```

The same panic exists in `Decryption::register` (`assert!(!self.enc_keys.contains_key(&participant))` at encryption.rs:356-360), reachable via `SecretShareMachine::verify_r1` — although that path is protected by `validate_map`, the blame paths have no equivalent guard. The doc comment on `AdditionalBlameMachine::new` (lib.rs:646-648) acknowledges this: "Usage of invalid commitments is considered undefined behavior, and may cause everything from inaccurate blame to panics."

### Impact Explanation
An unprivileged DKG participant (or any party able to submit a blame accusation to an honest node running PedPoP) can crash the victim's key-generation process at will by accusing a `sender`/`recipient` index that is not in `1 ..= n` (e.g., `Participant::new(n + 1)`, or any participant whose commitments were never delivered). Since `blame` returns `Participant` — not `Result` — there is no error path; the `HashMap` index panic unwinds through the caller, aborting the DKG session and, depending on the host, the whole coordinator/processor task. Repeated accusations produce repeated crashes, mirroring the CVE's "constant hit to the endpoint with an invalid request body" availability impact. This matches the accepted impact class of a reachable crash/DoS from public inputs (`EncryptedMessage::read`, `EncryptionKeyProof::read`, and blame API parameters).

### Likelihood Explanation
High. The panic requires no cryptography: the attacker only needs to invoke `blame` with an out-of-range `Participant` (a `u16`) and any well-formed `EncryptedMessage`/`EncryptionKeyProof` bytes — or even malformed ones, since `enc_keys[&decryptor]` is evaluated inside the `verify` call arguments only after the `msg.pop` Schnorr verification succeeds; with `proof: Some(...)`, reaching the index requires a valid PoP, which the attacker can generate for their own registered key, while still naming an unregistered `decryptor`. The `commitments[&sender]` panic needs only a `sender` outside the registered set plus a canonically-encoded share. Both are trivially constructible by any participant.

### Recommendation
Replace panicking `HashMap` indexing and the `assert!` in the blame/decryption path with fallible lookups returning `PedPoPError` (e.g., a new `UnknownParticipant(Participant)` variant):

```rust
let Some(enc_key) = self.enc_keys.get(&decryptor) else {
  return Err(DecryptionError::InvalidProof); // or a dedicated UnknownDecryptor error
};
```
and in `blame_internal`:

```rust
let Some(sender_commitments) = self.commitments.get(&sender) else {
  return sender; // or return an error
};
```
Additionally, validate `sender`/`recipient` against `1 ..= n` at the top of `BlameMachine::blame` and `AdditionalBlameMachine::blame` before any map access, so malformed accusations are rejected as errors rather than crashing the node.

### Proof of Concept
```rust
use pedpop::*;
use ciphersuite::Ristretto;
use dkg::ThresholdParams;
use rand_core::OsRng;
use std::collections::HashMap;

// Honest node finished a 2-of-3 PedPoP DKG and built an AdditionalBlameMachine
// from the three authenticated commitment messages (commitment_msgs: HashMap<_, _>).
let machine = AdditionalBlameMachine::<Ristretto>::new(context, 3, commitment_msgs).unwrap();

// Attacker-controlled inputs: a sender/recipient outside 1..=3 and any bytes for msg.
let attacker_sender = Participant::new(4).unwrap(); // never registered
let msg: EncryptedMessage<Ristretto, SecretShare<_>> =
  EncryptedMessage::read(&mut &attacker_bytes[..], params).unwrap();

// PANIC: decrypt_with_proof indexes self.enc_keys[&recipient] and/or
// blame_internal indexes self.commitments[&sender] -> HashMap index panic -> DoS.
machine.blame(attacker_sender, Participant::new(1).unwrap(), msg, Some(proof));
```

Concrete panic sites:
- `self.enc_keys[&decryptor]` — `crypto/dkg/pedpop/src/encryption.rs:388` (no `.get()`; `HashMap` `Index` panics on missing key).
- `self.commitments[&sender]` — `crypto/dkg/pedpop/src/lib.rs:599`.
- Registration-side `assert!` — `crypto/dkg/pedpop/src/encryption.rs:356-360` (duplicate-key panic if reachable through a caller that doesn't dedupe, though `verify_r1` mitigates via `validate_map`).

Caveat: whether a host exposes `blame` to unauthenticated input depends on the integrator, but the function is explicitly designed to evaluate accusations supplied by other (potentially malicious) participants, so attacker-controlled `sender`/`recipient`/`msg`/`proof` is the intended input domain — exactly like the webhook endpoint in the CVE.
