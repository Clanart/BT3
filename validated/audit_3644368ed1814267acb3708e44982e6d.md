### Title
`IetfTranscript` Discards Domain Separator and All Message/Challenge Labels, Yielding Context-Free Schnorr Challenges - (File: crypto/frost/src/algorithm.rs)

### Summary
Analogous to the reported bug (a parameter ignored and a constant substituted for it), `IetfTranscript` — the IETF-compatible transcript exposed via `IetfSchnorr::ietf()` — discards every binding input that distinguishes transcript contexts: `new(_: &'static [u8])` throws away the DST and always initializes an empty buffer, `domain_separate(&mut self, _: &[u8])` is a no-op, `append_message(&mut self, _: &'static [u8], message)` ignores its label, and `challenge(&mut self, _: &'static [u8])` ignores the challenge label and returns the raw accumulated buffer. The result is that the FROST binding factor `rho` and the Schnorr challenge produced through `Algorithm::sign_share` are computed from a transcript that is a constant function of the wire bytes only, independent of the domain or labels the caller supplied.

### Finding Description
In `crypto/frost/src/algorithm.rs`, the sealed `IetfTranscript` implements `Transcript` but drops every context parameter:

```rust
impl Transcript for IetfTranscript {
  fn new(_: &'static [u8]) -> IetfTranscript { IetfTranscript(vec![]) }
  fn domain_separate(&mut self, _: &[u8]) {}
  fn append_message<M: AsRef<[u8]>>(&mut self, _: &'static [u8], message: M) {
    self.0.extend(message.as_ref());
  }
  fn challenge(&mut self, _: &'static [u8]) -> Vec<u8> { self.0.clone() }
}
```

This is structurally identical to the reported `let value = 0; // ignores _value` pattern: the caller passes a domain separator, message labels, and challenge labels, and the implementation substitutes a fixed constant (empty context / unlabeled concatenation). Any two FROST deployments, or two different signing protocols over the same `ThresholdKeys`, that both use `IetfSchnorr::ietf()` therefore produce bit-identical challenge transcripts whenever the concatenated bytes coincide. `append_message` also performs no length-prefix framing — it is a raw `extend` — so `append_message(a, b)` collides with `append_message(ab)` for any split, compounding the collision surface. `BindingFactor::calculate_binding_factors` in `crypto/frost/src/nonce.rs` and `Schnorr::sign_share`/`verify` in `crypto/frost/src/algorithm.rs` (via `H::hram(R, A, m)`) both consume this transcript/challenge, so the missing binding propagates into the produced signatures.

### Impact Explanation
The domain separator is the mechanism that scopes a signature to its intended protocol context. Because it is replaced by a constant (empty) value, a Schnorr/FROST signature or signature share produced for a message `m` under `IetfSchnorr` is byte-for-byte valid for the same key and the same `R` in any other context that also uses `IetfSchnorr`. Concretely, an unprivileged party who can cause the threshold group to sign a chosen message in context A (e.g., a low-stakes signing request) obtains a signature that verifies for that message under context B, even though B's designers passed a distinct DST believing it isolated their signatures. This is signing-acceptance of an unintended (cross-context) message. Additionally, the unframed `append_message` means two different internal transcript layouts (e.g., different nonce/commitment arrangements fed through `Commitments::transcript`) can produce the same challenge bytes, weakening the participant/commitment binding that FROST's `rho` relies on.

### Likelihood Explanation
Reachability requires an attacker who can get the group to sign attacker-influenced messages — the standard threat model for FROST signers — plus a second context using the same group key and the naive transcript (or a transcript whose byte encoding collides with the concatenation). The collision is deterministic whenever it occurs; no probabilistic or colluding-validator assumption is needed. However, `IetfTranscript` is documented as "incredibly naive and should not be used within larger protocols," which mitigates the impact in disciplined integrations; the vulnerability materializes only when it is actually used for interop, which is its stated purpose (`IetfSchnorr` exists "in order to provide compatibility"). Given the conditional deployment requirement but deterministic effect, this is Medium.

### Recommendation
Do not silently discard transcript parameters. Either:
1. Prefix the DST into the transcript in `IetfTranscript::new` (`self.0.extend(domain)`), include labels in `append_message`/`challenge` with length-prefixed framing, and implement `domain_separate` as an actual separator marker; or
2. If strict byte-level IETF compatibility requires the current semantics, restrict `IetfSchnorr::ietf()` behind an explicit unsafe/`#[doc(hidden)]`-style API and enforce at the `AlgorithmMachine`/`ThresholdKeys` layer that a group key used with `IetfTranscript` cannot be reused with any other transcript/context.

### Proof of Concept
```rust
// Two distinct contexts produce identical challenge inputs.
let mut t1 = IetfTranscript::new(b"protocol-A-signature-v1");
let mut t2 = IetfTranscript::new(b"protocol-B-signature-v1");
// t1 == t2 == IetfTranscript(vec![]) — DST was dropped.

t1.domain_separate(b"session-1");
t2.domain_separate(b"session-2");
// Still identical; domain_separate is a no-op.

t1.append_message(b"nonce", b"AB");
t2.append_message(b"commitment", b"A"); t2.append_message(b"x", b"B");
// t1.0 == t2.0 == b"AB" — labels ignored and no framing,
// so differently-structured transcripts collide.

assert_eq!(t1.challenge(b"rho"), t2.challenge(b"challenge"));
// Identical challenges => a FROST signature share/R,S produced in
// context A verifies as a valid Schnorr signature in context B for
// the same group key, despite the callers supplying distinct domains.
```

The root cause is confirmed directly in `crypto/frost/src/algorithm.rs`: `IetfTranscript::new` discards its `&'static [u8]` argument (line ~107), `domain_separate` is an empty function (line ~111), and `append_message`/`challenge` ignore their label arguments (lines ~113, ~117), with the resulting unbound challenge feeding `BindingFactor::calculate_binding_factors` (`crypto/frost/src/nonce.rs`) and `Schnorr::sign_share`/`verify` (`crypto/frost/src/algorithm.rs`).
