### Title
Pool wallet `target_state` sticks after `generate_travel_transactions` reverts, permanently blocking join/self-pool - (File: `chia/pools/pool_wallet.py`)

### Summary
`PoolWallet.join_pool()` and `PoolWallet.self_pool()` set the in-memory pending-transition field `self.target_state` (plus `next_transaction_fee`/`next_tx_config`) *before* calling `generate_travel_transactions()`, which performs coin selection and fee/transaction generation that can raise. Because a Python exception does not roll back a prior attribute assignment (unlike a Solidity `revert`, which does roll back state), a failure inside `generate_travel_transactions()` leaves `self.target_state` permanently set even though no travel transaction was ever created or pushed. This is structurally the same bug class as the referenced report: a state field is updated as part of an operation that then fails/reverts, and the state update is not rolled back together with the rest of the operation, leaving the exposed status inconsistent with reality.

### Finding Description
In `join_pool()`: [1](#0-0) 
`self.target_state = target_state` is assigned, then `generate_travel_transactions(fee, action_scope)` is awaited. That method performs `get_current_state()`, builds the travel spend, and — when `fee > 0` — calls `generate_fee_transaction()` which delegates to `standard_wallet.generate_signed_transaction()`, a call that can raise (e.g. on coin selection/insufficient balance failures) before any transaction is queued: [2](#0-1) 

`self_pool()` has the identical pattern — `self.target_state` is assigned first, then `generate_travel_transactions()` is awaited, with no exception handling to revert the assignment on failure: [3](#0-2) 

Once `self.target_state` is non-`None`, both entry points refuse to run again: [4](#0-3) [5](#0-4) 

The only code path that clears `target_state` is `apply_state_transition()`, which clears it when a matching on-chain spend for that *exact* target state is later observed: [6](#0-5) 

Since the failed call never produced or pushed a matching spend, that condition can never become true, so `target_state` remains stuck until the wallet process is restarted (this field is not persisted/restored by `create_from_db()`): [7](#0-6) 

This mirrors the report's root cause precisely: an operation writes a pending/target state before performing a fallible sub-operation, and a failure in that sub-operation is not accompanied by a rollback of the earlier state write, producing a state that misrepresents the wallet's true condition to callers (RPC `pw_status`) and to future calls.

### Impact Explanation
This is reachable by any local wallet user (or RPC caller acting on their behalf) invoking `pw_join_pool` / `pw_self_pool` with parameters that trigger a failure inside `generate_travel_transactions()` (for example insufficient spendable balance to cover `fee`, or any other exception raised during coin selection/spend construction). After the failure:
- `PoolWalletInfo.target` (exposed via `pw_status` RPC) will show a pending target state that in fact never has, and never will, execute, misleading the user about the state of their plot-NFT/pool participation — directly analogous to the report's "state shows open/pending when the actual operation did not succeed."
- All subsequent `join_pool`/`self_pool` calls on that wallet raise `ValueError` ("Cannot join a pool while waiting for target state...") indefinitely, effectively halting the user's ability to manage their pooling wallet until the wallet node is restarted (which clears the unpersisted in-memory field).

This qualifies as a spend/action-triggered transaction-processing halt for an unprivileged wallet user, which is within the accepted impact categories.

### Likelihood Explanation
Likelihood is moderate-to-high: any ordinary user error (setting a `fee` greater than their spendable/available balance, or hitting any other exception raised while `generate_travel_transactions()` builds the fee/travel spend) triggers this without any adversarial behavior. No special privileges or network conditions are required — a single malformed or under-funded `pw_join_pool`/`pw_self_pool` RPC call from the wallet owner is sufficient.

### Recommendation
Wrap the `self.target_state`/`next_transaction_fee`/`next_tx_config` assignment and the call to `generate_travel_transactions()` in a `try`/`except` in both `join_pool()` and `self_pool()`, resetting `self.target_state` to `None` (and clearing `next_transaction_fee`/`next_tx_config`) if `generate_travel_transactions()` raises, so that a failed attempt does not leave the wallet in an unrecoverable pending state. Alternatively, only set `self.target_state` after `generate_travel_transactions()` has successfully completed and produced a transaction to push.

### Proof of Concept
1. Create a plot-NFT/pool wallet in `SELF_POOLING` state with a small XCH balance (e.g. only 1 mojo beyond the minimum reserved for the singleton).
2. Call `pw_join_pool` with a `fee` value greater than the wallet's spendable balance.
3. `join_pool()` sets `self.target_state = target_state` at `chia/pools/pool_wallet.py:669`, then calls `generate_travel_transactions(fee, action_scope)`.
4. Inside `generate_travel_transactions()`, since `fee > 0`, `generate_fee_transaction()` is called, which calls `standard_wallet.generate_signed_transaction()`; this raises because there aren't enough spendable coins to cover the fee.
5. The exception propagates out of `join_pool()` back to the RPC caller as a failure — but `self.target_state` remains set to the requested `target_state`.
6. Subsequent calls to `pw_status` show a non-`None` `target` even though no transaction was ever created or broadcast.
7. Any further call to `pw_join_pool` or `pw_self_pool` on this wallet immediately raises `ValueError("Cannot join a pool while waiting for target state...")` / `"Cannot self pool when already having target state..."`, permanently blocking the user until the wallet node process is restarted.
