## Analysis

The external report's core broken invariant is: **a reward computed over a time/height span is paid out based on batch-level bookkeeping (`cycleStart`/`cycleEnd`) rather than being tied to the specific participant who actually earned each portion of that span**, letting one party sweep a reward that spans work/participation it did not perform.

The closest local analog is Hyperbridge's relayer consensus-delivery incentive pallet, `pallet-consensus-incentives`. Its `FeeHandler::on_executed` implementation attributes **the entire batch's reward** to a single relayer identity that is derived from decoding only `messages[0]`, while the actual reward amount is computed by scanning **every** `StateMachineUpdated` event in the whole batch: [1](#0-0) 

Critically, the "relayer" for the whole batch is derived purely from a self-provided signature embedded in `messages[0]`, verified only against `keccak256(consensus_msg.consensus_proof)` — data that is fully public (it's the very same proof bytes carried in the message): [2](#0-1) 

Compare this to the sibling `pallet-relayer` outbound-consensus claim path, which deliberately binds the payee to the actual epoch validator set via `EvmHost._epochs[set_id]` recovered from a state proof — a much stronger binding than a bare self-signature over public bytes: [3](#0-2) 

The reward magnitude itself is a simple `blocks_since_watermark * block_cost` computation with no restriction that ties it to work performed by the specific signer in `messages[0]`: [4](#0-3) 

### Title
Consensus-incentive reward misattribution — single self-signed message can capture rewards for an entire multi-state-machine batch — (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::on_executed` decodes a "relayer" identity from only `messages[0]` of a processed batch, then pays that single identity for **every** `StateMachineUpdated` event contained in the whole batch — regardless of which specific message produced which event. Because the signature that establishes the relayer's identity is only checked against `keccak256(consensus_proof)` (public bytes already carried in the message, with no binding to extrinsic origin, msg.sender, or the destination chain's actual validator set), any unprivileged party can insert a self-crafted, self-signed message ahead of a batch to redirect the treasury payout for the whole batch's block-span rewards to themselves.

### Finding Description
`on_executed` computes `maybe_relayer_account` solely from `messages.get(0)`: [2](#0-1) 

It then aggregates the *highest* `latest_height` per `state_machine_id` across **all** `events` in the batch and pays the single relayer derived above for each one: [5](#0-4) 

The signature check backing this attribution has no connection to:
- The extrinsic's origin (the call is unsigned via `ensure_none`, per the sibling pallet's documented pattern of `validate_unsigned` tags being the only spam guard elsewhere in the codebase — no such origin binding exists here).
- The destination chain's actual consensus/validator identity (contrast with `outbound_consensus.rs`, which recovers an address from `EvmHost._epochs[set_id]` via a state proof before paying anything).

It is only a self-signature over `keccak256(consensus_proof)` — bytes that are already public within the same message. This means the "attribution" step proves nothing about who produced the proof, who paid gas for the relay, or who did the underlying light-client work for the other state machines in the batch.

This mirrors the H-04 pattern precisely: the reward window/"cycle" is a batch of `StateMachineUpdated` events spanning potentially several state machines and multiple blocks of accrued `block_cost`, and payout is determined by coarse batch-level position (`messages[0]`) rather than per-event/per-message provenance — letting a party with no real participation in advancing most of the batch's state machines claim the full reward for all of them.

### Impact Explanation
This allows unauthorized diversion of `Currency::transfer` from the protocol treasury (`T::TreasuryAccount`) to an attacker-controlled account, plus minted `ReputationAsset` tokens, for consensus deliveries the attacker did not perform. This is a direct "wrong beneficiary/amount" fund-movement bug against the treasury, matching the bounty's accepted impact category (unauthorized execution / logic attack causing incorrect fund distribution), reachable by any unprivileged actor able to submit an unsigned extrinsic (the same permissionless surface every legitimate relayer already uses).

### Likelihood Explanation
Exploitability depends on unsigned message batches (`Vec<Message>`) being able to combine an attacker-crafted `Message::Consensus` at index 0 alongside genuinely-processed messages for other state machines in a single `handle_unsigned` call, and on the FeeHandler still executing `on_executed` with that full batch/events set even if the attacker's own message content is otherwise inert. I was not able to fully confirm from the indexed code how `handle_unsigned` populates the `messages` argument passed into `FeeHandler::on_executed` when one message in the batch is invalid/unrelated to the resulting events (e.g., whether a bogus message[0] would abort the whole extrinsic or merely occupy position 0 while other messages still execute and emit events). This is the key uncertainty and should be verified directly against `pallet-ismp`'s message-dispatch code before treating this as fully weaponizable, since some resolution of the reward-collapsing issue documented in the surrounding comment (`highest_per_state_machine`) suggests the team is already actively hardening this exact reward-attribution path.

### Recommendation
Attribute and pay rewards per-message rather than per-batch: derive the relayer identity from the specific `Message::Consensus` that produced each `StateMachineUpdated` event (pairing message index to event), rather than reusing `messages[0]`'s signer for every event in the batch. Additionally, bind the reward-eligibility signature to something that cannot be freely produced by an uninvolved third party — e.g., require the signer to match the destination chain's actual light-client/validator identity (as `outbound_consensus.rs` already does via `EvmHost._epochs[set_id]`), rather than a bare self-attestation over publicly-known proof bytes.

### Proof of Concept
Conceptual sequence (exact feasibility gated by the `handle_unsigned` batching semantics noted above):
1. Attacker observes (or constructs) a legitimate pending batch of `Message::Consensus` entries destined for `pallet_ismp::Pallet::handle_unsigned`, covering multiple `StateMachineId`s with configured `StateMachinesCostPerBlock`.
2. Attacker crafts their own `Message::Consensus` whose `signer` field is `Signature::Sr25519 { public_key: attacker_pubkey, signature: sign(attacker_key, keccak256(consensus_proof_bytes)) }` — valid regardless of whether `consensus_proof_bytes` is attacker's own or copied/observed public proof bytes — and submits it as `messages[0]` in the same/adjacent unsigned extrinsic batch.
3. `on_executed` decodes `relayer_account = attacker` from `messages[0]` and, iterating `highest_per_state_machine` over the full `events` vec, pays `attacker` the accumulated `blocks * block_cost` reward for every state machine advanced in that batch via `process_message` → `T::Currency::transfer` from `T::TreasuryAccount`, as shown in: [6](#0-5) 
4. Legitimate relayers who actually produced/submitted the other proofs in the batch receive nothing for that batch.

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {

			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
