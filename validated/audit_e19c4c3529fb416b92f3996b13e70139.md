### Title
Malformed `ThresholdKeys` deserialize to an arbitrary public key and enable signature forgery - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary

`ThresholdKeys::read` accepts a secret share and a set of verification shares without checking that the secret share actually corresponds to the caller's verification share. For a `1-of-1` key, an untrusted serialized key can therefore declare any victim public key as its verification share while using secret share `0`; FROST will still sign and `complete` will return a signature that verifies under that victim key. [1](#0-0) [2](#0-1) 

### Finding Description

`ThresholdKeys::read` parses `t`, `n`, the participant index, the interpolation mode, one scalar secret share, and `n` public verification shares, then forwards them directly to `ThresholdKeys::new`. [3](#0-2) 

`ThresholdKeys::new` checks only the number and indexes of verification shares and the applicability of the interpolation mode; it then computes the group key from the first `t` verification shares. [2](#0-1) 

There is no check equivalent to:

```rust
C::generator() * secret_share == verification_shares[&params.i()]
```

For `t = n = 1`, `i = 1`, and Lagrange interpolation, `ThresholdKeys::new` sets `group_key` directly to the supplied verification share. [4](#0-3) 

During signing, `view` interpolates the attacker-supplied secret share unchanged for the single included participant. [5](#0-4)  The Schnorr algorithm then produces `s = r + c * secret_share`; with `secret_share = 0`, this becomes `s = r`, while verification still uses the forged `group_key = victim_key`. [6](#0-5)  `AlgorithmSignatureMachine::complete` accepts the result whenever the Schnorr verification formula succeeds. [7](#0-6) 

### Impact Explanation

An attacker who can supply a serialized `ThresholdKeys` blob to an import, recovery, or signing path can mint valid Schnorr signatures for an existing group public key without knowing its discrete logarithm or any legitimate key share. [8](#0-7) 

This is a signature-forgery primitive rather than merely a malformed-input rejection issue: the deserializer creates a semantically invalid private-key object whose declared public key is independent of its private share. Any caller that treats successful parsing as proof that the blob is a valid threshold key can be induced to emit signatures under a public key it does not control. [9](#0-8) [10](#0-9) 

### Likelihood Explanation

The exploit requires an attacker-controlled serialized `ThresholdKeys` value to reach `ThresholdKeys::read` and then a signing API. That is a narrower boundary than a wholly remote signature request, but it is plausible wherever key blobs are imported, restored, exchanged, or accepted from less-trusted components. Once reachable, the construction is deterministic and does not require race conditions, malformed curve encodings, or brute force. [1](#0-0) 

The root cause is not probabilistic: the code validates syntax and participant indexes but never validates the fundamental key-binding relation between `secret_share` and `verification_shares[i]`. [11](#0-10) 

### Recommendation

Before constructing `ThresholdKeys`, verify that the local secret share matches the local verification share:

```rust
if C::generator() * secret_share.deref() != verification_shares[&params.i()] {
  return Err(...);
}
```

This check should be performed in `ThresholdKeys::new` so every deserialization and construction path enforces it. [12](#0-11) 

For `n > 1`, this check alone cannot prove that every claimed verification share came from one consistent threshold polynomial. Serialized keys should therefore either remain authenticated private protocol state, or include the DKG commitments/proof material needed to validate the full verification-share set. At minimum, `ThresholdKeys::read` should document that it must not consume unauthenticated key blobs. [13](#0-12) 

### Proof of Concept

Conceptually, for any target public key `A` on the selected ciphersuite:

```rust
// Serialized ThresholdKeys fields, after the curve ID:
t = 1
n = 1
i = 1
interpolation = Lagrange
secret_share = 0
verification_shares[1] = A
```

`ThresholdKeys::read` accepts this object, and `group_key()` becomes `A` because the single verification share is used directly as the group key. [4](#0-3) 

A `1-of-1` signing session then needs no remote participants:

```rust
let keys = ThresholdKeys::<C>::read(&mut forged_blob.as_slice()).unwrap();
assert_eq!(keys.group_key(), victim_public_key);

let (machine, _preprocess) =
  AlgorithmMachine::new(schnorr_algorithm, keys).preprocess(&mut OsRng);

let (machine, _share) = machine.sign(HashMap::new(), message).unwrap();
let signature = machine.complete(HashMap::new()).unwrap();
```

The local nonce produces `R = rG`; because the supplied secret share is zero, the completed signature satisfies `sG = R + cA`, so `complete` returns a signature under `victim_public_key`. [6](#0-5) [14](#0-13)
