### Title
Embedded fake conflict-marker text in incoming branch content causes silent splice-misalignment and marker leakage in Copilot conflict resolution - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Sherlock report's broken invariant is: an external, attacker-influenced value (the oracle "liveness" state) is trusted as fresh without verifying its integrity before being used to gate a critical decision. The closest verifiable Desktop analog is in the AI conflict-resolution feature: two independently duplicated conflict-marker parsers — `extractConflictHunks` (used to build the model prompt and the "expected hunk count") and `reassembleResolvedFile` (used to splice the model's output back into the file) — both use a naive regex match for `>>>>>>> ` / `<<<<<<< ` / `=======` lines *anywhere* in the file, including inside content supplied by the "theirs" (incoming/remote) side of a merge. Neither function verifies that the matched marker line is the *genuine* boundary Git itself inserted, so attacker-controlled branch content containing a line that merely looks like a marker is silently treated as a real boundary.

### Finding Description
`extractConflictHunks` in [1](#0-0)  defines marker regexes that match any line starting with 7 `<`, `|`, `=`, or `>` characters, with no context awareness of whether that line is actually a Git-inserted marker or ordinary file content. While collecting `theirsContent`, the parser stops at the *first* line matching `theirsMarker`: [2](#0-1) 

Independently, `reassembleResolvedFile` in `copilot-conflict-resolution.ts` re-implements the same boundary detection from scratch using its own copies of the marker regexes: [3](#0-2) 
and splices resolved content up to the first matching closing marker it finds: [4](#0-3) 

Both parsers are logically duplicated but not provably identical, and neither validates that a matched marker line is genuinely Git-inserted (e.g. by checking it isn't nested inside already-collected hunk content, or by using Git's own conflict-hunk boundaries instead of re-parsing raw text). Because the "theirs" side of a conflict originates from a remote branch/PR that the user is merging or rebasing — i.e., attacker-controlled content — an attacker can craft a line that satisfies `oursMarker`, `separatorMarker`, or `theirsMarker` (e.g. a line consisting of `>>>>>>> footer` in a changelog, or documentation about Git internals) inside the content on their side of a real conflict. This causes:
1. `extractConflictHunks` to truncate `theirsContent` early and hand a shortened hunk to the model with `validateResolutionPaths` ( [5](#0-4) ) validating only path/hunk-count consistency — not marker-boundary correctness.
2. `reassembleResolvedFile` to independently stop splicing at the same fake marker, then copy the remaining text — including the genuine, unresolved `>>>>>>> ...` marker line from Git — through as ordinary file content (per its own "malformed marker" fallback: [6](#0-5) ).

The result is a file that Desktop reports as "resolved" and stages for commit, but which still contains a literal, unresolved Git conflict-marker string embedded mid-file.

### Impact Explanation
This is a "silent corruption of what the user commits or pushes": the AI conflict-resolution flow (`app/src/lib/stores/copilot-store.ts`, `runConflictResolutionTurn`/`parseCopilotConflictResolution`/`validateResolutionPaths`/`reassembleResolutions` pipeline, [7](#0-6) ) reports success and produces content that appears merged, while actually leaving corrupted/garbage marker text embedded in code that the user then commits and pushes — without any validation step flagging the residual marker or the truncated hunk boundary. Depending on the file type (source code, config, CI YAML) this can silently break builds, alter program behavior, or introduce a hard-to-notice defect that ships to production, all without the user reviewing raw diff markers because the tool claims full resolution.

### Likelihood Explanation
The precondition is only that the "incoming" (theirs) side of a real, ordinary Git conflict — content an attacker fully controls by contributing a branch/PR/commit that the victim later merges or rebases — contains one line that happens to satisfy `^<{7}(?:\s|$)`, `^={7}$`, or `^>{7}(?:\s|$)`. This is trivially craftable (e.g., a fake changelog entry, ASCII art, a code comment illustrating Git conflict syntax) and requires no local access, no admin rights, and no unusual user action beyond the ordinary "merge/rebase and click Resolve with Copilot" flow that this feature exists to serve. No existing guard in `validateResolutionPaths` or `reassembleResolutions` checks marker-boundary integrity — only path membership and hunk *count*, which is derived from the same flawed parser and therefore self-consistently wrong.

### Recommendation
- Do not re-derive conflict boundaries independently in `reassembleResolvedFile`. Instead, have `extractConflictHunks` record the exact line offsets (start/end indices) of each marker block and pass those offsets through to reassembly, so splicing operates on Git-verified positions rather than re-scanning raw text.
- When parsing markers, require that a `theirsMarker`/`separatorMarker` line encountered while inside a hunk is only accepted as a real boundary if it is not immediately followed by more theirs-side content that itself contains no matching closing structure (or, better, only trust boundaries derived once per file and shared between both functions via a single source of truth).
- After reassembly, scan the final resolved content for leftover marker-shaped lines (`^<{7}`, `^={7}$`, `^>{7}`) and treat their presence as a validation failure (throw `CopilotValidationError`) rather than silently committing them.

### Proof of Concept
1. Attacker pushes a branch/PR where a file's added content includes, among ordinary lines, a line exactly reading `>>>>>>> release-notes` (7 `>` + space + text).
2. Victim merges/rebases this branch into a file that also has a genuine local (`ours`) change to the same region, producing a real Git conflict:
   ```
   <<<<<<< HEAD
   our change
   =======
   some content
   >>>>>>> release-notes
   more attacker content
   >>>>>>> feature
   ```
3. Victim opens Desktop, triggers "Resolve conflicts with Copilot."
4. `extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:228-242`) stops `theirsContent` collection at the embedded `>>>>>>> release-notes` line, treating it as the hunk's real closing marker; the model receives only `some content` as theirs.
5. `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:559-598`) independently detects the same embedded line as the closing marker and splices the model's resolution only up to that point; `more attacker content` and the true `>>>>>>> feature` marker are copied through verbatim as "regular content."
6. The dialog reports the file as fully resolved with no warnings; the committed/staged file still contains a literal `>>>>>>> feature` marker line and orphaned attacker content mid-file — corruption that ships into the user's commit/push undetected.

Note: This analysis is based on static reading of the parsing logic; I was not able to execute the test suite to empirically confirm the exact truncation behavior end-to-end (e.g., interplay with `getHunkSkipReason` size gating). If further certainty is needed, a Devin session with repository/test execution access could add a targeted unit test reproducing the exact spliced output.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}
