### Title
Protocol fee and surplus-share fee rounds to zero on `IntentGatewayV2`, allowing fee-free order placement and fills - (File: evm/src/apps/IntentGatewayV2.sol / evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`IntentGatewayV2` computes protocol/surplus fees using integer division by `10_000` (bps denominator) with no floor/minimum check, the exact same rounding-to-zero pattern flagged in the RubiconMarket `buy()` report for low-decimal tokens.

### Finding Description
In `placeOrder`, the protocol fee is computed as:
```solidity
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
``` [1](#0-0) 

For small `originalAmount` values, or low `protocolFeeBps` (current deployments use 5 bps per the docs), `originalAmount * protocolFeeBps / 10_000` truncates to `0` whenever `originalAmount * protocolFeeBps < 10_000`. With the documented 5 bps rate, any input amount below `2000` base units (e.g. `< 0.002 USDC` in 6-decimal terms, or a much larger nominal amount for tokens with very few decimals) yields `protocolFee == 0`, and no `DustCollected` event or fee deduction occurs at all, matching the report's exact bug class. [2](#0-1) 

The same rounding-to-zero pattern is repeated for the solver-surplus protocol share in `_fillSameChain`:
```solidity
protocolShare = (dust * _params.surplusShareBps) / 10_000;
beneficiaryShare = dust - protocolShare;
``` [3](#0-2) 

Because `dust` (solver overpayment) and `surplusShareBps` can both be small, `protocolShare` truncates to `0`, and the surplus is fully routed to the beneficiary instead of being split with the protocol, with `if (protocolShare > 0) emit DustCollected(...)` silently skipped. [4](#0-3) 

Neither code path enforces a non-zero fee/minimum-amount guard, unlike the recommended mitigation in the original report (`require(fee != 0)`).

### Impact Explanation
This is a fee-bypass / logic-attack class finding rather than direct fund theft: an attacker can structure `placeOrder` calls with amounts sized just below the rounding threshold (or repeatedly split a larger order into many sub-threshold orders) to systematically avoid the protocol fee entirely, and solvers can similarly avoid paying their surplus share on small-dust overpayments. This causes the protocol to permanently lose fee revenue it is entitled to on every such transaction — a direct, repeatable loss of expected protocol funds, matching the "logic attacks"/fee-circumvention category accepted by the bounty scope. It does not compromise proof verification, custody correctness, or cause double-settlement.

### Likelihood Explanation
Likelihood is high for the fee-bypass because it requires no privileged role, no relayer/prover collusion, and no malformed proof — any ordinary user calling the public `placeOrder`/`fillOrder` entrypoints with small amounts triggers it deterministically. It's economically most attractive when `protocolFeeBps` is very low (5 bps in current deployments) or the input token has few decimals, letting attackers batch many sub-threshold orders to avoid fees on larger aggregate volume.

### Recommendation
Mirror the original report's mitigation: after computing `protocolFee`/`protocolShare`, either (a) revert when the intended fee amount is non-zero-bps but rounds to `0` and the order/fill amount exceeds some minimum, or (b) round the fee up (`divCeil`) instead of down when `protocolFeeBps > 0`, ensuring a strictly-positive fee is always collected for any nonzero-bps configuration. Apply the same fix to both `IntentGatewayV2.sol::placeOrder` and `IntrinsicIntents.sol::_fillSameChain`'s surplus-share calculation, and consider a protocol-level minimum order amount for fee-bearing chains.

### Proof of Concept
1. Deploy `IntentGatewayV2` with `protocolFeeBps = 5` (matches documented default).
2. Call `placeOrder` with `order.inputs[0].amount = 1000` (any token, e.g. USDC base units).
3. `protocolFee = (1000 * 5) / 10_000 = 0` (integer division truncates `0.5` to `0`).
4. `reducedAmount = 1000 - 0 = 1000`; no `DustCollected` event fires, per the test pattern already exercised in `testProtocolFeeWithZeroPercent` but reachable here even with `protocolFeeBps > 0` simply by choosing a sufficiently small `inputAmount`. [5](#0-4) 
5. Repeating step 2 across many small orders lets an attacker move arbitrary volume through the gateway while paying zero protocol fee, in contrast to the fee that would apply to an equivalent single large order.

### Protocol fees

Before escrowing, the contract deducts a protocol fee from each input amount:

```
protocolFee = input.amount × protocolFeeBps / 10_000
reducedAmount = input.amount − protocolFee
```

The fee is retained in the gateway as dust (emitting `DustCollected`), and per-destination overrides take precedence over the global `protocolFeeBps` when set. Current deployments charge **5 bps (0.05%)**. For a 100 USDC input:

| Item | Amount |
| --- | ---: |
| USDC transferred from your wallet | 100.000000 USDC |
| Protocol fee: `100 × 5 / 10,000` | 0.050000 USDC |
| Amount actually escrowed and offered to solvers | 99.950000 USDC |

The commitment hash is computed over the **fee-reduced inputs** — solvers read the reduced amounts from the `OrderPlaced` event and only need to match those. The fee is deducted at placement and is **not refunded** if the order expires, receives no bids, or is cancelled; a cancellation returns the remaining escrow and `order.fees`, but not the protocol fee.

    function testProtocolFeeWithZeroPercent() public {
        // Test with 0% protocol fee - should not emit DustCollected
        IntentGatewayV2 customGateway = _deployGatewayProxy();
        Params memory customParams = Params({
            host: address(host),
            dispatcher: address(dispatcher),
            solverSelection: false,
            surplusShareBps: 10000,
            protocolFeeBps: 0, // 0%
            priceOracle: address(0)
        });
        customGateway.initialize(customParams, new bytes[](0));

        uint256 inputAmount = 1000 * 1e6; // 1000 USDC

        deal(address(usdc), user, inputAmount);

        Order memory order = Order({
            user: bytes32(0),
            source: bytes(""),
            destination: host.host(),
            deadline: block.timestamp + 1 hours,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: new TokenInfo[](1),
            output: PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: new TokenInfo[](1), call: ""})
        });

        order.inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});
        order.output.assets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 2000 * 1e18});

        vm.startPrank(user);
        usdc.approve(address(customGateway), inputAmount);

        vm.recordLogs();
        customGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Check that DustCollected event was NOT emitted
        Vm.Log[] memory entries = vm.getRecordedLogs();
        bool dustCollectedFound = false;

        for (uint256 i = 0; i < entries.length; i++) {
            if (entries[i].topics[0] == keccak256("DustCollected(address,uint256)")) {
                dustCollectedFound = true;
            }
        }

        assertFalse(dustCollectedFound, "DustCollected event should NOT be emitted when protocolFeeBps is 0");

        // Verify the gateway received the full amount
        assertEq(usdc.balanceOf(address(customGateway)), inputAmount, "Gateway should have full input amount");
