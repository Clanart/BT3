### Title
mWOMSVBaseRewarder._calExpireForfeit never forfeits rewards, letting unlocking mWomSV holders steal 100% of bonus rewards - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`_calExpireForfeit` is supposed to reduce a user's claimable bonus rewards proportionally to the fraction of their mWomSV position that is in unlock cooldown (mirroring `mWomSV.getRewardablePercentWAD`), redistributing the forfeited share to remaining lockers. Instead, the function sets `rewardableAmount = _amount` unconditionally and checks a tautological condition, so `forfeitAmount` always evaluates to `0`, meaning no forfeiture ever occurs regardless of unlock status.

### Finding Description
In `mWOMSVBaseRewarder.sol`: [1](#0-0) 
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();

    uint256 forfeitAmount = _amount - rewardableAmount;
    
    if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
        forfeitAmount = 0;
        rewardableAmount = _amount;
    }

    return forfeitAmount;
}
```
`rewardableAmount` is assigned directly from `_amount` with no reference to `mWomSV.getRewardablePercentWAD(_account)`, which is the function that actually computes the percentage of a user's balance still fully locked vs. in cooldown/unlocked (see the analogous logic in `wombat/mWomSV.sol:181-206`). The intended computation (`rewardableAmount = _amount * getRewardablePercentWAD(_account) / 1e18`) is missing entirely, and the subsequent `if (rewardableAmount > _amount) revert` can never be true since `rewardableAmount == _amount` by construction. As a result `forfeitAmount = _amount - rewardableAmount` is always `0`.

This function is called from `_sendReward`: [2](#0-1) 
which is reached via the public `getReward`/`getRewards` entrypoints gated only by `onlyMasterMagpie` and `updateReward`, i.e., any mWomSV holder can trigger a claim through `MasterMagpie.multiclaim` regardless of their unlock/cooldown state. Since `forfeitAmount` is always `0`, `toSend = userRewards[...] - 0`, and the full accrued reward amount is transferred to the receiver even for a user who is fully in unlock cooldown or has already fully unlocked (`getFullyUnlock` / `startUnlock` in `mWomSV.sol`). No modifier, pause, or reentrancy guard addresses this — the checks that exist (`onlyMasterMagpie`, `updateReward`) only govern reward accounting/authorization, not the forfeiture calculation itself.

### Impact Explanation
This is a theft/misallocation of unclaimed yield: mWomSV holders who start or complete an unlock are supposed to forfeit a pro-rata share of bonus rewards to remaining lockers (per `getRewardablePercentWAD`), but due to this bug they always receive 100% of their accrued bonus rewards. This directly harms remaining lockers, who never receive the forfeited share that should have been redistributed via `_queueNewRewardsWithoutTransfer`. This matches the Immunefi impact class "theft of unclaimed yield" and violates the protocol's documented forfeiture/conservation invariant.

### Likelihood Explanation
Any unprivileged mWomSV holder can trigger this by simply locking mWomSV, accruing bonus rewards, calling `startUnlock` for part or all of their balance, and then calling `getReward`/`getRewards` via `MasterMagpie.multiclaim` before or after the cooldown ends. No special capital or privileged role is required beyond holding mWomSV and accrued rewards — this is trivially and repeatably exploitable by every unlocking user, making it a systemic, guaranteed loss rather than an edge case.

### Recommendation
Fix `_calExpireForfeit` to actually compute the rewardable amount using the user's `getRewardablePercentWAD` from `mWOMSV`:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();

    uint256 forfeitAmount = _amount - rewardableAmount;
    if (forfeitAmount < (_amount / 1000)) {
        forfeitAmount = 0;
    }
    return forfeitAmount;
}
```

1. Deploy `mWomSV`, `mWOMSVBaseRewarder`, `MasterMagpie` per existing test harness.
2. Have `userA` lock `100e18` mWomSV via `mWomSV.lock`.
3. Queue bonus rewards into `mWOMSVBaseRewarder` (e.g., via `queueNewRewards`) sufficient to accrue nonzero `rewardPerToken`.
4. Call `userA` -> `mWomSV.startUnlock(100e18)` to place 100% of the balance into cooldown (so `getRewardablePercentWAD(userA)` should return `0` or near `0`, not `1e18`).
5. Assert `mWOMSVBaseRewarder.calExpireForfeit(userA, rewardToken)` returns `0` (bug) instead of the full accrued `earned(userA, rewardToken)` amount (expected correct forfeiture).
6. Call `MasterMagpie.multiclaim` (or `mWOMSVBaseRewarder.getReward(userA, userA)`) and assert `userA` receives the entire pre-unlock accrued bonus reward balance, with `IERC20(rewardToken).balanceOf(userA)` equal to `earned(...)` pre-claim, proving 0 forfeiture despite full unlock cooldown — violating the conservation invariant that forfeited rewards should instead be redistributed via `_queueNewRewardsWithoutTransfer` to remaining lockers.
