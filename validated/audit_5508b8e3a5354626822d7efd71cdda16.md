### Title
Non-greedy `<promise>` tag extraction lets attacker-controlled/quoted text trigger premature Ralph-loop termination - ([File: plugins/ralph-wiggum/hooks/stop-hook.sh])

### Summary
`stop-hook.sh` extracts the completion promise from the last assistant message using a single first-match, non-greedy Perl regex over the entire joined text content, with no distinction between Claude's own genuine completion statement and any text Claude merely echoes/quotes from files, tool output, or issue/PR content it processed during the loop. Because the exact `completion_promise` string is not secret (it is embedded verbatim in the loop's own prompt, fed back into the transcript every iteration, and typically a short, guessable/documented value like `COMPLETE`/`DONE`), an attacker who controls content the model reads and quotes during the loop (a repo file, README, issue text, or tool/API response) can plant a matching `<promise>...</promise>` string that gets picked up as the "first" tag in the message and incorrectly satisfies the exact-match check, terminating the loop before genuine completion.

### Finding Description
The hook reads the last assistant message's joined text with `LAST_OUTPUT=$(... jq ... | map(.text) | join("\n"))` [1](#0-0) , then extracts the promise via `perl -0777 -pe 's/.*?<promise>(.*?)<\/promise>.*/$1/s; ...'`, which slurps the entire message and non-greedily captures the content of the FIRST `<promise>...</promise>` occurrence anywhere in the text, with no awareness of whether that occurrence is inside a quoted code block, a pasted file excerpt, or tool output versus Claude's own final statement [2](#0-1) . The result is compared with a literal string equality check against `COMPLETION_PROMISE`, and on match the loop state file is deleted and the loop is force-terminated with a "detected" success message [3](#0-2) .

Crucially, `COMPLETION_PROMISE` is not a secret: it is embedded directly in the loop's own prompt text (e.g. `Output <promise>COMPLETE</promise> when done.`), which is stored in `.claude/ralph-loop.local.md` and re-fed to Claude on every single iteration as the `reason` field of the hook's block response [4](#0-3) , and is also echoed in the `systemMessage` shown at the start of each loop turn (`"To stop: output <promise>$COMPLETION_PROMISE</promise>..."`) [5](#0-4) . Documentation and setup script examples also standardize on short, predictable values such as `COMPLETE`, `DONE`, `TASK COMPLETE`, `FIXED` [6](#0-5) [7](#0-6) , so an attacker seeding repository content (an issue, a file the loop's prompt instructs Claude to read/fix, or an API/tool response processed mid-loop) with a guessed or observed exact-match string wrapped in `<promise>` tags stands a real chance of it being echoed verbatim by Claude while it quotes/describes that content, and being picked up by the naive first-match regex before Claude's own true completion statement (if any) appears later in the same message.

No sanitization, quoting-context detection, structural anchoring (e.g., requiring the tag to be the last line, or stripping fenced code blocks/quoted text before matching), or provenance check exists to prevent this.

### Impact Explanation
This causes premature, attacker-triggered termination of the Ralph loop, which is the loop's sole gating mechanism against exiting with unfinished or unauthorized work still pending ("deny means deny" for loop continuation). Because the hook deletes the state file and returns a normal stop decision once the fabricated tag matches, work that never met its declared completion criteria is silently accepted as "done," hiding incomplete/unverified changes from the operator. This is a logic/trust-boundary bypass in an automation/agentic-loop control rather than a memory-safety or RCE bug, but it directly undermines the described invariant that the loop only terminates on Claude's genuine, truthful completion signal.

### Likelihood Explanation
The attack requires: (1) an active Ralph loop with a `completion_promise` set, (2) the loop's task causing Claude to read/quote attacker-influenced content (a very common workflow — "fix issues in this file", "summarize this PR/issue", tool/API responses), and (3) the attacker knowing or guessing the exact promise string. Since the promise string is not treated as a secret and is re-broadcast into the transcript every iteration and commonly documented as a short predictable value, guessing/observing it is realistic in scenarios where the loop's initial prompt (and thus the promise text) is itself derived from or visible in repository content (e.g., committed prompt/task files, PR descriptions, CI logs). The exploit needs no elevated privilege — only the ability to influence content the agent will process/quote, which matches the allowed threat model.

### Recommendation
Do not perform a naive first-match, whole-message regex scan. Instead: (1) restrict matching to only the tag that appears in the final, non-quoted portion of the message (e.g., require the `<promise>` tag to be outside of fenced code blocks/blockquotes, or only consider the last occurrence rather than the first), (2) prefer a structured signal instead of free text embedded in prose — e.g., require the promise tag to be the entire trailing content of the message, or use a dedicated tool-call/JSON field that the model must explicitly invoke rather than plain text that can be echoed from quoted material, and (3) treat `COMPLETION_PROMISE` as sensitive: avoid re-echoing it verbatim in every `systemMessage`/prompt if possible, or bind detection to message provenance (e.g., only trust `<promise>` tags emitted as the sole content of a dedicated final text block, not embedded within quoted/copied content).

3. Regression assertion: after fix, the same PoC transcript in step 1 should NOT match, and the loop should continue (exit code / decision `block`).
