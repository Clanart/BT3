### Title
ProtoJSON Duplicate/Aliased Field-Name Confusion Enables Cross-Runtime Value Smuggling - ([File: src/google/protobuf/json/internal/parser.cc])

### Summary
The Node.js report's invariant is: RFC 7230 forbids whitespace between a header field-name and colon specifically because *accepting* the deviation lets one parser (Node) and another parser (a proxy) disagree about how many logical messages a byte stream represents — enabling request smuggling. The Protobuf analog is structurally the same class of bug: the JSON→proto3 mapping guarantees a field has a canonical JSON name plus accepted aliases (original `snake_case` name, `lowerCamelCase` name, and an optional custom `json_name`), and the *spec-level* invariant is that a JSON object must have unique member names so that each JSON key deterministically maps to exactly one field value. ProtoJSON parsers across languages deviate from strict enforcement of that uniqueness invariant in different, mutually inconsistent ways, so the *same bytes* resolve to different field values depending on which language runtime parses them.

### Finding Description
`ParseOptions.allow_legacy_nonconformant_behavior` defaults to `true` in the C++ implementation [1](#0-0) . With this default, `ParseField` in the C++/upb-style JSON parser only rejects a "field already seen" condition when the field is part of a `oneof`; for ordinary duplicate/aliased keys it silently keeps parsing and overwrites/merges the value with the later occurrence ("last one wins") rather than rejecting the input [2](#0-1) .

The Python implementation's duplicate detector in `_ConvertFieldValuePair` tracks duplicates by the *literal JSON key string* seen (`names.append(name)` / `if name in names`), not by the resolved `field` object [3](#0-2) . This means a payload containing `"int32Value"` and `"int32_value"` (or a custom `json_name` alias) — two different spellings that both resolve to the *same* underlying field — bypasses the duplicate check entirely, and the later key silently wins. This is explicitly acknowledged as an "oversight bug" in the implementation, but is called out as unfixable without a breaking change [4](#0-3) .

The C# implementation has essentially no duplicate-key rejection for non-oneof fields at all: `Merge()` looks up every `Name` token in `jsonFieldMap` and unconditionally calls `MergeField`, so any number of aliased/duplicate keys for the same non-oneof field are silently merged/overwritten with no error, only `oneof` collisions are checked [5](#0-4) .

This divergence is not accidental — it's officially documented as unresolved, cross-runtime-inconsistent behavior in Protobuf's own design docs: "Conflicting mappings lead to undefined behavior. While the behavior is deterministic in all of the cases we've encountered, it's inconsistent across runtimes and unexpected" [6](#0-5) . The conformance suite itself only marks this `RECOMMENDED` (not `REQUIRED`) and explicitly allows either "last-wins" or "parse failure" as valid outcomes [7](#0-6) , and multiple backends (C++, upb, Python-upb) are listed as *known failing* for these exact `FieldNameDuplicate*` tests [8](#0-7) [9](#0-8) .

### Impact Explanation
Consuming applications commonly use Protobuf's JSON mapping as a trust boundary: e.g., a validating gateway/proxy (compiled with one language runtime, or with `allow_legacy_nonconformant_behavior=false`) parses and authorizes a client-supplied ProtoJSON payload, then forwards the same raw bytes to a backend service using a different Protobuf language runtime (or the default legacy-permissive settings) for the authoritative parse. Because the "duplicate/aliased key" resolution rule is implementation-defined and inconsistent, an attacker can craft a single JSON payload containing two spellings of the same field (e.g., `"amount": 1` and `"Amount": 1`, or default vs. custom `json_name`) where the gateway's parser resolves to the benign value while the backend's parser resolves to the attacker's value — the same "smuggled second message" effect as the HTTP case, but expressed as a smuggled field value instead of a smuggled HTTP request. This can bypass authorization/validation logic that inspected only the value the front-end parser produced.

### Likelihood Explanation
Requires only a crafted ProtoJSON body with two JSON keys that map to one field (trivial for an attacker to construct given a known/public `.proto` schema and its default camelCase/snake_case/json_name aliasing rules), sent through the normal public `JsonFormat.Parse` / `MessageToJson`/`ParseDict` / `upb_JsonDecode` APIs — no privileged access, hostile schema, or malicious peer needed. The likelihood of exploitation depends entirely on whether the deployment topology re-parses the same bytes in two different runtimes/configs (a common microservices/gRPC-JSON-transcoding pattern), which is an application-architecture question outside Protobuf's control, hence Medium rather than High/Critical.

### Recommendation
- Make duplicate/aliased field-name detection keyed off the resolved `FieldDescriptor`, not the literal JSON key string, consistently across all language runtimes (fixing the Python bug noted at `python/google/protobuf/json_format.py:663-670`).
- Add duplicate detection for non-oneof fields to the C# `JsonParser.Merge` loop, matching the stricter behavior other runtimes offer.
- Consider flipping the default of `allow_legacy_nonconformant_behavior` to `false` for new call sites (already flagged as the long-term direction in `docs/design/editions/edition-zero-json-handling.md`), and document clearly for security-sensitive consumers that ProtoJSON duplicate-key handling should not be relied upon to be consistent across runtimes unless `DISALLOW`/strict mode is used end-to-end.

### Proof of Concept
Given proto3 message `message M { int32 amount = 1; }`, feed the following payload to two different Protobuf JSON parsers in the same trust chain:
```json
{"amount": 1, "Amount": 999}
```
- C++ default (`allow_legacy_nonconformant_behavior=true`): both keys parsed, last one wins → `amount == 999` (no error) — behavior determined by `ParseField`/`RecordAsSeen` legacy branch [10](#0-9) .
- Python (`json_format.Parse`): with keys of identical literal spelling this raises `ParseError`, but with the alternate-casing/alias spelling shown above the check (keyed on literal `name`) does not fire, silently keeping the later value — confirmed by the test explicitly documenting this exact class of miss [4](#0-3) .
- C# `JsonParser`: no duplicate check exists for non-oneof fields at all; last key in document order always wins [5](#0-4) .

All three are within the documented/officially-acknowledged inconsistency [11](#0-10) , demonstrating that identical attacker-controlled bytes can yield different authoritative field values depending on which supported Protobuf JSON parser processes them — the value-confusion analog to the reported HTTP request-smuggling primitive.
