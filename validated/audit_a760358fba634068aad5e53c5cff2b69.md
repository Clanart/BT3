This is the finding: `clone.ts` explicitly disables Git's built-in clone protection by forcing `GIT_CLONE_PROTECTION_ACTIVE: 'false'` into the environment for every clone, unconditionally overriding whatever value would otherwise be inherited or defaulted.

### Title
Git clone protection is force-disabled for every clone, defeating malicious-repository safeguards - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` in `app/src/lib/git/clone.ts` builds the environment for `git clone` and unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'`, which turns off the clone-time protections Git ships to stop malicious repositories from writing files outside the working tree via crafted `.git` contents (e.g. symlinked `.git` directories, colliding case-insensitive/NTFS-alternate-stream paths, or other clone-time repository layout tricks). Desktop performs clones directly against attacker-supplied/attacker-hosted repository content, so this is a directly reachable, unprivileged path.

### Finding Description
The `clone` function is the single code path Desktop uses to fetch a brand-new copy of a repository from a URL the user (or an attacker via a deep link / "Open in Desktop" flow) supplies: [1](#0-0) 

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
```

This spreads whatever `envForRemoteOperation(url)` produces and then forcibly overwrites the clone-protection flag to `'false'`, so there is no way for it to remain enabled regardless of the installed Git version's default or any user/system configuration. The function does have a genuine, well-designed guard against one specific class of attack — cloning into a sensitive destination directory like `~/.ssh` — implemented in `isClonePathSensitive`: [2](#0-1) 

but that guard only checks the destination directory chosen by the user; it says nothing about what the untrusted remote repository content itself can do once cloned with protections disabled. The repository being cloned is fully attacker-controlled (any public/private git remote URL, including ones reached via `x-github-client://` deep links or "Open in Desktop" from a malicious page), so the broken invariant is: *Desktop assumes clone-time repository content is safe enough to process with Git's internal safety checks turned off, when the content is actually attacker-supplied.*

This mirrors the reported bug's shape: a security-relevant invariant (interest-timestamp / here, clone-time integrity protection) is unconditionally short-circuited to a "disabled" value on a hot path, rather than being conditionally applied only when genuinely safe to skip.

### Impact Explanation
If the disabled Git clone protections cover checks against clone-time filesystem escapes (e.g., a `.git` entry that is a symlink pointing outside the target directory, or path collisions exploitable on case-insensitive/NTFS filesystems), disabling them for every clone means a maliciously crafted repository can potentially write files outside the intended clone directory during `git clone --recursive`, i.e., file write outside the repo — one of the explicitly in-scope impact categories. Because `--recursive` is also passed, submodules from the same attacker-controlled repo are cloned too, multiplying the attacker-controlled content processed with protections off.

### Likelihood Explanation
High reachability: cloning a URL is a core, everyday, fully unprivileged Desktop action, and it is also reachable via `x-github-client://` "Open in Desktop" deep links that a user can be lured into clicking, and via any GitHub API repository object surfaced in the Clone dialog. No admin rights, local access, or pre-existing malware are required — only that the user clones or opens a repository the attacker controls, which is squarely inside this bug bounty's valid-impact scope.

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. Only set clone-related safety env vars to relax protections when there is a specific, justified, narrowly-scoped reason to do so (analogous to only skipping the `lastRateUpdate` in the original report during an explicit safe-pause state), and otherwise let Git's default (protection enabled) apply. If this flag was added to work around a specific legitimate clone scenario, gate it behind that scenario instead of applying it unconditionally to all clones.

### Proof of Concept
1. Attacker publishes a git repository crafted to abuse whatever clone-time check `GIT_CLONE_PROTECTION_ACTIVE` guards (e.g., a `.git`-adjacent symlink/path-collision payload).
2. Attacker distributes the clone URL, e.g. via a webpage using `x-github-client://openRepo/<url>` or a "Clone" link, or simply as a public repo URL.
3. Victim clicks the link or pastes the URL into Desktop's Clone Repository dialog; Desktop calls `clone()` in `app/src/lib/git/clone.ts`, which always injects `GIT_CLONE_PROTECTION_ACTIVE: 'false'` into the `git clone --recursive` invocation.
4. Git performs the clone with its internal clone-time protections disabled, allowing the malicious repository's crafted content to write/escape as permitted by whatever check that env var toggles — `isClonePathSensitive` only validates the destination path chosen by the user and does not restrict what the untrusted repository content can do once protections are off.

Note: I was not able to fully verify, from the indexed code alone, the exact upstream Git behavior that `GIT_CLONE_PROTECTION_ACTIVE` controls (this does not correspond to a standard documented Git environment variable I could cross-reference in this codebase), so the precise mechanics of the bypass could not be independently confirmed beyond what is stated in the surrounding code comments and structure. I'd recommend a Devin session with full repo/history access to trace the origin and intended semantics of this flag before treating this as fully confirmed.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
