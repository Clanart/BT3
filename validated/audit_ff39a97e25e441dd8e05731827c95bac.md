### Title
Tautological `_calExpireForfeit` in `mWOMSVBaseRewarder` makes cooldown forfeiture permanently unenforceable, freezing loyal lockers' expected yield - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` sets `rewardableAmount = _amount` unconditionally instead of scaling it by the account's actual rewardable/cooldown percentage (as the sibling `vlMGPBaseRewarder._calExpireForfeit` correctly does via `vlMGP.getRewardablePercentWAD(_account)`). As a result `forfeitAmount = _amount - rewardableAmount` is always `0`, regardless of whether the caller is 100% in cooldown. Any `mWomSV` holder who fully unlocks and calls `getReward` keeps 100% of accrued rewards, and the forfeiture pool that should be redistributed to remaining loyal lockers via `_queueNewRewardsWithoutTransfer` is never funded.

### Finding Description
`mWOMSVBaseRewarder._calExpireForfeit` (lines 385-398) is implemented as: [1](#0-0) 
```
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();
    uint256 forfeitAmount = _amount - rewardableAmount;
    if (forfeitAmount < (_amount / 1000)) {
        forfeitAmount = 0;
        rewardableAmount = _amount;
    }
    return forfeitAmount;
}
```
`rewardableAmount` is hard-set equal to `_amount` before the guard even runs, so `forfeitAmount` is always `0`, independent of `_account`'s lock/cooldown status. Compare this to the correctly implemented `vlMGPBaseRewarder._calExpireForfeit`, which computes `rewardableAmount = _amount * vlMGP.getRewardablePercentWAD(_account) / 1e18` — i.e., it actually queries the locker contract for the account's cooldown-based rewardable percentage. The `mWOMSVBaseRewarder` version never queries `mWOMSV` (the `ILocker`) for any equivalent percentage and is effectively dead/no-op forfeiture logic.

Both `getReward` → `_sendReward` (lines 362-376) and `getRewards` route through this broken function: [2](#0-1) 

Exploit flow: an attacker calls `startUnlock` on `mWomSV` for their entire balance, entering the cooldown state that (per design intent mirrored in the vlMGP counterpart) should reduce their rewardable share and forfeit the remainder to the shared pool. They then call `getReward` (via `MasterMagpie`, which is `onlyMasterMagpie`-gated but callable by any staker through normal claim flow). `_sendReward` computes `forfeitAmount = _calExpireForfeit(...) = 0`, so `toSend = userRewards[...] - 0` — the full accrued reward is paid out, and `_queueNewRewardsWithoutTransfer` is never invoked to redistribute anything back to remaining lockers.

No existing modifier (`onlyMasterMagpie`, `updateReward`, `nonReentrant`) prevents this because the bug is in the forfeiture math itself, not in access control or reentrancy — none of those guards touch the flawed calculation.

### Impact Explanation
This falls under "theft or permanent freezing of unclaimed yield." The forfeiture mechanism is a core economic invariant intended to penalize users exiting cooldown and redistribute that penalty to loyal, still-locked `mWomSV` holders. Because `forfeitAmount` is tautologically zero, that redistribution never occurs for any account, for the lifetime of the deployed contract (short of an upgrade). Loyal lockers are permanently denied yield they were designed to receive whenever any cooldown/exiting user claims rewards — a systemic, unbounded, and irreversible (without contract upgrade) loss of expected yield share, satisfying the "funds frozen ≥ 24 hours" / permanent freezing bar.

### Likelihood Explanation
Trivial and fully repeatable: any `mWomSV` holder (attacker or not) simply calls `startUnlock` for their full balance and then triggers `getReward`/`getRewards` through the normal `MasterMagpie` claim path. No special capital, timing, front-running, or privileged role is required — this happens on every single reward claim by any cooldown-state account, making it a certainty rather than a probabilistic path.

### Recommendation
Fix `_calExpireForfeit` in `mWOMSVBaseRewarder` to mirror the intended logic in `vlMGPBaseRewarder`: query `mWOMSV` (or the underlying locker) for the account's actual rewardable percentage based on cooldown/unlock status (e.g., add and call an `mWOMSV.getRewardablePercentWAD(_account)`-equivalent function), and compute `rewardableAmount = _amount * rewardablePercentWAD / 1e18` instead of hardcoding `rewardableAmount = _amount`.

### Proof of Concept
Foundry test plan:
1. Deploy `mWOMSVBaseRewarder`, `mWomSV` locker, and `MasterMagpie` with two accounts: `loyalLocker` (fully locked, never unlocks) and `attacker` (will fully cooldown).
2. Both stake equal `mWomSV` amounts; queue rewards via `queueNewRewards` so `rewardPerTokenStored` accrues for both.
3. `attacker` calls `mWomSV.startUnlock(fullBalance)` to enter 100% cooldown.
4. Assert `calExpireForfeit(attacker, rewardToken) == 0` despite `attacker` being fully in cooldown (proving the tautology — expected non-zero forfeit under correct design).
5. `attacker` calls `getReward` via `MasterMagpie`; assert `attacker` receives 100% of `earned(attacker, rewardToken)` and `rewards[rewardToken].queuedRewards == 0` (no forfeit funneled back).
6. Assert `loyalLocker`'s subsequent `earned(loyalLocker, rewardToken)` does not include any forfeited share that should have come from `attacker`'s exit, confirming the permanent loss of the redistribution the design intends (compare against a corrected `_calExpireForfeit` model run in the same test to show the delta).
