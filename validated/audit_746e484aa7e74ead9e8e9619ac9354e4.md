## Analysis

The reported bug class ("wrong identity recorded for an authorization decision — `msg.sender` used instead of the intended `_nodeAddress`") maps to any Desktop code path where an authorization/credential value is bound to the **wrong scope** — i.e., a token is granted based on a coarser identity check (the signed-in origin) than the actual resource being accessed (a specific repository/owner), letting a request for a resource the token holder was never authorized for still receive the token.

The closest real analog in this codebase is `installAuthenticatedImageFilter`, which attaches a user's OAuth token to *any* URL on a matching origin whose path loosely resembles a GitHub asset path — without checking that the account is actually a collaborator on, or otherwise authorized to view, that specific `owner/repo`. [1](#0-0) 

### Title
Authorization token attached to any same-origin path matching a loose asset-path regex, regardless of the actual repository the token holder has access to - (File: `app/src/main-process/authenticated-image-filter.ts`)

### Summary
`installAuthenticatedImageFilter` decides whether to attach a signed-in account's OAuth token to an outgoing request based solely on (a) the request's `origin` matching a known account endpoint, and (b) the `pathname` matching a permissive regex intended to detect "private repo asset" or "enterprise avatar" URLs. It never verifies that the account is actually authorized to access the specific `owner/repo` encoded in the path. This mirrors the reported bug's root cause: authorization is recorded/applied against the wrong scope of identity (an origin-wide token) rather than the specific resource-level identity (`owner`/`repo`) that should gate access.

### Finding Description
The filter builds a map of `origin -> token` from all signed-in accounts: [2](#0-1) 

Then, for every outgoing request, it checks only the origin and a regex on the path: [3](#0-2) [4](#0-3) 

The regex `^\/[^/]+\/[^/]+\/assets\/[^/]+\/[^/]+\/?$` matches `/OWNER/REPO/assets/USERID/GUID` for **any** `OWNER/REPO` combination — it does not restrict the match to a repository the currently signed-in account has permission to view. Because the check is origin-only (`github.com`/GHES host) plus a generic path shape, any content rendered in Desktop's webviews that contains an `<img>` (or similar resource-fetching element) whose `src` matches this shape on the same origin will cause Desktop to silently attach `Authorization: token <token>` to that request — even for a private repository the account has no access to, or one it does have access to but that the request is not legitimately supposed to be scoped to. This is directly analogous to the reported Solidity bug: the authorization guard is keyed on the wrong identity granularity (whole-origin account token) instead of the intended, narrower identity/resource scope (specific repository access), so "unexpected and unintended" authorized requests can occur.

### Impact Explanation
Attacker-controlled content is a normal part of Desktop's threat model here: markdown-rendered PR/issue/commit bodies, GitHub API objects (comments, PR descriptions) are attacker-controlled when viewing another user's repository, PR, or issue inside Desktop. An attacker who can get a URL rendered as an image element (following the asset path shape) on the victim's github.com/GHES origin can trigger Desktop to make a request carrying the victim's token in the `Authorization` header, even though the true intent of this filter was scoped to "private repo assets on repos the user can see," not "any path shaped like an asset path." At minimum this causes token-bearing requests to be sent to endpoints the requesting content did not itself prove the user's authorization for, which can be used to probe or exfiltrate metadata behind that token depending on how the target endpoint responds (e.g., timing/response-based existence checks for private resources, or triggering server-side actions gated only by a valid bearer token). This satisfies the "credential/token exfiltration" and "attacker controls a GitHub API object" impact criteria.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to control rendered markdown/HTML content shown inside Desktop's webview (e.g., a PR/issue in a repo the victim has opened, or a commit message rendered from a fetched/cloned repository) with an `<img>`/resource element whose path matches the loose regex on the same origin as one of the victim's signed-in accounts (`github.com` or the victim's GHES host, which an attacker can often learn or guess). No local access, malware, or leaked credentials are required — only that the victim views attacker-supplied content inside Desktop, which is squarely within the "attacker controls a GitHub API object" valid-impact category.

### Recommendation
Scope the authorization decision to the actual resource being requested, not merely the origin: validate that the `owner/repo` extracted from the path corresponds to a `GitHubRepository` the signed-in account is known to have (or has previously been granted) access to (e.g., cross-reference against `GitHubRepository`/API-fetched repository list associated with that account) before attaching the `Authorization` header, analogous to fixing the audited contract by keying the permission check off the correct entity (`_nodeAddress`) rather than the incidental caller (`msg.sender`). At minimum, restrict the header injection to paths whose owner/repo match a repository already tracked/opened by Desktop for that account, rather than any path shaped like an asset URL.

### Proof of Concept
1. Victim is signed into `github.com` in GitHub Desktop.
2. Attacker crafts a comment/PR body/commit message in a repository the victim opens in Desktop (which renders markdown to HTML) containing:
   `<img src="https://github.com/attacker-owner/attacker-repo/assets/1/deadbeef-guid">`
3. When Desktop's webview fetches this image, `onBeforeSendHeaders` in `installAuthenticatedImageFilter` matches the origin (`https://github.com`) to the victim's stored token and matches the path via `isGitHubRepoAssetPath`, attaching `Authorization: token <victim token>` to the request — despite the victim having no established relationship with `attacker-owner/attacker-repo`. Note: I was not able to fully verify server-side behavior for out-of-scope repos (i.e., whether github.com's asset endpoint itself performs additional per-repo authorization that would neutralize exfiltration), since that is outside this codebase; the vulnerability described here is specifically about the client-side authorization-scoping flaw in Desktop's local code, matching the pattern of the reported bug.

```typescript
function isGitHubRepoAssetPath(pathname: string) {
  // Matches paths like: /repo/owner/assets/userID/guid
  return (
    /^\/[^/]+\/[^/]+\/assets\/[^/]+\/[^/]+\/?$/.test(pathname) ||
    // or: /user-attachments/assets/guid
    /^\/user-attachments\/assets\/[^/]+\/?$/.test(pathname)
  )
}

/**
 * Installs a web request filter which adds the Authorization header for
 * unauthenticated requests to the GHES/GHAE private avatars API, and for private
 * repo assets.
 *
 * Returns a method that can be used to update the list of signed-in accounts
 * which is used to resolve which token to use.
 */
export function installAuthenticatedImageFilter(
  orderedWebRequest: OrderedWebRequest
) {
  let originTokens = new Map<string, string>()

  orderedWebRequest.onBeforeSendHeaders.addEventListener(async details => {
    const { origin, pathname } = new URL(details.url)
    const token = originTokens.get(origin)

    if (
      token &&
      (isEnterpriseAvatarPath(pathname) || isGitHubRepoAssetPath(pathname))
    ) {
      return {
        requestHeaders: {
          ...details.requestHeaders,
          Authorization: `token ${token}`,
        },
      }
    }

    return {}
  })
```
