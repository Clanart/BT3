### Title
Spoofed `WWW-Authenticate: realm="GitHub"` header from an untrusted remote/proxy forces a GitHub-Enterprise sign-in prompt scoped to an attacker-controlled endpoint - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
The reported bug's broken invariant is: a state-transition guard that is supposed to keep a value "locked" once set only fires when that value is non-default (`stakers[receiver].lockPeriod != 0`), so an attacker who first drives the value into the default state can change it freely afterward, and downstream logic (bonus/unlock calculation) trusts the now-unguarded value. The closest analog I could find in this Desktop checkout is in `getEndpointKind()` in `app/src/lib/trampoline/trampoline-credential-helper.ts`, where the classification of a remote as a trustworthy "GitHub"-flavored host is derived from an attacker-suppliable signal (an HTTP `WWW-Authenticate` header echoed back by the remote/proxy) with no independent verification, and that classification is trusted to launch a GitHub Enterprise sign-in flow against that same attacker-controlled origin.

### Finding Description
When Git needs credentials for an HTTPS remote, Desktop's credential-helper trampoline is invoked (`createCredentialHelperTrampolineHandler` → `getCredential` → `getEndpointKind`): [1](#0-0) 

The relevant "happy path" branch trusts any `wwwauth[...]` credential field forwarded by Git verbatim from the remote server's HTTP response:
```
for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
}
``` [2](#0-1) 

Unlike the network-verified fallback path (`isGitHubHost()`, which does a live HEAD request and checks for the `x-github-request-id` response header before trusting a host), this header-based shortcut performs **no verification of the actual host** — any HTTPS git server (or a MITM proxy sitting in front of one) can set `WWW-Authenticate: Basic realm="GitHub"` on a 401 response and Desktop will classify that endpoint as `'enterprise'`.

That classification is then consumed by `getCredential()`:
```
if (endpointKind !== 'generic' && !accounts.some(a => a.endpoint === apiEndpoint)) {
    ...
    const account = await ui.promptForGitHubSignIn(endpoint)
    ...
}
``` [3](#0-2) 

`promptForGitHubSignIn` uses the attacker-controlled `endpoint` origin directly to start an Enterprise sign-in flow:
```
const { hostname, origin } = new URL(endpoint)
if (hostname === 'github.com') {
  this.dispatcher.beginDotComSignIn(cb)
} else {
  this.dispatcher.beginEnterpriseSignIn(cb)
  await this.dispatcher.setSignInEndpoint(origin)
}
``` [4](#0-3) 

`setSignInEndpoint`/`setEndpoint` in the sign-in store only validates URL syntax and protocol (must be `https:`), not host identity or authenticity: [5](#0-4) 

This mirrors the report's pattern exactly: a guard ("is this really a GitHub host?") is only enforced through a weak, attacker-influenceable signal (`lockPeriod == 0` in the original / `wwwauth` header content here) instead of a value the attacker cannot control, and once that weak signal is accepted, the rest of the pipeline (bonus payout / Enterprise sign-in with credential entry) proceeds as if the state were legitimate.

### Impact Explanation
If a user has added, cloned, or is fetching/pushing to a remote controlled by an attacker (e.g., a malicious/compromised HTTP git server, or a MITM/corporate-proxy position on an HTTP(S) git remote — no OAuth-only account is required for Desktop to reach this code path), the attacker can force Desktop into presenting a "Sign in to GitHub Enterprise" dialog pointed at their own origin. If the user completes sign-in (basic-auth entry or the OAuth device/browser flow launched against the attacker endpoint), their GitHub Enterprise/GitHub.com credentials or the resulting token exchange traffic is sent to the attacker-controlled server instead of the legitimate GitHub host — a credential/token exfiltration primitive matching the "unauthorized OAuth or account binding, credential/token exfiltration" impact category.

### Likelihood Explanation
Likelihood is Medium: it requires the user to have a git remote pointing at (or proxied through) a server the attacker controls, and requires user interaction with the resulting sign-in prompt. However, no privileged access, malware, or leaked credentials are needed — only crafting an HTTP 401 response with a spoofed `WWW-Authenticate` header on a git smart-HTTP endpoint, which is fully within the "attacker controls a git remote/proxy response" threat model given in the report.

### Recommendation
Do not trust the `wwwauth[...]` realm string alone to classify a host as GitHub/Enterprise. Require this signal to be corroborated by the network-based `isGitHubHost()` check (or hostname pattern matching) before offering the GitHub Enterprise sign-in flow, and/or visibly warn the user with the literal endpoint host before starting any sign-in flow triggered by a git credential request, so users can recognize an unexpected/foreign host before entering credentials.

### Proof of Concept
1. Stand up an HTTPS git-smart-http server (or a MITM proxy in front of a normal remote) that, on any authentication challenge for `git-upload-pack`/`git-receive-pack`, responds with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, add this server's URL as a remote for a repository (or clone from it) and perform a `fetch`/`push`.
3. Git forwards the `wwwauth[...]="Basic realm=\"GitHub\""` value to Desktop's credential helper trampoline via `getCredentialUrl`/`cred.entries()`.
4. `getEndpointKind()` returns `'enterprise'` for the attacker's origin without any live verification.
5. Desktop calls `ui.promptForGitHubSignIn(endpoint)` with `endpoint` = attacker's origin, opening an "Enterprise sign in" dialog scoped to that origin.
6. If the user completes sign-in, their credentials/OAuth exchange traffic is sent to the attacker's origin.

Note: I was unable to fully trace the sign-in store's basic-auth code path (vs. browser/device OAuth-only flow) within the available tool budget, so whether raw username/password is ever transmitted directly (vs. only the OAuth authorize URL being opened in an external browser) is unconfirmed from local code alone — either way, the endpoint the user is asked to authenticate against is attacker-controlled, which is the core corrupted value (`endpoint`/`origin` passed into `beginEnterpriseSignIn`/`setSignInEndpoint`).

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
