### Title
Skewed Vote Accounting Between `totalVlMgpInVote` and Per-Pool `totalVoteInVlmgp` Corrupts Proportional Vote Casting - (File: `wombat/WombatBribeManager.sol`)

### Summary
`WombatBribeManager.vote()` updates each target pool's `totalVoteInVlmgp` unconditionally, but only updates the global `totalVlMgpInVote` counter when `msg.sender != delegatedPool` [1](#0-0) . Since the `delegatedPool` (a `DelegateVoteRewardPool`) itself calls `vote()` as part of its normal, permissionless staking flow, every user who routes votes through the delegate pool inflates per-pool vote totals without inflating the global total used to normalize `castVotes()`, permanently skewing the proportional vote-casting math.

### Finding Description
`vote()` loops over the supplied `_lps` and always mutates `pool.totalVoteInVlmgp` for each pool regardless of caller [2](#0-1) . It then conditionally updates the aggregate accounting:

```solidity
if (msg.sender != delegatedPool) {
    if (totalUserVote > 0) {
        userTotalVotedInVlmgp[msg.sender] += uint256(totalUserVote);
        totalVlMgpInVote += uint256(totalUserVote);
    } else {
        userTotalVotedInVlmgp[msg.sender] -= uint256(-totalUserVote);
        totalVlMgpInVote -= uint256(-totalUserVote);
    }
}
``` [3](#0-2) 

`DelegateVoteRewardPool.stakeFor`/`withdrawFor` (triggered whenever an ordinary user votes into the delegate pool via the normal `WombatBribeManager.vote()` flow, which internally calls `IBribeRewardPool(pool.rewarder).stakeFor(...)`) invoke `_updateVote()`, which itself calls `IWombatBribeManager(operator).vote(votePools, deltas)` — a nested call to `vote()` whose `msg.sender` is the delegate pool contract itself [4](#0-3) [5](#0-4) .

Because `msg.sender == delegatedPool` in that nested call, the underlying pools' `totalVoteInVlmgp` values are increased (via the per-pool loop) but `totalVlMgpInVote` is not. `castVotes()` then computes each pool's target Wombat vote allocation as:

```solidity
targetVote = targetVoteInLMGP * totalVotes() / totalVlMgpInVote;
``` [6](#0-5) 

With the numerator inflated relative to the denominator, the sum of `targetVote` across pools no longer reflects the actual proportion of locked MGP voting for each pool — pools reached through the delegate mechanism receive disproportionately more of the real Wombat vote weight (`totalVotes()`) than their true share of locked/voting MGP, while other pools receive correspondingly less. This is structurally the same accounting flaw as the referenced Aura report: a "total" counter that tracks a different population (direct votes only) than the per-entity counters that feed into governance-weight computations (all votes, including those routed through the delegate).

### Impact Explanation
This directly corrupts governance/voting-weight distribution for LP incentive voting: the proportion of real Wombat votes (and therefore bribe/reward allocation across pools) diverges from what locked-MGP holders actually intended to vote for, and the divergence grows every time an unprivileged user votes/unvotes through the delegate pool (which happens continually as part of ordinary staking/withdrawal). This is a governance voting result manipulation that misallocates yield/bribe distribution across pools without any privileged action — the trigger is purely normal user interaction with an already-configured delegate pool.

### Likelihood Explanation
High: once `delegatedPool` is configured (a one-time admin setup that is a normal part of the deployed system, not an attack), every ordinary vote/unvote transaction touching the delegate pool by any unprivileged wallet reproduces the mismatch. No special permissions, timing, or attacker capital beyond normal vlMGP locking is required.

### Recommendation
Track `totalVlMgpInVote` consistently with `pool.totalVoteInVlmgp` regardless of caller — i.e., remove the `msg.sender != delegatedPool` special case (or instead exclude the delegated pool's votes from `pool.totalVoteInVlmgp`/`castVotes` numerator consistently), so that the denominator used in `castVotes()` always represents the same population summed into the numerators.

### Proof of Concept
1. Admin configures `delegatedPool` and adds it (and target pools A, B) via `addPool` [7](#0-6) .
2. A regular user locks MGP in vlMGP and calls `WombatBribeManager.vote([delegatedPool], [amount])`. This calls `IBribeRewardPool(delegatedPool).stakeFor(user, amount)`.
3. `DelegateVoteRewardPool.stakeFor` executes `_updateVote()`, which computes per-pool target deltas from `votingWeights`/`totalWeight` and calls `IWombatBribeManager(operator).vote(votePools, deltas)` with `msg.sender == delegatedPool` [5](#0-4) .
4. Inside this nested `vote()` call, `poolInfos[A].totalVoteInVlmgp` and `poolInfos[B].totalVoteInVlmgp` increase, but because `msg.sender == delegatedPool`, `totalVlMgpInVote` is left unchanged [3](#0-2) .
5. When `castVotes()` runs, `sum(pool.totalVoteInVlmgp for all pools) > totalVlMgpInVote`, so `sum(targetVote) > totalVotes()`, permanently skewing the proportion of real Wombat votes allocated to pools A and B relative to every other pool, independent of actual locked-MGP intent.
