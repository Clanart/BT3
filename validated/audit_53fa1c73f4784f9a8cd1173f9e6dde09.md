## Summary

The reported Sherlock bug (`SingleSidedLiquidityVault`) breaks because a **global** per-token accounting parameter (`accumulatedRewardsPerShare`) is deleted on removal while an **individually-baked-in** value (the user's stored `rewardsPerShareBaseline`) survives, so re-adding the token desynchronizes the two and turns every subsequent claim into an underflow.

The same broken-invariant shape exists in Hyperbridge's `pallet-hyper-fungible-token`. The pallet stores a **mutable, current** conversion parameter (`Precisions<AssetId, StateMachine>`), but the ERC20-denominated amount that gets **baked into an in-flight cross-chain message body** at dispatch time is computed once, using whatever `Precisions` value was live at that moment. `update_token` allows overwriting or removing that precision at any time, and the timeout/refund path blindly re-reads whatever `Precisions` value is *currently* configured to reverse the conversion — with no linkage back to the value that was actually used when the message was created.

### Finding Description

`send()` locks/burns `params.amount` in local decimals, then re-encodes it in the destination chain's ERC20 decimals using the **precision in effect at dispatch time**, and bakes that `erc20_amount` into the outgoing `PostRequest` body: [1](#0-0) [2](#0-1) 

`update_token` (call index 2, gated only by `CreateOrigin`) can add/overwrite or remove a chain's precision entry for the same `asset_id` at any time, with no check for in-flight requests still outstanding against the old precision: [3](#0-2) 

If the request later times out (destination never delivered before `timeout`), `on_timeout` decodes the **already-encoded ERC20 amount** from the message body and reconverts it to local balance using `Precisions::<T>::get(local_asset_id, dest)` — but this reads the **current** value, not the value that was live when `send()` ran: [4](#0-3) 

This exactly mirrors the SSLV bug's structure: a config value that governs an accounting conversion is decoupled from the value already committed into an individual, unresolved transaction (the reward-per-share baseline in SSLV; the encoded ERC20 amount + timeout target here). Removing/re-adding or simply changing that config after dispatch but before timeout resolution corrupts the reverse conversion for any request still in flight.

### Impact Explanation

If governance calls `update_token` to change a chain's `decimals` for an asset (e.g. fixing a misconfiguration, or re-pointing to a redeployed contract with different decimals) while a `send()` request to that chain is still pending (not yet delivered, not yet timed out), any such pending request that eventually times out will have its refund computed with the **wrong** decimals conversion: [5](#0-4) 

- If the new precision is smaller than the one used at dispatch, `convert_to_balance` will scale the amount **up**, refunding the sender **more** than was ever escrowed — draining the pallet's custody account (`pallet_account()`) at the expense of other users' locked balances, i.e. fund loss for the protocol/other depositors.
- If the new precision is larger, the refund is scaled **down**, permanently under-refunding (locking) part of the user's escrowed funds.

Either direction is a direct "loss or theft of funds" / "transaction manipulation" outcome that matches the bounty's impact gate, and it does not require a malicious relayer, prover, or attacker — only the ordinary, intended governance action of updating a token's chain configuration while transfers are in flight, exactly as "removing/re-adding a reward token" is an ordinary admin action in the source report.

### Likelihood Explanation

`update_token` is a routine maintenance call (contract redeployments, decimal-precision corrections, chain rotations are explicitly what `add_chains`/`remove_chains` exist for). There is no requirement in the code that all pending `send()` requests to a chain be drained or timed out before its precision is changed, and no per-message snapshot of the precision used at dispatch is stored anywhere for later reconciliation. Any live deployment that ever needs to correct or migrate a token's EVM-side configuration for a chain with outstanding in-flight transfers will hit this.

### Recommendation

Store the precision (and/or the pre-encoded local amount) used at `send()` time as part of the request context (e.g. in the message body itself, or in a per-commitment side-table), and have `on_timeout` reconvert using that stored value rather than re-reading the live `Precisions` map. Alternatively, treat `Precisions`/`TokenContracts` updates like the SSLV recommendation: version them, or require an old precision entry to be preserved (not overwritten) until all requests dispatched under it have resolved (delivered or timed out).

### Proof of Concept

1. Governance registers asset `X` for `StateMachine::Evm(C)` with `decimals = 18` via `register_token` — `Precisions::<T>::insert(X, C, 18)`.
2. User calls `send()` for `X` to chain `C`, amount `A` (local decimals `d`). `erc_decimals = 18` is read, `erc20_amount = convert_to_erc20(A, 18, d)` is embedded in the dispatched `PostRequest.body`, with a future `timeout`.
3. Before the request is delivered or times out, governance calls `update_token` for asset `X`, `add_chains = { C: ChainConfig { decimals: 6, .. } }` (e.g. correcting a misconfigured redeploy) — this overwrites `Precisions::<T>::insert(X, C, 6)`.
4. The original request from step 2 never gets delivered and times out. `on_timeout` reads the **current** `Precisions::<T>::get(X, C) == 6` and calls `convert_to_balance(erc20_amount, 6, d)` instead of `convert_to_balance(erc20_amount, 18, d)`.
5. Because the erc20_amount was encoded assuming 18 decimals but is now decoded assuming 6 decimals, the refunded local amount is scaled by `10^(18-6) = 10^12`, vastly overpaying the original sender out of the pallet's shared custody account — draining funds belonging to other escrowed transfers.
