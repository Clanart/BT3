### Title
`updateRemoteUrl` silently repoints a repository's push/fetch remote to an attacker-controlled host supplied by a GitHub API response - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
The Sherlock finding's broken invariant is: a sensitive state-changing action (adding liquidity) is executed using externally-influenced data (pool tick/price) without validating that the data is within a safe/expected bound before committing funds. The reusable primitive is "attacker-influenced external input flows unchecked into a security-sensitive write."

The closest analog in GitHub Desktop is `updateRemoteUrl()`, which rewrites the local Git `origin` remote URL used for all future `push`/`fetch` operations based on `clone_url` returned by a GitHub API response, without validating that the new host matches an expected/trusted host.

### Finding Description
`updateRemoteUrl` is invoked from `repositoryWithRefreshedGitHubRepository` in `app-store.ts` every time the app refreshes GitHub repository metadata (e.g. on account change, periodic refresh, fetch): [1](#0-0) 

The function itself only checks three conditions before calling `git remote set-url`: [2](#0-1) 

1. `protocolsMatch` — only compares the URL *scheme* (`https:` vs `https:`), not the host.
2. `remoteUrlUnchanged` — verifies that the *current* local remote still equals the *previously stored* `gitHubRepository.cloneURL` (i.e., the user hasn't manually customized the remote). This is a consistency check against old state, not a validation of the new value.
3. `!urlsMatch` — verifies the new URL differs from the current remote.

Crucially, **there is no check that the new `apiRepo.clone_url` hostname matches the account's expected endpoint (github.com or the configured GHES host) or the previous remote's hostname**. `urlMatchesRemote`/`urlsMatch` (used only to detect "no change") compares hostname, owner, and name, but that comparison is used to *skip* the update when everything already matches — it is never used as a *gate* requiring the new host to equal the old host. As long as the scheme is the same and the local remote hasn't been hand-edited, whatever `clone_url` the API returns is written straight into the repository's git config via `gitStore.setRemoteURL` → `git remote set-url`: [3](#0-2) 

If the API response for a given `owner/name` (fetched via `api.fetchRepository`) ever contains a `clone_url` pointing at a different host than the account's real endpoint — for example due to a compromised/malicious GitHub Enterprise Server the account is configured against, a repository-transfer race, or any other means by which the attacker can influence the JSON `IAPIRepository`/`IAPIFullRepository` object returned to the client — Desktop will silently rewrite the user's `origin` remote to that attacker-controlled URL with no prompt, confirmation dialog, or warning.

This corrupted remote value then poisons all subsequent git operations:
- `git push` sends the user's commits to the attacker's server instead of the real one (silent corruption of what the user pushes).
- `git fetch`/`pull` pulls history from the attacker's server, which can then be merged/checked out locally.
- Authentication for the new host flows through the trampoline credential helper (`GIT_ASKPASS`/credential-helper trampoline), which resolves credentials per-hostname; a host swap can cause credentials meant for the legitimate service to be requested/sent against the new, attacker-supplied endpoint, per `getCredentialUrl`/`getEndpointKind` in `trampoline-credential-helper.ts`.

### Impact Explanation
Because the check only prevents a change when the URL is unchanged and the user hasn't manually edited the remote, it does not stop a hostname change coming from the API layer. A user who never touched their remote configuration can have `origin` silently redirected to a different server. Consequences:
- Commits and pushes are silently redirected to a repository the user did not intend, potentially exposing private code/history to the attacker.
- Because Git credential resolution is host-scoped, the credential/token flow initiated for the new host could hand credentials to the wrong endpoint depending on how the credential helper resolves the URL.
- The user receives no notification that their remote changed; the only observable effect is in `git remote -v` output, which most users never inspect.

### Likelihood Explanation
The precondition is that the API layer/endpoint returns an `IAPIRepository`/`IAPIFullRepository.clone_url` value for the same `owner/name` pair that differs in host from what the account is configured against. This can plausibly occur for accounts using GitHub Enterprise Server (custom, admin-configured endpoints, where the endpoint's authenticity is not independently re-verified per response) or in any scenario where the API response object is attacker-influenced (matching the report's explicit "attacker controls ... a GitHub API object" primitive). The refresh path (`repositoryWithRefreshedGitHubRepository`) runs routinely — on fetch, account switch, and periodic repository refresh — giving the attacker many opportunities to trigger the write with no user interaction required.

### Recommendation
Add an explicit host allow-list check in `updateRemoteUrl` before calling `setRemoteURL`: require that the hostname of `apiRepo.clone_url` matches the hostname of the account's configured endpoint (or the previous remote's hostname) in addition to the existing protocol check. If the hostname differs, do not silently update the remote — either skip the update entirely or surface a confirmation prompt to the user before altering `origin`.

### Proof of Concept
1. User has a repository whose `origin` remote is `https://github.example.com/org/repo.git`, associated with a GitHub Enterprise account whose endpoint is `https://github.example.com/api/v3`.
2. On a routine refresh (e.g. triggered by `_fetch` → `withRefreshedGitHubRepository` → `repositoryWithRefreshedGitHubRepository`), `api.fetchRepository(owner, name)` returns an `IAPIFullRepository` whose `clone_url` is `https://evil-mirror.example/org/repo.git` (same `https:` scheme, different host) — this can happen if the GHES instance is compromised or the response is otherwise attacker-influenced.
3. In `updateRemoteUrl`:
   - `protocolsMatch` is `true` (`https:` === `https:`).
   - `remoteUrlUnchanged` is `true` (current remote still equals the last-known good `cloneURL`, since the user never edited it).
   - `urlsMatch` is `false` (different host).
4. The condition `protocolsMatch && remoteUrlUnchanged && !urlsMatch` is satisfied, so `gitStore.setRemoteURL('origin', 'https://evil-mirror.example/org/repo.git')` executes, silently rewriting the git config's remote URL.
5. The next `git push`/`git fetch` performed by the user (or by any background fetch task) now targets `evil-mirror.example` instead of the legitimate host, with no warning shown to the user.

```typescript
  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
```
