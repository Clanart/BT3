Based on my investigation, I found a genuine checks-effects-interactions violation analog in the SSH askpass credential-storage flow.

### Title
SSH key passphrase is persisted to the OS credential store immediately on prompt, before the remote authentication (external interaction) is confirmed to succeed - (File: app/src/lib/trampoline/trampoline-askpass-handler.ts)

### Summary
`handleSSHKeyPassphrase` in the trampoline askpass handler writes the user-entered SSH key passphrase to the OS keychain (`TokenStore`/`setSSHKeyPassphrase`) as soon as the user chooses "remember," *before* the ongoing `ssh`/git network operation with the remote has completed or authenticated successfully. Only if the whole git operation subsequently throws an `SSHAuthenticationFailed` error is the just-stored credential rolled back.

### Finding Description
The flow is:
1. `withTrampolineEnv` (`app/src/lib/trampoline/trampoline-environment.ts:93-202`) spawns a git subcommand with `GIT_ASKPASS` wired to the trampoline. This subcommand talks to a network endpoint (a git remote over SSH), which is attacker-influenced input in the threat model (a malicious/compromised remote or MITM proxy can send arbitrary SSH prompts).
2. When `ssh` needs a key passphrase, the trampoline invokes `handleSSHKeyPassphrase` (`app/src/lib/trampoline/trampoline-askpass-handler.ts:55-109`). If the user opts to remember the passphrase, `setSSHKeyPassphrase(operationGUID, keyPath, passphrase)` is called immediately (line 103), which calls into `TokenStore.setItem` (`app/src/lib/ssh/ssh-key-passphrase.ts:37-54`) — writing the plaintext-equivalent secret into the OS-native secure storage right away.
3. The "effect" (persisting the secret) happens *before* the "interaction" (the actual outcome of the SSH handshake/authentication with the remote host) is known. The code comment in `ssh-credential-storage.ts:17-22` even acknowledges the intended invariant ("we don't want to store it until we know the git operation finished successfully") but the implementation does not honor it — the store happens synchronously on prompt, not after success.
4. Rollback only occurs in the `catch` block of `withTrampolineEnv` (`trampoline-environment.ts:148-158`), and only if the thrown error is classified as `isSSHAuthFailure(e)`. This is a heuristic keyed off error text/type, not a cryptographic proof of what actually happened during the SSH session.

Because the desktop app auto-forks a detached `setsid` process for the SSH wrapper (`vendor/desktop-trampoline/src/ssh-wrapper.c`) and treats the exchange as a black box relayed through `GIT_ASKPASS`, the only signal Desktop has that "the interaction succeeded" is the final exit status/error class of the whole git command. A remote or proxy that can influence intermediate protocol behavior (e.g., cause the overall command to appear to "succeed" via a partial network operation, or produce an error that isn't classified as `SSHAuthenticationFailed`, e.g. a timeout, a `Connection reset`, or protocol downgrade) will leave the persisted passphrase in the keychain despite authentication never having been confirmed as legitimate.

### Impact Explanation
The passphrase for the user's private SSH key is committed to persistent, OS-level secure storage optimistically, keyed only by the hash of the local key file — not by any verified relationship to a specific, authenticated remote. If the effects (persisting the secret) are not strictly gated on the interaction's confirmed success (and correctly classified failure paths), a malicious remote/proxy that can influence the shape of the failure (so it isn't detected as `SSHAuthenticationFailed`) can leave the user's decrypted-key passphrase permanently cached in the keychain even though the "trust" decision it was supposed to be conditioned on was never actually confirmed. This is a persistent local secret-exfiltration-adjacent risk: any other local process or later git operation that can read this keychain entry (or a future feature/bug reusing `getSSHKeyPassphrase`) obtains the passphrase for a private key without the user having re-confirmed the operation succeeded legitimately.

### Likelihood Explanation
This requires an attacker who controls the remote/proxy the user is authenticating against and who can shape the SSH askpass interaction (a plausible "attacker controls a git remote/proxy response" scenario per the task's valid-impact list). The failure-classification gap (`isSSHAuthFailure`) is a heuristic, not exhaustive of every way an operation can end without genuine successful authentication, so the effect (persisted passphrase) not being cleanly reverted is realistic rather than purely theoretical.

### Recommendation
Defer the `TokenStore.setItem` write until the git subcommand has fully and successfully completed (i.e., invert the pattern: only persist in the success path of `withTrampolineEnv`, not eagerly on prompt with a compensating delete on a narrow error match). If eager storage is required for UX reasons, gate the write on a definitive, explicit "authenticated" signal rather than the general command exit code/error class, and broaden failure handling to delete the pending credential on *any* non-success outcome, not just the ones matching `isSSHAuthFailure`.

### Proof of Concept
Conceptual PoC (network-observation dependent, cannot be fully demonstrated from static code alone):
1. User has an SSH remote configured to a repository controlled by an attacker (e.g., a spoofed self-hosted git server, or MITM on the network path).
2. User performs a fetch/clone; `ssh` prompts for the key passphrase; user opts "Remember passphrase."
3. `setSSHKeyPassphrase` immediately persists the passphrase to the keychain (`app/src/lib/trampoline/trampoline-askpass-handler.ts:103`, `app/src/lib/ssh/ssh-key-passphrase.ts:37-54`).
4. The attacker's server closes the connection or responds in a way that produces a git error not matching `isSSHAuthFailure` (e.g., a generic network/protocol error) rather than an explicit SSH auth failure.
5. `deleteMostRecentSSHCredential` is never invoked (`trampoline-environment.ts:149-158` only runs on `isSSHAuthFailure`), so the passphrase remains permanently stored in the OS keychain despite the interaction never having been confirmed as a legitimate, successful authentication.     await trampolineUIHelper.promptSSHKeyPassphrase(keyPath)

  // If the user wanted us to remember the passphrase, we'll keep it around to
  // store it later if the git operation succeeds.
  // However, when running a git command, it's possible that the user will need
  // to enter the passphrase multiple times if there are failed attempts.
  // Because of that, we need to remove any pending passphrases to be stored
  // when, in one of those multiple attempts, the user chooses NOT to remember
  // the passphrase.

    setSSHKeyPassphrase(operationGUID, keyPath, passphrase)
  } else {
    removeMostRecentSSHCredential(operationGUID)
  }

  return passphrase ?? ''
}

export async function setSSHKeyPassphrase(
  operationGUID: string,
  keyPath: string,
  passphrase: string
) {
  try {
    const keyHash = await getHashForSSHKey(keyPath)

    await setSSHCredential(
      operationGUID,
      SSHKeyPassphraseTokenStoreKey,
      keyHash,
      passphrase
    )
  } catch (e) {
    log.error('Could not store passphrase for SSH key:', e)
  }
}

/**
 * This map contains the SSH credentials that are pending to be stored. What this
 * means is that a git operation is currently in progress, and the user wanted
 * to store the passphrase for the SSH key, however we don't want to store it
 * until we know the git operation finished successfully.
 */
const mostRecentSSHCredentials = new Map<string, SSHCredentialEntry>()

/**
 * Stores an SSH credential and also keeps it in memory to be deleted later if
 * the ongoing git operation fails to authenticate.
 *
 * @param operationGUID A unique identifier for the ongoing git operation. In
 *                      practice, it will always be the trampoline token for the
 *                      ongoing git operation.
 * @param store         Store where the SSH credential is stored.
 * @param key           Key that identifies the SSH credential (e.g. username or
 *                      key hash).
 * @param password      Password for the SSH key / user.
 */
export async function setSSHCredential(
  operationGUID: string,
  store: string,
  key: string,
  password: string
) {
  setMostRecentSSHCredential(operationGUID, store, key)
  await TokenStore.setItem(store, key, password)
}
