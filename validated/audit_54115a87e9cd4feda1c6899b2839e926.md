### Title
Unbounded index read from attacker-controlled CLVM atom length prefix during mempool canonical-serialization check causes uncaught exception - (File: chia/full_node/mempool_manager.py)

### Summary
`MempoolManager.validate_spend_bundle()` calls `is_clvm_canonical(bytes(coin_spend.puzzle_reveal))` and `is_clvm_canonical(bytes(coin_spend.solution))` on every coin spend of every submitted spend bundle, before the bundle is accepted into the mempool [1](#0-0) . This mirrors the reported bug class: a length field taken from untrusted, attacker-supplied bytes is trusted to walk through a buffer without validating it against the buffer's actual size.

### Finding Description
`is_clvm_canonical()` walks the raw CLVM byte buffer using an `offset` cursor and, for atoms, delegates to `is_atom_canonical(clvm_buffer, offset)` to compute how many bytes to advance [2](#0-1) .

`is_atom_canonical()` reads a variable-length size prefix (1–6 bytes) directly from `clvm_buffer` and computes `atom_len` purely from attacker-controlled bytes, with no check that `offset` or `offset + prefix_len` stays within the buffer bounds before indexing into it:

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    ...
    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]
    return 1 + prefix_len + atom_len, atom_len >= min_value
``` [3](#0-2) 

The caller `is_clvm_canonical()` then advances `offset += atom_len` using this attacker-influenced `atom_len` and re-indexes `clvm_buffer[offset]` on the next loop iteration without a bounds check [4](#0-3) . Because `atom_len` can be crafted to claim far more bytes than actually remain in `clvm_buffer` (a "mismatched reported length vs. actual buffer size" condition — the same root cause class as the msgpack corrupted-array-length bug), the next `clvm_buffer[offset]` access can raise an unhandled `IndexError` inside `MempoolManager.validate_spend_bundle()`.

This code path is reached by an ordinary, unprivileged wallet action: submitting a spend bundle for mempool admission (`send_transaction` / `PushTX` RPC / full-node `transaction_ack` flow) with a puzzle reveal or solution whose CLVM atom uses a non-canonical, oversized length prefix. Existing tests confirm this exact scenario is already exercised for other purposes (rejecting non-canonical encodings), e.g. `test_mempool_requires_canonical_clvm` [5](#0-4) , though that test only exercises encodings that are non-canonical but still buffer-bounded — it does not construct a length prefix that overruns the buffer entirely.

### Impact Explanation
If an `IndexError` (or similar exception) propagates uncaught out of `validate_spend_bundle()`, it would not be converted into a normal `ValidationError`/`Err` rejection the way `pre_validate_spendbundle()`'s `ValueError` path is handled [6](#0-5) . Depending on where `validate_spend_bundle()` is invoked (under the blockchain mutex, per the mempool doc's admission pipeline [7](#0-6) ), an unhandled exception here could disrupt transaction-processing for that call, which matches the "spend-triggered transaction-processing halt" impact category. This would be reachable from a single, unprivileged spend-bundle submission — no peer/node compromise required.

### Likelihood Explanation
Medium-to-low confidence: I was able to prove the length-prefix computation is unbounded and unchecked at the `is_atom_canonical`/`is_clvm_canonical` level, and that this function is invoked directly on raw, attacker-controlled bytes (`coin_spend.puzzle_reveal`, `coin_spend.solution`) during ordinary mempool admission. However, I could **not** fully verify within the available context whether:
1. `validate_spend_bundle()`'s caller wraps the whole call in a broad `try/except` that would catch and convert an `IndexError` into a normal rejection (the analogous `pre_validate_spendbundle()` only catches `ValueError`, not `IndexError`), and
2. whether `bytes(coin_spend.puzzle_reveal)`/`bytes(coin_spend.solution)` (Rust-backed `SerializedProgram`) already performs its own structural validation on construction/deserialization that would reject a malformed atom length before `is_clvm_canonical` ever sees it (this validation, if any, lives in the compiled `chia_rs` extension and was not visible in this Python-only index).

Because of this uncertainty about exception handling and upstream Rust-side validation, I cannot assert this is a definitively exploitable, unguarded crash path with full confidence — only that the length-prefix-trust pattern matching the reported CVE class exists in this specific function.

### Recommendation
- Add explicit bounds checks in `is_atom_canonical()` before each `clvm_buffer[offset]` access (e.g., raise/return a "non-canonical"/error result rather than letting an out-of-range index be dereferenced) so a malformed length prefix cannot cause an unhandled exception.
- Ensure `is_clvm_canonical()`'s call site (`validate_spend_bundle()`) catches structural/parsing exceptions and converts them into `Err.INVALID_COIN_SOLUTION` (or equivalent) rather than allowing them to propagate, mirroring the `ValueError`-to-`ValidationError` translation already done in `pre_validate_spendbundle()`.
- Confirm (via the `chia_rs` Rust source, not available in this Python index) whether `SerializedProgram`/`CoinSpend` deserialization already rejects malformed atom length prefixes before they reach `is_clvm_canonical`; if so, document that invariant so this function's assumptions are load-bearing and enforced upstream.

def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
