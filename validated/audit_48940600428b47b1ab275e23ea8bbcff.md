### Title
Untrusted `ReceivedOutput` bytes can report unspendable Bitcoin outputs - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` deserializes an offset, a `TxOut`, and an `OutPoint` without proving that the `OutPoint` identifies a real transaction output or that the encoded `TxOut` is actually contained at that position. Downstream transaction construction trusts those fields, while `SignableTransaction::multisig` only checks that the serialized prevout script matches the tweaked group key. This allows attacker-controlled bytes to create a plausible-looking input for a nonexistent output.

### Finding Description
`ReceivedOutput::read` accepts three independent claims from untrusted input:

1. A scalar offset via `Secp256k1::read_F`.
2. A Bitcoin `TxOut` via consensus decoding.
3. An `OutPoint` via consensus decoding. [1](#0-0) 

There is no check that the decoded `TxOut` is actually `tx.output[vout]` for the decoded outpoint. This differs from outputs produced by `Scanner::scan_transaction`, which derives the `OutPoint` from the transaction actually being scanned and copies the corresponding output. [2](#0-1) 

When a deserialized output is passed to `SignableTransaction::new`, the decoder's `TxOut` is stored as the prevout and its `OutPoint` is placed in the unsigned transaction input. [3](#0-2) [4](#0-3) 

`SignableTransaction::multisig` then compares the derived tweaked key's P2TR script against `self.prevouts[i].script_pubkey`. It does not validate the outpoint or verify that the prevout is real. [5](#0-4) 

### Impact Explanation
An attacker who can provide serialized `ReceivedOutput` bytes can make the system treat a nonexistent or incorrectly represented Bitcoin output as received funds. They can encode:

- A random or nonexistent txid/vout.
- An arbitrary value.
- The exact P2TR script corresponding to the group key plus their encoded offset.

The object will pass the only consistency check in `multisig`, be counted toward `input_sat`, and produce a transaction that Bitcoin consensus cannot accept because its input does not exist or references a different output. This satisfies the “funds reported received that are not spendable” analog: accounting and signing logic can act on attacker-declared output contents rather than on data proven to be on-chain.

### Likelihood Explanation
The malicious input is only structurally valid serialized data. No private key material, validator compromise, race condition, or hash collision is needed. The attacker merely needs to reach a path where `ReceivedOutput::read` is used on attacker-influenced bytes and the resulting object is accepted into transaction planning or signing.

### Recommendation
Do not treat a deserialized `ReceivedOutput` as authenticated chain data. Before using it for balance accounting or signing:

- Resolve `outpoint` against the chain or a trusted UTXO view.
- Verify the resolved transaction contains `vout`.
- Require `resolved_tx.output[vout] == output`.
- Verify `p2tr_script_buf(group_key + offset * G)` equals the resolved output's script.
- Persist a chain-derived proof or trusted origin marker with scanner outputs rather than relying on the self-describing serialization.

### Proof of Concept
Conceptually:

```rust
use bitcoin::{OutPoint, TxOut, Amount, Txid};
use k256::Scalar;

use bitcoin_serai::{
  bitcoin::consensus::serialize,
  wallet::{p2tr_script_buf, ReceivedOutput, SignableTransaction},
};

// `group_key` is the even-Y key whose output Serai can spend.
let script = p2tr_script_buf(group_key).unwrap();

let mut serialized = Vec::new();
serialized.extend(Scalar::ZERO.to_bytes());
serialized.extend(serialize(&TxOut {
  value: Amount::from_sat(100_000_000),
  script_pubkey: script,
}));
serialized.extend(serialize(&OutPoint {
  txid: "00".repeat(32).parse::<Txid>().unwrap(),
  vout: 0,
}));

let forged = ReceivedOutput::read(&mut serialized.as_slice()).unwrap();

// This records the forged TxOut as the prevout and uses the forged OutPoint
// as an input. `multisig(keys)` then accepts it because the encoded script
// matches the group key with offset zero, despite the outpoint being fake.
let signable = SignableTransaction::new(
  vec![forged],
  &payments,
  change,
  None,
  fee_per_vbyte,
).unwrap();

assert!(signable.multisig(&keys).is_some());
```

The resulting transaction is signable by the threshold key but invalid on Bitcoin because the referenced input was never proven to exist or to contain the encoded `TxOut`.
