### Title
CW→ERC Pointer Registration Bypasses `RegisterPointerDisabled` Governance Gate via EVM `pointer` Precompile - ([File: precompiles/pointer/legacy/v562/pointer.go])

### Summary
The `RegisterPointerDisabled` chain parameter is meant to be a global kill-switch that blocks creation of new CW→ERC pointer contracts. It is enforced in the Cosmos-side `MsgServer.RegisterPointer` handler, but the equivalent EVM-side entry point — the `pointer` precompile's `AddNativePointer`, `AddCW20Pointer`, and `AddCW721Pointer` methods — never checks this flag. Any unprivileged EVM caller can therefore create native/CW20/CW721 pointer contracts directly through the precompile even after governance/admin has disabled pointer registration, mirroring the reported bug class of a security control enforced at only one interface while a second, equally privileged interface bypasses it entirely.

### Finding Description
`x/evm/keeper/msg_server.go`'s `RegisterPointer` handler is the sanctioned way to create CW20/CW721/CW1155 → ERC pointer contracts, and it explicitly gates on the parameter: [1](#0-0) 

This flag is set via `MigrateDisableRegisterPointer`, i.e. it is meant to permanently or conditionally shut off pointer creation chain-wide: [2](#0-1) 

However, the `pointer` EVM precompile — the "native/CW20/CW721" pointer creation path reachable directly by any EVM transaction sender — dispatches straight to `AddNative`/`AddCW20`/`AddCW721` with no reference to `RegisterPointerDisabled` anywhere in its `Execute` method or the individual handlers: [3](#0-2) [4](#0-3) 

The same omission exists in the newer `v580` variant of the precompile: [5](#0-4) 

Both handlers only validate payability/arg-length and the existing-pointer version — never the disabled param — before calling `evm.Create` to deploy a fresh pointer contract and persisting it via `SetERC20NativePointer` / `SetERC721CW721Pointer`. This is structurally identical to the CVE-2026-56256 pattern: a privileged/gated action ("mandatory 2FA"/"registration disabled") is enforced only on one API surface (Cosmos `MsgServer`/"UI") while a second, functionally equivalent surface (the EVM precompile/"backend API") allows the same state-changing operation to be replayed without the control.

### Impact Explanation
When an operator disables pointer registration (e.g., due to a discovered bug in pointer contract templates, to freeze the CW↔EVM bridge surface, or as an emergency mitigation), any unprivileged EVM account can still call the `pointer` precompile to deploy new native/CW20/CW721 pointer contracts and register them in EVM state (`SetERC20NativePointer`, `SetERC721CW721Pointer`). This defeats the intended chain-wide freeze of the pointer subsystem, undermines an operator's ability to halt pointer creation during an incident, and can enable continued exploitation of whatever bug motivated disabling registration in the first place (e.g., creating malicious/incorrect pointer mappings for arbitrary CW20/CW721 tokens that other users' wallets/dApps may then trust as canonical ERC20/ERC721 representations of those assets).

### Likelihood Explanation
High likelihood of exploitation once the flag is set: any address can call the `pointer` precompile at its fixed address with no authorization requirement, and the code path unconditionally reaches `evm.Create`/`SetERC20NativePointer`/`SetERC721CW721Pointer` — there is no gating check to bypass, it simply does not exist in this code path.

### Recommendation
Add a `RegisterPointerDisabled` (or equivalent) check to the `pointer` precompile's `Execute`/`AddNative`/`AddCW20`/`AddCW721` handlers (and any other CW1155/legacy variants), returning an error identical to the `MsgServer.RegisterPointer` behavior when the parameter is set, so that the EVM precompile entry point enforces the same governance-controlled gate as the Cosmos message-server entry point.

### Proof of Concept
1. Chain operator/governance sets `params.RegisterPointerDisabled = true` (e.g., via `MigrateDisableRegisterPointer` or a param-change proposal).
2. Confirm the Cosmos path is blocked: submitting `MsgRegisterPointer` fails with `"registering CW->ERC pointers has been disabled"` as covered by `TestRegisterPointerDisabled`.
3. From any unprivileged EVM account, call the `pointer` precompile's `addNativePointer("factory/.../subdenom")` (or `addCW20Pointer`/`addCW721Pointer`) method.
4. Observe the call succeeds: a new pointer contract is deployed via `evm.Create` and `SetERC20NativePointer`/`SetERC721CW721Pointer` persists the mapping — demonstrating that the governance-disabled state is bypassed entirely through the precompile surface.

func (p PrecompileExecutor) AddNative(ctx sdk.Context, method *ethabi.Method, caller common.Address, args []interface{}, value *big.Int, evm *vm.EVM, hooks *tracing.Hooks) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	token := args[0].(string)
	metadata, metadataExists := p.bankKeeper.GetDenomMetaData(ctx, token)
	if !metadataExists {
		return nil, 0, fmt.Errorf("denom %s does not have metadata stored and thus can only have its pointer set through gov proposal", token)
	}
	name := metadata.Name
	symbol := metadata.Symbol
	var decimals uint8
	for _, denomUnit := range metadata.DenomUnits {
		if denomUnit.Exponent > uint32(decimals) && denomUnit.Exponent <= math.MaxUint8 {
			decimals = uint8(denomUnit.Exponent)
			name = denomUnit.Denom
			symbol = denomUnit.Denom
			if len(denomUnit.Aliases) > 0 {
				name = denomUnit.Aliases[0]
			}
		}
	}
	contractAddr, err := p.evmKeeper.UpsertERCNativePointer(ctx, evm, token, utils.ERCMetadata{Name: name, Symbol: symbol, Decimals: decimals})
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(contractAddr)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
