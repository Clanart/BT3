### Title
Payout attribution (operator OP_RETURN) is not bound to the user's SinglePlusAnyoneCanPay withdrawal signature, allowing a payout to be misattributed to an operator who never funded it - ([File: core/src/operator.rs])

### Summary
The bridge determines which operator should be reimbursed for a withdrawal by reading an OP_RETURN output embedded in the confirmed payout transaction, not by anything the withdrawing user actually signed. Because the user's authorization signature uses `SIGHASH_SINGLE|ANYONECANPAY`, it only commits to the withdrawal input and the single matching payout output — it leaves every other input (fee funding) and output (including the OP_RETURN operator-attribution output) completely unconstrained. Any party that observes the signed withdrawal input (e.g., in the mempool before confirmation) can build a competing transaction spending the same input/output pair while embedding an arbitrary operator's `xonly_pk` in the OP_RETURN, and win the race to confirmation.

### Finding Description
The user authorizes a withdrawal payout by signing with `TapSighashType::SinglePlusAnyoneCanPay`, which is explicitly enforced in the parser: [1](#0-0) 

The operator's `withdraw()` builds the payout transaction from this single signed input/output pair and then funds it with `fund_raw_transaction(..., add_inputs: Some(true), ...)`, adding fee inputs, change, and (per the OP_RETURN based attribution mechanism used later) an operator identity commitment. None of these additions are covered by the user's SINGLE|ANYONECANPAY signature: [2](#0-1) 

Verifiers later scan confirmed blocks and derive *which operator gets credited for the reimbursement* purely from the OP_RETURN output of whatever payout transaction actually confirmed for that withdrawal UTXO: [3](#0-2) 

This attribution is then trusted as the source of truth for reimbursement eligibility — an operator is only allowed to proceed with the reimbursement (kickoff) flow if the DB-recorded payer matches its own key: [4](#0-3) 

Because the OP_RETURN (attribution data) is outside the signed message, the binding "party that authorized the spend of the withdrawal UTXO == party credited as payer" does not hold. The equality that should hold is:

`payer_xonly_pk (recorded from OP_RETURN of the tx that actually confirms) == operator whose funds actually paid the user`

but nothing enforces this, since the signature only binds `(withdrawal_input, user_payout_output)` and not `(funding_inputs, OP_RETURN_output)`.

### Impact Explanation
Since `SIGHASH_SINGLE|ANYONECANPAY` permits any third party to append arbitrary inputs/outputs to a transaction that still satisfies the same signature, an attacker who sees a real operator's payout transaction (once broadcast, but before confirmation) can construct a rival transaction that:
- reuses the identical signed withdrawal input and matching payout output (still valid under the SINGLE|ANYONECANPAY signature),
- substitutes its own (or a colluding operator's) fee-funding inputs,
- embeds a different operator's `xonly_pk` in the OP_RETURN,

and races it to confirmation (via a higher fee, or RBF/CPFP tricks against the honest operator's fee-bumping transaction). If this rival transaction confirms:
- The credit for the reimbursement is now attributed by `update_finalized_payouts`/`update_payout_txs_and_payer_operator_xonly_pk` to an operator that never actually funded the user's withdrawal, which lets that operator proceed through `validate_payer_is_operator` and claim the collateral-chain reimbursement it did not earn (Critical: "an operator reimbursed for a payout it never funded").
- Simultaneously, the honest operator who actually funded (via its own broadcast, now conflicting/double-spent) permanently loses its ability to be credited for that specific withdrawal, since the withdrawal UTXO can only be spent once and the DB attribution logic keys off the txid that actually lands on-chain (Critical: "an honest operator permanently unable to be reimbursed").

This is a direct analog to the report's core theme: the "vault"/credit-worthy state (who is entitled to reimbursement) is determined by data that is mutable by a party other than the one whose value/authorization actually matters, right up until the moment of on-chain settlement.

### Likelihood Explanation
Exploitation only requires: observing a broadcast-but-unconfirmed payout transaction (any Bitcoin network participant can do this via the mempool), being able to construct and fee-bump a standard Bitcoin transaction, and no privileged role, key, or insider access. Note that this analysis could not fully confirm from the indexed code exactly where/how the OP_RETURN commitment output is appended in the payout tx construction path (the fee/OP_RETURN addition appears to occur via wallet funding rather than in the reviewed `create_payout_txhandler` snippet), so the precise mechanics of "who normally adds the OP_RETURN and when" should be verified against the full source before treating this as conclusively exploitable; a Devin session with full repository access would be needed to trace `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs`) end-to-end and confirm the OP_RETURN output is unsigned relative to the user's SINGLE|ANYONECANPAY signature.

### Recommendation
Bind the operator-attribution data (OP_RETURN operator xonly_pk) inside the scope of a signature/commitment that cannot be altered by a third party — e.g., have the operator itself sign a message covering the OP_RETURN content together with the specific withdrawal outpoint before broadcast, or require verifiers to accept payout attribution only from a pre-registered, verifier-cosigned announcement rather than trusting whatever OP_RETURN happens to confirm on-chain.

### Proof of Concept
1. Honest Operator A observes a valid withdrawal request (SIGHASH_SINGLE|ANYONECANPAY-signed `input_signature` over `input_outpoint` and payout `output_txout`), builds a payout tx via `create_payout_txhandler`, funds it (adding its own fee inputs and an OP_RETURN with its own `xonly_pk`), and broadcasts it (`core/src/operator.rs:620-674`).
2. Attacker (or colluding Operator B) observes this transaction in the mempool. Because only `(input_outpoint, output_txout)` is covered by the SINGLE|ANYONECANPAY signature, Attacker constructs a new transaction reusing that exact signed input/output pair but with its own funding inputs and an OP_RETURN embedding Operator B's `xonly_pk` instead.
3. Attacker fee-bumps this competing transaction so it confirms instead of Operator A's.
4. Verifier's `update_finalized_payouts` (`core/src/verifier.rs:2283-2350`) scans the now-confirmed block, reads the OP_RETURN, and records Operator B as `payout_payer_operator_xonly_pk` for that withdrawal via `update_payout_txs_and_payer_operator_xonly_pk`.
5. Operator B calls `validate_payer_is_operator` (`core/src/operator.rs:1686-1729`), which succeeds because the DB now says Operator B is the payer, letting Operator B proceed to claim reimbursement it never funded — while Operator A, who actually paid the user, has no path to be credited for that withdrawal.

    async fn validate_payer_is_operator(
        &self,
        dbtx: Option<DatabaseTransaction<'_>>,
        deposit_id: u32,
    ) -> Result<(BlockHash, Txid), BridgeError> {
        let (payer_xonly_pk, payout_blockhash, kickoff_txid) = self
            .db
            .get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id(dbtx, deposit_id)
            .await?;

        tracing::info!(
            "Payer xonly pk and kickoff txid found for the requested deposit, payer xonly pk: {:?}, kickoff txid: {:?}",
            payer_xonly_pk,
            kickoff_txid
        );

        // first check if the payer is the operator, and the kickoff is handled
        // by the PayoutCheckerTask, meaning kickoff_txid is set
        let (payout_blockhash, kickoff_txid) = match (
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid,
        ) {
            (Some(payer_xonly_pk), Some(payout_blockhash), Some(kickoff_txid)) => {
                if payer_xonly_pk != self.signer.xonly_public_key {
                    return Err(eyre::eyre!(
                        "Payer is not own operator for deposit, payer xonly pk: {:?}, operator xonly pk: {:?}",
                        payer_xonly_pk,
                        self.signer.xonly_public_key
                    )
                    .into());
                }
                (payout_blockhash, kickoff_txid)
            }
            _ => {
                return Err(eyre::eyre!(
                    "Payer info not found for deposit, payout blockhash: {:?}, kickoff txid: {:?}",
                    payout_blockhash,
                    kickoff_txid
                )
                .into());
            }
        };
