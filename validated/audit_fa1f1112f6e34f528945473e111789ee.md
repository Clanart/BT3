## Title
Working-directory file paths are opened/revealed via raw `Path.join` instead of the app's own symlink-aware containment check, allowing a malicious repo to make Desktop act on files outside the repo - (File: `app/src/lib/app-shell.ts`)

## Summary
GitHub Desktop has a dedicated containment/symlink-escape guard, `resolveWithin()`, that resolves a relative path against a root and rejects it (returns `null`) if the *real* (symlink-resolved) path escapes the root [1](#0-0) . It is correctly used to gate filesystem access in at least two places: `dispatcher.ts`'s `openRepositoryFromUrl` (deep-link `filepath` handling) [2](#0-1)  and `copilot-conflict-context.ts`'s conflict-file reader, whose own comment states it exists to "Guard against path traversal and symlink escapes" [3](#0-2) .

However, the much more common "open/reveal a file from the Changes list, History, or PR diff view" code paths never call this guard at all. They build the target path with a bare `Path.join(repository.path, path)` and hand it straight to Electron's shell/spawn APIs:

- `revealInFileManager()` — `Path.join(repository.path, path)` → `shell.showItemInFolder` [4](#0-3) 
- `sidebar.tsx`'s `onOpenItem` — `Path.join(...)` → `openFile()` (opens with the OS default program) [5](#0-4) 
- `app.tsx`'s `onOpenInExternalEditor` — `Path.join(...)` → `dispatcher.openInExternalEditor(fullPath)` → spawns the user's configured editor process with that path as an argument [6](#0-5) [7](#0-6) [8](#0-7) 
- `selected-commits.tsx`, `pull-request-files-changed.tsx`, `filter-changes-list.tsx`, `unmerged-file.tsx` context menus — all do the same `Path.join(repository.path, file.path)` pattern before Reveal/Open/OpenInExternalEditor actions [9](#0-8) [10](#0-9) [11](#0-10) 

## Finding Description
The broken invariant here is the same class as the source report's `onlyOwner`/`onlyManager` modifiers: a check exists (`resolveWithin`), computes the right answer, but its result is not consistently *enforced* everywhere a sensitive operation is gated on "is this path inside the repository." Just as the Solidity modifier evaluated `msg.sender == owner` and discarded the boolean, GitHub Desktop's UI/dispatcher layer builds the "is-inside-repo" path with `Path.join` and never runs it — or its result — through the one function in the codebase (`resolveWithin`) that actually verifies containment after resolving symlinks, per the explicit test suite covering exactly this scenario (`fails for paths that use a symlink to traverse outside of the root`) [12](#0-11) .

`file.path` in these call sites is not app-generated — it comes directly from `git status`/`git diff` output for files that git considers part of the working tree (untracked, modified, or committed paths), which is fully attacker-influenced when the user clones or pulls a malicious repository. A commit can add a symlinked directory to the working tree (e.g., a symlink `docs -> /Users/victim/Library/Application Support/GitHub Desktop`) plus, via git status reporting untracked entries that git lstat's/walks (following the symlink for directory traversal purposes on POSIX), files that appear to Desktop as `docs/some-file` in the Changes list. `Path.join(repository.path, 'docs/some-file')` then legitimately resolves outside of the repository, but none of the six call sites above notice this, because they never call `resolveWithin`/`realpath` — they just trust `repository.path + relativePath`.

## Impact Explanation
Depending on which action the user takes from the (attacker-crafted) Changes/History/PR context menu:
- `revealInFileManager` / `showFolderContents` discloses the existence and location of files/directories outside the repo to the user (information disclosure, and a stepping stone for a follow-up social-engineering click).
- `openFile`/`OpenWithDefaultProgramLabel` opens the OS default handler for an arbitrary file path outside the repo, which for some extensions (e.g., `.url`, `.lnk`, `.desktop`, `.scpt` on macOS pre-restriction, or scripts if `isSafeFileExtension` doesn't cover the platform) can lead to code execution outside Desktop's control.
- `openInExternalEditor` spawns the user's configured editor with an absolute path outside the repo as an argument — for editors that support workspace/project files with embedded tasks or extensions auto-run on open (VS Code workspace trust edge cases, Sublime build systems, etc.), this can escalate to code execution, and at minimum lets an attacker force-open sensitive files (e.g., under `~/.ssh`, or the user's global git config, or another repository/credential store) inside an editor, which combined with e.g. VS Code Live Share or auto-formatting/auto-run extensions is a plausible code-execution vector.

This satisfies the report's required impact classes ("attacker controls a cloned/fetched repository" + "file write or read outside the repo" / potential "code execution").

## Likelihood Explanation
Likelihood is limited by two factors I could not fully verify with the tools available: (1) whether Desktop's status-parsing (`app/src/lib/git/status.ts`, not indexed in full) actually surfaces symlink-traversed untracked paths the way `git status --porcelain` does on the host OS, and (2) whether git's own checkout-time symlink protections (`core.protectHFS`/`core.protectNTFS`/symlink checkout refusal, no matches found in this codebase, meaning Desktop relies entirely on the system git binary's defaults) block the attacker from planting a *tracked* file through a symlinked directory in the first place. Modern git refuses to write tracked blobs through symlinked path components on checkout, so the most likely attacker path is a repository that ships a symlink and separately gets the user (or a build step) to create real files at the symlink target, or relies on already-existing files at that location — this narrows the practical trigger to "untracked file appears to live inside a symlinked dir the malicious repo introduced," which requires the target files to pre-exist outside the repo. Regardless of these caveats, the underlying code fact is unambiguous: `resolveWithin` exists specifically to close this gap and is bypassed by every open/reveal action listed above.

## Recommendation
Route every "open/reveal a repository-relative file path" call site through `resolveWithin(repository.path, path)` and refuse the action (matching the pattern already used in `dispatcher.ts` and `copilot-conflict-context.ts`) if it returns `null`:
- `app/src/lib/app-shell.ts` (`revealInFileManager`)
- `app/src/ui/changes/sidebar.tsx` (`onOpenItem`)
- `app/src/ui/app.tsx` (`onOpenInExternalEditor`)
- `app/src/ui/history/selected-commits.tsx`, `app/src/ui/open-pull-request/pull-request-files-changed.tsx`, `app/src/ui/changes/filter-changes-list.tsx`, `app/src/ui/lib/conflicts/unmerged-file.tsx`, `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx`

Alternatively, centralize this in a single wrapper (e.g., `toSafeRepositoryPath(repository, relativePath)`) so future call sites cannot forget the check, the same way the report recommends centralizing the `require` in the modifier rather than repeating an unenforced comparison.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
