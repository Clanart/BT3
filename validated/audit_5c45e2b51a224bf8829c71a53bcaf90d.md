### Title
Duplicate output-token legs in a single Intent Gateway order let a solver under-pay while the order is marked fully filled, permanently locking the input escrow for the skipped leg - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` tracks partial-fill progress per `(commitment, outputToken)` in `_partialFills`, not per output-array index. When an `Order.output.assets` array contains two or more entries for the **same** output token, filling the first entry silently satisfies the "remaining" check for every later entry with that same token — exactly the same class of bug as the external report: a cap/aggregate calculation that fails to correctly separate distinct legs of a bidirectional/multi-leg accounting structure, causing the wrong amount to be accepted as "already covered."

### Finding Description
In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:54-149`), the per-leg accounting is:

```solidity
uint256 totalRequired = order.output.assets[i].amount;
uint256 solverAmount = options.outputs[i].amount;

uint256 alreadyFilled = _partialFills[commitment][outputToken];
uint256 remaining = totalRequired - alreadyFilled;
if (remaining == 0 || solverAmount == 0) {
    if (solverAmount == 0 && remaining > 0) isFullyFilled = false;
    continue;
}
``` [1](#0-0) 

`_partialFills` is declared and documented as keyed by `(commitment, outputToken)` only, with no index component:

```solidity
mapping(bytes32 => mapping(bytes32 => uint256)) public _partialFills;
``` [2](#0-1) 

If `order.output.assets` contains two entries for the same `token` (e.g. `[ {A, 500}, {A, 500} ]`, total 1000 A owed), the loop processes them by index but consults a shared counter:
- Leg `i=0`: `alreadyFilled=0`, solver pays 500 A, `fillAmount=500`; `_partialFills[commitment][A]` is set to `500`; `escrowedAmount` is released for `order.inputs[0]`.
- Leg `i=1`: `alreadyFilled` is read as `500` (from the *same* key), so `remaining = 500 - 500 = 0`. The `remaining == 0` branch fires and the loop `continue`s — **without requiring or checking `solverAmount`**, without transferring any of `options.outputs[1].amount` to the beneficiary, and without setting `isFullyFilled = false` (that flag is only cleared in the `solverAmount == 0 && remaining > 0` sub-case, which is false here since `remaining == 0`).

Because `escrowedInputs[1]` is never assigned inside the `continue`d iteration, it keeps its default zero value (`token = bytes32(0)`, `amount = 0`) in the `TokenInfo[] memory escrowedInputs` array built for the withdrawal request. The order is nonetheless marked `_filled[commitment] = msg.sender` at the top of the function and `isFullyFilled` stays `true`, so `_withdraw(...)` is invoked with `isFullyFilled = true` and `OrderFilled` is emitted — permanently closing the order and blocking any future cancellation (`cancelOrder` reverts with `Filled()` once `_filled[commitment] != address(0)`).

The net effect:
1. The solver only has to actually transfer output tokens for the *first* leg referencing a given token — the required amount for every subsequent leg with the same token is treated as already satisfied and is never collected from the solver nor delivered to the beneficiary.
2. The escrowed input tokens reserved for that skipped leg (`order.inputs[1]`, i.e. `_orders[commitment][inputToken1]`) are never released via `escrowedInputs[1]` and can never be reclaimed afterward, since the order is already flagged filled — the funds are permanently stuck in the contract.

This is the direct local analog of the report's flaw: a "remaining/owed" computation aggregates over the wrong key (all legs sharing a token, instead of each individual leg), so a legitimate distinct obligation is wrongly treated as zero, corrupting both the amount released to the beneficiary and the amount released to the solver.

### Impact Explanation
- **Loss of funds / wrong beneficiary amount**: the order's beneficiary receives strictly less output than `order.output.assets` specifies, while the order is nonetheless marked fully filled — the solver systematically underpays relative to what the order committed to and the contract will never revisit that shortfall.
- **Fund lock**: the escrowed input tokens tied to any skipped duplicate-token leg become permanently unrecoverable — `cancelOrder` is blocked because `_filled[commitment]` is already set, and there is no other path in `IntrinsicIntents.sol`/`IntentGatewayV2.sol` that revisits a completed commitment.
- No admin, relayer, prover, or malicious-peer assumption is required — a solver interacting through the normal, unprivileged `fillOrder` entrypoint can trigger this outcome against any order whose `output.assets` happens to contain a duplicate token (which nothing in `placeOrder` prevents).

### Likelihood Explanation
Exploitability requires an order whose `output.assets` lists the same token more than once. Nothing in the order-placement path validates uniqueness of `output.assets[].token`, so a user (or a solver colluding with a malicious front-end/SDK bug) can produce such an order, after which any solver calling `fillOrder` can trigger the underpayment/lock behavior on the very first fill. This is a straightforward, low-cost, single-transaction exploit path with no external dependencies (no relayer, no proof, no governance), which makes it moderately-to-highly likely wherever order construction is not tightly restricted to unique output tokens.

### Recommendation
Track partial-fill progress per output-array index rather than (or in addition to) per output token, e.g. `mapping(bytes32 => mapping(uint256 => uint256)) _partialFills` keyed by `(commitment, i)`, or explicitly reject orders whose `output.assets` (or `inputs`) contain duplicate token entries at `placeOrder` time. Additionally, ensure `isFullyFilled` and the corresponding `escrowedInputs[i]` entry are only treated as "already satisfied" when the specific leg `i` — not merely some other leg sharing the same token — has actually received its required payment.

### Proof of Concept
1. User places an order with `order.output.assets = [{token: A, amount: 500}, {token: A, amount: 500}]` and two corresponding `order.inputs` entries reserving escrow for each leg (e.g. `inputs[0]` and `inputs[1]`, each backing one leg).
2. Solver calls `fillOrder` with `options.outputs = [{token: A, amount: 500}, {token: A, amount: 0}]` (or any amount for index 1 — it is never checked before the `continue`).
3. In `_fillSameChain`:
   - `i=0`: pays 500 A to beneficiary, releases `_orders[commitment][inputs[0].token]` to solver, sets `_partialFills[commitment][A] = 500`.
   - `i=1`: `alreadyFilled = 500 == totalRequired`, so `remaining == 0` → `continue`. No transfer of output token occurs; `escrowedInputs[1]` stays `{0, 0}`; `isFullyFilled` remains `true`.
4. `_filled[commitment]` is already set to the solver; `OrderFilled` is emitted with `isFullyFilled = true`.
5. Result: beneficiary received only 500 A instead of the committed 1000 A; the escrow reserved by `order.inputs[1]` remains in the contract (`_orders[commitment][inputs[1].token]` unchanged) and is now permanently unrecoverable because `cancelOrder` reverts with `Filled()`. [3](#0-2) [4](#0-3)

    function _fillSameChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        bool isFullyFilled = true;

        TokenInfo[] memory escrowedInputs = new TokenInfo[](outputsLen);
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            uint256 alreadyFilled = _partialFills[commitment][outputToken];
            uint256 remaining = totalRequired - alreadyFilled;
            if (remaining == 0 || solverAmount == 0) {
                if (solverAmount == 0 && remaining > 0) isFullyFilled = false;
                continue;
            }
            uint256 fillAmount;

            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;
            if (alreadyFilled == 0 && solverAmount > totalRequired) {
                fillAmount = totalRequired;
                uint256 dust = solverAmount - totalRequired;
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            } else {
                fillAmount = solverAmount > remaining ? remaining : solverAmount;
            }

            uint256 amountFilled = alreadyFilled + fillAmount;
            _partialFills[commitment][outputToken] = amountFilled;
            uint256 beneficiaryTotal = fillAmount + beneficiaryShare;

            if (token == address(0)) {
                if (msgValue < beneficiaryTotal + protocolShare) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }

            if (totalRequired > amountFilled) isFullyFilled = false;
            if (protocolShare > 0) emit DustCollected(token, protocolShare);

            uint256 escrowedAmount;
            if (amountFilled == totalRequired) {
                escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
            } else {
                escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
            }
            escrowedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: escrowedAmount});
            outputFills[i] = TokenInfo({token: outputToken, amount: fillAmount});
        }

        // Orders carrying output calldata must be filled completely in a single fill.
        // The attached call is only executed on a full fill, so a partial fill would
        // leave the intended side effect unexecuted while releasing proportional escrow.
        if (order.output.call.length > 0 && !isFullyFilled) revert PartialFillNotAllowed();

        WithdrawalRequest memory body = WithdrawalRequest({
            commitment: commitment, tokens: escrowedInputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
        });
        _withdraw(body, false, isFullyFilled);

        if (isFullyFilled) {
            _execute(order, outputsLen);
            emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: escrowedInputs});
        } else {
            delete _filled[commitment];
            emit PartialFill({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: escrowedInputs});
        }

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            (bool sent,) = msg.sender.call{value: msgValue}("");
            if (!sent) revert InsufficientNativeToken();
        }
    }
