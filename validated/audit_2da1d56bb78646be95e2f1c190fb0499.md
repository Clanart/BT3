### Title
Threshold key shares serialized and persisted unencrypted, recoverable by anyone with read access to the node's database - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::write` / `ThresholdKeys::serialize` emit the validator's FROST `secret_share` as raw scalar bytes with no encryption, and Serai's own persistence path (`GeneratedKeysDb::save_keys`) stores those bytes directly into the node's plaintext key-value database. This is the same bug class as CVE-2019-10291: long-term private credentials (threshold key shares) resting unencrypted in a general-purpose on-disk store that is not a secret store — while the codebase elsewhere acknowledges this hazard and encrypts cached FROST preprocesses precisely because "the DB isn't a proper secret store."

### Finding Description
`ThresholdKeys::write` serializes `self.core.secret_share` verbatim into the output stream: [1](#0-0)  The only protection applied is zeroizing the temporary `share_bytes` buffer after writing; the bytes that land in the `writer` are the raw secret scalar. [2](#0-1) 

The in-repo consumer that matters is `GeneratedKeysDb::save_keys` in the processor, which concatenates `substrate_keys.serialize()` and `network_keys.serialize()` and writes the result directly into `txn` — a plain RocksDB-style column family, not an encrypted store: [3](#0-2)  The paired `read_keys` reads them straight back with `ThresholdKeys::read`. [4](#0-3) 

The inconsistency proving this is a defect rather than intended design is in `SigningProtocol::preprocess_internal`: ephemeral cached preprocesses — which are weaker than a key share since they only leak the share if *reused* — are explicitly XOR-encrypted with a key derived from the validator's private key because "the DB isn't expected to be arbitrarily readable, it isn't a proper secret store and shouldn't be trusted as one": [5](#0-4)  No equivalent protection exists for the permanent `secret_share` itself, even though its disclosure is unconditionally catastrophic while preprocess disclosure is conditional.

### Impact Explanation
Any party able to read the node's database files — a co-located unprivileged OS user, a backup/snapshot leak, log shipping, or an unrelated file-read vulnerability — recovers the validator's full threshold `secret_share` in cleartext, for both the Ristretto (Substrate-side) and external-network (e.g., Bitcoin `Secp256k1`) keys. Possession of a key share is a permanent credential compromise: it contributes to any future signing set including that participant, enables blame/framing attacks against the victim, and combined with `t - 1` other compromised shares yields full group-key forgery — arbitrary Serai validator-set signatures and theft of bridged funds. Unlike the Jenkins CVE where stored credentials unlock a third-party service, here the stored credential *is* the signing key itself.

### Likelihood Explanation
Database files are routinely less protected than key material: they are copied into backups, shipped to replicas, and readable by processes/users that should never hold signing capability. The plaintext serialization makes any such exposure a key compromise with no additional work required — no memory scraping, no timing, no active attack. The exposure is silent and persistent (the share does not rotate on read).

### Recommendation
Apply the same treatment already used for `CachedPreprocesses`: encrypt `secret_share` before it leaves `ThresholdKeys`, or at minimum at the persistence boundary in `save_keys`, using a key derived from the node's secret (e.g., a domain-separated hash over the validator's sr25519 secret or a dedicated key-encryption secret). Ensure the at-rest format is authenticated (not bare XOR) so tampering with stored shares is detected on `ThresholdKeys::read`. Document that `serialize()` output is sensitive and must only be written to encrypted stores.

### Proof of Concept
Conceptual: obtain read access to the processor's DB directory (e.g., via a node backup or an unprivileged account on the host). Iterate the `GeneratedKeysDb` key space; each value is a concatenation of `ThresholdKeys` blobs. Each blob contains, after the curve ID, `t`, `n`, `i`, and interpolation tag, the raw 32/48-byte `secret_share` written by [6](#0-5)  with no length prefix or encryption — `ThresholdKeys::read` on the raw bytes succeeds and reconstructs a fully functional `ThresholdKeys`, as demonstrated by `read_keys` itself.         writer.write_all(&[0])?;
        for c in c {
          writer.write_all(c.to_repr().as_ref())?;
        }
      }
      Interpolation::Lagrange => writer.write_all(&[1])?,
    };
