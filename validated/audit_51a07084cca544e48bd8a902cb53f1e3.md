### Title
Spoofable `WWW-Authenticate: realm="GitHub"` header from a malicious git remote/proxy triggers Enterprise OAuth flow bound to an attacker-controlled host, leaking Desktop's OAuth `client_secret` - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
`getEndpointKind()` in the credential-helper trampoline classifies an arbitrary git remote host as a trusted "GitHub Enterprise" endpoint purely because the HTTP response returned by that remote (or a proxy in front of it) contains a `WWW-Authenticate` header with `realm="GitHub"`. That classification feeds directly into `trampolineUIHelper.promptForGitHubSignIn()`, which starts a normal Enterprise sign-in / OAuth flow *scoped to the attacker's host* without the user ever having manually entered or vetted that endpoint. Completing the resulting OAuth exchange causes Desktop to POST its shared, static `client_id`/`client_secret` to the attacker-controlled host via `requestOAuthToken()`.

### Finding Description
When Git needs credentials for an HTTPS remote, it invokes Desktop's credential helper trampoline (`createCredentialHelperTrampolineHandler`) → `getCredential()` → `getEndpointKind()`: [1](#0-0) 

If the remote is not `github.com`/`ghe.com` and there's no cached account for it, the function falls back to inspecting the `wwwauth[...]` credential fields, which Git populates directly from the server's (or an intermediary proxy's) `WWW-Authenticate` response header:

```
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    }
    ...
```

Any git server the user is fetching/pushing/cloning from — including a completely untrusted third-party host or a malicious/compromised HTTP proxy sitting between Desktop and the real remote — can simply respond with `WWW-Authenticate: Basic realm="GitHub"` to be classified as `'enterprise'`, i.e., a legitimate GitHub Enterprise Server.

That classification flows into `getCredential()`: [2](#0-1) 

which, when no account already exists for that endpoint, calls `ui.promptForGitHubSignIn(endpoint)` where `endpoint` is derived from the attacker's own remote URL (`getCredentialUrl(cred)`), not from any admin- or user-configured trust list: [3](#0-2) 

For a non-`github.com` hostname this calls `dispatcher.beginEnterpriseSignIn(cb)` followed by `dispatcher.setSignInEndpoint(origin)`, which maps to `SignInStore.setEndpoint()`. That method only validates URL *syntax* and *protocol* (must be `https:`), not host trustworthiness: [4](#0-3) 

If the user proceeds with "Sign in with your browser" from the resulting popup, `authenticateWithBrowser()` opens the OAuth authorize URL at the attacker's host: [5](#0-4) 

and once the (attacker-supplied) `code`/`state` come back through the deep-link handler, `resolveOAuthRequest()` calls `requestOAuthToken(endpoint, code)` where `endpoint` is still the attacker's host: [6](#0-5) 

`requestOAuthToken` then POSTs Desktop's static `ClientID` **and `ClientSecret`** to `https://<attacker-host>/login/oauth/access_token`: [7](#0-6) 

This is the corrupted trust value: an attacker-controlled HTTP response header (`WWW-Authenticate`) is used to promote an arbitrary host to "trusted GitHub Enterprise endpoint" status, bypassing the normal manual Enterprise-URL entry/trust step and causing the app's shared OAuth client secret to be sent to that host.

### Impact Explanation
The Desktop OAuth `client_secret` is a single, static, shared-across-all-users secret embedded in the application. Exfiltrating it lets an attacker impersonate the Desktop OAuth client for `login/oauth/access_token` exchanges elsewhere (a well-known category of impact for OAuth "confidential" client secrets baked into distributed desktop apps, which is why GitHub previously treated Desktop's client secret as effectively public — but this bug still constitutes unauthorized disclosure driven by a spoofed server response, and the same flow can be reused to phish the user through a convincing "Sign in to GitHub" dialog for a host the user never asked to trust). It also results in unauthorized binding of the sign-in flow to an endpoint the user did not choose, which corresponds to the "unauthorized OAuth or account binding" impact category.

### Likelihood Explanation
No local access, malware, or leaked credentials are required. The attacker only needs to control (or MITM-proxy) any git remote HTTPS endpoint the victim adds/fetches from — e.g., a malicious hosting service, a compromised internal proxy, or a spoofed corporate Git server — and have it answer authentication challenges with `WWW-Authenticate: realm="GitHub"`. This is a normal, unauthenticated HTTP response an attacker fully controls, matching the "attacker controls ... a git remote/proxy response" primitive in scope. The remaining step (user clicking "Sign in" in the resulting popup) is an expected, natural Desktop interaction (Desktop routinely prompts for credentials on failed git auth), not an unnatural step.

### Recommendation
Do not classify a remote as an `'enterprise'` (i.e., GitHub-trusted) endpoint based solely on an attacker-controlled `WWW-Authenticate` header value. At minimum:
- Require a positive server-side capability check (e.g., successful `isGitHubHost()` API probe) before trusting `wwwauth[...]` hints, rather than trusting the header as a happy-path shortcut for arbitrary hosts.
- Before initiating an Enterprise/OAuth sign-in flow originating from the credential helper, show the exact host being trusted and require explicit, unambiguous user confirmation (distinct from the generic "credential needed" prompt), and/or require the host to already be a previously verified GHE endpoint before short-circuiting via header hints.
- Avoid sending the shared `ClientSecret` to any endpoint that hasn't gone through the standard, fully-validated Enterprise-URL entry flow (`validateURL` + explicit user-entered host), since the credential-helper path bypasses that flow via `setSignInEndpoint(origin)`.

### Proof of Concept
1. Attacker stands up an HTTPS git server (or a MITM proxy in front of any HTTPS remote) at `https://git.attacker.example/victim/repo.git`.
2. Victim adds this as a remote in GitHub Desktop and performs a fetch/push; Git issues an HTTPS auth request.
3. The attacker's server responds with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
4. `getEndpointKind()` returns `'enterprise'` for `git.attacker.example` purely from that header [8](#0-7) .
5. `getCredential()` → `ui.promptForGitHubSignIn('https://git.attacker.example')` shows a "Sign in to GitHub Enterprise" popup bound to the attacker's host, calling `beginEnterpriseSignIn` + `setSignInEndpoint(origin)` without any manual trust step [9](#0-8) .
6. Victim clicks "Sign in with your browser"; Desktop opens `https://git.attacker.example/login/oauth/authorize?client_id=...&scope=...&state=...` [10](#0-9) .
7. Attacker's fake login page immediately redirects back to Desktop's `x-github-client://oauth?code=<attacker_code>&state=<state>` deep link.
8. `resolveOAuthRequest()` calls `requestOAuthToken('https://git.attacker.example', code)`, which POSTs `{client_id, client_secret, code}` to `https://git.attacker.example/login/oauth/access_token` [11](#0-10) , handing the attacker Desktop's OAuth `client_secret` and completing an OAuth flow the victim believed was for a legitimate corporate GitHub Enterprise instance.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined

export async function requestOAuthToken(
  endpoint: string,
  code: string
): Promise<string | null> {
  try {
    const urlBase = getHTMLURL(endpoint)
    const response = await request(
      urlBase,
      null,
      'POST',
      'login/oauth/access_token',
      {
        client_id: ClientID,
        client_secret: ClientSecret,
        code: code,
      }
    )
    tryUpdateEndpointVersionFromResponse(endpoint, response)

    const result = await parsedResponse<IAPIAccessToken>(response)
    return result.access_token
  } catch (e) {
    log.warn(`requestOAuthToken: failed with endpoint ${endpoint}`, e)
    return null
  }
}
