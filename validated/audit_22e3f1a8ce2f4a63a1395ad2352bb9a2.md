## Finding

### Title
Working-directory conflict resolution silently trusts `git diff --check`'s conflict-marker count, allowing a conflicted file to be committed with unresolved markers - (File: `app/src/lib/status.ts`)

### Summary
GitHub Desktop's conflict UI treats a conflicted file as "resolved" purely based on a derived counter (`conflictMarkerCount`) computed from parsing the stdout of `git diff --check`, rather than re-validating the file's actual content. This mirrors the LeXscrow pattern: a security-relevant decision ("is this deposit/file already satisfied/resolved?") is made against an ambient, indirectly-derived value that can diverge from the real state, rather than the authoritative value itself.

### Finding Description
When Desktop detects a merge/rebase/stash conflict, it calls `getFilesWithConflictMarkers()` [1](#0-0) , which runs `git diff --check` and regex-matches lines containing the literal string `leftover conflict marker` to build a `Map<path, count>` of marker counts per file. This count is attached to the file's status as `conflictMarkerCount` in `parseConflictedState` [2](#0-1) .

That derived count is then used as the sole gate for "is this file actually resolved": [3](#0-2) 

and again to decide whether to skip re-staging a manual resolution: [4](#0-3) 

The invariant being assumed is: *"if `git diff --check` reports 0 leftover-marker lines for this path, the file contains no conflict markers."* This is not guaranteed to be true in all cases, because `git diff --check` only flags marker-looking lines that appear as **added lines in the diff against the index/HEAD** for that invocation — it is a heuristic diff-based check, not a full-content scan of the working tree file. A conflicted file whose on-disk content still contains real `<<<<<<<`/`=======`/`>>>>>>>` markers can, depending on how those lines relate to the diff base being compared (e.g. content already present in a comparison base, encoding/formatting edge cases, or partial-hunk truncation), yield `conflictMarkerCount === 0` while the file is still genuinely unmerged. Notably, the codebase's own comment acknowledges git object-model edge cases around conflict detection ("We need to do these operations to detect conflicts that were the result of popping a stash into the index" [5](#0-4) ), which shows this exact family of surface is already known to be fragile.

Contrast this with the app's own conflict-hunk extractor used for the AI merge-resolution feature, which does *not* trust any external counter — it scans the raw file bytes directly for marker regexes: [6](#0-5) . The `hasUnresolvedConflicts`/`stageManualConflictResolution` path, by contrast, trusts the `git diff --check`-derived count instead of re-scanning file content, exactly analogous to LeXscrow trusting `address(this).balance` instead of tracking the expected deposit amount directly.

### Impact Explanation
If `conflictMarkerCount` is `0` for a file that is still genuinely conflicted:
- `hasUnresolvedConflicts()` returns `false`, so the UI/commit flow treats the file as resolved and will let it be committed as-is.
- `stageManualConflictResolution()` treats `conflictMarkerCount === 0` as "already resolved by the user" and returns early without staging the intended `ours`/`theirs` resolution — silently leaving whatever content is currently on disk (potentially still containing literal conflict markers, or content from the wrong side) staged for commit.

This is a silent corruption of what the user commits: the user believes they resolved (or Desktop believes it verified) the conflict, but the committed blob can contain unintended content (including raw conflict markers) without any warning dialog, because the only gate checked is a possibly-stale/derived counter rather than the file's real content.

### Likelihood Explanation
Exploitation does not require local/physical access or malware — it only requires an attacker-controlled repository/branch/remote whose history is structured to produce a merge/rebase/stash conflict where `git diff --check`'s line-added heuristic under-reports markers relative to the file's true content (this class of git diff heuristic mismatch is a known, git-version-dependent edge case, and the code already treats one such edge case, the stash-pop case, as special). This fits squarely in the requested threat model: "attacker controls a cloned/fetched repository ... result is ... silent corruption of what the user commits or pushes."

### Recommendation
Do not gate "is this conflict resolved" purely on the `git diff --check`-derived `conflictMarkerCount`. Instead, re-scan the actual working-tree file content for conflict-marker regexes (as already done in `extractConflictHunks`/`isConflictMarker` for the Copilot feature) before treating a conflicted file as resolved or skipping a manual resolution stage, and cross-check against the git index's unmerged/stage state rather than a derived line count.

### Proof of Concept
Because I could not execute git locally (index-search access only), I cannot provide a byte-exact `git diff --check` input that produces a 0-count mismatch. This part of the analysis is inferred from the code's own acknowledged edge cases (the stash-pop conflict comment) and the general limitation of diff-based line-added heuristics vs. full-content marker scans; a concrete reproduction (e.g., crafting a merge/stash scenario where `git diff --check` omits a marker line that is nonetheless present in the working tree) would need to be validated by a Devin session with terminal/git access to confirm the exact git version behavior that produces the divergence.

```typescript
export async function getFilesWithConflictMarkers(
  repositoryPath: string
): Promise<Map<string, number>> {
  const { stdout } = await git(
    ['diff', '--check'],
    repositoryPath,
    'getFilesWithConflictMarkers',
    { successExitCodes: new Set([0, 2]) }
  )

  const files = new Map<string, number>()
  const matches = stdout.matchAll(/^(.+):\d+: leftover conflict marker/gm)

  for (const [, path] of matches) {
    files.set(path, (files.get(path) ?? 0) + 1)
  }

  return files
```

```typescript
export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}
```
