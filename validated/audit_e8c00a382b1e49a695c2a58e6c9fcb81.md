### Title
Attacker-controlled participant count in `ThresholdKeys::read` triggers oversized `Vec::with_capacity` allocation before validation, enabling memory amplification DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` deserializes `t`, `n`, and `i` from attacker-supplied bytes, then immediately executes `Interpolation::Constant` deserialization which allocates `Vec::with_capacity(usize::from(n))` — before `ThresholdParams::new(t, n, i)` ever validates `n`. A ~15-byte prefix declaring `n = 0xFFFF` forces an allocation of 65,535 field elements (~2 MB for secp256k1 `Scalar`, ~3.7 MB for ed448 `F`) before a single scalar is read or validated. This mirrors the advisory's class: an untrusted length field drives buffering proportional to a declared size rather than to bytes actually present, with no size enforcement on the allocation path.

### Finding Description
In `ThresholdKeys::read`, the code reads `id_len`/`id`, then `t`, `n`, `i` as raw `u16`s via `read_u16` (crypto/dkg/src/lib.rs:591-602). It then reads a 1-byte interpolation tag; for tag `0` (`Interpolation::Constant`) it does `Vec::with_capacity(usize::from(n))` and loops `0 .. n` calling `C::read_F` (crypto/dkg/src/lib.rs:604-613). Only afterward does `ThresholdKeys::new(ThresholdParams::new(t, n, i)?, ...)` at lines 625-630 check `n` against `t`/protocol bounds — far too late, since the capacity allocation already happened. The same unvalidated `n` also drives the `verification_shares` loop at lines 620-623 (`for l in 1 ..= n` with `read_G` + `HashMap::insert`).

Unlike the `commitments` path in `Transaction::read` (coordinator), which multiplies declared lengths and checks them against `TRANSACTION_SIZE_LIMIT` before allocating (coordinator/src/tributary/transaction.rs:283-296), `ThresholdKeys::read` performs no `n * size_of::<F>` bound check prior to `with_capacity`. This path is reachable by an unprivileged party: serialized `ThresholdKeys` blobs are exchanged between participants, and `ThresholdKeys::read` is explicitly an untrusted-bytes entry point.

### Impact Explanation
Each maliciously crafted header of ~15 bytes forces a multi-megabyte heap allocation before the first `read_F` fails on missing bytes. The amplification factor exceeds 100,000× (15 bytes in → ~2–3.7 MB allocated). Because the allocation precedes validation, even a stream of truncated or erroring inputs forces allocation churn; concurrent submissions against any service deserializing `ThresholdKeys` (e.g., a coordinator/processor handling key material messages) can spike memory usage and cause OOM/denial of service. This is CWE-770 (allocation of resources without limits) — the same class as the referenced unbounded postponed-body buffering, mapped onto Serai's deserialization surface.

### Likelihood Explanation
Reachability requires only that an attacker get untrusted bytes into `ThresholdKeys::read`, which is a public API explicitly intended for reading serialized key material from peers. No valid signature, threshold cooperation, or protocol state is needed — the allocation fires before any cryptographic validation. The only mitigating factor is that the allocation is transient (freed when `read_F` errors), so sustained DoS requires repeated/concurrent submissions rather than a single message permanently pinning memory; this keeps it at Medium rather than higher.

### Recommendation
Validate `n` before using it: reorder `ThresholdKeys::read` so `ThresholdParams::new(t, n, i)` is constructed (rejecting `n == 0`, `n < t`, or `n` exceeding any sane maximum participant bound) before the interpolation and verification-shares deserialization. Additionally, avoid `Vec::with_capacity(n)` on untrusted input — push into `Vec::new()` and let capacity grow only as elements are actually read, matching the chunked-read approach used in `networks/ethereum/src/machine.rs:51-60`. The same fix bounds the `verification_shares` `HashMap` population loop.
