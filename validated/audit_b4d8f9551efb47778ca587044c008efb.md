### Title
Division by zero in `KIP71Config.NextMagmaBlockBaseFee` when `GasTarget` governance parameter is zero - (File: params/kip71_config.go)

### Summary
`KIP71Config.NextMagmaBlockBaseFee`, which computes the KIP-71/Magma dynamic base fee for every block after the Magma hardfork, divides by `kc.GasTarget` without any zero-guard, unlike the sibling `BaseFeeDenominator` parameter which is explicitly defended against a zero value.

### Finding Description
In [1](#0-0)  the code explicitly guards against `BaseFeeDenominator == 0` by substituting a default value of 64 to avoid a panic. However, `gasTarget := kc.GasTarget` at [2](#0-1)  has no equivalent guard.

Later, when the parent block's gas usage differs from `gasTarget`, the code performs: [3](#0-2) 
and, symmetrically, for the decreasing-baseFee branch: [4](#0-3) 

Both branches execute `x.Div(x, new(big.Int).SetUint64(gasTarget))`. If `GasTarget == 0`, then:
- The `parentGasUsed == gasTarget` branch is only taken when `parentGasUsed == 0` too.
- For any block with `parentGasUsed > 0`, execution falls into the `parentGasUsed > gasTarget` branch (since `parentGasUsed > 0` while `gasTarget == 0`), performing `x.Div(x, big.NewInt(0))`, which panics in Go's `big.Int.Div` (division by zero).

`GasTarget` is a governance-controlled parameter (`Kip71GasTarget` in `kaiax/gov/param.go`, exposed via `ParamSet.ToKip71Config()` in [5](#0-4) ). It is settable through the standard Kaia governance-vote mechanism (header-vote or contract-vote param governance), the same mechanism used for `BaseFeeDenominator`, `GasTarget`, `UpperBoundBaseFee`, etc. I was unable to fully verify (tool access ran out) whether `kaiax/gov/param.go`'s `FormatChecker` for `Kip71GasTarget` rejects a value of `0`; the analogous `Kip71BaseFeeDenominator` checker explicitly requires `v != 0`, and the code in `kip71_config.go` still independently defends against zero `BaseFeeDenominator` as defense-in-depth — but no such defense exists for `GasTarget`, which strongly suggests the governance-level format checker for `GasTarget` either permits zero or its correctness has not been mirrored by a corresponding safety check in the consuming function, unlike its sibling parameter.

### Impact Explanation
If a value of `0` for the `governance.kip71.gastarget` parameter (or the equivalent contract-governed value) can be admitted by governance (via a single governance-parameter-vote transaction reaching quorum, which is a standard on-chain transaction path, not an operator-only action), then every node computing the next block's base fee via `NextMagmaBlockBaseFee` — invoked during block header verification (`VerifyMagmaHeader`), block-making (`makeHeader`), and RPC fee estimation (`feehistory.go`, `gasprice.go`) — will panic with a division by zero as soon as any block has nonzero gas usage. This would crash consensus-critical code paths on every full node and validator simultaneously, halting the chain (a chain-wide denial of service caused by an on-chain governance value), which is a form of state-divergence/consensus-halt akin to "acceptance of an invalid transaction/block" causing chain failure, matching the required class of concrete, high-severity impact.

### Likelihood Explanation
Likelihood depends entirely on whether `GasTarget = 0` can pass the governance parameter's `FormatChecker`. This requires confirmation directly in `kaiax/gov/param.go` for the `Kip71GasTarget` entry, which I was unable to complete due to tool-call exhaustion in this session. Given the visible asymmetry — `BaseFeeDenominator` has both a format-checker guard (`v != 0`) documented as the pattern to follow, and a redundant runtime guard in the base-fee formula, while `GasTarget` has neither observed protection in the runtime formula — this is a plausible defense gap requiring code-level verification before treating it as fully confirmed.

### Recommendation
Add a zero-guard for `kc.GasTarget` in `NextMagmaBlockBaseFee`, mirroring the existing `BaseFeeDenominator` defense at [1](#0-0) , e.g. defaulting to a safe nonzero value (or the default `DefaultGasTarget`) when `kc.GasTarget == 0`. Additionally, verify and, if necessary, tighten the `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` to reject `0` at the governance-parameter-validation layer, consistent with `Kip71BaseFeeDenominator`.

### Proof of Concept
1. Via a governance parameter-vote transaction, set `governance.kip71.gastarget` (`Kip71GasTarget`) to `0` (assuming the format checker permits it — needs confirmation).
2. Once the vote takes effect at the next epoch/governance-effective block, any subsequent block with `GasUsed > 0` triggers `KIP71Config.NextMagmaBlockBaseFee` on every node (in header verification, block assembly, and gas-price RPC endpoints).
3. Inside `NextMagmaBlockBaseFee`, `parentGasUsed > gasTarget` (since `gasTarget == 0` and `parentGasUsed > 0`), leading to `x.Div(x, new(big.Int).SetUint64(0))`, i.e., `big.Int.Div(x, 0)`, which panics.
4. All nodes computing this value panic/crash simultaneously, halting the network.

Note: This PoC's premise (governance accepting `GasTarget = 0`) could not be fully confirmed with the available tool calls in this session; a Devin session with full repository access should verify the `Kip71GasTarget` `FormatChecker` in `kaiax/gov/param.go` before treating this as a confirmed, exploitable vulnerability.
