### Title
SchnorrAggregate verifier accepts an empty aggregate (zero `Rs`, `s = 0`) as a valid signature — vacuous-verification bypass analogous to the empty-secret auth bypass - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The external report describes an authorization check that returns `true` unconditionally when the configured secret is empty (`if (!this._opts.secret) return true`). The analog in Serai is `SchnorrAggregate::verify`, which returns `true` unconditionally when the aggregate contains zero signatures: the only length check is `Rs.len() != keys_and_challenges.len()`, so an attacker-supplied `SchnorrAggregate` with `Rs = []` and `s = 0` reduces the verification equation to `0 * G == identity`, which always passes.

### Finding Description
`SchnorrAggregate::read` deserializes a u32 count followed by that many points and one scalar; a count of `0` is accepted, yielding `SchnorrAggregate { Rs: [], s: <attacker scalar> }` from untrusted bytes (`crypto/schnorr/src/aggregate.rs:77-88`). In `verify` (`crypto/schnorr/src/aggregate.rs:127-146`):

```rust
if self.Rs.len() != keys_and_challenges.len() {
  return false;
}
// ... loop over keys_and_challenges pushes 2 pairs each ...
pairs.push((-self.s, C::generator()));
multiexp_vartime(&pairs).is_identity().into()
```

When `keys_and_challenges` is empty (consistent with `Rs` being empty), the loop appends nothing and `pairs` contains only `(-s, G)`. Choosing `s = 0` makes the multiexp the identity, so `verify` returns `true`. There is no `Rs.is_empty()` rejection anywhere — the signing-side API `SchnorrAggregator::complete` explicitly refuses to emit an empty aggregate (`return None` at `crypto/schnorr/src/aggregate.rs:176`), but the verification side performs no symmetric check, so a forged empty aggregate that could never be produced legitimately is accepted.

This is the same defect shape as the report: a guard that fails open when a security-relevant quantity is empty (empty secret → authorized; empty signer set → valid signature), combined with deserialization that allows the attacker to choose the empty case.

### Impact Explanation
Any verifier path that evaluates `SchnorrAggregate::verify(dst, keys_and_challenges)` where `keys_and_challenges` is derived from the same aggregate signature's `Rs` (or from an attacker-controlled / dynamically computed signer set that can be empty) accepts a completely forged signature: the attacker proves possession of no private key at all. An aggregate signature that "verifies" while binding to zero public keys authenticates nothing, yet returns `true` — an incorrect verifier edge case reachable purely through `SchnorrAggregate::read` on public bytes. Severity: Medium — the forgery is unconditional at the primitive level, but exploitation additionally requires a caller whose expected-key list can be empty (e.g., an empty signer set, an empty batch of challenges, or a list built from the signature itself).

### Likelihood Explanation
The forgery itself is trivial and deterministic: five bytes (`0x00000000` length prefix plus a zero scalar encoding) suffice. Whether a reachable call site supplies an empty `keys_and_challenges` depends on the integrator; the crate's own documentation only mandates a binding challenge, not a non-empty signer set, so the precondition is not enforced or documented. The asymmetry with `SchnorrAggregator::complete` (which rejects empty) shows the empty case was considered invalid on the proving side but overlooked on the verifying side.

### Recommendation
In `SchnorrAggregate::verify`, reject empty aggregates before the equality check:

```rust
if self.Rs.is_empty() || (self.Rs.len() != keys_and_challenges.len()) {
  return false;
}
```

Alternatively, reject a zero `Rs` count in `SchnorrAggregate::read` so an empty aggregate can never be constructed from untrusted input. Applying the check in `read` is stronger since it also protects any future consumers of the type.

### Proof of Concept
```rust
use zeroize::Zeroizing;
use ciphersuite::{group::ff::Field, Ciphersuite};
use ciphersuite_ed25519::Ed25519; // any PrimeGroup ciphersuite
use schnorr::aggregate::SchnorrAggregate;

// Attacker-controlled bytes: len = 0, s = 0
let mut bytes: &[u8] = &[0; 4 + 32];
let forged = SchnorrAggregate::<Ed25519>::read(&mut bytes).unwrap();
assert!(forged.Rs().is_empty());

// Any verifier whose expected signer list is empty accepts the forgery
assert!(forged.verify(b"any dst", &[]));
```

The multiexp over the single pair `(-0, G)` is the identity, so `verify` returns `true` despite no signature over any public key being present — the same fail-open-on-empty defect class as GHSA-j3vx-cx2r-pvg8.
