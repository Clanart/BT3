### Title
Server-Side Request Forgery (SSRF) via unauthenticated Data Layer mirror URLs - (File: `chia/data_layer/download_data.py`)

### Summary
Any wallet holder can publish arbitrary URLs on-chain as a Data Layer "mirror" for any singleton store via `DLNewMirror`/`create_new_mirror`. Any Data Layer node that subscribes to that store ingests these attacker-controlled URLs unvalidated and later issues an outbound HTTP GET to them (`http_download`) while syncing delta files, allowing an unprivileged spend-bundle/wallet action to force a victim node into making requests against internal/local network endpoints — the same bug class as the reported e107 "remote file fetcher" SSRF.

### Finding Description
`DataLayerWallet.create_new_mirror` lets any wallet with enough funds create a mirror coin that memoizes a `launcher_id` plus a list of caller-supplied `urls`, with no validation of scheme, host, or target (e.g. `127.0.0.1`, link-local/metadata addresses, or internal service ports) [1](#0-0) . This is exposed through the `dl_new_mirror` wallet RPC endpoint and the `add_mirror` Data Layer RPC/CLI command, both of which forward the URLs verbatim onto the chain [2](#0-1) [3](#0-2) .

Any other Data Layer client tracking the same store pulls these mirror URLs and merges them into its subscription/server list without any host/scheme allowlisting: `update_subscriptions_from_wallet` collects `mirror.urls` for the launcher and passes them straight to `data_store.update_subscriptions_from_wallet` [4](#0-3) .

When the victim node later syncs the store, `fetch_and_validate` picks a server from `get_available_servers_for_store` and calls `insert_from_delta_file` → `download_file` → `http_download`, which performs `aiohttp` `session.get(server_info.url + "/" + filename, ...)` directly against the attacker-supplied URL with no restriction on target host [5](#0-4) [6](#0-5) .

This is structurally identical to the e107 vulnerability: a user-supplied "fetch from URL" feature (there, the Media Manager remote-file field; here, a Data Layer mirror URL) is consumed by the server without validating that the target isn't an internal/loopback resource, causing the server to issue attacker-directed outbound requests.

### Impact Explanation
An attacker who creates a mirror pointing at `http://127.0.0.1:<port>/...` or other internal-only endpoints (e.g. a local RPC service, cloud metadata endpoint, or another internal host) can cause any peer that subscribes to and syncs the poisoned store to issue HTTP requests to those internal targets. Response content/behavior (e.g. HTTP status, timing, or body bytes written as a "delta file") can leak information about the victim's internal network or be used to probe for open internal services, and repeated forced downloads can be used to generate outbound traffic against arbitrary hosts under the victim's control. This is a confidentiality/network-boundary violation reachable purely through a normal wallet transaction (mirror coin creation), matching the CVSS 4.3 (C:L) classification of the reference CVE.

### Likelihood Explanation
Likelihood is moderate: creating a mirror only requires an unprivileged wallet with minimal funds (`amount`/`fee`), and the URLs are stored as free-form strings with no scheme/host validation anywhere in the mirror-creation, RPC, or download path. Exploitation additionally requires that a victim node subscribes to (tracks) the attacker's store and attempts to sync it, which is a normal Data Layer workflow for any store a user is interested in mirroring/reading.

### Recommendation
Validate and restrict mirror URLs before accepting them into the subscription/server list and before issuing outbound requests in `http_download`/`download_file`:
- Enforce an allowlist of schemes (e.g. `http`/`https` only, explicitly reject `file://`, etc.).
- Resolve the hostname and reject requests to loopback, link-local, private (RFC1918), and other reserved/internal address ranges (defense against DNS rebinding as well, e.g. by re-checking the resolved IP at connect time).
- Consider making outbound mirror-download requests opt-in/configurable (e.g. via an explicit allowlist of trusted mirror hosts) rather than automatically fetching from any URL published on-chain by third parties.

### Proof of Concept
1. Attacker creates a Data Layer store and publishes a mirror pointing at an internal address using the existing test pattern:
```python
await data_rpc_api.add_mirror({"id": store_id.hex(), "urls": ["http://127.0.0.1:<internal-port>/"], "amount": 1, "fee": 1})
```
(mirroring the exact call in the existing test) [7](#0-6) .
2. Victim runs `chia data subscribe`/tracks the attacker's `store_id`; `update_subscriptions_from_wallet` pulls in the malicious URL as an available server [4](#0-3) .
3. On the next sync cycle, `fetch_and_validate` selects the malicious server and `http_download` issues `session.get("http://127.0.0.1:<internal-port>/" + filename, ...)` from the victim's Data Layer process, hitting the internal service instead of a legitimate mirror [8](#0-7) .

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```
