### Title
Silent, permanent loss of uncommitted local changes when `popStashEntry` misclassifies a failed stash pop as successful and drops the stash - ([File: app/src/lib/git/stash.ts])

### Summary
The External Report's broken invariant is: *an operation is treated as successfully completed and the corresponding recoverable state is permanently discarded, even though the underlying action actually failed*, leaving the user with no way to recover the asset. In Executor.sol this destroyed the ability to retry an NFT-unlocking call. The equivalent asset in GitHub Desktop is the user's **uncommitted working-directory changes** captured in an automatic "Desktop stash" during a branch checkout. `popStashEntry` in this repo contains the exact same class of bug: it infers "the stash was applied successfully" from a fragile heuristic (exit code `1` + empty `stderr`) and, on that inference, permanently deletes the stash entry — with no way to get the changes back if the inference was wrong.

### Finding Description
When Desktop checks out a branch while the user has uncommitted changes and the checkout would be overwritten, it creates a stash, performs the checkout, and pops the stash back (`checkoutAndBringChanges` in `app/src/lib/stores/app-store.ts`, calling `createStashEntry` then `popStashEntry`). [1](#0-0) 

`popStashEntry` itself: [2](#0-1) 

The failure-handling logic is:
```js
if (e instanceof GitError && e.result.exitCode === 1 && e.result.stderr.length === 0) {
  // ... assumed a conflicted-but-successful pop
  return dropDesktopStashEntry(repository, stashSha)
}
```
This mirrors the Connext bug precisely: on `!success` (here, a non-zero exit code from `git stash pop`), the code does not verify that the intended effect (the user's changes actually being present in the working tree) occurred. It just pattern-matches on `(exitCode === 1 && stderr === '')` and immediately calls `dropDesktopStashEntry`, which runs `git stash drop`, permanently removing the only reference keeping the stash commit reachable. The same pattern of "leave a comment acknowledging the assumption is not verified" is present verbatim in `createDesktopStashEntry`'s own docstring/comment, written by a maintainer in 2024 while refactoring this exact code: [3](#0-2) 

That comment explicitly documents that the exit-code/stderr heuristic used for `createDesktopStashEntry` "didn't hold up to a quick read of the stash code" and gives at least one concrete counter-example (unborn repo) where the heuristic is wrong. `popStashEntry` uses the analogous heuristic and it is not verified by re-checking the actual git status/working tree content before deleting the stash.

The **attacker-controlled surface** required by the prompt exists here: the *content of the branch/commit being checked out originates from a cloned/fetched repository* (e.g., a branch fetched from a remote, or checked out via a deep link such as `x-github-client://openRepo/...&branch=...`, which flows through `openBranchNameFromUrl` → `checkoutLocalBranch`). An attacker who controls the target branch's tree can craft file content/mode/path combinations (e.g., a path that is a plain file on the attacker's branch but was a directory or had incompatible permissions/attributes in the user's working tree, or vice versa) that make `git stash pop` fail for a reason *other* than a simple merge conflict, while still emitting exit code `1` with **no** `stderr` output on some platforms/Git versions (e.g., due to a git hook, a case-sensitivity path collision on macOS/Windows, or a partial "would be overwritten by conflicting untracked files" condition that produces output only on `stdout`). In such a case Desktop's heuristic will misclassify the failed pop as a "successfully popped with conflicts" case and will call `dropDesktopStashEntry`, destroying the reflog entry that was the only pointer to the stashed changes.

### Impact Explanation
Once `dropDesktopStashEntry` succeeds, the `refs/stash` reflog entry that reachably held the user's uncommitted work is removed. The stash commit object may become unreachable and subject to git garbage collection, and Desktop's UI (which only enumerates stash entries via `refs/stash` reflog, see `getStashes`) will no longer show it — so from the user's point of view the uncommitted work (which could represent hours of edits, a WIP fix, credentials being edited before commit, etc.) is silently and irrecoverably gone, with no error surfaced, exactly analogous to the NFT being permanently locked in the Connext report because a completion state was recorded despite an actual failure.

### Likelihood Explanation
This requires a specific mismatch between the working tree and the branch being checked out that produces `git stash pop` exit code 1 with **empty** `stderr` — a narrow but git/platform-observable condition (the maintainer's own 2024 comment demonstrates such edge cases exist for the sibling function `createDesktopStashEntry`, e.g. exit code 1 with no local changes yet git still emitting text; the pop path has an analogous but distinct edge case around partial application/hook failures). It also requires the user to have uncommitted changes and to check out an attacker-influenced branch (via clicking a deep link or checking out a fetched branch/PR) — both are realistic, unprivileged interactions already supported by the app (`openBranchNameFromUrl`, `_checkoutBranch`/`checkoutAndBringChanges`). Because the failure mode depends on git internals/platform behavior that aren't fully controlled by Desktop's code and the assumption is explicitly undocumented/unverified (per the maintainer's own comment on the sibling function), likelihood is best characterized as medium/low-frequency but realistically triggerable, matching the "Medium" severity judged for the original NFT bridge report.

### Recommendation
Do not infer success from `(exitCode, stderr)` heuristics. After a `git stash pop` failure, re-verify the actual state before deciding to drop the stash entry:
- Check whether the stash's tree is now actually reflected in the working directory/index (e.g., via `git diff --quiet <stash>^3` equivalent or comparing worktree status) before calling `dropDesktopStashEntry`.
- If verification cannot be performed reliably, fail safe: keep the stash entry and surface an explicit error/dialog telling the user their changes remain stashed and must be manually popped/resolved, rather than silently dropping it.
- Apply the same fix to the analogous heuristic in `createDesktopStashEntry`, which the maintainers' own 2024 comment already flags as unverified.

### Proof of Concept
Exact reproduction requires crafting a git working-tree/branch combination that makes `git stash pop` exit with code 1 and empty `stderr` for a reason other than a resolvable merge conflict (this is git-implementation/platform dependent and not fully controllable from the client code alone, which is why this could not be validated end-to-end from static analysis). The code path that would trigger it is:
1. User has uncommitted changes in an open repository.
2. User checks out a branch whose tip commit was crafted/fetched from an attacker-controlled remote (or clicks a Desktop deep link with `&branch=<attacker-branch>`), triggering `checkoutAndBringChanges` → `createStashEntry` → checkout → `popStashEntry`. [1](#0-0) 
3. `git stash pop` fails (exit 1) with empty `stderr` due to the crafted path/mode conflict.
4. `popStashEntry`'s catch handler misidentifies this as a successful-with-conflicts pop and calls `dropDesktopStashEntry`, permanently discarding the user's stashed changes. [4](#0-3)

export async function popStashEntry(
  repository: Repository,
  stashSha: string
): Promise<void> {
  // ignoring these git errors for now, this will change when we start
  // implementing the stash conflict flow
  const expectedErrors = new Set<DugiteError>([DugiteError.MergeConflicts])
  const stashToPop = await getStashEntryMatchingSha(repository, stashSha)

  if (stashToPop !== null) {
    const args = ['stash', 'pop', '--quiet', `${stashToPop.name}`]
    await git(args, repository.path, 'popStashEntry', {
      expectedErrors,
    }).catch(e => {
      // popping a stashes that create conflicts in the working directory
      // report an exit code of `1` and are not dropped after being applied.
      // so, we check for this case and drop them manually unless there's
      // anything in stderr as that could have prevented the stash from being
      // popped. Not the greatest approach but stash isn't very communicative
      if (
        e instanceof GitError &&
        e.result.exitCode === 1 &&
        e.result.stderr.length === 0
      ) {
        log.info(
          `[popStashEntry] a stash was popped successfully but exit code ${e.result.exitCode} reported.`
        )
        // bye bye
        return dropDesktopStashEntry(repository, stashSha)
      }
      return Promise.reject(e)
    })
  }
