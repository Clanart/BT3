This mirrors the Juicebox bug class exactly: a required guard/pass-through was omitted, letting a state transition proceed on stale/wrong assumptions and finalizing an incorrect outcome that costs the rightful party funds — no malicious relayer, prover, or admin needed, just an unprivileged caller and ordinary out-of-order message delivery.

### Title
Missing `_filled[commitment]` check in `_cancelFromDest` allows a duplicate `RefundEscrow` dispatch after an order is already filled, causing solver fund loss - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`_cancelFromDest` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:240-267`) is reachable by *anyone* once `order.deadline` has passed, and it unconditionally overwrites `_filled[commitment]` and dispatches a `RefundEscrow` message to the source chain — without ever checking whether the order was already finalized by `_fillCrossChain` (`ExtrinsicIntents.sol:89-171`). A solver who fills the order just before the deadline (setting `_filled[commitment] = solver` and dispatching a `RedeemEscrow` message) can be pre-empted: if the later `RefundEscrow` message reaches the source chain first (a purely ordering/timing issue in ISMP message delivery — not requiring a malicious relayer), the source-side `_withdraw` (`IntentsBase.sol:390-425`) releases the full escrow to the user. The still-outstanding legitimate `RedeemEscrow` then reverts with `UnknownOrder()` because `_orders[commitment][token]` has already been zeroed, permanently denying the solver the input tokens they already paid the beneficiary for on the destination chain.

### Finding Description
- `_cancelFromDest` only authorization-checks the caller before the deadline; after the deadline, "anyone" can call it (`ExtrinsicIntents.sol:241-243`).
- It sets `_filled[commitment] = order.user` and dispatches `RefundEscrow` (`ExtrinsicIntents.sol:245-259`) with **no check** that `_filled[commitment]` is already non-zero (i.e., already filled by a solver via `_fillCrossChain`, `ExtrinsicIntents.sol:92`).
- On the source chain, `onAccept` processes `RedeemEscrow`/`RefundEscrow` identically via `_withdraw` (`ExtrinsicIntents.sol:289-295`), and `_withdraw` itself has no `_filled[commitment]` guard either — it only reverts if the *token escrow balance* is already zero (`IntentsBase.sol:400-401`).
- Consequently, whichever message (`RedeemEscrow` from the solver's fill, or the later `RefundEscrow` from the deadline-triggered cancel) arrives at the source chain **first** wins the escrow; the second one reverts on `UnknownOrder()`.
- Because ISMP message delivery/proof timing is not synchronized with local block numbers on each chain, a fill that completes just before `order.deadline` and a cancel that fires just after it can easily race, with the cancel's proof landing first.

### Impact Explanation
This causes real loss of solver funds: the solver has already delivered output tokens to the beneficiary on the destination chain (per `_fillCrossChain`), but if the `RefundEscrow` message wins the race, the solver's committed input-token repayment gets redirected to the user instead, and the solver's rightful `RedeemEscrow` claim is permanently blocked (revert on delivery, and ISMP does not silently retry an already-processed distinct message). This is unauthorized reallocation of escrowed funds to the wrong beneficiary — a direct fund-loss/wrong-beneficiary outcome under the Hyperbridge bounty scope, triggered by an ordinary unprivileged actor calling a public entrypoint (`cancelOrder`) with no privileged role, malicious relayer, or governance action required.

### Likelihood Explanation
Likelihood is realistic: `_cancelFromDest` is callable by any address after deadline (`ExtrinsicIntents.sol:241`), and the race window is inherent whenever a solver fills close to the deadline while relayers deliver the resulting `RedeemEscrow`/`RefundEscrow` messages to the source chain at different, uncoordinated times. No cooperation from a relayer, prover, or Hyperbridge operator is needed — only that two independently-triggered, legitimately-authenticated messages for the same commitment arrive out of order, which is a normal operational possibility rather than an attack on the messaging layer itself.

### Recommendation
Add an explicit `if (_filled[commitment] != address(0)) revert Filled();` guard in `_cancelFromDest` before overwriting `_filled[commitment]` and dispatching `RefundEscrow` (mirroring the check already required on the source side of `_withdraw`, and consistent with the `Filled()` error already defined in `IntentsBase.sol:191`). Additionally, add a defense-in-depth check inside `_withdraw`/`onAccept` on the source chain to reject a `RefundEscrow`/`RedeemEscrow` for a commitment whose escrow has already been finalized by the *other* kind, rather than relying solely on the per-token escrow-balance underflow to implicitly prevent double settlement.

### Proof of Concept
1. User places a cross-chain order with `deadline = D` on the source chain, escrowing input tokens.
2. At block `D-1`, solver calls `fillOrder` on the destination chain → `_fillCrossChain` sets `_filled[commitment] = solver` and dispatches `RedeemEscrow` (source: destination chain, target: source chain gateway).
3. At block `D+1`, any address (attacker or bystander) calls `cancelOrder` on the destination chain → `_cancelFromDest` passes the deadline check (`order.deadline >= _blockNumber()` is now false, so no authorization needed), sets `_filled[commitment] = order.user` (overwriting the solver's fill locally), and dispatches `RefundEscrow` to the source chain.
4. Both `RedeemEscrow` and `RefundEscrow` ISMP messages are independently relayed and proven on the source chain; whichever is delivered/proven first is processed by `onAccept` → `_withdraw`, which sends the full escrowed input tokens to that message's beneficiary and zeroes `_orders[commitment][token]`.
5. If `RefundEscrow` lands first: the user receives back the input tokens (as if never filled) even though the solver already paid the user the output tokens on the destination chain; the subsequent `RedeemEscrow` delivery reverts with `UnknownOrder()`, permanently denying the solver's rightful repayment.     function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            uint256 dust = solverAmount - totalRequired;
            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;

            if (dust > 0) {
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            }

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        address hostAddr = host();
        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RedeemEscrow)),
            abi.encode(
                WithdrawalRequest({
                    commitment: commitment, tokens: order.inputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
                })
            )
        );
        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        if (options.nativeDispatchFee > 0 && msgValue >= options.nativeDispatchFee) {
            IDispatcher(hostAddr).dispatch{value: options.nativeDispatchFee}(request);
            msgValue -= options.nativeDispatchFee;
        } else {
            dispatchWithFeeToken(request);
        }

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            (bool sent,) = msg.sender.call{value: msgValue}("");
            if (!sent) revert InsufficientNativeToken();
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
