### Title

Secret key shares and tweak scalars leaked via `Debug` formatting of `ThresholdKeys` / `ThresholdView` — missing redaction of sensitive fields - (File: crypto/dkg/src/lib.rs)

### Summary

CVE-2021-3447 describes Ansible modules logging credential-bearing parameters in plaintext because they were not protected by the `no_log` feature. The Rust/Serai analogue of `no_log` is a redacted `fmt::Debug` implementation, and the codebase uses this pattern deliberately everywhere secrets live (`SecretShare`'s `Debug` prints nothing; `Encryption`'s `Debug` omits `enc_key`; `SecretShareMachine`/`KeyMachine` omit `coefficients`/`secret`). However, `ThresholdKeys::core` (`ThresholdCore`) and `ThresholdView` print fields that contain secret key material — the `Interpolation::Constant` coefficient vector (which *is* the set of secret shares when `t == n`) and the `scalar`/`offset` tweak values — so any `{:?}`/`Debug`-format logging of these types writes secret shares to logs in plaintext.

### Finding Description

`ThresholdCore` holds `secret_share: Zeroizing<C::F>` and `interpolation: Interpolation<C::F>` [1](#0-0) . Its manual `Debug` impl correctly omits `secret_share` via `finish_non_exhaustive`, but prints `interpolation` verbatim [2](#0-1) . `Interpolation` derives `Debug`, and `Interpolation::Constant(Vec<F>)` is documented as "A list of constant coefficients, one for each of the secret key shares" [3](#0-2)  — i.e., for `t == n` key sets these coefficients are the secret shares themselves.

`ThresholdKeys` derives `Debug` [4](#0-3) , so formatting it prints `core` (through `Arc`/`Zeroizing`, which forward `Debug` transparently) including the secret `interpolation` constants, plus the `scalar` and `offset` fields — the ephemeral tweak scalars explicitly documented as secret-but-not-serialized ("This scalar is ephemeral and will not be included when these keys are serialized") [5](#0-4) . `ThresholdView` likewise prints `interpolation`, `scalar`, and `offset` [6](#0-5) , while correctly omitting `secret_share`.

Contrast with the deliberate redaction discipline elsewhere: `SecretShare`'s `Debug` prints an empty struct [7](#0-6)  and `Encryption`'s `Debug` omits the private `enc_key` [8](#0-7) . The `interpolation`/`scalar`/`offset` fields were simply not given the same treatment.

### Impact Explanation

Anyone able to read a node's logs (the exact attacker model in the CVE: "an attacker can take advantage of this information… provided they have access to the log files") who finds a `{:?}`-formatted `ThresholdKeys`/`ThresholdView`/`ThresholdCore` for a `t == n` `Interpolation::Constant` key set recovers every participant's secret share directly, yielding the full threshold secret key — total key compromise enabling arbitrary signature forgery and theft of all funds controlled by the multisig. For `Interpolation::Lagrange` keys the leak is narrower but still real: `scalar`/`offset` are secret tweak scalars whose disclosure reveals derived-key relationships and, combined with the offset's effect on the effective secret share (`offset` is added into `included[0]`'s share in `ThresholdView`), weakens the privacy/account-derivation scheme these values exist to protect.

### Likelihood Explanation

Requires (a) an integrator logging these types via `{:?}`/`{:#?}` or error paths that embed them — plausible since `Debug` is provided precisely to enable such logging and `ThresholdKeys` is the primary handle integrators hold — and (b) an attacker with read access to log output on the managed node, matching the CVE's `AV:L` model. No cryptographic attack, collusion, or protocol manipulation is needed; the secrets appear verbatim in the output. Notably, `KeyGen` in the processor derives `Debug` over `entropy: Zeroizing<[u8; 32]>` [9](#0-8)  — `Zeroizing` forwards `Debug`, so the same pattern leaks the key-generation seed there too.

### Recommendation

- Change `ThresholdCore`'s `Debug` to omit `interpolation` (or print only its discriminant), matching how `secret_share` is already omitted. [2](#0-1) 
- Implement manual `Debug` for `Interpolation` that prints `Constant(..)`/`Lagrange` without the coefficient bytes [3](#0-2) .
- Replace the derived `Debug` on `ThresholdKeys` with a manual impl that prints `core` (redacted) but not `scalar`/`offset`, or prints them as `..`. [4](#0-3) 
- Remove `scalar`, `offset`, and `interpolation` from `ThresholdView`'s `Debug`. [6](#0-5) 
- Consider a `redactable`/`Sensitive` marker or `zeroize`-style "redacted" wrapper for all secret scalar fields so future structs can't accidentally derive over them; audit `processor/src/key_gen.rs`'s derived `Debug` over `entropy` similarly.

### Proof of Concept

Conceptual (Rust, against `crypto/dkg`):

```rust
// After a PedPoP/Constant-interpolation DKG or manual ThresholdKeys::new:
let keys: ThresholdKeys<C> = ThresholdKeys::new(
  params,                                // t == n
  Interpolation::Constant(vec![share1, share2, share3]), // secret shares
  secret_share,
  verification_shares,
).unwrap();

// Any integrator log line like this writes every secret share in plaintext:
log::debug!("loaded keys: {:?}", keys);   // or format!("{keys:?}") / anyhow context

// Output contains:
//   ThresholdKeys { core: ThresholdCore { ..., interpolation: Constant(
//     [0x<share1>, 0x<share2>, 0x<share3>] ), ... }, scalar: ..., offset: ... }
//
// A party with read access to the log file reconstructs the full
// threshold secret from the printed coefficients — no signing oracle,
// no collusion, no cryptographic attack required.
```

The same applies to `keys.view(included)` → `format!("{view:?}")`, which prints `interpolation`, `scalar`, and `offset` [6](#0-5) .

pub enum Interpolation<F: Zeroize + PrimeField> {
  /// A list of constant coefficients, one for each of the secret key shares.

    There's no benefit to using a full linear combination here, as the additive term would have

  /// Lagrange interpolation.
  Lagrange,
}
