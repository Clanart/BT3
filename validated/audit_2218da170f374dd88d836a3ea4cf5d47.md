## Finding: Excess native-token overpayment in `EvmHost.dispatch()`/`fundRequest()` is never refunded to the caller

### Title
Silent loss of overpaid native token when funding requests via `swapETHForExactTokens` — ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept `msg.value` and forward the entire amount into `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)` to buy an exact amount of fee tokens. Uniswap V2's `swapETHForExactTokens` only consumes the ETH actually required for the exact-output swap and refunds any leftover ETH to `msg.sender` of that call — which is `EvmHost` itself, not the original user. `EvmHost` has no logic afterward to forward that refunded ETH back to the caller, so any ETH sent in excess of the true swap cost is silently retained by the host contract and permanently lost to the payer.

### Finding Description
In `evm/src/core/EvmHost.sol`: [1](#0-0) 

and identically for `DispatchGet`: [2](#0-1) 

and `fundRequest`: [3](#0-2) 

In each case, `msg.value` is passed wholesale as the `value` for `swapETHForExactTokens(exactOut, path, address(this), deadline)`. The Uniswap V2 Router semantics for this call are: it computes the amount of ETH actually required for `exactOut` tokens, uses only that amount, and refunds the remainder to `msg.sender` — the caller of the router, which here is the `EvmHost` contract, not the end user (`_msgSender()`/`post.payer`). The `dispatch`/`fundRequest` functions do not track a balance-before/after delta and do not forward any leftover ETH back to the caller. There is no corresponding refund transfer visible after any of these three call sites.

This is directly analogous to the referenced report: `sellBasePreview`'s returned value was consumed without validating that the actual/expected amount matches what the user is owed, causing value to leak silently. Here, the "expected" value is "any ETH beyond the exact swap cost belongs to the caller," and the code never validates or returns that residual — it is unconditionally absorbed by the contract with no accounting, exactly the "leak of value" pattern from the seed report, but manifesting as a stuck/lost native-token balance rather than a bad slippage check.

### Impact Explanation
Any user who calls `dispatch()` (POST or GET) or `fundRequest()` with `msg.value` greater than the exact ETH cost of the underlying Uniswap V2 swap for `post.fee`/`amount` feeTokens loses the difference permanently — it becomes ETH sitting in the `EvmHost` contract, not credited to anyone's fee metadata, not withdrawable by the user. Given price volatility on the swap path (WETH→feeToken) between the moment the user constructs the transaction (using an off-chain price/estimate) and the block it executes in, overpayment margins are common and expected — the docs even instruct callers to add a buffer, e.g. `sdk/packages/sdk/src/protocols/hyperFungibleToken.ts` deliberately adds a 1% buffer before calling `quote`: [4](#0-3) 
That buffer, plus any general slippage margin any integrator adds, is exactly the amount that gets stranded in the host contract on every dispatch call that pays with native token. This is unauthorized loss of user funds through a normal, unprivileged, public entry point (`dispatch`, `fundRequest`) — no malicious relayer, prover, or admin required.

### Likelihood Explanation
High. `dispatch()` with native payment and `fundRequest()` with native payment are ordinary, frequently used, public entry points for any Hyperbridge app or end user paying in ETH instead of the fee token. Any overestimate of the native cost (which is unavoidable off-chain, since prices move between quote and execution, and the SDK itself pads by an explicit buffer) triggers the loss on every single call. No attacker action or special conditions are needed — the loss is a byproduct of normal usage.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, measure the ETH actually consumed (e.g., via `address(this).balance` delta or by reading the router's returned `amounts[0]`) and refund any leftover native token back to `_msgSender()` (or `post.payer`), mirroring the refund pattern already used elsewhere in the repo (e.g., `UniV4UniswapV2Wrapper.swapETHForExactTokens` correctly refunds leftover ETH to `msg.sender`, see `evm/src/utils/uniswapv2/UniV4UniswapV2Wrapper.sol:83-96`). Add a regression test asserting that the caller's ETH balance is restored to `balanceBefore - actualSwapCost` after a dispatch call with deliberately overpaid `msg.value`.

### Proof of Concept
1. Deploy/fork `EvmHost` with a configured `uniswapV2` router and `feeToken`.
2. Determine the exact ETH cost `C` to buy `post.fee` feeTokens via `router.getAmountsIn(post.fee, [WETH, feeToken])[0]`.
3. Call `host.dispatch{value: C * 2}(DispatchPost{...})` from an EOA with 0 other pending approvals/balance dependencies.
4. Observe: `router.swapETHForExactTokens` only spends `C` ETH and refunds `C` ETH — but that refund lands on `address(host)`, increasing `host`'s ETH balance by `C`, while the caller's ETH balance decreases by `2C`, not `C`.
5. Assert `address(host).balance` increased by the leftover `C`, and no function exists to return that value to the original caller — it is stuck in the contract permanently (no `withdraw` path was found calling this out for user-owed refunds in the reviewed sections).
