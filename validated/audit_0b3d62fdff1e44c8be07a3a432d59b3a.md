### Title
ThresholdKeys deserialization accepts identity verification shares, enabling forged signature shares - (File: crypto/dkg/src/lib.rs)

### Summary
The ChurchCRM bug is a **sanitizer substitution**: a function that performed two protections (HTML stripping *and* SQL escaping) was replaced by one that kept only the first, silently dropping the second while callers still relied on it. Serai has the same shape: `Curve::read_G` is the strengthened reader that rejects identity points on top of canonicality, while `Ciphersuite::read_G` only enforces canonical encoding. `ThresholdKeys::read` deserializes attacker-influenced `verification_shares` through the weaker `Ciphersuite::read_G`, so an identity point — which the DKG and FROST preprocessing both exclude elsewhere — is accepted into the threshold key material.

### Finding Description
- `Curve::read_G` wraps `Ciphersuite::read_G` and adds an explicit identity rejection — this is the "stronger sanitizer". [1](#0-0) 
- FROST's own untrusted-input path (`Commitments::read` → `NonceCommitments::read` → `GeneratorCommitments::read`) correctly uses `<C as Curve>::read_G`, rejecting identity nonce commitments. [2](#0-1) 
- `ThresholdKeys::read`, however, loads `verification_shares` for all `n` participants via `<C as Ciphersuite>::read_G`, which performs only canonicality checks (`from_bytes` + re-encode equality) and explicitly does *not* reject the identity point. [3](#0-2) [4](#0-3) 
- `ThresholdKeys::new` then builds the `group_key` from those verification shares (participants `1..=t`) and `ThresholdView`/share verification uses them directly — an identity share means participant `j`'s share equation `s_j·G == R_j + c·A_j` degenerates to `s_j·G == R_j`, removing `c·s_j-secret` entirely.

### Impact Explanation
Whoever can feed a serialized `ThresholdKeys` blob (an in-scope reachable reader) installs a verification share of identity for a target participant index `j`. Two consequences:
1. **Share forgery**: signature-share verification is `SchnorrSignature { R: bound_nonce_j, s: share }.verify(A_j, c)`. With `A_j = identity`, any party controlling `j`'s preprocess commitments (picking hiding nonce `d_j` and `E_j`, bound via rho) produces a valid share as `s_j = d_j + rho_j·e_j` with no secret share — a forged share attributed to an honest participant.
2. **Weakened group key**: the group key reconstructed from shares `1..=t` contains no contribution from `j`, so the resulting threshold key is weaker than `t`-of-`n` policy claims — effective threshold drops, approaching rogue-key territory depending on how many identity shares are injected.

### Likelihood Explanation
Reachable whenever `ThresholdKeys::read` consumes bytes not generated by the honest DKG — key provisioning, key-file restore, or cross-device import paths. The protocol defenses elsewhere (PedPoP proof-of-knowledge on commitments, `Curve::read_G` identity rejection in preprocesses) show identity points are recognized as malicious; the deserialization path simply lost that check, exactly paralleling the lost SQL escaping. Requires delivering a malicious key blob rather than live protocol messages, so Medium rather than Critical.

### Recommendation
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs` ~line 622), read verification shares with `<C as Curve>::read_G` — or equivalently reject `is_identity()` after `Ciphersuite::read_G` — so deserialization enforces the same invariant as the DKG and preprocess readers. Optionally also validate inside `ThresholdKeys::new` that no `verification_shares` value is identity, defense-in-depth for non-`read` constructors.

### Proof of Concept
1. Build a valid serialized `ThresholdKeys` for ciphersuite `C` (correct `C::ID` length-prefixed, `t`, `n`, valid `i`, interpolation tag `0`/`1`, a canonical `secret_share`).
2. For the `n` verification shares, write the canonical identity encoding for slot `j` (e.g., all-zero 32 bytes for Ristretto255, `0x00…01` encoding per `GroupEncoding`) and valid non-identity points elsewhere.
3. `ThresholdKeys::read` succeeds — `Ciphersuite::read_G` accepts identity since it round-trips canonically — producing `ThresholdKeys` with `A_j = 0`.
4. In signing, supply a preprocess for `j` with commitments `(D_j, E_j)` of your choosing; emit share `s_j = d_j + rho_j·e_j`. `verify_share` computes `s_j·G - (D_j + rho_j·E_j) - c·A_j = 0` and accepts, completing a signature in which participant `j` contributed nothing and knew no secret share.

  #[cfg(any(feature = "alloc", feature = "std"))]
  #[allow(non_snake_case)]
  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
    reader.read_exact(encoding.as_mut())?;

    let point = Option::<Self::G>::from(Self::G::from_bytes(&encoding))
      .ok_or_else(|| io::Error::other("invalid point"))?;
    if point.to_bytes().as_ref() != encoding.as_ref() {
      Err(io::Error::other("non-canonical point"))?;
    }
    Ok(point)
  }
