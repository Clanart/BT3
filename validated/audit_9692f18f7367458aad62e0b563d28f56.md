### Title
`safeTransferFrom()` on `CW721ERC721Pointer` always reverts because the pointer never populates OpenZeppelin's internal ownership storage - (File: contracts/src/CW721ERC721Pointer.sol)

### Summary
`CW721ERC721Pointer` is an EVM-side ERC721 wrapper that proxies CW721 CosmWasm NFT contracts to EVM users via the wasmd precompile. It inherits OpenZeppelin's `ERC721` and only overrides `transferFrom`, `approve`, `setApprovalForAll`, `ownerOf`, `balanceOf`, `getApproved`, and `isApprovedForAll` to redirect state reads/writes to the underlying CW721 contract. It never overrides `safeTransferFrom`, `_transfer`/`_update`, or mints any token into OpenZeppelin's own internal storage (`_owners`/`_balances`). As a result, any call to either `safeTransferFrom` variant is unconditionally broken for every token.

### Finding Description
`CW721ERC721Pointer` overrides the *public* view functions `ownerOf`, `balanceOf`, `getApproved`, and `isApprovedForAll` to query the real CW721 contract state through the wasmd precompile [1](#0-0) , and overrides `transferFrom` to execute a `transfer_nft` CosmWasm message against the real contract [2](#0-1) .

However, `safeTransferFrom` is not overridden at all, so it falls back to OpenZeppelin's base `ERC721.safeTransferFrom`/`_safeTransfer` implementation, which operates on OpenZeppelin's own internal storage mappings (`_owners`, `_balances`, `_tokenApprovals`) rather than the CW721 contract's state. Because `CW721ERC721Pointer` never calls `_mint` for any token (ownership is always represented externally in the CW721 contract, not locally), these internal mappings remain empty for every token ID. OpenZeppelin's authorization check inside `_safeTransfer`/`_isApprovedOrOwner` reads the owner via the base (non-virtual-dispatched) `ERC721.ownerOf`/`_ownerOf`, which reverts (or resolves to the zero address) because the token was never "minted" in the base contract's storage. Consequently, `safeTransferFrom(address,address,uint256)` and `safeTransferFrom(address,address,uint256,bytes)` unconditionally revert for every token, regardless of the token's real ownership on the CW721 side, since the pointer's storage-shadow was never synchronized with the real contract.

This is analogous to the referenced report in that both bugs stem from an incomplete/incorrect implementation of the ERC721 `safeTransferFrom` family relative to the actual token state and the EIP-721 contract that is supposed to be represented — but here, instead of merely failing to forward the `bytes data` parameter to `onERC721Received`, the entire `safeTransferFrom` code path is non-functional because it operates on stale/never-populated internal storage instead of the real (precompile-backed) CW721 ownership records.

### Impact Explanation
Any EVM user, contract, or marketplace holding a CW721-backed pointer NFT that relies on the ERC721-standard `safeTransferFrom` (rather than `transferFrom`) — which is common practice for many marketplaces and receiver contracts that require the receiver-callback safety check — will find these NFTs untransferable through that interface. This breaks composability and standard compliance of `CW721ERC721Pointer`, effectively locking pointer-wrapped CW721 NFTs out of any protocol/integration that exclusively uses `safeTransferFrom`, even though the token itself is not lost (the overridden `transferFrom` still functions correctly against the real CW721 contract).

### Likelihood Explanation
This is deterministically triggered by any unprivileged EVM user calling either `safeTransferFrom` variant on a `CW721ERC721Pointer` contract, with no special preconditions, since the internal OpenZeppelin storage is guaranteed to be empty for all tokens (no `_mint` is ever invoked).

### Recommendation
Override `safeTransferFrom` (both variants) in `CW721ERC721Pointer` — analogous to how `transferFrom` is overridden — so that they execute the `transfer_nft` CosmWasm message via the wasmd precompile (consistent with `transferFrom`), then perform the ERC721 receiver callback (`onERC721Received`) manually, forwarding the caller-supplied `bytes data` to the recipient, instead of relying on OpenZeppelin's base storage-dependent `_safeTransfer`/`_update` logic.

### Proof of Concept
1. Deploy a `CW721ERC721Pointer` wrapping an existing CW721 collection where a token with `tokenId = 1` is legitimately owned by address `A` (verifiable via the pointer's overridden `ownerOf(1)`).
2. From `A`, call `pointer.safeTransferFrom(A, B, 1)` or `pointer.safeTransferFrom(A, B, 1, data)`.
3. The call reverts (e.g., with OpenZeppelin's `ERC721NonexistentToken`/`ERC721: invalid token ID`-style error) because the base contract's internal `_owners[1]` was never set via `_mint`, even though `ownerOf(1)` (the overridden version) correctly reports `A` as owner.
4. Calling `pointer.transferFrom(A, B, 1)` instead succeeds, confirming the discrepancy is isolated to the unoverridden `safeTransferFrom` path. [3](#0-2) [2](#0-1)

    function ownerOf(uint256 tokenId) public view override returns (address) {
        string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(tokenId)));
        string memory req = _curlyBrace(_formatPayload("owner_of", _curlyBrace(tId)));
        bytes memory response = WasmdPrecompile.query(Cw721Address, bytes(req));
        bytes memory owner_ = JsonPrecompile.extractAsBytes(response, "owner");
        return AddrPrecompile.getEvmAddr(string(owner_));
    }

    function getApproved(uint256 tokenId) public view override returns (address) {
        string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(tokenId)));
        string memory req = _curlyBrace(_formatPayload("approvals", _curlyBrace(tId)));
        bytes memory response = WasmdPrecompile.query(Cw721Address, bytes(req));
        bytes[] memory approvals = JsonPrecompile.extractAsBytesList(response, "approvals");
        if (approvals.length > 0) {
            bytes memory res = JsonPrecompile.extractAsBytes(approvals[0], "spender");
            return AddrPrecompile.getEvmAddr(string(res));
        }
        return address(0);
    }
