### Title
Check-then-act race in `SignInStore.resolveOAuthRequest` allows a duplicate/racing `x-github-client://oauth` deep link to hijack the in-flight sign-in session - (File: `app/src/lib/stores/sign-in-store.ts`)

### Summary
`SignInStore.resolveOAuthRequest`, the handler invoked when the OS-registered `x-github-client://oauth` protocol callback is triggered, validates the pending sign-in session's CSRF `state` *before* performing two awaited external network calls (`requestOAuthToken`, `fetchUser`), and only re-reads `this.state.oauthState` *after* those awaits resolve to invoke `onAuthCompleted`/`onAuthError` [1](#0-0) . This mirrors the report's core flaw: state that determines who "wins" the operation is finalized only after an external, attacker-influenceable interaction has already begun, rather than being locked/validated atomically around it.

### Finding Description
The deep link is parsed unauthenticated by `parseAppURL`, which extracts `code` and `state` directly from the URL query string with no further validation beyond presence [2](#0-1) , and is routed through `handleAppURL` in the main process to the renderer/dispatcher, ultimately calling `resolveOAuthRequest` [3](#0-2) .

Inside `resolveOAuthRequest`:
```ts
public async resolveOAuthRequest(action: IOAuthAction) {
  if (!this.state || this.state.kind !== SignInStep.Authentication) return
  if (!this.state.oauthState) return
  if (this.state.oauthState.state !== action.state) { ... return }

  const { endpoint } = this.state
  const token = await requestOAuthToken(endpoint, action.code)   // external call #1

  if (token) {
    const account = await fetchUser(endpoint, token)             // external call #2
    this.state.oauthState.onAuthCompleted(account)                // state re-read AFTER awaits
  } else {
    this.state.oauthState.onAuthError(new Error(...))
  }
}
``` [1](#0-0) 

The `state !== action.state` guard is only checked once, prior to the two `await`s. After the awaits resolve, the code re-reads the *live* `this.state.oauthState` rather than a snapshot taken at guard time, and never re-checks that the `state` token still matches `action.state` or that this is still the same sign-in session. Meanwhile, `authenticateWithBrowser` sets up a brand-new `Promise<Account>` per invocation with a freshly generated `oauthState` (including new `resolve`/`reject` callbacks) each time it is called [4](#0-3) .

Because the initial `state`-token check happens before the network round trip, and the eventual `onAuthCompleted`/`onAuthError` call re-derives its target from `this.state` at completion time instead of from a value captured at guard time, any concurrent mutation of `this.state.oauthState` between the two points (e.g. a second protocol invocation, or the sign-in flow being reset/restarted while the first request is still in flight) is not detected. The `.then()`/`.catch()` handlers of the wrapping `Promise` in `authenticateWithBrowser` do perform a `csrfToken` re-check [5](#0-4) , but `resolveOAuthRequest` itself — the function that actually consumes attacker-supplied `code`/`state` from the deep link — has no equivalent re-validation after its own awaits, and calls `onAuthCompleted`/`onAuthError` unconditionally as long as `this.state` still happens to be in the `Authentication` step with *some* `oauthState`, not necessarily the one that authorized the original call.

### Impact Explanation
If two `x-github-client://oauth` callbacks are delivered in close succession (a plausible occurrence given `handleAppURL` is exercised from both `open-url`/`second-instance` OS events and Windows' `--protocol-launcher` argv scanning), the second invocation's guard is evaluated against the *current* `this.state.oauthState`, and whichever `requestOAuthToken`/`fetchUser` pair resolves last determines which `Account` gets bound to the pending sign-in `Promise` and ultimately added via `emitAuthenticate`. This can result in the wrong account (or an error) being silently accepted for a sign-in the user believes completed against a specific identity/endpoint, which is a corruption of an account-binding decision the user did not actually make — comparable in spirit to the report's "state finalized after external interaction, without accounting for interleaving."

### Likelihood Explanation
The delivery mechanism (a link/deep link the user clicks or that the OS re-delivers) is squarely in the allowed attacker model. However, exploitation still requires a duplicate/racing invocation of the callback with a `state` value the app currently has pending, and does not by itself grant token/credential exfiltration to a remote-only attacker without some means of causing duplicate delivery or observing the CSRF token, so likelihood is limited to specific triggering conditions rather than being reliably remote-triggerable end-to-end.

### Recommendation
In `resolveOAuthRequest`, capture the specific `oauthState` object (not `this.state`) at guard-check time, and after both awaits complete, verify that `this.state?.oauthState === capturedOauthState` (identity check, not just token string match) before invoking `onAuthCompleted`/`onAuthError`. Consider also invalidating/clearing `oauthState` as soon as a `resolveOAuthRequest` call begins consuming it, so a second concurrent invocation for the same session cannot double-consume it — analogous to adding a `nonReentrant`-style guard around the async external calls in the reported contract fix.

### Proof of Concept
1. User initiates GitHub Enterprise/GitHub.com sign-in; `authenticateWithBrowser` sets `oauthState.state = csrfToken1` and opens the browser authorization URL.
2. Before the legitimate `x-github-client://oauth?code=C1&state=csrfToken1` callback is processed to completion (i.e., while `requestOAuthToken`/`fetchUser` are still awaiting), a second delivery of the same (or a differently-timed) `x-github-client://oauth?...&state=csrfToken1` URL is dispatched to `handleAppURL` — e.g. via OS re-launch handling, or a malicious page that repeatedly attempts to open the custom protocol handler while a user's legitimate flow is in progress.
3. Both invocations of `resolveOAuthRequest` pass the `state !== action.state` guard because `this.state.oauthState.state` has not yet changed.
4. Both proceed to `await requestOAuthToken` / `await fetchUser`; whichever completes last calls `this.state.oauthState.onAuthCompleted(account)` using the *current* `this.state`, potentially not corresponding to the invocation that performed the check, silently determining the outcome of the sign-in flow without re-validating consistency between guard time and completion time.

Note: I was not able to fully trace every caller of `handleAppURL`/second-instance re-delivery path in this session due to the iteration limit, so the precise conditions under which duplicate deep-link delivery occurs in practice (single-instance lock behavior, OS-level de-duplication) could not be fully confirmed from the index alone; a Devin session with full repo/tooling access would be needed to verify whether Electron's single-instance lock or `handleAppURL`'s callers already prevent duplicate delivery in all cases.

    } else {
      this.state.oauthState.onAuthError(

async function handleCommandLineArguments(argv: string[]) {
  const args = parseCommandLineArgs(argv, {
    boolean: ['protocol-launcher'],
  })

  // Desktop registers it's protocol handler callback on Windows as
  // `[executable path] --protocol-launcher "%1"`. Note that extra command
  // line arguments might be added by Chromium
  // (https://electronjs.org/docs/api/app#event-second-instance).

  if (__WIN32__ && args['protocol-launcher'] === true) {
    // On Windows we'll end up getting called with something like
    // `--protocol-launcher --allow-file-access-from-files x-github-client://..`
    // which minimist naturally interprets as
    // `--allow-file-access-from-files=x:/github-client`. This is due to
    // Chromium's hot take on parsing command line arguments, see:
    // https://github.com/electron/electron/issues/20322#issuecomment-534137321
    // So while we could add '--allow-file...' as a boolean we can't know for
    // sure that Chromium won't add more switches later on which is why we have
    // to resort to looking through all arguments looking for something that
    // appears to be an app url.
    const prefixes = Array.from(possibleProtocols, p => `${p}://`)
    const matchingUrl = argv.find(arg => {
      if (prefixes.some(p => arg.startsWith(p))) {
        try {
          new URL(arg)
          return true
        } catch (e) {
          log.error(`Unable to parse argument as URL: ${arg}`)
        }
      }
      return false
    })

    if (matchingUrl) {
      handleAppURL(matchingUrl)
    } else {
      log.error(`Encountered --protocol-launcher without app url`)
    }
    // If --protocol-launcher is present we always want to bail and not
    // risk a smuggled cli switch
    return
  }
