### Title
Attacker-controlled PR/branch name bypasses worktree path sanitization on macOS/Linux, allowing path traversal in "Checkout in New Worktree" - ([File: app/src/ui/lib/repository-path.tsx])

### Summary
`safeDirectoryName()` in `app/src/ui/lib/repository-path.tsx` only strips dangerous characters on Windows (`<>:"|?*`); on macOS and Linux it returns the input completely unmodified: [1](#0-0) 
This value is then joined directly into a filesystem path with no traversal check: [2](#0-1) 
The `RepositoryPath` component is prefilled from `initialWorktreeName`, which "Checkout in New Worktree" derives from repository name, branch name, and a PR number: [3](#0-2) 
Both branch names (`pullRequest.head.ref`) and other repo-derived strings, when they originate from a malicious fork/PR, are essentially attacker-controlled text that is never validated against path-traversal sequences (`../`) on POSIX platforms, unlike the equivalent clone-path logic which has an explicit sanitizer and tests: [4](#0-3) [5](#0-4) 

### Finding Description
The bug-class from the report is "a computed value that is supposed to guard against a bad outcome, but the margin/validation is missing or insufficient, so an out-of-range/negative/dangerous value slips through unchecked." The clone-path flow in this codebase demonstrates that the Desktop team is aware of this exact class of problem and added `isClonePathSensitive()` and `sanitizeCloneName()` as guards against path-traversal payloads embedded in attacker-supplied strings (repo names from URLs): [6](#0-5) 

However, the analogous worktree-creation path does not reuse that guard. `AddWorktreeDialog` populates `RepositoryPath` with `initialWorktreeName` (derived from a PR number or remote branch name) with no call to `sanitizeCloneName` or any traversal check: [7](#0-6) 
`RepositoryPath.getFullPath()` simply does `Path.join(path, safeDirectoryName(name))`, and since `safeDirectoryName` is a no-op on POSIX, a name like `../../../.ssh` (which could be crafted as a branch name via `pullRequest.head.ref` on a malicious fork, since GitHub branch names allow `/` and `.` sequences within slash-separated components) is passed through unchanged into `Path.join`, letting the resolved worktree destination escape the intended parent directory.

The resulting `fullPath` is then used directly as the destination for `git worktree add`: [8](#0-7) 
which writes a new working tree (files, `.git` file pointer, checked-out branch content) at that resolved location with no re-validation before the git call is made.

### Impact Explanation
If the resulting resolved path lands outside the intended base folder (e.g. inside the user's home directory, `.ssh`, or another sensitive folder), `git worktree add` will write repository files (including a `.git` gitlink and checked-out file contents from the branch, which are themselves attacker-influenced since they come from the PR/fork) into that location. This is a file-write-outside-intended-directory primitive driven by attacker-controlled PR/branch metadata, satisfying "file write... outside the repo" from the accepted impact list. Depending on the destination, this could overwrite configuration files or plant files that are later trusted/executed by the user's toolchain.

### Likelihood Explanation
Exploitation requires the victim to click "Checkout in New Worktree…" / "Checkout PR in New Worktree…" on a PR/branch from an attacker-controlled fork with a maliciously crafted branch name, then accept the pre-filled worktree name/path shown in the dialog without editing it. This is a plausible, low-friction interaction pattern in Desktop's PR review flow (view PR → checkout in worktree), and does not require local access, admin rights, or prior malware — matching the "attacker controls a git remote/PR" impact category.

### Recommendation
Reuse the existing `sanitizeCloneName` (or an equivalent traversal-safe sanitizer) inside `safeDirectoryName`/`RepositoryPath.getFullPath()` for all platforms, not just Windows, and/or validate that the final resolved `fullPath` (via `Path.resolve`) still starts with the chosen base directory before calling `addWorktree`, mirroring the `isClonePathSensitive` check already used for `clone.ts`.

### Proof of Concept
1. Attacker creates a fork/PR with a branch name/head ref containing traversal-like segments (e.g. a ref such as `x/../../../../tmp/evil`, or a PR whose combination of repository name + PR number, once used to build `initialWorktreeName`, contains `..` segments that survive branch/PR-name validation).
2. Victim opens the branch/PR dropdown in Desktop and selects "Checkout PR in New Worktree…", which calls `onCheckoutPRInNewWorktree` and pre-fills `initialWorktreeName` from the attacker-controlled ref/PR data.
3. `AddWorktreeDialog` passes this name into `RepositoryPath`, whose `getFullPath()` uses `safeDirectoryName(name)` — a no-op on macOS/Linux — before `Path.join(path, name)`.
4. The victim confirms the dialog (the displayed path may look benign if the traversal segments are visually inconspicuous), and `addWorktree()` runs `git worktree add <resolved-path>`, writing repository content outside the intended directory.

Note: I was not able to fully confirm from the index whether GitHub's server-side branch-name validation would allow a ref value containing `../` segments to reach `pullRequest.head.ref` unmodified — this would need to be verified in a live session (e.g., by testing against GitHub's ref-name rules and Desktop's `sanitizedRefName`/`testForInvalidChars` filters) to establish a fully working end-to-end PoC.

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function addWorktree(
  repository: Repository,
  path: string,
  options: {
    /** Branch name used with -b (create new branch) */
    readonly createBranch?: string
    /** Commit-ish to check out (branch name, ref, or SHA) */
    readonly commitish?: string
  } = {}
): Promise<void> {
  const args = ['worktree', 'add']

  if (options.createBranch) {
    args.push('-b', options.createBranch)
  }

  args.push(path)

  if (options.commitish) {
    args.push(options.commitish)
  }

  await git(args, repository.path, 'addWorktree')
}
