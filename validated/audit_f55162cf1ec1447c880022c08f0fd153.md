Based on my investigation, `updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts` is the closest structural analog to the Velodrome bug: a security-relevant decision hardcodes an assumption ("only compare `protocol`") about what must stay constant, while ignoring another attacker-influenceable field (`hostname`) that the underlying GitHub API response fully controls. This mirrors the original bug's pattern — a computation trusts a narrow, hardcoded check while a broader, externally-configurable parameter can silently invalidate the assumption.

### Title
Silent remote URL takeover via `updateRemoteUrl`'s protocol-only check ignores hostname changes from the GitHub API response - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically rewrites a repository's git remote URL using the `clone_url` field of an `IAPIRepository` object fetched from the GitHub API, gating the rewrite only on whether the URL's **protocol** stays the same. [1](#0-0)  It never validates that the **hostname** of the new `clone_url` matches the original remote's hostname, so any API response (or a repository's tracked `GitHubRepository.cloneURL` state) that changes only the host — while preserving protocol — will be silently written into the user's local git config as the new `origin` remote.

### Finding Description
The gating logic in `updateRemoteUrl` is:
1. `urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)` — true if the new URL parses to the same owner/name/hostname as the current remote. [2](#0-1) 
2. `protocolsMatch` — compares only `URL.parse(...).protocol` between old and new URLs, e.g. `https:` vs `https:`. [3](#0-2) 
3. `remoteUrlUnchanged` — checks that the *previously cached* `gitHubRepository.cloneURL` still matches the on-disk remote (i.e., the user hasn't manually repointed their remote).
4. If `protocolsMatch && remoteUrlUnchanged && !urlsMatch`, the remote is rewritten via `gitStore.setRemoteURL(...)`. [4](#0-3) 

The critical gap: `protocolsMatch` only guards the URL **scheme**, not the **hostname**. `urlsMatch` being false is actually the *triggering* condition for the rewrite (that's the whole point of the function — to follow renames/transfers), so a hostname change is exactly what causes the branch to fire, not something it defends against. This is the same shape as the Uniswap bug: a narrow, hardcoded invariant (fee assumed constant / protocol assumed to matter) stands in for a broader trust boundary (custom per-pool fee / actual destination host) that is fully attacker/externally controlled.

`updateRemoteUrl` is invoked from `repositoryWithRefreshedGitHubRepository` in `app-store.ts`, which runs automatically during periodic background refresh whenever Desktop re-fetches a repository's metadata from the GitHub API. [5](#0-4)  The `apiRepo` object comes directly from `api.fetchRepository(owner, name)` — a GitHub API response. If that response's `clone_url` (or, for GHE, an equivalent field on a compromised/mirrored/malicious enterprise server) reports a different host under the same scheme, Desktop will rewrite the tracked `origin` remote to point at that host without any user confirmation.

### Impact Explanation
If exploitable, this results in "silent corruption of what the user pushes/fetches": subsequent `git push`/`git fetch`/`git pull` operations, and — more importantly — the Desktop credential trampoline (`findGitHubTrampolineAccount`, which matches accounts by `origin` of the remote URL) would authenticate against the new host using the user's stored GitHub credentials. [6](#0-5)  This could exfiltrate push traffic (and potentially credentials, depending on the credential-helper's host-matching behavior) to an attacker-influenced host, and would happen without any explicit user action — the closest UI equivalent, `UpstreamAlreadyExists`, only warns about upstream-remote mismatches, not `origin` rewrites via `updateRemoteUrl`. [7](#0-6) 

### Likelihood Explanation
This requires either: (a) a compromised/malicious GitHub Enterprise Server response for a repository the user already has configured with a `GitHubRepository` association, or (b) some way to influence what `api.fetchRepository` returns for an owner/name pair the user already tracks (e.g., a repository rename/ownership-transfer race, or a malicious API proxy/MITM on a self-hosted GHE instance a user has added). This is plausible for the GHE case, which is explicitly a supported "custom" trust configuration in Desktop (analogous to Velodrome's custom per-pool fee), but I could not fully verify from the available index whether GitHub.com's API guarantees `clone_url` host stability strongly enough to rule out this path, nor could I trace all downstream credential-matching code paths (e.g., exact trampoline account resolution order) to confirm credential exfiltration versus just push-traffic redirection. This should be treated as a plausible-but-unconfirmed finding requiring further live testing.

### Recommendation
In `updateRemoteUrl`, compare the **hostname** of the current and updated URLs (not just protocol) before allowing an automatic remote rewrite, or require explicit user confirmation (similar to the existing `UpstreamAlreadyExists` dialog) whenever the resolved hostname changes as a result of an API-driven update. [8](#0-7) 

### Proof of Concept
1. Add a GitHub Enterprise account in Desktop and open a locally cloned repository whose `origin` remote is `https://ghe-legit.example.com/org/repo.git`, already associated with a `GitHubRepository` record.
2. During Desktop's periodic background refresh, `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository(owner, name)` against the configured GHE endpoint. [9](#0-8) 
3. If the response body's `clone_url` is `https://attacker-controlled.example.com/org/repo.git` (same scheme, different host) — e.g., via a compromised/MITM'd GHE server — `protocolsMatch` is `true`, `remoteUrlUnchanged` is `true` (nothing local changed), and `urlsMatch` is `false` (different hostname), satisfying `protocolsMatch && remoteUrlUnchanged && !urlsMatch`. [4](#0-3) 
4. `gitStore.setRemoteURL('origin', 'https://attacker-controlled.example.com/org/repo.git')` executes silently, rewriting the user's `origin` remote without any prompt.
5. The next `git push`/`fetch` sends the user's commits (and triggers credential-helper authentication) against `attacker-controlled.example.com`.

I was not able to fully verify the exact attacker capability required to control the raw GHE `fetchRepository` API response contents from the local index alone; a live Devin session with access to `app/src/lib/api.ts`'s `fetchRepository` implementation and the trampoline credential-matching code end-to-end would be needed to confirm whether stored tokens are actually sent to the new host or only push traffic is redirected.

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

  remoteUrl: string
