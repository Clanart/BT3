### Title
Unrestricted re-snapshotting via `updateEndRemainingAllocation()` collapses the bonus denominator, allowing theft of the forfeited-bonus pool - (File: rewards/Airdrop.sol)

### Summary
`updateEndRemainingAllocation()` is a `public`, unauthenticated function that can be called repeatedly by anyone at any time after `periodsEndTime[4]`, and it unconditionally overwrites `totalEndRemainingAllocation` with the *current* `totalRemainingAllocation`. Because `claim()` only auto-invokes it when `totalEndRemainingAllocation == 0` [1](#0-0) , an attacker can bypass this guard by calling `updateEndRemainingAllocation()` directly, re-snapshotting the denominator to a much smaller value right before their own `claim()`, inflating their `getBonusAmount()` share far beyond their fair pro-rata portion of `totalBonus`.

### Finding Description
The bonus mechanism works as follows:
- Early claimants who claim before full vesting forfeit part of their allocation; the forfeited amount accumulates into `totalBonus` [2](#0-1) .
- After period 4 ends, remaining (late) claimants are supposed to split `totalBonus` proportionally to their share of `totalEndRemainingAllocation`, a value that should be snapshotted **once**, representing the total allocation still unclaimed at the moment period 4 ended: [3](#0-2) .
- The snapshot function itself has no "already-set" guard:
```solidity
function updateEndRemainingAllocation() public {
    if (block.timestamp >= periodsEndTime[4]) {
        totalEndRemainingAllocation = totalRemainingAllocation;
    }
}
``` [4](#0-3) 

- `claim()` only calls it conditionally (`if (totalEndRemainingAllocation == 0)`), which is intended to snapshot it exactly once on the very first post-period-4 claim [1](#0-0) . But since `updateEndRemainingAllocation()` is public with no such guard, any unprivileged caller can invoke it directly at any later time, and it will overwrite the already-set `totalEndRemainingAllocation` with the new, smaller `totalRemainingAllocation` (which only shrinks monotonically as `claim()` zeroes out `allocations[msg.sender]` and decrements `totalRemainingAllocation` on each call [5](#0-4) ).

Exploit flow:
1. Attacker registers/holds a (small) allocation and waits until most other eligible users have already claimed after period 4, so `totalRemainingAllocation` has shrunk toward the attacker's own remaining allocation.
2. Attacker calls `updateEndRemainingAllocation()` directly, collapsing `totalEndRemainingAllocation` to this small value.
3. Attacker immediately calls `claim()`. `getBonusAmount()` computes `bonusAmount = userAllocation * totalBonus / totalEndRemainingAllocation`, which now approaches `totalBonus` even though the attacker's true pro-rata share (based on the allocation remaining at the actual end of period 4) is far smaller.
4. The attacker captures a disproportionate (potentially near-total) share of the pooled forfeited bonus meant for all late claimants, at the expense of subsequent legitimate claimants or the contract's own solvency for remaining principal payouts.

Existing checks (`claimableAmount > aidropToken.balanceOf(address(this))` revert) only bound a single transfer to the contract's current balance; they do not prevent the underlying accounting corruption or the unfair redistribution of `totalBonus`.

### Impact Explanation
This breaks the invariant that a participant cannot shrink the denominator scaling their own bonus. It directly enables theft of the pooled forfeited-bonus funds that rightfully belong to other unclaimed/late participants, and can leave the contract unable to fully pay remaining legitimate claimants (their principal 100% allocation plus fair bonus), matching the "Critical — Direct theft of user funds" impact class.

### Likelihood Explanation
No privileged role is required — `updateEndRemainingAllocation()` is `public` with zero access control, callable by any EOA or contract. The only precondition is waiting until most other allocations are claimed post period-4-end (a naturally occurring state as the airdrop progresses), which requires no capital, flash loans, or special timing beyond monitoring on-chain state. This is straightforward and repeatable by any of the last remaining claimants.

### Recommendation
Add a guard to `updateEndRemainingAllocation()` so the snapshot can only be taken once, e.g.:
```solidity
function updateEndRemainingAllocation() public {
    if (block.timestamp >= periodsEndTime[4] && totalEndRemainingAllocation == 0) {
        totalEndRemainingAllocation = totalRemainingAllocation;
    }
}
```
This mirrors the intended one-time-snapshot semantics already assumed by `claim()`'s conditional call, preventing re-snapshotting after the fact.

### Proof of Concept
Foundry test plan:
1. Deploy `Airdrop` with several registered users (e.g., users A, B, C, D with allocations summing to `T`) and fund the contract with the token.
2. Warp time past `periodsEndTime[4]`.
3. Have A, B, C call `claim()` sequentially (each forfeits nothing at period 4 since 100% is claimable, but assume some had claimed earlier periods to build up `totalBonus`) — after these, `totalRemainingAllocation` ≈ D's allocation only.
4. As D (attacker), directly call `updateEndRemainingAllocation()` to reset `totalEndRemainingAllocation` to the now-small `totalRemainingAllocation`.
5. Call `claim()` as D and assert `getBonusAmount(D)` ≈ `totalBonus` (far exceeding D's fair pro-rata share based on the true remaining allocation at the actual period-4-end moment).
6. Assert this violates the reconciliation invariant: sum of bonus paid across all claimants exceeds `totalBonus`, and D's balance gain is disproportionate to `allocations[D]` relative to other claimants' shares.
