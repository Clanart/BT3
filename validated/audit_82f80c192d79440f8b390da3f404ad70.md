## Analysis

This is a genuine analog of the GMX bug's core flaw — using a value fetched at execution time instead of the value the actor actually reviewed at decision time. In GMX, orders were priced with the *current* Chainlink price rather than the price at submission. In GitHub Desktop, commits are staged using a *freshly re-read* working-directory diff rather than the diff the user actually reviewed and selected lines from in the Changes view.

### Title
Partial-commit line selection is silently reapplied to a re-fetched diff at commit time, letting working-directory changes made after review get committed unreviewed - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user selects a subset of lines to include in a commit ("partial commit"), GitHub Desktop records the selection as a set of *absolute line indices* into the diff that was displayed at review time. That diff is computed once by `updateChangesWorkingDirectoryDiff` [1](#0-0)  and cached in UI state. However, when the user actually clicks "Commit", `_commitIncludedChanges` takes the files straight from the cached working-directory state [2](#0-1)  and hands them to `createCommit`, which calls `stageFiles` and ultimately `applyPatchToIndex`. That function re-reads the diff from disk at that moment (`getWorkingDirectoryDiff(repository, file)`) and reapplies the stale line-index selection to this brand-new diff via `formatPatch` [3](#0-2) .

### Finding Description
`DiffSelection` has no notion of line *content* — only integer line indices (`isSelected(lineIndex)`, `divergingLines: Set<number>`) [4](#0-3) . There is an explicit code comment acknowledging that the diff can change "dramatically" between the time it's loaded and later use, but the mitigation only updates which indices remain *selectable* — it does not re-validate that selected content still matches what the user saw: [5](#0-4) 

Critically, that reconciliation only runs while the UI's `updateChangesWorkingDirectoryDiff` path executes (e.g. on a status refresh). It is not invoked again right before `_commitIncludedChanges` stages files, and `applyPatchToIndex` independently re-fetches the diff from disk at staging time regardless of whether the renderer has re-synced [6](#0-5) . If the tracked file's content on disk changes between the moment the user reviews/selects lines and the moment the commit button's async chain (`unstageAll` → `stageFiles` → `applyPatchToIndex` → `git commit`) actually runs, the old index-based selection is blindly reapplied to the new diff content by `formatPatch`, which walks `hunk.lines` and asks `file.selection.isSelected(absoluteIndex)` for each line with no content comparison [7](#0-6) .

The attacker primitive here is a cloned/fetched repository that carries a benign-looking automation (e.g. an `npm` `prepare`/`postinstall` script commonly executed by an ordinary `npm install` in a freshly cloned project, or a bundled dev-server/build-watcher script the project's own README instructs the developer to run) which rewrites specific lines of a tracked file in place (not adding/removing lines, to preserve index alignment) while the developer has the diff open in Desktop and is composing a commit. Because the rewritten lines occupy the same diff hunk positions, the old selection silently includes attacker-controlled content in the commit that the user never saw or approved, while Desktop shows no warning that the underlying diff changed.

### Impact Explanation
This breaks the fundamental invariant that "what the user reviewed and checked in the Changes/diff view is what gets committed." An attacker who can get code to run in the context of the cloned repository (a very common, low-friction primitive for a git client, e.g. via `postinstall`) can cause GitHub Desktop to silently corrupt the contents of a commit the user believes they authored and reviewed, potentially reintroducing malicious code, secrets, or backdoors into a commit/push that then propagates to the shared remote — this is exactly the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
The race window is realistic: users routinely take noticeable time between opening a diff, selecting lines, writing a commit message, and clicking "Commit," especially for larger diffs or when the "Generate commit message" AI flow is used (also async) [8](#0-7) . No confirmation or re-diff-and-compare step exists between selection and staging in `_commitIncludedChanges` [2](#0-1) , and `applyPatchToIndex` is architecturally guaranteed to re-read from disk rather than reuse the reviewed diff [6](#0-5) .

### Recommendation
Before staging a partial selection, `applyPatchToIndex` (or its caller) should re-fetch the diff and verify it is unchanged (e.g. by comparing a hash/blob OID or the diff content itself) relative to the diff the selection was computed against, and abort/refresh-and-reprompt the user if it has changed, rather than silently reapplying stale line indices to new content.

### Proof of Concept
1. Clone an attacker-controlled repository containing a tracked file `config.js` with a line `const DEBUG = false` and a `package.json` `postinstall` script that, after a short delay, rewrites that exact line to `const DEBUG = true; exfiltrate()` (same line count/position).
2. Victim runs `npm install` (installing the postinstall hook/watcher) and opens the repo in GitHub Desktop, makes an unrelated edit, opens the Changes diff for `config.js`, and selects only some other lines to include (not touching the `DEBUG` line — it should remain excluded per the shown diff).
3. Before the victim clicks "Commit," the postinstall script's delayed rewrite fires and modifies the on-disk `DEBUG` line.
4. Victim clicks "Commit." `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-diffs `config.js` from disk (now containing the attacker's line) and reapplies the old index-based selection via `formatPatch`; because the malicious line occupies a diff position the user's selection maps to as selected/unselected without content verification, the attacker's line is committed even though the diff the user actually reviewed never showed it.
