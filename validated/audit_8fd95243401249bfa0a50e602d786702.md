### Title
Direct token transfer to MasterMagpie inflates `totalStaked()`, permanently freezing/diluting a portion of every reward distribution - (File: rewards/BaseRewardPool.sol / rewards/BaseRewardPoolV2.sol)

### Summary
`totalStaked()` in both `BaseRewardPool` and `BaseRewardPoolV2` returns the raw `IERC20(stakingToken).balanceOf(operator)` instead of the sum of recorded `UserInfo.amount` values tracked by `MasterMagpie`. An unprivileged attacker can inflate this balance by directly transferring `stakingToken` to `MasterMagpie` without going through `deposit()`, which never updates any user's stake record but does increase the denominator used in `_provisionReward`'s reward-per-token calculation, causing a portion of every subsequently queued reward to become permanently unclaimable.

### Finding Description
`totalStaked()` is defined identically in [1](#0-0)  and [2](#0-1)  as the raw balance of the staking token held by the `operator` (MasterMagpie), rather than an aggregate of legitimate stake accounting. Individual user balances, by contrast, are read from MasterMagpie's own `stakingInfo` mapping via `balanceOf(_account)` at [3](#0-2) , which is only updated through the deposit/withdraw flow, not by raw token balance.

When a manager calls `queueNewRewards`, `_provisionReward` computes the reward-per-token increment as `(_amountReward * 10**stakingTokenDecimals) / totalStaked()`, seen at [4](#0-3) . Since `totalStaked()` uses the raw balance rather than the sum of all `UserInfo.amount`, any attacker can inflate the denominator simply by calling `stakingToken.transfer(address(masterMagpie), dustAmount)` directly — no `deposit()` call, no `UserInfo` registration, and no access control is required since this is a plain ERC20 transfer to an arbitrary address.

Because the denominator is now larger than the true sum of stakers' recorded balances, `rewardInfo.rewardPerTokenStored` is incremented by less than it should be. Consequently, `sum(earned(user, token) for all stakers)` after the `queueNewRewards` event is strictly less than `_amountReward` actually transferred into the contract. The unaccounted remainder sits as the pool's raw reward-token balance but is never allocated to any `userRewards` mapping and there is no sweep/reclaim function for the manager or owner to redistribute it, since `rewardPerTokenStored` will continue to be diluted on all future distributions as long as the "phantom" stake balance remains in the contract. This is a genuinely permanent freeze because reward tokens accumulate in the contract with no mechanism to reallocate the shortfall to legitimate stakers.

No existing modifier or check (`onlyManager`, `updateReward`, etc.) prevents this because the vulnerability lies in `totalStaked()`'s definition itself, not in any guarded state-mutating function — the attacker's transfer is a completely permissionless ERC20 transfer that requires no interaction with `BaseRewardPool`/`BaseRewardPoolV2`/`MasterMagpie` access-controlled functions at all.

### Impact Explanation
This matches the Immunefi impact class "theft or permanent freezing of unclaimed yield." Every `queueNewRewards` call after the attacker's dust transfer distributes rewards using an inflated denominator, so a portion of the reward amount (proportional to `dustAmount / totalStaked()`) becomes permanently stuck in the pool contract, unclaimable by any staker and irrecoverable by governance/manager functions currently exposed in the contract. Repeated with larger dust transfers, this can dilute an arbitrarily large fraction of every future reward distribution.

### Likelihood Explanation
The attack requires only holding an amount of `stakingToken` (even a negligible "dust" amount) and calling a plain, permissionless ERC20 `transfer` to `MasterMagpie`'s address — no special privileges, flash loans, or complex sequencing needed. It is fully repeatable on every reward pool at any time, and the loss compounds with each subsequent `queueNewRewards` call as long as the phantom balance remains.

### Recommendation
Change `totalStaked()` to track and return an explicit accounting variable (e.g., a `totalSupply`/`totalStakedInternal` state variable) that is incremented/decremented only through `MasterMagpie`'s `deposit`/`withdraw` calls, rather than reading the raw `IERC20(stakingToken).balanceOf(operator)`. This ensures the denominator used in `_provisionReward`'s reward-per-token math always matches the true aggregate of user-recorded stakes.

### Proof of Concept
1. Deploy `MasterMagpie`, `BaseRewardPoolV2` (or `BaseRewardPool`), and a mock ERC20 staking token plus a mock reward token.
2. Have two legitimate stakers (`userA`, `userB`) each `deposit()` `100e18` staking tokens through `MasterMagpie`, so `UserInfo.amount` sums to `200e18`, matching `stakingToken.balanceOf(masterMagpie) == 200e18`.
3. Have an attacker (holding only, e.g., `50e18` staking tokens purchased/acquired independently) call `stakingToken.transfer(address(masterMagpie), 50e18)` directly — bypassing `deposit()` entirely, so no `UserInfo` entry is created for the attacker.
4. Confirm `totalStaked()` now returns `250e18` while the true sum of `UserInfo.amount` (userA + userB) remains `200e18`.
5. As the manager, call `queueNewRewards(amountReward, rewardToken)` with, e.g., `amountReward = 250e18` reward tokens.
6. Assert: `rewardPerTokenStored` increases by `(250e18 * 1e18) / 250e18 = 1e18` instead of the correct `(250e18 * 1e18) / 200e18 = 1.25e18` that would fully distribute the reward to legitimate stakers.
7. Call `earned(userA, rewardToken)` and `earned(userB, rewardToken)`, sum them, and assert `sum < amountReward` (specifically `sum == 200e18` vs. `amountReward == 250e18`), demonstrating `50e18` reward tokens are permanently trapped in the pool contract with no recovery path.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
