### Title
Unchecked ERC20 `transfer` return value in escrow withdrawal lets `withdraw()` mark orders filled/refunded without moving funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron `IntentGatewayV2.withdraw()` function pays out escrowed order tokens and transaction fees using raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` calls, checking only the boolean `success` returned by the call itself, never the ABI-encoded return value from the token's `transfer` function. This is the same root defect as the referenced report (`TimelockController._call`): the code trusts `call()`'s outer success flag as proof that the intended transfer actually happened, when in fact `success == true` only means the call didn't revert — not that tokens moved.

### Finding Description
In `withdraw()`, escrow release/refund and fee payout do: [1](#0-0) [2](#0-1) 

The pattern only checks `success` from the raw `.call`, never decoding/validating the ERC20 boolean return value the way `SafeERC20.safeTransfer` does (the sibling EVM contract `IntentsBase.sol` correctly uses `IERC20(token).safeTransfer(beneficiary, amount)` instead: [3](#0-2) ). Non‑reverting ERC20 implementations that return `false` on failure (rather than reverting) — e.g. insufficient balance, blacklist/pause logic, or any token with non-standard `transfer` semantics — will make `token.call(...)` return `success = true` while zero tokens are actually transferred. `withdraw()` proceeds to decrement escrow accounting, mark `_filled[body.commitment] = beneficiary`, and emit `EscrowReleased`/`EscrowRefunded` as if payment succeeded: [4](#0-3) 

Unlike `CallDispatcher.sol`, which explicitly reverts when the target has no code (`extcodesize == 0`) before calling and also bubbles up the low-level call failure: [5](#0-4) , `withdraw()` performs no such contract-existence or return-data validation at all.

### Impact Explanation
This falls under "false state acceptance" / "loss of funds": the escrow bookkeeping (`_orders[commitment][token]`) is decremented and the order is irreversibly marked filled/refunded (`_filled[body.commitment] = beneficiary`) even though the beneficiary receives nothing. Because `_filled` is set unconditionally once the loop completes, a failed transfer permanently locks the beneficiary out of any legitimate recovery for that commitment — the escrowed value is effectively burned/stranded while the protocol's accounting believes settlement is complete. Since `onGetResponse` also calls `withdraw(body, true)` directly without any additional balance verification, the same class of silent-failure/false-settlement applies to the timeout/refund path as well: [6](#0-5) .

### Likelihood Explanation
The vulnerable path (`withdraw`) is reached both via `onAccept` (RedeemEscrow/RefundEscrow after `authenticate`) and via `onGetResponse` for cancellations: [7](#0-6) . The trigger condition does not require a malicious relayer/prover — it requires only that one of the order's input tokens is a non-standard ERC20 that returns `false` instead of reverting on failure, which is a well-documented and common real-world token behavior (legacy USDT-style tokens, tokens with fee/blacklist logic). Because token selection for an order is controlled by the order creator at open time, this is reachable by ordinary unprivileged users creating orders with such tokens, without needing any compromised infrastructure.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` invocations in `withdraw()` (lines 697, 711) and `onAccept`'s `SweepDust` handler (line 665) with OpenZeppelin's `SafeERC20.safeTransfer`, matching the pattern already used correctly in `evm/src/apps/intentsv2/IntentsBase.sol`. This ensures both call-level success and the ERC20 boolean return value are validated before escrow state is mutated and the order is marked filled/refunded.

### Proof of Concept
1. Attacker/user creates an intent order whose input token is a non-reverting ERC20 that can be made to return `false` from `transfer` (e.g., a token with insufficient balance at settlement time due to a rebasing/fee mechanism, or a pausable/blacklist token where the escrow contract or beneficiary later gets blacklisted).
2. The order is escrowed normally (real `safeTransferFrom` succeeds at `open()` time, so `_orders[commitment][token]` is funded).
3. Later, cross-chain `RedeemEscrow`/`RefundEscrow` message arrives and `onAccept` → `withdraw()` runs; the token's `transfer(beneficiary, amount)` call executes without reverting but returns `false` (e.g., due to a state change on the token between escrow and withdrawal).
4. `token.call(...)` returns `success = true` (the call itself did not revert), so the `if (!success) revert TransferFailed();` check passes despite zero tokens moving.
5. `_orders[body.commitment][token] -= amount;` and `_filled[body.commitment] = beneficiary;` execute, and `EscrowReleased`/`EscrowRefunded` is emitted — the protocol now believes the beneficiary was paid, but the beneficiary holds no tokens and has no further path to reclaim the escrowed balance.
