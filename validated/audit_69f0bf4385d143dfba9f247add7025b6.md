This confirms the mechanism: `withTrampolineToken` in `app/src/lib/trampoline/trampoline-tokens.ts` generates a single random token that is valid for the entire duration of one outer `git` invocation and accepted by `isValidTrampolineToken` from *any* socket connection that presents it — there is no binding of the token to a specific child process or the specific askpass/credential-helper binary that is supposed to consume it.

### Title
Git-hook subprocesses inherit the live `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT`, allowing a repository-controlled hook to re-enter the askpass trampoline and exfiltrate credentials - ([File: app/src/lib/trampoline/trampoline-environment.ts])

### Summary
Every Git operation Desktop runs is wrapped in `withTrampolineEnv` (`app/src/lib/trampoline/trampoline-environment.ts:93-147`), which injects `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN` into the environment of the spawned `git` process for the sole purpose of letting the dedicated askpass/credential-helper trampoline binary talk back to Desktop's local `TrampolineServer` (`app/src/lib/trampoline/trampoline-server.ts`). The token is created by `withTrampolineToken` in `app/src/lib/trampoline/trampoline-tokens.ts:24-37` and is valid for the whole lifetime of that git invocation, and `isValidTrampolineToken` (`trampoline-tokens.ts:14-16`) accepts the token from **any** socket connection — it never verifies that the caller is the actual askpass helper.

### Finding Description
When Git executes hooks (`pre-commit`, `post-commit`, `pre-push`, `post-merge`, etc.) as a normal part of `commit`/`push`/`pull` (see the `interceptHooks` lists in `app/src/lib/git/commit.ts:58-65`, `app/src/lib/git/push.ts:78`, `app/src/lib/git/pull.ts:48-56`), those hook subprocesses are spawned by the underlying native `git` process, which itself was spawned by Desktop with `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` in its environment (`app/src/lib/git/core.ts:277-296`, `app/src/lib/git/spawn.ts:21-38`). Unless Desktop's own hooks-interception path (`app/src/lib/hooks/with-hooks-env.ts`, `app/src/lib/hooks/hooks-proxy.ts:166-176`) is active and its `safePrefixes`/`excludedEnvVars` filtering is applied, a hook script runs with the *unfiltered* process environment inherited from `git`, i.e. it can read `DESKTOP_TRAMPOLINE_TOKEN` and `DESKTOP_PORT` directly.

`core.hooksPath` can point into the working tree (e.g. tools like Husky/lefthook commit tracked hook scripts under a repo directory and set `core.hooksPath` to it), so an attacker-controlled cloned repository can ship an executable hook that runs automatically the next time the victim commits/pushes/pulls in Desktop. That script can open a TCP connection to `127.0.0.1:$DESKTOP_PORT`, send an `ASKPASS` (or `CREDENTIALHELPER`) trampoline command with the leaked `DESKTOP_TRAMPOLINE_TOKEN`, and the `TrampolineServer.processCommand` (`app/src/lib/trampoline/trampoline-server.ts:162-176`) will accept it and dispatch to `createAskpassTrampolineHandler`/`createCredentialHelperTrampolineHandler` (registered in `app/src/ui/index.tsx:262-270`) exactly as if it were the legitimate askpass binary, returning the signed-in account's stored credentials for whatever endpoint the hook requests.

### Impact Explanation
This lets an unprivileged, attacker-controlled cloned/fetched repository silently exfiltrate the user's GitHub (or generic Git) credentials/tokens by abusing Desktop's own trampoline authentication channel — a credential/token exfiltration path that requires no unusual user action beyond committing, pushing, or pulling in a normal Desktop workflow.

### Likelihood Explanation
The "check" that is meant to gate access to the askpass/credential channel is only the possession of the token string; the invariant that should hold — "only the process Desktop spawned as `GIT_ASKPASS`/credential helper can redeem this token" — is not enforced, and the token/port are broadcast to every process descending from the outer `git` invocation, including repository-supplied hooks. This mirrors the WildCredit pattern where a reserve/authorization check is performed after (or independent of) an external call whose side effects (spawning attacker-influenced code) can be used to re-enter and abuse the same privileged channel before the outer operation completes and the token is revoked in the `finally` block.

### Recommendation
Scope trampoline tokens to the specific child process that is supposed to use them (e.g., pass a per-process secret only via a channel not inherited by further descendants, or strip `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` from the environment before invoking hooks even when hook interception is disabled), and have `isValidTrampolineToken`/`processCommand` bind tokens to a single expected identifier/PID rather than accepting any client that knows the token value.

### Proof of Concept
Not independently executed; this is based on static analysis of `app/src/lib/trampoline/trampoline-tokens.ts`, `app/src/lib/trampoline/trampoline-environment.ts`, `app/src/lib/trampoline/trampoline-server.ts`, and the hook-interception env-filtering logic in `app/src/lib/hooks/hooks-proxy.ts`. I was not able to fully verify, within the available tool budget, whether some other layer of Desktop unconditionally strips `DESKTOP_*` variables before invoking hooks when the new hooks-environment feature (`getHooksEnvEnabled()`) is disabled — this would need to be confirmed by tracing `dugite`'s `exec`/`spawn` env handling and native `git` hook invocation. If it turns out `DESKTOP_TRAMPOLINE_TOKEN` is unconditionally excluded/regenerated for hook execution, this analog would not hold; a Devin session with full repo/checkout access could confirm this by instrumenting a hook script to dump `process.env` during a real Desktop-driven commit. const trampolineTokens = new Set<string>()

function requestTrampolineToken() {
  const token = crypto.randomUUID()
  trampolineTokens.add(token)
  return token
}

function revokeTrampolineToken(token: string) {
  trampolineTokens.delete(token)
}

/** Checks if a given trampoline token is valid. */
export function isValidTrampolineToken(token: string) {
  return trampolineTokens.has(token)
}

/**
 * Allows invoking a function with a short-lived trampoline token that will be
 * revoked right after the function finishes.
 *
 * @param fn Function to invoke with the trampoline token.
 */
export async function withTrampolineToken<T>(
  fn: (token: string) => Promise<T>
): Promise<T> {
  const token = requestTrampolineToken()
  let result

  try {
    result = await fn(token)
  } finally {
    revokeTrampolineToken(token)
  }

  return result
}

export async function withTrampolineEnv<T>(
  fn: (env: object) => Promise<T>,
  path: string,
  isBackgroundTask = false,
  customEnv?: Record<string, string | undefined>
): Promise<T> {
  const sshEnv = await getSSHEnvironment()

  return withTrampolineToken(async token => {
    isBackgroundTaskEnvironment.set(token, isBackgroundTask)
    trampolineEnvironmentPath.set(token, path)

    const existingGitEnvConfig =
      customEnv?.['GIT_CONFIG_PARAMETERS'] ??
      process.env['GIT_CONFIG_PARAMETERS'] ??
      ''

    const gitEnvConfigPrefix =
      existingGitEnvConfig.length > 0 ? `${existingGitEnvConfig} ` : ''

    // The code below assumes a few things in order to manage SSH key passphrases
    // correctly:
    // 1. `withTrampolineEnv` is only used in the functions `git` (core.ts)
    // 2. Those two functions always thrown an error when something went wrong,
    //    and just return a result when everything went fine.
    //
    // With those two premises in mind, we can safely assume that right after
    // `fn` has been invoked, we can store the SSH key passphrase for this git
    // operation if there was one pending to be stored.
    try {
      return await fn({
        DESKTOP_PORT: await trampolineServer.getPort(),
        DESKTOP_TRAMPOLINE_TOKEN: token,
        GIT_ASKPASS: '',
        // This warrants some explanation. We're configuring the
        // credential helper using environment variables rather than
        // arguments (i.e. -c credential.helper=) because we want commands
        // invoked by filters (i.e. Git LFS) to be able to pick up our
        // configuration. Arguments passed to git commands are not passed
        // down to filters.
        //
        // We're using the undocumented GIT_CONFIG_PARAMETERS environment

        // dependency or in a Python project commonly used to manage hooks
        // which isn't able to handle the blank environment variables we
        // need when using GIT_CONFIG_*.

        // See https://github.com/git/git/blob/ed155187b429a/config.c#L664
        GIT_CONFIG_PARAMETERS: `${gitEnvConfigPrefix}'credential.helper=' 'credential.helper=desktop'`,

        GIT_USER_AGENT: await GitUserAgent(),
        ...sshEnv,
      })
