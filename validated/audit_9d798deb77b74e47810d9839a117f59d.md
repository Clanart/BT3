### Title
Shared `CallDispatcher` forwards arbitrary `value`/`to` from its own balance on every cross-chain message, letting any user drain funds held by the dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
The external report's core defect is a low-level call-forwarding primitive (`mimicCall`) that lets an attacker control the `to` address and `value` of a *re-entrant* call, causing funds to move to an unintended recipient using someone else's balance. Hyperbridge's `CallDispatcher.dispatch()`, invoked from `HyperFungibleToken.onAccept` (and its Upgradeable/Wrapped variants) with fully attacker-supplied `Call[]` data, has the same broken invariant: it forwards `call.value` from the dispatcher's own balance to an arbitrary attacker-chosen `to`, with no ownership/authorization check tying the value to the message or its sender.

### Finding Description
`CallDispatcher.dispatch()` decodes an arbitrary `Call[]` array and executes each entry with a raw low-level call using the dispatcher's own balance: [1](#0-0) 

It has an unrestricted `receive()` that lets anyone deposit native tokens into it: [2](#0-1) 

The `dispatch()` entrypoint has **no access control** — any address (including any `IApp` that shares this dispatcher, or a call embedded in a cross-chain message) can invoke it with any `to`/`value`/`data`.

`HyperFungibleToken.onAccept()` (and `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleToken`, `WrappedHyperFungibleTokenUpgradeable`) automatically forwards the `data` field of every incoming cross-chain `Message` straight into `CallDispatcher.dispatch()`: [3](#0-2) 

Critically, the `data` field of `SendParams`/`Message` is **fully attacker-controlled** by whoever calls `send()` on the source chain — it is just user-supplied bytes that get ABI-decoded to `Call[]` on the destination: [4](#0-3) [5](#0-4) 

Because `onAccept` is only guarded by `onlyHost` (checking `msg.sender == host()`) and never validates the *contents* of `message.data`, and because `ICallDispatcher(_dispatcher).dispatch(message.data)` is called without forwarding any value (so `call.value` inside `dispatch()` is drawn from the dispatcher's pre-existing balance, not from the message), any legitimate, permissionless cross-chain message can instruct the shared `CallDispatcher` to send its entire native balance to an address of the attacker's choosing:
```solidity
(bool success, bytes memory result) = to.call{value: call.value}(call.data);
```
This mirrors the reported bug precisely: a shared, balance-holding forwarding contract executes a call whose `to` and `value` are attacker-supplied via a data path that was never intended to authorize spending of *that* contract's own funds.

### Impact Explanation
Any native token balance accumulated in the shared `CallDispatcher` (via its unrestricted `receive()`, via failed/partial calls, or via any other integrator app that funds it for composable "transfer-and-swap" flows) can be swept to an attacker-controlled address by simply calling the *public*, permissionless `send()` function on any `HyperFungibleToken`/`WrappedHyperFungibleToken` instance that shares the same `CallDispatcher`, with `data` encoding a `Call[]` of `{to: attacker, value: <dispatcher balance>, data: ""}`. This is unauthorized fund movement/loss of funds from a shared protocol contract, satisfying the "stealing or loss of funds" / "unauthorized execution" bounty criteria, and requires no relayer/prover/admin compromise — only a standard, honestly-relayed cross-chain message.

### Likelihood Explanation
Likelihood depends on the `CallDispatcher` actually holding a native-token balance at the time of the attack. Because `receive()` is unrestricted and the dispatcher is shared across multiple `HyperFungibleToken`-family deployments, any accidental transfer, refund, dust, or intentionally pre-funded amount (e.g., to subsidize destination-side swaps as part of the "transfer-and-swap" composable design) becomes an immediately sweepable target for the next dispatched message. The attack itself requires zero privileges and is triggerable via the standard, publicly documented `send(params.data)` flow.

### Recommendation
- Restrict `CallDispatcher.dispatch()` so that `call.value` can never draw from the dispatcher's own persistent balance — e.g., require the caller (the `IApp`) to forward exactly the value needed for that call (`payable`, and value must equal `msg.value` for that specific call), so the dispatcher never accumulates or exposes float.
- Remove the unrestricted `receive()`, or if funding is needed, scope funds per-caller/per-message rather than pooling them in a single shared contract.
- Alternatively, scope `CallDispatcher` per-app (one dispatcher instance per `HyperFungibleToken` deployment) so that no cross-application shared balance exists to drain.

### Proof of Concept
1. Assume `CallDispatcher` at address `D` has accumulated `X` wei of native token (via its permissive `receive()`, or leftover from a prior partial `dispatch()` call).
2. Attacker calls `HyperFungibleToken.send()` on the source chain with:
   - `params.to` = attacker's own address (or any valid recipient)
   - `params.amount` = 0 or minimal
   - `params.data` = `abi.encode([Call({to: attacker, value: X, data: ""})])`
3. The message is relayed normally through Hyperbridge (no malicious relayer needed — a legitimate relayer simply delivers this valid message).
4. On the destination chain, `HyperFungibleToken.onAccept()` passes `onlyHost` (called by the real host) and executes:
   ```solidity
   ICallDispatcher(_dispatcher).dispatch(message.data);
   ```
5. Inside `CallDispatcher.dispatch()`, the loop executes `attacker.call{value: X}("")`, sending the dispatcher's entire native balance to the attacker.
6. No check anywhere in `onAccept`, `HyperApp`, or `CallDispatcher` verifies that `call.value` originated from this specific message or sender — the entire shared balance is exposed to whoever dispatches next.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
