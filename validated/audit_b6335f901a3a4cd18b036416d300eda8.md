### Title
`InternalWithdraw` skips the aggregator-verification-signature check enforced by `Withdraw`, letting any caller who can reach the operator's gRPC front a payout without authorization - ([File: core/src/rpc/operator.rs])

### Summary
The operator gRPC service exposes two endpoints that both end up calling `Operator::withdraw()` and broadcasting a funded, real BTC payout transaction: `Withdraw` and `InternalWithdraw`. `Withdraw` enforces an ECDSA "verification signature" check against `aggregator_verification_address` when configured, but `InternalWithdraw` performs no such check at all, even though it triggers the exact same fund-and-broadcast side effect.

### Finding Description
`ClementineOperator::withdraw()` in [1](#0-0)  requires, when `self.operator.config.aggregator_verification_address` is set, that the caller supply a `verification_signature` that recovers to the configured aggregator address; if the signature is missing or invalid, the call is rejected with `ECDSAVerificationSignatureMissing`/`InvalidECDSAVerificationSignature`.

In contrast, `internal_withdraw()` performs no such check whatsoever before calling the identical `self.operator.withdraw(...)` state-changing function: [2](#0-1) 

The proto documentation for `InternalWithdraw` explicitly states it "is intended for operator's own use, so it doesn't include a signature from aggregator" [3](#0-2) , while `Withdraw`'s documentation makes clear the verification signature is the actual authorization gate for triggering a payout [4](#0-3) .

Both RPCs are registered on the same `ClementineOperator` gRPC service trait/server (`internal_withdraw` and `withdraw` sit side-by-side in the generated server trait) [5](#0-4) , meaning any client that can open a gRPC connection to the operator can invoke `InternalWithdraw` directly and bypass the authorization boundary that `Withdraw` was specifically built to enforce, so long as they have (or can obtain/replay) a valid `WithdrawParams` (withdrawal id, the user's off-chain `input_signature`, outpoint, output script/amount) that matches a withdrawal already registered on Citrea.

`Operator::withdraw()` itself only validates that the outpoint matches Citrea's registered withdrawal UTXO, that the payout is profitable for the operator, and that the schnorr `in_signature` is valid for the user's key over the payout sighash [6](#0-5)  - it does not know or care whether it was reached via the aggregator-gated `Withdraw` path or the ungated `InternalWithdraw` path. So the aggregator-verification-signature requirement is an application-layer authorization check that only one of the two equivalent entry points actually enforces.

This exactly matches the report's bug class ("incorrect selector/binding lets a caller reach a function meant for a different, authorized caller"): here, the binding broken is "the party the state-changing call is meant for" (the aggregator, gated by `Withdraw`) versus "the caller reaching the signing/broadcasting method" (anyone who can reach `InternalWithdraw` on the same service).

### Impact Explanation
When `aggregator_verification_address` is configured (the documented intended deployment configuration for controlling who can trigger operator payouts), `InternalWithdraw` provides an unauthenticated bypass: an unprivileged caller who reaches the operator's gRPC endpoint and possesses a valid withdrawal signature can force the operator to build, fund from its own wallet, and broadcast a payout transaction — the exact state-changing/broadcasting action `Withdraw`'s verification-signature gate was designed to prevent. This matches the "High - an unauthenticated state-changing or broadcasting call" impact category: it lets an unauthorized party trigger the operator's fund-committing payout flow outside of the aggregator's control, even though only the underlying signature-forgery/replay of a legitimate withdrawal is needed, not any operator/verifier/aggregator secret.

### Likelihood Explanation
Likelihood depends on network exposure of the operator's gRPC server (whether `InternalWithdraw`, despite being labeled "for operator's own use," is reachable over the same listener as `Withdraw` without a separate access control layer). Given both RPCs are defined on the identical service/trait with no differentiated authorization enforced at the transport or interceptor layer visible in the reviewed code (`core/src/rpc/mod.rs`, `core/src/rpc/interceptors.rs` show generic interceptors but no evidence of per-RPC ACL distinguishing `InternalWithdraw` from `Withdraw`), any client capable of connecting to the operator's RPC port can call it. This is analogous to the original report's core issue: an internal-only pathway is reachable by the wrong caller due to a missing binding check, causing the same effect as if the safeguard didn't exist.

### Recommendation
Either remove `InternalWithdraw` from the externally-reachable gRPC service (restrict it to a genuinely local-only transport, e.g. a Unix domain socket or loopback-bound listener), or make it enforce the same `aggregator_verification_address` check as `Withdraw` whenever that config is set, so the two entry points cannot diverge in authorization semantics for the same underlying state-changing action.

### Proof of Concept
1. Configure the operator with `aggregator_verification_address` set, so normal `Withdraw` calls require a valid EIP-712 ECDSA verification signature from the aggregator (per `recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>` in [7](#0-6) ).
2. Obtain (or otherwise acquire) a valid `WithdrawParams` for a real, Citrea-registered withdrawal, including the user's schnorr `input_signature` (which per the docs is "given to operators off-chain" and is not bound to a single specific operator or to the aggregator's authorization).
3. Instead of calling `Withdraw` (which would be rejected without the aggregator's verification signature), call `InternalWithdraw` directly with the same `WithdrawParams`: [2](#0-1) .
4. Observe that `internal_withdraw()` proceeds straight to `self.operator.withdraw(...)`, funds the payout transaction from the operator's wallet via RBF, and broadcasts it — with no aggregator authorization check performed, unlike the `Withdraw` path.

    async fn withdraw(
        &self,
        request: Request<WithdrawParamsWithSig>,
    ) -> Result<Response<RawSignedTx>, Status> {
        tracing::info!("Withdraw rpc called");
        let params = request.into_inner();
        let withdraw_params = params.withdrawal.ok_or(Status::invalid_argument(
            "Withdrawal params not found for withdrawal",
        ))?;
        let (withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount) =
            parser::operator::parse_withdrawal_sig_params(withdraw_params)?;

        tracing::warn!(
            "Parsed withdraw rpc params, withdrawal id: {:?}, input signature: {:?}, input outpoint: {:?}, output script pubkey: {:?}, output amount: {:?}, verification signature: {:?}", withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount, params.verification_signature
        );

        // if verification address is set in config, check if verification signature is valid
        if let Some(address_in_config) = self.operator.config.aggregator_verification_address {
            let verification_signature = params
                .verification_signature
                .map(|sig| {
                    PrimitiveSignature::from_str(&sig).map_err(|e| {
                        Status::invalid_argument(format!("Invalid verification signature: {e}"))
                    })
                })
                .transpose()?;
            // check if verification signature is provided by aggregator
            if let Some(verification_signature) = verification_signature {
                let address_from_sig =
                    recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>(
                        withdrawal_id,
                        input_signature,
                        input_outpoint,
                        output_script_pubkey.clone(),
                        output_amount,
                        verification_signature,
                    )?;

                // check if verification signature is signed by the address in config
                if address_from_sig != address_in_config {
                    return Err(BridgeError::InvalidECDSAVerificationSignature).map_to_status();
                }
            } else {
                // if verification signature is not provided, but verification address is set in config, return error
                return Err(BridgeError::ECDSAVerificationSignatureMissing).map_to_status();
            }
        }
