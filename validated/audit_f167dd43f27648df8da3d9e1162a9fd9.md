## Title
`ArbWomUp.incentiveDeposit` uses raw `IERC20.transfer` for USDT reward, causing a permanent DoS of the WOM→USDT incentive/airdrop deposit path - ([File: wombat/ArbWomUp.sol])

### Summary
`ArbWomUp.incentiveDeposit` rewards callers with USDT using the non-standard `IERC20(usdt).transfer(...)` call instead of OpenZeppelin's `safeTransfer`, even though the contract already imports and uses `SafeERC20` elsewhere in the same file.

### Finding Description
`ArbWomUp` is explicitly built to handle real USDT — the state variable is named `usdt`, the event is `USDTRewarded`, and the contract-level comment states "reward wom converter with USDT" for the "arbitrum Airdrop" [1](#0-0) . Despite this, and despite the contract already declaring `using SafeERC20 for IERC20;` and correctly using `safeTransferFrom` for WOM deposits, the USDT reward payout in `incentiveDeposit` uses the raw, unchecked `transfer` call: [2](#0-1) 

Mainnet USDT's `transfer` function does not return a `bool` at all, which is incompatible with Solidity's ABI decoding when the caller (via the `IERC20` interface) expects a `bool` return value. Any call through the standard `IERC20.transfer` signature against real USDT will revert during return-data decoding, since USDT contract returns no data for `.transfer`, and the calling context (through the `IERC20` interface) tries to decode a `bool` from empty returndata.

### Impact Explanation
Because the raw `transfer` call is made unconditionally whenever `rewardToSend > 0`, and `getRewardAmount` in the deposit flow will be non-zero for any depositor once tier multipliers are configured, any ordinary wallet calling `incentiveDeposit` with real USDT as the `usdt` token will have its entire transaction revert — this reverts the `_deposit` call as well (WOM transferFrom, `userWOMDeposited` update, `totalAccumulated` update). This is a full, permanent denial-of-service of the incentive/airdrop deposit function for as long as USDT (or any token with the same non-boolean-return quirk) is configured, blocking all unprivileged users from participating in the intended WOM airdrop conversion program.

### Likelihood Explanation
This triggers deterministically for any ordinary user calling `incentiveDeposit` whenever the reward ratio is turned on (i.e., `rewardMultiplier` populated) and `usdt` points to the real mainnet USDT contract, which is exactly the scenario the contract is designed and named for. No privileged action or special conditions are required beyond normal owner configuration (`setMultiplier`) that is part of intended contract operation.

### Recommendation
Replace the raw `IERC20(usdt).transfer(msg.sender, rewardToSend);` call in `incentiveDeposit` with `IERC20(usdt).safeTransfer(msg.sender, rewardToSend);`, consistent with the `SafeERC20` usage already present elsewhere in the same contract (e.g., `_deposit`'s `safeTransferFrom`).

### Proof of Concept
1. Owner deploys `ArbWomUp` with `usdt` set to the real USDT token address and calls `setMultiplier` to enable reward tiers.
2. An ordinary user calls `WOM.approve(arbWomUp, amount)` then `incentiveDeposit(amount)`.
3. Inside `incentiveDeposit`, `getRewardAmount` returns a non-zero `rewardToSend`, so `IERC20(usdt).transfer(msg.sender, rewardToSend)` is executed [3](#0-2) .
4. Since real USDT's `transfer` returns no boolean, Solidity's ABI decoding of the return value reverts, reverting the whole `incentiveDeposit` transaction — permanently blocking any user from depositing WOM for the airdrop/incentive program.
