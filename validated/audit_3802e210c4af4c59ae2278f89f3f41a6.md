Based on my investigation, the strongest local analog to the Skale rounding-error bug class ("decomposed values that should sum consistently but the code doesn't enforce it, leading to fund loss when an assumption breaks") is in the same-chain partial-fill escrow accounting of `IntrinsicIntents.sol`.

### Title
Per-token escrow bucket combined with per-index "final fill drains full balance" logic can steal/lock escrow across indices sharing an input token - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` computes, for each output index `i`, either a proportional escrow release or — once that index's cumulative fill equals `totalRequired` — releases the **entire remaining balance** of `_orders[commitment][token]` for that token, instead of the proportional share owed to that specific index. [1](#0-0) 

### Finding Description
`_orders` is a mapping keyed only by `(commitment, token address)` — it is not indexed by the position of the input in the order's `inputs` array: [2](#0-1) 

In `_fillSameChain`, the escrow release for output index `i` is computed as:
```solidity
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [3](#0-2) 

This branch is evaluated **per output index**, independently of the overall `isFullyFilled` flag which only gates whether the order is finalized and calldata executed — it does not gate which escrow amount is pulled per index. The "full remaining balance" branch implicitly assumes each token address in `order.inputs` appears at exactly one index, so that the entire live balance for that token is exactly what backs that one obligation. Nothing in `IntrinsicIntents.sol` or `IntentsBase.sol` enforces uniqueness of `order.inputs[i].token` across indices. If an order's `inputs` array contains the same token address at two different indices (e.g., two separate escrow legs both denominated in USDC, backing two different output legs), their deposits collapse into the *same* `_orders[commitment][token]` bucket at placement time (the mapping has no index dimension), yet the fill logic treats "my index just hit 100%" as license to sweep the *entire* bucket, including the amount that was meant to back the still-unfilled index.

This mirrors the Skale bug class precisely: multiple values (`_orders[commitment][token]`, and the "per-index proportional share" implied by `order.inputs[i].amount`) are supposed to be consistent decompositions of the same total, but the code doesn't preserve that invariant, and one code path (the "final release" branch) silently assumes an invariant ("this bucket == this index's remaining obligation") that can be false.

### Impact Explanation
- The solver who happens to complete the fill for the index whose cumulative amount reaches `totalRequired` first can receive more USDC (or whichever token repeats) than the proportional amount owed for that index — up to the entire multi-leg escrow balance — while providing tokens for only one leg's output.
- A subsequent solver attempting to fill the remaining leg (same repeated token) will find `_orders[commitment][token]` already drained to zero, causing `_withdraw` to revert with `UnknownOrder()` (escrowed == 0 check) — the order can never be completed, permanently locking the user's remaining input tokens with no unfilled leg possibly ever finalized normally, or the second solver's fulfilled output tokens sent to the user go uncompensated.
- This is unauthorized transfer of escrowed user funds to the wrong beneficiary/wrong amount and/or permanent fund lock — both are in-scope impacts (stealing/loss of funds, transaction manipulation).

### Likelihood Explanation
Exploitability requires that a same-chain order can legitimately contain two `inputs` entries referencing the same token address at different indices, matched 1:1 to two different `outputs` entries. I was not able to confirm from the code reviewed within the available tool budget whether `placeOrder`/order-validation logic in `IntentGatewayV2.sol` explicitly rejects duplicate token addresses within `order.inputs`. If such a uniqueness check exists elsewhere, the exposure is reduced to only same-index accounting (already covered/fixed per the "rounding dust" tests I found). If no such check exists — which is the normal case for an unconstrained-schema order structure — any user or solver colluding with the order structure (a user, an unprivileged party, can construct their own order this way) can trigger the miscounted release, making this a realistically reachable, no-privilege-required path.

### Recommendation
- Track escrow per `(commitment, index)` rather than per `(commitment, token)`, or explicitly disallow duplicate token addresses across `order.inputs` at `placeOrder` time.
- In the "final release" branch, cap the amount released to the proportional/expected remaining amount for that specific index rather than sweeping the entire `_orders[commitment][token]` balance, and only allow the "collect true residual dust" behavior after verifying no other index still references the same token with outstanding obligations.

### Proof of Concept
1. User places a same-chain order with `inputs = [{USDC, 600e6}, {USDC, 400e6}]`, `outputs = [{DAI, 600e18}, {ETH, 1e18}]` (index-aligned). Total escrowed in `_orders[commitment][USDC]` = 1000e6 (single bucket, per `IntentsBase.sol:140`).
2. Solver A fully fills output index 0 (600 DAI). `amountFilled[0] == totalRequired[0]` triggers the full-balance branch: `escrowedAmount = _orders[commitment][USDC] = 1000e6`, all of which is transferred to Solver A even though only 600e6 was proportionally owed for index 0.
3. `_orders[commitment][USDC]` is now 0.
4. Solver B attempts to fill output index 1 (1 ETH). On completion, the same full-balance branch executes for index 1: `escrowedAmount = _orders[commitment][USDC] = 0`. `_withdraw` reverts with `UnknownOrder()` — Solver B cannot be paid, and the order can never finalize normally, permanently stranding the arrangement while Solver A received 400e6 USDC beyond entitlement.
