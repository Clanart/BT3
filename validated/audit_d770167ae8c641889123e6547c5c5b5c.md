Based on my investigation, I found a genuine analog in the Copilot merge-conflict resolution feature that mirrors the broken-invariant pattern from the report: content is spliced back into a repository file based on a model-controlled ordering/index rather than a verified correspondence to the exact conflict block it claims to resolve.

### Title
Silent corruption of committed file content due to positional (not content-verified) splicing of AI-suggested hunk resolutions - (File: app/src/lib/copilot-conflict-resolution.ts)

### Summary
`reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` splices Copilot's per-hunk `resolvedContent` into the original conflicted file "matched by order, not by line number" [1](#0-0) . The only pre-splice validation performed by `validateResolutionPaths` checks that returned file paths match expected paths and that the *count* of hunks per file matches the expected count [2](#0-1) . There is no check that a given `IHunkResolution` actually corresponds to the specific conflict block (`oursContent`/`theirsContent`/`baseContent`) it is being substituted for — the mapping is purely "the Nth resolution in the array goes into the Nth conflict marker block found on disk." This is structurally the same class of bug as the reported issue: an index (`collateralIndex` there, hunk position here) is trusted to correctly identify the target entity (an accepted collateral token there, a specific conflict block here) without validating that they actually match.

### Finding Description
The pipeline is: `buildConflictContext` extracts hunks from disk in file order via `extractConflictHunks` [3](#0-2) , these are sent to Copilot as numbered "Conflict N of M" blocks in the prompt [4](#0-3) , and the model returns a JSON array of `hunks` per file. `validateResolutionPaths` only verifies `resolution.hunks.length !== expectedCount` [5](#0-4) , then `reassembleResolvedFile` walks the file, finds each `<<<<<<<`…`=======`…`>>>>>>>` block, and inserts `hunkResolutions[hunkIndex]` in strict incrementing order [6](#0-5) . If the model returns the correct number of hunks but in a different order than they appear in the source file (a plausible LLM failure mode, especially for files with several structurally similar conflict blocks, or if the model's JSON generation reorders array elements), the resolution intended for conflict block 3 gets written into conflict block 1's location instead. Since the file still has the correct number of hunks and paths, none of the existing guards (`validateResolutionPaths`, the "still contains conflict markers" check) will detect this mismatch [7](#0-6) .

The GitHub Desktop analog to the Treasury `invest` bug's "attacker controls the collateral index" is here "the model (an external/untrusted generative component processing attacker-influenced repository content) controls array ordering," and the "missing check that collateralToken matches the strategy's expected token" is here "missing check that a hunk's resolved content matches the specific conflict block's ours/theirs signature before splicing."

### Impact Explanation
If mis-ordered splicing occurs, the reassembled file is written to disk and can be staged/committed by the user believing it reflects Copilot's stated per-hunk reasoning. This is exactly the "silent corruption of what the user commits or pushes" impact category: the user's merge commit would silently contain the wrong resolution for one or more conflict regions (e.g., swapping which side's logic wins for two similar-looking `if` blocks), with no error, warning, or diff-level indicator distinguishing this from a correct resolution. Because the conflicting content originates from a git merge/rebase against a remote branch or PR that could itself be attacker-influenced (e.g., an attacker crafts confusingly similar-structured conflicting hunks in a branch/PR designed to increase the odds of hunk-order confusion), this touches the "attacker controls a cloned/fetched repository" surface named in the valid-impact criteria.

### Likelihood Explanation
Likelihood is **low-to-moderate** and depends on LLM output reliability rather than a directly attacker-triggerable mechanical flaw — I could not verify from the code alone whether Copilot's structured-output mode strictly preserves array order (this would require testing against the live model, which I don't have access to). The count-based validation reduces but does not eliminate the risk. This differs from the original report's determinism (a straightforward missing on-chain check); here the "check" that is missing would need to compare hunk content/context rather than just count, which is not standard practice in this kind of AI-diff-application code, but the actual reliability of the underlying model's ordering behavior is unverified.

### Recommendation
- **Short term:** In `validateResolutionPaths` (or a new validation step before `reassembleResolvedFile`), require the model to echo back an identifying anchor for each hunk (e.g., a hash or truncated snippet of `oursContent`/`theirsContent`) and verify it matches the corresponding on-disk hunk before splicing, rather than relying solely on positional order and count.
- **Long term:** Consider having the model return hunk resolutions keyed by a hunk ID assigned during context extraction (in `extractConflictHunks`), and thread that ID through the prompt and response schema, eliminating positional coupling entirely.

### Proof of Concept
I cannot produce a concrete, deterministic PoC in this environment because triggering the bug requires the Copilot model to return hunk resolutions in an order that differs from file order while still passing the count check — a behavior dependent on the live model's structured-output fidelity, which is outside the scope of static code analysis. The code path described above is confirmed and reproducible in principle: construct a file with ≥2 structurally similar conflict hunks, mock `parseCopilotConflictResolution`'s output to return valid, correctly-counted hunks but in reversed order for that file, and call `reassembleResolvedFile` — the reassembled file will contain resolution content transposed between conflict blocks, with no validation error raised, as can be verified against the logic at [8](#0-7)  and [2](#0-1) .

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }

    // The ours marker line is at oursStart - 1
    const markerStart = oursStart - 1
    const contextStart = Math.max(0, markerStart - contextLines)
    const contextEnd = Math.min(lines.length - 1, hunkEnd + contextLines)

    // Clamp context to not include conflict markers from adjacent hunks
    const contextBeforeLines: Array<string> = []
    for (let j = markerStart - 1; j >= contextStart; j--) {
      if (isConflictMarker(lines[j])) {
        break
      }
      contextBeforeLines.unshift(lines[j])
    }

    const contextAfterLines: Array<string> = []
    for (let j = hunkEnd + 1; j <= contextEnd; j++) {
      if (isConflictMarker(lines[j])) {
        break
      }
      contextAfterLines.push(lines[j])
    }

    const contextBefore = contextBeforeLines.join('\n')
    const contextAfter = contextAfterLines.join('\n')

    hunks.push({
      oursContent: oursLines.join('\n'),
      theirsContent: theirsLines.join('\n'),
      baseContent: hasBase ? baseLines.join('\n') : null,
      contextBefore,
      contextAfter,
    })
  }

  return hunks
}
