### Title
Unauthenticated `challenger_evm_address` in `create_challenge_txhandler` allows reimbursement theft on correct challenges - (File: core/src/builder/transaction/challenge.rs)

### Summary
`create_challenge_txhandler` embeds a `challenger_evm_address` into an OP_RETURN output of the Challenge transaction with no cryptographic binding to whoever actually produces the spend of `KickoffTx:Challenge`. Anyone able to construct a valid script-spend witness for that UTXO (the `NormalSignatureKind::Challenge` / `SpendPath::ScriptSpend(0)` input) can substitute their own EVM address, diverting Citrea's later reimbursement for a correct challenge away from the party that actually detected the misbehavior.

### Finding Description
The claimed binding is: `challenger_evm_address` embedded in the Challenge tx OP_RETURN == the identity of whoever incurred the cost of correctly challenging the operator.

In `create_challenge_txhandler` [1](#0-0) , the function takes `challenger_evm_address: Option<EVMAddress>` as a plain parameter and pushes its raw bytes into an `op_return_txout`, with zero relationship to the Taproot script-path signature used to spend the `Challenge` input (`SpendPath::ScriptSpend(0)`, `NormalSignatureKind::Challenge`). The signature over the input only commits to the script and the transaction's other committed fields per its sighash flags — it never binds to or authenticates the OP_RETURN payload's origin as "the entity that supplied that specific EVM address."

The caller in `creator.rs` shows the intended usage: the EVM address is meant to be derived from the local `context.signer` performing the reimbursement construction [2](#0-1) . This means whichever verifier/party actually builds and signs the Challenge transaction supplies its own address by convention, but nothing in the protocol enforces that only the "true" challenger can produce a spend of the Challenge UTXO with their own chosen address instead of someone else's.

Because the OP_RETURN field is not signed over in any address-specific way (i.e., it's not a preimage/commitment tied to a specific pubkey, nor validated against `SECP.verify_schnorr` for that address), any party who can supply the same script-spend witness needed to unlock `UtxoVout::Challenge` can freely rebuild the transaction with an arbitrary `challenger_evm_address`, producing a syntactically and cryptographically valid Challenge tx that still spends the same Challenge script path, just with a substituted reimbursement target.

### Impact Explanation
If exploited, when the challenge is later proven correct, Citrea would reimburse the attacker's chosen EVM address from the operator's collateral rather than the entity that genuinely detected and proved the misbehavior — this is a reimbursement credited to the wrong party, matching the "operator reimbursed/challenger credited incorrectly" analog of the Critical impact category (funds intended for one party diverted to an unrelated address). This is repeatable per challenge and per kickoff/operator, since the flaw is structural in `create_challenge_txhandler` and not tied to a specific deposit.

### Likelihood Explanation
Exploitability is gated entirely by the precondition explicitly noted in the question: producing a valid script-spend witness for `KickoffTx:Challenge` (`ScriptSpend(0)`) is required, and based on `create_kickoff_txhandler` in `operator_reimburse.rs` [3](#0-2) , that Challenge-path script involves keys/timelocks that are not trivially satisfiable by an arbitrary unprivileged attacker — I was not able to fully verify within available context exactly which key(s) gate script index 0 for the `Challenge` UTXO (this needs further tracing of `UtxoVout::Challenge`'s exact vout mapping and the applicable N-of-N/operator signature requirements, which I could not fully confirm from the indexed files before running out of iterations). If the script-spend requires a valid N-of-N (verifier) MuSig2 signature or an operator signature that only becomes available once a legitimate challenge is already in flight, an unprivileged outside attacker (per the threat model) cannot independently produce this witness, which would reduce this to a self-inflicted/verifier-only issue rather than an attacker-exploitable one. Given the explicit note in the question itself ("this specific spend path may require privileged data"), and my inability to confirm within the tool budget that an unprivileged attacker (as strictly defined in this audit's rules) can independently produce that witness, I cannot fully validate that this is reachable by the defined attacker class rather than only by a colluding/malicious verifier or a race between honest challengers.

### Recommendation
Bind the `challenger_evm_address` to the actual spender/broadcaster of the Challenge input cryptographically — e.g., have the address be committed as part of the message hashed into the script-spend signature (so any address substitution invalidates the existing signature), or require the reimbursement address to be derived deterministically from a pubkey that is verified as part of the script-spend (comparable to how `operator_reimbursement_address` should ideally be similarly bound). At minimum, ensure the entity constructing and broadcasting the Challenge tx is the same one whose script-spend key is checked against the OP_RETURN-embedded address, closing the gap between "who can produce the witness" and "who gets reimbursed."

### Proof of Concept
Not able to produce a fully validated `cargo test` given the unresolved precondition above. A concrete PoC would need to: (1) determine the exact witness/signature required to satisfy `UtxoVout::Challenge`'s `ScriptSpend(0)` from `operator_reimburse.rs`'s kickoff output construction and `states/kickoff.rs`/`states/matcher.rs` challenge-detection logic; (2) if that witness is obtainable by an unprivileged attacker (not requiring N-of-N verifier cooperation), build one valid Challenge witness, then call `create_challenge_txhandler` twice with the same `kickoff_txhandler`/`operator_reimbursement_address` but different `challenger_evm_address` values, reuse the same witness on the second, and assert both transactions are accepted by `test_mempool_accept` with differing OP_RETURN payloads and no signature mismatch. This last verification step was not completed due to tool-call exhaustion.

pub fn create_challenge_txhandler(
    kickoff_txhandler: &TxHandler,
    operator_reimbursement_address: &bitcoin::Address,
    challenger_evm_address: Option<EVMAddress>,
    paramset: &'static ProtocolParamset,
) -> Result<TxHandler, BridgeError> {
    let mut builder = TxHandlerBuilder::new(TransactionType::Challenge)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::Challenge,
            kickoff_txhandler.get_spendable_output(UtxoVout::Challenge)?,
            SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_output(UnspentTxOut::from_partial(TxOut {
            value: paramset.operator_challenge_amount,
            script_pubkey: operator_reimbursement_address.script_pubkey(),
        }));

    if let Some(challenger_evm_address) = challenger_evm_address {
        builder = builder.add_output(UnspentTxOut::from_partial(op_return_txout(
            challenger_evm_address.0,
        )));
    }
