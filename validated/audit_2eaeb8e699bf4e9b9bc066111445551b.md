### Title
Unbounded `_minMGPRec` allows AMM price-manipulation to drain MGP bonus reserve via `incentiveDeposit(bullMode=true)` - (File: wombat/ArbWomUp2.sol)

### Summary
`incentiveDeposit` lets any caller set `_minMGPRec` to any value (including `0`) when routing their `busd` reward through `_bullMGP`, which performs a spot swap on `ROUTER.swapExactTokensForTokens` with no oracle/TWAP check. An attacker can flash-loan-manipulate the BUSD/MGP pool immediately before calling `incentiveDeposit`, causing the swap to return an inflated `amounts[1]`, which is then multiplied by `bullBonusRatio` and locked into `vlMGP` on the attacker's behalf, extracting more MGP than their `busd` reward is fairly worth.

### Finding Description
`incentiveDeposit` computes `rewardToSend` (busd) via `getRewardAmount` and, when `_bullMode == true`, forwards it to `_bullMGP`: [1](#0-0) 

`_bullMGP` swaps the busd amount for MGP at the router's current spot price, with `_minRec` fully attacker-controlled, and then computes the amount to lock as `amounts[1] * (DENOMINATOR + bullBonusRatio) / DENOMINATOR`, approving and locking that amount into `vlMGP` for the caller: [2](#0-1) 

There is no minimum enforced by the contract itself (it trusts the caller-supplied `_minRec`) and no TWAP/oracle sanity check on the swap output. Because `mgpAmountToLcok` is a function of `amounts[1]` (the actual swapped-out MGP), any manipulation of the pool that increases `amounts[1]` for the same `busd` input directly increases the MGP amount locked for the attacker, including the bonus multiplier applied on top. `nonReentrant`/`whenNotPaused` do not mitigate price manipulation—they only prevent reentrancy and enforce pause state, neither of which stops a flash-loan sandwich around the call.

However, this depends entirely on `ROUTER` being a manipulable, thin-liquidity AMM pool (e.g., PancakeSwap V2 pair) at the time of the call. I could not verify from the indexed files what pool/liquidity backs `busd`/`mgp` on the deployed `ROUTER`, nor confirm the exact `VLMGP.lockFor` implementation (whether it pulls tokens via `transferFrom` from `ArbWomUp2` or performs other checks), since `VLMGP.sol`'s `lockFor` body was not retrievable via search in this session. This introduces uncertainty about whether `ArbWomUp2` in practice pre-funds a large-enough MGP "bonus reserve" balance that would make this attack profitable beyond gas/flash-loan fees, and whether the router/pool pair actually has exploitable low liquidity in the deployed environment. This is a protocol-design/parameter concern (using spot-price AMM swaps with attacker-controlled slippage tolerance) rather than a pure external-oracle-manipulation issue, since the contract itself fails to enforce any minimum acceptable rate — it is the root cause enabling the exploit, not merely a third-party oracle bug.

### Impact Explanation
If exploitable, the attacker extracts MGP disproportionate to the busd reward entitlement, draining the pre-funded MGP "bonus" reserve held by `ArbWomUp2` and/or arbitraging the router pool's liquidity providers. This falls under theft/permanent loss of protocol-held yield reserves (the bonus-MGP stash intended to reward genuine WOM depositors) if the preconditions (thin liquidity pool, no minMGPRec enforcement) hold.

### Likelihood Explanation
Feasibility hinges on unverifiable preconditions: (1) the `ROUTER`/`busd`-`mgp` pair set via `setup()` must have exploitably low liquidity relative to `rewardToSend`, and (2) the pre-funded MGP balance in `ArbWomUp2` must be non-trivial for the bonus to be worth extracting. Since this is an admin-configured router/pool (owner sets `ROUTER` via `setup`), and Wombat/Magpie deployments typically route through deep liquidity pools (e.g., PancakeSwap main busd/mgp pair), the attack's economic viability is uncertain without on-chain liquidity data, which is outside this index's scope. The core code-level flaw (unenforced minimum output, spot-price swap) is real and reachable by any unprivileged caller, but whether it's a *repeatable, profitable* exploit against the actual deployed pool cannot be confirmed from the available files.

### Recommendation
Do not trust caller-supplied `_minMGPRec` as the sole protection; enforce a contract-computed minimum acceptable output based on a manipulation-resistant price reference (e.g., a TWAP oracle or a chainlink-derived busd/mgp rate), and/or cap `_minMGPRec` to be no lower than a protocol-computed floor. Additionally, consider removing the caller's ability to set `_minMGPRec` entirely and instead deriving it internally from a trusted price source.

### Proof of Concept
Foundry fork test plan (not verifiable to completion given missing liquidity/config data):
1. Fork BSC mainnet at a block where `ArbWomUp2` is deployed and configured (`busd`, `mgp`, `vlMGP`, `ROUTER`, `bullBonusRatio` set).
2. Have attacker acquire enough WOM to trigger a `rewardToSend` from `getRewardAmount`.
3. Flash-loan a large amount of `busd` (or `mgp`) and swap it through the same router pool used by `ROUTER` to skew the busd/mgp price so that MGP becomes artificially cheap in busd terms.
4. Call `incentiveDeposit(_amount, 0, true)` from the attacker address.
5. Immediately after, reverse the flash-loan swap to restore the pool price and repay the flash loan.
6. Assert: MGP locked into `vlMGP` for the attacker (`mgpAmountToLcok`) is significantly higher than what would result from calling with an unmanipulated/pre-attack price, and quantify whether the profit (locked MGP fair value minus flash loan fees/gas) is positive — confirming actual extractable value beyond the attacker's fair busd-reward entitlement.

Note: this PoC requires concrete on-chain liquidity/router data not available in the indexed repository to fully validate profitability; the structural vulnerability (missing internal minimum-output enforcement in `_bullMGP`) is confirmed in code, but real-world exploitability is unconfirmed.

    function incentiveDeposit(
        uint256 _amount, uint256 _minMGPRec, bool _bullMode
    ) external _checkAmount(_amount) whenNotPaused nonReentrant {
        if (_amount == 0) return;

        uint256 rewardToSend = this.getRewardAmount(_amount, msg.sender);
        _deposit(_amount);
        claimedReward[msg.sender] += rewardToSend;
        
        if (_bullMode) {
            _bullMGP(rewardToSend, _minMGPRec, msg.sender);
        } else {
            IERC20(busd).transfer(msg.sender, rewardToSend);
            emit BUSDRewarded(msg.sender, rewardToSend);
        }
    }

    function _bullMGP(uint256 _busdAmount, uint256 _minRec, address _account) internal {
        IERC20(busd).safeApprove(address(ROUTER), _busdAmount);
        
        address[] memory path = new address[](2);
        path[0] = busd;
        path[1] = mgp;
        uint256[] memory amounts = ROUTER.swapExactTokensForTokens(
            _busdAmount,
            _minRec,
            path,
            address(this),
            block.timestamp
        );

        uint256 mgpAmountToLcok = amounts[1] * (DENOMINATOR + bullBonusRatio) / DENOMINATOR; // get bull mode bonus
        IERC20(mgp).approve(address(vlMGP), mgpAmountToLcok);
        vlMGP.lockFor(mgpAmountToLcok, _account);

        emit VLMGPRewarded(_account, _busdAmount, mgpAmountToLcok);
    }
