### Title
Attacker-controlled `n` field drives `Vec::with_capacity` before parameter validation, enabling memory-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes a `u16` participant count `n` from untrusted bytes and immediately allocates `Vec::with_capacity(usize::from(n))` for `Interpolation::Constant` coefficients — before `ThresholdParams::new(t, n, i)` is ever validated. This mirrors CVE-2016-6308's bug class (allocation performed before a length field is sanity-checked), allowing an unprivileged party who can feed bytes to `ThresholdKeys::read` to force allocations of ~2 MB+ per message with only a handful of input bytes.

### Finding Description
In `ThresholdKeys::read`, after the curve-ID check, `t`, `n`, and `i` are read as raw `u16`s with no validation: [1](#0-0) 

The interpolation tag is then read, and for `0` (`Interpolation::Constant`), a `Vec` is pre-allocated with capacity `n`: [2](#0-1) 

`Vec::with_capacity(65535)` commits heap memory proportional to `n * size_of::<C::F>()` (≥ 32 bytes/scalar, so ≥ 2 MB) purely from a 2-byte attacker-controlled field. Only afterward is the secret share read and `n` verification-share points parsed, and only at the very end is `ThresholdParams::new(t, n, i)` called to validate `t <= n`, `i <= n`, etc.: [3](#0-2) 

The same unvalidated `n` also bounds the `verification_shares` read loop, though that fails fast on EOF — the `with_capacity` allocation is the alloc-before-check defect: it succeeds even when the input is truncated immediately after the interpolation byte. The `n` value is never checked against the actual remaining input length nor against any sane bound before allocation.

### Impact Explanation
Any component that accepts a serialized `ThresholdKeys` blob from a less-trusted source (key-share exchange, recovery, reserialization of stored keys after an upgrade) can be driven to allocate ~2 MB per message with an input of only ~20 bytes — an amplification factor on the order of 10⁵. Repeated submissions exhaust heap memory and crash the process, a denial of service matching the CVE-2016-6308 pattern. Since `n` is a `u16`, a single allocation is bounded, but the per-byte amplification and repeatability make it a practical remote memory-consumption DoS wherever this deserializer is exposed to untrusted input.

### Likelihood Explanation
`ThresholdKeys::read` is a public, explicitly listed deserialization API in the in-scope `dkg` crate; integrations that transmit or persist threshold key material (DKG recovery, key handoff between coordinator and processor) feed it externally influenced bytes. The attacker only needs to control the byte stream — no valid key, signature, or protocol participation is required. Exploitation requires a caller that reads keys from a peer- or network-supplied buffer rather than only from local trusted storage, which limits it to Medium rather than High severity.

### Recommendation
Validate `t`, `n`, and `i` via `ThresholdParams::new` *before* any length-dependent allocation, and replace `Vec::with_capacity(n)`/`HashMap` growth with a push-based loop bounded by `n` only after validation (allocation proportional to already-consumed input is inherent to `read_exact` failing on EOF). At minimum:

```rust
let params = ThresholdParams::new(t, n, i).map_err(io::Error::other)?;
// then deserialize interpolation/share/shares using params.n()
```

### Proof of Concept
```rust
// Conceptual: feed a truncated blob to ThresholdKeys::<C>::read
let mut buf = vec![];
buf.extend(&(C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(&0u16.to_le_bytes());        // t (invalid, never checked before alloc)
buf.extend(&u16::MAX.to_le_bytes());    // n = 65535 -> with_capacity(65535)
buf.extend(&1u16.to_le_bytes());        // i
buf.push(0);                            // Interpolation::Constant
// EOF immediately: ~2 MB heap allocation already committed before error
let _ = ThresholdKeys::<C>::read(&mut buf.as_slice());
```

Each such short message forces a `n * size_of::<C::F>()` allocation at `crypto/dkg/src/lib.rs:608` even though deserialization fails moments later on EOF.
