### Title
Permissionless spend of an on-chain "mirror" coin injects attacker-controlled URLs that DataLayer automatically fetches over HTTP with no destination filtering, enabling post-authentication SSRF - (File: chia/data_layer/download_data.py)

### Summary
DataLayer's mirror mechanism lets any spend-bundle submitter attach arbitrary URLs to *any* store's `launcher_id` via a permissionless, unowned puzzle. Any full node/wallet that tracks that `launcher_id` (owners of the store, or any DL client that has `dl_track_new`'d it) will pick up those URLs during periodic sync and issue outbound `aiohttp` GET requests to them with no scheme restriction, no allow-list, and no RFC1918/link-local/loopback filtering — the same root-cause pattern as the Lemur CRL/OCSP SSRF (fetch a URL taken from attacker-supplied data with no destination validation).

### Finding Description
`create_new_mirror()` builds a standard coin spend that sends value to `create_mirror_puzzle().get_tree_hash()` (`P2_PARENT.curry(1)`) with a memo of `[launcher_id, *urls]`: [1](#0-0) 

Critically, nothing in this path (or in the RPC layer that exposes `dl_new_mirror`) checks that the caller owns or controls the `launcher_id` being targeted — it's just a `CREATE_COIN` condition with an arbitrary memo: [2](#0-1) 

Because this is a plain `CREATE_COIN` to a well-known puzzle hash with an attacker-chosen memo, an attacker does not even need to use the wallet RPC — they can construct and broadcast a raw spend bundle from any coin they own that creates a coin to `MIRROR_PUZZLE_HASH` with `memos = [victim_launcher_id, "http://169.254.169.254/", ...]`. Mempool/consensus validation has no concept of "who owns this DataLayer store" — it only requires a valid signature over the spender's own coin.

Any node that has ever tracked that `launcher_id` (its own DL stores, or any store it explicitly subscribed to for replication) will observe the new coin in `coin_added`, decode the memo via `get_mirror_info`, and — as long as `is_launcher_tracked(launcher_id)` is true — persist the attacker's URLs as a legitimate `Mirror` record with no validation of the URL's destination: [3](#0-2) [4](#0-3) 

`DataLayer.update_subscriptions_from_wallet()` then pulls these mirror URLs directly from the wallet and feeds them into the local subscription server list with no filtering: [5](#0-4) 

During the periodic sync loop, `fetch_and_validate()` iterates these `servers_info` (populated from attacker-controlled mirror URLs) and calls `insert_from_delta_file()` → `download_file()` → `http_download()`, which issues an unrestricted `aiohttp.ClientSession().get(server_info.url + "/" + filename, ...)`: [6](#0-5) [7](#0-6) 

There is no scheme allow-list, no hostname allow-list, and no filtering of RFC1918/loopback/link-local/IMDS addresses at any point in this chain — exactly the missing control described in the Lemur advisory (`crl_verify`/`ocsp_verify` fetching attacker-influenced URLs with `requests.get`/`openssl ocsp -url` and no destination validation).

### Impact Explanation
Any coin owner (an unprivileged spend-bundle submitter with no operator role, no wallet RPC access, and no relationship to the targeted DataLayer store) can force any node that tracks a given `launcher_id` to issue outbound HTTP requests to attacker-chosen internal/loopback/link-local destinations (e.g., cloud instance-metadata endpoints, internal RPC ports, RFC1918 services) purely by broadcasting a spend bundle. This is a genuine post-consensus, coin-triggered SSRF: it requires no authentication to the target DL node at all, only knowledge of a public `launcher_id`, which is on-chain information. Repeated/periodic execution occurs automatically via `periodically_manage_data()` without any operator interaction after the first sync cycle, and probing responses/timing can be inferred through subsequent `server_misses_file`/ban behavior, mirroring the Lemur report's characterization of internal network reconnaissance and IMDS access.

### Likelihood Explanation
High. Creating a `CREATE_COIN` output with an arbitrary memo to a fixed, public puzzle hash requires no special role, no on-chain approval, and no interaction with the victim — a single self-funded transaction suffices. Any node that has subscribed to or owns the targeted store will process the mirror automatically on its next sync cycle, since `is_launcher_tracked` only checks that the launcher_id is known locally, not that the mirror coin came from an authorized source.

### Recommendation
- Restrict which mirrors are trusted: require mirror-adding transactions to be authorized (e.g., signed by/associated with the store owner or an explicit allow-list), or otherwise validate the `launcher_id`/spender relationship before persisting a `Mirror` record in `dl_wallet_store.add_mirror`.
- Route all mirror/plugin URLs (`chia/data_layer/download_data.py::http_download`, `download_file`) through an SSRF-safe HTTP client that resolves the destination, rejects RFC1918/loopback/link-local/IPv6 ULA addresses, and pins the resolved IP before connecting.
- Enforce a scheme allow-list (e.g., `https://` only, or an explicit configured allow-list of hostnames) for mirror URLs before they are stored or fetched.
- Consider treating unexpected/duplicate mirror announcements for tracked launcher IDs from unrelated coins as suspicious and requiring explicit operator confirmation before they are added to the active subscription/download set.

### Proof of Concept
1. Determine any active DataLayer `launcher_id` that is publicly visible on-chain (store owners and subscribers routinely have this tracked).
2. From any wallet (no operator role, no relation to the target store), construct and broadcast a standard coin spend whose only requirement is spending one's own coin, with a `CREATE_COIN` condition to `create_mirror_puzzle().get_tree_hash()` and `memos = [victim_launcher_id, b"http://169.254.169.254/latest/meta-data/"]` — equivalent to calling `create_new_mirror(launcher_id=victim_launcher_id, amount=..., urls=[b"http://169.254.169.254/latest/meta-data/"], ...)` on an attacker-controlled `DataLayerWallet` instance targeting someone else's `launcher_id`.
3. Once the transaction confirms, any node tracking `victim_launcher_id` picks up the mirror via `coin_added` in `chia/data_layer/data_layer_wallet.py` and stores it via `dl_wallet_store.add_mirror`.
4. On the next `periodically_manage_data()` cycle, that node's `update_subscriptions_from_wallet()` pulls the malicious URL into its subscription server list, and `fetch_and_validate()`/`http_download()` issues an outbound GET to `http://169.254.169.254/latest/meta-data/` — observable via a packet capture on the victim node, exactly as demonstrated for the Lemur CRL/OCSP flow.

    async def add_mirror(self, mirror: Mirror) -> None:
        """
        Add a mirror coin to the DB
        """

        async with self.db_wrapper.writer_maybe_transaction() as conn:
            await conn.execute_insert(
                "INSERT OR REPLACE INTO mirrors VALUES (?, ?, ?, ?, ?)",
                (
                    mirror.coin_id,
                    mirror.launcher_id,
                    mirror.amount.stream_to_bytes(),
                    b"".join(
                        [uint16(len(url)).stream_to_bytes() + url for url in Mirror.encode_urls(mirror.urls)]
                    ),  # prefix each item with a length
                    1 if mirror.ours else 0,
                ),
            )

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
