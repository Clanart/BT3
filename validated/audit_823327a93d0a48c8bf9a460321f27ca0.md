## Title
Copilot conflict-resolution reassembly silently drops/misapplies unstaged merge conflicts when the model's hunk count doesn't match the file's actual conflict blocks - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The AI-assisted merge-conflict resolver (`resolveConflictsWithCopilot` → `parseCopilotConflictResolution` → `reassembleResolutions` → `reassembleResolvedFile`) validates the *shape* of the model's JSON response but never verifies that the *number* of returned hunk resolutions for a file matches the number of conflict blocks actually present in that file on disk. Reassembly matches resolutions to conflict blocks strictly by array order/index, so a mismatch causes conflict blocks to be silently dropped or filled with the wrong content, and the corrupted result is written straight to disk and staged when the user clicks "Continue Merge" - with no error, no warning, and no way for the user to notice before committing.

### Finding Description
`parseCopilotConflictResolution` validates each raw resolution entry structurally: that `path` is a non-empty string, `hunks` is a non-empty array, each hunk's `resolvedContent` is a string without leftover conflict markers, etc. [1](#0-0) 

Nowhere in this validation is `rawHunks.length` checked against the number of conflict hunks that were actually extracted from the file by `extractConflictHunks` (`ctx.hunks.length`), even though that value is available via the `IFileConflictContext` passed into the prompt. [2](#0-1) 

The reassembly step then splices resolutions into the file purely by encounter order, not by content or line correlation: [3](#0-2) 

Specifically, when the model returns fewer hunk resolutions than there are conflict blocks in the file, `hunkIndex < hunkResolutions.length` becomes false for the trailing blocks, so those conflict blocks are skipped entirely - both their markers *and* all of the surrounding "ours"/"theirs" content for that block are deleted from the reassembled file with no substitution and no error raised. Conversely, if hunks are returned out of order or one is missing from the middle, every subsequent hunk resolution silently gets applied to the wrong conflict block. The function's own doc comment concedes this design: "matched by order, not by line number." [4](#0-3) 

This mismatched/truncated result is treated as a fully valid resolution and, once the user clicks "Continue Merge", is written directly to the working tree and staged without further verification: [5](#0-4) 

The only pre-write guard is a check for whether the user manually resolved the file outside the dialog; there is no check that the written content is a faithful, complete merge of the original conflict. [6](#0-5) 

### Impact Explanation
The conflict resolution context that drives the model's output - file contents, "ours"/"theirs" commit messages, and referenced pull-request titles/bodies - originates from the two branches/commits being merged, i.e., content an attacker can fully control by authoring one side of the merge (a malicious branch, fork PR, or commit that the victim later merges/rebases/cherry-picks). Because the app performs no structural cross-check between the extracted conflict hunks and the model's returned hunks, any deviation - whether from adversarial prompt content designed to make the model omit or reorder hunks, or simply model unreliability on complex/large conflicts - results in code being silently deleted or spliced into the wrong location in the committed file. This is a case of the notary/processor-style hard-invariant violation from the report class ("trust an external producer's output count/order without validation") manifesting as silent corruption of what the user commits and potentially pushes, since the user is shown a "resolved" file and clicks through without inspecting every line against the original conflict markers.

### Likelihood Explanation
Triggering this does not require any privileged access: it only requires the victim to merge/rebase/cherry-pick a branch or PR whose conflicting content was authored by an untrusted party, and to accept the AI-suggested resolution (the default happy path presented by the dialog). No special local access, credentials, or social engineering beyond a normal merge workflow is needed; the flaw is a missing invariant check in first-party reassembly code, not a dependency issue, and is reachable through ordinary use of the "Resolve conflicts with Copilot" feature.

### Recommendation
In `reassembleResolutions`/`parseCopilotConflictResolution`, assert that `raw.hunks.length === ctx.hunks.length` for every non-action resolution before accepting it; if they diverge, treat the file as unresolved (fall back to `ICopilotSkippedFile`) rather than silently splicing a partial/misaligned set of hunks. Additionally, `reassembleResolvedFile` should fail loudly (throw a `CopilotValidationError`) rather than silently skip a conflict block when `hunkIndex >= hunkResolutions.length`, so a mismatch can never reach the on-disk write path.

### Proof of Concept
1. Craft a merge where the conflicting file contains two separate conflict blocks (e.g., two independent `<<<<<<<`/`=======`/`>>>>>>>` regions), with the second block containing security-relevant code (e.g., an auth check) that the attacker wants removed from the final merged file.
2. Because the prompt sent to Copilot includes attacker-controlled content (commit messages/PR body on the "theirs" side), craft that content to bias the model toward returning only one hunk resolution in the JSON response (`resolutions[0].hunks.length === 1`) while the file actually has two conflict blocks.
3. `parseCopilotConflictResolution` accepts this response since it only checks that `hunks` is non-empty, not that it matches `ctx.hunks.length`. [7](#0-6) 
4. `reassembleResolvedFile` splices the single resolution into the first conflict block and, upon reaching the second block, finds `hunkIndex (1) >= hunkResolutions.length (1)`, so it drops the second block's markers and both sides' content entirely - deleting the security-relevant code without any error. [8](#0-7) 
5. The result dialog shows a "successful" resolution; the user clicks "Continue Merge," `_applyCopilotConflictResolutions` writes the corrupted file to disk and stages it, and the merge is committed with the security check silently removed. [5](#0-4)
