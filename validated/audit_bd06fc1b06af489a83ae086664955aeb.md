This is a valid finding. The on-chain verifier confirms this design intentionally treats "not yet challenged" as the finality signal, with no separate check on the BoLD confirmation deadline (the ~6.4-day window during which a rival assertion can still be created). This is by design in this codebase's optimistic model (fishermen can veto/blacklist during the challenge period), similar to how the Orbit `verify_arbitrum_payload` path also accepts a node the instant it's created without any additional finality wait. However, given the review's decision standard, I need to assess whether this constitutes a valid finding under the bounty's scope.

### Title
Arbitrum BoLD consensus client accepts unconfirmed assertions as finalized state before the challenge period elapses - (File: modules/ismp/clients/arbitrum/src/lib.rs)

### Summary
`verify_arbitrum_bold` only requires two on-chain facts: (1) the assertion exists in the `_assertions` mapping, and (2) the assertion's parent's `secondChildBlock` word is zero at proof time. Neither condition proves the assertion has survived Arbitrum BoLD's confirmation/challenge period. A challenger can create a rival sibling assertion at any point up until the parent's confirmation deadline; until that happens, `secondChildBlock` reads as zero for every freshly created, still-contestable assertion.

### Finding Description
`compute_assertion_hash` derives the claim key and `get_value_from_proof` only confirms the assertion node was *created* in storage — assertions are inserted into `_assertions` immediately upon creation on L1, not upon confirmation. [1](#0-0) 
The only anti-fraud gate is reading the parent's packed `firstChildBlock | secondChildBlock` word and rejecting only if `secondChildBlock != 0`. [2](#0-1) 
This check proves "no rival sibling exists yet," not "the confirmation deadline has passed and no rival can ever be created." In Arbitrum BoLD, an assertion only becomes eligible for confirmation via `confirmAssertion` after `confirmPeriodBlocks` have elapsed from creation without a successful challenge, and a rival can be submitted any time before that deadline. There is no field read from the `AssertionNode` struct (e.g., confirmation status or created-at-block compared to a deadline) anywhere in `verify_arbitrum_bold`, and no such check exists upstream in `ArbitrumConsensusClient::verify_consensus`. [3](#0-2) 
The off-chain relayer code in `arb-host` mirrors exactly this same weak check when selecting which assertion to build a proof for — it only filters out assertions whose parent currently has a second child, with no deadline/confirmation-block comparison. [4](#0-3) 
Consequently, an unprivileged caller (anyone can submit a `ConsensusMessage`/`verify_consensus` call to the ISMP host with a `consensus_proof`) can construct a valid Merkle-Patricia proof, taken directly from L1 state right after an assertion is created, and have Hyperbridge accept that assertion's after-state as a trusted `StateCommitmentHeight` well before the real Nitro rollup's BoLD protocol would treat it as confirmed.

### Impact Explanation
This allows false remote-state acceptance: an attacker (or a party colluding with the assertion's proposer) can get a not-yet-finalized, still-challengeable Arbitrum state root registered as a trusted state commitment. Any ISMP messages, requests, responses, or Intent-Gateway settlements that rely on state/storage proofs against that height (e.g. proving a fill, an order, or a receipt on the "L2") can be settled before the real rollup has finalized the corresponding state, and if the assertion is later successfully challenged and overturned, the falsely-accepted commitment for that height remains in Hyperbridge's trusted store (no automatic retraction on losing a BoLD challenge) — the only recourse is a permissioned collator calling `veto_state_commitment`/`blacklist_arbitrum_claim`. This matches the bounty's "false proof/state acceptance" impact class and can lead to settlement using unfinalized/reorgable data.

### Likelihood Explanation
Every single BoLD assertion, the instant it is created, satisfies `secondChildBlock == 0` for its parent — there's nothing rare or hard to reach about this condition; it is the normal state of affairs for the entire confirmation window (multiple days on mainnet). Any actor who can generate a valid storage/account proof against the trusted L1 state root (which is itself untrusted input data, not a privileged action) can submit this consensus update. This is reachable through the standard, unprivileged `verify_consensus` entry point.

### Recommendation
Add an explicit confirmation-deadline check to `verify_arbitrum_bold`: read the `AssertionNode`'s creation block / confirmation deadline field (or the `RollupCore.confirmPeriodBlocks` plus the assertion's creation block) from storage via an additional proof, and require the trusted L1 height (`root`'s corresponding block) to be at or past that deadline, in addition to the current `secondChildBlock == 0` check. Alternatively, require an on-chain `Confirmed` status marker to be proven, matching Nitro's own `getAssertion(...).status == AssertionStatus.Confirmed` semantics, rather than approximating finality via absence-of-rival.

### Proof of Concept
1. Watch L1 for a fresh `AssertionCreated` event just after submission (before `confirmPeriodBlocks` L1 blocks have elapsed).
2. At the current L1 block, fetch: (a) the `_assertions[assertionHash]` storage proof (exists — accepted per line 339-340), (b) the `_assertions[parentAssertionHash]` slot-0 storage proof, whose `secondChildBlock` bytes are still `0` because no rival has been submitted yet.
3. Encode this into an `ArbitrumBoldProof` and submit it as the `consensus_proof` in an `ArbitrumUpdate` to `ArbitrumConsensusClient::verify_consensus` via the standard unprivileged ISMP consensus-update message path.
4. `verify_arbitrum_bold` (`modules/ismp/clients/arbitrum/src/lib.rs:301-379`) accepts it: assertion-exists check passes, `word[16..24] == 0` passes, and the after-state's `state_root`/`timestamp` are committed as a trusted `StateCommitmentHeight` for that height — despite the assertion still being fully within its open challenge window and possibly destined to be overturned.
