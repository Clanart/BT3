### Title
Tokenfactory Denom Allow-List (compliance restriction) Is Enforced Only in `MsgSend`/`MsgMultiSend`, Not in `MintCoins`/`SendCoinsFromModuleToAccount` — ([File: sei-cosmos/x/bank/keeper/msg_server.go], [File: sei-cosmos/x/bank/keeper/keeper.go], [File: x/tokenfactory/keeper/bankactions.go])

### Summary
Sei's `x/bank` module implements a per-denom `AllowList` restriction for `factory/...` denoms — a compliance/whitelist mechanism analogous to the Dinari blacklist — that is checked by `IsInDenomAllowList` only inside the `MsgSend` and `MsgMultiSend` message-server handlers. The check is missing from the underlying keeper-level transfer primitives (`SendCoinsFromModuleToAccount`, `MintCoins`, `BurnCoins`), which are the same primitives used by other modules (e.g. tokenfactory `MsgMint`/`MsgBurn`, IBC transfer completion, staking rewards, gov refunds) to move a restricted denom into or out of an arbitrary account. This mirrors the Dinari root cause: the transfer restriction is enforced at one entry point (regular transfer / `_beforeTokenTransfer` for `transfer`) but skipped for the mint/burn/module-to-account code paths that ultimately still place tokens into a user's balance.

### Finding Description
The compliance check lives in the `MsgSend`/`MsgMultiSend` handlers: [1](#0-0) 

It relies on `IsInDenomAllowList`, defined on `BaseSendKeeper`, which only inspects `factory/`-prefixed denoms against a stored allow list: [2](#0-1) 

However, `MintCoins`/`BurnCoins` on `BaseKeeper` perform no such check — they only validate module permissions and update supply before calling `AddCoins`/`SubUnlockedCoins` directly: [3](#0-2) [4](#0-3) 

The tokenfactory module's mint/burn flow calls these keeper primitives (`MintCoins` then `SendCoinsFromModuleToAccount`, or `SendCoinsFromAccountToModule` then `BurnCoins`) directly, entirely bypassing the `IsInDenomAllowList`/`BlockedAddr` gate that `MsgSend` enforces: [5](#0-4) 

This is structurally identical to the Dinari bug: a restriction (`transferRestrictor.requireNotRestricted` in Dinari, `IsInDenomAllowList`/`BlockedAddr` in Sei) is applied on the "plain transfer" path but skipped on the mint/burn and module-to-account paths that also change token ownership. Any module-to-account balance movement for a `factory/...` denom that does not go through `MsgSend`/`MsgMultiSend` (tokenfactory mint, and potentially other modules using `SendCoinsFromModuleToAccount`/`SendCoinsFromAccountToModule` for a restricted denom, e.g. IBC transfer completion or staking reward payout if such a denom were ever staked/rewarded) will silently ignore the denom's allow-list restriction.

### Impact Explanation
A denom issuer that relies on the `AllowList` feature to enforce compliance (only allow-listed addresses may hold the token, per the bank module's blocklist/allow-list documentation) cannot rely on that guarantee: any code path that credits or debits the restricted denom via `MintCoins`/`SendCoinsFromModuleToAccount`/`SendCoinsFromAccountToModule` bypasses the restriction entirely. This breaks the confidentiality/compliance invariant the allow-list is meant to provide and is a real logic flaw in the restriction enforcement layer, matching the "unauthorized transfer" impact category (a restricted token ending up in an unauthorized account through a path not covered by the intended access control).

### Likelihood Explanation
Reaching the tokenfactory mint path requires being the denom's admin, which reduces attacker-controlled exploitability for tokenfactory `MsgMint` specifically. However, the underlying keeper functions (`MintCoins`, `BurnCoins`, `SendCoinsFromModuleToAccount`, `SendCoinsFromAccountToModule`) are shared, generic bank primitives used across many modules; any current or future module path that moves a restricted `factory/` denom between a module account and a user account without going through `MsgSend`/`MsgMultiSend` will silently bypass the restriction. This is a structural gap in the enforcement architecture rather than a one-off bug, making the likelihood of some triggering path (present or introduced later) moderate.

### Recommendation
Move the `IsInDenomAllowList`/`BlockedAddr` restriction check down into the shared keeper primitives (`AddCoins`/`SubUnlockedCoins`, or at minimum `SendCoinsFromModuleToAccount`, `SendCoinsFromAccountToModule`, and `MintCoins`) rather than only at the `MsgSend`/`MsgMultiSend` handler layer, mirroring the Dinari fix recommendation to check the restriction "when burning and minting" rather than only on ordinary transfers. Alternatively, provide an explicit, clearly documented restriction-check hook that every module crediting/debiting a restricted denom must call.

### Proof of Concept
Not independently confirmed against a live path outside tokenfactory mint/burn within the scope of this review; the concrete demonstrated gap is:
1. Denom admin creates a `factory/{admin}/xyz` denom and sets `SetDenomAllowList` restricting holders to a specific set of addresses. [6](#0-5) 
2. Admin (or any code path with `Minter` permission on the tokenfactory module account) calls `mintTo`, which invokes `bankKeeper.MintCoins` then `bankKeeper.SendCoinsFromModuleToAccount` directly to any address, including one not on the denom's allow list — no `IsInDenomAllowList` check occurs in this path. [7](#0-6) 
3. Contrast with the same denom being sent via `MsgSend`, where an out-of-allow-list recipient is correctly rejected. [8](#0-7) 

This confirms the allow-list restriction is not uniformly enforced across all balance-crediting code paths, the same architectural flaw as the Dinari finding.

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

func (k BaseKeeper) MintCoins(ctx sdk.Context, moduleName string, amounts sdk.Coins) error {
	addFn := func(ctx sdk.Context, moduleName string, amounts sdk.Coins) error {
		acc := k.ak.GetModuleAccount(ctx, moduleName)
		if acc == nil {
			return fmt.Errorf("module account for %s not found", moduleName)
		}
		return k.AddCoins(ctx, acc.GetAddress(), amounts, true)
	}

	err := k.createCoins(ctx, moduleName, amounts, addFn)
	if err != nil {
		return err
	}
	return nil
}

func (k BaseKeeper) destroyCoins(ctx sdk.Context, moduleName string, amounts sdk.Coins, subFn SubFn) error {
	acc := k.ak.GetModuleAccount(ctx, moduleName)
	if acc == nil {
		panic(sdkerrors.Wrapf(sdkerrors.ErrUnknownAddress, "module account %s does not exist", moduleName))
	}

	if !acc.HasPermission(authtypes.Burner) {
		panic(sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "module account %s does not have permissions to burn tokens", moduleName))
	}

	err := subFn(ctx, moduleName, amounts)
	if err != nil {
		return err
	}

	for _, amount := range amounts {
		supply := k.GetSupply(ctx, amount.GetDenom())
		supply = supply.Sub(amount)
		k.SetSupply(ctx, supply)
	}

	logger.Info("burned tokens from module account", "amount", amounts, "from", moduleName)

	// emit burn event
	ctx.EventManager().EmitEvent(
		types.NewCoinBurnEvent(acc.GetAddress(), amounts),
	)
	return nil
}

func (k Keeper) mintTo(ctx sdk.Context, amount sdk.Coin, mintTo string) error {
	// verify that denom is an x/tokenfactory denom
	_, _, err := types.DeconstructDenom(amount.Denom)
	if err != nil {
		return err
	}

	logger.Info("Minting amount for module", "amount", amount, "module", types.ModuleName)
	err = k.bankKeeper.MintCoins(ctx, types.ModuleName, sdk.NewCoins(amount))
	if err != nil {
		return err
	}

	addr, err := sdk.AccAddressFromBech32(mintTo)
	if err != nil {
		return err
	}

	logger.Info("Sending minted amount to addr", "amount", amount, "addr", addr)
	return k.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName,
		addr,
		sdk.NewCoins(amount))
}

func (k Keeper) burnFrom(ctx sdk.Context, amount sdk.Coin, burnFrom string) error {
	// verify that denom is an x/tokenfactory denom
	_, _, err := types.DeconstructDenom(amount.Denom)
	if err != nil {
		return err
	}

	addr, err := sdk.AccAddressFromBech32(burnFrom)
	if err != nil {
		return err
	}

	logger.Info("Sending amount to module from account", "amount", amount, "module", types.ModuleName, "account", addr)
	err = k.bankKeeper.SendCoinsFromAccountToModule(ctx,
		addr,
		types.ModuleName,
		sdk.NewCoins(amount))
	if err != nil {
		return err
	}

	logger.Info("Burning amount from module", "amount", amount, "module", types.ModuleName)
	return k.bankKeeper.BurnCoins(ctx, types.ModuleName, sdk.NewCoins(amount))
}
