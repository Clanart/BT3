### Title
Unbounded attacker-controlled allocation in `ThresholdKeys::read` via `Interpolation::Constant` length - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` trusts the serialized `n` (u16) field and immediately performs `Vec::with_capacity(usize::from(n))` when the interpolation tag is `0` (`Constant`), before any element is read or any parameter is validated. An unprivileged party feeding untrusted bytes to `ThresholdKeys::read` can force a ~2 MiB allocation with a ~12-byte input, with no bound, authentication, or semantic check performed first. This is the direct Serai analog of the Scriban `string.pad_left`/`pad_right` uncontrolled-allocation class: a caller-supplied size parameter drives a raw allocation that occurs before any validation or limit enforcement.

### Finding Description
In `ThresholdKeys::read`, the header fields `t`, `n`, `i` are read first, then a single tag byte selects the interpolation mode. For tag `0` the code executes:

```rust
// crypto/dkg/src/lib.rs:607-613
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));
  for _ in 0 .. n {
    res.push(C::read_F(reader)?);
  }
  res
}),
```

`n` is fully attacker-controlled (`u16`, max 65535). `Vec::with_capacity` commits `n * size_of::<C::F>()` bytes (32 B/scalar → ~2 MiB for `n = 0xFFFF`) in a single allocation before the first `read_F` is attempted. If the stream is short, `read_F` fails, but the allocation has already been made. Additionally, the later loop at `crypto/dkg/src/lib.rs:620-623` inserts `n` entries into a `HashMap` of verification shares — again driven solely by `n`, with `ThresholdParams::new` validation applied only at the very end (line 626), after all allocation and parsing work is done. The same ordering issue exists for `n` scalars then `n` points being read unconditionally (~4-5 MiB total parsed structure for a maximally padded input).

This contrasts with e.g. `networks/ethereum/src/machine.rs:51-60`, where Serai explicitly chunked reads to bound the DoS surface ("A valid DoS would be to claim a 4 GB data... We read this in 1 KB chunks"), and `coordinator/src/tributary/transaction.rs:286`, which checks `commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT` before allocating. `ThresholdKeys::read` has no equivalent guard.

### Impact Explanation
Any component that deserializes `ThresholdKeys` from data influenced by an unprivileged party (replication/resync of key material, backup restore, share-transfer messages, or any of the reachable `read` entry points enumerated for untrusted bytes) can be forced to allocate up to ~2 MiB per call in the `with_capacity` step alone — before authentication or `ThresholdParams::new` rejects the parameters. Repeated calls (e.g., one per incoming message) translate trivial input into sustained multi-MiB-per-message allocation churn, causing memory exhaustion / `OOM` denial of service. This is a resource-exhaustion analog (CWE-770), not key recovery or forgery.

### Likelihood Explanation
Reachability requires the attacker to cause a victim to run `ThresholdKeys::read` over bytes the attacker controls. Within Serai, `ThresholdKeys::read` is a public deserialization API in-scope for untrusted input. The attack requires no key share, no valid signature, and no protocol participation — the allocation happens on the 7th-12th byte of the stream and succeeds even if deserialization ultimately errors. Impact is bounded per-call (~2 MiB eager + up to ~4-5 MiB if the attacker supplies the full body), so this is a Medium rather than High severity DoS.

### Recommendation
Validate `n` before allocating: check `t >= 1`, `n >= t`, `i <= n`, and an explicit upper bound (e.g., the maximum participant count the deployment supports, typically far below `u16::MAX`) immediately after reading `(t, n, i)` and before the interpolation branch. Prefer `Vec::new()` + `push` (or a chunked-read pattern like `Call::read` in `networks/ethereum/src/machine.rs:53-60`) over `with_capacity(n)` so allocation grows only with bytes actually present. Apply the same ordering to the `verification_shares` loop.

### Proof of Concept
Conceptually:

```rust
// 4-byte curve ID len || C::ID || t || n || i || interpolation tag
let mut bytes = vec![];
bytes.extend(4u32.to_le_bytes());          // C::ID length prefix (for a 4-byte ID curve)
bytes.extend(b"TEST");                     // matching C::ID
bytes.extend(1u16.to_le_bytes());          // t = 1
bytes.extend(0xFFFFu16.to_le_bytes());     // n = 65535 (attacker-controlled)
bytes.extend(1u16.to_le_bytes());          // i = 1
bytes.push(0u8);                           // Interpolation::Constant tag

// Vec::with_capacity(65535) allocates ~2 MiB here, before the first read_F fails
let _ = ThresholdKeys::<Ed25519>::read(&mut bytes.as_slice());
```

Each ~13-byte input forces a ~2 MiB eager allocation that is only released on error return; issuing these in a loop produces continuous allocator pressure with ~150,000x byte amplification on the allocation step.
