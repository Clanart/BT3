### Title
Auctioneer signature only binds the raw `SearcherSig` bytes, not the auction bid content — and the V2 EIP-712 struct excludes `MaxGasPrice` from what the searcher signs, allowing bid fields to be forged without invalidating either signature - (File: kaiax/auction/eip712.go, kaiax/auction/bid.go)

### Summary
Kaia's gasless-auction `Bid` scheme uses two independent signatures analogous to the ERC-4337 "two validators" pattern described in the report: a `SearcherSig` that is supposed to authorize the full `AuctionTx` content, and an `AuctioneerSig` that co-signs to admit the bid into the block. Just as the enable-mode signature in the report covers `(validator, initData)` but not `moduleType`, the Kaia V2 auction EIP-712 struct hash covers `targetTxHash, blockNumber, sender, to, nonce, bid, callGasLimit, data` but **not** `maxGasPrice`, even though `BidData.MaxGasPrice` is a live field carried in every `Bid`. On top of that, the `AuctioneerSig` does not sign the `AuctionTx` fields at all — it only signs the raw `SearcherSig` byte blob via `GetEthSignedMessageHash()`. This means whichever fields are excluded from the searcher's EIP-712 struct are not bound by *either* signature, letting a bid submitter or relayer forge those fields post-signature without invalidating admission checks.

### Finding Description
`Bid.EncodeData()` (the V2/default struct used whenever `auctionEntryPointVersion != AuctionVersionV3`) deliberately omits `MaxGasPrice` from the hashed data: [1](#0-0) 

Only the V3 variant, `bidV3.EncodeData()`, includes it: [2](#0-1) 

The version used for verification is chosen from the pool's configured `auctionEntryPointVersion`, not from the bid itself, in `ValidateSearcherSig`: [3](#0-2) 

Because `GetHashTypedData` falls back to the V2 (no-`MaxGasPrice`) struct hash for any version other than exactly `AuctionVersionV3`: [4](#0-3) 

any node/environment running with `AuctionVersionV2` will validate `SearcherSig` **without** binding `BidData.MaxGasPrice` in any way. A searcher (or anyone relaying/mutating the RLP/JSON bid payload before it is admitted to the pool) can therefore change `MaxGasPrice` to any value after producing `SearcherSig`, and `ValidateSearcherSig` will still pass.

Compounding this, `AuctioneerSig` is not a co-signature over the `AuctionTx` fields at all — it signs only the byte-string of `SearcherSig`: [5](#0-4) [6](#0-5) 

and admission logic (`validateBidSigs`) checks only these two independent signatures, with no cross-check binding `AuctioneerSig` to the actual `AuctionTx` content beyond the `SearcherSig` blob: [7](#0-6) 

This is structurally identical to the reported bug class: two independent signers/validators are used to admit an action, but the fields that determine the actual semantics/limits of that action (`moduleType` in the report; `MaxGasPrice` here) are not covered by the signature that is supposed to authorize them, so the field can be forged by the transaction/bid submitter without invalidating either signature.

### Impact Explanation
`MaxGasPrice` is intended to represent a searcher-approved gas price ceiling for their auction call (per the V3 typehash addition and the `IAuctionEntryPointAuctionTx.MaxGasPrice` field surfaced on-chain). If the auctioneer or the entry-point contract logic relies on the searcher having cryptographically committed to this cap (e.g., to prevent the block proposer / relayer from executing the auction call at an inflated gas price and draining more value from the searcher, or to enforce a fairness/ordering rule in the auction), then under the V2 configuration this cap is not actually authorized by the searcher's signature. A submitter (which per the scope is an allowed unprivileged actor — "auction bidder") can tamper with `MaxGasPrice` post-signing without invalidating admission into the bid pool, potentially causing unauthorized fee/gas-cost exposure for the searcher or bypassing an auction fairness constraint the field was meant to enforce. This is a concrete instance of "fee or fee-delegation abuse" / "auction settlement" manipulation reachable directly from a single submitted bid via public RPC (`auction_sendBid`/`SubmitBid`).

### Likelihood Explanation
This requires only a single call to the exposed `SubmitBid` RPC, or interception/relay of an already-signed bid (a normal, permitted flow for auction bidders) while the deployed `AuctionEntryPoint` is at version V2 (`AuctionVersionV2 = "0.0.1"`), which appears to be the currently-used/default version referenced throughout the test suite (`testAuctionEntryPointVersion = auction.AuctionVersionV2` patterns seen in tests). No privileged access, node compromise, or consensus-message manipulation is needed — an ordinary bidder can exploit the gap between what is signed and what is transmitted.

### Recommendation
Include `MaxGasPrice` (and any other economically meaningful bid field) in the V2 EIP-712 struct hash as well, or reject/zero out `MaxGasPrice` entirely when running against a V2 entry point so there is no unsigned-but-consumed field. More generally, have `AuctioneerSig` bind the full `AuctionTx` content (via the same EIP-712 struct, or by re-hashing all fields) rather than only the opaque `SearcherSig` bytes, so that no bid field can be altered after either signature is produced without invalidating both signatures — mirroring the report's recommendation to include the previously-uncovered field (`moduleType`) in the signed hash.

### Proof of Concept
1. Node/pool configured with `auctionEntryPointVersion = AuctionVersionV2` ("0.0.1").
2. Searcher builds `BidData{TargetTxHash, BlockNumber, Sender, To, Nonce, Bid, CallGasLimit, Data, MaxGasPrice: X}` and computes `SearcherSig = sign(GetHashTypedData(chainId, entryPoint, "0.0.1"))`, which per `Bid.EncodeData()` never includes `MaxGasPrice`.
3. Submitter changes `MaxGasPrice` from `X` to `Y` in the `BidInput`/`Bid` payload before or after auctioneer co-signing.
4. `bp.validateBidSigs` calls `ValidateSearcherSig` (still succeeds — `MaxGasPrice` not part of the digest) and `ValidateAuctioneerSig` (still succeeds — it only checks the `SearcherSig` bytes, unrelated to `MaxGasPrice`), so the bid with the tampered `MaxGasPrice = Y` is accepted into the bid pool and can win the auction / be forwarded to the `AuctionEntryPoint.call`. func (b *Bid) ValidateSearcherSig(chainId *big.Int, verifyingContract common.Address, version string) error {
```go
	if chainId == nil {
		return ErrNilChainId
	}

	if common.EmptyAddress(verifyingContract) {
		return ErrNilVerifyingContract
	}

	digest := b.GetHashTypedData(chainId, verifyingContract, version)

	recoveredSender, err := getSigner(b.SearcherSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover searcher sig: %v", err)
	}

	if recoveredSender != b.Sender {
		return fmt.Errorf("invalid searcher sig: expected %v, calculated %v", b.Sender.String(), recoveredSender.String())
	}

	return nil
}
```

```go
func (b *Bid) ValidateAuctioneerSig(auctioneer common.Address) error {
	digest := b.GetEthSignedMessageHash()

	recoveredAuctioneer, err := getSigner(b.AuctioneerSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover auctioneer sig: %v", err)
	}

	if recoveredAuctioneer != auctioneer {
		return fmt.Errorf("invalid auctioneer sig: expected %v, calculated %v", auctioneer.String(), recoveredAuctioneer.String())
	}

	return nil
}
```

```go
func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}
```
