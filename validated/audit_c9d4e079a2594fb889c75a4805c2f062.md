## Title
Escrow accounting in `IntentGatewayV2` (Tron build) credits declared `order.inputs` amount instead of the actual ERC20/TRC20 amount received, allowing phantom escrow inflation and drain of other users' pooled tokens - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` pulls tokens with `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits the *declared* (fee-reduced) amount into the `_orders[commitment][token]` accounting map, without ever checking the gateway's actual token balance before/after the transfer. [1](#0-0) 
This is the same broken invariant as the MonoX report: minted/credited "shares" are derived from a caller-declared amount rather than the verified balance delta of the transfer.

### Finding Description
`evm/src/apps/IntentGatewayV2.sol` (the primary EVM contract) was hardened against fee-on-transfer / non-standard ERC20 tokens by recording `balBefore`/`balAfter` deltas and mutating `order.inputs[i].amount` to the *actually received* value before it is used to compute the commitment and to credit escrow: [2](#0-1) 

The Tron fork of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, still uses the old pattern: it calls `safeTransferFrom` for the declared `order.inputs[i].amount`, then separately adds `reducedInputs[i].amount` (also derived from the declared amount, only reduced by the protocol fee) into the shared escrow ledger, with no `balanceOf` check: [1](#0-0) 

The same unverified pattern is repeated in the predispatch/CallDispatcher branch, where `dust = balance - requiredAmount` is computed but the escrow credit still uses `reducedInputs[i].amount` derived from the user-declared amount, not from what was actually swept back: [3](#0-2) 

Crucially, `_orders[commitment][token]` is purely an accounting entry — the contract holds one *pooled* ERC20/TRC20 balance per token across all orders. `withdraw()` pays out of that shared pool based on the ledger, not on any per-order isolated balance: [4](#0-3) 

If a user places an order using a token whose `transferFrom` can be made to move less than the requested amount (fee-on-transfer token, or an attacker-deployed/malicious token used as an input asset — same primitive as the `EvilERC20` in the referenced report), the gateway will credit the *full declared* amount to `_orders[commitment][token]` while its real token balance only increased by the smaller actual transfer amount. When that order is later filled/redeemed via `onAccept` → `withdraw()`, the contract pays out the phantom (over-credited) amount from the shared pool — funds that in reality belong to other users' still-escrowed balances of the same token. [5](#0-4) 

### Impact Explanation
This directly violates the Hyperbridge impact gate: "bridged assets, order escrow, refunds ... must move exactly once and only to the rightful beneficiary and amount." An attacker can inflate their own escrow entry beyond what they actually deposited, and upon settlement the gateway transfers that inflated amount out of the token's pooled balance — effectively stealing from other users' escrowed funds of the same token, or causing later legitimate withdrawals/cancellations to revert due to insufficient contract balance (fund lock). This requires no relayer/prover/admin compromise — it is reachable by any unprivileged user who places an order using a token with non-standard transfer semantics (fee-on-transfer, or one that they deployed themselves and that Hyperbridge later lists/accepts as an input asset).

### Likelihood Explanation
Likelihood is high for any deployment where `evm/tron/contracts/apps/IntentGatewayV2.sol` is live, since `placeOrder` is a fully public, unauthenticated entry point and the attacker only needs to supply an ERC20/TRC20 token of their choosing as `order.inputs[i].token`. The corresponding EVM contract already had this exact class of bug fixed (fee-on-transfer tests exist), strongly indicating the Tron variant is a stale, unpatched fork of the vulnerable code path.

### Recommendation
Apply the same balance-delta pattern used in `evm/src/apps/IntentGatewayV2.sol` (`balBefore`/`balAfter` around `safeTransferFrom`, mutate `order.inputs[i].amount` to the actual received amount before it is used to compute `reducedInputs`/escrow credit and the commitment hash) to `evm/tron/contracts/apps/IntentGatewayV2.sol`, in both the plain-transfer branch and the predispatch/CallDispatcher sweep branch.

### Proof of Concept
1. Attacker deploys a custom TRC20 token `EvilToken` whose `transferFrom` always moves `1` wei regardless of the `value` argument (mirrors `EvilERC20` in the reference report).
2. Attacker calls `placeOrder` with `order.inputs = [{token: EvilToken, amount: 1000e18}]`, approving the gateway for `1000e18`.
3. Inside `placeOrder`, `IERC20(EvilToken).safeTransferFrom(msg.sender, address(this), 1000e18)` succeeds but only transfers `1` wei to the gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol:453`).
4. The gateway nevertheless credits `_orders[commitment][EvilToken] += reducedInputs[i].amount` (≈`1000e18` minus protocol fee) (`evm/tron/contracts/apps/IntentGatewayV2.sol:457`).
5. A solver fills the order believing `~1000e18` `EvilToken` is escrowed; upon settlement `onAccept`/`withdraw()` attempts to transfer the credited amount out of the gateway's pooled `EvilToken` balance (`evm/tron/contracts/apps/IntentGatewayV2.sol:682-705`), which is actually funded by other legitimate users' escrowed `EvilToken` deposits, resulting in fund loss/lock for those users or a revert that traps unrelated orders.

**Note**: I could not fully verify the on-chain deployment status of `evm/tron/contracts/apps/IntentGatewayV2.sol` (whether it is actively used in production vs. a build artifact/fork awaiting the same fix as the main EVM contract) due to index limitations; a Devin session with full repo/build-config access would be needed to confirm deployment scope before treating this as a confirmed production finding.
