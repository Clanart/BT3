Audit Report

## Title
Vote account `pending_delegator_rewards` reservation can permanently lock lamports when active delegated stake drops to zero before distribution - ([File: programs/vote/src/vote_state/mod.rs])

## Summary
`pending_delegator_rewards` on `VoteStateV4` is incremented by `add_pending_delegator_rewards` when block-revenue commission accrues, and the `withdraw` instruction refuses to close the vote account or withdraw below `rent_exempt_minimum + pending_delegator_rewards` while this field is non-zero [1](#0-0) [2](#0-1) . The only mechanism that decrements this reservation, `calculate_block_reward`, unconditionally returns `0` whenever `total_active_stake` for that vote account is `0`, leaving `pending_delegator_rewards` unchanged and effectively undistributable [3](#0-2) .

## Finding Description
`total_active_stake` is looked up from `reward_epoch_delegated_stakes.delegated_stakes` keyed by the vote account's pubkey, defaulting to `0` when absent [4](#0-3) . When `total_active_stake == 0`, the function returns `0` for every delegation to that vote account, meaning no lamports are ever attributed against `pending_delegator_rewards` for that vote account in that reward computation, and I found no other call site in `calculation.rs` or elsewhere that decrements `pending_delegator_rewards` independent of this per-delegation attribution. The `withdraw` guard in `programs/vote/src/vote_state/mod.rs` then blocks the authorized withdrawer from closing the account (`pending_delegator_rewards > 0` check) or from withdrawing below `rent_exempt_minimum + pending_delegator_rewards`, with no alternate instruction in the vote program to sweep or reclaim this reservation.

## Impact Explanation
This falls within the "runtime/accounts fund loss" scope: lamports equal to `pending_delegator_rewards` become permanently locked in the vote account's balance, unreachable by the authorized withdrawer, with the exact corrupted/stuck value being the vote account's lamport balance gated by the `pending_delegator_rewards` field in `VoteStateV4`.

## Likelihood Explanation
The condition requires SIMD-0123 block-revenue-sharing to be active and a vote account to accrue `pending_delegator_rewards` while having (or later having) zero active delegated stake in the rewarded epoch — e.g., all delegators undelegate in the same epoch, or the account earns commission before any stake is delegated to it. This is triggerable through ordinary, unprivileged staker actions (stake deactivation/withdrawal) and does not require a malicious validator, privileged key, or trusted process, matching the required unprivileged-attacker constraint.

## Recommendation
Add a mechanism to redistribute, reclaim, or burn `pending_delegator_rewards` to the authorized withdrawer/collector when `total_active_stake` for the vote account is `0` at distribution time, or prevent the reservation from growing when there is no active stake available to eventually receive it.

## Proof of Concept
1. Create a vote account, delegate stake, and accrue `pending_delegator_rewards` via block-revenue commission (`add_pending_delegator_rewards`) [1](#0-0) .
2. Have all delegators fully deactivate/withdraw stake so `reward_epoch_delegated_stakes.delegated_stakes` has no non-zero entry for this vote account by the reward epoch boundary.
3. At the epoch boundary, `calculate_block_reward` returns `0` for this vote account regardless of the size of `pending_delegator_rewards` [5](#0-4) , leaving the field unchanged.
4. Call `Withdraw` for the full balance; the instruction fails with `InstructionError::InsufficientFunds` per the `pending_delegator_rewards > 0` check, matching the existing test `test_withdraw_pending_delegator_rewards` [6](#0-5) , which only clears the field manually rather than through any on-chain distribution path.

        }

        let reject_active_vote_account_close = vote_state
            .epoch_credits()
            .last()
            .map(|(last_epoch_with_credits, _, _)| {
                let current_epoch = clock.epoch;
                // if current_epoch - last_epoch_with_credits < 2 then the validator has received credits
                // either in the current epoch or the previous epoch. If it's >= 2 then it has been at least
                // one full epoch since the validator has received credits.
                current_epoch.saturating_sub(*last_epoch_with_credits) < 2
            })
            .unwrap_or(false);

        if reject_active_vote_account_close {
            return Err(VoteError::ActiveVoteAccountClose.into());

            // Deinitialize upon zero-balance
            VoteStateHandler::deinitialize_vote_account_state(&mut vote_account, target_version)?;
        }

            .checked_add(pending_delegator_rewards)
